## Title
Vote-transaction "fast lane" classification is based on unauthenticated packet shape, allowing unprivileged flooding of the reserved vote-cost budget - (File: `perf/src/sigverify.rs`, `runtime-transaction/src/runtime_transaction/transaction_view.rs`)

## Summary
This is a structural analog of the ZealousSwap bug: instead of trusting a caller-supplied `actualUser` address for fee-discount eligibility without checking that it is really the caller, Agave trusts a purely *structural* classification (`is_simple_vote_transaction`) to grant a transaction access to the privileged "vote" processing/cost lane, without verifying that the transaction is an authentic, would-succeed vote from an authorized voter.

## Finding Description
`is_simple_vote_transaction_view()` classifies a transaction as a "simple vote" purely from shape: ≤2 signatures, legacy message, exactly one instruction, and that instruction's program id equal to `vote::id()`. [1](#0-0) 

This classification is computed and stamped onto the packet (`PacketFlags::SIMPLE_VOTE_TX`) during sigverify, before/independent of whether the instruction data is a legitimate `VoteInstruction`/`TowerSync` payload or whether the signer is an authorized voter for the referenced vote account: [2](#0-1) 

The same "is it a vote" boolean is later re-derived (or accepted as a caller-supplied override, `Option<bool>`) when building the cached transaction metadata used by the runtime/cost-model: [3](#0-2) 

This `is_simple_vote_transaction` flag is exactly analogous to `actualUser` in the ZealousSwap report: it is a self-declared/derived attribute that grants preferential treatment (being routed through the dedicated vote pipeline and charged against the separate `WouldExceedMaxVoteCostLimit` budget instead of `WouldExceedMaxBlockCostLimit`), yet nothing in the check binds it to an actual, valid, authorized vote: [4](#0-3) [5](#0-4) 

Any unprivileged holder of an arbitrary keypair (no stake required) can craft a transaction that: (1) has 1–2 valid signatures from throwaway keys they control, (2) is a legacy message, (3) has exactly one instruction whose `program_id` is `vote::id()`, and (4) carries arbitrary/garbage instruction data. Because ed25519 signature verification only checks that the signature matches the *declared* signer pubkeys — not that the signer is an authorized voter, or that the instruction data is a valid vote — this packet passes `verify_packet()` and is marked `SIMPLE_VOTE_TX`, entering the vote-only processing path (`vote_worker.rs`, `VotePacketReceiver`) and being cost-accounted under the reserved vote-cost limit rather than the general block-cost limit.

## Impact Explanation
Because the vote lane is a small, specifically-reserved resource (dedicated cost bucket, dedicated buffering/queue in `vote_worker.rs`/`VoteStorage`) meant only for genuine consensus votes, flooding it with cheap, self-signed "vote-shaped" garbage transactions lets an unprivileged remote attacker consume/exhaust that reserved capacity without needing valid stake or an authorized-voter key. This can crowd out or delay legitimate validator votes from being scheduled/packed, degrading vote propagation and, at scale, threatening timely finality/liveness — this falls under the "non-RPC remote exhaustion/crash" and potentially "consensus halt" categories in the accepted impact list, and requires no malicious-peer/validator/admin assumption (any external unprivileged sender can do this over TPU-vote/gossip channels).

## Likelihood Explanation
Likelihood is moderate-to-high in terms of ease of construction (crafting a legacy, single-instruction, `vote::id()`-addressed transaction with throwaway keys is trivial and cheap — no stake, no real vote data needed), but the actual DoS magnitude depends on details not fully confirmed from the available index: the concrete numeric size of `max_vote_cost_limit` versus `max_block_cost_limit`, and whether additional downstream filters (e.g., account-lock validation against a real vote account, replay-protection, or admission control in `vote_packet_receiver.rs`/`VoteStorage`) further restrict or dedupe such garbage before it reaches the cost tracker. I was not able to locate the exact vote-cost-limit constant or the full de-duplication/admission logic within the indexed portion of `cost-model/src/cost_tracker.rs` in the time available, so the precise severity (temporary lane congestion vs. sustained validator-vote starvation) could not be fully verified from local code alone.

## Recommendation
Do not grant the vote-lane classification (and its separate, more permissive cost budget) based solely on transaction shape. Before classifying/admitting a transaction as `is_simple_vote_transaction`/`SIMPLE_VOTE_TX`:
- Additionally validate that the instruction data deserializes into a legitimate `VoteInstruction`/`TowerSync` variant.
- Cross-check that the signing key(s) correspond to the vote account's current `authorized_voter` (or otherwise rate-limit/charge non-authorized-voter "vote-shaped" transactions at the regular, non-discounted cost rate) before admitting them into the reserved vote pipeline/cost bucket.
- Consider decoupling the `Option<bool>` override path in `from_sanitized_transaction_view`/`RuntimeTransaction::try_from` so that only trusted internal callers (e.g., the validator's own tower/vote generation) can force `is_simple_vote_tx = true`; externally-received packets should always go through the full structural+semantic check.

## Proof of Concept
1. Generate an ephemeral keypair `K` (no stake, no relation to any real validator).
2. Construct a legacy `Transaction` with a single instruction whose `program_id` is `solana_sdk_ids::vote::id()`, arbitrary/garbage instruction `data`, and sign it with `K` (1–2 signatures).
3. Send this transaction packet directly to the TPU-vote port (bypassing any RPC-level rate limiting meant for regular transaction submission).
4. Observe in `perf/src/sigverify.rs::verify_packet` that `is_simple_vote_transaction_view` returns `true` purely from shape (see the structural checks at [1](#0-0) ), the ed25519 check passes (self-signed by `K`), and the packet is flagged `SIMPLE_VOTE_TX` and routed to `VoteWorker`/`VoteStorage` and accounted against the vote-cost bucket instead of the standard block-cost bucket.
5. Repeat at scale with many throwaway keypairs to occupy the reserved vote lane's capacity/cost budget, independent of any real stake or authorized-voter status.

fn is_simple_vote_transaction_view<D: TransactionData>(view: &SanitizedTransactionView<D>) -> bool {
    // vote could have 1 or 2 sigs; zero sig has already been excluded by sanitization.
    if view.num_signatures() > 2 {
        return false;
    }

    // simple vote should only be legacy message
    if !matches!(view.version(), TransactionVersion::Legacy) {
        return false;
    }

    // skip if has more than 1 instruction
    if view.num_instructions() != 1 {
        return false;
    }

    let mut instructions = view.instructions_iter();
    let Some(instruction) = instructions.next() else {
        return false;
    };
    if instructions.next().is_some() {
        return false;
    }

    let program_id_index = usize::from(instruction.program_id_index);
    let Some(program_id) = view.static_account_keys().get(program_id_index) else {
        return false;
    };

    *program_id == solana_sdk_ids::vote::id()
}

fn is_simple_vote_transaction<D: TransactionData>(
    transaction: &SanitizedTransactionView<D>,
) -> bool {
    let signatures = transaction.signatures();
    let is_legacy_message = matches!(transaction.version(), TransactionVersion::Legacy);
    let instruction_programs = transaction
        .program_instructions_iter()
        .map(|(program_id, _ix)| program_id);

    is_simple_vote_transaction_impl(signatures, is_legacy_message, instruction_programs)
}
