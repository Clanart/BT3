`Verifier::sign_optimistic_payout` (core/src/verifier.rs) bounds `output_amount > self.config.protocol_paramset().bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT` but never checks `output_amount` against any Citrea-recorded withdrawal amount, only against `withdrawal_utxo == input_outpoint`. Can an attacker register a withdrawal on Citrea for amount A, then call the aggregator's `optimistic_payout` gRPC with the same `input_outpoint` but a different `output_amount` B < bridge_amount - NON_EPHEMERAL_ANCHOR_AMOUNT, causing the move-to-vault UTXO to release B sats to the attacker while Citrea's withdrawal record and burn accounting reflect A? Binding: the amount Citrea's Bridge contract recorded as withdrawn == the amount actually released from the move-to-vault UTXO's `bridge_amount`. Impact: BTC leaving a move-to-vault UTXO without a matching fronted withdrawal (custody violation) if A != B is never rejected. Proof idea: cargo test with `MockCitreaClient` recording a withdrawal amount, then calling `sign_optimistic_payout` with a mismatched `output_amount`, asserting whether the verifier still signs.
