`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs) builds a Payout tx with output 0 = user payout, output 1 = `anchor_output(NON_EPHEMERAL_ANCHOR_AMOUNT)`, output 2 = OP_RETURN(operator xonly pk), signed via `set_p2tr_key_spend_witness(&user_sig, 0)` under `SinglePlusAnyoneCanPay`, then `Operator::withdraw` calls `self.rpc.fund_raw_transaction(...FundRawTransactionOptions{ add_inputs: Some(true), change_position: Some(1), ...})` on the already-signed tx. Can an attacker-chosen `out_amount`/`out_script_pubkey` combination, once ANYONECANPAY-signed, be re-targeted by the RBF/fund_raw_transaction step (which adds operator inputs/change) in a way that shifts operator change into the OP_RETURN slot or invalidates the anchor's assumed fixed index, so the signed output-0 commitment no longer matches the final broadcast transaction's fee structure? Binding: the output_txout committed under the user's SinglePlusAnyoneCanPay signature at output index 0 == output index 0 of the transaction actually funded and broadcast by `fund_raw_transaction`. Impact: BTC leaving a move-to-vault-funded payout into fees rather than the withdrawer, or an honest operator's funded payout becoming invalid after RBF funding reorders outputs. Proof idea: cargo test with regtest bitcoind funding a payout tx with `change_position: Some(1)`, asserting the final broadcast tx's output 0 is byte-identical to what was signed.
