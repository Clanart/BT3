Based on my investigation, I found a strong structural analog in Agave's Tower BFT switch-threshold / vote-threshold consensus logic.

### Title
Vote/switch threshold checks can stall consensus for extended periods when stale vote-weight data lags real-time fork state - (File: `core/src/consensus.rs`)

### Summary
The Sherlock report describes a boundary/threshold check (`_isPoolSafe()` comparing a fetched price against a fixed `THRESHOLD`) that can remain "unsafe"/failing for extended periods because the reference data it compares against (last chainlink fetch) can be stale relative to the actual current state, causing legitimate operations (deposits/withdrawals) to be blocked for up to the full heartbeat window. The Agave analog is `Tower::check_switch_threshold` / `check_vote_stake_thresholds` in [1](#0-0) , which gates whether a validator may switch its vote to a heavier fork based on `total_stake` and `voted_stakes` snapshots collected from gossip/replay at the time of the check, compared against a fixed `threshold_size` (`SWITCH_FORK_THRESHOLD`, and the shallow experimental thresholds at [2](#0-1) ). The comment in the code explicitly acknowledges that this exact class of staleness causes real stalls: "we wish to impose a shallow threshold check to prevent the frequent 8 deep lockouts seen multiple times a day." [3](#0-2) 

### Finding Description
`check_vote_stake_threshold` computes `lockout = fork_stake / total_stake` and compares it against a fixed `threshold_size` [4](#0-3) . `fork_stake` is derived from `voted_stakes`, a snapshot of stake that has *already landed votes on-chain for a given fork* — this is directly analogous to the "last fetched chainlink price," a value that only updates when new information (a landed vote) arrives, not continuously. If votes are delayed (e.g., because of blockhash expiration, as documented in the dedicated regression test `test_fork_choice_refresh_old_votes`) [5](#0-4) , the on-chain `voted_stakes`/fork-weight data can lag the real state of the network for an extended window, just as the chainlink price can lag the pool spot price for up to a full heartbeat period in the original report.

During that lag window, `check_switch_threshold`/`make_check_switch_threshold_decision` [6](#0-5)  can return `FailedSwitchThreshold`, blocking the validator from switching to the objectively heavier/canonical fork, exactly mirroring how `_isPoolSafe()` blocks deposits/withdrawals while the two data sources are transiently out of sync. The existing guard (`optimistically_bypass_vote_stake_threshold_check`, [7](#0-6) ) only bypasses the check when the *same validator's own* prior vote already covered the lockout — it does nothing to correct for network-wide stale `voted_stakes` snapshots, so it does not close the gap the same way that raising `THRESHOLD` in the report doesn't structurally fix a rate mismatch between two independently-updating values.

### Impact Explanation
When enough validators are simultaneously blocked by `FailedSwitchThreshold` due to stale fork-weight snapshots, the cluster's fork choice can stall on a fork instead of converging on the heaviest/canonical one, which is a consensus-halt / degraded-liveness condition — this matches the "Valid Impact" category of consensus halt. This is not a hypothetical: the in-repo comment explicitly states this "frequent 8 deep lockouts" pattern occurs "multiple times a day" [3](#0-2) , and a dedicated regression test exists specifically to reproduce a scenario where stale vote data plus threshold blocking "stalls the network" [8](#0-7) .

### Likelihood Explanation
This requires no malicious actor — it is triggered by ordinary network conditions (partitions, blockhash expiration on vote transactions, delayed vote propagation) which are explicitly called out as realistic scenarios in the codebase's own tests and comments, making it a naturally-occurring/likely condition rather than an attacker-crafted one.

### Recommendation
This is already a known, actively-monitored tradeoff in Agave (per the in-code comments about "experimentation purposes" and collecting metrics to tune depth/threshold), rather than a novel unpatched bug. Any change should be validated against the existing `test_fork_choice_refresh_old_votes` regression test and the shallow-threshold telemetry (`VOTE_THRESHOLD_DEPTH_SHALLOW`) already collecting data to determine a better depth/threshold percentage [2](#0-1) .

### Proof of Concept
The existing test `test_fork_choice_refresh_old_votes` in `local-cluster/tests/local_cluster.rs` constructs exactly this scenario: a validator's vote fails to land due to blockhash expiration, the network partitions and reconverges, and the validator with stale vote weight fails `check_switch_threshold` against the heavier fork, stalling the network until the vote is refreshed [9](#0-8) .

**Caveat:** This is presented as the closest structural analog found via search; I was not able to fully load the constant definitions (`VOTE_THRESHOLD_DEPTH`, `SWITCH_FORK_THRESHOLD`, `VOTE_THRESHOLD_SIZE`) due to tool/indexing limits in the final iteration, so exact numeric values and any additional mitigations directly surrounding those constants are unverified. I'd recommend a Devin session with full file access to confirm those constants and check whether more recent commits have already tuned the shallow-threshold experiment mentioned in the comments.

            return SwitchForkDecision::SameFork;
        };

        let empty_ancestors = HashSet::default();
        let empty_ancestors_due_to_minor_unsynced_ledger = || {
            // This condition (stale stray last vote) shouldn't occur under normal validator
            // operation, indicating something unusual happened.
            // This condition could be introduced by manual ledger mishandling,
            // validator SEGV, OS/HW crash, or plain No Free Space FS error.

            // the failure was OS or HW level).

            // could result in incorrect (= more than actual) locked_out_stake and
            // false-positive SwitchProof later in this function, there should be no such a
            // heavier fork candidate, first of all, if the last vote (or any of its
            // unavailable ancestors) were already optimistically confirmed.

            if self.is_first_switch_check() && switch_slot < last_voted_slot {

                // newer snapshots on validator restart

                     ledger."
                );
                warn!("{message}");
                datapoint_warn!("tower_warn", ("warn", message, String));
            }
            &empty_ancestors
        };

        let suspended_decision_due_to_major_unsynced_ledger = || {
            // This peculiar corner handling is needed mainly for a tower which is newer than
            // blockstore. (Yeah, we tolerate it for ease of maintaining validator by operators)
            // This condition could be introduced by manual ledger mishandling,
            // validator SEGV, OS/HW crash, or plain No Free Space FS error.

            // When we're in this clause, it basically means validator is badly running
            // with a future tower while replaying past slots, especially problematic is
            // last_voted_slot.

            // at the banking stage: https://github.com/solana-labs/solana/issues/8232)
            //
            // To be specific, the replay stage is tricked into a false perception where
            // last_vote_ancestors is AVAILABLE for descendant-of-`switch_slot`,  stale, and
            // stray slots (which should always be empty_ancestors).
            //
            // This is covered by test_future_tower_* in local_cluster
            SwitchForkDecision::FailedSwitchThreshold(0, total_stake)
        };

    pub(crate) fn check_switch_threshold(
        &mut self,
        switch_slot: Slot,
        ancestors: &HashMap<Slot, HashSet<u64>>,
        descendants: &HashMap<Slot, HashSet<u64>>,
        progress: &ProgressMap,
        total_stake: u64,
        epoch_vote_accounts: &VoteAccountsHashMap,
        latest_validator_votes_for_frozen_banks: &LatestValidatorVotesForFrozenBanks,
        heaviest_subtree_fork_choice: &HeaviestSubtreeForkChoice,
    ) -> SwitchForkDecision {
        let decision = self.make_check_switch_threshold_decision(
            switch_slot,
            ancestors,
            descendants,
            progress,
            total_stake,
            epoch_vote_accounts,
            latest_validator_votes_for_frozen_banks,
            heaviest_subtree_fork_choice,
        );
        let new_check = Some((switch_slot, decision.clone()));
        if new_check != self.last_switch_threshold_check {
            trace!("new switch threshold check: slot {switch_slot}: {decision:?}",);
            self.last_switch_threshold_check = new_check;
        }
        decision
    }

    /// Checks a single vote threshold for `slot`
    fn check_vote_stake_threshold<'a>(
        threshold_vote: Option<&Lockout>,
        tower_before_applying_vote: impl Iterator<Item = &'a Lockout>,
        threshold_depth: usize,
        threshold_size: f64,
        slot: Slot,
        voted_stakes: &VotedStakes,
        total_stake: u64,
    ) -> ThresholdDecision {
        let Some(threshold_vote) = threshold_vote else {
            // Tower isn't that deep.
            return ThresholdDecision::PassedThreshold;
        };
        let Some(fork_stake) = voted_stakes.get(&threshold_vote.slot()) else {
            // We haven't seen any votes on this fork yet, so no stake
            return ThresholdDecision::FailedThreshold(threshold_depth as u64, 0);
        };

        let lockout = *fork_stake as f64 / total_stake as f64;
        trace!(
            "fork_stake slot: {}, threshold_vote slot: {}, lockout: {} fork_stake: {} \
             total_stake: {}",
            slot,
            threshold_vote.slot(),
            lockout,
            fork_stake,
            total_stake
        );
        if Self::optimistically_bypass_vote_stake_threshold_check(
            tower_before_applying_vote,
            threshold_vote,
        ) || lockout > threshold_size
        {
            return ThresholdDecision::PassedThreshold;
        }
        ThresholdDecision::FailedThreshold(threshold_depth as u64, *fork_stake)
    }

// Verifies replay refreshes an old vote whose original transaction expired so fork
// choice can still converge instead of stalling on stale weight.
#[test]
#[serial]
// Steps in this test:
// We want to create a situation like:
/*
      1 (2%, killed and restarted) --- 200 (37%, lighter fork)
    /
    0
    \-------- 4 (38%, heavier fork)
*/
// where the 2% that voted on slot 1 don't see their votes land in a block
// due to blockhash expiration, and thus without resigning their votes with
// a newer blockhash, will deem slot 4 the heavier fork and try to switch to
// slot 4, which doesn't pass the switch threshold. This stalls the network.

// We do this by:
// 1) Creating a partition so all three nodes don't see each other
// 2) Kill the validator with 2%
// 3) Wait for longer than blockhash expiration
// 4) Copy in the lighter fork's blocks up, *only* up to the first slot in the lighter fork
// (not all the blocks on the lighter fork!), call this slot `L`
// 5) Restart the validator with 2% so that he votes on `L`, but the vote doesn't land
// due to blockhash expiration
// 6) Resolve the partition so that the 2% repairs the other fork, and tries to switch,
// stalling the network.

fn test_fork_choice_refresh_old_votes() {
    agave_logger::setup_with_default(RUST_LOG_FILTER);
    let max_switch_threshold_failure_pct = 1.0 - 2.0 * SWITCH_FORK_THRESHOLD;
    let total_stake = 100 * DEFAULT_NODE_STAKE;
    let max_failures_stake = (max_switch_threshold_failure_pct * total_stake as f64) as u64;

    // 1% less than the failure stake, where the 2% is allocated to a validator that
    // has no leader slots and thus won't be able to vote on its own fork.
    let failures_stake = max_failures_stake;
    let total_alive_stake = total_stake - failures_stake;
    let alive_stake_1 = total_alive_stake / 2 - 1;
    let alive_stake_2 = total_alive_stake - alive_stake_1 - 1;

    // Heavier fork still doesn't have enough stake to switch. Both branches need
    // the vote to land from the validator with `alive_stake_3` to allow the other
    // fork to switch.
    let alive_stake_3 = 2 * DEFAULT_NODE_STAKE;
    assert!(alive_stake_1 < alive_stake_2);
    assert!(alive_stake_1 + alive_stake_3 > alive_stake_2);

    let num_lighter_partition_slots_per_rotation = 8;
    // ratio of total number of leader slots to the number of leader slots allocated
    // to the lighter partition
    let total_slots_to_lighter_partition_ratio = 2;
    let partitions: &[(usize, usize)] = &[
        (
            alive_stake_1 as usize,
            num_lighter_partition_slots_per_rotation,
        ),
        (
            alive_stake_2 as usize,
            (total_slots_to_lighter_partition_ratio - 1) * num_lighter_partition_slots_per_rotation,
        ),
        (alive_stake_3 as usize, 0),
    ];
