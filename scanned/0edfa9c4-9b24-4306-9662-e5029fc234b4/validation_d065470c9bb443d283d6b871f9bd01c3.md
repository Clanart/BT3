## Agave Analog: `zk-elgamal-proof` program disablement locks Confidential-Transfer (Token‑2022) funds with no emergency exit

### Title
Disabling the `zk-elgamal-proof` native program via feature gate permanently blocks confidential-balance withdrawals with no emergency exit - (File: `programs/zk-elgamal-proof/src/lib.rs`)

### Summary
The external report describes an AMM `burn` flow that calls out to an external hook contract; if that hook breaks, the caller has no way to retrieve deposited funds because there is no emergency-exit path. The structural analog in Agave is the `zk-elgamal-proof` native builtin program, which SPL Token-2022's Confidential Transfer extension depends on as an external "hook" to verify zero-knowledge proofs before any confidential balance can be withdrawn, transferred, or emptied. That dependency can be switched off entirely by a single feature-gate flag, and once off, every confidential-transfer operation that needs proof verification fails permanently, with no alternate on-chain path to recover the encrypted balance.

### Finding Description
`zk-elgamal-proof` is a first-class Agave builtin program. Its entrypoint begins with a hard kill-switch: [1](#0-0) 

If `disable_zk_elgamal_proof_program` is active and `reenable_zk_elgamal_proof_program` is not, every instruction to this program — including `VerifyZeroCiphertext`, `VerifyCiphertextCiphertextEquality`, `VerifyCiphertextCommitmentEquality`, `VerifyBatchedRangeProof*`, and `CloseContextState` — immediately returns `InstructionError::InvalidInstructionData`.

SPL Token-2022's confidential transfer extension is architected around this program as its proof-verification "hook": a `WithdrawConfidentialTransfer` (and analogous `Transfer`/`EmptyAccount`/`WithdrawWithheldTokens`) instruction either (a) bundles proof data at an instruction offset that is verified inline by this program in the same transaction, or (b) references a pre-created "context state account" that was populated by a prior call into `zk-elgamal-proof`'s `process_verify_proof`: [2](#0-1) 

The RPC-side parsing of these confidential withdraw instructions confirms that a `WithdrawConfidentialTransfer` always requires either an `equalityProofContextStateAccount`/`rangeProofContextStateAccount` (populated by `zk-elgamal-proof`) or an instruction-offset proof that this program verifies inline: [3](#0-2) 

Because ElGamal-encrypted confidential balances are, by design, only movable through a validated proof, there is no fallback: once `disable_zk_elgamal_proof_program` is toggled on (a real feature flag that exists precisely because this program has previously needed to be disabled in production due to a proof-verification bug), users' confidential balances become frozen — the SPL Token-2022 program itself has no "emergency exit" instruction that lets a user reclaim confidential funds without a valid ZK proof, and the `zk-elgamal-proof` program provides no bypass either.

### Impact Explanation
This mirrors the report's "broken hook blocks user funds" pattern almost exactly: a mandatory external verifier program gates access to already-deposited user funds (confidential/encrypted token balances), and if that verifier is disabled or broken, users cannot withdraw, transfer, or empty their confidential accounts. Given that this is a cluster-wide feature toggle (not a self-serve emergency exit), affected users have no unprivileged remedy — their funds remain locked in the encrypted extension state until governance re-enables the program (`reenable_zk_elgamal_proof_program`) or ships a fix, which can take an extended period.

### Likelihood Explanation
This is not a hypothetical: the presence of both `disable_zk_elgamal_proof_program` and `reenable_zk_elgamal_proof_program` feature flags in `feature-set/src/lib.rs` reflects that this program has already been disabled once in production due to a discovered proof-verification vulnerability, and confidential transfer functionality was unusable cluster-wide for the duration. Any future bug discovered in the ZK proof verification logic would force the same mitigation, again freezing all pending confidential-transfer withdrawals/transfers with no emergency exit.

### Recommendation
Add an emergency-exit path in the Token-2022 confidential transfer extension (or equivalent SVM-level mechanism) that allows users to reclaim/convert confidential balances to standard (non-confidential) balances via an alternate, less proof-dependent path when the `zk-elgamal-proof` program is disabled, rather than relying solely on redeploying/re-enabling the verifier program.

### Proof of Concept
1. Set up a validator/test cluster with `disable_zk_elgamal_proof_program` active (as it was in a past incident) and `reenable_zk_elgamal_proof_program` inactive.
2. Create a Token-2022 mint with the `ConfidentialTransferMint` extension and configure a token account with a nonzero confidential balance (via `Deposit`).
3. Attempt `WithdrawConfidentialTransfer` (or `EmptyAccount`) using either the context-state-account flow or instruction-offset flow.
4. Observe that any CPI/instruction dispatched to `zk-elgamal-proof` (context-state creation or inline proof verification) fails with `InstructionError::InvalidInstructionData`, per [1](#0-0) , causing the withdrawal transaction to fail deterministically and the confidential balance to remain permanently locked until the feature is reversed.

fn process_verify_proof<T, U>(invoke_context: &mut InvokeContext) -> Result<(), InstructionError>
where
    T: Pod + ZkProofData<U> + VerifyZkProof,
    U: Pod,
{
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let instruction_data = instruction_context.get_instruction_data();

    // number of accessed accounts so far
    let mut accessed_accounts = 0_u16;

    // if instruction data is exactly 5 bytes, then read proof from an account
    let context_data = if instruction_data.len() == INSTRUCTION_DATA_LENGTH_WITH_PROOF_ACCOUNT {
        let proof_data_account =
            instruction_context.try_borrow_instruction_account(accessed_accounts)?;
        accessed_accounts = accessed_accounts.checked_add(1).unwrap();

        let proof_data_offset = u32::from_le_bytes(
            // the first byte is the instruction discriminator
            instruction_data[1..INSTRUCTION_DATA_LENGTH_WITH_PROOF_ACCOUNT]
                .try_into()
                .map_err(|_| InstructionError::InvalidInstructionData)?,
        );
        let proof_data_start: usize = proof_data_offset
            .try_into()
            .map_err(|_| InstructionError::InvalidInstructionData)?;
        let proof_data_end = proof_data_start
            .checked_add(std::mem::size_of::<T>())
            .ok_or(InstructionError::InvalidInstructionData)?;
        let proof_data_raw = proof_data_account
            .get_data()
            .get(proof_data_start..proof_data_end)
            .ok_or(InstructionError::InvalidAccountData)?;

        let proof_data = bytemuck::try_from_bytes::<T>(proof_data_raw).map_err(|_| {
            ic_msg!(invoke_context, "invalid proof data");
            InstructionError::InvalidInstructionData
        })?;
        proof_data.verify_proof().map_err(|err| {
            ic_msg!(invoke_context, "proof verification failed: {:?}", err);
            InstructionError::InvalidInstructionData
        })?;

        *proof_data.context_data()
    } else {
        let proof_data =
            ProofInstruction::proof_data::<T, U>(instruction_data).ok_or_else(|| {
                ic_msg!(invoke_context, "invalid proof data");
                InstructionError::InvalidInstructionData
            })?;
        proof_data.verify_proof().map_err(|err| {
            ic_msg!(invoke_context, "proof verification failed: {:?}", err);
            InstructionError::InvalidInstructionData
        })?;

        *proof_data.context_data()
    };

    // create context state if additional accounts are provided with the instruction
    if instruction_context.get_number_of_instruction_accounts()
        >= accessed_accounts
            .checked_add(2)
            .ok_or(InstructionError::ArithmeticOverflow)?
    {
        let context_state_authority = *instruction_context
            .try_borrow_instruction_account(accessed_accounts.checked_add(1).unwrap())?
            .get_key();

        let mut proof_context_account =
            instruction_context.try_borrow_instruction_account(accessed_accounts)?;

        if *proof_context_account.get_owner() != id() {
            return Err(InstructionError::InvalidAccountOwner);
        }

        let proof_context_state_meta =
            ProofContextStateMeta::try_from_bytes(proof_context_account.get_data())?;

        if proof_context_state_meta.proof_type != ProofType::Uninitialized.into() {
            return Err(InstructionError::AccountAlreadyInitialized);
        }

        let context_state_data =
            ProofContextState::encode(&context_state_authority, T::PROOF_TYPE, &context_data);

        if proof_context_account.get_data().len() != context_state_data.len() {
            return Err(InstructionError::InvalidAccountData);
        }

        proof_context_account.set_data_from_slice(&context_state_data)?;
    }
