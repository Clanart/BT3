### Title
Non-`AccountInUse`/`TooManyAccountLocks` lock-result errors (including transient cost-limit rejections) are silently classified as non-retryable, causing valid transactions to be permanently dropped instead of retried - (File: `core/src/banking_stage/consumer.rs`)

### Summary
The GMX report (M-15) describes an error-handling pattern where only a fixed, enumerated set of revert reasons is treated as "retry-worthy"; any other (unenumerated) error falls through a default branch that results in permanent cancellation, even though the underlying condition (wrong oracle block) was transient and keeper-supplied. The same *shape* of bug exists in Agave's `Consumer::execute_and_commit_transactions_locked`, which classifies per-transaction lock results into "retryable" vs. "not retryable" by explicitly matching only two `TransactionError` variants and funneling everything else into a permanent `None` (non-retryable) bucket.

### Finding Description
In `core/src/banking_stage/consumer.rs`, `execute_and_commit_transactions_locked` builds the initial `retryable_transaction_indexes` list directly from `batch.lock_results()`: [1](#0-0) 

Only `TransactionError::AccountInUse` is marked `immediately_retryable: true`; `TransactionError::TooManyAccountLocks` and *every other* error variant (`Err(_) => None`) are treated as final/non-retryable, meaning the transaction is dropped from the leader's processing pipeline entirely rather than being returned to the caller for later re-scheduling.

The doc comment on `Bank::prepare_sanitized_batch_with_results` (the function that produces these `lock_results`) states explicitly that the set of possible errors includes cost-model related failures: [2](#0-1) 

`WouldExceedMaxBlockCostLimit` and `WouldExceedMaxAccountCostLimit` (produced by `CostTrackerError` conversions in `cost-model/src/cost_tracker.rs`) are, per this comment, valid values that can appear in `lock_results`: [3](#0-2) 

Both are inherently *transient* conditions — the transaction did not fail because it is invalid, but because the current block (or a specific hot account) is currently over its cost budget. A well-formed retry classifier should treat these the same way `AccountInUse` is treated (immediately retryable), since the same transaction is very likely to succeed once cost pressure eases in a subsequent block/slot. Instead, the `Err(_) => None` catch-all silently converts them into a permanent drop — exactly the same "unenumerated-error-defaults-to-worst-case-outcome" pattern flagged in the GMX report, where `OracleBlockNumbersAreNotEqual`/`AreSmallerThanRequired`/`NotWithinRange` fell through to cancellation instead of being recognized as retryable.

### Impact Explanation
If a legitimate, well-formed, fee-paying transaction is transiently rejected at the lock/pre-check stage due to cost-tracker pressure (e.g., another transaction targeting the same hot account, or overall block cost saturation, driven by ordinary — not necessarily malicious — transaction flow that an unprivileged user can trigger by submitting many transactions touching the same account), that transaction is classified as non-retryable and dropped by this leader rather than being handed back to the scheduler/mempool for resubmission in the next slot. For time-sensitive protocol interactions (e.g., transactions racing to close a position, liquidate, or otherwise protect user funds before a deadline/blockhash expiry), being silently and permanently dropped instead of retried can translate into missed execution windows and financial loss for the transaction's sender — the same "position liquidation from wrongly-cancelled action" impact class cited in the GMX report, mapped onto Agave's leader transaction-processing pipeline.

### Likelihood Explanation
I was not able to fully confirm, within the available search budget, the exact upstream call site(s) that populate `lock_results`/`tx_results` with `WouldExceedMaxBlockCostLimit` / `WouldExceedMaxAccountCostLimit` *before* `prepare_sanitized_batch_with_results` is invoked (as opposed to these errors only ever being produced later, during `try_add_processed_transaction_costs`, which is handled separately via `cancel_processed_transactions_for_retry` and *does* correctly mark things retryable). The doc comment on line 3738 of `runtime/src/bank.rs` is the strongest evidence that this is a real, intended possible input to the match arm at consumer.rs:244-266, but I could not trace a concrete caller in the time available to prove reachability by an unprivileged, low-cost attacker. This uncertainty should be resolved with a full trace of all callers of `prepare_sanitized_batch_with_results` / `try_lock_accounts_with_results` before treating this as confirmed-exploitable.

### Recommendation
Audit all `TransactionError` variants that can appear in `batch.lock_results()` and explicitly classify cost-model-related transient errors (`WouldExceedMaxBlockCostLimit`, `WouldExceedMaxAccountCostLimit`, and any other congestion/transient errors) as `immediately_retryable: true` in `execute_and_commit_transactions_locked`, rather than relying on a catch-all `Err(_) => None` arm. This mirrors the GMX fix recommendation: enumerate and correctly handle every distinguishable transient failure mode instead of defaulting unknown/unenumerated errors to the most destructive outcome (permanent drop/cancellation).

### Proof of Concept
Not independently verified/executed; based on static code analysis only. A verifying PoC would need to: (1) confirm a code path that supplies pre-lock `tx_results` containing `WouldExceedMaxBlockCostLimit`/`WouldExceedMaxAccountCostLimit` into `prepare_sanitized_batch_with_results`, (2) construct a scenario where an unprivileged actor drives an account or block near its cost limit at the moment a victim transaction is locked, and (3) observe that the victim transaction is dropped (not present in `retryable_transaction_indexes`) rather than requeued.
