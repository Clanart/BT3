## Analysis

The external report's core pattern is: an **allow-list that only grows** (no bound, no eviction) is exhaustively/linearly scanned on every invocation of a security/consensus-relevant check, degrading over time into a denial-of-service.

The closest analog I found in Agave is in `LatestValidatorVotesForFrozenBanks::check_add_vote`, which stores an **unbounded, per-pubkey `Vec<Hash>`** of "frozen vote hashes" that is linearly scanned with `.contains()` on every gossip vote processed, and is never trimmed for a given (pubkey, slot) pair — the code even has a `TODO` acknowledging this gap. ### Title
Unbounded per-pubkey `Vec<Hash>` in `LatestValidatorVotesForFrozenBanks` grows without limit, causing linear-scan CPU/memory blow-up on the gossip vote hot path - (File: `core/src/consensus/latest_validator_votes_for_frozen_banks.rs`)

### Summary
`LatestValidatorVotesForFrozenBanks::check_add_vote` records, per pubkey, a `Vec<Hash>` of distinct "frozen vote hashes" observed for the latest tracked slot. Every incoming gossip vote for that (pubkey, slot) pair triggers a linear `.contains()` scan over this vector before appending a new entry if the hash is unseen. Unlike the `allowedContracts` array in the reported bug, there is no cap on the vector's size and no periodic pruning — the comment `// TODO: Clean outdated/unstaked pubkeys from this list.` on the struct confirms this is a known, unaddressed gap.

### Finding Description
A validator's vote account (which is permissionless to create and does not require meaningful stake) can be used to broadcast, through gossip, many distinct vote transactions targeting the *same* `vote_slot` while varying the claimed bank hash. Each such vote, once observed by another node's `ClusterInfoVoteListener`/`UnfrozenGossipVerifiedVoteHashes` pipeline for a slot the node has already frozen, is funneled into `check_add_vote` with `is_replay_vote = false`.

For a fixed `vote_slot` equal to the pubkey's currently tracked slot, the code performs:
```
} else if vote_slot == *latest_frozen_vote_slot
    && !latest_frozen_vote_hashes.contains(&frozen_hash)
{
    ...
    latest_frozen_vote_hashes.push(frozen_hash);
``` [4](#0-3) 

Each new (fabricated) hash value passes the `contains` check (since it has never been seen) and is appended, growing `latest_frozen_vote_hashes` without bound as long as the attacker keeps `vote_slot` fixed and varies the hash. Because `contains` performs an O(n) scan, each successive vote for the same slot costs progressively more CPU, and the `HashMap<Pubkey, (Slot, Vec<Hash>)>` (`max_gossip_frozen_votes`) itself is never pruned for entries whose slot has not advanced — it is only cleared for the `fork_choice_dirty_set` on `take_votes_dirty_set`, and only entries below the new root are dropped there, not from `max_gossip_frozen_votes` itself.

There is no existing guard preventing this: no maximum length on the `Vec<Hash>`, no per-slot/per-pubkey rate limiting at this layer, and no stake-weighted admission control before the vote reaches `check_add_vote`.

### Impact Explanation
This structure sits in the vote-processing/consensus hot path that feeds `heaviest_subtree_fork_choice` via `max_gossip_frozen_votes`. Unbounded growth of the per-pubkey `Vec<Hash>` combined with repeated O(n) linear scans on every subsequent vote for that (pubkey, slot) leads to increasing CPU consumption and unbounded heap growth in a core validator process — a non-RPC, in-process remote resource-exhaustion vector that can degrade or stall vote processing across the fleet of nodes that receive and process the crafted votes via gossip, without requiring any privileged/malicious-validator assumption beyond creating an ordinary (even unstaked) vote account.

### Likelihood Explanation
Vote accounts are permissionless and cheap to create, and vote transactions relayed through gossip are processed for hash-tracking purposes as soon as they pass basic vote-transaction parsing — there is no stake-weighted filter applied before `check_add_vote`. An attacker only needs to keep submitting votes for a slot that is already frozen on target nodes while varying the claimed hash. This makes the underlying primitive (submit many votes, same slot, distinct fabricated hash) straightforward to trigger repeatedly and cheaply, though the practical blast radius depends on how aggressively `ClusterInfoVoteListener` gates/deduplicates votes before this call — a detail I was not able to fully trace within the available search iterations.

### Recommendation
Bound `latest_frozen_vote_hashes` (e.g., cap to a small constant such as a handful of hashes) and/or use a `HashSet<Hash>` for O(1) membership checks instead of a linearly-scanned `Vec<Hash>`; additionally, evict/prune `max_gossip_frozen_votes` entries whose slot falls behind the current root (mirroring the existing root-based pruning already done for `fork_choice_dirty_set` in `take_votes_dirty_set`), directly addressing the pre-existing `TODO` comment on the struct.

### Proof of Concept
Conceptually:
1. Create an (unstaked) vote account and keypair.
2. Pick a `vote_slot` that target nodes have already frozen.
3. Repeatedly broadcast, via gossip, vote transactions for `vote_slot` that differ only in the claimed/declared bank hash (`frozen_hash`), each a freshly fabricated `Hash`.
4. Each vote reaching a target node's `UnfrozenGossipVerifiedVoteHashes::add_vote` → `LatestValidatorVotesForFrozenBanks::check_add_vote` finds `vote_slot == latest_frozen_vote_slot` and the new hash absent from `latest_frozen_vote_hashes`, so it appends unconditionally — with no cap — while the `.contains()` check cost grows linearly with each iteration.

I was unable to fully verify, within the available search budget, what upstream filtering (if any) `ClusterInfoVoteListener` applies to gossip votes before they reach this function (e.g., stake-weighted throttling), which would materially affect the real-world exploitability of this path; a Devin session with broader code access would be needed to confirm the full call chain from raw gossip ingestion to `check_add_vote`.

impl UnfrozenGossipVerifiedVoteHashes {
    // Update `latest_validator_votes_for_frozen_banks` if gossip has seen a newer vote
    // for a frozen bank.
    pub(crate) fn add_vote(
        &mut self,
        pubkey: Pubkey,
        vote_slot: Slot,
        hash: Hash,
        is_frozen: bool,
        latest_validator_votes_for_frozen_banks: &mut LatestValidatorVotesForFrozenBanks,
    ) {
        // If this is a frozen bank, then we need to update the `latest_validator_votes_for_frozen_banks`
        let frozen_hash = if is_frozen { Some(hash) } else { None };
        let (was_added, latest_frozen_vote_slot) = latest_validator_votes_for_frozen_banks
            .check_add_vote(pubkey, vote_slot, frozen_hash, false);

        if !was_added
            && latest_frozen_vote_slot
                .map(|latest_frozen_vote_slot| vote_slot >= latest_frozen_vote_slot)
                // If there's no latest frozen vote slot yet, then we should also insert
                .unwrap_or(true)
        {
            // At this point it must be that:
            // 1) `vote_slot` was not yet frozen
            // 2) and `vote_slot` >= than the latest frozen vote slot.

            // Thus we want to record this vote for later, in case a slot with this `vote_slot` + hash gets
            // frozen later
            self.votes_per_slot
                .entry(vote_slot)
                .or_default()
                .entry(hash)
                .or_default()
                .push(pubkey);
        }
    }
