### Title
Fixed epoch-length staleness window for on-chain timestamp votes admits stale/mismatched-real-time votes into the stake-weighted Clock estimate - ([File: runtime/src/stake_weighted_timestamp.rs], [File: runtime/src/bank.rs])

### Summary
Agave's `Bank::get_timestamp_estimate` filters which validator vote-timestamps are eligible to be folded into the stake-weighted `Clock::unix_timestamp` estimate using a single fixed criterion — `slot_delta <= slots_per_epoch` — regardless of how much *real* wall-clock time that slot range actually represents. This is structurally the same class of bug as the Renzo finding: a single fixed "staleness window" (there: `86400 + 60` seconds; here: `slots_per_epoch` slots) is used as a proxy for real elapsed time, but the actual relationship between the fixed unit and real time is not constant, so the window can be far "too stale" or "too fresh" depending on network conditions.

### Finding Description
`Bank::get_timestamp_estimate` collects each vote account's `last_timestamp` (a `(slot, timestamp)` pair set via `VoteState::process_timestamp`) and only keeps it if: [1](#0-0) 
```rust
let recent_timestamps = vote_accounts.iter().filter_map(|(pubkey, (_, account))| {
    let vote_state = account.vote_state_view();
    let last_timestamp = vote_state.last_timestamp();
    let slot_delta = self.slot().checked_sub(last_timestamp.slot)?;
    (slot_delta <= slots_per_epoch)
        .then_some((*pubkey, (last_timestamp.slot, last_timestamp.timestamp)))
});
```
The eligibility criterion is purely slot-count-based (`slot_delta <= slots_per_epoch`), not time-based. These surviving timestamps are then fed into `calculate_stake_weighted_timestamp` in `runtime/src/stake_weighted_timestamp.rs`, which computes a stake-weighted median and bounds it against the PoH-derived `epoch_start_timestamp` offset using `MAX_ALLOWABLE_DRIFT_PERCENTAGE_FAST`/`MAX_ALLOWABLE_DRIFT_PERCENTAGE_SLOW_V2` (25%/150%), themselves also fixed percentages of the *current* epoch's PoH-estimated elapsed duration: [2](#0-1) 

The bug-class parallel to the Renzo finding is exact: the original bug used one fixed heartbeat/staleness constant (24h+60s) to decide whether Chainlink price data was "too old," but the real cadence of updates varies by chain/token, so the fixed constant is sometimes too loose and sometimes too tight. Here, the "staleness window" for including a validator's timestamp vote is expressed in slots (`slots_per_epoch`), not seconds, and slot production rate is not guaranteed constant — it is only approximately `DEFAULT_MS_PER_SLOT`. If the cluster is running degraded (slow slot production due to congestion, replay stalls, or partition-induced fork churn) `slots_per_epoch` slots can span far longer real wall-clock time than intended, meaning `last_timestamp` votes that are actually many hours or days stale are still treated as "recent" and are eligible to be weighted into the estimate purely because they fall within the current epoch's slot range. Conversely, in low-slot-time test/private clusters, the same fixed slot count represents far less real time than production assumptions bake in.

Unlike the Renzo bug (single Chainlink price consumed directly), Agave's `calculate_stake_weighted_timestamp` does bound the final result against a PoH-derived offset (`max_allowable_drift`), which mitigates the worst-case magnitude of drift. However, that bound itself is derived from `elapsed_slot_duration`, which is computed from the *same* PoH-based `slot_range_duration_nanos` used to justify the slots_per_epoch cutoff — so both the staleness filter and its "sanity bound" share the same underlying assumption about slot-to-time ratio, and both can be degraded together under sustained slow slot production.

### Impact Explanation
The output of `get_timestamp_estimate` becomes `Clock::unix_timestamp` in the `Clock` sysvar, which is consensus-critical: every validator computes it deterministically from the same vote-account state, so this is not attacker/leader-privileged. Programs (including on-chain vesting, auctions, staking lockups, and various native/BPF programs) rely on the `Clock` sysvar for time-based logic. If the effective staleness window (in slots) diverges significantly from real elapsed time during a period of degraded slot production, the resulting `Clock::unix_timestamp` can silently reflect timestamps voted many multiples of the intended freshness window ago, propagating an inconsistent/incorrect time value cluster-wide — a false/misleading protocol-level value being accepted as canonical, deterministically, by all validators, matching the "false execution/acceptance" impact class.

### Likelihood Explanation
This is a low-probability-but-not-attacker-controlled edge case: it requires the cluster's actual slot production rate to differ substantially and sustained from the nominal rate assumed by `slots_per_epoch`/`DEFAULT_MS_PER_SLOT`, e.g., during sustained network degradation, mass restarts, or heavy fork resolution. It doesn't require a malicious validator, leaked keys, or trusted-plugin assumptions — it's a systemic design property of using a fixed slot-count proxy for a real-time staleness cutoff, identical in shape to the Renzo root cause. I was not able to fully trace all downstream consumers of `Clock::unix_timestamp` or quantify how much production epochs actually deviate from nominal slot timing in practice (out of scope for the index), so the concrete severity of drift under realistic degraded conditions is uncertain and would benefit from further investigation via a Devin session with full repo/test access.

### Recommendation
Replace or supplement the slot-count-based `slot_delta <= slots_per_epoch` cutoff in `Bank::get_timestamp_estimate` with a cutoff derived from actual estimated elapsed time (using the same `elapsed_slot_duration`/`slot_range_duration_nanos` machinery already available), so that vote timestamps are excluded once their *real* age exceeds a fixed wall-clock budget, independent of how many slots have nominally elapsed. Consider also decoupling the drift-bound computation from the same PoH-timing assumption used for the staleness filter, so a single systemic timing anomaly cannot simultaneously widen the staleness window and loosen the sanity bound.

### Proof of Concept
Conceptual (no test harness available in the index to execute):
1. Simulate/observe a cluster epoch where real slot production time per slot is, say, 5x the nominal `DEFAULT_MS_PER_SLOT` (e.g., due to sustained partial outages/forking), so that `slots_per_epoch` slots take 5x longer in wall-clock time than intended.
2. A validator's `last_timestamp` vote submitted near the start of that epoch remains "eligible" under `slot_delta <= slots_per_epoch` for the entire (now much longer) epoch, per [3](#0-2) .
3. `calculate_stake_weighted_timestamp` in [4](#0-3)  still includes this now much-staler-than-intended timestamp in the stake-weighted median, bounded only by the drift percentages computed from the same (also degraded) `elapsed_slot_duration`.
4. Resulting `Clock::unix_timestamp` reflects a value stale by a multiple of the intended freshness window, propagated identically to all validators as the canonical sysvar value.

```rust
pub(crate) fn calculate_stake_weighted_timestamp<I, K, V, T>(
    unique_timestamps: I,
    stakes: &HashMap<Pubkey, (u64, T /*Account|VoteAccount*/)>,
    slot: Slot,
    elapsed_slot_duration: impl Fn(Slot, Slot) -> Duration,
    epoch_start_timestamp: Option<(Slot, UnixTimestamp)>,
    max_allowable_drift: MaxAllowableDrift,
) -> Option<UnixTimestamp>
where
    I: IntoIterator<Item = (K, V)>,
    K: Borrow<Pubkey>,
    V: Borrow<(Slot, UnixTimestamp)>,
{
    let mut stake_per_timestamp: BTreeMap<UnixTimestamp, u128> = BTreeMap::new();
    let mut total_stake: u128 = 0;
    for (vote_pubkey, slot_timestamp) in unique_timestamps {
        let (timestamp_slot, timestamp) = slot_timestamp.borrow();
        let offset = elapsed_slot_duration(*timestamp_slot, slot);
        let estimate = timestamp.saturating_add(offset.as_secs() as i64);
        let stake = stakes
            .get(vote_pubkey.borrow())
            .map(|(stake, _account)| stake)
            .unwrap_or(&0);
        stake_per_timestamp
            .entry(estimate)
            .and_modify(|stake_sum| *stake_sum = stake_sum.saturating_add(*stake as u128))
            .or_insert(*stake as u128);
        total_stake = total_stake.saturating_add(*stake as u128);
```
