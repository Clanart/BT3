## Title
Unsolicited/replayed gossip `PullResponse` messages can unboundedly grow `CrdsGossipPull::failed_inserts`, causing per-node gossip-processing DoS — (File: `gossip/src/crds_gossip_pull.rs`)

### Summary
The Ajna report's core primitive is: an unprivileged caller can invoke a function that appends entries to a data structure keyed to another party's resource, with **no ownership check** and **no bound on the number of entries**, until an owner-side iteration (rewards calculation) exceeds a resource limit and DoSes.

The structural analog in Agave is the gossip pull-response path: any UDP sender can send `Protocol::PullResponse` packets to a validator's gossip socket without ever having issued a corresponding `PullRequest`, and each response value that fails to insert (e.g. because it is already known/outdated) is appended to `CrdsGossipPull::failed_inserts` with only a **time-based** purge, not a **count-based** cap.

### Finding Description
`Crds`/`CrdsGossipPull` correctly bounds the main CRDS table via `trim_crds_table`/`Crds::trim`, which caps the number of unique pubkeys [1](#0-0) . However, the auxiliary `failed_inserts` structure used for pull-filter construction has no such cap:

```
pub(crate) fn purge_failed_inserts(&self, now: u64) {
    if FAILED_INSERTS_RETENTION_MS < now {
        let cutoff = now - FAILED_INSERTS_RETENTION_MS;
        let mut failed_inserts = self.failed_inserts.write().unwrap();
        let outdated = failed_inserts.iter().take_while(|(_, ts)| *ts < cutoff).count();
        failed_inserts.drain(..outdated);
    }
}
``` [2](#0-1) 

Entries are inserted whenever a `PullResponse` value fails to insert into the CRDS table:
```
stats.failed_insert += failed_inserts.len();
self.purge_failed_inserts(now);
let failed_inserts = failed_inserts.into_iter().zip(repeat(now));
self.failed_inserts.write().unwrap().extend(failed_inserts);
``` [3](#0-2) 

Crucially, `filter_pull_responses` classifies *any* value that is outdated (older wallclock than what's already stored, or a value the table already "upserts"-rejects) as a failed insert — this includes simply resending an already-known, previously valid, publicly-observable `CrdsValue` (a pure replay, no forged signature needed):
```
if !crds.upserts(&response) {
    Some(response)
} ... else { stats.failed_timeout += 1; Some(response) }
``` [4](#0-3) 

Packet ingestion for `PullResponse` performs no correlation with outstanding requests — any inbound `Protocol::PullResponse` is parsed and queued for processing purely based on passing an address/duplicate-instance check, not proof that this node ever asked for it:
```
Protocol::PullResponse(_, mut data) => {
    if should_check_duplicate_instance { check_duplicate_instance(&data)?; }
    data.retain(&mut verify_gossip_addr);
    if !data.is_empty() { pull_responses.append(&mut data); }
}
``` [5](#0-4) 

The only anti-flood control in this path is `outbound_budget`/`pull_request_budget`, which throttles the *sending* side of pull-request scanning cost (per-IP token bucket) [6](#0-5) ; there is no equivalent per-IP/per-pubkey rate limit or count cap on *inbound* `PullResponse` ingestion or on the resulting `failed_inserts` collection. Because the retention window is purely time-based (`FAILED_INSERTS_RETENTION_MS = 20_000`), an attacker sending responses faster than the 20-second window can push the `failed_inserts` VecDeque's size arbitrarily high, bounded only by attacker bandwidth, not by any protocol invariant.

`failed_inserts` is also linearly scanned every pull round in `build_crds_filters` (used to build the bloom filters this node sends out with its own pull requests):
```
let num_items = crds.len() + crds.num_purged() + failed_inserts.len();
...
.chain(failed_inserts.par_iter().with_min_len(PAR_MIN_LENGTH).map(|(v, _)| *v))
.for_each(|v| filters.add(v));
``` [7](#0-6) 

This mirrors the Ajna vulnerability class exactly: an unprivileged, unauthenticated actor (any UDP sender able to reach the gossip port — no stake, no signature over new data, no validator identity required) can append entries into a per-node data structure that has no per-sender/per-count quota, degrading the victim's own bookkeeping/iteration cost over time, just as the memorialized positions array could be spammed with tiny valid LP positions until the owner's rewards-calculation iteration DoSed.

### Impact Explanation
Sustained flooding grows `failed_inserts` (and correspondingly the memory/CPU cost of `build_crds_filters`, which runs every gossip round on every node) without an explicit ceiling, other than the 20-second time window and the attacker's own send rate. This degrades or exhausts gossip-processing resources on the targeted validator — a non-RPC, remotely triggerable resource-exhaustion/degradation vector reachable by any network participant, not requiring malicious validator/stake assumptions.

### Likelihood Explanation
Likelihood is limited by the fact that the growth is bounded in time (20s sliding window) and requires sustained outbound traffic from the attacker matching or exceeding the node's processing/purge rate; it does not directly cause consensus failure. It is nonetheless a genuine missing invariant: unlike the CRDS table itself, which is explicitly size-capped via `trim`, this auxiliary structure has no count-based limit, so its severity scales purely with attacker bandwidth and the number of distinct hosts it can spoof/reach the gossip UDP port from.

### Recommendation
Add an explicit maximum size (count cap, not just a time-based cutoff) to `CrdsGossipPull::failed_inserts`, and/or require a lightweight proof of correlation between an inbound `PullResponse` and a `PullRequest` this node actually issued (e.g., a token/nonce embedded in requests) before queuing response values for CRDS-insert processing, similar to the existing per-IP scan-budget throttling already applied to inbound pull *requests*.

### Proof of Concept
Not executable from the index alone (gossip requires live network setup); the code-level PoC is the absence of any size bound in `purge_failed_inserts` combined with the unconditional queuing of `Protocol::PullResponse` packets shown above — a conceptual PoC would repeatedly unicast/broadcast previously-observed, validly-signed `CrdsValue`s wrapped in `Protocol::PullResponse` frames to a target node's gossip socket without ever sending a matching `PullRequest`, and observe `self.failed_inserts.read().unwrap().len()` (exposed via `failed_inserts_size()`) growing unbounded during the attack window. I was not able to run this in the current environment; a background Devin session with test/network tooling would be needed to fully validate the growth rate and downstream CPU/memory impact.

    // build a set of filters of the current crds table
    // num_filters - used to increase the likelihood of a value in crds being added to some filter
    pub fn build_crds_filters(
        &self,
        thread_pool: &ThreadPool,
        crds: &RwLock<Crds>,
        bloom_size: usize,
    ) -> Vec<CrdsFilter> {
        const PAR_MIN_LENGTH: usize = 512;
        let failed_inserts = self.failed_inserts.read().unwrap();
        // crds should be locked last after self.failed_inserts.
        let crds = crds.read().unwrap();
        let num_items = crds.len() + crds.num_purged() + failed_inserts.len();
        let num_items = MIN_NUM_BLOOM_ITEMS.max(num_items);
        let filters = CrdsFilterSet::new(&mut rand::rng(), num_items, bloom_size);
        thread_pool.install(|| {
            crds.par_values()
                .with_min_len(PAR_MIN_LENGTH)
                .map(|v| *v.value.hash())
                .chain(crds.purged().with_min_len(PAR_MIN_LENGTH))
                .chain(
                    failed_inserts
                        .par_iter()
                        .with_min_len(PAR_MIN_LENGTH)
                        .map(|(v, _)| *v),
                )
                .for_each(|v| filters.add(v));
        });
        drop(crds);
        drop(failed_inserts);
        filters.into()
    }
