### Title
`secp256r1_program` missing from `NON_MIGRATING_BUILTINS_COSTS` causes incorrect default compute-unit accounting - (File: `builtins-default-costs/src/lib.rs`)

### Summary
`BUILTIN_INSTRUCTION_COSTS` (built by merging `MIGRATING_BUILTINS_COSTS` and `NON_MIGRATING_BUILTINS_COSTS`) is the canonical, hand-maintained table of "which program ids are builtins" used across the transaction-cost pipeline. `secp256k1_program` and `ed25519_program` are present in `NON_MIGRATING_BUILTINS_COSTS`, but `secp256r1_program` is absent, despite `secp256r1` being fully supported everywhere else as a precompile (`precompiles/src/lib.rs::PRECOMPILES`, `SECP256R1_VERIFY_COST` in `cost-model/src/block_cost_limits.rs`, and `PrecompileSignatureDetailsBuilder` in `runtime-transaction/src/signature_details.rs`).

### Finding Description
`solana-builtins-default-costs` exposes `get_builtin_migration_feature_index()` and the `MAYBE_BUILTIN_KEY` fast-filter table, both derived solely from `BUILTIN_INSTRUCTION_COSTS`: [1](#0-0) 

These are consumed by `BuiltinProgramsFilter::check_program_kind` in `compute-budget-instruction/src/builtin_programs_filter.rs`, which classifies each instruction's program id as `Builtin`, `MigratingBuiltin`, or `NotBuiltin`: [2](#0-1) 

That classification feeds directly into `ComputeBudgetInstructionDetails::try_from` / `calculate_default_compute_unit_limit`, which decides — for transactions that don't explicitly request a compute-unit limit — whether each instruction contributes `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (builtin) or the much larger `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` (non-builtin) to the transaction's implicit compute budget: [3](#0-2) [4](#0-3) 

Because `secp256r1_program` is not registered as a builtin, `check_program_kind` returns `ProgramKind::NotBuiltin` for it, so a `secp256r1` verify instruction is counted under `num_non_builtin_instructions` and gets the full `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` (200,000 CU) share of the default budget instead of the small `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` share that `secp256k1`/`ed25519` verify instructions correctly receive. Meanwhile, `cost_model.rs::get_signature_cost` correctly prices `secp256r1` signatures via `SECP256R1_VERIFY_COST`, confirming the omission is specific to the builtin-classification table, not an intentional design choice: [5](#0-4) [6](#0-5) 

The module's own comment stresses that this table is consensus-sensitive: "This map CANNOT be modified without causing a consensus failure because this map is used to calculate the compute limit for transactions that don't specify a compute limit themselves... It's also used to calculate the cost of a transaction which is used in replay to enforce block cost limits": [7](#0-6) 

This is deterministic (all validators run the same code and reach the same wrong classification), so it is not a consensus-divergence bug, but it is a real, silent miscalculation of default/implicit compute-unit budgeting and block-cost accounting for any transaction that includes a `secp256r1_program` instruction without an explicit `SetComputeUnitLimit`.

### Impact Explanation
Any unprivileged user can submit a transaction containing a `secp256r1_program` verify instruction without setting an explicit compute-unit limit. That instruction is misclassified as non-builtin, inflating the transaction's default compute-unit allocation (`calculate_default_compute_unit_limit`) well beyond what the equivalent `secp256k1`/`ed25519` instruction would receive. This causes inconsistent, incorrect compute-budget/cost-model accounting for a class of legitimate transactions — the exact kind of dispatch/classification-table drift described in the report (a new case added to sibling logic but omitted from a duplicated lookup table). It does not directly cause fund theft, but it does corrupt the value used for block-cost-limit enforcement and default CU budgeting for `secp256r1` transactions, which is explicitly called out in-code as consensus-relevant data.

### Likelihood Explanation
High likelihood of being an actual latent bug: `secp256r1_program` support (precompile, signature counting, per-signature cost) was clearly added elsewhere in the codebase, but the `NON_MIGRATING_BUILTINS_COSTS` array in `builtins-default-costs/src/lib.rs` was never updated, exactly mirroring the pattern in the seed report where a new case (`0x07`) was added to one dispatch surface (`CoreBranchRouter`) but not propagated to a duplicated override (`ArbitrumCoreBranchRouter`). Any transaction using `secp256r1_program` without an explicit compute-unit-limit instruction triggers this path.

### Recommendation
Add `(secp256r1_program::id(), BuiltinCost::NotMigrating)` to `NON_MIGRATING_BUILTINS_COSTS` in `builtins-default-costs/src/lib.rs`, update `TOTAL_COUNT_BUILTINS`, and audit all other tables/enums derived from `BUILTIN_INSTRUCTION_COSTS` (and similarly-styled hand-maintained lists like `PRECOMPILES`, `signature_details.rs`'s `check_program_id`, and `builtins/src/lib.rs::BUILTINS`) for the same kind of manually-duplicated-list drift, ideally consolidating them into a single source of truth.

### Proof of Concept
1. Build a transaction containing one `secp256r1_program` instruction (verify) and no `ComputeBudgetInstruction::SetComputeUnitLimit` instruction.

Call `ComputeBudgetInstructionDetails::try_from(...)` on it — observe `num_non_builtin_instructions` incremented rather than `num_non_migratable_builtin_instructions`, via `BuiltinProgramsFilter::check_program_kind` returning `ProgramKind::NotBuiltin` for `secp256r1_program::id()` (`compute-budget-instruction/src/builtin_programs_filter.rs:46-60`).
3. Call `sanitize_and_convert_to_compute_budget_limits`; observe `compute_unit_limit` computed using `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` for that instruction instead of `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`, unlike an equivalent transaction using `secp256k1_program` or `ed25519_program` in the same slot (`compute-budget-instruction/src/compute_budget_instruction_details.rs:196-219`).

    fn calculate_default_compute_unit_limit(&self, feature_set: &FeatureSet) -> u32 {
        // evaluate if any builtin has migrated with feature_set
        let (num_migrated, num_not_migrated) = self
            .migrating_builtin_feature_counters
            .migrating_builtin
            .iter()
            .enumerate()
            .fold((0, 0), |(migrated, not_migrated), (index, count)| {
                if count.0 > 0 && feature_set.is_active(get_migration_feature_id(index)) {
                    (migrated + count.0, not_migrated)
                } else {
                    (migrated, not_migrated + count.0)
                }
            });

        u32::from(self.num_non_migratable_builtin_instructions.0)
            .saturating_add(u32::from(num_not_migrated))
            .saturating_mul(MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT)
            .saturating_add(
                u32::from(self.num_non_builtin_instructions.0)
                    .saturating_add(u32::from(num_migrated))
                    .saturating_mul(DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT),
            )
    }
