### Title
Permissionless `DepositDelegatorRewards` can grief vote accounts by trapping funds behind an inflated `pending_delegator_rewards` reserve - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The Agave vote program's `DepositDelegatorRewards` instruction (SIMD-0123) lets *any* signer deposit lamports into *any* vote account and increment its `pending_delegator_rewards` counter, without requiring authorization from the vote account's withdraw authority. The `withdraw()` instruction then uses this counter to block full account closure and to enforce a minimum lamport reserve, meaning an unrelated, unprivileged actor can unilaterally place a withdrawal-blocking value on someone else's vote account — conceptually the same "state changed by someone else with no unblock path" bug class as the referenced blocklist finding.

### Finding Description
`deposit_delegator_rewards` only requires the *source* account to sign the transfer; it never checks that the caller is the vote account's authorized withdrawer/voter: [1](#0-0) 

The deposited amount is added to `pending_delegator_rewards` via `add_pending_delegator_rewards`, which is a pure `checked_add` with no corresponding permissioned "remove"/"cancel" entry point exposed to the withdrawer: [2](#0-1) 

`withdraw()` then treats `pending_delegator_rewards` as a hard gate: a full-balance withdrawal (account close) is rejected outright if `pending_delegator_rewards > 0`, and any partial withdrawal must leave at least `rent_exempt_minimum + pending_delegator_rewards` in the account: [3](#0-2) 

The only code path that reduces `pending_delegator_rewards` is `calculate_block_reward`, invoked during Alpenglow epoch-reward distribution, and only for vote accounts that have active delegated stake tracked in `reward_epoch_delegated_stakes` for that epoch: [4](#0-3) 

This mirrors the reported bug class precisely: a state field (`blocklist` membership → here `pending_delegator_rewards`) that gates a withdraw/undelegate-style operation can be set by an external, non-consenting party, the affected account has no self-service function to clear/"unblock" it, and the only remediation path is an indirect, conditional mechanism (blocklist redeploy → here, waiting on epoch-based Alpenglow reward distribution, which requires the vote account to have active stake in that specific reward epoch).

### Impact Explanation
An attacker can deposit as little as 1 lamport (or any nonzero amount) into a target vote account they do not control, immediately preventing the withdraw authority from fully closing/withdrawing the account and forcing them to keep the deposited amount permanently reserved until the automatic reward-distribution mechanism reduces the counter — which does not happen at all if the vote account is not part of an active reward-eligible delegation set for a given epoch (e.g., low/no stake, non-Alpenglow epoch). This is a griefing/fund-lock issue against validator vote accounts rather than direct fund theft, matching the "false execution/acceptance"/fund-lock category rather than theft, and is exploitable by any unprivileged party with no special role.

### Likelihood Explanation
The instruction is permissionless by design (SIMD-0123 intentionally allows third parties to deposit delegator rewards), so triggering the griefing primitive requires only a single signed transaction with a tiny lamport transfer — no validator/admin/trusted-party assumption is needed, satisfying the "unprivileged" requirement. The blocking effect is deterministic given the `withdraw()` guard logic shown above.

### Recommendation
Decouple "minimum reserved balance" enforcement from allowing full closure semantics that an unrelated depositor can weaponize, or add an authorized-withdrawer-only instruction to sweep/zero out `pending_delegator_rewards` (paying it out immediately) so the withdraw authority is never permanently blocked by third-party deposits, independent of whether the account is part of the epoch's active reward distribution set.

### Proof of Concept
1. Attacker calls `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` on a victim vote account, signing only as the deposit source (no vote-account authority required) — see `deposit_delegator_rewards` at [1](#0-0) .
2. `add_pending_delegator_rewards` increments the victim's `pending_delegator_rewards` to `1` [2](#0-1) .
3. Victim's authorized withdrawer calls `Withdraw(<full balance>)`; the check `if pending_delegator_rewards > 0 { return Err(InstructionError::InsufficientFunds) }` rejects the close [5](#0-4) .
4. Any partial withdrawal is capped to `remaining_balance ≥ rent_exempt_minimum + pending_delegator_rewards`, permanently reserving at least the griefed amount [6](#0-5) .
5. The counter is only reduced through `calculate_block_reward` during epoch-based Alpenglow reward distribution for vote accounts with active delegated stake [4](#0-3) ; a vote account without qualifying active stake in the reward epoch has no path to clear the reserve, leaving it withdrawal-blocked indefinitely.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
