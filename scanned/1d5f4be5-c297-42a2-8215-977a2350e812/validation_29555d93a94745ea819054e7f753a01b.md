## Title
Per-IP connection-rate-limiter buckets can be reset to full capacity by an attacker-triggered LRU eviction, bypassing intended throttling - (File: `net-utils/src/token_bucket.rs`)

### Summary
`KeyedRateLimiter::maybe_shrink` (used by `ConnectionRateLimiter` to throttle QUIC connections per source IP) evicts the least-recently-used `TokenBucket` entries from an over-full DashMap shard whenever enough *new* keys have been inserted [1](#0-0) . If a bucket for a given key is evicted, the very next `consume_tokens` call for that same key allocates a brand-new bucket cloned from `prototype_bucket`, i.e. re-initialized to `initial_tokens`/`max_tokens` [2](#0-1) . This mirrors the reported bug class: a value meant to persist/accumulate over time (`oraclePrice`/here, remaining rate-limit budget tied to elapsed time since `last_update`) is silently reset to baseline by an operation an unprivileged actor can trigger (`requestCPIData`/here, inserting enough new keys to force `maybe_shrink`), defeating the throttling invariant the rest of the code relies on.

### Finding Description
`TokenBucket::update_state` grants new tokens strictly as a function of elapsed time since `last_update`, refilling toward `max_tokens` at `new_tokens_per_us` [3](#0-2) . This is the accumulator whose correctness the whole rate-limiting scheme depends on — the analog of `oraclePrice`/`startTime` in the reported issue.

`KeyedRateLimiter` stores one `TokenBucket` per key (e.g., per source `IpAddr`) in a sharded `DashMap`, using a lazy LRU policy to bound memory: every time a *new* key is inserted, a countdown decrements, and when it reaches zero `maybe_shrink()` is invoked [4](#0-3) . `maybe_shrink` walks each shard and, if it exceeds `1.5x` the target shard size, keeps only the `target_shard_size` entries with the most-recent `last_update`, dropping the rest [1](#0-0) .

`ConnectionRateLimiter::register_connection` (used to gate QUIC connections per IP, unprivileged/remote-facing) simply calls `consume_tokens` for the connecting IP [5](#0-4) . When a key is absent from the map (because it was never seen, or because it was evicted), `consume_tokens` treats it as brand new and clones `prototype_bucket` — restoring full token capacity — rather than reconstructing what the bucket's state "should" be based on historical consumption [2](#0-1) .

The broken invariant: the rate limiter assumes a key's remaining budget only changes via time-based refill (`update_state`) and consumption, i.e., it should monotonically reflect the true historical connection rate for that IP. But the LRU eviction path introduces an unauthenticated, attacker-reachable way to discard that history and instantiate a fresh, full-capacity bucket for an arbitrary key — exactly like `fulfill` recomputing `oraclePrice` from a reset `startTime` instead of compounding on the prior value.

Existing guards do not stop this because:
- Eviction is keyed purely on relative recency (`last_update`) within a shard, not on any attacker-resistant identity or quota; the number of distinct keys held per shard is bounded (`target_capacity`), so it is inherently finite and forceable.
- `is_allowed`/`register_connection` have no fallback logic to detect "this IP was throttled before eviction"; a missing entry is unconditionally interpreted as "never seen, allow" [6](#0-5) .
- The shrink trigger (`entry_added` counter reaching `shrink_interval`) is driven by the total count of new-key insertions, which an attacker can increase arbitrarily just by connecting from many distinct source IPs (QUIC connections carry a fully-verified source IP once a connection is confirmed and registered, so IP diversity is the attacker's only requirement, not spoofing).

### Impact Explanation
This affects an unprivileged, remote-facing surface — the QUIC connection-establishment path is explicitly gated by `ConnectionRateLimiter` to defend the TPU/QUIC listener against connection floods. By forcing repeated LRU evictions (e.g., establishing/registering connections from a spread of source IPs, potentially including the attacker's own throttled IP once it becomes the least-recently-updated relative to a churn of newer keys), an attacker can force their own previously-throttled bucket to be silently reset to full `initial_tokens`, and repeat this to indefinitely bypass the intended per-IP connection cap. This weakens (does not eliminate — depends on shard fill dynamics) protection against non-RPC remote resource exhaustion of the QUIC/TPU connection-handling path, which is within the accepted impact category ("non-RPC remote exhaustion/crash").

### Likelihood Explanation
Likelihood is moderate, not high: exploitation requires the attacker to generate enough distinct new keys within the same DashMap shard to push it over `1.5x target_shard_size` and to arrange for their own tracked IP to have a comparatively stale `last_update` at that moment, which is timing-dependent and somewhat probabilistic rather than deterministic on every attempt. It does not require any trusted role, malicious peer/validator assumption, or leaked keys — only an unprivileged network attacker capable of connecting from multiple source addresses, which is a normal capability for a DoS-motivated actor and not excluded by the stated scope.

### Recommendation
- Do not treat a missing key as "unseen, allow." When an entry has been evicted from the LRU but the caller can supply corroborating context (e.g. a persistent negative cache, or a strictly smaller `initial_tokens` for freshly (re)allocated buckets after eviction) avoid handing back full burst capacity.
- Alternatively, avoid resetting to `prototype_bucket`'s full state on every eviction/reinsertion churn; instead track eviction time separately and, on key reappearance shortly after eviction, seed the new bucket with reduced tokens (e.g., 0) rather than `initial_tokens`.
- Bound the rate at which distinct new keys can trigger shrink cycles, or size shards adaptively so that legitimate per-shard occupancy churn cannot be driven purely by attacker-controlled IP diversity within a short window.
- Add metrics/alerts on high churn/eviction rates in `KeyedRateLimiter` so operators can detect this bypass pattern in production.

### Proof of Concept
Conceptual reproduction (unit-test style), based on the existing `ConnectionRateLimiter` test [7](#0-6) :

1. Create `ConnectionRateLimiter::new(limit_per_minute, max_burst, num_shards)` with a small `target_capacity`/shard so eviction is easy to trigger (in production this is `CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD = 100_000`, but the same mechanics apply at scale [8](#0-7) ).
2. From IP `A`, call `register_connection` until tokens are exhausted (`is_allowed(&A) == false`), matching existing test behavior [9](#0-8) .
3. Register connections from a large number of other distinct IPs `B1..Bn` within the same shard as `A`, exceeding `target_shard_size * 3/2` for that shard, while not touching `A` (so `A`'s `last_update` becomes the stalest in the shard) [1](#0-0) .
4. This triggers `maybe_shrink`, which evicts `A`'s bucket (oldest `last_update`) via `select_nth_unstable_by_key`/`Reverse(last_update)` [10](#0-9) .
5. `A` reconnects: `is_allowed(&A)` now returns `true` again (`current_tokens` returns `None` for a missing key, which `is_allowed` treats as "never seen") [6](#0-5) , and `register_connection` allocates a fresh `TokenBucket` cloned from `prototype_bucket` with full `initial_tokens`/`max_burst` [2](#0-1) , fully resetting the throttle for `A` despite `A` having just been rate-limited.

Note: I was not able to fully verify end-to-end exploitability in the live QUIC pipeline (e.g., exact shard sizing under production `CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD`, and whether other layers such as `simple_qos.rs` or staked-connection prioritization mitigate this in practice) — a Devin session with the ability to run the streamer integration tests would be needed to confirm the exact exploitation window and quantify severity in production configuration.

    /// Updates internal state of the bucket by
    /// depositing new tokens (if appropriate)
    fn update_state(&self, now: u64) {
        // fetch last update time
        let last = self.last_update.load(Ordering::SeqCst);

        // If time has not advanced, nothing to do.
        if now <= last {
            return;
        }

        // Try to claim the interval [last, now].
        // If we can not claim it, someone else will claim [last..some other time] when they
        // touch the bucket.
        // If we can claim interval [last, now], no other thread can credit tokens for it anymore.
        // If [last, now] is too short to mint any tokens, spare time will be preserved in credit_time_us.
        match self.last_update.compare_exchange(
            last,
            now,
            Ordering::AcqRel,  // winner publishes new timestamp
            Ordering::Acquire, // loser observes updates
        ) {
            Ok(_) => {
                // This thread won the race and is responsible for minting tokens
                let elapsed = now.saturating_sub(last);

                // also add leftovers from previous conversion attempts.
                // we do not care about who uses the spare_time_us, so relaxed is ok here.
                let elapsed =
                    elapsed.saturating_add(self.credit_time_us.swap(0, Ordering::Relaxed));

                let new_tokens_f64 = elapsed as f64 * self.new_tokens_per_us;

                // amount of full tokens to be minted
                let new_tokens = new_tokens_f64.floor() as u64;

                let time_to_return = if new_tokens >= 1 {
                    // Credit tokens, saturating at max_tokens
                    self.add_tokens(new_tokens);
                    // Fractional remainder of elapsed time (not enough to mint a whole token)
                    // that will be credited to other minters
                    (new_tokens_f64.fract() / self.new_tokens_per_us) as u64
                } else {
                    // No whole tokens minted → return whole interval
                    elapsed
                };
                // Save unused elapsed time for other threads
                self.credit_time_us
                    .fetch_add(time_to_return, Ordering::Relaxed);
            }
            Err(_) => {
                // Another thread advanced last_update first → nothing we can do now.
            }
        }
    }

    pub fn consume_tokens(&self, key: K, request_size: u64) -> Result<u64, u64> {
        let (entry_added, res) = {
            let bucket = self.data.entry(key);
            match bucket {
                Entry::Occupied(entry) => (false, entry.get().consume_tokens(request_size)),
                Entry::Vacant(entry) => {
                    // if the key is not in the LRU, we need to allocate a new bucket
                    let bucket = self.prototype_bucket.clone();
                    let res = bucket.consume_tokens(request_size);
                    entry.insert(bucket);
                    (true, res)
                }
            }
        };

        if entry_added {
            if let Ok(count) =
                self.countdown_to_shrink
                    .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |v| {
                        if v == 0 {
                            // reset the countup to starting position
                            // thus preventing other threads from racing for locks
                            None
                        } else {
                            Some(v.saturating_sub(1))
                        }
                    })
            {
                if count == 1 {
                    // the last "previous" value we will see before counter reaches zero
                    self.maybe_shrink();
                    self.countdown_to_shrink
                        .store(self.shrink_interval, Ordering::Relaxed);
                }
            } else {
                self.approx_len.fetch_add(1, Ordering::Relaxed);
            }
        }
        res
    }

    #[allow(clippy::arithmetic_side_effects)]
    fn maybe_shrink(&self) {
        let mut actual_len = 0;
        let target_shard_size = self.target_capacity / self.data.shards().len();
        if target_shard_size == 0 {
            return;
        }
        let mut entries = Vec::with_capacity(target_shard_size * 2);
        for shardlock in self.data.shards() {
            let mut shard = shardlock.write();

            if shard.len() <= target_shard_size * 3 / 2 {
                actual_len += shard.len();
                continue;
            }
            entries.clear();
            entries.extend(
                shard.drain().map(|(key, value)| {
                    (key, value.get().last_update.load(Ordering::SeqCst), value)
                }),
            );

            entries.select_nth_unstable_by_key(target_shard_size, |(_, last_update, _)| {
                Reverse(*last_update)
            });

            shard.extend(
                entries
                    .drain(..)
                    .take(target_shard_size)
                    .map(|(key, _last_update, value)| (key, value)),
            );
            debug_assert!(shard.len() <= target_shard_size);
            actual_len += shard.len();
        }
        self.approx_len.store(actual_len, Ordering::Relaxed);
