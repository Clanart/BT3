### Title
Block-revenue reward sniping via `pending_delegator_rewards` proportional distribution by current-epoch stake snapshot - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
Agave's SIMD-0123 block-revenue-sharing mechanism accumulates delegator rewards in a vote account's `pending_delegator_rewards` field via the permissionless `DepositDelegatorRewards` instruction, and later splits that entire accumulated pool among stakers using only their *current* effective stake at the reward epoch relative to the vote account's total active stake — with no accounting for how long each stake was actually delegated while those rewards accrued. This is the same "current share ratio" flaw described in the BellumNursery report: a staker who delegates immediately before the epoch boundary can claim a full pro-rata share of rewards that accumulated (potentially over many prior epochs) before they staked.

### Finding Description
`pending_delegator_rewards` on a vote account can be increased by anyone at any time via `deposit_delegator_rewards`, which is a simple signer-gated lamport transfer plus a `checked_add`: [1](#0-0) [2](#0-1) 

There is no timestamp, epoch marker, or per-delegator record kept when a deposit is made — it is a single running total for the whole vote account.

At the epoch boundary, `calculate_block_reward` computes each stake account's share of this pool purely as `pending_delegator_rewards * stake / total_active_stake`, where `stake` is the delegation's *current* effective stake for the `rewarded_epoch` (via `delegation_effective_stake`) and `total_active_stake` is the vote account's total delegated stake for that epoch: [3](#0-2) 

This is invoked from `calculate_stake_rewards_and_commissions` for every stake delegation whenever `block_revenue_sharing` is enabled: [4](#0-3) 

Nothing in this computation differentiates a delegator that has been active for many epochs (while the deposits accrued) from one that activated in (or just before) `rewarded_epoch`. My search of `runtime/src/bank/` found no code that decrements or resets `pending_delegator_rewards` as part of this per-epoch payout calculation — the field is only ever read here, and mutated by the vote program's `deposit_delegator_rewards`/`withdraw` instructions. (I was not able to fully verify whether some other mechanism clears/reduces `pending_delegator_rewards` after distribution elsewhere in the codebase; this is a gap in my search, but it does not change the core defect: even if the pool is cleared post-distribution, the split for that distribution round is still based solely on the current-epoch stake ratio, not on how long each delegator held stake while the deposits accrued.)

Compare this to Agave's own inflation-reward path, which correctly guards against exactly this class of issue for `stake_reward` (non-block-revenue) points: it explicitly zeroes points earned in a stake's `activation_epoch`, and it accumulates points epoch-by-epoch from `credits_observed` forward rather than snapshotting a single ratio: [5](#0-4) 
No equivalent protection (e.g., excluding stake whose `activation_epoch == rewarded_epoch`, or requiring the deposit to be attributed only to stake active when it was deposited) exists in `calculate_block_reward`.

### Impact Explanation
An attacker (or a validator colluding with a large depositor) can:
1. Wait for a large `DepositDelegatorRewards` deposit to accumulate in a vote account's `pending_delegator_rewards` (block/MEV revenue sharing deposits are unprivileged and can be made by anyone at any time).
2. Delegate a large stake to that vote account just before the epoch boundary (subject only to normal stake activation warm-up, see Likelihood below).
3. At the next reward calculation, receive a proportional share of the *entire* accumulated `pending_delegator_rewards` pool, diluting long-term delegators' fair share of block-revenue rewards.

This is a fund-theft/unfair-distribution issue affecting SOL that should have accrued to long-term stakers, since block-revenue rewards intended for delegators who backed the validator over time are instead partially captured by short-term "snipers." It does not break consensus but does cause incorrect/unfair reward payouts (an "unprivileged issue causing fund loss" in the accounts/runtime reward-distribution path).

### Likelihood Explanation
Practical exploitation is constrained by Solana's stake warm-up mechanism: `delegation_effective_stake` applies the warm-up/cool-down rate, so a stake activated in the same epoch it targets normally has zero effective stake in `rewarded_epoch` (see the `JustActivated` skip logic used for inflation rewards). This means a pure "stake seconds before distribution" attack is largely mitigated for the *activation epoch* itself. However, the sniping window is still meaningfully larger than intended: an attacker only needs to delegate stake one epoch (an activation cycle) before a known/anticipated large deposit lands, well short of the multi-epoch commitment implied by "long-term staking," and can withdraw immediately after collecting the block-revenue share since block-revenue rewards (unlike inflation stake rewards) are not similarly gated by `activation_epoch == rewarded_epoch` checks in `calculate_block_reward`. Anyone can trigger deposits via `DepositDelegatorRewards`, and vote-account total stake / deposit amounts are public, making the timing attack observable and repeatable across epochs.

### Recommendation
Apply the same protections that already exist for inflation stake rewards to the block-revenue path in `calculate_block_reward`:
- Exclude or discount stake whose `delegation.activation_epoch == rewarded_epoch` (or more generally, stake that was not active for the epoch(s) in which the corresponding `pending_delegator_rewards` were deposited) from the block-reward pro-rata split, mirroring the `JustActivated` handling in `calculate_stake_rewards`.
- Track `pending_delegator_rewards` with per-epoch (or per-deposit) checkpoints of `total_active_stake` at deposit time, and distribute each deposit tranche according to the stake distribution that existed when it was deposited, rather than the stake distribution at payout time.
- Alternatively, require deposits to be attributed against a stake snapshot (similar to `RewardEpochDelegatedStakes`) taken at deposit time, so late stakers cannot retroactively claim shares of already-accrued deposits.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

                node_pubkey: identity.pubkey(),
                authorized_voter: identity.pubkey(),
                authorized_voter_bls_pubkey: bls_pubkey,
                authorized_voter_bls_proof_of_possession: bls_pop,
                ..VoteInitV2::default()
            };
            let mut vote_state = VoteStateV4::new(
                &vote_init,
                &voter_pubkey,
                &identity.pubkey(),
                &Clock::default(),
            );
            vote_state.pending_delegator_rewards = pending_delegator_rewards;
            let mut account = solana_account::AccountSharedData::new(
                1_000_000_000,
                VoteStateV4::size_of(),
                &solana_vote_program::id(),
            );
            account
                .serialize_data(&VoteStateVersions::new_v4(vote_state))
                .unwrap();
            VoteAccount::try_from(account).unwrap()
        };

        let vote_accounts = [(voter_pubkey, (total_stake, vote_account))]
            .into_iter()
            .collect();
        let ag_epoch_type = AlpenglowEpochType::Alpenglow {
            migration_epoch: 0,
            reward_epoch_delegated_stakes: RewardEpochDelegatedStakes {
                epoch: rewarded_epoch,
                delegated_stakes: [(voter_pubkey, total_stake)].into_iter().collect(),
            },
        };

        let delegation = Delegation {
            voter_pubkey,
            stake: individual_stake,
            activation_epoch: u64::MAX, // boostrap stake so it's fully active
            ..Default::default()
        };

        let mut stake_history = StakeHistory::default();
        for epoch in 0..=rewarded_epoch {
            stake_history.add(epoch, StakeHistoryEntry::with_effective(total_stake));
        }

        let use_fixed_point_stake_math = true;
        let new_warmup_cooldown_rate_epoch = Some(0);

        calculate_block_reward(
            rewarded_epoch,
            &delegation,
            &stake_history,
            &vote_accounts,
            &ag_epoch_type,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        )
    }
