### Title
Per-IP QUIC connection rate limiter can be bypassed via check-then-act race, enabling free connection-slot exhaustion - (streamer/src/nonblocking/quic.rs)

### Summary
The QUIC connection-accept path enforces per-IP throttling by calling `ConnectionRateLimiter::is_allowed()` — a **read-only** check — synchronously in the accept loop, and only consumes a token via the separate `register_connection()` method, whose actual invocation happens later inside the asynchronously spawned `setup_connection` task. Because the check and the token-consuming mutation are split across two different points in time (and across a `tokio::spawn` boundary), an unprivileged remote peer can open many concurrent connection attempts from the same IP before any of them reaches the point where a token is actually deducted, defeating the intended per-IP cap at effectively zero cost — conceptually the same "check with no accounting cost lets you keep re-triggering a control meant to be rate-limited" pattern as the Zivoe `depositReward(0)` bug, where reading/mutating shared state cheaply let an unprivileged caller repeatedly bypass an intended limiting mechanism.

### Finding Description
`ConnectionRateLimiter` exposes two separate operations:
- `is_allowed(ip)` — a pure lookup of `current_tokens(ip) > 0`, does **not** mutate the bucket. [1](#0-0) 
- `register_connection(ip)` — the only method that actually calls `consume_tokens`, i.e. debits the bucket. [2](#0-1) 

In the QUIC accept loop, `rate_limiter.is_allowed(&incoming.remote_address().ip())` is checked synchronously for each newly accepted `Incoming` connection, and if it passes, the connection setup is handed off to an asynchronously spawned task (`tasks.spawn(setup_connection(...))`) rather than being registered/consumed at that same synchronous point. [3](#0-2) 

Because `is_allowed` never decrements the bucket, and the loop iterates rapidly over `FuturesUnordered` accept futures without waiting for `setup_connection` (where the corresponding `register_connection` call would eventually occur) to complete, a remote peer that fires many QUIC connection attempts from the same source IP in a tight burst can have all of them pass the `is_allowed` check before any single one reaches the point where a token is actually consumed. The rate limiter's own code comment acknowledges the intended invariant ("we should only modify server state once source IP is verified") but does not close the window between the check and the mutation across the async task boundary. [4](#0-3) 

This is the same broken-invariant shape as the Zivoe report: a cheap, unprivileged, repeatable call reads/extends shared limiting state without paying the cost the mechanism assumes it will pay, letting the caller keep the control from ever engaging as designed.

### Impact Explanation
If confirmed, this allows an unauthenticated remote peer (no stake, no validator identity required — this is the public TPU QUIC ingress) to exceed `max_connections_per_ipaddr_per_min` by simply issuing a burst of connection attempts. Combined with the global `ClientConnectionTracker::new` / `max_concurrent_connections` cap being checked per-connection rather than atomically with the per-IP limiter, an attacker could consume a disproportionate share of the server's open-connection budget, degrading or denying legitimate stake-weighted QUIC/TPU traffic — a non-RPC remote exhaustion/degradation impact.

### Likelihood Explanation
Likelihood depends on exactly how quickly `setup_connection` reaches its `register_connection` call and how many accept events the `FuturesUnordered` loop can process before that happens. I was not able to view the body of `setup_connection` (where `register_connection` is presumably invoked) within the available context, so I cannot fully confirm the size of the race window or whether an intervening synchronous check exists there. This is the main gap in verifying real-world exploitability and should be checked directly in the full `streamer/src/nonblocking/quic.rs` file.

### Recommendation
Move the token consumption (`register_connection`) to the same synchronous point as the `is_allowed` check in the accept loop (i.e., check-and-consume atomically) rather than deferring it to the asynchronously spawned `setup_connection` task, so concurrent connection attempts from the same IP cannot all observe an unconsumed bucket.

### Proof of Concept
Not independently reproduced — this analysis is based on static code reading of the split `is_allowed`/`register_connection` API and the accept-loop/async-spawn structure. Confirming the race would require instrumenting `setup_connection` to see whether `register_connection` is deferred behind the QUIC handshake (which would make the exploitation window on the order of a full handshake RTT, making the bypass practically significant), and then demonstrating with concurrent connection attempts from one IP that more connections are accepted than the configured per-IP-per-minute limit allows.

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
