### Title
Vote account `pending_delegator_rewards` pool reused across epochs for block-reward share computation without confirmed decrement, mirroring the "withdrawn amount not reduced" invariant break - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The reported bug's root cause is a "pool" accounting variable (`withdrawnStakingEarnings`/`withdrawnFeeEarnings`) that is used to compute a participant's proportional share of a shared pool, but is never reduced when the underlying pool total is reduced by a payout — causing subsequent share computations to use a stale, inflated denominator/numerator and pay out more than the vault holds. The closest Agave analog is the SIMD-0123 delegator block-reward mechanism, where `pending_delegator_rewards` on a `VoteStateV4` account is the shared pool from which per-stake-account `block_reward` shares are computed every epoch via `calculate_block_reward`, and delegators withdraw against the same pool via `withdraw()`'s reserved-balance check [1](#0-0) .

### Finding Description
`calculate_block_reward` computes each stake account's share of a vote account's `pending_delegator_rewards` pool proportionally to `stake / total_active_stake`, capping the result at `pending_delegator_rewards` [2](#0-1) . This per-account `block_reward` is then credited to the stake account's lamports during partitioned distribution in `build_updated_stake_reward` and summed into `block_reward_lamports_distributed` [3](#0-2) [4](#0-3) .

Separately, `pending_delegator_rewards` is used by `withdraw()` as a lamport reservation: the authorized withdrawer cannot withdraw the vote account balance below `rent_exempt_minimum + pending_delegator_rewards`, and cannot close the account at all while `pending_delegator_rewards > 0` [5](#0-4) . The field is only ever *increased* by `deposit_delegator_rewards`/`add_pending_delegator_rewards` in the code paths I inspected [6](#0-5) . A repository-wide search for any subtraction/decrement of `pending_delegator_rewards` (`-=`, `checked_sub`, `saturating_sub`) returned zero matches anywhere in the codebase.

This is structurally identical to the reported bug: `pending_delegator_rewards` plays the role of `totalEarnings`/`totalFees` — a shared pool that is read repeatedly to compute payout shares (`calculate_block_reward`) and to gate withdrawals (`withdraw()`), but if it is never reduced when block rewards are actually paid out of it, then (a) the vote account's lamport reservation for delegators in `withdraw()` stays permanently inflated even after the underlying rewards have already been distributed to stakers, and/or (b) if `pending_delegator_rewards` is meant to be the literal lamport-backing for `block_reward` payouts and is not decremented, the vote account's real lamport balance backing that pool is silently depleted every epoch while the bookkeeping value stays flat — eventually causing `checked_sub_lamports`/`InsufficientFunds` failures or, if the pool is treated as still fully available, a repeat distribution of the same lamports across subsequent epochs (since `calculate_block_reward`'s cap is `min(pending_delegator_rewards)` — a value that never shrinks).

### Impact Explanation
If `pending_delegator_rewards` is not reduced when block rewards are distributed to stake accounts, the accounting invariant "pool balance == sum of amounts still owed" breaks in the same way as the reported vault bug: either (a) delegators are perpetually blocked from withdrawing the correct amount of principal (funds effectively frozen, since `withdraw()`'s minimum-balance check keeps reserving an amount that no longer reflects actual undistributed rewards), or (b) the same `pending_delegator_rewards` amount is treated as available for share calculation in a later epoch, causing the vote account to attempt to pay out lamports it no longer holds, hitting `checked_sub_lamports` failures during reward distribution (a runtime/accounts correctness issue), or successfully over-distributing if lamports happen to be replenished by unrelated deposits. This falls squarely within the in-scope "runtime, accounts" impact category (false execution / fund loss/mis-accounting).

### Likelihood Explanation
This is a bookkeeping-consistency question that triggers on every epoch boundary where a vote account has non-zero `pending_delegator_rewards` and active stake — i.e., every epoch SIMD-0123 is active for any voter accepting delegator deposits. However, I could not confirm from the code excerpts retrieved whether a decrement actually happens in a location I did not read in full (`vote_processor.rs`, `handler.rs`). This materially affects likelihood: if the decrement exists elsewhere, this finding is moot.

If no such decrement exists, add one so that `pending_delegator_rewards -= block_reward` (and the corresponding lamport debit from the vote account) occurs atomically with `build_updated_stake_reward`'s crediting of `block_reward` to the stake account, mirroring how `vaultEndedStakingEarnings`/`feeEarnings` must be reduced in the audited vault contract.
