### Title
`pending_delegator_rewards` is read and paid out per-epoch but has no corresponding decrement path, breaking the reward-liability invariant - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`pending_delegator_rewards` on a vote account is only ever incremented, via `VoteStateHandler::add_pending_delegator_rewards` [1](#0-0)  called from `deposit_delegator_rewards` [3](#0-2) . Every epoch, `calculate_block_reward` computes each staker's proportional share of the *full, undiminished* `pending_delegator_rewards` value and pays it out to stake accounts [4](#0-3) . I was unable to find any code path in `programs/vote/src/vote_state/handler.rs`, `programs/vote/src/vote_processor.rs`, or `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` that subtracts the distributed amount back out of `pending_delegator_rewards` after payout (a `grep` for any decrement of this field across the repo returned no matches outside of test setup code).

### Finding Description
The bug-class from the Tap report is: an accumulator meant to represent "amount currently owed/available" is consumed to compute a payout, but the bookkeeping that should shrink that accumulator after the payout is missing or incomplete, so the tracked liability and the real entitlement permanently diverge.

In Agave's SIMD‑0123 block-revenue-sharing design:
- `deposit_delegator_rewards` transfers real lamports into the vote account and calls `add_pending_delegator_rewards`, which only ever `checked_add`s to `v4.pending_delegator_rewards` [1](#0-0) .
- `calculate_block_reward` is invoked once per stake delegation, per epoch, and computes `pending_delegator_rewards * stake / total_active_stake`, capped at `pending_delegator_rewards` [5](#0-4) . This value (`block_reward`) is added directly to the staker's account lamports in `build_updated_stake_reward` (`account.checked_add_lamports(partitioned_stake_reward.block_reward)`), summed across all delegations of the vote account for that epoch.
- `withdraw()` in `programs/vote/src/vote_state/mod.rs` treats `pending_delegator_rewards` as an untouchable reserve that the authorized withdrawer cannot withdraw below [6](#0-5) , i.e. it is being used, on the withdrawer side, exactly like the Tap contract's `minimum`/`floor` — a floor below which spending is blocked.

The missing piece is the debit: nothing decrements `v4.pending_delegator_rewards` by the aggregate `block_reward` actually paid out for that vote account in a given epoch/distribution partition. This means:
1. The same `pending_delegator_rewards` figure is read and used as the numerator for the block-reward computation in every subsequent epoch, so stakers can be paid out from the same nominal pool repeatedly (analogous to the Tap bug where `tapped` should be reduced by what's actually withdrawn, but here the underlying pool used for the *calculation* input is never reduced at all).
2. Symmetrically, on the withdrawer side, the vote account's spendable balance is permanently capped by an ever-growing `pending_delegator_rewards` value that never shrinks even once the entitlement has already been paid out to delegators, causing the same "funds effectively lost to the intended recipient" outcome the Tap report described, just projected onto the withdraw-authority side instead of the delegator side.

This is exactly the failure mode the report calls out: the accounting field used to gate/derive a payout does not track the state after the payout occurs, so the invariant "liability decreases as it is paid" is broken.

### Impact Explanation
If confirmed end-to-end (see Likelihood/uncertainty note below), this breaks the fund-accounting invariant for the vote program's block-revenue-sharing mechanism (SIMD-0123 / SIMD-0392 family), which falls squarely in the "runtime/accounts" and "fund theft/loss" or "false execution/acceptance" categories called out as in-scope. A vote account's `pending_delegator_rewards` either (a) permanently locks the authorized withdrawer out of legitimately-spendable lamports (since `withdraw()` enforces it as a floor forever), or (b) if the same pool is repeatedly used as the basis for `calculate_block_reward` without depletion, delegators receive shares recomputed from a pool amount that no longer represents real, undistributed funds, which can desynchronize actual vote-account lamports from the value the reward-distribution logic assumes is still available for distribution.

### Likelihood Explanation
I was only able to confirm the increment path (`add_pending_delegator_rewards`) and the read/payout-computation path (`calculate_block_reward`); I could not, within the available tool budget, definitively trace whether some other code path elsewhere (e.g., in `distribute_reward_commissions` or a not-yet-indexed helper) decrements `pending_delegator_rewards` after distribution. My `grep_search` for any subtraction of this field across the whole repository turned up zero matches, which is suggestive but not conclusive proof of absence, since the index may not cover every file. This uncertainty should be resolved by directly reading `runtime/src/bank/partitioned_epoch_rewards/distribution.rs::distribute_reward_commissions` and any code that mutates a vote account's `pending_delegator_rewards` field during epoch-boundary processing.

### Recommendation
Verify, by reading the full epoch-rewards distribution pipeline (`begin_partitioned_rewards`, `distribute_reward_commissions`, `store_stake_accounts_in_partition`, `distribute_epoch_rewards_in_partition`), whether `pending_delegator_rewards` on the vote account is ever reduced by the aggregate `block_reward` paid out in a given epoch. If it is not, add an explicit, atomic decrement of `pending_delegator_rewards` by the total block reward distributed for that vote account for that epoch, performed alongside (in the same state transition as) the stake-account credit in `store_stake_accounts_in_partition`/`build_updated_stake_reward`, so the "available for distribution" pool and the withdraw-floor both reflect only truly-undistributed delegator rewards.

### Proof of Concept
Could not construct a concrete runnable PoC without confirming the debit path; the analysis is based on static code tracing of `add_pending_delegator_rewards`, `calculate_block_reward`, `build_updated_stake_reward`, and `withdraw`, cross-referenced with an exhaustive `pending_delegator_rewards` grep across the repository that found no decrement site. A Devin session with full file access and the ability to run the existing `test_calculate_block_reward_specific`/`test_withdraw_pending_delegator_rewards` test suites and add a multi-epoch integration test (deposit once, then call `calculate_block_reward`/distribute for two consecutive epochs and assert whether the second epoch's payout is spuriously non-zero, or whether `withdraw()`'s floor ever shrinks after distribution) would be needed to conclusively confirm or refute this finding.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
