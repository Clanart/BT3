## Title
Stale vote/stake delegation entries survive an account's ownership change in `StakesCache` - (File: `runtime/src/stakes.rs`)

### Summary
The external report's broken invariant is: *"an authority/privilege granted under a previous owner is not revoked when the owner changes, so the old owner's grant keeps functioning."* The closest verifiable analog in this codebase is `StakesCache::check_and_store`, which is the single choke point that keeps the Bank's in-memory view of stake/vote delegations in sync with on-chain account state. The code explicitly acknowledges via a `TODO` that it does **not** evict a cached vote/stake account entry when that account's owner changes away from the vote/stake program (it only evicts on the `lamports() == 0` path, and even then only if the *current* owner field still matches `vote_program`/`stake_program`).

### Finding Description
`check_and_store` is called on every account write to keep `Stakes<StakeAccount>` consistent with the ledger state used for staking/voting calculations: [1](#0-0) 

The function branches only on `account.owner()`, i.e. the account's *current* owner:
- If `lamports() == 0`, it removes the cached entry **only if** the current owner still equals `vote_program`/`stake_program` — [2](#0-1) .
- If `lamports() != 0` and the current owner is `vote_program` or `stake_program`, it re-derives and upserts the cached delegation — [3](#0-2) .
- **There is no `else` branch.** If an account was previously cached as a stake/vote delegation and its owner is later changed to anything other than `vote_program`/`stake_program` while carrying nonzero lamports, `check_and_store` silently does nothing — the stale delegation entry from the old owner is left in `Stakes<StakeAccount>`.

The code itself documents this exact gap:
```
// TODO: If the account is already cached as a vote or stake account
// but the owner changes, then this needs to evict the account from
// the cache. see:
// https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
``` [4](#0-3) 

This is structurally identical to the reported bug class: the "access key" (here, the cached stake/vote delegation record derived while owner = stake/vote program) is not tied to, or revoked with, the current owner. Once ownership legitimately moves away from the stake/vote program, the old delegation record keeps exerting influence on stake-weighted computations (leader schedule, vote credit accounting, etc.) that are supposed to only reflect accounts currently owned by those programs.

### Impact Explanation
`Stakes<StakeAccount>` backs consensus-critical computations (stake-weighted leader schedule, vote account bookkeeping) rooted in the Bank. If a stale/incorrect delegation persists after a legitimate owner change, the Bank could count stake or vote weight for an account no longer controlled by the stake/vote program, producing an incorrect view of the stake distribution. That falls into the "false execution/rooting/acceptance" / "consensus" impact category named in the task's valid-impact list.

### Likelihood Explanation
I could not fully confirm a concrete, unprivileged transaction sequence that changes a stake/vote account's owner away from `stake_program`/`vote_program` while keeping lamports nonzero and reusing cached data, because:
- Neither the stake program nor the vote program exposes an instruction that reassigns account ownership to an arbitrary program.
- `system_processor::create_account`/`assign` normally requires the account to already be owned by the System program to be reassigned, which is the standard runtime-enforced invariant (only the current owning program may change `owner`).

I was not able to complete tracing `system_processor.rs`'s `create_account`/`assign` checks or all `check_and_store` call sites in `runtime/src/bank.rs` within the available tool budget, so I cannot rule in or rule out a specific reachable path (e.g., account closing/reallocation sequences, or interaction with `accounts-db`'s zero-lamport account pruning) that could trigger the missing-eviction branch under normal transaction processing rather than only via a hypothetical/administrative account substitution. This is a known, developer-acknowledged gap (the TODO references solana-labs/solana#24200) rather than a confirmed exploitable path in this snapshot.

### Recommendation
- In `StakesCache::check_and_store`, evict any existing cached vote/stake entry for `pubkey` whenever the *previous* cached entry's owner no longer matches the *current* account owner, not only when `lamports() == 0`.
- Alternatively, track owner alongside the cached delegation and always validate current owner against `vote_program`/`stake_program`, removing the entry on any mismatch regardless of lamport balance.

### Proof of Concept
No end-to-end unprivileged transaction sequence was verified within the available investigation; the finding is based on the acknowledged code gap (`TODO` comment) in `check_and_store` at [5](#0-4) . Confirming exploitability would require tracing every call site of `check_and_store` in `runtime/src/bank.rs` and the account-owner-reassignment invariants enforced by `programs/system/src/system_processor.rs`, which was not completed due to tool-budget exhaustion.
