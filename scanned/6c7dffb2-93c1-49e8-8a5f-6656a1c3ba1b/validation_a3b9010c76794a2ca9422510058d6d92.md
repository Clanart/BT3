### Title
Partitioned epoch-reward distribution silently burns earned inflation rewards when a stake account legitimately mutates between the calculation and payout blocks - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Solana pays out inflation rewards to stake accounts using a two-phase, multi-block "partitioned epoch rewards" mechanism: rewards are calculated once at the epoch boundary from a snapshot of the `StakesCache`, and then paid out several blocks later, one partition per block, in `distribute_partitioned_epoch_rewards` / `store_stake_accounts_in_partition`. This is structurally identical to the Yieldy bug: a value is computed against state at time T, but the corresponding "commit" action only happens at time T+N, and any legitimate state change to the same key in between silently breaks the accounting instead of being reconciled.

### Finding Description
`begin_partitioned_rewards` (calculation.rs:241) computes `PartitionedStakeReward`s for every stake account from a `StakesCache` snapshot taken at the epoch boundary, then schedules payout `REWARD_CALCULATION_NUM_BLOCKS` blocks later, spread across `num_partitions` further blocks [1](#0-0) .

When the scheduled block for a stake's partition arrives, `build_updated_stake_reward` looks the account up again in the *current* `StakesCache` by pubkey:
```
let stake_account = stakes_cache_accounts
    .get(&partitioned_stake_reward.stake_pubkey)
    .ok_or(DistributionError::AccountNotFound)?
``` [2](#0-1) 

If that pubkey is no longer present in the cache — which happens whenever the account's lamports reach zero (fully withdrawn/closed, e.g. via `Split` that drains the source, or `Withdraw` of a fully-deactivated stake) — `store_stake_accounts_in_partition` treats this as an error and **burns** the computed reward instead of crediting it anywhere:
```
Err(err) => {
    ...
    stake_reward_lamports_burned += stake_reward_amount;
    block_reward_lamports_burned += block_reward_amount;
}
``` [3](#0-2) 

Crucially, `stake_reward_lamports_burned` is never added back to capitalization or paid to any account — only `stake_reward_lamports_minted` increases capitalization in `distribute_epoch_rewards_in_partition` [4](#0-3) . The burned amount is only used to keep the `EpochRewards` sysvar's accounting consistent (`update_epoch_rewards_sysvar(stake_reward_lamports_minted + stake_reward_lamports_burned, ...)`), i.e. the reward is marked "distributed" from the sysvar's point of view even though the staker never receives it.

The code's own comment on `store_stake_accounts_in_partition` states the (incorrect) assumption underlying this design:
> "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned." [5](#0-4) 

This mirrors exactly the flawed assumption in the Yieldy report: a guard/design is assumed to make a race condition impossible, but a completely ordinary, unprivileged user action taken in the gap between "record" and "commit" breaks that assumption, and the protocol's response to the mismatch is to drop the user's entitlement rather than reconcile it. Only one narrow case (rent-driven zeroing of a still-existing delegation, handled via `adjust_delegations_for_rent` / `delegation_may_need_adjustment`) is reconciled at distribution time [6](#0-5) ; full account closure (pubkey removed entirely from `stake_delegations`) is not handled at all and falls straight into the burn path.

The `StakesCache` itself confirms an account disappears from the map the instant its lamports hit zero, independent of the reward-distribution window:
```
if account.lamports() == 0 {
    ...
    } else if stake_program::check_id(owner) {
        stakes.remove_stake_delegation(...)
    }
    return;
}
``` [7](#0-6) 

### Impact Explanation
This is a fund-loss bug: an unprivileged staker's already-earned inflation reward for the prior epoch (calculated at the epoch boundary and represented as an entitlement in the pending `PartitionedStakeReward` list) is permanently forfeited if that staker performs a normal, unprivileged action — such as `Split`ing all lamports out of the stake account or `Withdraw`ing a fully-deactivated stake to zero — during the window between reward calculation and the specific block at which that account's partition is paid out. The lamports are neither delivered to the staker nor returned to the treasury/incinerator; they simply vanish from `capitalization` accounting via the burn path. This directly matches the "valid impact" categories of unprivileged fund loss in the runtime/accounts/built-in program surface.

### Likelihood Explanation
The distribution window spans multiple real blocks (`REWARD_CALCULATION_NUM_BLOCKS` for calculation-to-distribution-start, plus one further block per partition), during which ordinary transactions continue to be processed. Any staker whose stake account happens to be selected for a later partition, and who independently closes/splits/withdraws that account before their specific partition block arrives, will trigger this path with no special timing knowledge or malicious intent required — it can even happen accidentally (e.g., an automated staking bot that withdraws immediately once its stake is fully deactivated). This makes the likelihood non-trivial, though it requires the staker's own stake to have a pending reward and to independently decide to fully close the account in a multi-block window they cannot easily predict from outside.

### Recommendation
- At distribution time, if a stake pubkey is missing from `StakesCache` because its lamports were legitimately drained to zero, credit the pending reward to the account's last-known state before closure (e.g., pay it to the withdraw destination or re-create/refund via the treasury) instead of unconditionally burning it, mirroring how `adjust_delegation_for_rent` reconciles the rent-adjustment case.
- Alternatively, prevent a stake account from being closed to zero lamports while it still has a pending, uncredited `PartitionedStakeReward` outstanding in the current epoch's reward status, analogous to a "cooldown" that fully processes the entitlement before allowing account closure — similar in spirit to the Yieldy team's own mitigation of increasing `coolDownPeriod` to avoid to the ambiguous window entirely.
- At minimum, ensure `stake_reward_lamports_burned` is accounted for as an explicit, auditable loss (rather than silently matching the sysvar's `distributed_rewards` counter) so operators can detect when stakers are losing rewards this way.

### Proof of Concept
1. At an epoch boundary, staker A has a stake account with an active delegation and accrued voting credits; `begin_partitioned_rewards` computes and schedules a `PartitionedStakeReward` for A's stake pubkey to be paid several blocks later (`distribution_starting_block_height` + partition offset).
2. Before A's specific partition block is processed, staker A's stake has already fully deactivated in a prior epoch (effective stake = 0) and A submits a normal `Withdraw` instruction draining all remaining lamports, or a `Split` moving 100% of lamports to a new stake account. Both are ordinary, unprivileged stake-program operations.
3. `StakesCache::check_and_store` sees `account.lamports() == 0` for the original pubkey and calls `remove_stake_delegation`, deleting it from `stake_delegations` [7](#0-6) .
4. When the scheduled partition block arrives, `build_updated_stake_reward` fails to find the pubkey and returns `DistributionError::AccountNotFound` [2](#0-1) ; `store_stake_accounts_in_partition` adds the reward amount to `stake_reward_lamports_burned` instead of paying it to anyone [3](#0-2) .
5. `distribute_epoch_rewards_in_partition` never adds `stake_reward_lamports_burned` to `capitalization`, so staker A's already-computed inflation reward is permanently lost, while the `EpochRewards` sysvar bookkeeping treats it as "distributed" [8](#0-7) .

This scenario is directly acknowledged as an untested assumption in the existing code comment (`store_stake_accounts_in_partition`, "there should never be rewards burned") rather than being defended by any actual invariant enforced by the stake program against closing an account with a pending reward.

/// at distribution time.

        // unlike a requested deactivation which happens at the next epoch

        }

}
