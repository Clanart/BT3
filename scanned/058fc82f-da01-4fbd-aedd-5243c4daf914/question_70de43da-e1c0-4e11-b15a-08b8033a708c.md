Target: `ClementineAggregator::withdraw` operator-selection field `operator_xonly_pks`. Attacker action: attacker sends unauthenticated `Withdraw` specifying only a single, honest operator's `operator_xonly_pks` entry for a withdrawal_id the attacker fabricated (no real Citrea withdrawal), attempting to force that one operator into a payout flow while excluding others from ever seeing/vetoing the request. Preconditions: `client_verification=false`; multiple operators configured. Call sequence: request reaches `AggregatorServer::withdraw` unauthenticated, which per its own doc only forwards to the operators listed in `operator_xonly_pks`, calling `Operator::withdraw` only on the targeted operator. Binding: the operator credited/targeted for withdrawal i == the operator the Citrea Bridge contract's withdrawal record designates, which is false since no such record exists and the attacker chose the target directly. Impact: Critical - if the targeted operator's own `withdraw` validation has any gap, this open aggregator path lets an attacker single out one operator for an unauthorized payout attempt with the caller-authority layer that should have blocked it before reaching the operator entirely absent. Proof idea: `cargo test` with `MockCitreaClient` lacking a withdrawal record, call `withdraw` from an unauthenticated client naming one operator's xonly pk, and assert the operator's `withdraw` RPC is invoked without any aggregator-level certificate check having occurred.
