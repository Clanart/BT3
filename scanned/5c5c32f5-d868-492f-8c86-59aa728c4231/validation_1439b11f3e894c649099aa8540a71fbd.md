## Analog identified: On-chain `Clock::unix_timestamp` may deviate substantially from true time within Agave's own drift-tolerance bounds

### Title
Consensus `Clock` sysvar accepts a stake-weighted timestamp within an asymmetric 25%/150% drift band of the PoH estimate instead of the true elapsed time — ([File: runtime/src/stake_weighted_timestamp.rs])

### Summary
The external report's root cause is a broad acceptance window (±10 minutes) around a game's `endTime` that lets a stale or future price be treated as the "final" one, flipping the outcome. The direct Agave analog is `calculate_stake_weighted_timestamp()` in [1](#0-0)  and its caller `Bank::update_clock()`/`get_timestamp_estimate()` in [2](#0-1) . Instead of requiring the on-chain `Clock::unix_timestamp` to track the PoH-estimated wall-clock time exactly, the runtime accepts any stake-weighted median timestamp that falls within `MAX_ALLOWABLE_DRIFT_PERCENTAGE_FAST = 25%` faster or `MAX_ALLOWABLE_DRIFT_PERCENTAGE_SLOW_V2 = 150%` slower than the PoH-derived offset since epoch start, as defined in [3](#0-2) .

### Finding Description
`get_timestamp_estimate()` collects each validator's last reported vote timestamp, computes a stake-weighted median, and then clamps it against `poh_estimate_offset` using the fast/slow percentages: [4](#0-3) . Because the clamp is a *percentage of elapsed time since epoch start* rather than a fixed small tolerance, the allowed deviation grows without bound as the epoch progresses — late in a long epoch, the accepted timestamp can be slow by 150% of the elapsed epoch duration (many minutes to hours), exactly mirroring the reported bug's "threshold window" pattern where a stale/future value is accepted as if it were the value at the exact intended instant.

This computed value is written directly into the `Clock` sysvar consumed by every unprivileged program and by runtime logic during ordinary transaction processing: [5](#0-4) . Programs and built-ins that gate behavior on `Clock::unix_timestamp` (e.g., time-based lockups, vesting, deadlines encoded via `unix_timestamp` such as the stake program's `Lockup.unix_timestamp` field referenced throughout [6](#0-5) ) therefore evaluate against a value that the protocol itself only guarantees to be within a wide band of the true elapsed time — not the true time.

Unlike the reported contract bug, no malicious validator is required: honest validators naturally vote with network-latency-driven timestamp skew, and the bound is deliberately generous (150% slow) to avoid halting the clock under normal jitter. That generosity is precisely what reintroduces the "accept-within-a-threshold" flaw the report describes, just at the runtime/consensus layer instead of an oracle callback.

### Impact Explanation
Any unprivileged transaction or program logic keyed off `Clock::unix_timestamp` (stake lockup expiry checks, vesting/time-locked withdrawals, deadline-based instruction gating) can execute against a clock value that is legitimately, protocol-permitted, minutes-to-hours away from true wall time. This can cause premature or delayed release of locked funds, or acceptance/rejection of time-gated instructions based on an incorrect "final" timestamp — the same class of impact as the reported bug (wrong-party fund distribution due to a stale/future value being accepted as authoritative).

### Likelihood Explanation
The drift bound is a permanent, always-active part of `update_clock()`, invoked every slot in [2](#0-1) ; it doesn't require an attack, only ordinary variance in validator vote timestamps, which is expected and unavoidable, especially as elapsed-since-epoch-start grows and the 150% slow bound widens.

### Recommendation
Tighten the slow-drift bound to a fixed absolute cap (independent of elapsed-epoch-time) rather than a percentage that grows unbounded through the epoch, similar to the report's recommendation to evaluate the reported value at the exact intended instant rather than within a wide tolerance window.

### Proof of Concept
Not applicable as a standalone exploit — the behavior is demonstrated by the existing unit tests `test_timestamp_slow`/`test_timestamp_fast` in [7](#0-6) , which show `bank.clock().unix_timestamp` deviating from the true `recent_timestamp` by up to the full 150%/25% bound, confirming that `Clock::unix_timestamp` can legitimately diverge from actual elapsed time by a large margin under the current drift-tolerance design.

                unix_timestamp = ancestor_timestamp;
            }
        }

#[test]
fn test_timestamp_slow() {
    fn max_allowable_delta_since_epoch(bank: &Bank, max_allowable_drift: u32) -> i64 {
        let poh_estimate_offset = poh_estimate_offset(bank);
        (poh_estimate_offset.as_secs()
            + (poh_estimate_offset * max_allowable_drift / 100).as_secs()) as i64
    }

    let leader_pubkey = solana_pubkey::new_rand();
    let GenesisConfigInfo {
        mut genesis_config,
        voting_keypair,
        ..
    } = create_genesis_config_with_leader(5, &leader_pubkey, 3);
    let slots_in_epoch = 32;
    genesis_config.epoch_schedule = EpochSchedule::new(slots_in_epoch);
    let (mut bank, _bank_forks) =
        Bank::new_for_tests(&genesis_config).wrap_with_bank_forks_for_tests();
    let slot_duration = Duration::from_nanos(bank.ns_per_slot as u64);

    let recent_timestamp: UnixTimestamp = bank.unix_timestamp_from_genesis();
    let additional_secs =
        ((slot_duration * MAX_ALLOWABLE_DRIFT_PERCENTAGE_SLOW_V2 * 32) / 100).as_secs() as i64 + 1; // Greater than max_allowable_drift_slow_v2 for full epoch
    update_vote_account_timestamp(
        BlockTimestamp {
            slot: bank.slot(),
            timestamp: recent_timestamp + additional_secs,
        },
        &bank,
        &voting_keypair.pubkey(),
    );

    // additional_secs greater than MAX_ALLOWABLE_DRIFT_PERCENTAGE_SLOW_V2 for an epoch
    // timestamp bounded to 150% deviation
    for _ in 0..31 {
        bank = Arc::new(new_from_parent(bank));
        assert_eq!(
            bank.clock().unix_timestamp,
            bank.clock().epoch_start_timestamp
                + max_allowable_delta_since_epoch(&bank, MAX_ALLOWABLE_DRIFT_PERCENTAGE_SLOW_V2),
        );
        assert_eq!(bank.clock().epoch_start_timestamp, recent_timestamp);
    }
}
