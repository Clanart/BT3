## Title
Vote account `pending_delegator_rewards` reward pool is never decremented when block rewards are minted to stakers — reward pool double-counting / capitalization desync analog of "mixed staked and reward funds" - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs], [File: programs/vote/src/vote_state/handler.rs])

### Summary
The external report's broken invariant is: a value meant to represent a *segregated reward pool* is read/spent without ever debiting the pool's internal accounting variable, so the same funds can be paid out repeatedly. Agave's SIMD-0123 delegator-rewards mechanism has the same shape: `pending_delegator_rewards` on the vote account is credited via `deposit_delegator_rewards`/`add_pending_delegator_rewards`, and is read every epoch by `calculate_block_reward` to compute each stake account's proportional share, which is then minted directly into stake accounts. No corresponding "subtract" of `pending_delegator_rewards` (or of the vote account's real lamport balance) exists anywhere in the codebase.

### Finding Description
`add_pending_delegator_rewards` is the only mutator of the `pending_delegator_rewards` field found in the codebase: [1](#0-0) 

It is incremented when funds are deposited via the `DepositDelegatorRewards` instruction, which performs a real system-program lamport transfer into the vote account and then bumps the counter: [2](#0-1) 

That counter is the *only* accounting mechanism that separates "reward funds owed to delegators" from the vote account's general lamports — it is exactly the kind of internal-accounting variable the external report recommends (analogous to `totalStake` in the fixed `StakingERC20.sol`). It is enforced on withdrawal, where the authorized withdrawer cannot pull the account below `rent_exempt + pending_delegator_rewards`: [3](#0-2) 

However, at epoch-reward time, `calculate_block_reward` reads `pending_delegator_rewards` from the vote account and computes each stake account's proportional share purely as a function of `stake / total_active_stake`, with no mutation of the vote account or its `pending_delegator_rewards` field: [4](#0-3) 

The computed `block_reward` is then propagated into `PartitionedStakeReward.block_reward` and, at distribution time, minted straight into the stake account's lamports via `checked_add_lamports`: [5](#0-4) 

Capitalization bookkeeping in `distribute_epoch_rewards_in_partition` only adjusts `capitalization` for `stake_reward_lamports_minted` (inflation) and `block_reward_lamports_burned`; `block_reward_lamports_distributed` never causes a capitalization or vote-account lamport decrease: [6](#0-5) 

I was unable to find, anywhere in the codebase (`pending_delegator_rewards -=`, `checked_sub`, or any "subtract"/"consume" helper), code that reduces `pending_delegator_rewards` or debits the vote account's lamports after a block reward is paid out. `distribute_reward_commissions` (`load_and_reward_commission_accounts`/`store_commission_accounts_partitioned`) handles the validator's *commission* cut, a separate code path from the per-staker `block_reward` minted in `build_updated_stake_reward`, and does not appear related to consuming `pending_delegator_rewards` either.

### Impact Explanation
If `pending_delegator_rewards` is genuinely never decremented after being paid out as `block_reward`:
- The same deposited reward pool would be treated as fully available every subsequent epoch, so `calculate_block_reward` would keep computing and minting a fresh share of the *same* nominal pool each epoch via `checked_add_lamports`, while the vote account's actual lamports (and its `pending_delegator_rewards` counter) are never reduced to match.
- Because `checked_add_lamports` mints lamports into the stake account without a corresponding debit from the vote account and without incrementing `self.capitalization` for the block-reward amount, this breaks the invariant that total lamports in the ledger equal the tracked `capitalization`. That invariant is checked by validators/consensus-critical bank hashing; if it silently diverges it can cause non-deterministic/mismatched bank hashes across validators (false-acceptance/consensus-divergence class), or duplicate payouts that inflate SOL supply from stake to stake accounts using the same underlying "reward" claim across multiple epochs — a fund-integrity/theft-style bug at protocol scale, not merely a display bug.
- This is unprivileged: it requires no malicious validator or trusted party — it is exercised purely by ordinary reward distribution once `block_revenue_sharing` and Alpenglow are active.

### Likelihood Explanation
Confidence is moderate, not certain. I confirmed:
- `add_pending_delegator_rewards` is the only writer of the field I could locate via exhaustive grep across the repo.
- The per-stake `block_reward` computed from `pending_delegator_rewards` is minted via `checked_add_lamports` with no visible vote-account debit in the reward-distribution path.

I could not fully trace `load_and_reward_commission_accounts` / `update_reward_commissions` (referenced in `distribute_reward_commissions`) within the tool budget, so it remains possible — though I found no evidence for it — that vote-account lamport debit and `pending_delegator_rewards` decrement happen inside one of those unexamined functions. This uncertainty should be resolved by directly reading `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` (the `load_and_reward_commission_accounts` and `store_commission_accounts_partitioned` bodies) and the `VoteAccounts`/vote program CPI paths invoked during `distribute_reward_commissions`, which the current tool access did not surface.

### Recommendation
Verify (and if absent, add) that:
1. Whenever `block_reward` is computed and paid out to a stake account, the vote account's `pending_delegator_rewards` is decremented by the same amount, and its actual lamports are debited (mirroring how `stake_reward_lamports_minted` is tracked against `capitalization`).
2. `distribute_epoch_rewards_in_partition` (or wherever the debit occurs) increases/decreases `self.capitalization` consistently for `block_reward_lamports_distributed`, so ledger lamports and tracked capitalization never diverge.
3. Add an invariant/assertion (similar to the existing `assert!` in `distribute_reward_commissions` checking `point_value.rewards >= distributed + ...`) that the sum of block rewards paid out per vote account across a distribution never exceeds that vote account's `pending_delegator_rewards`, and that the field converges to zero (or the correct residual) after distribution completes.

### Proof of Concept
Conceptual reproduction (requires confirming the missing-decrement hypothesis against `load_and_reward_commission_accounts`):
1. Fund a vote account with `deposit_delegator_rewards(deposit = X)`, setting `pending_delegator_rewards = X` and transferring `X` real lamports into the vote account (`programs/vote/src/vote_state/mod.rs:936-988`).
2. Enable `block_revenue_sharing` + Alpenglow so `calculate_block_reward` executes (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`), giving each delegator's stake account a proportional share of `X`.
3. Across N successive epochs, `store_stake_accounts_in_partition` → `build_updated_stake_reward` mints `block_reward` into stake accounts via `checked_add_lamports` (`distribution.rs:262-267`) every epoch, using the same unreduced `pending_delegator_rewards = X` read from the vote account each time (since no epoch decremented it).
4. After N epochs, total lamports minted to stakers ≈ `N * X`, while the vote account still shows `pending_delegator_rewards = X` and its lamport balance was debited zero times — demonstrating the reward pool is not consumed/tracked correctly, diverging total ledger lamports from `capitalization`.

Confirming step 3's absence of debit requires reading the `load_and_reward_commission_accounts`/`store_commission_accounts_partitioned` implementations, which were not available within this session's tool budget — flagged here as the residual verification gap.
