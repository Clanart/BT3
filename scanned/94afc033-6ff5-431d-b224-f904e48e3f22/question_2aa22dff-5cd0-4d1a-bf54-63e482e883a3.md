target: `CircuitTransaction::mid_state_txid` (circuits-lib/src/bridge_circuit/transaction.rs). Attacker action: hand the bridge-circuit prover a `payout_spv.transaction` whose witness differs from the witness of the transaction actually mined on Bitcoin (same version/inputs/outputs/locktime) — e.g. swap the signature bytes of a segwit payout input. Preconditions: an operator has confirmed a Reimburse/Payout tx on regtest; attacker crafts an alternate serialization with identical non-witness fields but a bogus witness and submits it as `CircuitTransaction` inside `BridgeCircuitInput.payout_spv.transaction`. Call sequence: `CircuitTransaction::mid_state_txid` hashes `version`, `input` (script_sig/sequence/prevout only, no witness), `output`, `lock_time` -> `SPV::verify` accepts because `mid_state_txid` matches the mined tx's mid-state even though `Transaction.input[i].witness` differs. Binding: `self.transaction.inner()` (full attacker-supplied tx, including witness data later consumed for `payout_input_index` checks elsewhere in the bridge circuit) == the exact transaction whose witness was broadcast and confirmed on Bitcoin. Impact: Critical — if any downstream bridge-circuit logic keying off `payout_spv.transaction`'s witness (e.g. an OP_RETURN or script-path condition read from witness data) trusts this transaction as canonical, an attacker can splice in a different witness while `SPV::verify` still returns true, producing a `journal_hash` that misrepresents what was actually paid, letting a false claim be proven or a true claim be blocked. Proof idea: `cargo test` constructing two `Transaction`s identical except witness, verifying both produce the same `mid_state_txid` and that `SPV::verify` passes for the attacker's witness variant against the real block header, then asserting whichever downstream field is derived from witness diverges from the real tx.
