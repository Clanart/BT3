### Title
Alpenglow stake reward truncation permanently advances `credits_observed`, causing small stakers to earn zero inflation rewards forever - (`runtime/src/inflation_rewards/mod.rs`, `runtime/src/inflation_rewards/points.rs`)

### Summary
The Alpenglow reward-crediting path computes a stake's epoch points with integer division (`earned_credits * stake_amount / total_stake`), which truncates to zero for small stakes relative to total network stake. Unlike the Tower path, which defers redemption (does not advance `credits_observed`) when points round to zero, the Alpenglow path unconditionally advances `credits_observed` even when the computed reward truncates to zero. This is structurally the same bug class as the reported "H-04" issue: a per-period accumulator can be permanently starved of value while its "last updated" checkpoint (here, `credits_observed`) keeps moving forward, discarding the truncated remainder forever instead of letting it accrue.

### Finding Description
`calculate_alpenglow_points` computes the points a stake earned for a single reward epoch: [1](#0-0) 
`earned_points` is truncated by integer division against `total_stake`, which for the network can be on the order of the entire staked supply. For small individual stakes and a single epoch's earned credits, this expression can round to `0`.

The returned `new_credits_observed` is always advanced (via `calc_earned_credits`) regardless of whether `earned_points` truncated to zero: [2](#0-1) 

Back in `calculate_stake_rewards`, the Alpenglow branch checks `ag_points == 0` and calls `skip_reward`: [3](#0-2) 

`advance_credits_for_skipped_reward` is `true` whenever the epoch type is not Tower and credits changed — which is the normal case every epoch in Alpenglow. This means `skip_reward` returns `skipped_reward()`, which still reports `new_credits_observed` (the already-advanced value) with `staker_rewards: 0, voter_rewards: 0`: [4](#0-3) 

That result flows back into `redeem_stake_rewards`, which unconditionally commits `stake.credits_observed = calculated_stake_rewards.new_credits_observed` whenever `Some(...)` is returned — even for the zero-reward case: [5](#0-4) 

Contrast this with the Tower branch in the same function, which returns `None` outright (no `credits_observed` commit) when `tower_points == 0`, allowing the un-credited/un-rewarded epoch's earned credits to persist and accumulate across multiple epochs until they eventually cross the rounding threshold and produce a nonzero reward: [6](#0-5) 

So the safeguard that exists for Tower ("don't move credits_observed forward if rounding would erase the reward") is absent for Alpenglow. In Alpenglow, `calculate_alpenglow_points` only ever looks at a single epoch's `reward_epoch_credits` entry (not an accumulated backlog since last observation), so once `credits_observed` is advanced with a zero reward, that epoch's fractional entitlement is gone permanently — there is no mechanism to carry the rounding remainder into a future epoch.

### Impact Explanation
Any stake account whose `stake_amount * earned_credits / total_active_stake` rounds down to zero in a given epoch receives zero inflation reward for that epoch and can never recover it, because `credits_observed` is force-advanced. For a validator/staker with minimum viable stake relative to a large total network stake (a very plausible, non-adversarial configuration — e.g., minimum stake vs. hundreds of millions of SOL total stake), this can repeat every epoch indefinitely, meaning the staker earns essentially zero rewards for the lifetime of their delegation despite being fully entitled to a share of inflation. This is a correctness/fund-loss issue in the reward distribution logic (protocol-level "false" reward accounting), not requiring any malicious peer, validator, or admin action — it is a natural consequence of a common stake-size distribution.

### Likelihood Explanation
This does not require an attacker: it happens naturally whenever a delegator's stake is small relative to total network stake, which is common. The truncation is deterministic and reproducible on every affected epoch, not something an attacker needs to craft (unlike the original report's need to manipulate `timeSinceLastUpdated`). The magnitude of the bug depends on network-wide stake concentration and per-account stake size, but the code path itself unconditionally exhibits the flaw whenever `earned_points` computes to `0` in the Alpenglow branch.

### Recommendation
In the Alpenglow branch of `calculate_stake_rewards` (`runtime/src/inflation_rewards/mod.rs`), do not advance `credits_observed`/commit the skip when the computed `ag_points`/reward rounds to zero — mirror the Tower branch's behavior of returning `None` (deferring redemption) so the stake's earned-but-truncated credits can accumulate across epochs until they produce a nonzero reward, instead of being discarded every epoch via forced credit advancement.

### Proof of Concept
1. Configure (or observe) a network state where `total_active_stake` for a vote account is large (e.g., representative of real-world total stake) and a delegated stake account has a small `delegation.stake` relative to that total.
2. Each epoch, `calculate_alpenglow_points` (`runtime/src/inflation_rewards/points.rs:280-301`) computes `earned_credits * stake_amount / total_stake`; with `earned_credits` bounded by slots-per-epoch and `stake_amount` small relative to `total_stake`, the result truncates to `0`.
3. `calculate_stake_rewards`'s Alpenglow branch (`runtime/src/inflation_rewards/mod.rs:278-285`) sees `ag_points == 0`, calls `skip_reward`, and — because `advance_credits_for_skipped_reward` is `true` for non-Tower epochs (`mod.rs:251-254`) — returns `Some(CalculatedStakeRewards { staker_rewards: 0, voter_rewards: 0, new_credits_observed })` instead of `None`.
4. `redeem_stake_rewards` (`mod.rs:124-144`) commits `stake.credits_observed = new_credits_observed` unconditionally on `Some(...)`, permanently discarding the truncated epoch's reward entitlement.
5. Repeating over subsequent epochs shows the stake account's `credits_observed` tracking the vote account's credits exactly, while `staker_rewards` remains `0` every epoch — confirming permanent zero-reward status for that delegation, unlike the Tower path where `tower_points == 0` returns `None` (mod.rs:286-298) and lets credits accumulate toward a future nonzero payout.

/// Returns how many credits the stake actually earned based on what it has already observed and
/// the vote account has recorded.
///
/// Also updates the `new_credits_observed` as a side effect.
fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
