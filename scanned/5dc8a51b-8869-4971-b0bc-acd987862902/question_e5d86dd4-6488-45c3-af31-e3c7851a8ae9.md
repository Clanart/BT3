`update_finalized_payouts` uses `get_first_op_return_output`, which returns the first output in the transaction whose `script_pubkey.is_op_return()`. Can an unprivileged attacker take the honest operator's broadcast payout tx (input 0 + output 0 fixed by the `SinglePlusAnyoneCanPay` signature), insert an *additional* OP_RETURN output before the real one (e.g. at output index 1, ahead of the anchor and the operator's real OP_RETURN at index 2) containing a different operator's xonly pk, and get this rearranged transaction mined, so `get_first_op_return_output` picks the attacker-inserted OP_RETURN instead of the operator's own? Preconditions: attacker only needs to preserve input 0 and output 0; may add/reorder any other outputs since they are unsigned by `SinglePlusAnyoneCanPay`. Binding broken: the operator xonly pk recorded for withdrawal i == the party whose funds paid that payout output (ATTRIBUTION). Impact: Critical - misattributes the withdrawal to an operator who never funded it, and denies the honest operator a valid Reimburse path once `is_kickoff_malicious` compares against the wrong stored pk. Proof idea: cargo test crafting a payout tx with two OP_RETURN outputs and asserting `get_first_op_return_output`/`parse_op_return_data` in `update_finalized_payouts` picks the attacker's, not the honest operator's real, xonly pk.
