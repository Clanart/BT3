Based on the code I was able to examine, I found a strong structural analog to the reported bug in the `Middleware` reward-distribution path. I could not fully verify the exact accounting fields in `mod.rs` (`RewardCommissionAccounts`/`RewardCommissionLamportAmounts`) due to running out of tool iterations, so I flag that as an open verification item below.

### Title
Vote-account (commission collector) closure between reward calculation and distribution silently drops validator commission rewards - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The external report describes a pattern where a shared, externally-mutable reference (`collateralToOracle`) that reward logic depends on can be removed by a state-changing action taken between when rewards are computed and when they are claimed, causing the dependent reward accounting to fail or misbehave for historical epochs. The closest Agave analog is in the partitioned epoch-rewards commission flow: reward commissions are *calculated* against a vote/commission account reference during `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards`, but the actual account is only *loaded* later, at distribution time, in `load_and_reward_commission_accounts` [1](#0-0) . If the commission account no longer exists when distribution runs, the code silently returns `None` for that commission entry instead of accounting the lost lamports as burned, mirroring the "dependency on live state for a value calculated in the past" problem in the original report.

### Finding Description
`redeem_delegation_rewards` computes reward commissions during the calculation phase for the previous epoch based on the vote account state captured in `distribution_epoch_vote_accounts` [2](#0-1) . The `commission_pubkey` (which, pre-SIMD-0232, is always the vote account itself) is recorded into `RewardCommissions`, but the actual account data is *not* re-fetched until the separate distribution phase, potentially at a different slot/block height.

At distribution time, `load_and_reward_commission_accounts` loads each planned commission account with `get_account_with_fixed_root_no_cache` [3](#0-2) . If `custom_commission_collector` is not active and the account is missing (e.g., because the vote account was closed by its own withdraw authority in the interim), the code logs a debug message and simply `return None`, dropping that reward entry from `accounts_with_rewards` without adding `*commission_lamports` to any burned-lamports counter [4](#0-3) . Only the caller-supplied `burned_lamports != 0` pre-condition increments the burn counter — the newly-discovered "missing at distribution time" case does not [5](#0-4) .

The downstream invariant check in `distribute_reward_commissions` only asserts an upper bound (`point_value.rewards >= distributed + incinerator + burned + total_stake_rewards`) [6](#0-5) , so under-accounting for silently dropped commissions does not trip the assertion — it just passes silently, exactly as the original report describes: existing guards (the invariant check) do not protect against the loss because they were designed to catch over-payment, not accounting for reward value that vanished because the referenced account no longer exists.

### Impact Explanation
This is a fund-loss bug: a validator operator's earned commission reward for the previous epoch can be permanently lost (never paid, and not properly reflected as burned in capitalization tracking) if their vote account is closed in the window between reward calculation and reward distribution within the same reward period. This directly parallels the reported issue's "vaults cannot claim rewards because the oracle/dependency used for the calculation no longer exists at claim time," except in Agave's case the effect is silent loss rather than a revert.

### Likelihood Explanation
Likelihood is low: closing a vote account requires the account's own withdraw authority to act (not an outside attacker), and pre-SIMD-0232 vote accounts additionally can only be closed if they haven't voted for a full epoch — a narrow, self-inflicted, low-probability timing window between the calculation and distribution phases of partitioned rewards.

### Recommendation
- When a planned commission account is missing at distribution time, explicitly account the dropped `commission_lamports` into the burned/incinerator totals so capitalization bookkeeping and the `distribute_reward_commissions` invariant reflect the loss rather than silently discarding it.
- Consider disallowing vote account closure while a reward calculation referencing that account is still pending distribution, or snapshot/lock the referenced account state for the entire reward calculation-to-distribution window.

### Proof of Concept
I could not construct a fully verified end-to-end PoC within the available tool budget; verification of the exact `RewardCommissionAccounts`/`RewardCommissionLamportAmounts` field definitions in `runtime/src/bank/partitioned_epoch_rewards/mod.rs` (to confirm no other code path re-adds the dropped lamports to burned totals) was not completed. The existing repo test `test_load_and_reward_commission_accounts_reflects_vat_burn` [7](#0-6)  demonstrates the general pattern of "commission account state can change between calculation and distribution," but does not itself cover the missing-account branch; a Devin session with full repo access would be needed to add a targeted test that closes the vote account between the calculation and distribution phases and asserts on the resulting burned/distributed totals.

    #[test]
    fn test_load_and_reward_commission_accounts_reflects_vat_burn() {
        let (genesis_config, _mint_keypair) = create_genesis_config(1_000 * LAMPORTS_PER_SOL);
        let bank = Bank::new_for_tests(&genesis_config);
        let thread_pool = ThreadPoolBuilder::new().num_threads(1).build().unwrap();
        let pubkey = solana_pubkey::new_rand();

        let pre_burn_balance = 10 * crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let commission_lamports = 12_345;

        // Commission is planned against the pre-burn account state.
        let mut commission_account = AccountSharedData::default();
        commission_account.set_lamports(pre_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &commission_account);
        let mut reward_commissions = RewardCommissions::default();
        reward_commissions.insert(
            pubkey,
            RewardCommission {
                commission_bps: Some(500),
                commission_lamports,
                burned_lamports: 0,
                is_vote_account: true,
            },
        );

        // Simulate the VAT burn that would run in `update_epoch_stakes`
        // between reward calculation and distribution.
        let post_burn_balance = pre_burn_balance - crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let mut burned_account = commission_account.clone();
        burned_account.set_lamports(post_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &burned_account);

        let result = bank.load_and_reward_commission_accounts(&reward_commissions, &thread_pool);

        assert_eq!(result.accounts_with_rewards.len(), 1);
        let (pubkey_result, reward_info, account) = &result.accounts_with_rewards[0];
        assert_eq!(*pubkey_result, pubkey);
        // Commission is credited on top of the post-burn balance, not the
        // pre-burn snapshot captured at calculation time.
        let expected_post_balance = post_burn_balance + commission_lamports;
        assert_eq!(account.lamports(), expected_post_balance);
        assert_eq!(
            *reward_info,
            RewardInfo {
                reward_type: RewardType::Voting,
                lamports: commission_lamports as i64,
                post_balance: expected_post_balance,
                commission_bps: Some(500),
            }
        );
        assert_eq!(result.amounts.distributed_lamports, commission_lamports);
    }
