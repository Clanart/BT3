Based on my research, the strongest local analog to the DYAD bug (unprivileged actor calling a state-mutating function that sets a per-slot/per-block guard, which is then used to grief a legitimate operation) is the `ExtendProgram` instruction in the BPF Loader Upgradeable program.

### Title
Permissionless `ExtendProgram` instruction lets any attacker grief a program's data extension by poisoning the per-slot guard - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The BPF Loader Upgradeable program exposes `UpgradeableLoaderInstruction::ExtendProgram`, which invokes `common_extend_program(invoke_context, additional_bytes, false)` with `check_authority = false`, meaning **no signature from the upgrade authority is required** to extend a program's `ProgramData` account. [1](#0-0)  This mirrors the DYAD `deposit()` flaw: a function that should be scoped to an authorized party (owner/authority) is reachable by anyone, and its side effect (writing a slot marker) can be weaponized to block a subsequent legitimate call from the real authority.

### Finding Description
Inside `common_extend_program`, the function reads the `ProgramData` account's stored `slot` and compares it to `clock_slot`; if they match, it fails with `"Program was extended in this block already"`: [2](#0-1) 

Because `ExtendProgram` performs no authority check (`check_authority=false`), any unprivileged account can submit a minimal `ExtendProgram` transaction (paying only the trivial rent-topup for a small number of additional bytes) against **any** program's `ProgramData` account they choose, as long as it is writable and owned by the loader. This call succeeds and updates the stored `slot` field to the current `clock_slot` when the extension completes, exactly like the DYAD attacker's `0`-value `deposit()` updating `idToBlockOfLastDeposit[id]` to `block.number`.

If the program's real upgrade authority then submits their own `ExtendProgram`/`ExtendProgramChecked` transaction in the same slot (e.g., as part of an urgent program resize before an `Upgrade`), it will hit the exact same `clock_slot == slot` guard and revert with `InvalidArgument`, exactly analogous to how the DYAD `withdraw()` call reverts due to `idToBlockOfLastDeposit[id] == block.number`.

### Impact Explanation
An attacker can repeatedly front-run or simply race the authority's `ExtendProgram` calls every slot, at negligible cost (a few lamports of rent difference for 1 extra byte), indefinitely delaying an authority's ability to resize a program's data account. Since resizing is often a prerequisite step before deploying a larger replacement program (including urgent security-patch upgrades), this griefing vector can stall an authority's ability to patch a vulnerable on-chain program, which could allow continued exploitation of that program (false acceptance of unpatched/vulnerable execution) for as long as the attacker sustains the grief.

### Likelihood Explanation
The attack requires no special privileges, no validator collusion, and no race-condition assumptions beyond ordinary transaction submission within the same slot — the attacker only needs to know the target `ProgramData` pubkey (public information) and submit a cheap transaction every slot. This is comparable in cost and complexity to the original DYAD PoC (a 0-value/1-wei deposit repeated every block).

### Recommendation
Require the upgrade authority's signature for `ExtendProgram` (i.e., treat it the same as `ExtendProgramChecked`, `check_authority = true`), removing the unauthenticated path entirely, or scope the per-slot guard so it only blocks re-extension by the same signer/authority rather than blocking any subsequent extension regardless of caller.

### Proof of Concept
1. Attacker identifies a target program's `ProgramData` account (`programdata_key`), owned by `bpf_loader_upgradeable`.
2. Attacker submits `UpgradeableLoaderInstruction::ExtendProgram { additional_bytes: 1 }` against that `ProgramData` account, paying the minor rent top-up themselves; this succeeds because `common_extend_program` is called with `check_authority = false` and requires no signer check on the authority. [1](#0-0) 
3. This sets the `ProgramData` account's stored `slot` field to the current `clock_slot`. [3](#0-2) 
4. In the same slot, the legitimate upgrade authority submits their own `ExtendProgram`/`ExtendProgramChecked` transaction to grow the account ahead of a critical `Upgrade`; it hits the `clock_slot == slot` check and reverts with `InstructionError::InvalidArgument`. [4](#0-3) 
5. Attacker repeats step 2 every subsequent slot, indefinitely denying the authority the ability to extend/resize the program data account.

**Caveat / uncertainty:** I could not fully verify within the available context whether `ExtendProgramChecked` (the authority-gated variant) was intended to fully replace `ExtendProgram` via a feature gate that disables the unchecked path once activated (the `feature-set` references to `ExtendProgram`/`ExtendProgramChecked` suggest a migration exists), which — if active — would reduce or eliminate this exposure. I was not able to trace that feature-gating logic before running out of search iterations, so this finding's real-world severity depends on whether that mitigation is active by default. If it is confirmed that a feature gate universally disables unchecked `ExtendProgram` once activated on mainnet, this finding would be moot; a Devin session with full file access should verify this before treating the finding as exploitable in production.
