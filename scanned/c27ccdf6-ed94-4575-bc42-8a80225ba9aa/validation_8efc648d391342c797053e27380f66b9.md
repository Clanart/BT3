## Analog Found: Decoupled block-size guards causing a leader-side panic in the broadcast stage

### Title
Leader panics instead of gracefully rejecting oversized blocks when compute-unit-bounded entries exceed shred capacity - (`turbine/src/broadcast_stage/standard_broadcast_run.rs`)

### Summary
The external report describes a class of bug where one subsystem's size guard (CometBFT's `max_tx_bytes`) is decoupled from the actual payload-producing subsystem (the execution/consensus layer), so legitimate content can silently exceed the guard and get rejected, threatening liveness. Agave has an analogous three-way decoupling between the compute-unit cost limit that gates what a leader packs into a block, the shred-index capacity that gates what can be broadcast, and a nominal byte-size cap that appears to sit unenforced between them. When the shred-capacity guard is hit, instead of failing safely the code panics.

### Finding Description
Agave defines three separate, independently-tuned per-slot limits in `runtime/src/slot_params.rs`:
- `cost_tracker_limits` (compute units, e.g. `60_000_000` for `LEGACY_SLOT_PARAMS`) [1](#0-0) 
- `max_data_shreds_per_slot` / `max_code_shreds_per_slot` (shred index capacity, `32_768` for `LEGACY_SLOT_PARAMS`, shrinking to `16_384` under the 200ms slot-time feature) [2](#0-1) 
- `max_entry_bytes_per_slot` (a nominal byte cap, e.g. `20 * 1024 * 1024`) [3](#0-2) 

Of these, only the compute-unit limit is what actually gates transaction inclusion while the leader packs a block: `CostTracker::try_add` compares accumulated `block_cost` against `limits.block_cost` and rejects a transaction with `WouldExceedBlockMaxLimit` if it would exceed that budget [4](#0-3) . Compute-unit cost is a function of signatures, write locks, and `INSTRUCTION_DATA_BYTES_COST`-weighted instruction data [5](#0-4) , not a direct measure of serialized byte size — so it does not guarantee that a maximally-packed block's serialized entries stay under either `max_entry_bytes_per_slot` or, more importantly, under the shred-index capacity.

The shred-index capacity is enforced much later, downstream in the broadcast stage, after transactions have already been accepted into the block and turned into PoH entries. `component_to_shreds` shreds the entries and then checks the resulting shred indices against the per-slot limits:

```
if self.next_shred_index > self.max_data_shreds_per_slot {
    return Err(BroadcastError::TooManyShreds);
}
if self.next_code_index > self.max_code_shreds_per_slot {
    return Err(BroadcastError::TooManyShreds);
}
``` [6](#0-5) 

This is the guard that is supposed to play the role of CometBFT's `max_tx_bytes` check. However, its caller, `process_receive_results`, does not handle the `Err` case — it unconditionally unwraps the result:

```
let shreds = self
    .component_to_shreds(
        keypair,
        &component,
        reference_tick as u8,
        is_last_in_slot,
        process_stats,
    )
    .unwrap();
``` [7](#0-6) 

The header-shred call a few lines above has the identical pattern [8](#0-7) . A unit test explicitly demonstrates that once the shred-index limit is exceeded, `component_to_shreds` returns `Err(BroadcastError::TooManyShreds)` [9](#0-8)  — precisely the condition that the production `.unwrap()` call does not tolerate.

### Impact Explanation
Unlike the CometBFT report (proposal simply rejected by other validators, i.e., a soft-fail with retry), Agave's failure mode is a hard panic in the leader's own broadcast-stage thread when it happens to construct a legitimate, cost-limit-compliant block whose serialized entries exceed the shred-index capacity. `BroadcastStage::run` treats unexpected errors as logged errors for most `Error` variants [10](#0-9) , but the `.unwrap()` panics do not go through that path at all — they abort the thread directly, independent of that error-handling machinery. A leader panic while producing its own slot at minimum causes that leader to skip its slot (a self-inflicted, non-malicious liveness failure), and because the trigger is a size mismatch between two independently maintained constants (compute-unit budget vs. shred-index capacity), it is a systemic condition that any honest leader can hit whenever it happens to pack cheap-per-byte, high-density transaction data (e.g., transactions maximizing `INSTRUCTION_DATA_BYTES_COST`-weighted data relative to CU cost) up to the compute-unit block limit.

### Likelihood Explanation
This requires no malicious peer, validator, or trusted component — it is purely a function of the leader's own block-packing behavior interacting with existing, unprivileged network transactions. The likelihood scales with how tightly `MAX_BLOCK_UNITS`/`cost_tracker_limits` and `max_data_shreds_per_slot` track each other across changes (e.g., the slot-time-reduction feature table in `runtime/src/slot_params.rs` scales cost limits and shred limits by different ratios per regime), making a future parameter change (or a future SIMD raising `MAX_BLOCK_UNITS_SIMD_0286` to `100_000_000` without a matching shred-capacity increase, as already present in `cost-model/src/block_cost_limits.rs` lines 26-28) a plausible way to reintroduce or widen this gap.

I was not able to fully verify within available search budget whether `max_entry_bytes_per_slot` is actually enforced anywhere in the banking_stage/PoH-recorder transaction-packing path (my searches for its usage only surfaced `runtime/src/slot_params.rs`, `runtime/src/bank.rs`, and `runtime/src/bank/tests.rs`, with no hits in `poh/src/poh_recorder.rs` or `poh/src/transaction_recorder.rs` enforcing it against actual entry bytes). If it is unenforced at packing time, that removes the one guard that could otherwise have kept blocks under the shred-capacity ceiling before reaching the broadcast stage's `.unwrap()`.

### Recommendation
- Replace the `.unwrap()` calls on `component_to_shreds()` in `process_receive_results` with graceful error propagation (e.g., truncate/split the block, or return an `Err` up through `BroadcastRun::run` for `BroadcastStage::handle_error` to log and recover from) rather than panicking the thread.
- Verify and, if missing, enforce `max_entry_bytes_per_slot` (or an equivalent byte-size accounting) directly inside the transaction-packing/cost-tracker path so the compute-unit budget and the shred-index capacity are provably consistent for every slot-time regime, closing the same class of gap the CometBFT report identifies between `max_tx_bytes` and the execution payload/blob size.

### Proof of Concept
Conceptual reproduction, mirroring the existing unit test:
1. Configure/imagine a slot-time regime where `cost_tracker_limits.block_cost` (compute units) permits packing transactions whose total serialized entry size, once shredded, would require more shred indices than `max_data_shreds_per_slot` allows for that regime — analogous to `test_component_to_shreds_max`, which sets `max_data_shreds_per_slot = 10` and shows `component_to_shreds` returns `Err(BroadcastError::TooManyShreds)` once the entry batch is large enough [11](#0-10) .
2. In production, that same condition is reached inside `process_receive_results`, whose call site does not match on `Err` and instead calls `.unwrap()` [7](#0-6) , panicking the broadcast-stage thread for that leader's slot instead of returning a recoverable error.

            }
        }
        None
    }
