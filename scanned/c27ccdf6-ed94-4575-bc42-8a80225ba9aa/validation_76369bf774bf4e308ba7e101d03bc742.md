### Title
`CostModel::calculate_allocated_accounts_data_size` undercounts real account‑data growth, letting attackers bypass the per‑block accounts‑data‑size admission limit - ([File: cost-model/src/cost_model.rs])

### Summary
Just like the MozBridge bug where the LayerZero fee was estimated from a shorter payload than what was actually sent (causing the estimate to diverge from reality), Agave's cost model estimates how much new account data a transaction will allocate using only a partial view of the transaction — the top‑level instructions whose *outer* program id is the System Program — and misses account‑data growth that happens through CPI or in‑place resizing. This produces a systematically low `allocated_accounts_data_size` estimate that is used to gate the per‑block `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` admission check, letting a leader (or the transaction author) get far more real account‑data growth into a block than the model believes it is admitting.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` walks `program_instructions_iter()` — the transaction's top-level instructions — and only recognizes allocation when `program_id == system_program::id()` for a directly-included `SystemInstruction::CreateAccount/CreateAccountWithSeed/Allocate/AllocateWithSeed/CreateAccountAllowPrefund`: [1](#0-0) 

The doc comment on the enclosing function is explicit about the shortcut taken: [2](#0-1) 

This estimated value (`allocated_accounts_data_size`) is exactly the quantity used by the cost tracker to enforce the cluster-wide "how much new account data may a block create" budget: [3](#0-2) 

against the constant: [4](#0-3) 

The actual data growth realized during execution is tracked separately and independently, on-chain, as `accounts_data_size_delta_on_chain`, which is derived from real `accounts_resize_delta` recorded by each executed instruction — not from the cost model's estimate: [5](#0-4) 

Because these two accounting paths are disjoint, any instruction that grows account data through a mechanism other than a **top-level** `system_program::CreateAccount/Allocate*` instruction is invisible to `calculate_allocated_accounts_data_size`:
- A BPF program that CPIs into the System Program to call `create_account`/`allocate` (the transaction's top-level `program_id` is the calling program, not `system_program::id()`, so `calculate_account_data_size_on_instruction` returns `None`).
- A BPF program that resizes an account it owns directly via `set_data_length`/`realloc`, which does not go through the System Program at all. The only real guard on that path is the per-transaction cap enforced deep in the VM/transaction-context layer: [6](#0-5) 

That per-transaction guard limits a single transaction's total resize delta, but it has no knowledge of, and is not summed into, the leader's block-level `allocated_data_size` counter the way top-level `CreateAccount` calls are. So a transaction that grows accounts by up to the per-transaction maximum via CPI/realloc contributes `0` to `TransactionCost.allocated_accounts_data_size`, while contributing its full real size to `accounts_data_size_delta_on_chain` once executed.

### Impact Explanation
This is an unprivileged, remotely reachable resource-accounting bypass in the runtime/cost-model path (not RPC, not requiring a malicious validator). Any user can submit ordinary transactions (invoking any deployed program that CPIs into the System Program for account creation, or that reallocates account data in place — both extremely common patterns, e.g. SPL Token-2022, Anchor `#[account(zero)]`/`realloc` patterns) that are, from the cost model's point of view, "free" with respect to accounts-data growth, while in reality consuming the full allowed per-transaction allocation. By packing many such transactions into a block, the leader's admission control (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000` bytes/block) can be exceeded many times over without the cost tracker ever rejecting a transaction for `WouldExceedAccountDataBlockLimit`. This is a non-RPC, remote data-growth/resource-exhaustion vector: it lets the network's total AccountsDB size grow faster than the protocol's intended per-block ceiling, undermining the SIMD/limit that exists specifically to bound state bloat and the associated snapshot/replay/storage costs across the whole validator set.

### Likelihood Explanation
High likelihood of triggering in practice: CPI-based `create_account`/`allocate` and direct account `realloc` are core, everyday patterns used by a large fraction of deployed Solana programs (token programs, Anchor-generated programs, etc.), so an attacker does not need a novel program — they can simply submit many ordinary transactions that use these idioms, back-to-back, to a leader. No colluding/malicious validator, leaked keys, or special trust assumption is required; this exploits a pure static-analysis gap in `CostModel::calculate_allocated_accounts_data_size`.

### Recommendation
Estimate `allocated_accounts_data_size` conservatively rather than optimistically, mirroring the MozBridge fix's guidance to "error on the side of caution": account for CPI'd System Program allocation instructions (not just top-level ones) by inspecting inner instructions where available, and/or add a bounded worst-case contribution for any instruction whose program could resize/realloc accounts it owns (e.g., any writable account that is not read-only and not the System Program), so the block-level `allocated_data_size` counter cannot be silently bypassed. At minimum, reconcile the on-chain `accounts_data_size_delta_on_chain` growth against the cost tracker's committed `allocated_accounts_data_size` per block and clamp/backpressure future block packing when the real growth outpaces the modeled budget.

### Proof of Concept
1. Deploy (or use any existing) BPF program `P` that, on invocation, either (a) CPIs into `system_program::create_account`/`allocate` to create/grow an account it owns, or (b) directly calls `set_data_length`/`realloc` to grow an account's data up to `MAX_PERMITTED_DATA_LENGTH`/`MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`.
2. Submit a transaction whose only top-level instruction invokes `P` (top-level `program_id` is `P`, not `system_program::id()`).
3. Observe `CostModel::calculate_allocated_accounts_data_size` returns `0` for this transaction because `calculate_account_data_size_on_instruction` only special-cases top-level `system_program::id()` instructions (`cost-model/src/cost_model.rs:242-261`), so `CostTracker::try_add` never increments `allocated_accounts_data_size` and never returns `WouldExceedAccountDataBlockLimit` for it (`cost-model/src/cost_tracker.rs:186-193`).
4. Repeat the transaction (from different accounts to avoid per-account cost limits) enough times to fill a block; after execution, `Bank::update_accounts_data_size_delta_on_chain` (`runtime/src/bank.rs:4419-4430`) will show real per-block accounts-data growth vastly exceeding `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (`cost-model/src/block_cost_limits.rs:35-37`), even though the cost tracker admitted every transaction as consuming zero data-size budget.
