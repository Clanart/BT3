In `Verifier::deposit_sign` (core/src/verifier.rs), `insert_deposit_data_if_not_exists` is called only AFTER `is_deposit_valid` succeeds but the move-to-vault txid computed inside `insert_deposit_data_if_not_exists` via `create_move_to_vault_txhandler` is derived independently from `deposit_data` a second time. If an attacker submits a `DepositParams` where `deposit_data.get_deposit_scripts()` is non-deterministic across calls (e.g. depends on mutable cached `nofn_xonly_pk` state that could differ between the `is_deposit_valid` call and the later `insert_deposit_data_if_not_exists` call within the same request due to cloning boundaries), can the `move_to_vault_txid` persisted diverge from the txid verifiers actually presign sighashes for in `create_nofn_sighash_stream`? Binding: `move_to_vault_txid` stored in the `deposits` table == the txid whose sighash verifiers actually partial-sign in `deposit_sign`'s `create_nofn_sighash_stream`. Impact: Critical, divergence would mean verifiers' N-of-N signature authorizes a different transaction than the one the DB (and later Citrea proof machinery) believes was moved-to-vault. Proof idea: cargo test cloning `deposit_data` at each call boundary and asserting `get_move_txid` is stable and equals the txid used inside `create_nofn_sighash_stream`.
