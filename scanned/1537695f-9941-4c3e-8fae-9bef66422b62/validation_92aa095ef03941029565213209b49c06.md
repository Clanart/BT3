### Title
Missing rate limit on the JSON-RPC HTTP server allows a single client to trigger repeated unbounded `getProgramAccounts` full-ledger scans, causing memory/CPU exhaustion - (File: `rpc/src/rpc_service.rs`, `rpc/src/rpc.rs`)

### Summary
The external report is about a generic missing application-level rate limit exposing authentication/API endpoints to brute force/DoS. The closest real Agave analog is the JSON-RPC HTTP server: unlike the QUIC/TPU streamer path, which has extensive layered rate limiting (`ConnectionRateLimiter`, global `TokenBucket`, per-IP/per-peer connection caps in `SimpleQos`/`SwQos`), the JSON-RPC HTTP server configured in `JsonRpcService::new_with_config` has **no per-IP or per-client rate limiting or concurrency limiting** at all. Combined with the fact that `getProgramAccounts` (and related `get_token_accounts_by_*`) can trigger an unbounded, memory-collecting full-ledger scan when the queried program isn't covered by a secondary index, a single unprivileged low-rate client can repeatedly issue such requests to degrade or crash the validator's RPC service.

### Finding Description
The JSON-RPC HTTP server is built with `ServerBuilder::with_meta_extractor(...)` and configured only with `.threads(1)`, `.cors(...)`, `.request_middleware(...)`, and `.max_request_body_size(max_request_body_size)`: [1](#0-0) 

There is no per-IP connection limiter, no request-rate limiter, and no concurrency cap comparable to what exists for the QUIC/TPU streamer (`ConnectionRateLimiter`, `overall_connection_rate_limiter` `TokenBucket`, and `SimpleQos`/`SwQos` per-peer connection tables): [2](#0-1) [3](#0-2) 

Meanwhile, `get_filtered_program_accounts` in `JsonRpcRequestProcessor` explicitly takes the unbounded, no-byte-limit path whenever the requested program is not covered by a secondary account index — the comment itself acknowledges this path has no scan-size cap: [4](#0-3) 

This scan loads and collects every matching account into memory (`Vec<KeyedAccountSharedData>`/`Vec<(Pubkey, AccountSharedData)>`) via `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`: [5](#0-4) [6](#0-5) 

Only the *secondary-indexed* path (`get_filtered_indexed_accounts`) is size-bounded via `scan_results_limit_bytes` (`--accounts-index-scan-results-limit-mb`); the default/non-indexed path used for arbitrary program IDs (e.g. System Program, an SPL token program, or any popular unindexed program) has no such bound: [7](#0-6) 

Because there is no per-client/per-IP request-rate or concurrency limiter at the HTTP transport layer, a single unprivileged client can open several concurrent connections/requests (bounded only by `rpc_threads`/`rpc_blocking_threads` worker pool sizing, not by a client-aware limiter) each invoking `getProgramAccounts` on a high-cardinality/unindexed program, forcing the validator to repeatedly materialize large in-memory `Vec`s of every matching account concurrently.

### Impact Explanation
Repeated concurrent unbounded scans from even a single low-rate client can exhaust RPC worker/blocking threads and memory, degrading or crashing the RPC service (denial of service) without needing malicious peer/validator collusion or elevated privileges — this matches the "single-client low-rate RPC crash/degradation" impact category. It does not directly cause fund loss or consensus failure, since it is isolated to the RPC surface, but it can render the node's RPC endpoint unusable and consume host resources shared with other validator subsystems (though PoH/banking are on separate threads, blocking threads/memory pressure is a legitimate host-level risk).

### Likelihood Explanation
Likelihood is meaningful but bounded: this requires knowledge of a large or unindexed program to scan, and default operator configuration for `--full-rpc-api` + no ProgramId account index. RPC operators are typically encouraged to run indexes for hot programs, and node operators exposing public RPC frequently front it with external rate-limiting (nginx/cloudflare), which the report's "SOLVED" analog also does. Still, within the Agave codebase itself (not an external reverse-proxy), there is no built-in mitigation, unlike the QUIC/TPU path which was deliberately hardened this way.

### Recommendation
Add an application-level rate limiter (per-IP and/or global token-bucket, similar to `streamer::nonblocking::connection_rate_limiter::ConnectionRateLimiter` / `TokenBucket` used for QUIC) to the JSON-RPC HTTP server request middleware in `rpc/src/rpc_service.rs`, and/or extend the byte-limit-for-scan protection (`scan_results_limit_bytes`) to the non-indexed `get_filtered_program_accounts` path in `rpc/src/rpc.rs` so unbounded scans are capped regardless of whether a secondary index exists.

### Proof of Concept
1. Run an `agave-validator` with `--full-rpc-api` and without `--account-index program-id` for a program with a very large number of accounts on-chain (e.g., a widely used SPL program).
2. From a single client, issue concurrent `getProgramAccounts` JSON-RPC calls (no filters) for that program id at a modest rate (well under any network-level defenses), relying on `rpc_threads`/`rpc_blocking_threads` concurrency.
3. Observe each call taking the non-indexed path in `get_filtered_program_accounts` (`rpc/src/rpc.rs:2283-2308`), which has no `scan_results_limit_bytes` check, materializing the entire matching account set in memory per request.
4. With enough concurrent in-flight requests, RPC blocking-thread pool saturates and/or validator memory grows unbounded, degrading or crashing the RPC service — with no per-IP/per-client throttling in `rpc/src/rpc_service.rs` to stop the client from issuing further requests.

Note: I could not fully verify runtime memory/thread exhaustion behavior experimentally (no execution environment available); this analysis is based on static code inspection of the request-handling and scan paths.

use {
    solana_net_utils::token_bucket::{KeyedRateLimiter, TokenBucket},
    std::net::IpAddr,

/// Limits the rate of connections per IP address.
pub struct ConnectionRateLimiter {
    limiter: KeyedRateLimiter<IpAddr>,
}

/// The threshold of the size of the connection rate limiter map. When
/// the map size is above this, we will trigger a cleanup of older
/// entries used by past requests.
const CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD: usize = 100_000;

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }

    /// Use a set of filters to get an iterator of keyed program accounts from a bank
    #[allow(clippy::result_large_err)]
    async fn get_filtered_program_accounts(
        &self,
        bank: Arc<Bank>,
        program_id: Pubkey,
        mut filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> RpcCustomResult<Vec<(Pubkey, AccountSharedData)>> {
        optimize_filters(&mut filters);
        if self
            .config
            .account_indexes
            .contains(&AccountIndex::ProgramId)
        {
            if !self.config.account_indexes.include_key(&program_id) {
                return Err(RpcCustomError::KeyExcludedFromSecondaryIndex {
                    index_key: program_id.to_string(),
                });
            }
            self.get_filtered_indexed_accounts(
                &bank,
                &IndexKey::ProgramId(program_id),
                &program_id,
                filters,
                sort_results,
            )
            .await
            .map_err(|e| RpcCustomError::ScanError {
                message: e.to_string(),
            })
        } else {
            // this path does not need to provide a mb limit because we only want to support secondary indexes
            let mut accounts = self
                .runtime
                .spawn_blocking(move || {
                    bank.get_filtered_program_accounts(
                        &program_id,
                        |account: &AccountSharedData| {
                            filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                        },
                    )
                    .map_err(|e| RpcCustomError::ScanError {
                        message: e.to_string(),
                    })
                })
                .await
                .expect("Failed to spawn blocking task")?;
            if sort_results {
                // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
                accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
            }
            Ok(accounts)
        }
    }

    pub fn load_by_program_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        program_id: &Pubkey,
        filter: F,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let mut collector = Vec::new();
        self.accounts_db
            .scan_accounts(

    }
