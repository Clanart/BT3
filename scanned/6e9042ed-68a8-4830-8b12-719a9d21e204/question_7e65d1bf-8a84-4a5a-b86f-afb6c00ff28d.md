Target: `fn create_payout_txhandler` in `core/src/builder/transaction/operator_reimburse.rs`, called from `Operator::withdraw` (`core/src/operator.rs`) and `Aggregator::withdraw`/`Aggregator::optimistic_payout` (`core/src/rpc/aggregator.rs`), signing with `TapSighashType::SinglePlusAnyoneCanPay` via `TxHandler::calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs`). Attacker action: an unprivileged party observes a `WithdrawParams` (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) submitted by the withdrawer to Citrea's Bridge contract `withdraw` call (public event/state), then independently constructs and broadcasts a payout transaction spending the same `input_outpoint` with the exact same output[0] (script_pubkey, amount) but a different or absent OP_RETURN output (built via `op_return_txout`), funding only the fee themselves. Preconditions: a valid withdrawal is registered on Citrea with an index not yet fronted; no operator has yet broadcast the real payout tx. Call sequence: attacker crafts tx -> broadcasts to Bitcoin -> `bitcoin_syncer` detects it -> `Verifier::update_finalized_payouts` reads `get_first_op_return_output`/`parse_op_return_data` and calls `Database::update_payout_txs_and_payer_operator_xonly_pk`, writing `payout_payer_operator_xonly_pk` (possibly NULL or an arbitrary registered operator's xonly_pk chosen by the attacker) for that withdrawal idx. Binding that breaks: the operator whose xonly_pk is committed in `withdrawals.payout_payer_operator_xonly_pk` == the party whose own BTC actually funded output[0] of the payout transaction. Because `TapSighashType::SinglePlusAnyoneCanPay` at input index 0 only commits to output[0] (per `bitcoin::sighash::Prevouts::One` in `calculate_pubkey_spend_sighash`), the OP_RETURN at output index 2 is never covered by the withdrawer's signature, so anyone can rewrite it. Scoped impact: Critical - either an operator is reimbursed for a payout it never funded (attacker fronted the fee, named operator gets `bridge_amount` from `create_reimburse_txhandler` for free) or, if a real operator's simultaneous broadcast loses the UTXO race, that honest operator that funded the payout is permanently unable to be reimbursed since the withdrawal UTXO is already consumed with wrong/no attribution. Proof idea: `cargo test` under `core/src/test/deposit_and_withdraw_e2e.rs`-style test asserting `payout_payer_operator_xonly_pk` retrieved via `Database::get_payout_info_from_move_txid` equals the xonly_pk of the operator whose wallet balance actually decreased by the payout amount, and show they diverge once the attacker's rebuilt OP_RETURN is mined first.
