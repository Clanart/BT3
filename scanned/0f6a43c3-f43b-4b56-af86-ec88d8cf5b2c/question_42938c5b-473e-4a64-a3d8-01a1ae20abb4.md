Can an attacker who registers a withdrawal against operator A, but whose Reimburse flow is later invoked with a ContractContext carrying operator B's KickoffData (same round_idx, mismatched deposit_data), get get_challenge_ack_hashes to return operator A's hashes while kickoff_txhandler is signed under operator B's bitvm keys, breaking CALLER AUTHORITY (party reaching signing method == party protocol intends)? Preconditions: two operators registered, shared deposit_outpoint reused across ContractContext calls (test harness reuse bug). Call sequence: create_txhandlers -> db_cache.get_challenge_ack_hashes (keyed on operator_xonly_pk+deposit_outpoint) -> create_kickoff_txhandler. Binding: challenge_ack_public_hashes.len() == deposit_data.get_num_watchtowers() AND the operator_xonly_pk used to fetch them == kickoff's operator_xonly_pk. Impact: Critical, ChallengeNACK could burn an honest operator's collateral using another operator's ack hash set. Proof idea: cargo test under core/src/test seeding mismatched operator/deposit pairs and asserting create_txhandlers rejects them or that fetched hashes always match kickoff operator.
