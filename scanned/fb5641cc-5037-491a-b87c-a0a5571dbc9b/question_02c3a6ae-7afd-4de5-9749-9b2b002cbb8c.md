[Function: check-confidence] Does `(<= confidence (/ (* (to-uint price) (var-get max-confidence-ratio)) BPS))` compute the confidence BOUND from the RAW, unnormalized Pyth `price` int (still in the feed's native exponent, e.g. expo=-8 meaning price could be ~10^10 for a $100 asset) rather than from the NORMALIZED 8-decimal `final-price` computed by `normalize-pyth`, so for an asset whose native Pyth exponent differs drastically from -8 (e.g. expo=-2, native price=100 for $1.00, adj=6, final-price=100*10^6=100000000), the confidence bound `(* 100 max-confidence-ratio)/BPS` is computed against the SMALL raw price=100 instead of the scaled 100000000, letting an attacker-influenced or genuinely noisy feed with a confidence value up to ~100x looser than intended (relative to the true normalized price) still pass the gate, admitting a materially wider price band than `max-confidence-ratio` was designed to bound, in the direction that lets a stale-in-spirit / low-quality price through and be used as this asset's collateral value (inflated) at liquidation time? Preconditions: register an asset with native Pyth expo=-2 (adj=6), max-confidence-ratio set by DAO for the normalized scale. Call sequence: liquidate using this asset as collateral with confidence crafted just under the raw-scale bound but far above the normalized-scale-equivalent bound. Invariant: FEED_INTEGRITY (confidence gate must bound the value in the form/scale it protects, i.e. after normalization). Impact: Critical, inflated collateral valuation lets an undercollateralized position pass is-healthy and avoid liquidation, or lets a liquidator under-seize a healthy-looking position, at protocol's expense (insolvency). Proof idea: Clarinet test registers two mock assets with identical true USD price/confidence ratio but different native expo, shows one passes check-confidence and the other (mathematically equivalent) does not.
