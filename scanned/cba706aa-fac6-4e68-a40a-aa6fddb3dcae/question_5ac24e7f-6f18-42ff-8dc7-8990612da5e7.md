[Target: TxSenderClient::insert_try_to_send, disprove/challenge queueing] insert_try_to_send has no notion of 'payout_input_index' or 'storage_proof.index' — it queues whatever Challenge/Disprove/ChallengeNACK transaction it is handed. An attacker who controls the bytes of a withdrawal UTXO can cause payout_input_index (computed elsewhere via get_payout_input_index matching wd_txid against payout_tx inputs) to resolve ambiguously if two inputs of the payout tx share a spoofed previous_output.txid crafted by the attacker's own funding transactions, and insert_try_to_send will happily queue whichever Disprove/Challenge tx an operator subsequently builds from the wrong index. Precondition: attacker funds a withdrawal UTXO whose txid collides in low-order bytes with another input the operator constructs (feasible since txid choice is fully attacker-controlled pre-image). Call sequence: get_payout_input_index -> BridgeCircuitHostParams::new_with_wt_tx -> operator builds Disprove tx -> insert_try_to_send queues it unconditionally. Binding broken: PROOF_SOUNDNESS - payout_input_index used to select input.previous_output.txid == the index of the actual withdrawal input the storage proof commits to. Impact: Critical, a Disprove could target the wrong witness/committed data, letting an honest operator be disproved for a claim it did not make, burning its collateral. Proof idea: cargo test under circuits-lib constructing a payout_tx with two inputs whose previous_output.txid both equal a crafted wd_txid and asserting get_payout_input_index returns an index the caller cannot distinguish from the legitimate one, then showing insert_try_to_send queues the resulting Disprove tx without re-validation.
