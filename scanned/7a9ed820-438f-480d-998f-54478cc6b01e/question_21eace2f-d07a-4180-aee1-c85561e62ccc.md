Can a race between two operators (or an attacker replaying a leaked S+AP signature as an unprivileged relay of a legitimately-obtained signature) that both broadcast a `Payout`-type transaction spending the same withdrawal UTXO with different OP_RETURN `operator_xonly_pk` values result in `mark_payout_handled` (core/src/database/verifier.rs lines 348-361) recording a `kickoff_txid` tied to the operator whose kickoff happens to be sent first, while `get_payout_info_from_move_txid`'s `payout_payer_operator_xonly_pk` reflects whichever payout tx got mined, with no code path reconciling the two once they diverge? Preconditions: withdrawal UTXO with valid S+AP sig known to both parties (obtained via observing the withdraw RPC parameters, which per WithdrawParams protobuf comments are handed to operators off-chain but sighash types make replay by anyone with the bytes trivial). Call sequence: two payout txs race on mempool -> block confirms one -> `update_finalized_payouts` records attribution A -> a kickoff for operator B (who lost the race but still attempts kickoff) reaches `mark_payout_handled` for the same `idx`. Binding: `kickoff_txid`'s operator == `payout_payer_operator_xonly_pk`'s operator for the same `idx`. Impact: Critical - an operator reimbursed for a payout it never funded / an honest operator permanently unable to be reimbursed. Proof idea: cargo test under core/src/test simulating both a payout broadcast and a kickoff for a different operator, asserting `mark_payout_handled` and `get_payout_info_from_move_txid` diverge with no reconciling check before Reimburse tx creation.
