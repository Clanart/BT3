### Title
Missing consumed-slot marking on `UnknownSlotLeader` error path allows repeated re-verification of duplicate-shred proofs - (File: gossip/src/duplicate_shred_handler.rs)

### Summary
`handle_shred_data` drains the assembled chunk buffer with `std::mem::take(entry)` before resolving the slot leader, but only calls `self.consumed.insert(slot, true)` after successfully processing the proof. If `leader_schedule_cache.slot_leader_at(slot, None)` returns `None`, the function returns `Err(Error::UnknownSlotLeader(slot))` via `?` and skips the `consumed` update. [2](#0-1) 

### Finding Description
`should_consume_slot` gates whether new chunks for a slot are accepted into the reassembly buffer, based on the `consumed` map, falling back to `blockstore.has_duplicate_shreds_in_slot(slot)` only when the slot key is absent from the map: [3](#0-2) 

Since the failed proof was never stored to `blockstore` (the `UnknownSlotLeader` error occurs before `store_duplicate_slot`), `has_duplicate_shreds_in_slot(slot)` remains `false`, and the `consumed` entry for that slot never transitions to `true`. Consequently `should_consume_slot` continues to return `true` for that slot indefinitely, so a new 3-chunk proof for the same slot will always be re-buffered and, once all chunks are received again, re-run through `duplicate_shred::into_shreds` / `check_shreds`, repeating wincode deserialization and Ed25519 signature verification each time. [4](#0-3) 

### Impact Explanation
This allows an unprivileged gossip peer to trigger unbounded, repeated CPU-costly proof verification for any slot whose leader cannot be resolved via `slot_leader_at(slot, None)`. This matches the "non-RPC remote exhaustion" impact category in scope, since it forces repeated cryptographic verification work without ever converging to a terminal "consumed" state for that slot.

### Likelihood Explanation
Exploitability is conditioned on being able to reliably produce a slot for which `LeaderScheduleCache::slot_leader_at(slot, None)` returns `None` while still satisfying `should_consume_slot`'s bounds (`last_root < slot < last_root + cached_slots_in_epoch`) so the proof isn't rejected earlier. I could not fully verify from the code inspected how often/whether this condition is reachable in steady state (e.g., whether the leader schedule cache is guaranteed to be populated for all slots in that window, or whether there's a race/edge condition — such as near epoch boundaries — where it legitimately returns `None`). This affects the practical likelihood of the exploit but does not change the fact that the code path itself lacks the intended state update.

### Recommendation
Ensure `consumed.insert(slot, true)` (or an equivalent "do not reprocess" marker) is set for the slot even when `UnknownSlotLeader` (and other terminal, non-retryable errors) occurs after the chunks have been drained from the buffer, e.g. by restructuring `handle_shred_data` to mark the slot before or regardless of the `slot_leader_at` lookup failing, or by tracking "attempted and permanently failed" slots separately so they aren't perpetually re-buffered.

### Proof of Concept
1. Target a slot within the accepted window (`last_root < slot < last_root + cached_slots_in_epoch`) for which `leader_schedule_cache.slot_leader_at(slot, None)` returns `None`.
2. Send 3 valid-format chunks (via `duplicate_shred::from_shred`) constituting a full duplicate-shred proof for that slot.
3. Observe: `handle_shred_data` reassembles the chunks, calls `slot_leader_at`, gets `None`, returns `Err(UnknownSlotLeader)`; `self.consumed.insert(slot, true)` at line 155 is never reached.
4. Confirm via `should_consume_slot`/`consumed` map that the slot remains eligible (`false` in map, or absent-then-inserted-false), and blockstore never stores a duplicate proof for the slot (`has_duplicate_shreds_in_slot` stays `false`).
5. Resend the same 3-chunk set; repeat step 3 indefinitely, each time incurring `into_shreds`/`check_shreds` deserialization and signature-verification cost.

Note: I was unable to conclusively determine (within the code reviewed) how commonly/reliably `slot_leader_at(slot, None)` returns `None` for slots inside the `should_consume_slot` window during normal operation — this determines actual field exploitability and should be verified further (e.g., by examining `LeaderScheduleCache::slot_leader_at` in `ledger/src/leader_schedule_cache.rs`, which I could not fully inspect before running out of tool calls).

fn should_consume_slot(
    slot: Slot,
    blockstore: &Blockstore,
    consumed: &mut HashMap<Slot, bool>,
) -> bool {
    !*consumed
        .entry(slot)
        .or_insert_with(|| blockstore.has_duplicate_shreds_in_slot(slot))
}
