Target: kzg.Verify via Context.VerifyKZGProof for a blob whose committed polynomial is constant (all 4096 Lagrange evaluations equal to a single scalar c). Attacker input: blobCommitment = commitment to constant polynomial, kzgProof = PointAtInfinity (since quotient (f(X)-c)/(X-z) is exactly zero for constant f), inputPointBytes = arbitrary z, claimedValueBytes = c. Preconditions: for constant polynomials every z gives quotient 0, so proof=O is a legitimately valid proof for ALL z; attacker submits an out-of-domain or bit-reversed z alongside the correct c. Call sequence: DeserializeKZGCommitment/Proof -> Verify -> PairingCheck with quotient=O reduces to checking [f(α)-c]G1 == O i.e. f(α)==c (true since commitment IS constant c). Equality: Verify accepts ⇔ f(z)==c for the SPECIFIC z supplied; because f is constant this holds for all z, so acceptance is actually correct here -- but this proof idea is used to probe whether the SAME (commitment, proof=O) is reusable across unrelated z values that the caller did not originally request, i.e. pooled-state or replay risk if opening-proof for one z is presented as opening for a different z1 the verifier is checking against different claimed context. Impact: Critical only if a caller relies on proof binding to a single z (e.g. batch verification assuming per-index z uniqueness); flag as High: spec (which also accepts proof=O universally for constant polys) and this library agree, so this is SPEC_CONFORMANCE not a bug, but must be tested for regression.
