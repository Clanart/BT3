Based on my research, the closest structural analog to the external report—value being computed for a state that has already changed/disappeared by the time it is paid out, with no clawback or retry, silently destroying the user's entitlement—exists in Agave's partitioned epoch rewards distribution path.

### Title
Partitioned stake rewards are permanently burned instead of paid when the target stake account cannot be found at distribution time - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
Agave computes stake rewards for an epoch during a "calculation" block and then pays them out lazily, one partition at a time, over many subsequent blocks (`distribute_partitioned_epoch_rewards`) [1](#0-0) . When a partition's turn comes, `build_updated_stake_reward` re-fetches the stake account from the *current* `StakesCache` by pubkey and adds the previously-computed reward to it [2](#0-1) . If that lookup fails, `store_stake_accounts_in_partition` does not retry, refund, or fail the block — it just logs an error and adds the reward amount to `stake_reward_lamports_burned`, which is subtracted from capitalization/sysvar bookkeeping [3](#0-2) . This mirrors the DeFi bug pattern exactly: a reward that was "earned" against an old balance/state snapshot is discarded because the underlying account changed/vanished before the reward was actually delivered.

### Finding Description
The reward pipeline is split into two phases separated by many blocks:
1. **Calculation** (`calculate_stake_rewards_and_commissions` / `redeem_delegation_rewards`) walks the stake accounts as they existed in the `StakesCache` snapshot at the epoch boundary and computes `PartitionedStakeReward` entries [4](#0-3) .
2. **Distribution** happens later, one partition of accounts per block, and only then are the actual lamports added to the stake account by re-reading it from `stakes_cache.stake_delegations()` [5](#0-4) .

Between phase 1 and phase 2, a stake account referenced in an already-computed `PartitionedStakeReward` can no longer exist in `stakes_cache_accounts` (the cache only tracks accounts that still have `StakeStateV2::delegation().is_some()`). When `build_updated_stake_reward` cannot find the entry, it returns `DistributionError::AccountNotFound`, and the caller's only response is to burn the reward and move on [6](#0-5) [7](#0-6) .

Critically, the code's own comment states the developers' invariant assumption: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned"* [8](#0-7) . This is exactly the same class of bug as the external report: the code assumes a balance/account snapshot taken at "calculation time" remains valid until "distribution time," but the actual guard preventing account mutation/closure in that window is external to this file and was not found anywhere in this repository (`RewardInterval`/`get_reward_interval()` is only used internally by `Bank` to schedule when to run calculation/distribution — it is never referenced by any stake-instruction processor in this codebase) [9](#0-8) .

### Impact Explanation
If the assumed stake-program restriction does not actually cover every path that can remove a stake account's delegation between calculation and distribution (e.g., withdrawal of a fully-deactivated stake account, which is a completely permissionless, unprivileged action available to any staker via the standard `Withdraw` instruction), the staker's already-computed reward for that epoch is silently destroyed rather than paid. This is a direct fund-loss bug for an unprivileged actor's own stake rewards, and it is inconsistent with the design intent that "there should never be rewards burned."

### Likelihood Explanation
I could not locate the stake-program instruction processor in this repository that is supposed to enforce "no state mutation of stake accounts during active epoch rewards" (it may live in an external `solana-stake-program`/`solana-stake-interface` crate not indexed here). This means I cannot fully confirm from local code whether every withdrawal/closure path is actually blocked during the calculation→distribution window, which is the crux of whether this is exploitable. The distribution-side code itself, however, unconditionally treats "account not found" as an expected, non-fatal, silent-burn case — meaning if the guard has any gap (feature-gate transition, instruction that doesn't check the interval, or a race at epoch boundary), reward loss is not merely theoretical but the codified fallback behavior.

### Recommendation
Given the significant uncertainty about whether the missing guard is enforced elsewhere, this should be treated as a candidate needing verification rather than a confirmed vulnerability: locate and audit the stake-program instruction handlers (`Withdraw`, `Deactivate`, `Split`, `Merge`, `SetLockup`) to confirm each one actually checks `EpochRewardStatus`/`RewardInterval` before allowing any state change that removes or resizes the account, for every stake-program version. If any instruction lacks that check, the fix is either (a) make `store_stake_accounts_in_partition` recover/redirect burned rewards to a claimable location instead of silently discounting capitalization, or (b) close the gap in the stake-program guard so accounts referenced by a pending `PartitionedStakeReward` truly cannot be removed before distribution.

### Proof of Concept
A concrete PoC cannot be constructed from the code available here because the actual instruction-level guard (or its absence) lives outside this repository's indexed contents. The observable, confirmed behavior in-repo is:
1. Bank enters `EpochRewardPhase::Calculation`, computing a `PartitionedStakeReward` for stake account `S` based on the `StakesCache` snapshot [10](#0-9) .
2. Several blocks later, `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` looks up `S` in the *current* `stakes_cache_accounts` [11](#0-10) .
3. If `S` is not present (e.g., its delegation was removed in the interim), `build_updated_stake_reward` returns `Err(DistributionError::AccountNotFound)` and the reward is added to `stake_reward_lamports_burned` rather than paid [3](#0-2) .

If a background agent with terminal/test access is desired, this could be further verified by writing a bank test that: (1) sets up a stake reward via `set_epoch_reward_status_calculation`/`begin_partitioned_rewards`, (2) removes the corresponding stake account's delegation from `stakes_cache` before calling `distribute_partitioned_epoch_rewards`, and (3) asserts whether `stake_reward_lamports_burned` becomes nonzero — confirming the silent-burn fallback fires exactly as the code comment describes it should never happen.
