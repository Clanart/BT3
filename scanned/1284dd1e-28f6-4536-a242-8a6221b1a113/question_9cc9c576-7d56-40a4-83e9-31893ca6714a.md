In `Operator::withdraw` (core/src/operator.rs, `is_profitable` check around lines 598-612), profitability is computed only from `input_utxo.txout.value`, `output_txout.value`, `bridge_amount`, and `operator_withdrawal_fee_sats`, none of which are cross-checked against the actual amount Citrea's Bridge contract currently records for `withdrawal_index` beyond the earlier outpoint-equality check. Preconditions: attacker registers a withdrawal for outpoint O with output_amount X on Citrea, then via the public `withdraw`/`internal_withdraw` gRPC supplies `out_amount` different from X (Citrea's recorded amount is not fetched here directly - it's implied only via the operator trusting caller-supplied `out_amount`/`out_script_pubkey` and the `input_signature` verifying against a payout tx built from those exact caller-chosen values). Call sequence: `parse_withdrawal_sig_params` -> `Operator::withdraw(withdrawal_index, in_signature, in_outpoint, out_script_pubkey=attacker-chosen, out_amount=attacker-chosen)` -> `create_payout_txhandler` builds a payout tx from the attacker-chosen output values -> sighash/signature verifies (since attacker signed exactly these attacker-chosen values with SinglePlusAnyoneCanPay) -> operator funds and broadcasts it. Binding: out_amount and out_script_pubkey used to build and fund the payout == the amount and script_pubkey the Bridge contract recorded for withdrawal_index at registration. Impact: Critical - since nothing in `Operator::withdraw` re-fetches Citrea's registered withdrawal amount/address for withdrawal_index and compares it to caller-supplied out_amount/out_script_pubkey (only the input outpoint is checked), an attacker could get an operator to front a payout amount larger or smaller, or to a different address, than what was actually registered on Citrea, while later Reimburse still reimburses the operator the full `bridge_amount` from the vault - a custody mismatch between value fronted and value the Bridge contract will treat as satisfying the withdrawal. Proof idea: cargo test with mocked CitreaClientT registering withdrawal_index with amount X/address Y, then calling operator.withdraw with out_amount != X or out_script_pubkey != Y (but validly self-signed), asserting the operator rejects it because it doesn't match Citrea's own recorded values for that withdrawal_index, not merely because the signature failed to verify.
