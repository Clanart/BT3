In `BridgeCircuitInput`/`bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs, structs.rs), `deposit_constant` is computed from `operator_xonlypk` parsed from `get_first_op_return_output(&input.payout_spv.transaction)` (mod.rs lines 206-229), the same OP_RETURN an unprivileged withdrawer can forge into a self-funded transaction (per the attribution-forgery scenario). Preconditions: attacker broadcasts a self-funded payout-shaped transaction spending the registered withdrawal UTXO with OP_RETURN naming a real operator's xonly pk who never funded or signed it. Call sequence: an operator (or anyone able to submit a bridge-circuit host params for proving, gated in practice by needing operator collateral to gain from it, but the circuit itself performs no independent check) constructs `BridgeCircuitHostParams` from this attacker-forged SPV transaction; `bridge_circuit` computes `deposit_constant` and ultimately `journal_hash` treating `operator_xonlypk` as authoritative with zero verification that this key's holder actually signed any input of `payout_spv.transaction`. Binding: operator_xonlypk embedded in journal_hash/deposit_constant == the xonly pk of the party that actually signed a funding input of payout_spv.transaction. Impact: Critical - the bridge circuit's journal_hash, which downstream decides whether an operator's collateral is burned or reimbursement is honored, commits to an operator identity that is never independently verified against transaction signatures, only against unauthenticated OP_RETURN bytes. Proof idea: circuits-lib cargo test feeding `bridge_circuit` a payout_spv.transaction whose OP_RETURN names operator X but all inputs are signed by a different key Y, and asserting the circuit rejects (rather than accepts and commits deposit_constant naming X) when no signature from X exists over any input.
