## Title
Block-revenue-share reward distribution mints `block_reward` lamports into stake accounts without ever deducting the source amount from the vote account's `pending_delegator_rewards` / balance - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
Under SIMD-0123 block-revenue-sharing, a leader deposits real lamports into its vote account via `deposit_delegator_rewards`, which both transfers the lamports and increments `VoteStateV4::pending_delegator_rewards` [1](#0-0) . Each epoch, `calculate_block_reward` computes a per-stake-account share of that same `pending_delegator_rewards` pool [2](#0-1) , and `build_updated_stake_reward` credits that share directly into each staker's account via `checked_add_lamports` [3](#0-2) . Nowhere in the reward-commission or distribution path is the vote account's lamport balance debited or `pending_delegator_rewards` decremented by the amount actually paid out to stakers. This is structurally identical to the `AuraVault::claim` bug: a fee/share is computed from a shared pool and paid to a recipient without subtracting it from the pool's tracked balance.

## Finding Description
The block-reward flow is:
1. `deposit_delegator_rewards` CPIs a `system_instruction::transfer` from the leader to the vote account and calls `add_pending_delegator_rewards(deposit)`, which only ever adds to the counter, never subtracts [4](#0-3) .
2. During reward calculation, `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` and computes each stake account's proportional share, clamped to `pending_delegator_rewards` per call [5](#0-4) , but this clamp is per-individual-delegation, not a running total consumed from the pool - every stake account independently is entitled to compute its share off the *full, unmodified* `pending_delegator_rewards` value.
3. During distribution, `build_updated_stake_reward` mints the `block_reward` straight into the stake account's lamports with `account.checked_add_lamports(partitioned_stake_reward.block_reward)` [3](#0-2) .
4. `distribute_epoch_rewards_in_partition` only adjusts `capitalization` for `stake_reward_lamports_minted` (inflation) and `block_reward_lamports_burned` (failure case); the successfully-distributed `block_reward_lamports_distributed` is never subtracted from anywhere, including the source vote account's own lamport balance [6](#0-5) .

No code path was found (via targeted search across `vote_state`, `handler.rs`, and the partitioned-epoch-rewards module) that resets or decrements `pending_delegator_rewards` on the vote account, nor one that calls `checked_sub_lamports` on the vote account to fund the `block_reward` paid to stakers. The only consumer of `pending_delegator_rewards` besides the reward calculation is `withdraw`, which merely *reserves* that amount as a minimum balance floor [7](#0-6)  - it does not get spent down by the epoch-reward mechanism either.

The corrupted invariant is: `sum(all account lamports) == Bank::capitalization`. Because `block_reward` lamports are freshly created inside stake accounts (`checked_add_lamports`) with no offsetting debit anywhere, and `capitalization` is not incremented to match, the actual total lamports in the ledger silently exceeds the tracked `capitalization` value by the cumulative sum of all `block_reward` ever distributed, and — because `pending_delegator_rewards` is also never decremented — the same pool balance keeps re-qualifying for a new distribution share every subsequent epoch, so this divergence compounds continuously as long as the validator has stake and block-revenue-sharing is active.

## Impact Explanation
This breaks the core "no undocumented mint" invariant that all of Agave's capitalization tracking and bank-hash calculation rely on. Since capitalization bookkeeping in this path does not account for `block_reward_lamports_distributed`, every epoch that distributes a nonzero block reward silently inflates real, spendable lamports in stake accounts without any matching increase in `Bank::capitalization`. This is fund creation from nothing (theft of value relative to the rest of the network / dilution of all other holders), and because `pending_delegator_rewards` is never drawn down, the effect repeats and compounds epoch over epoch for every validator using block-revenue sharing — closely matching the "extra rewards successfully sent to the caller" branch of the referenced report. If any capitalization-consistency check exists elsewhere in the bank (e.g., during snapshot verification or bank-hash computation) that asserts `sum(lamports) == capitalization`, this divergence would trip it, causing consensus-relevant panics/halts across the fleet once triggered widely — matching the "false acceptance / consensus halt" impact category.

## Likelihood Explanation
This path executes automatically, without any privileged or malicious actor, every epoch in which block-revenue sharing is active (`block_revenue_sharing` feature) and a validator has deposited delegator rewards through the ordinary leader-fee flow. No attacker action, special permissions, or race condition is required — it is a systemic accounting gap in the default reward-distribution code path that fires each epoch boundary.

## Recommendation
When crediting `block_reward` to stake accounts in `build_updated_stake_reward` / `store_stake_accounts_in_partition`, symmetrically debit the same amount from the originating vote account's lamport balance and decrement `pending_delegator_rewards` by the total distributed for that vote account, analogous to how `distribute_reward_commissions` correctly pairs `checked_add_lamports` on commission accounts with corresponding capitalization bookkeeping. Ensure `distribute_epoch_rewards_in_partition` includes `block_reward_lamports_distributed` in its capitalization accounting (or explicitly nets it against a debit from the vote account) so that `sum(lamports) == capitalization` remains an enforced invariant across the whole distribution.

## Proof of Concept
Because I only have static/index-level access to this repository (no execution environment), I could not run this end-to-end; the following outlines the reproducible sequence:
1. Deposit block revenue: call `VoteInstruction::deposit_delegator_rewards` for a vote account, transferring `D` lamports and setting `pending_delegator_rewards = D` [1](#0-0) .
2. Let an epoch elapse with `block_revenue_sharing` active. `calculate_block_reward` computes each delegator's share of `D` based on `stake / total_active_stake` [8](#0-7) .
3. `build_updated_stake_reward` adds each computed share to the corresponding stake account's lamports [3](#0-2) , while the vote account's own lamport balance and `pending_delegator_rewards` field remain unchanged.
4. Repeat step 2 in the following epoch: the vote account still reports `pending_delegator_rewards == D` (never decremented), so stakers are paid a *second* full share of `D`, while the original `D` lamports also still sit untouched in the vote account. Sum of lamports across the network has now grown by `~2D` for one deposit of `D`, with no corresponding `capitalization` increase recorded for the block-reward portion.

I could not confirm within the indexed portion of the repo whether a decrement step exists elsewhere (e.g., in code excluded from indexing); if such logic exists outside what was searched, it should be verified directly in a full checkout via a Devin session, since size limits on the index may have excluded some files.

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```
