## Found: `warp_from_parent()` path can panic in `maybe_burn_vat_from_staked_accounts` due to a stale, unfiltered stakes snapshot

### Title
Multi-epoch `Bank::warp_from_parent` can panic in the VAT-burn path because `get_top_epoch_stakes()` is filtered against the *current* bank instead of the *skipped* epoch's stakes - ([File: runtime/src/bank.rs])

### Summary
This report's underlying bug class is a "precondition/postcondition mismatch": a value is checked for a condition (sufficient balance) at one point, but the operation that depends on that condition being true runs against a *different* snapshot of the same value, so the guard doesn't actually protect the operation. The closest structural analog in Agave is the Validator Admission Ticket (VAT) burn mechanism in `runtime/src/bank.rs`, where the filtering step (`clone_and_filter_for_vat`, which enforces `lamports >= minimum_vote_account_balance_for_vat()`) and the burn step (`maybe_burn_vat_from_staked_accounts`, which unconditionally subtracts `vat_to_burn_per_epoch` from each filtered vote account) are supposed to operate on the same guaranteed-sufficient balance, but can diverge along the `warp_from_parent` code path.

### Finding Description
`update_epoch_stakes` takes an `Option<VoteAccounts>` for `prefiltered_distribution_vote_accounts`: [1](#0-0) 

- On the normal epoch-boundary path (`process_new_epoch`), the `Some(filtered_distribution_vote_accounts)` branch is used: the filtering (`clone_and_filter_for_vat`) and the burn both operate on the same, single-epoch-advance snapshot computed a few lines earlier in `compute_new_epoch_caches_and_rewards`: [2](#0-1) [3](#0-2) 

- On the `warp_from_parent` path, which is used to jump the bank forward by many epochs at once (used at validator startup for `--warp-slot`, in `ledger-tool`, and in `program-test`), `update_epoch_stakes` is called with `None`: [4](#0-3) 

  This forces the `None` branch, which falls back to `self.get_top_epoch_stakes()`: [5](#0-4) 

  `get_top_epoch_stakes()` filters using `self.stakes_cache.stakes()` and `self.minimum_vote_account_balance_for_vat()` **as of the new, post-warp bank** — not the intermediate epoch(s) that were skipped over by the warp. Because `Bank::new_from_parent` is called first (which itself can trigger `process_new_epoch` only for the immediately-following epoch, not for every epoch skipped by a multi-epoch warp) and `warp_from_parent` explicitly re-derives `leader_schedule_epoch` from the warped `slot`, the vote-account balances used to satisfy the "is this account above the VAT minimum" filter check can be taken from a bank state whose account balances (and `vat_to_burn_per_epoch`, which depends on `current_slot_params()`/feature activation state at that slot) do not match what `maybe_burn_vat_from_staked_accounts` assumes.

- `maybe_burn_vat_from_staked_accounts` then re-fetches the *live* account for each vote pubkey from `self.get_account(vote_pubkey)` and unconditionally subtracts `vat_to_burn_per_epoch`, relying entirely on the invariant documented in its own comment — "Vote accounts have already been filtered ... to contain enough balance" — with no defensive check, just an `.expect()`: [6](#0-5) 

If the filtering snapshot and the live-account state diverge (e.g., because of a multi-epoch `warp_from_parent` jump, or because `vat_to_burn_per_epoch`/`minimum_vote_account_balance_for_vat` is evaluated against different feature/slot-params state than the filtering step used), `account.lamports().checked_sub(vat_to_burn_per_epoch)` can underflow and the `.expect(...)` will panic. This is exactly the report's bug class: a "whitelisting"/admission check performed against one state, while the dependent action executes against a state that doesn't actually satisfy the precondition, and the code has no fallback other than reverting/panicking.

### Impact Explanation
A panic inside `Bank::update_epoch_stakes`/`maybe_burn_vat_from_staked_accounts` during bank construction is not merely a `Result`-returning failure — it is a Rust panic in validator bank-processing code. Since `warp_from_parent` is invoked deterministically from data that all validators would compute identically (ledger replay, snapshot loading via `ledger-tool`, or startup `--warp-slot`), if the divergent-snapshot condition can be triggered on mainnet-like data (e.g., an epoch boundary crossed via a large slot jump, combined with Alpenglow VAT burn active), every validator that processes that same warp would panic identically, which is a network-wide crash/consensus-halt-class event rather than a single-node crash. Even in the narrower case where this occurs only for a subset of nodes (e.g., ledger-tool operators warping to arbitrary slots for debugging, or the `--warp-slot` startup flag), it is at minimum a validator crash triggered without any malicious peer involvement — purely from normal state evolution.

### Likelihood Explanation
This requires the Alpenglow feature (and its VAT burn) to be active and a multi-epoch skip via `warp_from_parent` (or any caller hitting the `None` branch of `update_epoch_stakes` at an epoch boundary) where the vote-account balance snapshot used for filtering doesn't match the balance state consumed during the burn. This is a narrower trigger than a routine one-epoch transition, but `warp_from_parent` is exercised in production-adjacent code paths (`--warp-slot`, `ledger-tool`, `program-test`), and the code's own comments explicitly acknowledge that "other callers (same-epoch refresh, warps) fall back to `get_top_epoch_stakes`" as a deliberately different, less-precise path than the main epoch-boundary path — indicating the authors were aware this fallback isn't equivalent, but did not add a guard against the resulting invariant violation in `maybe_burn_vat_from_staked_accounts`. I was not able to fully trace every intermediate-epoch code path that `warp_from_parent`/`new_from_parent` execute when skipping many epochs, so I cannot confirm with certainty whether an intermediate `process_new_epoch` call for a skipped epoch could leave `vat_to_burn_per_epoch` already deducted once via the `Some` branch, then deducted again via the `None` branch for the *same* epoch under some slot/epoch-schedule configuration — this would need to be confirmed with a live repro/test, ideally in a full Devin session with code execution.

### Recommendation
- Make `maybe_burn_vat_from_staked_accounts` defensive: instead of `.expect()`-panicking on underflow, use `saturating_sub` (skipping/logging the anomalous account) or explicitly re-verify `account.lamports() >= minimum_vote_account_balance_for_vat()` immediately before subtracting, mirroring the check performed in `clone_and_filter_for_vat`.
- Ensure `get_top_epoch_stakes()`/`update_epoch_stakes(.., None)` always filters and burns against the *same* snapshot (e.g., have `update_epoch_stakes` compute the filtered snapshot once and pass it directly into `maybe_burn_vat_from_staked_accounts`, rather than relying on the untracked invariant that the two independently-computed snapshots must agree).
- Add a targeted test exercising `Bank::warp_from_parent` across a multi-epoch jump with Alpenglow/VAT active and a vote account balance close to the VAT minimum, to confirm whether the panic is reachable.

### Proof of Concept
Not confirmed as directly exploitable from local code inspection alone — the exact epoch-skip/state-divergence conditions needed to make `get_top_epoch_stakes()`'s filtering snapshot disagree with the live account balances consumed in `maybe_burn_vat_from_staked_accounts` require dynamic testing (constructing a genesis with Alpenglow active, a vote account near `minimum_vote_account_balance_for_vat()`, and calling `Bank::warp_from_parent` across multiple epochs) which I could not execute in this read-only investigation.         &mut self,
        leader_schedule_epoch: Epoch,

        //  crossed a boundary

            self.epoch_stakes.retain(|&epoch, _| {
                // Note the greater-than-or-equal (and the `- 1`) is needed here
                // to ensure we retain the oldest epoch, if that epoch is 0.
                epoch >= leader_schedule_epoch.saturating_sub(MAX_LEADER_SCHEDULE_STAKES - 1)

            // reuse it here instead of re-cloning and re-filtering the
            // `stakes_cache`. Other callers (same-epoch refresh, warps)

                leader_schedule_epoch,
                new_epoch_stakes.total_stake(),
            );
