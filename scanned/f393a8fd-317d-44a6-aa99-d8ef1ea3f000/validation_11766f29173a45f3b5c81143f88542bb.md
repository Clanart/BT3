The key discovery is a hard `assert_eq!` invariant in `build_updated_stake_reward` that checks stake delegation consistency, guarded by a feature-flag branch, where the invariant is derived from precomputed calculation-phase values but re-verified at a separate distribution phase against live state — the exact "compute now, assert later" pattern that made the original Union `AssetManager.rebalance` fragile to precision drift.

### Title
Distribution-phase stake delegation consistency assertion can panic on legitimate reward payout - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`build_updated_stake_reward` contains a hard `assert_eq!` that requires the stake delegation stored during the calculation phase to exactly equal `stake.delegation.stake + stake_reward` computed independently at distribution time, when `adjust_delegations_for_rent` is disabled. This mirrors the reported bug-class: a strict equality invariant computed from values produced in two different phases/paths, which is only safe as long as no intervening arithmetic (rounding, truncation, or rate-based adjustment) can cause the two computations to diverge by even one lamport.

### Finding Description
In `build_updated_stake_reward`, when `adjust_delegations_for_rent` is `false`, the code asserts: [1](#0-0) 

This assertion depends on `partitioned_stake_reward.inflation.stake` (`new_stake`, precomputed and cached during the calculation phase, potentially blocks earlier) matching `stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward)`, where `stake` is the *live* stake account state loaded fresh from `stakes_cache_accounts` at distribution time: [2](#0-1) 

The reward and new-stake values themselves are the output of `redeem_stake_rewards`/`calculate_stake_rewards`, whose commission-splitting math intentionally truncates fractional lamports (`commission_split`) or reallocates the remainder (`commission_split_preserve_lamports`): [3](#0-2) [4](#0-3) 

This is structurally the same defect class as the Union `AssetManager.rebalance` bug: a value computed via basis-point/percentage math in one pass (calculation phase) is later checked for exact equality against an independently-derived value in a second pass (distribution phase), with no tolerance for the inherent truncation of integer percentage math. In the Union case the dust caused a revert of the whole rebalance; here, an inconsistency would fire a Rust `assert_eq!`, which panics the validator process rather than reverting a transaction — a strictly worse outcome (process crash instead of instruction failure).

### Impact Explanation
A panic inside `build_updated_stake_reward` (invoked from `store_stake_accounts_in_partition` in the epoch-boundary reward distribution path) would crash any validator processing that block/epoch. Because epoch reward distribution is deterministic bank-processing logic executed by every validator, a state that trips this assertion would either be reached by all validators simultaneously (crash-everywhere / consensus halt) or, if only reached under specific pre-existing account states, cause a subset of validators to crash while replaying blocks, producing an availability degradation. This directly matches the requested impact category of "false execution/rooting/acceptance, consensus halt" since it is unprivileged automatic bank code, not something requiring a malicious peer or admin action.

### Likelihood Explanation
This is a defense-in-depth invariant guarded by a feature flag (`adjust_delegations_for_rent` off, i.e. `relax_post_exec_min_balance_check` inactive), so it is only reachable on configurations where that feature is not yet active. I could not fully verify from the indexed code whether there exists a live path (e.g., interaction of `use_fixed_point_stake_math`, warmup/cooldown rate changes, or delayed commission updates between the calculation and distribution blocks) that could cause the cached `partitioned_stake_reward.inflation.stake` to diverge from a freshly recomputed value by even 1 lamport before this flag is fully rolled out. This uncertainty is a genuine limitation of the analysis — a full confirmation would require tracing every mutation path of `stakes_cache_accounts` between reward calculation and the corresponding partition's distribution block, which spans multiple files (`calculation.rs`, `distribution.rs`, `mod.rs`) beyond what the index surfaced.

### Recommendation
- Replace the hard `assert_eq!` with a `saturating` recomputation or an explicit reconciliation step (analogous to "give the last recipient the exact remainder" in the original report's mitigation), rather than an equality panic.
- If the invariant is expected to always hold given current code paths, downgrade the panic to a recoverable error (as already done for `DistributionError::ArithmeticOverflow` and `AccountNotFound` in the same function) so any latent divergence degrades gracefully (burns/skips that one reward) instead of crashing the validator.
- Add fuzz/property tests that push arbitrary combinations of commission bps, rent adjustments, and warmup/cooldown rate epoch transitions between the calculation and distribution phases to confirm the assertion can never be violated under the currently-active feature configuration.

### Proof of Concept

fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
