## Title
Unauthenticated, unbounded `getProgramAccounts` full-account-table scan lacks a byte-size guard when secondary indexes are disabled — ([File: rpc/src/rpc.rs])

### Summary
`getProgramAccounts` is a public, unauthenticated JSON-RPC method reachable by any client without stake or credentials, directly analogous to the report's unauthenticated `source` endpoint. The RPC layer enforces a `scan_results_limit_bytes` guard only when a secondary account index (`AccountIndex::ProgramId`) is configured for the queried key. When that index is absent (the common/default validator configuration), `get_filtered_program_accounts` performs an in-memory scan and collects the *entire* filtered result set into a `Vec` with no byte-size ceiling, no pagination, and no per-client rate limiting.

### Finding Description
`rpc_accounts_scan::AccountsScanImpl::get_program_accounts` accepts an arbitrary `program_id_str` and optional filters straight from the network with no authentication requirement [1](#0-0) . It flows into `JsonRpcRequestProcessor::get_filtered_program_accounts`, which branches on whether `AccountIndex::ProgramId` is configured:

- If indexed: calls `get_filtered_indexed_accounts` with `byte_limit_for_scans = self.config.scan_results_limit_bytes`, which aborts the scan once the accumulated size exceeds the configured limit [2](#0-1) .
- If **not** indexed — the code path explicitly comments "this path does not need to provide a mb limit because we only want to support secondary indexes" — it calls `bank.get_filtered_program_accounts` with no byte limit at all [3](#0-2) .

`Bank::get_filtered_program_accounts` forwards straight to `Accounts::load_by_program_with_filter`, which uses `Self::load_while_filtering` to push every matching account (full account data, cloned into `AccountSharedData`) into an unbounded `collector: Vec<KeyedAccountSharedData>` with no `ScanConfig` abort mechanism (`ScanConfig::default()` has no byte limit or abort flag) [4](#0-3) [5](#0-4) . The `byte_limit_for_scan`/abort machinery (`accumulate_and_check_scan_result_size`, `maybe_abort_scan`) exists in `accounts.rs` but is wired only into the indexed path (`load_by_index_key_with_filter`), never into `load_by_program`/`load_by_program_with_filter` [6](#0-5) .

Because most validators query programs like the SPL Token program, System program, or any widely-used on-chain program that owns millions of accounts, an unauthenticated client can send a single `getProgramAccounts` request for such a `program_id`, forcing the node to load and clone every owned account's full data into heap memory and then JSON-serialize and return the entire set — with no rate limit, byte cap, or authentication gate on this path. This mirrors the report's core defect: a reachable, unauthenticated request path with no cost-based throttling, enabling resource exhaustion from a single requester.

### Impact Explanation
A single unauthenticated RPC client issuing `getProgramAccounts` against a large program with no `AccountIndex::ProgramId` configured (the default unless the operator explicitly enables `--account-index program-id`) can force unbounded heap allocation and CPU-bound account cloning/serialization on the JSON-RPC node. Repeated or concurrent such requests can degrade or crash a single RPC-serving node — a "single-client low-rate RPC crash/degradation" per the accepted impact classes. Because the RPC node's `scan_accounts` runs against `Bank`/`AccountsDb` state shared with the validation path via `bank_forks`, sustained memory pressure or an OOM on a combined validator+RPC node could impact broader operation, though the strongest, directly demonstrable impact is degradation/crash of the RPC service itself.

### Likelihood Explanation
High. No privileged credentials, stake, or special network position are required — any JSON-RPC client can invoke `getProgramAccounts` with a popular `program_id`. This is the default configuration for the many public/full RPC nodes that do not enable the `ProgramId` secondary index (enabling it has its own memory/CPU tradeoffs, so many operators leave it disabled), meaning the unguarded path is commonly reachable in practice.

### Recommendation
Wire the existing byte-limit/abort machinery (`ScanConfig::recreate_with_abort`, `accumulate_and_check_scan_result_size`, `maybe_abort_scan`) into `load_by_program` / `load_by_program_with_filter` (and the `Bank::get_filtered_program_accounts` non-indexed path), using `self.config.scan_results_limit_bytes` regardless of whether a secondary index is configured. Additionally, consider requiring `dataSlice`/filters or imposing a hard server-side account-count/byte cap and per-IP request-rate limiting for `getProgramAccounts`, similar to the token-bucket rate limiting already used for QUIC/gossip/repair paths (e.g., `ConnectionRateLimiter`/`TokenBucket` in `streamer/src/nonblocking/connection_rate_limiter.rs`) [7](#0-6) .

### Proof of Concept
1. Run a validator with `--full-rpc-api` and without `--account-index program-id` (default).
2. From any unauthenticated client, send:
```json
{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA"]}
```
3. Observe the RPC thread executes `get_filtered_program_accounts` → non-indexed branch → `bank.get_filtered_program_accounts` [8](#0-7)  → `Accounts::load_by_program_with_filter` → unbounded `collector` growth proportional to every account owned by the program, with no abort or byte cap [4](#0-3) , unlike the indexed path's `maybe_abort_scan` check [9](#0-8) .
4. Compare against the indexed path (`get_filtered_indexed_accounts`), which does return `ScanError::Aborted` once `scan_results_limit_bytes` is exceeded — confirming the non-indexed path is the outlier lacking this guard [10](#0-9) .

Note: I could not fully verify the exact default value/behavior of `scan_results_limit_bytes` (its CLI flag `accounts_index_scan_results_limit_mb` default) within the available index truncation of `validator/src/commands/run/args/json_rpc_config.rs`; a Devin session with full file access would be needed to confirm the exact default and whether any operators override it in ways that mitigate this gap.

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }

use {
    solana_net_utils::token_bucket::{KeyedRateLimiter, TokenBucket},
    std::net::IpAddr,
};

/// Limits the rate of connections per IP address.
pub struct ConnectionRateLimiter {
    limiter: KeyedRateLimiter<IpAddr>,
}

/// The threshold of the size of the connection rate limiter map. When
/// the map size is above this, we will trigger a cleanup of older
/// entries used by past requests.
const CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD: usize = 100_000;

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
}
