## Title
Front-running Core BPF migration for a stateless builtin by pre-occupying its reserved program address — ([File: runtime/src/bank/builtins/core_bpf_migration/target_builtin.rs])

## Summary
Agave's Core BPF migration pipeline for **stateless builtins** (e.g., programs like Address Lookup Table, Config, or Feature Gate that ship without a real on-chain account until migrated) checks that the reserved program address does *not yet exist* before performing the migration. Because that address is a normal, unprivileged `System`-owned account slot until the migration feature activates, any user can pre-create an account at that exact fixed pubkey ahead of time. When the migration feature later activates, the migration logic sees the (attacker-controlled) account already occupying the address and aborts the migration with `AccountExists`, permanently blocking the transition of that builtin to Core BPF — the on-chain analog of the PreimageOracle bug where a not-yet-existing address is "pre-populated" and then relied upon (in this case, relied upon to be *empty*) once the real entity is introduced.

## Finding Description
`TargetBuiltin::new_checked` validates the state of a builtin program address before a Core BPF migration is executed: [1](#0-0) 

For `CoreBpfMigrationTargetType::Stateless`, the only guard is "the program account should _not_ exist" — if `bank.get_account_with_fixed_root(program_address)` returns `Some`, the migration fails with `CoreBpfMigrationError::AccountExists`, before any capitalization or account mutation occurs. Because a stateless builtin's reserved address is, prior to migration, just an ordinary pubkey not owned by anything special, any unprivileged actor who knows the (public, hard-coded) target address can send a normal `system_instruction::create_account` (or any transfer that funds it) to that address at any time before the migration feature is activated. `builtins/src/core_bpf_migration.rs` documents that these addresses are static, well-known constants baked into the validator binary, and `builtins/src/lib.rs` shows the migration is driven purely by `feature_id` activation, with no mechanism to reclaim or exclude a pre-existing account at that address: [2](#0-1) [3](#0-2) 

The migration entry point `migrate_builtin_to_core_bpf` calls `TargetBuiltin::new_checked` and simply logs a warning on failure — it does **not** retry, does **not** mark the feature as unsuccessfully processed, and does **not** otherwise recover: [4](#0-3) 

The unit test `test_target_program_stateless_builtin` explicitly confirms this exact behavior — pre-storing an account at the stateless builtin's address causes `AccountExists`: [5](#0-4) 

This mirrors the report's broken invariant precisely: `loadPrecompilePreimagePart()` let anyone write to a key derived from an address that "doesn't exist yet" but will later be trusted; here, anyone can occupy an address that "doesn't exist yet" but is later required to be trusted-empty for a protocol-critical migration to proceed. In both cases, the guard that is supposed to establish trust in future state is defeated because an unprivileged actor can act on the address before it acquires its special meaning.

## Impact Explanation
If a stateless builtin is scheduled for Core BPF migration (Agave's builtins framework is explicitly designed for this — see `STATELESS_BUILTINS` and the historical migrations of `address-lookup-table`, `config`, and `feature-gate` programs referenced in `fetch-core-bpf.sh`), any single unprivileged user can permanently block that specific migration from ever completing across the entire cluster by pre-funding/creating an account at the hard-coded target address before the feature-gate activates: [6](#0-5) 

Because all validators evaluate the same deterministic state, this does not cause a fork/consensus split, but it does cause a network-wide, deterministic failure of a planned protocol upgrade: the builtin remains stuck in its old (potentially soon-to-be-removed) native/stateless implementation indefinitely, and the feature is marked "activated" in `FeatureSet` while the intended code swap silently never happens. Depending on release planning (e.g., if client teams later drop the native implementation assuming the BPF migration succeeded), this could result in that builtin's instructions becoming fully non-functional cluster-wide — a protocol-level denial of service against a builtin program, triggered entirely by an unprivileged account-creation transaction.

## Likelihood Explanation
In the current snapshot, `STATELESS_BUILTINS` is empty outside of `dev-context-only-utils` test configs, so there is no builtin actively scheduled through this exact path today: [7](#0-6) 

However, the migration mechanism itself is shipped, unconditional, and has been used historically for real programs (address-lookup-table, config, feature-gate) that started as stateless builtins. Any future reuse of `CoreBpfMigrationTargetType::Stateless` with this unmodified check reintroduces the exploit window automatically, and the target addresses are necessarily public/hard-coded (`declare_id!`) well before the feature is proposed and voted on, giving an attacker ample advance notice and a trivial, cheap primitive (`system_instruction::create_account`) to execute the front-run.

## Recommendation
For `CoreBpfMigrationTargetType::Stateless`, do not unconditionally reject when the address already has an account. Instead:
- Verify the account, if present, is owned by the `System` program and has no meaningful data/executable flag (analogous to the existing "prefunded" allowance already used for the program-data address in the `Builtin` case), and absorb/burn any pre-existing lamports as part of the migration rather than aborting.
- Alternatively, require the migration authority to reclaim/close any account occupying the reserved address as a precondition recorded on-chain, rather than relying on an implicit "must not exist" invariant that unprivileged users can violate before the feature activates.

## Proof of Concept
1. Identify the reserved `program_address` for a builtin configured with `CoreBpfMigrationTargetType::Stateless` (these are compile-time constants, visible in the client source, e.g. via `solana_pubkey::declare_id!` in `builtins/src/lib.rs`'s `test_only` module or a future production config).
2. Before the associated `feature_id` is activated on cluster, submit an ordinary transaction: `SystemProgram::create_account(payer, program_address, lamports, 0, system_program::id())` (or simply a `transfer` that funds the address, which is enough for `get_account_with_fixed_root` to return `Some`).
3. Once the feature-gate account is later created and voted in, `Bank::apply_new_builtin_program_feature_transitions` invokes `migrate_builtin_to_core_bpf`, which calls `TargetBuiltin::new_checked(..., CoreBpfMigrationTargetType::Stateless, ...)`: [8](#0-7) 
4. `bank.get_account_with_fixed_root(program_address).is_some()` is `true` (the attacker's account), so the function returns `Err(CoreBpfMigrationError::AccountExists(program_address))`.
5. `migrate_builtin_to_core_bpf` returns `Err`, and `apply_new_builtin_program_feature_transitions` merely logs a warning and moves on — the builtin is never migrated, for every validator, permanently (unless a follow-up hard fork changes the logic).
