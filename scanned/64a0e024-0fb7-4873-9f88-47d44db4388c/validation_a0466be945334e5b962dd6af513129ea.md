### Title
Unchecked (non-saturating) counter subtraction in `CostTracker::remove_transaction_cost` can underflow/corrupt block-cost accounting - (File: cost-model/src/cost_tracker.rs)

### Summary
The Compound bug's broken invariant is: code assumes a numeric precondition (`dsr >= 1e27`) always holds and performs a raw subtraction without a guard, so if that assumption is ever violated the call reverts/panics, breaking downstream logic that depended on it running (`poke`). The Agave analog is the same broken-invariant/raw-subtraction pattern in `CostTracker::remove_transaction_cost`, which assumes a transaction being "removed" was always previously "added" with exactly matching counts, and decrements several counters with plain `-=` instead of `checked_sub`/`saturating_sub`.

### Finding Description
`CostTracker::add_transaction_cost` increments `transaction_count`, per-signature-type counters, and `allocated_accounts_data_size` unconditionally on insertion: [1](#0-0) 

`remove_transaction_cost` mirrors this with plain subtraction (`-=`), not `checked_sub`/`saturating_sub`, for `allocated_accounts_data_size`, `transaction_count`, and the three signature-type counters: [2](#0-1) 

In contrast, the sibling function `sub_transaction_execution_cost`, used inside the same removal path, deliberately uses `saturating_sub`/atomic `fetch_sub` for `cost_by_writable_accounts` and `block_cost`: [3](#0-2) 

This inconsistency is exactly the DSR-bug pattern: the safe/guarded arithmetic path (`saturating_sub`) exists right next to the unguarded raw-subtraction path, meaning the author assumed the invariant "every remove corresponds to exactly one prior add with the same values" can never be violated for the counter fields, while explicitly not trusting that same invariant for the cost totals. If that invariant is ever broken — e.g., a transaction's cost/signature counts get removed twice, or removed with a mismatched/larger value than what was added (through any bug in the retry/replay accounting that calls this API, or a future code change that doesn't preserve strict 1:1 add/remove symmetry) — the plain `-=` will either underflow-panic (if overflow checks are active) or silently wrap to a huge value (if not), corrupting `transaction_count`/signature counters used elsewhere for block-cost-limit enforcement.

### Impact Explanation
Depending on whether overflow checks are active in the build profile actually used for validators, this manifests as one of two `Valid Impact` categories:
- If overflow checks are enabled, an underflow triggers a Rust panic, which is a crash of the thread holding `CostTracker` (banking/replay), a non-RPC crash/availability impact.
- If overflow checks are disabled (the standard release default in Rust unless the workspace explicitly opts in — I could not confirm Agave's `Cargo.toml` profile setting for this within the available iterations), the subtraction silently wraps, corrupting the counters used by cost-tracking/block-limit logic, which is a false-acceptance risk (a block/bank could be treated as under its cost limit when it is not, or vice versa) — I could not confirm this without checking the Cargo.toml profile section, which returned tool errors before I ran out of iterations.

### Likelihood Explanation
Low-to-moderate confidence. I confirmed the code-level asymmetry (unguarded `-=` next to a guarded `saturating_sub` in the same struct/file) but did not verify:
1. Whether any call path can legitimately violate the 1:1 add/remove invariant (I did not trace all callers of `remove_transaction_cost`).
2. Whether the workspace `Cargo.toml` sets `overflow-checks = true` for release builds — my attempt to read this failed due to a tool error on the final iteration, so I cannot state definitively whether this underflows into a panic or silently wraps in production builds.

### Recommendation
Use `checked_sub`/`saturating_sub` (matching the pattern already used for `cost_by_writable_accounts` and `block_cost`) for `allocated_accounts_data_size`, `transaction_count`, and the three signature-count fields in `remove_transaction_cost`, and add an explicit invariant check/log if a removal is attempted for values that were never fully accounted for, rather than relying on raw subtraction to always succeed.

### Proof of Concept
Not independently verified — a concrete PoC requires confirming (a) the actual `overflow-checks` setting in the release profile Cargo.toml, and (b) a concrete call path in banking/replay that invokes `remove_transaction_cost` twice or with mismatched values relative to the corresponding `add_transaction_cost`. I recommend a Devin session with full repo/terminal access to inspect `Cargo.toml`'s `[profile.release]` section and trace all callers of `CostTracker::remove_transaction_cost` (e.g., in `qos_service.rs` / bank cost-tracker retry/rollback paths) to confirm reachability before treating this as a fully substantiated finding.

    /// Subtract extra execution units from cost_tracker
    fn sub_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) {
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_sub(adjustment);
        }
        self.block_cost.fetch_sub(adjustment);
    }
