### Title
Any WebSocket client can unsubscribe (cancel) another client's RPC pubsub subscription by guessing/enumerating its `SubscriptionId` - ([File: rpc/src/rpc_pubsub.rs])

### Summary
`RpcSolPubSubImpl` keeps a single, connection-agnostic table of all live subscriptions (`current_subscriptions: Arc<DashMap<SubscriptionId, SubscriptionToken>>`), and every `*_unsubscribe` RPC method removes an entry from that table purely by numeric ID, with no check that the caller's own WebSocket connection created that subscription. [1](#0-0)  This is the same class of bug as the reported `TransferAgentGateway`/`TransactionalModule` issue: a "cancel" entry point checks that the caller is *some* authorized actor, but never checks that the caller is the *owner* of the specific resource (`account`/`requestId` there, `SubscriptionId` here), letting any caller cancel/destroy state belonging to someone else.

### Finding Description
`RpcSolPubSubImpl::unsubscribe` is the common implementation backing `account_unsubscribe`, `program_unsubscribe`, `logs_unsubscribe`, `signature_unsubscribe`, `slot_unsubscribe`, `block_unsubscribe`, `vote_unsubscribe`, and `root_unsubscribe`:

```rust
fn unsubscribe(&self, id: SubscriptionId) -> Result<bool> {
    if self.current_subscriptions.remove(&id).is_some() {
        Ok(true)
    } else {
        Err(...)
    }
}
``` [2](#0-1) 

All of the corresponding `*_unsubscribe` handlers simply forward the raw `id` parameter into this shared method — none of them consult `meta`/connection identity to verify the subscription belongs to the caller's session: [3](#0-2) [4](#0-3) 

The subscription registry itself, `current_subscriptions`, is held on `RpcSolPubSubImpl` as a single shared `DashMap` — it is not partitioned per WebSocket connection, and `SubscriptionId` values are sequential/enumerable integers (as shown in tests using literal `0`, `1`, `2`, ... as IDs). [5](#0-4) [6](#0-5) 

Because the unsubscribe path removes by ID from this globally shared map without any ownership/session check, any connected RPC client can call, e.g., `accountUnsubscribe` (or any of the other `*Unsubscribe` methods) with an ID that was actually allocated to a *different* client's subscription, silently tearing down that other client's live subscription. The broken invariant is identical to the report's: "a caller can act on a resource identified by an ID, without the system verifying the caller is the resource's owner."

### Impact Explanation
An unprivileged, unstaked RPC client (no special permission, just a JSON-RPC/WebSocket connection) can enumerate small sequential subscription IDs and repeatedly issue unsubscribe calls, silently canceling other legitimate clients' `accountSubscribe`/`programSubscribe`/`signatureSubscribe`/`logsSubscribe`/etc. notifications. This causes those victim clients to stop receiving expected account/program/signature/log/slot notifications without any error being surfaced to them (they simply stop getting updates), which is a remote, low-rate, single-client-triggerable degradation/DoS of the RPC pubsub subsystem — the same "cancel someone else's pending state" DoS pattern described in the source report, just applied to Agave's RPC/pubsub subscription lifecycle instead of MMF transaction requests.

### Likelihood Explanation
High. Exploitation requires only: (1) opening a normal pubsub WebSocket connection, (2) calling any `*_subscribe` method to observe how `SubscriptionId` values are allocated (they are small increasing integers per the test fixtures), and (3) calling the matching `*_unsubscribe` method with IDs outside the attacker's own subscriptions. No stake, no admin privilege, and no race condition is needed — the missing check is a straightforward logic omission, not a timing-dependent bug.

### Recommendation
Bind each `SubscriptionToken`/`SubscriptionId` to the `Metadata`/connection (session) that created it, and have `unsubscribe` verify that the requesting connection's session matches the subscription's owning session before removing it from `current_subscriptions`, mirroring how the report recommends `TransferAgentGateway.cancelRequest` should verify `msg.sender == account` before forwarding the cancellation. Additionally, avoid predictable/enumerable subscription IDs to reduce the ease of guessing another client's subscriptions, and add tests asserting that unsubscribe calls from a different connection than the one that created the subscription fail.

### Proof of Concept
1. Open WebSocket connection A, call `accountSubscribe(pubkeyA)` → receives `SubscriptionId = N`.
2. Open WebSocket connection B (different, unprivileged client), call `accountUnsubscribe(N)`.
3. Because `RpcSolPubSubImpl::unsubscribe` only checks `self.current_subscriptions.remove(&id).is_some()` with no session/ownership check, connection B's request succeeds and connection A's subscription is silently torn down — despite B never having created it. [2](#0-1) 

Note: I was unable to fully confirm (index truncated before final read) whether `RpcSolPubSubImpl` is instantiated once and shared across all client connections vs. per-connection in `rpc/src/rpc_pubsub_service.rs`; the `Arc<DashMap<...>>` sharing pattern and the fact that `unsubscribe` takes no connection/session parameter strongly indicate a shared, connection-agnostic registry, but a Devin session with full repo access should verify `rpc_pubsub_service.rs`'s construction/wiring of `RpcSolPubSubImpl` to confirm this before treating the PoC as conclusively reproducible.

pub struct RpcSolPubSubImpl {
    config: PubSubConfig,
    subscription_control: SubscriptionControl,
    current_subscriptions: Arc<DashMap<SubscriptionId, SubscriptionToken>>,
}

impl RpcSolPubSubImpl {
    pub fn new(
        config: PubSubConfig,
        subscription_control: SubscriptionControl,
        current_subscriptions: Arc<DashMap<SubscriptionId, SubscriptionToken>>,
    ) -> Self {
        Self {
            config,
            subscription_control,
            current_subscriptions,
        }
    }

    fn subscribe(&self, params: SubscriptionParams) -> Result<SubscriptionId> {
        let token = self
            .subscription_control
            .subscribe(params)
            .map_err(|_| Error {
                code: ErrorCode::InternalError,
                message: "Internal Error: Subscription refused. Node subscription limit reached"
                    .into(),
                data: None,
            })?;
        let id = token.id();
        self.current_subscriptions.insert(id, token);
        Ok(id)
    }

    fn unsubscribe(&self, id: SubscriptionId) -> Result<bool> {
        if self.current_subscriptions.remove(&id).is_some() {
            Ok(true)
        } else {
            Err(Error {
                code: ErrorCode::InvalidParams,
                message: "Invalid subscription id.".into(),
                data: None,
            })
        }
    }
