## Title
Deterministic panic in `Bank::deposit_or_burn_fee` when a leader's vote account is absent from `epoch_stakes`, causing a validator-wide consensus halt - (File: `runtime/src/bank/fee_distribution.rs`)

## Summary
The external report's bug class is: an *unrelated* precondition check performed deep inside a call chain (a "hook" — `Disqualifier`/`ChefIncentivesController`) can `revert`/abort an otherwise-legitimate, routine operation (staking/withdrawal), because the code assumes the checked precondition can never fail. The closest Agave analog is `Bank::deposit_or_burn_fee`, which — instead of gracefully handling a missing lookup — uses `.expect(...)` to assert that the current slot's leader vote account is present in the epoch's cached stake/vote-account set. If that assumption is ever false, the routine, protocol-mandated per-block fee distribution operation panics deterministically on every validator processing that block.

## Finding Description
Per-block transaction fee distribution calls `distribute_transaction_fee_details()` → `deposit_or_burn_fee()`. When `custom_commission_collector` (SIMD-0232) is active, the collector address is resolved by looking up the current leader's vote account inside `self.epoch_stakes`: [1](#0-0) 

```rust
let vote_account = self
    .epoch_stakes
    .get(&self.epoch)
    .and_then(|stakes| {
        stakes
            .stakes()
            .vote_accounts()
            .get(&self.leader.vote_address)
    })
    .expect("The vote account for the leader must exist");
```

This lookup is asserted with `.expect("The vote account for the leader must exist")` rather than falling back to a safe default (as is done immediately afterward for the *collector field* being absent: `.unwrap_or(&self.leader.id)`). The code comment even acknowledges edge cases exist ("Protection in case the leader is on a vote state without a collector id, which can happen if a dormant pre-v4 vote state accrues stake") — showing the authors were aware that vote-account state can diverge from expectations, yet only guarded the inner field lookup and not the outer `vote_accounts().get(...)` lookup itself.

This mirrors the reported bug-class exactly: a routine, always-expected-to-succeed operation (distributing transaction fees for the current block, executed by every validator on every block) is made to depend on an unrelated invariant (that the current slot's leader is always present in the cached `epoch_stakes` vote-account map) holding perfectly. If that invariant is ever violated — e.g., due to a race between leader-schedule computation, epoch-stakes snapshotting, and vote-account lifecycle events (vote account closure/deinitialization via `withdraw()`, as seen in `programs/vote/src/vote_state/mod.rs`, or removal via any "VAT burn" logic referenced in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` around `update_epoch_stakes`) — the `.expect()` fires and the validator process panics, instead of the code degrading gracefully (e.g., falling back to `self.leader.id`, exactly as done for the collector-field case one line later).

Because `distribute_transaction_fee_details` runs deterministically as part of normal block-reward/fee bookkeeping for *every block*, on *every* validator that processes that block (not just the leader), a single triggering condition would cause a synchronized, cluster-wide panic — the "false execution/consensus halt" impact category — rather than a contained, recoverable error for one account/user, unlike the analogous smart-contract report which recommended isolating the failure to the affected user rather than reverting/halting everything.

## Impact Explanation
If the invariant "the current leader's vote account is always present in the cached epoch_stakes" is violated, `Bank::deposit_or_burn_fee` panics. Since this code path executes for every processed block on every validator (both replaying and voting nodes) as part of routine fee bookkeeping, a violation would not be an isolated node crash but a deterministic, network-wide panic at the same block — a consensus/liveness halt, which sits squarely in the "Valid Impact" categories (runtime, non-RPC-triggered halt).

## Likelihood Explanation
I was not able to fully confirm, from the available indexed code, a concrete path by which the current leader's vote account can become absent from `self.epoch_stakes.get(&self.epoch).stakes().vote_accounts()` for a slot where that node is still the scheduled leader (`epoch_stakes` is intended to be an immutable snapshot fixed at leader-schedule computation time, which should normally guarantee the entry exists). The code's own inline comment for the adjacent `unwrap_or(&self.leader.id)` fallback, together with the `distribute_reward_commissions` comment about "VAT burns in `update_epoch_stakes`" mutating vote/stake state after the fact, suggests the authors anticipated some divergence between snapshot-time and distribution-time account state, but I could not fully trace `update_epoch_stakes`'s effect on the `vote_accounts()` map within the indexed portion of the codebase (search results only surfaced related test files and the commission-distribution comment, not the mutation logic itself). This limits me to identifying the fragile pattern (`.expect()` on a lookup that is elsewhere treated as fallible) rather than a fully demonstrated triggering sequence — likelihood should be treated as unconfirmed/uncertain pending further investigation of `update_epoch_stakes`.

## Recommendation
- Replace the `.expect("The vote account for the leader must exist")` panic with a graceful fallback (e.g., default to `&self.leader.id`, matching the fallback pattern used one line later for the missing collector field), so an unexpected missing/stale epoch-stakes entry degrades to burning/depositing to the leader's identity account instead of panicking.
- Audit all other `.expect()`/`.unwrap()` calls in per-block, always-executed runtime paths (`runtime/src/bank/fee_distribution.rs`, `runtime/src/bank/partitioned_epoch_rewards/*`) for similar "this can never fail" assumptions about live vote/stake account state, and convert them to error-tolerant handling consistent with the surrounding code's existing defensive patterns.
- Add fuzz/property tests that intentionally desynchronize `epoch_stakes` from the live leader schedule (e.g., vote account closed/deinitialized mid-epoch) to confirm the fee-distribution path no longer panics.

## Proof of Concept
Not independently reproducible from the indexed code alone: a full PoC would require constructing a scenario in which `self.epoch_stakes.get(&self.epoch)` exists but its `vote_accounts()` map lacks the entry for `self.leader.vote_address` while that address is still the scheduled leader for the slot being processed (e.g., by manipulating `update_epoch_stakes`/VAT-burn logic referenced in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`).
