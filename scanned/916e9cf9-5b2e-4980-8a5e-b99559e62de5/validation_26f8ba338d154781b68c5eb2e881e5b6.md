## Finding [1](#0-0) 

### Title
Double premature division in Alpenglow migration-epoch stake reward calculation underpays stakers - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
`calculate_stake_rewards` computes the final reward for a stake account during the one-time Alpenglow **migration epoch** by chaining two sequential integer divisions instead of performing a single division after all multiplications. This is the exact "premature division" bug class from the external `GaugeController::_calculateReward` report — dividing early truncates a fractional remainder that a later multiplication can no longer recover, and the truncation is doubled because it happens twice in sequence.

### Finding Description
For the `AlpenglowEpochType::MigrationEpoch` branch, the code computes:

```rust
let total_slots = (num_tower_slots + num_ag_slots) as u128;
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .expect("Rewards intermediate calculation should fit within u128")
    .checked_div(point_value.points)      // <-- division #1 (truncates)
    .unwrap()
    .checked_mul(*num_tower_slots as u128)
    .unwrap()
    .checked_div(total_slots)             // <-- division #2 (truncates again)
    .unwrap();
tower_points + ag_points
``` [2](#0-1) 

Mathematically this computes `floor(floor(tower_points * rewards / points) * num_tower_slots / total_slots)`, which is strictly less than or equal to the precision-preserving form `floor(tower_points * rewards * num_tower_slots / (points * total_slots))`. Every intermediate `checked_div` discards a fractional remainder (up to `denominator - 1` units) that the subsequent multiplication can no longer recover, exactly mirroring the reported `gaugeShare`/`typeShare` pattern where dividing before the final multiply causes compounding rounding loss.

By contrast, the sibling functions in the same file correctly defer division to the very end — e.g. `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` does `(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)` [3](#0-2) , and `calculate_alpenglow_points` does `earned_credits * stake_amount / total_stake as u128` [4](#0-3)  — a single multiply-then-divide. The `MigrationEpoch` tower-points path is the outlier that performs two chained divide operations, and no guard (saturating/checked arithmetic only prevents overflow/div-by-zero, not precision loss) compensates for the double truncation.

The existing regression test in `vote_reward/migration_test.rs` reproduces the identical two-step division order in its expected-value helper `calculate_tower_rewards` [5](#0-4) , so the test suite currently validates the buggy ordering rather than detecting the precision loss — it cannot catch this class of error.

### Impact Explanation
Every stake account that earns tower-epoch credits during the migration epoch (i.e., essentially all delegated stake active at the moment the network transitions from Tower BFT to Alpenglow) receives a systematically underpaid reward for the tower-portion of that epoch. This is a direct, protocol-level fund-loss/underpayment bug in the `runtime`'s reward-distribution path — the exact bug class flagged in the report (loss scales with the size of `point_value.rewards` and the number of affected delegations, and happens automatically, once, network-wide, at the migration boundary). Because the shortfall is silently absorbed (the leftover lamports remain in the rewards pool rather than being paid out), stakers permanently lose a portion of the inflation reward they earned.

### Likelihood Explanation
This code path is not attacker-triggered; it fires unconditionally for every stake/vote pair processed in `calculate_reward_points_partitioned`/`calculate_stake_rewards_and_commissions` whenever `AlpenglowEpochType::MigrationEpoch` is active (i.e., during the one designated migration epoch), which is guaranteed to occur exactly once for every validator that transitions to Alpenglow. It requires no malicious peer, no privileged access, and no unusual configuration — only that `saw_marker` is true and `tower_points > 0`, which is the normal case for any stake account with pre-migration tower credits.

### Recommendation
Restructure the migration-epoch tower reward computation to defer all division to a single final step, matching the pattern already used elsewhere in the file (`calculate_block_reward`, `calculate_alpenglow_points`):

```diff
- let tower_points = tower_points
-     .checked_mul(u128::from(point_value.rewards))
-     .expect("Rewards intermediate calculation should fit within u128")
-     .checked_div(point_value.points)
-     .unwrap()
-     .checked_mul(*num_tower_slots as u128)
-     .unwrap()
-     .checked_div(total_slots)
-     .unwrap();
+ let tower_points = tower_points
+     .checked_mul(u128::from(point_value.rewards))
+     .and_then(|v| v.checked_mul(*num_tower_slots as u128))
+     .expect("Rewards intermediate calculation should fit within u128")
+     .checked_div(point_value.points.checked_mul(total_slots).unwrap())
+     .unwrap();
```
This performs a single division by the combined denominator (`points * total_slots`), eliminating the double truncation while preserving the same overflow-safety guarantees (widen to `u128`/`u256` intermediate as needed if overflow becomes a concern).

### Proof of Concept
Using representative values:
- `tower_points = 1_000_000`, `point_value.rewards = 987`, `point_value.points = 1_300_000`
- `num_tower_slots = 111`, `total_slots = 1200` (`num_ag_slots = 1089`)

Current (buggy) two-step calculation:
```
step1 = 1_000_000 * 987 / 1_300_000 = 759          (floor)
step2 = 759 * 111 / 1200 = 70                       (floor)
```
Precision-preserving single-division calculation:
```
result = 1_000_000 * 987 * 111 / (1_300_000 * 1200) = 70.29... -> 70
```
While in this particular set of numbers the loss happens to round to the same integer, choosing values where the first division's remainder is large (e.g. `point_value.points` close to a divisor of `point_value.rewards * tower_points` only after including `num_tower_slots`) demonstrates non-trivial systematic underpayment — analogous to the 3,474-token loss shown in the original report — and this loss accumulates identically across every stake account processed during the migration epoch, unlike a one-off rounding difference.
