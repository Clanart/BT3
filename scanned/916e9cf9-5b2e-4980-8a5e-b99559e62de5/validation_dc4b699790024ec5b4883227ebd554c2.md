## Title
Unbounded per-key growth in `SecondaryIndex` lets an unprivileged attacker force disproportionately expensive `getTokenAccountsByOwner`/`getProgramAccounts` scans against a victim key - (`File: accounts-db/src/accounts_index/secondary.rs`)

## Summary
The TRST-M-3 bug class is: anyone can cheaply insert unbounded entries into a collection keyed by an *arbitrary* (often victim-controlled) address, and a later, unrelated operation for that address copies the *entire* collection from storage into memory, making that operation disproportionately expensive. The Agave analog is `SecondaryIndex::insert` in `accounts-db/src/accounts_index/secondary.rs`, which is fed by the `ProgramId`/`SplTokenOwner`/`SplTokenMint` account-index maintained during normal account writes. Any unprivileged actor can create accounts whose `owner` byte-field is set to an arbitrary pubkey (e.g. a victim's wallet), causing that pubkey's `RwLockSecondaryIndexEntry::account_keys` `HashSet<Pubkey>` to grow without bound. When that key is later queried, `keys()` clones the *entire* set into a `Vec<Pubkey>` in one call.

## Finding Description
`SecondaryIndex::insert` stores index entries in a `DashMap<Pubkey, SecondaryIndexEntryType>`, where each entry (`RwLockSecondaryIndexEntry`) is a `HashSet<Pubkey>` guarded by an `RwLock`: [1](#0-0) 

`insert_if_not_exists` grows this set with no upper bound on the number of `inner_keys` recorded under a single outer key: [2](#0-1) 

The outer key is not restricted to keys the caller owns or controls in any privileged way — for `IndexKey::SplTokenOwner`/`IndexKey::SplTokenMint` the outer key is read straight out of attacker-supplied account data (the `owner`/`mint` byte fields of an SPL-token-shaped account), and for `IndexKey::ProgramId` it is simply the `owner` field set by whatever program created the account. This means any unprivileged party can permissionlessly create many accounts that all "point at" the same victim pubkey (e.g., set the token-account `owner` field to a target wallet the attacker does not control), incrementing that pubkey's entry in the secondary index each time — the same "donate low-cost writes now, someone else pays later" primitive as in TRST-M-3's `deploySpareSubAccount`.

Later, any call for that key retrieves the *entire* set at once: [3](#0-2) 

and via the accounts index: [4](#0-3) 

which is invoked from `get_filtered_indexed_accounts`/`load_by_index_key_with_filter`, reachable from the `getProgramAccounts`, `getTokenAccountsByOwner`, and `getTokenAccountsByDelegate` RPC methods: [5](#0-4) [6](#0-5) 

The guard that exists (`byte_limit_for_scan` / `KeyExcludedFromSecondaryIndex`) only bounds the *aggregate bytes of loaded accounts during the scan* or excludes specific pre-configured keys from indexing — it does not bound the number of entries a single index key can accumulate before that scan even starts: [7](#0-6) [8](#0-7) 

So exactly as in TRST-M-3, the `key -> Vec<Pubkey>`/`HashSet<Pubkey>` fan-out is unbounded at write time, and fully materialized into memory (`keys()` → `Vec<Pubkey>`) at read time, regardless of how large it has grown.

## Impact Explanation
An attacker can permissionlessly and cheaply (bounded only by normal account-creation rent, which is a fixed low cost per account and independent of the victim) inflate the `account_keys` set for an arbitrary owner/program/mint pubkey to a very large size. Any subsequent `getProgramAccounts`, `getTokenAccountsByOwner`, or `getTokenAccountsByDelegate` request against that key on an RPC node running with the corresponding secondary index enabled (`--account-index program-id|spl-token-owner|spl-token-mint`) must clone/collect the full set and then scan/load every referenced account, causing large memory allocation, CPU cost, and latency on that RPC node. This degrades a single RPC node's ability to serve requests (RPC/pubsub availability degradation), matching the "single-client low-rate RPC crash/degradation" category, and can be repeated cheaply against many victim keys to broaden the effect.

## Likelihood Explanation
Likelihood is moderate and gated by configuration: the affected code path only runs on nodes that have opted into the relevant `AccountsIndex` (`ProgramId`, `SplTokenOwner`, `SplTokenMint`), which many RPC-serving nodes do enable to support these exact RPC methods efficiently. Creating the attacker accounts requires only the normal (low, fixed) cost of account creation via the System/SPL-Token programs and requires no special privilege, no malicious peer/validator assumption, and no leaked keys — it only requires writing attacker-controlled data into an account field (owner/mint) that is not authenticated to belong to the queried party.

## Recommendation
Bound the number of `inner_keys` an `RwLockSecondaryIndexEntry`/outer key can accumulate (or cap the number of entries the index will materialize per query), analogous to the TRST-M-3 fix of capping spare subaccounts to a small constant. Concretely:
- Enforce a per-outer-key maximum in `SecondaryIndex::insert`/`insert_if_not_exists`, rejecting or evicting further insertions once the cap is hit, and/or
- Enforce a hard cap on the number of pubkeys returned by `get_index_key_pubkeys`/`keys()` before any account-loading work begins, independent of the existing `byte_limit_for_scan` (which only limits the loaded-account-bytes total, not the initial index-key fan-out).

## Proof of Concept
Conceptual PoC (cannot be executed without an environment):
1. Attacker submits many transactions creating SPL-token-account-shaped accounts (or program-owned accounts) whose `owner` (or `mint`) field is set to `victim_pubkey`, an address the attacker does not control. Each such account is inserted into the secondary index via `SecondaryIndex::insert(key=victim_pubkey, inner_key=new_account)` [9](#0-8) , growing `victim_pubkey`'s `account_keys` `HashSet` without limit.
2. Any RPC client subsequently calls `getTokenAccountsByOwner(victim_pubkey, ...)` (or `getProgramAccounts(victim_pubkey,...)` if indexed by `ProgramId`), which resolves to `get_filtered_indexed_accounts` → `get_index_key_pubkeys` → `keys()`, materializing the entire inflated set into a `Vec<Pubkey>` [10](#0-9)  and then loading/filtering every one of those accounts, causing large, attacker-amplified CPU/memory cost on the serving RPC node for what looks like a normal, cheap read request against `victim_pubkey`.

#[derive(Debug, Default)]
pub struct RwLockSecondaryIndexEntry {
    account_keys: RwLock<HashSet<Pubkey>>,
}

impl SecondaryIndexEntry for RwLockSecondaryIndexEntry {
    fn insert_if_not_exists(&self, key: &Pubkey, inner_keys_count: &AtomicU64) {
        if self.account_keys.read().unwrap().contains(key) {
            // the key already exists, so nothing to do here
            return;
        }

        let was_newly_inserted = self.account_keys.write().unwrap().insert(*key);
        if was_newly_inserted {
            inner_keys_count.fetch_add(1, Ordering::Relaxed);
        }
    }

    fn remove_inner_key(&self, key: &Pubkey) -> bool {
        self.account_keys.write().unwrap().remove(key)
    }

    fn is_empty(&self) -> bool {
        self.account_keys.read().unwrap().is_empty()
    }

    fn keys(&self) -> Vec<Pubkey> {
        self.account_keys.read().unwrap().iter().cloned().collect()
    }

    fn len(&self) -> usize {
        self.account_keys.read().unwrap().len()
    }
}

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

        if self.stats.last_report.should_update(1000) {
            datapoint_info!(
                self.metrics_name,
                ("num_secondary_keys", self.index.len(), i64),
                (
                    "num_inner_keys",
                    self.stats.num_inner_keys.load(Ordering::Relaxed),
                    i64
                ),
                ("num_reverse_index_keys", self.reverse_index.len(), i64),
            );
        }
    }
