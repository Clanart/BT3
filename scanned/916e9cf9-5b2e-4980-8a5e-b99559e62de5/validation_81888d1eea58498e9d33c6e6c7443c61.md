## Analysis

The claim is confirmed by the code: an unauthenticated GET request to `/v0/circulating-supply` is routed through `RpcRequestMiddleware::on_request`, which matches the path via `match_supply_path` and calls `process_rest` unconditionally for every matching request. [1](#0-0) 

`process_rest` spawns an async future that calls `handle_rest`, which for `/v0/circulating-supply` reads the root bank and calls `calculate_circulating_supply_async`. [2](#0-1) 

`calculate_circulating_supply_async` offloads the work to `tokio::task::spawn_blocking`, running `calculate_non_circulating_supply(&bank)` on the RPC service's blocking thread pool, not the async worker threads. [3](#0-2) 

`calculate_non_circulating_supply` performs a full program-account scan of all stake accounts (`get_filtered_indexed_accounts` or `get_program_accounts`), deserializes each into `StakeStateV2`, and sums balances — an O(accounts) operation with no caching, executed fresh on every single call. [4](#0-3) 

Critically, there is **no rate limiting, caching, or authentication** anywhere in this path — `on_request` in `RpcRequestMiddleware` performs the dispatch unconditionally for any request matching the path string, with no auth/session checks, and the result of the scan is not cached (contrast with `LargestAccountsCache`, which exists elsewhere in the same file for a similar RPC method but is not applied to this endpoint). [5](#0-4) [6](#0-5) 

**Mitigating factor:** the scan is explicitly offloaded via `spawn_blocking` onto the dedicated blocking thread pool (`rpc_blocking_threads`, configurable, default `num_cpus/2`), which is a separate pool from the async worker threads (`rpc_threads`) that service all other JSON-RPC requests. The code comment explicitly documents this design intent: "use `tokio::task::spawn_blocking()` to avoid blocking the worker threads on CPU bound operations ... so fast rpc calls (the majority) are not blocked by slow CPU bound ones." [7](#0-6) 

So while repeated requests to this endpoint will genuinely consume `rpc_blocking_threads` worker capacity and could exhaust that specific pool (a real, uncapped, unauthenticated resource-consumption path), it does not directly starve the primary async event-loop workers that service ordinary JSON-RPC method calls — those run on separate `rpc_threads`. If an attacker saturates all blocking threads (e.g., `rpc_blocking_threads` is defaulted to `num_cpus/2`), other blocking-pool consumers (e.g. `getMultipleAccounts`, other CPU-bound RPC calls that also use `spawn_blocking`) would be starved and degraded/timed out, but the primary jsonrpc event loop and TPU/QUIC/gossip/repair paths are unaffected.

## Verdict

This is a genuine, real design gap: `/v0/circulating-supply` is unauthenticated, uncached, and triggers a full uncapped account scan on every call, and there's no rate limiting on this REST path. This can degrade the RPC blocking thread pool under repeated invocation, which is consistent with "single-client low-rate RPC crash/degradation" in the valid impact criteria. However, the isolation via `spawn_blocking` limits blast radius to the blocking-thread pool rather than the full RPC subsystem, and this doesn't cause fund theft, consensus halt, or non-RPC exhaustion — it's a resource-exhaustion/degradation issue scoped specifically to RPC responsiveness for this endpoint and any other blocking-thread consumers.

### Title
Unauthenticated `/v0/circulating-supply` REST Endpoint Triggers Uncached Full Stake-Account Scan on Every Request, Enabling RPC Blocking-Thread-Pool Exhaustion - (rpc/src/rpc_service.rs)

### Summary
The `/v0/circulating-supply` HTTP REST endpoint, reachable without authentication via `RpcRequestMiddleware::on_request`, triggers a full, uncached, O(accounts) scan of all stake-program accounts on every single request via `calculate_non_circulating_supply`. There is no caching, deduplication, or rate limiting for this endpoint, unlike other expensive RPC calls (e.g., `getLargestAccounts` uses `LargestAccountsCache`).

### Finding Description
`on_request` dispatches any request whose path matches `/v0/circulating-supply` or `/v0/total-supply` to `process_rest`, which awaits `handle_rest`. For circulating supply, `handle_rest` calls `calculate_circulating_supply_async`, which offloads `calculate_non_circulating_supply(&bank)` to `spawn_blocking`. That function iterates all stake-program accounts (via `get_filtered_indexed_accounts` or fallback `get_program_accounts`), deserializes each into `StakeStateV2`, filters based on lockup/withdraw authority, and sums balances via `bank.get_balance` per account — with no caching of the result across calls. [8](#0-7) [9](#0-8) 

### Impact Explanation
Repeated unauthenticated requests to this single endpoint each incur a full stake-account scan, consuming a blocking-thread-pool slot for the scan duration. Because `rpc_blocking_threads` is a shared, size-limited pool (default `num_cpus/2`) also used by other CPU-bound RPC methods offloaded via `spawn_blocking`, sustained/repeated hits to this endpoint can starve that pool, degrading responsiveness of those other RPC calls. The primary async RPC event-loop threads (`rpc_threads`) that service the bulk of standard JSON-RPC requests are architecturally isolated from this specific scan and are not directly starved.

### Likelihood Explanation
High likelihood of triggering the underlying behavior: no authentication, no rate limiting, and no caching gate the endpoint, so the scan runs unconditionally on every call — this matches "single-client low-rate RPC crash/degradation" criteria. The severity of the resulting degradation depends on mainnet stake-account count, `rpc_blocking_threads` configuration, and concurrent usage of the blocking pool by other RPC methods.

### Recommendation
Add a time-based cache (analogous to `LargestAccountsCache`) for the `/v0/circulating-supply` and `/v0/total-supply` computation, and/or apply per-IP rate limiting to unauthenticated REST endpoints in `RpcRequestMiddleware`.

### Proof of Concept
Send repeated `GET /v0/circulating-supply` requests against a validator/test node with a large number of stake accounts and measure blocking-thread-pool saturation and latency of other blocking-pool-dependent RPC calls (e.g., `getMultipleAccounts`) under load, using the code paths cited above (`rpc/src/rpc_service.rs:394-451`, `runtime/src/non_circulating_supply.rs:19-79`).

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {

    let bank = Arc::clone(bank);
    let non_circulating_supply =

            .expect("Failed to spawn blocking task")

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))

pub fn service_runtime(
    rpc_threads: usize,
    rpc_blocking_threads: usize,
    rpc_niceness_adj: i8,
) -> Arc<TokioRuntime> {
    // The jsonrpc_http_server crate supports two execution models:
    //
    // - By default, it spawns a number of threads - configured with .threads(N) - and runs a
    //   single-threaded futures executor in each thread.
    // - Alternatively when configured with .event_loop_executor(executor) and .threads(1),
    //   it executes all the tasks on the given executor, not spawning any extra internal threads.
    //
    // We use the latter configuration, using a multi threaded tokio runtime as the executor. We
    // do this so we can configure the number of worker threads, the number of blocking threads
    // and then use tokio::task::spawn_blocking() to avoid blocking the worker threads on CPU
    // bound operations like getMultipleAccounts. This results in reduced latency, since fast
    // rpc calls (the majority) are not blocked by slow CPU bound ones.
    //
    // NB: `rpc_blocking_threads` shouldn't be set too high (defaults to num_cpus / 2). Too many
    // (busy) blocking threads could compete with CPU time with other validator threads and
    // negatively impact performance.
    let rpc_threads = 1.max(rpc_threads);
    let rpc_blocking_threads = 1.max(rpc_blocking_threads);
    Arc::new(
        TokioBuilder::new_multi_thread()
            .worker_threads(rpc_threads)
            .max_blocking_threads(rpc_blocking_threads)
            .on_thread_start(move || renice_this_thread(rpc_niceness_adj).unwrap())
            .thread_name("solRpcEl")
            .enable_all()
            .build()
            .expect("Runtime"),
    )

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}
