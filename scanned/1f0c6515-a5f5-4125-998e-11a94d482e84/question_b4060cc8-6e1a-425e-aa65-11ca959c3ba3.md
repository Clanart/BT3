Target: absence of rate/identity binding between `Withdraw` calls and the Citrea `withdraw` event they're supposed to represent (core/src/rpc/aggregator.rs `AggregatorServer::withdraw`, `Operator::withdraw`). Attacker action: unauthenticated caller submits `Withdraw` with `input_signature` being a *valid* Schnorr signature over a withdrawal UTXO the attacker controls (since they can construct any withdrawal UTXO+signature per the threat model), `output_script_pubkey` set to their own address, and `output_amount` inflated beyond what any real Citrea withdrawal recorded, betting that `Operator::withdraw`'s validation of the amount against the Citrea Bridge contract is the only remaining check. Preconditions: `client_verification=false` on the aggregator; a genuine Citrea withdrawal exists for a *smaller* amount that the attacker copies the outpoint/signature pattern from. Call sequence: aggregator forwards the raw params unauthenticated to operator(s), which must independently query Citrea for the recorded (amount, script) pair keyed by `withdrawal_id`. Binding: the amount owed per the Bridge contract's withdrawal record == the amount the operator is asked to front; if the aggregator's own request forwarding path has no sanity check and simply proxies attacker bytes, the burden falls entirely on `Operator::withdraw`'s Citrea lookup, which this attack targets to detect any acceptance gap. Impact: Critical — an operator reimbursed for a payout amount exceeding what it never actually needed to front. Proof idea: cargo test with `MockCitreaClient` returning a fixed withdrawal amount, unauthenticated `withdraw` call requesting a larger `output_amount` for the same `withdrawal_id`, asserting the operator rejects the mismatch rather than fronting it.
