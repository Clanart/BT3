**Rationale:** `receive_txn_thread` in `send-transaction-service/src/send_transaction_service.rs` contains no fee-payer lock/unlock logic whatsoever. This thread only receives serialized `TransactionInfo` (with `wire_transaction` bytes, `signature`, `blockhash`, `last_valid_block_height`) from an RPC client, deduplicates by signature against an in-memory `HashMap` and the `retry_transactions` pool, and forwards the batch via `tpu_sender.send_transactions_in_batch` [1](#0-0) . It never touches `AccountLocks`, `Accounts::lock_accounts`/`unlock_accounts`, or `TransactionBatch` — it just relays wire bytes to the TPU and later checks `root_bank.get_committed_transaction_status_and_slot` to decide whether to retry, expire, or drop a transaction [2](#0-1) .

Fee-payer lock/unlock (the actual invariant in question) is implemented entirely elsewhere, downstream in the runtime:
- `Bank::try_lock_accounts_with_results` / `prepare_sanitized_batch_with_results`, which delegate to `Accounts::lock_accounts` and dedupe by message hash within a batch [3](#0-2) .
- `TransactionBatch`'s `Drop` impl and `unlock_failures`, which guarantee accounts are unlocked exactly once, either on batch drop or on explicit failure handling, with an assertion that forbids flipping a previously-recorded lock error back to `Ok` [4](#0-3) .
- `consumer::check_fee_payer_unlocked`, which validates the fee payer's balance against the computed fee before allowing execution/commit [5](#0-4) .

Since `receive_txn_thread` never acquires, holds, or releases any account/fee-payer lock, there is no "lock lifetime" for an attacker to desynchronize by manipulating retries, blockhash freshness, or duplicate-signature timing at this entrypoint — the described lock/unlock split does not exist in this code path. The actual lock lifecycle is scoped per-batch inside the bank/runtime layer and is bounded by RAII (`Drop`) plus the assertion in `unlock_failures`, which already prevents the "unlock at the wrong moment" scenario the question hypothesizes.

    /// For every error result, if the corresponding transaction is
    /// still locked, unlock the transaction and then record the new error.
    pub fn unlock_failures(&mut self, transaction_results: Vec<Result<()>>) {
        assert_eq!(self.lock_results.len(), transaction_results.len());
        // Shouldn't happen but if a batch was marked as not needing an unlock,
        // don't unlock failures.
        if !self.needs_unlock() {
            return;
        }

        let txs_and_results = transaction_results
            .iter()
            .enumerate()
            .inspect(|(index, result)| {
                // It's not valid to update a previously recorded lock error to
                // become an "ok" result because this could lead to serious
                // account lock violations where accounts are later unlocked
                // when they were not currently locked.
                assert!(!(result.is_ok() && self.lock_results[*index].is_err()))
            })
            .filter(|(index, result)| result.is_err() && self.lock_results[*index].is_ok())
            .map(|(index, _)| (&self.sanitized_txs[index], &self.lock_results[index]));

        // Unlock the accounts for all transactions which will be updated to an
        // lock error below.
        self.bank.unlock_accounts(txs_and_results);

        // Record all new errors by overwriting lock results. Note that it's
        // not valid to update from err -> ok and the assertion above enforces
        // that validity constraint.
        self.lock_results = transaction_results;
    }
}
