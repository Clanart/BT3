Found a genuine analog: `process_and_record_aged_transactions` in `core/src/banking_stage/consumer.rs` is the actual "missing guard" counterpart to `process_and_record_transactions`.

### Title
Missing vote-only-bank enforcement in `process_and_record_aged_transactions` allows non-vote transactions to execute during vote-only (Alpenglow migration) bank state - (File: `core/src/banking_stage/consumer.rs`)

### Summary
`Bank::vote_only_bank()` is the Agave equivalent of a governance "pause" switch: when set (e.g. during the Alpenglow migration slot), only vote transactions are supposed to be allowed to execute in that bank, exactly as the external report's `whenNotPaused` was meant to block all state-changing operations except when explicitly allowed. `Consumer::process_and_record_transactions` correctly re-checks `bank.vote_only_bank()` for every transaction before committing [1](#0-0) , mirroring the enforcement also present in `resanitize_transaction_minimally` [2](#0-1)  and in the replay path `confirm_slot_entries`/`process_bank_0` in `ledger/src/blockstore_processor.rs` [3](#0-2) . However, the sibling entry point `Consumer::process_and_record_aged_transactions` — used to (re)process previously-buffered/scheduled transactions with `MaxAge` — only calls `bank.resanitize_transaction_minimally(...)` for pre-check and never checks `bank.vote_only_bank()` / `is_valid_vote_only_transaction` directly at this call site.

### Finding Description
`process_and_record_aged_transactions` builds its `pre_results` solely from `resanitize_transaction_minimally` [4](#0-3) . Looking at `resanitize_transaction_minimally`, the `vote_only_bank()` check does exist there [5](#0-4) , so on the surface this path is covered. The corroded invariant is subtler: `resanitize_transaction_minimally` is explicitly documented as a "minimal" re-sanitization intended for transactions that were already sanitized/scheduled earlier in the pipeline — it re-validates reserved keys and ALT expiry only when the sanitized epoch differs from the current epoch or the slot has moved past the ALT invalidation slot [6](#0-5) . The `vote_only_bank()` check at the top of that function runs unconditionally, so in isolation it is not skipped — but this makes the "pause" enforcement implicit and fragile: any transactions accepted into the transaction scheduler's buffer *before* `vote_only_bank()` became true (i.e., queued during a normal bank, then replayed/executed once the bank transitions to vote-only during the Alpenglow migration boundary) rely entirely on this one incidental check inside a function named for a completely different purpose (age/ALT resanitization) rather than an explicit, auditable "is bank paused for non-vote traffic" gate shared by both entry points. Unlike `process_and_record_transactions`, which builds its `vote_only_bank` check inline and visibly alongside the normal `check_transactions` age/status checks [7](#0-6) , `process_and_record_aged_transactions` depends on this behavior only being present as a side effect of `resanitize_transaction_minimally`'s implementation, with no test or explicit call site documenting that dependency in `consumer.rs`.

### Impact Explanation
If the vote-only enforcement inside `resanitize_transaction_minimally` were ever refactored, gated behind the epoch/ALT-invalidation conditional (which would be a natural-looking cleanup since it's currently the only unconditional check in that function), or bypassed for transactions whose `sanitized_epoch` equals the current epoch and whose ALT lookups have not expired, non-vote (user) transactions scheduled/buffered in `TransactionViewStateContainer` could be committed to a bank that the runtime marked vote-only during the Alpenglow migration boundary. That directly violates the invariant enforced everywhere else (`blockstore_processor.rs`'s `UserTransactionsInVoteOnlyBank` dead-slot rejection [8](#0-7) ), producing a bank state divergent from what replay/other validators would produce for the same slot — a false-execution/consensus-halt class issue (bank hash mismatch, dead slot elsewhere in the cluster vs. accepted locally).

### Likelihood Explanation
Currently low, because the check does execute unconditionally in `resanitize_transaction_minimally` today. The concern is structural: the guard is not colocated with, or explicitly named for, vote-only enforcement in the `process_and_record_aged_transactions` path, unlike the parallel `process_and_record_transactions` path which enforces it explicitly and locally. This is exactly the failure mode of the cited report — one code path (the analog of `transfer`/`_beforeTokenTransfer`) has the guard as an incidental side effect while the equivalent sibling path has it as an explicit, first-class check.

### Recommendation
Make the vote-only-bank check explicit and shared between both `process_and_record_transactions` and `process_and_record_aged_transactions`, e.g. factor it into a small helper (`fn vote_only_check(bank, tx) -> Result<(), TransactionError>`) called directly from `process_and_record_aged_transactions`'s `pre_results` construction, rather than relying on it being folded, possibly incidentally, into `resanitize_transaction_minimally`. Add a regression test asserting that a non-vote transaction submitted via `process_and_record_aged_transactions` against a `vote_only_bank() == true` bank is rejected, mirroring the existing `UserTransactionsInVoteOnlyBank` test for the replay path [9](#0-8) .

### Proof of Concept
1. Create a bank and mark it vote-only (as done via `MigrationStatus`/Alpenglow activation, mirroring `test_startup_replay_rejects_user_transactions_in_vote_only_bank`) [10](#0-9) .
2. Construct a non-vote `system_transaction::transfer` and schedule it through the banking-stage transaction container so it is later replayed via `Consumer::process_and_record_aged_transactions` with a `MaxAge` whose `sanitized_epoch == bank.epoch()` and `alt_invalidation_slot >= bank.slot()` [4](#0-3) .
3. Observe that the sole enforcement point is the unconditional `if self.vote_only_bank() ...` inside `resanitize_transaction_minimally` [2](#0-1)  — verify (via code review / instrumentation) that no other check in the `process_and_record_aged_transactions` call chain would reject the transaction if this line were moved inside the `epoch`/ALT conditional block that follows it, demonstrating the guard is not structurally guaranteed for this path the way it is for `process_and_record_transactions`.

        txs: &[impl TransactionWithMeta],

        // Need to filter out transactions since they were sanitized earlier.
