## Title
Deterministic seeded-address pre-funding permanently blocks `CreateAccount`/`CreateAccountWithSeed`, enabling cheap unprivileged DoS on stake/nonce account creation - (File: `programs/system/src/system_processor.rs`)

### Summary
The reported bonding-curve bug (pre-funding a deterministic escrow PDA to break an "expected zero balance" invariant and block account initialization) has a direct analog in Agave's own System built-in program. `create_account()` unconditionally rejects account creation whenever the target address already holds any lamports, and target addresses for `CreateAccountWithSeed` are fully deterministic and publicly computable (`base`, `seed`, `owner`). Any unprivileged actor can pre-fund such an address with 1 lamport before the legitimate creator's transaction lands, permanently causing `SystemError::AccountAlreadyInUse` for that specific address — exactly the same "assume balance starts at 0" invariant violation as the bonding-curve report.

### Finding Description
`create_account()` in the System program checks: [1](#0-0) 
```
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ...
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
```
This is the exact analog of the bonding-curve invariant check that fails when `sol_escrow` holds unexpected SOL: here, `CreateAccount`/`CreateAccountWithSeed` fails outright the moment the target has `lamports > 0`, regardless of why those lamports are there.

The target address for `CreateAccountWithSeed` is fully deterministic and computable by anyone from public inputs (`base` pubkey, `seed` string, `owner` program id) via `Pubkey::create_with_seed`, confirmed by the address-derivation helper in `Address::create`: [2](#0-1) 

This pattern is used pervasively for real funds-holding accounts, e.g. stake accounts: [3](#0-2) 
and nonce accounts: [4](#0-3) 
and bulk/sequential derivations (`base`, index `"0","1","2",...`) used by staking-pool tooling: [5](#0-4) 

An unprivileged attacker who knows (or brute-forces/observes) the `base` pubkey and an intended `seed` — e.g., by monitoring a staking-pool operator's known base key and predictable/sequential seed scheme — can send a plain, permissionless `Transfer` of 1 lamport to the derived address *before* the legitimate `CreateAccountWithSeed`/`CreateAccount` transaction executes. The subsequent legitimate creation transaction then unconditionally fails with `AccountAlreadyInUse`, blocking that specific stake/nonce/vote account from ever being created at that address.

Agave's own maintainers have implicitly acknowledged this exact bug class: a new, feature-gated instruction `CreateAccountAllowPrefund` was added specifically to tolerate pre-funded accounts: [6](#0-5) [7](#0-6) 
However, this is opt-in and gated behind `invoke_context.get_feature_set().create_account_allow_prefund`; all existing callers of the legacy `CreateAccount`/`CreateAccountWithSeed` path — including the CLI's stake and nonce account creation (`cli/src/stake.rs`, `cli/src/nonce.rs`), the `stake-accounts` bulk tooling, and `accounts-cluster-bench` — remain fully exposed to the pre-funding DoS since none of them have migrated to the new instruction.

### Impact Explanation
This is an unprivileged, cheap (1-lamport) built-in-program DoS: any actor can permanently block the creation of a specific stake, nonce, or vote account at a deterministic address, without needing the target's signature or any special privilege. For validators/staking-pool operators that programmatically derive many seeded addresses (`stake_accounts.rs`), an attacker who anticipates the seed scheme can systematically block bulk account creation, degrading network operations (stake account provisioning, nonce account setup for durable-nonce transaction flows, etc.) at negligible cost.

### Likelihood Explanation
Likelihood is limited to scenarios where an attacker can predict or observe `base`+`seed` before the legitimate creation transaction lands (e.g., sequential/incrementing seeds, publicly known operator base keys, or transaction-simulation/mempool observation). This mirrors the original report's "Medium" likelihood rating — the address is deterministic but requires knowledge of the specific base/seed pair to target ahead of time.

### Recommendation
Migrate all legacy `system_instruction::create_account`/`create_account_with_seed` call sites that build funds-holding accounts at deterministic addresses (stake, nonce, and any seeded PDAs) to the new `CreateAccountAllowPrefund` instruction once the `create_account_allow_prefund` feature is active, so pre-existing lamports are absorbed instead of causing `AccountAlreadyInUse`. Until then, document/mitigate the race for CLI and tooling flows (`cli/src/stake.rs`, `cli/src/nonce.rs`, `stake-accounts/src/stake_accounts.rs`) that rely on predictable seeds.

### Proof of Concept
1. Attacker observes a known `base` pubkey used by a staking-pool operator (e.g., from `stake_accounts.rs`'s sequential seed scheme `"0", "1", "2", ...`).
2. Attacker computes `stake_address = Pubkey::create_with_seed(&base, "5", &stake::program::id())` (same derivation used in `cli/src/stake.rs:1394-1398`).
3. Attacker submits a plain `SystemInstruction::Transfer` of 1 lamport to `stake_address` before the operator's `CreateAccountWithSeed` transaction lands.
4. When the operator's transaction executes `create_account()` in `system_processor.rs`, the check `if to.get_lamports() > 0` at line 164 triggers, returning `SystemError::AccountAlreadyInUse`, and the stake account can never be created at that address.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
