Based on my investigation, I found a concrete Agave analog to this pause-bypass bug class in `Bank`'s freeze-guard mechanism.

### Title
Bank state-mutation occurs before the `freeze_started` guard check in `add_precompiled_account_with_owner`/`add_builtin_account` - (File: `runtime/src/bank.rs`)

### Summary
Agave's `Bank::freeze()` is the analog of the report's `globalPause`: once `freeze_started` is set to `true`, the codebase's convention is that no further state mutation should occur, and most account-mutating entry points (`store_accounts_without_stakes_cache`, `register_tick`, `commit_transactions`) explicitly `assert!(!self.freeze_started())` at their very top before doing any work. However, two functions place a state-mutating call *before* that guard check instead of at the beginning, echoing the exact bug-class described in the report (state-changing functions unguarded, or guarded too late, by the pause flag).

### Finding Description
`add_precompiled_account_with_owner` and `add_builtin_account` both first look up whether an account already exists at a well-known program address. If it exists but is not `executable` (i.e., a "malicious"/pre-occupying account), they immediately call `self.burn_and_purge_account(program_id, account)` — which mutates `capitalization` and stores a zeroed account — and only *afterwards* execute the `assert!(!self.freeze_started(), "Can't change frozen bank ...")` guard: [1](#0-0) [2](#0-1) 

The intended invariant, visible throughout the rest of `bank.rs`, is that `freeze_started` must be checked at the very top of any function that can mutate bank state, exactly as done in `store_accounts_without_stakes_cache`, `register_tick`, and `commit_transactions`: [3](#0-2) [4](#0-3) [5](#0-4) 

But `add_precompiled_account_with_owner`/`add_builtin_account` violate that convention: `burn_and_purge_account` (which internally calls `self.store_account`, adjusting `capitalization` and account data) executes on the "malicious account occupying program_id" branch *before* the frozen-bank assertion is reached. `burn_and_purge_account` itself performs `capitalization.fetch_sub` directly and only then calls `store_account`, whose inner path re-checks `freeze_started` — so the capitalization decrement is not gated by any freeze check at all, and only the subsequent `store_account` call would panic on a frozen bank: [6](#0-5) 

This means, on a frozen bank, `Bank::capitalization` (a value that must be consistent for the bank hash / total-stake invariants) can be decremented by `burn_and_purge_account` via `capitalization.fetch_sub` before the subsequent `store_account` panics — i.e., a partial, uncontrolled state mutation happens ahead of the guard that is supposed to prevent any change to a frozen bank, analogous to the reported "unguarded public/external function that can affect contract state in paused scenarios."

### Impact Explanation
If reached on a frozen (post-freeze) bank, this ordering means `capitalization` is decremented outside of any `freeze_started` gate, corrupting a bank-global accounting value that bank-hash computation and supply invariants rely on, before the program panics inside `store_account`. Since this is a `debug_assert!`-free `assert!()` panic path, in production this would still crash the validator (denial of service) rather than silently succeed, but the capitalization corruption happens *before* the panic unwinds, which is meaningful if any caller catches panics or if the mutation is partially persisted via account cache prior to the abort.

### Likelihood Explanation
This requires reaching `add_precompiled_account_with_owner`/`add_builtin_account` with a pre-frozen bank and a pre-existing non-executable account already squatting at the reserved program pubkey — a narrow internal condition typically only exercised during builtin/precompile feature activation and genesis/snapshot-restore consistency checks (`apply_new_builtin_program_feature_transitions`, `add_active_builtin_programs`/`add_builtin_program_accounts`), which are called from `Bank::new_from_parent`/feature activation logic before freeze, not from arbitrary transaction execution. I could not confirm from local code whether any code path calls these functions *after* `freeze()` on the same bank instance in normal validator operation; the existing test `test_add_precompiled_account_after_frozen` only exercises the case where the account does not already exist (so `burn_and_purge_account` is not invoked), meaning this particular capitalization-before-panic ordering is untested. [7](#0-6) 

### Recommendation
Move the `assert!(!self.freeze_started(), ...)` check to the very top of `add_precompiled_account_with_owner` and `add_builtin_account`, before any lookup or mutation (including the `burn_and_purge_account` branch), matching the pattern already used in `store_accounts_without_stakes_cache`/`register_tick`/`commit_transactions`. More generally, audit all `Bank` methods that can mutate `capitalization`, accounts, or other bank-global state to ensure the `freeze_started` guard is the first statement executed, not one reached conditionally after other mutating branches.

### Proof of Concept
1. Construct a `Bank`, and before genesis/builtin-registration completes normally, pre-store a non-executable account at a reserved builtin/precompile pubkey (simulating account-squatting).
2. Call `bank.freeze()`.
3. Call `bank.add_builtin_account(name, &program_id)` (or `add_precompiled_account`) for that pubkey.
4. Observe that `existing_genuine_program` lookup finds the non-native-loader-owned account, triggers `burn_and_purge_account`, which executes `capitalization.fetch_sub` (state mutation on a frozen bank) prior to the `assert!(!self.freeze_started())` panic that occurs only in the subsequent `store_account` call inside `burn_and_purge_account` itself.

Note: I was only able to trace this within the currently indexed portions of `runtime/src/bank.rs`; a full audit of every caller of `add_builtin_account`/`add_precompiled_account_with_owner` and their reachability post-`freeze()` in production replay/leader flows was not possible from the index alone. A Devin session with full repository access would be needed to exhaustively confirm reachability from an unprivileged, non-leader-controlled path.

    /// Add a builtin program account
    fn add_builtin_account(&self, name: &str, program_id: &Pubkey) {
        let existing_genuine_program =
            self.get_account_with_fixed_root(program_id)
                .and_then(|account| {
                    // it's very unlikely to be squatted at program_id as non-system account because of burden to
                    // find victim's pubkey/hash. So, when account.owner is indeed native_loader's, it's
                    // safe to assume it's a genuine program.
                    if native_loader::check_id(account.owner()) {
                        Some(account)
                    } else {
                        // malicious account is pre-occupying at program_id
                        self.burn_and_purge_account(program_id, account);
                        None
                    }
                });

        // introducing builtin program
        if existing_genuine_program.is_some() {
            // The existing account is sufficient
            return;
        }

        assert!(
            !self.freeze_started(),
            "Can't change frozen bank by adding not-existing new builtin program ({name}, \
             {program_id}). Maybe, inconsistent program activation is detected on snapshot \
             restore?"
        );
