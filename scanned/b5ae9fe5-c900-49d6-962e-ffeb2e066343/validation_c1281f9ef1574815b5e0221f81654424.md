## Title
`getProgramAccounts` full-scan path has no byte-size limit when secondary indexes are disabled, allowing a single unstaked RPC caller to trigger unbounded memory/CPU consumption - ([File: rpc/src/rpc.rs])

## Summary
The external HAL-04 report is generic ("too many requests overload the API"). The strongest concrete Agave analog is not simply "no rate limiter" — Agave already implements extensive per-IP/connection/stream token-bucket throttling for QUIC/TPU (`streamer/src/nonblocking/quic.rs`, `connection_rate_limiter.rs`, `stream_throttle.rs`) and for repair (`serve_repair.rs` `data_budget`). The RPC HTTP surface, however, has no such throttling, and one specific handler explicitly skips its own size-bounding safeguard: the non-indexed path of `get_filtered_program_accounts`.

## Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` in `rpc/src/rpc.rs` has two code paths depending on whether the `ProgramId` secondary account index is enabled:

- If the `ProgramId` index is enabled, it calls `get_filtered_indexed_accounts`, which passes `byte_limit_for_scans` (from `JsonRpcConfig::scan_results_limit_bytes`) down into `Accounts::load_by_index_key_with_filter`, which aborts the scan once accumulated result size exceeds the configured byte limit (`accounts-db/src/accounts.rs` `accumulate_and_check_scan_result_size` / `maybe_abort_scan`).
- If the index is **not** enabled (the default/common configuration, since secondary indexes are opt-in and memory-expensive), the code takes the `else` branch:
```rust
// this path does not need to provide a mb limit because we only want to support secondary indexes
let mut accounts = self.runtime.spawn_blocking(move || {
    bank.get_filtered_program_accounts(&program_id, |account| { ... })
}).await...
```
This calls `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `AccountsDb::scan_accounts`, none of which take or enforce any byte/size limit — the collector `Vec<KeyedAccountSharedData>` grows unbounded, materializing every matching account (all accounts owned by the queried `program_id`) into memory before it is even serialized for the JSON-RPC response.

Because `getProgramAccounts` is reachable via the standard RPC HTTP interface by any unstaked/unprivileged client, a single low-rate request against a program with a very large number of accounts (e.g., a heavily used SPL program) forces the node to allocate and hold in memory the full set of matching accounts, then further clone/sort (`sort_unstable_by`) and JSON-encode them, all inside one JSON-RPC worker thread with no cap tied to available memory or configured limits. There is no equivalent of the token-bucket/data-budget mechanisms used elsewhere in the codebase (QUIC, repair) protecting this endpoint.

Existing guards do not stop this path:
- `verify_filters` / `MAX_GET_PROGRAM_ACCOUNT_FILTERS` (`rpc/src/rpc.rs`) bound the *number* of filters supplied, not the size of the result set.
- `scan_results_limit_bytes` only applies when a secondary index is configured and taken; it is bypassed entirely on the default/no-index path.
- The RPC server's `max_request_body_size` bounds the *incoming* request, not the outgoing response construction cost.

## Impact Explanation
A single unprivileged RPC client can force a validator/RPC node to perform an unbounded full-account-table scan and materialize an unbounded amount of data in memory in response to one request, without needing elevated stake, credentials, or a high request rate. On nodes serving public RPC without the ProgramId secondary index (the common case, since indexes add substantial memory/CPU overhead to every validator), this can degrade or crash the RPC service (OOM, prolonged scan blocking the JSON-RPC executor thread pool), directly matching the "single-client low-rate RPC crash/degradation" category called out as valid impact.

## Likelihood Explanation
High for a public/unstaked RPC target: `getProgramAccounts` is a documented, commonly used JSON-RPC method, requires only a valid `program_id` string, and the vulnerable code path is the *default* configuration (no secondary index configured). No malicious peer, validator, or leaked key assumptions are required — this is a plain unprivileged RPC caller.

## Recommendation
- Apply the same `scan_results_limit_bytes` (or an always-on default byte limit) to the non-indexed `get_filtered_program_accounts` path exactly as done for `get_filtered_indexed_accounts`, using `Accounts::accumulate_and_check_scan_result_size` / `ScanConfig::recreate_with_abort` inside `load_by_program_with_filter`.
- Consider enforcing this limit unconditionally at the RPC layer regardless of index configuration, and/or require at least one selective filter (e.g., `dataSize`, `memcmp`) for `getProgramAccounts` calls from unstaked/unauthenticated clients.
- Add RPC-level request-cost accounting/throttling analogous to the QUIC `ConnectionRateLimiter`/`TokenBucket` and repair `data_budget` mechanisms already present elsewhere in the codebase.

## Proof of Concept
1. Run a validator/RPC node with default `JsonRpcConfig` (no `account_indexes` configured, the default).
2. Identify or seed a widely-used program (e.g., SPL Token program) with a very large number of owned accounts on the target cluster/ledger.
3. Issue a single JSON-RPC request:
```json
{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["<program_id_with_many_accounts>"]}
```
4. Observe that `get_filtered_program_accounts` (`rpc/src/rpc.rs`) takes the non-indexed branch, calling `Bank::get_filtered_program_accounts` → `AccountsDb::scan_accounts` with no byte limit, causing the RPC worker to allocate and hold the entire result set (potentially hundreds of MB to GB depending on account count/size) before responding — degrading or crashing the node with a single low-rate request, unlike the indexed path which is protected by `scan_results_limit_bytes`.     pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }

    pub fn load_by_program_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        program_id: &Pubkey,
        filter: F,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let mut collector = Vec::new();
        self.accounts_db
            .scan_accounts(
                ancestors,
                bank_id,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        account.owner() == program_id && filter(account)
                    })
                },
                &ScanConfig::default(),
            )
            .map(|_| collector)
    }

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
