## Title
Alpenglow block-reward recalculation double-counts already-distributed stake, letting the numerator exceed the fixed pending-reward denominator and over-paying delegators from a fixed pool — (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Lido report's root cause is that a value denominated against a *changing* exchange rate (`totalProtocolFee`, tracked flat instead of in shares) is combined with values computed against the *current* rate, so the numerator/denominator pair used to split a fixed pool of "earnings" become inconsistent once some withdrawals have already happened, letting late/early withdrawers overdraw the pool. The closest Agave analog is Alpenglow's per-block delegator revenue-sharing calculation, `calculate_block_reward`, which splits a fixed pool (`pending_delegator_rewards`) between stake accounts using `stake / total_active_stake` as the split ratio. `total_active_stake` is a stale, epoch-boundary snapshot (`RewardEpochDelegatedStakes`), while `stake` (the numerator) is recomputed from the *live* stake account's `Delegation.stake`, which is itself mutated in-place as rewards are distributed (`stake.delegation.stake += staker_rewards` in `redeem_stake_rewards`, `runtime/src/inflation_rewards/mod.rs:166`). When reward computation is redone for a subset of accounts after partial distribution (which happens on every fork switch / bank recreation while `EpochRewards` is `active`), the numerator for already-rewarded accounts is inflated relative to the fixed, stale denominator — exactly the "unscaled fee vs. current exchange rate" defect from the Lido report, just expressed as "unscaled effective-stake numerator vs. stale total-stake denominator."

### Finding Description
`calculate_block_reward` implements SIMD-0123 block-revenue sharing: [1](#0-0) 

- `total_active_stake` comes from `reward_epoch_delegated_stakes.delegated_stakes`, a value snapshotted once at the reward epoch boundary and reused unchanged for every recalculation, as documented at [2](#0-1) 
- `stake` is `delegation_effective_stake(delegation, rewarded_epoch, ...)`, computed from the stake account's *live* `Delegation`. But `Delegation.stake` is mutated to include already-paid inflation rewards as soon as a partition is distributed (`stake.delegation.stake += staker_rewards`), see [3](#0-2) 
and persisted to the stake account by `build_updated_stake_reward` during `store_stake_accounts_in_partition`: [4](#0-3) 

The code itself documents the resulting inconsistency and only partially mitigates it: [5](#0-4) 
The mitigation clamps a *single* entry's block reward to `min(pending_delegator_rewards)`, but `pending_delegator_rewards` is read once per recalculation call from the vote account and is not decremented as each delegator's share is computed within the same pass — so across the *many* delegators recomputed together in `calculate_stake_rewards_and_commissions` (a `par_iter` over `stake_delegations`, see `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:815-849`), every already-rewarded delegator's inflated numerator is divided by the same stale `total_active_stake`. The sum of `pending_delegator_rewards * stake_i / total_active_stake` over all `i` is no longer bounded by `pending_delegator_rewards` once one or more `stake_i` have been inflated by already-distributed rewards while `total_active_stake` was never correspondingly reduced. This mirrors the Lido bug precisely: a "protocol fee"/"already-withdrawn" adjustment is applied to the numerator side (implicitly, by leaving `delegation.stake` bumped) without correspondingly adjusting the denominator that other unpaid parties still divide by.

This is a real, reachable path: `recalculate_stake_rewards` → `calculate_stake_rewards_and_commissions` → `calculate_block_reward` runs on **every** bank creation while `EpochRewardStatus` is active (`recalculate_partitioned_rewards_if_active`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1015-1032`), which happens naturally whenever a fork switch/reorg occurs mid-epoch-boundary reward distribution — an entirely normal, non-malicious operational event, not requiring any privileged actor.

### Impact Explanation
Overpaying block-revenue rewards from a fixed pool (`pending_delegator_rewards`, ultimately debited via `update_epoch_rewards_sysvar`'s `debit_block_reward_lamports`, `runtime/src/bank/partitioned_epoch_rewards/sysvar.rs:74-109`) either:
1. silently mints more lamports than the pool actually held, corrupting `capitalization` bookkeping and under/over-crediting stakers relative to their real entitlement (fund-accounting corruption / false execution of reward distribution), or
2. trips the `checked_sub_lamports`/rent-exemption `assert!` in `update_epoch_rewards_sysvar` ("programmer error if we debit too many block rewards"), which is a `panic!` inside bank/reward processing — since this path executes deterministically on every validator that experiences the same fork-switch sequence, a triggering sequence would crash all nodes that replay it, which is a non-RPC crash/consensus-halt class impact rather than a benign local issue.

### Likelihood Explanation
Requires: (a) Alpenglow block-revenue sharing active (`block_revenue_sharing` feature), (b) a fork switch/bank recreation occurring after at least one reward partition has already been distributed within the same active `EpochRewards` window, and (c) multiple delegators to the same vote account among the affected/recomputed set. Fork switches at epoch boundaries are routine validator behavior (not attacker-controlled), so no malicious peer/privileged access is needed, but the specific "denominator staleness after partial distribution" trigger condition is narrow and the authors have already added a partial defense (`.min(pending_delegator_rewards)`) plus a regression test asserting the AG-points path preserves "the original denominator" — indicating this exact bug class has been recognized but the block-reward numerator/denominator mismatch documented in the code comment is only partially, not fully, addressed.

### Recommendation
Track cumulative block-reward lamports already paid out of `pending_delegator_rewards` for the in-progress epoch (e.g., persist a running `distributed_delegator_rewards` alongside `RewardEpochDelegatedStakes`) and clamp the *aggregate* sum of recomputed block rewards to the remaining undistributed pool, rather than clamping each entry independently against the full original pool. Alternatively, recompute `stake` for the block-reward numerator using the stake amount as of the reward epoch (excluding any inflation reward already merged into `Delegation.stake`), so the numerator and `total_active_stake` denominator stay on a consistent basis, analogous to tracking `totalProtocolFee` in shares rather than flat ETH in the original report.

### Proof of Concept
1. Enable `block_revenue_sharing`; create a vote account V with `pending_delegator_rewards = R` and total active delegated stake `T` split across delegators A and B (`stake_A + stake_B = T`).
2. Reach the epoch boundary; `calculate_rewards_for_partitioning` snapshots `RewardEpochDelegatedStakes` with `total_active_stake = T` and computes `block_reward_A = R * stake_A / T`, `block_reward_B = R * stake_B / T`.
3. Distribute partition 1 containing A's reward first: `store_stake_accounts_in_partition` → `build_updated_stake_reward` adds `inflation.stake_reward` to A's `Delegation.stake`, so A's on-chain `Delegation.stake` becomes `stake_A' = stake_A + inflation_reward_A`.
4. Before partition 2 (B's reward) is distributed, force a bank recreation on an alternate fork containing the same partially-completed `EpochRewards` state (a normal reorg), triggering `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` → `calculate_stake_rewards_and_commissions` → `calculate_block_reward` for the still-pending delegators.
5. For A, if A were recomputed again, `calculate_block_reward` reads `delegation_effective_stake` off the now-inflated `Delegation.stake = stake_A'`, producing `block_reward_A' = R * stake_A' / T > block_reward_A`, while B's `total_active_stake = T` (unchanged, still includes A's *pre-reward* stake in the denominator). Summing recomputed rewards for all still-pending delegators against the stale `T` can exceed the remaining `R - already_distributed`, which either double-mints lamports (unaccounted capitalization growth) or trips the `debit_block_reward_lamports` assertion panic in `runtime/src/bank/partitioned_epoch_rewards/sysvar.rs:98-105`.
