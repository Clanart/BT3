### Title
`BlockIdRepairType::FecSetRoot` Merkle-Proof Verification Accepts Padding-Ambiguous Leaf Index Without Length/Binding Checks - ([File: core/src/repair/serve_repair.rs])

### Summary
`BlockIdRepairType::verify_response` in `core/src/repair/serve_repair.rs` validates two kinds of double-Merkle repair responses against a `merkle_tree::verify_merkle_proof` call. For the `ParentAndFecSetCount` variant, the code computes an exact expected `proof_size` from `fec_set_count` and enforces `parent_proof.len()` equals it exactly, and (per an existing regression test) binds `fec_set_count` into the leaf hash to defeat a padding-collision replay across the last two leaf indices of an odd-sized tree. [1](#0-0)  The `FecSetRoot` variant, however, only checks that `fec_set_proof` is non-empty and passes the raw, unbound `fec_set_root` hash directly as the leaf into `verify_merkle_proof`, with no equivalent length bound tied to the true number of leaves and no binding of `fec_set_index` into the leaf value. [2](#0-1) 

### Finding Description
`merkle_tree::MerkleTree::try_new_with_len` builds each tree level by pairing nodes two at a time and, when a level has an odd number of nodes, duplicates the last node against itself to compute its parent: `let other = &nodes[(index + 1).min(offset + size - 1)];`. [3](#0-2)  This self-duplication makes the last real leaf index `L` and the (non-existent) index `L+1` produce mathematically identical proof-folding behavior, since `get_merkle_root`'s fold only tracks parity of `index` and, for `index == 0`, keeps folding forever without any check that the number of proof entries actually matches the tree depth: `(index == 0).then_some(root).ok_or(...)` is evaluated only after consuming the *entire* supplied `proof` slice, and the loop never validates that `proof.len()` corresponds to the real depth for the claimed index. [4](#0-3) 

The existing unit test `test_verify_fec_set_count_non_malleable` demonstrates exactly this ambiguity for the `ParentAndFecSetCount` path: a genuine proof for the real (last) leaf at index `fec_set_count` also verifies when the attacker claims `fec_set_count + 1`, because the padded tree places the leaf at both position N and N+1 due to self-duplication. [5](#0-4)  That path was hardened by mixing `fec_set_count` into the leaf hash (`hashv(&[parent_slot, parent_block_id, fec_set_count])`) so a mismatched claimed count produces a different, non-matching leaf, and by an explicit `parent_proof.len()` equality check against the exact expected `proof_size`. [6](#0-5) 

The `FecSetRoot` branch has neither mitigation: `fec_set_proof` is only checked for `is_empty()`, not bound to an expected exact length derived from the true number of leaves in the block's double-Merkle tree, and the leaf fed into the proof (`*fec_set_root`) carries no binding to `fec_set_index` at all. [7](#0-6)  Because the verifier for this request type never learns the true total leaf count (`fec_set_count` is not part of the `FecSetRoot` request or response), it cannot even construct the length check that the sibling `ParentAndFecSetCount` path uses. This reproduces, on an unpatched code path in the same file, the exact "WithdrawTrieVerifier" bug class from the external report: proof length/leaf identity is not bound, so a proof legitimately generated for one leaf position can be replayed to make the verifier accept a `fec_set_root` value for a different, attacker-chosen `fec_set_index` whenever the tree's last level has an odd node count (any time `fec_set_count` is even, since total leaves = `fec_set_count + 1`).

### Impact Explanation
A `fec_set_root` accepted by `verify_response` is trusted by the requesting validator as the authoritative Merkle root for that FEC set, feeding into shred acceptance/verification for repair (`ShredForBlockId` uses a `fec_set_merkle_root` to validate individual repaired shreds). [8](#0-7)  If an arbitrary, unprivileged repair responder can cause the wrong `fec_set_root` to validate for a requested `fec_set_index` (by replaying a genuine proof/root pair from the padding-collision boundary), the requester can be made to accept metadata for the wrong FEC set, corrupting which shred root is trusted for that repair flow. This falls in the "false execution/acceptance" impact category for an unprivileged, remote (any repair-serving peer) actor, matching the scan's valid-impact criteria for blockstore/repair paths.

### Likelihood Explanation
Exploitation only requires being able to answer a repair request over the network (the standard, always-untrusted repair-response threat model, not a staked/privileged validator) and requires no leaked keys or trusted-plugin assumptions. It is conditioned on `fec_set_count` being even for the target block (so total leaves is odd, triggering self-duplication at the boundary) — a condition attacker-observable from public block structure, not something they need to force. Given the responsible team already identified and partially fixed this exact ambiguity class for the sibling `ParentAndFecSetCount` variant (per the regression test), the underlying primitive is proven exploitable in this codebase; only the analogous fix was not applied to `FecSetRoot`.

### Recommendation
Bind `fec_set_index` (and ideally the true leaf count / `fec_set_count`) into the `fec_set_root` leaf hash before calling `verify_merkle_proof`, analogous to how `parent_info_leaf` binds `fec_set_count`. Additionally, enforce an exact expected `fec_set_proof.len()` (derived from `merkle_tree::get_proof_size` using the known/validated total leaf count) rather than merely checking non-emptiness, mirroring the `ParentAndFecSetCount` branch's length check.

### Proof of Concept
1. Construct a block whose double-Merkle tree has an even `fec_set_count` (odd total leaves), so the last FEC-set-root leaf at index `fec_set_count - 1` is self-duplicated when computing its parent — reachable via `MerkleTree::try_new_with_len`'s odd-size duplication logic. [9](#0-8) 
2. As an arbitrary (unprivileged) repair responder, capture the genuine `(fec_set_root, fec_set_proof)` for real leaf index `fec_set_count - 1`.
3. When a validator sends `BlockIdRepairType::FecSetRoot { slot, block_id, fec_set_index }` where `fec_set_index / DATA_SHREDS_PER_FEC_BLOCK` maps to the padding-duplicate boundary index, reply with the captured `(fec_set_root, fec_set_proof)` unmodified.
4. `verify_response` calls `merkle_tree::verify_merkle_proof(*fec_set_root, leaf_index, fec_set_proof, *block_id)`, which succeeds because the fold's `index == 0` end-check does not distinguish between the two colliding indices, exactly as reproduced by the existing `test_verify_fec_set_count_non_malleable` test for the sibling code path. [10](#0-9)

        let fec_set_count: u32 = 2; // even => total leaves = 3, last leaf duplicated

            parent_block_id.as_ref(),

        let mut leaves: Vec<Hash> = fec_set_roots;
        leaves.push(real_parent_leaf);
        let tree =
            merkle_tree::MerkleTree::try_new_with_len(leaves.iter().copied().map(Ok), leaves.len())
                .unwrap();
        let block_id = *tree.root();
        let real_parent_proof: Vec<u8> = tree
            .make_merkle_proof(fec_set_count as usize, leaves.len())
            .flat_map(|entry| entry.unwrap().iter().copied())
            .collect();

        let request = BlockIdRepairType::ParentAndFecSetCount {
            slot: 100,
            block_id,
        };

        // honest response verifies
        assert!(
            request.verify_response(&BlockIdRepairResponse::ParentFecSetCount {
                fec_set_count,
                parent_info: (parent_slot, parent_block_id),

pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}

/// Given a flattened merkle `proof` for `node` at `index`,
/// verify the proof against merkle root `root`
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}
