## Analog Found: Permanent lock-out of vote-account closure via unprivileged `pending_delegator_rewards` griefing

### Title
Unprivileged `DepositDelegatorRewards` griefing can permanently block vote-account closure due to an exact-zero `pending_delegator_rewards` gate — ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The external report's bug class is an exact-equality (`== 0`) requirement on a residual balance that gates removal/closure, combined with a distribution mechanism that can leave small, uncollectible residues (rounding-down division), so the required exact-zero state may never be reachable. The Agave analog is the `withdraw()` instruction handler for vote accounts, which requires `pending_delegator_rewards == 0` before a vote account can be fully closed, while `pending_delegator_rewards` is (a) incremented by *any* unprivileged signer via `deposit_delegator_rewards`, and (b) drawn down only through a truncating-division reward-distribution formula.

### Finding Description
`withdraw()` in `programs/vote/src/vote_state/mod.rs` computes `remaining_balance` and, when it is exactly zero, only allows deinitializing/closing the vote account if `pending_delegator_rewards == 0`: [1](#0-0) 

`pending_delegator_rewards` is populated by `deposit_delegator_rewards`, which only requires the *source* account (not the vote account's authority) to sign — meaning any unprivileged party can add an arbitrary, attacker-chosen amount (as low as 1 lamport) to an arbitrary victim vote account's `pending_delegator_rewards`: [2](#0-1) [3](#0-2) 

The only path that reduces `pending_delegator_rewards` is the epoch block-reward distribution in `calculate_block_reward`, which uses truncating u128 integer division to split the pending amount across delegated stakers, then clamps to `pending_delegator_rewards`: [4](#0-3) 

Because the division `pending_delegator_rewards * stake / total_active_stake` always rounds down per stake account, and rewards are computed independently per delegator, the sum of distributed amounts can be strictly less than `pending_delegator_rewards` whenever the fractional remainder does not sum to a whole lamport across delegators (identical in nature to MarinateV2's "small uncollectible residues" caused by per-user reward rounding). This mirrors the same broken invariant the external report calls out: a state-transition guard requires an accumulator to hit *exactly* zero, but the mechanism that reduces the accumulator is lossy/truncating and may never fully drain it to zero.

### Impact Explanation
If `pending_delegator_rewards` cannot be driven to exactly zero (e.g., because the truncation residue is smaller than 1 lamport per delegator and never accumulates to a full lamport, or because the vote account no longer has any active delegated stake to receive further distributions at all — `total_active_stake == 0` returns `0` from `calculate_block_reward`, permanently freezing further reduction), the vote account's `withdraw()` full-close path is permanently blocked by `InsufficientFunds`. This locks the rent-exempt reserve and any other lamports in the vote account forever, and it can be triggered by any unprivileged actor who calls `DepositDelegatorRewards` against a victim vote account they do not control, at negligible cost (as little as 1 lamport plus a transaction fee). This is a fund-lock/loss impact reachable by an unprivileged party without needing a malicious validator, leaked key, or front-running assumption.

### Likelihood Explanation
Likelihood is moderate: the griefing primitive (calling `deposit_delegator_rewards` against any target vote account) requires no special privilege and no cooperation from the vote account owner, satisfying the "unprivileged" requirement. The harder part to confirm is whether truncation residue reliably prevents `pending_delegator_rewards` from ever reaching exactly zero in realistic reward-distribution conditions (e.g., a vote account with `total_active_stake == 0` after all its stakers move away would permanently stop distributing any part of `pending_delegator_rewards`, guaranteeing the value never becomes zero). I was not able to locate, within the available tool budget, the exact code path that subtracts the distributed amount from `pending_delegator_rewards` after `calculate_block_reward` runs (grep for `pending_delegator_rewards.*checked_sub` returned no matches), so I cannot fully confirm the decrement mechanics or whether a safeguard elsewhere forces the final residue to zero. This should be verified directly in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, which was not fully inspected.

### Recommendation
- Add an explicit forced write-off/rounding path so `pending_delegator_rewards` is set to exactly `0` once distribution can no longer be split further (e.g., once `total_active_stake == 0`, or once the remaining amount is smaller than the smallest possible per-delegator share), rather than requiring the incremental distribution to sum exactly to the original amount.
- Alternatively, change `withdraw()`'s exact-zero requirement to allow closure once `pending_delegator_rewards` is below a dust threshold that is swept/burned or paid entirely to the current authorized withdrawer.
- Consider requiring `deposit_delegator_rewards` deposits to be authorized/attributable to the vote account's stake pool rather than allowing any unprivileged signer to inject dust into an arbitrary victim account's `pending_delegator_rewards`.

### Proof of Concept
1. Attacker calls `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` against a victim's vote account, per `deposit_delegator_rewards`, using only their own signer/funds — no authorization on the vote account is required [5](#0-4) .
2. This sets/increases `pending_delegator_rewards` on the victim vote account via `add_pending_delegator_rewards` [3](#0-2) .
3. Over subsequent epochs, `calculate_block_reward`'s truncating division distributes at most `pending_delegator_rewards` but can leave an undistributed remainder if the vote account's total active stake is zero (returns `0` unconditionally) or the fractional split truncates to zero for the tiny deposited amount [6](#0-5) .
4. The victim's authorized withdrawer subsequently attempts `Withdraw(all_lamports)` to fully close the vote account; because `pending_delegator_rewards > 0`, `withdraw()` returns `InstructionError::InsufficientFunds` and the account can never be closed [7](#0-6) , matching the existing test `test_withdraw_pending_delegator_rewards`, which shows full-close blocked while `pending_delegator_rewards > 0` and only succeeds once it is manually reset to `0` [8](#0-7) .

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }
    }
