## Analog Found: Unbounded Stake-Delegation Set Fully Re-Scanned in a Single Block at Every Epoch Boundary

### Title
Unbounded, cheaply-inflatable stake-delegation set is fully recomputed synchronously in a single block at every epoch boundary, unlike the (bounded) reward *distribution* step - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The Beacon Kit report's broken invariant is: an unprivileged actor can cheaply create unbounded entries in a store that is never pruned and is fully re-scanned from the beginning on every block, so cost of block production grows without bound as the store grows, eventually halting consensus. Agave's epoch-boundary stake-reward *calculation* has the same structural weakness: it iterates over the entire, unbounded set of stake delegations in one shot, inside the single block that starts a new epoch, while only the reward *distribution* step (writing updated stake accounts) is explicitly partitioned across multiple blocks.

### Finding Description
At every epoch boundary, `Bank::process_new_epoch` (`runtime/src/bank.rs:1815-1904`) synchronously calls `compute_new_epoch_caches_and_rewards` → `calculate_rewards` → `calculate_rewards_for_partitioning` → `calculate_validator_rewards`, which in turn calls:

- `calculate_reward_points_partitioned` [1](#0-0) 
- `calculate_stake_rewards_and_commissions` [2](#0-1) 

Both functions take the full `stake_delegations: Vec<(&Pubkey, &StakeAccount<Delegation>)>` — every stake delegation in the cluster — and iterate over all of them (with rayon parallelism, but still O(N) total work) to compute points and redeem rewards, as noted explicitly in the code comment: "For N stake delegations, where N is >1,000,000, we produce N stake rewards..." [3](#0-2) . This calculation happens entirely within `begin_partitioned_rewards`, called once, synchronously, in the first block of the new epoch [4](#0-3) .

Unlike the stake-account *stores* for distributing rewards, which are explicitly capped per block via `stake_account_stores_per_block` / `get_reward_distribution_num_blocks` and spread over multiple blocks with a hard cap (e.g., capped at ~10% of epoch length) [5](#0-4) , the *calculation* step that scans `stake_delegations` has no such partitioning or cap.

The number of stake delegations is not bounded like vote accounts are (vote accounts are explicitly capped at `MAX_ALPENGLOW_VOTE_ACCOUNTS` via `clone_and_filter_for_vat` [6](#0-5) ). Creating a stake account only costs the rent-exempt reserve for a `StakeStateV2`-sized account plus the minimum delegation amount, and the minimum delegation itself can be as low as 1 lamport prior to the `upgrade_bpf_stake_program_to_v5` feature (and only 1 SOL once that feature activates) [7](#0-6) . There is no on-chain limit preventing an actor from creating an unbounded number of stake accounts, each delegated at the minimum amount, exactly mirroring the "1 BERA minimum deposit, never pruned" primitive in the Beacon Kit report.

### Impact Explanation
If the number of stake delegations grows very large (analogous to the report's 1M+ deposits), the epoch-boundary reward-calculation pass (`calculate_reward_points_partitioned` + `calculate_stake_rewards_and_commissions`) must scan the entire set inside a single block on every validator in the cluster simultaneously (since replay is deterministic and every validator must perform the identical computation to arrive at the same bank hash). Because there is no mechanism to spread or cap this specific computation across multiple blocks (only the account *stores* are partitioned), an unbounded growth in delegation count directly and proportionally increases the wall-clock time required to process the first block of every epoch, everywhere in the cluster at once — this is a stronger, cluster-wide analog to the Beacon Kit single-proposer timeout, since it affects every replaying validator rather than just the proposer.

### Likelihood Explanation
Exploitation requires only permissionless `SystemProgram::CreateAccount` + `StakeInstruction::DelegateStake` calls funded with rent-exempt reserve + minimum delegation lamports per stake account — no special privileges, no validator/peer trust assumptions. As in the original report, the attacker's capital is not lost (it remains delegated and earning rewards), only "locked" for the duration of the attack, making sustained large-scale account creation economically much cheaper than a pure griefing attack. The primary uncertainty is the actual wall-clock cost per delegation in `redeem_delegation_rewards`/point calculation at very large N, and whether current stake-account creation costs on a live cluster are high enough to make reaching a degrading N impractical; this would need empirical benchmarking (as the original reporter did for Beacon Kit) to establish a concrete inflection point.

### Recommendation
Partition the stake-reward *calculation* step the same way the *distribution* step is already partitioned, e.g., incrementally accumulate points/rewards for a bounded slice of delegations per block across multiple blocks at the epoch boundary, rather than requiring the entire `stake_delegations` vector to be processed within the single epoch-boundary block. Alternatively, impose an enforced cap on the number of stake delegations (as is already done for vote accounts via `MAX_ALPENGLOW_VOTE_ACCOUNTS`) or raise/enforce a materially higher minimum delegation amount to bound the growth rate of the unbounded set.

### Proof of Concept
Conceptual reproduction, following the same methodology as the original report:
1. Fund an attacker account and repeatedly submit `CreateAccount` + `DelegateStake` transactions, each delegating the minimum stake amount (`get_minimum_delegation`), to create a very large number (e.g., hundreds of thousands to millions) of stake accounts over successive epochs.
2. Instrument `calculate_stake_rewards_and_commissions` and `calculate_reward_points_partitioned` with timing measurements (analogous to the reporter's `before := time.Now()` / `spent := time.Since(before)` around `GetDepositsByIndex`).
3. Observe that the measured time for the epoch-boundary calculation grows roughly linearly with the number of stake delegations, since the whole `stake_delegations` vector is scanned unconditionally in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, in contrast to the bounded, per-block-capped stake-account *store* step performed during distribution.
4. Extrapolate/validate at what delegation count the epoch-boundary block's processing time begins to approach or exceed the cluster's block/slot time budget, at which point every replaying validator (not just the leader) would begin to stall similarly to the CometBFT `TimePropose` timeouts described in the original report.

        &self,
        stake_history: &StakeHistory,
        stake_delegations: &Vec<(&'a Pubkey, &'a StakeAccount<Delegation>)>,
        cached_vote_accounts: &CachedVoteAccounts<'_>,
        epoch_inflation_rewards: u64,
        ag_epoch_type: &AlpenglowEpochType,
        thread_pool: &ThreadPool,
        metrics: &RewardsMetrics,
    ) -> Option<PointValue> {
        let CachedVoteAccounts {
            distribution_epoch_vote_accounts,
            ..
        } = cached_vote_accounts;

        let solana_vote_program: Pubkey = solana_vote_program::id();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        match ag_epoch_type {
            AlpenglowEpochType::Alpenglow { .. } => {
                // In alpenglow, we do not need to compute `PointValue::points` as the final
                // rewards are simply the total credits stored in the vote account.  We just need
                // to return a `Some` value with valid rewards.
                return Some(PointValue {
                    rewards: epoch_inflation_rewards,
                    points: 0,
                });
            }
            AlpenglowEpochType::Tower => {
                // For tower we need to compute the valid `PointValue::points`.
            }
            AlpenglowEpochType::MigrationEpoch { .. } => {
                // For the migrating epoch, we need to compute the tower portion of `PointValue::points`.
            }
        }

        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        let (points, measure_us) = measure_us!(thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .map(|(_stake_pubkey, stake_account)| {
                    let vote_pubkey = stake_account.delegation().voter_pubkey;

                    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey)
                    else {
                        return 0;
                    };
                    if vote_account.owner() != &solana_vote_program {
                        return 0;
                    }

                    calculate_points_for_tower(
                        stake_account.stake_state(),
                        DelegatedVoteState::from(vote_account.vote_state_view()),
                        stake_history,
                        new_warmup_cooldown_rate_epoch,
                        use_fixed_point_stake_math,
                    )
                    .unwrap_or(0)
                })
