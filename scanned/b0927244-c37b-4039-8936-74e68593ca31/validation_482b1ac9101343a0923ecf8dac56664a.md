## Analysis

The XVS Vault bug is a class of "state removal is conditioned on the wrong predicate, so the tracked value can be left stale/duplicated." The closest local analog in Agave is in the validator's in-memory `StakesCache`, which mirrors the same anti-pattern: it removes a cached vote/stake entry only when specific conditions match the *current* observed account state, but does not handle the case where an account's *role* (owner) changes away from the type it was cached as. This is explicitly flagged as unresolved by the maintainers themselves.

### Title
Stale/duplicated delegated-stake entries in `StakesCache` when a cached stake/vote account's owner changes - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` decides whether to insert, update, or evict a cached stake/vote-account entry purely based on the **current owner of the account being processed**, not on whether that pubkey was previously cached as a stake or vote account. If a pubkey that is cached as a stake delegation is later observed with a non-zero lamport balance but a *different* owner (no longer the Stake or Vote program), the function silently does nothing — it neither evicts the stale entry nor updates it. This is directly analogous to the XVS Vault bug where voting power was only removed under one specific condition (reward-token == XVS) instead of the actual invariant that matters (pool token == XVS), leaving stale voting power in the system.

### Finding Description
`check_and_store` branches only on `account.owner()`: [1](#0-0) [2](#0-1) 

The comment at the top of the function is a maintainer-acknowledged TODO for exactly this gap: [3](#0-2) 

- If `lamports == 0`, the code correctly removes the cache entry based on the **owner at time of removal** (`solana_vote_program::check_id` / `stake_program::check_id`), covering the "closed account" case.
- If `lamports != 0` and the owner is Vote program or Stake program, the code updates the cache accordingly (`upsert_vote_account` / `upsert_stake_delegation`, or eviction on deserialize failure via `remove_vote_account` / `remove_stake_delegation`).
- **If `lamports != 0` and the owner is neither the Vote program nor the Stake program**, none of the branches fire. The function returns without touching the cache at all, even though this pubkey may still hold a stale `StakeAccount` entry in `stake_delegations` (contributing to `delegated_stakes` and `VoteAccounts`' stake tally for some validator).

This is confirmed as a known, still-open gap by the corresponding regression test, which is explicitly written to *not* exercise the owner-change scenario: [4](#0-3) 

`check_and_store` is invoked once per committed final account state per transaction (not per intermediate CPI state), via `update_stakes_cache`: [5](#0-4) 

and via `store_accounts` for direct bank-level stores: [6](#0-5) 

Because only the *final* post-transaction account state is observed, any intermediate zero-lamport state that occurred mid-transaction (e.g., a stake account fully withdrawn and its pubkey/account slot reused by another program within the same atomic transaction) is invisible to the cache. The cache only ever sees "still owned by Stake program" (handled) or "now owned by something else, non-zero lamports" (unhandled) — it never gets the chance to hit the correctly-handled `lamports == 0` branch for that pubkey.

Note: reassigning an account's owner via the runtime's account-mutation path independently requires the account data to be zeroed first (`is_zeroed(self.get_data())` in `BorrowedInstructionAccount::set_owner`): [7](#0-6) 
This constrains — but by itself does not eliminate — the reachability of an owner change while `stake_delegations` still references the pubkey, since the actual removal logic in `StakesCache` keys off `lamports == 0`, not off "data zeroed." Whether a stake account's data is fully zeroed as part of a full withdrawal (as opposed to just its lamports going to zero while `StakeStateV2::Uninitialized`/other non-zeroed state remains) could not be confirmed from the indexed portion of `programs/stake-program` in this pass; this is the main open uncertainty in fully weaponizing the primitive end-to-end.

### Impact Explanation
`StakesCache`'s `delegated_stakes` / `vote_accounts` feed directly into consensus-critical validator bookkeeping (stake-weighted voting/leader-schedule inputs derived from `Stakes<T>`). A stale, un-evicted stake-delegation entry that continues to contribute `effective_stake` to a `voter_pubkey`'s tallied stake — after the backing account has, from accounts-db's perspective, moved on to a different owner/program — is a corruption of the validator's internal view of stake weight (`delegated_stakes: ImblHashMap<Pubkey, u64>`, `VoteAccounts` stake totals). This falls into the "false execution/rooting/acceptance" impact category listed as valid, because it corrupts data used for leader-schedule/consensus-adjacent accounting without any actual on-chain stake backing it, in a way indistinguishable from double-counted voting power in the XVS Vault report.

### Likelihood Explanation
Medium-low confidence/likelihood. The maintainers themselves flagged this exact gap as unresolved (`bank/tests.rs` TODO referencing PR #24200 discussion, and the identical TODO comment inline in `stakes.rs`), which shows the class of bug is real and known to be unguarded. However, actually triggering it end-to-end requires that a stake-program-owned account (already cached as a delegation) can, within one committed transaction, both (a) have its lamports go through the zero state, and (b) simultaneously have its owner reassigned to a non-stake/non-vote program while ending with non-zero lamports and zeroed data — a path gated by the `is_zeroed(data)` requirement on `set_owner`. I could not fully confirm from the indexed code whether the Stake program's `Withdraw`/`Deactivate` instructions zero the account's data as part of a full withdrawal, which is the missing link needed to assert full exploitability rather than a defense-in-depth gap.

### Recommendation
Change the eviction/update logic in `StakesCache::check_and_store` (and `Stakes::remove_stake_delegation` / `remove_vote_account`) to key off of "was this pubkey previously cached as a stake/vote entry", not solely off "what is the account's current owner." Concretely: before dispatching on `account.owner()`, first check whether `pubkey` exists in `stake_delegations` or `vote_accounts`; if it does and the current owner no longer matches the expected program, evict it regardless of lamports/new owner — mirroring the XVS fix of keying removal off the actual invariant (pool token) rather than an incidental one (reward token / current owner).

### Proof of Concept
Conceptual reproduction using the existing test harness pattern in `runtime/src/stakes.rs` tests (e.g. `test_stakes_basic`, `test_stakes_change_delegate`):
1. Call `stakes_cache.check_and_store(&stake_pubkey, &stake_account, ...)` with a valid Stake-program-owned, non-zero-lamport stake account delegated to `vote_pubkey` — this inserts it into `stake_delegations` and increments `delegated_stakes[vote_pubkey]`.
2. Construct an `AccountSharedData` for the same `stake_pubkey` with non-zero lamports but `owner` set to some other program id (e.g. `system_program::id()` or an arbitrary pubkey), simulating the account having been reassigned/reused by a different program in a later transaction.
3. Call `check_and_store` again with this new account.
4. Observe that `stakes_cache.stakes().vote_accounts().get_delegated_stake(&vote_pubkey)` still reflects the old stake amount — the entry in `stake_delegations` was never evicted — even though the pubkey is no longer a stake account, demonstrating the stale/orphaned delegated-stake bug matching the report's "voting power not removed" class.     /// a bank-level cache of vote accounts and stake delegation info
    fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })
            .for_each(|(pubkey, account)| {
                // note that this could get timed to: self.rc.accounts.accounts_db.stats.stakes_cache_check_and_store_us,
                //  but this code path is captured separately in ExecuteTimingType::UpdateStakesCacheUs
                self.stakes_cache.check_and_store(
                    pubkey,
                    account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                );
            });
    }

    /// Assignes the owner of this account (transaction wide)
    pub fn set_owner(&mut self, pubkey: &[u8]) -> Result<(), InstructionError> {
        // Only the owner can assign a new owner
        if !self.is_owned_by_current_program() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the account is writable
        if !self.is_writable() {
            return Err(InstructionError::ModifiedProgramId);
        }
        // and only if the data is zero-initialized or empty
        if !is_zeroed(self.get_data()) {
            return Err(InstructionError::ModifiedProgramId);
        }
        // don't touch the account if the owner does not change
        if self.get_owner().to_bytes() == pubkey {
            return Ok(());
        }
        self.touch()?;
        self.account.copy_into_owner_from_slice(pubkey);
        Ok(())
    }
