Based on my investigation, I found a strong structural analog in Agave's SIMD-0123 "block revenue sharing" delegator-rewards mechanism, mirroring the report's core bug class: an amount is derived from a stored balance (`pending_delegator_rewards` / `yieldEarned`) to pay out a distribution, but the source balance is never correctly decremented after the payout, so the same value keeps getting distributed.

### Title
Block-revenue delegator rewards (`pending_delegator_rewards`) are never decremented after distribution, allowing indefinite re-distribution of the same deposit - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` computes a per-stake-account share of a vote account's `pending_delegator_rewards` field every rewarded epoch and this amount is paid to delegators via the epoch-rewards distribution path. `pending_delegator_rewards` is only ever *increased*, via `add_pending_delegator_rewards` in `deposit_delegator_rewards` (SIMD-0123's `DepositDelegatorRewards` instruction). No code path decrements this field after a block reward has been calculated and distributed for an epoch. This is directly analogous to the Convex report's bug: an amount computed from a "yield"-like variable is used to pay out value, but the corresponding source value used in the calculation is never correctly reduced/consumed, so downstream accounting is wrong.

### Finding Description
`calculate_block_reward` reads the vote account's `pending_delegator_rewards()` and computes each stake account's share proportional to its effective stake vs. total active stake for that vote account, capping the result at `pending_delegator_rewards`: [1](#0-0) 

This is invoked once per rewarded epoch for every stake delegation when `block_revenue_sharing` is enabled: [2](#0-1) 

The resulting `block_reward` lamports are added to stake accounts during distribution and their sum is tracked as `block_reward_lamports_distributed`: [3](#0-2) [4](#0-3) 

Test scaffolding shows that the lamports backing block rewards are actually pre-funded into the `epoch_rewards` sysvar balance and drained from there (`create_epoch_rewards_sysvar(... block_rewards)`), not subtracted from the vote account's own lamports/`pending_delegator_rewards` bookkeeping value: [5](#0-4) 

Meanwhile, the only place `pending_delegator_rewards` is mutated on the vote account is `add_pending_delegator_rewards`, a `checked_add`-only operation invoked from `deposit_delegator_rewards`: [6](#0-5) [7](#0-6) 

I was unable to locate any `checked_sub`/decrement of `pending_delegator_rewards` anywhere in `programs/vote/src/vote_state/*`, `programs/vote/src/vote_processor.rs`, or `runtime/src/bank/partitioned_epoch_rewards/*.rs` in the searches performed. This means once a validator/withdraw-authority deposits an amount `D` via `DepositDelegatorRewards`, `pending_delegator_rewards = D` persists unchanged across epochs. Every rewarded epoch thereafter (as long as the vote account has active delegated stake and `block_revenue_sharing` is enabled), `calculate_block_reward` recomputes and distributes up to the *entire* `D` again to delegators, because the value used as the numerator/cap (`pending_delegator_rewards`) never shrinks.

This is the direct analog of the Convex bug: there, `lpTokenEarned` was computed from `yieldEarned` (denominated incorrectly) without being tied back correctly to the actual amount that should be removed from the pool, causing more value to be extracted than intended. Here, `block_reward` is computed from `pending_delegator_rewards` without that source ever being reduced, so far *more* value (unboundedly, every epoch) is extracted/minted than the single deposit intended to fund.

### Impact Explanation
If confirmed, this breaks a core invariant of Solana's monetary accounting: rewards distributed to delegators are supposed to be bounded by the amount actually deposited/allocated for block revenue sharing (SIMD-0123). Because the deposited amount is never decremented, the same `pending_delegator_rewards` balance is redistributed to stake accounts every epoch indefinitely, and since the lamports paid out are drawn from the bank's `epoch_rewards` sysvar / freshly minted capitalization rather than the vote account's own escrowed balance, this effectively mints unbounded lamports over time — a direct violation of the intended reward cap and a fund-creation bug reachable by any validator that performs a single `DepositDelegatorRewards` deposit (an unprivileged, permissionless instruction, not requiring any malicious peer/validator collusion beyond normal participation).

### Likelihood Explanation
Likelihood is currently uncertain because it depends on confirming there is truly no decrement path — my tool-based search could not exhaustively verify all call sites (e.g., I could not fully inspect every line of `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` and `calculation.rs`, some of which were only partially returned by search). The feature is gated behind `block_revenue_sharing`, `commission_rate_in_basis_points`, `custom_commission_collector`, and vote-state V4, meaning it is behind currently-inactive/limited feature flags (SIMD-0123/0185/0232/0291), which reduces immediate exploitability but does not eliminate it if/when these features activate.

### Recommendation
Add a decrement of `pending_delegator_rewards` (a `checked_sub`) on the vote account whenever `block_reward` is computed/distributed for that vote account's stake accounts in an epoch, mirroring `add_pending_delegator_rewards`. This should be applied atomically with reward calculation/distribution so the pool being distributed from is properly consumed, analogous to fixing `lpTokenEarned` to be correctly and consistently tied to the actual withdrawable amount in the Convex report.

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,

            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
            }
        }

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
