**Analysis:**

The claim rests on the premise that `write_accounts_to_cache` and its ephemeral-account bookkeeping serialize on a single "write-cache mutex" that a bystander `getBalance` call would also need to acquire. This is not how the write cache is implemented.

`write_accounts_to_cache` increments `WriteAccountsToCacheStats::num_ephemeral_accounts_skipped` and `account_data_bytes_stored` as plain local `u64` fields on a per-call stack-allocated struct [1](#0-0) , which are then folded into `StoreAccountsUnfrozenStats` via `AtomicU64::fetch_add` [2](#0-1) . Neither path takes a mutex.

The actual account storage, `AccountsCache`, is backed by `DashMap` for both the per-slot `SlotCache` and the `AccountsCacheIndex` [3](#0-2) [4](#0-3) . `DashMap` shards its internal locking by key hash, so writes to an ephemeral account's pubkey only lock the shard(s) containing that pubkey, not the whole cache. A `getBalance` call for an unrelated pubkey goes through `do_load` → `accounts_cache.load_latest` [5](#0-4) , which only touches the shard(s) for the bystander's own pubkey in `AccountsCacheIndex` and `SlotCache`, not any global lock shared with the ephemeral-account writer.

So there is no code path where high-volume ephemeral-account churn (driving `num_ephemeral_accounts_skipped`/`account_data_bytes_stored` up) causes a single mutex to serialize with an unrelated bystander's `getBalance` lookup. The stats increments are lock-free atomics, and the underlying cache uses sharded `DashMap` locking keyed by pubkey, so contention is isolated per-pubkey-shard rather than global. The premised mechanism (a single "write-cache mutex") does not exist in this code, so the described PoC would not demonstrate the claimed degradation.
