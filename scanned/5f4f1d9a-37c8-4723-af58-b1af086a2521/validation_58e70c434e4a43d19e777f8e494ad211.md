## Analysis

The Biconomy report's broken invariant is: a monotonically-growing "IOU" accounting counter (`providedLiquidity`) is used to gate/limit withdrawals, but nothing ever decrements it when funds are paid out through a separate path — so the counter drifts from the actual spendable balance and legitimate withdrawals revert.

Agave's vote program has the same structural pattern around `pending_delegator_rewards` in `VoteStateV4`.

### Title
Vote account `pending_delegator_rewards` counter is never decremented after block-reward distribution, permanently inflating the authorized withdrawer's reserved-balance floor - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
`pending_delegator_rewards` is incremented via `add_pending_delegator_rewards` whenever `DepositDelegatorRewards` is processed [1](#0-0) [2](#0-1) . `withdraw()` treats this value as lamports that must remain reserved in the vote account: any withdrawal that would leave `remaining_balance < rent_exempt_minimum + pending_delegator_rewards` fails, and the account cannot even be closed while `pending_delegator_rewards > 0` [3](#0-2) . Separately, `calculate_block_reward()` reads this same field once per epoch to compute each delegator's proportional share of the "pending" reward and caps the per-delegator payout at `pending_delegator_rewards` [4](#0-3) , and that amount is then minted into stake accounts and capitalization during `distribute_epoch_rewards_in_partition` / `store_stake_accounts_in_partition` [5](#0-4) [6](#0-5) . A repo-wide search finds only one mutator of `pending_delegator_rewards` — the additive one in `handler.rs` — with no corresponding decrement anywhere in the codebase.

### Finding Description
`pending_delegator_rewards` on the vote account plays exactly the role of `providedLiquidity` in the Biconomy report: it is an accounting figure that is supposed to represent "lamports still owed/reserved for stakers," and it gates how much the account owner (here, the `authorized_withdrawer`) can withdraw. But the value only ever grows through `add_pending_delegator_rewards` [1](#0-0) , and no code path reduces it once the corresponding block reward has actually been paid out to delegators each epoch in `calculate_block_reward`/`store_stake_accounts_in_partition` [4](#0-3) . Every epoch this "reward pool" is effectively re-spent (the actual lamports come from newly minted capitalization, not from debiting the vote account or the `pending_delegator_rewards` counter), yet `withdraw()` keeps treating the entire, ever-increasing, historical total of `pending_delegator_rewards` as untouchable reserve on the vote account:

```
// SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
// is lamports - pending_delegator_rewards - rent_exempt_minimum.
let min_balance = min_rent_exempt_balance
    .checked_add(pending_delegator_rewards)
    .ok_or(InstructionError::ArithmeticOverflow)?;
if remaining_balance < min_balance {
    return Err(InstructionError::InsufficientFunds);
}
``` [7](#0-6) 

Since `pending_delegator_rewards` is never reduced when the associated reward has already been minted/paid to stakers, this reserve requirement diverges further from reality every epoch that block-revenue-sharing is active and deposits are made, exactly mirroring the LiquidityProviders.sol `providedLiquidity` vs `currentLiquidity` divergence.

### Impact Explanation
Once `pending_delegator_rewards` (the phantom reserve) grows large enough — which happens automatically over time as `DepositDelegatorRewards` deposits accumulate while the field is never drawn down — the authorized withdrawer of the vote account permanently loses the ability to withdraw any lamports beyond the shrinking (or zero) headroom, and can never fully close/redeem the account even though `pending_delegator_rewards > 0` blocks closing unconditionally [8](#0-7) . This causes legitimate lamports (rewards/commission owed to the withdrawer, or lamports simply parked in the account) to become permanently unwithdrawable — a fund-lock condition analogous to the original bug's "LP token holders unable to redeem shares."

### Likelihood Explanation
This requires no malicious actor: it triggers under the intended, documented usage of SIMD-0123 (block revenue sharing) — repeated `DepositDelegatorRewards` calls plus normal epoch-boundary reward distribution are sufficient to grow `pending_delegator_rewards` without bound relative to what's actually still owed. No privileged or adversarial behavior is needed; it is a straightforward consequence of the missing decrement path.

### Recommendation
Add a corresponding decrement to `pending_delegator_rewards` (e.g., `sub_pending_delegator_rewards`) that is applied to the vote account's stored state whenever its `block_reward` has been included in a partition and successfully distributed in `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition`, so the "reserved" counter tracks only rewards that are still actually outstanding and unpaid, keeping it consistent with the real spendable balance checked in `withdraw()`.

### Proof of Concept
1. Enable `block_revenue_sharing`/SIMD-0123 features; create a V4 vote account with delegated stake.
2. Repeatedly call `DepositDelegatorRewards` to add lamports and grow `pending_delegator_rewards`, as validated by `test_deposit_delegator_rewards`-style flows [9](#0-8) .
3. Let multiple epochs pass so that `calculate_block_reward`/`store_stake_accounts_in_partition` distribute the corresponding rewards to delegators from capitalization [10](#0-9)  — observe (via `pending_delegator_rewards()`) that the field never decreases even though the reward has been minted and delivered.
4. Attempt `Withdraw` as the `authorized_withdrawer` for an amount that would leave the account with less than `rent_exempt_minimum + pending_delegator_rewards`; observe `InstructionError::InsufficientFunds`, as covered by `test_withdraw_with_pending_delegator_rewards` [11](#0-10) , and note that this reserve requirement only ever grows across epochs, eventually exceeding the account's real available balance.

**Uncertainty**: I could not find any code in the indexed portions of the repository that decrements `pending_delegator_rewards`; a full-repo `grep` for the field turned up only the additive mutator. Given the size limits on the codebase index, it's possible (though I found no evidence of it) that a decrement exists in a file/module not surfaced by search — a Devin session with full repository access would be needed to conclusively rule this out before treating this as a confirmed, unpatched bug.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.

        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

            return Err(VoteError::ActiveVoteAccountClose.into());

            .checked_add(pending_delegator_rewards)

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

        );

        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),

            store_stake_accounts_us,

            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,

    fn store_stake_accounts_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) -> DistributionResults {
        let feature_snapshot = self.feature_set.snapshot();
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;

        let mut stake_reward_lamports_minted = 0;
        let mut stake_reward_lamports_burned = 0;
        let mut block_reward_lamports_distributed = 0;
        let mut block_reward_lamports_burned = 0;
        let indices = partition_rewards
            .partition_indices
            .get(partition_index as usize)
            .unwrap_or_else(|| {
                panic!(
                    "partition index out of bound: {partition_index} >= {}",
                    partition_rewards.partition_indices.len()
                )
            });
        let mut updated_stake_rewards = Vec::with_capacity(indices.len());
        let stakes_cache = self.stakes_cache.stakes();
        let stakes_cache_accounts = stakes_cache.stake_delegations();
        let stake_history = stakes_cache.history();
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let rent = &self.rent_collector.rent;
        for index in indices {
            let partitioned_stake_reward = partition_rewards
                .all_stake_rewards
                .get(*index)
                .unwrap_or_else(|| {
                    panic!(
                        "partition reward out of bound: {index} >= {}",
                        partition_rewards.all_stake_rewards.total_len()
                    )
                })
                .as_ref()
                .unwrap_or_else(|| {
                    panic!("partition reward {index} is empty");
                });
            let stake_pubkey = partitioned_stake_reward.stake_pubkey;
            let stake_reward_amount = partitioned_stake_reward.inflation.stake_reward;
            let block_reward_amount = partitioned_stake_reward.block_reward;

            match Self::build_updated_stake_reward(
                self.epoch,
                stake_history,
                new_warmup_cooldown_rate_epoch,
                stakes_cache_accounts,
                partitioned_stake_reward,
                rent,
                adjust_delegations_for_rent,
                use_fixed_point_stake_math,
            ) {
                Ok(stake_reward) => {
                    stake_reward_lamports_minted += stake_reward_amount;
                    block_reward_lamports_distributed += block_reward_amount;
                    updated_stake_rewards.push(stake_reward);
                }
                Err(err) => {
                    error!(
                        "bank::distribution::store_stake_accounts_in_partition() failed for \
                         {stake_pubkey}, {stake_reward_amount} lamports burned: {err:?}"
                    );
                    stake_reward_lamports_burned += stake_reward_amount;
                    block_reward_lamports_burned += block_reward_amount;
                }
            }
        }
        drop(stakes_cache);
        self.store_accounts(
            (self.slot(), &updated_stake_rewards[..]),
            // Reuse the rewards calculation thread pool to parallelize
            // loading the previous versions of the stake accounts.
            Some(crate::bank::rewards_calculation_thread_pool()),
        );
        DistributionResults {
            stake_reward_lamports_minted,
            stake_reward_lamports_burned,
            block_reward_lamports_distributed,
            block_reward_lamports_burned,
            updated_stake_rewards,
        }
    }
