## Title
Staked-stream throttling EMA never decays without new stream activity, causing indefinite QUIC starvation of staked validators after a load burst - (File: `streamer/src/nonblocking/stream_throttle.rs`)

## Summary
The Sherlock report (M-7) describes a class of bug where a windowed/observation-based average is only refreshed by external triggers rather than by the passage of time itself, so decisions made from that average can be stale relative to the true current state and cause economic harm. The closest structural analog found in this Agave checkout is `StakedStreamLoadEMA`, which computes a smoothed "load" used to decide whether staked-connection QUIC stream throttling should be enabled. Like the TWAP function that only updates when `Pair.sync()`/new observations are pushed, `StakedStreamLoadEMA::update_ema_if_needed` only recomputes the EMA when a stream event happens to occur — there is no periodic/background refresh independent of traffic. If load spikes and then activity stops, the EMA (and the derived `staked_throttling_enabled` flag) never decays back down, artificially throttling legitimate staked validator traffic indefinitely.

## Finding Description
`StakedStreamLoadEMA` tracks `current_load_ema` and a boolean `staked_throttling_enabled`, which gates how many QUIC streams staked peers are permitted (`available_load_capacity_in_throttling_duration`) [1](#0-0) .

The EMA is only advanced by `update_ema_if_needed`, which is invoked exclusively from three call sites tied to actual stream I/O events: `increment_load` (on a new stream being accepted), and `on_stream_error`/`on_stream_closed` [2](#0-1) . There is no timer-driven or independent tick that calls `update_ema_if_needed` on a fixed cadence; it is purely event-driven.

`update_ema_if_needed` itself is time-aware — it computes `since_last_update` and, if enough time elapsed, folds in `num_extra_updates` intervals of zero load via `ema_function(updated_load_ema, 0)` [3](#0-2) . This correctly *would* decay the EMA toward zero — but only if it is actually invoked. Because invocation depends entirely on new stream traffic arriving, once no further streams are opened/closed/errored on any connection, the function is simply never called again, and `current_load_ema` / `staked_throttling_enabled` freeze at whatever value they held at the last event [4](#0-3) .

`available_load_capacity_in_throttling_duration`, which is consulted by `SwQos::max_streams_per_throttling_interval` to size the throttle window for a peer [5](#0-4) , reads `staked_throttling_enabled` directly without first forcing a refresh, so any decision made purely from a *new* connection attempt without any accompanying "stream accepted/closed/error" event on the same tick will use a value that can be arbitrarily stale (bounded only by how long it has been since the last unrelated stream event anywhere in the streamer).

This mirrors the reported flaw exactly at the structural level: an "average" is derived from a rolling window of past observations, is supposed to reflect near-real-time state, but is only updated in reaction to specific external triggers (there, `Pair.sync()`/swaps; here, stream accept/close/error events) rather than unconditionally with the passage of time. In the TWAP case this meant fees calculated off stale prices; here it means QoS decisions computed off a stale load signal.

## Impact Explanation
If QUIC stream traffic to a validator spikes (e.g. due to a burst of transaction submissions, legitimate or otherwise) and then goes quiet, `staked_throttling_enabled` can remain `true` indefinitely because nothing triggers `update_ema_if_needed` to decay it. While it stays enabled, `available_load_capacity_in_throttling_duration` continues to allocate reduced, stake-proportional stream capacity to staked peers instead of the full `max_staked_load_in_throttling_window` [6](#0-5) . This degrades legitimate staked-validator transaction ingestion (TPU/QUIC path) for an unbounded period after the traffic that triggered throttling has stopped, which is a non-RPC remote degradation condition reachable by ordinary, unprivileged network activity (no malicious validator/peer collusion required — any burst of legitimate traffic can trigger it).

## Likelihood Explanation
Likelihood is limited by the fact that `on_stream_error`/`on_stream_closed` fire relatively often under normal cluster operation (any stream from any peer, staked or unstaked-adjacent code paths, refreshes the EMA), so the window during which the EMA is provably "stuck" stale in a live mainnet validator may be short in practice. However, the underlying mechanism has no independent time-based decay path — the bug is real and demonstrable in isolation via the unit test's own manual driving of `update_ema` (`test_ema_decay_handles_missing_intervals` explicitly relies on someone calling `update_ema` with a large `time_since_last_update_ms`, not on it happening automatically) [7](#0-6) . I could not fully verify from the indexed code whether some other background task elsewhere in the streamer periodically calls `update_ema_if_needed` independent of stream events; my searches within this checkout only found the three event-triggered call sites plus the reporting/read-only usage. If such a periodic driver does not exist, the staleness window is bounded only by inter-arrival time of streams cluster-wide, which can be arbitrarily long during quiet periods.

## Recommendation
Add a periodic (timer-driven) call to `StakedStreamLoadEMA::update_ema_if_needed` (or equivalent decay tick) independent of stream accept/close/error events, so the EMA and `staked_throttling_enabled` always reflect elapsed real time rather than only updating in reaction to new stream activity — analogous to the TWAP fix, which added the *current* price sample instead of relying solely on historical/triggered observations.

## Proof of Concept
1. Drive a burst of staked streams so that `current_load_ema` crosses `staked_throttling_on_load_threshold`, setting `staked_throttling_enabled = true` (as in `test_staked_throttling_on_off`) [8](#0-7) .
2. Stop all stream traffic on the validator (no further `increment_load`/`on_stream_error`/`on_stream_closed` calls occur).
3. Because nothing else calls `update_ema_if_needed`, `current_load_ema` and `staked_throttling_enabled` remain frozen at the burst-time values indefinitely, confirmed by the fact that `update_ema` (the only path that decays load toward zero via `ema_function(_, 0)`) is unreachable without an external trigger [3](#0-2) .
4. Any subsequent staked connection queries `available_load_capacity_in_throttling_duration`, which still reports throttled capacity based on the stale, burst-era EMA rather than the true (idle) current load [6](#0-5) .

    fn update_ema(&self, time_since_last_update_ms: u128) {
        // if time_since_last_update_ms > STREAM_LOAD_EMA_INTERVAL_MS, there might be intervals where ema was not updated.
        // count how many updates (1 + missed intervals) are needed.
        let num_extra_updates =
            time_since_last_update_ms.saturating_sub(1) / u128::from(STREAM_LOAD_EMA_INTERVAL_MS);

        let load_in_recent_interval =
            u128::from(self.load_in_recent_interval.swap(0, Ordering::Relaxed));

        let mut updated_load_ema = Self::ema_function(
            u128::from(self.current_load_ema.load(Ordering::Relaxed)),
            load_in_recent_interval,
        );

        for _ in 0..num_extra_updates {

    pub(crate) fn update_ema_if_needed(&self) {
        const EMA_DURATION: Duration = Duration::from_millis(STREAM_LOAD_EMA_INTERVAL_MS);
        // Read lock enables multiple connection handlers to run in parallel if interval is not expired
        if Instant::now().duration_since(*self.last_update.read().unwrap()) >= EMA_DURATION {
            let mut last_update_w = self.last_update.write().unwrap();
            // Recheck as some other thread might have updated the ema since this thread tried to acquire the write lock.
            let since_last_update = Instant::now().duration_since(*last_update_w);
            if since_last_update >= EMA_DURATION {
                *last_update_w = Instant::now();
                self.update_ema(since_last_update.as_millis());
            }
        }
    }

    pub(crate) fn increment_load(&self, peer_type: ConnectionPeerType) {
        if peer_type.is_staked() {
            self.load_in_recent_interval.fetch_add(1, Ordering::Relaxed);
        }
        self.update_ema_if_needed();
    }

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
