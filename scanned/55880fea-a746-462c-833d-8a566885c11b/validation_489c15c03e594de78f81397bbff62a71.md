## Title
Integer-truncation in per-transaction instruction-data cost lets attackers split payloads to evade cost-model accounting - (File: `cost-model/src/cost_model.rs`)

### Summary
The Eggs.sol bug arises from computing a per-period fee with `(rate * period) / denominator` and applying it repeatedly instead of once, so integer truncation lets an actor keep more value by splitting one large operation into many small ones. Agave's `CostModel::get_instructions_data_cost` has the same truncating-division-repeated-over-many-small-inputs shape: it divides each transaction's instruction data length by a fixed constant and floors the result, so an attacker who splits a large payload across many small transactions can make the "data bytes" component of the compute-unit cost model repeatedly round down to zero, in aggregate paying/accounting for far less CU cost than an equivalent single large transaction.

### Finding Description
`CostModel::get_instructions_data_cost` computes the data-bytes cost as: [1](#0-0) 

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```

`INSTRUCTION_DATA_BYTES_COST` is itself defined via an integer division that already truncates (140/30 = 4, discarding the 0.667 remainder): [2](#0-1) 

Because `get_instructions_data_cost` performs plain floor division (`/`) rather than a rounding-up (`div_ceil`) division, any transaction whose total instruction data is less than 4 bytes (`instruction_data_len < INSTRUCTION_DATA_BYTES_COST`) is charged **zero** data-bytes cost, and any transaction is under-charged by up to 3 bytes' worth of cost. This is the same broken invariant as the Eggs bug: `f(n) != n * f(1)` for the floor-division fee function, so a party that controls how work is partitioned into discrete "billing units" (transactions, in this case) can pick the partition that minimizes the aggregate integer-truncated total.

This value feeds directly into `TransactionCost::sum()`, which becomes each transaction's contribution to the cost tracker/block cost limits: [3](#0-2) 

`data_bytes_cost` is summed into the transaction's total CU cost used for `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS` enforcement in the cost tracker/banking stage (`check_block_cost_limits`, `cost_tracker.rs`), and it also affects transaction prioritization math in `core/src/transaction_priority.rs` and `core/src/forwarding_stage.rs`, which divide "reward" by `cost.sum()`.

Existing guards do not stop this path:
- `get_write_lock_cost` and `get_signature_cost` use exact multiplication (`saturating_mul`), so they are not vulnerable to this truncation.
- `calculate_pages_for_bytes` (loaded-account-data cost) explicitly rounds *up* (adds `page_size - 1` before dividing), which is the correct anti-truncation pattern the report recommends — but this same pattern was **not** applied to `get_instructions_data_cost`. [4](#0-3) 
- `get_prioritization_fee` in `compute-budget/src/compute_budget_limits.rs` also rounds up (adds `MICRO_LAMPORTS_PER_LAMPORT - 1` before dividing) to explicitly avoid under-charging. [5](#0-4) 

No such compensating rounding exists for `get_instructions_data_cost`, so an unprivileged transaction sender can exploit the floor division deterministically and repeatably.

### Impact Explanation
This is a resource-accounting integrity issue in the cost model that Agave uses to enforce per-block and per-writable-account compute-unit budgets. Since the cost model under-accounts instruction data cost when data is spread across many small transactions rather than concentrated in one large transaction, an attacker can push more real instruction-data bytes through the network/blockstore/leader pipeline than the cost model believes it is admitting, while still fitting within `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS`. Because the mis-accounted quantity is capped at 3 CU per transaction (`INSTRUCTION_DATA_BYTES_COST` = 4), the direct per-transaction skew is small, but it scales linearly with the number of transactions an attacker submits, and it degrades the accuracy of the block-cost-based resource-exhaustion defenses that gate CPU/serialization/bandwidth work admitted per block — an unprivileged-transaction path into non-RPC resource accounting drift, not a memory-safety or funds-custody bug.

### Likelihood Explanation
Any unprivileged user can submit transactions with instruction data lengths crafted to be under `INSTRUCTION_DATA_BYTES_COST` (4 bytes) per transaction, and can do so at scale without needing any special privileges, keys, or trust relationships. The exploit requires no cooperation from validators or other peers and is fully reproducible from the SDK alone, so the likelihood of triggering the miscalculation is high; the constraining factor is only how much aggregate benefit an attacker can extract given the small per-transaction magnitude (≤3 CU) relative to other cost components (signature cost, write-lock cost, execution cost) that already dominate the total.

### Recommendation
Change `get_instructions_data_cost` (and, ideally, redefine `INSTRUCTION_DATA_BYTES_COST`'s derivation) to use rounding-up (ceiling) division consistent with `calculate_pages_for_bytes` and `get_prioritization_fee`, e.g.:

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .div_ceil(INSTRUCTION_DATA_BYTES_COST as u16)
}
```

This guarantees `cost(n) * k <= cost(k*n)` is no longer violated by splitting a payload into many sub-4-byte transactions, matching the fix pattern already used elsewhere in this same cost model (`calculate_pages_for_bytes`) and in the compute-budget crate.

### Proof of Concept
1. Build a transaction whose total instruction data across all instructions is 3 bytes (any value `< INSTRUCTION_DATA_BYTES_COST == 4`).
2. Call `CostModel::calculate_cost` on it and observe `data_bytes_cost == 0` via `get_instructions_data_cost` (`3u16 / 4u16 == 0`), confirmed by the existing test pattern in `cost-model/src/cost_model.rs` (`test_zero_bytes`, lines 911-919, demonstrates the same floor-division-to-zero behavior for the analogous `calculate_loaded_accounts_data_size_cost`/`calculate_pages_for_bytes` pair before the ceiling fix was applied there — `get_instructions_data_cost` has no equivalent ceiling fix).
3. Repeat step 1 across `N` separate transactions carrying, in total, `3*N` bytes of instruction data.
4. Compare against a single transaction carrying `3*N` bytes of instruction data in one message, whose `get_instructions_data_cost` would report `floor(3*N/4)` — a materially larger accounted cost than the `N * 0 = 0` total accounted for the split case.
5. This demonstrates that the accounted `data_bytes_cost` summed into `TransactionCost::sum()` (and thus into block cost limits and priority calculations) is strictly lower for the split-transaction strategy than for the equivalent single-transaction strategy carrying identical total instruction-data bytes.
