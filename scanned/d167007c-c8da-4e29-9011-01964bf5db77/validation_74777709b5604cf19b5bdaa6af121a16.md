### Title
Hardcoded fee-burn percentage in `Bank::burn_percent()` disregards the `fee_rate_governor.burn_percent` field that the runtime otherwise treats as mutable state - ([File: runtime/src/bank/fee_distribution.rs])

### Summary
FrankenDAO's bug is a governance-updatable multiplier (`monsterMultiplier`) that is duly changed by `setMonsterMultiplier()` but silently ignored by a separate hardcoded calculation of `stakedTimeBonus`, so the update never actually takes effect where it matters. The Agave analog is `Bank::burn_percent()` in [1](#0-0)  which is hardcoded to `solana_fee_calculator::DEFAULT_BURN_PERCENT` regardless of `self.fee_rate_governor.burn_percent`, even though `fee_rate_governor.burn_percent` is a live, mutable bank field that the runtime itself updates during feature activation.

### Finding Description
`Bank` carries a `fee_rate_governor: FeeRateGovernor` struct whose `burn_percent` field is configurable at genesis via `--fee-burn-percentage` [2](#0-1)  and is subsequently *mutated at runtime* by the bank itself during epoch-boundary feature activation, once for `pico_inflation` and once for any full-inflation feature: [3](#0-2) 

This strongly implies `fee_rate_governor.burn_percent` is meant to be the authoritative, potentially-changing source of truth for how much of the transaction fee is burned.

However, the actual fee-burn calculation used for every transaction's fee distribution never reads `self.fee_rate_governor.burn_percent` at all. It instead calls a hardcoded helper: [4](#0-3) 

The comment inside `burn_percent()` acknowledges the discrepancy directly: *"NOTE: burn percent is statically 50%, in case it needs to change in the future, burn_percent can be bank property that being passed down from bank to bank, without needing fee-rate-governor."* This mirrors the FrankenDAO bug exactly: one code path (`fee_rate_governor.burn_percent`, analogous to `monsterMultiplier` updated by `setMonsterMultiplier()`) is treated as the configurable value, while the actual economic calculation (`calculate_reward_and_burn_fee_details`, analogous to `stakedTimeBonus`) uses a separate, hardcoded constant that never consults it.

Because `fee_rate_governor.burn_percent` is exposed via serialized snapshots and RPC (`getFeeCalculator`/`rpc-client-types::response`), any deployment or code path that assumes the field reflects the actual on-chain burn behavior (e.g. tooling, explorers, capitalization audits, or future consensus logic reading `fee_rate_governor.burn_percent` to reconcile `capitalization`) will diverge from the true value that `distribute_transaction_fee_details()` uses to decrement `self.capitalization` [5](#0-4) .

### Impact Explanation
Currently `DEFAULT_BURN_PERCENT` and the genesis-default/`fee_rate_governor.burn_percent` value are both 50, so there is no live divergence in the shipped default config. But the field is user-configurable at genesis (`--fee-burn-percentage`) and machine-mutated at epoch boundaries, so any cluster operator or future feature-set change that sets `fee_rate_governor.burn_percent` to a value other than `DEFAULT_BURN_PERCENT` will silently have zero effect on the real burn/deposit split computed in `calculate_reward_and_burn_fee_details`. This is a config-vs-behavior divergence bug rather than an unprivileged remote attacker exploit: the actual runtime burn amount is deterministic and identical across all validators (since all validators run the same code), so it does not by itself cause a fork, consensus halt, or an attacker-triggerable primitive. Its impact is limited to incorrect assumptions by anything (RPC clients, capitalization reconciliation tooling, future code) that reads `fee_rate_governor.burn_percent` as ground truth.

### Likelihood Explanation
Low-to-medium: it requires a cluster to be configured with (or a future feature activation to set) `fee_rate_governor.burn_percent != DEFAULT_BURN_PERCENT`, which is possible via existing genesis tooling but does not occur with default mainnet parameters today.

### Recommendation
Either remove the now-vestigial `fee_rate_governor.burn_percent` field's implied configurability (deprecate/clearly document it as unused for fee-burn accounting) or make `Bank::burn_percent()` read `self.fee_rate_governor.burn_percent` so that genesis configuration and epoch-boundary feature updates are actually honored by `calculate_reward_and_burn_fee_details`.

### Proof of Concept
1. Build a genesis config with `--fee-burn-percentage 30` (i.e., `fee_rate_governor.burn_percent = 30`), producing `Rent`/`FeeRateGovernor` state as constructed in [2](#0-1) .
2. Run a transaction and observe fee distribution: `Bank::calculate_reward_and_burn_fee_details` still computes `burn = fee_details.transaction_fee * self.burn_percent() / 100` with `self.burn_percent()` returning the hardcoded `DEFAULT_BURN_PERCENT` (50), not the configured 30, as shown in [6](#0-5) .
3. Compare `bank.fee_rate_governor.burn_percent` (30) against the actual capitalization delta from `distribute_transaction_fee_details()` [5](#0-4)  — the real burn will always reflect 50%, confirming the configured/reported value is never consulted by the calculation, exactly paralleling the FrankenDAO `monsterMultiplier`/`stakedTimeBonus` disconnect.

    pub fn calculate_reward_and_burn_fee_details(
        &self,
        fee_details: &CollectorFeeDetails,
    ) -> FeeDistribution {
        let burn = fee_details.transaction_fee * self.burn_percent() / 100;
        let deposit = fee_details
            .priority_fee
            .saturating_add(fee_details.transaction_fee.saturating_sub(burn));
        FeeDistribution { deposit, burn }
    }

    const fn burn_percent(&self) -> u64 {

        solana_fee_calculator::DEFAULT_BURN_PERCENT as u64
    }
