The Unlock Protocol bug (`PublicLock.initialize()` lacking access control, allowing anyone to front-run the legitimate initializer and force costly redeployment) maps to a real Agave analog in the System Program's nonce-account initialization path.

### Title
`InitializeNonceAccount` lacks a signer/ownership check, allowing an attacker to front-run initialization of a system-owned account and seize control of its nonce authority - (File: `programs/system/src/system_processor.rs`, `programs/system/src/system_instruction.rs`)

### Summary
`SystemInstruction::InitializeNonceAccount` transitions a nonce account from `State::Uninitialized` to `State::Initialized`, permanently binding a `nonce_authority` to the account. Unlike every other privileged system instruction (`Allocate`, `Assign`, `WithdrawNonceAccount`, `AuthorizeNonceAccount`), neither the processor dispatch nor the `initialize_nonce_account` helper requires the account (or its creator) to be a transaction signer.

### Finding Description
In `system_processor.rs`, the dispatch for `InitializeNonceAccount` only borrows the account and checks the `RecentBlockhashes`/`Rent` sysvars before calling `initialize_nonce_account`, with no signer set membership check: [1](#0-0) 

The helper itself only validates that the account is writable and currently `Uninitialized` before writing arbitrary caller-supplied `nonce_authority` state — again, no `signers` parameter is consulted: [2](#0-1) 

Contrast this with `withdraw_nonce_account`, which explicitly requires a signer check (`check_signer`) before allowing any state transition on the same account type: [3](#0-2) 

and with `allocate`/`assign`, which both require `address.is_signer(signers)`: [4](#0-3) 

This mirrors the Unlock finding exactly: `PublicLock.initialize()` had no access control gating who could call it first, so an attacker could front-run the legitimate deployer's initialization call and force the creator into costly redeployment/loss. Here, `InitializeNonceAccount` has the identical missing-authorization pattern — any account that is system-owned, has zero/uninitialized nonce data, and is rent-exempt can be initialized by *any* transaction, regardless of who created or funds it.

### Impact Explanation
Nonce accounts are typically created via `SystemInstruction::CreateAccount` (signed by the new account's keypair) in one transaction, then initialized via `InitializeNonceAccount` in a subsequent instruction/transaction. Because `InitializeNonceAccount` requires no signature from the account or its intended owner, an attacker who observes the pending `CreateAccount` (or any account sitting in the system-owned `Uninitialized` nonce state — including a zero-balance nonce account whose funds were fully withdrawn back to `Uninitialized` per `withdraw_nonce_account`'s zero-remaining-balance path) can submit `InitializeNonceAccount` first and bind an arbitrary `nonce_authority` of their choosing. Once initialized, only that attacker-controlled authority can call `AuthorizeNonceAccount` or `WithdrawNonceAccount` to reclaim control or funds, permanently locking the legitimate owner out of the rent-exempt lamports deposited into the account and forcing them to abandon it — directly analogous to the fund loss/forced redeployment described in the Unlock report.

### Likelihood Explanation
Exploitation requires no special privileges — any unprivileged network participant can submit a competing transaction containing `InitializeNonceAccount` targeting a known, not-yet-initialized nonce account address. The race window exists whenever `CreateAccount` and `InitializeNonceAccount` are not atomically bundled in the same transaction (which is not enforced by the protocol), or whenever a nonce account transiently returns to `Uninitialized` after a full withdrawal.

### Recommendation
Require the target nonce account (or a designated creator/authority) to be a signer of the `InitializeNonceAccount` instruction, mirroring the signer checks already present in `withdraw_nonce_account`, `allocate`, and `assign`, so that only the legitimate creator can transition the account out of `Uninitialized`.

### Proof of Concept
1. Attacker monitors the network for a `CreateAccount` transaction creating a new system-owned account with nonce-account space/rent-exemption (or observes a nonce account return to `Uninitialized` via full withdrawal).
2. Before the legitimate owner's `InitializeNonceAccount` transaction lands, attacker submits their own `InitializeNonceAccount` instruction targeting the same account pubkey, specifying an attacker-controlled `nonce_authority` — validated only by `initialize_nonce_account` in [5](#0-4)  which performs no signer/ownership check.
3. The account is now `Initialized` with the attacker's authority; the legitimate owner's later `InitializeNonceAccount` call fails with `InstructionError::InvalidAccountData` (already `Initialized`), and only the attacker can subsequently `AuthorizeNonceAccount`/`WithdrawNonceAccount`, locking the rent-exempt lamports away from the original depositor.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
