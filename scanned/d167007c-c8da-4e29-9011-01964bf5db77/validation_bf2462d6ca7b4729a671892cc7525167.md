## Analysis

The report's bug class is: **a value is computed and “locked in” at an early phase, then compared against a value recomputed later from live/mutated state; because the two computations use different state snapshots, an invariant check that assumes consistency fails.** In the Harmonix contract this caused a benign DoS (`require` revert). The Agave analog reproduces the identical pattern in the **partitioned epoch-rewards distribution pipeline**, but the failing check is a Rust `assert_eq!` rather than a `require`, so the failure mode is a **deterministic panic (validator crash / consensus halt)** instead of a recoverable revert.

### The two phases

1. **Calculation phase** (`calculate_stake_rewards_and_commissions`, invoked once at the epoch boundary) reads each stake account's delegation from a `StakesCache` snapshot and produces a `PartitionedStakeReward` per account, recording:
   - `inflation.stake_reward` – the reward computed from the delegation observed *at calculation time*.
   - `inflation.stake.delegation.stake` – the *expected* post-reward delegation (`old_delegation + stake_reward`), baked in at calculation time. [1](#0-0) 

2. **Distribution phase** happens over many subsequent blocks (one partition per block). For each account in the partition, `build_updated_stake_reward` re-fetches the **current, live** stake account from `stakes_cache_accounts` (the bank's present-day `StakesCache`, not a snapshot from calculation time) and validates consistency with an assertion:

```rust
let expected_delegation = stake.delegation.stake
    .saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(
    expected_delegation, new_stake.delegation.stake,
    "stake reward delegation must be consistent with the updated stake account \
     lamport balance"
);
``` [2](#0-1) 

This branch is taken whenever `adjust_delegations_for_rent` (gated by the `relax_post_exec_min_balance_check` feature) is **false**: [3](#0-2) 

### Why the check can fail

`stake.delegation.stake` here is read from the bank's *current* `StakesCache`, while `partitioned_stake_reward.inflation.stake_reward` / `.inflation.stake.delegation.stake` were fixed at the epoch-boundary calculation. If the stake account's delegation changes between those two points — e.g. the stake owner submits an ordinary, unprivileged `Split`, `Merge`, `Withdraw`, or `Deactivate` instruction that lands in a block during the multi-block distribution window, before that particular account's partition is processed — then `stake.delegation.stake` (current) no longer equals the delegation value assumed at calculation time, and `expected_delegation != new_stake.delegation.stake`.

The code comment next to the calling function claims this can't happen ("further state mutation prevents by stake-program restrictions, there should never be rewards burned"), but no such restriction exists in the stake program: a `grep` for `EpochRewardStatus`/`epoch_reward_status` in any stake-program file returns zero matches, and the only `RewardInterval`/`get_reward_interval` helper that exists is a `#[cfg(test)]`-only helper inside `runtime/src/bank/partitioned_epoch_rewards/mod.rs`, not code wired into stake-instruction processing. [4](#0-3) [5](#0-4) 

Because block processing is deterministic and executed identically by every validator, hitting this `assert_eq!` panics the process for the whole cluster simultaneously — a consensus-halting crash, not merely a single-node degradation.

### Title
Stale delegation snapshot causes `assert_eq!` panic in partitioned epoch-reward distribution — ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` compares a stake account's delegation as it exists at *distribution time* (read live from `StakesCache`) against a delegation value that was computed and frozen at *calculation time* (epoch boundary). If the account's delegation changes in between — via ordinary stake-owner instructions executed in blocks that fall inside the multi-block distribution window — the two values diverge and the assertion panics, crashing the bank/validator process deterministically across the cluster.

### Finding Description
The reward pipeline splits into two temporally separated phases: `calculate_stake_rewards_and_commissions` (run once, at the epoch boundary, over a `StakesCache` snapshot) and `store_stake_accounts_in_partition`/`build_updated_stake_reward` (run incrementally, once per block, over many subsequent blocks, reading the *live* `StakesCache`). When the `relax_post_exec_min_balance_check` feature is not active, distribution code enforces via `assert_eq!` that the current delegation plus the pre-computed reward equals the pre-computed expected new delegation. Nothing in the stake program (verified by absence of any `EpochRewardStatus` reference outside test helpers) prevents ordinary stake instructions from mutating `delegation.stake` for accounts still awaiting distribution. The invariant therefore assumes state immutability across a window where mutability is actually possible.

### Impact Explanation
An `assert_eq!` panic in bank/runtime code executed during normal block replay is not a recoverable transaction error — it aborts the validator process. Since every honest validator processes the same block deterministically, all validators that reach this code path panic identically and simultaneously, producing a network-wide consensus halt rather than an isolated crash. This is far more severe than the original report's fund-lock DoS.

### Likelihood Explanation
Likelihood depends on: (1) the `relax_post_exec_min_balance_check` feature being inactive (the assert branch is only reached when this feature is off), and (2) a stake owner performing a normal Split/Merge/Withdraw/Deactivate on their own delegated stake account during the epoch's multi-block reward-distribution window before their account's partition is processed. Both conditions are plausible under normal operation — no malicious validator, admin, or trusted process is required, only a regular unprivileged stake-account owner acting during an unlucky window. I was not able to fully confirm from local code whether this feature is active on current mainnet-beta, nor exhaustively trace every stake-instruction code path to rule out an equivalent guard elsewhere; this should be verified with a live/replay test.

### Recommendation
Do not compare a live-state delegation value against one computed from a stale, calculation-time snapshot with a hard `assert_eq!`. Either (a) always take the `adjust_delegations_for_rent` code path (which tolerates and reconciles balance/delegation drift instead of asserting), or (b) snapshot the exact stake-account state to be mutated during calculation and reuse that captured value at distribution time instead of re-reading current `StakesCache` state, or (c) replace the panic with a graceful degrade (skip/burn that one reward, as already done in the `Err` branch) instead of an unconditional `assert_eq!`.

### Proof of Concept
Not independently reproduced by execution; derived from local code inspection:
1. At an epoch boundary, `calculate_stake_rewards_and_commissions` computes and freezes `PartitionedStakeReward` entries, including account `A`'s expected new delegation `D0 + reward`. [6](#0-5) 
2. Distribution is spread across multiple subsequent blocks; account `A`'s partition is not processed on the first block. [7](#0-6) 
3. Before `A`'s partition block, the stake owner of `A` submits an authorized `Split` instruction moving part of the stake to a new account, changing `A`'s live `delegation.stake` to `D0 - X` in `StakesCache`.
4. When `A`'s partition is finally processed, `build_updated_stake_reward` computes `expected_delegation = (D0 - X) + reward`, which no longer equals the frozen `new_stake.delegation.stake = D0 + reward`, tripping the `assert_eq!` and panicking the bank during normal block execution. [8](#0-7)
