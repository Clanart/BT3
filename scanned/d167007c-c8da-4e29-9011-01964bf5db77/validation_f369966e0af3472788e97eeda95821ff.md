Based on my investigation, I found a genuine Agave analog to this bug class: unrestricted, unprivileged deposits into a pooled-reward account that get retroactively distributed pro-rata to stakers, allowing a last-moment depositor/staker to capture yield they didn't earn.

### Title
Unauthorized/unbonded delegator can front-run `pending_delegator_rewards` distribution by staking just before the epoch boundary - (`File: programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`deposit_delegator_rewards` (SIMD-0123) lets **any signer** transfer lamports into a vote account and increment `pending_delegator_rewards` with no restriction on who deposits or when. [1](#0-0) 
This pool of pending rewards is later distributed to delegators as `block_reward` during epoch-boundary reward calculation, computed from the *current* stake delegation snapshot rather than from stake that was active while the revenue was earned. [2](#0-1) 
This mirrors the Astaria `WithdrawProxy`/`ERC4626Cloned` issue: a pooled-yield account accepts unrestricted deposits and pays out yield to whoever holds "shares" (here, stake) at redemption time, regardless of whether they contributed capital/risk during the period that generated the yield.

### Finding Description
`deposit_delegator_rewards` performs only a signer check on the source account — there is no check that the depositor is the vote account's validator, an authorized party, or even a delegator to that vote account: [3](#0-2) 
It then unconditionally CPIs a System transfer and calls `add_pending_delegator_rewards`, incrementing a single pooled counter on the vote account with no per-depositor bookkeeping, timestamp, or lock-up: [4](#0-3) 

At the epoch reward boundary, `calculate_block_reward` reads this pooled value and allocates it across current stake delegations to that vote account, gated only by `block_revenue_sharing` feature and computed from `stake_account.delegation()` at reward-calculation time: [2](#0-1) 

Because delegation activation in Agave/Solana only requires stake to be delegated (it can even be within the same or a very recent epoch depending on warm-up rules), and because `deposit_delegator_rewards` has no cooldown or minimum holding period before the pool is drained, an attacker can:
1. Observe that a vote account is about to have (or already has) a large `pending_delegator_rewards` balance about to be distributed at the epoch boundary.
2. Delegate a large stake to that vote account just before the reward-calculation snapshot.
3. Receive a share of `block_reward` proportional to their newly-delegated stake even though they held no economic exposure during the period the revenue was actually earned/deposited.
4. Undelegate/withdraw immediately after, capturing yield "on demand" exactly as described in the Astaria report — diluting the payout to delegators who were actually staked/at-risk during the relevant period.

This is analogous to the root cause in the Astaria bug: a shared, unrestricted deposit/reward pool whose payout is determined by *current* balance/share ownership rather than ownership *during the yield-generating period*, with no guard (the Astaria fix was to make `afterDeposit` revert to block public deposits/mints; here there is no equivalent guard preventing "yield-on-demand" via last-minute stake reallocation against the pooled `pending_delegator_rewards`).

### Impact Explanation
Delegators who bore the risk/lock-up during the period corresponding to the pooled rewards receive a diluted share, while a party who delegates only immediately before the distribution snapshot captures rewards without commensurate exposure. This is a fund-loss/fund-misdirection issue affecting the runtime's stake-reward accounting (an unprivileged, non-malicious-validator actor can exploit ordinary staking flows), matching the "fund theft/loss" impact category for the `runtime`/`accounts`/built-ins area.

### Likelihood Explanation
Exploitation only requires ordinary permissionless actions available to any staker: delegating stake to a targeted vote account timed near an epoch boundary where `pending_delegator_rewards` is known to be non-trivial (which is observable on-chain from the vote account's SIMD-0123 field). No validator collusion, leaked keys, or privileged access is required, making this a plausible unprivileged, low-effort strategy, though it depends on the size of `pending_delegator_rewards` and stake-activation/warm-up timing relative to the reward snapshot — I was not able to fully verify within this session whether warm-up-rate delays effectively prevent same-epoch-delegation share capture, since I could not inspect `calculate_activated_stake`'s exact warm-up gating for `block_revenue_sharing` in relation to `distribution_epoch_vote_accounts` filtering.

### Recommendation
Snapshot delegations for `block_reward` distribution using the vote/stake state as of the epoch(s) during which the corresponding `pending_delegator_rewards` were deposited (or require a minimum stake-activation age before a delegation is eligible for pooled block-revenue rewards), analogous to the Astaria fix of blocking unrestricted deposit/mint paths into the yield pool. Concretely, gate `calculate_block_reward` to use `cached_vote_accounts`/stake snapshots captured at deposit time, or require deposits to be attributed to specific delegators/epochs rather than pooled anonymously.

### Proof of Concept
1. Vote account `V` accumulates `pending_delegator_rewards` via repeated `deposit_delegator_rewards` calls (open to any signer) — [5](#0-4) .
2. Shortly before the epoch's reward-calculation snapshot, attacker `A` (previously undelegated) delegates a large stake amount to `V`.
3. At epoch boundary, `calculate_stake_rewards_and_commissions` computes `calculate_block_reward` per delegation using the then-current `stake_account.delegation()` and `cached_vote_accounts.distribution_epoch_vote_accounts` — [2](#0-1) .
4. `A` receives a proportional share of `V`'s pooled `pending_delegator_rewards` as `block_reward`, credited via `store_stake_accounts_in_partition`/`build_updated_stake_reward` — [6](#0-5) .
5. `A` then deactivates/withdraws the stake, having captured yield without bearing risk during the period the deposits were actually earned — mirroring the Astaria "deposit/mint to Withdraw proxy right before distribution, redeem right after" exploit pattern.

**Note on uncertainty:** I could not fully confirm within available tool calls whether Agave's existing stake warm-up/cooldown mechanics (`new_warmup_cooldown_rate_epoch`, `calculate_activated_stake`) fully neutralize this specific timing window for `block_revenue_sharing` rewards specifically (as opposed to inflation rewards). If warm-up delays are enforced strictly enough for freshly delegated stake before it counts toward `block_reward` calculation, the practical exploit window may be narrower than described. A Devin session with fuller repo access would be needed to trace `calculate_activated_stake`'s interaction with `distribution_epoch_vote_accounts` filtering to close this gap definitively.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
