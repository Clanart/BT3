### Title
`BankWithSchedulerInner::with_active_scheduler` can panic while holding the scheduler's write lock, poisoning it and permanently disabling transaction scheduling for the bank - (File: runtime/src/installed_scheduler_pool.rs)

### Summary
The IC bug is a "lock held across a fallible/panicking operation" defect: a global write lock is taken, an operation that can panic is performed while the lock is held, and the panic leaves the lock permanently unusable, making the canister perpetually unresponsive. The Agave analog is `BankWithSchedulerInner::with_active_scheduler` in `runtime/src/installed_scheduler_pool.rs`, which acquires a `std::sync::RwLock` write guard on `self.scheduler` and then calls `.unwrap()` on an `Option` returned by `pool.take_resumed_scheduler(...)` while still holding that write lock.

### Finding Description
`with_active_scheduler` is the entry point used every time a bank needs to submit work to its installed scheduler [1](#0-0) . When the scheduler state is `SchedulerStatus::Stale`, the code takes a *write* lock on `self.scheduler` and, still holding that lock, invokes a closure that calls `pool.take_resumed_scheduler(context, result_with_timings).unwrap()`: [2](#0-1) 

If `take_resumed_scheduler` ever returns `None` (e.g., because the pool cannot resume/spawn a scheduler for the given context), this `.unwrap()` panics while the `RwLock` write guard (`scheduler` at line 533) is still on the stack. In `std::sync::RwLock`, a panic while a guard is held poisons the lock, so every subsequent `self.scheduler.read().unwrap()` or `self.scheduler.write().unwrap()` call anywhere else in the codebase will itself panic on the poisoned `Result`.

Critically, `with_active_scheduler` is not the only caller that assumes the lock is healthy — most other call sites in the same file use `self.scheduler.read().unwrap()` / `.write().unwrap()` directly, e.g. the initial read at line 513, `retrieve_error_after_schedule_failure` [3](#0-2) , and `wait_for_scheduler_termination` [4](#0-3) . Only one call site, the timeout-listener callback, defensively checks for poisoning and no-ops instead of panicking: [5](#0-4) 

This asymmetry mirrors the IC report exactly: one code path silently tolerates a broken/locked state (analogous to the "read lock can still succeed" case in the report), while the hot paths (`with_active_scheduler`, `retrieve_error_after_schedule_failure`, `wait_for_scheduler_termination`) will panic again on `.unwrap()` the moment they touch the poisoned lock — meaning the bank is left in a permanently unusable scheduling state, just like the cycles minting canister becoming perpetually unresponsive once its global-state lock was left held/poisoned across a panic.

### Impact Explanation
If the write lock guarding `BankWithSchedulerInner::scheduler` is poisoned by a panic inside the critical section (e.g., the `.unwrap()` on `take_resumed_scheduler`'s `Option`, or any panic surfacing from `transition_from_stale_to_active`'s closure), every later attempt by the validator to schedule, unwind errors from, or terminate the scheduler for that bank will itself panic when it calls `.read().unwrap()`/`.write().unwrap()` on the poisoned lock. Because these functions are on the hot path for transaction execution and bank teardown (`BankForks` shutdown, `wait_for_termination`), this would repeatedly crash the validator process attempting to make progress on that bank, which is consistent with a non-RPC remote/local crash and consensus-halt-adjacent impact rather than a benign one-off panic.

### Likelihood Explanation
The likelihood of actually triggering the `None` branch of `take_resumed_scheduler` depends on the internal implementation of the unified scheduler pool (I was not able to fully confirm the conditions under which `take_resumed_scheduler`/`do_take_resumed_scheduler` returns `None` before running out of tool iterations), so I cannot assert this is trivially reachable by an ordinary user-submitted transaction. The pattern itself — an `.unwrap()` on a fallible operation performed while a write lock is held, in a place that the same file's authors elsewhere treat as poison-prone (see the explicit poisoned-lock check in the timeout listener) — is a genuine, low-difficulty-to-spot structural weakness mirroring the report's bug class, but confirming an unprivileged trigger path requires inspecting `unified-scheduler-pool/src/lib.rs`'s `take_resumed_scheduler`/`do_take_resumed_scheduler` implementation, which I could not fully retrieve in the available turns.

### Recommendation
- Avoid panicking while holding `self.scheduler`'s write lock: replace the `.unwrap()` on `take_resumed_scheduler`'s result with an explicit error path that degrades gracefully (e.g., transition to `SchedulerStatus::Unavailable` with a recorded error) rather than unwinding through the write guard.
- Audit all `self.scheduler.read()/write().unwrap()` call sites in `runtime/src/installed_scheduler_pool.rs` and make them consistently poison-tolerant, matching the defensive pattern already used in `do_create_timeout_listener`.
- Long term, consider whether critical per-bank locks like this one should use a poison-recovering primitive (e.g., `parking_lot::RwLock`, which does not poison) for state that must remain usable even after a bug causes a panic inside a critical section.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the exact `None`-returning condition of `take_resumed_scheduler` within the remaining tool budget. The structural PoC is:
1. Drive a bank's scheduler into `SchedulerStatus::Stale`.
2. Trigger a call path that invokes `with_active_scheduler`, causing entry into the `Stale` branch and acquisition of the `scheduler.write()` lock at [6](#0-5) .
3. Cause `pool.take_resumed_scheduler(context, result_with_timings)` to return `None` (condition not fully confirmed from local code in this session), triggering the `.unwrap()` panic at [7](#0-6)  while the write guard is alive.
4. Observe that any subsequent call into `with_active_scheduler`, `retrieve_error_after_schedule_failure`, or `wait_for_scheduler_termination` for that same bank now panics again on the poisoned `RwLock`.

Given the uncertainty in step 3, I recommend a follow-up Devin session with full repository access to inspect `unified-scheduler-pool/src/lib.rs::take_resumed_scheduler`/`do_take_resumed_scheduler` and confirm whether an unprivileged caller can reach the `None` branch, before treating this as a confirmed exploitable finding rather than a structural analog.
