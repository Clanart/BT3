Based on my research, I found a concrete Agave analog in the precompile signature-verification path.

### Title
Precompile signature-verification loops (`secp256k1`/`ed25519`/`secp256r1`) run to completion with no per-iteration compute metering, letting a fixed per-signature cost estimate diverge from real CPU work - ([File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, precompiles/src/secp256r1.rs])

### Summary
The Morpho report's broken invariant is: a loop bound (`maxIterations`) is charged/accounted at a flat estimated cost per iteration, but the loop actually runs to completion regardless of whether real work diverges from that estimate, and no per-iteration checkpoint can abort it early. The Agave analog is the precompile verification loops for `secp256k1`, `ed25519`, and `secp256r1` instructions. Each loops `0..num_signatures` (attacker-controlled, up to 255) doing expensive cryptographic work per iteration, but unlike every other piece of code in the SVM execution path, these loops never call `compute_meter.consume_checked(...)` — they run entirely outside the compute-budget-metered VM, during `bank.verify_transaction` / `verify_if_precompile`, before the transaction even enters the SVM.

### Finding Description
`verify_if_precompile` in [1](#0-0)  dispatches to `secp256k1::verify`, `ed25519::verify`, or `secp256r1::verify` based on the precompile's program id. These are called from `Bank::verify_transaction` in `TransactionVerificationMode::HashAndVerifyPrecompiles` mode, i.e. before compute-budget accounting or SVM execution begins, as shown by the conformance harness call site [2](#0-1) .

Each verify function loops over `num_signatures` (an attacker-controlled `u8`, so up to 255) and does real cryptographic work per iteration with no `compute_meter` interaction at all:
- `secp256k1::verify` performs a `libsecp256k1::recover` (ECDSA public-key recovery) plus a keccak hash per iteration [3](#0-2) .
- `ed25519::verify` performs `ed25519_dalek` strict signature verification per iteration [4](#0-3) .
- `secp256r1::verify` performs OpenSSL `BigNum`/`EcPoint`/ECDSA verification (including a SHA-256 digest) per iteration [5](#0-4) .

Compare this with every genuine SVM syscall/builtin, which is gated by `invoke_context.compute_meter.consume_checked(cost)` before or during work is performed, e.g. the hashing syscall explicitly checks cost per slice inside its loop [6](#0-5) , or curve operations charge `consume_checked` immediately before doing the point math [7](#0-6) . Precompiles have no equivalent guard.

The only "cost" associated with these operations is a flat per-signature estimate used purely for the cost model/scheduling (block cost limits, fee estimation), not as a real-time cutoff during verification itself: [8](#0-7)  and [9](#0-8) . This is exactly the Morpho pattern: the "iteration count" parameter (here, `num_signatures`, up to 255, times up to 3 precompile instructions per transaction) is charged at a fixed unit price but the actual work performed is not truncated or checked against that budget — it always runs to completion.

### Impact Explanation
Because verification is unmetered and unconditional, an attacker can craft transactions that maximize real cryptographic work relative to the assumed flat cost, particularly for `secp256r1` which invokes OpenSSL BigNum/EC-group/ECDSA machinery (heavier per-call than the raw `libsecp256k1`/`ed25519_dalek` primitives used for the other two, yet priced comparably in the cost model: `SECP256R1_VERIFY_COST` = 160*30 vs `SECP256K1_VERIFY_COST` = 223*30). A leader/validator processing a block full of such transactions spends CPU time proportional to real crypto cost rather than the assumed budget used for block-cost/scheduling limits, degrading transaction-processing throughput for all validators that must replay the block — a non-RPC, remote, low-privilege resource-exhaustion/degradation vector, since it requires no special role and is triggered purely by submitting ordinary (fee-paying) transactions.

### Likelihood Explanation
Likelihood is limited by the fact that both `num_signatures` (max 255) and per-signature message/offset sizes are bounded by overall transaction size limits, and by the fee/cost-tracker mechanism that still limits how many such transactions fit in a block by the (possibly underestimated) flat cost. This makes the finding a genuine metering gap rather than an unbounded/catastrophic primitive, and the actual magnitude of any real-vs-assumed cost divergence would need empirical benchmarking of the OpenSSL path vs the flat `SECP256R1_VERIFY_COST` to establish severity, similar to the "stress testing" recommendation in the original Morpho report.

### Recommendation
Add per-iteration `compute_meter`-equivalent accounting (or equivalent early-abort gating) inside `secp256k1::verify`, `ed25519::verify`, and `secp256r1::verify` so real cryptographic cost cannot exceed the estimate charged by the cost model, and re-benchmark `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` against actual measured cost (especially the OpenSSL-based `secp256r1` path) to ensure the flat per-signature costs are conservative upper bounds rather than optimistic averages.

### Proof of Concept
1. Construct a transaction containing a `secp256r1_program` instruction with `num_signatures = 255` and offsets/instruction indices pointing at maximal-size message data within the transaction's own instruction data.
2. Submit many such transactions concurrently to a leader.
3. Measure wall-clock time spent in `Precompile::verify` (`secp256r1::verify`) via profiling versus the CU-equivalent time assumed by `SECP256R1_VERIFY_COST * 255` in the cost model, to demonstrate divergence between charged cost and real cost, none of which is checked or capped inside the verification loop itself (no `consume_checked` calls exist in `precompiles/src/secp256r1.rs`, `precompiles/src/secp256k1.rs`, or `precompiles/src/ed25519.rs`).

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}

            offsets.signature_instruction_index,
            offsets.signature_offset,

            offsets.public_key_instruction_index,
            offsets.public_key_offset,
            COMPRESSED_PUBKEY_SERIALIZED_SIZE,

        // Parse out message
        let message = get_data_slice(

            instruction_datas,
            offsets.message_instruction_index,
            offsets.message_data_offset,
            offsets.message_data_size as usize,
        )?;

        let r_bignum = BigNum::from_slice(&signature[..FIELD_SIZE])
            .map_err(|_| PrecompileError::InvalidSignature)?;
        let s_bignum = BigNum::from_slice(&signature[FIELD_SIZE..])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Check that the signature is generally in range
        let within_range = r_bignum >= one
            && r_bignum <= order_minus_one
            && s_bignum >= one
            && s_bignum <= half_order;

        if !within_range {
            return Err(PrecompileError::InvalidSignature);
        }

        // Create an ECDSA signature object from the ASN.1 integers
        let ecdsa_sig = openssl::ecdsa::EcdsaSig::from_private_components(r_bignum, s_bignum)
            .and_then(|sig| sig.to_der())
            .map_err(|_| PrecompileError::InvalidSignature)?;

        let public_key_point = EcPoint::from_bytes(&group, pubkey, &mut ctx)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key = EcKey::from_public_key(&group, &public_key_point)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key_as_pkey =
            PKey::from_ec_key(public_key).map_err(|_| PrecompileError::InvalidPublicKey)?;

        let mut verifier =
            Verifier::new(openssl::hash::MessageDigest::sha256(), &public_key_as_pkey)
                .map_err(|_| PrecompileError::InvalidSignature)?;
        verifier
            .update(message)
            .map_err(|_| PrecompileError::InvalidSignature)?;

        if !verifier
            .verify(&ecdsa_sig)
            .map_err(|_| PrecompileError::InvalidSignature)?
        {
            return Err(PrecompileError::InvalidSignature);
        }
    }
    Ok(())
