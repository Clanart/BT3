Based on the code I was able to examine, there is a strong Agave analog to the ERC-20 "replace instead of increase/decrease" allowance problem: the vote account **commission-update mechanism**, where a value that gates fund extraction from delegators is *replaced* rather than protected by both of the safeguards the legacy path relies on.

### Title
Vote-account `UpdateCommissionBps` (SIMD-0291) removes the epoch-timing anti-frontrunning guard used by the legacy commission path, enabling a commission spike/revert to extract excess stake rewards - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The legacy `UpdateCommission` instruction sets the vote account's commission by direct replacement (`vote_state.set_commission(commission)`), and Solana historically suffered a real fund-theft class where a validator's withdraw authority spiked commission to near 100% for a short window (to capture a disproportionate share of rewards) and then reverted it, hurting delegators who did not react in time. That was fixed by `is_commission_update_allowed`, which restricts commission *increases* to the first half of an epoch [1](#0-0) , enforced inside `update_commission` [2](#0-1) . The newer `UpdateCommissionBps` instruction (SIMD-0291) removes this timing check entirely - the code comment literally says "No commission update rule, per SIMD-0249 and SIMD-0291" [3](#0-2) , and a dedicated test confirms updates are "always allowed regardless of epoch position" [4](#0-3) .

### Finding Description
The design intent is that removing the epoch-half restriction is safe because `delay_commission_updates` makes the *effective* commission used for reward distribution lag by a full epoch. That delayed-snapshot logic is implemented for the inflation-rewards commission path: `redeem_delegation_rewards` looks up the commission from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` instead of the live vote state when `delay_commission_updates` is active [5](#0-4) . `VoteInstruction::UpdateCommissionBps` for `CommissionKind::InflationRewards` is gated so it can only run once `delay_commission_updates` is enabled [6](#0-5) , which is consistent with that protection.

However, `UpdateCommissionBps` also accepts `CommissionKind::BlockRevenue` (SIMD-0123/SIMD-0291), and `update_commission_bps` applies the *same unconditional, no-timing-check write* to `block_revenue_commission_bps` for that kind [7](#0-6) , [8](#0-7) . From what I could verify, block-revenue reward distribution reads commission from `distribution_epoch_vote_accounts` (the live/current vote account view), via `calculate_block_reward`, rather than the delayed `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` mechanism built specifically for the inflation-rewards path [9](#0-8) . I was not able to fully trace `calculate_block_reward`'s internals in the time available, so I could not conclusively confirm whether it independently re-implements an equivalent one-epoch delay for `block_revenue_commission_bps`; this is the key open question for confirming exploitability.

If block-revenue commission is indeed consumed without a delay, the broken invariant is: **the value gating what fraction of stakers' block-revenue rewards go to the operator is replaced in place with no rate-limiting and no delayed effect**, exactly the ERC-20 `_approve`-style "set, don't delta/guard" pattern the external report describes. A withdraw authority could raise `block_revenue_commission_bps` to a high value immediately before a reward/revenue distribution event that uses the live vote state, then lower it back afterward, extracting more of the delegators' revenue share than they agreed to when delegating - a within-epoch "front-run and revert" comparable to the legacy commission scam this same file was patched to prevent for the inflation-rewards path.

### Impact Explanation
If the delay protection does not equally apply to `block_revenue_commission_bps`, this allows fund theft from staking delegators: a validator operator can transiently claim a much larger share of block-revenue rewards than delegators expect, then quietly restore the advertised commission, repeating this every distribution cycle. This falls within the valid impact category of "fund theft/loss" via a built-in program (`programs/vote`) instruction with no external/trusted-node assumption beyond the vote account's own withdraw authority, which is a normal, expected transaction signer for this instruction (not a "malicious peer/validator/consensus" bypass).

### Likelihood Explanation
Likelihood cannot be finalized without confirming the exact commission-read path used for `BlockRevenue` distribution. The instruction path itself is trivially and repeatably triggerable by any vote account's authorized withdrawer with ordinary transactions, and the code comment explicitly states there is no timing restriction for this instruction, which is the exact precondition needed for the attack. The uncertainty is confined to whether `calculate_block_reward`/its dependencies apply an equivalent one-epoch delay elsewhere in code I did not retrieve.

### Recommendation
Verify whether `calculate_block_reward` (and any other consumer of `block_revenue_commission_bps`) resolves commission via a delayed epoch-snapshot analogous to the `InflationRewards` path in `redeem_delegation_rewards`. If it uses the live vote state instead, apply the same delayed-commission (or epoch-half timing) protection to `CommissionKind::BlockRevenue` updates in `update_commission_bps` and `UpdateCommissionBps` handling, so an operator cannot instantaneously spike and revert the commission used for revenue distribution within the same epoch.

### Proof of Concept
Not constructed - full confirmation requires reading the implementation of `calculate_block_reward` and its call sites, which I could not retrieve within the available tool budget. The PoC skeleton would be: (1) attacker sends `UpdateCommissionBps{commission_bps: 10000, kind: BlockRevenue}` immediately before a block-revenue distribution event for their vote account; (2) reward/commission split occurs using the spiked value if it is read live; (3) attacker immediately sends `UpdateCommissionBps{commission_bps: <normal>, kind: BlockRevenue}` to restore the advertised rate, as demonstrated functionally (without the exploit framing) in `test_vote_update_commission_bps` and `test_update_commission_bps` [10](#0-9) .

**Caveat:** Given the inability to fully verify the `calculate_block_reward` commission-resolution logic, I cannot state with full confidence that this is exploitable as described - the finding is reported as the strongest candidate found, but I recommend a Devin session with full file access to trace `calculate_block_reward` before treating this as confirmed.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}

    #[test]
    fn test_vote_update_commission_bps() {
        // Test UpdateCommissionBps instruction (SIMD-0291).
        let (vote_pubkey, _authorized_voter, authorized_withdrawer, vote_account) =
            create_test_account_with_authorized();

        let transaction_accounts = vec![
            (vote_pubkey, vote_account.clone()),
            (authorized_withdrawer, AccountSharedData::default()),
        ];

        let instruction_accounts = vec![
            AccountMeta {
                pubkey: vote_pubkey,
                is_signer: false,
                is_writable: true,
            },
            AccountMeta {
                pubkey: authorized_withdrawer,
                is_signer: true,
                is_writable: false,
            },
        ];

        let features = VoteProgramFeatures::all_enabled();

        let get_commission_bps = |vote_account: &AccountSharedData, kind: &CommissionKind| {
            let vote_state = deserialize_vote_state_for_test(vote_account.data(), &vote_pubkey);
            match kind {
                CommissionKind::InflationRewards => {
                    vote_state.as_ref_v4().inflation_rewards_commission_bps
                }
                CommissionKind::BlockRevenue => vote_state.as_ref_v4().block_revenue_commission_bps,
            }
        };

        let original_commission_bps =
            get_commission_bps(&vote_account, &CommissionKind::InflationRewards);

        let commission_bps = 200; // 2%

        for kind in [
            CommissionKind::InflationRewards,
            CommissionKind::BlockRevenue,
        ] {
            let other_kind = match kind {
                CommissionKind::InflationRewards => CommissionKind::BlockRevenue,
                CommissionKind::BlockRevenue => CommissionKind::InflationRewards,
            };

            // Get the original commission for the other kind.
            let original_other_commission_bps = get_commission_bps(&vote_account, &other_kind);

            let instruction_data = serialize(&VoteInstruction::UpdateCommissionBps {
                commission_bps,
                kind: kind.clone(),
            })
            .unwrap();

            // Should pass.
            let accounts = process_instruction(
                features,
                &instruction_data,
                transaction_accounts.clone(),
                instruction_accounts.clone(),
                Ok(()),
            );
            assert_eq!(get_commission_bps(&accounts[0], &kind), commission_bps);

            // Verify the other commission kind was not affected.
            assert_eq!(
                get_commission_bps(&accounts[0], &other_kind),
                original_other_commission_bps,
            );

            // Same value - should pass.
            let accounts = process_instruction(
                features,
                &instruction_data,
                vec![
                    (vote_pubkey, accounts[0].clone()),
                    (authorized_withdrawer, accounts[1].clone()),
                ],
                instruction_accounts.clone(),
                Ok(()),
            );
            assert_eq!(get_commission_bps(&accounts[0], &kind), commission_bps);

            // Verify the other commission kind is still unchanged.
            assert_eq!(
                get_commission_bps(&accounts[0], &other_kind),
                original_other_commission_bps,
            );
        }
