## Title
Stale `total_points` denominator vs. re-fetched live stake amounts in `recalculate_stake_rewards` can let reward payouts exceed the committed epoch reward pool - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The Tower (legacy) reward path computes a fixed `PointValue { rewards, points }` once at epoch-boundary calculation time and commits it into the `EpochRewards` sysvar via `create_epoch_rewards_sysvar` [1](#0-0) . During the multi-block distribution window, `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards` re-derives each stake account's numerator (`tower_points`, via `calculate_points_for_tower`) from the **live** `StakesCache` at recalculation time, while still dividing by the **frozen** `total_points` denominator taken from the sysvar [2](#0-1) . If any stake delegation's effective stake grows between calculation and recalculation, its recomputed numerator can be larger than the value baked into the original `total_points` sum, while the denominator never changes to reflect that growth — this is structurally the same "score sum invariant" violation described in the Venus Prime bug report.

### Finding Description
`calculate_reward_points_partitioned` computes `points` as the sum of `calculate_points_for_tower(...)` over every stake delegation present at epoch-boundary time, and this total is stored as `PointValue.points` [3](#0-2) . That total is persisted immutably in the `EpochRewards` sysvar as `total_points` for the rest of the multi-slot distribution window [4](#0-3) .

When a fork switch or snapshot restore causes `recalculate_partitioned_rewards_if_active` to run mid-distribution, `recalculate_stake_rewards` rebuilds `stake_delegations` from `self.stakes_cache.stakes()` — i.e., the bank's *current* live stake state, not a frozen snapshot from calculation time — via `get_epoch_params_for_recalculation` [5](#0-4) . It then re-invokes `calculate_stake_rewards_and_commissions` using `point_value = PointValue { rewards: epoch_rewards_sysvar.total_rewards, points: epoch_rewards_sysvar.total_points }` — the frozen denominator — against this potentially-changed stake set [6](#0-5) . Individual per-account points are computed from `calculate_stake_points_and_credits` / `calculate_points_for_tower`, whose value depends directly on the delegation's current effective stake amount at that live snapshot. There is no mechanism forcing the sum of freshly recomputed `tower_points` values to equal `total_points`; the code comment even acknowledges the resulting commission accounts are known-inconsistent ("`RewardCommissionAccounts` calculated in this function call should NOT be used ever") but makes no equivalent statement or guard for `StakeRewardCalculation::stake_rewards`, which *is* used to build the payout partitions.

This is exactly the Venus `updateAlpha`/`updateMultipliers` bug class: a global "sum of scores" (here, `total_points`) is fixed at one point in time, but per-user numerators used against that fixed sum are recomputed later from mutated (live) state, breaking the invariant that `Σ(individual_scores) == sum_used_for_division`.

By contrast, the newer Alpenglow path deliberately fixed this exact issue by persisting `RewardEpochDelegatedStakes` as an immutable on-chain account snapshot and always using it (rather than live epoch stakes) as the per-vote-account denominator, as shown by `calculate_alpenglow_points` using `reward_epoch_delegated_stakes.delegated_stakes` instead of any live value [7](#0-6) , and is explicitly regression-tested by `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` [8](#0-7) . The Tower path has no equivalent frozen-snapshot protection for the `total_points` numerator/denominator pairing under recalculation.

### Impact Explanation
If exploitable, the aggregate lamports paid out across all recalculated `PartitionedStakeReward` entries in the distribution partitions could exceed `total_rewards` committed in the `EpochRewards` sysvar for that epoch. This is a "fund accounting mismatch" class bug: some validators/stakers could receive inflated rewards while the sysvar's remaining `distributed_rewards` tracker is depleted faster than expected, potentially starving later partitions in the same epoch (mirroring the "early claimants profit, late claimants get nothing" outcome from the Venus report), and it would corrupt `capitalization` accounting since `distribute_reward_commissions`'s insolvency assertion is only checked against the **original** calculation-time `total_stake_rewards_lamports`, not against recalculated values [9](#0-8) .

### Likelihood Explanation
This requires: (1) recalculation to actually trigger mid-distribution (via fork switch/reorg or snapshot restore — `initialize_after_snapshot_restore` and `new_for_block_tests` both call `recalculate_partitioned_rewards_if_active`) [10](#0-9) , and (2) a stake delegation's effective stake to actually change between the epoch-boundary calculation and the later recalculation in a way that increases its `tower_points` numerator without a corresponding update to `total_points`. I was **not able to fully verify** within the available investigation whether normal transaction processing (e.g., `DelegateStake`, stake merges/splits, or warm-up activation crossing an epoch boundary) can actually increase a delegation's effective stake enough, and quickly enough, to matter during the short (few-block) distribution window, nor whether other guards elsewhere (e.g., partition/commission delivery ordering, or the fact that recalculation only affects *undistributed* remaining partitions) sufficiently bound the discrepancy in practice. This uncertainty should be resolved with local reproduction/testing before treating this as a confirmed, high-confidence finding.

### Recommendation
Freeze the Tower path's per-stake numerator inputs (or at minimum, the total-stake denominator per vote account) at calculation time, mirroring the `RewardEpochDelegatedStakes` snapshot mechanism already used for Alpenglow, so that `recalculate_stake_rewards` cannot silently divide against a `total_points` value that no longer corresponds to the live stake set it is dividing across. Alternatively, add an explicit assertion in `recalculate_stake_rewards` (or in `distribute_epoch_rewards_in_partition`) that the sum of recalculated `stake_reward` values never exceeds the sysvar's remaining `total_rewards - distributed_rewards`, failing loudly rather than silently over/under-paying.

### Proof of Concept
Not independently constructed/verified within this investigation — the analysis is based on static code tracing of `recalculate_stake_rewards` and its callers. A concrete PoC would need to: (1) create a reward bank with an active `EpochRewards` sysvar mid-distribution (as done in `test_recalculate_partitioned_rewards` at [11](#0-10) ), (2) mutate a stake delegation's `Delegation::stake` in the live `StakesCache` between the initial calculation and a triggered `recalculate_partitioned_rewards_if_active` call, and (3) assert that the sum of `stake_reward` across recalculated partitions exceeds `epoch_rewards_sysvar.total_rewards - epoch_rewards_sysvar.distributed_rewards`.

    fn get_epoch_params_for_recalculation<'a>(

        let cached_vote_accounts =
            self.get_cached_vote_accounts(rewarded_epoch, distribution_epoch_vote_accounts);

        EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        }
    }

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
