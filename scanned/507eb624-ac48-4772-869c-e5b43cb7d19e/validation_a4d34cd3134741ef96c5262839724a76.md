## Analog Found: Uncharged, Unbounded Crypto-Verification Loop in Precompile Signature Verification

### Title
Precompile signature-verification loops (`secp256k1`/`ed25519`/`secp256r1`) perform expensive elliptic-curve work with zero compute-unit accounting, enabling CPU-exhaustion via a single transaction - (File: `precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, `precompiles/src/secp256r1.rs`, `program-runtime/src/invoke_context.rs`)

### Summary
The reported Compound bug is about a `for` loop over an attacker/user-influenced collection with no `gasleft()` check, letting the loop do unbounded work relative to the gas actually charged. The Agave analog is the `verify()` routines of the `secp256k1`, `ed25519`, and `secp256r1` precompiles: each contains a `for i in 0..count` loop (count up to 255, a `u8`) that performs a full elliptic-curve signature verification/recovery per iteration [1](#0-0) . Unlike ordinary BPF/builtin instruction execution, this loop is executed by `InvokeContext::process_message` via `process_precompile`, which never touches the compute meter — `compute_units_consumed` is left at `0` for precompiles [2](#0-1) . The fixed per-signature costs used elsewhere (`SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) are only used for fee/prioritization accounting in the cost model [3](#0-2) [4](#0-3)  — they are not an enforced runtime budget on the actual verification work performed.

### Finding Description
Each precompile instruction can specify up to `count = data[0] as usize` (max 255) signatures to check [5](#0-4) . Inside the loop, for every entry the code:
- deserializes offsets,
- slices out signature/pubkey/message data,
- hashes the message and performs a full `libsecp256k1::recover` (secp256k1) or `ed25519_dalek` strict verification, or an OpenSSL ECDSA verify with fresh `EcGroup`/`BigNumContext` setup per iteration (secp256r1) [6](#0-5) [7](#0-6) .

A single transaction can contain multiple such precompile instructions (bounded only by `MAX_INSTRUCTION_TRACE_LENGTH` on total instruction count, checked at sanitization) [8](#0-7) , each independently allowed up to 255 signatures. Because `process_precompile` bypasses the `ComputeMeter`/`compute_units_consumed` accounting entirely [9](#0-8) , the actual CPU cost of this verification work is never checked against the transaction's declared/allowed compute budget the way ordinary instruction execution is (compare with `ComputeMeter::consume_checked`, which enforces `InstructionError::ComputationalBudgetExceeded` for normal instructions) [10](#0-9) .

This is precisely the "excess of gas limit" pattern from the report: a loop count that is attacker-controlled, doing real per-iteration work (EC math), with no per-iteration remaining-budget check and no enforcement tying the loop's real cost to any limit.

### Impact Explanation
An unprivileged party can submit ordinary transactions (no special permissions) that maximize the number of precompile instructions/signatures per transaction. Because the verification loop runs unmetered by the compute budget, and secp256r1/secp256k1 verification involves relatively expensive bignum/EC operations, a validator processing such a transaction spends CPU cycles disproportionate to the fee actually charged or to any CU limit the sender declared. Submitted at volume (many such transactions across TPU/QUIC ingestion), this becomes a non-RPC remote CPU-exhaustion / performance-degradation vector against validators processing the transaction stream, potentially degrading block production/replay throughput cluster-wide.

### Likelihood Explanation
Likelihood is moderate-to-high for triggering the condition (constructing a maximal-count precompile instruction is trivial and requires no privileges), but the magnitude of the effect (how many concurrent such transactions are needed to cause meaningful degradation, and whether other layers such as packet/transaction rate limiting or QUIC stream throttling absorb the cost) could not be fully verified from the code reachable here. In particular, I could not confirm within the available index exactly which stage(s) invoke precompile `verify()` outside of `InvokeContext::process_message` (e.g., an earlier sanitization-time `verify_precompiles` pass), nor the current per-connection/per-IP transaction-admission rate limits that might mitigate volumetric abuse. This should be verified with a full checkout of the ingestion pipeline (`SanitizedTransaction::verify_precompiles` callers, banking-stage/TPU throttling) before treating this as conclusively exploitable at scale.

### Recommendation
Add per-iteration compute-budget accounting to the precompile `verify()` loops (or charge the full precompile cost against the compute meter before invocation, and enforce it), analogous to the reported fix: check remaining budget in each loop iteration (or pre-charge and bail with `ComputationalBudgetExceeded`) rather than only using the per-signature cost figures for fee estimation.

### Proof of Concept
Conceptually: craft a transaction containing multiple `secp256k1_program`/`secp256r1_program`/`ed25519_program` instructions, each with `data[0] = 255` (max signature count) and well-formed (but not necessarily valid) offsets so the loop runs to completion or near-completion for each of the 255 entries per instruction, repeated across as many instructions as `MAX_INSTRUCTION_TRACE_LENGTH` allows. Submit many such transactions; measure validator CPU time spent in `precompiles::secp256k1::verify` / `secp256r1::verify` versus the compute units actually charged against the sender (which will show `0` compute units consumed for the precompile portion, per `process_precompile`'s handling in `InvokeContext::process_message`).

I was unable to locate and fully trace the exact earliest call site that first invokes precompile `verify()` for every incoming transaction (i.e., whether it happens unconditionally before fee/nonce checks) using the available index; a Devin session with full repository access would be needed to confirm the precise ingestion-path ordering and any existing throttles that might already mitigate this.

    pub fn consume_checked(&self, amount: u64) -> Result<(), Box<dyn std::error::Error>> {
        let compute_meter = self.0.get();
        let exceeded = compute_meter < amount;
        self.0.set(compute_meter.saturating_sub(amount));
        if exceeded {
            return Err(Box::new(InstructionError::ComputationalBudgetExceeded));
        }
        Ok(())
    }

    let one = BigNum::from_u32(1).map_err(|_| PrecompileError::InvalidSignature)?;

    // Define curve group
    let group = EcGroup::from_curve_name(Nid::X9_62_PRIME256V1)
        .map_err(|_| PrecompileError::InvalidSignature)?;
    let mut ctx = BigNumContext::new().map_err(|_| PrecompileError::InvalidSignature)?;

    for i in 0..num_signatures {
        let start = i
            .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
            .saturating_add(SIGNATURE_OFFSETS_START);

        // SAFETY:
        // - data[start..] is guaranteed to be >= size of Secp256r1SignatureOffsets
        // - Secp256r1SignatureOffsets is a POD type, so we can safely read it as an unaligned struct
        let offsets = unsafe {
            core::ptr::read_unaligned(data.as_ptr().add(start) as *const Secp256r1SignatureOffsets)
        };

        // Parse out signature
        let signature = get_data_slice(
            data,
            instruction_datas,
            offsets.signature_instruction_index,
            offsets.signature_offset,
            SIGNATURE_SERIALIZED_SIZE,
        )?;

        // Parse out pubkey
        let pubkey = get_data_slice(
            data,
            instruction_datas,
            offsets.public_key_instruction_index,
            offsets.public_key_offset,
            COMPRESSED_PUBKEY_SERIALIZED_SIZE,
        )?;

        // Parse out message
        let message = get_data_slice(
            data,
            instruction_datas,
            offsets.message_instruction_index,
            offsets.message_data_offset,
            offsets.message_data_size as usize,
        )?;

        let r_bignum = BigNum::from_slice(&signature[..FIELD_SIZE])
            .map_err(|_| PrecompileError::InvalidSignature)?;
        let s_bignum = BigNum::from_slice(&signature[FIELD_SIZE..])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Check that the signature is generally in range
        let within_range = r_bignum >= one
            && r_bignum <= order_minus_one
            && s_bignum >= one
            && s_bignum <= half_order;

        if !within_range {
            return Err(PrecompileError::InvalidSignature);
        }

        // Create an ECDSA signature object from the ASN.1 integers
        let ecdsa_sig = openssl::ecdsa::EcdsaSig::from_private_components(r_bignum, s_bignum)
            .and_then(|sig| sig.to_der())
            .map_err(|_| PrecompileError::InvalidSignature)?;

        let public_key_point = EcPoint::from_bytes(&group, pubkey, &mut ctx)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key = EcKey::from_public_key(&group, &public_key_point)
            .map_err(|_| PrecompileError::InvalidPublicKey)?;
        let public_key_as_pkey =
            PKey::from_ec_key(public_key).map_err(|_| PrecompileError::InvalidPublicKey)?;

        let mut verifier =
            Verifier::new(openssl::hash::MessageDigest::sha256(), &public_key_as_pkey)
                .map_err(|_| PrecompileError::InvalidSignature)?;
        verifier
            .update(message)
            .map_err(|_| PrecompileError::InvalidSignature)?;

        if !verifier
            .verify(&ecdsa_sig)
            .map_err(|_| PrecompileError::InvalidSignature)?
        {
            return Err(PrecompileError::InvalidSignature);
        }
    }
    Ok(())
