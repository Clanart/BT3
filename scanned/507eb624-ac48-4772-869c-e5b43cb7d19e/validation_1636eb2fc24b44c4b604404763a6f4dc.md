### Title
`SystemInstruction::CreateAccount` treats any account holding stray lamports as "already in use", enabling balance-only griefing of legitimate account creation - (File: `programs/system/src/system_processor.rs`)

### Summary
The DODO report's root cause is that `_existsPairPool()` infers "pool exists" purely from `ERC20.balanceOf()` at a computed address, rather than checking for actual deployed contract code/state. Any attacker can pre-fund that address with tokens to create a false positive and break downstream logic. The Agave analog is `create_account()` in `programs/system/src/system_processor.rs`, which infers "account already in use" purely from `to.get_lamports() > 0`, without checking whether the account has actual data or a non-system owner. This lets any unprivileged party permanently grief a specific `CreateAccount` call for a program-derived address (PDA) simply by sending it a minimal lamport transfer beforehand.

### Finding Description
`create_account()` performs its "is this address already in use" check as follows: [1](#0-0) 

```rust
// if it looks like the `to` account is already in use, bail
{
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    if to.get_lamports() > 0 {
        ic_msg!(..., "Create Account: account {:?} already in use", to_address);
        return Err(SystemError::AccountAlreadyInUse.into());
    }
    allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
}
```

The check is `get_lamports() > 0` only — it does not verify `get_data().is_empty()` nor `system_program::check_id(get_owner())`, unlike the analogous `allocate()` helper a few lines above which correctly checks both data emptiness and ownership: [2](#0-1) . This is exactly the DODO bug's structure: a downstream code path relies on a **balance-based existence signal** as a proxy for "the target has real, deployed state," when balance alone proves nothing about ownership or content.

Because lamports can be sent to *any* pubkey (a PDA included) by anyone via a plain `SystemInstruction::Transfer`, an attacker who can predict the address that a program is about to create via CPI to `CreateAccount` (PDAs are deterministic; ATA addresses, program state accounts, escrow accounts, etc. are all derived and public before creation) can pre-fund that address with 1 lamport. When the legitimate initializer's transaction later invokes `CreateAccount` for that same address, `to.get_lamports() > 0` is true even though the account has empty data and is still owned by the System Program — i.e., it is not actually "in use" in any meaningful sense — and the instruction fails with `SystemError::AccountAlreadyInUse`.

The codebase itself effectively acknowledges this flaw: a parallel function, `create_account_allow_prefund()`, was added specifically to skip the zero-lamports check ("Create a new account without checking for 0 lamports... Intended for use where account has already had rent paid in whole or in part before creation"): [3](#0-2) . This confirms the balance-only check in the original `create_account()` path is recognized internally as an overly strict/incorrect existence signal, but it remains the only path used by `SystemInstruction::CreateAccount`/`CreateAccountWithSeed`, which is what the vast majority of on-chain programs and PDAs still rely on for account initialization: [4](#0-3) .

For PDA-owned accounts specifically, the victim program cannot simply "sweep" the griefed lamports before creating, because a PDA cannot be an unprivileged signer for an outgoing `Transfer` outside of the program's own instruction logic, and most programs do not implement a reclaim/sweep path for pre-funded, not-yet-created PDAs. This mirrors the DODO scenario where the "pool" address is not a real deployed contract yet the balance check treats it as if it were.

### Impact Explanation
This is a denial-of-service / broken-invariant issue, not fund theft: the false "already in use" signal causes legitimate, unprivileged `CreateAccount` calls (used pervasively for PDAs: escrow accounts, vaults, associated accounts, program state accounts, etc.) to permanently revert for the targeted address, exactly as the DODO bug caused legitimate swaps to permanently revert for a "falsely existing" pool. This falls under "non-RPC remote exhaustion/crash"/denial-of-service of unprivileged transaction/CPI paths in Agave's builtin System Program, since any unprivileged actor (no special validator/node/peer role needed) can grief any predictable address before its owner's `CreateAccount` transaction lands.

### Likelihood Explanation
High in the sense that the attacker primitive is trivial and fully unprivileged: derive the target address (a public, deterministic computation for PDAs/seeded accounts) and send it any nonzero lamport amount via an ordinary `SystemInstruction::Transfer`, at any time before the victim's `CreateAccount` call executes. No front-running of a specific transaction, no privileged role, and no reliance on trusted infrastructure is required — the attacker only needs to know the deterministic target address in advance, which is normal for PDAs.

### Recommendation
Change the "already in use" check in `create_account()` to match the stricter, correct check already used in `allocate()`/`allocate_and_assign()` — i.e., require both `get_data().is_empty()` and `system_program::check_id(get_owner())`, treating lamport balance alone as irrelevant to "in use" status — or make the `create_account_allow_prefund()` behavior (ignore stray lamports, only assign/allocate) the default/only path for `CreateAccount`, consistent with the mitigation the codebase already implemented (per the doc comment referencing pre-funded rent).

### Proof of Concept
Not independently executable from static code review; the control-flow evidence is:
1. `to_address` for a future `CreateAccount` call is deterministic/public (e.g., a PDA via `Pubkey::find_program_address`, or an address derived `with_seed`).
2. An unprivileged attacker sends 1 lamport to `to_address` via a plain `Transfer` instruction, using `transfer()`/`transfer_verified()` in [5](#0-4) , which imposes no restriction on the recipient.
3. Victim's transaction later invokes `SystemInstruction::CreateAccount` (directly or via CPI from another program) for `to_address`; `create_account()` at [1](#0-0)  sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently blocking initialization of that address through the standard path.

Note: I could not fully trace every current on-chain call site (e.g., whether ATA/stake/vote program CPIs have all migrated to `create_account_allow_prefund` given the feature-gate matches found in `feature-set/src/lib.rs`); confirming the exact activation status of the corresponding feature gate would require deeper inspection than the remaining tool budget allowed.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
