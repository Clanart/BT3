Target: `Verifier::nonce_gen` (core/src/verifier.rs) and `Verifier::deposit_sign`'s `session.nonces.pop()` loop. Attacker action: an unprivileged caller cannot call `nonce_gen` directly with attacker-chosen deposit_id since only the aggregator is meant to drive `new_deposit`, but the aggregator gRPC port accepts a raw `DepositSign` stream call with a `VerifierDepositSignParams::agg_nonce` referencing an EXISTING `nonce_session_id` from a prior, unrelated deposit if the caller can guess/observe the u128 id (ids are sequential via `get_new_unused_id`, not randomized). Preconditions: `client_verification` disabled (default `Interceptors::Noop`), so `deposit_sign` is reachable with arbitrary agg_nonce. Call sequence: attacker sends `DepositSign` stream carrying a `DepositSignSession` whose `nonce_gen_first_response.id` is a session id previously opened for deposit X, but the stream's own sighash stream (`create_nofn_sighash_stream`) is derived from deposit Y's `deposit_data` because the aggregator computed the RPC using deposit Y's params while reusing the leaked/guessed session id. Binding: session_id_used_for_signing == session_id_the_nonces_were_generated_for, must hold; here nonce_from_deposit_X_session == signed_for_deposit_Y_sighash. Scoped impact: Critical, N-of-N partial signatures produced for a spend no Citrea withdrawal authorises (a move-to-vault or reimburse tx for a deposit whose nonces were never meant to cover it). Proof idea: cargo test creating two deposits, capturing session id from deposit A's NonceGen response, then invoking DepositSign for deposit B while supplying deposit A's session id, and asserting the verifier either signs (bug) or must reject (must remain rejecting) via an explicit deposit_id binding check.
