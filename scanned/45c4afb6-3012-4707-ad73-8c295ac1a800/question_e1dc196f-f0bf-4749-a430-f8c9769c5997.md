Target: `AllSessions::get_new_used_id`-family id issuance (`get_new_unused_id`) vs `used_ids: HashSet<u128>` (core/src/verifier.rs ~104-120). Attacker action: since `nonce_session_id`s are returned to the calling aggregator/verifier client in `NonceGenFirstResponse.id` and then echoed back by ANY caller in `OptimisticPayoutParams.nonce_gen.id` or `VerifierDepositSignParams`, an attacker who can observe an id from one deposit flow (e.g. via a race with a legitimate withdraw request they also control) can submit `OptimisticPayoutSign` with that borrowed id for a DIFFERENT deposit_id, relying on `session_map.sessions.get_mut(&nonce_session_id)` finding a session never validated to belong to `deposit_id`. Preconditions: `sign_optimistic_payout`'s only per-call deposit binding is `deposit_id` (a separate parameter) used to look up `move_txid`/`withdrawal_utxo`, while `nonce_session_id` is used purely to fetch a `NonceSession` with NO stored association to `deposit_id` inside `NonceSession { nonces: Vec<SecretNonce> }` itself. Call sequence: verifier pops a nonce from a session that was generated for deposit A's OptimisticPayout flow, but signs a sighash built from deposit B's withdrawal params (both supplied by the SAME unprivileged caller who legitimately registered withdrawals for A and B). Binding: deposit_id_that_generated_this_NonceSession == deposit_id_whose_sighash_is_signed_with_the_popped_nonce, which the code never records or checks. Scoped impact: Critical, a secnonce generated for one deposit's optimistic-payout signing round is consumed to sign an unrelated deposit's payout, and if a session's nonce is later cross-used with two different agg_nonces (attacker submits two nonce_gen calls, swaps ids across two optimistic_payout_sign calls for A and B respectively) this yields the double-sign-same-nonce key leak. Scoped impact: Critical, verifier secnonce/secret key recoverable, plus N-of-N partial signature for a spend outside its authorising withdrawal. Proof idea: cargo test that calls nonce_gen for deposit A and deposit B (two OptimisticPayoutSign nonce_gen flows), then calls optimistic_payout_sign for B's withdrawal params but passing A's nonce_session_id, and asserts the verifier must reject due to missing deposit binding inside NonceSession, or if it succeeds, recovers the leaked secnonce via the two resulting partial signatures' shared nonce component.
