Target: `AllSessions::add_new_session_with_id` / `remove_oldest_session` / `MAX_ALL_SESSIONS_BYTES` / `MAX_NUM_SESSIONS` (core/src/verifier.rs, core/src/constants.rs). Attacker action: repeatedly call the public `NonceGen` RPC (unauthenticated when `client_verification` off) for many distinct deposit ids in short succession to fill `AllSessions.session_queue` past `MAX_NUM_SESSIONS`/`MAX_ALL_SESSIONS_BYTES`, forcing `remove_oldest_session` to evict the legitimate, in-flight session for an honest deposit that is mid `deposit_sign`. Preconditions: verifier's session_queue currently holds the honest deposit's session (nonces generated, not yet popped/finalized) and no rate limiting is in scope, but the finding here is not DoS-scope -- it is that eviction silently drops secnonces still referenced by an in-flight `DepositSign` call so a LATER call with the same `nonce_session_id` (id not yet in `used_ids` reused by another caller since ids are never truly random) resolves against a freshly `add_new_session_with_id` session for a different deposit. Binding: NonceSession returned by session_map.get_mut(id) for a later signing call == the NonceSession created for the deposit named at nonce_gen time for that same id. Scoped impact: Critical, N-of-N partial signatures over a spend never authorised by the deposit that generated those nonces. Proof idea: cargo test that opens sessions until eviction occurs, then feeds a `deposit_sign` stream for a stale id and asserts the deposit_id bound inside the resolved NonceSession header must match the deposit_id in the sighash stream, failing if it does not.
