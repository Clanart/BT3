## Analysis

The Sablier bug reduces to a general pattern: **a protocol lets users send funds to a deterministically-derived, not-yet-existing address (a "counterfactual" address) and then relies on an account-creation call that unconditionally reverts if the target already holds a balance** — permanently stranding the prefunded balance because the salt/seed used to derive the address is entangled with parameters that must match exactly for the create to succeed.

Agave has the exact analog in the System Program's account-creation path, and — tellingly — the Agave team has already built (but not yet activated) a fix for it.

### The corrupted invariant
`programs/system/src/system_processor.rs`'s `create_account()` (used by both `CreateAccount` and `CreateAccountWithSeed`) treats any pre-existing balance on the target address as fatal: [1](#0-0) 

If a caller (or anyone) sends lamports to a deterministic address — e.g. a PDA computed off-chain via `Pubkey::create_program_address`/`find_program_address`, or a seed-derived address via `Pubkey::create_with_seed` — *before* the owning program issues its `CreateAccount` CPI, the check `to.get_lamports() > 0` unconditionally fails with `SystemError::AccountAlreadyInUse`, exactly mirroring Sablier's `createMerkleLT()` revert on a prefunded CREATE2 address.

### Agave's own acknowledgment and partial fix
Agave introduced a new instruction, `CreateAccountAllowPrefund`, specifically to remove the zero-balance requirement — the doc comment makes the intent explicit: [2](#0-1) 

This is gated behind SIMD-0312, listed in the feature registry as still pending/not universally active: [3](#0-2) [4](#0-3) 

The dispatch path explicitly rejects the new instruction until the feature is active, meaning **until `create_account_allow_prefund` is activated network-wide, every caller is still stuck with the old, revert-on-prefund `CreateAccount`/`CreateAccountWithSeed` behavior**: [5](#0-4) 

### Why existing recovery paths don't help for PDAs
For `CreateAccountWithSeed`, a user who controls the `base` keypair can still recover stuck funds via `TransferWithSeed` without ever creating the account, since that instruction only needs `base` to sign — this is a legitimate mitigant absent in the Sablier/CREATE2 case. However, for a pure **program-derived address (PDA)** with no `base` keypair (used by many higher-level programs — vaults, escrow accounts, ATA-style token accounts, vote/stake bootstrap accounts, bridge deposit accounts, etc.), there is no `TransferWithSeed`-equivalent recovery: only the owning program can move lamports out via CPI signed with `invoke_signed`, and if that program's *only* lamport-moving instruction is its account-initialization path (which itself CPIs into `CreateAccount` and hits the same revert), funds sent to that PDA before initialization are permanently stuck exactly like the Sablier CREATE2 case — no signature exists for a bare PDA, and changing the derivation parameters produces a different address.

### Title
System Program `CreateAccount`/`CreateAccountWithSeed` unconditionally reverts on prefunded PDAs, permanently stranding lamports sent to counterfactual program-derived addresses - (`programs/system/src/system_processor.rs`)

### Summary
Any unprivileged actor (or the depositing user themself) can transfer lamports to a program-derived address (PDA) before the owning on-chain program creates that account. Because `create_account()` in the System Program rejects creation whenever the target already has `lamports > 0`, the subsequent CPI-driven `CreateAccount`/`CreateAccountWithSeed` call permanently fails with `AccountAlreadyInUse`. Since a bare PDA has no keypair, there is no way to move the stranded lamports out except through the very program instruction that is now permanently blocked. This is the direct Agave analog of the Sablier `createMerkleLT()`/CREATE2 counterfactual-deployment bug.

### Finding Description
`create_account()` bails out before doing any allocation if the destination account balance is nonzero: [6](#0-5) 
This check is invoked for both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed`. Many Solana programs use a counterfactual/prefund pattern — a client computes a PDA off-chain and either transfers lamports to it directly, or a protocol collects deposits at a PDA prior to the on-chain "initialize" instruction being invoked. If that PDA is later system-owned/empty-data but nonzero-balance when the program's `CreateAccount` CPI runs, the entire CPI (and typically the whole transaction) fails, and it fails identically on every retry, since the balance that caused the failure cannot be changed by anyone without a signer for that address.

Agave's own fix — the new `CreateAccountAllowPrefund` instruction and its `create_account_allow_prefund()` handler, which drops the zero-balance requirement — confirms this is a recognized, real defect class, but it is currently only reachable behind the unactivated `create_account_allow_prefund` feature gate: [7](#0-6) 

### Impact Explanation
Lamports sent to a not-yet-created PDA are permanently unrecoverable if the only path to move them is through the blocked `CreateAccount` CPI (e.g., a vault/escrow/bridge PDA whose owning program has no "reclaim if uninitialized" instruction). This is a direct, unprivileged fund-loss vector matching the accepted impact category ("unprivileged Agave issues in ... runtime, accounts, or built-ins that cause fund theft/loss").

### Likelihood Explanation
Likelihood is driven by adoption of the counterfactual-deposit pattern for PDAs across the ecosystem (common for account-abstraction-style flows, bridges, and pre-funded vault addresses). No malicious peer, validator, or privileged actor is required — a normal user or normal integration triggers it simply by funding an address before its initializing instruction executes, or by an attacker griefing a victim's counterfactual PDA by sending a small prefund transfer to it first.

### Recommendation
Prioritize activation of the `create_account_allow_prefund` feature (SIMD-0312) network-wide, and audit/encourage downstream programs that rely on PDA-based counterfactual funding to migrate their account-initialization CPIs to `CreateAccountAllowPrefund` once active, mirroring Sablier's own remediation (allow deployment/creation regardless of prefund, and provide any necessary clawback/reclaim instruction at the program level for funds that land on an account before initialization).

### Proof of Concept
1. A program `P` derives a PDA `V` via `find_program_address` for a vault/escrow that a user is meant to fund before calling `P::initialize_vault`.
2. Attacker (or ordinary usage flow) sends 1 lamport via `SystemInstruction::Transfer` directly to `V` before `initialize_vault` is called — this succeeds trivially since any account can receive lamports.
3. User calls `P::initialize_vault`, which internally issues a `system_instruction::create_account` CPI (via `invoke_signed`, signing with `V`'s PDA seeds) to allocate/assign `V`.
4. `create_account()` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, per [8](#0-7) , aborting the whole transaction.
5. Every subsequent retry of `initialize_vault` fails identically since `V`'s balance can't be changed (no signer exists for `V`), and unless `P` exposes an independent reclaim/close instruction not gated on successful initialization, the lamports at `V` are permanently stuck — exactly analogous to funds locked at an un-deployable CREATE2 address in the Sablier report.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
