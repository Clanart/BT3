## Analysis

The Optimism bug's core pattern is: **a fixed-size "seen/pending" cache is far smaller than the sustained throughput of legitimate traffic, so under adversarial pressure the cache evicts still-valid entries, causing the node to permanently reject/drop legitimate data it needs to keep up with the chain.**

The closest Agave analog is the `OutstandingRequests` nonce-tracking cache used by shred repair, defined in `core/src/repair/outstanding_requests.rs`:

```rust
impl<T, U> Default for OutstandingRequests<T, U> {
    fn default() -> Self {
        Self {
            requests: LruCache::new(16 * 1024),
        }
    }
}
``` [1](#0-0) 

Every outstanding repair request the node sends gets a nonce inserted into this fixed 16384-entry LRU, with an independent 60s soft expiration: [2](#0-1) 

However, the repair-request issuance rate is not coupled to this cache size at all. `repair_service.rs` allows up to `MAX_REPAIR_LENGTH = 512` shred-repairs to be generated per repair pass, run every `REPAIR_MS = 1` millisecond: [3](#0-2) 

This means the node can legitimately (or under attacker-induced shred loss) generate far more than 16384 outstanding repair requests within the 60-second expiration window — the LRU will silently evict still-pending, still-valid nonces long before their real responses arrive.

When a genuine repair response finally arrives for an evicted nonce, it is treated exactly like an attacker-forged/unmatched nonce and the shred is discarded:

- In `core/src/shred_fetch_stage.rs`, `verify_repair_nonce` calls `register_response`; if the nonce is not found (because it was LRU-evicted), the packet is discarded: [4](#0-3) 

- In `turbine/src/sigverify_shreds.rs`, `extract_shred_and_location` explicitly documents this failure mode — "This indicates the request entry was evicted before consumption" — and drops the shred instead of inserting it into blockstore: [5](#0-4) 

An attacker who can induce sustained shred loss to a target (e.g., by being a marginal turbine peer that selectively fails to retransmit, or by exploiting network conditions/eclipse-style targeting) forces the victim to keep a very large number of outstanding repair requests in flight. Once concurrent outstanding requests exceed 16384, the fixed LRU begins evicting the oldest still-pending nonces well before the 60s soft-expiry, so correct, on-time repair responses are discarded as if they were spoofed/unmatched. This is functionally identical to the Optimism bug: a cache sized without regard to real traffic volume causes legitimate, valid, timely data to be treated as invalid, degrading (and, if sustained, permanently preventing) the node's ability to catch up via repair.

### Title
Undersized fixed-capacity `OutstandingRequests` LRU (16384 entries) in repair nonce-tracking causes legitimate repair responses to be discarded under high repair load - (File: core/src/repair/outstanding_requests.rs)

### Summary
`OutstandingRequests::default()` hard-codes an LRU capacity of `16 * 1024` entries for tracking repair request nonces, independent of the actual repair request issuance rate (`MAX_REPAIR_LENGTH = 512` requests every `REPAIR_MS = 1` ms in `repair_service.rs`). When outstanding requests exceed capacity within the 60s `DEFAULT_REQUEST_EXPIRATION_MS` window, the LRU silently evicts still-pending, not-yet-expired nonces. Genuine repair responses arriving after their nonce was evicted are then indistinguishable from forged/unmatched-nonce packets and are dropped in both `shred_fetch_stage.rs::verify_repair_nonce` and `sigverify_shreds.rs::extract_shred_and_location`.

### Finding Description
The nonce cache is meant to authenticate repair responses (only a nonce this node generated and is still awaiting should be accepted) and to route repaired shreds to the correct blockstore location. Its capacity of 16384 is a static constant unrelated to how fast the node can legitimately need to issue repair requests. During periods of elevated shred loss — which an unprivileged peer can induce by being a poor/non-cooperative turbine retransmitter, packet dropping, or targeted network interference toward the victim — the victim's `repair_service`/`block_id_repair_service` can enqueue far more than 16384 concurrent outstanding requests well inside the 60-second expiration window (at the documented max rate of 512 requests/ms, capacity is exhausted in ~32ms of sustained repair need). The `LruCache::put` used by `add_request_with_metadata` evicts the least-recently-used entry once at capacity, regardless of whether that entry's own timer has actually expired. This breaks the invariant that "a repair response for an outstanding, non-expired nonce should be accepted" — the corrupted/lost value is effectively the pending `RequestStatus` for that nonce, which disappears from the map before the correct response can be matched against it.

### Impact Explanation
Once a nonce is evicted, the correct/on-time repair shred is dropped rather than inserted into blockstore (`extract_shred_and_location` returns `None`, incrementing `num_unknown_block_location`) or discarded outright at the fetch stage (`verify_repair_nonce` returns `false`). Under sustained induced loss, this creates a persistent gap between the number of legitimate in-flight repair requests and the cache's ability to track them, causing wasted repair round-trips and repeated failure to fill missing shreds — degrading the node's ability to catch up to the cluster. This is a non-RPC, remotely triggerable degradation of a single victim node caused only by unprivileged network-layer behavior (shred non-retransmission/packet manipulation), matching the "non-RPC remote exhaustion/degradation" class.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to already be in a repair-heavy state (behind by many shreds/slots) and requires attacker-controlled or attacker-amplified shred loss sustained long enough to exceed 16384 concurrent outstanding requests, which is achievable given the documented repair issuance rate of up to 512 requests/ms. No validator/peer trust bypass or protocol-level malleability is required — only ordinary unprivileged network conditions (selective non-forwarding, packet delay/drop) directed at the victim.

### Recommendation
Size the `OutstandingRequests` LRU capacity relative to the maximum sustainable in-flight request rate and expiration window (e.g., `max_requests_per_ms * expiration_ms` with headroom), or switch eviction to be expiration-driven only (never evict a non-expired, still-awaiting-response nonce) rather than pure LRU capacity-based eviction. Alternatively, make the cache capacity configurable/dynamic based on observed repair backlog size.

### Proof of Concept
1. Target a validator that has fallen behind (common during normal operation, and easily exacerbated by an unprivileged peer that withholds/delays turbine retransmissions of shreds destined for the victim).
2. Ensure the victim's `repair_service`/`block_id_repair_service` sustains issuance of repair requests at or near the documented `MAX_REPAIR_LENGTH` (512) per `REPAIR_MS` (1ms) cadence for longer than the time needed to exceed 16384 concurrently outstanding, non-expired requests (~32ms of continuous max issuance, or less under normal sustained catch-up rates).
3. Delay (but not drop — e.g., via network jitter/attacker relaying) genuine responses for the earliest-issued nonces so they arrive after eviction but still within the intended 60s `DEFAULT_REQUEST_EXPIRATION_MS`.
4. Observe in `ShredSigVerifyStats::num_unknown_block_location` and/or discarded packets in `shred_fetch_stage` that valid, correctly-signed repair responses are being dropped solely due to LRU eviction of their tracking nonce, preventing the corresponding shreds from ever being inserted into blockstore even though a correct response was received.
