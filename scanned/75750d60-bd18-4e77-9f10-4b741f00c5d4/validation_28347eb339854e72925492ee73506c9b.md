### Title
Rent-driven stake delegation adjustment can leave a stake account below `get_minimum_delegation()` without fully deactivating it - (File: `runtime/src/inflation_rewards/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The SIMD-0392 rent-adjustment logic reduces a stake's `delegation.stake` to keep `lamports_with_rewards - minimum_lamports` non-double-counted with the rent-exempt reserve, using `std::cmp::min` and `saturating_sub`, but it never re-validates the resulting delegation amount against the protocol's minimum stake delegation (`get_minimum_delegation()`), only against zero.

### Finding Description
`delegation_may_need_adjustment` and `adjust_delegation_for_rent` compute: [1](#0-0) [2](#0-1) 

```
let new_delegation = std::cmp::min(
    new_delegation_with_rewards,
    lamports_with_rewards.saturating_sub(minimum_lamports),
);
```

The only special-casing is `if new_delegation == 0 { deactivate }` — there is no comparison against the network's `get_minimum_delegation()` (1 SOL post-upgrade), which is the value enforced everywhere else a delegation is created or modified (initial delegate, split, etc.): [3](#0-2) 

This mirrors the ETHCrowdfundBase.sol pattern exactly: the "minimum" check (`minContribution`/`get_minimum_delegation`) is enforced when a value is first established (delegate-stake instruction), but a later size-reducing adjustment (excess refund / rent-driven delegation shrink) is applied without re-enforcing that same minimum, so the invariant "every active stake ≥ minimum delegation" can be silently broken by a value that is non-zero but below minimum.

### Impact Explanation
If a stake's post-adjustment delegation ends up strictly between 1 and `get_minimum_delegation() - 1` lamports (i.e., non-zero but below the protocol minimum), the stake remains "active" per this code path (only deactivated at exactly zero) while violating the minimum-delegation invariant that the rest of the runtime/stake program assumes always holds for active delegations. This is analogous to the crowdfund case where a contribution below `minContribution` ends up "accepted" but produces degenerate voting-power / stake-weight behavior downstream (e.g., extremely small effective stake weight, edge cases in warmup/cooldown or activation-status math that assume delegations are either exactly 0 or ≥ minimum).

### Likelihood Explanation
This can only be reached through the SIMD-0392 rent-increase adjustment path (`adjust_delegations_for_rent` gated behind a feature/rent-increase event), which is a legitimate protocol-controlled path rather than attacker-controlled input, so likelihood is low and largely depends on how/whether Rent parameters are ever increased in practice.

### Recommendation
When computing `new_delegation` in `delegation_may_need_adjustment` / `adjust_delegation_for_rent`, clamp any non-zero result below `get_minimum_delegation()` down to `0` (full deactivation) rather than allowing values strictly between `1` and the minimum delegation to persist as "active."

pub(crate) fn delegation_may_need_adjustment(
    current_delegation: u64,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
    status: StakeActivationStatus,
) -> bool {
    if status.effective == 0 && status.activating == 0 {
        return false;
    }

    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    new_delegation != current_delegation
}

fn adjust_delegation_for_rent(
    delegation: &mut Delegation,
    rewarded_epoch: Epoch,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
) {
    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    if new_delegation != delegation.stake {
        delegation.stake = new_delegation;
        // Deactivate stake if needed. This deactivation is immediate,
        // unlike a requested deactivation which happens at the next epoch
        // boundary
        if new_delegation == 0 {
            delegation.deactivation_epoch = rewarded_epoch;
        }
    }
}

/// When this feature is added, it will be accompanied by an upgrade to the BPF Stake Program.
