## Finding: Sysvar underfunded for block rewards before distribution — `checked_sub_lamports` can underflow

### Summary

`update_epoch_rewards_sysvar` debits `debit_block_reward_lamports` from the `EpochRewards` sysvar account and `.expect()`s success on the `checked_sub_lamports` call [1](#0-0) . This value is populated during partitioned distribution as `block_reward_lamports_distributed + block_reward_lamports_burned`, which is the accumulated sum of the per-stake `block_reward` field computed at epoch-rewards calculation time [2](#0-1) [3](#0-2) .

### Finding Description

Each stake account's `block_reward` is calculated from the vote account's `pending_delegator_rewards()` proportional to stake, and is only nonzero when the `block_revenue_sharing` feature is active [4](#0-3) [5](#0-4) .

The sysvar account is only ever *credited* with block-reward lamports inside `create_epoch_rewards_sysvar`'s `block_rewards` parameter, which is added via `checked_add_lamports` [6](#0-5) . However, `begin_partitioned_rewards` — the function that creates the sysvar for the new epoch — hardcodes this parameter to `0`:

```rust
self.create_epoch_rewards_sysvar(
    distributed_lamports + distributed_to_incinerator_lamports + burned_lamports,
    distribution_starting_block_height,
    num_partitions,
    point_value,
    0, // block_rewards
);
``` [7](#0-6) 

Later, when each partition is distributed, `distribute_epoch_rewards_in_partition` debits the sysvar by the sum of the individually computed `block_reward` values for that partition [8](#0-7) . If `block_revenue_sharing` is active and any stake account earns a nonzero block reward, the sysvar account was never funded with those lamports at creation time, so `account.checked_sub_lamports(debit_block_reward_lamports)` returns an `Err`, and the subsequent `.expect("epoch reward sysvar has enough lamports for distribution")` panics [1](#0-0) .

Because `process_new_epoch`/`begin_partitioned_rewards`/`distribute_epoch_rewards_in_partition` execute deterministically as part of normal bank/epoch-boundary replay for every validator [9](#0-8) , this is not an attacker-triggerable, isolated crash — it would occur identically on every replaying node at the same slot.

### Uncertainty / Caveat

I could not fully rule out that block-reward lamports are funded into the sysvar account through a separate path executed between `begin_partitioned_rewards` and the first partition distribution — specifically `EpochInflationAccountState::new_epoch_update_account`, which is invoked immediately after `begin_partitioned_rewards` when the `alpenglow` feature is active [10](#0-9) . I was not able to inspect that function's implementation within the available tool budget. If that function (or another) transfers/credits the missing block-reward lamports into the sysvar account before the first distribution partition runs, this finding would be invalidated. I recommend verifying `EpochInflationAccountState::new_epoch_update_account` and any other code that touches the `epoch_rewards` sysvar's lamport balance between epoch-boundary creation and partitioned distribution before treating this as confirmed.

### Impact Explanation

If unconfirmed, a genuine mismatch here would cause a deterministic panic across all validators replaying the same epoch-boundary slot once `block_revenue_sharing` is active and any block reward is nonzero — a full consensus/network halt, which is in-scope critical impact.

### Likelihood Explanation

Contingent entirely on whether `block_revenue_sharing` is active and whether an alternate lamport-funding path (e.g., `EpochInflationAccountState::new_epoch_update_account`) exists that I was unable to verify.

### Recommendation

Verify whether `EpochInflationAccountState::new_epoch_update_account` (or another mechanism) funds the `epoch_rewards` sysvar's lamport balance with the total computed block-reward pool before the first `distribute_epoch_rewards_in_partition` call. If no such mechanism exists, `begin_partitioned_rewards` should pass the actual summed block-reward total (not a hardcoded `0`) to `create_epoch_rewards_sysvar`, matching what will later be debited during distribution.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
