### Title
Floating-point precision loss in stake-ratio threshold comparisons causes incorrect quorum decisions - (File: `core/src/consensus.rs`)

### Summary
The external report's bug class is "a value that has been scaled/precision-adjusted incorrectly is compared against a differently-scaled threshold, causing an incorrect boolean revert/accept decision, and the test suite never catches it because it uses unrealistic magnitudes." The real Agave analog is the use of raw `f64` division (`stake as f64 / total_stake as f64`) to evaluate consensus-critical quorum/threshold decisions in the TowerBFT fork-choice code, instead of exact integer (rational) arithmetic. Agave has already acknowledged and fixed this exact bug class elsewhere in the codebase (`votor-messages/src/fraction.rs`), but the legacy/still-active TowerBFT consensus path in `core/src/consensus.rs` was never migrated to the precise `Fraction` type.

### Finding Description
Several TowerBFT quorum checks compute a stake ratio via a lossy `u64 -> f64` cast and compare it against a constant threshold: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

All of these perform `(numerator_stake as f64) / (total_stake as f64) > threshold_constant` (e.g. `SWITCH_FORK_THRESHOLD = 0.38`, `DUPLICATE_THRESHOLD`, `VOTE_THRESHOLD_SIZE`, `SUPERMINORITY_THRESHOLD`) rather than exact cross-multiplication comparison.

`f64` has only 52 bits of mantissa, so it can represent integers exactly only up to `2^53 ≈ 9.007 × 10^15`. Mainnet total delegated stake, expressed in lamports, is on the order of `10^17`–`10^18` (hundreds of millions of SOL × `LAMPORTS_PER_SOL` = `10^9`), which already exceeds the exact-integer range of `f64`. This means both the numerator and denominator lose precision during conversion, and the resulting ratio can differ from the true rational value by an amount that flips the outcome of a strict `>` comparison exactly at/near the threshold boundary.

Agave's own test suite proves this is a real, exploitable numerical defect, not a theoretical concern — this is demonstrated by the dedicated `Fraction` type introduced to fix it for the Alpenglow/votor path: [8](#0-7) 

That test shows `total_stake = 100_000_000_000_000_000` (1e17 lamports) and `stake = 60_000_000_000_000_001` (60% + 1 lamport): the exact fraction is strictly greater than `60%`, but the `f64` division rounds down and evaluates as `<= 0.6` — the wrong answer. The fix (exact `u128` cross-multiplication in `Fraction::cmp`) was applied to `votor` / `votor-messages` (Alpenglow) call sites such as `votor/src/consensus_pool/slot_stake_counters.rs`, but the pre-existing TowerBFT functions in `core/src/consensus.rs` (`is_slot_duplicate_confirmed`, `check_vote_stake_threshold`, `make_check_switch_threshold_decision`), `core/src/consensus/progress_map.rs::ForkStats::fork_weight`, `runtime/src/commitment.rs::get_lockout_count`, and `core/src/replay_stage.rs::update_slot_propagated_threshold_from_votes` still use the unfixed `f64`-division pattern.

Existing guards do not stop this: there is no secondary exact-arithmetic check, no epsilon-aware rounding, and no assertion bounding stake magnitude below `2^53`. The comparisons are direct `f64 > constant` expressions with no correction.

### Impact Explanation
These functions gate core consensus safety/liveness decisions:
- `is_slot_duplicate_confirmed` / `check_vote_stake_threshold` determine whether a fork has reached duplicate-confirmation or vote-lockout quorum (affects whether a validator is allowed to vote for, or must abandon, a slot).
- `make_check_switch_threshold_decision` (`SWITCH_FORK_THRESHOLD`) determines whether a validator is permitted to switch its vote to a different fork — the code's own comment states that getting this wrong ("if everybody... abandons slot 4... the network halts because 90% of validators can't vote") can directly cause a **consensus halt**.
- `update_slot_propagated_threshold_from_votes` (`SUPERMINORITY_THRESHOLD`) gates leader-slot propagation confirmation, which feeds into whether the leader is allowed to keep producing/whether the block is treated as propagated.
- `commitment.rs::get_lockout_count` feeds `getBlockCommitment`/confirmation-count reporting used by clients to judge finality.

Because the erroneous ratio is computed identically by the reference client logic itself (not an attacker input), a stake distribution that lands on the precision-loss boundary can cause the network to systematically compute the wrong quorum decision — i.e. false rejection of a fork that has actually met the switch/lockout/propagation/duplicate-confirmation threshold (or, less likely, false acceptance), which maps to this task's "false execution/rooting/acceptance" and "consensus halt" impact categories.

### Likelihood Explanation
This is not attacker-controlled in the traditional sense — it depends only on the natural stake distribution of the cluster, which already exceeds `2^53` lamports on real networks, so the precision loss condition (magnitude exceeding exact-integer range) is already met today. What is not certain without live cluster telemetry is how often live stake ratios land close enough to a threshold boundary (`0.38`, `2/3`, `1/3`, etc.) for the ~2^-52 relative rounding error to actually flip a `>` comparison; this is inherently a rare, boundary-dependent condition, so likelihood is low but the values are within the theoretically reachable range and the bug is deterministic and reproducible once the boundary condition is met (as shown by the `Fraction` unit test itself, which reconstructs exactly such a boundary case).

### Recommendation
Replace the `f64`-based ratio comparisons in `core/src/consensus.rs` (`is_slot_confirmed`, `is_slot_duplicate_confirmed`, `check_vote_stake_threshold`, `make_check_switch_threshold_decision`), `core/src/consensus/progress_map.rs::ForkStats::fork_weight`, `runtime/src/commitment.rs::get_lockout_count`, and `core/src/replay_stage.rs::update_slot_propagated_threshold_from_votes` with the exact-precision `Fraction` type (`votor_messages::fraction::Fraction`, using `u128` cross-multiplication) that is already used to fix this exact class of bug in the `votor` module, so TowerBFT threshold decisions are computed without floating-point rounding error.

### Proof of Concept
The exact numerical pattern already exists as a passing unit test proving the defect, reusable against any of the vulnerable `core/src/consensus.rs` comparisons: [8](#0-7) 

```rust
let total_stake = NonZeroU64::new(100_000_000_000_000_000).unwrap(); // 1e17 lamports
let stake = 60_000_000_000_000_001u64; // exactly 60% + 1 lamport

let f64_ratio = stake as f64 / total_stake.get() as f64;
assert!(f64_ratio <= 0.6); // WRONG: true fraction is > 0.6
assert!(Fraction::new(stake, total_stake) > Fraction::from_percentage(60)); // correct
```

Substituting this same `stake`/`total_stake` pair (or an analogous pair tuned to `SWITCH_FORK_THRESHOLD = 0.38`) directly into `Tower::is_slot_duplicate_confirmed` or `Tower::check_vote_stake_threshold`'s `(*stake as f64 / total_stake as f64) > threshold_size` expression at `core/src/consensus.rs:591-607` / `1351-1364` reproduces the same wrong boolean outcome those consensus functions rely on.
