## Title
Stale VAT-balance filter causes deterministic `.expect()` panic in `Bank::maybe_burn_vat_from_staked_accounts` - (File: `runtime/src/bank.rs`)

## Summary
`Bank::update_epoch_stakes` filters vote accounts by balance via `clone_and_filter_for_vat`/`get_top_epoch_stakes` and then immediately calls `maybe_burn_vat_from_staked_accounts`, which re-reads each vote account's *current* lamports and subtracts `vat_to_burn_per_epoch` with `.expect("Vote accounts should have already been filtered to contain enough balance for the VAT")`. The balance snapshot used for the filter and the balance read at burn time are not guaranteed to be the same value in every code path, so the "already filtered" invariant documented on the function can be violated, turning what should be an impossible state into a live `panic!` in a deterministic state-transition function.

## Finding Description
The External Report's bug class is: a value used to gate a withdrawal/transfer (`totalUnderlying()`) can be stale relative to the actual liquid balance, so the guarded operation fails unexpectedly when executed.

The Agave analog is the SIMD-0357 Validator Admission Ticket (VAT) burn:

- `VoteAccounts::clone_and_filter_for_vat` computes `has_balance = vote_account.lamports() >= minimum_vote_account_balance` from a `VoteAccount` snapshot taken from the stakes cache, and drops accounts that don't have enough balance. [1](#0-0) 

- `Bank::update_epoch_stakes` uses either a freshly recomputed filter (`get_top_epoch_stakes`, which reads `self.stakes_cache.stakes()` at call time) or, on the epoch-boundary path, a `prefiltered_distribution_vote_accounts` snapshot that was produced earlier inside `compute_new_epoch_caches_and_rewards`. It then calls `maybe_burn_vat_from_staked_accounts` with whichever snapshot it has. [2](#0-1) 

- `maybe_burn_vat_from_staked_accounts` trusts that snapshot completely and does `self.get_account(vote_pubkey)` (the *live* account state on `self`) followed by `checked_sub(vat_to_burn_per_epoch).expect(...)`: [3](#0-2) 

The comment on the function explicitly documents the assumed invariant ("This must ONLY be called after the vote accounts have been filtered ... to contain enough balance for admission"), which shows the developers relied on filter-time balance equaling burn-time balance without an in-line re-check — mirroring the Sandclock bug where `totalUnderlying()` (a computed/cached value) was trusted to equal the actual liquid balance at the moment of transfer.

The filter-time snapshot (`unfiltered_distribution_vote_accounts` / `filtered_distribution_vote_accounts`) is derived from `self.stakes_cache.stakes()` inside `compute_new_epoch_caches_and_rewards`, evaluated via `stakes.calculate_activated_stake(...)`, which is a computed/cached view of vote-account state, not necessarily byte-identical in lamports to what `self.get_account(vote_pubkey)` returns at the moment `maybe_burn_vat_from_staked_accounts` executes moments later in the same call chain. [4](#0-3) 

No code path re-checks `account.lamports() >= vat_to_burn_per_epoch` at burn time; the only guard is the `.expect()`, which converts any drift between the filter snapshot and the live account into a hard panic rather than a graceful skip/error.

## Impact Explanation
If the assumed invariant is ever violated for even one vote account among up to 2000 filtered accounts, `Bank::maybe_burn_vat_from_staked_accounts` panics deterministically. Because this runs inside `update_epoch_stakes`, which is called from `process_new_epoch` on every bank at an epoch boundary, the exact same deterministic state transition is replayed by every validator processing that slot. A panic here therefore does not merely fail one transaction — it crashes the bank-processing thread on all validators simultaneously, producing a network-wide consensus halt. This satisfies the "cause consensus halt" criterion in the valid-impact list, and is strictly worse than the original Sandclock bug (a failed/reverted call) because it is an unrecoverable process panic in unprivileged, deterministic core-runtime code rather than a mere reverted transaction.

## Likelihood Explanation
This is a `runtime`/`accounts` bug-class issue (not a malicious-peer or trusted-integration scenario): it depends only on ordinary vote-account balance state (e.g., an authorized withdrawer withdrawing lamports down near the rent-exempt minimum via the normal `Withdraw` vote instruction, which only enforces `rent_exempt_minimum (+ pending_delegator_rewards)`, not the VAT reserve) combined with the timing/consistency of when the VAT balance filter snapshot is taken versus when the live account is read for the burn. Exploiting or triggering it requires no elevated privilege — it is achievable by an ordinary vote-account withdrawer performing a normal, permitted operation. However, verifying the *exact* magnitude of the staleness window (whether `compute_new_epoch_caches_and_rewards`'s snapshot can ever diverge from `self.get_account()`'s live value within the same `process_new_epoch` call, versus only being provably safe because both derive from the same immutable `self` state) requires deeper tracing of `stakes.calculate_activated_stake` and `VoteAccount` construction that was not fully completable within the available exploration. This should be treated as a code-level invariant risk warranting confirmation via a Devin session rather than a confirmed, reproduced crash.

## Recommendation
- Replace the `.expect()` panic in `maybe_burn_vat_from_staked_accounts` with a defensive re-check: if `account.lamports() < vat_to_burn_per_epoch`, skip burning for that account (and log/metric it) rather than panicking, matching the Sandclock mitigation of "when the system doesn't have enough balance to make the transfer, handle gracefully instead of failing."
- Ensure the balance check performed by `clone_and_filter_for_vat` and the balance read in `maybe_burn_vat_from_staked_accounts` are guaranteed, by construction (e.g., pass the exact same `VoteAccount`/lamports value through instead of re-deriving via `self.get_account`), to be from the identical account snapshot, eliminating any window for drift.
- Add a fuzz/property test that constructs a vote account whose cached "filtered" balance differs from its live/`get_account` balance at the exact call boundary to confirm whether the panic is reachable in practice.

## Proof of Concept
A full end-to-end PoC requires driving a live epoch boundary with alpenglow enabled and manipulating a vote account's balance between the filter snapshot and the burn call within `process_new_epoch`; this was not something I could execute or fully trace path-by-path with static search alone. The structural evidence supporting the risk is:
1. Filter criterion: [1](#0-0) 
2. Filter/burn call sequence and the documented but unenforced invariant: [5](#0-4) 
3. Independent snapshot construction earlier in the same epoch-boundary flow: [4](#0-3) 

I recommend a Devin session be used to write a targeted unit test in `runtime/src/bank/tests.rs` that: (a) constructs a bank with alpenglow active, (b) sets a vote account's balance to exactly `minimum_vote_account_balance_for_vat`, (c) between the filter computation and the burn call (e.g., via a modified/instrumented `update_epoch_stakes` test harness) reduces that vote account's lamports below `vat_to_burn_per_epoch` and confirms whether the existing `.expect()` panics, to conclusively prove or disprove exploitability.

    fn update_epoch_stakes(
        &mut self,
        leader_schedule_epoch: Epoch,
        prefiltered_distribution_vote_accounts: Option<VoteAccounts>,
    ) {
        // update epoch_stakes cache
        //  if my parent didn't populate for this staker's epoch, we've
        //  crossed a boundary
        if !self.epoch_stakes.contains_key(&leader_schedule_epoch) {
            self.epoch_stakes.retain(|&epoch, _| {
                // Note the greater-than-or-equal (and the `- 1`) is needed here
                // to ensure we retain the oldest epoch, if that epoch is 0.
                epoch >= leader_schedule_epoch.saturating_sub(MAX_LEADER_SCHEDULE_STAKES - 1)
            });
            // At the epoch boundary, `compute_new_epoch_caches_and_rewards`
            // has already produced the VAT-filtered vote-account snapshot;
            // reuse it here instead of re-cloning and re-filtering the
            // `stakes_cache`. Other callers (same-epoch refresh, warps)
            // fall back to `get_top_epoch_stakes`.
            let stakes = match prefiltered_distribution_vote_accounts {
                Some(prefiltered) => Stakes::new(prefiltered, self.epoch()),
                None => self.get_top_epoch_stakes(),
            };
            let stakes = SerdeStakesToStakeFormat::from(stakes);
            let new_epoch_stakes = VersionedEpochStakes::new(stakes, leader_schedule_epoch);
            info!(
                "new epoch stakes, epoch: {}, total_stake: {}",
                leader_schedule_epoch,
                new_epoch_stakes.total_stake(),
            );

            self.maybe_burn_vat_from_staked_accounts(&new_epoch_stakes);

            // It is expensive to log the details of epoch stakes. Only log them at "trace"
            // level for debugging purpose.
            if log::log_enabled!(log::Level::Trace) {
                let vote_stakes: HashMap<_, _> = self
                    .stakes_cache
                    .stakes()
                    .vote_accounts()
                    .delegated_stakes()
                    .map(|(pubkey, stake)| (*pubkey, stake))
                    .collect();
                trace!("new epoch stakes, stakes: {vote_stakes:#?}");
            }
            self.epoch_stakes
                .insert(leader_schedule_epoch, new_epoch_stakes);
        }
    }
