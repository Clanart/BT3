### Title
Unstaked repair-request flooding can drain the shared repair-serving bandwidth budget and starve legitimate (staked) repair requesters - (File: core/src/repair/serve_repair.rs)

### Summary
`ServeRepair::run_listen` / `handle_requests` guard outbound repair-response bandwidth with a single, unpartitioned `TokenBucket` (`data_budget`) shared by *all* incoming repair requesters, regardless of stake. Tokens are consumed in the arrival order of the batch rather than being weighted or reserved per-stake before consumption. An unstaked/low-stake peer (a normal, unprivileged validator identity — no admin or trusted role required) can flood the repair UDP port with cheaply-signed repair requests that arrive first in a processing batch, exhaust the shared budget, and cause the node to drop repair requests from legitimate, higher-stake validators for that interval, exactly analogous to the reported "submit/withdraw limit manipulation" pattern where a shared, unpartitioned limit is consumed by an attacker to disable the function for other users.

### Finding Description
`ServeRepair::listen` creates one process-wide `TokenBucket` capped at `MAX_BYTES_PER_SECOND` (12,000,000 bytes/sec) and reuses it across all callers of `run_listen`: [1](#0-0) 

Inside `run_listen`, incoming packets are batched (up to `target_max_buffered_packets`, e.g. 1024–4096) with no per-IP/per-stake admission control before decoding: [2](#0-1) 

`decode_requests` uses `data_budget.current_tokens()` only as a rough early-stop heuristic, and iterates the buffered packets in arrival order — not sorted by stake — so any request (staked or not) that lands earlier in the vector consumes the "remaining_budget_estimate" quota first: [3](#0-2) 

Stake-based prioritization only happens if the decoded-request count exceeds `MAX_REQUESTS_PER_ITERATION` (1024); otherwise no sort/truncation by stake occurs at all: [4](#0-3) 

The actual bandwidth token consumption in `handle_requests` is likewise FIFO over the (possibly unsorted) request list, not weighted by stake, and any request that fails the ping-cache check or produces no response gets a refund — but only after having already reserved (and thus temporarily denied to others) that budget: [5](#0-4) 

Because a repair request only needs to be a well-formed, signed `RepairProtocol` message — stake is merely looked up (`stake = 0` for unstaked/unknown identities) and does not gate whether the request is processed — an attacker can generate an arbitrary number of fresh unstaked keypairs at negligible cost and continuously send valid repair requests. There is no per-IP or per-stake partition of `data_budget` (unlike the QUIC/gossip layers, which use `KeyedRateLimiter`/per-IP `TokenBucket`s, e.g. `ConnectionRateLimiter` and the gossip `pull_request_budget`): [6](#0-5) [7](#0-6) 

No equivalent per-key isolation exists for the repair-serving `data_budget`, so a single unprivileged sender (or a handful of unstaked identities) whose requests happen to be processed earlier in a batch can consume the entire shared bandwidth allowance for that refill interval, causing `stats.dropped_requests_outbound_bandwidth` to be incremented for genuine (staked) repair requesters whose packets are processed later in the same batch/interval.

### Impact Explanation
This is the repair path used to serve missing shreds/blocks to peers that are catching up or reconstructing the ledger. If a validator's outbound repair-serving capacity is repeatedly drained by cheap, unstaked flood traffic, legitimate staked validators that legitimately need repair responses may be starved, delaying their ability to catch up to the cluster and increasing the risk of falling behind (a non-RPC remote resource-exhaustion/degradation effect on the repair/blockstore subsystem). It does not directly cause fund loss or consensus halt on its own, but it degrades repair availability for honest validators, which is exactly the "disable the action for other users" failure mode described in the source report, mapped onto Agave's unprivileged, unpartitioned shared rate limiter for repair-serving bandwidth.

### Likelihood Explanation
Likelihood is moderate: exploitation requires no special privilege, stake, or trust — anyone can create keypairs and sign well-formed `RepairProtocol` messages and send them over UDP to a target's repair port. The main friction is the ping-cache anti-spoof check (`check_ping_cache`), which requires completing a ping/pong round-trip per (sender, address) pair before requests are serviced, and the fact that the budget only fully drains under sustained volumetric flooding within the `MAX_BYTES_PER_SECOND` refill window. Still, since ping-cache success is per-identity and cheap to obtain (an attacker just needs to respond to the ping once), and the budget consumption/ordering has no stake weighting, sustained flooding from several unstaked identities is a realistic path to denying bandwidth to staked peers during that window.

### Recommendation
Partition the repair-serving `data_budget` per-stake or per-sender-class (e.g., reserve a guaranteed minimum bandwidth share for staked/whitelisted requesters similar to the QUIC/gossip `KeyedRateLimiter` pattern), and/or sort by stake before budget consumption regardless of whether `MAX_REQUESTS_PER_ITERATION` is exceeded, so that unstaked traffic cannot consume tokens ahead of staked traffic within the same batch.

### Proof of Concept
Conceptual (not executed): 
1. Generate N throwaway keypairs (unstaked).
2. For each, perform the repair ping/pong handshake once with the target validator's `serve_repair` UDP port to pass `check_ping_cache`.
3. Continuously send valid signed `RepairProtocol` requests (e.g. `WindowIndex`/`HighestWindowIndex`) from these unstaked identities at a rate that keeps `data_budget` near zero every `run_listen` iteration.
4. Observe (via the exposed `serve_repair-requests_received` datapoint, specifically `dropped_requests_outbound_bandwidth`) that requests from a legitimate staked validator sent concurrently are dropped due to bandwidth exhaustion, because the shared `TokenBucket` and FIFO ordering in `decode_requests`/`handle_requests` give no priority to stake unless the per-iteration decoded-request count exceeds 1024.         requests: Vec<BytesPacket>,
        epoch_staked_nodes: &Option<Arc<HashMap<Pubkey, u64>>>,
        whitelist: &HashSet<Pubkey>,
        my_id: &Pubkey,
        socket_addr_space: &SocketAddrSpace,
        mut remaining_budget_estimate: usize,
        stats: &mut ServeRepairStats,
    ) -> Vec<RepairRequestWithMeta> {
        const MIN_RESPONSE_SIZE: usize = PACKET_DATA_SIZE + SIZE_OF_NONCE;
        let decode_request = |request| {
            if remaining_budget_estimate < MIN_RESPONSE_SIZE {
                stats.dropped_requests_load_shed_sigverify += 1;
                return None;
            }
            let result = Self::decode_request(
                request,
                epoch_staked_nodes,
                whitelist,
                my_id,
                socket_addr_space,
            );
            match &result {
                Ok(req) => {
                    if req.stake == 0 {
                        stats.handle_requests_unstaked += 1;
                    } else {
                        stats.handle_requests_staked += 1;
                    }
                    // assuming we will reply to the request, we need to update the budget estimate
                    // some responses may be larger, but we have to be conservative here
                    remaining_budget_estimate -= MIN_RESPONSE_SIZE;
                }
                Err(e) => {
                    Self::record_request_decode_error(e, stats);
                }
            }
            result.ok()
        };
        requests.into_iter().filter_map(decode_request).collect()
    }

    fn handle_requests(
        &self,
        ping_cache: &mut PingCache,
        recycler: &PacketBatchRecycler,
        requests: Vec<RepairRequestWithMeta>,
        packet_batch_sender: &PacketBatchSender,
        stats: &mut ServeRepairStats,
        data_budget: &TokenBucket,
        byte_cost_multiplier: usize,
    ) {
        let identity_keypair = self.cluster_info.keypair();
        let mut pending_pings = Vec::default();

        for RepairRequestWithMeta {
            request,
            from_addr,
            stake,
            whitelisted: _,
        } in requests.into_iter()
        {
            // we deliberately consume early assuming that request succeeds,
            // if it does we will refund the unused tokens
            let max_response_cost = request.max_response_bytes() * byte_cost_multiplier;
            if data_budget
                .consume_tokens(max_response_cost as u64)
                .is_err()
            {
                stats.dropped_requests_outbound_bandwidth += 1;
                continue;
            }
            if !matches!(&request, RepairProtocol::Pong(_)) {
                let (check, ping_pkt) =
                    Self::check_ping_cache(ping_cache, &request, &from_addr, &identity_keypair);
                if let Some(ping_pkt) = ping_pkt {
                    pending_pings.push(ping_pkt);
                }
                if !check {
                    // return all borrowed tokens
                    data_budget.add_tokens(max_response_cost as u64);
                    stats.ping_cache_check_failed += 1;
                    continue;
                }
            }
            stats.processed += 1;
            let Some(rsp) = self.handle_repair(recycler, &from_addr, request, stats, ping_cache)
            else {
                data_budget.add_tokens(max_response_cost as u64);
                continue;
            };
