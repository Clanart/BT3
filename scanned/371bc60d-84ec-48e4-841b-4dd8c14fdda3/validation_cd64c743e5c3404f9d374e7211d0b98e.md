### Title
Delegator rewards deposited to an under-delegated vote account can be claimed entirely by a staker who delegates only at the reward-distribution boundary - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`DepositDelegatorRewards` (SIMD-0123) lets anyone add lamports to a vote account's `pending_delegator_rewards` counter at any time, independent of how much stake is currently delegated to that vote account. When rewards are later distributed, each delegated `Stake`'s share of `pending_delegator_rewards` is computed purely from its *current* proportion of `total_active_stake` at the reward-distribution snapshot, with no accounting for whether that stake was actually delegated during the period the rewards accumulated. This mirrors the Aave/Arcadia Tranche bug: a value ("earned interest" / `pending_delegator_rewards`) accrues to a pool before any (or before proportional) participants exist, and a participant who joins right at the settlement boundary can claim the whole accrued amount.

### Finding Description
`deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs` allows any signer to transfer lamports into a vote account and increment `pending_delegator_rewards` via `vote_state.add_pending_delegator_rewards(deposit)`, with no requirement that the vote account currently have any delegated stake: [1](#0-0) 

At the reward-payout epoch boundary, `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` computes each stake account's share of that vote account's `pending_delegator_rewards` strictly as `pending_delegator_rewards * stake / total_active_stake`, where `stake` and `total_active_stake` are the delegation values as of the reward epoch snapshot: [2](#0-1) 

The code comment itself acknowledges that stake proportions and `pending_delegator_rewards` are not reconciled against when the deposit actually happened ("if stake account has already received rewards, it's possible to have `stake > total_active_stake`... clamp it just to be safe") — this is purely a safety clamp against overflow/over-payment in aggregate, not a correctness guarantee that only stake delegated *during the accrual period* receives the reward.

The broken invariant: `pending_delegator_rewards` accrued while a vote account had zero (or very little) delegated stake is paid out pro-rata to whatever stake is delegated at the *next* distribution snapshot, not to the stake that was actually delegated while the rewards accrued. This is the exact analog of the reported bug: interest/rewards accrue to a pool independent of participation, and the eventual (dis)proportionate participant captures value they did not earn.

### Impact Explanation
A staker (or the validator operator itself, who fully controls when to call `DepositDelegatorRewards` and when new stake gets delegated/activates) can arrange for delegator-reward deposits to accumulate on a vote account with little or no active delegated stake, then have a new stake delegation activate right at the reward-distribution epoch boundary and collect a disproportionate—potentially the entire—share of `pending_delegator_rewards` that was economically intended to compensate different (or a larger set of) delegators. This results in fund misallocation/theft of delegator rewards from other stakers or from the depositor's intended beneficiaries.

### Likelihood Explanation
Likelihood is Medium: it requires a gap between when `DepositDelegatorRewards` deposits accumulate and when stake is delegated/activated to the vote account, similar to the original report's precondition (a gap between "eligible to earn" and "first deposit"). This is a plausible, unprivileged sequence of ordinary vote/stake operations (`DepositDelegatorRewards`, `DelegateStake`) that any account holder can trigger; no malicious peer, leaked key, or trusted-role assumption is required.

### Recommendation
Track `pending_delegator_rewards` accrual against the delegated-stake state at deposit time (e.g., only allow deposits proportional to currently active stake, or track a "rewards per stake-unit" accumulator similar to standard reward-per-token accounting) so that stake delegated after a deposit cannot retroactively claim rewards that accrued before its delegation was active. Alternatively, reject/queue `DepositDelegatorRewards` when `total_active_stake` for the vote account is zero, and only release accumulated rewards to stake weighted by time-in-delegation rather than point-in-time delegation at the payout snapshot.

### Proof of Concept
1. Vote account `V` exists with zero (or minimal) delegated stake.
2. Anyone calls `DepositDelegatorRewards` on `V` multiple times across several epochs, accumulating a large `pending_delegator_rewards` balance [1](#0-0) .
3. Just before the next reward-distribution epoch boundary, a staker delegates a stake account to `V` (or an existing minimal stake account is topped up), becoming (nearly) 100% of `total_active_stake` for `V` at the reward snapshot.
4. At distribution, `calculate_block_reward` computes this staker's share as `pending_delegator_rewards * stake / total_active_stake` ≈ `pending_delegator_rewards`, i.e. the staker collects essentially the entire pool of delegator rewards that accrued before their stake was ever delegated [3](#0-2) .

Note: I was unable to fully verify, due to tool-call limits, whether a later stage in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` decrements `pending_delegator_rewards` in a way that mitigates repeated over-claiming across multiple epochs (there were 9 references to `pending_delegator_rewards` in that file that I could not all inspect). This should be re-checked with full file access before treating the PoC as fully confirmed end-to-end.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
