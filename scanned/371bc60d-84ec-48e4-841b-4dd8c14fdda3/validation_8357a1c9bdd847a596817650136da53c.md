## Title
Extra lamports transferred into a stake account during the calculation-to-distribution window can silently inflate delegated stake beyond the amount the reward calculation snapshot accounted for - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

## Summary
This is the closest real Agave analog to the reported bug class: an action that changes user-controlled account state (a deposit/top-up) which is *not blocked* during a pending, multi-block, deferred settlement process, and which then gets folded into that deferred settlement in a way the original calculation did not anticipate. In the LendingPool report, depositing new collateral while `isUnderLiquidation` is true causes the new collateral to be swept into the liquidation. In Agave, `Bank::distribute_partitioned_epoch_rewards` runs over many blocks (per-epoch "Calculation" then "Distribution" phase) using a stake snapshot and reward numbers computed once at epoch-boundary, while the underlying stake account's lamport balance can still be freely mutated by ordinary transfer transactions before the distribution block for that account is reached.

## Finding Description
Rewards for an epoch are calculated once, at the epoch boundary, from the `stakes_cache` snapshot, and stored as `PartitionedStakeReward` entries that are distributed one partition per block over `REWARD_CALCULATION_NUM_BLOCKS`/multiple blocks [1](#0-0) . Actual crediting of the reward happens later in `build_updated_stake_reward`, which reads the **current** stake account from `stakes_cache_accounts` at distribution time and adds the pre-calculated reward to it [2](#0-1) .

Between the calculation block and the block that actually processes a given account's partition, ordinary system-program transfers can add lamports to the stake account (this is a normal, permitted operation - there is no guard analogous to `isUnderLiquidation` that blocks deposits to accounts with pending, uncommitted state). The comment in the codebase itself, `store_stake_accounts_in_partition`, explicitly assumes this cannot happen: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [3](#0-2) . That assumption is only about the delegation/stake-state mutation restrictions enforced by the stake program instructions; it does not restrict raw lamport transfers into the account via the system program, which the test suite itself demonstrates.

The unit test `test_delegation_adjustment_at_distribution` directly exercises this: it builds a `partitioned_stake_reward` entry from the calculation phase, then explicitly "transfers in more lamports before distribution time" by calling `checked_add_lamports` and `store_account` on the stake account prior to invoking `distribute_epoch_rewards_in_partition` [4](#0-3) . The test asserts that in the default configuration (no rent-adjustment feature), the delegation only reflects the pre-calculated reward and is unaffected — i.e. the extra lamports are *not* reflected in the effective stake amount used for warmup/cooldown accounting [5](#0-4) .

However, when `relax_post_exec_min_balance_check` (the SIMD-0392 rent-adjustment path) is active, `adjust_delegation_for_rent` recomputes the stake delegation using the account's *current* lamport balance at distribution time (`account.lamports()`), not the balance the calculation snapshot used [6](#0-5) [7](#0-6) . This is the exact same broken invariant as the LendingPool bug: a value frozen at the start of a multi-step process (`partitioned_stake_reward.inflation.stake`, computed at the epoch boundary) is combined with a *mutable* value read at settlement time (`account.lamports()`), where the mutable value can be changed by the user in between via an ordinary, unprivileged transfer, before the settlement (distribution) for that particular account has executed. There is no existing guard (equivalent to `isUnderLiquidation`) preventing lamport transfers into a stake account pending its reward distribution.

## Impact Explanation
Under the rent-adjustment code path, a staker who deposits additional lamports into their stake account after the epoch's reward calculation snapshot has been taken, but before their partition is processed in `distribute_epoch_rewards_in_partition`, can cause `adjust_delegation_for_rent` to derive a delegation figure using post-deposit lamports that were never part of the original point-value calculation, producing an inconsistency between capitalization accounting and the actual effective stake. Because `stake_reward_lamports_minted` is tracked from the (frozen) calculation amount while the stored delegation is derived from the live, deposit-inflated balance, the stake state written to the account and used by warmup/cooldown math for subsequent epochs can diverge from what the reward math and capitalization bookkeeping assumed, i.e., false state acceptance/incorrect accounting analogous to the LendingPool loss-of-funds scenario, though here it manifests as a state/consensus-accounting mismatch inside the runtime rather than a straightforward transfer of value to an attacker.

## Likelihood Explanation
Likelihood is low-to-medium: exploitation requires (1) the `relax_post_exec_min_balance_check` feature to be active, (2) precise timing of a lamport transfer into one's own stake account within the narrow multi-block window between epoch-boundary calculation and that account's specific distribution partition being processed, and (3) the account's rent-exempt minimum situation to actually engage the `adjust_delegation_for_rent` branch. The window is short (bounded by `REWARD_CALCULATION_NUM_BLOCKS` plus a handful of distribution blocks), but the trigger action (a plain SPL/system transfer to a stake account) is entirely unprivileged and requires no special access.

## Recommendation
Snapshot the stake account's lamport balance (not just its delegation) at calculation time and use that frozen balance in `adjust_delegation_for_rent`, or explicitly reject/ignore lamport deltas accrued between calculation and distribution when deriving the post-distribution delegation, so that a permissionless deposit performed during the pending distribution window cannot alter the delegation outcome relative to what was computed at the epoch boundary.

## Proof of Concept
The existing regression test already demonstrates the mechanics of the underlying primitive (deposit occurring between calculation and distribution): `test_delegation_adjustment_at_distribution` populates a stake account, computes its `PartitionedStakeReward` from the calculation phase, then calls `stake_account.checked_add_lamports(1_000_000_000)` followed by `bank.store_account(&stake_pubkey, &stake_account)` *before* calling `bank.distribute_epoch_rewards_in_partition(&partitioned_rewards, 0)` [8](#0-7) . This test passes only because `adjust_delegations_for_rent` is disabled in this scenario; enabling `relax_post_exec_min_balance_check` and re-running an analogous scenario against `check_rent_adjusted_stake_delegation` / `adjust_delegation_for_rent` with a pre/post deposit differing from the calculation-time balance would show the delegation figure tracking the live (attacker-controlled) balance rather than the frozen calculation snapshot [6](#0-5) .

**Uncertainty**: I could not confirm from the indexed code whether there are additional guards elsewhere (e.g., in the stake program's account-mutation validation) that specifically block *lamport-only* transfers (as opposed to state-changing stake instructions) into a stake account while `EpochRewardStatus::Active`. The comment at `distribution.rs:330-332` asserts stake-program restrictions prevent "further state mutation," but this appears scoped to stake-instruction state transitions, not plain system-program lamport transfers. Confirming this precisely, and whether `relax_post_exec_min_balance_check`/SIMD-0392 is active on mainnet-beta, would require running the full test suite or inspecting feature-activation status, which is not available through the current read-only index.

fn adjust_delegation_for_rent(
    delegation: &mut Delegation,
    rewarded_epoch: Epoch,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
) {
    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    if new_delegation != delegation.stake {
        delegation.stake = new_delegation;
        // Deactivate stake if needed. This deactivation is immediate,
        // unlike a requested deactivation which happens at the next epoch
        // boundary
        if new_delegation == 0 {
            delegation.deactivation_epoch = rewarded_epoch;
        }
    }
}
