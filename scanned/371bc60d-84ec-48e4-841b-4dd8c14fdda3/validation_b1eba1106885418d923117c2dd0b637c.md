## Analysis

The Talentir bug's root cause is: an attacker can cheaply flood a shared, unbounded data structure with many small entries; any legitimate operation that must enumerate/consume that structure is then forced to do unbounded work with no cap, causing resource exhaustion. The closest concrete analog in this Agave codebase is the **unbounded result collection in the non-indexed `getProgramAccounts`/`get_filtered_program_accounts` path**, which — unlike its "indexed" sibling — has no size cap on the accumulated results. ### Title
Unbounded result accumulation in non-indexed `getProgramAccounts` allows single-request memory/CPU exhaustion via cheap account spam - ([File: accounts-db/src/accounts.rs])

### Summary
`Accounts::load_by_program_with_filter` (the fallback path used by `get_filtered_program_accounts` whenever the relevant secondary index is not enabled, which is the default) scans all accounts and pushes every matching one into an in-memory `Vec` with no byte/size limit at all — unlike `load_by_index_key_with_filter`, which enforces `byte_limit_for_scan`/`scan_results_limit_bytes` and aborts the scan when exceeded.

### Finding Description
`load_by_program_with_filter` calls `accounts_db.scan_accounts` with a plain `ScanConfig::default()` and an unbounded `collector: Vec<KeyedAccountSharedData>`: [1](#0-0) 

Contrast this with the indexed variant, which explicitly tracks and enforces a size budget via `accumulate_and_check_scan_result_size`/`byte_limit_for_scan` and aborts the scan when the accumulated size grows too large: [4](#0-3) 

The RPC layer is explicit that the non-indexed path intentionally skips the byte-limit protection ("this path does not need to provide a mb limit because we only want to support secondary indexes"): [3](#0-2) 

An unprivileged attacker can cheaply create an arbitrarily large number of small accounts owned by a given program (e.g., a large batch of empty/near-empty SPL Token accounts, or accounts under an attacker-deployed program) — this is exactly the "many small entries at a chosen key" primitive from the original report, replacing "many cheap orders at the best price" with "many cheap accounts under one program owner." Once created, any single, low-rate `getProgramAccounts` RPC call against that program owner forces the node to materialize every matching account into an unbounded `Vec<KeyedAccountSharedData>` and then serialize it into a JSON-RPC response, with no cap on the resulting memory/CPU cost — exactly analogous to the marketplace being forced to loop over unboundedly many attacker-inserted orders with no minimum-order-size guard.

### Impact Explanation
This is a **single-client, low-rate RPC degradation/crash** vector — explicitly listed as valid impact. A single JSON-RPC request can force the target RPC node to allocate and serialize an attacker-controlled, effectively unbounded amount of account data, degrading or crashing the RPC-serving node (excessive memory allocation, GC/allocator pressure, thread-pool stall) from one connection at a time, without needing any RPC-side rate abuse — the cost multiplier comes from data planted on-chain beforehand via ordinary unprivileged transactions.

### Likelihood Explanation
Creating many small accounts under one program is cheap (rent-exempt minimum lamports per zero/small-data account) and requires no special privilege — any funded wallet can do this via ordinary transactions/CPI. The vulnerable code path (`load_by_program_with_filter`) is the *default* path taken whenever the relevant `AccountIndex` (ProgramId/SplTokenMint/SplTokenOwner) is not explicitly enabled, which is the out-of-the-box validator configuration, making this broadly reachable.

### Recommendation
Apply the same `byte_limit_for_scan`/abort mechanism used in `load_by_index_key_with_filter` (i.e., `accumulate_and_check_scan_result_size` + `ScanConfig::recreate_with_abort()`) to `load_by_program_with_filter`/`scan_accounts` so that non-indexed `getProgramAccounts` scans are also bounded by `scan_results_limit_bytes`, instead of relying solely on the secondary-index path for this protection.

### Proof of Concept
1. Do not enable `--account-index program-id` (default configuration).
2. Deploy a program `P` (or reuse a widely-queried owner such as the SPL Token program) and submit many ordinary, cheap transactions creating a very large number of small accounts owned by `P` (bounded only by attacker's lamports for rent-exemption).
3. Issue a single, low-rate `getProgramAccounts(P)` RPC call (optionally with filters that still match a large subset).
4. The RPC handler invokes `bank.get_filtered_program_accounts` → `Accounts::load_by_program_with_filter` → `accounts_db.scan_accounts` with `ScanConfig::default()` and an unbounded `Vec` collector [1](#0-0) , producing and serializing an attacker-sized response with no size cap, unlike the indexed code path that would have aborted via `byte_limit_for_scan` [2](#0-1) .

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
