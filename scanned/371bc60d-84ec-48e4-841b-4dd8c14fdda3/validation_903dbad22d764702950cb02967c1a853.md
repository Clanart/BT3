### Title
Unbounded `getProgramAccounts` full-table scan on public JSON-RPC allows unauthenticated single-request OOM/DoS - (File: `rpc/src/rpc.rs`)

### Summary
The Prysm report describes an unauthenticated, single-shot HTTP call (`GET /db/backup`) that forces the node to load its entire database into memory/disk, causing OOM or disk exhaustion, with no rate limiting or authentication protecting it. Agave's public JSON-RPC server exposes an analogous unauthenticated, single-request primitive: `getProgramAccounts` without a secondary account index configured. This method scans and materializes into memory every account owned by an arbitrary program ID across the entire accounts database, with no server-side cap on the number of accounts or total bytes returned, unlike the secondary-index scan path which explicitly threads through a byte limit.

### Finding Description
`getProgramAccounts` is implemented in the `AccountsScanImpl` trait impl and dispatches to `JsonRpcRequestProcessor::get_program_accounts`, which calls `get_filtered_program_accounts` [1](#0-0) .

Inside `get_filtered_program_accounts`, if the node's secondary `AccountIndex::ProgramId` index is not configured for the requested program (the common case — indexes are opt-in via validator flags), the code falls to the `else` branch, which calls `bank.get_filtered_program_accounts` directly, with no byte/count limit parameter at all [2](#0-1) . Contrast this with the indexed branch, `get_filtered_indexed_accounts`, which explicitly threads a `byte_limit_for_scan` [3](#0-2) .

`Bank::get_filtered_program_accounts` (unindexed path) delegates to `Accounts::load_by_program_with_filter`/`load_by_program`, which perform a full scan across all rooted+ancestor slots for the given `program_id`, pushing every matching account into an in-memory `Vec<KeyedAccountSharedData>` with no size cap [4](#0-3) . Because system-owned accounts, well-known token programs, or any program with millions of accounts can be targeted, a single client request can force the validator to allocate memory proportional to the entire live account set owned by that program — potentially many gigabytes on a mainnet-scale ledger.

This is invoked from the public JSON-RPC HTTP endpoint without any authentication, exactly mirroring the "unauthenticated endpoint that performs a memory/disk-heavy full-database operation" pattern from the Prysm report. Unlike the Prysm case (which required an explicit `--enable-db-backup-webhook` opt-in flag), this RPC method is available by default whenever `--full-rpc-api` behavior is enabled (the default for many public RPC deployments), and the dangerous unindexed fallback path is the *default* configuration unless the operator has explicitly configured `--account-index program-id` for every program a client might query.

### Impact Explanation
A single, unauthenticated, low-rate RPC request (`getProgramAccounts` targeting a large program) can force the node's RPC-serving process to allocate an amount of memory proportional to the total size of every account owned by that program, with no configurable cap in the non-indexed code path. On a public RPC node this can trigger OOM kill or severe latency degradation for all clients, matching the "single-client low-rate RPC crash/degradation" and "non-RPC remote exhaustion" impact classes.

### Likelihood Explanation
Likelihood is high for any RPC node that does not proactively configure secondary account indexes for every commonly-queried program — which is the out-of-the-box default. An attacker needs no special access: this is the standard, unauthenticated public JSON-RPC HTTP port, reachable directly or via CSRF/SSRF exactly as in the source report.

### Recommendation
Enforce a hard byte/count limit on the unindexed `get_filtered_program_accounts` scan path in `rpc/src/rpc.rs` (mirroring the `byte_limit_for_scan` already used for the indexed path in `runtime/src/bank.rs`), returning an RPC error (e.g., a "response too large, add filters or use an index" error) once the accumulated result size exceeds a configurable threshold, rather than allowing unbounded in-memory accumulation.

### Proof of Concept
1. Run a validator/RPC node without configuring `--account-index program-id` for the System Program or a large SPL program.
2. Send a single unauthenticated request: `curl -X POST -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["11111111111111111111111111111111"]}' http://<rpc-host>:8899`.
3. Observe the RPC thread's memory usage spike proportional to the total data size of all matching accounts (confirmed by the unbounded `Vec` accumulation in `get_filtered_program_accounts`/`load_by_program`), potentially triggering OOM or severe service degradation for a node with a large account set matching that owner.
