In `Operator::withdraw` (core/src/operator.rs), the caller supplies `withdrawal_index`, `in_signature` (SinglePlusAnyoneCanPay), `in_outpoint`, `out_script_pubkey`, `out_amount` to `create_payout_txhandler`. Preconditions: withdrawal `withdrawal_index` is registered on Citrea with a specific UTXO. Call sequence: `withdraw` checks `withdrawal_utxo != input_utxo.outpoint` against `Database::get_withdrawal_utxo_from_citrea_withdrawal`, but nothing marks that withdrawal index as consumed once one operator's payout tx enters the mempool. A second operator (also unprivileged relative to each other under this model, but consider an attacker replaying the same signed WithdrawParams via the public aggregator RPC to a second operator) submits the same `WithdrawParams` to a different operator process before the first payout confirms. Binding that breaks: at most one payout transaction per withdrawal_index == exactly one operator fronting funds for withdrawal_index. Impact: Critical - two operators fund/attempt the same payout, one of whom cannot ever be reimbursed once the withdrawal UTXO is spent by the other's tx, permanently freezing their reachable Reimburse path. Proof idea: core/src/test cargo test issuing withdraw() concurrently on two operator instances with the same WithdrawParams and asserting only one succeeds while the loser's payout_tx has no path to Reimburse.
