In `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs), `op_return_txout` embeds `operator_xonly_pk` chosen by the operator, not derived from which wallet's UTXOs funded the transaction via `fund_raw_transaction`/`sign_raw_transaction_with_wallet` in `Operator::withdraw`. Preconditions: withdrawal is registered; an unprivileged attacker cannot set the OP_RETURN, but can, by broadcasting a conflicting RBF replacement of the funding inputs (fee-bumping via mempool.space accelerator in `send_testnet4_nonstandard_tx` on testnet4, which the attacker can also call by supplying any transaction to the public accelerator endpoint) alter which inputs actually end up funding the confirmed transaction while leaving OP_RETURN bytes unchanged. Call sequence: `fund_raw_transaction` adds inputs -> operator signs -> attacker broadcasts a fee-bumped double-spend of the operator's added inputs (which are not anchored/locked against replacement) with the same OP_RETURN and payout output, funded instead by the attacker. Binding: OP_RETURN operator_xonly_pk == the xonly pk whose wallet inputs paid for the confirmed transaction's outputs. Impact: Critical - an unprivileged attacker could construct a variant of the payout transaction (same OP_RETURN, same withdrawal-UTXO input, replaced funding inputs) that gets mined instead, at which point `update_finalized_payouts` attributes the payout to the operator named in OP_RETURN even though the attacker's coins covered the value. Proof idea: core/src/test/deposit_and_withdraw_e2e.rs-style cargo test that funds a payout via a wallet-added input, then have a second party RBF-replace only the funding input (keeping OP_RETURN/withdrawal input) and confirm `get_payout_info_from_move_txid` still names the original operator.
