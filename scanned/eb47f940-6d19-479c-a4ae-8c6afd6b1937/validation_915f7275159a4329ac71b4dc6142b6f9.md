Based on the investigation, I found a real Agave analog matching the bug class described in the report: a value computed once under an implicit "state is roughly static" assumption is cached and reused for a long-lived operation, without ever being revalidated against the real, current state — exactly the failure mode in OnlyBoost's `rebalance()`.

### Title
Stale stake-ratio classification and `total_stake` snapshot in QUIC stake-weighted QoS causes persistent unfair/unbounded stream allocation - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::build_connection_context` computes a connection's `peer_type` (Staked vs. Unstaked) and caches `total_stake` a single time, at connection establishment, based on the gossip-derived `StakedNodes` snapshot available at that instant. This cached `SwQosConnectionContext` is then reused, unmodified, for the entire lifetime of the QUIC connection to compute per-stream throttling budgets via `available_load_capacity_in_throttling_duration`. If the real total stake or the peer's relative stake ratio changes meaningfully while the connection remains open (which QUIC connections commonly do for extended periods), the throttling decision is made against stale inputs, similarly to how OnlyBoost's `rebalance()` computed an "optimal" split against pre-withdrawal state that no longer matched reality after a large state change.

### Finding Description
`build_connection_context` snapshots stake data once: [1](#0-0) 

The resulting `peer_type` and `total_stake` fields are stored in `SwQosConnectionContext`: [2](#0-1) 

For every new stream on that connection, `on_new_stream` reuses this same, unrefreshed context to compute the throttling budget: [3](#0-2) 

which calls `max_streams_per_throttling_interval`, passing the cached `total_stake` straight into `available_load_capacity_in_throttling_duration`: [4](#0-3) 

The per-connection allocation is a direct linear proportion of `stake / total_stake`: [5](#0-4) 

This is structurally identical to the OnlyBoost bug: a proportional-split calculation (`stake_ratio` vs. `min_stake_ratio`, and later `stake / total_stake`) is computed once from a point-in-time state snapshot and is implicitly assumed to remain approximately valid ("S ~= S0") for the entire subsequent lifetime of the connection/operation. There is no mechanism analogous to "recompute before acting" — the connection's `peer_type`/`total_stake` is never refreshed against the live `staked_nodes` map (which is updated on every epoch boundary and gossip stake update) for the life of a still-open connection, and no code path re-derives `SwQosConnectionContext` mid-connection.

### Impact Explanation
Because `peer_type` classification and `total_stake` are frozen at connection-open time, a connection opened while total network stake was low (e.g., right after `staked_nodes` bootstrap, or during a period with fewer active validators) locks in an inflated `stake_ratio`, and thus an inflated `max_uni_streams` / per-throttle-window stream budget, for as long as that single QUIC connection is kept alive — even as the real total stake grows and the connection's fair share shrinks. This degrades QoS fairness for legitimate higher-stake validators sharing the TPU/QUIC ingestion path and can be leveraged by a low-stake but validly staked peer to sustain outsized throughput against the leader's `swqos` streamer, i.e. non-RPC remote resource consumption/degradation on the transaction-ingestion path.

### Likelihood Explanation
Exploitation only requires being any legitimately staked participant (no malicious-validator collusion, no privileged access) opening and keeping open a long-lived QUIC connection across a period where the real `total_stake` denominator changes materially (stake activation/deactivation is routine every epoch). No additional guard exists in `swqos.rs` or `stream_throttle.rs` to detect staleness or force periodic re-derivation of `SwQosConnectionContext`, making the drift persistent for the whole connection lifetime rather than self-correcting.

### Recommendation
Periodically re-derive (or at minimum periodically refresh `total_stake`/`peer_type`) for long-lived connections against the current `staked_nodes` snapshot — e.g., recompute `SwQosConnectionContext` fields on an interval (similar to the existing `STREAM_LOAD_EMA_INTERVAL_MS`/`STREAM_THROTTLING_INTERVAL_MS` cadences already present in `stream_throttle.rs`) rather than caching them permanently at `build_connection_context` time, mirroring the OnlyBoost fix of recomputing the optimal split from live state rather than relying on a value computed under a since-invalidated "small delta" assumption.

### Proof of Concept
1. Attacker (or any staked node) opens a QUIC connection to the TPU at a time `T0` when `staked_nodes` total stake is `S0`, e.g. right after startup or during low validator participation.
2. `build_connection_context` computes `stake_ratio = stake / S0` and stores `total_stake = S0` in `SwQosConnectionContext`, granting a corresponding per-connection stream budget via `available_load_capacity_in_throttling_duration(peer_type, S0)`.
3. The attacker keeps the connection open (no re-negotiation forced by the server) while real total stake grows to `S1 >> S0` over subsequent epochs.
4. Every subsequent stream on that connection still calls `max_streams_per_throttling_interval` with the stale `S0`, so the attacker's allocated budget stays `stake / S0` instead of the fair `stake / S1`, granting a persistently oversized share of the staked throttling window compared to what a freshly-established connection at the same stake would receive.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };

                SwQosConnectionContext {
                    peer_type,
                    total_stake,
                    remote_pubkey: Some(pubkey),
                    in_staked_table: false,
                    remote_address,
                    last_update: Arc::new(AtomicU64::new(timing::timestamp())),
                    stream_counter: None,
                }
            },
        )

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
