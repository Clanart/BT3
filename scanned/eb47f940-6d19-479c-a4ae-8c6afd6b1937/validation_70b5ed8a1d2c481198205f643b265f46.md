### Title
Vote account `pending_delegator_rewards` is never decremented after block-reward distribution, allowing repeated/unbounded reward payout from a single deposit - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Sherlock report's root cause is a classic "dual-ledger" bug: one side of an accounting pair (the CDS's cumulative profit value) is updated while the companion ledger (`totalCdsDepositedAmount`) is not, so the two diverge and a legitimate operation (withdrawal) later reverts. The Agave analog is in the SIMD-0123 "delegator rewards" feature: a vote account's `pending_delegator_rewards` field acts as a deposited-funds pool that is consumed every epoch to compute `block_reward` payouts to delegators' stake accounts, but nothing in the distribution path ever decrements `pending_delegator_rewards` on the vote account to reflect that consumption.

### Finding Description
`deposit_delegator_rewards` transfers lamports into a vote account and increments `pending_delegator_rewards` by the deposited amount in lock-step: [1](#0-0) 

Every epoch, `calculate_block_reward` reads the vote account's *current* `pending_delegator_rewards` value and computes each delegator's proportional share of it, explicitly noting the value is used as the divisible reward pool: [2](#0-1) 

That computed `block_reward` is then credited directly to the stake account's lamports via `checked_add_lamports` in `build_updated_stake_reward`: [3](#0-2) 

and summed into `block_reward_lamports_distributed`, which is used only to debit the `EpochRewards` sysvar and is *not* added to `self.capitalization` (only the inflation portion `stake_reward_lamports_minted` is): [4](#0-3) 

Nowhere in `distribution.rs` — the module that actually performs the payout and mutates account state — is `pending_delegator_rewards` written back to zero or decremented; a repository-wide search of that file for the field returns no matches. The only place the field is ever mutated is `add_pending_delegator_rewards` (increment-only) in the vote program: [5](#0-4) 

The invariant the code assumes is: `pending_delegator_rewards` represents an as-yet-unpaid liability funded by a one-time deposit, and `withdraw()` uses it to reserve the vote account's rent-exempt + pending balance so the authorized withdrawer cannot withdraw funds earmarked for delegators: [6](#0-5) 

Because `calculate_block_reward` treats `pending_delegator_rewards` as a *pool to be divided* but never records that the pool has been paid out, the exact same pool value is available to be redivided and redistributed again in every subsequent epoch that the vote account remains active with stake — as long as `pending_delegator_rewards` is nonzero, `calculate_block_reward` keeps handing out a share of it to every epoch's stakers, and the vote account's own lamports (from which the deposit originated) are never debited to fund those payouts. This is the same "one side of a two-sided ledger update was forgotten" defect as the Sherlock report, just inverted in effect: instead of a shortfall that blocks legitimate withdrawal, it is a shortfall in debiting that allows unbounded reissuance of the same deposited value as new stake-account lamports every epoch, with the block-reward accounting explicitly bypassing the capitalization fetch_add that would normally guard against silent supply inflation.

### Impact Explanation
This breaks the fund-accounting invariant that a delegator-rewards deposit is a finite, one-time pool. A single `DepositDelegatorRewards` deposit (an ordinary permissionless instruction, invocable by any signer once SIMD-0123/0232/0291/block-revenue-sharing features are active) would be redistributed to stakers every epoch that the vote account continues to have active stake, rather than being consumed once. Because the payout is credited to stake accounts as real lamports (`checked_add_lamports`) but the source is never debited and — critically — `block_reward_lamports_distributed` is excluded from the `capitalization` fetch_add, the bank's tracked `capitalization` value diverges from the true sum of all account lamports over time. This is an unprivileged, non-malicious-validator path (ordinary transaction submitted by any user) that produces incorrect/inflated economic state — a "false execution/acceptance" class issue affecting fund accounting integrity, since lamports are effectively minted for delegators beyond what was ever deposited, without a corresponding capitalization increase.

### Likelihood Explanation
Every validator applies the identical deterministic reward-calculation code each epoch, so this does not directly cause a consensus fork by itself (all honest nodes compute the same wrong-but-consistent result), but it is triggered automatically and repeatedly (once per epoch) for any vote account that has ever received a delegator-rewards deposit and continues to have active stake — no adversarial timing or race condition is required, only the passage of epochs. The bug is baked into the still-unreleased/newly-added SIMD-0123 code path used for the Alpenglow/block-revenue-sharing reward calculation.

### Recommendation
In `store_stake_accounts_in_partition` / `distribute_epoch_rewards_in_partition` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs`), after computing and crediting `block_reward` amounts to stake accounts, decrement each corresponding vote account's `pending_delegator_rewards` by the total `block_reward` amount actually distributed for that vote account (and correspondingly debit the vote account's lamports, or explicitly account for the transfer in `capitalization`), so that the deposited pool is consumed exactly once rather than being redivided every epoch.

### Proof of Concept
Not independently executable from the index alone (no test harness reachable here exercises multi-epoch reward distribution against a vote account with nonzero `pending_delegator_rewards`); however, the existing unit tests already demonstrate the two halves of the missing linkage separately: `test_deposit_delegator_rewards` shows `pending_delegator_rewards` only ever increasing, and `test_calculate_block_reward_specific`/`get_block_reward_for_test` show `calculate_block_reward` computing payouts purely from the current (static) `pending_delegator_rewards` value with no side effect that reduces it: [7](#0-6) 
A multi-epoch integration test that (1) deposits delegator rewards, (2) runs `distribute_partitioned_epoch_rewards` across two epoch boundaries with the same active stake, and (3) asserts `pending_delegator_rewards` is unchanged while stake-account lamports increased twice, would confirm the double-payout.

    pub(crate) fn add_pending_delegator_rewards(
        &mut self,
        amount: u64,
    ) -> Result<(), InstructionError> {
        match &mut self.target_state {
            TargetVoteState::V4(v4) => {
                v4.pending_delegator_rewards = v4
                    .pending_delegator_rewards
                    .checked_add(amount)
                    .ok_or(InstructionError::ArithmeticOverflow)?;
                Ok(())
