### Title
Unbounded secondary-index pubkey enumeration before `scan_results_limit_bytes` check enables RPC resource exhaustion - (File: `accounts-db/src/accounts_db.rs`)

### Summary
`Accounts::load_by_index_key_with_filter` is intended to bound `get_filtered_indexed_accounts` (used by `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate`, etc.) to a validator-configured `scan_results_limit_bytes`. However, the byte-limit check (`accumulate_and_check_scan_result_size`/`config.abort()`) is only applied while consuming a `Vec<Pubkey>` that was already fully materialized *before* the check loop began. An unprivileged client can choose an `index_key` (`ProgramId`/`SplTokenMint`/`SplTokenOwner`) whose secondary-index membership set is very large (e.g. a widely-used program id such as the SPL Token program, or a popular mint/owner) and force the RPC-thread to do O(n) work proportional to the *entire* index membership for that key, independent of the configured byte cap.

### Finding Description
`AccountsDb::index_scan_accounts` does: [1](#0-0) 

```
for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key) {
    if config.is_aborted() { break; }
    if let Some((account, slot)) = self.do_load(...) {
        scan_func(...)
    }
}
```

`get_index_key_pubkeys` returns `Vec<Pubkey>` by calling the underlying `SecondaryIndex::get`: [2](#0-1) [3](#0-2) 

```
pub fn get(&self, key: &Pubkey) -> Vec<Pubkey> {
    if let Some(inner_keys_map) = self.index.get(key) {
        inner_keys_map.keys()
    } else { vec![] }
}
```

and `RwLockSecondaryIndexEntry::keys()` clones the *entire* `HashSet<Pubkey>` for that key into a new `Vec`: [4](#0-3) 

This call — `for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key)` — happens as a single, unconditional, eagerly-evaluated expression that produces the full `Vec<Pubkey>` (all pubkeys ever mapped under that index key) *before* the `for` loop's `config.is_aborted()` check has any chance to run. The `scan_results_limit_bytes`/`ScanConfig::abort()` mechanism (`Accounts::load_by_index_key_with_filter`, `accumulate_and_check_scan_result_size`) only takes effect once loading (`do_load`) begins: [5](#0-4) 

So the enumeration cost (allocating/copying `n` `Pubkey`s, where `n` is the total number of accounts indexed under the chosen `ProgramId`/`SplTokenMint`/`SplTokenOwner` key) is entirely independent of `scan_results_limit_bytes`, and there is no upper bound on `n` set by that config option: `include_key` in `AccountSecondaryIndexes` allows any key unless the validator operator explicitly configured an exclude/include list, and by default `None => true, // include all keys`: [6](#0-5) 

Note: the subsequent `do_load` loop itself *is* correctly bounded — `config.is_aborted()` is checked before every `do_load`, so the loop stops shortly after `scan_results_limit_bytes` is exceeded (only marginal overshoot beyond the configured limit, not the entire index). The vulnerability is specifically in the pubkey-list materialization step (`get_index_key_pubkeys`), which is O(index-membership-size) and runs unconditionally regardless of the byte limit.

### Impact Explanation
An attacker with no special privileges can send a single `getProgramAccounts` (with a program id known to own a very large number of accounts, e.g. widely used built-in/SPL programs) or `getTokenAccountsByOwner`/`getTokenAccountsByMint` request (choosing a mint/owner with many associated token accounts) to a validator running with secondary indexes enabled (`--account-index program-id`/`spl-token-mint`/`spl-token-owner`) and `scan_results_limit_bytes` configured to a small value expecting it to bound resource use. This single low-rate call forces the RPC-thread to synchronously enumerate/allocate the *entire* pubkey membership set for that key (potentially millions of `Pubkey`s, tens/hundreds of MB) before the byte-limit is ever consulted, consuming CPU and memory proportional to total secondary-index size rather than the configured cap. Repeated single low-rate calls (still within a single-client's published request-rate limits) can be used to repeatedly force this large uncapped allocation/copy, degrading the RPC/pubsub service for other clients on that node.

This falls within the stated valid impact class: "single-client low-rate RPC crash/degradation" via a public RPC input, without needing malicious peer/validator assumptions.

### Likelihood Explanation
Likelihood is moderate: it requires the validator operator to have enabled a secondary account index (`account_indexes` non-empty) and to have configured `scan_results_limit_bytes` (this is an opt-in mitigation, so if unset, no limit is expected anyway and this isn't a regression for that case — the finding specifically matters for operators relying on `scan_results_limit_bytes` as their DoS mitigation). Given that secondary indexes and `scan_results_limit_bytes` exist precisely to protect against exactly this class of abuse, and large index-key membership sets (e.g. system/token programs) exist naturally on real clusters without any attacker action, the precondition is realistic for validators exposing indexed RPC methods publicly.

### Recommendation
Move the byte-limit (and abort) check into the pubkey-enumeration step itself, or replace the eager `Vec<Pubkey>` collection in `SecondaryIndex::get`/`get_index_key_pubkeys` with a bounded/streaming iterator that `index_scan_accounts` can short-circuit while enumerating, so that the enumeration cost — not just the subsequent `do_load` cost — is capped by `scan_results_limit_bytes` (or a separate configured cap on enumerated-pubkey count). At minimum, add an explicit cap on the number of pubkeys enumerated per index key before consulting `scan_results_limit_bytes`/aborting, so a single request cannot force O(total-index-membership) allocation regardless of the configured byte budget.

### Proof of Concept
1. Start a validator with a secondary index enabled, e.g. `--account-index program-id`, and set `scan_results_limit_bytes` to a small value (e.g. 4096 bytes) via `JsonRpcConfig`.
2. Populate the accounts index so that one `program_id` owns far more data than `scan_results_limit_bytes` allows — e.g., create many accounts owned by a single program id such that the secondary index's `program_id_index` entry for that key has a large membership count (this reflects real-world large program ids like SPL Token on mainnet, or can be simulated in a test cluster by funding many accounts under one program).
3. Issue a single `getProgramAccounts(program_id)` RPC call for that program id.
4. Observe (e.g. via `perf`/heap profiling or timing) that the RPC-processing thread spends CPU/memory proportional to the *total* number of pubkeys indexed under that program id (from the `SecondaryIndex::get`→`RwLockSecondaryIndexEntry::keys()` clone in `accounts-db/src/accounts_index/secondary.rs:104-106`), which occurs before `accumulate_and_check_scan_result_size`/`config.abort()` in `accounts-db/src/accounts.rs:396-433` ever runs, confirming the enumeration cost is not bounded by `scan_results_limit_bytes` — even though the subsequent full-account-loading phase is correctly aborted shortly after the byte budget is exceeded.
