### Title
Custom commission collector rent-exemption bypass via unchecked `pre_lamports` in `Bank::collector_type_checked` - ([File: runtime/src/bank/fee_distribution.rs])

### Summary
The external report flags that Gearbox's Yearn adapter records `balanceBefore` but never validates it is meaningful (`> 0`) before using it to drive downstream accounting. The Agave analog is in `Bank::deposit_fees` / `Bank::collector_type_checked`, where `pre_lamports` (the collector account's balance captured *before* the fee deposit) is used only as a boolean gate (`pre_lamports == 0`) rather than being combined with the account's actual pre-deposit rent state, unlike the parallel non-custom-collector path which uses the full `RentState` transition check via `check_static_account_rent_state_transition`.

### Finding Description
In `runtime/src/bank/fee_distribution.rs`, `deposit_fees` branches on whether `custom_commission_collector` (SIMD-0232) is active: [1](#0-0) 

For the custom-collector path, `pre_lamports` is captured and passed to `collector_type_checked`, which performs this check: [2](#0-1) 

The guard is: fail only if the account is *not* rent-exempt **and** (`relax_post_execution_balance_checks` is off **or** `pre_lamports == 0`). This means that once `relax_post_execution_balance_checks` (SIMD-392) is active, any collector account with a nonzero `pre_lamports` — regardless of whether that balance was itself below the rent-exempt minimum (i.e., already in the `RentPaying` state) — is permitted to receive a fee deposit and remain non-rent-exempt afterward.

Contrast this with the non-custom-collector path a few lines above, which uses `check_static_account_rent_state_transition`: [3](#0-2) 

That function computes the actual pre- and post-execution `RentState` (`Uninitialized` / `RentPaying{..}` / `RentExempt`) and only allows transitions permitted by `transition_allowed` (defined in `svm/src/rent_calculator.rs`), including the SIMD-392 relaxation that requires the account to have been `RentExempt` pre-execution and non-decreasing in balance: [4](#0-3) 

The custom-collector path does not call this shared state-machine logic at all — it substitutes a much weaker, ad hoc `pre_lamports == 0` check that conflates "account previously existed with any lamports" with "account was previously rent-exempt." This is exactly the same bug class as the reported issue: a `*_before` value is captured but never checked for the invariant that actually matters (here, "was rent-exempt", not merely "was nonzero"), so a check meant to enforce SIMD-0232's "rent-exempt after depositing inflation rewards commission" invariant can be silently bypassed.

### Impact Explanation
This affects the block-revenue/commission-collector accounts introduced by SIMD-0232/SIMD-0464. A collector account that is already `RentPaying` (nonzero but sub-rent-exempt lamports) prior to a leader setting it as `block_revenue_collector` can keep receiving fee-commission deposits indefinitely without ever reaching rent exemption, and without the deposit being burned/rejected as the SIMD-0232 invariant intends. Since the check that should enforce "collector must become/remain rent-exempt" is bypassed, this weakens the accounts-side and rent-state invariants that the runtime relies on for account lifecycle correctness, and diverges from the parity guarantee that both collector paths are supposed to enforce the same rent-exemption rule.

### Likelihood Explanation
This triggers deterministically whenever `custom_commission_collector` and `relax_post_execution_balance_checks` (SIMD-392) are both active and a leader sets a non-rent-exempt, nonzero-lamport system account as its `block_revenue_collector` (permitted by `NewCommissionCollector::validate_and_resolve_key`, used in vote-state commission-collector updates). No malicious peer or privileged role is required — a single validator operator configuring its own vote account's collector triggers the path on every block it produces.

### Recommendation
Replace the ad hoc `pre_lamports == 0` gate in `collector_type_checked` with the same `RentState`-based transition check (`get_pre_exec_account_rent_state` / `check_static_account_rent_state_transition`) used in the non-custom-collector branch, so both code paths enforce an identical, correctly-modeled rent-exemption invariant instead of a coarse "was the balance nonzero before" proxy.

### Proof of Concept
1. Enable `custom_commission_collector` and `relax_post_exec_min_balance_check` feature flags.
2. Create a system-owned collector account `C` with `1 < lamports(C) < rent_exempt_minimum` (i.e., `RentState::RentPaying`), owned by the system program, not reserved, not the incinerator.
3. Set a validator's vote account `block_revenue_collector` to `C` (via `initialize_account_v2`/commission-collector update, satisfying `NewCommissionCollector::validate_and_resolve_key`).
4. As leader, produce a block; `distribute_transaction_fee_details` → `deposit_or_burn_fee` → `deposit_fees(C, fee)` runs with `custom_commission_collector` true.
5. In `collector_type_checked`, `pre_lamports = lamports(C) > 0`, so even though `account` remains below `rent.minimum_balance(...)` after the deposit, the `!rent.is_exempt(...) && (!relax || pre_lamports == 0)` condition is `false` (because `pre_lamports != 0` and `relax` is true), so the function returns `Ok(ExternalCollectorType::SystemAccount)` instead of `Err(InvalidRentPayingAccount)`.
6. The deposit succeeds and `C` remains a non-rent-exempt account holding fee revenue indefinitely, unlike the equivalent leader-id (non-custom-collector) case which would be rejected/burned by `check_static_account_rent_state_transition` under the identical balance conditions absent a prior `RentExempt` state.

/// Determine the post-execution rent state of an account.
///
/// Equivalent to get_account_rent_state, with the additional option of
/// relaxing the criteria to designate an account as RentExempt. The relaxed
/// designation follows the rules specified by SIMD-392.
pub fn get_post_exec_account_rent_state(
    account_lamports: u64,
    account_size: usize,
    min_balance: u64,
    pre_rent_state: &RentState,
    pre_exec_balance: u64,
    relax_rent_exempt_criteria: bool,
) -> RentState {
    if !relax_rent_exempt_criteria {
        return get_account_rent_state(account_lamports, account_size, min_balance);
    };

    match (account_lamports, &pre_rent_state) {
        (0, _) => RentState::Uninitialized,
        (post_balance, _) if post_balance >= min_balance => RentState::RentExempt,
        (post_balance, RentState::RentExempt) if post_balance >= pre_exec_balance => {
            RentState::RentExempt
        }
        (post_balance, _) => RentState::RentPaying {
            data_size: account_size,
            lamports: post_balance,
        },
    }
}
