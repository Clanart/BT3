### Title
Potential division-by-zero freeze in Alpenglow voting-reward calculation when `total_stake_lamports` is zero - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
The Sherlock report describes a class of bug where a share-based accounting system computes a rate as `numerator / denominator`, and once the denominator collapses to zero while the numerator (supply/points) remains non-zero, all subsequent operations that depend on that division revert/fail, freezing the system until an unlikely recovery path (full share burn) occurs. The closest structural analog in Agave is the epoch/slot-level reward-rate calculation in the Alpenglow voting reward path, `calculate_reward`, which divides by `total_stake_lamports` (and `slots_per_epoch`) without an explicit check that the denominator is non-zero.

### Finding Description
`calculate_reward` in `runtime/src/block_component_processor/vote_reward.rs` computes a per-slot/per-validator reward as:

```
numerator   = max_possible_validator_reward * validator_stake_lamports
denominator = slots_per_epoch * total_stake_lamports
reward_lamports = (numerator / denominator).try_into().unwrap()
``` [1](#0-0) 

This mirrors the Carapace bug pattern: an exchange-rate/ratio style calculation (`fractional_stake * per_slot_inflation`) that divides a fixed numerator by a "total" denominator representing aggregate stake/supply. In the Carapace case, `totalSTokenUnderlying` could reach zero while `totalSupply` remained non-zero, causing `_getExchangeRate()`(`totalSTokenUnderlying / totalSupply`) to be zero and any subsequent division by that rate to revert, freezing deposits/protection buys. Here the analogous "total" quantity is `total_stake_lamports`, which is the reward-epoch's cluster-wide stake denominator used to size an individual validator's/leader's share of the per-slot inflation pool.

Similarly, the underlying points-based reward calculation in `runtime/src/inflation_rewards/points.rs::calculate_alpenglow_points` divides `earned_credits * stake_amount` by a `total_stake` value fetched from `reward_epoch_delegated_stakes.delegated_stakes`; that function explicitly guards against a zero denominator via `.filter(|stake| *stake != 0)` and returns an `Err(...)` when the stake is missing/zero [2](#0-1) . This shows the pattern is recognized as a hazard elsewhere in the codebase, but `calculate_reward`'s `total_stake_lamports` denominator does not have a similarly explicit guard at the point of division [3](#0-2) .

### Impact Explanation
If `total_stake_lamports` could ever be zero (e.g. due to an epoch-boundary edge case where no active/eligible stake is recorded for a reward epoch, or a data plumbing bug feeding a stale/uninitialized total), the division at line 506 would panic (Rust integer division by zero panics rather than reverting gracefully), which inside bank/reward-distribution code would crash the validator process handling that slot — a consensus-halting condition affecting all validators executing that reward calculation deterministically. This is structurally the same "freeze" outcome as the Carapace report, except manifesting as a validator panic/halt instead of a reverted transaction.

### Likelihood Explanation
I was unable to fully verify, within the available tool budget, whether `total_stake_lamports` is guaranteed non-zero by an upstream invariant (e.g., an assertion or a genesis/bootstrap guarantee that at least one validator always has stake) before `calculate_reward` is invoked, because I could not retrieve the full call-site context for `calculate_reward` (7 call sites exist in the file) or confirm the source of `total_stake_lamports` before I ran out of tool iterations. This is a real gap in verification — the finding should be treated as a **plausible but unconfirmed** analog rather than a fully proven vulnerability. A background agent with full repo access should trace all 7 call sites of `calculate_reward` and the construction of `total_stake_lamports` to determine whether zero is reachable in practice (e.g., after all stake deactivates, slashing, or an empty `reward_epoch_delegated_stakes` map).

### Recommendation
Add an explicit zero-check (analogous to the `.filter(|stake| *stake != 0)` guard already used in `calculate_alpenglow_points`) around `total_stake_lamports` before the division in `calculate_reward`, returning `(0, 0)` or skipping the reward distribution for that epoch/slot if the denominator is zero, rather than relying on an implicit panic-avoidance invariant.

### Proof of Concept
Not independently reproducible from the index alone — the concrete PoC would require constructing a bank/epoch state where `total_stake_lamports` passed into `calculate_reward` is zero (e.g., epoch with no eligible vote accounts / all stake deactivated) and confirming the division panics. This should be validated by a background Devin session with full test-harness access, since I could not confirm the exact call sites or whether an upstream guard already exists.

```rust
fn calculate_reward(
    epoch_state: &EpochInflationState,
    total_stake_lamports: u64,
    validator_stake_lamports: u64,
) -> (u64, u64) {
    // Rewards are computed as following:
    // per_slot_inflation = epoch_validator_rewards_lamports / slots_per_epoch
    // fractional_stake = validator_stake / total_stake_lamports
    // rewards = fractional_stake * per_slot_inflation
    //
    // The code below is equivalent but changes the order of operations to maintain precision

    let numerator =
        epoch_state.max_possible_validator_reward as u128 * validator_stake_lamports as u128;
    let denominator = epoch_state.slots_per_epoch as u128 * total_stake_lamports as u128;

    // SAFETY: the result should fit in u64 because we do not expect the inflation in a single
    // epoch to exceed u64::MAX.
    let reward_lamports: u64 = (numerator / denominator).try_into().unwrap();
    // As per the Alpenglow SIMD, the rewards are split equally between the validators and the leader.
    let validator_reward_lamports = reward_lamports / 2;
    let leader_reward_lamports = reward_lamports - validator_reward_lamports;
    (validator_reward_lamports, leader_reward_lamports)
}
```
