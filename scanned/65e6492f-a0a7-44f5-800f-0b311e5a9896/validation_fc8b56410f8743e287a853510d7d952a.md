### Title
Block-revenue commission (SIMD-0123/SIMD-0291) is applied without the epoch-delay protection that inflation commission uses, enabling last-minute commission rugs on block rewards - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The external report's broken invariant is: a value that determines how much of a counterparty's funds get taken (a "rate"/commission fetched from state) can be changed by the party who benefits from it, immediately before that rate is used to pull funds, with no lag or requester-side sanity check. Agave already recognizes and mitigates this exact class for legacy vote commission: `update_commission` restricts commission *increases* to the first half of an epoch via `is_commission_update_allowed`, and `redeem_delegation_rewards` deliberately reads a commission snapshot taken a full epoch earlier when `delay_commission_updates` is active, with the comment "This snapshot state is saved a full epoch before being used to prevent last minute commission rugs." [1](#0-0) [2](#0-1) 

However, the newer basis-points commission update path introduced for SIMD-0291/SIMD-0123 (`update_commission_bps`, covering both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`) explicitly removes the timing restriction — the code comment states "No commission update rule, per SIMD-0249 and SIMD-0291" — and the block-revenue-sharing reward path (`block_revenue_sharing` feature, `calculate_block_reward`) reads the commission live from `cached_vote_accounts.distribution_epoch_vote_accounts` rather than from the epoch-delayed snapshot used for inflation rewards commission. [3](#0-2) [4](#0-3) 

### Finding Description
- `update_commission_bps` allows the vote account's authorized withdrawer to change `block_revenue_commission_bps` at any slot, with no `is_commission_update_allowed`-style epoch-midpoint gate that exists for the legacy `update_commission` path. [5](#0-4) 
- In `redeem_delegation_rewards`, the inflation-rewards commission is deliberately fetched from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` (i.e., state cached at least a full epoch earlier) when `delay_commission_updates` is active, specifically "to attempt to delay the effect of commission updates by at least one full epoch." [6](#0-5) 
- The block-revenue reward path, gated by `block_revenue_sharing`, invokes `calculate_block_reward(... cached_vote_accounts.distribution_epoch_vote_accounts ...)` — the *current* (end-of-rewarded-epoch / distribution-epoch) vote-account snapshot, not the delayed one used for inflation commission. [4](#0-3) 
- `CachedVoteAccounts::distribution_epoch_vote_accounts` is explicitly documented as "Vote account state from the end of the rewarded epoch / beginning of the distribution epoch" — i.e., the freshest snapshot available, deliberately distinct from `snapshot_epoch_vote_accounts` which exists specifically to prevent "last-minute commission rugs." [2](#0-1) 

Put together: a validator operator (holding the authorized withdrawer key of their own vote account — not a "malicious peer" acting on someone else's account, simply exercising a privilege the protocol grants them over their own commission) can call `UpdateCommissionBps { kind: BlockRevenue, commission_bps: 10000 }` at any point, including right at epoch boundary just before block-revenue reward calculation runs, and the block-reward split computed against delegated stakers in `calculate_stake_rewards_and_commissions`/`calculate_block_reward` will use that just-changed 100% commission value, since it reads the un-delayed `distribution_epoch_vote_accounts` snapshot. This mirrors exactly the MechMarketplace bug pattern: a rate that is fetched from mutable state at execution time, without a delay/lock or a caller-provided expected-value check, and can be bumped by the counterparty who profits from the change immediately before the value is consumed to redirect funds.

### Impact Explanation
Delegators to a vote account participating in block-revenue-sharing rewards can have their expected share of block rewards captured by the validator operator, who bumps `block_revenue_commission_bps` up to 10000 (100%) immediately before the epoch's block-reward distribution runs. This is a fund-diversion/fund-theft vector against delegators — analogous in effect to the external report's "pull out all the requester's funds" scenario, except the resource redirected is the epoch's block-revenue reward pool rather than a token balance-tracker approval.

### Likelihood Explanation
Likelihood is high for any validator that has enabled block-revenue-sharing (SIMD-0123) commission sharing and wants to defect: the withdraw-authority-controlled `UpdateCommissionBps` instruction requires no waiting period, no slot-midpoint restriction (unlike the legacy path), and the reward-calculation code path deliberately reads the "distribution epoch" (freshest) vote-account snapshot for block-revenue commission rather than a delayed one. No other actor's cooperation, front-running, or privileged access is required — it's the vote account's own authorized withdrawer exercising a normal, permitted instruction at an advantageous time.

### Recommendation
Apply the same epoch-delay protection used for `inflation_rewards_commission`/`delay_commission_updates` to `block_revenue_commission_bps`: in `calculate_block_reward` (and any other block-revenue-sharing reward computation), source the commission from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` rather than `distribution_epoch_vote_accounts`, or otherwise reinstate a timing restriction (analogous to `is_commission_update_allowed`) on `UpdateCommissionBps` for `CommissionKind::BlockRevenue`.

### Proof of Concept
1. Validator operator activates block-revenue-sharing (SIMD-0123) for their vote account with an initial `block_revenue_commission_bps` low enough to attract delegated stake (e.g., 0).
2. Near the end of the rewarded epoch / just before the distribution-epoch reward calculation for that epoch runs, the authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`, which is accepted unconditionally by `update_commission_bps` (no timing gate). [5](#0-4) 
3. When `calculate_stake_rewards_and_commissions` runs for that epoch, `calculate_block_reward` reads `cached_vote_accounts.distribution_epoch_vote_accounts`, which reflects the just-updated 10000 bps commission, so essentially the entire block-revenue reward for that epoch's delegated stake is credited to the validator's commission collector instead of being split with delegators. [4](#0-3) 
4. Confirming the precise reward-lock-in slot boundary at which `distribution_epoch_vote_accounts` is snapshotted (i.e., the exact window of opportunity) requires reading the full body of `calculate_block_reward` and the epoch-boundary snapshotting code in `compute_new_epoch_caches_and_rewards`/`prune_program_cache`, which could not be fully retrieved due to index/tool limitations in this session — a Devin session with full file access should verify the exact snapshot slot and confirm there is no separate delay mechanism elsewhere in the block-revenue path.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
