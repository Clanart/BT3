Target: `Database::withdrawals` table schema (`idx int primary key`, one row per index) queried via `get_withdrawal_utxo_from_citrea_withdrawal` and written via `update_payout_txs_and_payer_operator_xonly_pk`/`get_payout_txs_for_withdrawal_utxos` in core/src/database/verifier.rs, feeding `Verifier::update_finalized_payouts`. Attacker action: broadcast a Bitcoin transaction that spends the withdrawal UTXO for index i (matching `withdrawal_utxo_txid`/`withdrawal_utxo_vout`) but is NOT the presigned optimistic-payout or operator payout transaction — e.g., any attacker-crafted tx consuming that outpoint with an OP_RETURN carrying an arbitrary xonly pubkey the attacker chooses. Preconditions: attacker knows the withdrawal UTXO's private key is not required because the UTXO's script pubkey is the user's own address from the withdrawal registration, and the withdrawal UTXO belongs to the user (attacker is the withdrawing user themselves, in scope as unprivileged). Call sequence: `update_finalized_payouts` -> `get_payout_txs_for_withdrawal_utxos(block_id)` joins on `bitcoin_syncer_spent_utxos` purely by `(txid, vout)` -> extracts OP_RETURN xonly pubkey via `parse_op_return_data` with NO validation that a real operator's key produced valid N-of-N sigs on that spend -> `update_payout_txs_and_payer_operator_xonly_pk` records an `operator_xonly_pk` chosen entirely by attacker-controlled OP_RETURN bytes. Scoped impact: Critical — an operator that never funded the payout could be falsely credited/reimbursed for withdrawal i if any downstream reimbursement logic trusts this attribution without checking the tx is presigned by N-of-N.
