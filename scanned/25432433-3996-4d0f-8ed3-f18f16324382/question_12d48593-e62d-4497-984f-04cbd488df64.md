Target: `CitreaClient::get_storage_proof`'s `tx_index: u32 = ind * 2` (core/src/citrea.rs) versus `verify_storage_proofs`'s independent `storage_proof.index * 2` recomputation (circuits-lib/src/bridge_circuit/storage_proof.rs). Attacker action: as the party constructing/relaying the `StorageProof` bytes into a `BridgeCircuitHostParams` is the operator (not directly attacker-controlled), but an attacker can instead force two withdrawals with indices i1 and i2 = i1 + 2^31 on Citrea (achievable only up to Citrea contract's own index counter — however, if the underlying `deposit_index` for `UTXOS_STORAGE_INDEX` slot ever reaches values >= 2^31, `index * 2` wraps identically for i1 and i1+2^31). Preconditions: bridge has processed at least 2^31 deposits/withdrawals (excluded as unrealistic operationally, BUT the equality can still be tested directly at the unit level). Binding that breaks: `keccak256(UTXOS_STORAGE_INDEX) + index*2` computed for index i1 == computed for index i2 when i2 ≡ i1 (mod 2^31), i.e. distinct withdrawal indices must map to distinct storage keys — the number of vault UTXOs spent for withdrawal index i == 1 fails if two indices collide onto the same storage slot verification. Scoped impact: Critical — CUSTODY, two independent withdrawals could pass proof-check against the same underlying withdrawal UTXO storage slot. Proof idea: circuits-lib unit test directly calling the storage-key derivation with `index = 1` and `index = 1 + (1u32<<31)` and asserting the two computed `storage_key_utxo` values are inequal (currently they'd be equal due to u32 wraparound), demonstrating the binding is not enforced by type.
