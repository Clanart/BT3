Target: `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs) asserting `payout_input_index` is used to cross-reference `input.payout_spv.transaction.input[payout_input_index]` against BOTH the withdrawal outpoint (`user_wd_outpoint`/`vout`) from `verify_storage_proofs` AND (elsewhere) the `deposit_constant`/kickoff commitments, while `payout_input_index` itself is derived host-side by `get_payout_input_index(wd_txid, &spv.transaction)` matching on `previous_output.txid` alone (bridge-circuit-host/src/structs.rs), ignoring `vout`. Attacker action: broadcast a payout transaction containing TWO inputs with `previous_output.txid == wd_txid` (same withdrawal-move txid used twice with different `vout` values) — feasible since `wd_txid` is the MOVE transaction's txid (identifying the deposit, not the unique withdrawal UTXO by itself), and if the move-to-vault tx has multiple spendable outputs (e.g., `DepositInMove` alongside other vouts used across different flows), an attacker structuring their OWN payout-adjacent transaction with an extra input sharing that txid could shift which input the host's `get_payout_input_index` selects. Preconditions: `get_payout_input_index` returns the FIRST matching input by txid regardless of vout; a payout transaction crafted (by an operator, but its BYTES/structure can be probed and influenced by an attacker submitting a conflicting/competing spend beforehand) with ambiguous input ordering. Call sequence: `get_payout_input_index` picks input[k] matching `wd_txid` by txid-only -> circuit later asserts `vout == input.payout_spv.transaction.input[payout_input_index].previous_output.vout`, which WOULD catch a vout mismatch and panic — so the true bug surface is whether `get_payout_input_index`'s FIRST-MATCH selection combined with the vout assert can still validate against the WRONG deposit if two different deposits' move-to-vault transactions happen to produce colliding `wd_txid` (extremely unlikely for real txids, but the point is the matching logic doesn't also assert single index i to single input(i) exclusivity across the whole transaction — a payout tx with two inputs from the SAME move_txid but different vouts, one legitimate and one crafted, only proves ONE of them via storage proof yet the whole payout tx (with both inputs' value) gets accepted as the fronting tx). Binding that breaks: the number of vault UTXOs spent for withdrawal index i == 1 and each equals exactly one payout actually fronted; a multi-input payout transaction could front MULTIPLE withdrawal indices’ worth of value in one broadcast while the circuit only individually verifies one input's linkage per proof run, allowing the operator to claim reimbursement once per index even though the aggregate fronted amount in the single tx could be misallocated across indices without per-index isolation of value. Scoped impact: Critical — PROOF SOUNDNESS: what the journal_hash claims (single withdrawal fronted) == what actually happened on Bitcoin (potentially a batched multi-withdrawal tx whose per-index value split isn't independently verified). Proof idea: circuits-lib test constructing a `payout_spv.transaction` with two inputs referencing withdrawal UTXOs from indices i and j but only proving index i's storage proof, then confirming the circuit does NOT implicitly certify anything about index j's fronting amount, and that operator reimbursement logic elsewhere can't double count from a single such tx.
