## Title
Unbounded, single-slot iteration over all stake delegations during epoch-boundary reward calculation scales with permissionlessly-created stake accounts — analogous to `settleFunding`'s unbounded-market DoS - (File: `runtime/src/bank.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Hubble finding is fundamentally: an unbounded loop over an attacker-uncontrolled-but-freely-growable collection ("markets") is executed synchronously inside a single call, so cost grows without bound as the collection grows, eventually exceeding the resource budget of the environment (block gas limit) and causing DoS for legitimate callers. The Agave analog is `Bank::process_new_epoch` → `compute_new_epoch_caches_and_rewards` → `calculate_activated_stake` / `calculate_stake_rewards_and_commissions` / `calculate_reward_points_partitioned`, which iterate over **every stake delegation in the network** synchronously, once per epoch boundary, inside the processing of a single slot. [1](#0-0)  Unlike reward *distribution*, which Agave already partitions across many blocks specifically to avoid this class of bug, the *calculation* phase (activated-stake refresh, point accumulation, and per-delegation reward/commission computation) is not partitioned and must complete within the single epoch-boundary slot. [2](#0-1) [3](#0-2) 

### Finding Description
`process_new_epoch` runs at every epoch boundary and calls `compute_new_epoch_caches_and_rewards`, which:
1. Calls `stakes.calculate_activated_stake(...)`, which does a `par_iter().fold()/reduce()` over **all** `stake_delegations` to compute activation status and refreshed vote-account delegated stakes. [4](#0-3) 
2. Calls `self.calculate_rewards(...)`, which computes reward points over all delegations (`calculate_reward_points_partitioned`, `par_iter` over `stake_delegations`) and then computes stake rewards and commissions for all delegations (`calculate_stake_rewards_and_commissions`, again `par_iter` over the full `stake_delegations` vector). [5](#0-4) [6](#0-5) 

All of this work happens inside `process_new_epoch`, which is invoked as part of freezing/processing the first slot of the new epoch — i.e., within the time budget of a single slot, not spread across many slots the way the actual reward **distribution** to stake accounts is (that part is explicitly `PartitionedStakeRewards`/`begin_partitioned_rewards`, split across many blocks precisely to bound per-block cost). [7](#0-6)  The comment in the code itself acknowledges the scale concern ("For N stake delegations, where N is >1,000,000..."). [8](#0-7) 

The attacker primitive is permissionless and cheap: creating a delegated stake account only requires the rent-exempt reserve plus the minimum delegation, which is a fixed, small amount (`get_minimum_delegation` returns either 1 lamport or 1 SOL depending on feature activation) — well within reach of any unprivileged user, and there is no network-wide cap on the total number of stake accounts/delegations that can exist. [9](#0-8)  Every additional delegation created by any user permanently and unconditionally adds to the O(n) work every validator must perform, every epoch, forever — this is the corrupted/growing value: the size of `stake_delegations` processed synchronously in `compute_new_epoch_caches_and_rewards`.

Unlike the Hubble contract, this work is parallelized via a `rayon` thread pool (`thread_pool.install(|| ... par_iter() ...)`), which raises the practical threshold at which the cost becomes problematic, but it does not bound it — it only divides the same unbounded total work among available cores. As delegation count grows (a permissionless, ever-increasing quantity with no upper bound and no per-account cost that scales with total count), the wall-clock cost of this step at every epoch boundary grows without bound, exactly mirroring the settleFunding pattern where "more markets" replaces "more stake delegations" and "block gas limit" replaces "slot time budget."

### Impact Explanation
If `compute_new_epoch_caches_and_rewards` takes too long relative to the slot time budget at an epoch boundary, this manifests as slowed or missed epoch-boundary slot processing across the entire validator set simultaneously (since every validator performs the identical unbounded computation deterministically as part of consensus-critical epoch transition). Because this is triggered identically by every validator (not a targeted single-node RPC crash), a sufficiently bloated stake-delegation set could produce cluster-wide degradation at epoch boundaries — a "non-RPC remote exhaustion" / potential consensus-halt-adjacent condition, consistent with the accepted valid-impact categories (runtime, accounts, built-ins; consensus halt; non-RPC remote exhaustion/crash).

### Likelihood Explanation
Likelihood is currently low-to-moderate in practice: minimum delegation of 1 SOL is a real economic cost for an attacker who wants to create enough accounts to meaningfully move the needle, and the computation is parallelized across a thread pool, both of which raise the bar significantly compared to the original Hubble bug (which had a near-zero-cost DoS trigger). However, the invariant — O(n) unbounded synchronous work per epoch boundary tied to a permissionlessly-growable count — is structurally unmitigated for the *calculation* phase even though Agave engineers explicitly solved the analogous problem for the *distribution* phase via partitioning, indicating the team is aware of and has partially, but not fully, addressed this exact bug class.

### Recommendation
Apply the same partitioning strategy already used for `PartitionedStakeRewards` distribution to the calculation phase: split `calculate_activated_stake`, `calculate_reward_points_partitioned`, and `calculate_stake_rewards_and_commissions` across multiple slots/blocks at the epoch boundary rather than requiring the entire pass over `stake_delegations` to complete within a single slot's processing window, or introduce hard/soft caps and continuous monitoring on total delegation count with alerting well before the computation time threatens slot timing.

### Proof of Concept
A concrete PoC (creating millions of low-value stake accounts across many epochs and benchmarking `process_new_epoch` wall-clock time on a devnet/testnet cluster) was not run as part of this ask-only investigation; the analysis is based on static code review of `runtime/src/bank.rs` (`process_new_epoch`, `compute_new_epoch_caches_and_rewards`), `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, `runtime/src/stakes.rs` (`calculate_activated_stake`), and `runtime/src/stake_utils.rs` (`get_minimum_delegation`), which together show the unbounded, single-slot, parallelized-but-uncapped iteration over all network stake delegations at every epoch boundary. Confirming actual wall-clock scaling behavior at very large delegation counts would require a live benchmark, which is outside the scope of this read-only code review.

    /// Returns reward lamports and points for the epoch or none if points == 0.

        stake_delegations: &Vec<(&'a Pubkey, &'a StakeAccount<Delegation>)>,
        cached_vote_accounts: &CachedVoteAccounts<'_>,
        epoch_inflation_rewards: u64,

        thread_pool: &ThreadPool,

    ) -> Option<PointValue> {
        let CachedVoteAccounts {
            distribution_epoch_vote_accounts,
            ..
        } = cached_vote_accounts;

        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        match ag_epoch_type {
            AlpenglowEpochType::Alpenglow { .. } => {
                // In alpenglow, we do not need to compute `PointValue::points` as the final
                // rewards are simply the total credits stored in the vote account.  We just need
                // to return a `Some` value with valid rewards.
                return Some(PointValue {
                    rewards: epoch_inflation_rewards,
                    points: 0,
                });
            }
            AlpenglowEpochType::Tower => {
                // For tower we need to compute the valid `PointValue::points`.
            }
            AlpenglowEpochType::MigrationEpoch { .. } => {
                // For the migrating epoch, we need to compute the tower portion of `PointValue::points`.
            }
        }

        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        let (points, measure_us) = measure_us!(thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .map(|(_stake_pubkey, stake_account)| {
                    let vote_pubkey = stake_account.delegation().voter_pubkey;

                    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey)
                    else {
                        return 0;
                    };
                    if vote_account.owner() != &solana_vote_program {
                        return 0;
                    }

                    calculate_points_for_tower(
                        stake_account.stake_state(),
                        DelegatedVoteState::from(vote_account.vote_state_view()),
                        stake_history,
                        new_warmup_cooldown_rate_epoch,
                        use_fixed_point_stake_math,
                    )
                    .unwrap_or(0)
                })
                .sum::<u128>()
        }));

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
        use_fixed_point_stake_math: bool,
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation_activation_status(
                            delegation,
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                            use_fixed_point_stake_math,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
