## Title
Floating-point precision loss in stake-ratio threshold comparisons causes incorrect vote-threshold/switch-threshold/root determination - (File: `core/src/consensus.rs`, `runtime/src/commitment.rs`, `ledger/src/blockstore_processor.rs`)

## Summary
This is the closest Agave analog to the Plaza `marketRate`/`redeemRate` bug class: a numeric-representation mismatch causes a boundary comparison that should be exact to silently evaluate incorrectly. In Plaza, decimal-scale mismatch made `marketRate < redeemRate` always false. In Agave's legacy (non-Alpenglow) consensus code, stake ratios are computed as `stake as f64 / total_stake as f64` and compared against exact rational thresholds (e.g. `2f64/3f64`, `0.38`), which loses precision at realistic mainnet stake magnitudes and can flip the comparison result near the threshold boundary.

## Finding Description
`Tower::check_vote_stake_threshold` computes the lockout ratio in floating point and compares it to `threshold_size` (`VOTE_THRESHOLD_SIZE = 2f64/3f64`): [1](#0-0) 

The same pattern recurs for duplicate confirmation (`DUPLICATE_THRESHOLD`): [2](#0-1) 

and for switch-threshold / consensus-safety decisions (`SWITCH_FORK_THRESHOLD = 0.38`): [3](#0-2) 

The same f64-ratio-vs-f64-threshold pattern is also used to determine the **root** during blockstore/ledger replay (`supermajority_root`, using `VOTE_THRESHOLD_SIZE`): [4](#0-3) 

and to compute the publicly-reported commitment/confirmation level: [5](#0-4) 

and propagation threshold in `replay_stage.rs` (`SUPERMINORITY_THRESHOLD`): [6](#0-5) 

Agave's own code demonstrates that this exact failure mode is real and has already been fixed — but only for the new Alpenglow/votor consensus path. `votor-messages/src/fraction.rs` introduces an exact-rational `Fraction` type specifically "for precise stake threshold comparisons" and its own test proves the bug: [7](#0-6) 

At `total_stake = 100_000_000_000_000_000` lamports (1e17, close to real mainnet total stake, which is already in the ~3-4e17 lamport range) and `stake` = exactly 60% + 1 lamport, the f64 ratio rounds down to `<= 0.6`, i.e. the naive `stake as f64 / total_stake as f64 > 0.6` comparison is **wrong** at exactly the boundary. `Fraction::new(stake, total_stake) > Fraction::from_percentage(60)` correctly returns `true` via integer cross-multiplication.

The `Fraction` fix is confined to `votor` (Alpenglow) code such as `votor/src/consensus_pool/slot_stake_counters.rs`: [8](#0-7) 

The legacy Tower BFT path in `core/src/consensus.rs`, `core/src/consensus/vote_stake_tracker.rs`, `runtime/src/commitment.rs`, and `ledger/src/blockstore_processor.rs` — which is the **currently active, non-Alpenglow consensus mechanism** used in production today — still performs the vulnerable raw f64 division/comparison and was not migrated to `Fraction`.

## Impact Explanation
Because IEEE-754 f64 has only 52 bits of mantissa (~15-17 significant decimal digits), and real mainnet total stake in lamports is on the order of `10^17`-`10^18`, the ratio `stake / total_stake` loses the ability to distinguish stakes differing by a small number of lamports near an exact threshold boundary (as demonstrated by Agave's own `test_f64_precision_loss`). This means:
- `check_vote_stake_threshold` (and thus a validator's ability to legally cast a vote per Tower BFT rules) can pass or fail incorrectly at the 2/3 boundary.
- `is_slot_duplicate_confirmed` and the switch-threshold checks, which govern whether a validator may safely switch forks without violating fork-choice safety invariants, can be miscalculated — this directly touches consensus-safety-critical logic (switching forks incorrectly can contribute to violating the "don't vote on two conflicting forks" safety property).
- `supermajority_root` in `blockstore_processor.rs` determines the root slot found during ledger replay/bootstrap using the same imprecise comparison against `VOTE_THRESHOLD_SIZE`, which can cause a false/incorrect root determination.
- `commitment.rs::get_lockout_count` affects publicly reported confirmation/finalization status exposed over RPC.

These fall within the requested impact categories of false execution/rooting/acceptance and consensus-related logic in the `runtime`/`accounts`/`blockstore`-adjacent path, without any peer/validator maliciousness assumption — the bug is triggered purely by the existing arithmetic on legitimate stake distributions.

## Likelihood Explanation
This does not require an attacker; it is a deterministic numerical property of f64 arithmetic that manifests whenever the real stake distribution lands within a few ULPs of an exact threshold (2/3, 0.38, etc.) at real-world stake magnitudes — a condition Agave's own test explicitly reproduces at `total_stake = 1e17`, well below current mainnet total stake. The likelihood of hitting such a boundary in practice depends on the exact stake distribution at a given moment, so it is probabilistic/edge-case rather than always-triggered, but it is a genuine, unprivileged latent correctness bug in code that runs on every vote/threshold/root check.

## Recommendation
Migrate the legacy Tower BFT threshold comparisons (`core/src/consensus.rs`, `core/src/consensus/vote_stake_tracker.rs`, `runtime/src/commitment.rs`, `ledger/src/blockstore_processor.rs::supermajority_root`, `core/src/replay_stage.rs`) to use exact integer/rational comparisons (e.g., the existing `votor-messages::Fraction` type, or equivalent cross-multiplication with `u128`) instead of `stake as f64 / total_stake as f64` compared against an `f64` threshold, mirroring the fix already applied in the `votor` consensus_pool code.

## Proof of Concept
Using the existing test in the repo as the reproduction case: [7](#0-6) 
Substitute the same `stake`/`total_stake` values (or any pair where `stake` is `threshold * total_stake + 1`, a single lamport past an exact rational threshold, at magnitudes near real mainnet total stake) into `Tower::check_vote_stake_threshold`, `Tower::is_slot_duplicate_confirmed`, or `blockstore_processor::supermajority_root`, and observe that `lockout > threshold_size` (or the equivalent `sum as f64 / total_stake as f64 > minimum_stake_percentage`) evaluates to `false` even though the true rational stake fraction exceeds the threshold.

fn supermajority_root(roots: &[(Slot, u64)], total_epoch_stake: u64) -> Option<Slot> {
    if roots.is_empty() {
        return None;
    }

    // Find latest root
    let mut total = 0;
    let mut prev_root = roots[0].0;
    for (root, stake) in roots.iter() {
        assert!(*root <= prev_root);
        total += stake;
        if total as f64 / total_epoch_stake as f64 > VOTE_THRESHOLD_SIZE {
            return Some(*root);
        }
        prev_root = *root;
    }

    None
}
