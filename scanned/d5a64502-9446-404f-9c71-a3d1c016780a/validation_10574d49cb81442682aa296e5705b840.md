## Analog Found

### Title
Deterministic panic in epoch-reward stake distribution when live delegation state diverges from calculation-time snapshot - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The external report's bug class is: a function that aggregates/finalizes state for many entities assumes a particular entity cannot be in an "already-changed" state relative to when it was computed, and when that assumption breaks, the aggregate operation reverts/fails entirely rather than degrading gracefully. The Agave analog is in `Bank::build_updated_stake_reward`, which is called once per stake account during the deterministic, per-epoch partitioned-rewards distribution path. It hard-codes an `assert_eq!` that the live stake delegation amount must exactly match what was predicted during the earlier calculation phase, and panics if not.

### Finding Description
During epoch-boundary processing, Agave computes reward point values and per-stake-account reward amounts in a "calculation" phase (`calculate_stake_rewards_and_commissions`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), then applies them to accounts in a later "distribution" phase, spread over several blocks (`distribute_partitioned_epoch_rewards` / `distribute_epoch_rewards_in_partition`, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:78-224`).

The actual per-account application happens in `build_updated_stake_reward`: [1](#0-0) 

When the `adjust_delegations_for_rent` feature path is *not* taken, the code computes `expected_delegation` from the **live** stakes-cache account (`stake.delegation.stake`, loaded fresh at distribution time) plus the previously-calculated `stake_reward`, and asserts it equals `new_stake.delegation.stake` (the value computed earlier, at calculation time): [2](#0-1) 

This assert is only valid under the documented assumption that stake account delegation cannot change between calculation time and distribution time: [3](#0-2) 

Unlike the two adjacent, genuinely-recoverable error paths in the same function — `AccountNotFound` when the account disappears, and `ArithmeticOverflow` when lamports overflow — which are surfaced as `Result` and handled by burning the reward (`store_stake_accounts_in_partition`, lines 393-407), a delegation-value mismatch is not modeled as a recoverable `DistributionError` variant at all. It is treated as an invariant via `assert_eq!`, i.e., an unrecoverable panic. This exactly mirrors the MetaVest bug pattern: the aggregate function (`getMajorityVotingPower` / here, the per-block reward-distribution loop that runs across every partition for every stake account) assumes a specific state transition ("terminated before vestingStartTime" / "delegation mutated between calculation and distribution") cannot occur, and does not defensively branch away from the failing call before it is reached.

The comment at line 330-332 acknowledges that this relies on "stake-program restrictions" to prevent delegation mutation during the reward window, but I was not able to locate, in the code reachable from this investigation, an explicit block in the stake program instruction processor that universally forbids all delegation-changing instructions (e.g. deactivate, split, merge, withdraw with subsequent re-delegation) for every account during the multi-block distribution interval. This is the load-bearing assumption for the `assert_eq!` to be safe, and I could not fully confirm or refute its completeness within the scope of this session — this is a genuine gap in my verification, not a settled fact.

### Impact Explanation
Reward distribution runs deterministically, in the same order, on every validator processing the same slot, since `store_stake_accounts_in_partition` iterates the state-hash-derived `partition_indices` against the current `stakes_cache`. If the assumption backing the `assert_eq!` is violated for any single stake account tracked in `all_stake_rewards`, every validator that processes that block hits the identical `assert_eq!` failure and panics identically — this is not a single-node crash but a synchronized, cluster-wide validator panic, i.e. a consensus-halt-class event, since the network cannot advance past that slot.

### Likelihood Explanation
Likelihood is **uncertain/unconfirmed**, which is the key caveat of this analog. The developers' own comment states they *believe* stake-program restrictions make the divergence impossible, so exploitability hinges entirely on whether an unprivileged, permissionless path (ordinary stake-owner instructions such as `Split`, `Merge`, `Withdraw`, `Deactivate`, or `SetLockup` interactions with `Rent`-adjustment logic) can mutate `delegation.stake` for an account between the calculation block and its corresponding distribution block, spanning up to `get_reward_distribution_num_blocks` blocks. I could not verify from the index whether such a restriction exists and is complete for every stake instruction and every account snapshot involved (`stake_delegations_vec()` at calculation vs. `stakes_cache.stake_delegations()` at distribution). Given the size and generated nature of the reward-distribution code and stake-program instruction handlers, I recommend this be confirmed with full repository access rather than treated as conclusively proven here.

### Recommendation
Convert the `assert_eq!` in `build_updated_stake_reward` (distribution.rs lines 284-294) into a recoverable `DistributionError` variant (mirroring `AccountNotFound`/`ArithmeticOverflow`) so that a detected mismatch causes the individual reward to be burned/skipped (as already done for the other error paths) rather than panicking the whole validator process. Separately, audit and document exactly which stake-program instructions are blocked, and by what mechanism, for the entire distribution window, to confirm the invariant the assert currently relies on is actually enforced end-to-end.

### Proof of Concept
Not constructed — this analog requires confirming, with full repository/build access, whether any permissionless stake instruction can alter `Delegation::stake` for an account between the reward-calculation block and its scheduled distribution block within the same epoch-reward cycle. A concrete PoC would: (1) identify a stake account included in `all_stake_rewards`, (2) submit an ordinary stake instruction that changes its `delegation.stake` before its partition's distribution block executes, and (3) observe the panic in `build_updated_stake_reward`'s `assert_eq!` at the corresponding block height. This could not be completed with the tools available in this session.
