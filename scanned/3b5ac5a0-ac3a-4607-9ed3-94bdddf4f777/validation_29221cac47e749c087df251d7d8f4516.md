Found a genuine analog. `try_convert_to_vote_state_v4` in `programs/vote/src/vote_state/handler.rs` lazily converts V1_14_11/V3 vote accounts into V4 the first time any vote instruction touches them, and it re-derives both commission collectors *at conversion time* from the account's current identity fields rather than storing a stable, explicit default at account-creation time.

### Title
Lazy V3→V4 vote-account conversion re-derives commission collectors from current identity, silently changing implicit collector defaults - ([File: programs/vote/src/vote_state/handler.rs])

### Summary
Legacy (V1_14_11/V3) vote accounts have no `inflation_rewards_collector`/`block_revenue_collector` fields. When such an account is first touched by any vote instruction after SIMD-0185/0232 activation, `try_convert_to_vote_state_v4` synthesizes these fields on the fly, setting `inflation_rewards_collector = *vote_pubkey` and `block_revenue_collector = state.node_pubkey` [1](#0-0) . Because this "default" is computed lazily at the moment of conversion (using whatever `node_pubkey`/`vote_pubkey` happen to be current then) rather than being fixed once and persisted explicitly, any instruction that partially updates the account (e.g. `UpdateCommissionCollector` for only one `CommissionKind`) forces the conversion and simultaneously stamps the *other*, untouched collector with a value derived from present-day identity — exactly the "unset value silently falls back to a moving default" pattern from the Juicebox finding.

### Finding Description
`update_commission_collector` calls `get_vote_state_handler_checked`, which internally calls `try_convert_to_vote_state_v4` if the account is still V1_14_11/V3 [2](#0-1) . The conversion function hard-codes the collector defaults from the *legacy* state's `node_pubkey` and the account's own pubkey [3](#0-2) :
```
VoteStateVersions::V3(state) => Ok(VoteStateV4 {
    ...
    inflation_rewards_collector: *vote_pubkey,
    block_revenue_collector: state.node_pubkey,
    ...
```
This is confirmed by an in-repo test explicitly documenting the effect: updating `InflationRewards` collector on a V3 account causes `BlockRevenue` collector to be simultaneously written to `v3_node_pubkey` as "its V4-conversion default" [4](#0-3) . Unlike `update_validator_identity`, which explicitly checks `custom_commission_collector_enabled` before touching `block_revenue_collector` [5](#0-4) , `try_convert_to_vote_state_v4` has no equivalent guard — there is no persisted flag distinguishing "collector was never customized, use identity" from "collector was explicitly customized." The value is recomputed from `node_pubkey`/`vote_pubkey` every time a legacy account is converted, so whichever identity is current *at the moment conversion is triggered* becomes baked in as the "default," even though from the validator operator's perspective no explicit choice about that collector was ever made or re-affirmed at that point in time.

### Impact Explanation
If a validator rotates its node identity (`UpdateValidatorIdentity`) while still holding a legacy V3 vote account (i.e., before any V4-triggering instruction executes), and only later some instruction (e.g. `UpdateCommissionCollector` for `InflationRewards` only) forces the lazy V3→V4 conversion, `block_revenue_collector` gets silently set to the *old* `node_pubkey` recorded in the frozen V3 state, not the validator's current identity — misdirecting future block-revenue commission payouts to a stale identity account the validator no longer controls or expects to receive funds. This is a fund-misdirection bug consistent with the reported bug class (wrong beneficiary receives funds due to an implicit, non-persisted default that is recomputed instead of carried forward).

### Likelihood Explanation
Likelihood is moderate: it requires (a) a validator still running on legacy V3 state after SIMD-0185/0232/0464 activation, and (b) an instruction sequence where node identity changes precede a lazy conversion trigger that only updates one collector kind. Because vote-account upgrades happen implicitly and are not something operators explicitly track, this ordering is plausible in real fleets during the migration window, and the bug is unprivileged in the sense that the vote-account authorized withdrawer, acting entirely within their own authority, can trigger it without realizing the side effect on the other collector field.

### Recommendation
When lazily converting legacy vote state to V4, do not derive `inflation_rewards_collector`/`block_revenue_collector` from potentially-stale legacy fields at arbitrary future conversion time. Instead, either (a) perform the V3→V4 migration eagerly/atomically at a fixed epoch boundary using the identity valid at that boundary, or (b) persist an explicit "collector not yet customized" marker so that any future defaulting logic is based on the vote account's *current* identity fields at the time of the actual triggering instruction rather than fields frozen inside the legacy serialized blob.

### Proof of Concept
The exact mechanics and expected (side-effect) behavior are already demonstrated by the existing test `programs/vote/src/vote_state/mod.rs` around lines 4734–4796, which shows that calling `update_commission_collector` for `CommissionKind::InflationRewards` on a V3-backed account causes `block_revenue_collector` to be simultaneously (re)written to `v3_node_pubkey` — a value taken from the frozen legacy state rather than the vote account's live, current node identity — as an acknowledged "V3 -> V4 auto-conversion side-effect" [4](#0-3) . The core defaulting logic under test is in `try_convert_to_vote_state_v4` [1](#0-0) .

pub(crate) fn try_convert_to_vote_state_v4(
    versioned: VoteStateVersions,
    vote_pubkey: &Pubkey,
) -> Result<VoteStateV4, InstructionError> {
    match versioned {
        VoteStateVersions::Uninitialized => Err(InstructionError::UninitializedAccount),
        VoteStateVersions::V1_14_11(state) => Ok(VoteStateV4 {
            node_pubkey: state.node_pubkey,
            authorized_withdrawer: state.authorized_withdrawer,
            inflation_rewards_collector: *vote_pubkey,
            block_revenue_collector: state.node_pubkey,
            inflation_rewards_commission_bps: u16::from(state.commission).saturating_mul(100),
            block_revenue_commission_bps: 10_000u16,
            pending_delegator_rewards: 0,
            bls_pubkey_compressed: None,
            votes: landed_votes_from_lockouts(state.votes),
            root_slot: state.root_slot,
            authorized_voters: state.authorized_voters.clone(),
            epoch_credits: state.epoch_credits,
            last_timestamp: state.last_timestamp,
        }),
        VoteStateVersions::V3(state) => Ok(VoteStateV4 {
            node_pubkey: state.node_pubkey,
            authorized_withdrawer: state.authorized_withdrawer,
            inflation_rewards_collector: *vote_pubkey,
            block_revenue_collector: state.node_pubkey,
            inflation_rewards_commission_bps: u16::from(state.commission).saturating_mul(100),
            block_revenue_commission_bps: 10_000u16,
            pending_delegator_rewards: 0,
            bls_pubkey_compressed: None,
            votes: state.votes,
            root_slot: state.root_slot,
            authorized_voters: state.authorized_voters,
            epoch_credits: state.epoch_credits,
            last_timestamp: state.last_timestamp,
        }),
        VoteStateVersions::V4(state) => Ok(*state),
    }
}

/// Update the node_pubkey, requires signature of the authorized voter
pub fn update_validator_identity<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    node_pubkey: &Pubkey,
    signers: &HashSet<Pubkey, S>,
    custom_commission_collector_enabled: bool,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    // new node must say "yay"
    verify_authorized_signer(node_pubkey, signers)?;

    vote_state.set_node_pubkey(*node_pubkey);

    // Before SIMD-0232, block_revenue_collector is always synced with node_pubkey.
    // After SIMD-0232, the collector can be set independently.
    if !custom_commission_collector_enabled {
        vote_state.set_block_revenue_collector(*node_pubkey);
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
