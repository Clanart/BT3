## Analysis

The Folks Finance report's broken invariant is: **a user picks an arbitrary, public, unique identifier for a resource; there is a time gap between broadcasting the request and it being committed; an unprivileged third party can observe the pending request and claim the same identifier first, causing the legitimate request to revert and the victim's funds/fees to be wasted.**

The closest structural analog in the Agave codebase is the System Program's account-creation ID-uniqueness check, `CreateAccount`/`CreateAccountWithSeed`, which enforces first-claim-wins on a **caller-chosen address**, with the same "observe pending tx → front-run with same target key → victim's tx reverts" primitive.

### Title
Griefing DoS on `CreateAccount`/`CreateAccountWithSeed` via address squatting during the mempool→confirmation window - (`programs/system/src/system_processor.rs`)

### Summary
`SystemInstruction::CreateAccount` (and the seed-derived variant) let the transaction sender choose an arbitrary target `Pubkey`/derived address for the new account. The processor's only uniqueness guard is a runtime check performed when the transaction is finally executed: if the target account already holds lamports or data/owner, creation fails with `SystemError::AccountAlreadyInUse`. Because Solana transactions are visible (via gossip/mempool, `sendTransaction`, or simulation) for some interval before they land in a block, any unprivileged actor who observes a pending `CreateAccount`/`CreateAccountWithSeed` transaction targeting a not-yet-existing account can submit a competing transaction that funds/creates an account at the exact same address first (for `CreateAccountWithSeed`, the address is fully deterministic from `base`, `seed`, `owner`, all of which are visible in the pending transaction). This is the same primitive as the report's `loanId`-squatting: a public, attacker-guessable/observable unique key, checked-then-created without any binding to the original requester.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` performs the existence check purely at execution time: [1](#0-0) 
and `allocate`/`assign` similarly bail with `AccountAlreadyInUse` if the account is not empty: [2](#0-1) 

The address for `CreateAccountWithSeed` is fully public/derivable, since it's just `Pubkey::create_with_seed(base, seed, owner)`, re-verified in `Address::create`: [3](#0-2) 

Once Alice broadcasts (or the address is otherwise learned, e.g. from a simulated/pending transaction, a dApp UI, or a predictable seed scheme) a `CreateAccount`/`CreateAccountWithSeed` transaction targeting address `X`, an unprivileged attacker Eve can submit a transaction that puts any nonzero lamports into `X` (a simple `Transfer` or her own `CreateAccount`) before Alice's transaction lands. When Alice's transaction is finally processed, the guard at line 164 (`to.get_lamports() > 0`) triggers, and her instruction — and the whole transaction if it's the only meaningful instruction — fails with `AccountAlreadyInUse`. This exactly mirrors the report's `isUserLoanActive(loanId)` check in `LoanManager.sol`, which the bounty report flagged as griefable: a "create-if-not-exists" check on a user-chosen, externally-visible identifier, racing against network propagation delay.

The CLI-level tooling exhibits the same pattern for nonce accounts and stake accounts — e.g., `process_create_nonce_account` explicitly must special-case the "already exists" race: [4](#0-3) 
and stake account creation has an identical pre-existing-account check: [5](#0-4) 
These client-side checks are advisory only (best-effort, checked before submission) — they do not prevent an attacker from squatting the address between the check and confirmation, and the actual enforcement/failure happens on-chain in `system_processor.rs`.

### Impact Explanation
This is a pure griefing/DoS vector, not a fund-theft path: the victim's `CreateAccount`/`CreateAccountWithSeed` transaction fails, the victim loses the transaction fee (and any compute paid for a failed attempt), and any downstream logic depending on the deterministic address (nonce accounts, stake accounts, PDAs used by programs/dApps) is blocked until the victim picks a new seed/address. Repeated squatting can indefinitely deny a specific user (or class of addresses) the ability to create accounts at predictable/derived locations, which matches "Griefing (no profit motive necessarily, but damage to users/protocol)" impact class from the source report.

### Likelihood Explanation
Likelihood is high for `CreateAccountWithSeed`/derived-PDA flows because the target address is a deterministic function of public inputs (`base`, `seed`, `owner`) that are visible the moment a transaction is gossiped, submitted via RPC, or simulated — no secret is involved. It is lower but still feasible for plain `CreateAccount` with a fresh random key if that key/transaction is observable before confirmation (e.g., via `sendTransaction` polling, mempool-adjacent infrastructure, or off-chain coordination such as pre-shared seeds in a dApp). This is a known, long-standing characteristic of Solana's account model (the code itself documents the "squatting" concern in `add_builtin_account`, see `runtime/src/bank.rs:6547-6561` and the associated tests `test_add_builtin_account_squatted_while_not_replacing` / `test_add_precompiled_account_squatted_while_not_replacing`), showing the maintainers are aware address-squatting is a real, exploitable condition against arbitrary/predictable addresses, not merely a theoretical concern. [6](#0-5) 

### Recommendation
No on-chain guard can fully eliminate this for a stateless, deterministic-address creation primitive without changing the address derivation scheme itself. Practical mitigations:
- For protocols/dApps building on `CreateAccountWithSeed`/PDAs, always bind the derived address to the requester's own pubkey (as the `base`/seed input) rather than a globally guessable/shared seed, so squatting requires the attacker to already control the victim's `base` key.
- Where the resource-identifier is chosen by an off-chain/asynchronous caller (bridges, relayers, or any flow with a confirm-later step, per the original report), require the resource ID to embed the caller's identity/authority (e.g., seed = requester pubkey + nonce) so a collision is fundamentally unreachable by a third party, not just detected after the fact.
- Consider a "reserve-then-confirm" pattern (two-phase create) for high-value flows so that transient squatting cannot silently strand fee-payer funds.

### Proof of Concept
1. Alice submits `SystemInstruction::CreateAccountWithSeed { base: Alice_base, seed: "s", owner: P, lamports, space }`, deriving address `X = create_with_seed(Alice_base, "s", P)`. This transaction is visible for one-to-several slots before landing (via RPC polling / gossip / simulate).
2. Eve, an unprivileged actor observing the network, computes the same `X` (trivial since `create_with_seed` is a public, deterministic function) and submits her own `Transfer` (or `CreateAccount`) instruction funding/creating `X` with higher priority fee so it lands first.
3. When Alice's transaction executes, `create_account`'s check `to.get_lamports() > 0` at `system_processor.rs:164` is now true, so it returns `SystemError::AccountAlreadyInUse`, matching the referenced `test_create_already_in_use` unit test behavior: [7](#0-6) 
4. Alice's transaction fails on-chain; she has paid the fee and must pick a new seed/address to retry — the exact griefing outcome described in the original report for `loanId` collisions.

        address: &Pubkey,
        with_seed: Option<(&Pubkey, &str, &Pubkey)>,

        let base = if let Some((base, seed, owner)) = with_seed {
            // The conversion from `PubkeyError` to `InstructionError` through
            // num-traits is incorrect, but it's the existing behavior.
            let address_with_seed =
                Pubkey::create_with_seed(base, seed, owner).map_err(|e| e as u64)?;
            // re-derive the address, must match the supplied address
            if *address != address_with_seed {
                ic_msg!(
                    invoke_context,
                    "Create: address {} does not match derived address {}",
                    address,
                    address_with_seed
                );
                return Err(SystemError::AddressWithSeedMismatch.into());
            }
            Some(*base)
        } else {
            None
        };

        Ok(Self {
            address: *address,
            base,
        })
    }
