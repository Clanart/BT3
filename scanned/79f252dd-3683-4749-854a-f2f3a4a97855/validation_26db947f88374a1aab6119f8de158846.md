### Title
Stake classification of a QUIC/TPU connection is fixed at connect-time and never revalidated against the live `StakedNodes` table for the life of the connection - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
The external report's broken invariant is: a privileged permission is granted based on a "trusted address" snapshot, and when that trusted address is later changed/revoked, previously-granted permissions do not automatically follow the update — they persist until someone manually re-checks/revokes them. In Agave's QUIC/TPU ingestion layer, the analogous "permission" is the `ConnectionPeerType::Staked(stake)` classification a peer receives when its QUIC connection is first accepted, computed once from a snapshot of the `StakedNodes` map via `get_connection_stake`/`build_connection_context` in `streamer/src/nonblocking/swqos.rs` and `streamer/src/nonblocking/simple_qos.rs`. That classification (and the resulting stake value) is cached inside the connection's `SwQosConnectionContext`/`SimpleQosConnectionContext`/`ConnectionEntry`, and is used for the entire lifetime of the connection to decide stream-throttling allowance and connection-table placement (`streamer/src/nonblocking/swqos.rs:292-343`, `streamer/src/nonblocking/quic.rs:860-901`).

### Finding Description
`StakedNodesUpdaterService` refreshes the shared `staked_nodes` map from the root bank every 5 seconds (`core/src/staked_nodes_updater_service.rs:16-40`), so the source of truth for "who is staked and by how much" does change over time (e.g., a validator delinquent/unstaked, or a delegated stake moved away).

However, the per-connection stake classification is computed exactly once, at `build_connection_context()` time, by reading `staked_nodes` (`streamer/src/nonblocking/swqos.rs:301-342`):
```
fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
    ...
    get_connection_stake(connection, &self.staked_nodes).map_or(
        SwQosConnectionContext { peer_type: ConnectionPeerType::Unstaked, ... },
        |(pubkey, stake, total_stake)| {
            let peer_type = { ... ConnectionPeerType::Staked(stake) ... };
            SwQosConnectionContext { peer_type, total_stake, ... }
        },
    )
}
```
This `peer_type`/`total_stake` pair is then stored in the long-lived `conn_context` and used directly for `max_streams_per_throttling_interval` (`swqos.rs:292-298`) and to decide staked-vs-unstaked connection-table placement and pruning immunity (`swqos.rs:354-414`, `ConnectionTable::prune_random` in `streamer/src/nonblocking/quic.rs:986-1006`). Nowhere in `try_add_connection`, `cache_new_connection`, or the connection's stream-handling loop is the peer's current stake re-queried against the live `staked_nodes` table. `ConnectionEntry::stake()` (`streamer/src/nonblocking/quic.rs:896-901`) simply returns the `peer_type` that was captured at accept time.

This mirrors the report's exact defect shape: `TalentirTokenV1.setMarketplace()` updates the "current" trusted address going forward, but does not retroactively revoke the `isApprovedForAll` grant already baked into previously-minted tokens. Here, `StakedNodesUpdaterService` updates the "current" stake table going forward, but does not retroactively revoke/downgrade the `ConnectionPeerType::Staked(stake)` grant already baked into already-open connections. The only mechanism that removes a connection is capacity-driven pruning (`prune_random`/`prune_oldest`) that runs when a *new* connection needs room — there is no periodic sweep that re-validates existing connections' stake against the current `staked_nodes` snapshot and demotes/closes ones whose stake has since dropped to zero or fallen off the epoch stake set.

### Impact Explanation
A peer that held meaningful stake at connection time keeps enjoying the privileged staked-connection slot, pruning immunity relative to lower-stake newcomers, and its stake-proportional QUIC stream-throttling allowance for as long as the connection stays open (which the client fully controls via keep-alives/idle timeouts), even after that stake is fully unstaked/delegated away/slashed in a later epoch. Because staked slots and staked-tier stream throughput are a scarce, prioritized resource on the TPU QUIC ingestion path, a peer that deliberately unstakes immediately after opening (and holding open) connections can continue occupying staked-table capacity and consuming a disproportionate stream-throttling budget indefinitely, degrading legitimate current stakeholders' ability to get TPU slots/throughput — a non-RPC remote resource-exhaustion/degradation vector on the TPU ingestion path, not merely a metrics/cosmetic issue.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires no admin/leaked-key/trusted-integration assumption — any current low/mid stake holder can trigger it unilaterally by unstaking/delegating away after opening TPU QUIC connections and simply keeping the connection alive. It does not require malicious peer/validator collusion beyond an ordinary staked entity's own unilateral stake action. The window of exploitation is bounded only by however long the attacker's client is willing/able to hold the QUIC connection open (idle-timeout permitting), which in the streamer's connection lifecycle can be indefinite absent an explicit stake-revalidation check.

### Recommendation
Periodically re-validate each open connection's classification against the live `staked_nodes` snapshot (e.g., during the existing pruning/cleanup passes in `streamer/src/nonblocking/quic.rs`), demoting or closing connections whose backing pubkey's current stake is zero/absent, instead of relying solely on capacity-triggered `prune_random`/`prune_oldest`. At minimum, tie the cached `peer_type`/`stake` to the same 5-second refresh cadence as `StakedNodesUpdaterService` rather than freezing it for the connection's entire lifetime.

### Proof of Concept
Not independently executable from static analysis alone (would require running a local test-validator/streamer harness to open a staked QUIC connection, then simulate stake removal via `StakedNodes::new` update, and observe the pre-existing connection continue to be classified `ConnectionPeerType::Staked` in `swqos.rs`/`simple_qos.rs`). The code paths cited above (`build_connection_context`, `ConnectionEntry::stake`, `prune_random`) demonstrate the absence of any re-check logic based purely on static review; dynamic confirmation would require a Devin session with test-harness access to `streamer/src/nonblocking/quic.rs` unit/integration tests (e.g., extending `test_try_add_connection_context_updates` in `streamer/src/nonblocking/simple_qos.rs`) to assert the classification does not change after mutating the underlying `StakedNodes`.
