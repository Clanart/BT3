## Analysis Result

The Blend bug class — *"removing an entity from the active reward set advances an internal accrual index past already-earned-but-undistributed amounts, permanently discarding them because the disabled entity can never re-observe that interval"* — has a real analog in this Agave fork's Alpenglow staking-reward pipeline.

### Title
Alpenglow reward-credit index is force-advanced without payout when a vote account is VAT-filtered out of `RewardEpochDelegatedStakes`, permanently burning already-earned stake rewards - (File: `runtime/src/inflation_rewards/points.rs`)

### Summary
`RewardEpochDelegatedStakes` is built only from the VAT-filtered top-`MAX_ALPENGLOW_VOTE_ACCOUNTS` set [1](#0-0) , using `VoteAccounts::clone_and_filter_for_vat`, which truncates/removes vote accounts by stake ranking [2](#0-1) . When a stake's delegated vote account is not present in that filtered set for the reward epoch, `calculate_alpenglow_points` still advances the stake's `new_credits_observed` all the way to `final_epoch_credits` via `calc_earned_credits`'s side effect, but discards the computed `earned_points`/rewards and reports `force_credits_update_with_skipped_reward: true` [3](#0-2) . That forced credit update is then unconditionally written back to the on-chain `stake.credits_observed` field even though zero reward was actually paid [4](#0-3) .

### Finding Description
`calc_earned_credits` computes `earned_credits` for the interval between what the stake previously observed and what the vote account now records, and as a side effect advances `*new_credits_observed` to `max(*new_credits_observed, final_epoch_credits)` *before* the caller checks whether the vote account's total delegated stake is available for that epoch [5](#0-4) .

`calculate_alpenglow_points` calls `calc_earned_credits` first, then attempts to look up `total_stake` for the vote account in `reward_epoch_delegated_stakes.delegated_stakes`. If that vote account is absent (because it was excluded by `clone_and_filter_for_vat` for the epoch), the function returns `Err(CalculatedStakePoints { tower_points: 0, ag_points: 0, new_credits_observed, force_credits_update_with_skipped_reward: true })` — i.e., the already-computed `earned_credits`/reward amount is thrown away, but `new_credits_observed` (already advanced to `final_epoch_credits`) is kept [6](#0-5) .

Upstream, `calculate_stake_rewards`'s `skip_reward` path returns `staker_rewards: 0, voter_rewards: 0, new_credits_observed` (the already fast-forwarded value) whenever `force_credits_update_with_skipped_reward` is set [7](#0-6) . `redeem_stake_rewards` then unconditionally commits this into the live stake account: `stake.credits_observed = calculated_stake_rewards.new_credits_observed;` while paying `staker_rewards = 0` [4](#0-3) .

This is structurally identical to the Blend bug: an entity (pool / vote account) is removed from the "active reward zone" (VAT-filtered top-N set), and the code sets the accrual index (`emission index` / `credits_observed`) to a value that has already passed the point where real rewards were earned — permanently precluding any later "gulp" (reward redemption) of the interval that had already accrued.

### Impact Explanation
Vote credits that a validator's vote account legitimately earned during an epoch where it temporarily falls out of the VAT top-`MAX_ALPENGLOW_VOTE_ACCOUNTS` (e.g., due to normal stake fluctuation near the cutoff boundary, since ties at the cutoff are dropped per SIMD-357 [8](#0-7) ) are permanently discarded for every stake delegated to it. Because `credits_observed` is force-advanced to `final_epoch_credits`, the next epoch's `calc_earned_credits` will see `credits_in_stake >= final_epoch_credits` and compute zero new credits for that interval even if the vote account re-enters the VAT set later — the emissions for that epoch are unrecoverably burned. This is a loss-of-funds bug affecting delegators of any validator that oscillates around the VAT stake-rank cutoff, without requiring a malicious actor.

### Likelihood Explanation
The VAT filter is stake-rank based and recomputed every epoch from live, fluctuating delegated stake [9](#0-8) ; any validator sitting near the `MAX_ALPENGLOW_VOTE_ACCOUNTS` boundary (or affected by the "drop ties at cutoff" rule) can be excluded in one epoch and included again in the next purely through ordinary stake movement by unprivileged delegators/withdrawals — no attacker collusion or admin action required, matching the "unprivileged" scope of this review.

### Recommendation
Do not advance `new_credits_observed` past the point actually reflected by `total_stake` availability. When `reward_epoch_delegated_stakes` lacks an entry for the vote account, either (a) leave `stake.credits_observed` unchanged so the earned interval can be redeemed once the vote account re-enters `RewardEpochDelegatedStakes`, or (b) retain the computed `earned_credits`/points and pay them out using a fallback stake denominator (e.g., the last known total stake) instead of discarding them silently while still committing the forward-advanced `credits_observed`.

### Proof of Concept
Not independently runnable without executing the full Alpenglow reward-calculation test harness; the existing test `test_alpenglow_reward_epoch_delegated_stakes_account_is_bounded` [10](#0-9)  demonstrates that a vote account can be excluded from `RewardEpochDelegatedStakes` in a given epoch through ordinary stake-rank truncation; extending that test to (1) increment vote credits for the excluded vote account's epoch, (2) run reward calculation for that epoch, and (3) assert that `stake.credits_observed` advanced to `final_epoch_credits` while `staker_rewards == 0` would confirm the permanent loss, then re-including the vote account in a later epoch and asserting no compensating reward is ever paid for the skipped interval.

Note: I was unable to fully trace `redeem_delegation_rewards`'s exact call chain into `calculate_stake_rewards_and_commissions` before the tool budget ran out; the analysis above is based on the confirmed code paths in `points.rs` and `inflation_rewards/mod.rs` that I did retrieve, which show the credits-advance-without-payout mechanism directly. A Devin session with full file access should verify the end-to-end call path from `calculate_stake_rewards_and_commissions` through `redeem_delegation_rewards` to eliminate any remaining ambiguity before treating this as fully confirmed.

```rust
    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }

        let valid_len = entries_to_sort.len();
        if entries_to_sort.len() > max_vote_accounts {
            // Find the cutoff stake using partial sort (more efficient than full sort).
            let (_, cutoff_entry, _) =
                entries_to_sort.select_nth_unstable_by(max_vote_accounts, |a, b| b.2.cmp(&a.2));
            let floor_stake = cutoff_entry.2;

            // Per SIMD 357, we remove all vote accounts with stake smaller or equal to
            // the first truncated one.
            entries_to_sort.retain(|(_, _, stake)| *stake > floor_stake);
        }
```

```rust
fn calc_earned_credits(
    stake: &Stake,
    final_epoch_credits: u64,
    initial_epoch_credits: u64,
    new_credits_observed: &mut u64,
) -> u128 {
    let credits_in_stake = stake.credits_observed;

    // figure out how much this stake has seen that
    //   for which the vote account has a record
    let earned_credits = if credits_in_stake < initial_epoch_credits {
        // the staker observed the entire epoch
        final_epoch_credits - initial_epoch_credits
    } else if credits_in_stake < final_epoch_credits {
        // the staker registered sometime during the epoch, partial credit
        final_epoch_credits - *new_credits_observed
    } else {
        // the staker has already observed or been redeemed this epoch
        //  or was activated after this epoch
        0
    };
    *new_credits_observed = (*new_credits_observed).max(final_epoch_credits);
    u128::from(earned_credits)
}
```

```rust
    fn test_alpenglow_reward_epoch_delegated_stakes_account_is_bounded() {
        let num_validators = crate::bank::MAX_ALPENGLOW_VOTE_ACCOUNTS + 1;
        let validator_keypairs = (0..num_validators)
            .map(|_| genesis_utils::ValidatorVoteKeypairs::new_rand())

        // account instead of dropping a tie group at the boundary.
        let stakes = (0..num_validators)

            .collect::<Vec<_>>();
        let filtered_vote_pubkey = validator_keypairs
            .last()
            .expect("validator keypairs must not be empty")
            .vote_keypair
            .pubkey();
        let GenesisConfigInfo {
            mut genesis_config, ..
        } = genesis_utils::create_genesis_config_with_alpenglow_vote_accounts(
            1_000_000_000 * LAMPORTS_PER_SOL,
            &validator_keypairs,

        );
        genesis_config.epoch_schedule = EpochSchedule::new(SLOTS_PER_EPOCH);
        let features_to_deactivate = crate::slot_params::slot_time_feature_ids().to_vec();

        let (bank, bank_forks) =
```
