## Title
Floating-point precision loss in stake-percentage threshold comparisons enables incorrect vote/switch/confirmation decisions - ([File: core/src/consensus.rs], [File: runtime/src/commitment.rs], [File: core/src/consensus/vote_stake_tracker.rs])

## Summary
The Paladin report is about a check computed on one value (`amount`) diverging from the value actually applied (`bias`) because of integer-division truncation, so a check that appears to pass in fact permits an outcome the check was meant to forbid. Agave's own codebase already contains, and explicitly tests, the analogous bug class: converting large `u64` lamport/stake values to `f64` before dividing to obtain a stake fraction loses precision once the values exceed the 53-bit mantissa of `f64` (~9.007×10^15), which is smaller than realistic Solana total-stake figures (hundreds of millions of SOL × 10^9 lamports/SOL, i.e. > 10^17). This means the computed "fraction of stake" used in several threshold checks can silently be on the wrong side of the intended boundary, exactly as in the Paladin case where the checked value (`amount`) and the value that determines the real outcome (`bias`) diverge.

## Finding Description
The repository's own `votor-messages/src/fraction.rs` demonstrates this precision-loss class directly in a regression test: [1](#0-0) 

`stake as f64 / total_stake.get() as f64 <= 0.6` evaluates to `true` even though `stake` is actually `60% + 1` of `total_stake`, i.e. the f64 ratio is *wrong* relative to the exact rational comparison, which the codebase itself flags with the comment `// wrong!`. The `Fraction` type with cross-multiplication in `u128` was introduced specifically to avoid this: [2](#0-1) 

However, several consensus-relevant call sites still use the unsafe `as f64` division pattern instead of the exact `Fraction`-style comparison:

- Tower's per-slot vote validity check (`check_vote_stake_threshold`), which determines whether a fork has enough votes to allow voting deeper into the tower: [3](#0-2) 

- The switch-proof (`SWITCH_FORK_THRESHOLD`) decision, which determines whether a validator is allowed to switch forks: [4](#0-3) 

- The commitment-level lockout accounting used for confirmation reporting (`get_lockout_count`, driven by `VOTE_THRESHOLD_SIZE = 2/3`): [5](#0-4) 

- The optimistic/duplicate confirmation tracker that decides when a slot crosses the supermajority or duplicate-confirmation stake threshold, feeding `cluster_info_vote_listener.rs`'s `process_last_vote_for_optimistic_confirmation`: [6](#0-5) [7](#0-6) 

In every one of these, a `u64` stake or lamport amount that can legitimately reach the 10^17 range (real total network stake) is cast to `f64` and divided/multiplied, which — exactly as in the Paladin `slope * boostDuration` truncation — can produce a result that differs from the true, exact rational value near the threshold boundary. Because the divergence direction is a function of the low-order bits of `total_stake`/`fork_stake`, and any staker/validator operator can choose lamport amounts for their own delegated stake, an unprivileged actor can pick stake amounts intentionally engineered to push the floating-point-rounded ratio to the opposite side of the boundary from the exact ratio (i.e., cause the check to say "reached 2/3" when the true weighted stake is marginally below 2/3, or vice versa), without needing to compromise any other validator or rely on a malicious peer/leader assumption.

## Impact Explanation
This maps to the "false execution/rooting/acceptance" impact category: the switch-proof, vote-threshold, and optimistic/duplicate-confirmation logic are all part of the fork-choice/consensus-safety machinery. An incorrect threshold decision caused by floating-point rounding could cause a validator to:
- report/act on a slot as "duplicate confirmed" or "optimistically confirmed" when the true weighted stake has not actually crossed the safety threshold (false acceptance), or
- refuse a legitimate switch/vote that should be permitted by the true (exact) fraction (availability/liveness degradation).

Both are within-scope non-RPC consensus-adjacent effects, distinct from an ordinary rounding nuisance, because they are safety-relevant boolean gates, not just approximate metrics.

## Likelihood Explanation
Likelihood is low but non-zero and grows with network stake concentration/size: it requires stake values whose bit patterns land exactly at the edge of the intended percentage boundary, which is realistic to engineer once total network stake — as it already is on mainnet — regularly exceeds the `f64` 53-bit exact-integer range (~9×10^15), amplifying rounding error to potentially many lamports. No privileged access, malicious peer, or trusted component is required; a normal, unprivileged staker choosing precise delegation amounts is sufficient to attempt to steer the boundary.

## Recommendation
Replace `as f64` ratio comparisons in consensus-critical threshold checks (`core/src/consensus.rs::check_vote_stake_threshold` and switch-proof logic, `runtime/src/commitment.rs::get_lockout_count`, `core/src/consensus/vote_stake_tracker.rs::add_vote_pubkey`) with exact integer/rational comparisons (e.g., cross-multiplication in `u128`, mirroring the `Fraction` type already added in `votor-messages/src/fraction.rs`), so that stake-fraction-vs-threshold decisions are always exact rather than approximate.

## Proof of Concept
The codebase's own unit test proves the underlying arithmetic flaw: [1](#0-0) 

Substituting the same `total_stake`/`stake` magnitudes (order 10^17, consistent with real mainnet total stake in lamports) into `core/src/consensus.rs`'s `lockout = *fork_stake as f64 / total_stake as f64` (line 1351) or `core/src/consensus/vote_stake_tracker.rs`'s `threshold_stake = (total_stake as f64 * threshold) as u64` (line 30) reproduces the same class of divergence between the exact fractional comparison and the `f64`-computed one, which can flip a `PassedThreshold`/`FailedThreshold` or `reached_threshold` boolean relative to the true stake-weighted outcome.

    fn get_lockout_count(&self, slot: Slot, minimum_stake_percentage: f64) -> Option<usize> {
        self.get_block_commitment(slot).map(|block_commitment| {
            let iterator = block_commitment.commitment.iter().enumerate().rev();
            let mut sum = 0;
            for (i, stake) in iterator {
                sum += stake;

                    return i + 1;
                }
