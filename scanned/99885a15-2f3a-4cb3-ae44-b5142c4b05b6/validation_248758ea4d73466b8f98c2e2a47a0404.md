Based on my research, the closest local analog to the Symbiotic `unregisterOperatorVault`/`_autoDeployedVault` staleness bug is an explicitly-acknowledged-but-unfixed staleness gap in Agave's `StakesCache`.

### Title
Stale `StakesCache` vote/stake entries survive owner reassignment away from the Vote/Stake program - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` only evicts a cached vote/stake account entry when the account's lamports drop to zero. It never checks whether the account's *owner* has changed away from the vote/stake program while lamports remain non-zero, so the bank-level `Stakes<StakeAccount>` cache (`vote_accounts`, `stake_delegations`) can retain a stale entry for a pubkey that the runtime no longer considers a valid vote/stake account — the same "mapping not updated on de-registration" pattern as the reported `_autoDeployedVault` bug.

### Finding Description
`StakesCache::check_and_store` branches purely on `account.owner()` and `account.lamports()`: [1](#0-0) 

If lamports are non-zero and the owner is neither the vote program nor the stake program, the function does nothing — it neither upserts nor removes the existing cached entry. There is a code comment in the very same struct acknowledging this gap: [2](#0-1) 

This is directly analogous to `unregisterOperatorVault` leaving `_autoDeployedVault[operator]` untouched: the authoritative on-chain state (account owner) has moved on, but the cache/index (`StakesCache`) keeps referencing the old, now-invalid, entry because the mutation code path that changed the underlying state has no corresponding update hook into the cache.

The gap is explicitly exercised (and left disabled) in the test suite: [3](#0-2) [4](#0-3) 

`update_stakes_cache` in `bank.rs` is the only call site feeding `check_and_store`, and it is invoked once per successfully-executed transaction touching the account, driven by whatever the account's owner is *after* execution: [5](#0-4) 

### Impact Explanation
`Stakes<StakeAccount>` is the bank-level cache used to compute `vote_accounts()`, `highest_staked_node()`, and to seed `EpochStakes` for future-epoch leader-schedule/stake-weight computations. A stale entry retained after the account's owner changes away from the vote/stake program means the bank continues to treat a pubkey as an active vote/stake account with its last-known delegated stake, even though the account is no longer owned by the corresponding native program. This falls into the runtime/accounts category and can propagate into consensus-relevant state (`vote_accounts`, `EpochStakes`) rather than being purely cosmetic — i.e. potential false-acceptance of stale voting/stake weight.

### Likelihood Explanation
Low-to-uncertain, and this is the main caveat I could not fully resolve given tool-call limits. The SVM/runtime account-owner-change invariant normally requires the *current* owning program (vote or stake, both native programs) to authorize any owner change on a writable account it owns. Neither the native Vote nor Stake program exposes an instruction that reassigns account ownership while leaving lamports non-zero (the only owner-vacating path exercised in tests is full withdrawal to zero lamports, which the zero-lamport branch already handles correctly: [6](#0-5) ). I was not able to confirm, within the available searches, a concrete unprivileged transaction sequence that reassigns a non-zero-lamport vote/stake account's owner without also zeroing its lamports first. The maintainers' own TODO/test (`check_owner_change: false`) indicates this is a recognized, deliberately-deferred hardening gap rather than a fully demonstrated live exploit path — so while the stale-cache pattern precisely mirrors the reported bug class, its reachability by an unprivileged actor is unconfirmed and should be verified further (e.g., by inspecting whether any account-reuse/slot-collision path in `accounts-db` could cause a pubkey to be observed with a different owner while retaining old `StakesCache` state without an intervening zero-lamport transition).

### Recommendation
Harden `StakesCache::check_and_store` (and its caller `Bank::update_stakes_cache`) to also evict cache entries when a previously-vote/stake-owned pubkey is observed with a non-vote/stake owner and non-zero lamports, rather than only on the zero-lamport path — mirroring the same "unregister must also purge derived mappings" fix applied in the Symbiotic report (overriding the unregister/removal path to clear all derived caches, not just the primary registry).

### Proof of Concept
Not fully constructible from local code alone: a concrete PoC requires an unprivileged, non-zero-lamport owner-reassignment transaction sequence for a vote or stake account, whose existence I could not confirm against the native Vote/Stake program instruction sets within the available searches. The existing regression test `check_stake_vote_account_validity(false, ...)` in `runtime/src/bank/tests.rs` demonstrates the cache does *not* invalidate on owner change under injected/simulated conditions (`bank.store_account` directly forging the owner field), but does not by itself demonstrate an unprivileged transaction path to reach that state in production.     fn update_stakes_cache(
        &self,
        txs: &[impl SVMMessage],
        processing_results: &[TransactionProcessingResult],
    ) {
        debug_assert_eq!(txs.len(), processing_results.len());
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let use_fixed_point_stake_math = self.use_fixed_point_stake_math();
        txs.iter()
            .zip(processing_results)
            .filter_map(|(tx, processing_result)| {
                processing_result
                    .processed_transaction()
                    .map(|processed_tx| (tx, processed_tx))
            })
            .filter_map(|(tx, processed_tx)| {
                processed_tx
                    .executed_transaction()
                    .map(|executed_tx| (tx, executed_tx))
            })
            .filter(|(_, executed_tx)| executed_tx.was_successful())
            .flat_map(|(tx, executed_tx)| {
                let num_account_keys = tx.account_keys().len();
                let loaded_tx = &executed_tx.loaded_transaction;
                loaded_tx.accounts.iter().take(num_account_keys)
            })
            .for_each(|(pubkey, account)| {
                // note that this could get timed to: self.rc.accounts.accounts_db.stats.stakes_cache_check_and_store_us,
                //  but this code path is captured separately in ExecuteTimingType::UpdateStakesCacheUs
                self.stakes_cache.check_and_store(
                    pubkey,
                    account,
                    new_warmup_cooldown_rate_epoch,
                    use_fixed_point_stake_math,
                );
            });
