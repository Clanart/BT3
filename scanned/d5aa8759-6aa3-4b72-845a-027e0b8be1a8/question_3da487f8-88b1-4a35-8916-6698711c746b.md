Target: core::citrea::CitreaClient::get_storage_proof(l2_height, deposit_index), which returns StorageProof{ index: ind, .. } echoing back the caller-supplied deposit_index verbatim with no cross-check against an independently observed Bridge-contract event (e.g. a WithdrawalUTXOSet or DepositReplaced log) proving this index was actually assigned to the withdrawal being reimbursed. Attacker action: an unprivileged attacker who controls the withdrawal UTXO bytes and Schnorr signature registered via `withdraw` cannot directly choose deposit_index (that's Bridge-contract-assigned), but can register a withdrawal whose withdrawal UTXO happens to coincide, after Aggregator-side lookup, with a stale/cached deposit_index value if the caller of get_storage_proof (per Scope, Aggregator::optimistic_payout reusing deposit_id) passes a deposit_id that was originally resolved for a *different* withdrawal round. Preconditions: an existing finalized payout for deposit_index i exists, and the withdrawal_utxo->deposit_id resolution used by the aggregator is not re-derived per RPC call but cached/passed through client input. Call sequence: gRPC OptimisticPayoutParams{ deposit_id: i, .. } -> Aggregator::optimistic_payout -> CitreaClient::get_storage_proof(l2_height, i) -> returns StorageProof{index: i} bound only to whatever slot i currently contains on Citrea, not to the withdrawal UTXO the caller supplied. Binding: the withdrawal UTXO embedded in StorageProof at index i (per Bridge contract's withdrawalUTXOs[2*i]) == the withdrawal UTXO the operator/aggregator is currently fronting BTC for. Impact: Critical - a payout can be signed and reimbursed against a withdrawal UTXO different from the one actually paid out on Bitcoin, letting an operator (or, via CALLER_AUTHORITY confusion, the wrong claim) be credited for BTC never fronted to that specific withdrawer.
