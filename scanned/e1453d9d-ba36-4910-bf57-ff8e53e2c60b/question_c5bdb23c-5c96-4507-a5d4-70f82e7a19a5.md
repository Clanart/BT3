Attacker action: send a `Setup(Empty{})` RPC to the aggregator's public port with no certificate while the aggregator already has verifier/operator key state cached from a prior successful setup. Preconditions: `client_verification=false`; at least one deposit round is in-flight with cached `VerifierPublicKeys`/`ParticipatingVerifiers`. Call sequence: Noop interceptor passes request untouched -> `AggregatorServer::setup` re-queries every verifier/operator endpoint and rewrites the aggregator's in-memory/DB key-distribution state used by every subsequent `NewDeposit`. Binding: the verifier/operator key set used to sign the currently in-flight deposit's move-to-vault tx == the verifier/operator key set `Setup` most recently wrote, and an attacker-triggered re-run can make these diverge mid-session. Impact: Critical - N-of-N partial signatures produced for a move tx under a key set the honest deposit session never agreed to, corrupting `MINT AUTHORITY`. Proof idea: cargo test that starts `NewDeposit` for a real regtest deposit, races an unauthenticated `Setup` call mid-flow, and asserts the resulting move tx's signature set matches the keys the deposit was actually opened with.
