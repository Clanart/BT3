`Aggregator::optimistic_payout` builds a Bitcoin transaction to pay the withdrawal UTXO identified by `get_withdrawal_utxo_from_citrea_withdrawal(deposit_id)` and collects verifier signatures via `Verifier::sign_optimistic_payout`, while a separately-running kickoff/Reimburse flow for the same `deposit_id` independently derives the reimbursement recipient from `get_move_to_vault_txid_from_citrea_deposit(deposit_id)`. If an attacker races both flows for the same `deposit_id` - triggering `optimistic_payout` at the aggregator while an operator's kickoff for the identical deposit is already mid-flight - can both the optimistic payout tx and the operator's Reimburse tx be independently broadcast and confirmed before either flow observes the other's on-chain state? Binding: number of on-chain BTC transactions that pay out withdrawal index i == 1. Impact: Critical, CUSTODY - a single fronted withdrawal produces two settled payouts, draining more BTC than was fronted. Proof idea: regtest-based cargo test in core/src/test starting a kickoff/Reimburse flow and calling `Aggregator::optimistic_payout` concurrently for the same `deposit_id`, mining blocks, and asserting only one of the two payout transactions confirms while the other is rejected by verifier signature checks referencing shared payout state.
