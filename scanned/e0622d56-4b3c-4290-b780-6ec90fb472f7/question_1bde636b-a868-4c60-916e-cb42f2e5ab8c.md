`CitreaClient::get_storage_proof` fetches three storage keys - `storage_key_wd_utxo_hex`, `storage_key_vout_hex`, `storage_key_deposit_hex` - all derived from a single `deposit_index: u32` parameter, and returns `StorageProof { index: ind, .. }` without any cross-check that the UTXO stored at `UTXOS_STORAGE_INDEX + ind*2` on the Bridge contract is the utxo actually registered for withdrawal `ind` versus some other index whose bytes an attacker-influenced caller substitutes. If a caller of `get_storage_proof` (e.g. a compromised or buggy downstream consumer building the bridge circuit input) supplies `deposit_index` equal to the index of a withdrawal that was already reimbursed via `optimistic_payout`, can the same on-chain withdrawal UTXO be re-proved and re-submitted for a kickoff-path reimbursement, producing two settled reimbursement claims for one fronted payout? Binding: number of Reimburse-path or optimistic payouts settled for withdrawal index i == 1. Impact: Critical, ATTRIBUTION/CUSTODY - more BTC leaves the move-to-vault UTXO than was ever fronted. Proof idea: cargo test in core/src/test/deposit_and_withdraw_e2e.rs driving one withdrawal through `Aggregator::optimistic_payout` and then attempting a second reimbursement via the kickoff/Reimburse path for the same `deposit_id`, asserting the second attempt is rejected.
