In `CitreaClient::get_storage_proof` (core/src/citrea.rs), `tx_index: u32 = deposit_index * 2` is computed as an unchecked `u32` multiplication before deriving `storage_key_wd_utxo` and `storage_key_vout`. Can an attacker register a Citrea withdrawal whose index, once relayed through the aggregator's payout flow, reaches `deposit_index` close to `u32::MAX / 2` (e.g. 2^31), such that `deposit_index * 2` wraps around in release-mode arithmetic, causing `get_storage_proof` to fetch storage proofs for an unrelated wrapped-around slot instead of the true withdrawal slot? Binding: `tx_index / 2` recovered from the fetched storage slot == the `deposit_index` of the withdrawal actually being reimbursed. Impact: Critical, CUSTODY - a bridge-circuit proof accepted for the wrong withdrawal UTXO, letting a payout be matched to the wrong (or no) fronted withdrawal. Proof idea: cargo test in core/src/test with a mocked `CitreaClientT` driving `deposit_index` to a value where `*2` overflows `u32`, asserting the returned `StorageProof.index` and derived storage keys do not silently alias another withdrawal's slot.
