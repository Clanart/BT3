Target: `DepositData::get_nofn_xonly_pk` and its cache field `nofn_xonly_pk: Option<XOnlyPublicKey>`. Attacker action: an unprivileged depositor cannot supply `actors.verifiers` directly (aggregator fetches them via `fetch_verifier_keys`), but the *same in-memory* `DepositData` instance is reused across `deposit_sign` and `deposit_finalize` calls on the verifier; attacker triggers a race by submitting two overlapping deposit-flow gRPC streams for the same outpoint O but where the aggregator-fetched verifier set differs between the two flows (e.g. a verifier list refresh happens on the aggregator between `new_deposit` and `deposit_finalize`). Preconditions: aggregator's verifier list is not pinned per-outpoint but re-fetched per RPC call. Call sequence: `deposit_sign` computes and caches `nofn_xonly_pk` from verifier set V1; `deposit_finalize` on a verifier receives `deposit_data` freshly parsed from a second stream with verifier set V2, recomputing `get_nofn_xonly_pk()` (cache is `None` on the fresh struct) yielding a different `nofn_xonly_pk` than what was used to build the presigned move tx. Binding broken: the move txid the verifiers presign == the move-to-vault script derived from the *same* nofn_xonly_pk used for signing, since `create_move_to_vault_txhandler` recomputes `nofn_xonly_pk` from whatever `DepositData` is passed at that moment. Impact: Critical - N-of-N partial signatures produced for a spend no Citrea withdrawal authorises (partial sigs valid for a stale/incorrect nofn key never checked against `check_nofn_correctness`'s cached contract key at finalize time). Proof idea: cargo test in core/src/test that constructs two `DepositData` instances differing only in verifier set for the same outpoint, and asserts `deposit_finalize` rejects finalization if the finalize-time nofn_xonly_pk differs from the sign-time nofn_xonly_pk committed in `insert_deposit_data_if_not_exists`.
