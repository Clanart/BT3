## Analysis

The reported pattern is a **griefing via an exact/strict balance check that can be perturbed by an unprivileged dust deposit**, where the check gates an important state transition (closing/clearing an account) but any external actor can permissionlessly alter the value being compared, permanently blocking that transition.

### Local Agave Analog

`solana_vote_program`'s withdraw instruction implements this exact pattern.

`withdraw()` computes the amount that will remain in the vote account after withdrawal by subtracting the caller-supplied `lamports` from the account's *current* balance, and gates account deinitialization strictly on that remainder being **exactly** zero: [1](#0-0) 

```
let remaining_balance = vote_account.get_lamports().checked_sub(lamports)...
if remaining_balance == 0 {
    ... VoteStateHandler::deinitialize_vote_account_state(...)
} else {
    // require remaining_balance >= rent_exempt_minimum + pending_delegator_rewards
    if remaining_balance < min_balance { return Err(InstructionError::InsufficientFunds); }
}
```

The `lamports` value withdrawn is a **fixed instruction parameter** chosen by the client when it builds the `Withdraw` transaction — it is not recomputed at execution time from the live account balance. The authorized withdrawer, wanting to fully close a vote account, sets `lamports == current_balance` so that `remaining_balance == 0`.

Any unprivileged party can, however, transfer lamports into the vote account before that transaction lands, using the ordinary `system_processor::transfer`, which requires only the **sender** to sign — the recipient (the vote account) requires no signature or permission at all: [2](#0-1) 

Once even 1 lamport of unsolicited dust is added, `vote_account.get_lamports()` no longer matches the value the withdrawer's transaction assumed. Execution then computes `remaining_balance = dust_amount` (e.g. `1`), which is nonzero and below `min_rent_exempt_balance`, so the withdraw call falls into the `else` branch and returns `InstructionError::InsufficientFunds` instead of closing/deinitializing the account. This exactly mirrors the reported bug class: an equality-to-zero condition intended to gate a legitimate close/finalize operation is defeated by anyone sending a trivial, unsolicited amount to the target account, since Solana account recipients never need to consent to receiving lamports.

### Title
Vote-account close/deinitialize via `Withdraw` can be permanently griefed by unprivileged dust transfers - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
`VoteState::withdraw` only deinitializes a vote account when the post-withdrawal balance is exactly zero. Because the withdrawn `lamports` amount is fixed at transaction-build time and any unprivileged account can add lamports to the vote account via a normal System Program transfer with no cooperation from the vote account, an attacker can perpetually break the `remaining_balance == 0` equality and force `InstructionError::InsufficientFunds`, blocking the authorized withdrawer from ever fully closing the vote account.

### Finding Description
`withdraw()` in [3](#0-2)  subtracts the requested `lamports` from `vote_account.get_lamports()` read at execution time, then branches on `remaining_balance == 0` to decide whether to deinitialize the account or instead enforce a `min_balance` floor [4](#0-3) . The `lamports` value comes from `VoteInstruction::Withdraw`, decided by the client ahead of submission, not recomputed from the live balance. Any address can add lamports to the vote account pubkey via `SystemInstruction::Transfer`, which only requires the *sender* to sign [2](#0-1) ; the destination account's owner/authority has no say in whether it receives lamports. This makes the equality check in `withdraw` trivially and repeatedly falsifiable by a third party with no special privileges.

### Impact Explanation
This blocks the authorized withdrawer's ability to fully close and reclaim the vote account's rent-exempt balance/decommission the account — a legitimate account-lifecycle operation gets permanently denied by an unrelated, unprivileged actor. This is a fund-availability/lock impact on an unprivileged built-in program code path (vote program), not requiring any malicious validator, peer, or trusted role — it only requires the ability to send an ordinary system transfer, which any Solana account holder can do.

### Likelihood Explanation
High likelihood and trivial cost: griefing requires only a single-lamport `SystemInstruction::Transfer` to a known, public vote-account address, repeatable indefinitely and cheaply. It requires no special timing beyond landing before/alongside the victim's `Withdraw` transaction, and the vote account address is always public.

### Recommendation
Do not gate deinitialization on an exact `remaining_balance == 0` computed against a client-supplied fixed `lamports` value. Instead, support an explicit "withdraw all" semantics that reads the live balance at execution time (so dust cannot desynchronize the intended full-withdraw amount), or tolerate any `remaining_balance` below a de-minimis dust threshold (rather than requiring literal zero) when deciding whether to deinitialize the vote account.

### Proof of Concept
1. Validator `W` (authorized withdrawer) wants to fully close vote account `V` with current balance `B`. `W` builds `Withdraw(lamports = B)`.
2. Before `W`'s transaction lands, attacker `A` (no relationship to `V`) submits `SystemInstruction::Transfer { lamports: 1 }` from `A` to `V`, needing only `A`'s own signature [5](#0-4) . `V`'s balance becomes `B + 1`.
3. `W`'s `Withdraw(B)` executes: `remaining_balance = (B + 1) - B = 1`, which is `!= 0` and `< min_rent_exempt_balance`, so `withdraw()` returns `InstructionError::InsufficientFunds` per [6](#0-5) , leaving the vote account open and un-closable via this exact-amount attempt.
4. `A` repeats step 2 whenever `W` retries with an updated amount, permanently griefing the close operation at negligible cost.

/// Withdraw funds from the vote account
pub fn withdraw<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    lamports: u64,
    to_account_index: IndexOfAccount,
    signers: &HashSet<Pubkey, S>,
    rent_sysvar: &Rent,
    clock: &Clock,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
