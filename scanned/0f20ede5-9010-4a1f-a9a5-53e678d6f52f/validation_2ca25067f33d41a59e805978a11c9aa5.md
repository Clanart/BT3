## Agave Analog Found

**Bug-class mapping**: The Gravity Bridge report's core defect is a fixed byte-limit check on a range/data scan (`check_for_events` over 5000 blocks, capped at 10MB) that returns a hard error with no retry/chunking logic when legitimate (non-malicious) growth of on-chain state (validator set size) pushes the scanned data past that limit — permanently breaking the query as the state naturally grows.

Agave has the same broken invariant in the secondary-index account scan path used by `getProgramAccounts`, `getTokenAccountsByOwner`, and `getTokenAccountsByDelegate`.

### Title
Fixed byte-limit account-index scans (`scan_results_limit_bytes`) permanently fail with no pagination once legitimate account growth exceeds the limit - (File: `accounts-db/src/accounts.rs`)

### Summary
`Accounts::load_by_index_key_with_filter` enforces a hard byte-size cap (`byte_limit_for_scan`, configured via the validator's `--accounts-index-scan-results-limit-mb` / `scan_results_limit_bytes`) on the accumulated size of scan results, aborting the scan and returning `ScanError` once the running total exceeds the limit. This is invoked from `JsonRpcRequestProcessor::get_filtered_indexed_accounts`, which backs `getProgramAccounts` (when the `ProgramId` secondary index is enabled) and `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`. There is no chunking, cursor, or retry mechanism: if the number of accounts under a given program/owner/delegate grows (through wholly legitimate on-chain activity) past the configured byte budget, every future call to that RPC method for that key fails identically and indefinitely, exactly as in the Gravity Bridge report where growing validator-set data permanently broke the fixed-size block-range log query.

### Finding Description
- `Accounts::accumulate_and_check_scan_result_size` [1](#0-0)  sums `pubkey + account` sizes during the scan and signals abort once the running total exceeds `byte_limit_for_scan`.
- `Accounts::load_by_index_key_with_filter` [2](#0-1)  uses this to set `config.abort()` mid-scan and, via `maybe_abort_scan`, converts that into a hard `ScanError::Aborted` — there is no partial-result/pagination return, just a full failure.
- `JsonRpcRequestProcessor::get_filtered_indexed_accounts` [3](#0-2)  passes the configured `scan_results_limit_bytes` straight through, and `get_filtered_program_accounts` maps any resulting error to `RpcCustomError::ScanError` [4](#0-3) .
- The byte limit is a static, validator-wide configuration value [5](#0-4) , unrelated to any per-request pagination the client can adjust — there's no `before`/`until`/offset parameter analogous to what exists for `getConfirmedSignaturesForAddress2` [6](#0-5) .
- The unit test explicitly documents the abort-on-exceed behavior with no retry/split: `test_get_filtered_indexed_accounts_limit_exceeded` [7](#0-6) .

Just as the Gravity Bridge's `find_latest_valset` had no way to shrink its 5000-block search window when the validator-set data exceeded 10MB, Agave's indexed scan has no way to shrink its query (e.g., by pubkey range, slot, or cursor) when a program/owner/delegate's account set exceeds `scan_results_limit_bytes`. Once a tracked index key's total account footprint crosses the configured limit through ordinary on-chain growth, the RPC call for that key fails on every subsequent attempt — the condition is monotonic and does not self-resolve, matching the report's "must patch to re-enable" framing but here manifesting as a permanently broken RPC method for that key rather than a validator crash.

### Impact Explanation
This falls under "single-client low-rate RPC crash/degradation": popular programs, mints, or delegates whose associated account set naturally grows past the configured scan byte-limit render `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` permanently broken for that key on any node with a secondary index enabled and a `scan_results_limit_bytes` configured, with no code path to page through partial results. This degrades RPC service availability for that specific dataset without requiring any malicious actor — purely a function of legitimate ecosystem growth, mirroring the Gravity Bridge scenario exactly.

### Likelihood Explanation
Likelihood is moderate and grows over time: it requires (a) a validator running with the relevant secondary index enabled (`ProgramId`/`SplTokenOwner`/`SplTokenDelegate`) and a `scan_results_limit_bytes` configured, and (b) the tracked key's account set organically growing past that byte budget — both realistic and increasingly likely as adoption of popular programs/tokens increases, with no attacker action needed.

### Recommendation
Apply the same fix pattern the report recommended for the Gravity Bridge: detect the byte-limit-exceeded condition explicitly and support paginated/chunked scanning (e.g., a cursor or `dataSlice`-like continuation token) instead of an unconditional hard abort, so that legitimately large result sets can still be retrieved incrementally rather than being permanently inaccessible via this RPC method.

### Proof of Concept
Not exploitable interactively without a live large dataset; the existing test demonstrates the failure mode deterministically: [7](#0-6)  stores a single account whose size exceeds the configured `limit` and shows `get_filtered_indexed_accounts` returns `Err`. In production, replace the single oversized account with the natural accumulation of many small accounts under one program/owner/delegate until their combined size exceeds `scan_results_limit_bytes`; every subsequent `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` call for that key will fail identically, with no retry or smaller-scope query able to succeed through the existing RPC surface.

            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }

            .spawn_blocking(move || {

                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()

                    byte_limit_for_scans,
                )

            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }
