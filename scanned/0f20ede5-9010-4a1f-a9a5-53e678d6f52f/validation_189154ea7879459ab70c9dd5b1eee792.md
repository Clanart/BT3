## Finding [1](#0-0) 

### Title
Unchecked `u128`→`u64` cast in Alpenglow vote-reward calculation can panic and halt consensus - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
`calculate_reward()` in `runtime/src/block_component_processor/vote_reward.rs` computes a validator's per-slot inflation reward via `u128` arithmetic and then narrows the result to `u64` with a bare `.try_into().unwrap()`, relying only on a code comment ("the result should fit in u64 because we do not expect the inflation in a single epoch to exceed u64::MAX") rather than a checked/saturating conversion. This is the same class of bug as the Angle `LibGetters.getCollateralRatio()` finding: a ratio/ percentage-style computation whose narrowing cast is not defensively guarded, so it can misbehave (here: panic) when the assumed invariant does not hold.

### Finding Description
```rust
// runtime/src/block_component_processor/vote_reward.rs
let numerator =
    epoch_state.max_possible_validator_reward as u128 * validator_stake_lamports as u128;
let denominator = epoch_state.slots_per_epoch as u128 * total_stake_lamports as u128;

// SAFETY: the result should fit in u64 because we do not expect the inflation in a single
// epoch to exceed u64::MAX.
let reward_lamports: u64 = (numerator / denominator).try_into().unwrap();
```
The value of `reward_lamports` is proportional to `validator_stake_lamports / total_stake_lamports`. The safety comment assumes `validator_stake_lamports <= total_stake_lamports`, but the codebase's own sibling function, `calculate_block_reward()` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, explicitly documents that this assumption can be violated during reward recalculation:
```rust
// During recalculation, if stake account has already received rewards,
// it's possible to have `stake > total_active_stake`. If
// `pending_delegator_rewards` is a huge number, we could potentially
// overflow a `u64`. ... This is harmless in practice, but we
// clamp it just to be safe
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
    .try_into()
    .unwrap_or(u64::MAX)
    .min(pending_delegator_rewards)
``` [2](#0-1) 

`calculate_block_reward()` defends against `stake > total_active_stake` with `unwrap_or(u64::MAX)` plus a `.min()` clamp, while `calculate_reward()` (used for the Alpenglow leader/validator vote-reward split) performs the analogous division and hard-`unwrap()`s the cast, with no fallback. Both consume the same category of inputs — per-validator stake vs. total epoch stake — pulled from `EpochStakes`/`epoch_state.max_possible_validator_reward`, which is state derived at epoch boundaries and can legitimately diverge from `total_stake_lamports` across recalculation/migration windows, exactly as the neighboring comment describes.

### Impact Explanation
If `numerator / denominator` exceeds `u64::MAX`, the `.unwrap()` panics. Because `calc_vote_rewards_update_vote_states()` → `RewardState::calculate_reward()` → `calculate_reward()` runs as part of deterministic bank reward processing on every validator replaying the same block, a panic here is not merely a single-node crash — it is triggered identically by all nodes processing the same epoch-boundary state, producing a chain-wide halt (a validated "consensus halt" impact) rather than an isolated fault.

### Likelihood Explanation
The triggering condition — `validator_stake_lamports` exceeding `total_stake_lamports` relative to `max_possible_validator_reward` and `slots_per_epoch` — is explicitly acknowledged as a real, reachable scenario in the sibling `calculate_block_reward()` comment ("it's possible to have `stake > total_active_stake`"), not a hypothetical. Unlike the Angle finding (which needed astronomically over-collateralized state), this only needs the stake/total ratio and `max_possible_validator_reward` (near `u64::MAX`) to combine such that the division result exceeds `u64::MAX` — a condition the codebase itself says arises "during recalculation."

### Recommendation
Replace the hard `unwrap()` with a saturating/clamped conversion consistent with `calculate_block_reward()`'s existing pattern, e.g. `.try_into().unwrap_or(u64::MAX).min(epoch_state.max_possible_validator_reward)`, or explicitly bound `validator_stake_lamports` to `total_stake_lamports` before the division, so the reward path can never panic regardless of intermediate stake/reward book-keeping drift.

### Proof of Concept
1. At an epoch boundary undergoing recalculation (as already described for `calculate_block_reward`), a validator's recorded `validator_stake_lamports` in `self.accounts` can exceed the `total_stake_lamports` snapshot used for the current calculation (both values sourced independently via `epoch_stakes.total_stake()` and per-account stake lookups).
2. `calculate_reward()` computes `numerator = max_possible_validator_reward * validator_stake_lamports` and `denominator = slots_per_epoch * total_stake_lamports`.
3. Because `validator_stake_lamports > total_stake_lamports`, `numerator / denominator > max_possible_validator_reward / slots_per_epoch`; if `max_possible_validator_reward` is large enough (as it plausibly can be given inflation over an epoch), the quotient exceeds `u64::MAX`.
4. `.try_into().unwrap()` panics inside `RewardState::calculate_reward()`, which is invoked from `update_account()` → `update_accounts()` → `calc_vote_rewards_update_vote_states()`, part of normal bank block-reward processing executed by every validator, causing a synchronized panic/halt.

/// Computes the voting reward in Lamports.
///
/// Returns `(validator rewards, leader rewards)`.
fn calculate_reward(
    epoch_state: &EpochInflationState,
    total_stake_lamports: u64,
    validator_stake_lamports: u64,
) -> (u64, u64) {
    // Rewards are computed as following:
    // per_slot_inflation = epoch_validator_rewards_lamports / slots_per_epoch
    // fractional_stake = validator_stake / total_stake_lamports
    // rewards = fractional_stake * per_slot_inflation
    //
    // The code below is equivalent but changes the order of operations to maintain precision

    let numerator =
        epoch_state.max_possible_validator_reward as u128 * validator_stake_lamports as u128;
    let denominator = epoch_state.slots_per_epoch as u128 * total_stake_lamports as u128;

    // SAFETY: the result should fit in u64 because we do not expect the inflation in a single
    // epoch to exceed u64::MAX.
    let reward_lamports: u64 = (numerator / denominator).try_into().unwrap();
    // As per the Alpenglow SIMD, the rewards are split equally between the validators and the leader.
    let validator_reward_lamports = reward_lamports / 2;
    let leader_reward_lamports = reward_lamports - validator_reward_lamports;
    (validator_reward_lamports, leader_reward_lamports)
}
```
