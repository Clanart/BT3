## Analog Found: Unrecoverable panic on finalized-block bank-hash mismatch (Votor)

### Title
Finalized block with `expected_bank_hash` mismatch causes an unrecoverable validator panic with no repair/recovery path - (File: `votor/src/event_handler.rs`)

### Summary
The Keystore report's broken invariant is: a corrupted authoritative hash (`rootHash`) gets committed via the normal state-transition function (`handleUpdates()`), and once committed there is no recovery mechanism — the account is permanently bricked. The Agave analog is `check_rootable_blocks_and_bank_hash_mismatches()` in the Alpenglow/Votor event handler, which is the function that advances the validator's root (the local equivalent of "committing the canonical root hash"). If a block that has already reached network finality (a `finalized_blocks` entry with a certificate) is frozen locally with a bank hash that disagrees with the `expected_bank_hash` carried in the block footer, the code explicitly documents that this is unrecoverable and calls `panic!`, terminating the validator process with no automated repair path.

### Finding Description
`Bank::set_expected_bank_hash()` stores an "expected" hash taken from an external block footer for later verification [1](#0-0) , and `Bank::freeze_and_verify_bank_hash()` compares this expected value against the locally computed hash when the bank is frozen [2](#0-1) . `update_bank_with_footer_fields()` is the call site that records this expected hash from the block footer into the bank before freezing [3](#0-2) .

In Votor's root-advancement path, `check_rootable_blocks_and_bank_hash_mismatches()` iterates over blocks that have already reached a finalization certificate and, for each one whose block ID matches the frozen bank, compares `bank.expected_bank_hash()` to `bank.hash()`. If they differ, the code panics with a message stating "At this point we will be unable to recover... please save a copy of your ledger to share on discord and restart from a snapshot" [4](#0-3) . This is precisely the "wrong rootHash committed, no recovery mechanism" bug class: the corrupted/mismatched hash is discovered only *after* the block has already been treated as finalized by the consensus protocol, and the only exposed recovery mechanism is an out-of-band, manual restart from an earlier snapshot — there is no automated invariant-repair or rollback logic in the codebase for this state. This is confirmed by the accompanying unit test that asserts a panic occurs in this exact situation [5](#0-4) .

A structurally identical pattern also exists in the legacy TowerBFT replay path: `dump_then_repair_correct_slots()` in `replay_stage.rs` calls `panic!("...This is most likely a bug in the runtime. At this point manual intervention is needed to make progress. Exiting")` once repair retries for a duplicate/mismatched hash exceed `MAX_REPAIR_RETRY_LOOP_ATTEMPTS` [6](#0-5) , and `process_active_banks()` marks a slot dead on any `BankHashMismatch` between the leader-declared hash and the locally computed one [7](#0-6) .

### Impact Explanation
Once triggered, the affected validator process terminates (`panic!`) with no automatic recovery: it must be manually restarted from a snapshot by an operator. Because the trigger condition is a hash mismatch on an already-*finalized*/certified block, if the divergence is caused by any genuine non-determinism in block execution (e.g. a runtime/consensus bug reachable via crafted transactions that produce different execution results across otherwise-honest validator builds/environments), multiple honest validators could hit this panic simultaneously on the same finalized slot, causing a coordinated, non-malicious-actor-triggered halt of a meaningful fraction of the cluster with no built-in remediation — matching the "consensus halt" / "false rooting acceptance" impact category, since the root-advancement pipeline has no fallback other than full manual intervention.

### Likelihood Explanation
This code path only fires once a finalization certificate already exists for the block, so a low-rate but structurally guaranteed panic occurs any time bank-hash computation legitimately diverges from the footer's declared hash after finality — there is no unprivileged attacker prerequisite beyond causing (via normal transaction submission) any execution divergence bug to manifest at exactly the point of root-advancement. The severity is amplified by the complete absence of any documented or implemented recovery mechanism in this function or its callers (`root_utils::set_root`), mirroring the original Keystore finding's exact recommendation gap.

### Recommendation
Introduce a bounded recovery path before resorting to a hard process panic in `check_rootable_blocks_and_bank_hash_mismatches()` (and the analogous `dump_then_repair_correct_slots()` panic), e.g.: attempt an automatic re-verification/re-execution or re-fetch of the block/footer, or degrade to a safe "halt voting but keep serving reads" state instead of an unconditional `panic!`, so operators are not forced into unattended-restart-only remediation for the entire fleet simultaneously.

### Proof of Concept
The existing test `test_finalized_block_with_bank_hash_mismatch_panics` already demonstrates the unrecoverable termination path deterministically: it constructs a bank, sets a mismatching `expected_bank_hash`, sends the corresponding `finalized` event, and asserts the process panics with "we have a bank hash mismatch" [5](#0-4) . The only way this state is reachable in production is by a footer's declared hash disagreeing with the locally-computed hash of an already-certified block — at which point the code path taken is identical to what is exercised in this test, confirming there is no recovery branch other than the `panic!`.

    /// Freeze the bank and verify its computed bank hash against the expected bank hash,
    /// If hashes do not match, return Err with (expected_hash, computed_hash)
    pub fn freeze_and_verify_bank_hash(&self) -> std::result::Result<(), (Hash, Hash)> {
        self.freeze();
        let computed_hash = self.hash();

        if let Some(expected_hash) = self.expected_bank_hash()
            && expected_hash != computed_hash
        {
            return Err((expected_hash, computed_hash));
        }
        Ok(())
    }

    /// If so panic as it is unrecoverable.
    fn check_rootable_blocks_and_bank_hash_mismatches(
        my_pubkey: &Pubkey,
        ctx: &SharedContext,
        vctx: &mut VotingContext,
        rctx: &RootContext,
        pending_blocks: &mut PendingBlocks,
        finalized_blocks: &mut BTreeSet<Block>,
        received_shred: &mut BTreeSet<Slot>,
        stats: &mut EventHandlerStats,
    ) {
        let bank_forks_r = ctx.bank_forks.read().unwrap();
        let old_root = bank_forks_r.root().max(vctx.vote_history.root());
        let Some((new_root, bank_hash)) = finalized_blocks
            .iter()
            .filter_map(|&block| {
                let bank = bank_forks_r.get(block.slot)?;

                // Check for bank hash mismatch
                if bank.is_frozen()
                    && bank.block_id() == Some(block.block_id)
                    && let Some(expected_hash) = bank.expected_bank_hash()
                    && expected_hash != bank.hash()

                    panic!(
                        "{my_pubkey}: Block {block:?} has been finalized, however we have a bank \
                         hash mismatch. The cluster bank hash is {expected_hash} however we \
                         computed {}. At this point we will be unable to recover. Ensure that you \
                         are running a supported Agave version for this cluster. If this is not \
                         operator error,please save a copy of your ledger to share on discord and \
                         restart from a snapshot > {}.",
                        bank.hash(),
                        block.slot
                    );
                }
