## Title
Unprivileged QUIC RTT Inflation Allows Uni-Stream Quota Amplification in Stake-Weighted QoS - (File: `streamer/src/nonblocking/swqos.rs`)

### Summary
`SwQos::cache_new_connection` derives the number of concurrent uni-directional streams a QUIC peer is allowed to open from a client-influenceable value — the connection's measured RTT (`connection.rtt()`) — and multiplies the peer's base quota by up to 7x for "high RTT" connections. Because RTT is effectively self-reported/controllable by the connecting client (it is derived from ACK timing that the client controls), any unprivileged, even unstaked, TPU/QUIC client can inflate its perceived RTT to obtain a stream allowance far above the value intended for its actual stake (or lack thereof), analogous to the `poke()` pattern in the report where a permissionless call recomputes a value from an externally manipulable input and immediately applies it to the caller's benefit.

### Finding Description
When a new QUIC connection is admitted, `cache_new_connection` computes: [1](#0-0) 

`rtt_millis` comes directly from `connection.rtt()`, clamped only from above at `MAX_RTT_MS`. This is fed into `compute_max_allowed_uni_streams_with_rtt`: [2](#0-1) 

For a staked peer, the base per-stake quota is clamped between `QUIC_MIN_STAKED_CONCURRENT_STREAMS` (128) and `QUIC_MAX_STAKED_CONCURRENT_STREAMS` (512); for an unstaked peer, the base is a fixed `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128). In both cases, that base value is subsequently **multiplied** by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS`, i.e. a factor between 1x (at ≤50ms) and 7x (at ≥350ms), with **no clamp applied after this multiplication**: [3](#0-2) 

The resulting `max_uni_streams` is applied directly to the connection via `connection.set_max_concurrent_uni_streams`: [4](#0-3) 

The broken invariant: the server trusts its own RTT sample as a proxy for genuine network latency to justify a larger bandwidth-delay-product stream allowance, but RTT estimation in QUIC is derived from client ACK timing (and the client-reported `ack_delay`), both of which the connecting peer fully controls. A client can deliberately delay acknowledging packets (while reporting a low/zero `ack_delay`) to make the server's RTT estimator believe the path has high latency, without any real latency existing. This is the "poke" analog: an unprivileged caller manipulates an externally-observed, attacker-influenceable value (RTT) that is then immediately and permissionlessly used to recompute a resource allotment (`max_uni_streams`) benefiting that same caller — exactly the class of issue described in the report, where `_getFee`'s dependence on manipulable external state let a caller "poke" a favorable outcome for itself.

Existing guards do not stop this path:
- The only bound is `rtt_millis.min(MAX_RTT_MS)` / `.clamp(REFERENCE_RTT_MS, MAX_RTT_MS)`, which limits the *scaling factor* to 7x but does not validate that the RTT sample is genuine.
- There is no clamp on the final `max_uni_streams` value after the RTT multiplier is applied, so a staked peer's true cap of 512 streams can become up to 3584, and an unstaked peer's cap of 128 can become up to 896.
- `QUIC_TOTAL_STAKED_CONCURRENT_STREAMS` (100,000) is only a documentation constant in this file; it is not referenced/enforced anywhere in the admission path found in `swqos.rs`, so there is no independent aggregate cap preventing this per-connection inflation from compounding across many connections.

### Impact Explanation
This lets any remote, non-privileged (including entirely unstaked) client obtain a substantially larger uni-stream quota than the QoS design intends, without holding any stake. Each additional concurrently open uni-stream consumes server-side buffer/state resources (receive windows, stream state) on the TPU/QUIC listener. Because the inflation applies per-connection and scales with the number of connections a client (or a small botnet of unstaked/low-stake clients) can open up to `max_unstaked_connections`/`max_connections_per_unstaked_peer`, this enables a remote resource-exhaustion vector against the QUIC/TPU ingestion path — falling under the accepted "non-RPC remote exhaustion/crash" impact category, without requiring any malicious-validator or stake assumption.

### Likelihood Explanation
Likelihood is dependent on how difficult it is in practice to manipulate quinn's RTT estimate from the client side; because RTT in QUIC is fundamentally computed from client-reported ACK timestamps and `ack_delay`, and the client is not required to ACK promptly or report accurate delay, an attacker fully controlling their own QUIC client implementation can trivially engineer inflated RTT samples. This requires no privileged access, no stake, and no cooperation from other validators — only a custom/modified QUIC client talking to the public TPU port, making the likelihood moderate-to-high for a determined attacker, though the precision of the resulting inflation (exact 7x vs. partial) depends on how many/which samples quinn's RTT estimator uses across the handshake and connection lifetime, which I was not able to fully verify from the local index (quinn internals are an external dependency, not part of this repo).

### Recommendation
- Do not scale `max_uni_streams` purely off the connection's self-reported/measured RTT; if BDP-based scaling is desired, bound the final result to the peer-type's intended hard cap (`QUIC_MAX_STAKED_CONCURRENT_STREAMS` / `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`) regardless of RTT scaling factor.
- Consider deriving BDP scaling from server-verifiable signals (e.g., handshake-time RTT sampled before any client-controlled ACK delay logic can be exploited) or from throughput actually observed, rather than trusting a live, client-influenceable RTT.
- Enforce a global aggregate stream/connection budget (the unused `QUIC_TOTAL_STAKED_CONCURRENT_STREAMS` constant suggests this was intended) so that per-connection inflation cannot be used to exhaust server-wide resources.

### Proof of Concept
Conceptual PoC (cannot be executed against local code alone; quinn client behavior is external):
1. Attacker connects to the validator's TPU QUIC port as either an unstaked or low-stake peer.
2. During the handshake and any subsequent ACK-eliciting exchange, the attacker's client deliberately delays sending ACKs (while reporting `ack_delay = 0`) so that the server's `connection.rtt()` estimate approaches/exceeds `MAX_RTT_MS` (350ms), even though the real network RTT may be a few ms.
3. When the server calls `cache_new_connection`, `rtt_millis` is computed as ~350ms, and `compute_max_allowed_uni_streams_with_rtt` returns up to 7x the intended base quota (e.g., 896 uni streams for an unstaked peer instead of 128, or up to 3584 for a maximally-staked peer instead of 512).
4. `connection.set_max_concurrent_uni_streams(max_uni_streams)` grants this inflated quota.
5. The attacker opens streams up to the inflated limit across multiple connections (bounded only by `max_connections_per_unstaked_peer`/`max_unstaked_connections`), consuming disproportionate server resources relative to their actual stake/trust level. [5](#0-4)

// Empirically found max number of concurrent streams
// that seems to maximize TPS on GCE (higher values don't seem to
// give significant improvement or seem to impact stability)
pub const QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS: u32 = 128;
pub const QUIC_MIN_STAKED_CONCURRENT_STREAMS: u32 = 128;

// Set the maximum concurrent stream numbers to avoid excessive streams.
// The value was lowered from 2048 to reduce contention of the limited
// receive_window among the streams which is observed in CI bench-tests with
// forwarded packets from staked nodes.
pub const QUIC_MAX_STAKED_CONCURRENT_STREAMS: u32 = 512;

pub const QUIC_TOTAL_STAKED_CONCURRENT_STREAMS: u32 = 100_000;

/// RTT after which we start BDP scaling
const REFERENCE_RTT_MS: u32 = 50;

/// Above this RTT we stop scaling for BDP
const MAX_RTT_MS: u32 = 350;

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}

impl SwQos {
    fn cache_new_connection(
        &self,
        client_connection_tracker: ClientConnectionTracker,
        connection: &Connection,
        mut connection_table_l: MutexGuard<ConnectionTable<ConnectionStreamCounter>>,
        conn_context: &SwQosConnectionContext,
    ) -> Result<
        (
            Arc<AtomicU64>,
            CancellationToken,
            Arc<ConnectionStreamCounter>,
        ),
        ConnectionHandlerError,
    > {
        // get current RTT and limit it to MAX_RTT_MS right away
        let rtt_millis = connection.rtt().as_millis().min(MAX_RTT_MS as u128) as u32;
        let max_uni_streams = VarInt::from_u32(compute_max_allowed_uni_streams_with_rtt(
            rtt_millis,
            conn_context.peer_type(),
            conn_context.total_stake,
        ));
