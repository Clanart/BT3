### Title
Alpenglow VAT burn ignores `pending_delegator_rewards` reserve, allowing the protocol to burn lamports owed to delegators from vote accounts - (File: `runtime/src/bank.rs`)

### Summary
The Lido report flags a case where a contract's tracked "ready to claim" accounting value can exceed the contract's actual token balance, because the code that transfers funds does not verify the contract holds enough balance to honor that specific obligation. The Agave analog is in the Alpenglow Validator Admission Ticket (VAT) burn path: `Bank::maybe_burn_vat_from_staked_accounts` unconditionally debits `vat_to_burn_per_epoch` lamports from every eligible vote account, using an eligibility filter (`VoteAccounts::clone_and_filter_for_vat`) that only checks total lamports against the VAT amount itself - it does not account for `pending_delegator_rewards`, an obligation to delegators that the vote program's own `withdraw()` path treats as untouchable reserved balance.

### Finding Description
`programs/vote/src/vote_state/mod.rs` enforces, via `withdraw()`, that a vote account's lamports may never be reduced below `rent_exempt_minimum + pending_delegator_rewards`: [1](#0-0) 

`pending_delegator_rewards` is an accounting field tracking lamports deposited into the vote account (via `DepositDelegatorRewards`, SIMD-0123) that are owed to delegators and must later be withdrawable via `WithdrawPendingDelegatorRewards`: [2](#0-1) 

However, the Alpenglow VAT burn logic in `Bank::maybe_burn_vat_from_staked_accounts` subtracts `vat_to_burn_per_epoch` directly from each vote account's raw lamports, completely bypassing the vote program's `withdraw()` invariant: [3](#0-2) 

The only precondition is that the vote account was retained by `VoteAccounts::clone_and_filter_for_vat`, whose eligibility test is `vote_account.lamports() >= minimum_vote_account_balance` (i.e., merely `>= vat_to_burn_per_epoch`): [4](#0-3) 

This filter has no awareness of `pending_delegator_rewards` or the rent-exempt minimum reserved by the vote program's own withdrawal logic. A vote account can simultaneously satisfy "lamports >= vat_to_burn_per_epoch" while its lamports minus `pending_delegator_rewards` minus rent-exempt-minimum is far less than `vat_to_burn_per_epoch` (or even negative). The runtime will still burn the full `vat_to_burn_per_epoch`, eating directly into the funds reserved for delegator rewards - exactly the "contract has less than `_readyToClaim`"-style broken invariant from the Lido report, except here the corrupted value is the vote account's actual lamports balance relative to its own `pending_delegator_rewards` commitment.

### Impact Explanation
This is not a self-inflicted loss by the vote account owner; delegator rewards deposited via `DepositDelegatorRewards` are supposed to be protected exactly like a segregated escrow (that is the entire point of the `withdraw()` reserve check). If the VAT burn silently consumes lamports that back `pending_delegator_rewards`, then when a delegator later calls `WithdrawPendingDelegatorRewards` for their share, the vote account may no longer hold enough lamports to honor the full `pending_delegator_rewards` figure recorded in vote state, even though `withdraw()`'s own bookkeeping still reports the same `pending_delegator_rewards` value. This is a fund-loss/fund-inconsistency bug affecting unprivileged delegators who have no way to prevent or predict the VAT burn touching their reserved rewards - it satisfies the "fund theft/loss" impact category since it silently transfers value that belongs to third parties (delegators) to the incinerator.

### Likelihood Explanation
This is deterministic, not probabilistic: any epoch boundary once `alpenglow` is enabled, for any vote account whose `lamports - pending_delegator_rewards - rent_exempt_minimum < vat_to_burn_per_epoch` (while total lamports still clears the VAT filter threshold), the burn will execute and cut into the reserved delegator rewards. A validator (or any account that funds the vote account, since `DepositDelegatorRewards` allows any signer to deposit) can trivially create this condition by ensuring the vote account's balance sits just above `vat_to_burn_per_epoch` while carrying a large `pending_delegator_rewards` balance from recent deposits. No malicious/trusted assumption is required beyond ordinary use of the SIMD-0123 deposit feature and the existence of the Alpenglow VAT mechanism, both of which are unprivileged, standard code paths.

### Recommendation
`VoteAccounts::clone_and_filter_for_vat` and/or `Bank::maybe_burn_vat_from_staked_accounts` should exclude the vote account's `pending_delegator_rewards` (and rent-exempt minimum) from the burnable amount, mirroring the reserve check already implemented in `vote_state::withdraw()`. Concretely, the "sufficient balance" check used for VAT eligibility should be `lamports >= rent_exempt_minimum + pending_delegator_rewards + vat_to_burn_per_epoch`, and the burn itself should use a checked subtraction against that same withdrawable ceiling rather than raw `lamports`.

### Proof of Concept
1. Enable `alpenglow` and SIMD-0123 features (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`).
2. Create a VoteStateV4 account with balance `rent_exempt_minimum + vat_to_burn_per_epoch` (just enough to satisfy `minimum_vote_account_balance_for_vat`, per `clone_and_filter_for_vat`'s check at `vote/src/vote_account.rs:226`).
3. Call `DepositDelegatorRewards` to deposit, e.g., `pending_delegator_rewards = 10 * vat_to_burn_per_epoch` lamports into the same vote account (per `programs/vote/src/vote_state/mod.rs:935-988`, this both transfers lamports in and increments `pending_delegator_rewards`).
4. At the next epoch boundary, `Bank::update_epoch_stakes` → `maybe_burn_vat_from_staked_accounts` (`runtime/src/bank.rs:2625,2648-2694`) burns `vat_to_burn_per_epoch` lamports unconditionally from this vote account, since it still passes the `clone_and_filter_for_vat` balance check (total lamports still comfortably exceeds `vat_to_burn_per_epoch`).
5. Attempt `WithdrawPendingDelegatorRewards` for the full `pending_delegator_rewards` amount recorded in vote state: the vote account's actual lamports are now `rent_exempt_minimum + pending_delegator_rewards - vat_to_burn_per_epoch`, i.e., short by `vat_to_burn_per_epoch` versus what `vote_state::withdraw()`'s accounting says should be available - demonstrating the vote account has "insufficient balance" to cover its own recorded `pending_delegator_rewards` obligation, directly mirroring the Lido `_readyToClaim` vs. actual balance mismatch.

Note: I could not fully trace the exact definition of `minimum_vote_account_balance_for_vat()` (only its call sites in `runtime/src/bank.rs`/`genesis_utils.rs`/tests were located, not its body) within the available search budget, so I cannot confirm with certainty whether it is defined as exactly `vat_to_burn_per_epoch` or includes some additional margin. If it does include `rent_exempt_minimum`, the described bug would still hold with respect to `pending_delegator_rewards`, since none of the located code paths reference that field when computing VAT eligibility.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    fn maybe_burn_vat_from_staked_accounts(&mut self, epoch_stakes: &VersionedEpochStakes) {
        let feature_snapshot = self.feature_set.snapshot();
        if !feature_snapshot.alpenglow {
            return;
        }

        let vat_to_burn_per_epoch = self.vat_to_burn_per_epoch();
        let vote_accounts = epoch_stakes.stakes().vote_accounts();
        debug_assert!(vote_accounts.len() <= 2000);
        // +1 for the incinerator account
        let mut accounts_to_store: Vec<(Pubkey, AccountSharedData)> =
            Vec::with_capacity(vote_accounts.len() + 1);
        let mut total_vat = 0u64;

        // Vote accounts have already been filtered by clone_and_filter_for_vat to only include
        // accounts with non-zero stake and sufficient balance.
        for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
            let mut account = self.get_account(vote_pubkey).unwrap();
            total_vat += vat_to_burn_per_epoch;
            account.set_lamports(
                account
                    .lamports()
                    .checked_sub(vat_to_burn_per_epoch)
                    .expect(
                        "Vote accounts should have already been filtered to contain enough \
                         balance for the VAT",
                    ),
            );
            accounts_to_store.push((*vote_pubkey, account));
        }

        // Per SIMD-0357, transfer collected VAT to the incinerator account.
        let mut incinerator_account = self.get_account(&incinerator::id()).unwrap_or_default();
        incinerator_account.set_lamports(
            incinerator_account
                .lamports()
                .checked_add(total_vat)
                .unwrap(),
        );
        accounts_to_store.push((incinerator::id(), incinerator_account));

        self.store_accounts((self.slot, accounts_to_store.as_slice()), None);
        info!(
            "Transferred total VAT of {total_vat} lamports to incinerator from staked vote \
             accounts"
        );
    }

    // This implements the filtering logic described in SIMD-357.
    // 1. Filter out any vote accounts without BLS pubkey
    // 2. Given minimum_vote_account_balance, filter out any vote account
    //    without required balance
    // 3. If we have more than max_vote_accounts vote accounts after above
    //    filtering, sort by stake and truncate
    // 4. If any vote account in the resulting list has the same stake as any
    //    truncated vote account, just remove this vote account as well (A and
    //    B have the same stake amount, it's unfair to keep A in and kick B out
    //    just because of Pubkey difference, because that can be grinded)
    // 5. If we end up with an empty list (can happen if everyone in the world
    //    has the same stake, happens in tests, doesn't happen in real world),
    //    log a warning
    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
