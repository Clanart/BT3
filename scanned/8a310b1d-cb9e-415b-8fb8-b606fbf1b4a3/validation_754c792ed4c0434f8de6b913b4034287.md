Based on the investigation, I found a concrete structural analog to the reported "modifier applied to sibling function but missing on the target function" bug class inside Agave's vote program.

### Title
Missing `block_revenue_sharing_enabled` feature-gate check in `update_commission_collector` (asymmetric with `update_commission_bps`) - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
`update_commission_bps` explicitly gates `CommissionKind::BlockRevenue` operations behind the `block_revenue_sharing_enabled` (SIMD-0123) flag, rejecting the call with `InstructionError::InvalidInstructionData` when the feature is not enabled. `update_commission_collector`, which mutates the same logical BlockRevenue-related vote-account field (`block_revenue_collector`), has no equivalent gate at all — it is missing the check that its sibling function enforces.

### Finding Description
`update_commission_bps` contains an explicit SIMD-0291/SIMD-0123 guard: [1](#0-0) 

This guard prevents any `CommissionKind::BlockRevenue` mutation from succeeding while the network-wide `block_revenue_sharing_enabled` feature has not activated.

`update_commission_collector`, the function responsible for changing where BlockRevenue commission funds are routed (`vote_state.set_block_revenue_collector(...)`), performs authorized-withdrawer signature verification and collector-account validation (SIMD-0232), but never checks `block_revenue_sharing_enabled` before writing to `block_revenue_collector`: [2](#0-1) 

The function signature does not even accept a `block_revenue_sharing_enabled` parameter, unlike `update_commission_bps`, confirming the check was never wired into this code path — a direct analog to the `sellForLP` function in the external report lacking the `isCrossChainAllowed` modifier that its sibling functions in the same contract enforce.

I was unable to verify, within the available tool budget, whether `programs/vote/src/vote_processor.rs` re-applies this feature gate at the instruction-dispatch layer before calling `update_commission_collector`. If the processor does not re-check `block_revenue_sharing_enabled` before invoking this function, the collector field can be set pre-activation.

### Impact Explanation
If the gate is indeed absent end-to-end, an authorized withdrawer could set `block_revenue_collector` on a vote account before SIMD-0123 activates cluster-wide. Depending on how downstream fee/reward distribution logic (e.g., `runtime/src/bank/fee_distribution.rs`) reads this field relative to the feature-set snapshot, this could produce validator-to-validator inconsistency in stored vote-account state versus what feature-gated distribution logic expects, which is the exact kind of divergence class (inconsistent account state depending on feature-activation timing) that can lead to state/consensus divergence across the fleet. This falls short of a full unprivileged exploit and requires further confirmation of the processor-layer call path.

### Likelihood Explanation
Low-to-moderate confidence: the asymmetry between the two sibling functions is confirmed directly in code, but the ultimate exploitability depends on whether `vote_processor.rs` independently re-implements the same feature check before dispatching to `update_commission_collector` — a detail this investigation could not confirm due to tool-call limits.

### Recommendation
Add the same `block_revenue_sharing_enabled` gate used in `update_commission_bps` to `update_commission_collector` for the `CommissionKind::BlockRevenue` case, and verify/add a corresponding check at the `vote_processor.rs` instruction-dispatch layer, mirroring the fix pattern of adding the missing modifier consistently across sibling functions operating on the same protected resource.

If the background agent (or a Devin session with full repo access) confirms `vote_processor.rs` does not independently enforce `block_revenue_sharing_enabled` before calling `update_commission_collector`, this becomes a confirmed missing-check vulnerability directly analogous to the reported `sellForLP`/`isCrossChainAllowed` issue.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
