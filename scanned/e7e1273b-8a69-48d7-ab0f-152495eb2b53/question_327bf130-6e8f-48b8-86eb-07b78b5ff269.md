[Scope: High.] Target: `SPV::verify`'s ordering of checks (merkle-root check before MMR check). Attacker action: submit a `BridgeCircuitInput.payout_spv` where `block_inclusion_proof` is valid against SOME `block_header.merkle_root` value the attacker fabricates wholesale (not from any real block), and craft `mmr_inclusion_proof`/`subroot_idx` to also validate against the guest's real MMR by choosing `block_header` fields such that `compute_block_hash()` happens to equal a genuinely committed hash the attacker independently mines/grinds off-protocol (e.g., an actual but irrelevant historical block hash reused). Call sequence: `bridge_circuit` never asserts that `payout_spv.block_header` is one of the headers actually verified inside `hcp`'s header-chain proof besides checking its resulting `compute_block_hash()` is present as an MMR leaf; if MMR leaves are appended purely from `hcp.chain_state.block_hashes_mmr`, then binding is only as strong as the height/leaf/proof triple matching, so this reduces to the mmr_inclusion_proof `subroot_idx`/`internal_idx` forgery cases above (Critical) rather than a wholly separate path. Scope/impact recorded as High: this ordering-and-decoupling design pattern deserves an explicit invariant test that `payout_spv.block_header` cannot be swapped for an unrelated header sharing the same computed hash accepted by the MMR without the merkle_root/tx pairing also being genuine.
