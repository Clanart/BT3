target: Operator::withdraw and its reuse of the same in_signature across fund_raw_transaction's add_inputs. Attacker action: attacker submits in_signature with sighash_type = SIGHASH_ALL|ANYONECANPAY over an initial two-output payout_txhandler (payout output + implicit change), where the real operator inputs to be added by fund_raw_transaction don't exist yet. Preconditions: ANYONECANPAY only commits to input 0 (the user's in_outpoint), ALL commits to all outputs present at signing time. Call sequence: calculate_sighash_txin(0, ALL|ANYONECANPAY) is computed and verified before fund_raw_transaction runs; fund_raw_transaction then calls add_inputs:true, change_position:1, which can insert a new output as the wallet's change ahead of/around the committed outputs, changing the output set the signature already committed to under SIGHASH_ALL. Binding that breaks: the sighash type verified against the user's key == a flag that commits the payout output the operator is reimbursed for; if fund_raw_transaction's output insertion shifts committed outputs, the signature becomes invalid for the final broadcast set, causing sign_raw_transaction_with_wallet to either fail (leaving the withdrawal stuck) or the wallet to reorder outputs such that operator reimbursement in a later Reimburse tx is computed against a moved output. Impact: Critical - an honest operator that funded a payout could become unable to be reimbursed if the mismatch between pre-funding SIGHASH_ALL commitment and post-funding output set makes the tx permanently unsignable, or the vault-side accounting keys off a different output than the one paid.
