### Title
Banlist::ban unconditionally overwrites an existing longer ban with a shorter one, allowing attacker to self-shorten bans - (File: net-utils/src/banlist.rs)

### Summary
`Banlist::ban` always overwrites the stored expiry for a key with the newly computed `expires_at`, regardless of whether the existing ban expiry is later than the new one. An attacker who is already banned for a long duration can trigger any code path that calls `ban(id, short_timeout)` for that same identity (e.g. a lower-severity QUIC/TPU infraction) to have their existing long ban replaced by a much shorter one, letting the ban lapse early.

### Finding Description

The `insert` call is unconditional — it does not compare the new `expires_at` to any previously stored value and take the maximum. The only safety net is a `debug_assert!(prev < Some(expires_at))` which is compiled out in release builds, so in production this ordering is never enforced. `is_banned()` and `prune()` both operate purely on the value currently stored in the map, so once the shorter expiry is written, the entity is treated as unbanned as soon as that shorter timeout elapses, irrespective of the original longer ban that was intended.

The `Banlist` type is used by the QUIC/streamer connection-handling code as an anti-abuse mechanism (`streamer/src/quic.rs`, `streamer/src/nonblocking/simple_qos.rs`) to temporarily block peers exhibiting bad behavior on the QUIC/TPU ingest path. Because different violation types can carry different ban durations (e.g. a long ban for a serious protocol violation vs. a short ban for a minor rate infraction), a peer that is already serving a long ban can trigger a separate, lower-severity condition against the same identity/connection key to have that entry's `insert` overwrite the long expiry with a short one.

### Impact Explanation
This defeats the intended throttling/anti-abuse protection on the QUIC/TPU path: an attacker can artificially shorten a long ban by intentionally committing a distinct, low-severity infraction, resuming abusive traffic much earlier than intended. Because bans in this subsystem exist specifically to protect the QUIC/TPU ingestion path from resource exhaustion by misbehaving unprivileged peers, undermining their duration weakens that protection and could contribute to sustained remote exhaustion/degradation on that path.

### Likelihood Explanation
Exploitability depends entirely on whether any caller can invoke `ban()` a second time for the same key with a shorter timeout while the first (longer) ban is still active — i.e., whether the calling code (in `streamer/src/quic.rs` / `simple_qos.rs`) maps distinct violation types to distinct ban durations for the same banned key. I was not able to fully confirm, within the available context, that a caller ever issues two different-duration bans against the identical key concurrently in this codebase's current usage; the `Banlist` struct itself has no protection against it, and the `debug_assert!` at line 26 signals the original authors intended `expires_at` to always increase, confirming the invariant is expected but not enforced in release builds.

### Recommendation
Change `ban()` to only update the stored expiry if the new `expires_at` is later than any existing one, e.g.:
```rust
self.banned
    .write()
    .unwrap()
    .entry(id)
    .and_modify(|e| *e = (*e).max(expires_at))
    .or_insert(expires_at);
```
and remove or replace the release-mode-ineffective `debug_assert!` with this real runtime enforcement.

### Proof of Concept
```rust
#[test]
fn test_ban_shortening_bug() {
    let banlist = Banlist::<String>::default();
    banlist.ban("peer".to_string(), Duration::from_secs(600)); // long ban
    banlist.ban("peer".to_string(), Duration::from_secs(1));   // second, shorter ban overwrites
    std::thread::sleep(Duration::from_secs(2));
    assert!(!banlist.is_banned("peer")); // ban lapsed despite original 600s duration
}

    pub fn ban(&self, id: T, timeout: Duration) -> bool {
