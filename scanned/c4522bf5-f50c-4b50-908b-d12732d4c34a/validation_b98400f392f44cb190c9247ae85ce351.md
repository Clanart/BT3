### Title
`block_revenue_commission_bps` changes bypass the delayed-commission protection applied to inflation-rewards commission - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
Agave introduced `UpdateCommissionBps` (SIMD-0291) allowing a validator's withdraw authority to change either the `InflationRewards` or `BlockRevenue` commission at any time, with no epoch-timing restriction [1](#0-0) . For the `InflationRewards` commission kind, the runtime explicitly mitigates "last minute commission rug" risk by using a cached, one-epoch-delayed vote-account snapshot (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) instead of the live commission value when computing `commission_bps` for stake rewards [2](#0-1) . However, `calculate_block_reward` — which computes the block-revenue-sharing payout for the same delegation — is invoked with `cached_vote_accounts.distribution_epoch_vote_accounts` directly, i.e. the vote account state at the *end* of the rewarded epoch / start of distribution, rather than the delayed snapshot used for inflation commission [3](#0-2) .

### Finding Description
This mirrors the Thruster `setYieldCut` finding precisely: a "yield cut"-like parameter (`block_revenue_commission_bps`) accrues value over an entire period (the epoch) under one rate, but the protocol applies whatever rate is in the vote account *at the moment fees/rewards are collected*, rather than settling/minting under the rate that was in effect while the value was accruing. Solana's own commit history/comments show this exact class of bug was intentionally fixed for `InflationRewards` commission via the "delay commission updates" (SIMD-0249) mechanism and the `CachedVoteAccounts` snapshot layering [4](#0-3) . The `BlockRevenue` commission kind was added later (SIMD-0123/SIMD-0291) and its instruction path explicitly documents "No commission update rule, per SIMD-0249 and SIMD-0291" — i.e., a deliberate design decision to *not* apply any timing gate to commission_bps changes [5](#0-4) . Combined with `calculate_block_reward` reading commission from `distribution_epoch_vote_accounts` (not the delayed snapshot), a validator operator can raise (or lower) `block_revenue_commission_bps` at any point during — or right at the end of — an epoch and have that new rate applied retroactively to the entire epoch's already-accrued block revenue for every delegated stake account, exactly the "wrong proportion of yield collected" scenario described in the source report.

I could not fully verify the internal body of `calculate_block_reward` (only its call-site signature was retrievable in the time available), so I cannot state with certainty whether it internally re-fetches a delayed commission value from elsewhere. This is the key open question that would need to be checked in the actual file at `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`.

### Impact Explanation
If confirmed, a validator operator could unilaterally and instantly redirect a larger (or smaller) share of already-accrued block revenue between themselves and their delegators by changing `block_revenue_commission_bps` shortly before epoch-boundary reward calculation — a "commission sandwich" that misallocates real SOL value away from delegators to the operator (or vice versa), without any of the one-epoch delay protections that exist for the analogous `InflationRewards` commission. This is a fund-misallocation issue affecting delegators' stake rewards.

### Likelihood Explanation
Likelihood depends entirely on whether `calculate_block_reward` uses the live/current commission (as the call-site evidence suggests) versus a delayed snapshot. If it uses live commission, the attack requires no special privileges beyond being the validator's own withdraw authority — a normal, low-cost, high-frequency action available to every validator operator — making it easily and repeatedly exploitable each epoch.

### Recommendation
Confirm the internal implementation of `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`. If it reads live `block_revenue_commission_bps` from `distribution_epoch_vote_accounts`, apply the same delayed-snapshot approach already used for `InflationRewards` commission (`snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` via `CachedVoteAccounts`) to the `BlockRevenue` commission kind as well, ensuring block-revenue commission changes only take effect starting the next full epoch's accrual, consistent with the SIMD-0249 rationale already applied elsewhere in the codebase.

### Proof of Concept
Not independently confirmed with a running reproduction due to inability to view the full body of `calculate_block_reward` in this session. A concrete PoC would: (1) delegate stake to a vote account with a low `block_revenue_commission_bps`; (2) accrue block revenue over most of an epoch; (3) call `UpdateCommissionBps { kind: CommissionKind::BlockRevenue, commission_bps: <max> }` near epoch end (allowed with no timing check, per `update_commission_bps` at [6](#0-5) ); (4) observe whether the higher commission is applied to the entire epoch's block reward at distribution rather than only revenue accrued after the change — this last step is the part requiring verification against `calculate_block_reward`'s actual body.

pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
