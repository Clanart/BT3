### Title
Non-unique `(withdrawal_utxo_txid, withdrawal_utxo_vout)` join in `get_payout_txs_for_withdrawal_utxos` lets a colliding second withdrawal be falsely marked as paid by the operator who only funded the first - ([File: core/src/database/verifier.rs])

### Summary
`get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` strictly on `(txid, vout)` with no guarantee that at most one `idx` maps to a given physical outpoint. If two different Citrea withdrawal indices are ever recorded with the identical `withdrawal_utxo_txid`/`withdrawal_utxo_vout`, the single Bitcoin spend event for that UTXO produces two joined rows, and `update_payout_txs_and_payer_operator_xonly_pk` then writes the same `payout_payer_operator_xonly_pk`/`payout_txid` into both `withdrawals` rows.

### Finding Description
The intended binding is: **for each withdrawal index `idx`, the operator credited as `payout_payer_operator_xonly_pk` must be the party whose transaction actually paid that specific withdrawal's recipient, and each physically-spent withdrawal UTXO must resolve to exactly one `idx`.**

The join implementing this binding is: [1](#0-0) 

This is a plain equality join on `(txid, vout)` with no `DISTINCT ON` per spent-UTXO and no uniqueness enforced on `withdrawals.(withdrawal_utxo_txid, withdrawal_utxo_vout)`. The value is written per-`idx` by a simple `UPDATE ... WHERE idx = $1` with no cross-row check: [2](#0-1) 

Because the withdrawal UTXO bytes are attacker-chosen dust the attacker controls (per the question's threat model), the attacker can submit two separate Citrea `withdraw()` calls (`d1`, `d2`) that both reference the identical outpoint before either is actually spent on Bitcoin. When the operator later broadcasts one honest payout transaction that spends that single physical UTXO to settle `d1`, `bitcoin_syncer_spent_utxos` records one spend row for that outpoint. The join in `get_payout_txs_for_withdrawal_utxos` matches that one spend row against *both* `withdrawals` rows (`d1` and `d2`), returning `[(d1, spending_txid), (d2, spending_txid)]`. This result is then fed into `update_payout_txs_and_payer_operator_xonly_pk`, which performs a batched `UPDATE ... FROM (values...)` keyed only by `idx`, writing the same `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` into both rows: [3](#0-2) 

None of the listed guards (`is_deposit_valid`, `verify_storage_proofs`, `SPV::verify`, presigned tx graph, etc.) validate that a withdrawal UTXO outpoint is unique across different deposit indices — they validate deposit/move-to-vault UTXOs and Citrea storage proofs, not cross-withdrawal outpoint collisions. There is also no DB-level `UNIQUE` constraint demonstrated on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` in the schema, and `update_withdrawal_utxo_from_citrea_withdrawal` performs an unconditional per-idx `UPDATE` that would silently accept the duplicate value.

### Impact Explanation
Once `d2` is (falsely) marked `payout_txid`/`payout_payer_operator_xonly_pk` identical to `d1`, downstream reimbursement logic (`get_first_unhandled_payout_by_operator_xonly_pk`, `mark_payout_handled`) operates per-`idx`, independent of the underlying `payout_txid`. This lets the credited operator drive `d2`'s own presigned kickoff/reimbursement path and be reimbursed from `d2`'s move-to-vault collateral even though the operator's Bitcoin transaction never paid `d2`'s intended recipient — an "operator reimbursed for a payout it never funded," matching the Critical category. The bug is repeatable per attacker across any number of self-issued withdrawals sharing a UTXO outpoint, and is not scoped to a single deposit or operator.

### Likelihood Explanation
I could not confirm from the available index whether a database uniqueness constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)` exists in `schema.sql`, nor could I read the full body of `Verifier::update_finalized_payouts` in `core/src/verifier.rs` to see whether it deduplicates the vector returned by `get_payout_txs_for_withdrawal_utxos` before calling `update_payout_txs_and_payer_operator_xonly_pk`, due to running out of investigation budget. This materially affects likelihood: if a unique constraint or a dedup-by-`spending_txid` step exists upstream, the exploit is blocked. Based on the code actually inspected, no such guard is present in the query layer itself.

### Recommendation
Enforce uniqueness of `(withdrawal_utxo_txid, withdrawal_utxo_vout)` across `withdrawals` (reject/ignore a second withdrawal registration reusing an already-registered outpoint), and/or change `get_payout_txs_for_withdrawal_utxos` to select `DISTINCT ON (bsu.txid, bsu.vout)` ordered deterministically (e.g., lowest `idx`) so a single physical spend can only ever be attributed to one withdrawal index.

### Proof of Concept
In `core/src/database/verifier.rs` test module, extend `update_get_payout_txs_from_citrea_withdrawal`-style test:
1. Insert two `withdrawals` rows via `upsert_move_to_vault_txid_from_citrea_deposit` + `update_withdrawal_utxo_from_citrea_withdrawal` for `idx = d1` and `idx = d2`, both bound to the same `OutPoint { txid, vout }`.
2. Call `insert_spent_utxo` once for that `(txid, vout)` under one `block_id`.
3. Call `get_payout_txs_for_withdrawal_utxos(block_id)` and assert `results.len() == 1` (expected/fixed behavior) — the current implementation will return `2` rows both carrying the same `spending_txid`, proving the collision.
4. Call `update_payout_txs_and_payer_operator_xonly_pk` with both rows and assert only one of `d1`/`d2` ends up with `payout_payer_operator_xonly_pk` set — currently both will be set identically.

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
