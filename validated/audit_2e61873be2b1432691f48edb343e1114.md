### Title
Desktop silently rewrites the trusted `origin` remote URL from an unverified GitHub API `clone_url` value - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Uniswap report's broken invariant is: a protocol trusts an easily-manipulated "current" value (spot price) instead of a validated/committed value, and uses it to silently move funds. The structural analog in GitHub Desktop is `updateRemoteUrl()` in [1](#0-0) , which reads the `clone_url` field of a `GitHubRepository` object returned by the GitHub API — an attacker-influenceable "current" value — and, if a set of loose heuristic checks pass, silently overwrites the user's local `origin` remote URL with it, without any user confirmation. This mutates the "trusted invariant" of where the user's future pushes/fetches go, based purely on API-supplied data.

### Finding Description
`updateRemoteUrl` compares the existing `origin` remote URL to `apiRepo.clone_url` using `urlMatchesRemote`, which only compares parsed `hostname`, `owner`, and `name` case-insensitively [2](#0-1) . It also checks that the URL protocol hasn't changed, and that the remote currently matches the GitHubRepository's previously stored `cloneURL` (i.e. the remote hasn't been manually customized) [3](#0-2) . If all these pass, it calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` — silently rewriting the origin remote to whatever `clone_url` the API returned [4](#0-3) .

None of these guards validate that the new URL still points at the *same underlying repository object* the user originally added — they only validate `owner/name` string equality extracted from the URL. This is exactly analogous to the Uniswap bug: instead of anchoring to a trusted/validated reference point (a TWAP, or here, the actual GitHub repository identity/ID), the code trusts a single "current" API response value (`clone_url`) and propagates it directly into a security-relevant sink (the git remote configuration that all future `git push`/`git fetch` operations rely on).

The realistic attacker primitive is repository-name squatting: if the tracked repository is renamed/transferred/deleted upstream and its `owner/name` slug becomes available again, an attacker can create a new repository at that same `owner/name`. The next background repository refresh (which fetches `apiRepo` for the tracked `GitHubRepository`) can return the attacker's repository's `clone_url`, `owner`/`name` matching the stale local remote well enough to satisfy `urlMatchesRemote`, and the code will auto-rewrite `origin` to the attacker's clone URL with zero user interaction or confirmation dialog.

### Impact Explanation
If `origin` is silently repointed to an attacker-controlled remote, all future `git push` operations from the user (including credentials sent via the git credential helper / stored PAT for that host) are sent to the attacker's repository instead of the intended one. This is a "silent corruption of what the user pushes" scenario explicitly called out as valid impact: commits, potentially including proprietary code, could be pushed to an attacker's repository, and subsequent `git fetch`/`pull` would pull attacker-supplied history into the user's working tree without any explicit re-add-remote action by the user.

### Likelihood Explanation
The precondition (a repository the user tracks losing its original name via deletion/rename, freeing up the `owner/name` slug for squatting) does occur in the real world and has been used in supply-chain/dependency-confusion-style attacks against other tools that resolve packages/repos by name. The check only requires that the local remote wasn't manually edited and that protocol matches, both of which are the default/common state for the vast majority of Desktop users who never touch remote settings manually. No local access, malware, or credential leak is required — only that a background sync picks up attacker-controlled repository metadata for a name the user's Desktop already tracks.

### Recommendation
Do not silently rewrite `origin` based solely on `clone_url` string matching. Either:
1. Never auto-update the remote URL without explicit user confirmation (show a prompt: "This repository's remote URL has changed to X, update?"), or
2. Validate repository identity via the stable numeric GitHub repository `id`/`node_id` (fetched and cached at the time the user originally added/cloned the repo) rather than by name-based string comparison, refusing to auto-update if the underlying repository ID differs from what was previously recorded.

### Proof of Concept
1. User adds/clones `https://github.com/victim-org/some-repo` in Desktop; Desktop stores the associated `GitHubRepository` (with `cloneURL` = that URL) and origin remote pointing at it.
2. `victim-org` renames or deletes `some-repo` (or the org is deleted/renamed), freeing the `victim-org/some-repo` slug.
3. Attacker creates a new repository at `victim-org/some-repo` (if the org allows public creation, or more realistically the case where the original repo's *owner user* renames their account, freeing a name an attacker registers) and sets it up as intended target.
4. Desktop's periodic repository refresh calls the API for the tracked `GitHubRepository`, receiving `apiRepo.clone_url` pointing at the attacker's new repository (protocol unchanged, owner/name string-matching the stale local remote).
5. `updateRemoteUrl` at [4](#0-3)  silently calls `gitStore.setRemoteURL`, rewriting `origin` to the attacker's clone URL with no prompt.
6. Next time the user pushes, their commits go to the attacker-controlled repository.

Note: I could not confirm within the available context the exact caller/trigger path that invokes `updateRemoteUrl` during a background refresh (I found the function itself and its call from `app-store.ts`'s upstream-remote-handling code paths, but did not trace the precise scheduling/frequency of the refresh that supplies `apiRepo`). This should be verified against `app-store.ts` refresh-GitHub-repository logic to confirm how often/where this runs automatically versus only after explicit user action.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
