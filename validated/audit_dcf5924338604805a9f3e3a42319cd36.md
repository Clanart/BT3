### Title
Unchecked `u64` arithmetic on attacker-influenced amounts lets the fee/funds checks in `SignableTransaction::new` be bypassed via wrap-around, producing signatures over unintended transactions - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--016/blob/master/networks/bitcoin/src/wallet/send.rs))

### Summary
The libX11 bug class is "integer overflow in size math → undersized allocation → heap corruption." Serai is memory-safe Rust, so heap corruption is not reachable; the reachable analog is *integer overflow in value math → bypassed safety check → an object the caller never intended gets produced and signed*. `SignableTransaction::new` performs plain `u64` addition and multiplication on input sums, payment sums, and `fee_per_vbyte * vbytes` — none of which are `checked_`, `saturating_`, or otherwise guarded — before deciding whether the transaction is funded and sufficiently priced.

### Finding Description
In `SignableTransaction::new`:

- `input_sat` and `payment_sat` are computed with `sum::<u64>()`, which wraps on overflow in release builds (`send.rs:175`, `send.rs:187`).
- `needed_fee = fee_per_vbyte * vbytes` is an unchecked product (`send.rs:206`), and likewise `fee_with_change = fee_per_vbyte * vbytes_with_change` (`send.rs:227`).
- The solvency check `input_sat < (payment_sat + needed_fee)` uses an unchecked add (`send.rs:215`).

An attacker-influenced `fee_per_vbyte` or set of `(ScriptBuf, u64)` payments (both arrive as parameters to `new`, i.e. plan/withdrawal-request data, not values validated against on-chain amounts) can make these expressions wrap:

1. `fee_per_vbyte * vbytes` wraps to a value that is simultaneously `>= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (passing `TooLowFee`) yet far smaller than the honest fee. The change branch then uses `input_sat.checked_sub(payment_sat + fee_with_change)` (`send.rs:228`); with a wrapped-small `fee_with_change`, a change output is created and the *actual* paid fee — `sum(inputs) - sum(outputs)`, per `fee()` at `send.rs:138` — collapses to the wrapped value. The resulting transaction is signed via `Prevouts::All` in `TransactionSignMachine::sign` (`send.rs:373-397`) and broadcastable, but sits below relay/effective fee requirements indefinitely — funds committed to the outputs are not recoverable by the normal signing flow (the signable form does not support re-signing the same plan with a different fee without coordination).

2. `payment_sat` itself wraps to a small value, so `input_sat < payment_sat + needed_fee` evaluates false and `NotEnoughFunds` is bypassed even though the serialized `tx_outs` carry the real, huge `Amount::from_sat(payment.1)` values. The multisig then produces a signature for a transaction whose outputs exceed its inputs / `MAX_MONEY` — a signed transaction that can never be mined, and that was never sanctioned by the checks.

`calculate_weight_vbytes` also feeds `payments` into `tx.weight()` (`send.rs:85-99`), but the wrap candidates are the three arithmetic sites above, which gate `NotEnoughFunds` and `TooLowFee`.

### Impact Explanation
The checks at `send.rs:211-221` are the only things preventing the threshold group from signing transactions that are underfunded, underpriced, or structurally invalid. Wrapping them produces one of two concrete harms within the accepted impact list:

- **Signing of an unintended message**: the group signs a transaction paying outputs totaling more than was authorized (wrap of `payment_sat`) or paying a fee orders of magnitude away from the intended `fee_per_vbyte * vbytes`.
- **Funds reported sent that are not spendable**: a validly-signed transaction with a negligible effective fee cannot be relayed or mined; the input UTXOs are effectively locked pending a new, mutually-agreed plan. With a wrapped-large `fee_with_change` the opposite occurs — `checked_sub` yields a small change output and the remainder of `input_sat` is burned as fee, i.e. funds are destroyed rather than sent.

This is the direct Serai analogue of XCreateImage: arithmetic on inputs the protocol treats as trusted dimensions overflows and the downstream guard (`input_sat < payment_sat + needed_fee`) is evaluated on the wrapped value, admitting a malformed object into the signing pipeline.

### Likelihood Explanation
Severity: Medium. Exploitability depends on the caller supplying adversarial `payments`/`fee_per_vbyte`; in Serai's deployment these originate from withdrawal plans and fee estimates, so an unprivileged party who can influence a plan's payment amounts or the selected fee rate reaches the code. The payment-amount overflow requires amounts exceeding `MAX_MONEY`, which is only useful as a DoS/unintended-signature path; the `fee_per_vbyte * vbytes` wrap is the more realistic path since a single large multiplier overflows `u64` at ~`2^64 / vbytes` sat/vbyte. No cryptographic assumption is broken — it is a pure arithmetic-safety failure, matching the "integer overflow" class rather than a signature forgery.

### Recommendation
Replace all `u64` sum/product/add sites in `SignableTransaction::new` with checked arithmetic and surface a dedicated `TransactionError` on overflow:

- `inputs.iter().map(|i| i.output.value.to_sat()).try_fold(0u64, u64::checked_add)`
- `payments.iter().map(|p| p.1).try_fold(0u64, u64::checked_add)`
- `fee_per_vbyte.checked_mul(vbytes)` / `checked_mul(vbytes_with_change)`
- `payment_sat.checked_add(needed_fee)` in the `NotEnoughFunds` comparison

Also bound payment amounts to `bitcoin::Amount::MAX_MONEY` (`21_000_000 * 100_000_000` sats) at parse time so that any wrap requires economically impossible outputs and is rejected early.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs — conceptual PoC
// Requires: a caller that forwards attacker-chosen fee_per_vbyte / payments
// into SignableTransaction::new (e.g. a withdrawal plan).

// Path A: wrapped fee multiplication bypasses TooLowFee.
// vbytes for a 1-in/1-out+change P2TR tx ~ 150-200 vB.
let fee_per_vbyte: u64 = u64::MAX / 150 + 1; // any multiplier that wraps
// true needed_fee = fee_per_vbyte * vbytes overflows u64 and wraps
// to a value >= (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000 but << intended.
// TooLowFee check passes; change branch uses the wrapped fee_with_change.
// Actual fee paid = input_sat - payment_sat - change ≈ wrapped value
// → signed tx has a negligible fee and can never confirm.

// Path B: wrapped payment sum bypasses NotEnoughFunds.
let payments = vec![
    (script_a, u64::MAX - 1_000), // each >= DUST, so DustPayment check passes
    (script_b, 5_000),            // payment_sat wraps to ~3,999
];
// input_sat (e.g. 100_000) < payment_sat + needed_fee evaluates with the
// wrapped payment_sat (~4k) instead of the real sum (~u64::MAX), so
// NotEnoughFunds is NOT raised.
// TransactionSignMachine::sign then produces a valid FROST signature over a
// transaction whose declared outputs (~2^64 sats) vastly exceed its inputs —
// an unintended, unmineable signature.
```
