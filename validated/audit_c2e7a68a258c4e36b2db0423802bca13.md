### Title
Copilot conflict reassembly matches hunk resolutions to conflict blocks by position, not by content, so a file edited or re-conflicted between hunk extraction and splicing silently corrupts the committed merge result - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`reassembleResolvedFile` splices per-hunk LLM resolutions into the on-disk conflicted file purely by ordinal position (`hunkIndex`), matching them against whichever `<<<<<<<`/`=======`/`>>>>>>>` blocks it finds when it walks `rawContent` at splice time. There is no check that this `rawContent` is the same content the hunks were extracted/prompted from. If the number, order, or identity of conflict blocks in the file changes between the time `IFileConflictContext.hunks` were captured and the time `reassembleResolutions` is invoked (e.g. the user manually edits the file, another conflict resolution pass runs, or the working tree is refreshed and produces a different `rawContent` for the same path), resolution *N* for one conflict gets written into the position of a different, unrelated conflict. [1](#0-0) [2](#0-1) 

### Finding Description
This is a structural analog of the reported bug class: a value assumed to stay invariant between "creation" (hunk generation from a snapshot of the conflicted file) and "use" (splicing at commit time) is not re-validated, and the code proceeds on the stale assumption, corrupting the final artifact.

- `IRawFileResolution.hunks` is an *ordered* array with "one entry per conflict in the file, matching the 'Conflict 1 of N', 'Conflict 2 of N' order from the input," per the system prompt contract itself: [3](#0-2) 
- `validateResolutionPaths` only checks that the *count* of hunks returned by the model matches the *count* of hunks in the file context gathered earlier — it does not verify the file's current on-disk content still contains the same conflict blocks: [4](#0-3) 
- `reassembleResolvedFile` then walks `rawContent` (`ctx.rawContent`, taken from the file context) and blindly assigns `hunkResolutions[hunkIndex]` to whichever conflict block it encounters next, with `hunkIndex` incrementing regardless of what that block actually contains: [5](#0-4) 
- The function's own doc comment concedes the matching is "by order, not by line number" — i.e., purely positional, with no content-hash or checksum tie-back to the specific conflict hunk that was sent to the model: [6](#0-5) 

The broken invariant: "the on-disk file at splice time has the exact same sequence of conflict blocks, in the same order, as when the hunks were extracted and sent to Copilot" is never re-checked. The `IFileConflictContext.rawContent` is captured once; nothing forces `reassembleResolutions` to be called against a file that hasn't changed since. If the file is touched in between (a plausible flow given the changelog explicitly documents users being able to "remove the conflict markers themselves before clicking Continue" and Desktop having to reconcile that: [7](#0-6) ), or if the async multi-chunk pipeline (`createDependencyAwareChunks`, `SinglePromptFileLimit`, `MaxConcurrentChunks`) causes a resolution for a stale snapshot to be applied after the working tree already changed, the mapping-by-position degenerates: resolution content generated for "conflict 2" of the original file gets written into whatever is now positionally "conflict 2" — potentially an unrelated hunk, or a conflict the user already hand-resolved and that reappeared via a different merge path.

Existing guards don't stop this:
- `validateResolutionPaths` verifies hunk *count* equality only, not identity/content of each hunk: [8](#0-7) 
- The conflict-marker regex check in `parseCopilotConflictResolution` only rejects resolutions that themselves still contain literal marker syntax, not resolutions that no longer correspond to the intended conflict: [9](#0-8) 
- The malformed-marker fallback in `reassembleResolvedFile` only guards against missing `=======`/`>>>>>>>`, not against a well-formed but *different* conflict occupying that position: [10](#0-9) 

### Impact Explanation
If exploited (e.g. an attacker-controlled repository/branch is crafted so that a merge/rebase/cherry-pick produces conflicts whose block count is attacker-influenced, or timing causes the file to be re-conflicted between context capture and splice), the result is silent corruption of what the user commits: the reassembled file can contain a plausible-looking, syntactically valid merge that actually mixes unrelated resolved content into the wrong conflict region. This matches the "silent corruption of what the user commits or pushes" impact category — the user sees the Copilot summary/reasoning as trustworthy, accepts the resolution, and commits/pushes incorrect code without any warning, since the app has no mechanism to detect a position/content mismatch.

### Likelihood Explanation
This requires no local/physical access or credentials — only that Desktop's Copilot conflict-resolution feature operates on a repository whose merge state can shift between context capture and application (a normal condition in interactive, potentially multi-chunk, async LLM-backed flows, and explicitly acknowledged as a real scenario in the product's own changelog entry about markers being removed before "Continue" is clicked). I could not fully trace, within available context, the exact caller that guarantees (or fails to guarantee) that `ctx.rawContent` used in `reassembleResolutions` is re-read immediately before splicing versus cached from an earlier point in the async pipeline — this is the key remaining uncertainty and would need to be confirmed by reading the calling code (likely in the Copilot store/dialog flow) that isn't included in the retrieved context.

### Recommendation
Bind each `IHunkResolution` to a content fingerprint (e.g., a hash of the specific conflict block's `oursContent`/`theirsContent`/`baseContent`) captured alongside `IFileConflictContext.hunks`, and have `reassembleResolvedFile` verify that fingerprint against the block it's about to replace before splicing, rejecting/falling back to manual resolution on mismatch instead of assuming positional order still holds. Additionally, re-fetch and diff `rawContent` immediately before reassembly against the snapshot used to build the prompt, refusing to apply resolutions if the file changed in the interim.

### Proof of Concept
Conceptual sequence (exact trigger path not fully confirmed from available code):
1. Desktop gathers `IFileConflictContext` for `file.ts` with two conflicts (A, B) and sends both hunks to Copilot for resolution.
2. Before the response is applied, the working copy of `file.ts` changes such that conflict A is manually resolved by the user but a new conflict C appears earlier in the file (e.g., from a follow-up fetch/rebase step in the same operation).
3. `reassembleResolutions` is called with the stale `rawHunks` (resolutions for original A, B) against the new `ctx.rawContent`, which now has conflicts C and B in that order.
4. `reassembleResolvedFile` walks the new file, finds conflict C first, and splices in the resolution intended for original conflict A (`hunkIndex === 0`) — content that has nothing to do with conflict C. [11](#0-10) 
5. The write path commits this file as if fully and correctly resolved, with no error or diff surfaced to the user, since `validateResolutionPaths` already passed on hunk-count equality alone.

```typescript
export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
```
