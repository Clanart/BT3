Based on my investigation, I found that the `NativeSeiTokensERC20.sol` contract exhibits the exact same bug pattern as the Portfolio.sol report: a decimals mismatch where a token amount is used without unit conversion between the ERC20/EVM WAD-scale (wei, 18 decimals implied) and the underlying native `usei` scale.

### Title
ERC20 wrapper for native Sei tokens exposes raw `usei` units as if they were 18-decimal wei, causing under/overpayment via `send`/`transfer` amount mismatch - (File: contracts/src/NativeSeiTokensERC20.sol)

### Summary
`NativeSeiTokensERC20` is a Solidity ERC20 wrapper deployed as the EVM-facing pointer for native Sei bank denoms (e.g. `usei`). Its `balanceOf`, `totalSupply`, and `_update` (transfer/transferFrom) all pass the raw amount straight through to the `IBank` precompile's `balance`/`supply`/`send` functions, which operate in the bank module's native integer units (e.g. micro-denom `usei`, 0 decimals per the bank precompile's `decimals()`), while `decimals()` on the ERC20 wrapper is set arbitrarily via the constructor argument `decimals_`.

### Finding Description
In `NativeSeiTokensERC20.sol`, `balanceOf`, `totalSupply`, and `_update` (used by `transfer`/`transferFrom`) call the `IBank` precompile directly with the caller-supplied `value`/`amount`, with no scaling applied: [1](#0-0) 

`decimals()` simply returns the constructor-provided `ddecimals` value, which is independent of the bank precompile's own `decimals()` (hard-coded to `0` for all native denoms, since native tokens are integer/micro-denom based): [2](#0-1) 

Any EVM contract or off-chain tool that treats `NativeSeiTokensERC20` as a standard ERC20 (i.e., assumes `amount` is denominated according to `decimals()`, and multiplies/divides human-readable quantities by `10**decimals()` before calling `transfer`/`approve`/reading `balanceOf`) will compute amounts in the wrong base. If `ddecimals` is set to a nonzero value (e.g. 6 or 18, as commonly expected for ERC20 tokens) while the underlying bank balance is denominated in raw integer `usei` units, any caller that scales a human amount by `10**decimals()` will send/receive an amount that is off by many orders of magnitude from what they intended, exactly analogous to the Portfolio.sol `useMax` bug where a token-decimals amount was fed into logic expecting WAD units.

### Impact Explanation
Because there is no reconciliation between the wrapper's advertised `decimals()` and the actual base unit the underlying `IBank.send`/`balance` calls operate on, integrations built against `NativeSeiTokensERC20` (bridges, DeFi contracts, aggregators) that trust `decimals()` to convert between human-readable and raw amounts will transfer amounts vastly different from what was intended — either sending far more than intended (draining a contract) or far less (locking/losing intended value) once tokens remain stuck in a contract due to a mismatched sub-amount, mirroring the "user loss because tokens remain in contract" impact described in the report.

### Likelihood Explanation
Any user or contract can deploy or interact with `NativeSeiTokensERC20` (or an equivalent pointer instance already deployed for a native denom) via a normal EVM transaction; no special privilege is required. Because the constructor decimal value is attacker/deployer-controlled and independent of the actual precompile semantics, exploitation only requires deploying a wrapper with a decimals value that diverges from callers' expectations, or normal usage by any client that reasonably assumes ERC20 semantics.

### Recommendation
Scale amounts passed to and from the `IBank` precompile by the difference between the wrapper's `decimals()` and the bank precompile's native decimals (`0`), consistently across `balanceOf`, `totalSupply`, and `_update`. Add tests exercising nonzero `decimals_` values to confirm `transfer`/`balanceOf` behave correctly under scaling.

### Proof of Concept
1. Deploy `NativeSeiTokensERC20("usei", "Wrapped SEI", "wSEI", 18)` (18 decimals, mimicking a typical ERC20).
2. A caller intending to send "1 wSEI" computes `amount = 1 * 10**18` and calls `transfer(recipient, amount)`.
3. `_update` forwards `amount` (10^18) directly to `IBank.send(from, to, "usei", 10**18)`, which the bank precompile interprets as `10**18 usei` (a vastly larger, incorrect quantity) rather than `1 usei`/`1 SEI`-equivalent, because the bank keeper's native `usei` unit has no independent decimal scaling relative to the constructor's `ddecimals`.
4. The transaction either reverts (insufficient balance) or transfers an amount catastrophically different from the caller's intent, demonstrating the same decimals-unit mismatch class as the reported Portfolio.sol issue.
