### Title
DLEq proof verification accepts a forged proof when the statement list is empty, skipping all `s`-dependent checks - (File: crypto/dleq/src/lib.rs)

### Summary
The Predy Finance incident involved a contract path that let an attacker drive protocol logic with attacker-shaped inputs that were never properly validated. The Serai analog is in `DLEqProof::verify` / `MultiDLEqProof::verify`: the Fiat-Shamir challenge is derived by iterating per-statement transcript data, but when the `generators`/`points` lists are empty (or when a `MultiDLEqProof` is deserialized with `discrete_logs` matching an empty statement list), no `verify_statement` call ever runs. The verification then reduces to `self.c == challenge(transcript)`, where `challenge` is computed over a transcript containing only the `"dleq"` / `"multi_dleq"` domain separator — a value any unprivileged party can compute publicly. `s` is never constrained, so the attacker supplies an arbitrary `s` and the deterministic `c`, producing a universally-forged proof.

### Finding Description
`DLEqProof::verify` at `crypto/dleq/src/lib.rs:160-180` only feeds the transcript inside the loop over `generators.iter().zip(points)`. With `generators == []` and `points == []` (the length check passes trivially), `verify_statement` is never invoked, so the transcript never commits to any point, nonce, or generator — and crucially, `self.s` is never used at all. The final check `self.c != challenge(transcript)` compares `c` against a hash of an effectively constant transcript. An attacker can compute that challenge themselves (it is a pure function of the public transcript initialization), set `c` to it, set `s` to anything, serialize via `DLEqProof::write`, and the proof verifies.

The same holds for `MultiDLEqProof::verify` at `crypto/dleq/src/lib.rs:264-294`: `MultiDLEqProof::read(r, 0)` yields `s == []`, and `verify(transcript, &[], &[])` passes all length checks and accepts `c == challenge` over a transcript with only the `"multi_dleq"` separator.

### Impact Explanation
Wherever Serai consumes a `DLEqProof`/`MultiDLEqProof` from untrusted bytes (`DLEqProof::read`, `MultiDLEqProof::read`) and the generator/point lists are derived from attacker-influenced data (e.g., a per-message generator set or key set that can be empty), a forged proof is accepted — the verifier believes a discrete-log equality that was never proven. This is a forged-proof acceptance reachable with public inputs only. Note: exploitation requires a call site whose statement lists can be empty under attacker control; with a fixed non-empty generator set the flaw is unreachable.

### Likelihood Explanation
Medium. The bug is unconditional in the verification math — no secret knowledge is needed to forge — but practical reachability depends on a consumer passing attacker-influenced or dynamically-sized `generators`/`points` vectors that can be empty. Any such consumer (e.g., a verifier batching proofs over a session-derived generator set) is fully exploitable.

### Recommendation
Reject empty statement lists: in both `DLEqProof::verify` and `MultiDLEqProof::verify`, add `if generators.is_empty() { return Err(DLEqError::InvalidProof); }` alongside the existing length checks, and in `prove` assert non-empty `generators`. Optionally also commit `generators.len()`/`points.len()` to the transcript so statement cardinality is bound into the challenge.

### Proof of Concept
```rust
// Given any transcript T the verifier will use, an attacker forges a proof:
let mut transcript = T::new(b"example_dst");      // same transcript construction as verifier
transcript.domain_separate(b"dleq");
let forged_c: F = challenge(&mut transcript);      // public computation
let forged = DLEqProof::<G> { c: forged_c, s: F::ZERO }; // s is never checked

// Verifier side:
let mut vtranscript = T::new(b"example_dst");
forged.verify(&mut vtranscript, &[], &[]).unwrap(); // incorrectly returns Ok
```
Root cause: `verify` never enforces `generators.len() > 0`, so the loop appends nothing to the transcript and `s` participates in zero statements (`crypto/dleq/src/lib.rs:166-179`).
