## Title
Malicious ERC20 order-input token permanently bricks cross-chain escrow settlement and lets order creators rug solvers — (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw`, called by both the `RedeemEscrow` settlement path (`ExtrinsicIntents`/`onAccept`) and the cancellation/refund paths of the Intent Gateway, iterates over *all* of an order's escrowed input tokens in a single loop and unconditionally calls `IERC20(token).safeTransfer(...)` on each one [1](#0-0) . `placeOrder` performs no whitelist check on `order.inputs[i].token` — any address supplied by the order creator is accepted and escrowed via `safeTransferFrom` [2](#0-1) . An order creator can therefore escrow one legitimate token plus one malicious, blacklist-capable ERC20 in the same order. A solver who fills the cross-chain order and delivers the requested output on the destination chain can then be blacklisted by the order creator on the source chain before the `RedeemEscrow` message settles, permanently reverting `_withdraw` for every token in that order — including the legitimate one — and leaving the solver's already-delivered output unrecoverable while the source-chain escrow is frozen indefinitely.

### Finding Description
This is a direct analog of the OpenQ H-8 bug class: a bounty (order) funded with a malicious/blacklisting ERC20 causes the claim/withdraw function to revert entirely, bricking distribution of *all* funds in that bounty, not just the malicious token.

1. `placeOrder` accepts arbitrary `order.inputs[i].token` addresses with no whitelist, and escrows them with `safeTransferFrom` [2](#0-1) . There is a duplicate-token check but no token-quality/whitelist check [3](#0-2) .
2. A solver fills the cross-chain order on the destination chain via `_fillCrossChain`, which immediately marks `_filled[commitment] = msg.sender` **on the destination chain** and unconditionally delivers the requested output tokens to the beneficiary before any cross-chain message is even dispatched [4](#0-3) [5](#0-4) .
3. A `RedeemEscrow` POST request is then dispatched back to the source chain, to be processed later by `onAccept` → `withdraw`/`_withdraw`.
4. Between the fill (step 2) and the message being finalized on the source chain, the order creator — who controls the malicious token's admin/blacklist function — blacklists the known solver address (now public from the fill transaction) on the source chain.
5. When the `RedeemEscrow` message is delivered, `_withdraw` sets `_filled[body.commitment] = beneficiary` and then loops over `body.tokens`, calling `safeTransfer` for each [6](#0-5) . The malicious token's transfer to the now-blacklisted solver reverts, which reverts the *entire* `_withdraw` call — including the `_filled` mapping write and the transfer of the legitimate token — atomically rolling back all of it.
6. The low-level dispatch wrapper that invokes `onAccept` (in `EvmHost`) treats a revert as "not yet handled" and simply deletes the request receipt so the message can be retried, rather than reverting the whole message-processing transaction [7](#0-6) . This means retries occur but always fail identically, since the blacklist persists.
7. Because the source-chain `_filled[commitment]` mapping is never actually set (the write is rolled back with the rest of `_withdraw`), the order superficially looks "not filled" on the source chain. However, cancellation is also blocked: the destination chain's `_filled[commitment]` was already set to the solver in step 2, so both the source-route cancellation (which proves the destination is *unfilled*) and the destination-route cancellation (which checks its own local `_filled` before allowing a refund dispatch) fail with `Filled()`.

The net effect: the solver's delivered output is gone, and the source-chain escrow (both the malicious and the legitimate token) is frozen permanently — it can neither be released to the solver nor refunded to the order creator through the protocol's own mechanisms (the order creator, being the attacker, simply never bothers to unblacklist, and in fact usually cannot benefit from doing so once state has already diverged).

### Impact Explanation
This causes real fund loss and permanent fund lock in the production Intent Gateway settlement path:
- The solver's output delivery on the destination chain (real value) is irrecoverable.
- The escrowed input tokens (including any legitimate, valuable tokens co-escrowed alongside the malicious one) on the source chain are frozen with no code path to release or refund them.
This matches the required impact class: "stealing or loss of funds" / "logic attacks" causing permanent lock via a public, unprivileged entrypoint (`placeOrder` + `fillOrder`), with no reliance on a malicious relayer, prover, or admin.

### Likelihood Explanation
The attacker only needs to be an ordinary, unprivileged Intent Gateway user (the order creator) who deploys their own blacklist-capable ERC20 and includes it as one of the order's `inputs`. No relayer, prover, governance, or leaked-key assumption is required — only ordinary control over their own token contract and observing the public `fillOrder` transaction to learn the solver's address before the cross-chain settlement message is processed. Given active solver competition for attractive orders, this is a realistic, repeatable attack against solvers.

### Recommendation
- Make `_withdraw`'s per-token transfer loop resilient to individual token failures: wrap each `safeTransfer` in a try/catch (or low-level call) and credit any un-transferable balance to an escrow/claimable mapping instead of reverting the whole withdrawal.
- Set `_filled[body.commitment] = beneficiary` and emit finalization events strictly before attempting transfers, and ensure a failing transfer for one token cannot block the release of the others or the marking of order completion.
- Consider a per-token allowlist for `order.inputs` and/or requiring solvers to explicitly opt in to the token set they will accept before committing to fill, so solvers can protect themselves from unknown/malicious escrow tokens.

### Proof of Concept
1. Order creator deploys `MaliciousToken` (ERC20 with an admin-controlled `blacklist` mapping enforced in `_beforeTokenTransfer`, analogous to `MockBAD` in the OpenQ report).
2. Order creator calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000}, {token: MaliciousToken, amount: 1} ]` and an attractive `order.output` on a different destination chain.
3. Solver observes the order, calls `fillOrder` on the destination chain, delivering the requested output to the beneficiary; `_fillCrossChain` sets `_filled[commitment] = solver` on the destination and dispatches `RedeemEscrow` to source [8](#0-7) .
4. Before the `RedeemEscrow` message is relayed/finalized on the source chain, the order creator calls `MaliciousToken.setBlacklist(solver)`.
5. When `onAccept` on the source chain processes the `RedeemEscrow` message and calls `withdraw`/`_withdraw`, the `safeTransfer` of `MaliciousToken` to `solver` reverts, reverting the whole `_withdraw` call including the USDC transfer [9](#0-8) .
6. Any resubmission of the same message hits the same revert indefinitely (the token stays blacklisted); the solver never receives the 1000 USDC, and the order can be neither filled-through nor cancelled since the destination side already recorded it as filled.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
