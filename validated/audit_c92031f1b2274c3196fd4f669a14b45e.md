This is a clear, exploitable analog to the reported bug class. `checkConsistency` explicitly only cross-checks `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` against each other; `gov.Kip71GasTarget` falls into the default no-op branch [1](#0-0) , and its `FormatChecker` is a no-op that accepts any `uint64` including 0 [2](#0-1) . ### Title
Governance vote can set `kip71.gastarget = 0`, causing a division-by-zero panic in base fee calculation that halts the network - (File: params/kip71_config.go)

### Summary
The KIP-71 (Magma) dynamic base fee parameter `GasTarget` is validated only with a `noopFormatChecker` (accepts any `uint64`, including 0) and is never cross-checked against zero in `checkConsistency`, unlike `LowerBoundBaseFee`/`UpperBoundBaseFee` which have explicit relational checks. When `GasTarget` is 0, `NextMagmaBlockBaseFee` divides by a zero-valued `big.Int`, panicking every node that computes the next base fee.

### Finding Description
Governance parameter votes for `Kip71GasTarget` are validated via `Params[Kip71GasTarget].FormatChecker`, which is `noopFormatChecker` and always returns `true`, so any `uint64` value including `0` is accepted [2](#0-1) . The header-level `checkConsistency` function performs additional relational sanity checks only for `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` (each checked against the other bound) [4](#0-3) , while `Kip71GasTarget` (along with `Kip71BaseFeeDenominator` and others) is routed to the no-op `default: return nil` branch with no further validation [1](#0-0) .

Once `GasTarget = 0` is committed via a passing governance vote/epoch governance update, it is consumed unguarded in `NextMagmaBlockBaseFee`:
```go
var baseFeeDenominator *big.Int
if kc.BaseFeeDenominator == 0 {
    // To avoid panic, set the fluctuation range small
    baseFeeDenominator = new(big.Int).SetUint64(64)
} else {
    baseFeeDenominator = new(big.Int).SetUint64(kc.BaseFeeDenominator)
}
gasTarget := kc.GasTarget
...
} else if parentGasUsed > gasTarget {
    ...
    gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
    x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
    y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // <-- division by zero when gasTarget == 0
``` [3](#0-2) 

Note the author was clearly aware that a zero governance parameter can cause a panic (the comment "To avoid panic, set the fluctuation range small" for `BaseFeeDenominator == 0`), but the equivalent guard was omitted for `GasTarget`. Since `parentGasUsed` is a `uint64`, it can never be less than `gasTarget == 0`, so the "decrease" branch (which also divides by `gasTarget`) can never execute; but the "increase" branch executes and panics whenever `parentGasUsed > 0`, i.e., in virtually every real block.

`NextMagmaBlockBaseFee` is called in two critical, protocol-wide code paths:
1. Block production: `worker.commitNewWork()` calls it to set the next block's `BaseFee` before proposing [5](#0-4) .
2. Header verification: `VerifyMagmaHeader` calls it to validate every incoming block's `BaseFee` field [6](#0-5) .

Both paths run unconditionally on every node once `GasTarget` becomes 0 for the current parameter set, causing a network-wide panic/crash rather than a mere transaction revert.

### Impact Explanation
This is a direct chain-halting bug: once the invalid `gastarget=0` governance value takes effect (at the next epoch boundary after being voted through), every full node — validators and RPC nodes alike — panics in `NextMagmaBlockBaseFee` on the very first non-empty block, both when constructing the next block and when verifying the received block header. This is a total network-wide denial of service requiring a hard fork or governance-contract intervention to recover, matching "state divergence/halt across nodes" and "acceptance-based failure of the network."

### Likelihood Explanation
Governance votes are restricted to validators (or, after Permissionless fork, the governing node in single mode) as enforced in `VerifyVote` (voter must be in council and must be block proposer) [7](#0-6) . This is a privileged but entirely in-protocol action (not requiring key leaks, node compromise, or consensus-message manipulation) — a single validator including the vote in a proposed block, if enough votes accumulate for the majority requirement, results in `gastarget: 0` being adopted as an epoch governance value with no rejection anywhere in the validation pipeline. Given the total absence of a zero/format check (unlike the analogous `BaseFeeDenominator == 0` case, which is explicitly guarded), the likelihood of this being triggered — accidentally via misconfiguration or deliberately by a malicious/faulty validator set — is non-negligible and the impact when triggered is total.

### Recommendation
Add an explicit rejection of `GasTarget == 0` either in `Params[Kip71GasTarget].FormatChecker` (reject non-positive values) or in `checkConsistency` in `kaiax/gov/headergov/impl/header.go`, and additionally add a defensive `if kc.GasTarget == 0 { ... }` fallback inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, mirroring the existing `BaseFeeDenominator == 0` guard, so that a bad governance value cannot panic the node even if it slips past validation.

### Proof of Concept
1. A validator/governing node casts a governance vote setting `kip71.gastarget = 0` (passes `NewVoteData`, `VerifyVote`, and `checkConsistency` unchanged since `Kip71GasTarget` has no format or consistency check for zero).
2. At the next epoch boundary, this value becomes part of the effective `ParamSet` (`GasTarget = 0`) via `VerifyGov`/`getExpectedGovernance`.
3. On the following block with any nonzero gas usage, `worker.commitNewWork()` (proposer) and `VerifyMagmaHeader` (all verifying nodes) both call `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` with `parentGasUsed > 0 = gasTarget`.
4. Execution enters the `parentGasUsed > gasTarget` branch, reaches `y := x.Div(x, new(big.Int).SetUint64(0))`, and panics with "division by zero," crashing every node processing this block. [8](#0-7)
