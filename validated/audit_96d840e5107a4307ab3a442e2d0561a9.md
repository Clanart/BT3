## Title
Attacker-controlled deep link silently switches the checked-out branch of an already-open repository - (File: `app/src/ui/dispatcher/dispatcher.ts`)

## Summary
The `AgentVeToken.stake()` bug lets an unrelated caller silently mutate a state field (`delegatee`) belonging to a *receiver* account they don't control, simply by supplying that receiver's address plus an attacker-chosen parameter, with no consent from the receiver. The Desktop analog is `Dispatcher.openRepositoryFromUrl` / `openBranchNameFromUrl`, reached from the OS-level `x-github-client://openrepo/...` protocol handler: clicking an attacker-crafted link can match an existing, already-open repository purely by its GitHub origin/upstream URL and then automatically fetch and check out a branch name supplied entirely by the link, with no confirmation dialog.

## Finding Description
`parseAppURL` extracts `url`, `branch`, `pr`, and `filepath` directly from an OS-delivered deep link with only superficial validation (`testForInvalidChars` on the branch string) [1](#0-0) . This is dispatched to `dispatchURLAction`, which calls `openRepositoryFromUrl` unconditionally for any `open-repository-from-url` action [2](#0-1) .

Inside `openRepositoryFromUrl`, when a `branch` is present the code calls `openBranchNameFromUrl(url, branch)` [3](#0-2) . That function resolves the target repository via `openOrCloneRepository`, which first tries to match the link's `url` against the **origin or upstream URL of a repository the victim already has open in Desktop** using `doesRepositoryMatchUrl` [4](#0-3) [5](#0-4) . If a match is found, Desktop does **not** show a clone/open dialog — it proceeds straight to refreshing, fetching, and checking out the attacker-specified branch on the victim's existing local repository: [6](#0-5) 

This mirrors the broken invariant in the report: a caller-supplied parameter (`branch`, analogous to `delegatee`) is automatically applied to a target the caller doesn't own (the victim's already-open repository, analogous to `receiver`), without any explicit confirmation from the party actually affected. The only "sender == receiver" check the report recommends is absent here: there is no check that the click was initiated by the same user session that intentionally wants a branch switch — any repository whose remote URL matches is silently repointed to whatever branch the link names.

## Impact Explanation
If the branch exists on the remote, Desktop fetches and checks it out into the working directory of a repository the user is actively using, with no prompt. Because the switch is silent and automatic, a user could then stage/commit/push changes while unknowingly on the attacker-chosen branch (e.g., a stale or unexpected branch), corrupting what gets committed or pushed relative to the branch the user believed they were on — one of the explicitly valid impacts (“silent corruption of what the user commits or pushes”). It also discards the visibility of "what am I on" that the normal UI flow provides via explicit user-driven branch switch actions.

## Likelihood Explanation
Requires only that the victim click a link (or the OS-registered `x-github-client://` / `github-mac://` / `github-windows://` scheme is invoked, e.g. via a webpage) referencing the URL of a repository the victim has already cloned/opened in Desktop, plus an existing branch name on that remote — both attacker-guessable for popular/public repos. No local access, credentials, or malware are required, matching the “link/deep-link the user clicks” valid-impact category.

## Recommendation
Require explicit user confirmation before performing an automatic branch checkout that originates from a URL-scheme/deep-link action, especially when it targets a repository the user did not select in-app. At minimum, surface a dialog naming the target repository and branch, mirroring the receiver-consent fix suggested in the original report (only proceed if the action was initiated in-context by the same user rather than an externally supplied link).

## Proof of Concept
1. Victim has a repository open in Desktop whose origin/upstream matches `https://github.com/some-org/some-repo`.
2. Attacker sends the victim a link (e.g., embedded on a webpage or in a chat client) such as:
   `x-github-client://openrepo/https://github.com/some-org/some-repo?branch=malicious-branch`
3. Victim clicks the link; the OS invokes Desktop's registered protocol handler, which calls `handleAppURL` → `parseAppURL` → `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` [6](#0-5) .
4. Desktop matches the existing repository by URL (`doesRepositoryMatchUrl`), fetches, and silently checks out `malicious-branch` with no confirmation shown to the user.

I could not verify within the tool budget whether uncommitted local changes are blocked/stashed before this automatic checkout (that would be handled deeper in `checkoutLocalBranch`, which I was unable to locate/read before the iteration limit) — this is a gap in verification and should be checked directly in a full session.

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }

      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }
