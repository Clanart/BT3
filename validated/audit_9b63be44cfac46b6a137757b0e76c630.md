### Title
Marker-syntax content that is not an actual git conflict is misidentified as a conflict hunk and silently overwritten - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` locates conflict blocks purely by regex-matching lines against `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` [1](#0-0) . Any line in the committed file that syntactically matches a 7-character marker (e.g. `<<<<<<< label`, `=======`, `>>>>>>> label`) is indistinguishable from a marker git actually inserted for a real conflict — there is no correlation with git's own conflict-region metadata.

### Finding Description
`extractConflictHunks` in `copilot-conflict-context.ts` uses the identical marker regexes (`oursMarker`/`baseMarker`/`separatorMarker`/`theirsMarker`) to scan the *entire* raw file text and build the hunk list sent to the model [2](#0-1) , [3](#0-2) . `reassembleResolvedFile` later re-scans the same raw content with equivalent lookahead logic to find splice points [4](#0-3) . Neither function has any awareness of which byte ranges git actually flagged as conflicted; both simply pattern-match text.

Because `buildConflictContext` is only invoked for paths git already reports as conflicted [5](#0-4) , an attacker who lands a real (even trivial) conflict in a file can also plant, elsewhere in that same file, literal lines that happen to form a complete `<<<<<<< X` / `=======` / `>>>>>>> Y` triplet as legitimate content (e.g. a tutorial/example about resolving git conflicts, a fixture, or ASCII documentation). `extractConflictHunks` will count this decoy block as an additional real "Conflict N of M" and include it in the prompt sent to Copilot; the model has no way to know it's not a real conflict and will fabricate a "resolvedContent" for it. `reassembleResolvedFile` then splices that fabricated content in place of the decoy block, permanently discarding the original, intentional file content the moment the user accepts the Copilot resolution and commits.

The function's own comment acknowledges the general risk category ("a `<<<<<<<` line ... is treated as regular content to avoid data loss from malformed or stray markers") [6](#0-5) , but the guard only covers *incomplete* marker sequences (missing separator or closing marker) [7](#0-6) . A syntactically well-formed but unintentional triplet is not detected and is treated exactly like a real conflict.

### Impact Explanation
Legitimate, intentional file content that merely resembles conflict-marker syntax is silently deleted/replaced with LLM-generated text during the Copilot "resolve conflicts" flow, without any warning that non-conflicting content was touched. This is a form of silent corruption of what the user ultimately commits — the described "Valid Impact" category. Because the misidentified block is presented to the LLM as a genuine "Conflict N of M" and its output is spliced back verbatim, the user reviewing only the model's summary/reasoning (rather than diffing every line) may commit the corruption unknowingly.

### Likelihood Explanation
Requires: (1) the attacker's branch/PR to actually produce a real conflict with the local branch so the file enters this pipeline at all, and (2) the same file to contain, on the attacker's side, a complete marker-syntax triplet as legitimate content outside the real conflict region. Both conditions are attacker-controllable by crafting the file content on the "theirs" side. The remaining dependency is that the user invokes GitHub Desktop's Copilot AI conflict-resolution feature and accepts its output without manually diffing every hunk, which is the feature's expected normal use.

### Recommendation
`reassembleResolvedFile` (and `extractConflictHunks`) should not rely purely on line-level regex matching of the whole file. Instead, conflict-block boundaries should be derived once (e.g., during `extractConflictHunks`, by recording line-index ranges) and reused verbatim by `reassembleResolvedFile`, rather than being independently re-derived via a second regex scan of the raw text. This at minimum eliminates the double-parsing inconsistency risk. To fully solve the false-positive issue, cross-check candidate conflict regions against git's actual conflict markers (e.g., via `git diff --check` or the merge's stage information / `.git/MERGE_MSG` conflict list) rather than trusting arbitrary in-file text that merely matches the marker syntax.

### Proof of Concept
1. Create a repository where merging `theirs` into the current branch produces one real conflict in `notes.md`.
2. In `notes.md` on the `theirs` side, additionally include unrelated, legitimate content such as:
   ```
   Example of a git conflict marker block:
   <<<<<<< HEAD
   old text
   =======
   new text
   >>>>>>> feature
   ```
   positioned outside the real conflict region.
3. After the merge, `notes.md` on disk contains two marker-matching regions: the real conflict and the "example" text.
4. Run `extractConflictHunks` on the file — it reports 2 hunks (verifiable via `app/test/unit/copilot-conflict-context-test.ts` style unit test), including the documentation block as `Conflict 2 of 2`.
5. Invoke Copilot conflict resolution; the model returns 2 `resolvedContent` entries, the second being a fabricated replacement for the documentation example.
6. `reassembleResolvedFile` splices that fabricated content in place of the original documentation block, and the reassembled file no longer contains the original example text once the resolution is applied and committed — confirming silent content loss for non-conflicting, intentional file content.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

export async function buildConflictContext(
  ourLabel: string,
  theirLabel: string,
  workingDirectory: string,
  files: ReadonlyArray<{
    readonly path: string
    /** Which side deleted the file (for delete-vs-modify conflicts). */
    readonly deletedSide?: 'ours' | 'theirs'
  }>
): Promise<ICopilotConflictContext> {
  const results = await Promise.all(
    files.map(async (file): Promise<IFileConflictContext> => {
      // Delete-vs-modify conflicts have no text markers on disk. Include
      // them in the context with metadata so the model can recommend
      // keep or delete — no file content is needed.
      if (file.deletedSide !== undefined) {
        return {
          path: file.path,
          hunks: [],
          deleteConflict: { deletedSide: file.deletedSide },
        }
      }

      // Guard against path traversal and symlink escapes (cross-platform)
      let absolutePath: string | null
      try {
        absolutePath = await resolveWithin(workingDirectory, file.path)
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File path could not be resolved safely',
        }
      }
      if (absolutePath === null) {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File path is outside the repository',
        }
      }

      // Guard against reading pathologically large files into memory. This is
      // a memory-safety bound only — resolvability is decided from the conflict
      // hunks below, not the whole-file size.
      try {
        const fileStat = await stat(absolutePath)
        if (fileStat.size > MAX_CONFLICT_FILE_READ_SIZE) {
          return {
            path: file.path,
            hunks: [],
            skippedReason: 'File too large to resolve automatically',
          }
        }
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

      let content: string
      try {
        content = await readFile(absolutePath, 'utf8')
      } catch {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'File could not be read',
        }
      }

      const hunks = extractConflictHunks(content)
      if (hunks.length === 0) {
        return {
          path: file.path,
          hunks: [],
          skippedReason: 'No conflict markers found',
        }
      }

      // Gate on the size of the conflict content we'd actually send to the
      // model, not the whole-file size.
      const hunkSkipReason = getHunkSkipReason(hunks)
      if (hunkSkipReason !== null) {
        return {
          path: file.path,
          hunks: [],
          skippedReason: hunkSkipReason,
        }
      }

      return { path: file.path, hunks, rawContent: content }
    })
