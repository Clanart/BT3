### Title
Missing identity/consistency checks on deserialized `ThresholdKeys` allow an attacker-chosen group key with a publicly known discrete logarithm, making received funds trivially spendable by anyone - (File: crypto/dkg/src/lib.rs)

### Summary
The bug-class in the external report — "value transferred to an unchecked/zero destination" — maps onto Serai as "untrusted bytes deserialized into a `ThresholdKeys` whose interpolated `group_key` is the identity point (or a point with a known discrete log)". `ThresholdKeys::read` reads `n` verification shares via `Ciphersuite::read_G`, which enforces canonical encodings but, unlike `frost::Curve::read_G`, does not reject the identity point, and `ThresholdKeys::new` validates only the count and indexes of `verification_shares` — it never checks that the interpolated `group_key` is non-identity, nor that `secret_share` is consistent with `verification_shares[i]`. A crafted serialization therefore yields keys whose group key is identity. When bitcoin-serai's `tweak_keys`/`Scanner` are applied to such keys, the resulting Taproot output key has a discrete logarithm equal to a publicly computable `TapTweakHash`, so funds "received" to it are spendable by any unprivileged party.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation variant, a `secret_share` scalar, and `n` verification shares, then calls `ThresholdKeys::new`. The only validation in `ThresholdKeys::new` is on the share count, participant index bounds, and the `Constant`-interpolation `t == n` restriction; the computed `group_key = Σ verification_shares[i] * interpolation_factor(i, 1..=t)` is never checked for identity.

Because each share is read with `Ciphersuite::read_G` (canonicality check only, no identity rejection) and shares may be adversarially related, an attacker can set `t = n = 2` with Lagrange interpolation and choose `V1 = G`, `V2 = 2G`. The Lagrange factors for `{1, 2}` are `λ1 = 2/(2−1) = 2` and `λ2 = 1/(1−2) = −1`, giving `group_key = 2·V1 − V2 = 2G − 2G = identity`. Both points are non-identity and canonically encodable, so deserialization succeeds. The attacker supplies `secret_share = 0` freely since `ThresholdKeys::new` never verifies `verification_shares[i] == G * secret_share`.

Downstream, `tweak_keys` computes `offset = TapTweakHash(group_key.to_bytes()[1..])` and returns `keys.offset(offset)`, so `group_key()` becomes `identity + offset·G = offset·G` — a point whose discrete logarithm `offset` is a deterministic hash anyone can recompute. `needs_negation`/`scale(±1)` only flips the sign, leaving `±offset` as the effective secret. `Scanner::new` and `p2tr_script_buf` then accept the resulting even key and produce a P2TR `script_pubkey` that `scan_transaction`/`scan_block` report as a `ReceivedOutput`.

### Impact Explanation
Any party who computes `TapTweakHash(identity_encoding[1..])` knows the private key (up to negation for BIP-340 parity) of the resulting Taproot address. Funds deposited to the scanned address are reported as received `ReceivedOutput`s by `Scanner::scan_transaction`/`scan_block`, yet are spendable by an unprivileged attacker — equivalent to sending tokens to a zero/attacker-known address. This satisfies the "funds reported received that are not safely spendable / are stealable" impact class.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ThresholdKeys::read` and the resulting keys being used for receiving funds — an entry point explicitly in scope. The construction needs no secret knowledge, no collusion, and no protocol participation: it is a pure deserialization forgery producing an identity group key for `t = n = 2` (or any configuration where a linear combination of chosen canonical shares sums to identity). Success is deterministic; the only prerequisite is that the victim treats deserialized `ThresholdKeys` as authoritative for address/key derivation.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), after computing `group_key`, reject `group_key.is_identity()`. Additionally, verify the deserialized `secret_share` is consistent with `verification_shares[i]` (i.e., `C::generator() * secret_share == verification_shares[&params.i()]` where `interpolation_factor(i) == 1` for its own share only holds when the index matches — at minimum check the share for `i` when the interpolation maps it directly), and consider having `read` reject identity verification shares via an identity-rejecting read as `frost::Curve::read_G` does. For `Interpolation::Constant`, also validate the coefficient vector is consistent with its intended use. In `tweak_keys`, additionally reject an identity `group_key()` after the offset/negation is applied.

### Proof of Concept
```
// Crafted serialization for C = Secp256k1:
//   ID len (4B LE) || C::ID || t=2u16 || n=2u16 || i=1u16
//   interpolation byte = 1 (Lagrange)
//   secret_share = 0 (32B)
//   verification_shares[1] = G   (33B compressed)
//   verification_shares[2] = 2G  (33B compressed)
let keys = ThresholdKeys::<Secp256k1>::read(&mut bytes).unwrap(); // succeeds
// group_key = 2*G*(λ1=2) ... => 2*V1 - V2 = 2G - 2G = identity
assert!(bool::from(keys.group_key().is_identity()));

let tweaked = tweak_keys(keys);           // offset = TapTweakHash(enc(identity)[1..])
let scanner = Scanner::new(tweaked.group_key()).unwrap(); // even key accepted
// Any output to scanner's P2TR script is reported as ReceivedOutput,
// yet private key = ±TapTweakHash(enc(identity)[1..]) — publicly computable.
```

Uncertainty noted: the exact 33-byte encoding k256 produces for the identity point (`to_bytes()[1..]`) was not verified line-by-line, but whatever fixed bytes result, `TapTweakHash` of them is a publicly computable scalar, so the resulting tweaked key still has a known discrete logarithm. Also, the interpolation-factor convention (`λ1 = 2, λ2 = −1` for participants `{1, 2}`) follows standard Lagrange evaluation at 0; the precise sign/order in `Interpolation::interpolation_factor` was not re-verified, but any consistent Lagrange scheme permits choosing `V1, V2` so the weighted sum is identity.
