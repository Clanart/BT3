### Title
Keychain Namespace Collapse via Unescaped `kc_user`+`kc_service` Concatenation - (File: `chia/daemon/keychain_server.py`)

### Summary
`KeychainServer.get_keychain_for_request()` partitions private-key storage across multiple `Keychain` instances by concatenating the caller-supplied `kc_user` and `kc_service` strings with no delimiter to form the lookup key for the `_alt_keychains` cache. Because the concatenation is ambiguous (`user1+service1` can equal `user2+service2` for different splits of the same combined string), two distinct logical keychain namespaces can collapse onto the same cached `Keychain` object, exactly analogous to the reported OTP `mod_auth` bug where distinct directory-configuration namespaces collapsed into a single shared user/group namespace.

### Finding Description
`get_keychain_for_request()` builds the cache key as: [1](#0-0) 

```
user = request.get("kc_user", self._default_keychain.user)
service = request.get("kc_service", self._default_keychain.service)
...
key = (user or "unnamed") + (service or "")
if key in self._alt_keychains:
    keychain = self._alt_keychains[key]
else:
    keychain = Keychain(user=user, service=service)
    self._alt_keychains[key] = keychain
```

`user` and `service` are read directly from the untyped request dict, which for legacy/hand-parsed commands (`add_key`, `add_private_key`, `check_keys`, `delete_all_keys`, `delete_key_by_fingerprint`, `get_all_private_keys`, `get_first_private_key`, `get_key_for_fingerprint`) is exactly the JSON payload the daemon received over the local websocket, per the daemon command-dispatch/keychain-interception behavior documented for `handle_command()`. Because the two strings are concatenated with no separator, `("ab", "cd")` and `("abc", "d")` produce the identical key `"abcd"`, so a request that intends to address one logical (user, service) keychain namespace can instead be served the cached `Keychain` instance created for a different, unrelated (user, service) pair — the same class of bug as the referenced CVE, where distinct configuration namespaces are collapsed into one shared authority because the partitioning mechanism does not preserve the boundary between the original inputs.

Every write/read keychain RPC (`add_key`, `get_all_private_keys`, `get_key_for_fingerprint`, `delete_key_by_fingerprint`, `delete_all_keys`, etc.) is dispatched through `get_keychain_for_request()`: [2](#0-1) 

so any collision in the derived key routes the operation to whichever `Keychain` object was first cached under that colliding string, silently mixing key material belonging to different logical namespaces.

### Impact Explanation
The daemon's keychain RPC is the local authority that owns private key custody for wallet, plotting, and other services (`KeychainProxy` in remote mode forwards all key operations here). If a local, authenticated-but-otherwise-unprivileged caller (any local process holding a valid daemon client certificate, e.g., a co-located service or plugin) can influence or predict `kc_user`/`kc_service`, it can cause its own `add_key`/`get_all_private_keys`/`delete_key_by_fingerprint` calls to be serviced by a `Keychain` instance actually intended for a different namespace — reading, deleting, or adding into another service's/user's key store. This can lead to unauthorized visibility or mutation of another entity's private keys, i.e., unauthorized custody/coin-movement risk once a wallet key from a different namespace becomes reachable.

### Likelihood Explanation
Exploitability requires only a colliding pair of ASCII strings (trivial to construct, e.g., `("a","bc")` vs `("ab","c")`) sent as `kc_user`/`kc_service` fields in an otherwise normal keychain JSON request over the local daemon websocket. No cryptographic material or peer/network access is needed — only local access to the daemon's mTLS trust boundary, which is the same access level assumed for any local RPC caller per the daemon's threat model documented for `KeychainServer`.

### Recommendation
Use a collision-free, unambiguous key when caching per-namespace `Keychain` instances — e.g., a tuple `(user, service)` as the dict key instead of string concatenation, or concatenate with an explicit length-prefixed/escaped separator that cannot appear in either field (e.g., `f"{len(user)}:{user}:{service}"`). Add regression tests asserting that distinct `(kc_user, kc_service)` pairs whose naive concatenation would collide resolve to distinct `Keychain` instances.

### Proof of Concept
1. Start the daemon's `KeychainServer` (or invoke `get_keychain_for_request()` directly).
2. Send request A: `{"kc_user": "a", "kc_service": "bc", "mnemonic_or_pk": "<mnemonic-1>", ...}` via `add_key` — this creates/caches a `Keychain(user="a", service="bc")` under key `"abc"`.
3. Send request B: `{"kc_user": "ab", "kc_service": "c", "mnemonic_or_pk": "<mnemonic-2>", ...}` via `add_key`.
4. Because `("a" + "bc") == ("ab" + "c") == "abc"`, request B is served by the same cached `Keychain` instance created in step 2, storing/reading `mnemonic-2` in namespace `(user="a", service="bc")` rather than creating an isolated `Keychain(user="ab", service="c")`.
5. A subsequent `get_all_private_keys` call using either `(kc_user, kc_service)` pair returns keys from both logical namespaces intermixed, demonstrating the namespace collapse. [3](#0-2)

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```
