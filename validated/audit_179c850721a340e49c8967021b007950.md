### Title
Unvalidated `head.repo.clone_url` from PR API is passed directly to `git remote add` / `git fetch` with no protocol allowlist - (`File: app/src/lib/stores/app-store.ts`)

### Summary
The Code4rena finding is a broken-invariant class bug: an address/URL value that the caller assumes is a valid, benign target is used directly in a state-changing operation without validating that it actually refers to a legitimate resource. In GitHub Desktop, the closest analog is `_findPullRequestBranch` in `app-store.ts`, which takes `headCloneUrl` — a string taken verbatim from a pull request's `head.repo.clone_url` field returned by a GitHub/GHE API response — and passes it unmodified to `addRemote()` and subsequently `git fetch` with no scheme/host validation.

The only checks performed on remote URLs anywhere in the remote/fetch pipeline are for proxy resolution (matching `^https?://`) and for GitHub.com/GHE hostname comparison used for *matching* purposes (`urlMatchesRemote`, `repository-matching.ts`), not for *validating* the value before it is handed to `git remote add`/`git fetch`: [5](#0-4) [6](#0-5) 

Neither `addRemote` nor `envForRemoteOperation` reject non-`http(s)`/`ssh` schemes (e.g. `ext::`, ssh options with `-oProxyCommand=`, or local `file://` paths), and no `GIT_ALLOW_PROTOCOL`/`protocol.allow` restriction exists anywhere in the codebase (confirmed by search — no matches for `GIT_ALLOW_PROTOCOL`, `protocol.allow`, or `ext::`).

### Impact Explanation
This mirrors the Stakehouse bug's broken invariant precisely: a value (`_smartWallet` address / `headCloneUrl`) that the caller implicitly trusts to be a legitimate, well-formed target is used directly in a sensitive operation without validating that it corresponds to what it's supposed to represent. Here, if the value returned as `head.repo.clone_url` (whether from a compromised/malicious GitHub Enterprise server, a MITM'd API response, or any other attacker-influenced source of the PR API object) is not a normal `https://`/`git@` URL but instead something like `ext::sh -c "..."`, running it through `git remote add` followed by `git fetch` would execute arbitrary shell commands with the privileges of the Desktop application — a direct path to code execution outside the sandbox, not merely "locked funds" as in the original bug, but the analogous root cause (trusting an unvalidated address/URL as a legitimate target of a subsequent operation).

### Likelihood Explanation
The likelihood is bounded by the trust placed in the PR API object's origin — for github.com this is normally a trusted first-party API, but GitHub Desktop also supports arbitrary GitHub Enterprise endpoints, and clone URLs travel through this exact same unauthenticated pathway (`addRemote`/`fetch`) with no allowlisting of protocol/scheme anywhere downstream. Because there is no defense-in-depth check at the point where the untrusted string transitions from "API field" to "git command argument," any compromise or spoofing of the API response (the report's allowed "attacker controls...a GitHub API object" category) directly reaches `git remote add`/`git fetch` unfiltered.

### Recommendation
Before calling `addRemote`/`fetch` with a URL sourced from an API response (`head.repo.clone_url`, `base.repo.clone_url`, etc.), validate that the URL matches one of the expected `https://`, `git@`/`ssh://` forms accepted by `parseRemote` in `remote-parsing.ts`, and reject anything else (in particular reject values containing `::`, leading `-`, or `ext::`/`fd::` style git transport helpers). Additionally, consider setting `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in `envForRemoteOperation` for all remote-touching git invocations to enforce protocol restriction at the git binary level as defense in depth.

### Proof of Concept
1. Compromise or spoof the GitHub Enterprise API endpoint configured in Desktop (or intercept the API response) so that a pull request's `head.repo.clone_url` field is set to `ext::sh -c "touch /tmp/pwned"` instead of a normal `https://` URL.
2. User opens that PR from Desktop's PR list, triggering `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`. [7](#0-6) 
3. Since no existing remote matches this URL, Desktop calls `addRemote(repository, forkRemoteName, headCloneUrl)` verbatim, then `_fetchRemote`, invoking `git fetch <ext-payload-remote>` which executes the injected shell command via git's `ext::` transport helper. [8](#0-7)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
