### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/vsize accounting, underpaying fees and bypassing the standardness weight check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Optimism report's bug class is: a cost/limit accounting step that fails to account for data being carried (twice, in their case), so items whose true delivery cost exceeds a hard bound are produced yet can never be delivered. `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` has the same shape: an attacker-influenced `data` payload is appended to the transaction as an OP_RETURN output, but the weight, vsize, fee, and `MAX_STANDARD_TX_WEIGHT` check are all computed from `payments` alone. The resulting transaction is strictly larger than what was accounted for, so its effective fee rate is lower than requested and can fall below the minimum relay fee, or its weight can exceed the standardness cap — in either case the signed transaction is undeliverable even though `SignableTransaction::new` accepted it.

### Finding Description
In `SignableTransaction::new`, the outputs actually used in the final `Transaction` are accumulated in `tx_outs`, which includes the OP_RETURN output built from the caller-supplied `data` (up to 80 bytes): [1](#0-0) 

However, both weight calculations are performed by `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which builds its dummy transaction from `payments` — not `tx_outs` — so the OP_RETURN output is never measured: [2](#0-1) [3](#0-2) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` uses a vsize that excludes the OP_RETURN output (~10–95+ bytes of script plus 8 bytes of amount, plus a possible output-count varint increment). The actual fee paid, `sum(inputs) - sum(outputs)`, is unchanged, so the real fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`.
2. The minimum-relay-fee guard at line 211 checks `needed_fee` against the underestimated `vbytes`, so a transaction built with `fee_per_vbyte` exactly at the relay minimum will, once broadcast, have a real fee rate below the minimum and be rejected/never relayed.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the under-measured `weight`, so a transaction with `payments` sized just under the cap plus an 80-byte OP_RETURN exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) and is non-standard — permanently undeliverable — yet the constructor returns `Ok`. [4](#0-3) 

### Impact Explanation
An OP_RETURN-bearing `SignableTransaction` is a consensus- and policy-valid object locally but is undeliverable or under-priced on the network, mirroring the Optimism issue where migrated withdrawals exceed the deliverability bound. If `data` is attacker-influenced (e.g., a payment memo or protocol payload embedded by an external party) and the fee rate is chosen near the relay minimum or the payments are sized near the weight cap, the threshold signatures are still produced and the funds committed to these inputs/outputs, but the transaction cannot propagate. Recovery requires re-signing a corrected transaction, and any system treating the txid (`Eventuality(signable.txid())`, processor/src/networks/bitcoin.rs:830) as the expected completion will wait for a transaction that can never confirm.

### Likelihood Explanation
The `data` field is public input to `SignableTransaction::new` and is explicitly capped at 80 bytes, so an 80-byte payload adds roughly 360+ weight units (~90+ vbytes) unaccounted. This alone cannot push a small transaction over 400,000 WU, but the scheduler caps inputs/outputs at 520 each precisely so a transaction sits near the weight limit (processor/src/networks/bitcoin.rs:564-576) — any plan near that bound with an OP_RETURN output crosses it. The fee underpayment manifests whenever `data` is present, since the measured vsize is always wrong; whether the real rate falls below the relay minimum depends on the configured `fee_per_vbyte`. Medium severity: delivery failure / stuck funds for a reachable subset, not a universal break.

### Recommendation
Pass `tx_outs` (or `payments` plus the serialized OP_RETURN `TxOut`) into `calculate_weight_vbytes` for both the no-change and with-change calls, so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
In `networks/bitcoin/src/wallet/send.rs`:

```rust
let data = Some(vec![0x42; 80]);
let st = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();
```

- `st.tx.output` contains `payments.len() + 1` outputs, but `st.needed_fee` was computed as `fee_per_vbyte * vsize(payments-only-tx)`.
- `st.fee() == st.needed_fee`, yet `st.tx.vsize()` is larger than the measured `vbytes`, so the true fee rate is `needed_fee / st.tx.vsize() < fee_per_vbyte`.
- With `fee_per_vbyte` at the relay minimum and enough payments/inputs to approach 400,000 WU, `st.tx.weight() > MAX_STANDARD_TX_WEIGHT` while the check at line 241 still passed — `send_raw_transaction` on such a transaction is rejected by standardness policy, leaving the signed transaction undeliverable.
