### Title
Withdraw/unlock functions gated by `whenNotPaused` allow admin-triggered pause to freeze already-vested user funds - ([File: VLMGP.sol])

### Summary
`VLMGP.sol` (and similarly `MasterMagpie.sol` / `WombatStaking.sol`) reuse the same `whenNotPaused` modifier for both deposit-type actions and withdrawal/unlock actions. This mirrors the reported `LpToken.sol` bug class: a pause switch meant to stop new deposits during a security incident also blocks users from retrieving funds they already own, including funds that have already finished their cooldown period.

### Finding Description
`VLMGP.lock`/`lockFor` (deposit-type) and `startUnlock`, `unlock`, `cancelUnlock`, `forceUnLock` (withdraw-type) are all guarded by the same `whenNotPaused` modifier [1](#0-0) . Critically, `unlock`, which transfers already-cooled-down MGP principal back to the user, is also blocked while paused [2](#0-1) , as is `cancelUnlock` and `forceUnLock` [3](#0-2) .

`pause()`/`unpause()` are simple owner-gated toggles with no separate flag distinguishing deposit-pause from withdraw-pause [4](#0-3) .

The same pattern is repeated in the broader protocol: `MasterMagpie.withdraw` and `withdrawFor` (used by pool helpers such as `WombatPoolHelper.withdraw`) are gated by `whenNotPaused` [5](#0-4) , and `WombatStaking.withdraw`/`burnReceiptToken` — both required steps in the user withdraw path from `WombatPoolHelper.withdraw` — are also gated by `whenNotPaused` [6](#0-5) [7](#0-6) .

This is the same root cause as the analogous, already-fixed `LpToken.sol` finding: pausing to stop new deposits during a security event unintentionally traps user principal that is otherwise ready to be withdrawn.

### Impact Explanation
While a pause is active (an ordinary, expected operational event during a security response), any user attempting to `unlock`/`cancelUnlock`/`forceUnLock` already-cooled-down MGP from `VLMGP`, or to `withdraw` staked LP/receipt tokens through `MasterMagpie`/`WombatStaking`/`WombatPoolHelper`, is reverted. Users' own principal — not admin funds — becomes inaccessible for the full duration of the pause, which constitutes a freeze of user funds until the contract is unpaused.

### Likelihood Explanation
Pausing is a normal, documented mitigation the protocol uses in response to security incidents (not a malicious admin action). Any time `pause()` is invoked for a legitimate reason on `VLMGP`, `MasterMagpie`, or `WombatStaking`, all in-flight withdrawal/unlock calls from unprivileged users are blocked as a side effect, which is highly likely to occur during exactly the periods (security incidents) where users are most likely to want to exit.

### Recommendation
Decouple pause scopes: keep `whenNotPaused` on deposit-side entry points (`lock`, `lockFor`, `deposit`, `depositFor`, `depositLP`) but remove it (or use a separate `whenWithdrawNotPaused`-style flag defaulting to unpaused) from principal-withdrawal paths such as `unlock`, `cancelUnlock`, `forceUnLock` in `VLMGP.sol`, `withdraw`/`withdrawFor` in `MasterMagpie.sol`, and `withdraw`/`burnReceiptToken` in `WombatStaking.sol`.

### Proof of Concept
1. User calls `VLMGP.startUnlock(amount)` and waits `coolDownInSecs`.
2. Protocol owner calls `pause()` on `VLMGP` in response to an unrelated security concern (e.g., a deposit-side issue) [8](#0-7) .
3. User's cooldown slot is now fully matured, but calling `unlock(slotIndex)` reverts due to `whenNotPaused` [9](#0-8) , and `cancelUnlock`/`forceUnLock` are equally blocked, leaving the user with no way to retrieve their MGP until an owner-controlled `unpause()` occurs.
4. Equivalently, a user mid-way through `WombatPoolHelper.withdraw` cannot complete withdrawal if `WombatStaking` is paused, since both `withdraw` and `burnReceiptToken` require `whenNotPaused` [10](#0-9) .
