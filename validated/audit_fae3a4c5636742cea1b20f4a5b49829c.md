### Title
IBC Receive Callback Fails with Non-Standard ERC20 Tokens - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
The `IBCReceivePacketCallback` function in the `x/ibc/callbacks` module is incompatible with non-standard ERC20 tokens (like USDT) that do not return a boolean value from the `approve` function. This causes the callback to revert when interacting with such tokens, leading to failed IBC transfers or stuck funds in isolated addresses if the callback logic is bypassed or fails inconsistently.

### Finding Description
In `x/ibc/callbacks/keeper/keeper.go`, the `IBCReceivePacketCallback` function is triggered upon receiving an IBC packet with callback data. To allow the destination contract to spend the received tokens, the keeper first calls `approve` on the ERC20 contract:

```go
res, err := k.evmKeeper.CallEVM(cachedCtx, erc20.ABI, receiverHex, tokenPair.GetERC20Contract(), true, remainingGas, "approve", contractAddr, amountInt.BigInt())
if err != nil {
    return errorsmod.Wrapf(types.ErrAllowanceFailed, "failed to set allowance: %v", err)
}
``` [1](#0-0) 

After the call, it attempts to unpack a boolean return value:

```go
var approveSuccess bool
err = erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)
if err != nil {
    return errorsmod.Wrapf(types.ErrAllowanceFailed, "failed to unpack approve return: %v", err)
}
``` [2](#0-1) 

Non-standard ERC20 tokens like USDT on Ethereum do not return any value (`void`) from the `approve` function. When `UnpackIntoInterface` is called on an empty return buffer (`res.Ret`), it returns an error because it expects a boolean. This causes the entire `IBCReceivePacketCallback` to return an error and revert the transaction.

While the `x/erc20` module's `ConvertERC20` function handles empty returns by checking for the `Transfer` event, the IBC callback module strictly requires a boolean return for `approve`.

### Impact Explanation
If the `approve` call fails, the IBC receive callback reverts. Depending on the IBC middleware stack configuration, this could result in:
1. **Permanent Freezing of Funds**: If the tokens are minted/unescrowed to the `isolatedAddr` but the callback fails, the tokens remain stuck in the `isolatedAddr`. The code attempts to check for this at the end of the function, but the check itself is part of the reverting execution.
2. **Denial of Service**: Users cannot use IBC callbacks with popular non-standard tokens, breaking cross-chain contract interactions.
3. **Inconsistent State**: If the underlying IBC transfer succeeds but the callback reverts (and is not properly wrapped in a reverting atomic block by the middleware), the user might receive bank tokens instead of the expected contract execution, or worse, tokens could be lost if the middleware doesn't handle the failure gracefully.

### Likelihood Explanation
High. Many widely used tokens (USDT, BNB, etc.) are non-standard. Any IBC transfer involving these tokens and a destination callback will consistently fail.

### Recommendation
Modify the `approve` handling in `x/ibc/callbacks/keeper/keeper.go` to support tokens that return `void`. This can be done by:
1. Checking if `res.Ret` is empty.
2. If empty, treat the call as successful (standard behavior for `void` returns).
3. Optionally, verify that an `Approval` event was emitted in `res.Logs`.

Example fix:
```go
if len(res.Ret) > 0 {
    var approveSuccess bool
    err = erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)
    if err != nil || !approveSuccess {
        return errorsmod.Wrapf(types.ErrAllowanceFailed, "failed to set allowance")
    }
}
// If Ret is empty, assume success for non-standard tokens
```

### Proof of Concept
1. Register a non-standard ERC20 token (e.g., a mock USDT that returns nothing from `approve`) as a `TokenPair`.
2. Initiate an IBC transfer to the chain with a `memo` containing a `dest_callback`.
3. The `OnRecvPacket` will trigger `IBCReceivePacketCallback`.
4. The `k.evmKeeper.CallEVM(..., "approve", ...)` will succeed, but `res.Ret` will be empty.
5. `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` will return an error: `abi: unmarshalling empty output`.
6. The callback returns `ErrAllowanceFailed`, and the transaction reverts.
