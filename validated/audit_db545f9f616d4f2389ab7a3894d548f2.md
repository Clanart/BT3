### Title
Recursive clone explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard, re-enabling hook/filter execution from an attacker-controlled repository/submodules during clone - (File: app/src/lib/git/clone.ts)

### Summary
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself uses to mark that a clone (including its `--recursive` submodule initialization) is currently in progress, so that hooks, filters, and other repository-controlled executables are not inadvertently invoked on content that the local user has not yet had a chance to trust/review. GitHub Desktop's `clone()` implementation explicitly forces this variable to `'false'` on every clone, unconditionally disabling that protection for every repository (and every submodule brought in via `--recursive`) that a user clones through the app. [1](#0-0) 

### Finding Description
GitHub Desktop's clone path builds the Git invocation environment and always sets:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
```
and then runs `git ... clone --recursive -- url path`. [2](#0-1) 

`--recursive` means every submodule listed in the attacker's `.gitmodules` is fetched and checked out as part of the same operation, in a repository the user has not yet inspected, and whose config (`core.hooksPath`, filter/clean/smudge attributes, hook scripts brought in via submodule) is entirely attacker-controlled content at this point. `GIT_CLONE_PROTECTION_ACTIVE` is the guard Git added specifically to stop hooks/filters from firing during this "not-yet-trusted" window of a clone; by forcing it to `'false'`, Desktop removes that guard for every clone, including clones of arbitrary/untrusted URLs entered by the user or reached via a clicked GitHub Desktop deep link (`x-github-client://openRepo?url=...`) or "Clone repository" dialog.

This mirrors the report's broken invariant exactly: a security-relevant parameter (`GIT_CLONE_PROTECTION_ACTIVE`, analogous to Gearbox's `creditManager` params) is unilaterally overridden/upgraded away from its safe default by application code, without any validation of whether doing so is safe for the specific (attacker-supplied) input being processed. Existing guards elsewhere in `clone.ts` — `isClonePathSensitive()` (checks only the destination path against `~/.ssh`, `~/.gnupg`, etc.) — do not address this at all, since they only look at where the clone lands on disk, not at what the cloned/recursed content is allowed to execute during the clone.

### Impact Explanation
If Git's clone-time hook/filter execution protection is disabled and the app performs `--recursive` submodule initialization automatically and unconditionally as part of the standard "Clone a repository" flow, an attacker who controls the content of a repository (or any of its submodules, transitively) can potentially get code to run during the clone itself — before the user has ever opened, browsed, or reviewed the repository in Desktop. That is unprivileged remote-content-triggered code execution outside of any explicit user git-command action, satisfying the report's valid-impact bar ("attacker controls a cloned/fetched repository ... result is code execution").

### Likelihood Explanation
Cloning is the primary, most common entry point into GitHub Desktop (via URL, deep link, or "Clone repository" dialog), and `--recursive` submodule fetch happens automatically without extra user confirmation. The disabling of the protection is unconditional (not behind any feature flag or opt-in), so every clone is affected. The main source of uncertainty is that I could not find the exact Git version/behavior this environment variable maps to in this codebase (no upstream Git source or changelog is indexed here) or confirm the precise mitigation it is meant to enforce beyond the variable's self-describing name and its exclusive use at the clone call site; I also could not find any comment/justification in this file for why it is forced to `'false'` (blame/history only shows a single "Initial commit"). This should be verified against the actual Git version bundled with dugite to confirm what protection is being bypassed and whether that protection is otherwise a no-op in this app's flow.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (app/src/lib/git/clone.ts) unless there is a documented, narrow reason it's required (e.g. a specific dugite/Git version incompatibility), and if so, gate it tightly and document why it's safe.
- If the override is required for a legitimate reason (e.g. progress-parsing compatibility), scope it as narrowly as possible and add compensating controls, such as deferring `--recursive` submodule initialization until after the top-level clone has completed and been confirmed safe, rather than doing it in the same protected/unprotected window.
- Add a regression test that clones a crafted repository containing a submodule with an executable hook/filter and asserts that no such hook/filter runs during the clone.

### Proof of Concept
1. Attacker publishes a Git repository (or a repository the target is invited/linked to) containing a `.gitmodules` entry pointing to a submodule repository that itself contains a `.git` config setting `core.hooksPath`/filter attributes wired to an executable script (or a symlinked `.git` structure abusing hook execution timing), following the class of clone-time hook/filter execution issues that `GIT_CLONE_PROTECTION_ACTIVE` is designed to prevent.
2. Victim clones this URL in GitHub Desktop (via the Clone dialog or a `x-github-desktop://` clone deep link).
3. Desktop invokes `git ... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment, per `app/src/lib/git/clone.ts` lines 81-93.
4. Because the protection is disabled, the recursively-fetched submodule's hook/filter executes during the clone step, before the user has ever opened or reviewed the repository in Desktop — i.e., before any explicit "trust this content" action.

Note: I could not execute this end-to-end in this environment (no filesystem/terminal access here) to confirm the exact upstream Git payload needed to trigger execution under this flag; the concrete finding is the deliberate, unconditional disabling of the named safety mechanism at `app/src/lib/git/clone.ts:83`, which is the direct code-level analog to the report's "unrestricted change to a security-relevant parameter" bug class.

```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```
