### Title
Selfdestructed native-ERC20 token pairs are deleted without burning already-minted backing coins, creating permanently unbacked native coin supply - (File: `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/token_pairs.go`)

### Summary
The external report's core defect is a **stale-data invalidation failure**: revoking one artifact (a certificate) does not clean up dependent artifacts (its CRL), letting already-issued, now-invalid trust be used forever. The Cosmos EVM analog is in the `x/erc20` native-ERC20 token-pair lifecycle: when a `OWNER_EXTERNAL` ("native ERC20") contract backing a token pair self-destructs, the module deletes the token-pair mapping but never burns or claws back the native Cosmos coins that were already minted 1:1 against tokens escrowed in that now-destroyed contract. The liability (circulating native coin) survives while the asset (escrowed ERC20 tokens in the destroyed contract) is gone forever, producing an irreversible, permanent, unbacked coin supply — a direct accounting-corruption of spendable user value.

### Finding Description
`ConvertERC20` and `ConvertCoin` both check whether a native-ERC20 contract has been self-destructed by testing `acc.HasCodeHash()`; if the code is gone, they call `k.DeleteTokenPair(ctx, pair)` and return, treating this purely as bookkeeping cleanup: [1](#0-0) [2](#0-1) 

`DeleteTokenPair` only removes the token pair record, the ERC20↔denom index maps, and the allowances — it performs **no** interaction with the bank module and does not burn any previously minted coin of that denom: [3](#0-2) 

However, prior to self-destruction, `convertERC20IntoCoinsForNativeToken` (the ERC20→Coin direction) escrows real ERC20 tokens into the module account inside the contract and mints an equal amount of native Cosmos coin via `k.bankKeeper.MintCoins`, sending it to the receiver: [4](#0-3) 

Once the backing contract self-destructs, that escrowed balance (and the contract entirely) disappears from the EVM state, but the minted native coin remains fully spendable/transferable in the bank module — there is no invariant anywhere that ties total circulating supply of `pair.Denom` to the actual value locked in the (now-defunct) contract, and no burn is triggered on deletion. The reverse direction, `ConvertCoinNativeERC20`, cannot be used to "unwind" this because it requires calling `transfer` on the (now codeless) contract, which will fail — so the coin can never be redeemed for real backing again; it simply persists as counterfeit, unbacked value.

Additionally, the balance invariant checks used by both conversion directions rely entirely on the target ERC20 contract's own self-reported `balanceOf` values before/after a `transfer` call: [5](#0-4) [6](#0-5) 

Because `RegisterERC20` is permissionless by default (`params.PermissionlessRegistration`) and accepts any external contract address without validating the code's honesty: [7](#0-6) 

an attacker-authored contract can report whatever `balanceOf` values are needed to satisfy the "expected == actual" checks even while not moving real value, since the check queries the same untrusted contract that performed the transfer — this mirrors the report's core flaw of trusting an unvalidated/attacker-influenced data source (there: PCCS-served CRLs; here: the token contract's self-reported balances) as the sole gate for a security-critical decision.

### Impact Explanation
This breaks the core `x/erc20` invariant (see "Asset-representation path" in the audit pivots) that native coin supply of a `TokenPair` denom must remain 1:1 backed by the ERC20 tokens actually escrowed in the module account. Once a native-ERC20-backed pair's contract is destroyed, the previously minted native coin becomes permanently unbacked, functionally equivalent to unauthorized minting: the "spendable user value" in circulation is no longer collateralized by anything, and there is no mechanism (governance or otherwise) to reconcile or burn it. This is irreversible accounting corruption of spendable user value, which falls squarely under the allowed Critical impact ("unauthorized minting... or irreversible accounting corruption of spendable user value across native balances... token-pair-backed balances").

### Likelihood Explanation
Triggering self-destruction of an `OWNER_EXTERNAL` contract requires only that some account: (1) permissionlessly register an ERC20 contract as a token pair via `RegisterERC20` (unprivileged, no governance needed when `PermissionlessRegistration` is true), (2) legitimately convert some tokens to native coin via `ConvertERC20` to mint circulating supply, and (3) self-destruct the contract (a standard, unprivileged EVM operation available to the contract's deployer/owner). All three steps are fully reachable by an ordinary user through normal transaction flow with no special privileges. I was not able to fully verify within the available investigation budget whether Cosmos EVM's `x/vm` statedb permits a *new* contract to be redeployed at the exact same address after self-destruction (which would additionally let an attacker exploit the self-reported-balance weakness to keep minting further unbacked coin); the finding does not depend on that redeploy step, since the unbacked-supply corruption from steps (1)–(3) alone is sufficient and independently reachable.

### Recommendation
- **Short term**: When a native-ERC20 token pair's backing contract is found to have no code (self-destructed) in `ConvertERC20`/`ConvertCoin`, before or as part of `DeleteTokenPair`, burn (or otherwise permanently escrow/mark-unredeemable-but-accounted) the entire circulating supply of `pair.Denom`, or halt further transfers of that denom and require a governance-supervised reconciliation instead of silently deleting the mapping.
- **Long term**: Do not rely on the target ERC20 contract's own `balanceOf` return values as the sole invariant check for mint/burn/escrow operations; track expected escrow amounts in module state independent of the contract's self-reported storage, and require additional validation (e.g., contract bytecode allow-list, minimum lock, or governance vetting) before treating an externally supplied ERC20 contract as canonical 1:1 backing for a native coin.

### Proof of Concept
1. Attacker deploys a standard ERC20 contract `T`.
2. Attacker calls `MsgRegisterERC20` for `T` (permissionless), creating `TokenPair{Erc20Address: T, Denom: "erc20/T", ContractOwner: OWNER_EXTERNAL}` — `x/erc20/keeper/msg_server.go:324-350`.
3. Attacker calls `MsgConvertERC20` to convert `N` tokens of `T` into `N` native coins of `erc20/T`; `convertERC20IntoCoinsForNativeToken` escrows `N` tokens in `T` under the module address and mints `N` `erc20/T` coins to the attacker (`msg_server.go:71-152`).
4. Attacker transfers the freshly minted `N` native `erc20/T` coins to other accounts / uses them as spendable value.
5. Attacker calls `selfdestruct` on `T` from within an EVM transaction, removing its code and stored balances (the escrowed `N` tokens vanish along with the contract).
6. Attacker (or anyone) submits another `MsgConvertERC20`/`MsgConvertCoin` referencing the same pair; `GetAccountWithoutBalance(...).HasCodeHash()` returns false, so `DeleteTokenPair` fires, quietly removing the token-pair record (`msg_server.go:42-53`, `token_pairs.go:110-117`).
7. Result: the `N` native `erc20/T` coins minted in step 3 remain fully valid and transferable in the bank module forever, with zero underlying collateral and no path to reconcile or burn them — a permanent, unauthorized increase in effectively-backed circulating value.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
