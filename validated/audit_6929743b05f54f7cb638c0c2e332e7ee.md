### Title
`WombatStaking.depositLP` mints receipt tokens and stakes based on input amount instead of actual LP tokens received - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP` transfers `_lpAmount` of the pool's LP token from the caller (via a `PoolHelper` acting on behalf of `_for`) using `safeTransferFrom`, but never verifies that `_lpAmount` was actually received. It then uses the unverified `_lpAmount` both to stake into `MasterWombat` and to mint `receiptToken` 1:1 to the depositor. If the LP token (or any token configured as `poolInfo.lpAddress`) is deflationary/fee-on-transfer or a rebasing token, the custodian contract receives less than `_lpAmount`, yet mints receipt tokens and records stake as if the full amount was received.

### Finding Description
In the `deposit` function (non-LP path), the code is careful: it measures `lpReceived` via a balance-diff after calling the Wombat pool's own deposit (`beforeBalance`/`afterBalance`), and mints receipt tokens using that verified value: [1](#0-0) 

However, `depositLP` skips this check entirely. It transfers `_lpAmount` from `_for` via `safeTransferFrom`, but then uses the raw, unverified `_lpAmount` to both stake into MasterWombat (through `_toMasterWomAndSendReward`) and mint receipt tokens 1:1: [2](#0-1) 

`safeTransferFrom` (OpenZeppelin `SafeERC20`) only reverts on failure — it never checks that the recipient's balance actually increased by `_lpAmount`. If `poolInfo.lpAddress` is a fee-on-transfer or rebasing token, `WombatStaking` receives strictly less than `_lpAmount`, but:
1. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints the full, unadjusted amount of receipt tokens, over-crediting the depositor relative to actual custodied LP balance.
2. `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` stakes `_lpAmount` (not the actual received balance) into `MasterWombat` via `_stakeToWombatMaster`, which approves and calls `IMasterWombat(masterWombat).deposit(poolInfo.pid, _lpAmount)`: [3](#0-2) 

This exactly matches the reported bug class ("loan/pool custodian contracts do not check that the expected amount has been sent on transfer"), applied here to `WombatStaking`'s LP custody accounting rather than `TickLogic.sol` directly (which does not exist in this repo — this is the closest reachable analog: LP-token custody + receipt-token minting logic).

### Impact Explanation
Over-minting receipt tokens relative to actual custodied LP balance breaks the 1:1 backing invariant between `receiptToken` supply and real assets held by `WombatStaking`. Since receipt tokens are burned 1:1 on withdraw (`burnReceiptToken`) and withdrawals pull real underlying tokens out of the pool, later depositors/withdrawers may be unable to redeem their full receipt-token balance once the shortfall accumulates — i.e., protocol insolvency for the affected pool, satisfying the "protocol insolvency" impact criterion.

### Likelihood Explanation
This requires the pool's `lpAddress` (a Wombat LP token) to actually be deflationary/fee-on-transfer/rebasing. Standard Wombat LP tokens are not fee-on-transfer today, so likelihood under current configured pools is low; however the vulnerability is directly reachable by any ordinary user calling `depositLP` through a `PoolHelper` — no privileged role is required — and the code contains no defensive balance check, unlike the sibling `deposit` function which does it correctly. This is a real code-level omission, not merely a hypothetical about an external protocol.

### Recommendation
In `depositLP`, measure the actual LP amount received via a `balanceOf` diff before/after the `safeTransferFrom` (mirroring the pattern already used in `deposit`), and use that verified amount for both `_toMasterWomAndSendReward` and the receipt-token `mint` call, instead of the caller-supplied `_lpAmount`.

### Proof of Concept
1. Configure a pool in `WombatStaking` whose `lpAddress` takes a transfer fee (e.g., 1%).
2. A user calls `depositLP(lpAddress, 100e18, user)` through the corresponding `PoolHelper`.
3. `safeTransferFrom` moves only 99e18 tokens into `WombatStaking` (1e18 taken as fee), but:
   - `_stakeToWombatMaster` attempts to stake 100e18 into `MasterWombat` (approval covers it since approve is set to `_lpAmount`, but actual balance held is only 99e18) — this would revert if the pool token itself checks balance, otherwise it stakes with insufficient real backing;
   - `receiptToken.mint(user, 100e18)` mints a full 100e18 receipt tokens regardless.
4. Now total `receiptToken` supply exceeds actual LP custodied by 1e18 for every such deposit, so aggregate withdrawals will eventually fail for the last claimants, demonstrating insolvency of the pool's accounting.

    function depositLP(
        address _lpAddress,
        uint256 _lpAmount,
        address _for
    ) nonReentrant whenNotPaused _onlyActivePoolHelper(_lpAddress) external {
        // Get information of the Pool of the token
        Pool storage poolInfo = pools[_lpAddress];

        // Transfer lp to this contract and stake it to wombat
        IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount);

        _toMasterWomAndSendReward(_lpAddress, _lpAmount, true); // triggers harvest from wombat exchange
        IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount);

        emit NewLPDeposit(_for, poolInfo.lpAddress, _lpAmount, poolInfo.receiptToken, _lpAmount);
    }
