### Title
Full-balance sweep of non-registry tokens in `compound()` lets any caller claim previously stranded dust - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` sweeps non-compoundable reward tokens back to `msg.sender` by reading the entire `balanceOf(address(this))` for any token address the caller supplies in `_rewards`, rather than tracking the amount actually attributable to that specific caller's claim. Any dust left behind by a previous `compound()` call (rounding, a `convertor`/`helper` that does not fully consume the `safeApprove`d amount, or a token that is claimed but never routed through a locker/convertor/helper) accumulates as raw ERC20 balance on the contract and is fully claimable by the next unrelated caller.

### Finding Description
In `compound()`, the first loop iterates over the caller-supplied `_rewards[i][j]` token addresses and, for any address not present in `compoundableRewards`, does: [1](#0-0) 
```
if (!compoundableRewards[_rewards[i][j]]) {
    uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
    if (rewardBalance > 0)
        IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
}
```
This reads the contract's *entire* balance for that token and sends it to `msg.sender`, with no bookkeeping of what portion of that balance was produced by this caller's own `multiclaimOnBehalf` call versus dust left over from a prior, unrelated caller's `compound()` invocation.

Dust can legitimately accumulate in the second loop, which handles registered `rewards[i]` entries: [2](#0-1) 
Here, `receivedBalance` is approved in full to a `_convertor`, `_locker`, or `_helperAddress`, but nothing in `ManualCompound.sol` guarantees those external contracts consume the full approved amount — a partial convert, a helper that only deposits up to a cap, or a locker with minimum/maximum constraints can all leave a remainder sitting on the contract as raw ERC20 balance, since `safeApprove` only sets an allowance, and any unspent amount stays in `ManualCompound`.

Because the sweep loop in the first block keys purely off `IERC20(token).balanceOf(address(this))`, any subsequent caller can name that same token address in their own `_rewards` array (as long as it is not registered in `compoundableRewards`) and immediately claim the whole balance — including dust that rightfully belongs to a prior compounder — without having contributed it. There is no per-user accounting, escrow, or "snapshot before/after this call's claim" mechanism to isolate the amount actually claimed on the current caller's behalf from previously stranded balance.

### Impact Explanation
This is a direct theft-of-funds vector: value belonging to a previous compounder (via rounding/under-consumption in convert/lock/deposit helpers) is not attributed to that user but instead sits as unowned contract balance, fully sweepable by the next arbitrary caller who merely knows the token's address and passes it in `_rewards`. This matches Immunefi's "Critical – Direct theft of user funds" class, since an unprivileged EOA with no special role can extract value that does not belong to them.

### Likelihood Explanation
Preconditions are modest: an attacker only needs (a) some reward token to have left dust on the contract from a prior compound (plausible whenever `convertor`/`locker`/`helper` integrations don't consume 100% of the approved amount, or whenever rounding occurs), and (b) to call `compound()` naming that token's address in a `_rewards[i]` inner array while it remains outside `compoundableRewards`. No capital is required beyond gas, and the exploit is repeatable every time dust reappears. The main uncertainty is how strictly `IMasterMagpie.multiclaimOnBehalf` validates the `_lps`/`_rewards` correspondence to actual claimable rewards for the caller — this could not be fully confirmed from the available `MasterMagpie.sol` contents, but the vulnerable sweep logic itself does not depend on that validation succeeding for the "non-compoundable" branch, since it operates purely on `balanceOf(address(this))` regardless of what (if anything) was actually claimed in that same transaction.

### Recommendation
Do not use raw `balanceOf(address(this))` as the sweep amount for non-compoundable tokens. Instead, snapshot the token's balance immediately before calling `multiclaimOnBehalf` and again after, and only transfer the delta (this call's own claimed amount) to `msg.sender`. For the compoundable-token loop, apply the same before/after delta pattern and route any leftover balance after the convertor/locker/helper interaction into a per-user or per-token accounting structure (a dust reserve mapping) that a legitimate owner can withdraw later, rather than leaving it as anonymous claimable balance.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie`, a mock reward token `TOKEN_A` registered via `addReward` with a mock `convertor` that only consumes 90% of the approved amount (simulate an under-consuming helper).
2. User A calls `compound()` with `_lps`/`_rewards` such that `masterMagpie.multiclaimOnBehalf` sends 100 `TOKEN_A` to `ManualCompound`; after the convertor call, assert `IERC20(TOKEN_A).balanceOf(ManualCompound)` is 10 (dust) and User A received the converted output.
3. Deploy/impersonate an unrelated attacker EOA with no stake and no role. Have the mock `masterMagpie.multiclaimOnBehalf` be callable by anyone with an empty/zero claim result for arbitrary `_lps`.
4. Attacker calls `compound(_lps=[dummyLp], _rewards=[[TOKEN_A]], ...)` where `TOKEN_A` is not in `compoundableRewards` for that mock configuration (or use a second token `TOKEN_B` left as dust that was never added to `compoundableRewards`).
5. Assert that `IERC20(TOKEN_A).balanceOf(attacker)` increases by the full 10 dust tokens and `IERC20(TOKEN_A).balanceOf(ManualCompound)` goes to 0, even though the attacker contributed nothing to that balance — i.e., `balanceOf(address(this))` before the attacker's call is inconsistent with the attacker's actual share (0), and the invariant "residual value must be attributed to its owner" is violated.
