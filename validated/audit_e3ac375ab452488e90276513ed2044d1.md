### Title
Conflict-hunk index desync between `extractConflictHunks` and `reassembleResolvedFile` can splice AI-generated resolutions into the wrong location, silently corrupting a commit - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Solady report is a "fixed-layout field placed at the wrong offset" bug: one function (`encodeMode`) writes a field at a byte offset that a sibling function (`getSelector`) does not read from, so decode silently returns the wrong bytes even though both sides individually look internally consistent. The Desktop analog is the same class of defect at the source level: the AI conflict-resolution pipeline builds a fixed-position index of conflict "hunks" with one parser (`extractConflictHunks`) and later re-derives that same fixed-position index with a second, independently-written parser (`reassembleResolvedFile`) when splicing the model's answer back in. Both parsers use the same marker regexes but different control flow for handling malformed/edge-case marker sequences, so the two "encodings" of hunk position can disagree on attacker-shaped input, exactly mirroring the report's root cause: two halves of a protocol that must agree on field/record placement, but don't.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks a conflicted file once and builds the ordered `IConflictHunk[]` that is (a) shown to Copilot in the prompt as "Conflict 1 of N", "Conflict 2 of N" (`app/src/lib/copilot-conflict-context.ts:560-562`) and (b) used as the expected hunk count for validation (`validateResolutionPaths`, `app/src/lib/copilot-conflict-resolution.ts:473-521`).

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) later re-scans the *same raw file content* from scratch with its own marker-matching loop, and matches the model's `hunks[]` array to conflict blocks purely **by discovery order** (`hunkIndex`), not by any content-derived key: [1](#0-0) 

This is architecturally identical to the report's flaw: `encodeMode`/`getSelector` are two independent encode/decode routines that must agree on a byte offset, and the bug arose because they didn't. Here, "offset" is replaced by "hunk index" and the two routines are `extractConflictHunks` (build time) vs. `reassembleResolvedFile` (splice time). The two loops differ subtly on malformed input:

* `extractConflictHunks` aborts its *entire* scan and drops all remaining hunks the first time an opened `<<<<<<<` marker never finds a closing `>>>>>>>` before EOF (`app/src/lib/copilot-conflict-context.ts:228-241`), because its cursor `i` is already run to `lines.length` by the inner collection loops.
* `reassembleResolvedFile` treats that same unclosed/malformed marker as ordinary content and keeps scanning forward (`app/src/lib/copilot-conflict-resolution.ts:574-579`), so it can still detect and index conflict blocks that occur *after* the point where `extractConflictHunks` gave up.

Since the conflicted file's raw text is attacker-influenced (it is the literal merge result of the victim's branch and an attacker-authored branch/PR that the victim merges, rebases, or cherry-picks through Desktop), an attacker who controls one side of the merge can shape the conflicting file so that an early, deliberately unclosed marker-like sequence causes `extractConflictHunks` to see fewer/different hunks than `reassembleResolvedFile` will see when re-scanning the same bytes at splice time. Because the model only ever sees and answers for the hunks `extractConflictHunks` reported, and `reassembleResolvedFile`'s independent re-count is what actually determines where each answer gets spliced, the two counts/positions can desync, causing a resolution meant for one hunk to be written into the location of a different hunk-shaped block in the file.

### Impact Explanation
If the index used to write the model's answer back into the file does not correspond to the index used to ask the model the question, the tool can silently splice unrelated resolved content into the wrong place in the file, or splice content into a position that isn't actually part of a real conflict. The resulting file has no remaining triple-marker sequences (so it looks "resolved" to the user and to Desktop's own status detection), but the code it contains is not what the user reviewed or intended — a direct instance of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires (1) the user to have GitHub Desktop's AI-assisted conflict resolution feature enabled and invoked, and (2) a merge/rebase/cherry-pick against attacker-influenced content that produces a conflicted file shaped to trigger the parser divergence. It is not a trivial one-line PoC and I was not able to dynamically execute the two parsers against a crafted fixture to conclusively prove the exact desync in this pass — this is a structural/code-review-level finding based on reading both implementations, not a confirmed exploit trace.

### Recommendation
Replace the order-based (`hunkIndex`) matching in `reassembleResolvedFile` with a single, shared hunk-extraction routine reused by both the context-building path and the reassembly path (i.e., call `extractConflictHunks` once, keep the exact line ranges/positions it identified, and splice resolutions back into those recorded positions instead of re-deriving positions with a second, differently-behaved scanner). This guarantees the same "offset" (hunk position) is used for both the prompt/validation side and the write-back side, closing the class of bug described in the report.

### Proof of Concept
Not independently verified end-to-end in this pass (no execution environment available). Conceptually:
1. Attacker crafts a file on their branch containing an unclosed `<<<<<<<`-shaped line followed later by a legitimate conflicting section, so that when merged with the victim's branch it produces a raw file where `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) stops early / miscounts hunks relative to what `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) will find when re-scanning the same text.
2. Victim merges/rebases via Desktop and invokes AI conflict resolution.
3. The model answers based on the (wrong) hunk list from step 1; `reassembleResolvedFile` splices those answers into positions computed independently, causing a mismatch.
4. Victim commits the "resolved" file without noticing the swapped/incorrect content, since no conflict markers remain. [2](#0-1) [3](#0-2)

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
