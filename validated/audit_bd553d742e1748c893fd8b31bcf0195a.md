### Title
Quadratic Lagrange interpolation DoS in `ThresholdKeys::read` / `ThresholdKeys::new` — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` (a `u16`, up to 65,535) and then calls `ThresholdKeys::new`, which computes the group key by summing `interpolation_factor(i, t)` for all `t` participants. With `Interpolation::Lagrange`, each factor is a linear pass over the `t` included indexes, so deserialization of a single untrusted byte string triggers O(t²) ≈ 4.3 billion field multiplications plus `t` scalar-point multiplications — super-linear work on a linear-size input, the same bug class as CVE-2025-27219.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` directly from the input and reads `n` scalars/points from the byte stream, then delegates to `ThresholdKeys::new`: [1](#0-0) 

`ThresholdKeys::new` computes `group_key` as a sum over participants `1..=t`, each term evaluating `interpolation_factor(*i, &t)`: [2](#0-1) 

`interpolation_factor` for `Interpolation::Lagrange` iterates over the entire `included` list per call, giving O(t²) field work overall: [3](#0-2) 

`ThresholdParams::new` imposes no upper bound on `n`/`t` beyond `u16`: [4](#0-3) 

The same quadratic pattern reappears in `ThresholdKeys::view`, which computes `interpolation_factor` for every participant in `included` (length up to `n`): [5](#0-4) 

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (a path explicitly in scope) causes ~4.3 billion field multiplications and 65,535 point multiplications from a ~4 MB input, hanging the parsing thread. Any node deserializing key material received over the wire (DKG/commitments flows in `dkg/pedpop`) before validating its provenance is exposed to a single-message CPU exhaustion attack. The work is quadratic-to-cubic in attacker-controlled length, satisfying the same CWE-400/CWE-770 class as the reference advisory.

### Likelihood Explanation
The parser performs the expensive group-key computation unconditionally inside `ThresholdKeys::new` — there is no cheap pre-validation that avoids it. A crafted input only needs a valid `C::ID`, `t = n = 65535`, `i = 1`, `Interpolation::Lagrange`, and `n` well-formed `read_F`/`read_G` encodings. Whether a production path actually feeds unauthenticated remote bytes to `ThresholdKeys::read` depends on the integrator; the quadratic algorithm is concretely present regardless.

### Recommendation
- Cap `n`/`t` at deserialization to a sane protocol bound (e.g., `MAX_KEY_SHARES_PER_SET`) before doing any interpolation work.
- Compute Lagrange denominators once (prefix/suffix products or batch inversion) so `group_key` derivation is O(t log t) or O(t) instead of O(t²).
- Consider computing `group_key` lazily or via a single `multiexp` over precomputed coefficients rather than per-participant interpolation loops.

use ciphersuite::Ciphersuite;
use dalek_ff_group::Ed25519;
use dkg::ThresholdKeys;

fn poc() {
  let n: u16 = u16::MAX;
  let mut buf = vec![];
  // C::ID
  buf.write_all(&(<Ed25519 as Ciphersuite>::ID.len() as u32).to_le_bytes()).unwrap();
  buf.write_all(<Ed25519 as Ciphersuite>::ID).unwrap();
  // t = n = u16::MAX, i = 1
  buf.write_all(&n.to_le_bytes()).unwrap();
  buf.write_all(&n.to_le_bytes()).unwrap();
  buf.write_all(&1u16.to_le_bytes()).unwrap();
  // Interpolation::Lagrange
  buf.write_all(&[1u8]).unwrap();
  // secret_share
  buf.write_all(<Ed25519 as Ciphersuite>::F::ONE.to_repr().as_ref()).unwrap();
  // n verification shares (all generator, for well-formedness)
  for _ in 1 ..= n {
    buf.write_all(<Ed25519 as Ciphersuite>::generator().to_bytes().as_ref()).unwrap();
  }
  // ~4.3e9 field muls + 65535 point muls inside ThresholdKeys::new
  let _ = ThresholdKeys::<Ed25519>::read(&mut buf.as_slice());
}
