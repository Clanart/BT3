## Analysis

The bug-class in H‑06 is: a contract accrues value that belongs to a specific party, but a structural gap in the code lets that value be permanently forfeited instead of ever reaching its rightful owner. The closest local analog in Hyperbridge is in `pallet-bandwidth`'s prepaid subscription ledger.

### Root cause

`pallet-bandwidth` stores prepaid bandwidth as a **FIFO, capacity-bounded list** per `(app_chain, app)` key: [1](#0-0) 

Every purchase appends a subscription via `push_subscription`. When the list is already at the 1024-entry cap, the **oldest, still-unconsumed** subscription is silently evicted and its remaining bytes are lost: [2](#0-1) 

The event doc comment even states plainly: *"`lost_bytes` is what the user paid for and won't get to use."* [3](#0-2) 

### The exploitable gap

The `(app_chain, app)` key that selects *which* queue a purchase lands in is **fully attacker-controlled** — it comes straight from the purchase message body, and by design any chain can "sponsor" any app on any other chain: [4](#0-3) 

On the EVM side, `BandwidthManager.purchase()` is a fully public, unprivileged entrypoint where the caller freely chooses `app` and `chain`: [5](#0-4) 

This is explicitly documented as the intended "sponsorship" feature — *"any deployment can sponsor any app on any chain"* and *"chain ... does not need to equal the source chain."* Combined with the FIFO eviction rule, this turns a self-service top-up feature into a cross-account griefing primitive: any unprivileged account can repeatedly call `purchase()` targeting a **victim's** `(app_chain, app)` pair with the cheapest configured tier, filling and overflowing the victim's 1024-slot queue and evicting the victim's own legitimate, unconsumed, higher-value subscription — destroying bandwidth the victim already paid real fee-token for, with no way to recover it (`BandwidthGate::try_consume` only drains from the front; there's no re-credit path once `SubscriptionEvicted` fires).

### Why existing guards don't stop it

- `BandwidthManager::<T>::get(&request.source)` only authenticates *which contract* sent the message, not *whose app* the message targets — `app`/`chain` are payload fields, not derived from `msg.sender`.
- There is no per-app rate limit, no minimum "own-purchase" ownership check, and no cap on how many entries a single external payer can push into another app's queue.
- The 1024 cap and FIFO-evict behavior are unconditionally applied to every push, including attacker-originated ones aimed at a third party's key.

This satisfies the bounty's "loss of funds" / "logic attack" gate: an unprivileged caller of a public entrypoint (`purchase()`) can force permanent, uncompensated loss of another account's already-paid-for allowance purely through normal message flow — no malicious relayer, prover, or governance actor required.

### Recommendation

Bind subscription slots to the paying entity as well as the app key (e.g. require `request.from`/payer identity match for any push beyond a self-serve quota), or replace the hard FIFO-evict-oldest rule with a per-`(payer, app_chain, app)` sub-bucket so a third party's purchases cannot displace another party's unconsumed bytes. At minimum, reserve some evict-immunity window for freshly credited, high-remaining-byte subscriptions, and/or emit a way to refund/reclaim evicted value rather than destroying it silently.

### Title
Unprivileged bandwidth-purchase griefing lets an attacker evict a victim app's paid, unconsumed subscription — `pallet-bandwidth` (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores prepaid bandwidth per `(app_chain, app)` in a FIFO list capped at 1024 entries (`MAX_SUBSCRIPTIONS`). Pushing past the cap evicts the oldest subscription and destroys its remaining, already-paid-for bytes. Because the `(app_chain, app)` key that a purchase targets is fully attacker-controlled through the public `BandwidthManager.purchase()` entrypoint (the "sponsorship" feature explicitly allows any chain/account to credit any app), any unprivileged account can spam cheap purchases against a victim's key to force-evict the victim's legitimate, higher-value, unconsumed subscription.

### Finding Description
- `push_subscription` unconditionally evicts `list[0]` once a `(app_chain, app)` row hits 1024 entries and emits `SubscriptionEvicted` with the lost bytes: [2](#0-1) 
- The `(app_chain, app)` key comes from the purchase message body (`msg.chain`, `msg.app`), which the caller of `BandwidthManager.purchase()` chooses freely: [4](#0-3) 
- `BandwidthManager.purchase()` on EVM is a fully public function with no relationship required between `msg.sender` and the `app`/`chain` arguments: [5](#0-4) 
- The only authentication performed on inbound purchase messages is that the sending contract matches the registered `BandwidthManager` for its source chain — never that the payer is authorized to write into the specific `app` bucket being targeted: [6](#0-5) 

### Impact Explanation
An attacker can permanently destroy bandwidth that a victim app already paid for (in ERC-20 fee tokens) and hasn't yet consumed, purely by calling a public, unprivileged entrypoint with the victim's `app`/`chain` identifiers. This is a direct "loss of funds" outcome reachable without any relayer, prover, or governance compromise — matching the required impact class.

### Likelihood Explanation
Feasible for any unprivileged account today: no role, key, or trust assumption beyond paying the (governance-set) tier price is required. The number of purchases needed to force an eviction shrinks as the victim's own queue naturally fills (through normal repurchases or sponsorship), and an attacker can watch on-chain `BandwidthCredited`/`SubscriptionEvicted` events to time the cheapest possible griefing purchase. The floor cost is bounded only by the cheapest governance-configured tier price, not by any protocol-level protection.

### Recommendation
Scope eviction protection to the payer: require that only the account/contract that owns an `(app_chain, app)` slot (or an allowlisted sponsor) can push into it beyond some free quota, or key subscriptions by `(payer, app_chain, app)` sub-buckets instead of a single shared FIFO queue that any third party can write into. Consider also exempting subscriptions with significant remaining, non-expired bytes from eviction, or providing a compensation/refund event path when eviction is forced by a non-owning payer.

### Proof of Concept
1. Victim's app buys a high-value tier (e.g. TierFour, 8 MB) via `BandwidthManager.purchase(app=VictimApp, tier=4, months=1, chain=VictimChain)`. This lands as the sole/oldest entry in `Allowance[VictimChain][VictimApp]`.
2. Attacker (any unrelated account, no special role) repeatedly calls `BandwidthManager.purchase(app=VictimApp, tier=1 /* cheapest */, months=1, chain=VictimChain)` from any source chain with a registered manager, each time incrementing the same `(VictimChain, VictimApp)` row.
3. Once the row reaches 1024 entries, the next attacker purchase pushes past the cap; `push_subscription` evicts `list[0]` — the victim's untouched 8 MB tier — and emits `SubscriptionEvicted { app_chain: VictimChain, app: VictimApp, tier: TierFour, lost_bytes: <victim's remaining bytes> }`.
4. The victim's paid-for bandwidth is gone; `BandwidthGate::try_consume` no longer sees it, and there is no refund or compensation mechanism.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
