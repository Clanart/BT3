### Title
Panic on untrusted DKG messages via `assert!`/unchecked map indexing in PedPoP encryption layer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The original report describes `assert`/`expect` being used to enforce invariants over data produced by an untrusted (sandboxed) process, letting an attacker crash the host with malformed state changes. The same class exists in Serai's PedPoP DKG encryption layer: messages received from other participants over the wire are processed by `Decryption::register` and `Decryption::decrypt_with_proof`, which use `assert!` and unchecked `HashMap` indexing on attacker-influenced data rather than returning errors.

### Finding Description
`Decryption::register` (crypto/dkg/pedpop/src/encryption.rs:351-362) enforces "each participant registers an encryption key at most once" with a panicking assert:

```rust
pub(crate) fn register<M: Message>(&mut self, participant: Participant, msg: EncryptionKeyMessage<C, M>) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

The `EncryptionKeyMessage` argument is built from `EncryptionKeyMessage::read` (crypto/dkg/pedpop/src/encryption.rs:57-59), which deserializes bytes received from remote participants (`M::read` + `C::read_G`). The `participant` index is protocol-controlled metadata derived from which sender the message is attributed to. If the PedPoP caller ever feeds a second registration message for the same `Participant` into `register` (e.g., a duplicated or replayed sender message reaching this point before/during deduplication), the `assert!` fires and aborts the host process instead of returning an error.

Additionally, `decrypt_with_proof` (crypto/dkg/pedpop/src/encryption.rs:381-392) indexes `self.enc_keys[&decryptor]`:

```rust
&[self.enc_keys[&decryptor], *proof.key],
```

`HashMap`'s `Index` impl panics on a missing key. `decryptor` is a `Participant` taken from the blame/decryption protocol flow, and `proof` is an `EncryptionKeyProof` deserialized from untrusted bytes via `EncryptionKeyProof::read` (crypto/dkg/pedpop/src/encryption.rs:267-269). A message attributing a decryption request to a participant index that never registered an encryption key — or for which registration was skipped — panics the process rather than producing `DecryptionError`.

Both sites mirror the reported bug class exactly: `assert`/panicking-index invariants applied to data derived from messages an unprivileged remote party can cause to be processed, where the correct behavior is to reject the input with an error (as `DecryptionError` already exists for the adjacent failure modes).

### Impact Explanation
A malicious DKG participant (or any party able to get a crafted/replayed PedPoP message processed by a victim) can crash the victim's node process during key generation or during the blame/decryption flow. In a validator deployment this is a remote denial of service that can halt the DKG ceremony and knock validators offline — analogous to the replica panic in the source report. No secret material is required, and no proof needs to verify: the panic happens before or independent of any cryptographic check (`register` asserts before inserting; `decrypt_with_proof`'s map index is evaluated while building the DLEq verification statement, so the panic precedes `dleq.verify`).

### Likelihood Explanation
Reachability is moderate and depends on the PedPoP caller's message routing: `register` panics only if the same `Participant` is registered twice, and `decrypt_with_proof` panics only if a `decryptor` index has no entry in `enc_keys`. If upstream code (e.g., a `validate_map`-style check in crypto/dkg) guarantees exactly-once registration keyed strictly by declared sender, the `register` assert is defense-in-depth rather than directly triggerable; however, the `enc_keys[&decryptor]` index in the blame path is only populated for participants whose registration messages were successfully processed, so a decryption/blame message referencing an unregistered participant reaches the panic directly. Determining exact upstream dedup coverage requires reading the PedPoP caller in crypto/dkg/pedpop/src/lib.rs, which was not fully verified in this analysis.

### Recommendation
- Replace the `assert!` in `Decryption::register` with a returned error (extend `DecryptionError` or introduce a `RegistrationError::AlreadyRegistered`) so duplicate/replayed registration messages are rejected, not fatal.
- Replace `self.enc_keys[&decryptor]` in `decrypt_with_proof` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`.
- Audit the rest of the DKG/frost crates for panicking constructs (`assert!`, `unwrap`, `expect`, unchecked `HashMap`/`Vec` indexing) applied to values derived from `read`/`read_G`/`read_F`/`EncryptedMessage::read`/`EncryptionKeyProof::read` inputs, per the report's long-term recommendation.

### Proof of Concept
Conceptual (assuming `C` is any in-scope ciphersuite such as `Ristretto`):

1. Registration panic: build two `EncryptionKeyMessage<C, M>` values with `EncryptionKeyMessage::read` from attacker-controlled byte streams, then call `Decryption::register(participant, msg1)` followed by `Decryption::register(participant, msg2)` with the same `Participant`. The second call hits `assert!(!self.enc_keys.contains_key(&participant))` at crypto/dkg/pedpop/src/encryption.rs:356-359 and aborts the process.

2. Blame-path panic: construct a `Decryption<C>` with a registered key only for participant 1. Call `decrypt_with_proof(from, decryptor = Participant(2), msg, Some(proof))` where `proof` is any structurally valid `EncryptionKeyProof` (e.g., via `EncryptionKeyProof::read` over well-formed encodings — the DLEq need not verify). Evaluation of `self.enc_keys[&decryptor]` at crypto/dkg/pedpop/src/encryption.rs:388 panics on the missing key before `dleq.verify` runs, so no valid proof is needed to trigger the crash.
