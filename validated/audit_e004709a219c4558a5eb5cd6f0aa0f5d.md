### Title
`ReceivedOutput::read` accepts an attacker-supplied `offset`/`output`/`outpoint` tuple with no binding between them, so an untrusted `ReceivedOutput` can claim funds under an offset/script pair that does not correspond to the multisig's spendable keys - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is "a privileged/identity parameter taken from caller input instead of being derived from the trusted source (`msg.sender`), so downstream privileged operations (mint/burn) operate on the wrong entity." In `bitcoin-serai`, the analogous construct is `ReceivedOutput`: it is the wallet's record that "the multisig received a spendable output", and the scalar that determines *which* derived key can spend it (`offset`) is deserialized verbatim from the reader, alongside the claimed `TxOut` and `OutPoint`, with zero consistency checks. The only place the offset is ever cross-checked against the script is much later, inside `SignableTransaction::multisig` — so any consumer that credits deposits from a deserialized `ReceivedOutput` reports funds as received which are not spendable.

### Finding Description
`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs:122-134` reads three independent, attacker-controlled fields:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

- `offset` is the scalar such that the output is spendable by `group_key + offset*G` (`wallet/mod.rs:91-92`, `send.rs:276-281`).
- `output.script_pubkey` is what proves (to `multisig`) that the offset is correct.
- `outpoint` and `output.value` are what the transaction builder trusts for funding (`send.rs:175-185`).

No check ties these together at parse time. A legitimately produced `ReceivedOutput` from `Scanner::scan_transaction` (`wallet/mod.rs:199-214`) is always internally consistent — the offset was registered via `register_offset` so `script_pubkey == p2tr(group_key + offset*G)`. But a `ReceivedOutput` reconstituted via `read` has no such guarantee. The constructor analog is exact: just as `WrappedAvail`'s `bridge` was set from `_bridge` rather than `msg.sender`, a consumer's "who can spend this" scalar is set from wire bytes rather than derived from the script.

The consistency check that does exist is deferred to `SignableTransaction::multisig` (`send.rs:273-285`):

```rust
let offset = keys.clone().offset(self.offsets[i]);
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
  None?;
}
```

This only runs when a spend is attempted, and it returns `None` ("wrong keys") — i.e., it merely refuses to sign. Anything that credited the claimed `output.value` at parse/report time has already recorded unspendable funds.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (explicitly an in-scope untrusted-bytes sink) can cause funds to be reported received that are not spendable:

1. **Phantom/misattributed deposit.** Set `output.script_pubkey = p2tr(A)` for an attacker key `A` (or any script), pick any `offset`, and point `outpoint` at anything. A consumer trusting the object as "multisig received `value` sats" credits a deposit that either doesn't exist, is already spent, or pays to a key the multisig cannot derive — mints against it cannot ever be burned/spent back out.
2. **Inflated value.** Keep a real multisig `outpoint`/`script_pubkey` but inflate `output.value`: `input_sat` in `SignableTransaction::new` (`send.rs:175`) is taken from the claimed `TxOut`, so payment/fee sufficiency checks pass against funds that do not exist on-chain.
3. **Silent offset/script mismatch.** A valid multisig `script_pubkey` paired with an inconsistent `offset` is only detected at spend time, stranding the deposit (direct analog of "if `bridge` is incorrect you can't burn or mint").

The signature itself can't be forged (the multisig check plus `Prevouts::All` sighash binding prevent signing a spend of a script that isn't `p2tr(group_key + offset)`), which caps severity at Medium — matching the source report.

### Likelihood Explanation
Reachable whenever serialized `ReceivedOutput`s cross a trust boundary — e.g., outputs persisted by a scanner and re-read (`ReceivedOutput::read`/`write` exist precisely for that round-trip, `wallet/mod.rs:120-148`), or outputs relayed between components. The attacker needs only to supply bytes, per the threat model; they do not need to be a validator or signer. Exploitation requires a consumer to credit/report the output before `multisig()` validates it, which is the natural usage pattern (scan/report now, spend later).

### Recommendation
Bind the offset to the script at the earliest trust boundary instead of trusting it:

- Have `ReceivedOutput::read` (or a new `ReceivedOutput::read_for(key, r)`) take the base `group_key` and reject bytes where `p2tr_script_buf(key + G*offset) != output.script_pubkey` or the resulting point isn't even — mirroring the fix "set `bridge` from `msg.sender`" by deriving the authorization parameter rather than accepting it.
- Alternatively, store/transmit only `(outpoint)` plus the registered-offset index and re-derive `offset`/`TxOut` from the scanner's `scripts` map (`wallet/mod.rs:153-196`) rather than deserializing them.
- Document that a `ReceivedOutput` obtained via `read` is unauthenticated until `SignableTransaction::multisig` succeeds, if the wire format must stay unchanged.
