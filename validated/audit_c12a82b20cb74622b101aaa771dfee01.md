### Title
Front-runnable `approve()` in `CW20ERC20Pointer` allows a malicious spender to drain more ERC20/CW20 tokens than the owner intended - (File: `contracts/src/CW20ERC20Pointer.sol`)

### Summary
`CW20ERC20Pointer.sol` wraps a CosmWasm CW20 token as an ERC20-compatible contract so that EVM users and contracts can interact with it. Its `approve()` implementation does not simply set the allowance; it queries the *current, live* allowance and issues a relative `increase_allowance`/`decrease_allowance` message on the underlying CW20 contract to reach the caller-specified target. Because the delta is computed from allowance state that can be mutated by the spender between transaction submission and inclusion, a malicious spender can front-run an owner's `approve()` call to spend the old allowance and then still receive the newly approved amount on top of it — the classic unbounded "approve race condition," here reachable by any EVM transaction sender through a pointer contract that is part of the production CW↔EVM bridge.

### Finding Description
`approve()` in `CW20ERC20Pointer.sol` computes the amount to add/remove based on a live query of the current allowance rather than atomically overwriting it or enforcing an "old value must match" precondition: [1](#0-0) 

```
function approve(address spender, uint256 amount) public override returns (bool) {
    if (amount > type(uint128).max) amount = type(uint128).max;
    uint256 currentAllowance = allowance(msg.sender, spender);
    if (currentAllowance > amount) {
        // decrease_allowance by (currentAllowance - amount)
    } else if (currentAllowance < amount) {
        // increase_allowance by (amount - currentAllowance)
    }
    return true;
}
```

`allowance()` itself is a live query against the underlying CW20 contract via the Wasmd precompile: [2](#0-1) 

Because the amount actually written to CW20 state is derived from `allowance(msg.sender, spender)` at the moment the transaction executes (not at the moment the owner decided on the new value), a spender who observes a pending `approve()` transaction lowering (or raising) their allowance can front-run it: consume the old allowance via `transferFrom` first, so that when the owner's transaction is applied it computes a delta from an allowance that has already been (partially) spent, granting the spender additional allowance on top of what was already transferred. This mirrors the report's root cause — a value that is not fully controlled by the caller (a live, externally-mutable state read) is trusted and used directly to move/authorize tokens, without enforcing the maximum total exposure the owner intended.

### Impact Explanation
An IP-owner-analog (a malicious spender who is also the operator of the CW20/pointer relationship, or any spender the owner interacts with) can cause the owner to grant/allow more total token movement than intended, resulting in direct loss of the owner's CW20/ERC20-pointer tokens beyond the approved cap the owner believed they were setting. This is unauthorized transfer of user funds reachable purely by any EVM transaction sender interacting with a public pointer contract, which is explicitly in scope (`CW<->EVM pointers and the wasm bridge`).

### Likelihood Explanation
Any spender that has been granted or previously held an allowance from a `CW20ERC20Pointer` owner can attempt this by monitoring the mempool for the owner's `approve()` calls and front-running with a `transferFrom`. No special privilege beyond being an approved spender is required, and the attack is deterministic once the front-run transaction lands before the owner's `approve()`.

### Recommendation
Avoid computing allowance deltas from a live, attacker-influenceable query inside `approve()`. Either:
- Overwrite the allowance atomically to the requested target value with a single CW20 message (if the underlying CW20 supports a "set allowance" style message), or
- Require callers to use explicit `increaseAllowance`/`decreaseAllowance` semantics (as already correctly implemented in the `example/cosmwasm/cw20` bridge contract's `execute_increase_allowance`/`execute_decrease_allowance`) instead of exposing a `approve(spender, amount)` that internally infers directionality from current state, and document/enforce that users should first set allowance to zero before changing it, consistent with standard ERC20 approve race mitigations.

### Proof of Concept
1. Owner calls `pointer.approve(spender, 0)` intending to revoke a previous 100-token allowance to `spender` (final intended allowance across the whole flow: 0 spent beyond original 100).
2. `spender` observes the pending transaction and front-runs it with `pointer.transferFrom(owner, spender, 100)`, spending the full existing allowance before the owner's tx lands.
3. Owner's `approve(spender, 0)` now executes: `allowance(owner, spender)` reads `0` (already spent), so `currentAllowance (0) == amount (0)`, no message is sent — but the spender has already extracted the full 100 tokens the owner was trying to revoke access to.
4. More generally, if the owner reduces allowance from 100 to 50 expecting a hard cap of 100 total, `spender` front-runs to spend 100, then the owner's tx computes `currentAllowance (0) < amount (50)` and issues `increase_allowance` by 50, granting the spender an additional 50 allowance — a cumulative 150 tokens transferable versus the owner's intended 100 cap.
