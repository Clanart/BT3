### Title
NULL pointer dereference when JSON-encoding an unset `google.protobuf.Value` message via `jsonenc_value` - (File: `upb/json/encode.c`)

### Summary
The upb JSON encoder's handling of `google.protobuf.Value` (and the byte-for-byte duplicated implementations in `ruby/ext/google/protobuf_c/ruby-upb.c` and `php/ext/google/protobuf/php-upb.c`) locates the single set oneof field via `upb_Message_Next`, but if the field is not found it calls an error routine and then falls through to code that dereferences the (unset) field pointer, mirroring the PoDoFo CVE-2017-6845 pattern of an unchecked "no case selected" path leading to a NULL/invalid pointer dereference during processing of attacker-influenced data.

### Finding Description
The CVE describes `PdfColor::operator=` in PoDoFo dereferencing a null pointer because the code assumed a color-space enum value always corresponds to a valid backing pointer, and a crafted file could produce a state where no matching case populated that pointer, so subsequent access dereferenced NULL.

The Protobuf analog is `jsonenc_value()`: [1](#0-0) 
This function encodes a `google.protobuf.Value` message to JSON. `google.protobuf.Value` models a `oneof kind` with six alternatives; per the `.proto` comment, "Absence of any variant is an invalid state," but that invariant is not actually enforced anywhere in the wire/JSON binary decoders — a `Value` sub-message with none of fields 1–6 set is a perfectly well-formed, zero-length embedded message and decodes without error: [2](#0-1) 

`jsonenc_value` finds "the" set field with `upb_Message_Next(msg, m, NULL, &f, &val, &iter)`. If the message has no fields set (the "invalid" empty state), this call returns `false`, and the code calls `jsonenc_err(e, "No value set in Value proto")` — but does **not** `return` afterward: [3](#0-2) 
Execution falls through unconditionally into `switch (upb_FieldDef_Number(f))`, dereferencing `f`, which was never assigned by `upb_Message_Next` on the false-return path (it remains whatever `upb_Message_Next` leaves it as, generally an unwritten/garbage output parameter, effectively behaving like a null/invalid pointer dereference analogous to the PoDoFo case). The same exact pattern exists in the two other embedded upb copies (`upb/json/encode.c`, `php/ext/google/protobuf/php-upb.c`), and the same dispatch logic (with an explicit `default: UPB_UNREACHABLE()`, treated as fatal-but-reachable) recurs in `jsondec_wellknownvalue` for JSON decoding.

Whether `jsonenc_err` performs a `longjmp`/exception that prevents reaching the `switch` is the one open question I could not fully verify from the available index (its body was not retrievable), so I cannot be certain the fallthrough is actually reached at runtime versus being cut off by a non-local jump inside `jsonenc_err`. This is the key unresolved uncertainty for this analog.

### Impact Explanation
If `jsonenc_err` does not immediately abort control flow (e.g., it just records an error and returns, as a non-fatal "err" helper name would suggest for many upb call sites), then `f` is used uninitialized/NULL in `upb_FieldDef_Number(f)`, causing a NULL/wild pointer read — a denial-of-service crash of the process performing JSON serialization of an attacker-supplied, technically-valid-on-the-wire message that has an unset `Value.kind` oneof (e.g., embedded inside an `Any`, `Struct`, or any message field of type `google.protobuf.Value` that a client parses from bytes and later serializes to JSON). This matches the CVE class exactly: a schema-legal/wire-legal but semantically "invalid" input causes an assumed-always-populated field to be missing, and the code dereferences it anyway.

### Likelihood Explanation
Reaching this state requires only sending a bounded, valid Protobuf binary message containing an empty embedded `Value` message (0 bytes) at any position where a `Value` is expected, then having the receiving application re-serialize that message to JSON via the upb-based Ruby/PHP JSON encoder (or upb core). No malicious schema, no privileged access, and no huge/unbounded payload are needed — a few bytes suffice. This is directly reachable through a public parse+serialize API pair that a consuming application would commonly use.

### Recommendation
1. Verify whether `jsonenc_err` truly halts execution (e.g., via `longjmp`) for all three copies (`upb/json/encode.c`, `ruby-upb.c`, `php-upb.c`). If it does not unconditionally prevent fallthrough, add an explicit `return;` immediately after the `jsonenc_err(...)` call in `jsonenc_value`, mirroring the `default: UPB_UNREACHABLE()` guard used in `jsondec_wellknownvalue`.
2. Add a regression test that JSON-encodes a `Struct`/`Any`/message containing a `Value` sub-message with no oneof field set (an empty embedded message) and asserts a controlled error rather than a crash.
3. Apply the same fix to all vendored/duplicated copies of this logic (`upb/json/encode.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`, `php/ext/google/protobuf/php-upb.c`) since they are independently maintained copies of the same code.

### Proof of Concept
Conceptual reproduction (not run in this session, since I have read-only access):
1. Build a minimal binary payload for a message containing a `google.protobuf.Value` field set to an empty embedded message: tag+len for the containing field, followed by length `0x00` for the `Value` submessage (i.e., zero bytes — no `kind` oneof member set).
2. Parse this payload with `upb_Decode` into a message whose schema includes a `Value` field (directly or via `Struct`/`Any`).
3. Call the JSON encoder (`upb_JsonEncode`/Ruby `to_json`/PHP `serializeToJsonString`) on the resulting message.
4. Observe whether `jsonenc_value` is entered with `upb_Message_Next` returning `false`, and confirm at that program point whether execution reaches `switch (upb_FieldDef_Number(f))` with `f` unset — this is the exact bypass point to validate the crash with a debugger/ASan build.

Because I could not inspect the body of `jsonenc_err` in this session, I am not able to confirm with certainty that the fallthrough is exploitable versus being intercepted by a non-local control transfer; a Devin session with terminal access would be required to build and run this PoC to confirm exploitability definitively.

static void jsonenc_value(jsonenc* e, const upb_Message* msg,
                          const upb_MessageDef* m) {
  /* TODO: do we want a reflection method to get oneof case? */
  size_t iter = kUpb_Message_Begin;
  const upb_FieldDef* f;
  upb_MessageValue val;

  if (!upb_Message_Next(msg, m, NULL, &f, &val, &iter)) {
    jsonenc_err(e, "No value set in Value proto");
  }

  switch (upb_FieldDef_Number(f)) {
    case 1:
      jsonenc_putstr(e, "null");
      break;
    case 2:
      if (upb_JsonEncode_HandleSpecialDoubles(e, val.double_val)) {
        jsonenc_err(
            e,
            "google.protobuf.Value cannot encode double values for "
            "infinity or nan, because they would be parsed as a string");
      }
      upb_JsonEncode_Double(e, val.double_val);
      break;
    case 3:
      jsonenc_string(e, val.str_val);
      break;
    case 4:
      jsonenc_putstr(e, val.bool_val ? "true" : "false");
      break;
    case 5:
      jsonenc_struct(e, val.msg_val, upb_FieldDef_MessageSubDef(f));
      break;
    case 6:
      jsonenc_listvalue(e, val.msg_val, upb_FieldDef_MessageSubDef(f));
      break;
  }
}
