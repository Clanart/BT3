## Analog Found: Stale in-memory working-directory snapshot used to gate destructive file writes during Copilot conflict resolution

### Title
Stale working-directory status snapshot lets `_applyCopilotConflictResolutions` silently overwrite user-resolved files - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Sherlock report is about an oracle whose `HEARTBEAT_TIME` window is too long, so a stale price snapshot is trusted for a security decision, enabling front-running. The same "broken invariant" — trusting a single, non-revalidated snapshot of external/mutable state across an unbounded async window — exists in GitHub Desktop's Copilot conflict-resolution write path in `app/src/lib/stores/app-store.ts`.

### Finding Description
`_applyCopilotConflictResolutions` fetches the working-directory state **once**, before iterating over all conflicted files: [1](#0-0) 

Inside the loop, for every file it awaits `resolveWithin` (an async `fs.realpath` based check) and then consults `onDiskFile`, which is looked up from that **same pre-loop `state` snapshot** — not a fresh git-status read taken immediately before the write: [2](#0-1) 

The code comment itself documents the exact hazard the guard is supposed to close: if the user resolves a conflict externally (in their editor) while the Copilot result dialog is open, git status will show no more conflict markers, and overwriting that file with Copilot's stored content would "silently clobber their work" — so it should be skipped: [3](#0-2) 

However, the "freshness" check only protects against edits that happened *before* `_applyCopilotConflictResolutions` was invoked and captured `state`. For every file after the first in the loop, an unbounded number of `await resolveWithin(...)` and `await writeFile(...)` calls occur, during which the user can still edit/resolve the file on disk — but the loop never re-queries the live working-directory status; it keeps consulting the stale `state.changesState.workingDirectory.files` captured at function entry. This is structurally identical to the oracle bug: a snapshot taken once is treated as valid for the entire decision window that follows, even though the underlying ground truth (price / file content) can change within that window.

### Impact Explanation
If the loop writes a file after the user has already hand-resolved it outside GitHub Desktop's watch, the write in `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` at line 7258 silently overwrites the user's manual resolution with Copilot's (potentially stale or repo-content-influenced) resolution, and the file is then staged with `git add` at lines 7262-7267. This is a silent corruption of what the user commits — matching the "Valid Impact" criterion of unprivileged corruption of commit/push content, since the source conflict content (and thus what Copilot resolved) can come from an attacker-controlled merged branch/fetched repository.

### Likelihood Explanation
This requires realistic, low-friction user behavior already anticipated by the code's own comment (editing a conflicted file in an external editor while the Copilot conflict dialog is open, for one of several conflicted files, before clicking "Continue Merge"). No admin rights, local malware, or leaked credentials are needed — only a merge/rebase against attacker-influenced content that produces multiple conflicting files, one of which the user manually fixes while Copilot's dialog remains open.

### Recommendation
Re-fetch the current on-disk/working-directory conflict status for each file immediately before writing (inside the loop, right before `writeFile`), rather than relying on the single `state` snapshot captured at function entry. This mirrors the fix pattern from the oracle report: replace a single stale-tolerant window with a check performed at the actual point of use.

### Proof of Concept
1. Start a merge/rebase that produces ≥2 conflicted files (e.g. via a crafted branch fetched from a remote).
2. Trigger Copilot conflict resolution; the result dialog opens with `copilotResolutions` computed for all conflicted files and `state` captured once in `_applyCopilotConflictResolutions`.
3. While still on the result dialog (before clicking "Continue Merge"), manually resolve file B in an external editor, removing its conflict markers.
4. Click "Continue Merge", invoking `_applyCopilotConflictResolutions`. Because file A comes first in `copilotResolutions` and requires an `await resolveWithin` + `await writeFile`, time passes before file B is processed — but the `onDiskFile` staleness check for file B still evaluates against the `state` object captured in step 2, not a fresh read.
5. Depending on timing/ordering, file B's Copilot content is written and staged despite the user's manual fix already existing on disk, silently discarding the user's real resolution before commit. [4](#0-3)

```typescript
  public async _applyCopilotConflictResolutions(
    repository: Repository
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    const { multiCommitOperationState } = state
    if (multiCommitOperationState === null) {
      return
    }

    const { copilotResolutions, step } = multiCommitOperationState
    if (copilotResolutions === null || copilotResolutions.length === 0) {
      return
    }

    // Respect any manual overrides the user chose in the result dialog
    const manualResolutions =
      step.kind === MultiCommitOperationStepKind.ShowCopilotConflicts
        ? step.conflictState.manualResolutions
        : new Map<string, ManualConflictResolution>()

    this.statsStore.increment('copilotConflictResolutionAcceptedCount')
    if (manualResolutions.size > 0) {
      this.statsStore.increment('copilotConflictResolutionWithOverridesCount')
    }

    const pathsToStage: string[] = []

    for (const resolution of copilotResolutions) {
      if (manualResolutions.has(resolution.path)) {
        continue
      }

      // Delete-vs-modify conflicts are resolved by setting a manual
      // resolution (ours/theirs) rather than writing file content.
      // The existing stageManualConflictResolution flow handles the
      // actual git checkout --ours/--theirs and staging at commit time.
      if (resolution.deleteConflictAction !== undefined) {
        const file = state.changesState.workingDirectory.files.find(
          f => f.path === resolution.path
        )
        if (file === undefined) {
          continue
        }
        const deletedSide = getDeletedSideFromStatus(file)
        if (deletedSide === undefined) {
          continue
        }
        // "keep" → choose the non-deleted side, "delete" → choose the deleted side
        const manualChoice =
          resolution.deleteConflictAction === 'keep'
            ? deletedSide === 'ours'
              ? ManualConflictResolution.theirs
              : ManualConflictResolution.ours
            : deletedSide === 'ours'
            ? ManualConflictResolution.ours
            : ManualConflictResolution.theirs
        this._updateManualConflictResolution(
          repository,
          resolution.path,
          manualChoice
        )
        continue
      }

      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(
          `Copilot resolution skipped: path outside repository: ${resolution.path}`
        )
        continue
      }

      // If the user resolved this file externally (e.g. in their editor) while
      // the result dialog was open, git status will report it with no remaining
      // conflict markers. Overwriting it with Copilot's stored content would
      // silently clobber their work, so skip it and let their resolution stand.
      // This mirrors how the manual conflicts dialog determines a file is
      // resolved (`hasUnresolvedConflicts`).
      const onDiskFile = state.changesState.workingDirectory.files.find(
        f => f.path === resolution.path
      )
      if (
        onDiskFile !== undefined &&
        isConflictedFileStatus(onDiskFile.status) &&
        !hasUnresolvedConflicts(onDiskFile.status)
      ) {
        continue
      }

      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
      pathsToStage.push(resolution.path)
```
