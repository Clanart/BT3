Based on the investigation, the closest structural analog to the Olympus M-9 pattern (a trusted checkpoint value gets overwritten/consumed using stale or externally-influenced state, permanently destroying data the user is entitled to) is in the Desktop **background branch pruner**, which deletes local git branches automatically using a "merged" classification that is derived from an externally-controlled ref (`defaultBranch`, which tracks the remote's advertised `HEAD`).

### Title
Background BranchPruner can silently delete local branches with un-pushed commits based on an attacker-influenced default branch ref - (File: `app/src/lib/stores/helpers/branch-pruner.ts`)

### Summary
`BranchPruner.pruneLocalBranches` runs automatically in the background (every ≥24h per repo) and deletes local branches it believes are "merged" into the repository's default branch and whose upstream is gone on the remote. The "merged" set is computed with `git branch --merged <defaultBranch>` where `defaultBranch` comes from state that is ultimately derived from the remote's advertised `HEAD`/branches during fetch — not from something the user explicitly reviewed. Because the merge-ancestry check and the "upstream gone" check are both driven by data supplied by whichever git server the repository is configured to fetch from, a malicious or compromised remote (or a MITM proxy sitting in front of a legitimate one) can manipulate what Desktop believes is "merged," causing the pruner to run `deleteLocalBranch` on branches that still contain unique, un-pushed local commits.

### Finding Description
`pruneLocalBranches` is invoked unconditionally on a timer once a repository is opened (`BranchPruner.start()` in `app-store.ts` via `startBackgroundPruner`), with no per-deletion user confirmation: [1](#0-0) 

The candidate set for deletion is computed via `findBranchesMergedIntoDefaultBranch`, which shells out to `git branch --merged <defaultBranch.name>`: [2](#0-1) 

`defaultBranch` and `allBranches`/remote-tracking refs come straight from `repositoriesStateCache`, which is populated from the locally cached remote-tracking refs (`refs/remotes/origin/*` and `origin/HEAD`) written during the last `fetch`: [3](#0-2) 

The final filter only protects reserved branch names, recently-checked-out branches, worktree branches, and branches whose upstream ref still exists among the locally cached remote branches — none of which validate that the "merged" determination itself is trustworthy: [4](#0-3) 

Deletion then happens with no per-branch prompt: [5](#0-4) 

The broken invariant: Desktop treats `git branch --merged <defaultBranch>` combined with "upstream ref missing from remote-tracking refs" as sufficient proof that a local branch's work is safely preserved upstream and can be destroyed. Both of these facts are populated purely from remote-advertised refs (`origin/HEAD`, `refs/remotes/origin/*`) captured on the most recent fetch, i.e., from a git remote/proxy response the attacker (a malicious repo owner, a compromised git host, or a MITM on an unauthenticated transport) controls. If the remote advertises a `HEAD`/default branch tip that happens to be a descendant of the user's local branch (trivial to arrange by including the user's already-observed public commits in a larger history), and simultaneously stops advertising the corresponding remote-tracking branch (e.g., server "deletes" the branch), the local branch satisfies both pruning conditions even though its actual commits were never truly merged/pushed anywhere the user controls.

### Impact Explanation
The result is silent deletion of local git branches, i.e., permanent local data loss (unless the user finds the SHA via reflog before it's garbage-collected) triggered without explicit user action, driven entirely by attacker-supplied remote ref data. This matches "silent corruption of what the user commits or pushes" in the accepted impact categories — analogous to the Olympus bug where an admin-adjacent operation destroyed value based on a stale/externally-manipulated checkpoint, permanently locking funds that could not be recovered by ordinary users.

### Likelihood Explanation
This requires the victim to have added/cloned a repository from a remote the attacker controls (or an unauthenticated/MITM'd transport), and for a normal automatic fetch/background prune cycle to occur — no unusual user interaction, elevated privileges, or pre-existing host compromise is needed. The pruner runs unconditionally every ≤24 hours for any GitHub-repository-backed local clone, which is a common Desktop configuration.

### Recommendation
Do not rely solely on locally cached remote-tracking refs and merge-ancestry to justify destructive branch deletion. At minimum: (1) re-verify against the live `git ls-remote` output (rather than only the last fetched cache) immediately before deleting, (2) require that the branch's commits appear reachable from a ref the user has actually observed/interacted with (e.g., something they've pushed themselves or that predates the last known-good default branch), and (3) surface a non-destructive confirmation or move deleted branches to a recoverable location (e.g., a "trash" ref/tag) rather than a hard `git branch -D` equivalent, so remote-driven manipulation cannot cause unrecoverable loss.

### Proof of Concept
1. Attacker controls (or MITMs) the git remote for `origin`.
2. Victim has a local branch `feature-x` with commits that have never been pushed to any other remote.
3. Attacker's server, on the next `git fetch`, advertises: (a) `refs/remotes/origin/main` (or configured default) whose tip is a descendant of `feature-x`'s tip (trivially built by rebasing/including `feature-x`'s commits into a new history the server controls), and (b) no ref at all for `feature-x`'s upstream (simulating "branch deleted upstream").
4. Desktop's normal background fetch updates `origin/HEAD` and the remote-tracking refs cache.
5. On the next scheduled `BranchPruner` run (`app/src/lib/stores/helpers/branch-pruner.ts:136`), `git branch --merged <defaultBranch>` reports `feature-x` as merged, and the upstream-existence filter passes because the (attacker-controlled) remote no longer advertises `feature-x`'s upstream ref.
6. `deleteLocalBranch(repository, 'feature-x')` runs automatically, deleting the branch and its un-pushed commits without any user confirmation.

Note: I was not able to fully trace `GitStore`'s `refreshDefaultBranch` logic (in `app/src/lib/stores/git-store.ts`) within the available search budget to confirm exactly how `defaultBranch` is refreshed relative to `origin/HEAD` vs. the GitHub API's `default_branch` field; this is worth double-checking during triage, since the exact provenance of `defaultBranch` affects how directly remote-controlled it is turn-by-turn.

  /** @returns a map of canonical refs to their shas */
  private async findBranchesMergedIntoDefaultBranch(
    repository: Repository,
    defaultBranch: Branch
  ): Promise<ReadonlyMap<string, string>> {
    const gitStore = this.gitStoreCache.get(repository)
    const mergedBranches = await gitStore.performFailableOperation(() =>
      getMergedBranches(repository, defaultBranch.name)
    )

    if (mergedBranches === undefined) {
      return new Map<string, string>()
    }

    const currentBranchCanonicalRef = await getSymbolicRef(repository, 'HEAD')

    // remove the current branch
    if (currentBranchCanonicalRef) {
      mergedBranches.delete(currentBranchCanonicalRef)
    }

    return mergedBranches
  }
