### Title
Broadcasting transaction/block messages to peers races with concurrent peer disconnection, causing an unhandled `RuntimeError` that can abort transaction processing mid-flight - ([File: chia/server/server.py])

### Summary
`ChiaServer.send_to_all()`/`send_to_all_if()` iterate directly over the live `self.all_connections` dict while `await`-ing `connection.send_message()` inside the loop body. Because these are async coroutines, the event loop can interleave other tasks between iterations, including `ChiaServer.connection_closed()`, which pops entries from that same dict when a peer disconnects. This produces the same class of bug reported for the Berachain `broker.go` file: a shared map is mutated concurrently with an in-progress fan-out/iteration with no synchronization, and the shutdown/removal path is not idempotent with respect to the in-flight iteration.

### Finding Description
`send_to_all()` and `send_to_all_if()` iterate the dict directly and await on each connection inside the loop: [1](#0-0) [2](#0-1) 

Meanwhile, `connection_closed()` — invoked whenever a peer disconnects, times out, or is banned — removes the connection from the exact same dict: [3](#0-2) 

Because each `await connection.send_message(message)` inside the `for _, connection in self.all_connections.items():` loop yields control to the event loop, a concurrently-scheduled `connection_closed()` call for a *different* peer can pop an entry from `all_connections` while the loop's dict-view iterator is still live. CPython dict-view iterators raise `RuntimeError: dictionary changed size during iteration` the next time `__next__()` is invoked after such a mutation, so the broadcast loop can crash mid-iteration instead of completing or cleanly erroring out.

This is directly reachable from ordinary transaction processing: an unprivileged spend-bundle submitter's transaction, once accepted into the mempool, triggers `FullNode.add_transaction()` to call `broadcast_added_tx()`, which calls `self.server.send_to_all(...)`: [4](#0-3) 

If any other peer connection closes at the same moment (a completely ordinary, non-malicious network event — timeouts, normal disconnects, etc.), the `RuntimeError` propagates up out of `send_to_all()`, through `broadcast_added_tx()`, and out of `add_transaction()`, which is invoked both from the peer message-handling path and directly from the RPC `/push_tx` endpoint (per `.cursor/context/full-node.md`: "`/push_tx` calls `FullNode.add_transaction()` directly ... it does not use the peer transaction queue").

The same unsynchronized-iteration-vs-removal pattern also exists in `broadcast_removed_tx()`, which is called on every mempool eviction (e.g., on every new block) and again reads/awaits over `all_connections` while peers may be concurrently removed: [5](#0-4) 

This mirrors exactly the reported bug class: a "Publish/Broadcast" style fan-out over a shared collection races with a "shutdown"/removal path (`connection_closed()`), with no mutex or copy-before-iterate protecting the collection, and the removal side is not defensively idempotent against in-flight iterators.

### Impact Explanation
When the race triggers, `add_transaction()` raises an unhandled `RuntimeError` after the spend bundle has *already been committed to the mempool* under the blockchain's priority mutex (the mutex is released before `broadcast_added_tx()` runs). This means:
- The mempool state mutation (successful `add_spend_bundle()`) has already happened, but the caller (RPC `/push_tx` handler or the peer transaction-processing pathway) receives an exception instead of the expected `SUCCESS` status, since the exception is raised after the `status == MempoolInclusionStatus.SUCCESS` branch begins executing: [6](#0-5) 
- This is a spend-triggered transaction-processing disruption: the exception can abort/kill the task handling that RPC call or peer message, and depending on how the caller framework handles the unhandled exception, it can leave the caller (wallet, RPC client) with an incorrect view of whether the transaction was actually accepted, and can interrupt broadcast to other honest wallet/full-node peers who should have learned about the new transaction (`mempool_items_added`) or removed transactions (`mempool_items_removed`), producing coin-set/mempool-state divergence in what different peers observe.
- Because this can occur on essentially any transaction submission when a peer happens to disconnect concurrently (a routine, frequent event on the public network), it is a systemic reliability issue rather than an edge case.

### Likelihood Explanation
Peer connect/disconnect churn is continuous and routine on a public full node (timeouts, client-initiated closes, bans, reconnects). Any transaction broadcast (which happens on every accepted spend bundle and every new block's mempool removals) that overlaps with a connection closing anywhere in `all_connections` can trigger the dict-mutation-during-iteration `RuntimeError`. No attacker control or malicious peer behavior is required — an ordinary spend-bundle submitter combined with normal network churn is sufficient, making this a Medium-likelihood issue that will occur under production load.

### Recommendation
- Protect `all_connections` mutations (`connection_closed()`) and iterations (`send_to_all()`, `send_to_all_if()`, and the ad-hoc iterations in `broadcast_added_tx()`/`broadcast_removed_tx()`) with a lock, or iterate over a stable snapshot (e.g., `list(self.all_connections.values())`) instead of the live dict view.
- Make `connection.send_message()` failures for an individual peer non-fatal to the overall broadcast loop (catch and log per-connection errors) rather than letting one connection's closure abort delivery to all remaining peers.
- Ensure `add_transaction()` cannot leak a mempool-accepted transaction as an unhandled exception to its caller; the broadcast step should be best-effort and isolated from the mempool-insertion result that is returned to the caller.

### Proof of Concept
1. Start a full node with several peer connections established (`all_connections` populated with multiple `WSChiaConnection` entries).
2. Submit a valid spend bundle via `push_tx` RPC or peer `new_transaction`, causing `FullNode.add_transaction()` → `broadcast_added_tx()` → `ChiaServer.send_to_all()` to iterate `self.all_connections.items()`.
3. While that iteration is suspended at an `await connection.send_message(message)` for one peer, trigger a disconnect/timeout/ban on a *different* connected peer so that `ChiaServer.connection_closed()` executes concurrently and pops it from `self.all_connections`.
4. On the next iteration step, Python's dict-view iterator detects the size change and raises `RuntimeError: dictionary changed size during iteration`, propagating out of `send_to_all()` → `broadcast_added_tx()` → `add_transaction()`, even though the spend bundle was already successfully inserted into the mempool.

    async def broadcast_removed_tx(self, mempool_removals: list[MempoolRemoveInfo]) -> None:
        total_removals = sum(len(r.items) for r in mempool_removals)
        if total_removals == 0:
            return

        start_time = time.monotonic()

        self.log.debug(f"Broadcasting {total_removals} removed transactions to peers")

        all_peers = {
            peer_id
            for peer_id, peer in self.server.all_connections.items()
            if peer.has_capability(Capability.MEMPOOL_UPDATES)
        }

        if len(all_peers) == 0:
            return

        removals_to_send: dict[bytes32, list[RemovedMempoolItem]] = dict()

        for removal_info in mempool_removals:
            for transaction_id, internal_mempool_item in removal_info.items.items():
                conds = internal_mempool_item.conds
                assert conds is not None

                hints_for_removals = await self.hint_store.get_hints([bytes32(spend.coin_id) for spend in conds.spends])
                peer_ids = all_peers.intersection(
                    peers_for_spend_bundle(self.subscriptions, conds, set(hints_for_removals))
                )

                if len(peer_ids) == 0:
                    continue

                self.log.debug(f"Broadcasting removed transaction {transaction_id} to wallet peers {peer_ids}")

                for peer_id in peer_ids:
                    peer = self.server.all_connections.get(peer_id)

                    if peer is None:
                        continue

                    removal = wallet_protocol.RemovedMempoolItem(transaction_id, uint8(removal_info.reason.value))
                    removals_to_send.setdefault(peer.peer_node_id, []).append(removal)

        for peer_id, removals in removals_to_send.items():
            peer = self.server.all_connections.get(peer_id)

            if peer is None:
                continue

            msg = make_msg(
                ProtocolMessageTypes.mempool_items_removed,
                wallet_protocol.MempoolItemsRemoved(removals),
            )
            await peer.send_message(msg)
