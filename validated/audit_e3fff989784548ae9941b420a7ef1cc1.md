### Title
Oracle Voting Power Computed At Tally Time Instead Of Vote-Submission Time Allows Last-Minute Stake Inflation To Skew The Weighted-Median Exchange Rate - (File: x/oracle/abci.go)

### Summary
Sei's oracle module tallies validator exchange-rate votes using each validator's *current* bonded/consensus power at the moment `MidBlocker` runs (the last block of the vote period), rather than the power the validator held when its price vote was actually cast. A validator (or a large delegator backing one) can submit a price vote early in the voting period and then increase that validator's bonded stake right up to the tally block — reachable via a normal `MsgDelegate` or via the EVM staking precompile — so that the already-cast vote is weighted with the inflated, last-minute stake. This mirrors the Anchor Governance finding: influence over a result is disproportionate to what a participant's stake was throughout the period it was supposed to represent.

### Finding Description
`MidBlocker` builds `validatorClaimMap` by iterating the *current* bonded validator set and reading `validator.GetConsensusPower(powerReduction)` at the instant the tally runs: [1](#0-0) 

This claim map (keyed by validator operator address, with `Power` fixed at tally time) is then used to assign vote power to every ballot entry for that validator via `OrganizeBallotByDenom`: [2](#0-1) 

and consumed directly by `Tally`/`pickReferenceDenom` to compute the weighted median exchange rate: [3](#0-2) 

The vote itself (`MsgAggregateExchangeRateVote`) can be submitted at any point earlier in the `VotePeriod`, but its power is only resolved when `MidBlocker` executes on the period's last block. Nothing checkpoints a voter's bonded power at the time the vote (or prevote) was cast — the same class of gap the external report describes for Anchor's poll `staked_amount` snapshot vs. later stake changes. `MsgDelegate` immediately updates `validator.Tokens`/`DelegatorShares` synchronously within the transaction that processes it: [4](#0-3) 

and this path is reachable from an EVM transaction through the staking precompile's `delegate`/`delegateFor` handlers, which route straight to `stakingKeeper.Delegate`: [5](#0-4) 

Because delegation state changes are applied immediately and `MidBlocker` reads the live bonded-validator iterator at tally time, any delegation transaction included in the same block as (or any block before) the tally block increases that validator's counted power for votes it already cast earlier in the period, without those votes needing to be re-submitted or re-verified against the new stake.

### Impact Explanation
The oracle module's weighted-median exchange rate is a chain-wide price oracle consumed by other Sei modules/precompiles for economic decisions. Inflating a validator's tally-time power relative to its power during most of the voting period lets that validator (or an actor who delegates heavily to it) exert outsized influence on the published exchange rate versus its actual economic stake-weighted share, enabling price-skewing without commensurate stake commitment. This falls into the fee/price-manipulation impact category tied to oracle vote admission that is explicitly in scope.

### Likelihood Explanation
The last block of each `VotePeriod` is deterministically computable from chain parameters (`utils.IsPeriodLastBlock`), so an attacker knows exactly which block to target. Delegating additional stake (via a standard `MsgDelegate` or the EVM staking precompile) is a permissionless, unprivileged action requiring no special access — any staker or EVM user with an associated Sei address can perform it. The main friction is the cost of temporarily bonding additional tokens, which bounds but does not eliminate the practicality of the attack, especially for a validator already near a delegation threshold trying to nudge its own weighting for a single period.

### Recommendation
Snapshot each validator's bonded power (or a bounded historical/EMA power) at vote/prevote submission time or at the start of the vote period, and use that recorded amount — not the live power read at `MidBlocker` — when tallying votes cast during that period. Alternatively, freeze the validator power set used for tallying at the start of the vote period (similar to Cosmos SDK governance's frozen electorate snapshot pattern already implemented in `sei-cosmos/x/gov`) so that stake changes occurring during the period cannot retroactively alter the weight of votes already cast.

### Proof of Concept
1. Validator V casts an `MsgAggregateExchangeRateVote` early in a `VotePeriod` with a self-serving exchange rate.
2. Shortly before the last block of that `VotePeriod` (computed deterministically via `utils.IsPeriodLastBlock`), an actor sends a large `MsgDelegate` to V — either directly or through the EVM staking precompile's `delegate` method (`precompiles/staking/staking.go:381`) — which synchronously increases `V.Tokens`/`DelegatorShares` (`sei-cosmos/x/staking/keeper/delegation.go:723-730`).
3. On the tally block, `MidBlocker` reads V's now-inflated `GetConsensusPower` from the live bonded validator iterator (`x/oracle/abci.go:26-44`) and applies it as V's vote weight for the already-cast vote (`x/oracle/keeper/ballot.go:18-44`), skewing the resulting weighted-median exchange rate (`x/oracle/tally.go:62-69`) beyond what V's stake represented for most of the voting period.
