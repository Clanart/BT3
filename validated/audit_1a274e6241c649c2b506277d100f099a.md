### Title
Unprivileged panic (complete DoS) via blame-decryption on an unregistered participant index - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::register` and `Decryption::decrypt_with_proof` in PedPoP index `self.enc_keys` with participant identities derived from peer-supplied messages. `enc_keys[&decryptor]` (and the `contains_key` assert in `register`) panic when the referenced participant was never registered or registers twice. Both inputs — the `EncryptionKeyMessage`/`EncryptedMessage` payloads and the accusing participant index — are untrusted bytes read via `EncryptionKeyMessage::read` / `EncryptedMessage::read` / `EncryptionKeyProof::read`. A panic in this path is a repeatable crash of the DKG/signing participant, directly analogous to the CVE class: unauthenticated network input causing a hang or repeatable crash of the client.

### Finding Description
- `EncryptionKeyMessage::read` reads `msg` and `enc_key` from raw bytes with no binding to a registration table [1](#0-0) .
- `Decryption::register` asserts rather than erroring on a duplicate registration: `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` — a second registration message from the same (or spoofed) participant index panics instead of returning `Err` [2](#0-1) .
- `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` when verifying the accuser-supplied `EncryptionKeyProof`'s DLEq. `HashMap`'s `Index` impl panics on a missing key, so a blame/accusation referencing a `decryptor` participant that never registered (index 0, an index > n, or one filtered earlier) crashes the process [3](#0-2) .
- The same unchecked indexing exists in `encrypt`: `self.decryption.enc_keys[&participant]` [4](#0-3) .
- Unlike the bounded-length reads elsewhere (e.g., `ThresholdKeys::read` caps loops at `n: u16`, `SchnorrAggregate::read` terminates on EOF), these paths convert untrusted input directly into a panic rather than an `io::Result` error [5](#0-4) .

### Impact Explanation
A single malformed DKG/blame message causes a deterministic panic in the receiving participant. In Serai's deployment model where a task panic aborts or kills the signing/validator process, this is a complete availability loss of the client — the exact impact class of CVE-2020-2570 (unauthenticated, network-reachable, repeatable crash) mapped onto Serai's PedPoP blame/registration flow.

### Likelihood Explanation
Any DKG counterpart can submit an accusation naming an arbitrary `decryptor` index or replay/duplicate a registration message. No key knowledge, collusion, or threshold is required — only the ability to send a protocol message, which the threat model explicitly grants to unprivileged parties feeding bytes to `EncryptedMessage::read`/`EncryptionKeyProof::read`.

### Recommendation
Replace `self.enc_keys[&decryptor]` with `enc_keys.get(&decryptor).ok_or(...)` and change the duplicate-registration `assert!` into a returned error, so malformed peer input yields `Err`/`DecryptionError` rather than a process abort.

### Proof of Concept
1. In a PedPoP session, send two `EncryptionKeyMessage`s with the same `Participant` index → `register` hits the `assert!` and panics (encryption.rs:357).
2. Alternatively, complete registration normally, then submit a blame/`decrypt_with_proof` invocation whose `decryptor` is a `Participant` never inserted into `enc_keys` (e.g., index beyond the registered set, or one whose registration failed earlier) with a syntactically valid `EncryptionKeyProof` → `self.enc_keys[&decryptor]` panics on `HashMap::index` (encryption.rs:388).
