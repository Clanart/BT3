### Title
Squatting the deterministic ERC-20 precompile address for a not-yet-received IBC denom permanently blocks `RegisterERC20Extension`, forcing an error acknowledgement after the voucher has already been minted, duplicating value across chains - (File: `x/erc20/keeper/token_pairs.go`, `utils/utils.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
The Fraxlend bug is a salt/name pre-emption bug: an attacker can compute in advance the deterministic key that a future, legitimate deployment will use, occupy it first with attacker-controlled data, and cause the existence-check in the deployer to permanently reject the honest deployment. The same "attacker pre-computes and squats a deterministic key before the legitimate actor uses it" pattern exists in `x/erc20`'s dynamic ERC-20 precompile registration for IBC vouchers: the target EVM address for a not-yet-seen `ibc/<hash>` denom is 100% deterministic from the denom trace (`utils.GetIBCDenomAddress`), and `CreateNewTokenPair` unconditionally rejects registration if any code already exists at that address.

### Finding Description
`utils.GetIBCDenomAddress` derives the ERC-20 precompile address for an IBC voucher purely as `common.BytesToAddress(sha256(fullDenomPath)[:20])`: [1](#0-0) 

`CreateNewTokenPair` (called from `RegisterERC20Extension`, which is invoked automatically the first time a given IBC denom is received via `OnRecvPacket`) checks whether an account already has code at that deterministic address, and if so, permanently fails registration: [2](#0-1) 

Because the source port/channel and base denom of any future ICS-20 transfer are public/predictable (e.g. once a channel is opened, or for well-known denoms like `transfer/channel-X/uatom`), an unprivileged attacker can:
1. Compute the exact `ibc/<hash>` denom that a legitimate future transfer will produce, and thus the exact `common.Address` that `GetIBCDenomAddress` will derive for it.
2. Send an ordinary EVM transaction that deploys arbitrary bytecode to that exact address (e.g. via `CREATE2` with a brute-forced salt, or simply via `CREATE` if the attacker controls the nonce sequence of a throwaway EOA to land on that address).
3. Once any relayer relays the first real ICS-20 transfer for that denom, `OnRecvPacket` -> `RegisterERC20Extension` -> `CreateNewTokenPair` finds `account.HasCodeHash() == true` and returns `types.ErrTokenPairAlreadyExists`: [3](#0-2) 

This causes `OnRecvPacket` to return `channeltypes.NewErrorAcknowledgement(err)` for the packet. Per standard ICS-20/IBC middleware semantics, this module's `OnRecvPacket` is a middleware wrapping the underlying ICS-20 transfer application: the transfer app runs first and mints/unescrows the voucher bank coin to the recipient as part of executing the packet, and only after that succeeds does this erc20 middleware attempt the ERC-20 conversion/registration step. If this later step fails and substitutes an error acknowledgement, that acknowledgement is what gets relayed back to the source chain — causing the source chain to treat the transfer as failed and refund/unlock the sender's escrowed coins — while the destination (Cosmos EVM) chain has already durably credited the recipient with the newly minted `ibc/<hash>` bank coin in the same block. Both sides of the transfer end up believing they hold the value: the destination recipient holds spendable bank coin, and the source chain refunds the sender's original coin, duplicating spendable value across the two chains for every subsequent transfer of that denom (since the pair can never be registered, this is not a one-off but a permanent, repeatable steal/duplication for the affected denom).

Note: I was not able to fully re-verify within the tool budget the exact call order inside `ibc/module.go`'s `OnRecvPacket` wrapper (i.e., that the wrapped ICS-20 transfer app's mint executes and commits before this erc20 keeper's `OnRecvPacket` runs and can no longer be rolled back by substituting the acknowledgement). This ordering assumption, based on the standard evmos/cosmos-evm ICS-20 middleware pattern, is the crux of the "duplication" impact and should be confirmed against `ibc/module.go` and `x/erc20/ibc_middleware.go` before treating this as fully proven.

### Impact Explanation
If the ordering assumption above holds, this is a critical, permanent, and repeatable duplication of spendable value across an IBC escrow and Cosmos EVM native balances: attackers can create free money by having voucher coins minted to a colluding recipient on the destination chain while the source chain independently refunds the original sender, for every transfer of the squatted denom, satisfying the "Critical unauthorized minting/duplication...across native balances...IBC escrows" impact gate. Even if the ordering assumption does not hold (i.e., the mint is rolled back together with the ack), the bug still permanently and unrecoverably denies ERC-20 registration for a legitimate IBC denom on an ordinary, unprivileged trigger, which is a lower-severity DoS not meeting the Critical bar on its own.

### Likelihood Explanation
The attacker's cost is a single EVM contract deployment to a chosen address, requiring only the ability to predict a plausible future IBC denom trace (trivial for common assets/channels) and to land a contract at the derived 20-byte address (feasible via `CREATE2` salt search or a controlled EOA nonce). No special privileges, validator collusion, or governance access are required — this is fully triggerable by an ordinary user.

### Recommendation
- Do not derive the ERC-20 precompile address for dynamically-registered IBC coins purely from a value (`sha256(denom trace)`) that any unprivileged actor can predict and pre-occupy with code; instead, mint IBC ERC-20 precompiles using the ERC-20 module's own account-creation authority (e.g. explicitly create/overwrite the module-owned account state) or maintain a separate, protected keyspace that ordinary EOAs cannot deploy contracts into.
- Alternatively, make `CreateNewTokenPair`/`RegisterERC20Extension` tolerant of a pre-existing account by verifying that any existing code/account at the derived address is not an externally-created contract before treating this as a genuine "already registered" collision, and reject or overwrite spurious squatter contracts.
- Ensure the ICS-20 middleware architecture is atomic: if the erc20 conversion/registration step fails, the underlying transfer mint for that packet must be rolled back in the same message execution so that a substituted error acknowledgement can never coexist with an already-committed mint.

### Proof of Concept
1. Choose a future ICS-20 transfer path/denom, e.g. `transfer/channel-7/uatom`, and compute `ibcDenom = "ibc/" + hex(sha256("transfer/channel-7/uatom"))`.
2. Compute `targetAddr = common.BytesToAddress(sha256Bytes[:20])` exactly as `utils.GetIBCDenomAddress` does.
3. From an ordinary EOA, deploy any contract (e.g. via `CREATE2` with a brute-forced salt) so that `targetAddr` ends up holding non-empty code/`CodeHash`.
4. Have (or wait for) a relayer relay the first ICS-20 transfer over `channel-7` for `uatom` to any recipient on the Cosmos EVM chain.
5. Observe: `OnRecvPacket` -> `RegisterERC20Extension` -> `CreateNewTokenPair` fails with `ErrTokenPairAlreadyExists` because `account.HasCodeHash()` is true at `targetAddr`, and `OnRecvPacket` returns `NewErrorAcknowledgement`.
6. Confirm on the destination chain whether the recipient's bank balance for `ibc/<hash>` was already credited by the wrapped ICS-20 transfer app prior to this failure (this determines whether step 5 causes double-credit/duplication or "only" a permanent DoS of that denom's ERC-20 conversion). If credited, the source chain will independently refund the sender upon seeing the error ack, completing the duplication.

// GetIBCDenomAddress returns the address from the hash of the ICS20's Denom Path.
func GetIBCDenomAddress(denom string) (common.Address, error) {
	if !strings.HasPrefix(denom, "ibc/") {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s does not have 'ibc/' prefix", denom)
	}

	if len(denom) < 5 || strings.TrimSpace(denom[4:]) == "" {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s is not a valid IBC voucher hash", denom)
	}

	// Get the address from the hash of the ICS20's Denom Path
	bz, err := ibctransfertypes.ParseHexHash(denom[4:])
	if err != nil {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrap(err.Error())
	}

	return common.BytesToAddress(bz), nil
}

func (k Keeper) CreateNewTokenPair(ctx sdk.Context, denom string) (types.TokenPair, error) {
	pair, err := types.NewTokenPairSTRv2(denom)
	if err != nil {
		return types.TokenPair{}, err
	}
	account := k.evmKeeper.GetAccount(ctx, pair.GetERC20Contract())
	if account != nil && account.HasCodeHash() {
		return types.TokenPair{}, errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	err = k.SetToken(ctx, pair)
	if err != nil {
		return types.TokenPair{}, err
	}
	return pair, nil
}
