### Title
Host `deposit_constant` Passes Deposit Value Instead of `move_txid`, Breaking Bridge Circuit Proof Generation — (`bridge-circuit-host/src/structs.rs`)

### Summary

`host_deposit_constant()` in `bridge-circuit-host/src/structs.rs` passes `deposit_value_bytes` (the deposit amount from the EIP-1186 storage proof) as the 4th argument to `deposit_constant()`, while the circuit itself and the verifier's setup both pass `move_txid` (the move transaction ID). This produces a permanently mismatched `deposit_constant`, causing `prove_bridge_circuit` to fail its journal-hash sanity check on every invocation, making it impossible for any operator to generate a valid bridge circuit proof and claim reimbursement.

---

### Finding Description

The `deposit_constant()` function has the following signature:

```rust
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],   // ← 4th parameter
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant
```

**Circuit side** (`circuits-lib/src/bridge_circuit/mod.rs`, lines 221–229) — correct:

```rust
let (user_wd_outpoint, vout, move_txid) =
    verify_storage_proofs(&input.sp, light_client_circuit_output.l2_state_root);
...
let deposit_constant = deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    *move_txid,   // ← move transaction ID
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
);
```

**Verifier setup** (`core/src/verifier.rs`, lines 2478–2486) — correct:

```rust
let deposit_constant = deposit_constant(
    kickoff_data.operator_xonly_pk.serialize(),
    watchtower_challenge_start_idx,
    &watchtower_pubkeys,
    move_txid,   // ← move transaction ID
    round_txid,
    vout,
    self.config.protocol_paramset.genesis_chain_state_hash,
);
```

**Host side** (`bridge-circuit-host/src/structs.rs`, lines 505–515) — **wrong**:

```rust
let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    deposit_value_bytes,   // ← deposit amount, NOT move_txid
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

`deposit_value_bytes` is a 32-byte big-endian encoding of the deposit amount (a U256 from the EIP-1186 storage proof). `move_txid` is a 32-byte Bitcoin transaction ID. They are structurally and semantically different and will never be equal.

`prove_bridge_circuit` documents "The journal hash does not match the expected hash" as a possible error, confirming it compares `public_inputs.host_journal_hash()` against the actual circuit output. Because `host_journal_hash()` is computed from the host's (wrong) `deposit_constant`, this comparison will always fail, and `prove_bridge_circuit` will always return an error. ---

### Impact Explanation

`prove_bridge_circuit` is the sole path by which an operator generates the Groth16 proof required to claim reimbursement from the bridge vault after fronting a withdrawal. Because the host's `deposit_constant` is always computed with the wrong 4th argument, the journal-hash check inside `prove_bridge_circuit` will always fail. Operators can never produce a valid bridge circuit proof, so they can never submit the assert transactions required to reclaim their collateral. Operator collateral is permanently locked in the bridge vault. This is a permanent liveness failure with direct material fund impact on every operator. [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

The bug is triggered unconditionally on every call to `prove_bridge_circuit`. No special attacker input is required; normal bridge operation (any operator attempting reimbursement after fronting a withdrawal) hits this path. The mismatch is deterministic: `deposit_value_bytes` (a deposit amount) can never equal `move_txid` (a Bitcoin transaction ID). [6](#0-5) 

---

### Recommendation

Replace `deposit_value_bytes` with the move transaction ID in `host_deposit_constant`. The move txid must be extracted from the storage proof in the same way the circuit does — via `verify_storage_proofs` or by deserializing `input.sp.storage_proof_deposit_txid` and reading the key/value that encodes the move txid, not the deposit amount. The corrected call should be:

```rust
Ok(deposit_constant(
    operator_xonlypk,
    input.watchtower_challenge_connector_start_idx,
    &input.all_tweaked_watchtower_pubkeys,
    move_txid,   // ← must match what verify_storage_proofs returns
    round_txid,
    kickoff_round_vout,
    input.hcp.genesis_state_hash,
))
```

Add a unit test that runs both the host and circuit paths on the same `BridgeCircuitInput` and asserts that their `deposit_constant` values are equal. [7](#0-6) 

---

### Proof of Concept

1. Construct a valid `BridgeCircuitInput` with a real storage proof whose `storage_proof_deposit_txid` encodes a non-zero deposit amount and a distinct `move_txid`.
2. Call `host_deposit_constant(&input)` → observe it returns `DepositConstant(SHA256(... || deposit_value_bytes || ...))`.
3. Run the circuit logic manually: call `verify_storage_proofs(&input.sp, state_root)` → obtain `move_txid`; call `deposit_constant(..., *move_txid, ...)` → observe a different `DepositConstant`.
4. Call `SuccinctBridgeCircuitPublicInputs::new(input)` → `host_journal_hash()` uses the wrong `deposit_constant`.
5. Call `prove_bridge_circuit(params, elf)` → the function returns `Err("Journal hash does not match the expected hash")` because the circuit commits the correct `move_txid`-based `deposit_constant` while the host computed a different one. [8](#0-7) [9](#0-8)

/// Computes a deposit constant hash using various transaction and cryptographic components.
///
/// # Parameters
///
/// - `operator_xonlypk`: A 32-byte array representing the operator's X-only public key.
/// - `watchtower_challenge_connector_start_idx`: A 16-bit unsigned integer marking the start index of the watchtower challenge connector.
/// - `watchtower_pubkeys`: A slice of 32-byte arrays representing tweaked watchtower public keys.
/// - `move_txid`: A 32-byte array representing the transaction ID of the move transaction.
/// - `round_txid`: A 32-byte array representing the transaction ID of the round transaction.
/// - `kickoff_round_vout`: A 32-bit unsigned integer indicating the vout of the kickoff round transaction.
/// - `genesis_state_hash`: A 32-byte array representing the genesis state hash.
///
/// # Returns
///
/// A `DepositConstant` containing a 32-byte SHA-256 hash of the concatenated input components.
pub fn deposit_constant(
    operator_xonlypk: [u8; 32],
    watchtower_challenge_connector_start_idx: u32,
    watchtower_pubkeys: &[[u8; 32]],
    move_txid: [u8; 32],
    round_txid: [u8; 32],
    kickoff_round_vout: u32,
    genesis_state_hash: [u8; 32],
) -> DepositConstant {
    // pubkeys are 32 bytes long
    let pubkey_concat = watchtower_pubkeys
        .iter()
        .flat_map(|pubkey| pubkey.to_vec())
        .collect::<Vec<u8>>();

    let watchtower_pubkeys_digest: [u8; 32] = Sha256::digest(&pubkey_concat).into();

    let pre_deposit_constant = [
        &move_txid,
        &watchtower_pubkeys_digest,
        &operator_xonlypk,
        &watchtower_challenge_connector_start_idx.to_be_bytes()[..],
        &round_txid,
        &kickoff_round_vout.to_be_bytes()[..],
        &genesis_state_hash,
    ]
    .concat();

    DepositConstant(Sha256::digest(&pre_deposit_constant).into())
}
