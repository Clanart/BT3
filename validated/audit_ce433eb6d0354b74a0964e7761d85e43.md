### Title
GitHub Desktop silently rewrites a repository's git remote URL based on an untrusted GitHub API `clone_url` field, redirecting future pushes/fetches without user consent - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop caches a `GitHubRepository` record (including a `cloneURL`) for every local repository, keyed by owner/name/endpoint. During periodic and on-demand "refresh" flows, Desktop re-fetches the repository object from the GitHub API and, if certain heuristics match, automatically calls `git remote set-url` to rewrite the user's `origin` remote to whatever `clone_url` the API happened to return — with no user prompt. This is analogous to the Teller bug: an identity/destination value (`bid.lender` / here, the git remote destination) is resolved dynamically from an external, mutable source (NFT ownership / a GitHub API response) and used to redirect where value flows (loan repayment / git push-fetch traffic) without re-validating that the resolved value is still the same trusted entity the user originally associated with.

### Finding Description
`updateRemoteUrl` [1](#0-0)  compares the locally configured remote URL to the `clone_url` field of an `IAPIRepository` object obtained from the GitHub API, and if:
- the protocols match, and
- the current remote still equals the previously cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually re-pointed the remote), and
- the new `clone_url` differs from the current remote URL

then it calls `gitStore.setRemoteURL(...)` [2](#0-1)  which shells out to `git remote set-url` [3](#0-2) . This happens with **no user confirmation dialog**.

This is invoked from `repositoryWithRefreshedGitHubRepository`, which re-matches the repository against the API using the *current* default remote's parsed owner/name and hostname, then calls `api.fetchRepository(owner, name)`: [4](#0-3)  The `owner`/`name` pair comes purely from `matchGitHubRepository`, which just parses the existing remote URL string and finds any account whose endpoint hostname matches — it performs no cryptographic or persistent-ID binding to the *actual* repository that was originally cloned: [5](#0-4) 

The critical trust assumption is that whatever `IAPIFullRepository` object the API returns for `owner/name` on that host is still "the same" repository the user originally added. There is no persistence-independent identifier check (e.g., GitHub's numeric repository `id`) tying the cached `GitHubRepository` to the fetched object before honoring its `clone_url`. If the owner/name on that host is ever re-associated with a different underlying repository (e.g. via GitHub's repo/organization/user rename-and-reclaim mechanics — a well known "repo-jacking"/dangling-reference class of issue where a renamed or deleted owner/repo slug becomes claimable by a third party while old remotes/links still reference the old slug), Desktop's background refresh will silently accept the new object's `clone_url` and rewrite the user's `origin` remote to point at it.

Compare this to the deliberate, user-facing safeguard that exists elsewhere in the same codebase for a structurally identical situation — the "upstream remote points elsewhere" dialog, which explicitly asks the user before changing a remote URL: [6](#0-5)  `updateRemoteUrl` bypasses this kind of explicit confirmation entirely for the `origin`/default remote — the remote that `git push`/`git fetch`/`git pull` operations actually use by default.

### Impact Explanation
If `origin` is silently rewritten to an attacker-controlled clone URL:
- Future `git push` operations (including committed source code, potentially secrets) are silently sent to the attacker's repository instead of the user's intended destination — this is exactly the "silent corruption of what the user commits or pushes" impact category.
- Future `git fetch`/`git pull` operations will pull attacker-supplied history/content into the user's local repository under the guise of the "same" project, which can be leveraged for supply-chain injection into what the developer believes is their own repo.
- Because the credential trampoline resolves the account to use for authentication by matching the *host* of the URL Git is currently authenticating against (`findGitHubTrampolineAccount`, matching by origin) [7](#0-6) , if the attacker keeps the same GitHub.com/GHE host (which is required for `matchGitHubRepository`/`repositoryMatchesRemote`'s hostname check to trigger the refresh flow at all), the user's legitimate GitHub token continues to be used, so the push/fetch to the attacker's repo/organization succeeds transparently and the user does not see any authentication prompt that might tip them off.

### Likelihood Explanation
This path executes automatically as part of routine background repository refresh (`repositoryWithRefreshedGitHubRepository` is invoked from many refresh call sites in `app-store.ts`, e.g. `withRefreshedGitHubRepository`) whenever Desktop doesn't currently have an account association or is doing a periodic repository-info refresh — the user does not need to take any unusual action beyond having the app open with the repository present. The attacker's required action is limited to causing the `owner/name` slug on the same GitHub host to resolve, at fetch time, to a different repository object with a different `clone_url` than what Desktop has cached — a scenario that maps to known GitHub account/repo-name reclamation ("repo-jacking") issues rather than any local/physical access, admin rights, or credential compromise on the victim's machine.

### Recommendation
- Do not trust `clone_url` from a freshly fetched `IAPIRepository`/`IAPIFullRepository` object as authoritative for automatically rewriting a user's configured remote. Instead, tie the cached `GitHubRepository` record to GitHub's immutable numeric repository `id` and only apply an automatic `set-url` when the freshly-fetched object's `id` matches the previously recorded id (i.e., it is genuinely the same repository that was merely renamed/moved), not merely when owner/name/hostname parsing lines up.
- If the `id` cannot be verified as unchanged, treat the situation the same way `UpstreamAlreadyExists` treats a stale upstream remote: show an explicit confirmation dialog before calling `setRemoteURL` on the default/origin remote.
- Add regression tests asserting that `updateRemoteUrl` never rewrites the default remote when the API-returned repository's persistent id differs from the cached one, even if owner/name/protocol heuristics match.

### Proof of Concept
1. Attacker-controlled precondition: the same `owner/name` slug on a GitHub host that a victim's Desktop `origin` remote currently points to becomes bound, at the API level, to a different repository (e.g., through a rename/deletion-then-reclamation of the owner or repo name — a well-documented class of GitHub dangling-reference issue), and that new repository's `clone_url` differs from the originally cached one (e.g. it now differs by owner or name suffix).
2. Victim already has this repository added in GitHub Desktop, with a cached `GitHubRepository.cloneURL` equal to the original (now-stale) URL, and has not manually altered `origin`.
3. Desktop performs one of its routine background refreshes, calling `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository`, which parses `owner`/`name` off the still-unchanged local `origin` URL [8](#0-7) , calls `api.fetchRepository(owner, name)`, and gets back the attacker's repository object with a different `clone_url`.
4. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (local remote still equals old cached clone URL), `urlsMatch === false` (new clone_url differs) and therefore calls `gitStore.setRemoteURL(...)`, silently pointing `origin` at the attacker's repository [9](#0-8) , verified by the existing test `"updates the repository's remote url when the github url changes"` [10](#0-9)  which demonstrates the exact mechanics (only the trust source of `clone_url` differs between the legitimate-rename case tested here and the attacker-controlled case above).
5. The next time the victim runs `git push`/`git fetch` from Desktop, code and/or credentials-backed operations are transparently directed at the attacker's repository.

    repository: Repository

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string

  const accounts = await accountsStore.getAll()
