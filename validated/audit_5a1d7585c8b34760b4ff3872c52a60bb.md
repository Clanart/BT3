### Title
Unauthenticated `send_tx` JSON-RPC Endpoint Allows Unauthorized Transaction Injection and Fee Wallet Drain — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The tx-sender JSON-RPC server exposes `send_tx` (and `send_citrea_tx`) over plain HTTP with no authentication, no TLS, and no caller restriction. When the server is bound to `0.0.0.0` — an explicitly supported and documented configuration — any network-reachable party can inject arbitrary transactions into the tx-sender queue with any `FeePayingType`. Submitting valid Bitcoin transactions with `FeePayingType::CPFP` or `FeePayingType::RBF` causes the tx-sender to spend from its own Bitcoin Core wallet to pay fees on behalf of the attacker, draining the fee wallet. An empty fee wallet prevents the bridge from fee-bumping kickoff, challenge, and payout transactions, breaking liveness and, in the worst case, enabling a fraudulent operator to steal bridged BTC by preventing timely challenge confirmation.

---

### Finding Description

`start_jsonrpc_server` in `crates/clementine-tx-sender/src/jsonrpc/server.rs` builds a plain `jsonrpsee` HTTP server with no middleware, no token, no mTLS, and no IP allowlist:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
    .build(bind_addr)
    .await
    ...
``` [1](#0-0) 

The `send_tx` handler accepts a fully caller-controlled `InsertTryToSendParams` — including `signed_tx_hex`, `fee_paying_type`, `cancel_outpoints`, `cancel_txids`, `activate_txids`, and `activate_outpoints` — and passes them verbatim to `TxSenderClient::insert_try_to_send`:

```rust
module.register_async_method("send_tx", |params, client, _| async move {
    let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;
    ...
    let try_to_send_id = client
        .insert_try_to_send(
            &mut dbtx,
            req.tx_metadata,
            &signed_tx,
            req.fee_paying_type,   // ← attacker-controlled
            req.rbf_signing_info,
            &req.cancel_outpoints,
            ...
        )
        .await
        .map_err(jsonrpc_err)?;
``` [2](#0-1) 

The bind address is configurable as either `127.0.0.1` or `0.0.0.0`. The code explicitly validates and accepts `0.0.0.0`:

```rust
if bind != "127.0.0.1" && bind != "0.0.0.0" {
    return Err(BridgeError::EnvVarMalformed(...));
}
``` [3](#0-2) 

The `run.sh` smoke-test script documents `TX_SENDER_JSONRPC_BIND` as a first-class operator-settable variable, defaulting to `127.0.0.1` but with `0.0.0.0` as the other accepted value: [4](#0-3) 

By contrast, every gRPC server uses mTLS with the `OnlyAggregatorAndSelf` interceptor that verifies the leaf certificate of the peer: [5](#0-4) 

The JSON-RPC server has no equivalent guard.

---

### Impact Explanation

When `TX_SENDER_JSONRPC_BIND=0.0.0.0` (e.g., in a Docker deployment where the port is reachable from the container network or the internet):

1. **Fee wallet drain via CPFP**: An attacker submits a valid Bitcoin transaction (spending their own UTXOs) with `fee_paying_type: CPFP`. The tx-sender broadcasts the parent, then creates a CPFP child transaction spending from its own Bitcoin Core wallet to pay fees. The attacker's transaction is confirmed at the bridge's expense. Repeating this drains the fee wallet.

2. **Fee wallet drain via RBF**: With `fee_paying_type: RBF`, the tx-sender calls `fund_raw_transaction` on the Bitcoin Core wallet to add inputs and fees, again spending bridge-controlled UTXOs.

3. **Liveness break**: Once the fee wallet is empty, the tx-sender cannot fee-bump kickoff transactions (operator collateral flow), challenge transactions (watchtower fraud detection), or payout transactions (withdrawal flow). This matches the `tx-sender-managed balances` and `bridge safety/liveness` impact criteria.

4. **Safety break**: If the fee wallet is drained before a watchtower's challenge transaction is confirmed within the BitVM2 challenge window, a fraudulent operator's payout transaction can confirm unchallenged, stealing bridged BTC.

The `InsertTryToSendParams` struct exposes the full power of the queue API — including `cancel_outpoints`, `cancel_txids`, `activate_txids`, and `activate_outpoints` — to any unauthenticated caller: [6](#0-5) 

---

### Likelihood Explanation

- The vulnerability is reachable whenever `TX_SENDER_JSONRPC_BIND=0.0.0.0` is set, which is an explicitly documented and validated configuration option.
- In containerized deployments (Docker Compose, Kubernetes), `0.0.0.0` is a common choice to allow inter-container communication.
- No special knowledge of the bridge internals is required; a plain HTTP POST with a valid Bitcoin transaction hex is sufficient.
- The attacker only needs a small amount of BTC to fund the initial parent transactions.

---

### Recommendation

1. **Add authentication to the JSON-RPC server.** Implement a shared-secret bearer token, mTLS (matching the gRPC pattern), or Unix-domain-socket-only binding so that only co-located bridge processes can call `send_tx`.

2. **Restrict the bind address.** Remove `0.0.0.0` as a valid option, or at minimum emit a loud warning and require an explicit opt-in flag when it is used.

3. **Validate the caller's identity inside the handler.** Even if network-level controls exist, add an application-level check (e.g., a pre-shared token in the request body or HTTP header) so that misconfigured deployments do not silently become exploitable.

---

### Proof of Concept

**Setup**: Operator deploys tx-sender with `TX_SENDER_JSONRPC_BIND=0.0.0.0` and `TX_SENDER_JSONRPC_PORT=3030`. The tx-sender's Bitcoin Core wallet holds 0.1 BTC for fee payments.

**Attack**:

```bash
# 1. Attacker creates a valid Bitcoin transaction spending their own UTXO
RAW_TX_HEX="<attacker_signed_tx_hex>"

# 2. Attacker submits it to the unauthenticated JSON-RPC endpoint
curl -sS -H 'content-type: application/json' \
  --data '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "send_tx",
    "params": [{
      "tx_metadata": null,
      "signed_tx_hex": "'"$RAW_TX_HEX"'",
      "fee_paying_type": "CPFP",
      "rbf_signing_info": null,
      "cancel_outpoints": [],
      "cancel_txids": [],
      "activate_txids": [],
      "activate_outpoints": []
    }]
  }' \
  http://<bridge_host>:3030
``` [7](#0-6) 

3. The tx-sender broadcasts the parent transaction (valid, confirmed by Bitcoin network), then creates a CPFP child spending from its own wallet.
4. Attacker repeats with fresh UTXOs until the fee wallet is empty.
5. With the fee wallet drained, the tx-sender can no longer fee-bump the watchtower's challenge transaction. A fraudulent operator's payout transaction confirms unchallenged.

The `spawn_txsender_loop` function confirms the JSON-RPC server is started unconditionally when `jsonrpc` config is present, with no authentication layer added before or after: [8](#0-7)

```rust
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
