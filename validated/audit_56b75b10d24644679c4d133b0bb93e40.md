### Title
Cross-precompile balance-event reentrancy corrupts EVM StateDB balances during ICS20 transfers of hook-bearing native ERC20 tokens - (File: precompiles/common/balance_handler.go)

### Summary
This is the Cosmos EVM analog of the ERC5115Form "reward token also input token" bug. In the Superform case, a permissionless `claimRewards` call interleaved into a swap inflated a direct-deposit amount because the vault's accounting relied on a before/after balance diff that didn't account for reentrant reward accrual. In Cosmos EVM, the `BalanceHandler` (`precompiles/common/balance_handler.go`) uses the identical "snapshot event-log length, then replay all new events" pattern (`BeforeBalanceChange` / `AfterBalanceChange`) to sync native balances from `ctx.EventManager()` into the EVM `StateDB`. Because the `sdk.Context`'s `EventManager` is process-wide/shared for the whole transaction, a nested precompile call triggered mid-flight (e.g., a malicious native ERC20's `_beforeTokenTransfer` hook calling `DISTRIBUTION_CONTRACT.claimRewards`) emits `EventTypeCoinSpent`/`EventTypeCoinReceived` bank events that get appended to the *same* event log the outer precompile call (e.g. ICS20 `transfer`) is watching. The outer call's `AfterBalanceChange` then replays *all* events since its own `prevEventsLen`, including the events generated by the fully-independent nested claim, double-applying balance deltas to the `StateDB` that are inconsistent with the actual bank-keeper ledger.

### Finding Description
`BalanceHandler.BeforeBalanceChange` (`precompiles/common/balance_handler.go:46-48`) records `len(ctx.EventManager().Events())` before a precompile's native action runs, and `AfterBalanceChange` (`balance_handler.go:68-136`) walks `events[bh.prevEventsLen:]` after the action completes, applying `StateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived` event found in that slice.

`Precompile.runNativeAction` (`precompiles/common/precompile.go:57-125`) creates one `BalanceHandler` per precompile `Run` invocation via the `BalanceHandlerFactory`, and executes `action(ctx)` between the `Before`/`After` calls. However, the `ctx` (and its `EventManager`) is not scoped to that single call — the same context flows into nested/recursive EVM calls made from within the action (e.g., a native ERC20's Solidity `_beforeTokenTransfer` hook invoked during a bank `SendCoins` performed by the outer precompile, which itself calls into another precompile such as `distribution.claimRewards`).

The repository's own regression tests confirm this exact class of bug:
- `evmd/tests/integration/balance_handler/balance_handler_test.go:23-25` states the suite "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... This leads to balance desync between native bank keeper and EVM stateDB." [1](#0-0) 
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` reproduces this with a real attack shape: a native ERC20 contract overrides `_beforeTokenTransfer` to loop and call `claimRewards()` on the distribution precompile during an ICS20 transfer of that ERC20-backed token: [2](#0-1) 
- The test's own comment identifies the reachable root cause: "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated." [3](#0-2) 
- The "without reverts" test case explicitly asserts the corrupted post-transfer state: the contract's native bank balance ends at `50` (non-zero) purely as a side effect of the reentrant `claimRewards` calls interleaved with the ICS20 transfer/escrow flow, and the event count comment ("20 base events + (1 successful reward claim + 1 send + 1 receive + 1 message + 1 transfer) + 4 empty reward claims") documents that events from the unrelated nested reward claim are counted alongside the outer transfer's own events: [4](#0-3) 

The underlying invariant broken is the "Asset-representation path" (x/erc20/bank/StateDB consistency) and "VM state path" (nested-call/journal consistency) pivots called out in the task: `x/erc20`, bank, and precompile flows must preserve 1:1 accounting between native coins and EVM-visible (`StateDB`) balances, and nested-call execution must not corrupt sibling/ancestor accounting.

### Impact Explanation
An unprivileged attacker who registers (permissionlessly, per `RegisterERC20` — `x/erc20/keeper/msg_server.go:324-361`) or otherwise controls a native ERC20 token pair with a malicious transfer hook can:
1. Trigger a bank-mediated action (ICS20 transfer, `ConvertCoin`/`ConvertERC20`, or any precompile call that moves the hook-bearing token) that internally calls the ERC20 contract's `transfer`, invoking the attacker's hook.
2. From the hook, recursively invoke another stateful precompile (distribution `claimRewards`, staking, bank, etc.) that emits its own `CoinSpent`/`CoinReceived` events into the same shared `ctx.EventManager()`.
3. The outer precompile's `AfterBalanceChange` then incorrectly aggregates the nested precompile's balance-changing events into the `StateDB`, producing an EVM-visible balance for arbitrary accounts (including the attacker/contract) that diverges from the actual bank-keeper ledger.

This is a direct instance of "irreversible accounting corruption of spendable user value across native balances / EVM balances" — StateDB balances (what all subsequent EVM logic, ERC20 `balanceOf` views via `x/vm`, and JSON-RPC balance queries within the same block report) desync from the bank module's ground truth. Depending on the direction of the desync this can manifest as free minting of spendable EVM-visible balance (theft/inflation) or loss of balance visibility (freezing), both of which are Critical per the allowed-impact gate.

### Likelihood Explanation
High likelihood/reachability: ERC20 token-pair registration is permissionless (`RegisterERC20`, `x/erc20/keeper/msg_server.go:324-361`), and any unprivileged user can deploy a contract with a custom `_beforeTokenTransfer`/`_afterTokenTransfer` hook, register it as a native ERC20 token pair, and then execute an ordinary transaction (ICS20 transfer, `MsgConvertCoin`, or a direct EVM transfer) to trigger the hook mid-flight. No privileged role, validator collusion, or governance action is required — this matches "ordinary transaction, contract, precompile, hook, or block-processing flow" from the Admission/Public-surface pivots. The repository maintainers have already written dedicated regression tests reproducing this exact scenario, indicating the bug class is real and was specifically investigated.

### Recommendation
Scope `BalanceHandler.prevEventsLen` (and the event replay window) to only the events emitted by the specific precompile invocation, not a shared/monotonic counter over the whole transaction-wide `EventManager`. Concretely:
- Execute nested/recursive precompile-triggered EVM calls (hooks) in an isolated cache context with its own `EventManager`, so that a nested precompile's `BeforeBalanceChange`/`AfterBalanceChange` pair only ever observes and consumes events it generated itself, and those events are not visible to (or re-consumed by) an ancestor call's `AfterBalanceChange`.
- Alternatively, track/consume events by index range with strict LIFO scoping (push/pop `prevEventsLen` per call depth, similar to how `AddPrecompileFn`/journal snapshots already track call depth) rather than storing a single mutable `prevEventsLen int` field, and ensure any events consumed by a nested call are excluded from the parent's slice before the parent computes its own applicable event range.
- Add an invariant check that sums of `StateDB`-applied balance deltas for the native `EvmCoinDenom` match the bank keeper's ledger delta for the same accounts at the end of each top-level transaction.

// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// AfterBalanceChange processes the recorded events and updates the stateDB accordingly.
// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
