### Title
Stale line-index `DiffSelection` reused against a freshly re-fetched diff silently corrupts partial commits - ([File: app/src/lib/git/apply.ts])

### Summary
This is the closest Desktop analog to the `TroveManager::openTrove` bug class: a value (`supply`/`totalActiveDebt`) is cached, an update happens that changes the "real" state, and the code then applies the *stale* cached value on top of the updated state instead of re-deriving it. In Desktop, the analogous cached value is a `WorkingDirectoryFileChange.selection` (`DiffSelection`), which records which *line indices* of a diff the user chose to include in a commit. That selection is carried forward across repository refreshes and is later applied against a **freshly re-fetched diff** at staging time, with no verification that index `N` still refers to the same content it did when the user made their selection.

### Finding Description
When a user partially stages a file (checking individual added/removed lines rather than the whole file), the selection is stored as an index-based `DiffSelection`: [1](#0-0) 

On every repository refresh, `updateChangedFiles` merges the new `IStatusResult` with the existing working-directory state and blindly re-attaches the **old** `existingFile.selection` object onto the **new** file entry, without any check that the diff content has stayed the same: [2](#0-1) 

The only place that attempts to reconcile a selection with an updated diff is `updateChangesWorkingDirectoryDiff`, and it explicitly does *content-agnostic* index bookkeeping only, and only for the single file currently displayed in the diff pane (it bails out entirely when zero or more than one file is selected for viewing): [3](#0-2) [4](#0-3) 

The comment at lines 3480-3485 is a direct admission of the broken invariant: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines."* This only filters out indices that no longer exist — it does **not** verify that index `N` still corresponds to the same line text it did before.

At commit time, `_commitIncludedChanges` takes whatever `selection` is currently attached to each file in `state.changesState.workingDirectory.files` (which may never have been reconciled at all, if that file wasn't the one being actively viewed) and hands it to `createCommit`: [5](#0-4) 

`createCommit` → `stageFiles` routes partially-selected files to `applyPatchToIndex`, which re-fetches a **brand-new** diff from disk/index right before building the patch: [6](#0-5) 

`formatPatch` then walks that *new* diff's hunks and asks `file.selection.isSelected(absoluteIndex)` — using the **old**, potentially unrelated, index set — to decide which lines go into the patch: [7](#0-6) 

This is structurally identical to the Solidity bug: a value (`supply` / here, the line-selection) is cached before an intervening update (`_accrueActiveInterests` / here, the working tree being changed by a refresh, fetch, checkout, or hunk-shifting edit), and the code then commits state built from the stale cached value composed with the *new* underlying state (`totalActiveDebt = supply + _compositeDebt` / here, `formatPatch(file, newDiff)` using `file.selection` computed against the old diff), instead of first re-deriving the cached value from the current state.

### Impact Explanation
If the working-directory content of a file changes between the moment a user selects specific lines to include in a commit and the moment they click "Commit" — for example due to a background repository refresh, a fetch/fast-forward of the current branch, a stash pop, or a PR/branch checkout that happens to touch the same file — the absolute line indices the user "selected" can silently point at entirely different content in the new diff. The resulting commit (and any subsequent push) can therefore contain lines the user never reviewed or intended to include, or omit lines they did intend to include, without any error or warning. This is a silent corruption of what the user commits/pushes, which matches the specified valid-impact category directly, since the divergent content the user unknowingly commits could originate from a remote/fork the user fetched or checked out.

### Likelihood Explanation
The reconciliation gap is narrow but real: it only protects the single file actively shown in the diff viewer, and even there only guards against out-of-bounds indices, not content drift. Any workflow where (a) a file has a partial (line-level) selection, (b) the user is not actively looking at that file's diff when the underlying content changes, and (c) a repository refresh (`_loadStatus`/`_refreshRepository`) occurs before the commit is made, is sufficient to trigger the mismatch — no unusual local access or privileges are required, only ordinary Desktop usage combined with content changing in the working tree from a fetched/checked-out source.

### Recommendation
Do not persist or reuse a `DiffSelection`'s absolute line indices across a diff refresh unless the new diff is verified to be identical (e.g., by hash) to the diff the selection was computed against. When the underlying diff for a file changes for any reason (status refresh, fetch, checkout, stash operations), either: (1) recompute/re-diff and re-validate every file with a non-`All`/`None` selection — not just the one currently displayed — comparing actual line content rather than just index bounds, or (2) fall back to full-file inclusion/exclusion (clear the partial selection) for any file whose diff has changed since the selection was last validated, mirroring the `clearPartialState` behavior already used elsewhere. `applyPatchToIndex` should also assert that the diff it fetches for staging matches (by hash/hunk identity) the diff associated with the `selection` it's about to apply, and abort/re-prompt rather than silently building a patch from mismatched data.

### Proof of Concept
1. Open a repository in Desktop with a modified file `foo.js` containing multiple hunks.
2. In the Changes view, partially select only certain added lines in `foo.js` for commit (line-level checkboxes), leaving other lines unselected. This selection is stored in `state.changesState.workingDirectory.files[...].selection` keyed by absolute diff-line index — [8](#0-7) .
3. Without switching the currently-viewed diff file (so `updateChangesWorkingDirectoryDiff`'s single-file reconciliation never touches `foo.js`), trigger any operation that updates `foo.js` on disk and causes a repository refresh — e.g., fetch and fast-forward the current branch from a remote whose latest commit also touches `foo.js`, shifting its hunks — via `_refreshRepository` → `_loadStatus` → `updateChangedFiles`, which reattaches the old `selection` onto the new file object — [2](#0-1) .
4. Click Commit. `_commitIncludedChanges` passes the file (with its stale selection) to `createCommit` → `stageFiles` → `applyPatchToIndex`, which fetches the *new* diff and calls `formatPatch(file, newDiff)` — [9](#0-8) , [7](#0-6) .
5. Inspect the resulting commit: it will include/exclude lines by position, not by the content the user actually reviewed and checked, demonstrating silent corruption of the committed content relative to user intent.
