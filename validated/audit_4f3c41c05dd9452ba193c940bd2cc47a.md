### Title
Coinbase outputs are reported as spendable received funds after `CONFIRMATIONS` (6) blocks while Bitcoin consensus enforces a 100-block maturity bound — the scanner's acceptance check and the protocol's spendability check use different minimums - (networks/bitcoin/src/wallet/scanner.rs)

### Summary
`bitcoin-serai`'s `Scanner` treats every transaction output paying to the multisig `script_pubkey` identically: it matches outputs purely on `script_pubkey` and emits a `ReceivedOutput` once the block is past `N::CONFIRMATIONS` (= 6 for `Bitcoin`). It never distinguishes coinbase (block reward) transactions, which Bitcoin consensus renders unspendable until 100 confirmations. The deposit-acceptance bound (6 confirmations) and the actual spendability bound (100 blocks) are computed by two different rules, exactly mirroring `_canDeposit` vs `getMaxDeposit` disagreeing on the maximum.

### Finding Description
In `processor/src/networks/bitcoin.rs`, `Bitcoin` declares `const CONFIRMATIONS: usize = 6`, and the scanner loop in `processor/src/multisigs/scanner.rs` only scans blocks up to `latest - (CONFIRMATIONS - 1)`, treating that as final. On the Bitcoin side, `Scanner` (`networks/bitcoin/src/wallet/scanner.rs`, used via `scan`/`scan_transaction` in `networks/bitcoin/tests/wallet.rs:249`) produces a `ReceivedOutput` for any output whose `script_pubkey` matches a registered offset key — there is no check that the containing transaction is a coinbase, nor any per-output maturity bound distinct from `CONFIRMATIONS`. Meanwhile `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:156-256`) will happily consume such an output as an input: it only checks `NoInputs`, dust, fee and weight, none of which encode coinbase maturity.

So the same logical quantity — "when may this output be used" — is evaluated two ways:
- Report/credit path: `block_number + CONFIRMATIONS (6) <= latest` ⇒ output reported as a received, schedulable `Output`.
- Spend/enforcement path: Bitcoin consensus maturity = coinbase height + 100, which the spend path does not model at all; it only fails when the signed transaction is rejected by the node at broadcast (`send_raw_transaction`).

### Impact Explanation
An unprivileged party can cause the protocol to act on funds that are not spendable: any output in a coinbase transaction paying to the multisig's tweaked P2TR script (miners, or anyone able to influence a coinbase's outputs, can do this with public data) is reported to the coordinator as a valid received output after only 6 confirmations. The scheduler then builds `Plan`s and `SignableTransaction`s spending it; every signing round that includes the immature input produces a transaction the Bitcoin network will reject (`bad-txns-premature-spend-of-coinbase`), burning the multisig's fee budget on the other inputs and stalling the plan/rotation pipeline until the bad output is manually excluded. Funds are reported received that are not spendable — the concrete impact class required.

### Likelihood Explanation
Reachable by an unprivileged external party: coinbase outputs are created by miners, and any miner (or pool paying out to arbitrary addresses) can include a P2TR output to Serai's public multisig/offset keys in a coinbase. The public input is just a Bitcoin transaction the attacker causes to exist. No malicious validator, leaked key, or integrator misuse is required. Exploitation is opportunistic (requires mining or influencing a block), so likelihood is moderate rather than high, matching a Medium severity.

### Recommendation
Make the acceptance bound match the spendability bound, as the original report recommends unifying `_canDeposit` and `getMaxDeposit`. In `Scanner::scan`/`scan_transaction` (`networks/bitcoin/src/wallet/scanner.rs`), detect `tx.is_coinbase()` (or equivalently `tx.input[0].previous_output.is_null()`) and either skip such outputs entirely or tag `ReceivedOutput`/the scanning DB with an extended maturity so `processor` treats them as final only after 100 confirmations rather than `N::CONFIRMATIONS`.

### Proof of Concept
1. A miner creates a block whose coinbase transaction includes an output paying `p2tr_script_buf(multisig_key)` (the same script `Scanner` matches in `networks/bitcoin/tests/wallet.rs:226` and `crypto.rs`).
2. After 6 further blocks, `Scanner::run` (`processor/src/multisigs/scanner.rs:478-490`) deems the block confirmed (`latest - (CONFIRMATIONS - 1)`) and `scan_transaction` emits a `ReceivedOutput` — indistinguishable from a normal deposit.
3. The scheduler builds a `Plan` spending it; `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:156`) accepts it as an input since only dust/fee/weight are checked.
4. The threshold-signed transaction is published via `send_raw_transaction` (`networks/bitcoin/tests/wallet.rs:283`) and is rejected by the node as a premature coinbase spend, while Serai has already credited and planned around the output.

Note: this assessment is based on the indexed code; I could confirm the scanner keys matching solely on `script_pubkey` and the `CONFIRMATIONS = 6` bound, but the coinbase-immaturity handling in `scanner.rs` was not directly visible in the indexed snippets — if an explicit `is_coinbase`/maturity filter exists elsewhere in that file, this finding does not hold.
