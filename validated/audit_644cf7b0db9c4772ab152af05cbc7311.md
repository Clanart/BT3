## Analysis

The seed bug (Sherlock M-6) is about a **rate/multiplier that is fixed at position-creation time but the *evaluation* of accumulated value later uses a *different, mutable* rate**, letting positions realize a rate that never applied while they existed. The Hyperbridge local analog is in `pallet-consensus-incentives`.

### Title
Stale unpaid block spans are repriced at the current `cost_per_block` on payout, letting relayers drain treasury funds by delaying claims across a governance rate change - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::calculate_reward` pays a relayer `blocks * block_cost` where `blocks = latest_height - LastRewardedHeight` and `block_cost` is read live from `StateMachinesCostPerBlock` at call time. Because the watermark (`LastRewardedHeight`) can lag far behind `latest_height` (nobody is forced to claim promptly), and `block_cost` is a single governance-mutable value applied uniformly to the *entire* unpaid span, any relayer can withhold submitting a pending consensus update, wait for governance to raise `cost_per_block` via `update_cost_per_block`, then submit — collecting the full backlog of blocks at the new, higher rate even though most of that span accrued under the old (lower) rate.

### Finding Description [1](#0-0) 
`process_message` reads the *current* `StateMachinesCostPerBlock` value and passes it into `calculate_reward`: [2](#0-1) 
`calculate_reward` computes `blocks = latest_height.saturating_sub(baseline)` where `baseline` is `LastRewardedHeight` (or `previous_height` if never rewarded), and multiplies the *entire* span by the single `block_cost` value passed in — there is no per-block or per-epoch rate history; only one scalar value exists in storage: [3](#0-2) 
`update_cost_per_block` simply overwrites `StateMachinesCostPerBlock` with no interaction with `LastRewardedHeight` and no snapshotting of the old rate for the span accrued so far: [4](#0-3) 

Nothing forces `LastRewardedHeight` to stay close to `latest_height`; `on_executed` only fires when *some* relayer submits a `ConsensusMessage`, which is entirely voluntary and permissionless — anyone holding a valid consensus proof can relay. This is structurally identical to the seed bug's core defect: a rate applied to a position/span is evaluated using whatever the *current* governance-set value is, not the value(s) that were actually in force while that span/position accrued. In the seed report the imbalance favored old positions (locked-in low bonus) or new positions (higher bonus); here the imbalance favors whichever relayer chooses to submit *after* a rate hike, applied retroactively across the whole unclaimed backlog.

### Impact Explanation
This directly drains the pallet's `TreasuryAccount` (`T::Currency::transfer` in `process_message`) beyond the amount actually owed for the historical block span, because a large backlog can be repriced at an arbitrarily higher rate the moment governance raises `cost_per_block`. This is a genuine loss-of-funds / logic-attack vector against the treasury, matching the "stealing or loss of funds" and "logic attacks" categories in the impact gate — it is not merely a fairness/voting-imbalance issue like the original report, but an actual overpayment from a shared fund.

### Likelihood Explanation
- Submitting a `ConsensusMessage` to trigger `on_executed` is a permissionless relayer action — no privileged role, no malicious peer/prover assumption, and no need for a leaked key.
- The attacker only needs to *observe* a public governance call (`update_cost_per_block`) and choose to submit their otherwise-valid, pending consensus proof afterward instead of immediately — a legitimate ordering choice, not front-running someone else's specific transaction.
- The backlog naturally grows whenever a state machine goes multiple update cycles without anyone bothering to claim (no incentive to claim promptly at the old, lower rate), which is realistic operational behavior, not a contrived edge case.

### Recommendation
Do not apply a single "current" `block_cost` to a span that may span multiple rate regimes. Either:
1. Cap/checkpoint the reward calculation so that `update_cost_per_block` also stamps `LastRewardedHeight` forward to the height current at the time of the rate change (forcing an implicit "settle at old rate" before the new rate applies), or
2. Store rate history keyed by height/timestamp and integrate `block_cost` piecewise over the unpaid span instead of using a single scalar for the whole backlog, or
3. Bound how far `LastRewardedHeight` may lag `latest_height` (e.g., permissionless partial-claim keepers) so backlogs cannot grow large enough to make rate-timing profitable.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[X] = 1` via `update_cost_per_block`.
2. State machine `X` advances from height 1000 to height 100000 (99000 blocks) over time, but no relayer submits a consensus update that reaches `on_executed`/`process_message` for `X` (network keeps generating valid proofs; the relayer simply doesn't relay yet) — `LastRewardedHeight[X]` stays at 1000.
3. Governance later raises `StateMachinesCostPerBlock[X] = 10000` (a legitimate governance action reacting to market conditions, unrelated to the backlog).
4. The relayer now submits a consensus proof for `X` (a fully valid message they always had). `on_executed` → `process_message` → `calculate_reward` computes `blocks = 100000 - 1000 = 99000` and `reward = 99000 * 10000`, paid entirely from `TreasuryAccount`, even though 99000 of those blocks accrued while the rate was `1`.
5. Repeat with `reward_covers_only_unpaid_heights_after_rollback`-style test harness in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs`, but insert an `update_cost_per_block` call raising the rate between accumulating the backlog and calling `on_executed`, to show the payout scales with the new rate for the entire stale span.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

	#[pallet::call]
	impl<T: Config> Pallet<T> {
		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}
