## Title
Stale ERC-decimals invariant lets `hyper-fungible-token` mint/release wildly inflated cross-chain amounts once local asset decimals diverge - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales amounts between an EVM ERC-20's decimals and the local Substrate asset's decimals using `convert_to_balance`/`convert_to_erc20`, which compute `10 ** erc_decimals.saturating_sub(local_decimals)`. Safety of this math depends entirely on the invariant `erc_decimals >= local_decimals`, which is checked **only once**, at `register_token`/`update_token` time, and then frozen into the `Precisions` storage map. However, `local_decimals` used in `send()` and `on_accept`/`on_timeout` is **not** the value snapshotted at registration — it is re-fetched live from `<T::Assets as fungibles::metadata::Inspect<_>>::decimals(asset_id)` on every call. If the local asset's decimals metadata can change after registration (e.g. an asset owner updating their own asset's metadata), the frozen `erc_decimals` and the live `local_decimals` diverge, `saturating_sub` silently returns 0 instead of underflowing/erroring, and the scaling factor collapses to `10**0 = 1`. This causes raw base-unit amounts to be forwarded across chains as-is instead of being rescaled, producing amounts inflated by many orders of magnitude relative to what is actually escrowed/burned — a direct false-amount cross-chain acceptance exactly analogous to the reported "tokens with <18 decimals allow draining of funds" bug class.

`u8::saturating_sub` makes `erc_decimals.saturating_sub(local_decimals)` return `0` whenever `local_decimals > erc_decimals`, instead of erroring. A `0` exponent means `10**0 = 1`, i.e. **no rescaling is applied at all** — the function silently degrades from "convert between decimal bases" to "pass the raw integer straight through," even though the two bases are actually different (e.g., 6 vs 18 decimals — a factor of 10¹²).

Attack path: register a token where `config.decimals` (erc_decimals) is only marginally `>=` the local asset's decimals at registration time (e.g., both configured at 6). After registration, the local asset's decimals metadata is later increased (via whatever surface in the runtime's `Config::Assets` implementation allows an asset's own metadata to be updated — a routine, asset-scoped action, not a Hyperbridge-governance or relayer/prover action). From that point on:
- In `send()`, `decimals` is read live as the new (higher) value while `erc_decimals` stays frozen at the old (lower) value in `Precisions`. `convert_to_erc20(amount, erc_decimals, decimals)` computes `10**(erc_decimals.saturating_sub(decimals)) = 10**0 = 1`, so the raw local balance (now expressed in more base units per token due to the higher decimals) is forwarded unscaled as the ERC-20 `amount` in the outbound `Message`. The destination HyperFungibleToken/WrappedHyperFungibleToken EVM contract trusts this `amount` field and mints/releases it verbatim — inflated by `10^(new_local_decimals - erc_decimals)` relative to what was actually escrowed/burned on the Substrate side.
- Symmetrically, `on_accept`/`on_timeout` would under-mint locally in the reverse direction, but the outbound over-mint on the EVM side is the fund-draining direction: a small burn of the local asset (denominated in inflated decimal units) yields a proportionally massive, wrongly-scaled ERC-20 release/mint on the destination chain, draining that chain's token custody/backing.

This is structurally identical to the reported Beedle `Lender.sol` bug: a decimals mismatch that is not defensively re-validated at the point of use turns into a scaling error that inflates the effective amount transferred, letting an attacker extract value far beyond what was actually deposited/escrowed.

### Impact Explanation
This breaks the "moved exactly once and only to the rightful beneficiary and amount" guarantee for bridged fungible-token transfers. A successful exploit lets an attacker burn/lock a small, real amount of the local Substrate asset and cause the paired EVM contract to release/mint an amount inflated by up to `10^18` (in the extreme, if decimals go from 0 to 18), draining the destination-chain custody backing that token. This is a direct, unauthorized-amount cross-chain acceptance (false state/amount acceptance) and fund loss, matching the bounty's "stealing or loss of funds" / "transaction manipulation" / "false proof or state acceptance" categories.

### Likelihood Explanation
The likelihood hinges entirely on whether the runtime's concrete `Config::Assets` implementation permits an asset's decimals metadata to change after the asset has been registered with `hyper-fungible-token` — this could not be fully confirmed from the indexed code (the runtime wiring for `pallet_assets`/`Config::Assets` in `parachain/runtimes/{gargantua,nexus}/src/ismp.rs` was not retrievable in full within the available search). If the concrete asset implementation allows the asset's owner/issuer to call something equivalent to `set_metadata` on their own permissionlessly-created asset (a common pattern for "foreign asset" registries on Substrate parachains), the attacker needs no privileged Hyperbridge role at all — they only need to be the owner of an asset they registered themselves, which is squarely within the "unprivileged attacker" bar required by this bounty. If, instead, decimals for every asset usable with this pallet are immutable once set (frozen metadata, or only settable at asset creation before it can ever be registered), this specific path is not exploitable and only the general code-hygiene issue (missing defensive re-check of the invariant at every conversion call site) remains.

### Recommendation
- Re-validate `erc_decimals >= local_decimals` inside `convert_to_balance`/`convert_to_erc20` themselves (or at every call site in `send`, `on_accept`, `on_timeout`) and hard-fail (return an error) rather than silently degrading to a `10**0` no-op via `saturating_sub`.
- Snapshot and freeze the local asset's decimals at `register_token`/`update_token` time (store it alongside `erc_decimals` in `Precisions`), instead of re-fetching live decimals metadata on every `send`/`on_accept`/`on_timeout` call, so a post-registration metadata change cannot silently desynchronize the two sides of the conversion.
- If the underlying asset implementation allows decimals to mutate after creation, treat any registered asset's decimals as append-only/immutable from the pallet's perspective, or require re-registration (with a fresh invariant check and, ideally, a migration path for in-flight messages) whenever decimals change.

### Proof of Concept
Conceptual reproduction (concrete PoC would require the runtime's actual `Config::Assets` implementation to confirm decimals mutability, which could not be exhaustively verified from the indexed code):

1. Attacker creates/owns a fungible asset `A` on the Substrate chain with `decimals = 6`.
2. Attacker (or governance, doesn't matter — the check only runs once) calls `register_token` for `A` against an EVM chain with `config.decimals = 6`. The check `config.decimals >= local_decimals` (6 >= 6) passes; `Precisions[A][EVM] = 6` is stored permanently.
3. Attacker calls whatever asset-metadata-update entry point the concrete `Config::Assets` exposes to change asset `A`'s decimals from `6` to `18`. `hyper-fungible-token` has no hook into this and does not re-validate or re-register.
4. Attacker calls `send()` to transfer `1` unit of asset `A` (now `1 * 10**18` raw base units) to the EVM side.
   - `decimals` (live) = 18, `erc_decimals` (frozen) = 6.
   - `convert_to_erc20(1e18, erc_decimals=6, decimals=18)` computes `10**(6u8.saturating_sub(18)) = 10**0 = 1`.
   - `erc20_amount = 1e18 * 1 = 1e18`, encoded directly into the outbound `Message.amount`.
5. The destination HyperFungibleToken/WrappedHyperFungibleToken EVM contract, which believes token `A` has 6 decimals, mints/releases `1e18` raw units = `1,000,000,000,000` (one trillion) tokens instead of the `1` token actually burned — draining the custody/backing for that token on the destination chain. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
