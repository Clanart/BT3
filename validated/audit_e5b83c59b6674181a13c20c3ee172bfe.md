### Title
Interactive commit reorder/insertion uses default lexicographic `Array.sort()` on numeric row indexes, corrupting drag-and-drop reorder/squash/cherry-pick targeting - ([File: app/src/ui/history/commit-list.tsx])

### Summary
`CommitList.onDropDataInsertion` computes the row indexes of the dragged commits and sorts them with a bare `.sort()` call, which in JavaScript defaults to lexicographic (string) comparison rather than numeric comparison. For commit lists with 10 or more rows, this silently miscomputes which commits are "contiguous," which commit is being dropped "above itself," and ultimately which commit SHA is passed as the retained/base reference for the reorder, squash, or cherry-pick-via-drag operation.

### Finding Description
`onDropDataInsertion` computes indexes of dragged commits by looking them up in `this.props.commitSHAs` and sorts them for a contiguity check: [1](#0-0) 

`Array.prototype.sort()` without a comparator converts elements to strings and compares them lexicographically. For indexes that reach double digits (e.g. `2`, `10`), the default sort produces `[10, 2]` instead of `[2, 10]`, exactly analogous to the twTAP bug where the wrong index (`i` instead of `claimableIndex`) was used to pull data from a differently-ordered structure — here the "wrong index" comes from an unintentionally re-ordered array being treated as sorted-ascending.

This mis-sorted `commitIndexes` array feeds directly into:
- The contiguity check `commitsAreContiguous`, which determines whether the drop is a no-op.
- `firstDroppedCommitIndex = commitIndexes[0]`, used to detect "commits dropped right above themselves."
- `this.getLastRetainedCommitRef(allIndexes)`, which resolves the base commit reference passed to `this.props.onDropCommitInsertion(baseCommit, data.commits, retainedRef)`. [2](#0-1) 

Because the index ordering is wrong whenever the commit list (or the set of selected/dragged commits) spans row 10+, `getLastRetainedCommitRef` and the contiguous/no-op checks can pick the wrong retained commit or fail to detect a self-drop, causing the downstream reorder/squash/cherry-pick operation invoked from `dispatcher.ts` to act on the wrong base commit.

### Impact Explanation
This directly matches the "silent corruption of what the user commits or pushes" impact category: a drag-and-drop reorder, squash, or cherry-pick performed by the user against an attacker-supplied repository with a sufficiently long commit history can silently target the wrong commit as the insertion point. The user believes they are reordering/squashing commit A next to commit B, but the operation is executed against a different, wrong base commit due to the index corruption, altering the resulting history without any warning.

### Likelihood Explanation
Likelihood is moderate: it requires the commit list (or the set of dragged commits combined with the base index) to include indexes ≥10, which is trivially satisfied by any repository with a non-trivial history — an attacker only needs the victim to clone/fetch a repo with more than 10 commits and use Desktop's built-in drag-to-reorder/squash/cherry-pick feature, a completely ordinary workflow, not an unnatural user step.

### Recommendation
Replace the default `.sort()` call with an explicit numeric comparator, e.g. `commitIndexes.sort((a, b) => a - b)`, mirroring the fix pattern in the original report of using the correct/intended index rather than an incidentally-wrong one.

### Proof of Concept
1. Open a repository in GitHub Desktop with at least 12 commits visible in the history list.
2. Multi-select two commits whose row indexes are e.g. `2` and `11`, and drag them to be inserted after row `9`.
3. In `onDropDataInsertion`, `commitIndexes` becomes `[2, 11]` before sort but `.sort()` (default) reorders to `[11, 2]` (string comparison: `"11" < "2"`), causing `commitsAreContiguous` and `firstDroppedCommitIndex` calculations, and the final `getLastRetainedCommitRef(allIndexes)` call, to use the wrong first element.
4. This can cause the app to treat the drop as a no-op when it should proceed (or vice versa) or to select the wrong retained commit SHA, resulting in the wrong commit being used as the reorder/squash base — silently altering the resulting commit history from what the user intended.

Note: I was unable to locate the exact body of `getLastRetainedCommitRef` and the downstream `dispatcher.ts` handlers in the indexed content (search returned only match counts, not code), so the precise git-level consequence (e.g., exact rebase `--onto` target) could not be fully traced end-to-end. Confirming the full downstream effect would require reviewing `app/src/ui/history/commit-list.tsx`'s `getLastRetainedCommitRef` method and `app/src/ui/dispatcher/dispatcher.ts`'s `onDropCommitInsertion`/reorder handling directly in a full checkout, which may exceed what the current index provides.
