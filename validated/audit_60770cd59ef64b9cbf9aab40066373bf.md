### Title
`Scanner::scan_block` reports immature coinbase outputs as received funds that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including the coinbase transaction at `block.txdata[0]`. Outputs received via a coinbase are bound by Bitcoin's 100-block maturity rule, yet `scan_block` returns them as ordinary `ReceivedOutput`s indistinguishable from spendable outputs. This is the Serai analog of the reported bug class: a protocol rule keyed on block height/number (coinbase maturity) whose semantics are invisible to the consumer of the API, so funds are reported received when they are not actually spendable.

### Finding Description
`scan_transaction` matches any output paying to a registered script and emits a `ReceivedOutput` carrying only the offset, `TxOut`, and outpoint — no flag distinguishing coinbase origin [1](#0-0) . `scan_block` then feeds every transaction in the block, including `txdata[0]` (the coinbase), through `scan_transaction` [2](#0-1) .

A miner (or a pool participant able to influence coinbase outputs — an unprivileged on-chain input) can place a P2TR output paying to a registered offset script in the coinbase. `scan_block` will report it identically to a normal deposit. However, Bitcoin consensus forbids spending that outpoint for 100 blocks, so any immediate spend constructed from it is invalid, and if the block is ever reorganized out before maturity the outpoint ceases to exist entirely — the reported funds were never spendable.

The doc comment acknowledges this only as a caller obligation ("a post-processing pass is needed to remove those outputs") [3](#0-2) , but nothing in the type system or API enforces it, and `ReceivedOutput` carries no `is_coinbase` marker to let a downstream consumer even perform that filtering reliably after the fact (it must re-fetch the block and check tx index). Notably, Serai's own processor separately re-implements this filtering by skipping `txdata[0]` in `get_outputs`, demonstrating that the raw `scan_block` result is unsafe as-is.

### Impact Explanation
Any consumer calling `scan_block` and crediting/queueing the returned outputs will treat immature coinbase outputs as confirmed received funds. Scheduling a spend of such an output produces a transaction that is consensus-invalid (rejected by the mempool and blocks) for 100 blocks, and if the containing block is orphaned the "received" funds vanish while the accounting already recorded them — funds reported received that are not spendable. This directly matches the accepted impact class.

### Likelihood Explanation
Any miner mining to a registered script (or anyone influencing a coinbase payout, e.g., via a mining pool payout address set to a Serai deposit script — a plausible accidental case) triggers the report. Deliberate exploitation requires mining a block, which limits frequency but not correctness: accidental triggering via pool payouts or batched coinbase outputs is realistic. Severity is Medium: requires a specific caller posture (crediting `scan_block` results without filtering) and a coinbase path.

### Recommendation
Skip `block.txdata[0]` inside `scan_block` (or mark coinbase-derived `ReceivedOutput`s with a flag and refuse to emit them until maturity is confirmable). At minimum, `scan_block` should mirror the processor's behavior of iterating `block.txdata[1 ..]` so the default API cannot return unspendable outputs, rather than relying on a documented caller-side post-processing pass.

### Proof of Concept
```rust
// networks/bitcoin regtest: mine a block whose coinbase pays a registered script
let key = /* multisig group key */;
let mut scanner = Scanner::new(key).unwrap();
let coinbase_script = p2tr_script_buf(key).unwrap();

// RPC: generatetoaddress(1, address_from_script(coinbase_script))
// The miner's coinbase output at txdata[0].output[0] pays our script.
let block = rpc.get_block(&rpc.get_block_hash(n).await).await;

let outputs = scanner.scan_block(&block);
// outputs[0] is a ReceivedOutput for OutPoint(coinbase_txid, 0).
// Spending it now is consensus-invalid (BIP-30/COINBASE_MATURITY = 100),
// and an orphan before maturity makes it permanently unspendable,
// yet it was reported as a normal received output.
```
The existing test even asserts this behavior: `outputs == scanner.scan_transaction(&block.txdata[0])` confirms the coinbase is returned verbatim [4](#0-3) .

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
