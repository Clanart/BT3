### Title
DataLayer mirror URLs enable SSRF via unrestricted outbound HTTP fetch in `fetch_and_validate`/`http_download` - (File: chia/data_layer/download_data.py)

### Summary
Any wallet holding a DataLayer singleton can publish arbitrary attacker-chosen URL strings on-chain as a "mirror" via the `dl_new_mirror` wallet RPC. Every other DataLayer node subscribed to (or owning) that store will subsequently pull those URLs into its local `mirrors`/`servers_info` table and automatically issue outbound HTTP GET requests to them from `fetch_and_validate` via `download_file`/`http_download`, with no validation that the URL points to a public, intended data-mirror host.

### Finding Description
`create_new_mirror` in `chia/data_layer/data_layer_wallet.py` lets any DL wallet owner spend a coin whose memos encode an arbitrary list of `urls`, with no format/scheme restriction beyond being decoded as UTF-8 strings [4](#0-3) . When that mirror coin is seen on chain, `DataLayerWallet.coin_added` decodes and stores those URLs verbatim into the `dl_wallet_store` mirrors table [5](#0-4) .

Any other node's `DataLayer` service periodically calls `update_subscriptions_from_wallet()`, which reads these mirror URLs from wallet RPC and stores them as the pool of `available_servers` for that store id, again without validation [3](#0-2) . During `fetch_and_validate()`, one of these attacker-supplied URLs is selected (randomly shuffled) and used directly as the download target [2](#0-1) , ultimately reaching `http_download()`, which opens a plain `aiohttp.ClientSession` and issues `session.get(server_info.url + "/" + filename, ...)` with no host/IP allow-listing, no blocking of loopback/link-local/private ranges, and default aiohttp redirect-following behavior [1](#0-0) .

This is structurally the same bug class as CVE-2025-32358: an authorized-but-untrusted actor (any wallet owner, analogous to an "authenticated admin" configuring a webhook) supplies a URL that is later fetched automatically by server-side code, and the fetching code performs no SSRF hardening (target validation or redirect restriction) — allowing that actor to make other operators' DataLayer nodes issue GET requests against arbitrary internal/local-network endpoints (e.g., cloud metadata services, internal admin panels, or loopback services) whenever they sync/subscribe to that store.

### Impact Explanation
An attacker who owns or controls a DataLayer store (trivial for any wallet user, no special privilege) can cause every peer node that subscribes to that store — including automated/service infrastructure running DataLayer for indexing or mirroring — to issue arbitrary outbound HTTP GET requests to attacker-chosen hosts. This can be used to probe internal networks, reach cloud-metadata endpoints (e.g., `169.254.169.254`) to potentially exfiltrate credentials, or interact with internal-only services that trust requests originating from the node's own network. Because `download_file`/`http_download` writes the response body to disk and later feeds it into `insert_from_delta_file`, response content is also partially consumer-controlled, compounding the impact beyond blind SSRF into potential resource exhaustion via `max_delta_file_size` bypass attempts on non-cooperating endpoints.

### Likelihood Explanation
Likelihood is high for triggering the SSRF request itself: creating a store and mirror coin is a normal, unprivileged DataLayer operation available to any wallet, and any node that chooses to subscribe (or that owns the store, since owned stores are pseudo-subscribed per `.cursor/context/data-layer.md`) will automatically fetch from the attacker-controlled URL without user interaction beyond the initial subscribe/own action .

### Recommendation
Validate and restrict mirror/server URLs before they are persisted as sync targets and before `http_download`/`download_file` dereference them: enforce an allow-list of schemes (http/https only), resolve and reject requests to loopback, link-local, private, and multicast address ranges (and re-validate after DNS resolution to prevent DNS-rebinding), and disable or bound automatic redirect following in the `aiohttp.ClientSession` used in `http_download` (`chia/data_layer/download_data.py`) and in the uploader/downloader plugin POST calls in `chia/data_layer/data_layer.py` (`get_uploaders`, `check_plugins`) and `download_data.py` (`download_file`).

### Proof of Concept
1. Attacker creates a DataLayer store and calls the wallet RPC `dl_new_mirror` (`chia/data_layer/data_layer_wallet.py:687`) with `urls=["http://169.254.169.254/latest/meta-data/", "http://internal-admin.local/"]` and pushes the transaction.
2. Any node that subscribes to (or already owns/pseudo-subscribes) that store id runs its normal `periodically_manage_data()` loop, calling `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979`), which pulls the attacker's URLs into that store's server list with no validation.
3. On the next `fetch_and_validate()` cycle (`chia/data_layer/data_layer.py:606`), the node selects one of these URLs and calls `download_file` → `http_download` (`chia/data_layer/download_data.py:110,298`), issuing an unauthenticated outbound GET request from the victim node's network context to the attacker-chosen internal/local address.
