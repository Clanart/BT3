### Title
`RebalanceTreasury`/`fillAllocated` silently swallows an RPC/contract-call failure and returns success, causing zeroed treasury balances to be burnt instead of redistributed - (File: `blockchain/system/rebalance.go`)

### Summary
`fillAllocated`, the helper used by `RebalanceTreasury` during the KIP‑103/KIP‑160 treasury-rebalance state transition, calls `contract.GetAllocatedCount(nil)` and, if that call returns an error, logs it and returns `nil` (success) instead of propagating the error. This exactly mirrors the CVE-2026-72496 bug class: a function returns success even though the underlying resource-retrieval step failed, so the caller proceeds as if the operation had completed correctly.

### Finding Description
`RebalanceTreasury` performs the deterministic state transition that executes at the KIP‑103/KIP‑160 hard-fork block: it zeroes out balances of "Zeroed" addresses and re-allocates the corresponding value to "Allocated" addresses read from a governance-configured rebalance contract. [1](#0-0) 

`fillZeroed` correctly propagates the error from `GetZeroedCount`:
```go
func (result *rebalanceResult) fillZeroed(contract RebalanceCaller, state *state.StateDB) error {
	numRetiredBigInt, err := contract.GetZeroedCount(nil)
	if err != nil {
		logger.Error(...)
		return err
	}
	...
}
```

But its sibling `fillAllocated` swallows the equivalent error and returns `nil`: [2](#0-1) 

```go
func (result *rebalanceResult) fillAllocated(contract RebalanceCaller, state *state.StateDB) error {
	numNewbieBigInt, err := contract.GetAllocatedCount(nil)
	if err != nil {
		logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
		return nil          // <-- BUG: should be `return err`
	}
	for i := 0; i < int(numNewbieBigInt.Int64()); i++ {
		...
	}
	return nil
}
```

Because `fillAllocated` returns `nil`, `RebalanceTreasury` treats the "Get Allocated" retrieval step as successful even though `result.After.Allocated` remains completely empty: [3](#0-2) 

The flow then continues:
- `totalAllocatedAmount := result.totalAllocatedBalance()` computes `0` since the map is empty.
- Validation step 4 (`totalZeroedAmount < totalAllocatedAmount`) never rejects the rebalance because the allocated total is artificially `0`.
- Execution step 1 still zeroes out every "Zeroed" address's balance.
- Execution step 2 iterates over the now-empty `result.After.Allocated` map, so **no funds are actually redistributed** to the intended new treasury addresses.
- The entire zeroed amount is folded into `result.Burnt` as "remainder", i.e., permanently destroyed instead of being moved to the addresses the governance-approved rebalance was supposed to fund.
- `result.Success` is still set to `true`, so the caller/consensus engine has no signal that anything went wrong.

This is the same bug class as CVE-2026-72496 (`bnxt_qplib_alloc_dpi` returning success despite `ioremap` failure): a resource/data-retrieval step fails, the wrapping function swallows the error and reports success, and the caller subsequently operates on incomplete/invalid state without any rollback.

### Impact Explanation
If the `GetAllocatedCount` call to the configured `Kip103ContractAddress`/`Kip160ContractAddress` ever fails or reverts at the exact hard-fork block (e.g., the contract is misconfigured, not yet fully initialized, hits an internal revert, or the call runs out of the implicit gas budget used by the `CallContract`/state-read path), every node executing `RebalanceTreasury` will silently zero the old treasury holders' balances while distributing zero KAIA to the new allocation targets — the entire amount is instead recorded as burnt. This is a supply-accounting/burn-accounting defect in a protocol-mandated state transition: legitimately-approved treasury funds are irrecoverably destroyed rather than transferred to the KIP‑103/KIP‑160-approved recipients, with `result.Success` misleadingly reporting success.

### Likelihood Explanation
This code path executes automatically and deterministically for every full node at the specific KIP‑103/KIP‑160 hard-fork block height, driven purely by the on-chain state of the governance-configured rebalance contract; it requires the paired retrieval call to fail for any reason (contract logic error, uninitialized/edge-case contract state, or an internal call failure) at that exact block. Given the sibling function `fillZeroed` correctly propagates the identical class of error, this looks like a copy-paste/logic inconsistency rather than an intentional design choice, making the erroneous "success" path plausible if the corresponding contract call is not always guaranteed to succeed.

### Recommendation
Change `fillAllocated` to propagate the error exactly as `fillZeroed` does:
```go
numNewbieBigInt, err := contract.GetAllocatedCount(nil)
if err != nil {
	logger.Error("Failed to get AllocatedCount from TreasuryRebalance contract", "err", err)
	return err
}
```
This ensures `RebalanceTreasury` aborts the rebalance (returning an error to the caller) instead of proceeding to zero out balances with an incomplete allocation set.

### Proof of Concept
1. Deploy/point `chain.Config().Kip103ContractAddress` (or `Kip160ContractAddress`) to a rebalance contract whose `getAllocatedCount()` (or its KIP‑160 equivalent) reverts or otherwise causes the bound Go caller `GetAllocatedCount(nil)` to return a non-nil error, while `getZeroedCount()` succeeds and returns a non-empty zeroed list.
2. Advance the chain to the configured KIP-103/KIP-160 rebalance block number and let block processing invoke `system.RebalanceTreasury`.
3. Observe that `fillAllocated` logs the error but returns `nil`; `RebalanceTreasury` proceeds, zeroes the balances of all "Zeroed" addresses, does not credit any "Allocated" address (loop body over an empty map never executes), adds the entire zeroed amount to `result.Burnt`, and returns `result.Success = true, err = nil` to the caller — silently destroying the treasury funds that governance intended to redistribute.
