### Title
Unhandled `AssertionError` in `compute_spend_hints_and_additions` on malformed `CREATE_COIN` puzzle hash — ([File: chia/wallet/util/compute_hints.py])

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` conditions produced by running an arbitrary, attacker-controlled `puzzle_reveal`/`solution` pair (from any coin spend a wallet processes: incoming CAT/DID/CR-CAT coins, singleton lineage lookups, and offer settlement). It extracts the puzzle-hash field with `.atom` and immediately asserts it is not `None`, with no exception handling, mirroring the CVE-2019-12101 pattern where an unexpected "null" field value (a cons/pair instead of the expected atom) is not defensively rejected and instead trips an unguarded fault.

### Finding Description
In `chia/wallet/util/compute_hints.py`:
```
rf = condition.at("rf").atom
assert rf is not None
``` [1](#0-0) 

`condition` here is a `CREATE_COIN` condition obtained by CLVM-executing `cs.puzzle_reveal` with `cs.solution` [2](#0-1) . Because CLVM has no static typing, the puzzle can output `(51 (a . b) amount ...)` where the second argument at `rf` is a cons pair rather than an atom. `.atom` on a pair returns `None`, so the `assert rf is not None` fails with a bare, unguarded `AssertionError`.

This function is invoked directly (no `try/except`) from several wallet code paths that process coin data received from the network or a counterparty:
- `CATWallet.identify()` — `hinted_coin = compute_spend_hints_and_additions(coin_spend)[0][coin_state.coin.name()]` [3](#0-2) 
- `DIDWallet.identify()` — same unguarded pattern [4](#0-3) 
- `WalletStateManager.find_lost_did()` [5](#0-4) 
- `TradeManager.calculate_tx_records_for_offer()` when validating an offer (`compute_spend_hints_and_additions(spend)` for each spend in the counterparty-provided settlement bundle) [6](#0-5) 

`identify()` is called for every newly-observed coin whose parent matches a known wallet's puzzle during wallet sync (`WalletStateManager`), so a coin created with a malformed `CREATE_COIN` puzzle-hash argument that is sent to (or observed by) a victim wallet will propagate an unhandled `AssertionError` up through that sync/identification call chain. Unlike the one call site inside `CRCATWallet.add_crcat_coin` and `Offer.__post_init__`, which wrap the call in `try/except Exception`, the `CATWallet.identify`, `DIDWallet.identify`, and `find_lost_did` call sites have no such guard [7](#0-6) [8](#0-7) .

### Impact Explanation
An `AssertionError` raised inside the wallet's coin-identification/sync pipeline is a spend-triggered fault: any party can construct a coin spend (e.g. a CAT, DID, or offer settlement coin) whose `CREATE_COIN` output uses a non-atom (pair) value in place of the puzzle hash. Once this spend is confirmed on chain (or supplied as an offer to be validated), a wallet that syncs to it or validates the offer will hit the unguarded assertion, halting that wallet operation (transaction-processing/sync halt for the affected wallet, or failure to validate/accept an otherwise-valid offer). This matches the "spend-triggered transaction-processing halt" impact category in scope for this triage. It does not directly cause coin-set divergence between full nodes (this code is wallet-side, not consensus validation), so severity is bounded to wallet-side denial of service rather than a chain-consensus break.

### Likelihood Explanation
Likelihood is High for a wallet user or offer counterparty: constructing a CLVM puzzle that outputs `(51 (c A B) amount)` for the puzzle-hash slot of a `CREATE_COIN` condition is trivial and requires no special privileges — any spend-bundle submitter or offer creator controls the puzzle/solution pair entirely. The only precondition is that a victim's wallet processes that specific coin (as an incoming CAT/DID coin or as part of an offer it is asked to validate), which is a routine wallet action (accepting an offer, syncing state for a coin sent by a counterparty).

### Recommendation
Replace the bare `assert rf is not None` with an explicit, catchable validation error (e.g. raise `ValidationError`/`ValueError` as is already done elsewhere in this same function for cost overruns), and audit all call sites of `compute_spend_hints_and_additions` (`CATWallet.identify`, `DIDWallet.identify`, `WalletStateManager.find_lost_did`, `TradeManager.calculate_tx_records_for_offer`) to ensure malformed `CREATE_COIN` output from an untrusted spend is handled gracefully (skip/log the malformed coin) rather than propagating an unhandled exception that halts wallet processing.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle, when run with its solution, outputs a condition list containing `(51 (c 0x1122 0x3344) 1000)` — i.e., `CREATE_COIN` with the puzzle-hash argument being a cons pair instead of a 32-byte atom.
2. Have this coin be a child of a coin tracked by a victim's `CATWallet` or `DIDWallet` (e.g., attacker sends/creates such a coin as the "next" CAT/DID coin observed by the victim wallet during sync), or submit it as the settlement spend of an `Offer` for the victim to validate.
3. When the victim wallet calls `identify()` (or `TradeManager.calculate_tx_records_for_offer`), `compute_spend_hints_and_additions` executes `condition.at("rf").atom`, which returns `None` for the pair, and the bare `assert rf is not None` raises an uncaught `AssertionError`, aborting that identification/validation call with no graceful handling.
