### Title
Fee and weight calculated on a transaction missing the OP_RETURN output, producing under-priced or oversized transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight and virtual size — and therefore the required fee and the `MAX_STANDARD_TX_WEIGHT` check — using `payments` only, after the OP_RETURN data output has already been pushed into `tx_outs`. The signed transaction is up to ~91 vbytes larger than the size the fee was priced for, so it pays a lower effective fee rate than `fee_per_vbyte` specifies and can evade both the minimum-relay-fee check and the maximum-standard-weight check. This is the same bug class as the reference report: a calculation performed on an incomplete/incorrect quantity produces a systematically wrong value, with the error compounding downstream.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [1](#0-0) 

`calculate_weight_vbytes` builds a mock `Transaction` whose outputs are derived solely from the `payments` slice plus an optional change script — `data` is never included [2](#0-1) . The OP_RETURN output pushed into `tx_outs` at lines 194–202 (8-byte value + script length + `OP_RETURN` + push opcode + up to 80 bytes of data, i.e. up to ~91 bytes / ~364 weight units) is therefore absent from `weight` and `vbytes`. The same omission recurs in the change path at line 225–227, which also calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` without the data output [3](#0-2) .

Three consequences follow, all because `needed_fee`, the minimum-fee gate, and the `MAX_STANDARD_TX_WEIGHT` gate are evaluated on a smaller transaction than the one actually signed:

1. `needed_fee = fee_per_vbyte * vbytes` underprices the real transaction by `fee_per_vbyte * (up to ~91)` satoshis. The shortfall is silently absorbed into the change output (or, absent change, inflates the actual fee — which is harmless) so when change exists the delivered TX pays a strictly lower effective sat/vbyte than requested.
2. The `TooLowFee` check compares against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` where `vbytes` is undercounted, so a transaction whose true fee rate is below the 1000 sat/kilo-vbyte relay minimum is accepted. Because inputs use `Sequence::MAX` (no RBF signalling, line 182) and the change output may be consumed by the fee, the resulting transaction can be unrelayable and un-bumpable.
3. The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses the undercounted `weight`, so a transaction genuinely over the standardness limit is not rejected.

`data` is attacker-influenceable input to `SignableTransaction::new` — it is the public API for constructing these transactions, and the function explicitly permits up to 80 bytes (line 171). Any caller-driven inclusion of `data` triggers the mispricing.

### Impact Explanation
The produced transaction pays a lower effective fee rate than the caller specified. In the worst case (small `fee_per_vbyte`, large `data`, change output present) the real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`, yielding a transaction that relay nodes reject. Since the inputs use `Sequence::MAX` the TX does not signal RBF, and with no change output (or change consumed) there may be no way to raise the fee — the funds it moves are effectively unspendable until it is mined via non-standard propagation, matching the "funds received that are not spendable" impact class. Additionally, the `TooLargeTransaction` guard can be bypassed, producing a transaction Bitcoin Core will never relay.

### Likelihood Explanation
Requires a caller of `SignableTransaction::new` to pass non-`None` `data` (the FROST-signed Bitcoin pipeline uses `data: None` per `processor/src/networks/bitcoin.rs:451`, so this is reachable only through direct library use or a future caller that sets `data`), combined with a low fee rate or near-limit weight. The miscalculation itself is deterministic whenever `data` is present — no adversarial timing needed. Medium-low likelihood, low-medium impact → Medium at most.

### Recommendation
Pass the OP_RETURN output into the weight/vbytes calculation. Either compute weight from `tx_outs` (and the change candidate) rather than `payments`, or thread `data` into `calculate_weight_vbytes` so the priced transaction is byte-identical in structure to the signed one, e.g.:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
```

with `calculate_weight_vbytes` taking `&[TxOut]` directly. Apply the same fix in the `fee_with_change` recalculation so both `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the final transaction.

### Proof of Concept
```rust
// 1 P2TR input paying 10_000 sat, 80-byte OP_RETURN, change back to self,
// fee_per_vbyte = 1 sat/vB.
let data = vec![0u8; 80];
let signable = SignableTransaction::new(
  inputs,                       // e.g. one ~20_000 sat ReceivedOutput
  &[(payment_script, 10_000)],
  Some(change_script),
  Some(data),
  1,                            // 1 sat/vbyte
).unwrap();

// vbytes was computed WITHOUT the ~91-byte OP_RETURN output.
// needed_fee = 1 * vbytes  (undercounted by ~91 sats)
// The change output absorbs the shortfall:
//   actual fee rate = (inputs - outputs) / real_vbytes < 1 sat/vB
// If real fee rate < 1000 sat/kvB, the TX is still constructed (the TooLowFee
// check used the same undercounted vbytes) yet fails DEFAULT_MIN_RELAY_TX_FEE
// on relay, and Sequence::MAX means it cannot be fee-bumped via RBF.
```

Concrete numbers: a 1-in/2-out TX is ~152 vB; adding an 80-byte OP_RETURN (~91 bytes) makes the real TX ~243 vB while `needed_fee` is priced for ~152 vB — an effective fee rate of ~0.63 sat/vB, below the ~1 sat/vB relay floor, accepted by `new()` but rejected by relay policy.
