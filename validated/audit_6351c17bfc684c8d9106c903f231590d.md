### Title
Out-of-bounds read / crash in `is_atom_canonical`/`is_clvm_canonical` CLVM canonicality check reachable from an unprivileged spend-bundle submission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical()` on the raw bytes of every submitted coin spend's `puzzle_reveal` and `solution` [1](#0-0) . This function walks the buffer byte-by-byte, and for multi-byte atoms delegates to `is_atom_canonical()`, which reads length-prefix continuation bytes at increasing offsets without ever checking that those offsets are within the buffer bounds [2](#0-1) .

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` decodes a variable-length atom-length prefix (1–6 bytes depending on the top bits of the first byte) and then loops `prefix_len` times, incrementing `offset` and indexing `clvm_buffer[offset]` each time, with no bounds check against `len(clvm_buffer)` [3](#0-2) . `is_clvm_canonical()`'s main loop similarly indexes `clvm_buffer[offset]` at the top of each iteration and calls `is_atom_canonical` without first verifying `offset < len(clvm_buffer)` [4](#0-3) . If an attacker crafts a `puzzle_reveal` or `solution` whose last byte is a high-order length-prefix marker (e.g. `0xFC`/`0xF8`/etc.) that declares a multi-byte length but the buffer ends right there, the loop reads past the end of the bytes object, raising an unhandled `IndexError` instead of the intended `False`/rejection outcome.

This mirrors the ALPINE-CVE-2019-3832 pattern precisely: the original canonicality/bounds check exists but is incomplete for the trailing/truncated case, exactly like the incomplete fix for CVE-2018-19758 in libsndfile's `wav_write_header()`, which still permitted a read beyond buffer limits despite an earlier partial fix.

This code path is reached directly from `validate_spend_bundle()`, which is invoked as part of ordinary spend-bundle admission for every coin spend in a submitted bundle — no privileged access or peer trust is required, only an RPC/wallet-protocol submission of a spend bundle whose `puzzle_reveal` or `solution` CLVM bytes are attacker-controlled [5](#0-4) .

### Impact Explanation
An unhandled `IndexError` raised out of `validate_spend_bundle()` during mempool admission is not part of the expected `Err` return contract of that function (which is documented to return `(Err | None, MempoolItem | None, list[bytes32])`). Depending on how the caller in the admission pipeline handles exceptions, this can propagate as an uncaught exception during spend-bundle processing, causing a crash/exception in transaction-processing for that call — a spend-triggered denial-of-service against the full node's mempool admission path, consistent with a "spend-triggered transaction-processing halt" in the validation scope defined by the rules.

### Likelihood Explanation
Likelihood is high for triggering the crash path: it only requires submitting a single spend bundle with a `puzzle_reveal` or `solution` byte string ending exactly at a truncated multi-byte atom length-prefix marker. Test coverage in the repo (`test_mempool_requires_canonical_clvm`, `test_atom_canonical`/`test_atom_not_canonical`) confirms this function is exercised by attacker-supplied hex data and is on the mandatory admission path for every spend, not an optional or feature-gated function [6](#0-5) .

### Recommendation
Add explicit bounds checks in both `is_atom_canonical()` and `is_clvm_canonical()` before every buffer index/slice: verify `offset < len(clvm_buffer)` prior to reading the initial byte, and verify enough remaining bytes exist for the declared `prefix_len` before looping over continuation bytes, raising/returning a graceful "not canonical"/`ValueError` outcome (mirroring the pattern already used in `chia/full_node/full_block_utils.py`'s `skip_bytes`/`skip_list`, which explicitly check remaining buffer length before indexing) rather than allowing a raw `IndexError` to escape.

### Proof of Concept
Submit a spend bundle whose `solution` (or `puzzle_reveal`) is the CLVM bytes `\xfc` (a single trailing byte announcing a 5-byte continuation length prefix with none following). When `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` → `is_atom_canonical(buf, 0)`, the decode determines `prefix_len = 5` and then loops incrementing `offset` and reading `clvm_buffer[offset]`, running off the end of the 1-byte buffer and raising `IndexError: index out of range` instead of returning `False`/an `Err`. This is directly analogous to the truncated/malformed length-prefixed data class of bug in ALPINE-CVE-2019-3832; I was not able to execute this PoC in this environment (no code execution access), so this reasoning is based on static analysis of the cited code paths — I recommend a Devin session with code execution to confirm the exact exception propagation behavior through `validate_spend_bundle()`'s caller in `add_spend_bundle`/mempool admission.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
