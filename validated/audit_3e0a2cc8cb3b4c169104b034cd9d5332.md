### Title
Adversarial offer file causes pathological CPU blowup in `Offer.get_cancellation_coins()`, leading to a spend-triggered wallet DoS - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_cancellation_coins()` in `chia/wallet/trading/offer.py` runs an unbounded, nested `while True` loop over attacker-controllable coin/announcement/dependency graphs derived directly from a received offer file's `CoinSpend`s. A malicious offer counterparty can craft an offer whose bundle contains many non-addition coin spends with a long chain of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` cross-dependencies, causing this function to take pathologically long to return. This mirrors the ManageIQ TimeProfile bug class: an object built from unvalidated/attacker-supplied input (here, an offer file) is persisted/loaded normally, but a *later* routine wallet/RPC/CLI operation that processes it (`cancel_offer(s)`) becomes extremely slow or effectively hangs, causing a denial of service on the wallet's RPC/CLI thread.

### Finding Description
`get_cancellation_coins()` [1](#0-0)  builds three attacker-influenced maps (`dependencies`, `announcements`, `coin_names`) directly from the offer's own `CoinSpend`s and their CLVM-run conditions: [2](#0-1) 

It then repeatedly calls `detect_dependent_coin()`: [3](#0-2) 

which is itself a triple-nested loop over `names × deps[name] × announcement_dict.items()` — i.e. `O(n^3)` per call for `n` coins in the offer. The outer `while True:` at line 449 calls `detect_dependent_coin()` again after every removal, and the inner `while True:` at line 456 rescans the full `dependencies` dict on every pass until no more announcements propagate. Because coin names, the number of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions per coin, and their dependency structure are all fully controlled by whoever authored the offer's `SpendBundle`, an attacker can construct a long, sparse dependency chain (e.g. `coin_1` announces a message asserted by `coin_2`, which announces a message asserted by `coin_3`, …) with many coins and many announcements per coin. Because the offer is only *parsed* (`Offer.from_bech32`/`from_bytes`), not consensus-validated (no cost limit, no `MAX_SPENDS_PER_BLOCK` enforcement, no signature check yet) at the time this function runs, the number of coin spends and the number of announcement/assertion conditions per spend can be made arbitrarily large, driving the combined complexity toward the worst case (`O(n^4)` or worse across outer/inner loop repetitions).

`get_cancellation_coins()` is reachable by any wallet holding the offer (maker or taker) via `TradeManager.cancel_pending_offers()`: [4](#0-3) 

which is exposed over the wallet RPC via `cancel_offer`/`cancel_offers` [5](#0-4)  and the CLI `cancel_offer` command [6](#0-5) , both of which are held under `wallet_state_manager.lock`, a process-wide lock that serializes essentially all other wallet operations (sync, balance queries, other RPC calls). An attacker only needs to get a victim to receive/take/store such a malicious offer (a normal trading interaction) — the DoS is triggered later, on an ordinary follow-up action (cancel), exactly analogous to the ManageIQ pattern where a malformed object is created cheaply but a later, routine request on it stalls the service.

### Impact Explanation
Because `cancel_pending_offers()` is called while holding `wallet_state_manager.lock`, an unbounded/very slow execution of `get_cancellation_coins()` blocks that lock for the duration, stalling all other wallet RPC calls (balance checks, syncing, sending transactions) for as long as the pathological computation runs. This is a genuine transaction/request-processing halt triggered by a single attacker-supplied object (an offer file), satisfying the "spend-triggered transaction-processing halt" criterion. Severity is Medium: it requires the victim to accept/process a maliciously crafted offer (similar to trust boundary of "offer counterparty"), but no signing keys or consensus rules are broken, and it doesn't cause loss of funds or chain-level divergence — only local wallet unavailability.

### Likelihood Explanation
Likely-but-conditional: an attacker must convince (or automate luring) a victim wallet to load/take an offer with a crafted `SpendBundle`, and eventually issue a `cancel_offer`/`cancel_offers` call (which is a fairly common user/automation action, e.g. cleanup scripts, wallet UIs offering “cancel my old offers” bulk actions via `cancel_offers` with `cancel_all=True`, which iterates all stored trades and calls this same path — increasing the chance a poisoned offer eventually gets processed). The crafted offer itself does not need to be broadcastable/valid on-chain; it only needs to parse successfully as an `Offer`, which is a much lower bar than full mempool/consensus validation.

### Recommendation
- Bound the total CLVM/complexity work done by `get_cancellation_coins()`: cap the number of coin spends, and/or the number of announcement/assertion conditions examined per spend, before running the dependency-resolution loops, and reject or short-circuit for oversized offers.
- Replace the `O(n^3)` linear scans in `detect_dependent_coin()` with hash-map lookups (e.g., build a reverse index from announcement message → coin) to reduce each call to near-linear time, and bound the number of outer-loop iterations to `len(coin_names)`.
- Consider not holding `wallet_state_manager.lock` for the entire duration of the cancellation coin computation, so a slow computation on one trade cannot stall unrelated wallet operations.
- Add a defensive size/cost check when constructing an `Offer` from untrusted bytes (bech32/hex import) analogous to mempool CLVM cost checks, rejecting offers whose spend count or CLVM cost is unreasonably large before they are stored or displayed.

### Proof of Concept
Conceptually (cannot be executed in this environment, but the mechanism is directly traceable in source):
1. Construct a `WalletSpendBundle` with `N` coin spends (e.g., `N = 2000`), none of which are "additions" of each other (so all are counted in `coin_names`).
2. For each coin `i`, encode a puzzle/solution whose run produces:
   - one `CREATE_COIN_ANNOUNCEMENT` (condition code 60) with a unique message `m_i`
   - one `ASSERT_COIN_ANNOUNCEMENT` (condition code 61) asserting `m_{i-1}` (forming a long dependency chain `coin_1 → coin_2 → … → coin_N`), plus a handful of extra bogus assertions per coin referencing many distinct earlier announcements to maximize the `set(deps) & set(removed_announcements)` work inside the inner loop.
3. Wrap this into an `Offer` (`requested_payments`, `_bundle`, `driver_dict`) and encode with `Offer.to_bech32()`.
4. Have the victim `take_offer`/store this offer, then invoke `cancel_offer`/`cancel_offers` (or `cancel_all=True`) via the wallet RPC.
5. Observe `TradeManager.cancel_pending_offers()` → `Offer.from_bytes(trade.offer).get_cancellation_coins()` taking disproportionately long (growing faster than linearly with `N`), during which `wallet_state_manager.lock` is held, blocking all other wallet RPC operations — reproducing the "later UI/API requests time out" DoS pattern from the ManageIQ TimeProfile advisory.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]

async def cancel_offer(

    tx_config: TXConfig,

    wallet_client = wallet_info.client
