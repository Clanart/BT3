## Finding



### Title
Stale working-directory snapshot in Copilot conflict-resolution write loop can silently overwrite a user's own conflict fix - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` is meant to skip writing Copilot's stored resolution for any file the user has already resolved themselves (e.g., in an external editor) while the result dialog was open [1](#0-0) . However, the `state` object used for that "already resolved" check is fetched exactly once at function entry [2](#0-1) , and the same frozen `state.changesState.workingDirectory.files` snapshot is reused for every iteration of the `for` loop, which itself performs multiple `await`s (`resolveWithin`, `writeFile`) per conflicted file [3](#0-2) . Any file resolved by the user after the snapshot was taken but before its turn in the loop is still evaluated against the old (conflicted) status, so the guard fails to trigger and Copilot's content overwrites the user's manual fix.

### Finding Description
The intended invariant, stated directly in the code's own comment, is: "If the user resolved this file externally ... while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it" [4](#0-3) .

This invariant is enforced by comparing `onDiskFile.status` from a `state` variable captured once, before the write loop begins:
```
const state = this.repositoryStateCache.get(repository)
...
for (const resolution of copilotResolutions) {
  ...
  const onDiskFile = state.changesState.workingDirectory.files.find(
    f => f.path === resolution.path
  )
  if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
    continue
  }
  await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
  ...
}
``` [5](#0-4) 

Because `resolveWithin` and `writeFile` are awaited per file, and there is no re-fetch of `repositoryStateCache` inside the loop, the guard only reflects working-directory state as of the moment the function started — not as of the moment each individual file is actually about to be written. A live status refresh (from the file-watcher-driven store update path, e.g. `refreshIndicatorForRepository`/`_refreshRepository`) that occurs concurrently with this loop is never consulted by the loop itself. For any conflicted file that isn't first in the list, there is a real window — spanning every prior file's `resolveWithin`+`writeFile` await — during which the user can resolve that later file externally and have their fix silently discarded.

This mirrors the Sherlock bug's structural flaw: a state-boundary check (`onlyActiveAllocation`/`onlyAfterAllocation`, here "conflicted"/"already resolved") is evaluated using a value that is not re-validated at the actual point of consequential action, letting an operation proceed on stale/overlapping state and irreversibly clobber correct data.

### Impact Explanation
This causes silent corruption of what the user ultimately commits: their manually/externally resolved file content for a merge/rebase/cherry-pick conflict is overwritten with Copilot's (possibly incorrect) resolution without any warning, error, or diff shown, and the corrupted content is then staged and committed as-is. This falls squarely under the listed valid impact category "silent corruption of what the user commits or pushes," since a normal, unprivileged user hits this via the completely ordinary flow of resolving a merge conflict with Copilot assistance while multiple files are in conflict.

### Likelihood Explanation
The write loop's duration scales with the number of conflicted files and the latency of `resolveWithin`/`writeFile` (disk I/O, potentially networked/virtualized filesystems), giving a real, non-instantaneous window for each file after the first. Any repository state refresh (background file watcher, periodic repository indicator refresh) racing with an in-progress "Continue Merge" click on a multi-file conflict is a normal occurrence, not one requiring privileged access, malware, or unnatural user steps — just resolving one of several conflicted files in an external editor slightly before/while clicking "Continue Merge" in Desktop's own dialog.

### Recommendation
Re-fetch the current `repositoryStateCache` state (or at minimum the specific file's live on-disk conflict status) immediately before each `writeFile` call inside the loop, rather than relying on the single snapshot taken at function entry, so the "already resolved externally" guard is evaluated against live state at the time of each individual write.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick with at least two conflicted files, A and B.
2. Use Copilot's "Resolve conflicts" feature; wait for the result dialog to display resolutions for both A and B.
3. Immediately click "Continue Merge" (`onContinue` in `copilot-conflicts-dialog.tsx`, which calls `dispatcher.applyCopilotConflictResolutions`) [6](#0-5) .
4. While the loop is writing file A (i.e., before it reaches file B), open file B in an external editor and manually resolve its conflict markers, saving the file.
5. Because `state` inside `_applyCopilotConflictResolutions` was captured before step 3 and is never refreshed, the loop still finds `onDiskFile` for B reporting the old "conflicted" status and proceeds to overwrite the user's manual fix in B with Copilot's stored resolution [5](#0-4) .
6. The user's manual resolution for B is silently lost; the corrupted content is staged (`git add`) and later committed to complete the merge.
