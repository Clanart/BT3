## Finding: Unbounded CLVM execution when parsing untrusted Offer files (DoS)

### Title
Wallet DoS via unbounded CLVM execution while summarizing/canceling an untrusted `Offer` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins()` and `Offer.get_cancellation_coins()` execute every puzzle reveal in an incoming, attacker-crafted offer with `INFINITE_COST` (or an unbounded running total seeded from `INFINITE_COST`), rather than a fixed, enforced CLVM cost ceiling. A counterparty can hand a wallet user a maliciously constructed offer file whose puzzle reveal is designed to consume enormous CLVM execution time (the same "malicious generator" pattern already recognized elsewhere in this codebase, e.g. `SINGLE_ARG_INT_SUBSTR_COND` in `chia/_tests/core/mempool/test_mempool.py:2620-2678`), and simply inspecting or attempting to cancel that offer can hang the wallet/node — mirroring the xgrammar issue where untrusted structured input triggers disproportionately expensive processing with no effective cost limit.

### Finding Description
`Offer.from_bytes()` decompresses a bech32m offer file into a `SpendBundle` plus driver dictionary; nothing in this parse path enforces a bounded CLVM cost per coin spend before the offer's puzzles are actually executed for summarization purposes.

- In `_get_offered_coins()` (used to compute what an offer is actually offering, i.e. `get_offered_coins()`), the cost budget is seeded as `cost_left = INFINITE_COST` and only decremented after each `inner_puzzle.run_with_cost(cost_left, inner_solution)` call: [1](#0-0) 
Because `cost_left` starts at `INFINITE_COST`, the very first (and any subsequent) puzzle execution is effectively unbounded — there is no enforced per-spend or per-offer cost ceiling analogous to `MAX_BLOCK_COST_CLVM`.

- Similarly, `get_cancellation_coins()` — used when determining which coins must be spent to cancel a pending trade — runs every coin spend's full puzzle reveal with `INFINITE_COST`: [2](#0-1) 

Contrast this with `Offer.__post_init__()`, which *does* correctly bound total CLVM work with a decrementing `max_cost` derived from `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` and raises `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` when exceeded: [3](#0-2) 
This shows the codebase is aware that puzzle execution on attacker-supplied offer data must be cost-limited — but that discipline was not applied to `_get_offered_coins()` / `get_cancellation_coins()`, which use the `INFINITE_COST` sentinel instead of a bounded constant.

The mempool/full-node layer already treats "duplicate the expensive-substr/large-string CLVM tricks" as a known DoS vector, and specifically times/limits execution during mempool validation: [4](#0-3) 
But that protection only applies once a spend bundle reaches mempool admission — it does not protect a wallet client inspecting an *unsubmitted* offer file (which never goes through `pre_validate_spendbundle`/mempool cost checks) before deciding whether to accept it.

### Impact Explanation
An offer counterparty (an unprivileged actor who merely shares an offer file, as offers are exchanged out-of-band before being pushed to the mempool) can craft a puzzle reveal that is cheap to serialize/store but extremely expensive to execute (unbounded loops via `concat`/`substr` self-recursion, as already demonstrated as attack primitives in this codebase's own mempool DoS tests). When the recipient's wallet calls `Offer.get_offered_coins()` (to show the user what is being offered) or `get_cancellation_coins()` (to cancel a pending trade), the wallet process will hang executing that puzzle with no cost limit, denying service to that wallet/node until the process is killed. This is a spend-triggered/offer-triggered transaction-processing halt reachable purely by receiving a file — no signature, submission, or acceptance is required to trigger the hang.

### Likelihood Explanation
Likelihood is moderate-to-high: crafting an offer with an expensive puzzle reveal requires no special privilege, no signing key compromise, and no interaction with consensus — only construction of an `Offer` object with a malicious `puzzle_reveal`/`solution` pair, something any wallet user or third-party tool can do and distribute as a normal offer file. The trigger path (viewing/summarizing an offer, or canceling one's own pending trade that references such a spend) is part of routine wallet UX.

### Recommendation
Bound all puzzle executions performed while summarizing or canceling an `Offer` to the same consensus-derived cost ceiling already used in `__post_init__` (e.g., `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`), decrementing a shared budget across all spends in `_get_offered_coins()` and `get_cancellation_coins()`, and raising a `ValidationError` (mirroring `Err.BLOCK_COST_EXCEEDS_MAX`) rather than passing `INFINITE_COST` to `run_with_cost`. Additionally, consider running these summarization executions with a wall-clock timeout guard (similar to the mempool's duration-guard DoS protection) so that even cost-metering bypasses cannot stall the wallet indefinitely.

### Proof of Concept
Conceptually (cannot be fully validated without running code, per the analog-based nature of this review):
1. Construct a `CoinSpend` whose puzzle reveal implements a self-referential `concat`/`substr` doubling loop parameterized similarly to `SINGLE_ARG_INT_SUBSTR_COND` in `chia/_tests/core/mempool/test_mempool.py:2634-2649`, tuned so CLVM execution time is minutes rather than mempool-cost-bounded milliseconds.
2. Wrap it as a `NotarizedPayment`/`Offer` (via normal offer construction, or hand-built `SpendBundle` + driver dict) and export via `Offer.to_bech32()`.
3. Send the resulting offer file to a victim wallet user.
4. Victim's wallet calls `Offer.from_bytes()` then `get_offered_coins()` (as done automatically by RPCs like offer summary/`get_offer_summary`) or later `get_cancellation_coins()` — both invoke `run_with_cost(..., INFINITE_COST, ...)` on the malicious puzzle, hanging the wallet process.

Note: I was not able to fully trace every RPC/UI call site that triggers `get_offered_coins()`/`get_cancellation_coins()` on a not-yet-accepted, externally supplied offer within the available search budget; confirming the exact reachable trigger (e.g., specific RPC endpoint auto-invoked on offer receipt) would benefit from a deeper trace in a full Devin session before treating this as fully proven.
