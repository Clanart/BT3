### Title
Unhandled missing-key panic in `BlameMachine::blame` crashes the node on blame accusations naming out-of-range participants - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2024-34088 (a lookup returning an absent value that callers dereference unconditionally, crashing the daemon), `BlameMachine::blame_internal` / `AdditionalBlameMachine::blame` index `self.commitments[&sender]` without checking that `sender` is an actual participant. `Participant` indexes are attacker-supplied and `Participant::new` only rejects zero, so a blame statement naming any `sender` outside the committed set panics the process.

### Finding Description
`BlameMachine` stores per-participant commitment vectors in `commitments: HashMap<Participant, Vec<C::G>>`, populated only for the `n` registered DKG participants (in `KeyMachine::calculate_share`, entries exist only for participants whose commitments were accepted; in `AdditionalBlameMachine::new`, only `1..=n`).

`blame_internal` evaluates an accusation `(sender, recipient, msg, proof)` taken entirely from untrusted input. After the ECDH proof/decryption succeeds and the plaintext parses as a canonical scalar, it executes:

```rust
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],   // crypto/dkg/pedpop/src/lib.rs:599
  Zeroizing::new(share),
))
```

`HashMap` indexing (`map[&key]`) panics when the key is absent. Neither `blame` nor `AdditionalBlameMachine::blame` validates `sender`/`recipient` against the participant set before this point — the doc comments only require the message to be *authenticated as from* the supposed sender, which a `Participant` index itself does not establish, and `Participant::new` accepts any non-zero `u16` regardless of `n`. The same unguarded indexing pattern exists on the happy path (`self.commitments[&l]` in `calculate_share`), but there `l` is drawn from the caller-provided shares map after `validate_map`, whereas in `blame_internal` `sender` is free-form. (Not fully verified whether `Decryption::decrypt_with_proof` indexes per-sender state even earlier; if it does, it panics on the same class of input rather than defending it.)

### Impact Explanation
An unprivileged party that can submit a blame/invalid-share accusation (exactly the shape of on-chain `InvalidDkgShare` transactions, which deserialize `accuser`/`faulty` as bare `Participant::new(u16)` values) can crash every node/library user evaluating the blame by naming a `sender` not present in the commitments map — e.g., an index `> n`, or for `BlameMachine`, a participant whose commitments were never registered. This is a remote, deterministic denial of service matching the CVE's crash-on-unhandled-missing-value class.

### Likelihood Explanation
Triggering requires the blame path to be exercised and decryption to succeed (or an earlier lookup in `decrypt_with_proof` to panic on the same input). Any accusation naming a valid-looking but non-member participant index suffices; blame evaluation is precisely the interface designed to ingest hostile inputs, so reachability is high whenever blame statements are processed at all.

### Recommendation
In `blame_internal` (and `Decryption::decrypt_with_proof` if applicable), validate `sender` and `recipient` membership before indexing: return an error or blame result instead of panicking — e.g., `self.commitments.get(&sender)` with an explicit `None` arm. Similarly, bound `Participant` values against `n` at the earliest deserialization/API boundary.

### Proof of Concept
```rust
// Given a completed DKG producing `blame: BlameMachine<Ed25519>` for n participants,
// an accuser submits a blame statement with a non-member sender:
let bogus_sender = Participant::new(n + 1).unwrap(); // non-zero, accepted
let msg: EncryptedMessage<Ed25519, SecretShare<_>> = /* any well-formed message
    that decrypts successfully, or that reaches the commitments lookup */;
// crypto/dkg/pedpop/src/lib.rs:599 -> thread panics:
// "no entry found for key"
blame.blame(bogus_sender, recipient, msg, proof);
```
The same panic is reachable via `AdditionalBlameMachine::blame`, which is explicitly documented as usable by non-participants evaluating blame proofs.
