Confirmed: `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` requires only `order.inputs.length != 0` — there is **no upper bound** on the number of input tokens (or output tokens) a user can include in an order. That unbounded, user-controlled array then flows unchanged into the settlement/refund path on the opposite chain, where it is looped over in a single atomic call.

### Title
Unbounded user-controlled `order.inputs`/`order.tokens` array permanently locks escrowed funds in cross-chain settlement/refund - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder()` only checks `order.inputs.length == 0`, imposing no maximum size on `order.inputs` or `order.output.assets`. This array is embedded in the order commitment and later reproduced, unmodified, inside a `WithdrawalRequest.tokens` array that is processed by `IntentsBase._withdraw()` — a single, atomic `for` loop over `body.tokens` [1](#0-0)  — on both the cross-chain settlement path (`onAccept` → `withdraw`) and the cross-chain cancel/refund paths (`_cancelFromSource`, `_cancelFromDest`) [2](#0-1) [3](#0-2) . `placeOrder` itself performs no length cap [4](#0-3) .

### Finding Description
A user can place a cross-chain order with an arbitrarily large `inputs` array (e.g. thousands of distinct token entries, or thousands of dust-amount entries for the same tokens is not possible since `_orders` is keyed by token, but distinct token addresses can be enumerated cheaply using many low-value ERC-20 contracts, or simply many `TokenInfo` structs referencing few unique tokens with tiny escrow amounts each — the `_withdraw` loop cost scales with `body.tokens.length` regardless of token uniqueness). Because `_orders[commitment][token]` decrements per entry and reverts with `UnknownOrder` if `escrowed == 0`, an attacker's own order fully controls both `escrowed` state and array length, so the loop always completes validation-wise — the only constraint is gas.

Once the order is placed and escrow is locked on the source chain, settlement is driven by a single cross-chain message (`RedeemEscrow` or `RefundEscrow`) whose body carries the full `tokens` array from the order. On the destination side, `onAccept` decodes this body and calls `_withdraw()` in one transaction with no batching or partial-execution mechanism. If the array is large enough that the loop's iteration count times per-iteration cost (an `SLOAD`/`SSTORE` pair plus an ERC20 `safeTransfer` or native `call`) exceeds the destination chain's block gas limit, this call can never succeed on that chain — not just this call, but *every* future attempt, since the request/message content and hence the gas requirement is fixed and immutable once dispatched.

For the settlement (`RedeemEscrow`) path, this means the solver who filled the order (already having delivered output tokens to the beneficiary out-of-pocket) can never redeem the escrowed input tokens: the escrow is durably stuck in the source-chain contract, marked `_filled` (in some paths) yet the fund transfer can never execute. For the cancel/refund (`RefundEscrow`) path, the user who placed the order can never recover input escrow if it was locked with an oversized `inputs` array, since the resulting refund message hits the same unbounded loop.

Unlike a generic node/network DoS, this is a **fund-lock via an unbounded loop reachable by an unprivileged, ordinary user through the public `placeOrder` entrypoint**, with no admin, relayer, or governance action able to remedy it — there is no partial-withdrawal or chunked-settlement function in `IntentsBase`/`IntentGatewayV2` to recover from an oversized commitment.

### Impact Explanation
This matches the "stealing or loss of funds" / "logic attack" category in the Hyperbridge Impact Gate: escrowed bridged assets can become permanently unrecoverable due to a self-inflicted or adversarial gas-bomb array size, with no code path in `IntentsBase.sol` to recover (no chunked/partial redemption, no re-dispatch with a smaller batch). This is distinct from a generic network/gas DoS because the broken invariant is architectural — settlement is designed as one atomic all-or-nothing loop over a user-supplied, unbounded array — and the result is unconditional loss of the escrowed principal for the affected order.

### Likelihood Explanation
Likelihood is moderate to high in adversarial or even accidental scenarios: `placeOrder` performs no upper-bound check on `order.inputs.length` or `order.output.assets.length`, so any user (or an SDK bug generating a malformed/large order) can trivially exceed a safe iteration count. Because the check `order.inputs.length == 0` is the only guard, this is reachable without any privileged role, relayer collusion, or malformed proof — a single unprivileged `placeOrder` call is sufficient to create a permanently unsettleable/unrefundable order.

### Recommendation
Add an explicit upper bound (e.g., `MAX_TOKENS`) on `order.inputs.length` and `order.output.assets.length` in `placeOrder`, enforced identically on both the source and destination gateway deployments so commitments remain consistent. Additionally, consider making `_withdraw()` resilient to partial completion (e.g., per-token claim functions, or checkpointed/resumable withdrawal) so that even a legacy oversized order can eventually be drained token-by-token rather than requiring one atomic call for the whole array.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing `N` (e.g., 2,000) `TokenInfo` entries, each referencing a distinct cheap ERC-20 token (or even the same handful of tokens split into many small `TokenInfo` records — note `_orders` is additively keyed per token so duplicate-token entries must sum correctly, but distinct-token entries are trivially unlimited). `placeOrder` succeeds because there is no length check beyond non-zero [5](#0-4) .
2. A solver fills the order on the destination chain and dispatches the `RedeemEscrow` settlement message back to source, embedding the full `N`-length `tokens` array in `WithdrawalRequest.tokens`.
3. On the source chain, `onAccept` invokes `_withdraw()`, which loops `for (uint256 i; i < len; i++)` over all `N` tokens performing an `SLOAD`, `SSTORE`, and external transfer per entry [1](#0-0) .
4. If `N` is large enough that total gas exceeds the source chain's block gas limit, the transaction reverts unconditionally; no other function exists to redeem the escrow in smaller batches, so the solver's rightful payment (and the user's cancel/refund path, symmetric via `_cancelFromDest`) is permanently locked in the contract.

Note: I was not able to fully verify the exact per-iteration gas cost or whether any off-chain (Tesseract messaging) preflight simulation rejects oversized orders before dispatch, as those components were outside the scope of what I could inspect in this session; a Devin session with full repo access could confirm gas-cost bounds precisely and check for any pre-relay validation guard I may have missed.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });
