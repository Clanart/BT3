### Title
`SignableTransaction::new` omits the OP_RETURN `data` output from the weight/fee calculation, underpaying the fee for every transaction carrying data — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Astaria issue — where `commitToLiens` performs a finalizing step against state that was already finalized, guaranteeing failure — `SignableTransaction::new` computes the transaction weight and `needed_fee` from a transaction skeleton that excludes the OP_RETURN data output it has already committed to `tx_outs`, so every data-carrying transaction is built with a fee that does not cover its actual size.

### Finding Description
In `SignableTransaction::new`, the `data` argument is serialized into an OP_RETURN output and pushed to `tx_outs` at `send.rs:194-202`. The subsequent fee calculation calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204`, which rebuilds a transaction using only `payments` (and optionally `change`); it has no parameter for the data output at all (`send.rs:62-99`). The same omission occurs in the change branch at `send.rs:225-226`.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed on vbytes that exclude the OP_RETURN output (~11 bytes of overhead plus up to 80 bytes of pushdata, since `data` is permitted up to 80 bytes per the check at `send.rs:171`).
- The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()` at `send.rs:138-141`); the OP_RETURN output has value 0, so no additional fee is contributed. The realized fee rate is therefore strictly below `fee_per_vbyte`.
- The minimum-relay-fee guard at `send.rs:211` validates `needed_fee` against the understated `vbytes`, so a transaction that passes the check can still fall below `DEFAULT_MIN_RELAY_TX_FEE` on its true virtual size and be rejected by the mempool — deterministic failure of the signing/publish flow, mirroring the "always reverts" class.
- Likewise, the `NotEnoughFunds` check at `send.rs:215` and the change-value computation at `send.rs:228` use the understated fee: when change is created, the change output absorbs `input_sat - payment_sat - fee_with_change`, where `fee_with_change` again ignores the data output, so the effective feerate is diluted across the whole transaction rather than just the change leg.

### Impact Explanation
Any Bitcoin transaction produced with a non-empty `data` payload pays a lower effective fee rate than requested. Near-minimum fee rates produce transactions that pass Serai's own `TooLowFee` validation yet are rejected as non-standard/insufficient-fee by Bitcoin nodes, stalling settlement of the corresponding plan. The error scales with `data.len()` and `fee_per_vbyte`, and `data` is attacker-influenceable via instructions that carry payload.

### Likelihood Explanation
Triggering only requires a transaction carrying an OP_RETURN payload; the miscalculation is unconditional in that code path. Whether the shortfall causes relay rejection depends on how close `fee_per_vbyte` is to the network minimum, but the fee is mis-accounted in every case, including silently inflated change.

### Recommendation
Extend `calculate_weight_vbytes` to take the full output list (or the `data` payload) so the OP_RETURN output's size and varint are included in `weight`/`vbytes` for both the no-change and with-change calculations, before computing `needed_fee`, the change value, and the `TooLowFee`/`NotEnoughFunds` checks.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)`. The resulting `SignableTransaction` contains an OP_RETURN output, but `needed_fee()` equals `fee_per_vbyte` times the vbytes of a transaction without it. `fee()` returns exactly `needed_fee`, while `tx.weight()`/`get_virtual_tx_size` of `transaction()` is ~90+ vbytes larger, so the true fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`. With `fee_per_vbyte` at the minimum relay boundary, the built transaction is rejected by Bitcoin Core's mempool despite passing the `TooLowFee` check.
