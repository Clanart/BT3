## Title
Recursive precompile calls desynchronize StateDB balances from x/bank ledger via shared `BalanceHandler` instance - (File: `precompiles/common/balance_handler.go`)

### Summary
This is the closest reachable analog to the StakedCitadel `balance()` bug: an internal-accounting function that is supposed to reconcile *all* relevant balance state but instead only accounts for a partial view, corrupting downstream accounting decisions. Here, the `BalanceHandler.AfterBalanceChange` mechanism reconciles EVM `StateDB` balances with `x/bank`/`x/precisebank` events emitted during a precompile call by scanning `ctx.EventManager().Events()[bh.prevEventsLen:]`. The repository's own test suite, `evmd/tests/integration/balance_handler/balance_handler_test.go`, is explicitly titled to test "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."

### Finding Description
`BalanceHandler` (in `precompiles/common/balance_handler.go`) tracks a cursor `prevEventsLen` marking where in the event log to start scanning for `EventTypeCoinSpent`, `EventTypeCoinReceived`, and precisebank's `EventTypeFractionalBalanceChange` events after a precompile executes, in order to replay those balance deltas onto the EVM `StateDB` via `AddBalance`/`SubBalance` [1](#0-0) . This is the counterpart of the vault's `balance()` — instead of returning a vault+strategy sum, it's supposed to fold "native bank state changes" into the EVM statedb's accounting.

When a precompile call is nested (a precompile call triggers another precompile call in the same EVM execution, e.g. via a contract that calls precompile A which internally re-enters precompile B), if both calls share the *same* `BalanceHandler` instance, the inner call's `BeforeBalanceChange`/`AfterBalanceChange` bookkeeping overwrites `prevEventsLen` set up by the outer call. This causes the outer call's post-processing to scan the wrong slice of events — either re-applying already-applied deltas or skipping events entirely, producing a StateDB balance that diverges from the actual `x/bank` ledger balance for the accounts involved.

### Impact Explanation
If `StateDB` balances diverge from actual `x/bank`/`x/precisebank` balances within a transaction, this directly corresponds to the required "Critical … irreversible accounting corruption of spendable user value across native balances, EVM balances, ERC20 representations" impact class. An attacker could construct a contract that recursively invokes precompiles (staking, distribution, bank, werc20, ICS20, etc.) to desynchronize their EVM-visible balance from their real bank balance — potentially inflating the EVM balance they can then spend/transfer within the same or later EVM calls (double-counted credit), or corrupting another account's balance view leading to unauthorized value extraction once committed to the KV store on `Commit()`.

### Likelihood Explanation
The trigger is a normal, unprivileged EVM transaction: any user can deploy or call a contract that makes nested precompile calls (a pattern already exercised by the codebase's own `StakingReverter.sol` test contracts doing nested try/catch precompile calls, and the dedicated `balance_handler_test.go` reproducing this exact scenario). No privileged role, relayer, or validator collusion is required — it's purely a contract-execution/reentrancy pattern, matching "Admission/execution path" and "recursive-call" invariant requirements in the audit scope.

### Recommendation
Ensure `BalanceHandler` state (`prevEventsLen`) is not shared/overwritten across nested precompile invocations — e.g., use a stack of cursors (push/pop per precompile call depth) instead of a single mutable field, or instantiate/clone a handler per call frame so inner calls cannot clobber the outer call's bookkeeping. Add invariant checks that assert `StateDB` balance equals the wrapped bank/precisebank balance after each precompile `Run` returns, especially after nested calls, and fail closed (revert) if divergence is detected.

### Proof of Concept
Exact reproduction steps could not be fully verified within tool-call limits (the target test file `evmd/tests/integration/balance_handler/balance_handler_test.go` and the reentrant precompile call chain it exercises could not be read in full due to iteration limits), but the file's own description states: a contract triggers a precompile call (outer) that internally causes another precompile call (inner) sharing the same `BalanceHandler`, causing `prevEventsLen` to be overwritten by the inner call's `BeforeBalanceChange`, so that the outer call's `AfterBalanceChange` scans an incorrect event range and leaves `StateDB` balance out of sync with the real `x/bank` balance for the accounts touched by the events skipped/double-applied. I could not confirm from the available context whether this test currently passes (i.e., whether the bug is already fixed) or fails (i.e., is an active, exploitable bug) — this needs to be verified by running the test suite or reading the full test body and `BalanceHandler` struct/lifecycle code (particularly where the handler is instantiated per precompile call vs. reused), which was not fully retrievable in the available iterations.

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```
