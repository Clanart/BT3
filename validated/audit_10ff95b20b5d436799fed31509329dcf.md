## Title
`aptos move verify-package` never compares on-chain module bytecode to the locally compiled bytecode, so it can report success for packages whose deployed bytes diverge from their declared/verified source — ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The CLI's `aptos move verify-package` command is documented as verifying that "the bytecode matches a local compilation of the Move code," but its implementation, `CachedPackageMetadata::verify`, only diffs `PackageMetadata` fields (name, deps, `ModuleMetadata` — which is gzipped *source text*/source-map, manifest, upgrade policy, extension, and `source_digest`). It never fetches or compares the actual on-chain compiled module bytes (`get_bytecode`) against the bytes the local `BuiltPackage` just compiled. Because `source_digest` is a hash of the *source files*, not of the bytecode, and the Move VM publish path performs no check that on-chain bytecode is consistent with the metadata's declared source, a package owner can publish benign-looking source/metadata alongside arbitrary, unrelated compiled modules. `verify-package` will still print "Successfully verified source of package."

### Finding Description
`code::publish_package` (Move) and the native `request_publish`/`request_publish_with_allowed_deps` handlers in `aptos-move/framework/natives/src/code.rs` only check that module addresses/names match `expected_modules` and that compatibility/upgrade-policy rules hold; they do not validate that the bytecode's semantics correspond to the `source`/`source_digest` fields stored in `PackageMetadata`. This is by design at the protocol level — the source and digest are informational, not enforced. [1](#0-0) 

The problem is that the CLI tool built specifically to give users/auditors confidence that "on-chain bytecode matches a local compilation of the Move code" does not perform that check either: [2](#0-1) 

`VerifyPackage::execute` builds the package locally, downloads the on-chain `PackageMetadata` (with `bytecode=false`, meaning module bytes are not even fetched), and calls `package.verify(&compiled_metadata)`: [3](#0-2) 

`CachedPackageMetadata::verify` only compares metadata-level fields — never the compiled module bytes: [4](#0-3) 

Notably `self_metadata.modules != package_metadata.modules` compares `ModuleMetadata`, whose fields are only `name`, `source` (gzipped source text), `source_map`, and `extension` — not bytecode: [5](#0-4) 

The `CachedPackageRegistry` does support fetching real bytecode via `get_bytecode`, and `DownloadPackage --bytecode` exercises this path, but `VerifyPackage` deliberately calls `CachedPackageRegistry::create(client, self.account, false)` (bytecode disabled) and never calls `get_bytecode` at all, so the actual deployed module bytes are never inspected during verification. [6](#0-5) 

### Impact Explanation
This breaks the "verified bytes vs. metadata vs. committed module bytes" invariant that downstream tooling and users implicitly rely on:
- `package_hooks.rs`'s `resolve_custom_dependency` downloads packages via `CachedPackageRegistry`/`save_package_to_disk`, which persists only the declared `source` field, and other tooling (dependents building against a package as a dependency, or auditors running `verify-package` before trusting a contract) may treat a "Successfully verified source of package" result as proof that the deployed bytecode equals what compiles from the shown source.
- A malicious or compromised package owner can therefore publish a package whose metadata/source describes benign, audited behavior while the actual bytecode executing on-chain does something entirely different (e.g., drains funds, adds backdoors), and this discrepancy will not be caught by `verify-package`.
- Since compatible/immutable-policy packages are exactly the ones users are told they can safely depend on (per `modules-and-packages.md`'s dependency-safety guidance), a false sense of security from a passing `verify-package` run undermines the code-safety guarantee the publish/verification pipeline is supposed to provide.

### Likelihood Explanation
Any package owner can trigger this by hand-crafting a `PackageMetadata` whose `source`/`source_digest`/`manifest` fields describe one thing while supplying different compiled module bytes in the `code` vector of `publish_package_txn`/`object_code_deployment::publish`/`upgrade`. Nothing in `code.move`, the native `request_publish*` functions, or `CachedPackageMetadata::verify` prevents or detects this mismatch. No special privilege is required beyond normal publish rights over one's own package/object.

### Recommendation
Update `VerifyPackage::execute` to always fetch and diff actual on-chain module bytecode (`registry.get_bytecode(module)`) against the freshly compiled `pack.extract_code()` byte-for-byte (or by content hash), in addition to the existing metadata comparison, and fail verification on any mismatch. Consider also warning callers if `bytecode` fetching was skipped, since a metadata-only "verification" provides no bytecode integrity guarantee.

### Proof of Concept
1. Build and publish a package where `Move.toml`/module source implements an innocuous function `f()`, but before submitting, replace the emitted `code: vector<vector<u8>>` in the publish transaction with a different compiled module that keeps the same module name/address (satisfying `expected_modules`) but different logic (e.g., adds a hidden withdrawal function). Submit via `code_publish_package_txn`/`object_code_deployment::publish`; this succeeds because neither `code.move` nor the native `request_publish` checks source/bytecode correspondence.
2. Run `aptos move verify-package --account <addr>` using the original, benign source tree.
3. Observe that `stored_package.rs`'s `verify()` only compares `name`, `deps`, `modules` (source text/source_map), `manifest`, `upgrade_policy`, `extension`, and `source_digest` — all of which match because they were derived from the same benign source used for both the metadata upload and the local rebuild — and the command prints `"Successfully verified source of package"` (`aptos-move/cli/src/commands.rs:2139`) despite the deployed bytecode being different from what was compiled/verified.

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
