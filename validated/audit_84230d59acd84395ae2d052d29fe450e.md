## Title
Trust granted via `addSafeDirectory` is bound to a mutable path, not to repository identity, enabling silent hook execution for an attacker-controlled repository that later occupies a previously trusted path - (File: `app/src/lib/git/config.ts`)

## Summary
The Connext report's broken invariant is that a permission ("Role.Router") was bound to a mutable, reusable identifier (a router's on-chain slot) rather than to the specific trusted entity, so removing/re-adding under that identifier silently transferred trust to an attacker-controlled owner without any re-validation, letting them drain funds that other honest participants still associated with that identifier.

The same class of flaw exists in Desktop's "Trust Repository" flow. When Git refuses to operate in a directory because of "dubious ownership," Desktop lets the user click "Trust Repository," which calls `addSafeDirectory()` and permanently appends the **literal filesystem path** to the user's global `safe.directory` Git config [1](#0-0) . This exception is never revoked, never re-validated, and is not bound to who or what actually owns/controls the content at that path — only to the path string itself.

## Finding Description
`addSafeDirectory(path)` adds `path` to `safe.directory` in the user's **global** `.gitconfig` [2](#0-1) . This call is triggered from two UI surfaces, both of which treat "trust" as a one-time action tied only to the path:

- `AddExistingRepository.onTrustDirectory` [3](#0-2) 
- `MissingRepository.onTrustDirectory` [4](#0-3) 

Once a path is in `safe.directory`, Git (and therefore Desktop, via `getRepositoryType`) will never again report that path as `unsafe`, regardless of which user/process owns or has rewritten the contents at that path afterward [5](#0-4) . The identifier that was trusted (a directory path) is decoupled from the identity that was actually vetted (the specific repository/owner present at the moment "Trust" was clicked) — the same broken invariant as the Connext report, where trust in a `Role.Router`-controlled slot did not travel with a specific vetted owner.

This matters because Desktop, by default, now intercepts and runs Git hooks found in a repository (`core.hooksPath` or `.git/hooks`) as part of normal operations like commit, push, pull, and merge [6](#0-5) . Hook execution flows through `withHooksEnv`, which is only guarded by whether the target path is "safe" per Git's ownership check [7](#0-6) . If a path has previously been added to `safe.directory`, that guard is permanently bypassed for that path — Desktop will happily discover and execute any hook the current occupant of the directory ships, without prompting the user again, via `createHooksProxy`/`spawn(gitPath, ...)` [8](#0-7) .

The explicit product feature "Support trusting repositories on network shares (Windows)" [9](#0-8)  confirms this exception mechanism is intended to be used for exactly the kind of shared/reusable-path scenario where a different, untrusted party can later occupy the same path (network shares, removable drives, shared build/checkout directories). Once trusted, Desktop never re-derives "is the current occupant of this path the same trusted entity as before" — the same missing re-validation as the `Role.Router` re-add in the Connext report.

## Impact Explanation
An attacker who can arrange for their own repository content to occupy a path that a victim previously marked "Trust Repository" (e.g., a shared network drive, removable media, or any reused checkout path) achieves silent, unprompted Git hook execution the next time Desktop opens/refreshes/interacts with a repository at that path — this is native code execution as the victim's user, without any further confirmation dialog, credential prompt, or ownership warning. Because the check is purely path-based and global-config-based, it persists indefinitely across unrelated repositories, unrelated remotes, and unrelated Git identities that later reuse the same filesystem location.

## Likelihood Explanation
The scenario requires: (1) the victim to have trusted a path once (a supported, documented, one-click workflow, not an edge case), and (2) the path to later be occupied by attacker-influenced content (a realistic condition on shared/mounted/removable storage, which Desktop explicitly added support for trusting). No malware pre-existing on the host, no admin rights, and no credential compromise are needed — only the ordinary trust-once UX plus a reused directory location, matching Desktop's own supported use cases (network shares).

## Recommendation
Do not bind the trust decision solely to a path string in the global Git config. Instead:
1. Re-validate the specific repository identity (e.g., remote URL, initial commit/SHA, or a fingerprint of `.git`) at the time trust was granted, and re-prompt if that identity changes for the same path.
2. Scope trust exceptions to the app's own state (e.g., per-`Repository` record) rather than relying exclusively on Git's global `safe.directory`, so Desktop can independently detect "this path now contains a different repository than the one I trusted" and force re-confirmation before running hooks or other automatic actions.
3. Consider surfacing a warning/re-prompt whenever a previously-trusted path's remote URL, root commit, or ownership changes, mirroring the Connext recommendation of tying continued trust to a durable, hard-to-spoof identity rather than a reusable identifier.

## Proof of Concept
1. Victim clones/opens a repository at path `P` (e.g., `D:\shared-checkout` on a network share, or `/Volumes/USB/repo`) that Git flags as `unsafe` due to differing ownership.
2. Victim clicks "Trust Repository," which calls `addSafeDirectory(P)`, permanently adding `P` to the global `safe.directory` list [4](#0-3) .
3. Victim later removes/disconnects that repository from Desktop (or the media is temporarily removed).
4. Attacker (a different user of the shared drive, or someone who swaps the removable media/network share content) places a different, malicious Git repository at the exact same path `P`, including a `pre-commit`/`post-checkout`/etc. hook script.
5. Victim reconnects the drive/share and opens/adds the repository at `P` again in Desktop, or Desktop auto-refreshes an existing entry pointing at `P`.
6. `getRepositoryType(P)` no longer reports `unsafe` (because `P` is in `safe.directory`) [10](#0-9) , so Desktop proceeds normally.
7. The next Git operation (commit, checkout, pull, etc.) triggers hook interception/execution via `withHooksEnv`/`createHooksProxy`, running the attacker's hook script as the victim, with no further prompt [8](#0-7) .

```typescript
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
```

```typescript
export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
```

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
