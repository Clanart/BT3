## Summary

The Linux HFSC bug (CVE‑2025‑38001) is a *guard-bypass* pattern: a re-entrant insertion path exists that the "already inserted" check does not cover, because the guard was written against only one of two ways an object can enter the same tracked structure. The strongest Protobuf analog in this checkout is in the **CPython C‑extension (`_message`) `MergeFrom`/`MergeFromString`/`ParseFromString` reentrant-oneof UAF mitigation**, `MaybeReleaseOneofBeforeMerge`, which was patched for one mutation path (scalar oneof switching) but explicitly and knowingly excludes a second mutation path with identical "destroy-while-referenced" semantics: **message-valued map entries that are overwritten wholesale during `MergeFrom`**.

## Finding Description

`MaybeReleaseOneofBeforeMerge` walks `self->composite_fields` (the map of Python wrapper objects that alias live C++ submessage pointers) and, for every singular message field the Python side has already materialized as a wrapper, releases/detaches the wrapper *before* the C++ merge runs, so that if the C++ merge deletes the underlying object (oneof switch), the stale Python wrapper is safely detached first: [1](#0-0) 

The guard explicitly skips repeated fields — and map fields are represented as repeated message fields in the descriptor API — with a comment that *acknowledges* the overwrite semantics but does nothing about them: [2](#0-1) 

```
if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
    // For normal repeated message, MergeFrom will append the messages.
    // For message map with same keys, it is overwrite
    !descriptor->is_repeated() &&
    reflection->HasField(*message, descriptor)) {
```

The invariant that fails to transfer/hold here is the same one that failed in HFSC: "a guard exists to prevent stale-reference-after-destroy, but it only covers one of the code paths that can destroy the referenced object." At the C++ map level, merging a map field with a duplicate key does not recursively merge the value message in place — it destroys the old node and replaces it: [3](#0-2) 

```
bool InsertOrReplaceNode(Arena* arena, KeyNode* node) {
  ...
  if (ABSL_PREDICT_FALSE(p.node != nullptr)) {
    EraseImpl(arena, p.bucket, static_cast<KeyNode*>(p.node),
              /*do_destroy=*/true);
    is_new = false;
  }
  ...
}
```

This "overwrite, not merge" semantic for message-valued maps is independently documented and tested at the C++/conformance level: [4](#0-3) [5](#0-4) 

and Python's own regression test proves the exact class of bug the guard was designed to fix for the *scalar-oneof* case: [6](#0-5) 

That test's comment states plainly: *"Accessing sub_ref would trigger UAF before the fix because the C++ message was deleted on oneof switch. With the fix, the message is released/detached…"* — i.e. this is a previously real, fixed vulnerability class in this exact function, and the fix was deliberately scoped to exclude the map/overwrite case.

`MergeFromStringImpl` (used by both `MergeFromString` and `ParseFromString`, both public parsing entry points) calls `MaybeReleaseOneofBeforeMerge` right before the real `MergeFrom`: [7](#0-6) 

Because map fields are excluded from the pre-release walk, any Python wrapper object previously obtained for a message-valued map entry (e.g. `sub = msg.map_field[key]`) is never detached before the C++ `MergeFrom` executes `InsertOrReplaceNode(..., do_destroy=true)`, which deletes the underlying C++ object that `sub` still wraps.

## Impact Explanation

For heap-allocated (non-arena) Python messages — the default construction path for `_message.Message` objects created without an explicit arena — `EraseImpl(..., /*do_destroy=*/true)` on the old map value results in an actual `delete` of the C++ submessage object. The Python-level wrapper object retains a raw pointer to that now-freed memory. Any subsequent field access on the stale wrapper (`sub.some_field`, `sub.SerializeToString()`, etc.) is a use‑after‑free, which for CPython typically manifests as memory corruption, incorrect field reads, or a crash, and in adversarial conditions can be leveraged for type confusion/heap corruption exploitation primitives — the same class of consequence (`C:H/I:H/A:H`) rated High for CVE‑2025‑38001.

## Likelihood Explanation

The trigger requires only application code that (a) reads a message-valued map entry into a retained Python reference, and (b) later calls `MergeFrom`/`MergeFromString`/`ParseFromString` on the parent message with attacker-controlled bytes containing the same map key. Both operations are ordinary, documented Protobuf Python usage patterns operating entirely within the public API surface — no privileged access, custom schema, or malicious plugin is needed. The "hold a reference across a merge" pattern is realistic in long-lived server/cache objects that keep references to sub-messages while periodically re-parsing/merging updates from external, attacker-influenced payloads.

## Recommendation

Extend `MaybeReleaseOneofBeforeMerge` (or add a parallel pass) to also walk cached map-field wrapper containers in `composite_fields`, detecting keys present in both `self` and `other` whose values are message-typed, and detach/release the corresponding cached Python map-value wrappers before invoking the C++ `MergeFrom`. Alternatively, change the C++ map merge semantics used by the Python-exposed path to perform recursive `MergeFrom` on colliding keys instead of destructive replace-in-place when foreign references may exist, or make `FixupMessageAfterMerge`/its map counterpart re-validate/rebind any cached map-entry wrappers post-merge the way it already does for singular message fields.

int MaybeReleaseOneofBeforeMerge(CMessage* self, const Message& other) {
  CMessage::CompositeFieldsMap* composite_fields =
      self->composite_fields.TryGet();
  if (!composite_fields) {
    return 0;
  }

  Message* message = AssureWritable(self);
  if (message == nullptr) return -1;
  const Reflection* reflection = message->GetReflection();
  PyMessageFactory* factory = GetFactoryForMessage(self);
  std::vector<const FieldDescriptor*> fields_to_release;
  std::vector<std::pair<const FieldDescriptor*, ScopedPyObjectPtr>>
      nested_message_fields;
  composite_fields->ForEach([&](const void* key, PyObject* value) {
    const FieldDescriptor* descriptor =
        reinterpret_cast<const FieldDescriptor*>(key);
    if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
        // For normal repeated message, MergeFrom will append the messages.
        // For message map with same keys, it is overwrite
        !descriptor->is_repeated() &&
        reflection->HasField(*message, descriptor)) {
      if (reflection->HasField(other, descriptor)) {
        Py_INCREF(value);
        nested_message_fields.emplace_back(descriptor, value);
      } else {
        // Release oneof message if the other message has set a different oneof
        const OneofDescriptor* oneof = descriptor->containing_oneof();
        if (oneof && reflection->HasOneof(other, oneof)) {
          fields_to_release.push_back(descriptor);
        }
      }
    }
  });

  for (const auto& [field, value] : nested_message_fields) {
    if (MaybeReleaseOneofBeforeMerge(
            reinterpret_cast<CMessage*>(value.get()),
            reflection->GetMessage(other, field, factory->message_factory)) <
        0) {
      return -1;
    }
  }

  for (const FieldDescriptor* field : fields_to_release) {
    if (InternalReleaseFieldByDescriptor(self, field) < 0) {
      return -1;
    }
  }
  return 0;
