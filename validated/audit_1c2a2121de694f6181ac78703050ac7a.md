### Title
Bitcoin scanner applies later transactions' origin and instruction data to earlier outputs - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates matched outputs across all non-coinbase transactions in a block, but then applies the current transaction's presumed origin and serialized InInstruction data to every accumulated output. A later transaction can therefore overwrite the metadata of an earlier deposit, potentially causing the earlier funds to be treated as a refund to an attacker-controlled origin or otherwise processed under attacker-chosen instructions.

### Finding Description
`Bitcoin::get_outputs` declares `outputs` outside the per-transaction loop at `processor/src/networks/bitcoin.rs:686-691`. For every transaction, newly discovered outputs are appended to this shared vector at `processor/src/networks/bitcoin.rs:692-700`. If the vector is non-empty, the function derives `presumed_origin` from only the current transaction's first input and `data` from only the current transaction at `processor/src/networks/bitcoin.rs:706-730`. It then assigns those values to every element of the shared `outputs` vector at `processor/src/networks/bitcoin.rs:731-736`, including outputs created by earlier transactions in the same block.

This is especially exploitable because the population block runs whenever any earlier output exists; the current transaction does not need to contain a matching output itself. `instruction_from_output` uses `output.data()` as the deposit's instruction and `presumed_origin` as the fallback refund origin at `processor/src/multisigs/mod.rs:45-91`. If no valid instruction survives but an origin exists, the output can be placed into a refund plan at `processor/src/multisigs/mod.rs:934-940`.

### Impact Explanation
An unprivileged Bitcoin sender who gets a transaction included later in the same scanned block can overwrite a victim deposit's instruction data and presumed origin. If the attacker supplies invalid or empty data, the victim's valid instruction can be replaced by a refund flow to the attacker-derived origin. If the attacker supplies valid instruction data, the victim's balance can instead be processed under attacker-chosen semantics.

### Likelihood Explanation
The attacker does not need validator privileges or private-key material. They need a transaction ordered after the victim's transaction in a block processed by the scanner. Achieving that ordering may require miner cooperation or favorable mempool/block inclusion, so the issue is not trivially deterministic, but it is reachable entirely through public Bitcoin transactions.

### Recommendation
Keep transaction metadata scoped to the transaction that produced the outputs. For example, populate a per-transaction `tx_outputs` vector inside the loop, extract `presumed_origin` and `data` only when that vector is non-empty, annotate only those outputs, and then extend the block-level result. Tests should cover multiple matching deposits and an unrelated later transaction in the same block.

### Proof of Concept
1. Victim transaction `tx1` pays `N::DUST` or more to the Serai external address and embeds a valid transfer instruction.
2. Attacker transaction `tx2` appears later in the same block and either pays no Serai output or pays one while carrying attacker-controlled OP_RETURN data.
3. `Bitcoin::get_outputs` appends `tx1`'s output, then reaches `tx2` while `outputs` is still non-empty.
4. It extracts `tx2.input[0]` as `presumed_origin` and `tx2`'s OP_RETURN as `data`, then writes both values into the already-collected `tx1` output.
5. `instruction_from_output` subsequently interprets the victim output using `tx2`'s metadata instead of `tx1`'s.
