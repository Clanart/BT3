### Title
Freezing an object's code permanently and irrecoverably bricks `init::internal_maybe_initialize` for any future object owner after a legitimate ownership transfer - ([File: aptos-move/framework/aptos-framework/sources/init.move])

### Summary
`aptos_framework::init::internal_maybe_initialize` gates lazy, code-driven self-initialization of object-hosted modules on an ownership check: it only hands out the module's signer if the object's current root owner still matches the owner recorded at the module's last publish (`record_deploy_owner`, called from `code::publish_package`). The only way to "resync" this recorded owner after a legitimate object transfer is to republish (upgrade) the package. `object_code_deployment::freeze_code_object` / `code::freeze_code_object` permanently sets a package's `upgrade_policy` to `immutable`, which permanently forecloses any future republish. Combining these two independently-documented, unprivileged, mainnet-relevant features produces a state that can never be fixed: after a code object is frozen and then legitimately transferred to a new owner, `internal_maybe_initialize` will abort forever for that module, with no owner override, no timeout, and no way to satisfy `assert_may_self_initialize` again.

### Finding Description
`init::internal_maybe_initialize` [1](#0-0)  marks a module "initialized" (`check_and_set_initialized`) and then gates minting the module's signer on `assert_may_self_initialize`: [2](#0-1) 

The recorded owner comparison is populated only by `code::publish_package`, and only when the module's home address is an object and the lazy-init feature is enabled at publish time: [3](#0-2) 

There is no other write path to `deploy_owner` in `init.move` — `freeze_code_object` never touches `InitializationState`: [4](#0-3) 

Once a package's `upgrade_policy` is `immutable`, `check_upgradability` unconditionally aborts on any further `publish_package` call for that package (`EUPGRADE_IMMUTABLE`): [5](#0-4) 

Because `check_and_set_initialized` writes `only_once = some(...)` *before* `assert_may_self_initialize` runs, and a failing `assert!` aborts the whole transaction (rolling back the write), every subsequent call to `internal_maybe_initialize` for that module re-enters the same `false` branch, re-checks the same mismatched owner, and aborts again — indefinitely. This is structurally identical to the referenced oracle bug: a state machine (`oracle.latest`/`InitializationState.deploy_owner`) can only advance via one recovery action (commit a fresh price / republish the package), and that recovery action becomes permanently unavailable (feed dead / package frozen) after a normal state transition (provider switch / object ownership transfer), leaving the protocol stuck forever with no governance or timeout escape hatch.

### Impact Explanation
Any module that relies on `internal_maybe_initialize` to lazily create its key on-chain state on first genuine use (the feature's stated purpose) will never be able to complete that initialization for a legitimately transferred, frozen code object. If application logic requires that first successful initialization before allowing deposits, withdrawals, or other core operations (a standard "initialize-on-first-call" pattern this API is explicitly designed to support for object-hosted, transferable code), then all functionality gated behind it is permanently unusable by the new (legitimate) owner. Object transfer and code freezing are both intentional, permissionless, unprivileged features (freezing is explicitly encouraged: "Once modules are marked as immutable, they cannot be made mutable again"), so no admin/governance action, no owner action, and no protocol mechanism can restore correct operation — this is a permanent denial of protected state mutation / bricking of the module, with potential for permanently locked user funds if a vault-like resource is created only via this init path. This matches the "Verifier, module-init, native validation, or write-set-publish failure that reaches protected state mutation" and "freeze ... code replacement" impact buckets.

### Likelihood Explanation
Both preconditions are ordinary, expected, permissionless usage patterns rather than edge cases:
1. `LAZY_MODULE_INITIALIZATION` is a mainnet feature flag intended for exactly this object-hosted/transferable-code use case.
2. `freeze_code_object` is a documented, encouraged action for any developer wanting to lock in immutability guarantees for users (e.g., to assure users code cannot change).
3. Object transfer (sale, marketplace transfer, re-parenting) is core, permissionless Aptos object functionality.

Any developer who (a) uses lazy self-init for a transferable object-hosted module and (b) freezes that object's code — a natural sequence for "ship it, then lock it down for user trust" — will trigger this permanently once the object changes hands. No attacker action beyond a normal object transfer is required; the "attack" is simply the intersection of two intended features with no cross-invariant currently enforced (e.g., no check preventing/warning freeze while lazy-init tracking is active, and no mechanism excluded from immutability to resync `deploy_owner`).

### Recommendation
Break the hard dependency between "resync deploy owner" and "package upgradability". Options:
- Provide an owner-resync path (e.g., `init::resync_deploy_owner` or extend `freeze_code_object`/a dedicated entry function) that lets the *current* object owner re-anchor `deploy_owner` to themselves without requiring a full code republish/upgrade, independent of the package's `upgrade_policy`.
- Alternatively, gate `freeze_code_object` to require that no module in the package has outstanding lazy-init state depending on `deploy_owner` synchronization, or document/emit a warning and provide an explicit, permissionless "resync" native/entry function usable even on immutable packages, since resyncing ownership metadata is not equivalent to changing code.
- At minimum, add e2e coverage combining `freeze_code_object` with `LAZY_MODULE_INITIALIZATION` + an object ownership transfer, to make this interaction a first-class, tested invariant rather than an unhandled cross-feature gap.

### Proof of Concept
1. Enable `FeatureFlag::LAZY_MODULE_INITIALIZATION`.
2. Deploy a module `M` to a fresh object `O` via `object_code_deployment::publish` (owner = `A`). `code::publish_package` records `deploy_owner(O, M) = A` (root owner of `O`) per [6](#0-5) .
3. `M`'s entry function calls `init::internal_maybe_initialize(false)` and, on `Some(signer)`, performs first-time setup (e.g., `move_to` a `Vault` resource used by all later deposit/withdraw calls).
4. `A` calls `object_code_deployment::freeze_code_object(A, O)` → `code::freeze_code_object` sets `upgrade_policy = immutable` for all packages at `O`, per [7](#0-6) . `InitializationState` is untouched.
5. `A` legitimately transfers object `O` to `B` (e.g., `object::transfer`), a fully permissionless, standard operation.
6. `B` calls `M`'s entry function. `internal_maybe_initialize(false)`:
   - `check_and_set_initialized` returns `false` (never yet initialized) and marks `only_once = some(false)`.
   - `assert_may_self_initialize(O, module_id)` computes `recorded = Some(A)`, `object::is_object(O) == true`, but `A != root_owner(O) == B` → `ok = false` → `abort EOWNER_CHANGED_SINCE_DEPLOY`.
   - Transaction aborts, rolling back the `only_once` mark, so state remains "never initialized."
7. `B` (or anyone) retries indefinitely: same abort every time. Since `check_upgradability` at [5](#0-4)  unconditionally rejects any publish to `O` because the package is now `immutable`, there is no way to call `code::publish_package` again to re-run `record_deploy_owner` and resync `deploy_owner` to `B`. `M`'s first-time initialization, and anything gated behind it, is permanently unreachable for `B` (or any future owner).

**Uncertainty**: This finding is based on static code review only; I did not execute an actual e2e test run to confirm the exact abort/rollback semantics under Aptos's real transaction execution engine (e.g., interactions with `resource_group_member`/`ManagingRefs` gas metering during the aborted attempt), though the Move abort/rollback semantics described are standard and consistent with the codebase's own comments (`"Marking happens before the initializer runs... An abort here rolls back the mark set above"`). Confirming this end-to-end (e.g., writing the exact e2e test combining `TestContext::freeze` + object transfer + `init_module_api` harness) would require running a background Devin session with repository access, which is outside the scope of this read-only analysis.

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }

    public fun freeze_code_object(publisher: &signer, code_object: Object<PackageRegistry>) acquires PackageRegistry {
        let code_object_addr = code_object.object_address();
        assert!(exists<PackageRegistry>(code_object_addr), error::not_found(ECODE_OBJECT_DOES_NOT_EXIST));
        assert!(
            object::is_owner(code_object, signer::address_of(publisher)),
            error::permission_denied(ENOT_PACKAGE_OWNER)
        );

        let registry = borrow_global_mut<PackageRegistry>(code_object_addr);
        registry.packages.for_each_mut(|pack| {
            let package: &mut PackageMetadata = pack;
            package.upgrade_policy = upgrade_policy_immutable();
        });

        // We unfortunately have to make a copy of each package to avoid borrow checker issues as check_dependencies
        // needs to borrow PackageRegistry from the dependency packages.
        // This would increase the amount of gas used, but this is a rare operation and it's rare to have many packages
        // in a single code object.
        registry.packages.for_each(|pack| {
            check_dependencies(code_object_addr, &pack);
        });
    }
