This confirms the analog: `Message.timeout()` explicitly treats `timeoutTimestamp == 0` as `type(uint64).max` — i.e. a permanently non-expiring request [1](#0-0) . The Intent Gateway's cross-chain settlement dispatches (`RedeemEscrow`/`RefundEscrow`) explicitly set `timeout: 0` [2](#0-1) [3](#0-2) , meaning these particular messages can **never** time out and therefore can never fall back to the timeout-refund path that other apps (HyperFungibleToken/WrappedHyperFungibleToken) rely on to recover locked funds when delivery to a beneficiary fails [4](#0-3) .

### Title
Permanent lock of escrowed Intent Gateway funds when the fixed settlement beneficiary becomes untransferable, with no timeout recovery path - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
Intent Gateway cross-chain settlement (`RedeemEscrow`, `RefundEscrow`) hard-codes a fixed beneficiary in the message body and dispatches with `timeout: 0`, which the protocol interprets as "never times out." If the token transfer to that beneficiary in `_withdraw`/`withdraw` ever reverts (e.g., the token itself blocks the beneficiary — analogous to a Circle-style blacklist, or the beneficiary is a non-payable/reverting contract for native transfers), the settlement message can never be redelivered with a different beneficiary and can never time out to trigger any refund/recovery flow. The escrowed input tokens on the source chain remain frozen in the gateway indefinitely.

### Finding Description
When a solver fills a cross-chain order, `ExtrinsicIntents._fillCrossChain` dispatches a `RedeemEscrow` POST request back to the source chain naming `msg.sender` (the solver) as the fixed beneficiary, with `timeout: 0` [5](#0-4) . Similarly, a destination-side cancellation dispatches a `RefundEscrow` POST request naming `order.user` as the fixed beneficiary, again with `timeout: 0` [6](#0-5) .

`Message.timeout()` converts `timeoutTimestamp == 0` into `type(uint64).max`, i.e. the request is defined to never expire [1](#0-0) . This means `handlePostRequestTimeouts` can never be legitimately invoked for these messages, since the timeout condition `timestamp >= leaf.request.timeout()` can never be satisfied. Consequently, `onPostRequestTimeout` — the callback that other Hyperbridge apps use to refund/re-mint locked value back to the source-side owner when destination delivery is impossible [7](#0-6)  — is unreachable for `RedeemEscrow`/`RefundEscrow` messages.

When the message is eventually delivered, `onAccept()` calls `_withdraw()`, which performs a direct token transfer to the hard-coded beneficiary: `IERC20(token).safeTransfer(beneficiary, amount)` (EVM base) or the raw `.call` variant on the Tron/other integration path [8](#0-7) [9](#0-8) . If this transfer reverts — because the token contract has since denied the beneficiary address (blacklist/freeze functionality that many stablecoins implement), or because the beneficiary is a contract that reverts on receiving native value — the entire `onAccept` call reverts. Since `IHandler.handlePostRequests` requires the whole message batch item to succeed to record delivery, this failure state is not recorded as delivered; the request commitment on the source chain remains pending, indefinitely re-deliverable by any relayer but always reverting for the same reason, and with no possibility of the timeout path activating due to `timeout: 0`.

There is no mechanism analogous to CCTP's `replaceMessage` to update the beneficiary of the in-flight message, and no other Hyperbridge code path lets `_orders[commitment][token]` escrow be released to any other address once the withdrawal request beneficiary is fixed and rejecting transfers.

### Impact Explanation
The escrowed input tokens for the order become permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract on the source chain: the solver cannot ever be paid (for `RedeemEscrow`) and the user cannot ever be refunded (for `RefundEscrow`). Because `timeout: 0` disables the only existing recovery mechanism (timeout-triggered `onPostRequestTimeout`), there is no path — permissioned or permissionless — to reclaim the funds once the beneficiary's token transfer starts reverting. This is a direct, permanent loss/lock of bridged escrow funds, matching the required impact class of stealing/loss of funds via a legitimate but unrecoverable settlement flow.

### Likelihood Explanation
The attacker primitive requires no privileged role: any unprivileged actor can cause a target token (e.g. a blacklist-capable stablecoin used as an order input/output) to refuse the solver's or user's address (via sanctions/blacklist processes, or by targeting a contract wallet that reverts on receipt), while a genuine cross-chain intent settlement is in flight. This is directly analogous to the externally reported CCTP/Wormhole scenario. Given `timeout: 0` is a hard-coded design choice (not a configuration mistake by any specific actor), any escrow settlement using a token capable of denying a recipient is permanently exposed once such denial occurs.

### Recommendation
- Do not use `timeout: 0` for `RedeemEscrow`/`RefundEscrow` dispatches; set a bounded timeout so that failed deliveries can eventually flow through `onPostRequestTimeout` and release escrow through an alternative path (e.g., back to the original order owner, or into a claimable-by-address-change recovery mapping) rather than being permanently stuck.
- Wrap the beneficiary transfer in `_withdraw`/`withdraw` with a try/catch (or use `call` with success handling as already done for native tokens) so that a reverting ERC20 transfer does not permanently block the settlement message from being marked delivered; on transfer failure, fall back to an escrow-style "claimable" balance that any authorized alternate address (e.g. governance-controlled) can redirect.
- Consider adding a governance-gated recovery action (as the external report also proposes) to redirect escrow to a new beneficiary address for orders whose settlement message is permanently undeliverable.

### Proof of Concept
1. Alice places a cross-chain order on Chain A with `order.inputs` in Token X (a blacklist-capable stablecoin), destined to be filled on Chain B.
2. A solver fills the order on Chain B via `fillOrder`, and `ExtrinsicIntents._fillCrossChain` dispatches a `RedeemEscrow` POST request back to Chain A naming the solver as `beneficiary`, with `timeout: 0` [10](#0-9) .
3. While the message is in flight, an attacker dusts the solver's address on Chain A with stolen/sanctioned Token X funds, causing Token X's issuer to blacklist the solver's address on Chain A.
4. When the relayer submits `handlePostRequests` on Chain A, `onAccept()` → `_withdraw()` attempts `IERC20(TokenX).safeTransfer(solver, amount)`, which reverts due to the blacklist [11](#0-10) .
5. The request is never marked delivered; it also can never time out because `timeoutTimestamp == 0` is defined as `type(uint64).max` [1](#0-0) .
6. The escrowed Token X remains locked in the `IntentGatewayV2` contract on Chain A forever — the solver cannot be paid and there is no alternate withdrawal or timeout-refund route.

`PostRequest` and `GetRequest` both have the ability to time out due to their `timeout_timestamp` value. This value stipulates the lifespan of a message.
