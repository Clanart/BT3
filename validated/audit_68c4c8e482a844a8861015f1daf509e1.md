### Title
Submodule update can be run with `file://` protocol re-enabled during untrusted branch/commit checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation()` conditionally appends `-c protocol.file.allow=always` to `git submodule update --init --recursive` based on an `allowFileProtocol` boolean threaded in from `checkoutBranch()`/`checkoutCommit()`. [1](#0-0)  Git disables the `file://` transport for submodules by default specifically to stop a malicious repository from declaring a submodule whose URL points at an arbitrary local path, which would otherwise be silently read/cloned into the working tree during `submodule update`. Desktop explicitly re-enables that transport for some checkout paths. [2](#0-1) [3](#0-2) 

### Finding Description
`checkoutBranch` and `checkoutCommit` both accept an `allowFileProtocol` flag (default `false`) that is forwarded unchanged to `updateSubmodulesAfterOperation`, which injects `protocol.file.allow=always` into the `git submodule update --init --recursive` invocation whenever the flag is `true`. [2](#0-1) [4](#0-3)  The corrupted value is the effective transport allow-list used for that single `submodule update` invocation: normally git refuses `file://` submodule URLs to prevent a hostile `.gitmodules` from pointing a submodule at an attacker-chosen local filesystem path; with the override, git will follow that URL and materialize its contents into the checkout.

The `.gitmodules` file and its submodule URLs are attacker-controlled content — they come from whatever commit/branch is being checked out, e.g. a fork branch associated with a pull request. Desktop's own test suite specifically exercises `checkoutBranch(repository, branchWithSubmodule, null, undefined, true)` to model "checking out a branch obtained from a PR" with an uninitialized submodule. [5](#0-4) 

### Impact Explanation
If a hostile PR author sets a submodule URL to `file:///Users/victim/.ssh` (or any other locally readable path) and the reviewer checks out that PR/branch in Desktop while `allowFileProtocol` is enabled for that path, `git submodule update --init --recursive` will clone/copy that local directory into the repository's working tree — a filesystem read outside the intended repository boundary. If the reviewer subsequently stages and pushes, the copied content is exfiltrated to the attacker's own fork/remote, i.e. silent corruption of what the user commits and pushes.

### Likelihood Explanation
This requires confirming that a reachable Desktop UI action (e.g., opening a fork's PR branch via `openBranchNameFromUrl`/protocol handler) actually passes `allowFileProtocol = true` into `checkoutBranch`/`checkoutCommit` for content originating from an untrusted fork. I was not able to trace that exact call site within the available iterations — I only found the parameter's existence, its doc comment ("Whether to allow file:// protocol for submodules"), and a unit test that simulates the PR-checkout-with-uninitialized-submodule scenario using `true`. This is circumstantial, not confirmed, so I flag this as **unverified but strongly suggestive** — the parameter's very existence and the specific test scenario indicate the flag is meant to be enabled specifically for fork/PR-originated content, which is exactly the untrusted-content case that matters. A full confirmation would require reading `app/src/ui/dispatcher/dispatcher.ts` around `openBranchNameFromUrl`/`openPullRequestFromUrl` and any UI action that calls `dispatcher.checkoutBranch`/`checkoutCommit` with this flag, which I could not complete.

### Recommendation
Before shipping/relying on this as a confirmed finding, verify whether `allowFileProtocol: true` is ever propagated from a PR/fork-checkout code path (as opposed to only being used for tests or fully local/trusted flows). If confirmed, restrict `protocol.file.allow=always` to genuinely trusted scenarios only (e.g., submodules whose URL was already present and initialized before the untrusted checkout), or validate/reject `file://` submodule URLs sourced from remote branches/PRs before calling `git submodule update`.

### Proof of Concept
Conceptual PoC (unverified end-to-end): attacker creates a fork PR whose branch modifies `.gitmodules` to include a submodule URL of `file:///Users/<victim>/.ssh`; if the Desktop code path that checks out that PR branch calls `checkoutBranch(...)`/`checkoutCommit(...)` with `allowFileProtocol=true`, then on checkout, `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which would materialize `.ssh` into the checkout. [4](#0-3) 

Given the unresolved call-site verification, I present this as the strongest analog I could substantiate from the indexed code, but with an explicit caveat about the missing link. If you want certainty here, a Devin session with full repo access (not the size-limited index) should trace every caller of `checkoutBranch`/`checkoutCommit` to see which pass `allowFileProtocol: true` and under what trust conditions.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
