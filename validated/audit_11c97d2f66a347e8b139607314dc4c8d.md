I found a plausible analog: GitHub Desktop's `updateRemoteUrl` silently rewrites a repository's `origin` remote URL based on data returned by the GitHub API, without any user confirmation, mirroring the report's core issue — an authoritative mapping being swapped to a new "backend" while old dependents (unaware of the swap) keep relying on stale assumptions, leading to funds/actions going to the wrong destination.

### Title
Silent, unconfirmed rewrite of a repository's remote URL from GitHub API data can redirect fetches/pushes to an attacker-influenced destination - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` [1](#0-0)  compares the locally configured `origin` remote URL against `apiRepo.clone_url` fetched fresh from the GitHub API, and if the stored `gitHubRepository.cloneURL` (last known API value) still matches the current remote and the protocol hasn't changed, it calls `gitStore.setRemoteURL` to overwrite the local remote with the new API-provided URL, with no user prompt [2](#0-1) . This is invoked from `repositoryWithRefreshedGitHubRepository`, which runs automatically on repository refresh / account-change flows [3](#0-2) .

### Finding Description
The invariant being broken is analogous to the report: a trusted mapping (payment-type → balance tracker in the contract; local git remote → GitHub repository clone URL in Desktop) is updated in place based on an external authority (marketplace owner call; GitHub API response) while old client-side state/assumptions (unspent credits; approvals from users/mechs; local git history and pending work) are not migrated or re-validated. In Desktop's case, `updateRemoteUrl` treats the GitHub API's `clone_url` as fully authoritative and rewrites the user's configured remote whenever it detects the remote "hasn't been manually changed" relative to the last cached `cloneURL` [4](#0-3) . Because renames, forks-to-different-owner, or transfer operations on the GitHub side are enough to change `clone_url`, and this whole chain runs unattended during background repository refresh [5](#0-4) , the app will silently repoint `origin` without the user reviewing or approving the new destination. There is no guard requiring the target owner/org to remain the same trust boundary as before — only that the *protocol* (https vs ssh) is unchanged and that the previously cached URL still matches what's configured locally.

### Impact Explanation
If an attacker can influence the API-reported `clone_url` for a repository the user has associated in Desktop (e.g., a repository owner renames/transfers a shared repo, or a compromised/malicious collaborator changes repository metadata in a way surfaced through the API), Desktop will automatically retarget the local `origin` remote to the new URL the next time the repository is refreshed — without any user-visible confirmation dialog (unlike the explicit, opt-in remote URL editing UI in Repository Settings [6](#0-5) ). Subsequent user actions like "Pull" or "Push" would then silently operate against a different remote than the user believes, which matches the requested impact category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
The refresh path executes automatically in the background (`refreshSelectedRepositoryAfterAccountChange` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) [7](#0-6) , requiring no unusual user action — the user simply needs to have the repository open in Desktop while background refresh runs. The precondition is that the GitHub API's `clone_url` for the associated repository changes in a way `urlMatchesRemote`/protocol checks don't block [8](#0-7) . This is a design decision baked into normal rename-handling behavior rather than an exploitable memory-safety bug, so likelihood of a distinct "attack" (versus legitimate rename UX) is uncertain without further verification of exactly which API-side actions (by whom, with what permission) can trigger a `clone_url` change for a repo the victim didn't rename themselves.

### Recommendation
Require explicit user confirmation before automatically changing the local `origin` URL based on API data, especially when the change implies a different owner/organization than before, and log or surface the change prominently (similar to how `MissingRepository`/`AddExistingRepository` prompt for explicit "Trust Repository" actions on `safe.directory` [9](#0-8) ). At minimum, gate the automatic rewrite on same-owner renames and prompt for cross-owner/org changes.

### Proof of Concept
1. User adds/clones a repository in Desktop that is associated with a GitHub repository (`gitHubRepository.cloneURL` cached).
2. Repository owner (or an attacker with sufficient permission on the GitHub-side repository object) renames/transfers the repository, changing `clone_url` returned by the API while keeping protocol the same.
3. Desktop performs a background refresh, calling `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` [3](#0-2) .
4. Since `remoteUrlUnchanged` is true (user hadn't manually edited remote) and protocols match, `gitStore.setRemoteURL` is called silently [10](#0-9) , confirmed by the existing unit test demonstrating automatic rewrite [11](#0-10) .
5. User's next push/pull now targets the new URL without having reviewed or approved it.

Note: I was unable to fully verify from the indexed code alone exactly which GitHub-side actors/permissions can cause `clone_url` to change for a victim's associated repository (e.g., whether a non-owner collaborator or a malicious fork/rename chain could trigger it), which affects the precise likelihood assessment. Confirming this would require deeper investigation of the API/account-matching logic (`matchGitHubRepository`) or a live Desktop session.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }
