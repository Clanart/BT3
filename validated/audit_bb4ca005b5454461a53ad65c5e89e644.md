## Title
`WombatStaking.depositLP()` mints receipt tokens and stakes based on nominal amount instead of actual LP tokens received, breaking accounting for fee-on-transfer LP tokens - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers the LP token via `safeTransferFrom` and then uses the caller-supplied `_lpAmount` (not the actual balance increase) both to stake into MasterWombat and to mint receipt tokens. This is the same bug class as the referenced Code4rena finding: it assumes the transferred amount equals the received amount, which is false for any fee-on-transfer token.

### Finding Description
In `deposit()`, the contract correctly guards against tokens whose received amount differs from the nominal transfer amount by measuring the LP balance before/after the external pool call: [1](#0-0) 

However, `depositLP()` does not apply the same before/after balance check. It transfers the LP token using `safeTransferFrom`, then immediately stakes and mints receipt tokens using the raw `_lpAmount` parameter, not the actual amount received: [2](#0-1) 

`_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` forwards `_lpAmount` into `_stakeToWombatMaster`, which approves and deposits exactly `_lpAmount` into MasterWombat: [3](#0-2) 

If `poolInfo.lpAddress` charges a transfer fee, the actual balance received by `WombatStaking` is strictly less than `_lpAmount`, yet:
1. The contract attempts to stake the full nominal `_lpAmount` to MasterWombat (which itself performs a `transferFrom` of `_lpAmount` from `WombatStaking`), and
2. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints receipt tokens for the full nominal amount rather than the amount actually custodied.

This path is reachable directly by an ordinary wallet through the corresponding pool helper's `depositLP()`, which forwards `_for = msg.sender` and does not perform any additional accounting correction for the actual LP amount received by `WombatStaking`: [4](#0-3) 

### Impact Explanation
If the pool's underlying LP token were ever a fee-on-transfer/deflationary token, `depositLP()` creates a permanent mismatch between (a) the receipt tokens minted (representing claims on custodied LP/staking-token balance) and (b) the LP tokens actually held/staked by `WombatStaking`. This leads to protocol insolvency for that pool: staked LP tokens redeemable via `withdraw()` are insufficient to cover all minted receipt-token claims, so eventually some depositors will be unable to withdraw their full balance — a permanent freeze/loss of user funds. In the more immediate case, the second `transferFrom` (into MasterWombat for the full nominal `_lpAmount`) can simply revert because `WombatStaking`'s actual balance is short by the fee, causing deposits to permanently fail (denial of service on deposits) whenever the shortfall cannot be covered by the contract's other residual balances.

### Likelihood Explanation
Likelihood depends on whether a currently or future configured LP token for a pool implements a transfer fee. `registerPool()` is admin-gated for adding pools, but the vulnerable code path itself is triggered by any ordinary user calling `depositLP()` through the pool helper — no privileged action is required to trigger the loss once such a pool exists. The root cause is purely an accounting assumption in `WombatStaking.sol` (not an external protocol or oracle issue), matching the exact bug class described in the referenced report.

### Recommendation
Mirror the pattern already used in `deposit()`: measure `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before and after the `safeTransferFrom` call in `depositLP()`, and use that actual delta (not `_lpAmount`) for staking via `_toMasterWomAndSendReward` and for minting the receipt token.

### Proof of Concept
1. Admin registers a pool where `poolInfo.lpAddress` is a fee-on-transfer token (e.g., 1% fee on transfer).
2. A user calls `WombatPoolHelper.depositLP(_lpAmount)`, which calls `WombatStaking.depositLP(lpToken, _lpAmount, msg.sender)`.
3. Inside `depositLP()`, `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount)` at [5](#0-4)  results in `WombatStaking` actually receiving `_lpAmount * 0.99`.
4. `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` attempts to stake the full `_lpAmount` (not the 0.99x actually held), and `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` mints receipt tokens for the full nominal amount at [6](#0-5) .
5. Over repeated deposits, minted receipt-token supply outpaces actual staked/held LP balance, so redemptions via `withdraw()` eventually fail for some holders, or the staking `transferFrom` to MasterWombat reverts outright due to insufficient balance.
