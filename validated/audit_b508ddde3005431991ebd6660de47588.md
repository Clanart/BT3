### Title
Deterministic reuse of cached FROST preprocess seeds leaks the secret share when the same signing context signs twice - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a single seeded `CachedPreprocess` per `context`, XOR-"encrypted" under a key derived from the private share, and never deletes or rotates it. `share_internal` calls `preprocess_internal` again for every signing round, so every `sign()` under the same `context` re-derives the exact same FROST nonces from `AlgorithmMachine::seeded_preprocess`. FROST's own documentation states that reusing a preprocess enables recovery of the private key share (crypto/frost/src/sign.rs:209-219, spec/cryptography/FROST.md:51-55). If any message (or re-attempted signing round) is signed twice under one context — which is precisely what an unbounded retry / parallel-session flow produces — the repeated nonce allows algebraic recovery of the signer's secret share, i.e., information disclosure of secret key material, the same impact class as the reported advisory (improper access control → information disclosure).

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148):

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) =
    AlgorithmMachine::new(algorithm.clone(), keys.clone()).preprocess(&mut OsRng);
  let mut cache = machine.cache();
  ... cache.0[b] ^= encryption_key_slice[b];
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}

let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
...
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

Key facts from the FROST crate:

- `from_cache` calls `seeded_preprocess(cache)` (crypto/frost/src/sign.rs:268-274), which deterministically regenerates the nonce scalars from the cached 32-byte seed. Same seed ⇒ same nonces ⇒ same published preprocess commitments.
- `share_internal` (signing_protocol.rs:150-181) invokes `preprocess_internal` for each signing operation and then calls `machine.sign(preprocesses, msg)`, producing `s = nonce + c · share` style shares (crypto/frost/src/algorithm.rs:201-211).
- There is no `CachedPreprocesses::remove`/deletion path in `signing_protocol.rs` — the cached seed persists for the lifetime of the context and is re-read on every subsequent sign.
- The XOR mask is derived from `Blake2s256("Cached Preprocess Encryption Key" || context || self.key)` (signing_protocol.rs:107-114), which is constant per context, so the stored ciphertext is also constant: this protects at-rest disclosure only, not reuse.

Therefore, if the coordinator signs two distinct `msg` values under the same `context` (or re-runs `share_internal` after a failed `complete`), the signer emits two shares `s₁ = k + c₁·x_i` and `s₂ = k + c₂·x_i` under the identical nonce `k` and identical verification data, yielding `x_i = (s₁ - s₂)/(c₁ - c₂)` — full secret-share disclosure. The library-level contract ("This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share", crypto/frost/src/sign.rs:211-213) is violated by the call site itself.

### Impact Explanation
Recovery of a validator's FROST secret share. Combined with the threshold structure, an attacker able to observe two signature shares emitted under the same cached preprocess obtains that validator's share, reducing the effective security of every threshold key (Substrate/Ristretto via `Schnorrkel`, and the same pattern applies to network keys). This is direct secret-key disclosure analogous in impact to the CVE's privileged local information disclosure.

### Likelihood Explanation
Reuse requires `share_internal` to be called more than once per `context`. The code does not enforce or document a single-use invariant for `context`, and the cache is keyed purely on `context.encode()` — any retry of a failed signing attempt, or any second signature request routed to the same context (e.g., a re-signed or corrected transaction batch in the same tributary session), deterministically produces a nonce collision. Because the collision is deterministic (seeded RNG), no adversarial preprocessing is needed: honest repetition is sufficient, and a malicious peer who can trigger a second sign under the same context recovers the share from the two public shares plus public challenge data.

### Recommendation
Either rotate the cached seed after each use (e.g., `CachedPreprocesses::set(context, hash(seed))` or delete the entry after `sign`), or include a per-signing-attempt nonce/attempt counter in `context` so each logical signature derives a distinct seed, or have `share_internal` generate a fresh `preprocess` via `preprocess(&mut OsRng)` instead of reusing the cached seed. At minimum, `preprocess_internal` must guarantee that each `from_cache` is consumed by at most one `sign`.

### Proof of Concept
1. Instantiate `SigningProtocol` with a fixed `context` C (e.g., a session+attempt encoding that does not change between retries).
2. Call `share_internal(participants, preprocesses_A, msg1)` → emits share `s₁` whose nonce is derived from `CachedPreprocess(seed)` persisted in `CachedPreprocesses`.
3. Call `share_internal(participants, preprocesses_B, msg2)` (a re-attempt or second payload under the same context) → `preprocess_internal` re-reads the same seed, `seeded_preprocess` regenerates identical nonce scalars, so the emitted share `s₂` uses the same nonce `k`.
4. With `s₁ = k + c₁·x_i`, `s₂ = k + c₂·x_i` (challenges `c` publicly computable from `nonce_sums`/`group_key`/`msg` per crypto/frost/src/algorithm.rs:208), solve `x_i = (s₁ − s₂)·(c₁ − c₂)⁻¹` — the signer's private share is fully recovered from public data.

Caveat: if the coordinator guarantees `context` is unique per logical signature (e.g., it embeds a monotonically increasing attempt ID), this reduces to a latent API hazard rather than an exploitable bug; the code shows no such guarantee inside `signing_protocol.rs` and the cache is never invalidated.
