### Title
Wallet-side DataLayer singleton record uses stale amount instead of `new_amount`, desyncing local DL wallet state from the on-chain spend - ([File: chia/data_layer/data_layer_wallet.py])

### Summary
`DataLayerWallet.create_update_state_spend` accepts an optional `new_amount` parameter to change a DataLayer singleton's amount on an update spend. The on-chain condition (the actual `CREATE_COIN`) correctly uses `new_amount` when provided, but the wallet's local `SingletonRecord` bookkeeping (`coin_id`, `lineage_proof`) is computed using the old `singleton_record.lineage_proof.amount` in every case, regardless of `new_amount`. This mirrors the reported bug class: a correctly-computed "new" value is calculated, but a different (stale) variable is used when persisting the resulting state, causing the tracked state to diverge from the actual on-chain outcome.

### Finding Description
In `create_update_state_spend` (`chia/data_layer/data_layer_wallet.py`), the `CreateCoin` primary that becomes the real on-chain condition is built with: [1](#0-0) 

using `singleton_record.lineage_proof.amount if new_amount is None else new_amount` — i.e., it correctly honors an overridden amount.

However, the `SingletonRecord` that the wallet stores locally to track the resulting singleton (used to compute the next spendable coin, generation, and `coin_id`) is built earlier using only the old amount, ignoring `new_amount` entirely: [2](#0-1) 

The same stale-amount value is reused for the announcement-path second-coin/second-record construction and for the corrected `new_singleton_record` replacement: [3](#0-2) 

If `new_amount` differs from `singleton_record.lineage_proof.amount`, the actual created coin on-chain will have `next_full_puz_hash` and `new_amount`, giving it a coin ID of `Coin(current_coin.name(), next_full_puz_hash, new_amount).name()`. But the wallet records `new_singleton_record.coin_id` (and `lineage_proof.amount`) as if the coin had the *old* amount: `Coin(current_coin.name(), next_full_puz_hash, singleton_record.lineage_proof.amount).name()`. Since `Coin.name()` is derived from `(parent, puzzle_hash, amount)`, a different amount produces a completely different coin ID. The wallet's DL store would then track a `SingletonRecord` whose `coin_id`/`lineage_proof` do not correspond to any coin that actually exists on-chain, while the true child coin (with the new amount) would be unrecognized by `singleton_removed`/tracking logic expecting the old-amount-derived ID.

### Impact Explanation
This causes the DataLayer wallet's local singleton lineage tracking to diverge from the true on-chain singleton chain whenever an amount-changing update is issued. Practical consequences:
- `get_spendable_singleton_info` (used by every subsequent `create_update_state_spend`/`generate_signed_transaction` call for that launcher) would build lineage proofs and parent-info pointing at a `coin_id` that was never actually created on-chain, producing spends that fail (`ASSERT_MY_PARENT_ID_FAILED`/coin-not-found), effectively halting further updates to that DL singleton until the wallet re-syncs from chain and self-heals via `singleton_removed`.
- Even if self-healing via chain sync eventually corrects the DB, in the interim the wallet can construct and submit an invalid/inconsistent update spend for a DataLayer root update, which is a spend-triggered transaction-processing halt for that singleton — consistent with the accepted impact class ("invalid spend or... spend-triggered transaction-processing halt").

This is scoped to the DataLayer wallet path exercisable by a local RPC caller through `chia data create_data_store` / `update_data_store` type flows (`DataLayerWallet.create_update_state_spend`, invoked from `generate_signed_transaction`/`wallet_rpc_api.py`), which matches the allowed "Data Layer client" caller class.

### Likelihood Explanation
Likelihood depends on whether any current caller actually passes a non-default `new_amount`. From the code paths inspected, no in-repo caller (`chia/wallet/wallet_rpc_api.py`, `chia/data_layer/data_layer_wallet.py`, or the DL wallet tests) currently supplies `new_amount` — all use the default `None`, so the wrong-amount branch is not exercised in the wiki's shipped call paths. This is a latent/reachable API-level bug (analogous to the disclosed "assign the wrong variable" defect) rather than one demonstrated to be triggered by a currently wired code path. I could not find any test or RPC surface (given the index limitations) that sets `new_amount`, so I cannot confirm this is reachable today without further investigation into any additional callers not covered by the index.

### Recommendation
In `create_update_state_spend`, compute the local `SingletonRecord`/`LineageProof` amount consistently with the actual on-chain amount used in the `CreateCoin` condition. Introduce a single `effective_amount = singleton_record.lineage_proof.amount if new_amount is None else new_amount` early in the function, and use `effective_amount` everywhere the new child coin's amount, coin ID, and lineage proof are computed (lines ~431-445, ~468-513), instead of always defaulting to `singleton_record.lineage_proof.amount`.

### Proof of Concept
Conceptual reproduction (given current callers don't set `new_amount`, this requires a call through the underlying API directly):
1. Create/track a DL singleton (`launcher_id`) with amount `1`.
2. Call `DataLayerWallet.create_update_state_spend(launcher_id, root_hash, action_scope, new_amount=uint64(3))` directly (bypassing the wrapper that never sets it).
3. Observe that the pushed spend bundle's `CreateCoin` output amount is `3` (correct, per line 519), but `new_singleton_record.coin_id` and `lineage_proof.amount` stored via `interface.side_effects.singleton_records.append(new_singleton_record)` are derived using amount `1` (the old amount).
4. On the next `get_spendable_singleton_info(launcher_id)` call, the wallet will construct a spend using a parent lineage/coin ID that does not match the coin that chain sync will eventually observe (whose ID is derived from amount `3`), causing the next update spend to fail validation on submission.
