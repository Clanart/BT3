### Title
`Interpolation::Constant` coefficient list is never length-checked, so attacker-deserialized `ThresholdKeys` panic on unconditionally indexed interpolation factor - ([File: crypto/dkg/src/lib.rs])

### Summary
The external report describes a NULL dereference: on an early-fallback path, the kernel deletes the subflow context and a later path unconditionally dereferences it. The Serai analog is an unconditionally indexed lookup into attacker-controlled structure fields: `Interpolation::Constant(Vec<F>)` stores a caller/deserializer-supplied coefficient vector, and `interpolation_factor` indexes it as `c[u16::from(i) - 1]` with no bounds check and no validation at construction or deserialization time that `c.len() >= n`. A `ThresholdKeys` decoded from untrusted bytes carrying a short `Constant` list therefore panics the first time any view is taken, mirroring the "context freed/invalid yet unconditionally dereferenced" class.

### Finding Description
`ThresholdKeys::new` validates `verification_shares.len() == n` and every participant key `<= n`, and for `Interpolation::Constant` only validates `t == n`. It never checks that the coefficient vector has at least `n` elements. Immediately after validation it computes the group key by indexing each participant's verification share and calling `interpolation.interpolation_factor(*i, &t)`, which for `Constant` executes `c[usize::from(u16::from(i) - 1)]`. The same unchecked index is used in `ThresholdKeys::view` for both the secret share and every per-participant verification share. If the `Interpolation::Constant` vector is shorter than `n` (e.g., empty, or truncated by a maliciously crafted serialization), any `i > c.len()` causes an out-of-bounds panic inside library code. Because the panic occurs inside `ThresholdKeys::new`/`view` rather than at the byte-parsing boundary, any code path that builds keys from `ThresholdKeys::read`/deserialization and then calls `view` (which `AlgorithmSignMachine::sign` does unconditionally via `self.params.keys.view(included.clone()).unwrap()`) hits the poisoned index.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (a listed attacker-reachable entry point) can persistently crash the host process: every signing attempt that interpolates the loaded keys panics. Within Serai's deployment this corresponds to permanently laming a signer/key-share holder who restores keys from serialized form — a denial of service on the threshold-signing path with no way to recover besides discarding the corrupted key material. This is availability-only (no key recovery, no forged signature), so severity is Medium.

### Likelihood Explanation
Reachability requires a `ThresholdKeys` serialization path that does not re-run `ThresholdKeys::new`'s (already insufficient) validation, or a deserialization that constructs `Interpolation::Constant` directly. I could not fully verify whether the borsh/`ThresholdKeys::read` path routes through `ThresholdKeys::new` — if it does, the gap is confirmed; if the core is deserialized field-wise without any check, it is confirmed a fortiori. In either case no code in `crypto/dkg/src/lib.rs` bounds `c.len()` before indexing, so the panic is guaranteed once a short vector reaches the structure.

### Recommendation
In `ThresholdKeys::new`, for `Interpolation::Constant(c)` require `c.len() == usize::from(params.n())` (or `>= n`) in addition to `t == n`, returning a `DkgError` otherwise. Ensure any `ThresholdKeys`/`ThresholdCore` deserialization constructor routes through this validation so untrusted bytes cannot produce an internally inconsistent `Interpolation`.

### Proof of Concept
```rust
// crypto/dkg style PoC (conceptual)
let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();
// Attacker-crafted: Constant interpolation with zero coefficients
let interp = Interpolation::Constant::<F>(vec![]);
let mut vs = HashMap::new();
vs.insert(Participant::new(1).unwrap(), G::generator());
vs.insert(Participant::new(2).unwrap(), G::generator());
// Passes all checks in ThresholdKeys::new (t == n, shares.len() == n),
// then panics inside interpolation_factor at c[0] (index out of bounds)
// when computing the group key.
let _ = ThresholdKeys::new(params, interp, Zeroizing::new(F::ONE), vs);
```
Equivalently, bytes fed to `ThresholdKeys::read` encoding `Interpolation::Constant` with a short vector produce the same panic on the first `view()`/`sign()`.
