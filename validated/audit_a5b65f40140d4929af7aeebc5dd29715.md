### Title
Coinbase outputs are reported as spendable before maturity - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_block` scans every transaction in `block.txdata`, including the coinbase, and emits matching outputs as `ReceivedOutput`, a type documented as “A spendable output” [1](#0-0) . A miner can therefore place a coinbase output paying a registered Serai script and cause the scanner to report funds as received even though Bitcoin consensus does not allow them to be spent until coinbase maturity [2](#0-1) .

### Finding Description
`scan_block` iterates over `block.txdata` starting at index 0 and forwards each transaction to `scan_transaction` [3](#0-2) . `scan_transaction` treats every matching `script_pubkey` as a `ReceivedOutput` containing the registered scalar offset, the full `TxOut`, and its outpoint [4](#0-3) . It does not distinguish ordinary transaction outputs from `block.txdata[0]`, so the returned value has no way to represent that the coinbase output is temporarily consensus-unspendable [1](#0-0) .

### Impact Explanation
An unprivileged miner can cause Serai’s Bitcoin scanner to report an immature coinbase output as a received, spendable wallet output [5](#0-4) . If downstream accounting treats `ReceivedOutput` according to its “spendable output” contract, it may credit funds or select an input that Bitcoin rejects until maturity [1](#0-0) . This produces funds reported as received that are not presently spendable and can cause an attempted spending transaction to fail consensus validation [6](#0-5) .

### Likelihood Explanation
The attacker needs to produce a valid Bitcoin block whose coinbase pays one of the scanner’s registered P2TR scripts [7](#0-6) . Mining is permissionless, and the attacker does not need access to Serai’s threshold key because the deposit script can be constructed from the public group key and registered offset [8](#0-7) . Once the block is supplied to `scan_block`, inclusion of the coinbase is deterministic [3](#0-2) .

### Recommendation
Do not pass `block.txdata[0]` to `scan_transaction`; iterate `block.txdata[1..]` when scanning full blocks [3](#0-2) . Alternatively, add an explicit maturity/coinbase marker to the returned output model so callers cannot mistake an immature coinbase for a spendable `ReceivedOutput` [1](#0-0) .

### Proof of Concept
```rust
// `key` is the scanner's public group key and `offset` was returned by
// `register_offset`.
let mut scanner = Scanner::new(key).unwrap();
let offset = scanner.register_offset(offset).unwrap();

// A miner constructs a valid block whose coinbase pays the registered script.
let coinbase = Transaction {
    // valid coinbase fields omitted
    output: vec![TxOut {
        value: Amount::from_sat(50_0000_0000),
        script_pubkey: p2tr_script_buf(
            key + (ProjectivePoint::GENERATOR * offset)
        ).unwrap(),
    }],
    ..Default::default()
};
let block = Block {
    header: valid_header,
    txdata: vec![coinbase],
};

// This returns one `ReceivedOutput`, even though Bitcoin rejects spending the
// coinbase output before maturity.
assert_eq!(scanner.scan_block(&block).len(), 1);
```

The behavior follows directly from `scan_block` including `block.txdata[0]` and `scan_transaction` converting the matching `script_pubkey` into `ReceivedOutput` [5](#0-4) [3](#0-2) .

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
