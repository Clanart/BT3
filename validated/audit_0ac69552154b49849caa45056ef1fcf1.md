### Title
Malformed PedPoP share reveals reusable ECDH decryption key - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`KeyMachine::calculate_share` produces and returns an `EncryptionKeyProof` before verifying the encrypted message’s Schnorr proof of possession. A malicious participant can replay a victim’s encryption public key with corrupted ciphertext and an invalid PoP. The recipient immediately derives the ECDH point and returns it as blame material when scalar deserialization fails, even though the batch verification that would have rejected the message has not yet run. That revealed ECDH point also decrypts the original ciphertext that used the same public ephemeral key.

### Finding Description
`EncryptedMessage::read` accepts untrusted serialized `key`, `pop`, and ciphertext fields without authenticating them. [1](#0-0)  During `Encryption::decrypt`, the PoP is only queued into the supplied `BatchVerifier`; the function then computes `ecdh(self.enc_key, msg.key)`, decrypts the ciphertext, and constructs an `EncryptionKeyProof` containing that ECDH point. [2](#0-1) 

`KeyMachine::calculate_share` calls this routine for every supplied share and immediately checks whether the decrypted bytes form a canonical scalar. [3](#0-2)  If `C::F::from_repr` rejects those bytes, the function returns `PedPoPError::InvalidShare` with `Some(blame.clone())` before reaching `batch.verify_with_vartime_blame`. [4](#0-3) 

This ordering creates an oracle for the ECDH point `recipient_enc_key * attacker_supplied_key`. The code explicitly identifies disclosure of such a blame key as dangerous: it notes that reusing an observed encryption key could cause a recipient to reveal the ECDH key and thereby expose another party’s message. [5](#0-4) 

### Impact Explanation
An attacker can copy a previously observed `EncryptedMessage` sent to a target recipient, preserve its ephemeral public key, alter the encrypted scalar bytes to a non-canonical representation, and use an invalid PoP. The recipient returns the ECDH point in `EncryptionKeyProof` before discovering the PoP is invalid. Anyone receiving that proof can initialize the same ChaCha20 cipher with the revealed point and decrypt the original message carried under the same ephemeral key. In this protocol, that message contains a PedPoP secret share, so the issue can disclose key-share material.

This is secret leakage caused by untrusted protocol input, not merely a DoS or malformed-message rejection.

### Likelihood Explanation
The attacker must be able to send a PedPoP share message to a recipient and observe a prior encrypted share message using the ephemeral key being attacked. PedPoP inputs are explicitly supplied as a `HashMap<Participant, EncryptedMessage<...>>` to the public `calculate_share` API. [6](#0-5)  No private-key compromise, unsafe code, malformed curve implementation, or protocol-level collusion is required. The malformed scalar is easy to construct because `SecretShare::read` accepts an arbitrary field representation buffer and validation only occurs after decryption. [7](#0-6) 

### Recommendation
Do not derive, return, or expose an `EncryptionKeyProof` until the message’s PoP has been verified successfully.

Concretely:

1. Queue the PoP and complete the relevant batch verification before decrypting `msg.msg` or constructing `EncryptionKeyProof`.
2. If authentication fails, return an invalid-message error with `blame: None`.
3. Ensure `calculate_share` cannot return a blame proof on the `C::F::from_repr` path before the queued PoP has passed.
4. Consider adding a regression test that copies an honest encrypted share, corrupts only its ciphertext and PoP, calls `calculate_share`, and asserts that no ECDH point capable of decrypting the original message is emitted.

`SecretShare::read` preserves arbitrary ciphertext bytes rather than checking scalar canonicity at decode time. [7](#0-6)  Decryption therefore produces non-canonical scalar bytes, causing `from_repr` to fail and returning `InvalidShare { blame: Some(blame) }` immediately. [8](#0-7)  The attached `blame.key` is `recipient_enc_key * observed_public_key`, which is exactly the ECDH point required by `cipher` to decrypt the observed ciphertext. [9](#0-8)
