## Title
`WombatPoolHelperV2.depositFor` hardcodes zero slippage protection, exposing depositors to sandwich attacks with unpredictable share pricing - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2` exposes two paths to deposit into a Wombat pool and mint receipt/staking shares: `deposit(uint256 _amount, uint256 _minimumLiquidity)`, which lets the caller supply their own slippage bound, and `depositFor(uint256 _amount, address _for)`, which silently passes `0` as the minimum liquidity regardless of user intent.

### Finding Description
`deposit()` forwards a user-supplied `_minimumLiquidity` all the way to the underlying Wombat pool's `deposit` call via `WombatStaking.deposit`, giving the depositor real slippage protection against unfavorable price movement between transaction submission and execution. [1](#0-0) 

`depositFor()`, however, calls `_deposit(_amount, 0, _for, address(this))`, hardcoding the minimum liquidity to `0` no matter what the actual market conditions are: [2](#0-1) 

This `_minimumLiquidity` value is passed straight through to the Wombat pool's own price-setting deposit call: [3](#0-2) 

Because `depositFor` is a fully public, unprivileged function — callable by any wallet directly, and also used internally as the deposit path for flows such as `mWOM.convertAndStake` via `ISimpleHelper(helper).depositFor(...)` — every share purchase routed through it commits the depositor to accept *any* amount of LP/receipt tokens greater than zero, no matter how the Wombat pool's internal price (governed by its cash/liability ratio) has moved by the time the transaction is mined.

This is exactly the class of issue described in the referenced report: users cannot set a bound on the price at which their deposit executes, because the price is read from state at execution time with no way for the caller to enforce a minimum acceptable output.

### Impact Explanation
Any user (or a flow like `mWOM.convertAndStake` that routes through `depositFor`) is committing to mint shares at whatever price exists at execution time, with a floor of zero. This allows a searcher/MEV bot to sandwich the deposit transaction: shift the Wombat pool's exchange rate unfavorably immediately before the victim's `depositFor` call executes (e.g., via a large swap that worsens the cash/liability ratio for the deposited asset), let the victim's deposit mint them a reduced amount of LP/receipt shares for their input, then reverse the price shift afterward and pocket the difference. This is a direct, silent value extraction from ordinary depositors' funds, not merely a theoretical inconvenience — since `_minimumLiquidity` is hardcoded to `0`, there is no way for the depositor to prevent or even detect the loss before it happens.

### Likelihood Explanation
`depositFor` is an unprivileged, externally callable function reachable directly by any wallet, and is also the deposit path used by the `mWOM` conversion flow. Since Wombat pool pricing (cash/liability-based) can be moved by ordinary swaps, sandwiching a `depositFor` call requires no special privilege or oracle manipulation — only a same-block front-run/back-run swap, which is standard, low-cost MEV activity.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (and thread it through from all callers, including `mWOM`/`ISimpleHelper` integrations) instead of hardcoding `0`, so that depositors — or the contracts depositing on their behalf — can specify an acceptable slippage bound just as `deposit()` already allows.

### Proof of Concept
1. Attacker observes a pending `depositFor(_amount, _for)` transaction (either called directly by a user or triggered via `mWOM.convertAndStake`).
2. Attacker front-runs with a large swap into the same Wombat pool's depositToken, moving the pool's cash/liability ratio unfavorably for new deposits.
3. Victim's `depositFor` executes: `WombatStaking.deposit` calls `IWombatPool(poolInfo.depositTarget).deposit(depositToken, _amount, 0, ...)` — since `_minimumLiquidity` is `0`, the call succeeds despite returning far fewer LP tokens than the victim would have received at the pre-attack price. [4](#0-3) 
4. Attacker back-runs, restoring the pool state and capturing the value difference extracted from the victim's deposit.
