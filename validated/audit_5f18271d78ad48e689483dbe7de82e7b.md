### Title
Identity (zero) group key / public key is accepted as a valid signer — forged signatures verify for `group_key == identity` - (File: crypto/dkg/src/lib.rs)

### Summary
The M-01 pattern — a degenerate "zero" value passing an authorization check (`privileges[address(0)] != 0`) — exists in Serai as: `ThresholdKeys::new` / `ThresholdKeys::read` never reject a `group_key` equal to the identity point or a zero `secret_share`, and `SchnorrSignature::verify` (and the FROST `Schnorr::verify` / batch path built on it) accepts *any* signature of the form `R = s·G` under an identity public key, for any challenge/message. Whoever can get a key set whose `group_key` is the identity installed (via `ThresholdKeys::read` of untrusted bytes, or a `ThresholdKeys::new` with attacker-chosen `verification_shares` summing to identity) obtains a "signer" that any unprivileged party can forge signatures for, with no secret knowledge.

### Finding Description
`ThresholdKeys::new` computes `group_key` purely by summing caller-supplied `verification_shares` interpolated over participants `1..=t` and stores it without any identity/zero check (`crypto/dkg/src/lib.rs:376-390`). `ThresholdKeys::read` feeds attacker-controlled bytes through `read_F`/`read_G` into `ThresholdKeys::new`, so an adversary can construct a serialized `ThresholdKeys` whose verification shares sum to `C::G::identity()` (e.g., `Y_1 = P`, `Y_2 = -P`, rest arbitrary) and whose `secret_share` is zero — deserialization succeeds (`crypto/dkg/src/lib.rs:604-632`).

`SchnorrSignature::verify` checks `R + c·A − s·G == identity` via `batch_statements` (`crypto/schnorr/src/lib.rs:88-110`). When `A == identity`, the `c·A` term vanishes, so every `(R, s)` with `R == s·G` verifies for every challenge — i.e., for every message. The FROST completion path inherits this: `Schnorr::verify` builds `SchnorrSignature { R: nonces[0][0], s: sum }` and calls `sig.verify(group_key, c)` (`crypto/frost/src/algorithm.rs:214-217`), and `AlgorithmSignatureMachine::complete` returns `Ok(sig)` whenever that check passes (`crypto/frost/src/sign.rs:465-467`). With `group_key == identity`, a single participant can pick a share `s` such that `s·G` equals the summed nonce commitment `R` (which they see in the preprocess round before choosing their share — they choose share `s_i = s − Σ others`), causing `complete` to emit a "valid" threshold signature without threshold participation. This is exactly the reported shape: the zero value (`address(0)` / identity key) is treated as a privileged signer, and the signature check degenerates to an always-satisfiable equation for it. Unlike the commented assumption that such a state is impossible, nothing in `ThresholdKeys::new`/`read`/`view` or the signature verifier rejects an identity group key or zero secret share — `ThresholdKeys::scale` rejects a zero *scalar* (`crypto/dkg/src/lib.rs:400-407`) but the core key material is never validated.

### Impact Explanation
High when triggered: signatures verifying under a group/public key are the authorization primitive for every consumer of `frost`/`schnorr`. If an identity group key ever occupies a signer slot (deserialized `ThresholdKeys`, or any caller that maps a deserialized/derived key to an authorized signer without its own identity check), an unprivileged attacker can produce valid signatures — and in the FROST path can drive `complete` to emit a threshold signature unilaterally — equivalent to stealing whatever that key controls.

### Likelihood Explanation
Low-to-Medium. It requires an identity `group_key` (or identity signer key) to be accepted somewhere authorization is checked — the same precondition as `privileges[address(0)] != 0`. `ThresholdKeys::read` is an explicitly supported untrusted-bytes entry point, and neither it nor `new` guards against it; any integrator that deserializes key material and uses `group_key()` as an authorization identity is exposed. Within `crypto/frost` itself, normal `key_gen`/`musig`/`pedpop` outputs won't produce identity keys, so exploitability depends on a deserialization or key-installation path accepting adversarial bytes.

### Recommendation
- In `ThresholdKeys::new` (and therefore `read`), reject `group_key.is_identity()` and a zero `secret_share`, mirroring `Participant::new`'s rejection of zero (`crypto/dkg/src/lib.rs:29-35`).
- In `SchnorrSignature::verify` / `batch_statements` consumers, reject identity `public_key` and identity `R` before verifying (the `Signed::read` path already rejects `R == identity` at `coordinator/tributary/src/transaction.rs:62-69`; apply the same defense at the key level).
- In `AlgorithmSignatureMachine::complete`, error if `view.group_key()` is identity rather than letting `verify` degenerate.

### Proof of Concept
```rust
// crypto/dkg + crypto/schnorr, over any in-scope Ciphersuite C

// 1) Deserialize attacker-chosen ThresholdKeys with identity group_key.
//    Craft verification shares Y_1 = P, Y_2 = -P for t = 2 (Lagrange over {1,2}
//    gives coefficients (2, -1): group_key = 2P - P... choose shares so the
//    interpolated sum is identity), secret_share = 0.
let keys = ThresholdKeys::<C>::read(&mut crafted_bytes).unwrap(); // succeeds; no identity check
assert!(keys.group_key().is_identity());

// 2) Forgery for the identity key: any (R = s*G, s) verifies.
let s = C::F::random(&mut OsRng);
let sig = SchnorrSignature::<C> { R: C::generator() * s, s };
assert!(sig.verify(keys.group_key(), any_challenge)); // passes for EVERY message/challenge

// 3) FROST path: a single participant, after seeing the combined nonce R in the
//    preprocess round, submits share s_i making sum*G == R.
//    complete() -> algorithm.verify(identity, Rs, sum) -> SchnorrSignature{R, sum}
//    .verify(identity, c) == true -> Ok(sig) with no threshold reached.
```
The forged signature is accepted because `batch_statements` reduces to `R − s·G` when `A == identity` (`crypto/schnorr/src/lib.rs:88-100`), and `ThresholdKeys::new`/`read` place no constraint preventing `group_key` from being the identity (`crypto/dkg/src/lib.rs:376-390`, `crypto/dkg/src/lib.rs:625-632`).
