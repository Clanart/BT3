### Title
Line-index-based partial commit selection survives content-changing status refreshes with the same file `id` — stale selection can silently stage unreviewed lines ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`FileChange.id` is derived only from `${status.kind}+${path}` (and `oldPath` for renames), not from any content hash or line-diff fingerprint. [1](#0-0) 
When Desktop recomputes working-directory status (`updateChangedFiles`), it reuses the previously selected file's line-selection (`existingFile.selection`) purely by matching this coarse `id`, and separately reuses the cached `diff`/selectable-lines only after a `getWorkingDirectoryDiff` re-fetch, but the persisted per-line partial `DiffSelection` itself is carried over unconditionally when the `id` matches. [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the `RocketJoeStaking` pattern: a stateful value (`lastRewardTimestamp` / here, the cached per-line `DiffSelection`) is carried forward across refreshes keyed on a coarse identity check (`joeSupply == 0` / here, `FileChange.id` string equality) instead of an invariant that actually reflects the underlying data (real elapsed reward time / real diff content). An attacker who controls the repository content (e.g., through a build tool, git hook, or any process triggered while the repo is checked out — `post-checkout`, `post-merge`, editor auto-format on save, etc.) can rewrite the tracked file **without changing its git status kind** (it stays `Modified`) and **without changing its path**. Because `id = "Modified+path/to/file"` remains identical, when Desktop's next background status poll (`updateChangedFiles`) runs, the file's previous `DiffSelection` (a per-line-index inclusion map built from the *old* hunk/line layout) is carried over verbatim to the *new* file object at line 56, even though the new diff's hunks/line numbers no longer correspond to the same content the user reviewed. The UI then shows the new diff, but the underlying `selection` used for staging is indexed against stale line numbers.

The `updateChangesWorkingDirectoryDiff` flow in `app-store.ts` does attempt to trim the selection to `selectableLines` derived from the newly-loaded diff, but it only clamps/filters the *set of valid line indices* — it does not re-derive *which* lines the user actually intended to include; it merely reintersects the old selected-line-index set against the new hunk line indices. [4](#0-3) 
If line offsets shift (lines inserted/removed elsewhere in the file by the attacker-controlled process between the user's review and the next status refresh, or between refresh and commit), the same numeric line indices in the old selection now point at *different* content in the new diff, so previously-excluded lines can become included (or vice versa) with no user action and no warning.

### Impact Explanation
This can cause silent corruption of what the user commits: a user reviews a diff, deliberately excludes certain lines (e.g., a suspicious change, secret, or partial fix) via partial-file staging, and due to an intervening content change with unchanged status kind/path, the actually-committed hunk includes different lines than what was last visually confirmed. This satisfies the stated valid-impact category of "silent corruption of what the user commits or pushes," and the trigger is fully attacker-controlled repository content (a cloned/fetched repo carrying a hook or tool that rewrites a tracked file), requiring no local/physical access, admin rights, or pre-existing host compromise.

### Likelihood Explanation
Desktop polls/refreshes working-directory status frequently (file watcher events, focus changes, periodic background refresh), and any of these can race with a content-modifying process running in the repo (git hooks distributed with the malicious repo, `.gitattributes` filters, build scripts, editor format-on-save tied to file watchers) between the user's last diff review and the commit action. No special user action beyond normal usage (having the malicious repo open with partial-selection in progress) is required, making the precondition realistic though timing-dependent — it needs the status refresh with the identity-preserving corruption to land in the narrow window between selection and commit. This is lower likelihood than a fully deterministic bug but is a genuine race rather than a contrived/local-access scenario.

### Recommendation
Track selection integrity by content, not by the coarse `${status.kind}+${path}` identity. Options:
- Include a lightweight content fingerprint (e.g., blob OID or working-tree hash) in the reuse-eligibility check in `updateChangedFiles` so a partial `DiffSelection` is only carried over when the underlying blob/mtime is unchanged, otherwise reset to "select all" or force a fresh diff-based re-confirmation.
- When `updateChangesWorkingDirectoryDiff` detects the new diff's hunks differ from what the previous selection was computed against, invalidate the partial selection rather than merely reintersecting selectable line indices, and surface this to the user.

### Proof of Concept
1. Clone or open an attacker-influenced repository that ships a `post-checkout`/`post-merge` hook (or any tool that runs automatically while the repo is open in Desktop) which appends/removes lines in a tracked file, `victim.txt`, while keeping the file "Modified" relative to HEAD.
2. In Desktop, modify `victim.txt` locally, open the Changes view, and use partial-line selection to include only lines 1–5, explicitly excluding a sensitive line 6.
3. Before committing, trigger any event that causes another `git status`/diff refresh (e.g., switch focus away and back, or let the attacker's hook fire on a background git operation Desktop performs, such as auto-fetch). The hook shifts line numbers in `victim.txt` while the file remains `Modified` at the same path, so `FileChange.id` is unchanged.
4. `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:43-60`) reuses the old `existingFile.selection` verbatim onto the new file object; `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3478-3497`) only reintersects selectable line indices against the new hunks rather than re-validating intent.
5. Commit. Inspect the resulting commit diff: due to the line-index shift, content the user never intended to include (previously "line 6", now at a different index that maps into the old "included 1–5" range) can end up staged, while excluded content is committed without the user's final visual confirmation matching the actually-committed hunk.

(Note: this analysis is based on static code review of `status.ts`, `changes-state.ts`, and `app-store.ts`; I was not able to execute a live end-to-end reproduction in this environment, and the exact timing window/frequency of background status refreshes racing with an attacker's hook would need to be confirmed dynamically.)

export class FileChange {
  /** An ID for the file change. */
  public readonly id: string

  /**
   * @param path The relative path to the file in the repository.
   * @param status The status of the change to the file.
   */
  public constructor(
    public readonly path: string,
    public readonly status: AppFileStatus
  ) {
    if (
      status.kind === AppFileStatusKind.Renamed ||
      status.kind === AppFileStatusKind.Copied
    ) {
      this.id = `${status.kind}+${path}+${status.oldPath}`
    } else {
      this.id = `${status.kind}+${path}`
    }
  }
