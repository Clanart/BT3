### Title
Stale line-index-based partial-commit selections cause silent commit-content corruption when working tree files change before staging - (File: `app/src/lib/patch-formatter.ts`, `app/src/lib/git/apply.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
`DiffSelection` (`app/src/models/diff/diff-selection.ts`) tracks which lines a user wants to commit purely by **numeric index** into a diff snapshot, with no binding to the actual line content or a diff/content generation identifier. When `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3760`) runs, it takes the files as they currently sit in `repositoryStateCache` — including their possibly-stale `selection` objects — and passes them straight to `createCommit` → `stageFiles` → `applyPatchToIndex`. `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`) then re-fetches a **fresh** diff via `getWorkingDirectoryDiff` and calls `formatPatch(file, diff)`, which walks the fresh diff's hunks and asks `file.selection.isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:157`) using the OLD selection's indices. There is no re-validation that the selection's diverging-line indices still correspond to the same content in the newly fetched diff.

### Finding Description
`DiffSelection.getSelectionType`/`isSelected` (`app/src/models/diff/diff-selection.ts:87-136`) operate purely on line-number sets (`divergingLines`). The only place selections are reconciled against a fresh diff is `updateSelectedFileDiff`-style logic in `app-store.ts` around line 3466-3497, which calls `withSelectableLines` to purge indices that no longer exist — but this reconciliation is only performed for the single file currently open in the diff viewer (`selectedFileIdBeforeLoad` check at `app-store.ts:3466-3468`). Every other file with a `Partial` selection sitting in `state.changesState.workingDirectory.files` is never re-checked against the working tree's current content before being committed.

`_commitIncludedChanges` (`app-store.ts:3681-3760`) filters files by `file.selection.getSelectionType() !== DiffSelectionType.None` and passes them directly, unrefreshed, into `createCommit`. `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) routes any `Partial`-selection file to `applyPatchToIndex`, which regenerates the diff from disk (`getWorkingDirectoryDiff`) at that moment and reuses the stale `selection`. If the file's content on disk shifted (lines inserted/removed/reordered) between the time the user made their line selections and the time the commit actually executes, the index-based `isSelected(absoluteIndex)` check in `formatPatch` (`patch-formatter.ts:157`) will silently select/deselect the wrong lines relative to what the user actually reviewed and approved, with no error, warning, or diff re-confirmation shown to the user.

### Impact Explanation
This breaks the same invariant class as the external report: a security-relevant decision (what to commit/push) is made using a value (`divergingLines` index set) that is not kept in sync with the actual current state (working tree content), because there is no generation/version binding between the selection and the diff it was derived from. The result is silent corruption of what the user commits — the app can stage lines the user never reviewed/approved (potentially attacker-injected content from a cloned/fetched repository, e.g. lines added by a build tool, checkout-time filter, or another process operating on the working tree) while appearing to only commit the lines the user explicitly checked. Since Desktop then pushes this commit, this is a "silent corruption of what the user commits or pushes" impact as defined in scope.

### Likelihood Explanation
Requires that a tracked file's on-disk content changes (line count/position shift) in the window between the user making a partial-line selection and clicking Commit, for a file that is not the one currently displayed in the diff viewer (so the selectable-line reconciliation at `app-store.ts:3466-3497` never runs for it). This is realistic for a repository controlled or partially influenced by an attacker (e.g., via a checked-in tool/script, a git smudge/clean filter, or another background process modifying files in the same clone) especially in multi-file commits, without needing local/physical access, admin rights, or social engineering beyond normal repository use.

### Recommendation
Bind `DiffSelection` to a content-derived identity of the diff it was generated from (e.g., a hash of hunk contents or the diff's revision/generation ID), and before staging, re-validate every `Partial`-selection file's selection against a freshly generated diff — not just the one currently open in the UI — refusing to stage/commit (or forcing a re-review) when the underlying content has diverged from what was selected.

  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
