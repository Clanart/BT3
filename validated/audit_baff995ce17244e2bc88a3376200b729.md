## Finding

Chia's daemon deliberately redacts sensitive fields (`password`, `key`, `secret`, `mnemonic`, etc.) before writing incoming websocket messages to the debug log via `redact_sensitive_data()`, but a separate code path re-logs the **entire unredacted message** — including its `data` payload — whenever the daemon receives a command name it doesn't recognize.

### Title
Unredacted secrets logged via daemon's "unknown command" error path - (File: chia/daemon/server.py)

### Summary
`WebSocketServer.incoming_connection()` redacts sensitive keys before debug-logging incoming websocket messages, but `WebSocketServer.handle_message()` logs the original, unredacted message dict at `ERROR` level whenever the `command` field does not match a known daemon or keychain command, leaking any sensitive values (`mnemonic`, `password`, `passphrase`, `private_key`, etc.) present in the request's `data`.

### Finding Description
The daemon's incoming-message handler calls `redact_sensitive_data(decoded)` before logging received messages for debugging: [1](#0-0) 

`redact_sensitive_data()` masks any dict key whose name contains `pass`, `key`, `secret`, or `mnemonic`: [2](#0-1) 

This redaction is verified explicitly by `test_message_logging_redaction`, which confirms `password`, `private_key`, `mnemonic`, `passphrase`, `secret_value`, and nested `api_key`/`seed_mnemonic` fields are masked before being written to the log: [3](#0-2) 

However, `handle_message()` contains an independent logging call that bypasses this protection entirely. When a caller sends a `command` that is not in `keychain_commands`, is not `"ping"`, and is not present in `get_command_mapping()`, the daemon logs the **original, unredacted `message` object** at `ERROR` severity: [4](#0-3) 

`message` is the full `WsRpcMessage` dict (`command`, `ack`, `data`, `request_id`, `destination`, `origin`) as received from the client — the same object that the earlier `redact_sensitive_data()` call was specifically designed to scrub before logging. This `f"UK>> {message}"` log statement performs no redaction, so any secret embedded in `data` (e.g., `mnemonic`, `password`, `passphrase`, `private_key`, `api_key`) is written verbatim into the daemon's persistent log file.

Unlike the `DEBUG`-level "Received message" log (which may be disabled by default log-level configuration), this leak occurs at `ERROR` level, which is far more likely to be enabled and retained in production log files (including any logs collected for support/bug-report purposes).

### Impact Explanation
Any local daemon RPC client that can open a mutually-authenticated TLS websocket to the daemon — including third-party or buggy wallet/GUI tooling, scripts under active development, or any caller that mistypes/misroutes a command name — can cause the daemon to persist plaintext secrets (mnemonics, passphrases, private keys) into its on-disk log files. This is directly analogous to the auth0.js issue: the original request object, including credentials the user intended to keep secret, is disclosed through an error/log object instead of being redacted, undermining the explicit redaction control that the codebase otherwise enforces. Log files often have different (broader) read permissions or retention/export paths (e.g., diagnostics bundles) than the keyring itself, so this converts an intended-to-be-protected secret into a persistently stored plaintext artifact.

### Likelihood Explanation
Triggering this requires only sending a single daemon websocket message with an unrecognized `command` string and any sensitive value placed in `data` — e.g. as a result of a client bug, a typo'd command name, or a malformed retry of `add_private_key`/passphrase commands. Since the daemon already accepts messages with arbitrary shapes and only routes based on the `command` string, this is trivially reachable by any connected RPC caller.

### Recommendation
Route the `"UK>> {message}"` log statement through the same `redact_sensitive_data()` call used in `incoming_connection()` before logging, or better, log only the `command` name plus a redacted/summarized view of `data` rather than the raw message object. Ensure all logging call sites that touch the raw incoming `message`/`data` (not just the one in `incoming_connection`) are audited for the same bypass.

### Proof of Concept
1. Establish a valid daemon websocket connection (as any local client with daemon certs).
2. Send a JSON payload with a `command` value that does not match any entry in `keychain_commands`, `"ping"`, or `get_command_mapping()` keys, e.g.:
```json
{"command": "add_private_keyy", "data": {"mnemonic": "abandon abandon ... about"}, "ack": false, "origin": "test", "destination": "daemon", "request_id": "1"}
```
3. The daemon's `handle_message()` falls into the `else` branch at [5](#0-4)  and calls `self.log.error(f"UK>> {message}")`, writing the full mnemonic in plaintext to the daemon log file, in contrast to the redacted `"Received message"` debug log produced for the same payload just lines earlier.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
