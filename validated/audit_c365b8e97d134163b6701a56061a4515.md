### Title
OP_RETURN transaction data is excluded from weight and fee calculations, producing under-priced or oversized signed transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends the attacker-supplied OP_RETURN output to `tx_outs`, but calculates transaction weight, virtual size, required fee, and the maximum-standard-weight check using only the payment outputs. As a result, a public transaction request containing up to 80 bytes of OP_RETURN data causes all signers to produce a Taproot transaction whose actual virtual size exceeds the size for which fees were computed. The resulting transaction can violate the requested feerate, Bitcoin's default minimum relay feerate, or the maximum standard transaction-weight bound even though `SignableTransaction::new` returned `Ok`. [1](#0-0) [2](#0-1) 

### Finding Description
The constructor accepts `data` and appends an OP_RETURN output before performing weight and fee accounting. [3](#0-2) 

However, the accounting call is:

```rust
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`payments` deliberately excludes the already-created OP_RETURN output, so `calculate_weight_vbytes` constructs a model transaction without it and returns weight/vbytes smaller than the transaction actually signed. [4](#0-3) [5](#0-4) 

The same stale values are then used for:

- `needed_fee`, returned to callers through `needed_fee()`. [6](#0-5) 
- the minimum-relay-fee guard. [7](#0-6) 
- the `MAX_STANDARD_TX_WEIGHT` rejection. [8](#0-7) 

The committed transaction stored in `SignableTransaction` nevertheless contains the omitted OP_RETURN output. [9](#0-8) 

During signing, every participant signs the real transaction's Taproot sighashes, including the OP_RETURN output, so there is no later opportunity for fee or size correction. [10](#0-9) 

### Impact Explanation
An external party who can influence the optional transaction data can cause the threshold signer set to produce an invalid-for-relay transaction despite all stated checks succeeding.

Two concrete outcomes are possible:

1. **Underpriced transaction:** The signature commits to a fixed output set and therefore a fixed fee. The OP_RETURN output adds serialized size but was not charged any fee. A transaction constructed at the requested minimum viable feerate can consequently have an actual feerate below `DEFAULT_MIN_RELAY_TX_FEE` and be rejected by Bitcoin nodes. [7](#0-6) 

2. **Oversized standard transaction:** If the model transaction is just below `MAX_STANDARD_TX_WEIGHT`, an allowed OP_RETURN payload can push the actual transaction over the bound while bypassing the check. The completed signature produces a transaction Bitcoin nodes will not accept through standard relay policy. [8](#0-7) 

This is a signing-path integrity failure: the bytes validated and priced are not the bytes that the group ultimately signs. It can stall withdrawals or force a new signing round, and therefore constitutes a transaction-availability issue rather than direct private-key compromise.

### Likelihood Explanation
The trigger is a normal, public input: `data` up to 80 bytes is explicitly accepted and serialized into an OP_RETURN output. [11](#0-10) [3](#0-2) 

The defect is deterministic whenever `data` is supplied. Whether it causes relay rejection depends on the requested feerate and how close the modeled transaction is to the relevant limit, but no cryptographic assumption or participant misbehavior is required. A requester can deliberately choose transaction size and fee parameters to cross either boundary.

### Recommendation
Include every actual output in the model transaction used for weight, vbytes, fee, and standardness checks.

Conceptually:

- calculate the initial weight after constructing the complete output set, including the OP_RETURN output;
- calculate the with-change weight using payments, the OP_RETURN output, and the change output;
- reject if either the actual signed transaction exceeds standard weight or the actual fee divided by the transaction's actual vsize is below the requested/minimum rate;
- add regression coverage for transactions with 1-byte and 80-byte OP_RETURN outputs, including a boundary case around `MAX_STANDARD_TX_WEIGHT` and `DEFAULT_MIN_RELAY_TX_FEE`.

### Proof of Concept
The following demonstrates the accounting mismatch:

```rust
// networks/bitcoin/src/wallet/send.rs

let data = vec![0u8; 80];

let tx = SignableTransaction::new(
    vec![received_output],
    &[(payment_script, 546)],
    None,
    Some(data),
    1, // one satoshi per modeled vbyte
)
.unwrap();

// The stored transaction has an OP_RETURN output.
assert_eq!(tx.transaction().output.len(), 2);
assert!(tx.transaction().output[1].script_pubkey.is_op_return());

// needed_fee was priced as though only the payment output existed.
let actual_vbytes = tx.transaction().vsize() as u64;
assert!(tx.needed_fee() < actual_vbytes);
```

For a transaction whose modeled vbytes are `V`, `needed_fee` is approximately `V` when `fee_per_vbyte` is one. The actual vbytes are approximately `V + 89` after adding the OP_RETURN output, so the fixed fee is no longer sufficient for one satoshi per actual vbyte and can fall below the default relay minimum. Similarly, choosing payment outputs so the modeled weight is just under `MAX_STANDARD_TX_WEIGHT` creates an accepted `SignableTransaction` whose signed transaction exceeds the standardness bound after the OP_RETURN is included. [12](#0-11)
