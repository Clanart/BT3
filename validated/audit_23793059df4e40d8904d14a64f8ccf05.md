### Title
Missing authorization on daemon keychain user/service partitioning allows a local RPC caller to read another partition's private keys - (File: chia/daemon/keychain_server.py)

### Summary
`KeychainServer.get_keychain_for_request()` selects which `Keychain` instance (and therefore which set of private/public keys) to operate on purely from the `kc_user`/`kc_service` fields supplied inside the client's own JSON request body, with no verification that the connected daemon client is actually entitled to use that particular user/service partition. Any process that can open a websocket connection to the local daemon (the same TLS trust boundary used by `chia keys`, `chia wallet`, GUI, and any other locally-registered service) can therefore address a *different* keychain partition than the one it was configured/registered for and read the fingerprints, public keys, and (for commands like `get_key`, `get_all_private_keys`, `get_key_for_fingerprint` with `private=True`) the private keys and mnemonics stored under that other partition.

### Finding Description
`KeychainProxy.format_request()` unconditionally injects the caller-supplied `kc_user`/`kc_service` strings into every keychain command payload: [1](#0-0) 

On the daemon side, `KeychainServer.get_keychain_for_request()` reads those same attacker/caller-controlled fields straight out of the request dictionary to decide which `Keychain` object to use, lazily creating and caching a new one for any previously-unseen `(user, service)` pair: [2](#0-1) 

`WebSocketServer.handle_message()` dispatches every command whose name is in `keychain_commands` (which includes `get_key`, `get_keys`, `get_all_private_keys`, `get_key_for_fingerprint`, `add_key`, `delete_key_by_fingerprint`, `delete_all_keys`, etc.) straight to `self.keychain_server.handle_command(command, data)` without any additional access check on `kc_user`/`kc_service`: [3](#0-2) 

`get_key_for_fingerprint`, `get_all_private_keys`, and the typed `GetKeyRequest`/`GetKeysRequest` handlers all call `get_keychain_for_request(request)` and then read secrets straight from whatever `Keychain` that returns: [4](#0-3) [5](#0-4) [6](#0-5) 

The daemon's authentication model is mutual-TLS at the websocket layer, not identity/partition-based; the daemon context notes the gate is "mutual TLS using daemon private certs plus local config," with no peer-style authorization enum for individual commands. There is no code anywhere in `KeychainServer` or `WebSocketServer.handle_message` that maps a connected client's certificate/service registration to an allow-listed set of `kc_user`/`kc_service` values it is permitted to request — the value is trusted verbatim from the JSON payload the client sends. This is the direct analog of the DolphinScheduler bug: a caller who is authenticated to the RPC boundary (comparable to an "authenticated user") can address a resource collection (comparable to an "alert group" — here a keychain partition of private keys) that it was never granted, purely by supplying a different identifier in the request, because the server performs no ownership/permission check before returning the associated secrets.

### Impact Explanation
An unprivileged local process that can reach the daemon websocket (e.g., a mis-scoped or compromised service, a locally running non-Chia process discovered to have daemon cert access, or any code path that ends up sending arbitrary keychain-command JSON) can enumerate `kc_user`/`kc_service` values (they are often predictable, e.g., version-tagged strings like `"testing-1.8.0"`/`"chia-testing-1.8.0"` as seen in `chia/simulator/block_tools.py`) and pull private keys, entropy/mnemonics, and derived farmer/pool keys belonging to a keychain partition it was not provisioned to access. This is a confidentiality-only disclosure of secret key material (CWE-200), matching the reported CVSS vector `C:H/I:N/A:N` — no direct funds movement occurs from the read itself, but leaked mnemonics/private keys allow full compromise of the affected wallet, farmer, and pool keys.

### Likelihood Explanation
Requires the attacker to already have local daemon RPC connectivity (a valid client TLS certificate under the same daemon trust root), so it is not remotely exploitable over the network. However, once that local trust boundary is reached — which many locally co-located services, plugins, or lower-privileged local tools do reach in normal Chia deployments — exploitation requires only sending a `get_key`/`get_all_private_keys`/`get_key_for_fingerprint` command with a guessed or discovered `kc_user`/`kc_service` pair; no cryptographic material or additional secret is needed to select the partition.

### Recommendation
Bind the set of `kc_user`/`kc_service` values a given daemon connection is allowed to use to that connection's registered identity (e.g., the service name it registered as, or its TLS client certificate), and reject `get_keychain_for_request` lookups for any `kc_user`/`kc_service` pair the connection has not been explicitly authorized to use, instead of trusting the values embedded in the request body.

### Proof of Concept
1. Start a local Chia daemon with the default keychain populated with real wallet keys.
2. As a locally-connected websocket client (same trust boundary as any other Chia service — e.g., using `KeychainProxy` directly instead of the intended service), send:
```json
{"command": "get_all_private_keys", "data": {"kc_user": "some-other-service-user", "kc_service": "chia-testing-1.8.0"}, "destination": "daemon"}
```
3. `KeychainServer.get_keychain_for_request` (chia/daemon/keychain_server.py:154-172) creates/returns the `Keychain(user="some-other-service-user", service="chia-testing-1.8.0")` instance and `get_all_private_keys` (chia/daemon/keychain_server.py:317-326) returns that partition's private keys and entropy in the response, without ever checking whether the requesting connection is entitled to that user/service pair.
4. Repeat with different guessed `kc_user`/`kc_service` values (e.g. testing fixtures like `"testing-1.8.0"`/`"chia-testing-1.8.0"` shown in `chia/simulator/block_tools.py:494-496`) to enumerate and read keys from other partitions.

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

    async def get_all_private_keys(self, request: dict[str, Any]) -> dict[str, Any]:
        all_keys: list[dict[str, Any]] = []
        if self.get_keychain_for_request(request).is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private_keys = self.get_keychain_for_request(request).get_all_private_keys()
        for sk, entropy in private_keys:
            all_keys.append({"pk": bytes(sk.get_g1()).hex(), "entropy": entropy.hex()})

        return {"success": True, "private_keys": all_keys}

    async def get_key_for_fingerprint(self, request: dict[str, Any]) -> dict[str, Any]:
        keychain = self.get_keychain_for_request(request)
        if keychain.is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private = request.get("private", True)
        keys = keychain.get_keys(include_secrets=private)
        if len(keys) == 0:
            return {"success": False, "error": KEYCHAIN_ERR_NO_KEYS}

        try:
            if request["fingerprint"] is None:
                key_data = keys[0]
            else:
                key_data = keychain.get_key(request["fingerprint"], include_secrets=private)
        except KeychainFingerprintNotFound:
            return {"success": False, "error": KEYCHAIN_ERR_KEY_NOT_FOUND}

        return {
            "success": True,
            "pk": bytes(key_data.public_key).hex(),
            "entropy": key_data.entropy.hex() if private else None,
        }
```
