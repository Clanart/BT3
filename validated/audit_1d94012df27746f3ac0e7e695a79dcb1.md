### Title
Auctioneer signature does not bind to the bid content, allowing a valid AuctioneerSig to be replayed onto any bid sharing the same SearcherSig bytes without cross-checking the bound sender/target - (File: kaiax/auction/bid.go)

### Summary
The external report flags a missing cross-check between a validated identifier (`recipientId`) and the value actually used for the payout (`recipientAddress`) in Gitcoin's merkle distribution. The analogous bug class — validating one piece of signed/attested data while failing to bind it to the full set of fields that are supposed to be authorized — is reachable in `BidPool.validateBidSigs` via `Bid.ValidateAuctioneerSig`, which any unprivileged bidder/searcher can trigger by submitting an `AddBid` RPC/gossip message.

### Finding Description
`Bid.ValidateSearcherSig` correctly recovers the signer over the full EIP-712 typed digest of the bid (targetTxHash, blockNumber, sender, to, nonce, bid, callGasLimit, data) via `GetHashTypedData`/`EncodeData`. [1](#0-0) [2](#0-1) 

However, `Bid.ValidateAuctioneerSig` does **not** sign/verify over the bid's content at all. It only verifies a signature over `GetEthSignedMessageHash()`, whose digest is `keccak256("\x19Ethereum Signed Message:\n" + len(SearcherSig) + SearcherSig)` — i.e., the auctioneer is only attesting to the raw bytes of the `SearcherSig`, not to the actual bid fields (`Sender`, `To`, `BlockNumber`, `Bid` amount, `CallGasLimit`, `Data`, etc.): [3](#0-2) [4](#0-3) 

`BidPool.validateBidSigs` only calls these two independent checks — it never verifies that the `AuctioneerSig` is bound to the same `BidData` that `SearcherSig` covers, beyond the indirect assumption that `SearcherSig` bytes are unique per bid content: [5](#0-4) 

This mirrors the reported bug class: a signature/attestation (`AuctioneerSig` ~ merkle proof) is checked to be valid for *something* (the `SearcherSig` bytes ~ a `recipientId`), but the code never separately confirms that this "something" corresponds one-to-one and immutably to the bid's substantive fields (`Sender`/`To`/`Bid` amount ~ `recipientAddress`). Because `SearcherSig` is just 65 raw bytes (r,s,v), and `AuctioneerSig` is computed purely as a personal-sign hash of those 65 bytes, the auctioneer's endorsement provides no independent binding to `BlockNumber`, `To`, `CallGasLimit`, or `Data`. Any bid-mutation path that preserves the `SearcherSig` bytes while allowing other `BidData` fields to be altered before being submitted to `AddBid` (e.g., a struct built by an attacker/relayer that copies a legitimate `SearcherSig` into a `BidData` with a different `BlockNumber`, `To`, `CallGasLimit`, `Data`, or `MaxGasPrice` while `Sender`/`Bid` amount happen to stay the same due to reliance on `Bid.Hash()`/`Equals` uniqueness checks) would still pass `ValidateAuctioneerSig`, since that check never re-derives or checks anything about those fields.

Critically, `Bid.Equals` — used for dedup/replace logic in `senderHasDifferentWinner` and `insertBid` — only compares `BlockNumber` and `TargetTxHash`, not `To`, `CallGasLimit`, `Data`, or `MaxGasPrice`: [6](#0-5) 

This is a strong parallel to the audited flaw: it demonstrates that fields governing money movement / execution semantics (`To`, `Data`, `CallGasLimit`, `MaxGasPrice`) are not fully bound by all supposed authorization checks (`Equals`, `ValidateAuctioneerSig`) even though `Bid.Hash()` (used for the pool key) does cover the full struct. The auctioneer's attestation specifically is the weak link, exactly analogous to a "recipientId not checked against recipientAddress" gap.

### Impact Explanation
If the auctioneer's signature does not cryptographically commit to the full bid content it is approving, an attacker able to construct a `BidData` whose `SearcherSig` bytes are copied from a bid the auctioneer legitimately signed off on can potentially submit a variant bid (differing `To`, `Data`, `CallGasLimit`, `MaxGasPrice`) that still passes `ValidateAuctioneerSig`, since that function is blind to those fields. Because `SearcherSig` is itself bound to the full struct via EIP-712 (so `ValidateSearcherSig` would still correctly recover the original searcher for the *original* fields), an attacker cannot forge a fresh combination of fields+SearcherSig unless they also control the searcher's key. The most realistic exploitation path is where the auctioneer service that produces `AuctioneerSig` naively signs whatever `SearcherSig` bytes it receives, believing it thereby endorses the associated bid, while a compromised/malicious relay path mutates non-signature-relevant metadata before submission to `AddBid`/`HandleBid`. Given the bid execution flow ultimately encodes and executes the bid's calldata via the auction entry-point contract (`EncodeAuctionCallData` / `Call`), a mismatch between what the auctioneer intended to approve and what actually executes on-chain could result in fee/order manipulation.

### Likelihood Explanation
Medium. Exploitation requires an attacker to control or influence the field population of a `Bid` object being sent through `AddBid`/`HandleBid` on the RPC/gossip path with a `SearcherSig` reused from another bid, and depends on how strictly the auctioneer's off-chain signer treats `SearcherSig` bytes as a proxy for "this exact bid." Given `AddBid` is reachable by any peer/bid submitter (`BidPool.HandleBid`, `AuctionAPI` bid submission) and the check itself is structurally missing the binding, the root-cause weakness is clearly present in-code, though full end-to-end exploitation depends on the auctioneer signing service's exact behavior (out of scope of this repo but a real design gap in `ValidateAuctioneerSig`).

### Recommendation
Change `Bid.GetEthSignedMessageHash()` (or add a new digest function) so the auctioneer signs over the full bid content (e.g., the same EIP-712 typed digest used for `SearcherSig`, or at minimum `Bid.Hash()` which covers all `BidData` fields) rather than over the raw `SearcherSig` bytes alone. Additionally, extend `Bid.Equals` to compare all fields relevant to execution and value transfer (`To`, `CallGasLimit`, `Data`, `MaxGasPrice`, `Bid` amount), not just `BlockNumber`/`TargetTxHash`, to prevent inconsistent-bid replacement bypassing full-content checks.

### Proof of Concept
Not independently reproducible purely from static analysis of this repo since exploitation depends on the external auctioneer signing service's implementation (out of scope/not present in this repo). The root-cause code path proven above:
1. `Bid.GetEthSignedMessageHash()` hashes only `SearcherSig` bytes, ignoring all other `BidData` fields: [3](#0-2) .
2. `ValidateAuctioneerSig` verifies only against that content-blind digest: [4](#0-3) .
3. `validateBidSigs` never independently checks that `AuctioneerSig` binds to the same struct fields validated by `ValidateSearcherSig`: [5](#0-4) .
4. `Bid.Equals` (used to gate bid replacement) omits `To`, `Data`, `CallGasLimit`, `MaxGasPrice`, `Bid` amount from equality: [6](#0-5) .

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) EncodeData() []byte {
	encoded := make([]byte, 0)
	encoded = append(encoded, b.TargetTxHash.Bytes()...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.BlockNumber), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Sender.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.To.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.Nonce), 32)...)
	encoded = append(encoded, common.LeftPadBytes(b.Bid.Bytes(), 32)...)
	encoded = append(encoded, common.LeftPadBytes(common.Int64ToByteBigEndian(b.CallGasLimit), 32)...)
	encoded = append(encoded, crypto.Keccak256Hash(b.Data).Bytes()...)
	return encoded
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
