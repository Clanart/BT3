### Title
Integer-division truncation in NFT royalty calculation allows royalty amount to round down to zero, enabling offer settlement theft against NFT royalty recipients - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`NFTWallet.compute_royalty_amount` and `NFTWallet.royalty_calculation` compute the royalty owed to an NFT creator using floor (truncating) integer division: `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`. When the offered/requested fungible amount is small relative to `royalty_split` (the number of royalty-enabled NFTs bundled into one side of an offer) and the royalty `percentage`, the result truncates to `0`, exactly mirroring the DODO `getUserQuota` precision-loss pattern where dividing a small numerator by a large denominator/decimals collapses to zero. [1](#0-0) [2](#0-1) 

### Finding Description
`compute_royalty_amount(offered_amount, royalty_split, percentage)` performs `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS`, a chained truncating division. `royalty_calculation` performs the analogous `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`. The project's own test suite confirms this truncation-to-zero behavior is a known, reachable edge case: `test_small_amount_truncates_to_zero` shows `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` returns `0`. [3](#0-2) 

These values are used by `NFTWallet.make_nft1_offer` to build the actual on-chain royalty payment (`CreateCoin`) that is bundled into the offer's spend bundle and to decide the `trade_prices_list` passed into the ownership-layer `-10` (change owner) condition that the NFT's transfer program checks: [4](#0-3) [5](#0-4) [6](#0-5) 

Critically, when `royalty_split` (the count of royalty-bearing NFTs being requested/offered together in one offer) increases, or when the offered/requested amount per unit is small, the per-NFT royalty computed by this floor-division chain can be driven to zero even though the aggregate value exchanged is significant — an offer party can bundle many NFTs and/or split the fungible-amount side into small enough chunks so that `amount // royalty_split` (or the subsequent `* percentage // 10000`) truncates to `0` for every NFT, resulting in a `payment_sum == 0` and the royalty-payment `CreateCoin` step being skipped entirely (`if sum(p.amount for _, p in payments) == 0: continue`): [7](#0-6) 

Because this same code computes both the CAT/XCH payment amounts and the `trade_prices_list` percentage check used to decide whether a trade price is even included (`if price[0] * offered_royalty_percentages[asset] // MAX_ROYALTY_BASIS_POINTS != 0`), the truncation is self-consistent and no invariant/consensus check outside this software enforces a non-zero royalty. This is directly analogous to the DODO `D3UserQuota.quotaTokenAmount` bug: repeated/split small-value transactions each independently round to zero, allowing the aggregate obligation (royalty owed) to be avoided even though total value transferred is non-trivial.

### Impact Explanation
An offer creator (maker or a script directly constructing an offer/spend bundle, bypassing the wallet UI) can structure an NFT-for-fungible-asset offer with enough royalty-bearing NFTs bundled together (increasing `royalty_split`) or with a small enough per-unit amount that the computed royalty for one or more NFTs rounds to zero mojos, entirely avoiding payment to the NFT creator's `royalty_address`. Because there is no on-chain minimum-royalty enforcement independent of this wallet-side calculation, the royalty recipient permanently loses funds they were contractually/protocol-intended to receive — a form of offer-settlement value extraction at the expense of a third party (the royalty beneficiary), reachable by any unprivileged offer creator with no special permissions.

### Likelihood Explanation
Reachable by any wallet user or CLI/RPC caller constructing an NFT offer with `create_offer_for_ids` — no privileged access required. Exploitation requires deliberately choosing offer parameters (many NFTs bundled per offer side, or small enough fungible amounts) to force the truncation; this is a straightforward and repeatable manipulation of ordinary offer-creation inputs, not a rare edge case, though it primarily disadvantages the passive royalty beneficiary who does not participate in constructing the offer.

### Recommendation
Avoid chained truncating integer division for royalty computation. Compute royalty using a single division at the end (e.g., `(abs(offered_amount) * percentage) // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`) to reduce truncation-to-zero occurrences, and/or enforce a minimum non-zero royalty (or reject offers producing zero royalty when a non-zero percentage is configured) in `NFTWallet.make_nft1_offer` and `compute_royalty_amount`/`royalty_calculation`.

### Proof of Concept
Using the existing test as the minimal PoC: `test_small_amount_truncates_to_zero` in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py` demonstrates `compute_royalty_amount(offered_amount=-50, royalty_split=1, percentage=100)` (i.e., a 1% royalty on 50 mojos) returns `uint64(0)` instead of a fractional/rounded-up nonzero amount. Extending this to `make_nft1_offer` with multiple royalty-bearing NFTs bundled on one side of the offer (raising `royalty_split`) causes the per-NFT royalty share (and thus the total `payment_sum`) to hit `0`, at which point the code path that creates the royalty-payment coin is skipped: [8](#0-7) 

**Uncertainty note:** I was unable to locate the on-chain Chialisp source for the NFT royalty/transfer program (`NFT_TRANSFER_PROGRAM_DEFAULT` / ownership-layer puzzle) in the indexed portion of this repository, so I could not fully confirm whether the puzzle itself independently re-derives or enforces a minimum royalty amount at the consensus level, or whether it merely checks for consumption of announcements whose content is dictated entirely by the offer-maker's off-chain calculation (as the Python-side evidence strongly suggests). If the on-chain puzzle performs its own independent, non-truncating royalty check, the practical exploitability would be reduced. A Devin session with full repository/CLVM access would be needed to verify this definitively.

```python
MAX_ROYALTY_BASIS_POINTS = 10000


def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```

```python
                        "address": address,

                    }
                )

        return summary_dict
```
