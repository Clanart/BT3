### Title
SignableTransaction::new omits the OP_RETURN data output from the fee/weight calculation, producing underpriced transactions that fail relay - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` computes `needed_fee` and the funding sufficiency check from a weight estimate built only on `payments` and an optional change output, even though an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` has already been pushed into `tx_outs`. The result is a transaction whose actual fee (`sum(inputs) - sum(outputs)`) is lower than `fee_per_vbyte * actual_vbytes` — analogous to the Unitas `withdrawCollateral` flaw where an incorrectly computed required-amount expression causes an operation that should succeed to revert/fail. Here, a send that was asked to pay a given feerate silently pays less, and can fall under the minimum relay feerate, stalling the withdrawal/send (DoS).

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`), the OP_RETURN output is appended at lines 194–202, but the fee estimation at line 204 calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a dummy transaction whose `output` vector contains only `payments` (lines 85–94) plus an optional change output (lines 95–99). The `data` output is never included in the weight/vbytes used for `needed_fee`, `TooLowFee` (line 211), or `NotEnoughFunds` (line 215). The change-calculation at lines 225–234 also uses `calculate_weight_vbytes(..., payments, Some(&change))`, again excluding the data output.

Concretely, for `data` of length `n`, the real transaction is roughly `n + ~10` bytes heavier than estimated (OP_RETURN script plus output overhead), so the real vbytes exceed `vbytes`/`vbytes_with_change` by up to ~22 vbytes. The actual fee paid is `needed_fee` (or `fee_with_change`), which is `fee_per_vbyte * underestimated_vbytes`, giving an effective feerate strictly below the requested `fee_per_vbyte`.

The minimum-fee guard at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated against the underestimated vbytes, so a caller requesting exactly the minimum relay feerate with a large `data` payload produces a transaction paying below `DEFAULT_MIN_RELAY_TX_FEE` for its true size, which nodes will reject/not relay.

### Impact Explanation
Any send created through `SignableTransaction::new` with a `data` payload pays less than the intended feerate. At low requested feerates the transaction is non-standard/unrelayable (below minimum relay fee), producing a stuck send that must be reconstructed — a temporary but attacker/usage-triggered DoS identical in class to the reference finding (a required-amount expression computed with the wrong terms blocks an otherwise valid operation). At higher feerates the transaction simply confirms slower than priced. Additionally, when change exists, the change output value is computed against `fee_with_change` (which excludes the data output), so the change absorbs no correction — the shortfall goes entirely to an underpriced fee rather than reducing change.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()`. The severity depends on the requested feerate and data length: with `fee_per_vbyte` at or near the minimum relay rate and `data` approaching the 80-byte cap, the produced transaction falls under the relay floor and cannot be broadcast. `data` is a public parameter to `SignableTransaction::new`, so this is reachable by any integrator/user supplying OP_RETURN data; no privileged position is required.

### Recommendation
Include the data output in the weight estimate. Either pass `tx_outs` (or `payments` plus a synthetic OP_RETURN `TxOut`) into `calculate_weight_vbytes`, or add the serialized size of the OP_RETURN output to the computed weight before deriving `vbytes`. Apply the same fix to the change variant (`vbytes_with_change`) so `needed_fee`, the `TooLowFee` check, the `NotEnoughFunds` check, and the change value all account for the data output.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Line 194-202: the OP_RETURN output is added to the real transaction
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(...data up to 80 bytes...),
});

// Line 204: fee estimate only covers `payments` (+ optional change), NOT tx_outs
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;

// Scenario:
//   1 input, 1 payment, change = Some(..), data = 80 bytes
//   fee_per_vbyte = 1 (min relay rate)
//   estimated vbytes (no data output) = ~154 vB  -> needed_fee = 154
//   actual vbytes (with ~91-byte OP_RETURN output) = ~177 vB
//   actual fee paid = inputs - outputs = fee_with_change (~155)
//   effective feerate ~= 155/177 < 1 sat/vB -> below DEFAULT_MIN_RELAY_TX_FEE
//   -> bitcoind rejects the tx (min relay fee not met): send DoS,
//      even though NotEnoughFunds / TooLowFee checks passed.
```
