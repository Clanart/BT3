### Title
Unauthenticated cross-chain "sponsorship" lets any registered chain's buyer evict another app's already-paid bandwidth allowance - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` credits a byte allowance to the key `(app_chain, app)` taken entirely from the *payload* of an inbound purchase message, not from `request.source` — this is the documented "sponsorship" feature. The `Allowance` storage list for that key is a bounded FIFO (cap 1024) shared across every payer on every registered chain. Because eviction on overflow removes the oldest entry regardless of who paid for it, any account holding a `BandwidthManager` registration on *any* chain can direct low-cost purchases at a victim's `(app_chain, app)` key to force out that victim's real, already-paid, unconsumed allowance. This is the same broken invariant as the Axelar `TokenManager` bug: a balance/allowance is credited and mutated under an identity key (`app_chain`) that is disconnected from the authenticated origin of the request, letting an attacker use a cheap/arbitrary source to manipulate a resource pool that legitimately belongs to a different, unrelated party.

### Finding Description
`is_purchase_message` and `on_accept` authenticate only that `request.from` matches the `BandwidthManager` registered for `request.source`: [1](#0-0) 

But the actual storage key used to credit (and later drain) the allowance is `msg.chain` / `msg.app`, decoded straight from the purchaser-supplied ABI body, completely independent of `request.source`: [2](#0-1) 

This is intentional per the docs ("a buyer on Ethereum can credit an app on Base") — but the same trust boundary also permits any buyer on *any registered chain* to push into any victim's `(app_chain, app)` FIFO list. `push_subscription` enforces the 1024-entry cap by evicting the *oldest* entry, with no notion of "whose money paid for it": [3](#0-2) 

The gate itself (`try_consume`) also only sums/drains from this shared, unsegregated list: [4](#0-3) 

Because `Allowance` is keyed solely by `(StateMachine, AppKey)` with no per-payer partition or reservation, and any of potentially many registered `BandwidthManager` contracts can write into any victim's key via a genuine (but attacker-chosen, minimal-cost) purchase, an attacker can enqueue enough purchases to push the victim's real subscriptions off the front of the list before they are consumed.

### Impact Explanation
A victim app that legitimately purchased bandwidth (paying real fee tokens) can have that paid-for, unconsumed allowance evicted and lost (`SubscriptionEvicted { lost_bytes }`) by a third party who never interacted with the victim's own chain or manager. This is a loss-of-funds condition (the victim paid for bytes it will never get to use) triggered purely through the intended public `purchase()` entrypoint — no relayer, prover, admin, or governance compromise is required, and no malformed proof is needed since the attack uses fully valid ISMP messages from a legitimately registered manager.

### Likelihood Explanation
Medium. The attack requires the attacker to fund 1024 (or however many are needed to reach the cap and push past the victim's live entries) minimum-tier purchases from any one of the registered `BandwidthManager` chains. Cost scales with the cheapest configured tier price across all registered chains and is entirely attacker-controlled/timed (no race condition or front-running needed — it is a straightforward batch of purchase calls). It becomes cheaper as more low-fee chains are onboarded with `BandwidthManager` deployments, and it is guaranteed to succeed eventually since the cap is fixed at 1024 regardless of the target's queue depth.

### Recommendation
Partition the `Allowance` FIFO (or eviction policy) per payer/source chain, or reserve/weight eviction by the value/tier of the entry rather than pure insertion order, so that a low-value purchase from an unrelated payer cannot evict a higher-value, unconsumed subscription belonging to another payer. At minimum, track `paid_from` per subscription and refuse to evict entries whose remaining value exceeds the incoming purchase's value, or split the cap per source chain so no single chain's buyers can monopolize eviction pressure on a shared `(app_chain, app)` key.

### Proof of Concept
1. Governance registers `BandwidthManager` contracts on Chain X (attacker-affordable, low tier prices) and Chain Y (victim's normal chain) — both legitimately configured per `docs/content/developers/evm/bandwidth/configuration.mdx`.
2. Victim buys a large/expensive tier from Chain Y's manager targeting `app_chain = "EVM-<Y>"`, `app = victimApp`. This lands in `Allowance::<T>::get("EVM-<Y>", victimApp)` per `modules/pallets/bandwidth/src/lib.rs:467-486`.
3. Attacker, using only Chain X's `BandwidthManager` (a chain they have no other relationship to `victimApp` on), issues 1024 minimal-cost `purchase()` calls with `app = victimApp`, `chain = "EVM-<Y>"` (i.e., sponsoring the victim's exact key with junk 1-byte/1-month tiers).
4. Each purchase calls `on_accept` → `push_subscription` (`modules/pallets/bandwidth/src/lib.rs:404-437`), which appends to the same bounded list. Once the list is full, further pushes evict the oldest entry — eventually evicting the victim's real, still-unconsumed high-value subscription, emitting `SubscriptionEvicted { lost_bytes }`.
5. Victim's app now fails `BandwidthGate::try_consume` (`GateError::NoAllowance` / `Insufficient`) despite having paid for the bytes, and must re-purchase — the attacker griefs it at will using an unrelated chain's manager, for the cost of 1024 cheap purchases instead of matching the victim's actual spend.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
