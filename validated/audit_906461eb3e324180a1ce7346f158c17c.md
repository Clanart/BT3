## Analysis

The `VaultBooster` bug class is: **irreversible state changes committed even though the operation ultimately reports failure**, leaving assets duplicated/orphaned because there is no atomicity between the "accept funds" step and the "validate/complete" step.

The Cosmos EVM analog is in the `x/erc20` IBC middleware `OnRecvPacket` flow, which auto-converts a received IBC/native-ERC20 Cosmos coin into its ERC20 representation *after* the underlying ICS-20 transfer has already unescrowed/minted the coin to the receiver's bank balance, on the **same, non-cached** `sdk.Context`: [1](#0-0) [2](#0-1) 

`im.Module.OnRecvPacket` invokes the real transfer app, which performs the coin unescrow/mint directly on `ctx` (not a cached context). Only afterward does `erc20.Keeper.OnRecvPacket` attempt the ERC20 conversion: [3](#0-2) 

If `MintingEnabled`/`ConvertCoinNativeERC20` fails (e.g., `SendEnabled=false` for the token, or another EVM/bank error), the middleware returns an **error acknowledgement**. Per ICS-20 semantics, an error acknowledgement causes the *sending* chain to refund/re-credit the original sender. However, the bank-side unescrow/mint that already happened on the *receiving* chain (this chain) during the underlying transfer step is **not rolled back** — there is no `CacheContext`/`writeFn` pattern wrapping the combined "transfer + convert" operation.

This exact behavior is acknowledged in the integration test suite itself: [4](#0-3) 

The comment `"SendEnabled=false will cause the conversion of bank tokens to erc20 tokens to fail, but not send them back to escrow"` confirms that the bank-side transfer (unescrow to receiver) is left in place while the acknowledgement returned is a failure.

### Why this matches the Critical impact gate
- On the receiving chain (here), the receiver keeps the unescrowed/minted Cosmos coin balance because that mutation was already committed before the conversion step failed.
- Since the acknowledgement is an error, the sending chain's `OnAcknowledgementPacket`/timeout path will refund the original sender (release escrow or re-mint voucher) there, believing the transfer never completed.
- Net effect: the same value now exists twice — once as a refund on the sending chain, once as spendable bank/erc20-representable balance on the receiving chain — an unauthorized duplication of spendable, escrow-backed value, which is exactly the pattern the required Critical impact list calls out ("duplication ... of spendable user value across ... IBC escrows ... token-pair-backed balances").

This needs to be verified against the full IBC-Go core `RecvPacket` handling (whether the core channel keeper independently reverts state on a failed ack — it does not; only a panicking handler causes a full revert, an explicit error acknowledgement return value is a valid, committed result) and confirmed with an end-to-end IBC relay test (not just direct `OnRecvPacket` invocation as in the existing unit test) to prove the sending-chain refund actually occurs concurrently with the receiving-chain balance being retained. Given the index limitations here (this is inferred from the exposed integration test and middleware code, not a full end-to-end relay trace), I'd recommend a Devin agent reproduce this with a live two-chain IBC testing setup to nail down the exact double-credit before finalizing severity, since the fix (wrapping the whole `Module.OnRecvPacket` + `keeper.OnRecvPacket` sequence in a `CacheContext`/`writeFn` that only commits on success) is well-defined but the precise duplication amount and conditions (which token types: native-ERC20 pairs vs. IBC vouchers, `SendEnabled` toggles vs. EVM call failures, self-destructed contracts, etc.) needs confirmation.

	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
