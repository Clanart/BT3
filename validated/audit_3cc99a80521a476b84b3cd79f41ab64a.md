### Title
Webhook HMAC verification does not bind the shop domain, allowing cross-shop webhook forgery via header spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates the HMAC over the raw request body [1](#0-0) , using `PayloadVerification#hmac_valid?`, which computes the digest exclusively from `data` (the body) and the app's shared secret [2](#0-1) . The `X-Shopify-Shop-Domain` header, which downstream code trusts as the authoritative shop identity for the webhook, is never included in the signed material [3](#0-2) . This mirrors the report's root cause pattern: a check that passes ("signature valid") does not actually prove what the caller assumes it proves ("this event is for shop X"), enabling a class of false-positive acceptance.

### Finding Description
The webhook pipeline works as follows:
1. `WebhooksController`/generated controllers include `ShopifyApp::WebhookVerification`, whose `before_action :verify_request` calls `hmac_valid?(request.raw_post)` [4](#0-3) [1](#0-0) .
2. `hmac_valid?` recomputes `HMAC-SHA256(secret, body)` and compares it to the `X-Shopify-Hmac-Sha256` header using `secure_compare` [2](#0-1) . Note it accepts either the current `secret` or `old_secret` [5](#0-4) , but critically the digest input is only `data` = the body — headers, including shop domain, are never part of the signed payload.
3. After verification passes, the controller (or generated equivalents) builds `ShopifyAPI::Webhooks::Request.new(raw_body: ..., headers: request.headers.to_h)` and enqueues a job using `webhook_request.shop` — derived from the unsigned `X-Shopify-Shop-Domain` header — as the trusted shop identity [6](#0-5) .
4. The generated jobs then look up the local `Shop` record purely by that `shop_domain` value and open a live Shopify API session for it: `shop = Shop.find_by(shopify_domain: shop_domain) ... shop.with_shopify_session do |session| ... end` [7](#0-6) , and the same pattern repeats in the mandatory privacy webhook jobs (`customers/data_request`, `customers/redact`, `shop/redact`) [8](#0-7) [9](#0-8) .

Because the app's client secret is shared across every merchant that installs the app (it is not shop-specific), any merchant who installs the app receives their own genuine webhook deliveries — real `(body, X-Shopify-Hmac-Sha256)` pairs signed with that shared secret. Since the shop-domain header is not covered by the signature, that merchant (an "unrelated merchant" relative to any other installed shop) can replay their own validly-signed webhook body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary target shop's domain. `hmac_valid?` still returns true, because it never inspected the header. The downstream job then loads a session for, and takes destructive action against, the victim shop `Shop.find_by(shopify_domain: forged_domain)` while operating on attacker-supplied webhook body content.

The test suite explicitly documents that only the body is signed and the shop-domain header is set independently: the HMAC is computed only over `"{}"`, and `x-shopify-shop-domain` is a separate, unsigned header [10](#0-9) .

### Impact Explanation
An attacker who is a legitimate (but unrelated) installed merchant can forge webhook events attributed to a victim shop that has also installed the app. Depending on which webhook/job is targeted, this enables: cross-shop data confusion/injection into a victim's records (e.g. `carts/update`-style jobs), or triggering the mandatory privacy webhook jobs (`shop/redact`, `customers/redact`, `customers/data_request`) against an arbitrary victim shop domain with attacker-controlled body content, causing operations to run under `shop.with_shopify_session` using the victim's real access token. This is a cross-shop access/integrity issue rooted in an incomplete signature check, directly analogous to the reported bug class where a "valid" check does not actually validate what the caller assumes.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own store (a normal, unprivileged, publicly-available action for any Shopify merchant) to obtain a genuine `(body, HMAC)` pair, and then send a crafted HTTP POST to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret material or elevated access is required, and the verification code as written performs no binding between the signed body and the shop-identity header.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header as an authenticated value on its own. Either derive shop identity exclusively from data that is itself covered by the HMAC (e.g., embed/validate the shop identifier that Shopify includes inside the signed body payload, cross-checked against the header), or track/verify webhook idempotency (`webhook_id`) plus explicit ownership records so that a replayed/relabeled webhook cannot be attributed to a shop it did not originate from. At minimum, jobs like the privacy/redact jobs and any state-mutating webhook handlers should independently verify that the resource identifiers in the webhook body are actually associated with `shop_domain` before acting.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
2. Attacker replays: `POST /webhooks/orders_create` with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `WebhookVerification#verify_request` → `hmac_valid?(B)` recomputes `HMAC-SHA256(secret, B)` and matches `H` [2](#0-1)  — request passes verification.
4. Controller extracts `webhook_request.shop` = `victim.myshopify.com` from the unsigned header and enqueues the job accordingly [6](#0-5) .
5. Job resolves `Shop.find_by(shopify_domain: "victim.myshopify.com")` and executes `shop.with_shopify_session` using the victim's stored access token while processing attacker-supplied body `B` [11](#0-10) .

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
