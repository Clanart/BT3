## Title
Cross-Origin Redirect Re-Injects Authorization Token After Same-Origin Sanitization — ([File: app/src/main-process/authenticated-image-filter.ts])

### Summary
GitHub Desktop installs two `webRequest` filters on the shared `session.defaultSession`: `installSameOriginFilter`, which strips `Authorization`/`Cookie` headers when a request is redirected to a different origin than it started at, and `installAuthenticatedImageFilter`, which *adds* an `Authorization: token <token>` header to any request whose current URL origin matches a signed-in account and whose path looks like a GitHub asset/avatar URL. Both filters are registered on the same `OrderedWebRequest.onBeforeSendHeaders` pipeline, with the same-origin filter registered first and the image filter registered second.

Because listeners run in registration order and each one operates only on the *current* leg of a request, the same-origin filter's origin-mismatch check does not stop the image filter from unconditionally adding a fresh `Authorization` header once a redirect chain lands on a URL whose origin/path match its criteria — even if the redirect originated from an attacker-controlled, cross-origin URL. This defeats the entire purpose of the same-origin filter for headers that get added *after* it runs.

### Finding Description
`installSameOriginFilter` remembers the origin of the very first request for a given `details.id` and, on every subsequent redirect leg, strips `authorization`, `authentication`, and `cookie` headers if the current origin differs from that initial origin: [1](#0-0) [2](#0-1) 

`installAuthenticatedImageFilter` independently attaches an `Authorization: token <token>` header to any request whose *current* URL origin is a known signed-in account origin and whose path matches a GitHub asset/avatar pattern: [3](#0-2) 

Both filters are attached to the same `OrderedWebRequest` instance: [4](#0-3) 

`OrderedWebRequest.onBeforeSendHeaders` invokes listeners strictly in registration order, feeding each listener's output headers into the next: [5](#0-4) 

Because `installSameOriginFilter` is registered before `installAuthenticatedImageFilter`, the sanitization step runs *first* and the token-injection step runs *second*, on the same redirected request. The image filter has no knowledge of the request's original origin (only `same-origin-filter.ts` tracks `requestOrigin`), so it will happily attach a fresh `Authorization` header to a request that arrived at a `github.com`/GHE asset path via a redirect from an arbitrary, attacker-controlled origin.

The reachable attacker-controlled entry point is markdown rendering of GitHub API objects (PR bodies, PR/issue comments) inside `SandboxedMarkdown`, which sanitizes HTML with DOMPurify but does not strip `<img>`/`src` and explicitly wires up `img` load listeners, meaning attacker-supplied remote image URLs are fetched by the renderer: [6](#0-5) [7](#0-6) 
This markdown is used to render pull request bodies and pull request/issue comments (attacker-controlled GitHub API content) directly in the app: [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who can get a PR/issue body or comment rendered in Desktop (i.e., any user who can open a PR/issue or comment on one that the victim views) can embed an `<img src="https://attacker.example/x">` that 302-redirects to a `github.com`/GHE URL matching `isGitHubRepoAssetPath`/`isEnterpriseAvatarPath` (e.g. `https://github.com/<owner>/<repo>/assets/<id>/<guid>` or `/user-attachments/assets/<guid>`). The initial request goes to the attacker's origin unauthenticated (no token attached, since the origin isn't a known account origin), but once redirected to the matching GitHub origin/path, `installAuthenticatedImageFilter` attaches the signed-in user's real GitHub token — bypassing the very protection `installSameOriginFilter` exists to provide. This lets an attacker use the victim's authenticated Desktop session as a confused deputy to fetch/disclose asset content the victim can access but the attacker cannot directly enumerate/prove access to, entirely outside the attacker's own repository or authorization scope, all triggered simply by the victim viewing normal GitHub content (PR/issue/comment) in Desktop.

### Likelihood Explanation
No special local access, admin rights, or social engineering beyond normal use of Desktop (viewing a PR/issue) is required. The only prerequisite is that the victim is signed in and views a PR/issue/comment authored or influenced by the attacker — a standard, low-friction interaction for any public/shared repository. The attacker fully controls the initial redirecting host and the final asset path chosen; the only variable outside their control is that the redirect must land on a URL pattern matching the fairly permissive regexes in `authenticated-image-filter.ts`, which is easy to satisfy.

### Recommendation
Make `installAuthenticatedImageFilter` origin/redirect-aware: track (like `installSameOriginFilter` does) whether the *current* request is part of a redirect chain that began at a different, non-GitHub origin, and refuse to attach the `Authorization` header in that case. Alternatively, merge the two filters into a single ordered check so that authorization-header injection only happens for requests whose entire redirect chain originated at a trusted GitHub origin, and reorder/consolidate logic so sanitization is always the last step applied before headers are sent.

### Proof of Concept
1. As an attacker, open a PR or comment on an issue/PR in a repository the victim will view in GitHub Desktop, with a body containing:
   `<img src="https://attacker.example/redirect">`
2. Host `https://attacker.example/redirect` to respond with `302 Found` and `Location: https://github.com/<any-owner>/<any-repo>/assets/<id>/<guid>` (or a known `/user-attachments/assets/<guid>` URL).
3. When the victim, signed in to GitHub Desktop, views this PR/issue/comment (rendered via `SandboxedMarkdown`), the iframe loads the `<img>`, which is fetched by Electron's `session.defaultSession`.
4. `installSameOriginFilter` strips any (nonexistent) auth headers on the redirect to `github.com`, but `installAuthenticatedImageFilter`, running afterward in the same `onBeforeSendHeaders` chain, then attaches `Authorization: token <victim's real GitHub token>` to the redirected request because its origin (`github.com`) and path match its allow-list — regardless of the fact that the request chain began at `attacker.example`.

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })

      webRequest.onBeforeSendHeaders.bind(webRequest),
      async (listeners, initialDetails) => {
        let details = initialDetails
        let response: BeforeSendResponse = {}

        for (const listener of listeners) {
          response = await listener(details)
          if (response.cancel === true) {
            break
          }

          if (response.requestHeaders !== undefined) {
            // I have no idea why there's a discrepancy of types here.
            // details.requestHeaders is a Record<string, string> but
