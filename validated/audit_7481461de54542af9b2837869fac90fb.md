### Title
Just-in-time stake/harvest/withdraw allows theft of accrued WOM/bonus rewards from legitimate stakers - ([File: rewards/BaseRewardPool.sol], [File: rewards/BaseRewardPoolV2.sol], [File: wombat/WombatStaking.sol], [File: wombat/WombatPoolHelper.sol])

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` compute dividend-style reward accrual (`rewardPerTokenStored`) using the **instantaneous** `totalStaked()`/`balanceOf()` at the moment a reward is injected, with no time-weighting, checkpointing, or lock. Since staking (`deposit`), unstaking (`withdraw`), and reward harvesting (`harvest`) are all permissionless and executable back-to-back with no cooldown, any wallet can front-run a reward injection with a large stake, capture a full proportional share of rewards that accrued to other users over time, and withdraw immediately — the same "incorrect dividends calculation" root cause as the BankrollNetwork exploit (dividends computed off a manipulable instantaneous balance/totalSupply).

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` and `BaseRewardPoolV2.sol` updates the global reward index as:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
``` [1](#0-0) 

`totalStaked()` and `balanceOf()` simply read the live balance from `MasterMagpie`, with no snapshot/vesting mechanism: [2](#0-1) 

Any address holding a balance the instant this index is updated is credited a share of the newly-added reward proportional to its **current** balance, regardless of how long it has been staked, because `earned()`/`_earned()` only compare `rewardPerTokenStored` against the user's last-paid checkpoint: [3](#0-2) 

Reward injection for the main WOM/bonus rewarder is triggered via `queueNewRewards`, called from `WombatStaking._toMasterWomAndSendReward`, itself reachable from the fully permissionless `harvest()` entrypoint on the pool helper: [4](#0-3) [5](#0-4) 

Staking and unstaking through `MasterMagpie` have no lock/cooldown — `deposit`/`withdraw` are plain external functions that immediately update `user.amount`/`user.available` and transfer tokens: [6](#0-5) [7](#0-6) 

Depositing/withdrawing LP through the pool helper is likewise unrestricted and immediate: [8](#0-7) 

Because `deposit()`/`harvest()`/`withdraw()` can all be composed by an ordinary wallet (optionally using a flash-loaned or self-funded large LP position) in the same transaction, or across consecutive transactions in the same block, an attacker can:
1. Stake a large amount of LP receipt tokens into `MasterMagpie` via the pool helper (inflating `totalStaked()`).
2. Call the permissionless `harvest()` to force `WombatStaking` to pull pending WOM emissions from the underlying Wombat protocol and inject them into `BaseRewardPool` via `queueNewRewards`, which divides the harvested reward by the now-inflated `totalStaked()` and credits the attacker's freshly-staked balance a full proportional share of rewards that accrued to other users over the elapsed emission period.
3. Immediately withdraw, harvesting the credited reward and removing the stake in the same block.

This is directly analogous to the BankrollNetwork bug class: dividends/rewards computed from a balance/totalSupply value that can be manipulated by depositing right before distribution and withdrawing right after, letting an attacker siphon yield that rightfully belongs to long-term participants.

### Impact Explanation
This results in theft of unclaimed yield belonging to legitimate long-term stakers of any Wombat pool integrated with `MasterMagpie`/`BaseRewardPool` (WOM and bonus/bribe tokens). Each JIT cycle dilutes/misappropriates a portion of the reward pool proportional to the attacker's temporary stake size, which can be scaled arbitrarily large (e.g., via flash-loaned LP/deposit tokens), enabling repeated extraction of protocol yield without bearing any real economic exposure or holding period.

### Likelihood Explanation
High: all steps (`deposit`/`depositLP`, `harvest`, `withdraw`) are unauthenticated, callable by any EOA/contract, require no special role, and are already designed to be composable in a single transaction (the pool helper's own `withdraw()` explicitly triggers harvesting as part of unstaking). No cooldown, vesting, or minimum holding period exists anywhere in the deposit/withdraw/harvest path to prevent this sandwiching.

### Recommendation
Introduce time-weighted or checkpointed reward accounting (e.g., snapshot balances before/after harvest windows, or a minimum stake duration before rewards accrue), and/or restrict `harvest()` to be triggerable atomically with, rather than independently of, deposits — e.g., disallow crediting new stake with rewards accrued before the deposit's block, and add a cooldown between deposit and withdrawal for a given account within a pool.

### Proof of Concept
Conceptual sequence (single transaction, optionally flash-loan funded):
1. `WombatPoolHelper.depositLP(largeAmount)` → mints receipt tokens and stakes them into `MasterMagpie`, inflating `totalStaked()` for the pool's `BaseRewardPool`. [9](#0-8) 
2. `WombatPoolHelper.harvest()` → `WombatStaking.harvest(lpToken)` → `_toMasterWomAndSendReward` → `BaseRewardPool.queueNewRewards` divides the harvested WOM reward by the inflated `totalStaked()`, crediting attacker's balance a full proportional share instantly. [4](#0-3) 
3. `WombatPoolHelper.withdraw(largeAmount, minAmount)` → `MasterMagpie.withdraw` triggers `_harvestAndUnstake`, paying out the attacker's credited reward share before returning the staked capital. [10](#0-9) 
4. Repay flash loan (if used); net gain = disproportionate reward share taken from long-term stakers.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
