## Title
`_abortSquashMerge` commits the squash-merge before the rollback step, and silently leaves it committed if the rollback fails - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The `record_external_operation` bug in rust-evm is a case where a state-committing action is performed, a subsequent step that can fail is executed afterward, and if that later step fails the caller is told the whole operation failed even though the earlier commit was never rolled back. The same "commit-then-maybe-fail-silently" pattern exists in GitHub Desktop's squash-merge abort flow: aborting a conflicted `--squash` merge actually creates a real commit first, and only *afterwards* attempts to undo it with `git reset --hard`. If that reset fails, Desktop swallows the error and leaves the squash commit permanently applied to the branch, even though the user asked to abort it.

### Finding Description
`_abortSquashMerge` is the implementation behind the "Abort" button shown to users resolving conflicts during a squash merge: [1](#0-0) 

The sequence is:
1. `_finishConflictedMerge` is called, which runs `createMergeCommit(...)` — this is a real `git commit`, i.e. it **advances HEAD and writes a new commit object**, exactly the kind of "substate commit" described in the rust-evm advisory. The code comment even confirms this is done *specifically* to clear `SQUASH_MSG`, not because the user wants to commit: `"By committing, we clear out the SQUASH_MSG..."` [2](#0-1) 
2. Only after that commit has succeeded does the code attempt to reverse it via `reset(repository, GitResetMode.Hard, tip.branch.tip.sha)`, using a `tip` value that was read from the state cache *before* the abort began (the comment explicitly says "we have not reloaded the status, this tip is the tip before the squash commit above") [3](#0-2) .
3. That reset is wrapped in `gitStore.performFailableOperation`, whose contract is: on error, emit it and return `undefined` — the function does **not** propagate a failure signal to its own return value or caller [4](#0-3) . `_abortSquashMerge`'s return value is `void`, so there is no way for the dispatcher to know the rollback failed.

The `Dispatcher` entry point calls this and unconditionally refreshes the repository, regardless of whether the reset succeeded: [5](#0-4) 

The UI code that invokes "Abort" (in `Merge.onAbort`) also does not check any result — it fires the abort and immediately ends the multi-commit-operation flow, presenting the operation as done: [6](#0-5) 

So the invariant that is broken is: **"Abort" must guarantee the repository returns to its pre-squash-merge state, or the user must be told it did not.** Instead, the commit (step 1) is unconditionally applied first, and the undo (step 2) is best-effort with silent failure semantics identical to the rust-evm bug: an error in the second, corrective operation is not surfaced as "the whole abort failed with your commit still in place" — it just logs to a background error/log channel while the UI marches on to "flow ended" / refreshed state.

### Impact Explanation
If `reset --hard` fails for any reason after the squash commit has already been created — e.g. the target SHA object is missing locally (shallow clone/partial fetch), the working tree contains files that make a hard reset fail, a `core.hooksPath`/hook rejects the operation, or the ref/lock is otherwise unavailable — the just-created squash-merge commit remains the tip of the user's branch. The user believes they clicked "Abort" and that the merge was discarded, but their branch now silently contains a real commit including whatever content came from the (potentially attacker-controlled) source branch/repository that was being squash-merged. If the user subsequently commits/pushes without noticing (the flow closes the dialog and shows the normal Changes view), this is a silent corruption of what the user commits and pushes — squarely in the accepted impact category ("silent corruption of what the user commits or pushes").

### Likelihood Explanation
This requires an unusual combination: performing a squash merge that produces conflicts, and then having the subsequent `git reset --hard` specifically fail (rather than the initial merge/commit). Conditions that make this more plausible in an attacker-influenced scenario include shallow/partial clones, an intervening background refresh mutating cached `tip` state right before abort, or the source branch/remote engineering repository state that causes the reset target to be stale or unreachable. It is not a trivially triggerable, one-click bug, so likelihood is moderate/low, but the code path and silent-failure contract genuinely exist as shown above — this isn't hypothetical, it's the exact commit-then-rollback-may-silently-fail shape of the reported CVE class.

### Recommendation
- Do not treat the squash-commit-then-reset sequence as fire-and-forget. Check the return value of `gitStore.performFailableOperation(() => reset(...))` in `_abortSquashMerge`, and if it is `undefined` (failed), surface an explicit, blocking error to the user stating that the abort did not complete and the squash commit is still present, rather than silently continuing to refresh/close the flow.
- Re-fetch `tip` right before computing the reset target rather than relying on the pre-commit cached `branchesState.tip`, since the comment already acknowledges this data can be stale.
- Consider avoiding the "commit-then-reset" trick entirely in favor of an approach that doesn't require creating a real commit merely to clear `SQUASH_MSG` (e.g., manually removing the `SQUASH_MSG`/`MERGE_MSG` files if git doesn't provide an escape hatch), which would remove the unsafe intermediate committed state altogether.

### Proof of Concept
1. Start a squash merge (`git merge --squash <branch>`) via Desktop against a branch that produces a conflict.
2. In the conflict resolution UI, click "Abort" (`Merge.onAbort` → `dispatcher.abortSquashMerge` → `AppStore._abortSquashMerge`).
3. `_finishConflictedMerge` succeeds and creates a real commit finalizing the squash merge onto the current branch tip.
4. Before/at the `reset(repository, GitResetMode.Hard, tip.branch.tip.sha)` call, cause the reset to fail — for example by having the target SHA unavailable locally (e.g. the repository was fetched with `--depth 1` or the object was pruned), or by locking `.git/index` externally at that moment.
5. Observe that `performFailableOperation` logs the error but returns `undefined`; `_abortSquashMerge` returns normally; `dispatcher.abortSquashMerge` proceeds to `_refreshRepository`; the UI flow ends as if abort succeeded.
6. Inspect `git log` on the branch: the squash-merge commit from step 3 is still present as HEAD, despite the user having clicked "Abort".

  /** This shouldn't be called directly. See `Dispatcher`. */
  public async _abortSquashMerge(repository: Repository): Promise<void> {
    const gitStore = this.gitStoreCache.get(repository)
    const {
      branchesState,
      changesState: { workingDirectory },
    } = this.repositoryStateCache.get(repository)

    const commitResult = await this._finishConflictedMerge(
      repository,
      workingDirectory,
      new Map<string, ManualConflictResolution>()
    )

    // By committing, we clear out the SQUASH_MSG (and anything else git would
    // choose to store for the --squash merge operation)
    if (commitResult === undefined) {
      log.error(
        `[_abortSquashMerge] - Could not abort squash merge - commiting squash msg failed`
      )
      return
    }

    // Since we have not reloaded the status, this tip is the tip before the
    // squash commit above.
    const { tip } = branchesState
    if (tip.kind !== TipState.Valid) {
      log.error(
        `[_abortSquashMerge] - Could not abort squash merge - tip was invalid`
      )
      return
    }

    await gitStore.performFailableOperation(() =>
      reset(repository, GitResetMode.Hard, tip.branch.tip.sha)
    )
  }
```

  public async performFailableOperation<T>(
    fn: () => Promise<T>,
    errorMetadata?: IErrorMetadata
  ): Promise<T | undefined> {
    try {
      const result = await fn()
      return result
    } catch (e) {
      e = new ErrorWithMetadata(e, {
        repository: this.repository,
        ...errorMetadata,
      })

      this.emitError(e)
      return undefined
    }
  }
```
