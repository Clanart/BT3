### Title
Coinbase outputs to a multisig address are reported as spendable inputs, denying transaction publication - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is a permissionless party forcing the protocol into a failed/emergency state by performing an action before the protocol expects it (as in `LaunchEvent.createPair` being denied by a pre-created pool). In `bitcoin-serai`, `Scanner::scan_block` scans `block.txdata` including the coinbase transaction, and emits matching outputs as ordinary `ReceivedOutput`s with no maturity tracking. Any miner (a permissionless actor) can pay a coinbase output to a Serai multisig's registered p2tr script. That output is unspendable for 100 blocks by consensus, yet the scanner reports it as a received, spendable input.

### Finding Description
`Scanner::scan_block` iterates over every transaction in the block, including `block.txdata[0]` (the coinbase), and the inline documentation concedes the hazard: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs." No maturity marker is stored on `ReceivedOutput` — it carries only `offset`, `output`, and `outpoint`, so downstream code cannot distinguish a coinbase output from a normal one. [1](#0-0) [2](#0-1) 

The processor-side scanner pushes every output returned by `get_outputs` whose value meets `N::DUST` into the `outputs` vec that is emitted to the rest of the processor as received funds — there is no coinbase or maturity check. [3](#0-2) 

Once such an output is included as an input to a `SignableTransaction`, the signed transaction is consensus-invalid for 100 blocks. On the Bitcoin path, any publish failure that is not a `ConnectionError` is fatal: `publish_completion` calls `panic!("failed to publish TX ...")` on other RPC errors, which kills the signer task — the exact "emergency state" outcome of the original finding. [4](#0-3) 

### Impact Explanation
Funds are reported received that are not (yet) spendable, and any plan that draws the immature output as an input produces a transaction the network rejects. Because the publish path panics rather than retrying or dropping the input, a single crafted coinbase output stalls signing/processing for the affected multisig until restart and/or manual intervention — a denial of service reachable entirely with public on-chain data (a Bitcoin transaction the attacker causes to exist), matching the "operation denied → emergency state" shape of the Trader Joe finding.

### Likelihood Explanation
Requires the attacker to mine a block with a coinbase paying the multisig's external or offset address — permissionless but expensive, and the griefing value (stalled processor) must justify the cost. The scanner otherwise gives the attacker nothing to extract, so this is a pure-DoS griefing vector: Medium, consistent with the source severity.

Caveat: I verified that `scan_block` includes the coinbase and that the emitted `ReceivedOutput` carries no maturity flag, but I could not fully confirm the processor's `get_outputs` implementation calls `scan_block` without filtering `txdata[0]`, since the relevant Bitcoin-side `get_outputs` body was not fully inspected. If it already calls `scan_transaction` on `block.txdata[1 ..]` or filters by maturity, the issue does not reproduce.

### Recommendation
Tag `ReceivedOutput`s produced from `block.txdata[0]` (or have `scan_block` skip the coinbase and only expose it via an opt-in path), and have the processor exclude immature coinbase outputs from plan inputs until `confirmations >= 100`. Additionally, `publish_completion` should distinguish "immature/dropped" from "double-spent/invalid" instead of panicking on non-connection errors.

### Proof of Concept
1. A Serai Bitcoin multisig registers key `K`; `Scanner::new(K)` registers `p2tr_script_buf(K)`.
2. A miner builds a block whose coinbase has an output with `script_pubkey = p2tr_script_buf(K)` and value ≥ `N::DUST` (10,000 sats).
3. The processor's scanner calls `scan_block`, which iterates `block.txdata` including the coinbase; `scan_transaction` matches the script and emits a `ReceivedOutput` whose outpoint references the coinbase.
4. The processor accepts it as a normal received output and later includes it as an input to a `SignableTransaction`.
5. Every publish attempt for the next 100 blocks fails consensus validation (`bad-txns-premature-spend-of-coinbase`), hitting the `panic!` in `publish_completion` and halting the signing pipeline — the multisig's operations are denied until manual recovery. [5](#0-4) [6](#0-5)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
