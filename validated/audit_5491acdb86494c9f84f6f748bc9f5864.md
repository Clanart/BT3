### Title
`Scanner::scan_block` counts immature coinbase outputs as received, reporting unspendable funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` scans every transaction in a block — including `block.txdata[0]`, the coinbase transaction — and returns any matching outputs as indistinguishable `ReceivedOutput`s. A `ReceivedOutput` carries only `offset`, `output`, and `outpoint`; it has no maturity/freshness marker. Bitcoin consensus (BIP-30/BIP-34 rules, `COINBASE_MATURITY = 100`) forbids spending a coinbase output for 100 blocks. So the scanner's "received" accounting is inconsistent with the actual spendable constraint: it fails to subtract the still-locked (immature) coinbase amount, exactly the bug class of a limit/balance check omitting a term (here, "emitted-but-locked" rather than "emitted"). ### Finding Description
- `scan_transaction` returns a `ReceivedOutput` for any output whose `script_pubkey` is in `self.scripts` (mod.rs:199–214). Matching is purely on `script_pubkey`; nothing about the funding transaction is recorded.
- `scan_block` iterates `block.txdata` unconditionally, including index 0, the coinbase (mod.rs:221–227).
- `ReceivedOutput` exposes `offset`, `output`, `outpoint`, `value` only (mod.rs:89–118). Once returned, an immature coinbase output is indistinguishable from a spendable one.
- Downstream, `SignableTransaction::new` accepts `Vec<ReceivedOutput>` and will happily construct a spend over an immature outpoint: the `NotEnoughFunds` check at send.rs:215 and the signature machines treat every input as spendable. `multisig()` (send.rs:273–285) only verifies the script_pubkey ↔ offset correspondence, not maturity.
- An unprivileged party can trigger this: any miner can direct a coinbase payout to the vault's P2TR script (the script is public/derivable from the group key), and any observer can feed the resulting block to `scan_block`.

### Impact Explanation
The vault/processor accounting derived from `scan_block` over-counts spendable balance by the value of immature coinbase outputs. If the coordinator builds a `SignableTransaction` spending such an output, the produced transaction is consensus-invalid (coinbase spend before maturity) and will be rejected by the network — a stall in the signing/broadcast pipeline, or worse, signed transactions that can never confirm while their inputs are reported consumed. The "funds reported received that are not spendable" acceptance criterion is met: the scanner reports value as immediately available that the network will refuse to spend for up to 100 blocks.

The doc comment on `scan_block` (mod.rs:216–220) acknowledges the issue ("a post-processing pass is needed"), but `ReceivedOutput` provides no field to perform that post-processing correctly — the only signal is `outpoint.txid`, forcing callers to re-fetch the funding transaction to check coinbase status. The inconsistency therefore lives in the in-scope API, not just in integrator misuse.

### Likelihood Explanation
Low-to-moderate: requires a miner (or a pool operator) to pay coinbase rewards to the Serai vault script. That is fully within an unprivileged party's power — miners choose their own coinbase outputs and need no cooperation from Serai validators. Given long vault lifetimes and pool payout behaviors, the trigger is realistic, though it depends on external action rather than being always-on.

### Recommendation
- In `scan_block`, skip `block.txdata[0]` (or filter coinbase transactions via `tx.is_coinbase()`), matching the documented alternative of scanning `block.txdata[1 ..]` internally.
- Alternatively/additionally, extend `ReceivedOutput` (and `ReceivedOutput::read`/`write`) with a flag such as `immature_coinbase`, set it in `scan_block` for coinbase-sourced outputs, and have `SignableTransaction::new` (send.rs:150–256) reject such inputs so unspendable funds can never be selected.

### Proof of Concept
1. Derive the vault P2TR script: `p2tr_script_buf(group_key)` as used in `Scanner::new` (mod.rs:162–166).
2. An unprivileged miner constructs a block whose coinbase pays `X` sats to that script and broadcasts it.
3. Any node calling `Scanner::scan_block(&block)` receives a `ReceivedOutput { offset: Scalar::ZERO, output, outpoint: coinbase_outpoint }` (mod.rs:205–211) that is byte-identical to a mature, spendable output — `ReceivedOutput::read`/`write` (mod.rs:122–141) round-trips it with no maturity flag.
4. Passing this output into `SignableTransaction::new` (send.rs:150) succeeds all checks (`NotEnoughFunds` at send.rs:215 passes since `input_sat` includes it), and `TransactionSignMachine::sign` (send.rs:355–398) produces threshold signatures committing via `Prevouts::All` over the immature prevout.
5. The completed transaction from `TransactionSignatureMachine::complete` (send.rs:413–428) is rejected by every Bitcoin node with `bad-txns-premature-spend-of-coinbase` — the reported-received funds were never spendable.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /// Scan a block.
  ///
  /// This will also scan the coinbase transaction which is bound by maturity. If received outputs
  /// must be immediately spendable, a post-processing pass is needed to remove those outputs.
  /// Alternatively, scan_transaction can be called on `block.txdata[1 ..]`.
  pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
  }
