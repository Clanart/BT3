## Finding

### Title
Front-runnable "receiver balance must be zero" check permanently strands IBC-transferred funds at the isolated callback address - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`ContractKeeper.IBCReceivePacketCallback` gates the success of an ICS-20 "receive with callback" flow on the isolated intermediary address holding **exactly zero** tokens of the transferred ERC20 after the target contract's `transferFrom` runs. Because the isolated address is deterministically derivable from public data before the packet is relayed, an attacker can donate a trivial amount (as little as 1 wei) of the same registered token to that address ahead of time, permanently breaking the zero-balance invariant. Since IBC callback errors are "best effort" and do not roll back the underlying ICS-20 transfer, the victim's entire transferred amount is left stranded forever at the isolated address, which has no corresponding controllable key.

### Finding Description
The isolated receiver address is computed purely from public packet fields: [1](#0-0) 

`types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)` depends only on the (already-known/fixed) destination channel and the sender's bech32 string on the source chain — both of which are public before the relayer submits the `MsgRecvPacket` on the destination chain (the source-chain transaction that initiates the transfer is visible in the source chain's mempool/block long before relaying completes). Any unprivileged actor can therefore precompute `isolatedAddrHex` for a specific victim transfer and, using an ordinary EVM transaction, transfer 1 wei of the exact ERC20 contract backing the token pair directly to that address before the callback executes.

After the target contract's callback runs (`approve` + calldata execution that is expected to invoke `transferFrom` for the full amount), the keeper enforces: [2](#0-1) 

The code's own comment confirms the severity of a failure here: *"This check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable."* Critically, `writeFn()` (which commits the EVM approve/callback execution) is invoked at line 227, **before** this balance check at line 236 — i.e., the check is purely diagnostic at this point and cannot undo the preceding state changes. Under IBC-Go's ADR-8 callbacks design, an error returned from `IBCReceivePacketCallback` does not fail the packet acknowledgement or reverse the underlying ICS-20 token transfer that already credited the isolated address; it only prevents forwarding of funds to the target contract. Consequently, if the attacker's 1-wei donation leaves any dust behind after the legitimate `transferFrom`, the check always fails, the forward-to-contract step is abandoned, and the full amount that ICS-20 already delivered to the isolated address remains there permanently — since the isolated address is a deterministically generated "security" address with no known private key backing it (see the function's own security note: *"Uses isolated addresses to prevent unauthorized access"*).

### Impact Explanation
This is a Critical, unauthorized permanent freezing/loss of user funds: an unprivileged attacker who merely knows (or predicts) an upcoming IBC-transfer-with-callback packet can send a 1-wei donation on the destination chain to permanently strand the entire transferred amount, with no recovery path for the victim. This falls squarely within the allowed impact gate ("Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... that an unprivileged user can trigger through ordinary transaction ... flow").

### Likelihood Explanation
Likelihood is high: the isolated address is fully deterministic and computable off-chain with public inputs (destination channel ID + sender bech32 string), the donation transaction is a trivial, cheap ERC20 transfer, and there is a natural time window between a source-chain IBC send and the relayer's execution of `MsgRecvPacket`/callback on the destination chain during which the attacker can front-run.

### Recommendation
- Before executing the callback, sweep/clear any pre-existing balance at the isolated address (similar to the "clear idle assets first" remediation in the referenced report) so pre-funded dust cannot corrupt the exact-zero invariant.
- Alternatively, compare only the *delta* introduced by the callback's `transferFrom` (i.e., balance before minus balance after equals the transferred amount) rather than requiring an absolute zero balance.
- If the check still fails after accounting for pre-existing dust, ensure there is a recovery path (e.g., allow the original receiver/sender to sweep residual funds from the isolated address) instead of leaving funds unconditionally irretrievable.

### Proof of Concept
1. Victim submits an ICS-20 transfer with a destination callback (`data.Sender` = victim's source-chain address, fixed `destChannel`) moving `N` tokens of a registered native ERC20 token pair to a target contract on the Cosmos EVM chain.
2. Before the relayer submits `MsgRecvPacket`, an attacker computes `isolatedAddr = GenerateIsolatedAddress(destChannel, victimSender)` (pure function, publicly derivable) and sends `1 wei` of the same ERC20 token pair contract to `isolatedAddrHex` via a normal EVM transfer.
3. The relayer delivers the packet; ICS-20 `OnRecvPacket` credits the isolated address with `N` tokens (now `N+1` total). `IBCReceivePacketCallback` runs `approve` + the target contract's calldata, which typically performs `transferFrom(isolatedAddr, contract, N)`, moving out `N` but leaving the attacker's `1 wei` behind.
4. The final check `receiverTokenBalance.Cmp(big.NewInt(0)) != 0` at [3](#0-2)  fails, the function returns an error, but per ADR-8 callback semantics the packet ack and the already-committed transfer/approve state (via `writeFn()` at line 227) are not reverted.
5. Result: `N` tokens (the victim's entire transferred amount) remain permanently stuck at `isolatedAddr`, an address with no corresponding private key, achieving permanent, unauthorized freezing of user funds triggered entirely by an unprivileged attacker's ordinary transaction.
