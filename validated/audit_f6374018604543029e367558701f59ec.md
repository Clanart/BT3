### Title
Stale ByteSizeLong()/serialization mismatch for reflection-based map fields with duplicate keys can produce corrupted or crash-inducing output - ([File: src/google/protobuf/map_field.cc])

### Summary
The external report's failed invariant is: a value (`_stakeAmount`) is captured from mutable state *before* an operation that changes that state, and the downstream consumer (`Treasury.lpBonds()`) trusts the now-stale value without revalidating it against the actual post-operation state, causing an economic/integrity mismatch that the attacker exploits. The nearest structural analog in Protobuf that I could locate and partially verify is the historical dual-representation inconsistency between a map field's "map" view and its "repeated field" (reflection) view in `MapFieldBase`, where `ByteSizeLong()` and the actual serializer could read two different representations of the same field, one of which is stale relative to the other, leading to a byte-size vs. actual-bytes-written mismatch (crash via `ByteSizeConsistencyError` or corrupted/misframed output when using `SerializeWithCachedSizes`).

However, I was **not able to fully confirm reachability purely from an untrusted parse call** on a generated (non-Dynamic) message. The regression test I found (`src/google/protobuf/map_test.inc`, `MapByteSizeDynamicMessage`) explicitly reproduces this stale-size-vs-actual-size defect only via `DynamicMessage` + explicit `Reflection::RemoveLast()` / `MergeFrom()` calls that force the field into `STATE_MODIFIED_REPEATED`, and the test comment states "Protobuf **used to have** a bug ... A crash might have happened ... this is now fixed/regression-tested." I could not verify within my remaining tool budget whether an ordinary `ParseFromString`/`MergeFromString` call on a `DynamicMessage` (i.e., attacker-controlled bytes only, no direct reflection API misuse by the victim application) can itself drive the map field into `STATE_MODIFIED_REPEATED` before serialization — `MapFieldBase::SetRepeatedDirty()` is only invoked from `MutableRepeatedField()`, and I did not get to inspect `wire_format.cc`'s map-field parse path (`ParseAndMergeField` / reflection-based map parsing) before running out of iterations to confirm whether that path calls `MutableRepeatedField()` per-entry (which would make this reachable from pure parsing of duplicate-key bytes) or goes through the map-native `InsertOrLookupMapValue` path (which would not).

### Finding Description
`MapFieldBase` maintains two synchronized representations of a map field: the actual hash map (`GetMapRaw()`) and a `RepeatedPtrField<Message>` view used by generic `Reflection` APIs (`SyncRepeatedFieldWithMap` / `SyncMapWithRepeatedField`, `src/google/protobuf/map_field.cc:196-331`, `421-509`). A tri-state flag (`CLEAN`, `STATE_MODIFIED_MAP`, `STATE_MODIFIED_REPEATED`) tracks which representation is authoritative [1](#0-0) .

`ByteSizeLong()`/serialization code paths that go through `Reflection`-based dynamic messages compute size from whichever representation is currently marked dirty. The regression test `WireFormatForMapFieldTest.MapByteSizeDynamicMessage` demonstrates that when the field is in `STATE_MODIFIED_REPEATED`, `ByteSizeLong()` computes size from the repeated-field view (which can contain duplicate keys and thus be **larger** than the deduplicated map that the wire serializer actually emits), producing `duplicate_size > expected_size` even though the two must be equal for `SerializeWithCachedSizes`'s size-precomputation contract to hold [2](#0-1) . The test comment states this used to cause a crash in `SerializeToString()` (via the `ByteSizeConsistencyError` fatal check in `message_lite.cc`) or an "unexpected end group" parse failure when `SerializeWithCachedSizes()` was used directly (bypassing the size-consistency check) [3](#0-2) .

The general contract that is being violated matches the external bug's structure exactly: `SerializeWithCachedSizes()`'s documented precondition is "the message must not have changed since the last call to `ByteSize()`" [4](#0-3) , and `MessageLite::ByteSizeConsistencyError`/`SerializePartialToCodedStream` exists specifically to detect this at runtime with a fatal `ABSL_CHECK` [5](#0-4) , [6](#0-5) . That is: protobuf's design explicitly acknowledges the "stale cached size vs. actual bytes produced" TOCTOU class and treats a mismatch as either a fatal crash (safe path, `ABSL_CHECK`-based DoS) or, if the caller used the unchecked `SerializeWithCachedSizes` fast path, silently emits malformed/corrupted bytes (unsafe path — analogous to the DeFi bug's "stale accounting value silently trusted").

### Impact Explanation
If reachable purely from attacker-controlled bytes (unconfirmed — see Likelihood below), the impact is:
- A remotely triggerable `ABSL_CHECK`/`ABSL_LOG(FATAL)` crash (denial of service) via `ByteSizeConsistencyError`, when an application re-serializes a `DynamicMessage`/reflection-driven message it just parsed from an attacker (e.g., proxies, gateways, or reflection-based routers that decode-then-re-encode Protobuf messages using `google::protobuf::Message`/`DynamicMessageFactory` rather than generated types).
- If the application uses `SerializeWithCachedSizes()` directly (bypassing the consistency check, which some performance-sensitive serializers do), a corrupted/misframed length-delimited output that fails to re-parse ("unexpected end group") — an integrity failure of the re-serialized wire bytes, structurally identical to the DeFi bug's silent trust of unsynced state.

This is bounded to reflection/`DynamicMessage`-based consumers; generated-code (`TcParser`) map parsing merges directly into the map and does not carry the repeated-field shadow representation the same way, so this does not affect the common "compiled .proto message, ParseFromString" case.

### Likelihood Explanation
**Unconfirmed.** I could not verify, within the available tool budget, whether the generic wire-format map-field parsing path (used by `DynamicMessage` or any `Message`-based type that receives untrusted bytes purely via `ParseFromString`/`MergeFromString`) itself drives the field into `STATE_MODIFIED_REPEATED` when the input contains duplicate map keys, or whether it always goes through the map-native insertion path (`MapFieldBase::InsertOrLookupMapValue`, which keeps the map, not the repeated view, authoritative) and therefore never exhibits this specific mismatch from parsing alone. The only concrete reproduction I found requires explicit `Reflection::RemoveLast()` + `MergeFrom()` application-level calls, which is outside the "ordinary client sending bounded bytes through a public parse API" threat model this scan requires. This weakens confidence that the bug is exploitable purely by an external, unprivileged party against a standard public parsing API without cooperating application logic.

### Recommendation
- If further investigation (not completed here) confirms that duplicate map keys in raw wire bytes parsed through `DynamicMessage`'s generic `Reflection`-based map path can set `STATE_MODIFIED_REPEATED` before size computation, the fix is to ensure `ByteSizeLong()`/`SerializeWithCachedSizes()` always synchronize map/repeated-field state (call `SyncMapWithRepeatedField()`/`SyncRepeatedFieldWithMap()`) to a single canonical representation *before* computing size, and re-verify that representation is unchanged before writing bytes, rather than trusting whichever view happens to be marked dirty at `ByteSizeLong()` time.
- More generally, any caller using the unchecked `SerializeWithCachedSizes()` fast path on `Message`/`DynamicMessage` objects derived from untrusted input should be flagged as unsafe unless the message type is known to have no possible dual-representation staleness (i.e., stick to `SerializeToString`/`SerializeToCodedStream`, which enforce the `ByteSizeConsistencyError` check).

### Proof of Concept
I was unable to construct or run a minimal reproduction limited strictly to "attacker sends bytes to a public parse API" within the remaining budget. The only working reproduction I located is the existing regression test, which requires direct application-level `Reflection` API calls (not just untrusted-bytes parsing) to force the mismatch: [7](#0-6) 

Given the inability to confirm the parse-only reachability requirement stipulated by the scan's threat model, I present this as the strongest structural analog found, but flag it as **unconfirmed/likely not directly exploitable** by an ordinary client through a public parse API alone. void MapFieldBase::SetRepeatedDirty() {
  MutableAccess();
  // These are called by (non-const) mutator functions. So by our API it's the

  payload().set_state_relaxed(STATE_MODIFIED_REPEATED);

namespace {

// When serializing, we first compute the byte size, then serialize the message.
// If serialization produces a different number of bytes than expected, we
// call this function, which crashes.  The problem could be due to a bug in the
// protobuf implementation but is more likely caused by concurrent modification
// of the message.  This function attempts to distinguish between the two and
// provide a useful error message.
void ByteSizeConsistencyError(size_t byte_size_before_serialization,
                              size_t byte_size_after_serialization,
                              size_t bytes_produced_by_serialization,
                              const MessageLite& message) {
  ABSL_CHECK_EQ(byte_size_before_serialization, byte_size_after_serialization)
      << message.GetTypeName()
      << " was modified concurrently during serialization.";
  ABSL_CHECK_EQ(bytes_produced_by_serialization, byte_size_before_serialization)
      << "Byte size calculation and serialization were inconsistent.  This "
         "may indicate a bug in protocol buffers or it may be caused by "
         "concurrent modification of "
      << message.GetTypeName() << ".";
  ABSL_LOG(FATAL) << "This shouldn't be called if all the sizes are equal.";
}

bool MessageLite::SerializePartialToCodedStream(
    io::CodedOutputStream* output) const {
  const size_t size = ByteSizeLong();  // Force size to be cached.
  if (size > INT_MAX) {
    ABSL_LOG(ERROR) << GetTypeName()
                    << " exceeded maximum protobuf size of 2GB: " << size;
    return false;
  }

  int original_byte_count = output->ByteCount();
  SerializeWithCachedSizes(output);
  if (output->HadError()) {
    return false;
  }
  int final_byte_count = output->ByteCount();

  if (final_byte_count - original_byte_count != static_cast<int64_t>(size)) {
    ByteSizeConsistencyError(size, ByteSizeLong(),
                             final_byte_count - original_byte_count, *this);
  }

  return true;
}
