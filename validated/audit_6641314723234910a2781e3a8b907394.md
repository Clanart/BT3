### Title
Attacker-controlled conflict-marker-lookalike lines cause Copilot auto-resolve to silently splice unreviewed content into committed files - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot conflict-resolution feature extracts conflict hunks from a file using naive, unescaped line-based regex matching for `<<<<<<<`, `|||||||`, `=======`, and `>>>>>>>` markers, then later re-locates those same boundaries with an independent (but structurally identical) scanner to splice the model's resolution back into the file. Both scanners take the *first* line that matches a marker regex as the boundary, with no validation that the marker is git-generated rather than literal file content. This mirrors the reported Solidity bug's root cause — a value that is a subset of another value being treated as independent, causing bad accounting — except here the "subset" is a maliciously placed marker-lookalike line *inside* legitimate conflict content that both boundary-detection passes treat as the real boundary, causing part of the actual `theirs` content to fall outside the hunk that is sent to (and resolved by) the model, and outside the block reassembly replaces.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file line by line and terminates the "theirs" section at the first line matching `theirsMarker = /^>{7}(?:\s|$)/` [1](#0-0) , and similarly terminates "ours"/"base" collection at the first `separatorMarker`/`baseMarker` match [2](#0-1) . If the incoming branch's file content contains a line that happens to match one of these 7-character marker regexes (e.g. a code comment, ASCII banner, log excerpt, or string literal containing `>>>>>>> foo` or `=======`), that line is treated as the authoritative conflict boundary — cutting the hunk short and leaving the remaining real "theirs" text (up to the genuine git-emitted closing marker) unclassified as ordinary file content.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) uses the same marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) and the same "first match wins" logic to find where to splice the model's resolved content back into the raw file [3](#0-2) . Because both passes use identical regex and identical greedy/first-match semantics, they agree on the *wrong* boundary — but that agreement is exactly the problem: the block from `<<<<<<<` to the attacker-embedded fake `>>>>>>>` line gets replaced by the model's resolution, while everything after the fake marker (the real, un-reviewed remainder of `theirs`, including the genuine `>>>>>>>` marker line, which is no longer recognized as a marker since it isn't preceded by a fresh `<<<<<<<`) is copied through verbatim into the "resolved" file as ordinary code, per the `else` branch of the outer loop [4](#0-3) .

The validation layer does not catch this: `validateResolutionPaths` only checks that the hunk *count* matches between the model's response and the extracted hunks, not that the underlying byte ranges are correctly bounded [5](#0-4) , and `parseCopilotConflictResolution` only rejects a hunk's `resolvedContent` if it contains an actual `<<<<<<<` + `=======` pair, not stray `>>>>>>>`-looking lines that leaked through from the truncated hunk boundary [6](#0-5) .

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits scenario matching the accepted impact class: an attacker who controls the incoming branch/PR content (the "theirs" side of a merge/rebase/cherry-pick) can plant an innocuous-looking line that matches a 7-character conflict-marker regex inside otherwise normal source, a comment, or a string literal. When the victim uses GitHub Desktop's AI conflict resolution on a conflict touching that content, the tool will (a) never show the model — and by extension the user, who trusts the AI summary — the true remainder of the attacker's content past the fake marker, and (b) splice that unreviewed, unresolved remainder directly and verbatim into the file Desktop then offers the user to stage and commit. The result can be broken code, a stray literal `>>>>>>>`-style line landing in a real commit, or attacker text that was never actually reconciled by either side silently ending up in the merged file and subsequently pushed.

### Likelihood Explanation
Requires only that the untrusted/incoming branch (fully attacker-controlled, e.g. a PR the user fetches and merges) contain one line matching `^<{7}(?:\s|$)`, `^\|{7}(?:\s|$)`, `^={7}$`, or `^>{7}(?:\s|$)` inside content that will end up conflicting with the local branch — an easy, natural-looking string for an attacker to smuggle into a file (it doesn't need to look suspicious; 7 repeated characters followed by whitespace/EOL is common in ASCII art, diff/patch text embedded as documentation, or minified separators). No local access, no admin rights, and no unnatural steps by the victim beyond the ordinary "resolve conflicts with Copilot" workflow that the feature is designed to be used for.

### Recommendation
Do not resolve hunk boundaries purely by scanning for the first regex-matching line. Instead:
- Count/track marker nesting so that only genuine git-emitted markers (which git guarantees are unique in a real conflict block, at the correct position in the format) are treated as boundaries, and validate that the extracted structure round-trips (e.g., re-serializing the parsed hunks against the raw content should reproduce it exactly).
- Have `reassembleResolvedFile` and `extractConflictHunks` share a single boundary-detection implementation (not parallel copies) so any future guard added to one automatically protects the other.
- Reject/flag any file where a conflict block's interior contains additional lines matching the marker regexes, surfacing it as `skippedReason` (as already done for oversized/unreadable files) rather than silently truncating and splicing.

### Proof of Concept
1. Attacker opens a PR/branch containing a file with a line such as:
   ```
   const banner = ">>>>>>>"
   ```
   placed inside a section that will conflict with the victim's local edits to the same file.
2. Victim fetches and merges/rebases the attacker's branch in GitHub Desktop, producing a real conflict with real `<<<<<<<`/`=======`/`>>>>>>>` markers, with the attacker's `banner` line sitting inside the real "theirs" section, above the true closing `>>>>>>>`.
3. Victim uses "Resolve conflicts with Copilot". `extractConflictHunks` stops the theirs section at the attacker's fake `>>>>>>>`-looking line, so the model resolves an incomplete hunk. `reassembleResolvedFile` independently finds the same fake line as the splice boundary, so the model's resolution is inserted there — and the real remaining theirs content plus the true (now unrecognized) closing marker line are copied through as literal file content.
4. Desktop presents the file as "resolved" with no visual indication that raw, unreviewed content (including a literal conflict-marker-like line) was retained; the user commits and pushes the corrupted file.

Note: I was unable to fully trace the exact UI/write path that stages `IFileResolution.resolvedContent` to disk (the write call in `app-store.ts`/`copilot-store.ts` was truncated in retrieval), so the precise post-splice UI review step could not be fully confirmed from the index; a Devin session with full file access would be needed to verify whether any additional diff-review safeguard exists before the write/commit step.
