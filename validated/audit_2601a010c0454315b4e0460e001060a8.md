### Title
Inputs and payments are only checked against the relay dust limit, not the cost of spending them, so dust deposits are credited but cost more to spend than they are worth - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Dinari bug class is a sufficiency check that only accounts for one side's fee, letting a user open a position that is guaranteed to be a net loss. In `bitcoin-serai`, `SignableTransaction::new` enforces `DUST = 546` on payments and on the change output, and performs a global `NotEnoughFunds` check, but never checks that each *input* contributes more than the marginal fee of spending it (~57 vbytes × `fee_per_vbyte`), nor that a payment of `DUST` is economically spendable by the recipient. `Scanner::scan_transaction` likewise reports every output paying to a registered script with no minimum-value filter, so an attacker can send a dust output to a Serai address and have it credited as spendable balance.

### Finding Description
`SignableTransaction::new` validates only the relay dust floor: [1](#0-0) [2](#0-1) 

and a per-input weight of ~57 vbytes is implicitly added by `calculate_weight_vbytes` for every input: [3](#0-2) 

yet there is no check that `input.value >= marginal_input_fee = 57 * fee_per_vbyte`. The only solvency check is aggregate: `input_sat < payment_sat + needed_fee` → `NotEnoughFunds`: [4](#0-3) 

Meanwhile `Scanner::scan_transaction` credits any output whose `script_pubkey` matches a registered offset, regardless of value: [5](#0-4) 

The code itself acknowledges this dimension: the processor documents that Bitcoin requires each output's value to exceed the fee of spending it at 3000 sat/kvB and sets its own `DUST = 10_000` so outputs remain spendable at 5000 sat/kvB — but `wallet/send.rs` uses `546` and applies no analogous check to inputs: [6](#0-5) 

Additionally, `calculate_weight_vbytes` is invoked with `payments` only — the OP_RETURN `data` output pushed to `tx_outs` earlier is excluded from the weight/fee estimate, so `needed_fee` is systematically under-computed whenever `data` is present: [7](#0-6) 

### Impact Explanation
Any party can send a P2TR output of, e.g., 546–600 sats to a Serai address (or a registered offset address). `Scanner` reports it as a `ReceivedOutput`; when included as an input, spending it adds ~57 vbytes, so at a feerate above ~10 sat/vbyte the input's marginal fee cost exceeds its value — the transaction's net position is worse than if the input were ignored, and the "received" funds are not economically spendable. This is the direct analog of the Dinari finding: a one-sided minimum check (relay dust) that ignores the spend-side cost. The OP_RETURN weight omission further means any transaction carrying `data` pays strictly less than the requested `fee_per_vbyte` rate.

### Likelihood Explanation
Reachable by any unprivileged party with public inputs: they only need to send a Bitcoin transaction to the (public) Serai deposit address with a dust-valued output. Whether a specific scheduler aggregates such inputs depends on processor logic outside the in-scope wallet crate, but `SignableTransaction::new` itself — the in-scope API — accepts such inputs unconditionally and `Scanner` unconditionally reports them.

### Recommendation
- In `SignableTransaction::new`, reject (or skip) inputs whose `output.value` is below the marginal spend cost `57 * fee_per_vbyte` plus a safety margin, rather than accepting every `ReceivedOutput`.
- Raise the payment/change minimum from the bare relay `DUST = 546` to an economically spendable threshold consistent with the documented 5000 sat/kvB assumption (as the processor's own `DUST = 10_000` already does).
- Include the OP_RETURN output in `calculate_weight_vbytes` when `data` is present.

### Proof of Concept
1. Attacker computes the Serai P2TR address (or a registered offset script) and broadcasts a transaction with an output of 546 sats to it.
2. `Scanner::scan_transaction` returns a `ReceivedOutput` with `value() == 546` — credited as spendable balance (wallet/mod.rs:199-213).
3. `SignableTransaction::new(vec![dust_output], &payments, ...)` includes it without error; `calculate_weight_vbytes` adds a 230-weight-unit input (send.rs:71-83).
4. At `fee_per_vbyte = 20`, the input's marginal cost is ~1140 sats > 546 sats contributed — the tx burns ~594 sats of other funds, and a payment output of exactly 546 sats is likewise unspendable by its recipient. No error is raised since only the aggregate `input_sat < payment_sat + needed_fee` is checked.

Caveat: I verified the wallet-level checks (`send.rs`) and the scanner (`wallet/mod.rs`) directly, but the input-selection path in `processor/src/multisigs/scheduler/utxo.rs` is outside the in-scope crates, so whether the dust input is actually selected for spending depends on scheduler behavior I could not fully trace within the permitted scope.
