### Title
`InitializeBuffer` accepts an unsigned, unverified authority — front-runnable takeover of BPF Loader Upgradeable buffer accounts - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `InitializeBuffer` handler in the BPF Loader Upgradeable program sets a buffer account's authority from instruction account index 1 without requiring that account to sign, and without requiring the buffer account itself to sign either. This is the same class of bug as the referenced "unprotected `initialize`" finding: whoever's `InitializeBuffer` transaction lands first on an existing, `Uninitialized` buffer account wins control of it, and there is no cryptographic proof binding the caller to the account.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

It only checks that the target buffer account's state is `Uninitialized`, then unconditionally stamps `authority_address` from account index 1 — with no `is_instruction_account_signer` check on that account, and no signer requirement on the buffer account (index 0) either. Contrast this with the `Write` instruction just below it, which does require the authority to sign and match: [2](#0-1) 

The bundled builder `bpf_loader_upgradeable::create_buffer()` normally packs `CreateAccount` + `InitializeBuffer` into one atomic message (confirmed by the test constructing both instructions in a single `Message`): [3](#0-2) 

However, atomicity is a client-side convention, not something the loader enforces. Nothing in `process_loader_upgradeable_instruction` requires `InitializeBuffer` to occur in the same transaction as the account's creation. If a caller (a script, a service, a partial-signing workflow, etc.) submits `CreateAccount` and `InitializeBuffer` as two separate transactions — which the loader fully permits — there is an on-chain window where the buffer account exists, is owned by `bpf_loader_upgradeable`, and is still `Uninitialized`. Any other party who observes the pending/first transaction (mempool/gossip observation, i.e., MEV-style front-running by another unprivileged user) can race a competing `InitializeBuffer` instruction referencing the same buffer pubkey with their own key as `authority_address`. Because no signature is required for account 1, and no signer/ownership check is required for account 0, this attacker-controlled transaction can land first and "steal" the authority slot as `AccountAlreadyInitialized` will then reject the legitimate owner's subsequent call.

### Impact Explanation
Whoever's `InitializeBuffer` transaction gets included first becomes the recognized `authority_address` for that buffer account. From then on, the legitimate creator's own `InitializeBuffer` call fails with `AccountAlreadyInitialized`, and only the attacker can subsequently call `Write` (which does enforce authority-signature matching) to populate the buffer with program bytes, or call `Close`/`SetAuthority` to claim the buffer's rent-exempt lamports and/or transfer authority further. Effectively, this hands the attacker control over a soon-to-be-deployed program's staging pipeline and any lamports funding it — a real state-corruption/asset-misdirection outcome, not merely a pricing inconvenience like the referenced AMM report.

### Likelihood Explanation
Exploitation requires that `CreateAccount` and `InitializeBuffer` land as two distinct transactions rather than one atomic transaction, which is a plausible (if non-default) usage pattern for tooling that separates account funding/creation from later configuration steps, or for scripts that build custom instruction sequences. The CLI path (`cli/src/program.rs`) bundles both, but the *program itself* provides no protection if any other caller does not bundle them, so the security boundary should live in the loader, not in client conventions.

### Recommendation
Require the buffer account (instruction account 0) to be a signer in `InitializeBuffer`, or otherwise cryptographically bind `InitializeBuffer` to the account's creation (e.g., require the transaction to include the `CreateAccount` for that same pubkey, or require the authority account to sign as `Write` already does). At minimum, mirror the `Write` instruction's signer check for the authority account so that unauthenticated parties cannot claim authority over any uninitialized buffer account they merely observe.

### Proof of Concept
1. Alice submits transaction T1: `system_instruction::create_account(buffer_pubkey, owner = bpf_loader_upgradeable::id())`.
2. Once T1 confirms (or is even visible pending), Bob — who has no relationship to `buffer_pubkey` — submits transaction T2: `InitializeBuffer` on `buffer_pubkey` with account index 1 = `bob_pubkey`, unsigned.
3. If T2 lands before Alice's own `InitializeBuffer` transaction, `process_loader_upgradeable_instruction` (`programs/bpf_loader/src/lib.rs:158-172`) sets `buffer.authority_address = Some(bob_pubkey)` because it never checks that account 1 signed.
4. Alice's subsequent `InitializeBuffer` call now fails with `AccountAlreadyInitialized`, and only Bob can `Write`/`Close`/`SetAuthority` on the account going forward.
