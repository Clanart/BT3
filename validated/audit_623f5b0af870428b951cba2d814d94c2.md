## Analysis

The scoped codebase implements an "unstake must include reward harvest" pattern very similar to the reported bug's "close position must include profit refund" pattern.

When a user withdraws staked LP/receipt tokens from `MasterMagpie`, the withdrawal path forces an atomic reward harvest before the principal is returned:

- `withdrawFor()` calls `_withdraw()`, which (per the code around lines 505-514) performs the staking-token `safeTransfer` back to the user only after harvesting is completed for that account.
- `_harvestAndUnstake()` unconditionally calls `_harvestMGP()` and `_harvestBaseRewarder()` before adjusting the user's balance [1](#0-0) .
- `_harvestBaseRewarder` ultimately invokes the rewarder's `getReward(_account, _receiver)`, which loops over every registered reward token and does `IERC20(rewardToken).safeTransfer(_receiver, reward)` for any nonzero balance [2](#0-1) . The V2 variant behaves the same way via `_sendReward` [3](#0-2) .

Because this reward `safeTransfer` is bundled in the same transaction as the principal withdrawal, if the withdrawing account is blacklisted (e.g. by USDC or another ERC-20 with transfer restrictions) for *any* accrued reward/bonus token in that pool's reward-token list, the `safeTransfer` reverts and unwinds the entire transaction — including the return of the principal staking token. There is no way to skip harvesting just the blacklisted token; `getReward`/`_sendReward` transfer whatever is in `userRewards[token][account]` unconditionally once nonzero.

This is entered via an ordinary user-triggered path: `WombatPoolHelper.withdraw()` → `WombatStaking.withdraw()` → `MasterMagpie.withdrawFor()` → `_harvestAndUnstake()` → `_harvestBaseRewarder()` → `BaseRewardPool.getReward()` [4](#0-3) . Since `burnReceiptToken` and the underlying LP release in `WombatStaking.withdraw` [5](#0-4)  only happen after this succeeds, a revert leaves the user's receipt tokens and underlying LP permanently locked with no alternative unstake path (the only bypass, `emergencyWithdraw`, requires the contract to be paused by the admin — not something the ordinary user controls, and it's an admin action, so it doesn't remove the freeze under normal operation).

This is a legitimate structural analog to the external report: an unavoidable "reward/profit transfer" bundled into a principal-return function can permanently `revert` and lock funds if the recipient is blacklisted for one of the transferred tokens. However, unlike the original H-01, this freeze only affects the individually-blacklisted account's own principal — it does not lock other users' funds or drain protocol-wide liquidity. Under this scan's acceptance rule for "permanent freezing of funds," self-inflicted freezing of the actor's own deposited stake meets a lower bar than the LP-insolvency scenario in the original report.

### Title
Blacklisted user's forced reward-harvest revert permanently locks their principal stake in `MasterMagpie` - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie` bundles mandatory reward-token distribution into the same transaction as principal withdrawal. If a staker becomes blacklisted (e.g., by USDC) for any bonus/reward token accrued in a pool they are staked in, the forced `safeTransfer` of that reward during unstaking will always revert, permanently blocking withdrawal of their principal staking/receipt tokens.

### Finding Description
`_harvestAndUnstake` unconditionally calls `_harvestBaseRewarder`, which triggers `BaseRewardPool.getReward`/`BaseRewardPoolV2._sendReward`, transferring all nonzero accrued reward tokens to the withdrawing account before the principal stake is released [1](#0-0) [2](#0-1) . There is no mechanism to skip a single blacklisted reward token and still return the principal.

### Impact Explanation
An affected user's WombatStaking-custodied LP position and receipt tokens become permanently unrecoverable through the normal `withdraw`/`withdrawFor` path once they are blacklisted on any accrued reward token for that pool, since the harvest-then-transfer step will always revert.

### Likelihood Explanation
Requires the staker to become blacklisted (e.g., USDC-style token) for a reward token accrued while staked — a rare, self-affecting edge case, analogous to what the original report's sponsor also characterized as rare and lower severity.

### Recommendation
Decouple mandatory reward distribution from principal withdrawal: allow `_withdraw`/`_harvestAndUnstake` to skip (and accrue to a claimable-later balance) any reward-token transfer that reverts, rather than reverting the whole withdrawal, e.g. via a try/catch and a `claims[token][account]` pull-payment pattern.

### Proof of Concept
1. User stakes LP receipt tokens via `WombatPoolHelper.deposit`, which routes through `MasterMagpie.depositFor` [6](#0-5) .
2. Reward tokens (e.g., a bonus USDC-based bribe/reward token) accrue to the user in the pool's `BaseRewardPool`.
3. User's address is later blacklisted by the reward token's issuer.
4. User calls `WombatPoolHelper.withdraw` → `WombatStaking.withdraw` → `MasterMagpie.withdrawFor` → `_harvestAndUnstake` → `_harvestBaseRewarder` → `getReward` → `safeTransfer(blacklistedUser, reward)` reverts, reverting the whole withdrawal.
5. User can never withdraw principal through the normal path again unless the admin pauses the system to allow `emergencyWithdraw` [7](#0-6) .
