### Title
Self-relayed oversized message bodies let an unprivileged actor mint unbounded Reputation Asset via `pallet-messaging-incentives` - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
The external report's core broken invariant is: a reward/mint formula trusts an attacker-influenced input (`tx.gasprice`) with no bound or oracle check, letting the attacker self-deal a disproportionate mint. The local analog is `pallet-messaging-incentives::on_executed`, which mints `ReputationAsset` to a relayer using `amount = rate * max(body_len, 32)` where `body_len` is the raw byte-length of a message body that the *same actor* fully controls (as the dispatching app on the source chain) and *also* delivers (as the self-relayer on Hyperbridge). There is no cap analogous to `maxTokens`, and no market/oracle check tying the byte count to real resource cost.

### Finding Description
`Pallet::on_executed` in [1](#0-0)  mints reputation proportional to `Self::message_bytes`, which sums `max(body.len(), 32)` across the requests in a delivered message [2](#0-1) . The mint amount is `rate.saturating_mul(bytes_balance)` with no upper bound on `bytes`, and the recipient is recovered purely from the sr25519 signature over the encoded requests — i.e., whoever signs/submits the message as "relayer" [3](#0-2) .

Both roles in this flow are unprivileged and permissionless:
- Dispatching a POST request with an arbitrarily large `body` from any source chain is a normal, permissionless app action (see `IDispatcher.dispatch`/`DispatchPost.body`) [4](#0-3) .
- Delivering ("relaying") that message to Hyperbridge and being credited as the signer is likewise permissionless — the ISMP `handle` flow explicitly documents relaying as open to "anyone" [5](#0-4) .

Because the same actor can be both the app that pays to dispatch a large-body message and the relayer that self-delivers it, the byte count fed into the mint formula is entirely attacker-chosen, just as `tx.gasprice` was attacker-chosen in the Unlock Protocol case. There is no oracle, no per-message cap, and no linkage back to real relayer effort (proof-verification/consensus work) — only a linear multiplier on a self-supplied number. This mirrors `uint tokensToDistribute = (estimatedGasForPurchase * tx.gasprice) * ... / udtPrice;` trusting an unclamped, self-controlled value.

The `state-coprocessor` pallet's `handle_get_requests` mints reputation through the exact same `pallet_messaging_incentives::MintPerByte` rate and the same "shared source of truth" reasoning, based on `total_bytes` of GetResponses, credited to an `address` field that is caller-supplied in the unsigned extrinsic body [6](#0-5) , compounding the exposure across two independent code paths sharing one economic parameter.

### Impact Explanation
`ReputationAsset` is not a decorative counter — `pallet-collator-manager::new_session` ranks all bonded candidates purely by their controller's `ReputationAsset` balance and selects the top N as collators for the session, burning the balance of whoever is chosen [7](#0-6) . Winning a collator seat yields real, transferable `$BRIDGE` block-production rewards, per the documented design where reputation is explicitly meant to "mirror your `$BRIDGE` earnings" and directly determines "your chances of being selected as a Collator" [8](#0-7) .

An attacker who cheaply inflates `bytes` (paying only source-chain calldata/storage cost, which can be minimal on low-fee chains, and zero protocol fee since apps like `BandwidthManager` dispatch with `fee: 0`) can mint reputation far in excess of what genuine message-relaying/proof-verification work would earn, guaranteeing themselves (or a colluding controller) a collator slot ahead of honest, resource-constrained operators. This is a logic attack on the host/collator-selection subsystem that converts a metering formula into an unauthorized route to real economic reward and block-production control — squarely in the "logic attacks" / "unauthorized execution" impact category, since it lets an unprivileged actor seize collator authority (and its associated funds/block rewards) without performing commensurate real work.

### Likelihood Explanation
Both preconditions are trivially satisfiable by a single unprivileged party: (1) dispatch a POST request from any connected source chain to any app/address with a maximal body, and (2) submit/sign that request as the delivering relayer on Hyperbridge — no governance, no compromised keys, no malicious peer/prover assumptions required. The formula has no cap, and the "same minimum-byte floor as bandwidth" comment in the code shows engineering awareness of gaming via tiny bodies, but there is no analogous ceiling awareness for oversized bodies. The only natural limits are block/extrinsic size caps on Hyperbridge, which are large enough to make repeated farming (across many self-relayed messages) practical over time to accumulate a decisive reputation lead before a session boundary.

### Recommendation
- Cap the per-message (and/or per-session) byte contribution counted toward `MintPerByte`, independent of the raw declared body length, so a single self-dealt message cannot dominate reputation.
- Tie minted reputation to verifiable, non-self-controllable cost signals (e.g., actual consensus/proof-verification weight consumed, or a market-priced bandwidth purchase) rather than a caller-influenced byte count alone — analogous to using an external oracle instead of trusting `tx.gasprice`.
- Consider requiring the relayer identity (`signer`) to differ from the dispatching app's account/controller relationship, or rate-limit reputation minted per `(app, relayer)` pair per session to blunt self-relay farming.
- Apply the same fix to `state-coprocessor::handle_get_requests`, which shares the vulnerable `MintPerByte` mechanism and additionally trusts a caller-supplied `address` for the mint target.

### Proof of Concept
1. Attacker deploys/controls an app on a cheap source chain (or an existing permissionless dispatcher) and calls `IDispatcher.dispatch(DispatchPost{ body: <near-max-size bytes>, fee: 0, ... })` repeatedly, paying only calldata/storage gas — see `evm/src/core/EvmHost.sol:921-944` for the permissionless dispatch path.
2. The same attacker (or a cooperating account) submits the resulting `RequestMessage`/`Message::Request` to Hyperbridge as the relayer, signing it themselves, per the documented "permissionless" relay path (`docs/content/protocol/ismp/requests.mdx:76-112`).
3. On successful execution, `pallet_messaging_incentives::Pallet::on_executed` computes `bytes = max(body.len(), 32)` per request and mints `rate * bytes` `ReputationAsset` directly to the attacker's signing account — `modules/pallets/messaging-incentives/src/lib.rs:156-186`.
4. Repeating this before a session boundary accumulates a `ReputationAsset` balance that dominates honest operators; at `new_session`, `pallet-collator-manager` ranks purely by this balance and selects the attacker as collator — `modules/pallets/collator-manager/src/lib.rs:499-571` — granting them real `$BRIDGE` block-production rewards for work they did not proportionally perform.

impl<T: Config> Pallet<T>
where
	T::AccountId: From<[u8; 32]>,
{
	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);

						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })

The request `handle` is used to notify onchain `IsmpModule`s of new requests to be processed. A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.

	impl<T: Config> SessionManager<T::AccountId> for Pallet<T>
	where
		T::AccountId: Into<<T as pallet_session::Config>::ValidatorId> + Clone,
	{
		fn new_session(_new_index: SessionIndex) -> Option<Vec<T::AccountId>> {
			T::IncentivesManager::reset_incentives();

			let desired_collators = core::cmp::max(
				pallet_collator_selection::DesiredCandidates::<T>::get(),
				<T as pallet_collator_selection::Config>::MinEligibleCollators::get(),
			) as usize;

			// Rank candidate controllers that have session keys by reputation, highest first.
			// We keep every eligible candidate, even those with no reputation, so the set never
			// shrinks below what's needed to keep producing blocks; reputation only orders them.
			let mut candidates = pallet_collator_selection::CandidateList::<T>::get()
				.into_iter()
				.map(|info| info.who)
				.filter(|stash_account| !Unbonding::<T>::contains_key(stash_account))
				.filter_map(|stash_account| Controller::<T>::get(&stash_account))
				.filter(|controller_account| {
					!RemovedValidators::<T>::contains_key(controller_account) &&
						pallet_session::NextKeys::<T>::get(controller_account.clone().into())
							.is_some()
				})
				.map(|controller_account| {
					(T::ReputationAsset::balance(&controller_account), controller_account)
				})
				.collect::<Vec<_>>();

			candidates.sort_by_key(|(balance, _)| *balance);

			// Invulnerables always collate unless root has removed them; the highest reputation
			// candidates fill the rest.
			let mut new_set: Vec<T::AccountId> =
				pallet_collator_selection::Invulnerables::<T>::get()
					.into_iter()
					.filter(|validator| !RemovedValidators::<T>::contains_key(validator))
					.collect();
			for (_, controller) in candidates.into_iter().rev().take(desired_collators) {
				if !new_set.contains(&controller) {
					new_set.push(controller);
				}
			}

			if new_set.is_empty() {
				return None;
			}

			for account_id in &new_set {
				let balance = T::ReputationAsset::balance(account_id);
				if balance.is_zero() {
					continue;
				}
				let result = T::ReputationAsset::burn_from(
					account_id,
					balance,
					Preservation::Expendable,
					Precision::Exact,
					Fortitude::Polite,
				);

				if result.is_ok() {
					Self::deposit_event(Event::ReputationReset {
						who: account_id.clone(),
						amount: balance,
					});
				}
			}

			Self::deposit_event(Event::NewCollatorSet(new_set.clone()));
			Some(new_set)
		}

### The Tokens

- **The Hyperbridge Token (`$BRIDGE`)**: This is the primary token earned as a reward for operating network infrastructure. It is a real, transferable asset that reflects your earnings.
