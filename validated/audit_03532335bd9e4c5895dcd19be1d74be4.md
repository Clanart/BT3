### Title
Attacker-controlled OP_RETURN data is excluded from transaction weight/fee estimation, producing under-funded or non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a classic size-accounting bug: a check computed against the wrong bound (`segments_left == 0` instead of the actual bytes about to be pushed) lets attacker-controlled growth exceed the reserved space. The analog in `bitcoin-serai` is `SignableTransaction::new`: the transaction's weight, vbytes, required fee, and the `MAX_STANDARD_TX_WEIGHT` standardness check are all computed from `payments` only, while the attacker-supplied OP_RETURN `data` output is pushed to `tx_outs` separately and is never included in the size estimate. The resulting transaction is larger than every bound that was checked.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight is computed:

```rust
// networks/bitcoin/src/wallet/send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` builds its template transaction's `output` vector exclusively from `payments` (lines 85-93), plus optionally `change` (lines 95-99). The OP_RETURN output (up to 80 bytes of data plus script/output overhead, roughly 90+ weight-units' worth of actual bytes, ~23 vbytes) is never part of the estimate. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed against a vbytes that excludes the OP_RETURN output.
- The `TooLowFee` check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) also uses the underestimated vbytes, so a transaction can pass this check while its *actual* fee rate is below the relay minimum.
- The `TooLargeTransaction` standardness check at line 241 (`weight > MAX_STANDARD_TX_WEIGHT`) uses the weight missing the OP_RETURN output, so a transaction just under the limit can actually exceed it once the data output is included.
- `SignableTransaction::fee()` (lines 138-141) reports the real fee (inputs minus real outputs), so the discrepancy between the advertised `fee_per_vbyte` and the achieved fee rate is silent.

The change path has the same shape: `calculate_weight_vbytes(..., Some(&change))` at line 226 again omits the data output from `vbytes_with_change`.

### Impact Explanation
`data` is caller/attacker-supplied transaction content (a full 80-byte OP_RETURN). The produced `SignableTransaction` is the object the FROST `TransactionSignMachine` signs (lines 373-397). Because the OP_RETURN output's weight was never counted:

- The transaction pays a lower effective fee rate than requested; if the uncounted ~23 vbytes push the actual rate below mempool minimum relay fee, the signed transaction will not propagate and the inputs it spends remain locked behind an unconfirmable signature (funds effectively unspendable until a re-sign at a corrected size).
- A transaction assembled near `MAX_STANDARD_TX_WEIGHT` can exceed the limit in reality, producing a non-standard (unrelayable) transaction.

Both cases mirror the kernel bug: a size bound was enforced against a stale/smaller figure while attacker-influenced bytes made the real object larger.

### Likelihood Explanation
Medium. Reaching it requires only that a plan/transaction include OP_RETURN data — a supported, public input to `SignableTransaction::new`. No collusion or validator misbehavior is needed. The impact is bounded to liveness/fund-availability of that one transaction (underpaid fee or non-standardness) rather than key or share compromise, so it rates Medium rather than Critical like the kernel OOB write.

### Recommendation
Include the OP_RETURN output in the weight/vbytes estimate. Compute weight over the fully-populated output set — e.g., pass the assembled `tx_outs` (or `payments` plus the data output) into `calculate_weight_vbytes` for both the no-change and with-change calculations, and perform the `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks against that inclusive figure.

### Proof of Concept
```rust
// Conceptual: any call site providing data to SignableTransaction::new
let payments: &[(ScriptBuf, u64)] = &[(payment_script, 10_000)];
let data = Some(vec![0xAA; 80]); // max allowed OP_RETURN payload

let tx = SignableTransaction::new(inputs, payments, Some(change), data, fee_per_vbyte)
  .unwrap();

// tx.needed_fee() == fee_per_vbyte * vbytes where vbytes excludes the OP_RETURN output.
// The real tx (tx.transaction()) contains the ~90-byte OP_RETURN output, so the
// achieved sat/vbyte is strictly less than fee_per_vbyte, and the weight bound
// checked at line 241 under-counts the real transaction weight.
```
Concretely, `calculate_weight_vbytes` at send.rs:62-127 constructs `tx.output` only from `payments` and `change`, while the `data` output is added to the real `tx_outs` at send.rs:194-202 and never to the template.

Caveat: I verified the weight-estimation path in `send.rs` directly, but did not trace every upstream caller (e.g., the processor scheduler) that feeds `data` into `SignableTransaction::new`; reachability from untrusted plan data is plausible but not fully confirmed within the available iterations.
