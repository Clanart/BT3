### Title
Shared `BalanceHandler` instance across nested/recursive precompile calls corrupts EVM StateDB balances vs. bank keeper truth - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
Cosmos EVM precompiles (ICS-20, staking, distribution, gov, slashing, erc20, werc20) use a `BalanceHandler` to reconcile native `x/bank` balance-change events into the EVM `StateDB` around each precompile invocation. The handler records `prevEventsLen` in `BeforeBalanceChange` and consumes `events[prevEventsLen:]` in `AfterBalanceChange` to compute balance deltas applied to `StateDB.AddBalance`/`SubBalance`. When a precompile call recursively/re-entrantly triggers another precompile call (e.g., via an ERC20 token with a malicious transfer hook, or nested ICS-20/distribution/staking calls), the same `BalanceHandler` instance's `prevEventsLen` bookmark is overwritten by the inner call before the outer call finishes, causing the outer call to read the wrong event-index window. This produces a desync between the actual `x/bank` ledger and the EVM `StateDB` balance view, which is what ultimately gets committed for gas accounting, subsequent transfers within the same tx, and cross-module (precisebank/erc20/ICS-20 escrow) accounting.

### Finding Description
`BalanceHandler.BeforeBalanceChange` stores `bh.prevEventsLen = len(ctx.EventManager().Events())`, and `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` to translate `CoinSpent`/`CoinReceived`/precisebank fractional-balance events into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) [2](#0-1) 

Every SDK-module precompile (ICS-20, staking, distribution, gov, slashing, erc20) is constructed with a single `BalanceHandlerFactory` embedded in the shared `cmn.Precompile` struct, e.g.: [3](#0-2) [4](#0-3) 

The debug-precompile test harness (mirroring production precompile `Run()` logic) explicitly documents the bug in its own comments: [5](#0-4) 

and the dedicated IBC/ICS-20 recursive-call regression test states the exact mechanism — reverted distribution calls leaving persistent bank events that get incorrectly aggregated by the shared handler: [6](#0-5) 

The `Run()` flow for a precompile call (shown in the debug precompile, which follows the same pattern as production precompiles via `cmn.Precompile.Execute`) is: snapshot state → `BeforeBalanceChange` (bookmark event index) → `Execute` (may internally invoke other precompiles/keepers, potentially through reentrant EVM calls triggered by hooked ERC20 tokens or nested Cosmos SDK module calls) → `AfterBalanceChange` (consume events from bookmark onward): [7](#0-6) 

If, during `Execute`, an inner precompile call reuses the *same* `BalanceHandler` instance (as opposed to a fresh one per invocation) and calls `BeforeBalanceChange` again, it overwrites `prevEventsLen` to a higher value. When the outer call's `AfterBalanceChange` subsequently runs, it uses this now-stale/advanced index, causing it to skip events that belong to the outer call (silently dropping balance credits/debits that should have been applied to `StateDB`) or double-process events already consumed by the inner call. Either way, the `StateDB` balance diverges from the actual `x/bank` ledger balance for the accounts involved.

### Impact Explanation
This breaks the "Asset-representation path" invariant explicitly called out in scope: `StateDB`, bank, and precompile-visible balances must stay 1:1 consistent. A divergence here is a critical accounting corruption of spendable user value:
- If events are skipped (outer call's own balance delta never applied to StateDB), a user's on-chain EVM-visible balance can end up higher than what was actually debited from `x/bank` — effectively creating spendable value that isn't backed by actual escrowed/burned coins (unauthorized "duplication" of value), which can then be transferred/withdrawn again through further EVM operations.
- If events are double-applied, StateDB balances can be corrupted downward, permanently freezing/locking user funds view for subsequent operations in the same or later transactions (since `StateDB` state is what's committed to the account after transaction execution).

Given the precompiles involved include ICS-20 (which mediates IBC escrow balances) and staking/distribution/erc20 (which mediate reward and token-pair balances), the blast radius covers exactly the "precompile-mediated assets" and "token-pair-backed balances" called out as in-scope Critical impact categories.

### Likelihood Explanation
The trigger does not require any privileged role — any user can deploy an ERC20 contract with a malicious/re-entrant transfer hook, or otherwise construct a call sequence that causes a precompile invocation to recursively invoke another (or the same) precompile within the same EVM call frame. The project's own test suites (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) exist specifically because this scenario is reachable and reproducible via ordinary transaction/contract flow, confirming realistic unprivileged reachability.

### Recommendation
- Ensure a fresh `BalanceHandler` instance (with its own `prevEventsLen`) is created for every precompile invocation rather than sharing one instance across nested/recursive calls — e.g., instantiate via `BalanceHandlerFactory.NewBalanceHandler()` at the start of each `Run()`/`Execute()` invocation rather than storing a handler as shared mutable state on the `Precompile` struct.
- Alternatively/additionally, use a stack-based (LIFO) bookmark of event-list lengths keyed to call depth (mirroring how `StateDB`'s journal/snapshot mechanism already handles nested reverts) so that inner-call bookmarking cannot clobber the outer call's bookmark.
- Add invariant checks (e.g., in `EndBlocker` or via CI-level differential tests) that assert `sum(StateDB EVM balances for evm-denom) == corresponding x/bank balances` after any transaction that exercises nested precompile calls, and expand the existing recursive-call regression tests to explicitly assert balance equality (not just event counts) after nested precompile calls across all SDK-module precompiles (staking, distribution, gov, slashing, erc20, ICS-20), not just the ICS-20/distribution case already tested.

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```go
func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}
```
