### Title
Missing point-at-infinity check in `x()`/`x_only()` lets attacker-supplied preprocess commitments panic the signer — ([File: networks/bitcoin/src/crypto.rs])

### Summary
`x()` in `networks/bitcoin/src/crypto.rs` panics (`expect("point at infinity")`) when passed the identity point, and `x_only()` likewise `expect`s a non-infinity point. `Hram::hram` calls `x()` on `R` and `A`, and `p2tr_script_buf`/`tweak_keys`/`Scanner`/`SignableTransaction::multisig` funnel attacker-influenced `ProjectivePoint` values into `x_only`. The `Hram::hram` path is reachable during FROST signing, where `R` is the aggregated nonce commitment derived from `read_preprocess` bytes supplied by other participants — untrusted input by design. [1](#0-0) [2](#0-1) 

### Finding Description
CVE-2018-16749 is a missing NULL check causing an assertion-failure/application-exit DoS on crafted input. The Serai analog is a missing identity check on a `ProjectivePoint` before unconditional point operations:

- `fn x(key)` calls `key.to_encoded_point(true)` and `expect("point at infinity")` on the missing x-coordinate — an unhandled failure mode for a well-formed group element (the identity). [3](#0-2) 
- `x_only` propagates this via `XOnlyPublicKey::from_slice(&x(key)).expect(...)`. [4](#0-3) 
- `Hram::hram(R, A, m)` calls `x(R)` and `x(A)` unconditionally. `R` is the sum of nonce commitments, where each participant's `Preprocess.commitments` are parsed from untrusted bytes via `read_preprocess` → `Commitments::read` → `C::read_G`. [5](#0-4) [6](#0-5) 
- `SignableTransaction::multisig` calls `p2tr_script_buf(offset.group_key())`, which uses `x_only` on a group key that incorporates `keys.clone().offset(self.offsets[i])`, where `offsets` come from `ReceivedOutput::read` bytes (`Secp256k1::read_F(r)` — any scalar is accepted). [7](#0-6) [8](#0-7) 

The crate documentation acknowledges the panic ("If either `R` or `A` is the point at infinity, this will panic"), asserting it has "negligible probability for a well-reasoned caller, even with malicious participants present" — but probability is irrelevant: a malicious participant can *deterministically* craft commitments whose sum is the identity (e.g., `D_i = -Σ D_j` for other committed nonces, or the identity point encoding itself if `read_G` accepts the all-zero/k256 identity encoding). [9](#0-8) 

### Impact Explanation
A malicious co-signer submits preprocess bytes such that the aggregated binding-factor-weighted nonce sum `R` — or a per-generator nonce commitment summed into `nonce_sums` — equals the point at infinity. When the honest signer's `sign_share`/verification path reaches `Hram::hram`, `x(R)` panics, crashing the signing process. This is the same attacker-model as the CVE: an unprivileged party causes a denial of service via crafted input bytes, aborting threshold signing (Bitcoin transaction signing and any `Schnorr`-using flow). [2](#0-1) 

Caveat: I was unable to fully trace `Commitments::read`/`SignableTransaction`'s binding-factor aggregation in `crypto/frost/src/sign.rs` beyond line ~320 to confirm whether an explicit identity rejection exists further downstream (e.g., a `R.is_identity()` → `InvalidPreprocess` check in the FROST nonce-sum computation). If such a check exists there, the `hram` path is safe and the residual exposure is the `p2tr_script_buf`/`x_only` path in `multisig`/`register_offset`, which returns `None` rather than panicking at the `to_encoded_point` stage — `x()` panics only on `encoded.x()` being `None`, i.e. infinity, which `p2tr_script_buf` does not pre-filter.

### Likelihood Explanation
Preprocess messages are unauthenticated broadcast bytes between threshold participants; any participant can choose their `Commitments` points adversarially after seeing others' (commit-then-reveal ordering matters, but an attacker committing last, or grinding against known sums, can force the aggregate to identity). Exploitation requires being a threshold participant rather than an arbitrary network user, which bounds the severity to Medium, matching the CVE's 6.5 DoS profile.

### Recommendation
Add an explicit `is_identity()` check: reject identity nonce commitments in `Commitments::read`/`read_preprocess` processing (map to `FrostError::InvalidPreprocess`), and make `x`/`x_only` return `Option`/error instead of `expect`, per BIP-340/341 which define distinct handling for infinity inputs. Also audit `tweak_keys`/`register_offset`/`multisig` callers to propagate failures rather than panic on attacker-controlled point values.

### Proof of Concept
```rust
// Attacker participant crafts a preprocess whose nonce commitments,
// combined under the FROST binding factors with the other parties'
// commitments, sum to ProjectivePoint::identity().
// The honest node calls machine.read_preprocess(&mut attacker_bytes) ->
// Commitments::read -> Secp256k1::read_G (identity encoding accepted
// unless explicitly rejected).
// In sign(), nonce_sums aggregated R == identity, then:
//   Hram::hram(&R_identity, &group_key, msg)
//     -> x(R) -> encoded.x() == None
//     -> panic: "point at infinity"
// Result: signer process aborts (denial of service), no signature
// is produced for this session.
```

If the downstream identity check in `sign.rs` exists and was simply not visible in the indexed excerpt, treat this finding as unconfirmed rather than valid.
