## Analog Found: BalanceHandler / StateDB desync in precompile-mediated balance updates

### Title
Recursive precompile calls with bank-triggered internal transfers can desync EVM StateDB balances from x/bank balances via `BalanceHandler` event-index tracking - ([File: precompiles/common/balance_handler.go])

### Summary
The C4 finding describes `USDMPegRecovery` tracking user deposits in isolated contract storage while the real pool balances diverge after a swap changes the pool's internal math — the "tracked" value and the "real" value fall out of sync, and withdrawals/settlement are computed against the wrong basis, risking locked/mismatched funds. The Cosmos EVM analog is the `BalanceHandler` used by every stateful precompile (`distribution`, `staking`, `ics20`, `bank`, `erc20`, `werc20`, etc.) to reconcile `x/bank` (the "real" ledger) with the EVM `StateDB` (the "tracked" ledger visible to contracts) after a precompile call mutates bank balances.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` before a precompile's native action runs, and `AfterBalanceChange` replays only the events emitted *after* that recorded index (`events[bh.prevEventsLen:]`) to translate `coin_spent`/`coin_received`/precisebank fractional-balance events into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) [2](#0-1) 

Each precompile call creates a *new* `BalanceHandler` from `p.BalanceHandlerFactory.NewBalanceHandler()` inside `runNativeAction`, and `BeforeBalanceChange`/`AfterBalanceChange` bracket the call to `action(ctx)`: [3](#0-2) 

The repo's own test suite explicitly documents that this "brackets by event index" design breaks under **recursive/nested precompile calls that share the underlying `EventManager`**: `evmd/tests/integration/balance_handler/balance_handler_test.go` states "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [4](#0-3) 

A second, closely related test suite (`ICS20RecursivePrecompileCallsTestSuite`) exercises exactly this pattern with a real economic flow: a contract performs an ICS20 transfer of a native-ERC20-backed token whose `_beforeTokenTransfer` hook re-enters and claims staking rewards (a nested precompile/bank-mutating call) before the outer ICS20 transfer completes. The suite's own comment says it "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated," and the two branches (reverting vs. non-reverting recursive call) produce materially different final bank balances / event counts / distributed rewards, confirming the accounting is sensitive to nesting order and revert behavior rather than being idempotent: [5](#0-4) [6](#0-5) 

This is the same failure mode as the C4 bug: one side of the system (StateDB balances visible to the EVM, i.e., what contracts and subsequent calls "see") is being derived from a positional snapshot (`prevEventsLen`) of a mutable shared log (`EventManager.Events()`), while the authoritative ledger (`x/bank`) is updated directly and correctly. When nested precompile calls interleave and each creates/overwrites tracking state relative to the same growing event list, the derived StateDB balance can diverge from the real bank balance — mirroring how the curve-LP-based internal accounting diverged from real pool balances after a swap changed the "real" state underneath a static internal formula.

### Impact Explanation
If StateDB balances diverge from `x/bank` balances for accounts/contracts involved in a nested precompile call chain (e.g., an ERC20 transfer hook that triggers an ICS20 transfer, staking delegate/undelegate, or distribution reward claim), this can produce:
- Incorrect balances reported to subsequent EVM opcodes/contract logic within the same or later transactions (accounting corruption of spendable value visible to contracts), and
- Downstream reverts/incorrect transfer amounts (as seen in the test where contract bank balance ends at 0 in one variant vs. 50 in another, and reward availability differs), which can manifest as funds becoming stuck or transferred amounts not matching what the contract's own logic (and therefore user expectations) computed.

This matches the "Critical … irreversible accounting corruption of spendable user value across native balances, EVM balances … or precompile-mediated assets" and "permanent freezing/locking … of user funds" impact categories, since the divergence is between the EVM-visible balance and the bank-settled balance for real, spendable tokens routed through precompiles (ICS20, staking, distribution, erc20/werc20).

### Likelihood Explanation
The trigger is unprivileged: any user can deploy an ERC20 with a transfer hook (`_beforeTokenTransfer`/`_afterTokenTransfer`) that calls back into a stateful precompile (staking, distribution, ICS20) during a conversion/transfer flow, exactly as demonstrated by the repository's own `ERC20RecursiveReverting`/`ERC20RecursiveNonReverting` test contracts and the `ICS20RecursivePrecompileCallsTestSuite`. This is a normal, permissionless contract-authoring pattern (recursive/reentrant precompile invocation via hooks), not a privileged or malicious-relayer scenario, so likelihood is meaningfully high wherever nested precompile calls are reachable from user-deployed contracts.

### Recommendation
Do not rely on a mutable, shared `EventManager` event-index snapshot to demarcate "this precompile call's" balance-changing events when calls can nest. Options:
- Use a per-call isolated event manager (e.g., `ctx.WithEventManager(sdk.NewEventManager())`) for the duration of each precompile's native action so `AfterBalanceChange` only ever sees events strictly produced by that call, regardless of nesting, then merge/re-emit events afterward.
- Or replace event-index bracketing with an explicit journal/diff of bank balances (before/after) per call frame, keyed by call depth, so `prevEventsLen` cannot be overwritten by a nested call sharing the same handler/factory state.
- Add invariant checks (as already done in `x/erc20` via `ErrBalanceInvariance`, see `x/erc20/keeper/msg_server.go`) comparing final StateDB-derived balances against `x/bank` balances after any precompile call completes, and fail loudly on mismatch instead of allowing silent divergence.

### Proof of Concept
The repository's own tests already constitute a working PoC:
1. `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile` — deploys a caller contract that recursively invokes a debug precompile, and asserts on the exact (bug-dependent) event/log counts resulting from the shared `BalanceHandler` instance's `prevEventsLen` being overwritten. [7](#0-6) 
2. `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go::TestHandleMsgTransfer` — deploys a native-ERC20 with a reentrant/reverting `_beforeTokenTransfer` hook that triggers a staking-rewards claim during an ICS20 transfer via the precompile, showing divergent final bank balances (`0` vs `50`) and reward-claim outcomes depending on whether the nested call reverts, directly demonstrating balance-accounting divergence driven by nested precompile calls. [8](#0-7) 

Note: I could not fully trace every call site that constructs/shares a `BalanceHandlerFactory`/`BalanceHandler` across nested precompile invocations (e.g., whether the ERC20/werc20/ICS20 precompiles pass down a factory instance that is reused vs. freshly created at each nesting level) due to index/context limits; a full reachability confirmation of the "same instance is shared" claim across the erc20-hook → ICS20 → staking/distribution call chain in production code (not just the test harness) would benefit from a Devin session with full repo access to trace `BalanceHandlerFactory` construction and passage through `x/erc20`, `precompiles/ics20`, and `x/vm` keeper call paths.

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
