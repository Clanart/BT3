Based on the pattern in the report — a state-update function gated by the *wrong* condition, letting a value drift out of sync with what the guard was meant to protect — the closest verified analog in this GitHub Desktop codebase is in the remote-URL auto-update logic.

### Title
Silent cross-host remote URL rewrite from GitHub API `clone_url` due to missing hostname check - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl` automatically rewrites the local `origin` remote URL whenever GitHub Desktop refreshes repository metadata from the API, but the guard conditions it uses (`protocolsMatch` and `remoteUrlUnchanged`) never verify that the **hostname** of the new `clone_url` matches the hostname of the existing remote before calling `gitStore.setRemoteURL()`. [1](#0-0) 

### Finding Description
The function computes three checks before mutating the remote:
- `urlsMatch`: whether the *current* remote already equals the new API-provided `clone_url` (only used to decide if an update is needed, not to constrain the new value).
- `protocolsMatch`: only compares the URL scheme (`https:` vs `ssh` is not even parseable by `URL.parse`, so this effectively only fires for `https` remotes).
- `remoteUrlUnchanged`: whether the current remote still equals the previously *cached* `gitHubRepository.cloneURL`, i.e., whether the user hasn't manually repointed the remote. [2](#0-1) 

None of these three checks compare the **hostname** of the old remote to the hostname of the new `apiRepo.clone_url`. `urlMatchesRemote`/`urlsMatch` in `repository-matching.ts` do parse and compare hostnames, but that comparison is only used to short-circuit unnecessary updates (`!urlsMatch`), not to reject the new value when the host differs. So if `apiRepo.clone_url` ever returns a value on a different host but the same scheme (`https`), and the local remote still matches the previously stored `gitHubRepository.cloneURL` (the common, unmodified case), the code proceeds to call:
```
await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
```
silently repointing `origin` to that new host, with no user confirmation and no re-validation that owner/name/host triple still line up. [3](#0-2) 

This is invoked as part of the periodic "refresh GitHub repository metadata" flow (`repositoryWithRefreshedGitHubRepository` in `app-store.ts`, which calls into `updateRemoteUrl`), meaning it runs automatically in the background whenever Desktop re-fetches the tracked repository object from the GitHub/GHE API — the exact "attacker controls a GitHub API object" primitive named as in-scope in this task.

### Impact Explanation
If the API response for the tracked repository's `clone_url` field can be influenced (e.g., a compromised/MITM'd GitHub Enterprise endpoint, or any scenario where the returned repository object doesn't match the true host the user intended to work with), Desktop will **silently corrupt the destination of the user's future `git push`/`git fetch` operations** by repointing `origin` to a different host, without any dialog or diff shown to the user. Because credential resolution in the trampoline helper is keyed off the remote's parsed hostname/endpoint (`findGitHubTrampolineAccount`, `getGenericCredential`), a subsequent push against the rewritten remote can trigger credential lookups/prompts scoped to the new host, risking token exposure or a user unknowingly pushing/pulling from an attacker-controlled repository. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
This requires the attacker to control or corrupt the specific API response used to refresh the tracked repository (same class of primitive named in scope: "a GitHub API object"). It does not require local access, admin rights, or pre-existing malware. The existing guards (`protocolsMatch`, `remoteUrlUnchanged`) give a false sense of safety but do not actually constrain the target host, so the path is not blocked by current code once the attacker-controlled API object condition is met.

### Recommendation
Add an explicit hostname equality check between the existing remote and `apiRepo.clone_url` before calling `setRemoteURL`, reusing `urlMatchesRemote`'s hostname-parsing logic but making it a required condition to *allow* the update to proceed. Alternatively, require the equivalent of `urlsMatch(oldCloneUrl, newCloneUrl)` on host only, or surface a confirmation prompt to the user whenever the remote host is about to change as a result of an automatic metadata refresh.

### Proof of Concept
1. Track a repository whose `gitHubRepository.cloneURL` and current git `origin` remote are `https://ghe.example.com/owner/repo.git` (unchanged by the user).
2. During a routine metadata refresh, the API response for that repository (`apiRepo.clone_url`) returns `https://attacker.example.com/owner/repo.git` (same scheme, different host) — e.g. due to a compromised/MITM'd GHE endpoint.
3. In `updateRemoteUrl`: `protocolsMatch` is `true` (both `https:`), `remoteUrlUnchanged` is `true` (git remote still equals the old cached `cloneURL`), `urlsMatch` is `false` (hostnames differ) → the condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is satisfied.
4. `gitStore.setRemoteURL('origin', 'https://attacker.example.com/owner/repo.git')` executes silently, with no user-visible warning, corrupting the destination of all future pushes/fetches for that repository. [6](#0-5)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
