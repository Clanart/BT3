### Title
Attacker-supplied identity nonce commitment in a FROST preprocess panics the BIP-340 `Hram`/`x()` path, aborting the signer — (File: `networks/bitcoin/src/crypto.rs`)

### Summary
The bug class from CVE-2015-8739 — a crafted input reaching code that asserts/panics instead of handling the case, producing a denial of service — maps onto Serai's FROST signing flow. A malicious (or merely faulting) counterparty's `Preprocess` message is deserialized via `SignMachine::read_preprocess` → `Commitments::read` → `GeneratorCommitments::read` → `C::read_G` (`crypto/frost/src/nonce.rs:34-36`, `crypto/frost/src/sign.rs:276-281`). The nonce commitments then flow into `B.nonces()` and `algorithm.sign_share(...)` / `algorithm.verify_share(...)`, which for the Bitcoin `Schnorr` algorithm calls `Hram::hram`, which calls `x(R)` — a function that explicitly `expect`s the point to be non-infinity.

### Finding Description
`x()` in `networks/bitcoin/src/crypto.rs:13-16` does:

```rust
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`Hram::hram` calls `x(R)` and `x(A)` unconditionally (`crypto.rs:59-67`), and the crate documents: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`) and "`verify`, `verify_share` MUST be called after `sign_share`... this library MAY panic" (`crypto.rs:82-83`).

The attacker-controlled `R` is the bound sum of nonce commitments `B.nonces(&nonces)` computed in `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:383`) from per-participant `GeneratorCommitments` read off the wire. There is no identity rejection visible in the deserialization path (`GeneratorCommitments::read` calls `C::read_G` twice with no `is_identity` check, `nonce.rs:34-36`), and nothing in `sign`/`complete` validates that the summed nonce `Rs` are non-infinity before `sign_share`/`verify_share`/`verify` invoke `hram`. A peer can therefore submit a preprocess whose (D, E) commitments are the identity point — or whose commitments sum to identity against an honest commitment — causing the aggregated nonce `R` passed to `x()` to be infinity, panicking the signing task.

A secondary, related panic surface exists in `AlgorithmSignatureMachine::complete` at `crypto/frost/src/sign.rs:477-479`: `responses[l]` is a direct `HashMap` index. If `validate_map` does not enforce that `shares` contains exactly `included() \ {i}`, an omitted share panics rather than erroring (I could not fully verify `validate_map`'s strictness; if it enforces exact membership this path is safe).

### Impact Explanation
A single crafted preprocess message deterministically crashes the signer's signing task/process during `sign`, `verify_share`, or `complete`. For the processor/validator embedding this algorithm, an uncaught panic halts that multisig's signing — a remote, unprivileged-party-reachable denial of service against threshold signing (and for panics in a shared task, potentially process exit, exactly the "assertion failure and application exit" shape of the CVE). Severity: Medium (availability only, no secret leakage).

### Likelihood Explanation
Reachable by any counterparty able to send a preprocess to a signer using the Bitcoin `Schnorr` algorithm: `read_preprocess` → `sign`/`complete`. The trigger is a constant (identity-encoded point or a commitment chosen to cancel an honest commitment in the binding-factor-weighted sum `D + rho*E`), so reliability is high. The main uncertainty is whether `Secp256k1::read_G` (kp256) rejects the SEC-1 identity encoding `0x00`; `k256`'s `from_bytes` accepts it, and no explicit identity check was found in the read path, but if a canonical-identity rejection exists upstream, the "sum-to-identity" variant still applies since it arises from arithmetic after deserialization.

### Recommendation
- Reject the identity point in `GeneratorCommitments::read` / `Commitments::read` (and generally in `C::read_G` for points used as nonces).
- After computing `Rs = B.nonces(&nonces)` in `sign`, assert non-identity and return `FrostError` instead of proceeding.
- Make `x()`/`Hram::hram` return an error/Option rather than `expect`/`panic` so malformed inputs cannot abort the signer.
- In `complete`, replace `responses[l]` with `responses.get(l).ok_or(FrostError::InvalidShare(*l))?`.

### Proof of Concept
```rust
// As a counterparty to an honest signer running the Bitcoin Schnorr algorithm:
// 1. Obtain the signer's preprocess (commitments D_s, E_s for participant i).
// 2. Read preprocess path feeds attacker bytes into GeneratorCommitments::read:
//    frost/src/nonce.rs:34  Ok(GeneratorCommitments([C::read_G(reader)?, C::read_G(reader)?]))
// 3. Craft preprocess whose commitments make the bound nonce identity:
//    - simplest: send D = E = identity encoding (0x00) if read_G accepts it, or
//    - send E = identity, D = -D_s (cancels the honest commitment after binding),
//      so the summed R over participants is the point at infinity.
// 4. Honest signer's AlgorithmSignMachine::sign computes Rs (sign.rs:383) and calls
//    algorithm.sign_share -> Hram::hram -> x(R) (crypto.rs:65),
//    hitting `encoded.x().expect("point at infinity")` (crypto.rs:15) -> panic.
// Same trigger reaches `verify`/`verify_share` in AlgorithmSignatureMachine::complete.
```
