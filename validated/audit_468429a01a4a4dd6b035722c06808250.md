### Title
Received/Reported outputs are not bound to the group key — arbitrary `ReceivedOutput` bytes are accepted as spendable inputs, so "received" funds may be unspendable - ([File: processor/src/networks/bitcoin.rs])

### Summary
`ReceivedOutput` consists of `(offset, TxOut, OutPoint)` and is freely deserializable via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`). `Output::key()` in `processor/src/networks/bitcoin.rs:112-122` then *derives* the owning key as `x_only_key(script_pubkey) - G * offset` instead of checking that the script equals `p2tr_script_buf(group_key + G * offset)`. Because the offset is attacker-controlled scalar data and `key()` performs the subtraction unconditionally, any `script_pubkey` can be paired with a chosen offset so that `key()` returns an arbitrary point — including the multisig group key. An output locked to a script the threshold group cannot sign for is therefore reported as a spendable `Output` of that group.

### Finding Description
- `Scanner::scan_transaction`/`scan_block` match outputs purely on `script_pubkey` and tag them with the registered offset (`networks/bitcoin/src/wallet/mod.rs:199-214`). That path is safe because the scanner only emits offsets it itself registered.
- The deserialization path is not: `ReceivedOutput::read` accepts a scalar `offset` and an arbitrary consensus-decoded `TxOut`/`OutPoint` with no binding between them (`networks/bitcoin/src/wallet/mod.rs:122-134`).
- `Output::read` wraps this (`processor/src/networks/bitcoin.rs:145-166`) and `Output::key()` reconstructs the key by subtracting `GENERATOR * offset` from the script's x-only key (`processor/src/networks/bitcoin.rs:112-122`). For any chosen script `S` (e.g. an attacker's own P2TR address) and target group key `K`, supplying `offset` such that `G*offset = script_point(S) - K` makes `key()` return `K`. No verification that `S == p2tr_script_buf(K + G*offset)` is performed anywhere on this path.
- `get_outputs` / the multisig scheduler then feed these `Output`s into `BSignableTransaction::new` (`processor/src/networks/bitcoin.rs:446-452`), which uses `input.offset` to build the signing keys (`networks/bitcoin/src/wallet/send.rs:175-185`). The produced signature will not satisfy the actual output script: the claimed balance is counted as received yet the resulting spend is invalid, or the output was never spendable by the group at all.

### Impact Explanation
The multisig's reported balance includes UTXOs that cannot be spent by the threshold key — analogous to ETH being trapped in `PythOracle.commit` with no withdrawal path. Plans consuming such outputs either burn plan capacity on transactions that can never complete or cause the scheduler to treat non-existent/unspendable value as available liquidity, permanently misaccounting funds until the malformed outputs are manually excluded.

### Likelihood Explanation
Requires untrusted `ReceivedOutput`/`Output` bytes to reach `Output::read` rather than being produced solely by `Scanner::scan_transaction`. If outputs are only ever produced by the local scanner over real blocks, the malformed-offset path is unreachable and the impact reduces to none. The severity is Medium contingent on outputs being (de)serialized across a trust boundary (scheduler/coordinator DB or cross-node messages), which the existence of `Output::read`/`write` strongly suggests.

### Recommendation
In `Output::read` (or at the point of use), recompute `p2tr_script_buf(group_key + GENERATOR * offset)` and reject outputs whose `script_pubkey` does not match, rather than trusting the serialized `(offset, script_pubkey)` pair. Alternatively, store the registered-script map and only accept outputs whose script appears in it.

### Proof of Concept
1. Let `K` be the victim multisig group key and `S` an attacker-controlled P2TR script with x-only key `P_S` (interpreted even, as in `Output::key`).
2. Set `offset = (P_S - K) / G` as a scalar, i.e. `offset * G = P_S - K`.
3. Serialize `Output { kind: External, output: ReceivedOutput { offset, TxOut{script_pubkey: S, value}, outpoint } }` via `Output::write`/`ReceivedOutput::write`.
4. When deserialized and `key()` is evaluated: `P_S - G*offset = P_S - (P_S - K) = K` — the output is attributed to group key `K` despite being locked to the attacker's script and never spendable by the group.

Note: I was unable to trace every call site of `Output::read` to confirm which deserialization contexts consume attacker-influenced bytes (e.g., coordinator-supplied output lists vs. locally scanned data); the finding's validity depends on that reachability as noted above.
