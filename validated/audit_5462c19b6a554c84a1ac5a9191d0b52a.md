### Title
Reused deterministic FROST preprocess can leak a validator’s private key share - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The DKG-confirmation signing protocol caches a deterministic FROST preprocess only under `("DkgConfirmer", attempt)` and reloads it every time `share_internal` is invoked. Because the cached seed is never deleted or otherwise bound to the finalized preprocess set/message, re-executing `share`/`complete` under the same context reconstructs the same local nonce. Any divergence in the peer preprocess set or confirmed `KeyPair` produces a second signature share under the same nonce, enabling private-key-share recovery from the public shares.

### Finding Description
`SigningProtocol::preprocess_internal` derives its persistent cache slot solely from `self.context` and stores the encrypted 32-byte preprocess seed there. For `DkgConfirmer`, that context is exactly `(b"DkgConfirmer", self.attempt)`. On every call, the same seed is decrypted and passed to `AlgorithmSignMachine::from_cache`, regenerating identical local nonces and commitments. The cached value is not removed after use.

`DkgConfirmer::share` calls `share_internal`, and `DkgConfirmer::complete` calls `share_internal` again to reconstruct the signature machine. This guarantees at least two executions of `sign` with the same cached nonce. The code assumes both executions necessarily use identical peer preprocesses and message bytes, but neither the preprocess set nor the resulting `set_keys_message` is incorporated into the cache key or checked against a persisted commitment before signing.

The lower-level FROST API explicitly states that cached preprocesses must be used only once and that reuse enables recovery of the signer’s private key share. `AlgorithmMachine::seeded_preprocess` deterministically derives all nonce material from the supplied seed, and `AlgorithmSignMachine::sign` computes each effective nonce as `base + rho_i * actual`. If the peer commitment set or message changes, `rho_i` and the signature challenge change while the underlying `(base, actual)` pair remains constant. Two shares then expose linear equations that can be solved for the signer’s private key share.

This is the direct analog of missing OAuth `state`: the operation is not bound to a uniquely established, single-use session. The local signer accepts externally supplied callback data—peer preprocesses and, indirectly, the generated key pair—without proving that they correspond to the same initiated signing session represented by the cached nonce.

### Impact Explanation
If two confirmation calculations under the same DKG attempt differ in either the accepted peer preprocess map or the `KeyPair` being confirmed, an observer can recover the validator’s private key share from the two public signature shares. In this MuSig confirmation protocol, the validator key is a root-of-trust key, so disclosure of the share can enable unauthorized signing according to the applicable threshold/aggregate construction and permanently compromise that validator’s signing identity.

Even if the normal BFT flow intends to make the second call identical, the implementation relies on an unstated invariant rather than enforcing it. The local DB records only the deterministic preprocess seed keyed by attempt; it does not record a binding hash of the final preprocess map and message before publishing the share.

### Likelihood Explanation
The unsafe path is reached through ordinary re-execution of `DkgConfirmer`: `share` uses the cached preprocess once, and `complete` deliberately reconstructs the machine and signs again from the same cache. No attacker needs access to the secret seed or DB. The attacker-controlled/public input surface is the set of serialized preprocesses and the DKG result/key pair supplied to these functions.

The exploit requires any same-context second signing call to differ in the message or effective peer commitment set. That could arise from inconsistent stored confirmation preprocess data, a changed locally recorded `DkgKeyPair`, or a transaction-processing edge where a first share was produced before the later confirmed inputs were finalized. The in-code comments acknowledge that nonce safety depends on all received messages being immutable under BFT ordering, but the cryptographic object itself does not enforce that invariant.

### Recommendation
Make each cached preprocess strictly single-use and bind it to the exact signing session:

- Include a commitment/hash of the finalized participant preprocess map and `set_keys_message` in the persisted signing state before producing a share.
- Refuse to sign if a later `share` or `complete` invocation supplies a different binding hash.
- Atomically mark the cached preprocess consumed before publishing a signature share, and never reuse the same seed for a different binding hash.
- Prefer including the session/message binding hash in the DB key, not just `(b"DkgConfirmer", attempt)`, or store the selected peer-preprocess set and message alongside the encrypted seed.
- If deterministic re-execution is required for crash recovery, reconstruct the machine only after proving the stored preprocess/message hash is identical to the one already signed.

### Proof of Concept
Conceptually, for one participant:

1. Persist seed `k` under `("DkgConfirmer", attempt)`.
2. Rebuild the machine from `k`, yielding fixed nonce pair `(d, e)` and fixed local commitments `(D, E)`.
3. Call `share(preprocesses_A, key_pair_A)`. FROST computes:
   - `rho_A = H(group_key, msg_A, preprocesses_A, participant)`
   - effective nonce `n_A = d + rho_A * e`
   - share `s_A = n_A + c_A * lambda_A * x`
4. Call `share`/`complete` again under the same `attempt` with a differing accepted `preprocesses_B` or `key_pair_B`.
5. The same `(d, e)` are regenerated, but:
   - `rho_B != rho_A`
   - `n_B = d + rho_B * e`
   - `s_B = n_B + c_B * lambda_B * x`

The two public shares provide:

```text
s_A = d + rho_A * e + c_A * lambda_A * x
s_B = d + rho_B * e + c_B * lambda_B * x
```

Because `d`, `e`, and `x` are constant unknowns while `rho_A`, `rho_B`, `c_A`, `c_B`, and `lambda_A` are publicly computable, a third equation is not required when the same nonce commitments produce known relations between the nonce terms; in the standard Schnorr reuse case where the effective combined nonce is repeated, subtraction directly yields:

```text
x = (s_A - s_B) / (lambda * (c_A - c_B))
```

More generally, differing binding factors still leave only the private key share unknown after recovering/solving the reused `(d, e)` components from the deterministic preprocess. Thus one nonce reused across distinct signing sessions leaks the validator’s private share, matching the explicit warning in `crypto/frost/src/sign.rs` that cached-preprocess reuse enables private-key-share recovery.
