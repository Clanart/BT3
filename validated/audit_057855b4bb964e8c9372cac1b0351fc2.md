### Title
Permanent, unrecoverable freezing of IBC-transferred funds at the module-derived isolated address when a destination callback contract fails to fully drain its approved allowance - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` sends IBC-transferred tokens to a deterministic "isolated address" (`GenerateIsolatedAddress`) that has no private key, approves the destination contract to pull the full amount, invokes the contract's calldata, and only afterward checks that the isolated address's balance is zero. Because the state produced by the EVM calls is committed via `writeFn()` *before* this balance check runs, the check can only detect the problem after the fact — it cannot prevent it. If the callback contract does not fully drain the approved amount (bug, edge-case rounding, or malicious construction), the residual tokens are left forever at an address nobody controls, with no bank/erc20/keeper method anywhere in the codebase to sweep or recover them.

### Finding Description
In `IBCReceivePacketCallback` [1](#0-0) , the receiver of the IBC packet must equal a module-derived `isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)` [2](#0-1) . This address is computed with `address.Module(...)`, i.e. it is not, and cannot be, controlled by any private key — it exists purely as a routing target for the callback flow.

The keeper then:
1. Uses a cached context (`cachedCtx, writeFn := ctx.CacheContext()`) to call `approve` on the ERC20 contract granting the destination contract an allowance for the full transferred amount, and to invoke the contract's calldata via `CallEVMWithData` [3](#0-2) .
2. Commits those state changes to the real context with `writeFn()` [4](#0-3) .
3. Only *after* committing, checks whether `isolatedAddr` still holds a nonzero ERC20 balance, and if so returns an error [5](#0-4) .

The code comment explicitly states the intent: *"This check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable."* However, because `writeFn()` already committed the approve + calldata execution before the check runs, the check cannot actually prevent anything — it can only report failure after the funds are already immovable. Returning an error here does not roll back the already-committed EVM state changes, and does not undo the fact that the transferred tokens now sit at `isolatedAddr`.

There is no sweep, admin-recovery, or reclaim function anywhere in the codebase for balances left at a `GenerateIsolatedAddress` output — a repo-wide search for `recoverToken`/`sweep`/`reclaim` found nothing relevant in the Cosmos EVM modules. Once tokens remain at `isolatedAddr` (e.g., because the destination contract's `transferFrom` call consumes less than the full approved amount, due to a bug, rounding, or a maliciously crafted contract), they are permanently locked: no key exists to sign a transaction from that address, and no protocol-level mechanism exists to move the balance out.

### Impact Explanation
This matches the "Critical permanent freezing/locking/theft of user funds" allowed impact: any IBC token transfer that carries a destination callback memo pointing at a contract which does not fully drain its allowance (whether due to developer error in a widely-used integration contract, or a purpose-built malicious contract that a user is tricked into targeting) results in permanent, irreversible loss of the transferred value with no recovery path. Because ICS20 callback flows are a normal, unprivileged part of IBC transfers (any sender can attach a destination-callback memo naming an arbitrary contract and calldata), this is reachable through ordinary transaction flow, not a privileged operation.

### Likelihood Explanation
Likelihood is moderate: it requires a destination callback contract that does not call `transferFrom` for the exact full amount (this is explicitly documented as a contract-integration requirement: *"contracts must implement an IERC20(token).transferFrom(msg.sender, address(this), amount) for the total amount, or the callback will fail"*). This can happen due to an honest bug in a third-party integration contract, an off-by-one/rounding condition, or a contract intentionally crafted to leave dust/full balance behind to grief users who are directed to interact with it. Given the callback contract address and calldata are attacker/sender-supplied via the transfer memo, an attacker fully controls this trigger path.

### Recommendation
Reorder the logic so the balance check happens against the cached context state *before* `writeFn()` commits, and only call `writeFn()` if the isolated address balance is verified to be zero. This restores the "prevent" behavior the comment describes instead of the current "detect after the damage is done" behavior. Separately, consider whether a protocol-level recovery mechanism (e.g., allowing the original `data.Sender` to reclaim any residual balance left at their own deterministically-derived isolated address after a callback failure) should be added, analogous to fixing the `SpiceAuction` issue by adding an explicit recovery path for value that ends up unroutable.

### Proof of Concept
Conceptual reproduction (cannot be executed without repo access/tooling in this session):
1. Deploy a destination contract whose callback function calls `IERC20(token).transferFrom(isolatedAddr, address(this), amount - 1)` (or simply forgets to transfer the full amount, or reverts internally after consuming only part of the allowance via multiple non-atomic calls).
2. Send an ICS20 transfer with a destination-callback memo targeting this contract with `receiver == isolatedAddr` for the given channel/sender pair.
3. On packet receipt, `IBCReceivePacketCallback` approves the full amount, invokes the contract, and `writeFn()` commits these changes to the chain state.
4. The subsequent balance check finds `receiverTokenBalance != 0` and returns an error, but by this point the approve/call already executed on-chain via `writeFn()`; the 1 unit (or full amount, depending on contract behavior) sitting at `isolatedAddr` cannot be transacted by anyone, since `isolatedAddr` has no corresponding private key and no keeper-level sweep function exists.

Note: I was unable to execute this against a live devnet in this session; the analysis is based on static code reading of `x/ibc/callbacks/keeper/keeper.go` and `x/ibc/callbacks/types/keys.go`. Confirming the exact commit/error-handling semantics of the surrounding `ProcessCallback` wrapper in `ibc-go`'s callback middleware (i.e., whether an error returned from `IBCReceivePacketCallback` triggers any additional rollback outside this function) would require deeper tracing into the `ibc-go` dependency, which is outside this repository's indexed code.

func (k ContractKeeper) IBCReceivePacketCallback(
	ctx sdk.Context,
	packet ibcexported.PacketI,
	ack ibcexported.Acknowledgement,
	contractAddress string,
	version string,
) error {
	data, err := transfertypes.UnmarshalPacketData(packet.GetData(), version, "")
	if err != nil {
		return err
	}

	cbData, isCbPacket, err := callbacktypes.GetCallbackData(data, version, packet.GetDestPort(), ctx.GasMeter().GasRemaining(), ctx.GasMeter().GasRemaining(), callbacktypes.DestinationCallbackKey)
	if err != nil {
		return err
	}
	if !isCbPacket {
		return nil
	}

	// `ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter,
	// so we need to generate a new infinite gas meter to run the EVM executions on.
	// Skipping this causes the EVM gas estimation function to deplete all Cosmos gas.
	// We re-add the actual EVM call gas used to the original context after the call is complete
	// with the gas retrieved from the EVM message result.
	cachedCtx, writeFn := ctx.CacheContext()
	cachedCtx = evmante.BuildEvmExecutionCtx(cachedCtx).
		WithGasMeter(evmtypes.NewInfiniteGasMeterWithLimit(cbData.CommitGasLimit))

	// receiver := sdk.MustAccAddressFromBech32(data.Receiver)
	receiver, err := sdk.AccAddressFromBech32(data.Receiver)
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"acc addr from bech32 conversion failed for receiver address: %s", data.Receiver)
	}
	receiverHex, err := utils.HexAddressFromBech32String(receiver.String())
	if err != nil {
		return errorsmod.Wrapf(types.ErrInvalidReceiverAddress,
			"hex address conversion failed for receiver address: %s", receiver)
	}

	// Generate secure isolated address from sender.
	isolatedAddr := types.GenerateIsolatedAddress(packet.GetDestChannel(), data.Sender)
	isolatedAddrHex := common.BytesToAddress(isolatedAddr.Bytes())

	acc := k.authKeeper.NewAccountWithAddress(ctx, receiver)
	k.authKeeper.SetAccount(ctx, acc)

// GenerateIsolatedAddress generates an isolated address for the given channel ID and sender address.
// This provides a safe address to call the receiver contract address with custom calldata
func GenerateIsolatedAddress(channelID string, sender string) sdk.AccAddress {
	return sdk.AccAddress(address.Module(ModuleName, []byte(channelID), []byte(sender))[:20])
}
