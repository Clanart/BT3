### Title
Bitcoin transactions can be replayed on a compatible hard fork because signatures lack chain binding - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` signs only the Taproot transaction digest and previous outputs, then `TransactionSignatureMachine::complete` attaches the resulting signatures without any chain, genesis, or fork-specific validation. If Bitcoin undergoes a compatible hard fork that preserves the relevant UTXOs and sighash rules, a published Serai transaction can be replayed on the fork and spend the duplicated outputs. [1](#0-0) [2](#0-1) 

### Finding Description
`SignableTransaction::multisig` creates one Schnorr machine per input after checking that each offset key corresponds to the previous output’s script. [3](#0-2)  During signing, each machine receives `cache.taproot_key_spend_signature_hash(i, &prevouts, TapSighashType::Default)`, where `prevouts` is simply `Prevouts::All(&self.tx.prevouts)`. [1](#0-0)  That digest commits to the transaction and its previous outputs, but Serai adds no chain ID, genesis hash, fork epoch, or post-signing canonical-chain check. `complete` then places each signature directly into the transaction witness and returns the transaction. [2](#0-1) 

The transaction identifier exposed by `SignableTransaction::txid` is also only the Bitcoin transaction ID, not an identifier bound to a particular fork. [4](#0-3) 

### Impact Explanation
After a compatible hard fork duplicates the UTXO set, an unprivileged observer can copy a signed Serai transaction from the canonical chain and broadcast it on the fork. Because the signature is valid for the same sighash and the referenced outpoints exist there, the fork accepts the replay and transfers the duplicated coins according to the original outputs. This can unexpectedly dispose of the fork-side assets represented by the same keys. [5](#0-4) 

### Likelihood Explanation
Exploitation requires a compatible hard fork that preserves both Bitcoin transaction validity and the relevant UTXOs. That is not routine, but it requires no private-key access or validator compromise: once the signed transaction is public, anyone can relay the same bytes on the fork. [2](#0-1) 

### Recommendation
Bind signing and completion to the intended chain. At minimum, record and verify a canonical genesis/checkpoint block hash before publishing or accepting completions. Where fork rules permit it, include a fork-specific commitment in the transaction or sighash path; otherwise treat preservation-of-UTXO hard forks as an operational migration event and rotate keys or invalidate pending plans before signing on the new chain.

### Proof of Concept
1. Construct and sign a `SignableTransaction` spending a Taproot output controlled by Serai.
2. Publish the returned transaction on canonical Bitcoin.
3. After a compatible hard fork that copies the UTXO set, submit the identical raw transaction to the fork.
4. The same signatures verify because they commit only to the transaction data and `Prevouts::All`; neither signing nor completion checks a chain identity. [1](#0-0) [2](#0-1)
