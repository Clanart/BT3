### Title
Unsigned timestamp subtraction in Bitcoin difficulty-retarget calculation inverts the timewarp defense, letting a prover mint an under-mined "valid" header-chain/total-work proof - (File: circuits-lib/src/header_chain/mod.rs)

### Summary
`calculate_new_difficulty` computes `last_timestamp - epoch_start_time` as a plain `u32` subtraction with no `checked_sub`/`saturating_sub` and no signed intermediate type, at [3](#0-2) . Bitcoin Core performs the equivalent computation as a signed 64-bit subtraction, so when the last block of an epoch has a timestamp earlier than the epoch's first block, the (legitimately negative) timespan is clamped to the **minimum** allowed timespan (`nPowTargetTimespan/4`), which *increases* difficulty and defeats "timewarp" manipulation. In this circuit, the same scenario underflows the unsigned `u32`, wrapping to a value near `u32::MAX`, which is instead clamped to the **maximum** allowed timespan (`EXPECTED_EPOCH_TIMESPAN*4`), *decreasing* difficulty — the exact opposite of Bitcoin consensus behavior for that input.

### Finding Description
The header-chain circuit is a self-contained, permissionless zkVM circuit: `header_chain_circuit` reads a `HeaderChainCircuitInput { method_id, prev_proof, block_headers }` from the host and applies `ChainState::apply_block_headers` [4](#0-3) . Its only per-block validations are: chain continuity (`prev_block_hash == best_block_hash`), the header's `bits` matching the circuit's *self-computed* `expected_bits`, PoW validity against that self-computed target, and the median-time-past rule (`block_time > median(prev_11_timestamps)`) at [5](#0-4) . Nothing ties `expected_bits`/`current_target_bits` to real Bitcoin network history beyond the circuit's own recursive computation from the (attacker-suppliable) block headers.

At every 2016-block epoch boundary, the next epoch's target is derived purely from `self.epoch_start_time` and the last header's `time` via `calculate_new_difficulty`:
```rust
let mut actual_timespan = last_timestamp - epoch_start_time;
if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
    actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
} else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
    actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
}
``` [6](#0-5) 

The median-time-past rule only constrains each new timestamp relative to the median of the *previous 11* timestamps — it does not prevent the cumulative sequence of 2016 timestamps within an epoch from trending below the epoch's starting timestamp. A prover who controls the header sequence (mining their own low-work private chain, choosing header timestamps freely subject only to the local median rule) can therefore arrange for the final header of an epoch to have `time < epoch_start_time`. Because the subtraction is unsigned `u32`, this underflows/wraps to a value just under `u32::MAX`, which is far above `EXPECTED_EPOCH_TIMESPAN * 4`, so the clamp forces `actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4` — the *maximum-timespan* branch, which lowers the next epoch's difficulty by 4x. In real Bitcoin (signed arithmetic), the same negative timespan is clamped to the *minimum*-timespan branch (`nPowTargetTimespan/4`), raising difficulty 4x instead. This is a direct sign inversion of Bitcoin's built-in timewarp-attack mitigation, and it is repeatable every epoch, letting difficulty be driven down compoundingly across the attacker-chosen header sequence rather than just once.

Because `assert_eq!(block_header.bits, expected_bits, ...)` at [7](#0-6)  only checks internal self-consistency (the circuit's own miscalculated `expected_bits`), a chain built this way is fully self-consistent and produces a valid header-chain circuit proof, even though it required far less real proof-of-work than an honest chain of the same claimed height/timespan would.

### Impact Explanation
This directly breaks the "a block hash committed versus a block hash proved" / "a false circuit claim proved" binding described by the bridge's threat model. The header-chain circuit's `total_work` is exactly the value the bridge circuit uses to arbitrate between an operator and challenging watchtowers: `total_work_and_watchtower_flags` extracts each watchtower's claimed `total_work` from a Work-Only Groth16 proof (itself built by recursively verifying a header-chain proof, see `work_only_circuit` at [8](#0-7) ), and `bridge_circuit` panics only if the operator's `hcp.chain_state.total_work` is *less* than the maximum watchtower `total_work` [9](#0-8) . Bitcoin's PoW rule is used here specifically as a canonical-chain-selection oracle ("the canonical Bitcoin blockchain is determined by the total Work done") per `docs/bridge-circuit.md`. If a party (operator or a colluding/adversarial watchtower) can cheaply mine a header sequence whose *claimed* `total_work` is inflated relative to the *real* hash-power actually expended — by repeatedly triggering the inverted difficulty-decrease clamp — they can fabricate a "more-work" or "less-work" claim that does not correspond to reality, letting an operator's forged claim appear to dominate an honest watchtower's correct challenge (or vice versa). This can let a dishonest party win the total-work comparison it should have lost, enabling a false circuit claim to be proved (a payout/disprove outcome resolved incorrectly on-chain) — a Critical-class outcome under the stated impact list.

### Likelihood Explanation
Exploitation requires no privileged role: anyone able to generate header-chain/work-only proofs (an operator or a watchtower) can supply their own `block_headers`. The prerequisite genuine PoW cost for the first epoch is unavoidable, but once the attacker reaches an epoch boundary they can choose the final header's timestamp to be below the epoch's start timestamp while still satisfying the local median-of-11 rule (a large design space over 2016 blocks), triggering the inverted clamp every epoch and compounding the effect. This is a deterministic, non-probabilistic bug (no hash grinding needed beyond ordinary mining) — likelihood is meaningfully higher than a generic theoretical concern, though it does still require sustained control over a private mining sequence over multiple epochs to compound the effect materially.

### Recommendation
Compute `actual_timespan` using a signed intermediate (e.g. `i64`) as Bitcoin Core does, or use `last_timestamp.checked_sub(epoch_start_time)` and explicitly map the `None` (underflow) case to the minimum-timespan clamp (`EXPECTED_EPOCH_TIMESPAN / 4`), matching Bitcoin's actual consensus behavior instead of silently wrapping to the maximum-timespan clamp.

### Proof of Concept
1. Bootstrap a `GenesisBlock` chain state (or start from `get_chain_state_from_height` at an arbitrary real height) and set `epoch_start_time = T0` for the new epoch (this happens automatically at the epoch's first header).
2. Mine 2015 further headers, choosing each header's `time` field so that it still satisfies `validate_timestamp` (`> median(prev_11_timestamps)`) but so that the *last* header of the epoch has `time < T0` (achievable because the median rule is local to the last 11 blocks and does not compare against `epoch_start_time`).
3. Feed this `block_headers` vector into `header_chain_circuit`; at the epoch boundary, `calculate_new_difficulty(T0, last_timestamp, bits)` computes `last_timestamp - T0` which underflows `u32`, wraps near `u32::MAX`, is clamped to `EXPECTED_EPOCH_TIMESPAN * 4`, and yields a target 4x easier than Bitcoin consensus would have produced for the same (negative) real timespan.
4. Use this reduced target to mine the next epoch's 2016 blocks far more cheaply than real proof-of-work would require, inflating `chain_state.total_work` relative to genuine work; repeat across epochs to compound the effect, then submit the resulting header-chain/work-only proof as either an operator's HCP or a watchtower's Work-Only proof in `total_work_and_watchtower_flags` to skew the total-work comparison in `bridge_circuit`.
