### Title
Manipulating `getRewardablePercentWAD` via `cancelUnlock` on an expired cool-down slot to bypass reward forfeiture - ([File: VLMGP.sol], [File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder._sendReward` computes the forfeit on a user's pending `userRewards` using the *current* value of `VLMGP.getRewardablePercentWAD(account)` at claim time, rather than the value that prevailed while the reward accrued. Because `cancelUnlock(_slotIndex)` instantly converts an expired-but-unwithdrawn cool-down slot back into "fully locked" balance, calling it immediately before triggering `getReward` raises `getRewardablePercentWAD` and lets the caller claim a larger share of `userRewards` than the diminishing-forfeit schedule intended, at the expense of the forfeit pool that funds other lockers.

### Finding Description
`_sendReward` applies the forfeit lazily at withdrawal time: [1](#0-0) 

The forfeit fraction comes from `_calExpireForfeit`, which uses `vlMGP.getRewardablePercentWAD(_account)`: [2](#0-1) 

`getRewardablePercentWAD` weights fully-locked balance at 100%, still-cooling-down balance at 100%, but an *expired, unclaimed* cool-down slot (`block.timestamp > endTime`) is weighted by a decaying factor `(endTime-startTime)/(timeNow-startTime)`, which strictly decreases the longer the user leaves the expired slot unclaimed: [3](#0-2) 

`cancelUnlock` lets the user zero out `slot.amountInCoolDown` for that slot with no time-boundary restriction beyond `_checkInCoolDown` (which, unlike `unlock()`, does not require the slot to still be within the cool-down window before `endTime`): [4](#0-3) 

Because `getUserTotalLocked` subtracts `getUserAmountInCoolDown` from the user's total balance in MasterMagpie, zeroing `slot.amountInCoolDown` instantly moves that amount from the "expired, decaying-weight" bucket into the "fully locked, 100%-weight" bucket, without changing the user's total `balanceOf` used for reward accrual: [5](#0-4) 

Reward accrual itself (`_earned`/`_updateFor`) only depends on `balanceOf(_account)` and the global `rewardPerToken` index, and is indifferent to lock/cool-down state — the state-dependent haircut is applied only once, at `_sendReward` time: [6](#0-5) 

Exploit sequence for an unprivileged user who already has pending `userRewards[token][account] > 0` and an expired, unclaimed cool-down slot:
1. Call `VLMGP.cancelUnlock(_slotIndex)` on the expired slot — no permission needed, `whenNotPaused` only.
2. Immediately (same block, or via a batching contract in the same transaction) trigger `getReward(account, receiver)` through MasterMagpie.
3. `_calExpireForfeit` now sees a higher `getRewardablePercentWAD`, so `forfeitAmount` is smaller (or zero) than it would have been had the user claimed with the slot still expired, and `toSend` is inflated.

The forfeited difference would otherwise be re-queued into the reward pool via `_queueNewRewardsWithoutTransfer`, increasing `rewardPerTokenStored` for all other stakers. By timing `cancelUnlock` before `getReward`, the user diverts that amount to themselves instead of the pool.

### Impact Explanation
This is a theft of unclaimed yield: reward amounts that the forfeiture schedule intends for redistribution to other `vlMGP` lockers are instead captured by the user who manipulates the timing of `cancelUnlock` vs. `getReward`. This matches the Immunefi "theft of unclaimed yield" impact class. The magnitude is bounded by the user's own pending `userRewards` and how long their slot sat expired (the longer it decayed, the bigger the forfeit avoided).

### Likelihood Explanation
- No privileged role needed; any account holding locked MGP with a naturally expired (>`endTime`), unclaimed cool-down slot can do this.
- No capital beyond normal locking/unlocking behavior is required.
- Fully repeatable each time a user lets a cool-down slot expire and accrues rewards before withdrawing/relocking.
- Requires only ordinary transaction sequencing (two txs in the same block, or one tx through a helper contract) — not third-party front-running, matching the question's framing.
- Note: I could not directly view the body of `_checkInCoolDown` in `VLMGP.sol` (only its call sites were confirmed); the analysis assumes it only checks `slot.amountInCoolDown > 0` and not `block.timestamp <= endTime`, consistent with `unlock()` having a *separate*, explicit `StillInCoolDown` check that `cancelUnlock` lacks, and with `forceUnLock`'s penalty math tolerating `block.timestamp > endTime`. This assumption should be verified directly against the deployed source if precise confirmation is required.

### Recommendation
Snapshot/apply the forfeit percentage at reward-accrual time (e.g., inside `_updateFor`/`updateRewards`, before any state-changing lock actions can alter `getRewardablePercentWAD`), rather than lazily at `_sendReward` time. Alternatively, make `getRewardablePercentWAD` monotonic with respect to `cancelUnlock`/relocking transitions relative to already-accrued-but-unclaimed reward buckets, e.g., by tracking a per-slot "decayed value already forfeited" so that canceling an expired slot cannot retroactively reduce forfeiture on rewards that accrued while the slot was in its decaying state.

### Proof of Concept
Hardhat test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, and MGP/reward tokens per existing test fixtures.
2. User locks MGP, then calls `startUnlock` for part of the balance to create a cool-down slot; advance time past `coolDownInSecs` so the slot is expired but not withdrawn.
3. Queue reward tokens via `queueNewRewards` so `rewardPerTokenStored` increases while the slot remains expired and unclaimed (let some time pass so `getRewardablePercentWAD` reflects meaningful decay), producing `userRewards[token][account] > 0`.
4. Branch A (baseline): directly call `getReward(account, receiver)` (via MasterMagpie) without canceling; record `toSend` from the `RewardPaid` event and confirm `toSend < userRewards` (forfeit > 0), and confirm the forfeited amount was queued via `ForfeitRewardAdded`.
5. Branch B (exploit): in the same block, first call `VLMGP.cancelUnlock(_slotIndex)` on the expired slot, then call `getReward(account, receiver)`; record `toSend` from `RewardPaid`.
6. Assert `toSend_B > toSend_A` for the same starting `userRewards`, and ideally `toSend_B == userRewards` (full amount, zero forfeit) while `toSend_A < userRewards`, demonstrating the pro-rated forfeit was bypassed by sequencing `cancelUnlock` before `getReward`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
