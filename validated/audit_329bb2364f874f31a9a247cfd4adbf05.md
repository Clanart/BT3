### Title
Missing upper-bound and calendar-field validation in `upb` JSON `Timestamp` decoder silently accepts and stores out-of-range values - (File: `upb/json/decode.c`)

### Summary
The external report describes a smart-contract bug where an attacker/DAO-controlled 64-bit value (`vestExpiry`) is narrowed to `uint32` without a bounds check, silently producing a wrong (zero) result instead of reverting, causing a funder to silently lose entitlement. The transferable invariant is: *an attacker-controlled numeric input must be range/format validated before being trusted; if validation is incomplete, out-of-range input is silently accepted and stored as a semantically wrong value instead of being rejected.*

In this Protobuf checkout, the `upb` JSON decoder for the `google.protobuf.Timestamp` well-known type, `jsondec_timestamp()` in `upb/json/decode.c`, performs the analogous mistake: it validates the **lower** bound of `seconds` but never validates the **upper** bound, and it never validates that the calendar fields (`month`, `day`, `hour`, `minute`, `second`) fall within their legal ranges. It only checks that each field has the correct number of decimal digits and the correct separator character.

### Finding Description
`jsondec_tsdigits()` (`upb/json/decode.c:1072-1090`) only checks digit count and the trailing separator character; it performs no range validation: [1](#0-0) 

`jsondec_timestamp()` then feeds these unchecked fields straight into `jsondec_unixtime()`/`jsondec_epochdays()` and stores the resulting `seconds`/`nanos` into the message, checking only the lower bound of the well-known-type range (`-62135596800`, i.e. `TimeUtil::kTimestampMinSeconds`) and never the upper bound (`TimeUtil::kTimestampMaxSeconds = 253402300799`, defined in `src/google/protobuf/util/time_util.h:39-41`): [2](#0-1) [3](#0-2) 

Compare this to the conformance-test expectations for the Timestamp well-known type, which require `TimestampJsonInputTooLarge`, `TimestampJsonInputMonthTooLarge`, `TimestampJsonInputDayTooLarge`, `TimestampJsonInputHourTooLarge`, `TimestampJsonInputMinuteTooLarge`, and `TimestampJsonInputSecondTooLarge` to all be rejected as parse failures: [4](#0-3) 

The `upb` decoder as shown does not implement any of these calendar-range checks (month ≤ 12, day ≤ 31, hour ≤ 23, minute ≤ 59, second ≤ 59) nor an upper-seconds-bound check — it only validates digit width/separators and the *lower* seconds bound. This mirrors the "narrow without validating" pattern in the external report: a formally well-shaped attacker input (`"9999-99-99T99:99:99Z"`, or any month/day/hour/min/sec digit sequence outside the calendar's valid range) is accepted where it should be rejected, and the arithmetic in `jsondec_epochdays`/`jsondec_unixtime` silently produces an incorrect `seconds` value that is then stored into the message as if it were a valid, spec-conformant `Timestamp`. `php/ext/google/protobuf/php-upb.c` embeds byte-identical logic, so the PHP and Ruby native extensions built on `upb` inherit the same gap: [5](#0-4) 

### Impact Explanation
A client sending bounded, well-formed-looking JSON containing a `Timestamp` field with an out-of-calendar-range or excessively large date (e.g., large year, month/day > valid range) to any consuming application that parses ProtoJSON via `upb` (PHP/Ruby bindings, or any `upb`-based JSON front end) will have that value silently accepted and stored as a `Timestamp` message with an incorrect (and possibly out-of-spec) `seconds`/`nanos` pair, rather than the parse being rejected as required by the well-known-type contract and by the project's own conformance suite. Application logic that trusts a successfully-parsed `Timestamp` to be within `[kTimestampMinSeconds, kTimestampMaxSeconds]` and calendar-valid (e.g., expiry checks, TTL/vesting-style logic, ordering/policy decisions) can therefore silently compute wrong results — directly analogous to the reported bug's "funder receives no tokens for a long time because the vesting value was silently miscomputed rather than rejected." This is a data-integrity/logic-correctness issue at the JSON parsing boundary, not a crash or memory-safety bug.

### Likelihood Explanation
Likelihood is high for any consumer of `upb`'s ProtoJSON parser (PHP/Ruby extensions) that accepts `Timestamp` fields from untrusted JSON input: no special privileges are needed, the payload is a normal, bounded JSON string that passes the digit/separator format check, and the missing checks are directly exercised by digit values that are simply outside the calendar's legal range. The C++ `json/internal/parser.cc` path was examined for the same gap; only the presence/format checks (`year != 0`, `mon != 0`, `day != 0`) were confirmed within the reviewed range, and time did not allow confirming whether an upper-bound/calendar-range check exists later in that function or in a caller — this remains **unverified** for the C++ path and should be checked separately before drawing conclusions about it.

### Recommendation
In `jsondec_timestamp()` (`upb/json/decode.c`) and the mirrored `php-upb.c` implementation, validate `month` (1–12), `day` (1–31, ideally month/leap-year aware), `hour` (0–23), `minute` (0–59), `second` (0–59) immediately after parsing each field, and add an explicit upper-bound check `seconds.int64_val > 253402300799` (mirroring the existing lower-bound check and `TimeUtil::kTimestampMaxSeconds`) before storing the value into the message, rejecting the input with `jsondec_err` on any violation — matching the validation already required by the conformance test suite.

### Proof of Concept
Not executed (no terminal access in this session); the following is the minimal reproduction to be run against a `upb`-based ProtoJSON parser (e.g., through the PHP or Ruby protobuf extension, or a small C harness calling `upb_JsonDecode` on a `Timestamp` message):
```
Input JSON: {"seconds_wrapper_field_of_type_Timestamp": "9999-99-99T99:99:99Z"}
```
Expected (per conformance suite, `TimestampJsonInputMonthTooLarge`/`DayTooLarge`/etc.): parse failure.
Actual (per code at `upb/json/decode.c:1128-1194`): `jsondec_tsdigits` accepts `mon=99`, `day=99`, `hour=99`, `min=99`, `sec=99` because it only checks digit-count and separator; `jsondec_epochdays`/`jsondec_unixtime` compute an arithmetic (but semantically invalid) `seconds` value; only the lower-bound check `seconds.int64_val < -62135596800` is applied (it will not trigger for this input), so the message is populated with a bogus `Timestamp` instead of the parse being rejected.

static int jsondec_tsdigits(jsondec* d, const char** ptr, size_t digits,
                            const char* after) {
  uint64_t val;
  const char* p = *ptr;
  const char* end = p + digits;
  size_t after_len = after ? strlen(after) : 0;

  UPB_ASSERT(digits <= 9); /* int can't overflow. */

  if (jsondec_buftouint64(d, p, end, &val) != end ||
      (after_len && memcmp(end, after, after_len) != 0)) {
    jsondec_err(d, "Malformed timestamp");
  }

  UPB_ASSERT(val < INT_MAX);

  *ptr = end + after_len;
  return (int)val;
}

static void jsondec_timestamp(jsondec* d, upb_Message* msg,
                              const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

  if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
  return;

malformed:
  jsondec_err(d, "Malformed timestamp");
}

  return (int64_t)jsondec_epochdays(y, m, d) * 86400 + h * 3600 + min * 60 + s;
}
