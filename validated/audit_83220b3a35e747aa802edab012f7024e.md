### Title
Copilot conflict resolution silently mismatches hunk-to-resolution mapping via array-order splicing with no content verification - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The ACO bug's root cause is a loop that maps a state-mutable, attacker-influenced collection to actions purely by array position/index, with no re-verification of identity at the moment the action is applied — allowing a crafted state to desynchronize "which item gets acted upon." The closest verified analog in this codebase is `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`, which splices an LLM's per-hunk conflict resolutions back into the on-disk file **purely by ordinal index** (`hunkIndex`), never re-validating that resolution `N` still corresponds to conflict block `N` in the actual file content at splice time.

### Finding Description
`extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts:179-279`) walks a conflicted file's text and produces an ordered list of `IConflictHunk` records used to build the prompt sent to Copilot. Later, `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) re-walks the **same raw file content string** and, for every syntactically well-formed marker block it encounters (`<<<<<<<` ... `=======` ... `>>>>>>>`), splices in `hunkResolutions[hunkIndex]` — advancing `hunkIndex` by one for every block, matched "by order, not by line number" as the code comment itself states (line 535). [1](#0-0) 

`validateResolutionPaths` (lines 473-521) only checks that the **count** of hunks returned by the model equals the count originally extracted per file — it never validates that hunk *contents* (ours/theirs text) still match what's on disk at reassembly time: [2](#0-1) 

This is structurally the same broken invariant as the ACOToken bug: a collection is processed by position, an item can be "skipped" or "merged" based on a state condition it satisfies (in ACOToken, a balance threshold; here, a malformed/ambiguous marker sequence in the file being merged), and the consumer of the loop's output (`_exerciseAccount` / `reassembleResolvedFile`) never re-checks that the entity it's acting on is the one it thinks it is.

Two separate desynchronization paths exist:
1. **Malformed-marker skip asymmetry.** `extractConflictHunks` silently drops a hunk if no closing `>>>>>>>` is ever found (`app/src/lib/copilot-conflict-context.ts:240-242`), while consuming lines greedily until either a fresh `theirsMarker` appears or EOF — it does not stop at an intervening, unrelated `<<<<<<<` belonging to the *next* conflict. A specially crafted merge conflict in an attacker-controlled branch (e.g., text inside one side's content that happens to look like a bare `<<<<<<<`/`=======`/`>>>>>>>` sequence without matching the strict 7-character/whitespace-anchored regex used for extraction, or an intentionally unterminated first marker) can cause `extractConflictHunks` to report fewer/merged hunks than the boundaries `reassembleResolvedFile` later walks independently over the same raw text, because both functions re-derive hunk boundaries from the raw string using near-identical but independently-implemented regex/loop logic rather than sharing a single source of truth or embedding any positional/content anchor in the resolution payload.
2. **Pure ordinal trust of LLM output.** Even absent a parsing divergence, `reassembleResolvedFile` has no way to verify that `hunkResolutions[k]` was actually computed for the `k`-th conflict block in the file the user is looking at — it trusts strict index alignment between what was *sent* to the model and what is *spliced back*, with the model's output itself derived from attacker-influenced merge content (a hostile remote branch or PR).

### Impact Explanation
If hunk index alignment is broken, the app silently writes the **wrong resolved content into the wrong conflict region** of a file the user is about to commit — e.g., splicing a resolution intended for a benign hunk into a different hunk (or vice versa), producing a file that looks resolved (no more conflict markers) but contains logic transplanted from an unrelated conflict block. This is a silent corruption of what the user commits/pushes, matching the "Valid Impact" criterion for corruption caused by an attacker-controlled cloned/fetched repository (a hostile branch merged into the user's repo). Because the reassembly path removes all conflict markers and produces what appears to be a clean merge, the user has no visual signal that content was misassigned before committing and pushing it.

### Likelihood Explanation
This requires the attacker only to control content in a branch/commit that the victim merges, rebases, or cherry-picks against using GitHub Desktop's Copilot-assisted conflict resolution — no local access, admin rights, or prior compromise is needed. It does depend on crafting a conflict payload that causes the two independently-implemented boundary-detection passes (extraction vs. reassembly) to disagree, or on influencing the LLM to reorder/omit array-order output; the existing count-only validation (`validateResolutionPaths`) would not catch a same-count-but-misordered/misaligned splice. Exploit reliability is therefore harder to guarantee than in a deterministic ACOToken-style balance check, since it depends on regex edge cases and on the model's raw JSON output ordering, which I could not fully verify end-to-end within the available context (e.g., I could not confirm what constraints, if any, exist elsewhere in the AI conflict-resolution UI code that might re-render or diff the resolved file for the user before commit).

### Recommendation
Do not match hunk resolutions to conflict blocks by array order alone. Embed an explicit identity anchor per hunk (e.g., a stable hunk id, or the original `oursContent`/`theirsContent` hash) in both the extraction output and the model's response schema, and have `reassembleResolvedFile` verify that the block it is about to replace matches the expected hunk identity before splicing — refusing (or flagging for manual review) any resolution whose anchor doesn't match the corresponding on-disk block. Additionally, unify marker-boundary parsing into a single shared implementation used by both `extractConflictHunks` and `reassembleResolvedFile` so the two passes can never diverge on what constitutes a hunk boundary.

### Proof of Concept
Conceptual PoC (not fully verified against the live LLM pipeline, since the model-output ordering step is outside local code):
1. Attacker crafts a branch such that merging it into the victim's branch produces a conflicted file containing an early conflict block whose "theirs" content embeds text resembling a `<<<<<<<`/`=======` sequence that doesn't satisfy the strict `/^<{7}(?:\s|$)/` anchor (e.g., indented or with extra characters) followed later by a genuine, well-formed conflict block.
2. `extractConflictHunks` and `reassembleResolvedFile`, parsing the same raw string independently, can be driven to disagree on how many/which conflict blocks exist purely due to subtle differences in how each loop handles an unterminated or ambiguous marker sequence (see `app/src/lib/copilot-conflict-context.ts:228-242` vs. `app/src/lib/copilot-conflict-resolution.ts:559-596`).
3. When `reassembleResolvedFile` walks the file to splice resolutions back in, `hunkIndex` no longer lines up with the hunk the resolution text was actually generated for, so the wrong resolved content is written into a conflict region, and the resulting file is committed as if fully and correctly resolved.
