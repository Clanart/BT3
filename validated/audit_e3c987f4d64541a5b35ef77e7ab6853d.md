### Title
Divide-by-Zero Crash in Mempool Block-Bundle Assembly via Fully-Deduplicated Spend - ([File: chia/full_node/mempool.py])

### Summary
`Mempool.create_bundle_from_mempool_items` computes a per-item cost as `item_cost = cost - cost_saving` and immediately divides by it (`fee / item_cost`) inside a logging call, with no zero-guard on `item_cost`, unlike the sibling `MempoolManager.validate_spend_bundle` path which explicitly rejects `cost == 0` before doing any division. [1](#0-0) [2](#0-1) 

### Finding Description
`cost` is the mempool item's total CLVM execution cost (`item.conds.cost`), and `cost_saving` is the sum of per-coin-spend costs (`DedupCoinSpend.cost`) for every coin spend in the item that `IdenticalSpendDedup.get_deduplication_info` finds already deduplicated against a previously-selected mempool item's identical spend (same coin, same solution). [3](#0-2) [4](#0-3) 

An unprivileged spend-bundle submitter can craft two spend bundles that spend the same coin with byte-identical solutions (a standard dedup-eligible pattern), then submit a follow-on spend bundle whose only coin spend duplicates an already-committed dedup entry. If the per-spend cost recorded for that coin (`spend_data.cost`) fully accounts for the item's total execution cost (e.g., a minimal single-spend bundle), `cost_saving` can equal `cost`, driving `item_cost` to `0`. The subsequent `fee / item_cost` on line 668 is an eagerly-evaluated Python expression passed as a logging argument — it is **not** lazily deferred by the logging framework — so a `ZeroDivisionError` is raised unconditionally at that point regardless of the configured log level. [1](#0-0) 

This code path executes inside `create_bundle_from_mempool_items`, which is invoked whenever the full node assembles a block template from the mempool (`create_block_generator`), a routine, mempool-driven operation triggered indirectly by ordinary spend-bundle admission and block-farming cadence — not requiring any privileged access, malicious peer, or malicious farmer behavior. [5](#0-4) 

### Impact Explanation
An uncaught `ZeroDivisionError` raised during block-bundle assembly would propagate out of `create_bundle_from_mempool_items`/`create_block_generator` unless caught by a broader handler I could not fully confirm within this investigation. If uncaught, this halts the transaction-processing/block-building routine on any full node that reaches this code path with the crafted mempool state, which maps to the "spend-triggered transaction-processing halt" impact category in scope for this report.

### Likelihood Explanation
Reaching this exact condition requires: (1) submitting a spend bundle with a dedup-eligible coin spend that gets admitted and selected for a block, (2) submitting a second spend bundle whose *entire* cost is attributable to a coin spend identical to (1)'s, so that `cost_saving == cost` for that item. Whether `cost_saving` (sum of per-coin-spend costs) can be made to exactly equal `cost` (the item's total `conds.cost`, which may include additional fixed/generator overhead not attributed to any single coin spend) is the key open question I was unable to fully verify given the available code — this determines whether `item_cost` can reach exactly zero versus only near-zero. This uncertainty should be resolved by a deeper trace of how `BundleCoinSpend.cost` is computed relative to `SpendBundleConditions.cost` in `chia_rs`, and by confirming the exception-handling scope around lines 629–735 of `mempool.py`, before treating this as a confirmed, exploitable crash.

### Recommendation
Add an explicit guard before the division, mirroring the existing `cost == 0` check in `MempoolManager.validate_spend_bundle`:
```python
item_cost = cost - cost_saving
fee_per_cost_log = fee / item_cost if item_cost > 0 else 0
log.info("Cumulative cost: %d, fee per cost: %0.4f, item cost: %d", cost_sum, fee_per_cost_log, item_cost)
```
Additionally, verify/enforce invariants in `IdenticalSpendDedup.get_deduplication_info` so `cost_saving` can never reach or exceed an item's `cost`, and confirm this arithmetic is not similarly unguarded in `create_block_generator2`'s equivalent batch-cost accounting. [6](#0-5) 

### Proof of Concept
1. Submit spend bundle A spending coin C with solution S (marks the spend dedup-eligible); it is admitted to the mempool.
2. Wait for a block-building cycle where A's spend of C is selected and recorded into `IdenticalSpendDedup.deduplication_spends` via `update_deduplication_spends`.
3. Submit spend bundle B, a single-coin-spend bundle that also spends (a distinct, but identically-solution-shaped) coin using solution S, chosen so that its `BundleCoinSpend.cost` is engineered to equal B's full `conds.cost`.
4. On the next `create_bundle_from_mempool_items` call, B's `cost_saving` equals `cost`, producing `item_cost = 0` and triggering `fee / item_cost` → `ZeroDivisionError` at chia/full_node/mempool.py:668.

*(Exact reproduction depends on confirming the per-spend vs. total-item cost accounting noted above, which I could not fully verify within the scope of this investigation.)*
