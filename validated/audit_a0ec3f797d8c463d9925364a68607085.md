### Title
Receipt tokens burned from the wrong account (`PoolHelper` instead of the withdrawing user) causes withdrawals to permanently revert - ([File: wombat/WombatPoolHelper.sol])

### Summary
This codebase contains the same bug class as the reported `CreditCaller` issue: a token that was minted/transferred to one account is later burned from a *different* account. In `WombatStaking`, receipt tokens are minted to the pool helper contract on deposit, but on withdraw they are unstaked directly to the end user's wallet via `MasterMagpie.withdrawFor`, while `burnReceiptToken` still burns from `msg.sender` (the pool helper), not from the account that actually holds the tokens.

### Finding Description
On deposit, `WombatStaking.deposit()` mints the pool's receipt token to `msg.sender`, which is the calling `PoolHelper` contract, not the end user: [1](#0-0) 

The helper then stakes these receipt tokens into `MasterMagpie` on behalf of the user via `depositFor`, transferring custody of the receipt token from the helper into `MasterMagpie` itself. This is confirmed by `BaseRewardPoolV2`, which tracks staked balances by reading `IMasterMagpie(operator).stakingInfo(...)` and computes `totalStaked()` as `IERC20(stakingToken).balanceOf(operator)` — i.e., `MasterMagpie` (the operator), not the pool helper, is the actual custodian of receipt tokens once staked: [2](#0-1) 

On withdrawal, the pool helper's `withdraw()` function performs three actions in sequence:
1. `WombatStaking.withdraw()` sends the underlying deposit token directly to `msg.sender` (the user).
2. `_unstake()` calls `MasterMagpie.withdrawFor(stakingToken, _amount, _sender)`, where `_sender` is the withdrawing user — this returns the receipt token directly to the user's wallet (per the `withdrawFor` natspec: "`_for` address of the user to withdraw for, and also harvested reward will be sent to").
3. `WombatStaking.burnReceiptToken(lpToken, _liquidity)` is then called, which burns from `msg.sender` of that call — i.e., the `PoolHelper` contract itself, not the user who now actually holds the receipt tokens. [3](#0-2) [4](#0-3) [5](#0-4) 

Because the receipt tokens are unstaked to the user's address (step 2) but the burn attempts to reduce the pool helper's own balance (step 3), the helper contract does not hold a sufficient balance of receipt tokens to satisfy the burn, causing the whole withdrawal transaction to revert. This affects `WombatPoolHelper.sol`, `WombatPoolHelperV2.sol`, and `AnkrBNBPoolHelper.sol`, all of which share this identical withdraw/burn pattern: [6](#0-5) [7](#0-6) 

### Impact Explanation
Since Solidity transactions are atomic, the underlying token transfer to the user in step 1 is rolled back along with the failing burn call in step 3. The net effect is that the entire `withdraw()` path for every pool that uses these helpers permanently reverts, freezing users' staked LP positions with no way to exit through the intended withdrawal function. This constitutes a permanent freezing of user funds.

### Likelihood Explanation
This is triggered by an ordinary user calling the standard, unprivileged `withdraw()` function on any `WombatPoolHelper`/`WombatPoolHelperV2`/`AnkrBNBPoolHelper` instance — no special privileges, governance, or external protocol manipulation is required. It will occur deterministically on every withdrawal attempt once the helper's receipt-token balance from any residual dust is exhausted (i.e., essentially always, since the helper receives no receipt tokens back from `MasterMagpie.withdrawFor`).

### Recommendation
Burn the receipt tokens from the account that actually holds them (the user, `_sender`), not from `msg.sender` of `burnReceiptToken` (the pool helper). This requires changing `WombatStaking.burnReceiptToken` to accept and burn from an explicit `_account` parameter (passed as the actual token holder), or restructuring `MasterMagpie.withdrawFor` to return the receipt tokens to the pool helper (`msg.sender` of `withdrawFor`) instead of directly to `_for`, so the helper can burn tokens it actually possesses.

### Proof of Concept
1. User calls `WombatPoolHelper.deposit()`. `WombatStaking.deposit()` mints receipt tokens to the helper, which stakes them into `MasterMagpie` under the user's account.
2. User calls `WombatPoolHelper.withdraw(_liquidity, _minAmount)`.
3. `WombatStaking.withdraw()` sends the deposit token to the user.
4. `_unstake()` → `MasterMagpie.withdrawFor(stakingToken, _liquidity, user)` sends the receipt token directly to the user's wallet, not the helper.
5. `WombatStaking.burnReceiptToken(lpToken, _liquidity)` attempts `receiptToken.burn(helperAddress, _liquidity)` — the helper's receipt-token balance is insufficient (it never received tokens back), causing the burn call to revert.
6. The entire `withdraw()` transaction reverts, permanently preventing withdrawal through this path.
