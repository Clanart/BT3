### Title
Out-of-bounds slice access via attacker-controlled `CompactBitArray` size in legacy Amino multisig decoding - (File: sei-cosmos/x/auth/legacy/legacytx/stdsign.go)

### Summary
`pubKeySigToSigData` in `sei-cosmos/x/auth/legacy/legacytx/stdsign.go` decodes a legacy-Amino multisig signature blob into a `multisig.AminoMultisignature{BitArray, Sigs}` and then iterates `n := multiSig.BitArray.Count()` times, indexing `pubKeys[i]` for each set bit, without ever checking that `n` (or the highest set-bit index) is bounded by `len(pubKeys)`. `pubKeys` is fixed to the number of keys actually configured on the multisig account, but `n` comes entirely from attacker-supplied bytes inside the transaction's `Signature` field. This mirrors the Xen CVE-2025-58147 pattern: a caller-supplied bitmask/mask input is converted into an index used against an internally-sized structure with insufficient boundary checking, causing an out-of-bounds access (`vpmask_set()` writing OOB vs. here `pubKeys[i]` reading OOB and panicking).

`CompactBitArray.Count()` (`sei-cosmos/crypto/types/compact_bit_array.go`) is derived purely from the unmarshalled `Elems`/`ExtraBitsStored` fields, both attacker-controlled via the raw signature bytes — it has no relationship to the actual pubkey set size of the account being signed for. `bitArray.GetIndex(i)` is itself bounds-checked against `n` (not against `len(pubKeys)`), so it happily returns `true` for `i >= len(pubKeys)`. When that happens, `pubKeys[i]` performs a Go slice index that panics with "index out of range" — the Go-idiomatic analog of the OOB read/write described in the CVE, since Go's runtime bounds checking converts what would be a memory-safety bug in C/Xen into an uncontrolled `panic`.

Notably, `verifyMultisignature` (`sei-cosmos/crypto/keys/multisig/multisig.go:60-112`) and `consumeMultisignatureVerificationGas` (`sei-cosmos/x/auth/ante/sigverify.go:444-488`) both explicitly guard against this same class of bug with `if len(pubKeys) != size { return error }` before indexing `pubKeys[i]`. `pubKeySigToSigData` is the one code path that omits this check.

### Impact Explanation
`pubKeySigToSigData` is reached from `StdTx.GetSignaturesV2()` [2](#0-1)  which is invoked by `SigVerificationDecorator.AnteHandle` and `SigGasConsumeDecorator.AnteHandle` [3](#0-2)  for every submitted legacy Amino StdTx whose signer account uses a `LegacyAminoPubKey` multisig, and is also reachable unauthenticated via the legacy REST decode endpoint `/cosmos/tx/v1beta1/txs/decode` [4](#0-3) , which converts arbitrary base64-encoded tx bytes to a `StdTx` and calls `GetSignaturesV2()` on it. A crafted transaction/signature blob is fully attacker-controlled input from an unprivileged sender or public-RPC/REST client — no privileged access is required.

The practical impact depends on whether the panic occurs within a scope protected by Cosmos SDK's `runTx` panic-recovery (which converts panics during ante-handling into a rejected tx rather than crashing the node) versus an unprotected path such as the legacy REST decode handler, which is a plain `http.HandlerFunc` with no `defer/recover` visible around `convertToStdTx`. In the latter case, a single crafted request would panic and crash the REST/RPC server process — matching the "crash of default-configuration RPC nodes" criterion. I was not able to fully verify within the available tool budget whether an outer recovery middleware wraps this specific REST handler, so this should be validated further (e.g., by tracing the HTTP router setup for `rest.PostProcessResponse`/middleware chains) before treating this as a confirmed crash vector; if no recovery wraps it, this is a High-severity, remotely-triggerable DoS against public REST/RPC endpoints and possibly node CheckTx paths lacking recovery.

### Likelihood Explanation
Likelihood is high for triggering the panic itself: constructing a malicious Amino-encoded multisig signature with a `CompactBitArray` whose `Count()` exceeds the actual number of pubkeys, and with at least one set bit at an index ≥ `len(pubKeys)`, requires only knowledge of the amino-multisig wire format and no valid signatures or special privileges. The uncertain part is solely whether the specific reachable call site is protected by panic recovery.

### Recommendation
Add the same bounds check used elsewhere (`verifyMultisignature`, `consumeMultisignatureVerificationGas`) to `pubKeySigToSigData`: validate `multiSig.BitArray.Count() == len(pubKeys)` (or at minimum that every set-bit index is `< len(pubKeys)`) before indexing `pubKeys[i]`, returning an error instead of allowing the loop to proceed. Additionally, confirm/add `defer/recover` around any HTTP handler paths (e.g., the legacy REST tx-decode endpoint) that parse untrusted transaction bytes outside of `baseapp.runTx`.

### Proof of Concept
1. Construct a `LegacyAminoPubKey` multisig account with `threshold=1` and 2 sub-pubkeys, and register it as an account (or target any existing 2-of-n multisig account known on-chain).
2. Build an Amino-encoded `multisig.AminoMultisignature{BitArray: <CompactBitArray with Count()=8, all-1 bits>, Sigs: [...]}` where the underlying pubkey set only has 2 entries, ensuring at least one set bit at index ≥ 2.
3. Wrap this blob as the `Signature` field of a `StdSignature{PubKey: multisigPubKey, Signature: maliciousBlob}` inside a `StdTx`.
4. Submit the resulting tx bytes to the legacy REST `/cosmos/tx/v1beta1/txs/decode` endpoint (or broadcast it so it hits the ante-handler `GetSignaturesV2()` call), triggering `pubKeys[i]` with `i` out of range and causing a Go runtime panic ("index out of range") in `pubKeySigToSigData`.

func pubKeySigToSigData(cdc *codec.LegacyAmino, key cryptotypes.PubKey, sig []byte) (signing.SignatureData, error) {
	multiPK, ok := key.(multisig.PubKey)
	if !ok {
		return &signing.SingleSignatureData{
			SignMode:  signing.SignMode_SIGN_MODE_LEGACY_AMINO_JSON,
			Signature: sig,
		}, nil
	}
	var multiSig multisig.AminoMultisignature
	err := cdc.Unmarshal(sig, &multiSig)
	if err != nil {
		return nil, err
	}

	sigs := multiSig.Sigs
	sigDatas := make([]signing.SignatureData, len(sigs))
	pubKeys := multiPK.GetPubKeys()
	bitArray := multiSig.BitArray
	n := multiSig.BitArray.Count()
	signatures := multisig.NewMultisig(n)
	sigIdx := 0
	for i := 0; i < n; i++ {
		if bitArray.GetIndex(i) {
			data, err := pubKeySigToSigData(cdc, pubKeys[i], multiSig.Sigs[sigIdx])
			if err != nil {
				return nil, sdkerrors.Wrapf(err, "Unable to convert Signature to SigData %d", sigIdx)
			}

			sigDatas[sigIdx] = data
			multisig.AddSignature(signatures, data, sigIdx)
			sigIdx++
		}
	}

	return signatures, nil
}

// convertToStdTx converts tx proto binary bytes retrieved from Tendermint into
// a StdTx. Returns the StdTx, as well as a flag denoting if the function
// successfully converted or not.
func convertToStdTx(w http.ResponseWriter, clientCtx client.Context, txBytes []byte) (legacytx.StdTx, error) {
	txI, err := clientCtx.TxConfig.TxDecoder()(txBytes)
	if rest.CheckBadRequestError(w, err) {
		return legacytx.StdTx{}, err
	}

	tx, ok := txI.(signing.Tx)
	if !ok {
		rest.WriteErrorResponse(w, http.StatusBadRequest, fmt.Sprintf("%+v is not backwards compatible with %T", tx, legacytx.StdTx{}))
		return legacytx.StdTx{}, sdkerrors.Wrapf(sdkerrors.ErrInvalidType, "expected %T, got %T", (signing.Tx)(nil), txI)
	}

	stdTx, err := clienttx.ConvertTxToStdTx(clientCtx.LegacyAmino, tx)
	if rest.CheckBadRequestError(w, err) {
		return legacytx.StdTx{}, err
	}

	return stdTx, nil
}
