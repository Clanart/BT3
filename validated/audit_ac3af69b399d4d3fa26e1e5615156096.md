### Title
Automatic, unconfirmed rewrite of a repository's `origin` remote URL based on trusted GitHub API `clone_url` field allows silent redirection of pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Connext report is fundamentally about a "canonical" pointer (`s.canonicalToAdopted[_canonical.id]`) that gets silently stale/incorrect when the underlying value it references (the wrapper token) is changed, and nothing forces re-validation of every place that pointer is used, so subsequent calls act on outdated/incorrect target data. The closest Desktop analog is `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts`, which uses the *GitHub API's* `clone_url` for a repository as the trusted "canonical" source and rewrites the local git remote (the value the user believes they are pushing/fetching against) automatically, with no user confirmation, whenever the previously-cached API `clone_url` matched the local remote.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` [1](#0-0)  which is run as part of Desktop's routine repository refresh flow. It fetches the repository object from the GitHub API (`api.fetchRepository(owner, name)`) and, if the local remote had not been "manually changed" relative to what was previously cached as `gitHubRepository.cloneURL`, it silently calls `gitStore.setRemoteURL` to overwrite `origin`'s URL with whatever `clone_url` the API now returns: [2](#0-1) 

The invariant being relied on is: "if the local remote URL still matches the *last cached* API clone_url, then any new value returned by the API must be a legitimate rename/move of the same repo, so it's safe to auto-apply." This is exactly analogous to Connext's flawed assumption that changing one canonical value (the wrapper) automatically keeps all dependent mappings (`canonicalToAdopted`) correct — except here it's inverted: Desktop *trusts* the external/canonical source (API response) to always be authoritative and blindly propagates it into the local, user-controlled remote configuration, without asking the user to confirm the change, similar to how AssetFacet's `setupAsset`/`setWrapper` silently changes what `canonicalToAdopted` points to without validating downstream consumers.

The existing guard is only a diff check between old/new clone_url strings and protocol match [3](#0-2) , not any user prompt, not any explicit signature/consistency validation. As long as an attacker who controls what the GitHub API returns for the `clone_url` field of the tracked repo — e.g., a malicious/compromised repository owner who transfers/renames the repo, or a GHES admin/malicious mirror serving crafted repository metadata for that endpoint — can cause Desktop to silently re-point the user's `origin` remote to a different destination.

### Impact Explanation
This matches the "silent corruption of what the user commits or pushes" impact class explicitly allowed by the task's Valid Impact criteria. If the remote silently repoints to an attacker-controlled repository/mirror, all subsequent `git push` operations from the unsuspecting user go to that destination instead of the one they believe they're using, potentially leaking proprietary code, secrets committed in the history, or letting an attacker plant malicious commits under the guise of the original repository name (since Desktop's UI still shows the same tracked `GitHubRepository`/owner/name association from `repositoriesStore`).

### Likelihood Explanation
The refresh path (`repositoryWithRefreshedGitHubRepository`) runs during Desktop's normal periodic/background repository-metadata refresh — no unusual user action is needed. The precondition is control over the `clone_url` field returned by the GitHub(Enterprise) API for the tracked repo, which is realistic for a scenario where a repository owner transfers/renames a repo they control (a legitimate use case the code intentionally supports) but is also exploitable if that owner is malicious, or on GHES where the API endpoint/server integrity can't be assumed to be as tightly controlled as github.com. There is no confirmation dialog shown to the user before the remote is rewritten, and the test suite at `app/test/unit/stores/updates/update-remote-url-test.ts` confirms the update happens unconditionally under these conditions (lines 68-81) with no user-facing step.

### Recommendation
- Do not silently rewrite the user's configured remote URL based solely on API `clone_url` drift; surface a confirmation dialog (similar to the existing fork-conversion or invalidated-token dialogs) before altering `origin`.
- If auto-following renames is desired for UX reasons, restrict it to same-owner path changes (case-insensitive name change under the same owner) and require an explicit user opt-in/notification for any owner or hostname change, since an owner change is the case most likely to indicate a hostile takeover/mirror rather than a benign rename.

### Proof of Concept
1. User clones `https://github.com/victim-org/victim-repo` and Desktop caches its `GitHubRepository.cloneURL` and adds the matching git `origin` remote.
2. The repository is transferred (or the org/owner account is compromised) such that the same `id`/`owner/name` combination the app is tracking now returns `clone_url: https://github.com/attacker-mirror/victim-repo` from the API (a legitimate GitHub "repository transfer" produces exactly this kind of `clone_url` change, and redirect endpoints keep old push/fetch working transiently, delaying detection).
3. On Desktop's next background refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees `remoteUrlUnchanged === true` (local remote still equals what was last cached) and `urlsMatch === false`, so it calls `gitStore.setRemoteURL(defaultRemote.name, updatedRemoteUrl)` and silently repoints `origin` to `attacker-mirror/victim-repo` [4](#0-3) .
4. The user, unaware of the change, performs `git push` from Desktop; the push now goes to the attacker's repository instead of the original.

Note: I could not fully trace every call-site/trigger condition of `repositoryWithRefreshedGitHubRepository` (e.g., exact refresh cadence/background timer) within the available tool budget, so the precise frequency of this automatic refresh should be verified in `app-store.ts` before treating the likelihood assessment as final.

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
```

```typescript
  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol
```
