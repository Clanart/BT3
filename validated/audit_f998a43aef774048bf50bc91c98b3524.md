### Title
`calculate_block_reward()` computes SIMD-0123 block-revenue-sharing rewards from a stale/mismatched stake denominator, allowing distributed lamports to exceed a vote account's `pending_delegator_rewards` pool - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The Autonomint bug is a rate-mismatch issue: a per-unit rate is computed from a denominator that has been reduced (`totalCdsDepositedAmountWithOptionFees - downsideProtected`), but the rate is then applied to the *original, unreduced* per-account principal, so the sum of individual payouts no longer matches the pool that funded the rate. The Agave analog is `calculate_block_reward()` in [1](#0-0) , which divides a vote account's total `pending_delegator_rewards` by a `total_active_stake` denominator taken from a point-in-time snapshot (`RewardEpochDelegatedStakes`), then multiplies by each stake account's *own* effective stake, which can diverge from that snapshot after rent-adjustment increases the delegation.

### Finding Description
`calculate_block_reward()` computes, per stake delegation:
```
(pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128).min(pending_delegator_rewards)
``` [2](#0-1) 

`total_active_stake` is looked up from `reward_epoch_delegated_stakes.delegated_stakes`, a fixed snapshot map computed once at the reward-epoch boundary [3](#0-2) . But `stake`, the numerator term for this individual delegation, is recomputed via `delegation_effective_stake()` using the *current* `Delegation` at the time of the call, not a value fixed to the same snapshot basis [4](#0-3) . The function's own comment acknowledges this basis mismatch:

> "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`. If `pending_delegator_rewards` is a huge number, we could potentially overflow a `u64`. We can also have individual rewards look greater than the pending rewards. This is harmless in practice, but we clamp it just to be safe" [5](#0-4) 

The mitigation applied (`.min(pending_delegator_rewards)`) only bounds a *single* delegation's reward to the vote account's total pending pot — exactly like clamping one CDS depositor's fee to the total fee pool would not fix the underlying rate-vs-denominator mismatch. It does **not** ensure that the *sum* of all `calculate_block_reward()` outputs across every delegation to the same vote account stays within `pending_delegator_rewards`. This is the exact broken invariant from the report: rate computed from one basis (`total_active_stake` snapshot), multiplied against a numerator computed from a different, larger basis (`stake` after rent-adjustment growth via `adjust_delegation_for_rent`/`redeem_stake_rewards`, see [6](#0-5) ), so `Σ stake_i / total_active_stake` can exceed 1, and each `min()`-clamped individual result can still sum to more than `pending_delegator_rewards`.

This code path is only reachable when `block_revenue_sharing` feature is active [7](#0-6)  and specifically during `recalculate_stake_rewards()` after a partial partitioned distribution / snapshot-restore boundary, where `distribution_epoch_vote_accounts` (used to build `reward_epoch_delegated_stakes`) may already reflect updated post-reward delegation amounts while individual stake accounts' effective stake at `rewarded_epoch` is separately recomputed [8](#0-7) [9](#0-8) .

### Impact Explanation
If the aggregate block-reward payouts to delegations of a single vote account exceed `pending_delegator_rewards`, the vote account is either debited more lamports than it actually holds/owes (an accounting overpayment funded by protocol-level reward emission, i.e., unbacked lamport creation/miscalculation of consensus-critical reward state), or later stakers in the same distribution partition receive less than their fair share because an earlier stake already consumed more than its proportional share of the pot. This is a fund-miscalculation bug in the reward/inflation subsystem, matching the "false execution" / accounting-corruption class for validator runtime state (bank capitalization, stake lamports) which affects consensus determinism if not all validators hit the exact same "recalculation" trigger condition consistently.

### Likelihood Explanation
The divergence requires: (1) `block_revenue_sharing` feature enabled, (2) the reward-distribution/recalculation-after-restore path (`recalculate_stake_rewards`) being exercised so that `stake` and `total_active_stake` are computed from different bases, and (3) at least one stake account whose effective stake has already grown via a partial reward payment relative to the frozen `total_active_stake` snapshot. The code comment itself documents that this scenario is anticipated ("if stake account has already received rewards, it's possible to have `stake > total_active_stake`"), indicating the authors were aware of a basis mismatch but only partially mitigated it (single-entry clamp, not aggregate-sum guarantee). Because this triggers deterministically off runtime/consensus state during normal reward recalculation (not attacker-controlled input), it is a systemic correctness bug rather than a targeted exploit, but it is gated behind an unreleased/newer feature flag whose current exposure in mainnet is uncertain from local code alone.

### Recommendation
Do not compute the per-delegation block-reward ratio using a `total_active_stake` denominator that can be inconsistent with the numerator `stake` basis. Either (a) freeze both numerator and denominator to the exact same epoch-boundary snapshot (do not recompute `stake` via `delegation_effective_stake` using post-adjustment `Delegation` state at recalculation time), or (b) track and enforce that the running sum of `block_reward` values paid out per vote account never exceeds that vote account's `pending_delegator_rewards`, decrementing a per-account remaining-budget counter across all delegations instead of independently clamping each individual value against the un-decremented total.

### Proof of Concept
Given the code paths cited above, conceptually:
1. `pending_delegator_rewards = 1000`, `total_active_stake` snapshot recorded as `900` (from `RewardEpochDelegatedStakes` at epoch boundary) for vote account `V`.
2. Stake account `A` delegated to `V` has already received a partial reward via `redeem_stake_rewards`/`adjust_delegation_for_rent`, growing its `Delegation::stake` from `450` to `500` (still within `stake > total_active_stake` note in the comment) before `calculate_block_reward()` runs for it during `recalculate_stake_rewards()`.
3. Stake account `B` (`stake = 450`) is unaffected, still at its epoch-boundary value.
4. `calculate_block_reward(A)` = `1000 * 500 / 900 = 555` (`.min(1000)` no-op).
5. `calculate_block_reward(B)` = `1000 * 450 / 900 = 500`.
6. Sum `A + B = 1055 > pending_delegator_rewards (1000)` even though each individual value passed its own `.min(pending_delegator_rewards)` clamp — reproducing the same "rate computed on stale/reduced basis, applied to grown numerator, sum exceeds pool" pattern as the Autonomint `CDS.sol` bug.

This PoC is derived purely from reading the cited local functions; it has not been executed against a live Agave test harness, so the exact numeric conditions required to trigger `stake > total_active_stake` in production reward recalculation should be validated with a Devin session running the existing `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` test suite (e.g. extending `test_rewards_point_calculation`-style tests) before treating this as confirmed exploitable.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
