## Title
Untyped-changed status codes (`T` typechange combos) silently reclassified as ordinary "Modified" by `mapStatus`, hiding file-type swaps from the commit UI - (File: `app/src/lib/status-parser.ts`)

### Summary
This is the same bug class as the Nethermind report: a parser accepts a wider set of raw values than the downstream classifier explicitly validates, and the classifier's fallback path silently coerces the unrecognized value into a "safe-looking" known type instead of rejecting/flagging it. In Nethermind, an RLP `TxType` byte that should be rejected as invalid is instead treated as ordinary work by a `switch` that doesn't fully validate the enum. In Desktop, the porcelain-v2 status-code regex accepts index/worktree pairs (including Git's `T` "typechange" code) that `mapStatus` never explicitly enumerates, so they fall into a generic "assume modified" branch that erases the actual semantic (e.g. a symlink⇄regular-file swap or an unmerged/typechange state).

### Finding Description
`git status --porcelain=2 -z` output is parsed by the regex at [1](#0-0) , which accepts any two-character combination from the class `[MADRCUTX?!.]`. This explicitly includes `T` (Git's type-change indicator, e.g. file replaced by symlink or vice versa) and `X` (unknown), alongside the "normal" `M/A/D/R/C/.` codes.

The resulting `statusCode` is then handed to `mapStatus` in the same file, which only has explicit branches for a curated subset of two-character codes (`.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, and the conflict set `DD/AU/UD/UA/DU/AA/UU`) — see [2](#0-1) . Any code the regex allowed but that isn't in this list — including `.T`, `T.`, `MT`, `TM`, `AT`, `TA`, `DT`, `TD`, `CT`, `TC`, `RT`, `TR`, `TT`, or anything containing `X` — falls through to the fallback:

```
// as a fallback, we assume the file is modified in some way
return {
  kind: 'ordinary',
  type: 'modified',
  submoduleStatus,
}
``` [3](#0-2) 

This `FileEntry` then feeds `convertToAppStatus` in `app/src/lib/git/status.ts`, which for `kind: 'ordinary'` just maps `type: 'modified'` straight to `AppFileStatusKind.Modified` [4](#0-3)  — with no distinguishing flag that the change is actually a type change (regular file↔symlink↔submodule-gitlink swap) rather than a content edit.

### Impact Explanation
A crafted/checked-out working tree (e.g., produced by cloning or fetching a hostile repository, or by an operation that leaves the index in a typechange state such as replacing a tracked file with a symlink) can present as `.T`/`T.`/`MT`/etc. in `git status --porcelain=2`. Because `mapStatus` silently downgrades this to an ordinary "Modified" entry, GitHub Desktop's Changes list shows the file as a plain modification rather than surfacing that its type changed (e.g. it is now a symlink). A user who reviews the diff and stages/commits/pushes believing they are looking at a normal text edit may actually be committing a symlink or other unexpected filesystem object without being alerted, i.e., silent corruption of what the user commits — one of the explicitly valid impact categories for this exercise.

### Likelihood Explanation
Typechange states are a normal, easily reachable Git condition (swap a tracked file for a symlink, or vice versa, then run `git add`), so no unusual local privileges are required beyond the attacker controlling repository content that gets checked out/fetched — exactly the "attacker controls a cloned/fetched repository" precondition in the Valid Impact section. The regex at line 103 already admits these codes, so the gap is purely in `mapStatus`'s classification completeness, not in some separate hard-to-reach code path.

### Recommendation
Enumerate `T`-involving and `X` status codes explicitly in `mapStatus` (mirroring how git categorizes typechange as distinct from modified) and surface a distinct `AppFileStatus`/UI indicator for type changes, instead of falling back to a generic "modified" classification. At minimum, the fallback branch should not silently claim `type: 'modified'` for codes it does not recognize — it should flag the entry for special handling/review.

### Proof of Concept
1. In a test repository, stage a tracked regular file for commit, then delete it and create a symlink with the same path (`rm file && ln -s /etc/passwd file && git add file`).
2. Run `git status --porcelain=2 -z`; the index/worktree pair reported is `T.` (or similar, depending on staged/unstaged state).
3. Feed this into `parsePorcelainStatus`/`mapStatus` from `app/src/lib/status-parser.ts` — the regex at line 103 matches, but no explicit branch matches `T.`, so the fallback at lines 420-425 returns `{ kind: 'ordinary', type: 'modified' }`.
4. `convertToAppStatus` in `app/src/lib/git/status.ts` (lines 135-152) reports this to the UI as an ordinary `Modified` file, with no indication that the file's type changed to a symlink, letting a user commit/push it unaware.
