## Analysis

The seed report's core defect: an accounting side-effect (`tokensSold -=`) is skipped on one code path while the fund-movement/state-transition logic proceeds anyway, letting on-chain state diverge from the funds that actually moved (or didn't). The strongest local analog in this repo is in the **Tron port of the Intent Gateway**, `evm/tron/contracts/apps/IntentGatewayV2.sol`, where the escrow-release function `withdraw()` marks the order settled and decrements escrow accounting **regardless of whether the underlying ERC-20 transfer actually succeeded**, because it uses a raw low-level `.call` and only checks call-level `success`, never validating the token's boolean return value.

### Title
Unchecked ERC-20 `transfer` return value in `IntentGatewayV2.withdraw` permanently locks escrowed funds while marking the order settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` releases escrowed order funds to a beneficiary and finalizes order state (`_filled[commitment] = beneficiary`, escrow decrement, `EscrowReleased`/`EscrowRefunded` event) using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checking that the *call itself* did not revert. It never decodes/validates the ERC-20 `transfer` return value.

### Finding Description
In `withdraw`, each escrowed token is paid out like this: [1](#0-0) 

`_filled[body.commitment] = beneficiary;` is set unconditionally up front, and for each token the code only checks `success` from the raw call — not the ABI-decoded boolean return value — before decrementing `_orders[body.commitment][token] -= amount;` and, at the end, emitting `EscrowRefunded`/`EscrowReleased`.

Many real ERC-20 tokens (deflationary/pausable/blocklist-style tokens, or any non-reverting implementation) return `false` on a failed transfer instead of reverting. For such tokens, the low-level `.call` succeeds (the callee executed without reverting) even though `false` was returned, so `success == true` and the code proceeds exactly as if funds were delivered: it finalizes `_filled[commitment]`, decrements the escrow record, and emits the success event — even though **no tokens actually left the contract**.

This is the direct local analog of the seed bug: an accounting/state-finalizing side effect is applied without being conditioned on the actual fund-movement outcome, leaving on-chain bookkeeping (and settlement status) inconsistent with real asset custody.

Contrast with the audited/reference EVM implementation, which uses OpenZeppelin's `SafeERC20.safeTransfer` (reverts on failed/false-returning transfers) and also decrements storage **before** the external call: [2](#0-1) 

The Tron port reintroduces both the unchecked-return-value issue and a checks-effects-interactions inversion (transfer before decrement) that the mainline contract had already fixed.

### Impact Explanation
Once `withdraw` runs for a commitment:
- `_filled[commitment]` is set to the beneficiary, permanently blocking any retry of `fillOrder`/`cancelOrder` for that order (`Filled()` guard).
- `_orders[commitment][token]` is decremented/zeroed, so the escrow bookkeeping shows the funds as already paid out.

If the escrowed token silently returns `false` instead of reverting on transfer failure, the user's escrowed tokens remain stuck in the `IntentGatewayV2` contract with no way to ever reclaim them — the order is marked filled/refunded but the beneficiary never received the funds. This is a direct, unrecoverable loss/lock of user funds, matching the "stealing or loss of funds" impact bucket, reachable by any unprivileged user who places or fills an order using a non-standard ERC-20 as an input/output token — no malicious relayer, prover, or admin required.

### Likelihood Explanation
Likelihood is contingent on the token used for escrow being a non-reverting-on-failure ERC-20 (a known and common class of real-world tokens), and requires no elevated privileges, no consensus/proof manipulation, and no cooperation from any protocol actor — placing and cancelling/filling an order is the standard, unprivileged happy path. The only precondition is token choice, which the Intent Gateway does not restrict.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw` (and the analogous pattern in `onAccept`'s `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. Additionally, restore checks-effects-interactions ordering by decrementing `_orders[body.commitment][token]` before performing the transfer, rather than after.

### Proof of Concept
1. Deploy a minimal ERC-20 whose `transfer` function returns `false` on failure instead of reverting (e.g., simulate insufficient allowance/blocklist by returning `false`).
2. Call `placeOrder` escrowing this token as an input.
3. Trigger `cancelOrder` (same-chain path) once conditions are such that the token's `transfer` call to the beneficiary returns `false` (e.g., beneficiary is blocklisted in the token's logic, or the token has an internal invariant that fails softly).
4. Observe: `withdraw` still sets `_filled[commitment] = beneficiary`, decrements `_orders[commitment][token]`, and emits `EscrowRefunded`, despite the beneficiary's token balance not increasing.
5. Any further attempt to fill/cancel/withdraw the order reverts with `Filled()`, permanently locking the escrowed tokens in the contract.
