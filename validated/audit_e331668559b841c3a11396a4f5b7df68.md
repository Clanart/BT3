## Finding: Missing zero-amount guard in `IntentGatewayV2.withdraw()` (Tron variant) reproduces the M-08 fallback/receive fund-lock pattern

### Title
Escrow settlement/refund in the Tron `IntentGatewayV2.withdraw()` unconditionally attempts a native ETH `.call` even for zero-amount legs, permanently locking escrowed funds when the beneficiary lacks `receive()`/`fallback()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM intents implementation (`IntentsBase.sol`) already patches the exact bug class described in the M-08 report by skipping any token leg whose `amount == 0` before attempting a native transfer. The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, reimplements the identical escrow-withdrawal logic but omits this guard, reintroducing the vulnerability locally.

### Finding Description
`IntentsBase._withdraw` (used by the EVM `ExtrinsicIntents`/`IntrinsicIntents` intent apps) explicitly skips zero-amount legs before performing the native transfer: [1](#0-0) 

The Tron `IntentGatewayV2.withdraw()` function implements the same escrow-settlement/refund logic but has no such guard - it checks only that the escrow slot is non-zero (`_orders[body.commitment][token] == 0`), not that the *transfer amount* is non-zero, before unconditionally calling `beneficiary.call{value: amount}("")`: [2](#0-1) 

This is precisely the pattern flagged in the M-08 report: an unconditional native-value call with empty calldata to a `beneficiary` address, executed even when the transfer amount is `0`. A call with empty data to a contract lacking both `receive()` and `fallback()` reverts regardless of the value sent, so this reverts the whole settlement (fill) or refund (cancel) transaction.

`withdraw()` is invoked from two ISMP-driven entry points: `onAccept` (escrow release on a successful cross-chain fill) and `onGetResponse` (escrow refund after `cancelOrder`'s GET-proof confirms the order was never filled): [3](#0-2) 

Both are called by the local `IsmpHost` when delivering a proven message - there is no admin, relayer, or prover compromise required; the trigger is simply an order whose escrow accounting produces a zero-amount leg (e.g. a partial fill causing one input's proportional share to round to zero) for a beneficiary address that is a contract without a payable fallback.

### Impact Explanation
When the failure occurs inside `onAccept`/`onGetResponse`, `EvmHost.dispatchIncoming` catches the revert and deletes the request/response receipt "so that it can be retried": [4](#0-3) 

This retry mechanism mirrors Taiko's suggested mitigation (`retryMessage`/`failMessage`), but it does not help here: the underlying condition (zero-amount leg + non-payable beneficiary) is deterministic and does not change across retries. The message can never be delivered successfully, so the associated escrowed tokens (including any other, valid legs bundled in the same `WithdrawalRequest`) are permanently stuck in the `IntentGateway` contract with no recovery path - the same "funds lost, recovery reverts too" outcome the external report describes.

### Likelihood Explanation
No privileged actor, malicious relayer, or compromised prover is required. Any solver/order-creator that ends up with a zero-amount leg in a multi-input/partial-fill order combined with a smart-contract beneficiary lacking a payable fallback will hit this path deterministically once the corresponding ISMP message is delivered.

### Recommendation
Add the same guard used in `IntentsBase._withdraw` to the Tron `IntentGatewayV2.withdraw()`: skip the native-value `.call` (and, ideally, the whole loop iteration) whenever `amount == 0`, matching: [5](#0-4) 

### Proof of Concept
1. Construct an order with two native-ETH input legs where a partial fill causes `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired` to round down to `0` for one leg, while `_orders[commitment][address(0)]` remains non-zero from the other leg.
2. Set the fill beneficiary (`msg.sender`/solver) or cancel-refund beneficiary (order creator) to a deployed contract with no `receive()`/`fallback()`.
3. Trigger the cross-chain `RedeemEscrow`/refund message so that `withdraw()` is invoked from `onAccept`/`onGetResponse` with a `body.tokens` entry where `amount == 0` for `token == address(0)`.
4. Observe `beneficiary.call{value: 0}("")` reverting because the beneficiary has no fallback, causing `TransferFailed`/`InsufficientNativeToken` and rolling back the entire settlement; retries via `dispatchIncoming` fail identically forever, leaving the escrowed tokens permanently locked in the contract.
