### Title
Deterministic reuse of cached FROST/MuSig preprocess across all signing calls within a context enables secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives signing nonces from a seed stored once per `context` in `CachedPreprocesses`. Every `share_internal` call under the same context calls `from_cache` with the identical seed, regenerating identical nonces `(d, e)`. If an honest validator's `share`/`complete` path is driven with two or more distinct `(preprocess set, key_pair)` inputs within one `attempt` context, the published signature shares form a linear system that leaks the validator's MuSig secret share — the same class as CVE-2019-8308, where a boundary meant to confine untrusted input (the Flatpak sandbox / the one-shot preprocess) instead exposes host-side state (the ChaCha20 nonce seed) to attacker-influenced mutation, letting the attacker compromise the host (recover the validator key share).

### Finding Description
`preprocess_internal` caches only the 32-byte RNG seed, keyed by `self.context` (e.g., `(b"DkgConfirmer", self.attempt)`), and rebuilds the sign machine via `AlgorithmSignMachine::from_cache` on *every* invocation — including each call to `share_internal` and `complete_internal` [1](#0-0) . `seeded_preprocess` deterministically expands that seed through `ChaCha20Rng` into the FROST nonces and commitments [2](#0-1) . `share_internal` then parses attacker-supplied preprocess bytes via `read_preprocess` and calls `machine.sign(preprocesses, msg)` where `msg` is `set_keys_message(set, removed, key_pair)` — both the preprocess map and the `key_pair` embedded in `msg` originate from finalized tributary transactions [3](#0-2) . The FROST spec and the module's own header document that nonce reuse across distinct `(commitments, msg)` pairs leaks the secret share [4](#0-3) .

### Impact Explanation
With the nonces fixed, each published share has the form `s = d + b·e + c·λ·s_i`, where the binding factor `b` and challenge `c` vary with the attacker-chosen preprocess set and message. Each additional `share` call under the same context yields one more linear equation in the unknowns `(d, e, s_i)`; three calls suffice to solve for `s_i` outright. Recovery of a validator's MuSig key share undermines the root-of-trust key used for on-chain DKG confirmation, enabling signature forgery attributed to that validator. In `DkgConfirmer`, `complete` itself re-runs `share_internal`, so each share/complete round and each distinct `key_pair`/`preprocesses` combination finalized in the attempt contributes an equation [5](#0-4) .

### Likelihood Explanation
The code relies on BFT ordering to guarantee `sign` is only ever re-executed on identical inputs [6](#0-5) . However, BFT ordering does not deduplicate distinct transactions: an unprivileged participant can publish a distinct `preprocesses` map or induce a distinct `key_pair` message within the same `attempt`, and each such finalized input deterministically drives `share_internal` again with the same seed. The file itself flags that the analogous check ("the commitments generated from the decided nonces are in fact its commitments on-chain") is an unimplemented TODO [7](#0-6) . Exploitation requires only transactions any validator can submit, not consensus faults.

### Recommendation
- Include the full `(preprocess set digest, msg)` — not just the attempt — in the `CachedPreprocesses` context, or store the signed-input digest and reject any `share_internal` call whose inputs differ from the first-signed input for that context.
- Implement the noted TODO: before publishing a share, verify on-chain that the preprocess/commitment set matches the presumed one, so a divergent finalized set cannot silently trigger a second signing.
- Clear the cached seed after a successful `complete` for the context so late-arriving inputs cannot provoke re-signing.

### Proof of Concept
1. Attempt `k` begins; the honest coordinator calls `preprocess()`, storing `CachedPreprocesses[("DkgConfirmer", k)] = seed` and publishing commitments `D, E` derived from `ChaCha20Rng(seed)`.
2. A participant submits a transaction carrying preprocess set `P₁` and key pair `K₁`; `share` → `share_internal` → `from_cache(seed)` → `sign(P₁, m₁)` publishes `s₁ = d + b₁·e + c₁·λ·s_i`.
3. A second distinct finalized input `(P₂, K₂)` in the same attempt triggers `share` again: `s₂ = d + b₂·e + c₂·λ·s_i` with the same `(d, e)`.
4. A third distinct input `(P₃, K₃)` yields `s₃`. With `bⱼ`, `cⱼ`, `λ` publicly computable, solve the 3×3 linear system for `(d, e, s_i)`, recovering the coordinator's validator key share — confirmed by the documented consequence that reuse "will enable third-party recovery of your private key share" [4](#0-3) .

Caveat: I could not fully verify the exact call multiplicity of `share`/`complete` per attempt inside `handle.rs` (the final grep returned match counts without context). The finding stands on the deterministic-seed reuse in `preprocess_internal` and the module's own acknowledgment that safety depends entirely on inputs never diverging.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
