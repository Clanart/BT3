### Title
`get-asset-price` in the position/health data contract prices `stSTXbtc`/`zstSTXbtc` using the STX feed instead of the BTC feed - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
The `get-asset-price` helper used to compute collateral/debt USD values and the derived `health-factor` / `is-liquidatable` verdict in `get-user-position` fetches the **STX** Pyth feed for the `stSTXbtc` and `zstSTXbtc` assets, even though the code comments explicitly say "BTC price" and these assets are BTC-denominated (liquid-staked BTC / its z-vault wrapper). This misattributes a completely different asset's price to `stSTXbtc`/`zstSTXbtc`, producing a wrong valuation and a wrong health verdict.

### Finding Description
In `get-asset-price`, every other asset correctly maps to its own oracle constant (`STX`→`PYTH-STX`, `sBTC`→`PYTH-BTC`, `USDC`→`PYTH-USDC`, `USDH`→DIA, etc.). For `stSTXbtc` and `zstSTXbtc` the code instead calls `get-pyth-price PYTH-STX`: [1](#0-0) 

```clarity
;; stSTXbtc - BTC price (liquid staked STX with BTC yield)
(if (is-eq aid stSTXbtc) (default-to u0 (get-pyth-price PYTH-STX))
;; zstSTXbtc - stSTXbtc price x liquidity index
(if (is-eq aid zstSTXbtc)
    (let ((btc-price (default-to u0 (get-pyth-price PYTH-STX)))
          (lindex (get-vault-liquidity-index stSTXbtc)))
      (mul-div-down btc-price lindex INDEX-PRECISION))
```

The variable is even named `btc-price` while the call actually fetches the STX/USD feed defined at [2](#0-1)  (`PYTH-STX` vs `PYTH-BTC`). Since STX and BTC trade at wildly different magnitudes, this makes the computed price for `stSTXbtc`/`zstSTXbtc` off by orders of magnitude (understated, since STX ≪ BTC).

This price is consumed directly by `sum-collateral-usd` and `sum-debt-usd`, which feed `coll-usd`/`debt-usd`, `current-ltv`, `health-factor`, and `is-liquidatable` in `get-user-position`: [3](#0-2) [4](#0-3) 

### Impact Explanation
Direction of the error: because the STX price is used instead of the correct BTC price, any position that holds `stSTXbtc`/`zstSTXbtc` as **debt** has `debt-usd` drastically understated, which drives `current-ltv` down and `health-factor` up — the position is reported as far healthier (or entirely non-liquidatable) than it truly is. Borrowers who take on `stSTXbtc`/`zstSTXbtc` debt profit: they can accumulate real BTC-denominated debt while this on-chain health/position endpoint (which liquidators/integrators rely on to identify and act on unhealthy accounts) reports the account as safe, so no liquidation is triggered even as bad debt builds up. This leads to under-liquidated, undercollateralized debt accumulating against the vault backing `stSTXbtc`, which is a path to protocol insolvency / permanent freezing of lender funds once the mispriced debt is never liquidated in time. (Conversely, if held as collateral, the same bug understates collateral value, which is not itself exploitable for profit but corrupts every consumer of this endpoint.)

This lands on the **Critical** impact category (protocol insolvency / permanent loss of funds) because it produces a systematically wrong health verdict for a real Zest asset via a wrong price-to-asset mapping — one of the explicitly in-scope analog classes.

### Likelihood Explanation
Likelihood is high for any account that opens a `stSTXbtc`/`zstSTXbtc` position (borrowing or holding it as debt), since the mispricing is deterministic and triggers on every call to `get-asset-price`/`get-user-position` for those two asset IDs — no special conditions or oracle manipulation are required, it is a straightforward wrong-constant bug reachable on every position read.

### Recommendation
Change the two branches to call `get-pyth-price PYTH-BTC` instead of `PYTH-STX` for both `stSTXbtc` and `zstSTXbtc`, consistent with the existing comments and with the `sBTC`/`zsBTC` branches that correctly use `PYTH-BTC`.

### Proof of Concept
1. Call `contract-call? .v0-1-data get-user-position <account>` for an account with `stSTXbtc` (aid `stSTXbtc`, u10) recorded as debt.
2. Observe `get-asset-price` (line 582) returns the current STX/USD price (e.g. ~$2) instead of the actual BTC-denominated value of `stSTXbtc` (e.g. ~$60,000+), so `debt-usd` is understated by orders of magnitude.
3. `current-ltv` and `health-factor` in the returned tuple therefore show the account as healthy/non-liquidatable even though its true BTC-priced debt would make it deeply undercollateralized, so any liquidator or integration trusting this read-only endpoint will fail to flag/liquidate it.
