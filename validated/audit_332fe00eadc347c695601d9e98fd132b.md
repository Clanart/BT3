### Title
Permanent, unrecoverable forfeiture of pending vlMGP/mWomSV rewards grows the longer a user waits to finalize an already-completed unlock, with no way to reclaim the lost yield - (File: `VLMGP.sol`)

### Summary
The original report's bug class is: an irreversible value-extraction event (a fee taken at order time) is not returned/recoverable when the triggering action is later cancelled/reversed. The reachable analog in this codebase is in the vlMGP (and identical mWomSV) unlock-slot / reward-forfeit mechanism: once a user's `UserUnlocking` slot passes `endTime` (cooldown finished), `getRewardablePercentWAD()` keeps *decreasing* the user's rewardable share the longer they delay calling `unlock()`, and this shortfall is permanently siphoned off to the reward pool via `_calExpireForfeit`/`_queueNewRewardsWithoutTransfer` on every subsequent claim — with no mechanism for the user to recover it, exactly analogous to fees being transferred away immediately with no path back to the user.

### Finding Description
`getRewardablePercentWAD()` computes the percentage of a user's vlMGP rewards that are "rewardable" (not forfeited): [1](#0-0) 

For a slot still inside its cooldown window, the code adds full weight (`amountInCoolDown * 1e18 / userTotalVlmgp`) — i.e. no forfeiture. But for a slot whose `endTime` has already passed (the user is fully eligible to call `unlock()` and reclaim principal), the code instead computes:
```
percent += amount * 1e18 * (endTime - startTime) / userTotal / (timeNow - startTime)
```
As `timeNow` grows past `endTime`, `(timeNow - startTime)` grows unbounded while `(endTime - startTime)` stays fixed, so this term monotonically shrinks toward zero. This means the *longer* a user simply forgets or delays calling `unlock()` after their cooldown has already completed, the *smaller* their rewardable percentage becomes — the opposite of what a user (or protocol designer) would expect, since the user has done nothing wrong by leaving fully-unlocked tokens un-withdrawn.

This percentage feeds directly into the forfeiture calculation used whenever pending rewards are paid out: [2](#0-1) 

`_calExpireForfeit` multiplies the user's accrued `userRewards` by `(1 - rewardablePercentWAD)` and the forfeited portion is permanently re-queued into the shared reward pool for other stakers via `_queueNewRewardsWithoutTransfer`, never credited back to the affected user. Once `userRewards[_rewardToken][_account]` is zeroed out in `_sendReward`, that forfeiture is final — there is no `cancel`/`re-lock` action that restores it, mirroring the original report's core defect (value extracted up front with no refund path once the triggering condition changes).

The user's only way to stop the bleed is to call `unlock()` (withdraw principal) or, while still inside cooldown, `cancelUnlock()`: [3](#0-2) 
but `cancelUnlock()` is only usable *before* `endTime` (`_checkInCoolDown` reverts with `NotInCoolDown` once `endTime` has passed) — see: [4](#0-3) 
so once a slot's cooldown has elapsed, the user has no lever except to unlock immediately; any delay (missed transaction, gas spikes, front-end downtime, or simply forgetting) causes escalating, permanent, unrecoverable loss of already-earned reward yield. The identical logic exists in `mWomSV.sol`: [5](#0-4) 

### Impact Explanation
This causes permanent loss ("theft") of unclaimed yield for any ordinary vlMGP/mWomSV holder who has started an unlock and does not immediately call `unlock()` the instant the cooldown ends. Every subsequent reward harvest/claim while the eligible-but-unwithdrawn slot exists silently siphons an increasing fraction of the user's pending rewards to the shared reward pool, permanently and irreversibly, satisfying the "permanent freezing/theft of unclaimed yield" impact bar.

### Likelihood Explanation
This requires no privileged role, malicious admin, or external protocol interaction — it is triggered purely by normal, expected user behavior (starting an unlock and not claiming/unlocking the exact instant the cooldown expires), which is a highly common real-world occurrence (users don't monitor exact unlock timestamps). Any interaction that triggers a reward claim/harvest for the account while the slot is expired-but-unwithdrawn (`multiclaimFor`, harvests, etc.) re-evaluates and worsens the forfeiture, making this reliably and repeatedly reachable.

### Recommendation
Cap the rewardable percentage contribution of an expired-but-unwithdrawn cooldown slot at 100% (i.e., treat any slot past `endTime` as fully rewardable, not decaying), or freeze/snapshot the rewardable percentage at the moment `endTime` is reached rather than continuing to recompute it as a function of `timeNow`. Alternatively, allow `cancelUnlock`/an equivalent recovery path even after `endTime` has passed so a user who cannot immediately call `unlock()` is not penalized.

### Proof of Concept
1. User calls `startUnlock(amount)`, creating a `UserUnlocking` slot with `startTime = T0`, `endTime = T0 + coolDownInSecs` [6](#0-5) .
2. Cooldown ends at `T0 + coolDownInSecs`; user does not immediately call `unlock()` (e.g., waits an extra day for gas reasons).
3. Any reward claim triggered for this user (their own `multiclaimFor` call from another action, or a batched harvest) calls into `vlMGPBaseRewarder._sendReward` → `_calExpireForfeit` → `vlMGP.getRewardablePercentWAD(user)` [7](#0-6) .
4. Because `timeNow > endTime` for this slot, `getRewardablePercentWAD` returns a percentage that shrinks the further past `endTime` the current block is [8](#0-7) .
5. The forfeited amount (`_amount - rewardableAmount`) is deducted from the user's `userRewards` and re-queued to the pool, permanently, before the user ever calls `unlock()` [9](#0-8) .
6. The user eventually calls `unlock()` and recovers only their MGP principal [10](#0-9)  — the forfeited reward yield is gone with no recovery mechanism.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }

        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;

        return ((_userVlmgpShare *
                (rewardPerToken(_rewardToken) -

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
