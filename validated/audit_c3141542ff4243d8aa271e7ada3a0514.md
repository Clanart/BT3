## Title
Unchecked ERC20 `transfer()` return value causes silent, permanent loss of incentive rewards in `ArbWomUp`/`ArbWomUp2` - (File: `wombat/ArbWomUp.sol`, `wombat/ArbWomUp2.sol`)

### Summary
`ArbWomUp.incentiveDeposit()` and `ArbWomUp2.incentiveDeposit()` pull a user's WOM via `safeTransferFrom` (which reverts on failure) but then pay out the USDT/BUSD incentive reward with a raw, unchecked `IERC20(usdt).transfer(...)` / `IERC20(busd).transfer(...)` call whose boolean return value is discarded, mirroring the H03 report's pattern of unchecked transfers combined with premature state finalization.

### Finding Description
In `ArbWomUp.sol`: [1](#0-0) 
the function deposits the user's WOM (`_deposit`, using `safeTransferFrom`), immediately marks the reward as claimed via `claimedReward[msg.sender] += rewardToSend;`, and only afterward calls the raw `IERC20(usdt).transfer(msg.sender, rewardToSend);` without checking the return value or reverting on failure. `ArbWomUp2.sol` has the identical pattern for BUSD: [2](#0-1) 

Both contracts use `SafeERC20` for the deposit leg (`IERC20(wom).safeTransferFrom`) but deliberately use the raw, non-safe `IERC20(...).transfer(...)` for the reward payout leg, discarding the boolean success value — exactly the class of bug described in the referenced report (`finalizeGrant`/`cashOutOrg` transferring without checking success and prematurely updating accounting state).

If the reward token (`usdt`/`busd`) ever returns `false` on failure instead of reverting (e.g., due to a paused/blacklist state or any non-standard ERC20 behavior), the transfer silently fails while:
1. The user's WOM has already been taken (via the reverting `safeTransferFrom`), and
2. `claimedReward[msg.sender]` has already been incremented by the full `rewardToSend` amount, and
3. A `USDTRewarded`/`BUSDRewarded` event is emitted as if the payment succeeded.

Because `getRewardAmount()` computes the claimable amount as `rewardAmount/DENOMINATOR - claimedReward[_account]` (or `calDoubledCounted` in v2), once `claimedReward` is incremented the user can never claim that same reward again — the entitlement is permanently zeroed out even though they never received the tokens.

### Impact Explanation
An ordinary user calling `incentiveDeposit()` risks permanently losing their incentive reward entitlement: they pay in WOM (irreversibly, via `safeTransferFrom`) but the reward payout can fail silently, and the accounting (`claimedReward`) is updated as if payment succeeded, permanently freezing/erasing that portion of their unclaimed yield with no recovery path.

### Likelihood Explanation
This requires the reward token's `transfer()` to return `false` rather than revert on failure (e.g., a paused/blacklist state, or contract logic that returns false instead of reverting). It is not guaranteed to trigger under normal ERC20 behavior, but any deployment/reconfiguration of `usdt`/`busd` (which are owner-settable via `__arbWomUp_init`/`setup`) to a non-standard-reverting token, or a state where the token temporarily disallows transfers, immediately triggers permanent, un-recoverable loss for the depositing user.

### Recommendation
Use `SafeERC20.safeTransfer` for the reward payouts in both `ArbWomUp.incentiveDeposit` and `ArbWomUp2.incentiveDeposit` (consistent with how the WOM deposit leg already uses `safeTransferFrom`), and only update `claimedReward` after confirming the transfer succeeded, so that a failed transfer reverts the whole transaction instead of silently finalizing the claim.

### Proof of Concept
1. Owner configures `usdt` (or `busd`) to a token whose `transfer()` returns `false` on failure without reverting (or the token later enters a state — e.g. paused — where this occurs).
2. User calls `incentiveDeposit(amount)`; `_deposit` succeeds via `safeTransferFrom`, WOM is taken from the user.
3. `claimedReward[msg.sender] += rewardToSend` executes, then `IERC20(usdt).transfer(msg.sender, rewardToSend)` returns `false` but does not revert; `USDTRewarded` is emitted regardless.
4. User received no USDT, yet `claimedReward` reflects that the reward was paid; subsequent calls to `getRewardAmount` compute a lower or zero claimable amount, so the user can never recover the lost reward. [3](#0-2) [4](#0-3)

    function incentiveDeposit(
        uint256 _amount, uint256 _minMGPRec, bool _bullMode
    ) external _checkAmount(_amount) whenNotPaused nonReentrant {
        if (_amount == 0) return;

        uint256 rewardToSend = this.getRewardAmount(_amount, msg.sender);
        _deposit(_amount);
        claimedReward[msg.sender] += rewardToSend;
        
        if (_bullMode) {
            _bullMGP(rewardToSend, _minMGPRec, msg.sender);
        } else {
            IERC20(busd).transfer(msg.sender, rewardToSend);
            emit BUSDRewarded(msg.sender, rewardToSend);
        }
    }
