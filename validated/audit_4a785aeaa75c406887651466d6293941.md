### Title
Unbounded length-prefixed read in `SchnorrAggregate::read` enables memory-allocation denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The libtiff advisory (JLSEC-2025-255) describes a bug class where a crafted input drives an oversized memory allocation whose failure aborts the process (denial of service). The same class exists in Serai's in-scope `crypto/schnorr` crate: `SchnorrAggregate::read` trusts a 4-byte attacker-controlled length prefix and pushes that many group elements into a `Vec`, with no upper bound and no correlation check against remaining input. `SchnorrAggregate::verify` additionally pre-allocates `Vec::with_capacity(2 * len + 1)` based on the already-parsed, attacker-sized `Rs` vector.

### Finding Description
`SchnorrAggregate::read` reads a little-endian `u32` and then loops `u32::from_le_bytes(len)` times, pushing `C::read_G(reader)?` results into `Rs`:

- crypto/schnorr/src/aggregate.rs:77-88 — `let mut len = [0; 4]; reader.read_exact(&mut len)?; ... for _ in 0 .. u32::from_le_bytes(len) { Rs.push(C::read_G(reader)?); }`
- crypto/schnorr/src/aggregate.rs:138 — `let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);` in `verify`.

There is no cap on the declared count (up to 4,294,967,295 entries ≈ 137 GB of `C::G` elements for 32-byte encodings) and no early consistency check such as comparing the declared count against remaining reader length. A caller feeding untrusted bytes to `SchnorrAggregate::read` (e.g., batch-signature messages in processor/coordinator communication, which use `SchnorrAggregator`/`SchnorrAggregate`) lets an unprivileged peer supply a stream with a huge declared length. Two abort paths exist:

1. If the reader yields the declared bytes, the `Vec` grows until the global allocator fails → Rust aborts (allocation failure is not recoverable via `Result`).
2. Even with fewer bytes, `verify`'s `Vec::with_capacity(2n+1)` on the parsed `Rs` length amplifies allocation immediately (for `n` near `usize::MAX/2` this also risks capacity-overflow panic).

This is the direct analog of `tif_read.c` allocating based on untrusted TIFF fields and aborting on allocation failure.

### Impact Explanation
An unprivileged party who can get their bytes fed to `SchnorrAggregate::read`/`verify` can crash the signing/verification process — a processor node, coordinator, or any component deserializing aggregate signatures — causing denial of service of the threshold-signing pipeline. No secret material is needed; the attack only requires sending crafted bytes. Halting a validator/processor in a threshold network disrupts signing liveness and, depending on the deployment's redundancy, can stall bridge operations.

### Likelihood Explanation
Reachability requires a path from network-controlled input to `SchnorrAggregate::read`. `SchnorrAggregator`/`SchnorrAggregate` are used for batch Schnorr signatures in Serai's processor message flow (`processor/messages`), and the crate is explicitly in scope as production code handling peer-supplied data. The attack requires delivering a large buffer (for path 1) — proportional to the induced allocation — which limits amplification on strict transport size limits; however Serai's transaction/message size limits are enforced in out-of-scope coordinator code, and nothing in the in-scope deserialization layer itself enforces a bound. The `verify` pre-allocation path needs only the parsed vector length, not extra bytes beyond what was already read. Rate of exploitation: any malformed length field triggers at minimum a failed-read error; the crash requires the attacker to actually transmit the data or to reach `verify` with a large parsed `Rs`. Severity is Medium, matching the advisory (CVSS 5.5, availability-only impact).

Caveat: the allocation growth is linear in attacker-supplied bytes rather than superlinear (the count field alone doesn't force the allocation on a short reader — the loop errors on EOF). The strongest abort without proportional input is `verify`'s `with_capacity(2n+1)`, which is bounded by the largest `Rs` an attacker successfully deserializes. If no production caller pipes untrusted input into `SchnorrAggregate::read` without an outer size cap, the effective impact degrades.

### Recommendation
- Bound the count before reading in `crypto/schnorr/src/aggregate.rs` `SchnorrAggregate::read`: reject counts above a sane maximum (aggregate signature sets are bounded by the validator set size, e.g., `u16::MAX` or the protocol's actual max signer count).
- Where the reader supports it, compare the declared count against remaining input length and error early.
- In `verify`, avoid `with_capacity` scaling with an untrusted length, or cap `keys_and_challenges.len()` before allocating.

### Proof of Concept
```rust
// crypto/schnorr aggregate read path, e.g. with C = Ristretto
use schnorr::SchnorrAggregate;

// Attacker-controlled bytes: length prefix = u32::MAX, then enough valid
// 32-byte encodings (or a reader that synthesizes them) to exhaust memory.
let mut bytes = Vec::new();
bytes.extend_from_slice(&u32::MAX.to_le_bytes());
// Attaching ~u32::MAX group encodings (or serving them from a streaming
// reader) causes Rs to grow until the allocator aborts the process.
let _ = SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice());
```
With a `Read` implementation returning a valid encoding for `C::read_G` on each call, the loop at crypto/schnorr/src/aggregate.rs:83-85 performs ~4.3 billion pushes; `Vec` growth aborts on allocation failure, replicating the libtiff `tif_read.c` abort-on-alloc-failure DoS. Similarly, passing a large parsed `Rs` into `verify` triggers the `Vec::with_capacity((2 * len) + 1)` allocation at crypto/schnorr/src/aggregate.rs:138.
