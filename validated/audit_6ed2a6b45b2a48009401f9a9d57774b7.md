## Finding: Silent commit corruption from stale line-selection state reused against a freshly re-fetched diff

The Polynomial bug's core pattern is: a calculation (`newPosition`) is derived from one snapshot of state (`_getTotalPerpPosition()`), while a second, unaccounted-for piece of state (`queuedPerpSize`) has already advanced past that snapshot — and the code applies the result as if both were still in sync, silently producing a wrong on-chain position. The closest structural analog in Desktop is in the partial-commit ("stage selected lines") pipeline, where line-selection indices captured against one diff snapshot are blindly reapplied against a second, independently-fetched diff snapshot with no reconciliation check.

### Title
Partial-commit patch generation reuses stale line-selection indices against a freshly re-fetched diff, silently corrupting committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages a partial selection of lines for commit, Desktop stores the selection as *line indices* on `WorkingDirectoryFileChange.selection` [1](#0-0) , decoupled from the diff content that produced those indices. At commit time, `applyPatchToIndex` independently re-fetches the working directory diff via `getWorkingDirectoryDiff` and immediately builds the patch from that new diff using the old, unvalidated indices [2](#0-1) . `formatPatch` maps `absoluteIndex = hunk.unifiedDiffStart + lineIndex` back onto the freshly-fetched hunks and uses `file.selection.isSelected(absoluteIndex)` with no verification that the underlying line content still matches what was originally selected [3](#0-2) .

### Finding Description
The intended invariant is: "the patch committed must correspond exactly to the lines the user selected in the diff they were looking at." That invariant silently breaks whenever the working-directory file content changes between the moment a `WorkingDirectoryFileChange` with its `selection` is captured (e.g., in the Changes view, or passed into `_commitIncludedChanges`) and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` actually re-derives the diff and turns the selection into a unified patch.

Desktop's own code acknowledges this exact class of drift, but the acknowledged mitigation only covers the live UI diff-refresh path, not the commit-time patch generation path: [4](#0-3) 

That logic runs in `updateChangesWorkingDirectoryDiff`, which trims out selection indices that no longer correspond to includable lines *in the UI's model of the diff*. However, `_commitIncludedChanges` passes `state.changesState.workingDirectory.files` (with whatever `selection` object is attached at that point) straight into `createCommit`, and `applyPatchToIndex` performs a completely separate, unsynchronized `getWorkingDirectoryDiff` call [5](#0-4) . There is no hash/content check, no hunk-boundary comparison, and no re-validation between the diff that produced the user's selection and the diff that is used to render the final patch. Any timing where the file mutates in that window causes `formatPatch` to reinterpret the stale indices against new hunk contents, producing a patch that stages/commits different lines than the user intended — potentially including content the user never reviewed, or dropping content the user meant to keep.

### Impact Explanation
This directly matches the in-scope impact "silent corruption of what the user commits or pushes." A user could unknowingly commit and push unintended content (e.g., partially-reviewed sensitive text, or content differing from what they visually approved in the diff viewer), with no error, warning, or diff-content check surfaced by Desktop. Because the corrupted commit is created and can be pushed without any indication of the mismatch, this can propagate incorrect/undesired content into shared history.

### Likelihood Explanation
This requires the working-directory file to change between the selection being made and the final patch generation at commit time — e.g., from an external editor autosave, a build/format-on-save tool, a background process, or content rewritten by Git filters/smudge handlers tied to a cloned repository's `.gitattributes`/LFS configuration. No admin rights, local exploitation tooling, or social engineering beyond normal repository use is required; the race window exists any time Desktop's diff/staging isn't atomic with respect to file mutation, which is architecturally guaranteed by the two independent diff-fetch call sites (`updateChangesWorkingDirectoryDiff` in `app-store.ts` and the second fetch inside `applyPatchToIndex`).

### Recommendation
Before generating the patch in `applyPatchToIndex`/`formatPatch`, validate that the diff being used to interpret `file.selection` is the same diff the selection was computed against — for example, by re-deriving/reconciling `selectableLines` from the freshly-fetched diff (as already partially done in `updateChangesWorkingDirectoryDiff`) and failing/re-prompting the user if the diff has materially changed, rather than silently mapping stale indices onto new hunk content. At minimum, associate a content fingerprint (e.g., diff/hash of the pre-image) with `DiffSelection` and abort the partial-commit path if it doesn't match the diff fetched at staging time.

### Proof of Concept
1. Open a repository in Desktop and select a file with a multi-hunk diff in the Changes view.
2. Select only specific lines/hunks for inclusion (partial selection), producing a `DiffSelection` with `divergingLines` tied to hunk offsets from the diff rendered at that moment.
3. Externally modify the same file (e.g., via an editor auto-save, a formatter, or a Git smudge/clean filter triggered by another git operation) so that hunk boundaries shift, without Desktop's Changes view re-synchronizing the selection state before the commit action fires.
4. Click "Commit" — `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff fresh [6](#0-5)  and applies the old `file.selection` indices to the new hunk layout via `formatPatch` [3](#0-2) .
5. Inspect the resulting commit: it contains different content than what the user visually selected, with no warning shown.
