### Title
Cross-chain `fillOrder` lets a solver dictate escrow-withdrawal amounts from unverified calldata instead of the recorded escrow — potential arbitrary-amount fund drain - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The reported Shardus bug is fundamentally about a fund-moving code path trusting caller/gossip-supplied data (`appData`) instead of deriving it from independently verified state. The local Hyperbridge analog is in the IntentGateway's cross-chain fill path: `_fillCrossChain` builds the `WithdrawalRequest.tokens` field that is later dispatched to the source chain to release escrow directly from the solver-supplied `order.inputs` calldata, rather than from the source chain's own recorded escrow ledger. This is architecturally inconsistent with the same-chain path, which correctly derives the withdrawal amount from the persisted `_orders[commitment][token]` mapping.

### Finding Description
`IntentGatewayV2.fillOrder()` computes `commitment = keccak256(abi.encode(order))` from the calldata `order` argument supplied entirely by the caller (the solver) on the **destination** chain: [1](#0-0) 

For cross-chain orders it calls `_fillCrossChain`, which builds the redeem message using `order.inputs` verbatim — a solver-controlled field on a chain that has no visibility into what was actually escrowed on the source chain: [2](#0-1) 

Compare this to the same-chain path `_fillSameChain`, which explicitly reads the amount to release from the persisted escrow record `_orders[commitment][token]` — the ground-truth value written at `placeOrder` time — rather than trusting `order.inputs` directly: [3](#0-2) 

and `_cancelSameChain` follows the identical pattern of reading `_orders[commitment][token]` rather than the calldata `order.inputs`: [4](#0-3) 

The cross-chain settlement message is authenticated on the source chain only by *sender identity* (that `request.from` equals the registered peer gateway instance for `request.source`), not by re-deriving or cross-checking the withdrawal amount against the source chain's own escrow bookkeeping: [5](#0-4) 

This mirrors the root cause of the external report exactly: a value that should be re-derived from trusted local state (there: `nominee`/stake data via `txPreCrackData`; here: the escrowed input amount via `_orders[commitment]`) is instead accepted from a remote, attacker-influenced source (there: gossiped `appData`; here: solver-supplied `order.inputs` on a different chain) and used directly to move funds.

I was not able to fully inspect the body of the source-chain `_withdraw`/`withdraw()` function that ultimately processes `WithdrawalRequest.tokens` (only its call sites were visible in the available context) — this is the piece that determines whether the transferred amount is capped/checked against actual escrow before executing `IERC20.transfer`. If that function trusts `body.tokens[i].amount` for the given `commitment` without independently validating it against `_orders[commitment][token]` (the way `_cancelSameChain` does), a solver can dispatch an arbitrary `WithdrawalRequest` (any token, any amount) while paying near-zero on the destination side (e.g., an order with an empty `output.assets` array, so the fill loop transfers nothing), and drain the gateway's token balance on the source chain.

### Impact Explanation
If the source-side `withdraw()` handler does not independently validate the requested amount against escrow ledger state, this is a direct fund-loss / unauthorized-transfer primitive reachable by any solver (unprivileged actor), matching the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories — analogous to the original report's reward theft via untrusted appData.

### Likelihood Explanation
The destination-chain `fillOrder` entry point is fully permissionless and its `order` argument is entirely attacker-controlled calldata; the only genuine cross-chain authentication is of the *sender module identity*, not of the settlement amount's provenance. This makes the attack straightforward to attempt for anyone willing to call `fillOrder` with a crafted `Order` (zero-cost output, inflated `inputs`). The severity/likelihood hinges entirely on the unread `_withdraw` implementation; I could not confirm within the available tool budget whether it re-validates `tokens` against `_orders[commitment]` before transferring, which is why this is flagged rather than confirmed.

### Recommendation
Have `withdraw()` on the source chain independently verify each `tokens[i].amount` against the escrow amount recorded under `_orders[commitment][token]` at `placeOrder` time (the same pattern already used by `_fillSameChain`/`_cancelSameChain`), rather than trusting the amount carried in the cross-chain `WithdrawalRequest` body. The redeem/refund message should only ever be able to release up to what was actually escrowed for that specific `commitment`.

### Proof of Concept
Not executable from the available context — a full PoC requires confirming the implementation of `_withdraw`/`withdraw()` in the source-chain `ExtrinsicIntents.sol` (not fully retrievable in this session). Conceptually: a solver calls `fillOrder(order, options)` on the destination chain with `order.output.assets` empty (so the fill loop pays nothing) and `order.inputs` set to an arbitrary token/amount; `_fillCrossChain` dispatches a `RedeemEscrow` message carrying those attacker-chosen `tokens` back to the source chain, where `onAccept()`/`withdraw()` would transfer them to the solver if the amount is not cross-checked against the real escrow ledger.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
