### Title
Cached FROST preprocess is reused across distinct messages/participant sets, enabling nonce reuse and secret share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` caches the FROST preprocess **seed** keyed only on `context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`). Every subsequent call — including the re-sign inside `complete` — reconstructs identical nonces via `AlgorithmSignMachine::from_cache` / `seeded_preprocess` (ChaCha20Rng seeded from the cached seed). Nothing binds the cached preprocess to the participant set or the message being signed, so the same deterministic nonce can be applied to two different challenges. Analogous to CVE-2021-32062, a restriction intended to scope a security-sensitive resource (here, a one-time nonce) to a specific input fails to enforce which inputs it may be used with.

### Finding Description

- `preprocess_internal` loads/creates the cache purely by `context`: `CachedPreprocesses::get(self.txn, &self.context)` / `set(...)` — `coordinator/src/tributary/signing_protocol.rs:123-145`. The `participants` argument and the eventual `msg` are not part of the key.
- `from_cache` → `seeded_preprocess` regenerates `nonces` deterministically from the seed — `crypto/frost/src/sign.rs:121-145`.
- `DkgConfirmer::share` and `DkgConfirmer::complete` both call `share_internal` → `preprocess_internal` with the *same* context — `signing_protocol.rs:288-327`. `complete` re-derives the signing machine and produces a second signature share.
- The signed message is `set_keys_message(set, removed_participants, key_pair)` — `substrate/validator-sets/primitives/src/lib.rs:148-154`. `removed_participants` comes from `removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)` evaluated fresh in each `DkgConfirmer::new` — `signing_protocol.rs:263-277`. Because it is read from live DB state at call time, a validator-removal event between the `share()` call and the `complete()` call (or between two `share()` calls) yields a *different* `msg` under the *same* cached nonces.
- In `sign_share`, the share is `s = nonce + c·secret_share` with `c = hram(R, A, len‖ctx‖msg)` — `crypto/frost/src/algorithm.rs:201-211`, `crypto/schnorrkel/src/lib.rs:110-129`. Same nonce, two different `c` values ⇒ `secret_share = (s₁ − s₂)/(c₁ − c₂)`.

### Impact Explanation

Signature shares are published on the public tributary. Anyone observing two shares produced under the same seed but different messages recovers the validator's MuSig secret share (`params.secret_share()`), compromising that validator's key used for DKG confirmation — the root of trust for confirming threshold keys on-chain. This is concrete key-share recovery reachable with public data.

### Likelihood Explanation

Requires two signing calls under the same `(DkgConfirmer, attempt)` context with differing `removed`/`key_pair`. `removed` is stateful and can legitimately change as removal transactions are processed during the attempt window, so divergence occurs in normal operation — no byzantine behavior needed to *expose* the reused nonce (exploiting it only needs the two public shares). The structural flaw — cache keyed without binding to msg/participants — is unconditional.

Note: I could not fully verify the exact call sequence in `coordinator/src/tributary/handle.rs` (index limits), so the precise triggering path (share-then-complete vs. repeated share) is inferred from `DkgConfirmer`'s public methods; the cache-without-binding defect itself is confirmed in code.

### Recommendation

Include the participant set and the message (or their hashes) in the `CachedPreprocesses` key / encryption-key preimage, so a cached seed is only ever reused for the identical signing instance; alternatively regenerate a fresh preprocess (evict the cache) whenever `participants` or the derived `msg` differs, and never reuse a cached seed after `share_internal` has produced a share for a different message.
