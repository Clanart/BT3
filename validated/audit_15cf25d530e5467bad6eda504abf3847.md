### Title
DNS-rebinding bypass of the JSON-RPC `virtualHostHandler` via unspecified `0.0.0.0` Host header - (File: networks/rpc/http.go)

### Summary
The Kaia JSON-RPC HTTP server implements a Host-header allowlist (`virtualHostHandler`) specifically to defeat DNS-rebinding attacks against the RPC endpoint, mirroring the exact bug class described in the referenced report (CVE-2022-32212/CVE-2018-7160 class). The implementation treats **any** string that `net.ParseIP` can parse as automatically trusted and bypasses the vhosts allowlist entirely — including `0.0.0.0`, the unspecified/"any" address — instead of restricting the bypass to genuinely safe loopback/explicit addresses.

### Finding Description
`virtualHostHandler.ServeHTTP` extracts the `Host` header, and if it parses as an IP address it unconditionally forwards the request to the RPC handler, skipping the vhosts whitelist check entirely: [1](#0-0) 

Because `net.ParseIP("0.0.0.0")` succeeds, a Host header of `0.0.0.0:<port>` is treated as trusted and passed straight through to the JSON-RPC dispatcher, with no check for `IsUnspecified()`/loopback semantics.

This is the same root cause pattern as the report: an attacker lures a victim (with the node's HTTP-RPC endpoint reachable, e.g. bound to `127.0.0.1` or a LAN interface) to a page that opens `http://0.0.0.0:<rpc-port>`. On macOS/browsers exhibiting the `.local` mDNS quirk (or any environment where DNS rebinding to `0.0.0.0` is possible), the attacker's DNS infrastructure can first serve an attacker-controlled IP for the `.local` name resolution used behind the scenes, then rebind the same-origin `0.0.0.0:<port>` target to `127.0.0.1`. Since the Host header sent by the browser in both phases is `0.0.0.0:<port>`, the `virtualHostHandler` will happily forward the second (rebound) request straight to the node's local RPC server — completely bypassing the purpose of the vhosts whitelist (which is by default just `localhost`): [2](#0-1) 

The comment in the configuration explicitly documents the intended protection this handler is supposed to provide: [3](#0-2) 

which is exactly what this `0.0.0.0` gap defeats.

### Impact Explanation
If exploited, an attacker's malicious webpage can bypass the Host-header/DNS-rebinding protection and reach the node's JSON-RPC HTTP endpoint as if it were an authorized local caller. Any JSON-RPC namespace exposed over HTTP (whichever modules are configured, e.g. `eth`/`kaia`/`personal`/`admin` if enabled) becomes reachable from the attacker's browser context, allowing unauthorized transaction submission, account operations, or node administration depending on what APIs are exposed — a concrete unauthorized-access / potential value-movement vector consistent with the "unrestricted public RPC caller" reachable surface.

### Likelihood Explanation
Exploitation requires: (1) the victim node's HTTP-RPC server to be reachable by the attacker's rebinding path (commonly true for `127.0.0.1`/LAN-bound RPC endpoints accessed by browser-based dApps or wallets), (2) the victim visiting an attacker page, and (3) DNS-rebinding conditions similar to those in the original report (or any environment allowing rebind to the same `0.0.0.0` origin). This mirrors a well-known, previously-fixed bug class in comparable software, so the technique itself is established and reproducible; the main variable is the specific rebinding trick used to make the browser treat `0.0.0.0` as re-bindable, which is documented in the source report.

### Recommendation
Harden `virtualHostHandler.ServeHTTP` in `networks/rpc/http.go` to not blanket-trust every parseable IP address. Specifically, reject or otherwise handle unspecified addresses (`ipAddr.IsUnspecified()`, i.e. `0.0.0.0`/`::`) the same as an untrusted hostname, requiring it to be present in the vhosts allowlist (or disallowing it outright), consistent with the IANA guidance cited in the original report for the `0.0.0.0/8` reserved range.

### Proof of Concept
1. Start a Kaia node with the HTTP-RPC server enabled and bound to a locally reachable interface (default host `127.0.0.1`, per `node/defaults.go`).
2. Set up an attacker-controlled DNS entry mirroring the report's approach, resolving to attacker's IP first, then to `127.0.0.1` (the rebinding).
3. Lure the victim to a page that issues a fetch/navigation to `http://0.0.0.0:<rpc-port>/`.
4. Because `virtualHostHandler` (`networks/rpc/http.go:476-503`) sees `Host: 0.0.0.0:<rpc-port>`, parses it successfully via `net.ParseIP`, and forwards it unconditionally, the second (rebound) request reaches the real local RPC server, bypassing the vhosts allowlist meant to block exactly this class of attack.

```go
// ServeHTTP serves JSON-RPC requests over HTTP, implements http.Handler
func (h *virtualHostHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	// if r.Host is not set, we can continue serving since a browser would set the Host header
	if r.Host == "" {
		h.next.ServeHTTP(w, r)
		return
	}
	host, _, err := net.SplitHostPort(r.Host)
	if err != nil {
		// Either invalid (too many colons) or no port specified
		host = r.Host
	}
	if ipAddr := net.ParseIP(host); ipAddr != nil {
		// It's an IP address, we can serve that
		h.next.ServeHTTP(w, r)
		return

	}
	// Not an ip address, but a hostname. Need to validate
	if _, exist := h.vhosts["*"]; exist {
		h.next.ServeHTTP(w, r)
		return
	}
	if _, exist := h.vhosts[host]; exist {
		h.next.ServeHTTP(w, r)
		return
	}
	http.Error(w, "invalid host specified", http.StatusForbidden)
}
```
