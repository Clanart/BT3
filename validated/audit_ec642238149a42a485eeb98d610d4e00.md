### Title
Unbounded MGP reward drain in `ArbWomUp3.incentiveDeposit` mode=1 via externally-sourced tier and missing per-call reward decrement - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount(_amountToConvert, _account, false)` derives the reward multiplier from `getUserTier(_account)`, which reads `mWomSV.getUserTotalLocked(_account)` — a balance entirely unrelated to and unaffected by the mode=1 deposit path itself. Combined with the fact that the `_lock == false` branch computes `mgpReward` as a flat `_amountToConvert * rewardMultiplier[tier] / DENOMINATOR` with no subtraction of previously granted rewards (unlike the `_lock == true` branch, which subtracts `calDoubledCounted`), any account holding a modest `mWomSV` lock can repeatedly call `incentiveDeposit(_amount, ratio, false, 1)` with large `_amount` values and receive the top-tier multiplier on the *entire* amount every single call, with no cap besides the contract's MGP balance.

### Finding Description
`incentiveDeposit` computes the reward before depositing: `rewardToSend = this.getRewardAmount(_amount, msg.sender, _mode == 2)` [3](#0-2) . For `_mode == 1`, `_lock` is `false`, and `_deposit` for mode 1 only converts WOM to mWOM and forwards it to `smartWomConvert` — it never interacts with `mWomSV` [4](#0-3) .

Yet `getRewardAmount`'s `!_lock` branch computes:
```solidity
mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
``` [5](#0-4) 

and `getUserTier` is defined purely in terms of `mWomSV.getUserTotalLocked(_account)`:
```solidity
function getUserTier(address _account) public view returns (uint256) {
    uint256 userMWOMSVBal = mWomSV.getUserTotalLocked(_account);
    ...
``` [6](#0-5) 

This is a value the attacker fully controls independent of any mode=1 activity, since `mWomSV.lock(uint256)` is a public, unprivileged function [1](#0-0) . Critically, unlike the `_lock == true` branch, which subtracts `calDoubledCounted(_account)` (itself derived from `mWomSV.getUserTotalLocked`) to prevent double-counting reward already implied by the existing lock [7](#0-6) , the `!_lock` branch performs no such subtraction and no tracking of cumulative amounts already converted by `_account`. Each call to `incentiveDeposit(_amount, _convertRatio, false, 1)` independently computes and pays out `_amount * rewardMultiplier[tier] / DENOMINATOR` in full, and this is not bounded by `nonReentrant` or `whenNotPaused` in any way relevant to the double-spend — those guards only prevent reentrancy/pausing, not repeated legitimate calls.

### Impact Explanation
An attacker locks a comparatively small amount of `mWOM` into `mWomSV` (via `mWomSV.lock()` directly, or via a single cheap mode=2 `incentiveDeposit`) to reach the top reward tier, then repeatedly calls `incentiveDeposit(largeAmount, ratio, false, 1)`. Each call yields the top-tier `rewardMultiplier` applied to the entire `_amount`, capped only by `IERC20(mgp).balanceOf(address(this))` [8](#0-7) . This allows draining the entire MGP reward pool intended to incentivize proportionally-tiered participation, i.e., theft of unclaimed MGP yield at scale, matching the "theft of unclaimed yield" impact class.

### Likelihood Explanation
This requires only: (1) enough WOM to convert (or reused/looped capital, since mode 1 forwards WOM into `smartWomConvert` and does not lock the attacker's capital), and (2) a single modest `mWomSV` lock to reach the top tier once. Both are achievable by any unprivileged EOA with no special permissions, and the exploit is fully repeatable across many transactions/blocks as long as the reward pool holds MGP.

### Recommendation
For the `_lock == false` (mode=1) branch, derive the tier from a deposit/conversion amount tracked specifically for this program (e.g., a per-account cumulative "converted" mapping analogous to `userWOMDeposited` in `ArbWomUp.sol`), and subtract already-claimed reward for that account, mirroring the bracket-accumulation and `claimedReward` deduction pattern used in `ArbWomUp.sol.getRewardAmount` [9](#0-8) , instead of reusing `mWomSV.getUserTotalLocked` (a balance unrelated to mode=1's actual activity) as a flat, non-decrementing multiplier source.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, `mWOM`, mock `smartWomConvert`, and `vlMGP`; set `rewardTier = [0, X, Y]` and `rewardMultiplier = [low, mid, high]` via `setMultiplier`; fund the contract with a large MGP balance.
2. As attacker (unprivileged EOA), acquire enough WOM to mint mWOM and call `mWomSV.lock(smallAmount)` sized to just clear the top `rewardTier` threshold.
3. Call `incentiveDeposit(largeAmount1, ratio, false, 1)` and assert `vlMGP` balance for attacker increased by `largeAmount1 * rewardMultiplier[topTier] / DENOMINATOR`.
4. Call `incentiveDeposit(largeAmount2, ratio, false, 1)` again (same attacker, same tiny `mWomSV` lock unchanged) and assert the reward is again `largeAmount2 * rewardMultiplier[topTier] / DENOMINATOR` — i.e., not diminished or bounded relative to the attacker's small underlying lock, demonstrating unbounded repeatable extraction versus the fair/expected behavior where reward should scale with an account's own mode-1 program participation, not an externally-sourced, non-decrementing tier proxy.
