### Title
Attacker-injected `ReceivedOutput` values falsify the input accounting of a `SignableTransaction` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Tokemak issue is an accounting value (`externalBalance`/`debtValue`) derived from an externally mutable source (`maverickRewarder.balanceOf(address(this))`), which anyone could inflate via a permissionless `stake(amount, account)` — so the vault's reported balance diverged from what it actually deposited. The analog in Serai's in-scope code is `SignableTransaction`'s accounting of input funds: `SignableTransaction::new` computes `input_sat`, `NotEnoughFunds`, change, and `fee()` entirely from the `output.value` fields embedded in caller-supplied `ReceivedOutput`s, which are deserializable from untrusted bytes via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`). `TransactionSignMachine::sign` then commits those attacker-controlled values into the Taproot sighash via `Prevouts::All(&self.tx.prevouts)` (`send.rs:373-390`). The only integrity check performed on inputs is that `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` in `multisig` (`send.rs:275-279`) — the claimed `value` and `outpoint` are never validated against the chain.

### Finding Description
`ReceivedOutput::read` accepts an arbitrary scalar offset, an arbitrary `TxOut` (including its `value`), and an arbitrary `OutPoint` — there is no binding between the claimed value and the real UTXO on chain (`mod.rs:122-134`). `SignableTransaction::new` sums `input.output.value` into `input_sat` and uses it to check `NotEnoughFunds` and compute the change amount (`send.rs:175`, `send.rs:215-235`). `fee()` is `sum(prevouts.value) - sum(outputs)` (`send.rs:138-141`). During signing, `Prevouts::All` commits to the claimed `prevouts` (`send.rs:375`); BIP-341 signatures commit to these amounts, and consensus does **not** check that committed prevout amounts equal the real UTXO amounts — validity only requires `real_inputs - outputs >= 0` as fee.

Therefore an attacker who can feed a crafted `ReceivedOutput` to the transaction-construction path can:

- Understate `output.value` on an outpoint genuinely owned by the group key: `input_sat` is underestimated, so change is computed too small or omitted, while the *real* on-chain input is larger. The resulting signed transaction is valid and spends the real UTXO, burning `(real_value - claimed_value)` as an unintended miner fee. Signers believe they authorized fee `needed_fee`; the broadcast transaction pays far more.
- Overstate `output.value` (the direct Maverick analog — inflating the reported balance): `NotEnoughFunds` passes and the group signs a transaction that can never confirm, since real inputs < outputs. The multisig's reported spendable balance is inflated, mirroring the inflated `externalBalance`.

### Impact Explanation
Like the Maverick finding, this is a divergence between an internal accounting figure (`input_sat`, `fee()`, `needed_fee`, change computation) and the actual controllable value. Understatement produces a valid, consensus-acceptable transaction that permanently burns group funds as fees — a concrete loss. Overstatement wastes a full threshold signing round on an unbroadcastable transaction (funds reported spendable that are not). Note the understatement direction additionally constitutes signing of an unintended message in effect: participants intend fee `needed_fee` but authorize a transaction whose true fee is the real input sum minus outputs.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read`/`SignableTransaction::new` — the rules explicitly treat bytes fed to `ReceivedOutput::read` as reachable public input. The attacker must use an outpoint whose `script_pubkey` matches `key + G*offset` for an offset they provide; reusing a legitimately scanned script (e.g., the base address at offset `ZERO`, or a branch/change script whose offset is derivable from `KEY_DST` = `b"Serai Bitcoin Output Offset"` via `hash_to_F` in `processor/src/networks/bitcoin.rs:308-344`) satisfies the `multisig` script check, and the offset field is fully attacker-chosen in the serialized form. Exploitation needs no key material, no validator collusion, and no protocol privilege — only the ability to inject a fabricated output record.

### Recommendation
Do not trust the `value` (or `outpoint`) embedded in a `ReceivedOutput` for accounting. Before constructing a `SignableTransaction`, verify each input against the chain (fetch the real `TxOut` for `outpoint` and compare), or maintain an internal ledger of confirmed output values keyed by outpoint — the exact analog of the report's recommended "internal global counter" instead of trusting externally mutable balance sources. At minimum, `SignableTransaction::new`/`multisig` should treat `prevouts[i]` as unverified claims and reject any `ReceivedOutput` whose serialized value wasn't produced by `Scanner::scan_transaction`/`scan_block` on a confirmed block.

### Proof of Concept
1. The group controls key `K`; `p2tr_script_buf(K)` is its public deposit address. A real UTXO `O` of 100,000 sats pays to that script at outpoint `P`.
2. Attacker serializes `ReceivedOutput { offset: Scalar::ZERO, output: TxOut { value: 1,000 sats, script_pubkey: p2tr_script_buf(K) }, outpoint: P }` and delivers the bytes to the input-construction path (`ReceivedOutput::read`, `mod.rs:122`).
3. `SignableTransaction::new` computes `input_sat = 1,000`; `multisig` passes because `p2tr_script_buf(K.offset(0)) == script_pubkey` (`send.rs:276-278`).
4. Participants sign via `TransactionSignMachine::sign` with `Prevouts::All` committing to the fabricated 1,000-sat prevout (`send.rs:375-390`); `complete` yields a valid signed transaction (`send.rs:417-425`).
5. Broadcasting spends the real 100,000-sat UTXO; the 99,000-sat discrepancy becomes miner fees, while `fee()`/`needed_fee()` reported only the intended amount (`send.rs:133-141`).
