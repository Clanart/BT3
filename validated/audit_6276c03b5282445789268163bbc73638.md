### Title
Missing Slippage Control in `WombatPoolHelperV2.depositFor` Enables Fund Loss via Sandwich Attack - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor` hardcodes the `_minimumLiquidity` parameter to `0` when depositing into the Wombat pool, unlike the sibling `deposit`/`depositNative` functions which let the caller specify their own slippage-protecting minimum. This mirrors the reported bug class: a user-facing deposit path that omits configurable slippage control, allowing the deposit to complete regardless of how unfavorable the exchange rate is at execution time.

### Finding Description
`deposit()` and `depositNative()` both forward a caller-supplied `_minimumLiquidity` value into `WombatStaking.deposit`, which passes it straight to the underlying Wombat pool's `deposit` call as the slippage bound [1](#0-0) . In contrast, `depositFor` unconditionally passes `0` as `_minimumLiquidity`: [2](#0-1) 

This value flows into `WombatStaking.deposit`, which uses it directly as the `_minimumLiquidity` argument to `IWombatPool(poolInfo.depositTarget).deposit(...)` — the only slippage guard in the entire deposit path [3](#0-2) . With `_minimumLiquidity` forced to `0`, the Wombat pool's internal slippage check is neutralized entirely for any deposit routed through `depositFor`, regardless of how the pool's exchange rate has moved between transaction submission and execution.

Any ordinary wallet calling `depositFor` (e.g., to deposit on behalf of another address, or through a front-end that uses this entry point) receives zero protection against exchange-rate manipulation or volatility, unlike callers of `deposit`/`depositNative`.

### Impact Explanation
An attacker monitoring the mempool can sandwich a `depositFor` transaction: swap heavily against the underlying Wombat pool asset right before the deposit executes (worsening the deposit token's exchange rate for LP minting), let the victim's zero-slippage deposit go through and receive a reduced amount of LP/receipt tokens, then reverse the swap afterward. Since the receipt token is minted 1:1 with LP received and immediately staked for `_for` [4](#0-3) , the victim permanently receives fewer receipt/staking tokens than the fair-value deposit should yield — a direct, unrecoverable loss of funds for the depositing/beneficiary wallet, with the difference captured by the attacker.

### Likelihood Explanation
Any unprivileged wallet can call `depositFor` at any time with no special permissions, and sandwich/MEV attacks against AMM pools are a well-established, low-cost, high-reliability attack technique. The hardcoded `0` removes the only protection value present in the codebase for this exact operation, making exploitation straightforward whenever the function is used.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (analogous to `deposit`) so callers can specify their own slippage tolerance, instead of hardcoding `0`:
```solidity
function depositFor(uint256 _amount, uint256 _minimumLiquidity, address _for) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Attacker observes a pending `depositFor(_amount, _for)` transaction in the mempool.
2. Attacker front-runs it with a large swap into the Wombat pool's deposit-token asset to shift the pool's internal exchange rate unfavorably.
3. The victim's `depositFor` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit` succeeds even though the LP output is far below fair value [2](#0-1) .
4. The reduced LP amount is minted into the receipt token and staked to `_for` [5](#0-4) .
5. Attacker back-runs with the reverse swap, restoring the pool rate and pocketing the value difference, while the victim is left permanently under-compensated for their deposit.
