### Title
Relayer reward misattribution across unrelated state machines via unbound signer field in batch's first message - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`Pallet::<T>::on_executed` (the `FeeHandler` implementation) derives the sole reward recipient for an entire batch of ISMP messages from a signature embedded in `messages[0]`, without binding that signer to the extrinsic's origin or to the specific state machine(s) that message actually advanced. It then iterates every `StateMachineUpdated` event produced by the whole batch — including chains updated by other messages in the batch — and pays the accumulated `blocks * block_cost` reward for each of them to that single derived account.

### Finding Description
`on_executed` extracts a candidate relayer only from the first message: [1](#0-0) 

The `signer` field is attacker-suppliable: `Signature::decode` and `verify_and_get_sr25519_pubkey` only prove that *some* keypair signed `keccak_256(consensus_proof)` — it does not prove the pubkey belongs to the extrinsic's submitter (`handle_unsigned` is callable with `RuntimeOrigin::none()`, i.e. permissionless) or that it is a registered/whitelisted relayer: [2](#0-1) [3](#0-2) 

Once a signer is recovered from `messages[0]`, the code aggregates **all** `StateMachineUpdated` events emitted anywhere in the batch — not just events tied to `messages[0]` — into `highest_per_state_machine`, and pays a reward for each of them to that single `relayer_account`: [4](#0-3) 

Because an attacker fully controls the ordering and content of the `Vec<Message>` submitted in a batch (the `handle_unsigned` extrinsic takes an arbitrary message vector), they can:
1. Set `messages[0]` to a trivially cheap `Message::Consensus` for state machine A, self-signing it with their own keypair (any keypair can sign arbitrary bytes — the signature check never authenticates "this account did the costly work").
2. Append genuine, publicly-obtainable consensus proofs for high-`cost_per_block` state machines B, C, ... as later messages in the same batch.
3. When the batch is processed, `events` will contain `StateMachineUpdated` for A, B, and C. `on_executed` pays the reward for B and C — chains the attacker did not relay any distinguishing work for beyond copying public proof data — to the attacker's `relayer_account`, derived solely from message[0]'s self-signature.

This breaks the invariant that "reward flows only to the rightful relayer beneficiary": the reward for state machine B/C is diverted from the legitimate relayer whose message actually appears later in the batch to the attacker's account, purely because the attacker controls slot 0 and its signature.

### Impact Explanation
This directly causes wrongful movement of treasury-held relayer-incentive funds to an unintended beneficiary, and it undermines relayer reward accounting for the entire consensus-incentives pallet. Given `StateMachinesCostPerBlock` can be set arbitrarily high for chains needing frequent updates, the diverted amount (`blocks * block_cost`) can be significant per batch, and the attack is repeatable every time a batch containing multiple state machines' consensus updates is submitted.

### Likelihood Explanation
Likelihood is high: the attacker only needs to submit an unsigned/permissionless `handle_unsigned` extrinsic (as shown to be permissionless via `RuntimeOrigin::none()` in the test setup) with a crafted `Vec<Message>` where slot 0 is a cheap, self-signed consensus message, and subsequent slots contain copies of genuinely valid, publicly observable consensus proofs for other high-value chains. No privileged access, compromised infrastructure, or malicious relayer collusion is required — only reordering/inclusion of public proof data in a batch they construct themselves.

### Recommendation
Bind reward attribution to the specific message that produced each `StateMachineUpdated` event rather than applying a single signer recovered from `messages[0]` across the whole batch. Concretely: recover (and verify) a relayer signature per `Message::Consensus` entry, and only credit the state machine(s) whose consensus proof was included in that same message (or otherwise correlate each event back to the message/proof that generated it) before crediting rewards. Additionally, consider requiring the recovered signer to match the extrinsic's signed origin (or an explicitly registered relayer identity) rather than trusting an arbitrary self-signature over proof bytes.

### Proof of Concept
1. Configure `StateMachinesCostPerBlock` with a high cost for state machine `B` and a low/zero cost for state machine `A`.
2. Attacker builds `messages = [Message::Consensus(trivial proof for A, signer = attacker's self-signature), Message::Consensus(genuine, publicly obtained proof for B)]` and submits via `pallet_ismp::Pallet::<T>::handle_unsigned(RuntimeOrigin::none(), messages)`.
3. Processing emits `StateMachineUpdated` events for both A and B; `on_executed` in `modules/pallets/consensus-incentives/src/impls.rs` recovers `relayer_account` solely from message[0]'s signature and then loops over `highest_per_state_machine`, paying the reward for B's block span to `relayer_account` as well as A's.
4. Assert: `Balances::balance(&attacker_account)` increases by `blocks_B * cost_per_block_B` even though the attacker did not "relay" B's proof under any accountable identity distinct from a self-chosen signature — confirming the reward for B is not restricted to the legitimate relayer of that update.
