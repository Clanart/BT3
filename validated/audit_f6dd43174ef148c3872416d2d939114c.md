## Title
Automatic, unconfirmed rewrite of a repository's `origin` remote URL from a GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

## Summary
The Trail of Bits finding is about `Main.transferOwnership()` performing a critical, security-relevant reconfiguration (who controls the contract) in a single un-confirmed step instead of a two-step propose/accept flow. The GitHub Desktop analog is `updateRemoteUrl()`, which silently rewrites a repository's `origin` remote — the destination of every future `git push`/`git fetch` — based on data returned by the GitHub API, with no user confirmation step, unlike Desktop's own pattern for comparable remote changes (`UpstreamAlreadyExists` dialog) which does prompt the user.

## Finding Description
`updateRemoteUrl()` compares the local `origin` remote URL to the `clone_url` field of an `IAPIRepository`/`IAPIFullRepository` object fetched from the GitHub API, and if a small set of heuristic conditions hold, calls `gitStore.setRemoteURL()` to rewrite the remote — with no dialog, confirmation, or diff shown to the user: [1](#0-0) 

The only guards are: the remote isn't `null`, the URL protocol (`ssh`/`https`) is unchanged, the previously-stored `gitHubRepository.cloneURL` still matches the current remote (i.e. the user hasn't "manually" diverged), and the new URL doesn't already match. None of these validate that the API response is trustworthy — they only prevent *accidental* churn, not a *malicious* update.

This function is invoked automatically, without any user action or prompt, from `repositoryWithRefreshedGitHubRepository()`: [2](#0-1) 

That method runs on ordinary background events the user does not initiate deliberately as a "change my remote" action, including: selecting a repository (`_selectRepositoryRefreshTasks`), adding a repository from disk (`_addRepositories`), and generally whenever `withRefreshedGitHubRepository` is used: [3](#0-2) [4](#0-3) 

The underlying git operation is a real `git remote set-url`: [5](#0-4) 

By contrast, Desktop already has a UI pattern for this exact class of decision — updating a remote pointer based on server-side repository info — that correctly asks the user first: `UpstreamAlreadyExists`, shown when a fork's `upstream` remote doesn't match the parent repo returned by the API: [6](#0-5) 

And the manual "Repository Settings → Remote" flow is an explicit, user-initiated single text field edit that the user types and submits themselves: [7](#0-6) [8](#0-7) 

`updateRemoteUrl()` bypasses both of these confirmation mechanisms and silently applies the change on the origin remote.

## Impact Explanation
The `origin` remote determines where `git push` sends the user's commits and where `git fetch`/`git pull` retrieve code from. If an attacker can influence what `apiRepo.clone_url` resolves to for a repository the victim already has open in Desktop — e.g., by taking over a repository name after the legitimate owner renamed/transferred it away (a well-documented "repo-jacking" technique), or by controlling a GitHub Enterprise Server endpoint/proxy the victim's Desktop is configured against — Desktop will automatically retarget `origin` to attacker infrastructure that matches protocol and superficially "looks like" the same repo family. Subsequent pushes silently go to the attacker's repository (source code / credential exposure via HTTPS creds in the URL, or via the credential helper), and subsequent fetches/pulls silently ingest attacker-controlled history and objects into the user's working copy — corrupting what the user believes they are pushing to or pulling from, without any warning.

## Likelihood Explanation
The rewrite path executes automatically as part of routine, frequent flows (opening the app, selecting a repository, adding a repository) — it requires no unusual user action once the attacker-controlled API response condition is met. It only requires the attacker to control one `IAPIRepository` object handed back to `repositoryWithRefreshedGitHubRepository()`; on GHES/proxy setups this can be an on-path attacker's API response, and on GitHub.com it maps to well-known repo-renaming/reclaiming abuse. The existing guard conditions (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) are consistency checks, not authenticity or user-consent checks, so they don't stop this path.

## Recommendation
- **Short term:** Require explicit user confirmation before silently rewriting `origin` (or any remote) based on GitHub API data, mirroring the existing `UpstreamAlreadyExists` dialog pattern — show old vs. new URL and let the user accept or decline.
- **Long term:** Treat remote-URL mutation as a privileged, security-sensitive action across the codebase; audit all call sites that invoke `gitStore.setRemoteURL()`/`setRemoteURL()` without direct, explicit user input (e.g., `updateRemoteUrl`, `_convertRepositoryToFork`) and gate the ones triggered by external/API data behind a confirmation step, consistent with how ownership-style, high-impact changes should use a "propose/confirm" pattern rather than a single automatic step.

## Proof of Concept
1. User has a repository open in Desktop with `origin` pointing at `https://github.com/victim-org/victim-repo` (recorded `GitHubRepository.cloneURL` matches this).
2. Attacker gains control of what `api.fetchRepository(owner, name)` returns for this `owner/name` pair — for example by claiming the repository name on GitHub.com after the legitimate org renamed/deleted it, or by operating/compromising the GHES endpoint the victim's account is configured against.
3. Attacker-controlled API response sets `clone_url` to an attacker-controlled HTTPS URL (same protocol, so `protocolsMatch` passes) that differs from the currently stored one (`!urlsMatch` passes), and the local remote hasn't manually diverged (`remoteUrlUnchanged` passes).
4. On the victim's next repository selection or app restart, `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` fires: [9](#0-8)  and silently calls `gitStore.setRemoteURL(...)`, executing `git remote set-url origin <attacker-url>` with no dialog shown to the user.
5. The victim's next `git push` in Desktop's Changes/History UI now pushes to attacker-controlled infrastructure, and future fetches pull attacker-controlled content, with the user having no indication that `origin` changed.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

/** Changes the URL for the remote that matches the given name  */
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
