### Title
Malicious FROST preprocess forcing the nonce-sum `R` to the point at infinity panics BIP-340 `Hram`/`x()`, aborting signing - (File: `networks/bitcoin/src/crypto.rs`)

### Summary
The upstream bug class is a crafted-input crash inside a decoder: attacker-controlled bytes drive the implementation into an out-of-bounds/abort condition, yielding a denial of service. In Serai, the same shape exists in the Bitcoin FROST algorithm: untrusted preprocess bytes are read into nonce commitments via `SignMachine::read_preprocess`/`Commitments::read`, summed into `nonce_sums`, and passed to `Hram::hram`, which calls `x()` — a function that unconditionally `expect`s the point to be non-infinity and panics otherwise. A malicious signer who submits a preprocess whose commitment is the negation of the other signers' commitment sum forces `R = identity` and deterministically panics every honest participant's `sign`/`complete`.

### Finding Description
`networks/bitcoin/src/crypto.rs` defines `x(key)` as `key.to_encoded_point(true)` followed by `.x().expect("point at infinity")`, and `x_only` similarly `expect`s a non-infinity point [1](#0-0) . `Hram::hram` feeds `x(R)` and `x(A)` into the BIP-340 challenge hash, so any call with `R` at infinity is an unconditional panic, not a `None`/`Err` [2](#0-1) . The `Schnorr` algorithm itself documents that it "MAY panic" for identity nonces/group keys [3](#0-2) .

On the input side, `AlgorithmSignMachine::read_preprocess` deserializes attacker-supplied bytes into `Commitments` via `Commitments::read` → `NonceCommitments::read` → `GeneratorCommitments::read` → `C::read_G`, with no rejection of the identity point and no check that per-nonce sums are non-infinity [4](#0-3) [5](#0-4) [6](#0-5) . `sign` then aggregates these preprocesses across participants and computes the nonce sums used for the challenge, with validation limited to the participant index set (sorted, unique, `<= n`) — nothing validates the group elements [7](#0-6) . Since preprocesses are broadcast before signing, a malicious participant sees all other `D` commitments and publishes `D_malicious = -Σ D_others` (and likewise `E` if needed), making the aggregated nonce `R = Σ D_i` the point at infinity. Both the sign-time challenge and `verify`/`verify_share` then hit `x(R)`'s `expect`, panicking the processor [8](#0-7) .

### Impact Explanation
Any single participant in a Bitcoin (secp256k1) FROST signing session can deterministically crash every honest signer's `sign`/`complete` path by submitting crafted preprocess bytes. This is a denial of service of the threshold signing pipeline: the panic unwinds through `read_preprocess` → `sign` → `hram` → `x()` and, in calling processor code, aborts the signing attempt. Because `panic`s here are not caught as `FrostError`, the malformed participant cannot even be blamed through the `InvalidParticipant`/`FrostError::InvalidPreprocess` channel — the process dies rather than returning an error [9](#0-8) . It does not leak key material; impact is availability only, matching the source CVE's DoS class.

### Likelihood Explanation
Reachable by any unprivileged party able to submit a preprocess message (a signing-set participant sending public bytes that flow through `read_preprocess`), which is an in-scope reachable input per the rules. The attack requires no collusion and no special ordering beyond seeing the other preprocesses, which is inherent to the two-round protocol. The trigger is deterministic — `R` at infinity always panics — unlike the comment's claim that identity nonces have "negligible probability ... even with malicious participants" [3](#0-2) . That assumption is wrong: the adversary directly chooses their commitment to cancel the honest sum.

### Recommendation
- Reject the identity point in `read_G`-consumed preprocess paths, or explicitly filter identity `D`/`E` commitments when aggregating `nonce_sums` in `crypto/frost/src/sign.rs` before `sign_share`/challenge computation.
- Make `Hram::hram`/`x()` non-panicking for edge inputs (return a defined challenge or a `FrostError`), and enforce in `Schnorr::verify`/`verify_share` that `R` and the group key are non-infinity, returning `None`/`Err` instead of panicking [1](#0-0) .
- Surface the failure as `FrostError::InvalidPreprocess(l)` so the malicious participant can be blamed rather than crashing the node.

### Proof of Concept
Conceptual, on a 2-of-2 Bitcoin `Schnorr` sign session:

1. Honest party broadcasts preprocess with nonce commitments `(D_h, E_h)` (`NonceCommitments` pairs [10](#0-9) ).
2. Attacker computes `D_m = -(D_h)` and `E_m = -(E_h)` (point negation on secp256k1), serializes both as SEC1 encodings, and submits them as their preprocess bytes.
3. Each signer calls `read_preprocess` → `Commitments::read` → `C::read_G`, which parses the points without an identity/sum check [4](#0-3) [5](#0-4) .
4. `sign` aggregates `nonce_sums`: `R = D_h + D_m = identity` [11](#0-10) .
5. `sign_share` computes the challenge via `Hram::hram(R, A, m)` → `x(R)` → `to_encoded_point(true).x().expect("point at infinity")` → panic on all signers [12](#0-11) [2](#0-1) .

Result: deterministic panic/abort of the signing session from crafted public bytes, matching the "crafted input → denial of service during processing" class of CVE-2017-15372.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
