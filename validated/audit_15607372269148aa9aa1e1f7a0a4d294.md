### Title
Stale line-selection bitset combined with a freshly re-fetched diff can silently stage the wrong lines during partial commit - (File: `app/src/lib/git/apply.ts`)

### Summary
This mirrors the Derby `blacklistProtocol` bug-class: a cached aggregate (there, `savedTotalUnderlying`; here, the user's per-line `DiffSelection` bitset) is combined with a freshly recomputed value (there, `balanceProtocol`; here, a newly fetched `git diff`) without re-validating that the two still describe the same underlying state. When they've drifted apart, the invariant "the patch reflects what the user visually selected" breaks silently instead of failing loudly.

### Finding Description
`applyPatchToIndex` in [1](#0-0)  re-fetches the working-directory diff from disk immediately before building the patch:

```
const diff = await getWorkingDirectoryDiff(repository, file)
...
const patch = await formatPatch(file, diff)
```

`formatPatch` decides which lines to include purely by absolute index into the **freshly fetched** hunks, checked against the file's `selection` object: [2](#0-1) . That `selection` (a `DiffSelection` bit-set) was populated earlier, against whatever diff/hunk layout was loaded when the user reviewed and checked lines in the Changes list, and is carried forward unmodified through the repository state cache: [3](#0-2) .

The code that *does* reconcile the selection against a new diff, `updateChangesWorkingDirectoryDiff`, explicitly acknowledges the diff can shift and only trims out-of-range indices — it does not attempt to guarantee that surviving indices still refer to the same logical content: [4](#0-3) . That reconciliation only runs when Desktop happens to reload the diff for the selected file; it is not re-run immediately before `stageFiles`/`applyPatchToIndex` executes during `_commitIncludedChanges`: [5](#0-4) , [6](#0-5) .

If the working-tree file's contents change between the moment the user made a partial selection (based on one diff snapshot) and the moment `git apply --cached` runs (based on a second, freshly fetched diff), `absoluteIndex` values in the new hunks no longer correspond to the lines the user actually reviewed and approved. `formatPatch` will happily build a patch using stale bit positions against new hunk content, and `git apply --cached -` will accept whatever hunk/line-count arithmetic is produced — there is no cross-check that the selected content matches what was shown to the user.

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes." The user could believe they are committing hunk A (reviewed on screen) while the actual staged patch, computed from a shifted/altered diff, includes different lines, additional lines, or omits lines they intended to include — with no error, warning, or diff mismatch shown before or after the commit completes.

### Likelihood Explanation
The window between "user reviews/selects lines in the Changes view" and "Desktop stages and commits" is attacker-influenceable via content that ships with a cloned/fetched repository: Git clean/smudge filters and merge drivers declared in a repository's own `.gitattributes` (referencing a filter name) can rewrite file content as part of routine plumbing commands (`git diff`, `git status`, `git add`/`update-index`) that Desktop already issues during its normal refresh cycle, without requiring any unusual user action beyond having the malicious repository open. Because `getWorkingDirectoryDiff` and `applyPatchToIndex` are two independent git invocations separated in time by UI interaction, any such filter-driven or otherwise externally triggered mutation of the file between the two calls reintroduces the drift described above. I was not able to fully verify, from static code alone, the exact minimum filter/driver configuration required to trigger content rewriting purely from repository-supplied `.gitattributes` without any local config being pre-set by the user, so the likelihood of a fully "zero local setup" trigger is uncertain and would need runtime verification.

### Recommendation
Before building the patch in `applyPatchToIndex`, verify that the diff used to construct the user's `selection` is still equivalent to the diff about to be patched (e.g., by comparing a content hash/blob id captured when the selection was made, not just hunk count/line count), and abort/re-prompt the user rather than silently applying a patch built from mismatched hunk indices. At minimum, re-diff and re-validate selectable lines immediately before staging, in `_commitIncludedChanges`, rather than relying on whatever reconciliation happened the last time the diff panel was rendered.

### Proof of Concept
Conceptual (not fully runtime-verified):
1. Open a cloned repository containing a `.gitattributes` entry that routes a tracked file through a filter/driver capable of rewriting its content on `git diff`/`git status` invocations.
2. In the Changes view, select a subset of lines from the file's diff (e.g., lines 10–15 of hunk 1).
3. Before clicking "Commit", let Desktop's periodic refresh (`_refreshRepository` → `_loadStatus`) run again, during which the filter driver alters the file's on-disk diff shape (shifts line offsets) without the UI re-displaying an updated selection to the user.
4. Click "Commit". `_commitIncludedChanges` stages the file using the stale `selection` object: `stageFiles` → `applyPatchToIndex` fetches the new diff and calls `formatPatch(file, diff)` using the old bit-set against new hunk offsets, producing a patch whose selected lines no longer match what the user saw/approved.
5. Inspect the resulting commit: it contains different content than what was displayed and selected in the UI, with no error surfaced to the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
