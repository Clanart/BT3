### Title
Incomplete dangerous-extension validation in `isSafeFileExtension` allows execution of attacker-committed files via "Open with Default Program" - ([File: app/src/ui/lib/context-menu.ts])

### Summary
The reported BLS bug is a classic "incomplete validation" flaw: the check verifies one necessary property (group membership) but omits another required property (rejecting the identity/infinity element), so a malicious key that should be rejected is accepted. The Desktop analog is `isSafeFileExtension()`, which is supposed to gate whether a file changed/committed in a repository can be launched via the OS's default handler from the Changes list, History view, and Pull Request file-diff context menus. It checks membership against a tiny hardcoded blocklist and — critically — is a complete no-op on macOS and Linux, and an incomplete blocklist on Windows. A file whose name/extension is entirely attacker-controlled (it comes from a cloned/fetched/PR-diff repository) is treated as "safe" whenever it isn't literally `.cmd`, `.exe`, `.bat`, or `.sh`.

### Finding Description
`isSafeFileExtension` is defined as: [1](#0-0) 

```
const RestrictedFileExtensions = ['.cmd', '.exe', '.bat', '.sh']
...
export function isSafeFileExtension(extension: string): boolean {
  if (__WIN32__) {
    return RestrictedFileExtensions.indexOf(extension.toLowerCase()) === -1
  }
  return true
}
```

This function is used as the sole gate for enabling "Open with Default Program" on files whose paths originate from the working directory diff, commit history, and pull-request diff views — all of which can contain attacker-controlled file names/extensions from a cloned or fetched repository, or from a viewed PR diff: [2](#0-1) [3](#0-2) [4](#0-3) 

The broken invariant: the guard is supposed to reject any extension that the OS's default handler would treat as an executable/script and instead only rejects four specific Windows extensions, returning `true` unconditionally on macOS/Linux and for every other extension on Windows. This mirrors the BLS bug pattern exactly — a narrow check (`RestrictedFileExtensions.indexOf(...) === -1`) that is treated as proof of "safe" when it only proves "not one of these four specific known-bad strings."

Existing guards elsewhere in the app (file existence check via `pathExists`, `Path.join(repository.path, file.path)`) only confirm the file exists on disk — they do nothing to constrain what type of file it is, so they do not stop this path.

### Impact Explanation
On Windows, attacker-controlled repository content named `payload.ps1`, `payload.vbs`, `payload.js`, `payload.hta`, `payload.msi`, `payload.scr`, `payload.jar`, `payload.lnk`, `payload.wsf`, or any other Windows-launchable/script extension outside the 4-item blocklist is marked "safe," enabling the "Open with Default Program" menu item.

On macOS and Linux, the function returns `true` for every extension with no filtering at all — an attacker-committed `.command` file (macOS, runs as a shell script when opened) or a `.desktop` file (Linux, can specify an arbitrary `Exec=` command) will always be reported "safe."

If the user right-clicks such a file in Changes/History/PR-diff and selects "Open with Default Program," the OS invokes its default handler for that extension, which for these extensions typically means script/command execution rather than passive viewing — resulting in arbitrary code execution driven entirely by a value from a cloned/fetched repository or a viewed PR diff (attacker-controlled input per the report's valid-impact criteria).

### Likelihood Explanation
The trigger requires the user to right-click a suspicious file and explicitly choose "Open with Default Program," which is a real, expected menu action always present for any file with a "safe" extension — no unusual steps beyond normal repository/PR review are required. An attacker only needs to add a file with a crafted name/extension to a public repository, fork, or PR branch that the victim later clones/fetches/reviews in Desktop. The bug is 100% reachable through this single code path with no additional privilege.

### Recommendation
Replace the blocklist approach with an explicit allowlist of extensions known to be safe to open passively (e.g., common document/image/text types), or at minimum expand `RestrictedFileExtensions` to cover the full set of OS-launchable/script extensions on all three platforms (`.scr`, `.msi`, `.js`, `.vbs`, `.wsf`, `.hta`, `.jar`, `.lnk`, `.ps1` on Windows; `.command`, `.app`/executable bundles on macOS; `.desktop`, `.sh`, and files with the executable bit set on Linux), and stop returning an unconditional `true` for non-Windows platforms.

### Proof of Concept
1. Attacker pushes a file named `update.command` (macOS) or `update.desktop` (Linux) or `update.js` (Windows) to a public repository/fork/PR branch.
2. Victim clones/fetches the repository in GitHub Desktop, or opens the PR diff in the "Files changed" view.
3. Victim right-clicks the file in the Changes list, History view, or PR Files Changed view.
4. `isSafeFileExtension(extension)` returns `true` because the extension is not one of `.cmd/.exe/.bat/.sh` (Windows) or the platform is not Windows at all, so "Open with Default Program" is enabled: [5](#0-4) 
5. Victim clicks "Open with Default Program"; the OS launches its default handler for that extension, executing the attacker-supplied script/command.

Note: I was unable to inspect `app/src/ui/lib/open-file.ts` in full (index truncated) to confirm the exact native call used to launch the file; the underlying OS "open" behavior for these extension types (particularly `.command`/`.desktop` semantics) should be verified in a full checkout before treating this PoC as final.
