### Title
Unbounded `ThresholdKeys` deserialization enables repeated memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` trusts the serialized participant count `n` before validating the threshold parameters. If the interpolation byte selects `Interpolation::Constant`, it immediately executes `Vec::with_capacity(usize::from(n))` and then attempts to deserialize `n` field elements. An attacker can therefore make a very small malformed input allocate roughly `32 * 65,535` bytes for Secp256k1 before the reader reports EOF. With a complete serialized body, the same unchecked `n` also causes up to 65,535 field-element and group-element decodes, `HashMap` inserts, and threshold-key construction work before invalid parameters are rejected. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from attacker-controlled bytes, but does not call `ThresholdParams::new` until after all variable-sized fields have been consumed. For interpolation byte `0`, it preallocates a coefficient vector solely from the serialized `n`. For either interpolation mode, it then reads one secret share and `n` verification shares. Only after this work does it validate `(t, n, i)` and construct `ThresholdKeys`. [1](#0-0) 

This differs from a normal bounded decode because a malformed input need not contain the claimed number of elements. Merely declaring `n = u16::MAX` causes an allocation proportional to 65,535 before deserialization fails. An unprivileged party that can submit serialized `ThresholdKeys` bytes can repeat this operation to create sustained allocator pressure and CPU burn.

### Impact Explanation
The impact is availability loss in any process that exposes `ThresholdKeys::read` to untrusted serialized key material. A truncated Secp256k1 encoding can force approximately 2 MiB of coefficient-vector capacity from a header-sized request. Complete encodings can further force tens of thousands of scalar/point decoding operations and hash-table insertions before parameter validation rejects inconsistent values such as `t != n` for constant interpolation. Concurrent or repeated requests can exhaust memory or monopolize worker threads. [2](#0-1) 

### Likelihood Explanation
The vulnerable parser accepts a generic `Read`, so it does not require access to secrets, validator status, malformed curve implementations, or protocol misuse beyond providing attacker-controlled bytes. The bug is deterministic: the allocation and loop counts are controlled by the serialized `n`, and validation occurs only after the expensive deserialization phase. Exploitability depends on an integration exposing serialized `ThresholdKeys` input, but such deserialization is part of the public API surface. [3](#0-2) 

### Recommendation
Validate `ThresholdParams::new(t, n, i)` immediately after reading `t`, `n`, and `i`, before allocating vectors or parsing shares. Apply an explicit protocol-level maximum for `n` rather than accepting the full `u16` range. For constant interpolation, reject `t != n` before allocating the coefficient vector, and avoid preallocating purely from the declared length; read incrementally or reserve only after enforcing a bounded byte budget.

### Proof of Concept
```rust
use bitcoin_serai::bitcoin::secp256k1; // illustrative only if Secp256k1 is re-exported
use frost::{curve::Secp256k1, ThresholdKeys};
use ciphersuite::Ciphersuite;

fn malicious_threshold_keys() -> Vec<u8> {
    let mut bytes = Vec::new();
    bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
    bytes.extend(Secp256k1::ID);

    bytes.extend(1u16.to_le_bytes());        // t
    bytes.extend(u16::MAX.to_le_bytes());    // n = 65,535
    bytes.extend(1u16.to_le_bytes());        // i
    bytes.push(0);                           // Interpolation::Constant

    // No coefficients follow. ThresholdKeys::read still allocates
    // Vec::with_capacity(65_535) before discovering EOF.
    bytes
}

let mut bytes = malicious_threshold_keys().as_slice();
let result = ThresholdKeys::<Secp256k1>::read(&mut bytes);
assert!(result.is_err());
```

A complete-body variant appends 65,535 scalar encodings and 65,535 point encodings. The parser consumes and stores all of them before `ThresholdParams::new` and `ThresholdKeys::new` reject an inconsistent constant-interpolation parameter set. [4](#0-3)

    {

      let mut id_len = [0; 4];

      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;

      secret_share,
      verification_shares,
