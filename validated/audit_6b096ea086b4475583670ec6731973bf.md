## Finding confirmed: `onAccept` binds only chain identity, not module identity [1](#0-0) 

### Title
Missing `request.from` binding to `PALLET_BANDWIDTH_MODULE_ID` in `BandwidthManager.onAccept` — inbound governance messages are only chain-authenticated, not module-authenticated - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` addresses its outbound dispatch to `PALLET_BANDWIDTH_MODULE_ID` via the `to` field [2](#0-1) , but `onAccept` never checks the corresponding inbound identity: it only verifies `request.source.equals(IDispatcher(_host).hyperbridge())` (the source *chain*), and never compares `request.from` (or any other request field) against `PALLET_BANDWIDTH_MODULE_ID` [3](#0-2) .

### Finding Description
The natspec explicitly states "tier prices and treasury withdrawals are governed exclusively by the pallet via `onAccept`" [4](#0-3) , and the contract even documents that `PALLET_BANDWIDTH_MODULE_ID` "Must equal `pallet-bandwidth`'s `PalletId`. The pallet enforces this on inbound messages, so changing it on either side breaks the round-trip" [5](#0-4) . However, the actual `onAccept` implementation performs only a chain-level check (`request.source == hyperbridge`) before dispatching into `SetTiers` (governance price update) or `Withdraw` (arbitrary token/native transfer to `w.beneficiary`) [6](#0-5) .

This is a real gap relative to the pattern used by sibling apps in the same codebase, which consistently bind both source chain *and* source module identity:
- `HyperFungibleToken.onAccept` checks `expectedSource` against `request.from` in addition to the chain lookup [7](#0-6) .
- `HyperbridgeLzEndpoint.onAccept` checks `keccak256(request.from) == keccak256(abi.encodePacked(address(this)))` [8](#0-7) .
- `ExtrinsicIntents.onAccept` authenticates privileged actions against `incoming.request.source` as well as a per-action `_authenticate` call [9](#0-8) .

`BandwidthManager` is the outlier: it omits the module-identity (`from`) check entirely for both of its privileged actions (`SetTiers`, `Withdraw`).

On the EVM host side, routing of an inbound POST request to a destination contract's `onAccept` is keyed solely off `request.to` resolving to the contract's own address, not off `request.from` [10](#0-9) . This means the EVM host layer provides no guarantee that the sender's module id equals `pallet-bandwidth`'s id — that check is expected to be performed by the destination app itself, exactly as `HyperFungibleToken` and `HyperbridgeLzEndpoint` do, and exactly as `BandwidthManager`'s own comments claim it does but the code does not.

### Impact Explanation
If any entity other than `pallet-bandwidth` on the hyperbridge coprocessor chain can cause a POST request to be dispatched with `to = address(BandwidthManager)`, `onAccept` will process it as legitimate governance:
- A forged `SetTiers` payload can rewrite `tierPrice` mappings, letting purchasers pay attacker-chosen (e.g., near-zero) prices for bandwidth tiers.
- A forged `Withdraw` payload can drain the entire ERC20 fee-token balance or native ETH balance held by `BandwidthManager` to an attacker-chosen `beneficiary` [11](#0-10) .

This directly matches the Hyperbridge pivot requirement that "request... paths must bind chain id, module/app identity... on both Substrate and EVM" and the "stealing or loss of funds... unauthorized transaction" impact gate.

### Likelihood Explanation
I was unable to fully confirm, within the scope of this review, whether an *unprivileged* end user can cause the hyperbridge coprocessor chain to dispatch an arbitrary-`from` POST request addressed to `address(BandwidthManager)` — this depends on whether pallet-ismp's dispatch API lets any calling pallet set `from` to a value it does not truly own, or whether some other governance-tier but non-`pallet-bandwidth` pallet on the coprocessor chain could be tricked/reused to hit this `to` address. What is confirmed and code-verifiable is that the destination-side identity check that `BandwidthManager`'s own documentation and sibling contracts rely on is simply missing, so the security of `SetTiers`/`Withdraw` currently rests entirely on (a) the source-chain check and (b) trust in whatever dispatches messages `to` this contract on the coprocessor side — an invariant the code does not itself enforce, contrary to its documented design intent.

### Recommendation
In `onAccept`, add an explicit binding of `request.from` to `PALLET_BANDWIDTH_MODULE_ID` (mirroring the `expectedSource`/`request.from` check pattern used in `HyperFungibleToken.onAccept` and `HyperbridgeLzEndpoint.onAccept`), e.g.:
```solidity
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
placed alongside the existing `request.source` check at [12](#0-11) .

### Proof of Concept
A unit test can demonstrate the gap structurally:
1. Assert `PALLET_BANDWIDTH_MODULE_ID` is referenced as the `to` field in `purchase()`'s `DispatchPost` [2](#0-1) .
2. Grep `onAccept`'s body and show no reference to `PALLET_BANDWIDTH_MODULE_ID` or `request.from` anywhere in the function [13](#0-12) .
3. Construct an `IncomingPostRequest` with `request.source = hyperbridge`, `request.to = address(bandwidthManager)`, and `request.from = <anything other than "BWMARKET">`, body = `abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(Withdrawal({token: address(0), beneficiary: attacker, amount: address(bandwidthManager).balance})))`; call it via `vm.prank(host)` and `bandwidthManager.onAccept(incoming)` — it succeeds and drains funds, since no check rejects the mismatched `from`.

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
