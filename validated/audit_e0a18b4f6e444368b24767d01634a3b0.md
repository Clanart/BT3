## Analysis

The WatchPug bug's core invariant: an aggregate accounting value (`ibRatio`, paired with `totalSupply`) was not updated proportionally when a partial "burn" happened, so the aggregate bucket got fully swept by one action while other legitimate shares became unreachable/lost.

I found a direct structural analog in `IntrinsicIntents._fillSameChain()`, which manages the aggregate `_orders[commitment][token]` escrow bucket during same-chain partial/multi-output intent fills.

### Title
Same-chain partial fill drains the entire shared escrow bucket when two order inputs reuse the same token address, letting the first filler take escrow owed to a later, unfilled output - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` releases input escrow per output index by reading `_orders[commitment][token]` — a bucket keyed **only by token address**, aggregated across every `order.inputs[i]` entry that shares that token — not per output index. When an output finishes (`amountFilled == totalRequired`), the code assigns the **entire remaining balance** of that token's bucket to the current output's `escrowedInputs[i]`: [1](#0-0) 

If `order.inputs` contains two (or more) entries with the same token address — nothing in the reviewed placement/fill path enforces uniqueness of input tokens — the filler who completes *any one* of the outputs mapped to that shared token drains the combined bucket, including the portion that was meant to back a different, still-unfilled output.

### Finding Description
`_orders[commitment][token]` is a single running total per `(commitment, token)` pair: [2](#0-1) 

During a fill, the escrow amount handed to a filler for output `i` is computed two different ways depending on whether that output just became fully satisfied: [3](#0-2) 

- Non-final partial progress: `escrowedAmount = order.inputs[i].amount * fillAmount / totalRequired` (a proportional share of that specific index's original allocation).
- Final completion of output `i`: `escrowedAmount = _orders[commitment][token]` — i.e. **whatever is currently left in the whole token bucket**, not `order.inputs[i]`'s own allocation.

This is only safe if each token address appears in `order.inputs` at most once. If a user places an order whose `inputs` array has two entries with the same token backing two different `output` legs, then:

1. Filler A fully satisfies output leg 0 (whose input token is `X`) in one transaction. `escrowedAmount` for that leg becomes the *entire* `_orders[commitment][X]` balance — which secretly also contains the escrow meant to back output leg 1 (also token `X`, not yet filled). `_withdraw` transfers that whole amount to filler A and decrements `_orders[commitment][X]` to zero.
2. Output leg 1 is left open (`isFullyFilled = false`, so `_filled[commitment]` is deleted, order stays fillable).
3. Filler B later fully fills output leg 1, delivering real output tokens to the beneficiary. Its computed `escrowedAmount` reads `_orders[commitment][X]`, which is now `0`. In `_withdraw`, a zero amount is silently skipped rather than reverting: [4](#0-3) 

So filler B receives no input-token compensation for a legitimate fill, while filler A walked away with escrow that covered two output legs while only delivering one.

Existing guards do not stop this: `fillOrder`/`cancelOrder` only check `_filled[commitment] == address(0)`, array-length equality between `order.inputs` and `order.output.assets`, and per-output-token remaining balances (`_partialFills`) — none of these check for duplicate token addresses across `order.inputs`, and `_orders` is aggregated purely by token address with no per-index sub-accounting (the missing "ibRatio" analog).

### Impact Explanation
This directly matches the required impact set: an unprivileged filler (no relayer/prover/admin/governance role needed) can receive **more escrowed value than entitled** for the work performed, while another party (a later, honest filler, or the user via cancellation) receives less than owed or nothing — funds are misdirected/lost rather than paid to the rightful beneficiary in the correct amount. No malicious peer, prover, or front-running condition is required; the only precondition is an order whose `inputs` array repeats a token address across legs, which the protocol does not forbid anywhere in the paths reviewed (`IntentGatewayV2.sol`, `IntentsBase.sol`, `IntrinsicIntents.sol`).

### Likelihood Explanation
Likelihood depends on whether `placeOrder` (not fully reviewed in this session) enforces input-token uniqueness; no such check was found in any of the fill/cancel/base logic examined. Multi-leg same-chain orders with overlapping input tokens are a plausible, unremarkable user pattern (e.g., paying for two different output assets partly from the same input token), making this reachable without any adversarial setup beyond crafting the order itself.

### Recommendation
Track escrow per `(commitment, outputIndex)` — or at minimum per `(commitment, inputIndex)` — instead of aggregating purely by token address, so that completing one output leg can never consume escrow reserved for another leg. Alternatively, enforce a uniqueness check on `order.inputs[].token` at `placeOrder` time, or change the "final release" branch to always compute the proportional/exact share for that specific index (mirroring the non-final branch) rather than sweeping the whole remaining token-keyed bucket.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [ {token: X, amount: 100}, {token: X, amount: 50} ]` and two output legs `output.assets = [ {token: A, amount: 100}, {token: B, amount: 50} ]`. `_orders[commitment][X] = 150` after escrow.
2. Filler A calls `fillOrder` supplying only output leg 0's full amount (`A: 100`, `B: 0`). In `_fillSameChain`, leg 0 hits `amountFilled == totalRequired`, so `escrowedAmount = _orders[commitment][X] = 150` is released entirely to Filler A via `_withdraw`; `_orders[commitment][X]` becomes `0`. `isFullyFilled = false` (leg 1 untouched), order stays open.
3. Filler B calls `fillOrder` later, supplying leg 1's full amount (`B: 50`). Leg 1's `escrowedAmount = _orders[commitment][X] = 0`; `_withdraw` skips the zero-amount transfer. Filler B delivered `50` of token `B` to the beneficiary but received `0` input compensation, while Filler A received `150` of token `X` for delivering only `100` of token `A`. [5](#0-4) [6](#0-5)

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        // Orders carrying output calldata must be filled completely in a single fill.
        // The attached call is only executed on a full fill, so a partial fill would
        // leave the intended side effect unexecuted while releasing proportional escrow.
        if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();

        WithdrawalRequest memory body = WithdrawalRequest({
            commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        });
        _withdraw(body, false, isFullyFilled);

        if (isFullyFilled) {
            _execute(order, outputsLen);
            emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        } else {
            delete _filled[commitment];
            emit PartialFill({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;
