### Title
Unbounded Unicode NFKD Normalization in `mnemonic_to_seed` Enables CPU Denial-of-Service via `add_key` RPC/Keychain Calls - (File: `chia/util/keychain.py`)

### Summary
`chia/util/keychain.py`'s `mnemonic_to_seed()` calls `unicodedata.normalize("NFKD", mnemonic)` on an attacker/caller-supplied string with no prior length or character-set validation whenever the string contains any non-ASCII character. This mirrors the CWE-770 bug class in the reported Django advisory (slow Unicode NFKC normalization on unbounded user input causing DoS), except here the vulnerable normalization is NFKD and is reachable through the Keychain `add_key` path used by the daemon keychain RPC and wallet key-import flows.

### Finding Description
`mnemonic_to_seed()` is defined as: [1](#0-0) 

The function only takes the "shortened 4-letter word" / length-validated path (`mnemonic_from_short_words`, which enforces mnemonic length ∈ {12,15,18,21,24}) when **every** character is ASCII: [2](#0-1) 

If the input string contains even a single non-ASCII character (`ord(c) >= 128`), that length-bounding branch is skipped entirely, and `unicodedata.normalize("NFKD", mnemonic)` is invoked directly on the raw, attacker-controlled string of arbitrary length. Unlike `bytes_from_mnemonic()` (used for entropy derivation and separately validated), `mnemonic_to_seed()` performs no length check before normalization in this non-ASCII branch.

This function is exercised by `Keychain.add_key()`: [3](#0-2) 

`add_key()` is reachable from the daemon keychain RPC server (`chia/daemon/keychain_server.py`) and the keychain proxy (`chia/daemon/keychain_proxy.py`), which are the local-RPC-caller surfaces explicitly in scope for this class of bug (daemon/keychain/RPC authorization). A caller supplying a very large string containing Unicode combining/decomposable characters (e.g., long sequences of Hangul, decomposable CJK compatibility characters, or repeated combining diacritics) as the "mnemonic" parameter forces the process to perform NFKD normalization over an unbounded-length string, which is CPU/time expensive, especially for pathological decomposition sequences.

### Impact Explanation
A local/authorized RPC caller (or any component that forwards untrusted key-import input, e.g., a GUI/CLI wrapper) can pass an arbitrarily long, decomposition-heavy Unicode string as a "mnemonic" to `add_key`. Because no length bound is applied before `unicodedata.normalize("NFKD", ...)` runs, this can consume significant CPU time in the process handling the keychain/daemon RPC, degrading or blocking that daemon's responsiveness (a resource-exhaustion / availability impact), consistent with CWE-770 as in the reported analog.

### Likelihood Explanation
Exploitation requires access to the daemon keychain RPC or an equivalent add-key/import code path, so it is bounded to callers with keychain RPC access rather than a fully unauthenticated network attacker. Within that reachable actor set (local RPC caller category explicitly in scope), the trigger condition (a string containing at least one non-ASCII character) is trivial to satisfy, and no additional validation currently prevents an oversized input from reaching the normalization call.

### Recommendation
Add an explicit upper bound on mnemonic string length (and/or validate that it decomposes to one of the standard BIP-39 word counts) before calling `unicodedata.normalize` in `mnemonic_to_seed()`, regardless of whether the input is pure ASCII. Reject inputs exceeding a small sane bound (e.g., a few hundred characters) prior to normalization, mirroring the length checks already present in `mnemonic_from_short_words()` and `bytes_from_mnemonic()`.

### Proof of Concept
1. Start the daemon and connect via the keychain RPC (or use `Keychain().add_key(...)` directly, as exercised in `chia/_tests/core/util/test_keychain.py`).
2. Call `add_key` with a "mnemonic" string consisting of a very large number (e.g., hundreds of thousands) of Unicode characters that have long/pathological NFKD decompositions, with at least one non-ASCII character present so the ASCII short-word branch is bypassed:
   `mnemonic = "\u1100" * 500000  # or similar decomposable Hangul/compat characters`
3. Observe that `mnemonic_to_seed(mnemonic)` — invoked from `add_key` — spends disproportionate CPU/wall time in `unicodedata.normalize("NFKD", mnemonic)` relative to the trivial length check that a legitimate 12/24-word mnemonic would require, demonstrating the unbounded normalization cost. Legitimate mnemonic validation would be expected to reject this input before any normalization work is performed.

```python
def mnemonic_to_seed(mnemonic: str) -> bytes:
    """
    Uses BIP39 standard to derive a seed from entropy bytes.
    """
    # If there are only ASCII characters (as typically expected in a seed phrase), we can check if its just shortened
    # 4 letter versions of each word
    if not any(ord(c) >= 128 for c in mnemonic):
        mnemonic = mnemonic_from_short_words(mnemonic)
    salt_str: str = "mnemonic"
    salt = unicodedata.normalize("NFKD", salt_str).encode("utf-8")
    mnemonic_normalized = unicodedata.normalize("NFKD", mnemonic).encode("utf-8")
    seed = pbkdf2_hmac("sha512", mnemonic_normalized, salt, 2048)

    assert len(seed) == 64
    return seed
```
