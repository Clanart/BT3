### Title
Checks-Effects-Interactions violation and missing reentrancy guard in the Tron `IntentGatewayV2.withdraw()` escrow-release path - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core broken invariant is: *internal accounting state (LP supply / reserves) is not kept atomically consistent with the value-moving operation, allowing a state mismatch that corrupts subsequent transactions.* The direct local analog in this repository is in the Tron deployment of `IntentGatewayV2`, where the escrow debit (`_orders[commitment][token] -= amount`) is performed **after** the external token transfer, and the contract carries **no reentrancy guard** at all — unlike the hardened, canonical EVM implementation which performs the debit before the transfer and wraps all mutating entrypoints in `nonReentrant`.

### Finding Description
In the canonical EVM implementation, `IntentsBase._withdraw` correctly follows checks-effects-interactions: the escrow mapping is decremented **before** any external call: [1](#0-0) 

The Tron variant of the same contract reverses this ordering — it performs the external `.call` to the (attacker-choosable) token contract **first**, and only decrements `_orders[body.commitment][token]` afterward: [2](#0-1) 

Additionally, unlike the main `IntentGatewayV2.sol`, which composes `ReentrancyGuardTransient` and marks `placeOrder`/`fillOrder`/`cancelOrder` as `nonReentrant`: [3](#0-2) [4](#0-3) 

the Tron `IntentGatewayV2` inherits no reentrancy protection whatsoever, and `cancelOrder`, which invokes `withdraw()` directly for same-chain orders, is a plain `public payable` function: [5](#0-4) 

The `withdraw()` function also uses raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` instead of `SafeERC20.safeTransfer`, meaning execution of arbitrary code inside the token being withdrawn is guaranteed to run synchronously, in the middle of the escrow-release loop, while `_orders[commitment][token]` for that very token — and for any co-escrowed token not yet reached in the loop — is still at its pre-transfer (undebited) value: [6](#0-5) 

The only guard against re-entering the same commitment is `_filled[body.commitment] = beneficiary;`, set once at the very top of `withdraw()`: [7](#0-6) 

This blocks the most direct reentry vector (calling `cancelOrder` again on the same commitment), but it does **not** compensate for the underlying design defect: fund custody logic that performs value transfer before committing the corresponding accounting change, combined with a total absence of `nonReentrant` protection anywhere in the contract. Any future code path added to this file (or any inherited/overridden function reachable during the token callback window, e.g. `placeOrder`, `onAccept`'s `SweepDust`/`NewDeployment` handling, or subsequent refactors that add partial-fill support mirroring the same-chain `IntrinsicIntents` logic) can be entered while `_orders[commitment][token]` is stale, which is precisely the class of accounting/invariant break described in the source report ("mathematical discrepancies… allow unfavorable transactions" / "invariant not guaranteed… leading to insolvency").

### Impact Explanation
If the raw `.call` to an attacker-supplied token address is ever combined with any state read of `_orders[commitment][token]` elsewhere in the withdrawal/settlement flow (a routine occurrence given the many `onAccept` request kinds multiplexed through this same contract — `RedeemEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, `RefundEscrow`), a malicious or fee-on-transfer/rebasing token used as an order input can execute arbitrary code mid-withdrawal while escrow bookkeeping has not yet been committed. This is exactly the invariant-break class flagged in the report ("insolvency… valid liquidity removal might revert" / mismatched internal vs. actual state), and here it manifests as escrowed user/protocol funds being moved through a transfer call that has not yet been reflected in `_orders`, with zero reentrancy protection anywhere in the contract to bound the blast radius of that code execution.

### Likelihood Explanation
The attacker primitive is fully unprivileged: any user can `placeOrder` with a self-deployed ERC-20/TRC-20 contract as one of the order's escrowed input tokens (a standard, permitted operation — no allow-list on token addresses is enforced), then trigger `cancelOrder` themselves. The vulnerable code path (`withdraw()`) is reached on every same-chain cancellation and on every cross-chain `RedeemEscrow`/`RefundEscrow` settlement, since it is the sole escrow-release function in this file. No relayer, prover, or admin cooperation is required to reach the vulnerable code region — only the presence of a malicious token contract, which is fully attacker-supplied.

### Recommendation
1. In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, decrement `_orders[body.commitment][token]` **before** performing the external transfer, mirroring `IntentsBase._withdraw` in the main EVM implementation.
2. Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with OpenZeppelin's `SafeERC20.safeTransfer`, which both reverts on failure and avoids ambiguity around unchecked return values.
3. Add a reentrancy guard (e.g. `ReentrancyGuardTransient`, consistent with the main `IntentGatewayV2.sol`) to `placeOrder`, `cancelOrder`, `onAccept`, and `onGetResponse` in the Tron contract.
4. Audit the Tron contract for any other divergences from the canonical `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` implementation, since it appears to be an independently maintained fork that has drifted from the hardened logic (e.g., it also lacks the duplicate-input-token rejection present in the main `placeOrder`).

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20/TRC-20 whose `transfer(to, amount)` function, on the first invocation, calls back into `IntentGatewayV2` (e.g., attempts a fresh `placeOrder` or any other unguarded state-mutating function) before returning `true`.
2. Attacker calls `placeOrder` with `order.inputs = [EvilToken: X, USDC: Y]`, escrowing both tokens under one `commitment`.
3. Attacker calls `cancelOrder` for this same-chain order. Execution enters `withdraw()`:
   - `_filled[commitment] = attacker` is set.
   - Loop reaches `EvilToken` first: `_orders[commitment][EvilToken]` is still `X` (undebited) and `_orders[commitment][USDC]` is still `Y` (untouched) at the moment `EvilToken.transfer()` executes attacker code.
   - Because there is no `nonReentrant` guard anywhere in the contract, the attacker's callback can invoke any other unguarded function of `IntentGatewayV2` while both escrow slots are stale, demonstrating that the fund-custody function does not enforce atomicity between transfer and accounting update.
4. This is directly verifiable by diffing the transfer/decrement ordering and guard modifiers between `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` (lines 682-705, no guard, transfer-then-decrement) and `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` (lines 390-425, decrement-then-transfer, called only from `nonReentrant`-guarded entrypoints).
