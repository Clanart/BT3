### Title
VerifyBlame passes accuser/accused in swapped order to `BlameMachine::blame`, causing the honest accuser to always be blamed and fatally slashed instead of the faulty sender - (File: processor/src/key_gen.rs)

### Summary
The PedPoP blame API `BlameMachine::blame(sender, recipient, msg, proof)` / `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` expects the *sender* of the disputed encrypted share (the accused party) as the first argument and the *recipient* (the accuser who revealed the ECDH key proof) as the second. The `CoordinatorMessage::VerifyBlame` handler calls `.blame(accuser, accused, ...)` — the arguments are transposed. This is the exact analog of the reported bug class: a check applied to the wrong party (there, `validateOwner` applied to the pending owner instead of the current owner), causing the protocol to penalize the honest actor and let the faulty actor escape.

### Finding Description
`blame_internal` in `crypto/dkg/pedpop/src/lib.rs` is documented and implemented as `blame(sender, recipient, msg, proof)`, where `msg` is "the encrypted secret share from the accused sender to the accusing recipient":

```rust
// crypto/dkg/pedpop/src/lib.rs
fn blame_internal(&self, sender: Participant, recipient: Participant, ...)
  -> Participant {
  let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
    Err(DecryptionError::InvalidSignature) => return sender,   // sender signed a bad msg
    Err(DecryptionError::InvalidProof)    => return recipient, // accuser's key proof bad
  };
  ...
}
```

Inside `decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs`), the per-message proof-of-possession is verified with `pop_challenge(context, R, key, from, msg)` where `from` must be the *actual sender's* `Participant` index — the PoP transcript binds `sender.to_bytes()`. The DLEq proof is checked against `self.enc_keys[&decryptor]` — the *recipient's* registered encryption key, which is what the accuser legitimately reveals.

In `processor/src/key_gen.rs` the handler does:

```rust
.blame(accuser, accused, substrate_share, substrate_blame);   // line ~549
.blame(accuser, accused, network_share, network_blame);       // line ~556
```

So `sender = accuser` and `recipient = accused`. Two consequences:

1. `decrypt_with_proof` computes `pop_challenge(..., from = accuser, ...)`, but the share message's PoP was signed by the accused sender binding `sender = accused`. The PoP verification therefore fails → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender`, i.e. the **accuser**.
2. Even if the PoP check were bypassed, the DLEq would be verified against `enc_keys[&accused]` as "decryptor" — again wrong roles.

Every `VerifyBlame` resolution therefore returns `accuser`, and the handler emits `ProcessorMessage::Blame { participant: accuser }`, which the tributary (`coordinator/src/tributary/handle.rs`, `Transaction::InvalidDkgShare`) treats as grounds to **fatally slash the accuser**. A validator that honestly reports `InvalidDkgShare` for a genuinely faulty peer is slashed; the faulty participant is never identified.

### Impact Explanation
An attacker participant can send invalid/undecryptable DKG shares and be guaranteed that any honest participant who files an `InvalidDkgShare` blame transaction is themselves fatally slashed. This inverts the accountability mechanism: malicious DKG participants are unpunishable, and honest reporters lose their stake/key material — a direct theft of bonded funds and a deterrent that prevents the key-generation accountability path from functioning at all.

### Likelihood Explanation
Deterministic: the argument order is wrong unconditionally, so *every* blame verification misattributes fault. The only mitigating factor is that most `blame_internal` paths short-circuit at the PoP check (`InvalidSignature` → returns the swapped `sender` = accuser), so the misblame occurs on the very first check.

### Recommendation
Swap the arguments at both call sites in `processor/src/key_gen.rs`:

```rust
.blame(accused, accuser, substrate_share, substrate_blame);
.blame(accused, accuser, network_share, network_blame);
```

and rename `blame_internal`'s parameters / add a type-level distinction (e.g., newtype wrappers for `Sender`/`Recipient`) to prevent transposition.

### Proof of Concept
1. Run a DKG via PedPoP where participant `A` (accused) sends participant `B` (accuser) a share with an invalid PoP, invalid share value, or wrong encryption.
2. `B` errors with `PedPoPError::InvalidShare { participant: A, blame }` and the processor emits `ProcessorMessage::InvalidShare { faulty: A, blame }`, which the coordinator turns into `Transaction::InvalidDkgShare { accuser: B, faulty: A, share, blame }`.
3. Each validator executes the `VerifyBlame` handler: `AdditionalBlameMachine::new(...).blame(accuser = B, accused = A, share, blame)`.
4. `decrypt_with_proof(from = B, decryptor = A, msg, proof)` computes `pop_challenge` with `sender = B`, which does not match the signature `A` produced → `Err(InvalidSignature)` → returns `B`.
5. Handler emits `Blame { participant: B }`; `B` (the honest accuser) is fatally slashed, `A` (the faulty sender) escapes.

This mirrors the reference bug exactly: the validation (`pop_challenge` sender binding / `enc_keys[decryptor]` lookup, analogous to `validateOwner`'s `msg.sender` check) is applied against the wrong party because the roles were transposed at the call site.
