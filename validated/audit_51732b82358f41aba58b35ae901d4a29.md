### Title
DID recovery list allows a former owner to reclaim singleton control after "selling" the DID - (File: `chia/wallet/did_wallet/did_wallet.py`)

### Summary
The reported NounsBuilder bug is a class of "founder pre-configures a persistent privileged backdoor before transferring ownership, and can exploit it after control has ostensibly moved to a new party." The closest reachable analog in this chia-blockchain codebase is the DID (Decentralized Identifier) singleton's recovery-list mechanism: a DID owner can leave (or intentionally set) `backup_ids` / `num_of_backup_ids_needed` on the DID's inner puzzle, transfer the DID to a buyer via `transfer_did`/`did_transfer_did`, and — because the transfer path does not force-clear the recovery list — a party listed in that recovery list can still exercise recovery authority over the DID coin after the "ownership transfer," independent of the new owner's key.

### Finding Description
`DIDWallet.transfer_did` (chia/wallet/did_wallet/did_wallet.py:805-837) builds the new DID inner puzzle from `self.did_info.backup_ids` and `self.did_info.num_of_backup_ids_needed` unless `reset_recovery_list()` clears them, and `reset_recovery_list()` (did_wallet.py:1017-1032) only returns a cleared hash under narrow preconditions (`num_of_backup_ids_needed == 0` and empty `backup_ids`), otherwise it preserves the pre-existing recovery-list hash into the newly transferred puzzle: [1](#0-0) 

`get_innerpuz_for_new_innerhash`, used when constructing the inner puzzle for a new owner, explicitly documents that the recovery list is *kept* across a transfer, and that clearing it is a manual step the seller must remember to take: "Note: the recovery list will be kept. In a selling case, the seller should clean the recovery list then transfer to the new owner." [2](#0-1) 

Because the recovery-list hash (and thus the set of "recovery DIDs"/attestors who can authorize a recovery spend on the DID singleton) is curried into the DID inner puzzle itself, whoever is on that list retains cryptographic recovery authority over the identity coin regardless of who now holds the p2 (spend) key of the DID. This is the same structural flaw as the Manager/Token `minter` role: a privilege is granted by the pre-transfer owner and is not automatically revoked when nominal ownership/control moves to a new party — the new owner has no way to know from possession of the coin alone whether a dormant recovery/minter-style privilege was left active by the previous controller.

Additionally, the CHANGELOG for this repo shows that the wallet-level RPC endpoints for driving a DID recovery spend (`did_update_recovery_ids`, `did_recovery_spend`, `did_get_recovery_list`, `did_create_attest`, `did_get_information_needed_for_recovery`) were removed from the wallet software: [3](#0-2) 

This removal only eliminates the *convenience RPCs* in this particular wallet client — it does not change the on-chain DID inner puzzle's consensus rules. A former owner (or anyone included in the pre-transfer recovery list) who still knows the curried recovery-list contents and signatures required can construct and submit a raw recovery spend bundle directly to the mempool/full node, bypassing the wallet entirely, exactly analogous to how the Nouns founder could call `updateMinters` and later exercise that role directly via a raw transaction regardless of what the DAO's front end exposes.

### Impact Explanation
If a buyer purchases/receives a DID (and any NFTs whose ownership/DID-based permissions key off that DID) without independently verifying that the DID's recovery list was reset to empty at transfer time, the seller (or any address placed on the recovery list) can later submit an unauthorized recovery spend that reassigns the DID singleton's p2 puzzle to an address the seller controls — effectively reclaiming the identity/coin-set control without any cooperation or signature from the current legitimate owner. This is a concrete unauthorized-coin-movement / forged-identity scenario: control of the singleton (and by extension DID-gated NFTs, CR-CAT authorized-provider identity, or other DID-anchored permissions) can be wrested back by a party who is nominally no longer the owner.

### Likelihood Explanation
Likelihood depends on user/wallet behavior: exploitation requires that the recovery list was non-empty at the time of transfer and that the transferring party (buyer, marketplace, or wallet software) did not enforce/verify that `reset_recovery_list()` produced a cleared list before accepting the transfer as final. Since `transfer_did`'s default behavior preserves the recovery list unless explicit conditions are met, and the DID-transfer CLI/RPC flag `with_recovery_info`/`reset_recovery` exists specifically because this is not automatic, unaware or careless counterparties in a DID sale (offer, marketplace) are plausibly exposed. This is a real, previously-documented risk in the DID design (explicit code comment), not a hypothetical.

### Recommendation
- Make `transfer_did` (and the corresponding RPC/CLI path) clear the recovery list (`backup_ids = []`, `num_of_backup_ids_needed = 0`) by default on ownership transfer, requiring an explicit opt-in flag to preserve it, rather than requiring the seller to remember to reset it.
- Surface a clear warning/verification step in wallet RPC and CLI (`did_transfer_did`) and in any DID-offer flow so that a buyer can verify, before accepting a DID, that its recovery list hash matches the "no recovery" nil hash.
- Consider adding a wallet-side check on DID acquisition (via offer or transfer) that refuses to treat a DID coin as fully "owned" if a non-empty recovery list is still curried into it, unless the acquiring party explicitly acknowledges the residual recovery risk.

### Proof of Concept
1. Owner A creates a DID with `backup_ids = [X]`, `num_of_backup_ids_needed = 1`, where X is an address/DID A controls.
2. Owner A sells/transfers the DID to Owner B using `transfer_did` (chia/wallet/did_wallet/did_wallet.py:805) without resetting the recovery list (default behavior preserves `backup_ids`/`num_of_backup_ids_needed` per `reset_recovery_list()`, did_wallet.py:1017-1032).
3. Owner B now holds the DID coin and believes they have full control.
4. Owner A, still in possession of the recovery attestation key(s) corresponding to X, constructs a raw recovery-spend `CoinSpend`/`SpendBundle` against the DID singleton's current coin, satisfying the DID inner puzzle's recovery-mode conditions (attestation announcements + `AGG_SIG_UNSAFE` from the backup key, as built by `create_recovery_message_puzzle`, chia/wallet/did_wallet/did_wallet_puzzles.py:138-155) and submits it directly to a full node, bypassing any wallet-level RPC restriction.
5. If accepted, this recovery spend re-derives the DID's p2 puzzle hash to an address Owner A controls, reclaiming control of the identity coin without Owner B's cooperation or signature — even though Owner B was the current, expected owner.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
