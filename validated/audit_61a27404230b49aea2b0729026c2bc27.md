### Title
`BaseRewardPool.getReward` reverts entirely if a single reward token transfer fails, permanently freezing all other unclaimed rewards for a staker - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool.getReward` iterates over every reward token registered for a pool and performs a `safeTransfer` for each one in a single loop with no isolation between tokens. Because `getRewards` (the selective, per-token claim variant meant to work around exactly this situation) is an empty, unimplemented stub, an unprivileged staker has no way to skip a single problematic reward token when claiming. If any one reward token in the pool's `rewardTokens` array reverts on transfer to a given account, the staker permanently loses the ability to claim any of the other (otherwise healthy) reward tokens accrued in that same pool, mirroring the `RootManager.propagate` "one revert blocks everything" bug class.

### Finding Description
`getReward` loops through `rewardTokens` and calls `IERC20(rewardToken).safeTransfer(_receiver, reward)` for every token with a nonzero claimable balance, with no try/catch or per-token isolation: [1](#0-0) 

The only mechanism that could let a user bypass a single bad token — `getRewards(address, address, address[])`, which accepts a caller-selected subset of `_rewardTokens` — is defined but completely empty (no logic at all): [2](#0-1) 

`MasterMagpie._claimBaseRewarder`, which is invoked from every user-facing claim path (`multiclaim`, `multiclaimSpec`, `multiclaimFor`, `multiclaimOnBehalf`, and internally from `_multiClaim`), only calls the (no-op) `getRewards` when the caller supplies a non-empty `_rewardTokens` array, and otherwise falls back to `getReward`, which claims *all* registered tokens in one atomic loop: [3](#0-2) 

Reward tokens are appended to a pool's `rewardTokens` array dynamically through `queueNewRewards`, called by authorized managers such as `WombatStaking` when forwarding bribe rewards harvested from Wombat's voter/bribe contracts — meaning the token list for a pool is not static and can include arbitrary ERC20s that later become non-transferable to specific addresses (e.g., centralized stablecoins with blacklist functionality such as USDC/USDT, or tokens that later pause): [4](#0-3) 

If any single one of those tokens starts reverting `transfer`/`safeTransfer` calls to a particular account (e.g., that account gets blacklisted by the stablecoin issuer, or the token contract is paused), every future call to `getReward` for that account in that pool reverts at the point of iterating over that token — permanently blocking withdrawal of all other legitimate, already-accrued reward tokens in the same pool for that user, since there is no functioning fallback path to skip it.

### Impact Explanation
This results in permanent freezing of unclaimed yield for affected stakers: once one reward token in a pool becomes non-transferable to a user's receiver address, that user can never again claim any reward token from that pool via `multiclaim`/`multiclaimSpec`/`multiclaimFor` — the `getRewards` selective path that should allow skipping the bad token is a non-functional stub, so there is no on-chain workaround. This matches the accepted impact criterion of permanent freezing of unclaimed yield, and is reachable purely through normal, unprivileged multi-reward-token pool usage (bribe rewards routed through `WombatStaking.vote` → `BaseRewardPool.queueNewRewards`), not through any admin misbehavior.

### Likelihood Explanation
Likelihood is proportional to how many distinct reward tokens accumulate per pool over the pool's lifetime and how likely at least one becomes non-transferable to some user (blacklist-capable stablecoins are common bribe/incentive tokens in DeFi, and any address can be blacklisted or the token temporarily paused). As more bribe/reward tokens are added to a pool over time — exactly the "as more chains/tokens are added, the risk grows" dynamic called out in the analogous report — the probability that one problematic token blocks the rest increases.

### Recommendation
Make `BaseRewardPool.getReward` fail-safe per reward token, e.g., wrap each token's transfer in a try/catch (or use low-level `call` and check success) so a single failing token does not revert the whole loop, and/or implement `getRewards` properly so callers can reliably claim only the healthy subset of reward tokens, bypassing a known-bad token entirely.

### Proof of Concept
1. A pool's `BaseRewardPool` accumulates two reward tokens over time: `MGP`-adjacent token `A` (healthy) and stablecoin `B` with blacklist capability, added via `queueNewRewards` (e.g., forwarded bribe reward from `WombatStaking.vote`).
2. User `U` has claimable balances of both `A` and `B` in this pool (`userRewards[A][U] > 0`, `userRewards[B][U] > 0`).
3. Token `B`'s issuer blacklists `U` (or the pool's configured receiver) for reasons entirely outside Magpie's control.
4. `U` calls `MasterMagpie.multiclaim([stakingToken])` (or `multiclaimSpec`/`multiclaimFor`), which calls `_claimBaseRewarder` → `rewarder.getReward(U, receiver)`.
5. Inside `getReward`'s loop, the `safeTransfer` for token `B` reverts, causing the entire transaction — including the transfer of the otherwise-healthy token `A` — to revert.
6. `U` attempts to use the "selective" `multiclaimSpec` with only `A` specified, calling `_claimBaseRewarder` with a non-empty `_rewardTokens` array; this routes to `rewarder.getRewards(...)`, which is an empty function body and silently does nothing — `A` is never transferred.
7. `U` has no remaining code path to retrieve their accrued `A` rewards from this pool: their yield is permanently frozen.

            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
