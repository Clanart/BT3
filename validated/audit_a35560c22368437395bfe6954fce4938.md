### Title
Path-only (content-blind) file-change IDs let a repeatedly-modified working-tree entry keep a stale cached diff/selection across status refreshes - ([File: app/src/models/status.ts])

### Summary
`FileChange`/`WorkingDirectoryFileChange` identity is computed purely from `status.kind` and `path` (and `oldPath` for renames), never from the file's content (no hash, no timestamp, no OID). `updateChangedFiles` (the reconciliation function run every time Desktop refreshes `git status`) uses this content-blind `id` to decide whether a file in the new status result is "the same" file as one already selected, and if so, it **reuses the previously cached diff** for that id instead of re-fetching it. This mirrors the root cause of the Notional `GovernorAlpha` finding: an identifier that carries no information about the underlying object's actual content, combined with logic that treats "same ID" as "same intent/content", lets an attacker-controlled change to the underlying object (a proposal / here, working-tree file content) get silently associated with state (a vote / here, a diff review + inclusion selection) that was established for a *different* version of that object.

### Finding Description
`FileChange`'s id is built like this: [1](#0-0) 

Only `status.kind` (e.g. `Modified`, `New`, `Untracked`) and `path` feed into `id` - the actual blob content/OID is never part of the identifier.

This id is then treated as a stable "same file" key across successive `git status` polls in `updateChangedFiles`: [2](#0-1) 

Critically, the previously rendered/cached diff is reused whenever the selected file id is unchanged between the old and new state: [3](#0-2) 

Because the id does not encode content, this "same id → keep old diff/selection" logic cannot distinguish between:
- the same file being polled twice with no real change, and
- the same path/status-kind file whose on-disk content changed between two polls (e.g., an untracked/modified file that is rewritten by a build step, a git hook, a symlinked file, or any process that touches the working tree while Desktop is running).

`WorkingDirectoryFileChange` selection (the "include in commit" checkbox state, including partial line selections) is likewise keyed and carried forward by this same `id`: [4](#0-3) 

The attacker primitive that fits the bug class described in the report (an ID that doesn't bind to the object it names, combined with a race between "create/modify" and "read/act") is a repository whose content is not static during the interval between two Desktop status refreshes - for example a cloned/fetched repo containing a Git hook (`post-checkout`, `post-merge`, `post-commit`) or a build/test script that Desktop or an IDE invokes, which rewrites a working-tree file's contents in place without changing its path or its high-level status kind (still `Modified`/`New`/`Untracked`). Desktop's periodic/backgrounded status refresh (`updateChangedFiles`) will compute the same `id` for the before- and after-content versions of that file, and if the file was already selected/reviewed, Desktop keeps showing the old cached diff (`state.selection.diff`) rather than fetching a fresh one, while the "include in commit" checkbox state (`selection`) is also carried over unchanged.

Existing guards do not stop this path because:
- `updateChangedFiles` explicitly optimizes for exactly this "keep the diff to avoid needless re-render" case, gated only on `id` equality, not content equality (`start="90" end="95"` above).
- Nothing in `WorkingDirectoryStatus`/`FileChange` validates that content hasn't changed for a given `id` (`app/src/models/status.ts:356-397`); the map is purely path/status-kind keyed.
- `git-store.ts`'s `commitLookup` and other stores use SHA-based keys for *commits* (which are content-addressed and therefore immune to this class of bug), but the working-directory file model has no equivalent content anchor.

### Impact Explanation
If the diff shown to the user in the Changes pane is stale relative to what is actually on disk/in the index at commit time, the user can review content that no longer matches what will actually be committed and staged (git operates on the live working tree/index, not on Desktop's cached `IDiff` object). This is a "silent corruption of what the user commits" scenario: the user believes they reviewed and consciously included/excluded specific hunks of a file, but the file's real content diverged from that review before the commit was made. In a supply-chain-adjacent scenario (cloned/fetched repository with a hook or build step that rewrites tracked files), this could be leveraged to get a developer to commit and push content they never actually reviewed, under the visual assurance of Desktop's diff view. Severity is Medium: it requires content churn timed against Desktop's status-refresh cadence, and does not, by itself, achieve code execution or credential theft, but it can produce commits/pushes with unreviewed content.

### Likelihood Explanation
Desktop refreshes `git status` frequently (on window focus, git operations, background polling, file-system watcher events), so the window in which an in-place content rewrite at the same path/kind can occur between two polls is realistic, especially for a file being actively modified by tooling (build scripts, formatters, generated files, git hooks fired by `checkout`/`merge`/`commit`) inside a repository the user cloned from an attacker-controlled source. No special local access, elevated privileges, or social engineering beyond "clone/open this repo and let its tooling run" is required, and no explicit user click is needed beyond normal usage of the Changes view.

### Recommendation
Bind `WorkingDirectoryFileChange`/`FileChange` identity (or at minimum the diff cache validity check in `updateChangedFiles`) to something content-derived rather than only `status.kind + path` — e.g., include the git status entry's OID/mode information already available from `git status --porcelain`, or a content hash/mtime+size check, and invalidate the cached `selection.diff` whenever that content fingerprint changes even if `id` is unchanged.

### Proof of Concept
1. Clone an attacker-controlled repository that includes a `post-checkout` or `post-merge` hook (or a build step invoked by an editor/IDE integration) which rewrites `src/important.ts` in place after checkout, without changing the file's path.
2. Open the repo in Desktop; the working tree shows `src/important.ts` as `Modified`, so `id = "Modified+src/important.ts"`. Select it and let Desktop render/cache the diff (`state.selection.diff`) via `updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:90-95`).
3. Trigger a background status refresh (e.g. focus/blur the window, or wait for the poll interval) while the hook/build step silently rewrites `src/important.ts` again with different content, keeping the file `Modified` and the same path.
4. Because `id` is unchanged (`app/src/models/status.ts:263-275`), `updateChangedFiles` treats it as the same file and keeps `state.selection.diff` (the pre-rewrite diff) instead of fetching the new content's diff.
5. The user commits believing they reviewed the diff shown; the actual committed content reflects the rewritten file, which was never shown to the user.

export class WorkingDirectoryStatus {
  /** Create a new status with the given files. */
  public static fromFiles(
    files: ReadonlyArray<WorkingDirectoryFileChange>
  ): WorkingDirectoryStatus {
    return new WorkingDirectoryStatus(files, getIncludeAllState(files))
  }

  private readonly fileIxById = new Map<string, number>()
  /**
   * @param files The list of changes in the repository's working directory.
   * @param includeAll Update the include checkbox state of the form.
   *                   NOTE: we need to track this separately to the file list selection
   *                         and perform two-way binding manually when this changes.
   */
  private constructor(
    public readonly files: ReadonlyArray<WorkingDirectoryFileChange>,
    public readonly includeAll: boolean | null = true
  ) {
    files.forEach((f, ix) => this.fileIxById.set(f.id, ix))
  }

  /**
   * Update the include state of all files in the working directory
   */
  public withIncludeAllFiles(includeAll: boolean): WorkingDirectoryStatus {
    const newFiles = this.files.map(f => f.withIncludeAll(includeAll))
    return new WorkingDirectoryStatus(newFiles, includeAll)
  }

  /** Find the file with the given ID. */
  public findFileWithID(id: string): WorkingDirectoryFileChange | null {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? this.files[ix] || null : null
  }

  /** Find the index of the file with the given ID. Returns -1 if not found */
  public findFileIndexByID(id: string): number {
    const ix = this.fileIxById.get(id)
    return ix !== undefined ? ix : -1
  }
}
