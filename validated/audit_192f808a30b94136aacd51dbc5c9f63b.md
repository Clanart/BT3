### Title
Attacker can fund the multisig with dust outputs that are registered as received yet are economically unspendable - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The Lend report describes a class where a protocol accepts value below an economic minimum: the position exists on the books, but no rational actor will ever pay the gas to clean it up, so it becomes permanent bad debt. The analogous surface in Serai's in-scope Bitcoin wallet is its handling of UTXO value: `DUST = 546` is enforced on outgoing payments and on change, but neither `ReceivedOutput` (the scanned representation of an incoming deposit) nor the input side of `SignableTransaction::new` imposes any minimum on what is accepted into the wallet's accounting. An unprivileged party who sends dust-valued outputs to the multisig's Taproot `script_pubkey` creates "received" funds that cost more in fee weight to spend than they are worth — the same "sub-economic obligation nobody will service" shape.

### Finding Description
`SignableTransaction::new` rejects any *payment* below `DUST` and suppresses a change output when the leftover would be below `DUST`, but places no floor on the value of entries in the `inputs: Vec<ReceivedOutput>` argument [1](#0-0) [2](#0-1) .

`ReceivedOutput` is produced by the wallet's scanner, which matches an on-chain output purely by its `script_pubkey` against the offset group key (`p2tr_script_buf`) — there is no value check anywhere in that path, and `multisig()` likewise validates only the script, not the amount [3](#0-2) . So any P2TR output paying the multisig's tweaked key is treated as a received, owned output regardless of whether its value is 1 sat.

Each input consumes ~57.5 vbytes of witness/txin weight (witness is a single 64-byte Schnorr signature, as modeled in `calculate_weight_vbytes`) [4](#0-3) . At any non-trivial `fee_per_vbyte`, spending a 1-sat input costs far more than it returns — and `needed_fee` is enforced to clear the mempool minimum relay fee, so the input cannot be spent "for free" [5](#0-4) . Additionally, because `sign` commits to *all* inputs via `Prevouts::All` and produces a signature per input, every dust input inflates the signature count and transaction weight toward `MAX_STANDARD_TX_WEIGHT`, at which point `TooLargeTransaction` aborts the construction entirely [6](#0-5) [7](#0-6) .

### Impact Explanation
Two concrete harms, mirroring the original's "bad debt" framing:

1. **Funds reported received that are not economically spendable.** A dust deposit to the multisig key is registered as a received output; sweeping it burns more fee than it yields, so it is dead value on the wallet's books — exactly the "position no one will liquidate" analog.
2. **Griefing via input-set bloat.** An attacker can cheaply flood the multisig address with dust UTXOs. If input selection includes them, fees are wasted per input; if enough accumulate, any transaction spanning them exceeds `MAX_STANDARD_TX_WEIGHT` and `new` fails, blocking spends that would otherwise succeed.

### Likelihood Explanation
The attacker needs no privileges — only the multisig's public Taproot `script_pubkey`, which is derivable from the group key and is necessarily public to receive deposits. Sending dust outputs is a trivial, low-cost on-chain action. Whether the damage materializes as wasted fees or a hard `TooLargeTransaction` failure depends on how the caller assembles `inputs`, but the wallet code itself offers no defense or signal to filter sub-economic outputs — the burden is pushed entirely to the integrator, with no documented warning on `ReceivedOutput` or `new`.

### Recommendation
Enforce the same `DUST` floor symmetrically:
- Have the scanner/`ReceivedOutput` ignore (or flag) outputs whose `value < DUST`, so they never enter the spendable set.
- In `SignableTransaction::new`, either reject `inputs` entries below `DUST` or sum only economically-spendable inputs, and treat sub-dust inputs as nonexistent rather than silently increasing `needed_fee` and weight.
- Document that dust outputs sent to the multisig are irrevocably burnt (donated to miners as fee if ever spent), so accounting treats them as zero.

### Proof of Concept
```text
1. Attacker derives the multisig's P2TR script_pubkey from the public
   (offset) group key — no secret material needed.
2. Attacker broadcasts N transactions, each paying a 330-sat (sub-546)
   output to that script_pubkey.
3. The wallet scanner matches each output by script_pubkey alone and
   produces a ReceivedOutput for each — no value check exists on this path.
4. A subsequent withdrawal calls SignableTransaction::new with these
   dust ReceivedOutputs in `inputs`. Each adds ~57.5 vbytes to
   `needed_fee` (send.rs:204-213) and one full Schnorr signature share to
   `sign` (send.rs:377-397), while contributing ~0 sats of usable value.
5. With enough dust inputs, `weight > MAX_STANDARD_TX_WEIGHT` and `new`
   returns TooLargeTransaction — the multisig cannot construct a
   transaction spending its full UTXO set — or, if a subset is used, the
   dust outputs remain permanently on the books as unspendable "received"
   funds, the direct analog of un-liquidatable dust debt.
```

Note: this analog holds provided downstream input selection does not already discard dust UTXOs — that filtering, if present, lives in the out-of-scope processor code, and nothing within `networks/bitcoin/src` enforces it.
