### Title
`removePool()` fails to deactivate/clean stale votes, permanently corrupting governance vote proportions and bribe distribution - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager.removePool(uint256 _index)` removes a pool only from the `pools` array (swap-and-pop) but never sets the corresponding `poolInfos[_lp].isActive` flag to `false`, and never withdraws or clears existing votes/stakes for that pool. This mirrors the `detachHSG()` bug class: a "detachment"/removal action does not clean up already-granted state (votes, stake, active flag), leaving unprivileged voters with permanent, unauthorized influence over governance accounting.

### Finding Description
`removePool` only mutates the `pools` array: [1](#0-0) . It never touches `poolInfos[_lp].isActive`, which is set to `true` on `addPool` [2](#0-1) . Because `vote()` gates on `poolInfos[_lps[i]].isActive` (still `true` after removal) [3](#0-2) , any unprivileged wallet holding vlMGP can continue to call `vote()` targeting the delisted pool address indefinitely (not just as a front-run of the `removePool` transaction, but forever afterward), which:
- increments `pool.totalVoteInVlmgp` and `userVotedForPoolInVlmgp` for a pool that is no longer iterated by `castVotes()` (which only loops over the `pools` array) [4](#0-3) ,
- increments the global `totalVlMgpInVote` denominator used to compute every other (still-active) pool's proportional target vote: `targetVote = targetVoteInLMGP * totalVotes() / totalVlMgpInVote` [5](#0-4) ,
- and calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, ...)` on the (still live) rewarder contract of the removed pool [6](#0-5) , so the attacker's stake keeps accruing any bribe rewards later deposited to that rewarder.

This is the same root cause pattern as `detachHSG()`: a removal/detachment function leaves stale privileged state (owner rights in HSG; active-vote/stake rights in WombatBribeManager) unregistered, and the state can be persistently or repeatedly inflated by an ordinary wallet.

### Impact Explanation
Because votes routed to the delisted pool are permanently excluded from the real `castVotes()` distribution to the underlying `Voter`/`veWom` system, yet they still count in `totalVlMgpInVote`, they permanently and irreversibly dilute the proportional vote weight computed for every legitimately active pool — this is a direct governance voting result manipulation that skews the DAO's real veWom vote allocation across pools indefinitely, since there is no path to correct `totalVlMgpInVote` once votes are "lost" in a removed pool. Additionally, an unprivileged wallet can continue directing bribe stake toward the decommissioned pool's rewarder, diverting/permanently misallocating bribe yield that governance intended to stop routing there.

### Likelihood Explanation
This requires no privileged role — any vlMGP holder can call `vote()` at any time, including before or after a pool is removed via `removePool`, since `poolInfos[_lp].isActive` is never flipped to `false`. The precondition (a pool being removed via `removePool`) is a normal, expected admin operation, and the exploit path (continuing to call `vote()` against the stale pool address) is trivially reachable by any wallet, making this highly likely to occur, either accidentally or as a deliberate front-run/exploit of the removal transaction.

### Recommendation
In `removePool`, explicitly set `poolInfos[_lp].isActive = false` (and ideally force-unwind any residual `pool.totalVoteInVlmgp` / `totalVlMgpInVote` contributions, e.b. by withdrawing all stakes from `pool.rewarder`) before removing it from the `pools` array, so `vote()` correctly reverts with `PoolNotActive()` for the removed pool and the voting-weight denominator remains consistent with the pools actually processed in `castVotes()`.

### Proof of Concept
1. Owner calls `addPool(lpA, rewarderA, "A")` — `poolInfos[lpA].isActive = true`.
2. Owner later decides to decommission pool A and calls `removePool(indexOfA)` — this only removes `lpA` from the `pools` array; `poolInfos[lpA].isActive` remains `true` (see [1](#0-0) ).
3. Any vlMGP holder subsequently calls `vote([lpA], [positiveDelta])`. Because `poolInfos[lpA].isActive` is still `true`, this succeeds: `pool.totalVoteInVlmgp` and `totalVlMgpInVote` both increase, and `IBribeRewardPool(rewarderA).stakeFor(...)` stakes the caller's vote weight into the (still-live) rewarder contract.
4. `castVotes()` iterates only over the current `pools` array (which no longer contains `lpA`), so this newly added vote weight is never translated into a real vote via `wombatStaking.vote(...)`, yet it permanently remains counted in `totalVlMgpInVote`, permanently under-allocating veWom votes to every remaining active pool in the `targetVote` calculation [5](#0-4) .
5. The attacker's stake in `rewarderA` continues to receive any bribe funds later deposited to that pool's rewarder contract, permanently diverting yield away from active-pool voters.
