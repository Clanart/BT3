## Summary

The Zetachain report's core broken invariant is: **a manual, multi-step, order-dependent recovery procedure exists to keep the bridge live, and skipping/mis-sequencing any step leaves the bridge either halted or in an unprotected state.** The direct local analog in Hyperbridge is the `submit_mandatory_sequential` admin-relayer path for EVM `EvmHost` freeze/unfreeze gating.

## Finding Description

`EvmHost.sol` gates protocol operation with a `FrozenStatus` (`admin`-controlled `setFrozenState`), where `FROZEN_ALL = 3` halts the host and `FROZEN_NONE = 0` re-enables it [1](#0-0) . The intended design for the "Sequential" submission mode (used on chains without EIP-7702 support, e.g. Soneium) is to run three ordered transactions: `setFrozenState(None)` → `handleConsensus` → `setFrozenState(All)`, so the host is only briefly unfrozen for the exact duration required to admit the mandatory consensus proof [2](#0-1) .

However, in the actual implementation of `submit_mandatory_sequential`, both the unfreeze and refreeze transactions are commented out: [3](#0-2) 

The doc comment even acknowledges the intended invariant ("The refreeze step is always attempted, even if the consensus step fails, to avoid leaving the host unfrozen") but the code that would enforce it is dead/disabled. This mirrors the Zetachain bug class exactly: a documented multi-step state-transition procedure (unfreeze→act→refreeze) where one or more steps can be skipped, either by human error or partial failure, leaving the system in an unintended state indefinitely — with no automatic mechanism to detect or correct the drift.

Two possible failure states result on any chain configured with `SubmissionMode::Sequential`:
1. If the host is left in `FROZEN_ALL` outside of a maintenance window, `handleConsensus` calls will revert (since the host stays frozen), causing consensus updates to silently fail to land — halting mandatory light-client updates on that chain, which per the docs' own description of "mandatory" proofs is required or "its on-chain client will fall behind and stop accepting Hyperbridge proofs altogether" [4](#0-3) .
2. Conversely, if operators previously ran the batched/unfreeze step through some other means and the refreeze call is simply never issued (as coded), the host is left in `FROZEN_NONE` indefinitely — an unintended fully-unfrozen state that removes the safety property the freeze mechanism exists to provide (this is the more dangerous direction, since the freeze mechanism exists precisely to shut off value-moving/message-accepting entry points).

## Impact Explanation

This is a state-machine/host-halt issue in the mandatory-consensus-delivery path itself, not a peer/relayer trust assumption issue — the vulnerable code is in the repository's own admin-relayer logic that operators are expected to run as-is. Because `FROZEN_ALL` blocks message and consensus processing across the entire `EvmHost`, an operationally-triggered chain-wide halt (or, worse, an unintended permanent unfreeze bypassing the admin-only freeze control) on any chain using `SubmissionMode::Sequential` directly maps to the "Observer Can Temporarily Halt Chain" bug class: a supposedly transient state-toggle sequence that is not actually executed atomically/completely, producing prolonged denial of the mandatory consensus-update path (or removal of the freeze safety net) with no automated self-correction.

## Likelihood Explanation

This triggers whenever an operator configures `submission_mode = "sequential"` for a chain (explicitly supported and documented as the fallback for chains lacking EIP-7702, e.g. Soneium) — no malicious peer, prover, or relayer collusion is required; it is a straightforward consequence of running the shipped code path as intended. Given the comments show the unfreeze/refreeze calls were deliberately disabled (not simply an oversight elsewhere), any deployment relying on this mode will exhibit the described behavior deterministically.

## Recommendation

Restore (or gate behind a feature flag that is verified before deployment) the `setFrozenState(FROZEN_NONE)` and `setFrozenState(FROZEN_ALL)` calls in `submit_mandatory_sequential`, and make the refreeze step unconditionally executed with retries/alerting on failure (matching the doc comment's stated intent), so the host is provably never left outside its intended default `FROZEN_ALL` state outside of the exact `handleConsensus` transaction window. Add an on-chain or off-chain monitor that asserts the host's `FrozenStatus` returns to `FROZEN_ALL` after every sequential submission and pages on drift.

## Proof of Concept

1. Configure a chain with `submission_mode = "sequential"` in the admin-relayer's `AdminRelayerConfig` [5](#0-4) .
2. Run `submit_mandatory_sequential`; observe that only the middle `handleConsensus` transaction (`consensus_cd`) is submitted — the `_unfreeze_cd` and `_freeze_cd` transactions are never sent (lines are commented out) [6](#0-5) .
3. If the host's on-chain `FrozenStatus` was `FROZEN_ALL` beforehand, `handleConsensus` reverts against a frozen host, and the mandatory consensus update never lands, causing the chain's light client to fall behind indefinitely.
4. If instead the host had previously been unfrozen by any other means, it remains permanently in `FROZEN_NONE` after this call since the refreeze transaction is never issued, defeating the admin freeze safety mechanism for that chain going forward.
