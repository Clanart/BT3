### Title
Vetoing the latest state commitment resets `latestStateMachineHeight` to `1`, re-opening the door to previously superseded (stale) state commitments - (File: `evm/src/core/EvmHost.sol`)

### Summary
The report's core broken invariant is: "a mechanism meant to remove a bad/fraudulent entry has no safe floor, and once the removal window/logic is exercised, the system's trust state degrades to an unsafe default." Hyperbridge's local analog is the fisherman veto path (`deleteStateMachineCommitmentInternal`), which is the *only* on-chain way to strike a malicious/fraudulent state commitment from a connected chain. When it strikes the currently-latest height, it does not restore the previous good height — it resets the height watermark to the sentinel value `1`. [1](#0-0) 

### Finding Description
`handleConsensus` in `HandlerV2.sol` only accepts and stores a new intermediate state commitment when it strictly advances the state machine's height watermark:
```
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [2](#0-1) 

This monotonic check is the only replay/rollback protection for consensus-derived state commitments — it is the analog of the "only 1st year unregisterKey removal" restriction in the reported bug: a narrow, single-purpose removal capability with no thought given to the safe state after removal.

`deleteStateMachineCommitmentInternal` (invoked via `deleteStateMachineCommitment`, `restrict(_hostParams.handler)`) is the designated path for fishermen to veto a fraudulent/byzantine state commitment discovered during the challenge period:
```
if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
    _latestStateMachineHeight[height.stateMachineId] = 1;
}
``` [3](#0-2) 

Instead of restoring the watermark to the last known-good height, it unconditionally collapses it to `1`. Because `handleConsensus`'s only guard is `intermediate.height > latestHeight`, resetting to `1` means the *very next* consensus proof containing intermediate states at heights greater than 1 — including a height lower than the one that was just vetoed as malicious, or a stale/already-superseded height that the relayer/prover legitimately holds proofs for — will pass the monotonicity check and get written into `_stateCommitments`. This effectively removes any per-state-machine floor against re-accepting a state commitment older than (or equal to, at a different height slot) the one that was just proven fraudulent.

This mirrors the original bug's root cause exactly: a corrective action (`removeNodeFromRegistry` / vetoStateCommitment) exists but is scoped so narrowly and implemented so bluntly that it leaves the system in a strictly worse trust state than before the correction — here, the "worse state" is a watermark reset to `1` instead of a proper rollback to last-known-good height, re-opening acceptance of stale/malicious-adjacent state.

### Impact Explanation
If a relayer (any unprivileged/permissionless actor per `docs/content/developers/explore/relayers.mdx`) can submit a consensus proof containing an intermediate state at a low height right after a veto resets the watermark to `1`, the host will accept and store that state commitment as the new "latest," bypassing the intended monotonic protection. Since `stateMachineCommitment` and `stateMachineCommitmentUpdateTime` gate downstream `handlePostRequests`, `handleGetResponses`, and timeout handlers, an accepted stale/incorrect state commitment can lead to false proof acceptance for request/response delivery and timeouts — i.e., wrong-state message execution, potentially enabling fund loss/incorrect settlement for anything relying on that state machine's commitments.

### Likelihood Explanation
The veto path is explicitly designed to be invoked whenever byzantine behavior is detected — it is a routine, expected part of the fisherman/challenge-period security model, not an edge case. Any time a veto lands on the current latest height (a common case, since fraud is usually caught on the newest submitted commitment), the reset to `1` occurs automatically with no additional guard, and the next `handleConsensus` call from any permissionless relayer can immediately exploit the weakened floor.

### Recommendation
On veto of the latest height, restore `_latestStateMachineHeight[stateMachineId]` to the highest still-valid stored height below the vetoed one (tracked via a sorted/prev-height pointer) rather than a hardcoded sentinel `1`. Alternatively, track a per-state-machine "floor" that can only increase, independent of vetoes, so that once a height has been superseded by a higher legitimate commitment, no future commitment below that floor can ever be re-accepted.

### Proof of Concept
1. Consensus advances state machine `X` to height `100` via `handleConsensus`; `_latestStateMachineHeight[X] = 100`.
2. A fisherman detects `height 100`'s commitment is fraudulent and calls the handler-restricted veto path, which invokes `deleteStateMachineCommitmentInternal(height=100, fisherman)`. Since `_latestStateMachineHeight[X] == 100`, it is reset to `1`. [4](#0-3) 
3. Any relayer submits a new consensus proof whose verified intermediate states include state `X` at height `50` (an old, already-superseded, possibly stale/incorrect state root that would have been rejected under the height-100 watermark).
4. `handleConsensus`'s check `intermediate.height > latestHeight` (`50 > 1`) passes, and `storeStateMachineCommitment` writes this stale commitment as authoritative. [2](#0-1) 
5. Downstream request/response/timeout handlers now operate against this stale, previously-rejected-height state root, enabling false proof acceptance for messages that should not be considered valid under the current chain state.

     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
