### Title
Receipt-token over-minting in `WombatStaking.depositLP()` due to trusting nominal amount instead of actual token balance received - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP()` mints receipt tokens 1:1 for the caller-supplied `_lpAmount`, but never verifies that this is the amount of LP tokens actually received by the contract via `safeTransferFrom`. This is inconsistent with the sibling function `deposit()`, which correctly measures the actual LP tokens received using a before/after balance diff before minting receipt tokens and staking. This mismatch is the same bug class as the BOSS report: a helper/staking contract that mints tokens based on a nominal transfer amount rather than the balance actually delivered, which — for any LP/deposit token with non-standard transfer semantics (fee-on-transfer, rebasing, deflationary, or any hook that can reduce the delivered amount) — produces a permanent skew between receipt-token supply and the LP tokens actually custodied by the contract.

### Finding Description
In `deposit()`, LP tokens received from depositing into the Wombat pool are measured safely: [1](#0-0) 

In `depositLP()`, however, the contract transfers the LP token directly from the user and immediately mints the receipt token for the caller-specified `_lpAmount`, without ever checking how many tokens the contract's balance actually increased by: [2](#0-1) 

Because `poolInfo.lpAddress` is treated generically (its address is only fixed at `registerPool` time and the transfer/stake logic makes no assumption-checking call to verify balance deltas), any LP token whose `transferFrom` delivers less than the requested `_lpAmount` (fee-on-transfer, rebasing-down, or any deflationary mechanism) will cause the receipt-token supply minted via `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)` to exceed the LP tokens actually custodied and staked into MasterWombat via `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)`.

This is precisely the "mint/burn ... skew" pattern described in the BOSS report: the token/pool accounting trusts the nominal transfer amount instead of the delivered balance, letting supply of a claim token (BOSS's helper mint, here the Magpie `receiptToken`) drift out of sync with the real underlying asset held by the contract.

### Impact Explanation
If receipt-token supply exceeds actual LP token custody, redemptions on `withdraw()` (which burns the receipt token 1:1 and pulls real LP liquidity out of the underlying Wombat pool) will eventually fail for the last withdrawing users once the shortfall is exposed — this is a protocol insolvency / permanent freezing of funds scenario for later withdrawers, and it also dilutes existing receipt-token holders' backing immediately upon each affected deposit, since more claim tokens exist than assets held.

### Likelihood Explanation
`depositLP()` is directly reachable by an ordinary wallet through `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()` / `AnkrBNBPoolHelper.depositLP()` with no privileged role required: [3](#0-2) 
The likelihood is contingent on at least one registered `lpAddress` exhibiting non-standard transfer behavior (fee-on-transfer/rebasing/deflationary), which is a property of the token itself rather than of a privileged actor's decision at call time — the deposit/withdraw code path itself contains no defensive check, unlike its sibling `deposit()` function, which shows the developers were aware of and already mitigated this exact issue in one function but not the other. I could not fully verify the internals of `_toMasterWomAndSendReward()` (the tool budget was exhausted before I could inspect its full body), so I cannot confirm whether that internal staking call would itself revert on an insufficient balance and thus block exploitation; this is a gap in my verification.

### Recommendation
In `depositLP()`, measure the pool's LP token balance before and after `safeTransferFrom`, and use that delta (not the caller-supplied `_lpAmount`) for both `_toMasterWomAndSendReward` and the receipt-token `mint` call, mirroring the pattern already used in `deposit()`.

### Proof of Concept
1. Assume/register (or encounter) a `lpAddress` pool token with fee-on-transfer or deflationary semantics (e.g., delivers 99% of `_lpAmount` on transfer).
2. Ordinary user calls `WombatPoolHelper.depositLP(_lpAmount)` → `WombatStaking.depositLP(lpToken, _lpAmount, user)`.
3. `safeTransferFrom` only delivers `0.99 * _lpAmount` LP tokens to `WombatStaking`, but `receiptToken.mint(msg.sender, _lpAmount)` mints the full nominal amount.
4. Repeat deposits accumulate a growing gap between receipt-token supply and actual LP custody.
5. When enough users call `withdraw()`, the pool's actual LP balance is insufficient to satisfy the total receipt-token claims, causing later withdrawals to revert (insolvency / fund freeze) while earlier withdrawers may still succeed.
