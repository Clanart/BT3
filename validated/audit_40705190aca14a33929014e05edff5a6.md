### Title
Burn-on-Transfer / Deflationary ERC20 Tokens Cause Supply Inflation in Cross-Chain Bridge Value Transfer - (File: contracts/service_chain/bridge/BridgeTransferERC20.sol)

### Summary
`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` pull tokens from the caller via `safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then request a cross-chain value transfer for the *declared* `_value`, rather than the amount actually received by the bridge contract. For deflationary/burn-on-transfer tokens (tokens that burn or otherwise reduce the transferred amount during `transfer`/`transferFrom`), the bridge will hold strictly less than `_value + _feeLimit`, yet it will still request/record the full nominal `_value` for release on the counterpart chain.

### Finding Description
`requestERC20Transfer` calls `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))` and then immediately calls `_requestERC20Transfer`, which computes the fee via `_payERC20FeeAndRefundChange` and emits `RequestValueTransfer(..., _value, requestNonce, fee, ...)` using the caller-supplied `_value`, not a balance-before/after delta [2](#0-1) [1](#0-0) .

On the counterpart chain, operators call `handleERC20Transfer`, which either mints `_value` new tokens to `_to` (`modeMintBurn == true`) or transfers `_value` out of the bridge's existing token reserve (`modeMintBurn == false`), again using the nominal `_value` from the request event with no cross-check against actual escrowed/burned amounts [3](#0-2) . In `modeMintBurn` mode, the request side also calls `ERC20Burnable(_tokenAddress).burn(_value)` on the (already deflated) balance held by the bridge, using the nominal `_value` again rather than the true post-transfer balance [4](#0-3) .

If a registered ERC20 token implements burn-on-transfer or fee-on-transfer semantics, the actual amount received by the bridge (`balanceOf(bridge) after - before`) will be less than `_value + _feeLimit`. Because neither `requestERC20Transfer` nor `_payERC20FeeAndRefundChange`/`_requestERC20Transfer` verify the bridge's real balance delta, the accounting recorded in `RequestValueTransfer` (and consequently minted/released via `handleERC20Transfer` on the counterpart chain) is based on the inflated nominal value rather than the true received amount. This is architecturally identical to the reported burn-on-transfer bug pattern: a component trusts a caller-declared/nominal transfer amount instead of measuring the actual balance received.

### Impact Explanation
Any unprivileged caller who registers (or who convinces an operator to register) a burn-on-transfer/deflationary token, and repeatedly calls `requestERC20Transfer`, can cause the bridge to under-collateralize its token reserve relative to the nominal amounts it has requested. In `modeMintBurn` mode this directly leads to `ERC20Burnable.burn(_value)` potentially reverting (since the bridge's real balance is less than `_value`) or, more critically, to counterpart-chain minting of `_value` tokens that were never actually escrowed/burned in full, resulting in unbacked token supply inflation on the other chain. In non-mint-burn mode, `handleERC20Transfer`'s `safeTransfer(_to, _value)` draws from the shared reserve pool, meaning a deflationary-token depositor can drain value contributed by other depositors' un-deflated tokens (a classic "eating into someone else's deposit" scenario, matching the report's exact framing).

### Likelihood Explanation
Exploitability depends on a deflationary/burn-on-transfer token being registered with the bridge (`onlyRegisteredToken`), which requires token registration (typically an operator/governance action), so it is not exploitable against arbitrary unregistered tokens. However, once such a token is registered — which is plausible since bridge operators register arbitrary user-requested ERC20 tokens for cross-chain use — any regular, unprivileged transaction sender interacting with that token can trigger the mismatch on every transfer, making this a systematic and repeatable issue rather than a one-off edge case.

### Recommendation
In `requestERC20Transfer`/`onERC20Received`, measure the bridge contract's token balance immediately before and after `safeTransferFrom` and use the actual received delta (rather than the caller-declared `_value + _feeLimit`) as the basis for fee calculation, `RequestValueTransfer` emission, and (in mint-burn mode) the `burn()` amount. Alternatively, explicitly document and technically enforce that only standard-compliant, non-deflationary ERC20 tokens can be registered via `registerToken`, and add a registration-time or first-deposit invariant check verifying that transferred amounts match expected balances.

### Proof of Concept
1. Deploy (or have an operator register) a deflationary ERC20 token `DFLT` that burns X% of every `transfer`/`transferFrom`.
2. As any user, call `token.approve(bridge, value + feeLimit)` then `bridge.requestERC20Transfer(DFLT, to, value, feeLimit, extraData)`.
3. Observe: `safeTransferFrom` pulls `value + feeLimit` nominal units, but the bridge's actual `balanceOf(bridge)` increases by less than `value + feeLimit` due to the burn.
4. `_payERC20FeeAndRefundChange` and `RequestValueTransfer` still operate on the nominal `_value`/`_feeLimit`, so the emitted event (and hence the counterpart-chain `handleERC20Transfer` mint/transfer of `_value`) does not reflect the shortfall.
5. In `modeMintBurn` mode, repeat step 2 enough times that `_requestERC20Transfer`'s `ERC20Burnable(_tokenAddress).burn(_value)` call reverts because the bridge's true balance is less than the cumulative nominal `_value`, or, in non-mint-burn mode, show that `handleERC20Transfer`'s payout on the counterpart chain draws down the shared reserve funded by other users' honest-token deposits.
