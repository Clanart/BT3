### Title
`updateEndRemainingAllocation()` re-snapshots the bonus denominator on every call, letting an attacker shrink it to inflate their own share of `totalBonus` - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is `public`, has no access control and no one-shot guard, so it can be invoked repeatedly by anyone after `periodsEndTime[4]`. Because `totalRemainingAllocation` decreases every time a user calls `claim()`, an attacker can wait until other users have already claimed and then call `updateEndRemainingAllocation()` themselves right before claiming, shrinking `totalEndRemainingAllocation` and capturing a disproportionately large share of `totalBonus`.

### Finding Description
`totalEndRemainingAllocation` is meant to be a single, fixed snapshot of `totalRemainingAllocation` taken the moment the vesting period ends, and it is used as the fixed denominator in `getBonusAmount()`: [1](#0-0) 

The only guard against re-triggering is inside `claim()`: [2](#0-1) 

`claim()` only calls `updateEndRemainingAllocation()` when `totalEndRemainingAllocation == 0`, i.e. it self-guards against re-triggering *through claim()*. But `updateEndRemainingAllocation()` itself is a standalone public function with no such guard: [3](#0-2) 

Anyone can call it directly, any number of times, as long as `block.timestamp >= periodsEndTime[4]`. Each call overwrites `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation`, which shrinks every time a user claims (`totalRemainingAllocation -= userAllocation` in `claim()`). 

Exploit flow:
1. After `periodsEndTime[4]`, several legitimate users claim, shrinking `totalRemainingAllocation` from the original snapshot value down toward the attacker's own allocation size.
2. The attacker calls `updateEndRemainingAllocation()` directly, re-snapshotting `totalEndRemainingAllocation` to this much smaller value.
3. The attacker immediately calls `claim()`. Since `totalEndRemainingAllocation != 0` already, `claim()` skips re-updating it and uses the attacker-manipulated (small) denominator.
4. `bonusAmount = userAllocation * totalBonus / totalEndRemainingAllocation` is now computed with an artificially small denominator, giving the attacker a share of `totalBonus` far larger than their fair pro-rata portion relative to everyone who was actually unclaimed at `periodsEndTime[4]`.

This breaks the invariant that the bonus denominator must be fixed exactly once for all participants; instead it is fixed to whatever value is convenient for whoever calls it last before claiming, favoring late/opportunistic claimers over earlier or later legitimate claimants and potentially causing `InsufficientBalance` reverts (temporary freezing) or a bonus over-payout that reduces funds available to remaining users.

### Impact Explanation
The attacker extracts more than their fair pro-rata share of `totalBonus`, directly at the expense of other users entitled to a share of the same forfeited pool, and can also drain the contract such that later legitimate claimants revert with `InsufficientBalance`, freezing their funds. This matches direct theft of user funds / theft of unclaimed yield.

### Likelihood Explanation
No privileged role is needed - `updateEndRemainingAllocation()` has no `onlyOwner` or similar modifier. The only precondition is waiting until after `periodsEndTime[4]` and until enough other users have claimed to shrink `totalRemainingAllocation`, both of which are externally observable on-chain and require no capital beyond the attacker's own (potentially minimal) registered allocation. The attack is trivially repeatable by any registered allocatee or, since the function is public, callable by any address at all (though only registered allocatees benefit from a subsequent `claim()`).

### Recommendation
Snapshot `totalEndRemainingAllocation` exactly once, e.g. add a boolean flag (`bool endSnapshotTaken`) or check `if (totalEndRemainingAllocation == 0 && !endSnapshotTaken)` and set the flag atomically, or restrict `updateEndRemainingAllocation()` so it can only ever transition from `0` to a nonzero value and never be overwritten again, regardless of caller.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, register 3 users: Alice, Bob (large allocations), Attacker (small allocation).
2. Warp time to `periodsEndTime[4]`.
3. Alice and Bob call `claim()` first (this triggers the first `updateEndRemainingAllocation()` snapshot at the original large `totalRemainingAllocation`, and both forfeit nothing/some amount into `totalBonus` depending on timing — arrange so `totalBonus > 0`, e.g. have another user forfeit before period 4 by claiming early in earlier periods).
4. After Alice and Bob claim, `totalRemainingAllocation` shrinks to roughly Attacker's allocation.
5. Attacker calls `updateEndRemainingAllocation()` directly, then `claim()`.
6. Assert: `getBonusAmount(attacker)` computed with the re-snapshotted small `totalEndRemainingAllocation` is much larger than it would have been under the original snapshot (`attackerAllocation * totalBonus / originalTotalRemainingAllocation`).
7. Assert: total tokens paid out (`sum of claimableAmount`) can exceed what should be owed to remaining claimants, or a subsequent legitimate claimant reverts with `InsufficientBalance`.

    function claim() external {
        if (totalEndRemainingAllocation == 0) {
            updateEndRemainingAllocation();
        }
        uint256 claimableAmount = getClaimableAmount(msg.sender);
        
        if(claimableAmount == 0) revert NothingToClaim();
        if(claimableAmount > aidropToken.balanceOf(address(this))) revert InsufficientBalance();

        uint256 userAllocation = allocations[msg.sender];
        allocations[msg.sender] = 0;
        totalRemainingAllocation -= userAllocation;
        if (claimableAmount <= userAllocation) {
            uint256 forfeited = userAllocation - claimableAmount;
            totalBonus += forfeited;
        }
        aidropToken.safeTransfer(msg.sender, claimableAmount);
    }
