## Finding: CEI-Pattern Regression in `IntentGatewayV2.withdraw()` (Tron Fork)

### Title
Escrow decrement occurs after external token/native transfer in `withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron-specific fork of `IntentGatewayV2` contains an internal `withdraw()` function that performs the external transfer to the beneficiary *before* decrementing the escrow accounting (`_orders[body.commitment][token]`), reproducing exactly the Checks-Effects-Interactions violation described in the external report. This is the same bug class that was explicitly fixed elsewhere in the codebase — the mainline EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` decrements escrow (`_orders[body.commitment][token] = escrowed - amount;`) *before* making the external call, and a dedicated regression-test suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) documents that this ordering was deliberately fixed to defeat reentrancy theft of escrow.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // <== External Call

            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); // <== External Call
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <== State Change, AFTER interaction
        ...
```

By contrast, the sibling implementation that received the CEI fix decrements the escrow mapping *before* transferring: [2](#0-1) 

and the regression tests explicitly assert this ordering is what defeats reentrancy on the EVM path: [3](#0-2) 

The guard check in the Tron `withdraw()` is also weaker than a sufficiency check — `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only verifies the escrow slot is non-zero, not that it covers `amount`, relying solely on Solidity 0.8's built-in underflow revert on `-= amount` as the actual safety net, which only fires *after* the external call has already executed.

The `_filled[body.commitment] = beneficiary;` assignment does happen before the loop, which blocks the most direct reentry vector — a malicious `beneficiary` re-entering `cancelOrder()` (which unconditionally checks `_filled[commitment] != address(0)` first) is rejected. However, this same `withdraw()` is also invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()` — both driven by cross-chain message delivery — and the per-token escrow value (`_orders[commitment][token]`) is only protected by the `_filled` mutex on the *order* as a whole, not on each token slot independently, while the actual token accounting update happens strictly after interaction. Any escrow token contract with transfer-time callback semantics (e.g., ERC-777-style hooks or a token with `_beforeTokenTransfer`/`_afterTokenTransfer` logic that calls back into other contracts) executing as part of the `token.call(...)` step runs with `_orders[commitment][token]` still un-decremented, which is a structural CEI violation independent of whether the specific `_filled` mutex happens to close off the most obvious replay path.

### Impact Explanation
If exploitable, this class of bug allows escrowed input tokens to be paid out more than once for the same commitment/token before accounting is updated, i.e. loss/duplicate-settlement of bridged escrow funds — squarely in-scope for the bounty ("stealing or loss of funds," "logic attacks," "double-settlement"). The bug lives in the fund-custody path (`withdraw()`), which is reached by both user-initiated `cancelOrder()` and host-driven `onAccept`/`onGetResponse` cross-chain settlement, i.e., production bridge/contract logic, not test or dependency code.

### Likelihood Explanation
Likelihood is **Low-to-Medium**, not fully proven exploitable within available investigation. The `_filled[body.commitment]` mutex, set before the vulnerable loop, blocks the most obvious same-order re-entry through `cancelOrder()`, and `onAccept`/`onGetResponse` are `onlyHost`-gated so cannot be re-entered directly by an arbitrary externally-owned or token contract. The residual risk is specific to escrowed ERC-20 tokens with transfer-time callback hooks interacting with the still-unified per-token escrow slot before it is decremented — a scenario that depends on which tokens are actually escrowable on the deployment (standard ERC-20 `transfer` has no callback, so ordinary tokens are not exploitable this way). I was not able to fully verify within the tool budget whether any callback-capable token or any other function that reads `_orders[commitment][token]` without checking `_filled` is reachable during this window; the file's `fillOrder`/entry-point functions for this Tron fork were not fully reviewed.

### Recommendation
Refactor `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the fixed pattern in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw()`: check `amount <= _orders[body.commitment][token]`, decrement `_orders[body.commitment][token]` first (Effects), and only then perform the native/token transfer (Interaction). Apply the same ordering to the transaction-fee payout block later in the same function.

### Proof of Concept
Conceptual PoC (not executed, since only static analysis tools were available):
1. Deploy an ERC-20-like token with a transfer hook (e.g., ERC-777 equivalent) as an order input token on the Tron `IntentGatewayV2`.
2. Place an order escrowing this token, then trigger a cross-chain `RedeemEscrow`/`RefundEscrow` message that calls `withdraw()`.
3. Inside the token's transfer hook (invoked synchronously during `token.call(transfer(...))` before `_orders[commitment][token] -= amount` executes), attempt to re-enter a code path that reads/pays out `_orders[commitment][token]` again without checking `_filled[commitment]`.
4. If such a path exists (not conclusively found here), the escrow for that token would be paid out twice before the accounting decrement lands, causing double-settlement of bridged funds.

Given the residual uncertainty on step 3, this should be treated as a confirmed **code-quality/CEI regression** in the fund-custody path with a plausible-but-unconfirmed reentrancy consequence, warranting the same fix already applied to the non-Tron implementation.
