### Title
`SignableTransaction` omits the OP_RETURN data output from weight/vsize calculation, undercharging the fee and producing non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes a user-influenced `OP_RETURN` output into the real transaction's `tx_outs`, but the fee and standardness checks are computed by `calculate_weight_vbytes`, which reconstructs a template transaction containing only `payments` (and optionally `change`). The `data` output is never included in that template. The resulting `needed_fee` and `weight` are calculated on a shorter transaction than the one actually signed and broadcast — the same bug class as CVE-2026-80522, where `cryptlen` was computed with a formula inconsistent with the operation actually performed, yielding a wrong length that propagates into the real operation.

### Finding Description
In `SignableTransaction::new`, when `data` is `Some`, an additional `TxOut` with an `OP_RETURN` script is appended to `tx_outs` (the outputs of the transaction actually signed):

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

However, the fee/weight estimation is invoked as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` only, with no `data` parameter:

```rust
// networks/bitcoin/src/wallet/send.rs:204
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

Inside `calculate_weight_vbytes` the template `tx.output` is built only from `payments` (plus optional `change`), so every payment output's `script_pubkey` length is accounted for, but the `OP_RETURN` output — 8-byte value + compact-size length + script bytes + output-count/varint effects — is missing entirely:

```rust
// networks/bitcoin/src/wallet/send.rs:85-99
output: payments
  .iter()
  .map(|payment| TxOut {
    value: Amount::from_sat(payment.1),
    script_pubkey: payment.0.clone(),
  })
  .collect(),
```

Both downstream consumers of the incorrect length are affected:
- `needed_fee = fee_per_vbyte * vbytes` undercharges by `fee_per_vbyte * vsize(OP_RETURN output)`, and the change-amount path `input_sat.checked_sub(payment_sat + fee_with_change)` uses the same undercounted `vbytes_with_change`, so change is over-credited relative to the intended fee rate.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` is evaluated against a weight that excludes the `OP_RETURN` output, so a transaction which is actually over the standard weight limit is accepted by `SignableTransaction::new`.

### Impact Explanation
The `data` field originates from user-supplied payment/instruction data, so an unprivileged party can force the discrepancy. Consequences:

- The produced transaction has a lower effective sat/vbyte rate than the `fee_per_vbyte` requested. For large `data` (tens of bytes of script), the shortfall can push the real feerate below the node's minimum relay fee even though the `TooLowFee` check passed, yielding a transaction that signs successfully but is rejected/dropped by the Bitcoin network — inputs remain locked to a plan that never settles on-chain.
- A transaction legitimately near `MAX_STANDARD_TX_WEIGHT` can be constructed that exceeds the limit once the `OP_RETURN` output is serialized, again producing a non-relayable transaction despite the explicit `TooLargeTransaction` guard.

This maps to the accepted impact "funds reported received that are not spendable" in its weaker form: outputs are planned and signed for, but the resulting transaction cannot reliably propagate/confirm, so scanned funds are not spendable in practice until reconstructed.

### Likelihood Explanation
Any plan/payment carrying `data` (e.g., an `InInstruction` data payload reflected into a refund/forward transaction) triggers the miscalculation; no attacker sophistication is needed — merely supplying a non-empty data field suffices. Severity is Medium: it requires the data-carrying path to be exercised and a fee-rate or weight boundary to be crossed, and the failure is liveness/fund-accessibility rather than direct theft.

### Recommendation
Pass the `data` output into `calculate_weight_vbytes` (e.g., extend `payments` to a full `&[TxOut]`-equivalent including the `OP_RETURN` script) so the template transaction's output set exactly matches `tx_outs`, for both the no-change and with-change calculations. Alternatively, compute weight directly on the final `Transaction` after all outputs are appended, eliminating the duplicated formula entirely — mirroring the upstream fix's approach of computing `cryptlen` identically in both paths.

### Proof of Concept
```rust
// Conceptual: networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 75]; // any non-empty OP_RETURN payload
let tx = SignableTransaction::new(
    vec![input], &payments, Some(change_script), Some(data.clone()), FEE,
).unwrap();

// The real transaction includes the OP_RETURN output:
assert_eq!(tx.transaction().output.len(), payments.len() + 2 /* payment + OP_RETURN + change */);

// But needed_fee was computed without it:
//   actual_vsize = tx.transaction().vsize() + witness share > vbytes used for needed_fee
//   => needed_fee < FEE * actual_vsize
// The shortfall equals FEE * vsize_of(TxOut{ value: 0, script_pubkey: OP_RETURN data }),
// so the effective feerate of the broadcast tx is strictly less than FEE,
// and the MAX_STANDARD_TX_WEIGHT check under-counts by the same output's weight.
```
