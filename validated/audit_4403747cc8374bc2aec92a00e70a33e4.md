### Title
`headCloneUrl` from GitHub API pull-request objects is passed unvalidated to `git remote add` / `git remote set-url`, allowing an attacker-controlled fork to inject Git command options via a leading-dash URL - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_findPullRequestBranch` takes `headCloneUrl` — a string that comes directly from the GitHub API's pull-request payload (`pullRequest.head.repo.clone_url` / `pullRequest.head.gitHubRepository.cloneURL`) — and, without any format/allow-list validation, forwards it to `addRemote()`, which builds the argument vector `['remote', 'add', name, url]` and executes it as a git subprocess argument. [1](#0-0) [2](#0-1) 

### Finding Description
The broken invariant, analogous to the DYAD `MIN_MINT_DYAD_DEPOSIT` bug, is: "a value that must always be constrained to a safe/trusted shape is enforced (validated) at one entry point but not at another entry point that consumes the same underlying attacker-controlled data." In DYAD, `mint()` checked a minimum deposit, but `redeemDeposit()` never re-checked it, letting the same actor bypass the protection through the second call path. Here, the "value" is the pull-request head clone URL, which is attacker-controlled because any GitHub user can open a pull request from a forked repository and supply/rename that fork; the URL is materialized into `pullRequest.head.repo.clone_url` by the GitHub API.

While GitHub Desktop does validate/parse URLs strictly in some paths (`parseRemote`/`parseRepositoryIdentifier` in `app/src/lib/remote-parsing.ts`, `sanitizeCloneName`, and `isClonePathSensitive` in `app/src/lib/git/clone.ts`), the pull-request-checkout code path does **not** route through any of those guards:

- `openPullRequestFromUrl` (triggered by an "Open in Desktop" deep link, i.e. `github-mac://openRepo/...` parsed in `app/src/lib/parse-app-url.ts`) fetches a PR object from the API and passes `pullRequest.head.repo.clone_url` straight into `_checkoutPullRequest` → `_findPullRequestBranch`. [3](#0-2) 
- The dispatcher's `checkoutPullRequest` (triggered from the in-app pull request list, i.e. simply clicking a listed PR that could be authored by anyone with a fork) does the same, forwarding `pullRequest.head.gitHubRepository.cloneURL` unchecked. [4](#0-3) 
- `_findPullRequestBranch` only checks whether the URL matches an *existing* remote (`urlMatchesRemote`); if not, it calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the raw string. [5](#0-4) 
- `addRemote` simply builds `['remote', 'add', name, url]` and hands it to the `git` subprocess wrapper — there is no check that `url` doesn't begin with `-` (which `git remote add` would interpret as an option rather than a positional URL, e.g. `--upload-pack=` style option smuggling, or values recognized by embedded transport helpers such as `ext::sh -c ...` when the remote is later fetched). [2](#0-1) 

By contrast, the codebase clearly demonstrates that the maintainers *know* URL-derived values must be sanitized before use in file-system or git operations — see the hardened `sanitizeCloneName`/`isClonePathSensitive` logic used specifically for the "Clone Repository" flow. [6](#0-5) [7](#0-6) 
That same discipline is missing for the PR-checkout remote-add code path, which is reachable from a strictly less-trusted source (an arbitrary fork owner's `clone_url`, and a clickable deep-link/PR-list entry) than a manually typed clone URL.

### Impact Explanation
`git remote add`/`git remote set-url` accepting attacker-influenced, unsanitized strings is a known class of Git argument-injection vector: a crafted `clone_url` beginning with `-` can be interpreted by `git remote` (or, once fetched, by git's transport-helper dispatch, e.g. `ext::`, `fd::`, or other helper schemes if not blocked by the runtime git version/config) as a flag or alternate protocol rather than as a plain URL, and depending on the resolved git version/config can lead to unexpected command execution or SSRF-like remote-transport control on the victim's machine, silently corrupting what repository/remotes the user subsequently fetches/pushes to. This satisfies "attacker controls a GitHub API object … result is code execution … or silent corruption of what the user commits or pushes."

### Likelihood Explanation
The attacker precondition is low-effort and fully within the described threat model: any user can open a public pull request from a fork whose `clone_url` they influence (via repo name/transfer or a self-hosted Enterprise remote in more permissive configurations), and the victim only needs to either (a) click the PR in the Pull Requests list of a repository they already have open in Desktop, or (b) click a "View in Desktop"/`x-github-client://openRepo/...` deep link — both are normal, expected user interactions, not "unnatural user steps." No local access, admin rights, or pre-existing malware is required.

### Recommendation
Validate `headCloneUrl` (and any `clone_url`/`cloneURL` sourced from GitHub API PR objects) through the same strict parser used elsewhere (`parseRemote`/`parseRepositoryIdentifier`) before calling `addRemote`/`setRemoteURL`, rejecting any value that does not match a known `https://`/`ssh://`/`git@` remote-URL shape (in particular reject values starting with `-` or containing `::`). Apply this check inside `addRemote`/`setRemoteURL` themselves (in `app/src/lib/git/remote.ts`) so the guard is centrally enforced for every call site, not just the ones a reviewer remembers to protect — the same "add the invariant at the primitive, not at each caller" recommendation as in the source report.

### Proof of Concept
1. Attacker forks a target repository and (where the git hosting allows a custom/renamed remote-mapping or the attacker registers a repo name) opens a pull request whose head repo's `clone_url` is crafted to start with `-` (e.g. `--upload-pack=touch$IFS/tmp/pwned;`) or an alternate transport scheme.
2. Attacker sends the victim (who has the base repository open in GitHub Desktop) a link to the PR, or the victim simply opens the built-in Pull Requests list and clicks the malicious PR.
3. Desktop calls `dispatcher.checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`, which finds no existing remote matching the crafted URL and calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the raw, attacker-controlled string. [8](#0-7) 
4. `addRemote` executes `git remote add <name> <headCloneUrl>` without validating the URL shape, and the crafted value is passed straight to the `git` subprocess as an argument. [2](#0-1)

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
