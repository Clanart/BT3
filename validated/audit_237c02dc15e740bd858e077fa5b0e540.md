**Analysis:**

`entryIsEligibleForRefresh` compares the entry's `fetchedAt` against `Date.now()` using the *local system clock*, not any value derived from the API/proxy response: [1](#0-0) 

Tracing every place `fetchedAt` is written in the store, all of them assign it from the local wall clock (`new Date()`), never from an API response header, timestamp field, or any other attacker-influenced value:

- [2](#0-1)  (manual refresh)
- [3](#0-2)  (failed fetch fallback)
- [4](#0-3)  (successful refresh)
- [5](#0-4)  (branch-name change, uses `offsetFromNow(-61, 'minutes')` — also purely local-clock arithmetic, and it moves the entry 61 minutes into the *past*, forcing eligibility, not blocking it)

`offsetFromNow` itself is a pure local-time helper with no external input: `app/src/lib/offset-from.ts`. There is no code path in `commit-status-store.ts` (or its dependencies `ci-checks.ts`, `api.ts`) that reads a timestamp or clock-skew value out of the GitHub API/proxy response body or headers and feeds it into `fetchedAt`. Since the attacker (a malicious API/proxy) has no way to influence the value written to `fetchedAt`, they cannot seed a cache entry with a future `fetchedAt` remotely — that would require controlling the local system clock, which is out of scope (local/physical access). The `check` object's fields (e.g. `htmlUrl`, `actionsWorkflow`) are indeed API-controlled, but that is a separate rendering/escaping concern unrelated to the `entryIsEligibleForRefresh` staleness logic described in this question, and no reachable path was found by which an attacker forces `fetchedAt` itself to be poisoned.

Given the premise (attacker controls the `fetchedAt` timestamp via API/proxy response or clock skew) does not correspond to any actual code path, this finding does not hold.

function entryIsEligibleForRefresh(entry: ICommitStatusCacheEntry) {
  // The age (in milliseconds) of the cache entry, i.e. how long it has
  // sat in the cache since last being fetched.
  const now = Date.now()
  const age = now - entry.fetchedAt.valueOf()

  // The GitHub API has a max-age of 60, so no need to refresh
  // any more frequently than that since Chromium would just give
  // us the cached value.
  return age > 60 * 1000
}
