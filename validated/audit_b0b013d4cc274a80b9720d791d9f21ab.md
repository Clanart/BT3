### Title
Missing Slippage Protection on WOM→mWom Conversion in `ArbWomUp3.incentiveDeposit()` (mode 2) - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit()` is a public, unprivileged entry point that lets any wallet deposit WOM to receive MGP/mWomSV rewards. When called with `_mode == 2`, the internal `_deposit()` routes half of the user's WOM through `SmartWomConvert.convert()`, but hardcodes the minimum-received parameter to `0`, completely disabling the slippage check that `SmartWomConvert._convertFor()` otherwise enforces.

### Finding Description
`incentiveDeposit()` calls `_deposit(msg.sender, _convertRatio, _amount, _mode)`, and for `_mode == 2` the internal logic is: [1](#0-0) 

```
} else if (_mode == 2) {
    ...
    // 50% smart smart convert
    IERC20(wom).safeApprove(smartWomConvert, toSwap);
    IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0);
    ...
}
```

The `_minRec` argument passed to `SmartWomConvert.convert()` is hardcoded `0`, even though `_convertFor()` in `SmartWomConvert.sol` normally uses this exact value to protect against price manipulation of the WOM→mWom swap: [2](#0-1) 

```
if (buybackAmount > 0) {
    ...
    amountRec = IWombatRouter(router).swapExactTokensForTokens(
        tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp
    );
}
...
if (convertAmount + amountRec < _minRec)
    revert MinRecNotMatch();
```

The internal swap itself is also called with a `0` minimum (`swapExactTokensForTokens(..., 0, ...)`), relying entirely on the outer `_minRec` check to enforce user-provided slippage tolerance. Because `ArbWomUp3` forces `_minRec = 0`, this check becomes a no-op for any user that chooses `_mode == 2`, exactly matching the reported bug class: a slippage parameter that is supposed to validate the *actual* value ultimately delivered to the user is bypassed/decoupled from the real output, allowing the user to receive an arbitrarily small amount of `mWom` without any revert.

This differs slightly from the original report (which described a check against the wrong variable) but is the closest reachable analog in scope: the slippage safeguard exists in the underlying `SmartWomConvert` conversion path but is deliberately neutralized by the caller, so an ordinary user's `incentiveDeposit()` call can be sandwiched around the `WombatRouter` swap inside `_convertFor()` to reduce `amountRec`, and the check `convertAmount + amountRec < _minRec` can never fail since `_minRec == 0`.

### Impact Explanation
An MEV/sandwich attacker can manipulate the WOM/mWom pool price around a user's `incentiveDeposit(_mode=2)` transaction. Because `_minRec` is fixed at `0`, the user's WOM gets converted at whatever (manipulated) price is available at execution time with no floor, resulting in the user permanently receiving less `mWom`/locked value than the fair-market amount for their deposited WOM. This is a direct loss of user funds during an unprivileged, user-initiated transaction.

### Likelihood Explanation
This requires no privileged role or admin action — any wallet holding WOM can call `incentiveDeposit()` with `_mode == 2`. The only difficulty for an attacker is generating a sandwich around the internal `IWombatRouter.swapExactTokensForTokens` call. Since this is a common and inexpensive MEV technique (front-run/back-run), likelihood is non-trivial. However, the deposit amount used in the vulnerable path is only half of `_amount` (`toSwap`), and the actual value at risk depends on the buyback ratio and pool depth/liquidity of the WOM/mWom pool.

### Recommendation
Do not hardcode `_minRec` to `0` in `ArbWomUp3._deposit()`'s mode-2 branch. Either:
- Expose a `_minRec`/slippage parameter on `incentiveDeposit()` that the caller can set and thread it through to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, 0)`, or
- Compute an expected minimum via `SmartWomConvert.estimateTotalConversion()` off-chain and pass it through with an acceptable tolerance.

### Proof of Concept
1. User calls `incentiveDeposit(amount, convertRatio, false, 2)` on `ArbWomUp3`.
2. Internally, `toSwap = amount - amount/2` WOM is routed to `SmartWomConvert.convert(toSwap, convertRatio, 0, 0)`.
3. An attacker front-runs with a large WOM→mWom swap on the `womMWomPool`, worsening the exchange rate, then back-runs to restore the price after the victim's transaction executes.
4. Inside `_convertFor()`, `amountRec` from `IWombatRouter.swapExactTokensForTokens(..., 0, ...)` is much lower than fair value, but `convertAmount + amountRec < _minRec` never reverts because `_minRec == 0`.
5. Victim's transaction succeeds and they receive materially less `mWom` (locked into `mWomSV`) than expected, with the difference captured by the attacker. [3](#0-2)
