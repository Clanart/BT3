### Title
Sandwichable on-chain swap in `SmartWomConvert._convertFor`/`smartConvert` due to weak, self-referential minimum-output check - (File: `wombat/SmartWomConvert.sol`)

### Summary
`SmartWomConvert.smartConvert()` and the underlying `_convertFor()` route a portion of user WOM through an on-chain AMM swap (`IWombatRouter.swapExactTokensForTokens`) with a hard-coded `0` minimum output at the actual swap call site, relying instead on a post-hoc aggregate check against `_minRec`. In the `smartConvert` path, `_minRec` is auto-set to the full input amount (`_amountIn`), which is far below the fair market value the swap should produce, making the true slippage protection effectively worthless and the swap exploitable via sandwich attacks, mirroring the `harvest`/`getSwapOutput` bug class in the external report.

### Finding Description
`smartConvert()` decides how much WOM to route to a direct swap versus a 1:1 mint based on the current on-chain AMM ratio: [1](#0-0) 

It then calls `_convertFor` passing `_minRec = _amountIn`, i.e., the floor is only "you get back at least what you put in," not a fair-value-based minimum: [2](#0-1) 

Inside `_convertFor`, the actual swap sent to the router hard-codes `0` as `minAmountOut`, and the only protection is an aggregate check performed *after* the swap already executed: [3](#0-2) 

Because `smartConvert` is only triggered when the pool is skewed (`mWomToWom < buybackThreshold`, i.e., mWom is objectively cheaper than WOM), a fair swap should yield materially more than 1:1. However, since the enforced floor is only the 1:1 baseline (`_amountIn`), and the direct-mint portion (`convertAmount`) already contributes 1:1 toward that floor, the swap portion only needs to return roughly break-even to pass the check — leaving the entire "fair value premium" of the swap exposed to extraction. An attacker can sandwich the swap transaction (front-run to push the price down, let the victim's swap execute near the floor, back-run to capture the difference), stealing the yield that legitimate WOM depositors/harvesters were supposed to receive from the favorable convert ratio.

This is directly comparable to the reported `harvest()` issue: an on-chain quote/floor is used to gate a swap that any unprivileged wallet can trigger (directly via `smartConvert`, `convert`, or `convertFor`, or indirectly via `WombatStaking`'s reward-conversion flow, which the code comments confirm as intended caller: "should mainly used by wombat staking upon sending wom"). [4](#0-3) 

### Impact Explanation
Any WOM reward/deposit that flows through `smartConvert` (or `convert`/`convertFor` with a similarly loose `_minRec`) can have its "buyback" swap sandwiched, letting an attacker capture the value that should have accrued to depositors/reward claimants converting WOM to mWom. This is a theft of unclaimed/expected yield from an unprivileged, permissionless entry point, not merely a DoS.

### Likelihood Explanation
Medium: the swap only triggers when `mWomToWom < buybackThreshold` (a market condition that recurs naturally), and `smartConvert`/`convert`/`convertFor` are all callable by any wallet without special permissions, so the precondition for a profitable sandwich is common and detectable off-chain by watching mempool/ratio state.

### Recommendation
Do not derive the swap's real protection from a self-referential floor (`_minRec = _amountIn`). Either:
- Require the caller (or an authorized keeper) to supply a proper `_minRec` reflecting current fair-market value with a bounded slippage tolerance, and pass that same protection down to the actual router call (not just an aggregate post-check), or
- Restrict `smartConvert`'s auto-swap path to trusted/role-gated callers and use commit-reveal or TWAP-based pricing instead of spot on-chain quotes for setting minimum output.

### Proof of Concept
1. Monitor `WombatStaking`/user calls to `SmartWomConvert.smartConvert` (or `convert`/`convertFor`) where the pool is skewed (`mWomToWom < buybackThreshold`), triggering a non-trivial `buybackAmount` swap.
2. Front-run with a large WOM→mWom swap on the same Wombat pool used in `_convertFor` (`womMWomPool`) to worsen the exchange rate.
3. Let the victim's `_convertFor` swap execute; because `_minRec` only requires `convertAmount + amountRec >= _amountIn` (roughly break-even), the swap succeeds even at a degraded rate.
4. Back-run to restore the pool price and capture the extracted mWom/WOM value, which came out of the yield that should have gone to the depositor. [5](#0-4)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
