### Title
Division-by-zero panic in `consolidatedNode.Split` when a zero-stake proposer has a zero-balance consensus-liquidity pool - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split`, used to divide block rewards between a CN validator and its associated Prague-era Consensus Liquidity (CL) pool, divides by `totalAmount = cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount` with no zero-check. When the block proposer's CN staking amount and its CL pool's staking amount are both zero, this line panics, crashing every honest full/validator node that finalizes the block. This mirrors the reported bug class: an unchecked division whose divisor can legitimately become zero at a boundary condition (two equal/zero quantities), turning normal protocol operation into an unrecoverable failure.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- panics if totalAmount == 0
	...
}
```

`c.StakingAmount` is a validator's CN staking amount, which the codebase explicitly acknowledges can be zero for a qualified/proposing validator ("Note: validators can be qualified with zero stakes, if all are understaked" and the weighted-proposer test guarantees every validator, including zero-stake ones, at least one slot in the proposer list): [2](#0-1) 

`c.CLStakingInfo.CLStakingAmount` is derived by dividing the CL pool's native balance by `params.KAIA` and flooring to `uint64`, so any CL pool with a balance below 1 KAIA (e.g., a newly registered, unfunded pool) yields `CLStakingAmount == 0`: [3](#0-2) 

`Split` is invoked unconditionally on the block's proposer whenever `cn.CLStakingInfo != nil`, with no check that `cn.StakingAmount` (or the combined amount) is nonzero, in both the legacy and flex reward finalization paths: [4](#0-3) [5](#0-4) 

So if the elected block proposer is a validator whose CN staking amount is 0 and whose registered CL pool balance rounds down to 0, `totalAmount` is `big.NewInt(0)`, and `clAmount.Div(clAmount, totalAmount)` panics (`big.Int` division by zero is an unrecovered Go panic), crashing block finalization (`FinalizeState`) deterministically on every honest node that processes that block.

### Impact Explanation
This function runs during block reward finalization (`FinalizeState`), which every full node and validator executes for every block. A deterministic panic here halts block processing chain-wide rather than reverting a single transaction, since there is no transaction-level recovery around this code path in consensus/state processing. This is a consensus-liveness-breaking bug: once the vulnerable proposer/CL-pool combination is elected, the entire network fails to finalize that block, an availability impact on the order of a chain halt, materially worse than the "stuck account" impact described in the original report.

### Likelihood Explanation
Reaching this condition only requires normal, permitted staking/CL actions reachable via transactions:
1. A validator registers (or drains) its CN staking amount to zero via its `CnStaking` contract while remaining in the AddressBook/validator set (explicitly acknowledged as a supported state by the codebase's own tests/comments).
2. The same validator registers a CL pool in the CLRegistry (per KIP-226) that currently holds a balance under 1 KAIA (e.g., immediately after registration and before liquidity providers deposit).
3. The weighted-random proposer algorithm guarantees every qualified validator, including zero-stake ones, at least one slot in the proposer list, so this validator will eventually be selected as proposer.

No malicious node/peer behavior or privileged access is required; a legitimate staker/validator can reach this state through ordinary staking/CL registration transactions, making the precondition plausible under normal chain operation once the Prague/CL feature is enabled.

### Recommendation
In `consolidatedNode.Split` (kaiax/staking/staking_info.go), guard against `totalAmount.Sign() == 0` and return `(amount, big.NewInt(0))` (or an equivalent safe default) in that case, mirroring the "no split" branch already present when `CLStakingInfo == nil`. Additionally, consider requiring a minimum combined stake (CN + CL) before treating a validator as CL-eligible for reward-splitting purposes, consistent with the `minStake` checks already applied elsewhere (e.g., in `assignStakingRewards`/`assignStakingRewardsFlex`) but missing from `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`.

### Proof of Concept
1. Enable Prague hardfork (CL staking active).
2. Register a validator `V` in the AddressBook with `StakingAmount = 0` (fully withdrawn but still registered/qualified — as acknowledged possible by `TestWeightedRandomProposer_ListWeighted`'s "zero stakes" case).
3. Register a CL pool for `V` in the CLRegistry with a balance below `1 KAIA` (e.g., freshly deployed pool with no deposits yet), so `parseCallResult`/`parsePermissionlessCallResult` compute `CLStakingAmount = 0` (kaiax/staking/impl/getter.go:296-301).
4. Wait until the weighted-random proposer selection elects `V` as the block proposer (guaranteed at least one slot, per KIP-226/weighted proposer logic).
5. When the block is finalized, `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` → `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` → `cn.Split(proposer)` is invoked with `cn.StakingAmount = 0` and `cn.CLStakingInfo.CLStakingAmount = 0`, causing `totalAmount = big.NewInt(0)` and a division-by-zero panic in `clAmount.Div(clAmount, totalAmount)`, crashing every node that finalizes this block.
