### Title
Rule engine silently fails to match `old_text`/`old_string` conditions on `MultiEdit` tool calls, allowing block rules to be bypassed - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` implements per-tool branches to pull field values out of `tool_input`, but for the `MultiEdit` tool it only supports `file_path`, `new_text`, and `content` — it has no branch for `old_text`/`old_string`. Any block rule written against `old_text`/`old_string` (a documented, valid field per the function's own docstring) will never match when the identical edit is performed via `MultiEdit` instead of `Edit`, silently disabling the protection.

### Finding Description
`RuleEngine.evaluate_rules` → `_rule_matches` → `_check_condition` → `_extract_field` is the exact call chain used by `PreToolUse enforcement` (`plugins/hookify/hooks/pretooluse.py`) for every tool invocation [1](#0-0) .

Inside `_extract_field`, tool-specific handling diverges between `Edit`/`Write` and `MultiEdit`:

```
elif tool_name in ['Write', 'Edit']:
    ...
    elif field == 'old_text' or field == 'old_string':
        return tool_input.get('old_string', '')
    elif field == 'file_path':
        return tool_input.get('file_path', '')

elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
``` [2](#0-1) 

The `MultiEdit` branch never returns a value for `field == 'old_text'` or `field == 'old_string'`, so execution falls through to `return None` [3](#0-2) . Back in `_check_condition`, a `None` field value causes an immediate `return False` regardless of the configured operator/pattern [4](#0-3) , and since `_rule_matches` requires *all* conditions to match, the whole rule silently fails to match [5](#0-4) .

Consider a block rule such as:
```
---
name: protect-auth-check
event: file
tool_matcher: "Edit|Write|MultiEdit"
action: block
conditions:
  - field: old_text, operator: contains, pattern: "verify_signature("
---
Do not remove signature verification!
```
If Claude (driven by ordinary content in the repo, an issue/PR, or prompt injection reachable through normal automation) edits a file with the `Edit` tool and an `old_string` containing `verify_signature(`, the rule correctly fires and the operation is denied. But if the exact same file mutation is performed with the `MultiEdit` tool (which Claude routinely uses interchangeably with `Edit`, and which is explicitly covered by the rule's `tool_matcher`), `_extract_field` returns `None` for `old_text`, the condition fails, and the block rule never fires — the dangerous edit is silently allowed even though the `tool_matcher` explicitly listed `MultiEdit` as a protected tool. The tool-matcher check passes, but the field-extraction layer treats `MultiEdit` as a different, incompletely-supported representation of the same "edit" operation, breaking the invariant that a matching block rule reliably denies the protected operation.

### Impact Explanation
This is a Security-control bypass: a rule author (or a default/shipped hookify rule) that intends to block dangerous file edits based on removed/changed content (`old_text`/`old_string`) is silently ineffective whenever the edit is carried out via `MultiEdit` rather than `Edit`/`Write`. Since Claude Code chooses which tool to use for a given edit and can be influenced by adversarial repository content (prompt injection in files, issues, PRs, etc.), this allows a dangerous operation (e.g., stripping a security check, a permission gate, or a validation call) to bypass the intended PreToolUse block, defeating the review/permission boundary the rule was meant to enforce, without any error or warning being shown to the user.

### Likelihood Explanation
No special privileges are required beyond normal Claude Code usage with hookify rules enabled: the only precondition is that a block rule references `old_text`/`old_string` and is expected to also protect `MultiEdit`. Because `MultiEdit` is a common, everyday tool Claude uses for multi-location edits, this bypass is easily and repeatably triggered — deliberately or as a side effect of normal agent behavior — every time an equivalent edit is expressed through `MultiEdit` instead of `Edit`/`Write`.

### Recommendation
Add `old_text`/`old_string` extraction support to the `MultiEdit` branch of `_extract_field`, mirroring the `new_text`/`content` handling (e.g., concatenate `e.get('old_string', '')` across `tool_input.get('edits', [])`). More generally, audit `_extract_field` so every field documented as valid (`command`, `new_text`/`new_string`, `old_text`/`old_string`, `content`, `file_path`) is consistently supported across all tools included in the corresponding `event`/`tool_matcher` categories (`Edit`, `Write`, `MultiEdit`), rather than being hand-maintained per tool with silent `None` fallthrough.

### Proof of Concept
Unit test to add to (or alongside) `plugins/hookify/core/rule_engine.py`'s test harness:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="protect-auth-check",
    enabled=True,
    event="file",
    tool_matcher="Edit|Write|MultiEdit",
    action="block",
    conditions=[Condition(field="old_text", operator="contains", pattern="verify_signature(")],
    message="Do not remove signature verification!"
)
engine = RuleEngine()

# Edit tool: rule correctly blocks
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "auth.py", "old_string": "verify_signature(token)", "new_string": "pass"}
}
result_edit = engine.evaluate_rules([rule], edit_input)
assert result_edit.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# MultiEdit tool, same semantic edit: rule silently fails to match (BUG)
multiedit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "MultiEdit",
    "tool_input": {
        "file_path": "auth.py",
        "edits": [{"old_string": "verify_signature(token)", "new_string": "pass"}]
    }
}
result_multiedit = engine.evaluate_rules([rule], multiedit_input)
# Expected (fixed): same deny as Edit
# Actual (current bug): result_multiedit == {} -- operation is allowed
assert result_multiedit == {}, "demonstrates bypass: MultiEdit not blocked despite matching tool_matcher"
```
This demonstrates that identical dangerous content changes are blocked via `Edit` but pass through unblocked via `MultiEdit`, confirming the tool-matching/field-extraction inconsistency in `RuleEngine._extract_field`.
