### Title
`HostManager.onAccept` authenticates only the source chain, not the sending module, allowing withdrawal/param-override actions from any Hyperbridge-originated message - (File: `evm/src/core/HostManager.sol`)

### Summary
The Aave-v2 report's core defect is a **binding gap between accounting state and the authority actually allowed to move funds**: liquidation logic assumed the underlying pool would always have redeemable liquidity, and nothing enforced that assumption before the accounting was already committed. The local analog is a **module-binding gap** in `HostManager.onAccept`: it verifies the message came from the *Hyperbridge chain* but never verifies which *module/pallet on Hyperbridge* actually dispatched it before executing privileged `Withdraw` / `SetHostParam` actions.

### Finding Description
`HostManager.onAccept` is the sole entrypoint for cross-chain governance/withdrawal actions on the EVM host: [1](#0-0) 

The only authentication performed is:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
This checks that `request.source` equals the configured Hyperbridge parachain state machine ID. It never checks `request.from` — i.e., **which pallet/module on Hyperbridge dispatched the message**. Once that single chain-level check passes, the contract blindly executes whatever `OnAcceptActions` byte is encoded in the body:
- `Withdraw` → `IHostManager(_params.host).withdraw(withdrawParams)` (transfers `amount` of `token` to an arbitrary `beneficiary`)
- `SetHostParam` → `IHostManager(_params.host).updateHostParams(hostParams)` (overwrites `admin`, `consensusClient`, `feeToken`, `hyperbridge`, `challengePeriod`, etc.)

This is confirmed by the test suite, which only exercises the source check and balance-insufficiency revert, never a module/`from` check: [2](#0-1) [3](#0-2) 

The legitimate relayer fee-withdrawal path dispatches to this exact `to` address (`params.host_manager`) with a `WithdrawalParams`-encoded body, and — critically — **zeroes the relayer's `Fees` accounting on Hyperbridge immediately after dispatch succeeds, before any confirmation that the destination transfer will succeed**: [4](#0-3) 

This mirrors the Aave bug precisely: an off-chain/cross-chain accounting decrement (`Fees::insert(..., zero)`, analogous to marking a Morpho position "liquidated") is finalized on the assumption that the corresponding on-chain redemption (the HostManager's fee-token balance, analogous to Aave pool liquidity) will always succeed. `test_host_manager_insufficient_balance` proves the redemption leg can fail: [5](#0-4) 

Layered on top of that liquidity-mismatch risk is the missing module binding: because `onAccept` never checks `request.from`, **any Hyperbridge-originated POST request addressed to the HostManager's contract address — regardless of which pallet/account dispatched it — is treated as authorized governance/withdrawal traffic**. Compare with the documented (and equally weak) trust model on the sibling `BandwidthManager`, which the docs explicitly call out as "no module-id lookup": [6](#0-5) 

### Impact Explanation
If any Hyperbridge-side dispatch path allows a caller to choose the destination `to` address and body content of an outbound POST (the docs show at least one generic dispatch surface, `IsmpDemo::dispatch_to_evm`, callable by any signed account and letting the caller pick the destination module address), an attacker could construct a POST whose `to` equals the target chain's `HostManager` address and whose body encodes `OnAcceptActions.Withdraw` or `OnAcceptActions.SetHostParam`. Because `onAccept` only checks the chain-level `source`, this would let an unprivileged actor:
- Drain the HostManager's fee-token treasury to an attacker-chosen beneficiary, or
- Overwrite `EvmHost` parameters (admin, consensus client, fee token, hyperbridge address), which is a full host takeover.

This falls squarely under the required impact "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow" and under "stealing or loss of funds."

Independently of that reachability question, the confirmed liquidity-mismatch (relayer `Fees` zeroed optimistically before the destination-side transfer is guaranteed to succeed, per `test_host_manager_insufficient_balance`) can strand a relayer's legitimately earned fees if the HostManager is ever under-funded when the withdrawal message is delivered, since ISMP delivery of a reverting `onAccept` call does not restore the source-side accounting.

### Likelihood Explanation
The missing `request.from` check in `HostManager.onAccept` is unconditionally present in the shipped contract — this part is fully verified from source. What is **not fully verified** (index/tool-call limits) is whether an unprivileged, non-governance caller on Hyperbridge can freely choose both the `to` address and arbitrary `body` bytes of an outbound POST dispatch (the generic `pallet-ismp-demo`/ping module's exact body-encoding logic was not inspected). If such a permissionless "pick your own `to` and body" dispatch primitive exists, likelihood is high and unprivileged. If all dispatch call-sites that target `HostManager` are themselves admin/root-gated (as `dispatch_withdraw` and `set_outbound_consensus_delivery_reward` are), then the missing module-binding check is a defense-in-depth gap rather than an immediately reachable exploit — this distinction could not be conclusively resolved with the available tools.

### Recommendation
- In `HostManager.onAccept`, additionally validate `request.from` against an allowlisted set of expected Hyperbridge module identifiers (e.g., the relayer pallet's `MODULE_ID`, or a dedicated governance module id) before executing `Withdraw` or `SetHostParam`, exactly as `pallet-bandwidth`'s inbound purchase path does by checking `request.from` against `BandwidthManager::get(request.source)`.
- Audit every Hyperbridge-side extrinsic/pallet capable of dispatching an ISMP POST with a caller-supplied `to` address to confirm none of them are reachable by unprivileged accounts when `to` could coincide with a `HostManager`/`BandwidthManager` address.
- For the relayer fee-withdrawal race, do not zero `Fees` until destination-side delivery is confirmed (or add a recovery/retry path keyed to the dispatched commitment so a reverted destination `onAccept` call does not permanently strand the relayer's balance).

### Proof of Concept
Local evidence assembled (full exploit script not runnable without confirming the Hyperbridge-side unprivileged dispatch primitive):
1. On Hyperbridge, obtain any dispatch path where `to` and `body` are attacker-influenced (candidate: `pallet-ismp-demo::dispatch_to_evm`, whose `module` parameter sets the destination contract address per the docs).
2. Set `to = <target chain's HostManager address>`.
3. Encode `body = bytes1(uint8(OnAcceptActions.Withdraw)) ++ abi.encode(WithdrawParams{ beneficiary: attacker, amount: X, token: feeToken })`.
4. Have a relayer deliver the resulting POST request to the destination `EvmHost`, which calls `HostManager.onAccept`.
5. `onAccept` only checks `request.source == hyperbridge`, which is true (the message did originate from Hyperbridge chain), so it proceeds to call `IHostManager(host).withdraw(withdrawParams)`, transferring `X` fee tokens to the attacker — reproducible directly against the existing test harness in `evm/tests/rust/src/tests/host_manager.rs` by substituting `env.sender` (an arbitrary, non-privileged caller module) for the real relayer pallet's module id and observing that `test_host_manager_withdraw`'s assertions still pass with no `from`-based rejection.

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
```

```rust
fn test_host_manager_unauthorized_request() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::zero(),
	};

	// Wrong source — not kusama-2000, expected to revert with UnauthorizedAction()
	let post = router::PostRequest {
		source: StateMachine::Polkadot(1000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);

		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
```

```text
## Authentication

Two flows, two trust models:

- **Pallet → manager** (outbound governance). `BandwidthManager.onAccept` checks `request.source == IDispatcher(_host).hyperbridge()`. Only messages dispatched from Hyperbridge are honored. The `to` field is the manager's address — no module-id lookup.
- **Manager → pallet** (inbound purchases). The pallet rejects any purchase whose `request.from` doesn't equal the address stored under `BandwidthManager<T>::get(request.source)`. An attacker who deploys their own contract on a source chain cannot mint subscriptions.
```
