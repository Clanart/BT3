## Analysis

The Notional bug's core flaw was two code paths computing what should be the *same* value (accumulated votes for a block) using inconsistent logic — one path silently omitted a component the other included, and a discrepancy in that computation could flip the outcome of a vote. The GitHub Desktop analog with the same broken-invariant shape is the AI conflict-resolution feature, where **two independent parsers scan the identical raw file text for conflict-marker blocks using non-identical logic**, and the results of one parser (hunk count/boundaries) are blindly assumed to align with the other when splicing AI-generated resolutions back into the file by array index.

### Title
Divergent conflict-marker parsing between `extractConflictHunks` and `reassembleResolvedFile` silently drops or misplaces resolved content when writing Copilot's conflict resolution to disk - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
Desktop's Copilot-assisted merge/rebase/cherry-pick conflict resolution feature extracts conflict hunks from a conflicted file using `extractConflictHunks` [1](#0-0)  to build the prompt sent to the model, and later independently re-scans the *same* raw content with `reassembleResolvedFile` [2](#0-1)  to splice the model's per-hunk resolutions back into the file, matched purely by array order (`hunkIndex`). These two scanners handle malformed/ambiguous marker sequences differently, so they can disagree on how many hunks exist and where they start/end. When they disagree, resolutions get spliced into the wrong hunk, or a real conflict block is deleted outright with no replacement and no error, and the corrupted file is then staged and committed automatically.

### Finding Description
`extractConflictHunks` treats an "ours" section as unterminated unless it hits a base marker (`|||||||`) or separator (`=======`) — it does **not** check for the closing marker (`>>>>>>>`) while collecting "ours" content [3](#0-2) . If a `>>>>>>>`-looking line appears before any `=======`/`|||||||`, the ours-collection loop keeps consuming lines all the way to EOF looking for a separator that never comes, so `hunkEnd` is never set, and the malformed hunk (and everything absorbed into it) is discarded via `continue` [4](#0-3) . Any real, well-formed conflict block that happened to occur *after* this point in the file is swallowed into the abandoned "theirs" collection and never produced as a hunk — silently reducing the hunk count returned to the caller.

`reassembleResolvedFile`, scanning the identical text independently, handles the same malformed sequence differently: when it can't find a separator before the file ends (`!hasSeparator || closingIndex === -1`), it treats only the single `<<<<<<<` line as ordinary content and advances one line at a time [5](#0-4) , rather than consuming to EOF. It therefore continues to find and correctly recognize legitimate, well-formed conflict marker blocks that appear later in the file — blocks that `extractConflictHunks` already discarded and never sent to the model.

The two functions are never reconciled: `reassembleResolvedFile` blindly assumes the `hunkIndex`-th marker block it finds corresponds to `hunkResolutions[hunkIndex]`, i.e. the `i`-th entry produced by `extractConflictHunks`/the model [6](#0-5) . When the counts diverge, remaining marker blocks in the file are still fully consumed (`i = closingIndex + 1`) but, once `hunkIndex >= hunkResolutions.length`, nothing is pushed to replace them [6](#0-5)  — the block (both "ours" and "theirs" code) is deleted from the output with no warning.

This exactly mirrors the report's broken invariant: the "authoritative" computation (`extractConflictHunks`, which drives what the model even sees) and the "consuming" computation (`reassembleResolvedFile`, which decides what actually lands on disk) are supposed to agree on the same underlying value (the ordered list of conflict hunks) but use inconsistent logic for edge cases, and nothing cross-checks that they agree before the result is trusted.

### Impact Explanation
The attacker primitive is a cloned/fetched repository (or any branch/commit an unsuspecting user merges, rebases onto, or cherry-picks) that contains ordinary file content resembling a git conflict marker (e.g. a documentation file, patch/diff sample, or fixture containing a line of 7+ `<` or `>` characters) positioned near a real conflicting region. When the user invokes "Resolve with Copilot" [7](#0-6) , the two parsers can disagree on hunk boundaries/count, causing `applyCopilotConflictResolutions` to write a file to disk that silently omits or misplaces real code from either side of the merge [8](#0-7) . The corrupted content is then `git add`ed and, on "Continue", committed and potentially pushed — this is exactly the "silent corruption of what the user commits or pushes" impact category, requiring no local/physical access, no admin rights, and no prior malware — only that the user resolve a conflict against attacker-influenced content using the AI feature.

### Likelihood Explanation
This requires the AI conflict-resolution feature to be used (opt-in, gated behind an account and a disclaimer [9](#0-8) ), and requires attacker-influenced file content that happens to contain a conflict-marker-like line near a real conflict — plausible in documentation, patch/diff samples, generated fixtures, or files about git itself, but not guaranteed to occur in every repository. Because the divergence depends on specific malformed-marker edge cases in both parsers, it is not trivially triggered by every conflict, but it is fully reachable with ordinary crafted file content and no exploitation of memory-safety or sandbox primitives.

### Recommendation
Make `reassembleResolvedFile` reuse the exact same hunk boundaries that `extractConflictHunks` computed (e.g., pass the extracted `IConflictHunk` list, or byte offsets, from context-gathering time to reassembly, instead of independently re-scanning the raw text with different tolerance for malformed markers). At minimum, assert that the number of marker blocks found during reassembly equals `hunkResolutions.length` for that file, and fail closed (skip the file, surface an error) rather than silently deleting or misapplying content when the counts disagree.

### Proof of Concept
1. Create a repository containing a Markdown/documentation file, `docs/git-tips.md`, with ordinary example text that includes a line of literal `<<<<<<< example` (illustrating git conflict syntax) that is *not* part of any real conflict, followed later in the same file by a genuine merge conflict region (`<<<<<<< HEAD` / `=======` / `>>>>>>> feature`) introduced by a normal merge.
2. Trigger a real merge/rebase that leaves `docs/git-tips.md` conflicted (git inserts the real markers around the genuinely conflicting lines) while the earlier illustrative `<<<<<<< example` text remains untouched above it.
3. In Desktop, open the conflicts dialog and click "Resolve with Copilot". `buildConflictContext` → `extractConflictHunks` scans the file, hits the illustrative `<<<<<<< example` line first, fails to find a `=======`/`>>>>>>>` before EOF is reached inside its ours/theirs collection loops (per `app/src/lib/copilot-conflict-context.ts:200-242`), consumes the remainder of the file including the real conflict block, and discards the malformed hunk — reporting the file as `skippedReason: 'No conflict markers found'` or with fewer hunks than actually exist.
4. If instead the illustrative marker is arranged so at least one closing `>>>>>>>`-looking line exists later (e.g. from the real conflict), `extractConflictHunks` emits a reduced/garbled hunk count while `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:559-591`), scanning the same raw text independently, finds the real conflict block correctly on its own line-by-line walk.
5. When `applyCopilotConflictResolutions` writes the reassembled content back to disk (`app/src/lib/stores/app-store.ts:7233-7259`), the mismatch between the model's resolution array length and the number of marker blocks `reassembleResolvedFile` finds causes the real conflicting code to be dropped or a wrong resolution spliced in — with no error shown, `git add` is run, and the corrupted file is ready to commit.

**Uncertainty note:** I was not able to execute this scenario end-to-end (no test harness available in this session) to confirm the exact character sequence that triggers divergence deterministically; the analysis is based on static reading of the two parsers' control flow. A background Devin session with repo/terminal access could construct a concrete fixture file and unit test (extending `app/test/unit/copilot-conflict-context-test.ts` and `app/test/unit/copilot-conflict-resolution-test.ts`) to confirm the hunk-count mismatch and resulting data loss empirically.
