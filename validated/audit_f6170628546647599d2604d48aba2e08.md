### Title
Governance `update_token` removal of a chain deletes the `ContractToAsset` mapping that `on_timeout` needs, permanently trapping escrowed/burned user funds - (`modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
The C4 finding shows that removing a whitelisted backing entry (`usdc2`) from `asdUSDC` strands liabilities that depended on it, since the withdraw path hard-requires the removed entry to still be present. The local analog is `pallet-hyper-fungible-token`: an in-flight cross-chain transfer's refund path (`on_timeout`) depends on the very same `ContractToAsset`/`Precisions` mappings that governance can delete via `update_token`'s `remove_chains`, with no fallback. If those mappings are removed while a user's transfer to that chain is still pending, the timeout refund can never resolve and the user's escrowed/burned principal is permanently lost.

### Finding Description
`Pallet::send` (`modules/pallets/hyper-fungible-token/src/lib.rs:241-325`) escrows (native custody) or burns (mint/burn model) the caller's tokens into `Self::pallet_account()` and dispatches a `DispatchPost` with a user-controlled `timeout` to `TokenContracts[dest][asset_id]`.

If the request times out, ISMP invokes `on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:218-296`), which:
```
let local_asset_id = ContractToAsset::<T>::get(dest, &to)
    .ok_or(HftError::UnknownContractOnTimeout)?;
...
let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
    .ok_or(HftError::DecimalsNotConfigured(dest))?;
``` [1](#0-0) 

Both lookups are required to compute the refund amount and beneficiary before releasing the escrow back via `NativeCurrency::transfer`/`Assets::transfer`/`Assets::mint_into`.

`update_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:384-433`), callable by `CreateOrigin` as routine token/chain maintenance (e.g. redeploying a contract at a new address, deprecating a chain), unconditionally deletes these same entries for any chain in `remove_chains`:
```
for chain in update.remove_chains {
    if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone()) {
        ContractToAsset::<T>::remove(chain, old_contract);
    }
    TokenContracts::<T>::remove(chain, update.asset_id.clone());
    Precisions::<T>::remove(update.asset_id.clone(), chain);
}
``` [2](#0-1) 

There is no check for outstanding/in-flight requests still bound to the chain/contract pair being removed. Because `params.timeout` in `send` is fully attacker/user-controlled (`modules/pallets/hyper-fungible-token/src/lib.rs:241-310`), an ordinary transfer can be dispatched with a timeout that elapses after a routine governance `update_token` call removes that destination chain's mapping. When the timeout fires, `on_timeout` hits `ContractToAsset::<T>::get(dest, &to)` → `None` → `Err(HftError::UnknownContractOnTimeout)`, so the refund transfer/mint-back never executes. The escrowed/burned principal sitting in `Self::pallet_account()` (or already destroyed via `burn_from` for the mint/burn model) has no other recovery path in this pallet.

This mirrors the report's broken invariant exactly: a shared/backing registration (`whitelistedUSDCVersions` ↔ `ContractToAsset`/`Precisions`) is removed by routine, non-malicious governance action while value that depends on it (`usdcBalances`/escrowed principal) is still outstanding, and the guard meant to protect correctness (`require(whitelisted...)` / `ContractToAsset::get(...).ok_or(...)`) instead becomes the mechanism that locks/loses funds once the mapping is gone.

### Impact Explanation
This is a real fund-loss/lock bug reachable via normal production operation, not a malicious-admin scenario: `update_token` is a legitimate, expected maintenance call (e.g., migrating a token's EVM contract to a new address, or removing a decommissioned chain), and users routinely have in-flight transfers with nonzero timeouts at any given moment. Any user whose transfer to the affected chain is in flight when the removal lands, and whose message subsequently times out, has their escrowed or burned principal permanently stranded with no on-chain recovery mechanism in the pallet. This satisfies "stealing or loss of funds" / "logic attacks" under the bounty's impact gate, since it results in unconditional, unrecoverable loss of user principal through a standard bridging code path.

### Likelihood Explanation
Likelihood is moderate-to-high in active production use: `update_token` is documented as ordinary chain/contract maintenance (`modules/pallets/hyper-fungible-token/README.md:53`), and any window between a `send()` with a live timeout and a maintenance-driven `remove_chains` call is sufficient to trigger the bug — no coordination or malicious behavior by governance is required, only the routine act of updating token configuration while messages are in flight.

### Recommendation
- Do not delete `ContractToAsset`/`Precisions` entries for a chain in `update_token::remove_chains` while any dispatched-but-unresolved request against that `(chain, contract)` pair may still time out; instead, retain the old contract's `ContractToAsset`/`Precisions` mapping (perhaps in a deprecated/frozen state that is only usable by `on_timeout`) until in-flight requests referencing it are guaranteed resolved, or
- Change `on_timeout` to fall back to data embedded in the original request body/commitment (rather than requiring current governance-mutable storage) so refunds do not depend on mappings that can be revoked after dispatch, and
- Add an explicit escape hatch (e.g., a governance-only rescue function) allowing recovery of stuck `pallet_account()` balances tied to orphaned `(chain, contract)` pairs.

### Proof of Concept
1. Governance registers asset `X` for `StateMachine::Evm(A)` via `register_token`, setting `TokenContracts[A][X] = contract_v1`, `ContractToAsset[A][contract_v1] = X`, `Precisions[X][A] = d`.
2. User calls `send(asset_id = X, destination = A, timeout = T)`. Their native asset is escrowed into `Pallet::pallet_account()` (or burned for non-native/mint-burn assets) per `modules/pallets/hyper-fungible-token/src/lib.rs:257-290`, and a `DispatchPost` with `timeout = T` is sent.
3. Before the request is delivered/times out, governance calls `update_token` with `remove_chains = [A]` for asset `X` (e.g. as part of migrating to `contract_v2`), which executes `modules/pallets/hyper-fungible-token/src/lib.rs:423-430`, deleting `ContractToAsset[A][contract_v1]` and `Precisions[X][A]`.
4. The request never reaches its destination (or is otherwise rejected) and times out after `T`. `pallet_ismp` invokes `Pallet::on_timeout` (`modules/pallets/hyper-fungible-token/src/module.rs:218`), which calls `ContractToAsset::<T>::get(A, &contract_v1)` → returns `None` → `Err(HftError::UnknownContractOnTimeout)`.
5. The refund transfer/mint-back to the original sender never executes; the user's principal remains locked in `Pallet::pallet_account()` (custody model) or is permanently destroyed with no compensating mint (burn model), with no further retry path exposed by the pallet.
