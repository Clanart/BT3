### Title
Unvalidated `Participant` indexes in PedPoP blame evaluation panic on attacker-supplied indices - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to the JSSE advisory (unauthenticated remote input causing a partial denial of service), Serai's PedPoP DKG exposes publicly reachable APIs that perform unchecked `HashMap` indexing with attacker-controlled `Participant` values. `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender` and `recipient` as `Participant` and index `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without validating membership, panicking on any out-of-range index and crashing the calling validator.

### Finding Description
`blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which indexes `self.enc_keys[&decryptor]` — a `HashMap` only populated for the participants registered at `Decryption::new`/`register` (in `AdditionalBlameMachine::new`, exactly `1 ..= n`) [1](#0-0) . `Participant::new` accepts any nonzero `u16`, so a value like `n + 1` is a valid `Participant` but absent from the map, and `HashMap`'s `Index` impl panics on a missing key [2](#0-1) . Similarly, `blame_internal` later indexes `self.commitments[&sender]`, panicking for any `sender` not among the commitment senders [3](#0-2) . Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` bounds-check either argument before these lookups [4](#0-3) .

### Impact Explanation
An accusation carrying a participant index outside `1 ..= n` causes an unconditional panic inside `decrypt_with_proof`/`blame_internal` rather than a clean blame result. In an integrating validator/processor, a single crafted blame message aborts key-gen / share handling (a partial denial of service), matching the CVE's profile: unauthenticated network-reachable input → availability impact only. Unlike the malformed-share paths, which return `PedPoPError::InvalidShare`/`DecryptionError` gracefully, this path provides no error handling.

### Likelihood Explanation
The inputs `sender`/`recipient`/`accused` originate from blame/accusation messages authored by other protocol participants, i.e. untrusted public data, and are forwarded verbatim into `blame` (e.g., the processor's `VerifyBlame` handler passes `accuser`/`accused` straight through) [5](#0-4) . No caller-side validation of these indices is enforced by the API contract (the only documented precondition is message authenticity, not index membership) [6](#0-5) . Triggering requires only sending an accusation referencing a non-existent participant index.

### Recommendation
In `Decryption::decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or treat an unregistered decryptor as accuser-fault). In `blame_internal`, use `self.commitments.get(&sender)` and return a defined result when the sender wasn't a participant. Alternatively, validate `sender`/`recipient` against `params`/`included` at the top of `blame`/`AdditionalBlameMachine::blame` and return the accusing party as faulty.

### Proof of Concept
```rust
// With n participants, construct an AdditionalBlameMachine from valid
// commitment messages for participants 1..=n:
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Then submit a blame statement where `recipient` (or `sender`) is an
// index that was never registered, e.g. n + 1:
let malicious_recipient = Participant::new(n + 1).unwrap(); // valid nonzero Participant
machine.blame(sender, malicious_recipient, msg, proof);
// -> decrypt_with_proof indexes self.enc_keys[&malicious_recipient]
//    -> HashMap Index on absent key -> panic! (crash/abort of the caller)
```
Equivalently, passing `sender = Participant::new(n + 1)` reaches `self.commitments[&sender]` in `blame_internal` and panics the same way [7](#0-6) .
