### Title
Uncontrolled resource consumption via quadratic Lagrange interpolation in `ThresholdKeys::read` / `ThresholdKeys::new` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t`, `n`, and `i` parameters (each a `u16`, so up to 65,535) and then calls `ThresholdKeys::new`, which computes `group_key` by evaluating a Lagrange `interpolation_factor` for every participant `1..=t`. Each `interpolation_factor` call is O(t) field multiplications plus one field inversion, making `ThresholdKeys::new` O(t²) multiplications plus t inversions. A ~2 MB crafted blob (65,535 encoded points) therefore forces billions of field operations and tens of thousands of inversions — severe CPU exhaustion triggered by a single untrusted input, directly analogous to CVE-2017-5637's CPU-intensive command reachable by unauthenticated parties.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i` from the byte stream and reads `n` verification shares, then calls `ThresholdKeys::new` [1](#0-0) .

`ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` for all `t` participants [2](#0-1) .

`Interpolation::Lagrange::interpolation_factor` iterates over the entire `included` set (length `t`), performing O(t) field multiplications and one `denom.invert()` per call [3](#0-2) .

`ThresholdParams::new` only enforces `t <= n <= u16::MAX` and `i <= n`; there is no practical cap on the participant count, so an attacker can legally claim `t = n = 65535` [4](#0-3) .

The same quadratic blowup also exists in `ThresholdKeys::view`, which calls `interpolation_factor` once per included signer plus per verification share [5](#0-4) , but `read`/`new` is the cleanest single-call trigger.

### Impact Explanation
Feeding ~2 MB of attacker bytes encoding `t = n = 65535` into `ThresholdKeys::read` forces ~65,535 field inversions and ~4.3 billion field multiplications inside `ThresholdKeys::new` before any validity of the key material is established. Any service that deserializes `ThresholdKeys` (or PedPoP `Commitments`/`EncryptedMessage` flows that construct `ThresholdKeys`, e.g. `KeyMachine::calculate_share` → `ThresholdKeys::new` at crypto/dkg/pedpop/src/lib.rs:528) from untrusted input can be driven to consume CPU per request, denying service to legitimate signing/verification requests — matching the CWE-400 class of the ZooKeeper `wchp/wchc` advisory.

### Likelihood Explanation
High. The bug requires no privileges, no valid cryptographic material, and no race: the points don't need to be valid shares, only decodable `read_G` encodings. Any exposed deserialization path of `ThresholdKeys` (key import, DKG result reconstruction, DB/peer-fed bytes) is a trigger.

### Recommendation
- Reject absurd thresholds early: cap `n`/`t` at a protocol-realistic maximum (e.g. the validator-set size, on the order of hundreds) inside `ThresholdParams::new` or `ThresholdKeys::read` before any interpolation work.
- Compute Lagrange coefficients in O(t) total (precompute the full numerator product and per-participant denominator with a single batched inversion, e.g. Montgomery batch inversion), rather than O(t) inversions and O(t²) multiplications.
- Alternatively, derive `group_key` directly from `verification_shares[1..=t]` only when needed, and lazily — so deserialization cost stays linear in input size.
