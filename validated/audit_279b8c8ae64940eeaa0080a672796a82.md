## Finding

### Title
Missing zero-value validation on `Kip71GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
The Kaia governance parameter `kip71.gastarget` is registered with a `noopFormatChecker`, meaning it accepts any `uint64` value including `0`, unlike its sibling parameter `kip71.basefeedenominator` which explicitly rejects zero. A `gasTarget` of `0` reaches `KIP71Config.NextMagmaBlockBaseFee`, where it is used as a divisor without a zero-guard, causing a division-by-zero panic in Go's `big.Int.Div`.

### Finding Description
In the governance parameter registry, `Kip71GasTarget` is defined with a no-op format checker that performs no validation at all: [1](#0-0) 

By contrast, the closely related `Kip71BaseFeeDenominator` parameter explicitly guards against a zero value: [2](#0-1) 

This missing check means `kip71.gastarget` can be ratified to `0` through ordinary Kaia governance (via `governance_vote` in header governance, or via the `GovParam` contract in contract governance), which only requires being the recognized governing node/council member — no protocol-level guard rejects the value before it becomes an effective `ParamSet.GasTarget`.

The parameter then flows into `KIP71Config.NextMagmaBlockBaseFee`, the consensus-critical base fee calculation function that every node runs to validate and build blocks (KIP-71/Magma base fee rule): [3](#0-2) 

When `parentGasUsed > gasTarget` (true for any nonzero gas usage once `gasTarget == 0`), the code computes:
```go
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
```
Dividing by zero with `math/big.Int.Div` panics at runtime. This function is called on every block by all Kaia nodes (header validation, block production, gas price estimation, tx pool checks), as shown by its multiple call sites: [4](#0-3) [5](#0-4) 

### Impact Explanation
A panic in `NextMagmaBlockBaseFee` during header verification or block assembly would crash every full node and validator processing that block, effectively halting the Kaia chain network-wide — a total denial of service. This is a direct analog of the reported bug class (missing zero/bounds check on a numeric input enabling DoS), but here the blast radius is the entire chain rather than a single contract.

### Likelihood Explanation
Low to Medium: it requires a governance vote (single-mode governing node, or council majority in none-mode, or an on-chain `GovParam.setParamIn` call) to set `kip71.gastarget` to `0`, either through operator error or malicious governance action. Unlike a normal user transaction, this needs governance-level access, but no additional validation anywhere in the pipeline (vote casting, header verification, or contract-governance ingestion) rejects the unsafe value before it takes effect and is consumed by all nodes.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0`, mirroring the existing check on `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` before using `gasTarget` as a divisor, so that even a misconfigured genesis/chain config cannot trigger a panic.

### Proof of Concept
1. A governing node (or governance quorum) casts `governance_vote("kip71.gastarget", 0)`.
2. Because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, the vote passes `checkConsistency`/format validation and is ratified at the next epoch boundary.
3. Once effective, any block header with `parentGasUsed > 0` triggers `NextMagmaBlockBaseFee` to execute `x.Div(x, big.NewInt(0))`, panicking on every node that verifies or produces the next block (`BlockValidator.ValidateHeader`, `worker.go` block assembly, tx pool gas price checks), halting the network.
