### Title
Working directory row-index → file mapping can toggle/select the wrong file after a background status refresh reorders the list, silently changing what gets committed - (File: `app/src/ui/changes/sidebar.tsx`)

### Summary
The External Report's broken invariant is: a stable, ordered list is referenced by *position* by the client, but the app is allowed to silently reorder that list between the time the client "locked in" a position and the time the position is consumed, producing an operation on the wrong element with no integrity check. In `angle-transmuter` this was `ts.collateralList` reordered by `revokeCollateral` while `Redeemer.redeem` still trusted positional `minAmountsOut`.

The same shape exists in GitHub Desktop's Changes list. The working directory file array (`state.workingDirectory.files`) is not stable in index terms — it is regenerated and **re-sorted by path** on every status refresh in `updateChangedFiles` [1](#0-0) . The keyboard "toggle include" handler and the list's `onFileSelectionChanged` callback both convert a UI row *index* back into a file by indexing directly into this array at the time the callback fires: `workingDirectory.files[row]` [2](#0-1)  and `changes.workingDirectory.files[i]` [3](#0-2) . If a background git-status refresh lands between when the user visually targets a row (e.g. presses Space on a keyboard-focused row) and when the resulting index is resolved against the (now reordered) `files` array, the wrong `WorkingDirectoryFileChange` is included/excluded from the commit, or the wrong file's diff/discard action is applied — with no re-validation that the file at that index is still the file the user saw.

### Finding Description
`updateChangedFiles` merges the new git status into the working directory and explicitly re-sorts the merged file list by path every time status is refreshed: [1](#0-0) 

This sort order is not guaranteed to match the order the renderer last displayed, because any new file appearing (e.g. an editor autosave, a build tool writing a new artifact, a `.gitignore`-driven untracked file appearing/disappearing, or simply another file's status flipping) changes which paths exist and therefore can shift every subsequent row's array index.

The keyboard handler for the checkbox toggle receives a bare row number and indexes straight into the live (not snapshotted) `workingDirectory.files` prop at call time: [2](#0-1) 
There is no check that the file found at `row` is the same file that was rendered/focused when the user pressed the key — only a null check (`if (!file)`), which only catches array-shrinkage, not reordering.

Likewise, list-selection changes map an array of numeric `rows` straight back to files positionally: [3](#0-2) 
and this result is fed to `dispatcher.selectWorkingDirectoryFiles`, which ultimately becomes the set of files whose diff is loaded/committed via `_selectWorkingDirectoryFiles` [4](#0-3) .

By contrast, when the filtered list (`FilterChangesList`) resolves selection it goes through IDs, not raw indices, converting `IChangesListItem.id` → `findFileIndexByID` before handing rows up [5](#0-4)  — this is the safer pattern that the plain sidebar's keyboard/index path does not consistently use, showing the invariant is only inconsistently enforced across the codebase, exactly as in the Angle report where the fix was "not fully mitigated."

The final commit path itself is not index-based — `_commitIncludedChanges` filters by `file.selection.getSelectionType()` on the current `state.changesState.workingDirectory.files`, i.e. by whatever inclusion flags are on the file objects at commit time [6](#0-5) . This means the exposure is not "commit the wrong file outright," but "silently flip the include/exclude flag (or replace the active diff/selection) on a *different* file than the one the user was looking at," which then persists into whatever commit is made next — a silent corruption of what the user commits, matching the impact class in the report (user acts on stale positional information, unaware the underlying ordered collection changed).

### Impact Explanation
If the row-to-file resolution races a background status refresh, the checkbox state (included/excluded) or diff selection ends up applied to the wrong file. Because `_commitIncludedChanges` blindly includes whatever files currently have a non-`None` selection, a toggle mistake here directly changes the contents of the next commit without any user-visible error — this is a silent corruption of the user's intended commit contents, one of the explicitly valid impact categories (no code execution needed, but it matches "silent corruption of what the user commits or pushes"). The severity is bounded by the fact that an attacker cannot directly control which file gets picked; it depends on natural repository churn (new/removed files) coinciding with user interaction timing, and the user retains ultimate control by reviewing the diff before pushing — but the review pathway itself is also index/selection driven and susceptible to the same stale-state issue at `updateChangesWorkingDirectoryDiff`'s guard, which does check for `selectedFileIDs` equality post-load [7](#0-6)  — showing the diff-loading path was hardened with an ID-based staleness check, while the raw keyboard/row-index toggle path was not.

### Likelihood Explanation
Requires: (1) the user interacting with the Changes list via keyboard-focused row toggling or non-filtered list selection at essentially the same moment as (2) a background status refresh that changes the sort position of files (new/removed/renamed file, or a path whose sort order relative to others changes). Desktop polls/refreshes status frequently (on window focus, file system events, after git operations), so such races are plausible in active repos with frequent file churn (e.g. build output, generated files, IDE temp files) but not attacker-triggerable without the user already having such a repo open — this keeps it in "unprivileged issue triggered by a normal git workflow," not requiring local/admin access beyond normal app use.

### Recommendation
Resolve row → file mappings by stable identity (`WorkingDirectoryFileChange.id`, which the file-list model already computes) rather than by raw array index at the moment a keyboard or list callback fires. Specifically:
- In `onToggleInclude`/`onFileSelectionChanged` in `app/src/ui/changes/sidebar.tsx`, snapshot the file's `id` at focus/interaction time and re-resolve it via `workingDirectory.findFileWithID(id)` before applying selection/include-state, discarding the action (or re-confirming) if the id is no longer present at that row.
- Follow the same pattern already used in `filter-changes-list.tsx`'s `onFileSelectionChanged`, which resolves through `findFileIndexByID` rather than trusting raw positional indices.

### Proof of Concept
1. Open a repository in Desktop with several modified/untracked files in the Changes list; use keyboard navigation to focus row N (a specific file, say `b.txt`).
2. Concurrently (e.g. via a script or editor autosave) create a new untracked file whose path sorts alphabetically before `b.txt`, and trigger/await Desktop's background status refresh — `updateChangedFiles` re-sorts `mergedFiles` by path [1](#0-0) , shifting `b.txt` from index N to N+1.
3. Press Space (toggle include) while the UI still shows row N focused; `onToggleInclude(row)` resolves `workingDirectory.files[row]` against the *new* array [2](#0-1) , now returning the new file at index N instead of `b.txt`.
4. The new file's include/selection state is toggled instead of `b.txt`'s. Running "Commit" afterwards includes/excludes the wrong file, per `_commitIncludedChanges`'s selection-based filter [6](#0-5) , with no error shown to the user.
