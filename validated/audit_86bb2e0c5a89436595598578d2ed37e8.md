### Title
Reentrant escrow release in Tron `IntentGatewayV2.withdraw()` due to external token transfer preceding the escrow debit - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core defect class is "a value used to move funds is computed/consumed without the guard that ensures the accounting state is correct at the moment of use." The local Hyperbridge analog is not a missing `SafeMath` wrapper (Solidity ≥0.8 already reverts on overflow/underflow) but a **checks-effects-interactions violation** in the Tron variant of the Intent Gateway's escrow-release routine: the token transfer is executed *before* the escrow ledger (`_orders[commitment][token]`) is debited, unlike the equivalent EVM implementation which debits first.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` releases escrowed order inputs to a beneficiary (solver on fill, or user on refund): [1](#0-0) 

The loop only checks that the escrow slot is non-zero (`_orders[body.commitment][token] == 0`), sends the tokens via a raw low-level `.call` to `transfer` (or a native value transfer), **and only afterwards** decrements `_orders[body.commitment][token] -= amount`. This is the opposite order of the equivalent EVM contract, `IntentsBase.sol`'s `_withdraw()`, which correctly writes the reduced balance to storage *before* making any external call: [2](#0-1) 

Because `order.inputs[i].token` is attacker-controlled at `placeOrder()` time (the user picks any ERC-20 address as an escrowed input), a malicious escrow token can implement a `transfer()`/fallback hook that reenters the gateway contract while `_orders[body.commitment][token]` for that token is still un-decremented. Any other public/permissioned surface in the same contract that reads or mutates `_orders[commitment][*]` for the same or a different in-flight commitment during that window operates on a stale, not-yet-updated ledger — the classic reentrancy window that "unchecked math operations" reports generalize to: a state value used for a transfer/accounting decision is stale relative to the guard that was supposed to protect it.

### Impact Explanation
This falls squarely under the bounty's "unauthorized transaction manipulation" / "replay / double-claim / double-settlement" category: the escrow debit that is supposed to make each redemption or refund a one-time action is deferred past an external call, breaking the one-time-use invariant Hyperbridge's Method section calls out for request/response paths ("...one-time receipt handling..."). Even though Solidity ≥0.8's automatic underflow checks bound a naive same-call double-spend by eventually reverting (which would also unwind any value already sent within the same transaction), the ordering is still an objectively incorrect and dangerous pattern versus the hardened EVM sibling contract, and it exposes any code path in the contract that inspects `_orders[commitment][token]` mid-callback to a stale value, which is exactly the "corrupted value" class of bug the SimpleTokenSale report describes (a value computed/consulted before its supporting state is finalized).

### Likelihood Explanation
Exploitability depends on whether an attacker can get a malicious, hook-bearing token accepted as an order's escrowed input (feasible since `order.inputs[].token` is user-supplied at `placeOrder`), and on whether another entry point touching the same commitment's escrow is reachable mid-reentrancy without additional privilege. I could not fully verify a complete end-to-end double-payout PoC within the indexed code (some call paths, e.g. the exact guards inside `_authenticate`/`onGetResponse` reentry protection, were not fully visible in this pass), so likelihood should be treated as **medium** pending a live/dynamic reentrancy trace — but the code-level CEI violation itself is a concrete, verifiable defect independent of that uncertainty.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to mirror `IntentsBase.sol`: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed`, not just `!= 0`) **before** performing the native/ERC-20 transfer, and add a `nonReentrant` guard around all functions that touch `_orders` as defense in depth.

### Proof of Concept
Conceptual PoC (not fully executed against a live harness — index does not expose a runnable Tron test environment):
1. Attacker calls `placeOrder()` with `order.inputs[0].token` set to a malicious ERC-20 (`EvilToken`) whose `transfer()` implementation calls back into the gateway.
2. Attacker (or colluding solver) fills/settles the order so that a `RedeemEscrow`/`RefundEscrow` message reaches `onAccept` → `withdraw()`.
3. Inside `withdraw()`'s loop, `EvilToken.transfer(beneficiary, amount)` is invoked at [3](#0-2)  while `_orders[body.commitment][EvilToken]` is still un-decremented.
4. `EvilToken.transfer` reenters the gateway (e.g., attempting a second redemption path or reading `_orders` for a decision elsewhere) before line 701 executes, observing/using the stale (pre-debit) escrow balance.
5. Contrast with the hardened ordering in `IntentsBase.sol` at [2](#0-1) , where the debit happens first, closing this window.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                if (!success) revert TransferFailed();
            }

                ++i;
            }
        }
