### Title
Path-safety check in `resolveWithin` verifies a resolved symlink target but returns the un-verified path string, creating a check-then-use gap exploited via attacker-controlled repository content - (File: `app/src/lib/path.ts`)

### Summary
GitHub Desktop's `resolveWithin` helper is the central guard used to stop a repository-relative path (taken from git output, e.g. a list of conflicted files) from escaping the repository root via `..` traversal or symlinks. The function performs its safety check with `realpath`, but then returns the **unresolved** path string rather than the value it actually verified. Callers such as `buildConflictContext` subsequently `stat`/`readFile` that unresolved path in separate filesystem calls, after the check has already completed. This mirrors the Blend report's root cause: a security invariant validated against one piece of state (the realpath at check time) is trusted for a later, distinct action (the actual read) instead of being re-verified at the point where the effect happens.

### Finding Description
`_resolveWithin` in `app/src/lib/path.ts` computes `resolved = resolve(normalizedRoot, normalizedRelative)`, then calls `realpath` on both the root and `resolved`, and only if `realResolved.startsWith(realRoot)` does it return — not `realResolved`, but the original `resolved` string: [1](#0-0) 

Every consumer of this API treats a non-null return as proof that the path is safely contained, and then performs the actual file operation later, as a separate syscall, against that unresolved string:
- `buildConflictContext` calls `resolveWithin(workingDirectory, file.path)`, then in later, independent `await` calls performs `stat(absolutePath)` and `readFile(absolutePath, 'utf8')`: [2](#0-1) 
- `dispatcher.ts`'s `openRepositoryFromUrl` does the same pattern for opening arbitrary attacker-influenced deep-link paths via `shell.showItemInFolder`: [3](#0-2) 

Because the containment check and the actual file read/open are two distinct, non-atomic operations, the safety guarantee only holds for the instant the check ran. Since the conflicted-file paths and their on-disk content originate from an attacker-controlled cloned/fetched repository (the "theirs" side of a merge, rebase, or cherry-pick), the attacker directly controls the filesystem entries that Desktop will later act on at those repository-relative paths. If the entry at a given path changes between the `realpath` check and the subsequent `stat`/`readFile` (for example, because a concurrent git checkout/submodule operation driven by the same conflict resolution flow replaces a regular file with a symlink at that path, which is plausible during multi-stage merge conflict checkouts), the later read follows the new target unconditionally — the code never re-validates containment at the point of use.

### Impact Explanation
The `buildConflictContext` path is used to gather conflicted file content and send it to the Copilot SDK (via `formatConflictContextForPrompt`) to auto-resolve merge conflicts. If a symlink escaping the repository root exists at the checked path at the moment of `readFile`, arbitrary file content outside the repository (e.g., SSH keys, `.netrc`, other project source) could be read and exfiltrated to the Copilot backend as part of the conflict-resolution prompt. The `dispatcher.ts` variant could similarly cause Desktop to reveal/open a path outside the repository via a crafted deep link. This lines up with the "read outside the repo" / "credential exfiltration" categories called out as valid impact.

### Likelihood Explanation
The check itself (using `realpath` to defeat symlinks) is a real, existing mitigation and does correctly block a static symlink present at check time — this is confirmed by the project's own tests. The remaining gap is the narrow window between the check and the use, and I was not able to confirm, within the available tooling, a reliable attacker-controlled mechanism to swap the filesystem entry in that exact window without invoking local/background execution (which is excluded from valid impact). Because of this, likelihood is lower than the confirmed cases in `path-test.ts`, and this should be treated as a hardening gap (check-then-use / non-atomic validation) rather than a demonstrated, reliably exploitable remote path at this time.

### Recommendation
Make `resolveWithin` return the `realResolved` value it actually verified (not the pre-`realpath` `resolved` string), and have callers perform subsequent `stat`/`readFile`/`open` operations against that verified real path. Where possible, open the file with `O_NOFOLLOW` semantics or re-run the containment check immediately before the read/write, so the validated state and the acted-upon state are the same object, closing the gap between check and use — directly analogous to the Blend fix of moving the invariant check to the point where the effect is finally applied instead of an earlier, separable step.

### Proof of Concept
Conceptual PoC (not fully verifiable without live race timing, given tool constraints):
1. Attacker crafts a branch such that merging it produces a conflict at path `notes/todo.md`.
2. Through the merge/rebase machinery invoked by Desktop's conflict-resolution flow, the working-tree entry at `notes/todo.md` is momentarily a regular file (passing the `realpath` check in `resolveWithin`) and is later replaced by a symlink pointing to `~/.ssh/id_rsa` by a subsequent git checkout step in the same operation, before `buildConflictContext`'s `stat`/`readFile` calls execute: [2](#0-1) 
3. Because `resolveWithin` returns the unresolved `resolved` path rather than `realResolved`, and the read happens in a separate later call, `readFile` follows the symlink and its content is included in the context sent to Copilot.

Existing unit tests confirm the intended symlink defense works for a static symlink present at check time, but do not test the check-then-use ordering against a symlink introduced after the check: [4](#0-3)
