### Title
Order-independent multisig transactions are malleable, allowing an unprivileged party to clone a broadcast transaction with a different `txid` but an identical nonce/effect - ([File: stacks-codec/src/transaction.rs])

### Summary
The `ApprovalVotingModule` bug let an attacker who never held the legitimate governor's authority squat a `proposalId` because the module accepted an externally-supplied ID without recomputing/binding it to the data that actually produced it. The structural analog in `stacks-core` is `OrderIndependentMultisigSpendingCondition`: the address (identity) check that authorizes a transaction is computed in a way that is intentionally insensitive to the order of the auth fields, while the `txid` used everywhere else (mempool key, nonce-conflict resolution, block inclusion) is computed over the exact byte-serialized field order. This decouples "the value that authorizes the transaction" from "the value that uniquely identifies the transaction," letting an unprivileged observer reorder already-public fields to mint a second, equally valid transaction with a different `txid` but the same origin, nonce, fee, and payload.

### Finding Description
`OrderIndependentMultisigSpendingCondition::verify` recovers all public keys from the `fields` vector (in whatever order they appear), requires only `num_sigs >= signatures_required` (not `==`), and then derives the authorizing address from the recovered `pubkeys` list using the order-independent hash mode: [1](#0-0) 

The whole point of the "OrderIndependent" hash mode (gated to Epoch ≥ 3.0) is that signers do not need to coordinate on the order in which their signatures/public keys are appended, so the derived address does not depend on the order of `self.fields`: [2](#0-1) 

Fields are freely reorderable by anyone holding the transaction, via the very same push/pop primitives used for legitimate signing: [3](#0-2) 

However, the transaction's `txid` — the value used as the mempool primary key, the RBF/nonce-conflict key, and the block-inclusion key — is computed over the full consensus-serialized byte stream, in which the auth `fields` are written in vector order: [4](#0-3) [5](#0-4) 

Because the auth fields (public keys and already-produced signatures) are entirely public once a transaction is broadcast to the mempool, an unprivileged third party — with no private key and no relationship to the signers — can take a valid, broadcast `OrderIndependentMultisig` transaction, permute the order of its `fields` (or, since the check is `>=` rather than `==`, append already-visible signature/public-key fields it did not create), and re-serialize it. The result:
- Still satisfies `verify()` (same set of pubkeys ⇒ same derived address; `num_sigs` still ≥ threshold), so `TransactionAuth::verify_origin`/`verify` still accepts it: [6](#0-5) 
- Has a **different `txid`** than the original, because `txid()` hashes the exact byte order of `fields`.
- Carries the **same origin address, nonce, and fee** as the original, since those are unchanged.

This breaks the implicit equality the mempool and node relies on: "one signed intent ⇒ one canonical `txid`." Mempool admission and nonce-conflict handling key off `txid`/nonce pairs: [7](#0-6) 

### Impact Explanation
Two different, both individually-valid transaction encodings now exist for the same signer/nonce/payload. Depending on which encoding a given node's mempool first observes, different nodes can end up with different candidate transactions for the same account/nonce slot — a mempool-versus-block admissibility divergence. If a miner mines the attacker's reordered clone (same nonce) instead of, or racing with, the originally-broadcast one, the legitimate sender's specific transaction (identified by its original `txid`, e.g. tracked by wallets/services via that `txid`) is silently invalidated/evicted even though its semantic content was mined — and any off-chain system that tracked the original `txid` (exchanges, bridges, front-ends) will treat it as dropped/lost while the funds/state change actually occurred under a different `txid`. This is a concrete instance of a transaction being "classified differently by different nodes" / accepted with a `txid` different from the one the sender obtained, purely by manipulation from an unprivileged third party who never held a signing key.

### Likelihood Explanation
This requires no cooperation from, or compromise of, the transaction's signers. Any node relaying the mempool, or any observer of the broadcast transaction bytes, can perform the reordering/duplication and rebroadcast, since the `OrderIndependentMultisigSpendingCondition` fields are fully public in the unconfirmed transaction. The only precondition is that the transaction in question uses the `OrderIndependentMultisig` spending condition (available since Epoch 3.0) and has more than one auth field (any real multisig account).

### Recommendation
Canonicalize the on-wire ordering of `OrderIndependentMultisigSpendingCondition::fields` before/while computing `txid` (e.g., require fields to be serialized in a canonical, deterministic order such as sorted-by-public-key, and reject transactions whose fields are not in that canonical order), so that `txid` becomes a strict function of the semantic authorization, matching the order-independence already guaranteed by the address-derivation check. Alternatively, bind the nonce-conflict/mempool-replacement logic to `(origin address, nonce)` plus a canonicalized signature-set hash rather than solely to the raw `txid`.

### Proof of Concept
1. Alice creates a 2-of-3 `OrderIndependentMultisig` account and broadcasts transaction `T` with nonce `N`, fee `F`, and fields `[sig(k1), sig(k2)]` appended in that order. `T` has `txid = H1`.
2. Mallory (no private key, not a party to the multisig) observes `T` in the mempool, clones it, and swaps the order of the two signature fields to `[sig(k2), sig(k1)]`, producing `T'` with identical `version/chain_id/nonce/fee/payload/post-conditions` but `txid = H2 != H1`.
3. `T'.auth.verify()` succeeds: `OrderIndependentMultisigSpendingCondition::verify` recovers the same two public keys regardless of field order, `num_sigs (2) >= signatures_required (2)`, and `StacksAddress::from_public_keys(...)` yields the same address as `Alice`'s account, matching `self.signer` — verification passes.
4. Mallory rebroadcasts `T'`. Nodes now hold two distinct, independently valid transactions (`H1`, `H2`) for the same origin/nonce pair; whichever is mined first consumes the nonce, and any tracking keyed on the original `txid` `H1` will show that transaction as never confirmed even though the semantically identical action executed on-chain under `H2`.
