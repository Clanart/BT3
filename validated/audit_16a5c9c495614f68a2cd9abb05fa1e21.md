## Analysis

The `DiffSelection` class stores a set of *absolute line indices* (`divergingLines`) that were computed against one specific diff (the one rendered in the UI when the user selected/deselected lines). Nothing ties this selection to the diff/content hash it was computed against — line indices are just integers. [1](#0-0) [2](#0-1) 

When the user commits, `_commitIncludedChanges` takes the cached `WorkingDirectoryFileChange` objects (with their possibly-stale `selection`) straight from `repositoryStateCache` and passes them to `createCommit` → `stageFiles` → `applyPatchToIndex`. [3](#0-2) [4](#0-3) 

`applyPatchToIndex` then re-fetches a **fresh** diff of the file at staging time (`getWorkingDirectoryDiff`), not the diff the user actually looked at when choosing lines, and calls `formatPatch(file, diff)`, which walks the *new* diff's hunks and checks `file.selection.isSelected(absoluteIndex)` using the *old* line indices: [5](#0-4) [6](#0-5) 

The Desktop authors already documented this class of problem for the diff-viewer selection-remap path, admitting that only "selectable lines" are pruned and that stale selections are not properly re-validated against a changed diff: [7](#0-6) 

But that remap only runs for the **currently displayed** file in `updateChangesWorkingDirectoryDiff`, and only updates `selectableLines`, not the semantic mapping of line index → content. It is never invoked as part of the commit path itself — `_commitIncludedChanges` never re-syncs the selection against a fresh diff before staging. If the on-disk file content shifts (lines added/removed above the previously-selected hunk) between the moment the user made a partial line selection and the moment they click "Commit", the line-index-based `divergingLines` set now points to the wrong lines in the new diff, silently producing a patch that includes/excludes content the user never intended.

### Title
Stale line-index diff selection can silently commit unintended content when working tree changes between selection and commit - (File: `app/src/lib/git/apply.ts`)

### Summary
`DiffSelection` tracks partial-commit choices purely as abstract line-index numbers with no binding to a diff's content or hash. `applyPatchToIndex` fetches a brand-new diff of the file at staging time and reuses the old, possibly-mismatched line indices to decide which lines to include, silently corrupting the resulting commit if the file changed in the interim.

### Finding Description
1. A user opens the diff for a modified file and selects a subset of lines via `withLineSelection`/`withRangeSelection`, which stores only integer `divergingLines` indices relative to that diff's hunks. [8](#0-7) 
2. Before the user clicks Commit, the tracked file on disk changes — e.g., a build tool, formatter, linter auto-fix, or any process spawned from the opened repository (npm/yarn scripts, IDE tasks, git hooks bundled in the repo, a watch process) rewrites the file, shifting line numbers.
3. `_commitIncludedChanges` reads the file list, including the now-stale `selection`, straight from `repositoryStateCache` without re-validating it against a fresh diff. [9](#0-8) 
4. `stageFiles`/`applyPatchToIndex` fetches a **new** diff (`getWorkingDirectoryDiff`) and builds the patch using `file.selection.isSelected(absoluteIndex)` against this new diff's hunk line offsets. [5](#0-4) 
5. Because `isSelected` only compares raw indices, not diff content, lines that shifted position are silently mis-attributed as selected/unselected — the generated patch (and thus the commit) no longer matches what the user actually reviewed and chose in the UI.

The only mitigation Desktop has for this class of bug — `updateChangesWorkingDirectoryDiff`'s `withSelectableLines` remap — only applies to the file currently open in the diff viewer, is explicitly acknowledged by the code comment as incomplete ("Ideally we would be more clever about validating that any partial selection state is still valid..."), and is never invoked from the commit path itself. [10](#0-9) 

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": a partial commit can end up containing lines the user explicitly deselected, or omit lines the user explicitly selected, without any warning, error, or diff-preview mismatch surfaced to the user. In a repository set up by an attacker (e.g., one with an automatic post-checkout/build script, editor task, or watcher that mutates tracked files shortly after clone/open), this can be weaponized to smuggle unintended content into a commit that the victim believes only contains their reviewed, hand-picked lines — a supply-chain-relevant integrity issue since the commit is then pushed/shared under the victim's authorship.

### Likelihood Explanation
Moderate-to-low without an active attacker, but realistic: partial-selection commits are a commonly used Desktop feature, and any external process that rewrites the file between diff review and clicking "Commit" (auto-formatters, lint --fix, generated file regeneration, build watchers commonly configured in cloned repositories) can trigger the mismatch. An attacker who controls the cloned repository can deliberately configure such automation (e.g., a `.vscode/tasks.json` autorun task, an editor formatter, or a background script) to increase the window and reliability of the race, without requiring any unusual user action beyond normal partial-commit workflow.

### Recommendation
Bind `DiffSelection` (or the `WorkingDirectoryFileChange`) to a content fingerprint of the diff it was computed against (e.g., hash of `diff.text` or the underlying blob OIDs). Before staging in `applyPatchToIndex`/`stageFiles`, re-fetch the diff and verify the fingerprint matches; if it doesn't, abort the partial-commit for that file and prompt the user to re-review the (changed) diff rather than silently applying stale line selections to new diff content.

### Proof of Concept
Conceptual sequence (cannot be executed without a live app instance, but derivable purely from the code paths above):
1. Modify `modified-file.md` to have an extra unrelated hunk at the top; open it in Desktop's Changes view.
2. In the diff viewer, deselect a specific line (e.g., line at hunk 2) — this stores its absolute index in `divergingLines`.
3. Before clicking Commit, run a script (simulating an attacker's post-checkout/build automation) that prepends lines to the file, shifting hunk boundaries.
4. Click Commit. `applyPatchToIndex` calls `getWorkingDirectoryDiff` again, obtaining a diff whose hunk offsets have shifted; `formatPatch` evaluates `file.selection.isSelected(absoluteIndex)` using the old indices against the new hunks. [6](#0-5) 
5. Inspect the resulting commit: the line that was deliberately deselected by the user is now included (or vice-versa), with no warning shown, confirming the silent-corruption path described above.

      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent

    const to = from + length

    // selected and we're being asked to select more or when no lines are
    // selected and we're being asked to unselect something.

      return this

      if (typeMatchesSelection(this.defaultSelectionType, selected)) {
