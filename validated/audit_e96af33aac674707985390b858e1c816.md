Notably, `BandwidthManager` — the sibling app on the same pattern — defines a `PALLET_BANDWIDTH_MODULE_ID` constant and explicitly documents that this must match the module id on the Substrate side, implying it is meant to check the `from` field against this constant. `HostManager.onAccept`, which controls fee-token withdrawal and host-parameter mutation, does **not** perform this check.

### Title
Missing `request.from` module-id binding in `HostManager.onAccept` allows unauthorized cross-chain fund withdrawal - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager.onAccept` (evm/src/core/HostManager.sol:95-109) validates only that `request.source` equals the configured Hyperbridge state machine, but never checks `request.from` — the module identifier of the specific pallet on Hyperbridge that is authorized to issue `Withdraw`/`SetHostParam` actions. Any pallet or ISMP-dispatch-capable module on the Hyperbridge chain can therefore construct a `PostRequest` with `source == hyperbridge` and an arbitrary `from`, which will be delivered and accepted by `HostManager`, triggering `IHostManager(_params.host).withdraw(...)` to drain the host's fee-token balance to any beneficiary, or `updateHostParams(...)` to rewrite consensus/host configuration.

### Finding Description
`HostManager.onAccept` is restricted to `msg.sender == _params.host` via the `restrict` modifier [1](#0-0) , and additionally checks that `request.source` equals `IHost(_params.host).hyperbridge()` [2](#0-1) . That confirms the message *originated from the Hyperbridge chain*, but it does not confirm *which module on that chain* dispatched it. The subsequent branch decodes the action byte and, for `Withdraw`, directly calls `IHostManager(_params.host).withdraw(withdrawParams)` with attacker-controlled `beneficiary`, `amount`, and `token` fields decoded straight from the request body [3](#0-2) .

Compare this to the sibling contract `BandwidthManager`, which documents an explicit per-module binding requirement: `PALLET_BANDWIDTH_MODULE_ID` is declared as "must equal `pallet-bandwidth`'s `PalletId`. The pallet enforces this on inbound messages, so changing it on either side breaks the round-trip" [4](#0-3) . `HostManager` has no analogous `from`-binding constant or check at all — only the chain-level `source` is validated [1](#0-0) .

On the Substrate side, ISMP dispatch is available generically to any pallet through `IsmpDispatcher`, and the `RequestCommitments` storage explicitly "ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge" — confirming multiple independent pallets can originate requests with `source == hyperbridge` but different `from` module ids. Because `HostManager` never checks `from` against the specific pallet id expected to control the treasury (e.g. host-executive's or relayer's module id), any of those other legitimate hyperbridge-side pallets — or any future one added to the runtime — that can be induced to dispatch a POST request with `dest` pointed at an EVM chain and a body starting with the `Withdraw`/`SetHostParam` action byte would have that message accepted and executed by `HostManager` as if it were an authorized governance/relayer withdrawal.

### Impact Explanation
This breaks the "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow" invariant. A successful exploit results in unauthorized withdrawal of the `IsmpHost`'s accumulated fee-token/native-token revenue to an attacker-chosen beneficiary, or unauthorized mutation of `HostParams` (consensus client, accepted state machines, etc.), which is direct loss/theft of bridge funds and unauthorized execution of privileged host-management logic.

### Likelihood Explanation
Exploitability depends on whether any non-privileged, non-governance pallet on the Hyperbridge chain can be made to dispatch an ISMP POST request with a `from` value other than the intended host-executive/relayer module id, but with `source` correctly set to Hyperbridge (which is automatic for any local dispatch) and `dest`/body crafted to match the `Withdraw` action encoding. Given that ISMP dispatch is a generic capability shared across many pallets (host-executive, intents-coprocessor, token-governor, relayer, bandwidth, and "any other pallet"), and given that `HostManager` performs no `from`-based allowlisting, the guard that exists (`source` check) does not stop a message from an unintended module reaching the withdrawal/param-update logic. I could not fully verify from the indexed code whether the runtime restricts which pallets are permitted to set `dest` to an EVM-managed chain or otherwise gates this path (e.g., through relayer-only extrinsics with signature checks as seen in `pallet-relayer`'s `withdraw`), so likelihood should be treated as dependent on that runtime-level gating, which was not fully visible in the available files.

### Recommendation
Add an explicit `from`-module check in `HostManager.onAccept`, analogous to `BandwidthManager`'s documented `PALLET_BANDWIDTH_MODULE_ID` pattern: define a constant module id matching the specific pallet(s) authorized to issue `Withdraw`/`SetHostParam` (e.g., the host-executive/relayer pallet id or `HYPERBRIDGE_MODULE_ID`), and revert if `request.from` does not match it, in addition to the existing `request.source` check.

### Proof of Concept
1. On the Hyperbridge chain, from any pallet capable of calling `IsmpDispatcher::dispatch_request` (not just the intended host-executive/relayer module), construct a `PostRequest` with:
   - `source` = Hyperbridge's own state machine id (automatically satisfied for any local dispatch),
   - `dest` = the target EVM chain's state machine id,
   - `to` = the `HostManager` contract address on that EVM chain,
   - `body` = `abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(WithdrawParams({beneficiary: attacker, amount: hostBalance, token: feeToken})))`.
2. Once delivered and proven on the destination via the normal ISMP relay flow, `EvmHost` calls `HostManager.onAccept(incoming)`.
3. `onAccept` checks `msg.sender == host` (satisfied, since the call comes from the host contract itself) and `request.source == hyperbridge` (satisfied, since the request truly originated from the Hyperbridge chain) [1](#0-0) ; it never checks `request.from`.
4. Execution proceeds to `IHostManager(_params.host).withdraw(withdrawParams)` [5](#0-4) , transferring `hostBalance` of `feeToken` to `attacker`.
