### Title
Scanner::scan_block reports immature coinbase outputs as received funds that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class in the report is an access/validity check that validates only the existence of a resource (a share session) while ignoring a state flag that should revoke it (expired / deleted / view-limit reached). The Serai analog lives in the Bitcoin wallet `Scanner`: `scan_transaction` treats an output as a valid, received `ReceivedOutput` purely because its `script_pubkey` exists in the registered `scripts` map, and `scan_block` applies that check to every transaction in a block — including `block.txdata[0]`, the coinbase. Coinbase outputs are unspendable until 100 confirmations (BIP-30/consensus COINBASE_MATURITY), so the scanner reports funds as received that are not actually spendable, exactly the "existence check, missing state check" shape.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) iterates `tx.output`, looks up `output.script_pubkey` in `self.scripts`, and pushes a `ReceivedOutput` on match. It performs no check on the nature or spendability of the producing transaction. `Scanner::scan_block` (lines 221-227) then calls `scan_transaction` over `block.txdata` unfiltered, including the coinbase transaction at index 0:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {           // includes txdata[0], the coinbase
        res.extend(self.scan_transaction(tx));
    }
    res
}
```

`ReceivedOutput` is the type consumed by the spend path (`ReceivedOutput::output()`, `outpoint()`, `value()`, `offset()` at lines 99-118 feed `wallet/send.rs` transaction construction). An output produced by a coinbase transaction is consensus-invalid as an input for 100 blocks, yet it is surfaced identically to a normal spendable output. The only mitigation is the doc comment advising callers to post-process or scan `block.txdata[1 ..]` — the API itself performs no exclusion, mirroring `check_shared_access_allowed()` validating session existence while ignoring the `inactive`/`deleted` flags.

### Impact Explanation
A miner (or anyone able to get a coinbase paying the scanned script into a block — e.g., via a mining pool payout or a found block) causes the scanner to emit a `ReceivedOutput` that downstream code treats as a spendable UTXO. Consequences: the wallet's reported balance is inflated by immature funds; a transaction built spending that outpoint is rejected by the network (non-BIP68-final/immature coinbase), wasting fees on attempted rebroadcasts and potentially stalling the signing pipeline while the "received" funds are believed available. The accept criterion "funds reported received that are not spendable" is met directly.

### Likelihood Explanation
Reachable with public inputs: an attacker only needs a coinbase output paying to a registered script in a block fed to `scan_block`. For an actively mining counterparty or a pool payout configuration this is trivially induced; even without targeting, pools commonly pay arbitrary addresses from coinbases, so any Serai deployment scanning blocks for deposit detection will eventually encounter it. Exploitation requires no authentication, no key material, and no collusion — just an untrusted `Block` passed to `scan_block`. Rated Medium: the effect is availability/accounting corruption and fee burn rather than direct key or fund theft, and the limitation is documented, requiring an integrator that scans whole blocks without post-processing.

### Recommendation
Exclude `block.txdata[0]` in `scan_block` (scan `&block.txdata[1 ..]`), or better, detect coinbase transactions (`tx.is_coinbase()`) in `scan_transaction`/`scan_block` and either skip them or attach maturity metadata to `ReceivedOutput` so callers cannot treat immature outputs as spendable. Alternatively track spends within the scanned block so outputs consumed in the same block are not reported.

### Proof of Concept
1. Build a `Scanner` via `Scanner::new(group_key)` and `register_offset` for a deposit offset.
2. Construct a regtest/test block whose coinbase transaction (`txdata[0]`) contains an output with `script_pubkey` equal to the registered script (paying `key + offset` tweaked, e.g. 50 BTC).
3. Call `scanner.scan_block(&block)`.
4. Observe a `ReceivedOutput` returned with the coinbase outpoint; calling `send.rs`'s transaction builder with it produces a transaction spending an immature coinbase input, which bitcoind rejects (`bad-txns-premature-spend-of-coinbase`). The scanner reported funds received that are not spendable.
