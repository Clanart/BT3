### Title
Payout OP_RETURN operator attribution is not committed by the withdrawal signature, allowing wrong-party reimbursement attribution - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs the payout transaction's input0 with `SinglePlusAnyoneCanPay`, which under BIP-341 only commits to input0 and output0 (the user payout). The anchor output and the OP_RETURN output that names the fronting operator's x-only pubkey are completely unsigned. Any party who knows the withdrawer's `SinglePlusAnyoneCanPay` signature (including the withdrawer themselves, who legitimately owns it) can therefore construct a *different*, self-funded transaction that spends the same withdrawal input, pays the identical output0, but embeds an arbitrary OP_RETURN naming any registered operator (or none). `update_finalized_payouts` blindly trusts whatever OP_RETURN is present in the confirmed transaction with no cross-check against who actually funded the extra inputs.

### Finding Description
The broken binding is: `withdrawals.payout_payer_operator_xonly_pk` (read by `get_payout_info_from_move_txid`, core/src/database/verifier.rs:253-280) must equal the xonly pubkey of the party that economically funded the confirmed payout transaction's non-committed inputs.

`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds:
- input0: user's withdrawal UTXO, signed `SinglePlusAnyoneCanPay` by the user
- output0: user payout (committed by the signature, since SIGHASH_SINGLE covers the same-index output)
- output1: anchor, output2: OP_RETURN(operator_xonly_pk) — **neither is committed** by the SinglePlusAnyoneCanPay signature (`ANYONECANPAY` also frees any other inputs added later)

`Operator::withdraw` (core/src/operator.rs:560-637) verifies only that the signature is valid for input0/output0, then funds the tx with `fund_raw_transaction` (adding the operator's own paying inputs, separately signed) and broadcasts it.

Because the user's signature never commits to the OP_RETURN or to which party supplies the fee-paying inputs, anyone possessing that signature (most simply, the withdrawing user themselves, who legitimately holds it after calling Citrea's `withdraw`) can build a competing transaction with the same input0/output0, their own fee-paying inputs, and an arbitrary OP_RETURN naming any currently-registered operator Q's xonly pubkey. If this transaction confirms instead of the genuine operator's, `update_finalized_payouts` (core/src/verifier.rs:2283-2353) parses the OP_RETURN via `get_first_op_return_output`/`parse_op_return_data` and persists `payout_payer_operator_xonly_pk = Q` via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:198-251) with no validation that Q actually contributed to the transaction's funding inputs.

Operator Q's own `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, finding this entry, automatically calls `handle_finalized_payout` and proceeds through the kickoff/reimbursement flow. `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) only checks that the stored `operator_xonly_pk` matches the kickoff's operator and that the committed blockhash matches — both trivially satisfied since Q's own kickoff naturally uses Q's own pubkey and the block is genuine chain data. No code path checks that Q actually paid for the payout's funding inputs.

### Impact Explanation
An operator (Q) can be automatically and fully reimbursed by the bridge for a withdrawal it never funded — matching the Critical category "an operator reimbursed for a payout it never funded." The economic loss falls on the bridge/protocol (paying out `bridge_amount` in the eventual Reimburse transaction) while the actual funder of the withdrawal's fee-paying inputs is the attacker (who, if they are the withdrawer, largely just pays themselves and the mining fee). Alternatively, by naming no operator (or a garbage pubkey), the attacker can prevent any operator from ever being attributed for that withdrawal, permanently denying reimbursement to whichever operator would otherwise have funded it. This is repeatable per withdrawal and is not specific to any one deposit or operator — it applies to every payout transaction in the system, since the OP_RETURN attribution mechanism itself is not committed by any signature.

### Likelihood Explanation
No special privilege is required beyond being the withdrawer on Citrea (a capability explicitly granted to the unprivileged attacker) or observing a broadcast payout in the mempool. Constructing the competing transaction only requires standard Bitcoin wallet operations (add inputs, set outputs, reuse the extracted `SinglePlusAnyoneCanPay` witness) and paying a mining fee; RBF or plain double-spend race dynamics (whichever conflicting tx is mined) determine the final attribution. This works against `NON_STANDARD_V3` payout transactions on any regtest/testnet/mainnet deployment with no additional preconditions.

### Recommendation
Commit the OP_RETURN (and ideally all other outputs/inputs) to the user's authorization, or otherwise cryptographically bind the attribution to the actual funder: e.g., require the operator to sign the full transaction (SIGHASH_ALL/DEFAULT covering all outputs including the OP_RETURN) with their own key over a structure that the verifiers can validate came from that operator, rather than trusting an unauthenticated OP_RETURN byte string extracted from whichever transaction happens to confirm.
