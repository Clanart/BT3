### Title
Batched clawback claim/clawback spends mark all included coins as "sent" atomically, causing legitimate coins to become stuck when one coin in the batch fails - (File: chia/wallet/clawback_manager.py)

### Summary
`ClawbackManager.spend_clawback_coins` aggregates multiple independent clawback merkle coins into a single `WalletSpendBundle`, and marks every included coin's incoming transaction as `sent` before the aggregate bundle is actually validated/accepted by the mempool. Because a Chia spend bundle is atomic (all coin spends must be individually valid or the whole bundle is rejected), a single problematic coin in the batch (e.g. one whose timelock condition is not yet satisfied, one that was already clawed back/claimed by the counterparty in a race, or one with corrupted/incompatible metadata) causes the entire aggregated bundle to fail mempool admission. However, since `increment_sent` was already called for every coin in the batch prior to knowing the outcome, all the otherwise-valid, legitimately spendable clawback coins bundled alongside the bad one are now marked as already "pending a spend" and are excluded from subsequent auto-claim attempts, effectively getting stuck.

### Finding Description
`spend_clawback_coins` iterates over the `clawback_coins` dict and, for each coin, builds a `CoinSpend` and immediately calls: [1](#0-0) 

```
coin_spend: CoinSpend = generate_clawback_spend_bundle(coin, metadata, inner_puzzle, inner_solution)
coin_spends.append(coin_spend)
# Update incoming tx to prevent double spend and mark it is pending
await self.transaction_store.increment_sent(incoming_tx.name, "", MempoolInclusionStatus.PENDING, None)
```

All these individual `CoinSpend`s are later combined into a *single* `WalletSpendBundle`: [2](#0-1) 

A spend bundle in Chia is atomic: if any one coin spend inside it fails puzzle/condition validation (e.g. `ASSERT_SECONDS_RELATIVE_FAILED` because the timelock for that particular coin hasn't matured, or the coin was already claimed/clawed back by the other party, or its metadata cannot be parsed as demonstrated by the exception handling around `parsed_metadata()`), the entire bundle is rejected by the mempool and none of the coins are actually spent on-chain.

Despite this, `increment_sent` has already been called for every coin in the batch — including the coins that would have spent successfully on their own. `auto_claim_coins` subsequently filters out any coin whose `incoming_tx.sent > 0` unless `force=True`: [3](#0-2) 

Since automated retries (`auto_claim_coins`) never pass `force=True`, and the wallet re-selects unspent clawback coins from `coin_store` on each pass, the same problematic coin can repeatedly get bundled with newly-eligible coins in subsequent auto-claim passes (or the previously-batched good coins are simply skipped forever because `sent > 0`), permanently blocking their automatic claim/clawback. Recovery is only possible if the user manually invokes the `clawback` CLI/RPC command with `--force` and manually excludes the offending coin id, which most users are unaware of.

### Impact Explanation
This is the direct on-chain analog of the reported bug class: multiple independent withdrawal-like operations (here, multiple independent clawback merkle coins for different transactions/users) are coupled into one atomic unit of work, so the failure of a single one blocks the finalization (auto-claim) of the others. Funds are not permanently lost at the consensus level (the coins remain spendable via manual `force` claim), but from the perspective of the wallet's automated flow they become stuck/unreachable, which is a direct availability/fund-recovery impact matching the "funds stuck if one withdrawal request cannot be finalized" bug class.

### Likelihood Explanation
This can be triggered whenever `auto_claim_batch_size > 1` and a batch happens to include:
- a coin that has already been claimed/clawed back by the counterparty (a natural race that occurs in normal operation), or
- a coin whose timelock has not actually elapsed due to a timestamp edge case, or
- a coin with unexpected/corrupted metadata.

Because `auto_claim_coins` batches multiple unrelated users'/transactions' clawback coins together by default, this is a realistic occurrence in normal wallet operation, not merely a theoretical edge case.

### Recommendation
Do not call `increment_sent` for a coin until the aggregate spend bundle containing it has actually been accepted into the mempool/confirmed. Alternatively, submit each clawback coin as its own independent spend bundle (or validate each coin's spendability, e.g., timelock and double-spend status, immediately before inclusion) so that failure of one coin's spend does not affect the sent/pending state of unrelated coins, and unaffected coins remain eligible for retry by `auto_claim_coins` without requiring manual `force`.

### Proof of Concept
1. Send two separate clawback transactions to the same recipient wallet with different timelocks/creation heights, resulting in two clawback merkle coins A and B tracked in the coin store.
2. Have coin A already claimed by the recipient through another path (e.g., manual claim) so it is now spent, while B remains unspent and eligible.
3. Trigger `auto_claim_coins`, which selects both A and B into the same batch (since both were previously unspent per `coin_store` and batch size ≥ 2), builds one aggregate `WalletSpendBundle`, and calls `increment_sent` for both incoming transactions before the bundle is pushed.
4. The aggregate spend bundle fails mempool validation because coin A's spend is now invalid (already spent).
5. Observe that coin B's `incoming_tx.sent` is now `>0`, so future `auto_claim_coins` passes skip coin B (per the `incoming_tx.sent > 0 and not force` check), even though coin B was independently valid and claimable — its funds are now stuck from the wallet's automated claim flow until a manual `--force` claim is issued.
