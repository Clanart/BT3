Based on my investigation, I found a genuine analog of the Stader `poolIdArrayIndexForExcessDeposit` bug class in `IntrinsicIntents._fillSameChain`.

### Title
Solver can steal first-fill surplus share on same-chain orders by front-running with a dust partial fill - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The Stader bug let an attacker cheaply nudge a shared "next allocation" pointer (`poolIdArrayIndexForExcessDeposit`) forward with a trivial deposit, redirecting the *next* round's benefit to their own validator regardless of whether the underlying condition (sufficient balance) was actually met. The local analog is the `alreadyFilled == 0` gate in `_fillSameChain` that decides who is entitled to the overpayment/"surplus" split on a partial-fill order: whichever solver's transaction is first to touch `_partialFills[commitment][outputToken]` permanently consumes the "first fill" privilege for that output token, even with a negligible amount, exactly like rolling the Stader index forward with 1 wei.

### Finding Description
`_fillSameChain` computes surplus/dust only "on the first fill of each output token pair", gated by:
```solidity
if (alreadyFilled == 0 && solverAmount > totalRequired) {
    fillAmount = totalRequired;
    uint256 dust = solverAmount - totalRequired;
    ...
    protocolShare = (dust * _params.surplusShareBps) / 10_000;
    beneficiaryShare = dust - protocolShare;
}
``` [1](#0-0) 

`alreadyFilled` is read straight from persistent state `_partialFills[commitment][outputToken]` [2](#0-1) , and updated unconditionally after every fill regardless of size:
```solidity
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;
``` [3](#0-2) 

This mirrors the Stader bug's structure precisely: a shared piece of state (`poolIdArrayIndexForExcessDeposit` / `_partialFills[...]`) is advanced on *every* call irrespective of whether the call actually satisfies the invariant the state is meant to gate (sufficient balance to fund a validator / a genuine, economically meaningful fill). Because `fillOrder` is a public entrypoint open to any solver (same-chain orders have no `solverSelection` binding requirement enforced before the loop unless the order enables it), an attacker can front-run the legitimate solver's fill transaction with `options.outputs[i].amount = 1` wei (satisfying `solverAmount != 0`, and `remaining = totalRequired > 0`), which sets `_partialFills[commitment][outputToken] = 1` and permanently flips `alreadyFilled != 0` for that output token. The legitimate solver's subsequent (and only real) fill — even if it substantially overpays — now always falls into the `else` branch (`fillAmount = solverAmount > remaining ? remaining : solverAmount`), so `beneficiaryShare`/`protocolShare` are never computed and the surplus entitlement for that token pair is permanently forfeited for the true filler, regardless of the real economics.

### Impact Explanation
This is a value-diversion path against public state on a live-funds contract: the surplus split (`surplusShareBps`) that the order beneficiary and protocol are entitled to when a solver overpays can be nullified by any unprivileged party for a dust cost (a 1-wei fill), by racing to be the first partial fill on a token pair. It does not steal escrowed principal directly, but it manipulates the fee/surplus-distribution logic exactly like Stader's judged Medium-severity finding — "leak value with a hypothetical attack path with stated assumptions, but external requirements" — since the attacker gains no principal but denies the legitimate solver/protocol/beneficiary their intended surplus share, and could combine it with sandwiching to capture that surplus for themselves in a separate low-value fill of their own.

### Likelihood Explanation
The precondition is cheap and requires no privileged role, relayer, or admin — only mempool visibility of a pending `fillOrder` call and a 1-wei-output transaction of their own, i.e. a plain front-run by an unprivileged actor, matching the Hyperbridge Impact Gate's accepted category (transaction manipulation / logic attack) rather than the excluded "front-run-only" category, because the manipulation targets a persistent shared-state gate (`_partialFills` "first fill" flag), not merely transaction ordering for its own sake.

### Recommendation
Do not key the surplus eligibility purely off `alreadyFilled == 0`. Either: (1) require a minimum fill ratio (e.g., `fillAmount >= totalRequired * minFillBps / 10_000`) before a fill can be treated as the "first" fill eligible for surplus accounting, or (2) track surplus eligibility with an explicit boolean that is only set once a fill meaningfully progresses the order (mirroring Stader's fix of adding a `require(findValidator)` guard before mutating shared round-state), so a dust-sized fill cannot consume the first-fill surplus slot.

### Proof of Concept
1. User places a same-chain order with `output.assets[i].amount = 1000e18` DAI and no `solverSelection` restriction (or with a session key an attacker can front-run before selection).
2. Legitimate solver A prepares to fill with `solverAmount = 1100e18` (overpaying, expecting `dust = 100e18` split via `surplusShareBps`).
3. Attacker sees A's pending tx, and submits `fillOrder` first with `options.outputs[i].amount = 1` wei. This satisfies `remaining > 0 && solverAmount != 0`, sets `_partialFills[commitment][outputToken] = 1`, and takes the `else` branch (`fillAmount = 1`), incurring negligible cost.
4. When A's transaction lands, `alreadyFilled = 1 != 0`, so the `if (alreadyFilled == 0 && solverAmount > totalRequired)` surplus branch at [4](#0-3)  is skipped entirely; A's fill falls into the `else` branch and is clamped to `remaining` (999.999...999e18), meaning A's 1100e18 offer is silently truncated with no surplus computed/distributed to protocol or beneficiary — the intended fee-sharing invariant is defeated for a 1-wei cost to the attacker.
