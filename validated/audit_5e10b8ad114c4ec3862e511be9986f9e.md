### Title
Double-Application of Bank Balance Events Across Recursive/Nested Precompile Calls Causes StateDB Balance Duplication - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
The read-only-reentrancy pattern in the external Hanji report ("state is read/derived from data that is stale/mutated across a reentrant call boundary") maps onto Cosmos EVM's precompile-to-StateDB balance synchronization mechanism. `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` records a slice offset (`prevEventsLen`) into the shared `sdk.Context` event log and, after the precompile's native action executes, replays every bank `coin_spent`/`coin_received`/fractional-balance event emitted since that offset into the EVM `StateDB` via `AddBalance`/`SubBalance`. When a precompile call recursively (or via nested/re-entrant EVM calls) triggers another precompile call before the outer one finishes, both handlers read from the *same, ever-growing* `ctx.EventManager()` event log without truncating or marking already-consumed events. The inner call's `AfterBalanceChange` applies the inner-call events to `StateDB`, but the outer call's later `AfterBalanceChange` — because its `prevEventsLen` was captured *before* the inner call ran — re-processes the entire event window including the events the inner call already applied, effectively crediting/debiting the same bank transfer twice against the EVM StateDB.

### Finding Description
The base precompile execution path in `precompiles/common/precompile.go` (`runNativeAction`) instantiates a fresh `BalanceHandler` per call and does: [1](#0-0) 

Each call captures `prevEventsLen := len(ctx.EventManager().Events())` before running `action(ctx)`, then diffs `events[prevEventsLen:]` after the action completes: [2](#0-1) [3](#0-2) 

The `sdk.Context`'s `EventManager` is shared across the whole EVM call stack (it is not swapped out between nested precompile invocations), and it is append-only — events are never removed or marked consumed. If, during `action(ctx)` of an *outer* precompile call, a *nested* precompile call occurs (recursive contract logic calling back into a precompile, e.g. an ERC20/staking/distribution precompile whose native action triggers a bank transfer that a contract callback then re-enters), the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pair will already consume and apply its slice of events to `StateDB`. When control returns to the outer call and it finishes, the outer `AfterBalanceChange` computes `events[outerPrevEventsLen:]`, a range that still contains the inner call's already-applied events (since `outerPrevEventsLen < innerPrevEventsLen`), causing those `CoinSpent`/`CoinReceived`/fractional-balance deltas to be applied to `StateDB` a second time.

This is precisely analogous to the reported read-only-reentrancy class: a balance-accounting update path derives its result from external/shared mutable state (`ctx.EventManager().Events()`) that can be mutated mid-flight by a reentrant call, and the accounting logic has no guard against replaying already-applied deltas.

This exact hazard is acknowledged by an existing regression test in the repository, explicitly documenting "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB": [4](#0-3) 

### Impact Explanation
If reachable by an unprivileged EOA, this results in duplicated crediting of `StateDB` balances (EVM-visible balance) relative to the true `x/bank` balance for accounts involved in nested precompile-driven bank transfers — an unauthorized duplication/inflation of spendable EVM balance without a corresponding native-side mint, which is exactly the "unauthorized duplication ... irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact class. A contract that intentionally triggers a nested/recursive precompile call sequence (e.g., staking/distribution/erc20/gov precompiles whose native handlers can invoke bank transfers and which can be re-entered via callback contracts, as seen in the recursive-precompile test fixtures in `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol` and `evmd/tests/integration/balance_handler/`) could inflate its own or another account's `StateDB` balance beyond what the underlying bank ledger holds, enabling theft/extraction of value once that inflated EVM balance is spent (e.g., transferred out via EVM `transfer`/precompile calls) before the discrepancy is reconciled.

### Likelihood Explanation
The precompile framework (`RunNativeAction`) is invoked for every stateful precompile call (erc20, staking, distribution, gov, slashing, ics20), and several already exist with legitimate recursive/callback patterns (delegate → claimRewards, contract callbacks during `_beforeTokenTransfer`, etc., as seen in `ERC20RecursiveNonRevertingPrecompileCall.sol`/`ERC20RecursiveRevertingPrecompileCall.sol`). The presence of a dedicated regression test (`balance_handler_test.go`) purpose-built to reproduce this exact recursive-call/`prevEventsLen` desync scenario strongly indicates the root cause is real and reachable through ordinary, unprivileged contract-driven transaction flow (a user deploying/calling a contract that performs nested precompile calls), not a privileged or externally-mediated condition.

### Recommendation
Do not rely on a shared, append-only, cross-call `EventManager` slice offset to demarcate "events belonging to this call." Instead:
- Use a per-call isolated event manager/context (e.g., wrap `ctx` with a fresh `sdk.NewEventManager()` for the duration of each `action(ctx)` call) so nested calls cannot see or double-consume outer-call events, then merge/emit the isolated events into the parent context only after successful, deduplicated processing.
- Alternatively, after `AfterBalanceChange` finishes processing a window of events, mark/truncate or otherwise flag those events as consumed (e.g., re-slice/replace the events in the context, or track a global consumed-index) so an outer call cannot re-process events already applied by a nested call.
- Add an explicit reentrancy guard/counter around `runNativeAction` to detect and correctly nest `prevEventsLen` bookkeeping (e.g., maintain a stack of offsets rather than a single scalar per handler, ensuring the outer handler resumes diffing from where the inner handler left off).

### Proof of Concept
Deploy a contract that:
1. Calls a stateful precompile (e.g., the distribution or erc20 precompile) whose native action performs a bank `SendCoins`/`MintCoins` producing `coin_spent`/`coin_received` events.
2. From within that same EVM call (before it returns to the ante/EVM caller), triggers a second, nested precompile call (recursively, via a callback hook such as `_beforeTokenTransfer`/`claimRewards`, matching the pattern already present in `contracts/solidity/ERC20RecursiveNonRevertingPrecompileCall.sol`) that also causes bank events to be emitted and consumed by its own `BeforeBalanceChange`/`AfterBalanceChange` pair.
3. After both calls return, compare `stateDB.GetBalance(receiver)` (EVM-visible) against the actual `x/bank` `GetBalance` for the same address — the existing `evmd/tests/integration/balance_handler/balance_handler_test.go` (`TestRecursivePrecompileCallsWithDebugPrecompile`) already exercises this recursive-call scenario and can be extended/instrumented to assert on the resulting balance divergence between `StateDB` and the bank keeper. func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
