### Title
Panic on unbounded participant indexes in PedPoP blame evaluation enables remote DoS - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs) / [File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The µD3TN bug class — a NULL-style dereference triggered by a destination identifier that doesn't resolve to a known entity — maps directly onto PedPoP's blame path. `BlameMachine::blame_internal` and `Decryption::decrypt_with_proof` index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `Participant` values supplied by the accuser, without checking they exist in the map. `Participant` is any nonzero `u16`, so any out-of-range index (> n, or simply a participant that never registered) causes a HashMap-index panic — a reliable, remotely triggerable crash of the evaluating node.

### Finding Description
`Participant::new` only rejects zero; any value `1 ..= u16::MAX` parses as a valid identifier [1](#0-0) . The blame API takes `sender` and `recipient` as free parameters:

- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` [2](#0-1) .
- Inside `decrypt_with_proof`, when a proof is present, the decryptor's encryption key is fetched by unchecked indexing: `self.enc_keys[&decryptor]` [3](#0-2) . `enc_keys` only contains entries for participants whose `EncryptionKeyMessage` was registered [4](#0-3) .
- Independently, `blame_internal` does `self.commitments[&sender]` when evaluating share-verification statements [5](#0-4) . `commitments` is populated only for `1 ..= n` (in `AdditionalBlameMachine::new`) or for actual DKG participants [6](#0-5) .
- The documentation for `AdditionalBlameMachine::new` even warns that invalid inputs "may cause … panics" — but `blame()` takes attacker-influenced indexes after construction, which is not covered by that caveat [7](#0-6) .

On the wire, blame accusations deserialize `accuser`/`faulty` as raw `Participant`s with only the nonzero check [8](#0-7) , so a value like `Participant(n + 1)` reaches the blame evaluator unfiltered.

### Impact Explanation
Any node evaluating a blame proof (a DKG participant via `BlameMachine::blame`, or a non-member coordinator node via `AdditionalBlameMachine::blame`) panics when `recipient`/`decryptor` ≥ n+1 (with `proof: Some(..)`) or when `sender` is out of range (unconditionally, at `self.commitments[&sender]`). A panic in consensus-adjacent code aborts the evaluating process — a remotely triggered, reliable denial of service, matching the "unprivileged input → guaranteed crash" shape of CVE-2025-8183. Because the panic occurs deterministically for every node that evaluates the malicious accusation, it can halt the DKG/blame-resolution round entirely.

### Likelihood Explanation
`sender`/`recipient` are derived from accusation data an unprivileged party can inject (e.g., an `InvalidDkgShare` transaction whose participant fields are only validated as nonzero). No cryptographic work, collusion, or race is required — a single malformed accusation referencing a nonexistent participant index crashes every evaluator. The only precondition is that blame evaluation runs, which is the documented failure-handling path of the DKG.

### Recommendation
Validate `sender` and `recipient` against the registered sets before indexing: return a `PedPoPError` (or a defined `Participant` verdict) if `!self.commitments.contains_key(&sender)` / `!self.enc_keys.contains_key(&decryptor)` instead of using `map[&key]`. Also bound-check `recipient`/`sender` ≤ `params.n` at the `blame`/`AdditionalBlameMachine::blame` entry point, mirroring the `InvalidParticipant` check already done in `ThresholdKeys::new`/`view` [9](#0-8) . Deserialization of accusation transactions should additionally reject participant indexes > n.

### Proof of Concept
```rust
// Any curve; assumes a DKG context with n participants has completed or an
// AdditionalBlameMachine was built from commitment_msgs for 1..=n.
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs).unwrap();

// Attacker-controlled accusation bytes: sender/recipient parsed as Participant(n + 1),
// which is nonzero and therefore accepted by Participant::new.
let sender = Participant::new(n + 1).unwrap();
let recipient = Participant::new(n + 1).unwrap();
let msg: EncryptedMessage<Ristretto, SecretShare<_>> = /* any well-formed message, e.g. relayed */;

// Panics at `self.enc_keys[&decryptor]` (encryption.rs:388) when proof is Some,
// or at `self.commitments[&sender]` (lib.rs:599) on any out-of-range sender.
machine.blame(sender, recipient, msg, Some(proof));
```

Uncertainty note: I verified the panic sites and the `Participant` validation gap directly in the in-scope crates; the exact on-chain path that forwards `accuser`/`faulty` into `blame()` lives in the coordinator (out of the crypto scope), but the panic is a property of the in-scope library API itself, which accepts and indexes on attacker-controlled identifiers without bounds checks.
