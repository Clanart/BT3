### Title
Unbounded recursion in nested `AccountKeyRoleBased` RLP decoding causes stack-exhaustion DoS - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
CVE-2017-15595 describes unbounded recursion/stack consumption in Xen caused by allowing arbitrarily deep page-table stacking supplied by an unprivileged guest. The analogous bug class — attacker-controlled unbounded recursive structure parsing before any depth/composite-type validation — is reachable in Kaia through `AccountKeyRoleBased` RLP decoding, which recursively decodes nested `AccountKey` values without any depth limit, and the composite-type rejection check only runs *after* the full recursive decode has already completed.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of independently RLP-encoded sub-keys and, for each element, recursively decodes an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a `keyType` byte, allocates the corresponding `AccountKey` via `NewAccountKey`, and then decodes into it — and `NewAccountKey` accepts `AccountKeyTypeRoleBased` as a valid type with no restriction on nesting depth: [2](#0-1) [3](#0-2) 

If the decoded sub-key type is itself `AccountKeyTypeRoleBased`, decoding recurses into `AccountKeyRoleBased.DecodeRLP` again — with no depth counter, size accounting, or recursion guard anywhere in this decode path. The only defense against nested `RoleBased` keys — `CheckInstallable`/`CheckUpdatable` rejecting composite sub-keys with `kerrors.ErrNestedCompositeType` — is invoked strictly *after* the entire RLP structure has already been fully decoded: [4](#0-3) 

This mirrors the Xen bug class exactly: validation/limiting logic exists, but it is checked only after the vulnerable recursive parsing step has already consumed stack, so a sufficiently deep input can crash the process before rejection logic ever runs.

This decode path is reached from an ordinary, unprivileged `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate...` transaction: `fromSerializable` calls `rlp.DecodeBytes` on the attacker-supplied `Key` bytes directly: [5](#0-4) 

and more generally, any `Transaction.DecodeRLP`/`UnmarshalBinary` call (triggered by `eth_sendRawTransaction`, p2p tx propagation, or block import) will trigger this recursive account-key decode for account-update transaction types: [6](#0-5) 

### Impact Explanation
An attacker who can submit or relay a single crafted `AccountUpdate`-family transaction (via public RPC `eth_sendRawTransaction`, gossip, or transaction pool submission) can force any node that decodes it — including the mempool/RPC-serving node and, if propagated, other full nodes — to recurse arbitrarily deep while unmarshalling the `Key` field, before any semantic validation (`ErrNestedCompositeType`, `MaxTxDataSize`, signature checks) is applied. This can exhaust the goroutine stack and crash the node process (denial of service), which is a High-severity availability impact consistent with the CVE's "denial of service ... stack consumption ... hypervisor crash" characterization, scaled to a Kaia node/validator crash.

### Likelihood Explanation
The size/byte overhead needed per recursion level is small (one `keyType` byte plus RLP list/byte-string framing per nested `AccountKeySerializer`), so a modest-size transaction payload can encode many thousands of nesting levels. Constructing this transaction requires no special privileges — only a valid signature format is required to pass initial `SanityCheckSignatures`, and the payload itself does not need to be semantically valid since the crash occurs during decode, prior to signature/threshold/nesting checks.

### Recommendation
Enforce a maximum nesting/recursion depth for `AccountKey` decoding (both RLP and JSON paths) before or during decode — e.g., pass and check a depth counter through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP`, and immediately reject `AccountKeyTypeRoleBased` sub-keys nested inside a `RoleBased` key at decode time rather than only in the later `CheckInstallable`/`CheckUpdatable` steps. Additionally consider bounding total decode work via `rlp.Stream` size/depth limits before allocating and recursing into nested types.

### Proof of Concept
Conceptually (exact byte-level PoC would need to be generated and verified with a Devin session that has code-execution access, which is outside the scope of this read-only analysis):
1. Construct an `AccountKeySerializer` RLP encoding with `keyType = AccountKeyTypeRoleBased`.
2. Encode its list value as `[[keyType=RoleBased, [[keyType=RoleBased, [...]]]]]`, nesting thousands of times, each level being a two/three-byte RLP wrapper.
3. Set this blob as the `Key` field of a `TxTypeAccountUpdate` transaction and sign it validly (`SanityCheckSignatures` only checks signature format/shape, not the key content).
4. Submit via `eth_sendRawTransaction` or p2p gossip; the receiving node calls `Transaction.DecodeRLP` → `TxInternalDataAccountUpdate.fromSerializable` → `accountkey.AccountKeySerializer.DecodeRLP` → recursively `AccountKeyRoleBased.DecodeRLP`, consuming stack proportional to nesting depth before any nested-composite-type check occurs.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}

func NewAccountKey(t AccountKeyType) (AccountKey, error) {
	switch t {
	case AccountKeyTypeNil:
		return NewAccountKeyNil(), nil
	case AccountKeyTypeLegacy:
		return NewAccountKeyLegacy(), nil
	case AccountKeyTypePublic:
		return NewAccountKeyPublic(), nil
	case AccountKeyTypeFail:
		return NewAccountKeyFail(), nil
	case AccountKeyTypeWeightedMultiSig:
		return NewAccountKeyWeightedMultiSig(), nil
	case AccountKeyTypeRoleBased:
		return NewAccountKeyRoleBased(), nil
	}

	return nil, errUndefinedAccountKeyType
}
