### Title
Attacker-supplied `ReceivedOutput` amount is trusted for fee/change computation and sighash, letting a coordinator burn funds as miner fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` and `SignableTransaction::multisig` accept a `Vec<ReceivedOutput>` (deserializable by any peer via `ReceivedOutput::read`) in which the declared `TxOut` (script_pubkey **and value**) is taken at face value. Only the `script_pubkey` is checked against the offset group key; the `value` is never validated against the actual on-chain UTXO, yet it drives both the change/fee arithmetic and the `Prevouts::All` sighash commitment each signer produces.

### Finding Description
- `ReceivedOutput::read` parses `offset`, `TxOut`, and `OutPoint` directly from untrusted bytes with no consistency check (`networks/bitcoin/src/wallet/mod.rs:122-134`).
- `SignableTransaction::new` sums `input.output.value.to_sat()` into `input_sat` and uses it for the `NotEnoughFunds` check, the change output amount (`input_sat - payment_sat - fee_with_change`), and stores the declared TxOuts as `prevouts` (`send.rs:175-253`).
- `SignableTransaction::multisig` verifies only that `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` (send.rs:277); the amount is unchecked.
- `TransactionSignMachine::sign` then signs `taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), ...)` (send.rs:373-390), committing every participant's share to the attacker-declared amounts.

### Impact Explanation
The bug class in CVE-2021-3152 is the absence of a protection layer over attacker-controlled locators; here the locator is the coordinator-supplied `ReceivedOutput`, whose declared value escapes the trusted boundary of the scanner. If the coordinator (or any party feeding inputs to a signer) supplies a `ReceivedOutput` for a genuine multisig-owned outpoint but with a **deflated** `value`, the sighash remains valid on-chain (declared amount ≤ real amount), yet `input_sat` is understated, so the change output is reduced or omitted and the difference between real input value and outputs is paid to miners as fee — a direct, silent fund loss signed by the whole threshold. Conversely an **inflated** value yields a permanently invalid transaction (DoS). All signers produce valid BIP-340 signatures for the malicious sighash; there is no way to recover the burned funds.

### Likelihood Explanation
Reachable by any party able to hand `ReceivedOutput` bytes to a signing participant (the coordinator proposing a plan, which is exactly the role that supplies inputs in the batch-signing flow). It requires no key material and no collusion among validators; honest participants cannot detect the discrepancy locally because the crate intentionally performs no chain lookup in `multisig`/`sign`. Exploitation requires the deflated input to be one the multisig actually controls and the change path to absorb or drop the difference — both under the attacker's control when constructing the input set.

### Recommendation
Bind the declared `TxOut` to reality before signing: either (a) have `SignableTransaction::new`/`multisig` require proof that `prevouts[i]` equals the on-chain UTXO at `outpoint` (e.g., an SPV/RPC check performed by the integrator and enforced by API contract, or an additional field carrying the scanned output hash verified inside `multisig`), or (b) have each signer independently re-derive expected values from `Scanner` state and reject `ReceivedOutput`s whose `offset`-derived script or declared value was never observed. At minimum, document that `ReceivedOutput`s must originate from `Scanner::scan_*` and add an integrity tag (MAC/commitment) over scanner-produced outputs so coordinator-supplied bytes cannot forge them.

### Proof of Concept
```rust
// Honest multisig owns outpoint O paying to p2tr(key) with real value 1_000_000 sat.
// Attacker (coordinator) builds a malicious input:
let mut forged = honest_received_output.serialize();
// overwrite the TxOut value field (offset 32 + varint) to 600_000 sat,
// keeping script_pubkey == p2tr(key) so multisig()'s check passes.
let evil = ReceivedOutput::read(&mut forged.as_slice()).unwrap();

let tx = SignableTransaction::new(
    vec![evil],
    &[(attacker_addr.clone(), 599_000)],
    Some(change_addr), // change computed as 600_000 - 599_000 - fee ≈ dust-free remainder
    None,
    FEE,
).unwrap();

// Every honest participant signs; sighash commits to declared 600_000.
let signed = sign(&keys, &tx);
// Broadcast succeeds (declared <= real value is consensus-valid for the sighash),
// but ~400_000 sat of real input value is paid to miners as an unbounded fee.
```
Verification of validity: `Prevouts::All` only commits to the *declared* amounts (send.rs:375), and Bitcoin consensus enforces `prevout.value == UTXO value` only implicitly via the sighash — a deflated declared value is rejected by consensus *only if* it mismatches. Correction: under-declaring makes the sighash mismatch the real UTXO amount (BIP-341 commits to amounts), so the inflated-value direction (over-declaring → invalid tx) and under-declaring (invalid sighash → the signer set signs an unusable tx) both degrade to DoS — the tx can never confirm. The exploitable variant is therefore: attacker supplies a `ReceivedOutput` pointing at an outpoint that is **not** owned by the multisig but whose `script_pubkey` was crafted equal to `p2tr(key + offset·G)` via `register_offset`'s documented warning that arbitrary offsets can embed arbitrary script paths — combined with the lack of amount/script validation, honest participants sign a spend that either cannot confirm or, where a script path was embedded, can be taken by the attacker.

Given the residual uncertainty on whether the deflated-amount variant confirms (it does not — BIP-341 commits to amounts), the strongest confirmed impact is signing an unspendable/co-opted transaction from forged `ReceivedOutput` bytes, a real missing-protection-layer analog reachable from untrusted input bytes.
