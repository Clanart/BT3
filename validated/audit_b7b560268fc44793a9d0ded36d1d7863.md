### Title
Precompile signature verification cost is charged per declared signature count only, independent of `message_data_size`, while actual work is O(num_signatures × message_size) and consumes zero VM compute units - ([File: precompiles/src/ed25519.rs, precompiles/src/secp256k1.rs, precompiles/src/secp256r1.rs, cost-model/src/cost_model.rs])

### Summary
Precompile instructions (`ed25519`, `secp256k1`, `secp256r1`) are executed via `process_precompile` in `program-runtime/src/invoke_context.rs`, which bypasses normal VM compute-unit metering entirely — confirmed by the test `test_builtin_ix_precompiled` which asserts `"VM Execution: consume 0 from CU-meter"` for a precompile instruction [1](#0-0) . The only compute accounting applied to these instructions is a flat per-signature constant in `cost-model/src/cost_model.rs::get_signature_cost`, which multiplies the declared `num_signatures` (read from the first byte of the instruction data) by a fixed cost (`ED25519_VERIFY_STRICT_COST`, `SECP256K1_VERIFY_COST`, `SECP256R1_VERIFY_COST`) with no dependence on `message_data_size` [2](#0-1) [3](#0-2) [4](#0-3) . Meanwhile, each of the three `verify()` implementations loops `num_signatures` times, and on each iteration hashes/processes a message slice of up to `message_data_size` (a `u16`, max 65,535 bytes) that can be pulled from any instruction in the transaction (`message_instruction_index`) — including the precompile instruction's own data, meaning it can be reused identically across every signature slot [5](#0-4) [6](#0-5) [7](#0-6) .

### Finding Description
`verify_if_precompile` (`precompiles/src/lib.rs:99-119`) is invoked once per precompile-owned top-level instruction and calls `Precompile::verify`, which dispatches to `ed25519::verify`, `secp256k1::verify`, or `secp256r1::verify` [8](#0-7) . Inside the runtime, this happens through `InvokeContext::process_precompile`, which pushes/pops the instruction stack but never calls the compute-meter consumption path used for BPF/builtin native programs (`declare_process_instruction`-driven programs charge CUs via `consume_checked` inside `process_instruction`) [9](#0-8) . This is corroborated by the scheduler cost-adjustment test explicitly stating and asserting that VM execution of a precompiled instruction "consume[s] 0 from CU-meter" [10](#0-9) .

The transaction-level cost model instead statically estimates the cost of these instructions using `get_signature_cost`, which sums `num_secp256k1_instruction_signatures * SECP256K1_VERIFY_COST`, `num_ed25519_instruction_signatures * ED25519_VERIFY_STRICT_COST`, and `num_secp256r1_instruction_signatures * SECP256R1_VERIFY_COST` [2](#0-1) . The signature count itself is derived solely from `data[0]` of the precompile instruction (`get_num_signatures_in_instruction`), with no factor for `message_data_size` [4](#0-3) .

However, the real cost of each `verify()` call is `O(num_signatures × message_data_size)`:
- `ed25519::verify` calls `publickey.verify_strict(message, &signature)` for each of `num_signatures` (up to 255) entries, where `message` is a slice of up to `u16::MAX` bytes sourced via `get_data_slice`, and `message_instruction_index` can equal the precompile instruction itself (`u16::MAX` sentinel) or any other instruction index, permitting the same message bytes to be reused across all `num_signatures` entries [11](#0-10) .
- `secp256k1::verify` computes a full Keccak-256 hash over `message_slice` (`solana_keccak_hasher::hash`) for each of up to 255 signature entries [12](#0-11) .
- `secp256r1::verify` streams the entire message through an OpenSSL SHA-256 `Verifier` for each of up to 8 signature entries [13](#0-12) .

The `benches/*_instructions.rs` files explicitly benchmark this scaling behavior at `message_length = u16::MAX - required_extra_space`, confirming this is a known, exercised code path whose cost is meant to be quantified but is not reflected back into the on-chain fee/CU charge model [14](#0-13) [15](#0-14) . Because the flat per-signature `SIGNATURE_COST`-family constants in `block_cost_limits.rs` are the *only* charge levied for a precompile instruction (given the 0-CU VM execution), an attacker who maximizes `message_data_size` while keeping `num_signatures` at its cap pays exactly the same cost model charge as one with `message_data_size = 0`, despite the verification work scaling linearly with message size.

### Impact Explanation
This falls under "materially underpriced compute" (CPU-time DoS via disproportionately expensive precompile verification relative to charged cost). Since the cost model's signature-cost component is what gates block packing/scheduling limits (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`) and precompiles consume zero real VM compute units, a validator can be made to spend real wall-clock CPU time proportional to `num_signatures × message_data_size` (bounded per-instruction by `u16::MAX` for message size, and per-transaction by `num_signatures` caps of 255 for ed25519/secp256k1, 8 for secp256r1) while the leader's cost accounting and the transaction's declared/charged cost do not scale with the message size at all.

### Likelihood Explanation
Preconditions are met by an unprivileged user: constructing a transaction with a single precompile instruction, setting `num_signatures` to its maximum, and pointing every `SignatureOffsets`/`SecpSignatureOffsets` entry's `message_instruction_index`/`message_data_offset`/`message_data_size` at the same message bytes is fully attacker-controlled instruction data, requiring no special privileges — only that the attacker supply `num_signatures` valid signatures over that shared message (trivially computable off-chain for ed25519/secp256k1/secp256r1). This is repeatable per-transaction with no cluster-state dependency.

Note: the practical worst-case message size achievable is constrained by the maximum serialized transaction size the network accepts (I could not confirm the exact enforced transaction/packet size limit for the SVM/TPU ingestion path in this session, e.g., whether it is the classic 1232-byte MTU-based `PACKET_DATA_SIZE` or a larger QUIC-permitted size). This bounds the severity of the attack but does not eliminate the underlying pricing flaw: within whatever the enforced transaction size ceiling is, the attacker can still reuse the same message bytes across up to 255 (or 8) signature slots at zero marginal cost-model charge, meaning the actual/charged cost ratio is materially non-linear regardless of the absolute ceiling.

### Recommendation
Incorporate `message_data_size` (summed or maximized across all signature offset entries) into the precompile signature cost calculation in `cost-model/src/cost_model.rs::get_signature_cost`, e.g., by parsing each precompile instruction's offsets and adding a per-byte hashing/verification cost term (similar to `INSTRUCTION_DATA_BYTES_COST`) multiplied by `num_signatures`, rather than charging a flat per-signature constant. Alternatively, meter precompile execution through the standard compute-unit consumption path in `InvokeContext::process_precompile` so actual CPU work is charged against the transaction's compute budget like any other instruction.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
