### Title
Divergent EVM host/host-manager addresses across `EvmHosts` and `HostParams.host_manager` storage in `pallet-host-executive` - (File: `modules/pallets/host-executive/src/lib.rs`)

### Summary
`pallet-host-executive` maintains the authoritative EVM-side host binding for every connected chain in **two independent storage items** that are updated by two different, uncoordinated extrinsics. `EvmHosts<T>` (a `StateMachine → H160` map) is written only by `update_evm_hosts`, while the `host_manager` address consumed for outbound cross-chain governance lives inside `HostParams<T>` (`HostParam::EvmHostParam.host_manager`), written only by `set_host_params`/`update_host_params`. Nothing in the pallet enforces that these two records agree, which mirrors the exact bug class in the external report: the same authoritative address is duplicated in two places, and updating one without the other silently desynchronizes the protocol's trust anchor for a chain.

### Finding Description
`update_host_params` dispatches its governance payload to the address taken from the `HostParams` entry, not from `EvmHosts`: [1](#0-0) 

Meanwhile, the "canonical" EVM host contract address per state machine — the value consumed elsewhere in the ISMP state-machine/consensus verification code (`modules/ismp/state-machines/evm/src/lib.rs`, `tendermint.rs`, `substrate_evm.rs`) — is stored and updated completely separately: [2](#0-1) [3](#0-2) 

Both call paths are guarded only by `T::HostExecutiveOrigin::ensure_origin(origin)` and have no cross-check against each other: [4](#0-3) 

This is structurally identical to the `IsleGlobal`/`Receivable` governor duplication: one logical value (“the trusted EVM host contract for chain X”) is stored redundantly — once as the address that receives cross-chain governance dispatches (`HostParams.host_manager`), and once as the address treated as the chain's canonical `IsmpHost` for state/consensus verification purposes (`EvmHosts`). A single `update_evm_hosts` call (e.g. following a legitimate host redeployment) updates only the latter; the operator must remember to separately call `update_host_params`/`set_host_params` to update `host_manager` to match, and vice versa. There is no invariant check anywhere in the pallet that `HostParams::<T>::get(sm).host_manager == EvmHosts::<T>::get(sm)`.

### Impact Explanation
If the two records diverge (e.g., after a host redeploy where only one of the two calls is made — an easy and plausible operational mistake given they are two separate, unlinked extrinsics with no read of each other's storage):
- `update_host_params` will keep dispatching `SetHostParam`/`Withdraw` governance messages to a stale `host_manager` address that no longer corresponds to the chain's actual, currently-trusted `EvmHost` contract in `EvmHosts`.
- Verification logic elsewhere in the ISMP stack that treats `EvmHosts` as the canonical per-chain host reference will continue trusting an address that is out of sync with the address governance actually believes it is managing.
- This directly threatens the "cross-chain admin or host-management effects must not be reachable through … wrong module bindings" pivot: governance-authorized state (revenue withdrawal target, host-param updates such as fee token, consensus client, unstaking/challenge period) can be routed to or validated against the wrong contract, producing unauthorized execution / misrouted funds or acceptance of state from a contract that is no longer the operationally intended one.

### Likelihood Explanation
The divergence itself only arises from a legitimate `HostExecutiveOrigin`-gated operation being applied incompletely (updating one map but not the other), exactly as in the original report (an operational/human-error trigger, not a malicious actor). However, unlike the original Isle Global case, once the split occurs it is silently exploitable through the pallet's normal, unprivileged execution path (`update_host_params` dispatch and any downstream consumer of `EvmHosts`) — no further privileged or malicious action is required to trigger the resulting misrouting. Given the two calls (`update_evm_hosts` and `update_host_params`) are separate extrinsics with no shared validation, this is a realistic operational hazard for any host redeployment or address rotation.

### Recommendation
Store the EVM host/host-manager address for a given `StateMachine` in exactly one place, and have the other consumer read from it (e.g., derive the governance dispatch target for `update_host_params` from `EvmHosts::<T>::get(state_machine)` rather than from a separately-set `HostParams.host_manager` field), or add an explicit consistency check in both `update_evm_hosts` and `update_host_params` that rejects the call if it would leave the two records mismatched.

### Proof of Concept
1. Governance calls `set_host_params`/`update_host_params` for `StateMachine::Evm(X)` with `HostParam::EvmHostParam { host_manager: H_old, .. }`, and separately (at an earlier point) `update_evm_hosts` set `EvmHosts[Evm(X)] = H_old` as well — the two agree initially. [4](#0-3) [3](#0-2) 
2. The EVM host contract for chain X is redeployed at a new address `H_new` (e.g. consensus-client rotation, per `evm/script/DeployHostUpdates.s.sol`). The operator calls `update_evm_hosts` to set `EvmHosts[Evm(X)] = H_new`, but forgets (or the second call is delayed/misses in a multi-step governance queue) to call `update_host_params` to update the embedded `host_manager` field in `HostParams`.
3. Any subsequent `update_host_params` call now dispatches `SetHostParam`/`Withdraw` governance messages to `to: H_old`, while any code path that trusts `EvmHosts` as the canonical host for chain X now references `H_new`. Depending on which downstream consumer is authoritative for a given check, this produces either governance messages arriving at a stale/incorrect contract, or state/consensus verification trusting a contract address that governance no longer believes is authoritative — a direct violation of the "cross-chain admin/host-management effects must not be reachable through wrong module bindings" invariant.

Note: I was unable to fully trace, within the available tool budget, every downstream consumer of `EvmHosts` in `modules/ismp/state-machines/evm/src/lib.rs`, `tendermint.rs`, and `substrate_evm.rs` to confirm the precise verification role that address plays (e.g., whether it gates state-commitment acceptance directly). Confirming that exact consumption path would strengthen or narrow the severity assessment above; a Devin session with full repository access would be needed to trace those call sites in depth.

		/// Set or update the addresses for the specified evm hosts
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(2)]
		pub fn update_evm_hosts(
			origin: OriginFor<T>,
			params: BTreeMap<StateMachine, H160>,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			for (state_machine, address) in params {
				let old = EvmHosts::<T>::get(&state_machine);
				EvmHosts::<T>::insert(state_machine.clone(), address);
				if let Some(old_address) = old {
					Self::deposit_event(Event::<T>::HostAddressUpdated {
						state_machine,
						old_address,
						new_address: address,
					});
				} else {
					Self::deposit_event(Event::<T>::HostAddressSet { state_machine, address });
				}
			}

			Ok(())
		}
