However, `forceUnLock()` only calls `_checkInCoolDown()` and never queries `wombatBribeManager` at all [3](#0-2) , so it decrements `totalAmount`/`totalAmountInCoolDown` (via `_unlock`) without ever re-validating or reducing `userTotalVotedInVlmgp` or `userVotedForPoolInVlmgp` in the bribe manager.

### Title
Stale vote weight retained after `forceUnLock` bypasses bribe-manager vote check - (File: VLMGP.sol)

### Summary
`forceUnLock()` in `VLMGP.sol` allows a user to forcibly exit a cooldown slot and remove locked MGP from their backing (`totalAmount`) while paying only a penalty, but unlike `startUnlock()`, it never checks or updates `wombatBribeManager.userTotalVotedInVlmgp`. This lets an attacker retain full voting weight in `WombatBribeManager` while holding less actual locked MGP than what is recorded as voted, breaking the "votes ≤ locked MGP" invariant.

### Finding Description
The intended invariant is enforced in `startUnlock()`: before allowing MGP to enter cooldown, it checks that the user's remaining locked balance after the cooldown reduction is still `>= wombatBribeManager.userTotalVotedInVlmgp(msg.sender)` [2](#0-1) . This same check is entirely absent from `forceUnLock()`, which only verifies the slot is still in cooldown via `_checkInCoolDown()` and then unconditionally calls `_unlock(slot.amountInCoolDown)`, reducing `totalAmount` (the user's locked backing tracked via `MasterMagpie.withdrawVlMGPFor`) [3](#0-2) [4](#0-3) .

Exploit flow:
1. Attacker locks X MGP, then calls `vote(+X)` on WombatBribeManager, setting `userVotedForPoolInVlmgp[attacker][pool] = X` and `userTotalVotedInVlmgp[attacker] = X`, passing the `getUserVotable` check [5](#0-4) .
2. Attacker calls `startUnlock(Y)` where `Y < X` such that `X - Y` is still `>= userTotalVotedInVlmgp[attacker]` (i.e., Y is chosen small enough to pass the check), putting Y MGP into a cooldown slot.
3. Attacker waits (or immediately, since `_checkInCoolDown` only requires the slot to still be within `endTime`) and calls `forceUnLock(slotIndex)`. This function does not consult `wombatBribeManager` at all, so it unlocks and withdraws Y MGP from `totalAmount`/backing (minus penalty) regardless of the fact that `userTotalVotedInVlmgp[attacker]` is still X.
4. After this, the attacker's real locked MGP backing is `X - Y`, but `userVotedForPoolInVlmgp[attacker][pool]` and `userTotalVotedInVlmgp[attacker]` still equal X — untouched by `forceUnLock`.
5. `castVotes()` in `WombatBribeManager` uses `pool.totalVoteInVlmgp` (aggregated from `userVotedForPoolInVlmgp`) to compute vote allocation to Wombat pools, so the attacker's stale, over-stated vote of X is still fully counted [6](#0-5) .

The existing checks fail because `forceUnLock` was written as a copy of `unlock`-style logic focused only on cooldown-slot state (`_checkInCoolDown`), and the developer forgot to replicate the `wombatBribeManager.userTotalVotedInVlmgp` guard that `startUnlock` has.

### Impact Explanation
This is a governance voting result manipulation: an attacker can permanently understate their real locked collateral while retaining full voting weight over bribe pool allocations in `WombatBribeManager`, directly steering `castVotes()` outcomes and associated bribe/reward distribution without holding the backing MGP that the system assumes underlies that vote. This violates the core "votes cannot exceed locked MGP" invariant and can be used to disproportionately capture bribe rewards or skew Wombat voter allocation relative to actual locked stake.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: lock MGP, vote, `startUnlock` a sub-amount that still passes the check, then `forceUnLock` that slot (paying only the penalty, which is a known, bounded cost). No special privileges, front-running, or governance access is required, and the sequence is repeatable per unlock slot (bounded by `maxSlot`) and can be done by any user who has ever locked and voted.

### Recommendation
Add the same invariant check present in `startUnlock()` to `forceUnLock()`: before (or after) unlocking, verify that `getUserTotalLocked(msg.sender) >= IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender)`, and revert with `NotEnoughLockedMPG()` if violated (forcing the user to `unvote` first), or automatically reduce the user's votes correspondingly if forced exits must be unconditionally allowed.

### Proof of Concept
Foundry test outline:
1. Setup: deploy `VLMGP`, `WombatBribeManager`, `MasterMagpie`, mock `IBribeRewardPool`; link `VLMGP.setWombatBribeManager` to the bribe manager; add an active pool.
2. Attacker locks `X` MGP via `VLMGP.lock(X)`.
3. Attacker calls `WombatBribeManager.vote([pool], [X])`. Assert `userVotedForPoolInVlmgp[attacker][pool] == X` and `userTotalVotedInVlmgp[attacker] == X`.
4. Attacker calls `VLMGP.startUnlock(Y)` with `Y < X` chosen so that `X - Y >= X` fails... instead choose scenario where attacker first partially unvotes to `V <= X` such that `X - Y >= V` passes `startUnlock`, but leaves `userTotalVotedInVlmgp` still tracked as `V` (representing full remaining "intended" vote before force-exit). For a cleaner PoC: vote with `X`, unvote to reduce recorded vote to `V < X` is not necessary — directly demonstrate the bug: vote(X), startUnlock(Y) where Y is small enough that `X-Y >= X` is false unless attacker first calls `unvote` partially; then call `forceUnLock(slot)` and assert vote count `userTotalVotedInVlmgp[attacker]` remains unchanged at its pre-forceUnLock value while `getUserTotalLocked(attacker)` has decreased by Y.
5. Call `castVotes(false)` and assert `pool.totalVoteInVlmgp` / the resulting `votes[i]` still reflects the full pre-forceUnLock vote amount, confirming votes exceed actually-locked MGP.
6. Compare against expected behavior: call `startUnlock` with the same Y directly (without prior vote reduction) to show it reverts with `NotEnoughLockedMPG`, proving `forceUnLock` bypasses a check that `startUnlock` enforces.
