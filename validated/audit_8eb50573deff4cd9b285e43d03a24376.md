### Title
Buyback swap in `SmartWomConvert._convertFor` executes with hardcoded zero minimum output, enabling sandwich theft of depositor funds - (File: wombat/SmartWomConvert.sol)

### Summary
`_convertFor()` in `wombat/SmartWomConvert.sol` swaps the "buyback" portion of a deposit via `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)`, passing a hardcoded `0` as the router's own slippage floor regardless of the caller-supplied `_minRec`. The only guard against slippage is the post-swap check `convertAmount + amountRec < _minRec`, but when `SmartWomConvert.convert()` is invoked from `ArbWomUp3._deposit()` mode 2, `_minRec` is itself hardcoded to `0`, removing all slippage protection for that call path and allowing an MEV attacker to sandwich the swap and extract value from the depositing user.

### Finding Description
`_convertFor` (wombat/SmartWomConvert.sol, lines 175-220) splits the caller's `_amount` of WOM into a `buybackAmount` (swapped WOM→mWom through the Wombat router) and a `convertAmount` (deposited 1:1 via `IMWom(mWom).deposit`). The router call itself is: [1](#0-0) 

The `0` passed as `minimumAmountOut` to `swapExactTokensForTokens` means the swap can execute at an arbitrarily bad price with no protocol-level floor. The only remaining safety net is: [2](#0-1) 

This check depends entirely on the caller-supplied `_minRec`. When `SmartWomConvert.convert()` is reached via `ArbWomUp3._deposit()` mode 2, that parameter is itself hardcoded to zero: [3](#0-2) 

so `convertAmount + amountRec < 0` can never be true, and the post-swap check provides no protection either. The result is a swap path with **no slippage floor at any layer** reachable through `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, _mode=2)`, a public, unprivileged, non-owner-gated entrypoint.

An MEV attacker (unprivileged, front-running capable, as permitted by the rules) can:
1. Observe a pending `incentiveDeposit(..., _mode=2)` transaction (or any `convert`/`convertFor` call reachable with `_minRec=0`) in the mempool.
2. Front-run it with a swap on `womMWomPool` that skews the WOM/mWom price unfavorably.
3. Let the victim's `_convertFor` buyback swap execute against the skewed price, receiving far less mWom than fair value, with no revert since `_minRec = 0`.
4. Back-run to restore the pool price and capture the extracted value as arbitrage profit.

This directly reduces the mWom amount locked for the victim in `mWomSV.lockFor(mWomBal, _account)`, transferring value from the depositing user to the attacker.

### Impact Explanation
This is a direct theft of user funds vector: any user depositing WOM through `ArbWomUp3.incentiveDeposit` with `_mode == 2` has their `convert`-routed buyback swap executed with zero slippage protection at both the router-call level and the post-swap check level, allowing sandwich attackers to systematically extract value from every such deposit. This matches "Critical - Direct theft of user funds."

### Likelihood Explanation
The precondition (call path through `ArbWomUp3._deposit` mode 2 with `_minRec` hardcoded to `0`) is hit on every normal use of `incentiveDeposit(..., _mode=2)`, requiring no special attacker privilege—only mempool visibility and capital to front-run/back-run the pool, which is standard MEV tooling. It is fully repeatable for every mode-2 deposit and does not depend on admin error, oracle manipulation, or leaked keys.

### Recommendation
Compute a proper minimum-output bound for the router swap (e.g., derive from `getAmountOut` with an acceptable slippage tolerance, or thread a real caller/oracle-derived `_minRec` through to the swap call) instead of hardcoding `0` in `_convertFor`'s `swapExactTokensForTokens` call, and remove the hardcoded `0` for `_minRec` in `ArbWomUp3._deposit` mode 2, replacing it with a value derived from `SmartWomConvert.estimateTotalConversion` minus an acceptable slippage tolerance.

### Proof of Concept
Foundry test plan:
1. Deploy `SmartWomConvert`, `ArbWomUp3`, mock `IWombatRouter`/pool with configurable price, `mWom`, `wom`, `mWomSV`.
2. Fund victim with WOM; victim calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, false, 2)`.
3. Simulate MEV: before victim's tx, call router/pool to shift WOM/mWom exchange rate unfavorably (mock router's `swapExactTokensForTokens` to return a reduced `amountRec` reflecting the skewed rate).
4. Execute victim's `incentiveDeposit` tx; assert it does **not** revert despite `amountRec` being far below the pre-skew fair-value quote from `estimateTotalConversion`.
5. Assert `mWomSV.getUserTotalLocked(victim)` reflects the reduced (post-sandwich) amount, quantifying the loss versus the fair-value baseline computed from `estimateTotalConversion` before the price skew.
6. Assert the attacker's back-run trade profits by the same amount extracted from the victim.
