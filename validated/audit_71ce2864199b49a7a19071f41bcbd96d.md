### Title
Outputs to a Bitcoin multisig key in its activation block are never scanned, permanently stricking funds - (File: processor/src/multisigs/scanner.rs)

### Summary
The external report describes funds that land in a contract outside the accounted "delta window" and become permanently stuck. The Serai analog lives in `processor/src/multisigs/scanner.rs`: when the first network key is registered, `register_key` sets `ram_scanned = Some(activation_number)` and records `activation_number` as already scanned, while the key is only considered active for `block_being_scanned >= activation_number`. The main scanning loop then begins at `ram_scanned + 1`, i.e. `activation_number + 1`, so block `activation_number` — the first block where the key is active — is never scanned. Any output paying to the multisig's external/branch/change/forward script in that block is silently dropped forever.

### Finding Description
In `register_key` (processor/src/multisigs/scanner.rs), for the first registered key:

```rust
if scanner.keys.is_empty() {
  assert!(scanner.ram_scanned.is_none());
  scanner.ram_scanned = Some(activation_number);
  assert!(ScannerDb::<N, D>::save_scanned_block(txn, activation_number).is_empty());
}
```

The scanning loop iterates `(ram_scanned + 1) ..= latest_block_to_scan`, so it starts at `activation_number + 1`. Yet the per-block key filter treats the key as scannable when `activation_number <= block_being_scanned` (`if activation_number > block_being_scanned { continue }`). The key's activation block is therefore inside the key's active range but outside the scanned range — a one-block blind spot matching the "only transfers inside the counted call are credited" pattern of the auraBAL finding.

The dropped output is never emitted as a `ScannerEvent::Block` output, never written via `save_outputs`, never tracked in `ram_outputs`, and `latest_scanned_block` advances past it. On reboot, scanning resumes from the saved block, so there is no recovery path.

### Impact Explanation
An output paying to the multisig (external deposit address, branch, change, or forward script) confirmed exactly in the activation block is permanently invisible to the processor. The scheduler never sees it, it can never be aggregated or spent via `SignableTransaction`, and since spending requires a threshold signature there is no manual recovery — the funds are burned, exactly analogous to auraBAL locked in the Strategy with no sweep path.

### Likelihood Explanation
Reachable by an unprivileged party via a Bitcoin transaction they send. The multisig group key is published on Serai (`ProcessorMessage::GeneratedKeyPair`), from which the external P2TR address is deterministically derivable (`p2tr_script_buf(key)`). An attacker who observes key generation and the scheduled activation height can broadcast a transaction timed to confirm in the activation block (miner-assisted or simply racing). Even absent a deliberate attack, any early depositor sending to a leaked/precomputed address before `activation_number + 1` triggers the loss. Because this requires the first-registered key path (`scanner.keys.is_empty()`), it applies to genesis/bootstrapped multisigs; subsequent keys take the `else` branch and are scanned from `ram_scanned + 1` normally, so their activation block *is* scanned — making the first-key case an inconsistent off-by-one.

### Recommendation
Initialize `ram_scanned` to `activation_number - 1` (or `Some(activation_number.saturating_sub(1))`) for the first key so the scan loop covers `activation_number ..= latest`, matching the `activation_number <= block_being_scanned` activity condition. Alternatively, keep `ram_scanned = activation_number` but change the key filter to `activation_number < block_being_scanned`, and do not mark `activation_number` as scanned in `save_scanned_block` until it has actually been processed.

### Proof of Concept
1. Serai completes a Bitcoin DKG; `register_key(txn, activation_number = H, key)` is called on an empty `scanner.keys`, setting `ram_scanned = Some(H)` and persisting `H` as scanned.
2. Attacker (or early user) broadcasts a TX paying `> DUST` to `p2tr_script_buf(key)`, confirmed in block `H`.
3. The scan loop iterates `H + 1 ..= latest`; `get_outputs` is never invoked on block `H` for this key.
4. No `ScannerEvent::Block` carries the output; `save_scanned_block` advances past `H`; the UTXO is permanently unspendable by the scheduler.

Note the asymmetry confirming the bug: for a second key registered at `H'` while `ram_scanned = S < H'`, the loop scans `S+1 ..` and the key activates at `block_being_scanned == H'`, which *is* scanned — only the first key's activation block is skipped.
