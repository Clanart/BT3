Webhook shop-of-origin (`X-Shopify-Shop-Domain`) not bound to the HMAC-authenticated payload, enabling cross-shop webhook spoofing - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook exclusively by checking `hmac_valid?(request.raw_post)`, i.e. it verifies only that the raw body was signed with the app's shared secret [1](#0-0) . The tenant identifier used downstream, `shop_domain`, is read straight from the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC computation and is therefore completely unauthenticated [2](#0-1) [3](#0-2) . This is directly analogous to the reported `redeem()` flaw: a value that establishes "chain of origin" (there, `_fromChain`; here, the originating shop) is trusted without being cryptographically bound to the verified payload.

### Finding Description
The HMAC in `hmac_valid?` is computed over `data = request.raw_post` only, using the single app-wide `ShopifyApp.configuration.secret`/`old_secret` [4](#0-3) . Because the secret is shared across every shop that has installed the app, any merchant who has installed the app can legitimately receive a genuine `(raw_body, HMAC)` pair for their own shop from Shopify. That merchant can then replay the identical body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g. a victim shop's domain). `verify_request` will still pass because it never inspects or authenticates the header - it is not part of the signed data at all.

The `shop_domain` value produced by this concern is the documented, recommended way apps identify the tenant for custom webhook controllers:
```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification
  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end
end
```
(from `docs/shopify_app/webhooks.md`)

This same unauthenticated-header pattern is reused by every generator-produced job, e.g. `AppUninstalledJob` and `ShopRedactJob`, both of which look up `Shop.find_by(shopify_domain: shop_domain)` using the attacker-controlled header and then act on the resolved shop record [5](#0-4) [6](#0-5) .

### Impact Explanation
An attacker who is a legitimate (or trial) merchant of the app can:
1. Capture a valid webhook (raw body + `X-Shopify-Hmac-Sha256`) that Shopify sent for their own shop (e.g. any subscribed topic, or trigger one themselves via an action in their store).
2. Replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to a victim shop's domain.
3. `verify_request` accepts it because only the body HMAC is checked.
4. The downstream job (built exactly per the gem's own generators/docs) resolves the victim `Shop` record via the forged header and performs a destructive, shop-scoped action attributed to the wrong tenant - e.g. `AppUninstalledJob#perform` calling `shop.destroy` on the victim's shop record, or `ShopRedactJob` initiating GDPR redaction/`with_shopify_session` for the victim shop while carrying the attacker's own webhook body.

This is a cross-shop integrity/availability issue: an unrelated merchant can trigger privileged shop-scoped side effects (deletion of another shop's local installation record, redaction flows, or any custom `shop_domain`-keyed job logic) without ever compromising the victim's credentials.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that follow the documented `WebhookVerification` custom-controller pattern or use the generator-produced jobs verbatim (which is the common/default path). No secret leakage, model of internal access, or dependency vulnerability is needed - only that the attacker's own shop has the app installed, which is the normal onboarding path for any SaaS app on the Shopify App Store. The main mitigating factor is that the attacker needs a genuine signed webhook payload from their own shop first (trivial to obtain by triggering any subscribed event), and any topic-specific fields inside the JSON body (e.g. an order/customer ID) will reflect the attacker's own shop's data rather than the victim's, limiting some (but not all) topics' usefulness. Topics like `app/uninstalled` or the mandatory privacy webhooks, whose job logic depends purely on `shop_domain` and does not need topic-specific correctness, are fully exploitable.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` as an authenticated tenant identifier. Either:
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed data check, or cross-validate the header against a shop identifier embedded in the verified JSON payload where available, or
- Change `WebhookVerification#shop_domain` (and the generator templates that consume it) to fail closed unless the header can be corroborated against another authenticated signal, and document clearly in `docs/shopify_app/webhooks.md` that `shop_domain` is not itself authenticated by `verify_request`.

### Proof of Concept
1. As Merchant A (attacker), install the target app on shop `attacker.myshopify.com`, causing Shopify to send a webhook, e.g. `app/uninstalled`, with body `B` and a valid `X-Shopify-Hmac-Sha256: H` (H = HMAC-SHA256(secret, B)).
2. Capture `(B, H)`.
3. Send:
```
POST /webhooks
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim.myshopify.com
Body: B
```
4. `verify_request` computes `hmac_valid?(B)` using the shared app secret - passes, since `B` and `H` are a genuine, unmodified pair [1](#0-0) .
5. The controller/job reads `shop_domain` from the (forged) header and executes `Shop.find_by(shopify_domain: "victim.myshopify.com")` then `shop.destroy` (in the generated `AppUninstalledJob`) [7](#0-6) , deleting the victim's local installation/session record despite the request originating entirely from the attacker's own shop.

      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
