### Title
`compound()` sweeps the entire shared contract balance to the caller using attacker-chosen `_convertRatio`/`_minRec` - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` uses `IERC20(_tokenAddress).balanceOf(address(this))` as the amount to process for every registered reward, rather than the amount actually claimed on behalf of `msg.sender` in that same call. It then routes 100% of that balance to `msg.sender`, using caller-supplied `_convertRatio`/`_minRec` for any token that has a `convertor` configured, or a plain `safeTransfer` for tokens without one. Any reward-token balance sitting in the contract that does not belong to the caller (dust from prior swaps, partially processed prior calls, or tokens sent to the contract outside of `multiclaimOnBehalf`) is swept to whoever calls `compound()` next.

### Finding Description
`compound()` does two loops:

1. It calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0)  which pushes claimed reward tokens into `address(this)` (the `ManualCompound` contract), and forwards non‑compoundable tokens back to `msg.sender` immediately [2](#0-1) .

2. It then iterates over **all registered rewards** (`rewardTokensLength = rewards.length`, independent of what `_lps`/`_rewards` actually claimed) and, for each, reads `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` — the **whole contract balance**, not an amount scoped to the current claim — and disposes of it entirely to `msg.sender`:

```solidity

if (receivedBalance > 0) {
    if (_convertor != address(0)) {
        IERC20(_tokenAddress).safeApprove(_convertor, receivedBalance);
        IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
    } else if (_locker != address(0) && _lockMgp) {
        ...
    } else if (_helperAddress != address(0)) {
        ...
    } else {
        IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance);
    }
}
``` [3](#0-2) 

There is no per‑caller bookkeeping anywhere in the contract: no mapping tracks how much of `receivedBalance` corresponds to the just-executed `multiclaimOnBehalf` call versus leftovers from a previous transaction. The entire routing logic (including the caller-controlled `_convertRatio`/`_minRec` passed straight into `IConverter.convertFor` [4](#0-3) , and the destination `_for = msg.sender` inside `SmartWomConvert._convertFor` [5](#0-4) ) assumes the full balance belongs to the current caller. `_minRec`/`_convertRatio` are global to the whole call and are never derived from or checked against what was actually claimed for `msg.sender`; they are simply attacker-controlled parameters applied to whatever tokens happen to be sitting in the contract.

For the reward branch with no `convertor`/`locker`/`helper` configured, the code skips slippage entirely and does a direct `safeTransfer(msg.sender, receivedBalance)` of the full balance — meaning any residual balance of that token in the contract (e.g., not fully consumed due to another user's partially-processed compound, rounding dust from a prior conversion, or tokens sent to the contract by any other flow) is handed in full to the next caller, with zero relationship to `msg.sender`'s actual claim.

Because `compound()` has no `nonReentrant` guard interacting with balance snapshots and no accounting struct that ties `receivedBalance` to the specific `_lps`/`_rewards` just claimed, any unprivileged caller can invoke `compound()` with a trivial or empty claim and still receive whatever balance is currently resting in the contract for every registered reward token, using their own `_convertRatio`/`_minRec` on the convertor path for tokens that do have a convertor configured.

### Impact Explanation
If reward tokens can accumulate in the contract between calls (rounding remainders from `SmartWomConvert._convertFor`'s buyback/deposit math [6](#0-5) , partially-completed multi-lp claims, or tokens otherwise present in the contract), an attacker calling `compound()` captures that entire balance for themselves — direct theft of value that was not claimed on their behalf. This matches "Critical – Direct theft of user funds" since the loss is principal/yield belonging to other users or the protocol, not the caller's own claim.

### Likelihood Explanation
The mechanism itself (balance-wide processing with attacker-chosen conversion parameters and no per-caller accounting) is present in every call to `compound()` and requires no special privileges — any EOA can call it. The magnitude of loss depends on how much residual/foreign balance is present at call time (rounding dust, timing of other users' partially-processed compounds, or external transfers into the contract), so the size of the exploitable balance is variable and, in the narrowest interpretation, may only be dust in an idealized single-caller-per-block scenario. Note: the specific precondition given in the prompt ("no convertor, locker, or helper configured for one of the registered rewards") actually routes that reward through the plain `safeTransfer` branch, which does not use `_minRec`/`_convertRatio` at all — so the precondition as stated does not exercise the `convertFor`-slippage mechanism described in the question; it only demonstrates the more general "shared balance swept to caller" flaw for the non-convertor branch. The convertor-specific `_minRec` misuse requires a different precondition (a convertor actually configured on the reward) to be triggered.

### Recommendation
Track per-token amounts actually received during the current `multiclaimOnBehalf` call (e.g., balance-before/after delta scoped to that call) instead of using the raw `balanceOf(address(this))`, and only process that delta for `msg.sender`. Any pre-existing balance should either be disallowed (revert on non-zero unexpected balance) or accounted to the correct owner via an internal ledger, so a caller can never dispose of tokens they did not just claim.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound`, `MasterMagpie` mock, and register a reward token with no `convertor`/`locker`/`helper` set (matching the stated precondition).
2. Seed the `ManualCompound` contract with a balance of that reward token that is not associated with the attacker (simulate dust/leftover from a prior partially-processed compound, or a direct token transfer representing another user's pending value).
3. Have the attacker call `compound([], [[]], 0, 0, false)` (empty `_lps`/`_rewards`, so `multiclaimOnBehalf` claims nothing on the attacker's behalf).
4. Assert that the pre-seeded reward-token balance is nonetheless transferred in full to the attacker via the `else` branch `safeTransfer(msg.sender, receivedBalance)`, even though the attacker claimed zero rewards — demonstrating that `compound()` does not tie disposed balances to the caller's own claim.
5. Repeat with a reward that has a `convertor` configured, seeding pre-existing balance and having the attacker supply `_convertRatio=0`/`_minRec=0`, and assert the entire pre-existing balance (not just the attacker's claim) is converted and sent to the attacker via `convertFor`, confirming the caller-controlled slippage floor applies to a shared balance that is not solely theirs.
