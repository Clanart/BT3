### Title
ReDoS in unbounded `re.compile`/`regex.search` inside `RuleEngine._regex_match` can exhaust the 10s PreToolUse hook timeout and fail open, bypassing a `block` rule - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`compile_regex()`/`_regex_match()` compile and execute attacker-influenced regex patterns with no complexity validation or execution time bound [1](#0-0) . Because `pretooluse.py` runs synchronously under a fixed 10-second hook timeout and the plugin's own error-handling philosophy is "on any error, allow the operation" [2](#0-1) , a catastrophic-backtracking pattern in a rule file can hang the hook process past its timeout, causing the intended `block` decision to never be emitted and the guarded tool call to proceed unchecked.

### Finding Description
`RuleEngine._regex_match` calls the module-level `compile_regex(pattern)` (an `@lru_cache(maxsize=128)` wrapped `re.compile(pattern, re.IGNORECASE)`) and then `regex.search(text)` with no timeout, no `re2`/safe-regex engine, and no static ReDoS pattern validation [3](#0-2) . This is reached from `evaluate_rules -> _rule_matches -> _check_condition -> _regex_match` for every rule whose `operator: regex_match` is configured [4](#0-3) .

Rules are loaded purely by globbing `.claude/hookify.*.local.md` in the current working directory with no git-tracked/ownership check and no confirmation prompt [5](#0-4) . Although documentation recommends these files be gitignored ("Rule Files: Keep rules in `.claude/hookify.*.local.md` - they should be git-ignored"), this is advisory only and not enforced by the loader [6](#0-5) . A malicious contributor can therefore commit such a file in a PR; once merged/pulled, it is picked up automatically on the victim's next tool call with no opt-in step, satisfying the attacker-controlled-pattern precondition.

`hooks.json` enforces a fixed 10-second timeout on `pretooluse.py` [7](#0-6) . If a rule's pattern (e.g. an intentionally crafted nested-quantifier expression disguised as a legitimate "block secret exposure" guard, matched against `command`/`new_text`/`content` fields that are influenced by normal Bash/Edit/Write operations) triggers catastrophic backtracking against realistic input, `regex.search` can run far longer than 10 seconds. `pretooluse.py`'s own `try/except/finally` only catches exceptions raised inside the process — it cannot catch or recover from the parent process forcibly terminating the hook on timeout. Hookify's design already treats every internal error as "allow" rather than "deny" (`except Exception: ... sys.exit(0)` with no blocking output) [2](#0-1) , and since no `hookSpecificOutput`/`permissionDecision: deny` is produced when the process is killed on timeout, the guarded operation is not denied — it proceeds, defeating the `block` rule's purpose.

The separately described LRU-cache-eviction scenario (many distinct patterns evicting a cached compiled regex) only causes repeated recompilation cost, which is on the order of microseconds even for complex patterns; it does not by itself change match correctness or approach the 10-second budget, so it is not an independent bypass vector — it is a negligible performance concern, not a security bypass.

### Impact Explanation
This allows an unprivileged repository contributor to plant a rule file that looks like a legitimate secret/dangerous-command guard but is actually a ReDoS trap. When a real dangerous or secret-exposing Bash/Edit/Write operation is attempted, the hook that should emit `permissionDecision: deny` instead hangs and times out, and the operation executes unchecked — a resource-exhaustion-driven bypass of a security-guard hook (fail-open on timeout), directly undermining the "deny means deny" invariant for a plugin whose entire purpose is to block dangerous tool calls.

### Likelihood Explanation
Preconditions are realistic: the attacker only needs to get a `.claude/hookify.*.local.md` file merged into the repository (e.g., via a PR adding a "helpful" security rule) — no admin/maintainer privilege, key leakage, or social engineering beyond ordinary code review is required, since the file's `.local.md` naming and gitignore recommendation are not technically enforced. Crafting an actual catastrophic-backtracking regex/text pair that reliably exceeds 10 seconds against realistic Bash-command or file-content text needs some regex engineering but is a well-known, low-effort technique (e.g., nested-quantifier patterns like `(a+)+$`-style constructs matched against plausible long/near-matching input, such as long paths, tokens, or repeated-character strings that legitimately occur in commands or file diffs). This is repeatable on every future matching tool call.

### Recommendation
- Bound regex execution: use a regex engine without catastrophic backtracking (e.g., Python's `re` compiled with a linear-time engine like `re2`/`regex` module's timeout support) or wrap `regex.search` in a hard per-pattern timeout (e.g., via `signal.alarm` or a worker process) well under the hook's 10s budget, and treat a per-pattern timeout as "rule failed to evaluate" without discarding other rules' evaluation or failing the whole hook open.
- Validate/reject rule patterns at load time for known ReDoS-prone constructs (nested quantifiers, overlapping alternations) similar to the approach already used in `plugins/security-guidance/hooks/extensibility.py`, which explicitly validates custom regexes for catastrophic-backtracking structure and skips them [8](#0-7) .
- For `block` rules specifically, prefer fail-closed behavior on internal timeout/error rather than fail-open, or at minimum surface a `systemMessage`/log so a hung block rule is visibly reported rather than silently bypassed.
- Enforce or check that `.claude/hookify.*.local.md` files are not committed/tracked by git (or require explicit user confirmation before auto-loading rules newly introduced via a pulled commit), closing the "attacker commits a rule file" path entirely.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
1. Construct a `Rule` with `event: bash`, `action: block`, `conditions: [{field: command, operator: regex_match, pattern: "(a+)+$"}]`.
2. Build `input_data = {"tool_name": "Bash", "tool_input": {"command": "a" * 40 + "!"}}` (long run of `a` followed by a non-matching character — classic catastrophic-backtracking trigger).
3. Call `RuleEngine().evaluate_rules([rule], input_data)` wrapped with a wall-clock timer; assert it completes in under, e.g., 200ms for a safety margin under the 10s `hooks.json` timeout.
4. Expected/observed failure: execution time grows exponentially with input length (e.g., 30 → 40 → 50 chars of `a`), demonstrating that `_regex_match` has no bound and will exceed the 10s hook timeout for realistic input lengths, at which point the hook process is killed and the `block` decision is never emitted, allowing the `command` to execute — confirming the fail-open bypass.
5. Extend as a fuzz corpus test: for a set of "realistic user-writable" patterns (drawn from `plugins/hookify/skills/writing-rules/SKILL.md` and `examples/`), assert no `(pattern, text)` pair exceeds a defined safety margin (e.g., 1s) to catch regressions.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
