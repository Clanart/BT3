### Title
Fee computed on a transaction missing the OP_RETURN `data` output, so transactions underpay the specified fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reported bug class is "a fee (or dependent value) computed against a pre-conversion amount and then applied against the post-conversion amount." In `SignableTransaction::new`, the OP_RETURN `data` output is appended to `tx_outs` (the outputs actually placed into the signed transaction), yet the weight/vbyte estimation — and hence `needed_fee` — is computed via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which only sees `payments`, never the OP_RETURN output. The fee is therefore calculated on a smaller transaction than the one that is actually built and signed — the same "fee computed on the wrong (pre-transformation) quantity" mistake.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` at `networks/bitcoin/src/wallet/send.rs:194-202` [1](#0-0) . Both fee computations then call `calculate_weight_vbytes` with `payments` only — first without change at lines 204-206 and again with change at lines 225-227 [2](#0-1) [3](#0-2) . `calculate_weight_vbytes` builds its template transaction's outputs solely from `payments` plus an optional change output (lines 85-99) [4](#0-3) . The OP_RETURN output — roughly `8 (value) + 1 (script len) + 1 (OP_RETURN) + 1 (push opcode) + data.len()` bytes, up to ~91 base bytes with the allowed 80-byte payload — is omitted from every weight estimate.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` uses an underestimated `vbytes` (line 206), so the transaction pays fewer satoshis than `fee_per_vbyte` × its real vsize.
- The minimum-relay-fee check at lines 211-213 validates `needed_fee` against the underestimated `vbytes`, so a transaction whose real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` can be produced and signed [5](#0-4) .
- When change is present, `fee_with_change` is equally underestimated, so the change output absorbs value that was intended as fee (lines 228-230), and `fee()`/`needed_fee()` report a consistent-looking but wrong rate — the discrepancy is only detectable against real vsize [6](#0-5) .

The `data` parameter is public, caller-supplied input to `SignableTransaction::new` (line 154); an external party who causes a data-bearing transaction to be constructed reaches this path.

### Impact Explanation
A transaction carrying data pays an effective fee rate strictly below the requested `fee_per_vbyte`, and can fall below Bitcoin's default minimum relay fee even though `TransactionError::TooLowFee` was not raised. Such a transaction is rejected by relay/mempool policy or stalls unconfirmed, leaving the spent inputs' value (including the change output to a Serai-controlled script) unspendable until the transaction is rebuilt at a corrected fee — matching the accepted impact class of "funds reported received that are not spendable" / signing a transaction that fails its own fee contract. Mis-accounting is bounded by the OP_RETURN overhead (~91 bytes ⇒ up to ~91 vbytes of unpaid weight), keeping this Medium rather than High.

### Likelihood Explanation
Deterministic whenever `data` is `Some` — no adversary timing or collusion required. The only moderating factor is that Serai's own processor currently always passes `None` for `data` [7](#0-6) , so the bug manifests only for users of the `bitcoin-serai` wallet library who attach data (the documented feature guarded by the 80-byte `TooMuchData` check). Reachability through public API input keeps it in scope; the narrower caller set limits likelihood.

### Recommendation
Compute the fee over the final output set. Either pass `tx_outs` (post-OP_RETURN) into `calculate_weight_vbytes`, or add the serialized size of the OP_RETURN output to the weight estimate:

```rust
// In networks/bitcoin/src/wallet/send.rs, replace `payments` with the
// post-OP_RETURN `tx_outs` when sizing the transaction:
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, None);
// ...
let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs, Some(&change));
```

changing `calculate_weight_vbytes` to accept `&[TxOut]` directly, so the template transaction mirrors the real `tx_outs` exactly.

### Proof of Concept
Construct a transaction with a data payload near the limit:

```rust
let payments = vec![(addr(), 10_000)];
let data = Some(vec![0u8; 80]); // passes the <= 80 byte check
let tx = SignableTransaction::new(inputs, &payments, None, data.clone(), fee_per_vbyte).unwrap();

// The serialized transaction includes an OP_RETURN output of ~91 bytes.
let real_vsize = tx.transaction().vsize() as u64;
// needed_fee only covers the vsize of a transaction WITHOUT the OP_RETURN output:
assert!(tx.needed_fee() < fee_per_vbyte * real_vsize);
// Actual fee paid equals needed_fee (no change case: inputs - payments),
// so effective sat/vbyte < fee_per_vbyte, and may be < DEFAULT_MIN_RELAY_TX_FEE * real_vsize / 1000
// despite the TooLowFee check having passed.
```

At `fee_per_vbyte = 1`, an input sized so `input_sat - payment_sat` equals `min_relay * estimated_vbytes / 1000` passes the `TooLowFee` check, yet the real fee rate is below 1 sat/vbyte because the ~91-byte OP_RETURN output was never counted — the signed transaction is non-relayable while appearing valid.
