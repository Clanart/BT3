## Title
Deep-link `filepath` parameter is validated inconsistently with `branch`, allowing unsanitized attacker-controlled path data to flow into repository open actions - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The bug pattern in the report is an access-control/validation check that is applied to some inputs but bypassed for others due to inconsistent enforcement of a security-relevant predicate, allowing attacker-controlled values to reach a sensitive sink. The equivalent pattern in the desktop client is in `parseAppURL()`, the parser for the `x-github-client://openRepo/...` custom-protocol deep link handled by `handleAppURL` in `app/src/main-process/main.ts`. In `parseAppURL`, the `branch` query parameter is explicitly checked for invalid/dangerous characters with `testForInvalidChars`, but the `filepath` query parameter — which is documented as "the file to open after cloning the repository" — receives **no validation at all** before being returned as part of the `IOpenRepositoryFromURLAction`. [1](#0-0) 

### Finding Description
`parseAppURL` validates the `pr` parameter with a strict numeric regex, and validates `branch` against `testForInvalidChars`: [2](#0-1) 

But `filepath` is read straight from the query string with `getQueryStringValue` and passed through unchanged: [3](#0-2) 

This is a deep link that is fully attacker-controlled: any web page, README, or chat message can embed `x-github-client://openRepo/https://github.com/owner/name?filepath=<ARBITRARY>` and the "Open in Desktop" flow (or macOS `open-url` / Windows `--protocol-launcher` handling in `app/src/main-process/main.ts`) will parse it via `handleAppURL` → `parseAppURL` without ever rejecting a malformed or traversal-style `filepath` (e.g. `../../../../etc/passwd`, an absolute path, or a UNC path on Windows) the way it would reject a malformed `branch`.

### Impact Explanation
This matches the required impact category: the attacker controls a link/deep link the user clicks, and the asymmetric/missing validation could let an attacker steer where the app subsequently attempts to open a file after cloning (a file-read/open outside the cloned repository directory, depending on how the consuming code joins `filepath` with the repository path). This mirrors the root cause of the referenced Solidity finding: a security check exists in the code but is inconsistently/incorrectly applied to only part of the input surface, allowing a bypass for the unchecked branch.

### Likelihood Explanation
Likelihood is **not fully confirmed** — I was not able to complete verification of the exact consumer of `IOpenRepositoryFromURLAction.filepath` (in `app/src/ui/dispatcher/dispatcher.ts`) within the available tool budget to confirm whether it performs its own path-join sanitization (e.g., rejecting absolute paths or `..` segments) before opening the file. The grep results show `filepath` is referenced in `dispatcher.ts` (6 matches) and `main.ts` (1 match), but I could not read those call sites to confirm the exact sink behavior. Given this uncertainty, this should be treated as a **lead requiring confirmation** rather than a fully proven exploit chain.

### Recommendation
Apply the same validation used for `branch` (or equivalent path-safety checks such as rejecting absolute paths, `..` traversal segments, and platform-specific dangerous characters) to the `filepath` query parameter inside `parseAppURL` before it is returned. Additionally, wherever `filepath` is consumed (in `dispatcher.ts`), it should be defensively re-validated/normalized relative to the freshly cloned repository root and rejected if it resolves outside that root.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/some/public-repo?filepath=..%2F..%2F..%2F..%2Fetc%2Fpasswd` (or a Windows UNC/absolute-path equivalent).
2. Victim clicks the link (e.g., embedded in a webpage, chat message, or malicious repo README that GitHub Desktop or a browser resolves via the registered protocol handler).
3. `app.on('open-url', ...)` (macOS) or `handleCommandLineArguments`/`--protocol-launcher` (Windows) in `app/src/main-process/main.ts` invokes `handleAppURL(url)` → `parseAppURL(url)`.
4. `parseAppURL` validates `branch` but returns `filepath` unchanged and unsanitized as part of `IOpenRepositoryFromURLAction`.
5. **Unverified next step**: if the dispatcher subsequently joins this `filepath` with the local clone path and opens/reads it without further sanitization, this results in file access outside the intended repository. This last step needs to be confirmed by inspecting `app/src/ui/dispatcher/dispatcher.ts`'s handling of `open-repository-from-url` actions, which I was unable to complete in this session due to the iteration limit — a follow-up review of that file is recommended before treating this as a confirmed, exploitable vulnerability.

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
