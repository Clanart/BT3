## Binding Under Test

`withdrawals.payout_payer_operator_xonly_pk` for withdrawal idx `i` is meant to equal the x-only public key of the operator whose Bitcoin funds actually paid `output[0]` of the mined Payout tx for that withdrawal. In fact the code sets it to **whatever OP_RETURN key appears in whichever transaction happens to be mined spending the withdrawal outpoint** — a value that a third party can freely choose, because the user's authorization signature never commits to that output.

## Trace

- The withdrawal signature required from the user is pinned to `TapSighashType::SinglePlusAnyoneCanPay` and any other type is rejected: [1](#0-0) 
- `create_payout_txhandler` builds `[output0 = user payout, output1 = anchor, output2 = OP_RETURN(operator_xonly_pk)]`, and the operator's key-spend signature is placed only on input 0: [2](#0-1) 
- For `SinglePlusAnyoneCanPay`, the sighash machinery commits only to the signed input's own prevout (`Prevouts::One`), and by BIP341 SINGLE semantics only `output[input_index]` (i.e. `output[0]`) is covered — outputs 1 and 2 (anchor, OP_RETURN) and any other inputs are unconstrained: [3](#0-2) 
- The operator's own `withdraw()` verifies exactly this same sighash before funding/broadcasting: [4](#0-3) 
- Attribution is later derived purely from the on-chain OP_RETURN of the transaction that actually spent the withdrawal outpoint, with no check that its funder matches the OP_RETURN key: [5](#0-4) 
- That DB value is what `is_kickoff_malicious` compares against the real kickoff sender's key to decide whether to challenge: [6](#0-5) 

This confirms every element of the attacker's construction: input 0 and output 0 are byte-for-byte reusable (they're exactly what the signature commits to), while output index 2 (OP_RETURN) and the extra fee input are free to rewrite, and the v3 (TRUC) payout transaction format is inherently RBF-replaceable, enabling the attacker's higher-fee variant to be mined instead of the honest one.

### Title
Payout OP_RETURN operator attribution is not covered by the `SinglePlusAnyoneCanPay` signature, letting anyone rewrite it and frame the true fronting operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The Payout transaction's OP_RETURN output (the operator attribution field) is not committed by the user's `SinglePlusAnyoneCanPay` signature, since that sighash type only covers input 0 and output 0. An attacker observing an honest operator's broadcast Payout tx can rebroadcast a variant with the same input/output0 but a rewritten OP_RETURN naming a different operator and an extra higher-fee input, get it mined via the tx's inherent v3/TRUC replaceability, and cause the real fronting operator to be recorded as not the payer.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk[i] == operator whose funds paid output[0] of the mined Payout tx for withdrawal i`. This binding is broken because `create_payout_txhandler` places the OP_RETURN with `operator_xonly_pk` at output index 2, but the only signature authorizing the transaction (`user_sig`, sighash type forcibly `SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`) is a Taproot key-spend signature over input 0 whose SIGHASH_SINGLE|ANYONECANPAY semantics commit only to input 0's prevout and to `output[0]` — see `calculate_pubkey_spend_sighash`'s use of `Prevouts::One`. Outputs 1 (anchor) and 2 (OP_RETURN), and any additional funding inputs, are entirely outside the signed message.

An attacker who observes the honest operator A's broadcast Payout tx in the mempool can therefore construct: input 0 = the same withdrawal outpoint with the same witness (still valid, since the message it signs is unchanged), output 0 = the identical user payout output, plus an attacker-funded extra input for a higher fee, and output 2 rewritten as `OP_RETURN(B)` for any other registered operator B (or even an arbitrary/garbage value). Because Payout is built with `NON_STANDARD_V3` (TRUC), it is implicitly RBF-eligible, so the higher-fee variant can replace A's transaction in mempools and get mined first.

`update_finalized_payouts` then parses the OP_RETURN of whatever transaction actually appears on-chain spending the withdrawal UTXO and stores that key as `payout_payer_operator_xonly_pk`, with no verification that the inputs funding output 0 belong to that key's owner. When A later sends its Kickoff (since A genuinely paid the user), `is_kickoff_malicious` compares `kickoff_data.operator_xonly_pk` (A) against the DB-stored payer key (B, attacker's rewritten value) and — because they differ — flags A's kickoff as malicious, triggering Challenge and eventually Disprove/collateral burn, even though A funded the payout honestly. None of the existing guards (`SECP.verify_schnorr`, `is_kickoff_malicious`'s own equality check, or the database) detect this because they all trust the on-chain OP_RETURN as ground truth without any cryptographic tie between it and the actual funding operator.

### Impact Explanation
An honest operator's collateral is destroyed via wrongful Challenge/Disprove even though it correctly fronted the withdrawal — this matches the Critical category "an honest operator's collateral burned." The attack is repeatable for every withdrawal handled via the standard (non-optimistic) Payout path and works against any operator set, since the OP_RETURN payload is a free-form 32-byte value the attacker fully controls. The blast radius is bridge-wide: any operator performing a standard payout is exposed the moment its unconfirmed Payout tx becomes visible in the mempool.

### Likelihood Explanation
No privileged role is required: the attacker only needs to observe the mempool (public), and rebroadcast a modified transaction with a higher fee (attacker pays their own BTC fee/UTXO, no protocol key or aggregator access needed). The payout transaction is v3/TRUC, which by policy is always fee-bumpable/replaceable, making the replace-in-mempool step feasible with only marginal fee cost. This is fully reproducible offline against regtest without mainnet or a live Citrea node.

### Recommendation
Require the OP_RETURN (operator attribution) output to be committed by the user's signature, e.g. by having the user sign with `AllPlusAnyoneCanPay` (or a full `SIGHASH_ALL` variant that still allows extra funding inputs via `ANYONECANPAY` but commits to all outputs), or by moving the operator's own key-spend signature to also cover the OP_RETURN output and validating it, so that the mined transaction's attribution output cannot diverge from what was originally authorized/broadcast by the actual fronting operator.

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Set up a deposit and a withdrawal for two registered operators A and B (as in existing `core/src/test/deposit_and_withdraw_e2e.rs` helpers).
2. Have operator A call `withdraw`/`create_payout_txhandler` to build and sign the Payout tx (`op_return = A.xonly_pk`), and obtain the raw signed transaction without broadcasting it through the operator (simulate "observed in mempool").
3. Construct a second transaction reusing input 0 (same outpoint + same witness) and output 0 verbatim, adding an attacker-controlled extra input for fee, and setting `op_return = B.xonly_pk`.
4. Assert `SECP.verify_schnorr` still succeeds for the reused signature against the new transaction's sighash (proving output 2 is unconstrained).
5. Mine the attacker's transaction instead of A's original.
6. Run the verifier's `update_finalized_payouts` equivalent sync and assert `db.get_payout_info_from_move_txid(...)` now returns `Some(B.xonly_pk)` even though A funded the payout.
7. Have operator A submit its Kickoff for this deposit and assert `Verifier::is_kickoff_malicious` returns `true` for A's kickoff (`operator_xonly_pk (B) != kickoff_data.operator_xonly_pk (A)`), reproducing wrongful Challenge/collateral-burn on the honest operator A.

        sighash_type: TapSighashType,

            .txins
            .iter()
