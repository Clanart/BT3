## Finding [1](#0-0) 

The Hyperbridge `IntentGateway` (both the EVM `ExtrinsicIntents`/`IntentsBase` and the Tron `IntentGatewayV2` implementations) contains the same broken invariant as the reported `ragequit`/`safeRagequit` bug: **escrow release for a multi-token order is all-or-nothing, and there is no pull-pattern fallback to redeem the tokens that *can* be transferred if one token in the list reverts.**

### Title
Multi-token escrow release is all-or-nothing with no pull-pattern fallback, permanently locking all escrowed order tokens if any single token transfer reverts - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw()` in `IntentsBase.sol` (used by `ExtrinsicIntents.sol`'s `onAccept`) and its Tron twin `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` iterate over every token in `WithdrawalRequest.tokens` inside a single transaction and push funds directly to the beneficiary via `IERC20.safeTransfer`/`.call{value:}`. If any one of those transfers reverts (blacklisted beneficiary for one specific ERC20 like USDC/USDT, a paused token, or any token whose `transfer` can revert), the entire loop reverts, which reverts `onAccept`, which reverts the whole cross-chain message delivery.

This function is called from `onAccept` for both `RedeemEscrow` and `RefundEscrow` kinds: [3](#0-2) 

`onAccept` is invoked by `EvmHost.dispatchIncoming` via a low-level `.call`, and the host's only failure handling is to delete the receipt so the *entire identical message* can be retried later: [4](#0-3) 

Because the retry re-executes the exact same `WithdrawalRequest` (same commitment, same token list, same beneficiary), if even one token in a multi-token order is permanently untransferable to that beneficiary (e.g., the beneficiary gets blacklisted on one stablecoin, or one of the order's input tokens is paused/pausable and stays paused), **the release can never succeed**, and all of the other, otherwise-transferable tokens in that same order remain locked in escrow forever. There is no per-token/subset withdrawal path (the analog of `safeRagequit`) and no pull-based claim mechanism where a beneficiary could withdraw the tokens that do work while leaving the problematic one pending.

The Tron variant has the identical structure: [5](#0-4) 

### Impact Explanation
This is a direct analog of the reported bug class: legitimate, otherwise-redeemable escrowed funds become permanently unrecoverable because the withdrawal path is atomic across a set of tokens with no pull/partial-redemption fallback. Given that `order.inputs` can be an arbitrary list of ERC20s chosen when the order is created, and that blacklist-capable tokens (USDC, USDT) are common intent-fill assets, any order with a mixed token set is exposed: a single blacklist event or paused token state on one asset locks the entire order's escrow, not just the affected token.

### Likelihood Explanation
Likelihood is moderate: it doesn't require a malicious relayer, prover, or governance actor — only a token in the order's input set that can revert (blacklist, pause, or similar) for the specific beneficiary address at settlement time. This is exactly the same trigger condition as the original Moloch `ragequit` report (external blacklist/censorable token), which the reporter treated as a real, in-scope funds-loss/lock issue.

### Recommendation
Adopt the pull pattern recommended in the original report: decouple escrow accounting from the transfer. On `RedeemEscrow`/`RefundEscrow`, credit the beneficiary's claimable balance per-token in storage first (already partially done via `_orders[commitment][token]`), then let transfers happen in a separate, per-token `claim(token)` call that can be retried independently, so a revert on one token cannot block withdrawal of the others. Alternatively, wrap each transfer in a try/catch inside the loop and only revert/skip the specific failing token, emitting an event so it can be claimed via a separate path later, while still releasing all other tokens in the same call.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [tokenA, tokenB]` where `tokenB` is a blacklist-capable stablecoin (e.g., mirroring USDC).
2. Order is filled by a solver on the destination chain; solver's address becomes `beneficiary` for the `RedeemEscrow` message routed back to source via Hyperbridge.
3. Before the `RedeemEscrow` message is delivered, `tokenB`'s issuer blacklists the beneficiary address (external event, independent of Hyperbridge).
4. Relayer submits the proof; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`. The loop transfers `tokenA` successfully (storage already decremented) but reverts on `tokenB.safeTransfer(beneficiary, amount)`.
5. The whole `onAccept` call reverts; `EvmHost` deletes `_requestReceipts[commitment]` so it can be retried — but any resubmission hits the same revert, because `tokenB` remains blacklisted and the message body/beneficiary never change.
6. Result: `tokenA`, which was perfectly transferable, remains permanently trapped in escrow alongside `tokenB`, with no mechanism to withdraw it separately. [1](#0-0) [6](#0-5)

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
