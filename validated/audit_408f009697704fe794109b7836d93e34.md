### Title
Protocol fee rounds to zero on small per-input order amounts, allowing full fee-evasion by order splitting - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` computes the protocol fee for each escrowed input with integer division: `protocolFee = (originalAmount * protocolFeeBps) / 10_000`. When `originalAmount` is small relative to `protocolFeeBps`, this truncates to zero, so `reducedAmount == originalAmount` and the order is escrowed with **no fee deducted at all**. Any unprivileged user calling the public `placeOrder` entrypoint can repeatedly submit orders sized just under the fee-rounding threshold to move arbitrary total value through the gateway while paying zero protocol fee, exactly the fee-bypass pattern described in the source Allo `_fundPool` report.

### Finding Description
In `placeOrder`, the fee-deduction loop is: [1](#0-0) 

```solidity
if (protocolFeeBps > 0) {
    reducedInputs = new TokenInfo[](inputsLen);
    for (uint256 i; i < inputsLen;) {
        uint256 originalAmount = order.inputs[i].amount;
        if (originalAmount == 0) revert InvalidInput();
        uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
        uint256 reducedAmount = originalAmount - protocolFee;
        ...
        if (protocolFee > 0) emit DustCollected(token, protocolFee);
        reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
        ...
```

The only validation on `originalAmount` is `!= 0` (nonzero, not a minimum). For any `originalAmount < 10_000 / protocolFeeBps`, `protocolFee` truncates to `0`, so `reducedAmount == originalAmount` — the deposit is escrowed at full face value with zero fee taken, and the `if (protocolFee > 0)` guard even suppresses the `DustCollected` event so the bypass is silent.

The docs confirm the live deployment fee is 5 bps: [2](#0-1) 

At `protocolFeeBps = 5`, any single-order input amount `< 2000` base units (e.g. `$0.002` for a 6-decimal stablecoin, or ~2000 wei-equivalent smallest units on low-decimal tokens) pays **zero** protocol fee. There is no `minFundAmount`/minimum-order-size check anywhere in `placeOrder` — the same class of guard that Sherlock's judges required as the fix for the Allo `_fundPool` finding is absent here. `placeOrder` is a fully public, unauthenticated entrypoint (`function placeOrder(Order memory order, bytes32 graffiti) public payable`), so this is exploitable by any ordinary user, not merely a privileged pool-manager-equivalent role — a stronger primitive than the original finding, which Sherlock still ruled Medium even under the "pool manager only" exception.

An attacker fragments what would otherwise be one large order into many sub-threshold orders (each below `10_000/protocolFeeBps` units), each escaping the fee entirely, while still routing the full economic value of the intended trade to solvers/fillers. Gas cost on L2 deployments (explicitly the target environment per the Hyperbridge docs) makes this cheap to repeat.

### Impact Explanation
The protocol systematically loses fee revenue on any low-value-denominated or low-decimal input token, and any user can deliberately structure deposits to always land below the truncation threshold, defeating the fee mechanism entirely for that flow. This is a direct financial/logic-invariant break in the fee-collection guarantee that `placeOrder` is documented to enforce ("Before escrowing, the contract deducts a protocol fee from each input amount") — the protocol's `protocolFeeBps` parameter can be silently and completely nullified by any caller, with no privileged actor, relayer, or prover involvement required.

### Likelihood Explanation
High. No special conditions are needed beyond choosing an input amount below `10_000 / protocolFeeBps` units (trivial at the documented live 5 bps rate) and calling the public, permissionless `placeOrder` function — the same function normal users already call. No admin, governance, relayer, or malicious peer assumption is required.

### Recommendation
Enforce a `minOrderInputAmount` (per token, or a floor such that `protocolFee` is guaranteed non-zero when `protocolFeeBps > 0`) in `placeOrder`, rejecting orders whose per-input amount would round the protocol fee to zero, mirroring the `minFundAmount` fix recommended for the original Allo `_fundPool` issue. Alternatively, round the fee up (ceiling division) instead of truncating down so a non-zero fee is always collected whenever `protocolFeeBps > 0`.

### Proof of Concept
1. Deploy/observe `IntentGatewayV2` with `protocolFeeBps = 5` (current production value per docs).
2. Attacker calls `placeOrder` with `order.inputs[0].amount = 1999` (any token, e.g. 6-decimal USDC — `$0.001999`).
3. In the fee loop: `protocolFee = (1999 * 5) / 10_000 = 9995/10000 = 0`.
4. `reducedAmount = 1999 - 0 = 1999`; `DustCollected` is not emitted since `protocolFee == 0`.
5. Repeat step 2 in a loop (or batch via multicall) to move an arbitrarily large total amount through the gateway, 1999 units at a time, paying zero protocol fee on the entire flow — matching the escalated/accepted Sherlock M-4 pattern where fee rounding to zero on small deposits fully bypasses the protocol fee.

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |
```
