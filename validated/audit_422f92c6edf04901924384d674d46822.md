### Title
`GitStore.discardChanges` resolves attacker-controlled `file.path` without repo-root confinement, allowing symlink-based file deletion/write outside the repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` builds the on-disk path to discard with plain `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)`, using `file.path` values that originate from parsing `git status --porcelain=2` output (`app/src/lib/git/status.ts`, `app/src/lib/status-parser.ts`). Unlike other file-path-handling code in the same codebase (`resolveWithin` in `app/src/lib/path.ts`, used in `app/src/ui/dispatcher/dispatcher.ts` and `app/src/lib/copilot-conflict-context.ts`), the discard path is never validated to stay within the repository root. Because git status paths can traverse through a symlink that a malicious repository commits inside its own working tree, a cloned/fetched hostile repository can cause Desktop's "Discard Changes" feature to delete or overwrite files outside the repository when the victim performs a routine discard operation.

### Finding Description
`GitStore.discardChanges` (`app/src/lib/stores/git-store.ts:1545-1649`) iterates over `WorkingDirectoryFileChange` objects and, for each non-deleted, non-submodule file, resolves the on-disk target purely by string-joining the repository root with `file.path`: [1](#0-0) 

Neither `moveItemToTrash` nor the fallback `rm()` call verifies that the resolved path actually stays inside `repository.path`. `file.path` is attacker-influenced: it is derived verbatim from `git status --porcelain=2` entries parsed by `parseChangedEntry`/`parseUntrackedEntry` in `app/src/lib/status-parser.ts` (lines 101-182), which simply extract whatever byte string git reports as the path, with no traversal or symlink checks. If a malicious repository commits a symlink (e.g. `evil-dir -> /home/victim/.ssh` or `%APPDATA%\...`) and then, on the victim's clone/fetch, an "untracked"/"modified" file appears to git status as `evil-dir/something` (through the symlinked directory), Desktop will report it as a normal changed/untracked file. The `Path.resolve`/`Path.join` in `discardChanges` will happily follow the symlink and produce a path outside the repository, and `shell.moveItemToTrash` (or the direct `rm()` fallback) will act on that external path.

This is the structural analog to the `SynthVault.withdraw` bug: a state-mutating "cleanup" operation (`withdraw` clearing weight without first claiming reward; `discardChanges` deleting a file without first confirming the target is inside the trusted domain) skips the invariant-preserving step that other, similar operations in the same codebase enforce. The codebase already recognizes this exact invariant is important — `resolveWithin` in `app/src/lib/path.ts` explicitly performs `realpath` resolution and confines paths to a root, and it is used for deep-link file opening (`openRepositoryFromUrl` in `dispatcher.ts:1957-1971`) — but `discardChanges` was never updated to reuse this guard, despite already special-casing submodules (`listSubmodules`) for a related but narrower concern.

### Impact Explanation
If exploitable, "Discard Changes" — an everyday, low-friction action the user performs on files they believe belong to the cloned repository — could delete or corrupt files anywhere on the victim's filesystem reachable via a symlink target (SSH keys, config files, other repositories, etc.), or via the permanent-delete fallback (`rm()`), silently and irrecoverably (bypassing the Trash safety net entirely once "always discard permanently" has been chosen). This satisfies the "file write/read outside the repo" and "silent corruption of what the user commits" impact classes from an attacker-controlled cloned/fetched repository, with no local access, admin rights, or social engineering beyond the ordinary act of cloning and using Desktop's UI.

### Likelihood Explanation
Requires the victim to clone/fetch a repository containing a committed symlink whose target already exists on the host and points to a sensitive path, then to open that symlinked path via git status recognizing new/modified content inside it, and finally to invoke "Discard Changes" on the affected entry. Git working trees exist within OS filesystem constraints, so producing "modified content" inside a symlinked directory generally requires the target to already be writable/pre-populated or requires an additional actor (e.g. a build script, another tool, or app-injected content) to write into the followed symlink target after checkout — I could not confirm from the indexed code whether Desktop's own checkout/refresh flow would itself create such content, or whether git status would report symlinked-directory contents in a way that reaches `discardChanges` for arbitrary hosts (this needs live reproduction). Because of this remaining uncertainty about the precise trigger conditions, likelihood is moderate rather than confirmed high.

### Recommendation
In `GitStore.discardChanges` (and the analogous discard/reset code path in `app/src/lib/stores/git-store.ts`), replace the raw `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` calls with the existing `resolveWithin` helper from `app/src/lib/path.ts`, which already performs `realpath`-based root confinement and null-byte checks. If `resolveWithin` returns `null`, refuse to discard that file and surface an error instead of silently operating outside the repository, mirroring the guard already applied in `dispatcher.ts`'s `openRepositoryFromUrl`.

### Proof of Concept
Conceptual reproduction (not run against the live app; based on static code paths):
1. Attacker creates a repository containing a tracked symlink `link -> /home/victim/.ssh` (or a Windows-junction equivalent) and commits it.
2. Victim clones the repository with GitHub Desktop.
3. Through any mechanism that writes into `link/` (e.g., victim's own tooling, an editor autosave, or a subsequent `git checkout` of another branch that adds a file under `link/`), git status reports a changed/new path like `link/authorized_keys`.
4. `GitStore.discardChanges` computes `Path.resolve(repo.path, 'link/authorized_keys')`, which resolves through the symlink to `/home/victim/.ssh/authorized_keys`.
5. `shell.moveItemToTrash(...)` (or `rm(...)` if trash fails and the user previously chose permanent discard) is invoked on the resolved path — outside the cloned repository. [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

  public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
