### Title
Deserialized `ThresholdKeys` never validates verification shares, allowing a forged/identity group key - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of "no function to populate the whitelist, so `isWhitelisted` vacuously returns true" is `ThresholdKeys::new`/`ThresholdKeys::read`: the `verification_shares` map is taken wholesale from the input, yet nothing verifies that the shares are non-identity, consistent with `secret_share`, or that the resulting `group_key` corresponds to any real secret. The "protection" (that the group key commits to t-of-n shares with matching verification shares) is vacuous — the group key is whatever the supplied bytes interpolate to, and the secret share is never checked against its own verification share.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, an interpolation blob, a `secret_share`, and `n` verification shares via `C::read_G`, then calls `ThresholdKeys::new`. `C::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonical encoding — the identity element is accepted.

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) performs exactly three checks:
- `verification_shares.len() == n` (line 355)
- every key in the map is `<= n` (lines 361-365)
- `Constant` interpolation only when `t == n` (lines 367-374)

It then computes the group key as `sum over participants 1..=t of verification_shares[i] * interpolation_factor(i, {1..=t})` (lines 376-378). Critically:

1. **No non-identity check.** Setting `verification_shares[1..=t]` to the identity point yields `group_key == identity`.
2. **Participants `t+1..=n` never contribute to the group key.** Their verification shares are stored but unbound — arbitrary points are accepted.
3. **No consistency check** between `secret_share` and `verification_shares[i]` (i.e., `G * secret_share == verification_shares[i]` is never asserted), and between `group_key` and the shares.

The FROST `complete` path (`crypto/frost/src/sign.rs:447-495`) acknowledges this gap in a comment: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" — i.e., the code knows semantic invalidity is possible but neither rejects it at read time nor fails safely.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as a reachable untrusted-bytes entry point) produces keys whose `group_key()` is attacker-controlled:

- With all-identity shares for `1..=t`, `group_key() == identity`. Any Schnorr signature `(R, s)` with `s·G == R` then verifies against this key in `algorithm.verify(self.view.group_key(), &self.Rs, sum)` (`crypto/frost/src/sign.rs:465`), since `s·G == R + c·identity`. Anyone can forge signatures for such a group key — funds/outputs attributed to it are spendable by anyone, i.e., a forged-signature / funds-not-spendable-by-the-group outcome.
- More generally, an attacker can embed arbitrary verification shares for participants `> t` or shares inconsistent with the local `secret_share`, causing the node to participate in signing for a group key that does not correspond to any honestly-held t-of-n sharing. Honest participants' signature shares get aggregated under a key the attacker can separately forge or that is unrecoverable, producing "concrete signing under an unintended/inconsistent group key" and shares that cannot reconstruct a usable secret.

### Likelihood Explanation
Reachability requires an integrator path that deserializes `ThresholdKeys` from untrusted/attacker-influenced bytes (backup/restore, recovery exchange, or peer-supplied key material — the crate explicitly exposes `read`/`serialize` for key transport and `promote`/`recovery` flows consume such bytes). No local secret is needed to mount it; the malformed bytes fully determine the resulting group key. Exploitation is deterministic once the keys are loaded and used for FROST signing or address derivation (e.g., a Bitcoin wallet address derived from `group_key == identity` or from a key whose shares do not interpolate correctly reports received funds that either anyone can steal or no one can spend).

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), validate the material:

1. Reject identity verification shares (`verification_shares.values().any(is_identity)`).
2. Check `C::generator() * secret_share == verification_shares[&params.i()]` — the holder's share must match its verification share.
3. Reject `group_key == identity` after interpolation.
4. Consider binding all `n` verification shares (not just `1..=t`) into the computed/checked group key, or document that shares above index `t` are unauthenticated hints.
5. Return a `DkgError` for semantically invalid keys instead of constructing them, removing the reliance on the FROST `complete` InternalError fallback.

### Proof of Concept
```rust
// Craft bytes for ThresholdKeys::<C>::read: t = 1, n = 1, i = 1, Lagrange,
// secret_share = arbitrary, verification_shares[1] = identity.
let mut buf = Vec::new();
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes()); // t
buf.extend(&1u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes()); // i
buf.push(1);                     // Interpolation::Lagrange
buf.extend(<C::F>::random(&mut OsRng).to_repr().as_ref()); // any secret_share
buf.extend(C::G::identity().to_bytes().as_ref());          // verification_shares[1]

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

// Any (R, s) with s*G == R now verifies under keys.group_key() in
// AlgorithmSignatureMachine::complete -> algorithm.verify(group_key, Rs, sum),
// i.e., signatures for this "threshold" key are forgeable by anyone.
```

All checks in `ThresholdKeys::new` (map length, participant bounds, interpolation applicability) pass; only the semantic validity of the shares is missing — the same class as the ShareToken report's unset-whitelist bypass.
