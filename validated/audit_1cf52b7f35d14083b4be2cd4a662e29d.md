### Title
Unauthenticated `ThresholdKeys` deserialization accepts attacker-defined shares — forged signatures under an attacker-chosen group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reconstructs a full threshold-signing keypair (secret share + verification shares) from raw bytes with only syntactic validation: curve-ID match, `t <= n`, `i <= n`, canonical scalars/points. It never verifies that the supplied `secret_share` is consistent with `verification_shares[i]` (`secret_share * G == verification_shares[i]`), nor that the shares were produced by any authorized DKG. Additionally, `ThresholdKeys::new` derives `group_key` exclusively from `verification_shares[1..=t]` (participants `1..=t`), so the remaining `t+1..=n` verification shares never influence the committed group key. Analogous to the Chamilo endpoint guarded only by "is enrolled" rather than "is authorized for this action", this deserialization guards only "is parseable" rather than "is a consistent, authorized key set".

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i`, the interpolation vector, `secret_share`, and `n` verification shares directly from the reader, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (lines 349-391) checks only the count and index bounds of `verification_shares`, then computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Two missing checks:

1. **No share/key consistency check**: `secret_share` is never compared against `verification_shares[i]`. A crafted blob can pair any scalar with any verification-share map. Downstream, `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:398) uses `view.secret_share()` (derived from the attacker-supplied `secret_share`) to produce the share, while `complete` (sign.rs:447-495) verifies only the aggregate signature against `view.group_key()` — which is itself derived from the attacker-supplied verification shares. The whole chain is self-consistent under whatever key the attacker chose.

2. **Group key commits only to participants `1..=t`**: shares `t+1..=n` are parsed and stored but contribute nothing to `group_key`. Swapping or forging those entries in serialized bytes leaves the group key unchanged while changing what individual verification-share checks later "prove" (e.g., `view()` lines 500-507 interpolates whatever is stored, and share-verification blame in `complete` is judged against these attacker-controlled shares).

The code itself acknowledges the consequence: `AlgorithmSignatureMachine::complete` ends with `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` and comments that "the only known way to cause this ... is to deserialize a semantically invalid FrostKeys" — i.e., invalid keys are a known, unhandled input class rather than a rejected one.

### Impact Explanation
Any unprivileged party who can feed bytes into `ThresholdKeys::read` (e.g., a key-backup/restore path, a coordinator-supplied key blob, or any channel where serialized `ThresholdKeys` cross a trust boundary) obtains a machine that:

- produces valid FROST signature shares and complete Schnorr signatures under a **group key fully controlled by the attacker** (choose secret scalars, set `verification_shares[1..=t] = G * share_i`), or
- impersonates participation in an existing multisig with mismatched share/verification data, corrupting per-participant blame (`verify_share` checks run against the forged `verification_shares`).

This yields a forged-signature primitive: `complete` returns `Ok(sig)` where `sig.verify(group_key, c)` holds — for a `group_key` that never underwent any DKG or authorization. It is a concrete violation of the "concrete signing / forged proof" acceptance bar, rooted in deserialization accepting structural validity as authorization.

### Likelihood Explanation
Reachability is direct: `ThresholdKeys::read` is one of the designated untrusted-byte entry points and requires no authentication. Exploitation requires an attacker to control the serialized bytes handed to a signer — realistic wherever keys are restored from storage/backup or transmitted rather than produced in-process by the PedPoP DKG. No cryptographic assumption is broken; no collusion needed. Severity is bounded by whether the consuming system authenticates the provenance of key blobs out-of-band; the crate itself provides no such binding (there is no embedded hash or MAC tying the blob to a DKG transcript).

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and return an error on mismatch.
- Document and/or enforce that `group_key` derivation from only `1..=t` is intentional; preferably commit `group_key` to all `n` verification shares (e.g., a transcript hash stored in the blob) so tampering with shares `t+1..=n` is detectable.
- Consider storing a binding tag (hash of the DKG transcript/context) in the serialization so restored keys are bound to the session that produced them.

### Proof of Concept
```rust
// Attacker crafts bytes for ThresholdKeys<Secp256k1> (t = n = 1, i = 1).
let secret = Secp256k1::random_nonzero_F(&mut OsRng);          // attacker-chosen
let vshare = Secp256k1::generator() * secret;                  // self-consistent, or arbitrary

let mut blob = vec![];
blob.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
blob.extend(Secp256k1::ID);
blob.extend(1u16.to_le_bytes());        // t
blob.extend(1u16.to_le_bytes());        // n
blob.extend(1u16.to_le_bytes());        // i
blob.push(1);                          // Lagrange
blob.extend(secret.to_repr().as_ref()); // secret_share
blob.extend(vshare.to_bytes().as_ref());// verification_shares[1]

let keys = ThresholdKeys::<Secp256k1>::read(&mut blob.as_slice()).unwrap();
// keys.group_key() == attacker-chosen vshare; no DKG ever occurred.
// AlgorithmMachine::new(alg, keys).preprocess/sign/complete now yield
// signatures that verify under the attacker's key.
```

To demonstrate the share/substitution variant, set `verification_shares[i]` to an honest participant's share while setting `secret_share` to a different scalar — deserialization succeeds, and the inconsistency is only detected (if at all) as an opaque `InternalError` at `complete`, after shares have already been broadcast.
