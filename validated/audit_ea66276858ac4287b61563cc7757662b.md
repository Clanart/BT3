### Title
Unbounded protobuf-unmarshal allocation amplification in the Cosmos Tx decoder allows memory-exhaustion DoS from any submitted transaction - ([File: sei-cosmos/x/auth/tx/decoder.go])

### Summary
The Adminer report is a DoS caused by an unauthenticated, crafted serialized payload forcing PHP to allocate far more memory than the wire size of the payload implies (CWE-502-adjacent amplification DoS). The closest reachable analog in sei-chain is the Cosmos SDK transaction decoder used on every `CheckTx`/`DeliverTx` path: `defaultTxDecoder` unmarshals `TxRaw`, `TxBody`, and `AuthInfo` with plain gogoproto `Unmarshal` [1](#0-0)  with no bound on the Go-heap allocation that a maliciously crafted, repeated-field-heavy wire payload can trigger — the exact wire-to-heap amplification class that the sei-tendermint team has already identified and mitigated (but only for p2p-layer protobuf messages).

### Finding Description
sei-tendermint added `protoutils.allocEstimate`/`UnmarshalWithLimit` specifically to bound "wire-to-Go amplification," where a small protobuf payload (e.g., tens of KB) encodes thousands of empty repeated-message/scalar entries that each cause a full Go struct/slice-header allocation during `proto.Unmarshal`, producing multi-MB heap blowups from tiny inputs [2](#0-1) [3](#0-2) . Their own load tests demonstrate ~20KB of wire bytes turning into "many MB" of allocation without the guard [4](#0-3) , and unit tests show similar amplification for unpacked repeated scalars, maps, and gogoproto message types like `tmproto.Commit.Signatures` [5](#0-4) [6](#0-5) .

However, `UnmarshalWithLimit`/`UnmarshalGogoWithLimit` are only invoked from that package's own test files — no production call site was found anywhere in the codebase (verified via repo-wide search matching zero non-test usages). The application-level transaction decoder that every submitted Cosmos transaction passes through — `defaultTxDecoder` in `sei-cosmos/x/auth/tx/decoder.go`, used for both `CheckTx` and `DeliverTx` — calls `cdc.Unmarshal` (gogoproto) directly on `TxRaw`, `TxBody`, and `AuthInfo` with no equivalent allocation-amplification guard [7](#0-6) . Critically, this decode happens *before* the ante-handler chain runs (including `ConsumeGasForTxSizeDecorator`, which only charges gas per wire byte, not per allocated heap byte) [8](#0-7) , so the unmarshal cost is incurred unmetered and ungated. Fields such as `AuthInfo.SignerInfos` (a direct `repeated` message, not wrapped in `Any`) can be packed with a very large number of near-empty entries that are cheap on the wire but expensive as Go structs — the same amplification pattern already proven exploitable against gogoproto types elsewhere in this codebase.

### Impact Explanation
Any unprivileged client can submit a transaction via the public RPC `broadcast_tx_*`/`CheckTx` surface. A crafted, size-bounded transaction with a wire-cheap but heap-expensive `AuthInfo`/`TxBody` payload can force a disproportionate memory allocation on decode, before signature verification, fee checks, or gas metering occur. Repeated submissions (or concurrent submissions from multiple senders) can drive node memory usage up rapidly, causing GC pressure, latency spikes, or OOM — a crash/hang of a default-configuration validator or RPC node consistent with the "crash of default-configuration RPC nodes" / "block delay beyond 2.5 seconds" impact bar.

### Likelihood Explanation
Likelihood is moderate-to-uncertain rather than fully proven: the exact amplification factor depends on the configured mempool `max_tx_bytes` cap and the specific message/field layout chosen by an attacker, and I was not able to fully verify the effective tx-size limit enforced in this deployment's default config or confirm empirically (via execution) the achievable amplification ratio for `AuthInfo`/`TxBody` structures, since this is a read-only code review. The underlying bug class (wire-to-heap amplification in gogoproto/protobuf `Unmarshal`) is proven to exist and previously fixed for p2p messages in this same codebase, which strongly suggests the Tx-decode path shares the same weakness because it uses the identical unmarshal mechanism without the mitigation.

### Recommendation
Apply the same allocation-bounding technique already implemented in `sei-tendermint/internal/protoutils` (`allocEstimate`/`UnmarshalWithLimit`) to the Cosmos Tx decode path in `sei-cosmos/x/auth/tx/decoder.go`, estimating and capping the projected heap allocation for `TxRaw`, `TxBody`, and `AuthInfo` before calling `cdc.Unmarshal`, with the limit enforced ahead of/independent from tx-size gas charging so that decode cost cannot be incurred for free by rejected transactions.

### Proof of Concept
Not independently executed (no code-execution access in this review). Conceptually: encode an `AuthInfo` protobuf message whose `signer_infos` repeated field contains a very large number of minimal/empty `SignerInfo` entries (each ~2–3 bytes on the wire), keeping total `AuthInfoBytes` under the configured `max_tx_bytes`, and submit it via `broadcast_tx_sync`/`CheckTx`. Following the same methodology as `sei-tendermint/internal/protoutils/alloc_scan_test.go`'s `TestUnmarshalGogoWithLimit_ManyEmptySignaturesRejected` (10k empty `CommitSig` entries kept wire-size under 1MB but exceeded a 1MB allocation estimate) [5](#0-4) , an analogous crafted `AuthInfo`/`TxBody` should be constructed and measured against `defaultTxDecoder` to confirm the achieved allocation-to-wire-size ratio in this specific message schema.

// UnmarshalWithLimit estimates the heap allocation that proto.Unmarshal would
// make for bytes and returns an error if the estimate exceeds limitBytes.
// This bounds allocation amplification where a small wire payload encodes many
// empty repeated-field entries, each causing a Go heap allocation. The estimate
// is conservative (may over-count) so legitimate messages must stay well within
// the limit.
func UnmarshalWithLimit[T Message](bytes []byte, limitBytes int) (T, error) {
	if limitBytes <= 0 {
		panic(fmt.Sprintf("protoutils: limitBytes must be positive, got %d", limitBytes))
	}
	if err := Scan[T](bytes); err != nil {
		return utils.Zero[T](), err
	}
	desc := New[T]().ProtoReflect().Descriptor()
	est, err := allocEstimate(bytes, desc)
	if err != nil {
		return utils.Zero[T](), fmt.Errorf("protoutils: alloc scan: %w", err)
	}
	if est > limitBytes {
		return utils.Zero[T](), fmt.Errorf("protoutils: message would allocate ~%d bytes, limit is %d", est, limitBytes)
	}
	t := New[T]()
	if err := proto.Unmarshal(bytes, t); err != nil {
		return utils.Zero[T](), err
	}
	return t, nil
}

// TestUnmarshalGogoWithLimit_ManyEmptySignaturesRejected verifies that
// UnmarshalGogoWithLimit protects gogoproto-generated Tendermint P2P types.
// A Commit with 100k empty CommitSig entries is tiny on the wire but would
// allocate many structs during Unmarshal.
func TestUnmarshalGogoWithLimit_ManyEmptySignaturesRejected(t *testing.T) {
	// CommitSig has a non-nullable time.Time timestamp that encodes non-zero
	// even when empty, so wire bytes grow faster than a purely empty message.
	// Use 10k entries: small enough to stay comfortably under 1MB on the wire
	// while still causing enough struct allocations to exceed the 1MB limit.
	msg := &tmproto.Commit{Signatures: make([]tmproto.CommitSig, 10_000)}
	bz, err := gogoproto.Marshal(msg)
	require.NoError(t, err)
	require.Less(t, len(bz), 1<<20, "wire bytes should be well under 1MB")

	out := &tmproto.Commit{}
	err = protoutils.UnmarshalGogoWithLimit(bz, out, 1<<20 /* 1MB */)
	require.Error(t, err, "10k CommitSig entries should exceed the 1MB allocation estimate")
}

func TestUnmarshalWithLimit_UnpackedRepeatedScalarSliceHeaderCounted(t *testing.T) {
	// SizedOk.f64_count is repeated fixed64 (field 14). fixed64 always uses
	// Fixed64Type wire encoding — never packed. Each occurrence costs 8 bytes
	// element + 24 bytes slice header = 32 bytes in the estimate.
	// 100k occurrences × 32 = ~3.2MB, well over the 1MB limit.
	// Wire size: 100k × (1 tag + 8 value) = ~900KB, under 1MB.
	var bz []byte
	for range 100_000 {
		bz = protowire.AppendTag(bz, 14, protowire.Fixed64Type)
		bz = protowire.AppendFixed64(bz, 0)
	}
	require.Less(t, len(bz), 1<<20, "wire bytes should be under 1MB")
	_, err := protoutils.UnmarshalWithLimit[*pb.SizedOk](bz, 1<<20)
	require.Error(t, err, "100k unpacked fixed64 elements should exceed 1MB due to per-occurrence slice header cost")
}
