### Title
`_openInBrowser` opens attacker-supplied Check/Status URLs from the GitHub API with no protocol allowlist, unlike other URL-entry points in Desktop - (File: app/src/lib/stores/app-store.ts)

### Summary
GitHub Desktop already has a pattern for validating URLs before trusting them: `validateURL()` in `enterprise-validate-url.ts` strictly rejects any protocol other than `https:` when a user enters a GitHub Enterprise server address. [1](#0-0)  However, the single choke-point used to actually launch a URL in the OS default handler, `AppStore._openInBrowser`, performs **no protocol or host validation at all** — it just forwards whatever string it receives straight to `shell.openExternal`. [2](#0-1) 

### Finding Description
`_openInBrowser` is the shared implementation behind `Dispatcher.openInBrowser`, which is called from many UI surfaces that render **attacker-influenced GitHub API data**, not just app-generated URLs:

- Check run "View on GitHub" / "View Job Step" buttons pass `checkRun.htmlUrl`, a field sourced directly from the Checks/Statuses API, straight to `openInBrowser`: [3](#0-2) 
- The equivalent path in the failed-checks notification does the same with `checkRun.htmlUrl`: [4](#0-3) 

The commit-status/check-run `target_url`/`details_url` field is set by whatever CI system or GitHub App posts the status, and for a public repository any contributor able to configure a status check (e.g. via a personal token, a GitHub Action in their own fork, or a public CI integration) controls that string. That value flows: `checkRun.htmlUrl` → `Dispatcher.openInBrowser(url)` → `AppStore._openInBrowser(url)` → `shell.openExternal(url)` [5](#0-4) [2](#0-1)  — with zero scheme/host restriction anywhere along the chain.

The main-process IPC handler that ultimately backs `shell.openExternal` in the renderer-facing `app-shell.ts` also does not enforce a protocol allowlist; it only *logs* when a URL looks like `http(s)://` but does not block anything else before calling `shell.openExternal(path)`: [6](#0-5) 

This is the exact class of bug described in the seed report: one code path (`validateURL`, used for the GHE sign-in field) enforces "only `https:` is allowed," while the parallel/sibling code path that performs the analogous sensitive action — launching an external URI sourced from untrusted, attacker-influenced data — has no such guard. An attacker doesn't need to touch the sign-in flow at all; they just need to get a crafted URL into any GitHub API object that Desktop later feeds into `openInBrowser`.

### Impact Explanation
`shell.openExternal` with an unvalidated URI is a well-documented Electron attack surface: a crafted `file://` UNC path (e.g. `file://attacker-host/share/`) can trigger Windows to initiate outbound SMB/NTLM authentication to an attacker-controlled host, leaking NTLM credential material; certain OS-registered custom protocol handlers can also be abused for command/argument smuggling depending on installed applications. Because the URL here originates from GitHub API check/status data rather than a git remote, it satisfies the "attacker controls a GitHub API object" criterion, and the result (credential exfiltration / unintended OS-level handler invocation) is a legitimate reportable impact — though the severity is bounded by requiring a user to click "View on GitHub"/"View Job Step" in the UI.

### Likelihood Explanation
Likelihood is high for exploitation but requires user interaction (clicking the "view on GitHub" affordance for a check run they don't control, e.g. on a fork's PR). Any external CI integration, GitHub App, or contributor with permission to post a commit status/check run on a repository the victim has open in Desktop can set the malicious `target_url`/`details_url`.

### Recommendation
Centralize outbound URL handling through a single validator (reusing or generalizing `validateURL`'s protocol allowlist from `app/src/ui/lib/enterprise-validate-url.ts`) and enforce it inside `AppStore._openInBrowser` (and/or the `open-external` IPC handler in `app/src/main-process/main.ts`) so that only `http:`/`https:` URLs are ever passed to `shell.openExternal`, regardless of whether the URL came from user input, git remote data, or a GitHub API response field like `checkRun.htmlUrl`.

### Proof of Concept
1. As a contributor (or via a CI integration) with permission to post a commit status/check run on a repository, set the status/check's `target_url`/`details_url` to a malicious value, e.g. a Windows UNC-style `file://` URI pointing at an attacker-controlled SMB share.
2. Victim opens the PR/commit in GitHub Desktop and clicks "View on GitHub" / "View Job Step" for that check in `ci-check-run-popover.tsx` (`onViewCheckDetails`/`onViewJobStep`) or in the failed-checks notification (`onViewOnGitHub`).
3. `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser(url)` → `shell.openExternal(url)` is invoked with no protocol check, causing the OS to resolve the crafted URI (e.g. triggering outbound SMB authentication, leaking the victim's NTLM credentials to the attacker-controlled host).

Note: I was not able to fully verify within the available searches whether any markdown/URL sanitizer elsewhere in the renderer intercepts and re-validates `checkRun.htmlUrl` before it reaches `LinkButton`/`openInBrowser`; if such a sanitizer exists it would need to be checked for completeness, but no such call was found on the `_openInBrowser`/`open-external` code paths cited above.

```typescript
export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
```

```typescript
  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)

    try {
```
