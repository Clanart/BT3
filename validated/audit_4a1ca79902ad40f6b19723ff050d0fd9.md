## Analysis

The external report's core issue is: **a privileged sink (liquidity transfer) is reachable through an entry point that performs no validation of the caller or the input it's about to act on.** The closest structural analog in GitHub Desktop is the `open-external` IPC handler in the main process, which is the trust boundary between the (less-trusted, content-rendering) renderer and the OS-level `shell.openExternal` call — and it does not validate the URL scheme before invoking it.

### Title
Unvalidated scheme in `open-external` IPC handler allows opening arbitrary local resources/UNC paths from attacker-controlled GitHub content - (File: `app/src/main-process/main.ts`)

### Summary
The main process exposes an `open-external` IPC handler that forwards whatever string the renderer sends straight to Electron's `shell.openExternal`, with no allow-list or scheme validation. [1](#0-0) 

### Finding Description
`shell.openExternal` is invoked for links that ultimately originate from GitHub-hosted, attacker-influenceable data: pull request bodies/comments rendered as markdown, check-run URLs, PR review comments, notification banners, etc. The renderer components that surface these links call this same IPC channel from many different places (`pull-request-quick-view.tsx`, `ci-check-run-popover.tsx`, `pull-request-comment.tsx`, `pull-request-review.tsx`, `menu-update.ts`, and others). [1](#0-0) 

Only one of these call sites — the sandboxed markdown renderer — documents that it verifies a clicked link is `https` before invoking the callback: [2](#0-1) 

But the actual privileged action happens in the main process, and the main-process handler itself does not enforce this restriction — it only special-cases `http`/`https` for a log message and otherwise unconditionally calls `shell.openExternal(path)`:
```
app/src/main-process/main.ts:581-597
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (pathLowerCase.startsWith('http://') || pathLowerCase.startsWith('https://')) {
    log.info(`opening in browser: ${path}`)
  }
  try {
    await shell.openExternal(path)
    return true
  } ...
})
```
This mirrors the router bug's broken invariant exactly: the *enforcement point that matters* (the process boundary that actually performs the privileged action) trusts its caller/input implicitly, while any validation that exists lives only in one of several upstream callers and is not guaranteed to be applied uniformly across every code path that reaches this IPC channel.

### Impact Explanation
`shell.openExternal` with a non-`http(s)` value is a well-known Electron footgun: passing a UNC path (`\\attacker-host\share\file`) or certain custom protocol/file URIs can cause the OS shell to initiate an outbound SMB connection (leaking the Windows NTLM handshake / credential material) or open local files/executables via a registered protocol handler outside the app's control. Since the values reaching this handler are sourced from GitHub API objects (PR body, comments, check-run metadata) supplied by a fork/PR author, this satisfies the "attacker controls a GitHub API object" impact category — potentially resulting in credential exfiltration or execution of unintended local resources without the user consciously navigating to an external URL.

### Likelihood Explanation
Exploitability depends on whether any of the several call sites that forward URLs to this channel fail to re-validate the scheme the way `sandboxed-markdown.tsx` does. Because the check lives in only one renderer component and the main process does not re-enforce it, this is a **defense-in-depth gap** rather than a confirmed exploitable path from every surface — I could not fully trace every caller (e.g. `pull-request-quick-view.tsx`, `ci-check-run-popover.tsx`) within the available context to confirm each one performs an equivalent `https`-only check before invoking `open-external`. This uncertainty is a limitation of what I could verify with the tools available; a Devin session with full repo access would be needed to enumerate every call site and confirm whether all of them gate on scheme before calling the shared IPC channel.

### Recommendation
Enforce the scheme allow-list (`http:`/`https:` only, or a documented explicit allow-list including `mailto:` if needed) inside the `open-external` main-process handler itself, since that is the actual trust boundary, rather than relying on renderer-side call sites to have each independently implemented the same check.

### Proof of Concept
Not independently confirmed end-to-end due to indexing limitations on every renderer call site; the concrete PoC would be: attacker opens a PR whose body/comment/check-run text contains a link with a UNC/non-http scheme; if any renderer surface that displays it forwards the raw string to `dispatcher`/`main-process-proxy` → `ipcRenderer.invoke('open-external', url)` without an https-only check, then opening that link triggers `shell.openExternal` with attacker-controlled non-http content on the victim's machine.
