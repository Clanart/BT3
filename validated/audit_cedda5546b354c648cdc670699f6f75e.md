## Analysis

Reducing the report to its essential shape: a safety/validation mechanism exists specifically to stop an attacker-controlled input from producing an unsafe/unintended result, and the codebase deliberately disables that guard for a code path that is fully driven by attacker-controlled data (a message hash in the original report; a cloned repository's contents here).

In GitHub Desktop, the exact analog is the clone implementation unconditionally turning off Git's own protections against malicious recursive-submodule clones.### Title
Recursive clone disables Git's built-in clone-protection guard, reintroducing malicious-submodule RCE - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for every `git clone --recursive` invocation, including clones of attacker-controlled URLs triggered from the UI or from the `x-github-client://openRepo/...` deep-link handler. `GIT_CLONE_PROTECTION_ACTIVE` is the flag Git uses internally to guard the recursive-clone/submodule-checkout path against the class of attack fixed as CVE-2024-32002 (malicious submodules using case-insensitive/symlink tricks on `.git`/hooks paths to get arbitrary files planted and executed during `clone --recursive`). By force-disabling this guard on every clone, Desktop removes the very check that is supposed to prevent an attacker-controlled repository from corrupting or escaping the intended clone target. [1](#0-0) 

### Finding Description
`clone()` builds the environment for the `git clone --recursive` command and hard-codes the protection flag off, with no conditional or opt-in: [2](#0-1) 

This applies to every clone regardless of the source, including the deep-link-driven "Open in Desktop" flow, where an attacker supplies the `url` (and optionally `branch`) entirely through a link a victim clicks. `parseAppURL` only validates branch name characters, not the target URL's trustworthiness, and hands the raw remote URL through to the clone pipeline: [3](#0-2) [4](#0-3) 

`clone()` also always passes `--recursive`, meaning any submodules declared by the attacker-controlled repository are automatically initialized and checked out in the same protection-disabled clone invocation: [5](#0-4) 

The existing guard in this same function — `isClonePathSensitive` — only validates the *destination* path against a fixed deny-list (home dir, `.ssh`, `.gnupg`, `.config`, `APPDATA`); it does nothing to constrain what a malicious submodule inside the cloned repository can do to files under the resulting clone directory (e.g., planting a symlinked `.git`/hooks entry that would normally be caught by Git's own clone protections): [6](#0-5) 

So the invariant that's broken is the same shape as the original report: a safety check exists specifically to stop attacker-controlled content from producing an unintended, unsafe result, and the caller deliberately turns that check off for the exact operation (recursive clone of untrusted content) it was designed to protect.

### Impact Explanation
If the underlying Git binary bundled with Desktop enforces `GIT_CLONE_PROTECTION_ACTIVE` the way upstream Git does for the CVE-2024-32002 protections, disabling it during `--recursive` clone reopens the path for a malicious repository with a crafted submodule to write files outside the intended working tree location (e.g., into the `.git` hooks path via symlink/case-collision tricks), which Git then may execute as part of checkout — i.e., code execution triggered purely by cloning an attacker-controlled repository. This satisfies the "valid impact" bar: attacker controls a cloned/fetched repository, and the outcome is code execution / file write outside the repo, achieved with no local access, admin rights, or pre-existing compromise — only the user cloning a repo or opening a deep link.

### Likelihood Explanation
High relative to the class: the disabling is unconditional (not behind a flag, not scoped to trusted sources), and `clone()` is reachable both from normal "Clone repository" UI flow and from the `open-repository-from-url` deep-link action, which an attacker can deliver via a web page or message (`x-github-client://openRepo/<attacker-url>`) without any unusual user steps beyond clicking a link and confirming the clone, which is the expected Desktop workflow.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for clones of untrusted/remote URLs. Only relax this protection, if at all, for verified/first-party operations, and otherwise let Git's default (protection-active) behavior stand for `git clone --recursive`. If the override exists to work around a specific compatibility issue, scope it narrowly and document why disabling a security control is safe in that specific context, and add regression tests confirming that a submodule attempting the symlink/case-collision attack is rejected during Desktop clones.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule crafted per the CVE-2024-32002 technique (a submodule whose path collides case-insensitively with `.git`, using a symlink to redirect Git's hook execution during checkout).
2. Attacker sends the victim a link such as `x-github-client://openRepo/https://github.com/attacker/evil-repo`.
3. Victim clicks the link; `parseAppURL` accepts it as `open-repository-from-url` and Desktop calls `clone()` with the attacker's URL. [3](#0-2) 
4. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false`, disabling Git's own defense against the submodule symlink attack. [1](#0-0) 
5. During the automatic recursive submodule checkout, the malicious submodule's crafted content is written/executed via the hooks path outside the intended clone directory, achieving code execution on the victim's machine as soon as the clone (triggered by clicking a link) completes.

Note: I could not execute Git locally to empirically confirm the exact upstream semantics/behavior of `GIT_CLONE_PROTECTION_ACTIVE` in the bundled Git version, since only static code search tools were available in this session — this should be verified against the vendored Git/dugite binary's source before treating this as fully confirmed exploitable, but the code pattern (unconditionally disabling a named "protection" flag for exactly the operation it protects) is a clear and concrete red flag independent of that confirmation.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
