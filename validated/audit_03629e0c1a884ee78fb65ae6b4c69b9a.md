### Title
Attacker-controllable HTTP response header spoofs GitHub Enterprise host detection, triggering a trusted-looking sign-in prompt for an untrusted git remote - (File: `app/src/lib/api.ts`, `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The credential helper decides whether to treat a git remote host as a genuine GitHub/GitHub Enterprise (GHE) endpoint using a chain of heuristics that ends in `isGitHubHost()`. When none of the earlier, reliable classifications apply (not `github.com`, not a known GHE account, no `WWW-Authenticate: realm="GitHub"` header seen), the code falls back to making an unauthenticated network probe to the remote itself and trusts a header (`x-github-request-id`) that the attacker's own server can freely set. This mirrors the report's broken invariant: when the object cannot be matched against a trusted table, the code silently falls back to a weaker classification that the attacker fully controls.

### Finding Description
`getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies a git-credential request's endpoint into `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`: [1](#0-0) 

The last-resort branch calls `isGitHubHost(endpoint)`: [2](#0-1) 

`isGitHubHost()` in `app/src/lib/api.ts` performs a `HEAD` request to `${endpoint}/meta` and classifies the host as a GitHub host purely based on the presence of the `x-github-request-id` response header: [3](#0-2) 

This header is attacker-controllable: any HTTP server the attacker operates can add `x-github-request-id: <anything>` to its response, with no cryptographic binding to GitHub. There is no TLS certificate pinning, no signature validation, and no check that the response actually originates from GitHub's infrastructure — unlike `isDotCom`/`isGHE`, which compare against configured, previously-authenticated endpoints, this path trusts an arbitrary response from an as-yet-unknown host.

Back in `getCredential()`, once `getEndpointKind()` returns anything other than `'generic'` for a host with no matching stored account, Desktop calls `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

This means an attacker who controls the git server behind a remote URL (e.g. added via `git clone`, a fetch, or a deep link that resolves to `open-repository-from-url`) can make Desktop believe the remote is a legitimate GitHub Enterprise host, causing Desktop itself to surface a "Sign in to GitHub" prompt scoped to the attacker's domain. This is materially different from, and more dangerous than, a generic-git-auth prompt because it borrows Desktop's own GitHub Enterprise sign-in UX/OAuth flow and implicitly signals trust ("this looks like an enterprise GitHub instance") to the user.

### Impact Explanation
If the user completes the resulting GitHub-style sign-in for the attacker's spoofed "enterprise" endpoint, Desktop will store an `Account` object (login + token) associated with the attacker-controlled endpoint. Because git credential resolution and other endpoint-scoped operations rely on this stored account/endpoint pairing (e.g., `findGitHubTrampolineAccount`, `getAPIEndpoint`), this can result in:
- The user's real credentials/token being solicited for and sent to an attacker-controlled host that Desktop misrepresented as a trusted GitHub Enterprise server.
- Subsequent silent reuse of that "account" for later interactions with the same attacker-controlled endpoint (repository access, PR checkout flows, etc.), since the account is now persisted as a legitimate GHE account.

This matches the accepted impact class ("attacker controls...a git remote/proxy response...resulting in...unauthorized OAuth or account binding" / credential exfiltration).

### Likelihood Explanation
The attacker only needs to control the server behind a git remote URL the user is induced to add (via clone, fetch, or an `x-github-client://openRepo/...` deep link handled by `parseAppURL`/`openRepositoryFromUrl`), and to add one static response header to their HTTP server. No other classification branch (`isDotCom`, `isGHE`, existing-account match, `wwwauth` realm) needs to succeed — this is precisely the fallback path reached whenever the pair (host, no-known-account) is not already tracked, directly analogous to the `(target, selector)` fallback in the original report.

### Recommendation
- Do not classify an unknown host as an "enterprise" GitHub host based solely on a spoofable response header. At minimum, corroborate with something not trivially forgeable by any HTTP server (e.g., a documented signed response, certificate transparency data, or simply require explicit user confirmation/account setup before ever treating an unknown endpoint as GitHub Enterprise for the purposes of a sign-in prompt).
- Have `getEndpointKind()` fall back to `'generic'` credential handling by default instead of `'enterprise'` when classification is only based on the heuristic network probe, and require an explicit, user-initiated "Add Enterprise Server" action before offering the trusted GHE sign-in UI for a new host.

### Proof of Concept
1. Attacker stands up an HTTP(S) server at `git.attacker.example` that responds to `HEAD /meta?ghd=*` with header `x-github-request-id: 1234:ABCD:....`.
2. Victim adds/clones/fetches from `https://git.attacker.example/foo/bar.git` (e.g., via a crafted `x-github-client://openRepo/https://git.attacker.example/foo/bar` deep link handled by `parseAppURL`/`dispatchURLAction`/`openOrCloneRepository`).
3. During the git credential-helper `get` flow, `getEndpointKind()` fails all reliable checks and calls `isGitHubHost('https://git.attacker.example')`, which performs the HEAD request and observes the attacker-set `x-github-request-id` header, returning `true`.
4. `getCredential()` sees `endpointKind !== 'generic'` and no matching account, and invokes `ui.promptForGitHubSignIn('https://git.attacker.example')`, presenting Desktop's trusted "Sign in to GitHub Enterprise" UI for the attacker's host.
5. If the victim completes sign-in, an `Account` bound to the attacker's endpoint is created/stored, and their real credentials are sent to the attacker's OAuth endpoint.

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
