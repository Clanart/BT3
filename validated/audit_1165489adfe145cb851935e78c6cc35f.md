### Title
Stale line-index diff selection is silently replayed against a freshly re-fetched diff, corrupting partial commits - (File: app/src/lib/stores/updates/changes-state.ts, app/src/lib/git/apply.ts)

### Summary
GitHub Desktop's partial-staging feature stores a user's line selection as a set of *line indices* (`DiffSelection`), not as content-addressed line identifiers. When the working directory status refreshes, that same `DiffSelection` object is carried over to the new file object purely by file id (path), without checking whether the underlying diff actually changed. At commit time, `applyPatchToIndex` fetches a **brand-new** diff and blindly re-applies the old, potentially stale, index-based selection to it via `formatPatch`. If a repo-controlled process (e.g. a `post-checkout`/`post-merge` hook run automatically by Desktop, see above) rewrites a tracked file's content between the moment the user reviews/selects lines in the Changes view and the moment they click "Commit", the line indices no longer point at the lines the user actually looked at — yet the patch is generated and applied anyway.

### Finding Description
- The working-directory diff is loaded once and shown to the user, who then selects/deselects specific lines using `DiffSelection.withLineSelection`/`withRangeSelection`, which record selection purely as line-index sets. [4](#0-3) 
- Whenever `getStatus`/`_loadStatus` refreshes the working directory (this happens continuously in the background via polling/`_refreshRepository`), `updateChangedFiles` merges the *old* `DiffSelection` object onto the *new* file object solely by matching `file.id` (path), with no comparison of diff content, hash, or hunk boundaries: `return file.withSelection(existingFile.selection)`. [5](#0-4) 
- When the user commits, `_commitIncludedChanges` takes the files exactly as they sit in `changesState.workingDirectory.files` (i.e., carrying that possibly-stale selection) and calls `createCommit`, which ultimately calls `stageFiles`. [6](#0-5) [7](#0-6) 
- For any file with a partial selection, `stageFiles` calls `applyPatchToIndex`, which does **not** reuse the diff the user actually reviewed — it re-fetches the diff fresh from disk (`getWorkingDirectoryDiff`) and then builds the patch by calling `formatPatch(file, diff)`, using the (stale) `file.selection.isSelected(absoluteIndex)` against the **new** diff's line indices. [8](#0-7) 
- `formatPatch` trusts `file.selection.isSelected(absoluteIndex)` line-for-line with no validation that the selection was computed against this exact diff (no hunk/content fingerprint check). [9](#0-8) 

The broken invariant is identical in shape to the Notional bug: a value (there, the WR valuation; here, the line-selection state) is priced/applied against a *different* underlying object than the one it was actually derived from, because the code assumes the referenced object (yield token amount / diff line layout) is immutable between derivation and use, when in fact repo-controlled events (slashing / hook-driven file mutation) can change it in between.

### Impact Explanation
If a tracked file's content changes between the user's diff review and the click of "Commit" — triggered by an attacker-supplied `post-checkout` or `post-merge` hook that Desktop itself proxies and executes during its automatic background fetch/pull/checkout cycle — the stale line indices from the old selection will silently map onto different lines in the new diff. This can cause GitHub Desktop to commit and push content the user never selected or intended (e.g., omitting a security fix the user thought they included, or including attacker-injected lines the user explicitly deselected), a direct "silent corruption of what the user commits or pushes" per the accepted impact classes. Because the patch is generated and applied without any warning to the user, the corruption is invisible in the UI at commit time.

### Likelihood Explanation
Requires: (1) the user has a partial (line-level) selection pending on a file, (2) a background status refresh occurs (this is routine/automatic in Desktop — refreshes happen after every fetch/pull/checkout and periodically), and (3) the file's content on disk is mutated in that window by a hook the repository ships and that Desktop's own machinery executes without additional prompting. All three conditions are plausible in normal usage of a malicious repository: partial commits are a core, commonly used Desktop feature, background refresh is unconditional, and hook execution is a first-class capability Desktop already implements for hooks discovered in the repo. No local/physical access, no admin rights, no pre-existing malware, and no unnatural user steps are required beyond the ordinary "clone/fetch a repo and use partial staging."

### Recommendation
- Invalidate/clear a file's `DiffSelection` (or convert to full "All" selection with a user warning) whenever the underlying diff for that file changes between the moment it was computed and the moment it is used to build a patch, not just when `clearPartialState` is explicitly requested.
- Bind `DiffSelection` to a content fingerprint of the diff it was derived from (e.g., hash of hunk headers/line count) instead of purely file-path identity, and reject/re-derive the selection if the fingerprint no longer matches.
- In `applyPatchToIndex`/`stageFiles`, verify that the diff used at staging time matches the diff that was last shown to/reviewed by the user before silently generating and applying a patch; if it does not match, surface an error or force the user to re-review before committing.

### Proof of Concept
1. Clone a malicious repository that ships a `post-checkout` (or `post-merge`) hook script.
2. In Desktop, open a tracked file with existing local modifications and use the line-by-line diff view to select only some lines/hunks for a partial commit; leave the commit dialog open without committing immediately.
3. Trigger a background fetch/pull (or simply wait for Desktop's periodic background refresh/fetch cycle), which causes Desktop to run the repo's hook via the `withHooksEnv`/`getRepoHooks` proxy mechanism. [2](#0-1)  The hook silently rewrites the same tracked file (e.g., inserts/removes lines earlier in the file), shifting line numbers.
4. `updateChangedFiles` on the next status refresh merges the *old* selection object onto the new file state purely by path match. [10](#0-9) 
5. Click "Commit". `applyPatchToIndex` fetches the new diff and applies the old line-index selection to it via `formatPatch`, producing a patch that stages different content than what the user actually selected in step 2. [11](#0-10) 
6. The resulting commit (and subsequent push) silently contains content the user never reviewed or approved.

Note: I was not able to fully confirm from the indexed code whether Desktop's automatic background-fetch cycle runs `post-checkout`/`post-merge` hooks specifically outside of explicit user-initiated pull/checkout actions (vs. only on explicit git operations triggered by the user), since the scheduling logic in `background-fetcher.ts` was only partially inspected. If background auto-fetch does not itself trigger a checkout/merge, the hook-firing window is still reliably reachable via the user's own routine "Fetch" / "Pull" clicks during normal use, which is unprivileged and requires no unnatural steps.
