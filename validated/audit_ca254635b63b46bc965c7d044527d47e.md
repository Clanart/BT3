### Title
`SignableTransaction::new` excludes the OP_RETURN data output from the fee/weight calculation, so the actual signed transaction pays a lower feerate than requested — (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the Rubicon `_matcho()` report — where the quantity used to drive the matching loop excluded the taker fee, so the actual consumed amount was smaller than the amount assumed (`min(m_pay_amt, t_buy_amt)` instead of `m_pay_amt + fee`) — `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` computes `needed_fee` from a weight estimate that omits one of the transaction's actual outputs. When a caller supplies `data`, an OP_RETURN output is pushed into `tx_outs` (lines 194–202), but `calculate_weight_vbytes` (lines 62–127) reconstructs a transaction only from `payments` and the optional `change` — it never includes the OP_RETURN output. The resulting `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore prices a smaller transaction than the one that will actually be signed and broadcast.

### Finding Description
`SignableTransaction::new` performs the following sequence:

1. `data` is validated to `<= 80` bytes and an OP_RETURN `TxOut` is pushed into `tx_outs` (lines 194–202).
2. `(weight, vbytes)` is computed via `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), which builds a fresh `Transaction` containing only the `payments` outputs plus optional change — the OP_RETURN output is absent.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) and the minimum-relay-fee check (lines 211–213) are both evaluated against this underestimated `vbytes`.
4. The final `tx` includes the OP_RETURN output (line 250), so the real vsize is larger than the vsize used to price the fee.

The OP_RETURN output adds ~9 + len(data) bytes (up to ~90 bytes, nearly all non-witness → 4 weight units/byte). Consequences mirror the report's pattern: the quantity the code assumes (priced vbytes) differs from the actual quantity (real vbytes) by an omitted "fee-relevant" component, and the discrepancy is attacker-reachable — `data` is untrusted caller input derived from in-instructions/`RefundableInInstruction` payloads (see `processor/src/networks/bitcoin.rs` where `data: None` is currently passed, but the wallet API accepts arbitrary 80-byte payloads and `tests/processor/src/networks.rs` shows OP_RETURN instructions being attached to deposits).

Concrete effect: with `fee_per_vbyte = 1` (sat/vbyte, the relay minimum), a transaction whose real vsize exceeds the estimated vsize by ~90 vbytes has an effective feerate of `vbytes / (vbytes + 90)` sat/vbyte. For a small tx (~150 vbytes estimated), the actual feerate is ~0.62 sat/vbyte — below `DEFAULT_MIN_RELAY_TX_FEE`, despite the check at lines 211–213 passing, because that check divides the underpriced `needed_fee` by the undercounted `vbytes`. The threshold-signed transaction will not relay/confirm, and the wallet offers no RBF or fee-bump mechanism — the inputs are effectively locked behind a non-propagating, already-signed transaction until it is replaced by an entirely new signing session.

### Impact Explanation
An unprivileged party who can cause `data` to be attached (or any caller of the wallet API) causes the multisig to produce a threshold-signed transaction whose actual fee rate is strictly below the requested `fee_per_vbyte` and potentially below the network's minimum relay fee. The signed TX is a valid consensus transaction (the fee is still `inputs - outputs`), but it pays less than intended — matching the accepted bug class of "actual amount differs from expected because a fee component was omitted from the quantity calculation." Result: signed transactions that fail to propagate or confirm, wasting a signing session and leaving payments unexecuted; in a bridge/scheduler context this stalls payouts and requires re-signing at a corrected fee.

### Likelihood Explanation
The trigger only requires `data.is_some()`. Any path feeding user-controlled bytes into `SignableTransaction::new`'s `data` parameter hits it deterministically — no race, no collusion. The severity of the outcome scales with how small the payment set is relative to the 80-byte data payload; at low fee rates (1 sat/vbyte) the underpayment can push below relay minimum for small transactions. When `data` is `None` (the current processor call site), the bug is unreachable, which bounds practical likelihood to integrations that attach OP_RETURN data.

### Recommendation
Include the data output in the weight estimate. The clean fix is to pass the OP_RETURN `ScriptBuf` (or the already-built `tx_outs`) into `calculate_weight_vbytes` rather than reconstructing outputs solely from `payments`, e.g. compute weight over `tx_outs` after the OP_RETURN push, plus the hypothetical change output. The change-calculation at lines 224–235 should likewise account for the data output's weight (it currently also prices change against `payments` only). Alternatively, drop `data` support if unused by the processor.

### Proof of Concept
```rust
// networks/bitcoin context; assumes a funded ReceivedOutput `input`
// and a P2TR `addr()` as in networks/bitcoin/tests/wallet.rs
let payments = vec![(addr(), 1000)];
// Attach an 80-byte OP_RETURN payload (max allowed)
let data = vec![0u8; 80];
let tx = SignableTransaction::new(vec![input], &payments, None, Some(data), 1).unwrap();

// needed_fee was priced without the OP_RETURN output (~90 extra vbytes)
assert_eq!(tx.needed_fee(), /* vbytes_without_opreturn */);

// The real transaction is larger, so the actual feerate is < 1 sat/vbyte
let real_vsize = tx.transaction().vsize() as u64;
assert!(tx.fee() < real_vsize); // feerate < 1 sat/vbyte -> below DEFAULT_MIN_RELAY_TX_FEE
// yet the TooLowFee check at send.rs:211 passed because it used the
// underestimated vbytes, exactly as _matcho used m_pay_amt instead of
// m_pay_amt + fee.
```

Root cause: `calculate_weight_vbytes` (`networks/bitcoin/src/wallet/send.rs:62-127`) builds its estimation `Transaction` from `payments`/`change` only, while the OP_RETURN output pushed at `send.rs:194-202` is included in the real transaction assembled at `send.rs:245-255`; `needed_fee` (line 206), the `TooLowFee` check (lines 211–213), `NotEnoughFunds` check (line 215), and the change amount (lines 224–235) all consume the underestimated size.
