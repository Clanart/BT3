## Analysis

This maps to a genuine analog in Zest's `collateral-remove` function. The Symmio bug pattern — requiring solvency to hold under *both* the pre-action state and the post-action state, when only the final (post-action) state should matter — reproduces in Zest's egroup-based health check gating.

### Title
Unnecessary pre-removal health check under the stale egroup blocks valid `collateral-remove` calls that would otherwise leave the position healthy under the new egroup - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove` enforces a health check using the position's *current* (pre-removal) egroup `LTV-BORROW` before it evaluates whether the *post-removal* state (potentially under a *different, more favorable* egroup) is healthy. This mirrors the Symmio `fillCloseRequest`/`isSolventAfterClosePosition` flaw: the code requires the position to satisfy solvency at two different parameter sets (old egroup, new egroup) instead of only requiring solvency at the final, resulting state.

### Finding Description
In `collateral-remove`, when the caller has debt: [1](#0-0) 
the code computes `current-ltvb` from `current-group`, the egroup resolved from the **pre-removal** `position-mask`, and immediately asserts that the account is healthy under this stale threshold before evaluating the removal at all: [2](#0-1) 

Only after that gate passes does the function branch on `removing-all`. If the user is removing the entirety of one collateral asset, the mask changes and the function resolves a **new** egroup (`future-mask`) and correctly checks solvency there: [3](#0-2) 

Because efficiency groups (`egroup.clar`) assign different `LTV-BORROW` thresholds to different asset-set masks — an intentional feature to grant higher LTV to correlated collateral/debt sets — a user's position can simultaneously be "unhealthy" under the current (mixed) egroup's `LTV-BORROW` while being fully healthy after removing one asset and moving into a different egroup with a materially higher `LTV-BORROW`. The line 1136 check evaluates solvency at the *wrong* (stale) parameter set — analogous to Symmio checking solvency at the market price in addition to the close price — and reverts the entire transaction (`ERR-UNHEALTHY`) even though the `is-healthy-with-mask` check at line 1143 on the *correct*, final state would have passed.

### Impact Explanation
A user whose position sits between `LTV-BORROW` and `LTV-LIQ-PARTIAL` (a legitimate, non-liquidatable state) — as documented in `docs/market.md:220-228` — is unable to execute the one corrective action (removing a specific collateral asset to switch into a more favorable egroup) that would restore their position to a fully compliant, healthy state. The transaction reverts at line 1136 before the correct post-removal health evaluation is ever reached. If price movement continues, the position can cross into liquidation territory (`LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL`) and be liquidated with a penalty, even though the user attempted and was capable of a valid, self-correcting action. This is a temporary freezing of the user's ability to manage their own position, directly leading to avoidable liquidation losses — matching the in-scope "temporary freezing of funds" (and, in the liquidation-loss tail case, fund loss) impact class.

### Likelihood Explanation
This triggers under ordinary market conditions whenever: (1) a user holds collateral spanning an egroup mask with a comparatively low `LTV-BORROW`, (2) price movement pushes them past that threshold but not past `LTV-LIQ-PARTIAL`, and (3) removing one collateral asset entirely would move them into a different, higher-LTV egroup. No governance/oracle compromise or malicious input is required — it's a natural consequence of Zest's own core "efficiency group" design combined with normal price volatility, making it moderately likely to occur for users holding multi-asset/mixed-egroup positions.

### Recommendation
Remove (or relax) the pre-removal gate at line 1136 that checks solvency against `current-ltvb`, or make it conditional such that it does not block the `removing-all` branch. The authoritative check should be the post-removal evaluation against the resulting mask's egroup (`is-healthy-with-mask` for `removing-all`, or `is-healthy` under `current-ltvb` for partial removal) — i.e., require solvency only at the final resulting state, not at both the stale and final states.

### Proof of Concept
1. Configure two egroups: Group A = {assetX + assetY as collateral, debtZ} with `LTV-BORROW = 60%`; Group B = {assetY only as collateral, debtZ} with `LTV-BORROW = 85%` (correlated-asset efficiency bonus).
2. User supplies assetX and assetY as collateral (mask resolves to Group A) and borrows debtZ such that current LTV = 70% (unhealthy under Group A's 60% `LTV-BORROW`, but below `LTV-LIQ-PARTIAL`, e.g. 85%).
3. User calls `collateral-remove` to withdraw 100% of assetX. Post-removal, only assetY remains as collateral, mask resolves to Group B (`LTV-BORROW = 85%`); with debtZ unchanged, post-removal LTV recomputed under Group B is well below 85% — i.e., healthy.
4. Transaction reverts at `(asserts! (is-healthy collateral-value debt-value current-ltvb) ERR-UNHEALTHY)` [2](#0-1)  using the stale Group A threshold, before the correct Group B check at line 1143 is ever evaluated — blocking a self-healing action that should have succeeded.
