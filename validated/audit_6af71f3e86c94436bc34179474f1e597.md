### Title
Partial-commit line selections are applied to a re-fetched diff, silently corrupting committed content - (File: app/src/lib/git/apply.ts)

### Summary
`_commitIncludedChanges` snapshots the working-directory file list and each file's `DiffSelection` (line/hunk indices chosen by the user while reviewing the diff) once, at the moment the user clicks "Commit". That snapshot is then handed, unchanged, into `createCommit` → `stageFiles` → `applyPatchToIndex`, which does **not** reuse the diff the user actually reviewed. Instead it calls `getWorkingDirectoryDiff(repository, file)` again, fresh, at staging time, and applies the previously captured line-range `selection` against this brand-new diff via `formatPatch`. If the file's on-disk content (and therefore its diff/hunk boundaries) changes between the time the user made the selection and the time `applyPatchToIndex` runs, the line indices no longer point at the same lines the user reviewed and approved — the same structural bug as the reported `withdrawAuction()` issue, where a caller-supplied parameter (`_p.crabToWithdraw` / here, `file.selection`) is computed against one state snapshot but applied against a different, later state (`usdcReceived` sum / here, the newly computed diff).

### Finding Description
- `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` synchronously and filters to `selectedFiles` before any awaits happen: [3](#0-2) .
- The function then awaits `formatCommitMessage` and the whole `createCommit` pipeline (including running commit hooks via `onHookProgress`) before the commit is actually written, all using the same, now possibly-stale `selectedFiles` array: [4](#0-3) .
- Inside that pipeline, for any file with a partial (line-range) selection, `applyPatchToIndex` is invoked. It recomputes the diff from disk right before staging (`getWorkingDirectoryDiff`) and then builds the patch to apply from that *new* diff plus the *old* `file.selection` line indices: [5](#0-4) .
- `WorkingDirectoryFileChange.selection` (a `DiffSelection`) is purely index/range based — it carries no content hash or anchor tied to the specific diff it was created against, so there is nothing to detect that the diff has drifted.
- Nothing between the initial snapshot (`_commitIncludedChanges`) and the final `git apply --cached` call re-validates that the working directory is unchanged; the only related safeguard, `isCommittingFileHiddenByFilter`, only checks whether the selected files are hidden by the *changes-list text filter* UI, not whether the underlying file content changed: [6](#0-5) .

### Impact Explanation
If the working tree for a selected file mutates during the window between the user's line-selection and the actual `git apply --cached` call (e.g. due to a background operation Desktop itself performs concurrently, such as another async git operation, a stash pop, hook execution, or any tool that rewrites the file), the indices from the old selection get replayed against different hunk/line content. The result is that `git apply --cached` can succeed while staging different lines than the ones the user selected and reviewed in the diff viewer — i.e., the commit (and anything later pushed) silently contains content the user never approved, or omits content the user believed was included. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires a real (even if narrow) timing window between selection and staging, and requires the file to actually change during that window — something not fully within the sole control of a remote/unprivileged attacker without an additional local trigger (e.g. a hook or tool that writes to the working tree while Desktop is mid-commit). This keeps the severity moderate/likelihood low-to-medium, analogous to the original report's "Medium" rating, which itself depended on a specific precondition (`isAuctionLive == false`) being met before the race was exploitable.

### Recommendation
- Have `_commitIncludedChanges`/`createCommit` capture (or re-verify) the diff used to build each file's patch at staging time, and fail/re-prompt the user if the diff used for `formatPatch` differs from the diff that produced the `DiffSelection` the user approved (e.g. by hashing the diff or comparing hunk boundaries/line counts before applying).
- Alternatively, regenerate the selection against the fresh diff and re-render the commit confirmation if a mismatch is detected, rather than silently applying stale indices to new content.

### Proof of Concept
1. Open a repository in Desktop with a modified tracked file; in the Changes list, select only a subset of lines (a partial `DiffSelection`) for that file.
2. Before the commit finishes staging (e.g., trigger any concurrent operation that rewrites the same file's on-disk content — for example a hook, editor auto-save, or another Desktop-triggered git operation that touches the working tree), click "Commit".
3. Observe that `applyPatchToIndex` (`app/src/lib/git/apply.ts:60-81`) recomputes the diff from the now-changed file and applies the old line-index selection to it, producing a committed patch that does not correspond to the lines originally shown/selected in the UI.

  public async _commitIncludedChanges(
    repository: Repository,
    context: ICommitContext
  ): Promise<boolean> {
    const state = this.repositoryStateCache.get(repository)
    const files = state.changesState.workingDirectory.files
    const selectedFiles = files.filter(file => {
      return file.selection.getSelectionType() !== DiffSelectionType.None
    })

    const gitStore = this.gitStoreCache.get(repository)

    return this.withIsCommitting(repository, async () => {
      const result = await gitStore.performFailableOperation(
        async () => {
          const message = await formatCommitMessage(repository, context)
          let aborted = false
          return createCommit(repository, message, selectedFiles, {
            amend: context.amend,
            onHookProgress: this.onHookProgress(repository),
            onHookFailure: this.onHookFailure(() => (aborted = true)),
            onTerminalOutputAvailable: subscribeToCommitOutput => {
              this.repositoryStateCache.update(repository, state => ({
                ...state,
                subscribeToCommitOutput,
              }))
            },
            noVerify: state.skipCommitHooks,
            signOff: state.signOffCommits,
            allowEmpty: state.allowEmptyCommit,
          }).catch(err => (aborted ? undefined : Promise.reject(err)))
        },
        { gitContext: { kind: 'commit' }, repository }
      )

    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

export const isCommittingFileHiddenByFilter = memoizeOne(
  (
    fileIdsIncludedInCommit: ReadonlyArray<string>,
    filteredItems: Map<string, IChangesListItem>,
    fileCount: number,
    filters: IFileListFilterState
  ): boolean => {
    // All possible files are present in the list (no active filters or all files match active filters)
    if (!hasActiveFilters(filters) || filteredItems.size === fileCount) {
      return false
    }

    // If filtered rows count is 1 and included for commit rows count is 2,
    // there is no way the included for commit rows are visible regardless of
    // what they are.
    if (fileIdsIncludedInCommit.length > filteredItems.size) {
      return true
    }

    // If we can find a file id included in the commit that does not exist in
    // the filtered items, then we are committing a hidden file.
    return fileIdsIncludedInCommit.some(fId => !filteredItems.get(fId))
  }
