### Title
Tokenfactory denom allow-list is not enforced for CosmWasm-initiated bank transfers, allowing blocked addresses to send/receive restricted denoms via the wasm bridge - (File: `sei-wasmd/x/wasm/keeper/keeper.go`)

### Summary
The tokenfactory module lets a denom admin restrict which addresses may send or receive a `factory/...` denom by setting a per-denom `AllowList` (`SetDenomAllowList`/`GetDenomAllowList`). This restriction is enforced by the bank module's `MsgSend`/`MsgMultiSend` handlers via `IsInDenomAllowList`, but the CosmWasm bank-transfer path used by contract `BankMsg::Send` execution (`BankCoinTransferrer.TransferCoins`) never calls `IsInDenomAllowList`. Any CosmWasm user can therefore move an allow-list-restricted denom to/from an address that is not on the allow list simply by routing the transfer through a contract, exactly the same "enforced-here-but-not-there" pattern described in the report (a per-item circuit breaker checked on one entry point but silently skipped on another reachable transfer path).

### Finding Description
Bank `MsgSend` enforces three checks before transferring: `IsSendEnabledCoins`, `IsInDenomAllowList` (sender and receiver), and `BlockedAddr`: [1](#0-0) 

`IsInDenomAllowList` is documented as the sole gate for token-factory allow-listed denoms — “allowed to send the coins only if it is in the allow list”: [2](#0-1) 

However, CosmWasm contracts move coins through a different code path: `wasmd`'s `BankCoinTransferrer.TransferCoins`, which backs `BankMsg::Send` execution from any contract. That function only checks `IsSendEnabledCoins` and `BlockedAddr` — it never calls `IsInDenomAllowList`: [3](#0-2) 

Because any CosmWasm user can instantiate/execute a contract that issues `BankMsg::Send` for an arbitrary denom held by (or routed through) the contract, a user excluded from a tokenfactory denom's `AllowList` can still receive or forward that denom by having a contract perform the transfer on their behalf — the allow-list "circuit breaker" that the token admin relies on is silently bypassed on this path, just as `ownerSetCategoryEnabled` was bypassed by the `_claim` path in the original report.

### Impact Explanation
Tokenfactory admins use `AllowList` as an access-control/compliance mechanism (e.g., permissioned or KYC-gated denoms, sanctions-list enforcement). Bypassing it via the wasm bridge allows unauthorized transfer of a restricted asset to or from disallowed addresses, defeating the admin's intended access control and enabling fund movement that should have been blocked — this is a concrete unauthorized-transfer/fund-control-bypass impact reachable from an ordinary CosmWasm transaction, not merely an informational gap.

### Likelihood Explanation
Likelihood is high: any CosmWasm user can deploy or use an already-deployed generic "forwarder"/"wrapper" contract that holds coins and issues `BankMsg::Send`. No privileged role or contract-specific logic is required beyond funding the contract with the restricted denom and calling it to relay the transfer — the allow-list is a per-denom setting that many tokenfactory admins may rely on for compliance, making the bypass immediately usable once such a contract exists.

### Recommendation
Enforce `IsInDenomAllowList` (and ideally the same `BlockedAddr`/`IsSendEnabledCoins` set already applied) inside `BankCoinTransferrer.TransferCoins` in `sei-wasmd/x/wasm/keeper/keeper.go`, mirroring the checks performed in `sei-cosmos/x/bank/keeper/msg_server.go`'s `Send`/`MultiSend` handlers, so that contract-initiated bank transfers cannot circumvent tokenfactory denom allow-lists. Audit other bank-transfer entry points (precompiles, IBC transfer hooks, module-to-module sends triggered by user messages) for the same gap.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/<admin>/RESTRICTED` and calls `SetDenomAllowList` with an allow list containing only a small set of addresses (e.g., `{addrA}`), excluding `addrB`.
2. Deploy/instantiate a simple CosmWasm "relay" contract whose `Execute` handler returns a `BankMsg::Send{to_address: <recipient>, amount: [RESTRICTED denom]}` response, using coins that the contract holds (e.g., sent to it in the same execute call).
3. `addrB` (not on the allow list) sends `MsgExecuteContract` to the relay contract, including `RESTRICTED` denom as funds, instructing the contract to forward the coins back to `addrB` or to another disallowed address `addrC`.
4. `wasmd`'s message dispatcher processes the `BankMsg::Send` via `BankCoinTransferrer.TransferCoins`, which checks only `IsSendEnabledCoins` and `BlockedAddr(to_address)`, and never calls `IsInDenomAllowList` — the transfer succeeds even though `addrB`/`addrC` are not in the denom's `AllowList`, whereas the same transfer attempted via `MsgSend` directly would be rejected with `"... is not allowed to send/receive funds"`.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
