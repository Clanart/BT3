### Title
Bank precompile's `sendNative` transfers usei/wei while bypassing the `SendEnabled` (`IsSendEnabledCoins`) check enforced by `MsgSend` - ([File: precompiles/bank/legacy/v67/bank.go])

### Summary
The Zetachain finding describes an outbound-transfer control-flow bug where an `else if` branch checking an "enabled" flag can be skipped while a later, unconditional branch still executes the fund-moving logic — effectively making the disable switch ineffective. Sei-chain's bank precompile has an analogous inconsistency: the `x/bank` module's `SendEnabled`/`DefaultSendEnabled` param is meant to be a chain-wide switch that disables transfers of a given denom (`IsSendEnabledCoins`, enforced in `MsgSend`/`MultiSend` via `bankMsgServer.Send`), but the EVM bank precompile's native-token transfer path (`sendNative`) reaches the low-level `SendCoinsAndWei`/wei balance mutation functions directly, never calling `IsSendEnabledCoins`.

### Finding Description
`x/bank`'s `SendEnabled` parameter is the chain's mechanism to disable transfers of a coin denom entirely. It is enforced centrally in `BaseSendKeeper.IsSendEnabledCoins` / `IsSendEnabledCoin` [1](#0-0) , and the standard `MsgSend` message-server handler calls this check before moving funds [2](#0-1) .

The EVM bank precompile's ERC20-pointer-based `send` function correctly reuses this validated path by dispatching through `bankMsgServer.Send`, which includes the `IsSendEnabledCoins` check [3](#0-2) .

However, the precompile's native-token transfer entrypoint, `sendNative` (reachable by any EVM contract/EOA that sends value to the bank precompile address), does not go through `bankMsgServer.Send` or call `IsSendEnabledCoins` at all. It resolves usei/wei amounts via `HandlePaymentUseiWei` and then calls `p.bankKeeper.SendCoinsAndWei` directly [4](#0-3) . `SendCoinsAndWei` only mutates wei/usei balances and emits events; it never checks `SendEnabled` [5](#0-4) .

This mirrors the ZetaChain bug pattern: one control path (the "if" branch, here `MsgSend`/pointer `send`) properly gates the operation on an enabled/disabled flag, while a parallel/sibling path (the "else if" that is effectively always reachable, here `sendNative`) performs the same fund movement without that gate.

### Impact Explanation
If governance or an admin disables sending of the base denom (`usei`) — e.g. `SendEnabled = [{denom: "usei", enabled: false}]` or `DefaultSendEnabled = false`, a control intended to halt transfers network-wide (for incident response, migrations, or compliance) — users can still move native usei/wei value by calling the EVM bank precompile's `sendNative` (i.e., sending a value-bearing call to the precompile address) from any EVM account. This defeats the purpose of the `SendEnabled` safety switch and could be used to move funds during a period when transfers are supposed to be frozen (e.g., during an exploit response), enabling continued fund movement/theft mitigation bypass. This is a control-bypass rather than a direct token-minting bug, but it undermines a documented, load-bearing safety mechanism (`x/bank` `SendEnabled` is explicitly described in the spec as allowing the chain to "start a network without enabling transfers while ensuring critical network functionality is operating as expected" [6](#0-5) ), reachable by any unprivileged EVM caller.

### Likelihood Explanation
High reachability: any account can call the bank precompile with a nonzero `value` to invoke `sendNative` [7](#0-6) ; no special privilege is required. The only precondition is that an operator/governance has disabled sending for `usei` (or another wei-backed denom) via `SendEnabled`/`DefaultSendEnabled` — a state that occurs specifically in emergency/maintenance scenarios where the bypass is most damaging.

### Recommendation
Add an `IsSendEnabledCoins` (or equivalent `IsSendEnabledCoin(usei)`) check inside `sendNative` before invoking `SendCoinsAndWei`, consistent with the pointer-based `send` path and `MsgSend`. More robustly, push the `SendEnabled` check down into `BaseSendKeeper.SendCoinsAndWei` (and any other low-level coin-moving helper reachable from EVM precompiles/CW bridges) so that all fund-transfer entry points are uniformly gated, rather than relying on each caller to remember to check it beforehand.

### Proof of Concept
1. Governance/admin sets `x/bank` params with `SendEnabled = [{denom: "usei", enabled: false}]` (or `DefaultSendEnabled = false`), intending to freeze all usei transfers.
2. A user deploys/uses a contract that calls the bank precompile's `sendNative(receiver)` method with a non-zero `msg.value` (usei/wei), per `precompiles/bank/legacy/v67/bank.go` lines 253-311.
3. `HandlePaymentUseiWei` resolves the payment amount, then `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` executes unconditionally, moving funds despite `SendEnabled=false` for usei — because `SendCoinsAndWei`/`SubWei`/`AddWei` never call `IsSendEnabledCoins`.
4. Compare with the equivalent native `MsgSend` for usei, which is correctly rejected with `ErrSendDisabled` via `IsSendEnabledCoins` in `msgServer.Send`.

Note: I could not fully trace every historical precompile version (`v601`–`v670`) or confirm whether the currently-active (non-legacy) `precompiles/bank/bank.go` `sendNative` implementation is identical to the `v67` legacy snippet cited above; the index only exposed the legacy copies with matching logic, so it is possible (but unconfirmed) that a fix or additional check exists in the latest non-legacy `bank.go` that wasn't fully returned by search. A Devin session with full file access should verify the current `precompiles/bank/bank.go` `sendNative` function directly to confirm whether this gap still exists in production.

// IsSendEnabledCoins checks the coins provide and returns an ErrSendDisabled if
// any of the coins are not configured for sending.  Returns nil if sending is enabled
// for all provided coin
func (k BaseSendKeeper) IsSendEnabledCoins(ctx sdk.Context, coins ...sdk.Coin) error {
	for _, coin := range coins {
		if !k.IsSendEnabledCoin(ctx, coin) {
			return sdkerrors.Wrapf(types.ErrSendDisabled, "%s transfers are currently disabled", coin.Denom)
		}
	}
	return nil
}

// IsSendEnabledCoin returns the current SendEnabled status of the provided coin's denom
func (k BaseSendKeeper) IsSendEnabledCoin(ctx sdk.Context, coin sdk.Coin) bool {
	return k.GetParams(ctx).SendEnabledDenom(coin.Denom)
}

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
	if readOnly {
		return nil, 0, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		bz, err := method.Outputs.Pack(true)
		return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, 0, err
	}

	msg := &banktypes.MsgSend{
		FromAddress: senderSeiAddr.String(),
		ToAddress:   receiverSeiAddr.String(),
		Amount:      sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount))),
	}

	err = msg.ValidateBasic()
	if err != nil {
		return nil, 0, err
	}

	if _, err = p.bankMsgServer.Send(sdk.WrapSDKContext(ctx), msg); err != nil {
		return nil, 0, err
	}

func (p PrecompileExecutor) sendNative(ctx sdk.Context, method *abi.Method, args []interface{}, caller common.Address, callingContract common.Address, value *big.Int, readOnly bool, hooks *tracing.Hooks, evm *vm.EVM) ([]byte, uint64, error) {

		return nil, 0, errors.New("cannot call sendNative from staticcall")
	}

		return nil, 0, errors.New("cannot delegatecall sendNative")
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	if value == nil || value.Sign() == 0 {
		return nil, 0, errors.New("set `value` field to non-zero to send")
	}

	senderSeiAddr, ok := p.evmKeeper.GetSeiAddress(ctx, caller)
	if !ok {
		return nil, 0, errors.New("invalid addr")
	}

	if !ok || receiverAddr == "" {
		return nil, 0, errors.New("invalid addr")

		return nil, 0, err

		return nil, 0, err
	}

	if err := p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei); err != nil {
		return nil, 0, err
	}
