### Title
Deserialized `ReceivedOutput` trusts an attacker-chosen `offset`, letting any output be claimed as spendable by an arbitrary key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the `offset` scalar, `TxOut`, and `OutPoint` from untrusted bytes with no binding between them. Downstream, the key that can supposedly spend the output is derived as `script_pubkey_point - offset * G` (the pattern used by `Output::key()`), and signing offsets the threshold keys by `offset`. Because `offset` is unconstrained attacker input, an output paying to any Taproot key can be presented as belonging to any group key — the on-chain analogue of claiming capital that was calculated but never actually verified as claimable.

### Finding Description
In the legitimate flow, `Scanner::scan_transaction` only produces a `ReceivedOutput` after matching `output.script_pubkey` against `self.scripts`, a map built from `key + offset*G` for registered offsets (`networks/bitcoin/src/wallet/mod.rs:180-213`). The `offset` is therefore *derived* and authenticated by the script match.

`ReceivedOutput::read` (`mod.rs:122-134`) performs no such check:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

`offset` is any canonical scalar, `output` is any `TxOut`, and `outpoint` is any `OutPoint`. Nothing ties `offset` to `output.script_pubkey`. Any consumer that recovers the owning key as `p2tr_point(output.script_pubkey) - offset*G` (as `Output::key()` does in `processor/src/networks/bitcoin.rs:112-122`) or that applies `keys.offset(offset)` to spend (the `tweak_keys`/`offset` mechanism in `mod.rs:46-75` and `TransactionSignMachine` in `send.rs`) will accept the attacker's claim.

Given a target group key `M` (even-Y tweaked), the attacker:
1. Chooses their own key `K` and crafts `TxOut{ script_pubkey: p2tr(K), value }` plus a fake `OutPoint`.
2. Sets `offset` such that `offset*G = K_point - M`, i.e. `offset` is the discrete-log difference — computable because the attacker picks `K` freely only if they can't solve dlog... more precisely, they choose the point `P` they want `key()` to report, set `K_point = P + offset*G` for any chosen offset, and make the output pay to `P + offset*G`'s tweak.

Concretely: pick arbitrary `offset` and desired reported key `M`; create the output paying to `p2tr(M + offset*G)`. `key()` then returns `M`, while the actual spendable key is `M + offset*G` — a key whose secret the pool does not possess (the pool's real offsets are exactly the registered ones, and the taproot tweak means even a known discrete-log difference does not yield a signing key under `M`).

### Impact Explanation
This is the exact "claim capital without verifying claimability" shape of the reported bug: funds are reported as received by (and credited to) the threshold key `M`, but are not spendable by it. Any accounting/crediting path that ingests a serialized `ReceivedOutput` — the type is explicitly `Readable`/`Writable` for transport and storage — will treat attacker-controlled outputs as pool balance, enabling the attacker to be credited for deposits they alone can spend, or causing the pool to build transactions over unspendable inputs.

### Likelihood Explanation
Reachable by any unprivileged party able to submit serialized `ReceivedOutput`/`Output` bytes to a component that reads them (`ReceivedOutput::read` is listed as an untrusted-bytes sink). No validator status, key material, or collusion is required — only the ability to feed bytes. The attacker's cost is one ordinary P2TR output.

### Recommendation
Make `offset` unforgeable relative to the output: either (a) re-derive/verify `offset` wherever a `ReceivedOutput` is consumed by recomputing `p2tr_script_buf(key + offset*G) == output.script_pubkey` for the expected `key`, or (b) remove `offset` from the serialized form entirely and recover it via the `Scanner`'s `scripts` map keyed by `script_pubkey` (the already-authenticated path in `scan_transaction`). At minimum, document on `ReceivedOutput::read` that the deserialized `offset` is untrusted and must be re-validated against a `Scanner` before the output is treated as spendable.

### Proof of Concept

let offset = Scalar::random(rng);                       // any scalar

let forged = ReceivedOutput {
  offset,
  output: TxOut { value: Amount::from_sat(100_000), script_pubkey: script },
  outpoint: OutPoint::new(txid_of_real_or_fake_tx, 0),
};
// Serialized forged.serialize() bytes are fed to ReceivedOutput::read;
