### Title
Stale voter stake in `BribeRewardPool` is not cleared on `removePool`, letting a past voter siphon bribe rewards from a re-added pool without re-voting - ([File: rewards/WombatBribeManager.sol])

### Summary
`WombatBribeManager.removePool(_index)` only pops the LP address out of the `pools` array; it never touches `poolInfos[_lp]`, `userVotedForPoolInVlmgp[user][_lp]`, or the corresponding `BribeRewardPool`'s internal `_balances`/`totalSupply`. If the owner later re-adds the same `_lp` (typically re-using the same `_rewarder`, which is the natural operational choice for a temporarily-delisted pool), any user who never called `unvote()` before/after removal still holds a live stake inside the rewarder contract and continues to accrue a share of every bribe deposited into that rewarder going forward, with zero new vote weight actually cast for the reactivated pool.

### Finding Description
`removePool` at [1](#0-0)  only does a swap-and-pop on the `pools` array:
```solidity
function removePool(uint256 _index) external onlyOwner {
    uint256 length = pools.length;
    if(_index >= length) revert OutOfPoolIndex();
    pools[_index] = pools[length - 1];
    pools.pop();
}
```
It does not zero `poolInfos[_lp]`, does not reset `userVotedForPoolInVlmgp[user][_lp]`, and — critically — never calls `withdrawFor` on `poolInfos[_lp].rewarder` to unstake voters, the way `unvote()` does at [2](#0-1) .

The actual reward accounting lives entirely inside the `BribeRewardPool` contract itself via its own `_balances`/`totalSupply` state, set by `stakeFor`/`withdrawFor` [3](#0-2) . This state is completely decoupled from `WombatBribeManager.poolInfos[_lp].totalVoteInVlmgp`. Because `removePool` never calls `withdrawFor`, a voter's stake inside the rewarder persists untouched through a remove/re-add cycle.

When the owner calls `addPool` again for the same `_lp` (reusing the existing `_rewarder`), only the `WombatBribeManager`-side bookkeeping is reset to a fresh `Pool` struct with `totalVoteInVlmgp: 0`; `userVotedForPoolInVlmgp` is untouched and the rewarder's `_balances`/`totalSupply` are untouched: [4](#0-3) 

`claimBribeFor` → `_claimBribeFor` performs no check against `userVotedForPoolInVlmgp` at all and simply forwards the call to the rewarder: [5](#0-4) 

Since the rewarder's `earned()`/`getReward()` logic is driven purely by `balanceOf(_account)` and `totalSupply` (inherited from `BaseRewardPoolV2`) [6](#0-5) , an attacker who voted before removal and never called `unvote()` retains a nonzero `_balances[attacker]` in the reused rewarder. Once the pool is reactivated and genuine new voters call `vote()` (which calls `stakeFor` and increases `totalSupply`) and new bribe rewards are queued into that same rewarder, the attacker's still-outstanding balance automatically shares in `rewardPerToken` distribution — despite never re-casting a vote in the new epoch and despite `WombatBribeManager`'s own `totalVoteInVlmgp` for that pool having been reset to 0.

No existing guard stops this: `onlyOwner` on `removePool`/`addPool` only restricts who can trigger the pool lifecycle transition, but the attacker's exploitation step (`claimBribeFor`) is a plain unprivileged external call, and it performs no cross-check against `WombatBribeManager`'s vote bookkeeping.

### Impact Explanation
This results in theft/dilution of unclaimed bribe yield: rewards deposited by/for the re-added pool's genuine new voters are partially diverted to a user who holds no legitimate vote weight in the current epoch. This matches the "theft of unclaimed yield" impact class. The magnitude is bounded by the attacker's stale stake size relative to total restaked amount and by how much new bribe reward flows into the reused rewarder before someone finally calls `unvote()`/re-votes to flush the stale balance.

### Likelihood Explanation
Requires: (1) attacker previously voted for a pool with real locked MGP (unprivileged, ordinary action) and simply never called `unvote()`; (2) owner independently performs a normal, plausible operational sequence — `removePool` followed by `addPool` for the same LP with the same rewarder address (e.g., re-listing after a temporary pool issue). The attacker does not need to time or trigger the admin action, only to be a dormant stale-voter when it happens, then call `claimBribeFor`/`claimAllBribes` afterward — making it low-effort and fully repeatable for every remove/re-add cycle where the rewarder is reused.

### Recommendation
In `removePool`, before removing the LP from `pools`, fully reset its `poolInfos[_lp]` (mark `isActive = false` or delete) and, most importantly, force-unstake all outstanding balances from the associated rewarder (or disallow reusing an old rewarder address in `addPool` when previous stale balances remain, e.g. by requiring `totalSupply() == 0` on the rewarder before allowing a pool with that LP to be re-added, or by deploying a fresh rewarder on every `addPool`). Additionally, `_claimBribeFor`/`claimBribeFor` should validate that the caller currently has `userVotedForPoolInVlmgp[_for][lp] > 0` (mirroring the check already present in `claimAllBribes`) as defense in depth.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatBribeManager`, a `BribeRewardPool` for LP `X`, add pool via `addPool(X, rewarderX, "poolX")`.
2. Attacker locks MGP, calls `vote([X], [100])` → `userVotedForPoolInVlmgp[attacker][X] == 100`, `rewarderX.balanceOf(attacker) == 100`, `rewarderX.totalSupply() == 100`.
3. Owner calls `removePool(indexOfX)`. Assert `pools` no longer contains `X`, but `rewarderX.balanceOf(attacker)` is still `100` and `poolInfos[X].isActive` is still `true` (unchanged).
4. Owner calls `addPool(X, rewarderX, "poolX-v2")` (same rewarder reused). Assert `poolInfos[X].totalVoteInVlmgp == 0` while `userVotedForPoolInVlmgp[attacker][X]` is still `100` and `rewarderX.totalSupply() == 100`.
5. A genuine new voter `bob` calls `vote([X],[100])` → `rewarderX.totalSupply() == 200`.
6. Fund `rewarderX` with new bribe rewards (simulate `queueNewRewards`).
7. Attacker (who never re-voted) calls `claimBribeFor([X], attacker)`.
8. Assert attacker receives a nonzero reward payout equal to ~50% of the newly queued rewards despite having zero vote weight cast in the new epoch, confirming yield diverted from `bob`'s legitimate share.
