## Title
Path-containment check in `resolveWithin` uses unanchored `startsWith`, allowing symlink-based reads outside the repository - (File: `app/src/lib/path.ts`)

## Summary
The bug-class in the report is "a resolver returns a value that looks valid but was never checked against the live/actual target, so a downstream trust decision (delegatecall / file read) is made on unverified data." The GitHub Desktop analog is `_resolveWithin` in `app/src/lib/path.ts`, the function Desktop relies on everywhere it needs to guarantee "this path stays inside the repository." Its final containment check compares real paths with plain string `startsWith`, without verifying a path-separator boundary, so a sibling directory whose name is prefixed by the repository's directory name is treated as "inside" the repository.

## Finding Description
`_resolveWithin` computes the real, symlink-resolved paths of the root and the candidate target and then approves the target if: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` is not path-boundary aware: `"/Users/victim/Documents/GitHub/repo-private".startsWith("/Users/victim/Documents/GitHub/repo")` is `true` even though `repo-private` is a completely different, sibling directory. Because `realpath` is applied to the *resolved* path (which follows symlinks), a symlink inside the repository that targets a sibling directory whose name happens to be prefixed by the repo's own name will pass the containment check even though it clearly escapes the intended root.

This is the exact same class of defect as the audited `SocketGateway.addressAt` issue: the guard exists (a "committed to be safe" resolution path), but the equality/boundary check it relies on is insufficiently strict, so a value that should be rejected (an out-of-root path) is accepted as valid and used later for a trust-sensitive operation (here, `readFile`/`stat` instead of `delegatecall`).

`resolveWithin` is the sole containment primitive used by:
- `buildConflictContext` in `app/src/lib/copilot-conflict-context.ts`, which reads conflicted-file content straight off disk to send to the Copilot SDK for AI-assisted conflict resolution: [2](#0-1) 
- the `open-repository-from-url` deep-link handler, which uses the resolved path to reveal a file in the file manager: [3](#0-2) 

Neither caller re-validates the result beyond trusting `resolveWithin`'s null/non-null return, so the boundary weakness propagates directly into a file read (Copilot context) or file-manager reveal (deep link) outside the intended repository.

## Impact Explanation
Desktop's default clone location places all repositories as siblings under one parent folder (e.g. `~/Documents/GitHub/<repo>`), so name-prefix collisions between an attacker-controlled and a victim-owned repository are a realistic, unprompted scenario (e.g. `evil-corp` vs `evil-corp-internal`, or an attacker naming their fork/clone `repo` while the victim has `repo-secrets` cloned next to it). An attacker who controls the contents of a cloned/fetched repository (e.g. via a crafted PR the user checks out, or a repo the user clones) can commit a symlink at a conflicted-file path that targets a sibling directory. When the user later hits a merge conflict and uses the Copilot conflict-resolution feature, `buildConflictContext` will `readFile` through that symlink, believing the boundary check protected it, and the sibling directory's file content (potentially private/secret files from another repository) is read into memory and sent off to the AI backend as prompt context — a file read (and exfiltration) outside the intended repository root, matching the report's "silent corruption/violation of trust boundary via unenforced resolution."

## Likelihood Explanation
Exploitation requires only that the victim clone/checkout attacker-controlled content containing a symlink and that a sibling directory exists whose name is prefixed by the repo's directory name — both are common given Desktop's default flat clone layout and organizations' common repo-naming conventions (`x`, `x-private`, `x-internal`, `x-legacy`, etc.). No local access, admin rights, or social engineering beyond normal clone/checkout/merge-conflict usage is required, which is squarely in-scope per the stated valid-impact criteria (attacker controls a cloned/fetched repository, result is file read outside the repo).

## Recommendation
Change the containment check in `_resolveWithin` to require an exact match or a match followed immediately by the path separator, e.g.:
```
const withSep = realRoot.endsWith(sep) ? realRoot : realRoot + sep
return realResolved === realRoot || realResolved.startsWith(withSep) ? resolved : null
```
This mirrors the OZ `Address.isContract`-style recommendation in the original report: don't trust a resolution result until it has been checked with a boundary-correct equality test, not a naive prefix match.

## Proof of Concept
1. Victim has previously cloned a private repository to `~/Documents/GitHub/repo-secrets` (Desktop's default clone location convention).
2. Attacker publishes/forks a repository named `repo` and gets the victim to clone it to `~/Documents/GitHub/repo` (or opens a PR the victim checks out into that path).
3. Inside `repo`, the attacker includes a file that will show as conflicted on merge, where the working-tree entry is a symlink `secret-leak -> ../repo-secrets/credentials.txt`.
4. Victim triggers a merge that conflicts and uses "Resolve with Copilot." `buildConflictContext` calls `resolveWithin(workingDirectory, 'secret-leak')`:
   - `resolved` = `~/Documents/GitHub/repo/secret-leak`
   - `realResolved` = `~/Documents/GitHub/repo-secrets/credentials.txt` (symlink followed)
   - `realRoot` = `~/Documents/GitHub/repo`
   - `realResolved.startsWith(realRoot)` → `true` (incorrect), so the path is accepted.
5. `readFile(absolutePath, 'utf8')` in `buildConflictContext` reads `credentials.txt` from the sibling repository and includes its content in the prompt sent to Copilot, exfiltrating data outside the intended repository boundary.
