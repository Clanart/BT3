### Title
Unvalidated repository-derived file paths passed to `shell.openExternal` allow path traversal outside the repository - (File: `app/src/ui/lib/open-file.ts`)

### Summary
The bug class in the external report is a *missing guard on a sensitive operation that a sibling function already protects*: `payableCall` allowed arbitrary calls while `call` enforced `requiresApprovedCaller`. The Desktop analog is `openFile()`, which opens a filesystem path built by joining the repository root with a repository-derived (attacker-influenceable) relative path, with no containment check — while a nearly identical operation (opening a path from a deep link) explicitly validates that the resolved path stays inside the repository.

### Finding Description
`openFile()` builds the path to launch and calls `shell.openExternal` directly: [1](#0-0) 

Its callers construct `fullPath` by joining the repository root with a `path` value that comes from repository/commit/diff data — i.e., data that originates from a cloned/fetched repository or a pull request's file list, both of which are attacker-influenceable in the threat model described (`file.path` from `CommittedFileChange`/diff entries): [2](#0-1) [3](#0-2) [4](#0-3) 

None of these call sites validate that the joined path (`Path.join(repository.path, path)`) actually resolves *inside* `repository.path`. Compare this to the deep-link `filepath` action, where the exact same class of operation (turning a repository-relative path into a filesystem action) is explicitly guarded: [5](#0-4) 

That code rejects absolute paths and uses `resolveWithin(repository.path, filepath)`, only proceeding if the resolved path is confirmed to remain under the repository root. `openFile()`'s callers have no equivalent check — the "approved caller"-equivalent guard (path containment enforcement) exists on one path and is missing on the other, exactly mirroring the `call()` vs `payableCall()` asymmetry in the original report.

### Impact Explanation
If a repository-derived `path` string (from a commit's file list, PR diff, or stash entry) can contain traversal sequences (e.g. `..\..\..\Windows\System32\...` or similar), `Path.join(repository.path, path)` can resolve to a location outside the cloned repository. That resolved path is then passed to `shell.openExternal('file://' + fullPath)`, which launches the OS's default handler for that file. This is a "file read/open outside the repo, triggered by attacker-controlled repository content" primitive — the same class of impact the task's Valid Impact section calls out explicitly (attacker controls a cloned/fetched repository or a GitHub API object such as a PR file list, and the result is a file operation outside the repository).

### Likelihood Explanation
Uncertain/lower confidence: exploitability depends on whether a crafted commit/diff can actually produce a `file.path` value containing `..` segments that survive Git's own tree-path validation and Desktop's diff/status parsing. Git itself normally rejects `..` components in tracked tree entries (`verify_path`), so a directly malicious tracked filename is unlikely to reach this code un-mangled. The more plausible vector is a bug in Desktop's own diff/rename parsing (e.g., quoted/escaped filenames in unified diff headers) producing a path string that isn't re-validated before being joined — I was not able to fully verify this parsing path within the available tool budget, so this should be confirmed by reviewing the diff-parsing code that produces `CommittedFileChange.path`/rename entries before this is treated as a confirmed, exploitable bug rather than a design gap.

### Recommendation
Add the same containment check used in `dispatcher.ts`'s `openRepositoryFromUrl` to `openFile()`'s call sites (or inside `openFile()` itself): reject absolute paths and use `resolveWithin(repository.path, path)` before constructing `fullPath`, refusing to open anything that resolves outside the repository root.

### Proof of Concept
Not fully constructible from static analysis alone — a working PoC requires demonstrating that Desktop's diff/status parsing can be made to emit a `file.path` (or rename "to"/"from" path) containing traversal sequences despite Git's own tree-path validation. This gap should be verified with a live Desktop instance/dev session (e.g., crafting a diff with an escaped/quoted rename target such as `"..\\..\\..\\evil.exe"` in the unified-diff header and confirming whether `selected-commits.tsx`/`pull-request-files-changed.tsx` surfaces it unmodified as `file.path`) before treating this as a confirmed vulnerability rather than a design asymmetry.

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
