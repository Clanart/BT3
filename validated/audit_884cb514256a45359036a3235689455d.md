### Title
Empty aggregate signature deserializes and verifies successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::read` accepts an aggregate with zero nonces, while `SchnorrAggregate::verify` treats the resulting empty verification equation as valid when supplied an empty signer/challenge set. Although `SchnorrAggregator::complete` refuses to produce an empty aggregate, that invariant is not enforced during deserialization or verification. A public caller can therefore submit the serialization of an “empty” aggregate signature and have it accepted as a valid aggregate over no signatures. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

The deserializer reads a four-byte nonce count, then returns `SchnorrAggregate { Rs, s }` without requiring the count to be nonzero. [1](#0-0) 

Verification only checks that `self.Rs.len() == keys_and_challenges.len()`. For an empty aggregate and an empty `keys_and_challenges` slice, no nonce or public-key statements are added; only `(-self.s) * generator` is checked. If `s == 0`, that statement is the identity and verification succeeds. [2](#0-1) 

This bypasses the invariant maintained by the legitimate aggregation path: `SchnorrAggregator::complete` explicitly returns `None` when no signatures were aggregated. [3](#0-2) 

The concrete malicious encoding is:

```text
00 00 00 00                                      // Rs length = 0
00 00 ... 00                                     // canonical scalar zero
```

The byte length of the scalar suffix is the curve’s canonical field encoding length.

### Impact Explanation

An unprivileged party can forge an aggregate signature for the empty signer set using only public input bytes. Any verifier path that interprets an empty signer/challenge list as the claimed authorization set will accept the object despite no signature having been produced or verified. [2](#0-1) 

This is an incorrect verifier result and a forged aggregate signature rather than a malformed-input rejection. [4](#0-3) 

### Likelihood Explanation

The malicious input is deterministic, does not require knowledge of a private key, and is reachable through `SchnorrAggregate::read` followed by `verify`. [1](#0-0) [2](#0-1) 

Exploitation requires the caller to verify against an empty signer/challenge list. Protocols that independently reject empty signer sets before calling `verify` reduce exposure, but the primitive itself accepts a serialization that its constructor correctly refuses to generate. [5](#0-4) 

### Recommendation

Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. Verification should additionally reject `keys_and_challenges.is_empty()` before evaluating the multiexp, ensuring deserialization cannot bypass the construction-time invariant in `SchnorrAggregator::complete`. [1](#0-0) [2](#0-1) [5](#0-4) 

### Proof of Concept

```rust
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;
use std::io::Cursor;

fn empty_aggregate_forges<C: Ciphersuite>() {
  // Four-byte little-endian nonce count of zero, followed by scalar zero.
  let mut bytes = Vec::new();
  bytes.extend_from_slice(&0u32.to_le_bytes());
  bytes.extend_from_slice(C::F::ZERO.to_repr().as_ref());

  let aggregate = SchnorrAggregate::<C>::read(&mut Cursor::new(bytes)).unwrap();

  // For an empty signer/challenge set, the multiexp is only (-0) * G = identity.
  assert!(aggregate.verify(b"example domain separation", &[]));
}
```

`SchnorrAggregator::new` and `aggregate` cannot produce this object because `complete` returns `None` for zero signatures; only the permissive deserializer creates the invalid state. [6](#0-5)
