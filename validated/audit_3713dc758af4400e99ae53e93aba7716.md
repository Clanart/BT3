## Title
Path-containment check in `resolveWithin` uses an unanchored string-prefix comparison, allowing sibling-directory escape when resolving attacker-controlled conflict/deep-link paths - (File: `app/src/lib/path.ts`)

### Summary
The report's broken invariant is: *a value/state that is validated once is later trusted for a security-relevant action, even though the validation logic doesn't actually enforce the invariant it claims to enforce* (in the Fairside case, `fShareRatio` is "checked" but the check can be satisfied without the real collateralization being true; in Desktop, a path is "checked to be inside the repo" but the check can pass without the path actually being inside the repo).

The shared helper `_resolveWithin` in `app/src/lib/path.ts` is meant to guarantee that a resolved, symlink-followed path is contained within a given repository root before that path is read, written, or revealed in the Finder/Explorer. The containment test is:

```ts
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` is a raw character-prefix test with no path-separator boundary check. If the repository root is, e.g., `/Users/bob/code/repo` and an attacker-controlled path resolves (after symlink resolution) to `/Users/bob/code/repo-secrets/id_rsa`, the check returns **true** even though `repo-secrets` is a completely different, sibling directory. The function returns `resolved` (the pre-symlink path used by all subsequent I/O), not the validated `realResolved` value, compounding the disconnect between what was checked and what is used.

### Finding Description
`resolveWithin` (and its POSIX/Win32 variants) is the single security boundary guarding three sensitive call sites that all take attacker-influenced input:

1. `buildConflictContext` reads the content of conflicted files from disk and sends it to the Copilot SDK/API. It calls `resolveWithin(workingDirectory, file.path)` before `readFile`, trusting the result to stay inside the repo. [2](#0-1) 

2. `AppStore`'s Copilot-conflict acceptance flow calls `resolveWithin(repository.path, resolution.path)` and then `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, silently overwriting whatever file the check resolved to. [3](#0-2) 

3. `Dispatcher.openRepositoryFromUrl` — reachable from an `x-github-client://` deep link a user clicks — calls `resolveWithin(repository.path, filepath)` and then `shell.showItemInFolder(resolved)`. [4](#0-3) 

In all three cases, `file.path` / `resolution.path` / `filepath` are strings that originate from attacker-controlled sources: a maliciously crafted commit's conflict markers/paths (cloned/fetched repository), or a deep link. The `_resolveWithin` boundary check is the only thing standing between "confined to the repo" and "anywhere on disk the process can reach," and it can be satisfied by resolving into any sibling directory whose name happens to start with the repository directory's full name (e.g. `repo` vs `repo-1`, `repo-old`, `repo-backup`, `repo.bak`) — a naming pattern that is common in practice (Desktop itself, and users generally, create numbered/suffixed sibling clone directories when a name collision occurs).

This mirrors the Fairside bug class exactly: the code performs a check that looks like it enforces the true invariant ("resolved realpath is inside root") but the implementation (`startsWith` without a separator) allows the checked value to diverge from the intended invariant, and the divergence is then used to make a security decision (safe-to-read/write/reveal).

### Impact Explanation
- Read path (`copilot-conflict-context.ts`): file contents from a sibling directory (e.g., a neighboring cloned repo containing `.env`, SSH keys, or other credentials) can be exfiltrated to the external Copilot API as part of the "conflict content" payload — credential/token exfiltration outside the repo.
- Write path (`app-store.ts`): a maliciously crafted conflict-resolution path can cause GitHub Desktop to silently write attacker-supplied content to a file outside the intended repository, corrupting user data outside the repo boundary without git ever tracking the change.
- Reveal path (`dispatcher.ts`): a deep link can be crafted so that `shell.showItemInFolder` reveals/interacts with a file outside the repo, which is a file-disclosure/repo-boundary-escape primitive triggered purely by the user clicking a link.

### Likelihood Explanation
Exploitation requires no timing race, no local/physical access, and no elevated privileges — only that the victim (a) opens a repository containing crafted conflict data (from a clone/fetch/merge of an attacker-influenced branch) or (b) clicks a crafted `x-github-client://openRepo` deep link, and (c) has, or can be induced to have, a sibling directory whose path is a superstring of the repo path. This last precondition is the main limiting factor — it is plausible (multiple clones, forks, or backup folders with suffixed names are common) but not guaranteed, which keeps this from being trivially reliable in every environment. Existing guards (`resolveWithin`'s `realpath`-based symlink resolution, null-byte rejection) do not stop this path because the flaw is in the final containment comparison itself, not in the symlink-following step.

### Recommendation
Fix the containment check to use path-boundary-aware comparison instead of a raw string prefix, e.g.:
```ts
const relative = Path.relative(realRoot, realResolved)
const isContained =
  relative === '' ||
  (!relative.startsWith('..') && !Path.isAbsolute(relative))
return isContained ? resolved : null
```
and consider returning/using `realResolved` (the actually-validated value) rather than the pre-symlink-resolution `resolved` path for the downstream I/O, so the value that is checked is the value that is used.

### Proof of Concept
1. Victim has two directories side by side: `/Users/victim/code/repo` (a GitHub Desktop repository) and `/Users/victim/code/repo-secrets/token.txt` (an unrelated sibling directory containing a secret).
2. Attacker pushes/crafts a branch whose merge produces a conflicted file, or crafts a deep link, whose path component, once joined and `realpath`-resolved against `/Users/victim/code/repo`, is `/Users/victim/code/repo-secrets/token.txt`. (Because `resolveWithin` normalizes `..`-based traversal via `path.resolve`, the same effect can be reached with a `../repo-secrets/token.txt`-style relative path from a file inside the repo.)
3. In `_resolveWithin` (`app/src/lib/path.ts:71`), `realResolved.startsWith(realRoot)` evaluates `'/Users/victim/code/repo-secrets/token.txt'.startsWith('/Users/victim/code/repo')`, which is `true`.
4. `buildConflictContext` (or the Copilot resolution writer, or the deep-link handler) proceeds to read/write/reveal `/Users/victim/code/repo-secrets/token.txt`, even though it is outside `/Users/victim/code/repo`. [5](#0-4)

    it('fails for paths outside of the root', async () => {
      assert((await resolveWithin(root, join('..'))) === null)
      assert((await resolveWithin(root, join('..', '..'))) === null)
    })

    it('succeeds for paths that traverse out, and then back into, the root', async () => {
      assert.equal(await resolveWithin(root, join('..', basename(root))), root)
    })

    it('fails for paths containing null bytes', async () => {
