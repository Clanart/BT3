### Title
Partial-fill rounding lets the completing solver capture rounding dust owed to earlier partial fillers - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` releases escrowed input tokens to a partial-fill solver using floor division: `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`. Every fill before the one that completes the order loses the fractional remainder to truncation, and that entire accumulated remainder is dumped — undivided — on whichever transaction happens to be the one that satisfies `amountFilled == totalRequired`, via the special-cased branch `escrowedAmount = _orders[commitment][token]`. This is the same class of bug as the Burve `Closure.addValue` report: proportional accounting drifts because of rounding, and the drift is captured disproportionately by one party instead of being distributed fairly.

### Finding Description [1](#0-0) 

For every fill that does not complete the order, the escrow released is:
```
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired
```
This floors toward zero whenever `order.inputs[i].amount * fillAmount` is not an exact multiple of `totalRequired`. The truncated remainder is never credited to that filler — it simply stays parked in `_orders[commitment][token]`.

Only the fill that pushes `amountFilled` to exactly `totalRequired` takes the other branch:
```
escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
```
i.e., it sweeps the *entire remaining escrow balance*, not just its own proportional share plus its own remainder. Every rounding remainder accumulated from all previous partial fills on that order is bundled into this single payout.

Because `fillOrder`/`_fillSameChain` is a fully public, permissionless entry point that any address can call with any `fillAmount` up to `remaining` [2](#0-1) , nothing binds "who completes the order" to "who contributed most of the output." Any solver can watch an order that is close to completion (`remaining` small relative to `totalRequired`) and submit the final, arbitrarily small completing fill themselves, collecting the whole accumulated escrow balance for a fill that may represent only a tiny fraction of the total output actually required — value that rounding math implicitly still "owed" to the earlier partial fillers.

`_partialFills[commitment][outputToken]` tracks output progress precisely (no rounding), but `_orders[commitment][token]` (input escrow) is drained non-proportionally, so the two ledgers diverge exactly the way `Closure.balances` and `Closure.targetX128` diverge from `Closure.targetX128`'s intended relationship in the referenced report — the invariant "escrow released is proportional to output delivered" is violated, and a party who did not deliver a proportional share can absorb the difference.

### Impact Explanation
This breaks the intended "wrong beneficiary or amount" guarantee for escrowed order settlement: a solver who did the bulk of the work delivering output tokens across several partial fills can be under-paid (receiving `floor()` of their proportional share every time), while a different, unrelated solver who merely submits the final dust-sized completing fill receives the entire unclaimed remainder of the user's escrowed input tokens. This is a direct fund-misallocation bug in a production bridge/intent-settlement contract reachable by any unprivileged caller through the ordinary `fillOrder` path — no malicious relayer, prover, or admin is required.

### Likelihood Explanation
Any order that is split into multiple partial fills where `order.inputs[i].amount` is not an exact multiple of the fill granularity relative to `totalRequired` will exhibit truncation on every non-final fill. Because the function is public and anyone may fill any un-filled portion of an order at any time, a rational MEV-aware actor watching mempool/state for `remaining` approaching zero can always race to submit the tiny completing fill and capture the accumulated dust. The larger the number of partial fills (attacker-controlled, since `fillAmount` is caller-chosen down to 1 wei) and the more skewed the input/output amount ratio, the larger the extractable remainder — this can be deliberately engineered rather than left to chance.

### Recommendation
Track cumulative escrow already released per commitment/token (mirroring `_partialFills`) and compute each fill's release as `proportional(amountFilled) - alreadyReleased`, so every fill (including the final one) only ever receives its own floor-consistent slice, with the *first* fill (not the last) absorbing at most a single rounding unit — or better, use a scheme like `mulDiv` with round-up on the final release balanced against a running total, ensuring the sum of all releases never exceeds and is fairly distributed against `_orders[commitment][token]`. This mirrors the Burve report's suggested mitigation of recomputing the target value from a canonical formula rather than letting rounding accumulate unchecked in one place.

### Proof of Concept
1. Create a same-chain order with `order.inputs[i].amount = 7`, `order.output.assets[i].amount = totalRequired = 10`, no output calldata.
2. Solver A calls `fillOrder` nine times, each with `options.outputs[i].amount = 1` (fillAmount = 1 each time).
   - Each call: `escrowedAmount = floor(7 * 1 / 10) = 0`. Solver A delivers 9 units of real output tokens to the beneficiary and receives 0 input tokens back nine times in a row.
   - After 9 calls: `_partialFills[commitment][outputToken] = 9`, `_orders[commitment][inputToken]` is still 7 (nothing withdrawn).
3. Solver B (any unrelated address, front-running or simply watching state) calls `fillOrder` with `options.outputs[i].amount = 1` for the last remaining unit.
   - `amountFilled = 10 == totalRequired` → `escrowedAmount = _orders[commitment][inputToken] = 7` (the full remaining escrow) [3](#0-2) .
   - Solver B delivers only 1/10 of the total output but receives all 7 escrowed input tokens — the entire value "owed" (via rounding) to Solver A's nine prior contributions.

This confirms the escrow ledger and the output-progress ledger diverge under partial fills, and that divergence can be captured by an arbitrary, unprivileged party at order-completion time.
