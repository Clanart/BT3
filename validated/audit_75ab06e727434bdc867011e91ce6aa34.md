## Title
Nil pointer dereference in legacy EVM precompile error handling causes RPC/validator node crash - (File: `precompiles/common/legacy/v605/precompiles.go`)

### Summary
Several legacy versions of the shared precompile dispatcher (`precompiles/common/legacy/{v562,v575,v580,v600,v605,v606,v610}/precompiles.go`) call `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)` inside `HandlePrecompileError` without checking whether `GetDBImpl` returned `nil`. `GetDBImpl` explicitly returns `nil` when `evm.StateDB` is not a `*state.DBImpl` and does not wrap one via `*state.HookedStateDB` [1](#0-0) . When `Prepare` cannot obtain a `DBImpl` from the `StateDB`, it returns an error and a zero `sdk.Context` [2](#0-1) , but the deferred `HandlePrecompileError` still runs and re-invokes `GetDBImpl(evm.StateDB)` on the same non-`DBImpl` state, gets `nil` again, and dereferences it — panicking the node process [3](#0-2) .

This is the same bug class as CVE-2025-58142: code assumes a backing resource (there, a mapped guest page; here, the `DBImpl` wrapper around `StateDB`) is always present and dereferences it without a presence check, causing a crash.

### Finding Description
`Precompile.Run` and `DynamicGasPrecompile.RunAndCalculateGas` both defer `HandlePrecompileError(err, evm, operation)` before calling `p.Prepare(evm, input)` [4](#0-3) . `Prepare` itself guards against a nil `DBImpl`:

```go
ctxer := state.GetDBImpl(evm.StateDB)
if ctxer == nil {
    return sdk.Context{}, nil, nil, errors.New("cannot get context from EVM")
}
``` [2](#0-1) 

However, the deferred error handler does not repeat this check:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
    if err != nil {
        state.GetDBImpl(evm.StateDB).SetPrecompileError(err)
        metrics.IncrementErrorMetrics(operation, err)
    }
}
``` [5](#0-4) 

Since `evm.StateDB` has not changed between the two calls, whenever `Prepare` fails specifically because `GetDBImpl` returned `nil`, the deferred handler calls `GetDBImpl` again, gets `nil` again, and calls `.SetPrecompileError(err)` on a nil `*DBImpl`, causing a Go nil-pointer-dereference panic.

This defect was fixed starting at legacy version v614, which added a nil check:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
    if err != nil {
        if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
            sdb.SetPrecompileError(err)
        }
        ...
``` [6](#0-5) 

The unguarded versions (`v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`) remain in the codebase as legacy precompile implementations dispatched by block height, so they are used for historical calls (e.g. `eth_call`, `debug_traceCall`, `debug_traceTransaction`, `eth_estimateGas`) targeting blocks in the height range where those versions were the live precompile logic.

### Impact Explanation
A nil pointer dereference in a precompile's error path panics the executing goroutine. Any unprivileged RPC caller who can trigger the precompile execution path (e.g., through `eth_call`/`debug_trace*`/`eth_estimateGas` against a precompile at a historical block height, or scenarios where `evm.StateDB` is a non-`DBImpl` wrapper) can crash the RPC/full node process, matching the "crash of default-configuration RPC nodes" acceptance criterion.

### Likelihood Explanation
The trigger requires `evm.StateDB` at Prepare-time to not resolve to a `*state.DBImpl` (directly or via `*state.HookedStateDB`), which is the exact condition `GetDBImpl` is designed to reject with a normal error rather than crash. Any call flow that ends up invoking one of the affected legacy versions with such a `StateDB` (e.g., tracing/simulation code paths using an alternate `vm.StateDB` implementation) will hit the panic deterministically, since the same nil result is produced twice on the same input.

### Recommendation
Backport the nil-check fix already present in v614+ to all legacy `HandlePrecompileError` implementations (`v562`, `v575`, `v580`, `v600`, `v605`, `v606`, `v610`):
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
    if err != nil {
        if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
            sdb.SetPrecompileError(err)
        }
        metrics.IncrementErrorMetrics(operation, err)
    }
}
```
Alternatively, recover from panics in the precompile dispatch boundary (e.g., in `Run`/`RunAndCalculateGas`) so that a bad `StateDB` type can never crash the host process.

### Proof of Concept
1. Trigger execution of any precompile whose dispatcher is the legacy `precompiles/common/legacy/v605` (or v562/v575/v580/v600/v606/v610) implementation — i.e., issue an RPC call (`eth_call`, `debug_traceCall`, `eth_estimateGas`) against a precompile address at a historical block height mapped to that precompile version.
2. Ensure the call path supplies an `evm.StateDB` that is not a `*state.DBImpl` and does not wrap one via `*state.HookedStateDB` (any code path that constructs the EVM with an alternate/raw `vm.StateDB` implementation for that historical trace/call).
3. `Prepare` returns `err = "cannot get context from EVM"` with `ctxer == nil`.
4. The deferred `HandlePrecompileError(err, evm, operation)` re-calls `state.GetDBImpl(evm.StateDB)`, again receiving `nil`, and calls `.SetPrecompileError(err)` on it — panicking the goroutine and crashing the RPC/full node process.

	operation := fmt.Sprintf("%s_unknown", p.name)
	defer func() {
		HandlePrecompileError(err, evm, operation)
		if err != nil {
			bz = []byte(err.Error())
			err = vm.ErrExecutionReverted
		}
	}()
	ctx, method, args, err := p.Prepare(evm, input)
	if err != nil {
		return nil, err
	}

	operation = method.Name
	em := ctx.EventManager()
	ctx = ctx.WithEventManager(sdk.NewEventManager())
	ctx = ctx.WithEVMPrecompileCalledFromDelegateCall(isFromDelegateCall)
	bz, err = p.executor.Execute(ctx, method, caller, callingContract, args, value, readOnly, evm, hooks)
	if err != nil {
		return bz, err
	}
	events := ctx.EventManager().Events()
	if len(events) > 0 {
		em.EmitEvents(ctx.EventManager().Events())
	}
	return bz, err
}
