### Title
Third-party malleability of the Payout tx via `SinglePlusAnyoneCanPay` lets an attacker rewrite the OP_RETURN operator key before confirmation, permanently blocking the funding operator's reimbursement - ([File: core/src/verifier.rs::update_finalized_payouts])

### Summary
The Payout transaction's only signed input uses `TapSighashType::SinglePlusAnyoneCanPay`, which BIP341 defines to commit *only* to input 0 and the output at the same index (output 0, the user's payout). The anchor output (1) and the OP_RETURN output (2) carrying the operator's `xonly_pk` are not covered by the signature, so anyone who observes the broadcast/mempool transaction can copy the witness for input 0 into a new transaction that keeps output 0 identical but swaps output 2 for a different (or garbage) operator key, producing a distinct, still-validly-signed txid competing to spend the same withdrawal outpoint.

### Finding Description
Binding under test: `withdrawals.payout_payer_operator_xonly_pk` for withdrawal index `i` must equal the operator whose own funds paid output 0 of the confirmed payout tx (Operator A).

- The withdrawal signature is required to be `SinglePlusAnyoneCanPay` and is enforced as such both at the operator (`Operator::withdraw`, core/src/operator.rs:560-637) and at the aggregator's `withdraw` RPC (`core/src/rpc/parser/operator.rs::parse_withdrawal_sig_params`, lines 161-187), which explicitly rejects any other sighash type. [1](#0-0) 
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the tx with output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(`operator_xonly_pk`), and finalizes the witness for input 0 using the user's `SinglePlusAnyoneCanPay` signature. [2](#0-1) 
- Because `SinglePlusAnyoneCanPay` only commits to input 0 and output 0 (BIP341 semantics), the outputs at index 1 and 2 - including the operator's identifying OP_RETURN - are unauthenticated by the user's signature. `crates/clementine-tx-sender/src/rbf.rs::copy_witnesses` explicitly documents and relies on this property to preserve S+AP witnesses across RBF replacements, confirming the codebase's own understanding that these signatures survive transaction mutation. [3](#0-2) 
- `Verifier::update_finalized_payouts` resolves the operator purely from whichever transaction happens to be the one recorded as spending the withdrawal outpoint in `bitcoin_syncer_spent_utxos` (via `get_payout_txs_for_withdrawal_utxos`), then reads output 2's OP_RETURN of that specific confirmed tx to set `payout_payer_operator_xonly_pk`. [4](#0-3) 
- `get_payout_txs_for_withdrawal_utxos` joins on `bitcoin_syncer_spent_utxos.spending_txid`, which records the txid of whatever transaction actually spent `withdrawal_utxo_txid`/`vout` on the finalized chain - there is no check that this txid matches the one Operator A originally broadcast, nor any signature/output binding beyond the OP_RETURN parse. [5](#0-4) 

Exploit flow: after Operator A broadcasts its payout tx (with output 0 = user payout, output 2 = OP_RETURN(Operator A pk)) but before it confirms, an unprivileged attacker observes it in the mempool, copies input 0's witness (signature valid under S+AP), and constructs a new transaction with the same input 0 witness, the same output 0 (required for SIGHASH_SINGLE validity), but a different output 2 (Operator B's pubkey or garbage bytes) and/or altered fee/change via the anchor output. This new tx has a different txid and directly conflicts with (double-spends) Operator A's original. If this attacker tx is the one that gets mined (e.g., attacker submits with higher fee, or opts into replaceability the original didn't, or races propagation/relay), `update_finalized_payouts` will bind the withdrawal to Operator B's key (or `None`), never Operator A's.

None of the listed guards prevent this: `Verifier::is_deposit_valid`, `verify_storage_proofs`, `SPV::verify`, and `lc_proof_verifier` operate on Citrea-side commitments to the withdrawal outpoint and payout block, not on the identity of the fee-payer/OP_RETURN of whichever tx spends that outpoint on Bitcoin; there is no on-chain or off-chain check tying the OP_RETURN operator key to the party who actually funded output 0 in `update_finalized_payouts`, `Operator::withdraw`, or the bridge circuit's `bridge_circuit` (which likewise trusts `get_first_op_return_output` of whatever payout tx is referenced by the SPV proof).

### Impact Explanation
Operator A's own BTC left its wallet to satisfy output 0 of the withdrawal, but the DB permanently records a different (or no) `payout_payer_operator_xonly_pk` for that withdrawal index. `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:41-47) queries `get_first_unhandled_payout_by_operator_xonly_pk` keyed on Operator A's own key and will never find this withdrawal, so `handle_finalized_payout`/`Reimburse` never fires for Operator A - a permanent, uncompensated loss of the funds it fronted. This matches the Critical category "an honest operator permanently unable to be reimbursed." It is repeatable per withdrawal against any operator, and if Operator B's key was injected instead of `None`, it also sets up a false claim (Operator B could later attempt to claim reimbursement it never funded, though that would require Operator B's own kickoff/BitVM machinery cooperating - out of scope to fully trace here but is a secondary blast-radius consideration).

### Likelihood Explanation
The attacker needs no privileged role: only the ability to observe the Bitcoin mempool (any public node/mempool watcher) and to broadcast a competing transaction with sufficient fee to win the race for the block. The precondition is a race between Operator A's original broadcast and the attacker's malleated variant before confirmation - this is a well-known consequence of using `SinglePlusAnyoneCanPay` on a multi-output transaction where non-input-adjacent outputs are unauthenticated. Attacker cost is limited to fees for the competing transaction (potentially bidding above Operator A's fee), no special hardware or majority hashrate is required since this exploits standard mempool/relay replacement dynamics, not a chain reorg. This is repeatable across every withdrawal/payout for every operator.

### Recommendation
Change the withdrawal user's signature sighash flag (or transaction structure) so the OP_RETURN operator-identity output is committed by the signature - e.g., require `SIGHASH_ALL` or `SIGHASH_SINGLE` without `ANYONECANPAY` is insufficient by itself; the real fix is to not let the operator's identity output be excluded from what's signed. Since the user's signature must remain agnostic to which operator fronts the payout (that's the purpose of S+AP), instead bind the operator identity through a mechanism the signature does cover, or authenticate the OP_RETURN separately (e.g., require the spending transaction to be signed/co-signed by the operator itself over all outputs, or have `update_finalized_payouts`/off-chain bookkeeping require that output 0's actual funding UTXO trace back cryptoeconomically to whichever key appears in OP_RETURN, e.g. via requiring the OP_RETURN operator's key to also correspond to an input in the transaction, or restructure so an operator-controlled input funds an operator-committed output).

    /// Returns the withdrawal indexes and their spending txid for the given
    /// block id.
    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
