### Title
Consensus reward mis-attribution: a single relayer's signature is paid for every `StateMachineUpdated` event in a batch, regardless of who actually submitted the update - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` pays consensus relayers by inspecting only the **first** message in a batch to recover a signer, then pays that single signer for **every** `StateMachineUpdated` event that batch execution produced — even when those events were caused by other, later `Message::Consensus` entries in the same `handle_unsigned` call that were signed by different relayers.

### Finding Description
`Pallet::execute` in `modules/pallets/ismp/src/impls.rs` accepts a `Vec<Message>` in a single `handle_unsigned` extrinsic, executes all of them, aggregates every event produced (including all `StateMachineUpdated` events from all messages) into one `events` vector, and calls `T::FeeHandler::on_executed(messages_with_weights, events.clone())` exactly once for the whole batch: [1](#0-0) 

`pallet-consensus-incentives::on_executed` then derives the reward recipient from `messages.get(0)` alone: [2](#0-1) 

and then loops over **every** `StateMachineUpdated` event in the whole batch (collapsed per state machine to the highest height) and pays the *single* `relayer_account` recovered from message 0 for each one: [3](#0-2) 

`handle_unsigned` is a fully permissionless, unsigned extrinsic — `messages: Vec<Message>` — so nothing prevents a caller from submitting a batch that concatenates:
1. A cheap/self-authored `Message::Consensus` as `messages[0]`, signed by the attacker.
2. One or more genuinely valid `Message::Consensus` entries for *other* state machines, extracted/replayed from other relayers' already-broadcast (public, unsigned mempool) submissions, or simply batched together with the attacker's own message when several state machines advance in the same block.

Because `T::FeeHandler::on_executed` is invoked once per `handle_unsigned` call with the union of all events, and reward attribution is keyed only off `messages[0]`'s signer, the attacker's account collects the `$BRIDGE` reward (plus 1:1 reputation-asset mint) for state-machine advances it did not perform, while the relayer whose message actually produced those `StateMachineUpdated` events is skipped entirely for that batch. The `LastRewardedHeight` watermark still advances for the correctly-updated state machine, so the honest relayer cannot re-claim that reward later — it is fully captured by the attacker's account, not merely delayed.

This is not a case of a malicious relayer/peer assumption being violated — any unprivileged party can call `Ismp::handle_unsigned` with an arbitrary `Vec<Message>` as long as message-level proof verification passes for each entry (verification happens per-message in `handle_incoming_message`, independent of who is credited). Batching itself requires no cooperation from the other message's original submitter; consensus proofs are public artifacts, not owned by whoever first crafts them, and `validate_unsigned` already accepts multiple independent messages together (see the batch content-hash `provides` tag logic), confirming that multi-message, multi-signer batches through this single extrinsic are an expected, sanctioned code path.

### Impact Explanation
This is a **wrong-beneficiary / unauthorized fund reallocation** bug: `$BRIDGE` treasury funds and reputation-asset mints (which directly feed into collator-selection eligibility, per the docs) are diverted from the relayer that actually performed the finality-advancing work to whichever account happens to occupy `messages[0]` of a batch. An attacker can systematically front-load their own trivial/self-signed consensus message ahead of genuine third-party updates in every batch they submit, capturing rewards and reputation that should accrue to other relayers, degrading the incentive model that protects Hyperbridge's need for continuously fresh state commitments and undermining the reputation-weighted collator selection (`pallet-collator-manager`) with mis-earned reputation.

### Likelihood Explanation
High. `handle_unsigned` is unsigned and permissionless by design (documented as "anyone can execute ISMP messages for free with valid proofs"). No admin, governance, or trusted-relayer assumption is required — only that the attacker can assemble a `Vec<Message>` containing at least one `Message::Consensus` they control as the first element, plus additional consensus messages (their own for other state machines, or ones observed from the public network) that produce `StateMachineUpdated` events. This requires no proof forgery, no compromised relayer key, and no race condition beyond simple transaction construction — it is a direct consequence of batch reward attribution logic.

### Recommendation
In `pallet-consensus-incentives::on_executed`, attribute each `StateMachineUpdated` event to the signer of the specific `Message::Consensus` that produced it, not to `messages[0]`. This requires threading the per-message signer through to event correlation (e.g., pairing each `Message::Consensus` with the state-machine IDs it actually advanced, rather than pooling all events against a single recovered signer), or splitting `on_executed` processing so each consensus message in the batch is credited only for the state-machine advances it individually caused.

### Proof of Concept
1. Attacker controls account `A` and constructs a valid `Message::Consensus` for `chain_X` signed by `A`, producing a genuine (but perhaps minimal/cheap) `StateMachineUpdated { chain_X, height: h1 }`.
2. Attacker observes (from the public mempool/RPC, since these are unsigned, freely gossiped, permissionless extrinsics) a separate, unrelated, already-valid `Message::Consensus` for `chain_Y`, originally signed by honest relayer `B`, which would independently produce `StateMachineUpdated { chain_Y, height: h2 }`.
3. Attacker submits a single `handle_unsigned` call with `messages = [attacker_message_for_chain_X, honest_message_for_chain_Y]`.
4. `Pallet::execute` processes both messages, verifying each independently (proof verification does not check "the submitter must be the one who benefits"), and yields `events` containing both `StateMachineUpdated` entries.
5. `on_executed` recovers `relayer_account = A` from `messages[0]` only, then iterates `highest_per_state_machine` (containing both `chain_X` and `chain_Y`) and calls `process_message` for both — paying `A` from the treasury for `chain_Y`'s advance and minting `A` the corresponding reputation, even though `B` did the work and gets nothing for that submission.
6. `LastRewardedHeight` for `chain_Y` is now updated to `h2`, so `B`'s original submission (if it lands separately/later) or any re-submission for the same span pays zero reward (`calculate_reward` returns 0 for spans already covered by the watermark).

**Uncertainty:** I was not able to fully confirm within the available context whether `handle_unsigned`'s `#[frame_support::transactional]` combined with mempool validity checks in `validate_unsigned` would reject a batch mixing an attacker-authored message with a "stolen" pre-broadcast message from another relayer before it lands on-chain (e.g., due to nonce/priority tag collisions in the transaction pool) — this could reduce practical exploitability to same-block, self-authored multi-chain submissions only (still a valid, simpler version of the same mis-attribution bug: an attacker who legitimately runs consensus clients for multiple chains and batches them loses nothing, but an attacker who front-runs *others'* messages before they land might be blocked at the txpool layer). A Devin session with the ability to build and run the runtime's transaction pool tests would be needed to confirm the exact blast radius.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
