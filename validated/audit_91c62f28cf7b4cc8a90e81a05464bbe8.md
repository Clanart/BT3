## Answer

The report's bug class ("action costs nothing/flat regardless of actual work → attacker exploits it to disrupt other users cheaply") maps onto a genuine underpriced-compute pattern in `SyscallGetProcessedSiblingInstruction`.

### Title
Underpriced compute for `sol_get_processed_sibling_instruction` allows cheap linear-scan DoS of compute budget accounting - (File: `syscalls/src/lib.rs`)

### Summary
`SyscallGetProcessedSiblingInstruction` charges only a flat `syscall_base_cost` no matter how many instruction-trace entries it has to scan, while its implementation performs a reverse linear scan over the transaction's instruction trace.

### Finding Description
The syscall consumes a constant cost up front and only afterward performs an unbounded (up to `MAX_INSTRUCTION_TRACE_LENGTH = 64`, [1](#0-0) ) reverse walk of the instruction trace: [2](#0-1) 

The cost model treats this as an `O(1)` syscall (`syscall_base_cost`, default 100 CU, see [3](#0-2) ), but the actual work is `O(trace length)`, bounded only by `MAX_INSTRUCTION_TRACE_LENGTH`. A caller program can cheaply grow the instruction trace via CPIs (each CPI itself is only charged the flat `invoke_units` base cost, see `cpi_common` at [4](#0-3) ) and then repeatedly call `sol_get_processed_sibling_instruction` with a non-matching `index`, forcing the runtime to walk the full trace each time for the same flat 100 CU charge.

### Impact Explanation
This is a "materially underpriced compute" instance: the price charged (constant `syscall_base_cost`) does not scale with the real work performed (linear scan up to 64 trace entries per call, repeatable many times per transaction while compute budget allows). Compared to the report's core complaint — an action that costs the attacker far less than the resource consumption it imposes — this lets a malicious program pack many cheap-but-linear scans into a single transaction, extracting more CPU work per compute unit than intended by the fee/compute-unit model. This degrades the fairness/throughput guarantees of the compute-unit pricing scheme (nodes do more work than they are paid for in CU terms), though the blast radius is bounded by `MAX_INSTRUCTION_TRACE_LENGTH = 64` and the per-transaction compute unit limit, which caps the total amplification.

### Likelihood Explanation
High likelihood of being reachable by any unprivileged on-chain program (no special privilege needed — any program can invoke `sol_get_processed_sibling_instruction`, build up CPI trace depth, and loop the syscall). However, because the trace length is hard-capped at 64 and the syscall base cost is nonzero, the actual amplification factor is small and bounded, which limits severity — this is a mispricing/underpricing issue rather than an unbounded resource-exhaustion vector.

### Recommendation
Charge a per-entry cost proportional to the number of trace entries scanned (e.g., `syscall_base_cost + mem_op_base_cost * entries_scanned`), similar to how other trace/array-scanning syscalls (e.g., hashing, sysvar reads) charge cost proportional to length rather than a flat base cost.

### Proof of Concept
Not independently verified with a live cluster/harness in this pass; the finding is based on static analysis of `syscalls/src/lib.rs` (`SyscallGetProcessedSiblingInstruction::rust`, lines 2009–2107) and its cost accounting versus the actual reverse-scan loop over the instruction trace. A concrete PoC would require: (1) a BPF program that performs nested CPIs to build a deep/wide instruction trace, (2) repeated calls to `sol_get_processed_sibling_instruction` with an `index` guaranteed not to match (forcing full scans), and (3) comparing measured wall-clock/instruction-count cost per CU charged against a baseline syscall of equivalent CU cost. I was not able to execute this PoC within the current investigation and flag this as unverified beyond the static code-path analysis above.
