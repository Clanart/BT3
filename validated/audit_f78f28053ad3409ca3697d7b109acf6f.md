### Title
Copilot conflict-resolution write path validates only "inside repo root," not "is an actual conflicted file," allowing writes into `.git/` internals - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Solana report's root cause was that the `burn` instruction checked a coarse global invariant (`amount_in < VRT supply`) instead of verifying the caller actually owns a specific withdrawal ticket, letting any VRT holder redeem funds outside the intended ticket-based workflow. The analogous flaw in GitHub Desktop is in the Copilot conflict-resolution "accept" flow: when writing an AI-suggested resolution to disk, the code only verifies that `resolution.path` resolves to somewhere *inside the repository root* via `resolveWithin`, rather than verifying it is one of the specific files that were actually presented to the model as conflicted (the fine-grained authorization the workflow is supposed to enforce).

### Finding Description
`buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:376-470`) builds the list of conflicted files sent to Copilot, resolving each `file.path` with `resolveWithin(workingDirectory, file.path)` [1](#0-0) .

When the user accepts Copilot's suggested resolutions, the write-back logic in `app-store.ts` iterates `copilotResolutions` and, for each entry, does:
1. `resolveWithin(repository.path, resolution.path)` — only checks that the final path is inside the repo root, not inside the *working tree of tracked files*.
2. A skip-check that looks up `resolution.path` in `state.changesState.workingDirectory.files` — but this only fires (skips the write) when the file *is found* and is already a resolved conflict; if no matching entry is found, the code falls through and writes anyway.
3. `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally in that fallthrough case. [2](#0-1) 

Since `resolveWithin` only verifies path containment under `repository.path` — and `.git` is a subdirectory of `repository.path` — a `resolution.path` value such as `.git/hooks/post-checkout` or `.git/config` will (a) pass `resolveWithin` and (b) never match any entry of `workingDirectory.files` (git status never lists `.git` internals as a working-directory file), so the "already resolved externally" skip never triggers, and `writeFile` executes unconditionally against attacker/model-supplied content. `resolveWithin` (`app/src/lib/path.ts:36-72`) is a generic path-traversal guard that has no concept of "must be a tracked, conflicted file" [3](#0-2)  — exactly the same class of gap as the Solana `burn` check that verified "less than total supply" instead of "tied to a specific ticket."

### Impact Explanation
If an attacker can influence the `path` field of a Copilot-generated conflict resolution — e.g., via prompt injection embedded in the conflicting file content of a repository the victim clones/fetches and then merges/rebases with conflicts — the resulting `writeFile` call can drop attacker-controlled content into `.git/hooks/*`, silently installing an executable git hook. That hook then runs with the user's privileges the next time a matching git operation (`post-checkout`, `pre-commit`, `post-merge`, etc.) executes inside Desktop or from the command line — achieving code execution outside of what the user intended to write, and outside the review the "manual resolution" flow is meant to provide.

### Likelihood Explanation
This requires: (1) the victim uses the Copilot conflict-resolution feature, (2) the attacker can shape the conflicted file content/AI prompt so that the model's structured output includes a resolution entry whose `path` is `.git/...` rather than one of the real conflicted files, and (3) no additional allowlist check exists between "files sent to the model" and "the specific list of paths the app allows writing back to." Point 3 is the piece confirmed from `app-store.ts`; I could not verify from the index whether an earlier stage (in `app/src/lib/copilot-conflict-resolution.ts`, which I was unable to fully read) already filters resolutions to a strict allowlist of the original file paths before they reach this write step — if such a check exists there, likelihood drops significantly. This should be verified directly in that file before treating this as confirmed-exploitable.

### Recommendation
Before calling `writeFile`, validate that `resolution.path` is a member of the exact set of file paths that were sent to Copilot in `buildConflictContext` (i.e., cross-check against the original `files` list / `copilotResolutions` source, not just repo-root containment), and explicitly reject any path under `.git/` regardless of containment. This restores the "tied to a specific authorized entity" check that `resolveWithin` alone does not provide.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
