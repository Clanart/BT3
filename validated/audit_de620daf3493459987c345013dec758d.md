## Title
Unhandled exception in `UncurriedNFT.uncurry()` when parsing an attacker-crafted NFT coin puzzle can crash wallet sync (`chia/wallet/nft_wallet/uncurry_nft.py`)

### Summary
`UncurriedNFT.uncurry()` is called by `WalletStateManager.determine_coin_type()` whenever a wallet observes any new coin with an odd amount (potential singleton) during normal sync, as part of automatically detecting NFT coins. [1](#0-0)  Any peer/counterparty can cause a victim's wallet to receive (or simply observe on-chain, via `get_coin_state` subscriptions) a coin whose puzzle is curried in a way that satisfies the outer singleton check but has a malformed/foreign inner structure, and this reaches unguarded structural-parsing code in the uncurry routine.

### Finding Description
`UncurriedNFT.uncurry()` parses a puzzle_reveal's curried arguments in two separate `try/except` blocks, but between them there is an **unguarded** parsing statement:

```python
try:
    (singleton_struct, nft_state_layer) = curried_args.as_iter()
    singleton_mod_hash = singleton_struct.first()
    singleton_launcher_id = singleton_struct.rest().first()
    launcher_puzhash = singleton_struct.rest().rest()
except ValueError as e:
    log.debug(...)
    return None

mod, curried_args = curried_args.rest().first().uncurry()   # <-- NOT wrapped in try/except
if mod != NFT_MOD:
    ...
try:
    ...
except Exception as e:
    ...
    return None
``` [2](#0-1) 

`curried_args.rest().first()` assumes `curried_args` (the outer singleton curry args) always contains at least a second CLVM cons-pair element that can be unpacked with `.first()`. If an attacker crafts a puzzle whose outer mod exactly equals `SINGLETON_TOP_LAYER_MOD` (so the initial `mod != SINGLETON_TOP_LAYER_MOD` check at line 97 passes) but whose curried arguments are structured such that `curried_args.rest()` evaluates to an atom (e.g. `nil`) rather than a cons pair, calling `.first()` on it raises an unhandled exception (CLVM `EvalError`/similar, not `ValueError`), which propagates out of `uncurry()` uncaught — the exact same bug class as the p7zip CVE: a missing null/structure check on attacker-controlled parsed data leading to a crash instead of a graceful parse failure.

This is directly analogous to CVE-2016-9296: p7zip's `CInArchive::ReadAndDecodePackedStreams` lacked a null check on `folders.PackPositions` when decoding a malformed archive, causing a crash/DoS. Here, `UncurriedNFT.uncurry()` lacks an exception guard around a structural assumption when decoding an attacker-supplied malformed puzzle, causing an unhandled exception.

### Impact Explanation
`determine_coin_type()` is invoked on essentially every new coin the wallet learns about during sync (any coin with an odd amount is speculatively treated as a possible singleton/NFT), reachable simply by sending the victim wallet's tracked puzzle hashes a crafted coin, or by a peer serving coin states for subscribed puzzle hashes. [3](#0-2)  If the unguarded call raises, and the exception is not caught further up the call stack in the wallet sync pipeline, this becomes a spend/coin-state-triggered denial of service against the victim's wallet process — halting wallet sync/transaction processing until manual intervention, which satisfies the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Medium-High. Exploitation requires only the ability to get a wallet to observe a coin with a puzzle reveal that passes the outer `SINGLETON_TOP_LAYER_MOD` check but has a malformed/short curry-argument list for the second (inner) position — something fully controllable by whoever creates the coin's puzzle (no signature or special privilege needed, since parsing happens before/independent of any spend authorization). The only mitigating factor is that the exact CLVM shape needed to make `curried_args.rest()` return a non-pair while `curried_args.as_iter()` two-tuple-unpacks successfully needs to be verified experimentally against the Rust CLVM `Program` implementation's exact behavior for `.first()`/`.rest()` on atoms.

### Recommendation
Wrap the `mod, curried_args = curried_args.rest().first().uncurry()` line (and any other similarly unguarded structural CLVM parsing calls in the `uncurry()` method) in the same broad exception handling used elsewhere in the function, returning `None` on any parsing failure instead of letting exceptions propagate. Ensure the same treatment is applied to related uncurry helpers (e.g. `nft_puzzle_utils.py`, `did_wallet_puzzles.py`, `pool_puzzles.py`) that perform unguarded `.first()`/`.rest()` chains on attacker-influenced `Program` structures.

### Proof of Concept
Not independently verified end-to-end in this session — I could not execute the CLVM runtime to confirm which specific exception type (`ValueError` vs. an uncaught type) is raised by `Program.first()`/`.rest()` on a non-pair atom in the current `chia_rs`-backed `Program` implementation, nor trace whether any outer caller (e.g. `_add_coin_state`) wraps `determine_coin_type()` in a catch-all. This should be confirmed by constructing:
1. An inner puzzle curried with `SINGLETON_TOP_LAYER_MOD.curry(singleton_struct, X)` where `X` is a single atom (not a further pair), so `curried_args.rest().first()` fails structurally, and
2. Observing whether `WalletStateManager.determine_coin_type()` or its callers swallow the resulting exception or crash wallet processing of that sync batch. [4](#0-3) [3](#0-2)
