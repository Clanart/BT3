## Analog Found: Automatic `BranchPruner` deletes local branches based on remote-supplied ref state, without user confirmation

### Title
Attacker-controlled remote ref advertisement during `fetch --prune` causes silent, unconfirmed local branch deletion via `BranchPruner` - (File: `app/src/lib/stores/helpers/branch-pruner.ts`)

### Summary
The StakeWise report's broken invariant is: a background "state update" routine silently mutates a user's asset even though the precondition that should gate the mutation (the vault being collateralized) is never checked, because the routine is implicitly coupled to another subsystem (legacy V2) that the developer didn't account for. The closest structural analog in GitHub Desktop is `BranchPruner`, which runs automatically on a timer and silently deletes local branch refs based on state that is itself derived from remote-supplied data (`git fetch --prune`), with none of the confirmation dialogs that gate every other destructive git operation in this codebase (checkout, undo commit, reset, stash overwrite).

### Finding Description
`AppStore.startBackgroundPruner` starts a `BranchPruner` per repository that repeats every 4 hours without any user interaction: [1](#0-0) 

`BranchPruner.pruneLocalBranches` decides which local branches to hard-delete (`git branch -D`) using three signals: (1) `getMergedBranches` — real local ancestry check against the cached `defaultBranch.tip`, (2) recency of checkout, (3) whether the branch's configured upstream ref is still present in the locally cached remote-tracking refs (`refs/remotes/...`): [2](#0-1) 

The remote-tracking refs used in check (3) are populated by ordinary `git fetch`, which always runs with `--prune`: [3](#0-2) 

`--prune` makes the local remote-tracking ref set fully trust whatever the remote (or a proxy/MITM sitting in front of it) chooses to advertise during the fetch negotiation. If a branch's ref is simply omitted from the remote's advertised ref list, `git fetch --prune` deletes the corresponding local `refs/remotes/origin/<branch>` — this is standard git behavior, not a Desktop bug by itself. The Desktop-specific issue is that `BranchPruner` then treats "upstream ref missing from local remote-tracking cache" as authoritative evidence that the branch was deleted on GitHub, and — for any local branch it deems "merged" into the default branch — silently force-deletes the local branch (`deleteLocalBranch` → `git branch -D`) with zero user confirmation: [4](#0-3) 

Every other equally-or-less destructive operation in the same codebase (checkout with stash conflict, undo commit, reset to commit) explicitly stops and shows a confirmation dialog before proceeding: [5](#0-4) [6](#0-5) [7](#0-6) 

`BranchPruner` has none of these guards — it is invoked purely from a timer/interval and from every background fetch cycle, with no popup, no dispatcher confirmation path, and no way for the user to see it coming: [8](#0-7) 

This mirrors the StakeWise bug precisely: a state-sync routine (`updateState` / `pruneLocalBranches`) is wired to run unconditionally/automatically and mutates a value the user cares about (vault shares / local branch refs) based on data supplied by a system the routine implicitly trusts (legacy V2 linkage / remote ref advertisement), with no explicit precondition check ("is the vault collateralized" / "is this deletion something the user actually wants").

### Impact Explanation
A malicious or compromised git remote (or a MITM proxy terminating the user's git transport — explicitly in-scope per the Valid Impact section) can manipulate the ref advertisement returned during `git fetch --prune` to omit a branch that still exists. On Desktop's next background prune cycle (which runs automatically, without any user action beyond having the app open), any local branch whose commits are already reachable from the cached default branch tip and whose upstream now appears "gone" will be force-deleted with `git branch -D`, and the deletion also propagates via `this.onPruneCompleted` → `_refreshRepository`, updating the UI so the branch disappears from the user's branch list without any prompt. This is a silent, attacker-influenced corruption of the user's local repository state (branch pointers/tracking configuration removed) achieved purely by controlling remote/proxy responses — no local access, no leaked credentials, no malware, and no unusual user steps required.

### Likelihood Explanation
The prerequisite conditions are all realistic and already covered by the app's normal operation: background fetching is on by default for every repository with a linked GitHub repository, `--prune` is unconditionally passed to every fetch, and the pruner runs every 4 hours checking a 24-hour threshold. Any attacker capable of serving fetch responses for a remote the victim has added (self-hosted/enterprise remote, compromised third-party mirror, or network-level proxy/MITM in a corporate environment) can trigger this without the victim taking any unusual action.

### Recommendation
`BranchPruner.pruneLocalBranches` should not treat the absence of a remote-tracking ref as sufficient, silent justification for `git branch -D`. At minimum: (1) re-verify the branch's remote status against the GitHub API (which the app already has access to via `GitHubRepository`) rather than relying solely on local ref-advertisement state from `git fetch --prune`, and (2) surface the same class of confirmation Dialog used for checkout/reset/undo (`PopupType`) the first time a batch of branches is about to be auto-pruned, or provide a persisted, visible log/undo affordance before the ref is destroyed.

### Proof of Concept
1. Victim adds a remote pointing at an attacker-controlled git server (or one behind an attacker-controlled proxy), and has a local branch `feature` whose upstream is `origin/feature`, already fully merged into the default branch locally.
2. Attacker's git server responds to the next `git fetch --prune` (issued automatically by Desktop's `BackgroundFetcher`/`RepositoryIndicatorUpdater`, see `app/src/lib/stores/helpers/background-fetcher.ts`) with a ref advertisement that simply omits `refs/heads/feature`, even though the branch still exists.
3. `git fetch --prune` deletes the local `refs/remotes/origin/feature` tracking ref as designed.
4. Within 24 hours, `BranchPruner.pruneLocalBranches` runs (`app/src/lib/stores/helpers/branch-pruner.ts:136-259`), finds `feature` merged and its upstream absent from `remoteBranches`, and executes `deleteLocalBranch(repository, 'feature')` → `git branch -D feature`, with no dialog and no way for the user to intervene.
5. The user's local branch disappears silently; if they had any local-only tracking configuration or intended to keep working on that ref, it's gone without warning — unlike every comparable destructive action elsewhere in the app.
