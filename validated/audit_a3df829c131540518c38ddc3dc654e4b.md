## Title
Duplicate concurrent clones for the same deep-linked repository URL corrupt the destination directory - (`app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The Lighthouse bug is a TOCTOU race: a peer could be queued for dialing twice because the "already dialing" bookkeeping was updated only *after* the peer entered the processing queue rather than before, so two concurrent discovery events for the same peer both passed the "not yet dialing" check. GitHub Desktop has the same shape of defect in its `x-github-client://openRepo/...` deep-link ("Open in Desktop") handling: the dedup check that decides whether a URL should trigger a brand-new clone is only checked against *fully registered* repositories, not against clones that are already in flight, and the dedup state is registered too late relative to when a second event can be processed.

### Finding Description
`dispatchURLAction` handles incoming deep-link events and, for `open-repository-from-url`, calls `openRepositoryFromUrl` without awaiting it (fire-and-forget): [1](#0-0) 

`openRepositoryFromUrl` eventually calls `openOrCloneRepository(url)`: [2](#0-1) 

`openOrCloneRepository` de-duplicates only against `state.repositories` — i.e. repositories that have already been fully added/cloned: [3](#0-2) 

Repositories that are currently *being cloned* are **not** tracked in `state.repositories`; they live in a separate `cloningRepositoriesStore` collection, which `openOrCloneRepository`/`doesRepositoryMatchUrl` never consults: [4](#0-3) 

The actual clone kickoff, `AppStore._clone`, also performs no de-duplication — it unconditionally pushes a new `CloningRepository` and starts a new `git clone` process for whatever `url`/`path` it's given: [5](#0-4) [6](#0-5) 

Because the "is this URL already being handled?" check (`openOrCloneRepository`) only looks at completed repositories, and the deep-link dispatch is not awaited/serialized, two `open-repository-from-url` events for the same URL arriving in quick succession (e.g., the user or a malicious page firing the `x-github-client://` scheme twice, or the OS replaying the launch event) will both pass the "not already present" check before the first clone has registered anywhere that `openOrCloneRepository` inspects. Each occurrence opens its own `CloneRepository` popup targeting the same computed default path (derived deterministically from the repo URL) and can independently invoke `AppStore._clone` / `cloningRepositoriesStore.clone` against the identical destination directory concurrently.

This is the same broken invariant as the Lighthouse bug: the "in-progress" state is registered too late (after admission into the concurrent-processing path) rather than being checked-and-set atomically before a new instance of the operation can be queued.

### Impact Explanation
Two concurrent `git clone` processes writing into the same target directory can corrupt the resulting working tree/`.git` directory (partial/interleaved object writes, inconsistent index, or an incomplete clone that Desktop nonetheless treats as valid). Since the destination path and URL are attacker-influenced when the flow originates from a clicked "Open in Desktop" link on an attacker-controlled or compromised web page, an attacker can reliably trigger this race by firing the protocol handler twice for the same URL, producing a corrupted local repository once the user opens it — the "silent corruption of what the user commits or pushes" class of impact, since operations on a corrupted repo may behave unpredictably without clear error surfacing.

### Likelihood Explanation
Requires only that the deep-link/protocol handler be invoked twice for the same URL within the window before the first clone completes and is registered in `state.repositories` — no local access, admin rights, or prior compromise needed. This can plausibly happen from double-invocation of the OS URL handler (common on some platforms when relaunching), or from a webpage that fires the link twice (e.g., via a redirect plus a JS-triggered navigation) — no unnatural multi-step user interaction is required beyond clicking a link that is fired more than once by the surrounding page/OS.

### Recommendation
Track in-flight "open/clone from URL" requests keyed by the normalized URL (and target path) at the point `openOrCloneRepository`/`_startOpenInDesktop` is entered, and short-circuit (or await/coalesce into) any request that is already in flight, mirroring the fix pattern from the Lighthouse commit: register the "in-progress" marker *before* the operation is allowed to proceed, not after it completes.

### Proof of Concept
1. Register/trigger the `x-github-client://openRepo/<url>` handler twice in rapid succession (e.g., two OS `open-url` events, or a web page invoking the protocol link twice) with the same repository URL and no existing local repository for it.
2. Both invocations reach `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository`, and since neither is yet present in `state.repositories`, both pass the existing-repository check. [3](#0-2) 
3. Both open a `CloneRepository` popup (or call `_startOpenInDesktop`) for the same computed destination path, and each can independently call `AppStore._clone`, launching two concurrent `git clone` processes into the same directory. [5](#0-4) 
4. The resulting directory ends up with interleaved/partial writes from two concurrent clones, yielding a corrupted repository that Desktop may still surface to the user as "successfully cloned."

```typescript
  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }
```

```typescript
/** The store in charge of repository currently being cloned. */
export class CloningRepositoriesStore extends BaseStore {
  private readonly _repositories = new Array<CloningRepository>()
  private readonly stateByID = new Map<number, ICloneProgress>()

  /**
   * Clone the repository at the URL to the path.
   *
   * Returns a {Promise} which resolves to whether the clone was successful.
   */
  public async clone(
    url: string,
    path: string,
    options: CloneOptions
  ): Promise<boolean> {
    const repository = new CloningRepository(path, url)
    this._repositories.push(repository)

    const title = `Cloning into ${path}`

    this.stateByID.set(repository.id, { kind: 'clone', title, value: 0 })
    this.emitUpdate()

    let success = true
    try {
      await cloneRepo(url, path, options, progress => {
        this.stateByID.set(repository.id, progress)
        this.emitUpdate()
      })
    } catch (e) {
      success = false

      const retryAction: RetryAction = {
        type: RetryActionType.Clone,
        name: repository.name,
        url,
        path,
        options,
      }
      e = new ErrorWithMetadata(e, { retryAction, repository })

      this.emitError(e)
    }

    this.remove(repository)

    return success
  }
```

```typescript
  /** This shouldn't be called directly. See `Dispatcher`. */
  public _clone(
    url: string,
    path: string,
    options: { branch?: string; defaultBranch?: string } = {}
  ): {
    promise: Promise<boolean>
    repository: CloningRepository
  } {
    const promise = this.cloningRepositoriesStore.clone(url, path, options)
    const repository = this.cloningRepositoriesStore.repositories.find(
      r => r.url === url && r.path === path
    )!

    promise.then(success => {
      if (success) {
        this.statsStore.recordCloneRepository()
      }
    })

    return { promise, repository }
  }
```
