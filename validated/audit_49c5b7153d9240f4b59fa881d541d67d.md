This confirms the tracking is generic: `get_payout_txs_for_withdrawal_utxos` joins on `withdrawals.withdrawal_utxo_txid`/`vout` against `bitcoin_syncer_spent_utxos.txid`/`vout` — i.e. it records whichever transaction actually spends the withdrawal outpoint on-chain, regardless of who broadcast it [1](#0-0) . Since a UTXO can only be spent once, the attacker's copy racing to confirm first (with the honest operator's still-valid `SinglePlusAnyoneCanPay` signature but a swapped OP_RETURN output) permanently supersedes the honest operator's original broadcast, and the row is written once with the attacker's chosen (or absent) operator pubkey.

### Title
Payout tx's `SinglePlusAnyoneCanPay` signature does not cover the OP_RETURN operator-attribution output, allowing third-party malleation of payer attribution - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `Payout` transaction built by `create_payout_txhandler` places the fronting operator's x-only pubkey in an unsigned OP_RETURN output (output index 2), while the user's `SinglePlusAnyoneCanPay` signature (verified in `Operator::withdraw`) only commits to input 0 and output 0. Because `SIGHASH_SINGLE|ANYONECANPAY` never covers the OP_RETURN output, any observer of the honest operator's broadcast (but unconfirmed) payout tx can rebuild an equivalent transaction with the same input/witness and output 0, a different OP_RETURN, and a higher fee, and get it mined first, hijacking the payout attribution.

### Finding Description
The intended binding is: `withdrawals.payout_payer_operator_xonly_pk` (for withdrawal index i) == the operator who actually funded output 0 of the transaction that spends withdrawal outpoint i.

`create_payout_txhandler` constructs the payout tx with input 0 = withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user's payout, output 1 = anchor, output 2 = `op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()))` [2](#0-1) . `Operator::withdraw` verifies the user's signature with `sighash_type = SinglePlusAnyoneCanPay` via `SECP.verify_schnorr` [3](#0-2) , and `calculate_script_spend_sighash`/`calculate_sighash_txin` uses `Prevouts::One(txin_index, ...)` for `*PlusAnyoneCanPay` sighash types [4](#0-3) . Per BIP-341/342, `SIGHASH_SINGLE` commits only to the output at the same index as the input (index 0 here); it does not commit to any other output, so outputs 1 (anchor) and 2 (OP_RETURN) are completely unauthenticated.

Exploit: an unprivileged attacker observes the honest operator's payout tx in the mempool, copies input 0 (same outpoint, same witness/signature — no key material needed), copies output 0 verbatim, replaces output 2's OP_RETURN with a different operator's xonly pubkey (or invalid/garbage bytes), optionally changes fee/anchor, and rebroadcasts (RBF or simple race). This produces a different, still-validly-signed transaction spending the same outpoint. If it confirms first, the honest operator's original tx becomes permanently invalid (double-spend of a now-consumed UTXO).

`Verifier::update_finalized_payouts` and `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:168-196`) determine the payout transaction generically by finding whichever transaction spends `withdrawals.withdrawal_utxo_txid`/`vout` in `bitcoin_syncer_spent_utxos`, not by matching a pre-recorded expected txid [1](#0-0) . It then extracts `operator_xonly_pk` purely from `get_first_op_return_output` + `parse_op_return_data` on whatever tx actually confirmed [5](#0-4)  and stores it via `update_payout_txs_and_payer_operator_xonly_pk` [6](#0-5) . No check ties the recorded pubkey back to whoever actually funded/broadcast the tx, nor to the pubkey the honest operator used when constructing it. No existing guard (`Verifier::is_deposit_valid`, `SECP.verify_schnorr`, `SPV::verify`, etc.) checks that the OP_RETURN output is covered by the sighash or matches the actual fee-payer.

Downstream, `Operator::validate_payer_is_operator` requires `payer_xonly_pk == self.signer.xonly_public_key` [7](#0-6) ; if the recorded pubkey is wrong or `NULL`, this permanently fails for the honest operator (the withdrawal row's `payout_txid`/`payout_payer_operator_xonly_pk` are fixed once the spending tx confirms, and the UTXO can't be re-spent). `PayoutCheckerTask::run_once`'s `get_first_unhandled_payout_by_operator_xonly_pk` will never return this withdrawal for the honest operator either, since the SQL filters on `payout_payer_operator_xonly_pk = $1` [8](#0-7) . Separately, `Verifier::is_kickoff_malicious` treats any kickoff later sent by the honest operator for this deposit as malicious because the recorded `operator_xonly_pk` won't match `kickoff_data.operator_xonly_pk` [9](#0-8) .

### Impact Explanation
The operator who actually funded the user's withdrawal (fronting the full `bridge_amount`, e.g. 10 BTC) loses the ability to ever be reimbursed through the normal Reimburse path, and any kickoff they send for this deposit is flagged malicious, exposing their collateral to Challenge/Disprove. This is a permanent, one-shot-per-withdrawal griefing primitive repeatable across every future withdrawal and every operator, matching the "Critical - honest operator permanently unable to be reimbursed" / "honest operator's collateral burned" categories.

### Likelihood Explanation
The attacker needs no privileged role, no key material, and no funds beyond fees: they only need to observe the honest operator's payout tx in the mempool (a public event) and win a fee race or first-seen race to get their modified copy confirmed instead. This is straightforward transaction malleability enabled by an under-committing sighash type, feasible any time a payout tx is broadcast pre-confirmation, and repeatable for every withdrawal/operator.

### Recommendation
Include the OP_RETURN (operator attribution) output in the committed sighash — e.g., have the user sign with `AllPlusAnyoneCanPay` or `Default`/`All` sighash covering all outputs, or otherwise cryptographically bind the operator identity to the signed message so a third party cannot substitute the fronting operator's identity without invalidating the signature.

        .finalize();
