### Title
Prefix-based write-whitelist check allows unauthorized key writes when a permitted key name is a string prefix of another key - ([File: store/whitelist/kv/store.go])

### Summary
The `store/whitelist/kv` package enforces which store keys a caller may write to via a simple `strings.HasPrefix` comparison against a whitelist of key strings, rather than requiring an exact key match or a properly delimited prefix boundary. This mirrors the Opencast CVE-2017-1000221 bug class: access is granted based on partial/prefix string matching of an identifier (there, usernames; here, KV store keys), rather than exact identity comparison.

### Finding Description
`Store.validateKeyForWrite` walks the whitelist set and allows the write if the candidate key merely starts with any whitelisted string: [1](#0-0) 

Because `strings.HasPrefix(keyStr, whitelist)` has no delimiter/boundary check, any whitelist entry `"X"` also authorizes writes to every key beginning with `X`, e.g. whitelisting `"foo"` also permits writing to `"foofoo"`, `"foobar"`, etc. This is confirmed directly by the module's own test suite, which asserts that `"foofoo"` does not panic (i.e., is treated as permitted) when only `"foo"` is whitelisted: [2](#0-1) 

This `kv.Store` wrapper is installed on every module store accessed through the whitelisted `MultiStore`/`CacheMultiStore` wrappers, which look up a per-store-key whitelist and wrap the underlying KV store with this prefix-matching guard: [3](#0-2) [4](#0-3) 

If any caller of this whitelist mechanism intends to scope write access narrowly (e.g., only allow deferred/async execution or an OCC parallel task to write specific narrow sub-keys within a module's store), the prefix bug silently widens that grant to any key sharing the same string prefix. Any state key that happens to share a prefix with a whitelisted key becomes writable even though it was never intended to be included in the allow-list.

### Impact Explanation
This is an access-control/incorrect-permission-assignment bug directly analogous to the Opencast CVE: a partial-match check substitutes for an exact-match authorization decision. Depending on how granular the whitelist entries are configured for a given module (i.e., how "prefix-collision-prone" the key namespace is), an entity restricted to writing only a specific whitelisted key/prefix could end up with write access to adjacent, unintended state within the same module's store — enabling out-of-scope state mutation (e.g., balances, allow-lists, or other module data whose keys happen to share a prefix) that the whitelist was supposed to exclude. Because this store wrapper guards writes reachable during transaction execution (OCC parallel execution / deferred-write paths use this layered store), a crafted transaction or contract interaction that causes writes to attacker-influenced keys sharing a prefix with a whitelisted key could result in unauthorized state modification — potentially affecting fund-related state depending on how whitelist strings are configured for bank/tokenfactory-related stores.

### Likelihood Explanation
Exploitability is contingent on the specific whitelist configuration passed to `multi.NewStore`/`cachemulti.NewStore` (the `storeKeyToWriteWhitelist` map) at runtime — I was not able to locate, within the available index, the call site(s) that actually construct/populate this map with real whitelist string values (grep for `storeKeyToWriteWhitelist`/`WriteWhitelist` outside the `store/whitelist/*` package and its tests returned no results in the indexed codebase). Without visibility into the concrete whitelist strings used in production module wiring, I cannot fully confirm which module keys are prefix-vulnerable in practice, nor whether the whitelist strings used are always full key names (making prefix collision unlikely) or short/partial keys (making it likely). This is a genuine gap in what I could verify from the indexed code; a Devin session with full repo access would be needed to locate the production call sites and assess exploitability with concrete whitelist values.

### Recommendation
Change `validateKeyForWrite` to require an exact match or a properly delimited prefix (e.g., append a key separator/delimiter and compare `keyStr == whitelist || strings.HasPrefix(keyStr, whitelist+separator)`), rather than a bare `strings.HasPrefix` comparison, mirroring the Opencast fix of requiring full identity comparison rather than partial matching.

### Proof of Concept
Using the existing test harness pattern in `store/whitelist/kv/store_test.go`: whitelist only `"foo"` via `kv.NewStore(rawStore, []string{"foo"})`, then call `Set([]byte("foobar"), val)`. The call does not panic despite `"foobar"` never being explicitly whitelisted — demonstrating that any key sharing the `"foo"` prefix is treated as authorized for write, as shown by the assertion `require.NotPanics(t, func() { whitelistedStore.Set([]byte("foofoo"), []byte("val")) })` in the existing test file.

```go
func (store *Store) validateKeyForWrite(key []byte) {
	keyStr := string(key)
	for whitelist := range store.writeWhitelist {
		if strings.HasPrefix(keyStr, whitelist) {
			return
		}
	}
	// Panic since the Store interface does not return error on Set. Can be
	// intercepted by calling routine through `err := recover()`
	panic(fmt.Sprintf("Setting disallowed key %s in whitelisted KV store", keyStr))
}
```
