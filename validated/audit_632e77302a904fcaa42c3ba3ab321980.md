### Title
Forfeiture bypass on vesting MGP via same-block `cancelUnlock` before `multiclaimFor` resets `getRewardablePercentWAD` to 100% - ([File: VLMGP.sol / rewards/MasterMagpie.sol / rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder.queueMGP` computes the forfeiture on MGP emissions purely from the *live* value of `vlMGP.getRewardablePercentWAD(_account)` at claim time, not from the state that existed while the reward accrued. Because `VLMGP.cancelUnlock` clears `slot.amountInCoolDown` without checkpointing/harvesting pending rewards first, an unprivileged user can accrue `unClaimedMgp` while partially in cooldown (where the intended percent is < 100%), then call `cancelUnlock` immediately before claiming to make `getRewardablePercentWAD` read 100%, eliminating the forfeiture that governance intended.

### Finding Description
- `MasterMagpie._multiClaim` (`rewards/MasterMagpie.sol:536-566`) aggregates `_calNewMGP(_stakingToken, _user) + unClaimedMgp[_stakingToken][_user]` into `vlMGPPoolAmount` and forwards it via `_sendMGPForVlMGPPool` [1](#0-0)  to `IvlmgpPBaseRewarder(vlMGPRewarder).queueMGP(_amount, _account, _receiver)` [2](#0-1) .
- `queueMGP` (`onlyManager`, called by MasterMagpie which is a manager) computes the forfeiture strictly from the caller-supplied `_amount` and a **fresh, live** call to `_calExpireForfeit(_account, _amount)` [3](#0-2) .
- `_calExpireForfeit` reads `vlMGP.getRewardablePercentWAD(_account)` at the moment of the call, with no snapshot of the state at accrual time [4](#0-3) .
- `getRewardablePercentWAD` is a time-weighted formula intended to give a partial rewardable percent while tokens sit in cooldown (i.e., stakers who unlock forfeit a pro-rata amount of their pending MGP proportional to time already spent unlocking) [5](#0-4) .
- `cancelUnlock` simply zeroes `slot.amountInCoolDown` and decrements `totalAmountInCoolDown`, with **no call to harvest/checkpoint pending MGP** and no interaction with MasterMagpie's reward-debt accounting [6](#0-5) . Contrast this with `unlock()` and `startUnlock()`, which both explicitly call `multiclaimFor` *before* mutating cooldown state to force a checkpoint at the correct percent [7](#0-6) [8](#0-7) .

Exploit flow:
1. Attacker locks MGP, then calls `startUnlock` to move some amount into cooldown. This checkpoints their percent correctly at that moment (a lower, partial percent).
2. Over subsequent blocks, MGP emission continues to accrue into `unClaimedMgp[vlmgp][attacker]` via `updatePool`/`_calNewMGP`, while `getRewardablePercentWAD(attacker)` would legitimately return something less than 100% (they still have cooldown balance not yet expired, or expired-but-unclaimed forfeitable balance).
3. Instead of claiming now (which would trigger a partial forfeit via `queueMGP`), attacker calls `cancelUnlock(_slotIndex)`. This costs nothing, requires no waiting, and immediately zeroes `amountInCoolDown`, making `getUserTotalLocked` (and thus `getRewardablePercentWAD`) return 100% for the whole balance.
4. In the same transaction/block, attacker calls `multiclaimFor`/`multiclaim`. `_multiClaim` reads the now-100%-recalculated percent inside `queueMGP`'s `_calExpireForfeit`, so `forfeitAmount = 0` and the attacker receives the entirety of `vlMGPPoolAmount`, including MGP that accrued while their true, historical percent was below 100%.
5. The `nonReentrant` guards on `_multiClaim` and `queueMGP`, and the `onlyManager`/`onlyMasterMagpie` modifiers, do not stop this because the exploit does not require reentrancy or unauthorized calls — it is a pure state-manipulation-then-legitimate-call sequence available to any staker.

The root cause is that forfeiture accounting is not accrual-linked (no per-period checkpoint of rewardable percent tied to the reward that vested during that period); it is entirely determined by whatever state exists at the instant `queueMGP` executes, and `cancelUnlock` is the one state-transition function that fails to force a checkpoint before mutating that state.

### Impact Explanation
This is theft of unclaimed/vesting yield: MGP that governance intended to forfeit (and redistribute to other vlMGP stakers via `_queueNewRewardsWithoutTransfer` inside `queueMGP`) is instead captured entirely by the attacker [3](#0-2) . This directly reduces the forfeit pool that funds other stakers' rewards, violating the conservation invariant, and matches the Immunefi "theft of unclaimed yield" impact class.

### Likelihood Explanation
Requires no privileged role and no capital beyond having a normal vlMGP staking/cooldown position. The attacker only needs: (1) to hold vlMGP with an active cooldown slot, (2) let MGP emissions accrue, and (3) call `cancelUnlock` immediately before `multiclaimFor`/`multiclaim`, all of which are ordinary public/external functions. This is fully repeatable every time a user has an in-progress cooldown and pending emission, making it a low-cost, high-repeatability exploit.

### Recommendation
Checkpoint (harvest) the user's pending MGP reward under the *current* `getRewardablePercentWAD` state before any state mutation that changes that percentage. Specifically:
- In `VLMGP.cancelUnlock` (and the analogous `mWomSV.cancelUnlock`), call `IMasterMagpie(masterMagpie).multiclaimFor(...)` for `msg.sender` *before* zeroing `slot.amountInCoolDown`, mirroring the pattern already used in `startUnlock` and `unlock`.
- Alternatively, make `_calExpireForfeit` operate on a per-slot/time-weighted historical record rather than a single live snapshot, so forfeiture cannot be erased by a same-block state change.

### Proof of Concept
Foundry test plan:
1. Deploy MasterMagpie, VLMGP, vlMGPBaseRewarder, MGP token with test harness (or use existing test fixtures if present).
2. Setup: attacker locks 100 MGP; later calls `startUnlock(50)` to put half in cooldown; advance time to mid-cooldown so `getRewardablePercentWAD(attacker)` returns, e.g., ~75%.
3. Advance blocks/emit MGP rewards so `unClaimedMgp[vlmgp][attacker]` accrues a known `X` MGP while percent is ~75%.
4. **Scenario A (genuine cooldown state):** call `multiclaimFor` directly. Assert `queueMGP` forfeits ~25% of `X` (i.e., `MGPHarvested` event shows non-zero `forfeitAmount`), and attacker receives ~0.75*X.
5. **Scenario B (exploit):** from the same starting accrued state, call `cancelUnlock(slotIndex)` then immediately (same tx or same block) call `multiclaimFor`. Assert `getRewardablePercentWAD(attacker)` now returns 100%, `forfeitAmount == 0` in `MGPHarvested`, and attacker receives the full `X`.
6. Compare balances: Scenario B yields strictly more MGP to attacker than Scenario A for identical `unClaimedMgp[vlmgp][attacker]` starting balances, proving the forfeiture bypass and the resulting shortfall to the vlMGP rewarder's forfeit pool (`rewardInfo.rewardPerTokenStored` under-credited by the forfeited amount other stakers should have received).

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
