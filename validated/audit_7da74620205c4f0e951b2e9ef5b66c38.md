### Title
`rewards()` in distribution precompile is missing non-payable validation, permanently stranding attached native value - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` method of the distribution precompile (`0x0000000000000000000000000000000000001007`) is a view function that queries delegation rewards, but it is the only method in the precompile's dispatch table that does not enforce `ValidateNonPayable`. A caller can invoke `rewards(address)` with a non-zero `msg.value`, and the call succeeds instead of reverting, leaving the attached usei/wei value stuck at the precompile's associated account with no code path to reclaim it.

### Finding Description
`PrecompileExecutor.Execute` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` without passing `value` at all: `case RewardsMethod: return p.rewards(ctx, method, args)` [1](#0-0) . Every other transaction and query handler in this file is guarded — transactions check `readOnly` and non-payability inline (e.g. `WithdrawValidatorCommissionMethod` at lines 176-183), and every remaining query calls `p.validateInput(value, args, n)`, which internally invokes `pcommon.ValidateNonPayable(value)` before proceeding [3](#0-2) . Because `rewards()` skips this check entirely, an EVM call to it with `value > 0` is not rejected by the precompile logic itself.

At the EVM/state-transition level, when a precompile is called with value, the EVM's native value-transfer semantics move the wei/usei balance to the precompile's associated account before/while the precompile logic executes (this is why every other payable-but-should-be-non-payable path must explicitly call `ValidateNonPayable` and revert, or otherwise route the payment through `HandlePaymentUseiWei`/`HandlePaymentUsei` to refund/redirect it, as seen in `sendNative` in the bank precompile [6](#0-5)  and in `HandlePaymentUseiWei` itself [7](#0-6) ). Since `rewards()` neither rejects the payment nor refunds it via `HandlePaymentUseiWei`/`HandlePaymentUsei`, any value sent along with the call is absorbed by the precompile's account and is not returned to the caller, nor is there a withdraw/sweep function on the distribution precompile to recover it later.

This matches the reported bug class: a contract (here, a stateful precompile account) can receive/accept native value through a code path that lacks payability validation, and there exists no corresponding withdrawal mechanism, so the funds become permanently stuck. The test suite's own commentary confirms this is a recognized quirk: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" [8](#0-7) .

### Impact Explanation
Any unprivileged EVM caller (a normal transaction sender or a smart contract) can send native SEI/usei/wei value with a call to `rewards(address)` on the distribution precompile. That value is not refunded, not credited to any account's queryable/spendable balance, and there is no owner/withdraw function on the precompile to sweep it out. This results in permanent freezing of user funds — direct, irrecoverable fund loss for any caller who mistakenly (or is tricked, e.g. via a wrapping/proxy contract that forwards `msg.value`) attaches value to this call. This satisfies "permanent freezing of funds," a Medium-severity criterion.

### Likelihood Explanation
Likelihood is moderate: the `rewards` ABI function is declared as a query/view intended to be called without value, so most direct callers using the standard `IDistr` interface would call it without `msg.value`. However, wallets, multicall wrappers, or contracts that route arbitrary calldata with a nonzero `value` field (or that use a generic "payable call" pattern for all precompile invocations) can trigger this. Because it requires no special privilege, permission, or unusual conditions — just an ordinary EVM call with `value != 0` — this is trivially reachable by any transaction sender.

### Recommendation
Add a non-payable check to the `rewards` method, consistent with all other view methods in the precompile:
```go
case RewardsMethod:
    if err = pcommon.ValidateNonPayable(value); err != nil {
        return nil, 0, err
    }
    return p.rewards(ctx, method, args)
```
or thread `value` into `p.rewards` and call `pcommon.ValidateNonPayable(value)` at its start, mirroring the pattern used in `validatorOutstandingRewards`, `delegationRewards`, etc. [9](#0-8) .

### Proof of Concept
1. Deploy/use any EVM account with an associated Sei address.
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and set `msg.value` to a non-zero amount (e.g., 1 SEI).
3. Observe the call succeeds (returns delegation rewards data) rather than reverting with "sending funds to a non-payable function," as all sibling view methods would produce via `pcommon.ValidateNonPayable` [10](#0-9) .
4. Query the caller's EVM balance before/after — the attached value is deducted and not returned; there is no subsequent method on the distribution precompile that can retrieve or transfer this stranded balance back out.

	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))

		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
