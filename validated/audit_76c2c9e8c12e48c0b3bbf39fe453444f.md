### Title
Untrusted `ReceivedOutput::read` input can represent an unspendable deposit - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the claimed key offset, output, and outpoint without verifying that the output’s `script_pubkey` is actually controlled by the scanner key after applying the claimed offset. This lets attacker-supplied bytes construct a `ReceivedOutput` describing funds the wallet cannot spend.

### Finding Description
`ReceivedOutput` is documented as a spendable output, and its fields are private, so normally only `Scanner::scan_transaction` can create one. `scan_transaction` enforces ownership by looking up `output.script_pubkey` in `self.scripts` and associating it with the registered offset.

The public `ReceivedOutput::read` path bypasses that invariant. It only calls `Secp256k1::read_F` for the offset and consensus-decodes a `TxOut` and `OutPoint`. It never checks that:

```rust
p2tr_script_buf(scanner_key + (ProjectivePoint::GENERATOR * offset))
    == Some(output.script_pubkey.clone())
```

It also accepts an arbitrary `OutPoint`, which is not cryptographically bound to the decoded `TxOut`.

Later, `SignableTransaction::multisig` does perform the correct consistency check by deriving the spend key with `self.offsets[i]` and comparing its P2TR script to `self.prevouts[i].script_pubkey`. If the deserialized association was false, it returns `None`. Thus the object can report a received output even though no valid signing machine can be created for it.

### Impact Explanation
An attacker who can cause an application to import attacker-controlled `ReceivedOutput` bytes can make the wallet report a deposit that is not spendable. Depending on accounting logic, this may inflate displayed or tracked balances, cause the application to select phantom UTXOs, or make transaction construction fail after the deposit has already been accepted as received.

This maps to the reported class because a function/interface that establishes an object’s security invariant accepts only the serialized fields while omitting the authorization-equivalent check: the binding between the key offset and the output script.

### Likelihood Explanation
The condition is directly reachable through the public `ReceivedOutput::read` API with arbitrary bytes. No private key, validator privilege, threshold collusion, malformed curve implementation, or Bitcoin consensus violation is required.

The impact requires the calling application to treat deserialized `ReceivedOutput` values as trusted wallet state or to expose an import path to less-trusted input. The cryptographic failure is prevented later during `multisig`, but only after the invalid received output has already been accepted.

### Recommendation
Add a validity check tying the `ReceivedOutput` to the scanner key before accepting deserialized data.

Possible approaches:

1. Require `ReceivedOutput::read` to take the scanner public key and reject bytes unless the decoded offset derives the decoded output’s `script_pubkey`.
2. Add a separate `ReceivedOutput::verify_for_key(scanner_key)` API and require callers to invoke it after deserialization.
3. Prefer serializing the scanner key alongside the output, or persisting only authenticated scanner-generated `ReceivedOutput` values.
4. Continue enforcing the existing `SignableTransaction::multisig` script check, but do not rely on it as the first ownership validation point.

### Proof of Concept
Conceptually, construct byte input containing:

1. A canonical secp256k1 scalar, such as zero, for `offset`.
2. A consensus-encoded `TxOut` whose `script_pubkey` is any valid P2TR script not equal to `p2tr_script_buf(scanner_key + G * offset)`.
3. Any consensus-encoded `OutPoint`, including one referencing an unrelated or nonexistent transaction output.

Feeding those bytes to `ReceivedOutput::read` succeeds because it only parses the three fields. The resulting `ReceivedOutput` is returned as a spendable output despite its script not being controlled by the wallet key under the claimed offset.

When passed into `SignableTransaction::new` and then `SignableTransaction::multisig`, the code calculates:

```rust
let offset = keys.clone().offset(self.offsets[i]);
if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
    None?;
}
```

The comparison fails and `multisig` returns `None`, proving the previously accepted “received” funds cannot be spent.
