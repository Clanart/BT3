### Title
Cached FROST nonce seed persisted before signing and never cleared on failure, enabling deterministic nonce reuse across retried share rounds - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The external report describes cleanup code operating on fields of an object whose initialization failed partway. The structural analog in Serai is `SigningProtocol::preprocess_internal`: the deterministic preprocess seed is written to `CachedPreprocesses` *before* the signing round has succeeded, and the code contains no path that deletes it after failure or after use. Any re-execution of `share_internal`/`complete` for the same `context` reloads the identical seed, regenerates identical FROST nonces via `ChaCha20Rng::from_seed`, and signs again — mirroring "stale half-built state reused by a later code path", with the consequence here being nonce reuse rather than a refcount underflow.

### Finding Description
- `preprocess_internal` writes `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` keyed only by `self.context` (e.g. `(b"DkgConfirmer", attempt)`), then unconditionally reconstructs the machine from that cache via `AlgorithmSignMachine::from_cache` (lines 123–145).
- `from_cache` → `seeded_preprocess` derives `nonces` deterministically from `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:127–141). Same seed ⇒ same nonces `(d, e)` ⇒ same published commitments.
- `share_internal` re-runs `preprocess_internal` then `machine.sign(preprocesses, msg)` where `preprocesses` is built from attacker-supplied bytes via `read_preprocess` (lines 155–168). `Commitments::read`/the addendum reader can reject untrusted bytes, returning `Err(FrostError::InvalidPreprocess(p))` — after the seed was already persisted.
- `DkgConfirmer::complete` invokes `share_internal` a *second* time for the same context (lines 321–324), and `share` is independently callable whenever the coordinator handles the relevant tributary event. `CachedPreprocesses` has `get`/`set` only — a grep of the crate shows no `del`/removal anywhere.
- Because `threshold_i_map_to_keys_and_musig_i_map` re-indexes participants according to which threshold signers appear in the `preprocesses` map (lines 213–249), two invocations carrying different signer subsets produce different `included` sets and different per-participant binding factors `rho` in `sign()` — while our nonces stay identical. The result is two Schnorr signature shares `s = d + e·ρ_i + λ_i·c_i·share` over the same nonce with different `(ρ, c, λ)`. If the effective challenge/binding pair differs, the secret share is linearly recoverable.

### Impact Explanation
Reuse of a FROST nonce across two distinct signing sessions is the canonical key-share-recovery condition, explicitly acknowledged by the code itself ("it is explicitly unsafe to reuse nonces across signing sessions", lines 25–35) and by `CachedPreprocess` docs ("Reuse will enable third-party recovery of your private key share", crypto/frost/src/sign.rs:85–87). Here the reused key is the validator's MuSig substrate key — recovery of it compromises the validator's root-of-trust key used to confirm DKG results on-chain.

### Likelihood Explanation
The safety argument in the file rests entirely on BFT ordering guaranteeing identical inputs. It does not account for: (a) an invalid preprocess aborting `sign` after the seed is persisted, then a retried round with a *different valid* participant subset (the map keys control MuSig indices, so distinct subsets are trivially constructible by an unprivileged counterparty's messages); (b) `complete` re-signing after `share` already produced a share, with no check that the preprocess set is identical; (c) partial rebuilds, which the comments admit are "a bound preventing partial rebuilds which is accepted". Each of these is reachable from public protocol messages (preprocess bytes fed to `read_preprocess`) without colluding-threshold assumptions. The residual uncertainty is whether the coordinator's event handling ever actually invokes `share`/`complete` twice for one context with divergent inputs — that dispatch is in `coordinator/src/tributary/handle.rs`, outside the cryptographic evidence, but the persistent-seed primitive makes any such repeat fatal.

### Recommendation
- Delete `CachedPreprocesses[context]` when the share is successfully produced, and/or record a "share already published for this context + preprocess-set hash" marker so a second `sign` under the same seed can never emit a share over different inputs.
- Bind the cached seed entry to the hash of the exact `preprocesses` map and `msg`; refuse to sign if a later call presents different bytes, matching the TODO at line 51 ("check the commitments generated from the decided nonces are in fact its commitments on-chain").
- On `InvalidPreprocess`, keep the aborted attempt distinguished so a retry uses a fresh seed rather than deterministically replaying the failed one.

### Proof of Concept
Conceptual, against the in-scope libraries:
1. Validator's coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair)`. `preprocess_internal` stores seed `s` under `("DkgConfirmer", attempt)`; nonces `d, e = ChaCha20Rng(s)` are fixed.
2. First call: include preprocesses from signer set `S1` (threshold_i → musig_i mapping via `threshold_i_map_to_keys_and_musig_i_map`). `sign()` emits share `σ1 = d + e·ρ1 + λ1·c1·share`, which is broadcast.
3. Trigger a second signing pass for the same context — either via `DkgConfirmer::complete(preprocesses_B, …)` where `preprocesses_B` covers a different signer subset `S2`, or via a retried `share` after a first attempt aborted on a deliberately malformed preprocess (the seed persists either way, since nothing deletes the cache).
4. Second pass reloads `s`, producing the same `d, e` but binding factor `ρ2` and challenge `c2` over a different aggregate `R`. The emitted share `σ2 = d + e·ρ2 + λ2·c2·share` differs.
5. From `(σ1, σ2, ρ1, ρ2, c1, c2, λ1, λ2)` — all public except `d, e, share` — solve the 2×2 linear system. Even partial knowledge (e.g., equality of commitments proves `d, e` identical) lets an attacker extract the validator's secret share, defeating the threshold.
