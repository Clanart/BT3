## Analog Found: Missing SHA-pinning when checking out a pull request allows silent branch-swap by the PR author (Desktop analog of "no expiration deadline")

The Beedle bug's broken invariant is: *the code trusts a value ("current price"/`block.timestamp`) that can change between when the user decided to act and when the action executes, with no check that the value used at execution time matches what was intended.* The equivalent invariant in GitHub Desktop is: *Desktop fetches and displays a pull request's `head.sha` from the GitHub API, but when the user later clicks "checkout", it resolves and checks out the branch **by name**, never verifying the SHA still matches what was reviewed/fetched.*

### Title
Missing head-SHA verification when checking out a pull request allows a malicious fork owner to swap the checked-out content between PR display and checkout - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop stores each pull request's head SHA (`IPullRequestRef.sha` / `PullRequestRef.sha`) when it syncs PRs from the API [1](#0-0) , and uses that SHA to compute diffs, commit counts, and PR status shown to the user [2](#0-1) . However, when the user actually initiates a checkout, `_checkoutPullRequest`/`_findPullRequestBranch` only take `headRepoOwner`, `headCloneUrl`, and `headRefName` — the SHA is never passed in or checked against what gets fetched and checked out [3](#0-2) . The branch resolution logic fetches the remote by name and checks out whatever is currently at the tip of that ref [4](#0-3) , with no comparison to the previously observed/displayed `pullRequest.head.sha`.

### Finding Description
`Dispatcher.checkoutPullRequest` and the deep-link handler `openPullRequestFromUrl` both call `_checkoutPullRequest(repository, prNumber, headRepoOwner, headCloneUrl, headRefName)` [5](#0-4) [6](#0-5) . Inside `_findPullRequestBranch`, Desktop adds (or reuses) a remote pointing at the fork's `headCloneUrl`, fetches it if the ref isn't already known locally, and returns whatever branch/ref currently exists at `remote/headRefName` [7](#0-6) . At no point is the fetched ref's SHA compared to the `head.sha` that was recorded when the PR was listed/reviewed (e.g. in the "Open Pull Request" diff view, PR list, or notification banners like `pull-request-review.tsx` / `pull-request-comment.tsx` which trigger the exact same `checkoutPullRequest` call after a user reviews a PR [8](#0-7) [9](#0-8) ).

Because the head repository of a PR is attacker-controlled (any fork owner can force-push to their own branch at any time), the fork owner can:
1. Open a benign-looking PR and let Desktop cache/display its `head.sha` and diff.
2. Wait for the victim to click "checkout" (from the PR list, a deep link, or a review/comment notification).
3. Force-push new, malicious commits to the same branch name just before/at the moment of checkout.

Desktop performs no deadline/anchor check — it will fetch and check out whatever is live on that ref at that moment, not the SHA the user actually reviewed. This is the direct structural analog to the reported bug: no "expiration" on the trusted value (the reviewed SHA), so an attacker who controls timing (here, force-push timing on their own fork instead of miner/validator block ordering) can substitute different content than what the victim believed they were accepting.

### Impact Explanation
A successful attack silently replaces the working directory contents with commits the user never reviewed, right at the moment they choose to inspect/build/run a PR — this is the "silent corruption of what the user commits/pushes/checks out" category. Combined with the fact that checkout also runs `git submodule update --init --recursive` on the (now attacker-controlled) submodule URLs from the checked out tree [10](#0-9) , this can escalate to fetching from arbitrary attacker-chosen submodule remotes, or delivering a payload the victim opens in an editor/IDE task runner, achieving code execution outside of any explicit "clone untrusted code" warning the user might have otherwise heeded.

### Likelihood Explanation
No special access is required — any GitHub user can open a PR from their own fork and force-push at will. The victim only needs to perform an action Desktop actively invites: clicking "Checkout" from the PR list, a deep link (`x-github-client://openRepo/...?pr=N`), or one of the PR notification banners. There is no user-facing warning that the branch content might differ from what was last reviewed, and no re-diff/re-confirmation step comparing the newly fetched SHA to the previously displayed one.

### Recommendation
Before performing the checkout in `_checkoutPullRequest`/`_findPullRequestBranch`, compare the resolved branch tip SHA against the `pullRequest.head.sha` value the caller last observed (surfacing a warning/confirmation if they differ, similar to how force-push/rewritten-history warnings are handled elsewhere). At minimum, re-fetch and re-verify the SHA immediately prior to checkout, and refuse (or explicitly warn) if it doesn't match the SHA associated with the PR state the user is acting on.

### Proof of Concept
1. Attacker forks a repository and opens PR #1 from branch `feature` with an innocuous commit; Desktop syncs and caches `head.sha = A`.
2. Victim reviews PR #1 in Desktop (diff for SHA `A` looks safe) and clicks "Checkout" or receives a "review submitted" notification and clicks "Switch to branch" [8](#0-7) .
3. Milliseconds before Desktop's fetch/checkout completes, attacker force-pushes malicious commit `B` (e.g., adding a malicious `.vscode/tasks.json`, `Makefile`, submodule pointing to a malicious host, or build script) to `feature`.
4. `_findPullRequestBranch` fetches the remote, finds `origin-fork/feature` now at `B`, and checks it out via `_createBranch(... , remoteRef, ...)` [11](#0-10)  — with no check that `B == A`. The victim's working directory now silently contains attacker-chosen code they never reviewed.

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
