### Title
Unhandled `IndexError` in `is_clvm_canonical`/`is_atom_canonical` can crash spend-bundle validation on a truncated atom length-prefix - (File: `chia/full_node/mempool_manager.py`)

### Summary
`chia/full_node/mempool_manager.py::is_atom_canonical` and `is_clvm_canonical` index into a `bytes` buffer using an `offset` that is advanced based on an attacker-controlled length-prefix byte, without ever checking that `offset` stays within `len(clvm_buffer)`.

### Finding Description
`is_atom_canonical` reads the leading byte `b = clvm_buffer[offset]` and, depending on its high bits, decides how many additional prefix bytes (`prefix_len`, up to 5) to consume, then loops `for i in range(prefix_len): ... atom_len |= clvm_buffer[offset]` [1](#0-0) . Neither this loop nor the caller `is_clvm_canonical` bound-checks `offset` against `len(clvm_buffer)` before indexing, and `is_clvm_canonical`'s main loop likewise does `b = clvm_buffer[offset]` on every iteration with no length guard, relying only on an `assert clvm_buffer != b""` at the top [2](#0-1) . A buffer that starts a long length-prefix atom (e.g. bytes `0xF8`/`0xFC`, which claim a 4–5 byte length prefix) but is truncated before providing all the prefix bytes causes `clvm_buffer[offset]` to run past the end of the byte string, raising `IndexError`.

This function is invoked, per coin spend, directly on attacker-supplied bytes inside `MempoolManager.validate_spend_bundle`: `if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(bytes(coin_spend.solution))` [3](#0-2) . This runs synchronously in `add_spend_bundle` → `validate_spend_bundle`, on the main asyncio event-loop thread (unlike the CLVM-cost/signature validation, which runs in a worker pool via `pre_validate_spendbundle`) [4](#0-3) . Crucially, this canonical check runs *after* `pre_validate_spendbundle` has already called the Rust `validate_clvm_and_signature`, which successfully parses/executes the puzzle/solution CLVM and returns `SpendBundleConditions` — the Rust CLVM deserializer tolerates non-canonical/garbage-suffixed atom encodings that this Python-side canonical checker is specifically designed to reject for dedup-eligibility purposes. That means a spend bundle can pass CLVM/cost/signature validation yet still contain a byte sequence in `puzzle_reveal` or `solution` whose length-prefix byte claims more prefix bytes than remain in the buffer, triggering this unhandled `IndexError` in `is_clvm_canonical`.

### Impact Explanation
Whether this crashes the whole node (an availability-affecting DoS analogous to the reported alos-http bug) depends on how deep in the call stack `validate_spend_bundle`/`add_spend_bundle` sits and whether any caller wraps it in a broad `except Exception`. I was not able to fully confirm the exact call path from the peer/RPC message handler (e.g. `respond_transaction`/`send_transaction` RPC) down into `add_spend_bundle`, nor whether an uncaught `IndexError` there is swallowed by a top-level `try/except` somewhere in the full-node message-handling loop. If it is not caught, this is a single-spend-bundle-submission unauthenticated remote DoS, matching the reported bug class (index-out-of-range panic on truncated/malformed length-prefixed data path, reachable before/outside normal error handling). If it is caught by a broad handler, the practical impact is degraded to a per-spend-bundle rejection/log-noise issue rather than a full crash, in which case this would not meet the "Medium/High/Critical, spend-triggered halt" bar the validation criteria require.

### Likelihood Explanation
Constructing a malformed `puzzle_reveal` or `solution` blob that (a) is accepted by the Rust CLVM parser/cost-metering as valid, executable CLVM, and (b) simultaneously contains a truncated long-form atom length prefix that is only reached during the *Python* canonical scan (which walks the raw bytes independently of program structure) requires careful crafting, but is plausible: CLVM atoms not on the "hot" execution path (e.g. an unused/quoted trailing atom, or one nested where the interpreter doesn't traverse in the same order as the canonical scanner) could still be truncated relative to declared length while the executed part of the program is well-formed. This needs concrete confirmation (I could not fully verify from static reading whether such a buffer is actually producible, since the interaction between the Rust CLVM parser's own bounds-checking and this Python re-scan is not fully covered by the available context/tests I found, e.g. `test_mempool_requires_canonical_clvm` in `chia/_tests/core/mempool/test_mempool_manager.py`, exercises non-canonical-but-well-formed cases, not truncated/OOB ones).

### Recommendation
Add explicit bounds checks in both `is_atom_canonical` and `is_clvm_canonical` before every indexing operation (checking `offset < len(clvm_buffer)` and `offset + prefix_len < len(clvm_buffer)` before the prefix-consuming loop), returning `False`/raising a well-defined `ValidationError` instead of allowing a raw `IndexError` to propagate. As defense in depth, wrap the call site in `validate_spend_bundle` (or higher up in whatever calls `add_spend_bundle` for a freshly-received spend bundle) so any unexpected exception from CLVM-buffer inspection is converted into `Err.INVALID_COIN_SOLUTION` rather than propagating out of the coroutine.

### Proof of Concept
Not independently confirmed end-to-end (would require constructing a `puzzle_reveal`/`solution` blob that passes `validate_clvm_and_signature` but truncates before a declared long-form atom length prefix, e.g. ending right after a lone `0xF8` byte with no following length bytes, and submitting it as a `SpendBundle` through the normal mempool-add path). Given the reasoning above I cannot fully certify reachability of the uncaught crash without executing the code, so I flag this analog with **medium confidence** rather than asserting it as a proven high-severity finding.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len
