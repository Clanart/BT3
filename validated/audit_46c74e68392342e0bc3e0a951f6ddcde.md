Based on the investigation, the strongest local analog to the front-runnable/collision-based identity check in the reported `registerFunctionSelector` bug is the **module-identity authentication fallback** in Hyperbridge's `IntentGatewayV2` / `IntentsBase` contracts, where an unregistered remote-chain binding silently defaults to trusting the contract's *own* address as the counterparty.

### Title
Unregistered-Chain Fallback in `instance()`/`_instance()` Lets a Same-Address Contract on Any Non-Configured Chain Pass Module Authentication - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s `authenticate()`/`_authenticate()` function is supposed to bind incoming Hyperbridge `PostRequest`s to a known, admin-registered `IntentGateway` deployment on the request's source chain. However, when no instance has been registered for a given `stateMachineId`, the lookup silently falls back to `address(this)` instead of rejecting the message, which weakens the module-binding invariant that request/response paths are required to enforce.

### Finding Description
`instance()` resolves the trusted counterparty address for a source chain: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
```

The same pattern (`_instance`/`_authenticate`) exists in the shared base used by the primary EVM deployment: [2](#0-1) 

When `_instances[keccak256(stateMachineId)]` is unset (the default `address(0)`, i.e., the admin has never explicitly registered a gateway instance for that particular chain), `instance()`/`_instance()` returns `address(this)` — the local contract's own address — instead of failing closed. `authenticate()` then treats any incoming request whose `from` field equals `address(this)` as legitimate, for *any* source chain that has not been explicitly configured.

This mirrors the core defect pattern from the report: an identity/selector check that is supposed to bind a specific, admin-approved counterparty instead accepts a value that an attacker can realistically reproduce (there, a 4-byte selector collision; here, matching `address(this)` on an unconfigured chain). Since EVM contract addresses are derivable ahead of time via `CREATE2` or deterministic deployer nonces, an attacker can:
1. Identify a Hyperbridge-supported state machine (chain) for which the target `IntentGatewayV2` instance is not yet in `_instances` (new chains, or any chain governance hasn't gotten around to registering — this list only grows via the privileged `NewDeployment` flow).
2. Deploy an arbitrary malicious contract on that source chain at the exact same address as the victim `IntentGatewayV2` proxy/contract on the destination chain (trivial with `CREATE2` and a chosen salt, since the attacker fully controls that contract's bytecode/deployer).
3. Dispatch a crafted `PostRequest` from that malicious contract through Hyperbridge, with `to` = the real `IntentGatewayV2` and `body` decoding to a privileged `RequestKind` such as `RedeemEscrow`, `NewDeployment`, `UpdateParams`, or `SweepDust`.
4. Because `request.source` is a chain nobody registered an instance for, `instance(request.source)` returns `address(this)`, which equals `request.from` (the attacker's contract address) — `authenticate()` passes.

No relayer, prover, or admin compromise is required; the attacker only needs to control a contract deployment on any chain Hyperbridge is willing to relay proofs from, using standard `CREATE2` address matching.

### Impact Explanation
A successful forged authentication lets an unprivileged attacker invoke privileged `RequestKind` handlers (`RedeemEscrow`, `RefundEscrow`, `SweepDust`, `NewDeployment`, `UpdateParams`) as if they came from a trusted sibling `IntentGateway`. Depending on which handler is reachable this way, this can directly cause unauthorized release of escrowed order funds to an attacker-chosen beneficiary, forged registration of a malicious gateway "instance" address for a chain (poisoning future `authenticate()` checks permanently), or unauthorized parameter/fee changes — all classic "unauthorized execution" / "wrong beneficiary" / "loss of funds" impacts.

### Likelihood Explanation
Likelihood depends on whether Hyperbridge's live coprocessor accepts and relays valid state/consensus proofs from chains for which the `IntentGatewayV2` instance mapping hasn't yet been populated (e.g., newly supported chains, or chains supported at the protocol level but not yet onboarded at the application level by governance). Given that instance registration is a separate governance/admin action (`NewDeployment`) from chain-level ISMP support, such a gap is plausible during rollout, and `CREATE2` address-matching across EVM chains is a well-established, no-privilege technique.

### Recommendation
Fail closed instead of falling back to `address(this)`: if `_instances[keccak256(stateMachineId)] == address(0)`, `authenticate()`/`_authenticate()` should revert (e.g., `UnknownSourceChain`) rather than treat the local contract's own address as an implicitly trusted peer. Only the chain the contract is deployed on (verified via `request.source == host chain` combined with an explicit "self" allowance) should ever be allowed to short-circuit to `address(this)`, and that should be an explicit branch, not a default returned for every unmapped chain.

### Proof of Concept
Not independently executed against a live deployment; the code-level trace above (from `instance()`/`authenticate()` in `IntentGatewayV2.sol` and the mirrored `_instance()`/`_authenticate()` in `IntentsBase.sol`/`ExtrinsicIntents.sol`) demonstrates the exact corrupted value (`instance(request.source)` defaulting to `address(this)`) and the exact guard it bypasses (`authenticate()`'s equality check). Full exploitation would require confirming, at the specific commit/deployment, which chains currently lack a registered `_instances` entry and which `RequestKind` handlers are reachable purely via `onAccept` → `authenticate()` without additional gating — this could not be fully confirmed from the indexed code alone due to `onAccept`'s dispatch body not being fully retrieved in this session.
