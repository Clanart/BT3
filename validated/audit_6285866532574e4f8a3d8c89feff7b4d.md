### Title
Unrecoverable panic (DoS) in PedPoP blame evaluation on out-of-range participant index - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The sqlite3 advisory is a bug class where passing an invalid/unchecked parameter to a binding API causes a fatal, uncatchable crash instead of a recoverable error. The analog in Serai lives in the PedPoP blame path: `BlameMachine::blame_internal` and `AdditionalBlameMachine::blame` index `self.commitments` with a caller-supplied `Participant` via `HashMap`'s `Index` impl, which panics if the key is absent. A `Participant` is only validated as non-zero (`Participant::new`), so an index `> n` — or any participant whose commitments were never registered — causes an unconditional panic rather than a `PedPoPError`, crashing the calling process during dispute resolution.

### Finding Description
`blame_internal` computes the share-verification statements with `&self.commitments[&sender]` [1](#0-0) . `HashMap`'s `Index` implementation panics on a missing key, and there is no validation that `sender` (or `recipient`) is within `1 ..= n` or present in the commitments map before this lookup. `Participant` construction only rejects zero [2](#0-1) , so `sender = Participant(n + 1)` reaches the indexing panic.

The same unchecked index appears in `KeyMachine::calculate_share`, where `self.commitments[&l]` is indexed by share-map keys [3](#0-2)  — that one is protected by `validate_map` checking the share map against `all_participant_indexes` [4](#0-3) , but no equivalent guard exists in the blame path. The crate itself acknowledges that improper inputs here "may cause everything from inaccurate blame to panics" [5](#0-4) , yet `blame()` accepts attacker-attributable indices with no documented precondition that `sender`/`recipient ∈ 1..=n`.

The panic is triggered exactly in the adversarial scenario the function exists for: resolving an accusation that a named participant misbehaved. An accusation naming an out-of-set or unregistered "sender" — e.g. forwarded from a malicious counterparty claiming `Participant(0xFFFF)` sent them a bad share — aborts the process instead of returning `sender`/`recipient` blame.

### Impact Explanation
An unprivileged party who can cause a node to evaluate a blame claim (by submitting or relaying an accusation naming an arbitrary `Participant` index) can crash the victim's DKG/blame-resolution process. This is a remote, unauthenticated-originating denial of service hitting an infallible-looking code path (`blame` returns `(AdditionalBlameMachine, Participant)`, not `Result`), so callers have no way to catch it short of `catch_unwind`. It matches the advisory's class: malformed input to a public API produces a fatal error that cannot be caught through the API's error channel.

### Likelihood Explanation
Blame evaluation is initiated per accusation received from other participants; anything triggering `blame`/`blame_internal` with a `sender` not in `commitments` panics deterministically — no probabilistic condition required. The only mitigating factor is that the caller must be induced to call `blame` with an out-of-range index, but since accusations are themselves attacker-originated protocol messages, this is a realistic reachability path in any integrator that maps a wire "accused participant" field to `Participant` and calls `blame`.

### Recommendation
Validate `sender` and `recipient` against the registered participants before indexing: return `sender` (or a dedicated `PedPoPError`) when `self.commitments.get(&sender)` / `.get(&recipient)` is `None` instead of using `HashMap::index`. Concretely, replace `&self.commitments[&sender]` at crypto/dkg/pedpop/src/lib.rs:599 with a `get` + early-return, and apply the same check to any `recipient` indexing in `decrypt_with_proof`. Document on `BlameMachine::blame` / `AdditionalBlameMachine::blame` that arbitrary indices are handled without panic, and add a regression test feeding `Participant::new(n + 1)` as `sender`.

```rust
// A well-formed EncryptedMessage from some real participant i
let msg: EncryptedMessage<Ed25519, SecretShare<_>> = /* any registered share msg */;

// Panics inside blame_internal at `self.commitments[&sender]`:
// HashMap Index -> "no entry found for key" -> abort/panic, not a PedPoPError
let (_additional, _faulty) = blame_machine.blame(attacker_index, recipient_i, msg, None);
```
