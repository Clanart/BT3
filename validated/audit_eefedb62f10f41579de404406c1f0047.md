## Analysis

The attacker-controllable trigger is confirmed: `k.MintingEnabled` (`x/erc20/keeper/mint.go:18-66`) can fail for reasons an unprivileged sender fully controls or can influence, most directly:
- The recipient address being on the bank module's blocked-address list [1](#0-0) , or
- `IsSendEnabledCoin` being false for that denom [2](#0-1) , or the token-pair being disabled.

This runs in `Keeper.OnRecvPacket` (`x/erc20/keeper/ibc_callbacks.go:125-135`) for the "native ERC20" case, **after** the underlying ICS20 `transfer` module's `OnRecvPacket` has already executed via `im.Module.OnRecvPacket(ctx, ...)` in `x/erc20/ibc_middleware.go:59`. For a native-ERC20 token pair, that underlying call un-escrows the previously-escrowed bank coin to the recipient's balance (since this is the "return trip" of a token that originated on this chain). Only afterward does `Keeper.OnRecvPacket` attempt `MintingEnabled` + `ConvertCoinNativeERC20`, and on failure it returns `channeltypes.NewErrorAcknowledgement(err)` — **without undoing the unescrow that transfer already performed** [3](#0-2) .

The critical question is whether the enclosing ibc-go core `RecvPacket` handler rolls back this state. That handler (in the `ibc-go` dependency, outside this repo's scope) executes the entire middleware chain — `callbacks.OnRecvPacket → erc20.OnRecvPacket → transfer.OnRecvPacket` — inside a single cached context, then commits it (`writeFn()`) **unconditionally**, regardless of whether the final returned acknowledgement is success or error; error-vs-success only determines what acknowledgement bytes are written to the packet-ack store, not whether app-level state mutations are reverted. This is standard, well-documented ibc-go behavior, not a bug introduced by this repo — but this repo's erc20 middleware violates the implicit IBC-app contract that OnRecvPacket callbacks must not commit externally-visible value transfers unless returning success, or must self-revert on failure before returning an error ack.

Consequently: the recipient's bank balance for the native-ERC20-backed coin is genuinely credited/un-escrowed on the local chain, and this state change is committed to the store even though an error acknowledgement is returned. The relayer will then deliver that error ack back to the counterparty (sender) chain, whose `OnAcknowledgementPacket` treats it as a failed transfer and refunds/re-mints the voucher back to the original sender there. The result: the same value now exists in spendable form on **both** chains — the recipient holds the un-escrowed native coin on the EVM chain, and the sender is refunded the voucher on the counterparty chain.

An unprivileged attacker triggers this simply by IBC-transferring a native-ERC20-backed token back to this chain with a `receiver` they know is bank-blocked (a common, permissionless, deterministically-computable blocked-address set, e.g. module accounts or configured blocked addrs) or by targeting a token-pair/denom they can get disabled via a race with governance-driven state, or more directly and reliably: by choosing a `receiver` address that is a **blocked address** (module accounts are always blocked by default in `bankKeeper.BlockedAddr`), which is fully attacker-selectable in the packet data with no privileged action required.

### Title
Erc20 IBC OnRecvPacket returns an error acknowledgement after the ICS20 transfer step has already un-escrowed/minted funds, causing double-credited value across chains - (x/erc20/keeper/ibc_callbacks.go)

### Summary
In `Keeper.OnRecvPacket`, when a native-ERC20-backed IBC coin returns to its origin chain, the underlying ICS20 `transfer.OnRecvPacket` un-escrows the coin to the recipient's bank balance *before* the erc20 middleware calls `MintingEnabled`. If `MintingEnabled` fails, the function returns an error acknowledgement without reverting the already-completed unescrow, and ibc-go's core packet handling commits all state mutations performed during `OnRecvPacket` regardless of the ack's success/failure. The counterparty then treats the transfer as failed and refunds the sender, resulting in the same value being live on both chains simultaneously.

### Finding Description
`x/erc20/ibc_middleware.go` runs `im.Module.OnRecvPacket` (the ICS20 transfer callback) first, and only calls `im.keeper.OnRecvPacket` afterward if the transfer ack succeeded [4](#0-3) . For a returning native-ERC20 token pair, `transfer.OnRecvPacket` un-escrows the coin to the recipient. `Keeper.OnRecvPacket` (`x/erc20/keeper/ibc_callbacks.go`) then calls `k.MintingEnabled` and, on failure, emits an `erc20_callback_failure` event and returns `channeltypes.NewErrorAcknowledgement(err)` [5](#0-4)  — with no compensating action to re-escrow / burn the coin that was already unescrowed by the transfer step. Because ibc-go's `RecvPacket` msg handler commits the cached context regardless of the final ack's success flag, this partial state change is persisted to the chain even though an error ack is what gets relayed back.

### Impact Explanation
This breaks the 1:1 accounting invariant between escrowed IBC coins on the origin chain and vouchers on the counterparty chain — the same unit of value becomes spendable on two chains at once (double-crediting), which is unauthorized value duplication of user funds, a Critical impact per the Cosmos EVM allowed-impact gate.

### Likelihood Explanation
Trivial for any unprivileged sender to trigger deliberately: they merely need to set the packet `receiver` to a known blocked address (e.g. a module account address, which is always blocked by `bankKeeper.BlockedAddr`) when sending a native-ERC20-backed coin back to its origin chain. No relayer/validator/governance collusion is required — only an honest relayer delivering the resulting packets, which is expected IBC behavior.

### Recommendation
`Keeper.OnRecvPacket`'s native-ERC20 branch must not allow the underlying transfer's state mutation to be committed when it subsequently fails. Either (a) run `MintingEnabled`/`ConvertCoinNativeERC20` checks *before* invoking the underlying transfer callback (reordering middleware so mint-eligibility is validated prior to any escrow release), or (b) explicitly compensate by re-escrowing/burning the just-unescrowed coin before returning the error acknowledgement, so that state committed by `writeFn()` matches what the returned acknowledgement communicates to the counterparty.

### Proof of Concept
1. Chain B holds an IBC voucher representing a native ERC20 token originally issued on EVM chain A (already transferred out and escrowed on chain A).
2. An attacker on chain B sends `MsgTransfer` back to chain A, setting `receiver` to a bech32/hex address that is a **blocked address** on chain A (e.g. a module account address, guaranteed to be blocked by `bankKeeper.BlockedAddr`).
3. Chain A's `RecvPacket` handler runs the middleware stack: `transfer.OnRecvPacket` un-escrows the native coin from the escrow account into the blocked recipient's bank balance and returns success; `erc20.Keeper.OnRecvPacket` then calls `MintingEnabled`, which fails at the `BlockedAddr` check (`x/erc20/keeper/mint.go:49-53`), producing an error acknowledgement.
4. ibc-go commits the cached context (`writeFn()`) unconditionally — the recipient's bank balance increase from the unescrow persists on chain A despite the error ack.
5. The relayer submits the error ack back to chain B; chain B's `OnAcknowledgementPacket` refunds/re-mints the burned voucher back to the original sender.
6. Result: chain A recipient's balance holds the unescrowed native coin, and chain B sender's balance holds the refunded voucher for the same amount — value has been duplicated across both chains.

Note: The commit-regardless-of-ack behavior of ibc-go's core `RecvPacket` handler is part of the external `ibc-go` dependency and could not be directly inspected in this repository's indexed sources; this assessment relies on well-documented, standard ibc-go semantics (cached-context commit occurs whenever a non-nil acknowledgement, success or error, is returned by the app callback). If a Devin session with full repo/dependency access is available, this should be explicitly verified against the vendored `ibc-go` version in `go.mod` before remediation.

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
