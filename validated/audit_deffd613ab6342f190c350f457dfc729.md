### Title
Fee/vbyte calculation omits the OP_RETURN data output, undercharging fees on attacker-influenced transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary

`SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, but computes `weight`, `vbytes`, and `needed_fee` from `payments` alone, which never includes that output. Like the OpenDollar `auctionSurplus` bug (a value computed against the wrong base, producing a figure inconsistent with what is actually emitted/accounted), the declared fee is computed against a smaller transaction than the one actually signed and broadcast. An unprivileged party who can cause `data`/`payments` to be fed into `SignableTransaction::new` (anyone who can trigger a transaction carrying metadata) causes the multisig to sign a transaction whose effective fee rate is lower than `fee_per_vbyte` and possibly below the relay minimum, while the `TooLowFee`/`NotEnoughFunds` checks still pass on the understated size.

### Finding Description

In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before any size accounting occurs:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

However, the size and fee are then computed only from `tx_ins.len()` and the `payments` slice:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its synthetic `Transaction` from `payments` plus an optional `change` script, so the `OP_RETURN` output (roughly `1 + 1 + up to 80` bytes of script plus the fixed ~9-byte output header) is never included in `weight`/`vbytes`. The same omission occurs in the change branch, which calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`.

As a result:

- `needed_fee` is understated by `fee_per_vbyte * (size of the OP_RETURN output)`, so `fee()` (`sum(inputs) - sum(outputs)`) yields an effective fee rate strictly below `fee_per_vbyte`.
- The minimum-relay check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` is evaluated against the understated `vbytes`, so a transaction whose *actual* fee rate is below relay minimum can pass validation and be signed.
- The `NotEnoughFunds` check uses the understated `needed_fee`, letting marginal inputs through that the real fee rate wouldn't support.

### Impact Explanation

The multisig produces and signs (via `TransactionSignMachine::sign`, which commits to the real `tx` including the OP_RETURN output) a transaction that pays less than the intended fee rate. With a large `data` payload or a marginal `fee_per_vbyte`, the signed transaction falls below the default minimum relay fee and will not propagate or confirm, leaving the input UTXOs effectively unspendable until the multisig can be coordinated to re-sign — a denial-of-confirmation / funds-stuck condition reachable purely from transaction data an unprivileged party supplies. This is the same class of flaw as the reference report: an emitted economic value (here, the committed fee implied by the signed outputs) is computed on a basis inconsistent with the real object, breaking the accounting invariant `fee = fee_per_vbyte * actual_vbytes`.

### Likelihood Explanation

Any input that controls `data` or the payment set reaching `SignableTransaction::new` (e.g., withdrawal/metadata requests in downstream integrators such as the processor's Bitcoin outputs) can induce the miscalculation; the delta is deterministic and grows with `data` length up to ~90 bytes × `fee_per_vbyte`. Triggering a non-relayable transaction additionally requires the intended fee rate to be near the relay minimum, so the reliable impact is a systematic fee-rate underpayment rather than guaranteed unspendability — consistent with Medium severity.

### Recommendation

Include the OP_RETURN output in the weight/vbyte calculation. Pass the complete output set (payments + `OP_RETURN` + optional change) to `calculate_weight_vbytes`, e.g. by constructing the size-estimation transaction from `tx_outs` directly, or by appending a `(op_return_script, 0)` entry into the `payments`-shaped list used for sizing. Recompute `needed_fee` and re-run the `TooLowFee` / `NotEnoughFunds` checks against that corrected size, including the change-output pass.

### Proof of Concept

```rust
// In-scope illustrative PoC against SignableTransaction::new:
// - one input of 10_000 sats
// - one payment of 5_000 sats (>= DUST)
// - data = 80 bytes (maximum allowed)
// - fee_per_vbyte = 2
let tx = SignableTransaction::new(
  vec![received_output_10k],
  &[(payment_script, 5_000)],
  None,                        // no change
  Some(vec![0xAA; 80]),        // OP_RETURN output
  2,
).unwrap();

// needed_fee is computed for a tx WITHOUT the ~90-byte OP_RETURN output.
// Actual signed tx includes it, so:
//   actual_vbytes > vbytes_used_for_needed_fee
//   tx.fee() == needed_fee  (all leftover already accounted)
//   effective rate = tx.fee() / actual_vbytes < 2 sats/vbyte
// With fee_per_vbyte near the relay minimum (e.g. 1 sat/vbyte), the signed
// transaction is below DEFAULT_MIN_RELAY_TX_FEE for its real size and will
// not be relayed, despite passing the TooLowFee check.
```

Key lines: the OP_RETURN output is added to `tx_outs` at `send.rs:194-202`, while `vbytes`/`needed_fee` are derived only from `payments` at `send.rs:204-206` and `send.rs:225-228`; the real transaction containing the extra output is what gets signed at `send.rs:373-397`.
