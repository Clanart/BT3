### Title
Uncontrolled Recursion in `PuzzleWithRestrictions.from_memo()` — Attacker-Controlled Custody Memo Nesting Can Crash Wallet Parsing (Stack Overflow / DoS) - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a CHIP-0043 custody structure (used by the plotnft/pool custody driver and general custody-architecture puzzles) from an untrusted `Program` memo. When the memo encodes an `MofN` puzzle, the method recurses into itself once per member with **no depth limit**, unlike every other tree-walking routine in this codebase, which was deliberately hardened against exactly this bug class.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses a hinted memo `Program` and, for `MofN` members, calls itself recursively for every nested member: [1](#0-0) 

Specifically the recursive branch: [2](#0-1) 

There is no bound on nesting depth (`MofN` members are themselves `PuzzleWithRestrictions`, which can again be an `MofN`), and no check on the number of members or recursion depth before calling `from_memo()` on each child. A memo can be crafted with a `MofN` node whose members recursively encode further `MofN` nodes, causing Python-level recursion proportional to attacker-chosen nesting depth.

This mirrors the CVE-2018-8015 bug class exactly: a malformed/untrusted structured file (there, an ORC file; here, a coin memo/custody puzzle hint) drives an unbounded recursive parser, and the fix in the referenced advisory is to add a depth/size bound. The chia-blockchain codebase already recognizes and defends against this exact class elsewhere:
- `sha256_treehash()` is explicitly implemented iteratively "to avoid Python recursion limits on deeply nested CLVM" [3](#0-2) 
- DataLayer's Merkle-tree ingestion path enforces an explicit `RecursionDepthExceededError` at the Rust layer to reject deeply nested untrusted trees [4](#0-3) 

`from_memo()` has no such protection, and the sibling method `unknown_puzzles` / `fill_in_unknown_puzzles` further recurse over the same unbounded `MofN` structure once constructed [5](#0-4) , compounding the exposure any time a wallet inspects a parsed custody object derived from an untrusted memo.

### Impact Explanation
Custody-architecture memos are attached to coins as hints/memos and are consumed by wallet code that reconstructs custody puzzle structure (`plotnft_wallet.py` and other custody consumers reference `PuzzleWithRestrictions`/`from_memo`). Any party that can create a coin observed by a victim wallet (a pool operator, plotnft counterparty, or any coin sender using this puzzle-hint convention) can embed a deeply nested `MofN` memo. When the wallet parses that memo, unbounded Python recursion triggers a `RecursionError`, which — depending on where it's caught — can crash the wallet's coin-processing/sync task or otherwise halt processing of the affected code path, a spend-triggered denial-of-service consistent with the "no-impact analogs are out of scope but a spend-triggered transaction-processing halt is in scope" validation criteria.

### Likelihood Explanation
Constructing a maliciously deep memo is inexpensive: an attacker only needs to nest `MofN` hint entries in a `Program` that is later delivered as a coin's memo/hint. No signature, special privilege, or protocol-level breakage is required — this is directly reachable by any unprivileged coin creator/counterparty whose coin gets processed by a wallet that parses custody memos (plotnft/pool custody flow is explicitly in scope).

### Recommendation
Add an explicit recursion/nesting depth limit (and/or convert `from_memo()`/`unknown_puzzles()`/`fill_in_unknown_puzzles()` to an iterative, stack-based traversal) mirroring the pattern already used in `sha256_treehash()` and the DataLayer `RecursionDepthExceededError` guard. Reject memos whose `MofN` nesting exceeds a sane bound (e.g., matching whatever depth production custody puzzles are expected to use) before recursing.

### Proof of Concept
1. Construct a `Program` memo of the form `("CHIP-0043" [nonce, [], 1, [m, [<memo_N>, ...]]])` where `<memo_N>` is itself a nested `MofN` memo of the same shape, repeated to a large depth (e.g., tens of thousands of levels), using `MofNHint.to_program()`/`PuzzleWithRestrictions.memo()` shape as reference: [6](#0-5) 
2. Deliver this memo as the puzzle hint of an observed coin (e.g., via a coin sent to a wallet that uses custody-architecture parsing, such as the plotnft/pool flow).
3. When the wallet calls `PuzzleWithRestrictions.from_memo()` on the received hint, Python recursion depth grows linearly with the crafted nesting and raises `RecursionError`, aborting the parsing/sync task that invoked it — a spend-triggered processing halt analogous to CVE-2018-8015's DoS in the ORC parser.

Note: I was not able to fully trace, within the available search budget, the exact call site in `chia/wallet/plotnft_wallet/plotnft_wallet.py` that invokes `from_memo()` on attacker-supplied coin data end-to-end (only that this file references `custody_architecture`/`from_memo`); confirming the precise trigger path (automatic vs. RPC-invoked) would benefit from a full Devin session with complete file access.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )

@pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)
