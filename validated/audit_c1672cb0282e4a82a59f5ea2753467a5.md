### Title
OP_RETURN data is omitted from Bitcoin transaction fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--024/blob/master/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` adds the attacker-supplied `data` as an `OP_RETURN` output, but calculates transaction weight, virtual size, minimum relay fee, requested fee, and change using only `payments`. The accounting therefore reflects the pre-`OP_RETURN` transaction rather than the transaction actually signed.

### Finding Description
`new` appends an `OP_RETURN` `TxOut` to `tx_outs` when `data` is supplied. [1](#0-0)  However, both calls to `calculate_weight_vbytes` pass `payments`, not the final `tx_outs`, so the generated measurement transaction omits the `OP_RETURN` output entirely. [2](#0-1)  The resulting underestimated `vbytes` value is used for `needed_fee`, the minimum-relay check, the funds check, and the change calculation. [3](#0-2)  The returned `SignableTransaction` nevertheless contains the uncounted output. [4](#0-3) 

### Impact Explanation
For a transaction with change, the change amount is too large and the signed transaction pays less than the caller-requested fee rate. If no change is created, the excess becomes fee, so the transaction pays more than `needed_fee()` reports. With an `OP_RETURN` payload approaching the allowed 80 bytes, the discrepancy is roughly the size of an additional output—on the order of 90–100 vbytes multiplied by `fee_per_vbyte`.

The omission also means `TooLowFee` and `TooLargeTransaction` are evaluated against a smaller transaction than the one produced. A crafted call can therefore create a transaction whose actual weight exceeds the standardness limit or whose actual fee rate falls below relay requirements after the additional output is included.

### Likelihood Explanation
`data` is a public parameter to `SignableTransaction::new`, and the defect is deterministic whenever it is `Some`. [5](#0-4)  The transaction is then signed using the real transaction containing the omitted output, making the incorrect accounting part of the signed result. [6](#0-5)  Serai's own processor currently passes `None` for this argument, which limits the impact to integrations or other callers that use the wallet API's documented `data` support. [7](#0-6) 

### Recommendation
Base weight and virtual-size calculation on the complete output list, including the `OP_RETURN` output and any change output. A clean fix is to make `calculate_weight_vbytes` accept `&[TxOut]`—or have `new` construct the candidate transaction first—and recalculate both candidate variants against their actual outputs before deriving `needed_fee` and change.

### Proof of Concept
```rust
let inputs = vec![received_output];
let payments = vec![(payment_script, 1_000)];
let data = vec![0u8; 80];

let tx = SignableTransaction::new(
  inputs,
  &payments,
  Some(change_script),
  Some(data),
  fee_per_vbyte,
).unwrap();

// The reported fee was calculated without the OP_RETURN output.
assert!(tx.transaction().vsize() as u64 * fee_per_vbyte > tx.needed_fee());

// The emitted transaction still contains the omitted output.
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));
```

At 80 payload bytes, the script alone contributes approximately 82 bytes, plus the eight-byte value and output framing. Those bytes are absent from both `vbytes` and `vbytes_with_change`, but present in `tx_outs` and the eventual sighash-signed transaction.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
