### Title
`ReceivedOutput::read` accepts an unverified scalar offset, allowing forged "received" outputs that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The bug class is "value minted/credited without backing" — the USSD initializer minted tokens with no collateral deposit behind them. In Serai's in-scope Bitcoin wallet code, the analog is the crediting of a spendable output (`ReceivedOutput`) without any backing proof that the claimed spend authority (the scalar `offset`) actually controls that output. `ReceivedOutput::read` deserializes an attacker-supplied `offset`, `TxOut`, and `OutPoint` from raw bytes and returns them as a fully-formed spendable output, with no check that `key + offset·G` produces the output's `script_pubkey`.

### Finding Description
`ReceivedOutput` is Serai's representation of a spendable, received Bitcoin output. Its spend authority is entirely derived from the `offset` field: `send.rs` tweaks the threshold keys by `output.offset()` to obtain the key that must sign. Legitimate `ReceivedOutput`s are produced by `Scanner::scan_transaction`, which looks up `output.script_pubkey` in `self.scripts` — a map built by `register_offset` where each entry's offset provably satisfies `p2tr_script_buf(key + offset·G) == script_pubkey` [1](#0-0) .

However, `ReceivedOutput::read` bypasses this invariant entirely:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...;
  outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  Ok(ReceivedOutput { offset, output, outpoint })
}
``` [2](#0-1) 

It reads an arbitrary scalar as `offset` and arbitrary bytes as `output`, then returns the pair as a valid `ReceivedOutput`. There is no binding between the two: nothing verifies that `p2tr_script_buf(scanner_key + offset·G) == output.script_pubkey`. Like the USSD `_mint` which created tokens with no collateral deposit, this constructor creates a "spendable output" claim with no evidence the offset actually unlocks it. Callers downstream (e.g., `processor/src/networks/bitcoin.rs`, which consumes `ReceivedOutput::offset()`) treat the object as authoritative.

### Impact Explanation
An unprivileged party that feeds bytes to `ReceivedOutput::read` can cause the wallet/processor to report a received output that is not actually spendable: funds "received" without backing, exactly mirroring the unbacked mint. Concretely, an attacker can submit a real on-chain UTXO (even one paying a completely unrelated script) paired with any offset. The system credits it as spendable; when a spend is attempted, the key tweaked by the forged offset does not correspond to the output's script, so the produced threshold signature is worthless for that input — the funds are unspendable, and any fee/change logic in `send.rs` built around them operates on phantom inputs. This satisfies the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
The gap exists whenever serialized `ReceivedOutput`s cross a trust boundary (scanner → processor/signers). `register_offset` explicitly documents that arbitrary offsets can introduce spendable script paths [3](#0-2) , yet the read path enforces no consistency at all. Exploitation requires only crafting bytes — a scalar plus consensus-encoded `TxOut`/`OutPoint` — no key compromise or collusion. Severity is Medium: it enables unbacked crediting of outputs, but a forged output ultimately fails at spend time rather than silently stealing funds.

### Recommendation
Bind the offset to the output at deserialization time. `ReceivedOutput::read` should take the scanner's base key (or the `Scanner` itself) and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)`, rejecting any pair that fails. Alternatively, make `read` a method on `Scanner` so deserialized outputs are validated against the registered `scripts` map exactly as `scan_transaction` does.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
let mut buf = vec![];
// 1. Any scalar — does NOT need to satisfy p2tr(key + offset*G) == script
buf.extend(Scalar::from(0xdeadbeefu64).to_bytes());
// 2. A real TxOut paying an unrelated script_pubkey
buf.extend(serialize(&TxOut { value: Amount::from_sat(50_000), script_pubkey: victim_script }));
// 3. Its real outpoint
buf.extend(serialize(&OutPoint::new(real_txid, 0)));

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.offset() now claims spend authority over an output the offset does not open;
// the wallet credits 50_000 sats as spendable — an unbacked credit.
```

Caveat: I confirmed `read` performs no offset↔script binding and that `scan_transaction`/`register_offset` maintain that binding internally; I could not fully trace every consumer of serialized `ReceivedOutput`s in `processor/` within scope, but the acceptance rule covers untrusted bytes fed to `ReceivedOutput::read` regardless of the specific caller.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
