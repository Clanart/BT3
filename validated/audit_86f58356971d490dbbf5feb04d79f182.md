### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` causes stack-consumption DoS via crafted AccountUpdate transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each role-key element by calling `rlp.DecodeBytes` on a nested byte string. If that nested byte string itself encodes another `AccountKeyRoleBased`, the function recurses into itself with no depth limit. This mirrors the ALPINE-CVE-2016-4074 bug class (`jv_dump_term` in jq recursing on crafted JSON without a depth bound, causing stack consumption and crash) — here the same "unbounded recursion on attacker-supplied nested container" pattern exists in the AccountKey deserialization path used during `TxTypeAccountUpdate` (and fee-delegated variants) transaction processing.

### Finding Description
`AccountKeyRoleBased` is decoded as follows: [1](#0-0) 

For each element `b` in the decoded `[][]byte`, `rlp.DecodeBytes(b, &serializer)` is called, which invokes `AccountKeySerializer.DecodeRLP`: [2](#0-1) 

If the decoded `keyType` is `AccountKeyTypeRoleBased`, `NewAccountKey` returns a fresh `*AccountKeyRoleBased`, and `s.Decode(serializer.key)` re-invokes `AccountKeyRoleBased.DecodeRLP` — i.e. the same function recurses on nested attacker-controlled byte strings, with **no depth check** anywhere in this decode path.

The only defense against nested `RoleBased` keys — `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable` returning `kerrors.ErrNestedCompositeType` — is applied **after** decoding has fully completed: [3](#0-2) 

This is confirmed by the existing regression test, which shows the nested-key rejection happens at `txpool.AddRemote` / block validation time (i.e., after `DecodeRLP` already ran to completion): [4](#0-3) 

Because `TxInternalDataAccountUpdate.Key` is of type `accountkey.AccountKey` and is populated via generic RLP struct decoding whenever any raw transaction bytes are parsed (e.g., from `eth_sendRawTransaction`, p2p tx broadcast, or block import), an attacker can craft an `AccountUpdate` (or `FeeDelegatedAccountUpdate*`) transaction whose `Key` field is a deeply self-nested `AccountKeyRoleBased` (RoleBased → RoleBased → RoleBased → …). Because each nesting level only costs a few bytes of RLP overhead (list header + type byte + length-prefixed string), a single transaction payload of moderate size (bounded only by the node's max tx-size/gas-limit-derived byte limits) can encode tens of thousands of nesting levels, well before any semantic validation (`CheckInstallable`) is reached. [5](#0-4) 

### Impact Explanation
Decoding such a transaction drives unbounded Go call-stack recursion inside a core transaction-parsing path shared by the mempool, block processing, and JSON-RPC decode helpers (`DecodeAccountKey`, `EncodeAccountKey`): [6](#0-5) 

A sufficiently deep nesting depth exhausts the goroutine stack, producing a fatal `runtime: goroutine stack exceeds ... - fatal error: stack overflow`, which is unrecoverable via `recover()` and crashes the entire node process. Since this can be triggered by any unprivileged party submitting a single transaction (via `eth_sendRawTransaction`, p2p tx gossip, or the `kaia_decodeAccountKey`/`kaia_encodeAccountKey` RPC endpoints), this is a remotely triggerable denial-of-service against full nodes, CNs, and validators that accept and decode the transaction — matching the "acceptance of an invalid transaction" / DoS class analogous to the reported jq CVE.

### Likelihood Explanation
High likelihood: no special privileges, no prior state, and no complex preconditions are required — the attacker only needs to construct and broadcast/submit one RLP-encoded `AccountUpdate`-family transaction with a deeply self-referential `AccountKeyRoleBased` payload. The decode path (`AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`) is exercised on every node that receives or processes the transaction (mempool admission, gossip relay, block validation), before signature or role-composite checks are applied, so the crash can be triggered widely across the network with a single crafted payload.

### Recommendation
Add an explicit recursion/nesting depth limit (and/or an early type check) in `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP`, rejecting any nested `AccountKeyTypeRoleBased` value immediately upon encountering it during decode (mirroring the existing `IsCompositeType`/`ErrNestedCompositeType` semantic rule), rather than only after full decode. Alternatively, track and bound decode depth via a shared context/counter across recursive `rlp.DecodeBytes` calls in this type family.

### Proof of Concept
Conceptually:
1. Construct `k0 = AccountKeyPublic` (or any leaf key).
2. Iteratively wrap: `k_{i+1} = AccountKeyRoleBased{ k_i }`, encoded via `AccountKeySerializer` RLP, for N (e.g., 50,000+) iterations, producing nested byte strings each containing the previous encoded key.
3. Encode a `TxTypeAccountUpdate` transaction whose `Key` field is the resulting deeply-nested `k_N` byte blob, sign it, and submit via `eth_sendRawTransaction` or directly to a node's txpool/p2p interface.
4. When the receiving node calls `tx.DecodeRLP` (mempool admission or block import), decoding descends into `AccountKeyRoleBased.DecodeRLP` recursively N times before any `CheckInstallable`/`ErrNestedCompositeType` validation occurs, exhausting the goroutine stack and crashing the process.

Note: exact N required to trigger a crash depends on Go's dynamic stack growth limits and the node's configured max transaction/RLP size; this was not empirically measured (no execution environment available), but the recursive, depth-unchecked structure of the decode path is confirmed directly in the cited source.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
