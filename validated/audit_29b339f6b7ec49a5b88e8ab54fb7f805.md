## Finding: Stale diff-selection reapplied to a freshly recomputed diff can silently corrupt partial commits

The report's core pattern is: a security-relevant computation (the "penalty," i.e. `feeDelta`) is derived from *state at one point in time*, but the actual enforcement happens against *state recomputed at a later point*, and nothing verifies the two states are consistent — so an attacker who can change the state in between silently defeats the guarantee. The corresponding invariant in Desktop is: "the commit that gets created must contain exactly the lines the user reviewed and selected in the diff view, nothing else."

### Title
Stale line-index diff selection is reapplied to a freshly recomputed working-directory diff, allowing partial commits/discards to silently include unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` builds the patch that will be staged for a partially-selected file by calling `getWorkingDirectoryDiff` again, right before staging, and then walking that *freshly fetched* diff's hunks/lines, checking each line against `file.selection.isSelected(absoluteIndex)`. [1](#0-0) 

The `selection` object, however, was computed by the renderer against the diff that was rendered earlier in the Changes view — it is a set of raw line-index positions (`DiffSelection`), not tied to the content/hash of the diff it was created against. [2](#0-1) 

Nowhere in `applyPatchToIndex`, `formatPatch`, or `stageFiles` is there a check that the diff fetched at staging time is the same diff (same hunks/line count/content) the selection indices were computed against. [3](#0-2) 

### Finding Description
The flow for a partial commit is:
1. The UI renders a diff via `getWorkingDirectoryDiff` and the user selects specific lines/hunks to include, producing a `DiffSelection` that is purely index-based (`withLineSelection(absoluteIndex, …)`).
2. Later, `_commitIncludedChanges` passes the `WorkingDirectoryFileChange` (carrying that stale `selection`) into `createCommit` → `stageFiles` → `applyPatchToIndex`. [4](#0-3) 
3. `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` to obtain the diff to actually apply, then calls `formatPatch(file, diff)`, which walks the new diff's hunks and, for every non-context line, decides inclusion solely from `file.selection.isSelected(absoluteIndex)` — a positional index into whatever diff is passed in, with no comparison to the diff that produced the selection. [5](#0-4) 

If the tracked file's content on disk changes between step 1 and step 3 — for example because a repository-defined Git mechanism executes in that window (a `.gitattributes` clean/smudge filter, a `post-checkout`/`post-merge` hook shipped in the repository, or any other tracked automation that rewrites a file after the app's last status/diff refresh but before the user clicks "Commit") — the hunk layout and line numbering of the new diff no longer correspond to what the user reviewed. The stale index-based selection is nonetheless blindly reapplied, so `formatPatch` can select/deselect the wrong lines (including lines the user never saw or never intended to commit), and `git apply --cached` stages that mismatched patch without any warning to the user.

This mirrors the reported bug class exactly: the guarantee ("only the reviewed/selected delta is committed") is computed against one snapshot and enforced against a different, attacker-influenceable snapshot, with no reconciliation between the two.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits class issue: a user could believe they are committing (and possibly pushing) only the lines they explicitly reviewed/selected, while the actual staged/committed content diverges — e.g., excluding a security-relevant line the user meant to keep out, or including content the user never reviewed at all. Because git hooks and clean/smudge filters are configured via repository-tracked files (`.gitattributes`, `.git/hooks` via `core.hooksPath` set in-repo config, or filters wired up by a project's own tooling that the user already trusts and runs), an attacker who controls the repository content can arrange for such a rewrite to happen in the narrow window between diff display and commit action.

### Likelihood Explanation
The window between "diff shown/selected" and "commit clicked" is entirely a normal, unprompted part of the UI workflow (the user reviews, selects lines, types a commit message, then clicks Commit) — no unnatural steps are required from the user. The trigger (a file being rewritten by repository-defined automation between those two points) requires only that such automation exist and fire during that window, which is plausible for hook-heavy or filter-heavy repositories that a victim has intentionally cloned and is working in.

### Recommendation
Bind the `DiffSelection` to the diff it was generated against (e.g., store a content hash/hunk fingerprint alongside the selection), and have `applyPatchToIndex`/`formatPatch` verify that the diff fetched at staging time matches the one the selection was computed from before applying it. If it doesn't match, refuse to stage and force the UI to re-diff and re-prompt the user for selection, similar in spirit to the report's suggestion of tracking intervening state changes rather than blindly trusting a delta computed against a possibly-stale reference point.

### Proof of Concept
1. Attacker adds a repository-tracked mechanism (e.g. a `.gitattributes` clean filter, or `core.hooksPath` pointing to a repo-tracked hooks directory with a `post-checkout`/background watcher script) that rewrites `target-file.txt` shortly after it is touched.
2. Victim opens Desktop, modifies `target-file.txt`, views the diff, and selects only lines 1–5 for the commit (deliberately excluding lines 6–10).
3. Before the victim clicks "Commit", the repository-tracked automation rewrites `target-file.txt`, shifting/altering hunks (e.g., inserting lines above the original changes).
4. Victim clicks "Commit". `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [6](#0-5) , and `formatPatch` reapplies the stale line-index selection to the new hunk layout [7](#0-6) , staging different lines than what the victim selected.
5. The resulting commit (and any subsequent push) silently contains content the victim never reviewed/approved, with no warning from the application.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
