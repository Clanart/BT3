### Title
SSRF via unrestricted DataLayer mirror URLs fetched during subscription sync - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer mirror feature lets any wallet holder publish arbitrary URL strings on-chain for any DataLayer store, and other nodes' DataLayer services automatically issue outbound HTTP requests to those URLs during routine subscription sync, with no validation of scheme, host, or destination (no blocklist for loopback/link-local/internal addresses). This mirrors the CVE-2017-7200 bug class: a URL-driven "fetch" feature that lets an attacker make the service perform requests to attacker-chosen internal/local targets, masking a port scan as legitimate service traffic.

### Finding Description
Any wallet user can create a mirror coin for **any** DataLayer store id (not just their own) via the `dl_new_mirror` RPC, which calls `DataLayerWallet.create_new_mirror()`. The URLs are stored as plain memo strings on the mirror coin puzzle with no format/host validation: [1](#0-0) 

These mirror URLs are read back via `dl_get_mirrors` / `get_mirrors()` and fed into `update_subscriptions_from_wallet()`, which strips trailing slashes but performs no scheme/host restriction: [2](#0-1) 

Any peer that subscribes to that store id (a normal, unprivileged DataLayer client action) runs `fetch_and_validate()` in its periodic sync loop, which iterates `get_available_servers_for_store()` results and calls `insert_from_delta_file()` → `download_file()` → `http_download()`: [3](#0-2) 

`http_download()` performs an unauthenticated, unrestricted `aiohttp` GET directly against the attacker-supplied URL plus a filename, with no check on the host (e.g., `127.0.0.1`, `169.254.169.254`, internal service ports, `file://`-adjacent schemes handled by aiohttp, etc.): [4](#0-3) 

The `.cursor/context/data-layer.md` documentation itself flags this as a known trust boundary concern ("Plugin and mirror URLs are external trust inputs"), but the code implements no host/IP validation, only response-size limits: [5](#0-4) 

The test suite even demonstrates publishing loopback URLs (`http://127.0.0.1/8000`) as valid mirrors without any rejection: [6](#0-5) 

This is the direct structural analog of CVE-2017-7200: a feature designed to fetch remote content on behalf of the service, driven by an attacker-controlled URL, with no destination validation — enabling masked port scans / probing of internal network endpoints (localhost, internal service ports, cloud metadata endpoints) that appear to originate from the victim's DataLayer node rather than the attacker.

### Impact Explanation
Any user who subscribes to (or already owns) a DataLayer store controlled or targeted by an attacker will have their node's outbound HTTP client automatically probe attacker-chosen network locations at every `manage_data_interval` sync cycle. This can be used to:
- Perform masked port/service scans against internal infrastructure or localhost services of DataLayer node operators (matching the CVE's core impact).
- Response timing/behavior (timeout vs. connection-refused vs. HTTP status) can be inferred through subsequent `server_misses_file`/backoff or exception logging, providing an oracle for internal network reconnaissance.
- Potential targeting of cloud metadata services or internal RPC/admin endpoints reachable from the node's network position.

This does not directly cause coin-state divergence or fund theft, but it is a genuine SSRF enabling network reconnaissance/probing from a mempool/wallet-reachable action (subscribing to a store whose mirrors were poisoned by any spend-bundle submitter), fitting the Medium severity class of the original CVE.

### Likelihood Explanation
Likelihood is high for the trigger step: creating a malicious mirror only requires a `dl_new_mirror` transaction (any wallet with minimal XCH), and the URLs are never validated. The only precondition on the victim side is that their DataLayer node subscribes to (or owns/tracks) the targeted store id, which is normal DataLayer usage (e.g., subscribing to a public/shared store to sync its data) — an action fully within the reach of an "unprivileged... Data Layer client" as scoped by this assessment.

### Recommendation
- Validate mirror URLs at creation time (`create_new_mirror`) and/or at consumption time (`update_subscriptions_from_wallet` / `http_download`) to reject or flag non-HTTP(S) schemes and disallow loopback, link-local, private, and other non-public IP ranges (resolve DNS and check resulting IPs, not just the literal host string) unless explicitly opted in via configuration.
- Add configurable allow/deny lists for mirror hosts, similar to conventional SSRF mitigations, and make outbound requests via a hardened HTTP client that enforces these checks and disables redirects to disallowed hosts.
- Consider rate-limiting/backing off aggressively on newly-seen mirror URLs and logging/alerting when mirror URLs point to private/reserved address space.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` RPC (`DLNewMirror(launcher_id=<victim_store_id>, amount=..., urls=["http://127.0.0.1:22"], fee=...)`) to publish a malicious mirror URL for a store the victim subscribes to — see the mirror-creation flow in `chia/wallet/wallet_rpc_api.py:3255-3274` and `chia/data_layer/data_layer_wallet.py:687-703`.
2. Victim's DataLayer service, subscribed to the same `store_id`, runs its periodic `periodically_manage_data()` loop, which calls `update_subscription()` → `update_subscriptions_from_wallet()` (`chia/data_layer/data_layer.py:979-985`), pulling in the attacker's URL as a server candidate.
3. `fetch_and_validate()` (`chia/data_layer/data_layer.py:642-694`) selects the malicious server and calls `insert_from_delta_file()` → `download_file()` → `http_download()` (`chia/data_layer/download_data.py:298-324`), causing the victim's process to issue `GET http://127.0.0.1:22/<delta-filename>`.
4. The attacker observes differential behavior (connection failure vs. success/timeouts logged, or via `server_misses_file` backoff behavior) to infer whether the victim's internal port 22 (or any other attacker-chosen target) is open — the scan appears to originate from the victim's DataLayer node, exactly matching the CVE-2017-7200 impact pattern.

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
