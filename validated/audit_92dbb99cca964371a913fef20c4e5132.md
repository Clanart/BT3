### Title
`ThresholdKeys::new` / `ThresholdKeys::read` never validate that `secret_share` matches `verification_shares[i]`, nor that verification shares are non-identity — crafted key material yields a `group_key` that is unspendable or attacker-controlled - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the report's "no validation of the address parameter before use" class, `ThresholdKeys::new` validates only the *count* and *index range* of `verification_shares`, never their *values*. A `Participant(0)` cannot be constructed (enforced by `Participant::new` at `crypto/dkg/src/lib.rs:29-35`), but the point values themselves are unchecked: identity elements or arbitrary attacker-chosen points are accepted. `ThresholdKeys::read` feeds attacker-controlled bytes through `C::read_G` directly into this constructor (`crypto/dkg/src/lib.rs:620-631`).

### Finding Description
`ThresholdKeys::new` performs these checks only:

```rust
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... }
}
```

Then it derives the group key from the first `t` shares:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

There is no check that:
- `verification_shares[i] == C::generator() * secret_share` for the local participant `i`, i.e., the secret share is never validated against its own verification share;
- any verification share is non-identity (an identity share contributes nothing and silently shifts `group_key` toward whatever the remaining shares define);
- the shares lie on a common degree-`t-1` polynomial at all.

`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) makes this reachable from untrusted bytes: it reads `n` points via `C::read_G` (which does not reject the identity element), reads `secret_share` via `C::read_F`, and calls `ThresholdKeys::new` — the deserialized `group_key` is then whatever the byte stream dictates, with no relation between the stored `secret_share` and the stored shares.

### Impact Explanation
- **Funds received but unspendable**: if a signer loads `ThresholdKeys` from a tampered/untrusted serialization, the resulting `group_key()` may be a point with no known discrete log (e.g., interpolation over garbage or identity shares). Outputs scanned/attributed to `group_key()` can never be signed for — the protocol is "blocked" exactly like the report's zero-address governance lock.
- **Key substitution**: an attacker who can supply the serialized key blob sets `verification_shares[1..=t]` to points whose Lagrange combination equals a key they control (e.g., `G * k` for known `k`, achievable trivially for `t == 1`, or by choosing shares summing to a known key). The victim's `ThresholdKeys::group_key()` then reports the attacker's key while the victim's `secret_share` is useless — deposits to that address are stealable, and FROST signatures produced under the view will not verify against the claimed group key.

### Likelihood Explanation
Medium. Exploitation requires the attacker to influence the bytes passed to `ThresholdKeys::read` (backup/restore, coordinator-distributed key material, or any channel feeding serialized keys) — a public-input path per the threat model. The missing-validation root cause is unconditional; there is no consistency check anywhere in `new`, `read`, or `view` (the `view` checks at `crypto/dkg/src/lib.rs:463-491` cover participant indexes only, not share consistency).

### Recommendation
In `ThresholdKeys::new`:
- Reject identity verification shares (`share.is_identity()`).
- Verify `verification_shares[&params.i()] == C::generator() * secret_share` (and for `Interpolation::Constant`, that `c.len() == n`).
- Optionally, verify the shares lie on a common polynomial by checking each share `j` against the first `t` shares' interpolation, or document that `ThresholdKeys::read` input must be authenticated.

### Proof of Concept
```rust
// t = 1 so group_key = verification_shares[1] exactly.
let params = ThresholdParams::new(1, 2, Participant::new(1).unwrap()).unwrap();
let attacker_scalar = C::F::random(rng);
let attacker_key = C::generator() * attacker_scalar;

let mut shares = HashMap::new();
shares.insert(Participant::new(1).unwrap(), attacker_key);      // attacker-controlled
shares.insert(Participant::new(2).unwrap(), C::G::identity());  // identity accepted

let keys = ThresholdKeys::new(
  params,
  Interpolation::Lagrange,
  Zeroizing::new(C::F::random(rng)), // inconsistent with shares[1]; never checked
  shares,
).unwrap();

assert_eq!(keys.group_key(), attacker_key); // attacker knows discrete log
// keys.secret_share() cannot produce valid signatures; funds to group_key are lost/stolen.
```
Equivalently, serialize this structure and hand the bytes to `ThresholdKeys::read` — deserialization succeeds with no consistency error.
