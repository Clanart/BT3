## Analog Found: Git clone always disables git's built-in submodule protocol protection [1](#0-0) 

### Title
GitHub Desktop unconditionally disables Git's clone protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) during recursive clone, allowing malicious submodule URLs to read/write outside the repository - (File: app/src/lib/git/clone.ts)

### Summary
The original report's broken invariant is "a safer, parameterized code path exists but the codebase falls back to the less-safe default instead of using it where the operation actually needs the safety guard." The same pattern exists in Desktop's `clone()` function: it hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for every clone, unconditionally disabling Git's own submodule/embedded-repository protections, instead of gating that behind an explicit opt-in like the codebase already does elsewhere for the same class of risk (`allowFileProtocol`).

### Finding Description
`clone()` builds its environment and args like this: [1](#0-0) 

Note that `--recursive` is always passed and `GIT_CLONE_PROTECTION_ACTIVE` is always forced to `'false'`. `GIT_CLONE_PROTECTION_ACTIVE` is the upstream Git safety switch (introduced for the class of issues fixed as CVE-2022-39253) that normally blocks recursive submodule clones from following `file://` submodule URLs or symlinked/embedded `.git` directories that point outside the intended checkout — exactly the mechanism designed to stop a malicious repository from making the clone step read or write files elsewhere on disk.

Crucially, Desktop's own code shows it is aware that "allow file protocol" is a dangerous, opt-in-only capability: `checkoutBranch`/`checkoutCommit` and `updateSubmodulesAfterOperation` take an explicit `allowFileProtocol` boolean (default `false`), and only when the caller explicitly sets it does the code add `-c protocol.file.allow=always`: [2](#0-1) [3](#0-2) 

`clone()`, however, does not thread any such conditional parameter through — it always fully disables Git's clone-time protection rather than only doing so when a user has explicitly indicated they trust the source (the same "optimal/safe version exists but isn't used where required" gap as the report's `_depositAndSwap()` overload issue).

### Impact Explanation
An attacker who controls the contents of a repository (a public/forked repo, or a repo shared via a clone URL/deep link) can add a `.gitmodules` entry with a submodule URL that abuses `file://`/local-path semantics or embed a `.git` directory that is a symlink to a path outside the working tree. When a victim clones that repository with GitHub Desktop, the recursive submodule step runs with Git's protection fully disabled, potentially causing Desktop's git process to read or write files outside the cloned repository directory on the victim's machine — matching the report's "unprivileged attacker controls a cloned repo → code execution/file read-write outside repo" impact class.

### Likelihood Explanation
Every single clone performed by Desktop (all of them are `--recursive`) runs with the protection off, unconditionally, for both first-party and untrusted third-party remotes. No user action beyond a normal "Clone repository" is required — the attacker only needs the victim to clone their repository, which is a completely ordinary/expected Desktop workflow, not a contrived local-access or admin scenario.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally. Thread the same explicit, opt-in `allowFileProtocol`-style parameter that `checkout.ts`/`submodule.ts` already use into `clone()`, defaulting to the safe/protected behavior (`GIT_CLONE_PROTECTION_ACTIVE` left enabled, i.e. not overridden), and only relax it when there is a legitimate, user-approved reason (e.g., the same trust decision already surfaced for `allowFileProtocol` elsewhere).

### Proof of Concept
1. Attacker creates a public repository with a `.gitmodules` file defining a submodule whose URL uses `file:///` (or an equivalent embedded/symlinked `.git` layout) pointing at a path outside the repository.
2. Victim uses GitHub Desktop to clone the attacker's repository (`clone(url, path, options)` in `app/src/lib/git/clone.ts`).
3. Desktop always executes `git -c init.defaultBranch=... clone --recursive ... -- <url> <path>` with `env.GIT_CLONE_PROTECTION_ACTIVE` set to `'false'` [1](#0-0) , disabling the exact Git safety check meant to reject such submodule definitions.
4. The recursive submodule update proceeds against the attacker-controlled `file://`/embedded path instead of being blocked, letting the attacker's repo pull local files into the checkout or otherwise touch paths outside the intended clone target.

Note: I was not able to fully trace every downstream call site of `allowFileProtocol=true` (e.g., in `app-store.ts`) before running out of tool budget, so I cannot confirm whether any additional guard rails exist further up the call chain that mitigate this at the UI layer; this should be verified in a follow-up session with full repository access.
