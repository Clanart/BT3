**Reasoning:** The `Location` passed to `ParentOrParentsExecutivePlurality::contains` is not attacker-supplied message content — it is the *origin* location derived by the XCM transport layer (DMP for relay-chain-originated messages, XCMP for sibling messages) before the barrier is even evaluated [1](#0-0) . An unprivileged attacker interacting with the parachain cannot forge the *origin* of an inbound XCM message; that origin is set by the consensus-level channel the message physically arrived on (Cumulus's DMP/XCMP handling), not by data embedded in the program itself. The only way to obtain a `(parents: 1, X1(Plurality{ id: BodyId::Executive }))` origin is for the relay chain's own runtime to author a `DescendOrigin` into that plurality within a message it sends down the DMP channel — something only the genuine relay chain executive (via governance) can do, since a parachain has no channel through which non-relay-chain content can be injected as a "parent" origin.

This filter is boilerplate copied unmodified from the standard Polkadot SDK/Cumulus template `Barrier` configuration used by virtually all Substrate parachains (the same pattern also appears at [2](#0-1) ), and its security rests on the trusted-transport assumption inherent to XCMP/DMP channel provenance, not on message-content validation. Exploiting it would require either compromising the relay chain's executive/governance path or forging XCMP channel provenance — both of which fall outside the unprivileged-attacker threat model and are explicitly excluded scope items (malicious peers/nodes, compromised infrastructure). No unprivileged call, message, or proof path lets an attacker set their own origin location to the Executive plurality value.
