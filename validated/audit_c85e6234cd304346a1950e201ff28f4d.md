### Title
Copilot merge-conflict resolution can silently delete or corrupt unrelated code due to inconsistent conflict-marker parsing - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The seed report is a smart-contract accounting bug: `ZNSTreasury` records a `stakedAmount` based on a naive read of a token transfer, while the token's actual balance can diverge (rebasing/deflationary), so the recorded state silently drifts from the real reserve and the user loses funds on withdrawal with no error. The same *class* of bug — two independent components computing "the same" quantity from attacker-influenced input, disagreeing without validation, and silently corrupting a value the user relies on — exists in GitHub Desktop's AI ("Copilot") merge-conflict resolution feature. Here the "accounting" is the location and count of conflict hunks in a merged file: one function (`extractConflictHunks`) determines the hunks to show the model and the expected hunk count, and a second, independently-written function (`reassembleResolvedFile`) re-parses the same raw file text to splice the model's resolutions back in. Because both parsers use naive, first-match regex scanning of `<<<<<<<` / `=======` / `>>>>>>>` and only their *counts* are cross-checked (never their boundaries), attacker-controlled file content that merely resembles a conflict marker (but isn't part of a real git conflict) causes the two parsers to disagree on where a conflict hunk begins and ends. The result is that the AI's resolution is spliced into the wrong span of the file, silently deleting or corrupting real code — including unresolved conflicting code — with no residual markers and no error before the content is written to disk and staged with `git add`.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks the raw conflicted file line-by-line looking for `^<{7}(?:\s|$)`, `^\|{7}(?:\s|$)`, `^={7}$`, and `^>{7}(?:\s|$)` to find hunk boundaries: [1](#0-0) 

Note that once an "ours" marker is found, the ours-content loop just keeps consuming lines until it sees *any* line matching the base/separator regex — it does not require that separator to be the one that git actually paired with this marker. Likewise the theirs-content loop stops at the *first* line matching the closing-marker regex: [2](#0-1) 

If no closing marker is ever found (e.g., because a stray look-alike `<<<<<<<`-style line appears in ordinary, non-conflicted file content with nothing that looks like `=======`/`>>>>>>>` after it), the loop runs to the end of the file and the whole hunk — and the scan itself — is abandoned via `continue`, silently dropping any real conflicts that exist later in the same file: [3](#0-2) 

This exact "give up and lose remaining hunks" behavior is confirmed by the project's own test: [4](#0-3) 

Separately, `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` re-implements the *same* first-match marker scanning independently against the raw on-disk content to splice the model's per-hunk resolutions back in, but its failure handling differs: on an unresolved/malformed marker it does **not** abort the whole scan — it treats only that one line as literal content and keeps scanning forward for the next `<<<<<<<`: [5](#0-4) 

The only cross-check between the model's hunk output and the actual file is a hunk-*count* comparison in `validateResolutionPaths` — it never verifies that the hunks the model resolved correspond to the same byte ranges that `reassembleResolvedFile` will later locate: [6](#0-5) 

Because `extractConflictHunks` can under-report hunks (aborting on a stray look-alike marker) while `reassembleResolvedFile` keeps finding real hunks further down the file, `hunkIndex` in the reassembly loop runs past the end of `hunkResolutions` for the "hidden" hunks. In that case the splice code executes `i = closingIndex + 1` (removing the entire conflict block, markers and all) but skips writing any replacement content: [7](#0-6) 

The reassembled content is then written directly to disk and staged with no marker-residue check that would catch a *silent deletion* (there are no markers left to detect): [8](#0-7) 

### Impact Explanation
An attacker who controls a branch, PR, or fork that the victim merges/pulls/rebases (a "cloned/fetched repository") can craft a file so that when it genuinely conflicts with the victim's changes, the file also contains innocuous-looking text matching Desktop's marker regex (e.g. a line of exactly seven `<` characters in a comment, string literal, or documentation snippet). When the victim uses Desktop's "Resolve conflicts with Copilot" feature, `extractConflictHunks` can misparse or entirely drop a real conflict occurring after the fake marker, while `reassembleResolvedFile` still locates and removes that real conflict block from the file during the splice — but with no resolution content available for it, the entire block (both "ours" and "theirs" code, potentially security- or logic-critical) is silently deleted. The user is shown a "fully resolved" file with no visible markers or errors, and if they accept and commit/push, the corruption ships to the repository undetected. This matches "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires only an unprivileged attacker who can get the victim to merge a branch/PR they authored (a normal collaboration workflow, not local/physical access, malware, or leaked credentials) and requires the victim to use the built-in Copilot conflict-resolution feature on a file that both genuinely conflicts and contains attacker-controlled text resembling a conflict marker (comments, embedded documentation about git conflicts, ASCII-art separators, generated diffs/patches stored as text, etc. are all plausible carriers). No unnatural user steps are needed beyond the normal "merge, then click Resolve with Copilot, then accept" flow the feature is designed for.

### Recommendation
Make `reassembleResolvedFile` and `extractConflictHunks` share a single hunk-boundary parser (not two independently maintained regex state machines), and have reassembly locate hunks by validating full markers (`<<<<<<<`, correct pairing of `=======`/`|||||||`, `>>>>>>>`) using the exact same boundary list the context builder produced (e.g., pass hunk start/end line indices through instead of re-deriving them). Additionally, `validateResolutionPaths`/reassembly should hard-fail (rather than silently drop content) if the number of hunk boundaries found during reassembly does not exactly match the number found during context extraction, and should refuse to stage/write any file where reassembly cannot account for every marker block that exists in the raw content.

### Proof of Concept
1. Attacker pushes a branch `evil` where a shared file (e.g. `auth.ts`) contains, in an unrelated comment/docstring far from the real change, a line consisting of exactly `<<<<<<< example` (matches `^<{7}(?:\s|$)`) with no `=======`/`>>>>>>>` anywhere after it until a later, real diverging line.
2. The same branch also modifies a security-relevant line further down (e.g. an authorization check), producing a real, well-formed git conflict block at that location when merged against the victim's branch.
3. Victim merges/pulls `evil` into their branch; git writes the real `<<<<<<<`/`=======`/`>>>>>>>` markers around the real conflicting authorization code, plus the attacker's untouched look-alike line elsewhere in the file.
4. Victim clicks "Resolve conflicts with Copilot." `buildConflictContext` → `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-242`) hits the attacker's look-alike line first, fails to find a proper closing marker forward, and drops/mis-scopes the real conflict — the model is never shown (or is shown a corrupted view of) the real authorization conflict.
5. `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`), scanning the same raw content independently, still finds the real `<<<<<<<...>>>>>>>` block and removes it (`i = closingIndex + 1`) but has no corresponding resolution to splice in (`hunkIndex >= hunkResolutions.length`), so the entire authorization conflict block is deleted with no trace.
6. The resulting file is written via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add` (`app/src/lib/stores/app-store.ts:7258-7267`), with no leftover conflict markers and no error — the user commits/pushes code that is missing the authorization check with no warning.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
