### Title
Sandwichable public-router swap in `_bullMGP` due to caller-controlled `_minMGPRec` - (File: wombat/ArbWomUp2.sol)

### Summary
`incentiveDeposit` allows the caller to fully control the slippage floor (`_minMGPRec`) passed into a synchronous, protocol-funded swap of BUSD for MGP executed against a public AMM router (`ROUTER.swapExactTokensForTokens`). Because there is no independent price check (oracle, TWAP, or fixed minimum) reconciling the swap output with a fair market price, an attacker can manipulate the router pool immediately before and after the call within the same transaction (or via a bundled/atomic sequence) to force the swap to execute at a self-chosen, favorable price, and the extra MGP is locked directly into their own `vlMGP` position.

### Finding Description
In `incentiveDeposit`, when `_bullMode` is true, the reward computed for the user (`rewardToSend`, in BUSD) is passed into `_bullMGP`: [1](#0-0) 

`_bullMGP` swaps the contract's BUSD for MGP using `_minRec` supplied verbatim by the caller as `_minMGPRec`, with no lower bound enforcement, no oracle cross-check, and no TWAP validation: [2](#0-1) 

Since `_minMGPRec` can be set to `0`, the router call `ROUTER.swapExactTokensForTokens(_busdAmount, _minRec, path, address(this), block.timestamp)` will accept virtually any output amount. The attacker, who controls the exact block/transaction in which `incentiveDeposit` executes, can push the BUSD/MGP pool price down (e.g., by selling MGP into the pool) immediately before calling `incentiveDeposit`, causing the contract's BUSD to be swapped into an abnormally large MGP amount, then restore the pool price afterward. The resulting `amounts[1]` (and the derived `mgpAmountToLcok`, which additionally applies the `bullBonusRatio` bonus) is locked for `_account = msg.sender`: [3](#0-2) 

Because the attacker is both the price manipulator and the beneficiary (`vlMGP.lockFor(mgpAmountToLcok, _account)` credits the same address), they can extract value from the AMM's liquidity in the same block, inflating their locked vlMGP amount beyond the fair-value bonus the protocol intended to grant, at the router pool's/protocol's expense. `nonReentrant` and `whenNotPaused` do not mitigate this because the manipulation occurs via separate router trades surrounding (not reentering) the call, and there is no check on `amounts[1]` against any independent reference price.

### Impact Explanation
The attacker can cause the contract to convert its BUSD reward pool into MGP at a manipulated (favorable-to-attacker) price and lock the inflated MGP amount to their own `vlMGP` position, extracting value beyond the intended reward/bonus schedule. This is a direct value-extraction path against protocol-held funds (the BUSD reward balance) and/or the router pool's liquidity, repeatable on every `incentiveDeposit(..., true)` call as long as the BUSD/MGP pair has thin liquidity, matching a Critical/High severity direct-theft class.

### Likelihood Explanation
Feasibility depends on the liquidity depth of the configured `ROUTER`'s BUSD/MGP pair (set via `setup`, an owner-only function, but the pair's liquidity is externally controlled and can be thin). No privileged role is required by the attacker—only a standard EOA/contract capable of trading on the same router and calling `incentiveDeposit` with `_minMGPRec = 0`. The attack is capital-bounded by the cost of moving the pool and reversible in the same transaction/block, making it cheap and repeatable whenever pool depth is shallow relative to `rewardToSend`.

### Recommendation
Remove caller control over slippage for a protocol-initiated swap: either (a) compute `_minMGPRec` on-chain from a trusted oracle/TWAP with a bounded max deviation and ignore/clamp the caller-supplied value, or (b) require `_minMGPRec` to be validated against an internally tracked fair price before executing the swap, or (c) route protocol-owned swaps through a mechanism resistant to same-block manipulation (e.g., a TWAP-based AMM, a commit-reveal, or restricting execution to keeper-only with off-chain quoted minimums).

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ArbWomUp2`, mock `wom`/`busd`/`mgp` ERC20s, a mock `vlMGP`, and a Uniswap/Pancake-V2-style router+pair seeded with thin BUSD/MGP liquidity.
2. Configure the contract via `setup` and `setMultiplier` so that a deposit of `_amount` produces a known `rewardToSend` in BUSD.
3. As the attacker: 
   - Record MGP pool reserves and price.
   - Trade against the BUSD/MGP pair to crash the MGP price (sell MGP for BUSD).
   - Call `incentiveDeposit(_amount, 0, true)` from the attacker's own address.
   - Immediately after, trade again to restore the pool to its original price.
4. Assert: `mgpAmountToLcok` locked to the attacker's `vlMGP` position (verify via mock `vlMGP.lockFor` call args or emitted `VLMGPRewarded` event) significantly exceeds the amount that would have resulted from an unmanipulated pool price for the same `rewardToSend`.
5. Assert the attacker's net token balance (BUSD/MGP spent manipulating the pool, minus fees) plus the inflated locked MGP value exceeds what a fair-price swap would have granted, demonstrating extractable profit.

        IERC20(busd).safeApprove(address(ROUTER), _busdAmount);
        
        address[] memory path = new address[](2);
        path[0] = busd;
        path[1] = mgp;
        uint256[] memory amounts = ROUTER.swapExactTokensForTokens(
            _busdAmount,
            _minRec,
            path,
            address(this),
            block.timestamp
        );

        uint256 mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR; // get bull mode bonus
        IERC20(mgp).approve(address(vlMGP), mgpAmountToLcok);
        vlMGP.lockFor(mgpAmountToLcok, _account);

        emit VLMGPRewarded(_account, _busdAmount, mgpAmountToLcok);
    }
