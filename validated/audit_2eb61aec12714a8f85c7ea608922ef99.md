### Title
Divergent conflict-marker parsers cause Copilot to silently merge the wrong `ours`/`theirs` content into a committed file - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted conflict resolution feature parses a conflicted file's `<<<<<<<`/`=======`/`>>>>>>>` markers **twice**, with two independently-implemented parsers that are required to stay in lock-step: `extractConflictHunks` builds the hunk content sent to the model, and `reassembleResolvedFile` later splices the model's per-hunk resolution back into the original file "matched by order, not by line number" [1](#0-0) . The two parsers use different termination rules for the `=======` separator, so a conflict hunk whose "ours" section legitimately contains a line matching the separator regex is split at the wrong place in one parser but not the other — silently corrupting the content that gets written to disk and eventually committed.

### Finding Description
`extractConflictHunks` collects the "ours" side of a hunk by scanning forward until it sees a line matching `baseMarker` or `separatorMarker`, then immediately treats everything from there until the next `>>>>>>>` as `theirsContent`, without ever looking for a second `=======` line: [2](#0-1) 

`separatorMarker` is `/^={7}$/` — any standalone line consisting of exactly seven `=` characters (a common banner/section divider in source and markdown files) matches it, regardless of whether it is an actual git conflict separator.

`reassembleResolvedFile`, which later splices the model's resolved content back into the original file, performs its own independent lookahead for the same conflict block: [3](#0-2) 

Both parsers agree on the *count* of hunks in this scenario (one hunk, since the real `>>>>>>>` closing marker is unaffected), so the guard in `validateResolutionPaths` that checks hunk counts match `expectedHunkCounts` does not catch the discrepancy: [4](#0-3) 

But the *content* the model reasoned about is wrong: if the true "ours" section of a conflict contains a benign standalone `=======`-length line (e.g. a comment divider added on the attacker's branch), `extractConflictHunks` truncates `oursContent` at that point and folds the remainder — including the real conflict separator and the true "theirs" text — into `theirsContent`. The model is shown this corrupted split, reasons about it, and produces a `resolvedContent` for what it believes is "the merged content." `reassembleResolvedFile` then splices that resolution into the *entire* real conflict block (from the real `<<<<<<<` to the real `>>>>>>>`), because its own lookahead only needs to observe *any* `=======`-matching line before finding the closing `>>>>>>>` — it does not care which one was used to split the content for the prompt.

The net effect: the file written to disk (and staged/committed) is a splice of the model's resolution — which was computed against a mis-parsed, truncated view of "ours" — into the full original conflict region. None of the existing validators (`parseCopilotConflictResolution`'s "resolution still contains markers" check, or `validateResolutionPaths`'s hunk-count check) detect this because the corruption is content-level, not marker-presence or count-level.

### Impact Explanation
This causes **silent corruption of what the user commits**: the user asks Copilot to resolve a merge/rebase conflict, sees a plausible-looking resolution and reasoning, accepts it, and the resulting file that gets staged and committed can differ from what the model actually intended to produce, without any error, warning, or diff mismatch being surfaced. Because the corrupted region is exactly the boundary between "ours" and "theirs" content, this can drop or misplace code the user's own branch introduced, producing a working file that silently reverts or garbles the user's own changes at commit time.

### Likelihood Explanation
Likelihood is **Medium**: it requires (a) a conflict whose true `ours` section on either branch legitimately contains a line of exactly seven `=` characters — plausible in real code, comment banners, Markdown horizontal rules, or ASCII-art dividers, and fully controllable by whoever authored the conflicting branch/PR (an attacker who can get their branch merged/rebased against), and (b) the user invoking the Copilot conflict-resolution feature on that file. No local access, admin rights, or social engineering beyond normal collaborative branch/PR contribution is required — the "attacker" simply needs to introduce a benign-looking divider line into content that later conflicts with the victim's branch.

### Recommendation
Make `extractConflictHunks` and `reassembleResolvedFile` share a single conflict-block-parsing implementation (or have `extractConflictHunks` verify, like `reassembleResolvedFile` does, that the line it identifies as the separator is followed by a valid closing `>>>>>>>` with no intervening `<<<<<<<`/`|||||||` before accepting it as the real separator) so both passes agree not just on hunk *count* but on the exact boundary between `ours` and `theirs` content for every hunk.

### Proof of Concept
1. On the "ours" branch, add a file containing:
```
function foo() {
  // =======
  return 1
}
```
2. On the "theirs" branch, modify the same lines differently so a merge conflict results in:
```
<<<<<<< ours
function foo() {
  // =======
  return 1
}
=======
function foo() {
  return 2
}
>>>>>>> theirs
```
3. `extractConflictHunks` scans the "ours" collection loop, hits the comment line `// =======`... actually note the regex requires the *entire* line to be exactly `=======` (no leading `//`), so use a genuine standalone divider line instead of a comment, e.g. a Markdown or plain-text banner of exactly `=======` inside the "ours" content. `extractConflictHunks` treats this line as the separator, ending `oursContent` early and folding the real separator plus true "theirs" content into `theirsContent`.
4. Invoke Copilot conflict resolution on this file; the model reasons over the corrupted `oursContent`/`theirsContent` split and returns a `resolvedContent`.
5. `reassembleResolvedFile` splices that resolution into the *entire* real `<<<<<<<`…`>>>>>>>` block (since its own lookahead only needs one `=======`-like line before the real `>>>>>>>`), producing a final file whose content differs from what a correct, consistent parse of "ours" vs "theirs" would have produced — and this gets written to disk and can be committed by the user without any warning.

**Note on verification limits:** I was not able to execute the code to confirm the exact byte-for-byte output difference (no runtime/tooling access in this mode); the divergence is derived from static analysis of the two parsing functions cited above. Recommend a Devin session with the sandbox to write a unit test reproducing this exact scenario against `extractConflictHunks` and `reassembleResolvedFile` to confirm the corrupted splice.
