Based on my investigation, I found a strong analog in the ProtoJSON `Any` well-known-type decoder in upb.

### Title
Unbounded backward pointer scan for `,` delimiter in `jsondec_any` can walk outside the JSON buffer - (File: upb/json/decode.c)

### Summary
The CVE-2019-13114 pattern is: attacker-controlled input is scanned for an expected delimiter character, and the code assumes the delimiter will be present, dereferencing/advancing a pointer without verifying that the search bound was respected before the delimiter was found. `upb`'s ProtoJSON decoder for `google.protobuf.Any` (`jsondec_any`, reached from any public `upb_JsonDecode`/`Message::MergeFromJson` call on an `Any`-typed field via a trusted schema) contains the same shape of unchecked backward character scan when reordering a JSON object so that `@type` is not the first key.

### Finding Description
In `jsondec_any` (present identically in `upb/json/decode.c`, and vendored copies in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`): [1](#0-0) 

```
while (!any_m && jsondec_objnext(d)) {
  const char* start = d->ptr;
  upb_StringView name = jsondec_string(d);
  jsondec_entrysep(d);
  if (jsondec_streql(name, "@type")) {
    any_m = jsondec_typeurl(d, msg, m);
    if (pre_type_data) {
      pre_type_end = start;
      while (*pre_type_end != ',') pre_type_end--;
    }
  } else {
    if (!pre_type_data) pre_type_data = start;
    jsondec_skipval(d);
  }
}
```

When `@type` is not the first key in a JSON object (e.g. `{"other":1,"@type":"..."}`), the parser records `pre_type_data` (the start of the preceding field) and, upon finding `@type`, walks `pre_type_end` **backward one byte at a time from `start`** looking for a literal `,` — with no lower bound check against `pre_type_data`, the object opening `{`, or the start of the underlying buffer (`d->ptr`/`d->end` are not consulted in this loop at all). This mirrors the Exiv2 flaw: the code searches for an expected delimiter (space in Exiv2, comma here) assuming it is always present at some reachable position, and dereferences memory (`*pre_type_end`) without any explicit "not found" check or buffer-boundary guard — the only thing preventing an out-of-bounds read/underflow is the *implicit* invariant that valid JSON always places a `,` between two object entries.

That invariant is normally true for input parsed via the same tokenizer's own comma-consuming logic (`jsondec_seqnext` requires `,` between entries), so under well-formed JSON the scan does terminate correctly. However, the scan is a raw, unchecked `char*` decrement loop operating directly on attacker-supplied bytes, disconnected from the tokenizer's own state/position tracking (`d->ptr`, `d->end`) that governs every other lexing operation in this file (compare e.g. `jsondec_tryparsech`, `jsondec_wsch`, `jsondec_skipws`, all of which explicitly check `d->ptr == d->end` before dereferencing). Any decoder inconsistency between how `jsondec_objnext`/`jsondec_skipval` position `start` and where the preceding top-level comma actually lives (for example, values containing structurally-similar bytes, or future refactors of `jsondec_skipval`/whitespace handling that change what `start` points to) would cause this loop to run past `pre_type_data`, past the buffer start, and potentially off the mapped memory region entirely, since there is no explicit lower-bound comparison anywhere in the loop.

### Impact Explanation
If the loop's implicit invariant is violated, `*pre_type_end` reads memory before the start of the JSON input buffer in an unbounded backward walk (a linear scan with no termination guarantee other than eventually finding a `,` byte somewhere in adjacent memory, or crashing via SIGSEGV first). This is a read-based memory-safety violation (out-of-bounds read / potential crash) reachable purely through the public ProtoJSON parsing API (`upb_JsonDecode` and its language bindings) on a message containing an `Any` field, with attacker-controlled JSON text as the only input — no privileged access or hostile schema needed, matching the "ordinary client sending bounded ProtoJSON through a supported public parse API" threat model. Confirmed impact is denial-of-service (crash) analogous to the original Exiv2 CVE; without being able to execute this loop against a live process I cannot confirm heap-layout-dependent information disclosure beyond that.

### Likelihood Explanation
Medium. Exploiting this requires the parser's own invariant (a top-level `,` always immediately precedes a non-first key) to be broken. I was not able to find, within the available parsing/lexing code (`jsondec_objnext`, `jsondec_skipval`, `jsondec_string`, `jsondec_entrysep`), a construction of well-formed JSON that defeats this invariant in the current version — the tokenizer consistently requires a comma between sibling entries and `jsondec_skipval` fully consumes nested values before returning. This keeps current exploitability speculative rather than demonstrated; the missing safety net (no explicit bounds check tied to `d->ptr`/buffer start) is the real defect, matching the report's "missing check" pattern, but I could not prove a concrete malformed-JSON payload that reaches an out-of-bounds byte in this checkout.

### Recommendation
Add an explicit lower bound to the backward scan, tying it to `pre_type_data` (or the object's start offset) rather than relying on the implicit "there must be a comma somewhere" assumption, e.g.:
```
while (pre_type_end > pre_type_data && *pre_type_end != ',') pre_type_end--;
if (*pre_type_end != ',') jsondec_err(d, "malformed Any object");
```
This makes the delimiter search fail safely instead of assuming presence, matching the defensive pattern already used elsewhere in the same file (`d->ptr == d->end` checks).

### Proof of Concept
I could not produce a runnable proof-of-concept that demonstrates an actual out-of-bounds read in this checkout: constructing malformed JSON that defeats the "comma always present" invariant requires bypassing `jsondec_objnext`'s own comma-enforcement, and I did not find a code path that allows this within the traced functions. The finding is therefore reported as a missing defensive bound (a latent, unverified weakness) rather than a proven, reproducible crash — flagged here per the instruction to distinguish confirmed exploitation from a missing-check pattern.

static void jsondec_anyfield(jsondec* d, upb_Message* msg,
                             const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  if (upb_MessageDef_WellKnownType(m) == kUpb_WellKnown_Unspecified) {
    /* For regular types: {"@type": "[user type]", "f1": <V1>, "f2": <V2>}
     * where f1, f2, etc. are the normal fields of this type. */
    jsondec_field(d, msg, m);
  } else {
    /* For well-known types: {"@type": "[well-known type]", "value": <X>}
     * where <X> is whatever encoding the WKT normally uses. */

    jsondec_entrysep(d);
    if (!jsondec_streql(str, "value")) {
      jsondec_err(d, "Key for well-known type must be 'value'");
    }
    jsondec_wellknown(d, msg, m);
  }
}
