### Title
DKG confirmation reuse of cached FROST nonce seed can expose validator key shares - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
`SigningProtocol::preprocess_internal` persists one FROST `CachedPreprocess` per `(context, attempt)` and reloads that same seed for every call to `share_internal` / `complete`. Reuse of the cached seed regenerates the same nonce commitments and underlying nonces. If two executions under the same context differ in either participant preprocesses or the signed message, the resulting shares disclose the signer's secret key share through standard Schnorr/FROST nonce-reuse algebra.

### Finding Description
`preprocess_internal` stores an encrypted 32-byte `CachedPreprocess` under only `self.context`, then reconstructs an `AlgorithmSignMachine` with `AlgorithmSignMachine::from_cache` every time it is invoked.

Relevant flow:

- The DB key is `CachedPreprocesses: (context) -> [u8; 32]`.
- If no cache exists, a fresh machine is created and only its seed is stored.
- On every subsequent call, the same seed is decrypted and passed to `from_cache`.
- `share_internal` calls `preprocess_internal` again immediately before calling `machine.sign(preprocesses, msg)`.
- `DkgConfirmer::complete` calls `share_internal` again after `DkgConfirmer::share` has already been used, re-executing signing with the same cached nonce seed.

The surrounding comments acknowledge that re-execution relies on fixed nonces and that safety requires the received preprocesses and message to remain identical. However, `SigningProtocol` itself does not persist or verify a digest of the exact `serialized_preprocesses`, `participants`, or `msg`; it only keys the cache by context. For `DkgConfirmer`, the context is solely `(b"DkgConfirmer", attempt)`, while the message contains the mutable `KeyPair` and `removed` set and the preprocess map is supplied separately.

A second call for the same context but with different public preprocess bytes or `key_pair` therefore produces a second signature share using the same secret nonce.

### Impact Explanation
FROST signature shares are Schnorr-like equations over the signer's secret nonce and interpolated secret key share. Reusing the same nonce commitments/nonces across two distinct binding-factor/message challenges leaks the underlying private share:

```text
share₁ = nonce + c₁ · secret_share
share₂ = nonce + c₂ · secret_share

secret_share = (share₁ - share₂) / (c₁ - c₂)
```

For the coordinator-side DKG confirmation protocol, the exposed value is the validator's private key share/private key material used in the MuSig confirmation. That key is the validator root of trust and can enable unauthorized signatures within the affected validator-set context if combined according to the protocol's aggregation rules.

This meets the analog criteria because the failure is reached by untrusted preprocess bytes, participant set changes, or a changed key-pair message; no malicious validator assumption is required beyond supplying protocol messages.

### Likelihood Explanation
The code intentionally reuses the cached preprocess seed and relies on an external invariant that every later signing attempt under that context is byte-for-byte equivalent. There is no local check enforcing that invariant:

- No stored transcript/message digest is compared before signing again.
- `share_internal` accepts attacker-controlled serialized preprocesses and parses them immediately before signing.
- The message is computed at call time and is not bound into the cached-preprocess record.
- `complete` re-executes signing instead of using the state generated by `share`, making duplicate signing an explicit design path.

The issue requires another signing execution under the same context with a distinct binding relation or message. The comments describe the intended BFT-level invariant, but the production code does not itself enforce it, and any edge case, recovery path, inconsistent state, duplicate processor message, or alternative key-pair value reaching `share_internal` converts deterministic nonce reuse into key-share disclosure.

### Recommendation
Do not reuse a `CachedPreprocess` unless all signing inputs are cryptographically bound and proven identical.

At minimum:

1. Store the selected participant list, exact serialized preprocesses, and final message digest alongside the cached seed.
2. Before `machine.sign`, require all of those values to match the originally published/signing inputs.
3. Never call `sign` more than once with the same cached seed; persist the resulting `AlgorithmSignatureMachine` state/signature share instead of re-deriving a sign machine in `complete`.
4. If re-execution is required for recovery, cache the generated signature share after first use and return that cached share on identical requests; error on any altered preprocess map or message.
5. Include `context`, validator set, participant list, preprocess digest, and message digest in the persisted record to prevent cross-protocol or cross-message ambiguity.

### Proof of Concept
The vulnerable sequence is directly represented by the production control flow:

```rust
// coordinator/src/tributary/signing_protocol.rs
fn share_internal(
  &mut self,
  participants: &[...],
  serialized_preprocesses: HashMap<Participant, Vec<u8>>,
  msg: &[u8],
) -> ... {
  // Reloads the same CachedPreprocess whenever self.context repeats.
  let machine = self.preprocess_internal(participants).0;

  // Parses externally supplied preprocess bytes.
  let mut preprocesses = HashMap::new();
  for participant in participants {
    preprocesses.insert(
      participant,
      machine.read_preprocess(
        &mut serialized_preprocesses.remove(&participant).unwrap().as_slice(),
      )?,
    );
  }

  // Produces a Schnorr/FROST share using the regenerated nonce.
  let (_, share) = machine.sign(preprocesses, msg)?;
}
```

And `DkgConfirmer` can invoke this path repeatedly for the same `(b"DkgConfirmer", attempt)` context:

```rust
// coordinator/src/tributary/signing_protocol.rs
fn signing_protocol(&mut self) -> DkgConfirmerSigningProtocol<'_, T> {
  let context = (b"DkgConfirmer", self.attempt);
  SigningProtocol { key: self.key, spec: self.spec, txn: self.txn, context }
}

pub(crate) fn complete(...) -> ... {
  let machine = self
    .share_internal(preprocesses, key_pair)
    .expect("trying to complete a machine which failed to preprocess")
    .0;
}
```

If the first execution signs `(preprocesses_A, key_pair_A)` and a second execution under the same attempt signs `(preprocesses_B, key_pair_B)` where either value changes the challenge, the two public signature shares differ only in their challenge-derived terms. Subtracting the two shares and multiplying by the inverse of the challenge difference recovers the signer's private share, as shown by the equation above.
