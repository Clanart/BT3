### Title
Unbounded Python recursion in `DataStore.get_nodes_for_file()` writing untrusted DataLayer trees can crash the DataLayer/full-node process - (File: `chia/data_layer/data_store.py`)

### Summary
`DataStore.get_nodes_for_file()` recursively walks a Merkle tree with plain Python `await self.get_nodes_for_file(...)` calls, one per child, and has no depth bound. This mirrors the Exiv2 `printTiffStructure` bug class: an attacker-influenced, arbitrarily deep tree structure drives a recursive tree-walking function past the interpreter's recursion/stack limits, causing a crash (Denial of Service). This function is reached from `insert_from_delta_file()` right after inserting data downloaded from a DataLayer mirror/plugin server, which the codebase's own documentation explicitly treats as untrusted input.

### Finding Description
`get_nodes_for_file()` recurses once per level of tree depth with no guard: [1](#0-0) 

Contrast this with the sibling ingestion path `insert_into_data_store_from_file()`, which relies on the Rust `chia_rs.datalayer` `MerkleBlob` construction to reject overly deep or malformed trees via `RecursionDepthExceededError`/`CycleFoundError`, as demonstrated by the test suite itself: [2](#0-1) 

However, `get_nodes_for_file()` is not that ingestion path — it is the *output/write* path, invoked from `insert_from_delta_file()` immediately after a delta file has been successfully committed, to generate a full-tree `.dat` file for future serving/mirroring: [3](#0-2) 

Because the just-inserted root did pass the Rust `MerkleBlob` construction checks (bounded depth), the depth of a single successfully-inserted tree is currently bounded by whatever depth the Rust layer permits before raising `RecursionDepthExceededError`. The project's own test comments show this bound is exercised at real, large depths (`1000`, `100_000`) and treated as an expected-error boundary rather than a hard architectural ceiling in Python code: [4](#0-3) 

The documentation for the module confirms that downloaded delta/full files originate from mirrors or plugins and are explicitly untrusted until the local root is rebuilt and matched against the wallet-advertised chain root — but the *write-out* helper (`get_nodes_for_file`) applies no independent depth bound of its own, unlike the tests' own iterative `create_graph_util()` helper, which was deliberately rewritten to avoid Python recursion limits ("Implemented iteratively to avoid Python recursion limits for deep graphs"): [5](#0-4) [6](#0-5) 

If the Rust-side recursion limit (`RecursionDepthExceededError`) is ever higher than Python's own recursion ceiling (Python's default `sys.getrecursionlimit()` is 1000, and `get_nodes_for_file` is `async`, adding extra frames per level via the coroutine/await machinery), a maliciously crafted but still Rust-acceptable deep tree could pass insertion yet blow the Python call stack during the subsequent `write_tree_to_file()`/`get_nodes_for_file()` call, raising an uncaught `RecursionError`.

### Impact Explanation
A crash in `get_nodes_for_file()` raises an unhandled `RecursionError` inside the DataLayer service's background sync loop (`update_subscription()` / `fetch_and_validate()`), which is wrapped in broad exception handling at the outer service loop but still represents an uncontrolled crash/DoS of the affected coroutine and repeatedly disrupts DataLayer sync for that store id. Because DataLayer sync is a routine automated background process reachable purely by subscribing to a store hosted by a malicious/compromised mirror or plugin server, this is a transaction/data-processing halt for the DataLayer subsystem without requiring any elevated privileges — consistent with the "spend-triggered transaction-processing halt" class of impact called out in scope, adapted to the DataLayer client processing path.

### Likelihood Explanation
Exploitability requires an attacker to control (or compromise) a DataLayer mirror or plugin download source that a victim node is configured to sync from, and to craft a tree whose depth is large enough to be accepted by the Rust `MerkleBlob` bound but exceeds Python's practical async recursion capacity. This is a moderately involved but realistic scenario given DataLayer's mirror/plugin trust model is explicitly untrusted-by-design (per the module's own documentation), and no additional protections exist in `get_nodes_for_file()` beyond what the Rust insertion path already enforces.

### Recommendation
Rewrite `get_nodes_for_file()` (and any other Python-side recursive Merkle-tree walkers reachable on data ingested from untrusted mirrors/plugins) to use an explicit iterative stack, matching the pattern the test suite already uses in `create_graph_util()`, and/or enforce an explicit maximum tree depth check before recursing, independent of the Rust-side bound.

### Proof of Concept
Conceptual PoC (not run, since only static/index access was available):
1. Stand up a malicious DataLayer mirror/plugin server for a store id the victim node subscribes to.
2. Construct a binary "line graph" delta/full file at a depth just under the Rust `MerkleBlob` construction recursion limit (as exercised by `test_insert_into_data_store_from_file_line_graph_depth` with `depth=100_000`, which is accepted rather than rejected for smaller depths) but at a depth known to exceed Python's coroutine recursion capacity.
3. Have the victim node's `fetch_and_validate()`/`insert_from_delta_file()` download and successfully insert this delta file (it passes Rust-side checks).
4. Because `target_generation - existing_generation <= maximum_full_file_count - 1`, the node then calls `write_tree_to_file()` → `get_nodes_for_file()` on the newly inserted deep tree, triggering unbounded Python recursion and a `RecursionError` crash of that sync task.

**Note on uncertainty:** I was unable to directly view `write_tree_to_file()`'s exact body or confirm the precise numeric relationship between the Rust `RecursionDepthExceededError` threshold and Python's coroutine-adjusted recursion limit within the available index snippets, so the exact depth needed to trigger a Python-side crash (versus being rejected earlier by the Rust insertion check) is not fully verified from the indexed source alone. A Devin session with full repository access would be needed to confirm the exact threshold values and validate the PoC end-to-end.

    async def get_nodes_for_file(
        self,
        root: Root,
        node_hash: bytes32,
        store_id: bytes32,
        deltas_only: bool,
        delta_file_cache: DeltaFileCache,
        tree_nodes: list[SerializedNode],
    ) -> None:
        if deltas_only:
            if delta_file_cache.seen_previous_hash(node_hash):
                return

        raw_index = delta_file_cache.get_index(node_hash)
        raw_node = delta_file_cache.get_raw_node(raw_index)

        if isinstance(raw_node, chia_rs.datalayer.InternalNode):
            left_hash = delta_file_cache.get_hash_at_index(raw_node.left)
            right_hash = delta_file_cache.get_hash_at_index(raw_node.right)
            await self.get_nodes_for_file(root, left_hash, store_id, deltas_only, delta_file_cache, tree_nodes)
            await self.get_nodes_for_file(root, right_hash, store_id, deltas_only, delta_file_cache, tree_nodes)
            tree_nodes.append(SerializedNode(False, bytes(left_hash), bytes(right_hash)))
        elif isinstance(raw_node, chia_rs.datalayer.LeafNode):
            tree_nodes.append(
                SerializedNode(
                    True,
                    raw_node.key.to_bytes(),
                    raw_node.value.to_bytes(),
                )
            )
        else:
            raise Exception(f"Node is neither InternalNode nor TerminalNode: {raw_node}")

@pytest.mark.anyio
@pytest.mark.parametrize("depth", [1000, 100_000])
async def test_insert_into_data_store_from_file_line_graph_depth(
    data_store: DataStore,
    store_id: bytes32,
    tmp_path: Path,
    depth: int,
) -> None:
    # Binary "line graph":
    #   1 -> leaf_1, 2
    #   2 -> leaf_2, 3
    #   ...
    #   depth -> leaf_depth, leaf_end
    #
    # This stresses depth/stack handling while staying strictly binary.
    #
    # Node IDs:
    # - internal nodes: 1..depth
    # - per-level leaf nodes: (depth+1)..(2*depth)
    # - final leaf: (2*depth+1)
    internal_first = 1
    internal_last = depth
    leaf_base = internal_last + 1
    leaf_end = (2 * depth) + 1

    edges: list[tuple[int, int]] = []
    for i in range(internal_first, internal_last):
        # Order matters: first edge is left child, second edge is right child.
        edges.append((i, leaf_base + (i - internal_first)))  # unique leaf for this internal node
        edges.append((i, i + 1))  # next internal node

    # last internal points to its leaf and a final leaf
    edges.append((internal_last, leaf_base + (internal_last - internal_first)))
    edges.append((internal_last, leaf_end))

    filename = tmp_path / f"line_graph_depth_{depth}.dat"
    root_hash = create_graph_util(filename, edges)

    with pytest.raises(chia_rs.datalayer.RecursionDepthExceededError):
        await data_store.insert_into_data_store_from_file(store_id, root_hash, filename)
