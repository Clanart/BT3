### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` allows stack-overflow DoS via crafted `AccountUpdate`/`AccountCreation` transaction or `kaia_decodeAccountKey` RPC call - (File: `blockchain/types/accountkey/account_key_role_based.go`, `blockchain/types/accountkey/account_key_serializer.go`)

### Summary
`AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` recursively decode account keys with no depth limit. Because `AccountKeyRoleBased` can contain another `AccountKeySerializer`-wrapped key, and the "no nested composite key" rule (`ErrNestedCompositeType`) is only enforced *after* decoding is complete (in `CheckInstallable`/`CheckUpdatable`), an attacker can submit RLP bytes encoding thousands of nested `RoleBased` keys. The decoder recurses once per nesting level with no bound, driving the Go call stack to its limit and crashing the process — the same root-cause class as the Scriban `ExpressionDepthLimit`-is-non-enforcing bug: a semantic/validation-time guard exists, but the recursive decoder itself has no structural limit and runs to completion (or crash) before that guard is ever consulted.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a key type tag and then recursively decodes the key body: [1](#0-0) 

When the decoded type is `AccountKeyTypeRoleBased`, `s.Decode(serializer.key)` invokes `AccountKeyRoleBased.DecodeRLP`, which for every element of the role list re-invokes `rlp.DecodeBytes` on a fresh `AccountKeySerializer`: [2](#0-1) 

If that inner serializer is itself typed `RoleBased`, the cycle repeats. Nothing in this decode path checks nesting depth or the `IsCompositeType()`/`ErrNestedCompositeType` rule. That rule is only enforced afterward, in `CheckInstallable`/`CheckUpdatable`: [3](#0-2) 

Exactly as in the Scriban advisory — where `EnterExpression()`'s depth check only logs and never stops recursion — here the equivalent guard (`ErrNestedCompositeType`) exists but is applied too late: after the full recursive `DecodeRLP` walk has already completed (or crashed the process). The recursion depth is fully attacker-controlled by the byte-string nesting depth supplied in the transaction's account-key payload, and there is no `RuntimeHelpers`-style stack-guard or an explicit maximum-nesting counter anywhere in the RLP account-key decode path.

This decode path is reached by:
1. Decoding `KeyData`/`Key` fields of `TxTypeAccountCreation`/`TxTypeAccountUpdate` transactions (`accountkey.NewAccountKeySerializer(); rlp.DecodeBytes(serialized.KeyData, serializer)`), executed whenever any node RLP-decodes an incoming raw transaction (tx pool admission, p2p propagation, block processing) — reachable by any unprivileged transaction sender: [4](#0-3) [5](#0-4) 
2. The public RPC method `kaia_decodeAccountKey`, which takes arbitrary attacker-supplied hex bytes and RLP-decodes them directly into an `AccountKeySerializer`: [6](#0-5) 

### Impact Explanation
A crafted payload (nested `RoleBased` account keys, e.g. thousands of levels deep) triggers unbounded Go-stack recursion during RLP decoding. Go's runtime response to stack exhaustion is an unrecoverable fatal error (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`) that terminates the process and cannot be caught by any `recover()`. Since this path is exercised during transaction-pool admission (`AddRemote`) and block/transaction processing on every full node, a single malicious transaction or a single RPC call can crash any node that processes it — a network-wide, remotely triggerable denial of service requiring no privileges, matching CWE-674 and the severity class of the referenced advisory.

### Likelihood Explanation
High. The vulnerable code path is reached purely by constructing a byte string (no valid signature or balance is strictly required to reach the RLP decode step, since decoding happens before/while validating the transaction), or via a single public RPC call (`kaia_decodeAccountKey`) that needs no transaction at all. The existing `ErrNestedCompositeType` check demonstrates the team is already aware nested composite keys are dangerous, but the check is structurally incapable of preventing the recursion because it only runs after decode.

### Recommendation
- Add an explicit nesting-depth counter/limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., pass a decode depth via context or a package-level counter) and return an error immediately once a small bound (e.g., 1, since nested `RoleBased` is never valid) is exceeded — enforce the "no composite-in-composite" rule *during* decode, not only in `CheckInstallable`/`CheckUpdatable`.
- Alternatively/additionally, bound total recursion using `debug.SetMaxStack` awareness or an explicit iterative/depth-tracked decoder instead of naive recursive `rlp.DecodeBytes` calls.
- Add regression tests using a payload nested deep enough to previously overflow the stack (tens of thousands of levels), asserting a clean `ErrNestedCompositeType`/decode error rather than a process crash.

### Proof of Concept
Conceptually (mirroring the Scriban PoC pattern):
1. Build an `AccountKeySerializer` for `AccountKeyTypeRoleBased` whose single role slot is itself the RLP encoding of another `RoleBased` serializer, and repeat this nesting N times (N large, e.g. 50,000), using `AccountKeyRoleBased.EncodeRLP` recursively: [7](#0-6) 
2. Submit the resulting bytes either as the `Key`/`KeyData` field of an RLP-encoded `TxTypeAccountUpdate`/`TxTypeAccountCreation` transaction via `eth_sendRawTransaction`, or directly as the argument to `kaia_decodeAccountKey`.
3. On decode, `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurse N times before any `CheckInstallable`/`ErrNestedCompositeType` validation is ever reached, exhausting the goroutine stack and crashing the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
