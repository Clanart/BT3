### Title
Reward token accounting in `ManualCompound.compound()` uses raw contract balance instead of before/after delta, allowing theft of other users' unclaimed rewards - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` determines the amount of reward tokens to convert/lock/forward to the caller by reading the contract's entire raw token balance (`IERC20(_tokenAddress).balanceOf(address(this))`) rather than measuring the balance change caused by the caller's own claim. This is the same bug class as TREC-3: using `balanceOf(address(this))` to size a reward payout allows any value sitting in the contract — whether from another user's leftover/unswept claim, a stuck partial transfer, or a token sent directly to the contract — to be attributed to whichever unprivileged wallet next happens to call the function.

### Finding Description
`compound()` first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`, which pulls the caller's pending rewards from the various `BaseRewardPool`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder` contracts into `ManualCompound`. It then, for each configured reward token, reads: [1](#0-0) 
`receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` and forwards the *entire* balance to `msg.sender` (via convertor, locker, helper, or direct transfer). The same pattern is used for non-compoundable rewards: [2](#0-1) 

Because the amount is derived from the absolute balance rather than a before/after delta scoped to the current call, several unprivileged-wallet scenarios exist:
- If a prior `compound()` call left dust in the contract (e.g., due to rounding, a reward token whose `convertFor`/`depositFor`/`lockFor` target reverts partially, or a reward claimed for one `_lps`/`_rewards` combination but not fully consumed), the next caller's `compound()` invocation will sweep that leftover balance along with their own legitimately claimed rewards.
- Any wallet can transfer reward tokens (or tokens matching an `addReward`-registered `tokenAddress`) directly to the `ManualCompound` contract address, then call `compound()` (even with an empty/no-op `_lps`/`_rewards` claim) to have those tokens swept, converted, or locked in their own name.
- Two users calling `compound()` in quick succession are not isolated from each other: whichever transaction executes second inherits any token balance not yet consumed by the first, since there is no accounting for "what was claimed by this specific call".

### Impact Explanation
This allows direct theft of reward tokens that belong to other users or that are otherwise queued in the rewards system, satisfying the "direct theft of user funds" / "theft of unclaimed yield" bar. Because `ManualCompound` forwards the swept balance into `convertFor`, `lockFor`, or `depositFor` on behalf of `msg.sender`, or transfers it directly, an attacker can permanently redirect funds that should have gone to other users' claims.

### Likelihood Explanation
Any unprivileged wallet can call `compound()` at will; no special role is required. The trigger conditions (dust left in the contract from prior imperfect calls, or a plain direct token transfer to the `ManualCompound` address) require no privileged action and can be engineered by any user, making this a realistically reachable path from an ordinary wallet.

### Recommendation
Track the balance of each reward token immediately before pulling rewards via `multiclaimOnBehalf` and compute `receivedBalance` as the post-call balance minus the pre-call balance, mirroring the fix already applied elsewhere in the codebase (e.g., `WombatStaking._toMasterWomAndSendReward`, which computes `womRewards = IERC20(wom).balanceOf(address(this)) - womBeforeBalance` [3](#0-2) ). Apply the same before/after delta pattern to both the compoundable-reward loop and the non-compoundable "return to caller" loop in `ManualCompound.compound()`.

### Proof of Concept
1. Attacker transfers 1 WOM (a token registered via `addReward`) directly to the `ManualCompound` contract address.
2. Attacker calls `compound([], [], 0, 0, false)` (or with a minimal legitimate `_lps`/`_rewards` claim of near-zero value) as `msg.sender`.
3. Inside `compound()`, `receivedBalance = IERC20(wom).balanceOf(address(this))` reads the full 1 WOM donated in step 1 plus any dust already present, and forwards/converts/locks it entirely to the attacker via `IConverter(_convertor).convertFor(...)`, `ILocker(_locker).lockFor(...)`, or `safeTransfer(msg.sender, receivedBalance)`, none of which verify that this balance originated from the attacker's own claim in this call.
