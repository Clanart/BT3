### Title
Change remainder below the dust threshold is silently burned as miner fee on every transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Yieldoor bug class is: a mul/div state update truncates a sub-unit remainder on every invocation, so value that should accrue to honest users is permanently lost whenever interactions occur — an attacker can force the loss repeatedly with public inputs. The same shape exists in `bitcoin-serai`'s transaction builder: when the leftover input value after payments and fees falls below `DUST` (546 sats), `SignableTransaction::new` drops the change output entirely, so the entire remainder — up to 545 sats per transaction — is converted into excess miner fee instead of being accumulated or returned. Each constructed transaction can silently burn a non-trivial fraction of a low-decimal denomination (the analog of "wbtc has few decimals, so sub-unit loss is real money").

### Finding Description
In `SignableTransaction::new`, the change path computes the change value as `input_sat - payment_sat - fee_with_change` and only emits a change output if it satisfies `value >= DUST`:

```rust
// networks/bitcoin/src/wallet/send.rs:224-234
if let Some(change) = change {
  let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
  let fee_with_change = fee_per_vbyte * vbytes_with_change;
  if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
    if value >= DUST {
      tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
      weight = weight_with_change;
      needed_fee = fee_with_change;
    }
  }
}
```

If the leftover is 1–545 sats, no change output is created and `needed_fee` remains `fee_per_vbyte * vbytes` (the no-change fee). The actual fee paid by the signed transaction is `sum(inputs) - sum(outputs)` (`fee()`, lines 138-141), so the entire sub-dust remainder is paid to miners. There is no carry-forward mechanism: the remainder is not credited to the multisig, not accumulated into a future transaction, and not reported as an error — exactly the "remainder < 1 unit of account is truncated away per interaction" pattern of the source report, mapped onto satoshis.

Additionally, the minimum-fee guard uses truncating integer division `(DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211), which rounds the required minimum down by up to ~1 sat — the same class of truncation error, weakening a correctness bound.

An external party can influence this via public inputs: anyone can send Bitcoin transactions to the multisig address, choosing output values. By paying the wallet with outputs sized so that `input - payments - fee` lands in `[1, DUST)`, each spend the wallet performs donates the remainder to miners. Since change outputs below dust are also economically unspendable, discarding them is partially justified, but the loss is unbounded in aggregate across repeated transactions and is never surfaced to the caller beyond `fee()`.

### Impact Explanation
Every transaction the multisig signs can burn up to 545 sats of wallet funds as unintended excess fee, with no change returned and no error raised. For a high-throughput multisig (the Serai processor signs Bitcoin transactions continuously), the loss compounds per transaction, mirroring the source report's "depositor may not be able to take any profits at all or may receive reduced profits" — here, the multisig's balance is reduced by the truncated remainder each time. Unlike the report's benefit to no one, burned sats transfer to miners.

### Likelihood Explanation
Medium. The remainder landing in `[1, 546)` requires `input_sat ≡ payment_sat + fee_with_change (mod ~anything)` within the dust window — for arbitrary input values and fee rates this occurs for a substantial fraction of transactions (the dust window is only ~7× smaller than the ~4096-sat range of typical leftover magnitudes, and inputs arriving at the address are attacker-influenced). No secret access is needed; the triggering inputs are Bitcoin transactions anyone can send to the multisig's address. This is documented behavior in the doc comment ("any leftover funds will be sent to it if the leftover funds exceed the minimum output amount"), which weakens severity but does not eliminate the silent loss or the truncated min-fee check.

### Recommendation
- If `0 < value < DUST`, either roll the remainder into `needed_fee` accounting explicitly (report it distinctly from the feerate-derived fee so callers/auditors see the burn), or accumulate it by adding it to a future change output rather than dropping it silently.
- Consider `Err`ing on sub-dust change when the remainder is economically significant relative to the payments, so the integrator can merge inputs instead of donating the remainder.
- Use ceiling division in the minimum relay fee check: `(DEFAULT_MIN_RELAY_TX_FEE * vbytes + 999) / 1000` so the guard never under-prices the relay minimum by a fraction of a sat.

### Proof of Concept
Conceptual, directly from `SignableTransaction::new` semantics:

1. Multisig holds a `ReceivedOutput` worth `input_sat = 10_000` sats.
2. `payments` = `[(script, 9_000)]`, `change = Some(change_script)`, `fee_per_vbyte = 1`, and suppose `vbytes = 200`, `vbytes_with_change = 234`.
3. `needed_fee = 200`; min-fee check: `200 >= (1000 * 200)/1000 = 200` — passes.
4. Change: `value = 10_000 - 9_000 - 234 = 766 ≥ 546` → change output created, `needed_fee = 234`. Actual fee = 234. Fine.
5. Now repeat with `input_sat = 9_780`: `value = 9_780 - 9_000 - 234 = 546 ≥ 546` → returned. With `input_sat = 9_779`: `value = 545 < 546` → no change output pushed; `needed_fee` stays `200`.
6. `fee() = 9_779 - 9_000 = 779` sats — **545 sats beyond the intended 234-sat fee are burned to miners**, and the caller-visible `needed_fee` reports only 200, understating the actual cost by 545 sats.
7. An attacker funding the multisig with dust-window-sized outputs can repeat this on every spend; each transaction loses up to 545 sats with no remainder carried forward — the satoshi-level analog of `newTotalBorrows` never incrementing because the accrued interest is below 1 wei.

Caveat: I could not verify whether downstream callers (outside the in-scope `networks/bitcoin` tree) reconcile `fee()` against `needed_fee()`; if they do and abort, the impact is a DoS on signing rather than silent loss.
