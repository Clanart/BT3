Based on the investigation, the closest analog to the report's "broken invariant" (an escape-hatch flag that bypasses an intended protective check when applied to attacker-influenced input) is the `allowFileProtocol` flag used during submodule updates in GitHub Desktop's checkout pipeline.

### Title
Escape-hatch `allowFileProtocol` flag can re-enable `file://` submodule cloning, bypassing Git's local-file-exfiltration protection - (File: `app/src/lib/git/submodule.ts`)

### Summary
Git disabled `file://`/local-path submodule URLs by default (`protocol.file.allow`) specifically to stop a malicious repository's `.gitmodules` from pointing a submodule at an arbitrary local path on the victim's machine and having it cloned into the working tree during `submodule update --init --recursive`. Desktop's checkout code contains an explicit escape hatch, `allowFileProtocol`, that re-adds `-c protocol.file.allow=always` to the submodule-update invocation, functionally identical in spirit to the `exit()` bypass described in the report: a flag meant for a narrow, trusted case that removes a safety check governing what content can be pulled into the user's tree.

### Finding Description
`checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts` accept an `allowFileProtocol: boolean = false` parameter and forward it into `updateSubmodulesAfterOperation`: [1](#0-0) [2](#0-1) 

`updateSubmodulesAfterOperation` conditionally injects `protocol.file.allow=always` before running `git submodule update --init --recursive`: [3](#0-2) 

This is exactly the class of check the git project added (in response to CVE-2022-39253) to stop a cloned/fetched repository's `.gitmodules` from instructing the local Git client to clone from `file:///arbitrary/local/path` — letting an attacker read files or directories that exist on the victim's machine, populate them into the working tree, and have their contents surfaced back to the attacker via a subsequent push, diff view, or commit. When `allowFileProtocol` is `true`, that protection is turned off for the whole `submodule update --init --recursive` invocation, meaning any submodule entry in the checked-out tree's `.gitmodules` — content that originates from a cloned/fetched repository the user does not control — can use a `file://` or local-path URL.

The tests confirm this exact mechanic is exercised for submodule initialization flows (`checkoutBranch(repository, branchWithSubmodule, null, undefined, true)`), and helper fixtures deliberately add submodules with `-c protocol.file.allow=always`: [4](#0-3) 

The existing guard (Git's own default deny of `protocol.file.allow`) is bypassed the moment any caller passes `true` for a checkout whose target ref/commit is not fully trusted (i.e., it came from a fetch of a remote or PR branch), because `.gitmodules` content is attacker-controlled once the ref is fetched — Desktop's flag operates repo-wide, not per-submodule-origin, so it cannot distinguish "a submodule I just added locally in this session" from "a submodule defined in a branch someone else pushed."

### Impact Explanation
If `allowFileProtocol=true` is reachable on any checkout path applied to a ref obtained from a remote/fetch (branch checkout, PR checkout, "checkout commit" from history/CI, etc.), an attacker who controls a repository or PR branch that the victim clones/checks out could point a submodule at a sensitive local path (e.g., another repository, a config directory, or a path under the user's home directory) and have Desktop silently `git clone` it into the working tree, disclosing local file/directory contents outside the intended repo boundary into version control, matching the "file read outside the repo" impact category.

### Likelihood Explanation
Likelihood depends entirely on whether production call sites (in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts`, both of which reference `checkoutBranch`/`checkoutCommit`) ever pass `allowFileProtocol=true` for checkouts of remote-sourced refs rather than only for locally-created submodule scenarios. I was not able to confirm the exact argument used at each call site within this session — this needs direct verification of those call sites before treating this as a confirmed, exploitable bug rather than a latent design risk.

### Recommendation
- Verify every call site of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` and ensure `allowFileProtocol=true` is only ever used for repositories/refs fully created or controlled locally by the current user (e.g., first-time local submodule add flows), never for checkouts sourced from a fetched remote branch, PR, or commit.
- Prefer validating `.gitmodules` submodule URLs against an allow-list of protocols (https/ssh) before invoking `submodule update`, rather than relying on a coarse, repo-wide `protocol.file.allow=always` override.
- Add regression tests asserting that checking out a remote/fetched branch containing a `file://` submodule URL fails closed (i.e., `allowFileProtocol` defaults to `false` for that code path).

### Proof of Concept
1. Attacker creates a public repository with a `.gitmodules` entry: `url = file:///home/victim/.ssh` (or any path likely to exist on a Desktop user's machine).
2. Victim clones/fetches the repository in GitHub Desktop and checks out the branch containing this `.gitmodules`.
3. If the checkout path in question is invoked with `allowFileProtocol=true` (per `app/src/lib/git/checkout.ts` → `app/src/lib/git/submodule.ts`), `git submodule update --init --recursive -c protocol.file.allow=always` clones the local path into the working directory.
4. The victim's local files are now tracked in the repository's working tree, and can be observed by the attacker if the victim later syncs/pushes/shares the branch, or simply inspected locally by anything watching the repo.

Given I could not fully confirm the production call-site arguments for `allowFileProtocol` in `app-store.ts`/`dispatcher.ts` within this session, I recommend a follow-up code review (or Devin session) specifically tracing all callers of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm whether `true` is ever passed for remote-sourced checkouts before treating this as a fully validated vulnerability.
