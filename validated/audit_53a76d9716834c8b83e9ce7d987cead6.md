### Title
Cached FROST preprocess reused across distinct signing operations under a context-insensitive key leaks the validator's secret key share - ([File: coordinator/src/tributary/signing_protocol.rs])

### Summary
The libcurl bug class — a security-scoped object (an authenticated connection) cached under an insufficiently specific lookup key and reused for a differently-parameterized operation — maps directly onto `SigningProtocol`'s `CachedPreprocesses` table. The cache key is only `self.context` (`(b"DkgConfirmer", attempt)`); it does not bind the participant set, the received preprocesses, or the message. `DkgConfirmer::complete` re-invokes `share_internal`, which deterministically regenerates the **same FROST nonces** from the cached seed and calls `machine.sign(preprocesses, msg)` a second time, even if the preprocesses or `key_pair` (and therefore `msg = set_keys_message(...)`) differ from the earlier `share` call. ### Finding Description
`preprocess_internal` stores the 32-byte ChaCha20 seed for a preprocess under `CachedPreprocesses::(context)` and loads it on every invocation, rebuilding identical nonces via `AlgorithmMachine::seeded_preprocess` → `Commitments::new` from `ChaCha20Rng::from_seed(seed)`. The doc-comment acknowledges nonce reuse "enables third-party recovery of your private key share" and asserts safety only from BFT ordering of messages — but the code signs **twice per attempt**: once in `share(preprocesses, key_pair)` and again inside `complete(preprocesses, key_pair, shares)`, each with caller-supplied `preprocesses` (untrusted bytes via `read_preprocess`) and a caller-supplied `key_pair` folded into `msg` by `set_keys_message`. The nonce cache key `("DkgConfirmer", attempt)` does not commit to either input, so two calls within one attempt reuse `d, e` while `rho` (bound to the preprocesses challenge) and `c` (bound to `msg`) may differ.

With shares `s = d + e·ρ + λ·x·c`, two observations `(s₁, s₂)` over the same nonces but different `(ρ, msg)` yield two linear equations in the unknowns `d, e, λ·x` — and since `ρ` and `c` are publicly computable, `λ·x` (the validator's MuSig secret share) is recoverable. The file's own TODO at lines 50–54 concedes the missing check that on-chain preprocesses match the presumed preprocess before publishing shares. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
Recovery of a validator's MuSig secret key share for the `DkgConfirmer` context, i.e., the validator-key path used to confirm DKG results on Substrate. Repeating across `t` validators (or combining with DKG-share equivalents) yields forgery of `set_keys_message` confirmations — concrete signing of an unintended message and key-share recovery, the exact impact the cache encryption (lines 104–114) is designed to prevent. [9](#0-8) 

### Likelihood Explanation
Trigger requires `share`/`complete` to be invoked twice for the same `attempt` with differing preprocesses or `key_pair`. The adversary-facing inputs — the `preprocesses` HashMap (deserialized via `read_preprocess`) and which preprocesses are BFT-finalized — are remote-controlled; a faulty validator can publish preprocesses for the same attempt in a way that makes the finalized set used by `complete` differ from the set presented at `share` time, or cause confirmation of a distinct `key_pair`. The safety argument in the header rests entirely on BFT delivering identical messages, but the code performs no equality check between the `share`-time and `complete`-time inputs before re-signing with the cached nonces. Confidence: **Medium** — I verified the double-sign path and context-insensitive cache key in code, but did not fully trace `handle.rs` to confirm how often divergent inputs reach both calls. [10](#0-9) [11](#0-10) 

### Recommendation
Bind the cached preprocess to everything it will sign over: derive the cache key as `(context, hash(sorted preprocesses), hash(msg))`, or cache the *published* preprocess bytes and `msg` alongside the seed and refuse to `sign` when either differs. Implement the acknowledged TODO — verify the preprocesses/first message on-chain match the presumed ones before emitting a share — and avoid re-running `sign` in `complete`; persist the signature machine or the emitted share from `share` instead.

### Proof of Concept
1. Validator set reaches attempt `a`; coordinator calls `DkgConfirmer::share(P, kp)` → nonces `(d,e)` from `CachedPreprocesses[("DkgConfirmer", a)]`, share `s₁ = d + e·ρ₁ + λ·x·c₁` broadcast.
2. `DkgConfirmer::complete(P', kp', S)` is invoked where `P'` differs in membership/order or `kp'` differs (distinct `set_keys_message`) → `share_internal` reloads the same seed → identical `d, e`, but `ρ₂ ≠ ρ₁` and/or `c₂ ≠ c₁`; emits `s₂ = d + e·ρ₂ + λ·x·c₂`.
3. Observer solves `s₁ - s₂ = e(ρ₁ - ρ₂) + λ·x(c₁ - c₂)`; with `e` recoverable from the commitment `E = e·G` relation across both shares (or a third observation), obtains `λ·x` — the validator's MuSig key share for this set.

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  Additionally, to ensure a rebuilt service isn't flagged as malicious, we have to check the
  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
