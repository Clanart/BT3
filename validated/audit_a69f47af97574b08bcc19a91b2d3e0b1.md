### Title
Relayer fees escrowed for GET requests are permanently frozen on timeout instead of refunded - (`evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut(GetRequestTimeout, ...)` deletes the `_requestCommitments[commitment]` fee-metadata entry for a timed-out GET request but never transfers the escrowed fee anywhere. This is the same class of bug as H-23: a mutable, money-backed accounting slot is wiped by a code path that is *supposed* to settle the balance (pay it back or forward it), but instead just clears the bookkeeping and leaves the underlying `feeToken()` balance stuck in the contract forever, unreachable by any account.

### Finding Description
`dispatch`-side, a GET request escrows a relayer fee the same way a POST request does: `_requestCommitments[commitment] = FeeMetadata({sender: payer, fee: fee})`, transferring `feeToken()` into `EvmHost`. On the Substrate/`pallet-ismp` side this design is explicit and symmetric — `on_request_timeout` in `modules/pallets/ismp/src/host.rs` refunds the fee for *any* timed-out request (GET or POST) back to `leaf_meta.fee.payer`: [1](#0-0) 

and the pallet-ismp test suite explicitly validates that a `DispatchGet` fee is refunded on timeout: [2](#0-1) 

On the EVM side, however, `EvmHost.dispatchTimeOut` for `GetRequestTimeout` only deletes the escrow entry — it contains **no fee transfer at all**, and the code even comments that this is intentional ("Does not refund any protocol fees"): [3](#0-2) 

Compare this to the sibling function for `PostRequestTimeout`, which does move the escrowed `feeToken()` back to `meta.sender` on success: [4](#0-3) 

The docs corroborate that this asymmetry is a known, accepted behavior on the EVM host rather than a design choice grounded in GET requests being fee-less by protocol design (the Substrate side proves GET requests can and do carry fees): [5](#0-4) 

The broken invariant mirrors H-23 exactly: a storage slot that tracks an escrowed value (`initialGas`/`executionBudget` in AnyCall vs. `_requestCommitments[commitment].fee` in Hyperbridge) is cleared by a code path that is reachable by an ordinary, permissionless caller (`handleGetRequestTimeouts` → `dispatchTimeOut`), and clearing it discards the associated value instead of returning it to the rightful owner. There is no mechanism afterward to recover the fee — the commitment is deleted, so the funds cannot even be claimed via a later resubmission of the timeout proof.

### Impact Explanation
Any user (or an application built on Hyperbridge, e.g. an intent-filling contract that self-issues GET requests) that dispatches a fee-bearing GET request and experiences a timeout — which is a normal, expected outcome of cross-chain messaging under network/liveness conditions, not an attack — permanently loses the escrowed relayer fee. The tokens remain locked inside `EvmHost` with no code path to withdraw them to the payer. This is a direct, unconditional loss-of-funds bug reachable by calling the permissionless `handleGetRequestTimeouts`/`dispatchTimeOut` path with any legitimately timed-out GET request that had `fee > 0`; no malicious relayer, prover, or governance actor is required.

### Likelihood Explanation
High. Any GET request with `fee != 0` that times out (a normal, permissionless, expected condition, triggered simply by processing a valid `GetTimeoutMessage`) hits this code path. No special conditions, front-running, or privileged access are required — only that a fee-bearing GET request is issued and later legitimately times out, after which anyone can submit the timeout proof and the fee vanishes into the contract's balance.

### Recommendation
Make `dispatchTimeOut(GetRequestTimeout, ...)` refund `meta.fee` to `meta.sender` exactly as `dispatchTimeOut(PostRequestTimeout, ...)` does, mirroring the Substrate/`pallet-ismp` behavior where both GET and POST timeouts pass through the same `on_request_timeout` refund logic. If GET requests are intended to never carry a fee, enforce that invariant at `dispatch()` time (reject/ignore `post.fee`/`get.fee` for GET dispatch) rather than silently discarding escrowed value at timeout.

### Proof of Concept
1. A user (or app) calls `dispatch(DispatchGet{... fee: F, payer: user})` on `EvmHost`, paying `F` in `feeToken()`; `_requestCommitments[commitment] = FeeMetadata(user, F)` is stored and `F` tokens are pulled into the host.
2. The destination chain/state never produces (or delays) a response until the request's `timeout` elapses.
3. Anyone (permissionless) submits a valid `GetTimeoutMessage` to `HandlerV2.handleGetRequestTimeouts`, which calls `host.dispatchTimeOut(GetRequestTimeout(request, relayer), meta, commitment)`.
4. `dispatchTimeOut` (EvmHost.sol:856-877) deletes `_requestCommitments[commitment]` and calls `onGetTimeout` on the source module — but performs **no `feeToken()` transfer**.
5. `F` tokens remain locked in `EvmHost` indefinitely; `user` has no further function to call to recover them, since the commitment record that would identify the entitled `payer`/`fee` has just been deleted. [6](#0-5)

    /**
     * @dev Dispatch an incoming GET timeout to the source module.
     * @notice Does not refund any protocol fees.
     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof
     * @param meta - fee metadata for the original request
     * @param commitment - request commitment
     */
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
