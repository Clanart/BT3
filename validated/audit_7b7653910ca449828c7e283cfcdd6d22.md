### Title
App Proxy signed request verification never checks the `timestamp` for staleness, allowing indefinite replay of captured signed app-proxy requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only checks that the HMAC `signature` in the query string matches a value computed over the other query parameters (including `timestamp`); it never checks that the `timestamp` parameter is recent. This mirrors the `LibOracle` bug class of "trusting signed/oracle data without checking that its timestamp is fresh," except here the consequence is that a captured, validly-signed app-proxy URL can be replayed by an attacker at any point in the future and will always be accepted as authentic.

### Finding Description
The `AppProxyVerification` concern is used to authenticate requests forwarded by Shopify's App Proxy to the app's backend. The signature is computed from the full query string (including `shop`, `path_prefix`, and `timestamp`) using the app's shared secret: [1](#0-0) 

`query_string_valid?` deletes the `signature` param and compares the calculated HMAC to the supplied one, but at no point does it read the `timestamp` value out of `query_hash` and compare it to `Time.now` (or any staleness window): [2](#0-1) 

Because `timestamp` is only used as an input to the HMAC and never validated for recency, a URL that was validly signed by Shopify at some point in the past (and observed/logged/leaked by anyone with network visibility - e.g. via browser history, proxies, logs, referrer headers, or a shared/public link) remains fully valid and accepted by `verify_proxy_request` indefinitely: [3](#0-2) 

This is directly analogous to the oracle report's root cause: a piece of externally-supplied, signed data includes a timestamp, but the verifying code checks the signature/validity of the data while omitting a freshness/staleness check on that timestamp, allowing stale (here, replayed) data to be accepted as current and trusted.

### Impact Explanation
An attacker who obtains a single previously-valid, Shopify-signed app-proxy request URL (which is not treated as a secret by Shopify - it is expected to appear in browser navigation, server logs, CDN/proxy logs, or Referer headers) can replay it against the app's app-proxy endpoint at any later time and have it accepted as a legitimate, currently-authenticated request from that shop. This is an "accepted forged/replayed signed request" as defined by the validation criteria, since the code never re-establishes that the signature still corresponds to a recent, live request rather than a captured/leaked one.

### Likelihood Explanation
Exploitation requires obtaining one historical signed app-proxy URL, which is a realistic bar given that these URLs are not marked confidential and routinely appear in logs, analytics tools, or browser history, and app-proxy endpoints are reachable by third parties (they are the mechanism by which storefront-adjacent, less-trusted traffic reaches the app). No merchant/dev cooperation or secret leak is needed beyond passive observation of one legitimate request.

### Recommendation
In `query_string_valid?`, after signature verification succeeds, additionally parse `query_hash["timestamp"]` and reject the request (return `false`) if `Time.now.to_i - timestamp.to_i` exceeds a bounded staleness window (e.g. a few minutes), mirroring the recommended Chainlink `chainlinkStaleLimit` pattern from the referenced report but applied to the app-proxy timestamp.

### Proof of Concept
1. A legitimate merchant browses a page rendered through the app's App Proxy; the resulting URL (e.g. `https://shop.example.com/apps/my-app/some/path?shop=...&path_prefix=...&timestamp=1700000000&signature=...`) gets logged by an intermediary (CDN access log, corporate proxy, browser history sync, etc.).
2. Any party who later obtains that historical URL replays it verbatim, months later, directly against the app's backend endpoint.
3. `verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC over the same, unchanged query parameters (including the old `timestamp`) and finds it matches the supplied `signature`, per [2](#0-1)  — the request is accepted as if freshly issued by Shopify, since no code path checks `timestamp` against `Time.now`.

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
