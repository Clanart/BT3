### Title
`ReceivedOutput::read` accepts arbitrary (offset, TxOut) pairs, decoupling the spend offset from the script_pubkey — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::scan_transaction` only ever produces `ReceivedOutput`s where `output.script_pubkey == p2tr(key + G*offset)`, so downstream code assumes that invariant. However `ReceivedOutput::read` deserializes the `offset` scalar, `TxOut`, and `OutPoint` independently with no consistency check. Untrusted bytes can therefore encode an offset that does not correspond to the key the output's `script_pubkey` actually locks to — a deserialization-level bypass of the offset↔script binding, analogous to a parser quirk bypassing a path restriction.

### Finding Description
`ReceivedOutput::read` reads three independent fields (`Secp256k1::read_F`, `TxOut::consensus_decode`, `OutPoint::consensus_decode`) and returns them as a `ReceivedOutput` without validating that the offset actually derives the output's script_pubkey [1](#0-0) . The honest producer, `Scanner::scan_transaction`, guarantees this binding by only emitting outputs whose `script_pubkey` was found in `self.scripts`, a map keyed by `p2tr_script_buf(key + G*offset)` [2](#0-1) . The deserialized form carries no such guarantee.

The inconsistency materializes in `Output::key()`, which reconstructs the owning key as `xonly(script_pubkey) - G*offset` [3](#0-2) . For scanner-produced outputs this yields the registered group key; for a crafted `ReceivedOutput` where `offset` does not match the script's key, it yields a different, uncontrolled-by-the-set point. `Output::read` feeds attacker bytes straight into `ReceivedOutput::read` [4](#0-3) , and `balance()`/`tx_id()` then report the crafted output's value and origin under that wrong key [5](#0-4) .

### Impact Explanation
A `ReceivedOutput` with a mismatched offset is reported to the processor as an output held under a derived key that no `ThresholdKeys`/scanner ever registered. If such an output is later scheduled for spending, `SignableTransaction`/the FROST `TransactionMachine` will apply `keys.offset(offset)` (per-input commitment re-keying), producing signatures for `key + G*offset` — which does not match the UTXO's actual `script_pubkey` lock. The result is funds reported received that are not spendable (the signature can never satisfy the real output), or misattribution of an output's balance to the wrong key/event stream. This is a reachable-with-public-inputs analog: the only requirement is feeding crafted bytes to `ReceivedOutput::read`/`Output::read`.

### Likelihood Explanation
Exploitation requires the attacker to control bytes on a path deserialized via `ReceivedOutput::read` (e.g., processor `Output` deserialization / stored-output replay). It does not require a threshold of validators, key material, or broken consensus — only the ability to supply a crafted `(offset, TxOut, OutPoint)` triple where `offset` is inconsistent with `TxOut.script_pubkey`. The absence of any binding check in `read` makes the primitive itself trivially constructible; impact depends on the consumer trusting the deserialized pair as scanner-authentic.

### Recommendation
Bind the offset to the output at deserialization or consumption time: when the expected group key is known (as in `Output::key`/processor scanning paths), verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` and reject mismatches. Alternatively, store/serialize the registered script alongside the offset and require equality, or treat deserialized `ReceivedOutput`s as unverified and re-derive the offset via a `Scanner` lookup on `output.script_pubkey` rather than trusting the encoded scalar.

### Proof of Concept
1. Let `K` be the group key, `o` a registered offset, `S = p2tr(K + G*o)`.
2. Craft bytes: `offset' = random scalar` (≠ o), `TxOut{ value: V, script_pubkey: S }`, valid `OutPoint`.
3. `ReceivedOutput::read(&mut crafted)` succeeds — no check ties `offset'` to `S`.
4. `Output::key()` computes `xonly(S) - G*offset' = K + G*o - G*offset'`, a key distinct from `K` and from any registered offset key.
5. The output is reported as received/spendable under that phantom key; any spend attempt signs for `K' + G*offset'` which cannot satisfy `S`, leaving funds unspendable (or, if `offset'` is chosen so `xonly(S) - G*offset'` collides with another registered key stream, misattributed).

Note: reachability of `ReceivedOutput::read` with fully attacker-controlled bytes depends on the integrator's deserialization boundary (it is explicitly in the accepted attack surface per the audit rules); within Serai's own scanner path the producer is honest, so the vulnerability manifests wherever serialized outputs cross a trust boundary.

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
