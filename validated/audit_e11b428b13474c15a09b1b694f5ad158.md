## Analysis

The report is a generic "unchecked ERC20 return value" bug class. Searching for the same anti-pattern inside Hyperbridge's actual settlement code turns up a real, exploitable analog in the Tron variant of `IntentGatewayV2`.

### Title
Escrow settlement accepts silent ERC20 `transfer` failures as success, permanently locking funds while emitting release/refund events — (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (Tron build) releases escrowed ERC20 funds via a raw low-level `call` to `transfer`, and only checks that the *call itself* did not revert (`success`) — it never decodes/validates the returned boolean payload as required by ERC20. Tokens that return `false` on failure instead of reverting (a well-known, common non-standard-but-compliant ERC20 behavior) will report `success == true` even though no tokens moved. The contract nonetheless finalizes escrow bookkeeping and emits `EscrowReleased`/`EscrowRefunded`, permanently losing/locking the beneficiary's funds while the protocol's own state says settlement succeeded.

### Finding Description
In `withdraw()`, escrowed tokens are paid out with: [1](#0-0) 
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```
Only `success` (whether the call reverted) is checked; the returned `bytes` data — which per ERC20 encodes the boolean transfer result — is discarded. The same pattern repeats for fee redemption: [2](#0-1) 
and for the admin `SweepDust` request handler: [3](#0-2) 

Immediately before the loop, the contract has already committed the fill/refund state: [4](#0-3) 
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    _orders[body.commitment][token] -= amount;
```
`_filled` is marked and `_orders[...][token]` is decremented (i.e., the escrow accounting is zeroed/reduced) regardless of whether the underlying token actually transferred the funds. If the token's `transfer()` implementation returns `false` instead of reverting on failure (e.g., insufficient balance under some non-standard implementations, blacklist/pausable tokens that return false, or any ERC20-compliant-but-non-reverting implementation), the low-level `call` succeeds (`success == true`), the `if (!success) revert TransferFailed()` guard does not trigger, and the function proceeds to emit `EscrowReleased`/`EscrowRefunded` as if the beneficiary was paid.

This is exactly the class of bug the seed report calls out (ERC20 boolean return values not processed), reproduced on a real fund-custody/settlement path rather than a cosmetic swap helper.

### Impact Explanation
This directly causes stealing/loss of funds within intent settlement: escrowed input tokens tracked in `_orders[commitment][token]` are decremented and `_filled[commitment]` is set to the beneficiary as if delivery succeeded, but the beneficiary receives nothing. Because `_orders[...]` is zeroed and `_filled` is set, there is no remaining on-chain state pointing to an outstanding claim — the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to retrieve them, and the beneficiary cannot re-trigger withdrawal since `UnknownOrder()` is enforced by `_orders[body.commitment][token] == 0` on any next attempt. This satisfies the bounty's "false state acceptance" and "loss of funds" categories on a production settlement path (bridge custody / intent settlement), not a peripheral utility.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — the only precondition is that one of the escrowed `order.inputs`/`body.tokens` tokens is a non-reverting-on-failure ERC20 (a category of tokens that legitimately exist and are commonly listed, especially relevant on Tron where the low-level `call` pattern was specifically introduced to accommodate non-standard TRC20/ERC20 tokens such as Tron's USDT). Given this file's `call`-based transfer pattern is deliberately used across the whole Tron `IntentGatewayV2` (fills, withdrawals, fee redemption, dust sweep) instead of `SafeERC20`, any configured token with this behavior will trigger silent fund loss on ordinary, unprivileged settlement calls (`onPostResponse`/`onGetResponse` driven `withdraw`), making this readily reachable in normal operation.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls in `withdraw()`, the `TRANSACTION_FEES` payout, and `SweepDust` handling with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this very file (`using SafeERC20 for IERC20;`, and `safeTransferFrom` used in the escrow-in path). If a specific token on Tron truly cannot return a standard boolean, decode and validate the return data explicitly (`success && (returndata.length == 0 || abi.decode(returndata, (bool)))`) before finalizing `_filled`/`_orders` state, matching the pattern OpenZeppelin's `SafeERC20` already implements.

### Proof of Concept
1. Configure/escrow an order input token that is ERC20-compliant but returns `false` (rather than reverting) from `transfer()` when it cannot move funds (e.g., due to an internal balance check, blacklist, or paused state) — such tokens are commonly encountered on Tron/EVM deployments.
2. Drive normal settlement so `withdraw()` is invoked (e.g. via `onPostResponse`/`onGetResponse` for `RedeemEscrow`/refund flows) for that token and commitment.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(success=true, data=abi.encode(false))`.
4. `success` is `true`, so `if (!success) revert TransferFailed();` does not fire.
5. `_orders[body.commitment][token]` is decremented to zero and `_filled[body.commitment]` is set; `EscrowReleased`/`EscrowRefunded` is emitted.
6. The beneficiary's balance is unchanged — the escrowed tokens are now stuck in the `IntentGatewayV2` contract with no order record left to reclaim them, while all on-chain events/state indicate the settlement succeeded.
