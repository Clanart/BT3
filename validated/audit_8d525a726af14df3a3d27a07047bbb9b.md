### Title
`get_outputs` applies a later transaction's `presumed_origin` and `InInstruction` data to outputs scanned from earlier transactions in the same block - (File: processor/src/networks/bitcoin.rs)

### Summary
The bug class in CVE-2020-10751 is "validate/process the first item in a container, then apply that single decision to all remaining items." In `Bitcoin::get_outputs`, the `outputs` accumulator is declared once *outside* the per-transaction loop, so the `presumed_origin` and serai `data` computed for one transaction are applied to every output accumulated so far — including outputs that came from entirely different transactions earlier in the block.

### Finding Description
In `processor/src/networks/bitcoin.rs:686-739`, `get_outputs` iterates `block.txdata[1..]`:

```rust
let mut outputs = vec![];              // line 689 — outside the tx loop
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) { ... outputs.push(output); }

  if outputs.is_empty() { continue; }  // line 702

  let presumed_origin = { ... &tx.input[0] ... };   // lines 707-729
  let data = Self::extract_serai_data(tx);          // line 730
  for output in &mut outputs {                     // lines 731-736
    if output.kind == OutputType::External {
      output.data.clone_from(&data);
    }
    output.presumed_origin.clone_from(&presumed_origin);
  }
}
```

`outputs` is never scoped to the current `tx`. The `if outputs.is_empty() { continue }` check only guards the *first* transaction that produces a match; for every subsequent transaction in the block, the loop body runs (since `outputs` is non-empty) and **overwrites** `presumed_origin` (derived from `tx.input[0]`) and `data` (the embedded `InInstruction` via `extract_serai_data`) on all previously collected outputs — even though those outputs belong to earlier, unrelated transactions.

This mirrors the SELinux flaw exactly: the per-transaction authorization metadata (`data`, `presumed_origin`) is computed for one message/transaction and then stamped onto outputs it was never derived from.

### Impact Explanation
`Output.data` carries the `InInstruction` (e.g., a `Transfer`/`Refund` destination on Serai) associated with a deposit, and `presumed_origin` carries the sender address. An attacker who places a transaction in the **same block, after** a victim's deposit transaction can cause the victim's `External` output to be re-labeled with the attacker's `InInstruction` data and origin. The victim's deposit would then be credited/processed under attacker-chosen instructions (e.g., refunding minted coins to an attacker-controlled Serai address), while the underlying output is genuinely the victim's. This is reachable by any unprivileged party that can get a transaction mined in the same block as a target deposit — requiring no keys, no validator access, only public Bitcoin transactions.

Conversely, an attacker could also strip/overwrite their own output's data using a preceding transaction, affecting how their deposit is interpreted.

### Likelihood Explanation
Any Bitcoin user can broadcast a transaction carrying an `InInstruction`-bearing input that lands in the same block as another user's deposit to a Serai address. No collusion, no validator compromise, and no special access is needed — just ordering within a block, which miners/attacker transactions routinely control. The flaw is deterministic whenever more than one transaction follows a matching deposit in the scanned block.

### Recommendation
Scope the post-processing to the outputs of the *current* transaction:

```rust
for tx in &block.txdata[1 ..] {
  let mut tx_outputs: Vec<Output> = scanner.scan_transaction(tx)
    .into_iter()
    .map(|output| /* build Output */)
    .collect();
  if tx_outputs.is_empty() { continue; }
  // compute presumed_origin and data from tx
  for output in &mut tx_outputs { ... }
  outputs.extend(tx_outputs);
}
```

i.e., declare the accumulator inside the loop (or iterate only over the slice pushed by the current `tx`) so `presumed_origin` and `data` are only ever attached to outputs produced by the transaction they were extracted from.

### Proof of Concept
1. Victim broadcasts deposit `tx_A` paying a Serai external address, embedding `InInstruction_V`.
2. Attacker gets `tx_B` mined in the same block after `tx_A`. `tx_B` spends an input the attacker controls and embeds `InInstruction_A` (e.g., `Transfer`/`Refund` to the attacker's `SeraiAddress`). `tx_B` need not pay any Serai address.
3. In `get_outputs`, processing `tx_A` pushes the victim's `External` output and correctly sets `data = InInstruction_V`, `presumed_origin = victim`.
4. Processing `tx_B`: `scanner.scan_transaction(tx_B)` yields nothing, but `outputs` is non-empty, so the body runs; `for output in &mut outputs` overwrites the victim output's `data` with `InInstruction_A` and `presumed_origin` with attacker's address.
5. The scanner reports the victim's deposit with the attacker's instruction, and downstream processing credits the attacker.
