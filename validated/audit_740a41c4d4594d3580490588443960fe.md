## Finding: Missing module-identity check on the inbound leg of `BandwidthManager.onAccept`

### Summary
`BandwidthManager.sol`'s `onAccept` validates only the *chain-level* origin (`request.source == hyperbridge`) but never validates the *module-level* origin (`request.from`) against `PALLET_BANDWIDTH_MODULE_ID`, even though the outbound `purchase()` path explicitly binds `to = PALLET_BANDWIDTH_MODULE_ID` when dispatching to the pallet. This is a one-directional binding of module identity.

### Finding Description
On the outbound leg, `purchase()` builds a `DispatchPost` with `to: PALLET_BANDWIDTH_MODULE_ID`, guaranteeing the request is routed to `pallet-bandwidth` on the hyperbridge chain: [1](#0-0) 

On the inbound leg, `onAccept` handles governance actions (`SetTiers`, `Withdraw`) that mutate `tierPrice` and, critically, transfer arbitrary ERC20/native balances out of the contract to an attacker-chosen beneficiary: [2](#0-1) 

The only authenticity check performed is: [3](#0-2) 

`request.from` (the sending module identifier on the hyperbridge chain) is never compared to `PALLET_BANDWIDTH_MODULE_ID` (`"BWMARKET"`). The comment on the constant itself states the intended invariant that is not actually implemented in this file: "the pallet enforces this on inbound messages, so changing it on either side breaks the round-trip": [4](#0-3) 

For comparison, other apps in this same codebase correctly bind `request.from` on the inbound leg — e.g., `HyperbridgeLzEndpoint.onAccept` explicitly checks `keccak256(request.from) == keccak256(abi.encodePacked(address(this)))`: [5](#0-4) 

This confirms that binding `request.from` on `onAccept` is the established pattern for this app family, and `BandwidthManager.sol` deviates from it.

The routing on the receiving EVM chain dispatches to whichever contract corresponds to `request.to` (the destination address), but it does not itself enforce that `request.from` matches any particular sender module — that responsibility is delegated to the app's `onAccept`, per the pattern shown in `receiving.mdx`/`HyperbridgeLzEndpoint`. Since `BandwidthManager` skips this check, **any** message from the hyperbridge state machine (`request.source == hyperbridge`) addressed to the deployed `BandwidthManager` contract, regardless of which pallet or module on hyperbridge actually produced it, will be accepted and dispatched into `SetTiers`/`Withdraw` handling as long as its body decodes to the expected `OnAcceptActions` format.

### Impact Explanation
If a body with a valid `OnAcceptActions.Withdraw` discriminant and payload can reach `BandwidthManager` from any module other than `pallet-bandwidth` (i.e., `request.from != "BWMARKET"`), an attacker could drain the contract's fee-token/native balance to an arbitrary beneficiary — a direct, wrongful movement of escrowed purchase funds. Even `SetTiers` forgery would let a non-pallet source manipulate pricing, corrupting purchase-tier state used to gate future dispatches. This matches the "bridged assets... must move exactly once and only to the rightful beneficiary" and "module identity... on both Substrate and EVM" pivots.

### Likelihood Explanation
I could not confirm, with the tool budget available, a currently-reachable **unprivileged** production extrinsic on the hyperbridge chain that lets an attacker fully control both the `to` (destination contract address) and a `body` byte-for-byte matching `BandwidthManager`'s `OnAcceptActions` ABI (prefixed action byte + ABI-encoded `Tier[]`/`Withdrawal`). Every dispatcher call site reviewed (`pallet_hyper_fungible_token::send`, `pallet_host_executive::*`, `pallet_bandwidth` itself, `intents-coprocessor::dispatch`, the demo pallet's `dispatch_to_evm`) hardcodes its own `from` to its own `PalletId` and constructs `body` from its own typed payload, not raw attacker bytes matching this contract's action encoding. The `pallet-ismp` dispatcher itself sets `PostRequest.from`/`to`/`body` directly from whatever the calling pallet supplies with no independent enforcement: [6](#0-5) 

so the check's absence is a real gap in defense-in-depth, but full exploitability depends on an as-yet-unverified pathway (e.g., a generic user-facing "raw dispatch" extrinsic referenced but not fully inspected in `docs/content/developers/polkadot/dispatching.mdx`) that would let an unprivileged signed account fully control both `to` and `body`. This should be verified directly against the live `pallet-ismp`/governance extrinsics before treating this as a confirmed end-to-end critical exploit; as a code-level authorization gap versus the documented invariant, it is nonetheless real and should be fixed regardless.

### Recommendation
Add an explicit check in `onAccept` binding `request.from` to `PALLET_BANDWIDTH_MODULE_ID`, mirroring the outbound `to` binding in `purchase()` and the pattern already used in `HyperbridgeLzEndpoint.onAccept`:
```solidity
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```

### Proof of Concept
A Foundry unit test can demonstrate the gap directly:
1. Deploy `BandwidthManager`, set host to a mock host returning `hyperbridge()` for the source-chain check.
2. Construct an `IncomingPostRequest` with `request.source == hyperbridge` (passes the only existing check) but `request.from = bytes("ATTACKER")` (≠ `PALLET_BANDWIDTH_MODULE_ID`), and `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(Withdrawal({token: address(feeToken), beneficiary: attacker, amount: contractBalance})))`.
3. Call `onAccept` from the host address — assert it succeeds and drains the contract, proving the module-identity check is not enforced on the inbound leg despite being enforced (via `to`) on the outbound leg. [2](#0-1)

```text
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
```
