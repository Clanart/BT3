### Title
Unauthenticated FIFO Eviction of Paid Bandwidth Subscriptions via Cheap Repeat Purchases - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`purchase()` on `BandwidthManager.sol` is callable by anyone, for any `(app_chain, app)` pair, with no requirement that the caller controls or is related to the target `app`. Every successful purchase message lands on `pallet-bandwidth`'s `on_accept` and calls `push_subscription`, which appends to a FIFO list capped at `MAX_SUBSCRIPTIONS` (1024) and **evicts the oldest entry — regardless of its remaining bytes or expiry — once the cap is hit** [1](#0-0) .

### Finding Description
The bandwidth pallet keys its FIFO allowance list purely by `(app_chain, app)`, taken from the purchase message body — not by the payer/manager identity [2](#0-1) . The `Sponsorship` design explicitly documents that the credit chain/app is attacker-controllable and independent of the source chain [3](#0-2) , and the docs confirm `chain` is "not validated against the source chain" [4](#0-3) .

`push_subscription` unconditionally evicts index `0` (the oldest entry) when the list is at the 1024 cap, with no check on how many bytes remain unconsumed on that entry or how much time is left before it expires: [5](#0-4) 

Because anyone can call `purchase()` cheaply and repeatedly against a victim `app`'s bucket (paying only the cheapest tier price each time, e.g. `TierOne`), an attacker can push 1024 tiny, throwaway subscriptions into the victim's list and evict every legitimate subscription the victim already paid for — including large, long-duration, mostly-unconsumed allowances. This is structurally the same broken invariant as the source report: a decision (which entries survive) is made purely from a local counter/order (FIFO position / list length) with **no threshold check against the value actually at stake** (remaining bytes, i.e. paid dollars) before an irreversible state change (eviction) is applied.

### Impact Explanation
This is a direct loss-of-funds / loss-of-paid-resource vector: a victim who bought, say, the $1000/8MB tier can have that entire allowance permanently evicted and unrecoverable by an attacker spending a fraction of a cent per purchase (1024 × cheapest-tier price), since `SubscriptionEvicted` deletes state with no refund path — the docs even frame this as an accepted "pathological repeat-buy" edge case rather than an adversarial one [6](#0-5) . The attack is fully permissionless: it requires only calling `purchase()` on the public `BandwidthManager` contract for an arbitrary `app` and letting a normal (non-malicious) relayer deliver the resulting ISMP messages — no compromised relayer, prover, or admin key is needed.

### Likelihood Explanation
Likelihood is high for any high-value or actively-used `app`: the cost to the attacker is 1024 purchases at the cheapest configured tier (a governance-controlled, potentially trivial value), versus destroying a victim's paid allowance of arbitrary size. No rate limiting, minimum-hold-time, or "don't evict an entry with meaningfully more remaining bytes/duration than the incoming one" rule exists on the eviction path.

### Recommendation
Do not evict purely by FIFO position/list length. Before evicting on a full list, either:
- reject the purchase (or require an explicit governance/admin override) when the oldest entry still has materially unspent `remaining_bytes` and has not expired, or
- evict based on a value/priority ordering (e.g., always evict the entry with the least remaining value, and require the new purchase's tier value to exceed it) rather than blind insertion order, or
- raise `MAX_SUBSCRIPTIONS` substantially and/or charge an increasing cost for repeat purchases into the same bucket so eviction of unexpired value becomes economically irrational for an attacker.
At minimum, emit a way for the bandwidth-buying app to detect and be compensated for adversarial eviction, and consider gating `purchase()` so only the app itself (or an authorized sponsor list) can credit its own bucket, closing the "anyone can push into anyone else's queue" primitive entirely.

### Proof of Concept
1. Victim app `A` on `app_chain = EVM-8453` purchases `TierFour` (8 MB / $1000, long duration), landing as a `Subscription` in `Allowance::<T>::get(EVM-8453, A)`.
2. Attacker, using `BandwidthManager.purchase()` on any registered source chain, calls `purchase({ app: A, tier: TierOne, months: 1, chain: "EVM-8453" })` 1024 times (or fewer if other purchases already partially fill the queue), each dispatching an ISMP POST that the pallet's `on_accept` credits via `push_subscription` [7](#0-6) .
3. Once `Allowance::<T>::get(EVM-8453, A).len() == MAX_SUBSCRIPTIONS`, each subsequent attacker purchase evicts index `0` — eventually reaching and evicting victim `A`'s `TierFour` entry, emitting `SubscriptionEvicted { lost_bytes: <victim's remaining 8MB tier bytes> }` with no refund to `A`.
4. `Pallet::remaining(EVM-8453, A)` now reflects only the attacker's cheap `TierOne` leftovers; `A`'s paid-for bandwidth is unrecoverably gone, verifiable via the existing eviction test scaffolding in `modules/pallets/testsuite/src/tests/pallet_bandwidth.rs` [8](#0-7)  which already exercises FIFO position/count semantics that this attack abuses.

Note: I was not able to inspect the full `BandwidthManager.sol` `purchase()` Solidity source in this session (only its documented behavior and the pallet-side ABI/decoding), so I cannot rule out a possible unseen access-control check on the EVM side restricting who may name an arbitrary `app` in a purchase; if such a check exists there, this finding would need to be reassessed. This should be verified directly against `evm/src/apps/BandwidthManager.sol` before treating this as fully confirmed.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

## Sponsoring Another Chain

The `chain` argument is **not validated against the source chain** — see [Overview → Sponsorship](/developers/evm/bandwidth/overview#sponsorship) for the model. A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`:

```solidity
manager.purchase({
    app:    abi.encodePacked(appAddressOnBase),
    tier:   2,
    months: 6,
    chain:  bytes("EVM-8453")
});
```

The pallet keys allowance storage on `(msg.chain, msg.app)`, so the credit lands on Base regardless of which chain sent the payment. The recommended pattern for teams running a central treasury is to deploy `BandwidthManager` on one low-fee chain and sponsor bandwidth for app instances elsewhere.
```
