### Title
Copilot conflict-resolution reassembly silently overwrites non-conflicted content that merely resembles conflict markers - ([File: app/src/lib/copilot-conflict-context.ts], [File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The Hats/Curve report is about a Newton's-method loop (`get_D`) that never verifies its iterative result actually converged before the pool trusts and uses it — a broken invariant that silently corrupts protocol state. The structural analog in Desktop's Copilot merge-conflict resolver is two **independently implemented, non-identical text scans** over the same untrusted file content — `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`) — that are assumed to always agree on where the "real" conflict hunks are, with no check that they actually converge on the same interpretation of the file.

### Finding Description
`extractConflictHunks` scans a conflicted file line-by-line for any line matching `^<{7}(?:\s|$)` and treats it as the start of a conflict hunk, purely based on regex pattern matching, without any correlation to git's actual conflict metadata: [1](#0-0) 

Later, once the model returns per-hunk resolutions, `reassembleResolvedFile` performs a **separate**, independently written scan of the same raw file content to find `<<<<<<<` / `=======` / `>>>>>>>` blocks and splice the model's resolved text into them, counted with its own `hunkIndex`: [2](#0-1) 

Both functions rely on the same broken assumption: any line that *looks like* a conflict marker is treated as a genuine conflict boundary, even though a file's actual content (e.g., documentation about Git, example diffs, test fixtures) can legitimately contain lines matching `<<<<<<<`, `=======`, or `>>>>>>>` that are not part of git's real conflict. If such a file also has a real, unrelated conflict elsewhere (so it legitimately appears with `AppFileStatusKind.Conflicted` status and enters the Copilot flow), the phantom marker text is picked up as an extra "hunk" by `extractConflictHunks`, sent to the model as `### Conflict N of M` (see `formatConflictContextForPrompt`, `app/src/lib/copilot-conflict-context.ts:560-590`), and the model's fabricated replacement text is spliced back in by `reassembleResolvedFile` at the corresponding position. The only cross-check performed is a hunk **count** comparison in `validateResolutionPaths` [3](#0-2)  — there is no verification that the *positions/content* the two independent scans identified as "hunk N" actually refer to the same block of text, i.e. no check that the two computations "converged" on the same structural result.

The final resolved content is written directly to disk and staged without further validation: [4](#0-3) 

### Impact Explanation
An attacker who controls a branch/commit that the victim merges, rebases, or cherry-picks (a git remote the user pulls from, or a PR they check out) can craft a file that:
1. Contains a real, small conflicting region (to guarantee `AppFileStatusKind.Conflicted` and be picked up by `buildConflictContext`), and
2. Contains, elsewhere in the same file, ordinary text lines that happen to match the conflict-marker regexes (`<<<<<<<`, `=======`, `>>>>>>>`) — e.g. a documentation/tutorial snippet about Git.

When the victim uses the Copilot "resolve conflicts" feature, non-conflicted content unrelated to any real merge conflict is silently replaced by LLM-generated text and staged/committed as if it were a legitimate conflict resolution — this is a "silent corruption of what the user commits" per the specified valid-impact class. Because the resolution is written straight to the working file and staged (`writeFile` + `git add`), the corruption can end up permanently in the user's commit/push history without an explicit diff review forcing the user to notice the unrelated hunk being altered.

### Likelihood Explanation
This requires: (a) the attacker's content to be merged by the victim (a normal collaboration workflow, not privileged access), and (b) the victim to opt into the Copilot AI conflict-resolution feature and accept the AI's resolution. The "phantom marker" condition is realistic for any repository containing documentation, tests, or fixtures that literally show conflict-marker syntax — a common occurrence in tooling/docs repositories. I was not able to fully verify, in the time available, whether the result dialog (`copilot-conflicts-dialog.tsx` / `copilot-conflicts-changes.tsx`) presents a full line-by-line diff of every touched region that would let an attentive user catch the extra corrupted hunk before accepting — this is a gap in my investigation and should be confirmed before treating this as high-confidence exploitable, since a sufficiently prominent diff review in that dialog could mitigate real-world impact.

### Recommendation
- Do not rely on independent duplicate regex scans of the same file for extraction and reassembly. Have `extractConflictHunks` return, alongside each hunk, the exact line-range/byte-offsets it identified, and make `reassembleResolvedFile` splice strictly by those recorded offsets rather than re-deriving hunk boundaries from a second, separately-written scan.
- Cross-validate that the number of hunks and their line ranges recovered by the extraction pass and the reassembly pass are identical before accepting the reassembled content (i.e., check "convergence" between the two computations), and refuse to write/stage the file (falling back to manual resolution) if they diverge.
- Consider scoping conflict-marker detection to the actual byte ranges git reports as being in conflict (rather than any regex match anywhere in the file) to avoid misclassifying ordinary content as a conflict hunk.

### Proof of Concept
1. On `main`, create `docs.md`:
   ```
   line A
   <<<<<<< example
   sample ours text
   =======
   sample theirs text
   >>>>>>> example
   line B
   ```
2. On branch `feature`, edit only `line A` → `line A changed`. On `main`, edit `line B` → `line B changed` (or similarly force a real conflict on lines A/B while leaving the fake marker block untouched by either side but still within the same file so the whole file is reported `Conflicted`).
3. Merge `feature` into `main` in Desktop, triggering a real conflict on `line A`/`line B`.
4. Invoke "Resolve with Copilot". `extractConflictHunks` will report **two** hunks: the real conflict and the fake `example`/`example` block that is plain documentation text, not a real conflict.
5. The model resolves both "hunks" (having no way to know hunk 2 isn't real). `reassembleResolvedFile` splices the model's fabricated text over the `sample ours text` / `sample theirs text` documentation lines.
6. The user accepts the resolution; `_applyCopilotConflictResolutions` writes and stages the file — the documentation content between the "fake" markers is now silently replaced by AI-generated content unrelated to any actual merge conflict, and becomes part of the committed history.
