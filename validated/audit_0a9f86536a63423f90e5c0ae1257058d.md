### Title
Stale Light Client Proof Returned for Wrong Payout Block Height in Operator Assert Flow — (File: `core/src/citrea.rs`)

---

### Summary

`fetch_validate_and_store_lcp` caches a Light Client Proof (LCP) keyed only by `deposit_id`. If the function is called again for the same deposit with a different `payout_block_height` (e.g., after a chain reorganization moves the payout transaction to a different block), it silently returns the stale LCP without re-fetching. The stale LCP carries a different L1 block hash than the one the bridge circuit expects, causing the assert transaction to be provably invalid. An operator who cannot submit a valid assert within the challenge window loses their collateral.

---

### Finding Description

`fetch_validate_and_store_lcp` in `core/src/citrea.rs` is the function responsible for obtaining the LCP that the operator embeds in the BitVM2 assert transaction:

The backing table stores exactly one LCP per deposit, with no column for the block height it was generated at:

The bridge circuit then enforces that the LCP's committed L1 block hash equals the SPV proof's block hash:

```rust
let lc_l1_block_hash = light_client_circuit_output.latest_da_state.block_hash;
let spv_l1_block_hash = input.payout_spv.block_header.compute_block_hash();

If the cached LCP was generated for block height X but the payout transaction is now confirmed at block height Y (different hash), the circuit panics and the assert proof is invalid.

---

### Impact Explanation

An operator who cannot produce a valid assert cannot disprove a watchtower challenge within the protocol's timelock window. The result is that the operator's collateral is slashable — a direct, material loss of bridge-controlled funds. The bridged BTC reimbursement path is also blocked for that deposit.

---

### Likelihood Explanation

The mismatch arises whenever `fetch_validate_and_store_lcp` is invoked a second time for the same `deposit_id` with a different `payout_block_height`. Concrete triggers:

1. **Chain reorganization** — the payout transaction is evicted from block X and re-confirmed in block Y. The LCP stored for block X is now stale; the second call returns it unchanged.
2. **Payout-checker retry with corrected height** — `core/src/task/payout_checker.rs` and `core/src/operator.rs` both call this function. If the payout checker first records an incorrect height (e.g., off-by-one, or before finality), the wrong LCP is persisted and all subsequent calls for that deposit return it. [4](#0-3) 

---

### Recommendation

Add `payout_block_height` to the `lcp_for_asserts` table as part of the primary key (or as a validated column). In `fetch_validate_and_store_lcp`, after retrieving a cached LCP, decode its journal and assert that the committed block height matches `payout_block_height`. If it does not match, discard the stale entry, fetch a fresh LCP, and overwrite the row.

```sql
-- revised schema
create table if not exists lcp_for_asserts (
    deposit_id int not null primary key,
    payout_block_height bigint not null,   -- add this
    lcp_receipt bytea not null
);
```

In Rust:

```rust
if let Some((stored_height, lcp)) = saved_data {
    if stored_height == payout_block_height {
        return Ok(lcp);
    }
    // height mismatch — fall through to re-fetch
}
```

### Proof of Concept

1. Operator's payout transaction is mined in block **X** (height 800 000).
2. `fetch_validate_and_store_lcp(800_000, deposit_id, …)` is called; LCP for block 800 000 is fetched and stored in `lcp_for_asserts` with `deposit_id` as the sole key.
3. A shallow reorg (or a payout-checker retry with a corrected height) causes the payout transaction to be confirmed in block **Y** (height 800 001, different hash).
4. `fetch_validate_and_store_lcp(800_001, deposit_id, …)` is called. The DB already has a row for `deposit_id`, so the function returns the LCP for block 800 000 immediately — `payout_block_height = 800_001` is silently ignored.
5. The operator builds the assert transaction embedding the stale LCP (block hash of 800 000).
6. The bridge circuit compares `lc_l1_block_hash` (800 000's hash) with `spv_l1_block_hash` (800 001's hash) and panics — the assert proof is invalid.
7. A watchtower challenges; the operator cannot produce a valid disprove proof within the timelock.
8. Operator collateral is slashed. [5](#0-4) [6](#0-5)
