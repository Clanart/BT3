### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s, causing the wallet to build consensus-invalid spends — ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase), and emits `ReceivedOutput`s for any output paying a registered script. Coinbase outputs are unspendable for 100 blocks by consensus, yet `ReceivedOutput` carries no maturity/spendability flag and `SignableTransaction::new`/`TransactionSignMachine::sign` will happily commit to spending one. The resulting transaction is rejected by the network, and if the coinbase output was batched with genuine inputs, the entire spend fails — funds are reported received but are not spendable.

### Finding Description
`scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no notion of coinbase maturity:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
``` [1](#0-0) 

The only guard is a doc comment stating "If received outputs must be immediately spendable, a post-processing pass is needed" — but neither `ReceivedOutput` nor `SignableTransaction` exposes the data needed to enforce this:

- `ReceivedOutput { offset, output, outpoint }` stores no flag indicating the output came from a coinbase; `outpoint.txid` is just the coinbase's txid, indistinguishable from a normal transaction to the wallet layer. [2](#0-1) 
- `SignableTransaction::new` accepts any `Vec<ReceivedOutput>` and builds `TxIn`s for all of them without checking coinbase maturity (it cannot — it doesn't know the spending height). [3](#0-2) 
- `TransactionSignMachine::sign` then produces FROST signature shares over `Prevouts::All(&self.tx.prevouts)`, causing the threshold group to sign and broadcast a transaction that every node rejects (`bad-txns-premature-spend-of-coinbase`). [4](#0-3) 

The caller-side "post-processing pass" is not implementable from the `ReceivedOutput` API alone: distinguishing a coinbase output requires tracking whether `outpoint.txid` was `txdata[0]` of its block, information `scan_block` discards.

### Impact Explanation
An output credited by `scan_block` cannot be spent for 100 blocks. Any `SignableTransaction` including it produces a transaction that fails mempool acceptance and would fail consensus — the spend is dead. Because `TransactionSignMachine` batches all inputs into one transaction (`Prevouts::All`), a single immature coinbase output poisons an entire withdrawal batch: the honest inputs in the same transaction are also unspendable until the transaction is rebuilt without the poisoned input. Additionally, the threshold signing round burns a FROST preprocess/signing session on a doomed transaction.

An attacker needs only to mine a block paying the multisig's scanned script (e.g., via the registered external-address script). On a live network this is achievable by anyone mining, or by influencing a pool's coinbase outputs; no privileged access to the multisig or its signers is required. The scanner must be fed blocks, which is its normal operating input — `scan_block(&block)` is a public API consuming untrusted chain data.

### Likelihood Explanation
In normal operation, miners do not direct coinbase rewards to the multisig script, so this is not triggered accidentally. However, it is trivially triggerable deliberately by any miner, and the failure mode (a poisoned output set that blocks batched spends for ~100 blocks per poisoned output) makes it an attractive griefing vector: the attacker sacrifices a coinbase reward to freeze or disrupt the protocol's UTXO handling. Reorgs also make "mature" coinbases immature again with no mechanism to un-report them. Severity is Medium: it causes a temporary denial of withdrawals and wastes signing rounds, but does not directly enable theft.

### Recommendation
Do not scan `block.txdata[0]` in `scan_block`, or record coinbase origin on `ReceivedOutput` (e.g., a `coinbase: bool` or the block height) so `SignableTransaction::new` can reject immature inputs. The clean fix is to make `scan_block` call `self.scan_transaction` on `&block.txdata[1 ..]` and require callers who want coinbase outputs to opt in explicitly. At minimum, return enough metadata for the post-processing pass the doc comment mandates to actually be implemented.

### Proof of Concept
1. Construct a `Scanner` for an even-parity key `key`; the base script `p2tr_script_buf(key)` is registered (`Scanner::new`, `networks/bitcoin/src/wallet/mod.rs:162-166`).
2. Produce a regtest block whose coinbase (`txdata[0]`) pays 50 BTC to that script.
3. Call `scanner.scan_block(&block)` — it returns a `ReceivedOutput` for the coinbase output (confirmed by the existing test, which asserts `scan_block(block) == scan_transaction(&block.txdata[0])` and that the output is found at `txdata[0]` — `networks/bitcoin/tests/wallet.rs:65-70` — the test even mines 100 extra blocks to work around maturity before spending, evidencing the hazard).
4. Pass that `ReceivedOutput` to `SignableTransaction::new(vec![output], payments, change, None, fee)` and run `multisig(keys)` → `preprocess` → `sign` → `complete`. The wallet produces a fully-signed transaction spending an immature coinbase.
5. Broadcast: bitcoind rejects with `bad-txns-premature-spend-of-coinbase`; if the output was batched with mature inputs, the whole spend fails, demonstrating that reported-received funds are not spendable and that one poisoned output stalls the entire transaction.
