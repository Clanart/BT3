I found a solid local analog: the Tron variant of `IntentGatewayV2.withdraw()` and its `SweepDust` handler use raw low-level `.call()` with the ERC20 `transfer` selector and only check that the call itself didn't revert — they never decode/verify the returned boolean, unlike the standard EVM contracts in this repo which use `SafeERC20.safeTransfer`.

### Title
Unchecked ERC20/TRC20 boolean return value in escrow withdrawal and dust sweep lets tokens be marked settled without actually moving funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron deployment of `IntentGatewayV2.sol` perform ERC20/TRC20 transfers via a raw low-level call to the `transfer` selector and only check the boolean `success` returned by `.call(...)` (i.e., that the call did not revert), never decoding and validating the ERC20 return value itself. Per the ERC-20 standard (and the exact bug class from the referenced Yearn report), some tokens signal transfer failure by returning `false` instead of reverting. Because the contract updates escrow accounting (`_orders[...] -= amount`, `_filled[...] = beneficiary`) unconditionally once the raw call "succeeds", a beneficiary can be marked as paid while the underlying token transfer silently failed, permanently locking/losing the escrowed funds while the settlement bookkeeping shows it as released.

### Finding Description
In `withdraw()`: [1](#0-0) 
tokens are redeemed with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only checks that the external call did not revert. It does not decode `success` return data and confirm it equals `abi.encode(true)`. A TRC20/ERC20 token that returns `false` on a failed transfer (rather than reverting) will make `success == true` here (the call completed normally), so the check passes even though no tokens moved. The same unchecked pattern appears in the `SweepDust` handler inside `onAccept()`: [2](#0-1) 

Contrast this with the EVM (non-Tron) implementation of the same escrow-release logic, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, decoding the ERC20 return value and reverting on `false`: [3](#0-2) 

The Tron contract deliberately avoids `SafeERC20` and uses raw `.call` with only a success check, which drops the return-value validation that `SafeERC20` provides.

### Impact Explanation
This falls squarely within "stealing or loss of funds" / "false proof/state acceptance" of settlement. Once `withdraw()` is invoked (e.g., via `onGetResponse` after a proven cancellation/refund, or via the normal fill-settlement path), the contract decrements `_orders[commitment][token]` and marks `_filled[commitment] = beneficiary` regardless of whether the token transfer actually delivered funds. If the transfer silently fails (returns `false`), the escrowed balance is effectively burned from accounting perspective (order state says released) but the beneficiary's wallet balance never increases — the funds are stuck in the gateway contract with no order record left to reclaim them, since `_orders[...]` is already decremented and `_filled[...]` is already set (blocking any retry/refund path).

### Likelihood Explanation
This requires only the use of a token that returns `false` on failed transfer instead of reverting — a well-known non-conforming-but-still-common ERC20/TRC20 behavior (old ERC20 tokens, some TRC20 tokens on Tron). No malicious relayer, prover, or governance actor is needed; a normal user placing an order with such a token, combined with a transient/edge transfer failure condition (e.g., blacklist, paused token, insufficient token-side balance due to fee-on-transfer edge cases already handled elsewhere in this codebase), is sufficient to trigger the loss. Given Tron's TRC20 ecosystem includes tokens with non-standard transfer semantics, and the contract is the production Tron deployment of the intents gateway, this is a realistic, unprivileged-triggerable path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere via `using SafeERC20 for IERC20;` in this same file), so both call success and the decoded boolean return value are validated before mutating escrow state.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer` function returns `false` on failure instead of reverting (e.g., due to an internal blacklist check or paused state) rather than reverting.
2. Place an order on `IntentGatewayV2` (Tron) using this token as an escrowed input, so `_orders[commitment][token] = amount`.
3. Trigger settlement/refund such that `withdraw(body, isRefund)` is called (e.g., via the `onGetResponse` refund path after proving the order was unfilled) with the beneficiary in a state where the token's `transfer` call returns `false` (e.g., beneficiary blacklisted by the token).
4. Observe: `token.call(...)` returns `success = true` (the call completed without reverting) even though the token's internal logic returned `false` and moved no balance.
5. `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment] = beneficiary;` is set, emitting `EscrowRefunded`/`EscrowReleased`.
6. The beneficiary's token balance is unchanged, but the order is now considered fully settled on-chain with no remaining escrow record — the funds are permanently stuck in the `IntentGatewayV2` contract.
