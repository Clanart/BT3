Let me verify it's never deleted and how context is scoped.### Title
Cached FROST preprocess is never deleted after use, causing nonce reuse across `share`/`complete` and leaking the validator's secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` generates a FROST preprocess seed once, stores it (XOR-encrypted) in the `CachedPreprocesses` DB table, and — critically — **never deletes it after consumption**. Both `DkgConfirmer::share` and `DkgConfirmer::complete` call `share_internal`, which calls `preprocess_internal`, which rebuilds the `AlgorithmSignMachine` via `from_cache` from the *same* seed. The seed deterministically regenerates identical nonces via `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:127`). Each call therefore executes `AlgorithmSignMachine::sign` with the identical `(d, e)` nonce pair. If the preprocess set (the `included` participant list or any commitment value) differs between the two `sign` invocations, the binding factor `rho` and Lagrange coefficient differ, producing two distinct published signature shares over the same nonce — the classic FROST/Schnorr nonce-reuse condition that allows algebraic recovery of the signer's secret share by anyone who observes the shares.

### Finding Description
Root cause chain:

1. `preprocess_internal` checks `CachedPreprocesses::get(self.txn, &self.context).is_none()` and only writes a new seed when absent (`signing_protocol.rs:123-135`). The table is keyed by `context = (b"DkgConfirmer", attempt)` (`signing_protocol.rs:275`). There is no `txn.del` anywhere for `CachedPreprocesses` — a `grep` for `CachedPreprocesses` shows only this file, and the entry is never removed after the machine is built (`signing_protocol.rs:137-145`).
2. `share_internal` invokes `self.preprocess_internal(participants).0` and then `machine.sign(preprocesses, msg)` (`signing_protocol.rs:156-180`).
3. `DkgConfirmer::share` calls `share_internal` once (`signing_protocol.rs:304-310`), and `DkgConfirmer::complete` calls `share_internal` **again** to rebuild the machine (`signing_protocol.rs:321-324`). `complete` can additionally be invoked repeatedly as more share data arrives.
4. `from_cache` → `seeded_preprocess` derives nonces deterministically from the cached seed (`crypto/frost/src/sign.rs:127-132`), so every `sign` call uses the same `nonces`.
5. Inside `sign`, the share is `d + e*rho + c*lambda*x` where `rho` comes from the transcript of `group_key || hash_msg(msg) || hash_commitments(preprocesses-transcript)` (`crypto/frost/src/sign.rs:361-398`). Any difference in `included` participants or in any participant's commitments changes `rho` and/or `lambda`.

Analogous to the kernel bug (a single-use resource not freed during cleanup, leaving it dangling for reuse), the cached seed is a single-use cryptographic resource that persists past its consumption, violating the FROST precondition documented in the same codebase: "A preprocess MUST only be used once. Reuse will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`, `spec/cryptography/FROST.md:51-55`).

The differing preprocess set arises without any protocol violation: `share` is emitted as soon as a threshold of preprocesses is available, while `complete` is invoked later with whatever preprocess set is then known — a superset or a differently-ordered map, or a re-published conflicting preprocess. Each distinct set produces a new share equation `z_i - z_1 = e(rho_i - rho_1) + x(c_i·lambda_i - c_1·lambda_1)` in only the two unknowns `e` and `x` (since `d` cancels); two distinct-set shares beyond the first yield a solvable 2x2 system giving the validator's MuSig/FROST secret share `x`.

### Impact Explanation
Signature shares are broadcast on the tributary and observable publicly. Recovery of the validator's `Ristretto` secret share `x` breaks the unforgeability of that validator's participation in every protocol secured by that MuSig key (DKG confirmations via `set_keys_message`, and any other `SigningProtocol` context sharing the same key). A recovered share also combines with publicly known preprocess material (`CachedPreprocess` documentation states third-party knowledge of a preprocess alone enables share recovery). This is a key-share recovery primitive reachable purely from messages published to the tributary during a single `attempt` — exactly the "third-party recovery of your private key share" the FROST docs warn against.

### Likelihood Explanation
The reuse path is not hypothetical: `complete` unconditionally re-enters `share_internal`/`sign` on the same cached seed — it is the designed control flow, not an edge case (`signing_protocol.rs:322-324`). What is required beyond that is that the preprocess map passed to `complete` differ from the map used in `share`. Preprocesses arrive asynchronously; `share` fires at threshold while `complete` typically runs after more preprocesses (or a conflicting re-published preprocess from any validator) have been collected. Repeated calls to `complete` with evolving preprocess sets supply the additional independent equations needed to solve for `e` and `x`. One caveat: if `share` and every `complete` call receive byte-identical preprocess maps, the second `sign` reproduces the identical share and nothing leaks — the vulnerability therefore requires the ordinary, uncoordinated variance in which preprocesses are known at each step, which is expected in an asynchronous protocol but was not exhaustively confirmed in `handle.rs` call sites. Note also the encryption of the cached seed (`signing_protocol.rs:104-114`) protects against DB readers but does nothing to prevent reuse by the coordinator itself.

### Recommendation
Delete the `CachedPreprocesses` entry the first time it is consumed — i.e., after `CachedPreprocesses::get` succeeds in `preprocess_internal` (`signing_protocol.rs:137`), call `txn.del` on the key before building the machine, and persist the resulting `AlgorithmSignMachine` state (or the produced share/machine) rather than re-deriving it. `complete` should reuse the *same* machine/share produced by `share` rather than re-running `sign` on a fresh-but-identical machine; alternatively, cache the computed `SignatureShare` keyed by the preprocess-set hash and return it verbatim for identical sets while refusing to sign under a different `included` set with the same seed. At minimum, mirror the FROST "MUST only be used once" contract in the DB layer so the nonce seed cannot outlive its first `sign`.
