### Title
SignableTransaction omits the OP_RETURN data output from the fee/vbyte calculation, producing under-funded transactions that cannot be relayed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output to `tx_outs` when `data` is specified, but computes the transaction's vbytes and required fee from `payments` alone via `calculate_weight_vbytes`. The resulting signed transaction is under-funded relative to both the caller-specified `fee_per_vbyte` and the enforced minimum-relay-fee check, and can therefore be rejected as non-standard by Bitcoin nodes — while the threshold signature is already bound to that exact transaction.

### Finding Description
When `data` is provided, an `OP_RETURN` output is pushed to `tx_outs` (send.rs:194-202). The fee computation, however, runs `calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which builds a mock transaction containing only the payment outputs and no data output:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

The same omission occurs in the change branch (send.rs:225-226): `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again ignores the `data` output. Consequently:

- `needed_fee` is computed on a smaller vsize than the real transaction. For an 80-byte payload the `OP_RETURN` output adds ~90+ vbytes that are never charged for.
- The minimum-relay-fee guard uses the same undercounted `vbytes`, so it cannot catch the shortfall.
- The change output absorbs the leftover, meaning the final transaction pays exactly `needed_fee` while being larger than assumed — its true feerate is strictly below `fee_per_vbyte`, and for low fee rates or large `data` it falls below `DEFAULT_MIN_RELAY_TX_FEE` per actual vbyte.

### Impact Explanation
An unprivileged caller controls the `data` field routed into `SignableTransaction::new` (it's the transaction payload/API input). By supplying data, they force construction of a transaction whose real feerate is below the minimum relay fee. FROST signing proceeds via `TransactionSignMachine::sign`, which commits to `Prevouts::All` and the exact sighash of this under-funded transaction (send.rs:373-390). The completed transaction cannot be relayed, and the fee cannot be bumped without an entirely new threshold-signing ceremony — the inputs are effectively stuck in a transaction that the network will not propagate, the analog of "redeem returns a useless output because a required parameter wasn't accounted for".

### Likelihood Explanation
Any plan/payment path that attaches `data` (up to 80 bytes is explicitly allowed by the `TooMuchData` check at send.rs:171) triggers the miscalculation. The shortfall is deterministic: every extra byte of `data` is ~1 vbyte of unpaid size. Whether the transaction is outright rejected depends on the fee rate — at 1 sat/vB (the enforced floor) an 80-byte payload reliably produces a non-standard transaction.

### Recommendation
Pass the `data` output into the weight/vbytes calculation. Extend `calculate_weight_vbytes` to accept the optional data payload (or a fully built `tx_outs` list) and include the `OP_RETURN` output in both the no-change and with-change invocations, so `needed_fee` and the minimum-relay check reflect the real transaction size.

### Proof of Concept
1. Construct inputs with sufficient value and a payment ≥ `DUST`.
2. Call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), 1)`.
3. The OP_RETURN output (80 bytes + script overhead ≈ 92 vB) is present in `tx.output` but excluded from `vbytes`, so `needed_fee ≈ vsize - 92` sats at 1 sat/vB.
4. The signed transaction's actual feerate is < 1 sat/vB, below `DEFAULT_MIN_RELAY_TX_FEE` for its real vsize, and is rejected by `sendrawtransaction` as non-standard; the FROST signature in `TransactionSignatureMachine::complete` is already bound to this txid.
