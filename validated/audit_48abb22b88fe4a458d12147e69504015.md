### Title
`SignableTransaction::new` computes fee and weight on a transaction missing the OP_RETURN output, understating the fee and bypassing the size check - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The external report's bug class is a formula that produces a wrong result because it does not account for every factor in the computation (a missing decimals-normalization term in the collateral ratio). The analog in `bitcoin-serai` is `SignableTransaction::new`, which calls `calculate_weight_vbytes` on a transaction template that omits the OP_RETURN `data` output the caller explicitly requested, so both `needed_fee` and the standard-weight check are computed over a smaller transaction than the one actually constructed and signed.

### Finding Description

`SignableTransaction::new` accepts a `data: Option<Vec<u8>>` argument and, after validating `data.len() <= 80`, pushes an OP_RETURN output onto `tx_outs` (`networks/bitcoin/src/wallet/send.rs:193-202`). However, the subsequent fee and weight computation calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), and `calculate_weight_vbytes` builds its template transaction from `payments` plus optional `change` only (`send.rs:85-99`) — it never includes the data output.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed on a transaction that is missing an output of `1 + 1 + 8 + (1 + len(data))` bytes. The resulting transaction, once signed by `TransactionSignMachine` / `TransactionSignatureMachine`, pays `sum(inputs) - sum(outputs)` (`fee()`, `send.rs:138-141`), which equals a lower feerate than the `fee_per_vbyte` the caller requested and than `needed_fee()` reports.
2. The `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) uses `weight` from the same undersized template, so a transaction that actually exceeds the standard weight limit can be accepted (with `data` alone this is bounded to ~88 bytes, but combined with the missing-change path — when the change output is dropped because `value < DUST` at `send.rs:229` the no-change `weight`/`needed_fee` are kept while the dust remainder inflates the fee — the accounting diverges from the real signed transaction).
3. The minimum-fee check (`send.rs:211`) can pass while the true transaction is below `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction that will not be relayed.

The input is reachable by an unprivileged party: `payments`, `change`, `data`, and `fee_per_vbyte` are all caller-supplied parameters to the public `SignableTransaction::new` API, and the result is signed by `TransactionSignMachine::sign` and broadcast.

### Impact Explanation

The signed transaction's actual fee rate is strictly lower than the requested `fee_per_vbyte`, and `needed_fee()` over-reports nothing — callers relying on it (e.g., fee amortization over payments) will under-charge. At the boundary, the produced transaction can fail the real minimum-relay-fee policy or exceed `MAX_STANDARD_TX_WEIGHT`, yielding a transaction that cannot be relayed — funds committed to its inputs are locked in an unbroadcastable/unconfirmable spend. This mirrors the report's impact: a core accounting formula returns a wrong value, breaking every dependent decision (fee sufficiency, size validity).

### Likelihood Explanation

Triggered whenever `data` is `Some` (or when change is dropped as dust and `theoretical` vs actual outputs diverge): the miscalculation occurs on every such construction, deterministically, with no attacker sophistication required. Severity is bounded by the 80-byte data cap, so the per-transaction fee error is small, but the size-check bypass and consistent fee understatement make it a real correctness defect rather than noise.

### Recommendation

Compute weight/vbytes over the exact transaction being built. Move the OP_RETURN push before the size computation and pass the data output into `calculate_weight_vbytes` (e.g., extend its signature to take the full `tx_outs` list, or call it after `tx_outs` is finalized for both the change and no-change cases). Recompute `weight`/`vbytes` whenever the output set changes (data added, change added or dropped) so `needed_fee`, the minimum-fee check, and `MAX_STANDARD_TX_WEIGHT` all reflect the transaction that will actually be signed.

### Proof of Concept

```rust
// networks/bitcoin/src context
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, None, Some(data), fee_per_vbyte).unwrap();
// The real transaction includes an OP_RETURN output (tx.output.len() == payments.len() + 1),
// but needed_fee() was computed via calculate_weight_vbytes(..., payments, None),
// which built a template WITHOUT that output (send.rs:85-99, 204).
// Therefore:
//   tx.fee() == needed_fee == fee_per_vbyte * vbytes(without_op_return)
//   actual feerate == tx.fee() / signed_tx.vsize() < fee_per_vbyte
// and if signed_tx.weight() > MAX_STANDARD_TX_WEIGHT while the template's was below,
// the TooLargeTransaction check at send.rs:241 was bypassed.
```
