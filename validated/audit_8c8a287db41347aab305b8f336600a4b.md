# Reentrancy TOCTOU in same-chain intent fills lets a malicious order-creator steal escrowed input tokens from an honest solver

### Title
Reentrant escrow drain during native-token output transfer in `_fillSameChain` — ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
The reported Uniswap TOCTOU bug hinges on one invariant: a value is *checked* at one point, control is *handed to the attacker*, and the value is *used* afterward without re-validating that it hasn't changed. The Hyperbridge Intent Gateway's same-chain fill path (`_fillSameChain`) has the identical structural flaw: it transfers native-token output payments to the order's `beneficiary` via a raw `.call` **before** it finalizes/decrements the escrowed input-token accounting (`_orders[commitment][token]`) via `_withdraw()`. Because `beneficiary` can be attacker-controlled and identical to `order.user`, the attacker can reenter `cancelOrder` mid-fill and redirect the still-un-decremented escrow to themselves, after which the solver's own withdrawal silently resolves to a zero-amount no-op instead of reverting.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`), for each output asset the contract:
1. Updates `_partialFills[commitment][outputToken]` (line 98).
2. Immediately sends native ETH to `beneficiary` via a low-level `.call` (line 104) — **before** any escrow accounting for the input tokens is touched.
3. Only *after* the full output loop completes does it call `_withdraw(body, false, isFullyFilled)` (line 134), which is what actually reads and decrements `_orders[commitment][token]` (the escrowed input balance) inside `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`, escrow check/decrement at lines 400-403).

`escrowedInputs[i]` (the amount to be paid to the solver) is computed at line 116-121 by reading `_orders[commitment][token]` **after** the native transfer has already executed:
```solidity
if (token == address(0)) {
    ...
    (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");   // <-- control ceded here
    ...
}
...
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))]; // <-- read AFTER external call
}
```
`_cancelSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:161-187`) only requires `order.user == msg.sender` and that some escrow remains (`hasEscrow`); it does not check whether a fill is already in progress. Because `order.user` and `order.output.beneficiary` are both attacker-chosen at `placeOrder` time and can be set to the *same* malicious contract address, the attacker can:
1. Place an order with `beneficiary == order.user == MaliciousContract`, and an output asset of `token = address(0)` (native ETH).
2. When an honest solver calls `fillOrder`/`_fillSameChain`, the ETH transfer at line 104 invokes `MaliciousContract`'s `receive()`, which reenters `cancelOrder()` → `_cancelSameChain()`.
3. `_cancelSameChain` passes the `Unauthorized` check (`msg.sender == order.user`) and reads `_orders[commitment][token]` — still at its **pre-fill, full value**, since the outer `_fillSameChain` has not yet reached its own `_withdraw()` call. It then transfers the *entire* escrowed input balance to `MaliciousContract` and zeroes `_orders[commitment][token]`.
4. Control returns to `_fillSameChain`, which now computes `escrowedAmount = _orders[commitment][token] == 0` and calls `_withdraw()` for the solver with `amount == 0`. `_withdraw` explicitly skips zero-amount entries (`if (amount == 0) continue;`, `evm/src/apps/intentsv2/IntentsBase.sol:398`) — it does **not** revert.
5. The overall `fillOrder` transaction succeeds, emitting `OrderFilled`, even though the solver received **zero** escrowed input tokens in exchange for the output tokens it just paid to the attacker.

The root cause mirrors the report's core defect exactly: the contract "checks" (implicitly, by reading storage) the escrowed amount to release, but hands control to an attacker-influenced address (`beneficiary.call`) before that check's underlying state (`_orders[commitment][token]`) is locked in, allowing the attacker to mutate it via a reentrant path (`cancelOrder`) in between.

### Impact Explanation
This is a direct loss-of-funds / logic-attack vulnerability reachable by any unprivileged user (order placer) against any unprivileged counterparty (solver) — no relayer, prover, governance, or admin trust assumption is required. The solver pays real value (native ETH output) to the beneficiary and receives nothing back, while the attacker (order creator = beneficiary) drains the full escrow that should have compensated the solver. This falls squarely within "stealing or loss of funds," "unauthorized transaction," and "logic attacks" from the bounty's accepted impact list.

### Likelihood Explanation
Likelihood is high: `placeOrder` and `fillOrder`/`cancelOrder` are all public, permissionless entry points; the attacker only needs to author a small malicious contract that both places the order and reenters on receiving ETH. The only precondition is that the order's output includes a native-token (`address(0)`) asset, which is an explicitly supported, common configuration, not an edge case.

### Recommendation
Enforce checks-effects-interactions in `_fillSameChain`: decrement/finalize all escrow accounting (`_orders[commitment][token]`, i.e., call the escrow-release logic) for a given output *before* performing the external `.call`/`safeTransferFrom` to `beneficiary`. Alternatively, add a reentrancy guard around `fillOrder`/`cancelOrder`, and/or make `_cancelSameChain` check a fill-in-progress flag that is set before any external calls in `_fillSameChain` and cleared only after `_withdraw()` for the solver has completed. Additionally, `_withdraw`'s silent `continue` on `amount == 0` should not be relied upon as a safety net — the intended solver payout amount should be captured and validated *before* any external call is made in the fill loop.

### Proof of Concept
1. Attacker deploys `MaliciousContract` with a `receive()` function that calls `IntentGateway.cancelOrder(order, cancelOptions)` for a known `commitment`.
2. Attacker calls `placeOrder` with `order.user = MaliciousContract`, `order.output.beneficiary = MaliciousContract`, `order.output.assets[0].token = address(0)` (native ETH), and escrows some input token (e.g., 100 USDC) via normal escrow flow.
3. Honest solver calls `fillOrder(order, options)` with `options.outputs[0].amount >= totalRequired` in ETH.
4. Inside `_fillSameChain`, `beneficiary.call{value: beneficiaryTotal}("")` (line 104) transfers ETH to `MaliciousContract`, triggering `receive()` → `cancelOrder()` → `_cancelSameChain()`.
5. `_cancelSameChain` reads `_orders[commitment][USDC] == 100` (untouched), transfers the full 100 USDC to `MaliciousContract`, and zeroes `_orders[commitment][USDC]`.
6. Reentrant call returns; `_fillSameChain` computes `escrowedAmount = _orders[commitment][USDC] == 0`, calls `_withdraw` for the solver with `amount = 0` (no-op, no revert), and emits `OrderFilled`.
7. Result: solver paid ETH to `MaliciousContract` and received 0 USDC; attacker received both the ETH output and the full 100 USDC escrow. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Note: I could not fully verify the outermost `fillOrder`/`cancelOrder` public entrypoints (likely defined in `IntentGatewayV2.sol` or a shared router contract that dispatches to `_fillSameChain`/`_cancelSameChain`) since that file's full contents were not returned by the index before the tool budget ran out — I was unable to confirm whether a top-level reentrancy guard (e.g., `nonReentrant` modifier) is applied at that outer layer, which would neutralize this path. If such a guard exists at the public `fillOrder`/`cancelOrder` level, this specific reentrant call chain would revert instead of succeeding. This should be verified directly in the full `IntentGatewayV2.sol` (or wherever `fillOrder`/`cancelOrder` are exposed) before treating this as confirmed-exploitable.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
