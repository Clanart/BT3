### Title
Heuristic "stash succeeded" detection in `createDesktopStashEntry` can silently leave uncommitted changes unprotected during checkout - (File: app/src/lib/git/stash.ts)

### Summary
`createDesktopStashEntry` in `app/src/lib/git/stash.ts` runs `git stash push` and, when the command exits with code `1`, does **not** treat that as a definitive failure. Instead it applies a heuristic: if `stderr` contains no line matching `/^error: /m`, it assumes the stash was created successfully and returns `true` to the caller. [1](#0-0) 

This mirrors the structural flaw in the reported `mToken.redeem()` bug: a non-standard, non-reverting return signal (`git`'s exit code / stderr shape) is interpreted with an incomplete heuristic instead of verifying the actual resulting state, allowing the caller to believe an operation succeeded when it may not have.

### Finding Description
`git stash push` can exit with `1` for reasons other than "stash created but with a benign warning" — for example, on an unborn branch ("You do not have the initial commit yet") the docstring in the code itself acknowledges this ambiguity was never fully resolved: [2](#0-1) 

The only signal used to distinguish "stash succeeded with exit 1" from "stash actually failed" is the absence of a line beginning with `error: ` in stderr. This is a textual heuristic over git's output, not a real state check. Any Desktop-version/locale/git-version combination that produces an exit code `1` without an `error: `-prefixed line (e.g., new/uninitialized repos, other localized or unbadged warnings) causes the function to be treated as `true` (stash created) even when the working directory changes were never actually stashed and remain untouched on disk.

`createDesktopStashEntry` is invoked before Desktop performs destructive branch-switch operations (checkout) in order to preserve uncommitted changes: [3](#0-2) 

If the caller believes the working directory is now "safe" (stash succeeded) when it is not, Desktop proceeds to check out a different branch, run pull/rebase, or other destructive git operations on the assumption the working tree is clean. The real uncommitted content is never protected by an actual stash entry, so it can be silently overwritten, merged with the target branch's content, or blended into whatever gets staged/committed next — a direct parallel to the router contract continuing to act on stale/false state after `mToken.redeem()`'s unchecked failure signal.

### Impact Explanation
Unlike the Compound/Moonwell case (financial loss), the Desktop analog is user-data integrity: uncommitted local changes can be silently lost or intermixed with content from the target branch, and if the user then commits, the resulting commit's content silently diverges from what they intended to have preserved. Because this can occur transparently to the user (no error dialog, since the code path explicitly logs "info" and continues) this satisfies "silent corruption of what the user commits" per the report's valid-impact criteria.

### Likelihood Explanation
This is a narrow heuristic bug rather than a deterministically-triggerable exploit primitive: it requires a specific git output shape (exit `1`, no `error: `-prefixed stderr line) that the code's own commentary admits is not proven safe ("I got curious about the assumptions... That didn't hold up to a quick read of the stash code"). I was not able to fully verify from the indexed code whether an attacker-controlled repository state (rather than a repository/environment condition like an unborn branch) can reliably force this exact exit-code/stderr combination — this would require exercising real `git stash push` behavior across git versions, which is outside what static code search can confirm.

### Recommendation
Do not infer stash success from exit code and absence of an `error: ` stderr prefix. After `git stash push` returns a non-zero code, verify success by checking for the actual creation of a new stash entry (e.g., diff `git stash list` before/after, or check `refs/stash` SHA changed) rather than relying on stderr text pattern matching.

      if (e instanceof GitError && e.result.exitCode === 1) {
        // search for any line starting with `error:` -  /m here to ensure this is
        // applied to each line, without needing to split the text
        const errorPrefixRe = /^error: /m

        const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
        if (matches !== null && matches.length > 0) {
          // rethrow, because these messages should prevent the stash from being created
          return Promise.reject(e)
        }

        // if no error messages were emitted by Git, we should log but continue because
        // a valid stash was created and this should not interfere with the checkout

        log.info(
          `[createDesktopStashEntry] a stash was created successfully but exit code ${result.exitCode} reported. stderr: ${result.stderr}`
        )
        return e.result
      }
      return Promise.reject(e)
    }
  )

  // Stash doesn't consider it an error that there aren't any local changes to save.
  if (result.stdout === 'No local changes to save\n') {
    return false
  }

  return true
