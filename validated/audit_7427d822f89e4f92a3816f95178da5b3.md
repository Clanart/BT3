## Confirmed key fact
The comment "*Messages are processed in batches, all messages in a batch should originate from the same chain*" at [1](#0-0)  shows batches are meant to be homogeneous per source chain, but nothing in `pallet-consensus-incentives` enforces that the reward-attribution signer actually corresponds to the events being paid for. `ConsensusMessage.signer` is a bare, attacker-choosable `Vec<u8>` field carried alongside the (public, replayable) `consensus_proof` bytes [2](#0-1) .

### Title
Reward misattribution in `pallet-consensus-incentives::on_executed` pays the whole batch's consensus rewards to the signer of `messages[0]` only - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`FeeHandler::on_executed` derives the rewarded relayer account from a single message (`messages.get(0)`), then pays that one account for **every** `StateMachineUpdated` event found anywhere in the whole batch's `events`, regardless of which message in the batch actually produced each event [3](#0-2) . This is analogous to the Alchemix bug: a claimant is paid for state (an "epoch"/height span) they did not personally verify/deliver, because the code checks a checkpoint/signature that isn't bound to the specific reward-triggering state.

### Finding Description
`process_message`/`calculate_reward` compute a reward purely from the global on-chain watermark `LastRewardedHeight[state_machine_id]` versus `host.latest_commitment_height(state_machine_id)` [4](#0-3) . There is no check binding the *specific* `Message::Consensus` that advanced a given `state_machine_id` to the account being credited. Instead, `on_executed` extracts a signer once from `messages[0]` and then loops over the highest `StateMachineUpdated` height per `state_machine_id` collected from `events` across the **entire batch** — a batch which the submitter alone constructs and can contain multiple independent `Message::Consensus` items for unrelated `state_machine_id`s [5](#0-4) .

Because `consensus_proof` and `signer` bytes inside a `ConsensusMessage` are ordinary, publicly-visible extrinsic data (not bound by nonce or by tx-origin to the account that produced them) [2](#0-1) , an unprivileged actor can copy any already-broadcast/pending `ConsensusMessage` for chain B (crafted and signed by a legitimate relayer to update chain B's height, currently worth a large reward under `StateMachinesCostPerBlock`) into position `messages[1..]` of their own batch, while placing a trivial, self-signed `ConsensusMessage` for a cheap chain A as `messages[0]`. `on_executed` extracts the reward-recipient signer only from `messages[0]` (the attacker), yet the highest-height collapse loop still credits the attacker for chain B's `StateMachineUpdated` event triggered by the copied message — paying the attacker's account for work whose signature and delivery belongs to someone else [6](#0-5) . The genuine `signer` field embedded in `messages[1]` is decoded and used only to identify a payee when that item happens to sit at index 0; it is otherwise completely ignored for attribution purposes.

`LastRewardedHeight` only guards against re-paying the *same* height span twice ("`.max()`" watermark, see comment) [7](#0-6) ; it does nothing to ensure the *payee* is correct, exactly like the Alchemix `Bribe` contract's checkpoint balance read that ignored whether the claimant actually voted in that epoch.

### Impact Explanation
This lets an unprivileged actor divert `T::Currency::transfer` payouts from the treasury PalletId account to themselves for chain updates they neither discovered, signed for reward purposes as intended, nor were the "attributed" relayer for — an unauthorized/duplicate diversion of protocol treasury funds to the wrong beneficiary, matching the bounty's "wrong beneficiary or amount" / "unauthorized transaction" impact class. Because the reward is currency, not a settlement receipt, this is direct value extraction from the treasury, and it also mints `T::ReputationAsset` to the wrong account [8](#0-7) , corrupting the reputation/incentive accounting long-term.

### Likelihood Explanation
Exploitable by any single unprivileged account able to submit a batched extrinsic containing more than one `Message::Consensus`; it needs no relayer collusion, no compromised key (signatures/proofs are copied verbatim, not forged), no admin/governance action, and is not merely a "front-run the same reward" race — it is a distinct wrong-beneficiary payment triggered purely by the batch-level (not per-message) attribution logic. The only prerequisite is that `StateMachinesCostPerBlock` is configured with non-zero cost for the targeted chain (an ordinary, expected governance configuration, not a bug precondition).

### Recommendation
Bind reward attribution per-message: iterate the batch pairing each `Message::Consensus` with the specific `StateMachineUpdated` event(s) it produced (e.g. via message index/order or an explicit commitment returned by the ISMP host per message), and derive/verify the signer separately for each `state_machine_id` being rewarded, rather than using a single `messages.get(0)` signer for the whole batch's collapsed event map.

### Proof of Concept
1. Governance configures `StateMachinesCostPerBlock` with high cost for chain B, low/zero for chain A.
2. Honest relayer R broadcasts (or has pending) a valid `ConsensusMessage` for chain B advancing `LastRewardedHeight[B]` by a large span, self-signed by R.
3. Attacker observes this public message (mempool/prior block), copies its `consensus_proof`/`signer` bytes verbatim into `messages[1]` of their own extrinsic, and places their own trivial self-signed `ConsensusMessage` for chain A as `messages[0]`.
4. Attacker submits the combined batch. `pallet_ismp` processes both messages, producing `StateMachineUpdated` events for both A and B.
5. `on_executed` decodes signer only from `messages[0]` (attacker) [9](#0-8) , then loops over `highest_per_state_machine` (containing both A and B) and pays the attacker's account the full reward for B's span, even though B's advance was authored/signed by R [10](#0-9) .
6. `LastRewardedHeight[B]` advances, permanently foreclosing R (or anyone) from ever being paid for that span.

**Note on confidence:** I was unable to fully trace the top-level extrinsic entry point that assembles `Vec<MessageWithWeight>` and invokes `FeeHandler::on_executed` (e.g., `pallet-ismp`'s `handle`/`handle_messages` call) within the remaining tool budget, so I cannot cite the exact origin-validation code that confirms an unprivileged, unsigned submitter fully controls arbitrary batch composition. This should be verified in a follow-up session before treating the finding as fully proven end-to-end.

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
