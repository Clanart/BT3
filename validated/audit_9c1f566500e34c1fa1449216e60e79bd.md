### Title
External-link "https-only" safety check is bypassed by `LinkButton`/`shell.openExternal`, allowing attacker-controlled GitHub data to trigger arbitrary-protocol navigation - (File: `app/src/ui/lib/sandboxed-markdown.tsx`, `app/src/ui/lib/link-button.tsx`, `app/src/main-process/main.ts`)

### Summary
The bug class in the report is: an explicit safety restriction exists in one code path, but a second, broader-access code path completely bypasses it, making the restriction meaningless. In GitHub Desktop, the "restriction" is the https-only check applied to links rendered from untrusted markdown before they are allowed to be opened externally. That check is enforced only inside the markdown renderer's click interceptor and is not enforced by the underlying primitive it eventually calls (`shell.openExternal`/the `open-external` IPC handler), nor by other UI components (`LinkButton`) that call the same primitive directly with attacker-influenced data pulled from the GitHub API.

### Finding Description
`SandboxedMarkdown` intentionally restricts navigation from rendered (untrusted) markdown to `https:`/`http:` links only: [1](#0-0) 

This is the intended guardrail — analogous to "freezing" role modification in the audited contract: it exists specifically to stop untrusted, repository/PR/comment-controlled content from causing arbitrary external navigation.

However, the actual boundary between the renderer and the OS is the main-process IPC handler, which performs **no protocol validation** at all — it only logs when the URL happens to start with `http(s)://`, but calls `shell.openExternal` unconditionally for any string: [2](#0-1) 

And the generic `LinkButton` component — used throughout the UI to render clickable links, including ones populated from GitHub API objects (e.g. repository homepage, user profile/blog URL, PR/issue metadata) — calls `shell.openExternal(uri)` directly on click with **no protocol check whatsoever**: [3](#0-2) 

So exactly like `GranularRoles#hasRole` allowing `ADMIN_ROLE` to bypass the `DEFAULT_ADMIN_ROLE` freeze, here the narrow https-only gate in `sandboxed-markdown.tsx` is rendered moot because the same underlying capability (`shell.openExternal`) is reachable through `LinkButton` and the unguarded `open-external` IPC handler without ever passing through that gate. Any attacker-controlled string that ends up as a `LinkButton`'s `uri` prop (or is otherwise forwarded to `dispatcher.openInBrowser`/`shell.openExternal`) is opened with the OS's default handler for whatever scheme it declares, not just `http(s)`.

### Impact Explanation
Electron's `shell.openExternal` hands the given string to the OS shell to be opened by whatever application is registered for its scheme. Non-http(s) schemes (e.g. Windows `search-ms:`, `ms-officecmd:`, or crafted `file://`/UNC paths) have historically been used in other Electron apps to achieve unexpected local application launches, information disclosure, or (in combination with a vulnerable helper app) code execution — all without the user ever seeing the https-only guard that the developers clearly intended to enforce for exactly this class of untrusted content. Since GitHub repository/user metadata (homepage URLs, profile links, etc.) is attacker-influenced and rendered via `LinkButton` outside the sandboxed-markdown https gate, this is a real navigation-restriction bypass reachable from a GitHub API object, matching the report's required attacker primitive.

### Likelihood Explanation
Likelihood is bounded by whether any concrete `LinkButton` (or similar direct `shell.openExternal` caller) is populated straight from attacker-controlled, non-URL-validated GitHub API fields (e.g. a repository's `homepage`, a user's `blog`/profile URL) without an intermediate `https:`-scheme check like the one `sandboxed-markdown.tsx` performs. I was not able to fully enumerate every call site that feeds `LinkButton`'s `uri` prop within the indexing window available, so this should be verified by inspecting all `<LinkButton uri={...}>` usages that source data from `IAPIRepository`/`IAPIUser`-like objects. This is the main uncertainty in this analog.

### Recommendation
Move the protocol allow-list check down to the single choke point — either the `open-external` IPC handler in `app/src/main-process/main.ts` or a shared wrapper around `shell.openExternal` — so that it uniformly rejects any non-`http(s)` scheme regardless of which UI component (markdown link interceptor, `LinkButton`, or any future caller) initiates the request. Relying on a per-component check like the one in `sandboxed-markdown.tsx` is exactly the same design flaw as relying on `AccessControlUpgradable#grantRole`/`revokeRole` remaining unreachable by convention instead of being hard-blocked at the source.

### Proof of Concept
1. Find (or construct) a `LinkButton` instance whose `uri` is populated from an attacker-controlled GitHub API field (e.g. a forked/malicious repository's `homepage` value, or a PR author's profile URL) rather than being pre-validated as `https:`.
2. Set that field to a non-http(s) URI, e.g. a Windows `search-ms:` handler URI or another OS-registered custom scheme.
3. Have the victim view the repository/PR in Desktop and click the rendered link.
4. `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:85`) calls `shell.openExternal(uri)` directly; this reaches the IPC handler in `app/src/main-process/main.ts:581-597`, which performs no scheme validation and unconditionally invokes Electron's `shell.openExternal`, launching the OS handler for the attacker-chosen scheme — bypassing the https-only restriction that `sandboxed-markdown.tsx` enforces for equivalent untrusted content rendered as markdown.

    const pathLowerCase = path.toLowerCase()

      pathLowerCase.startsWith('https://')

      log.info(`opening in browser: ${path}`)
