### Title
Circular (2-node) referral ring bypasses `Circled()` self-referral guard, allowing Sybil-controlled accounts to mutually claim referral bonuses on their own real capital - (File: rewards/ReferralStorage.sol)

### Summary
`useCode()` only rejects a *direct* self-reference (`codeOwners[_code] == msg.sender`), but does not check for indirect (transitive) loops. Two Sybil-controlled EOAs can register codes and use each other's codes, forming a 2-cycle where `myReferer[A] == B` and `myReferer[B] == A`. Every subsequent `trigger()` call made by `masterMagpie` on behalf of A or B then pays a referral bonus to the other Sybil address instead of to a genuine, independently-acquired referee.

### Finding Description
`useCode()` at [1](#0-0)  enforces only:
- `codeOwners[_code] == msg.sender` revert `Circled()` (blocks only "I use my own code")
- `myReferer[msg.sender] != address(0)` revert `HasReferral()` (blocks re-referral, but is checked per-account, not transitively across the graph)

There is no traversal of `myReferer` to detect that granting `msg.sender` a referer would create a cycle. Attack flow:
1. A calls `registerCode(codeA)` → `codeOwners[codeA] = A`.
2. B calls `registerCode(codeB)` → `codeOwners[codeB] = B`.
3. B calls `useCode(codeA)` → `codeOwners[codeA] == A != B`, `myReferer[B] == 0` → allowed, sets `myReferer[B] = A`.
4. A calls `useCode(codeB)` → `codeOwners[codeB] == B != A`, `myReferer[A] == 0` → allowed, sets `myReferer[A] = B`.

Now `myReferer[A] = B` and `myReferer[B] = A`, a closed 2-node loop, while `Circled()` never fires because neither call is a direct self-use.

Once the loop exists, every real staking/locking action A and B perform (which normally triggers `masterMagpie` to call `trigger(_referee, _amount)` at [2](#0-1) ) causes:
- `trigger(A, amount)`: `_referer = myReferer[A] = B` → `refererInfo (B).rewardAmount += refererAmount`, `refereeInfo (A).rewardAmount += refereeAmount`.
- `trigger(B, amount)`: `_referer = myReferer[B] = A` → `refererInfo (A).rewardAmount += refererAmount`, `refereeInfo (B).rewardAmount += refereeAmount`.

So both A and B receive the "referer" bonus normally reserved for bringing in a genuinely independent new user, in addition to their own "referee" share — all funded from the same real staking activity that a normal unreferred user would otherwise generate with no referral bonus overhead. Rewards accumulate in `userInfos[x].rewardAmount` and are paid out later via `claimReward()` at [3](#0-2)  by direct `safeTransfer` from the contract's MGP balance, with no accounting check against how much MGP was actually funded for legitimate referral rewards.

### Impact Explanation
This lets any two colluding addresses extract additional MGP referral-tier rewards on capital they already own and stake, without bringing any real new user/volume into the protocol — i.e., gaming the referral incentive budget. Because `claimReward()` performs an unconditioned `safeTransfer` from the contract's MGP balance, this ring can drain the shared MGP allocation set aside for referral incentives, potentially causing `InsufficientRewardBalance` reverts / failed claims for genuine referrers later (yield theft / partial freezing of unclaimed MGP for honest referral participants). This falls under theft/permanent freezing of unclaimed yield.

### Likelihood Explanation
Trivial and fully permissionless: requires only two EOAs (or one EOA controlling two addresses) each calling `registerCode` and `useCode` once — no privileged role, no flash loan, no reentrancy. Any user willing to also perform the underlying staking/locking actions that generate `trigger()` calls can execute this repeatably at zero marginal cost beyond gas.

### Recommendation
Prevent indirect cycles, not just direct self-reference: when processing `useCode(_code)`, walk (or bound-check) the referer chain of `codeOwners[_code]` to ensure `msg.sender` does not already appear as an ancestor referer of the code owner (i.e., reject if `codeOwners[_code]`'s referer chain eventually reaches `msg.sender`). At minimum, for a single-level program, explicitly disallow `myReferer[codeOwners[_code]] == msg.sender` to block the 2-node cycle case shown here. Also consider tracking a separate accounted MGP reward liability vs. actual balance to detect/prevent insolvency from any residual gaming vectors.

### Proof of Concept
Hardhat test outline:
1. Deploy `ReferralStorage`, `VLMGP` mock, `MasterMagpie` mock (or use real `MasterMagpie` with `_onlyMasterMagpie` caller set to test signer), set a tier with nonzero `rewardPercentage`, fund the `ReferralStorage` contract with MGP.
2. `A.registerCode(codeA)`, `B.registerCode(codeB)`.
3. `B.useCode(codeA)`; `A.useCode(codeB)` — assert both succeed (no `Circled()` revert) and `myReferer[A]==B`, `myReferer[B]==A`.
4. From the `masterMagpie` address, call `referralStorage.trigger(A, amount)` and `referralStorage.trigger(B, amount)`.
5. Assert `userInfos[A].rewardAmount + userInfos[B].rewardAmount` includes both referer and referee components for each side (i.e., each address received a `refererAmount` derived from the other's `trigger` call), demonstrating each Sybil address earns referral-tier bonuses on its own capital that a non-referred, single, unrelated user would not receive — confirming the mutual-referral bypass of `Circled()`.
