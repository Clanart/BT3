### Title
Copilot conflict-resolution reassembly misparses nested conflict-marker-like text, silently corrupting merged file content - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
GitHub Desktop's AI conflict-resolution feature parses conflicted files twice with two *independently re-implemented* line scanners that must stay in lock-step: `extractConflictHunks` (used to build the prompt sent to Copilot) in [1](#0-0)  and `reassembleResolvedFile` (used to splice the model's per-hunk answers back into the on-disk file) in [2](#0-1) . Both scanners identify a conflict block purely by matching bare regexes (`^<{7}`, `^={7}$`, `^>{7}`) against individual lines, with no concept of nesting. If the *content* of a genuine conflict (the "ours" or "theirs" side, which is attacker-influenceable source text coming from a fetched/merged branch) itself contains lines that look like conflict markers, both scanners latch onto the first inner match instead of the real outer one. Because they misparse identically, the hunk-count cross-check in `validateResolutionPaths` ( [3](#0-2) ) does not catch the mistake, and the reassembly step silently writes a corrupted file — including duplicated/omitted code and literal leftover git conflict markers — to disk as the "resolved" result that the user then stages and commits.

### Finding Description
`extractConflictHunks` walks a file line by line. After the opening `<<<<<<<` line it appends every subsequent line to the "ours" buffer **until it sees any line matching `^={7}$`**, without regard for whether that line originated from a legitimately nested/embedded marker-like string rather than the real separator: [4](#0-3) 

The same weakness exists in the reassembly scanner, which only looks ahead for *any* `=======`-shaped line followed by *any* `>>>>>>>`-shaped line to decide where a conflict block ends: [5](#0-4) 

Consider a file that legitimately contains literal conflict-marker text on its own lines — this is not an exotic assumption; this very codebase's own test fixtures do exactly that, e.g. `'<<<<<<< HEAD'`, `'======='`, `'>>>>>>> feature'` joined by newlines in [6](#0-5) . Any documentation snippet, template literal, or test fixture describing Git conflict resolution can contain such lines at column 0.

If a branch fetched/merged from an attacker-controlled remote touches such a file elsewhere (a trivially craftable, ordinary-looking change), Git will wrap the *whole* region — including the embedded marker-like text — inside one real `<<<<<<< / ======= / >>>>>>>` block. Both `extractConflictHunks` and `reassembleResolvedFile` will then stop at the **first nested** `=======`/`>>>>>>>` instead of the real outer ones:
- The prompt sent to Copilot only shows a truncated slice of the actual conflict.
- `reassembleResolvedFile` treats everything after the falsely-matched nested closing marker — which includes the real `console.log`/code lines, the real `=======`, the real `theirs` content, and the real `>>>>>>>` — as ordinary non-conflicted file content and copies it through **verbatim**.

Because the hunk count produced by both scanners is identical (they misparse the same way), `validateResolutionPaths`'s `hunks.length` check in [7](#0-6)  passes — there is no guard that detects the desync. `reassembleResolutions` then writes the spliced content out as the file's final resolved content with no further sanity check that leftover conflict markers or duplicated code are absent, via [8](#0-7) .

The broken invariant is: *"the region between the Nth `<<<<<<<` and its matching `>>>>>>>` that the prompt-builder shows the model is the same region that the reassembler later replaces."* This invariant silently breaks whenever conflict-adjacent content contains marker-like text, and none of the existing checks (`validateResolutionPaths` hunk-count check, the "still contains conflict markers" check on `resolvedContent` in [9](#0-8) ) validate the *reassembled full file* — they only validate the model's small per-hunk string, never the final spliced-together output that gets written to disk and offered up for commit.

### Impact Explanation
The result is silent corruption of what the user commits: the "resolved" file written to disk can contain a mix of both branches' unrelated code, duplicated lines, and literal leftover `=======`/`>>>>>>>` marker text — while the UI presents the conflict as successfully AI-resolved. If the user trusts the automated resolution and commits/pushes without carefully re-diffing the entire file, broken or semantically wrong code (or literal garbage bytes) enters the commit history. This falls squarely under "silent corruption of what the user commits or pushes" from an attacker who only controls the content of a fetched/merged branch — no local access, credentials, or social engineering beyond a normal merge is required.

### Likelihood Explanation
Triggering this requires only that a repository the victim merges/rebases from contains, in a file that later develops a genuine conflict, a line that structurally matches `^<{7}`, `^={7}$`, or `^>{7}` (7+ repeated characters at line start) — e.g., inside a fixture, a doc/readme about Git, a code comment, or a string literal. This is a realistic, easily crafted pattern for any attacker who can offer a branch/PR/fork the user will merge, and does not require unusual repository structure or elevated permissions. The main mitigating factor is that it depends on such marker-like text existing near a real conflict region, so exploitation requires deliberate placement by an attacker (which is straightforward) rather than occurring by pure accident in most repos.

### Recommendation
Make `reassembleResolvedFile` structurally aware of nesting depth, or better, derive hunk boundaries from a single shared parser (reuse `extractConflictHunks`'s exact boundary offsets, e.g. by returning line ranges instead of re-deriving them independently) so the prompt-builder and the reassembler can never disagree about where a conflict block starts and ends. Additionally, after reassembly, scan the final spliced content for any remaining lines matching the conflict-marker regexes and refuse to treat the file as resolved (surface it as a skipped/failed file for manual resolution) instead of silently writing corrupted content to disk.

### Proof of Concept
1. In a shared repository, add a file (e.g. `notes.ts`) whose "ours"-side content legitimately contains marker-like text on separate lines, such as:
```
function unrelatedOurs() {}

const DOC_EXAMPLE = `
<<<<<<< HEAD
foo
=======
bar
>>>>>>> feature
`
console.log("ours-only line")
```
2. On another branch (`feature`), make an unrelated overlapping edit to the same region (e.g. change `unrelatedOurs` and add `console.log("theirs-only line")` plus a different `DOC_EXAMPLE` value), producing a real Git conflict where Git wraps the whole block in one outer `<<<<<<< HEAD ... ======= ... >>>>>>> feature`.
3. Start a merge in Desktop and invoke the Copilot "Resolve conflicts" flow.
4. Observe (via `extractConflictHunks`/`formatConflictContextForPrompt`) that the prompt sent to the model only contains the truncated inner slice (`foo` / `bar`), not the real ours/theirs content.
5. After Copilot returns a resolution for that single (mis-detected) hunk, `reassembleResolvedFile` splices it in and copies through everything after the nested `>>>>>>> feature` — including the real `=======`/`>>>>>>> feature` markers and both branches' unrelated real changes — verbatim into the file that Desktop writes to disk and marks as resolved.   contextLines: number = 3

  const hunks: Array<IConflictHunk> = []

      i++

    const oursLines: Array<string> = []
    const baseLines: Array<string> = []

    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content

      if (baseMarker.test(lines[i])) {
        hasBase = true

        i++

      i++

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
