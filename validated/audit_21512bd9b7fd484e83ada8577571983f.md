### Title
Arbitrary local file disclosure via malicious in-repo symlink in `getWorkingDirectoryImage` - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the path to read purely from `repository.path` and the working-directory-relative `file.path`, then calls `fs/promises.readFile` on it without ever checking whether the resolved path stays inside the repository or whether any path component is a symlink. Since git can track symlinks as ordinary blob entries (mode `120000`), a malicious repository can ship a "file" (with an image-like name/extension such as `logo.png`) that is actually a symlink pointing at an arbitrary absolute path on the victim's machine (e.g. `~/.ssh/id_rsa`, browser profile files, etc.). When the user views the change for that path in the diff pane, Desktop calls `getWorkingDirectoryImage`, and Node's `readFile` transparently follows the symlink, reading and base64-encoding the target file's bytes and rendering them as if they were repository content.

### Finding Description
`getWorkingDirectoryImage` is: [1](#0-0) 

It does `Path.join(repository.path, file.path)` and immediately `readFile`s the result — there is no `fs.lstat`/`realpath` check to confirm the target is a regular file located inside `repository.path`, and no verification that `file.path` does not resolve through a symlink. `file.path` is derived from the working directory status of a checked-out repository (`WorkingDirectoryFileChange`), and its on-disk representation is entirely determined by what `git checkout`/`git clone` materialized there. Git supports tracking symlinks (mode `120000`) as first-class blob content, and does not validate or sandbox the symlink target when writing it to the working tree — the target string is written verbatim as an OS symlink. This means an attacker who controls the content of a cloned repository fully controls what such a symlink resolves to, including paths outside the repository entirely (absolute paths or `../../..` traversals).

Because the classification of "is this an image diff" in this file is done by extension (`imageFileExtensions`, e.g. `.png`, `.jpg`, etc. at lines 94-103) rather than by verifying the underlying file's type via `lstat`, a symlinked entry with an image-like extension is routed straight into `getWorkingDirectoryImage`, and the traversal happens transparently at the OS level when `readFile` follows the symlink.

### Impact Explanation
This lets a malicious repository cause GitHub Desktop to read and render, inside the app's own diff pane, the contents of arbitrary files on the local filesystem that are readable by the victim's OS user account — which matches the in-scope impact category of "file... read outside the repo." The displayed bytes are base64-encoded and injected into the UI as image data; even for non-image target files, the raw bytes are loaded into an `Image` object in the renderer process and could subsequently reach other data paths mentioned in the finding's stated scope (diff pane, commit context, error reports) if the resulting `Image`/buffer is handled elsewhere without additional validation.

### Likelihood Explanation
Exploitation requires nothing beyond cloning/fetching a malicious repository — a fully in-scope, unprivileged attacker-controlled input. No additional local access, credentials, or social engineering step beyond opening the repository and viewing the changed "file" in Desktop's UI (a normal, expected user action) is needed. Git natively supports tracked symlinks, so producing the malicious fixture is trivial for a repository author.

### Recommendation
In `getWorkingDirectoryImage` (and any sibling working-directory-content readers in `app/src/lib/git/diff.ts`), before reading:
- `lstat` the joined path and reject/short-circuit if it is a symlink (or resolve it and verify the `realpath` is still within `repository.path`).
- More generally, verify `Path.resolve(repository.path, file.path)` stays within `repository.path` and that no path segment is a symlink, consistent with how the same fix should be applied everywhere `repository.path`/`file.path` are joined and read (e.g. `getBlobImage`'s sibling working-directory paths, staging operations, etc.).

### Proof of Concept
1. Create a repository containing a tracked symlink named `evil.png` whose target is an absolute path to a sensitive file on the victim's machine, e.g.:
   ```
   ln -s /home/victim/.ssh/id_rsa evil.png
   git add evil.png
   git commit -m "add logo"
   ```
2. Victim clones the repository with GitHub Desktop and makes/undoes any change that puts `evil.png` into the Changes list (or the attacker ships a second commit that modifies the symlink target, showing up as a working-directory or commit diff for `evil.png`).
3. Victim clicks on `evil.png` in the Changes/History view; Desktop calls `getWorkingDirectoryImage(repository, file)` at: [2](#0-1) 
4. `readFile(Path.join(repository.path, 'evil.png'))` follows the OS-level symlink and returns the bytes of `/home/victim/.ssh/id_rsa`, which are base64-encoded into an `Image` and rendered in the diff pane — confirming the read occurred outside `repository.path`.

Note: I was not able to fully confirm, within the available tool budget, whether upstream status/diff-classification code (which decides to route a given `FileChange` into `getWorkingDirectoryImage`) performs any `lstat`-based symlink filtering before dispatch; the containment gap is confirmed at the `getWorkingDirectoryImage` sink itself.

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```
