### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable received funds — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a cache returning one party's authenticated data to an unauthenticated requester — a shared-state path returning "valid-looking" output that the recipient cannot actually use. The analog in Serai is `Scanner::scan_block` in `networks/bitcoin/src/wallet/mod.rs`, which scans every transaction in a block — including the coinbase — and returns matching outputs as ordinary `ReceivedOutput`s, even though coinbase outputs are immature and unspendable for 100 blocks under consensus rules.

### Finding Description
`scan_transaction` matches any output whose `script_pubkey` is in `self.scripts` and pushes a `ReceivedOutput` carrying the offset, output, and outpoint (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` iterates `block.txdata` starting at index 0, i.e. including the coinbase transaction (`networks/bitcoin/src/wallet/mod.rs:221-227`):

```rust
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));
}
```

There is no maturity check anywhere in the in-scope wallet code — no coinbase detection, no confirmation-depth gating. The only mitigation is a doc comment: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed" (`mod.rs:218-220`). Notably, the downstream processor-side scanner *does* skip the coinbase (`processor/src/networks/bitcoin.rs:691`, `for tx in &block.txdata[1 ..]`), which shows the intended treatment — but that skip lives out of this crate's API, and any caller of `scan_block` in `networks/bitcoin` gets the immature output reported as a normal receive. Like the Directus bug, a shared/standard path returns data that looks authoritative and usable but is not valid for the recipient.

### Impact Explanation
Any miner — an unprivileged party acting only through public inputs (a Bitcoin block they produce) — can cause a `ReceivedOutput` to be reported for the multisig's key that is consensus-unspendable until 100 confirmations. If the wallet/scheduler treats the scanned output as available balance and builds a `SignableTransaction` spending it, the resulting transaction is invalid and rejected by the network, or worse, the accounting treats non-existent spendable funds as received. This matches the accepted impact class "funds reported received that are not spendable". Severity: Medium — availability/accounting correctness, no permanent loss and no secret leakage.

### Likelihood Explanation
Requires a miner to direct a coinbase output to a Serai-registered script (external or offset key). This is cheap for any miner and does not require cooperation from Serai nodes. Exploitation also requires the consumer to call `scan_block` (rather than `scan_transaction` on `txdata[1..]`) and to act on outputs without a maturity filter — plausible, since the API presents coinbase outputs identically to normal outputs.

### Recommendation
In `Scanner::scan_block`, skip `block.txdata[0]`, or track/report a maturity/confidence flag on `ReceivedOutput` for coinbase outputs so callers cannot mistake them for spendable funds. Alternatively, add a `coinbase`/`maturity` field to `ReceivedOutput` and have `scan_transaction` accept an `is_coinbase` parameter.

### Proof of Concept
1. Construct a `Scanner` for key `K` via `Scanner::new(K)` (`mod.rs:162`).
2. Mine a regtest block whose coinbase pays `p2tr_script_buf(K)` — exactly what `networks/bitcoin/tests/wallet.rs:43-52` already does with `generatetoaddress`.
3. Call `scanner.scan_block(&block)`. It returns a `ReceivedOutput` for the coinbase output (the existing test `send_and_get_output` relies on this: `wallet.rs:65-69` asserts `outputs[0]` is the coinbase output at `block.txdata[0]`).
4. Build a `SignableTransaction` spending that `ReceivedOutput` and broadcast it — the transaction is rejected as immature (`bad-txns-premature-spend-of-coinbase`), while the scanner already credited the funds.
