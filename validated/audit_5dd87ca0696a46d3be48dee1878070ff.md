### Title
Unclaimed pooling rewards are forwarded to whichever pool is *currently* configured, not the pool that earned them, allowing reward misdirection on a pool switch — (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
A PlotNFT's pending, unclaimed farming-reward coins (paid to the plot's `p2_singleton_puzzle_hash` while farming for Pool A) are not settled/forwarded before the wallet is allowed to switch the plot's pool target to Pool B. Because the forwarding puzzle is curried with whatever pool config is *currently* on the singleton at the moment the reward is swept — not the config that was active when the reward coin was created — rewards earned under Pool A can end up paid to Pool B (or to self-pooling) once the switch confirms, mirroring the "pending fee should be settled before adjusting the fee" bug class.

### Finding Description
`PlotNFT2Wallet.join_pool()`/`leave_pool()` let the owner change `pool_config.pool_puzzle_hash` (the reward distribution target) immediately, with no requirement that outstanding `p2_singleton` reward coins be swept first: [1](#0-0) . `leave_pool()` similarly starts the exit/second-pool transition without settling pending rewards: [2](#0-1) .

When a pending reward is finally swept, `forward_pool_reward()` builds the forwarding delegated puzzle from `self.guaranteed_pool_config.pool_puzzle_hash`, i.e. the *current* on-chain pool configuration of the `PlotNFT` object being spent, not the configuration that was active at the time the reward coin was farmed: [3](#0-2)  and [4](#0-3) . The on-chain CLVM (`claim_pool_rewards_dpuz.clsp`) only checks that the singleton's current puzzle hash matches and that a specific reward coin id is consumed — it has no notion of "which pool earned this reward": [5](#0-4) . The actual payout puzzle hash used is whatever `forward_pool_reward_dpuz()` was curried with at call time, i.e. the pool config live on the singleton *now*.

This is confirmed by the project's own tests, explicitly named "LOSE REWARDS (while pooling)" and "LOSE REWARDS (while leaving)", which show reward coins earned earlier being forwarded/lost according to whatever state the plot is in when swept, rather than the state under which they were earned: [6](#0-5) [7](#0-6) .

Because sweeping a pending reward coin is a plain spend of the singleton with a fixed delegated puzzle and does not require the owner's signature (it's proven via `pool_proven_spend()`, part of the trustless-pool design), the entity that currently controls the pool-facing branch of the singleton (i.e., the new pool, or the plot owner if self-pooling) can unilaterally sweep reward coins that were actually earned while the plot was assigned to a different, prior pool — as long as it does so before the old pool gets to them.

### Impact Explanation
An attacker (a new pool the owner switches to, or the owner switching to self-pooling) can capture reward coins that were farmed on behalf of a previous pool simply by winning the race to sweep them after a pool switch confirms. This is a genuine, reachable coin-value misdirection: value that should go to Pool A is redirected to Pool B/self via a single spend bundle, with no signature from Pool A required. Impact is Medium: it requires unswept reward coins to exist at switch time and a race to claim them, but the mechanism itself unconditionally pays out to "whoever is current," not "whoever earned it."

### Likelihood Explanation
Likelihood is Medium: pool switching (join/leave) is a normal, frequently-used wallet operation, and pools/farmers do not always sweep every reward coin immediately (batching, downtime, or user-initiated switches can leave rewards pending for some time). Any of the involved actors (new pool operator, or the plot owner during a self-pool transition) is economically incentivized to sweep pending rewards as soon as their pool config becomes current, so exploiting the race does not require any privileged access — only submitting a `forward_pool_reward`/RPC-equivalent spend bundle after observing the switch.

### Recommendation
Before allowing `join_pool()`/`leave_pool()` (and the two-stage `_finish_leaving_pool()` re-join) to change `pool_config.pool_puzzle_hash`, require or enforce that any outstanding `p2_singleton` reward coins be forwarded/claimed under the *current* pool config first (or block the transition until pending rewards reach zero), similar to how `PoolWallet.claim_pool_rewards()`'s unconfirmed-transaction gate protects singleton-tip integrity. Alternatively, bind the reward-forwarding delegated puzzle to the pool config that was active at the block height the reward coin was created (rather than whatever config is current at forward time), so a reward can only ever be swept to the pool that actually earned it.

### Proof of Concept
1. Owner creates a PlotNFT and joins Pool A via `PlotNFT2Wallet.join_pool()`: [8](#0-7) .
2. Farmer earns several block rewards to `p2_singleton_puzzle_hash` while farming for Pool A; these coins remain unswept (as in the "RECEIVE REWARDS (while pooling)" test step): [9](#0-8) .
3. Owner calls `join_pool()` again with Pool B's `PoolConfig`, which internally calls `leave_pool(... new_pool_config=pool_config)`, changing the on-chain pool target: [10](#0-9) .
4. Once the switch to Pool B is confirmed on-chain, anyone (in practice, Pool B's sweep bot) calls `PlotNFT.forward_pool_reward()` on the still-pending reward coins that were earned under Pool A; because `forward_pool_reward_dpuz()` is built from the *current* `pool_config.pool_puzzle_hash` (now Pool B), those coins are paid to Pool B instead of Pool A: [4](#0-3) .
5. The wallet-level test suite reproduces exactly this loss pattern under the labels "LOSE REWARDS (while pooling)" / "LOSE REWARDS (while leaving)", confirming rewards are forwarded according to the state at sweep time rather than the state at earn time: [11](#0-10) .

; This puzzle is intended to be a fixed spend path inside a Plot NFT while it is pooling
;
; The idea to send a fixed specific message to a p2_singleton (must be a farming reward)
; and then recreate the singleton exactly as it is
(mod (
    GENESIS_PREFIX
    SINGLETON_MOD_HASH
    SINGLETON_STRUCT_HASH
    REWARD_HASH
    REWARD_MESSAGE
    inner_puzzle_hash
    reward_height
    reward_amount
  )

  (include condition_codes.clib)
  (include curry.clib)

  (defun-inline calculate_pool_parent_id (GENESIS_PREFIX reward_height)
    (logior (ash GENESIS_PREFIX 128) (logand (- (lsh 1 128) 1) reward_height))
  )


  (defun-inline calculate_full_puzzle_hash (SINGLETON_MOD_HASH SINGLETON_STRUCT_HASH inner_puzzle_hash)
    (curry_hashes_inline SINGLETON_MOD_HASH
      SINGLETON_STRUCT_HASH
      inner_puzzle_hash
    )
  )

  (list
    (list ASSERT_MY_PUZZLEHASH (calculate_full_puzzle_hash SINGLETON_MOD_HASH SINGLETON_STRUCT_HASH inner_puzzle_hash))
    (list CREATE_COIN inner_puzzle_hash 1 (list SINGLETON_STRUCT_HASH))
    (list
      SEND_MESSAGE
      0x17  ; mode = puzzle sender, coin receiver -> 0x00 010 111
      REWARD_MESSAGE
      (coinid (calculate_pool_parent_id GENESIS_PREFIX reward_height) REWARD_HASH reward_amount)
    )
  )
