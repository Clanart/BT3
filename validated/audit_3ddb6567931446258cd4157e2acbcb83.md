## Analog Found

### Title
Unchecked ERC20 `transfer`/`transferFrom` return value in the CW20→ERC20 pointer contract can desynchronize CW20 accounting from actual token balances - ([File: example/cosmwasm/cw20/src/contract.rs])

### Summary
Sei's CW20-wrapping-ERC20 pointer contract (the CosmWasm contract deployed via `registerPointerForERC20`/`deployErc20PointerForCw20` to let CosmWasm callers interact with an underlying EVM ERC20 token as if it were CW20) issues the underlying `transfer`/`transferFrom` call via `EvmMsg::DelegateCallEvm` but never inspects the boolean return value of the ERC20 call. It only checks that the delegatecall itself didn't revert. This is the same bug class as the reported Amp.sol issue: any ERC20 implementation that signals failure by returning `false` instead of reverting (a common pattern predating OpenZeppelin's safe-transfer conventions) will cause the pointer to treat a failed transfer as successful.

### Finding Description
The `transfer` and `transfer_from` functions build an ERC20 call payload and dispatch it as an `EvmMsg::DelegateCallEvm`, without validating the encoded boolean result: [1](#0-0) [2](#0-1) 

`EvmMsg::DelegateCallEvm` is encoded/dispatched through the wasm binding layer as `MsgInternalEVMDelegateCall`: [3](#0-2) [4](#0-3) 

The handler for this message (`HandleInternalEVMDelegateCall`) only fails the CosmWasm execution if the underlying EVM call reverts (VM error) — it does not, and structurally cannot, decode and check the ABI-encoded `bool` return of `transferFrom`/`transfer`, because the CosmWasm message layer discards the returned bytes entirely (`add_message` does not capture return data). This mirrors exactly the Amp.sol pattern where `swapToken.transferFrom(...)` was called without a `require(...)` on its boolean result — the difference here is that the boolean is not even accessible to check, since it is dropped by the message-passing abstraction.

By contrast, the reverse pointer direction (ERC20 pointer wrapping a CW20 token) correctly treats the underlying call's `success` (i.e., whether the delegatecall reverted) as the sole success signal, which is safe because CosmWasm `execute` messages always revert on `ContractError` — there is no CW20 analog to a "return false" native token: [5](#0-4) 

However, arbitrary EVM ERC20 tokens are not required to revert on failure. Any ERC20 contract that implements `transferFrom`/`transfer` to return `false` (rather than reverting) on insufficient balance/allowance — a legacy but still-existing pattern — will cause the CW20 pointer contract's `transfer`/`transfer_from` handlers to report success (via `Response` attributes and no error) even though no value moved on the underlying ERC20 token.

### Impact Explanation
An attacker can permissionlessly register a pointer for a maliciously crafted (or simply non-standard) ERC20 token via the pointer-registration flow, then interact with it through the CW20 interface. Any CosmWasm contract or user that treats a successful `transfer_from`/`send_from` response from the pointer as proof that value moved (e.g., escrow logic, CW20 "pull payment" patterns, DEX/vault contracts that call `send_from` and rely on the accompanying `Cw20ReceiveMsg` to represent real value transferred) can be tricked into crediting balances or releasing other assets without the underlying ERC20 balance actually decreasing. This is a fund-loss/accounting-desync vector reachable purely from a submitted CosmWasm execute message against a permissionlessly created pointer.

### Likelihood Explanation
Reaching this requires: (1) deploying/registering an ERC20 pointer for an attacker-controlled or non-standard ERC20 token (permissionless, no privilege needed), and (2) a downstream CW20 consumer contract that trusts the pointer's success signal for value-transfer semantics. Both conditions are plausible in an open ecosystem where third-party ERC20 tokens are pointed and then composed with CW20-native DeFi contracts. It requires an atypical (non-reverting) ERC20 implementation, which somewhat limits likelihood but is exactly the scenario the original report calls out as a real-world risk class.

### Recommendation
In `transfer`/`transfer_from` (and any other CW20 pointer method that mutates state via `DelegateCallEvm` to an ERC20 `transfer`/`transferFrom`), do not rely solely on the CosmWasm message succeeding. Either:
- Use `EvmMsg::CallEvm`/`DelegateCallEvm` reply handling (`SubMsg` with `reply_on_success`) to decode the ABI-encoded boolean return and explicitly fail the transaction if it is `false`, or
- Add a defensive pre/post balance check (query `balanceOf` before and after) inside the wasm contract before finalizing the response, similar to how `TransferHelper.sol`/`SafeToken` in this same repo already guard against non-compliant ERC20 return values on the Solidity side.

### Proof of Concept
1. Deploy a malicious ERC20 token whose `transferFrom` returns `false` (no revert) when `amount > allowance` (i.e., does not follow OpenZeppelin's revert-on-failure convention).
2. Call `registerPointerForERC20` to create a CW20 pointer wrapping this token (permissionless, as shown in `contracts/test/CW20toERC20PointerTest.js`).
3. From the CW20 pointer, call `transfer_from` with an amount exceeding the real allowance/balance.
4. Because `transfer_from` in `contract.rs` never checks the boolean return of the underlying ERC20 call, the CosmWasm message succeeds and returns `action: transfer_from` attributes, even though the ERC20 `transferFrom` internally returned `false` and moved no tokens.
5. A downstream contract relying on this success signal (e.g., crediting internal ledger balances) would be defrauded. [6](#0-5)

func EncodeDelegateCallEVM(rawMsg json.RawMessage, sender sdk.AccAddress, info wasmvmtypes.MessageInfo, codeInfo wasmtypes.CodeInfo) ([]sdk.Msg, error) {
	encodedCallEVM := bindings.DelegateCallEVM{}
	if err := json.Unmarshal(rawMsg, &encodedCallEVM); err != nil {
		return []sdk.Msg{}, err
	}
	decodedData, err := base64.StdEncoding.DecodeString(encodedCallEVM.Data)
	if err != nil {
		return []sdk.Msg{}, err
	}
	s := sender
	if origSender, err := sdk.AccAddressFromBech32(info.Sender); err == nil {
		s = origSender
	}
	internalCallEVMMsg := types.MsgInternalEVMDelegateCall{
		Sender:       s.String(),
		To:           encodedCallEVM.To,
		CodeHash:     codeInfo.CodeHash,
		Data:         decodedData,
		FromContract: sender.String(),
	}
	return []sdk.Msg{&internalCallEVMMsg}, nil
}

    function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
        require(to != address(0), "ERC20: transfer to the zero address");
        string memory sender = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));
        string memory req = _curlyBrace(_formatPayload("transfer_from", _curlyBrace(_join(_join(sender, recipient, ","), amt, ","))));
        _execute(bytes(req));
        return true;
    }

    function _execute(bytes memory req) internal returns (bytes memory) {
        (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
            abi.encodeWithSignature(
                "execute(string,bytes,bytes)",
                Cw20Address,
                bytes(req),
                bytes("[]")
            )
        );
        require(success, "CosmWasm execute failed");
        return ret;
    }
