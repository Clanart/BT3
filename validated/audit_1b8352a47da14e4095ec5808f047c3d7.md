### Title
Missing path-containment guard when opening pull-request file changes lets a crafted diff entry escape the repository directory - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
The reported Dopex bug is a classic "guard rollout" defect: the codebase implements a security check (`whenNotPaused()`) consistently across most state-changing functions but omits it on one sibling function (`redeem()`), letting an attacker exploit the one path where the invariant isn't enforced. The same *pattern* — a path-safety guard applied in one function but missing in a structurally identical sibling function that consumes the same class of attacker-influenced data — exists in GitHub Desktop's pull-request file viewer.

### Finding Description
`Dispatcher.openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` explicitly treats a `filepath` value taken from an "Open in Desktop" deep link as untrusted, and defends against path traversal before touching the filesystem: [1](#0-0) 

It rejects absolute paths and calls `resolveWithin(repository.path, filepath)`, refusing to act if the resolved path escapes the repository root.

By contrast, `PullRequestFilesChanged` (rendered inside the "Open Pull Request" dialog, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`) builds the on-disk path for a file coming from `CommittedFileChange.path` — a value tied to the PR's diff/changeset data, i.e., content authored by whoever opened the pull request (potentially from an untrusted fork) — using plain `Path.join`, with **no** `isAbsolute`/`resolveWithin`-style containment check: [2](#0-1) [3](#0-2) 

This joined `fullPath` is then handed to three filesystem-facing actions with no re-validation:
- `revealInFileManager(repository, file.path)` — reveals the resolved path in Finder/Explorer.
- `dispatcher.openInExternalEditor(fullPath)` — launches the user's configured external editor on `fullPath`.
- `this.onOpenFile(file.path)` → `openFile(fullPath, dispatcher)` — opens `fullPath` with the OS's default handler for that file type.

The invariant "a file path derived from PR/commit data must resolve inside `repository.path`" is enforced in the deep-link handler but not enforced here, even though both code paths ultimately do the same kind of thing (turn an untrusted relative path string into a filesystem action).

### Impact Explanation
If `file.path` can ever contain `..` segments or otherwise resolve outside the repository (e.g., through a crafted tree/rename/copy entry in a PR's diff, or a bug in how `CommittedFileChange.path`/`oldPath` is derived from the diff parser or GitHub API `filename`/`previous_filename` fields), the resulting `Path.join(repository.path, path)` would escape the repository sandbox. Downstream, `openFile`/default-program-open and "open in external editor" execute an OS-level action on a file outside the repo, and depending on the file's registered handler this can range from information disclosure (revealing/executing an arbitrary file on disk) to code execution via a file type associated with an executable handler. This directly matches the "file read/write outside the repo" and "code execution via untrusted repository/API content" categories in the report's valid-impact criteria.

### Likelihood Explanation
Likelihood is **moderate to low** and could not be fully confirmed with the available tooling/index. Git's own plumbing normally rejects tree entries whose names contain `..` path components, and the diff parser used for local commit ranges (`app/src/lib/git/diff.ts`) passes paths through `ensureRelativePath`. Whether the PR dialog's `changesetData.files` are always sourced through that same sanitized git path, or can instead be populated from raw GitHub API `filename` strings before the PR is fully fetched/checked out locally (the component explicitly supports a `nonLocalCommitSHA` state, implying file lists can be shown before local checkout), is the open question — I was not able to trace `commitSelection.changesetData` all the way back to its origin within the remaining tool budget. This is exactly the kind of ambiguity that the dispatcher.ts author clearly worried about, since they added the `isAbsolute`/`resolveWithin` guard specifically for attacker-influenced path strings arriving via a similarly "external" channel (a deep link). The asymmetry between the two code paths is the concrete, verifiable defect; whether it is reachable end-to-end depends on the exact provenance of `file.path`, which the index does not let me confirm with full certainty.

### Recommendation
Apply the same containment check used in `dispatcher.ts` (`isAbsolute` rejection + `resolveWithin(repository.path, file.path)`) before computing `fullPath` in `PullRequestFilesChanged.onFileContextMenu`, `onOpenFile`, and `onRowDoubleClick`, and reject/refuse the action (with a log message, matching the existing pattern) if the resolved path is not contained within `repository.path`. Consider centralizing this into a single helper (e.g. `resolveRepositoryFilePath(repository, path)`) used by every UI surface that turns a diff/commit/PR-sourced relative path into a filesystem action, so the guard can't be silently omitted from future call sites.

### Proof of Concept
Not independently verified end-to-end due to index/tool limitations — verifying this would require confirming (a) whether `CommittedFileChange.path` for a PR's file list can be populated with a `../`-containing string before/without a sanitized local git diff, and (b) reproducing that GitHub API/diff response locally. I recommend a Devin session with full repo/checkout access to trace `commitSelection.changesetData` population (`app-store.ts`, `repository-state-cache.ts`) back to its data source and, if confirmed exploitable, add a regression test analogous to `app/test/unit/path-test.ts`'s `resolveWithin` tests but exercised through `PullRequestFilesChanged`.
