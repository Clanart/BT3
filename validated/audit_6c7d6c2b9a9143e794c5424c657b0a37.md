### Title
Empty aggregate signature verifies successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` validates only that the number of nonces equals the number of supplied signer/challenge pairs, but does not reject an empty aggregate. An attacker can therefore supply `Rs = []` and `s = 0`, causing the verification equation to contain only `0 * G` and evaluate to identity.

### Finding Description
`SchnorrAggregate::read` accepts a serialized aggregate whose nonce vector length is zero. `SchnorrAggregate::verify` then checks `self.Rs.len() == keys_and_challenges.len()`, builds no signer terms when both are empty, and evaluates only `(-self.s, C::generator())`. With `s = 0`, this is the identity, so verification returns `true`.

This is inconsistent with `SchnorrAggregator::complete`, which explicitly refuses to produce an aggregate when no signatures were aggregated. The producer-side invariant therefore exists, but the verifier-side path does not enforce it—the same missing-validation pattern as the referenced finding.

### Impact Explanation
Any caller that interprets `verify(..., &[])` as authorizing a message, without independently enforcing a non-empty signer set or quorum, will accept an attacker-created aggregate signature for arbitrary messages and arbitrary domain separators. The forged object requires no private key or nonce knowledge.

Within Serai’s Tendermint adapter, quorum weight is checked separately after aggregate verification, reducing the immediate impact there. The primitive API nevertheless has an incorrect verifier edge case and can be unsafe for other in-scope consumers.

### Likelihood Explanation
Exploitation requires a reachable path where an unprivileged party controls the aggregate signature bytes and the caller invokes verification with an empty signer list. The primitive accepts this directly from serialized input, but deployments that independently require positive signing weight prevent the impact. Medium severity is appropriate because authorization bypass requires this integration-specific edge case rather than a malicious validator or leaked secret.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify`, matching `SchnorrAggregator::complete`:

```rust
if self.Rs.is_empty() || (self.Rs.len() != keys_and_challenges.len()) {
  return false;
}
```

Also consider rejecting empty aggregates during `SchnorrAggregate::read` so malformed serialized values cannot be represented.

### Proof of Concept

```rust
use dalek_ff_group::{Ristretto, Scalar};
use group::ff::PrimeField;
use schnorr::aggregate::SchnorrAggregate;

const DST: &[u8] = b"test aggregate DST";

let mut bytes = Vec::new();
bytes.extend(0u32.to_le_bytes()); // zero Rs
bytes.extend(Scalar::ZERO.to_repr()); // s = 0

let aggregate = SchnorrAggregate::<Ristretto>::read(&mut bytes.as_slice()).unwrap();

// No signers and no signatures, yet verification succeeds.
assert!(aggregate.verify(DST, &[]));
```
