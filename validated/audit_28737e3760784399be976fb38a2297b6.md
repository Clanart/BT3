### Title
Unprivileged Bandwidth-Subscription Eviction Griefing Destroys Another App's Paid, Unconsumed Allowance - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s sponsorship feature lets *anyone* pay for bandwidth on behalf of *any* `(app_chain, app)` pair, because the credited app identity is taken entirely from the purchaser-supplied message body rather than tied to `request.from`/`request.source`. The subscription list per `(app_chain, app)` is capped at `MAX_SUBSCRIPTIONS = 1024` and, on overflow, unconditionally evicts the oldest entry regardless of how much it paid or how many `remaining_bytes` it still has. An attacker can therefore spam cheap-tier purchases targeting a victim app's key to push its list to the cap and evict the victim's large, unconsumed, still-valid subscription — a real loss of already-paid funds/entitlement for the victim.

### Finding Description
The purchase flow is:
1. Anyone calls `purchase()` on a registered `BandwidthManager` on any source chain, paying the tier price, and encodes `BandwidthPurchaseMsg { app, tier, months, chain }` — `app` and `chain` (the *credit* chain, called `app_chain`) are caller-supplied, arbitrary values [1](#0-0) .
2. On Hyperbridge, `Pallet::on_accept` only checks that `request.from` matches the registered manager for `request.source` — it does **not** check that the purchaser is, or is authorized by, the app being credited [2](#0-1) .
3. `push_subscription` appends the new entry to `Allowance::<T>` keyed by `(msg.chain, key)`, and if the list is already at `MAX_SUBSCRIPTIONS` (1024), it unconditionally removes index `0` — the FIFO head — regardless of that entry's remaining bytes, tier, or expiry, and only emits an audit event; it does not block or compensate [3](#0-2) .

Because sponsorship is intentionally open ("a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`" — [1](#0-0) ), and because the eviction target is always the oldest entry irrespective of who paid or how much bandwidth remains, an attacker who is not the app owner can drive the victim's list to the 1024-entry cap with minimal-tier purchases, forcing eviction of the victim's legitimately-purchased, unconsumed, higher-value subscription. This is exactly analogous to the TrueFi report's core flaw: an entity other than the depositor (there: the Sherlock admin triggering `liquidExit`; here: an unrelated third-party purchaser) can force a withdrawal-like event (subscription eviction) on someone else's deposited value, with no safeguard tying the loss to consent of, or benefit to, the party whose funds/entitlement are destroyed.

### Impact Explanation
This directly causes loss of paid-for bandwidth allowance for the targeted app — the victim already paid the fee-token cost for that subscription (e.g. the $1000/8MB tier) but the entry can be evicted before a single byte of it is consumed, purely because a griefer purchased enough cheap-tier subscriptions against the same `(app_chain, app)` key. This is unauthorized destruction of another party's prepaid balance via a fully public, permissionless entrypoint (`purchase()`), matching the bounty's "stealing or loss of funds" / "logic attacks" category — it requires no relayer, prover, admin, or leaked key, only calling a public contract function.

### Likelihood Explanation
Likelihood is bounded by cost: the attacker must fund `1024` (or fewer, if the list is already partially filled) cheapest-tier purchases targeting the victim's exact `(app_chain, app)` key to force the eviction. At the documented $50/tier this is up to ~$51,200 in attacker capital, refundable in the sense that the attacker also receives bandwidth for their spam purchases (on the same app key, which they don't want/need) but this is a real, deterministic, low-complexity attack path with no cryptographic or timing barriers — any competitor or malicious actor targeting a high-value app (e.g. a core token gateway) that has meaningfully less than 1024 live subscriptions can execute it directly.

### Recommendation
Do not let eviction be purely FIFO/insertion-order-blind to payer identity and remaining value. Options: (1) restrict `push_subscription`'s effective app key to require `request.from == app` (or an authorization mapping) so only the app itself, or an explicitly whitelisted sponsor, can credit it; (2) when evicting under the cap, prefer evicting entries nearest to expiry rather than strictly the oldest by insertion order, so purchasing many long-duration cheap subscriptions cannot be used to bump out a valid, far-from-expiry high-value entry; (3) track remaining-bytes-weighted eviction cost so an attacker cannot destroy more `remaining_bytes` than they've paid for.

### Proof of Concept
1. Victim app `A` on chain `C` is credited a `TierFour` ($1000, 8MB) subscription via a legitimate purchase — `Allowance[C][A]` now has 1 entry with `remaining_bytes = 8MB` and a `purchased_at` timestamp `T0`.
2. Attacker calls `BandwidthManager.purchase()` on any registered source chain 1023 times (or fewer, if other entries already exist), each time encoding `BandwidthPurchaseMsg { app: A, chain: C, tier: TierOne, months: 1 }` — the manager only requires payment of the `TierOne` price ($50) and does not check the caller owns `app` [2](#0-1) .
3. Each purchase's `on_accept` calls `push_subscription(C, A, TierOne, ...)`, and once `Allowance[C][A]` hits `MAX_SUBSCRIPTIONS = 1024`, further purchases each evict the current oldest entry (`list.remove(0)`) [4](#0-3) .
4. Once the attacker's purchases exceed the number needed to push the original `TierFour` entry to index 0 and then evict it, `A`'s 8MB, still-valid, unconsumed subscription is permanently gone — `SubscriptionEvicted { app: A, tier: TierFour, lost_bytes: 8MB }` fires, but `A` receives no compensation and cannot recover the lost bandwidth or the fee it paid for it.

		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;

				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);
