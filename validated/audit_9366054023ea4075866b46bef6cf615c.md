### Title
Balance handler event replay across nested precompile revert boundaries can desync EVM StateDB balances from bank state - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`, `x/vm/statedb/journal.go`)

### Summary
The external report describes `MainController._update_rate()` consuming a stale `total_debt` because the accounting value is read/used before the authoritative state is updated. The closest reachable analog in this repository is the `BalanceHandler`'s reliance on `ctx.EventManager().Events()` as the sole source of truth for reconciling `x/bank`/`x/precisebank` state changes into the EVM `StateDB`, combined with nested/recursive precompile calls that can revert independently of the outer call via the `precompileCallChange` journal/snapshot mechanism [1](#0-0) . Events emitted by an inner precompile call that is later reverted are not guaranteed to be excised from `ctx.EventManager().Events()` in the same way the underlying `MultiStore`/bank state is rolled back via `RevertToSnapshot`, creating a window where `AfterBalanceChange` could apply `StateDB.AddBalance`/`SubBalance` deltas derived from events belonging to a reverted sub-call.

### Finding Description
Each precompile invocation records `prevEventsLen` at the start (`BeforeBalanceChange`) and, after the native action executes, slices `ctx.EventManager().Events()[prevEventsLen:]` to derive balance deltas to apply to the `StateDB` (`AfterBalanceChange`) [2](#0-1) [3](#0-2) . In `runNativeAction`, the sequence is: snapshot the multi-store and events, commit the cache context, run the native action, then reconcile balances from the event log [4](#0-3) . Reverts of nested precompile calls are implemented via `AddPrecompileFn`, which journals a `(snapshot, events)` pair for later `RevertToSnapshot` handling in `x/vm/statedb/journal.go` and `statedb.go` [5](#0-4) . The store portion of a reverted nested call is rolled back through the `MultiStoreSnapshot`/`RevertToSnapshot` mechanism, but the event-manager events consumed by `AfterBalanceChange` are tracked by simple slice length (`prevEventsLen`), not through the same journaled snapshot/rollback path shown for the store. If the SDK event manager's events are not pruned back to the pre-call length when a nested precompile call reverts, an *outer* `AfterBalanceChange` invocation that later re-reads `ctx.EventManager().Events()[prevEventsLen:]` can still observe `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events emitted by the already-reverted inner call, and apply their deltas to `StateDB` even though the corresponding bank/precisebank store mutation was rolled back. The repository's own test suite explicitly documents this class of issue: `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` states it "tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [6](#0-5) , and `evmd/tests/integration/balance_handler/balance_handler_test.go` documents a related bug "where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten... leads to balance desync between native bank keeper and EVM stateDB" [7](#0-6) .

However, I was unable to fully confirm within this session whether the production precompile call path (`common.Precompile.RunNativeAction`, used by `staking`, `distribution`, `gov`, `slashing`, `erc20`, `ics20` precompiles) is actually vulnerable, because:
- Production precompiles obtain a **fresh** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` inside `runNativeAction` [8](#0-7) , which appears to avoid the "shared instance/overwritten prevEventsLen" variant of the bug that the debug-precompile test explicitly targets (that test uses a bespoke `testutil/testdata/debug` precompile with a single persistent `balanceHandler` field via `GetBalanceHandler()`, not the production factory pattern) [9](#0-8) .
- I could not locate and inspect the exact revert path in `x/vm/statedb/journal.go` that processes `precompileCallChange.events` during `RevertToSnapshot` to determine definitively whether it truncates `ctx.EventManager()`'s event list back to the pre-call snapshot, or only reverts the `MultiStore`. Confirming this requires reading the `Revert()` implementation of `precompileCallChange` in `journal.go`, which I did not have remaining tool budget to inspect.

### Impact Explanation
If confirmed exploitable through a production precompile call chain (e.g., a contract that calls the `staking`/`distribution`/`ics20` precompile, which internally triggers a nested precompile call that reverts, e.g. via `try/catch` as demonstrated in `StakingReverter.sol`'s `performDelegation`/`nestedTryCatchDelegations` patterns [10](#0-9) ), an attacker could cause the EVM `StateDB` to credit or debit balances that do not correspond to actual bank-module state changes. This is exactly the invariant-breaking pattern targeted by the "Asset-representation path" gate (1:1 accounting between native coins and EVM/precompile-visible balances): a desync would let a user's EVM-visible balance diverge from their real, spendable bank balance, enabling unauthorized "phantom" balance credit (mint-equivalent) or an incorrect debit (fund-lock/loss) depending on event direction.

### Likelihood Explanation
Uncertain — I could not verify from available code whether (a) the production per-call `BalanceHandler` instantiation neutralizes the "shared instance" bug variant, and (b) whether the `precompileCallChange` journal entry's revert actually truncates the SDK event manager's events, closing the "stale reverted events aggregated by outer call" variant. Both repo-included tests (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) suggest these bug classes were known and are being actively tested against, which could mean they are already fixed by the surrounding infrastructure (snapshot/revert code) rather than exploitable in current production precompiles.

### Recommendation
- Have the `precompileCallChange.Revert()` implementation in `x/vm/statedb/journal.go` explicitly truncate/reset `ctx.EventManager()`'s event slice back to the journaled `events` snapshot when a nested precompile call is reverted, not just the `MultiStore`.
- Ensure `AfterBalanceChange` only processes events whose associated store mutation is still live (not part of a rolled-back snapshot range), e.g., by re-deriving balance deltas directly from the (already-reverted) `MultiStore` state rather than from the append-only event log.
- Extend `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` and `evmd/tests/integration/balance_handler/balance_handler_test.go` assertions to cover production precompiles (staking/distribution/ics20 with real nested-revert contracts) rather than only the debug precompile, to close the gap in verification identified above.

### Proof of Concept
Not constructed — verifying a working PoC requires reading the `Revert()` method for `precompileCallChange` in `x/vm/statedb/journal.go` (not retrieved in this session) to confirm whether reverted-call events remain visible to the outer `AfterBalanceChange` call. Given this unresolved uncertainty about whether existing revert/snapshot logic already guards the invariant, this should be treated as a **candidate requiring further code-level verification** rather than a confirmed Critical finding.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

// AddPrecompileFn adds a precompileCall journal entry
// with a snapshot of the multi-store and events previous
// to the precompile call.
func (s *StateDB) AddPrecompileFn(snapshot int, events sdk.Events) error {
	s.journal.append(precompileCallChange{
		snapshot: snapshot,
		events:   events,
	})
	s.precompileCallsCounter++
	if s.precompileCallsCounter > types.MaxPrecompileCalls {
		return fmt.Errorf("max calls to precompiles (%d) reached", types.MaxPrecompileCalls)
	}
	return nil
}

    /// @dev nestedTryCatchDelegations performs nested try/catch calls to precompile
    /// where inner calls revert intentionally. Only the successful delegations
    /// outside the reverting scope should persist.
    ///
    /// Expected successful delegations: 1 (before loop) + outerTimes (after each catch) + 1 (after loop)
    function nestedTryCatchDelegations(uint outerTimes, uint innerTimes, string calldata validatorAddress) external {
        // Initial successful delegate before any nested reverts
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

        for (uint i = 0; i < outerTimes; i++) {
            // Outer call that will revert and be caught
            try StakingReverter(address(this)).performDelegation(validatorAddress) {
                // no-op
            } catch {
                // After catching the revert, perform a successful delegate
                STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

                // Inner nested loop of reverting calls
                for (uint j = 0; j < innerTimes; j++) {
                    try StakingReverter(address(this)).performDelegation(validatorAddress) {
                        // no-op
                    } catch {}
                }
            }
        }

        // Final successful delegate after the loops
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);
    }
