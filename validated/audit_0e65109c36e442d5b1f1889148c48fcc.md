## Analysis

The M‑1 root cause is generic: code computes an amount to sweep/deposit by reading `balanceOf(address(this))` (the whole balance) instead of the delta actually produced by the current operation, so unrelated funds sitting in the contract get swept in and misattributed to the current operation.

The exact same pattern exists in `IntentGatewayV2.placeOrder`'s predispatch-sweep step. The `dispatcher` (`_params.dispatcher`) is a single, persistent, publicly-known `CallDispatcher` contract shared by **every** order across the gateway's lifetime — it is not a fresh per-order contract. When a predispatch call is present, the gateway sweeps back **the dispatcher's entire current balance** of each `order.inputs[i].token`, not the amount actually produced by *this* predispatch call: [1](#0-0) 

```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token, value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
balancesBefore[i] = IERC20(token).balanceOf(address(this));
```

then the gateway credits `order.inputs[i].amount` from what it measured as "received": [2](#0-1) 

If `received <= order.inputs[i].amount` the order is accepted at that (possibly stray-funded) amount with no revert; if `received > order.inputs[i].amount` the excess is only logged as protocol `DustCollected`, never returned to whoever's earlier predispatch actually produced it. Because the dispatcher is shared and has no access control on inbound transfers, any token that a predispatch call produces but that isn't listed in that order's `order.inputs` (e.g., swap byproducts, referral/reward tokens, rounding remnants) is left stranded in `dispatcher` — there is no code path that returns it to its rightful owner. It sits there until some **later, unrelated** `placeOrder` call happens to list that same token in its `inputs`; that unrelated order's sweep then vacuums up the stranded balance and credits it as if it were freshly produced by its own predispatch call. This lets a caller (1) fabricate/inflate the escrowed amount of their own order using dust that belongs to an earlier order/user, or (2) deliberately pre-seed the dispatcher with tokens via a plain `transfer()` and place a trivially-cheap predispatch order that "launders" the pre-seeded balance into its own escrow accounting — mirroring exactly the audited bug's "whole balance swept instead of just the funds produced by this operation."

### Title
Shared `CallDispatcher` balance sweep in `IntentGatewayV2.placeOrder` misattributes stray/pre-existing token balance to unrelated orders - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s predispatch flow sweeps `IERC20(token).balanceOf(dispatcher)` — the dispatcher's *entire* current balance — instead of the delta actually produced by the current predispatch call, then credits the swept amount as the order's escrowed input.

### Finding Description
`_params.dispatcher` is one persistent `CallDispatcher` instance reused by every `placeOrder`/fill call for the gateway's lifetime [3](#0-2) . It is a plain contract with no restriction on who can send it tokens/ETH. In the predispatch sweep, the amount transferred back to the gateway is `balance = IERC20(token).balanceOf(dispatcher)` — the dispatcher's whole balance for that token — not `balanceAfter - balanceBeforeThisCall` [4](#0-3) . The subsequently measured `received` is then written directly into `order.inputs[i].amount` when it is at or below the required amount, with no check that this amount was actually generated by the just-executed predispatch call [2](#0-1) . Any token balance a prior predispatch call produced but did not list among that order's `inputs` (a very plausible outcome of arbitrary swap/DeFi calldata) is stranded in the shared dispatcher with no return path to its producer, and is instead absorbed by whichever future order happens to include that token as an input.

### Impact Explanation
Escrowed order inputs can be funded, in whole or in part, by tokens that do not belong to the current caller's transaction — either dust orphaned by an earlier unrelated order's predispatch execution, or tokens an attacker pre-seeds directly into the well-known, unguarded `dispatcher` address. This breaks the invariant that escrowed/bridged funds move "exactly once and only to the rightful beneficiary and amount," since the source of the escrowed value is conflated with whatever balance happens to be sitting in a shared, persistent contract at call time.

### Likelihood Explanation
No relayer, prover, admin, or malicious peer is required. Any user calling `placeOrder` with `predispatch.call`/`predispatch.assets` set can trigger the sweep; an attacker only needs a plain `IERC20.transfer` to the (publicly known, address in `params()`) dispatcher followed by a cheap `placeOrder` call to attempt to launder stray balance into their own order's escrow. The precondition of a nonzero stray/lingering token balance in `dispatcher` naturally recurs whenever any predispatch call's calldata produces a token not enumerated in `order.inputs`.

### Recommendation
Track a per-token balance snapshot immediately before executing the predispatch call (`balancesBefore[i] = balanceOf(dispatcher)` taken pre-dispatch) and sweep only the delta (`balanceOf(dispatcher) - balancesBefore[i]`) produced by this specific call, exactly as the M‑1 fix recommends distinguishing pre-existing balance from funds acquired by the current operation. Any token balance that legitimately remains in the dispatcher afterward should be swept to a protocol treasury via an explicit, access-controlled sweep rather than silently absorbed into the next unrelated order that references the same token.

### Proof of Concept
1. Read `dispatcher = IntentGatewayV2.params().dispatcher` (public getter).
2. Send `T` tokens directly to `dispatcher` via `IERC20(T).transfer(dispatcher, X)` from any account — no access control prevents this.
3. Call `placeOrder` with a minimal/cheap `predispatch.call` (any no-op-ish call satisfying `predispatch.call.length > 0`) and `predispatch.assets` funding some trivial unrelated token, while setting `order.inputs[0] = {token: T, amount: X}`.
4. In the sweep step, `balance = IERC20(T).balanceOf(dispatcher) == X` (pre-seeded, not produced by the predispatch call executed in step 3), so `received == X == requiredAmount`, and `order.inputs[0].amount` is accepted as `X` with the tokens now escrowed under the attacker's commitment — funded by balance that predates and is unrelated to this transaction's predispatch execution.
