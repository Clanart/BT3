### Title
Unauthenticated operator attribution in withdrawal payout OP_RETURN allows crediting reimbursement to an operator that never funded the payout - (core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` extracts the "payer" operator identity purely from an OP_RETURN output that is *not* covered by the withdrawer's `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` signature, and stores it in the database without checking that the named xonly key belongs to `deposit_data.actors.operators` or that the named party actually supplied the payout funds. Because only output 0 (amount + script) is signed, anyone completing the transaction can attach any operator's public key (or an arbitrary key) to the OP_RETURN, fabricating who is later treated as having fronted the withdrawal.

### Finding Description
The intended binding is: `recorded_payer_xonly_pk == the operator whose own BTC funded output 0 of the payout tx`, and that operator must additionally be a member of `deposit_data.actors.operators` for that deposit.

In `update_finalized_payouts`, the verifier locates the payout transaction in the block, extracts the first OP_RETURN output, and derives `operator_xonly_pk` directly from its bytes: [1](#0-0) 
with no verification that:
- the named key belongs to `deposit_data.actors.operators` for this deposit, or
- the named party actually controls/signed the additional input(s) that fund output 0.

The result is written unconditionally into the payout/withdrawal tracking table: [2](#0-1) 

The withdrawal's user-side authorization only covers output 0's amount and script via `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, meaning any party (including this attacker) can add the fee-paying input(s) and the OP_RETURN output containing an arbitrary xonly public key while still producing a transaction that satisfies output 0 exactly as required. This lets an unprivileged attacker with only fee-paying BTC complete a valid payout transaction and unilaterally decide which xonly key — including a real operator's key who never spent anything, or a key not present in `deposit_data.actors.operators` at all — is recorded as the payer for that withdrawal index.

`update_finalized_payouts` performs no cross-reference against the deposit's registered operator set and no check that the named key's holder actually signed/funded the non-signature-covered parts of the transaction. This is the exact break identified in the question: `parse_op_return_data`/`XOnlyPublicKey::from_slice` accept any 32 bytes with no membership or funding-authorization check.

### Impact Explanation
If the recorded `operator_xonly_pk` for a withdrawal index is later relied upon (directly or by any downstream consumer/state-machine step) to authorize release of bridge/move-to-vault collateral to that operator for "having funded" the payout, then:
- An operator can be credited with (and potentially reimbursed for) a payout it never funded — collateral/bridge value tied to that withdrawal index is released to a party that spent nothing, which is one of the explicitly listed Critical categories ("an operator reimbursed for a payout it never funded").
- Because the attacker only needs fee-paying BTC and a mempool-visible/obtainable withdrawal signature, this is repeatable across every withdrawal and every deposit, and the attacker can target any operator (or any non-operator key) at will.

I was not able to fully trace, within the available iterations, the exact downstream consumer that gates the Reimburse/Kickoff signing decision on this stored `operator_xonly_pk` value (e.g., inside `core/src/states/kickoff.rs` or `is_kickoff_malicious`), so I cannot confirm with full certainty that this unauthenticated value is the sole/final authorization gate for releasing collateral, versus being informational bookkeeping cross-checked against additional signature-based proof of operator participation elsewhere in the reimbursement transaction graph. This uncertainty should be resolved before treating the impact as conclusively demonstrated.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged attacker model: fee-paying BTC and observation of a withdrawal's `SIGHASH_SINGLE|ANYONECANPAY` signature (obtainable via `withdraw()` calls or mempool visibility). No verifier, operator, or aggregator privilege is required, and the attack is repeatable per withdrawal with no rate limiting relevant to this bug.

### Recommendation
In `update_finalized_payouts` (core/src/verifier.rs), after parsing `operator_xonly_pk` from the OP_RETURN, validate membership against `deposit_data.actors.operators` for the corresponding deposit before persisting it, and require that the actual funding/spending input(s) of the payout transaction be verifiably controlled by that same key (e.g., via a signature check binding the OP_RETURN identity to the input that pays the withdrawal amount) before treating it as authoritative "payer" data used anywhere in the reimbursement decision path.

### Proof of Concept
```
cargo test -p core update_finalized_payouts_accepts_unauthorized_operator_pk
```
Test plan:
1. Set up a deposit with `deposit_data.actors.operators = [OperatorA_pk]`.
2. Construct a valid withdrawal payout transaction whose output 0 satisfies the withdrawer's `SIGHASH_SINGLE|ANYONECANPAY` signature exactly (amount/script fixed), but attach an OP_RETURN containing `OperatorB_pk` (not in `operators`, or a random key not corresponding to whoever funded the extra input).
3. Feed the block containing this tx into `update_finalized_payouts`.
4. Assert (both sides of binding, before/after):
   - Before: no DB row exists for this withdrawal index with a payer key.
   - After: `db.get(payout row).operator_xonly_pk == OperatorB_pk` is stored despite `OperatorB_pk ∉ deposit_data.actors.operators` and despite `OperatorB` never signing/funding the transaction — demonstrating `update_finalized_payouts` performs no membership or funding-authorization check.
