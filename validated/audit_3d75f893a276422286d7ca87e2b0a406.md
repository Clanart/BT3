### Title
Single failing token transfer in `withdraw()` permanently locks an entire order's multi-token escrow (redeem and refund both blocked) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The external report describes a bridge/vault position that becomes permanently un-unwindable because a single external call (`remove_liquidity_one_coin`) reverts forever once `is_killed` is set, causing total loss of the position. The local analog is `IntentGatewayV2.withdraw()`, which iterates over *all* of an order's escrowed tokens (plus the fee token) in one atomic loop and reverts the entire withdrawal if even one token's low-level `.call` transfer fails — with no isolation, retry, or partial-settlement path.

### Finding Description
`withdraw()` is the single internal function used both to redeem escrow to a solver and to refund escrow to a user: [1](#0-0) 

For each token in `body.tokens`, it performs a raw `.call` transfer and reverts the whole function (via `TransferFailed()`/`InsufficientNativeToken()`) if that single transfer fails: [2](#0-1) 

This function is reached from three call sites with no per-token isolation (no try/catch):
- `onAccept()` for both `RequestKind.RedeemEscrow` and `RequestKind.RefundEscrow`, which is the *only* path that releases cross-chain escrow after the host authenticates the request: [3](#0-2) 
- `cancelOrder()` same-chain refund path: [4](#0-3) 

An order's `inputs` array can contain multiple distinct ERC-20 tokens escrowed together under one `commitment` (built up per-token in `_orders[commitment][token]` during order placement): [5](#0-4) 

If **any single one** of those tokens becomes non-transferable to the current `beneficiary` for reasons entirely outside the protocol's control — e.g. the token's issuer blacklists that address (USDC/USDT-style), pauses transfers, or the beneficiary is a contract that reverts on receipt — the low-level `.call` fails and `TransferFailed()` reverts the **entire** `withdraw()` call. Because `_orders[commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` are written in the same atomic transaction as the transfers, the revert rolls all of it back. There is no mechanism to skip the poisoned token and still release the other tokens/fees, and no path exists to reassign/rotate the beneficiary for that commitment. Both the redeem branch (payment to the solver) and the refund branch (return to the order's `user`) are permanently blocked for that commitment, exactly like `remove_liquidity_one_coin` reverting forever once `is_killed` is set in the CurveSpell analog — a single always-failing external call permanently prevents unwinding/settlement, with the difference here that *all* other escrowed assets under that commitment (not just the affected token) become unrecoverable too, since the loop and fee redemption for the whole order are gated behind the same atomic call.

### Impact Explanation
This falls under "loss/lock of funds" in the accepted impact categories. All input tokens escrowed under an order commitment (potentially including unrelated, perfectly-transferable tokens and the accumulated transaction fee), not just the poisoned one, become permanently stuck once one token transfer to the current beneficiary starts failing — with no recovery, retry-with-different-beneficiary, or partial-withdrawal mechanism in the contract.

### Likelihood Explanation
Requires only that one of the order's escrowed ERC-20 tokens implement a blacklist/pause capability (common for USDC/USDT-class stablecoins that are realistic intent-gateway settlement assets) and that the specific beneficiary address gets blacklisted, or that the beneficiary is later paused/blocked before settlement completes. This needs no malicious relayer, prover, or admin — any unprivileged token issuer action (or the beneficiary itself becoming non-receiving) triggers it, and it is entirely locally verifiable from the atomic, non-isolated token loop in `withdraw()`.

### Recommendation
Isolate each token transfer in `withdraw()` behind a `try/catch` (or track per-token completion state) so a single failing transfer cannot block release of the remaining tokens and fees for the same commitment; additionally, provide a governance/permissionless "sweep to escrow-holding" fallback for tokens that permanently fail transfer to the designated beneficiary, so funds are never irrecoverably locked.

### Proof of Concept
1. User places a cross-chain order whose `inputs` include Token A (freely transferable) and Token B (a blacklist-capable stablecoin), escrowed together under one `commitment`.
2. Before the order is filled, Token B's issuer blacklists `order.user` (e.g., due to an unrelated compliance action) — no protocol actor needs to be malicious.
3. The order expires unfilled; anyone triggers the cancellation/refund flow, which resolves to `onAccept()` → `withdraw(body, true)`.
4. Inside `withdraw()`, the loop reaches Token B's transfer, which reverts (`token.call(transfer(...))` returns `success=false`), causing `TransferFailed()` and reverting the whole transaction.
5. Token A, which had no issue, is now also permanently unrecoverable, because every future retry of `withdraw()` for this `commitment` hits the same Token B revert — the order can never be settled or refunded.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
