## Answer

The Sherlock finding's underlying invariant break is: **the code computes an "expected" outcome from stale/pre-transfer state, and then applies a state-changing operation using that stale value instead of re-validating actual on-disk state, with no verification mechanism (no context check) to catch drift.** The strongest analog I could find in this codebase is in the *discard changes* patch application path, which builds and applies a **zero-context** patch derived from a diff snapshot that can go stale between the time it is computed/shown to the user and the time it is actually applied to the working directory.

### Title
Silent working-directory corruption via stale zero-context patch in `discardChangesFromSelection` - (File: app/src/lib/git/apply.ts)

### Summary
`discardChangesFromSelection` builds a patch from a caller-supplied `ITextDiff` snapshot and a `DiffSelection`, then applies it with `git apply --unidiff-zero` [1](#0-0) . Unlike `applyPatchToIndex` used for partial staging, which re-fetches a fresh diff (`getWorkingDirectoryDiff`) immediately before formatting the patch [2](#0-1) , `discardChangesFromSelection` never re-reads the working directory — it trusts whatever `diff` object it was handed.

### Finding Description
The `diff` passed into `discardChangesFromSelection` originates from UI state that can be arbitrarily old relative to the moment of application:
- In the side-by-side diff view, `onDiscardChanges` explicitly passes `this.props.diff` — noted in a comment as intentionally "the original diff (from props) instead of the (potentially) expanded one" [3](#0-2) .
- When confirmation is required, that same stale `diff`/`selection` pair is stashed into a popup (`PopupType.ConfirmDiscardSelection`) and rendered later in `DiscardSelection`, which only calls `discardChangesFromSelection` once the user clicks confirm [4](#0-3) [5](#0-4) .
- `formatPatchToDiscardChanges` constructs the patch purely from that stale diff/selection, with no re-validation against current file contents [6](#0-5) .
- The patch is applied with `--unidiff-zero`, i.e. hunks carry **zero context lines**, so `git apply` matches hunks by line offset only, not by verifying surrounding content [7](#0-6) .

If the working directory file is modified between diff computation/dialog display and the user's confirm click (e.g., an external editor autosave, a build/watch tool, a git hook triggered by another Desktop operation, or simply another rapid discard/checkout the app itself performed), the previously computed line numbers may no longer correspond to the same content. Because there are no context lines to detect this mismatch, `git apply --unidiff-zero` can still "succeed" — inserting/removing lines at the recorded line numbers of what is now different content, rather than failing loudly the way a normal, context-bearing patch would.

### Impact Explanation
This is the same broken invariant as the ERC20 fee-on-transfer bug: an operation is completed using an expected/stale value (line offsets from an old diff) instead of the actual current state, and the zero-context patch format removes the one safety check (context-line comparison) that would otherwise catch the drift. The result is silent corruption of the user's working directory content — lines can be dropped or inserted at the wrong place without any error surfaced to the user, directly matching the "silent corruption of what the user commits or pushes" impact category, since a subsequent commit will capture the corrupted file.

### Likelihood Explanation
The window is bounded by how long the diff/selection persists before being applied — trivially widened when `askForConfirmationOnDiscardChanges` is enabled, since the app waits for explicit user interaction on the `ConfirmDiscardSelection` dialog while holding the old diff. It also depends on something else touching the file during that window (external process, editor, or another git operation), which is a plausible but not attacker-controlled scenario in the strict sense required (no remote/malicious repo content is directly the trigger here — it is a TOCTOU in local file state).

### Recommendation
Re-fetch (or at minimum re-validate) the diff for the target file immediately before constructing/applying the discard patch, mirroring the pattern already used in `applyPatchToIndex`, and prefer patches with full context (rather than `--unidiff-zero`) wherever feasible so `git apply` can detect and reject stale hunks instead of silently misapplying them.

### Proof of Concept
1. Modify a tracked file with several uncommitted hunks; open the diff view and select a hunk to discard, with "ask for confirmation on discard" enabled — this stores the current `ITextDiff` and `DiffSelection` in the `ConfirmDiscardSelection` popup state.
2. Before confirming, have another process (editor autosave, build script, etc.) modify the same file, shifting line numbers within/around the hunk in question without changing its length in a way `git status` would flag as a fresh diff (i.e., Desktop doesn't recompute).
3. Confirm the discard dialog. `discardChangesFromSelection` builds a patch off the stale diff/selection and applies it with `git apply --unidiff-zero`, which applies by line offset only.
4. Observe that the resulting file content is corrupted relative to what the user actually intended to discard, with no error reported. [1](#0-0) [6](#0-5) [8](#0-7)

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
```

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
```
