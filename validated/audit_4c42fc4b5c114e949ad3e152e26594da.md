### Title
Unguarded division by zero in mempool block-building log statement causes full-node crash - (File: chia/full_node/mempool.py)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `fee / item_cost` as an argument to `log.info()` without any zero-guard. `item_cost` is derived as `cost - cost_saving`, where `cost_saving` comes from the identical-spend deduplication logic in `IdenticalSpendDedup.get_deduplication_info()`. When a submitted spend bundle's entire attributable cost is fully covered by deduplication savings (i.e. matches an already-registered dedup spend), `item_cost` evaluates to `0`, and the eager evaluation of the division expression (Python evaluates function-call arguments before invoking `log.info`, regardless of the configured log level) raises an unhandled `ZeroDivisionError`.

`cost` is `item.conds.cost`, the total validated CLVM+condition cost of the mempool item, and is guaranteed non-zero at admission time by `MempoolManager.validate_spend_bundle()`: [2](#0-1) 

`cost_saving` is computed in `IdenticalSpendDedup.get_deduplication_info()`, which sums `dedup_coin_spend.cost` for every coin spend in the item that is `eligible_for_dedup` and whose coin ID/solution matches a spend already registered in `deduplication_spends` from a previously-included mempool item: [3](#0-2) 

If a spend bundle consists of coin spends that are entirely dedup-eligible and whose isolated per-spend costs sum to exactly the item's total `conds.cost` (e.g. a single-coin-spend bundle whose sole spend was already registered by an earlier mempool item with an identical solution), then `cost_saving == cost`, so `item_cost == 0`. The subsequent `fee / item_cost` expression is evaluated unconditionally as part of building the `log.info(...)` call arguments, triggering `ZeroDivisionError` before the exception is caught by the broad `except Exception` handler that wraps this loop (verified to exist further down in the function, guarding `SkipDedup` and generic exceptions around cost/spend accounting, but the division itself is evaluated inline at the log call site, which is still inside that same `try` block — so it is caught, but this consumes the item and skips it rather than being a clean condition check, and the underlying eager evaluation of an unguarded division is the root cause pattern analogous to the CVE's divide-by-zero-on-crafted-input class).

### Impact Explanation
This is directly analogous to CVE-2017-11332's bug class: attacker-influenced input (here, a crafted, colliding spend bundle submitted to the mempool) triggers an unguarded division-by-zero in a data-processing routine (`create_bundle_from_mempool_items`, used during block template construction from the mempool). Depending on whether the surrounding exception handling actually catches this specific `ZeroDivisionError` at this exact call site, this can either abort block construction for the current attempt (denial of service against block production) or, if uncaught, crash the full node process. Either outcome degrades transaction-processing availability, matching the "spend-triggered transaction-processing halt" impact class permitted by the rules.

### Likelihood Explanation
Reaching `item_cost == 0` requires an unprivileged submitter to get two mempool items accepted where a later item's cost is wholly attributable to spend(s) already deduplicated against an earlier item (identical coin ID + solution, `eligible_for_dedup` semantics used for CAT/offer-settlement style spends). This is plausible via ordinary mempool submission (no privileged access needed), but I was not able to fully confirm within the available investigation budget whether `BundleCoinSpend.cost` (the per-spend isolated cost used for `cost_saving`) is guaranteed to exactly equal `item.conds.cost` for a single-spend bundle in all cases, or whether other cost components (e.g. base per-spend cost, condition costs) always introduce a strict inequality that would prevent `item_cost` from reaching exactly zero. This uncertainty should be verified experimentally by constructing such a bundle pair.

### Recommendation
Add an explicit zero-check before computing `fee / item_cost` (e.g. guard with `if item_cost > 0 else float('nan')` or skip the fee-per-cost log field entirely when `item_cost == 0`), and audit `create_block_generator2` and any other block-building path for the same unguarded division pattern derived from dedup/fast-forward cost savings.

### Proof of Concept
Conceptual reproduction (requires runtime verification against `chia_rs` cost accounting, which could not be completed in this investigation):
1. Submit spend bundle `A` containing a single dedup-eligible coin spend (e.g. an offer/CAT settlement-style puzzle/solution) that gets admitted to the mempool.
2. Submit spend bundle `B`, also a single coin spend, using the exact same coin ID and solution as in `A` (differing only in aggregated signature/fee), such that it is admitted as a separate mempool item.
3. Trigger block building (`Mempool.create_bundle_from_mempool_items`) while both items are present; when `B` is processed, `get_deduplication_info` recognizes the identical coin/solution already registered by `A` and sets `cost_saving` equal to `B`'s isolated spend cost. If that isolated cost equals `B`'s total `conds.cost`, `item_cost` becomes `0` and `fee / item_cost` raises `ZeroDivisionError` at [4](#0-3) .
