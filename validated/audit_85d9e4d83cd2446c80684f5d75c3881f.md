### Title
Unauthenticated tx-sender JSON-RPC Server Allows Any Caller to Trigger Operator-Key Signing of Attacker-Controlled Transactions, Enabling Collateral Theft — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The standalone tx-sender JSON-RPC server (`start_jsonrpc_server`) is started with no authentication, no TLS, and no access control of any kind. Any HTTP client that can reach the bound port can call `send_tx` with an arbitrary `signed_tx_hex`, `fee_paying_type: RBF`, and a crafted `rbf_signing_info` pointing to any input. The tx-sender task loop will then sign that input with the operator's Taproot secret key and broadcast the result. Because the operator's collateral UTXO is a plain P2TR key-path output controlled by that same key (no script, no multisig), an attacker can construct a transaction that spends the collateral to an attacker-controlled address, supply `RbfSigningInfo { vout: 0, spend_path: KeyPath { tweak_merkle_root: None }, tap_sighash_type: Default }`, and the tx-sender will produce a valid witness and broadcast the theft transaction.

---

### Finding Description

**Root cause — no authentication on the JSON-RPC server**

`start_jsonrpc_server` builds the server with `ServerBuilder::default()`: [1](#0-0) 

There is no TLS layer, no API-key check, no IP allowlist, and no mTLS — in stark contrast to every gRPC endpoint, which enforces certificate-pinned mTLS via `Interceptors::OnlyAggregatorAndSelf`. [2](#0-1) 

The configuration explicitly permits binding to `0.0.0.0`: [3](#0-2) 

**The `send_tx` handler accepts fully attacker-controlled parameters** [4](#0-3) 

The handler deserialises `InsertTryToSendParams` — which includes `fee_paying_type`, `rbf_signing_info`, and the raw transaction hex — and passes them verbatim to `insert_try_to_send`. No field is validated against the operator's own UTXOs or key.

**The task loop signs with the operator's key without verifying UTXO ownership**

When the queued entry has `FeePayingType::RBF`, `send_rbf_tx` is called. On the first attempt it calls `create_funded_psbt` (Bitcoin Core `walletcreatefundedpsbt`, which accepts inputs not owned by the wallet), then `fill_in_utxo_info` to fetch the prevout from the node, then `attempt_sign_psbt`: [5](#0-4) 

`attempt_sign_psbt` computes the Taproot sighash for `input_index = rbf_signing_info.vout` over all prevouts and calls `self.signer.sign_with_tweak_data(sighash, tweak_data)`: [6](#0-5) 

The signer holds the operator's secret key and will sign any sighash presented to it: [7](#0-6) 

There is no check that the UTXO at `input_index` is actually controlled by the tx-sender's key.

**The operator's collateral UTXO is a plain P2TR key-path output — exactly what the signer can spend**

The collateral is created as a Taproot address with the operator's xonly key and no merkle root: [8](#0-7) 

`RbfSigningSpendPath::KeyPath { tweak_merkle_root: None }` maps directly to `TapTweakData::KeyPath(None)`, which is the exact tweak the signer applies when signing a key-path spend of that address. [9](#0-8) 

---

### Impact Explanation

An attacker who can reach the JSON-RPC port submits a transaction spending the operator's collateral UTXO (e.g., 90,000,000 sat / 0.9 BTC in the regtest paramset, larger in production) to an attacker-controlled address. The tx-sender produces a valid Schnorr witness and broadcasts it. The collateral is permanently lost. Without collateral, the operator cannot start a new round, breaking bridge liveness and potentially triggering slashing or loss of reimbursement rights for in-flight withdrawals.

---

### Likelihood Explanation

The JSON-RPC server is only started when `TX_SENDER_JSONRPC_PORT` is set, which is required for the standalone tx-sender binary (`crates/clementine-tx-sender/src/main.rs`). The `run.sh` smoke-test script defaults `TX_SENDER_JSONRPC_BIND` to `127.0.0.1`, but the config explicitly accepts `0.0.0.0` and Docker deployments commonly use it to allow inter-container communication. Any operator running the standalone tx-sender with `0.0.0.0` binding — or any attacker with SSRF access to the host — can trigger the exploit with a single HTTP POST.

---

### Recommendation

**Short term:** Add authentication to the JSON-RPC server before it is reachable in any deployment. The simplest approach consistent with the existing security model is to require a shared secret (bearer token or HMAC) on every request, or to restrict the server to Unix-domain sockets only (already supported by the gRPC layer).

**Medium term:** In `attempt_sign_psbt`, verify that the UTXO being signed (`input_index`) has a `script_pubkey` that matches `self.signer.address().script_pubkey()` before producing a signature. Reject any request where the input to be signed is not owned by the tx-sender's key.

**Long term:** Treat the JSON-RPC server with the same trust boundary as the gRPC servers: mTLS with certificate pinning, or move the interface entirely to a Unix socket accessible only by the co-located operator process.

### Proof of Concept

```python
import json, base64, requests

# Publicly visible on-chain data
COLLATERAL_TXID = "<operator_collateral_txid>"   # from blockchain
COLLATERAL_VOUT = 0
COLLATERAL_SAT  = 90_000_000
ATTACKER_ADDR   = "<attacker_p2tr_address>"

# Build a raw transaction spending the collateral to the attacker
# (use python-bitcoinlib or similar; sequence must enable RBF)
raw_tx_hex = build_raw_tx(
    inputs  = [{"txid": COLLATERAL_TXID, "vout": COLLATERAL_VOUT, "sequence": 0xFFFFFFFD}],
    outputs = [{ATTACKER_ADDR: (COLLATERAL_SAT - 5000) / 1e8}],   # minus fee
)

payload = {
    "jsonrpc": "2.0", "id": 1, "method": "send_tx",
    "params": [{
        "tx_metadata":    None,
        "signed_tx_hex":  raw_tx_hex,          # unsigned; tx-sender will sign
        "fee_paying_type": "RBF",
        "rbf_signing_info": {
            "vout": 0,                          # input index to sign
            "spend_path": {"KeyPath": {"tweak_merkle_root": None}},
            "tap_sighash_type": "Default",
        },
        "cancel_outpoints": [], "cancel_txids": [],
        "activate_txids": [], "activate_outpoints": [],
    }]
}

# TX_SENDER_JSONRPC_BIND=0.0.0.0, TX_SENDER_JSONRPC_PORT=3030
r = requests.post("http://<operator-host>:3030", json=payload)
print(r.json())
# → {"result": <try_to_send_id>, ...}
# tx-sender task loop will sign with operator key and broadcast
```

The tx-sender task loop picks up the entry, calls `send_rbf_tx` → `create_funded_psbt` → `fill_in_utxo_info` → `attempt_sign_psbt` (signs input 0 with the operator's key, `tweak_merkle_root=None`) → `send_raw_transaction`. The collateral UTXO is spent to the attacker's address.

    pub(crate) fn sign_with_tweak_data(
        &self,
        sighash: TapSighash,
        tweak_data: TapTweakData,
    ) -> Result<schnorr::Signature, BridgeError> {
        let keypair;
        let keypair_ref = match tweak_data {
            TapTweakData::KeyPath(merkle_root) => {
                keypair = calc_tweaked_keypair(&self.keypair, merkle_root)?;
                &keypair
            }
            TapTweakData::ScriptPath => &self.keypair,
            TapTweakData::Unknown => return Err(eyre::eyre!("Spend Data Unknown").into()),
        };

        Ok(SECP
            .sign_schnorr_no_aux_rand(&Message::from_digest(sighash.to_byte_array()), keypair_ref))
    }
