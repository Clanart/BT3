### Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, allowing cross-shop request forgery — (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates a webhook's authenticity solely by checking an HMAC over the raw request body, using a secret shared across every shop that has installed the app. It separately exposes a `shop_domain` helper that reads the caller-supplied `X-Shopify-Shop-Domain` header directly, with no cryptographic tie to the HMAC-signed body. Any actor who can produce (or capture) one validly-signed webhook body — trivially true for any merchant that has installed the app, since the app secret is shared across all shops — can replay that exact body while substituting an arbitrary shop domain in the header. The signature still validates, and the app-level code that trusts `shop_domain` for record lookup/dispatch (as shown in this gem's own generator templates) will operate on a different merchant's data.

### Finding Description
`verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` only checks: [1](#0-0) 
i.e. `hmac_valid?(request.raw_post)` — a comparison that covers only the raw POST body, computed with `ShopifyApp.configuration.secret`/`old_secret`: [2](#0-1) 

The same module then exposes: [3](#0-2) 
`shop_domain` is read straight from the `X-Shopify-Shop-Domain` request header, which is **not** included in the HMAC computation. Nothing in this module binds the header value to the signed body, so the header can be freely set to any value by the requester without invalidating the signature.

The gem's own documentation instructs developers to build custom webhook controllers exactly this way, trusting `shop_domain` for dispatch: [4](#0-3) 

And the generator-produced job templates use this shop-domain value to look up a `Shop` record and perform a sensitive, shop-scoped action such as destroying the shop record on `shop/redact` / `app/uninstalled`: [5](#0-4) 

Because the app's HMAC secret (`ShopifyApp.configuration.secret`) is identical for every shop using the app (it is the app's client secret, not a per-shop secret), any installed merchant — an "unrelated merchant" from the perspective of any other tenant — can obtain a validly-signed webhook body from their own shop, then resend that exact body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to point at a different merchant's `shopify_domain`. `hmac_valid?` still returns true because it never inspects the header, and the downstream logic (per the gem's documented pattern and templates) will act on the victim shop's `Shop` record (e.g., `shop.destroy`, or any custom webhook processing keyed on `shop_domain`) — a cross-shop confused-deputy analog to the VaderPoolV2 issue, where a caller-supplied identifier (there: the liquidity-provider address; here: the shop domain) is trusted for a sensitive action instead of being derived from a value cryptographically bound to the authenticated request.

### Impact Explanation
An attacker (any merchant with the app installed, or anyone who otherwise obtains one valid signed webhook body/HMAC pair for the shared app secret) can forge webhook deliveries "on behalf of" an arbitrary other shop domain. Depending on which webhook topic/job is targeted, this enables cross-shop data corruption or destruction (e.g. triggering `shop.destroy` for `app/uninstalled` or GDPR redact jobs against a victim shop, or feeding forged data into any custom webhook job that trusts `shop_domain`). This is a tenant-isolation break reachable from an unrelated, unprivileged merchant account — no host-operator or secret-leak assumption required beyond the ordinary ability to install the app once and capture one legitimate webhook.

### Likelihood Explanation
High for any app that follows the gem's documented custom-webhook pattern (or generator templates) that key business logic off `WebhookVerification#shop_domain`/`shop_domain:` job argument. The prerequisite — obtaining one valid signed body — is trivially met by simply installing the app on one's own store and capturing any webhook Shopify sends. The only work for the attacker is replaying the POST with a modified header, which requires no cryptographic material beyond what a normal merchant already has.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header value in isolation. Either:
- Derive the shop from data verified as part of the signed payload (e.g., parse `shop`/`myshopify_domain` from the JSON body, which is covered by the HMAC), and cross-check it against the header, rejecting mismatches; or
- Use `ShopifyAPI::Webhooks::Registry.process`/`ShopifyAPI::Webhooks::Request` (the library-provided flow that the shopify_api gem uses to resolve `shop:` in `handle`) consistently instead of `WebhookVerification#shop_domain`, and audit/update generator templates and docs so they don't recommend keying shop-scoped actions off the unauthenticated header directly.
- Alternatively, sign the shop domain into the HMAC input (i.e., include it as part of `data` in `hmac_valid?`) so any modification invalidates the signature.

### Proof of Concept
1. Install the app on shop A (`shop-a.myshopify.com`) and capture a legitimate incoming webhook request, e.g. `app/uninstalled`, including its raw body and the resulting `X-Shopify-Hmac-Sha256` header (both are visible/loggable by the shop owner or via a test webhook trigger).
2. Replay the exact same POST (same raw body, same `X-Shopify-Hmac-Sha256` header) to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com` (an unrelated merchant's domain).
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks the body against the shared app secret — it succeeds because the body/HMAC pair is unchanged.
4. The custom controller/job (per `docs/shopify_app/webhooks.md` pattern or `AppUninstalledJob` template) uses `shop_domain` from the header to `Shop.find_by(shopify_domain: shop_domain)` and executes the shop-scoped action (`shop.destroy`, etc.) against shop B, despite the request never having been legitimately signed for shop B.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
class CustomWebhooksController < ApplicationController
```

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
