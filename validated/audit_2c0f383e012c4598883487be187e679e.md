### Title
Deliver-tx ante pipeline trusts an unverified `Derived` sender-identity field instead of recomputing it from the transaction's actual ECDSA signature - ([File: app/ante/evm_delivertx.go])

### Summary
`EvmDeliverHandleSignatures` in `app/ante/evm_delivertx.go` accepts a pre-populated `msg.Derived` (containing `SenderEVMAddr`, `SenderSeiAddr`, and `PubKey`) as the authoritative sender identity for an EVM transaction whenever that field is non-nil, and only bails out if `PubKey` is `nil`. It never re-derives the sender by recovering the ECDSA signature over the embedded Ethereum transaction (`txData`), nor does it verify that `PubKey` actually corresponds to `SenderEVMAddr`/`SenderSeiAddr`, nor that `PubKey` actually produced the signature carried in `txData`. This is structurally the same bug class as CVE-2017-11103: an unauthenticated/unverified identity claim (`Derived`, analogous to Heimdal's unencrypted `ticket` service name) is trusted in place of the value that must be recomputed from the cryptographically protected material (the actual tx signature, analogous to Heimdal's encrypted `enc_part`).

### Finding Description
`EvmDeliverHandleSignatures` [1](#0-0)  :
```go
func EvmDeliverHandleSignatures(...) (...) {
	if msg.Derived != nil {
		if msg.Derived.PubKey == nil {
			return common.Address{}, nil, 0, sdkerrors.ErrInvalidPubKey
		}
		evmAddr := msg.Derived.SenderEVMAddr
		seiAddr := msg.Derived.SenderSeiAddr
		version := msg.Derived.Version
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, msg.Derived.PubKey); err != nil {
			return evmAddr, seiAddr, version, err
		}
		...
		return evmAddr, seiAddr, version, nil
	}
	// only computed here if Derived was nil
	evmAddr, seiAddr, seiPubkey, version, err := CheckAndDecodeSignature(ctx, txData, chainID, ...)
	...
}
```
The comment in the sibling `PreprocessUnpacked` function explicitly documents the threat but only implements a partial guard: [2](#0-1) 
```go
if msgEVMTransaction.Derived != nil {
	if msgEVMTransaction.Derived.PubKey == nil {
		// this means the message has `Derived` set from the outside, in which case we should reject
		return sdkerrors.ErrInvalidPubKey
	}
	// already preprocessed
	return nil
}
```
This code acknowledges that `Derived` can be set "from the outside" (i.e., attacker-controlled, since `derived` is a regular field of the `MsgEVMTransaction` proto message: [3](#0-2) ), but the only rejection condition is `PubKey == nil`. If an attacker supplies **any** valid-looking `PubKey` object together with a `SenderEVMAddr`/`SenderSeiAddr` of their choosing, the check passes.

The consuming helper, `AssociateAddress` → `AssociationHelper.AssociateAddresses`, compounds the problem: it never checks that `pubkey.Address()` matches `seiAddr` or that `PubkeyToEVMAddress(pubkey)` matches `evmAddr` before wiring up the address mapping and treating `evmAddr`/`seiAddr` as the verified transaction sender: [4](#0-3) . It simply calls `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)` and sets the pubkey on the account if absent — no cross-check that the three values are mutually consistent, and no check that this pubkey signed the embedded `txData` at all.

By contrast, when `Derived` is nil the code path correctly recomputes the sender by recovering the signature from `txData` via `CheckAndDecodeSignature`, which performs true ECDSA-based verification: [5](#0-4) . The `Derived`-present branch skips this recomputation entirely and just trusts the supplied claim, exactly mirroring `_krb5_extract_ticket()` trusting the unencrypted principal name instead of recomputing it from the encrypted (verified) part of the ticket.

### Impact Explanation
If reachable with attacker-controlled `Derived` content on the code path that actually executes in `DeliverTx` (i.e., a transaction whose protobuf-encoded bytes include a pre-populated `derived` field that is not overwritten/re-validated before execution), an attacker could:
- Set `SenderEVMAddr`/`SenderSeiAddr` to any already-associated victim address while supplying a `PubKey` of their own choosing (not the victim's), causing the EVM transaction (nonce, fee debit, `msg.sender` in EVM execution, ante context `ctx.WithEVMSenderAddress`/`ctx.WithSeiSenderAddress`) to be attributed to and executed as the victim.
- This enables unauthorized transfers of funds, unauthorized contract calls performed "as" another account, and fee/nonce state corruption for that victim — a direct impersonation/fund-loss primitive from a single submitted transaction.

### Likelihood Explanation
This is intentionally reachable design surface: `Derived` is a first-class field of `MsgEVMTransaction`, and the code comment itself states that the message "has `Derived` set from the outside" is a scenario the authors anticipated needing to reject — but the implemented guard (`PubKey == nil` check) does not actually validate the semantic correctness of the claim (that the pubkey/addresses are mutually consistent and that the pubkey produced the signature over `txData`). Whether this is actually exploitable end-to-end depends on implementation details I could not fully verify from the index — specifically, whether the ABCI/mempool layer ever re-decodes a `MsgEVMTransaction` for `DeliverTx` directly from externally-submitted, attacker-controlled byte blobs containing a populated `derived` field (as opposed to only ever propagating an in-process, CheckTx-computed struct that can't be forged this way). Given the code's own acknowledgment of the outside-set-`Derived` scenario and the fact that the guard is incomplete regardless of how it is reached, this is flagged as Medium-High likelihood pending confirmation of the exact mempool→DeliverTx data flow for the `derived` field.

### Recommendation
- In `EvmDeliverHandleSignatures` (and `PreprocessUnpacked`), never trust a pre-populated `Derived` for identity purposes unless it can be proven to originate from this node's own prior verified `CheckTx`/preprocessing step (e.g., via an unforgeable in-process channel, not a value that round-trips through externally-supplied tx bytes).
- At minimum, when `Derived != nil`, always independently re-verify that `PubkeyToEVMAddress(Derived.PubKey) == Derived.SenderEVMAddr`, `sdk.AccAddress(Derived.PubKey.Address()) == Derived.SenderSeiAddr`, and that `Derived.PubKey` actually produced the ECDSA signature over the embedded `txData`/`etx` before using these values as the transaction's sender.
- Add explicit unit/integration tests that submit a `MsgEVMTransaction` with an attacker-forged `Derived` (mismatched pubkey vs. addresses, or pubkey not matching the embedded tx's signature) and assert rejection.

### Proof of Concept
1. Craft a Cosmos SDK `Tx` containing a single `MsgEVMTransaction` where:
   - `Data` is any syntactically valid signed Ethereum transaction (signed by the attacker, so `EvmStatelessChecks` passes basic decode/validation).
   - `Derived` is populated with `PubKey` = attacker's own pubkey, but `SenderEVMAddr`/`SenderSeiAddr` = a victim address that is already associated on-chain.
2. Submit this transaction so that it is included in a block and processed via `EvmDeliverTxAnte` → `EvmDeliverHandleSignatures`.
3. Because `msg.Derived != nil` and `PubKey != nil`, the code skips `CheckAndDecodeSignature` and uses the attacker-chosen `evmAddr`/`seiAddr` directly, calling `AssociateAddress`/`AssociateAddresses` without validating pubkey-address consistency, and proceeds to charge fees/execute the EVM transaction with the victim's addresses set as `ctx.EVMSenderAddress()`/`ctx.SeiSenderAddress()`.
4. Full confirmation of exploitability requires validating (outside the indexed code available to me) that the specific ABCI/mempool wiring allows an externally-submitted, attacker-crafted `derived` field to survive into the `DeliverTx` decode of `msg` unmodified — this could not be fully traced with the available tooling and should be verified in a live/test environment.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func CheckAndDecodeSignature(ctx sdk.Context, txData ethtx.TxData, chainID *big.Int, isBlockTest bool) (common.Address, sdk.AccAddress, cryptotypes.PubKey, derived.SignerVersion, error) {
	ethTx := ethtypes.NewTx(txData.AsEthereumData())
	if ethTx.Type() != ethtypes.LegacyTxType {
		chainID = ethTx.ChainId()
	}
	chainCfg := evmtypes.DefaultChainConfig()
	ethCfg := chainCfg.EthereumConfig(chainID)
	version := evmante.GetVersion(ctx, ethCfg)
	signer := evmante.SignerMap[version](chainID)
	if !evmante.IsTxTypeAllowed(version, ethTx.Type()) {
		return common.Address{}, sdk.AccAddress{}, nil, 0, ethtypes.ErrInvalidChainId
	}

	var txHash common.Hash
	V, R, S := ethTx.RawSignatureValues()
	if ethTx.Protected() {
		V = helpers.AdjustV(V, ethTx.Type(), ethCfg.ChainID)
		txHash = signer.Hash(ethTx)
	} else {
		if isBlockTest {
			// need to allow unprotected legacy txs in blocktest
			// to not lose coverage for other parts of the code
			txHash = ethtypes.FrontierSigner{}.Hash(ethTx)
		} else {
			return common.Address{}, sdk.AccAddress{}, nil, 0, errors.New("unsupported tx type: unsafe legacy tx")
		}
	}
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, txHash)
	if err != nil {
		return common.Address{}, sdk.AccAddress{}, nil, 0, sdkerrors.ErrInvalidChainID
	}
	return evmAddr, seiAddr, seiPubkey, version, nil
}
