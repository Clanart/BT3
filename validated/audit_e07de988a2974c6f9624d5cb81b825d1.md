**Analysis:** In `publish_package` in `code.move`, the `upgrade_number` field is unconditionally recomputed and overwritten regardless of any attacker-supplied value in the deserialized `PackageMetadata` blob passed via `publish_package_txn`.

The function first deserializes the untrusted blob (`util::from_bytes<PackageMetadata>(metadata_serialized)`) at [1](#0-0) , then computes the correct value by scanning the existing registry: [2](#0-1) 

- `upgrade_number` is initialized to `0` before the scan (covers the "first publish" case where `index == len` and the loop body never matches, leaving it at `0`).
- If an existing package with the same name is found, it's set to `old.upgrade_number + 1` (derived from the *stored* on-chain value, not the attacker's new blob).
- Line 204, `pack.upgrade_number = upgrade_number;`, unconditionally overwrites whatever value the attacker put in the serialized blob **before** the package is written into `PackageRegistry.packages` (either via `*packages.borrow_mut(index) = pack` or `packages.push_back(pack)`).

There is no branch in this function where the attacker-controlled field survives to storage — the overwrite happens for both the fresh-publish (`index == len`) and upgrade (`index < len`) cases, prior to any registry mutation. This is also explicitly covered by the Move formal spec requirement: "The upgrade number of a package increases incrementally in a monotonic manner with each subsequent upgrade... On each upgrade... the publish_package function updates the upgrade_number" [3](#0-2) .

Since the CLI/`extract_metadata` tooling that builds the initial blob also always sets `upgrade_number: 0` client-side [4](#0-3) , and the on-chain module ignores whatever is submitted anyway, there is no path by which an unprivileged caller can corrupt the stored `upgrade_number` invariant. The proof-of-concept described (submitting `upgrade_number = 9999`) would simply be discarded by line 204 regardless of `index == len` or not.
