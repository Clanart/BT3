### Title
Unvalidated `shell.openExternal` scheme allows RCE via attacker-controlled Check-Run/Status URL - (File: `app/src/main-process/main.ts`)

### Summary
GitHub Desktop's IPC handler for `open-external` forwards any string to Electron's `shell.openExternal` without validating the URI scheme. Several UI surfaces feed values that originate from the GitHub API (specifically the check-run/commit-status `html_url`/`target_url` fields) directly into this call chain. Because these fields are attacker-influenceable (any CI integration, GitHub App, or Statuses-API client with write access to a repo/PR can set `target_url`/`details_url` to an arbitrary string, including `file://` or UNC/`smb://` paths), a malicious contributor or compromised CI integration can cause a Desktop user who clicks "View check details" to execute an arbitrary local binary or a remote SMB payload—the exact bug class described in the external report for `shell.openExternal`.

### Finding Description
The main-process handler that services the renderer's `openExternal` proxy call performs no scheme allow-listing; it only *logs* when the value looks like `http(s)://`, then unconditionally calls `shell.openExternal(path)`: [1](#0-0) 

This handler is reached from the renderer via `main-process-proxy.ts`: [2](#0-1) 

and from `IAppShell.openExternal`, `AppStore._openInBrowser`, and `Dispatcher.openInBrowser`: [3](#0-2) [4](#0-3) 

While the markdown link interceptor (`SandboxedMarkdown.setupLinkInterceptor`) does whitelist `https?:` before invoking `onMarkdownLinkClicked` [5](#0-4) , this guard is a renderer-side, per-component convention rather than an enforcement point in the trusted main process. Other call sites do not apply any such filter before reaching `openInBrowser`/`shell.openExternal`. Notably, `CICheckRunPopover.onViewCheckDetails` passes `checkRun.htmlUrl` straight through: [6](#0-5) 

and `onViewJobStep` similarly forwards a URL derived from check-run/job-step API data: [7](#0-6) 

`checkRun.htmlUrl` is populated from the GitHub Checks/Statuses API `html_url`/`target_url` fields (see the multiple matches in `app/src/lib/ci-checks/ci-checks.ts` and `app/src/lib/api.ts`), both of which GitHub's API accepts as free-form strings with no server-side scheme restriction. Any actor able to post a commit status or check run against a PR/commit — e.g., a contributor's own CI integration, a malicious GitHub App installed by a repo collaborator, or any client holding a `repo:status` token for the repository — can set this field to `file:///path/to/binary`, a UNC path rendered as `file://`, or an `smb://` URI.

### Impact Explanation
Since the true "broken invariant" is the same one the external report described (no scheme validation before `shell.openExternal`), the impact is identical in class: local code execution on the victim's machine when they click "View check details" (or a job-step link) for a check run/status set by an attacker. This can execute an arbitrary local binary (`file://`) or, on Windows, cause the OS to fetch and execute a binary from an attacker-controlled SMB share, per the well-known dangers of Electron's `shell.openExternal`.

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires the attacker to get a check-run/status entry attached to a repository or PR the victim opens in Desktop (e.g., via a PR from a fork whose CI reports a status, or a malicious/compromised third-party CI integration), and then requires one user click on the check-details affordance. No local access, admin rights, or pre-existing malware is needed — the primitive is entirely driven by data the attacker can inject through the normal GitHub Checks/Statuses API, and no additional social-engineering steps beyond a single expected UI interaction (viewing/clicking check details, a routine PR-review action) are required.

### Recommendation
- In `app/src/main-process/main.ts`'s `open-external` handler, enforce an allow-list of schemes (e.g., only `https:` and, if required, `mailto:`) and reject/reject-with-error anything else before calling `shell.openExternal`, rather than merely logging.
- Apply the same validation used in `sandboxed-markdown.tsx` (`/^https?:/` check) centrally, at the IPC boundary, so every caller (including `CICheckRunPopover`, `pull-request-quick-view.tsx`, `branch-dropdown.tsx`, etc.) is protected regardless of whether the individual component remembers to validate.
- Treat all GitHub API fields such as `html_url`/`target_url` on check runs/statuses as untrusted third-party input and validate/sanitize them before use in `openInBrowser`/`openExternal`.

### Proof of Concept
1. Attacker forks the target repository, opens a PR, and (via their own CI integration or a script using a `repo:status`-scoped token) posts a commit status/check run on the PR's head commit with `target_url` (or `details_url`) set to `file:///System/Applications/Calculator.app` (macOS) or a UNC/`smb://` path pointing to an attacker-controlled payload share (Windows).
2. Victim opens the PR/commit in GitHub Desktop and opens the CI Check Runs popover (`CICheckRunPopover`).
3. Victim clicks the check entry, invoking `onViewCheckDetails`, which calls `dispatcher.openInBrowser(checkRun.htmlUrl)` [8](#0-7) .
4. This flows to `AppStore._openInBrowser` → `shell.openExternal` (renderer proxy) → `ipcMain.handle('open-external', ...)` in the main process, which performs no scheme check and calls Electron's `shell.openExternal(path)` [9](#0-8) , causing the OS to launch the attacker-specified binary/share.

Note: I was unable to fully inspect `app/src/lib/api.ts` and `app/src/lib/ci-checks/ci-checks.ts` field-by-field (only confirmed via grep matches for `target_url`/`html_url`/`htmlUrl`) due to the final-iteration cutoff, so the exact typing/normalization of `checkRun.htmlUrl` (e.g., whether any partial validation happens in `ci-checks.ts`) should be double-checked in a follow-up session before treating this as fully confirmed end-to-end.
