### Title
`ThresholdKeys::read` accepts keys whose secret share does not match its verification share, enabling inconsistent/misrepresented threshold keys - ([File: crypto/dkg/src/lib.rs])

### Summary
Analogous to the StakingRewards bug — where a vault credited staked balances without ever confirming the staking token contract existed — `ThresholdKeys::read` (and `ThresholdKeys::new`) reconstructs a threshold key from untrusted bytes without ever confirming the secret share actually belongs to the verification-share set it claims membership in. The serialized `secret_share` is accepted at face value; it is never checked against `verification_shares[i]` via `C::generator() * secret_share == verification_shares[i]`, nor are the `t + 1 ..= n` verification shares checked for consistency with the shares `1 ..= t` that determine the group key.

### Finding Description
`ThresholdKeys::read` deserializes `(t, n, i)`, an interpolation method, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` only checks the count of shares and that participant indices are `<= n` (lines 355-365), then computes `group_key` solely as the interpolation of `verification_shares[1 ..= t]` (lines 376-378). Two gaps result:

1. `secret_share * G == verification_shares[i]` is never verified. Any scalar is accepted as "the share of participant `i`".
2. Shares `t+1 ..= n` never enter the group key computation, so an attacker can submit a fully fabricated set: choose arbitrary points for `verification_shares`, yielding a group key `Y` under the attacker's sole control (e.g., a key for which they know the discrete log), while embedding any `secret_share` and claiming index `i`.

Like the reported bug, an entity is registered and credited (a share position / group key) without confirming the underlying object (a real share of that key) exists.

### Impact Explanation
If `ThresholdKeys` bytes can be influenced by an unprivileged party (restored backups, migration payloads, or any path feeding attacker bytes to `ThresholdKeys::read` — an explicitly in-scope sink), the node ends up holding "keys" for a group key entirely chosen by the attacker. Deposits scanned against that group key (e.g., via `Scanner::new(key)` in networks/bitcoin/src/wallet/mod.rs:162) appear controlled by the threshold while actually being solely spendable by the attacker — funds reported received that the honest participant cannot co-spend. Alternatively, mismatched `secret_share`/verification-share pairs yield views whose signatures are silently rejected, or worse, where the node's `view()` produces partial signatures consistent with attacker-set verification shares.

### Likelihood Explanation
Requires attacker-controlled bytes reaching `ThresholdKeys::read`, which is plausible only in deployments persisting/restoring keys from untrusted channels. The cryptographic primitives are all correct; this is a missing consistency invariant in deserialization. Medium likelihood, Medium/High impact given the fund-custody role of these keys.

### Recommendation
In `ThresholdKeys::new` (so `read` inherits it), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Additionally document/verify that `verification_shares[t+1..=n]` are on the same polynomial (e.g., verify via the commitments used at generation time or by re-interpolating consistency), or at minimum reject reconstructed keys whose shares fail the self-consistency check.

### Proof of Concept
```rust
// Attacker-chosen key they fully control
let x = Secp256k1::random_nonzero_F(&mut OsRng);
let attacker_key = <Secp256k1 as Ciphersuite>::generator() * x;

// Craft verification_shares[1..=t] that interpolate to attacker_key:
// e.g. t == n style Constant interpolation, shares[1] = attacker_key, shares[rest] = IDENTITY
let mut shares = HashMap::new();
shares.insert(Participant::new(1).unwrap(), attacker_key);
for l in 2 ..= t { shares.insert(Participant::new(l).unwrap(), <_>::identity()); }
// pad t+1..=n with anything
for l in (t+1) ..= n { shares.insert(Participant::new(l).unwrap(), <_>::identity()); }

let forged = ThresholdKeys::new(
  ThresholdParams::new(t, n, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Constant(vec![attacker_key * inv_of_interp_factors... ]), // or Lagrange
  Zeroizing::new(<Secp256k1 as Ciphersuite>::F::ZERO), // arbitrary secret_share accepted
  shares,
).unwrap(); // succeeds; forged.group_key() == attacker_key, controlled solely by attacker
```
No assertion ever checks `G * secret_share == verification_shares[i]` (crypto/dkg/src/lib.rs:349-391, 574-632), so the forged keys are accepted and `group_key()` reports the attacker's key as the multisig's key.
