## Title
Silent commit corruption via stale diff line-selection re-use in `applyPatchToIndex` - ([File: app/src/lib/git/apply.ts])

### Summary
The report's core invariant is: a positional/quantity total (`lobReservesByTokenId`) is computed against one state of the world, then a *different* state of the world is used at settlement time without reconciling the two, causing the tracked value to diverge from reality. The Desktop analog is the `DiffSelection` used for partial-file/partial-line commits: the selection (`divergingLines`, i.e., which line *indices* the user chose to include) is computed against the diff that was rendered in the Changes view, but `applyPatchToIndex` independently re-fetches a *fresh* diff from disk at staging time and blindly re-applies the old index-based selection to it, with no check that the two diffs are the same shape.

### Finding Description
`DiffSelection` tracks "diverging lines" purely as **absolute line indices** (`hunk.unifiedDiffStart + lineIndex`), not by line content or hash: [1](#0-0) 

When the user commits, `stageFiles` routes any file with a `Partial` selection through `applyPatchToIndex`: [2](#0-1) 

Critically, `applyPatchToIndex` does **not** use the diff object the UI displayed to the user when the selection was made — it fetches a brand-new diff from the working directory right before formatting the patch: [3](#0-2) 

`formatPatch` then walks this freshly-fetched diff and, for every non-context line, decides inclusion purely by `file.selection.isSelected(absoluteIndex)` — i.e., by looking up the *old* index-based selection against the *new* diff's line positions: [4](#0-3) 

There is a separate mechanism, `updateChangesWorkingDirectoryDiff`, that reconciles `selectableLines` when the Changes panel refreshes its own diff view due to a status change: [5](#0-4) 

but this only runs opportunistically on a UI status refresh of the *currently selected* file, and its comment explicitly acknowledges the limitation: *"Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines."* This reconciliation is not guaranteed to run — or to run against the exact diff — right before `applyPatchToIndex` fetches its own independent copy of the diff during the commit flow (`stageFiles` → `applyPatchToIndex` → `getWorkingDirectoryDiff`). If the working-directory file content changes between the last UI diff refresh and the commit's own `getWorkingDirectoryDiff` call (e.g., because a git hook, a build/watch script bundled in the repository, a filter/smudge driver, or another background process touches the file), the hunk boundaries and line indices shift, but the stale `divergingLines` set is still applied by absolute index. This can cause `formatPatch` to include lines the user never selected (attacker/tool-inserted content silently makes it into the commit) or exclude lines the user did select — without any error, since `formatPatch` only throws when the patch is completely empty, not when it diverges from user intent.

### Impact Explanation
This breaks the same invariant class as the reported bug: a value (here, "what the user actually approved for commit") is computed once against one snapshot and reused unchecked against a different, later snapshot. The result is silent corruption of what gets committed and potentially pushed to a remote — e.g., a partially-reviewed hunk could end up containing attacker-influenced lines that the user never saw or approved, and Desktop would present the commit as reflecting the user's explicit line-level choices. Since GitHub Desktop explicitly advertises line-level partial staging as a security/review feature, silently committing unreviewed content is a meaningful integrity failure.

### Likelihood Explanation
This requires a legitimate but constrained condition: something must modify the working-directory file's line layout between the diff render used for selection and the moment `stageFiles`/`applyPatchToIndex` independently reloads the diff during commit. This is plausible via repository-controlled tooling (pre-commit/post-checkout hooks, file watchers, format-on-save integrations, or attacker-controlled build scripts checked into a cloned repo) rather than requiring local/physical access or malware — it fits the "attacker controls a cloned/fetched repository" threat model listed as valid. However, the attack requires a specific timing window (asynchronous gap between UI diff display and the commit's independent diff re-fetch) and reproducing it reliably from local code inspection alone (without running the app) is not fully verified; I could not confirm from static analysis exactly how large this window is in practice or whether other guards elsewhere in the commit dispatch path (not found in the searched code) close it.

### Recommendation
`applyPatchToIndex` should not silently re-fetch an independent diff and blindly apply the previously computed `DiffSelection`. Instead, the diff used to build the selection and the diff used to build the patch must be the same object (or the code must re-validate selectable/diverging line sets against the newly fetched diff, failing loudly — not silently applying stale indices — if hunks/lines have shifted since the selection was made), extending the partial validation logic already present in `updateChangesWorkingDirectoryDiff` to the commit path itself.

### Proof of Concept
Not independently executed; based on static code review only. Conceptually:
1. Open a repo in Desktop, modify a large file, and select only specific lines (e.g., lines 10–12) for a partial commit via the diff view, leaving the commit dialog open before clicking "Commit".
2. Trigger a change to the same file outside Desktop's diff-refresh cycle (e.g., a repository-configured file watcher/build hook rewrites the file, shifting line numbers) in the brief window between selection and commit submission.
3. Click "Commit changes." `stageFiles` → `applyPatchToIndex` fetches a new diff via `getWorkingDirectoryDiff` (app/src/lib/git/apply.ts:60) and applies the stale `DiffSelection` indices against it via `formatPatch` (app/src/lib/patch-formatter.ts:157), potentially including/excluding different lines than what the user visually approved, with no error surfaced to the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
