### Title
Governance `EvmHost.withdraw()` Can Drain Relayer-Owed Delivery Fees Before They Are Claimed - ([File: evm/src/core/EvmHost.sol])

### Summary
The external report's core invariant is: an owner-privileged action that moves/drains funds to a different destination executes without first "checkpointing" (crediting) value already earned but not yet claimed by a third party, causing that value to become permanently unrecoverable. The Hyperbridge analog is `EvmHost.withdraw()` [1](#0-0) , which sweeps an arbitrary amount of the host's `feeToken` balance to a beneficiary chosen by cross-chain governance, with no accounting for relayer fees that are already committed in `_requestCommitments` but not yet paid out to the relayer who will eventually deliver proof of that request.

### Finding Description
`EvmHost` stores, for every outgoing request, a `FeeMetadata` entry recording the fee "put up for relayers" in `_requestCommitments` [2](#0-1) . That fee sits physically inside the host's `feeToken` balance until a relayer proves delivery and is credited/paid (the credit/claim step is the "checkpoint" — analogous to the Convex `_checkpoint`).

Separately, `IHostManager.withdraw()` lets cross-chain governance sweep "bridge revenue" from the host:
```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    if (params.token == address(0)) {
        (bool sent,) = params.beneficiary.call{value: params.amount}("");
        if (!sent) revert WithdrawalFailed();
    } else {
        IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    }
    emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
}
``` [1](#0-0) 

This function performs a raw balance transfer for any `amount`, up to the full `feeToken` balance of the contract. It never computes or reserves the sum of `_requestCommitments[...].fee` for requests that have been dispatched (fee already collected into the host balance) but not yet delivered/claimed by a relayer. The docstring even says "withdraws host revenue," but the code has no concept of "revenue" separate from "committed relayer fees" — both live in the same ERC-20 balance.

The `HostManager.onAccept` entrypoint that reaches this function is driven purely by a Hyperbridge-originated `Withdraw` governance message [3](#0-2) , with `WithdrawParams.amount` fully attacker/governance-controlled and no on-chain floor check against outstanding relayer commitments.

This is structurally identical to the ConvexStakingWrapper shelter bug: a privileged, legitimate maintenance/administrative operation (fund sweep / shelter enactment) executes without checkpointing value owed to a different class of participants (relayers vs. LP depositors), so that value is silently lost once the balance is moved.

### Impact Explanation
Relayers who have already delivered messages and accrued fee entitlement in `_requestCommitments` can have the underlying token balance withdrawn out from under them via a legitimate `dispatch_withdraw`/`HostManager.withdraw` operation sized larger than actual "swept protocol revenue." Their fee becomes unclaimable — the ERC-20 balance is gone, and the relayer-fee accounting pathway (relayer proof + payout) has no failure mode other than a reverted transfer at claim time. This is a direct loss of funds for relayer participants, matching the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" impact categories, and mirrors the judged medium-severity "Owner Privilege + Yield Loss" characterization of the original report.

### Likelihood Explanation
`withdraw()` is reachable any time governance (or the host-executive/relayer withdrawal pathways that also transit `HostManager`) issues a sweep sized without knowledge of outstanding commitments — there is no on-chain invariant preventing it, so the bug is triggerable by ordinary, intended governance operations rather than requiring any malicious actor, forged proof, or compromised key. The only reason it hasn't caused visible loss is operational discipline off-chain (governance manually estimating "revenue" vs reserved fees), not a contract-level guard.

### Recommendation
Track a running total of outstanding (dispatched-but-unclaimed) relayer fees on `EvmHost` — e.g., increment on dispatch when `FeeMetadata.fee > 0`, decrement when the relayer module credits/claims it — and enforce `amount <= feeTokenBalance - outstandingRelayerFees` inside `withdraw()`. Alternatively, segregate relayer-fee escrow from protocol revenue in separate balances/contracts so a revenue sweep can never touch funds already committed to a specific relayer.

### Proof of Concept
1. Relayer delivers `PostRequest` A with `FeeMetadata.fee = 100 feeToken`; `_requestCommitments[hash(A)].fee = 100` is recorded and the 100 feeToken sits in `EvmHost`'s balance, but the relayer has not yet claimed it.
2. Before the relayer submits their delivery-proof claim, Hyperbridge governance dispatches a `Withdraw` message via the relayer/host-executive pathway with `amount = full feeToken balance` (a routine revenue sweep) to `HostManager.onAccept` → `EvmHost.withdraw()` [3](#0-2) .
3. `withdraw()` transfers the entire balance, including the 100 feeToken reserved for the relayer's delivery of A, to the governance-specified beneficiary — no check against `_requestCommitments`.
4. The relayer later submits a valid delivery proof and attempts to claim; the payout transfer now fails or under-pays because the underlying `feeToken` balance backing that fee no longer exists in the host contract.

**Uncertainty note:** I was unable to fully read `modules/pallets/relayer/src/withdrawal.rs` in full (tool errors truncated the file), so I cannot confirm whether pallet-relayer applies any independent reservation accounting on the Substrate side that would mitigate this specific EVM-side gap; the finding is scoped to the EVM `EvmHost.withdraw()` / `HostManager` path, which was fully verified from the retrieved source.
