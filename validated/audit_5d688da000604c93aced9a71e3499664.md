## Title
Pointer reverse-registry key truncates bech32 addresses instead of hashing them, collapsing the address space and allowing pointer-type/pointer-identity confusion - (File: `x/evm/keeper/pointer.go`, `x/evm/types/keys.go`)

### Summary
Sei's EVM↔CosmWasm pointer registry is the analog of Connext's canonical-asset registry: it maps a "pointee" (native denom, CW20/CW721/CW1155 address, or ERC20/721/1155 address) to a pointer contract, and also maintains a reverse mapping so the module can detect "pointer of a pointer" and answer `GetXPointee` queries. Just like the Connext bug, the reverse map is keyed on a *truncated identifier* rather than a proper hash/domain-separated key, so distinct assets/pointer-types can collide on the same store key.

### Finding Description
Forward pointer keys are namespaced correctly, with a distinct type prefix per direction: [1](#0-0) 

But the reverse-registry key, which is shared by **all** pointer types (native→ERC20, CW20→ERC20, CW721→ERC721, CW1155→ERC1155, and the reverse CW→ERC directions), has no type discriminator at all — it is just the raw 20-byte `common.Address`: [2](#0-1) 

For the CW-pointer→ERC directions, the "id" fed into this key is not an EVM address at all — it's a bech32 Sei address **string** for the newly created CW20/CW721/CW1155 pointer contract, forced into a `common.Address` via `common.BytesToAddress([]byte(addr))`, which (per go-ethereum's `Address.SetBytes`) keeps only the *last 20 bytes* of the input, silently truncating/dropping entropy from the ~40+ character bech32 string: [3](#0-2) [4](#0-3) [5](#0-4) 

This reverse-registry entry is precisely what governs the "no pointer-to-pointer" invariant: [6](#0-5) 

Because the key space is (a) truncated to 20 raw ASCII bytes of a bech32 string rather than hashed, and (b) shared across every pointer type/direction without any type or "domain" tag, two semantically different pointees (e.g., a CW20 pointer address and a CW721 pointer address, or two different CW contract addresses whose last 20 characters coincide) can map to the identical reverse-registry key. Whichever registration happens last silently overwrites the other's reverse entry (`store.Set` in `setPointerInfo`, `x/evm/keeper/pointer.go` around line 341-347), and lookups such as `GetCW20Pointee`, `GetCW721Pointee`, `GetCW1155Pointee`, `evmAddressIsPointer`, and `cwAddressIsPointer` can then return/associate the wrong pointee for a given ERC address, or fail to recognize an address as an existing pointer (defeating the pointer-to-pointer guard).

### Impact Explanation
If the pointer-to-pointer guard can be defeated (or an unrelated CW20/CW721/CW1155 identity swapped in) via this collision, a permissionless caller of the `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` precompile methods (any EVM sender can invoke them, as seen in the pointer precompile executor `Execute`) could register a pointer contract whose reverse-mapped "pointee" resolves to a different, unintended CW/ERC asset. Since pointers are used by the EVM/CW bridge to route mints/transfers between the ERC20 pointer and its CW pointee, misrouting or bypassing the anti-chaining check enables unauthorized transfer/mint confusion between assets — a fund-safety issue analogous to Connext's canonical asset mix-up.

### Likelihood Explanation
Triggering an exact, chosen collision against a *specific* existing address requires overcoming close to the full 160-bit key space and is impractical for a targeted attack; however, forcing a collision between two attacker-controlled CW20/CW721/CW1155 contracts is meaningfully easier than intended, because CosmWasm's `Instantiate2` allows salt grinding, and the effective entropy of the last 20 ASCII characters of a bech32 address (base-32 alphabet) is only ~100 bits rather than the full 160-bit address space the code implicitly assumes. This is a real reduction from the intended security margin and is architecturally identical to the reported bug class (identifier truncation used as a unique key instead of a full hash), even though the concrete collision search is nontrivial.

### Recommendation
Derive the reverse-registry key (and any other pointer key built from a non-address string) via `crypto.Keccak256` of the type-tagged identifier, e.g. `keccak256(pointerTypePrefix || pointeeIdentifierBytes)`, instead of truncating with `common.BytesToAddress([]byte(addr))`. This ensures the full identifier and its type/domain are both preserved in the key, exactly as recommended in the referenced report for canonical asset keys.

### Proof of Concept
Conceptual (store-key) collision, illustrating the root cause without requiring an actual grinding run:
1. Register a CW20 pointer for ERC20 address `E1` whose target CW20 bech32 address is `A1` — this stores `PointerReverseRegistryKey(common.BytesToAddress([]byte(A1)))` → `E1` (see `SetCW20ERC20PointerWithVersion`, `x/evm/keeper/pointer.go:174-183`).
2. Grind (via `Instantiate2` salt search) a second CW721/CW1155 contract address `A2` such that `common.BytesToAddress([]byte(A2)) == common.BytesToAddress([]byte(A1))` (i.e., the last 20 ASCII bytes match).
3. Register a CW721/CW1155 pointer for a different ERC address `E2` pointing at `A2` (`SetCW721ERC721PointerWithVersion`/`SetCW1155ERC1155PointerWithVersion`, `x/evm/keeper/pointer.go:219-263`) — this overwrites the same reverse-registry key with `E2`.
4. Subsequent calls to `GetCW20Pointee(E1)`/`evmAddressIsPointer(E1)` (`x/evm/keeper/pointer.go:203-211, 396-402`) now resolve against the overwritten entry, returning stale/incorrect pointee data or incorrectly reporting `E1` as no longer a recognized pointer, defeating the `ErrorPointerToPointerNotAllowed` guard for future registrations targeting `E1`.

```go
// CW20 -> ERC20
func (k *Keeper) SetCW20ERC20PointerWithVersion(ctx sdk.Context, erc20Address common.Address, addr string, version uint16) error {
	if k.evmAddressIsPointer(ctx, erc20Address) {
		return ErrorPointerToPointerNotAllowed
	}
	err := k.setPointerInfo(ctx, types.PointerCW20ERC20Key(erc20Address), []byte(addr), version)
	if err != nil {
		return err
	}
	return k.setPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(addr))), erc20Address[:], version)
}
```
