### Title
Tokenfactory Denom Allow-List (Deny Policy) Enforced Only in MsgServer, Bypassed by Direct SendCoins/InputOutputCoins Callers - (File: sei-cosmos/x/bank/keeper/send.go, sei-cosmos/x/bank/keeper/msg_server.go)

### Summary
The Consul advisory describes a fail-open condition where a data-plane enforcement layer (Envoy xds) failed to apply a configured deny/default-deny intention, letting traffic pass that should have been blocked. sei-chain has a structurally analogous layering problem in `x/bank`: the tokenfactory denom allow-list ("deny by default" policy for restricted denoms) is implemented as a keeper-level predicate, `IsInDenomAllowList`, but it is invoked only from the `MsgServer.Send` and `MsgServer.MultiSend` handlers rather than inside the actual balance-moving primitives (`SendCoins`, `InputOutputCoins`). Any code path that reaches those primitives without going through the two message handlers moves the coins with no allow-list (or `BlockedAddr`) check at all.

### Finding Description
`BaseSendKeeper.IsInDenomAllowList` implements the actual per-denom access control: for tokenfactory-prefixed denoms with a configured allow list, an address must be in that list to send/receive the coin; otherwise the transfer is rejected. [1](#0-0) 

This check, together with `BlockedAddr`, is wired in exactly two places — `msgServer.Send` and `msgServer.MultiSend`: [2](#0-1) [3](#0-2) 

A repo-wide search for `IsInDenomAllowList` returns matches only in `msg_server.go` (the enforcement call sites), `send.go` (the function definition itself), and test files — there is no re-check of the allow list inside `SendCoins`/`InputOutputCoins` themselves, nor any reference to it from the EVM bank precompile, the CosmWasm bank bindings/CW20 pointer transfer path, IBC transfer keeper, or tokenfactory force-transfer logic. This mirrors the Consul bug class: the "deny" policy is correctly modeled and works when traffic flows through the one code path that was instrumented (the L7 filter / the two Msg handlers), but any other path that produces the same effect (moving the coin) does not re-derive or re-apply the same decision, so the restriction "fails open."

### Impact Explanation
If a tokenfactory denom creator configures a `DenomAllowList` to restrict who may hold/transfer a sensitive denom (a compliance/whitelist control exposed via tokenfactory), that control can be silently bypassed by any component that ends up calling `SendCoins`/`InputOutputCoins` directly instead of going through `MsgSend`/`MsgMultiSend` — e.g., internal module-to-account transfers, precompile-driven transfers, or any future/existing integration that moves the denom without routing through the two guarded message handlers. This allows an address that is not on the allow list (and even one on `BlockedAddr`) to send or receive the restricted asset, defeating the intended access control and enabling unauthorized transfer of a token whose distribution is supposed to be restricted.

### Likelihood Explanation
Likelihood depends entirely on whether any reachable, non-`MsgSend`/`MsgMultiSend` path invokes `SendCoins`/`InputOutputCoins` for a tokenfactory-restricted denom. This is plausible given the number of independent subsystems that move bank balances (EVM precompiles, CW/wasm bindings, IBC), but I was unable to fully enumerate every call site of `SendCoins`/`InputOutputCoins` for tokenfactory denoms within the remaining investigation budget, so the concrete exploitable path (which specific caller bypasses the check) is not fully confirmed here.

### Recommendation
Move the `IsInDenomAllowList` (and `BlockedAddr`) enforcement into `BaseSendKeeper.SendCoins` and `InputOutputCoins` themselves (or a shared pre-transfer hook that all coin-movement entry points funnel through), rather than relying on each caller (currently only the two `MsgServer` handlers) to independently re-implement the check. This closes the fail-open class regardless of how many additional entry points call the keeper directly in the future.

### Proof of Concept
Not fully constructible from the available static analysis alone — confirming exploitability requires identifying and exercising a concrete non-`MsgSend`/`MsgMultiSend` code path (e.g., a precompile or wasm binding) that calls `k.SendCoins`/`k.InputOutputCoins` with a tokenfactory-allow-listed denom and observing that the transfer succeeds despite the sender/receiver not being on the allow list. This would need to be validated with a running Devin session against the full test suite/codebase to enumerate all callers of `SendCoins`/`InputOutputCoins`.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)
	if err != nil {
		return nil, err
	}

func (k msgServer) MultiSend(goCtx context.Context, msg *types.MsgMultiSend) (*types.MsgMultiSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	denomToAllowListCache := make(map[string]AllowedAddresses)
	// NOTE: totalIn == totalOut should already have been checked
	for _, in := range msg.Inputs {
		if err := k.IsSendEnabledCoins(ctx, in.Coins...); err != nil {
			return nil, err
		}
		accAddr := sdk.MustAccAddressFromBech32(in.Address)
		if !k.IsInDenomAllowList(ctx, accAddr, in.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", accAddr)
		}
	}

	for _, out := range msg.Outputs {
		accAddr := sdk.MustAccAddressFromBech32(out.Address)

		if k.BlockedAddr(accAddr) || !k.IsInDenomAllowList(ctx, accAddr, out.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", out.Address)
		}
	}

	err := k.InputOutputCoins(ctx, msg.Inputs, msg.Outputs)
	if err != nil {
		return nil, err
	}
