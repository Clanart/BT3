### Title
Prefix-only path-boundary check in `resolveWithin()` allows escaping the repository root via sibling-directory name collision - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` decides whether a resolved path is "inside" a repository by doing a raw string `startsWith()` comparison between the resolved path and the root path, with no check that a path separator follows the root prefix. This is the same class of bug as the C4 report: a boundary/invariant check that is subtly wrong (an off-by-something comparison) and silently defeats the guarantee the function exists to provide. Here, instead of "unlock never subtracts amount", the invariant "resolved path is inside root" is broken whenever a sibling directory's name happens to start with the root directory's name (e.g. `myrepo` vs. `myrepo-secrets`).

### Finding Description
`resolveWithin()` / `_resolveWithin()` is Desktop's canonical helper for confining a user- or attacker-influenced relative path to a root directory: [1](#0-0) 

```
const normalizedRoot = normalize(rootPath)
...
const resolved = resolve(normalizedRoot, normalizedRelative)

const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```

`path.resolve(normalizedRoot, normalizedRelative)` correctly collapses `..` segments, but the *only* containment test afterward is a plain string `startsWith`. If `realRoot` is, say, `/Users/victim/Documents/GitHub/myrepo`, then a relative segment such as `../myrepo-secrets/secret.txt` resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/secret.txt`, which **literally starts with** the string `/Users/victim/Documents/GitHub/myrepo` even though `myrepo-secrets` is a completely different, sibling directory. No `..` remains in `resolved`, no symlink is used, so this bypasses every case currently covered by the unit tests: [2](#0-1) 

The existing tests only check "goes above root" (`../..`) and "traverses out and back into the exact root", never the sibling-name-collision case, so this gap is untested.

One concrete attacker-reachable call site is the "Open in Desktop" deep-link handler: [3](#0-2) 

```
if (filepath !== null) {
  if (isAbsolute(filepath)) {
    log.error(`Refusing to open absolute path: ${filepath}`)
    return
  }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
```

`filepath` comes straight from a `github-mac://openRepo/...?filepath=...` (or `x-github-client://openrepo/...`) URL that the app dispatches via `parseAppURL`: [4](#0-3) 

The only guard applied is `isAbsolute(filepath)` — which blocks `/etc/passwd`-style absolute inputs but does nothing to stop a **relative** payload such as `../<reponame>-something/secret-file`. Since Desktop clones repos into a shared parent folder (e.g. `~/Documents/GitHub/<reponame>`), and `<reponame>` is attacker-known (it's part of the same URL/clone target), an attacker who controls a link the user clicks can pick a `filepath` value that resolves outside the actual repository into a sibling folder whose name shares the repo's name as a prefix, and `resolveWithin` will incorrectly treat it as "inside" the root.

### Impact Explanation
`resolveWithin` is Desktop's general-purpose containment primitive; the `startsWith`-without-separator bug means **any** caller that relies on it to keep user/attacker-supplied relative paths inside a specific directory can be tricked into operating on a path in a sibling directory. The identified corrupted value is the return value of `_resolveWithin` (a "safe, contained path") which is actually an arbitrary path outside the intended root whenever a same-prefix sibling directory exists. Concretely, via the "Open in Desktop" deep link this leads to `shell.showItemInFolder()` being invoked and the containing folder of an out-of-repo file being revealed/opened in the OS file manager — a file-system disclosure driven purely by a link the user clicks, matching the "file read outside the repo" impact category. Other current or future callers of `resolveWithin` (e.g. Copilot conflict-context file resolution) inherit the same weakened guarantee.

### Likelihood Explanation
Exploitation requires only that the user click a crafted deep link (or open a crafted URL scheme) while having a locally cloned repository whose default clone directory contains, or can be made to contain, a sibling folder whose name is a prefix-extension of the repository name (a very plausible naming collision, e.g. `project` vs `project-backup`, `project-old`, `project.bak`, or an attacker-supplied clone target name chosen specifically to create this collision before sending the link). No admin rights, no pre-existing malware, and no credential leakage are required — only a link click and normal repository layout on disk, which satisfies the valid-impact criteria for this analysis.

### Recommendation
Change the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) from a raw prefix test to one that requires a path-separator boundary (or exact equality with the root):

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

Add regression tests covering the sibling-directory-prefix case (e.g. root `.../myrepo` vs. resolved `.../myrepo-evil/secret`) for both POSIX and Win32 variants.

### Proof of Concept
1. User has a repository cloned at `~/Documents/GitHub/myrepo` and, independently, a folder `~/Documents/GitHub/myrepo-secrets` (or an attacker gets the user to clone/create such a sibling, e.g. via a prior deep link `x-github-client://openrepo/https://github.com/attacker/myrepo-secrets`).
2. Attacker sends the user a link:
   `x-github-client://openrepo/https://github.com/victim/myrepo?filepath=../myrepo-secrets/secret.txt`
3. `parseAppURL` parses this into `open-repository-from-url` with `filepath = "../myrepo-secrets/secret.txt"`.
4. `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1971`) checks `isAbsolute(filepath)` → false, so it proceeds.
5. `resolveWithin(repository.path, filepath)` computes `resolved = ~/Documents/GitHub/myrepo-secrets/secret.txt`, and since this string starts with `~/Documents/GitHub/myrepo`, the check passes and returns the resolved path instead of `null`.
6. `shell.showItemInFolder(resolved)` opens/reveals a file in `myrepo-secrets`, a directory entirely outside the intended repository — demonstrating disclosure of file-system content outside the repo root triggered purely by a clicked link. [5](#0-4) [6](#0-5) [4](#0-3) [2](#0-1)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
      }

        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }
```
