Based on my research, I found a strong analog in the GitHub Desktop codebase involving the same class of bug: a hardcoded assumption about which "side" of a two-sided value corresponds to which semantic meaning, where that mapping is actually context-dependent and the correctness is pushed onto the caller rather than being enforced by the code that produces the value.

### Title
Ours/Theirs conflict-resolution stage mapping is not rebase-aware, causing silent corruption of committed content - (File: app/src/lib/git/diff.ts)

### Summary
`getResolutionDiff` hardcodes `ours` to git index stage `:2` and `theirs` to stage `:3`, but git's own semantics for these stages flip during a rebase (the upstream branch becomes "ours" and the branch being replayed becomes "theirs"). The function's own doc comment admits this and states the caller must perform the remapping, but the Copilot-conflict UI code path (`copilot-conflicts-changes.tsx`, `copilot-conflicts-dialog.tsx`) passes the UI-facing `'ours'`/`'theirs'` choice straight through to `getResolutionDiff` as the `stage` option without any indication of a rebase-specific inversion. This mirrors the `BondOracleAdapter` bug: a fixed assumption about which "slot" holds which side, correct only for one relative ordering (merge, not rebase) of the two inputs, with no code-level guard forcing the mapping to be checked/corrected.

### Finding Description
`getResolutionDiff` in [1](#0-0)  converts a `stage: 'ours' | 'theirs'` argument directly to git index stage `:2` / `:3`. The function's own documentation explicitly states the ordering assumption is conditional and not self-verifying: [2](#0-1) 

This is functionally identical to the `BondOracleAdapter` root cause: the code returns a value assuming a fixed slot ordering (bondToken=tokenB) that is only valid for one arrangement of the underlying data, and doesn't verify which arrangement is actually in effect — the burden of correctness is placed entirely on the caller.

The Copilot conflict-resolution UI (`copilot-conflicts-changes.tsx`) calls this function directly using the user's UI selection as the stage: [3](#0-2) 

The resolution labels shown to the user ("Current" / "Incoming") come from a static map that does not vary by operation kind: [4](#0-3) 

I was unable to fully trace, within the remaining tool budget, whether `stageManualConflictResolution` (which drives the actual `git checkout --ours/--theirs` staging at commit time, in `app/src/lib/git/stage.ts` and `app/src/lib/git/checkout.ts`) or the `ourBranch`/`theirBranch` labels surfaced in `app-store.ts` correctly invert for rebase operations elsewhere in the codebase. The diff-preview path (`getResolutionDiff`) is the piece I confirmed does not perform any rebase-aware inversion, and its own comment flags this as a caller responsibility that is easy to miss.

### Impact Explanation
If the diff preview mislabels which content belongs to "Current" vs "Incoming" during a rebase (attacker controls the upstream/rebased branch content via a malicious fetched branch, e.g. in a spoofed rebase-onto-upstream workflow), a user could visually confirm what they believe is their own content in the preview, pick that resolution, and have the opposite side's (attacker-supplied) content silently staged and committed/pushed instead — corrupting what the user commits without any warning. This falls under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Likelihood depends on how many UI surfaces rely on `getResolutionDiff`'s preview to make a "ours"/"theirs" decision during an active rebase with conflicts against attacker-influenced content (e.g. a fetched/rebased-onto branch). This is a plausible but conditional path (rebase + Copilot-conflict resolution flow specifically), and I could not confirm from the index whether a compensating inversion exists upstream in the caller chain, which limits confidence in exploitability being unmitigated end-to-end.

### Recommendation
`getResolutionDiff` (and any similar `ours`/`theirs`-to-stage mapping) should accept the current operation kind (merge vs. rebase) as an explicit parameter and internally resolve stage `:2`/`:3` accordingly, rather than relying on callers to remember and correctly apply the inversion. Add a regression test that exercises the "resolution diff during rebase" scenario to confirm the preview always matches what will actually be staged by `stageManualConflictResolution`.

### Proof of Concept
Not independently verified beyond static code reading; would need to be reproduced by: starting a rebase where the upstream (attacker-controlled) branch conflicts with the local branch, opening the Copilot-conflict resolution dialog, and confirming whether the "Current"/"Incoming" diff preview and the label attribution (`ourBranch`/`theirBranch`) match git's own git-rebase-time ours/theirs semantics (stage 2 = upstream, stage 3 = local) rather than the merge-time semantics assumed by `getResolutionDiff`.
