### Title
`_applyCopilotConflictResolutions()` overwrites externally-resolved conflict files using a stale in-memory status snapshot instead of a fresh `getStatus()` check - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions()` decides whether it is safe to overwrite a conflicted file on disk with Copilot's stored resolution by consulting `this.repositoryStateCache.get(repository)` — an in-memory snapshot of the working directory taken once at function entry — rather than re-checking the file's live conflict-marker state on disk immediately before the write. This is structurally identical to the Sherlock M-5 bug: a critical decision (liquidate / not liquidate, overwrite / not overwrite) is made from a stale cached value (`exchangeRateStored()` / `repositoryStateCache`) instead of the up-to-date value (`exchangeRateCurrent()` / a fresh `getStatus()` call) that the codebase already knows how to compute.

### Finding Description [1](#0-0) 

At the top of `_applyCopilotConflictResolutions`, the function grabs the current cached repository state once: [2](#0-1) 

Later, for each Copilot-generated resolution, the function explicitly guards against clobbering a conflict that the user already resolved themselves (e.g. in an external editor) while the Copilot AI run was in progress: [3](#0-2) 

The guard's own comment states the invariant it is trying to protect: *"If the user resolved this file externally… while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work."* However, the check reads `onDiskFile` from `state.changesState.workingDirectory.files` — the same `state` object captured once at function entry — not from a fresh `getStatus(repository)` call. `state` is only as current as the last time `repositoryStateCache` was updated via `_loadStatus`/`_refreshRepository` elsewhere in the app (e.g. on window focus or after other git operations), and nothing in this function forces a refresh before either the "which side was deleted" decision at line 7206 or the "has this file already been resolved" decision at line 7247, or before the destructive `writeFile` at line 7258.

The AI-driven Copilot conflict resolution flow is explicitly documented (via its own telemetry) to run long enough for the user to keep editing files in the meantime: [4](#0-3) 

`copilotConflictResolutionOver60sCount` / `Over120sCount` confirm that this AI turn can take well over a minute — ample time for the user to open the conflicted file in an editor, resolve it manually, and save, all while `repositoryStateCache` is not guaranteed to reflect that edit by the time `_applyCopilotConflictResolutions` runs. The same conflicted-file status object (`WorkingDirectoryFileChange`/`isConflictedFileStatus`/`hasUnresolvedConflicts`) used elsewhere in the app is only trustworthy immediately after a `getStatus` call: [5](#0-4) [6](#0-5) 

The dialog itself acknowledges this exact race by re-checking conflict-marker counts against `this.props.workingDirectory` at render time and treats the on-disk edit as "the source of truth" over any previously chosen dropdown value: [7](#0-6) 

But that live re-check only feeds the dialog's *display*; it does not feed `_applyCopilotConflictResolutions`, which independently re-derives `onDiskFile` from the stale `repositoryStateCache` snapshot rather than from a fresh status call or from the props the dialog itself used.

### Impact Explanation
If the cached `repositoryStateCache` state is stale relative to the user's own last-second manual resolution of a conflicted file (via external editor), `_applyCopilotConflictResolutions` will pass the `hasUnresolvedConflicts` guard incorrectly (because the cache still shows conflict markers present or the file's deleted-side classification is out of date) and proceed to call `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, silently overwriting the user's own resolution with Copilot's AI-generated content, and then stage it via `git add`. This is a silent corruption of what the user is about to commit/push — content the user believes they resolved is discarded without any warning, error, or diff review, satisfying the "silent corruption of what the user commits or pushes" impact category. Because this happens on the attacker-controllable-content path (Copilot's suggestion is derived from the untrusted conflicting branch/remote content being merged/rebased/cherry-picked), a maliciously crafted upstream branch could increase the chance that Copilot proposes a resolution that reintroduces attacker content over the user's correct fix, and the stale-cache race removes the last line of defense meant to prevent exactly that.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the user to use the Copilot AI conflict-resolution feature, (b) the AI run to take a non-trivial amount of time (confirmed as commonly >60s/>120s per existing telemetry), and (c) the user to resolve a conflicted file externally during that window before clicking "Continue Merge". This is a realistic workflow — users frequently jump to an editor while waiting on a slow operation — and does not require any admin rights, local malware, or unnatural steps; it is a natural consequence of the app's own async AI-resolution design combined with its reliance on a stale cache instead of a fresh status read.

### Recommendation
Before writing any Copilot resolution to disk in `_applyCopilotConflictResolutions`, call a fresh `getStatus(repository)` (as already done in `getStatus`/`gitStore.loadStatus`) and use that live result — not the cached `repositoryStateCache` snapshot — to determine both the deleted-side classification and whether the file still has unresolved conflict markers. Only files that are still genuinely conflicted according to the live status should be overwritten; anything already resolved externally should be skipped, matching the intent already documented in the code's own comments.

### Proof of Concept
1. Start a merge/rebase/cherry-pick that produces a conflict in `file.md`, and trigger the Copilot conflict-resolution flow (`_generateCopilotConflictResolution` / the "Continue Merge" flow that eventually calls `_applyCopilotConflictResolutions`).
2. While the AI resolution is running (commonly 60–120+ seconds, per `copilotConflictResolutionOver60sCount`/`Over120sCount` telemetry), manually resolve `file.md` in an external editor and save, removing all conflict markers.
3. Do not touch Desktop's UI (so `repositoryStateCache` for this repo is not refreshed by an unrelated focus/status-triggering event) before the AI run completes and the result dialog appears.
4. Click "Continue Merge" in the Copilot conflicts dialog, invoking `_applyCopilotConflictResolutions`.
5. Because `state.changesState.workingDirectory.files` still reflects the pre-edit conflicted snapshot, the guard at lines 7250–7256 fails to detect the external resolution, and `writeFile` at line 7258 overwrites the user's manually resolved `file.md` with Copilot's stored `resolvedContent`, which then gets staged via `git add` — silently discarding the user's actual fix before it is committed.

Note: I was unable to fully trace the exact timing/refresh guarantees between the start of the Copilot AI turn and `_applyCopilotConflictResolutions` (e.g., whether any intervening `_refreshRepository` call reliably updates the cache in all code paths), since the AI-resolution generation logic and its exact dispatcher wiring were not fully visible in the indexed portions of `app-store.ts`. Confirming the precise refresh cadence would require reading the full Copilot conflict-resolution flow in `app-store.ts` (the section preceding line 7100) and `dispatcher.ts`.

 * Determine if we have any conflict markers or if its been resolved manually

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
