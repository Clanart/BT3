### Title
Cached DKG-confirmation preprocess is never invalidated, allowing nonce reuse across distinct `share`/`complete` invocations - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class — a session artifact that remains valid after it should have been invalidated — maps directly onto `SigningProtocol::preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs`. A deterministic FROST nonce seed (`CachedPreprocess`) is stored in `CachedPreprocesses` keyed only by `context = (b"DkgConfirmer", attempt)` and is never deleted, rotated, or marked consumed. Every call to `share_internal`/`complete` re-derives identical nonces from that seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`, and then calls `machine.sign(...)` again. If any two invocations operate on distinct participant preprocess sets or a distinct `key_pair` (hence a distinct `set_keys_message` / distinct binding factors), the validator emits two signature shares under the same nonce pair — the classic FROST nonce-reuse private-share recovery.

### Finding Description
- `preprocess_internal` creates a seed once and caches it: `if CachedPreprocesses::get(self.txn, &self.context).is_none() { ... CachedPreprocesses::set(...) }` (signing_protocol.rs:123-135). There is no deletion path; the same seed serves the entire `(DkgConfirmer, attempt)` lifetime.
- Each use reconstructs identical nonces: `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (line 144-145), and `seeded_preprocess` derives nonces deterministically from the seed via `ChaCha20Rng::from_seed` (`crypto/frost/src/sign.rs:127-132`).
- `share_internal` calls `machine.sign(preprocesses, msg)` (line 170). `DkgConfirmer::complete` calls `self.share_internal(preprocesses, key_pair)` *again* (lines 321-324) to rebuild the machine — meaning `sign` runs once for `share(...)` and a second time inside `complete(...)`, both under the same nonces.
- The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)` (lines 296-300), and the FROST share value additionally depends on the binding factors derived from *all* submitted preprocesses (`preprocesses` parameter, lines 152-168). Both `key_pair` and `preprocesses` are caller-supplied per invocation and are fed from on-chain validator transactions in `handle.rs`.
- The module's own safety argument (lines 25-51) admits reuse is only safe if `sign` is called with identical inputs, and flags the missing verification as a TODO (lines 50-54). Nothing cryptographically enforces that `share` and `complete` (or a rebuilt `DkgConfirmer::new` for the same `attempt` with a different `removed_as_of_dkg_attempt` result, which changes `removed` and thus the message) receive identical inputs.

### Impact Explanation
FROST signature shares are linear in the nonce: `s_i = d_i + e_i·ρ_i + λ_i·share_i·c`. Two shares issued under the same `(d_i, e_i)` nonces but different binding factors `ρ`, messages `c`, or signer sets yield independent linear equations, allowing recovery of the validator's secret share — i.e., the private key behind its MuSig participation in DKG confirmation. Since the coordinator's root-of-trust key is used here (not a processor key), compromise undermines validator-set confirmation signing. The code itself states: "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md`, `crypto/frost/src/sign.rs:85-87`, `211-219`).

### Likelihood Explanation
Triggering requires two `share_internal` executions with differing inputs under one `attempt` context. `share` and `complete` are separate public entry points driven by distinct on-chain transactions carrying validator-supplied preprocesses and key pairs; a validator influencing which finalized messages reach each call (e.g., different participant subsets or a different `key_pair` between the share and complete phases, or after a rebuild where `removed_as_of_dkg_attempt` returns a different removed set) induces the second `sign` on changed inputs. Reorganizations are argued away in comments, but the gap between the two call sites and the missing commitment-consistency check (explicitly TODO) leaves the exposure real. An unprivileged external party cannot trigger it alone — a participating validator submitting confirmation transactions can — keeping this at Medium severity rather than higher.

### Recommendation
Invalidate the cached seed after first use: on `share_internal`, perform `CachedPreprocesses::set` removal/overwrite (e.g., store a tombstone or regenerate a fresh seed) so `preprocess_internal` cannot reconstruct the same nonces twice. Alternatively, persist the exact `preprocesses`/`key_pair` hash alongside the seed and abort (returning an error rather than re-signing) if a subsequent call presents different inputs — implementing the "check commitments match presumed on-chain commitments" already marked TODO at lines 50-54. The seed should be bound not just to `attempt` but to the finalized message and participant set.

### Proof of Concept
1. Validator set enters a DKG confirmation `attempt`; `DkgConfirmer::preprocess` publishes commitments derived from seed `S` stored under `(b"DkgConfirmer", attempt)`.
2. `DkgConfirmer::share(preprocesses_A, key_pair_A)` executes `share_internal` → `sign` with nonces from `S`, producing share `s_A` for message `m_A` and binding-factor set `A`.
3. `DkgConfirmer::complete(preprocesses_B, key_pair_B, shares)` re-enters `share_internal` (signing_protocol.rs:321-324) → `preprocess_internal` reloads the same un-invalidated seed `S` → identical nonces → `sign` produces `s_B` for message `m_B`/binding set `B`.
4. With `s_A` and `s_B` sharing the same nonce scalars, an observer solves the linear system to recover the validator's secret share — exactly the key-share recovery the `CachedPreprocess` docs warn about (`crypto/frost/src/sign.rs:211-219`).

Uncertainty: I could not fully inspect `coordinator/src/tributary/handle.rs` to confirm whether the coordinator guarantees `share` and `complete` are fed byte-identical finalized payloads; if the BFT layer strictly enforces identical inputs for both calls, the practical exploitability narrows to the rebuild/`removed`-changes path. The missing enforcement is nonetheless a real correctness/security gap consistent with the file's own TODOs.
