### Title
Depositing while vault utilization is 100% mints zero shares and silently donates the deposit to existing shareholders - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
The BakerFi report describes a `totalSupply == 0` / `totalAssets != 0` mismatch that either DoSes future deposits or, in the rounding-dust variant, permanently strands a small amount of funds. Zest's tokenized vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) use the mirror-image branch of the same rounding logic in `convert-to-shares-preview`: when `total-supply-preview` is non-zero but `total-assets-preview` is zero, the function returns `u0` shares [1](#0-0) . Unlike the "both zero" guard in BakerFi's `_depositInternal`, Zest's `deposit` does not revert in this state - it still pulls the depositor's underlying tokens and credits them to the shared `assets` pool while minting zero zTokens to the depositor [2](#0-1) .

### Finding Description
`total-assets` for a vault is `current-assets + max(debt - total-borrowed, 0)` [3](#0-2) . `current-assets` (the `assets` var) is reduced to `u0` whenever the vault reaches 100% utilization, which happens legitimately through `system-borrow`, gated only by `<= amount available-assets` [4](#0-3) . Because `accrue` is invoked at the start of the same call and synchronizes `index`/`debt` before the borrow executes, immediately after a borrow that drains `assets` to zero, `debt == total-borrowed`, so the "uncollected interest" term is also zero. At this exact point `total-assets-preview == u0` while `total-supply-preview > u0` (existing shareholders still hold zTokens backed by the outstanding loan).

Any subsequent `deposit` call in this window computes `inkind = convert-to-shares-preview(amount)`, which hits the `(is-eq ta u0) → u0` branch [1](#0-0) . The only protection is `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` [5](#0-4) ; if the caller supplies `min-out = u0` (the natural default when a depositor is not defending against slippage, since they don't expect a 100%-utilized pool to yield 0 shares), the deposit proceeds: `receive-underlying` pulls the real tokens, `ft-mint? zft u0 recipient` mints nothing to the depositor, and `var-set assets (+ current-assets amount)` adds the deposited funds to the shared pool [6](#0-5) . The deposited principal is absorbed into `total-assets` and thus proportionally redistributed to all pre-existing zToken holders (their `convert-to-assets-preview` value rises), while the depositor receives zero shares and zero recourse.

This is the rounding-direction root cause called out in the report (division truncating a legitimate ratio to zero), reachable without any external donation, oracle manipulation, or privileged access - purely through normal borrow/deposit sequencing at 100% utilization.

### Impact Explanation
This is direct, permanent theft of a user's principal at rest: the depositor's underlying asset transfer is absorbed into the vault's `assets` pool and effectively distributed to existing shareholders, with zero shares issued to the depositor and no way to reclaim the deposited amount. This satisfies the Critical impact class ("direct theft of user funds at rest ... or protocol insolvency" is not needed - fund theft alone qualifies).

### Likelihood Explanation
Requires (1) a vault reaching exactly 100% utilization via a legitimate `system-borrow` call, and (2) a `deposit` landing before enough time/interest accrues to push `total-assets` back above zero, and (3) the depositor (or the calling front-end/integrator) passing `min-out = u0`. High-utilization pools are a normal, intended operating state for a lending market, and `min-out = u0` is a common default for programmatic integrators or simple UIs that don't anticipate a 0-share outcome, making this realistically triggerable, especially by an opportunistic actor who can time a large borrow immediately before another user's deposit lands (e.g., front-running a pending deposit in the same block).

### Recommendation
In `convert-to-shares-preview`, when `ts > u0` and `ta == u0` (state where all previous depositors' claims are technically un-backed at that instant), do not silently mint 0 shares. Either (a) revert the `deposit` with an explicit error (e.g., `ERR-OUTPUT-ZERO`, mirroring the check already present in `redeem`) so no assets change hands, or (b) fall back to minting `amount` shares 1:1 as is already done for the `ts == u0` case, so the depositor is fairly credited rather than donating funds to existing holders. Additionally, enforce a non-zero `min-out` at the protocol level (or default it defensively) for `deposit` calls so a `0`-share outcome cannot be silently accepted.

### Proof of Concept
1. Vault `v0-vault-stx` has one depositor A with shares outstanding; utilization pushed to 100% via `system-borrow` (borrower B borrows exactly `available-assets`), driving `assets` var to `u0` [4](#0-3) .
2. In the same block (before further interest accrues), `total-debt == total-borrowed`, so `total-assets-preview == u0` while `total-supply-preview > u0` [7](#0-6) .
3. User C calls `deposit(amount, min-out: u0, recipient: C)`. `convert-to-shares-preview` returns `u0` [1](#0-0) . The slippage assert `(>= u0 u0)` passes, `receive-underlying` pulls C's tokens, `ft-mint? zft u0 C` mints nothing, and `assets` increases by `amount` [8](#0-7) .
4. C's tokens are now part of the vault's `assets`, redeemable only by existing shareholder A via `redeem`, while C holds zero zTokens - a complete, permanent loss of C's deposit.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))

(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (CAP-DEBT (var-get cap-debt))
      (available-assets (get-available-assets))
      (scaled-principal (var-get principal-scaled))
      (idx (var-get index))
      (debt (total-debt))
      (scaled-amount (mul-div-up amount INDEX-PRECISION idx))
      (updated-scaled-principal (+ scaled-principal scaled-amount)))

    (try! (check-caller-auth))
    (asserts! (not (get borrow states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (<= amount available-assets) ERR-INSUFFICIENT-VAULT-LIQUIDITY)
    (asserts! (<= (+ debt amount) CAP-DEBT) ERR-DEBT-CAP-EXCEEDED)

    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed (+ (var-get total-borrowed) amount))
    (try! (send-underlying amount receiver))

    (print {
      action: "system-borrow",
      caller: contract-caller,
      data: {
        receiver: receiver,
        amount: amount,
        scaled-amount: scaled-amount,
        principal-scaled: updated-scaled-principal,
        total-borrowed: (var-get total-borrowed),
        index: idx
      }
    })

    (ok true)))
