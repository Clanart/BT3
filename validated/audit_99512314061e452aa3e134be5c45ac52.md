## Title
Silent, instant remote-URL retargeting from untrusted GitHub API metadata — ([File: app/src/lib/stores/updates/update-remote-url.ts])

## Summary
The external report's core defect is that a governance-controlled parameter (fee/margin/lot-size) takes effect **instantly** upon a state change coming from a privileged-but-external source, with no delay for the user to react before the new value materially changes their exposure. The GitHub Desktop analog is `updateRemoteUrl`, which silently and instantly rewrites the local `origin` remote URL — the destination of every future `git push`/`git fetch` — based on the `clone_url` field of a `GitHub API` repository object, with no user confirmation, warning, or delay.

## Finding Description
`updateRemoteUrl` compares the repository's currently configured remote URL to the `clone_url` returned by the GitHub API for the same repository record. If the protocol matches and the previously-stored `clone_url` matched the existing remote (i.e. the user hasn't manually customized it away from what Desktop last saw), but the *new* API-reported `clone_url` now differs, Desktop calls `gitStore.setRemoteURL` immediately — with no dialog, confirmation, or delay: [1](#0-0) 

This ends up calling the low-level remote mutation with no user-facing gate at all: [2](#0-1) 

Compare this to the intentional, user-driven path for changing a remote URL, which requires the user to open Repository Settings, edit the field, and explicitly click Save before `dispatcher.setRemoteURL` is invoked: [3](#0-2) 

The `clone_url` value is sourced entirely from the `GitHub API` repository object — a value the report's threat model explicitly allows an attacker to control (e.g., a repository owner/collaborator who renames or transfers a repo the victim has cloned, or an attacker-operated GitHub Enterprise Server the victim is configured to talk to). Desktop's own test suite confirms this update happens automatically and unconditionally once the heuristic conditions are met: [4](#0-3) 

The corrupted value is the local `origin` remote URL, i.e., the destination git object of the user's next push/fetch. Existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlsMatch` via `urlMatchesRemote`) only prevent the update when the user has already diverged their local remote from what Desktop last recorded — they do nothing to validate that the *new* URL is safe or expected, and they provide no timelock/notice before applying it: [5](#0-4) 

## Impact Explanation
If a repository the victim has cloned is renamed or transferred by its owner (or the victim is pointed at a malicious/compromised GitHub Enterprise instance), Desktop will silently retarget the local `origin` remote to whatever URL the API now reports, without ever displaying a dialog or requiring confirmation — unlike the manual Repository Settings flow which always requires explicit user action. Because Desktop's credential helper resolves credentials per-endpoint, a retargeted remote whose host differs from what the user expects can result in the user unknowingly pushing commits (and, depending on host/credential matching, exposing credentials) to a different endpoint than the one they intended to trust. This mirrors the "silent corruption of what the user commits or pushes" impact class explicitly named as valid.

## Likelihood Explanation
The trigger conditions are narrow but realistically reachable without any local/physical access, admin rights, or prior malware: the attacker only needs control over the repository's `clone_url` as seen by the GitHub API (achievable by a repo owner/admin renaming/transferring a repo the victim has already cloned, or by operating a GHES/GHAE instance the victim connects to). No unusual user interaction is required — the update happens as part of normal background repository refresh logic, distinct from the deliberate Repository Settings save path.

## Recommendation
Do not apply automatic remote-URL updates derived from API metadata silently. At minimum:
- Surface a confirmation dialog (similar to the existing `UpstreamAlreadyExists` pattern) before rewriting `origin`'s URL: [6](#0-5) 
- Add a delay/staging window and a persistent, dismissible notice showing old vs. new URL, giving the user time to notice and reject an unexpected retarget before it silently takes effect, echoing the report's timelock recommendation.

## Proof of Concept
1. Victim clones a repository and Desktop stores its GitHub metadata, including `clone_url`, matching the local `origin` remote.
2. Attacker (owner/admin of that repository, or operator of a malicious GHES the victim is configured against) changes the repository's underlying `clone_url` (e.g., via rename/transfer, or by serving a crafted API response from a GHES instance).
3. On the next background repository refresh, `updateRemoteUrl` sees `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is true and calls `gitStore.setRemoteURL(...)` automatically: [7](#0-6) 
4. The victim's next `git push` from Desktop is silently sent to the new remote with no warning ever shown, as confirmed by the automated test asserting the URL changes without any user interaction: [4](#0-3) 

**Note:** I was unable to fully trace the exact call site in `app-store.ts` that invokes `updateRemoteUrl` (three references exist there) within the available tool budget, so the precise refresh trigger (e.g., periodic background fetch vs. explicit repository open) could not be pinned down from local evidence alone; the behavior and its lack of confirmation/timelock is nonetheless established directly from `update-remote-url.ts` and its accompanying test.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
