## Title
Desktop explicitly disables Git's clone-time hook/config injection protection (`GIT_CLONE_PROTECTION_ACTIVE=false`) during recursive clone — (`File: app/src/lib/git/clone.ts`)

### Summary
`clone()` performs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` while explicitly setting the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. [1](#0-0) 
This is the exact opposite of Git's own hardening: Git introduced `GIT_CLONE_PROTECTION_ACTIVE`/`clone.protectHookExecPath`-style safeguards after multiple CVEs (e.g. CVE‑2024‑32002, CVE‑2024‑32004, CVE‑2024‑32465) in which a malicious remote — combined with `--recursive` submodule checkout, case‑insensitive or symlink‑friendly filesystems, or crafted nested `.git`/hooks paths — could cause Git itself to write and then execute a hook (`post-checkout`, etc.) during clone, achieving code execution as soon as the clone completes. Setting `GIT_CLONE_PROTECTION_ACTIVE=false` turns that protection off for every clone performed through Desktop's UI.

### Finding Description
The attacker-controlled object here is the remote/cloned repository itself (its ref/submodule/tree layout), matching the "attacker controls a cloned/fetched repository" primitive named in the task. Desktop's `clone()`:

1. Always uses `--recursive` (auto-initializes and checks out all submodules) [2](#0-1) .
2. Explicitly forces `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the child Git process's environment [3](#0-2) .

Desktop separately ships a brand-new "git hooks" execution subsystem (`app/src/lib/hooks/*`) that auto-discovers and runs `post-checkout`, `post-merge`, `pre-commit`, etc. hooks found under `core.hooksPath` for the repo [4](#0-3) , and this environment/hook-interception feature is enabled by default (`"[New] Enable hooks support by default - #21590"`) [5](#0-4) . The clone protection variable exists in Git precisely to stop a hostile repository from smuggling an executable hook file into `.git/hooks` (or a `core.hooksPath` target) through recursive submodule checkout tricks before the app has a chance to sanitize it. By disabling this protection unconditionally on every clone, Desktop removes the primary Git-side barrier, and then layers its own hook auto-execution feature on top — meaning that once such a hook file lands on disk via the disabled-protection clone, Desktop's own `withHooksEnv`/`getRepoHooks` pipeline will pick it up and run it on the very next `commit`, `pull`, `push`, or `merge` operation the user performs [6](#0-5) [7](#0-6) .

Existing Desktop guards do not address this specific path:
- `isClonePathSensitive()` only checks the *destination path* is not `~/.ssh`, `~/.gnupg`, `~/.config`, etc. — it says nothing about the *contents* written inside the destination during a recursive clone [8](#0-7) .
- The hooks feature's own gating (`getHooksEnvEnabled()`) only controls whether Desktop intercepts/proxies hook execution for progress reporting — it does not prevent Git itself, or a plain `git`-invoked flow with hooks env disabled, from executing a hook binary that ended up on disk through the clone [9](#0-8) .
- No code path re-enables or scopes `GIT_CLONE_PROTECTION_ACTIVE` back on for the recursive-submodule portion of the clone.

### Impact Explanation
If the bundled Git version is subject to any of the clone-time hook/config-injection classes that `GIT_CLONE_PROTECTION_ACTIVE` was designed to stop, an attacker who gets a victim to clone a crafted repository through Desktop's Clone dialog can achieve local code execution outside the intended repository content (e.g., via a hostile `post-checkout` hook written through a malicious submodule/case-collision trick) — satisfying the "code execution" and "file write/read outside the repo" valid-impact categories. Because Desktop also runs its own hook-interception machinery by default, any hook file that does land on disk this way is guaranteed to be executed on the user's very next Git operation performed via Desktop, even if Desktop's bundled/system Git version itself would otherwise refuse.

### Likelihood Explanation
Likelihood depends on whether the specific bundled `dugite`/Git version in this build is still vulnerable to a clone-time hook-injection bug that `GIT_CLONE_PROTECTION_ACTIVE` mitigates; if it's patched at the Git-binary level, disabling the app-level flag is redundant-but-still-risky defense-in-depth removal. I could not verify the exact bundled Git/dugite version from the indexed files, so I cannot confirm a currently-exploitable Git binary is shipped — this is the main uncertainty in this finding. What is certain from the code is that Desktop actively and unconditionally opts out of a security control that upstream Git ships specifically to guard against untrusted-clone hook injection, for every single clone operation, without any repo-specific risk assessment.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override, or replace it with the narrowest possible allow-list (e.g., only disable for known-safe local file:// clones initiated by the app itself, never for network URLs).
- Audit why this override was introduced (likely to work around a compatibility issue with the recursive submodule flow) and instead fix the underlying compatibility issue without disabling the security control globally.
- Add regression tests analogous to the existing `clone-path-safety-test.ts` suite that assert clone-time hook/config injection protections remain active for standard `clone --recursive` invocations.

### Proof of Concept
1. Bundle a Git version affected by a clone-time hook/config injection issue that `GIT_CLONE_PROTECTION_ACTIVE` mitigates (verify via the shipped `dugite`/git version — not confirmed from indexed files).
2. Attacker crafts a malicious repository containing a submodule structured to exploit that issue such that, upon `git clone --recursive`, a hook script (e.g. `post-checkout`) is written into `.git/hooks` (or a `core.hooksPath` location) of the top-level or nested repo.
3. Victim uses Desktop's "Clone a repository" dialog to clone the attacker's URL: `clone()` runs with `GIT_CLONE_PROTECTION_ACTIVE=false` and `--recursive` [1](#0-0) .
4. The malicious hook file is written to disk unprotected.
5. On the user's next Desktop-driven Git operation (commit/pull/push/merge), Desktop's own hooks subsystem discovers and executes it automatically [4](#0-3) [10](#0-9) , achieving code execution under the victim's user account.

```typescript
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```

```typescript
export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
```

```typescript
export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```
