### Title
Live re-fetch of mutable asset decimals in `pallet-hyper-fungible-token` lets an unprivileged asset owner inflate cross-chain transfer amounts - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` validates that a remote ERC20's decimals are `>=` the local asset's decimals exactly once, at `register_token`/`update_token` time, and permanently fixes the remote value into the `Precisions` storage map. The *local* side of the conversion, however, is never snapshotted: it is re-read live from `<T::Assets as fungibles::metadata::Inspect>::decimals(asset_id)` on every subsequent `send`, `on_accept`, and `on_timeout` call. Because a non-native asset's metadata decimals in `pallet-assets` can be changed at any time by that asset's own owner/admin (a capability inherent to being the creator of an arbitrary, permissionlessly-created asset — not a privileged, protocol-level `CreateOrigin`), the attacker can register a token at one decimal precision, get the invariant `config.decimals >= local_decimals` validated and a fixed `erc_decimals` cached, then silently shrink the local decimals afterward. Every later `convert_to_erc20`/`convert_to_balance` call now uses a stale, larger decimal delta, multiplying amounts by additional powers of 10, exactly mirroring the reported SPL `MintCloseAuthority`/`ld2sd_rate` bug pattern (mutable decimal property trusted post-hoc without re-validation or pinning).

### Finding Description
- `register_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:330-376`) computes `local_decimals` live from the asset's metadata, checks `config.decimals >= local_decimals` (line 353), and then writes only the *remote* `config.decimals` into `Precisions::<T>` (line 367). It never stores `local_decimals` anywhere.
- `send` (`lib.rs:241-325`) re-reads local decimals live at line 287-289 (`<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)`) and combines it with the frozen `erc_decimals` from `Precisions` to compute `convert_to_erc20(amount, erc_decimals, decimals)` (line 295), which multiplies by `10^(erc_decimals - decimals)` (`impls.rs:57-59`).
- `on_accept` (`module.rs:75-91`) and `on_timeout` (`module.rs:239-255`) do the symmetric thing with `convert_to_balance`, dividing by `10^(erc_decimals - decimals)`.
- The local `decimals` value is sourced from `fungibles::metadata::Inspect`, which for `pallet-assets` reflects the asset's mutable metadata record. That metadata's `decimals` field can be changed after asset creation by the asset's own owner/admin via `pallet-assets::set_metadata` — a capability scoped only to that specific asset the caller created (asset creation in `pallet-assets` is typically permissionless, gated only by a deposit), not by the hyper-fungible-token pallet's privileged `CreateOrigin`.
- Consequence: the invariant `erc_decimals >= local_decimals` that was checked once at `register_token` time is silently invalidated the moment the attacker lowers their own asset's decimals metadata. `Precisions` still holds the old, larger `erc_decimals`, so the decimal delta used in every subsequent `convert_to_erc20`/`convert_to_balance` call grows, and amounts are scaled up by an attacker-controlled additional power of 10 on outbound `send`, or scaled down (dust) on inbound `on_accept`/`on_timeout`, in either direction from what the registered configuration was meant to enforce.
- Existing guards do not stop this: there is no re-validation of `erc_decimals >= local_decimals` at `send`/`on_accept`/`on_timeout` time, and no snapshot of `local_decimals` is stored at registration to compare against later.

### Impact Explanation
This is a direct fund-amount manipulation on a live bridging pallet: a user who registers (or gets a privileged operator to register) their own non-native asset can burn a tiny amount of their local asset via `send` and cause the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint/release an amount inflated by orders of magnitude (each decimal of shrinkage multiplies the transferred amount by 10x), i.e. unauthorized creation of value / theft of bridge liquidity on the destination chain. It falls squarely under "transaction manipulation" and "stealing or loss of funds" for the live bridge runtime, and requires no relayer, prover, or governance compromise — only the standard, unprivileged capability of owning an asset one created in `pallet-assets`.

### Likelihood Explanation
Requires: (1) an attacker to have (or a permissive `CreateOrigin` to grant) a non-native asset registered through `register_token`, and (2) that the same account is the metadata owner/admin of that `pallet-assets` asset (satisfied by default since asset creation in `pallet-assets` is normally permissionless and the creator becomes owner/admin). No relayer collusion, no prover compromise, and no governance action is needed — only a standard `pallet-assets::set_metadata` call the attacker is already authorized to make on their own asset, followed by a normal `send`. This is realistically reachable and does not depend on any malicious third party.

### Recommendation
- At `register_token`/`update_token` time, snapshot `local_decimals` into a dedicated storage item (e.g. extend `Precisions` or add a `LocalDecimals` map) instead of re-deriving it live on every operation.
- In `send`, `on_accept`, and `on_timeout`, use the pinned `local_decimals` value rather than calling `fungibles::metadata::Inspect::decimals` live, or re-validate `erc_decimals >= live_local_decimals` on every call and reject the transfer if the invariant no longer holds.
- Alternatively, disallow registering assets whose decimals metadata can be mutated after registration by anyone other than the pallet's own `CreateOrigin` (e.g. require `pallet-assets` metadata to be locked/frozen for bridged assets before `register_token` succeeds).

### Proof of Concept
1. Attacker calls `pallet_assets::create` to mint asset `A` (permissionless, attacker becomes owner/admin) and `pallet_assets::set_metadata(A, decimals = 6)`.
2. A privileged `CreateOrigin` (e.g. governance or an ops multisig) calls `register_token` for asset `A`, registering EVM chain config with `decimals = 18`. Check `18 >= 6` passes; `Precisions[A][evm_chain] = 18` is stored permanently. `local_decimals` (6) is never stored.
3. Attacker calls `pallet_assets::set_metadata(A, decimals = 0)` on their own asset — a fully unprivileged, self-authorized action.
4. Attacker calls `send(asset_id = A, amount = 1, destination = evm_chain, ...)`. In `send` (`lib.rs:287-295`), `decimals` is now read live as `0`; `erc_decimals` is still `18`. `convert_to_erc20(1, 18, 0)` = `1 * 10^18`, so the `Message.amount` sent to the destination `HyperFungibleToken` contract is `1e18` instead of `1e12` (what the 6-decimal registration intended), inflating the amount released/minted on the destination chain by six orders of magnitude for burning a single raw unit locally. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
