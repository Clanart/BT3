### Title
`ReceivedOutput::read` uses a `BufReader` which consumes bytes belonging to subsequent stream items, corrupting/desynchronizing any reader holding multiple serialized outputs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The audit-report bug class is "the wrong variant of a shared utility was mixed into a system expecting a consistent set, causing collisions". The in-scope analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which wraps the caller's `&mut R` reader in a `BufReader` to decode the embedded `TxOut`/`OutPoint`. A `BufReader` reads ahead from the underlying reader into its internal buffer and discards it on drop, so the bytes it buffers (belonging to the *next* `ReceivedOutput` in the same stream) are silently consumed and lost.

### Finding Description
`ReceivedOutput` defines a self-delimiting serialization (`offset || TxOut || OutPoint`) via `write`/`serialize`, and `read` is the public inverse (part of the untrusted-bytes API surface):

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output =
      TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
    outpoint =
      OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

The intent is to prevent `consensus_decode` from over-consuming `r`. However, `BufReader` itself performs exactly that over-consumption: a `BufReader` always has a non-zero effective internal buffer (Rust's implementation enforces a minimum capacity, and `capacity 0` is rounded up to at least one byte / the implementation minimum), so its first `read` call pulls up-to-capacity bytes from `r` in one shot. `consensus_decode` consumes only the bytes it needs; the remainder sit in `buf_r`'s buffer and are dropped when `buf_r` goes out of scope — they are never returned to `r`.

Contrast with `write` (mod.rs:137-141), which emits exactly `offset || TxOut || OutPoint` with no padding. Any reader that holds a concatenation of `ReceivedOutput`s — e.g., a `Vec<ReceivedOutput>` decoded as `iter().map(|_| ReceivedOutput::read(&mut cursor))`, or a network/message-queue payload with an output followed by additional fields — is desynchronized after the first `read`: the second `read_F` is called at an offset `k` bytes past where it should be, where `k` is however many bytes the `BufReader` buffered beyond the `OutPoint`.

This is the "mixed variants cause collisions" pattern concretely: the write path assumes a byte-exact stream contract, while the read path silently swaps in a buffering variant that violates that contract.

### Impact Explanation
`ReceivedOutput` is what the `Scanner` produces for every deposit matched in a transaction (`scan_transaction`, mod.rs:199-214) and is the type fed into `SignableTransaction` to spend funds. If outputs are transported or persisted as serialized streams (the `read`/`write`/`serialize` trio exists precisely for that), then:

- Every `ReceivedOutput` after the first in a shared buffer fails to decode (`read_F` hits shifted bytes that are either non-canonical → error, or a valid-but-wrong scalar) or is silently assigned a different `offset`/`TxOut`/`OutPoint` than was serialized.
- A wrong `offset` makes the output unspendable: `SignableTransaction::multisig` (send.rs:273-285) requires `p2tr_script_buf(keys.offset(offset).group_key()) == prevout.script_pubkey`, so a shifted offset fails that check and the funds cannot be signed for.
- A wrong `TxOut`/`OutPoint` corrupts the sighash inputs (`Prevouts::All`, send.rs:375-390), so even if parsing "succeeds" the produced transaction is invalid.

An unprivileged party reaches this purely through bytes fed to the public `ReceivedOutput::read` API, which is expressly in scope. The result is deposits that were correctly scanned being reported as received yet unspendable/unreadable downstream — a liveness/funds-availability failure reachable via the documented deserialization API.

### Likelihood Explanation
Whether this triggers depends on the underlying `R`'s behavior: `BufReader` only over-consumes if `r` yields more bytes than requested in a single `read`. For in-memory `&[u8]`/`Cursor` readers and any reader returning full buffers, it triggers deterministically whenever more than one item is in the stream. For byte-at-a-time readers it may not trigger. Since `serialize` produces a flat `Vec<u8>` and the natural consumer is a slice/cursor decode, the common usage pattern hits it. It requires no malicious participant — a benign integrator parsing a concatenated stream triggers it — though it is also reachable when untrusted bytes are supplied to `read` and an error in a later element masks earlier corruption.

### Recommendation
Remove the `BufReader` wrapper and bound the decode differently — either decode `TxOut`/`OutPoint` directly from `r` (`consensus_decode` is already self-delimiting for these types), or if protection against over-read is required, use a non-buffering adapter such as `r.by_ref()` / a `Take`-style limited reader that never reads ahead. Alternatively, prefix the payload with explicit lengths and read exact-length slices before decoding.

### Proof of Concept
```rust
use std::io::Cursor;
use bitcoin::consensus::encode::serialize;
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, Txid, hashes::Hash};
use k256::Scalar;
use serai_bitcoin::wallet::ReceivedOutput;

// Build two outputs and serialize them into one stream
let o1 = ReceivedOutput /* construct via Scanner::scan_transaction or fields */;
let o2 = /* a second ReceivedOutput */;

let mut buf = o1.serialize();
buf.extend(o2.serialize());

let mut cur = Cursor::new(&buf);
let first = ReceivedOutput::read(&mut cur).unwrap(); // succeeds,
// but buf_r inside read() buffered bytes belonging to o2
let second = ReceivedOutput::read(&mut cur);         // Err: read_F starts mid-o2
```

Specifically: after the `OutPoint` of `o1` is consensus-decoded, `buf_r` has already consumed additional bytes of `o2`'s `offset` into its (non-zero) internal buffer. Those bytes are dropped with `buf_r`, so `Secp256k1::read_F(&mut cur)` for `o2` reads a shifted 32-byte window — either failing canonical decoding or yielding a wrong scalar. The same desync applies to any trailing field placed after a `ReceivedOutput` in a shared encoding.

Caveat: I could not enumerate every call site of `ReceivedOutput::read` in this snapshot (processor/wallet code paths outside `networks/bitcoin/src`), so the precise production caller that streams multiple outputs is unverified; the defect itself is fully contained in `read` and is independent of the caller.
