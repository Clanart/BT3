## Finding

**Valid vulnerability.** The pallet does not snapshot the local asset's decimals at `register_token` time — it re-reads `pallet-assets` metadata live on every `send`/`on_accept`/`on_timeout` call, while the ERC20-side decimals (`Precisions`) are fixed once at registration. This decouples the two halves of the scaling ratio, and only one half is committed to storage.

### Title
Live re-read of mutable `Assets::decimals()` combined with fixed `Precisions` allows an asset owner to inflate minted amounts on `on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token` validates `config.decimals >= local_decimals` once, and permanently stores only the remote/ERC20 decimals in `Precisions::<T>` [1](#0-0) . It never snapshots `local_decimals` itself. Every later boundary operation (`send`, `on_accept`, `on_timeout`) instead calls `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(local_asset_id)` live [2](#0-1) . For a `pallet-assets` asset created permissionlessly via `create`, the asset's `Owner` can call the standard `set_metadata` extrinsic to change `decimals` at any time after `register_token` runs, since nothing in this pallet freezes or locks that metadata.

`convert_to_balance` then divides the incoming raw ERC20 `U256` amount by `10^(erc_decimals.saturating_sub(local_decimals))` [3](#0-2) . If the owner raises `local_decimals` closer to (or equal to) the fixed `erc_decimals` after registration, this exponent shrinks, the divisor shrinks, and the same fixed on-chain `Message.amount` mints a proportionally larger local balance via `Assets::mint_into` in the non-native branch of `on_accept` [4](#0-3) .

### Impact
This breaks the invariant that a fixed escrowed/burned amount on the source chain must map deterministically to the same local balance on the destination chain. By inflating the local decimal count after registration, the attacker (as the unprivileged owner of their own registered asset) can mint an inflated local balance relative to what was actually escrowed/burned on the EVM side for the same message, causing loss of backing for the bridged asset — a direct "loss of funds"/wrongful-amount outcome per the bounty's impact gate.

### Likelihood
Requires: (1) an asset created via `pallet-assets::create` (permissionless) and later approved/registered via `register_token` (a `CreateOrigin`-gated action, but the registration is legitimate — it's the metadata mutation afterwards that's unprivileged and unguarded); (2) the same account remains (or the asset's `Owner`/`Issuer` role remains) able to call `set_metadata`; (3) a genuine relayed message arrives via `on_accept` after the decimals change. No compromised infra or malicious relayer is required — the only privileged step (registration) behaves exactly as documented, and the exploit is purely the omission of a decimals snapshot/lock afterward.

### Recommendation
Store `local_decimals` in a pallet-owned map at `register_token` time (in addition to or instead of relying on live `Assets::decimals()`), and use that frozen value in `send`/`on_accept`/`on_timeout` conversions. Alternatively/additionally, call `pallet-assets::freeze_metadata` (or equivalent) for any asset accepted into `register_token`/`update_token`, and re-validate `config.decimals >= local_decimals` on every conversion path, not just at registration.

### Proof of Concept
1. Attacker creates a permissionless asset via `pallet-assets::create`, sets `decimals = 6` via `set_metadata`.
2. Governance/`CreateOrigin` calls `register_token` with `native = false`, `chains[chain].decimals = 18` — `Precisions::<T>::get(asset, chain) == 18` is now fixed.
3. Attacker calls `set_metadata` again to raise the asset's on-chain decimals to `18` (permissionless — they are the asset `Owner`).
4. Attacker sends (or gets sent) a genuine cross-chain message with a fixed `Message.amount` (e.g. `1_000_000_000_000_000_000` raw units, corresponding to 1 unit at 18 decimals as escrowed/burned on the source chain).
5. `on_accept` computes `decimals = 18` (live read), `erc_decimals = 18` (fixed), divisor `= 10^0 = 1`, and mints `1_000_000_000_000_000_000` local units instead of the `1_000_000` units (at the originally intended 6-decimal scale) that would have been minted had decimals not changed — a 10^12x inflation of minted balance for the same backed amount. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
