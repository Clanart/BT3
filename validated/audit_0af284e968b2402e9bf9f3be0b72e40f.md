## Title
Deep-link branch parameter bypasses dash-prefix filtering and reaches `git checkout` as an unescaped positional argument, enabling Git argument injection - (File: `app/src/lib/parse-app-url.ts`)

## Summary
The external report's broken invariant is: a value that is supposed to protect the user (`_minReturnedTokens`) is validated by one code path but silently defeated because a different, conflicting code path is chosen at execution time, and the guard never actually gets enforced. The GitHub Desktop analog is a validation/sanitization mismatch: two different functions are used to vet the same class of untrusted input (a Git ref name) — one (`sanitizedRefName`) actively strips a dangerous leading `-`/`+` prefix, while the other (`testForInvalidChars`), which is the one actually used to gate attacker-controlled deep-link input, does **not** check for a leading dash at all. The unguarded value then flows straight into a `git checkout` invocation as a positional argument placed *before* the `--` end-of-options marker, which does not protect against option parsing of a preceding token.

## Finding Description
`parseAppURL()` handles the `x-github-client://openRepo/...` protocol handler (and other product-specific url schemes) that GitHub.com's "Open in Desktop" button, and any web page or email, can invoke without any user privilege check: [1](#0-0) 

The only check applied to the `branch` query parameter is `testForInvalidChars`, defined here: [2](#0-1) 

Note that `invalidCharacterRegex` rejects control characters, `~^:?*[\|"<>`, `@{`, consecutive dots, a leading/trailing dot, `.lock` suffix, and a trailing `/` — but it never rejects a **leading dash**. Compare this to the sibling function `sanitizedRefName` in the very same file, which explicitly strips a leading `-`/`+` (`.replace(/^[-\+]*/g, '')`) precisely because Git will interpret an argument starting with `-` as an option rather than a ref name. This is confirmed by the unit tests: [3](#0-2) 

So the codebase clearly *knows* that a leading dash must be neutralized in ref names, but the function actually used to gate the deep-link `branch` parameter (`testForInvalidChars`) omits that check. A branch value such as `--orphan=x` or any other single/double-dash-prefixed string passes `parseAppURL` validation unmodified and becomes part of the returned `IOpenRepositoryFromURLAction`.

That action is dispatched to `openRepositoryFromUrl`, which — when a `branch` (and no `pr`) is present — calls `openBranchNameFromUrl(url, branch)`: [4](#0-3) 

`openBranchNameFromUrl` ultimately calls `checkoutLocalBranch(repository, branchName)`, which resolves into `checkoutBranch()` in `app/src/lib/git/checkout.ts`. That function builds the Git command line as: [5](#0-4) [6](#0-5) 

The resulting argv is `['checkout', <branch.name>, '--']` (or with `-b <name>` inserted for remote branches). The `branch.name` token is placed **before** the `--` end-of-options marker, so if it begins with `-`, Git will parse it as an option/flag rather than a ref name — the `--` that follows does not retroactively protect the preceding argument. This is the classic Git "argument injection via ref/file name" class of bug (the same class Git itself defends against internally via `check_ref_format` refusing refs that start with `-`, but that server-side check is irrelevant here because Desktop is passing the value directly to its own local `git checkout` invocation before any such enforcement by a remote).

## Impact Explanation
This satisfies the accepted impact categories: the attacker only needs to control a link/deep link that the user clicks (no local/physical access, no leaked credentials, no admin rights). Depending on which Git checkout option gets smuggled in, the result ranges from unexpected/forced repository state changes (e.g., `--orphan=<name>` silently creates and switches to a disconnected branch, `-b`/`-B` force-creates or resets a branch to an attacker-chosen name) to more severe corruption of the user's working tree/index depending on which `git checkout` options are reachable. This is a corruption-of-committed-state class of bug in the same spirit as the original finding — a value the user reasonably expects to be a validated ref name is instead used to smuggle unintended Git behavior because the validation function that's actually wired into the deep-link path is weaker than the sanitizer that exists elsewhere in the same module.

## Likelihood Explanation
Likelihood is meaningful: deep links of the form `x-github-client://openRepo/<url>?branch=<value>` are handled unconditionally by `handleAppURL`/`parseAppURL` in the main process without any user confirmation dialog showing the raw branch value, and the flow is reachable from any web page, README link, or email a victim clicks while GitHub Desktop is installed. The only friction is that `pr` is not set (so the stricter `pr/\d+` branch regex doesn't apply) and the `branch` value must avoid the explicitly blocked characters, which a `-`-prefixed option string like `--orphan=pwn` trivially does.

## Recommendation
Use the same sanitization discipline in `parseAppURL` as the codebase already applies elsewhere: reject (or sanitize) `branch` values that begin with `-`/`+`, mirroring `sanitizedRefName`'s existing behavior, or centralize on a single validating function used both for UI ref-name entry and for deep-link/CLI-sourced ref names. Additionally, harden `getBranchCheckoutArgs`/`checkoutBranch` defensively by always prefixing the ref argument with `--` immediately before it (`git checkout -- <branchOrArgs...>` is not valid syntax for checkout with `-b`, so at minimum validate/reject any ref argument starting with `-` before it reaches `git()`).

## Proof of Concept
1. Host or send a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--orphan%3Dpwned`
2. Victim (with GitHub Desktop installed) clicks the link.
3. `parseAppURL` accepts `branch = "--orphan=pwned"` because `testForInvalidChars` does not reject a leading `-`.
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch` → `checkoutBranch` runs `git(['checkout', '--orphan=pwned', '--'], ...)`, i.e., an attacker-influenced flag is passed to the local `git checkout` invocation instead of being treated as a literal branch name.

I was not able to execute this in a live build to observe the exact process behavior for every possible injected flag (e.g., which specific `git checkout` options are most damaging beyond `--orphan`/`-b`), since I only have static code access here — a background Devin session with a runnable checkout of the repo could confirm the exact blast radius by fuzzing the `branch` parameter against `checkoutBranch`.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,

  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(

    title,
    branch.name,
