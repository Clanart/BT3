### Title
Tokenfactory denom admin can add itself/counterparty to a `DenomAllowList` after the fact to permanently brick native ERC20-pointer transfers, freezing counterparty funds - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
The `Cooler.sol` report describes a lender deliberately getting itself blacklisted on the debt token so that `debt.transferFrom(msg.sender, loan.lender, repaid)` always reverts, permanently blocking repayment and forcing the counterparty into default/loss. Sei's analog is the tokenfactory `DenomAllowList` feature enforced inside `bank.SendCoins`, combined with the "native" ERC20 pointer contract `NativeSeiTokensERC20.sol` that hard-reverts the *entire* EVM `transfer`/`transferFrom` call whenever the underlying `MsgSend` fails.

### Finding Description
Any account can permissionlessly create a tokenfactory denom and becomes its admin (`x/tokenfactory`), then call `MsgUpdateDenom` to set a `DenomAllowList` on that denom at any time [1](#0-0) . Once an allow list exists for a `factory/...` denom, `bank.SendCoins` enforces it for both sender and receiver via `IsInDenomAllowList`, rejecting the transfer with `"is not allowed to receive funds"` / `"is not allowed to send funds"` for any address not on the list [2](#0-1) , as demonstrated in `TestSendReceiverNotInAllowList` [3](#0-2) .

Every bank denom (including tokenfactory denoms) can have a "native" ERC20 pointer contract deployed for it via the `pointer` precompile's `AddNative`, which deploys the bytecode embedded from `NativeSeiTokensERC20.sol` and registers it as the canonical ERC20 wrapper for that denom [4](#0-3) . This contract's `_update` (the OpenZeppelin ERC20 internal transfer hook used for `transfer`/`transferFrom`/`mint`/`burn`) calls the bank precompile's `send` and **requires** success or reverts the whole EVM call:
```solidity
function _update(address from, address to, uint256 value) internal override {
    bool success = BankPrecompile.send(from, to, denom, value);
    require(success, "NativeSeiTokensERC20: transfer failed");
    emit Transfer(from, to, value);
}
``` [5](#0-4) 

The bank precompile's `send` method forwards straight to `bankMsgServer.Send`/`SendCoins` [6](#0-5) , so any allow-list rejection from `SendCoins` propagates as a permanent EVM revert on that ERC20 pointer for that denom, for **any address excluded from the allow list**, on both incoming and outgoing legs.

This mirrors the Cooler bug class exactly: a party who controls (or colludes with the controller of) the token's transfer eligibility can, after entering into an on-chain agreement (loan, escrow, vesting stream, DEX position, etc.) denominated in a tokenfactory-backed native ERC20 pointer, unilaterally call `MsgUpdateDenom` to add an allow list that excludes the counterparty's address (or excludes their own address to block being repaid/refunded). Any future protocol logic built on `IERC20.transfer`/`transferFrom` for that pointer (e.g. a lending contract analogous to `Cooler.sol`, but built on Sei using the native ERC20 pointer as the debt token) will permanently revert for the excluded address, exactly as in the original report.

### Impact Explanation
Because `require(success, ...)` in `_update` causes any denied `SendCoins` call to hard-revert the ERC20 transfer, a counterparty relying on token transferability (e.g., to receive a scheduled repayment, refund, or liquidation payout denominated in a tokenfactory native-pointer token) can be permanently frozen out of receiving or returning funds once the denom admin (who could be the "lender"/counterparty analog in a lending flow) sets an allow list excluding the victim's address. This is a concrete, permanent fund-freezing/loss vector reachable purely through standard tokenfactory messages (`MsgCreateDenom`, `MsgUpdateDenom`) and standard ERC20 pointer calls — no privileged/validator access required.

### Likelihood Explanation
`MsgCreateDenom` is fully permissionless, and `MsgUpdateDenom`/allow-list changes are available to any unprivileged denom admin at any time after the denom has already been used as collateral/debt in ERC20-pointer-integrated contracts [7](#0-6) . There is no timelock or restriction preventing an admin from adding an allow list retroactively to a denom that is already circulating and integrated with third-party contracts through its native ERC20 pointer, making the attack straightforward to execute with a single transaction once a victim's dependency on transfers of that denom is established.

### Recommendation
- Do not allow `SetDenomAllowList`/`MsgUpdateDenom` to silently break transfers for addresses that already hold balances or have outstanding obligations denominated in a pointer-wrapped token; consider grandfathering existing holders or requiring allow-list changes to only restrict *future* transfers, not existing counterparties.
- In `NativeSeiTokensERC20.sol`, avoid a blanket `require(success)` that reverts the entire transfer; instead surface the bank-level failure reason distinctly and consider an escrow/pull-payment fallback pattern (similar to the report's own recommendation) for any downstream lending/vesting logic built atop the pointer, so a single denied recipient cannot indefinitely lock funds meant for others.
- Document prominently for integrators that tokenfactory denoms (and their native ERC20 pointers) can have admin-mutable allow lists, so protocols should not treat such denoms as unconditionally transferable collateral/debt assets without accounting for this risk.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/<attacker>/loan` and becomes its admin [8](#0-7) .
2. Attacker mints the denom and uses the `pointer` precompile `addNativePointer(denom)` to deploy a `NativeSeiTokensERC20` ERC20 wrapper for `factory/<attacker>/loan` [4](#0-3) .
3. Attacker (as "lender") lends this token via a lending contract built on the ERC20 pointer interface, receiving collateral from a borrower who owes repayment in the pointer token.
4. Before/at the point repayment is due, attacker calls `MsgUpdateDenom` on `factory/<attacker>/loan`, setting a `DenomAllowList` that excludes the attacker's own address (or includes only addresses that exclude the borrower's payment path) [9](#0-8) .
5. Any subsequent `transfer`/`transferFrom` call on the ERC20 pointer targeting or from the now-excluded address fails `SendCoins`'s allow-list check and the ERC20 `_update` hook reverts with `"NativeSeiTokensERC20: transfer failed"` [5](#0-4) , permanently preventing repayment and forcing the borrower into default, exactly mirroring the original Cooler exploit.

func (k BaseSendKeeper) SetDenomAllowList(ctx sdk.Context, denom string, allowList types.AllowList) {
	store := ctx.KVStore(k.storeKey)
	denomAllowListStore := prefix.NewStore(store, types.DenomAllowListKey(denom))

	m := k.cdc.MustMarshal(&allowList)
	denomAllowListStore.Set([]byte(denom), m)
}

func (k BaseSendKeeper) GetDenomAllowList(ctx sdk.Context, denom string) types.AllowList {
	store := ctx.KVStore(k.storeKey)
	store = prefix.NewStore(store, types.DenomAllowListKey(denom))

	bz := store.Get([]byte(denom))
	if bz == nil {
		return types.AllowList{}
	}

	var allowList types.AllowList
	k.cdc.MustUnmarshal(bz, &allowList)

	return allowList
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, suppliedGas uint64, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	existingAddr, existingVersion, exists := p.evmKeeper.GetERC20NativePointer(ctx, token)
	if exists && existingVersion >= 1 {
		return nil, 0, fmt.Errorf("pointer at %s with version %d exists when trying to set pointer for version %d", existingAddr.Hex(), existingVersion, native.CurrentVersion)
	}
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	constructorArguments := []interface{}{
		token, name, symbol, decimals,
	}

	packedArgs, err := native.GetParsedABI().Pack("", constructorArguments...)
	if err != nil {
		panic(err)
	}
	bin := append(native.GetBin(), packedArgs...)
	if value == nil {
		value = utils.Big0
	}
	ret, contractAddr, remainingGas, err := evm.Create(caller, bin, suppliedGas, uint256.MustFromBig(value))
	if err != nil {
		return
	}
	err = p.evmKeeper.SetERC20NativePointer(ctx, token, contractAddr)
	if err != nil {
		return
	}

	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypePointerRegistered, sdk.NewAttribute(types.AttributeKeyPointerType, "native"),
		sdk.NewAttribute(types.AttributeKeyPointerAddress, contractAddr.Hex()), sdk.NewAttribute(types.AttributeKeyPointee, token),
		sdk.NewAttribute(types.AttributeKeyPointerVersion, fmt.Sprintf("%d", native.CurrentVersion))))
	ret, err = method.Outputs.Pack(contractAddr)
	return
}

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.
```

  denom `factory/{creator address}/{subdenom}`. Admin is automatically set as the
  Msg sender.
- Add denom to the `CreatorPrefixStore`, where a state of denoms created per
  creator is kept.
