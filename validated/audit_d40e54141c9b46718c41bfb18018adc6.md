### Title
Liquidation reverts via `unwrap-panic` on stale/failed price for disabled collateral, blocking liquidation and enabling bad-debt accrual - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The C4 finding describes AxelarGateway's `_mintToken`, which reverts the whole cross-chain transfer when a sub-call (`_callERC20Token`/`transfer`) fails, causing the user to lose funds instead of degrading gracefully. In Zest's `v0-4-market.clar`, the liquidation path has an analogous "hard revert instead of graceful handling" pattern: when a borrower's collateral asset is disabled (not present in the pre-resolved `assets` list), `process-collateral-asset` fetches its price with `unwrap-panic` rather than a recoverable error path. If that on-demand `price-resolve` call fails (oracle down, or staleness/confidence check fails — exactly the kind of gating this ruleset calls out), the entire `liquidate` transaction panics and reverts, rather than allowing liquidation to proceed or fail gracefully.

### Finding Description
`process-collateral-asset` resolves price for the collateral being liquidated. When the asset is *not* found in the already-priced `assets` list (i.e., it is a disabled collateral), it performs an on-demand oracle read and unconditionally unwraps it with `unwrap-panic`: [1](#0-0) 

That call goes through `price-resolve`, which enforces both a positivity check and a staleness/monotonicity check (`oracle-timestamp-fresh`) against a per-asset `max-staleness` before returning a price — any violation returns an `err`, not a price: [2](#0-1) 

Because the liquidation code path wraps this call in `unwrap-panic` (as opposed to `unwrap!`/`try!` with a typed error, as is done elsewhere, e.g. in `collateral-remove`'s disabled-collateral branch which uses `ERR-DISABLED-COLLATERAL-PRICE-FAILED`): [3](#0-2) 

...any transient oracle failure (staleness threshold exceeded, Pyth/DIA call error, confidence-ratio rejection) for a *disabled* collateral asset causes the whole `liquidate` call to abort with a runtime panic. This is precisely the AxelarGateway pattern: a sub-call failure (price fetch) that should be handled gracefully instead reverts the entire top-level operation, and it disproportionately affects the exact scenario where the asset was disabled — often because its price feed became unreliable in the first place, meaning this exact code path is more likely to be triggered when it matters most.

### Impact Explanation
This directly produces a wrong health/liquidation verdict by omission: instead of computing "unhealthy → liquidatable" or gracefully rejecting with a typed error that a keeper could retry/route around, the protocol is left unable to execute `liquidate()` at all for any borrower holding disabled collateral whose oracle is stale or erroring. Bad debt on that position can accrue unchecked while it cannot be liquidated, which is a temporary freezing of the liquidation mechanism and a path toward protocol insolvency if the position continues to deteriorate — squarely in the in-scope "Temporary freezing of funds" / "protocol insolvency" category.

### Likelihood Explanation
Disabled collateral is, by definition, more likely to have a problematic/paused oracle (that's often *why* it was disabled), so hitting a failing `price-resolve` in exactly this code path is realistic. Any liquidator attempting to liquidate a mixed position (enabled + disabled collateral) during a period of feed staleness for the disabled asset will always panic-revert, with no fallback.

### Recommendation
Replace `unwrap-panic` in `process-collateral-asset`'s disabled-collateral branch with a typed error (`unwrap!` / `try!`) that propagates a specific error code (mirroring `ERR-DISABLED-COLLATERAL-PRICE-FAILED` used in `collateral-remove`), and consider allowing liquidation of the remaining priceable collateral/debt to proceed rather than failing the entire transaction when a single disabled asset's price is unavailable.

### Proof of Concept
1. Register a collateral asset, then disable it in the asset registry (removed from the enabled bitmap) after its Pyth/DIA feed becomes stale or the confidence check begins failing.
2. A borrower holds this disabled asset as collateral alongside other debt/collateral, and their position becomes unhealthy.
3. A liquidator calls `liquidate(...)` against `debt-ft`/`collateral-ft` where `collateral-ft` corresponds to the disabled asset.
4. `process-collateral-asset` is invoked with `coll-asset` = the disabled asset; since it is absent from the `assets` (pre-priced/enabled) list, the code calls `(unwrap-panic (price-resolve oracle-data))`.
5. `price-resolve`'s staleness/positivity assertion fails and returns `(err ...)`; `unwrap-panic` on an `err` causes a runtime panic, aborting the entire `liquidate` call — no liquidation occurs, and the unhealthy position remains open, accruing more bad debt.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
