## Analysis

The Badger vulnerability's broken invariant: a "vest" state object (`lockedAmounts`, `claimedAmounts`, `unlockBegin`/`unlockEnd`) is re-initialized for a *new* operation while a derived accounting field (`claimedAmounts`) from a *previous* operation is silently carried over, causing incorrect computation against the new timeline.

GitHub Desktop's `updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` has the same shape of bug: when a conflict of the same *kind* (`merge` or `rebase`) is detected, the store carries over `manualResolutions` from the *previous* conflict state into the *new* one without verifying it's actually the same operation instance. [1](#0-0) 

Specifically:
- `manualResolutions` is taken from `prevConflictState.manualResolutions` whenever `prevConflictState !== null`, regardless of whether the new conflict is the *same* rebase/merge [2](#0-1) .
- The "same operation" grouping check only tests conflict *kind* (`isMergeConflictState`/`isRebaseConflictState`), not identity of the operation (`originalBranchTip`, `targetBranch`, `baseBranchTip`) [3](#0-2) .
- `performEffectsForRebaseStateChange`/`performEffectsForMergeStateChange` only use branch-name/tip changes to fire *telemetry* counters (`rebaseAbortedAfterConflictsCount`, etc.) — they do **not** clear `manualResolutions` when the identity changes [4](#0-3) .

This means: if a user aborts a rebase/merge (or the operation is externally reset, e.g. by a malicious pre-checkout/post-checkout hook shipped in a cloned/fetched repository, or by rapid app-store polling racing a repository swap) and a **new** rebase/merge against a completely different branch/tip starts while `conflictState` transitions merge→merge or rebase→rebase, the old `manualResolutions` map (keyed by file path, e.g. `"theirs"`/`"ours"`) is reused for the new conflict. Files with the same path in the new, unrelated conflict inherit a stale resolution choice from the previous conflict and can be silently marked "resolved" (`getConflictedFiles` filters out paths present in `manualResolutions`) even though their content was never inspected in the new context [5](#0-4) .

The existing tests confirm this is intentional "preserve resolutions" behavior across state churn, without any check on whether it's truly a continuation of the same rebase [6](#0-5) .

### Why guards don't stop it
`_updateManualConflictResolution` and `updateMultiCommitOperationStateAfterManualResolution` only append/remove single entries from the map on user interaction — they never purge it wholesale when a brand-new conflict of the same kind starts [7](#0-6) . The only clearing path is a full kind transition (merge↔rebase) or `conflictState === null`, which isn't hit for same-kind consecutive operations.

### Uncertainty
I could not fully trace the exact caller sequence (`app-store.ts` status-refresh loop / `initializeMultiCommitOperationIfConflictsFound`) that would produce two *distinct* rebase/merge operations without an intervening `conflictState === null` refresh in between, which is required for `manualResolutions` to actually leak into a second, unrelated conflict — the index does not show the full polling/refresh cadence code, so whether a race window realistically exists (vs. status refresh always observing `conflictState === null` between operations) is not certain from available code. Confirming exploitability would require running the app and testing rapid abort → re-conflict sequences, which is not verifiable through static search alone.

### Recommendation
`updateConflictState` should compare operation identity (e.g. `originalBranchTip`/`targetBranch` for rebase, `currentBranch`/`currentTip` for merge) between `prevConflictState` and the new status, and reset `manualResolutions` to an empty map whenever the identity differs, mirroring the report's fix of resetting `claimedAmounts` when the vest timeline changes.

Given the residual uncertainty about whether the intervening `conflictState === null` transition always occurs in practice (which would make this unreachable), I present this as the closest structural analog found in local code rather than a fully confirmed exploitable path.

function performEffectsForRebaseStateChange(
  prevConflictState: RebaseConflictState | null,
  newConflictState: RebaseConflictState | null,
  status: IStatusResult,
  statsStore: IStatsStore
) {
  const previousBranchName =
    prevConflictState != null ? prevConflictState.targetBranch : null
  const currentBranchName =
    newConflictState != null ? newConflictState.targetBranch : null

  const branchNameChanged =
    previousBranchName != null &&
    currentBranchName != null &&
    previousBranchName !== currentBranchName

  // The branch name has changed while remaining conflicted -> the rebase must have been aborted
  if (branchNameChanged) {
    statsStore.increment('rebaseAbortedAfterConflictsCount')
    return
  }

  const { currentTip, currentBranch } = status

  // if the repository is no longer conflicted, what do we think happened?
  if (
    prevConflictState != null &&
    newConflictState == null &&
    currentTip != null &&
    currentBranch != null
  ) {
    const previousTip = prevConflictState.originalBranchTip

    const previousTipChanged =
      previousTip !== currentTip &&
      currentBranch === prevConflictState.targetBranch

    if (!previousTipChanged) {
      statsStore.increment('rebaseAbortedAfterConflictsCount')
    }
  }

  return
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  public _updateManualConflictResolution(
    repository: Repository,
    path: string,
    manualResolution: ManualConflictResolution | null
  ) {
    this.repositoryStateCache.updateChangesState(repository, state => {
      const { conflictState } = state

      if (conflictState === null) {
        // not currently in a conflict, whatever
        return { conflictState }
      }

      const updatedManualResolutions = new Map(conflictState.manualResolutions)

      if (manualResolution !== null) {
        updatedManualResolutions.set(path, manualResolution)
      } else {
        updatedManualResolutions.delete(path)
      }

      return {
        conflictState: {
          ...conflictState,
          manualResolutions: updatedManualResolutions,
        },
      }
    })

    this.updateMultiCommitOperationStateAfterManualResolution(repository)

    this.emitUpdate()
  }
