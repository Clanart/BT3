### Title
FROST preprocess seed copied out of `Zeroizing` wrapper into unprotected stack memory, duplicating key-equivalent material to RAM - ([File: crypto/frost/src/sign.rs](crypto/frost/src/sign.rs))

### Summary
CVE-2023-32099 describes key material being duplicated to RAM because a buffer-clearing step was ineffective. The analogous defect in Serai is not a missing `zeroize()` call but a copy of a secret that escapes the `Zeroizing` wrapper entirely: `AlgorithmMachine::seeded_preprocess` dereferences `CachedPreprocess`'s `Zeroizing<[u8; 32]>` into a plain `[u8; 32]` passed by value to `ChaCha20Rng::from_seed`. That seed is documented to be as sensitive as the private key share itself, yet the by-value copy (and the ChaCha20Rng state derived from it) is never zeroized.

### Finding Description
`preprocess` fills a `CachedPreprocess` (a `Zeroizing<[u8; 32]>`) with RNG output and hands it to `seeded_preprocess` [1](#0-0) . Inside `seeded_preprocess`, the seed is copied out of the `Zeroizing` wrapper by value:

```rust
let mut rng = ChaCha20Rng::from_seed(*seed.0);
``` [2](#0-1) 

`*seed.0` produces a plain `[u8; 32]` on the stack / in an argument slot. Neither this copy nor the `ChaCha20Rng` internal state (which is deterministically derived from the seed) is ever cleared; only the `Zeroizing`-wrapped original in `CachedPreprocess` is scrubbed on drop. The crate itself documents that this seed is key-equivalent: "this MUST be handled with the same security as your private key share, as knowledge of it also enables recovery" [3](#0-2) , and `cache`/`from_cache` repeat that third-party recovery of a cached preprocess "enables recovery of your private key share" [4](#0-3) .

The same pattern occurs wherever the seed is materialized as raw bytes: `seeded_preprocess` is invoked both from `preprocess` and from `from_cache` [5](#0-4) , so every signing session — whether online or from a cached preprocess — leaves at least one un-zeroized copy of the key-equivalent seed in RAM (the `from_seed` argument plus the live `ChaCha20Rng` struct, which retains its key state and is dropped without wiping).

### Impact Explanation
An attacker (or forensic process) able to read process memory after a signing session can recover the preprocess seed from the uncleared copy. The seed deterministically regenerates the FROST nonces via `ChaCha20Rng::from_seed` → `Commitments::new` → `Curve::random_nonce` [6](#0-5) . With the nonces and the public signature share (`z_i = d_i + e_i·ρ_i + λ_i·s_i·c`), the victim's private key share is recovered algebraically — full key-share disclosure from passive memory contents, matching the "key material duplication to RAM" class of CVE-2023-32099.

### Likelihood Explanation
Exploitation requires memory disclosure on the signing host (e.g., core dump, swap, hibernation image, a co-resident read primitive, or a subsequent memory-corruption bug) — the same precondition assumed by CVE-2023-32099 (CVSS 5.3, confidentiality-only). It is not reachable purely through protocol messages, which caps severity at Medium; but the leak persists for the lifetime of the stale stack/heap pages, and it affects every FROST signing path because `seeded_preprocess` is the single nonce-generation entry point.

### Recommendation
Avoid producing an unprotected copy of the seed: change `seeded_preprocess` to construct the RNG without dereferencing out of `Zeroizing` — e.g., keep the seed borrowed and pass it through a `Zeroizing<[u8; 32]>` temporary, or wrap the `ChaCha20Rng` in `Zeroizing`/`Drop`-zeroizing glue so its key state is wiped after `Commitments::new` and `preprocess_addendum` consume it. Concretely:

```rust
let rng = Zeroizing::new(ChaCha20Rng::from_seed(**seed.deref())); // still copies once;
// better: implement/use a from_seed taking &mut Zeroizing<[u8;32]> that zeroizes
// its internal copy, and wrap `rng` in Zeroizing so the cipher state is wiped.
```

At minimum, wrap `rng` in `Zeroizing` so the ChaCha20 key state is scrubbed when `seeded_preprocess` returns, and zeroize the temporary `[u8; 32]` argument copy.

### Proof of Concept
```rust
// crypto/frost/src/sign.rs
fn seeded_preprocess(self, seed: CachedPreprocess) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
  let mut params = self.params;
  // BUG: *seed.0 copies the key-equivalent seed into a plain [u8;32] on the stack.
  // That copy and the resulting ChaCha20Rng key state are never zeroized.
  let mut rng = ChaCha20Rng::from_seed(*seed.0);
  let (nonces, commitments) = Commitments::new::<_>(
    &mut rng,
    params.keys.original_secret_share(),
    &params.algorithm.nonces(),
  );
  ...
}
```

1. Run any `AlgorithmMachine::preprocess`/`from_cache` signing session.
2. Inspect process memory (e.g., via `/proc/<pid>/mem` snapshot or a core dump captured after `seeded_preprocess` returns).
3. Locate the 32-byte seed value (identifiable as the `CachedPreprocess` contents or the `ChaCha20Rng` state) outside any `Zeroizing`-protected region.
4. Rebuild `ChaCha20Rng::from_seed(seed)`, call `Commitments::new(&mut rng, secret_share, nonces)` to regenerate the victim's nonces `d_i, e_i`.
5. Given the observed signature share `z_i` and public `ρ_i`, `λ_i`, challenge `c`: `s_i = (z_i − d_i − e_i·ρ_i) / (λ_i·c)` — the private key share is recovered, confirming key-material duplication to RAM.
