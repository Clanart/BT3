## Summary

The Velodrome bug is a **"two independent one-time actions on the same underlying value, neither aware of the other's finalization"** pattern: Alice's managed-NFT vote and Bob's withdrawn-NFT vote both succeed because each is gated only by its own per-tokenId `lastVoted` flag, not by a check that the *combined* voting power was already spent once. The same structural gap exists in `IntentGatewayV2`'s cross-chain intent settlement: **fill** and **cancel-from-destination** are two independent finalization paths for the same order `commitment`, each dispatching a settlement message to the source chain, and neither checks whether the *other* path already finalized the order before firing.

### Title
Fill and cancel-from-destination can both finalize the same order commitment, causing wrong-beneficiary escrow settlement and solver fund loss - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Finding Description
`_fillCrossChain` (line 89) sets `_filled[commitment] = msg.sender` (the solver), delivers output tokens to the beneficiary, and dispatches a `RedeemEscrow` `PostRequest` to the source chain [1](#0-0) .

`_cancelFromDest` (line 240) is reachable by **anyone after `order.deadline`** — it only checks the caller when the deadline has not yet passed (`order.deadline >= _blockNumber()`), and it unconditionally overwrites `_filled[commitment] = order.user`, then dispatches a `RefundEscrow` `PostRequest` to the source chain: [2](#0-1) 

Crucially, `_cancelFromDest` never checks whether `_filled[commitment]` was already set by a prior fill — there is no `if (_filled[commitment] != address(0)) revert Filled();` guard analogous to the one enforced in `fillOrder` (`IntentGatewayV2.sol` line 426, `if (_filled[commitment] != address(0)) revert Filled();`). So a solver's completed fill (which already delivered real output tokens to the beneficiary) does not block a subsequent cancel-from-destination call from also firing a `RefundEscrow` for the same commitment.

On the source chain, `_withdraw` (called from both `RedeemEscrow` and `RefundEscrow` `onAccept` branches, and from `onGetResponse`) has no ordering/idempotency check tying `finalize` to which message kind arrived first — it just decrements `_orders[commitment][token]` and pays whichever beneficiary the current message specifies: [3](#0-2) 

Because `RedeemEscrow` and `RefundEscrow` are independent ISMP posts from the destination chain with no dispatch-order guarantee, whichever one is *delivered and relayed to the source chain first* wins the payout of the escrowed input tokens, and the second one lands on an already-zeroed `_orders[commitment][token]` and reverts with `UnknownOrder`. If `RefundEscrow` (post-deadline cancel) is delivered before the earlier-in-wall-clock-time `RedeemEscrow` (post-fill), the escrow goes to the **user**, even though the **solver already irreversibly gave the user the requested output tokens on the destination chain**. This is the direct analog of Alice's and Bob's independent one-time actions each firing successfully against the same underlying value — here it's "fill" and "cancel" both being independently authorized state transitions on the same `commitment`, guarded on the destination side only by non-overlapping local checks (`fillOrder` checks `_filled==0`; `_cancelFromDest` does not).

### Impact Explanation
This directly matches the bounty's "wrong beneficiary or amount" and "logic attack / double-settlement" categories:
- The solver delivers real value (output tokens) on the destination chain but never receives the escrowed input tokens — the escrow is instead paid to the original user, giving the user *both* the solver's output tokens *and* their own refunded input tokens. This is unconditional loss of solver funds and unjust enrichment of the order owner.
- No malicious relayer, prover, admin, or governance actor is required — the trigger is any unprivileged account calling the public cancel path after `order.deadline`, racing naturally-occurring cross-chain message delivery latency of the legitimately-dispatched `RedeemEscrow`.

### Likelihood Explanation
The race window is realistic: a solver can legally fill an order at (or very near) `order.deadline` since `fillOrder` only requires `order.deadline >= _blockNumber()`. The `RedeemEscrow` post must still be relayed cross-chain to the source chain and processed there. Meanwhile, `_cancelFromDest` becomes permissionlessly callable by *anyone* the instant the deadline passes, and its dispatch (`RefundEscrow`) can be relayed with equal or lower cross-chain latency. No collusion, front-running of the fill transaction itself, or privileged role is needed — an opportunistic user (or the order owner) simply calls `cancelOrder` on the destination chain immediately after the deadline block, independent of whether a fill already landed there moments earlier.

### Recommendation
Add a finalization guard in `_cancelFromDest` mirroring the one already present in `fillOrder`: `if (_filled[commitment] != address(0)) revert Filled();` before overwriting `_filled[commitment]` and dispatching `RefundEscrow`. This closes the gap the same way the Velodrome fix closed the managed/normal NFT gap — by making the second independent finalization path aware of, and blocked by, the first.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `D` (or just before), a solver calls `fillOrder` → `_fillCrossChain`: sets `_filled[commitment] = solver` on the destination chain, transfers output tokens to the beneficiary, and dispatches `RedeemEscrow` to the source chain.
3. Immediately at block `D+1`, any address calls `cancelOrder` on the destination chain → `_cancelFromDest`: since no `_filled` check exists, it overwrites `_filled[commitment] = order.user` and dispatches `RefundEscrow` to the source chain.
4. Due to independent relayer delivery timing, `RefundEscrow` is delivered to and processed on the source chain (via `onAccept` → `_withdraw`) before `RedeemEscrow`. The escrowed input tokens are paid to `order.user`.
5. When `RedeemEscrow` later arrives, `_orders[commitment][token]` is already zero, so `_withdraw` reverts with `UnknownOrder` for the solver's claim — the solver receives nothing despite having already paid out the order's output tokens on the destination chain.

I was not able to fully verify, in the time available, whether the public `cancelOrder` wrapper in `IntentGatewayV2.sol` (as opposed to the internal `_cancelFromDest` I read directly) adds an extra `_filled` check before calling into `_cancelFromDest` — I only confirmed the internal function itself lacks this guard. If `cancelOrder` does add such a check, the exploit path as described would be blocked; this should be confirmed by reading `IntentGatewayV2.sol`'s `cancelOrder` function body in full.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            uint256 dust = solverAmount - totalRequired;
            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;

            if (dust > 0) {
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            }

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        address hostAddr = host();
        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RedeemEscrow)),
            abi.encode(
                WithdrawalRequest({
                    commitment: commitment, tokens: order.inputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
                })
            )
        );
        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        if (options.nativeDispatchFee > 0 && msgValue >= options.nativeDispatchFee) {
            IDispatcher(hostAddr).dispatch{value: options.nativeDispatchFee}(request);
            msgValue -= options.nativeDispatchFee;
        } else {
            dispatchWithFeeToken(request);
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
