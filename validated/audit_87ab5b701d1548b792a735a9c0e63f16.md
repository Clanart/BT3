## Analysis

I found a real GitHub Desktop analog of the Gondi front-running invariant issue: a check-then-act race between a mergeability preview and the actual `git merge` execution, where the intervening state mutation is driven by an attacker-controlled remote via Desktop's automatic background fetch.

### Title
Stale mergeability preview allows silent merge of unreviewed remote commits due to TOCTOU between `determineMergeability` and `git merge <branch-name>` - (File: `app/src/ui/multi-commit-operation/choose-branch/merge-choose-branch-dialog.tsx`, `app/src/lib/stores/app-store.ts`, `app/src/lib/git/merge.ts`)

### Summary
`MergeChooseBranchDialog` computes a "clean merge / conflicts / commit count" preview once, when the user selects a branch, by calling `determineMergeability` and caching the result keyed by `branch.tip.sha` [1](#0-0) . When the user later clicks "Merge", `start()` passes that stale `mergeStatus`/`selectedBranch` object straight to `dispatcher.mergeBranch` without recomputing anything [2](#0-1) . `_mergeBranch` in `app-store.ts` never re-validates the branch's current tip; the `mergeStatus` argument is used only to increment telemetry counters [3](#0-2) , and the real work is delegated to `gitStore.merge(sourceBranch, ...)` → `merge(repository, branch.name, ...)`, which executes `git merge <branch-name>` by **ref name**, not by the previously-checked SHA [4](#0-3) . Meanwhile, `BackgroundFetcher` runs automatically (as often as every 5 minutes, controlled by the remote/server's poll-interval header) and silently advances local tracking refs from the attacker-controlled remote [5](#0-4) , with no coordination with an open merge dialog.

### Finding Description
This is the same broken invariant as the Gondi report: a security-relevant decision (in Gondi, `loanId`; here, the "clean merge"/conflict/commit-count preview) is validated against one state snapshot, but the actual state-mutating operation is executed against a **ref name** whose underlying value can be changed by an untrusted third party (a collaborator/fork owner controlling the tracked remote branch) in the window between validation and execution.

Concretely:
1. User opens "Merge into current branch", selects a branch. `updateStatus` computes `mergeStatus` and `commitCount` from `branch.tip.sha` at that moment [6](#0-5) .
2. The dialog stays open (user reads the diff, gets distracted, dialog is not auto-refreshing beyond user-driven `onSelectionChanged`).
3. Desktop's `BackgroundFetcher`, unrelated to the dialog's lifecycle, fetches the tracked remote on its own schedule and advances the local `refs/remotes/<remote>/<branch>` (and, if it's a local branch tracking that remote, the local branch ref can also move via other flows) [7](#0-6) . This fetch is driven entirely by content from the remote — an attacker who controls that remote (a malicious collaborator, a compromised or hostile fork used in a merge-from-fork workflow) can push new commits at the moment they know a merge is about to happen.
4. User clicks "Merge". `start()` uses the stale `mergeStatus`/`selectedBranch` reference to invoke `dispatcher.mergeBranch` [2](#0-1) .
5. `_mergeBranch` doesn't re-check `sourceBranch.tip.sha` against the live ref before calling `gitStore.merge` [8](#0-7) .
6. `merge()` runs `git merge <branch.name>` [9](#0-8) , which resolves `<branch.name>` to whatever it **currently** points to — potentially new commits injected by the attacker after the "clean, N commits" preview was shown and never re-validated.

Existing guards do not stop this path:
- `canStartOperation` only checks that a branch is selected, isn't the current branch, and that the cached `mergeStatus.kind`/`commitCount` (both stale) look OK [10](#0-9)  — it re-validates nothing against live git state.
- The staleness check inside `updateStatus` (`this.state.selectedBranch?.tip.sha !== branch.tip.sha`) only protects against the user switching the *selection* while the async `determineMergeability`/`getAheadBehind` calls are in flight; it does nothing once the async call has resolved and the dialog is just sitting open waiting for the user to click "Merge" [11](#0-10) .
- Unlike the rebase/reorder/squash flows, which capture `beforeChangeSha`/`originalBranchTip` for the *current* branch and use it for post-hoc reconciliation via `updateConflictState` (aborting the multi-commit operation state if the tip changed unexpectedly) [12](#0-11) , the merge path performs no analogous tip-drift check before or after the actual `git merge` call.

### Impact Explanation
This corresponds to the report's "silent corruption of what the user commits or pushes" category. The user is shown "clean merge, 3 commits" and clicks merge expecting exactly that content to be integrated; if the attacker (a collaborator on the fork/branch being merged) pushes additional commits timed to land between the preview and the click, those commits get silently merged with no re-confirmation, no new conflict warning, and no diff re-review — because `git merge <name>` always resolves the ref at execution time, not at preview time. If the merge is followed by a push (a common immediate follow-up action in Desktop's workflow), attacker-controlled content can end up on the shared/protected branch without the user ever seeing or approving it.

### Likelihood Explanation
The precondition is realistic and requires no local access, malware, or leaked credentials — only that the user merges from a branch/remote the attacker (a co-maintainer, or a fork owner in an "Open in Desktop"/PR review flow) controls, and that the attacker times a push while the merge dialog is open. `BackgroundFetcher`'s interval can be as short as `MinimumInterval` (5 minutes) if the server-provided poll interval is low [13](#0-12) , and the dialog has no time pressure forcing the user to click immediately, so the race window is wide in practice (any time the dialog is left open). This mirrors exactly the judge's rationale for the original Gondi finding — the attack is "pretty likely to happen" whenever the operation is left pending near a state-changing window, and here the "expiry-like" analog is simply the time the merge dialog stays open.

### Recommendation
Before executing the actual `git merge`, re-resolve the selected branch's current tip SHA and compare it against the SHA the mergeability preview was computed for; if it has changed, refuse to merge and force Desktop to recompute `determineMergeability`/`commitCount` and re-prompt the user, analogous to the rebase/reorder/squash operations' `originalBranchTip` reconciliation. Additionally, consider pausing/deferring the background fetcher for the currently open merge/rebase dialog's target and source branches while the dialog is open, similar to how Gondi ultimately mitigated the underlying issue by restricting when loan-ID-changing operations could run relative to time-sensitive user actions.

### Proof of Concept
1. Attacker and victim collaborate on a repo; victim opens GitHub Desktop, selects "Merge into current branch", and picks the attacker's branch/fork branch.
2. `determineMergeability` computes "Clean, 2 commits ahead" and caches it against `branch.tip.sha = X` [6](#0-5) .
3. Victim reviews the 2 commits, but leaves the dialog open (e.g., switches window briefly).
4. Attacker pushes a 3rd, malicious commit to the same branch. Desktop's `BackgroundFetcher`, running on its own timer, fetches it and updates the local tracking ref to `Y` (the attacker's new tip) without any dialog interaction [5](#0-4) .
5. Victim returns and clicks "Merge", trusting the "Clean, 2 commits" preview still shown in the dialog.
6. `start()` → `dispatcher.mergeBranch` → `_mergeBranch` → `gitStore.merge` → `git merge <branch-name>` merges the *current* ref value `Y` (3 commits, including the attacker's unreviewed commit), not the previewed `X` [9](#0-8) , with no re-validation anywhere in the call chain [8](#0-7) .

### Note on scope / confidence
I could not directly confirm from the indexed code whether Desktop pauses `BackgroundFetcher` while a `MultiCommitOperation` popup (merge/rebase dialog) is open — no such pause/resume call was found in the available files (`app-store.ts`, `background-fetcher.ts`, `repository-indicator-updater.ts`), which supports the conclusion that no such guard exists, but this is based on the indexed subset of the codebase and a full grep across the entire repository (not fully covered by the index) would be needed to rule out an unseen guard with certainty. If you need to confirm this exhaustively, a Devin session with full filesystem access could grep the complete source tree for any fetch-pausing logic tied to `PopupType.MultiCommitOperation`.

  private updateStatus = async (branch: Branch) => {
    const { currentBranch, repository } = this.props

    const mergeStatus = await determineMergeability(
      repository,
      currentBranch,
      branch
    ).catch<MergeTreeResult>(e => {
      log.error('Failed determining mergeability', e)
      return { kind: ComputedAction.Clean }
    })

    // The user has selected a different branch since we started or the branch
    // has changed, so don't update the preview with stale data.
    //
    // We don't have to check if the state changed from underneath us if we
    // loaded the status from cache, because that means we never kicked off an
    // async operation.

      return

      this.setState({ mergeStatus })
      return

  public async _mergeBranch(
    repository: Repository,
    sourceBranch: Branch,
    mergeStatus: MergeTreeResult | null,
    isSquash: boolean = false
  ): Promise<void> {
    const { multiCommitOperationState: opState } =
      this.repositoryStateCache.get(repository)

    if (
      opState === null ||
      opState.operationDetail.kind !== MultiCommitOperationKind.Merge
    ) {
      log.error('[mergeBranch] - Not in merge operation state')
      return
    }

    this.repositoryStateCache.updateMultiCommitOperationState(
      repository,
      () => ({
        operationDetail: { ...opState.operationDetail, sourceBranch },
      })
    )

    const gitStore = this.gitStoreCache.get(repository)

    if (isSquash) {
      this.statsStore.increment('squashMergeInvokedCount')
    }

    if (mergeStatus !== null) {
      if (mergeStatus.kind === ComputedAction.Clean) {
        this.statsStore.increment('mergedWithCleanMergeHintCount')
      } else if (mergeStatus.kind === ComputedAction.Conflicts) {
        this.statsStore.increment('mergedWithConflictWarningHintCount')
      } else if (mergeStatus.kind === ComputedAction.Loading) {
        this.statsStore.increment('mergedWithLoadingHintCount')
      }
    }

    let aborted = false
    const mergeResult = await gitStore.merge(sourceBranch, {
      squash: isSquash,
      onHookFailure: this.onHookFailure(() => (aborted = true)),
    })

  /** Perform a fetch and schedule the next one. */
  private async performAndScheduleFetch(
    repository: GitHubRepository
  ): Promise<void> {
    if (this.stopped) {
      return
    }

    const shouldFetch = await this.shouldPerformFetch(this.repository)

    if (this.stopped) {
      return
    }

    if (shouldFetch) {
      try {
        await this.fetch(this.repository)
      } catch (e) {
        const ghRepo = this.repository.gitHubRepository
        const repoName =
          ghRepo !== null ? ghRepo.fullName : this.repository.name

        log.error(`Error performing periodic fetch for '${repoName}'`, e)
      }
    }

    if (this.stopped) {
      return
    }

    const interval = await this.getFetchInterval(repository)
    if (this.stopped) {
      return
    }

    this.timeoutHandle = window.setTimeout(
      () => this.performAndScheduleFetch(repository),
      interval
    )
  }

export function canStartOperation(
  selectedBranch: Branch | null,
  currentBranch: Branch,
  commitCount: number | undefined,
  statusKind: ComputedAction | undefined
): boolean {
  // Is there even a branch selected?
  if (selectedBranch === null) {
    return false
  }

  // Is the selected branch the current branch?
  if (selectedBranch.name === currentBranch?.name) {
    return false
  }

  // We can always start if there are conflicts, we'll just
  // have to deal with the conflicts post the operation
  if (statusKind === ComputedAction.Conflicts) {
    return true
  }

  // Are there even commits to operate on?
  if (commitCount === undefined || commitCount === 0) {
    return false
  }

  return statusKind !== ComputedAction.Invalid
}
