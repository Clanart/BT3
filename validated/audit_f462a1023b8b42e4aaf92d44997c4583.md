### Title
Server-Side Request Forgery via unrestricted DataLayer mirror URLs consumed by `http_download` - ([File: chia/data_layer/download_data.py])

### Summary
Any wallet user can publish an on-chain "mirror" coin for a DataLayer store (`create_new_mirror` / `dl_new_mirror`) with an arbitrary URL string embedded as a coin memo [1](#0-0) . Any other node that tracks/subscribes to that store id automatically ingests these attacker-chosen URLs from wallet state via `update_subscriptions_from_wallet()` [2](#0-1)  and its periodic sync loop then issues outbound HTTP GET requests to those URLs with no host/scheme allow-listing, enabling SSRF against the victim's local network or cloud metadata services.

### Finding Description
Mirror URLs are wholly attacker-controlled data placed inside a spendable coin's memo field: `create_new_mirror()` builds a `CREATE_COIN` condition whose memos are `[launcher_id, *urls]`, with no validation of URL scheme or target host [1](#0-0) . When that coin is created on-chain, any peer's `DataLayerWallet.coin_added()` extracts `launcher_id, urls = get_mirror_info(...)` from the spend and, if the wallet is already tracking that `launcher_id`, stores the mirror verbatim via `dl_store.add_mirror(Mirror(...))` [3](#0-2) .

The DataLayer service's background loop (`periodically_manage_data` → `update_subscription`) calls `update_subscriptions_from_wallet()`, which pulls all mirror URLs for a subscribed store id via `dl_get_mirrors` and pushes them straight into the local subscription list with only trailing-slash trimming — no URL scheme or destination validation [2](#0-1) .

`fetch_and_validate()` later selects one of these `server_info.url` values and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs `session.get(server_info.url + "/" + filename, ...)` using `aiohttp` with no restriction on the target host (no blocking of loopback, RFC1918 ranges, link-local addresses, or cloud metadata IPs like `169.254.169.254`) [4](#0-3) [5](#0-4) . The only `proxy_url` option is an operator-configured outbound proxy, not an SSRF mitigation. The existing test suite even demonstrates loopback URLs (`http://127.0.0.1/8000`) being accepted for mirrors without complaint [6](#0-5) .

This mirrors the CVE-2024-5186 bug class: a user-influenced "path"/URL value that the server later dereferences via an outbound request with no destination allow-listing, allowing requests to be redirected to internal-only endpoints.

### Impact Explanation
Any wallet user tracking a DataLayer store can force the tracking node to make an unauthenticated outbound HTTP request to an attacker-chosen destination on the victim's behalf. This can be used to probe/attack internal network services unreachable from outside, or to reach cloud metadata endpoints (e.g., `169.254.169.254` on AWS/GCP) from any host running the DataLayer service in a cloud environment, potentially exfiltrating instance credentials. Response bodies aren't directly reflected back to the attacker (the request expects delta file bytes), but blind SSRF alone is high-impact for internal network reconnaissance, port scanning, and metadata-credential theft, and can also be leveraged for local service interaction (e.g., hitting other localhost-bound RPC/admin endpoints).

### Likelihood Explanation
Likelihood is high for anyone operating a DataLayer node that subscribes to a public/foreign store: publishing a mirror is a cheap, permissionless on-chain action (`dl_new_mirror`) requiring only a small XCH amount, and consumption is fully automatic via the periodic sync loop — no operator interaction or opt-in beyond initially subscribing to the store id is required.

### Recommendation
Validate and restrict mirror/subscription URLs before they are persisted or dereferenced: enforce an allow-list of schemes (e.g., `http`/`https` only), reject loopback/private/link-local/multicast destinations (including DNS resolution results, not just literal IPs) unless explicitly permitted by configuration, and consider resolving hostnames server-side with a strict egress policy before issuing the `aiohttp` request in `http_download()`. This validation should occur both when mirrors are ingested from wallet state (`update_subscriptions_from_wallet`) and defensively again immediately before use in `http_download`/`download_file`.

### Proof of Concept
1. Attacker runs `chia data add_mirror --id <store_id> --url http://169.254.169.254/latest/meta-data/iam/security-credentials/ -a 1 -m 1` to publish a mirror pointing at a cloud metadata endpoint (or `http://127.0.0.1:<internal-port>/` for internal service targeting), using the on-chain flow shown by `create_new_mirror`/`dl_new_mirror` [1](#0-0) .
2. Victim node is subscribed/tracking the same `store_id` (a normal Data Layer client action).
3. On the next `periodically_manage_data` cycle, `update_subscriptions_from_wallet()` ingests the malicious URL into the victim's subscription list [2](#0-1) .
4. `fetch_and_validate()` selects that server and calls `http_download()`, which issues `session.get("http://169.254.169.254/.../filename")` from the victim's process [7](#0-6) , completing the SSRF.
