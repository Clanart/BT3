## Analysis

The external report describes a "revert on zero value transfer" DOS: an unconditional `safeTransfer` of a possibly-zero amount reverts the whole payout for the specific class of ERC20 that reverts on zero-value transfers, locking the entire withdrawal.

Hyperbridge's local intents infrastructure has a near-identical fund-payout function, and — critically — the fix for exactly this class of bug already exists in one copy of the code but is missing in a parallel copy:

- [1](#0-0) , `_withdraw()` explicitly guards with `if (amount == 0) continue;` before calling `IERC20(token).safeTransfer(beneficiary, amount)`.
- [2](#0-1) , the Tron deployment's `withdraw()` has **no such guard** — it unconditionally does `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for every token leg, even when `amount == 0`.

### Title
Missing zero-amount guard in Tron `IntentGatewayV2.withdraw()` allows permanent escrow lock with revert-on-zero-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds, delivered as authenticated cross-chain ISMP messages from the paired `IntentGatewayV2` instance [3](#0-2) . It iterates every `TokenInfo` in `body.tokens` (mirroring `order.inputs`) and unconditionally transfers `amount` of each token to the beneficiary, without skipping zero amounts, unlike the sibling implementation in `IntentsBase.sol` which explicitly `continue`s on `amount == 0`.

### Finding Description
`withdraw()` only checks that the *escrowed balance* for a token is non-zero (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`), not that the per-call `amount` being transferred is non-zero. If any input leg of an order has a zero `TokenInfo.amount` (an entry the base contract's `_withdraw` was specifically hardened to tolerate), the Tron `withdraw()` will still attempt `token.call(transfer(beneficiary, 0))`. For tokens that revert on zero-value transfers, this call fails, `success` is false, and the function reverts with `TransferFailed`.

Because `_filled[body.commitment] = beneficiary;` is set at the top of the same function body (not persisted independently), a revert anywhere in the loop rolls back the *entire* transaction, including the `_filled` write and all prior-processed `_orders[...] -= amount` decrements in that same call. There is no retry path that skips the offending zero-amount leg — every retry of the same `RedeemEscrow`/`RefundEscrow` message hits the identical zero-transfer revert.

### Impact Explanation
This is a fund-lock: the order's escrowed input tokens (potentially including other, non-problematic tokens bundled in the same multi-asset order) become permanently unredeemable because the finalize path can never complete. This matches the bounty's "loss/lock of funds" impact category and is reachable by a normal unprivileged flow — any order containing a zero-amount input leg paired with a revert-on-zero-transfer token, processed through the standard `RedeemEscrow`/`RefundEscrow` cross-chain settlement path — no malicious relayer, prover, or admin action is required.

### Likelihood Explanation
Likelihood depends on whether orders can legitimately carry a zero-amount `TokenInfo` leg (the existence of the `if (amount == 0) continue;` guard in the canonical EVM `IntentsBase._withdraw` strongly suggests this is an anticipated/supported case elsewhere in the protocol) combined with the target order including a revert-on-zero-transfer ERC20 among its `inputs`/`output.assets`. Given the protocol's own README-style token compatibility concerns (as referenced in the seed report) and that this exact defensive check exists in the sibling contract but was dropped in the Tron port, this is a straightforward divergence bug rather than a purely theoretical one.

### Recommendation
Add the same guard used in `IntentsBase._withdraw()` to the Tron `IntentGatewayV2.withdraw()`:
```solidity
if (amount == 0) { unchecked { ++i; } continue; }
```
before the token transfer branch, for both the token loop and, for symmetry, the fee-token branch already guarded by `if (fees > 0)`. Audit all other Tron-specific reimplementations (`sweepDust` in `onAccept`, etc.) for the same class of missing checks that were fixed only in the canonical `IntentsBase.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` that reverts on `transfer(to, 0)` (a real-world "revert on zero value" ERC20 per the seed report's token-weirdness class).
2. Place an order whose `inputs` include a leg `TokenInfo{token: T, amount: 0}` alongside another legitimate escrowed token (the base contract's explicit skip logic in `IntentsBase._withdraw` shows such zero-amount legs are an expected/valid order shape).
3. Solver fills (or the deadline passes and cancellation is triggered), producing a `RedeemEscrow`/`RefundEscrow` `WithdrawalRequest` with `tokens` containing the same zero-amount `T` leg.
4. On the Tron gateway, `onAccept` → `withdraw()` reaches `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, 0))` for `T`, which reverts inside `T`.
5. The whole `withdraw()` call reverts, `_filled[body.commitment]` is never set, and every subsequent delivery attempt of the identical message reverts identically — the order's entire escrow (including the legitimate, non-zero-amount tokens) is permanently locked.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
