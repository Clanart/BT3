### Title
Empty statement list makes `DLEqProof::verify` / `MultiDLEqProof::verify` accept a proof bound to nothing - (File: crypto/dleq/src/lib.rs)

### Summary
`DLEqProof::verify` checks that `generators.len() == points.len()` but never requires that count to be non-zero. When both slices are empty, the verification loop runs zero times, so no `(generator, R, point)` tuples are ever transcripted. The proof's `c` is then compared against a challenge derived from a transcript containing only `domain_separate(b"dleq")` — a value any unprivileged party can compute offline. The same shape exists in `MultiDLEqProof::verify`, where empty `generators`, `points`, and `s` satisfy all length checks and again bind `c` to nothing. This mirrors the Spring Boot advisory: the protection (the per-statement binding, analogous to the per-endpoint authorization rule) silently evaporates when a component is absent.

### Finding Description
In `DLEqProof::verify` (`crypto/dleq/src/lib.rs:160-180`):

- `if generators.len() != points.len()` passes trivially for `len == 0`.
- `transcript.domain_separate(b"dleq")` is appended, then the `for (generator, point) in generators.iter().zip(points)` loop iterates zero times, contributing zero `verify_statement` calls.
- `self.c != challenge(transcript)` compares `c` against `challenge()` over a transcript that contains only the domain separator. `challenge()` (`lib.rs:28-85`) is a deterministic public function of the transcript state; the attacker computes the same `c` themselves with no secret.
- `self.s` is never constrained — with zero statements there is no equation `s*G - c*A = R` checked at all.

`MultiDLEqProof::verify` (`lib.rs:264-294`) has the identical hole: `self.s.len() != generators.len()` passes when all are `0`, the outer loop body never runs, and `c` binds to a bare `domain_separate(b"multi_dleq")` transcript.

`DLEqProof::read` (`lib.rs:191-193`) and `MultiDLEqProof::read` (`lib.rs:308-315`) deserialize `c`/`s` directly from attacker-controlled bytes, and `read` takes `discrete_logs` as a parameter, so a caller plumbing an untrusted length through can produce an `s` of length 0.

### Impact Explanation
A proof that verifies while binding to no statement is a forged proof: any verifier that calls `verify` with an attacker-influenced (or degenerate) empty `generators`/`points` accepts a "proof of discrete-log equality" the prover never established. In protocols built on this primitive (e.g., generator-promotion or key-linking proofs in the DKG/MuSig stack), this collapses the soundness guarantee — the proof asserts equality of discrete logs across generators, yet proves nothing about any key. The concrete acceptance criterion "a forged proof" is met: verification succeeds for a transcript containing zero proven statements.

### Likelihood Explanation
Exploitation requires a call site that passes empty `generators`/`points` (or `discrete_logs == 0`) derived from or influenced by untrusted input. `DLEqProof::read`/`MultiDLEqProof::read` plus `verify` are exactly the read/verify surface the threat model covers. If all current call sites use fixed non-empty generator sets, the bug is latent — a Medium-severity soundness gap in a public API rather than a live Critical exploit. There is no compile-time or runtime guard preventing the empty case, and `prove` itself does not assert non-empty `generators`, so the vacuous case is fully reachable through the public API.

### Recommendation
Reject empty statement lists in both verifiers and in `read`/`prove`:

```rust
// crypto/dleq/src/lib.rs, in DLEqProof::verify and MultiDLEqProof::verify
if generators.is_empty() || generators.len() != points.len() {
  Err(DLEqError::InvalidProof)?;
}
// in MultiDLEqProof::verify, also reject generators.len() == 0 and any empty inner Vec
```

Mirror the check in `DLEqProof::prove` and `MultiDLEqProof::prove` (assert non-empty `generators`/`scalars`), and in `MultiDLEqProof::read` reject `discrete_logs == 0`, so a vacuous proof can never be constructed, serialized, or accepted.

### Proof of Concept
```rust
// For any Transcript T and any PrimeGroup G:
let mut transcript = fresh_transcript(); // same initial state the verifier uses
transcript.domain_separate(b"dleq");
// challenge() is public-crate logic; replicate it or call verify's path:
// The verifier computes challenge over a transcript with ONLY this domain separator.
let forged_c: G::Scalar = challenge_over_empty_dleq_transcript(); // == challenge(&mut transcript)

// Any s works — it is never checked against anything.
let forged = DLEqProof::<G> { c: forged_c, s: G::Scalar::random(&mut OsRng) };

// Verifier side (empty generators/points):
assert!(forged.verify(&mut fresh_transcript(), &[], &[]).is_ok());
```

`MultiDLEqProof` variant: `MultiDLEqProof { c: challenge over bare "multi_dleq" domain separator, s: vec![] }` verifies against `generators = &[]`, `points = &[]`, and `MultiDLEqProof::read(r, 0)` produces exactly this shape from attacker bytes.
