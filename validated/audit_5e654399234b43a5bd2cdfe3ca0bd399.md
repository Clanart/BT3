### Title
Attacker-controlled payment amounts overflow `payment_sat`, bypassing the `NotEnoughFunds` check and causing the multisig to sign a consensus-invalid transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to CVE-2019-13108 (an integer-overflow/mishandled-value bug reachable via attacker-controlled data producing a crash/DoS), `SignableTransaction::new` sums untrusted payment amounts and the required fee in plain `u64` arithmetic. Values summing past `u64::MAX` wrap (or panic on overflow checks), bypass the `NotEnoughFunds` sanity check, and let a transaction be constructed — and threshold-signed — whose declared output values exceed the inputs, making it consensus-invalid and unbroadcastable.

### Finding Description
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` takes `payments: &[(ScriptBuf, u64)]`, where each amount is an arbitrary `u64`. It computes:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
let mut needed_fee = fee_per_vbyte * vbytes;
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

- `payments.iter().map(...).sum::<u64>()` (line ~187) can overflow `u64` if the sum of attacker-influenced payment amounts exceeds `u64::MAX` — two payments of e.g. `u64::MAX / 2 + 2` suffice.
- `payment_sat + needed_fee` (line ~215) can likewise overflow, and `payment_sat + fee_with_change` in `input_sat.checked_sub(payment_sat + fee_with_change)` (line ~228) can wrap to a small value, making `checked_sub` succeed and producing a fabricated change output of nearly `input_sat`.

In debug builds the wrapping `sum`/`+` panics (crash, the direct CVE-2019-13108 analog). In release builds it wraps silently: the `NotEnoughFunds` check is bypassed and the returned `SignableTransaction` contains `TxOut`s whose `Amount::from_sat(payment.1)` values exceed `MAX_MONEY`/the real inputs. `TransactionSignMachine::sign` then has the whole FROST threshold set produce BIP-340 signatures over this transaction (`send.rs:355-398`), and `complete` returns a transaction that no Bitcoin node will ever accept.

### Impact Explanation
The multisig completes a full FROST signing round and "successfully" emits a consensus-invalid, unbroadcastable transaction. Effects:

- Permanent burning of a signing session/preprocesses and, in systems like the Serai processor where plans are retried, repeated invalid-signing attempts (liveness failure for that payment batch).
- In debug/checked builds, a remote-triggerable panic crashing the signer (direct availability loss, matching the CVE's SIGSEGV denial of service).
- A change output (`send.rs:228-234`) can be computed from a wrapped `payment_sat`, yielding a change `Amount` far above the real residual; even if the tx were valid-shaped, the accounting is corrupted.

Real Bitcoin inputs can't exceed ~2.1e15 sats, so the overflow can only originate from the payment amounts — which are exactly the attacker-supplied values in payment instructions.

### Likelihood Explanation
Any party who can cause a `Plan`/payment instruction to be created controls the `u64` amounts flowing into `SignableTransaction::new` (the processor builds `payments` from user-supplied out-instruction data). No threshold collusion, leaked keys, or malicious validator is required — only specifying payment amounts whose sum overflows `u64`. There is no other validation: `DustPayment` only checks a lower bound, and `TooLargeTransaction` only checks weight, not total value.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:

- `payments.iter().try_fold(0u64, |a, p| a.checked_add(p.1))` for `payment_sat` (and likewise for `input_sat`, defensively).
- `payment_sat.checked_add(needed_fee)` / `payment_sat.checked_add(fee_with_change)` instead of `+`.
- Additionally reject any single payment `> MAX_MONEY` (21e14 sats) as a belt-and-suspenders check, and cap `fee_per_vbyte * vbytes` with `checked_mul`.

Return a new `TransactionError` variant (e.g. `AmountOverflow`) on failure instead of wrapping.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs context
// A batch of two attacker-chosen payments whose amounts sum past u64::MAX:
let payments: &[(ScriptBuf, u64)] = &[
  (p2tr_script_buf(even_key).unwrap(), u64::MAX / 2 + 2), // >= DUST, passes dust check
  (p2tr_script_buf(even_key).unwrap(), u64::MAX / 2 + 2),
];
// payment_sat wraps to ~3; `input_sat < (payment_sat + needed_fee)` is false,
// so NotEnoughFunds is bypassed and tx_outs contain Amount::from_sat(u64::MAX/2+2)
// values far exceeding the real inputs -> consensus-invalid transaction.
SignableTransaction::new(inputs, payments, None, None, 20 /* sat/vB */).unwrap();
// In debug builds, `.sum::<u64>()` panics immediately on the overflow.
```

The resulting `SignableTransaction` passes all checks; `multisig(...)` + `preprocess` + `sign` + `complete` yield a fully FROST-signed transaction that Bitcoin consensus rejects (output amount > `MAX_MONEY` / exceeds inputs), and on overflow-checked builds the call panics outright — a remotely triggerable denial of service from untrusted payment data.
