### Title
Empty aggregate signatures bypass verification - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero nonces, and `SchnorrAggregate::verify` accepts it when the caller’s key/challenge list is empty and `s = 0`. This lets an attacker forge a valid aggregate authorization for the empty signer set. [1](#0-0) 

### Finding Description
Deserialization reads a `u32` count, reads that many `R` values, and then reads `s`; it does not reject a count of zero. [1](#0-0)  During verification, the only signer-count check is equality between `self.Rs.len()` and `keys_and_challenges.len()`, so two empty lists pass. [2](#0-1)  With no signatures queued, verification constructs only `(-s)G`; when the encoded `s` is zero, that expression is identity and verification returns `true`. [3](#0-2) 

### Impact Explanation
An untrusted party can submit the 36-byte encoding of an empty aggregate with a canonical zero scalar and have it treated as a valid signature by any caller that dynamically verifies the supplied signer/challenge list and reaches the empty-set case. [1](#0-0)  This is a signature forgery caused by an absent minimum-participant check, analogous to allowing a sensitive operation after checking no required credentials. [4](#0-3) 

### Likelihood Explanation
The forged input is deterministic and requires no secret, invalid encoding, or control over honest signers. [1](#0-0)  Exploitation requires a verifier path where an attacker-selected or otherwise reachable empty `keys_and_challenges` list is meaningful; callers enforcing a nonempty policy before invoking this API would not be affected. [2](#0-1) 

### Recommendation
Reject empty aggregates in `SchnorrAggregate::read` and defensively reject `keys_and_challenges.is_empty()` in `verify`. [1](#0-0)  Add a regression test asserting that an encoded empty aggregate with `s = 0` fails deserialization or verification. [4](#0-3)
