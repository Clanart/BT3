### Title
Git-hooks sandbox interception (`core.hooksPath` override) is silently clobbered by the trampoline environment, letting local repo hooks run unfiltered with Desktop's secrets - ([File: app/src/lib/git/core.ts])

### Summary
`git()` in [1](#0-0)  composes two independent environment wrappers, `withHooksEnv` and `withTrampolineEnv`, and merges their outputs with the trampoline environment applied last: `{ TERM: 'dumb', ...opts.env, ...hooksEnv, ...env }`. Both wrappers communicate their intent through the *same* environment variable key, `GIT_CONFIG_PARAMETERS`: `withHooksEnv` sets it to redirect Git's hook execution through Desktop's sandboxing proxy (`core.hooksPath=<tmpHooksDir>`), while `withTrampolineEnv` sets its own `GIT_CONFIG_PARAMETERS` for the credential helper, unaware of the hooks value because it only looks at `opts.env`/`process.env`, never at `hooksEnv` [2](#0-1) . Because `env` (trampoline) is spread after `hooksEnv` in the final object, its `GIT_CONFIG_PARAMETERS` value completely replaces (not merges with) the one that redirects hooks to the sandbox, silently disabling the hook-interception mechanism whenever the operation also needs a trampoline environment — which is effectively every Git command executed through `git()`.

### Finding Description
`withHooksEnv` is meant to protect the user by intercepting execution of any Git hooks that already exist in a repository (found via `getRepoHooks`) and running them through `createHooksProxy`, which strips sensitive environment variables (`GIT_ASKPASS`, `GIT_SSH_COMMAND`, `GIT_USER_AGENT`, `GIT_CONFIG_PARAMETERS`, etc.) before spawning the actual hook binary [3](#0-2) [4](#0-3) . This is achieved purely by pointing `core.hooksPath` at a temp directory populated with proxy stubs via `GIT_CONFIG_PARAMETERS` [5](#0-4) .

`withTrampolineEnv` independently constructs its own `GIT_CONFIG_PARAMETERS` to configure `credential.helper=desktop`, and also injects `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`, which give any process access to the trampoline TCP server (askpass/credential helper) [6](#0-5) . In `git()`, this trampoline output (`env`) is spread last, so its `GIT_CONFIG_PARAMETERS` string (which never included the hooks path prefix, since `customEnv` passed to `withTrampolineEnv` is `opts.env`, not `hooksEnv`) overwrites the one produced for sandboxing hooks. As a result `core.hooksPath` reverts to the repository's real hooks directory, and the pre-existing hook script executes directly under Git rather than through the proxy — with full unfiltered access to `DESKTOP_PORT`, `DESKTOP_TRAMPOLINE_TOKEN`, `GIT_ASKPASS`, and `GIT_CONFIG_PARAMETERS` that the proxy's `excludedEnvVars`/`safePrefixes` allowlist was specifically designed to keep away from hook processes.

### Impact Explanation
Any hook already present on disk for a repository the user opens (e.g. a repository cloned/copied with a pre-populated `.git/hooks/<name>` script, or one where `core.hooksPath` is locally configured to a directory an attacker can write into) is executed with Desktop's internal trampoline token and port exposed in its environment, instead of the sanitized `safeEnv`. With `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN`, a malicious hook process can talk to the trampoline server's credential-helper/askpass command channel and solicit GitHub/SSH credentials that Desktop would otherwise only hand to its own askpass/credential-helper trampoline binaries, resulting in credential/token exfiltration. It also silently defeats the "safe hooks environment" feature entirely, since the interception it was designed to add (env sanitization, `onHookFailure` prompts, shell-env correctness) never engages when a trampoline environment is also required — which is unconditionally true for `git()`.

### Likelihood Explanation
This triggers on every Git operation that (a) has at least one existing hook in the repo/hooks path and (b) goes through `git()` (nearly all Desktop git operations, since `withTrampolineEnv` is always invoked as part of `git()`'s option composition). No unusual user action is required beyond opening/using a repository that already contains a hook script — the override happens deterministically due to plain object spread order, not a race condition.

### Recommendation
Make the two environment builders compose their `GIT_CONFIG_PARAMETERS` values instead of one clobbering the other — e.g. have `withTrampolineEnv` accept and prefix the value produced by `withHooksEnv` (the same way it already prefixes `customEnv`/`process.env`), or have `core.ts` concatenate `hooksEnv.GIT_CONFIG_PARAMETERS` and `env.GIT_CONFIG_PARAMETERS` explicitly rather than relying on last-write-wins spread order. Add a regression test asserting that when both hooks interception and trampoline env are active, the final `GIT_CONFIG_PARAMETERS` contains both the `core.hooksPath` override and the credential-helper configuration.

### Proof of Concept
1. Open/clone a repository that has an existing local hook, e.g. `.git/hooks/pre-commit`, that reads and reports `process.env.DESKTOP_TRAMPOLINE_TOKEN` and `process.env.DESKTOP_PORT` (or connects to that port to invoke the askpass/credential-helper protocol).
2. Enable the hooks-environment feature so `interceptHooks` is set for the relevant `git()` calls (per `getHooksEnvEnabled`/`enableHooksEnvironment`, per [7](#0-6) ).
3. Trigger a commit from Desktop. In `git()`, observe that the final `env.GIT_CONFIG_PARAMETERS` passed to `exec` is the trampoline's value (`'credential.helper=' 'credential.helper=desktop'`) with no `core.hooksPath=<tmp>` component, confirmed by inspecting the merge at [8](#0-7) .
4. Because `core.hooksPath` never got redirected to the sandboxed proxy directory, Git invokes `.git/hooks/pre-commit` directly, inheriting the full process environment including `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`/`GIT_ASKPASS`, which the hooks proxy's `excludedEnvVars` allowlist at [3](#0-2)  would otherwise have stripped — demonstrating the hook obtains data it should never see.
