## Title
Signed integer overflow in `TimeUtil::DurationToNanoseconds` from unchecked multiplication of attacker-controlled `Duration.seconds` - (File: `src/google/protobuf/util/time_util.cc`)

## Summary
The Uniswap-style report describes `getMaxLiquidityForAmount0Precise` overflowing because it multiplies attacker-influenced values before dividing, with the only "safety net" being that a large-enough overflow makes the transaction revert (or, worse, silently wrap). The transferable invariant is: *a value that is nominally range-checked, but whose validity check is a no-op/soft-fail in the deployed binary, is multiplied by a large constant before any narrowing operation, producing silent signed-integer overflow (UB) on ordinary, schema-valid input.* In protobuf's C++ `util/time_util.cc`, `TimeUtil::DurationToNanoseconds()` reproduces exactly this pattern: it computes `duration.seconds() * kNanosPerSecond + duration.nanos()` where `seconds()` comes directly from an attacker-parsed `google.protobuf.Duration` message, and the only bounds check is `ABSL_DCHECK(IsDurationValid(duration))`, which compiles to nothing in release (`NDEBUG`) builds.

## Finding Description
`google.protobuf.Duration` is a standard well-known-type message with an unconstrained `int64 seconds` field [1](#0-0) . Binary/ProtoJSON parsing of a `Duration` message via any of protobuf's public `ParseFrom*`/JSON parse APIs places no restriction on `seconds` beyond the wire format's own varint decoding — the value can legitimately be parsed anywhere in `[INT64_MIN, INT64_MAX]`, since `Duration` is an ordinary proto3 message with a plain `int64` field, not something the wire parser itself range-checks.

`TimeUtil::DurationToNanoseconds` then computes:
```cpp
int64_t TimeUtil::DurationToNanoseconds(const Duration& duration) {
  ABSL_DCHECK(IsDurationValid(duration))
      << "Duration is outside of the valid range";
  return duration.seconds() * kNanosPerSecond + duration.nanos();
}
``` [1](#0-0) 

`kNanosPerSecond` is `1000000000` [2](#0-1) . The multiplication `seconds() * 1e9` is exactly analogous to the FunC report's `(amount0 * sqrtRatioAX96) * sqrtRatioBX96`: a product of an attacker-controlled magnitude and a large constant, performed with no saturating/overflow-checked arithmetic and no prior narrowing. Signed integer overflow in C++ is undefined behavior, not merely an incorrect result — unlike Solidity/FunC where it deterministically reverts.

The "missing check" mirrors the report precisely: the function relies on `ABSL_DCHECK`, which — like many `assert`-style macros — is compiled away in release/`NDEBUG` builds (the same category of "audit-only, not enforced-at-runtime" validation the Trail of Bits report flags as insufficient). `IsDurationValid` itself only checks `seconds` against `kDurationMinSeconds`/`kDurationMaxSeconds`  (roughly ±315,576,000,000), so even the *intended* invariant would reject the overflow case, but the enforcement is dead code in production.

`DurationToMicroseconds`/`DurationToMilliseconds` also multiply `DurationToSeconds(duration) * kMicrosPerSecond` etc. with no `ABSL_DCHECK` at all guarding that specific call [3](#0-2) , making them reachable overflow sites with even less protection.

## Impact Explanation
This is a genuine but narrow analog: it requires an application to (1) parse an attacker-supplied `Duration` message via a public protobuf parse API, and (2) call `TimeUtil::DurationToNanoseconds` (or the micro/milli variants) on the unvalidated result — a pattern that is common in services converting protobuf `Duration` to native time types for scheduling, rate limiting, or timeout computation. The overflow itself is UB in C++; in practice it typically wraps to a small or negative `int64_t`, which can invert timeout/duration semantics (e.g., a "huge" duration becoming negative or tiny), a logic-integrity failure comparable in class to the "user permanently loses funds" outcome in the report (both are silent-corruption-of-arithmetic-result bugs stemming from unchecked multiply-before-narrow on attacker data). It is not a memory-safety RCE and does not itself crash or leak memory, which caps the severity below Critical.

## Likelihood Explanation
Likelihood is Low-Medium. Reaching the bug requires no privileged access — an ordinary client can trivially craft a `Duration{seconds: INT64_MAX/2, nanos: ...}` and send it through any binary or ProtoJSON parse path, since `Duration.seconds` is not range-restricted by the wire format itself. The gating factor is that the vulnerable code path is not the wire parser but the well-known-type utility conversion functions in `time_util.cc`, and it only manifests in release builds where `ABSL_DCHECK` is a no-op and only if calling application code invokes `DurationToNanoseconds`/`DurationToMicroseconds`/`DurationToMilliseconds` on unsanitized, attacker-derived `Duration` values — a common but not universal usage pattern.

## Recommendation
- **Short term:** Replace `ABSL_DCHECK(IsDurationValid(duration))` in `DurationToNanoseconds` with an enforced check (`ABSL_CHECK`, or return an `absl::StatusOr`/clamp) that is active in release builds, and add the same validation to `DurationToMicroseconds`/`DurationToMilliseconds`, which currently have no guard at all. Alternatively, perform the multiplication in a wider/overflow-checked type (e.g., `absl::int128` as already used elsewhere in this file) before narrowing back to `int64_t`, mirroring the report's "compute an intermediate wider value before the final narrowing" recommendation.
- **Long term:** Fuzz all `TimeUtil`/`Timestamps`/`Duration` conversion helpers with out-of-range `seconds`/`nanos` values (including `INT64_MIN`/`INT64_MAX`) under `-fsanitize=undefined,integer` to catch silent signed-overflow paths that rely solely on debug-only assertions.

## Proof of Concept
Conceptual (production code, no schema/plugin changes needed):
```cpp
google::protobuf::Duration d;
d.set_seconds(9223372036854775807LL / 2);  // parsed from attacker-controlled bytes via Duration::ParseFromString
d.set_nanos(0);
// In a release (NDEBUG) build, ABSL_DCHECK is a no-op:
int64_t ns = google::protobuf::util::TimeUtil::DurationToNanoseconds(d);
// ns is the result of signed-overflow UB (typically wraps to a small/negative value)
```
Because `Duration` is parsed with an ordinary `int64` field and no wire-level bound on `seconds`, any client able to send a Duration message (e.g., embedded in an application's RPC payload parsed via `ParseFromArray`/ProtoJSON) can supply `seconds` values that trigger this overflow once the receiving service calls `DurationToNanoseconds` in a release build. I was not able to execute this locally within the current environment (no build/test execution available here); this should be confirmed with a UBSan-instrumented unit test added to `time_util_test.cc` before relying on it for a security fix.
