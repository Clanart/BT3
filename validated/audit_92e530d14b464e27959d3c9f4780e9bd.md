Based on the investigation, I found a concrete GitHub Desktop analog of the same bug class: **a security backstop (an unchecked boolean/flag) that, when bypassed, causes an untrusted, attacker-supplied value (here, a submodule URL from a cloned/fetched repository) to trigger unintended, silent local file exposure across a whole class of operations** — exactly the same shape as the `vaultAddress` invariant that, once flipped to an unsafe state, breaks protection for every subsequent swap/flash call.

### Title
Disabling Git's `protocol.file.allow` submodule guard (`allowFileProtocol=true`) lets an untrusted repository exfiltrate local files during checkout/submodule update - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean that, when `true`, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This flag is threaded through `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts`, which default the parameter to `false` but allow callers to opt in to `true` [2](#0-1) [3](#0-2) . Modern Git (2.38+, backported to 2.35.5) defaults `protocol.file.allow` to `user` specifically to close CVE-2022-39253, which allowed a malicious repository's `.gitmodules` to declare a `file://` submodule URL that, on clone/checkout with `--recursive`, copies an arbitrary local Git repository's contents into the working tree. Explicitly re-enabling `protocol.file.allow=always` for a checkout removes that backstop for whichever repository is being checked out.

### Finding Description
The corrupted value here is the `protocol.file.allow` git config option, forced to `always` by the app instead of left at Git's safe default (`user`). Once this flag is `true` for a given checkout/submodule-update call, `.gitmodules` content **from the repository being checked out** — which is attacker-controlled if the repository was cloned, forked, or fetched from an untrusted remote — is trusted to specify `file://` submodule URLs pointing anywhere on the local filesystem that itself is a Git repository (e.g. another one of the user's cloned repos, or a `.git` directory reachable by relative traversal). Git will then clone that local repository's objects and refs into the submodule directory inside the working tree, exposing its full history/config to the attacker-controlled repo (and to whatever it later pushes/exfiltrates).

Existing hardening in this codebase (`isClonePathSensitive` in `app/src/lib/git/clone.ts` [4](#0-3)  and `sanitizeCloneName` in `app/src/lib/remote-parsing.ts` [5](#0-4) ) shows the team is actively defending against repository-supplied values escaping their intended scope, but none of those guards inspect or restrict `.gitmodules` URLs when `allowFileProtocol` is `true` — the guard is entirely binary and, once set, applies with no further scoping (no allow-list of paths, no confirmation prompt referencing the actual submodule URL).

### Impact Explanation
If any code path passes `allowFileProtocol: true` while checking out a branch or commit sourced from a repository the user doesn't fully control (a fork, a PR branch, or any remote content), the checkout can silently exfiltrate the contents of another local Git repository (potentially including embedded credentials, tokens in `.git/config`, or private history) into the working tree of the untrusted repository, from which it can then be committed and pushed to the attacker's remote. This mirrors the original report's impact category ("silently corrupt what the user commits or pushes") and constitutes an unprivileged, repository-controlled read of files outside the intended repo boundary.

### Likelihood Explanation
I was not able to fully trace, within the available investigation budget, which specific UI call sites (`app/src/ui/dispatcher/dispatcher.ts` and `app/src/lib/stores/app-store.ts` each have multiple call sites for `checkoutBranch`/`checkoutCommit`) pass `allowFileProtocol: true`, or under what precondition (e.g. only for repositories already flagged as "local"/trusted vs. for any branch checkout including PR/fork branches). This is the key open question: if `true` is only ever passed for repositories the user explicitly added as local/trusted, the exploitability is much lower; if it is passed generically for ordinary branch checkouts (including checking out branches that originated from an untrusted fork/remote), the primitive is directly reachable by an unprivileged repository author. Due to index size limits I could not view the full contents of `dispatcher.ts`/`app-store.ts` call sites to confirm this; a Devin session with full repository access would be needed to verify the exact call graph.

### Recommendation
- Confirm every call site that passes `allowFileProtocol: true` and restrict it strictly to operations on repositories/branches the user has explicitly marked as trusted (mirroring the existing "unsafe repository" trust model in `app/src/ui/missing-repository.tsx` / `add-existing-repository.tsx`).
- Never derive `allowFileProtocol` from data contained within the repository being checked out (e.g. branch metadata, PR info) — it should only be a property of explicit user/host trust.
- Consider dropping the `protocol.file.allow=always` override entirely and instead surfacing an explicit, per-submodule-URL confirmation prompt when a repository declares `file://` submodules, consistent with Git's own default posture.

### Proof of Concept
Cannot be fully constructed without confirming the exact caller that supplies `allowFileProtocol: true` for untrusted content; conceptually:
1. Attacker publishes a public repository with a branch whose `.gitmodules` declares a submodule with `url = file:///Users/victim/some/other/local/repo/.git` (or a relative `file://../../` traversal to a sibling repository on disk).
2. Victim clones/forks and checks out that branch in GitHub Desktop through a code path that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, cloning the victim's other local repository's contents into the submodule folder [6](#0-5) .
4. The victim, unaware, commits and pushes, exfiltrating the other repository's history/config to the attacker's remote.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

/**
 * Extracts a safe single-component directory name from a URL-derived repo name.
 *
 * Mirrors the approach of git's `git_url_basename()` in `dir.c`: treat `/`,
 * `\`, and `:` as path separators, take the last non-empty component, strip a
 * trailing `.git` suffix, and reject traversal segments. This ensures the
 * result is always a single path component that cannot escape the parent
 * directory when passed to `Path.join()`.
 *
 * Examples:
 *  - `"Hello-World"` → `"Hello-World"` (unchanged)
 *  - `"desktop.git/../../otherdir"` → `"otherdir"` (last component, traversal segments skipped)
 *  - `".."` → `null` (traversal-only name rejected)
 *
 * See: https://github.com/git/git/blob/master/dir.c (`git_url_basename`)
 */
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
