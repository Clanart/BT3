I'll check the PedPoP ECDH/blame path and EncryptedMessage handling, which is the closest analog to "reading data outside intended permissions via confused identity."### Title
PedPoP blame path leaks the ECDH key for a forged message before its proof-of-possession is verified, allowing key-share recovery - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In `KeyMachine::calculate_share`, every incoming `EncryptedMessage` is decrypted via `Encryption::decrypt`, which immediately computes `ecdh(our_enc_key, msg.key)` and returns an `EncryptionKeyProof` containing that ECDH point. The sender's Schnorr proof-of-possession over `msg.key` is only *queued* into a `BatchVerifier` (`msg.pop.batch_verify`), and the batch is verified at the end of the loop. If the decrypted share bytes fail `C::F::from_repr`, the function early-returns `PedPoPError::InvalidShare` with `blame: Some(proof)` — before the batch (and thus the PoP) is ever verified. An attacker can copy another participant's per-message key `K` into their own `EncryptedMessage`, triggering publication of `our_enc_key * K`, which is the decryption capability for the victim's copy of that other participant's secret share.

### Finding Description
`Encryption::decrypt` computes the shared key and builds the blame proof unconditionally (`crypto/dkg/pedpop/src/encryption.rs:487-499`), while the PoP is deferred to a batch (`encryption.rs:479-485`). In `calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-492`), a non-canonical decrypted scalar produces `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` via `ok_or_else` at lines 480-482, which returns immediately — `batch.verify_with_vartime_blame()` at line 493 is never reached for that message.

This is precisely the attack the PoP was added to prevent, documented in the code itself: "Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X … they'd reveal bX, revealing Alice's message to Bob" (`encryption.rs:84-88`). The mitigation exists but is enforced too late: the blame proof — including `key = ecdh(our enc_key, msg.key)` — is already produced and attached to the error before the PoP check runs.

The message format allows the forgery: `msg.key` is an arbitrary `C::G` read from untrusted bytes (`encryption.rs:171-177`), and the ciphertext `msg.msg` is just keystream-xored bytes. The attacker supplies any ciphertext (e.g. bytes that deserialize to a non-canonical scalar) plus a garbage `pop`; `read` succeeds, `decrypt` computes the ECDH for the copied key, `from_repr` fails, and the victim emits a blame proof whose `dleq` is valid because it honestly proves knowledge of `enc_key` relating `enc_pub_key` to `key` (`encryption.rs:493-498`).

When the victim's processor broadcasts the blame (e.g. `CoordinatorMessage::VerifyBlame` in `processor/src/key_gen.rs:504-549`), `AdditionalBlameMachine::blame` / `decrypt_with_proof` will correctly fault the attacker (the forged PoP fails `msg.pop.verify` at `encryption.rs:374-379`), but the published `EncryptionKeyProof.key` already publicly exposes `enc_key_victim * K`. Anyone can then derive `cipher(context, K * enc_key_victim)` and decrypt the *original* honest message from the participant whose `K` was copied — learning that participant's secret share `f_sender(j)` intended only for victim `j`.

### Impact Explanation
A single malicious DKG participant can recover the entire group private key. For each victim `j`, the attacker copies participant `s`'s per-message key `K_{s,j}` (visible on the wire) into a forged share message to `j`. Each honest victim independently runs `calculate_share`, hits the early `from_repr` failure, and broadcasts a blame proof revealing `enc_key_j * K_{s,j}` — decrypting `s`'s real share to `j`. Collecting `t` such decrypted shares `f_s(j)` interpolates sender `s`'s contributed secret `f_s(0)`. Repeating for every sender `s` recovers every Pedersen contribution, whose sum is the group private key — total compromise of the threshold key from one malicious participant, with no collusion. Even if the attacker is later slashed for the forged PoP, the key material is already public.

### Likelihood Explanation
The attack requires only that the attacker be a DKG participant able to send crafted share messages and observe the publicly broadcast blame proofs — the standard PedPoP threat model. The forgery is trivial: copy a `key` field from a ciphertext the attacker can observe being delivered to the victim, attach random bytes for `pop` and `msg`. Every honest victim deterministically emits the leaking proof because the deserialization failure path precedes batch verification.

### Recommendation
Verify the PoP before producing or exposing the ECDH-derived proof. Concretely: in `calculate_share`, do not attach `blame` to the `InvalidShare` error until the batch PoP verification has succeeded for that participant's message; or restructure `Encryption::decrypt` to check `msg.pop.verify` inline (or split the batch into a pre-decryption PoP batch verified before any `EncryptionKeyProof` is returned). A blame proof for a message whose PoP fails should be `None`, matching the `BatchId::Decryption` path which already discards the blame for exactly this reason.

### Proof of Concept
1. Honest participant Alice encrypts her share to victim Bob: `EncryptedMessage { key: K = kG, pop: σ_A, msg: ct }`, broadcast normally.
2. Malicious participant Eve observes `K` and sends to Bob `EncryptedMessage { key: K, pop: garbage, msg: b"\xff…" }` (non-canonical scalar bytes).
3. Bob's `calculate_share` calls `decrypt` → computes `proof.key = enc_key_Bob * K`, queues the (invalid) PoP, then `C::F::from_repr(b"\xff…")` fails → returns `InvalidShare { participant: Eve, blame: Some(proof) }` before `batch.verify_with_vartime_blame()` runs.
4. Bob broadcasts `proof` as a blame attestation. Eve computes `cipher(context, proof.key)` and decrypts Alice's `ct`, recovering `f_Alice(bob_index)`.
5. Eve repeats for `t` victims and every sender, interpolating each `f_s(0)` and summing to obtain the group private key.
