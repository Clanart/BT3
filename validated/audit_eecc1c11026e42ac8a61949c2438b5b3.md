This is exactly the read-only reentrancy pattern from the Hanji report, mirrored on-chain: `_cancelFromSource` cross-chain cancellation makes its "not-yet-filled" decision based on the destination's `_filled` storage slot, which is read via a raw ISMP GET storage proof rather than through any of the destination's own state-changing execution order. The direct analog worth flagging, however, is inside `_fillSameChain` itself, where the escrow value used to build the withdrawal (and by extension, what any external observer reads from the public `_orders` mapping) is computed **after** external, hook-capable token transfers have already fired.

### Title
Escrow accounting (`_orders`) is read/consulted after external token transfers instead of before, in `_fillSameChain` — ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` transfers output tokens to the beneficiary (including a raw `.call{value:}` to an attacker-controllable beneficiary address, or `safeTransferFrom` of an ERC-20 that may have transfer hooks) *before* it reads `_orders[commitment][token]` to compute the escrow amount to release, and *before* `_withdraw` performs the actual decrement of `_orders`. The `_filled[commitment]` write-reentrancy path is already hardened (CEI at the top of the function, confirmed by `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), but the `_orders` escrow mapping — a public, externally-readable state variable — is left stale (still showing the full pre-fill escrow) for the entire duration of the beneficiary/token callback window, matching the exact "state updated after external transfer" invariant break the Hanji report calls out for `getTraderBalance`.

### Finding Description [1](#0-0) 
In `_fillSameChain`, the beneficiary is paid via `beneficiary.call{value: beneficiaryTotal}("")` (native) or `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` (ERC-20), both of which can trigger externally-controlled code (a malicious `beneficiary` contract's `receive()`, or a token with transfer hooks). Only *after* this call does the function read `_orders[commitment][...]` to compute `escrowedAmount`, and the actual decrement of `_orders` happens later still, inside `_withdraw`: [2](#0-1) 
`_orders` is a state variable read by the public getter used by the SDK's own status checker: [3](#0-2) 
Any integration, downstream contract, or another IntentGatewayV2 order (e.g., a solver contract that also queries `_orders(commitment, token)` to size a collateralized action) that reads this mapping during the reentrant callback window sees the pre-fill escrow value even though the fill is already irreversibly in progress and the beneficiary has already received funds — an accounting invariant break identical in shape to `getTraderBalance` reporting a stale trader balance mid-transfer.

### Impact Explanation
Because `_filled[commitment]` is set at the very top of the function (CEI-compliant), a reentrant call into `fillOrder` for the *same* commitment is blocked. This limits the practical blast radius compared to the original write-reentrancy bugs the test suite fixed. The residual risk is specifically the read-only exposure of `_orders`: any code path — inside or outside this contract — that trusts `_orders(commitment, token)` as a live "is this order's escrow still available" signal during the beneficiary callback will observe stale, pre-decrement escrow. This does not by itself let an attacker double-spend the escrow (the eventual `_withdraw` decrement is still consistent), but it breaks the "exactly-once, correct-amount" observability guarantee for a value used by SDK tooling (`isOrderRefunded`) and any future/external contract-level integration that composes on top of `_orders`.

### Likelihood Explanation
Requires (a) an order whose `output.beneficiary` is a contract with a `receive()`/fallback (native output) or the output token has transfer hooks, and (b) some other logic — in this repo, currently only off-chain SDK tooling, but potentially any future on-chain integration — reading `_orders(commitment, token)` mid-callback. As a purely on-chain, single-transaction exploit against this contract's own funds, likelihood is low today because no other in-repo contract logic consumes `_orders` mid-callback; the concrete exposure is that a beneficiary contract can, during its `receive()`, observe/act on the stale escrow value for its own or another integration's benefit, and the pattern is only one refactor away from becoming exploitable if any future feature (e.g., collateralizing against unfilled escrow) is added.

### Recommendation
Apply the same CEI discipline already used for `_filled` to `_orders`: decrement `_orders[commitment][token]` for the amount being released *before* any external call in `_fillSameChain` (and symmetrically in `_fillCrossChain`), rather than deferring the mutation to `_withdraw`, which currently runs after all beneficiary transfers. If the current escrow-then-withdraw ordering is intentional for partial-fill accounting, at minimum ensure no other function (on-chain or documented for off-chain reliance) treats `_orders` as safe to read mid-transaction, and document the reentrancy-window caveat prominently next to the public mapping declaration.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with a `receive()` that calls back into `IntentGatewayV2`/an external contract reading `_orders(commitment, inputToken)` or `_partialFills`.
2. Attacker (as `order.user`) places a same-chain order with `output.beneficiary = MaliciousBeneficiary`, native ETH output, ERC-20 input escrowed via `placeOrder`.
3. A solver calls `fillOrder`, which reaches `_fillSameChain`; the `beneficiary.call{value: beneficiaryTotal}("")` at [4](#0-3)  triggers `MaliciousBeneficiary.receive()`.
4. Inside `receive()`, `MaliciousBeneficiary` reads `_orders(commitment, inputToken)` via the auto-generated public getter (or an external contract that has cached/observes this mapping) and sees the full pre-fill escrow amount, even though the beneficiary has already been paid and the order is about to be finalized — demonstrating the stale-read window that mirrors the Hanji `getTraderBalance` read-only reentrancy class.

This is a narrower, currently lower-severity analog than the original write-reentrancy bug (which is already fixed per `IntrinsicIntentsReentrancyTest.sol`); I could not find an in-repo on-chain consumer of `_orders` mid-callback that would translate this directly into fund loss today, so the fund-loss impact is not fully provable from local code alone — only the stale-read/broken-observability invariant is demonstrable.
