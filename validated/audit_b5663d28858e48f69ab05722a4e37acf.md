## Analysis

I evaluated the report's core invariant break: **an operation commits to a decision (redeeming/issuing shares) based on state that is captured at one point in time, but an attacker can mutate the underlying state (share price) between that capture and the final action, silently corrupting the outcome (loss of funds).**

I searched `Kirstentat/desktop--016` for an equivalent "decide against stale state, execute against fresh state" pattern. I found one directly analogous, code-supported mechanism: `applyPatchToIndex` in `app/src/lib/git/apply.ts`.

- The user's line/hunk selection (`WorkingDirectoryFileChange.selection`) is computed by the UI against a diff that was fetched earlier and cached in Redux state (`updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3404-3465`).
- At commit time, `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) **re-fetches a brand-new diff** from disk via `getWorkingDirectoryDiff(repository, file)`, then calls `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129-232`), which re-applies the **stale, UI-captured selection indices** (`file.selection.isSelected(absoluteIndex)`, `absoluteIndex = hunk.unifiedDiffStart + lineIndex`) against the **hunk offsets of the newly-fetched diff**.
- Nothing in this path verifies that the freshly fetched diff's hunk boundaries/line offsets still match the diff the user actually reviewed and hand-selected lines from.

This mirrors the report's essence — a value (share price / diff-offset mapping) is captured, an attacker-influenced mutation occurs in the gap, and the final action (deposit/shares → commit/patch) is executed using an index that no longer means what it meant when the decision was made — silently producing wrong output (wrong shares → wrong committed content) with no validation catching the mismatch.

However, I want to be explicit about the gap in this analog relative to the "Valid Impact" bar: to actually mutate the on-disk file content between the user's line-selection and clicking "Commit," you generally need something *already running on the user's machine* (an editor autosave, a build watcher, a `post-checkout`/`post-merge` git hook from a cloned malicious repo, etc.). The `interceptHooks` list in `createCommit` (`app/src/lib/git/commit.ts:58-65`) only intercepts `pre-commit`/`prepare-commit-msg`/`commit-msg`/`post-commit`/`post-rewrite`/`pre-auto-gc` — it does **not** intercept `post-checkout` or `post-merge`, meaning those hooks (which a malicious/cloned repository can ship) run in the background, uncontrolled by Desktop's UI, and can modify working-directory files at any time, including in the window between when Desktop renders a diff and when the user clicks "Commit" on a partial selection.

This makes the primitive attacker-controlled-repo-triggered (a hook shipped in a cloned/fetched repository), not merely "local access," which satisfies the impact criteria of "the result is ... silent corruption of what the user commits."

I was not able to fully verify, within available tool budget, the exact timing window in the UI (e.g., whether Desktop always re-fetches/re-renders the diff and invalidates a stale selection object before allowing "Commit" to be clicked), which would be necessary to confirm real-world exploitability end-to-end. That verification requires either running the app or deeper tracing of the Commit button's enablement logic and the `WorkingDirectoryFileChange` object identity/liveness checks in `git-store.ts`/`app-store.ts`, which I could not fully complete in this pass.

### Title
Partial-commit patch application re-applies stale UI line-selection offsets against a freshly re-fetched diff, risking silent commit of unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines/hunks of a modified file ("partial commit"), Desktop's `applyPatchToIndex` re-fetches the file's diff from disk immediately before building the patch, but reuses the `DiffSelection` (a set of absolute line indices) that was computed against the diff shown earlier in the Changes view. If the working-directory file is mutated between the time the diff was rendered/selected and the time the user clicks "Commit" — for example by a `post-checkout` or `post-merge` git hook shipped in a cloned/fetched malicious repository — the hunk offsets in the newly-fetched diff can shift relative to the offsets the selection was built against, causing `formatPatch` to select different underlying lines than the ones the user actually reviewed and checked in the UI.

### Finding Description
- The UI computes and caches a diff for the currently selected file via `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404-3465`), and the user builds a `DiffSelection` against that diff's hunk `unifiedDiffStart`/`unifiedDiffEnd` offsets (see usage patterns in `app/test/unit/patch-formatter-test.ts:65-71`). [1](#0-0) 
- At commit time, `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) invokes `applyPatchToIndex` for every file with a partial selection. [2](#0-1) 
- `applyPatchToIndex` re-fetches the diff from disk at commit-time (`getWorkingDirectoryDiff`), independent of the diff the user actually saw, then formats the patch by reapplying the caller-supplied `file.selection` against this new diff's hunks. [3](#0-2) 
- `formatPatch` computes `absoluteIndex = hunk.unifiedDiffStart + lineIndex` from the *new* diff and looks up `file.selection.isSelected(absoluteIndex)` from the *old* selection object — there is no check that the new diff's structure (hunk count, line offsets, line content) still corresponds to what the selection was built from. [4](#0-3) 
- Desktop's git-hook interception for `createCommit` only covers `pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-rewrite`, and `pre-auto-gc` — it does not intercept `post-checkout` or `post-merge`, which are hooks that can be shipped inside a cloned/fetched repository (`.git/hooks/post-checkout`, `.git/hooks/post-merge`) and can silently rewrite tracked files in the working directory outside of any Desktop-mediated action. [5](#0-4) 

The broken invariant: *"the set of lines the user visually reviewed and explicitly selected for inclusion is the exact set of lines included in the resulting patch."* Existing guards (`--unidiff-zero`, `--whitespace=nowarn`, hook interception for commit-time hooks) do not address this because they operate on the already-mismatched diff/selection pairing and do not validate diff-identity (e.g., a content or hash check) between the diff a selection was derived from and the diff used to build the final patch.

### Impact Explanation
If exploited, the user could unknowingly commit and subsequently push content they never reviewed or intended to include — a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact class. Because commits are cryptographically identified by content, this could also let a malicious repository (via its own hooks) inject unreviewed lines into a user's commit that then gets pushed upstream, potentially to a shared/protected branch.

### Likelihood Explanation
Likelihood is constrained by the need for a background process (most plausibly a `post-checkout`/`post-merge` hook from a cloned/fetched malicious repository, since these are not intercepted/sandboxed by Desktop) to modify the target file in the narrow window between diff-render and clicking "Commit" while a partial selection is in effect. This requires the user to be actively doing a partial/line-level commit (a less common but supported workflow) and for the hook-triggered write to land within that window, so the practical likelihood is moderate-to-low without further confirmation of the exact UI timing/invalidation behavior — a point I could not fully verify with the available tools.

### Recommendation
- Before applying a partial-selection patch, re-validate that the freshly fetched diff used to build the patch is structurally identical (e.g., compare hunk headers/line content or a hash of the pre-selection diff) to the diff the `DiffSelection` was derived from; if it differs, abort and force the UI to refresh the diff and require the user to re-select.
- Alternatively, avoid the redundant re-fetch in `applyPatchToIndex` and always operate on the exact diff object that was used to render the selection UI, threading it through instead of calling `getWorkingDirectoryDiff` again.
- Consider intercepting/sandboxing `post-checkout` and `post-merge` hooks similarly to how `pre-commit`/`post-commit` are already intercepted, to prevent repository-supplied hooks from silently mutating the working directory outside of user-initiated, reviewable actions.

### Proof of Concept
Conceptual reproduction (not independently executed in this session):
1. Clone a malicious repository containing a `.git/hooks/post-merge` (or `post-checkout`) script that, after a delay, silently appends/reorders lines in a tracked file the user is likely to edit.
2. In Desktop, modify that file and open the Changes diff; select only specific lines/hunks for a partial commit.
3. Before clicking "Commit," let the hook fire in the background (or the timing window naturally elapses) and shift the file's line offsets.
4. Click "Commit." `applyPatchToIndex` re-fetches the diff and reapplies the stale `DiffSelection` indices against the new hunk layout, producing a patch that stages different lines than the ones visually checked in the UI.
5. Inspect the resulting commit content (`git show`) to confirm it differs from the lines the user selected in the Changes view.
