## Finding [1](#0-0) 

### Title
Hyperbridge accepts OP-Stack `FaultDisputeGame` root claims as final state merely because they are "not yet challenged," letting a fresh, disputable claim be trusted before OP's own dispute window resolves - (File: `modules/ismp/clients/optimism/src/lib.rs`)

### Summary
`verify_optimism_dispute_game_proof` / `verify_not_challenged` accept an OP Stack dispute-game root claim as a trusted `IntermediateState` as soon as a storage proof shows `claimData.length == 1` (`FAULT_DISPUTE_CLAIM_DATA_SLOT`) — i.e. no `move()` has been made against it yet at the specific L1 block used in the proof. [2](#0-1)  This is the same class of flaw as the external report: a transient "not-yet-countered" signal is treated as equivalent to final correctness, letting the party who benefits from the false claim (here, whoever submits the state update before an honest challenger acts) win the race and get the state trusted.

### Finding Description
OP Stack's `FaultDisputeGame` is permissionless: anyone can create a game with an arbitrary root claim, and the claim is only proven wrong if a challenger disputes it within the game's live clock (a multi-day window on mainnet). "Unchallenged" is a point-in-time condition, not a finality signal — a claim can be perfectly valid-looking (`claimData.length == 1`) for the entire time between creation and the moment a challenger's `move()` lands, which is *by design* up to the full duration of the dispute clock.

Hyperbridge's `verify_optimism_dispute_game_proof` only checks this transient "unchallenged" condition at the specific L1 root height supplied in the proof, and does not require the game to be resolved (`status == DEFENDER_WINS`) or require any minimum elapsed time/clock-exhaustion before trusting the claim: [3](#0-2) 

Once accepted, the resulting `IntermediateState`/`StateCommitment` is stored on Hyperbridge and becomes usable for verifying requests, responses, and timeouts as soon as Hyperbridge's own, independently configured `challenge_period` elapses — a value governance sets per state machine and which has no structural relationship to OP's actual fault-proof clock: [4](#0-3) [5](#0-4) 

So there are two independent, uncoordinated clocks: (1) OP's own dispute-game clock (multi-day, by design, to give real challengers time to react), and (2) Hyperbridge's `ChallengePeriod`/`challengePeriod()` delay before a stored `StateCommitment` can be used to verify proofs. Nothing ties Hyperbridge's delay to "the OP game must actually resolve, or the OP dispute window must fully elapse." If Hyperbridge's configured `challenge_period` for the OP state machine is shorter than the real time an honest challenger needs to notice and successfully dispute a bad root claim (which the OP protocol explicitly assumes can take up to the full clock duration), Hyperbridge will treat the attacker's fabricated `state_root` as final and let it be used to verify withdrawal/request/response/timeout proofs before the real OP dispute game is resolved.

### Impact Explanation
This directly enables false remote state to become trusted on Hyperbridge — a state proof/state-commitment integrity break. Once a fabricated `state_root` for an OP-stack chain is accepted as an `IntermediateState`/`StateCommitment` and Hyperbridge's (unrelated, potentially much shorter) challenge period elapses, an attacker can construct arbitrary storage-proof-backed request/response/timeout messages against that fabricated root (e.g. a fake `RequestReceipts` slot to claim relayer rewards via `process_outbound_request_delivery_claim`, or a fake withdrawal proof) and have them accepted by `pallet-ismp`/`HandlerV2`, since those handlers only require the (irrelevant) Hyperbridge challenge period to have elapsed, not that the underlying OP dispute game is actually resolved. This is unauthorized/false state acceptance leading to fund loss, matching the bounty's "false proof/state acceptance" and "stealing or loss of funds" categories.

### Likelihood Explanation
Creating an OP `FaultDisputeGame` with an arbitrary root claim is fully permissionless on L1 (no privileged actor needed) — this is a core, intended property of OP Stack fault proofs, not a "malicious peer" assumption within Hyperbridge. The only additional requirement is that whoever submits the `ConsensusMessage`/`OptimismDisputeGameProof` to Hyperbridge does so while the game is still in its unchallenged window — a normal, expected state for any freshly created game, not a rare race condition, because OP deliberately gives challengers a multi-day window to react. The exploitability hinges entirely on Hyperbridge's own `ChallengePeriod` configuration for the relevant OP state machine; the code contains no enforcement or cross-check tying it to OP's actual dispute-resolution time, and `ChallengePeriod` is a routinely configurable, non-zero-tolerant value.

### Recommendation
`verify_optimism_dispute_game_proof` should not accept a game merely because it is unchallenged at proof time. It should instead require proof that the game has fully resolved (`status == DEFENDER_WINS` and `resolvedAt` set) or that the game's `createdAt` plus its maximum clock duration has fully elapsed with no successful challenge, mirroring the same finality guarantee OP Stack itself relies on before treating an output root as canonical. Additionally, Hyperbridge's `challenge_period` for OP-stack-consensus state machines should be bound to be at least as long as the OP dispute game's configured maximum resolution time, so Hyperbridge's own challenge window cannot expire before the source chain's dispute window does.

### Proof of Concept
1. Attacker calls OP `DisputeGameFactory.create()` on L1 with an arbitrary/incorrect root claim for a target L2 block (permissionless, no bond restrictions preventing claim content).
2. Immediately (before any challenger `move()`), attacker/relayer builds an `OptimismDisputeGameProof` against the current L1 state: `dispute_factory_proof`, `game_impl_proof`, `proxy_account_proof`, and `challenge_proof` all prove `claimData.length == 1` for the new game — this passes `verify_not_challenged` trivially since no move has occurred yet.
3. Relayer submits this as a `ConsensusMessage` to Hyperbridge's `pallet-ismp`; `verify_optimism_dispute_game_proof` accepts it and returns an `IntermediateState` carrying the attacker's fabricated `header.state_root`, which gets stored as the `StateCommitment` for that OP height.
4. After Hyperbridge's configured `challenge_period` for that state machine elapses (independent of, and potentially much shorter than, OP's actual multi-day dispute clock), any storage proof rooted at the fabricated `state_root` becomes acceptable to `pallet-ismp`/`HandlerV2` request/response/timeout handlers, letting the attacker fabricate receipts/withdrawal data to steal relayer rewards or drain escrowed funds — all while the real OP `FaultDisputeGame` for that claim is still live and could later resolve as `CHALLENGER_WINS`, by which point Hyperbridge has already acted on the false state.

pub fn verify_optimism_dispute_game_proof<H: Keccak256 + Send + Sync>(
	payload: OptimismDisputeGameProof,
	root: H256,
	dispute_factory_address: H160,
	game_type_configs: Vec<GameTypeConfig>,
	consensus_state_id: ConsensusStateId,
) -> Result<IntermediateState, Error> {
	// Find the per-game-type configuration for this proof's game type.
	let game_config = game_type_configs
		.iter()
		.find(|c| c.game_type == payload.game_type)
		.ok_or(Error::UnsupportedGameType(payload.game_type))?
		.clone();

	let factory_storage_root =
		get_contract_account::<H>(payload.dispute_factory_proof, &dispute_factory_address.0, root)?
			.storage_root
			.0
			.into();
	let l2_block_hash = Header::from(&payload.header).hash::<H>();

	let root_claim = calculate_output_root::<H>(
		payload.version,
		payload.header.state_root,
		payload.withdrawal_storage_root,
		l2_block_hash,
	);

	let game_uuid = get_game_uuid::<H>(payload.game_type, root_claim, payload.extra_data);

	let dispute_game_key = derive_map_key::<H>(game_uuid.0.to_vec(), DISPUTE_GAMES_SLOT);

	// Does the dispute game's unique identifier exist in the _disputeGames map?
	let proof_value = match get_value_from_proof::<H>(
		dispute_game_key.0.to_vec(),
		factory_storage_root,
		payload.dispute_game_proof,
	)? {
		Some(value) => value.clone(),
		_ => Err(Error::DisputeGameIdMissing)?,
	};

	let mut encoded_game_id = <alloy_primitives::Bytes as Decodable>::decode(&mut &*proof_value)
		.map_err(|_| Error::DecodeDisputeGameId(format!("{:?}", &proof_value)))?
		.0
		.to_vec();

	let game_id = get_game_id(payload.game_type, payload.timestamp, payload.proxy);
	let game_id_bytes = game_id.to_big_endian();

	// Pad the encoded game id gotten from proof with zeros so it becomes 32 bytes long
	(0..game_id_bytes.len().saturating_sub(encoded_game_id.len()))
		.for_each(|_| encoded_game_id.insert(0, 0));

	// Derived game id must be equal to encoded game id
	if encoded_game_id != game_id_bytes {
		Err(Error::DisputeGameIdMismatch)?
	}

	// Bind the proxy's storage layout to the expected implementation by proving
	// `gameImpls[game_type]` in the factory matches the configured address. This is what makes
	// the per-kind "not challenged" check below meaningful: a factory upgrade that swaps
	// `gameImpls` to an implementation with a different layout would fail this check.
	let game_type_key = {
		let mut key = vec![0u8; 32];
		key[28..].copy_from_slice(&payload.game_type.to_be_bytes());
		derive_map_key::<H>(key, GAME_IMPLS_SLOT)
	};
	let impl_value = get_value_from_proof::<H>(
		game_type_key.0.to_vec(),
		factory_storage_root,
		payload.game_impl_proof,
	)?
	.ok_or(Error::GameImplsMissing)?;
	let impl_address = decode_address_from_storage_value(&impl_value)?;
	if impl_address != game_config.expected_impl {
		Err(Error::GameImplMismatch {
			game_type: payload.game_type,
			actual: impl_address,
			expected: game_config.expected_impl,
		})?
	}

	// Prove the proxy account, then verify "not challenged" against its storage root.
	verify_not_challenged::<H>(
		&game_config.kind,
		root,
		payload.proxy,
		payload.proxy_account_proof,
		payload.challenge_proof,
	)?;

	Ok(IntermediateState {
		height: StateMachineHeight {
			id: StateMachineId {
				// note: This will state machine id should not be used to store the state commitment
				state_id: StateMachine::Evm(Default::default()),
				consensus_state_id,
			},
			height: payload.header.number.low_u64(),
		},
		commitment: StateCommitment {
			timestamp: payload.header.timestamp,
			overlay_root: None,
			state_root: payload.header.state_root,
		},
	})
}

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
