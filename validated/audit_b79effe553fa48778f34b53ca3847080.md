### Title
`SignableTransaction` provides no bound on the actual fee paid: any excess input value is silently burned to miners when change is absent or below dust - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The referenced Aave finding is a "missing user-specified bound" bug: the caller cannot cap the worst-case economic outcome of an operation, because the bound (`slippageTolerance`) is a global operator-set value that can be stale. The same shape exists in `bitcoin-serai`'s transaction builder: `SignableTransaction::new` lets the caller specify `fee_per_vbyte` (the *rate*), but provides no parameter bounding the *actual* fee paid. When `change` is `None`, the entire `input_sat - payment_sat` difference becomes fee (documented at lines 143-147 but with no opt-out or cap), and when change *is* provided but the leftover is below `DUST`, that leftover is also folded into the fee (lines 224-235). The advertised cost `needed_fee()` can therefore diverge arbitrarily from `fee()`.

### Finding Description
`SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)` computes `needed_fee = fee_per_vbyte * vbytes` (line 206) and enforces only a *minimum* (`TooLowFee`, lines 211-213) and solvency (`NotEnoughFunds`, lines 215-221). There is no maximum-fee check:

- If `change` is `None`, the constructed transaction contains only the payment/OP_RETURN outputs, so `fee() = sum(prevouts) - sum(outputs)` (lines 137-141) equals `input_sat - payment_sat`, which can exceed `needed_fee` by an unbounded amount.
- If `change` is `Some` but `input_sat - (payment_sat + fee_with_change) < DUST`, the change output is silently dropped (lines 228-234) while `weight`/`needed_fee` are left at the no-change values computed at line 204-206; the would-be change amount is added to the fee with no bound.
- Inputs are `ReceivedOutput`s, which can be materialized from untrusted bytes via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs` lines 122-134) — including an attacker-controlled `output.value`. A `ReceivedOutput` whose `output.value` is inflated relative to what the signer believes will cause `SignableTransaction` to build a transaction committing the excess to miners, and `TransactionSignMachine::sign` will sign it with `Prevouts::All` (lines 373-390) without any independent check that the fee matches `needed_fee`. Notably, `sign` even `panic!`s if the signer tries to pass their own `msg` (lines 360-362) — the signer cannot substitute or constrain the message/fee they are authorizing, exactly analogous to `rebalance()` signers being unable to pass their own slippage bound.

### Impact Explanation
Analogous to the Aave issue's "user repays more than expected": a transaction is signed that pays a fee far above `needed_fee`. If a `ReceivedOutput`'s value was sourced from untrusted serialization, an inflated reported value converts directly into excess miner fee — concrete funds loss, not merely a stuck transaction. Even absent adversarial bytes, any caller feeding inputs whose sum exceeds `payments + needed_fee` without a change output has the entire remainder burned, with `fee()` only discoverable after the fact.

### Likelihood Explanation
Medium: it requires either untrusted/mis-stated `ReceivedOutput` values flowing into `SignableTransaction::new` (the read API is reachable from untrusted bytes) or a caller omitting `change` while inputs exceed payments — the same "stale/operator-set parameter the user can't bound" precondition as the original finding.

### Recommendation
Add a `max_fee` (or explicit acknowledgment of the implied fee) parameter to `SignableTransaction::new` and error when `input_sat - payment_sat - output_sat` exceeds it; alternatively, refuse `change: None` constructions unless the caller asserts the fee, and expose/assert the actual `fee()` before signing so `TransactionSignMachine::sign` commits to a bounded cost.

### Proof of Concept
```rust
// Two ReceivedOutputs totaling 200_000 sats are fed to the builder;
// only 100_000 is intended to be spent, with change omitted.
let inputs = vec![received_output_a, received_output_b]; // 200_000 sats total
let payments = vec![(dest_script, 100_000)];

// Caller sets a reasonable rate; needed_fee ends up ~few hundred sats.
let tx = SignableTransaction::new(inputs, &payments, None, None, FEE).unwrap();

// needed_fee reports the rate-derived cost...
assert!(tx.needed_fee() < 1_000);
// ...but the actual signed fee is the entire remainder:
assert_eq!(tx.fee(), 100_000 - tx.needed_fee() + tx.needed_fee());
// i.e. ~99_xxx sats paid to miners, unbounded by any caller parameter.

// Any participant completing TransactionSignMachine::sign commits to this
// unconditionally (Prevouts::All, SIGHASH_ALL) and cannot inject a bound.
```

Caveat: if the inputs' values are supplied honestly and the caller deliberately omits change, the excess fee is deterministic and documented — the exploitable case requires mis-stated `ReceivedOutput` values or a caller who reasonably expects `fee_per_vbyte` to bound the outcome, mirroring the original report's "the bound exists but the user can't control it" structure.
