### Title
PedPoP blame proofs leak the ECDH key for a message whose PoP was never verified, revealing other participants' secret shares - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`KeyMachine::calculate_share` decrypts every received `EncryptedMessage` and immediately produces an `EncryptionKeyProof` containing the recipient's ECDH shared point, while the Schnorr proof-of-possession that authorizes use of that per-message key is only queued into a `BatchVerifier` and checked later. If the share bytes fail to decode, `calculate_share` returns early with `blame: Some(blame)` — before `batch.verify_with_vartime_blame()` ever runs — publishing a blame proof for a message whose PoP may be invalid. This re-enables the exact attack the PoP was added to prevent: reusing another participant's per-message encryption key to make the victim's blame proof reveal that participant's encrypted secret share.

### Finding Description
In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:479-500), the PoP signature is queued via `msg.pop.batch_verify(...)`, but the function unconditionally computes `key = ecdh::<C>(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }`. In `calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499), `C::F::from_repr` failing at line 480-482 returns `PedPoPError::InvalidShare { blame: Some(blame) }` immediately, so the batch verification at line 493 — the only place the PoP is actually checked — is skipped. The processor then serializes this blame into `ProcessorMessage::InvalidShare` (processor/src/key_gen.rs:419-425), making `proof.key = victim_enc_key * attacker_supplied_key` public.

The comments at encryption.rs:84-90 describe this exact scenario — Eve reusing Alice's key X so that Bob's blame "would reveal bX, revealing Alice's message to Bob" — and state the PoP prevents it. The prevention only holds if the PoP is verified before the blame proof is emitted; the early error return breaks that invariant. Additionally, `blame_internal` (lib.rs:582-593) will still correctly identify the attacker as faulty (the garbage share fails `from_repr`), so the attacker is slashed but the victim's share is already leaked — the PoP was specifically meant to stop the side-effect disclosure, not just assign blame.

### Impact Explanation
A participant Eve copies Alice's `EncryptedMessage` (public `key` field `K_A`), swaps in garbage ciphertext, and sends it to victim Bob as her own share. Bob's `calculate_share` returns `blame: Some(proof)` where `proof.key = b·K_A` (b = Bob's encryption key) before the PoP is checked. Once published, anyone computes `cipher(context, b·K_A)` and decrypts Alice's original ciphertext to Bob, recovering the secret share Alice generated for Bob. Combined with shares Eve collects legitimately (or by repeating against multiple recipients), this leaks threshold secret-share material that the DKG encryption was designed to keep confidential — a confidentiality breach of the DKG equivalent to the CVE's unauthorized-information disclosure.

### Likelihood Explanation
Any DKG participant can send a malformed `EncryptedMessage`; copying a public `key` field and corrupting the ciphertext requires no privileged access. The trigger (decoded bytes failing `from_repr`) occurs with overwhelming probability for random garbage (a random 32-byte string is almost never a canonical scalar for 25519-class fields), and the attacker's slashing does not prevent the one-shot leak, which is irreversible.

### Recommendation
Do not attach an `EncryptionKeyProof` to the error until the PoP has been verified. Concretely, in `calculate_share`, either (a) verify each message's PoP synchronously (or run `batch.verify_with_vartime_blame()` for the `Decryption` statements) before emitting `blame: Some(...)` on the `from_repr` / share-validation error paths, or (b) make `Encryption::decrypt` return a proof only after confirming `msg.pop.verify(...)` for that message, returning `blame: None` when the PoP fails so no ECDH material is ever revealed for an unauthenticated key.

### Proof of Concept
1. Run a PedPoP DKG with participants Alice (1), Bob (2), Eve (3). Observe Alice's broadcast `EncryptedMessage` to Bob: `msg_A = { key: K_A, pop: σ_A, msg: c_A }` (public fields via `EncryptedMessage::read`/serialize).
2. Eve constructs `EncryptedMessage { key: K_A, pop: <any signature>, msg: <32 garbage bytes> }` and submits it as her share to Bob. (Garbage can also be produced by flipping bytes of `c_A`, which additionally invalidates the PoP since `pop_challenge` binds `msg` at encryption.rs:319.)
3. Bob calls `calculate_share` → `encryption.decrypt` returns `proof = EncryptionKeyProof { key: b·K_A, ... }` → `from_repr` fails → `Err(InvalidShare { participant: Eve, blame: Some(proof) })`; the PoP batch check at lib.rs:493 never runs.
4. Bob publishes `proof.serialize()` in `ProcessorMessage::InvalidShare` (key_gen.rs:419-425). Anyone reads `proof.key`, runs `cipher::<C>(context, &proof.key)`, and applies the keystream to `c_A`, recovering Alice's secret share to Bob — the leak the PoP (encryption.rs:84-90) was introduced to prevent.
