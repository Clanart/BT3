### Title
`ThresholdKeys::read` accepts identity verification shares and a zero secret share, allowing a crafted key set whose group key is the identity - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the reported "missing check on a retrieved address/value," `ThresholdKeys::read` deserializes `secret_share` and per-participant `verification_shares` and constructs a `ThresholdKeys` via `ThresholdKeys::new` without ever checking that the resulting values are non-zero/non-identity. Unlike the FROST preprocess path, which deliberately rejects identity points, this path uses `Ciphersuite::read_G` (canonicality only, no identity check) and `read_F` (canonicality only, no zero check). A crafted serialization can therefore produce a `ThresholdKeys` whose `group_key` is the identity point, corresponding to a group secret of `0` — a key anyone can sign under.

### Finding Description
`ThresholdKeys::read` reads each verification share with `<C as Ciphersuite>::read_G(reader)?`, which only checks canonical encoding, not identity (`crypto/dkg/src/lib.rs:620-623`, `crypto/ciphersuite/src/lib.rs:91-100`). The secret share is read with `C::read_F` with no zero check (`crypto/dkg/src/lib.rs:618`). `ThresholdKeys::new` then computes `group_key` as the interpolation of `verification_shares[1..=t]` without checking the result is non-identity (`crypto/dkg/src/lib.rs:376-378`), and never checks `secret_share != 0` or that `verification_shares[i] == generator * secret_share` for the local participant.

Compare with `Curve::read_G` used for all network-received FROST commitments, which explicitly rejects identity (`crypto/frost/src/curve/mod.rs:125-131`). The deserialization path has no equivalent guard. Additionally, `Interpolation::Constant` coefficients are read with `read_F` and can be zero (`crypto/dkg/src/lib.rs:607-612`), so `interpolation_factor` may return `0`, nullifying a participant's contribution to `group_key` (`crypto/dkg/src/lib.rs:226-248`).

### Impact Explanation
An attacker who supplies the serialized `ThresholdKeys` bytes (the threat model explicitly includes untrusted bytes fed to `ThresholdKeys::read`) can set all `verification_shares` to the identity point. The resulting `group_key` is the identity, i.e. a public key with discrete logarithm `0`. Any Schnorr/FROST signature under a zero private key is trivially forgeable by anyone (`s = r`, `R = rG`), so funds controlled by this group key — e.g., a Bitcoin wallet whose script commits to this key — are stealable by any observer, and signatures "of the group" can be forged. If shares are set to identity while `secret_share` is nonzero, `verify_share` fails deterministically, giving a selective DoS of the signer as well.

### Likelihood Explanation
Requires an attacker to control the bytes passed to `ThresholdKeys::read`, which normally reads locally produced DKG output. Where serialized keys transit untrusted storage, backups, or are reconstructed from peer-supplied data, this is reachable with a fully crafted input — no probabilistic or collusion requirements. Severity is bounded by the need to corrupt the key blob itself, hence Medium rather than High.

### Recommendation
In `ThresholdKeys::new` (or `ThresholdKeys::read`), reject:
- `secret_share == 0`,
- any `verification_shares[i]` that is the identity,
- `Interpolation::Constant` coefficients equal to `0`,
- a computed `group_key` that is the identity.

Optionally verify `verification_shares[params.i()] == C::generator() * secret_share` so a malformed blob fails fast instead of producing shares that can never combine into a valid signature.

### Proof of Concept
```rust
// Crypto: ciphersuite = C (e.g. Secp256k1 / Ristretto)
// Craft a serialized ThresholdKeys for t = 1, n = 1, i = 1:
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref());          // secret_share = 0
buf.extend(C::G::identity().to_bytes().as_ref());   // verification_shares[1] = identity

// Accepted without error:
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));

// group_key == identity == G * 0, so a Schnorr signature with private key 0
// (R = rG, s = r) verifies under this group key for any challenge/message.
```
