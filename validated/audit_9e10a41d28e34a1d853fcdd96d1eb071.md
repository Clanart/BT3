### Title
Unchecked multiplication overflow in gaskv per-byte gas accounting can wrap gas cost to a near-zero value, allowing gas-metering bypass - (File: sei-cosmos/store/gaskv/store.go)

### Summary
`sei-cosmos/store/gaskv/store.go` computes the per-byte gas charge for `Get`, `Set`, and iterator `Next` operations as `gasConfig.ReadCostPerByte*types.Gas(len(...))` / `gasConfig.WriteCostPerByte*types.Gas(len(...))`, a raw `uint64` multiplication performed before the result is handed to `ConsumeGas`. The developers themselves flag this as unresolved with `// TODO overflow-safe math?` comments at both `Get` and `Set`. Unlike additions inside `basicGasMeter.ConsumeGas`, which are checked via `addUint64Overflow` and panic with `ErrorGasOverflow` on wraparound, this multiplication has no such guard, so if `ReadCostPerByte`/`WriteCostPerByte` (module-configured constants, typically small, e.g. 1–3) is multiplied by a sufficiently large `len(value)`, the uint64 product can wrap around to a small number, silently under-charging gas for the operation actually performed.

### Finding Description
This mirrors the bug class of CVE-2019-13445: a numeric input/size value flows into an unchecked integer multiplication, producing a wrapped, attacker-influenced small result instead of erroring out or saturating. Here, `len(key)`/`len(value)` (bounded per write by `types.AssertValidValue`/state size limits, but in aggregate across many keys/iterator steps within a single transaction, cumulative uint64 gas consumed can still be engineered close to overflow boundaries through the additive accumulation in `basicGasMeter.consumed`) combined with a per-byte cost constant is multiplied without an overflow check. While a single `Set`/`Get` value is unlikely to reach the ~1.8×10^19-per-byte-cost boundary needed to overflow uint64 directly (since state values are bounded well below `math.MaxUint64` bytes), the missing check at this specific multiplication site is nonetheless a real latent primitive: any future gas-config constant increase, or any code path that constructs `len(...)` from an unbounded/attacker-influenced accumulator (e.g., precompile-side gas math elsewhere that reuses the same unguarded-multiplication pattern, as also seen in `x/evm/keeper/params.go`'s `GetCosmosGasLimitFromEVMGas`/`getEvmGasLimitFromCtx` using big.Int-bounded conversions but relying on manual `Cmp` checks rather than the KV store's raw uint64 math) inherits this unguarded arithmetic.

### Impact Explanation
If exploitable, gas under-accounting for storage reads/writes allows a transaction to perform disproportionately expensive state I/O while being charged near-zero metered gas, which is a gas/fee-accounting bypass. At scale this could let a single transaction perform enough KV work to slow block processing well past the halt/delay threshold, since gas metering is the primary defense against unbounded per-block work in the OCC/state-machine execution path.

### Likelihood Explanation
Likelihood is low-to-moderate: exploiting this requires reaching a `len(...)` or gas-config-constant combination whose product overflows `uint64` (~1.8×10^19), which is far beyond any single value size sei-chain currently permits in one KV operation. The primitive is real and unguarded (confirmed by the maintainers' own `// TODO overflow-safe math?` annotations), but current gas-config constants and value-size limits keep it from being triggered with realistic inputs today; it becomes exploitable only if per-byte cost constants or value-size limits are raised, or if a caller can supply an inflated `len(...)` through some other unbounded aggregation.

### Recommendation
Add explicit overflow-checked multiplication (mirroring `addUint64Overflow`) before charging per-byte costs in `gaskv.Store.Get`/`Set` and `gasIterator.consumeSeekGas`, saturating to `math.MaxUint64` or panicking with `ErrorGasOverflow` on overflow, exactly as already done for the additive path in `basicGasMeter.ConsumeGas`.

### Proof of Concept
Not independently reproducible against current production constants — the value-length and per-byte-cost constants in use are far too small to reach the `uint64` overflow boundary in a single call. The exploitability of this analog is therefore unconfirmed at present configuration; it is flagged as a defense-in-depth gap explicitly acknowledged in-code (`// TODO overflow-safe math?`) rather than as a demonstrated, currently-triggerable critical/high vulnerability.

func (g *basicGasMeter) ConsumeGas(amount Gas, descriptor string) {
	g.lock.Lock()
	defer g.lock.Unlock()

	var overflow bool
	g.consumed, overflow = addUint64Overflow(g.consumed, amount)
	if overflow {
		g.consumed = math.MaxUint64
		g.incrGasExceededCounter("overflow", descriptor)
		panic(ErrorGasOverflow{descriptor})
	}
	if g.consumed > g.limit {
		g.incrGasExceededCounter("out_of_gas", descriptor)
		panic(ErrorOutOfGas{descriptor})
	}
}
