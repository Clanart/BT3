### Title
Missing domain separation in `SubstrateCalldata` signature payload allows cross-deployment signature/call replay - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
In `Pallet::on_accept`, when a cross-chain message carries optional `SubstrateCalldata`, the Ed25519/Sr25519/ECDSA signature is verified over `keccak_256((nonce, substrate_data.runtime_call.clone()).encode())` where `nonce` is only the beneficiary's local `frame_system` account nonce. [1](#0-0)  No chain id, `StateMachine`, pallet/contract address, or asset id is folded into the signed payload.

### Finding Description
The signed message `(nonce, runtime_call)` binds only to a numeric nonce and the raw SCALE-encoded call bytes — nothing chain- or pallet-specific. Contrast this with the sibling relayer pallet, which explicitly domain-separates its signed withdrawal/fee messages by including the `StateMachine` in the hashed payload (`message(nonce, dest_chain, beneficiary)` / `beneficiary_message(nonce, state_machine, beneficiary_address)`), and even has a regression test asserting "replayed signature from a different chain must be rejected". [2](#0-1) [3](#0-2) [4](#0-3) 

The `hyper-fungible-token` module has no such protection: the same `AccountId` (a Substrate keypair is chain-agnostic and commonly reused by users across parachains) can have the same nonce value on two different chains/pallet deployments (e.g. a fresh account with nonce 0 on both). The `data` field of the bridged `Message` — including `signature` and `runtime_call` — is fully attacker-controlled at send time (an attacker crafts their own `SendParams`/message on the source side); a valid signature that was publicly observed (e.g. from a block explorer showing the `PostRequest` body of a legitimate cross-chain call) can be copied verbatim into a new message targeting a different asset/chain deployment of this same pallet, and it will pass verification as long as the beneficiary's nonce on that destination happens to match. [5](#0-4) 

Because `runtime_call` is decoded with the destination chain's own `T::RuntimeCall` type (`T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)`), the exact same SCALE byte sequence can decode to a semantically different (or coincidentally identical, e.g. a `Balances::transfer_allow_death`) call on a different chain sharing similar pallet index ordering (this repo ships multiple Hyperbridge parachain runtimes, e.g. `gargantua` and `nexus`, that could plausibly share pallet indices for common pallets). [6](#0-5) 

### Impact Explanation
A replayed signature causes `on_accept` to dispatch an authenticated `RuntimeCall` as `RawOrigin::Signed(beneficiary)` on a deployment/chain the original signer never intended to authorize a call on. This is unauthorized execution under the beneficiary's identity on an unintended settlement context (different asset/chain instance), which can move funds or invoke other dispatchables the user did not approve for that specific chain — matching the "unauthorized transaction or execution" / "logic attacks" / "replay" impact categories.

### Likelihood Explanation
Exploitability requires: (1) the same public key/account controls a beneficiary account on two separate deployments of this pallet, which is common since Substrate account keys are freely reused across parachains, and (2) the nonce happening to coincide between the two chains at replay time — trivially true for any account that has not yet transacted on the second chain (nonce = 0 is the default and extremely common state). The attacker fully controls the cross-chain message contents on the sending side, so no relayer or node compromise is needed — only the ability to observe a previously broadcast signature (public by design, since it travels inside an on-chain `PostRequest` body) and resubmit it via a new legitimate bridge send. This is realistically exploitable, though it is probabilistic on nonce collision and requires the victim to actually use the signed-calldata feature on more than one chain sharing the pallet.

### Recommendation
Include chain/deployment-specific domain separation in the signed payload before hashing, e.g. `(genesis_hash_or_state_machine, pallet_instance_id/contract_address, nonce, runtime_call).encode()`, mirroring what `pallet-ismp-relayer` already does with `state_machine` in `message()`/`beneficiary_message()`. At minimum, bind the local `StateMachine` identifier (and ideally the source contract/asset id) into the hashed message so a signature is cryptographically scoped to exactly one settlement context.

### Proof of Concept
1. On chain A (asset X), a user signs `SubstrateCalldata { signature: Some(sig), runtime_call }` where `sig` = `Ed25519/Sr25519(keccak256((0u64, runtime_call).encode()))`, submitted through a legitimate cross-chain send and observed publicly in the resulting `PostRequest` body (as in the existing test `should_receive_asset_with_calldata`, which shows the exact construction of this payload). [7](#0-6) 
2. An attacker copies `signature` and `runtime_call` bytes unchanged into a new `Message.data` for a send targeting a different pallet deployment (different `local_asset_id`/chain) where the same beneficiary `AccountId` currently has `frame_system::account_nonce == 0`.
3. `on_accept` on the second deployment recomputes the same `(0, runtime_call).encode()` hash, verifies successfully against the same public key, and dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)` — even though the beneficiary never authorized any call on this second deployment/chain.
