Confirmed. The `withdraw()` function (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`) and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` both use raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the `success` boolean from the call itself — they never decode/verify the ERC20's returned `bool`. This is the exact bug class from the report: a call can "succeed" (not revert) while the token's `transfer` returns `false`, and the code has no way to detect that.

### Title
Escrow release and dust-sweep in `IntentGatewayV2.sol` (Tron) accept ERC20 `transfer` success without checking the returned boolean, permanently losing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed tokens to a beneficiary using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and gate the failure path solely on `success` (i.e., whether the call reverted), never decoding/inspecting the actual ABI-encoded `bool` return value. [1](#0-0) [2](#0-1)  Meanwhile, `placeOrder`'s escrow-in path in the same contract correctly uses `SafeERC20.safeTransferFrom`, which reverts on a `false` return. [3](#0-2)  This asymmetry is the local analog of the Vepoch.sol `transfer()`/`transferFrom()` unchecked-return-value pattern.

### Finding Description
`withdraw()` decrements the escrow accounting (`_orders[body.commitment][token] -= amount`), marks the order filled (`_filled[body.commitment] = beneficiary`), and emits `EscrowReleased`/`EscrowRefunded` regardless of whether the beneficiary actually received the tokens: [4](#0-3) 

The token transfer itself is:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted, not whether the token's `transfer` logic returned `true`. Per the ERC20 spec, a compliant token is permitted to return `false` on failure instead of reverting. In that case the low-level call completes normally (`success == true`) even though no tokens moved, so `withdraw()`, the transaction-fee release, and `SweepDust` all proceed to finalize state as if the transfer succeeded. [5](#0-4) 

This is the same class of file whose escrow-in path (`placeOrder`) explicitly uses `SafeERC20.safeTransferFrom` — which does decode and enforce the boolean return — showing the codebase is aware of the return-value hazard but failed to apply the same guard to the escrow-out (withdrawal/settlement) and dust-sweep paths. [6](#0-5) 

### Impact Explanation
This falls under "bridged assets... must move exactly once and only to the rightful beneficiary and amount" and "stealing or loss of funds." If the escrowed `token` is a strict-ERC20 implementation that returns `false` rather than reverting on transfer failure (e.g., paused token, blacklisted recipient, insufficient contract balance due to any prior accounting drift, or any token intentionally implementing false-on-failure semantics), the contract will:
- Mark the cross-chain settlement/refund as finalized (`_filled` set, escrow debited, `EscrowReleased`/`EscrowRefunded` emitted) even though the beneficiary received nothing.
- Permanently lock the tokens in the `IntentGatewayV2` contract with no recovery path, since the commitment is now considered settled and `withdraw` cannot be invoked again for the same commitment (`_orders[body.commitment][token] == 0` guard would reject retries, and `_filled` already set).

This is a direct fund-loss/fund-lock vulnerability reachable through the normal, unprivileged cross-chain settlement flow (`onAccept` triggered by the ISMP host after legitimate proof verification) — no malicious relayer, prover, or admin is required, only a token whose `transfer` can return `false`.

### Likelihood Explanation
The trigger condition depends on the specific ERC20 token configured for the order/escrow returning `false` instead of reverting — this is standard, spec-compliant ERC20 behavior for some tokens, not an exotic edge case. Given IntentGatewayV2 is designed to support arbitrary configured tokens per order (`order.inputs[i].token`), and the same file already treats this exact hazard as real enough to guard on the deposit side with `SafeERC20`, the omission on the withdrawal/sweep side is a directly exploitable gap whenever such a token is used, without requiring any privileged or adversarial actor.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (escrow release, fee release) and the `SweepDust` handler with `IERC20(token).safeTransfer(...)` (the `SafeERC20` library already imported and used elsewhere in this file), so that a `false` return value reverts the entire settlement instead of being silently treated as success.

### Proof of Concept
1. Deploy an ERC20 whose `transfer` returns `false` on failure (spec-compliant, non-reverting) and register it as an order input token.
2. Place a cross-chain order via `placeOrder` on the source chain, escrowing this token (`_orders[commitment][token] = amount`).
3. Have the destination fill the order, triggering the `RedeemEscrow` request back to the source chain.
4. Arrange for the token transfer inside `withdraw()` to fail in a way that returns `false` rather than reverting (e.g., beneficiary is blacklisted by the token, or the token is paused for transfers).
5. `onAccept` → `withdraw()` executes: `token.call(...)` returns `(success=true, false-encoded-data)`, so `success` is `true`, `TransferFailed()` is not raised, `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowReleased` is emitted.
6. The beneficiary's token balance never increased — the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no way to re-trigger `withdraw` for that commitment, since accounting already shows it as settled.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
