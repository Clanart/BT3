### Title
Users calling `emergencyWithdraw` in `MasterMagpie` permanently lose all unclaimed MGP and BaseRewarder rewards accrued since their last interaction - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie.emergencyWithdraw()` reduces a user's staked `amount` and resets `rewardDebt` without first calling `_harvestMGP` or `_harvestBaseRewarder`, unlike the normal `_harvestAndUnstake` path used by regular withdrawals. This causes any pending, unregistered MGP and bonus-reward-pool rewards to be permanently and silently forfeited, and the corresponding reward tokens become stuck in the contract/rewarder.

### Finding Description
In the normal withdraw flow, `_harvestAndUnstake` (called by `withdraw`/`withdrawFor`) always calls `_harvestMGP` and `_harvestBaseRewarder` before reducing `user.amount` and recomputing `user.rewardDebt`: [1](#0-0) 

`_harvestMGP` computes `pending = (user.amount * accMGPPerShare)/1e12 - user.rewardDebt` using the **old** `user.amount` and stores it into `unClaimedMgp` so it is not lost: [2](#0-1) 

`_harvestBaseRewarder` calls `rewarder.updateFor(_account)` on the pool's `BaseRewardPool`/`BaseRewardPoolV2`, which snapshots `userRewards[token][account] = earned(...)` before the user's `balanceOf` (sourced from `MasterMagpie.stakingInfo`, i.e. `user.amount`) changes: [3](#0-2) [4](#0-3) [5](#0-4) 

However, `emergencyWithdraw` skips both harvest calls entirely: it zeroes `user.available`, transfers the staking token out, reduces `user.amount`, and recomputes `rewardDebt` using the **already-reduced** `user.amount`: [6](#0-5) 

Because `rewardDebt` is set to `(user.amount * pool.accMGPPerShare) / 1e12` with the new (lower or zero) `user.amount`, any MGP reward accrued via `accMGPPerShare` growth since the user's last checkpoint — the portion `(old_amount * accMGPPerShare)/1e12 - old_rewardDebt` — is silently discarded: it is never moved into `unClaimedMgp` and can never be recovered since `_calNewMGP` will now compute pending rewards relative to the new (zero) `amount`. Likewise, because `_harvestBaseRewarder` is never invoked, the BaseRewardPool's `userRewards`/`userRewardPerTokenPaid` for that account are never updated. Since `BaseRewardPool.balanceOf()` reads live `user.amount` from `MasterMagpie.stakingInfo` (which is now reduced/zeroed by `emergencyWithdraw`), any subsequent `earned()` calculation is `newBalance * (rewardPerToken - stalePaid) + staleUserRewards`, which strands the reward portion that had accrued against the user's pre-withdraw balance. Those reward tokens remain locked in the `BaseRewardPool` contract forever, unclaimable by anyone since the accounting no longer refers to them for this user.

This is the exact bug class described in the external report (`GaugeV2.emergencyWithdraw()` failing to run `updateReward`) reproduced in `MasterMagpie.emergencyWithdraw()`, which likewise fails to harvest pending rewards before mutating the user's balance/rewardDebt.

### Impact Explanation
Any unprivileged staker who triggers `emergencyWithdraw()` (reachable whenever the contract is paused, a normal operational state, not requiring any privileged role by the withdrawer) permanently loses all MGP rewards and bonus/extra reward-pool rewards accrued since their last deposit/withdraw/claim interaction. The forfeited reward tokens remain stuck and unclaimable in the `BaseRewardPool` contracts, representing a permanent freeze/loss of user yield — matching the "theft or permanent freezing of unclaimed yield" impact category.

### Likelihood Explanation
The path is trivially reachable by any staked user: it only requires the contract to be in the paused state (an operational, non-privileged-triggered scenario for the caller) and the user calling `emergencyWithdraw(_stakingToken)` with any pending unclaimed rewards, which is the common case for active stakers who have not just harvested.

### Recommendation
In `MasterMagpie.emergencyWithdraw()`, call `_harvestMGP(_stakingToken, msg.sender)` and `_harvestBaseRewarder(_stakingToken, msg.sender)` (or equivalent reward-snapshotting logic) before mutating `user.amount`/`user.available`, so that accrued-but-unclaimed rewards are preserved in `unClaimedMgp` and the rewarder's `userRewards` mapping instead of being silently dropped.

### Proof of Concept
1. User deposits `stakingToken` via `MasterMagpie.deposit` (or `depositFor`), establishing `user.amount` and `user.rewardDebt`, and the pool's `BaseRewardPool` begins accruing `rewardPerToken` against the user's live balance.
2. Time passes; `accMGPPerShare` and the BaseRewardPool's `rewardPerTokenStored` both increase, so `_calNewMGP` and `BaseRewardPool.earned()` both report nonzero pending rewards for the user, none of which have been harvested via `deposit`/`withdraw`/`claim`.
3. Contract is paused (e.g., by owner in an incident) enabling `emergencyWithdraw`.
4. User calls `MasterMagpie.emergencyWithdraw(_stakingToken)`: [7](#0-6) 
   `user.available` is zeroed and tokens are transferred out; `user.amount` is reduced and `user.rewardDebt` is recomputed from the new reduced `user.amount`, with no call into `_harvestMGP`/`_harvestBaseRewarder`.
5. Subsequent calls to `_calNewMGP`/`BaseRewardPool.earned(account, token)` for this user now compute pending rewards relative to the user's new (near-zero) `amount`/`balanceOf`, permanently losing the rewards that had accrued against the pre-withdrawal balance; those reward tokens remain stuck in the `BaseRewardPool` contract.

    function emergencyWithdraw(address _stakingToken) external whenPaused {
        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][msg.sender];
        uint256 availableaAmount = user.available;
        user.available = 0;
        IERC20(pool.stakingToken).safeTransfer(address(msg.sender), availableaAmount);
        emit EmergencyWithdraw(msg.sender, _stakingToken, availableaAmount);
        user.amount = user.amount - availableaAmount;
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;
    }
