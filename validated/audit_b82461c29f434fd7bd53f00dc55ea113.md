## Analysis

The report's core primitive — a raw `transfer()` call whose `success` bool reflects only "did the call not revert," not "did the token actually move" — has a direct, more severe analog in `IntentGatewayV2.sol` on Tron. The escrow-release path there checks call success but never decodes/validates the ERC20's returned boolean, and irreversibly mutates escrow accounting and fill state regardless of whether the token transfer actually succeeded.

### Title
Escrow release silently accounts for and finalizes non-reverting failed ERC20 `transfer`, permanently locking user/solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` (used for both `RedeemEscrow` and `RefundEscrow` settlement) pays out escrowed tokens using a raw low-level call to the ERC20 `transfer` selector and only checks that the *call itself* did not revert, never decoding the boolean return value that ERC20 defines for success/failure. The same pattern is repeated in the `SweepDust` handler.

### Finding Description
In `withdraw()`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
    ...
}
``` [2](#0-1) 

`success` here is only `true` when the target contract call did not revert — it says nothing about the ABI-encoded boolean that ERC20 `transfer` is supposed to return. For ERC20-like tokens that signal failure by returning `false` instead of reverting (the exact class of token the source report M-5 warns about, e.g. legacy tokens or tokens with transfer-blocking logic such as blacklists), `token.call(...)` succeeds with `success = true` even though no tokens moved. The function proceeds to:
1. Mark the order as finalized: `_filled[body.commitment] = beneficiary`.
2. Decrement escrow accounting: `_orders[body.commitment][token] -= amount`.
3. Emit `EscrowReleased`/`EscrowRefunded`.

This is strictly worse than a plain unchecked-transfer bug: the contract does not merely fail to detect the problem — it **actively finalizes and zeroes out the escrow slot for the corrupted transfer**. Once `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, the escrow can never be redeemed or refunded again (`UnknownOrder()` guards revert on any retry, since `_orders[body.commitment][token] == 0` is checked at the top of the loop). Notably, the same contract elsewhere consistently uses `SafeERC20.safeTransferFrom`/`safeTransfer` for inbound and internal-dispatcher transfers, showing the raw-call payout path in `withdraw()` and `SweepDust` is the one inconsistent, unguarded spot: [3](#0-2) 

### Impact Explanation
The exact corrupted value is `_orders[body.commitment][token]`, which is decremented to (or toward) zero, and `_filled[body.commitment]`, which is set to the beneficiary, on the false assumption that the payout succeeded. Both mutations are irreversible in this code path — there is no recovery, retry, or admin sweep tied to the specific `commitment`, since `SweepDust` only sweeps dust the protocol itself tracks, not a specific user's failed escrow release. This is a direct, permanent loss/lock of user or solver funds — escrowed input tokens intended for the solver (`RedeemEscrow`) or refund to the user (`RefundEscrow`) become permanently stranded in the `IntentGatewayV2` contract with no beneficiary able to claim them, satisfying the "stealing or loss of funds" bounty impact category.

### Likelihood Explanation
This is reachable through the standard, unprivileged, cross-chain settlement flow (`onAccept` → `withdraw`) that every filled/cancelled order goes through — no malicious relayer, prover, or admin is required. It is triggered whenever an escrowed input token is one of the non-standard ERC20s that return `false` on failure rather than reverting (a known, real-world token category, explicitly the subject of the seed report), or when a transfer-blocking condition (e.g., a token with recipient-side restrictions) causes a `false` return instead of a revert for a specific beneficiary. Given IntentGatewayV2 accepts an open set of user/solver-specified `token` addresses for escrow, an attacker or unlucky combination of token+beneficiary can hit this path without any privileged access.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the contract's inbound transfer handling. `safeTransfer` decodes and validates the ERC20 return value (or the absence thereof) and reverts on failure, so `_filled` and `_orders` are never finalized/decremented unless the token transfer genuinely succeeded.

### Proof of Concept
1. User places a cross-chain order with an input token `T` that implements `transfer` to return `false` on failure instead of reverting (or a token where the destination beneficiary becomes blacklisted/restricted after order placement).
2. Solver fills the order on the destination chain; a `RedeemEscrow` message is dispatched back to the source chain (Tron `IntentGatewayV2`).
3. `onAccept` → `withdraw(body, false)` is invoked. `token.call(transfer(beneficiary, amount))` returns `success = true` (call didn't revert) but the encoded return data is `false` (transfer logically failed) — this is never checked.
4. `_orders[commitment][token] -= amount` executes, and `_filled[commitment] = beneficiary` is set; `EscrowReleased` is emitted.
5. The solver/beneficiary never received the tokens, and the escrow slot is now zero/finalized, so any subsequent attempt to redeem reverts with `UnknownOrder()`. The tokens remain stuck in `IntentGatewayV2` permanently.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
