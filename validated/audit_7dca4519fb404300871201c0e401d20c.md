### Title
Hand-rolled YAML frontmatter parser silently drops `conditions:` when written in valid YAML flow-sequence style, turning a `action: block` rule into a permanent no-op - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` only understands YAML *block-style* (indented `-` dash) lists for the `conditions:` key. If a rule file expresses `conditions` using standard YAML *flow-style* syntax (e.g. `conditions: [field: command, operator: regex_match, pattern: "rm -rf"]`), the parser silently stores the whole value as an opaque string instead of a list, causing `Rule.from_dict` to drop it to an empty `conditions` list with no warning. `RuleEngine._rule_matches` then unconditionally returns `False` for that rule (`if not rule.conditions: return False`), so a rule that a human/CI reviewer would read as a fully-specified `action: block` rule never actually blocks anything.

### Finding Description
The parsing chain is `load_rules()` → `load_rule_file()` → `extract_frontmatter()` → `Rule.from_dict()`, used by every hookify hook (`pretooluse.py`, `posttooluse.py`, etc.) [1](#0-0) .

In `extract_frontmatter`, top-level keys are detected with `if indent == 0 and ':' in line and not line.strip().startswith('-')`, and the value is taken from `line.split(':', 1)` [2](#0-1) . If a rule author writes:

```
conditions: [field: command, operator: regex_match, pattern: "rm -rf"]
```

the entire bracketed text after the first colon becomes the *value* string (since it's non-empty, it takes the "Simple key-value pair" branch instead of the list branch), so `frontmatter['conditions']` ends up being the literal string `"[field: command, operator: regex_match, pattern: \"rm -rf\"]"` rather than a parsed list — there is no handling anywhere in the function for `[...]` flow sequences [3](#0-2) .

`Rule.from_dict` then does `cond_list = frontmatter['conditions']; if isinstance(cond_list, list): conditions = [...]` — since `cond_list` is a `str`, this check silently fails and `conditions` stays `[]` [4](#0-3) . No exception is raised and no diagnostic is printed by `load_rule_file`, so the returned `Rule` looks superficially valid (`enabled=True`, `action='block'`) but has zero conditions [5](#0-4) .

Finally, `RuleEngine._rule_matches` explicitly treats an empty `conditions` list as "never match": `if not rule.conditions: return False` [6](#0-5) . Because `evaluate_rules` only ever adds a rule to `blocking_rules` if `_rule_matches` returns `True` [7](#0-6) , this rule can never block anything, regardless of the dangerous command/edit it was meant to catch.

The `conditions: [ ... ]` flow-sequence form is completely valid YAML and visually indistinguishable (to a human reviewer, CI linter, or the plugin's own documented format) from a legitimate rule, since the docs only show the block-style form but nothing forbids or warns against flow style [8](#0-7) . No validation, allowlist, or schema check exists anywhere in `load_rules`/`load_rule_file` to catch this divergence before the rule is registered as "enabled".

### Impact Explanation
This causes a documented, intended security-blocking rule (e.g., "block `rm -rf`", "block writing secrets") to be loaded successfully and appear active, while `RuleEngine` treats it as permanently non-matching. The dangerous `Bash`/`Write`/`Edit` operation the maintainer intended to hard-block is instead silently allowed to execute with no warning message and no error in stderr that would tip off the user, breaking the "deny means deny" invariant of the hookify enforcement layer.

### Likelihood Explanation
No special access is required beyond the ability to add or modify a `.claude/hookify.*.local.md` file in a checked-out repository (e.g. via a malicious PR merge, a compromised contributor commit, or any checked-in project-local rule) before the victim opens the project. The bug is 100% deterministic (not a race condition or timing issue) and triggers on ordinary, technically-valid YAML syntax that a reviewer would plausibly accept as correct, making it both easy to reproduce and easy to disguise during code review.

### Recommendation
Reject/normalize any frontmatter value for `conditions` (or any key expecting a list) that is a non-empty string starting with `[` — either implement proper flow-sequence parsing or explicitly raise/log an error when a list-typed key resolves to a scalar string, rather than silently discarding it. More robustly, replace the hand-rolled parser with a real YAML parser (e.g. `yaml.safe_load`) so structural type mismatches like this are impossible, and add a startup/self-check in `load_rule_file` that warns loudly (and treats the rule as disabled/failed, not silently "empty but enabled") whenever `action == 'block'` but `conditions` end up empty and no legacy `pattern` was supplied.

### Proof of Concept
Unit test for `plugins/hookify/core/config_loader.py`:

```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

content = '''---
name: block-rm
enabled: true
event: bash
action: block
conditions: [field: command, operator: regex_match, pattern: "rm -rf"]
---

Dangerous rm -rf detected!
'''

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# What a human/CI reviewer expects:
assert rule.action == 'block'
assert rule.enabled is True
assert len(rule.conditions) == 1          # FAILS: conditions is []

engine = RuleEngine()
input_data = {"tool_name": "Bash", "tool_input": {"command": "rm -rf /"}}
assert engine._rule_matches(rule, input_data) is True   # FAILS: always False, rule never blocks
```

Fuzz-test plan: generate variants of `conditions:` using flow-style `[...]`, JSON-object style `{...}`, and mixed comma/colon edge cases, and assert that any input a human/CI would read as defining ≥1 condition for an `action: block` rule always results in `len(rule.conditions) >= 1` and, for matching input, `RuleEngine._rule_matches` returns `True`.
