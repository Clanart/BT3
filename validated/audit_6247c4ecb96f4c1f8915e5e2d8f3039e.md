### Title
Permanent Freeze of User vlMGP via Inverted `isActive` Check in `WombatBribeManager.unvote` - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.unvote` contains an inverted condition on `pool.isActive` that causes it to do the opposite of what its own docstring and design intent require, permanently trapping user votes (and the underlying locked vlMGP) once a pool is deactivated.

### Finding Description
The `unvote` function is documented as the mechanism to let users pull their votes out of a pool that has been deactivated so that pool removal or rewarder changes "doesn't block users from withdrawing": [1](#0-0) 

```
/// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    if(!pool.isActive)
        revert PoolNotActive();
    ...
```

The check is inverted: it reverts with `PoolNotActive` precisely when the pool `isActive` is `false` — i.e., exactly the scenario the function is meant to handle. As a result, once a pool is deactivated, `unvote` becomes permanently uncallable for that pool, and `userVotedForPoolInVlmgp`, `pool.totalVoteInVlmgp`, and `userTotalVotedInVlmgp` can never be decremented for the votes cast into that pool.

This directly cascades into `VLMGP.startUnlock`, which blocks unlocking of locked MGP whenever the user's committed votes exceed the amount that would remain locked after the unlock: [2](#0-1) 

Because `userTotalVotedInVlmgp[msg.sender]` can never decrease for votes tied to the now-inactive pool (the only path to reduce it, `unvote`, always reverts for inactive pools), any user who voted for a pool that later gets deactivated has that portion of their vlMGP locked amount permanently unable to satisfy the `startUnlock` check, freezing the corresponding MGP indefinitely.

This is the same bug class as the referenced `UpdateManager` report: an incorrectly ordered/inverted condition causes a legitimate state transition (an ordinary protocol lifecycle action) to leave a downstream component permanently unusable for the affected users, rather than being a malicious-admin or purely privileged-role issue — the freeze is suffered by ordinary unprivileged wallets that voted before the pool was deactivated.

### Impact Explanation
Any user who has voted for a pool that is later deactivated has their allocated vlMGP votes permanently stuck: they cannot call `unvote` to release the vote allocation, and consequently cannot pass the `userTotalVotedInVlmgp` check in `VLMGP.startUnlock`, permanently freezing the underlying locked MGP tokens tied to those votes. This constitutes a permanent freezing-of-funds condition well beyond 24 hours, with no user-accessible remedy in the current code.

### Likelihood Explanation
Pool deactivation is a normal, expected lifecycle event (pools get deprecated, migrated, or rewarders changed over the protocol's life), not a rare or adversarial event. Any user who voted for such a pool before it is deactivated is affected with certainty, since the inverted check unconditionally blocks `unvote` for inactive pools.

### Recommendation
Invert the condition in `unvote` to match its documented intent — the pool being inactive should be the case that is *permitted* (or at least not blocked), while attempting to unvote from a pool that doesn't exist/was never voted for should be guarded separately. Concretely, remove the `if(!pool.isActive) revert PoolNotActive();` guard (or replace it with a check appropriate to allow unvoting from inactive pools, e.g. only reverting when `currentVote == 0`), consistent with the docstring's stated purpose.

### Proof of Concept
1. User calls `vote([lpA], [1000])`, allocating 1000 vlMGP votes to `lpA`; `userVotedForPoolInVlmgp[user][lpA] = 1000` and `userTotalVotedInVlmgp[user] += 1000`.
2. Protocol admin later deactivates `lpA` (sets `poolInfos[lpA].isActive = false`), a normal, non-malicious operational action.
3. User calls `unvote(lpA)` to reclaim their vote allocation — the call reverts with `PoolNotActive()` because of the inverted check at [3](#0-2) .
4. User's `userTotalVotedInVlmgp[user]` remains at 1000 forever, since this is the only function that can decrement it for that pool.
5. User calls `VLMGP.startUnlock` attempting to unlock MGP; if the resulting `totalLockAfterStartUnlock` would be less than the stuck 1000 votes, the call reverts per [4](#0-3) , permanently freezing that portion of the user's locked MGP with no available recovery path.
