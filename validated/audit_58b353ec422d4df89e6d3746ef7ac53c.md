### Title
CW20↔ERC20 pointer's `approve` re-derives allowance via `increase_allowance`/`decrease_allowance` diff, remaining vulnerable to classic approve front-running - ([File: contracts/src/CW20ERC20Pointer.sol])

### Summary
The `CW20ERC20Pointer` contract exposes an arbitrary CosmWasm CW20 token as an ERC-20 through the EVM, translating ERC-20 `approve` calls into CW20 `increase_allowance`/`decrease_allowance` messages. The implementation still computes the delta to reach the caller-specified target allowance by first *querying* the live on-chain allowance and then issuing an increase/decrease for the difference, so the resulting allowance always converges to the value the caller passed in `approve(spender, amount)`. This reproduces the exact "approval process can be front-run" bug class from the external report: a `spender` who sees a pending `approve` transaction in the mempool can front-run it by draining the *current* allowance via `transferFrom`, and then, once the pointer's `approve` transaction lands (recomputing the diff against the now-drained allowance), the spender is granted the full newly-approved amount on top of what was already drained.

### Finding Description
`CW20ERC20Pointer.approve` is defined as: [1](#0-0) 

It queries `allowance(msg.sender, spender)` at execution time and issues a CW20 `increase_allowance`/`decrease_allowance` message for `|amount - currentAllowance|`, so the resulting CW20 allowance ends up equal to `amount` regardless of what the allowance was when the transaction was submitted. This mirrors the underlying CW20 contract's own increase/decrease allowance handlers, which perform the identical relative-adjustment pattern against a freshly queried EVM-side ERC20 allowance: [2](#0-1) 

Because the delta is computed against whatever the allowance happens to be *at the moment the pointer's `approve` transaction executes* (not at the moment the owner decided on the new limit), an attacker who is the current `spender` can:
1. Observe the owner's pending `pointer.approve(spender, newAmount)` transaction in the mempool.
2. Front-run it with `pointer.transferFrom(owner, attacker, oldAllowance)`, draining the full existing allowance before the owner's transaction executes.
3. Let the owner's `approve` transaction execute afterward; since the queried `currentAllowance` is now `0` (post-drain), the pointer issues `increase_allowance(spender, newAmount)`, setting the allowance to the full `newAmount`.
4. Immediately transfer the new `newAmount` as well.

The attacker thus extracts `oldAllowance + newAmount`, exactly the double-spend scenario described in the external report, even though the pointer uses `increase_allowance`/`decrease_allowance` rather than a naive `allowances[owner][spender] = amount` overwrite — the diff-based emulation does not provide atomicity/idempotence against interleaved front-run transactions because the "read current allowance, then adjust" step is not atomic with the owner's original *intent* (submission time), only with the pointer transaction's own execution.

### Impact Explanation
This allows an approved `spender` (an unprivileged EVM caller who already holds some spending allowance on a CW20 token exposed via the pointer) to extract more tokens than the owner ever intended to expose at once, resulting in direct fund loss for the token owner. Because `CW20ERC20Pointer` contracts are deployable/usable by any CosmWasm/EVM user, and `approve`/`transferFrom` are reachable via ordinary public EVM transactions, this is reachable by any unprivileged transaction sender who is or colludes with a `spender`.

### Likelihood Explanation
Exploitation requires only mempool visibility and the ability to submit a higher-gas-priced front-running transaction — a standard, well-known MEV/front-running technique, not requiring any privileged access, making likelihood moderate-to-high whenever an owner adjusts an existing non-zero allowance downward or upward through this pointer.

### Recommendation
Do not attempt to emulate an absolute "set allowance to X" semantics via read-then-diff increase/decrease calls, since this does not eliminate the underlying front-running window. Instead, expose `increaseAllowance`/`decreaseAllowance` as the primary API (matching OpenZeppelin's safe pattern) and document/require that consumers use relative adjustments; if `approve(spender, amount)` must remain for ERC-20 compatibility, consider requiring the allowance to be zero before increasing (revert if `currentAllowance != 0 && amount != 0`), which is the common mitigation for this bug class.

### Proof of Concept
1. Owner deploys/uses a `CW20ERC20Pointer` for an existing CW20 token and calls `approve(spender, 100)`; CW20 allowance(owner, spender) = 100.
2. Owner decides to reduce risk and submits `approve(spender, 10)` to lower the allowance.
3. `spender` observes this pending tx in the mempool and front-runs with `transferFrom(owner, spender, 100)` at higher gas price, draining the full old allowance (now 0).
4. Owner's `approve(spender, 10)` executes: pointer queries `allowance(owner, spender)` = 0, computes diff = 10, issues `increase_allowance(spender, 10)` → CW20 allowance becomes 10.
5. `spender` calls `transferFrom(owner, spender, 10)` again, extracting the newly granted amount.
6. Total extracted by `spender`: 110, versus the 10 the owner intended to ultimately expose — demonstrating the fund-loss front-running scenario.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }

// Decrease the allowance of spender by amount.
// Expiration does not work here since it is not supported by ERC20.
pub fn execute_decrease_allowance(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    spender: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    // Query the current allowance for this spender
    let querier = EvmQuerier::new(&deps.querier);
    let current_allowance = querier.erc20_allowance(erc_addr.clone(), info.sender.clone().into_string(), spender.clone())?.allowance;

    // If the new allowance after deduction is negative, set allowance to 0.
    let new_allowance = match current_allowance.checked_sub(amount)
    {
        Ok(new_amount) => new_amount,
        Err(_) => Uint128::MIN,
    };
    
    // Send the message to approve the new amount.
    let payload = querier.erc20_approve_payload(spender.clone(), new_allowance)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };

    let res = Response::new()
        .add_attribute("action", "decrease_allowance")
        .add_attribute("spender", spender)
        .add_attribute("amount", amount)
        .add_attribute("new_allowance", new_allowance)
        .add_attribute("by", info.sender)
        .add_message(msg);

    Ok(res)
}
