### Title
Broken/no-op forfeiture in `mWOMSVBaseRewarder._calExpireForfeit` lets unlocking mWomSV holders keep 100% of rewards intended to be forfeited to remaining lockers - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder` is meant to mirror `vlMGPBaseRewarder`'s design of penalizing holders who begin unlocking (start cooldown) by forfeiting a time/weight-based portion of their accrued rewards back into the pool for continuing lockers. In `mWOMSVBaseRewarder`, `_calExpireForfeit` never calls `mWOMSV.getRewardablePercentWAD(_account)` (unlike its sibling), so it always computes `forfeitAmount = 0`, meaning any holder — including one who calls `startUnlock` the instant they receive rewards — captures their full pro-rata share forever with no discount, unlike the analogous vlMGP mechanism.

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`, `_sendReward` computes the amount to forfeit via `_calExpireForfeit(_account, userRewards[...])` before paying out rewards: [1](#0-0) 

But `_calExpireForfeit` is dead code — it sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount = _amount - rewardableAmount` is always `0`: [2](#0-1) 

Compare this to the sibling `vlMGPBaseRewarder`, whose `_calExpireForfeit` correctly queries the locker's `getRewardablePercentWAD(_account)` to compute a rewardable fraction based on how much of the user's balance is fully locked vs. actively/expired in cooldown, and forfeits the rest back into the pool via `_queueNewRewardsWithoutTransfer`: [3](#0-2) 

The underlying locker `mWomSV.sol` even implements the exact same `getRewardablePercentWAD` logic that `mWOMSVBaseRewarder` should be consuming but never calls: [4](#0-3) 

Root cause: `mWOMSVBaseRewarder._calExpireForfeit` was never wired to `mWOMSV.getRewardablePercentWAD`, leaving the forfeiture feature entirely inert. Reward accrual itself (`rewardPerToken`, `_earned`) is the standard Synthetix-style accumulator, so timing of claims relative to `queueNewRewards` does not itself grant an unfair share — every holder earns proportional to `balanceOf` over elapsed reward-per-token deltas regardless of when they call `getReward`. However, the specific exploit path described — locking, earning full pro-rata rewards, then immediately calling `startUnlock` — is real: in the intended (vlMGP-equivalent) design this exit should trigger a forfeiture redistributed to still-locked holders, but here it never does, so the "instant unlock" strategy retains funds that loyal, fully-locked stakers were supposed to receive via `ForfeitRewardAdded`.

### Impact Explanation
This is a theft/misappropriation of unclaimed yield: rewards that the protocol design intends to redistribute to committed (fully-locked) `mWomSV` holders when another holder exits early are instead retained in full by the exiting holder, since `forfeitAmount` is permanently `0`. This directly benefits any account that locks, harvests, and immediately unlocks, at the expense of long-term lockers who never receive the forfeited-reward top-ups via `_queueNewRewardsWithoutTransfer`/`ForfeitRewardAdded`. This matches the "theft of unclaimed yield disproportionate to actual lock commitment" impact class.

### Likelihood Explanation
No special privileges, capital, or timing tricks are required beyond normal usage: any unprivileged `mWomSV` holder who locks and later calls `startUnlock` benefits automatically because the forfeiture code path can never produce a non-zero value. This is 100% reproducible on every call to `getReward`/`_sendReward` and requires no flash loans, reentrancy, or front-running — simply comparing behavior against the intended (and implemented-elsewhere) `vlMGPBaseRewarder` design confirms the discrepancy.

### Recommendation
Wire `mWOMSVBaseRewarder._calExpireForfeit` to `mWOMSV.getRewardablePercentWAD(_account)` exactly as `vlMGPBaseRewarder` does, computing `rewardableAmount = _amount * rewardablePercentWAD / 1e18` and forfeiting the remainder (subject to the same dust threshold), so that rewards accrued by holders who are unlocking/exiting are properly redistributed to remaining fully-locked holders.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, and `MasterMagpie` wiring per existing test fixtures.
2. Two users, `A` (long-term locker) and `B` (instant claimer), each lock identical `mWOM` amounts at `t0`.
3. `rewardManager` calls `queueNewRewards` at `t1` with a fixed reward amount.
4. `B` immediately calls `startUnlock(fullAmount)` right after harvesting via `getReward`; `A` never unlocks and keeps re-harvesting at each epoch.
5. Repeat `queueNewRewards` -> `B` harvest+`startUnlock` cycle across multiple epochs while `A` remains fully locked and only harvests at the end.
6. Assert: total rewards received by `B` equal 100% of `B`'s pro-rata share (no forfeiture ever deducted, `ForfeitRewardAdded` never emitted for `B`), and compare against expected behavior mirrored from `vlMGPBaseRewarder`/`VLMGP` where an equivalent "instant unlock" `vlMGP` user would incur a nonzero forfeit deducted via `_calExpireForfeit` and redistributed as `ForfeitRewardAdded`, which `A` would then additionally benefit from. Confirm `mWOMSVBaseRewarder`'s `A` never receives any forfeited top-up because `forfeitAmount` is always `0`.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
