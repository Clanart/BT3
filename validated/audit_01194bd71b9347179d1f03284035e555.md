### Title
Unvalidated attacker-controlled length-prefix offset walk in `is_atom_canonical`/`is_clvm_canonical` can raise an unhandled `IndexError` during spend-bundle admission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` decodes a CLVM atom's variable-length size prefix by repeatedly indexing into `clvm_buffer` at an `offset` that is advanced purely based on bytes read from the buffer itself, with no check that `offset` stays within `len(clvm_buffer)` before each access [1](#0-0) . `is_clvm_canonical()` drives this same unchecked offset walk across the whole buffer [2](#0-1) . This mirrors the reported bug class: a length/offset value taken from untrusted, uploaded data is used to compute a read position without validating it stays inside the underlying buffer.

### Finding Description
`is_clvm_canonical()` is called for every coin spend's `puzzle_reveal` and `solution` inside `validate_spend_bundle()`, which is on the direct path of `add_spend_bundle()` used for admitting a spend bundle submitted by any wallet/RPC caller: [3](#0-2) 

Inside `is_atom_canonical`, once the length-prefix format is determined from the first byte, the function loops `prefix_len` times, incrementing `offset` and indexing `clvm_buffer[offset]` to build up `atom_len`, with no bound check against `len(clvm_buffer)`: [4](#0-3)  This computed `atom_len`/offset is then used by the caller to advance `offset` further and keep indexing `clvm_buffer[offset]` in the main loop: [5](#0-4) 

Because Python `bytes`/`memoryview` indexing is itself bounds-checked, an out-of-range `offset` does not produce silent memory corruption (unlike the native Elasticsearch process) — it raises a Python `IndexError`. The critical issue is that this exception is **not caught** anywhere between `is_clvm_canonical()` and its caller in `validate_spend_bundle()` [6](#0-5) , unlike the sibling call `pre_validate_spendbundle()` which only catches `ValueError` from the Rust validator [7](#0-6) .

I was **not able to fully confirm** whether it is actually possible to smuggle a truncated/malformed atom-prefix buffer through as a valid `SerializedProgram` for `coin_spend.puzzle_reveal`/`coin_spend.solution` and still reach this line — the buffer is normally the output of a prior, presumably well-formed CLVM (de)serialization, in which case every prefix's declared length should already be backed by enough trailing bytes and the offset walk stays in bounds. This is the key uncertainty in escalating the classification, and it depends on internal `chia_rs` invariants about `SerializedProgram` construction that are implemented in Rust and outside what I could inspect in this index.

### Impact Explanation
If a crafted `puzzle_reveal`/`solution` buffer can reach `is_clvm_canonical()` with an atom whose declared multi-byte length prefix claims more prefix bytes than remain in the buffer, the resulting uncaught `IndexError` would propagate out of `validate_spend_bundle()` / `add_spend_bundle()`. Depending on how far up the call stack this is caught (or not), this could crash or abort mempool processing for that add_spend_bundle call, matching the accepted "spend-triggered transaction-processing halt" impact category — not remote code execution or memory corruption, since Python bounds-checks all buffer indexing.

### Likelihood Explanation
Low-to-Medium. The precondition for reaching this code with a malformed offset is that `coin_spend.puzzle_reveal`/`coin_spend.solution` bytes are already accepted as syntactically valid `SerializedProgram`/CLVM objects (since this runs after `pre_validate_spendbundle`'s Rust CLVM execution succeeds). If chia_rs's own CLVM deserializer enforces that every declared atom length is backed by sufficient trailing bytes (which is the typical guarantee of a length-prefixed format), then a buffer that already parsed successfully as CLVM cannot have a length prefix pointing past the buffer end, and this code path is unreachable in practice. I could not verify this invariant from the available Python-side code/tests.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (and in `is_clvm_canonical()`'s main loop), returning a definitive "not canonical"/error result instead of relying on the buffer always being well-formed by construction. Wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` in a `try/except` that maps any unexpected exception (e.g. `IndexError`) to a `MempoolInclusionStatus.FAILED` / `Err.INVALID_COIN_SOLUTION` result, consistent with how `pre_validate_spendbundle()` already converts Rust validation errors.

### Proof of Concept
Could not construct a concrete, verified PoC spend bundle without access to the `chia_rs` deserialization internals — a full PoC requires confirming whether a `SerializedProgram` whose bytes have a truncated multi-byte atom length prefix (e.g. a buffer ending in `0xFC` without its required 5 trailing length bytes) can ever be constructed as a `puzzle_reveal`/`solution` that still passes `validate_clvm_and_signature` before reaching `is_clvm_canonical()`. This gap should be validated with a Devin session that has the full `chia_rs` source/tests available.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
