### Title
ThresholdKeys deserialization accepts all-zero Constant interpolation, collapsing the group key to the identity - (crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts serialized keys using `Interpolation::Constant` whose coefficients are all zero. `ThresholdKeys::new` validates only the participant indexes, the share count, and the `t == n` constraint; it never checks that the constant coefficients are nonzero. An all-zero coefficient vector makes every interpolation factor zero, so the group key computed as `sum(verification_shares[i] * factor_i)` degenerates to the identity point. The resulting `ThresholdKeys` object is fully usable: `view()` produces zeroed interpolated secret shares, and the FROST signing pipeline will emit signatures under a group key whose discrete logarithm is publicly known (zero plus any applied offset).

### Finding Description
The bug class in the external report — accepting a degenerate "zero amount of real participation" input that produces a functional but meaningless object — maps directly onto `Interpolation::Constant`.

In `crypto/dkg/src/lib.rs`, `interpolation_factor` for `Interpolation::Constant` is `c[i - 1]` taken verbatim from the coefficient vector, with no nonzero check [1](#0-0) . The group key is then computed by `ThresholdKeys::new` as the sum of `verification_shares[i] * interpolation_factor(i)`, which is the identity when every coefficient is zero [2](#0-1) . The constructor's only validation of the interpolation is that `Constant` requires `t == n` — satisfied trivially by crafted input [3](#0-2) .

`ThresholdKeys::read` feeds attacker-controlled bytes into this path: the interpolation tag byte `0` selects `Constant`, and it reads `n` raw scalars as the coefficients [4](#0-3) . There is no consistency check that the deserialized `secret_share` corresponds to the `verification_shares`, and no check that the resulting `group_key` is non-identity.

Downstream, `ThresholdKeys::view` silently applies the zero factors: `secret_share = factor * scalar * share = 0` (plus the offset for `included[0]`), and every interpolated verification share becomes `V_i * 0 = identity` [5](#0-4) . The FROST `sign`/`complete` pipeline in `crypto/frost/src/sign.rs` then produces a valid Schnorr signature whose `s` is consistent with group key `identity` — i.e., a signature for private key `0` (or `offset`, a locally supplied public scalar) [6](#0-5) . Individual share verification also passes, because each share equation is consistent under the zero interpolation.

### Impact Explanation
Two concrete consequences mirror the original report:

- **Unspendable / anyone-can-spend funds.** If `bitcoin-serai` derives a deposit address from the resulting `group_key`, `Scanner::new`/`p2tr_script_buf` will either fail to produce an address (identity has no even-Y encoding) or, once an `offset` is applied via `ThresholdKeys::offset`, produce a Taproot key whose private key is exactly `offset` — a scalar the offsetting party already knows. Funds sent to that address are either permanently locked or spendable without any threshold participation. This is the analog of "the position remains locked forever."
- **Signatures with zero threshold security.** `complete()` returns a signature valid under the degenerate group key; the signatures verify, so the failure is silent — exactly like the zero-leverage position that opens "successfully" while providing nothing.

The analog preserves the original's essence: a zero-valued parameter that should have been rejected produces an irreversible state where value (deposits, signatures) is committed to a key no honest threshold process controls.

### Likelihood Explanation
Exploitation requires untrusted bytes to reach `ThresholdKeys::read` — e.g., a signer restoring keys from attacker-influenced serialized state, or a coordinator distributing crafted key blobs. `ThresholdKeys::read` is among the listed reachable deserialization APIs. Honest DKG flows (`key_gen`, PedPoP, MuSig) never produce zero coefficients, so this is a deserialization-only path: moderate-to-low likelihood, high impact when reached.

### Recommendation
In `ThresholdKeys::new`, when `interpolation` is `Interpolation::Constant`, reject vectors containing a zero coefficient, and/or assert `group_key` is not the identity before returning. Additionally, reject identity `verification_shares` at construction/deserialization time.

### Proof of Concept
```rust
// Crypto/dkg: deserialize ThresholdKeys with a zeroed Constant interpolation
let mut bytes = vec![];
// ciphersuite ID
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
// t = 1, n = 1, i = 1  (t == n so Constant is "applicable")
for v in [1u16, 1, 1] { bytes.extend(v.to_le_bytes()); }
bytes.push(0); // Interpolation::Constant
bytes.extend(C::F::ZERO.to_repr().as_ref()); // coefficient = 0 -> factor always 0
bytes.extend(C::F::random(rng).to_repr().as_ref()); // arbitrary secret_share
bytes.extend((C::generator() * C::F::random(rng)).to_bytes().as_ref()); // arbitrary V_1

let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // group key degenerates

// FROST proceeds: view(1) gives secret_share = 0, and complete() emits a
// Schnorr signature valid under private key 0 (+ any applied offset).
```
