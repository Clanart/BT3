Audit Report

## Title
Vote account `pending_delegator_rewards` counter is never decremented after block-reward distribution, permanently inflating the authorized withdrawer's reserved-balance floor - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`pending_delegator_rewards` on a `VoteStateV4` account is incremented every time `DepositDelegatorRewards` is processed [1](#0-0)  via the only mutator found in the codebase, `add_pending_delegator_rewards` [2](#0-1) . `withdraw()` treats this field as an untouchable reserve added on top of the rent-exempt minimum, and additionally forbids closing the account entirely while it is nonzero [3](#0-2) , but no code path ever reduces it, including the epoch-boundary logic that actually pays out the corresponding block reward from newly-minted capitalization/epoch-rewards-sysvar lamports rather than from the vote account's own balance [4](#0-3) [5](#0-4) .

## Finding Description
`calculate_block_reward()` reads `pending_delegator_rewards` from the vote state once per epoch purely to compute a delegator's proportional share and to cap payout, and the resulting `block_reward` is minted into stake accounts and capitalization via `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition`, funded from the epoch-rewards sysvar balance (explicitly noted as lamports that "already existed" in capitalization, i.e., not sourced from the vote account's own balance) [6](#0-5) . Nothing in this distribution path writes back an updated (decremented) `pending_delegator_rewards` value into the vote account. A repo-wide search for the field confirms `add_pending_delegator_rewards` (strictly additive, `checked_add`) is the only mutator; there is no `sub_pending_delegator_rewards` or equivalent anywhere in `programs/vote` or `runtime/src/bank/partitioned_epoch_rewards`.

Because `DepositDelegatorRewards` is a public, unprivileged instruction that only requires the source account to sign its own transfer [7](#0-6) , any unprivileged caller can repeatedly deposit lamports into any V4 vote account, growing `pending_delegator_rewards` (and the account's real balance) in lockstep. Once an epoch passes and `calculate_block_reward`/`store_stake_accounts_in_partition` "spends" that pending amount by minting the equivalent block reward to delegators from freshly minted capitalization, the deposited lamports that are already sitting in the vote account are never released from the reserve — `pending_delegator_rewards` stays exactly as high as before the payout. The `withdraw()` guard `remaining_balance < min_rent_exempt_balance + pending_delegator_rewards` therefore treats already-distributed rewards as still outstanding forever, and blocks `Withdraw` from returning to zero balance while `pending_delegator_rewards > 0` regardless of real state [3](#0-2) .

## Impact Explanation
This causes a permanent, unbounded, and growing lock of lamports actually held in the vote account: the `authorized_withdrawer` progressively loses the ability to withdraw funds beyond the ever-shrinking headroom `lamports - rent_exempt_minimum - pending_delegator_rewards`, and can never fully close/redeem the account since `pending_delegator_rewards > 0` unconditionally blocks the zero-balance close path. This is a runtime/accounts-correctness bug that results in legitimate fund loss (inaccessible lamports) for the vote account's withdraw authority, matching the "fund theft/loss" impact category via corrupted accounting state (`pending_delegator_rewards`).

## Likelihood Explanation
No privileged access or malicious peer/validator behavior is required. `DepositDelegatorRewards` is callable by any signer using only public inputs (their own funds and any target vote pubkey) [7](#0-6) , and normal SIMD-0123 epoch reward distribution (which is a standard, intended validator operation, not an attacker action) is sufficient to trigger the missing decrement every epoch. The condition is deterministic and repeatable, growing worse over time with no recovery path.

## Recommendation
Introduce a `sub_pending_delegator_rewards` mutator on `VoteStateHandler`/`VoteStateV4` and invoke it from the block-reward distribution path (e.g., in `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition`, or a dedicated post-distribution step) to decrement each vote account's `pending_delegator_rewards` by the `block_reward_amount` actually distributed for that vote account's delegators in that epoch, keeping the reserve consistent with the real amount still outstanding and unpaid.

## Proof of Concept
1. Enable `block_revenue_sharing`/SIMD-0123 and related features; create a V4 vote account with delegated stake and an authorized withdrawer.
2. As any unprivileged signer, call `DepositDelegatorRewards` one or more times to grow the vote account's real balance and `pending_delegator_rewards` together, as validated by `test_deposit_delegator_rewards` [8](#0-7) .
3. Advance epochs so `calculate_block_reward` and `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` mint/distribute the corresponding block reward to delegator stake accounts from the epoch-rewards sysvar/capitalization [6](#0-5) .
4. Read back the vote account's `pending_delegator_rewards` via `VoteStateHandler::pending_delegator_rewards()` — observe it is unchanged despite the reward having been paid.
5. Attempt `Withdraw` as the `authorized_withdrawer` for an amount leaving less than `rent_exempt_minimum + pending_delegator_rewards`; observe `InstructionError::InsufficientFunds`, matching `test_withdraw_with_pending_delegator_rewards` [9](#0-8) , and note the reserve requirement never shrinks across subsequent epochs.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

    /// Update EpochRewards sysvar with distributed rewards
    pub(in crate::bank::partitioned_epoch_rewards) fn update_epoch_rewards_sysvar(
        &self,
        inflation_reward_lamports_minted_and_burned: u64,
        debit_block_reward_lamports: u64,
    ) {
        let mut epoch_rewards = self.get_epoch_rewards_sysvar();
        assert!(epoch_rewards.active);

        epoch_rewards.distribute(inflation_reward_lamports_minted_and_burned);

        self.update_sysvar_account(&sysvar::epoch_rewards::id(), |account| {
            create_account(
                &epoch_rewards,
                self.inherit_specially_retained_account_fields(account),
            )
        });

        // Debit the lamports separately without updating capitalization,
        // since block reward lamports already existed
        let mut account = self
            .get_account_with_fixed_root(&sysvar::epoch_rewards::id())
            .expect("created sysvar account exists");

        // SAFETY: programmer error if we debit too many block rewards
        account
            .checked_sub_lamports(debit_block_reward_lamports)
            .expect("epoch reward sysvar has enough lamports for distribution");
        assert!(
            account.lamports() >= self.get_minimum_balance_for_rent_exemption(account.data().len()),
            "Sysvar account must have enough for rent exemption after debiting block rewards"
        );
        self.store_account(&sysvar::epoch_rewards::id(), &account);
