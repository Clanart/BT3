### Title
Attacker-controlled `ThresholdKeys::read` parameters trigger quadratic Lagrange interpolation, causing a CPU hang (DoS) - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `ThresholdParams` triple `(t, n, i)` and a set of `n` verification shares, then calls `ThresholdKeys::new`, which computes the group key by evaluating a Lagrange `interpolation_factor` for each of the `t` participants. Each `interpolation_factor` call iterates over all `t` included indexes, so group-key derivation is `O(t²)` scalar operations. With `t = n = u16::MAX` (65535), a single ~4 MB serialized input forces ~4.3 billion field multiplications inside `ThresholdKeys::new`, hanging the caller. This maps the CVE-2018-2562 class — a low-privileged, network-reachable input causing a hang/complete DoS — onto Serai's threshold-key deserialization path.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the byte stream, then reads `n` verification shares and delegates to `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` validates `t <= n` and `t == n` only for `Constant` interpolation; for `Interpolation::Lagrange` it proceeds to compute the group key as a sum over `1..=t` of `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` [2](#0-1) . `interpolation_factor` for `Lagrange` runs a loop over every participant in `included`, performing a scalar multiply for the numerator and denominator per element [3](#0-2) . Since `included` here is `1..=t`, total work is `t * t` field multiplications plus `t` point multiplications. `n` is a `u16`, so an attacker can legitimately encode `t = n = 65535` with `65535` group elements and the interpolation byte `0x01` (Lagrange), producing ~4×10⁹ scalar multiplications — a hang lasting far beyond any reasonable timeout — with no early length or cost bound. The same quadratic blowup exists in `ThresholdView` construction via `view()` (`interpolation_factor` per included signer) [4](#0-3) , but `view` inherits `n` from already-validated local keys, so `read` → `new` is the reachable path.

### Impact Explanation
A party able to feed serialized `ThresholdKeys` bytes to a Serai component (e.g., keys propagated, recovered, or relayed between processors/coordinators, or any caller that deserializes key material received over a channel) can cause a complete denial of service of that process: the deserialization call does not return for an attacker-chosen amount of work quadratic in `n`. This mirrors the upstream advisory's impact (unauthenticated/low-privileged input → repeatable hang/crash of the server). No secret is leaked and no signature is forged; impact is availability-only, matching the CVE's dominant `A:H` component.

### Likelihood Explanation
Likelihood is moderate: exploitation only requires that the attacker control bytes passed to `ThresholdKeys::read` and the ~4 MB input be deliverable (well within the multi-megabyte message limits seen elsewhere in the codebase, e.g., `MAX_LIBP2P_REQRES_MESSAGE_SIZE`). It does not require any threshold of colluding validators or leaked secrets — a single crafted blob suffices. However, `ThresholdKeys::read` is a library API; the concrete exposure depends on an integrator passing network-sourced bytes to it. Within the stated scope (untrusted bytes fed to `ThresholdKeys::read`), the path is direct and needs no authentication.

### Recommendation
Enforce a sane upper bound on `t`/`n` at the top of `ThresholdKeys::read` (and `ThresholdParams::new`), or cap interpolation work. Options:
- Reject `n` above a protocol-meaningful maximum (Serai validator sets are far below `u16::MAX`; e.g., enforce `n <= 2^10` or a configured limit) before reading `n` points.
- Validate `ThresholdParams::new(t, n, i)` immediately after reading the header, before performing `n` `read_G` calls or any interpolation.
- Compute the group key via a single multiexp with per-participant Lagrange coefficients computed in `O(t)` total (share the denominator-product precomputation / use prefix-suffix products) rather than the current `O(t²)` per-party loop, or cap `t` for Lagrange.

### Proof of Concept
Construct a serialized `ThresholdKeys` blob: `id_len = len(C::ID)` + `C::ID`, then `t = 0xFFFF`, `n = 0xFFFF`, `i = 0x0001`, interpolation byte `0x01` (Lagrange), one valid scalar `secret_share`, and `65535` copies of a valid encoded point (e.g., `C::generator()`). Feeding this ~4.2 MB buffer to `<C as ...>::read` / `ThresholdKeys::<C>::read` reaches `ThresholdKeys::new`, which passes validation (`t == n`, Lagrange allowed for any `t`) and then evaluates `interpolation_factor` for each of the 65535 participants, each iterating over all 65535 included indexes — ~4.3×10⁹ field multiplications plus inversions, hanging the thread inside a nominally "safe" deserialize call.
