### Title
`update_finalized_payouts` attributes payout ownership from an unauthenticated OP_RETURN, letting an attacker frame a victim operator for a payout it never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` derives the "paying operator" solely from the first OP_RETURN push of a confirmed payout transaction, with no check that the OP_RETURN pubkey belongs to whoever actually supplied the funds/signature for that transaction. Because the withdrawal UTXO is spent under `SIGHASH_SINGLE|ANYONECANPAY`, additional inputs/outputs (including the OP_RETURN) are unconstrained by the user's signature, so anyone able to fund the payout output can insert an arbitrary victim operator's xonly_pk and get it persisted as the "payer" of that payout.

### Finding Description
The claimed binding is:
`operator credited (OP_RETURN xonly_pk parsed by update_finalized_payouts)` == `operator whose funds actually paid the user (the real signer/funder of the confirmed payout tx)`.

In `update_finalized_payouts`, the operator identity is extracted purely syntactically: [1](#0-0) 
No signature or key-ownership check ties `operator_xonly_pk` to who actually signed/funded the transaction; the value is persisted directly via `update_payout_txs_and_payer_operator_xonly_pk`. [2](#0-1) 

The reusable OP_RETURN parser, `get_first_op_return_output`/`parse_op_return_data`, performs no cryptographic binding either — it just returns the first pushed data after `OP_RETURN`: [3](#0-2) [4](#0-3) 

Root cause enabling the attack: the withdrawal input's authorization signature is `SIGHASH_SINGLE|ANYONECANPAY`, which only commits to input 0 and output 0 (the user's payout output/amount) and leaves any additional inputs or outputs — including the OP_RETURN carrying the operator xonly_pk — completely unconstrained: [5](#0-4) [6](#0-5) 

This is exactly the transaction shape `Operator::withdraw` builds (single dust input, keyspend witness, then funded via the TxSender's RBF/CPFP mechanism): [7](#0-6) 

Exploit flow: attacker (or the withdrawing user themselves, since anyone can call `withdraw` on the Citrea contract and obtain/produce a valid `SinglePlusAnyoneCanPay` signature over the dust input and output 0) constructs a competing spend of the same withdrawal UTXO that reuses the honest signature/output-0, funds the payout output amount from their own coins, but appends an OP_RETURN containing a victim operator's real 32-byte xonly_pk (`XOnlyPublicKey::from_slice` accepts any 32-byte value), and gets it to confirm ahead of (or instead of) the honest operator's version via higher fee/RBF.

Downstream, `Verifier::update_finalized_payouts` records the victim's xonly_pk as `payer_xonly_pk`, and `Operator::validate_payer_is_operator` — run autonomously by the victim's own node — matches it against `self.signer.xonly_public_key` and proceeds: [8](#0-7) 
This leads the victim operator's automation to build and sign its own kickoff/reimbursement chain (using its own presigned round tx and MuSig2-signed kickoff) for a payout it never actually funded. Because `deposit_constant`/the bridge-circuit journal only re-derives `operator_xonlypk` from the same unauthenticated OP_RETURN and `round_txid` from the victim's own genuine round tx, the resulting proof is internally self-consistent and indistinguishable from a legitimate payout by the victim: [9](#0-8) 

None of the existing guards catch this: `is_deposit_valid`/`SPV::verify`/`verify_storage_proofs`/`lc_proof_verifier` only check that the withdrawal outpoint, block inclusion, and L2 state are correct — none verify who signed/funded the payout transaction's non-committed outputs; `SECP.verify_schnorr` is used elsewhere (optimistic payout path) but never to bind the OP_RETURN operator pubkey to the payout tx's actual spender in `update_finalized_payouts`.

### Impact Explanation
An honest ("victim") operator can be induced to run its automated kickoff/reimbursement flow — spending its own presigned round transaction and consuming its collateral rotation — to claim reimbursement for a Bitcoin payout it never made and never funded, matching the Critical category "an operator reimbursed for a payout it never funded." Because `parse_op_return_data`/`XOnlyPublicKey::from_slice` accept arbitrary 32-byte data and no cross-check exists anywhere in the reachable path, this is repeatable for any withdrawal and against any operator whose real xonly_pk is public (all operator xonly_pks are public protocol data), so the blast radius spans every deposit/withdrawal and every operator.

### Likelihood Explanation
Preconditions: attacker must be able to fund the exact payout output amount (real BTC cost equal to the withdrawal amount) and win the fee race against the honest operator's payout broadcast — feasible via RBF/fee bumping, requiring only public mempool access and the withdrawal's own `SinglePlusAnyoneCanPay` signature (obtainable by the attacker being the withdrawing user, or by observing/racing a legitimate withdrawal signature that was disclosed off-chain to operators). No verifier/operator/aggregator privilege, key compromise, or majority hashrate is needed — fully within the stated unprivileged attacker capabilities.

### Recommendation
Bind the OP_RETURN operator xonly_pk cryptographically to the actual payer: e.g., require that the additional funding input(s) of the payout transaction are provably controlled by the same xonly_pk (verify a signature over the OP_RETURN commitment from that key, or restrict payout tx construction/verification to check that funding UTXOs resolve to addresses derived from the claimed operator's xonly_pk) before `update_finalized_payouts` persists `operator_xonly_pk`, and before `validate_payer_is_operator` allows the operator to proceed with reimbursement.

/// Parses the OP_RETURN data from a Bitcoin script. It retrieves the first data push after an OP_RETURN.
pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
