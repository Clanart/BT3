### Title
Unauthenticated forced address association via signature replay lets attacker migrate a victim's funds and permanently orphan their account - ([File: precompiles/addr/addr.go])

### Summary
The `addr` precompile's `associate` method (and the equivalent `HandleAssociateTx` path in `app/ante/evm_checktx.go`) links a Sei address to an EVM address by verifying an ECDSA signature over `keccak256(customMessage)`, where **both** `customMessage` and the raw `(v, r, s)` signature are fully attacker-supplied call arguments. [1](#0-0)  There is no domain separation, chain-ID binding, nonce, or on-chain enforcement that the signed text is specific to Sei address association or to this chain. [2](#0-1)  This mirrors the CVE class of "verification bypass using an arbitrary/leaked credential that was never intended for this exact confirmation purpose" — the addr-precompile equivalent of Zammad accepting an arbitrary e-mail token to authenticate an unrelated identity.

### Finding Description
`GetAddresses` simply ECDSA-recovers a pubkey from whatever `(v, r, s)` and message hash are handed to it — it performs no check that the signature was produced specifically to authorize a Sei/EVM association, for this chain, or at this point in time. [2](#0-1)  The precompile's `associate` function takes `v, r, s, customMessage` directly as call arguments, hashes `customMessage` with keccak256, and recovers `(evmAddr, seiAddr, pubkey)` from it with the only guard being "not already associated": [3](#0-2) 

Any valid secp256k1 signature the victim ever produced for an unrelated purpose (e.g., a `personal_sign` challenge for a completely different dApp, wallet-login flow, or even a signature on a different chain) can be replayed by anyone who observes it, as long as they also know the exact plaintext that was signed, to force a permanent, one-time association between the victim's EVM address and their canonical Sei address — without the victim ever intending or consenting to a Sei association. Once used, `AssociateAddresses` is invoked, which migrates the account's balance from the EVM-cast address to the Sei address and removes the cast account entirely. [4](#0-3)  This is a state-changing, irreversible operation gated only by "not already associated," with no re-verification the caller has current authorization or intent.

Notably, the codebase itself documents that this exact bug class — a signature that authenticates its own scope/chain and is trivially replayable outside that scope — was patched for EIP-7702 SetCode authorizations via `AuthorityToPreAssociate`, which explicitly checks `auth.ChainID` before accepting a recovered authority, citing the precise risk of "a publicly-visible authorization a user signed for another chain... replayed... to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state." [5](#0-4)  The `addr` precompile's `associate`/`associatePubKey` entry points (and all `legacy/vXXX` copies) do not have an analogous domain-separation check — they accept any `(v, r, s, customMessage)` tuple unconditionally. [3](#0-2) [6](#0-5) 

### Impact Explanation
A successful forced association permanently binds a victim's Sei/EVM identity pair against their will, migrates any spendable balance and wei balance sitting at the EVM-cast address to the newly bound Sei address, and removes the cast account. [7](#0-6)  Because associations are one-time/immutable ("account already has association set"), the victim cannot later self-associate with their intended pubkey, causing permanent freezing/orphaning of any future direct-cast balance or interaction that depends on the correct association, and unauthorized transfer of funds already present at the cast address to a Sei address whose control the attacker may influence (e.g., if attacker also controls or can front-run the corresponding EVM key for gas-sponsored replay, or simply griefs a victim into an unusable association state).

### Likelihood Explanation
Exploitation requires the attacker to obtain a signature `(v, r, s)` the victim produced along with its exact plaintext — this is realistic given widespread `personal_sign`/message-signing prompts across dApps, some of which are logged, publicly leaked (e.g., posted for support/debugging), or intentionally solicited via a phishing site under any pretext ("sign to verify you own this wallet"). Because the on-chain check does not require the message to reference Sei, EVM/Sei association, a chain ID, a nonce, or an expiry, essentially any previously-observed signature+plaintext pair is replayable at any time by any unprivileged caller submitting an ordinary EVM transaction to the `addr` precompile.

### Recommendation
Add domain separation and freshness to the association signature scheme, mirroring the fix already applied for SetCode authorizations in `AuthorityToPreAssociate`: require the signed payload to include the chain ID (rejecting foreign-chain signatures unless explicitly zero/wildcard and intentionally allowed), a purpose-specific fixed prefix that cannot be satisfied by unrelated application signatures, and ideally a nonce/expiry tied to the target seiAddr/evmAddr pair so a given signature cannot be replayed after use or reused for an unintended purpose. Enforce this validation identically across `precompiles/addr/addr.go` and all `precompiles/addr/legacy/vXXX/addr.go` copies, and in `app/ante/evm_checktx.go`'s `HandleAssociateTx`.

### Proof of Concept
1. Victim signs an arbitrary `personal_sign` message `M` for any unrelated dApp/service (message content becomes known/leaked, e.g., via a phishing site, public bug bounty log, or dApp backend that stores signatures), producing `(v, r, s)` over `M`.
2. Attacker calls the `addr` precompile's `associate(v, r, s, M)` at `0x0000000000000000000000000000000000001004`, exactly reproducing `M` as `customMessage`. [3](#0-2) 
3. `GetAddresses` recovers the victim's EVM address, Sei address, and pubkey from the replayed signature with no check that `M` was intended for association or bound to this chain. [2](#0-1) 
4. Since the victim's Sei address had no prior association, `associateAddresses` succeeds, calling `AssociateAddresses`, which migrates the victim's balance from the cast address to the (now forcibly bound) Sei address and deletes the cast account. [8](#0-7) 
5. The victim's intended association is now permanently blocked ("account already has association set"), and their funds have moved without their consent for this specific action.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
