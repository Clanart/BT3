### Title
Hardcoded zero slippage protection in `ArbWomUp3._deposit` (mode 2) exposes users to sandwich attacks on WOM→mWOM buyback swap - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit()` is a public, unprivileged entry point that lets any wallet deposit WOM and, in `_mode == 2`, routes half of the deposit through `SmartWomConvert.convert()` to perform an on-chain AMM swap (WOM→mWOM) before locking the proceeds. The call hardcodes the slippage-protection parameter (`_minRec`) to `0`, completely disabling the only protection mechanism `SmartWomConvert` offers against price manipulation, mirroring the exact bug class described in the referenced report (missing slippage protection enabling sandwich attacks).

### Finding Description
`incentiveDeposit()` is external and callable by any wallet with a user-chosen `_convertRatio` and `_mode` [1](#0-0) . When `_mode == 2`, it calls the internal `_deposit()` function, which splits the WOM amount in half: one half is deposited to mint `mWOM` 1:1, and the other half is swapped through `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)` — note the third argument (`_minRec`) is hardcoded to `0` [2](#0-1) .

Inside `SmartWomConvert._convertFor`, the portion of the amount not covered by `_convertRatio` (`buybackAmount`) is swapped through `IWombatRouter.swapExactTokensForTokens` with the underlying swap call itself hardcoded to `0` minimum-out, and the *only* aggregate protection is the post-swap check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` [3](#0-2) . Since `ArbWomUp3` passes `_minRec = 0`, this check becomes `x < 0`, which can never revert — i.e., no slippage protection exists at all for this call path, regardless of how unfavorable the executed swap price is.

The user only controls `_convertRatio` (the split between direct deposit and AMM buyback) but has no way to specify a minimum acceptable `mWOM` output for the buyback swap performed on their behalf. An attacker observing a pending `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` transaction in the mempool can:
1. Front-run by swapping WOM→mWOM (or vice versa) in the shared `womMWomPool` to shift the price unfavorably against the victim's upcoming buyback swap.
2. Let the victim's transaction execute, receiving a manipulated (worse) amount of `mWOM` from `swapExactTokensForTokens`.
3. Back-run by reversing the swap to capture the price difference as profit, extracted directly from the victim's deposited WOM.

### Impact Explanation
This is a direct theft of user funds: an ordinary user calling `incentiveDeposit` with `_mode == 2` can have a portion of their deposited WOM value extracted by a sandwiching attacker with zero slippage protection to prevent it, since the responsible parameter is hardcoded to `0` rather than derived from user input.

### Likelihood Explanation
`incentiveDeposit` is a normal, unprivileged, whenNotPaused external function that any wallet can call at any time with `_mode = 2` and a `_convertRatio` less than `DENOMINATOR` to force a nonzero `buybackAmount` swap; no special permissions or preconditions are required, and MEV/sandwiching of AMM swaps is a routine and easily automatable attack in production.

### Recommendation
Add a user-supplied `_minRec` (or equivalent slippage/deadline) parameter to `incentiveDeposit`/`_deposit` and forward it (instead of the hardcoded `0`) to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minRec, 0)`, so the existing `MinRecNotMatch` check in `SmartWomConvert._convertFor` can actually enforce a meaningful minimum output.

### Proof of Concept
1. Victim calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)` with `convertRatio < DENOMINATOR`, intending to deposit WOM and lock the resulting mWOM.
2. `_deposit` computes `toSwap` and calls `IConverter(smartWomConvert).convert(toSwap, convertRatio, 0, 0)` [4](#0-3) .
3. Attacker front-runs with a swap in `womMWomPool` to move the WOM/mWOM price against the victim.
4. `SmartWomConvert._convertFor` executes the buyback swap via `swapExactTokensForTokens(..., 0, ...)` and its own aggregate check `convertAmount + amountRec < _minRec` (with `_minRec == 0`) never reverts, so the victim receives a manipulated, lower `mWOM` amount [5](#0-4) .
5. Attacker back-runs, reversing the swap and capturing the difference as profit at the victim's expense.
