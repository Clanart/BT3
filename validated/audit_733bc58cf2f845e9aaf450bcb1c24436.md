### Title
Reachable `IndexError` in `is_clvm_canonical()` from an untrusted spend bundle's puzzle reveal/solution can crash mempool spend-bundle validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`chia/full_node/mempool_manager.py`'s `is_clvm_canonical()`/`is_atom_canonical()` parse the raw CLVM serialization of a coin spend's `puzzle_reveal` and `solution` to decide DEDUP eligibility. The atom-length parsing trusts the encoded length prefix and advances the cursor (`offset`) by the *claimed* atom length without ever validating that the buffer actually contains that many trailing bytes. This is analogous to the CVE-2022-23484 class of bug: a length value taken from attacker-controlled input is used to compute a buffer/cursor position without a bounds check, leading to an out-of-bounds access. [1](#0-0) [2](#0-1) 

### Finding Description
`is_atom_canonical()` decodes a variable-length atom-length prefix (1–6 bytes) directly from the buffer and returns `1 + prefix_len + atom_len` as the number of bytes the atom occupies, without checking that `offset + 1 + prefix_len + atom_len <= len(clvm_buffer)`: [3](#0-2) 

`is_clvm_canonical()` then unconditionally does `offset += atom_len` and, if `tokens_left != 0` (i.e., there are more pending list items to parse, such as inside a `(A . B)`-style pair), immediately re-indexes `clvm_buffer[offset]` on the next loop iteration: [4](#0-3) 

Because `atom_len` is fully attacker-controlled (up to a 32-bit value from the 6-byte-prefix branch) and is never validated against remaining buffer length, an attacker can craft a `puzzle_reveal` or `solution` byte string such as a pair (`0xFF`) followed by a short atom whose declared length exceeds the buffer, causing `offset` to be pushed past the end of `clvm_buffer` while `tokens_left > 0`. The subsequent `clvm_buffer[offset]` access raises an unhandled `IndexError`.

This function is invoked directly and synchronously from `MempoolManager.validate_spend_bundle()` on every coin spend of every spend bundle a peer/wallet submits, with no surrounding `try/except`: [5](#0-4) 

`validate_spend_bundle()` is called from `add_spend_bundle()`, again with no exception handling around the call: [6](#0-5) 

### Impact Explanation
An unprivileged spend-bundle submitter (wallet RPC caller, offer participant, or any peer relaying a transaction) can supply a `puzzle_reveal`/`solution` whose CLVM-serialized bytes deliberately violate the implicit assumption in `is_atom_canonical`/`is_clvm_canonical` that the declared atom length is consistent with the remaining buffer. This raises an `IndexError` inside `validate_spend_bundle()`, propagating up through `add_spend_bundle()`. Since these functions run under the mempool/blockchain lock during spend-bundle admission, an uncaught exception here can abort in-flight transaction-processing for that call path, matching the "spend-triggered transaction-processing halt" impact category. This is a Denial-of-Service class issue against mempool admission reachable from a single submitted spend bundle, without needing any signature or on-chain funds beyond what is required to build a `CoinSpend` (note: `puzzle_reveal`/`solution` content itself is not directly fee-gated the way full CLVM execution cost is, since the crash occurs before/independent of the cost-based rejection logic that governs `is_clvm_canonical`'s *result* being used only for DEDUP eligibility — the parsing itself already crashes).

### Likelihood Explanation
High: the buggy code path is exercised on every coin spend in every spend bundle admitted to the mempool (`is_clvm_canonical` is called unconditionally in `validate_spend_bundle`). Constructing a malformed-but-CLVM-parseable byte sequence that trips this specific off-by-length condition requires only crafting raw bytes (no signature checks are needed to reach this function, since it runs before/alongside other validation, purely on the raw `bytes(coin_spend.puzzle_reveal)` / `bytes(coin_spend.solution)`).

### Recommendation
In `is_atom_canonical()`/`is_clvm_canonical()` (`chia/full_node/mempool_manager.py`), bound-check every computed offset against `len(clvm_buffer)` before dereferencing, and treat any out-of-range atom length as "not canonical" (return `False`) rather than allowing `offset` to run past the buffer end. Wrap the call sites in `validate_spend_bundle()` in a defensive `try/except (IndexError, ValueError)` that treats a parse failure as "not canonical" (fail closed, e.g., `Err.INVALID_COIN_SOLUTION`) instead of letting the exception propagate.

### Proof of Concept
Construct a 2-byte CLVM buffer: `b"\xff\x81"`.
- `is_clvm_canonical()` sees `0xFF` → pair, `tokens_left = 2`, `offset = 1`.
- At `offset = 1`, byte is `0x81` (in the 6-bit-length-prefix range `0x81–0xBF`), so `is_atom_canonical` computes `atom_len = 0x81 & 0x3F = 1`, and returns `1 + 0 + 1 = 2`.
- `offset += 2` → `offset = 3`; `tokens_left -= 1` → `tokens_left = 1` (not zero, loop continues).
- Next iteration executes `b = clvm_buffer[offset]` with `offset = 3` on a 2-byte buffer → `IndexError: index out of range`.

Submitting a `CoinSpend` whose `puzzle_reveal` or `solution` serializes to bytes matching this pattern (e.g., embedded inside a larger otherwise-valid CLVM program/solution as a sub-list) will trigger this unhandled exception when `MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` / `is_clvm_canonical(bytes(coin_spend.solution))`.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
