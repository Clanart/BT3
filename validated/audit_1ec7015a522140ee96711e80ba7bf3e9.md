### Title
ReDoS via attacker-controlled rule pattern in `compile_regex`/`_regex_match` can hang PreToolUse enforcement with no internal timeout guard - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._regex_match` compiles and executes user/agent-supplied `pattern` strings from `.claude/hookify.*.local.md` rule files with no bound on execution time or pattern complexity. A catastrophic-backtracking pattern (e.g. `(a+)+$`) evaluated against a long attacker-influenced `command`/`new_text` field will hang inside `re.Pattern.search`, and neither `_regex_match`'s `except re.error` nor `pretooluse.py`'s outer `try/except/finally` can interrupt or catch a hang (only exceptions are caught, not CPU-bound blocking calls).

### Finding Description
The call chain `pretooluse.py:main()` → `load_rules()` → `RuleEngine.evaluate_rules()` → `_rule_matches()` → `_check_condition()` → `_regex_match()` → `compile_regex(pattern).search(text)` takes the `pattern` field straight from parsed rule frontmatter ( [1](#0-0) ) into `re.compile(pattern, re.IGNORECASE)` cached via `lru_cache` ( [2](#0-1) ) and then calls `.search(text)` where `text` is the attacker/user-influenced `field_value` from `tool_input` such as the Bash `command` or Edit/Write `new_text` ( [3](#0-2) ).

There is no pattern validation, complexity limit, or execution timeout anywhere in this path — the only exception handling is for `re.error` (invalid syntax), not for long-running matches. `evaluate_rules()` also loops over every rule/condition sequentially with no time budget, so multiple bad patterns compound ( [4](#0-3) ). Because Python's `re` engine cannot be interrupted mid-match by ordinary exception handling, `pretooluse.py`'s `try/except Exception` / `finally: sys.exit(0)` wrapper ( [5](#0-4) ) never gets a chance to run — the process simply hangs inside the regex call rather than raising an exception that would trigger the documented fail-open path.

The plugin's own `hooks.json` sets a 10-second timeout for the PreToolUse hook ( [6](#0-5) ), meaning a ReDoS pattern will reliably exceed this budget with a sufficiently long attacker-controlled input string. What Claude Code's hook runner does when a PreToolUse hook exceeds its `timeout` (i.e., whether it treats the tool call as allowed or denied) is implemented outside this repository and could not be verified from the available code, but regardless of that external behavior, the finding stands that this plugin provides **no internal fail-closed guarantee**: the hook is fully able to be driven into an unbounded hang by rule content it itself loads and evaluates, undermining the invariant that hook enforcement completes and yields a deterministic decision.

### Impact Explanation
An attacker who can get a rule file with a catastrophic-backtracking `pattern` checked into `.claude/hookify.*.local.md` (e.g., via a Step 3 user-supplied or agent-suggested pattern during `/hookify` rule authoring, or via a malicious PR/commit adding such a file) can cause every subsequent `Bash`/`Edit`/`Write`/`MultiEdit` tool call whose input is long enough to hang the PreToolUse hook for the full timeout window (10s per hook invocation, compounding across multiple bad rules/conditions in the same evaluation). This degrades or defeats the hook-based guardrail mechanism that the repo relies on to block dangerous commands, and depending on the (unverified, out-of-repo) timeout-handling behavior of the Claude Code hook runner, may allow the triggering tool call to proceed unchecked.

### Likelihood Explanation
Requires an attacker-authored or attacker-influenced rule file to exist under `.claude/` with a `regex_match` condition using a vulnerable pattern — this is explicitly a scenario the question calls out as reachable via `/hookify` Step 3 (user-supplied or agent-suggested patterns), and no validation in `config_loader.py`/`rule_engine.py` rejects such patterns. Triggering the hang additionally requires an attacker-influenced input string of sufficient length in a subsequent tool call (e.g., a long Bash command), which is easily arranged. This is straightforward to reproduce deterministically.

### Recommendation
- Validate/sanitize regex patterns at rule-load time (e.g., reject patterns matching known ReDoS constructs, or run a static complexity check).
- Enforce a hard execution-time budget per regex match, e.g., run `compile_regex(pattern).search(text)` in a worker process/thread with a timeout (or use `regex` module's timeout support, or `signal.alarm` on POSIX) and treat a timeout as "rule does not match" rather than hanging.
- Cap the length of `text` passed to `_regex_match` for pathological inputs.
- Add an overall wall-clock budget inside `evaluate_rules()` so that no single hook invocation can exceed a safe fraction of the hook's configured `timeout`.
- Ensure that whatever happens on timeout, the plugin explicitly emits a deterministic deny/allow decision within the budget rather than depending on the external hook runner's timeout-handling default.

### Proof of Concept
Unit/fuzz test plan for `plugins/hookify/core/rule_engine.py`:
```python
import time
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

def test_redos_pattern_bounded_time():
    rule = Rule(
        name="redos-rule",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"(a+)+$")],
        message="test",
        action="block",
    )
    engine = RuleEngine()
    evil_input = {
        "tool_name": "Bash",
        "tool_input": {"command": "a" * 40 + "!"},  # classic (a+)+$ ReDoS trigger
    }
    start = time.monotonic()
    result = engine.evaluate_rules([rule], evil_input)
    elapsed = time.monotonic() - start
    # Expect evaluation to complete within a bounded time (e.g., < 1s)
    assert elapsed < 1.0, f"ReDoS pattern caused unbounded hang: {elapsed}s"
    # Expect a deterministic decision, not a silent pass-through
    assert result != {}
```
Expected current (failing) result: `evaluate_rules()` hangs (does not return within seconds/minutes) for inputs like `"a"*40 + "!"` against `(a+)+$`, demonstrating no internal timeout guard and no bounded execution guarantee, which is the defect this PoC should catch once a timeout/validation fix is added.

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
