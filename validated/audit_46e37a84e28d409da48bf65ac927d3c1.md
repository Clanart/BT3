### Title
Naive `str.split('---', 2)` frontmatter delimiter parsing lets an attacker-influenced regex `pattern` value truncate the YAML block and silently drop `action: block` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the YAML frontmatter boundaries with a plain `content.split('---', 2)` instead of matching `---` only on its own line. Since the hookify skill explicitly recommends writing **unquoted** patterns into the frontmatter, any attacker-influenced regex/pattern text that itself contains a literal `---` substring (e.g. a rule meant to catch triple-dash markers, git-conflict markers, YAML-doc separators, etc.) will be treated as the closing frontmatter delimiter, truncating the frontmatter early and silently dropping trailing keys such as `action: block`.

### Finding Description
`extract_frontmatter` in [1](#0-0)  does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
```
This split matches the literal substring `---` anywhere in the file content, not just on a line by itself as required by real YAML frontmatter conventions. `/hookify` (per [2](#0-1) ) writes `pattern: {regex pattern}` as an **unquoted** value directly derived from the analyzed behavior/conversation/`$ARGUMENTS`, and the companion skill explicitly instructs to keep patterns unquoted: "**Recommendation**: Use unquoted patterns in YAML" ( [3](#0-2) ). Neither the command nor the skill instructs escaping or rejecting `---` inside pattern text.

If the attacker-influenced pattern text (sourced from a PR/issue description or `$ARGUMENTS`, which is threaded verbatim into the workflow per [4](#0-3) ) contains a literal `---` (e.g. a rule intended to flag git-conflict markers or YAML separators), the file Claude writes looks like:
```
---
name: rule
enabled: true
event: bash
pattern: foo---bar
action: block
---

message body
```
`content.split('---', 2)` splits at the opening `---` and then at the **first subsequent occurrence of the substring `---`**, which is inside `pattern: foo---bar` on the same line — not the real closing delimiter. As a result `parts[1]` ends at `...pattern: foo`, and `action: block` (and the true closing `---`) get shoved into `parts[2]`, becoming part of the message body instead of frontmatter. The line-oriented key/value parser ( [5](#0-4)  ) then never sees `action:`. `Rule.from_dict` falls back to the default `action='warn'` ( [6](#0-5) ), so a rule the user/agent intended as `block` silently becomes `warn`.

No existing check catches this: `load_rule_file`/`load_rules` only validate IO/parsing exceptions ( [7](#0-6) ), not semantic mismatches between intended and parsed `action`/`enabled` fields, and there is no allowlist or escaping step before the `Write` tool persists the frontmatter.

### Impact Explanation
This breaks the stated invariant "deny means deny": a rule the user selected as `action: block` (e.g., "Block operation" in Step 2 of `hookify.md`) can silently degrade to `warn`, meaning `PreToolUse`/`Stop` enforcement in `pretooluse.py`/`stop.py` no longer actually blocks the dangerous command/edit it was created to stop — it only prints a warning and the tool call proceeds. This is a policy/enforcement-bypass class impact: a security control created specifically to block a class of dangerous operations becomes a no-op guard due to a parser bug reachable from ordinary attacker-influenced text summarized into the rule.

### Likelihood Explanation
Feasibility depends on the agent (Claude) actually writing an unquoted pattern value containing a literal `---` substring, which is realistic because: (1) the skill/command explicitly recommend unquoted pattern values without warning against `---`, and (2) plausible legitimate behaviors to hookify naturally involve `---` (e.g., "block edits that add git conflict markers", "warn on triple-dash YAML separators", or an attacker simply padding a `$ARGUMENTS` string with `---` in their description). It is not a guaranteed 100%-of-the-time trigger since it depends on LLM-generated content, but it is a deterministic parser flaw once the trigger string is present, and repeatable via direct unit testing of `extract_frontmatter` independent of the LLM.

### Recommendation
Replace the naive substring split with a delimiter that requires `---` to appear alone on its own line (e.g. `re.split(r'(?m)^---\s*$', content, maxsplit=2)`), and additionally validate after parsing that required keys (`name`, `enabled`, `event`) and the intended `action` are present and match the expected type before treating the rule as loaded — falling back to a hard failure (reject the rule / do not treat it as `enabled`) rather than a silent default when frontmatter looks truncated or malformed. Also update `writing-rules/SKILL.md` guidance to require quoting/escaping pattern values that could contain YAML-significant sequences like `---`.

### Proof of Concept
Unit test against `extract_frontmatter`/`Rule.from_dict` in `config_loader.py`:
```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

content = """---
name: block-conflict-marker
enabled: true
event: file
pattern: foo---bar
action: block
---

This should BLOCK the operation.
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Expected (semantic intent): action == 'block'
# Actual: action falls back to default 'warn' because 'action: block'
# was pushed into the message body by the premature split.
assert rule.action == 'block', f"action downgraded to {rule.action!r}; block rule silently became warn"
```
Running this against the current implementation fails the assertion, demonstrating that `action: block` is dropped and the rule silently downgrades to `warn`, confirming the vulnerability.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)

        return None
    except Exception as e:
