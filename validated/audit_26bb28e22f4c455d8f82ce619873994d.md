Aggregator gRPC server applies `Interceptors::Noop` with no hardcoded authentication floor when `client_verification=false`, exposing all state-mutating aggregator RPCs unauthenticated - ([File: core/src/servers.rs])

### Summary
`create_grpc_server` selects the interceptor purely based on `config.client_verification`, with no server-role-specific override: if `client_verification` is `false`, every service — including the aggregator — is wrapped in `Interceptors::Noop` instead of `Interceptors::OnlyAggregatorAndSelf`. `create_aggregator_grpc_server` only emits a `tracing::warn!` when `client_verification` is `true`; it never forces or checks that the aggregator enforces client authentication, so with `client_verification=false` any TCP client can reach every aggregator RPC without presenting a certificate.

### Finding Description
The claimed binding — "a caller reaching any aggregator method mutating protocol state or spending a bridge UTXO == a party holding the aggregator's certificate" — is not enforced in code; it is entirely contingent on the deployment-time boolean `config.client_verification`.

In `core/src/servers.rs::create_grpc_server` (lines 106-139), the TLS config and interceptor are chosen together from the single flag: [1](#0-0) 
When `config.client_verification` is `false`, `tls_config` omits `client_ca_root`, and the interceptor is unconditionally `Noop` — there is no separate check for "is this the aggregator's own server" that would force `OnlyAggregatorAndSelf` regardless of the flag.

`create_aggregator_grpc_server` (lines 293-317) does not add any additional enforcement; it merely logs a warning if `client_verification` is *enabled*, and calls the same generic `create_grpc_server` used by operator/verifier servers: [2](#0-1) 

Since `is_internal()` and `only_aggregator_and_self()` in `core/src/rpc/interceptors.rs` (lines 12-77) are only invoked when the interceptor variant is `OnlyAggregatorAndSelf`, the `Noop` path bypasses that logic entirely, allowing any TCP peer (with plain TLS, no client cert) to invoke every aggregator method — `Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`, `GetEntityStatuses` — identically to the aggregator itself.

Root cause: authentication of the aggregator's own gRPC surface is entirely delegated to an operator-controlled config flag with no code-level floor, contrary to `docs/usage.md`'s claim that TLS-only (no client cert) is an accepted, safe posture for the aggregator ("does not enforce client certificates but does use TLS for encryption").

### Impact Explanation
If an operator deploys the aggregator with `client_verification=false` (matching the documented, apparently-supported configuration), any internet-reachable, cert-less TLS client can call the same RPCs the aggregator normally restricts to itself and legitimate parties on operator/verifier servers. Depending on what these RPCs allow (setup, deposit/withdrawal signing session initiation, emergency-stop transaction retrieval/broadcast, move-to-vault transaction broadcast), this is an unauthenticated state-changing or broadcasting call path, matching the High severity category defined by the rules ("an unauthenticated state-changing or broadcasting call"). It is reachable identically across all deposits and operators served by that aggregator instance, since the authorization gap applies to the entire aggregator gRPC surface, not to a specific method or deposit.

### Likelihood Explanation
The only precondition is a specific deployment configuration: `client_verification=false` on the aggregator's `BridgeConfig`. The `docs/usage.md` explicitly frames this configuration as an accepted mode of operation for the aggregator ("does not enforce client certificates but does use TLS for encryption"), meaning it is not a hypothetical misconfiguration but a documented/intended posture. No BTC cost, no key material, and no privileged role are required — only network reachability to the aggregator's gRPC port with a standard TLS client (attacker does not need a valid certificate, since `client_ca_root` is not configured when `client_verification=false`). This is fully repeatable and requires no on-chain action.

### Recommendation
Add a hardcoded requirement in `create_aggregator_grpc_server` (or `create_grpc_server` when `server_name == "Aggregator"`) that always applies `Interceptors::OnlyAggregatorAndSelf` (or an aggregator-specific authenticated interceptor) regardless of `config.client_verification`, and fail server startup instead of silently degrading to `Noop` if the required certificates are unavailable. Alternatively, remove `client_verification=false` as a legal aggregator configuration and validate this invariant at config-load time (outside `.toml`/`docs` scope — as a Rust-level assertion in `create_aggregator_grpc_server`).
