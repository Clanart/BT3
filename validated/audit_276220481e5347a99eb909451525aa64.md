### Title
Cached FROST preprocess seed is never cleared and is deterministically reused for every signature under the same context, enabling nonce reuse and secret-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The bug class in the external report is "state set once and never reset before the next operation" (missing `approve(0)` → revert/failure on reuse). In Serai, the analogous shape is the cached FROST preprocess: `SigningProtocol::preprocess_internal` derives the entire signing nonce state from a single 32-byte seed stored in `CachedPreprocesses`, keyed only by `context`. Once written, the entry is never deleted — every subsequent `share_internal`/`complete` call for the same context reloads the same seed and regenerates identical nonces and identical commitments.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs` (lines 123–145), `preprocess_internal`:

1. Writes `CachedPreprocesses::set(txn, &context, &cache)` only `if CachedPreprocesses::get(...).is_none()` — i.e., the seed persists forever per context.
2. On every call, reads the cached seed back and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))`.

`from_cache` → `seeded_preprocess` (`crypto/frost/src/sign.rs` lines 121–144) instantiates `ChaCha20Rng::from_seed(*seed.0)` and derives `nonces` and `commitments` purely deterministically from that seed. The FROST spec (`spec/cryptography/FROST.md` lines 45–62) and the `SignMachine::from_cache` docs (`sign.rs` lines 216–224) both state: *"After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share."* The coordinator never deletes the DB entry — there is no `CachedPreprocesses::del`/`take` call anywhere.

Concretely, `DkgConfirmer` uses `context = (b"DkgConfirmer", self.attempt)` (line 275). Both `share()` and `complete()` route through `share_internal`, which calls `preprocess_internal` again — reusing the same seed. The signed message is `set_keys_message(set, removed, key_pair)` (lines 296–301), so if `share`/`complete` are ever driven twice under the same `attempt` with a different `key_pair` (which is supplied by the caller/protocol flow and influenced by validator-submitted DKG data) or a different effective message, the same nonce pair `(d, e)` produces two signature shares over two different challenges `c1 ≠ c2`. Any observer of both shares computes `s_share1 - s_share2 = λ·x_i·(c1 - c2)` and recovers the validator's MuSig/FROST secret share `x_i`, since the Lagrange coefficient `λ` is public.

Even absent differing messages, rebroadcasting identical deterministic preprocesses across parallel/retried sessions gives other participants replayable commitment material — the exact parallel-session/ROS-style weakness the prompt targets.

### Impact Explanation
Recovery of a validator's Ristretto secret share for the tributary signing set. Combined with threshold-many compromised shares (or used to forge that validator's participation), this undermines the MuSig layer authenticating DKG confirmations (`set_keys_message` → `KeyPair` registration on Substrate). Critical severity if two distinct messages are signed under one context.

### Likelihood Explanation
The deterministic-reuse machinery is unconditionally present: `from_cache` is invoked on *every* `share`/`complete` call, not just crash recovery. Whether two distinct `key_pair` values are signed under one `attempt` depends on the tributary message flow in `handle.rs` (not fully verified here); the `attempt` scoping mitigates cross-retry reuse but does not prevent same-attempt double-signing with differing `key_pair` or differing preprocess sets. The persistent, never-invalidated cache means any such replay deterministically reuses nonces rather than reverting — unlike USDT, there is no failure mode, just silent key leakage. Medium-to-high likelihood given attacker-influenced preprocess/share inputs reach `share_internal`.

### Recommendation
Delete the `CachedPreprocesses` entry (e.g., `txn.del`) when it is consumed for signing, or include the message/preprocess-set digest in the context key so any distinct signing attempt derives a distinct seed. At minimum, assert in `share_internal` that the cached-seed-derived `preprocess` matches the one already broadcast for this context before producing a share.

### Proof of Concept
1. `coordinator/src/tributary/signing_protocol.rs` lines 123–145: seed stored once under `context`, never removed; `from_cache` called on every share/complete.
2. `crypto/frost/src/sign.rs` lines 121–144: `ChaCha20Rng::from_seed(*seed.0)` → identical `nonces`/`commitments` for identical seed.
3. `crypto/frost/src/sign.rs` lines 216–224 + `spec/cryptography/FROST.md` lines 51–62: explicit contract that reuse leaks the private key share — the code violates its own documented MUST.
4. Attack: a participant causes `DkgConfirmer::share` and later `DkgConfirmer::complete` (or two `share` calls) to execute under the same `attempt` with a different `key_pair` (hence different `set_keys_message`). Two shares `σ1 = d + ρe + λx c1`, `σ2 = d + ρe + λx c2` with the same `(d, e)` yield `x = (σ1-σ2)/(λ(c1-c2))`.

Uncertainty note: I could not fully verify from `handle.rs` within the available iterations whether the coordinator permits two distinct `key_pair`/preprocess inputs under one `attempt`; if the protocol strictly enforces a single message per context, impact reduces to the documented-MUST violation without a demonstrated second message.
