## Title
NFT offer royalty payments can be reduced (or zeroed) via floor-division truncation by increasing `royalty_split` — ([File: chia/wallet/nft_wallet/nft_wallet.py])

## Summary
The bug report describes an LP-reward formula that is evaluated per-transaction against a shared, mutable divisor (`lpSupply`). Because `lpSupply` shrinks with each partial withdrawal in the same block, a user who splits one large withdrawal into many small ones accumulates more total reward than a single withdrawal, due to favorable rounding at each step. The Chia analog is `chia/wallet/nft_wallet/nft_wallet.py`'s NFT royalty computation, which divides an offered/requested fungible amount by a `royalty_split`/`offer_side_royalty_split` count *before* multiplying by the royalty percentage. Structuring a single offer to increase that split count (by bundling more royalty-enabled NFTs into one trade) causes the same per-unit floor-division truncation pattern, systematically reducing (and, for small enough per-NFT shares, zeroing) the royalty paid to creators relative to what an equivalent single-NFT trade of the same aggregate value would pay.

## Finding Description
`compute_royalty_amount()` computes:

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
``` [1](#0-0) 

and `royalty_calculation()` (used by the RPC-facing royalty summary) applies the identical `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS` pattern. [2](#0-1) 

The `royalty_split` value used in `make_nft1_offer` is `offer_side_royalty_split`/`request_side_royalty_split` — simply the *count* of royalty-enabled NFTs on one side of a single offer — and the same divide-then-multiply operation is applied both to `trade_prices` and to the actual royalty `CreateCoin` payment:

```
trade_prices.append((uint64(amount // offer_side_royalty_split), settlement_ph))
...
extra_royalty_amount = compute_royalty_amount(amount, request_side_royalty_split, percentage)
``` [3](#0-2) 

Because integer division floors, `abs(offered_amount) // royalty_split` loses up to `royalty_split - 1` units at each division. Bundling more NFTs into a single offer (or requesting NFTs in exchange for the same fungible amount split across more royalty-holding NFTs) increases `royalty_split`, which increases the total rounding loss subtracted before the percentage is even applied — this is the same rounding/truncation family exploited by the external report's LP-split attack: an operation is deliberately fragmented to change a divisor value used in a per-unit reward/fee formula, shifting value away from the counterparty (royalty recipients/NFT creators here; other LPs there).

## Impact Explanation
If a maker or taker structures an offer with a larger `royalty_split` (more royalty NFTs bundled per fungible payment) instead of doing multiple single-NFT trades, the aggregate royalty actually paid to NFT creators can be strictly less than the sum of royalties that would be paid across separate single-NFT trades of equivalent value — and can be driven to zero when `abs(amount) // royalty_split` truncates to 0 for small per-NFT shares. This is a direct value-transfer from royalty recipients to trade counterparties, i.e., unintended reduction/theft of settlement value in offer completion, reachable purely by an offer-maker/taker crafting an ordinary spend bundle.

## Likelihood Explanation
Any wallet user creating or accepting an NFT offer with royalty-enabled NFTs controls the numerator/denominator shape of this calculation and can trivially bundle multiple NFTs or restructure trades to maximize truncation loss; no privileged access or network-level compromise is required. The effect is most profitable when the offered fungible amount is small relative to `royalty_split` and/or `MAX_ROYALTY_BASIS_POINTS`, similar to how the original LP bug is most profitable during high volume, but is a straightforward gain here regardless of timing since it is entirely within a single, atomic offer-accept flow.

## Recommendation
Compute royalty per-NFT precisely (e.g., allocate the floor amount to each NFT but assign the remainder rather than dropping it, or compute royalty independently per-NFT’s own fair-share of the trade price rather than via floor(`total // count`)), and ensure the sum of individually computed royalties matches the royalty that would be charged for an economically equivalent single-item trade, closing the gap that lets bundling reduce total royalty paid.

## Proof of Concept
Using `compute_royalty_amount` directly (as exercised in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`): [4](#0-3) 
- Single NFT, offered_amount = -2_000_000, royalty_split=1, percentage=1000 (10%): royalty = 200_000.
- Two NFTs bundled together for the same total 2_000_000 payment, royalty_split=2, percentage=1000: `compute_royalty_amount(-2_000_000, 2, 1000)` = `(2_000_000 // 2) * 1000 // 10000` = 100_000 total across both NFTs (50_000 each) — half of what a single NFT trade of equal aggregate value would yield, with the shortfall growing (and truncating fully to 0 for small per-item shares) as `royalty_split` increases further.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty

```

    @staticmethod
    def royalty_calculation(
        royalty_assets_dict: dict[Any, tuple[Any, uint16]],
        fungible_asset_dict: dict[Any, uint64],
    ) -> dict[Any, list[dict[str, Any]]]:
        summary_dict: dict[Any, list[dict[str, Any]]] = {}
        for id, royalty_info in royalty_assets_dict.items():
            address, percentage = royalty_info
            summary_dict[id] = []
            for name, amount in fungible_asset_dict.items():
                summary_dict[id].append(
                    {
                        "asset": name,
                        "address": address,
                        "amount": abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS,
                    }
                )

        return summary_dict
