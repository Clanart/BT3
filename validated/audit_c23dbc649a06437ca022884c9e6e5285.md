## Title
`placeOrder()` on Tron credits escrow with the nominal input amount instead of the actual balance received, allowing insolvent escrow accounting for fee-on-transfer / non-standard tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` still contains the exact bug class the external report describes: it credits internal accounting (`_orders[commitment][token]`) with a value that is computed from the *requested* order amount rather than the *actual* tokens the contract received. The canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly patched to avoid this — its comment even states "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds" [1](#0-0) , and it enforces this via balance-before/after deltas both for the predispatch-sweep path [2](#0-1)  and for the direct-transfer path [3](#0-2) . The Tron contract never does this measurement.

### Finding Description
In the Tron contract's direct-transfer branch, escrow is incremented with the pre-computed `reducedInputs[i].amount` (order-specified amount minus protocol fee) immediately after calling `safeTransferFrom`, with no check of what the contract's balance actually increased by: [4](#0-3) 

The same pattern repeats in the predispatch-sweep branch: `dust` is computed from the dispatcher's balance vs. `requiredAmount`, but the escrow write still uses the nominal `reducedInputs[i].amount`, not any measured amount that actually landed on the gateway: [5](#0-4) 

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user-supplied, unvalidated request) minus the protocol fee, computed before any transfer occurs: [6](#0-5) 

If the input token is a fee-on-transfer, deflationary, or rebasing token, `safeTransferFrom` delivers strictly less than `order.inputs[i].amount` to the gateway's actual balance, yet `_orders[commitment][token]` is credited as if the full nominal amount arrived. The contract's own test suite proves this exact scenario is handled correctly in the canonical EVM contract via `FeeOnTransferToken` tests [7](#0-6) , confirming the project is aware this token class is expected to be encountered and is a real threat model — but the Tron port lacks the fix.

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) determines how much a solver can redeem on `fillOrder`/withdrawal once a commitment is proven filled. If escrow is inflated beyond the gateway's actual token balance (because the nominal amount was recorded instead of the delivered amount), the contract becomes insolvent for that token: cumulative escrow liabilities exceed on-hand balance. The first solver(s) to withdraw will drain real balance backed by *other users'* legitimately-escrowed orders, so subsequent legitimate order fills/refunds fail or pay out short — a direct loss/lock of funds for other users, matching the bounty's "stealing or loss of funds" and "logic attacks" categories. This requires no relayer, prover, or governance compromise — any ordinary user can place an order using a fee-on-transfer ERC-20 as input to trigger the shortfall.

### Likelihood Explanation
High. `placeOrder()` is a fully public, unprivileged entrypoint; the only requirement is using (or having the solver select) a non-standard ERC20 as an input token — fee-on-transfer/deflationary/rebasing tokens are common in the wild and the repo's own test suite (`FeeOnTransferToken`) demonstrates this exact class is anticipated. No specific chain condition beyond deploying/using the Tron variant is needed.

### Recommendation
Port the fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure the gateway's actual token balance immediately before and after each transfer/sweep, and credit `_orders[commitment][token]` (and use in the commitment hash) only the actually-received delta, not the caller-supplied nominal amount. Apply the fix to both the predispatch-sweep branch and the direct `safeTransferFrom` branch.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with `protocolFeeBps = 0` for simplicity.
2. Deploy a fee-on-transfer ERC-20 (e.g., the `FeeOnTransferToken` helper already in the test suite, with a 5% transfer fee) and mint tokens to `attacker`.
3. `attacker` calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch. `safeTransferFrom` delivers only `950e18` to the gateway (5% burned/fee), so the gateway's real FOT balance increases by `950e18`.
4. Because of line `_orders[commitment][token] += reducedInputs[i].amount;` with `reducedInputs[i].amount == 1000e18` (no protocol fee), escrow now records `1000e18` although the gateway holds only `950e18`.
5. Repeat with a second, unrelated order using the same FOT token, or simply have a solver fill the first order and withdraw the full `1000e18` escrow amount recorded — the contract will attempt to pay out `1000e18` while only holding `950e18` (plus whatever other orders' balances happen to be sitting in the same pooled token balance), draining balance backing other users' escrowed orders and causing later fills/refunds to revert or be shorted.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
