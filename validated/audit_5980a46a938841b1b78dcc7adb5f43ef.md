### Title
`ThresholdKeys::new` / `ThresholdKeys::read` accept a secret share without verifying it matches the committed verification share — ([File: crypto/dkg/src/lib.rs])

### Summary

The phpMyCVE bug class — a credential update accepted without proving possession of the existing credential — maps onto Serai's `ThresholdKeys` construction. `ThresholdKeys::new` (and therefore `ThresholdKeys::read`, which deserializes `t`, `n`, `i`, interpolation, `secret_share`, and all `verification_shares` from raw bytes) performs no check that `C::generator() * secret_share == verification_shares[i]`. The "password" (the secret share and claimed participant identity) is adopted purely from the supplied bytes, with the verification-share map acting only as an attacker-controlled policy blob — never as proof the secret is consistent with the account's public commitments.

### Finding Description

In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` validates only structural properties: the count and index range of `verification_shares` (lines 355–365), and that `Constant` interpolation is only used when `t == n` (lines 367–374). It then computes `group_key` from `verification_shares[1..=t]` and stores everything without ever checking the supplied `secret_share` against `verification_shares[params.i()]` (lines 376–390). `ThresholdKeys::read` (lines 574–632) feeds fully attacker-controlled bytes into this constructor: the claimed participant index `i` (line 600), the interpolation method including arbitrary `Constant` factors (lines 604–616), the raw `secret_share` (line 618), and every verification share (lines 620–623).

Every honest construction path — `dealer::key_gen`, PedPoP `KeyMachine::calculate_share` (pedpop/src/lib.rs lines 511–521 computes `C::generator() * self.secret` for the local share), and MuSig `musig` (musig/src/lib.rs line 152 `debug_assert_eq!(our_pub_key, verification_shares[&params.i()])`, a check removed in release builds) — establishes the `secret_share`/`verification_share` correspondence internally, so the missing check in `new`/`read` is the sole gap: the deserialized credential is never re-verified against the public commitment, exactly mirroring "password changed without verifying the current password".

### Impact Explanation

A party supplying crafted serialized `ThresholdKeys` causes the victim to operate under a fully attacker-defined key set:

- With `Interpolation::Constant` and `t == n`, the attacker chooses arbitrary interpolation factors and arbitrary `secret_share`/`verification_shares`, so `view()`/`sign_share` produce valid partial signatures under a group key the attacker computed and fully controls (since they know every underlying scalar). The victim node attests and signs under an attacker-chosen group key rather than the key established by its real DKG — the analogue of silently replacing the account password.
- Alternatively, with mismatched `secret_share` vs. `verification_shares[i]`, or by claiming a different participant index `i` while keeping others' verification shares, the victim's `verify_share` (frost/src/algorithm.rs lines 219–230) evaluates honest shares against attacker-substituted verification shares, causing valid peer shares to fail and honest participants to be blamed (PedPoP/FROST blame attribution skews toward the attacker-authored map).

This is Medium: it requires feeding crafted key bytes to a deserialization path (key restore/import/rotation flows reach `ThresholdKeys::read`), and yields signing under an attacker-controlled group key and/or false blame and aborted signing, rather than recovery of honest shares.

### Likelihood Explanation

The library exposes `ThresholdKeys::read`/`serialize` as the supported persistence and transport format, so any flow importing or restoring keys from storage or the network exercises this path. No cryptographic proof binds the secret share to its slot; exploitation needs only byte-level control of the serialized structure. It is not reachable purely from in-band DKG/signing messages, which limits the rating to Medium.

### Recommendation

In `ThresholdKeys::new`, verify `C::generator() * *secret_share == verification_shares[&params.i()]` and reject on mismatch (covers `read`, `dealer`, `musig`, `promote`, and PedPoP uniformly, replacing the `debug_assert_eq!` in `musig`). Additionally, when `Interpolation::Constant` is used, verify that `interpolation_factor(i, &included)` reproduces the binding-factor-derived values rather than trusting serialized factors, or restrict `Constant` deserialization to internally constructed keys.

### Proof of Concept

```rust
// Crypto: build ThresholdKeys the victim will sign under a key we fully control.
let n = 3u16;
let scalar_a = Scalar::random(&mut OsRng); // attacker's "participant" secret
let mut verification_shares = HashMap::new();
// Attacker-chosen shares -> attacker-known group key
for l in 1..=n {
    let s = Scalar::random(&mut OsRng);
    verification_shares.insert(Participant::new(l).unwrap(), RistrettoPoint::generator() * s);
}
let keys = ThresholdKeys::<Ristretto>::new(
    ThresholdParams::new(n, n, Participant::new(1).unwrap()).unwrap(),
    Interpolation::Constant(vec![Scalar::ONE; n as usize]),
    Zeroizing::new(scalar_a), // never checked against verification_shares[1]
    verification_shares,
).unwrap(); // Accepted: group_key == attacker-computed key

// Or via the serialization sink: arbitrary bytes -> ThresholdKeys::read
// installs index `i`, `secret_share`, and `verification_shares` with no
// secret-share/verification-share consistency check (crypto/dkg/src/lib.rs:574-632).
```
