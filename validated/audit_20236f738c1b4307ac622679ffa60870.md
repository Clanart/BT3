### Title
Insufficient validation of CW20/CW721/CW1155 pointer target contract type-confusion in `AddCW721`/`AddCW1155` - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `addCW721Pointer` and `addCW1155Pointer` methods (and their legacy versions) accept any bech32 contract address and validate it only by calling the generic CosmWasm `{"contract_info":{}}` query and asserting that the JSON response contains `name`/`symbol` string fields, then unconditionally register that contract as the CW721/CW1155 backing for a newly deployed ERC721/ERC1155 pointer contract. There is no check that the target contract actually implements the CW721 or CW1155 execute/query interface (e.g. `ownerOf`, `nft_info`, `balance` with `token_id`), nor any differentiation between the two types (both use the identical `contract_info` query and identical `name`/`symbol` extraction). This mirrors the reported bug class: config/identity data is accepted as valid for a given adapter/type merely because it superficially matches a shape shared by multiple types, without any type-identifying check or interface probe, allowing a mismatched (wrong-type) target to pass validation.

### Finding Description
`AddCW721` and `AddCW1155` in `precompiles/pointer/pointer.go` (lines 166-228) both query only `{"contract_info":{}}` and require the JSON body to contain `name` and `symbol` fields: [1](#0-0) [2](#0-1) 

Any CosmWasm contract exposing a `contract_info` query returning `{"name": "...", "symbol": "..."}` — which is a trivially satisfiable, generic response shape not unique to CW721 or CW1155 — will pass this "validation" and be registered as the backing contract for a freshly created ERC721 or ERC1155 pointer via `evmKeeper.UpsertERCCW721Pointer` / `UpsertERCCW1155Pointer`. Nothing distinguishes a CW721 contract from a CW1155 contract at this validation step (both checks are byte-for-byte identical), and nothing confirms the contract implements NFT/multi-token semantics at all (a CW20 contract, or an arbitrary contract exposing only that one query handler, would also pass).

This is directly analogous to the reported issue: `ConstantPriceAdapter.isPriceAdapterConfigDataValid` accepted config bytes intended for other adapters because it performed no length/identifier check; here the pointer precompile accepts a contract as CW721 or CW1155 because the only check performed is a generic, type-agnostic query whose response shape offers no adapter/type discrimination.

Downstream, the generated pointer contract (e.g. `CW721ERC721Pointer`) blindly forwards ERC721 calls (`ownerOf`, `balanceOf`, `tokenURI`, etc.) as smart-contract queries/executes assuming CW721 message schemas. If the underlying contract does not actually implement those handlers (e.g., it was really meant to be a CW1155 contract, or an arbitrary contract crafted to pass the superficial `contract_info` check), calls into the pointer will behave unpredictably: some may revert, some may silently return attacker-controlled/mismatched data (since the wasmd/json precompiles used by the pointer, `IWasmd.query` / `IJson.extractAsBytes`, will parse whatever JSON the attacker-controlled contract returns).

### Impact Explanation
Because pointer registration is irreversible and permanently associates an EVM pointer address with a Cosmos contract address in on-chain state (`SetERC721CW721Pointer` / `SetERC1155CW1155Pointer`), an attacker can deploy a minimal CosmWasm contract that (a) responds to `contract_info` with a crafted `name`/`symbol` and (b) returns attacker-chosen data for the NFT/multi-token queries the pointer forwards (`ownerOf`, `balance_of`, `owner_of`, etc.), since nothing forces those handlers to reflect real token custody. Any downstream EVM consumer that trusts the pointer as a genuine ERC721/ERC1155 view (e.g. marketplaces, lending protocols using `ownerOf`/`balanceOf` for collateral or transfer authorization) can be misled into believing false ownership/balance state, enabling unauthorized transfers or fraudulent collateralization — i.e., real fund loss for any protocol built atop the pointer's reported state. This is a Medium-severity type-confusion/insufficient-validation issue reachable by any unprivileged EVM caller through the public `addCW721Pointer`/`addCW1155Pointer` precompile methods.

### Likelihood Explanation
Likelihood is high for exploitation of the *validation gap* itself: any address holder can call `addCW721Pointer`/`addCW1155Pointer` with an arbitrary contract they control, and the check trivially passes by exposing a `contract_info` handler with `name`/`symbol`. The remaining step — building a wasm contract that returns attacker-favorable data for the specific queries the pointer performs — requires only writing a CosmWasm contract, which is fully within reach of a normal, unprivileged user (no governance, no validator, no p2p access needed).

### Recommendation
Require the target contract to unambiguously self-identify and prove interface conformance before registering it as a pointer target:
- Query a CW721/CW1155-specific endpoint that a CW20 or generic contract cannot satisfy (e.g., for CW721 require a successful `{"num_tokens":{}}` or `{"all_nft_info":{...}}`-style probe with an expected response schema; for CW1155 require a `{"balance_of":{...}}`/multi-token-specific probe), and reject registration if the probe fails or the response schema does not match.
- Ensure `AddCW721` and `AddCW1155` use distinct, non-overlapping validation queries so a single contract cannot be registered as both types.
- Consider embedding an explicit self-reported interface marker (analogous to CW721/CW1155's `contract_info` `name`/`symbol` being augmented with a required `type` discriminator) and reject on mismatch, mirroring the report's recommendation to add a type identifier to config-like data instead of relying on shape alone.

### Proof of Concept
1. Deploy a minimal CosmWasm contract `Fake` that implements only:
   - `{"contract_info":{}}` → `{"name":"FakeNFT","symbol":"FAKE"}`
   - Any NFT-style query the pointer later forwards (e.g. `owner_of`) → attacker-controlled JSON (e.g., always returns the attacker's own Sei address as owner for any `token_id`).
2. From an unprivileged EVM account, call `pointer.addCW721Pointer(FakeContractAddress)`. The Go handler in [3](#0-2)  succeeds because only `name`/`symbol` are checked, and a new `CW721ERC721Pointer` is deployed and registered via `UpsertERCCW721Pointer`.
3. Any external protocol that queries `ownerOf(tokenId)` on the returned pointer address receives the attacker-controlled owner value even though no real CW721 mint/transfer semantics back it, demonstrating that the pointer accepted a non-conforming contract as a valid CW721 due to the missing interface/type check.

func (p PrecompileExecutor) AddCW721(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	cwAddr := args[0].(string)
	cwAddress, err := sdk.AccAddressFromBech32(cwAddr)
	if err != nil {
		return nil, 0, err
	}
	res, err := p.wasmdKeeper.QuerySmartSafe(ctx, cwAddress, []byte("{\"contract_info\":{}}"))
	if err != nil {
		return nil, 0, err
	}
	formattedRes := map[string]interface{}{}
	if err := json.Unmarshal(res, &formattedRes); err != nil {
		return nil, 0, err
	}
	name := formattedRes["name"].(string)
	symbol := formattedRes["symbol"].(string)
	contractAddr, err := p.evmKeeper.UpsertERCCW721Pointer(ctx, evm, cwAddr, utils.ERCMetadata{Name: name, Symbol: symbol})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
