### Title
Unbounded recursion in outer-puzzle driver matching allows a stack-overflow denial of service when parsing an attacker-supplied offer or coin spend - ([File: chia/wallet/outer_puzzles.py])

### Summary
The `protobuf.js` advisory shows that a decoder which recurses on untrusted nested input without any depth limit can be driven to exhaust the call stack and crash the process. The Chia wallet's outer-puzzle "driver" framework has the same structural weakness: `match_puzzle()` and the various `*OuterPuzzle.match()`/`get_inner_puzzle()`/`get_inner_solution()`/`construct()`/`solve()` methods recurse through an attacker-controlled chain of curried puzzle layers (the `"also"` chain) with no depth bound, and this code path is reached directly from parsing an untrusted offer file or an untrusted coin spend's puzzle reveal.

### Finding Description
`match_puzzle()` in [1](#0-0)  tries each registered driver's `match()` on an `UnknownPuzzle`. Each driver (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`, …) calls back into `self._match` (which is `match_puzzle` itself) on the puzzle's inner layer whenever it recognizes the outer mod, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

The same recursive pattern also appears in `get_inner_puzzle()` / `get_inner_solution()` / `construct()` / `solve()` on all of these drivers, and in `PuzzleInfo.check_type()` ( [5](#0-4) ), which recurses over the `"also"` chain with no limit either.

Nothing in this call chain bounds recursion depth by a puzzle-layer count, a CLVM cost, or `sys.setrecursionlimit`. The only thing that "limits" the number of layers is how many times an attacker can curry one recognized outer mod inside another — and the codebase's own tests demonstrate this is trivial: `test_cat_outer_puzzle.py` nests a `CAT` puzzle inside a `CAT` puzzle (`double_cat_puzzle`) at [6](#0-5)  and `test_cr_outer_puzzle.py` does the same for the credential-restricted layer at [7](#0-6) . There is no consensus rule stopping an attacker from nesting thousands of such layers in a single puzzle reveal — CLVM tree construction/currying cost is comparatively cheap and each layer only adds a fixed small amount of program size, well within block/solution size limits.

This is the direct analog of the protobuf.js bug: a decoder (`match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve`, and `PuzzleInfo.check_type`) recurses proportionally to attacker-controlled nesting depth in untrusted input, with no depth cap, risking a Python `RecursionError`/native stack overflow.

Chia's own `sha256_treehash()` deliberately avoids this exact class of bug by using an explicit iterative stack instead of recursion ( [8](#0-7) , [9](#0-8) ), and the doc comment in `.cursor/context/types.md` even calls this out as a "robustness property" — but the outer-puzzle driver framework built later does not follow this contract.

### Impact Explanation
This code path is reachable by an unprivileged **offer counterparty** or via ordinary **wallet sync** of coins the local wallet is a party to:
- `Offer.from_spend_bundle()` calls `match_puzzle(UnknownPuzzle(known_program=coin_spend.puzzle_reveal))` on every coin spend in an attacker-crafted offer file ( [10](#0-9) ).
- `Offer._get_offered_coins()` (called while examining/accepting an offer) calls `match_puzzle`, then `get_inner_puzzle`/`get_inner_solution`, then `construct_puzzle`, on parent puzzle reveals taken directly from the untrusted spend bundle ( [11](#0-10) ).
- `TradeManager.check_for_final_modifications()`/`check_for_requested_payment_modifications()` call `puzzle_info.check_type(...)` on driver info built from the same untrusted offer ( [12](#0-11) ).

A crafted offer file (or a coin spend a wallet is asked to inspect) with a sufficiently deep chain of nested recognized outer layers (e.g., CAT-in-CAT, singleton-in-singleton, CR-in-CR) would drive Python's recursion depth to its limit, raising an uncaught `RecursionError` (or, in worse cases, a native stack overflow inside CPython that can crash the interpreter outright, since some of this recursion happens through native `dataclass`/property machinery). Because offer inspection happens automatically as part of normal wallet UX (viewing/accepting an offer, or even just wallet coin sync attributing hints/additions), this is a spend-triggered/offer-triggered denial of service against the wallet process — a legitimate CWE-674 analog with practical availability impact for a wallet user or offer counterparty.

### Likelihood Explanation
Likelihood is high: constructing deeply nested, mutually-recognized outer puzzle layers (CAT-in-CAT, singleton-in-singleton, etc.) requires no special privilege, no valid signature, and no on-chain confirmation — it only requires crafting a `SpendBundle`/offer file with a puzzle reveal that curries one recognized mod inside another repeatedly, which is well within CLVM program size and typical wallet resource constraints. No existing code path enforces a maximum "also"/outer-layer depth before recursively processing it.

### Recommendation
- Convert the mutually recursive `match_puzzle`/`get_inner_puzzle`/`get_inner_solution`/`construct`/`solve` driver chain and `PuzzleInfo.check_type()`/`PuzzleInfo.also()` traversal into an explicit iterative loop with a bounded stack (mirroring the pattern already used in `sha256_treehash()`), or
- Enforce an explicit maximum outer-puzzle-layer nesting depth before attempting to match/construct/solve, rejecting (with a clear `ValidationError`) any puzzle reveal or offer whose recognized-layer chain exceeds that bound.
- Apply the same treatment to any other untrusted-input-driven recursive puzzle/PuzzleInfo traversal in the wallet (e.g., `recursive_uncurry_dump` in debug tooling, `_sexp_replace` in `program.py`) if they can be reached from untrusted spend data.

### Proof of Concept
1. Build `inner = Program.to(1)` (or any ACS puzzle).
2. Repeatedly wrap it N times (e.g., N = 5,000–50,000, tuned to exceed the Python recursion limit) using any of the recognized outer-layer constructors that are demonstrated to nest in the existing tests, e.g. `construct_cat_puzzle(CAT_MOD, tail, construct_cat_puzzle(CAT_MOD, tail, ...))` as shown in [6](#0-5) , or nest `construct_cr_layer` as in [7](#0-6) .
3. Package the resulting puzzle reveal into a `CoinSpend`/`WalletSpendBundle`, and construct an `Offer` from it via `Offer.from_spend_bundle()` ( [10](#0-9) ), or simply call `match_puzzle(UnknownPuzzle(known_program=puzzle_reveal))` directly ( [1](#0-0) ).
4. Observe that the recursive `match`/`get_inner_puzzle` calls raise `RecursionError` (or crash the process) well before the puzzle's actual CLVM cost or block/solution size limits are reached, demonstrating the DoS.

Note: I was not able to execute this PoC in this environment (no code execution/filesystem access), so the exact nesting depth required to trigger `RecursionError` under CPython's default recursion limit was not empirically measured here — this should be validated by a Devin session with code execution.
