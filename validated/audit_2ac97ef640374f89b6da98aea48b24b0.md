### Title
Reward forfeiture in `vlMGPBaseRewarder` can be reset to zero via `cancelUnlock()`, letting users game the unlock cool-down and permanently avoid ceding yield to other lockers - (File: `rewards/vlMGPBaseRewarder.sol`, `VLMGP.sol`)

### Summary
The reported bug class is: a value used to size a fee/forfeit charged on withdrawal is computed from a snapshot of user state that can be manipulated by timing withdraw/re-enter actions, letting an attacker dodge the fee that should be shared with other participants. The same structural flaw exists in `vlMGPBaseRewarder`'s reward-forfeiture logic, which relies on `VLMGP.getRewardablePercentWAD()` — a value that can be reset to 100% at will via `cancelUnlock()`, erasing accrued forfeiture that should otherwise be redistributed to other vlMGP holders.

### Finding Description
`vlMGPBaseRewarder` accrues rewards for every account based on the account's full vlMGP balance (`balanceOf`, locked + in-cooldown) [1](#0-0) , but only assesses a "forfeit" (a fee redistributed to other stakers) at claim time, computed from the account's *current* `getRewardablePercentWAD()`: [2](#0-1) 

`getRewardablePercentWAD()` in `VLMGP.sol` computes 100% (no forfeit) while a user's cool-down slot has not yet passed `endTime`, and only starts degrading the rewardable percentage once the slot's `endTime` has elapsed and the user has not yet called `unlock()`: [3](#0-2) 

Critically, `cancelUnlock()` unconditionally zeroes out `slot.amountInCoolDown` for any slot flagged as "in cool down", with no distinction for whether the cool-down period has already elapsed and forfeiture has begun accruing: [4](#0-3) 

This is different from `unlock()`, which explicitly reverts if `endTime > block.timestamp` [5](#0-4)  — showing that a separate, explicit `endTime` check is required elsewhere in the contract but is absent from `cancelUnlock()`. As a result, `cancelUnlock()` can be called on a slot whose `endTime` has already passed (i.e., where forfeiture has already begun accruing against the user under `getRewardablePercentWAD`), instantly restoring `getUserTotalLocked` to include the full amount and resetting the user's rewardable percentage back to 100% before the user ever calls `getReward()`. Because the forfeit is computed lazily and only at the moment of claim, an attacker can:
1. Let an unlock slot's cool-down complete and simply not call `unlock()` (avoiding paying the time-decaying forfeit that would otherwise apply to accumulated `vlMGPBaseRewarder` rewards for that portion),
2. Call `cancelUnlock()` on the completed slot right before calling `getReward()`, resetting `getRewardablePercentWAD()` back to 100%,
3. Claim `getReward()` with zero forfeit deducted via `_calExpireForfeit`,
4. Optionally restart a new unlock cycle to repeat the cycle indefinitely.

### Impact Explanation
The forfeit amount that should be deducted from a user's rewards and redistributed to other vlMGP holders via `_queueNewRewardsWithoutTransfer` [6](#0-5)  can be permanently avoided by any unprivileged wallet timing its `cancelUnlock()`/`unlock()` calls. This constitutes direct theft of unclaimed yield from other, honest vlMGP lockers who would otherwise receive the forfeited amount, matching the accepted impact category of "theft ... of unclaimed yield."

### Likelihood Explanation
The exploit requires only ordinary wallet transactions (`startUnlock`/waiting/`cancelUnlock`/`getReward`) available to any vlMGP holder, with no privileged role, oracle, or external protocol dependency. It is deterministic and repeatable, requiring only that the attacker wait for a cool-down slot to fully elapse before canceling it, so likelihood is high for any user monitoring their own positions.

### Recommendation
Assess and lock in the forfeit amount at the moment a cool-down slot's `endTime` elapses (or accrue/checkpoint the forfeit continuously) rather than recomputing `getRewardablePercentWAD()` lazily from live, resettable state. `cancelUnlock()` should either be disallowed once `endTime` has passed, or should itself trigger settlement of any forfeit that has already accrued for that slot before resetting `amountInCoolDown`.

### Proof of Concept
1. User locks MGP in `VLMGP` and accrues `vlMGPBaseRewarder` rewards proportional to `balanceOf` (full locked+cooldown balance).
2. User calls `startUnlock` for a slot; the slot's cool-down passes `endTime` without the user calling `unlock()`.
3. Per `getRewardablePercentWAD` [7](#0-6) , the rewardable percentage for that stale slot begins to decay the longer it is left unclaimed, meaning if the user called `getReward()` now, `_calExpireForfeit` would deduct a growing forfeit.
4. Instead, the user calls `cancelUnlock(slotIndex)` [4](#0-3) , which zeroes `amountInCoolDown` regardless of elapsed time, restoring `getUserTotalLocked` and thus `getRewardablePercentWAD` to 100%.
5. The user then calls `getReward()` on `vlMGPBaseRewarder`; `_calExpireForfeit` returns 0 forfeit [8](#0-7) , and the user receives their full accrued reward with no share redistributed to other stakers.
6. This can be repeated indefinitely by restarting the unlock cycle, permanently denying other vlMGP holders their expected share of forfeited rewards.

Note: full verification of `_checkInCoolDown()`'s exact conditions was not completed due to reaching the tool-call limit; based on `unlock()` containing its own explicit, separate `endTime` check, `_checkInCoolDown()` most likely only validates `amountInCoolDown > 0` rather than the cool-down time window, which is the basis for this finding. A Devin session with full repository access can confirm this function's exact implementation to conclusively validate the PoC.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
