### Title
Exact-string `RuleEngine._matches_tool` tool_matcher allows dangerous file-write operations to bypass block rules via unlisted synonymous tool (MultiEdit) - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._matches_tool` performs a literal, pipe-delimited exact-string comparison of `tool_name` against a rule's `tool_matcher` with no awareness that `Edit`, `Write`, and `MultiEdit` are treated elsewhere in the same plugin as equivalent "file" operations. A block rule authored (in the plugin's own documented style) as `tool_matcher: "Edit|Write"` will never fire against an equivalent dangerous mutation performed through `MultiEdit`, even though `MultiEdit`'s `file_path`/`edits[].new_string` fields are fully supported by the condition-matching logic.

### Finding Description
`_rule_matches` first checks `rule.tool_matcher` via `_matches_tool` and returns `False` immediately if it doesn't match, before any condition (e.g. secret/dangerous-pattern regex) is evaluated: [1](#0-0) 

`_matches_tool` implements only exact membership in a pipe-split list, or the literal `'*'` wildcard — no regex, no case normalization, and no notion that `Edit`, `Write`, and `MultiEdit` are semantically the same "file" capability: [2](#0-1) 

Yet the plugin's own hook scripts (`pretooluse.py`, `posttooluse.py`) treat these three tools as one equivalence class when bucketing rules by `event`: [3](#0-2) 

And `_extract_field` fully implements field extraction for `MultiEdit` (`file_path`, concatenated `new_string` across `edits`), meaning conditions written for the "file" event class are semantically capable of catching dangerous content via `MultiEdit` just as well as via `Edit`/`Write`: [4](#0-3) 

Because `tool_matcher` is a free-form override field independent of the `event` bucketing (`tool_matcher: Optional[str] = None  # Override tool matching`), a rule author following the plugin's own documented matcher style (`"Read|Write|Edit"`, as shown in `plugins/plugin-dev/skills/hook-development/SKILL.md:396`) but omitting `MultiEdit` produces a block rule that silently never fires for `MultiEdit`-based edits, despite the rule's condition (e.g. a regex for secrets or `rm -rf`-equivalent dangerous content) being fully capable of matching the same payload if it were delivered via `Edit` or `Write`. [5](#0-4) 

### Impact Explanation
A block rule intended to deny a dangerous file mutation (e.g., writing to `.env`, injecting a malicious script, or overwriting a sensitive file with attacker-controlled content) can be silently bypassed by performing the equivalent mutation through `MultiEdit` instead of the enumerated `Edit`/`Write` tools in the `tool_matcher`. Since Claude's tool selection can be steered by prompt-injection content in ordinary repository files, issues, or automation instructions, this is a real path to unauthorized file/command-adjacent action that bypasses the hookify approval/deny control layer, matching the "Unauthorized local command execution that bypasses Claude Code approval or deny controls" impact class (in this case, unauthorized file-mutation enforcement bypass reachable through the same hook-controlled surface).

### Likelihood Explanation
This requires no elevated privileges — only that: (1) a defender has configured a block rule scoping `tool_matcher` to a subset of the synonymous file-editing tools (a pattern directly mirrored by the plugin's own documentation), and (2) the attacker can influence tool selection toward the unlisted tool (`MultiEdit`) via ordinary prompt-injection content. Given the plugin's documentation encourages exactly this kind of pipe-separated tool list without warning that `MultiEdit` must always be included alongside `Edit`/`Write`, this misconfiguration is plausible and the bypass is fully deterministic and repeatable once present.

### Recommendation
Make `_matches_tool` aware of tool synonym groups (or normalize tool names to their `event` class before matching) so that a `tool_matcher` targeting "file" tools automatically covers `Edit`, `Write`, and `MultiEdit` together, rather than relying on rule authors to enumerate every current and future synonymous tool name. Alternatively, require/derive `tool_matcher` values from the same `event`-to-tool mapping used in `pretooluse.py`/`posttooluse.py` so the two enforcement layers cannot diverge, and add validation/warnings when a `file`-event rule's `tool_matcher` omits any tool from that mapping.

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules`:
1. Construct a `Rule` with `event="file"`, `action="block"`, `tool_matcher="Edit|Write"`, and a condition `field=new_text, operator=regex_match, pattern="SECRET_KEY"`.
2. Call `engine.evaluate_rules([rule], {"tool_name": "Edit", "tool_input": {"file_path": "config.py", "new_string": "SECRET_KEY=abc"}})` — assert the result contains a `deny`/block response.
3. Call `engine.evaluate_rules([rule], {"tool_name": "MultiEdit", "tool_input": {"file_path": "config.py", "edits": [{"new_string": "SECRET_KEY=abc"}]}})` — assert (per the bug) the result is `{}` (allowed), demonstrating that the identical dangerous content bypasses the block rule solely because `MultiEdit` isn't in `tool_matcher`, violating the invariant "a matching block rule must reliably deny the protected operation."

```python
    def _matches_tool(self, matcher: str, tool_name: str) -> bool:
        """Check if tool_name matches the matcher pattern.

        Args:
            matcher: Pattern like "Bash", "Edit|Write", "*"
            tool_name: Actual tool name

        Returns:
            True if matches
        """
        if matcher == '*':
            return True

        # Split on | for OR matching
        patterns = matcher.split('|')
        return tool_name in patterns
```
