### Title
Empty DLEq statement verifies without checking any point equality - (File: crypto/dleq/src/lib.rs)

### Summary
`DLEqProof::verify` accepts `generators == []` and `points == []` because it only rejects unequal lengths, then iterates over zero statements and compares the submitted challenge against the transcript-derived challenge. [1](#0-0)  Consequently, a proof whose serialized `c` matches the empty-statement challenge verifies regardless of `s` and without proving knowledge of any discrete logarithm. [2](#0-1) 

### Finding Description
The verifier fails to enforce the implicit non-vacuity precondition of a DLEq proof. After the length check, `verify` domain-separates the transcript, executes no per-generator/per-point statements when both slices are empty, derives the Fiat-Shamir challenge, and accepts if `self.c` equals it. [3](#0-2)  `DLEqProof::read` exposes this path to untrusted bytes by reading only canonical scalar encodings and not requiring a non-empty relation. [2](#0-1) 

### Impact Explanation
An unprivileged caller can make an application accept a serialized DLEq proof for an empty generator/point relation without supplying a valid witness or even a meaningful `s` value. [4](#0-3)  The proof is forgeable because the challenge is deterministic and public for the supplied transcript state: for an empty statement, the transcript receives only the `b"dleq"` domain separator before challenge derivation. [5](#0-4) 

### Likelihood Explanation
The attack only requires the verifier to call `DLEqProof::read` and then `verify` with attacker-controlled or otherwise empty `generators` and `points` slices. [6](#0-5) [2](#0-1)  No malicious validator, private key, protocol secret, or invalid curve encoding is needed; both scalar fields are parsed only with canonical `read_scalar`. [7](#0-6) 

### Recommendation
Reject empty relations in `DLEqProof::verify`, and apply the same check to `prove` so the prover and verifier agree that a DLEq proof must bind at least one generator/point pair. [8](#0-7) [6](#0-5)  `MultiDLEqProof::verify` should similarly reject zero discrete logarithms and empty inner series rather than allowing a vacuous challenge comparison. [9](#0-8) 

### Proof of Concept
```rust
// Conceptual PoC for a ciphersuite group G and caller-selected Transcript T.

let generators: &[G] = &[];
let points: &[G] = &[];

// Obtain the exact challenge expected by an empty DLEq transcript.
// This can be produced by prove(..., &[], &any_scalar) because no statement binds
// that scalar or nonce.
let proof = DLEqProof::<G>::prove(
    &mut rng,
    &mut verifier_transcript.clone(),
    generators,
    &Zeroizing::new(G::Scalar::ZERO),
);

// Serialize it, optionally corrupt/change `s`, and deserialize it through the
// public read path. `s` is not consumed for an empty relation.
let mut bytes = proof.serialize();
// Replace the second scalar with an arbitrary canonical scalar.
bytes[scalar_len..].copy_from_slice(G::Scalar::ONE.to_repr().as_ref());
let forged = DLEqProof::<G>::read(&mut &bytes[..]).unwrap();

// Passes: equal lengths, no statements are queued, and `c` still matches the
// deterministic empty-statement challenge.
forged.verify(&mut verifier_transcript, generators, points).unwrap();
```

`prove` appends no generator, nonce, or point messages when `generators` is empty, so its challenge is independent of the selected scalar and nonce. [10](#0-9)  During verification, the loop over `zip(generators, points)` executes zero times, leaving only the same domain separator and making the altered `s` irrelevant. [4](#0-3)
