### Title
Crafted FROST preprocess forces `R = ∞`, panicking BIP-340 `Hram` and crashing honest signers - (File: networks/bitcoin/src/crypto.rs)

### Summary
`Secp256k1::read_G` accepts the point at infinity, and a malicious FROST participant can craft their nonce commitments so the aggregated nonce `R` is exactly the point at infinity. The BIP-340 `Hram` in `networks/bitcoin/src/crypto.rs` calls `x(R)`, which `expect`s a non-infinity point and panics. This is reachable by an unprivileged co-signer via `read_preprocess` followed by `sign`, producing a deterministic remote denial of service — the same bug class as CVE-2017-17722 (reachable assertion via crafted input).

### Finding Description
`Hram::hram` calls `x(R)` and `x(A)`, where `x` does `key.to_encoded_point(true).x().expect("point at infinity")` — panicking on the identity point [1](#0-0) . `hram` is invoked from `Schnorr::sign_share` with `nonce_sums[0][0]` [2](#0-1) .

`nonce_sums` is `B.nonces(&nonces)`, computed in `BindingFactor::nonces` as `D + Σ rho_l * E_l`, i.e. `commitment_D_l + rho_l * commitment_E_l` per participant [3](#0-2) . Both `D` and `E` are attacker-controlled points read via `GeneratorCommitments::read` → `Curve::read_G` [4](#0-3) , which accepts any canonically encoded point including the identity [5](#0-4) .

An attacker who submits their preprocess last computes every other participant's bound contribution `S = Σ_{l≠i} (D_l + rho_l·E_l)` (all inputs public: `rho` is derived from the preprocess transcript, and `E_i = ∞` makes `rho_i·E_i = 0` regardless of the challenge). They then set `D_i = -S`, forcing `nonce_sums[0][0] = identity`. Every honest signer calling `sign` reaches `sign_share` → `hram` → `x(∞)` and panics [6](#0-5) . No participation index, threshold, or canonicality check rejects the commitment — only the infinity-encoding acceptance in `read_G` matters.

### Impact Explanation
A single malicious participant in a Bitcoin FROST signing session deterministically crashes every honest signer's process during `sign`. For the processor, which runs this `Schnorr` algorithm for Bitcoin outputs, a crashed signer aborts the signing round and halts the multisig — a remote denial of service on fund movement. The code's own comment claims this "negligible probability ... even with malicious participants present" [7](#0-6) , which is incorrect: the attacker does not need luck, they algebraically force `R = ∞`.

### Likelihood Explanation
Reachable by any party able to submit a preprocess message to an honest signer (a co-signer in the multisig, i.e. a validator in the threshold — reachable via the `read_preprocess`/`sign` path the scope permits). Requires only crafting two point encodings: `E = infinity` and `D = -(sum of others' bound contributions)`. Deterministic, no grinding. Severity Medium: DoS only, no key/share leakage (the victim's nonce is never used in a published share since signing panics before broadcasting).

### Recommendation
Reject the identity point in `Commitments::read`/`GeneratorCommitments::read` (check `bool::from(point.is_identity())` and return an `io::Error`), and/or make `x()`/`x_only()` return `Option`/`io::Result` instead of panicking so `sign_share` surfaces `FrostError` rather than crashing. A defense-in-depth check in `BindingFactor::nonces`/`Schnorr::verify` that rejects identity `R` would also close the hole for other `Hram` implementations.

### Proof of Concept
```rust
// Attacker is included participant i; all other preprocesses already received.
// Secp256k1 Schnorr: nonces() = vec![vec![G]] — one nonce, one generator.

// 1. Compute S = sum over other participants of their bound contributions.
//    For each l: rho_l = Secp256k1::hash_binding_factor(rho_transcript + participant_l)
//    contribution_l = commitments[l].nonces[0].generators[0].0[0]
//                   + rho_l * commitments[l].nonces[0].generators[0].0[1]
//    (rho_transcript is computable: it binds group_key, hash_msg(msg), and
//     hash_commitments(challenge over all preprocess transcripts — attacker's own
//     preprocess contributes commitments that are fully attacker-chosen and do not
//     affect the others' rho_l, which are computed before the attacker's binding
//     factor is needed).

// 2. Attacker preprocess: generators[0] = GeneratorCommitments([-S, infinity]).
//    Encoded as [(-S).to_bytes(), 0x00 * 33] — read_G accepts both.

// 3. Victim: machine.read_preprocess(&mut bytes).unwrap()  // succeeds
//           machine.sign(preprocesses, msg)                // -> sign_share ->
//           Hram::hram(&nonce_sums[0][0] /* = infinity */, &group_key, msg)
//           -> x(R) -> expect("point at infinity")          // PANIC
```

Note: `E_i = ∞` neutralizes the attacker's own `rho_i` term (`rho_i · ∞ = ∞` in the additive sum contributes identity), so `D_i = -S` alone zeroes the aggregate `R`. The panic occurs identically in `complete`'s `verify` path if `sign_share` were somehow bypassed, since `verify` → `sig.verify` → challenge recomputation also hits `x(∞)`.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))

      Err(io::Error::other("non-canonical point"))?;
