## Analysis

The relevant binding the code is supposed to enforce is:

**Intended:** `operator_xonly_pk_in_OP_RETURN == identity_of_the_party_that_actually_funded_the_payout_tx`

**Actually checked in `Verifier::is_kickoff_malicious`:**
`operator_xonly_pk_in_OP_RETURN == kickoff_data.operator_xonly_pk` [1](#0-0) 

The problem is that the left side of both equalities is populated purely from unauthenticated OP_RETURN bytes. `update_finalized_payouts` parses whichever OP_RETURN happens to be in the mined payout tx and stores it with no check on who actually paid for the tx: [2](#0-1) 

And `create_payout_txhandler` shows why this OP_RETURN is unauthenticated: the only Schnorr signature attached to the payout tx is the user's `SinglePlusAnyoneCanPay` signature over the withdrawal input, and under `SIGHASH_SINGLE` that signature only commits to the *single corresponding output* (index 0, the user's payout output), never to output 2 (the OP_RETURN) or output 1 (the anchor): [3](#0-2) [4](#0-3) 

Because `AnyoneCanPay` also permits arbitrary extra inputs to be attached, **anyone** holding a validly-signed `SinglePlusAnyoneCanPay` withdrawal input (e.g., the withdrawing user themselves, who legitimately creates and controls that signature via `parse_withdrawal_sig_params`) [5](#0-4)  can construct their own version of the payout transaction, fund it with their own BTC, and stamp the OP_RETURN with *any* operator's real, public xonly pubkey — including one who never funded anything. This is exactly the transaction that `Operator::withdraw` normally builds honestly with `self.signer.xonly_public_key` [6](#0-5) , but nothing prevents a third party from building the same shape of transaction with a forged OP_RETURN.

Once this forged payout is mined and finalized, the targeted operator X's **own automation** — not an attacker action — completes the exploit: `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered only by the (forged) `payout_payer_operator_xonly_pk` column [7](#0-6) , then calls `handle_finalized_payout`, which claims a kickoff connector and eventually leads to a `Reimburse` transaction crediting X [8](#0-7) . When the verifiers later run `is_kickoff_malicious` on X's resulting kickoff, `operator_xonly_pk_opt` (== X, from the forged OP_RETURN) trivially equals `kickoff_data.operator_xonly_pk` (== X, genuinely X's key, since X really is the one who later has to broadcast the kickoff with its own key), so the function returns `Ok(false)` — "not malicious" — even though X never funded the underlying payout.

None of the listed guards catch this: `is_kickoff_malicious` only compares the two attacker-influenced/legitimate-looking pubkeys to each other [9](#0-8) ; `update_finalized_payouts` performs no signature/funding-source check on the OP_RETURN [10](#0-9) ; and `validate_payer_is_operator`, used only inside the operator's own client-side reimbursement-tx-fetch helper, checks `payer_xonly_pk == self.signer.xonly_public_key` [11](#0-10)  — which is exactly the field that was forged, so it also passes.

### Title
Unauthenticated payout OP_RETURN lets anyone forge operator attribution, causing an operator to be reimbursed for a payout it never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::is_kickoff_malicious` and the underlying `payout_payer_operator_xonly_pk` DB column trust the OP_RETURN of the mined payout transaction to identify who fronted a withdrawal, but that OP_RETURN output is not covered by the user's `SinglePlusAnyoneCanPay` signature (which only commits to the single corresponding output, index 0). Anyone who funds the payout output with their own money can therefore stamp any operator's real xonly pubkey into the OP_RETURN, causing that operator's own honest automation to later claim a `Reimburse` transaction for a payout it never funded, while `is_kickoff_malicious` reports the resulting kickoff as non-malicious.

### Finding Description
Binding claimed to hold: `operator_xonly_pk_opt (DB, from OP_RETURN) == kickoff_data.operator_xonly_pk` implies "the operator named in the kickoff is the one who paid for the withdrawal." In reality this equality is checked, but the left-hand side has no cryptographic tie to the party who funded the transaction, only to whatever bytes were placed in output index 2 of the mined payout tx (`get_first_op_return_output` / `parse_op_return_data` in `update_finalized_payouts`, `core/src/verifier.rs:2312-2342`). The payout tx's only signature (`SinglePlusAnyoneCanPay`, verified in `Operator::withdraw`/`create_payout_txhandler`, `core/src/operator.rs:630-637`, `core/src/builder/transaction/operator_reimburse.rs:407-436`) is `SIGHASH_SINGLE|ANYONECANPAY`, which per `calculate_pubkey_spend_sighash` (`core/src/builder/transaction/txhandler.rs:210-233`) commits only to the input being signed and the output at the same index (index 0, the user's payout output) — never to the anchor (index 1) or OP_RETURN (index 2), and `AnyoneCanPay` permits arbitrary additional funding inputs added by anyone.

Exploit flow:
1. An unprivileged actor (the withdrawing user themselves, or anyone in possession of that user's `SinglePlusAnyoneCanPay` signature and the withdrawal input details) builds a payout-shaped transaction: input = the registered withdrawal UTXO with the user's `SinglePlusAnyoneCanPay` signature, output 0 = the user's payout (matching the committed amount/script), plus their own extra funding input(s) to cover the value, anchor output, and an OP_RETURN containing operator X's real, publicly known xonly pubkey (not their own).
2. Attacker broadcasts and confirms this transaction before any operator's genuine payout for that withdrawal.
3. `update_finalized_payouts` stores `payout_payer_operator_xonly_pk = X` from the OP_RETURN with no check that X actually signed/funded anything.
4. X's own `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-106`) picks up this "unhandled payout" (matched purely by the forged pubkey column) and automatically calls `handle_finalized_payout`, generating and broadcasting a genuine Kickoff transaction signed with X's real key, ultimately queuing a `Reimburse` transaction crediting X.
5. When verifiers process this kickoff, `is_kickoff_malicious` compares `operator_xonly_pk_opt` (== X, forged) to `kickoff_data.operator_xonly_pk` (== X, genuine) — they match, so the function returns `Ok(false)`, and no challenge is raised.

### Impact Explanation
Operator X's `Reimburse` transaction (bridge collateral `bridge_amount`) is credited to X for a payout X never funded — the explicit "operator reimbursed for a payout it never funded" Critical category. This breaks attribution invariants the slashing/challenge mechanism depends on: the false attribution and the kickoff's `operator_xonly_pk` trivially match, so an operator who took no legitimate risk collects reimbursement, while the actual funder (the attacker/withdrawing party) receives no credit in the protocol's bookkeeping. This is repeatable per withdrawal/deposit and against any operator whose xonly pubkey is public (all operator pubkeys are public protocol data), so the blast radius spans every deposit/withdrawal cycle in the system.

### Likelihood Explanation
No special privileges are required: the attacker only needs to be the withdrawing user (able to legitimately create a `SinglePlusAnyoneCanPay` signature for their own withdrawal per `parse_withdrawal_sig_params`) and enough BTC to fund the payout output themselves, then broadcast directly to the Bitcoin network before any operator's fronted version confirms. No verifier, operator, or aggregator credentials, key shares, or collateral are needed. Feasibility is high and the attack is repeatable across every withdrawal.

### Recommendation
Bind the OP_RETURN operator attribution to the actual funding party cryptographically — e.g., require the fronting operator's own signature (with a sighash type that commits to the OP_RETURN output, such as `SIGHASH_ALL` or `SIGHASH_SINGLE` over an index that includes it) over the full payout transaction including the OP_RETURN, and have `is_kickoff_malicious`/`update_finalized_payouts` verify that signature against the claimed `operator_xonly_pk` rather than trusting unauthenticated OP_RETURN bytes.

### Proof of Concept

1. Set up a deposit and its `move_to_vault_txid` as in existing e2e tests (`core/src/test/deposit_and_withdraw_e2e.rs`).
2. Build a payout transaction using `create_payout_txhandler` with the withdrawal UTXO/user signature, but set the OP_RETURN to a real registered operator X's xonly pubkey while adding a *different* actor's funding input (simulating attacker-funded, not-X-funded broadcast).
3. Call `db.update_payout_txs_and_payer_operator_xonly_pk` with `(idx, payout_txid, Some(X_xonly_pk), block_hash)` as `update_finalized_payouts` would after parsing this forged OP_RETURN.

6. Assert it returns `Ok(false)`, and assert (as the broken binding) that the actual funder of the payout tx (a different keypair used for the funding input) is **not** equal to `kickoff_data.operator_xonly_pk`/`X_xonly_pk`, demonstrating attribution and checked equality diverge from real-world funding.

    async fn update_finalized_payouts(

        block_id: u32,

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {

                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());

            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}
