### Title
Unbounded resubmission of soft-failing spend bundles starves the mempool's 2-worker validation pool, halting transaction processing - ([File: chia/full_node/full_node.py])

### Summary
`FullNode.add_transaction()` only records a spend bundle in the long-lived `seen_bundle_hashes` cache when `pre_validate_spendbundle()` raises a `ValidationError` (a hard, consensus-level rejection). When `pre_validate_spendbundle()` instead raises a plain `ValueError` (a "soft failure" — e.g. the internal duration/timeout guard, or the CLVM-cost `nice=(5, -fee_per_cost)` scheduling path), the transaction is *not* added to `seen_bundle_hashes`, so it can be resubmitted immediately and indefinitely by the same caller with no cooldown. [1](#0-0) 

### Finding Description
`pre_validate_spendbundle()` runs CLVM execution and BLS signature validation on a small dedicated thread pool (`MempoolManager.pool`, documented as 2 workers) and enforces a wall-clock `validation_timeout`/duration guard before returning, raising `ValueError` when the bundle is too slow or otherwise "soft"-invalid: [2](#0-1) 

In `add_transaction`, the spend bundle is marked `in_flight` before the expensive validation call, but on the `ValueError` branch the function returns directly with `MempoolInclusionStatus.FAILED` without ever calling `add_and_maybe_pop_seen(spend_name)` — only `remove_in_flight` runs (in the `finally` block): [1](#0-0) 

By contrast, the `ValidationError` branch explicitly keeps the bundle in `seen_bundle_hashes` "to prevent re-validation": [3](#0-2) 

This asymmetry is confirmed by the test suite, which documents the intended (but exploitable) behavior: on `ValueError`, the seen-cache entry must be removed so the transaction *can be retried*, while on `ValidationError` it is deliberately kept to avoid re-validation: [4](#0-3) [5](#0-4) 

Because only `ValidationError` (thrown for consensus-invalid bundles such as double-spend, bad puzzle, exceeded amounts, etc.) is "remembered," while `ValueError` (timeouts, and any other soft failure surfaced as `ValueError`, e.g. `raise ValueError(f"timeout {duration:0.4} s")` or the too-many-atoms/pairs checks) is not, an unprivileged caller (wallet RPC `push_tx`, or any peer via `send_transaction`/`respond_transaction`) can craft or select a spend bundle that reliably triggers the `ValueError` path — for instance one that is expensive enough to approach `validation_timeout` (or the `duration * 1e9/cost > validation_timeout*5` ns-per-cost heuristic) — and resubmit it in a tight loop. Each resubmission is neither deduplicated by `seen()`/`in_flight()` after completion, nor throttled, and each occupies one of the mempool's two dedicated validation worker threads for up to the timeout duration: [6](#0-5) 

With only 2 worker threads (per `.cursor/context/mempool.md` documentation of `MempoolManager.pool`), a small number of concurrently repeated submissions of such a bundle is sufficient to keep both workers permanently busy re-validating the same known-bad bundle, starving `pre_validate_spendbundle()` calls for legitimate, fee-paying transactions submitted by other users/peers at the same time — directly analogous to the DeversiFi incident where a single oversubmitted, repeatedly-rejected order was reprocessed over and over and blocked processing of other orders.

### Impact Explanation
This is a transaction-processing halt reachable purely from a single or few unprivileged spend-bundle submitters (no privileged access, no malicious peer/node assumption, no protocol-layer or crypto exploit needed). While it does not directly move funds or corrupt consensus state, it can deny mempool admission service to legitimate transactions for as long as the attacker keeps flooding the small worker pool, which is explicitly listed as an accepted impact category ("a spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood is moderate-to-high: constructing a spend bundle that reliably lands in the `ValueError` (soft-failure) branch of `pre_validate_spendbundle` (e.g. one that runs close to the timeout threshold, or one that is cheap to build but slow to execute) requires no special privileges, no signature forgery, and no fee payment (the failure occurs before/without needing to pass fee/capacity checks). The attacker only needs the ability to submit spend bundles repeatedly, which any wallet or peer can do via `push_tx` or `send_transaction`. [7](#0-6) 

### Recommendation
Treat `ValueError` (soft-failure) outcomes the same as `ValidationError` for seen-cache bookkeeping — or otherwise track a per-spend-bundle-hash (and/or per-peer) retry cooldown independent of the `seen`/`in_flight` sets — so that a bundle which failed the duration/cost heuristics cannot be resubmitted and re-validated on the scarce mempool worker pool without backoff. Consider also rate-limiting `add_transaction` calls per peer/spend-bundle-hash regardless of failure type.

### Proof of Concept
1. Craft (or select) a `SpendBundle` whose CLVM execution cost/time is tuned so that `validate_clvm_and_signature` completes but `pre_validate_spendbundle`'s duration guard trips, raising `ValueError(f"timeout {duration:0.4} s")`: [8](#0-7) 
2. Submit this bundle via RPC `push_tx` or protocol `send_transaction` repeatedly and concurrently (e.g., 2+ simultaneous submissions to saturate the 2-worker pool).
3. Observe that after each failure, `seen_bundle_hashes` does not contain the bundle hash (per `test_add_transaction_remove_seen_on_value_error`), allowing immediate resubmission: [9](#0-8) 
4. While this loop runs, submit a normal, valid, fee-paying transaction from another wallet and observe delayed `pre_validate_spendbundle` scheduling/execution due to worker-pool contention.

@pytest.mark.anyio
async def test_add_transaction_remove_seen_on_value_error(
    one_node_one_block: tuple[FullNodeSimulator, ChiaServer, BlockTools],
) -> None:
    """When pre_validate_spendbundle raises ValueError, the seen-cache entry
    must be removed so the transaction can be retried."""
    full_node_1, _server_1, _bt = one_node_one_block
    fn = full_node_1.full_node

    spend_bundle = make_spend_bundle(1)
    spend_name = spend_bundle.name()

    original_pre_validate = fn.mempool_manager.pre_validate_spendbundle

    async def raise_value_error(*_args: Any, **_kwargs: Any) -> SpendBundleConditions:
        raise ValueError("simulated soft failure")

    fn.mempool_manager.pre_validate_spendbundle = raise_value_error  # type: ignore[method-assign]
    try:
        status, err = await fn.add_transaction(spend_bundle, spend_name, test=True)
    finally:
        fn.mempool_manager.pre_validate_spendbundle = original_pre_validate  # type: ignore[method-assign]

    assert status == MempoolInclusionStatus.FAILED
    assert err == Err.INVALID_SPEND_BUNDLE
    assert not fn.mempool_manager.in_flight(spend_name)
    assert not fn.mempool_manager.seen(spend_name)
