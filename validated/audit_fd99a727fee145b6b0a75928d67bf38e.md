### Title
Payout attribution (`payout_payer_operator_xonly_pk`) is forgeable via a competing transaction because `SIGHASH_SINGLE|ANYONECANPAY` never commits to the OP_RETURN output - ([File: core/src/verifier.rs], [File: core/src/builder/transaction/operator_reimburse.rs], [File: core/src/operator.rs])

### Summary
The payout transaction's user-provided signature is verified against a sighash type chosen by the withdrawing user (an unprivileged party), and `create_payout_txhandler` signs the withdrawal input with a single key-spend witness while leaving the anchor and OP_RETURN outputs unauthenticated. When the sighash is `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` (the documented/expected flow), the signature only binds input 0 to output 0 (the recipient output); the OP_RETURN output carrying `operator_xonly_pk` (the payer attribution consumed later by `update_finalized_payouts`) is left completely outside the signed commitment, so anyone holding the same signature can rebroadcast a competing, double-spending transaction with an arbitrary/forged operator pubkey in place of the real payer's.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk` stored for withdrawal `i` == the xonly_pk of the operator whose funds actually paid output 0 of the confirmed payout transaction for withdrawal `i`.

Trace:
- `Operator::withdraw` (core/src/operator.rs:560-637) takes attacker-supplied `in_signature` (including its `sighash_type`) and `out_script_pubkey`, builds the payout tx via `create_payout_txhandler`, computes the sighash with `calculate_sighash_txin(0, in_signature.sighash_type)` and verifies it with `SECP.verify_schnorr` — no server-side enforcement forces a specific sighash flag beyond what the attacker chooses, and the documented/expected type is `SinglePlusAnyoneCanPay`. [1](#0-0) 
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the tx with one signed input (`SpendPath::KeySpend` with `user_sig` only) and three outputs: the recipient output (index 0), an anchor (index 1), and the OP_RETURN with `operator_xonly_pk` (index 2). [2](#0-1) 
- Under `SIGHASH_SINGLE|ANYONECANPAY`, the Schnorr signature commits only to input 0 and the output at the same index (index 0). Outputs 1 and 2 — including the OP_RETURN carrying the payer's `operator_xonly_pk` — are **not** covered by the signature, and additional inputs/outputs can be freely attached by anyone (that is the entire point of `ANYONECANPAY`, allowing an operator to add funding inputs later, per the docstring "Funding the withdrawal transaction using TxSender RBF option").
- `Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) later scans the confirmed block, finds whichever transaction actually spent the withdrawal UTXO, extracts its first OP_RETURN via `get_first_op_return_output`, and parses it with `parse_op_return_data`/`XOnlyPublicKey::from_slice` (core/src/verifier.rs:2319-2321) to set `operator_xonly_pk` used as `payout_payer_operator_xonly_pk` — with no cross-check that the party who funded the extra inputs is the same key referenced in the OP_RETURN. [3](#0-2) 

Exploit flow: the withdrawal-requesting attacker (who legitimately possesses `in_signature` since they produced it themselves for their own withdrawal) can, at any time before the honest operator A's payout tx confirms, build a second transaction spending the same withdrawal UTXO with:
- output 0 identical (same script/amount, satisfying the SINGLE-signed commitment),
- their own funding input(s) to cover the same amount A would have fronted,
- a forged OP_RETURN naming an uninvolved honest operator B's `operator_xonly_pk` instead of A's,
and get this version mined instead of A's (higher fee / first-seen / RBF race). Because the OP_RETURN and the extra funding inputs are outside the signed domain, this transaction is valid and indistinguishable from a legitimate one to `update_finalized_payouts`, which will then attribute the payout to B.

Existing guards do not close this: `SECP.verify_schnorr` in `Operator::withdraw` only verifies the recipient-output commitment, not who supplies the remaining outputs; `is_profitable` only checks profitability math, not payer identity; there is no on-chain binding (e.g., a signature/commitment from the actual fronting operator) tying the OP_RETURN content to the party who supplied the extra funding inputs.

### Impact Explanation
If a forged OP_RETURN is confirmed, the DB records an uninvolved, honest operator B as the payer of withdrawal `i` even though B never funded anything. Downstream, reimbursement/kickoff logic keyed on `payout_payer_operator_xonly_pk` (e.g. `is_kickoff_malicious`) will treat any kickoff by the real fronting operator A for this withdrawal as unattributed/malicious (A never appears as payer), while operator B — who did nothing — becomes the party expected to claim reimbursement or is exposed to being flagged for a payout it never made. This can result in an honest operator's collateral being burned or an honest operator permanently unable to be reimbursed for funds it actually fronted, both explicitly listed Critical impacts. The attack is repeatable per withdrawal and can target any operator pair, since the attacker only needs to be the withdrawal requester and does not need any privileged role.

### Likelihood Explanation
The attacker only needs to be an unprivileged withdrawal requester (able to call Citrea `withdraw`, choose `out_script_pubkey`, and produce `in_signature`/sighash flag for their own withdrawal) and enough BTC to front the same output-0 amount that the real operator would have fronted, plus fees to win the block-inclusion race. No verifier, operator, or aggregator keys are needed. This is feasible for any single withdrawal and is limited mainly by the attacker's willingness to front the withdrawal amount themselves (recovered to their own address) and by winning the race against the real operator's broadcast — both realistic given attacker controls fee rate and timing.

### Recommendation
Bind the OP_RETURN operator attribution cryptographically to the signature that authorizes spending the withdrawal UTXO, or otherwise ensure the fronting operator's identity cannot be swapped without invalidating the transaction — e.g., require `SIGHASH_ALL` (or a covenant/leaf that commits to all outputs) for the payout input so the OP_RETURN and funding structure cannot be altered by a third party, or have `update_finalized_payouts` independently verify that the source of the additional funding inputs corresponds to the operator named in the OP_RETURN before writing `payout_payer_operator_xonly_pk`.

### Proof of Concept
`cargo test` outline:
1. Set up a deposit and a withdrawal (as in existing withdrawal integration tests) with `in_outpoint`/`out_script_pubkey` controlled by the "attacker" test actor.
2. Have operator A call `Operator::withdraw`, obtaining the unbroadcast `payout_txhandler`/signature (do not broadcast it).
3. Using the same `in_signature` (with `SIGHASH_SINGLE|ANYONECANPAY`), construct a second transaction spending the same `in_outpoint`, with identical output 0, attacker-supplied funding input(s) covering the same amount, and an OP_RETURN encoding operator B's `xonly_public_key` instead of A's.
4. Broadcast/mine the attacker's transaction instead of A's.
5. Run the finalized-payout block processing path (`update_finalized_payouts`) and assert `payout_payer_operator_xonly_pk == B.xonly_public_key` even though B never funded anything.
6. Call `is_kickoff_malicious` (or the reimbursement path) for operator A's genuine kickoff attempt for this withdrawal and assert it is incorrectly treated as unattributed/malicious, and/or for operator B and assert B is exposed to being credited/penalized for a payout it never made.

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
