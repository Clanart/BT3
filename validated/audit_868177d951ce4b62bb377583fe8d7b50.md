### Title
Missing timestamp/staleness validation in `AppProxyVerification#query_string_valid?` allows indefinite replay of signed app-proxy requests - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` accepts any app-proxy request whose HMAC `signature` matches the recomputed value over the remaining query params, but it never inspects the `timestamp` parameter that Shopify includes in every signed app-proxy request. This is the same bug class as the reported `OmoOracle.convertUSDToToken()` issue: a value that carries freshness information (`updatedAt` in the oracle, `timestamp` in the app-proxy query string) is fetched/available but never checked against a staleness window before the signed data is trusted.

### Finding Description
`query_string_valid?` in `lib/shopify_app/controller_concerns/app_proxy_verification.rb` computes an HMAC over all query parameters except `signature` and does a constant-time compare against the supplied `signature`: [1](#0-0) 

The `timestamp` parameter is part of the signed payload (it's included in `calculated_signature`) but the module never verifies that `timestamp` is close to `Time.now`. As a result, a request+signature pair captured once (e.g., via a shared proxy, misconfigured logging, browser history, network capture, or a malicious storefront script that reads the outgoing proxy URL) remains valid forever and can be replayed by any anonymous actor directly against the app's App Proxy endpoint, bypassing Shopify entirely. [2](#0-1) 

The included test fixtures confirm `timestamp` is present in the signed query string but only its inclusion in the signature is exercised — no test asserts rejection of an old/expired timestamp: [3](#0-2) 

By contrast, the equivalent webhook path suffers the same gap: `WebhookVerification#verify_request` / `PayloadVerification#hmac_valid?` validate only the HMAC digest with no freshness/replay check at all: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who obtains one valid, signed app-proxy request (which is not secret-derived — it can leak via browser history, referrer headers, shared devices, proxies/CDNs, or logs since it travels as a GET query string) can replay it against the app's `AppProxyController`/any controller including `ShopifyApp::AppProxyVerification` at any point in the future, causing the app to process it as an authentic, current request from Shopify on behalf of the shop. Depending on what the app-proxy endpoint does (e.g., writing reviews, mutating shop data, granting content), this enables unauthorized state changes or data disclosure without needing the app secret.

### Likelihood Explanation
Likelihood is medium: exploitation requires capturing one previously-issued valid signed URL (no cryptographic secret needed), and app-proxy URLs are GET requests that commonly appear in browser history, shared links, proxies, or server logs, making passive capture plausible. The vulnerability is only reachable by unrelated/anonymous requestors hitting the storefront-facing App Proxy endpoint, matching the required unprivileged HTTP entry point.

### Recommendation
Add a staleness check on `timestamp` in `query_string_valid?` (or a dedicated method), rejecting requests where `Time.now.to_i - timestamp.to_i` exceeds an acceptable window (e.g., a few minutes), mirroring the recommendation from the original report to validate freshness before trusting a signed value. Apply the same timestamp/replay-window validation to `WebhookVerification`/`PayloadVerification` if a timestamp header is available, or otherwise adopt a nonce-based replay-protection mechanism for both flows.

### Proof of Concept
1. Capture a legitimate signed app-proxy request URL once, e.g.:
`GET /app_proxy/basic?shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd`
2. Wait an arbitrary amount of time (days/months later).
3. Replay the exact same URL against the app's App Proxy endpoint.
4. `query_string_valid?` recomputes the same HMAC over the same (stale) params and returns `true`, so `verify_proxy_request` allows the request through — as shown by the passing test that never varies or checks the `timestamp` age: [6](#0-5)

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
