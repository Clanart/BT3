This confirms the mechanism precisely: `DiffSelection.withSelectableLines` (`app/src/models/diff/diff-selection.ts:320-330`) only filters `divergingLines` by whether the numeric index is still present in `selectableLines` — it never compares line *content*, only index membership. Combined with `updateChangesWorkingDirectoryDiff` in `app-store.ts`, this produces a genuine content-integrity gap when the working tree changes between diff-load and commit.

### Title
Partial-commit line selection is preserved by numeric index, not content, allowing a concurrently modified working tree to silently redirect a user's selected lines onto different content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a file has a partial (line-level) commit selection open, GitHub Desktop reconciles that selection against a freshly loaded diff purely by numeric line index via `DiffSelection.withSelectableLines`. If the tracked file on disk changes between the time the diff/selection was captured and the time the working-directory diff is refreshed (e.g. from an external process, git hook, or another tool touching the file while Desktop is open), the same index can now correspond to entirely different content, yet the previously "selected" bit remains set. This causes the user to unknowingly stage/commit content they never reviewed or intended to include.

### Finding Description
`updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404-3513`) reloads the diff for the selected file and then reconciles the old partial selection against it: [1](#0-0) 

The code's own comment acknowledges the shortcut: it only removes selection bits for lines that are "no longer selectable" (out of range or turned into context lines) — it does not validate that a still-selectable index still refers to the same logical change.

`DiffSelection.withSelectableLines` implements exactly that shallow index-based filter: [2](#0-1) 

Because `divergingLines` stores raw numeric positions in the unified diff (`h.unifiedDiffStart + index`, see `app/src/lib/patch-formatter.ts:143-144`), a selection captured against diff version N is blindly replayed against diff version N+1 as long as the index count/shape happens to still fall within `isIncludeableLine()` bounds. There is no hash/content check tying a "selected" bit to the line's actual text.

The staging path that turns this selection into what actually lands in the commit is `formatPatch` (`app/src/lib/patch-formatter.ts:129-221`), which trusts `file.selection.isSelected(absoluteIndex)` purely on index, and `stageFiles`/`applyPatchToIndex` (`app/src/lib/git/update-index.ts:109-168`) which apply that patch to the index without any secondary confirmation from the user.

### Impact Explanation
This is a silent corruption of what the user commits/pushes: a user who has carefully reviewed and selected specific lines for a commit can end up committing (and later pushing) different content than what they saw and approved, without any warning dialog. This is especially dangerous in code-review/security-sensitive workflows where a user intentionally excludes certain lines (e.g. a debug statement or credential placeholder) from a commit — a race that flips the underlying content at the same index could cause that content to be included in the commit unnoticed.

### Likelihood Explanation
Requires a specific but realistic sequence: the user must have an open partial selection on a file, and the working tree file must change (in a way that preserves enough diff shape for the stale indices to remain "selectable") before the diff is reloaded/committed. This is plausible with format-on-save tooling, lint-staged/husky git hooks, editors auto-fixing on save, or any watched build/codegen step running concurrently with Desktop — none of which require admin rights or prior compromise, only a repository that ships such tooling (attacker-controlled repo content triggering local tools). The window is real because Desktop does not re-diff/re-validate at commit time beyond what `updateChangesWorkingDirectoryDiff` already (incompletely) does, and it does not diff the actual bytes ultimately staged against what was shown to the user in the diff viewer.

### Recommendation
When reconciling a partial selection against a newly loaded diff, validate identity by line content (or a stable hunk/line hash) rather than by raw numeric index — mirroring the report's core recommendation to require an exact match rather than a permissive "still in range" check. Concretely, `withSelectableLines`/`updateChangesWorkingDirectoryDiff` should drop (not preserve) any diverging line whose underlying text differs from what was recorded when the selection was made, and ideally the commit flow should re-diff the file immediately before staging and warn the user if the diff has changed since they last reviewed it.

### Proof of Concept
1. In a repository, modify `file.txt` to add 5 new lines; open it in Desktop's Changes view so its diff is loaded.
2. Use partial selection to select line index 10 only (a genuine local addition) and leave the diff view open (do not commit yet).
3. While Desktop is open, have an external process (e.g. a save hook, lint-staged runner, or `git checkout -- .` followed by reapplying a different patch) rewrite the file so that a new, unrelated addition ends up at the same absolute unified-diff index 10, while keeping the overall hunk shape/line count similar enough that `isIncludeableLine()` still marks index 10 as selectable.
4. Trigger a status refresh (Desktop periodically refreshes, or trigger manually); `updateChangesWorkingDirectoryDiff` reconciles the selection and keeps index 10 selected because it passes `withSelectableLines`.
5. Commit. `formatPatch` stages line 10's *new* content (which the user never saw or approved) because `isSelected(10)` is still true, even though the content at that index has silently changed — confirming the commit now contains unintended, unreviewed content.
