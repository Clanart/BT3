## Title
Missing `resolveWithin` containment check when opening committed/changed file paths from a malicious repository leads to file access outside the repo root - (File: `app/src/ui/app.tsx`)

### Summary
GitHub Desktop already has a purpose-built guard, `resolveWithin` (`app/src/lib/path.ts:36-100`), whose explicit job is to join a repository-relative path with the repository root and verify the resolved path does not escape that root. It is used in `dispatcher.ts`'s `openRepositoryFromUrl` before calling `shell.showItemInFolder` for a deep-link-supplied `filepath`. [1](#0-0)  However, the structurally identical operation — turning a repo-relative file path into a full path and handing it to a shell/editor-launching API — is repeated in several "sibling" call sites that instead do a raw `Path.join(repository.path, path)` with **no** containment check at all, most notably `onOpenInExternalEditor` in `app/src/ui/app.tsx`. [2](#0-1) 

### Finding Description
`resolveWithin` was written specifically to prevent a repo-relative path from resolving outside `repository.path`, including protection against absolute-path segments, null bytes, and symlink escapes (via `realpath` comparison). [3](#0-2)  It is invoked when handling `filepath` from an `x-github-client://openRepo/...` deep link before calling `shell.showItemInFolder(resolved)`: 

```ts
if (isAbsolute(filepath)) {
  log.error(`Refusing to open absolute path: ${filepath}`)
  return
}
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} ...
``` [1](#0-0) 

The equivalent code path for "Open in External Editor" from the Changes list / Commit view / Pull Request files view does not apply this guard at all. `app.tsx`'s `onOpenInExternalEditor` builds the full path with a bare `Path.join`:
```ts
private onOpenInExternalEditor = (path: string) => {
  const repository = this.state.selectedState?.repository
  if (repository === undefined) return
  const fullPath = Path.join(repository.path, path)
  this.props.dispatcher.openInExternalEditor(fullPath)
}
``` [2](#0-1) 

That `fullPath` is handed straight to `dispatcher.openInExternalEditor` → `appStore._openInExternalEditor`, which passes it to `launchCustomExternalEditor`/`launchExternalEditor` to spawn the user's configured editor on that path — no re-validation happens downstream. [4](#0-3) 

The same unguarded pattern (`Path.join(repository.path, file.path)`, then passed to `revealInFileManager`/`openFile`/`dispatcher.openInExternalEditor`) recurs in the Commit History file context menu, the Pull Request "Files changed" context menu, and the Copilot conflicts overflow menu: [5](#0-4) [6](#0-5) [7](#0-6) 

In every one of these, the `path`/`file.path` value originates from git-reported metadata (`git status`/`git diff` entries, `WorkingDirectoryFileChange`/`CommittedFileChange` objects) for a repository the user cloned or fetched, i.e. attacker-influenced content, exactly the attacker model the report calls out ("attacker controls a cloned/fetched repository"). Unlike the clone-path hardening already present elsewhere in this codebase (`isClonePathSensitive` in `clone.ts`, `sanitizeCloneName` in `remote-parsing.ts`), no equivalent containment check exists for these post-clone, path-join sites, and the one function that *does* implement the correct guard (`openRepositoryFromUrl`) demonstrates the developers are aware of and intend this class of check, but simply omitted it from the sibling call sites — the same "missing modifier that its counterparts have" pattern as the original report.

### Impact Explanation
If a crafted or low-level-manipulated git object (e.g., created via plumbing commands like `hash-object`/`mktree`/`update-index` rather than normal `git add`, which enforce fewer path restrictions than the porcelain layer) causes a tracked path containing traversal sequences (`../`) or a Windows-style backslash-based traversal to appear in `git status`/`git diff` output, Desktop will compute a `fullPath` outside the repository root and pass it unchecked to `shell`-level operations (open in editor, reveal in file manager, open with default program). This can result in launching the user's editor, default OS handler, or file manager against arbitrary files/paths outside the intended repository — a "file read/open outside the repo" primitive, and depending on the OS handler for the resolved file type, potentially command/code execution (e.g. opening a `.desktop`/`.lnk`/`.scr`/`.command` styled path with an OS-default handler).

### Likelihood Explanation
Exploitation is not trivial to fully confirm from static analysis alone: whether current Git versions still allow such paths to reach `git status`/`git diff` output for an unchecked-out object (rather than being rejected at checkout time by `core.protectNTFS`/`core.protectHFS`) was not verified in this pass, and downstream OS-handler behavior for a resolved path is platform dependent. This uncertainty should be validated with a proof-of-concept repository before treating this as fully confirmed. That said, the underlying design flaw — the containment guard existing in one call path but omitted from several structurally identical ones — is unambiguous and independently worth fixing regardless of how easy it is to inject a traversal-bearing path today, since any future change loosening git's own path validation would immediately become exploitable here with zero additional Desktop-side changes.

### Recommendation
Route every place that joins a repository-relative, git-reported `file.path` with `repository.path` before invoking a shell/editor/file-manager action through `resolveWithin` (or `resolveWithinWin32`/`resolveWithinPosix` as appropriate), mirroring what `openRepositoryFromUrl` already does, and refuse the action (with a user/log message) when the resolved path is `null`. At minimum this applies to: `onOpenInExternalEditor` in `app/src/ui/app.tsx`, the context-menu handlers in `selected-commits.tsx`, `pull-request-files-changed.tsx`, `filter-changes-list.tsx`, and `copilot-conflicts-dialog.tsx`.

### Proof of Concept
Not independently reproduced in this pass (no code-execution/filesystem access available). Conceptually:
1. Attacker crafts a repository where a tracked blob's path (added via low-level plumbing rather than `git add`) is something like `../../../../Users/victim/.ssh/config` or a Windows-style `..\..\..\Windows\System32\some.exe`, and gets the victim to clone/fetch it in GitHub Desktop.
2. If that entry surfaces as a file in `git status`/`git diff` in Desktop's Changes list, History view, or a Pull Request's "Files changed" view.
3. The victim right-clicks and selects "Open in External Editor" / "Reveal in Finder/Explorer" / double-clicks the row.
4. `Path.join(repository.path, file.path)` (e.g. `app/src/ui/app.tsx:3435`, `app/src/ui/history/selected-commits.tsx:384`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx:162`) resolves outside the repository directory, and the resulting path is passed unchecked to the editor/shell APIs, unlike the `resolveWithin`-guarded `filepath` handling in `dispatcher.ts:1957-1972`. ```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
