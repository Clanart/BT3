### Title
Payout tx's `SIGHASH_SINGLE|ANYONECANPAY` user signature leaves the OP_RETURN operator-credit output unsigned, letting anyone race the honest operator's fronted payout and steal/erase the reimbursement credit - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds the payout tx with only `output[0]` (user payout) covered by the user's `SinglePlusAnyoneCanPay` signature; `output[1]` (anchor) and `output[2]` (OP_RETURN operator xonly pk) are completely unconstrained by that signature. Anyone who can see the operator's broadcast payout tx (or who created the signature themselves) can build a conflicting transaction spending the same `withdrawal_utxo`, keep `output[0]` byte-identical (required to keep the signature valid), but substitute a different OP_RETURN and extra funding inputs, and get it mined instead. `update_finalized_payouts` then records whatever OP_RETURN pubkey is embedded in the transaction that actually confirmed, permanently binding the withdrawal to that pubkey via `verifier.rs`'s `is_kickoff_malicious`.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk` (as stored in `withdrawals.payout_payer_operator_xonly_pk`, derived from the OP_RETURN of the transaction that actually spends `withdrawal_utxo`) should equal the `kickoff_data.operator_xonly_pk` of the operator that economically fronted `output_txout` to the user.

`create_payout_txhandler` [1](#0-0)  signs only input 0 with the user's `taproot::Signature` using `set_p2tr_key_spend_witness`, and the sighash type is enforced to be exactly `TapSighashType::SinglePlusAnyoneCanPay` in `parse_withdrawal_sig_params` [2](#0-1) . `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0 and the output at the same index (`output[0]`); it places zero constraint on `output[1]` (anchor) and `output[2]` (`op_return_txout(operator_xonly_pk)`), and zero constraint on any additional inputs added for funding.

`Operator::withdraw` funds the (large) `output_txout` value using only the small `input_utxo` plus TxSender-added funding inputs (comment: "Funding the withdrawal transaction using TxSender RBF option") [3](#0-2) . Because these extra funding inputs and the OP_RETURN output are unsigned, any party that observes the honest operator's broadcast tx (or that already possesses the same withdrawal signature) can build an alternate transaction that: spends the identical `withdrawal_utxo` with the identical signature, keeps `output[0]` (script_pubkey/amount) byte-for-byte identical to preserve signature validity, but supplies its own funding inputs and a different `op_return_txout` (a different xonly pubkey, an invalid/garbage value, or omits the field), and pays a higher relay fee to win the mempool/mining race before the honest operator's tx confirms.

Once this alternate transaction confirms, `update_finalized_payouts` scans the block, finds the payout by matching only `(withdrawal_utxo_txid, withdrawal_utxo_vout)` against `bitcoin_syncer_spent_utxos` (not by operator identity or txid the operator submitted) [4](#0-3) , and extracts whatever OP_RETURN pubkey is present in that confirmed tx [5](#0-4) , writing it into `payout_payer_operator_xonly_pk` [6](#0-5) .

Subsequently, `is_kickoff_malicious` reads this DB value and compares it to the honest operator's real `kickoff_data.operator_xonly_pk`; since they no longer match (or the value is `None`), it unconditionally returns `Ok(true)` (malicious) [7](#0-6) , which drives verifiers to treat the honest operator's kickoff as malicious and challenge it [8](#0-7) . There is no re-derivation path: the DB record is permanently tied to whichever transaction actually confirmed on the withdrawal UTXO.

None of the existing guards prevent this: `SECP.verify_schnorr` only validates the signature against the committed sighash (which excludes the OP_RETURN and extra inputs by design of the sighash flag), `only_aggregator_and_self`/gRPC auth is irrelevant since the race happens purely on the Bitcoin p2p/mempool layer, and there is no DB uniqueness constraint tying a withdrawal to a specific operator-submitted txid before confirmation - matching is done purely by outpoint-spend, so whichever tx confirms wins by construction.

### Impact Explanation
The honest operator has already sent real BTC to the user (funded via TxSender inputs) expecting to be reimbursed through the kickoff/BitVM path. If a competing transaction reusing the same input+signed output confirms instead, the honest operator's kickoff is permanently flagged as malicious by every verifier's `is_kickoff_malicious` check for that specific deposit, with no recovery mechanism - matching "an honest operator permanently unable to be reimbursed" (Critical). If the substituted OP_RETURN pubkey belongs to a different, colluding operator, that operator could instead attempt to claim reimbursement for a payout it never itself funded (a second Critical category), though this requires operator collusion which is a stronger precondition. This is repeatable against any withdrawal/operator pair as long as the racing party can win the mempool/mining race and supply the necessary matching funding for `output[0]`.

### Likelihood Explanation
Exploitation requires the attacker to construct a transaction that reuses the exact same `output[0]` (same amount and script pubkey as the operator's committed payout, since `SIGHASH_SINGLE` commits to it), meaning the attacker must supply funding inputs covering close to the full withdrawal amount themselves (in addition to the dust `withdrawal_utxo`) to keep the transaction balanced. This is a substantial capital requirement (comparable to `bridge_amount`), which limits casual exploitation but does not eliminate it for a well-funded adversary, especially since the attacker recovers no value from `output[0]` (it still pays the same user) - their gain is purely griefing the targeted operator's reimbursement path or (with a colluding operator) diverting the reimbursement credit. The race itself is a standard Bitcoin mempool RBF/fee-race, requiring no privileged access, no hashrate majority, and no key compromise, only visibility of the mempool and fee-bumping capability. I was unable to confirm within available context whether `DEFAULT_SEQUENCE` used for the payout input explicitly signals BIP125 opt-in RBF (the exact constant value wasn't found in the indexed snippets), which affects how easily a higher-fee competing transaction can evict the honest operator's mempool transaction before either confirms; this should be verified in a live cargo test.

### Recommendation
Require the payout signature to cover more of the transaction: use `SIGHASH_ALL` (or at minimum `SIGHASH_SINGLE` without `ANYONECANPAY`, or a signature scheme where the operator's identity/OP_RETURN pubkey is also user-signed or otherwise cryptographically bound to the specific operator broadcasting the tx), so that the OP_RETURN operator pubkey and the additional funding inputs cannot be swapped post-hoc while reusing the same user signature. Alternatively, bind the withdrawal registration to a specific operator (or specific txid template) before broadcast, and only credit a confirmed payout if it matches the operator's originally-submitted, aggregator-acknowledged transaction template rather than trusting whatever OP_RETURN happens to confirm on-chain.

### Proof of Concept
Under `core/src/test` (e.g., extending `deposit_and_withdraw_e2e.rs` / `manual_reimbursement.rs`):
1. Set up a deposit and a withdrawal registered via `Aggregator::withdraw`/`Operator::withdraw` with a `SinglePlusAnyoneCanPay` signature over `withdrawal_utxo` and `output_txout` (same helper as `payout_and_start_kickoff`).
2. Let operator 0 build and broadcast its payout tx (`output[0]` = real user payout, OP_RETURN = operator 0's xonly pk), but do not mine it yet.
3. Construct a second, attacker-shaped transaction spending the same `withdrawal_utxo` with the identical `input_signature` and identical `output[0]`, but with a different OP_RETURN (e.g., a bogus/mismatched xonly pk or omit it), funded by extra attacker-controlled inputs, and give it a higher fee.
4. Broadcast the attacker tx and mine it (ensuring it replaces/precedes operator 0's tx in the confirmed block); confirm `get_txid_where_utxo_is_spent_while_synced` returns the attacker's txid, not operator 0's.
5. Let operator 0 proceed to send its kickoff as normal.
6. Assert: `db.get_payout_info_from_move_txid(...)` returns `payout_payer_operator_xonly_pk != Some(operator0_xonly_pk)` (either `None` or a mismatched value).
7. Assert: `Verifier::is_kickoff_malicious(...)` returns `Ok(true)` for operator 0's genuine kickoff, proving the honest operator's Reimburse path is permanently unreachable despite having fronted the real payout output.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

#[allow(clippy::result_large_err)]
pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    let input_outpoint: OutPoint = params
        .input_outpoint
        .ok_or_else(error::input_ended_prematurely)?
        .try_into()?;

    let users_intent_script_pubkey = ScriptBuf::from_bytes(params.output_script_pubkey);

    Ok((
        params.withdrawal_id,
        input_signature,
        input_outpoint,
        users_intent_script_pubkey,
        Amount::from_sat(params.output_amount),
    ))
}

            .script_pubkey
            .try_get_taproot_pk()
            .wrap_err("Input utxo script pubkey is not a valid taproot script")?;

            output_txout,
            self.signer.xonly_public_key,
            in_signature,
            self.config.protocol_paramset().network,

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
