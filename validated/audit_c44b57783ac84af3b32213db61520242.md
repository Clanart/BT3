### Title
Tron port of `IntentGatewayV2` ships without the reentrancy guard present in the canonical EVM contract, enabling double-counted escrow via balance-diff accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` guards `placeOrder`/`fillOrder` with OpenZeppelin's `ReentrancyGuardTransient` (EIP-1153 backed `nonReentrant`), which is what stands between an attacker and double-crediting escrow when the contract measures token balances before/after a transfer to support fee-on-transfer tokens. The Tron fork of this same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not import `ReentrancyGuardTransient` and has no `nonReentrant` modifier anywhere in the file, while retaining the identical balance-diff escrow-crediting logic and the same attacker-triggerable external-call surface (`predispatch.call` dispatched through `ICallDispatcher`, plus arbitrary ERC-20 `safeTransferFrom`). This is a structural analog of the external report's root cause: a balance-diff deposit accounting scheme that depends entirely on an EVM-feature-specific reentrancy lock, deployed on a chain/VM where that lock's underlying mechanism is silently absent.

### Finding Description
In the mainline contract, `placeOrder` is declared: [1](#0-0) [2](#0-1) 

and its escrow accounting explicitly measures balances before and after transfers to tolerate fee-on-transfer tokens and to account for `predispatch` call flows: [3](#0-2) [4](#0-3) 

This is exactly the pattern flagged in the external report: `initialBalance` snapshot → external transfer/call → `balanceAfter - initialBalance` credited to the depositor's escrow. The report's exploit works precisely because such patterns are only safe when a hard reentrancy lock prevents re-entering the function between the snapshot and the credit.

The Tron port, `evm/tron/contracts/apps/IntentGatewayV2.sol`, declares the contract as: [5](#0-4) 
with no `ReentrancyGuardTransient` (or any `ReentrancyGuard`) in its inheritance list or imports — confirmed by a repo-wide search for `nonReentrant`, which returns zero hits under `evm/tron/`. The Tron file imports the exact same order/predispatch/call-dispatch primitives (`ICallDispatcher`, `Call`, `IDispatcher`) used by the mainline contract's attacker-reachable external-call surface (`order.predispatch.call` dispatched via `ICallDispatcher(dispatcher).dispatch(...)`), meaning the same reentrant control-flow opportunity that the mainline guard exists specifically to block is present on Tron without any lock at all.

The core corrupted value is the per-commitment escrow mapping `_orders[commitment][token]`, credited from a balance-diff measurement that assumes no reentry can occur between the "before" snapshot and the "after" credit. On Tron, nothing enforces that assumption.

### Impact Explanation
If `placeOrder`/`fillOrder` on the Tron deployment lack reentrancy protection, an attacker can supply `predispatch.call` data that reenters `placeOrder` (or a malicious ERC-20/hook token in the input set) between the balance snapshot and the escrow credit, causing the same balance window to be counted twice — directly mirroring the external report's double-spend mechanic. This lets an attacker mint escrow credit against tokens they only deposited once, up to draining available Tron-side liquidity, i.e. direct loss of bridged/escrowed funds, matching the bounty's "stealing or loss of funds" and "double-settlement" categories.

### Likelihood Explanation
Medium-to-Low: the vulnerability's existence depends on whether this Tron contract is actually deployed and live (versus a template that has since been patched or is unused), which I could not confirm within the available tool budget. However, the structural gap is unambiguous and requires no privileged actor, relayer, or governance participation — only an unprivileged caller using `placeOrder`'s own attacker-controlled `predispatch.call` field, which is a public entrypoint parameter.

### Recommendation
Add `ReentrancyGuardTransient` (or, if Tron's TVM does not support TSTORE/TLOAD, the classic `ReentrancyGuard` with persistent storage) to `evm/tron/contracts/apps/IntentGatewayV2.sol` and apply `nonReentrant` to `placeOrder`, `fillOrder`, and any other function that performs balance-diff based accounting around an external call, matching the protection already present in the canonical `evm/src/apps/IntentGatewayV2.sol`. Additionally, audit all EVM-feature-dependent primitives (transient storage duplicate-token checks, `nonReentrant`) for parity across every chain-specific fork before deployment, since divergence between "canonical" and "ported" contracts is exactly the class of bug the external report describes.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` on Tron with a fee-token or hookable token as input.
2. Attacker calls `placeOrder` with `order.predispatch.call` set to invoke a malicious dispatcher/callback that re-enters `placeOrder` (or uses a token whose `transferFrom` triggers attacker-controlled code, e.g. an ERC-777-style token) before the first call's balance-after measurement completes.
3. Because no `nonReentrant` modifier exists in this file (confirmed via inheritance list and grep), the reentrant call executes its own balance-diff snapshot/credit cycle inside the outer one's window.
4. Both calls compute a "received" delta against overlapping balance snapshots, crediting `_orders[commitment][token]` for more than what was actually transferred once — exactly the double-count arithmetic shown in the external report's numeric example (deposit 20, reenter, end up credited 60 for only 40 actually transferred in).

I was not able to fully step through the Tron `placeOrder` body byte-for-byte to confirm identical balance-diff line numbers within the iteration budget; the finding rests on the confirmed absence of the reentrancy-guard inheritance/modifier that the canonical contract relies on for the same accounting pattern.
