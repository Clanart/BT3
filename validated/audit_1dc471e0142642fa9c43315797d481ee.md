## Finding

The GitHub Desktop analog is the `isSafeFileExtension` allow/deny check that gates the **"Open with Default Program"** context-menu action on files inside a cloned/checked-out repository. [1](#0-0) 

### Title
Incomplete/platform-limited `isSafeFileExtension` check allows execution of attacker-controlled repository files via "Open with Default Program" - (File: `app/src/ui/lib/context-menu.ts`)

### Summary
When a user right-clicks a changed/committed file and selects "Open with Default Program," Desktop calls `openFile()`, which hands the file to the OS via `shell.openExternal('file://' + fullPath)` with no sandboxing of the resulting handler invocation. [2](#0-1) 
This is gated only by `isSafeFileExtension`, which on macOS and Linux unconditionally returns `true` for every extension, and on Windows only blocks four hardcoded extensions (`.cmd`, `.exe`, `.bat`, `.sh`): [3](#0-2) 

### Finding Description
The broken invariant mirrors the ERC721 report: an operation hands off control to an untrusted external actor (there, an arbitrary contract via `transferFrom`; here, the OS's default file-type handler via `shell.openExternal`) without verifying that the recipient can safely process what it's given. The `.cmd/.exe/.bat/.sh` denylist is both incomplete and platform-scoped:
- On macOS, `isSafeFileExtension` always returns `true`, so files with extensions macOS treats as executable when opened (e.g. `.command`, `.workflow`, `.scpt`) pass the check.
- On Linux, the same unconditional `true` applies, so a `.desktop` file (which can carry an `Exec=` line) or a shell-script-associated extension not in the Windows-only denylist passes.
- Even on Windows, the denylist omits many launchable extensions (e.g. `.com`, `.scr`, `.msi`, `.ps1`, `.vbs`, `.js`, `.jar`, `.hta`, `.wsf`, `.lnk`).

This check is used across the file-history and changes UI to enable/disable the "Open with Default Program" menu item for files that are entirely attacker-controlled content in a cloned/fetched repository: [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
If an attacker crafts a repository (or a pull request the user opens in Desktop) containing a file with an extension that the OS treats as directly launchable but that isn't on the narrow Windows-only denylist (or any extension at all on macOS/Linux, since the check is a no-op there), selecting "Open with Default Program" invokes the OS handler on that file, which can result in code execution in the context of the logged-in user — outside of git's own working-tree semantics and outside any sandboxing Desktop provides.

### Likelihood Explanation
Requires the user to right-click a file and choose "Open with Default Program" — a normal, expected interaction with a feature Desktop explicitly exposes for inspecting changed/committed files, not an unnatural or privileged step. The attacker only needs to control the repository content (a cloned or fetched repo, or a PR's changed files), which matches the described threat model.

### Recommendation
Replace the hardcoded denylist with a maintained, cross-platform denylist (or better, an explicit allowlist of known-safe document types), enforce it identically on all platforms instead of returning `true` unconditionally for macOS/Linux, and consider warning/confirming before invoking the OS default handler on any file type capable of executing code (mirroring the recommendation to use `safeTransferFrom`-style "verify the recipient can safely handle this" pattern before performing the external hand-off).

### Proof of Concept
1. Attacker publishes/pushes a repository containing a file named e.g. `payload.command` (macOS) or `payload.desktop` (Linux) with executable content in its body.
2. Victim clones or fetches the repo in Desktop and views the file in the Changes/History/PR-diff panel.
3. Victim right-clicks the file and selects "Open with Default Program"; `isSafeFileExtension` returns `true` for this extension on macOS/Linux (or is not covered by the Windows-only denylist), so the menu item is enabled.
4. `openFile()` calls `shell.openExternal('file://<path>')`, and the OS launches/executes the file via its default handler. [2](#0-1)

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
