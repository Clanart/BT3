### Title
Missing proof-of-possession on the PedPoP encryption key lets a participant register a third party's `enc_key`, redirecting confidential secret shares to an unauthorized decryptor - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage` carries a participant-chosen `enc_key` that is registered and trusted without any proof that the registrant knows its discrete logarithm, and without being bound into the round-1 Schnorr proof of knowledge. A participant can therefore register *another party's* encryption public key (or any key whose secret they don't know but someone else does), causing every sender's per-recipient ECDH ciphertext to be decryptable by the holder of the substituted key — not by the participant the sender addressed. This mirrors CVE-2019-12429's class: confidential data accessible to a party that was never authorized to see it.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs:50-58`, `EncryptionKeyMessage { msg, enc_key }` is read from the wire and the `enc_key` field is stored as-is by `Decryption::register` (`encryption.rs:351-362`), keyed only by the claimed `Participant` index. There is no proof-of-possession on `enc_key`:

- The round-1 PoK challenge `challenge::<C>` (`crypto/dkg/pedpop/src/lib.rs:86-94`) transcript-binds only the commitment bytes (`cached_msg` covers `commitments`, per `Commitments::read`/`write` at `lib.rs:110-133`). `enc_key` is appended to the message *after* the signed portion and is covered by no signature.
- The per-message `pop` (`encryption.rs:302-324`) authenticates the ephemeral `msg.key`, not the long-term `enc_key`.

Subsequently, `SecretShareMachine::generate_secret_shares` (`lib.rs:359-370`) calls `self.encryption.encrypt(rng, l, share_bytes)`, which resolves `self.decryption.enc_keys[&participant]` (`encryption.rs:460-467`) and encrypts with `cipher(context, ecdh(&key, to))` (`encryption.rs:135-167`), where `to` is whatever `enc_key` the participant registered.

An attacker-participant Eve therefore broadcasts a valid `EncryptionKeyMessage` but sets `enc_key = V`'s published `enc_pub_key` (all round-1 messages are broadcast, so V's key is public). Every honest sender encrypts Eve's share `f_s(Eve)` to V's private key. Anyone holding V's `enc_key` secret (V itself, or a later compromiser of V) can compute `ecdh(v_priv, msg.key)` and decrypt the shares — ciphertexts are additionally persisted for blame (coordinator `DkgShare` storage), so they remain available to non-recipients. V thereby recovers *Eve's* aggregate secret share — key-share material V was never authorized to access — without Eve needing to cooperate with V at all.

### Impact Explanation
Confidentiality of DKG secret shares is broken across participants: shares addressed to Eve become decryptable by the owner of whatever public key Eve substituted. This is key-share recovery by an unauthorized party. It lowers the effective compromise threshold of the resulting `ThresholdKeys`: an attacker who later compromises V alone obtains both V's share and Eve's share (and, in low-`t` configurations such as 2-of-n, can produce FROST signature shares for both slots unilaterally by supplying its own nonces for the stolen share). Unlike key-reuse-by-owner (which the code explicitly deems self-harm at `encryption.rs:84-90`), the harmed parties here are the honest senders whose share evaluations are disclosed beyond their intended recipient.

### Likelihood Explanation
Medium-low. The attacker must control a participant slot in the DKG and submit a crafted `EncryptionKeyMessage` — public input the protocol accepts without any cryptographic check on `enc_key`. No collusion is required to cause the disclosure; exploitation of the leaked share requires the substituted key's owner to decrypt (honest-but-curious suffices) or to be compromised later. The cipher's correctness (`cipher`/`ecdh`/`ChaCha20` with static IV) is otherwise sound, so the only exposure is this missing binding.

### Recommendation
Bind `enc_key` to the participant in round 1: either (a) include `enc_key` in the `cached_msg` covered by the round-1 Schnorr PoK `challenge`, and/or (b) add a dedicated proof-of-possession (Schnorr signature by `enc_key` over `context || participant`) verified in `verify_r1`/`Decryption::register` before the key is trusted in `Encryption::encrypt`. This guarantees ciphertexts are only decryptable by a key whose secret the registrant actually controls.

### Proof of Concept
```rust
// Round 1: victim V and attacker Eve both run KeyGenMachine::generate_coefficients.
// V's EncryptionKeyMessage contains enc_key = enc_pub_key_V (public).
// Eve builds her EncryptionKeyMessage normally, then substitutes:
//   eve_msg.enc_key = v_msg.enc_key;  // no PoP exists to prevent this
//
// Round 2: each honest sender s runs
//   generate_secret_shares -> encrypt(rng, Eve, f_s(Eve))
//   -> cipher(context, ecdh(&ephemeral_k, enc_pub_key_V))  // encrypted to V!
//
// V (or anyone with v_priv) decrypts every ciphertext addressed to Eve:
//   key = ecdh(v_priv, msg.key);                       // encryption.rs:487 equivalent
//   cipher(context, &key).apply_keystream(msg.msg)     // yields f_s(Eve)
// Summing all f_s(Eve) over senders yields Eve's ThresholdKeys secret_share,
// recovered by a party never authorized to hold it.
```
