### Title
Recursion depth double-counted for `MessageSet` extensions parsed via `_InternalParse`/`ParseContext` (C++) — legitimate deeply-nested messages rejected below the documented limit — ([File: src/google/protobuf/parse_context.h])

### Summary
The external report's failed invariant is: a value that should be transformed/consumed **once** per unit of logical nesting is instead transformed **twice**, so the effective limit against which it is checked is silently halved, making a legitimate operation (liquidation / parsing) fail well before the documented threshold. I looked for a wire-format analog where a *bounded, valid* input is rejected because an internal counter (recursion depth) is incremented/decremented more than once per logical level, rather than a resource-exhaustion or unbounded-allocation issue (explicitly excluded by the rules).

I found a directly analogous, currently-acknowledged discrepancy in the C++ `MessageSet` extension parsing path: each layer of `TestMessageSet`-style `MessageSet` extension nesting consumes **two** units of `ParseContext`/`CodedInputStream` recursion budget instead of one, while the Python pure and other backends consume only one. This is explicitly called out as a known bug in the C++ implementation in the conformance test suite: [1](#0-0) 

```
def testRecisionMessageSet(self):
    ...
    if api_implementation.Type() == 'cpp':
      # TODO: message_set_extension was double counted for
      # depth in c++. Should fix it to only count once.
      depth = 33

      depth = 50
```

The test itself compensates for the bug by using a *smaller* depth (33) for the C++ backend so the test still passes — proving that with the documented default recursion limit (100), the C++ engine actually only tolerates roughly half as many `MessageSet`-nested levels as the Python/other backends before spuriously raising `DecodeError`/`RecursionDepthExceeded` for input that is well-formed and within the intended limit.

A related, more explicit confirmation of the "each layer costs 2 depth units instead of 1" pattern shows up in the Objective-C test suite, which documents the same doubled accounting for MessageSet-of-MessageSet nesting and adjusts its own expected pass/fail boundaries accordingly rather than fixing the root cause: [2](#0-1) 

### Finding Description
Protobuf's core parsers protect against stack overflow from maliciously or accidentally deeply-nested messages by maintaining a recursion budget that is decremented exactly once per nested message/group and incremented back exactly once when that submessage finishes parsing: [3](#0-2) [4](#0-3) 

The C++ `MessageSet` extension parsing path (used by generated code and `WireFormat::ParseAndMergeMessageSetItem` / `ExtensionSet` merge logic) nests a `MessageSet` item's embedded message inside its own length-delimited parse scope. Just as the reported bug applies `rayMul` twice — once inside `getUserDebt()` and once again in `liquidateBorrower()` — the C++ MessageSet path appears to charge the recursion budget twice for a single logical level of nesting: once for entering the `MessageSet` item's own sub-message parse, and again for the extension's `recursive`/message field parse that is logically the *same* nesting step, rather than a fresh one. This is exactly analogous to `scaledUserDebt = debt * usageIndex^2` instead of `debt * usageIndex`: the safety-check input (depth counter) is transformed twice where the design intends once.

The consequence mirrors the report's "harder over time, eventually impossible" impact pattern: as a producer nests `MessageSet` extensions to legitimate, bounded depths (e.g., 50 layers, well under the documented `kDefaultRecursionLimit` of 100), the C++ runtime consumes the budget at 2x rate and spuriously exhausts it around depth ~50 real API levels / ~33 in the compensating test scenario — a valid, schema-conformant, bounded message is rejected as "too deep" even though the *actual* nesting is within policy. This is a **consuming-application-exposure** scenario: any service that accepts client-supplied Protobuf containing `MessageSet`-style extensions (still used in some legacy schemas, e.g. many `google3`-style descriptor-adjacent extension patterns) and nests them to depths near, but under, its intended recursion budget will see legitimate requests intermittently or systematically fail, exactly as the report describes a systematic, invariant-violating impact ("occurs for every liquidation attempt... systematic issue").

### Impact Explanation
This is a correctness/availability defect in the trusted, non-privileged public parsing surface (`ParseFromString`/`MergeFrom` on schemas that use `MessageSet`), not a memory-safety or RCE issue. Its impact is a **false-rejection denial-of-service class problem**: valid, bounded, schema-conformant input that a consuming application expects to accept (because it configured/relies on the documented default recursion limit of 100) is incorrectly rejected roughly halfway to that limit when it uses `MessageSet` extensions, exactly mirroring the report's core harm — an artificially inflated internal accounting value causes legitimate operations that should succeed under the stated invariant to fail. This does not enable disclosure, corruption, or code execution, and is bounded to well-formed schemas, so it sits at low/Medium severity per the excluded categories (no exploitation, no unbounded resource growth — the counter simply reaches zero "too early").

### Likelihood Explanation
This will reproducibly occur for *every* C++-backend parse of nested `MessageSet` extensions once nesting approaches half of the configured recursion limit, since the double counting is structural (per the maintainers' own `TODO` acknowledging it), not input-dependent noise. It is limited to the `MessageSet` legacy extension mechanism and the C++ backend specifically (Python pure, and presumably others, count once per the test's own differing constants), which narrows likelihood/impact but does not eliminate it for any service still relying on `MessageSet`.

### Recommendation
Apply the same recommendation the original report gives — "create consistency in usage of scaling" — to depth accounting: ensure the C++ `MessageSet` extension parse path increments/decrements the shared `ParseContext`/`CodedInputStream` recursion counter exactly once per logical nesting level, matching the Python/other backends' semantics and the documented `kDefaultRecursionLimit` contract, then update/remove the compensating `depth = 33` workaround in `message_test.py` once fixed.

### Proof of Concept

  // Each MSetMessage carries a single MSetMessageExtension1, whose
  // `recursive` field is again a MSetMessage. Chaining N of these produces
  // a MessageSet-of-MessageSet payload nested N levels deep. The parser
  // for each MessageSet item allocates a fresh CodedInputStream, so depth

  // kDefaultRecursionLimit (100) to actually apply.

  // 51 layers attempts to reach depth 101 (kDefaultRecursionLimit + 1), which must fail
  // with GPBCodedInputStreamErrorRecursionDepthExceeded rather than silently parsing.

inline void CodedInputStream::SetRecursionLimit(int limit) {
  recursion_budget_ += limit - recursion_limit_;
  recursion_limit_ = limit;
}

inline bool CodedInputStream::IncrementRecursionDepth() {
  --recursion_budget_;
  return recursion_budget_ >= 0;
}

inline void CodedInputStream::DecrementRecursionDepth() {
  if (recursion_budget_ < recursion_limit_) ++recursion_budget_;
}

inline void CodedInputStream::UnsafeDecrementRecursionDepth() {
  assert(recursion_budget_ < recursion_limit_);
  ++recursion_budget_;
}
