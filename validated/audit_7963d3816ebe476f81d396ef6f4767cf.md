### Title
`aptos move verify-package` never compares on-chain module bytecode, only package metadata - (File: aptos-move/cli/src/stored_package.rs, aptos-move/cli/src/commands.rs)

### Summary
The `VerifyPackage` CLI command is documented as verifying "that the on-chain copy matches" the local source, but its implementation only compares `PackageMetadata` struct fields (name, deps, module source text/source map, manifest, upgrade policy, extension, source digest). It never fetches or compares the actual compiled bytecode stored on-chain for each module.

### Finding Description
`VerifyPackage::execute()` builds the package locally, extracts `compiled_metadata`, then calls: [1](#0-0) 
Note `CachedPackageRegistry::create(client, self.account, false)` — the third argument `with_bytecode` is hardcoded `false`. Looking at `create()`: [2](#0-1) 
When `with_bytecode` is `false`, the `bytecode: BTreeMap<String, Vec<u8>>` field remains empty — no `get_account_module` (which fetches actual on-chain compiled bytes) call is made.

The final check is `package.verify(&compiled_metadata)`, which only compares `PackageMetadata`/`ModuleMetadata` fields: [3](#0-2) 
`ModuleMetadata.modules` only contains `name`, gzipped `source`, gzipped `source_map`, and `extension` — not the compiled bytecode: [4](#0-3) 

So `verify-package` effectively checks that the *source text* and metadata a publisher chose to attach match a local rebuild, but the actual bytes executed by the VM (fetched only via `get_account_module`, used solely by `DownloadPackage` when `--bytecode` is passed) are never compared. Documentation explicitly claims the opposite: [5](#0-4) 

### Impact Explanation
This is a tooling/verification-integrity gap, not an on-chain state-mutation bug: the Aptos VM's own publish-time bytecode verifier, compatibility checker, and dependency checks in `code.move`/`aptos_vm.rs` are unaffected and still enforce correctness for what actually gets stored. The impact is limited to the CLI's `verify-package` auditing/reproducibility guarantee: a third party auditing a deployed package by running `aptos move verify-package` can be given a false sense of security — matching source/metadata does not guarantee the deployed bytecode was compiled from that exact source (e.g., a malicious or buggy toolchain, hand-crafted bytecode upload via `code_publish_package_txn`, or a compiler bug could produce bytecode diverging from the "verified" source while `ModuleMetadata.source`/`source_map` are set to match). Under "Publish Impact Gate", this falls into "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" — but severity is bounded because it does not itself corrupt on-chain state, bypass upgrade/compatibility policy, or grant unauthorized publish/upgrade/freeze rights. It undermines a trust/verification tool rather than a protected state-mutation path.

### Likelihood Explanation
High likelihood of occurring in practice: any user relying on `verify-package` to confirm reproducibility of a third-party or governance-proposed package would be affected, since the code path is unconditional (`with_bytecode` hardcoded to `false`) and requires no attacker action beyond normal publishing with metadata whose `source`/`source_map` fields don't correspond exactly to the actually-uploaded module bytes (which the framework itself does not enforce — `code::publish_package` never checks source-to-bytecode correspondence on-chain).

### Recommendation
In `VerifyPackage::execute()`, call `CachedPackageRegistry::create(client, self.account, true)` to fetch on-chain bytecode, and extend `CachedPackageMetadata::verify()` (or add a new check) to compare each module's on-chain bytecode bytes against the freshly compiled bytecode produced by `pack.extract_code()` / `pack.module_code_iter()`, failing verification on any mismatch.

### Proof of Concept
1. Compile and publish a package where `ModuleMetadata.source`/`source_map` correspond to legitimate source `A`, but the module bytecode actually uploaded (via a modified `code_publish_package_txn` payload) is compiled from a semantically different but ABI/layout-compatible source `B` (passes `BACKWARD_INCOMPATIBLE_MODULE_UPDATE` / bytecode verifier checks, which do not check source correspondence).
2. Run `aptos move verify-package --account <addr>` against local source `A`.
3. Observe that `package.verify(&compiled_metadata)` returns `Ok(())` because `deps`, `modules` metadata (source/source_map text of `A`), `manifest`, `upgrade_policy`, `source_digest` all match, even though the actual bytecode differs from what `A` compiles to — the mismatch is never checked because `with_bytecode = false` is passed at `aptos-move/cli/src/commands.rs:2121` and `CachedModuleMetadata` never exposes/compares real bytecode in `verify()`.
