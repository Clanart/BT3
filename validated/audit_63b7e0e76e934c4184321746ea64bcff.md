### Title
Persisted `CachedPreprocess` is reused across re-executed signing sessions whose parameters changed, enabling validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives FROST nonces deterministically from a `CachedPreprocess` seed stored in the DB keyed solely by `context = (b"DkgConfirmer", attempt)`. The signing set (`participants`), the `removed` set, the received `preprocesses` map, and the message (`set_keys_message`) are all excluded from the cache key. Any time `share_internal`/`complete` re-executes `sign` under the same attempt with different received preprocesses or a different `KeyPair`, the identical nonces `(d, e)` are signed again under different binding factors `rho` and different challenges — classic FROST nonce reuse that yields the validator's MuSig secret share.

### Finding Description
`preprocess_internal` caches a 32-byte seed once per context and rebuilds the `AlgorithmSignMachine` via `from_cache` on every call, so `self.nonces` and the published commitments are identical for every invocation under a given attempt. `seeded_preprocess` in `crypto/frost/src/sign.rs` regenerates the same `nonces` and `commitments` from the same seed. In `share_internal`/`complete`, `sign(preprocesses, msg)` binds `rho` over `group_key`, `hash_msg(msg)`, and the transcript of all received preprocesses — so two calls with different `included` sets or different `key_pair` produce shares `s = d + e·rho + λ·x·c` with the same `(d, e)` but different `rho`, `c`. Two such shares under different Lagrange coefficients, or three under different `rho`, are a linear system recovering the secret share `x` — the validator's root-of-trust key.

The file's own safety argument concedes the gap: it assumes re-execution always sees identical finalized messages and admits "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" — that check is not implemented. Because the seed is persisted in `CachedPreprocesses` and the context key does not include the spec/genesis, a partial rebuild following a divergent chain (explicitly acknowledged as an accepted bound) re-decides nothing: the same nonces sign the new chain's distinct messages and preprocess sets.

### Impact Explanation
Reuse of the deterministic nonces across two signing sessions with differing `rho`/message lets any observer of the published signature shares solve for the secret share of the validator's MuSig key. That key is the root of trust confirming DKG results on-chain (`set_keys_message`); its recovery enables forging validator-set confirmation signatures.

### Likelihood Explanation
Requires the coordinator to issue shares under the same `attempt` for distinct finalized inputs — via the acknowledged unimplemented on-chain-preprocess consistency check, or a partial rebuild onto a divergent chain. Not a default-path trigger, which is why the nonce-reuse determinism was accepted; however the persistence of the seed in the DB keyed by an insufficient context silently invalidates the documented safety argument.

### Recommendation
Include the spec set/genesis (or the full `removed` set and `participants` list) in the `CachedPreprocesses` key and the encryption-key preimage so a divergent chain deterministically derives different nonces; implement the noted TODO to verify the locally derived commitments match the on-chain preprocess before publishing a share; refuse to sign if the received preprocess set differs from the one previously signed under the same context.

### Proof of Concept
1. Attempt `a` finalizes; `share()` publishes share `s₁ = d + e·rho₁ + λ₁·x·c₁` for preprocess set `P₁` and `key_pair` `K₁`.
2. Process is partially rebuilt (or the missing TODO check allows) following a chain where `key_pair` `K₂` (or preprocess set `P₂`) was finalized for the same `attempt`. `CachedPreprocesses::get(("DkgConfirmer", a))` returns the same seed → identical `(d, e)`.
3. Share `s₂ = d + e·rho₂ + λ₂·x·c₂` is published. With `lambda` known (participant indexes public), `(s₁ - s₂)` yields a linear equation in `x` after `e` is eliminated via a third share or differing `λ`; the validator's secret share is recovered from the on-chain-published shares.
