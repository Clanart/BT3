### Title
Scanner accepts zero/dust-value outputs as received funds, which then cost more in fees than they contribute - (networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` registers any output paying to a watched `script_pubkey` as a `ReceivedOutput`, without checking `output.value`. An unprivileged party can send transactions with 0-value or sub-dust outputs to a scanned Serai address; the scanner reports them as owned inputs. `SignableTransaction::new` (send.rs) validates that *payments* are above `DUST` but never filters *inputs*, so each dust input is included in a future spend, inflating the transaction's vsize (and required fee) while contributing effectively no value — a net drain on the multisig, and on the accounting side, value "received" that cannot be economically spent.

### Finding Description
The reported bug class is: a function accepts `amount > 0` (or any amount) as its only constraint, but the derived allocation/result rounds down to zero, producing a position/output worth nothing while still consuming the deposit.

`Scanner::scan_transaction` mirrors this. Its only membership check is a `script_pubkey` map lookup:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    ...
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
            offset: *offset,
            output: output.clone(),
            outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
    }
```

There is no lower bound on `output.value` — `ReceivedOutput::value()` can return 0 or any value below `DUST` (defined in `networks/bitcoin/src/wallet/send.rs`).

On the spend side, `SignableTransaction::new` enforces `DUST` on payments (`if *amount < DUST { Err(DustPayment) }`) and on change (`if value >= DUST`), but performs no equivalent check on `inputs`: it simply sums `input_sat` and builds one `TxIn` per supplied `ReceivedOutput`. Each input contributes a fixed weight (~68 WU for key-path Taproot inputs, per the witness/txin sizing in `calculate_weight_vbytes`), so a 0- or 1-sat input raises `needed_fee` by `fee_per_vbyte * ~58` while adding ~0 sat to `input_sat`. If enough dust inputs are present, `input_sat.checked_sub(payment_sat + fee)` can fail or consume value that would otherwise go to change.

The caller of `scan_transaction`/`scan_block` (any consumer of this crate) receives `ReceivedOutput`s indistinguishable from legitimate deposits and will feed them as inputs, having no API-level signal that they are economically worthless.

### Impact Explanation
- An attacker sends a Bitcoin transaction with many sub-`DUST` outputs to a watched multisig script. No privilege, key material, or validator status is required — sending a transaction to a public address is fully public input.
- Every such output is reported as received funds, but each is unspendable in practice: spending it costs more in fees than it returns. This is exactly "funds reported received that are not spendable" — the same shape as a minted position that yields 0 mgCVG/ysCVG despite a non-zero deposit.
- If the consumer aggregates these inputs into `SignableTransaction::new`, the multisig pays the marginal per-input fee out of real funds; at scale this is a forced fee drain on the vault.

### Likelihood Explanation
- Reachable by any unprivileged party: creating dust outputs to a known address requires only an on-chain transaction.
- Likelihood is bounded by the attacker's own cost (creating dust outputs costs real satoshis + tx fees), and by whether the consuming system credits these outputs toward deposits before they're swept. The damage per dust output is small (~one input's weight worth of fee), making this Medium at most, consistent with the source report's severity.

### Recommendation
- In `Scanner::scan_transaction`, skip outputs with `output.value.to_sat() < DUST` (or expose the value and let the caller filter). A dust output to the multisig can never be profitably spent, so treating it as a `ReceivedOutput` has no upside.
- Alternatively/additionally, in `SignableTransaction::new`, reject or warn when an input's value is below the marginal fee it introduces (i.e., when `input.value < fee_per_vbyte * input_vbytes`), so a caller cannot accidentally include economically-negative inputs.

### Proof of Concept
```rust
// networks/bitcoin — conceptual PoC
let (keys, key) = keys();
let mut scanner = Scanner::new(key).unwrap();

// Attacker crafts a tx with a 0-value / dust output to the multisig script
let dust_output = TxOut {
    value: Amount::from_sat(0), // or 1..DUST
    script_pubkey: p2tr_script_buf(key).unwrap(),
};
let attacker_tx = Transaction {
    version: Version(2),
    lock_time: LockTime::ZERO,
    input: vec![/* any input */],
    output: vec![dust_output],
};

// Scanner reports it as a received output despite value == 0
let received = scanner.scan_transaction(&attacker_tx);
assert_eq!(received.len(), 1);
assert_eq!(received[0].value(), 0); // credited output worth nothing

// If used as an input, it adds weight => fee, contributing nothing
let tx = SignableTransaction::new(
    vec![received[0].clone(), legit_output],
    &payments, change, None, fee_per_vbyte,
);
// tx.needed_fee() now includes ~58 vbytes * fee_per_vbyte attributable
// to an input worth 0 satoshis — a forced fee burn.
```
