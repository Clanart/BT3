Based on my investigation, I found a structurally analogous bug in GitHub Desktop's partial-commit (line-level staging) pipeline. The Curve/Convex bug class is: *an operation is executed using freshly-computed state instead of the state that was validated/used to build the caller's inputs, silently discarding/corrupting the intended delta*. The closest verified analog in this codebase is the mismatch between the diff used to build a user's line selection and the diff re-fetched at staging time.

### Title
Partial-commit staging re-fetches the working directory diff instead of the one the user's line selection was built against, allowing silent corruption of staged/committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only some lines of a modified file ("partial commit"), Desktop builds a `DiffSelection` bound to absolute line indices of a specific `ITextDiff` that was rendered in the UI. When the commit is actually executed, `applyPatchToIndex` does **not** reuse that diff — it calls `getWorkingDirectoryDiff` again to fetch a brand-new diff of the file, and then builds the patch by applying the old `DiffSelection`'s absolute indices to this newly-fetched diff via `formatPatch`. ### Finding Description
The UI selection flow computes selectable/selected line indices against a diff fetched by `updateChangesWorkingDirectoryDiff`, and the code explicitly acknowledges that this diff can go stale: [3](#0-2) 

That reconciliation only recalculates which line indices are *selectable*, it does not re-validate that a previously selected index still corresponds to the same semantic line. Later, when the commit is created, `stageFiles` → `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call and directly reuses `file.selection` (the possibly-stale `DiffSelection`) against hunks from this new diff: [4](#0-3) [5](#0-4) 

This is the same broken invariant as the Curve report: state (`lastUpdate`/`periodFinish` there, the diff/hunk layout here) is advanced/refetched without first reconciling it against the value the caller's action was based on (`_updateIntegrals` there, the originally-rendered diff/selection here). `formatPatch` never verifies that `hunk.unifiedDiffStart` offsets in the new diff still line up with what the user actually saw and clicked on — it will silently apply the old absolute-index selection to whatever hunks git currently reports.

### Impact Explanation
If the working tree content that git diffs against changes between the moment the user reviews a diff and selects lines, and the moment `createCommit`/`applyPatchToIndex` re-diffs the file, hunk boundaries and line offsets can shift. The stale `DiffSelection` indices will then select the wrong lines in the new hunks, so `git apply --cached` stages content the user never selected (or drops content they did select) — with no error, dialog, or diff re-confirmation shown, because a syntactically valid patch is still produced. This is a silent corruption of exactly what gets committed and subsequently pushed to the remote, matching the impact category of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires the working-directory content underlying the diff to change between diff-render time and commit-time re-diff — e.g., a filesystem watcher, format-on-save, background build/lint tool, or a git clean/smudge filter declared by a cloned/malicious repository's `.gitattributes` producing non-identical output on repeated invocations. Desktop does sandbox hook execution via a proxy mechanism (`withHooksEnv`), which limits (but does not eliminate) this vector for hook-driven modification; filters invoked by `git diff`/`git apply` are a separate mechanism not covered by that sandbox and are configurable per-repository via tracked `.gitattributes`. I could not find code in this diff/patch pipeline that pins or re-verifies the diff identity (e.g., hashing hunk content or blob OIDs) between selection-time and apply-time, so no existing guard stops this path once the underlying content changes.

### Recommendation
Before calling `applyPatchToIndex`, either (a) pass through and reuse the exact diff object that was used to build the current `DiffSelection` rather than re-fetching, or (b) re-fetch the diff and compare its hunk/line structure (or underlying blob content) against what the selection was computed from, aborting/re-prompting the user if they differ, analogous to requiring `_updateIntegrals` to run against the exact state that will be consumed rather than trusting freshly-derived state.

### Proof of Concept
1. Modify a tracked file so it has a multi-hunk diff against HEAD.
2. In Desktop, select only specific lines from hunk 2 for a partial commit (`DiffSelection` records absolute indices based on the current diff's hunk layout, per `app/src/lib/patch-formatter.ts:143-157`).
3. Before the commit action completes, cause the file's diff shape to change without the user re-reviewing it (e.g., via a `.gitattributes`-declared clean filter in the cloned repository that normalizes content differently on repeated invocation, or a background process rewriting the file) — this only needs to occur between the async gap in `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3444-3497`) and the commit's own diff fetch in `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`).
4. Trigger commit; `createCommit` → `stageFiles` → `applyPatchToIndex` re-diffs and builds the patch from the stale `DiffSelection`, staging/committing different lines than what the user selected in step 2, with no warning shown.

Note: I was not able to fully verify a concrete, guaranteed-attacker-triggerable timing mechanism (e.g., a specific filter driver behavior) purely from the indexed code; this would need direct testing in a full checkout (e.g., via a Devin session) to confirm exploitability end-to-end, since some file contents (e.g., full `diff.ts`, `git-diff` filter invocation code) were not completely available through the index.
