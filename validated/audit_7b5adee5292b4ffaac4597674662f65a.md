### Title
No slippage protection in `PublicDelegation.stake()` allows share-price manipulation for KAIA public delegation stakers - ([File: contracts/bindings/publicdelegation/PublicDelegation.go])

### Summary
The `PublicDelegation` system contract implements an ERC4626-like vault for KAIA public delegation staking, exposing `stake()`, `stakeFor(address)`, `convertToShares(uint256)`, and `convertToAssets(uint256)`. None of the state-changing entry points (`stake`, `stakeFor`, `redeem`) accept a `minSharesOut`/`minAssetsOut` or `deadline` parameter, mirroring exactly the bug class described in the external report for `BaseControlledAsyncRedeem.deposit()`.

### Finding Description
`stake()` is a payable function with no arguments [1](#0-0) , and `stakeFor(address _recipient)` only takes a recipient address, also with no slippage-guarding parameter [2](#0-1) . The contract exposes `convertToShares`/`convertToAssets` and `previewDeposit`/`previewRedeem`/`previewWithdraw` view functions that are consistent with an ERC4626-style share-price formula based on `totalAssets()`/`totalSupply()` [3](#0-2) , and it emits a `Staked(user, assets, shares)` event confirming that `stake()` converts the staked KAIA into shares at execution time [4](#0-3) . This is the same pattern as the reported `convertToShares` formula (`assets.mulDivDown(supply, totalAssets())`) — if `totalAssets()` can change between transaction submission and inclusion (e.g., due to reward accrual, commission distribution, or another staker's `stake()`/`redeem()`/withdrawal being included first), the number of shares a staker receives for a given KAIA deposit is not guaranteed and can be front-run.

### Impact Explanation
Because there is no `minSharesOut` or `deadline` parameter on `stake()`/`stakeFor()`, a staker's transaction can be sandwiched: a third party (or the block proposer itself, given proposer-controlled transaction ordering in Kaia's block assembly) can cause `totalAssets()`/`totalSupply()` to shift immediately before the staker's `stake()` executes, reducing the shares minted to the staker relative to what they expected from a `previewDeposit`/`convertToShares` call made off-chain. This results in a staker unexpectedly receiving fewer PublicDelegation shares (and therefore a smaller claim on future assets/rewards) for the same KAIA deposited — a concrete value-transfer/loss-of-funds scenario for an unprivileged staker, matching the "unauthorized value movement" category for staking modules.

### Likelihood Explanation
Exploitability depends on whether any single-transaction or same-block action can materially move `totalAssets()`/`totalSupply()` before a targeted `stake()` is executed (e.g., another large `stake()`/`redeem()` in the same block, or reward/commission crediting logic triggered elsewhen). I could not verify from the available Go bindings alone (the Solidity source of `PublicDelegation.sol` is not present in this repository — only ABI-generated bindings under `contracts/bindings/publicdelegation/PublicDelegation.go`) whether `totalAssets()` fluctuates within a block in a way an ordinary user/proposer could exploit, or whether shares are rounded/protected elsewhere. This is a real limitation of the available index: the actual implementation logic of `stake()`, `convertToShares()`, and reward crediting lives in a `.sol` file that isn't included in this repo's indexed contents.

### Recommendation
Add optional slippage-protection parameters (`minSharesOut` for `stake`/`stakeFor`, `minAssetsOut` for `redeem`) and a `deadline` parameter to `PublicDelegation`'s state-changing entry points, reverting if the actual conversion result falls short of the caller-specified minimum or the deadline has passed, consistent with the recommendation in the source report for `BaseControlledAsyncRedeem.deposit()`.

### Proof of Concept
Not independently verifiable from the indexed contents: the vulnerable arithmetic (`convertToShares`) and any within-block mutators of `totalAssets()`/`totalSupply()` reside in the Solidity source of `PublicDelegation.sol`, which is not present in this repository (only the generated Go ABI bindings are indexed under `contracts/bindings/publicdelegation/PublicDelegation.go`). A concrete PoC transaction sequence (attacker `stake()`/`redeem()` immediately before victim's `stake()` in the same block) cannot be constructed with certainty without access to that source file — starting a full Devin session with filesystem access would be needed to pull and review `PublicDelegation.sol` directly and confirm exploitability.
