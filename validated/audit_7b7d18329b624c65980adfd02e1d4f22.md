### Title
PedPoP share verification ignores participant exponents, accepting shares evaluated at participant 1 for every recipient - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`exponential` intends to produce coefficients `1, i, i^2, ...` for checking a Pedersen commitment against a share. It computes `exp * i` but discards the result, so every commitment is weighted by `1`. `calculate_share` therefore verifies `share == f(1)` rather than `share == f(i)` for every participant.

### Finding Description
In `exponential`, the closure pushes `(exp, values[l])` and then evaluates `exp * i` without assigning it back to `exp`. Because `exp` remains `C::F::ONE`, the returned statement list is equivalent to checking the sum of all commitment points against `share * G`, which is the polynomial evaluation at participant index `1`. `share_verification_statements` passes the recipient's `Participant` value into this broken routine, and `calculate_share` queues the resulting statements for verification.

### Impact Explanation
A participant-controlled secret-share message can be valid under the implemented check while being invalid for the intended recipient. For every participant other than `1`, a share equal to the sender polynomial evaluated at `1` passes verification instead of the required evaluation at that recipient's index. This is an incorrect verifier formula and allows malformed DKG shares to be accepted into `ThresholdKeys::new`, producing inconsistent threshold state rather than detecting the invalid share.

### Likelihood Explanation
Any protocol participant able to submit an `EncryptedMessage<C, SecretShare<C::F>>` to a victim's `calculate_share` can trigger the flawed verification. The malformed share does not require solving a challenge or forging a proof: after encryption/decryption succeeds, the value is converted to a scalar and checked using the incorrect all-ones coefficient list.

### Recommendation
Update the accumulator inside `exponential` so it is multiplied by the participant index on each iteration, for example by assigning `exp *= i` after pushing the current coefficient. Add regression coverage showing that shares for participants `1` and `2` are verified against distinct powers and that a share valid only for participant `1` is rejected for participant `2`.

### Proof of Concept
For a sender polynomial `f(x) = a0 + a1*x + ...`, let the advertised commitments be `A_j = a_j * G`. `exponential(i, commitments)` currently emits:

```text
[(1, A0), (1, A1), (1, A2), ...]
```

Thus `share_verification_statements(i, commitments, f(1))` checks:

```text
A0 + A1 + A2 + ... - f(1)G == 0
```

This equation is true for every recipient `i`, even though correct PedPoP verification requires:

```text
A0 + i*A1 + i^2*A2 + ... - f(i)G == 0
```

Consequently, sending `f(1)` to participant `i != 1` is accepted by `calculate_share`.
