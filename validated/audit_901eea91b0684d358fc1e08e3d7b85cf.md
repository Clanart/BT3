Missing registration check in PedPoP blame decryption causes panic on attacker-controlled `recipient` (denial of service) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2023-5090 is an improper/missing check in a state path (guest APIC reset) that grants unintended access and yields a denial of service (CVSS 5.5, A:H only). The Serai analog lives in PedPoP's blame machinery: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` without verifying the decryptor ever registered an encryption key. `enc_keys` is populated in `Decryption::register` for every participant *except the local party* (`verify_r1` skips `l == params.i()`), and `blame()` accepts `sender`/`recipient`/`msg`/`proof` values that are all attacker-influenceable (the `msg` is an `EncryptedMessage` deserializable via `EncryptedMessage::read` — an in-scope untrusted-bytes entry point). A crafted accusation naming a `recipient` with no registered key panics the node during blame evaluation — a reachable DoS matching the CVE's availability-only profile.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` as an argument to `dleq.verify` (line 388). `HashMap` indexing panics if the key is absent. `enc_keys` is only filled via `Decryption::register` (lines 351–362), which is called from `KeyMachine::verify_r1`/`calculate_share` for all participants *except* `self.params.i()` — the local participant never registers its own encryption key under itself. `BlameMachine::blame` (crypto/dkg/pedpop/src/lib.rs:623) passes the caller-supplied `recipient` straight into `blame_internal` → `decrypt_with_proof`, and `AdditionalBlameMachine` reconstructed via `AdditionalBlameMachine::new` has the same gap. To reach the panic, the accusation must carry `proof: Some(_)` and a `msg` whose Schnorr PoP verifies — trivially satisfied by an attacker who generates their own per-message key and signs it (the PoP binds `from`, `msg.key`, and the ciphertext, all attacker-chosen). No check anywhere verifies `recipient` is a registered participant before the map index.

### Impact Explanation
A single crafted blame/accusation message causes a panic (index-out-of-map) inside PedPoP blame resolution on any node that evaluates it, aborting DKG completion and crashing the processor's key-gen task. This is a denial of service only — no key material is leaked — exactly matching the CVE's A:H / C:N / I:N profile. Severity: Medium.

### Likelihood Explanation
The attacker needs only to participate in (or submit to) the blame flow with an `EncryptedMessage` bearing a valid PoP — cheap to construct — and a `recipient` index equal to the evaluating node's own participant ID or any non-registered `Participant`. Since `blame` is invoked by nodes adjudicating accusations received from peers, an unauthenticated-in-crypto-terms party can trigger it. The main mitigations are caller-level authentication and the fact that honest accusations name real registered recipients, which is why this is Medium rather than High.

### Recommendation
In `decrypt_with_proof`, replace `self.enc_keys[&decryptor]` with a `get(&decryptor)` lookup that returns `Err(DecryptionError::InvalidProof)` (or a dedicated error) when the decryptor has no registered key. Additionally, `blame()`/`blame_internal` should validate that `sender` and `recipient` are distinct members of `params.all_participant_indexes()` before processing.

### Proof of Concept
1. Run a PedPoP DKG to completion of `calculate_share`, yielding a `BlameMachine` (or build `AdditionalBlameMachine::new(context, params, commitment_msgs)`).
2. Attacker crafts `EncryptedMessage { key: k*G, pop: SchnorrSignature::sign(k, r, pop_challenge(ctx, r*G, k*G, from, ciphertext)), msg: ciphertext }` — PoP verifies.
3. Supply any `EncryptionKeyProof` (e.g., a `DLEqProof::prove` over attacker keys).
4. Call `blame(sender, recipient = params.i() /* the evaluating node itself, never registered */, msg, Some(proof))`.
5. `decrypt_with_proof` passes the PoP check, then evaluates `self.enc_keys[&decryptor]` → panic: HashMap index on absent key → node crash. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
