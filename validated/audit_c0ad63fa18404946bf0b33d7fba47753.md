### Title
Just-in-time deposit before `queueNewRewards` lets an unprivileged staker steal a disproportionate, non-time-weighted share of newly injected rewards - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` (and the equivalent `BaseRewardPoolV2` / `vlMGPBaseRewarder` / `mWOMSVBaseRewarder`) distribute rewards via `_provisionReward`, which instantly injects the entire `_amountReward` into `rewardPerTokenStored` based on the pool's *current* `totalStaked()`, with no time-weighting, streaming (`rewardRate`/`periodFinish`), or minimum staking duration. Because `earned()` only compares a user's current balance against the stored per-token index at the moment of their last checkpoint, an attacker can deposit immediately before a manager's `queueNewRewards` call and withdraw immediately after, capturing a pro-rata share of the reward for zero time staked.

### Finding Description
`_provisionReward` in `rewards/BaseRewardPool.sol` computes: [1](#0-0) 
This adds `_amountReward` to `rewardPerTokenStored` scaled by `this.totalStaked()` at that exact instant — there is no accrual over time (no `rewardRate`, `lastUpdateTime`, `periodFinish`). Compare this to `earned()`: [2](#0-1) 
`earned` = `balanceOf(account) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals + userRewards`. `userRewardPerTokenPaid` is only updated in `_updateFor`, which is called via the `updateReward` modifier on `getReward`, and internally inside `MasterMagpie._deposit` / `_withdraw` through `_harvestBaseRewarder` before the user's `amount`/`available` balance is changed.

Exploit flow:
1. Attacker calls `MasterMagpie.deposit(stakingToken, largeAmount)`. Inside `_deposit`, `_harvestBaseRewarder` runs first (checkpointing the attacker's *old*, small balance), then `user.amount`/`user.available` is increased by `largeAmount`: [3](#0-2) 
The attacker's `userRewardPerTokenPaid` in `BaseRewardPool` is now pinned at the pre-injection index, but `balanceOf(attacker)` (read live from `MasterMagpie.stakingInfo`) is now the large deposited amount.
2. A manager calls `queueNewRewards(_amountReward, _rewardToken)`, which is `onlyManager`-gated but its effect (`_provisionReward`) uses `totalStaked()` at that moment, which already includes the attacker's just-added large stake — diluting the increment for genuine long-term stakers while still crediting the attacker's now-large balance the full pro-rata cut.
3. Attacker calls `MasterMagpie.withdraw(stakingToken, largeAmount)`. This triggers `_harvestAndUnstake` → `_harvestBaseRewarder` → `getReward`, which runs `updateReward(_account)` → `_updateFor` BEFORE `user.amount` is decremented: [4](#0-3) 
`_updateFor` computes `earned()` using the still-large `balanceOf(attacker)` against the new `rewardPerToken`, crediting the attacker with the full pro-rata share of the reward injected in step 2, despite zero holding duration.

No modifier, cooldown, vesting, or time-weighting exists in `BaseRewardPool`/`MasterMagpie` to prevent this: `deposit`/`withdraw` only carry `whenNotPaused`/`nonReentrant`, which do not prevent sequential same-block or same-transaction-batch execution of deposit → (manager tx) → withdraw. The root cause is the reward-pool design choosing an instantaneous, balance-at-injection-time accounting model instead of a duration-weighted (e.g., Synthetix `rewardRate`/`periodFinish`) accrual model.

### Impact Explanation
This is a direct theft of user funds: pro-rata rewards that should accrue to long-term stakers based on duration-weighted stake are instead diverted to an attacker who holds the position for effectively zero time. The magnitude scales with the size of the reward being queued and the attacker's ability to temporarily out-stake the rest of the pool, directly diluting/stealing unclaimed yield from legitimate long-term stakers. This matches the "theft or permanent freezing of unclaimed yield" / "direct theft of user funds" Immunefi impact classes.

### Likelihood Explanation
- No privileged role is required by the attacker; only visibility of the manager's pending `queueNewRewards` transaction (mempool-visible) and enough capital/flash-loanable stakingToken to temporarily acquire a large relative share of `totalStaked()`.
- The attack requires no reentrancy and no bypass of any check — `deposit`, `queueNewRewards`, and `withdraw` are each fully valid, independently authorized calls; the vulnerability is purely in accounting design.
- Feasible via front-running or same-block bundling (e.g., flashbots-style ordering) whenever a reward-queueing transaction is visible before inclusion; repeatable every time a manager queues new rewards, and further amplified with flash-loaned stakingToken if the token supports it.

### Recommendation
Redesign reward accrual in `BaseRewardPool`/`BaseRewardPoolV2`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder` to use a duration-weighted streaming model (Synthetix-style `rewardRate`, `lastUpdateTime`, `periodFinish`) instead of instantaneously crediting `rewardPerTokenStored` based on point-in-time `totalStaked()`. Alternatively, enforce a minimum staking duration/cooldown before a deposited balance is eligible to receive newly queued rewards, or snapshot `totalStaked()`/eligible balances prior to the block in which `queueNewRewards` executes.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool` (with a manager address), and a mock ERC20 staking token and reward token.
2. Fund and have a "long-term staker" (Alice) deposit `100e18` staking tokens and let several blocks/time pass (no rewards queued yet, since the pool design provides no time-based accrual — even so, this establishes baseline stake).
3. Have the attacker (Bob) call `MasterMagpie.deposit(stakingToken, 9900e18)` in one transaction — massively diluting/dominating `totalStaked()` (now `10000e18`, with Bob holding 99%).
4. In the next transaction, the manager calls `BaseRewardPool.queueNewRewards(1000e18, rewardToken)`, transferring 1000e18 reward tokens into the pool; `rewardPerTokenStored` increases based on `totalStaked() = 10000e18`.
5. Immediately after, Bob calls `MasterMagpie.withdraw(stakingToken, 9900e18)`, triggering `getReward` and crediting Bob ~990e18 of the 1000e18 reward (99% share) despite having staked for 0 blocks/seconds.
6. Assert: `rewardToken.balanceOf(bob)` ≈ `990e18` while `rewardToken.balanceOf(alice)` (after she calls `withdraw`/`getReward`) is only ≈ `10e18`, even though Alice was the only staker present for the entire pre-injection period. Assert this violates duration-weighted conservation: Bob's claimed reward vastly exceeds his time-weighted entitlement (0 since he held for effectively 0 duration relative to the reward event).

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
```

```text
        if (!_isVlMgp && user.available < _amount)
```
