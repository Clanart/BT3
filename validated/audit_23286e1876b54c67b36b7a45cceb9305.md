### Title
Chainlink Circuit-Breaker/Malfunction Price Not Filtered in `SimplexPaymaster._getOraclePrice` — Users Can Be Overcharged in ERC-20 Gas Fees - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` trusts any Chainlink `latestRoundData()` answer that is positive and within `maxOracleAge`, with no check against the aggregator's `minAnswer`/`maxAnswer` bounds and no cross-validation against a second price source. If a configured native or token oracle malfunctions or hits its circuit breaker during a real market move (as opposed to becoming stale), it will keep emitting a plausible, "fresh" but wrong price. That price is used unmodified to compute `tokenPrice` in `_tokenPrice()`, which every UserOp uses to determine the ERC-20 amount charged via `PaymasterERC20`'s prefund/postOp flow.

### Finding Description
`_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:426-442`) performs exactly the two checks the original Sublime report criticized as insufficient: non-zero/positive answer and heartbeat freshness. It does not:
- Compare the Chainlink answer against a second source (e.g., the on-chain Uniswap V2 router already wired into the contract via `IDispatcher(host()).uniswapV2Router()`) for sanity/bound checking, as the original report's mitigation recommends.
- Detect the well-known Chainlink circuit-breaker failure mode, where the aggregator's answer sticks at `minAnswer`/`maxAnswer` while `updatedAt` keeps advancing with each heartbeat — passing both the staleness and non-positivity checks while being materially wrong.

`_tokenPrice()` (lines 419-424) feeds this unchecked price directly into `tokenPrice`, returned from `_fetchDetails()` (lines 374-393), which `PaymasterERC20` uses to compute the ERC-20 cost charged to the UserOp sender at validation time (prefund) and settled in `_postOp`. Every unprivileged account that submits a UserOp through this paymaster is exposed — no relayer, prover, or governance compromise is required, only a malfunctioning price feed, matching the original report's premise verbatim.

### Impact Explanation
A corrupted-but-"valid" price (frozen at a circuit-breaker bound during a real depeg/crash of the native asset or the fee token) causes every UserOp routed through the paymaster to be charged an incorrect ERC-20 amount pulled via `transferFrom`/permit from the user's wallet. Depending on direction, this either drains user funds (overcharge) or drains the paymaster's own EntryPoint deposit/treasury reserves (undercharge), both of which are within the bounty's "stealing or loss of funds" / "transaction manipulation" categories.

### Likelihood Explanation
The code comment itself acknowledges the risk ("bounding exposure to the residual allowance even against a malicious oracle") and mitigates it only by convention — advising clients to keep permit/approval amounts small — rather than by an on-chain guard. This is a design gap, not a hypothetical: Chainlink circuit-breaker incidents have occurred in production (e.g., during LUNA/UST and stETH depeg events) and are a recognized real-world failure class, making this a concretely reachable, non-malicious-actor scenario exactly like the seed report.

### Recommendation
In `_getOraclePrice`, additionally reject answers at or near the aggregator's documented `minAnswer`/`maxAnswer` bounds (fetch via `aggregator()`/`phaseAggregators` or hardcode per-feed bounds in `TokenConfig`/`Params`), and/or cross-check the Chainlink price against the existing Uniswap router quote within a configurable deviation tolerance before using it in `_tokenPrice()` and `swapAndDeposit()`.

### Proof of Concept
1. Governance registers a token/native oracle pair via `RegisterToken`/`UpdateParams` (`evm/src/utils/SimplexPaymaster.sol:200-238`).
2. The underlying Chainlink aggregator's underlying asset experiences a sharp real depeg/crash; the aggregator's answer pins at its `minAnswer` (or `maxAnswer`) while continuing to update `updatedAt` each heartbeat.
3. `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:428-434`) passes both its checks (`answer > 0`, fresh `updatedAt`) despite the answer being stuck far from the true market price.
4. Any user submits a UserOp; `_fetchDetails` → `_tokenPrice` (lines 374-424) computes `tokenPrice` from the corrupted feed, and `PaymasterERC20` charges the user's registered token accordingly via `transferFrom`, resulting in an incorrect (potentially far larger) ERC-20 debit than the actual gas cost.

```text
    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
