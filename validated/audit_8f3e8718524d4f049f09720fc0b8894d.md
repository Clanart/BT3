## Analysis

The Flayer report's core broken invariant: a public "no-op-in-progress" guard is keyed on presence in a mutable map/counter (`shutdownVotes != 0`), and the same actor who triggers that state can call a separate, legitimate public function (`reclaimVote`) to zero it back out, defeating the guard's purpose without ever satisfying the real precondition it was meant to enforce.

The direct local analog is in `modules/pallets/intents-coprocessor/src/lib.rs`, in the phantom-order bidding flow.

### Title
Filler bypasses the phantom-order "one bid, no updates" invariant via `retract_bid` + `place_bid` - (File: `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
`place_bid` enforces a documented invariant for phantom orders — "one bid per filler, no updates" — by checking `!Bids::<T>::contains_key(&commitment, &filler)` before accepting a bid. But `retract_bid` is a public, unrestricted extrinsic that removes exactly that map entry and refunds the deposit. A filler can call `retract_bid` then `place_bid` again with a different `user_op` any number of times inside the same bidding window, completely bypassing the "no updates" rule the duplicate check exists to enforce.

### Finding Description
`place_bid` at [1](#0-0)  gates phantom-order bids on `Bids::<T>::contains_key(&commitment, &filler)`, explicitly documented as "one bid per filler, no updates, and only within the configured acceptance window."

`retract_bid`, a separate signed extrinsic open to any caller, removes the caller's own entry from `Bids` and unreserves the deposit: [2](#0-1) 

Because `place_bid`'s duplicate check only inspects current map membership rather than any monotonic "has this filler ever bid on this commitment" record, a filler can:
1. `place_bid(commitment, user_op_A)` — reserved deposit, `Bids` entry set.
2. `retract_bid(commitment)` — deposit unreserved, `Bids` entry removed, well before the window in `PhantomOrderInfo.created_at_block + window` closes (checked at [3](#0-2) ).
3. `place_bid(commitment, user_op_B)` — passes `!Bids::contains_key(...)` again, accepted as a "fresh" bid.

This can be repeated arbitrarily within the single acceptance window, exactly mirroring the Flayer pattern: a guard based on transient state (`shutdownVotes != 0` / `Bids::contains_key`) that the same actor neutralizes via a legitimate, unrelated public call (`reclaimVote` / `retract_bid`) before the privileged/structural check is meaningfully evaluated.

Phantom orders exist specifically to produce a price signal: each window's bids are captured for the indexer to aggregate once `PhantomBidWindowExhausted` fires at [4](#0-3) , and the SDK documents that this snapshot feeds order quoting ("prices the order's input/output amounts via Phantom order snapshots by default"). Allowing a single filler unlimited resubmissions inside one window lets that filler inject an arbitrary number of self-chosen price points into the snapshot used to price real swaps, directly undermining the invariant the duplicate-bid check was written to guarantee.

### Impact Explanation
A filler can flood a phantom order's bid set with many different self-authored price points within a single window, skewing the VWAP/phantom snapshot the indexer aggregates for real order pricing. Since that snapshot feeds the default quote strategy for cross-chain swap pricing, a filler who can manipulate it can bias quotes in their own favor when later filling real user orders — a logic/transaction-manipulation attack on settlement pricing reachable by any unprivileged, unpermissioned account, with no relayer, prover, or admin compromise required.

### Likelihood Explanation
Both `place_bid` and `retract_bid` are ordinary signed extrinsics open to any account; no special permissions, front-running, or peer collusion is needed. The only cost is the storage-deposit reserve/unreserve cycle (returned in full on retract), so the attack is essentially free and repeatable every block within the bidding window.

### Recommendation
Track "has filler already bid on this phantom commitment" independently of live `Bids` membership (e.g., a separate `PhantomBidHistory` set that is never cleared by `retract_bid`, or simply disallow `retract_bid` for phantom-order commitments while their window is open), so the duplicate/no-update rule cannot be reset by the bidder's own retraction.

### Proof of Concept
1. Governance activates a phantom order via `set_phantom_order_config`, and `on_initialize` registers commitment `C` with `created_at_block = N` and a bid window of, say, 10 blocks (`PhantomOrderRegistered`).
2. At block `N+1`, filler `F` calls `place_bid(C, userOp_1)` — succeeds, `Bids::<T>::insert(C, F, deposit)`.
3. At block `N+2`, `F` calls `retract_bid(C)` — succeeds, `Bids::<T>::remove(C, F)`, deposit unreserved.
4. At block `N+3` (still `<= N + window`), `F` calls `place_bid(C, userOp_2)` with a different price/userOp — the `!Bids::contains_key` check passes again, so this is accepted as a "new" bid despite `F` already having bid once in this window.
5. Repeat steps 3–4 up to `window` times, injecting an unbounded number of self-chosen bids from the same filler into the snapshot the indexer aggregates when `PhantomBidWindowExhausted` fires — violating the documented "one bid per filler, no updates" rule and skewing the resulting price snapshot.

		pub fn retract_bid(origin: OriginFor<T>, commitment: H256) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Get the bid deposit amount
			let deposit = Bids::<T>::get(&commitment, &filler).ok_or(Error::<T>::BidNotFound)?;

			// Unreserve the deposit
			<T as Config>::Currency::unreserve(&filler, deposit);

			// Remove the bid marker from onchain storage
			Bids::<T>::remove(&commitment, &filler);

			// Clear the bid from offchain storage
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::clear(&offchain_key);

			Self::deposit_event(Event::BidRetracted { filler, commitment, refund: deposit });

			Ok(())
		}
