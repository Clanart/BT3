### Title
CW721 pointer's `transfer_nft`/ERC721 pointer's `transferFrom` use unsafe `transferFrom` semantics, permanently freezing bridged NFTs sent to non-receiving contracts - (File: `x/evm/client/wasm/query.go`, `contracts/src/CW721ERC721Pointer.sol`)

### Summary
Sei's EVM<->CosmWasm NFT bridging always moves the underlying ERC721 token using the unsafe `transferFrom` selector, never `safeTransferFrom`. Because CosmWasm's `transfer_nft` execute message has no "safe" variant and the CW721 pointer contract for a real ERC721 collection is built purely on top of `transferFrom`, any transfer routed through the pointer permanently skips the ERC721 receiver-capability check. If the destination address resolves to a smart-contract account that does not implement `onERC721Received`, the NFT becomes permanently stuck with no way to recover it through the pointer's exposed interface.

### Finding Description
`x/evm/client/wasm/query.go`'s `HandleERC721TransferPayload` builds the calldata for a real ERC721 contract using `abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())` [1](#0-0) . This payload is the only transfer primitive exposed to CosmWasm contracts via the `erc721_transfer_payload` query, and it is consumed by the example CW721-over-ERC721 pointer's `transfer_nft` handler, which resolves the owner, builds the payload, and delegate-calls the real ERC721 contract with it — the only transfer path available to callers of the pointer [2](#0-1) .

Symmetrically, on the EVM side, `CW721ERC721Pointer.sol` (the ERC721 pointer wrapping a real CW721 collection) implements `transferFrom` by directly issuing a `transfer_nft` CosmWasm execute message, with no analog of `safeTransferFrom` overridden to add a receiver check; the base OZ `ERC721` contract's `safeTransferFrom` would call this overridden `transferFrom` and then attempt `_checkOnERC721Received`, but any EVM caller that instead calls the underlying CosmWasm `transfer_nft` execute message directly (bypassing the pointer's Solidity entrypoint via the wasmd precompile or a wasm-side contract) achieves the same unsafe transfer with no check at all [3](#0-2) .

Both directions of the NFT pointer bridge (`CW721 -> ERC721` and `ERC721 -> CW721`) route every transfer through the unsafe ERC721 `transferFrom` selector. Unlike a normal ERC721 collection where a caller retains the choice to call `safeTransferFrom` themselves, here the bridging layer is the only path available to move a real ERC721 token from a CosmWasm-originated transfer, so the safety check can never be exercised.

### Impact Explanation
An NFT (real ERC721 token) transferred through the CW721 pointer's `transfer_nft` message to a Sei address whose associated EVM address is a smart-contract account not implementing `IERC721Receiver` becomes permanently locked in that contract with no way to move it out, since only the unsafe `transferFrom`-based `transfer_nft` path is exposed by the pointer. This is a permanent fund (NFT) freezing condition, reachable by any unprivileged CosmWasm user who owns the NFT and initiates a normal `transfer_nft` execute message.

### Likelihood Explanation
Likelihood is moderate: any CosmWasm holder of an ERC721 token wrapped by the pointer contract who transfers it to a Sei address mapped to a contract account (e.g., another CosmWasm contract's associated EVM address, or any EVM contract without `onERC721Received`) will trigger permanent loss, without requiring any privileged role or attacker cooperation — a normal, well-intentioned transfer to a contract-controlled address is sufficient.

### Recommendation
Change `HandleERC721TransferPayload` (and the mirrored `CW721ERC721Pointer.transferFrom`) to build/execute `safeTransferFrom(from, to, tokenId, "")` instead of `transferFrom`, so that the ERC721 receiver-capability check is enforced on every bridged transfer, consistent with the ERC721 standard's recommended usage. Alternatively, expose a recovery path so that pointer transfers can be reversed/rescued if the destination cannot handle the token.

### Proof of Concept
1. Deploy (or use) a real ERC721 collection and its CW721 pointer contract on Sei per `example/cosmwasm/cw721`.
2. Create a Sei-address-associated EVM smart contract that does not implement `onERC721Received` (e.g., a plain contract with no fallback logic).
3. As the NFT owner, send a CosmWasm `transfer_nft` message on the pointer, with `recipient` set to the Sei address associated with that non-receiving contract.
4. `transfer_nft` internally calls `erc721_transfer_payload`, which packs `transferFrom(from, to, tokenId)` [1](#0-0)  and delegate-calls the real ERC721 contract — the transfer succeeds because `transferFrom` performs no receiver check.
5. The NFT is now owned by the non-receiving contract on the EVM side; there is no `transfer_nft`/`transferFrom` caller who can move it out (the contract has no logic to call `transferFrom`/`approve`), so the token is permanently frozen.

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```

```text
    }
```
