## Finding: Git's clone symlink-attack protection is explicitly disabled during recursive clones [1](#0-0) 

### Title
`GIT_CLONE_PROTECTION_ACTIVE=false` disables Git's built-in recursive-clone symlink/submodule protection - (File: `app/src/lib/git/clone.ts`)

### Summary
Just like the Raft report where a hard security bound (`MAX_REDEMPTION_SPREAD`) was set to a value that defeated its own stated purpose, GitHub Desktop's `clone()` function hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment used for every `git clone --recursive` invocation. This environment variable is Git's own internal safety flag (introduced as part of the fix family for CVE‑2024‑32002) used to detect and reject clones where a malicious repository/submodule tries to abuse case-insensitive or symlinked `.git` paths to write files outside the intended working tree during a recursive submodule clone. Forcing it to `'false'` at the process level defeats that protection for every clone Desktop performs.

### Finding Description
`clone()` builds the git invocation with `--recursive` and explicitly sets:
```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

`GIT_CLONE_PROTECTION_ACTIVE` is not a user preference — it's the flag Git itself sets/reads to know whether it is already inside a protected clone context so it can refuse to write submodule content into paths that collide with `.git` on case-insensitive filesystems or via symlink tricks (the underlying issue behind CVE‑2024‑32002/33005, which allowed a malicious repo with crafted submodules to escape the clone destination and write arbitrary files, including hooks, enabling code execution). By unconditionally forcing this to `'false'`, Desktop tells Git "the protection context is not active," short-circuiting the very guard Git added to stop this class of attack, for every recursive clone Desktop performs — i.e., for any repository/URL the user clones, which is fully attacker-controlled content (a malicious public repo with crafted submodules).

The only other guard present, `isClonePathSensitive()`, only checks the *destination* directory the user chose (home dir, `.ssh`, `.gnupg`, `.config`, `.gitconfig`) [3](#0-2)  — it does nothing to stop a malicious submodule from writing to arbitrary paths *inside or beside* the chosen destination via the symlink/case-folding collision that `GIT_CLONE_PROTECTION_ACTIVE` exists to prevent. So the destination-path check does not compensate for disabling Git's own protection.

### Impact Explanation
If the disabled check is the one that stops a malicious repository from smuggling a submodule/gitlink that collides with `.git` (via symlink or case-insensitive filesystem trick), an attacker who controls a repository that a victim clones through Desktop (satisfying the "attacker controls a cloned/fetched repository" impact criterion) could write files outside the intended clone directory — e.g., into `.git/hooks` — leading to arbitrary code execution the next time Git runs a hook, or silent corruption of the checked-out working tree.

### Likelihood Explanation
Every single clone performed by Desktop (the core "Clone repository" flow) uses `--recursive` with this environment override, so the disabled protection is on the default, unprivileged path any user takes when cloning an untrusted/public repository — no special user action beyond a normal clone is required.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Remove the override (or set it to `'true'`/leave it unset so Git's default protective behavior applies) so Git's own case-folding/symlink collision checks for recursive submodule clones remain active. If the override was added to work around a specific compatibility issue, that workaround should be re-scoped (e.g. only for verified-safe repositories) rather than applied globally to all clones.

### Proof of Concept
1. Host a git repository containing a submodule/gitlink entry crafted to exploit the case-insensitive `.git` collision technique underlying CVE‑2024‑32002 (a submodule path that, on a case-insensitive filesystem, resolves to `.git`, combined with a symlink to redirect subsequent writes).
2. Have a victim clone this repository through GitHub Desktop's "Clone repository" dialog (`clone()` in `app/src/lib/git/clone.ts`), which always passes `--recursive` and sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`.
3. Because Desktop suppresses Git's protection flag, Git does not treat this as a protected recursive-clone context and proceeds to check out the crafted submodule content, allowing the write to occur outside/alongside the real `.git` directory (e.g., overwriting hooks) rather than being rejected as it would be with the protection enabled.

Note: full confirmation that this reproduces on a current `dugite`/Git build bundled with Desktop (i.e., that the vulnerable Git version and code path are still present) would require running the actual clone against a crafted test repository, which is outside what static code review can confirm; the code-level fact that Desktop explicitly forces this protective flag off is clearly established in the source.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
