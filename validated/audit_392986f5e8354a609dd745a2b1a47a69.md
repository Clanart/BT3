### Title
Hidden bidirectional Unicode characters in a malicious repo's diff content are only warned about, not blocked or sanitized, before being written into the staged patch - ([File: app/src/lib/patch-formatter.ts], [File: app/src/lib/diff-parser.ts])

### Summary
The Sablier report's broken invariant is: a value used to gate/validate an action is derived from the same untrusted, attacker-influenced source as the action itself, so the "check" cannot actually catch manipulation. The closest verified analog in this codebase is in the partial-commit/patch-generation path: `formatPatch` (`app/src/lib/patch-formatter.ts`) builds the exact bytes that get passed to `git apply --cached` (`app/src/lib/git/apply.ts`) directly from `line.text` of the parsed diff, and the diff parser's only defense against Trojan-Source-style hidden bidirectional Unicode characters (`HiddenBidiCharsRegex` in `app/src/lib/diff-parser.ts`) is surfaced purely as a UI banner (`app/src/ui/diff/diff-contents-warning.tsx`), not as a block on staging/committing. The file content shown to the user and the file content actually staged both come from the same attacker-controlled repository bytes, and the "protection" (the warning) does not prevent those bytes from being committed.

### Finding Description
When a user opens the diff for a file that was cloned/fetched from a repository under attacker control, `getWorkingDirectoryDiff`/the diff parser detects invisible bidi override characters and sets `hasHiddenBidiChars` on the diff object (`app/src/lib/diff-parser.ts`, `app/src/models/diff/raw-diff.ts`, `app/src/models/diff/diff-data.ts`). This flag is consumed only by `app/src/ui/diff/diff-contents-warning.tsx` to render an informational banner in the UI.

Crucially, when the user performs a partial commit (selecting individual lines/hunks) or a full commit, `formatPatch` in `app/src/lib/patch-formatter.ts` reconstructs the patch to be applied by copying `line.text` verbatim from the parsed diff hunks: [1](#0-0) 

This patch is fed straight into `git apply --cached` in `applyPatchToIndex`: [2](#0-1) 

Nothing in this pipeline consults `hasHiddenBidiChars` to strip the invisible characters or to refuse staging/committing. The same is true for `formatPatchToDiscardChanges`, which similarly copies raw line text into a patch applied to the working directory.

The "guard" that exists (`HiddenBidiCharsRegex` detection and the warning banner) is purely informational — a user who misses or dismisses the banner (or who is looking at a hunk that wasn't expanded, since the regex is also applied per-expansion in `app/src/ui/diff/text-diff-expansion.ts`) will have the invisible/reordering characters committed exactly as they exist in the attacker's file, silently causing the committed/pushed content to render or execute differently than what appeared selected in the diff view.

### Impact Explanation
This allows a "Trojan Source"-class attack: an attacker who controls a file the user pulls/clones/checks out can embed bidirectional Unicode control characters that make code displayed in the Desktop diff view look benign (e.g., a comment) while the underlying bytes reorder to something else (e.g., malicious logic) once compiled/interpreted or displayed by a plain editor/CI. Since GitHub Desktop's diff and commit machinery both derive from the same untrusted bytes, and the only mitigation is a dismissible/omittable UI banner rather than a hard stop, the user can be tricked into committing and pushing content whose real semantic meaning differs from what was shown in the review UI — a silent corruption of what the user commits, which falls within the report's valid-impact category ("attacker controls a cloned/fetched repository ... result is ... silent corruption of what the user commits or pushes").

### Likelihood Explanation
Moderate. The attacker needs to get the user to interact with a repository/branch/PR containing crafted bidi characters (a realistic scenario: any public repo the user clones, or a PR they check out via Desktop). No local access, no admin rights, and no social-engineering beyond normal collaboration workflow is required — this mirrors common supply-chain "Trojan Source" attack patterns that have been publicly documented across many tools. The main uncertainty (not fully verified due to tool-call limits) is whether there is additional logic elsewhere (e.g., in `diff-helpers.tsx`) that blocks commit actions when `hasHiddenBidiChars` is true; based on the citations found, the flag's only confirmed consumer is the warning banner component, and `patch-formatter.ts`/`apply.ts` show no reference to it.

### Recommendation
- Treat `hasHiddenBidiChars` as a hard gate, not just a display warning: block or require explicit confirmation before `applyPatchToIndex`/`discardChangesFromSelection`/full commit when hidden bidi characters are present in the affected hunks.
- Consider stripping or visually rendering (rather than silently passing through) bidi control characters in the actual bytes used to build the patch, or refusing to stage content containing them without an explicit, per-file user override.
- Extend the same detection to `formatPatchToDiscardChanges` and any other code path that emits `git apply` input from parsed diff text.

### Proof of Concept
Conceptual PoC (not run, based on code reading only):
1. Attacker publishes a repository with a file containing Unicode bidirectional override characters that make a line render as an innocuous comment in most editors and in the Desktop diff view, while the underlying byte order forms different code (classic CVE-2021-42574 "Trojan Source" pattern).
2. Victim clones/fetches the repo in GitHub Desktop, modifies the file, and reviews the diff. The diff parser sets `hasHiddenBidiChars = true` and the UI shows a dismissible warning banner (`app/src/ui/diff/diff-contents-warning.tsx`), but selection/staging is not blocked.
3. Victim selects lines to commit (or commits the whole file). `formatPatch` (`app/src/lib/patch-formatter.ts:153-168`) copies `line.text` byte-for-byte into the patch, which `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-81`) applies via `git apply --cached`.
4. The resulting commit contains the same hidden bidi bytes; anything downstream that renders/compiles the file differently than the Desktop diff view (terminal, CI, another editor) will execute or display the "real" reordered content, even though the user never saw or approved that specific rendering — the commit silently diverges from what the user believed they were committing.

Given the size limits of the code index, I was not able to fully confirm whether any additional confirmation dialog exists elsewhere in the commit flow that consults `hasHiddenBidiChars`; a Devin session with full repository access would be needed to trace every consumer of that flag and confirm there is no blocking check before staging/commit.
