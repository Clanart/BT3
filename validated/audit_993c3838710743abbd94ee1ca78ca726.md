### Title
Missing Validation Allows `kip71.gastarget` Governance Parameter to Be Set to Zero, Causing a Division-by-Zero Panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
Similar to the reported `PoolManager.addSeries()` bug — where `zeroParams`/`lpTokenParams` are used without the same emptiness check that `addTarget()` applies to `targetParams` — Kaia's governance parameter validation is inconsistent across the KIP-71 (Magma base-fee) parameters. `kip71.basefeedenominator` has both a `FormatChecker` requiring a non-zero value and a runtime zero-guard before use, but `kip71.gastarget` has neither, even though it is used as a divisor in the exact same base-fee formula.

### Finding Description
In `kaiax/gov/param.go`, the parameter table defines format checkers per governance parameter: [1](#0-0) 
`Kip71BaseFeeDenominator` explicitly rejects zero (`return ok && v != 0`), while `Kip71GasTarget` is registered with `FormatChecker: noopFormatChecker`, which always returns true regardless of the value: [2](#0-1) [3](#0-2) 

`kip71.gastarget` is not one of the parameters given special-case consistency checks in `headerGovModule.checkConsistency` (only `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` are range-checked there); it falls into the catch-all branch that accepts any value passing only the (no-op) format checker: [4](#0-3) 

The resulting `GasTarget` value flows unguarded into `KIP71Config.NextMagmaBlockBaseFee`, which is invoked by `VerifyMagmaHeader` during block header validation for every Magma-enabled block: [5](#0-4) 

Inside `NextMagmaBlockBaseFee`, `BaseFeeDenominator` is defensively guarded against zero ("To avoid panic, set the fluctuation range small"), but the analogous guard is missing for `GasTarget`, which is used directly as a divisor via `big.Int.Div`: [6](#0-5) [7](#0-6) [8](#0-7) 

If `GasTarget == 0` and the parent block's `GasUsed != 0` (which is true for essentially any real block), execution enters either the "used more gas than target" or "used less gas than target" branch and calls `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`. Go's `math/big.Int.Div` panics on division by zero.

### Impact Explanation
`NextMagmaBlockBaseFee` (via `VerifyMagmaHeader`) is called by every full node's `BlockValidator.validateHeader` when processing each new block post-Magma fork: [9](#0-8) 
A panic here during block validation would crash the node processing the block. Because all nodes (proposers and validators alike) run this same code path when validating and building blocks, a single successfully ratified `kip71.gastarget = 0` update would cause every node in the network to panic simultaneously at the next block after the parameter takes effect — a network-wide liveness/consensus-halt event, which is a critical availability impact for the chain.

### Likelihood Explanation
Reaching this bug requires only a normal, already-supported governance action: casting a `governance_vote` for `kip71.gastarget` with value `0`. Unlike `kip71.basefeedenominator`, `kip71.lowerboundbasefee`, and `kip71.upperboundbasefee`, there is no format-level or consistency-level rejection of zero for `kip71.gastarget`, so the vote would be accepted by `NewVoteData`'s format check and by `checkConsistency`, ratified normally, and take effect at the next epoch boundary — with no additional bypass or privilege escalation required beyond the existing (governance-mode-gated) vote mechanism itself. The asymmetry with the neighboring `BaseFeeDenominator` field (which is both format-checked and runtime-guarded) shows this is an overlooked validation gap rather than an intentional design choice.

### Recommendation
Add a non-zero `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go`, mirroring the existing check for `Kip71BaseFeeDenominator` (`return ok && v != 0`). As defense in depth, also add a runtime zero-guard for `GasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, analogous to the existing `BaseFeeDenominator == 0` fallback, so that even a pre-existing or externally-injected zero value (e.g., via genesis/ChainConfig) cannot crash block validation.

### Proof of Concept
1. On a test/permissioned network in `single` governance mode, have the governing node call `governance_vote` with `("kip71.gastarget", 0)`.
2. Observe the vote is accepted (format check passes because `Kip71GasTarget`'s checker is `noopFormatChecker`) and ratified at the next epoch boundary, since `checkConsistency` performs no special validation for this parameter.
3. At the block following the parameter's effective height, any block with non-zero `GasUsed` triggers `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))`, which panics per Go's `math/big` semantics, crashing block validation on every node that processes/validates that header (`params/kip71_config.go` lines 99-103 and 117-121, reached via `VerifyMagmaHeader` from `blockchain/block_validator.go` lines 202-213).

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
