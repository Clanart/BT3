### Title
Suspended (misbehaving) validators remain reward-eligible and retain Council/governance rights despite exclusion from block production - ([File: kaiax/valset/impl/getter_permissionless.go])

### Summary
Kaia's permissionless validator set (KIP-286) marks validators as `Suspended` when they are flagged via AddressBookV2's `getSuspendedValidators()`. This flag correctly removes the validator from the `Committee`/`QualifiedValidators` sets used for block proposing and signing, but it is never consulted anywhere else. All other privileges tied to `State == ValActive` — including block-reward eligibility, Council membership (and therefore governance voting rights), and CN peer-list membership — remain fully intact for a Suspended validator. This mirrors the reported pattern where a "suspended" principal is blocked from one privileged action but is still able to perform other, similarly privileged actions because the restriction was only wired into a single code path.

### Finding Description
The valset module models each validator node with both a `State` (`ValActive`, `ValPaused`, etc.) and a separate boolean `Suspended` flag [1](#0-0) . `Suspended` is populated from AddressBookV2's suspended-validator list via `NodeMap.MarkSuspended` [2](#0-1) , and merged into every node snapshot inside `getNodes`/`applyTransition` [3](#0-2) .

The only place `Suspended` is actually consumed is in `committeeWithFallback`, which subtracts the suspended set from `ValActive` to compute `Committee`/`QualifiedValidators`: [4](#0-3) 

Every other privilege keyed off `State == ValActive` ignores `Suspended` entirely:

1. **Reward eligibility.** `NodeState.IsRewardEligible()` only checks `State == ValActive`, with no reference to `Suspended`: [5](#0-4) 
This is used directly to decide which validators keep receiving staking rewards after the permissionless fork: [6](#0-5) 
The reward module (`kaiax/reward`) never references `Suspended` at all (confirmed by search), so a suspended-but-still-`ValActive` validator continues to receive both minting and fee rewards exactly as an unsuspended validator would.

2. **Council membership / governance.** `getCouncil` includes `{ValActive, ValPaused}` without excluding suspended nodes: [7](#0-6) 
Council membership is what `VerifyVote`/`checkConsistency` use to authorize header governance votes and to validate the governing node: [8](#0-7) [9](#0-8) 
Because Council doesn't filter by `Suspended`, a suspended validator remains eligible to cast governance votes that are honored by `VerifyVote`.

3. **Peer connectivity.** `CNPeers = {VA, VR, VP, CR, CT}` is likewise defined purely from `State`, not `Suspended`: [10](#0-9) 

4. **`applyViolationTransition` explicitly treats `Suspended` as non-exempting for violation state machine transitions** — the code comment even calls out that "Suspended is informational, not a violation exemption" [11](#0-10) . This confirms the design intent that `Suspended` is a soft/temporary flag layered on top of `State`, but the intent is only enforced for the Committee/qualified-validator computation — not for rewards, council, or governance.

### Impact Explanation
A validator that has been suspended by the on-chain suspender role (via AddressBookV2's `suspendValidator`) is meant to be excluded from active block-production duties. However, because only `getQualifiedValidators`/`GetCommittee` consult the `Suspended` flag, the same validator:
- Continues accruing block/staking rewards it should arguably forfeit while suspended (`IsRewardEligible` ignores `Suspended`), causing reward distribution to a validator the protocol has flagged for exclusion.
- Remains part of the `Council`, and thus retains governance voting power and can remain/act as the `GoverningNode` even while suspended, since `VerifyVote`/`checkConsistency` only check Council membership.
- Remains counted as a CN peer for network connectivity purposes.

This is a Medium-severity value-movement/authorization inconsistency: rewards (a concrete token value transfer) continue to flow to an account that the system has explicitly restricted from consensus duties, and governance-vote authorization is not consistent with the suspension state.

### Likelihood Explanation
This triggers automatically and deterministically whenever any validator's node is placed on AddressBookV2's suspended list while its `State` remains `ValActive`. No adversarial transaction crafting is required beyond the (governance/admin-controlled) `suspendValidator` call already anticipated by the design; the divergence between "excluded from Committee" and "still reward-eligible / still in Council" happens on every subsequent block/epoch computation for that validator, making it a systematic rather than edge-case issue.

### Recommendation
Make `Suspended` a first-class exclusion criterion wherever `ValActive`/Council membership currently grants privileges beyond block-signing:
- In `kaiax/staking/impl/getter.go`, exclude nodes where `Suspended == true` (or thread the flag through `IsRewardEligible`) so suspended validators stop earning block/staking rewards.
- In `kaiax/valset/impl/getter_permissionless.go`'s `getCouncil` (and correspondingly in the governance vote-authorization path), decide explicitly whether suspended validators should retain Council/voting rights; if not, subtract `Suspended` there as is already done for `Committee`.
- Audit `getCNPeers` and any other `State`-based getter for the same gap, and add explicit unit tests (analogous to `TestSuspendedFallback`) asserting that `Suspended` nodes are excluded from reward eligibility and Council-derived governance authority, not just from the qualified/committee set.

### Proof of Concept
1. Deploy/advance the chain past the Permissionless (KIP-286) hardfork so AddressBookV2 governs validator state.
2. As the on-chain "suspender" role, call `AddressBookV2.suspendValidator(nodeId)` for a validator `V` whose `State` is `ValActive` (see `SuspendValidator`/`GetSuspendedValidators` bindings) [12](#0-11) .
3. Observe that:
   - `ValsetModule.GetCommittee`/`GetQualifiedValidators` correctly exclude `V` (per `committeeWithFallback`) [4](#0-3) .
   - `ValsetModule.GetCouncil` still includes `V` [7](#0-6) .
   - `StakingModule.GetStakingInfo` still lists `V` as reward-eligible because `parsePermissionlessCallResult` only checks `p.State == ValActive` [6](#0-5) , and the reward module distributes staking rewards to `V` in `assignStakingRewards`/`assignStakingRewardsFlex` unchanged.
   - `VerifyVote` still accepts a governance vote cast by `V` if `V` remains the block proposer/governing node, since it only checks Council membership [8](#0-7) .

Note: I was unable to directly execute this on a live/test network within this session; the analysis is based on static code inspection of the described getters, reward/staking modules, and existing unit tests (`TestSuspendedFallback`, `TestApplyViolationTransition_SuspendedNotExempt`) that confirm `Suspended` is deliberately excluded from the violation/committee logic but not from Council/reward eligibility logic.

// Mutates the receiver in place; the only in-place mutator on NodeMap.
func (v NodeMap) MarkSuspended(suspended []common.Address) {
	set := make(map[common.Address]struct{}, len(suspended))
	for _, addr := range suspended {
		set[addr] = struct{}{}
	}
	for addr, vs := range v {
		_, vs.Suspended = set[addr]
	}
}

// committeeWithFallback returns the committee at the given block.
// Committee = {VA} - {Suspended}.
//
// Safety fallback: when len(committee)=0 due to {ValActive} ⊆ SuspendedSet, fallback to all VA.
func committeeWithFallback(nodes valset.NodeMap) (committee valset.NodeMap, fellBack bool) {
	committee = nodes.Committee()
	if len(committee) > 0 {
		return committee, false
	}

	// ignore SuspendedSet
	return nodes.FilterByState(valset.ValActive), true
}

// getQualifiedValidators: qualified = committee = {VA} − {Suspended} (with safety fallback).
func (v *ValsetModule) getQualifiedValidators(num uint64) (*valset.AddressSet, error) {
	nodes, err := v.getNodes(num)
	if err != nil {
		return nil, err
	}
	committee, fellBack := committeeWithFallback(nodes)
	if fellBack && v.lastSuspendFallbackLog != num {
		logger.Warn("all ValActive are suspended, ignoring suspended set for committee", "num", num)
		v.lastSuspendFallbackLog = num
	}
	return valset.NewAddressSet(committee.Addresses()), nil
}

// TestApplyViolationTransition_SuspendedNotExempt verifies that suspended
// ValActive validators are subject to the same violation rules as non-suspended
// ones — Suspended is informational, not a violation exemption.
func TestApplyViolationTransition_SuspendedNotExempt(t *testing.T) {
	m := NodeMap{
		addr1: {State: ValActive, StakingAmount: belowMinStake, Suspended: true},  // minStake violation
		addr2: {State: ValActive, StakingAmount: aboveMinStake, Suspended: true},  // PFS severe
		addr3: {State: ValActive, StakingAmount: aboveMinStake, Suspended: false}, // no violation
	}
	ctx := violationCtx(t, ctxOpts{
		PfsThreshold:     2,
		MaxSlotAvailable: noSlotLimit,
		MinActiveCount:   noMinActive,
		PFS:              map[common.Address]uint64{addr2: 3},
		PfReport:         []common.Address{addr1},
	})
	out := ctx.applyViolationTransition(m)
	assert.Equal(t, ValExiting, out[addr1].State, "suspended + low staking → ValExiting")
	assert.Equal(t, ValExiting, out[addr2].State, "suspended + PFS severe → ValExiting")
	assert.Equal(t, ValActive, out[addr3].State, "non-suspended, no violation → unchanged")
}
