Based on my investigation, the strongest analog I found is the `protocol.file.allow=always` override in submodule handling, which re-enables the `file://` submodule vulnerability class that upstream Git deliberately disabled by default (Git's fix for the local-clone submodule attack, hardened after CVE-2022-39253/GHSA-related issues). Notably, `clone()` itself also always passes `--recursive` for submodule init/update without this override, and the `checkoutBranch`/`checkoutCommit` flows plumb an `allowFileProtocol` flag through to `updateSubmodulesAfterOperation`, which — when true — adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation.

### Title
Attacker-controlled `.gitmodules` `file://` URLs can force Desktop to read arbitrary local paths into a submodule when `allowFileProtocol` is enabled - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean that, when true, injects `-c protocol.file.allow=always` into the `git submodule update --init --recursive` command [1](#0-0) . This flag is threaded through from `checkoutBranch`/`checkoutCommit` [2](#0-1) . Upstream Git disabled `file://` submodule URLs by default specifically because a malicious repository's `.gitmodules` can point a submodule at an arbitrary local filesystem path (not just other clones), causing Git to copy the contents of that local directory into the submodule working tree during `submodule update --init`. Re-enabling `protocol.file.allow=always` for a checkout that originates from an untrusted/attacker-controlled repository defeats that protection.

### Finding Description
When a user clones or checks out a branch from an attacker-controlled repository whose `.gitmodules` declares a submodule with a `file:///absolute/local/path` URL (e.g., pointing at the user's home directory, a cloud-sync folder, or another local repo containing secrets), `git submodule update --init --recursive` run with `protocol.file.allow=always` will happily treat that local path as a git repository to clone/copy into the submodule directory inside the tracked working tree, subject to standard OS file permissions [3](#0-2) . This mirrors the 1inch bug's core flaw: a value fully controlled by an untrusted party (the merkle root / here, the submodule URL in the repo) is trusted without any bound or allow-list, and the "owner" analog here is Desktop's decision to force `protocol.file.allow=always` rather than deferring to Git's safer default (`user`/deny).

### Impact Explanation
If the copied local content lands inside the working tree and the user later stages/commits/pushes (a very plausible flow if they don't notice a new nested directory, especially if the submodule folder name is chosen to look innocuous), the attacker's malicious repo can exfiltrate local files to whatever remote the victim pushes to next, or the victim could inadvertently `git submodule update`/re-init this into other clones. This satisfies the "silent corruption of what the user commits or pushes" / "file read outside the repo" categories in the given valid-impact list, and the trigger is entirely attacker-controlled repository content (`.gitmodules`), matching the "attacker controls a cloned/fetched repository" criterion.

### Likelihood Explanation
I could not confirm from the indexed code which production call sites pass `allowFileProtocol: true` for `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` on a genuinely untrusted, attacker-supplied repository (the only call sites I could find with `true` are in test helpers such as `setupRepositoryWithUninitializedSubmodule`) [4](#0-3) . Because the codebase index has size limits and may exclude some file contents, I was unable to fully trace every caller in `app-store.ts`/`dispatcher.ts` to determine under what real-world condition (e.g., opening a repo from a clicked deep link, or checking out a PR branch from a fork) this flag is actually set to `true` for a repository the user does not already trust. This is a material gap: if `allowFileProtocol` is only ever `true` for repositories the user has explicitly and knowingly added, the likelihood is low; if it is set `true` unconditionally or based on attacker-influenced state (e.g., automatically for any checkout that previously had an uninitialized submodule), the likelihood is materially higher.

### Recommendation
Confirm and, if necessary, restrict all production call sites that set `allowFileProtocol: true` to only trusted/local scenarios, and prefer Git's default `protocol.file.allow` behavior (or an explicit user confirmation dialog before permitting `file://` submodule URLs) rather than blanket `always`. Additionally, validate `.gitmodules`-declared submodule URLs before running `submodule update --init`, rejecting `file://` URLs that resolve outside the already-cloned repository tree.

### Proof of Concept
I could not construct/verify an end-to-end PoC purely from the indexed code because the exact call chain that supplies `allowFileProtocol: true` for an untrusted repository is not fully visible in the index (only test fixtures were found). A conceptual PoC would be: attacker publishes a repo with `.gitmodules` containing `url = file:///C:/Users/victim/AppData/Roaming/SensitiveApp` (or a `~`-relative equivalent path on macOS/Linux); victim opens/clones this repo and checks out a branch containing that submodule; if the checkout path in question was invoked with `allowFileProtocol: true`, Git copies that directory's tracked-looking content into the submodule folder of the working tree, where it becomes visible to `git status`/`git add` and could be committed and pushed by the victim. **I recommend starting a Devin session with repository access to trace every runtime caller of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm whether `allowFileProtocol` can be `true` for an untrusted, attacker-supplied repository before treating this as a confirmed (rather than plausible) vulnerability.**
