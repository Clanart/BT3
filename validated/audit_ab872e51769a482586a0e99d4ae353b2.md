### Title
Duplicate/unexpected DKG encryption-key registration triggers an `assert!` panic, crashing the participant (remote DoS) - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
The libgit2 CVE-2018-15501 bug class is "crafted protocol message causes an out-of-bounds access / crash (DoS)". Serai's actual parsers are safe against truncated input — `Ciphersuite::read_F`/`read_G` use `read_exact` and canonicality checks (`crypto/ciphersuite/src/lib.rs:74-101`), and all `EncryptedMessage::read`/`EncryptionKeyMessage::read`/`EncryptionKeyProof::read` paths funnel through them (`crypto/dkg/pedpop/src/encryption.rs:57-59, 171-177, 267-269`). However, the same crash-on-crafted-message class exists one layer up: `Decryption::register` enforces uniqueness with a bare `assert!`, so a participant who submits the encryption-key-registration message twice causes a panic in every honest peer processing the DKG round.

### Finding Description
`Decryption::register` records the per-participant ECDH encryption key used for the PedPoP share-distribution round:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

The `EncryptionKeyMessage` is parsed entirely from untrusted wire bytes via `EncryptionKeyMessage::read` (`encryption.rs:57-59`), which itself only performs canonical `read_G` decoding — there is no deduplication at the parse layer. The uniqueness invariant is enforced by panicking, not by returning an `Err`. The same panic-on-untrusted-input pattern exists for lookups: `encrypt` indexes `self.decryption.enc_keys[&participant]` (`encryption.rs:466`) and `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`), both of which panic via `HashMap`'s `Index` impl if the peer's registration was never processed (e.g., dropped/reordered messages in the assumed-authenticated-but-unreliable channel).

The mapped defect is therefore: an untrusted protocol message (a second registration frame for an already-registered `Participant`, or a share message routed before registration) reaches a panic path instead of an error path.

### Impact Explanation
Any unprivileged participant in the DKG who emits a duplicate `EncryptionKeyMessage` — trivially producible by replaying their own valid message — causes every honest node that processes it to panic. In a validator/coordinator deployment this aborts the key-generation ceremony (and, depending on panic handling at the task level, crashes the signer process), halting threshold-key setup. This is a direct analog of the CVE's remote DoS: a well-formed-but-semantically-invalid packet from the network causes a crash, with no cryptographic validity required beyond being a DKG participant.

### Likelihood Explanation
- Reachable from public inputs: the trigger is a duplicated/ misordered DKG message, which any protocol participant can send; the parsing path (`read` → `register`) performs no I/O failure, only an `assert!`.
- Exploitation requires no collusion and no valid signature forgery — the attacker's own genuine message replayed once suffices.
- Cost to attacker is negligible; effect is deterministic panic. The only mitigation is upstream deduplication, which is not enforced in this crate (the `assert!` exists precisely because the caller is trusted not to double-register — an assumption an attacker violates).

Severity assessment: Medium-High DoS on the DKG path; no key material is leaked, so it does not reach Critical.

### Recommendation
- Replace the `assert!` in `Decryption::register` (`encryption.rs:356-359`) with an `io::Result`/typed error return, treating a duplicate registration as a protocol violation that marks the participant as faulty rather than aborting the process.
- Similarly, replace `enc_keys[&participant]` / `enc_keys[&decryptor]` indexing (`encryption.rs:388, 466`) with `.get()` + error, so a missing registration yields a blame/decryption error instead of a panic.
- Audit sibling `assert!`s in the PedPoP message handlers for the same reachability from untrusted `Participant`-tagged input.

### Proof of Concept
Conceptual (no code execution performed — ask-only mode):

1. Two honest nodes and one malicious node run PedPoP with `ThresholdParams { t: 2, n: 3 }`.
2. In the encryption-key-registration round, the malicious node sends its `EncryptionKeyMessage` twice (identical bytes, both parse successfully).
3. Each honest node calls `Decryption::register` for the first copy — succeeds — then for the second copy — `enc_keys.contains_key(&participant)` is `true`, the `assert!` at `encryption.rs:356` fails, and the node panics mid-protocol.

A unit-level reproduction is:

```rust
let mut dec = Decryption::<C>::new(context);
let msg = EncryptionKeyMessage::<C, M>::read(&mut bytes.as_slice(), params)?;
dec.register(attacker, msg.clone()); // ok
dec.register(attacker, msg);         // panic: "Re-registering encryption key"
```

Caveat: I could not fully trace whether the PedPoP orchestration layer in `crypto/dkg/pedpop/src/lib.rs` deduplicates per-participant messages before calling `register`; if it does, this downgrades to defense-in-depth, but the panic-on-index in `decrypt_with_proof`/`encrypt` remains a reachable crash on any ordering where a share arrives without a prior registration.
