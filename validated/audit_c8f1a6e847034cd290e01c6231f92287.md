Confirmed: for KIP-160 (`TreasuryRebalanceV2`), the on-chain contract has no `require` that `sum(allocated amounts) <= sum(zeroed balances)`, and the client-side `RebalanceTreasury` function only checks this invariant for the legacy KIP-103 path.

### Title
Missing check that KIP-160 rebalance allocation does not exceed zeroed balance, allowing arbitrary net-mint of KAIA - (File: blockchain/system/rebalance.go)

### Summary
`RebalanceTreasury()` in `blockchain/system/rebalance.go` enforces "Validation 4" (`totalZeroedAmount >= totalAllocatedAmount`) only when `isKIP103` is true, but silently skips it for the `isKIP160` path. As a result, an owner-approved `TreasuryRebalanceV2` contract can allocate an amount to newbies that is arbitrarily larger than the total balance being zeroed out, and the state-transition code will mint the difference into the new accounts with only the excess being recorded (not prevented) as negative "burnt" (i.e., net mint), with no on-chain or client-side bound check comparable to the AMO's missing rebalance-threshold check.

### Finding Description
`RebalanceTreasury` builds a `rebalanceResult` from the `Zeroed`/`Allocated` data read off the active rebalance contract, and then performs a sequence of validations before executing the balance changes: [1](#0-0) 

Specifically:
- Validation 1–3 (target block number, `Approved` status, `CheckZeroedsApproved`) apply uniformly to both KIP-103 and KIP-160.
- Validation 4, the only check that ties the allocated amount to the zeroed amount, is explicitly gated with `if isKIP103 && ...`, meaning for KIP-160 (`TreasuryRebalanceV2`) this bound is never checked.
- Execution then unconditionally zeroes out the "Zeroed" addresses and sets the "Allocated" addresses to the registered amounts, adding any pre-existing balance of an allocated address plus the `remainder := totalZeroedAmount - totalAllocatedAmount` to `result.Burnt` (which becomes negative, i.e., a net mint, if allocation exceeds the zeroed total).

On the contract side, `TreasuryRebalanceV2.sol`'s `registerAllocated()` only requires the amount to be nonzero and the address not already registered — it does not validate the amount against the sum of zeroed balances: [2](#0-1) 

`checkZeroedsApproved()`/`finalizeApproval()` verify approver quorum only, not amounts: [3](#0-2) 

This mirrors the referenced AMO finding: a state-changing operation ("rebalance") is gated by a precondition check (approval/status) but the actual amount moved is never checked against the invariant/threshold that the operation is supposed to preserve (zeroed balance must cover allocated balance), letting the approved configuration silently inflate supply instead of just redistributing it.

### Impact Explanation
If a KIP-160 rebalance is configured (by the contract owner, following the standard KIP-160 approval workflow) with `sum(allocated) > sum(zeroed)`, the protocol-level `RebalanceTreasury` execution — which runs automatically for every node at the designated fork block — will mint the shortfall directly into the allocated addresses' balances without reverting or flagging an error, unlike the KIP-103 path which aborts with `ErrRebalanceNotEnoughBalance`. This is a direct, protocol-level uncontrolled KAIA supply inflation at a hard-forked block, silently accepted by all nodes (so no state divergence, but a supply-invariant violation is finalized on-chain).

### Likelihood Explanation
This requires a KIP-160 rebalance contract to be deployed and go through the owner-only registration/approval flow, and then have `Kip160ContractAddress`/`Kip160CompatibleBlock` set in chain config — this is an operational/governance action, not something an arbitrary unprivileged transaction sender can trigger directly. However, once such a misconfigured (or malicious) rebalance contract is approved through the normal process, there is no independent safety check anywhere in the client code (unlike KIP-103) to catch or prevent the resulting supply inflation, so the risk is entirely dependent on the correctness of the off-chain amount-registration process with zero on-chain/client backstop.

### Recommendation
Apply the same "Validation 4" invariant check (`totalZeroedAmount.Cmp(totalAllocatedAmount) < 0` → abort) to the `isKIP160` branch as well in `RebalanceTreasury`, or add an equivalent `require(sum(allocated) <= sum(zeroed balances))` check inside `TreasuryRebalanceV2.finalizeApproval()`/`checkZeroedsApproved()` so that unintended (or malicious) net-mint rebalances cannot be finalized regardless of which rebalance path is active.

### Proof of Concept
1. Deploy `TreasuryRebalanceV2` with `rebalanceBlockNumber = N`.
2. `registerZeroed(addrA)` where `addrA` holds `X` KAIA.
3. `registerAllocated(addrB, amount)` with `amount >> X` (only constrained by `amount != 0`).
4. Complete `finalizeRegistration()` → `approve(addrA)` (EOA self-approval) → `finalizeApproval()`; contract reaches `Status.Approved`.
5. Set `chain.Config().Kip160ContractAddress` / `Kip160CompatibleBlock = N` and mine to block `N`.
6. `RebalanceTreasury` runs: `isKIP160 == true`, so Validation 4 is skipped; `state.SetBalance(addrA, 0)` then `state.SetBalance(addrB, amount)` executes unconditionally, as shown in: [4](#0-3) 
resulting in `amount - X` KAIA being minted into `addrB` with no error returned and `result.Success = true`, `result.Burnt` negative.

    /**
     * @dev verify if quorom reached for the zeroed approvals
     */
    function checkZeroedsApproved() public view {
        uint256 numZeroeds = zeroeds.length;
        for (uint256 i = 0; i < numZeroeds; i++) {
            Zeroed memory zeroed = zeroeds[i];
            bool isContract = isContractAddr(zeroed.addr);
            if (isContract) {
                (address[] memory adminList, uint256 req) = _getState(zeroed.addr);
                require(zeroed.approvers.length >= req, "min required admins should approve");
                //if min quorom reached, make sure all approvers are still valid
                address[] memory approvers = zeroed.approvers;
                uint256 numApprovers = approvers.length;
                uint256 validApprovals = 0;
                for (uint256 j = 0; j < numApprovers; j++) {
                    if (_validateAdmin(approvers[j], adminList)) {
                        validApprovals++;
                    }
                }
                require(validApprovals >= req, "min required admins should approve");
            } else {
                require(zeroed.approvers.length == 1, "EOA should approve");
            }
        }
    }
