### Title
Missing replay/expiry check in `AppProxyVerification` allows indefinite reuse of any previously issued signed app‑proxy request - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` verifies only that the HMAC `signature` query parameter matches the other query parameters. It never checks the `timestamp` parameter that Shopify includes in every app‑proxy request, so a signed request never expires. Any query string (including its valid signature) that was ever generated by Shopify for a storefront visit can be replayed by any anonymous party, at any time in the future, and will still be accepted as authentic.

### Finding Description
`verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC over every query parameter except `signature` and compares it with `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

The `timestamp` parameter is treated exactly like any other signed field — it is included in the signature computation but its *value* is never checked against the current time, and no state is kept to detect that a particular `(query params, signature)` pair has already been consumed: [2](#0-1) 

This is structurally the same root cause described in the external report: a signature is verified to be *internally consistent* with the request data, but nothing binds the acceptance decision to a one‑time-use or freshness guarantee, and there is no mechanism to detect resubmission of a previously issued, valid signature. As a result, once a signed app‑proxy URL is produced (Shopify generates these URLs for anyone browsing the storefront pages the proxy is mapped to), that exact URL remains permanently valid and can be resubmitted by anyone who has ever seen it — including anonymous third parties who obtained it via browser history, shared links, referrer headers, web archives/caches, logs, or screenshots — not just the original visitor.

The gem's own test suite confirms only signature correctness is exercised, with no test asserting rejection of stale/old timestamps: [3](#0-2) 

### Impact Explanation
Any controller that includes `ShopifyApp::AppProxyVerification` (the gem's recommended and generator-scaffolded pattern for app‑proxy endpoints) trusts `query_string_valid?` as its sole authenticity/freshness gate: [4](#0-3) 

Because the check never expires, a captured app‑proxy query string is a permanently valid, "Shopify‑signed" credential that an unrelated, fully anonymous attacker can replay indefinitely against the app's public endpoint — for any app‑proxy route the developer builds (including state‑changing ones, per the gem's own documented example of writing app‑proxy `ReviewsController` actions). This allows an attacker with no relationship to the shop or the original visitor to repeatedly trigger app‑proxy actions under a `shop` value they never legitimately visited with, at a time of their choosing, long after the original signed URL was issued.

### Likelihood Explanation
App‑proxy URLs are, by design, exposed to the client/browser (they are the URLs a storefront visitor's browser actually requests), so capturing one requires no special access or secret knowledge — only observing a URL that was already shown to some browser. Combined with the complete absence of any timestamp/freshness/one‑time‑use check in `query_string_valid?`, exploitation requires no privileges beyond making a plain unauthenticated HTTP request to the app's public app‑proxy route with a previously observed query string.

### Recommendation
- Short term: in `query_string_valid?`, in addition to the signature check, validate that `query_hash["timestamp"]` is within an acceptable freshness window (e.g., a few minutes) of the current time, rejecting stale requests.
- Additionally, consider maintaining short-lived state (e.g., a cache of consumed `signature` values with TTL matching the freshness window) to explicitly reject resubmission of a signature that has already been processed, mirroring the "prevent replay of previous signatures" recommendation from the referenced report.
- Document this expectation clearly for any developer building custom app‑proxy controllers on top of this concern.

### Proof of Concept
1. As any storefront visitor (no app/merchant credentials needed), load a page served through the app's registered app‑proxy path, e.g.
   `GET https://shop.example.com/apps/my-app/reviews?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1700000000&signature=<validHmac>`
2. Record the full query string (including `signature`) — it is visible in the browser address bar/network log.
3. At any later time (minutes, days, or months after), as a completely anonymous third party unrelated to the original visitor or shop, resend the exact same query string directly to the app's public endpoint:
   `GET https://app.example.com/app_proxy/reviews?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1700000000&signature=<validHmac>`
4. `query_string_valid?` recomputes the HMAC over the (unchanged) parameters, finds it matches `signature`, and the request is accepted as if freshly issued by Shopify — despite being an arbitrarily old, replayed request.

    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
