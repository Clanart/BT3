Confirmed: `Nonce<T>` in `modules/pallets/relayer/src/lib.rs` is a single `StorageDoubleMap<Vec<u8> (address), StateMachine, u64>` shared by both `withdrawal.rs::withdraw()` (relayer fee withdrawal) and `accumulate.rs::accumulate()` (fee accumulation with an optional beneficiary redirect). Both functions read `Nonce::<T>::get(address, state_machine)`, verify a signature over a message that embeds that nonce, and then increment the same counter.

### Title
Shared relayer `Nonce` map lets a front-run on `accumulate_fees` invalidate a pending `withdraw_fees` signature - (File: `modules/pallets/relayer/src/lib.rs`, `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
The external report's core defect is: two independently-submittable, signature-gated calls consume the *same* nonce counter, so an unprivileged party who observes a pending signed call in the mempool can front-run it with an unrelated call that increments the shared nonce first, causing the original signed call to revert with a stale-nonce/invalid-signature error. The Hyperbridge `pallet-ismp-relayer` reproduces this exact pattern: `withdraw()` (`modules/pallets/relayer/src/withdrawal.rs:81-187`) and `accumulate()` (`modules/pallets/relayer/src/accumulate.rs:48-170`) both key off the single `Nonce<T>` double-map defined in `modules/pallets/relayer/src/lib.rs:124-135`, keyed only by `(address, state_machine)` with no discriminator for which call/purpose consumed it.

### Finding Description
`withdraw()` builds `msg = message(nonce, dest_chain, beneficiary)` from `Nonce::<T>::get(address, dest_chain)` [1](#0-0) , verifies the relayer's signature over it, then increments `Nonce::<T>` for `(address, dest_chain)` [2](#0-1) .

`accumulate()` independently builds `msg = beneficiary_message(nonce, state_machine, beneficiary_address)` from the very same `Nonce::<T>::get(&delivery_address, state_machine)` map [3](#0-2) , and on success increments the same `Nonce<T>` entry for `(delivery_address, state_machine)` [4](#0-3) .

Both `accumulate_fees` and `withdraw_fees` are dispatched with `ensure_none(origin)` — i.e. unsigned extrinsics whose calldata (including the relayer's off-chain signature over the nonce-bound message) is fully public once broadcast [5](#0-4) . A relayer signs a `withdraw_fees` payload for nonce N and broadcasts it. Because `accumulate` for the *same relayer address* is a completely independent, permissionless call that also reads/bumps `Nonce::<T>::get(address, chain)`, any third party who has (or can construct, e.g. from previously-claimed but not yet nonce-redirected receipts, or their own delivered requests attributed to that same relayer) a valid `WithdrawalProof` with `beneficiary_details` set can submit `accumulate_fees` first. That call passes its own signature check against the *current* nonce N (the relayer's `beneficiary_details` signature is unrelated and doesn't need to be the same signature — any past, valid beneficiary-redirect signature signed by that relayer for nonce N works, or the attacker can simply wait for/replay whichever accumulate call the relayer already produced with a beneficiary redirect), increments the shared `Nonce<T>` to N+1, and only then does the pending `withdraw_fees` (still signed for nonce N) land — it now recomputes `message(N+1, ...)`, the signature no longer matches, and `Error::<T>::InvalidSignature` is raised, aborting the withdrawal [1](#0-0) .

This is exactly the mETH `permit()`/`unstakeRequestWithPermit()` conflict: two logically-distinct, signature-authorized flows share one mutable nonce, so any publicly-observable, permissionlessly-submittable call that advances the nonce invalidates the other pending signed call.

### Impact Explanation
A relayer's legitimate `withdraw_fees` extrinsic can be made to revert by any unprivileged actor who front-runs it with an `accumulate_fees` call that happens to also increment the same nonce slot. Since `Fees::<T>` is only zeroed on a *successful* `withdraw`, funds are not lost outright, but the relayer's withdrawal is blocked/griefed indefinitely as long as an attacker keeps racing accumulate calls ahead of the withdraw for that `(address, state_machine)` pair. Because nonce and nonce-bump are shared across two otherwise-unrelated dispatchables, this also creates unpredictable ordering/state coupling between the fee-accumulation and fee-withdrawal flows that the pallet's own inline documentation ("mirroring how `withdraw_fees` binds its signed payload") assumes are independent, but the storage layer does not actually keep independent.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics (`ensure_none(origin)`), meaning their full calldata, including relayer signatures, is visible to all network observers before inclusion, exactly like the mempool-visibility precondition in the original report. No relayer, prover, or governance collusion is required — an ordinary node operator or bot that watches pending extrinsics can trigger this by submitting a same/near-same-block `accumulate_fees` call for the target relayer address before its `withdraw_fees` is included.

### Recommendation
Separate the nonce namespaces used by `withdraw()` and `accumulate()` — e.g. two distinct storage maps (`WithdrawNonce`, `BeneficiaryNonce`) instead of the shared `Nonce<T>` — so that advancing one flow's nonce cannot invalidate the other's in-flight signature. Alternatively, bind each signed message to a call-specific domain separator (e.g. include a discriminant byte for "withdraw" vs "accumulate-beneficiary" in the hashed payload) so cross-call nonce reuse cannot occur even if the counters remain shared.

### Proof of Concept
1. Relayer `R` has fees accrued for `(state_machine=SM, address=R)`; current `Nonce::<T>::get(R, SM) == N`.
2. `R` signs `message(N, SM, beneficiary)` off-chain and broadcasts `withdraw_fees(WithdrawalInputData{signature, dest_chain: SM, beneficiary})` [6](#0-5) .
3. An observer sees this pending unsigned extrinsic on the p2p layer (or already has a valid, previously-signed `beneficiary_details` payload from `R` for nonce N from an earlier `accumulate_fees` flow) and submits `accumulate_fees` with a `WithdrawalProof` for any of `R`'s deliverable commitments plus `beneficiary_details = (beneficiary, sig_over(N, SM, beneficiary))`.
4. If the observer's `accumulate_fees` call lands first, `Nonce::<T>` for `(R, SM)` is bumped to N+1 inside `accumulate()` [4](#0-3) .
5. `R`'s `withdraw_fees` (still bound to nonce N) then executes, recomputes `message(N+1, SM, beneficiary)` from the now-advanced nonce, and `signature.verify(&msg, ...)` fails, returning `Error::<T>::InvalidSignature` [7](#0-6)  — the relayer's withdrawal is blocked even though `R` had a valid signature and sufficient accrued fees.
