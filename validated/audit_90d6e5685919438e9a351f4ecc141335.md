### Title
Non-locking WOM conversions (`_mode=1`) use the flat top-tier multiplier gated by pre-existing `mWomSV` lock size instead of the actual deposited amount, allowing disproportionate MGP reward extraction - ([File: wombat/ArbWomUp3.sol])

### Summary
In `ArbWomUp3.getRewardAmount`, the `_lock == false` branch (used for `_mode=1` deposits) computes reward as `_amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR`, where `getUserTier` is derived from `mWomSV.getUserTotalLocked(_account)` [1](#0-0) [2](#0-1) . Unlike the `_lock == true` branch, which computes reward progressively across tiers based on the cumulative locked amount (tax-bracket style) and unlike the sibling contract `ArbWomUp2`, which gates tier on `userWOMDeposited[_account]` — an amount actually contributed through the program itself [3](#0-2) [4](#0-3)  — `ArbWomUp3`'s non-lock path applies a single flat top-tier rate to the entire converted amount, with the tier keyed off a completely separate state variable (`mWomSV` lock balance) that has no relation to the size of the current or historical deposits made through this incentive contract.

### Finding Description
A user with a large pre-existing `mWomSV` lock (obtained independently, e.g. via `_mode=2` deposits in this or another contract, or by directly locking into `mWomSV`) will have `getUserTier(_account)` return the highest tier index for which `userMWOMSVBal >= rewardTier[i]` [2](#0-1) . That tier index is then used to select `rewardMultiplier[tier]`, which is applied as a flat rate to the *entire* `_amountToConvert` passed into `incentiveDeposit` with `_mode=1` [5](#0-4) [6](#0-5) .

Because `rewardMultiplier` is monotonically increasing by tier (as configured via `setMultiplier`) [7](#0-6) , a whale with a large existing lock gets the top-tier per-WOM multiplier applied to any size of fresh WOM converted via `_mode=1`, while a first-time user converting the exact same amount is stuck with the lowest tier rate — since their `mWomSV` lock (unrelated to this transaction) is zero. This decouples the incentive-per-WOM from the "graduated tier accumulation" model intended by the progressive `_lock == true` path and by `ArbWomUp2`'s design, where the reward rate ramps up gradually and only in proportion to cumulative contribution to *this specific program*.

The `mgpReward` is capped by `IERC20(mgp).balanceOf(address(this))` [8](#0-7) , so this is not an unbounded mint, but it is a finite, admin-funded MGP incentive pool that gets drained disproportionately in favor of pre-existing whales who repeatedly (or in one large transaction) convert fresh WOM at the top rate, leaving less MGP reward available for other, smaller/newer participants performing the intended progressive lock-based accumulation.

### Impact Explanation
This results in unfair/disproportionate extraction of the shared, finite MGP reward pool (funded by the protocol for this incentive program) by users who exploit the tier/rate mismatch, effectively diverting yield/incentive intended to be distributed according to actual deposited/locked amounts. This matches the "theft of unclaimed yield" impact class — the reward pool is a fixed resource, and this bug allows one class of user to claim an outsized share of it relative to their actual contribution in a given transaction, at the expense of other legitimate participants who cannot claim it once drained.

### Likelihood Explanation
Exploitability requires the attacker to already hold (or cheaply acquire) a large `mWomSV` lock balance — attainable by any unprivileged actor through normal, permissionless staking/locking flows (including via `_mode=2` in this very contract, which locks mWom into `mWomSV` for the caller). No privileged role is required. Once obtained, the attacker can repeatedly call `incentiveDeposit(_amount, _convertRatio, false, 1)` with arbitrary `_amountToConvert` to claim the top-tier rate on each call, as long as the MGP pool has balance. This is fully repeatable and requires only capital (to acquire the lock) and gas.

### Recommendation
Make the non-locking reward calculation consistent with the locking branch and with `ArbWomUp2`: track cumulative WOM/mWom actually contributed by the account through this contract (e.g. a `userWOMDeposited`-style mapping) and use the progressive/graduated tier calculation for the `_lock == false` case as well, rather than applying a flat top-tier multiplier gated by an external, unrelated `mWomSV` balance to the entire deposit amount.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3` with mocked `mWom`, `mWomSV` (mock `ILocker.getUserTotalLocked`/`lockFor`), `smartWomConvert`, `vlMGP`, and `mgp` token; fund the contract with a large MGP balance.
2. Configure `rewardTier = [0, T1, T2]`, `rewardMultiplier = [m0, m1, m2]` with `m2 > m0`.
3. Whale setup: call `incentiveDeposit(largeAmount, 0, false, 2)` (or otherwise mock `mWomSV.getUserTotalLocked(whale)` to return a value `>= T2`) so `getUserTier(whale) == 2`.
4. Fresh user: ensure `mWomSV.getUserTotalLocked(freshUser) == 0`, so `getUserTier(freshUser) == 0`.
5. Both call `incentiveDeposit(1e18, 0, false, 1)` (mode=1, non-locking) with the same `_amount = 1 WOM`.
6. Assert `getRewardAmount(1e18, whale, false) == 1e18 * m2 / DENOMINATOR` while `getRewardAmount(1e18, freshUser, false) == 1e18 * m0 / DENOMINATOR`, with `m2 > m0`, confirming the whale receives strictly more MGP for an identical deposit purely due to unrelated pre-existing `mWomSV` lock size, and that this reward is not gated or reduced by any accumulation logic tied to deposits made through this contract.

    function getRewardAmount(uint256 _amount, address _account) external view returns (uint256) {
        if (_amount == 0 || rewardMultiplier.length == 0) return 0;
        uint256 accumulated = _amount + userWOMDeposited[_account];

        uint256 rewardAmount = 0;
        uint256 i = 1;
        while (i < rewardTier.length && accumulated > rewardTier[i]) {
            rewardAmount +=
                (rewardTier[i] - rewardTier[i - 1]) *
                rewardMultiplier[i - 1];
            i++;
        }
        rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];

        uint256 busdReward = (rewardAmount / DENOMINATOR) - this.calDoubledCounted(_account);
        uint256 busdleft = IERC20(busd).balanceOf(address(this));

        return busdReward > busdleft ? busdleft : busdReward;
    }
