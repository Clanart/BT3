### Title
Missing validation of registered DKG encryption keys allows identity/low-order ECDH keys, publicly exposing secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG registers each participant's encryption key (`enc_key`) from an `EncryptionKeyMessage` with no validation that it is a non-identity, full-order group element. Because the confidentiality of secret shares rests entirely on the ECDH shared point `enc_key * msg.key` fed into a deterministic transcript-derived ChaCha20 key, a participant who registers the identity (or a small-order) point causes every encrypted secret share addressed to them to be decryptable by anyone who observes the ciphertext — including third parties who are not participants at all. This is the Serai analog of "insufficient validation producing excessive data exposure of sensitive information."

### Finding Description
`EncryptionKeyMessage::read` parses the encryption public key with `C::read_G(reader)?` and no further checks [1](#0-0) . `Decryption::register` stores it verbatim, the only check being a duplicate-registration assert [2](#0-1) . When a sender encrypts a share, `encrypt` computes `ecdh(key, to)` = `enc_key_recipient * k` and derives the ChaCha20 key solely from `context || ecdh.to_bytes()` [3](#0-2) . If `enc_key_recipient` is the identity (encodable for Ristretto/Ed25519 via `read_G`), the ECDH result is `k * identity = identity` for every message, so the cipher key reduces to a deterministic, publicly-known function of `context` and the identity encoding. Note the DKG spec explicitly assumes only an *authenticated* channel, not a confidential one [4](#0-3) , so any observer of the transcript can recompute the keystream and read the secret shares sent to that participant.

### Impact Explanation
All `n` secret shares addressed to the offending participant become world-readable, revealing that participant's aggregate secret share (and all per-dealer contributions) to any party who sees the `EncryptedMessage` bytes [5](#0-4) . This reduces the threshold security assumption: an external observer — not just a protocol participant — obtains key material they were never authorized to see, weakening the group key's confidentiality to `t-1` additional compromises.

### Likelihood Explanation
A DKG participant (or anyone able to inject an `EncryptionKeyMessage`/`Commitments` byte blob into round 1) only needs to supply identity-encoded bytes as `enc_key`; `EncryptedMessage`s to them are still produced normally and their PoP checks pass for honest senders, so the malformed registration is silently accepted. Requires no collusion or special privileges beyond submitting round-1 message bytes.

### Recommendation
In `Decryption::register` (or in `EncryptionKeyMessage`/`Commitments` verification in `verify_r1`), reject `enc_key` values that are the identity or otherwise not in the prime-order subgroup — e.g., check `!bool::from(enc_key.is_identity())` (and subgroup membership where applicable) before inserting into `enc_keys` [2](#0-1) .

### Proof of Concept
1. In round 1, attacker `i` constructs `EncryptionKeyMessage { msg: valid Commitments, enc_key: <identity encoding> }` (`C::G::identity().to_bytes()`).
2. `verify_r1`/`register` accept it; honest participants encrypt their shares to `i` via `encrypt(..., self.decryption.enc_keys[&i], share_bytes)` [6](#0-5) .
3. Any observer reconstructs the keystream: `cipher(context, identity)` → `RecommendedTranscript(b"DKG Encryption v0.2")` + `context` + `identity.to_bytes()` → `challenge(b"key")` + IV `b"DKG IV v0.2\0"`, then XORs it against `msg.msg` to recover each `SecretShare` plaintext sent to `i`.

```rust
fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
```

```markdown
### Encryption

In order to protect the secret shares during communication, the `dkg` library
establishes a public key for encryption at the start of a given protocol.
Every encrypted message (such as the secret shares) then includes a per-message
encryption key. These two keys are used in an Elliptic-curve Diffie-Hellman
handshake to derive a shared key. This shared key is then hashed to obtain a key
and IV for use in a ChaCha20 stream cipher instance, which is xor'd against a
message to encrypt it.
```

```rust
  pub fn generate_secret_shares<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    commitments: HashMap<Participant, EncryptionKeyMessage<C, Commitments<C>>>,
  ) -> Result<
    (KeyMachine<C>, HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>),
    PedPoPError<C>,
  > {
    let commitments = self.verify_r1(&mut *rng, commitments)?;

    // Step 1: Generate secret shares for all other parties
    let mut res = HashMap::new();
    for l in self.params.all_participant_indexes() {
      // Don't insert our own shares to the byte buffer which is meant to be sent around
      // An app developer could accidentally send it. Best to keep this black boxed
      if l == self.params.i() {
        continue;
      }

      let mut share = polynomial(&self.coefficients, l);
      let share_bytes = Zeroizing::new(SecretShare::<C::F>(share.to_repr()));
      share.zeroize();
      res.insert(l, self.encryption.encrypt(rng, l, share_bytes));
    }

    // Calculate our own share
    let share = polynomial(&self.coefficients, self.params.i());
    self.coefficients.zeroize();

    Ok((
      KeyMachine { params: self.params, secret: share, commitments, encryption: self.encryption },
      res,
    ))
  }
```
