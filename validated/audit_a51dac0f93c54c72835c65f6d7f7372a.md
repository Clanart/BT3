## Confirmed vulnerability

The `_orders[commitment][token]` mapping in `_withdraw` (in `evm/src/apps/intentsv2/IntentsBase.sol:390-425`) is a **per-token** escrow bucket, decremented by `amount` on every withdrawal call, with `revert UnknownOrder()` if the bucket is already zero. [1](#0-0) 

In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`), the escrow amount computed for release on a per-`i` (per output-asset) basis reads:

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [2](#0-1) 

When output pair `i` reaches its own individual full-fill (`amountFilled == totalRequired` for that pair), the code releases **the entire current balance of `_orders[commitment][token]`**, not just the proportional share owed for pair `i`. This was deliberately written this way to fix rounding-dust locking for the *single-pair* case (tested in `testPartialFill_RoundingDustReleasedToFinalSolver`). [3](#0-2) 

The invariant this breaks: `_orders[commitment][token]` is **shared across every output index `i` that references the same input token**. If a user places a same-chain order with two (or more) output pairs whose `order.inputs[i].token` are equal (e.g., both backed by the same USDC escrow), a solver who fully fills only the first, smaller output pair drains the *entire* remaining USDC escrow bucket for that token — including the amount that was meant to back the still-open second output pair. The second output pair's solver either finds `_orders[commitment][token] == 0` and reverts with `UnknownOrder()`, permanently locking that leg, or — if a partial payout already occurred for it — receives less than they're entitled to while the first solver walked away with funds that weren't proportionally theirs.

This is a direct structural analog to the report's core broken invariant: a **stale/aggregate checkpoint value is read and paid out wholesale at a point where only a partial claim is legitimate, because the code conflates "my share is fully filled" with "the whole shared balance is now free to disburse."** In the original report, `Bribe.sol` read a stale `balanceOf` checkpoint across an epoch boundary and let the reset-then-claim sequence extract more than the actor was entitled to. Here, the full-fill branch reads a *cross-index shared* balance (`_orders[commitment][token]`) instead of the *per-index proportional* balance, letting one solver's completion event silently consume funds escrowed against a sibling, unfilled leg of the same order.

### Impact
- **Unauthorized fund extraction / wrong amount to wrong recipient**: a solver receives escrow tokens that were reserved for a different (unfilled) output leg of the same order, at no extra cost.
- **Fund lock**: the order's other leg can end up permanently unfillable (`UnknownOrder()` revert) since its backing escrow was already swept away, leaving the user unable to receive their remaining output and the residual input tokens stuck/misallocated.
- No malicious relayer, prover, or governance actor is needed — a single unprivileged solver crafting/selecting an order whose `inputs[]` reuses a token address across multiple `output.assets[]` entries triggers this deterministically by calling public `fillOrder`.

### Likelihood
Requires an order where `order.inputs[i].token == order.inputs[j].token` for `i != j` (or more generally, wherever two output legs are priced against the same input escrow token) — a normal, unrestricted input to `placeOrder`/`fillOrder`; nothing in `IntentGatewayV2.sol` or `IntrinsicIntents.sol` validates that input tokens are distinct across indices. This is fully reachable by any user creating an order and any solver calling `fillOrder`.

### Recommendation
Track per-`(commitment, outputIndex)` escrow remaining (or compute the proportional share strictly from `order.inputs[i].amount` scaled by `fillAmount/totalRequired` even on the pair's own full-fill), rather than reading/zeroing the aggregate `_orders[commitment][token]` bucket, which can be shared across multiple output legs. The "release remaining dust to final solver" behavior should only trigger when *the whole order* (`isFullyFilled` across all `i`) completes, not when a single output leg completes, or should be scoped per-input-index rather than per-token.

### Note on verification depth
I was not able to fully trace whether `placeOrder`/order validation elsewhere in `IntentGatewayV2.sol` rejects duplicate input tokens across `inputs[]` before this code path is reached — the index size limits on the tool prevented me from pulling the complete `placeOrder` body. If such a check exists and rejects duplicate input token addresses across indices, this finding would not be exploitable as described and should be treated as unconfirmed until that function is read in full via a Devin session with complete file access.
