### Title
Scanner accepts arbitrarily small attacker-sent outputs, letting anyone fragment Serai's UTXO set into economically unspendable dust - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to `claimMultiple` letting a third party force a large contributor's balance into many tiny NFTs, `Scanner::scan_transaction` credits any output paying to a registered script — with no minimum-value filter — as a spendable `ReceivedOutput`. An unprivileged attacker can send dust-valued transactions to the Serai vault/deposit addresses, fragmenting the wallet's balance into many outputs whose individual value is below (or barely above) the cost of spending them. Each such output then forces one full FROST signature machine per input in `SignableTransaction::multisig`/`TransactionSignMachine::sign`, inflating both the per-input signature count and the transaction fee, and producing funds that are reported received yet are not economically spendable.

### Finding Description
`scan_transaction` matches outputs purely on `script_pubkey` and pushes every match into the result, regardless of `output.value` (networks/bitcoin/src/wallet/mod.rs:199-213). `register_offset` documents that the offsets/scripts are derivable by design (they are P2TR scripts under the group key), so any Bitcoin user can pay to them (lines 180-196).

On the spend side, `SignableTransaction::new` rejects dust *payments* (`*amount < DUST`, send.rs:165-169) but performs no equivalent check on dust *inputs* — the only input checks are `NoInputs`, `NotEnoughFunds`, and `TooLargeTransaction` (send.rs:157-243). Every input then gets its own `AlgorithmMachine` (send.rs:275-284) and its own Schnorr signature share and witness (send.rs:377-397, 417-425), and each input adds a fixed ~58-vbyte weight to `calculate_weight_vbytes` (send.rs:68-83).

So an attacker can split a payment into N outputs of value near `DUST` (546 sats). Each output is individually near-worthless once its ~58-vbyte input cost is paid at a non-trivial `fee_per_vbyte`, yet the scanner reports all N as received funds, and any spend must sign for all included inputs. This is the same shape as the PartyDAO finding: a third party unilaterally decides the fragmentation of someone else's balance, converting one economical unit into many uneconomical ones.

### Impact Explanation
- Wallet/scanner infrastructure credits deposits that can never be profitably spent ("funds reported received that are not spendable"). At moderate fee rates, a 546–1000 sat input costs more in added fee than it contributes.
- Each forced input multiplies FROST signing work: one `AlgorithmMachine`, one preprocess, one share, one completion per input — a parallel-session cost blowup driven entirely by attacker-chosen on-chain fragmentation.
- Sufficiently fragmented inputs can push weight over `MAX_STANDARD_TX_WEIGHT` (`TooLargeTransaction`, send.rs:241-243), forcing additional consolidation transactions that themselves require threshold signatures.

### Likelihood Explanation
The attack requires only sending ordinary Bitcoin transactions to publicly derivable P2TR scripts (the vault group-key script and any registered offset script). No validator access, no collusion, and no malformed input is needed — the griefing input is a standard, consensus-valid payment, exactly as reachable as calling `claimMultiple` on someone else's behalf in the original report.

### Recommendation
Apply a minimum-value floor in `Scanner::scan_transaction` (e.g., ignore outputs below `DUST` or below a configurable economic-spendability threshold that accounts for the ~58-vbyte input weight at a reference fee rate), or have `SignableTransaction::new` drop/reject inputs whose value is less than their marginal fee contribution, so attacker-fragmented dust is never treated as received/spendable balance.

### Proof of Concept
1. Obtain the Serai vault's P2TR `script_pubkey` (from `Scanner::new(group_key)` / any registered offset via `register_offset`, mod.rs:162-196) — all public.
2. Broadcast a transaction paying K outputs of ~546 sats each to that script.
3. `scan_transaction` (mod.rs:199-213) returns K `ReceivedOutput`s; the wallet reports K×546 sats received.
4. Any `SignableTransaction::new` including these inputs pays `fee_per_vbyte * ~58` per input (send.rs:204-206) and spawns K FROST `AlgorithmMachine`s (send.rs:275-282). For fee rates above ~9 sat/vB, each input costs more to spend than its 546-sat value, so the reported balance is unspendable — funds credited but economically locked, decided entirely by the attacker.
