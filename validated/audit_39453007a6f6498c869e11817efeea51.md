### Title
Stale rebase/cherry-pick conflict state written into `IRepositoryState` after unguarded async gap - ([File: app/src/lib/stores/app-store.ts])

### Summary
`AppStore._loadStatus()` calls `initializeMultiCommitOperationIfConflictsFound()`, which performs several `await`s (`getRebaseSnapshot`, `getRebaseInternalState`, `getCommit`, `getCherryPickSnapshot`) and then unconditionally writes the results into `repositoryStateCache` via `this._initializeMultiCommitOperation(...)`, with no re-validation that the repository's conflict/tip state is still the same one that existed when the async calls were kicked off.

### Finding Description
The method reads `multiCommitOperationState`/`conflictState`/`branchesState.tip` once at entry [1](#0-0) , then performs multiple `await` points to fetch rebase/cherry-pick snapshots and commit lookups from disk [2](#0-1) , and finally commits the result unconditionally: [3](#0-2) 

Unlike every other async state-application site in the same file — `_changeFileSelection`, `updateChangesWorkingDirectoryDiff`, `updateChangesStashDiff` — which explicitly snapshot state before the await and compare it against the state after the await, bailing out if anything changed [4](#0-3) [5](#0-4) , `initializeMultiCommitOperationIfConflictsFound` has no such "before/after" comparison. This is the same class of bug as the Aptos `HotState` issue: a background/async completion mutates shared state based on a snapshot taken before the async gap, without confirming the shared context (there, the fork branch; here, the current conflict/tip state) is still consistent at write time.

During the window opened by these awaits, `_loadStatus` can be re-entered concurrently (it's invoked from multiple flows — `_refreshRepository`, background fetch, `_pull`/`_push`, and repeatedly via periodic refresh) and the user can abort a conflicted operation, switch to a different repository/branch, or resolve conflicts through the dispatcher's own `initializeMultiCommitOperation`/`_endMultiCommitOperation` paths. If any of that happens while `getRebaseSnapshot`/`getCommit`/`getCherryPickSnapshot` are still pending, the code still calls `this._initializeMultiCommitOperation(...)` with the stale `operationDetail`/`targetBranch`/`originalBranchTip`, clobbering whatever multi-commit-operation state exists at that point.

### Impact Explanation
`originalBranchTip` and `targetBranch` computed from stale data are used later to determine when a conflicted rebase/cherry-pick/merge is considered "finished" and what the "before" state was for undo/abort operations. Writing a stale `multiCommitOperationState` can cause GitHub Desktop to believe it is still resolving conflicts against the wrong original tip/target branch, or re-initialize an operation the user already finished/aborted. This can lead to the wrong resolution/commit being finalized for what the user believes is a clean commit or push (silent corruption of what gets committed), matching the "silent corruption of what the user commits or pushes" impact category. It does not require local/physical access or credentials — it only requires a normal repository-refresh race that any user hits by simply having multiple refresh triggers fire while in a conflicted state (e.g., background fetch during an in-progress rebase).

### Likelihood Explanation
Moderate to hard to trigger deterministically: it requires overlapping `_loadStatus` calls (or a user-driven conflict-flow transition) landing precisely inside the multi-await window of `initializeMultiCommitOperationIfConflictsFound`. `_loadStatus` is invoked frequently (from `_refreshRepository`, fetch/pull/push flows, and periodically), and conflicted states routinely persist across multiple refresh cycles, so the window is real but timing-dependent, which is why every sibling method in the file added the explicit stale-check guard that this one lacks.

### Recommendation
Snapshot `multiCommitOperationState`/`conflictState`/`branchesState.tip` before the `await`s in `initializeMultiCommitOperationIfConflictsFound`, and re-read `repositoryStateCache.get(repository)` after each await, bailing out (mirroring the pattern used in `updateChangesStashDiff` / `updateChangesWorkingDirectoryDiff` / `_changeFileSelection`) if `conflictState`, `multiCommitOperationState`, or `branchesState.tip` no longer match what was observed at the start of the function, before calling `_initializeMultiCommitOperation`.

### Proof of Concept
1. Put a repository into a conflicted rebase state (e.g., start a rebase that hits conflicts).
2. Trigger two overlapping calls to `_loadStatus` for the same repository in quick succession — e.g. have a background fetch fire (`performFetch` → `_refreshRepository` → `_loadStatus`) at the same time the user manually aborts the rebase via the dispatcher (`_endMultiCommitOperation`, clearing `multiCommitOperationState`).
3. While the first `_loadStatus` call is awaiting `getRebaseSnapshot`/`getRebaseInternalState`/`getCommit` inside `initializeMultiCommitOperationIfConflictsFound` [2](#0-1) , let the abort complete and clear the operation state.
4. When the first call's awaits resolve, it calls `this._initializeMultiCommitOperation(...)` unconditionally [3](#0-2) , re-creating a `multiCommitOperationState` for an operation the user just aborted, using the stale `originalBranchTip`/`targetBranch` captured before the abort.

I was unable to fully trace every downstream consumer of `originalBranchTip`/`operationDetail` to construct a fully deterministic exploit chain from within the static index (some call sites live in `dispatcher.ts` and rely on runtime timing), so this should be validated with a live repro in a full checkout before treating it as confirmed-exploitable rather than a design-level race.
