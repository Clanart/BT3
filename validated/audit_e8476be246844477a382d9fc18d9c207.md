### Title
Permissionless ERC20 pointer "upsert" re-derives metadata (decimals/name/symbol) from mutable state, letting a denom/CW20 admin front-run or retroactively rewrite an already-deployed pointer's decimals - ([File: x/evm/keeper/pointer_upgrade.go])

### Summary
The CW→ERC pointer precompile (`addNativePointer` / `addCW20Pointer`) lets *any* caller request creation of an ERC20 pointer for a token by supplying only the token reference (denom or CW20 address) - it never lets the caller pin down the `decimals`/`name`/`symbol` it expects. Those values are instead fetched live from mutable state (bank `DenomMetadata` for native tokens, or the CW20 contract's `token_info` query) at the moment the precompile executes, exactly mirroring the reported Mech Marketplace bug where `deliveryRate`/`paymentType` were pulled from the mutable state of a party the requester doesn't control instead of being pinned by the requester.

### Finding Description
`AddNative` in the pointer precompile takes only a `token` string and reads its decimals from whatever `DenomMetadata` currently exists in the bank keeper: [1](#0-0) 

The same pattern is used for CW20 pointers, where `name`/`symbol` are queried live from the CW20 contract's `token_info`: [2](#0-1) 

Both funnel into `UpsertERCPointer`, which is even more permissive than the metadata read itself: it is **idempotent/permissionless** and, crucially, if a pointer already exists for the token, it does not redeploy a new contract - it regenerates the pointer's bytecode from *whatever metadata is current at call time* and overwrites the code living at the **same, already-integrated** contract address via `SetCode`: [3](#0-2) 

Nothing in this path lets the caller assert "I expect this token's decimals to be X / name to be Y"; the values are simply re-derived from the denom's/CW20 contract's current mutable state, exactly the pattern the report flags: the requester supplies a reference to something (a service/mech ID in the report; a denom/CW20 address here) and the code fetches critical, security-relevant parameters (delivery rate/payment type in the report; decimals/name/symbol here) from the referenced entity's *current* state rather than from a value the requester pinned in their own request.

The denom's metadata is controlled by the tokenfactory admin via `MsgSetDenomMetadata`/`MsgUpdateDenom` (or the CW20 contract owner for CW20 tokens), which is a completely independent, unprivileged actor relative to whoever calls `addNativePointer`: [4](#0-3) [5](#0-4) 

### Impact Explanation
Because pointer creation/upsert is permissionless and always re-reads live metadata, a token admin can:
1. Front-run someone else's `addNativePointer(token)`/`addCW20Pointer(cwAddr)` transaction by changing the denom's `DenomMetadata` (or the CW20 contract's declared name/symbol via a migration) immediately before the requester's tx lands, causing the pointer that gets permanently deployed to carry decimals/name/symbol different from what the requester (and any downstream integrator relying on the pointer, e.g. a DEX or bridge UI) expected.
2. Worse, at any later point, **anyone** can call `addNativePointer`/`addCW20Pointer` again for a token whose metadata has since changed. Because the upsert path (`UpsertERCPointer`) reuses the same contract address and simply overwrites the pointer's bytecode with `SetCode` using the metadata current at that moment, an already-live, integrated ERC20 pointer contract's `decimals()` can be silently rewritten after the fact - without moving or migrating any balances. Any protocol (AMM, lending market, price oracle) that priced or accounted for the token using the pointer's original decimals will then compute wrong exchange rates/collateral values against the new decimals, which is a direct value-extraction/fund-loss vector (e.g., depositing at decimals=6 pricing then withdrawing after a retroactive decimals bump to a higher exponent, or vice versa).

This matches the report's "Medium/High" impact class of "the requester's/integrator's assumed parameters are silently swapped out by the party controlling the referenced entity," reachable purely from an unprivileged EVM transaction (calling the pointer precompile) combined with an ordinary tokenfactory/CW20 admin action - no validator, node, or p2p compromise required.

### Likelihood Explanation
Likelihood is high: `addNativePointer`/`addCW20Pointer` and `MsgUpdateDenom`/`MsgSetDenomMetadata`/CW20 migration are all ordinary, unprivileged (or self-privileged, from the token admin's perspective) transactions available on every deployment. No governance, validator collusion, or off-chain access is needed - only normal transaction ordering/mempool visibility (front-running) or simply waiting and calling the upsert again later.

### Recommendation
- Require the caller of `addNativePointer`/`addCW20Pointer` to supply the expected `decimals`/`name`/`symbol` (or at least `decimals`) as request parameters, and validate them against the live queried metadata before creating/upserting the pointer, failing the call on mismatch - mirroring the report's recommendation that the requester provide the parameters to be matched against the referenced entity's state rather than blindly trusting values fetched at execution time.
- Alternatively/additionally, make pointer upserts immutable once created (disallow decimals/name/symbol changes on re-registration), or gate re-registration behind a permissioned/governance path as is already partially done via `RegisterPointerDisabled`/version checks in `x/evm/keeper/msg_server.go`'s `RegisterPointer`.

### Proof of Concept
1. Token admin creates tokenfactory denom `factory/admin/foo` with `DenomMetadata` exponent (decimals) = 6, and announces this to integrators.
2. A third party (integrator) submits `addNativePointer("factory/admin/foo")` expecting a decimals=6 ERC20 pointer, based on the currently-published metadata.
3. Admin front-runs by calling `MsgUpdateDenom`/setting new `DenomMetadata` with exponent = 18 just before the integrator's tx is included.
4. The integrator's `addNativePointer` call executes after the admin's metadata change; `AddNative` (precompiles/pointer/pointer.go:106-124) reads the *new* metadata and deploys a pointer with decimals = 18, not the 6 the integrator expected.
5. Later, even without any front-running, the admin changes metadata again and any unrelated account calls `addNativePointer` a second time; `UpsertERCPointer` (x/evm/keeper/pointer_upgrade.go:115-141) detects the pointer already exists and overwrites its code via `SetCode` at the same address, silently changing `decimals()` for every existing integration built on that pointer address. func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
```go
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
```

```go
func (k *Keeper) UpsertERCPointer(
	ctx sdk.Context, evm *vm.EVM, typ string, args []interface{}, getter PointerGetter, setter PointerSetter,
) (contractAddr common.Address, err error) {
	pointee := args[0].(string)
	evmModuleAddress := k.GetEVMAddressOrDefault(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName))

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv
	// forbids writing a frozen layer, and same-tx readers that skip frozen-empty
	// parents would miss those writes. The precompile Prepare `ctx` is that top at
	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)
	var remainingGas uint64
	if exists {
		var ret []byte
		contractAddr = existingAddr
		ret, remainingGas, err = evm.GetDeploymentCode(evmModuleAddress, bin, suppliedGas, utils.Big0, existingAddr)
		if err != nil {
			return
		}
		// Only write on success: a failed GetDeploymentCode can leave ret as nil or
		// revert data, which must not clobber live pointer bytecode (even transiently).
		writeCtx := liveCtx()
		k.SetCode(writeCtx, contractAddr, ret)
		if sdb != nil {
			sdb.RefreshCodeCache(contractAddr, ret)
		}
	} else {
		_, contractAddr, remainingGas, err = evm.Create(evmModuleAddress, bin, suppliedGas, uint256.NewInt(0))
	}
	if err != nil {
		return
	}
	ctx.GasMeter().ConsumeGas(k.GetCosmosGasLimitFromEVMGas(ctx, suppliedGas-remainingGas), "ERC pointer deployment")
	if err = setter(liveCtx(), pointee, contractAddr); err != nil {
		return
	}
```
