### Title
Malleable/unsigned OP_RETURN attribution field in `create_payout_txhandler` allows attacker to corrupt `payout_payer_operator_xonly_pk`, permanently locking the honest operator out of reimbursement - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction with only a single witness — `user_sig` applied via `set_p2tr_key_spend_witness` at input 0 — and no signature from the operator at all over the OP_RETURN output that carries `operator_xonly_pk`. `update_finalized_payouts` later trusts whatever OP_RETURN bytes end up in the *confirmed* payout transaction, unconditionally, to attribute the payout to an operator identity. If the sighash used for `user_sig` is `SIGHASH_SINGLE|ANYONECANPAY` (as is explicitly required for the sibling `optimistic_payout` flow, per the error message at `core/src/rpc/aggregator.rs:1126`), the signature covers only input 0 and output 0, leaving outputs 1 (anchor) and 2 (OP_RETURN) completely unauthenticated and freely rewritable by anyone who observes the unconfirmed transaction.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk` stored by `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) should equal the xonly_pk of the operator whose funds actually paid the withdrawer output.

Code path:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds: input 0 = withdrawal UTXO (KeySpend, signed only by `user_sig`), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN with `operator_xonly_pk.serialize()` (line 418). Only `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)` is applied (line 434) — no operator signature covers this transaction at all.
- `update_finalized_payouts` (`core/src/verifier.rs:2312-2342`) reads the *confirmed on-chain* transaction, extracts the first OP_RETURN output, parses it as an xonly_pk with no further validation, and persists it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).
- `validate_payer_is_operator` (`core/src/operator.rs:1687-1729`) later compares the persisted `payer_xonly_pk` against `self.signer.xonly_public_key`; on mismatch it returns a permanent error, which is unrecoverable since the row is fixed once written.

Root cause: the OP_RETURN attribution field is not covered by any signature check that binds it to the actual funder of the payout. If `SIGHASH_SINGLE|ANYONECANPAY` is used for `user_sig` (confirmed pattern in the parallel `optimistic_payout` flow), an observer of the unconfirmed transaction in the mempool can rebuild a transaction that keeps input 0 and output 0 exactly as signed, but replaces output 2's OP_RETURN bytes and adds fee-bumping inputs/outputs of their own (all permitted since ANYONECANPAY explicitly allows arbitrary additional inputs/outputs, and SIGHASH_SINGLE only commits the output at the signer's input index). Broadcasting this with higher fee lets it confirm instead of the original.

Existing guards that do NOT catch this: `Verifier::is_deposit_valid`, `SECP.verify_schnorr` (only checks `user_sig` against the committed sighash, which under `SINGLE|ANYONECANPAY` does not cover the OP_RETURN), and `is_kickoff_malicious` (which reads the same corrupted DB value it would need to detect corruption against, so it just enforces internal consistency between the (already-poisoned) DB and kickoff data — it does not detect the substitution itself).

### Impact Explanation
- Critical, matching the listed category "an honest operator permanently unable to be reimbursed": once the malleated transaction confirms, `validate_payer_is_operator` will forever reject the honest operator (`payer_xonly_pk != self.signer.xonly_public_key`), blocking `get_reimbursement_txs` (`core/src/operator.rs:2098-2149`) and the `PayoutCheckerTask` path unconditionally, with no recovery path since the DB row and on-chain confirmation are immutable facts.
- The stronger variant claimed in the question — crediting the attacker's *own* registered operator identity and having that operator get reimbursed — additionally requires the attacker to actually hold a pre-registered operator identity with collateral and a presigned round/kickoff transaction graph for that specific deposit. That contradicts the stated unprivileged attacker model ("not ... an operator ... hold no key share, collateral"), so the fund-theft variant is out of scope for a strictly unprivileged attacker; only the "permanent lockout" variant is achievable by them (using an arbitrary/unregistered pubkey, or `None`/malformed data, in the OP_RETURN).
- Repeatable per withdrawal that the attacker can observe pre-confirmation; blast radius is any honest operator whose payout tx is still in the mempool when the attacker acts.

### Likelihood Explanation
Requires: (1) confirmation that the sighash type actually used for the non-optimistic `create_payout_txhandler`'s `user_sig` is `SIGHASH_SINGLE|ANYONECANPAY` — this was directly confirmed only for the sibling `optimistic_payout` RPC (`core/src/rpc/aggregator.rs:1126`); I could not locate and verify the exact validation code path for the standard (non-optimistic) payout signature within this session, so this is an unverified assumption carried over from the parallel flow. (2) The mempool-visible unconfirmed transaction with the extractable witness. (3) Feasibility of getting a conflicting/replacement transaction to confirm instead (depends on `DEFAULT_SEQUENCE`/RBF signaling, which I was not able to confirm in this session, and general miner/relay policy). Attacker cost is limited to the fee bump needed to win the replacement race.

### Recommendation
Cannot be finalized with full confidence: this needs codebase confirmation of (a) the exact sighash type enforced for the standard `create_payout_txhandler` flow (not just `optimistic_payout`), and (b) the `DEFAULT_SEQUENCE`/RBF policy on this transaction, both of which I could not verify within the available tool budget. If confirmed, the fix would be to bind the OP_RETURN (and ideally all outputs) into the committed sighash — e.g., require `SIGHASH_ALL` or otherwise cryptographically commit the operator identity so it cannot be altered without invalidating `user_sig`, or have verifiers independently attest to/re-derive the operator identity rather than trusting the OP_RETURN bytes verbatim in `update_finalized_payouts`.

### Proof of Concept
Not executed — requires live confirmation of the sighash type used in the standard payout flow and of RBF/replacement feasibility for this transaction shape, which could not be established from the available code snippets in this session. A `cargo test` proof would need to: construct an honest operator's `create_payout_txhandler` output, verify the exact `sighash_type` bound into `user_sig`, build a substitute transaction reusing the witness with an altered OP_RETURN, confirm it via regtest bitcoind, and assert `get_payout_info_from_move_txid`/`update_finalized_payouts` records the substituted pubkey while `validate_payer_is_operator` permanently rejects the honest operator's key — but this cannot be certified complete without the missing verification step noted above.
