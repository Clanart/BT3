### Title
Scanner credits arbitrarily small (dust/uneconomic) deposits that cost more to spend than their value, letting an unprivileged sender force value loss on the group - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The PartyDAO bug class is "an unprivileged actor can permissionlessly trigger a spend of the group's funds, forcing value leakage up to a maximum." In `bitcoin-serai`, the permissionless entry point is `Scanner::scan_transaction`/`scan_block`: anyone can send a Bitcoin transaction paying to a registered script, and the scanner will report it as a spendable `ReceivedOutput` with no minimum-value filter. `SignableTransaction::new` then charges a fixed per-input weight (~57.5 vB witness + ~41 vB input) against every included input, so dust outputs whose value is below their spend cost are reported as funds received while being net-negative to spend.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output` and pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, without checking `output.value` at all [1](#0-0) . `scan_block` does the same for every transaction in a block, including coinbase [2](#0-1) .

On the spend side, `SignableTransaction::new` computes weight/vbytes purely from the number of inputs and payment shape [3](#0-2) , enforces a dust floor only on *payments* (`*amount < DUST` → `DustPayment`) [4](#0-3) , and checks solvency via `input_sat < payment_sat + needed_fee` [5](#0-4) . Nothing verifies that each contributed input's value exceeds the marginal fee it adds. Each Taproot input adds roughly 99+ bytes of base data (outpoint, sequence, etc.) plus a 64-byte witness (≈16 vB), i.e. ~57–58 vB marginal — at a modest 10 sat/vB that is ~570 sats, already above the `DUST = 546` threshold [6](#0-5) ; at higher fee rates the uneconomic range is much wider.

So an attacker can send transactions paying, say, 546–5,000 sats to the group's P2TR script. These are indistinguishable from legitimate deposits at the scanner layer and are surfaced as received/spendable funds, yet spending them destroys value instead of releasing it — the exact "forced to overpay for the item" shape of the PartyDAO finding, realized as "forced to overpay to redeem a deposit."

### Impact Explanation
- **Value leakage / griefing**: every uneconomic output the group is compelled (or induced by accounting) to spend burns `marginal_input_fee − output_value` in extra fees. If the integrator aggregates all scanned outputs into `SignableTransaction::new`, the attacker directly forces the group to overpay fees; `NotEnoughFunds` only fires when the total is insolvent, not when individual inputs are net-negative.
- **Inflated reported balances / UTXO bloat**: `scan_transaction`/`scan_block` report these outputs identically to real deposits (`ReceivedOutput::value` returns the raw amount [7](#0-6) ), so attackers can cheaply inflate the wallet's UTXO set and reported receivables with funds that are not economically spendable — matching the accepted impact class "funds reported received that are not spendable."
- Cost to the attacker is only the dust value itself (~546 sats minimum to be relay-standard), symmetric to the PartyDAO attacker risking only their own bid.

### Likelihood Explanation
Sending a transaction to a registered P2TR script requires no privilege, no cooperation, and no validator misbehavior — it is the most basic public input to this crate. Every bridge/aggregator integrating `Scanner` will observe these outputs, and any accounting that sums `ReceivedOutput`s will count them. The only mitigating factor is that an integrator could add a post-scan minimum-value filter, but nothing in the in-scope API (`Scanner`, `ReceivedOutput`, `SignableTransaction`) does this or warns about it for inputs (the only dust check is on outgoing payments). Medium severity: bounded per-output loss and partially dependent on integrator aggregation policy, but reachable by any unprivileged party and undocumented.

### Recommendation
- Add a minimum-value/economic-spendability check, either in `Scanner::scan_transaction` (reject or flag outputs below a configurable threshold) or in `SignableTransaction::new` (reject any input whose `output.value` is below `fee_per_vbyte * marginal_input_vbytes`, or at minimum emit a warning/error variant such as `UneconomicInput`).
- Document on `Scanner::scan`/`scan_block` that all matching outputs are reported regardless of value and that callers must filter dust before funding transactions.
- Optionally track, per `ReceivedOutput`, whether it is economically spendable at a given fee rate.

### Proof of Concept
1. Group registers/tweaks a key; `Scanner::new`/`register_offset` maps its P2TR `script_pubkey` in `self.scripts` [8](#0-7) .
2. Attacker broadcasts a transaction with N outputs of `V` sats each paying to that exact `script_pubkey`, where `V` is small (e.g. 1,000 sats) — no relationship to the group needed.
3. `scan_block`/`scan_transaction` returns N `ReceivedOutput`s with `offset` set; balance/accounting reports `N * V` received [9](#0-8) .
4. Group constructs `SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)` including those outputs. At `fee_per_vbyte = 20`, each of those inputs adds ~57.5 vB ≈ 1,150 sats of fee but contributes only 1,000 sats — net −150 sats each. `NotEnoughFunds` never triggers since totals remain solvent; the extra cost is silently absorbed either into `needed_fee` or into reduced change [10](#0-9) .
5. Repeat at scale: with thousands of small outputs, the attacker either forces the group to burn fees to consolidate its own reported funds, or permanently strands "received" balance that can never be spent profitably — the direct analog of forcing the crowdfund to bid up to `maxBid`.

  /// Register an offset to scan for.
  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script
  /// path into the output, allowing the output to be spent by satisfaction of an arbitrary script
  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();

    // Now calculate the size in vbytes

    /*
      "Virtual transaction size" is weight ceildiv 4 per
      https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki

      https://github.com/bitcoin/bitcoin/blob/306ccd4927a2efe325c8d84be1bdb79edeb29b04
        /src/policy/policy.cpp#L295-L298
      implements this almost as expected, with an additional consideration to signature operations

      Signature operations (the second argument of the following call) do not count Taproot
      signatures per https://github.com/bitcoin/bips/blob/master/bip-0342.mediawiki#cite_ref-11-0

      We don't risk running afoul of the Taproot signature limit as it allows at least one per
      input, which is all we use
    */
    (
      weight.to_wu(),
      u64::try_from(bitcoin::policy::get_virtual_tx_size(
        i64::try_from(weight.to_wu()).unwrap(),
        0i64,
      ))
      .unwrap(),
    )
  }
