### Title
Unauthenticated blame accusations let any party mark an arbitrary participant as faulty - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`BlameMachine::blame` / `AdditionalBlameMachine::blame` and the underlying `Decryption::decrypt_with_proof` implement a "privileged" operation — adjudicating fault in the DKG and attributing blame to a named participant — without verifying that the accuser is actually the message's recipient. Analogous to the Ech0 advisory (endpoints that check "a token is present" but never check the caller's role), `decrypt_with_proof` accepts `decryptor: Participant` and `proof: Option<EncryptionKeyProof>` as caller-supplied inputs and returns `DecryptionError::InvalidProof` whenever `proof` is `None`, which `blame_internal` then maps to blaming the named `recipient` — a participant the attacker chose, not one they proved themselves to be.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` takes `from`, `decryptor`, the ciphertext, and an `Option<EncryptionKeyProof>`:

```rust
// crypto/dkg/pedpop/src/encryption.rs, lines 366-397
pub(crate) fn decrypt_with_proof<E: Encryptable>(
  &self,
  from: Participant,
  decryptor: Participant,
  mut msg: EncryptedMessage<C, E>,
  proof: Option<EncryptionKeyProof<C>>,
) -> Result<Zeroizing<E>, DecryptionError> {
  if !msg.pop.verify(msg.key, pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, ...)) {
    Err(DecryptionError::InvalidSignature)?;
  }
  if let Some(proof) = proof {
    proof.dleq.verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],
    ).map_err(|_| DecryptionError::InvalidProof)?;
    ...
  } else {
    Err(DecryptionError::InvalidProof)   // <-- reached for proof == None
  }
}
```

`blame_internal` in `crypto/dkg/pedpop/src/lib.rs` (lines 575-609) translates this:

```rust
Err(DecryptionError::InvalidSignature) => return sender,   // bad PoP → sender's fault
Err(DecryptionError::InvalidProof) => return recipient,    // no/wrong proof → *recipient* blamed
```

So the authorization gap: the only "credential" required to have `recipient` declared faulty is a well-formed `EncryptedMessage` whose `pop` Schnorr signature verifies under `pop_challenge(context, R, key, sender, ciphertext)`. Crucially:

- The `pop` proof binds `from` (sender index) but **not** `decryptor`/`recipient` — `pop_challenge` (`encryption.rs` lines 302-324) never appends the recipient index.
- Any `EncryptedMessage` with a valid PoP suffices; it need not be the message actually sent to the named recipient. `msg.key` and `msg.pop` are attacker-chosen, and anyone can produce a valid PoP for a fresh ephemeral key (`encrypt()` at lines 135-168 requires no identity).
- With `proof == None`, `InvalidProof` is returned unconditionally and `blame_internal` returns `recipient` as the faulty party — even if that recipient is honest and never made any accusation.

An unprivileged observer can therefore call `AdditionalBlameMachine::blame(sender, victim, forged_msg_with_valid_pop, None)` — or submit the equivalent blame request to a coordinator — and have an arbitrary honest `victim` declared the faulty party.

### Impact Explanation
Blame attribution is the mechanism Serai uses to identify and punish faulty DKG participants. Marking an honest participant as faulty forces protocol abort (`PedPoPError::InvalidShare` / blame output is fed to the caller's fault handling) and, in the Serai protocol's economic layer, can subject the blamed validator to slashing or removal from the validator set. An attacker with only public inputs (any `EncryptedMessage` they fabricate themselves, plus a chosen `recipient` index) can:

1. Repeatedly accuse honest validators of issuing false claims, forcing DKG aborts (denial of threshold-key generation), or
2. Cause an honest validator to be recorded as the faulty party in a blame adjudication they were never a party to — a forged accusation with no requirement that the accuser possess the ECDH key proving they were the message's intended recipient.

This mirrors the advisory's impact model: a low-privilege party exercising a privileged adjudication path because the implementation validates a credential (the PoP) without validating the caller's authorization for *this* operation (being the actual decryptor).

### Likelihood Explanation
The attack requires no special position: any party that can feed a blame request to a blame evaluator (in Serai's design, blame statements are broadcast/adjudicated publicly — `AdditionalBlameMachine::new` exists precisely so non-participants can evaluate blame, lines 639-662 of `lib.rs`). The attacker needs only:

- knowledge of `context` (public) and the victim's participant index (public),
- ability to construct `msg.key` + valid `pop` for `sender`'s index — trivially done since `pop_challenge` only binds the *sender* index, and the PoP is a plain Schnorr signature over a key the attacker generates,
- `proof = None`.

`decrypt_with_proof` then deterministically returns `InvalidProof` → victim blamed. Note the defense documented at `lib.rs` lines 615-617 and 664-669 — "This message must have been authenticated as actually having come from the sender" — authenticates the *sender*, not the *accuser/recipient*, so it does not mitigate this gap.

Uncertainty: the concrete economic consequence (slashing vs. abort-only) depends on the coordinator's fault handling, which is outside the in-scope crates. The cryptographic-level defect — unauthenticated blame assignment — is fully supported by the code above.

### Recommendation
Bind the accuser's identity into the blame path so that `InvalidProof` can only ever blame the party who actually produced a decryption claim:

- Include `decryptor` (the recipient's participant index) in `pop_challenge` (`encryption.rs` line 302), so a fabricated message cannot be repurposed against arbitrary recipients.
- Require the blame submission to carry a proof that the accuser knows the ECDH shared key for *some* validly-PoP'd message addressed to them — i.e., make the `None`-proof path unreachable for external accusers, or require `AdditionalBlameMachine::blame` to take an `EncryptionKeyProof` (non-optional) plus evidence the submitter is `recipient` (e.g., a signature over the accusation under the recipient's registered `enc_key` or validator key).
- At minimum, `blame_internal` should treat a missing proof as "inconclusive/malformed accusation" rather than defaulting to blaming the named `recipient` (`lib.rs` line 587).

### Proof of Concept
```rust
// Attacker knows: context (public), n, all commitment msgs (broadcast),
// and picks a victim participant index `victim`.

// 1. Attacker fabricates a "secret share" message with a valid PoP, as if
//    from honest `sender`, encrypted under attacker-chosen ephemeral key.
let attacker_key = <C as Ciphersuite>::random_nonzero_F(&mut rng);
let pub_key = C::generator() * attacker_key;
let nonce = <C as Ciphersuite>::random_nonzero_F(&mut rng);
let pub_nonce = C::generator() * nonce;

let mut msg_body = <SecretShare<C::F> ...>::default(); // any bytes
let pop = SchnorrSignature::sign(
    &attacker_key,
    nonce,
    pop_challenge::<C>(context, pub_nonce, pub_key, sender, msg_body.as_ref()),
);
let forged_msg = EncryptedMessage { key: pub_key, pop, msg: msg_body };

// 2. Attacker submits a blame adjudication naming `victim` as recipient,
//    with proof = None.
let evaluator = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs)?;
let faulty = evaluator.blame(sender, victim, forged_msg, None);

// 3. decrypt_with_proof:
//    - pop verifies (attacker made a valid PoP for `sender`'s index;
//      the challenge does not bind `victim`)
//    - proof is None → Err(DecryptionError::InvalidProof)
//    - blame_internal returns `recipient` == `victim`
assert_eq!(faulty, victim); // honest victim is declared faulty
```

The honest `victim` never sent any secret-share message, made no accusation, and possesses no way to distinguish this adjudication from a legitimate one — the evaluator had no authorization check that the accuser was the message's intended decryptor.
