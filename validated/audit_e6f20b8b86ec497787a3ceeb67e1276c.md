### Title
`PoolWallet.new_peak()` can raise unhandled exceptions during the two-stage leave-pool travel transaction, halting `WalletStateManager.new_peak()` processing for all wallets and stalling wallet sync progression - (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet` implements a multi-step, state-machine rebalancing flow analogous to the reported `BalancedVault._rebalance` bug: switching between pool states (`FARMING_TO_POOL`/`SELF_POOLING` ↔ `LEAVING_POOL` ↔ target state) requires two sequential on-chain transitions separated by a relative-lock-height wait, and the second step is automatically retried on every new peak via `PoolWallet.new_peak()`. If this second step fails — either because of an internal invariant mismatch (`ValueError` at [1](#0-0) ) or because `generate_travel_transactions`/`generate_fee_transaction` cannot build a valid spend (e.g. insufficient main-wallet balance for the fee) — the exception propagates uncaught out of `WalletStateManager.new_peak()`.

### Finding Description
`WalletStateManager.new_peak()` iterates over every wallet and calls `wallet.new_peak(height)` for each `PoolWallet`/`PlotNFT2Wallet`, with no per-wallet exception isolation: [2](#0-1) 

`PoolWallet.new_peak()` performs the deferred second half of a pool state transition (analogous to the Vault's deferred rebalance) once the relative lock height has passed: [3](#0-2) 

Note the unconditional `raise ValueError(...)` at line 818 when `target_state == pool_wallet_info.current` (an internal-state-desync guard), and the unguarded assertions at lines 839-848 that fire before `generate_travel_transactions` is invoked. `generate_travel_transactions` itself builds a spend from the current singleton tip and, when `fee > 0`, calls `generate_fee_transaction`, which selects coins from the standard wallet: [4](#0-3) [5](#0-4) 

If the standard wallet cannot cover the fee (or any other precondition inside `generate_signed_transaction`/`create_travel_spend` fails), this call raises, and that exception is never caught anywhere in the call chain up to `WalletNode.new_peak_wallet()`: [6](#0-5) 

Because the exception occurs while holding `self.wallet_state_manager.lock` and before the code that advances `finished_sync_up_to`, retries fee-failed transactions, or runs clawback auto-claim, all of those steps are skipped for that peak — and since `target_state` is never cleared (the exception aborts before `apply_state_transition` would clear it, and the failing condition in `new_peak()` re-evaluates the same way on the very next peak), the failure recurs on every subsequent peak until a user manually intervenes (e.g., funds the standard wallet, cancels the pending pool operation, or deletes the stuck unconfirmed transaction, as hinted by the error messages in `join_pool`/`self_pool`): [7](#0-6) [8](#0-7) 

This is the direct structural analog of the reported Vault issue: a mandatory, automatically-retried multi-step rebalancing/state-transition routine that can revert/raise, and whose only remedy is external, out-of-band user action (funding the wallet) rather than a graceful in-protocol recovery path.

### Impact Explanation
An unhandled exception in one `PoolWallet`'s `new_peak()` call aborts the loop in `WalletStateManager.new_peak()` for that iteration, meaning **any other wallet later in iteration order (other `PoolWallet`/`PlotNFT2Wallet` instances) does not get its `new_peak()` invoked for that block either**. It also causes `WalletNode.new_peak_wallet()` to abort before advancing `finished_sync_up_to` and before running the fee-retry and clawback-auto-claim logic on every peak, effectively stalling those wallet-sync-driven processing paths repeatedly (each new peak reproduces the same failure) until a user manually resolves the stuck pool wallet by depositing additional funds or canceling the in-flight transaction. This matches the "spend-triggered transaction-processing halt" impact class, though the affected surface is local wallet-sync bookkeeping rather than consensus or peer-visible state, and requires the operator to actively be mid-way through a pool switch with insufficient standard-wallet balance for the fee (or another precondition of `generate_travel_transactions` failing).

### Likelihood Explanation
Likelihood is comparatively low: it requires a user to have initiated a pool-switch (`join_pool`/`self_pool`) with a fee, wait through the relative-lock-height, and then have the standard wallet's spendable balance drop below the fee amount by the time the second travel transaction is attempted (or some other `generate_travel_transactions` precondition to fail). This is a plausible but not trivially reachable operational misconfiguration rather than an attacker-controlled trigger from a single external spend bundle.

### Recommendation
Wrap the per-wallet call in `WalletStateManager.new_peak()` (and the pool-wallet-specific logic inside `PoolWallet.new_peak()`) in a try/except that logs the error and continues to the next wallet, so one stuck pool wallet cannot prevent other wallets from processing new peaks or block `finished_sync_up_to`/fee-retry/clawback-auto-claim progression. Additionally, avoid raising a bare `ValueError` for the internal-state-desync case at line 818; log and return instead, consistent with other invariant violations that are treated as recoverable rather than fatal.

### Proof of Concept
1. Create a `PoolWallet`, join a pool with `fee > 0` via `pw_join_pool` (targeting a later self-pool or different pool).
2. Wait for the transition to `LEAVING_POOL` and let the relative lock height pass so `new_peak()` attempts the second travel transaction.
3. Before that peak arrives, drain the main (`standard_wallet`) balance below the configured `fee` (e.g., by spending all XCH elsewhere).
4. On the next peak, `PoolWallet.new_peak()` calls `generate_travel_transactions` → `generate_fee_transaction` → `standard_wallet.generate_signed_transaction`, which raises due to insufficient funds; this exception is unhandled and propagates through `WalletStateManager.new_peak()` and `WalletNode.new_peak_wallet()`.
5. Observe that on every subsequent peak the same exception recurs (since `target_state` was never cleared), and that `finished_sync_up_to` is not advanced and other wallets' `new_peak()` calls in the same iteration are skipped, until the user funds the wallet or otherwise clears the stuck transaction.

    async def new_peak(self, peak_height: uint32) -> None:
        # This gets called from the WalletStateManager whenever there is a new peak

        pool_wallet_info: PoolWalletInfo = await self.get_current_state()
        tip_height, tip_spend = await self.get_tip()

        if self.target_state is None:
            return
        if self.target_state == pool_wallet_info.current:
            self.target_state = None
            raise ValueError(f"Internal error. Pool wallet {self.wallet_id} state: {pool_wallet_info.current}")

        if (
            self.target_state.state in {FARMING_TO_POOL.value, SELF_POOLING.value}
            and pool_wallet_info.current.state == LEAVING_POOL.value
        ):
            leave_height = tip_height + pool_wallet_info.current.relative_lock_height

            # Add some buffer (+2) to reduce chances of a reorg
            if peak_height > leave_height + 2:
                unconfirmed: list[
                    TransactionRecord
                ] = await self.wallet_state_manager.tx_store.get_unconfirmed_for_wallet(self.wallet_id)
                next_tip: Coin | None = get_most_recent_singleton_coin_from_coin_spend(tip_spend)
                assert next_tip is not None

                if any([rem.name() == next_tip.name() for tx_rec in unconfirmed for rem in tx_rec.removals]):
                    self.log.info("Already submitted second transaction, will not resubmit.")
                    return

                self.log.info(f"Attempting to leave from\n{pool_wallet_info.current}\nto\n{self.target_state}")
                assert self.target_state.version == POOL_PROTOCOL_VERSION
                assert pool_wallet_info.current.state == LEAVING_POOL.value
                assert self.target_state.target_puzzle_hash is not None

                if self.target_state.state == SELF_POOLING.value:
                    assert self.target_state.relative_lock_height == 0
                    assert self.target_state.pool_url is None
                elif self.target_state.state == FARMING_TO_POOL.value:
                    assert self.target_state.relative_lock_height >= self.MINIMUM_RELATIVE_LOCK_HEIGHT
                    assert self.target_state.pool_url is not None

                async with self.wallet_state_manager.new_action_scope(self.next_tx_config, push=True) as action_scope:
                    await self.generate_travel_transactions(self.next_transaction_fee, action_scope)
