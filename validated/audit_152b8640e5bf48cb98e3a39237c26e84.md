### Title
Unauthenticated CAT→CR-CAT wallet-type conversion via attacker-chosen `authorized_providers`/`proofs_checker` bypasses compliance and can halt a victim's legitimate CAT spends - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
`CATWallet.identify()` automatically converts a victim's already-existing, unrestricted `CATWallet` into a `CRCATWallet` the moment it observes an incoming coin for the same `tail_hash` that is wrapped in a Credential-Restricted (CR) layer. The conversion, performed by `CRCATWallet.convert_to_cr()`, blindly trusts the `authorized_providers` and `proofs_checker` values taken from the attacker-crafted coin's own puzzle reveal — there is no on-chain authority or registration step that vets these values, and (unlike the analogous `RCATWallet.convert_to_revocable()`) there is no guard preventing conversion of a wallet that already holds unrestricted CAT coins.

### Finding Description
When a new CAT-type coin syncs in, `CATWallet.identify()` uncurries the puzzle and, if it detects a CR layer, extracts `crcat.authorized_providers` / `crcat.proofs_checker` directly from the spend that created the coin: [1](#0-0) 

If a matching plain `CATWallet` already exists for that `tail_hash` (i.e., the victim already owns non-restricted CATs of that asset), the code unconditionally calls `CRCATWallet.convert_to_cr()`, passing along the attacker-supplied `authorized_providers`/`proofs_checker` extracted from the incoming coin, and immediately swaps the wallet object in `wallet_state_manager.wallets`: [2](#0-1) 

`convert_to_cr()` performs this swap with no validation and — critically — with no check that the target `CATWallet` is still "empty" of prior coins: [3](#0-2) 

This is the exact same class of bug as the STRX `forceAllow()` report: a security-relevant state (which "authorized providers"/compliance policy governs a wallet's coins) is silently and irreversibly reinstated/assigned based on an untrusted, attacker-controlled input, without going through the proper registration/authorization flow. In STRX, removing an address from the denylist implicitly (and wrongly) added it to the allowlist by trusting stale/attacker-influenced state; here, receiving one attacker-crafted coin implicitly (and wrongly) converts a victim's wallet's entire governing CR policy (`authorized_providers`, `proofs_checker`) by trusting values taken straight from the untrusted incoming spend.

Contrast this with the sibling conversion path for revocable CATs, `RCATWallet.convert_to_revocable()`, which explicitly guards against converting a wallet that already has existing coin history: [4](#0-3) 
`convert_to_cr()` has no equivalent check, so the conversion happens even when the victim's `CATWallet` already has confirmed, spendable, unrestricted CAT coins on lineage.

### Impact Explanation
Any unprivileged party can construct and broadcast a single spend bundle that creates a CR-CAT-wrapped coin for an existing CAT asset ID (`tail_hash`) hinted to a victim's known puzzle hash. Once this coin syncs, the victim's local `CATWallet` for that asset is silently replaced in `wallet_state_manager.wallets` by a `CRCATWallet` whose `authorized_providers` and `proofs_checker` are dictated entirely by the attacker. From that point on, the wallet's spend logic for that asset id is the `CRCATWallet` implementation, which requires a `VerifiedCredential` matching the (now attacker-chosen) `authorized_providers`/`proofs_checker` before it will authorize any CR-CAT spend (`claim_pending_approval_balance`, `_generate_unsigned_spendbundle`, etc. all look up a VC via `get_vc_with_provider_in_and_proofs(self.info.authorized_providers, ...)`). Since the victim has no VC from the attacker's chosen provider, this can prevent the victim from spending assets held under that wallet id through normal client flows — a spend-triggered halt of legitimate transaction processing for that wallet, and a compliance/authorization bypass in the sense that a party with no on-chain authority determines which "compliance provider" now governs the victim's wallet state.

### Likelihood Explanation
High likelihood of triggering: it requires only a single unprivileged spend bundle creating a CR-CAT coin (via `CRCAT.launch`) hinted to any address holding a `CATWallet` for a known/guessable `tail_hash`, no special permissions, no cooperation from the victim, and no consensus-level restriction prevents this since CR-CAT wrapping of an existing tail is a normal, permitted puzzle construction.

### Recommendation
Mirror the safeguard already present in `RCATWallet.convert_to_revocable()`: before converting a `CATWallet` to `CRCATWallet` in `CRCATWallet.convert_to_cr()`, verify the existing `CATWallet`'s lineage store is empty (i.e., it holds no prior unrestricted coins) and reject/ignore the conversion (or split the coin into a separate, explicitly-named wallet) if it is not. More generally, do not let an untrusted incoming coin's self-declared CR-layer parameters (`authorized_providers`, `proofs_checker`) silently override the governing policy of an existing wallet instance; require explicit user confirmation or treat differing CR parameters for the same `tail_hash` as a distinct/new wallet rather than mutating the existing one in place.

### Proof of Concept
1. Victim runs a wallet with a `CATWallet` for `tail_hash = T`, holding legitimate unrestricted CAT coins.
2. Attacker (any unprivileged spend-bundle submitter) uses `CRCAT.launch()` to create a CR-CAT coin for the same tail `T`, setting `authorized_providers=[attacker_DID]` and a trivial `proofs_checker` (e.g., an empty/near-trivial flag set), with the payment puzzle hash hinted to the victim's known puzzle hash.
3. Attacker broadcasts this spend bundle to the mempool; it is a valid, standalone CAT/CR-CAT construction and gets accepted/farmed.
4. The victim's wallet syncs the coin. `CATWallet.identify()` detects the CR layer, matches the existing plain `CATWallet` for tail `T` ( [2](#0-1) ), and calls `CRCATWallet.convert_to_cr(found_cat_wallet, [attacker_DID], attacker_proofs_checker)`.
5. `convert_to_cr()` ( [3](#0-2) ) performs the swap unconditionally, without checking whether `found_cat_wallet` already has confirmed unrestricted coins.
6. The victim's wallet object for asset `T` is now a `CRCATWallet` gated by the attacker's chosen provider; subsequent spend attempts through the wallet RPC for that wallet id require a VC from `attacker_DID`, which the victim does not have, blocking normal spend flows for that wallet id.

    @classmethod
    async def convert_to_cr(
        cls,
        cat_wallet: CATWallet,
        authorized_providers: list[bytes32],
        proofs_checker: ProofsChecker,
    ) -> None:
        replace_self = cls()
        replace_self.standard_wallet = cat_wallet.standard_wallet
        replace_self.log = logging.getLogger(cat_wallet.get_name())
        replace_self.log.info(f"Converting CAT wallet {cat_wallet.id()} to CR-CAT wallet")
        replace_self.wallet_state_manager = cat_wallet.wallet_state_manager
        replace_self.info = CRCATInfo(
            cat_wallet.cat_info.limitations_program_hash, None, authorized_providers, proofs_checker
        )
        await cat_wallet.wallet_state_manager.user_store.update_wallet(
            WalletInfo(
                cat_wallet.id(), cat_wallet.get_name(), uint8(WalletType.CRCAT.value), bytes(replace_self.info).hex()
            )
        )
        updated_wallet_info = await cat_wallet.wallet_state_manager.user_store.get_wallet_by_id(cat_wallet.id())
        assert updated_wallet_info is not None
        replace_self.wallet_info = updated_wallet_info
        replace_self.tail_hash = replace_self.info.limitations_program_hash

        cat_wallet.wallet_state_manager.wallets[cat_wallet.id()] = replace_self
