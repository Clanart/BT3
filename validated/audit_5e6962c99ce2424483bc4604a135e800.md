### Title
OP_RETURN data output excluded from fee metering and weight check, undercharging fees and bypassing the standard-weight limit - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` meters the transaction's weight/vbytes for fee calculation and for the `MAX_STANDARD_TX_WEIGHT` check using only the `payments` slice. When a `data` payload is supplied, an OP_RETURN `TxOut` is pushed into `tx_outs` *before* metering, yet `calculate_weight_vbytes` is called with `payments`, not `tx_outs`. The produced transaction is therefore larger than what was metered: `needed_fee` is undercharged and the standard-weight limit can be exceeded.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds `tx_outs` from `payments` and then appends an OP_RETURN output carrying up to 80 bytes of attacker-integrator-supplied `data` [1](#0-0) . Immediately after, the weight/vbyte metering — which drives both `needed_fee` and the `TooLargeTransaction` check — is computed over `payments` only, omitting the OP_RETURN output [2](#0-1) . The same omission occurs in the change-output re-metering, again passing `payments` [3](#0-2) , and the final `MAX_STANDARD_TX_WEIGHT` gate uses that under-metered `weight` [4](#0-3) . `calculate_weight_vbytes` faithfully includes every output it is given [5](#0-4)  — it is simply never given the OP_RETURN output.

This is a direct analog of incorrect metering: resource consumption (transaction size/weight) that consensus nodes actually charge for is computed on a smaller object than the one produced. The OP_RETURN output adds roughly 11–92 vbytes (8-byte amount + compactsize + `OP_RETURN` + push opcode + up to 80 bytes of data) that are never billed.

### Impact Explanation
Two concrete harms:

1. **Undercharged fee.** `needed_fee = fee_per_vbyte * vbytes` uses the smaller vbytes. The actual signed transaction pays a lower effective feerate than requested and than `needed_fee()` reports — including potentially dropping below `DEFAULT_MIN_RELAY_TX_FEE` in edge cases where the metered fee was barely above it. The resulting transaction the threshold key signs may be unrelayable or stuck, delaying/derailing an intended payment.
2. **Weight-limit bypass.** A transaction whose real weight exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) passes the check because the OP_RETURN output's weight is never counted, producing a consensus-valid but policy-non-standard transaction no relay node will accept — funds committed to an unspendable-in-practice path until manually reconstructed.

### Likelihood Explanation
`data` is a public caller-supplied input to `SignableTransaction::new`, gated only by an 80-byte length check [6](#0-5) . Any code path (or caller of this library, which exists to construct transactions for untrusted-requested payments) that attaches an OP_RETURN triggers the under-metering deterministically — no race, no adversary collusion, no special state required. Exploitation requires only that the transaction be near the fee floor or weight cap, but the miscount itself occurs on every call with `data.is_some()`.

### Recommendation
Meter over the actual outputs: pass `tx_outs` (as `(ScriptBuf, u64)` pairs or by refactoring `calculate_weight_vbytes` to accept `&[TxOut]`) instead of `payments` at both metering sites, including the OP_RETURN output. Recompute the final `weight` after all outputs (payments + OP_RETURN + change) are fixed, before enforcing `MAX_STANDARD_TX_WEIGHT`.

### Proof of Concept
```rust
// networks/bitcoin wallet code path
let data = vec![0u8; 80]; // largest allowed OP_RETURN payload
let tx = SignableTransaction::new(inputs, &payments, change, Some(data), fee_per_vbyte)?;
// Inside new():
//   tx_outs gets an extra TxOut { value: 0, script_pubkey: OP_RETURN <80 bytes> }
//   calculate_weight_vbytes(tx_ins.len(), payments, ...)  // OP_RETURN omitted
//   needed_fee = fee_per_vbyte * vbytes                    // ~92 vbytes unbilled
//   weight > MAX_STANDARD_TX_WEIGHT check                  // under-counted
assert!(tx.needed_fee() < fee_per_vbyte * actual_signed_tx_vsize);
```
The test in `networks/bitcoin/tests/wallet.rs` only exercises `data = None` and asserts `needed_fee == vsize * FEE` [7](#0-6) ; repeating it with `Some(vec![0; 80])` shows `needed_fee` falling short of `vsize * FEE` by ~92 vbytes worth of satoshis.
