### Title
ComputationCostLimit is never enforced for the top-level call/precompile-entry code path - ([File: blockchain/vm/evm.go])

### Summary
The `ComputationCostLimit` mechanism in Kaia's EVM is intended to bound the wall-clock execution time of a transaction independently of its gas cost, mirroring how Scriban's `LoopLimit` is meant to bound iteration regardless of declared cost. In the opcode interpreter loop, the accumulated `opcodeComputationCostSum` is checked against `ComputationCostLimit` immediately after every opcode's cost is added [1](#0-0) . However, when a call target is a precompiled contract, the dedicated `run()` helper adds the precompile's `computationCost` to `evm.opcodeComputationCostSum` but never performs the corresponding limit check [2](#0-1) .

### Finding Description
`RunPrecompiledContract` first charges gas via `contract.UseGas(gas)` and then fully executes the precompile's `Run()` method before returning `computationCost` [3](#0-2) . The caller, `run()` in `evm.go`, adds this cost to the running total but does not compare it against `in.evm.Config.ComputationCostLimit` [4](#0-3) . Enforcement of the limit only happens inside `EVMInterpreter.Run`'s bytecode loop, on the *next* opcode after control returns from `run()` [1](#0-0) .

This means:
1. When a transaction's `to` address is itself a precompiled contract (e.g., BLS12-381 pairing/multiexp, `bigModExp`), execution goes through `EVM.Call` → `run()` directly, without ever entering the bytecode interpreter loop for that call frame. In that case the accumulated computation cost is never checked at all for the entire transaction, since there is no "next opcode" to trigger the check.
2. When a precompile is invoked via `CALL`/`STATICCALL` from within contract bytecode as the *last* operation before `RETURN`/`STOP`, the extremely expensive computation already ran to completion before any check occurs, and if the calling contract does nothing further, the limit is effectively bypassed for that heavy computation.

This is structurally analogous to the reported Scriban bug: the cost-accounting bookkeeping is updated correctly, but the actual bound (`LoopLimit`/`ComputationCostLimit`) is not enforced before or immediately after the expensive operation runs, allowing the heavy operation to execute in full regardless of the configured limit.

Several precompiles have computation costs that scale with attacker-controlled input while remaining well inside normal gas limits per unit of wall-clock time (e.g., `bls12381Pairing`/`bls12381G1MultiExp`/`bls12381G2MultiExp` scale linearly with `k` pairs/points [5](#0-4) , and `bigModExp`'s cost model is independently tunable from real computation time via `modexpIterationCount`/`osakaModExpGas` [6](#0-5) ), so a sender can size the call to consume a large multiple of `OpcodeComputationCostLimit`/`OpcodeComputationCostLimitCancun` (100–150ms nominal) [7](#0-6)  while paying for gas but never triggering `ErrOpcodeComputationCostLimitReached`.

### Impact Explanation
An unprivileged sender can craft a plain transaction (or an internal call ending in a precompile invocation) that consumes real CPU time far beyond the node's intended per-transaction computation budget, without the safety check that exists for ordinary bytecode ever firing. Since this budget exists specifically to bound block-production/verification wall-clock time regardless of gas paid, bypassing it can pin CPU during block assembly/validation, a resource-exhaustion condition matching the "Medium" DoS class of the reference CVE. This does not directly cause fund loss or consensus divergence between honest nodes (since all nodes execute the same code path identically), but it undermines the intended defense-in-depth against computation-time-based DoS.

### Likelihood Explanation
Reaching this path requires only a single transaction sent to (or calling) a precompiled contract address with attacker-controlled sizing (e.g., large blob of BLS12-381 point/scalar pairs) that stays within the normal gas limit while exceeding `ComputationCostLimit` in actual execution time — no special privileges, node access, or consensus role needed.

### Recommendation
Add the same `opcodeComputationCostSum > ComputationCostLimit` check inside `run()` in `blockchain/vm/evm.go` immediately after `evm.opcodeComputationCostSum += computationCost`, returning `ErrOpcodeComputationCostLimitReached` (or propagating it via `err`) consistently with the interpreter's opcode loop, so top-level and last-in-bytecode precompile calls are bounded the same way ordinary opcode sequences are.

### Proof of Concept
Conceptual PoC (would need to be validated in a running node/test harness):
1. Send a transaction with `to` = the BLS12-381 pairing precompile address (or `bigModExp`), with `data` sized so that `GetRequiredGasAndComputationCost` reports a `computationCost` several multiples of `params.OpcodeComputationCostLimitCancun`, while the required `gas` remains under the block gas limit (achievable because gas and computationCost scale differently, e.g. modexp's Osaka gas formula vs. the flat `ComputationCostLimit` constant).
2. Observe that `RunPrecompiledContract` fully executes the heavy computation in `run()` [8](#0-7) , and because this is a top-level call (or the last opcode before return), the `ErrOpcodeComputationCostLimitReached` check in `interpreter.go` [1](#0-0)  is never reached for that call frame — the transaction succeeds despite exceeding the configured computation-cost budget.

Note: I was unable to fully trace every path through `EVM.Call`/`CallCode`/`DelegateCall`/`StaticCall` in this session to confirm there is no other enforcement point for the top-level precompile-call case; a Devin session with full build/test access would be needed to write and run an actual reproduction test confirming the missing check has real-world effect (e.g., measuring wall-clock time or asserting the error is never returned).

func RunPrecompiledContract(p PrecompiledContract, input []byte, contract *Contract, evm *EVM) (ret []byte, computationCost uint64, err error) {
	gas, computationCost := p.GetRequiredGasAndComputationCost(input)
	if contract.UseGas(gas) {
		ret, err = p.Run(input, contract, evm)
		return ret, computationCost, err
	}
	return nil, computationCost, kerrors.ErrOutOfGas
}

// modexpIterationCount calculates the number of iterations for the modexp precompile.
// This is the adjusted exponent length used in gas calculation.
func modexpIterationCount(expLen uint64, expHead uint256.Int, multiplier uint64) uint64 {
	var iterationCount uint64

	// For large exponents (expLen > 32), add (expLen - 32) * multiplier
	if expLen > 32 {
		carry, count := bits.Mul64(expLen-32, multiplier)
		if carry > 0 {
			return math.MaxUint64
		}
		iterationCount = count
	}

	// Add the MSB position - 1 if expHead is non-zero
	if bitLen := expHead.BitLen(); bitLen > 0 {
		count, carry := bits.Add64(iterationCount, uint64(bitLen-1), 0)
		if carry > 0 {
			return math.MaxUint64
		}
		iterationCount = count
	}

	return max(iterationCount, 1)
}

// byzantiumModexpGas calculates the gas cost for the modexp precompile using Byzantium rules.
func byzantiumModexpGas(baseLen, expLen, modLen uint64, expHead uint256.Int) uint64 {
	const (
		multiplier = 8
		divisor    = 20
	)

	maxLen := max(baseLen, modLen)
	multComplexity := byzantiumMultComplexity(maxLen)
	if multComplexity == math.MaxUint64 {
		return math.MaxUint64
	}
	iterationCount := modexpIterationCount(expLen, expHead, multiplier)

	// Calculate gas: (multComplexity * iterationCount) / divisor
	carry, gas := bits.Mul64(iterationCount, multComplexity)
	gas /= divisor
	if carry != 0 {
		return math.MaxUint64
	}
	return gas
}

// GetRequiredGasAndComputationCost returns the gas required to execute the pre-compiled contract.
func (c *bls12381Pairing) GetRequiredGasAndComputationCost(input []byte) (uint64, uint64) {
	k := uint64(len(input) / 384)
	return params.Bls12381PairingBaseGas + k*params.Bls12381PairingPerPairGas,
		params.Bls12381PairingBaseComputationCost + k*params.Bls12381PairingPerPairComputationCost
}
