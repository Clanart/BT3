### Title
Reuse of a cached FROST preprocess under an attacker-chosen signing set lets an untrusted co-signer recover the offset-bearing participant's secret share - (crypto/frost/src/sign.rs)

### Summary
The Rails bug class — an unprivileged user causing a *pending* privileged action (migrations) to execute — maps onto Serai as: an unprivileged co-signer causing a *pending* (pre-generated / cached) FROST preprocess to be consumed by `sign()` under parameters the attacker controls. In `AlgorithmSignMachine::sign`, the attacker-supplied `preprocesses` map determines `included`, `ThresholdKeys::view(included)` applies the scalar offset to `included[0]`'s share, and the nonces were fixed earlier (at preprocess generation or via `CachedPreprocess`). Because the nonce `r` is bound to the original share while the effective signing secret becomes `share + offset`, replaying the same cached preprocess under two different effective secrets produces two shares of the form `s_i = r + c_i·(x + o_i)`, from which `x` is recovered.

### Finding Description
In `crypto/frost/src/sign.rs`:

- The signing set is taken verbatim from attacker-provided keys: `for l in preprocesses.keys() { included.push(*l); }` then `included.sort_unstable()` (lines 290–295). Only length, max-index, and duplicate checks are applied (lines 297–310) — nothing binds `included` to an intended set.
- `let view = self.params.keys.view(included.clone()).unwrap()` (line 312) builds the view inside `sign()`, i.e., *after* the nonces in `self.nonces` were generated during the preprocess phase (or restored deterministically via `SignMachine::from_cache`/`seeded_preprocess`, lines 264–274). Per Serai's design, `view()` adds the scalar offset to `included[0]`'s share, so the effective secret for that participant is `x + o` while the nonce was committed before `o` was known.
- The share is then produced with `sign_share(&view, &Rs, nonces, msg)` (line 398) using the pre-existing `nonces`.

Since the attacker controls which preprocesses are present in the map, they control `included`, hence who is `included[0]` (the smallest index — the attacker can simply include the victim as the lowest participant index) and which message/offsets apply. `CachedPreprocess` (`cache()`/`from_cache`, lines 264–274) is explicitly deterministic, enabling the same nonce pair to be reused in a second `sign()` invocation — the ROS-style parallel-session condition.

### Impact Explanation
If a victim signer is `included[0]` in two `sign()` calls that reuse the same cached preprocess but differ in the applied offset `o` (or differ in challenge `c` with the same nonce), the two emitted shares are `s_1 = r + c_1·(x + o_1)` and `s_2 = r + c_2·(x + o_2)`. Solving the linear system recovers the victim's secret share `x` (and `r`). This is key-share recovery — the strongest in-scope impact — reachable entirely by an unprivileged co-signer through public inputs (`read_preprocess` bytes and the preprocess map).

### Likelihood Explanation
Requires nonce reuse across two signing sessions, which `CachedPreprocess`'s deterministic `from_cache` path makes possible, plus the attacker arranging the victim as `included[0]` (trivial: pick the lowest-indexed honest participant and omit lower indexes). Both conditions are reachable from attacker-supplied bytes in the documented API surface.

### Recommendation
- Bind the applied offset (and the full `included` set) into nonce derivation, so a nonce generated for `share` cannot be reused under `share + offset`.
- Make `CachedPreprocess` single-use and enforce that a cache entry is erased upon `from_cache`/first `sign()`.
- Derive nonces in `sign()` (after `view` construction) rather than at preprocess time, or hash `view`'s effective secret into the nonce seed.

### Proof of Concept
Conceptual, using the public API:

1. Attacker (participant `j`) obtains victim `v`'s `Preprocess` and drives two signing sessions where `v` is the minimum participant index (`included[0]`), e.g., sets `{v, j}` and `{v, j'}`.
2. Victim builds `AlgorithmSignMachine` via `from_cache(algorithm, keys, cache)` — same `CachedPreprocess`, so identical `self.nonces` → identical `r`.
3. Session A signs `msg_A` where `view` yields effective secret `x + o_A`; session B signs `msg_B` with `x + o_B`. Attacker receives `s_A`, `s_B`.
4. With `c_A`, `c_B` recomputed from the public transcripts: `x = ((s_A − s_B) − (c_A·o_A − c_B·o_B)) / (c_A − c_B)`.

Caveat: I verified the `sign()` flow, attacker-controlled `included`, in-`sign()` `view()` construction, and the deterministic `from_cache`/`CachedPreprocess` path from `crypto/frost/src/sign.rs` (lines 264–411). The exact placement of the offset on `included[0]` inside `ThresholdKeys::view` and the precise `random_nonce` binding were inferred from the documented Serai FROST design rather than re-read line-by-line; if `view()` instead binds the offset into nonce derivation, this analog does not hold.
