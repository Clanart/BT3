### Title
Attacker-controlled PR `clone_url` from the GitHub API is passed unvalidated into `git remote add`/`fetch`, allowing the `ext::`/`fd::` git transport to execute arbitrary commands - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user opens a pull request through Desktop, `_findPullRequestBranch` takes `headCloneUrl` straight from the pull request JSON returned by the GitHub/GHE API and feeds it into `addRemote()`, then fetches it. Neither `addRemote` nor the environment set up for the fetch (`envForRemoteOperation`) restrict the git transport scheme, so a crafted `clone_url` using git's `ext::` (or `fd::`) helper protocol will spawn an arbitrary local process the moment the remote is fetched.

### Finding Description
`Dispatcher._checkoutPullRequest` → `AppStore._findPullRequestBranch` (`app/src/lib/stores/app-store.ts:8633-8721`) receives `headCloneUrl` as a plain string argument that ultimately originates from `pullRequest.head.repo.clone_url` in the API response object (`app/src/ui/dispatcher/dispatcher.ts:1998-2048`, specifically line 2043 `pullRequest.head.repo.clone_url`). This value is compared against existing remotes with `urlMatchesRemote()`, and if no match is found: [1](#0-0) 

```
if (remote === undefined) {
  try {
    const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
    remote = await addRemote(repository, forkRemoteName, headCloneUrl)
```

`addRemote()` performs no scheme allow-listing: [2](#0-1) 

The remote is then fetched via `this._fetchRemote(...)`, which uses `envForRemoteOperation(remote.url)` to build the git process environment. That function only recognizes `http(s)://` for proxy resolution and does nothing else to constrain the protocol: [3](#0-2) 

Git natively supports the `ext::` remote helper, which executes an arbitrary shell command as the "transport" (e.g. `ext::sh -c "touch /tmp/pwned"`), and `fd::`, both of which are valid `clone_url`-style strings from git's perspective. Nothing in this call chain sets `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow=never`, or similar hardening that upstream Git (and many other GUI clients) apply specifically to block `ext::`/`fd::`/`file://` when handling untrusted URLs. Unlike the `clone()` function in `app/src/lib/git/clone.ts`, which was explicitly hardened against local-path-traversal clone destinations (`isClonePathSensitive`), no equivalent hardening exists for the transport scheme used by `addRemote`/fetch triggered by PR checkout.

While `clone_url` normally reflects the real HTTPS URL of a repository as generated by github.com, the valid-impact criteria for this exercise explicitly include "a GitHub API object" as an attacker-controlled input (e.g., a malicious/compromised GitHub Enterprise Server, a MITM'd TLS session that an enterprise proxy trusts, or any code path that deserializes pull request JSON from a source the user's Desktop instance is configured to trust). Any of these can supply a poisoned `clone_url` string.

### Impact Explanation
If the attacker controls the `clone_url` field for the head repo of a fork PR, they can substitute `ext::<command>` (or the related `fd::` helper) and get arbitrary command execution on the victim's machine the moment Desktop tries to open/check out that PR — no local access, no leaked credentials, and no unusual user action beyond the normal "Open PR from Desktop" or in-app checkout-PR workflow. This is remote code execution triggered purely by an attacker-influenced GitHub API object, matching the "attacker controls a GitHub API object... resulting in code execution" impact category.

### Likelihood Explanation
Exploitability depends on the attacker being able to influence the API response (rather than public github.com, which generates `clone_url` server-side from the real repository), so likelihood is moderate: it requires a GHE Server instance, an API proxy, or a MITM position that the app trusts, but does not require any credential compromise, local access, or social engineering beyond a normal PR-checkout click. No existing guard in the codebase (neither `addRemote`, nor `envForRemoteOperation`, nor `urlMatchesRemote`) validates or restricts the transport scheme of `clone_url` before it reaches `git remote add`/`fetch`.

### Recommendation
- Validate that any URL originating from GitHub API objects (`clone_url`, `ssh_url`, etc.) matches an allow-listed scheme (`https://`, `ssh://`, `git@`) via `parseRemote()`/`parseRepositoryIdentifier()` before calling `addRemote()`.
- Set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or the equivalent `protocol.*.allow=never` git config flags) in `envForRemoteOperation` for all remote-touching git invocations, disabling `ext`, `fd`, and `file` transports by default, mirroring the hardening already applied to clone-path safety in `app/src/lib/git/clone.ts`.
- Add regression tests analogous to `app/test/unit/git/clone-test.ts`'s sensitive-path tests, but covering rejection of `ext::`/`fd::` URLs in `addRemote`/fetch flows.

### Proof of Concept
1. Configure Desktop against a GitHub Enterprise Server (or a MITM proxy in an environment where Desktop is configured to trust it) that an attacker controls or has compromised.
2. Have the malicious server return a pull request JSON object where `head.repo.clone_url` is set to `ext::sh -c "touch /tmp/pwned"`.
3. In Desktop, trigger "Open in Desktop" / checkout for that PR, driving `Dispatcher._checkoutPullRequest` → `AppStore._findPullRequestBranch(repository, prNumber, headRepoOwner, "ext::sh -c \"touch /tmp/pwned\"", headRefName)`.
4. `addRemote(repository, forkRemoteName, "ext::sh -c \"touch /tmp/pwned\"")` succeeds and writes the URL into `.git/config`; the following `this._fetchRemote(...)` invokes git, which instantiates the `ext::` transport helper and executes the attacker's command as a child process of the user's shell, without any confirmation dialog referencing the "URL."
