### Title
Unlocking mWomSV holders keep 100% of bonus rewards instead of forfeiting a pro-rata share - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` unconditionally sets `rewardableAmount = _amount`, so `forfeitAmount` is always `0` regardless of the caller's unlock/cooldown status. This differs from the analogous `vlMGPBaseRewarder._calExpireForfeit`, which multiplies the accrued amount by `vlMGP.getRewardablePercentWAD(_account)` to reduce the share paid to users who are mid-unlock. Because `mWomSV.getRewardablePercentWAD` is never invoked, any mWomSV holder who has started an unlock (`startUnlock`) still receives their full bonus rewards via `getReward`/`getRewards`.

### Finding Description
`mWomSV.sol` implements `getRewardablePercentWAD(address _user)` [1](#0-0)  which explicitly reduces a user's rewardable share while tokens are in cooldown (`startUnlock`) as a decaying function of elapsed cooldown time, mirroring the design used for `vlMGP`.

`vlMGPBaseRewarder._calExpireForfeit` correctly consumes this percent to compute the forfeited portion of a claim: [2](#0-1) .

However, `mWOMSVBaseRewarder._calExpireForfeit` — the function that gates every `_sendReward` call triggered from `getReward`/`getRewards` (via `MasterMagpie`, `onlyMasterMagpie`-gated) — ignores `mWOMSV.getRewardablePercentWAD(_account)` entirely and hardcodes `rewardableAmount = _amount`, making `forfeitAmount` always `0`: [3](#0-2) .

The claim path is: `getReward`/`getRewards` (`onlyMasterMagpie`, `updateReward`/`updateRewards`) → `_sendReward` → `_calExpireForfeit(_account, userRewards[...])` [4](#0-3) . Since `_calExpireForfeit` always returns `0`, `toSend = userRewards[...] - 0`, i.e. the user always receives 100% of accrued rewards, even if they are actively unlocking (`startUnlock` called, cooldown slot open, `getUserAmountInCoolDown > 0`).

No modifier, reentrancy guard, or reward-index update prevents this — the forfeiture logic itself is simply missing, unlike its `vlMGPBaseRewarder` counterpart. Existing checks (`onlyMasterMagpie`, `updateReward`) only gate *who* can call and *when* balances are synced; they do not compute or enforce forfeiture.

### Impact Explanation
This causes a permanent underpayment to the remaining (fully-locked) mWomSV holders: rewards that should have been redistributed to them as `queuedRewards`/`rewardPerTokenStored` increments (via `_queueNewRewardsWithoutTransfer`) are instead paid out in full to users who are already unlocking and reducing their commitment. This is a direct theft of the pro-rata forfeited share that should accrue to remaining lockers — matching the Immunefi "theft of unclaimed yield" / "direct theft of user funds" impact class, since it silently transfers value from long-term lockers to short-term/unlocking participants.

### Likelihood Explanation
Trivially and repeatably exploitable by any unprivileged mWomSV holder: (1) hold mWomSV balance (already locked via `lock`), (2) call `startUnlock` to open a cooldown slot for any nonzero amount, (3) wait for bonus rewards to accrue (`queueNewRewards` called by managers/reward flow), (4) call `getReward`/`getRewards` through `MasterMagpie`. No special capital beyond normal staking is needed, and it can be repeated on every reward accrual cycle for as long as a cooldown slot remains open (cooldown periods can be long, and `cancelUnlock`/re-`startUnlock` can be used to keep exploiting).

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder`'s implementation: compute `uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);` and set `rewardableAmount = _amount * rewardablePercentWAD / 1e18;` before computing `forfeitAmount = _amount - rewardableAmount`. This requires `ILocker` (or the appropriate interface used for the `mWOMSV` variable) to expose `getRewardablePercentWAD`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` per existing test harness.
2. User A locks mWomSV, User B locks mWomSV (equal amounts).
3. Fund bonus reward token via `queueNewRewards`; let `rewardPerTokenStored` accrue for both.
4. User A calls `startUnlock` for 100% of their locked balance, opening a cooldown slot (`userUnlockings[A][0]`), immediately reducing `getRewardablePercentWAD(A)` well below `1e18`.
5. Call `mWOMSVBaseRewarder.calExpireForfeit(A, rewardToken)` — assert it returns `0` (proving the bug) instead of `earned(A, rewardToken) * (1e18 - getRewardablePercentWAD(A)) / 1e18`.
6. Call `getReward(A, A)` via `MasterMagpie`; assert User A receives the full `earned` amount and `rewardInfo.queuedRewards`/`rewardPerTokenStored` for User B is not increased by any forfeited amount, confirming User B is denied their expected pro-rata share.
7. Compare against equivalent `vlMGPBaseRewarder` test where an unlocking `vlMGP` holder's `calExpireForfeit` returns a nonzero value, demonstrating the inconsistency and root cause.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
