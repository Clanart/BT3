### Title
Single unremovable reward token that reverts on transfer permanently freezes deposits/withdrawals for an entire pool's stakers - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.getReward()` loops unconditionally over every entry in `rewardTokens` and calls `safeTransfer` for any non-zero pending amount. There is no per-token error isolation and no way to remove a reward token from the array once added. `MasterMagpie` calls this function synchronously as part of every unprivileged user's deposit and withdraw flow, so a single reward token that becomes non-transferable (paused, blacklists the receiver, or otherwise reverts) permanently blocks every user of that pool from depositing, withdrawing, or harvesting — mirroring the reported "processReceipt" bug class where one failing item in a loop bubbles up and stalls the whole batch, except here the "batch" is every staker sharing the pool's `BaseRewardPool`.

### Finding Description
`getReward` iterates the full `rewardTokens` array and executes `IERC20(rewardToken).safeTransfer(_receiver, reward)` for each token with `reward > 0`, with no try/catch and no ability to skip a broken token: [1](#0-0) 

Reward tokens are appended to this array by `queueNewRewards`, which is `onlyManager`-gated but is invoked automatically as part of normal, unprivileged flows such as vote/bribe harvesting (e.g. `WombatStaking.vote` calling `queueNewRewards` for whatever bribe reward tokens the underlying voting/bribe system returns): [2](#0-1) [3](#0-2) 

Once a token is in `rewardTokens`, there is no removal mechanism, so any token that becomes permanently un-transferable (issuer pause, blacklist of the pool/receiver, or any other revert-on-transfer condition) stays in the array forever.

Every unprivileged deposit and withdraw call in `MasterMagpie` triggers `_harvestBaseRewarder`, which calls `getReward` on the pool's `BaseRewardPool` unconditionally: [4](#0-3) 

Because `_updateFor` (called by the `updateReward` modifier on every interaction) continuously accrues `userRewards[rewardToken][_account]` for all stakers based on their proportional share, essentially every active staker in the pool eventually accrues a non-zero balance of the broken token. Once that happens, their `getReward` call reverts on that token's `safeTransfer`, which reverts the entire `_harvestBaseRewarder` call, which reverts the entire `deposit`/`withdraw` transaction — with no way to bypass it, since `getReward` has no per-token skip logic and `rewardTokens` cannot be pruned.

### Impact Explanation
This is the reward-pool analog of the reported bug: a single failing element inside a loop causes the entire operation to fail, and because the failing element (the bad reward token) is never removed, the failure recurs on every subsequent attempt — a permanent freeze rather than a one-off revert. Unlike the original bug (transient batch retry), here it directly and permanently locks user principal (staked LP tokens) and any other legitimate, still-claimable reward tokens for every affected staker of the pool, since `withdraw` cannot complete without `getReward` succeeding for all tokens. This satisfies the "permanent freezing of funds" / "permanent freezing of unclaimed yield" bar.

### Likelihood Explanation
The precondition — an ERC20 reward token that starts reverting on transfer to some holder (compliance blacklist, pause, or any other revert path) after it has already been queued as a pool reward — is a realistic, well-documented failure mode for tokens like USDC/USDT-style assets, and the contract offers no mitigation (no try/catch, no removal function, no ability to specify which reward tokens to claim in `getReward`). Given `queueNewRewards` can be triggered as a side effect of routine vote/bribe operations, the set of reward tokens attached to a pool is not tightly curated, increasing the chance of an incompatible token ending up in the list.

### Recommendation
Wrap each reward token's transfer inside `getReward` (and `_getReward` in `BribeRewardPool`) in a try/catch or low-level call, logging/skipping failures instead of reverting the whole loop, and/or add an admin/manager function to deactivate or exclude a specific reward token from the payout loop without blocking withdrawals of principal and other healthy reward tokens.

### Proof of Concept
1. A reward token `T` is added to a pool's `BaseRewardPool.rewardTokens` via `queueNewRewards` (e.g. as a bribe reward token surfaced through `WombatStaking.vote`).
2. Token `T`'s issuer subsequently blacklists the `BaseRewardPool` contract itself (or the pool address is added to a sanctions list, or the token is paused) — a scenario external to the audited contracts but not requiring any privileged action within this codebase.
3. Any staker in the pool who has accrued a non-zero pending balance of `T` calls `withdraw`/`deposit`, which triggers `_harvestBaseRewarder` → `getReward`.
4. `getReward`'s loop reaches token `T`, `safeTransfer` reverts, and the entire transaction reverts.
5. Because `T` can never be removed from `rewardTokens`, this failure is permanent for every current and future staker who accrues `T`, freezing their staked principal and other reward tokens indefinitely.

        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
