### Title
Webhook HMAC verification lacks a domain separator, enabling cross-shop webhook forgery/replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` and the underlying `ShopifyApp::PayloadVerification#hmac_valid?` authenticate an incoming webhook solely by computing `HMAC-SHA256(secret, raw_body)` and comparing it to the `X-Shopify-Hmac-Sha256` header. The shop identity used by the app (`X-Shopify-Shop-Domain` header, exposed via `shop_domain`) is read independently and is never bound into the signed material. Because the app secret used to sign webhooks is shared across every shop that has installed a public app, any actor who can obtain one valid `(body, HMAC)` pair (e.g., by installing the app on their own store) can replay that exact pair against the webhook endpoint while forging the shop-domain header to name a different, victim shop. The signature passes verification even though it was never issued "for" that shop — this is precisely the missing-domain-separator class of bug described in the external report.

### Finding Description
`hmac_valid?` computes the digest only from `data` (the raw POST body) and the shared `ShopifyApp.configuration.secret`/`old_secret`: [1](#0-0) 

`WebhookVerification#verify_request` gates the whole action purely on this body/secret check: [2](#0-1) 

The `shop_domain` value used by the concern (and passed down as `shop:`/`shop_domain:` to job handlers) is taken straight from the `X-Shopify-Shop-Domain` request header, with no cryptographic link to the HMAC that was just verified: [3](#0-2) 

The generated webhook controller and jobs propagate this unauthenticated shop value directly into persistence and session logic: [4](#0-3) [5](#0-4) [6](#0-5) 

Because Shopify signs webhooks with the app's client secret — the same secret for every shop that installs the app — a valid `(raw_body, HMAC)` pair obtained from a webhook delivered to *any* shop (including one the attacker fully controls, such as a free development store) is a signature that will validate against `hmac_valid?` for *any other* shop domain too, since the shop domain is not part of the signed payload. There is no per-shop or per-installation "domain separator" mixed into the HMAC input, exactly analogous to the smart-contract report's missing `chain.id`/contract-address binding in `hashForKYC()`.

### Impact Explanation
An attacker replaying a captured, genuinely-signed webhook body with a forged `X-Shopify-Shop-Domain` header naming a victim shop that has the app installed can cause the app to execute webhook-driven business logic *as if it originated from the victim shop*:
- `AppUninstalledJob` looks up `Shop.find_by(shopify_domain: shop_domain)` and calls `shop.destroy`, letting the attacker trigger destruction of the victim shop's local install record using only a self-obtained signature.
- Any other generated job (`ShopRedactJob`, custom webhook jobs) calls `shop.with_shopify_session` for the victim's shop, executing whatever webhook-processing logic exists using the **victim's stored access token**, with attacker-controlled webhook body content.

This is a cross-shop authentication bypass: the "proof" (HMAC) an attacker legitimately possesses for their own shop is accepted as valid proof for an unrelated shop's identity, because the signature carries no domain-binding information.

### Likelihood Explanation
Reachability requires no privileges beyond the ability to install the target public app on any shop (trivial for a public/listed app, and free via a development store) to obtain one legitimate `(body, HMAC)` pair, plus the ability to send an unauthenticated POST to the app's public webhook endpoint with a spoofed header — both of which are directly reachable by an anonymous/unrelated-merchant HTTP client. No secret leakage or developer/operator access is needed.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is authenticated, rather than trusting a header that sits outside the HMAC. Concretely: after `hmac_valid?` succeeds, cross-check that the `shop_domain` from the header actually corresponds to a shop record whose install/session was established via OAuth/token-exchange for that domain and that the webhook's `shop_domain` matches an already-known, previously provisioned shop — but more fundamentally, do not treat the header-derived `shop_domain` as trustworthy on its own for driving destructive or session-bearing actions unless it's corroborated by out-of-band shop state. Where feasible, rely on the shop identity resolved by the underlying `ShopifyAPI::Webhooks::Registry`/session-lookup flow rather than a bare header value, and document for app developers that job handlers must not assume `shop_domain` is cryptographically authenticated per-shop.

### Proof of Concept
1. Attacker installs the target public Shopify app on a store they control (`attacker.myshopify.com`), which shares the app's single client secret with all other installs.
2. Attacker triggers (or waits for) any webhook delivery to their own store, capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` value.
3. Attacker sends this exact `(body, HMAC)` pair to the app's webhook endpoint, replacing the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com` (a real shop that has installed the app).
4. `PayloadVerification#hmac_valid?` recomputes `HMAC(secret, body)` — identical to what was sent — and verification passes. [1](#0-0) 
5. The controller dispatches to the configured job with `shop_domain: "victim-shop.myshopify.com"`, and generated job templates perform destructive/session-bearing actions (`shop.destroy`, `shop.with_shopify_session`) against the victim shop using attacker-supplied webhook content. [7](#0-6)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
