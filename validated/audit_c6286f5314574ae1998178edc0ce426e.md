### Title
Out-of-range blame participant causes a deterministic panic - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept arbitrary nonzero `Participant` values, but `blame_internal` later indexes `self.commitments` with the supplied `sender` without first checking that the sender belongs to the configured `1..=n` participant set. [1](#0-0) [2](#0-1)  A syntactically valid encrypted share message can therefore turn an invalid participant ID into a panic instead of an attribution or validation error.

### Finding Description
The blame path parses an untrusted `EncryptedMessage` containing a public encryption key, Schnorr proof of possession, and encrypted scalar payload. [3](#0-2)  After decryption succeeds and the decrypted bytes decode as a canonical scalar, `blame_internal` evaluates the share against `self.commitments[&sender]`. [4](#0-3)  `AdditionalBlameMachine::new` only populates commitments for participants `1..=n`, leaving no entry for a larger valid `Participant`. [5](#0-4)  Calling `blame` with `sender == Participant::new(n + 1)` consequently panics on the map index rather than rejecting the accusation. [2](#0-1) 

### Impact Explanation
A party able to submit or trigger adjudication of a blame statement can repeatedly crash the process evaluating it. The required attacker-controlled inputs are the accused `Participant`, recipient `Participant`, serialized `EncryptedMessage`, and optional ECDH proof accepted by the public `blame` API. [6](#0-5)  This is a remotely reachable denial of service against DKG fault adjudication and can prevent completion or coordinated handling of the protocol.

### Likelihood Explanation
The attacker must make the message pass PoP/decryption and deserialize to a scalar, but does not need a valid share commitment for the fake participant because the unchecked map access occurs during share verification. [7](#0-6)  A valid encrypted payload can be constructed to the recipient’s registered encryption key and bound to the forged sender ID in the message’s proof of possession. [8](#0-7)  Once supplied, the panic is deterministic.

### Recommendation
Validate both `sender` and `recipient` against the configured participant set before decryption or share verification. `blame_internal` should return a structured invalid-participant error or deterministically blame an invalid sender, and `AdditionalBlameMachine::new` should reject extraneous commitment-map entries as well as missing participants.

### Proof of Concept
```rust
// Assume:
// - `n` is the DKG participant count.
// - `commitments` contains valid messages for participants 1..=n.
// - `recipient` is a valid participant in 1..=n.
let fake_sender = Participant::new(n + 1).unwrap();

// Construct bytes for an EncryptedMessage whose:
// 1. `key` is a non-identity ephemeral public key,
// 2. `pop` proves possession of that key with `from = fake_sender`,
// 3. `msg` is a ChaCha20-encrypted canonical scalar addressed to the
//    recipient's registered encryption key.
let mut bytes = malicious_message_bytes.as_slice();
let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(&mut bytes, params)?;

// `proof` is the recipient-supplied ECDH proof allowing decryption.
let machine = AdditionalBlameMachine::<C>::new(context, n, commitments).unwrap();

// Decryption succeeds, the scalar decodes, then this indexes
// `self.commitments[fake_sender]`, which does not exist and panics.
machine.blame(fake_sender, recipient, msg, proof);
```

The vulnerable operation is the unchecked `self.commitments[&sender]` lookup in `BlameMachine::blame_internal`. [9](#0-8)
