### Title
Checking out a pull request never verifies the head SHA, allowing a silent bait-and-switch of the code a reviewer checks out - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The reported Solidity bug is a missing-bound-check issue: the `buy()` function computes an expected value (price) at call time but never verifies it against the value the user actually agreed to, letting an attacker change the underlying state between the user's decision and the state used to execute it. The Desktop analog is `AppStore._checkoutPullRequest` / `_findPullRequestBranch`, which resolve and check out a PR branch by **ref name** only, never pinning to or verifying the **commit SHA** (`pullRequest.head.sha`) that the app itself already fetched and that the user presumably reviewed.

### Finding Description
`PullRequestStore` stores each PR's head as `{ ref, sha, repoId }` [1](#0-0) , and the `PullRequestRef`/`PullRequest` models likewise carry both `ref` and `sha` [2](#0-1) .

However, when the user actually performs the checkout — via `Dispatcher.checkoutPullRequest`, the "Open PR from Desktop" deep link, or drag-and-drop cherry-pick — only `ref` (branch name) and `cloneURL` are passed through; `sha` is dropped entirely: [3](#0-2) [4](#0-3) 

`AppStore._checkoutPullRequest` delegates to `_findPullRequestBranch`, which adds/uses a remote for the fork, fetches it, and then simply resolves "whatever commit is currently at `<remote>/<headRefName>`" — there is no comparison to any expected SHA anywhere in this path: [5](#0-4) 

The fetch inside this function (`this._fetchRemote(repository, remote, ...)`) is a normal `git fetch` of the fork remote — it will happily pull down whatever the fork owner has pushed at that moment, with no fast-forward-only or SHA-pinning constraint, and then `_checkoutBranch` checks out the tip of that ref.

### Impact Explanation
Because a PR's fork is attacker-controlled (the PR author, by definition, controls that remote), the author can force-push new/different commits to the same branch name at any point between:
1. The moment a reviewer decides to check out the PR (e.g., clicking "Checkout" in Desktop's PR list, or clicking an `x-github-client://openRepo/...?pr=NNN` link generated from an earlier PR state), and
2. The moment Desktop actually executes `git fetch` + `git checkout` for that PR.

Desktop performs a live `_fetchRemote` at checkout time [6](#0-5)  and checks out whatever is fetched, without confirming it matches the SHA that was displayed to the user (e.g., in the PR list, PR quick-view, or the `IAPIPullRequest.head.sha` returned when the deep link was resolved via `fetchPullRequest`) [7](#0-6) . The reviewer ends up with the working directory checked out to code they never reviewed, silently. This can lead to running/reviewing/committing on top of injected malicious code — matching the "silent corruption of what the user commits/reviews" impact class, driven entirely by an untrusted, attacker-controlled Git remote (the fork), with no local access, credentials, or social engineering step beyond a normal PR checkout the user already intended to do.

### Likelihood Explanation
Likelihood is **low-to-medium**: it requires precise timing (the PR author force-pushing between the reviewer's decision and the actual fetch/checkout), which is plausible for automated/scripted attacks (e.g., a bot watching Desktop's `PullRequestList` API polling cadence or reacting to the deep-link click via GitHub.com's "Open in Desktop" button) but not trivially guaranteed for manual attackers. It mirrors exactly the "Alice sends tx, Bob frontruns, price changes before settlement" pattern in the source report, translated to "reviewer initiates checkout, author force-pushes, ref changes before settlement (fetch+checkout)."

### Recommendation
Pin PR checkouts to the expected commit, analogous to adding `maxPrice`/slippage protection in the original report:
- Thread `pullRequest.head.sha` through `_checkoutPullRequest`/`_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` and `Dispatcher.checkoutPullRequest`/`openPullRequestFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`.
- After fetching the fork remote, verify that the resolved branch/ref tip SHA equals the expected `sha`. If it differs, warn the user explicitly ("This pull request has new commits since it was loaded — do you want to check out the latest commit anyway?") rather than silently checking out the new tip.
- Consider checking out the commit by SHA (detached) as the default trusted target, with an explicit opt-in to follow the moving branch tip.

### Proof of Concept
1. Attacker forks the base repo and opens a PR with an innocuous head commit `A` on branch `feature`.
2. Victim reviewer, using GitHub Desktop, sees the PR (head sha `A`) in the PR list or clicks the "Open this in GitHub Desktop" link generated for that PR.
3. Before the reviewer's click is processed / before they click "Checkout" in the branch list, attacker force-pushes commit `B` (containing malicious build scripts, `.git/hooks`, or altered source) to `feature`.
4. Reviewer's Desktop client proceeds: `openPullRequestFromUrl` / `checkoutPullRequest` calls `_checkoutPullRequest` → `_findPullRequestBranch`, which does `getRemotes`, `addRemote`/`urlMatchesRemote`, then `_fetchRemote` and resolves `origin-fork/feature` — now pointing at `B` [8](#0-7) .
5. `_checkoutBranch` checks out commit `B` without ever comparing it to the `sha: A` that was originally fetched/displayed [9](#0-8) .
6. The reviewer's working directory and any build/run/commit they perform is now against attacker's swapped commit `B`, with no warning shown.

      pullRequest.head.repo.clone_url,

      pullRequest.head.gitHubRepository.owner.login,

  public async _checkoutPullRequest(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<void> {
    const prBranch = await this._findPullRequestBranch(
      repository,
      prNumber,
      headRepoOwner,
      headCloneUrl,
      headRefName
    )
    if (prBranch !== undefined) {
      await this._checkoutBranch(repository, prBranch)
      this.statsStore.increment('prBranchCheckouts')
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
