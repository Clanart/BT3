### Title
Hardcoded 1:1 pricing of the yield-bearing `stSTXbtc` token against the raw STX price, ignoring its real conversion/exchange rate — (File: `mainnet/contracts/utility/v0-1-data.clar`, `local-testing/contracts/utility/protocol-data.clar`, `mainnet/contracts/proposals/mainnet/v0-init.clar`)

### Summary
The Pendle bug class is "the protocol assumes a wrapped/derivative token is always worth exactly 1 unit of its underlying, ignoring the real conversion rate between them." Zest reproduces this exact class of bug for the `stSTXbtc` collateral asset: it is priced as if it were plain STX, with no ratio/conversion callcode applied, unlike its sibling derivative `stSTX`, which correctly applies a live exchange-rate transform.

### Finding Description
`stSTXbtc` is registered as a liquid-staking derivative described in code comments as "liquid staked STX with BTC yield" [1](#0-0) . Despite being a yield-accruing wrapped token, it is registered on-chain with `callcode: none`, meaning its USD value is computed purely from the raw STX/USD Pyth feed with no adjustment for its own redemption/exchange rate: [2](#0-1) 

This is visible directly in the price-lookup helper, where `stSTXbtc`'s price is computed as literally `get-pyth-price PYTH-STX` — the same STX price used for the base STX asset itself, with the accompanying comment even mismatching the code (comment says "BTC price", code uses the STX feed): [3](#0-2) 

Contrast this with the sibling derivative `stSTX`, which is explicitly given a `CALLCODE-STSTX` transform to account for its real staking exchange ratio via `call-ststx-ratio`/`resolve-ststx`, precisely because 1 `stSTX` is not always equal to 1 STX: [4](#0-3) [5](#0-4) 

The `CALLCODE-ZSTSTXBTC` transform applied to the vault-wrapped `zstSTXbtc` only multiplies by the vault's own liquidity index (`resolve-ztoken`) — it does not apply any stSTXbtc-to-STX conversion ratio, because none exists in the oracle logic: [6](#0-5) 

This is the same root cause pattern as the Pendle finding: a hardcoded pricing formula (`price(stSTXbtc) = price(STX)`) that assumes a 1:1 peg between a yield-bearing wrapped asset and its reference asset, instead of resolving the token's actual redemption/exchange rate the way the protocol correctly does for the analogous `stSTX` asset.

### Impact Explanation
`stSTXbtc` and its vault wrapper `zstSTXbtc` are enabled as collateral in the protocol (`(assets enable .vault-ststxbtc true)` / `(assets enable STSTXBTC-TOKEN true)`) [7](#0-6) . Any deviation between the true `stSTXbtc`:STX exchange rate and the hardcoded 1:1 assumption directly and proportionally corrupts the collateral USD valuation used for health-factor/LTV checks and liquidation thresholds. If the real exchange rate rises above 1 (as staking/yield derivatives typically do over time), the oracle undervalues the collateral (safety-conservative but degrades UX/capital efficiency); if the true rate diverges below the assumed 1:1 for any reason (e.g., yield mechanics unwinding, BTC-leg depegging from STX, or slashing), the oracle overstates collateral value, permitting under-collateralized positions to pass health checks, causing liquidation reverts, and exposing the protocol to bad debt — the same systemic mispricing / insolvency vector described in the Pendle SY≠YT report. This lands in the in-scope impact class of protocol insolvency / bad debt from mispriced collateral.

### Likelihood Explanation
This is a design/configuration gap reachable simply by holding `stSTXbtc`/`zstSTXbtc` as collateral under normal protocol operation — no attacker action or external oracle manipulation is required; the mispricing is baked into the oracle configuration itself (`callcode: none` for a yield-bearing token) and triggers on every price resolution for this asset.

### Recommendation
Introduce an `stSTXbtc`-specific conversion-rate callcode (analogous to `CALLCODE-STSTX`) that queries the actual redemption/exchange rate of `stSTXbtc` relative to STX (or its true underlying reference asset) before deriving its USD price, mirroring the `resolve-ststx` pattern already used for `stSTX`, instead of reusing the raw STX price unmodified.

### Proof of Concept
Not applicable — the issue is a static, always-active pricing-formula defect visible directly in `get-asset-price`/`resolve-callcode` and the asset-registration proposal scripts (no dynamic exploit path needed to demonstrate the mispricing exists).

```text
(define-private (resolve-ststx (p uint))
  (let ((ratio (unwrap! (call-ststx-ratio) ERR-ORACLE-CALLCODE)))
    (ok (mul-div-down p ratio STSTX-RATIO-DECIMALS))))

(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))

(define-private (resolve-callcode (p uint) (callcode (optional (buff 1))))
  (let ((cc (unwrap! callcode (ok p))))
    (if (is-eq cc CALLCODE-STSTX) (resolve-ststx p)
    (if (is-eq cc CALLCODE-ZSTX) (resolve-ztoken p STX)
    (if (is-eq cc CALLCODE-ZSBTC) (resolve-ztoken p sBTC)
    (if (is-eq cc CALLCODE-ZSTSTX) (resolve-ztoken (try! (resolve-ststx p)) stSTX)
    (if (is-eq cc CALLCODE-ZUSDC) (resolve-ztoken p USDC)
    (if (is-eq cc CALLCODE-ZUSDH) (resolve-ztoken p USDH)
    (if (is-eq cc CALLCODE-ZSTSTXBTC) (resolve-ztoken p stSTXbtc)
```
