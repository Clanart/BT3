### Title
Webhook shop identity (`shop_domain`) is not cryptographically bound to the HMAC signature, allowing cross-shop webhook forgery - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only authenticates the **request body**, not the `X-Shopify-Shop-Domain` header. The tenant identity (`shop_domain`) that downstream app code trusts to know "which shop this webhook is for" is read straight from that unauthenticated header, so a valid HMAC on one shop's webhook body can be replayed with a different shop-domain header and still pass verification — exactly the same class of bug as the analog report: a value asserted to identify the acting party (`srcChainSender_` in the source report, `shop_domain` here) is propagated and trusted by downstream privileged logic without being bound to the cryptographic proof that authenticated the message.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes the HMAC over `request.raw_post` only: [1](#0-0) 

`WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` — again, only the body is verified — and separately exposes a `shop_domain` helper that reads the shop identity directly from an unsigned header: [2](#0-1) 

Because the HMAC is computed with the app's client secret and does not incorporate the `X-Shopify-Shop-Domain` header (or any other shop-binding value) into the signed data, any request whose body+HMAC pair was legitimately issued by Shopify for shop A can be re-sent by the operator of shop A to the app's webhook endpoint with the header rewritten to shop B's domain, and `verify_request` will still accept it as authentic. The `shop_domain` value returned by this concern is documented as the trust source apps should use when dispatching background jobs: [3](#0-2) 

Generated job templates for privileged operations (e.g. app uninstall) look up the tenant record purely from this shop-domain value and perform destructive actions on it: [4](#0-3) 

This is directly analogous to the `TapiocaOmnichainSender` bug: there, `srcChainSender_` was recorded as "the initiator" during message crafting but was not re-derived/verified on the receiving side against the actual authorized party, letting an attacker substitute a victim's identity into a signed message and have it trusted downstream. Here, `shop_domain` is treated as "the shop this signed webhook is for" but is never bound into what the signature actually authenticates, letting an attacker substitute an arbitrary victim shop domain onto a signature they legitimately possess.

### Impact Explanation
An attacker who is a legitimate (even free/trial) merchant installing the target app receives genuine, validly-HMAC'd webhooks from Shopify for their own shop. Because the shop identity is not covered by the signature, the attacker can replay that valid body/HMAC pair while swapping the `X-Shopify-Shop-Domain` header to point at any other installed shop. The app backend will accept the request as an authentic webhook and process it under the victim shop's tenant context. Depending on which webhook job is wired up, this enables cross-shop state corruption (e.g., writing attacker-controlled order/product/customer data into the victim's shop records) or destructive actions such as triggering `app/uninstalled` handling (`shop.destroy`) against the victim shop using the attacker's own valid signed payload. This is a cross-shop access / accepted forged signed request bug.

### Likelihood Explanation
Likelihood is high for any app relying on the gem's stock webhook verification and the documented `shop_domain` pattern: no secrets need to be leaked, the attacker only needs their own valid app installation (which is the normal, unprivileged state of any merchant), and the attack is a simple HTTP replay with one header modified. The `X-Shopify-Hmac-Sha256` and `X-Shopify-Shop-Domain` headers are both attacker-controllable in a raw HTTP request to the webhook endpoint; only the body is checked.

### Recommendation
Bind the shop identity into what is cryptographically verified before it is trusted for tenant lookups:
- Compute or verify the HMAC over a canonical representation that includes the shop domain (or otherwise reject/ignore the `X-Shopify-Shop-Domain` header and derive the shop strictly from a verified source, e.g. by decoding it from the signed webhook body payload rather than the header), and
- Ensure any generated job/template that uses `shop_domain` (or `webhook_request.shop`) for privileged, tenant-scoped operations only accepts a shop value that was part of the authenticated payload, not an independent unsigned header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a real webhook delivery from Shopify (e.g. `orders/create`), including its `raw_post` body and the valid `X-Shopify-Hmac-Sha256` header value (both legitimately produced by Shopify using the app's secret).
2. Attacker crafts a new POST to the app's webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks the body against the secret — this passes because the body/HMAC pair is genuinely valid. [5](#0-4) 
4. The app-level webhook handler reads `shop_domain` (or `webhook_request.shop`) — now `victim-shop.myshopify.com` — and enqueues/executes tenant-scoped logic (e.g., `Shop.find_by(shopify_domain: shop_domain)` followed by destructive or data-mutating operations) against the victim shop's record using attacker-controlled webhook content. [6](#0-5)

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
