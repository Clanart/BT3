## Analysis

The reported Sherlock issue is about a manager-controlled percentage parameter (`raiseTargetPercentage`) that can be left at its zero default and is then used unchecked in downstream arithmetic, silently breaking the intended behavior of a permissionless function (`raiseAssetTargets()`).

Kaia's KIP-71 dynamic base-fee parameter set contains the same bug-class: an asymmetric/missing zero-validation on a governance-configurable scaling parameter that is later used as a **divisor**, but unlike its sibling parameter it has no non-zero check at all.

### Root cause

In `kaiax/gov/param.go`, the `Kip71BaseFeeDenominator` parameter explicitly rejects zero: [1](#0-0) 

But the sibling parameter `Kip71GasTarget`, which is used as a divisor in the exact same base-fee formula, uses `noopFormatChecker` and has **no zero-value validation**: [2](#0-1) 

That unchecked `GasTarget` value flows straight into `NextMagmaBlockBaseFee`, where it is used both as a comparison target and, critically, as a division divisor in `big.Int.Div`: [3](#0-2) 

Specifically:
- Line 90: `if parentGasUsed == gasTarget` — only true when a block used exactly 0 gas.
- Line 92-103 (`parentGasUsed > gasTarget` branch): `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` — if `gasTarget == 0`, and `parentGasUsed > 0` (true for essentially any block that includes at least one transaction), this becomes `Div(x, 0)`, which panics in Go's `math/big` package ("division by zero").

There is a defensive fallback only for `BaseFeeDenominator == 0` (line 71-76 of the same file, `params/kip71_config.go`), showing the pattern was recognized for that parameter but was never mirrored for `GasTarget`, exactly the same class of oversight described in the external report (one related knob validated, the sibling knob left unchecked).

### Reachability

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked by every full node and consensus node during ordinary block assembly and header verification for every block after the Magma hardfork. Once `reward`/`governance.kip71gastarget` is set to `0` (via a governance vote — the same "before the manager configures it" scenario as the raiseTargetPercentage report, since there is no validation forcing it non-zero at the param layer), **any subsequent transaction that causes a block to use more than 0 gas** (i.e., virtually any submitted transaction) will drive `parentGasUsed > gasTarget(=0)`, causing every node computing/verifying the next block's base fee to panic on division by zero. This halts block production/verification network-wide — a state-transition/consensus liveness failure triggered by an ordinary, permissionless transaction submission once the parameter is misconfigured.

### Title
KIP-71 `GasTarget` governance parameter lacks non-zero validation, causing division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`)

### Summary
`Kip71GasTarget` is accepted by the governance parameter validator with a `noopFormatChecker`, unlike its sibling `Kip71BaseFeeDenominator` which explicitly rejects `0`. `NextMagmaBlockBaseFee` divides by `gasTarget` when `parentGasUsed > gasTarget`, so a `GasTarget` of `0` causes a `big.Int` division-by-zero panic during ordinary block base-fee computation.

### Finding Description
`kaiax/gov/param.go`'s `Kip71GasTarget` entry sets `FormatChecker: noopFormatChecker`, meaning any `uint64` value including `0` passes validation and can become the effective `reward.kip71gastarget`/`governance.kip71.gastarget` chain config value. This value is consumed by `KIP71Config.NextMagmaBlockBaseFee` in `params/kip71_config.go`, where `gasTarget := kc.GasTarget` is used unguarded as a divisor at `x.Div(x, new(big.Int).SetUint64(gasTarget))` in the "gas used above target" branch. The code base already demonstrates awareness of this exact hazard for the sibling `BaseFeeDenominator` parameter (explicit `if kc.BaseFeeDenominator == 0` fallback and non-zero `FormatChecker`), but the same protection was never added for `GasTarget`.

### Impact Explanation
If `GasTarget` is ever configured to `0` (governance misconfiguration, default-omission, or a race before governance sets it — analogous to the report's "not guaranteed to be set by the time it's used"), then the very next block that consumes any gas (`parentGasUsed > 0`, true for nearly all real blocks) will cause every consensus/full node computing or verifying `NextMagmaBlockBaseFee`/`VerifyMagmaHeader` to panic. This is a chain-halting, consensus-wide state-transition failure — not merely a functional inconvenience — since header verification is mandatory for block acceptance across all node types.

### Likelihood Explanation
Likelihood depends on `GasTarget` actually reaching `0`, but the parameter is validated by `noopFormatChecker` with no defense-in-depth at the point of use for the "above target" branch (only the "== target" and "below target" branches happen to be less immediately catastrophic in some sub-cases). Given the codebase's demonstrated practice of guarding `BaseFeeDenominator` against zero, the absence of the equivalent guard for `GasTarget` indicates this is an overlooked validation gap rather than an intentional allowance.

### Recommendation
Add the same defense used for `BaseFeeDenominator` to `GasTarget`:
1. In `kaiax/gov/param.go`, change `Kip71GasTarget`'s `FormatChecker` from `noopFormatChecker` to a checker that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`).
2. As defense-in-depth, in `params/kip71_config.go`'s `NextMagmaBlockBaseFee`, guard against `gasTarget == 0` similarly to the existing `BaseFeeDenominator == 0` fallback before performing the division.

### Proof of Concept
1. Governance sets `governance.kip71.gastarget` (or `reward.kip71gastarget`) to `0` — this passes validation because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go` lines 324-334).
2. Any subsequent block includes at least one ordinary transaction, so `parentHeaderGasUsed > 0`.
3. On the next block, `NextMagmaBlockBaseFee` computes `parentGasUsed = min(parentHeaderGasUsed, upperGasLimit)` (> 0), takes the `parentGasUsed > gasTarget` branch (`gasTarget == 0`), and executes `y := x.Div(x, new(big.Int).SetUint64(0))`, which panics with "division by zero" in every node that calls `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`, halting block processing network-wide.
