### Title
Unvalidated `sender`/`recipient` indexes in PedPoP blame handling cause a reachable panic and abort of the protocol - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Bitcoin Core bug class (CVE-2024-35202) is "untrusted message reaches an internal assertion, crashing the node". In Serai, the PedPoP DKG's blame-evaluation path indexes `HashMap`s by attacker-chosen `Participant` values without bounds checks. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` panic on any participant index outside `1..=n`, turning a malformed blame accusation into a process abort — the same attacker-reachable-assertion DoS shape.

### Finding Description
`AdditionalBlameMachine::blame` / `BlameMachine::blame` are public APIs explicitly documented as usable by non-participants to adjudicate blame accusations (`crypto/dkg/pedpop/src/lib.rs:639-648`, `674-682`). They forward caller-supplied `sender` and `recipient` `Participant` values into `blame_internal` and `Decryption::decrypt_with_proof`, which perform unchecked indexing:

- `self.enc_keys[&decryptor]` in `decrypt_with_proof` (`encryption.rs:388`) — panics if `recipient` is not one of the `1..=n` registered participants.
- `self.commitments[&sender]` in `blame_internal` (`lib.rs:599`) — panics if `sender` is outside `1..=n` (e.g., `Participant(n+1)` or any index whose commitment message was absent).

`Participant::new` only rejects zero (`crypto/dkg/src/lib.rs:29-35`); no upper bound is enforced on the blame path. An accuser who crafts an accusation naming a `sender`/`recipient` outside the actual participant set — which any party broadcasting a blame claim can do — causes every honest evaluator running `blame` to panic rather than return a `Participant` verdict. The `msg.pop.verify` gate (`encryption.rs:374-379`) does not help: the accuser can encrypt a share to a key they control, producing a valid PoP for arbitrary `sender`/`msg` bytes before the indexing is reached.

Note: this requires the attacker to be (or impersonate) a DKG participant issuing a blame accusation; the accusation itself is the untrusted public input consumed by any third-party evaluator, which is exactly the role `AdditionalBlameMachine` exists for.

### Impact Explanation
A single crafted blame message crashes (panic = abort in `panic = abort` builds, or unwinds out of the consensus loop) every node evaluating it, halting DKG completion/blame resolution — a remote denial of service directly analogous to the `blocktxn` assertion-exit.

### Likelihood Explanation
Blame accusations are a designed public input after a failed `calculate_share`; a faulty participant has both motive (evade accountability) and a trivial trigger (one out-of-range `u16`).

### Recommendation
In `Decryption::decrypt_with_proof` and `blame_internal`, replace `map[&key]` indexing with `map.get(&key)` and return `DecryptionError::InvalidProof` / a defined faulty-party result (or reject non-participant indexes up front in `blame`).

### Proof of Concept
Build a valid `AdditionalBlameMachine` via `AdditionalBlameMachine::new(context, n, commitment_msgs)`. Then call `blame(sender = Participant::new(n + 1).unwrap(), recipient, msg_with_valid_pop, Some(proof))`: `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` or `blame_internal` indexes `self.commitments[&sender]`, producing `thread panicked: key not found` instead of a blame verdict.
