### Title
IntentGatewayV2 (Tron) escrow accounting uses nominal `order.inputs[i].amount` instead of actual `transferFrom`-received balance, letting fee-on-transfer/deflationary ERC-20 inputs over-credit escrow relative to real token holdings - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` credits the order's escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived purely from the user-declared `order.inputs[i].amount` minus the protocol fee, without ever measuring the gateway's actual token balance before/after the `safeTransferFrom` call. [1](#0-0) 

### Finding Description
The mainline EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`) explicitly guards against tokens that deliver less than the requested amount (fee-on-transfer / deflationary tokens) by snapshotting the gateway's balance before and after the transfer and mutating `order.inputs[i].amount` to the **actual received** amount before it is used to compute the commitment hash and escrow credit: [2](#0-1) 
This is validated by dedicated fee-on-transfer tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) which assert `_orders[commitment][token]` always equals the *actually received* balance. [3](#0-2) 

The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not carry this guard. In the non-predispatch path it calls:
```
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is computed earlier purely as `originalAmount - protocolFee` from the **declared** `order.inputs[i].amount`, using no balance check at all: [4](#0-3) [5](#0-4) 
The predispatch branch does compare `balance` against `requiredAmount` and emits `DustCollected` for *excess* dust, but it still credits `_orders[commitment][token] += reducedInputs[i].amount` (the declared, fee-reduced amount), not the balance actually swept into escrow: [6](#0-5) 

If any TRC-20/ERC-20 token integrated with this deployment takes a transfer fee, rebases downward, or otherwise delivers less than the nominal `transferFrom` amount, the contract's internal escrow ledger `_orders[commitment][token]` will be **larger than the token balance actually held by the gateway** for that commitment. Because a solver later fills the order and is paid out based on the ledger value (not the real balance), the accounting becomes structurally insolvent: cumulative escrow liabilities recorded across multiple orders can exceed the gateway's real token balance.

### Impact Explanation
This maps directly to the Hyperbridge Impact Gate's "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" and "stealing or loss of funds" categories. An unprivileged user placing an order with a deflationary/fee-on-transfer token inflates their own order's recorded escrow relative to what they actually deposited. When solvers fill orders and the contract disburses/refunds based on `_orders[commitment][token]`, the gateway can end up paying out (to solvers, or refunding to users on cancellation) more than the real token balance backing that specific commitment — draining the pooled balance and causing legitimate, unrelated orders in the same token to become unfillable or under-collateralized (fund lock/loss for other users). This is a direct false-state-acceptance-style bug at the escrow layer: the "trusted" recorded value diverges from the token's true custodial balance, exactly analogous to the reported `_cachedTotalUnderlying` overstatement from slippage in the external report.

### Likelihood Explanation
The bug triggers deterministically, without any privileged actor, relayer, or prover assumption — merely by placing an order with an ERC-20 that has any transfer-fee/deflationary mechanic (a broad and common token category on production chains, and one the codebase's own EVM variant explicitly anticipates and hardens against). No malicious peer, governance, or leaked key is required; a single unprivileged `placeOrder` call from any user is sufficient to desynchronize the ledger from real custody. Likelihood is high if this Tron deployment accepts arbitrary/permissionless input tokens (as the mainline EVM version does), since the divergence directly parallels a defense the team explicitly built and tested for the sibling contract.

### Recommendation
Port the same actual-balance-based accounting used in `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot the gateway's (or dispatcher's) token balance immediately before and after each `safeTransferFrom`/predispatch sweep, mutate `order.inputs[i].amount` to the measured delta, and derive `reducedInputs`/`commitment`/`_orders[...]` credits from that measured amount rather than the caller-declared nominal amount, for both the predispatch and non-predispatch code paths.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a TRC-20 token that charges e.g. a 1% transfer fee (mirroring `FeeOnTransferToken` used in the EVM test suite: `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2501+).
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e18` of that token, no predispatch.
3. `safeTransferFrom` moves only 990e18 into the gateway (1% fee burned/redirected), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from the original `1000e18` (minus any protocol fee) — i.e., a value up to ~1000e18, not the 990e18 actually held.
4. Repeat with additional orders in the same token; the sum of `_orders[...]` entries for that token across commitments now exceeds `IERC20(token).balanceOf(gateway)`.
5. When solvers/`fillOrder`/refund flows pay out based on the ledger, the last order(s) to settle cannot be paid the recorded escrow amount from the real balance, causing fund loss/lock for a legitimate order holder — while the token issuer of the deflationary token (or a colluding user) has effectively extracted value the contract believed it still custodied.

(Note: the exact `fillOrder`/refund payout code paths in the Tron file were not fully retrieved before the tool budget was exhausted; the finding is based on the confirmed escrow-crediting logic in `placeOrder`, cross-validated against the sibling EVM contract's explicit fix and tests for the identical bug class. A Devin session with file access should confirm the downstream payout function's exact behavior to finalize severity.)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
