### Title
Payout OP_RETURN operator attribution is unauthenticated, letting an operator be reimbursed for a withdrawal it never funded - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
The `payout_tx` created by `create_payout_txhandler` carries the "who fronted this withdrawal" claim in a plain `OP_RETURN` output containing an operator's x-only pubkey. The user's signature over the transaction only uses `SIGHASH_SinglePlusAnyoneCanPay`, which commits solely to the withdrawal input and the single payout output at index 0 - it does **not** cover the OP_RETURN output or any inputs added for funding. Anyone who obtains this signature (which is submitted on-chain, in the clear, as part of the public Citrea `safeWithdraw` call) can build their own version of the payout transaction, add whatever inputs they like to fund it, and freely choose the operator pubkey embedded in the OP_RETURN. The chain-scanning logic in `update_finalized_payouts` (`core/src/verifier.rs`) blindly trusts this OP_RETURN value to decide which operator "fronted" the withdrawal and is therefore eligible for reimbursement, and `PayoutCheckerTask` / `is_kickoff_malicious` act on that unauthenticated attribution to trigger automatic reimbursement.

### Finding Description
`create_payout_txhandler` builds the payout transaction as: [1](#0-0) 

Note that the OP_RETURN output containing `operator_xonly_pk` is added as an unsigned/plain output, and the user's witness only covers input 0 via key-spend (`SIGHASH_SinglePlusAnyoneCanPay`, per the `WithdrawParams.input_signature` doc comment): [2](#0-1) 

`SinglePlusAnyoneCanPay` only binds the signature to the single input being spent and to the output at the same index (index 0, the user's payout). It leaves the anchor output and, critically, the OP_RETURN operator-attribution output completely free to be set by whoever assembles the final transaction - including any additional funding inputs.

This user signature is not a protocol secret: it is submitted to the public Citrea `safeWithdraw` contract call as part of registering the withdrawal, e.g.: [3](#0-2) 

Once this becomes visible (any Citrea/L2 observer can read the calldata), any unprivileged party can reconstruct a valid payout transaction: reuse the signed input+output0, add their own funding input(s) to cover the payout+fees, and set the OP_RETURN's `operator_xonly_pk` to *any* value they choose - e.g., a real operator's key, without that operator spending a single sat.

Once this forged payout transaction confirms, the verifier's Bitcoin-syncer logic determines the "payer" purely from the OP_RETURN bytes, with no cryptographic check that the named operator actually funded the transaction: [4](#0-3) 

That attribution is persisted and later trusted: [5](#0-4) 

The operator's own automated background task then finds this unhandled payout keyed solely on its own xonly pubkey and proceeds to claim reimbursement from the deposit/vault flow, with no verification that it actually funded the payout: [6](#0-5) 

Separately, `is_kickoff_malicious` only checks that the kickoff's `operator_xonly_pk` equals the OP_RETURN value recorded for the payout - again, no check that the named operator's funds were actually used to pay the user: [7](#0-6) 

**Binding broken:** *the operator credited (OP_RETURN pubkey, unauthenticated) versus the party that actually funded the withdrawal (whoever supplied the extra BTC inputs to the payout tx).* Before the attack, this equality would normally hold because only the fronting operator (via its own RPC `withdraw`/`internal_withdraw`, funded through its own wallet) constructs the payout tx. After the attack, an unprivileged party can fund the payout themselves yet write an arbitrary operator's pubkey into the OP_RETURN, permanently decoupling "who paid" from "who is credited."

### Impact Explanation
This maps to the Critical impact category: *"an operator reimbursed for a payout it never funded."* The reimbursement mechanism ultimately allows the credited operator to reclaim the corresponding bridge-deposit value from the vault-backed round/kickoff flow. If an attacker funds the payout tx with non-operator BTC but writes a chosen (possibly self-controlled) operator's pubkey into the OP_RETURN, that operator's automation (`PayoutCheckerTask`) will treat the withdrawal as fronted by itself and proceed through `handle_finalized_payout`/`end_round`, eventually reclaiming bridge-vault value it never spent. This is a direct value-extraction path: bridge deposit funds leave the vault/round custody to reimburse a party that did not front the corresponding withdrawal.

### Likelihood Explanation
The only prerequisite is observing a valid `WithdrawParams.input_signature`, which is not confidential - it is submitted publicly to the Citrea L2 contract as part of the standard withdrawal-registration flow (`safeWithdraw`). No verifier/operator/aggregator role, key compromise, or majority stake is required; any party capable of reading an L2 transaction and broadcasting a Bitcoin transaction (funding it with their own BTC) can perform the attack. This makes it a directly reachable, unauthenticated exploitation path.

### Recommendation
Bind the operator attribution cryptographically to the actual funding party instead of trusting a free-form OP_RETURN field:
- Extend the sighash coverage (e.g., use `SIGHASH_All`/`SIGHASH_AllPlusAnyoneCanPay` with a Taproot-friendly scheme, or add a covenant/commitment) so the OP_RETURN operator pubkey output is committed to by a signature tied to the operator's own key, not left as unauthenticated data any funder can set.
- Alternatively, require the credited operator's own signature (or N-of-N/verifier co-signature) authorizing that specific operator as the payer for the specific withdrawal, and validate that signature in `update_finalized_payouts`/`is_kickoff_malicious` before trusting `payout_payer_operator_xonly_pk`.
- Reject reimbursement flows where the OP_RETURN attribution cannot be tied to inputs actually controlled/spent by the credited operator's wallet.

### Proof of Concept
1. User initiates a withdrawal and signs `WithdrawParams` with `SIGHASH_SinglePlusAnyoneCanPay` over the withdrawal input and payout output only (per `create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407-436`).
2. User (or attacker observing it) submits this `input_signature` publicly via Citrea's `safeWithdraw` (`core/src/test/common/citrea/mod.rs:415-443`), making the signature public.
3. Attacker (not a registered operator, or an attacker-controlled operator) builds their own payout transaction reusing the signed input/output0, adds their own funding input(s) to cover the payout amount + fee, sets the anchor output freely, and sets the OP_RETURN to an arbitrary operator's `xonly_pk` of their choosing.
4. Attacker broadcasts and confirms this transaction on Bitcoin.
5. The verifier's chain scan (`update_finalized_payouts`, `core/src/verifier.rs:2311-2350`) parses the OP_RETURN and records that operator as `payout_payer_operator_xonly_pk` for the withdrawal in the DB (`update_payout_txs_and_payer_operator_xonly_pk`, `core/src/database/verifier.rs:198-251`).
6. The named operator's own `PayoutCheckerTask` (`core/src/task/payout_checker.rs:39-106`) finds this "unhandled payout" credited to itself and proceeds through the kickoff/reimbursement flow, which `is_kickoff_malicious` (`core/src/verifier.rs:1857-1890`) will accept because the OP_RETURN pubkey matches the kickoff's operator pubkey - despite that operator never having funded the user's payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
