### Title
Unauthenticated `ReceivedOutput` bytes can report nonexistent or inflated inputs and trigger unusable signatures - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts the scalar offset, claimed `TxOut`, and claimed `OutPoint` as three independent, attacker-controlled fields, without proving that the outpoint actually resolves to that output. [1](#0-0)  `SignableTransaction::new` then trusts both the claimed value and outpoint when constructing the transaction. [2](#0-1)  This is analogous to using the wrong authority for a transfer: the spend authority is derived from attacker-supplied account metadata rather than a chain-authenticated UTXO.

### Finding Description
A `ReceivedOutput` is the wallet’s representation of a spendable output, including its key offset, output data, and outpoint. [3](#0-2)  Its deserializer accepts those components independently from a byte stream. [1](#0-0) 

`SignableTransaction::new` uses the attacker-controlled `output.value` as available input value and the independently supplied `outpoint` as the transaction input. [2](#0-1)  `SignableTransaction::multisig` verifies only that the claimed script corresponds to `keys.offset(offset)`; it does not verify that the referenced outpoint contains that script or value. [4](#0-3) 

During signing, the fabricated `TxOut` is committed through `Prevouts::All`, so the produced signatures are bound to the attacker’s false prevout data rather than the actual UTXO. [5](#0-4)  The resulting transaction is then completed and returned normally by the threshold-signing machine. [6](#0-5) 

### Impact Explanation
An unprivileged party who can feed serialized bytes to `ReceivedOutput::read` can cause the wallet to report funds as received and spendable when no corresponding UTXO exists, or when the real UTXO has a different script or amount. [7](#0-6)  The threshold participants can consequently be induced to generate a signature for a transaction that cannot spend the claimed funds. [5](#0-4) 

This does not forge authority over an unrelated valid UTXO because Bitcoin verification uses the actual spent output, but it does create false spendable-balance state and can cause threshold signing rounds to produce transactions doomed to rejection. [8](#0-7)  Repeated forged records can repeatedly consume signing resources or leave accounting permanently dependent on outputs that cannot be spent.

### Likelihood Explanation
The attack requires only control of bytes supplied to `ReceivedOutput::read`; no private key, validator privilege, or malformed cryptographic encoding is required. [1](#0-0)  The forged object passes the wallet’s ownership check whenever the embedded script is any registered P2TR script for the supplied offset, including offset zero and the wallet’s own group key. [4](#0-3) 

### Recommendation
Treat `ReceivedOutput` as an authenticated chain-derived object rather than a self-authenticating portable claim. [9](#0-8)  Constructors should bind the offset, `TxOut`, and `OutPoint` to evidence from the containing transaction or block, such as a full transaction plus vout, a merkle proof, or verified chain data. [9](#0-8)  If `ReceivedOutput::read` is retained for trusted persistence, it should be explicitly separated from untrusted-input APIs and `SignableTransaction::new` should require chain-validated inputs. [10](#0-9)

let signable = SignableTransaction::new(
    vec![claimed],

    None,
    None,

// Succeeds because only script = key + offset is checked.
