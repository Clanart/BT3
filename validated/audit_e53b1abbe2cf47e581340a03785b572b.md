### Title
Unbounded-capacity allocation in `ThresholdKeys::read` enables memory-amplification denial of service - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `n` (the participant count) directly from attacker-controlled bytes and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficients — before validating `n` against `ThresholdParams` and before confirming the input actually contains `n` scalars. A maliciously crafted serialization declares `n = 65535` with only a handful of bytes present, forcing a multi-megabyte allocation per call. This is the same defect class as the py7zr decompression bomb: consumption of resources is driven by a declared (not actual) size, with no cumulative limit.

### Finding Description

In `ThresholdKeys::read` [1](#0-0) , the flow is:

1. `id_len` + `C::ID` checked against the curve ID (attacker supplies the correct constant).
2. `t`, `n`, `i` are each read as raw `u16`s. `Participant::new` validates `i`, but `t` and `n` are **not** validated here — `ThresholdParams::new(t, n, i)` is only called later inside `ThresholdKeys::new` at line 625-630.
3. If the interpolation tag byte is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` at line 608 and only then begins reading `n` scalars via `C::read_F`.
4. If the reader hits EOF, `read_F` errors — but the oversized allocation has already occurred, and a streaming reader (e.g. a network socket `Read` impl) can hold the allocation alive indefinitely by dribbling bytes.

A payload of `C::ID.len() + 4 + 6 + 1` bytes (~20 bytes for Ristretto/Secp256k1) triggers `Vec::with_capacity(65535)` of a 32-byte field element — roughly 2 MiB of heap allocation before any element is read, an amplification of ~100,000:1. By contrast, the analogous `Vec::with_capacity` in `musig::musig` (crypto/dkg/musig/src/lib.rs:140-142) is sized from an already-materialized `keys` slice, so it cannot amplify; `ThresholdKeys::read` is the one place an unprivileged party reaches this pattern via untrusted bytes.

For comparison, `SchnorrAggregate::read` [2](#0-1)  also reads a `u32` count but pushes elements one at a time with no pre-allocation, so memory consumed is bounded by bytes actually present — `ThresholdKeys::read` lacks exactly this property.

### Impact Explanation

An unprivileged party who can cause a validator/processor to call `ThresholdKeys::read` on their bytes (e.g. malformed key material supplied during DKG/multisig setup flows, backups, or peer-delivered payloads) can force each call to allocate ~2 MiB per ~20-byte message. Concurrent requests multiply the pressure: memory exhaustion / OOM-kill of the node process, denying service, at trivial bandwidth cost. Consistent with the reference advisory's Medium severity — availability impact only, no key or signature integrity compromise.

### Likelihood Explanation

Reachability depends on integrators passing untrusted bytes into `ThresholdKeys::read`; the prompt's threat model explicitly includes this reader as an entry point for untrusted data. No valid signatures, proofs, or threshold participation are needed — the allocation happens before `ThresholdParams::new` can reject the params and before any `read_F` succeeds, so even a truncated garbage stream triggers it. Exploitation requires only bytes, no cryptographic validity.

### Recommendation

Validate `n` before allocating: deserialize `t`, `n`, `i`, then immediately run `ThresholdParams::new(t, n, i)` and move the `Vec::with_capacity` after successful parameter validation. Additionally, cap the pre-allocation or grow the vector incrementally (push into `Vec::new()` per successful `read_F`) so memory consumed is proportional to bytes actually received — mirroring the pattern used in `SchnorrAggregate::read` and the 1 KiB-chunked read already used in `Call::read` (networks/ethereum/src/machine.rs:51-60) with its explicit "claimed 4 GB for 4 bytes" mitigation comment.

### Proof of Concept

```rust
use std::io;
use frost::{curve::Ristretto, ThresholdKeys};

fn main() {
    // Minimal malicious serialization:
    //   id_len(u32) || C::ID || t(u16)=1 || n(u16)=0xffff || i(u16)=1 || interpolation=0(Constant)
    let mut bomb = Vec::new();
    bomb.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
    bomb.extend(Ristretto::ID);
    bomb.extend(&1u16.to_le_bytes());        // t
    bomb.extend(&u16::MAX.to_le_bytes());    // n = 65535 -> Vec::with_capacity(65535)
    bomb.extend(&1u16.to_le_bytes());        // i
    bomb.push(0);                            // Interpolation::Constant
    // No scalar bytes follow.

    // ~20-byte input forces ~2 MiB allocation before read_F fails on EOF.
    let _ = ThresholdKeys::<Ristretto>::read(&mut bomb.as_slice());
}
```

Observed behavior: `Vec::with_capacity(usize::from(65535))` at crypto/dkg/src/lib.rs:608 reserves ~2 MiB (65535 × `size_of::<C::F>()`) even though the reader contains zero scalars; the error path only unwinds after the allocation. Looping this from a remote caller yields sustained heap pressure disproportionate to input size.
