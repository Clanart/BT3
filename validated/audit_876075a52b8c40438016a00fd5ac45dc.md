### Title
Copilot conflict resolution silently corrupts non-UTF-8 byte sequences when reading/splicing/writing conflicted files - (File: app/src/lib/copilot-conflict-context.ts)

### Summary
The Solidity bug report is about an unnecessary decimal round-trip conversion (`18 → assetDecimal → 18`) that silently produces a wrong number instead of preserving the original value. The Desktop analog is a lossy round-trip **encoding** conversion: a conflicted file's raw bytes are read as `'utf8'`, spliced with model-generated resolution text, and written back as `'utf8'`, with no validation that the original bytes were valid UTF-8 in the first place. Just as the contract's `changeDecimals(..., 18, assetDecimal)` truncated precision and produced `0` for small amounts, Node's `'utf8'` decoder silently replaces any malformed byte sequence with the U+FFFD replacement character, and re-encoding writes back a different byte stream than what was originally on disk — permanently and silently altering file content that the user then stages and commits.

### Finding Description
`buildConflictContext` reads every conflicted file with a hard-coded UTF-8 decode: [1](#0-0) 

This decoded string is stored verbatim as `rawContent` on `IFileConflictContext`: [2](#0-1) 

Later, `reassembleResolvedFile` (in `copilot-conflict-resolution.ts`) splices the model's per-hunk resolution text into this `rawContent` to produce the final `resolvedContent`: [3](#0-2) 

Finally, `_applyCopilotConflictResolutions` writes that spliced string back to disk with `'utf8'` and immediately `git add`s it: [4](#0-3) 

None of the size/length guards in `getHunkSkipReason` or the file-size check in `buildConflictContext` validate encoding — they only bound byte count and line length: [5](#0-4) 

If any byte sequence in the file — including bytes far outside the actual conflict markers, in the surrounding "ours"/"theirs" context or unrelated regions of the file — is not valid UTF-8 (e.g. a file legitimately encoded in Latin-1, Shift-JIS, UTF-16, or containing embedded binary-ish data such as a serialized blob, BOM-less legacy text, or deliberately crafted malformed sequences), `readFile(absolutePath, 'utf8')` silently substitutes `U+FFFD` for the offending bytes. That corrupted text is what gets spliced with the AI's resolution and written back verbatim, then staged with `git add`. The user sees a diff (via `getResolutionDiff`, which suffers the identical unconditional `'utf8'` conversion at both the base-read and the git-blob read) but the diff itself is generated from data that has already lost fidelity, so the "preview" the user is shown does not accurately warn them that non-UTF-8 bytes were mangled.

### Impact Explanation
This can happen with an attacker-controlled cloned/fetched repository: a repository containing files with legacy or mixed encodings (a legitimate scenario for internationalized codebases, or a file deliberately crafted with invalid UTF-8 byte sequences positioned in a merge-conflict region) will, when it produces a merge/rebase/cherry-pick conflict that the user resolves via "Resolve with Copilot", have those non-UTF-8 bytes silently replaced with `U+FFFD` and permanently committed. This is a silent corruption of what the user commits and pushes — the on-disk byte content the user believes they are keeping (their own file, or the "ours"/"theirs" stage content) is altered without any error, warning, or diff indication of the substitution, satisfying the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The code path is triggered by the ordinary/expected user action of resolving a merge conflict with Copilot, requiring no unnatural steps — the user only needs to have (or fetch) a repository containing a non-UTF-8-encoded file that ends up in conflict. This is a fairly common real-world occurrence (legacy Windows-1252/Shift-JIS files, generated files with encoded binary payloads, etc.), and the existing safety checks (`MAX_CONFLICT_FILE_READ_SIZE`, `MAX_CONFLICT_LINE_LENGTH`, `MAX_CONFLICT_CONTENT_SIZE`) do nothing to detect or reject invalid encodings, so no existing guard stops the corrupted content from being written and staged.

### Recommendation
Before treating a conflicted file as text for the Copilot flow, detect whether the raw buffer round-trips losslessly through UTF-8 (e.g., compare `Buffer.from(buf.toString('utf8')).equals(buf)`, or use a strict UTF-8 validator) and, if not, skip the file with a `skippedReason` (as is already done for oversized/unreadable files) rather than silently decoding it. The same guard should be applied in `getResolutionDiff`'s blob/base reads in `app/src/lib/git/diff.ts` so the preview diff and the actual applied write are consistent and never fed corrupted text.

### Proof of Concept
1. Create a repository with a file `legacy.txt` containing valid Shift-JIS (or otherwise non-UTF-8) bytes, e.g. bytes `0x82 0xA0` (a Shift-JIS hiragana character) mixed with ASCII text.
2. On branch `main`, modify one line of `legacy.txt`; on branch `feature`, modify a different line, ensuring the non-UTF-8 bytes remain in a context line adjacent to (or inside) the conflicting hunk.
3. Fetch/clone this repository (simulating an attacker-supplied repo) and start a merge of `feature` into `main`, producing a conflict in `legacy.txt`.
4. Use "Resolve with Copilot" in GitHub Desktop; `buildConflictContext` reads the file with `readFile(absolutePath, 'utf8')`, silently turning the Shift-JIS bytes into `U+FFFD` replacement characters.
5. Accept the Copilot resolution and click "Continue Merge"; `_applyCopilotConflictResolutions` writes the corrupted `resolvedContent` back to `legacy.txt` with `'utf8'` and runs `git add`.
6. Inspect the committed blob: the original Shift-JIS byte sequence is now permanently replaced by `U+FFFD` (`0xEF 0xBF 0xBD` in UTF-8) — the user has unknowingly committed corrupted file content that neither the app nor Git flagged as an error.

export function getHunkSkipReason(
  hunks: ReadonlyArray<IConflictHunk>
): string | null {
  let totalContent = 0

  for (const hunk of hunks) {
    const sides = [hunk.oursContent, hunk.theirsContent, hunk.baseContent ?? '']
    for (const side of sides) {
      totalContent += side.length
      for (const line of side.split('\n')) {
        if (line.length > MAX_CONFLICT_LINE_LENGTH) {
          return 'Conflict contains lines too long to resolve automatically'
        }
      }
    }
    if (totalContent > MAX_CONFLICT_CONTENT_SIZE) {
      return 'Conflict region too large to resolve automatically'
    }
  }

  return null
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
