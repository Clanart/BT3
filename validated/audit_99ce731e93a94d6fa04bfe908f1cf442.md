### Title
Missing minimum-deposit/virtual-shares protection allows first-depositor share-price inflation in `PublicDelegation` staking vault - (File: contracts/bindings/publicdelegation/PublicDelegation.go, contract: PublicDelegation)

### Summary
The `PublicDelegation` contract implements an ERC4626-style share-accounting vault for public KAIA staking/delegation, exposing `deposit`/`withdraw`, `convertToShares`/`convertToAssets`, `previewDeposit`/`previewRedeem`/`previewWithdraw`, `totalAssets`, and `totalSupply`, and emitting `Staked(user, assets, shares)`. This mirrors exactly the vulnerable pattern described in the external report (Surge `Pool.sol` `tokenToShares`), where a first depositor can mint a negligible number of shares, then "donate" assets directly to the vault (or via a native-KAIA `receive()` — the contract exposes a `payable receive`) to inflate `totalAssets` relative to `totalSupply`, and subsequently withdraw a disproportionate amount of value from later depositors' contributions.

### Finding Description
`PublicDelegation` is reachable by any unprivileged sender via its public `deposit`/`stake`-style entrypoints (selectors visible in the ABI: `deposit`, `withdraw`, `convertToShares`, `convertToAssets`, `previewDeposit`, `previewRedeem`, `previewWithdraw`, `totalAssets`, `totalSupply`) and a `payable receive()` function that lets anyone send native KAIA directly to the contract [1](#0-0) . The `Staked` event confirms an assets→shares minting flow analogous to ERC4626 `deposit` [2](#0-1) , and `ConvertToShares`/`ConvertToAssets`/`PreviewDeposit`/`PreviewRedeem`/`PreviewWithdraw`/`TotalAssets` together form the price-per-share calculation surface that the exploit in the report targets [3](#0-2) [4](#0-3) .

If (as in the standard ERC4626 formula referenced by the report) shares are minted as `assets * totalSupply / totalAssets` with no floor protection on the very first deposit, an attacker can: (1) deposit a minimal amount of assets to become the first depositor and receive a minimal nonzero share balance, (2) directly transfer/donate a large amount of native KAIA into the contract via the payable `receive()` (increasing `totalAssets` without minting new shares), thereby inflating the share price, and (3) redeem their shares for a disproportionately large fraction of the pool's total assets — extracting value contributed by subsequent depositors whose deposits get rounded down to fewer shares than their fair value.

**Important caveat**: I could only locate the compiled Go bindings (ABI/bytecode) for `PublicDelegation` in this index; the actual Solidity source (`PublicDelegation.sol`) implementing `_convertToShares`/`_convertToAssets` and the `deposit`/`withdraw` internal logic was not found in the indexed files, so I could not directly confirm whether the implementation already includes standard ERC4626 mitigations (e.g., a `decimalsOffset`/virtual-shares scheme, as adopted in OpenZeppelin's ERC4626 v4.9+, or a minimum-liquidity lock). This means the root cause cannot be proven at the exact source-line level from available context — only the public attack surface and share-based accounting design (which is architecturally identical to the vulnerable pattern in the report) can be confirmed.

### Impact Explanation
If unmitigated, this would allow direct value extraction from other delegators' staked KAIA — a concrete unauthorized value movement / supply-inflation-style theft consistent with the High severity of the original report, since `PublicDelegation` appears to hold real staked KAIA (per the `Staked`/`WithdrawApprovedStaking`-adjacent flows and `CnStakingV4`/`CnStakingV4Factory` integration) [5](#0-4) .

### Likelihood Explanation
Likelihood cannot be established with confidence: exploitation strictly depends on whether the actual `deposit`/`convertToShares` implementation lacks first-depositor protection, which I was unable to verify because the Solidity source is not present in the indexed repository content — only compiled Go bindings are available.

### Recommendation
Not applicable without source confirmation; if unmitigated, the standard remedy (minimum initial deposit burned to a dead address, or a virtual-shares/decimals-offset ERC4626 scheme) would apply, matching the report's own recommendation.

### Proof of Concept
Not constructible from available context — the actual share-minting formula in `PublicDelegation.sol` could not be located in this repository's indexed files (only ABI/bytecode bindings were found), so a concrete PoC analogous to the report's Foundry test cannot be produced here.
