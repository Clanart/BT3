Based on my investigation, I found a genuine analog in the PR-checkout flow (`_findPullRequestBranch` / `_checkoutPullRequest`), where an attacker-controlled GitHub API object (`clone_url`) is passed directly into `addRemote()` without protocol/format validation, mirroring the bug-class of "attacker-influenced data flowing into a git-affecting operation without the guard that a similar/sibling function has."

### Title
Unvalidated PR head `clone_url` from GitHub API passed to `git remote add`, enabling argument/URL smuggling into git subprocess - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user opens a pull request from a link (deep link `x-github-client://openRepo/...?pr=NNN` or the "Open PR from Desktop" flow), Desktop fetches the PR object from the GitHub API and uses `pullRequest.head.repo.clone_url` — a value fully controlled by whoever created the head fork/PR — as the URL argument to `addRemote()`, which shells out to `git remote add <name> <url>`.

### Finding Description
`Dispatcher.openPullRequestFromUrl` fetches the PR via the API and forwards the head repo's `clone_url` verbatim into `AppStore._checkoutPullRequest` → `_findPullRequestBranch`: [1](#0-0) 

`_findPullRequestBranch` then calls `addRemote(repository, forkRemoteName, headCloneUrl)` whenever no existing remote already matches the URL: [2](#0-1) 

`addRemote` builds the git command with the URL as a plain positional argument, with no protocol allow-listing and no check for a leading `-` (which git/CLI parsers can interpret as an option rather than a URL) or dangerous git "smart" transport helpers such as `ext::` or `fd::` that execute arbitrary local commands when git ever operates against that remote (fetch/pull/push): [3](#0-2) 

By contrast, the codebase already hardened analogous surfaces that ingest attacker-influenced strings: `sanitizeCloneName()` strips traversal and restricts to a single path component for clone destinations, `parseAppURL` runs `testForInvalidChars` on branch names, and `clone.ts` added `isClonePathSensitive()` as a "backstop against path traversal attacks where a crafted URL tricks the UI." No equivalent allow-list/backstop exists for `clone_url` before it's handed to `addRemote`. [4](#0-3) [5](#0-4) 

This is exactly the same *invariant break* as the TON report: a value that is supposed to be validated/normalized before being handed to a lower-level "protocol executor" (there: `send_withdraw` vs `send_withdraw_native`; here: an arbitrary API-controlled `clone_url` vs. a URL restricted to known-safe git transports) skips that check and reaches the primitive directly.

### Impact Explanation
If `git remote add` accepts a URL using `ext::` (or on Windows, similar helper syntax) it registers a remote that, when git subsequently runs any network operation against it (`fetch`, which `_findPullRequestBranch` immediately performs at [6](#0-5)  ), spawns an arbitrary external command with the current user's privileges — a full remote-code-execution primitive triggered purely by the victim clicking a "View pull request in GitHub Desktop" deep link or opening a PR whose head fork was created by the attacker. This satisfies the "attacker controls a GitHub API object" and "code execution" criteria in the Valid Impact section.

### Likelihood Explanation
Likelihood is moderate-to-low in practice because: (1) it requires the remote to actually be fetched, which does happen automatically in `_findPullRequestBranch`; (2) modern `dugite`/git builds have `protocol.ext.allow` defaulting to `user`/disabled for many transport helpers in some environments, and I could not verify from the indexed files whether Desktop explicitly sets `protocol.*.allow=never` anywhere (I did not find such a setting in `environment.ts` or `core.ts` during this session — this is unverified, not confirmed absent). This uncertainty should be resolved before treating this as a confirmed, exploitable finding.

### Recommendation
Before calling `addRemote` with a PR head `clone_url`, validate it against the same allow-list already used elsewhere (only `https://`/`ssh://`/`git@` forms accepted by `parseRemote` in `app/src/lib/remote-parsing.ts`), rejecting anything that doesn't match a known GitHub-style remote shape — mirroring how `sanitizeCloneName` and `isClonePathSensitive` already gate other attacker-reachable strings. Additionally confirm (or add) `protocol.ext.allow=never` / an equivalent transport allow-list in the git execution environment used for all remote operations (`envForRemoteOperation`), as defense in depth.

### Proof of Concept
1. Attacker forks a public repo and, via the GitHub API (not through Desktop), sets/renames things such that the PR's `head.repo.clone_url` field is not a normal `https://github.com/...` URL — this requires either a compromised/spoofed API response, a malicious GitHub Enterprise-style endpoint, or a MITM'd API response, since GitHub.com itself always returns canonical `clone_url` values. **This step could not be independently verified against GitHub.com's actual API behavior from the indexed code alone** — the finding assumes an untrusted/enterprise API endpoint or a value populated from a source the attacker fully controls, which is stated in the report's own scope ("GitHub API object" attacker control).
2. Victim clicks the PR's "Open in Desktop" link or the deep link `x-github-client://openRepo/<url>?pr=<n>`, hitting `parseAppURL` → `dispatchURLAction` → `openPullRequestFromUrl`. [7](#0-6) 
3. `_findPullRequestBranch` finds no existing remote matching the crafted URL and calls `addRemote(repository, forkRemoteName, headCloneUrl)` unchecked, then immediately fetches it. [8](#0-7) 
4. If the underlying git binary's transport-helper protocol is not restricted, the `fetch` executes the attacker-supplied command.

**Confidence caveat:** I was not able to fully confirm within the indexed files whether Desktop's git execution environment (`envForRemoteOperation`, `core.ts`) sets `GIT_ALLOW_PROTOCOL` or `protocol.*.allow=never`, which would neutralize this path. If such a restriction is already present and applied to all `git` invocations including `addRemote`/`fetch`, this finding's severity should be downgraded to informational (defense-in-depth only), since the missing input validation would still be the retained "broken invariant" but without the direct RCE consequence.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
