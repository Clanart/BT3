### Title
Stale-snapshot splice in Copilot conflict resolution can silently discard on-disk changes made during the AI round-trip - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Copilot-assisted merge/rebase/cherry-pick conflict resolver reads each conflicted file's full content once, before sending it to the network-bound Copilot completion API, and only re-uses that captured snapshot (`rawContent`) to reassemble the final file — line-splicing the model's per-hunk output back into the *original* pre-request text — without ever re-reading or re-validating the file against its current on-disk state at write time. This mirrors the reported ERC777 pattern where a state check is performed before an external, attacker/timing-influenced call, and the effect is applied afterward against the stale pre-call assumption instead of the post-call reality.

### Finding Description
`buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` reads each conflicted file into memory and stores it as `rawContent` on the `IFileConflictContext` object: [1](#0-0) 

That context, including `rawContent`, is then handed off to the Copilot SDK, which performs a network round trip (an "external call" from the perspective of local state) whose duration is attacker/network influenced (large diffs, many files, chunking via `createDependencyAwareChunks`/`MaxConcurrentChunks`).

When the model's response comes back, `reassembleResolutions` reassembles the final write-ready content strictly from the **original captured `ctx.rawContent`**, never re-reading the file from disk: [2](#0-1) 

`reassembleResolvedFile` then walks that stale snapshot line-by-line and splices in the model's hunk resolutions to produce the file content that is ultimately written to the working directory: [3](#0-2) 

There is no invariant check anywhere in this path (parsing, validation in `validateResolutionPaths`, or reassembly) that the file on disk still matches `rawContent` at the moment of writing. `validateResolutionPaths` only checks that the *set of paths* and *hunk counts* match what was expected — it does not check content freshness: [4](#0-3) 

Between the initial read (`buildConflictContext`) and the eventual write, an unbounded amount of time and I/O can occur: git can continue advancing the merge/rebase/cherry-pick state machine, hooks can run, the user (or another automated process, e.g. autosave/format-on-save extensions watching the working tree) can edit the conflicted file, or a `git checkout --theirs`/manual resolution can be applied concurrently through the same UI. None of these intervening changes are detected before the AI-derived content is spliced onto the old snapshot and written, so the final on-disk result silently reflects a "merge" of the model's hunks against a **file state that may no longer exist**, discarding whatever changed in the interim without any conflict, warning, or diff review gate. Unlike the report's Solidity fix advice, the general lesson (checks/state validated at the point of use, not before an intervening external interaction) is not applied here.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." If the underlying conflicted file changes between context capture and Copilot's response — through any legitimate concurrent git/editor activity, or through content in the cloned/fetched repository whose resolution takes an unusually long time (large/complex hunks intentionally crafted by a hostile remote to prolong AI turnaround) — the eventual write can clobber that intervening state and reintroduce or fabricate content the user never reviewed as final, which is then staged/committed/pushed as if it were correct.

### Likelihood Explanation
Requires the standard, unprivileged Copilot-conflict-resolution feature to be in use during a merge/rebase/cherry-pick with real network latency to the Copilot API, which is routine. No local/physical access, admin rights, or pre-existing compromise is needed — the only "attacker" lever is the shape/size of conflicting content from a cloned/fetched branch (which is exactly the sanctioned "attacker controls a cloned/fetched repository" primitive), which can be engineered to widen the read-then-write race window via `MAX_CONFLICT_FILE_READ_SIZE`/`MAX_CONFLICT_CONTENT_SIZE`-adjacent large hunks or many chunked files.

### Recommendation
Re-read (or otherwise verify via mtime/hash captured at snapshot time) each conflicted file immediately before applying `reassembleResolutions`' output, and abort/re-prompt the user if the on-disk content no longer matches the `rawContent` that was sent to the model — i.e., move the "is this still valid to apply" check to after the external (Copilot) call completes and immediately before the write, rather than relying on a pre-call snapshot, analogous to moving the balance check in `_transferByPartition` to after the pre-transfer hook in the original report.

### Proof of Concept
1. Start a merge/rebase/cherry-pick that produces a conflicted file with content sized near `MAX_CONFLICT_CONTENT_SIZE`/multiple hunks so Copilot resolution takes long enough for a human-observable window.
2. Trigger AI conflict resolution; while the Copilot request is in flight, edit the same conflicted file on disk (or run `git checkout --theirs -- <file>` / let another concurrent process touch it).
3. Let the Copilot response return; observe that `reassembleResolutions`/`reassembleResolvedFile` splice the model's hunks into the original pre-edit `rawContent` captured in step 1, and that output is written back — silently discarding the edit made in step 2 with no warning, diff review, or conflict surfaced to the user.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
