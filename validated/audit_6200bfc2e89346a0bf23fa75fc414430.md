### Title
Bank precompile `send` bypasses tokenfactory denom allow-list and blocked-address restrictions by calling `SendCoins` directly instead of the `MsgServer.Send` handler - (File: precompiles/bank/legacy/v555/bank.go)

### Summary
The `send` method of the (legacy) bank precompile transfers coins between two arbitrary Sei addresses by calling `bankKeeper.SendCoins` directly, whereas the canonical Cosmos-SDK bank transfer path enforces tokenfactory denom allow-lists and blocked-address checks inside `msgServer.Send`/`MultiSend`, not inside `SendCoins` itself.

### Finding Description
`BaseSendKeeper.SendCoins` (the lowest-level "moves the coins" primitive) performs no allow-list or blocked-address validation — those checks (`IsInDenomAllowList`, `BlockedAddr`) live exclusively in `msgServer.Send`/`MultiSend`. [4](#0-3) [5](#0-4) 

The legacy bank precompile's `send` function accepts an arbitrary sender/receiver pair supplied via calldata (resolved through `accAddressFromArg`) and calls `p.bankKeeper.SendCoins` directly, entirely skipping the allow-list/blocked-address gate that the canonical `MsgSend` handler enforces: [6](#0-5) 

This mirrors the CVE-2021-31864 pattern precisely: a permission gate implemented at one entry point (the normal issue-notes web submission / the `MsgServer.Send` RPC) is absent from a second, independently-reachable entry point (the mail handler / the EVM precompile) that ultimately performs the same privileged operation through a shared lower-level primitive.

Note that newer precompile versions (`v65`, `v66`) were updated to route through `p.bankMsgServer.Send(...)`, which does enforce the allow-list checks — confirming that the fix for equivalent versions was precisely "route through the message server instead of calling the keeper directly." [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged EVM contract deployer/caller invoking the (legacy) bank precompile's `send` can move tokenfactory-denominated coins on behalf of the pointer-linked sender/receiver identities while bypassing denom-level transfer restrictions (allow-lists) that token-factory denom admins rely on for regulatory/compliance controls, and bypassing the blocked-address check that prevents sends to protected module accounts. This constitutes unauthorized transfer via precompile, potentially enabling restricted-denom holders to move funds to addresses that were explicitly disallowed, or to a blocked module account, undermining an authority control that the chain guarantees at the Cosmos-message level.

### Likelihood Explanation
Any address holding an ERC20-pointer-eligible tokenfactory denom with an active allow-list restriction can trigger this by simply calling the bank precompile's `send` method with denom, sender, and receiver arguments — no special privilege, validator collusion, or governance action is required. It is reachable purely from a submitted EVM transaction.

### Recommendation
Route the precompile `send`/`sendNative` (and any similar direct-`SendCoins` callers) through the bank `MsgServer.Send`/`MultiSend` handlers (as already done in the `v65`/`v66` precompile revisions) so that `IsSendEnabledCoins`, `IsInDenomAllowList`, and `BlockedAddr` checks are consistently enforced regardless of entry point. Audit all other precompiles/pointers that call bank keeper primitives directly for the same class of bypass.

### Proof of Concept
1. Governance/denom admin sets a tokenfactory denom allow-list via `SetDenomAllowList` restricting transfers to specific addresses (e.g., only `addr1`).
2. `addr1` funds itself with the restricted denom, then registers/uses an ERC20 pointer for that denom.
3. `addr1` calls the bank precompile's `send(from=addr1, to=addr2, denom, amount)` where `addr2` is NOT in the allow-list.
4. Because `precompiles/bank/legacy/v555/bank.go`'s `send` calls `p.bankKeeper.SendCoins` directly (not `msgServer.Send`), the transfer succeeds despite `addr2` not being permitted to receive the restricted denom — whereas the same transfer attempted via `MsgSend` would be rejected with `"is not allowed to receive funds"` as shown in the SDK's own test. [9](#0-8)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)
	if err != nil {
		return nil, err
	}

func (p Precompile) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
