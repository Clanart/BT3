## Analysis

The relevant code path is confirmed. `OnTimeoutPacket` in `x/erc20/keeper/ibc_callbacks.go` delegates directly to `ConvertCoinToERC20FromPacket`, which — for a native-ERC20 token pair — calls `k.ConvertCoinNativeERC20` without first checking whether the backing ERC20 contract still exists. [1](#0-0) 

Contrast this with the direct message-server entrypoints (`ConvertCoin`/`ConvertERC20`), which explicitly guard against a self-destructed contract *before* touching any balances, and simply delete the stale token pair if the backing contract's code is gone: [2](#0-1) 

`ConvertCoinNativeERC20` itself performs the coin **escrow first**, then attempts the on-chain ERC20 transfer, and only burns the escrowed coin *after* a successful transfer: [3](#0-2) 

Because `OnTimeoutPacket`/`OnAcknowledgementPacket` skip the "is the contract still alive" guard that the msg-server path has, when the ERC20 contract has been self-destructed (or is otherwise stale), `ConvertCoinNativeERC20` escrows the sender's coin into the `erc20` module account, then fails at the EVM-transfer/`validateTransferEventExists` step, returning an error *after* the escrow already succeeded. That error is caught and swallowed in `ConvertCoinToERC20FromPacket`, which only emits a `EventTypeFailedConvertERC20` event and returns `nil`: [4](#0-3) 

The integration test for this exact scenario (`"err - self-destructed contract"`) only checks that the failure event is emitted; it never asserts on the sender's or module account's balances after the failure, so the fund-stranding effect is not caught by existing tests: [5](#0-4) 

### Title
Escrow-before-verify ordering in `ConvertCoinNativeERC20` permanently strands IBC-refunded coins when invoked from `OnTimeoutPacket`/`OnAcknowledgementPacket` against a self-destructed or stale ERC20 contract - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`OnTimeoutPacket` (and `OnAcknowledgementPacket`) call `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20` without first checking that the backing ERC20 contract is still alive, unlike the `MsgConvertCoin`/`MsgConvertERC20` message-server handlers which perform this check up front. `ConvertCoinNativeERC20` escrows the coin from the user to the `erc20` module account *before* attempting the ERC20-side transfer/verification. If the contract is self-destructed (or otherwise fails the transfer/verification step), the function returns an error which is silently swallowed by the IBC callback, leaving the escrowed coin permanently stuck in the module account with no burn, no refund, and no re-mint.

### Finding Description
`ConvertCoinNativeERC20` performs, in order: (1) `SendCoinsFromAccountToModule` (escrow), (2) `CallEVM("transfer", ...)` to move ERC20 tokens out of the module's balance to the receiver, (3) balance-invariance check via `validateTransferEventExists`/transfer return value, and only then (4) `BurnCoins` on the escrowed coin. If step (2)/(3) fails — e.g., because the target contract has been self-destructed via `DeleteAccount` and therefore emits no `Transfer` log/return value — the function returns an error *after* step (1) has already committed. Because `ConvertCoinToERC20FromPacket` (used by both `OnTimeoutPacket` and `OnAcknowledgementPacket`) does not use a cached/rolled-back context for this sub-call, and swallows the returned error by emitting an event and returning `nil`, the escrow performed in step (1) is never undone. The `MsgConvertCoin`/`MsgConvertERC20` handlers avoid this because they check `acc == nil || !acc.HasCodeHash()` and short-circuit (deleting the stale pair) before any balance mutation occurs; the IBC-callback path lacks this same guard.

### Impact Explanation
Any coin refunded via IBC timeout/error-ack for a native-ERC20 token pair whose contract has been destroyed or otherwise made non-functional gets moved into the `x/erc20` module account and is never returned to the user, never burned, and never re-mintable — it becomes permanently locked. Since a native-ERC20 token pair can be created permissionlessly (subject to `PermissionlessRegistration`) and self-destructed by its own deployer, this can be used to freeze in-flight IBC refunds belonging to *other* users of the same shared token pair, not just the party who destroyed the contract. This matches the "Permanent locking/freezing of funds" critical impact class for token-pair-backed balances.

### Likelihood Explanation
Triggering requires: (1) a native ERC20 contract registered as a token pair, (2) the contract's code becoming unavailable (self-destruct, which is a normal EVM operation available to any contract owner/attacker who deploys such a contract), and (3) an IBC transfer of that pair's native coin timing out or receiving an error acknowledgement while the contract is dead. All of these are reachable through ordinary, unprivileged transaction flows (`MsgRegisterERC20` if permissionless, contract deployment/self-destruct, ICS-20 transfer, and IBC timeout/ack processing), making this practically triggerable without any privileged access.

### Recommendation
Add the same "is the contract still alive" check used in `ConvertCoin`/`ConvertERC20` to `ConvertCoinToERC20FromPacket` before calling `ConvertCoinNativeERC20`, and/or make `ConvertCoinNativeERC20`'s escrow step transactional with the ERC20 transfer (e.g., use `ctx.CacheContext()` around the whole conversion and only `writeFn()` on full success, or reorder the operations so failure paths never leave the coin removed from the sender without a corresponding token/mint). If the contract is found to be dead, the coin should simply remain with the sender rather than being escrowed.

### Proof of Concept
1. Permissionlessly deploy an ERC20 contract with a `selfdestruct` path and register it via `MsgRegisterERC20` as a native-ERC20 token pair.
2. Convert ERC20 to the native coin representation via `MsgConvertERC20`, then IBC-transfer some of that coin out via ICS-20 (creating an in-flight escrow on the sending chain).
3. Before the packet is acknowledged, self-destruct the ERC20 contract (`DeleteAccount` on the EVM side, e.g. via a `selfdestruct` call in the contract).
4. Let the packet time out (or fail with error ack) so `x/erc20/keeper/ibc_callbacks.go:OnTimeoutPacket` fires.
5. Observe: `ConvertCoinNativeERC20` moves the refunded coin into the `erc20` module account, then fails the EVM transfer/validate step; the error is swallowed, `OnTimeoutPacket` returns `nil` (packet processing "succeeds"), and the sender's coin balance is never restored, no ERC20 tokens are minted, and the escrowed coin sits unburned and unclaimable in the module account — replicating the existing `"err - self-destructed contract"` test case in `tests/integration/x/erc20/test_ibc_callback.go`, but extending the assertions to check sender and module-account balances (which the current test omits) to confirm the fund is permanently stranded.

```go
func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}
```
