## Finding

<title>
Unvalidated symlink-based path escape in "Reveal in Finder"/"Open" file actions - (File: `app/src/lib/app-shell.ts`)
</title>

### Summary
Several UI actions that operate on a file path taken from a cloned/checked-out repository's working directory (e.g. "Reveal in Finder/Explorer", "Open with Default Program", "Open in External Editor") build the absolute path with a raw `Path.join(repository.path, path)` and never verify that the result actually stays inside the repository. This is the same broken invariant as the reported "on-behalf" withdrawal bug: a caller-controlled value (here, a working-directory path that an attacker-controlled repository can arrange to be a symlink) is used to compute a target resource without a containment/ownership check, even though the very same codebase already recognizes this exact risk and fixes it elsewhere.

### Finding Description
`revealInFileManager` in `app/src/lib/app-shell.ts` computes the target path with no bounds check at all: [1](#0-0) 

The same unguarded pattern (`Path.join(repository.path, path)` followed directly by `shell.showItemInFolder`/`shell.openExternal`/opening in an external editor) is repeated at every call site that reacts to a user click on a listed working-directory/committed file:
- `onOpenInExternalEditor` in `app/src/ui/app.tsx`: [2](#0-1) 
- `onOpenItem` in `app/src/ui/changes/sidebar.tsx`: [3](#0-2) 
- `onOpenItem` in `app/src/ui/history/selected-commits.tsx`: [4](#0-3) 
- `onOpenFile`/context menu in `app/src/ui/open-pull-request/pull-request-files-changed.tsx`: [5](#0-4) 
- `makeMarkerConflictDropdownClickHandler` in `app/src/ui/lib/conflicts/unmerged-file.tsx`: [6](#0-5) 
- `onOverflowMenuClick` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`: [7](#0-6) 

None of these validate that the joined path stays within `repository.path`. `Path.join` only textually normalizes `..` segments; it does not resolve or reject symlinks. If a cloned repository contains a tracked symlink (a normal git blob of mode `120000`) whose target points outside the repository (e.g. `../../../..`), checking out that repository materializes a real on-disk symlink. Any working-directory entry whose relative path passes through that symlink component will, after `Path.join`, still textually resolve underneath `repository.path`, but the actual filesystem object that `shell.showItemInFolder`/`shell.openExternal`/the external editor is pointed at can be anywhere on disk.

The codebase already treats this exact class of bug as security-relevant and has fixed it in two other places using `resolveWithin` (`app/src/lib/path.ts`), whose own doc comment and test suite explicitly call out "symlink escapes": [8](#0-7) [9](#0-8) 

These fixed call sites are:
- Deep-link `filepath` handling for "Open in Desktop" (`Dispatcher.openRepositoryFromUrl`): [10](#0-9) 
- Copilot conflict resolution reading/writing file content (`buildConflictContext` / `_finishCopilotConflictResolution`): [11](#0-10) [12](#0-11) 

`app-shell.ts` even documents the expectation that callers validate paths before calling `openPath`/`showFolderContents` ("Do not use this method with non-validated paths"), but `revealInFileManager` — the most commonly used helper, wired into nearly every file list context menu in the app — does not perform that validation itself, nor do any of its callers.

### Impact Explanation
An attacker who controls a repository that the victim clones or fetches (the same "attacker controls a cloned/fetched repository" primitive named in the report's valid-impact list) can commit a tracked symlink pointing outside the repository, then arrange for a corresponding path to show up in the Changes list, History file list, or a Pull Request's file list. When the victim simply right-clicks and chooses "Reveal in Finder/Explorer" or "Open with Default Program"/"Open in [Editor]" — completely ordinary Desktop usage — the app resolves and opens/exposes a filesystem location entirely outside the repository, chosen by the attacker's symlink target (e.g. the user's home directory, `.ssh`, or other sensitive paths), i.e. file read/disclosure outside the repo boundary, which the task explicitly names as valid impact.

### Likelihood Explanation
No admin rights, local access, or leaked credentials are required — only a normal `git clone`/checkout of an attacker-authored repository and one context-menu click that is part of Desktop's everyday workflow (revealing or opening a changed file). Desktop's own code (`resolveWithin`, `sanitizeCloneName`, `copilot-conflict-context.ts` comments) shows the team is already aware that symlinks in untrusted repositories are an exploitable escape vector for path-join based logic, but that fix was not applied consistently to the much more frequently used "reveal/open file" pathways.

### Recommendation
Route every `Path.join(repository.path, path)` construction that stems from a repository-tracked/working-directory path (in `app-shell.ts`, `app.tsx`, `sidebar.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`, and `filter-changes-list.tsx`) through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` (as already done in `dispatcher.ts` and `copilot-conflict-context.ts`), rejecting or refusing the action when the resolved real path escapes `repository.path`. Consider making `revealInFileManager` itself perform this check centrally so future call sites cannot forget it.

### Proof of Concept
1. Attacker creates a repository containing a tracked symlink `escape -> ../../../../` (mode `120000`) and commits it.
2. Victim clones/fetches this repository with GitHub Desktop; the symlink is materialized on disk during checkout.
3. Attacker's next commit adds/modifies a file whose relative path traverses the symlink, e.g. `escape/Documents/secret.txt` appears as a changed/untracked entry in the Changes or History file list (the symlink component makes the on-disk target resolve outside the repo, while `file.path` textually still looks like a normal repo-relative path).
4. Victim right-clicks that entry and selects "Reveal in Finder"/"Open with Default Program".
5. `Path.join(repository.path, file.path)` textually stays "inside" the repo, but the OS follows the symlink and shows/opens content from outside the repository — with no `resolveWithin`-style check ever performed, unlike the deep-link and Copilot flows in this same codebase.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
