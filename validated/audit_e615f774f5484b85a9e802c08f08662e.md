### Title
Fee-collector balance is not consolidated until EndBlock, causing per-block transient understatement of collected fees - (File: `sei-cosmos/x/bank/keeper/keeper.go`)

### Summary
Sei's bank keeper defers all fee (and other) transfers into module accounts via a `DeferredCache` rather than crediting the module account immediately, exactly analogous to the ERC777 Pod issue: funds are deducted from the sender right away, but the recipient's (module account's) balance does not reflect the credit until a later "consolidation" step (`WriteDeferredBalances`), which only runs once per block in `EndBlock`/`ProcessBlock`.

### Finding Description
`DeductFeeDecorator.checkDeductFee` / `chargeFees` in the ante pipeline calls `bankKeeper.DeferredSendCoinsFromAccountToModule` for every transaction's fee payment: [1](#0-0) [2](#0-1) 

`DeferredSendCoinsFromAccountToModule` immediately subtracts coins from the sender (`SubUnlockedCoins`), but instead of crediting the fee-collector module account, it only records the amount in a `DeferredCache` keyed by module address and tx index: [3](#0-2) 

The actual credit to the module account only happens when `WriteDeferredBalances` is invoked, which iterates and flushes the cache into real balances via `AddCoins`, then clears the cache: [4](#0-3) 

This consolidation step is called exactly once, at the very end of block processing (after all per-tx execution and the EVM `MidBlock` step), inside `ProcessBlock`: [5](#0-4) 

This is structurally identical to the `pods` audit finding: the "deposit" (fee/coin transfer into the module account) is scheduled but the real balance is not updated until an explicit consolidation call (`consolidateBalanceOf` ↔ `WriteDeferredBalances`), and any code that queries the recipient's balance ("ERC777 `send`/`transfer`" ↔ any `BankKeeper.GetBalance`/`GetAllBalances` call, EVM precompile balance query, or any keeper logic reading the fee-collector's balance) mid-block will see a stale, understated value that doesn't include fees/coins already deducted from payers in the same block.

### Impact Explanation
Because the fee collector's (and any other module account's) balance is deliberately stale for the whole block (an OCC/parallel-execution design choice to avoid write contention on a hot account), any logic that reads that module account's balance mid-block — e.g. governance/distribution logic, other precompiles, or CosmWasm/EVM code paths that query `usei` balances of well-known module addresses within the same block before `EndBlock` — will undercount funds that have already been irrevocably debited from senders. This does not, by itself, allow theft of funds (money is not permanently lost or duplicated — it is reconciled at `WriteDeferredBalances`), but it is a genuine "incomplete accounting until consolidation" bug class matching the reported issue, and any invariant check, precompile, or downstream contract logic that assumes a queried module-account balance is authoritative mid-block can be misled, producing incorrect results for a single block window. The severity is bounded because full consolidation always occurs before `EndBlock` finishes and no direct fund-loss/freeze path was found within the available context.

### Likelihood Explanation
The deferred-cache pattern is exercised on every single transaction that pays fees (essentially every tx), so the "unconsolidated" state exists continuously during block execution. However, exploiting this for concrete fund loss would require identifying a specific in-block reader of the fee-collector (or another deferred-credit target module account) balance that makes a security-relevant decision based on it before `WriteDeferredBalances` runs; no such reader was confirmed within the accessible code in this session.

### Recommendation
- Audit all keeper/precompile/query code paths that read a module account's `usei`/coin balance mid-block (i.e., before `WriteDeferredBalances` executes) and ensure they account for pending deferred-cache entries, similar to how the Pod fix extended `send`/`transfer` to call `consolidateBalanceOf` first.
- Consider exposing a "consolidated balance" accessor (analogous to making `consolidateBalanceOf` public) that transparently merges `DeferredCache.GetBalance` with the on-chain balance for any reader that needs an authoritative mid-block value, rather than relying solely on the end-of-block flush.

### Proof of Concept
Not independently verified with a runnable reproduction in this session — the analysis is based on direct code-path tracing of `DeductFeeDecorator`/`chargeFees` → `DeferredSendCoinsFromAccountToModule` → `DeferredCache` → `WriteDeferredBalances` in `app.go`'s `ProcessBlock`. A concrete PoC would need to identify and exercise a specific mid-block reader of the fee-collector module account balance (e.g., a bank precompile `balanceOf` call for the fee collector's associated address, or a governance/module hook) within the same block as pending fee deductions to demonstrate a materially incorrect read; this was not confirmed to exist in the explored context.

	}

	feeTx := tx.(sdk.FeeTx)
	feePayer := feeTx.FeePayer()

	deductFeesFromAcc := accountKeeper.GetAccount(ctx, feePayer)
	if deductFeesFromAcc == nil {
		return nil, sdkerrors.ErrUnknownAddress.Wrapf("fee payer address: %s does not exist", feePayer)
	}

	// deduct the fees
	if !feeCoins.IsZero() {
		if !feeCoins.IsValid() {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrInsufficientFee, "invalid fee amount: %s", feeCoins)
		}

		err := bankKeeper.DeferredSendCoinsFromAccountToModule(ctx, deductFeesFromAcc.GetAddress(), authtypes.FeeCollectorName, feeCoins)
		if err != nil {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%s", err.Error())
		}
	}

	return feePayer, nil
}

// DeferredSendCoinsFromAccountToModule transfers coins from an AccAddress to a ModuleAccount.
// It deducts the balance from an accAddress and stores the balance in a mapping for ModuleAccounts.
// In the EndBlocker, it will then perform one deposit for each module account.
// It will panic if the module account does not exist.
func (k BaseKeeper) DeferredSendCoinsFromAccountToModule(
	ctx sdk.Context, senderAddr sdk.AccAddress, recipientModule string, amount sdk.Coins,
) error {
	if k.deferredCache == nil {
		panic("bank keeper created without deferred cache")
	}
	// Deducts Fees from the Sender Account
	err := k.SubUnlockedCoins(ctx, senderAddr, amount, true)
	if err != nil {
		return err
	}
	// get recipient module address
	moduleAcc := k.ak.GetModuleAccount(ctx, recipientModule)
	if moduleAcc == nil {
		panic(sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", recipientModule))
	}
	// get txIndex
	txIndex := ctx.TxIndex()
	if txIndex < 0 {
		return fmt.Errorf("negative tx index: %d", txIndex)
	}
	err = k.deferredCache.UpsertBalances(ctx, moduleAcc.GetAddress(), uint64(txIndex), amount) //nolint:gosec // bounds checked above
	if err != nil {
		return err
	}

	return nil
}

// WriteDeferredDepositsToModuleAccounts Iterates on all the deferred deposits and deposit them into the store
func (k BaseKeeper) WriteDeferredBalances(ctx sdk.Context) []abci.Event {
	if k.deferredCache == nil {
		panic("bank keeper created without deferred cache")
	}
	ctx = ctx.WithEventManager(sdk.NewEventManager())

	// maps between bech32 stringified module account address and balance
	moduleAddrBalanceMap := make(map[string]sdk.Coins)
	// slice of modules to be sorted for consistent write order later
	var moduleList []string

	// iterate over deferred cache and accumulate totals per module
	k.deferredCache.IterateDeferredBalances(ctx, func(moduleAddr sdk.AccAddress, amount sdk.Coin) bool {
		currCoins, ok := moduleAddrBalanceMap[moduleAddr.String()]
		if !ok {
			// add to list of modules
			moduleList = append(moduleList, moduleAddr.String())
			// set the map value
			moduleAddrBalanceMap[moduleAddr.String()] = sdk.NewCoins(amount)
			return false
		}
		// add to currCoins
		newCoins := currCoins.Add(amount)
		// update map
		moduleAddrBalanceMap[moduleAddr.String()] = newCoins
		return false
	})
	// sort module list
	sort.Strings(moduleList)

	// iterate through module list and add the balance to module bank balances in sorted order
	for _, moduleBech32Addr := range moduleList {
		amount, ok := moduleAddrBalanceMap[moduleBech32Addr]
		if !ok {
			err := fmt.Errorf("failed to get module balance for writing deferred balances for address=%s", moduleBech32Addr)
			logger.Error(err.Error())
			panic(err)
		}
		err := k.AddCoins(ctx, sdk.MustAccAddressFromBech32(moduleBech32Addr), amount, true)
		if err != nil {
			logger.Error("Failed to add coin to module address", "coin", amount, "address", moduleBech32Addr, "err", err)
			panic(err)
		}
	}

	// clear deferred cache
	k.deferredCache.Clear(ctx)
	return ctx.EventManager().ABCIEvents()
}
