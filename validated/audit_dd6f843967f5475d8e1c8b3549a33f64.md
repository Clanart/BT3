### Title
Stale line-index selection is trusted against a freshly re-fetched diff, silently corrupting partial commits - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/apply.ts`)

### Summary
The reported Solidity bug is a classic "checked-then-used" flaw: `reconcile()` computes a fulfillment flag from balances at one instant, but `_borrow()`/`_contribute()` can still mutate those balances afterward, so `validateBalances()` later trusts a flag that no longer reflects the true state. The GitHub Desktop analog is the partial-commit pipeline: a file's `DiffSelection` (which lines the user chose to include) is captured against one diff snapshot, but when the file changes underneath the app, Desktop re-fetches a *new* diff and re-applies the *old* selection by raw line index rather than by line identity, then uses that stale-but-trusted selection to build the actual patch that gets applied to the index and committed.

### Finding Description
When a user partially selects lines/hunks of a file to commit, the UI keeps a `DiffSelection` object addressed by absolute line index (`hunk.unifiedDiffStart + index`), computed from whatever diff was loaded at selection time.

If the working file changes (e.g. a build tool, an editor auto-format, or a hook triggered by another Desktop operation modifies it) while the file is still selected, `updateChangesWorkingDirectoryDiff` re-fetches the diff and reconciles the selection with the mutated diff by only pruning indices that are no longer selectable — it does **not** re-validate that a given index still refers to the same logical line: [1](#0-0) 

The comment in the code itself acknowledges the gap: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines."* [2](#0-1) 

At actual commit time, `applyPatchToIndex` re-fetches the diff *again* (a second, independent snapshot) and blindly combines it with whatever `file.selection` currently holds to build the patch that is staged: [3](#0-2) 

`formatPatch` walks the new diff's hunks and, for each line, asks `file.selection.isSelected(absoluteIndex)` — purely a positional lookup against index numbers computed from a possibly different (older) hunk layout: [4](#0-3) 

Because hunk boundaries and line offsets shift whenever the underlying file content changes (insertions/deletions above the hunk, whitespace changes, etc.), the same absolute index can point to a semantically different line in the newly-fetched diff than the one the user actually clicked to include. Desktop trusts this stale index-based selection as if it were re-validated ("_solverFulfilled"-style trust), when in fact the state it was computed against (the working-directory content) has moved on — exactly the invariant violated in the reported bug: a flag/derived value is set against state S₀ and later trusted at state S₁ ≠ S₀ without recomputation.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user reviewing a diff, deliberately excluding certain lines (e.g., a secret, a debug statement, or an unrelated change) from a partial commit, can have Desktop instead stage and commit different lines than intended if the file content shifts between the time the selection was made and the time `Commit` is pressed. Because git and Desktop's UI both show a subsequently-fetched diff, there is no error — the user is not warned that their previous selection was invalidated; the commit is created and can be pushed without the user noticing the discrepancy. This is attacker-relevant when the file mutation is driven by content that ships with a cloned/fetched repository (e.g., a build script, watcher, formatter config, or a hook triggered by another Desktop-invoked git operation) rather than the user's own keystrokes.

### Likelihood Explanation
The race window is realistic: partial-commit workflows are common, and any external process (linter/formatter on save, build watcher, `post-checkout`/`post-merge` hook shipped in a cloned repository, or another concurrent Desktop operation touching the file) can shift line offsets while the Changes view still shows a stale selection. No local/physical access or malware is required beyond the attacker controlling repository content that triggers a benign-looking automated file mutation. However, this requires a specific timing overlap (diff loaded → file changes → commit before the user notices/re-reviews), so it is a genuine but conditionally-triggered defect rather than a fully attacker-driven, deterministic exploit; the exact reachability depends on tooling configured by the repo (e.g., format-on-save extensions, hooks) which I was not able to fully enumerate within the available index.

### Recommendation
When the diff is refreshed for a file with an active partial selection, re-map or invalidate the selection by line *content/context* (e.g., diff/patience matching against the previous diff) rather than by raw absolute index, or conservatively clear/re-confirm the selection whenever the underlying diff changes non-trivially before allowing a partial commit. At minimum, `applyPatchToIndex`/`stageFiles` should re-verify — immediately before building the patch — that the diff used to interpret `file.selection` is the same diff the user last visually reviewed (e.g., compare a content hash/hunk fingerprint), and abort/re-prompt if it has changed, mirroring the report's recommendation to always re-check true end state rather than trusting a previously-computed flag.

### Proof of Concept
1. In a repository, modify a tracked file so it has multiple hunks.
2. In Desktop's Changes view, select the file and deselect a specific line/hunk you don't want committed (e.g., a line containing a secret token), leaving other hunks selected.
3. Before pressing "Commit", let an external process (simulating a build tool/formatter/hook bundled in the repository) insert or remove lines above the hunk you deselected, shifting line offsets but keeping the diff "shape" superficially similar (e.g., add a blank line earlier in the file).
4. Desktop's `updateChangesWorkingDirectoryDiff` reloads the diff and prunes/keeps the selection purely by index (`app/src/lib/stores/app-store.ts:3478-3497`), not by content identity.
5. Press "Commit". `applyPatchToIndex` re-fetches the diff once more and calls `formatPatch`, which stages lines based on `isSelected(absoluteIndex)` against the new hunk layout (`app/src/lib/git/apply.ts:52-81`, `app/src/lib/patch-formatter.ts:129-171`).
6. Inspect the resulting commit: the line the user explicitly deselected (e.g., the secret) is included, while a different, previously-included line is silently dropped — demonstrating that Desktop committed content the user did not intend, without any warning.
