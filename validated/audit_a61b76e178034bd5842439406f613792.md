### Title
Symlink working-directory escape via `resolveWithin` inconsistently applied to "Reveal in File Manager" / "Open File" / "Open in External Editor" actions - (File: app/src/lib/app-shell.ts)

### Summary
GitHub Desktop's own security fix, `resolveWithin` (`app/src/lib/path.ts:36-100`), was built specifically to stop a repo-relative path from resolving — via a symlink planted in the working directory — to a location outside the repository root. This guard is applied only in a couple of call sites (`app/src/ui/dispatcher/dispatcher.ts:1963` for `x-github-client` deep-link file opens, and `app/src/lib/copilot-conflict-context.ts:393` / `app/src/lib/stores/app-store.ts:7233` for Copilot-assisted conflict resolution writes). It is **not** applied to the much more common "Reveal in Finder/Explorer", "Open with Default Program", and "Open in External Editor" context-menu actions in the Changes list, History view, PR files-changed view, stash diff viewer, and manual-conflict resolution UI, all of which build the target path with a plain `Path.join(repository.path, file.path)`.

### Finding Description
`revealInFileManager` in `app/src/lib/app-shell.ts:61-64` does:
```ts
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
```
`Path.join` performs pure lexical joining; it does not resolve symlinks or verify the result stays inside `repository.path`. The exact same unguarded pattern is used for:
- `app/src/ui/changes/sidebar.tsx:282-285` (`onOpenItem` → `openFile`)
- `app/src/ui/history/selected-commits.tsx:384/408/418` (`RevealInFileManagerLabel`, `onOpenInExternalEditor`, `onOpenItem`)
- `app/src/ui/open-pull-request/pull-request-files-changed.tsx:162-199`
- `app/src/ui/lib/conflicts/unmerged-file.tsx:409-417` (manual conflict resolution menu)
- `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:214-233`
- `app/src/ui/changes/filter-changes-list.tsx:628-654`

Contrast this with `app/src/lib/path.ts:36-71`'s `_resolveWithin`, which explicitly `realpath`s both the root and the resolved candidate and rejects the result if it escapes the root — a guard whose own test suite (`app/test/unit/path-test.ts:65-101`) specifically covers "fails for paths that use a symlink to traverse outside of the root." The presence of this dedicated defense, and its deliberate use in `dispatcher.ts` (`openRepositoryFromUrl`) and the Copilot conflict-write path, shows the Desktop team is aware that repo-relative paths from git-tracked or working-directory content cannot be trusted to stay inside the repo when a symlink is involved — yet the guard was not extended to the everyday file-action call sites listed above, which instead only check `pathExists`/file-extension safety (`isSafeFileExtension`), neither of which prevents symlink traversal.

`file.path` values reaching these call sites originate from `git status` (`WorkingDirectoryFileChange`), `git diff --raw` for a commit (`CommittedFileChange`), or PR files-changed data — i.e., content that is fully attacker-controlled if the user clones/fetches/checks out a hostile branch or opens a hostile PR in Desktop. If such content contains (or the working tree ends up containing, via an untracked file placed by a build script or a previous checkout) a symlinked directory pointing outside the repository (e.g., `link -> /`), a git-status entry such as `link/secrets.txt` will cause `Path.join(repository.path, 'link/secrets.txt')` to literally resolve, at the filesystem level, to `/secrets.txt` once the OS follows the symlink component.

### Impact Explanation
- **Reveal in File Manager** (`shell.showItemInFolder`) discloses to the user, and potentially any macOS/Windows Explorer/Finder preview pane, the existence and location of a file outside the repository chosen indirectly by the attacker (path disclosure / minor information exposure), and can be chained with the file-manager's own preview/thumbnail generation.
- **Open with Default Program** (`openFile` → `shell.openExternal('file://' + fullPath)`) and **Open in External Editor** (`launchExternalEditor`/`launchCustomExternalEditor` in `app/src/lib/editors/launch.ts:61-86`) will open/execute the OS default handler or the user's configured editor on a file path that an attacker steered outside of the repository, which can be used for file read outside the repo, or — depending on file type and default handler association — for more impactful effects (e.g., a `.desktop`/`.url`/`.lnk`/shell-script style handler misconfiguration on the victim's machine).
- Overall this matches the "attacker controls a cloned/fetched repository ... and the result is ... file write or read outside the repo" impact category from the report scope.

### Likelihood Explanation
Requires the user to open a malicious/compromised repository (or PR) in Desktop and interact with a normal context-menu action ("Reveal in Finder", "Open with Default Program", "Open in External Editor", or double-click) on an attacker-crafted entry in the Changes/History/PR file list — actions users routinely perform to inspect diffs. No admin rights, local access, or pre-existing malware are needed; the primitive is a symlink checked into (or produced in) the working tree plus a normal file path underneath it. Likelihood is moderated by the fact that `git status`/`git diff` must actually surface a path traversing through the symlink, which depends on git's own symlink-in-tree handling for that platform (behavior can differ slightly between macOS/Linux and Windows, and Windows symlink creation typically requires elevated privileges or developer mode, reducing the Windows attack surface).

### Recommendation
Route every repo-relative `file.path` used to build a filesystem path for `revealInFileManager`, `openFile`, `launchExternalEditor`/`launchCustomExternalEditor`, and the "Copy Path" clipboard actions through `resolveWithin(repository.path, path)` (as already done in `dispatcher.ts` and the Copilot conflict-resolution code), and refuse the action (with the same "path could not be resolved safely" pattern used in `copilot-conflict-context.ts`) when the resolved path is `null`.

### Proof of Concept
This is a code-review-derived analog; it has not been executed against a running Desktop build. Conceptual repro:
1. Attacker publishes/pushes a branch containing a tracked or generated symlink `escape -> /` (or `..\..\..` on Windows, dev-mode/elevated) at the repo root, plus a working-tree entry that git surfaces as `escape/etc/passwd` (or any host path) in `git status`/diff output.
2. Victim clones/fetches this branch in GitHub Desktop and opens the Changes or History view; the crafted entry appears as a normal changed/committed file with path `escape/etc/passwd`.
3. Victim right-clicks the entry and selects "Reveal in Finder/Explorer" (or "Open in default program" / "Open in external editor").
4. `revealInFileManager`/`openFile`/`launchExternalEditor` compute `Path.join(repository.path, 'escape/etc/passwd')`; the OS resolves the `escape` symlink component and the action is performed against the host path outside the repository, whereas `resolveWithin` would have returned `null` and blocked it (as demonstrated by the existing symlink-escape test in `app/test/unit/path-test.ts:65-78`). async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
