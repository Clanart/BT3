### Title
Explicit `GIT_CLONE_PROTECTION_ACTIVE=false` disables Git's built-in clone protection during recursive clones - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` function unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and runs `git clone --recursive` against an attacker-controlled URL. `GIT_CLONE_PROTECTION_ACTIVE` is the toggle Git introduced (as part of the fix for the family of clone/checkout hook-injection vulnerabilities, e.g. CVE-2024-32002/32004/32020/32021) to keep its "unsafe clone" heuristics active by default. By explicitly forcing this to `'false'`, Desktop opts every clone (including all recursively-cloned submodules) out of Git's own safety checks against maliciously-crafted repositories.

This mirrors the report's bug class exactly: a security-relevant value (`beaconChainETHStrategy` in the audit, here the clone-protection guard) is deliberately excluded/disabled from a safety-critical computation path, silently weakening the invariant the rest of the system relies on. In the EigenLayer case the exclusion undercounted burnable shares; here the exclusion removes Git's own runtime defenses against symlinked `.git` directories, case-insensitive-filesystem collisions, and malicious nested/`.gitmodules`-driven hook paths that the upstream Git project added specifically to stop attacker-controlled repositories from achieving code execution or file writes outside the intended clone directory during `clone --recursive`.

Desktop does add its own narrower guard, `isClonePathSensitive()`, which only checks that the destination directory itself isn't a sensitive path like `~/.ssh` — it does nothing to replace the protection Git's own `GIT_CLONE_PROTECTION_ACTIVE` provides for symlink/hooks-path/embedded-git-directory attacks that occur *inside* the cloned tree (including submodules), not at the top-level destination. [3](#0-2) 

Because the URL and its full remote object graph (including `.gitmodules`, submodule URLs, and repository content) are entirely attacker-controlled when a victim clones a malicious or compromised repository, disabling this specific Git-side guard removes exactly the safety net designed for this attacker model.

### Impact Explanation
If a victim clones or opens a malicious repository (or one compromised via supply chain/social distribution, e.g. a link to `github.com/attacker/repo` opened via Desktop's clone flow or an `x-github-client://` deep link), the `--recursive` clone proceeds with Git's clone-protection heuristics turned off. This falls squarely within the listed valid impact categories: "the attacker controls a cloned/fetched repository ... and the result is code execution, file write ... outside the repo." Depending on the exact Git version bundled/available, this can re-expose the classes of vulnerabilities the `GIT_CLONE_PROTECTION_ACTIVE` flag was created to mitigate (malicious submodule paths/hooks causing files to be written outside the working tree or hooks being wired up unexpectedly during a supposedly inert `clone --recursive`).

### Likelihood Explanation
Every clone Desktop performs (including onboarding "Clone a repository" flow and the "Open with GitHub Desktop" deep-link flow) passes through this single `clone()` function with the same hardcoded, unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. No user interaction beyond the ordinary "clone this repo" action is required, and the guard is disabled for 100% of clones, not just an edge case — this is a very high-likelihood, low-friction path for an attacker who can get a victim to clone their repository.

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's default (protection-enabled) behavior is preserved for `git clone --recursive`.
- If Desktop disabled this for a specific compatibility reason (e.g., a legitimate submodule/relative-path/`file://` workflow), scope the override narrowly (only for the specific known-safe scenario) instead of globally disabling it for every clone of arbitrary remote URLs.
- Add regression tests analogous to `app/test/unit/clone-path-safety-test.ts` that assert clone operations retain Git's clone-protection env behavior for untrusted URLs.

### Proof of Concept
1. An attacker publishes a public repository containing a `.gitmodules` file with a submodule crafted to exploit the class of clone-protection bypass Git's `GIT_CLONE_PROTECTION_ACTIVE` guard defends against (e.g., a submodule path designed to collide with `.git`/hooks locations on case-insensitive filesystems).
2. The attacker sends the victim a normal clone URL or an `x-github-client://openLocalRepo`/clone deep link pointing at this repository.
3. Victim clicks "Clone" in GitHub Desktop. Desktop calls `clone(url, path, options)` in `app/src/lib/git/clone.ts`, which invokes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE` forced to `'false'` in the environment.
4. Because Git's own defensive check is disabled, the recursive submodule clone proceeds without the safety heuristics Git otherwise applies, allowing the attacker's crafted repository layout to reach the code paths those heuristics exist to block — potentially writing/executing content outside the intended clone directory.

Note: I could not execute a live clone against a specific vulnerable Git version in this environment to confirm end-to-end code execution; the finding is based on static analysis of `clone.ts` showing the explicit, unconditional disabling of Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard for all attacker-supplied clone URLs, which is the direct config-level analog of the report's "explicitly excluded from a safety-relevant tracking/guard mechanism" bug class.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
