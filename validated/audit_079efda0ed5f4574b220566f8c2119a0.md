### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from the fee/weight calculation, producing transactions that underpay the relay fee or exceed standardness limits - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The NFT-receiver bug class (assets accepted but unusable/stuck) maps onto Serai's Bitcoin wallet as **transactions constructed and signed for a payment that can never confirm/broadcast as built**. In `SignableTransaction::new`, the OP_RETURN `data` output is pushed onto `tx_outs` *before* the weight/vbytes computation, but `calculate_weight_vbytes` is invoked with `payments` only — the data output is never included. Both `needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check are therefore computed over a transaction that is ~90+ vbytes smaller than the one actually signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds the real output list including an OP_RETURN carrying up to 80 bytes of attacker/user-supplied data:

```rust

if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data) ...
``` [1](#0-0) 

Yet the size used for the fee and for the minimum-relay-fee check is computed from `payments` and `tx_ins.len()` alone — the `data` output is absent:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [2](#0-1) 

The same omission propagates into the change path (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at lines 225–227) and into the final standardness check (`if weight > MAX_STANDARD_TX_WEIGHT` at lines 241–243), since `weight`/`weight_with_change` both exclude the OP_RETURN output that is actually present in `self.tx`.

An 80-byte OP_RETURN output adds roughly 90–92 serialized bytes (~368 WU / ~92 vbytes) that are neither paid for nor counted. The `fee()` function confirms the actual fee paid equals `sum(prevouts) - sum(outputs)` — i.e., `needed_fee`, computed on the smaller phantom transaction [3](#0-2) . The signed transaction's effective feerate is `needed_fee / actual_vbytes`, which can drop below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed, or push the real weight over `MAX_STANDARD_TX_WEIGHT` even though the check passed. In both cases the threshold-signed transaction is rejected by the Bitcoin P2P network's mempool policy — the multisig has produced an unusable signature artifact and the payment cannot execute as constructed.

This is reachable by an unprivileged party: `data` is an arbitrary caller-supplied `Option<Vec<u8>>` (checked only against an 80-byte cap at lines 171–173), and any transaction output/witness bytes an external sender causes to be committed are public inputs. A user requesting a Bitcoin payment with attached data (an OutInstruction carrying data, per the integrations spec where `OutInstruction` supports `data: Option<Data>`) causes the signed transaction to be systematically underpriced.

### Impact Explanation
Analogous to the reported bug — assets arriving at a contract that cannot actually receive/use them — the multisig commits signing rounds to a transaction that the Bitcoin network will not accept. Concretely:

- A payment at the minimum relay feerate with any `data` present produces a transaction below the real minimum relay fee, so `sendrawtransaction` rejects it. The payment is stuck until a *new* signing round with different parameters completes; the already-signed transaction is worthless.
- In the worst case (many inputs near `MAX_STANDARD_TX_WEIGHT`), the produced transaction is permanently non-standard — no feerate change can rescue it, so the plan can never execute as signed, stalling the scheduler's Batch/Eventuality for that payment.

Inputs remain owned (the tx is never mined), so this is a liveness/correctness failure of the signing pipeline — Medium, consistent with "funds cannot be moved by the produced transaction" rather than outright theft.

### Likelihood Explanation
Any `data`-bearing Bitcoin send hits the underestimation deterministically; whether it crosses a policy boundary depends on size/feerate. Since the miscount is a fixed ~92 vbytes, the most likely outcome on larger transactions is merely a ~consistent feerate undershoot. Crossing the min-relay or max-weight boundary requires boundary conditions (low specified feerate or near-limit weight), which keeps this at Medium rather than High. Exploitation requires only the ability to attach `data` to a Bitcoin send — no validator collusion, no key access.

### Recommendation
Include the data output in the size model: extend `calculate_weight_vbytes` to accept the OP_RETURN script (its length varies with `data.len()`, so it must be included in the expanded transaction used for `tx.weight()`), or move the OP_RETURN push into `payments`-style accounting before calling it for both the no-change and change paths. Additionally, base the `MAX_STANDARD_TX_WEIGHT` check on the final fully-constructed `tx.weight()` rather than the modeled weight, so any future output-type additions cannot silently bypass the standardness check.

### Proof of Concept
```rust
// Conceptual, against networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80]; // maximally-sized public input, allowed by the len <= 80 check
let tx = SignableTransaction::new(
    vec![scanned_output],          // ReceivedOutput from Scanner::scan_transaction
    &[(payment_script, 546)],      // minimal non-dust payment
    None,
    Some(data),
    fee_per_vbyte,                 // e.g. min relay rate
).unwrap();

// needed_fee was computed for a tx WITHOUT the OP_RETURN output
let paid_fee = tx.fee();                        // == needed_fee
let actual_vbytes = tx.transaction().vsize();   // includes OP_RETURN (~+92 vbytes)
// paid_fee / actual_vbytes < fee_per_vbyte, and can be < DEFAULT_MIN_RELAY_TX_FEE
// -> bitcoind testmempoolaccept / sendrawtransaction rejects the signed tx
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));
assert!(tx.needed_fee() < actual_vbytes as u64 * fee_per_vbyte);
```

Uncertainty note: whether the processor currently forwards user-supplied `data` into `SignableTransaction::new` was not fully verified end-to-end (the OutInstruction→`prepare_send` path in `processor/src/networks/bitcoin.rs` was not inspected in detail); the defect itself in `bitcoin-serai`'s public API is confirmed by the code above regardless of the exact call site.
