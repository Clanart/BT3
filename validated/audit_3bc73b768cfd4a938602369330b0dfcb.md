## Title
Silent, unauthenticated remote-URL rewrite via `updateRemoteUrl`'s "unchanged from API" heuristic when a GitHub repository is renamed/transferred — corrupts push/fetch destination without user consent - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's `origin` remote URL whenever the GitHub API's `clone_url` for the associated `GitHubRepository` differs from the locally configured remote. The decision to auto-rewrite hinges entirely on a heuristic — `remoteUrlUnchanged`, which compares the *locally cached* `gitHubRepository.cloneURL` against the current git remote — with no confirmation from the user and no verification that the "new" clone URL still refers to the repository the user originally added. [1](#0-0) 

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` whenever Desktop refreshes GitHub metadata for a repository (e.g., on app launch, account refresh, or periodic repository indicator refresh), passing in the live GitHub API response (`apiRepo`) for the repo the local git config's `owner/name` currently matches. [2](#0-1) 

Inside `updateRemoteUrl`, the code computes:
```
const remoteUrlUnchanged =
  gitStore.defaultRemote &&
  urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
``` [3](#0-2) 

This mirrors the structure of the reported Linea bug: a critical safety check ("has the user manually changed this value away from what we last observed?") is validated against a **previously cached value** (`gitHubRepository.cloneURL`) rather than against the ground truth of user intent. Just as `dataFinalStateRootHashes[startingDataParentHash]` was empty/stale on the very first post-migration batch — causing the guard to make the wrong decision — `gitHubRepository.cloneURL` can be stale or attacker-influenceable at points where the cached association was only just (re)established:

- The GitHub repository match (`owner`/`name`) used to fetch `apiRepo` is derived from matching the *current* remote URL to a GitHub API repository via `matchGitHubRepository`, not from a durable, user-confirmed identity. Repository name/owner (and hence which GitHub repo the URL resolves to) is attacker-influenceable data: any GitHub user can rename a repository or transfer ownership, and a third party can then create a *new* repository at the old owner/name, causing `api.fetchRepository(owner, name)` to return a **different repository's** metadata (a classic "repo-jacking" scenario) — see the test suite's own "url changes" case, showing the mechanism is designed to auto-follow whatever the API currently reports for that owner/name. [4](#0-3) 
- Since the guard only asks "does the local remote still match `gitHubRepository.cloneURL`, our last-seen API value?" — not "did the user explicitly approve this repository identity?" — once the cached `cloneURL` is refreshed to a squatter/attacker-controlled repo's URL on one refresh cycle, subsequent refreshes will treat *that* attacker URL as the trusted baseline, and any further legitimate-looking API changes will continue to be silently applied.
- There is no verification of repository identity beyond owner/name string matching (no repository ID check), so once an attacker acquires the freed owner/name, `fetchRepository` will resolve to the attacker's repo indefinitely, and `updateRemoteUrl` will silently retarget the user's `origin` remote to it.

The result: `git remote set-url origin <attacker_url>` is executed without any dialog, confirmation, or diff shown to the user — corrupting where the user's future `git push`/`git fetch` operations go, entirely silently. This satisfies the "silent corruption of what the user commits or pushes" impact category, and the "attacker controls a GitHub API object" precondition, because the entire decision path is driven by `apiRepo.clone_url`, which is fully attacker-controlled once they control the repo behind `owner/name`.

### Impact Explanation
If exploited, a user's local git remote is silently rewritten to point at an attacker-controlled repository. Since GitHub Desktop performs pushes/fetches based on the configured remote, this can lead to:
- The user unknowingly pushing commits (and their content) to a repository they do not control, exposing potentially private code to the attacker.
- The user pulling/fetching from and later basing further work on attacker-supplied content without any indication the remote changed.
- Credential exposure risk: HTTPS credential helpers / cached tokens may be sent to the attacker's endpoint if the hostname portion also changes and Desktop's credential resolution logic keys off the remote URL.

This is a silent corruption of push/fetch destination, matching the specified valid-impact class.

### Likelihood Explanation
The trigger conditions are realistic and require no local/physical access, admin rights, or social engineering beyond normal GitHub repository lifecycle events (rename/transfer/deletion+recreation of a repo name) which are common and already a known "repo-jacking" attack pattern on GitHub. The check runs automatically as part of normal background repository-info refresh flows (`repositoryWithRefreshedGitHubRepository`), so no unusual user action is needed to trigger the vulnerable code path — only that the user has previously used the affected owner/name at some point and the attacker later reclaims it.

### Recommendation
- Do not silently auto-update the remote URL based solely on matching the previously cached `cloneURL`. Require the repository's stable numeric ID (available in `IAPIRepository`) to match between the original association and the refreshed one before treating a clone-URL change as a legitimate rename/transfer.
- When the underlying repository ID differs (i.e., owner/name now points to an unrelated GitHub repository), do not auto-rewrite the remote; instead, surface a warning/dialog to the user before changing `origin`.
- Log/audit remote URL changes made automatically, and consider requiring explicit user confirmation any time the remote URL changes as a result of an automatic background refresh rather than a user-initiated action.

### Proof of Concept
1. User adds a GitHub repository `github.com/victim-org/handy-lib` in Desktop; Desktop stores `gitHubRepository.cloneURL = https://github.com/victim-org/handy-lib` and configures `origin` to the same URL.
2. `victim-org` renames or deletes `handy-lib` (or the repo becomes orphaned/renamed away), freeing the `victim-org/handy-lib` name (or, alternately, `victim-org` itself is deleted/renamed by GitHub after account compromise/expiry — the specific mechanism only needs to make `owner/name` resolve to a different underlying repo).
3. Attacker creates a new repository also reachable as `victim-org/handy-lib` (through org name reuse, repo re-creation, or a similar-looking fork accepted by matching logic) with `clone_url = https://github.com/attacker/handy-lib-evil`.
4. On next periodic refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` which now returns the attacker's repo metadata as `apiRepo`.
5. `updateRemoteUrl` computes `remoteUrlUnchanged = urlMatchesRemote(gitHubRepository.cloneURL /* old victim URL */, gitStore.defaultRemote /* still victim URL */)` → `true`, and `urlsMatch = false` (new clone_url differs), so the guard `protocolsMatch && remoteUrlUnchanged && !urlsMatch` passes.
6. `gitStore.setRemoteURL('origin', apiRepo.clone_url)` executes `git remote set-url origin https://github.com/attacker/handy-lib-evil` with no prompt to the user.
7. The user's next `git push` sends their work to the attacker's repository, and the next `git fetch`/pull may merge attacker-controlled history into the user's working tree — confirmed feasible by the existing test `"updates the repository's remote url when the github url changes"` which demonstrates the exact automatic rewrite path with no user interaction. [4](#0-3)

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
