Based on my research, I found a genuine array/string-index parsing bug in `parseCommitSHA` that structurally mirrors the Pendle bug: a fixed index is extracted from a tokenized string, but the token layout shifts under certain (attacker-influenceable) conditions, so the code silently extracts the wrong field and treats it as the commit SHA.

### Title
`parseCommitSHA()` Returns Wrong Token as Commit SHA for Root Commits, Corrupting the SHA Returned by `createCommit()`/`createMergeCommit()` - (File: app/src/lib/git/core.ts)

### Summary
`parseCommitSHA()` extracts the commit SHA from `git commit`'s first output line by doing `stdout.split(']')[0].split(' ')[1]`, hard-coding index `1` as the position of the SHA token. This assumption only holds for the ordinary `[<branch> <sha>]` format. When the commit is the repository's first ("root") commit, Git emits `[<branch> (root-commit) <sha>]`, inserting an extra token before the SHA, so index `1` resolves to the literal string `(root-commit)` instead of the SHA [1](#0-0) .

### Finding Description
`parseCommitSHA` is the single source of truth GitHub Desktop uses to learn the SHA of a commit it just created, used by both `createCommit()` and `createMergeCommit()`: [1](#0-0) [2](#0-1) [3](#0-2) 

Just like Pendle's bug — where a fixed array index (`[0]`) was assumed to always be the "output amount" but was actually the "input amount" once the return-array shape changed — `parseCommitSHA` assumes token index `1` is always the SHA. That assumption breaks the moment Git's own output format inserts an additional token, which happens deterministically whenever the commit being created is the very first commit in the repository (`git commit` prints `(root-commit)` in that case). Because an attacker fully controls the content and history of a repository they publish (including publishing a repository/branch with **zero commits**), they can trivially force the user's very first commit action in Desktop against that repository to be a root commit, guaranteeing this code path executes with the corrupted parse.

No guard exists: `parseCommitSHA` performs no validation that the extracted token actually looks like a SHA (e.g. hex format/length check) before returning it as "the commit SHA" to callers.

### Impact Explanation
The broken invariant is: *the value returned by `createCommit`/`createMergeCommit` is guaranteed to be the created commit's SHA.* When violated, the string `"(root-commit)"` is silently returned and treated as a real SHA by any caller. This is analogous to Pendle's `returned` variable silently holding the wrong (but still numeric/plausible-looking) value — here Desktop silently holds a wrong (and non-hex) value as an identifier for the commit it just made. Any downstream logic that treats the return value as a real, comparable SHA (e.g., recording it for commit-message autocompletion, amend/undo bookkeeping, telemetry, or comparing it against `HEAD` to confirm the commit landed) will operate on bad data, silently diverging from what was actually committed — i.e., silent corruption of the app's understanding of what the user just committed, without any error being surfaced to the user.

### Likelihood Explanation
High for triggering the parse bug itself: any first commit to a repository with no prior history (a state fully controllable by whoever creates/hosts the repository the victim clones) deterministically produces the `(root-commit)` format and thus the wrong parse — no special user interaction beyond "clone an empty/fresh repo and make the first commit" is required. What is unverified (I could not trace it further given the available context) is exactly which UI/store code consumes the return value of `createCommit`/`createMergeCommit` and whether that consumer's misuse of the bad SHA can be escalated to a concretely damaging action (e.g., an incorrect `reset`/`revert` target). That downstream consumption path would need to be inspected in the full `app/src/lib/stores` code to confirm the worst-case severity.

### Recommendation
Do not rely on a fixed token index. Parse the trailer robustly, e.g. by matching the SHA with a regex such as `/\[[^\]]*\s([0-9a-f]{7,40})\]/` against the raw stdout, or better, avoid parsing human-readable porcelain output entirely and retrieve the SHA via `git rev-parse HEAD` (or `--format=%H`) immediately after the commit succeeds.

### Proof of Concept
```ts
import { parseCommitSHA } from './core'

// Normal commit
parseCommitSHA({ stdout: '[master 8b32213] Initial commit\n 1 file changed' } as any)
// => '8b32213'  (correct)

// Root commit (first commit ever in the repo) — Git inserts "(root-commit)"
parseCommitSHA({ stdout: '[master (root-commit) 8b32213] Initial commit\n 1 file changed' } as any)
// => '(root-commit)'  (WRONG — not a SHA at all)
```
An attacker need only host/publish a fresh repository with no commits; when the victim clones it in GitHub Desktop and makes their first commit, `createCommit()`/`createMergeCommit()` returns `"(root-commit)"` instead of the real SHA [2](#0-1) .
