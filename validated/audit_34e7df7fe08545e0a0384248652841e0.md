### Title
Native-token transfers to a byte-cast (unassociated) address can permanently and irrecoverably fail once that address is associated to a different account — ([File: x/evm/keeper/address.go])

### Summary
The external report's bug class is: a contract that must receive native coin as part of a withdrawal/bridge-back flow has no way to actually receive it, so the transfer always reverts and the funds can never be pulled back. Sei-chain has a structurally similar trap at the EVM↔Cosmos address-bridge layer: a Cosmos `AccAddress` that is the direct 20-byte cast of an EVM address becomes permanently blocked from receiving `usei`/`wei` bank transfers once that EVM address has been associated with a *different*, real Sei address. Any code path (precompile, EndBlock settlement, EVM value transfer) that later tries to route native funds to that byte-cast address will always fail with `ErrInvalidRecipient`, with no way to recover.

### Finding Description
`Keeper.CanAddressReceive` implements the invariant: [1](#0-0) 

```
// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr)
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	return associatedAddr.Equals(addr) || !isAssociated
}
```

Once an EVM address is associated to a real Sei address via `SetAddressMapping` [2](#0-1) , the plain byte-cast `AccAddress` derived from that same EVM address stops being able to receive funds — this check is wired into `app.go` (referenced twice) as a bank send-restriction/blocked-address hook, so it is enforced by the generic `bank` module's coin-movement path, not just EVM code.

This matters because Sei's EVM↔Cosmos bridging relies heavily on exactly this kind of byte-cast address whenever an explicit association hasn't happened yet — e.g. `GetSeiAddressOrDefault` / `GetEVMAddressOrDefault` fall back to `common.BytesToAddress(seiAddress)` / `sdk.AccAddress(evmAddress[:])` throughout the precompile and StateDB code: [3](#0-2) 

Native-value transfers driven by EVM execution (`CALL{value: ...}`, precompile `sendNative`, wasmd precompile coin forwarding, or EndBlock coinbase-surplus settlement) all funnel through `bank.SendCoinsAndWei` / `AddCoins` / `AddWei`, e.g.: [4](#0-3) [5](#0-4) 

If a user, a precompile caller, or bridging logic ends up sending funds to a plain byte-cast recipient address whose EVM counterpart has since been associated to a *different* real key (a state transition entirely reachable by an ordinary user simply calling the association precompile/tx), every subsequent attempt to credit that address will hit `CanSendTo`/`CanAddressReceive` and fail with `ErrInvalidRecipient`. Unlike a Solidity `receive()`-less contract, where the caller controls whether to retry or design around it, here the failure condition is created unilaterally by a *third party* (whoever associates that EVM address), and it is permanent — the recipient can never again receive funds at that address, mirroring the report's "no way to get funds out" scenario but for inbound transfers created earlier by other flows.

### Impact Explanation
Any escrowed/pending native-token flow (bridge withdrawal parameters, precompile-mediated payments, or scheduled EndBlock settlements such as coinbase surplus sweep) that targets a byte-cast recipient address becomes permanently undeliverable the moment that EVM address is associated by anyone. Funds routed to such a destination are effectively frozen — the same "cannot receive native coin, so it just fails forever" impact class as the referenced report, but triggered without any code deployment mistake, purely through the ordinary association flow that any user can invoke.

### Likelihood Explanation
Likelihood is high because: (1) address association is a routine, permissionless, unprivileged user action; (2) byte-cast addresses are the default fallback used pervasively (`GetSeiAddressOrDefault`/`GetEVMAddressOrDefault`) whenever no explicit association exists yet, meaning many legitimate transfers target such addresses; and (3) the failure is silent from the sender's perspective until the transfer is attempted, at which point it deterministically and permanently reverts.

### Recommendation
- When queuing/pending a native-coin transfer to an address that is currently unassociated (byte-cast), re-validate `CanAddressReceive` at the time of actual settlement, not just at initiation, and provide a fallback recovery path (e.g., re-route to the associated Sei address, or an explicit reclaim/refund mechanism) if the destination becomes blocked in the interim.
- Ensure any deferred/EndBlock settlement logic (e.g., `EndBlock` coinbase surplus sweep) that sends to potentially byte-cast addresses handles `ErrInvalidRecipient` by crediting an escrow account instead of silently dropping/failing the sweep, so funds are not stranded.

### Proof of Concept
Not applicable in this repo-analysis context — this is a design-level invariant issue in `CanAddressReceive`/`CanSendTo`, not a single reproducible transaction; a full PoC would require (1) sending native funds via an EVM tx/precompile call to a byte-cast address `X` before any association exists, succeeding, then (2) having `X`'s corresponding EVM address later call the association flow with a different keypair, and (3) demonstrating that any subsequent transfer targeting the original byte-cast `X` (e.g., another `AddWei`/`AddCoins` call) now permanently fails with `ErrInvalidRecipient`. Full verification of the exact `app.go` wiring of `CanAddressReceive` into the bank module's send-restriction hook was not completed within the available investigation and should be confirmed before treating this as fully proven.

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])

		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))

		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

func (k *Keeper) GetSeiAddress(ctx sdk.Context, evmAddress common.Address) (sdk.AccAddress, bool) {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.EVMAddressToSeiAddressKey(evmAddress))
	if bz == nil {
		return []byte{}, false
	}
	return bz, true
}

func (k *Keeper) GetSeiAddressOrDefault(ctx sdk.Context, evmAddress common.Address) sdk.AccAddress {
	addr, ok := k.GetSeiAddress(ctx, evmAddress)
	if ok {
		return addr
	}
	return sdk.AccAddress(evmAddress[:])
}
