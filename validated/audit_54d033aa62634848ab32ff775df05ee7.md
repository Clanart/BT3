### Title
Unauthenticated `dispatch()` lets any caller drain pooled ETH from `CallDispatcher` — ("unnecessary ETH acceptance" analog escalated to fund theft) - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report flags contracts that implement `receive() external payable {}` without needing ETH, risking stuck funds. `CallDispatcher` in this repo has the same unnecessary `receive()` [1](#0-0) , but unlike the reported contracts, it also exposes a fully public, unauthenticated `dispatch()` function that forwards attacker-chosen `value` to attacker-chosen `to` addresses out of the contract's own balance. This turns "stuck ETH" into "stealable ETH": any ETH that ever lands in `CallDispatcher` (via its own `receive()`, via `selfdestruct`, or via cross-chain `onAccept` flows in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` that call `ICallDispatcher(_dispatcher).dispatch(message.data)`) can be swept out by any unprivileged caller.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an attacker-supplied `Call[]` and executes: [2](#0-1) 

There is no access control (no `onlyHost`, no restriction to a specific caller) on `dispatch()` — it is `external` and callable by anyone, and `call.value` and `call.to` are fully attacker-controlled fields decoded from the input parameter, not tied to `msg.value`. Combined with the unconditional `receive() external payable {}` [1](#0-0) , any ETH balance held by this contract (accumulated from direct sends, `selfdestruct` forced-ETH, or leftover value from cross-chain apps that invoke `ICallDispatcher.dispatch` in `onAccept`/`onPostRequestTimeout` handlers, e.g. `WrappedHyperFungibleToken.onAccept` calling `ICallDispatcher(_dispatcher).dispatch(message.data)`) [3](#0-2)  is a shared pool with no ownership tracking per depositor. Because `dispatch()` is unauthenticated, any external account can encode a `Call[]` with `to = attacker`, `value = address(this).balance`, `data = ""` and drain the entire pooled balance to themselves.

This differs from the reported issue's "funds get stuck" framing: here the unnecessary ETH-accepting `receive()` combined with an unauthenticated value-forwarding entrypoint produces an active theft primitive rather than a mere fund-lock.

### Impact Explanation
Any ETH balance accrued in `CallDispatcher` — whether from accidental sends, `selfdestruct`-forced transfers, or transient balances left over from cross-chain message execution — can be stolen by an arbitrary unprivileged caller, since `dispatch()` performs `to.call{value: call.value}(call.data)` with no check that the caller is authorized or that `call.value` is bounded to funds the caller is entitled to. This is a direct loss-of-funds primitive matching the bounty's "stealing or loss of funds" / "unauthorized execution" categories.

### Likelihood Explanation
Exploitability depends entirely on `CallDispatcher` actually holding a nonzero ETH balance at some point. Since `receive()` accepts ETH unconditionally and the contract is wired into cross-chain `onAccept` flows (`WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`) that call `dispatch(message.data)` where message.data can encode calls carrying `value`, any residual value left in the dispatcher (e.g., a `Call` that under/over-forwards `msg.value` due to rounding, refunds, or repeated `receive()` deposits) becomes drainable. I was not able to fully trace, given remaining tool budget, whether the current call sites always send exactly matching ETH with `dispatch()` calls (i.e., whether a nonzero standing balance is actually reachable in practice) — this is the main uncertainty in confirming real-world triggerability versus a theoretical unauthenticated drain path.

### Recommendation
- Remove `receive() external payable {}` from `CallDispatcher` if it never needs to hold ETH; require the caller (`msg.sender`) to be the intended actor and forward `msg.value` directly per call, or
- Restrict `dispatch()` to a trusted caller (e.g., an approved app/host) and validate that `call.value` amounts sum to `msg.value` sent alongside the dispatch call, ensuring no shared pooled balance without an accounting mechanism.
- Following the same pattern recommended for `TradableSettings` in the external report, eliminate any unconditional ETH acceptance where the contract has an established non-ETH message-passing method and no legitimate need to custody native value.

### Proof of Concept
1. Any actor sends ETH directly to `CallDispatcher` (accepted unconditionally by `receive()`), or ETH becomes stranded there via a cross-chain `onAccept` call that invokes `dispatch(message.data)` with a `Call.value` that doesn't fully account for the ETH forwarded.
2. Attacker calls `CallDispatcher.dispatch(encoded)` where `encoded` decodes to `Call[] = [{to: attacker, value: address(this).balance, data: ""}]`.
3. `dispatch()` executes `attacker.call{value: address(this).balance}("")` with no authorization check, transferring all pooled ETH to the attacker. [2](#0-1)

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```
