### Title
Silent commit-content corruption from path-keyed status map when a staged deletion and untracked re-creation share the same path - ([File: app/src/lib/git/status.ts])

### Summary
`getStatus` builds the working-directory file list by folding `git status --porcelain=2 -z` entries into a `Map<string, WorkingDirectoryFileChange>` keyed on the raw file **path** rather than a status-aware identifier [1](#0-0) . This mirrors the SFPM bug class exactly: a key ("path", analogous to "position key") can legitimately be "touched" more than once by distinct, semantically different entries in the same status output, and the reducer's last-write-wins semantics silently discard one of them.

### Finding Description
`buildStatusMap` explicitly acknowledges that Git can report two different lines for the same path — a staged deletion (`1 .D ...`) and a re-created untracked file (`?? ...`) — and "resolves" the collision by deleting whichever entry was previously stored under that path key whenever an untracked entry for the same path is processed:

```
if (status.kind === 'untracked') {
  // when a delete has been staged, but an untracked file exists with the
  // same path, we should ensure that we only draw one entry in the
  // changes list - see if an entry already exists for this path and
  // remove it if found
  files.delete(entry.path)
}
...
files.set(entry.path, new WorkingDirectoryFileChange(entry.path, appStatus, selection))
``` [2](#0-1) 

This logic implicitly assumes:
1. Only the untracked-vs-staged-deletion overlap can ever produce two entries sharing a path, and
2. The order of entries emitted by `git status --porcelain=2 -z` (and thus by `parsePorcelainStatus`) always places the entry that should "win" (the untracked one) after the one that should be discarded (the staged deletion).

Neither assumption is defended against structurally. The `Map` is keyed purely by `entry.path`, with no verification of which `kind` of collision is occurring or in which order. `parsePorcelainStatus` simply preserves whatever order Git's porcelain stream returns (interleaved by type: `1`/`2` changed entries, then `u` unmerged, then `?` untracked, then `!` ignored) [3](#0-2) . If an attacker-controlled repository/working state — e.g. delivered via a crafted merge, stash pop, submodule checkout, or rename operation that a victim performs against a hostile remote — produces a path collision that is *not* the untracked/staged-delete pair the code anticipates (for example a rename whose destination path coincides with another path, or any future/edge-case Git status combination that emits multiple lines for one path), `files.set()` silently overwrites the earlier `WorkingDirectoryFileChange` with no cleanup or warning, while `AppFileStatus`/selection state computed for the discarded entry (e.g. conflict markers, "Deleted" status, or partial-selection diff data) simply vanishes from `IStatusResult.workingDirectory`.

This directly parallels the SFPM issue: the code assumes a `1:1` relationship between a key and a specific piece of state ("chunk liquidity" vs. "net liquidity" in SFPM; "file status" vs. "path" in Desktop), but the key can be touched multiple times, and the equality/overwrite check does not hold in general.

### Impact Explanation
If the discarded entry corresponds to `AppFileStatusKind.Deleted` or `Conflicted` state while the retained entry is `Untracked`/`New`, the Changes list and diff view shown to the user no longer reflects the true index state. Since `WorkingDirectoryStatus.fromFiles` and the commit flow both operate purely off this `files` array [4](#0-3) , a user could stage/commit or discard changes based on a UI view that has silently dropped a status entry — i.e., what gets committed or pushed can diverge from what the user saw and intended, satisfying the "silent corruption of what the user commits" impact class. It does not, on the evidence gathered, provide direct code execution or credential exfiltration; the concretely demonstrable case (staged-delete + untracked overlap) is the one already anticipated by the comment, so the realistic residual risk is limited to less-common/edge-case Git status combinations that were not verified to exist in current Git versions in the time available.

### Likelihood Explanation
The mechanism is triggerable purely by controlling repository content (a hostile remote, submodule, or merge target) that produces two porcelain-v2 lines for the same path — no local access, elevated privileges, or pre-existing malware is required, satisfying the "attacker controls a cloned/fetched repository" precondition. However, I was not able to fully verify from the indexed code/tests whether Git can emit a *second* colliding-path scenario beyond the documented staged-delete/untracked case (i.e., a concrete reproducible sequence of git operations was not confirmed within available tool budget), so likelihood of an exploitable, attacker-triggerable second collision path is uncertain rather than confirmed.

### Recommendation
Key the working-directory map by a status-aware identifier (the same `kind+path[+oldPath]` scheme already used for `FileChange.id`, see `app/src/models/status.ts:263-275`) instead of the raw path, and only apply the deliberate untracked/staged-deletion merge as a special, explicitly-checked case (verifying the existing entry actually is the staged-deletion counterpart) rather than an unconditional `Map.delete`/`Map.set` on bare path.

### Proof of Concept
Not independently reproduced against a live Git binary within this investigation; the concrete overlap case documented in the code (staged deletion + untracked file at the same path, e.g. via `git rm --cached <path>` followed by recreating `<path>` in the working tree, or an equivalent state introduced by a hostile merge/stash) demonstrates the collision mechanism itself: [5](#0-4) 
A background Devin session with terminal access would be needed to confirm whether an ordering or additional-collision variant that defeats the `files.delete(entry.path)` safeguard is reachable from a crafted repository state.
