### Title
`SchnorrAggregate::verify` accepts a trivially-forged "empty" aggregate signature — an attacker who can make a verifier evaluate an empty signer set bypasses signature verification entirely - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
CVE-2016-2790 concerns a data structure whose memory was never initialized, so attacker-influenced bytes were treated as a valid object. The in-scope analog is the inverse edge of the same class: `SchnorrAggregate::read` accepts an aggregate with zero `Rs`, and `SchnorrAggregate::verify` treats the resulting *empty* statement list as valid — the aggregated equation degenerates to `s·G == identity`, so any blob encoding `len = 0, s = 0` verifies. The "data structure" (the set of `(key, challenge)` pairs the signature is claimed to bind to) was never populated, yet verification still returns `true`.

### Finding Description
`SchnorrAggregate::read` reads a `u32` count and zero or more `R` points with no lower bound:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

`verify` only checks length equality between `self.Rs` and the caller-supplied `keys_and_challenges`, then queues pairs; with both empty, the multiexp contains only `(-s, G)`:

```rust
// crypto/schnorr/src/aggregate.rs:127-145
if self.Rs.len() != keys_and_challenges.len() { return false; }
...
let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() { ... }
pairs.push((-self.s, C::generator()));
multiexp_vartime(&pairs).is_identity().into()
```

With `Rs = []`, `keys_and_challenges = []`, `s = 0`, `pairs = [(0, G)]` → `is_identity()` → `true`. No `signers.len() > 0` or `Rs.len() > 0` guard exists anywhere. The concrete consumer, `Validators::verify_aggregate` (`coordinator/tributary/src/tendermint/mod.rs:201-229`), checks only `signers.len() != aggregate.Rs().len()` — where `signers` is derived from the untrusted block data itself — then calls `aggregate.verify`, so a block/transaction claiming an empty signer set with the 36-byte payload `00 00 00 00 || 0x00*32` passes signature verification unconditionally.

### Impact Explanation
An aggregate signature that never bound to any public key, nonce, or message is accepted as valid. Wherever aggregate-signature validity is used as the authorization check (Tendermint commit verification in `coordinator/tributary`, and any external consumer of `crypto/schnorr`), a public-input-only attacker can satisfy it with constant bytes — a forged signature over no keys. Concrete exploitation requires a call path that accepts an attacker-chosen (possibly empty) signer set without an independent quorum/weight check; `verify_aggregate` itself performs none, so the check is pushed to consensus weight accounting rather than enforced at the cryptographic boundary. Impact on any consumer that fails to independently require `signers.len() >= quorum` is a full signature forgery.

### Likelihood Explanation
The bytes are fully attacker-controlled (`SchnorrAggregate::read` over wire data) and the bypass requires no grinding — `s = 0` is deterministic. The mitigating factor is that a real BFT layer should reject a block claiming zero signers before or alongside signature verification, and an honest aggregator (`SchnorrAggregator::complete`, `aggregate.rs:175-178`) never produces an empty aggregate. The bug is real and trivially triggerable at the library level; whether it yields forged acceptance depends on callers that the crypto layer is supposed to protect.

### Recommendation
Reject empty aggregates at both boundaries:
- In `SchnorrAggregate::read` (or `verify`), return an error/`false` when `Rs.is_empty()`.
- In `Validators::verify_aggregate` (`coordinator/tributary/src/tendermint/mod.rs:201-229`), require `!signers.is_empty()` (and ideally a minimum weight threshold) before invoking `aggregate.verify`.
- Optionally reject `s == 0` aggregates, since an all-zero witness cannot be produced by an honest `SchnorrAggregator`.

### Proof of Concept
```rust
use schnorr::aggregate::SchnorrAggregate;
use ciphersuite::{group::ff::Field, Ciphersuite};
use dalek_ff_group::Ristretto;

// Forged aggregate: len = 0, s = 0
let mut forged = vec![0u8; 4];
forged.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());

let agg = SchnorrAggregate::<Ristretto>::read::<&[u8]>(&mut forged.as_slice()).unwrap();
// Verifies despite binding to zero keys, zero nonces, zero challenges
assert!(agg.verify(b"any dst", &[]));
```

Via the Tendermint path: `Validators::verify_aggregate(&[], msg, &forged)` returns `true` for any `msg`, since `signers.len() == aggregate.Rs().len() == 0` and `verify` succeeds.
