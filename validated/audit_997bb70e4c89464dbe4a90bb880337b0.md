## Analog Identified: ProtoJSON parser exceptions embed unredacted, attacker-controlled field values (bypassing the `debug_redact` protection that Protobuf itself defines)

### Title
ProtoJSON parse-error messages leak raw field values, bypassing `debug_redact` sensitive-field protection - (File: `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java`, `python/google/protobuf/json_format.py`)

### Summary
The Jenkins report's failed invariant is: "text written into logs by exception messages must not contain unmasked sensitive values." Protobuf explicitly recognizes this exact invariant for the `debug_redact` field option — TextFormat/`DebugString()` deliberately replaces annotated field values with `[REDACTED]` before they can appear in debug/log output [1](#0-0) , and the option's own documentation states it exists "e.g. when the field contains sensitive credentials" [2](#0-1) . However, the ProtoJSON parsing error paths in Java's `JsonFormat` and Python's `json_format` never consult this redaction annotation: when a client-supplied JSON value fails to parse into a field, the raw, attacker-controlled JSON value is concatenated directly into the thrown exception's message.

### Finding Description
`JsonFormat.Parser` in Java builds parse-error messages by string-concatenating the raw `JsonElement` text into the exception, for numbers, booleans, enums, maps, and repeated-field mismatches: [3](#0-2) [4](#0-3) [5](#0-4) 

None of these call sites check `field.getOptions().getDebugRedact()` before embedding the value, unlike `TextFormat.Printer`, which explicitly performs this check via `TryRedactFieldValue`/`shouldRedact` before ever printing a field's contents [6](#0-5) .

Python's `json_format.py` exhibits the identical pattern: `_ConvertFieldValuePair` wraps the underlying `ValueError`/`TypeError`/`ParseError` with the field name, and separately embeds the raw `value` directly for repeated/type mismatches (`'repeated field {0} must be in [] which is {1} at {2}'.format(name, value, path)`), again with no `debug_redact` check: [7](#0-6) 

C#'s `JsonParser` follows the same pattern, embedding the raw numeric `value` into `InvalidProtocolBufferException` messages on overflow/range errors: [8](#0-7) 

### Impact Explanation
Any consuming application that parses untrusted ProtoJSON via `JsonFormat.parser().merge(...)` (Java), `json_format.Parse(...)` (Python), or `JsonParser.Parse(...)` (C#) and later logs, surfaces, or returns the caught exception's `getMessage()`/`str(e)`/`.Message` — a very common pattern for API error responses and application logs — will have the raw, attacker-supplied field content (which may include values intended to be marked sensitive via `debug_redact`, or otherwise sensitive strings/numbers submitted by the caller) written unmasked into that log/response. This is precisely the CWE-522/CWE-779 class in the report: sensitive data reaching an output channel (logs/error responses) without the masking that the same codebase already implements for `DebugString`. Impact is confined to information disclosure (Confidentiality: Low), matching the report's CVSS vector (`C:L/I:N/A:N`).

### Likelihood Explanation
This is trivially reachable by any ordinary client sending a bounded, malformed ProtoJSON payload through the public `JsonFormat`/`json_format`/`JsonParser` parse APIs — no privileged access or schema tampering is required. It only requires the schema to contain a `debug_redact`-annotated (or otherwise sensitive) field and a type/format mismatch on that field's JSON value (e.g., sending a string where an int is expected, or a scalar where an array is expected). The application must additionally log/surface the exception message for actual exposure, which is a common but not universal integration pattern — hence Medium rather than High likelihood.

### Recommendation
Extend the ProtoJSON parsers' error-construction paths (Java `JsonFormat.Parser` numeric/enum/map/repeated-field error sites, Python `json_format._ConvertFieldValuePair`/`_ConvertAndSetScalar`, C# `JsonParser`) to check `FieldDescriptor.options().debug_redact()` (mirroring `TextFormat::Printer::TryRedactFieldValue`/`shouldRedact`) and substitute a `[REDACTED]`-style placeholder for the offending value before it is embedded into any thrown `InvalidProtocolBufferException`/`ParseError` message.

### Proof of Concept
Given a proto schema:
```proto
message Secret {
  string token = 1 [debug_redact = true];
}
```
A Java caller does:
```java
try {
  JsonFormat.parser().merge("{\"token\": {\"nested\":\"ignored\"}}", Secret.newBuilder());
} catch (InvalidProtocolBufferException e) {
  log.error("parse failed", e); // e.getMessage() embeds the raw offending JSON, unredacted
}
```
Because `token` is typed `string` but the client sends an object, `JsonFormat` throws with the raw JSON echoed into the message (per the `"...but found " + json` / `"Not a ... value: " + json` patterns cited above), and no `debug_redact` check intervenes — unlike the equivalent `DebugString()` path, which would print `[REDACTED]` for the same field. This is a direct code-path comparison inside the checkout (`TextFormat` redacts; `JsonFormat`/`json_format`/`JsonParser` do not), demonstrating the missing check without requiring speculative execution.

bool TextFormat::Printer::TryRedactFieldValue(
    const Message& message, const FieldDescriptor* field,
    BaseTextGenerator* generator, bool insert_value_separator) const {
  TextFormat::RedactionState redaction_state =
      DescriptorPool::MemoizeProjection(
          field, [](const FieldDescriptor* field) {
            return TextFormat::GetRedactionState(field);
          });
  if (redaction_state.redact) {
    if (redact_debug_string_) {
      IncrementRedactedFieldCounter();
      if (insert_value_separator) {
        generator->PrintMaybeWithMarker(MarkerToken(), ": ");
      }
      generator->PrintString(kFieldValueReplacement);

        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {
          generator->PrintLiteral("\n");
        }
      }
      return true;
    }
  }
  return false;
}
