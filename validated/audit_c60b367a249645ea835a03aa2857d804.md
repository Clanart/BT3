### Title
Git credential helper trusts a spoofable `WWW-Authenticate` realm header to classify arbitrary hosts as GitHub, before validating protocol/TLS - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
GitHub Desktop's git credential trampoline decides whether a remote host should be treated as a "GitHub"/"enterprise" endpoint (and therefore whether Desktop's GitHub sign-in/OAuth flow and stored GitHub tokens are relevant to it) largely based on unauthenticated, attacker-controllable signals - most notably a `WWW-Authenticate: ... realm="GitHub"` response header that git itself forwards to the credential helper as `wwwauth[n]` fields. This mirrors the report's bug class: a security-relevant classification ("is this host trusted/local/GitHub") is made from a value that is easy for an attacker to spoof, rather than from an authoritative, unspoofable check, and the check that *would* catch bad cases (protocol/TLS) is applied too late.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` is invoked from `getCredential`, `storeCredential`, and `eraseCredential` for every git credential request that the trampoline services (i.e., every `git fetch`/`clone`/`push`/submodule operation Desktop performs) [1](#0-0) .

Inside `getEndpointKind`, after checking the endpoint against known dotcom/GHE hosts, the function inspects git-forwarded `wwwauth[...]` credential fields and, if any value contains `realm="GitHub"`, immediately classifies the endpoint as `'enterprise'` - i.e., a legitimate GitHub Enterprise host: [2](#0-1) 

Crucially, the HTTPS-only sanity check that exists later in the same function: [3](#0-2) 
is only reached if the `wwwauth[...]` realm check does *not* match. This means the realm-based classification is evaluated **before** any transport-security validation, so a plain-HTTP git remote (or an on-path attacker performing a MITM/TLS-downgrade against a git server) can trivially set `WWW-Authenticate: Basic realm="GitHub"` on a 401 response and have Desktop treat an arbitrary, attacker-chosen host as `'enterprise'`.

Once classified as `'enterprise'`, `getCredential` checks whether an account is already registered for the corresponding API endpoint; if not, it invokes `ui.promptForGitHubSignIn(endpoint)` [4](#0-3) , surfacing a "Sign in to GitHub" prompt that the user reasonably attributes to a trusted git operation, for a host the user never asked to authenticate to. If an account *does* already exist for that origin (`findGitHubTrampolineAccount` matches purely by `origin` string equality, not by any stronger binding) [5](#0-4) , the stored token is handed back to git as the credential for that host via `credWithAccount` [6](#0-5) .

The classification's only requirement is that the response body/headers contain the literal string `realm="GitHub"` - it does not verify the host is `github.com`/`*.ghe.com`, does not require a valid TLS certificate, and does not perform any of the network-based confirmation that `isGitHubHost()` (`app/src/lib/api.ts`) otherwise performs for other cases. This is the same class of flaw as the Nextcloud report: the guard (`isGHE`, `isDotCom`) is bypassed by an alternate, attacker-forgeable representation of "GitHub-ness" (a spoofed header) that the real validation logic does not additionally scrutinize.

### Impact Explanation
- Any git remote the user fetches/clones/pushes to - including a malicious repository the user is asked to clone, or a compromised/MITM'd proxy sitting on a plain-HTTP or otherwise interceptable git transport - can trigger Desktop to misclassify itself as talking to "GitHub"/"GitHub Enterprise."
- If the user already has a GitHub account configured whose HTML-URL origin happens to collide with the attacker's chosen origin (feasible for GHE users pointing at custom domains, or via DNS tricks/subdomain reuse), Desktop will hand the stored OAuth token to git for that connection, which git will then send to the attacker-controlled server - direct **credential/token exfiltration**.
- Even without an existing matching account, the attacker can force an unsolicited "Sign in to GitHub" prompt bound to their host during what looks like a normal git operation, which is a strong social-engineering primitive for account/OAuth phishing that a user would not expect from simply fetching a repo.

### Likelihood Explanation
Triggering the `wwwauth[...]` realm path requires nothing more than controlling the server (or a MITM position) that Desktop's underlying `git` process talks to during a fetch/push/clone - exactly the "attacker controls ... a git remote/proxy response" scenario called out as in-scope. No local access, admin rights, or pre-existing malware is required; the only user action needed is a normal, expected one (adding/cloning/fetching a repository), which is not an "unnatural" step.

### Recommendation
- Do not use the `wwwauth[...]` `realm="GitHub"` header as a standalone trust signal. At minimum, require it to be accompanied by an HTTPS transport and either a certificate matching a known GitHub/GHE fingerprint or a successful confirmation via the existing `isGitHubHost()` network probe.
- Move the `credentialUrl.protocol !== 'https:'` check before the `wwwauth` inspection so plain-HTTP hosts can never be classified as `'enterprise'`.
- Bind stored GitHub accounts/tokens to endpoints using a stronger identity check than raw origin string equality (e.g., pinned endpoint identifiers established at sign-in time) so credential handoff cannot be redirected to a look-alike or attacker-controlled origin.

### Proof of Concept
1. Set up an HTTP git server (or a MITM proxy in front of a plain `http://` git remote) that, on any authentication challenge, responds with `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add/clone a repository whose remote points at that server (`http://attacker.example/repo.git`).
3. When Desktop's git process performs the fetch and receives a 401 with the crafted header, it forwards `wwwauth[0]=Basic realm="GitHub"` to the trampoline credential helper.
4. `getEndpointKind` classifies `attacker.example` as `'enterprise'` per [7](#0-6) , before the HTTPS-only fallback check would have rejected it.
5. Observe Desktop either (a) presenting an unsolicited GitHub sign-in prompt for `attacker.example`, or (b) - if the user has an account whose endpoint origin matches - silently supplying that account's stored token as the git credential for `attacker.example`, which git then transmits to the attacker's server.

Note: I was not able to fully trace `trampoline-ui-helper.ts`'s `promptForGitHubSignIn` implementation within the available iterations, so the exact downstream UX (e.g., whether the sign-in dialog explicitly displays the untrusted hostname, and whether OAuth completion could bind the real token to the attacker's endpoint) is not fully confirmed and should be verified directly in that file before treating the sign-in-prompt phishing vector as conclusively proven; the token-leak path via `findGitHubTrampolineAccount`'s origin-equality matching is, however, directly supported by the cited code.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
