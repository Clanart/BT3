## Analog Identified

The external report's core issue is: a value that shares its wire-format with a different, security-sensitive value gets mistaken for that sensitive value without any check that it was legitimately produced (the "private key looks like an assetID" confusion). The Hyperbridge analog is `Pallet::decode_receipt_relayer`, which reinterprets an attacker-controlled, unauthenticated byte blob as a *verified* `Signature` and extracts its embedded address as the "delivering relayer" — without ever calling `Signature::verify`.

### Title
Relayer/reward beneficiary spoofing via unverified `Signature` decoding of an attacker-controlled receipt blob - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`RequestReceipts[commitment]` on a substrate destination is populated with `msg.signer`, a raw `Vec<u8>` field of the incoming `RequestMessage` that is **not cryptographically bound to anything** [1](#0-0) . When the fee-accumulation and outbound-request-reward paths later read this receipt back from a state proof, `decode_receipt_relayer` treats any blob longer than 32 bytes as a SCALE-encoded `Signature` enum and returns `.signer()` directly — without ever calling `Signature::verify` [2](#0-1) . Since `.signer()` for `Signature::Evm` simply returns the embedded `address` field verbatim [3](#0-2) , an attacker can plant an arbitrary address as the "proven" delivery signer with no valid signature at all.

### Finding Description
When a `PostRequest`/`GetRequest` is delivered to a substrate destination, the handler stores `msg.signer` as-is into the request receipt: `host.store_request_receipt(&wrapped_req, &msg.signer)` [4](#0-3) . `msg.signer` is documented only as "Signer information. Ideally should be their account identifier" — it is not verified against any cryptographic proof in the request-handling path [5](#0-4) . The `handle` extrinsic that carries this message is unsigned/permissionless (`validate_unsigned`), so any caller who supplies a valid membership proof for the request can set `msg.signer` to whatever bytes they choose.

Later, two separate reward flows read this receipt back via a destination state proof and call `Pallet::decode_receipt_relayer` to determine "who delivered this and should be paid":

- `accumulate_fees` (relayer fee accumulation) [6](#0-5) 
- `process_outbound_request_delivery_claim` (BRIDGE reward for hyperbridge-originated requests) [7](#0-6) 

For substrate destinations, the decode logic is:
```rust
let bytes = <Vec<u8>>::decode(&mut &*raw)...?;
Ok(if bytes.len() > 32 {
    Signature::decode(&mut &*bytes)...?.signer()
} else {
    bytes
})
``` [2](#0-1) 

If the attacker crafts `msg.signer` as the SCALE encoding of `Signature::Evm { address: <attacker_address>, signature: <any 65 bytes> }` (total length > 32 bytes), `decode_receipt_relayer` will successfully decode it and return `address` as the "delivering relayer" — `Signature::signer()` never checks that `signature` actually verifies against any message [3](#0-2) . The genuine cryptographic `Signature::verify` path exists elsewhere in the same file (used for the *beneficiary redirect*, not for this receipt decode) [8](#0-7) , confirming that the receipt-decode path is missing the check that the analogous beneficiary-redirect path has.

### Impact Explanation
This breaks the "relayer rewards must move only to the rightful beneficiary" invariant: an unprivileged caller who submits (or colludes to submit) a `RequestMessage`/timeout/response delivery to a substrate destination can plant an arbitrary "signer" blob in `RequestReceipts`, then later claim the fee-accumulation reward (`accumulate_fees`) or the outbound-request delivery reward (`claim_outbound_request_delivery_reward`) to an address of their choosing — regardless of who actually paid gas to deliver the message. This is direct theft/misdirection of protocol funds (relayer fees and BRIDGE treasury payouts), matching "stealing or loss of funds" / "wrong beneficiary or amount" in the impact gate.

### Likelihood Explanation
The entrypoints involved (`handle` for message delivery, `accumulate_fees`/`claim_outbound_request_delivery_reward` for payout) are all public, permissionless, unsigned extrinsics that only require a valid state/membership proof of the underlying request — no admin, prover, or peer-compromise assumption is needed. The only additional requirement is crafting a >32-byte blob that decodes as a `Signature` variant, which is a straightforward SCALE-encoding exercise.

### Recommendation
`decode_receipt_relayer`'s substrate branch must not treat receipt bytes as a trusted `Signature` unless it also calls `Signature::verify` against a well-defined message (e.g., the request commitment) and confirms the recovered signer matches the embedded `address`/`public_key`, exactly as already done for the beneficiary-redirect signature in the same file. Alternatively, the receipt stored by `store_request_receipt` should be constrained to the real dispatch-origin account (not an attacker-suppliable free-form field), removing the ambiguity between "raw account bytes" and "structurally similar encoded Signature" entirely.

### Proof of Concept
1. Attacker observes (or is) the party submitting a legitimate `RequestMessage` delivery to a substrate destination chain, with a valid membership proof for the request.
2. Attacker sets `msg.signer` to the SCALE encoding of `Signature::Evm { address: <attacker_evm_addr>, signature: [0u8; 65] }` (a >32-byte blob). Note `signature` never gets cryptographically checked in this path.
3. The handler stores this blob verbatim: `host.store_request_receipt(&wrapped_req, &msg.signer)` [9](#0-8) .
4. Once the request is delivered/finalized, anyone (including the attacker) submits `accumulate` (fee accumulation) or `claim_outbound_request_delivery_reward` with a state proof of `RequestReceipts[commitment]` for that destination.
5. `decode_receipt_relayer` decodes the stored blob, sees length > 32, decodes it as `Signature::Evm`, and returns `address` (the attacker's address) as the "delivering relayer" with zero cryptographic validation [2](#0-1) .
6. The relayer fee / outbound reward is credited to `attacker_evm_addr` [10](#0-9) .
