### Title
Unbounded RPC-retry livelock in `get_outputs` lets any external depositor permanently stall Bitcoin block scanning - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
CVE-2024-55563 describes transaction-relay jamming: flooding/malformed traffic that prevents time-critical transaction propagation, yielding a network-reachable availability loss (CVSS 5.3, A:L). The same "an unprivileged on-chain party can halt processing" class exists in Serai's Bitcoin network handler: `Bitcoin::get_outputs` enters an infinite retry loop fetching the parent transaction of a deposit's first input, so a single attacker-crafted deposit transaction whose parent cannot be resolved via `get_transaction` stalls the processor's block scanner forever.

### Finding Description
For every transaction in a confirmed block that pays to a scanned Serai address, `get_outputs` fetches `tx.input[0].previous_output.txid` via `self.rpc.get_transaction` to populate `presumed_origin`: [1](#0-0) 

```rust
let mut tx;
while {
  tx = self.rpc.get_transaction(&spent_tx).await;
  tx.is_err()
} {
  log::error!("couldn't get transaction from bitcoin node: {tx:?}");
  sleep(Duration::from_secs(5)).await;
}
tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
```

There is no bound, no error propagation, and no fallback: any permanent lookup failure spins forever at 5-second intervals inside `get_outputs`, which is awaited under the scanner's write lock in `Scanner::run`: [2](#0-1) 

Two additional amplifying facts:

- `get_transaction` on Bitcoin Core only resolves arbitrary transactions when `txindex=1` (or they are mempool/wallet txs). A deposited output whose first input spends a parent not retrievable by the configured node hits this path. Even with txindex, transient error classes are not distinguished — the code retries identically for "not found" (permanent) and connection failures.
- The same `while ... is_err() { sleep }` pattern blocks `get_eventuality_completions` when resolving the block number and intermediate blocks, so the failure mode is systemic, not confined to one call site. [3](#0-2) 

### Impact Explanation
Reachability: any unprivileged party can send a Bitcoin transaction paying to Serai's External/Branch/Change/Forwarded addresses (the scanner registers these scripts per key in `scanner()` [4](#0-3) ). Once such a transaction confirms and `scanner.scan_transaction` matches it, `get_outputs` unconditionally enters the presumed-origin fetch. If the parent-tx lookup persistently fails, `Scanner::run` never advances `ram_scanned`, no `ScannerEvent::Block` is emitted, no Batch is produced for that or any subsequent block, and the processor's funds pipeline halts — a permanent availability loss for the Bitcoin leg of the bridge, directly analogous to the relay-jamming A:L impact of the CVE. The `swap_remove(usize::try_from(input.previous_output.vout).unwrap())` indexing is a secondary panic risk: a coinbase-like or malformed prevout pointing past the parent's output count would crash the processor outright, though valid consensus txs prevent that on mainnet.

### Likelihood Explanation
Medium. The trigger requires only a confirmed transaction to a Serai address — cheap and fully public — but the livelock additionally requires the parent lookup to fail permanently. That occurs when the bitcoind RPC lacks `txindex` (a supported configuration, since Serai only needs block/tx lookups it implements), when the parent lives in a pruned block range, or under sustained RPC errors. Because the retry loop never gives up or falls back to `presumed_origin: None`, a single such deposit converts a transient/node-config issue into a permanent stall requiring manual intervention.

### Recommendation
Bound the retry loop and degrade gracefully: after N failures, set `presumed_origin` to `None` (the field is already `Option<Address>` [5](#0-4) ) and continue scanning rather than blocking. Additionally, distinguish permanent "transaction not found" errors from transient connection errors and fail fast on the former, and bounds-check `input.previous_output.vout` against `tx.output.len()` instead of `unwrap`/`swap_remove` panicking.

### Proof of Concept
```rust
// Conceptual PoC against processor/src/networks/bitcoin.rs::get_outputs
// 1. Attacker creates tx A paying an arbitrary script, confirms it in a block range
//    the Serai bitcoind node cannot serve via `gettransaction` (no txindex /
//    pruned, or mempool eviction of a 0-conf parent).
// 2. Attacker creates tx B spending A:0 as input[0], paying >= DUST sats to the
//    Serai External p2tr address (script_pubkey matching Scanner::new(key)).
// 3. B confirms. Scanner::run -> get_outputs -> scan_transaction matches B,
//    then `while rpc.get_transaction(parent_of_B).is_err() { sleep(5s) }`
//    spins forever inside the write-locked scanner loop.
// 4. ram_scanned never advances; no further ScannerEvent::Block emitted;
//    all Bitcoin deposits/withdrawals halt.
```

The corresponding panic variant is `tx.unwrap().output.swap_remove(vout)` if the fetched parent has fewer outputs than `previous_output.vout` claims — only reachable with non-consensus data, so the livelock is the primary issue.
