### Title
Global (non-per-sender) gasless bundle-tx quota lets a single sender DoS all gasless users - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The gasless module enforces two *global* caps — `MaxBundleTxsInQueue` and `MaxBundleTxsInPending` — on the total number of gasless bundle (approve+swap) transactions the tx pool will admit/promote, exactly the shared-limit pattern described in the report (a single actor exhausting a shared rate/quota resource to lock out every other user). Unlike the PSM's per-duration reset, here there is no per-account share and no automatic reset window tied to time; the quota is a raw global counter checked against `knownTxs`, so one address can occupy the entire allowance and block all other public callers' gasless swaps from being pooled/promoted.

### Finding Description
`PreAddTx` rejects any new bundle tx once the global queue counter reaches the configured cap, regardless of who submitted the prior transactions: [1](#0-0) 

`GetMaxBundleTxsInQueue`/`GetMaxBundleTxsInPending` default to 200/100 and can be disabled only by an operator flag, but by default they are small, fixed, shared numbers with no per-sender partition: [2](#0-1) 

Similarly, promotion into `pending` is gated by a global `numExecutable` count compared against `maxBundleTxsInPending`, again with no per-account isolation: [3](#0-2) 

`numQueue()`/`numExecutable()` are computed over the entire `knownTxs` map shared by all senders: [4](#0-3) 

A single externally-owned account can generate many approve+swap bundle-tx pairs (increasing its own nonce sequentially) and submit them to the public RPC/tx pool. Each pair is only checked for structural validity, decodability, and (depending on `BalanceCheckLevel`) balance/allowance sufficiency at admission time — none of these checks are prohibitively expensive to satisfy for the attacker's own funds, and they say nothing about limiting the *number* of self-submitted bundle txs. Once the attacker's txs fill `numQueue()`/`numExecutable()` up to the configured caps, every other user's gasless bundle tx is rejected with `ErrBundleTxQueueFull` at `PreAddTx`, or fails the `IsReady` promotion check and is silently held un-promoted, exactly analogous to the reported PSM DoS where one user maxes out a shared mint/redeem allowance.

### Impact Explanation
This blocks the entire gasless transaction path (and, by extension, gasless-fee-sponsored users and their intended token swaps/approvals) for all senders until the attacker's transactions clear via `QueueTimeout`/`PendingTimeout`/`KnownTxTimeout` (10s/10s/30s) or are mined — but the attacker can keep resubmitting from the same or new accounts to keep the global quota saturated indefinitely, similar to how the PSM attacker could keep resetting/re-exhausting the rate limit window. This is a availability/DoS impact against a public-facing feature (gasless swaps) reachable by any unprivileged transaction sender, matching Medium severity per the reference report's classification of this bug class.

### Likelihood Explanation
Likelihood is Medium: the caps default to 200 (queue) / 100 (pending), which is a nontrivial but attacker-affordable number of self-issued approve+swap pairs, each merely requiring the attacker to hold nonzero token balance/allowance for itself (attacker can use its own token/router pair or trivial amounts) — there is no fee-based cost differentiation preventing a sender from occupying most/all of the shared quota with its own sequential nonces, since the checks in `checkBalanceForApprove`/`checkBalanceForSwap` only validate the attacker's own balances, not a systemic anti-spam cost per the shared resource.

### Recommendation
Partition `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` per sender (or per unique token/router) in addition to (or instead of) a single global counter in `knownTxs.numQueue()`/`numExecutable()`, so no single account can consume the entire shared quota. Consider adding a per-address sub-limit inside `PreAddTx`/`IsReady` and/or an eviction/priority scheme (e.g., first-come reservation with per-address caps) so legitimate users are not starved. Continue to expose `MaxBundleTxsInPending`/`MaxBundleTxsInQueue` as tunable governance/CLI parameters, but document that they must be set considering worst-case single-sender consumption, and add off-chain monitoring on `txpool/knowntxs/num/*` metrics (already emitted in `kaiax/gasless/impl/tx_counter.go`) to detect anomalous single-sender saturation.

### Proof of Concept
1. Attacker generates N ≈ `MaxBundleTxsInQueue` (default 200) sequential approve+swap bundle-tx pairs from a single EOA it controls, using tokens/allowances it owns (satisfying `checkBalanceForApprove`/`checkBalanceForSwap`).
2. Attacker submits all pairs to the public RPC/tx pool in rapid succession. Each call passes `IsModuleTx`/`GetCheckBalance` and is admitted by `PreAddTx` until `knownTxs.numQueue()` reaches `MaxBundleTxsInQueue`. [5](#0-4) 
3. Any subsequent legitimate user's approve/swap bundle tx submitted while the attacker's txs remain in `queue`/`pending` is rejected with `ErrBundleTxQueueFull`, or fails to be promoted because `numExecutable+numSeqTxs > maxBundleTxsInPending`. [6](#0-5) 
4. Attacker repeats step 1–2 as the previous batch times out (`QueueTimeout`/`PendingTimeout`/`KnownTxTimeout`), keeping the shared gasless-tx admission channel continuously saturated and denying gasless service to all other users.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

// Check promotion condition and enforce pending pool flow control.
func (g *GaslessModule) IsReady(txs map[uint64]*types.Transaction, next uint64, ready types.Transactions) bool {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	tx, ok := txs[next]
	if !ok {
		return false
	}

	if !g.isReady(txs, next, ready) {
		return false
	}

	if g.IsBundleTx(tx) {
		// If prev tx is bundle tx, there's no need to check the knownTxs limit because it has been checked in the previous `IsReady()` execution.
		isPrevTxBundleTx := len(ready) != 0 && g.IsBundleTx(ready[len(ready)-1])
		if isPrevTxBundleTx {
			g.knownTxs.add(tx, TxStatusPending)
			return true
		}

		maxBundleTxsInPending := g.GetMaxBundleTxsInPending()
		if maxBundleTxsInPending != math.MaxUint64 {
			numExecutable := uint(g.knownTxs.numExecutable())

			numSeqTxs := uint(1)
			for i := next + 1; i < next+uint64(len(txs)); i++ {
				if tx, ok := txs[i]; ok && g.IsBundleTx(tx) {
					numSeqTxs++
				} else {
					break
				}
			}

			// false if there is possibility of exceeding max bundle tx num
			if numExecutable+numSeqTxs > maxBundleTxsInPending {
				logger.Trace("Not promoting a tx because of exceeding max bundle tx num", "tx", tx.Hash().String(), "numExecutable", numExecutable, "maxBundleTxsInPending", maxBundleTxsInPending)
				return false
			}
		}

		g.knownTxs.add(tx, TxStatusPending)
	}

	return true
}

func (k knownTxs) numPending() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusPending {
			num++
		}
	}
	return num
}

func (k knownTxs) numExecutable() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusPending && !knownTx.tx.IsMarkedUnexecutable() {
			num++
		}
	}
	return num
}

func (k knownTxs) numQueue() int {
	num := 0
	for _, knownTx := range k {
		if knownTx.status == TxStatusQueue {
			num++
		}
	}
	return num
}
