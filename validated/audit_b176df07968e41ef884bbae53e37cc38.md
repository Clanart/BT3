### Title
`ReceivedOutput::read` accepts an unvalidated offset/output pairing, letting untrusted bytes claim outputs are spendable by Serai when they are not - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` is the sole authority that legitimately produces `ReceivedOutput`s: it maps a `script_pubkey` to the scalar offset needed to spend it (`scan_transaction`, `networks/bitcoin/src/wallet/mod.rs:199-214`). However, `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) deserializes `offset`, `output`, and `outpoint` from raw bytes with no check that `output.script_pubkey == p2tr(scanner.key + offset·G)`. Any consumer that ingests a serialized `ReceivedOutput` from an untrusted source will treat the claimed output as a spendable deposit, exactly the "false compatibility signal" bug class: the bytes assert "spendable via this offset" while nothing verifies the assertion.

### Finding Description
`ReceivedOutput::read` performs only structural decoding:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  output = TxOut::consensus_decode(&mut buf_r)?;
  outpoint = OutPoint::consensus_decode(&mut buf_r)?;
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

The struct's invariants are enforced only by `Scanner::scan_transaction`, which builds a `ReceivedOutput` exclusively from `self.scripts.get(&output.script_pubkey)` — i.e., the offset is always the one registered for that exact script. The deserializer bypasses this entirely: `offset` is never checked against `output.script_pubkey`, and the `Scanner`'s `key`/`scripts` map is never consulted. This is analogous to `L2ECO` implementing `IL2StandardERC20`: a public artifact carries a signal ("this output is spendable with this offset") that the validation path trusts without verifying the underlying capability.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (it is a listed untrusted-bytes sink) can:

- Report an arbitrary on-chain output (e.g., one paying to the attacker's own script) as a Serai deposit spendable with a chosen offset. Downstream scheduling that signs a spend using `keys.offset(offset)` (the spend path in `send.rs` derives the signing view from `output.offset()`) will produce a signature for `key + offset·G` — which does not correspond to the attacker's script — yielding an invalid transaction after the network has credited/acted on the "received" funds.
- More dangerously, per the documented warning at `wallet/mod.rs:177-179`, arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script". A crafted `{offset, output}` pair lets the attacker steer which effective key/scripts the signer operates on, decoupled from what `register_offset` securely registered.

The concrete result is funds reported received that are not spendable, or signing resources committed to outputs that can never be moved — locked funds and corrupted deposit accounting.

### Likelihood Explanation
Reachable by any unprivileged party able to supply serialized `ReceivedOutput` bytes (peer-provided scan data, imported/replayed blobs). No key material, threshold collusion, or validator status is required; the attacker only crafts a `Scalar || TxOut || OutPoint` byte string. `read_F` accepts any canonical scalar, and consensus decoding accepts any `TxOut`/`OutPoint`.

### Recommendation
Either:

- Bind deserialization to a `Scanner`: change the API to `Scanner::read_output(&self, r)` that, after decoding, verifies `self.scripts.get(&output.script_pubkey) == Some(&offset)` and rejects otherwise; or
- Store the internal key in `ReceivedOutput` and check `output.script_pubkey == p2tr_script_buf(key + G·offset)` (with parity handling per `needs_negation`), failing the read on mismatch.

### Proof of Concept
```rust
let mut bytes = Vec::new();
// arbitrary offset
bytes.extend(Scalar::ONE.to_bytes());
// TxOut paying to an attacker-controlled script_pubkey
let attacker_output = TxOut { value: Amount::from_sat(50_000), script_pubkey: attacker_script };
bytes.extend(serialize(&attacker_output));
bytes.extend(serialize(&OutPoint::new(real_txid, 0)));

let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// ro is accepted; downstream code treats attacker_script's output as spendable
// via offset == 1, which it is not.
```
