### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls corrupts `prevEventsLen`, causing StateDB balance desync from bank state - ([File: precompiles/common/balance_handler.go])

### Summary
`RunNativeAction` in `precompiles/common/precompile.go` creates a `balanceHandler` via `p.BalanceHandlerFactory.NewBalanceHandler()` per precompile invocation and uses `BeforeBalanceChange`/`AfterBalanceChange` to translate `x/bank` (and `x/precisebank`) events emitted during the native action into `StateDB.AddBalance`/`SubBalance` calls, keyed on the event slice `ctx.EventManager().Events()[bh.prevEventsLen:]`. The repo's own test, `evmd/tests/integration/balance_handler/balance_handler_test.go` (`TestRecursivePrecompileCallsWithDebugPrecompile`), documents that when a precompile call is re-entered recursively/nested (e.g., a contract calling a precompile which calls back into another/the same precompile), a shared `BalanceHandler` state is at risk of having `prevEventsLen` overwritten, so previously-emitted bank events get either replayed or skipped when reconciling into the EVM `StateDB`. This mirrors the `OperatorDelegator.getTokenBalanceFromStrategy()` bug class: an index/key used to track "already accounted for" state is clobbered by a nested/second invocation, causing incorrect accounting of value.

### Finding Description
`RunNativeAction`/`runNativeAction` (`precompiles/common/precompile.go:46-126`) does:
1. `balanceHandler := p.BalanceHandlerFactory.NewBalanceHandler()` — this allocates a **new** handler per top-level `RunNativeAction` call. [1](#0-0) 
2. `balanceHandler.BeforeBalanceChange(ctx)` records `bh.prevEventsLen = len(ctx.EventManager().Events())`. [2](#0-1) 
3. After executing `action(ctx)`, `balanceHandler.AfterBalanceChange(ctx, stateDB)` walks `events[bh.prevEventsLen:]` and applies `StateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event, to keep the EVM `StateDB` in sync with actual bank-level balance mutations performed by the precompile's native Cosmos SDK call. [3](#0-2) 

The design assumes each precompile invocation's event window `[prevEventsLen, len(events))` is disjoint and fully "consumed" exactly once. However, if a precompile call synchronously re-enters the EVM (e.g., via `CallEVM`/another precompile call, or a contract call that calls back into a precompile) *before* the outer call's `AfterBalanceChange` executes, and the recursive call also constructs a handler from the *same* `BalanceHandlerFactory` bound to the same underlying `ctx.EventManager()`s events accumulator, the nested `BeforeBalanceChange` overwrites/moves the effective "already consumed" boundary. The `evmd/tests/integration/balance_handler/balance_handler_test.go` `TestRecursivePrecompileCallsWithDebugPrecompile` test exists specifically to demonstrate this — it forces recursive precompile calls (`callback(0)`) and asserts on the exact count of `debug_precompile` events, showing the code path was written to catch/guard the case where nested calls corrupt event accounting. [4](#0-3) [5](#0-4) 

If the guard is imperfect for some nested/recursive call ordering not covered by that specific test (e.g., different precompile types calling each other, or reentrant calls through `ics20`/`erc20`/`distribution`/`staking`/`bank` precompiles that perform `SendCoinsFromModuleToAccount` etc.), some bank-level `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` events would either be double-applied to `StateDB` (inflating an EVM-visible balance beyond what bank/precisebank actually holds — free value creation) or skipped (bank moves funds but EVM `StateDB` view doesn't reflect it, causing balance desync that can be exploited to make the EVM environment believe an account has more/less spendable balance than the bank ledger, enabling double-spends within the same transaction's nested calls, or committing an incorrect balance to `StateDB.Commit()`.

### Impact Explanation
If the `prevEventsLen` corruption causes double-application of `AddBalance` on `StateDB` for the same underlying bank credit, this is unauthorized minting of EVM-visible balance not backed by an equivalent bank/precisebank ledger entry — a direct violation of the required 1:1 accounting invariant between native coins and EVM-visible balances (`x/vm` statedb vs `x/bank`/`x/precisebank`). Conversely, if events are skipped, a legitimate bank-level credit is not reflected in `StateDB`, and on `Commit()` the discrepancy could result in balance corruption or permanent loss/freezing of the credited value from the EVM's perspective (unspendable via EVM despite existing in bank state, or vice versa erasable). Both are Critical-class outcomes per the impact gate (irreversible accounting corruption / unauthorized creation of spendable value across EVM balances).

### Likelihood Explanation
This requires an unprivileged user to trigger recursive/nested precompile calls in a single EVM transaction — e.g., a smart contract that calls a precompile (bank/distribution/staking/ics20/erc20) which in turn triggers another precompile call or a re-entrant call path — which is achievable by any contract deployer without special privileges. The repository maintainers have already identified this exact bug class and added a targeted regression test (`TestRecursivePrecompileCallsWithDebugPrecompile`) using a purpose-built `debugprecompile` and `DebugPrecompileCaller` contract specifically to reproduce "recursive calls that share the same BalanceHandler instance", which strongly suggests this was a real, previously-existing, and only partially-mitigated defect. I could not fully verify from the available index whether the current code fully closes every recursive-call ordering (e.g., across different precompile addresses, or with intermediate plain contract calls between two precompile invocations), because I do not have visibility into the complete precompile dispatch/call-stack code (e.g., how nested `RunNativeAction` calls interact when the outer handler hasn't yet run `AfterBalanceChange`) or the full `debugprecompile`/`DebugPrecompileCaller` contract source, which the codebase index does not fully expose.

### Recommendation
- Verify that `BalanceHandlerFactory`/`BalanceHandler` correctly nest: instead of a flat `prevEventsLen` int that can be overwritten by a reentrant call, use a stack-based or reference-counted mechanism so that each nested `RunNativeAction` call captures its own event window and restores the outer caller's window correctly upon return (analogous to properly scoping `queuedShares` per the correct key rather than a globally shared/overwritable value).
- Add invariant checks (e.g., in CI / integration tests) that assert, for arbitrary depths and orderings of nested precompile calls across different precompile types (bank, distribution, staking, ics20, erc20), that the sum of `StateDB` balance deltas applied via `AfterBalanceChange` exactly matches the net bank/precisebank ledger deltas for the whole transaction — not just the specific reproduced case in the existing test.
- Consider deriving the event window from an explicit event index snapshot/pointer object owned by the specific `RunNativeAction` call frame (e.g., closures over `len(events)` at entry, restored via defer) rather than a mutable field on a shared struct, to make the correctness independent of reentrancy depth or call ordering.

### Proof of Concept
The repository already contains a proof-of-concept demonstrating the underlying mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go`'s `TestRecursivePrecompileCallsWithDebugPrecompile` deploys a `DebugPrecompileCaller` contract that invokes `callback(0)` against a registered `debugprecompile`, causing recursive precompile invocations within a single EVM transaction, and asserts specific event counts (`15` total events, `10` `debug_precompile` events) to detect any divergence caused by `prevEventsLen` corruption. [6](#0-5) 

I was unable to fully trace the exact conditions (call depth, precompile-address mixing) under which the current guard could still fail, because the complete precompile call-stack code and the `debugprecompile`/`DebugPrecompileCaller` contract implementation were not available in the indexed context — a Devin session with full repository access would be needed to construct a concrete failing sequence (e.g., contract → precompile A → precompile B → precompile A) and confirm whether `StateDB` balances diverge from bank ledger balances after `Commit()`.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
