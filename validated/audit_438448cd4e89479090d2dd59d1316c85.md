### Title
Cached FROST preprocess seed is never invalidated, enabling deterministic nonce reuse across distinct signed messages (ROS-style share recovery) - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol::preprocess_internal` persists a FROST preprocess RNG seed in the `CachedPreprocesses` DB keyed only by `context`, and `from_cache` re-derives identical nonces on every call. Because the cached seed is never deleted or rotated after a share is produced, every subsequent `share_internal`/`complete` invocation signs again with the same FROST nonces `(d, e)`, even for different messages. This mirrors the reported bug class — security-critical state (the one-time preprocess "session") is not invalidated after use/key-context change.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), a 32-byte `ChaCha20Rng` seed is generated once per `context` and stored XOR-masked under `CachedPreprocesses::set(self.txn, &self.context, &cache.0)` (line 134). On every later call, the same seed is loaded and passed to `AlgorithmSignMachine::from_cache` (lines 137-145). `from_cache` routes to `seeded_preprocess` (crypto/frost/src/sign.rs:121-144), which deterministically regenerates the identical nonce pair `(d, e)` and identical commitments from `ChaCha20Rng::from_seed(*seed.0)`.

The cache is never invalidated: there is no `CachedPreprocesses::del`/overwrite after `sign` succeeds. `share_internal` calls `preprocess_internal(...).0` (line 156) and then `machine.sign(preprocesses, msg)` (line 170). `DkgConfirmer::complete` calls `share_internal` a second time (line 322) — with a `key_pair` supplied in the call — producing another share under the same `(d, e)` but over a *different* `set_keys_message` whenever the supplied `key_pair` differs (lines 296-301). `preprocess()` (line 285) and `share()` (line 309) likewise each re-derive the same machine.

The `context` is `(b"DkgConfirmer", attempt)` (line 275) — it does not include the message/`key_pair`, the participant mapping, or `removed`, so it cannot distinguish distinct signing sessions within an attempt.

### Impact Explanation
FROST nonce reuse across distinct messages enables recovery of the signer's secret share. Each emitted share has the form `s = d + rho·e + c·λ·x` where `rho` (binding factor) and `c` (Schnorr challenge) are publicly computable from the broadcast preprocess commitments and the message. With `k` distinct signed messages under the same `(d, e)`, the attacker obtains `k` linear equations in `d`, `e`, `x`. Three distinct `key_pair`/`msg` values signed under one attempt context yield a solvable 3×3 system, revealing the coordinator's MuSig/FROST secret share `x` — full compromise of that validator's threshold signing key, enabling forgery of set-keys confirmations and, combined with threshold-many compromised shares, arbitrary signatures.

Even two reuses with a controlled preprocessing set (attacker-influenced preprocess map in `share`/`complete`, which flows through `threshold_i_map_to_keys_and_musig_i_map`) reduce the entropy and, per the documented contract, reuse "will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:85-87, 211-213; spec/cryptography/FROST.md:51-55).

### Likelihood Explanation
The inputs that trigger re-signing — `preprocesses`, `shares`, and `key_pair` — all arrive as serialized tributary/protocol messages handled by `DkgConfirmer::share`/`complete`, i.e., bytes supplied by other participants in the confirmation protocol. A single `share()` call followed by `complete()` with any mutated `key_pair` already produces a second signature under the same nonces. No reboot or race is required; determinism is guaranteed by `from_cache`. Likelihood is bounded by needing multiple distinct `key_pair` messages accepted under one `(DkgConfirmer, attempt)` context, hence Medium-High rather than Critical.

### Recommendation
Treat the cached preprocess as single-use and invalidate it on consumption:
- Delete `CachedPreprocesses` entry (or store a "spent" tombstone) inside `share_internal` before/after `machine.sign`, and refuse to sign if the entry is already spent — `complete` must reuse the `AlgorithmSignatureMachine` produced by `share` rather than re-running `share_internal`.
- Alternatively, bind the seed context to the full signing instance: include `key_pair`/message hash and the `removed`/participant set in `context` so distinct messages can never share a seed.
- Persist which `(context)` values have already produced a share and assert-once in `share_internal`, mirroring the `AttemptDb` pattern used in `processor/src/batch_signer.rs`.

### Proof of Concept
1. Under attempt `A`, `preprocess_internal` stores seed `S` under context `(b"DkgConfirmer", A)` and emits preprocess `P` (commitments `D=d·G`, `E=e·G`).
2. Call `DkgConfirmer::share(preprocesses, key_pair_1)` → emits `s1 = d + ρ1·e + c1·λ·x` for `m1 = set_keys_message(set, removed, key_pair_1)`.
3. Call `DkgConfirmer::complete(preprocesses, key_pair_2, shares)` where `key_pair_2 ≠ key_pair_1` → `share_internal` reloads `S`, regenerates the same `(d, e)`, and emits `s2 = d + ρ2·e + c2·λ·x` for `m2`.
4. Repeat with `key_pair_3` → `s3`. Solve the linear system `{s_i = d + ρ_i·e + c_i·λ·x}` (ρ_i, c_i, λ all public) for `x` → coordinator's secret share recovered.

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
