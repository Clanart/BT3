### Title
Excess native-token overpayment on `dispatch()`/`fundRequest()` is trapped in `EvmHost` instead of being refunded to the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the direct on-chain analog of the reported `SecuritizeBridge.bridgeDSTokens()` issue: a user who must guess an exact native-token amount to cover a fluctuating quote either reverts (Securitize) or, in Hyperbridge's case, silently overpays and permanently loses the difference because `EvmHost` never routes the Uniswap refund back to the original caller.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and, when `msg.value > 0`, call: [1](#0-0) [2](#0-1) 

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` only consumes the exact ETH needed to buy `post.fee` (or `amount`) units of `feeToken`; any leftover ETH from `msg.value` is refunded by the Uniswap router via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Critically, from the router's perspective `msg.sender` is `EvmHost` itself (it is the contract that invoked the router), not the original transaction sender or the app contract that called `dispatch`/`fundRequest`. The refunded ETH therefore lands in `EvmHost`'s own balance.

Neither `dispatch()` nor `fundRequest()` contains any subsequent logic that forwards this leftover native balance back to `_msgSender()`/`post.payer` — there is no `(bool ok,) = payable(_msgSender()).call{value: address(this).balance}("")` or equivalent refund step after the swap call. Because callers (exactly as in the external report) cannot know the precise on-chain conversion rate at submission time — Uniswap's price can move between the quote and the transaction — any user who sends `msg.value` even slightly above the exact amount required by `getAmountsIn` at execution time has that excess permanently absorbed into `EvmHost`'s balance rather than refunded.

### Impact Explanation
This is a genuine loss-of-funds bug reachable by any unprivileged user through the normal, documented dispatch flow (native-token payment path, which the docs themselves recommend for "user-facing apps"). Every overpayment — which is the norm, not the exception, since users must send `msg.value >= exact quote` to avoid reverting on price movement, and `quote()` itself is documented as "Approximate (subject to slippage)" — is siphoned into the Host contract with no recovery path for the depositor. Repeated across many dispatches this represents systemic value leakage from ordinary users into the protocol contract, matching the "stealing or loss of funds" and "bridged assets / relayer fee balances must move exactly once to the rightful beneficiary" impact categories.

### Likelihood Explanation
High. Any caller using the native-token payment path (the flow explicitly documented in `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx` for "User Convenience") who sends any amount of ETH above the exact swap requirement — which is unavoidable in practice because on-chain quotes drift between estimation and execution — triggers the loss. No malicious relayer, prover, or admin is required; it is a self-inflicted but structurally guaranteed side effect of normal usage.

### Recommendation
After the `swapETHForExactTokens` call in both `dispatch()` and `fundRequest()`, refund any residual native balance received back to `_msgSender()` (or `post.payer`), e.g.:
```solidity
uint256 dust = address(this).balance - balanceBeforeSwap;
if (dust > 0) {
    (bool sent, ) = payable(_msgSender()).call{value: dust}("");
    require(sent, "refund failed");
}
```
This mirrors the fix Securitize applied for the analogous exact-value-quote issue: accept an upper-bound value and refund the excess.

### Proof of Concept
1. User calls `MyApp.sendMessage{value: X}(...)` which forwards to `EvmHost.dispatch{value: X}(post)` where `post.fee = F` (fee-token units).
2. At call time, due to price movement since the client fetched `quote()`, the actual ETH needed to buy `F` feeToken units via `swapETHForExactTokens` is `Y < X`.
3. `swapETHForExactTokens{value: X}(F, path, address(this), deadline)` swaps `Y` ETH for `F` feeToken, and the Uniswap router refunds `X - Y` ETH to `msg.sender` of the router call — which is `EvmHost`.
4. `EvmHost`'s balance increases by `X - Y`; no code path returns any of it to the original user.
5. The user has permanently lost `X - Y` native tokens with no view function, event, or recovery mechanism to reclaim it.
