## Finding

### Title
Unauthenticated `initialize()` on SDK token bridge apps allows any address to seize contract ownership and bridge custody - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol] / [File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.initialize()` and `WrappedHyperFungibleTokenUpgradeable.initialize()` accept an attacker-controlled `initialOwner` parameter and are gated only by OpenZeppelin's one-time-call `initializer` modifier — with no check that the caller is a designated deployer/admin. Unlike every other initializer in this codebase, these two have no deployer binding at all, so whichever address calls `initialize()` first on the proxy permanently becomes the contract's `Ownable` owner and controls `_host`/`_dispatcher`/`_supportedChains`, i.e. the entire cross-chain trust configuration for that token's bridge custody.

### Finding Description
Compare the initializer patterns across the repo:

- `EvmHost.initialize()` requires `_msgSender() == _hostParams.admin`, where `admin` is fixed in the constructor [1](#0-0) .
- `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `setParams()` requires `msg.sender == _admin`, with `_admin` fixed in the constructor [2](#0-1) .
- The EVM `IntentGatewayV2` and `SimplexPaymaster` initializers have no `msg.sender` gate, but production deployment always bundles the implementation deployment and `initialize()` call into a single atomic transaction via `ERC1967Proxy{salt}(implementation, initData)` [3](#0-2) [4](#0-3) , and tests explicitly confirm the raw implementation is separately locked with `_disableInitializers()` [5](#0-4) .

By contrast, `HyperFungibleTokenUpgradeable.initialize(string name, string symbol, address initialOwner)` is `public virtual initializer` with **no** msg.sender restriction — `initialOwner` is simply whatever the caller supplies: [6](#0-5) 

The same pattern exists in `WrappedHyperFungibleTokenUpgradeable.initialize(address initialOwner)`: [7](#0-6) 

No deployment script in the repo bundles proxy creation with `initData` for these two SDK apps (unlike `DeployIntentGateway.s.sol` / `DeploySimplexPaymaster.s.sol`), and the repo's own TRON migration demonstrates that this codebase's actual deployment tooling routinely performs deploy and configuration as two separate, non-atomic transactions (deploy `IntentGatewayV2`, wait for confirmation, then call `setParams` in a later transaction) [8](#0-7) . That pattern is safe there only because `setParams` checks `msg.sender == _admin`. The SDK token apps have the identical two-transaction deployment exposure but **without** any equivalent admin check on `initialize()`.

Once an attacker becomes `owner`, `configure()` lets them set `_host` (only if still zero) and `_dispatcher` unconditionally, and `addChain()`/`removeChain()` let them freely (re)bind `_supportedChains` to any module ID they choose: [9](#0-8) 

Because `host()` simply returns the owner-set `_host`, and `onAccept`/`onGetResponse` are gated by `onlyHost` (i.e., `msg.sender == host()`), an attacker who controls both `owner` and `_host` can trivially satisfy `onlyHost` from any address they choose and inject arbitrary "incoming" cross-chain messages into the token's mint/unlock/withdraw logic.

### Impact Explanation
This falls under "unauthorized transaction or execution" and "logic attacks" in the bounty's impact gate. Any unprivileged address that observes an un-initialized proxy of these SDK bridge-token contracts (a state that exists any time deployment and initialization are not the exact same transaction — which the repo's own TRON deployment tooling shows is a normal deployment pattern for this codebase) can permanently take over the contract as owner and host, allowing:
- Redirection of cross-chain peer bindings (`_supportedChains`) to attacker-controlled "peers".
- Forging `onAccept` calls (since attacker also controls `_host`) to mint arbitrary `HyperFungibleTokenUpgradeable` supply to themselves, or to release/unlock the underlying escrowed ERC20 balance held by `WrappedHyperFungibleTokenUpgradeable` to themselves once users start trusting and using the officially-documented contract address.

This is a full loss-of-custody / unauthorized-execution primitive on any bridge token deployed with this SDK contract without atomic proxy initialization.

### Likelihood Explanation
The vulnerability does not depend on racing a specific victim's pending transaction (no mempool front-running is required) — it depends only on the ordinary condition that proxy deployment and `initialize()` occur as two separate transactions, which this same codebase's own TRON migration script demonstrates is a standard operational pattern (deploy then configure in a later confirmed block) [8](#0-7) . Any address can call `initialize()` at any time before the legitimate deployer does, with no admin/deployer restriction whatsoever, unlike every comparable initializer in the codebase.

### Recommendation
Add a deployer/admin binding to `initialize()` in both `HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` (e.g., an immutable `_deployer` set in the constructor and checked with `if (msg.sender != _deployer) revert Unauthorized();`, mirroring `EvmHost.initialize`), or mandate atomic proxy+initData deployment for these contracts as is already done for `IntentGatewayV2` and `SimplexPaymaster`, and provide/require an official deploy script that enforces this atomicity for every SDK consumer.

### Proof of Concept
1. A project deploys the `HyperFungibleTokenUpgradeable` implementation and an `ERC1967Proxy` pointing to it with empty `initData` (a two-step deployment, as is standard practice elsewhere in this repo's own tooling, e.g. `evm/tron/migrations/2_deploy_ismp.js`).
2. Before the legitimate deployer's follow-up transaction calling `initialize(name, symbol, deployerAddress)` is mined, an attacker submits `initialize(name, symbol, attackerAddress)` to the proxy.
3. `initializer` modifier allows this first call to succeed; `attackerAddress` becomes the `Ownable` owner permanently. The deployer's subsequent `initialize()` call reverts (`InvalidInitialization`).
4. Attacker calls `configure({host: attackerControlledHost, dispatcher: attackerDispatcher})` — succeeds since `_host == address(0)`.
5. Users, trusting the officially published proxy address, call `send()` to bridge tokens (for `WrappedHyperFungibleTokenUpgradeable`, locking real underlying ERC20 into the contract).
6. Attacker, controlling `_host`, calls `onAccept()` directly (satisfies `onlyHost` since `msg.sender == host()`), crafting an incoming message that mints tokens to themselves or unlocks the escrowed underlying balance to themselves.
