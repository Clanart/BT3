## Valid Finding

### Title
Log Injection via Unescaped Newlines in Error Messages Allows Forging Fake Log Entries - (File: `app/src/lib/logging/format-log-message.ts`)

### Summary
`formatLogMessage` concatenates an `Error`'s `message`/`stack` verbatim into the single string that becomes one winston log record, with no newline/control-character sanitization. Because Git stderr (and other attacker-influenced text) can end up as an `Error.message`/`.stack` that reaches `log.error(...)`, and because the on-disk file format is a plain `timestamp - level: message` string per line, an attacker who controls a cloned/fetched repository's git output can embed `\n<fake-timestamp> - <level>: <fake message>` inside the error text to forge what looks like an independent, later, timestamped log line in the real Desktop log file.

### Finding Description
`formatLogMessage` simply calls `formatError`, which returns `error.stack.trim()` (or falls back to `${error.name}: ${error.message}`) with no escaping: [1](#0-0) [2](#0-1) 

This formatted string is written to disk as-is. The main-process file transport formats each winston record as `${timestamp()} - ${level}: ${message}` and appends `EOL`, i.e., it does not re-encode embedded newlines in `message`: [3](#0-2) [4](#0-3) 

Both the main-process and renderer-process logger wrappers pass errors through `formatLogMessage` unchanged before writing: [5](#0-4) [6](#0-5) 

An attacker-controlled `GitError` message is a realistic source of untrusted content: `GitError` is constructed directly from raw `stderr`/`stdout` of a git invocation (`isRawMessage = true` path) when git's exit code isn't recognized: [7](#0-6) 

Such errors are subsequently passed as the `error` argument to `log.error(message, error)` in multiple call sites — for example, when handling conflict-detection failures: [8](#0-7) 

or via `performFailableOperation`/other catch-and-log patterns elsewhere in the app (`git-store.ts`, `app-store.ts`, `trampoline-server.ts`, etc.) that call `log.error(<msg>, e)` on the raw caught error. Because a malicious repository can influence git's stderr output (e.g., via crafted refs, a malicious `pre-commit`/`post-checkout` hook that writes to stderr, a crafted LFS filter/smudge command that errors out, or crafted file/ref names that appear in git's error text), the resulting `Error.message`/`.stack` is attacker-controlled and flows unescaped into the log line.

### Impact Explanation
This is a log-forgery/log-injection issue: an attacker who controls repo content, a hook, or an LFS filter can inject fabricated, plausible-looking timestamped log lines into GitHub Desktop's on-disk log file (e.g., fake "error" entries attributed to times/events that never happened). This could be used to mislead a user or support engineer reviewing logs (log forensics tampering), or to hide/obscure the attacker's own malicious activity among fabricated noise. It does not by itself grant code execution, file access outside the repo, or credential exfiltration — the impact is limited to log integrity/forgery within the application's own log file.

### Likelihood Explanation
Reasonably likely to be reachable: cloning/fetching a malicious repository that triggers a git error (e.g., via a crafted hook, LFS filter, or malformed ref/path that git reports in stderr) is a normal, low-friction attacker capability under this bounty's threat model (attacker controls repository content). No special user interaction beyond normal repository operations (clone/fetch/checkout, which can trigger hook execution) is required.

### Recommendation
Sanitize/escape control characters (particularly `\n`, `\r`) in `formatLogMessage`/`formatError` (or in the file transport's `printf` formatter) before writing to the single-line log record — e.g., replace embedded newlines with a visible escape sequence (`\\n`) or indent continuation lines with a marker that cannot be confused with the `timestamp - level:` prefix, so that attacker-supplied text can never be rendered as an independent, well-formed log entry.

### Proof of Concept
1. In a test harness, call the real logging pipeline with an attacker-crafted error message such as:
```ts
const evil = new Error("boom\n2099-01-01T00:00:00.000Z - error: [main] fake forged entry")
log.error('git status failed', evil)
```
2. Inspect the resulting on-disk log file (as written by `DesktopFileTransport`) — it will contain two lines that look like two independent winston records:
```
2026-08-23T12:00:00.000Z - error: [main] git status failed
Error: boom
2099-01-01T00:00:00.000Z - error: [main] fake forged entry
    at ...
```
3. The second embedded line is indistinguishable in the raw log file from a genuine entry logged by Desktop at that (fake) date, because `formatLogMessage`/`formatError` placed the attacker-controlled newline-containing string directly into the message field with no escaping, and the file transport wrote it verbatim.

Realistically, step 1's `evil` error would originate from `GitError`'s raw-stderr message path [7](#0-6)  when operating on a malicious repository/hook/LFS filter, and reach `log.error` via a catch site such as [8](#0-7) .

export function formatError(error: Error, title?: string) {
  error = withSourceMappedStack(error)

  if (error.stack) {
    return title ? `${title}\n${error.stack}` : error.stack.trim()
  } else {
    return title
      ? `${title}\n${error.name}: ${error.message}`
      : `${error.name}: ${error.message}`
  }
}

function initializeWinston(path: string): winston.LogMethod {
  const timestamp = () => new Date().toISOString()

  const fileLogger = new DesktopFileTransport({
    logDirectory: path,
    level: 'info',
    format: winston.format.printf(
      ({ level, message }) => `${timestamp()} - ${level}: ${message}`
    ),
  })

  // The file transport shouldn't emit anything but just in case it does we want
  // a listener or else it'll bubble to an unhandled exception.
  fileLogger.on('error', noop)

  const consoleLogger = new DesktopConsoleTransport({
    level: process.env.NODE_ENV === 'development' ? 'debug' : 'error',
  })

  winston.configure({
    transports: [consoleLogger, fileLogger],
    format: winston.format.simple(),
  })

  return winston.log
}
