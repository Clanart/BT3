### Title
Attacker-sent dust outputs to a scanned Taproot key cause `SignableTransaction::new` to fail atomically, DOSing spends of legitimate funds - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The OpenQ bug: an attacker adds `1 wei` of a reverting token to a bounty, so the claim loop that iterates `tokenAddresses` reverts and the claimer loses their reward. The Serai analog lives in the Bitcoin wallet: `Scanner::scan_transaction` returns *every* output paying to a registered script, including uneconomical dust, and `SignableTransaction::new` then treats the whole input set atomically — a single unprofitable attacker-injected input raises `needed_fee` enough to make the entire transaction construction fail, even though simply excluding the attacker's output would succeed. There is no per-input skip/try-catch equivalent.

### Finding Description
`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches on `output.script_pubkey` and pushes a `ReceivedOutput` for **any** value, with no dust/economic filter. `register_offset`/`Scanner::new` give the attacker a public, payable P2TR address (`p2tr_script_buf`, `mod.rs:80-86`), so anyone on-chain can create matching outputs.

`SignableTransaction::new` (`send.rs:150-256`) then:
- sums all inputs into `input_sat` (`send.rs:175`),
- computes `needed_fee` from the total input count (`send.rs:204-211`, ~57 vbytes per input per `processor/src/networks/bitcoin.rs:619-620`),
- and hard-fails with `NotEnoughFunds` if `input_sat < payment_sat + needed_fee` (`send.rs:215-221`), and with `TooLargeTransaction` if aggregate weight exceeds `MAX_STANDARD_TX_WEIGHT` (`send.rs:241-243`).

The error is evaluated on the aggregate set — exactly like `_claimAtomicBounty` reverting on the aggregate `tokenAddresses` — with no mechanism to drop an unprofitable input. (The `N::DUST` filter exists only in the out-of-scope processor scanner, `processor/src/multisigs/scanner.rs:564`; the in-scope library code performs no such filtering.)

### Impact Explanation
A wallet that consumes all scanned outputs as inputs (the intended usage) can be forced into persistent construction failure:
- Each dust input adds ~57 vbytes of fee but contributes ~1 sat of value; once the change margin is thin, `input_sat < payment_sat + needed_fee` returns `NotEnoughFunds`, blocking the spend of all legitimate inputs.
- Sufficient dust outputs push weight past `MAX_STANDARD_TX_WEIGHT`, yielding `TooLargeTransaction` regardless of amounts.

Legitimate received funds cannot be spent via the library until inputs are manually curated — an externally reachable DOS of a "claim" (spend) via attacker-added set entries, matching the reported class.

### Likelihood Explanation
Sending dust to a known P2TR address is permissionless and cheap; the multisig/offset addresses are public. Triggering `NotEnoughFunds` requires the wallet to auto-include scanned inputs and have a fee margin smaller than the injected cost — a plausible configuration; the weight-limit variant requires more capital.

### Recommendation
Filter uneconomical outputs in `Scanner::scan_transaction` (skip `output.value < DUST`), and/or make `SignableTransaction::new` skip inputs whose marginal fee cost exceeds their value instead of erroring on the aggregate.

### Proof of Concept
```rust
// Attacker sends 1 sat to the victim's scanned P2TR address (permissionless).
let dust = ReceivedOutput from tx paying 1 sat to p2tr_script_buf(key);

// Victim wallet consumes all scanned outputs:
let inputs = vec![legit_output, dust]; // legit funds barely cover payments + fee
let res = SignableTransaction::new(inputs, &payments, change, None, fee_rate);
// res == Err(TransactionError::NotEnoughFunds { .. })
// because +57 vbytes of needed_fee exceeds the +1 sat contributed,
// while excluding the dust input would have succeeded — atomic DOS.
```
