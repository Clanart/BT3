### Title
Session assigned to attacker-supplied `params[:shop]` without token proof, enabling cross-shop session confusion/enumeration - (File: `app/controllers/concerns/shopify_app/ensure_installed.rb`)

### Summary
In non-token-exchange mode, `EnsureInstalled#current_shopify_domain` derives and memoizes the "installed" shop purely from the unauthenticated `params[:shop]` query string, sanitized only for domain format, and `check_shop_known` uses that value directly to fetch `installed_shop_session` from `SessionRepository`. No HMAC, ID token, or cookie-bound proof ties the requester to that shop.

### Finding Description
`current_shopify_domain` reads `params[:shop]`, passes it through `ShopifyApp::Utils.sanitize_shop_domain` (which only validates/normalizes the domain suffix against `TRUSTED_SHOPIFY_DOMAINS`, it does not verify caller identity) and memoizes it: `app/controllers/concerns/shopify_app/ensure_installed.rb:29-38`. `check_shop_domain` (`before_action`) only checks that a sanitized domain exists, not that it belongs to the requester: `app/controllers/concerns/shopify_app/ensure_installed.rb:46-48`. In the non-token-exchange branch, `check_shop_known` then calls `installed_shop_session`, which calls `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` using that attacker-controlled string: `app/controllers/concerns/shopify_app/ensure_installed.rb:40-42,50-59`. If a session exists for that shop, `@shop` is set to the victim's session and no redirect occurs, so the controller action proceeds with a session object (and its access token) belonging to a shop the attacker doesn't operate. If no session exists, the request is redirected to `shop_login`/`redirect_for_embedded`, and if a session exists but the stored token is no longer valid, `validate_non_embedded_session` (`app/controllers/concerns/shopify_app/ensure_installed.rb:73-82`) redirects with a 401-triggered `shop_login`, otherwise re-raises. These three distinguishable outcomes (no session → login redirect; valid session → proceed to action; stale/invalid token → different redirect or raised error) leak, purely from `params[:shop]`, whether a session record exists for an arbitrary shop domain, without any token proof of identity. `EnsureInstalled` explicitly cannot be combined with `ShopifyApp::LoginProtection` (`app/controllers/concerns/shopify_app/ensure_installed.rb:8-16`), so none of `LoginProtection`'s HMAC/signature checks are available to close this gap in this mode.

### Impact Explanation
Scoped impact is cross-shop probing/session enumeration: an anonymous attacker (or a merchant of an unrelated shop) can iterate `shop=` values and observe response differences (redirect target, presence of a successful non-redirected response, or raised error vs. graceful redirect) to determine whether an app session exists for a shop they don't control. This maps to Shopify's "Information Disclosure — enumeration of app-installed shops" impact class. It falls short of direct token/data theft only because `check_shop_known` alone does not return session contents to the response; but it does allow the controller action to execute using the victim shop's session (`@shop`), which is the boundary condition the invariant is testing.

### Likelihood Explanation
Preconditions match realistic conditions for legacy (non–token-exchange) apps still supported by the gem: no id_token, no cookie, only a guessable/known `shop` query parameter, which is not secret (shop domains are often discoverable). The behavior is deterministic and repeatable per shop domain, requiring no timing side channel — only observing the redirect target/response code differs by session existence.

### Recommendation
Do not use `params[:shop]` alone as the trust boundary for loading `installed_shop_session` in `EnsureInstalled`. Require a verified session (ID token, session cookie set by `CallbackController`/`SessionsController`, or `ShopifyAPI::Utils::SessionUtils.current_session_id`) to determine `current_shopify_domain`, or make the redirect/response indistinguishable for "no session" vs. "session belongs to another shop" (e.g., always redirect to `shop_login` with the same shape regardless of session lookup result), and document that this legacy mode must be paired with an HMAC/session-token check equivalent to `LoginProtection` before enabling `EnsureInstalled`.

### Proof of Concept
```ruby
# test/controllers/concerns/ensure_installed_test.rb (illustrative addition)
test "check_shop_known behavior differs based on unauthenticated shop param" do
  known_shop = "known-shop.myshopify.com"
  unknown_shop = "unknown-shop.myshopify.com"
  ShopifyApp::SessionRepository.store_session(
    ShopifyAPI::Auth::Session.new(shop: known_shop, access_token: "tok", is_online: false)
  )

  get :index, params: { shop: known_shop }
  known_response = response

  get :index, params: { shop: unknown_shop }
  unknown_response = response

  # No id_token, no cookie, no HMAC was supplied for either request,
  # yet the responses differ, leaking session existence for `known_shop`
  # that the attacker does not operate.
  refute_equal known_response.location, unknown_response.location
end

      def sanitize_shop_domain(shop_domain)
        uri = uri_from_shop_domain(shop_domain)
        return if uri.nil? || uri.host.nil?

        trusted_domains.each do |trusted_domain|
          no_shop_name_in_subdomain = uri.host == trusted_domain
          from_trusted_domain = trusted_domain == uri.domain

          return myshopify_domain_from_unified_admin(uri) if unified_admin?(uri) && from_trusted_domain
          return nil if no_shop_name_in_subdomain || uri.host&.empty?
          return uri.host if from_trusted_domain
        end
        nil
      end
