Based on the code evidence gathered, the closest structural analog to the reported bug class — a value computed once from mutable external state, cached, and later relied upon as ground truth for a security-relevant action without revalidation — is the partial/line-selection commit path in GitHub Desktop's staging logic.

### Title
Stale diff-selection bitmap applied to a freshly re-fetched diff causes silent corruption of partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
Desktop's partial-staging feature lets a user select individual added/deleted lines in a diff and commit only those lines. The selection is stored as a bitmap of *absolute line indices* computed against the specific `ITextDiff` (hunk layout) that was on screen when the user made the selection. When the user actually commits, `applyPatchToIndex` re-fetches a brand-new diff from disk/index and reuses the old, unrevalidated selection bitmap against the new hunk layout, exactly mirroring the reported pattern of computing a quorum value once and never re-checking it against the state that exists at time-of-use.

### Finding Description
`stageFiles` calls `applyPatchToIndex` for every file with a partial selection: [1](#0-0) 

`applyPatchToIndex` does **not** use the diff the user reviewed; it fetches a completely fresh diff at staging time and formats a patch from it using `file.selection`, which was computed earlier (potentially minutes earlier, and definitely at a point in time decoupled from this fresh diff): [2](#0-1) 

`formatPatch` maps the stored selection onto the newly-fetched diff purely by `absoluteIndex` (position within the hunk array), with no check that the hunk layout it's mapping into is the same one the selection was created against: [3](#0-2) 

Desktop does attempt to keep the UI's `selectableLines` in sync when the working-directory diff is refreshed (`updateChangesWorkingDirectoryDiff`), but this reconciliation only happens on the specific refresh cycle tied to the Changes view, and even then it merely intersects previously selected indices with currently selectable ones — it does not invalidate the selection or force a re-render/re-selection when a hunk's line numbering has shifted: [4](#0-3) 

Critically, `_commitIncludedChanges` — the code path invoked when the user clicks "Commit" — does **not** refresh the diff or revalidate selection state before staging; it takes whatever `file.selection` is currently sitting in `repositoryStateCache` and passes it straight into `createCommit` → `stageFiles` → `applyPatchToIndex`: [5](#0-4) 

So the sequence is:
1. User opens Changes view; Desktop loads diff D1 for file F and the user selects specific lines (bitmap indexed by D1's hunk positions).
2. Before the user clicks Commit, the file on disk is modified by something other than Desktop's own commit action (e.g., a build/format tool, a linter with `--fix`, a watch-mode bundler, or any tooling bundled with/triggered by a freshly cloned/fetched repository) shifting hunk boundaries/line counts.
3. User clicks Commit. `applyPatchToIndex` fetches diff D2 (post-modification) but applies the D1-indexed selection bitmap to D2's hunks.
4. `git apply --cached` stages whatever `formatPatch` produced from this mismatched mapping — which can silently include lines the user never reviewed/selected, or exclude lines the user explicitly wanted committed.

This is the same broken invariant as the reported issue: a security/integrity-relevant quantity (`quorumVotes` there, the committed-line selection here) is derived once from external mutable state and used later without being recomputed against the state that actually exists at the moment of the privileged action (dropping the art piece / staging the patch).

### Impact Explanation
This falls squarely under "silent corruption of what the user commits or pushes" from the accepted impact list. A user could believe they excluded a sensitive line (credential, debug flag, malicious snippet) from a partial commit, yet it gets silently staged and committed anyway — or conversely, reviewed/approved content could be silently dropped from the commit without any error or warning. Since GitHub Desktop's UI is the user's sole basis for what they believe they are committing, this directly undermines trust in the tool's core "review before commit" guarantee.

### Likelihood Explanation
Confidence is moderate, not high. Exploitability strictly requires the working-directory file content to change between the moment the user's selection bitmap was computed and the moment `applyPatchToIndex` re-diffs the file — this is a narrow race window rather than something a remote attacker can trigger directly through a crafted repository/PR/link alone. I was not able to verify from the indexed code whether Desktop forces a synchronous, blocking diff refresh immediately before invoking `_commitIncludedChanges` (which would close this window) or whether any additional guard exists elsewhere in the commit flow that I didn't locate. This uncertainty should be resolved by a deeper trace of the full Commit-button click handler before treating this as confirmed-exploitable.

### Recommendation
Before calling `applyPatchToIndex`, either (a) re-diff the file and reject/re-map the selection if the hunk structure differs from what the selection was computed against (failing the commit with an explicit "diff changed, please re-review" error), or (b) generate the patch from the exact diff object that was last shown to and confirmed by the user, and fail loudly if that diff is no longer consistent with the working directory, rather than silently reusing a stale index-based selection against fresh hunk data.

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end against the running app in this pass):
1. Modify `modified-file.md` to introduce several new lines, open Desktop's Changes view, and select only specific added lines via the diff view (e.g., select line at absolute index 4 only).
2. Externally (simulating a build tool/linter triggered by repo tooling) modify the same file again, shifting line numbers — e.g., insert 2 new lines above the previously selected region — without going through Desktop.
3. Click Commit without reopening/refreshing the diff view.
4. Inspect the resulting commit's diff (`git show`): the staged content corresponds to `absoluteIndex 4` in the *new* hunk layout, not the line the user actually selected in the UI, demonstrating the mismatch produced by `formatPatch` in `app/src/lib/patch-formatter.ts` line 157 combined with the fresh re-diff in `app/src/lib/git/apply.ts` line 60.
