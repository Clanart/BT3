### Title
Integer overflow via unsafe `uint64`→`int64` cast in `consolidatedNode.Split` corrupts CN/CL reward split ratio - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split` in [1](#0-0)  converts `uint64` staking amounts to `*big.Int` via an unsafe `int64(...)` cast instead of using `new(big.Int).SetUint64(...)`. This is the direct Go analogue of the reported Solidity bug class (`AbstractRewards#_correctPoints` casting a `uint256` into `int256` via `toInt256()`/unchecked cast, which flips sign once the value exceeds `2^255`): here, a `uint64` value greater than `math.MaxInt64` (2^63-1) is reinterpreted as negative when passed through `int64(...)`, corrupting all downstream arithmetic.

### Finding Description
`StakingInfo.StakingAmounts` and `CLStakingInfo.CLStakingAmount` are `uint64` fields, denominated in whole KAIA units (rounded down from kei/wei), as documented at [2](#0-1)  and populated via [3](#0-2) , where staking amounts are derived directly from the permissionless CN staking / CL registry multicall results (`new(big.Int).Div(amounts[i], big.NewInt(params.KAIA)).Uint64()`).

`consolidatedNode.Split`, used to proportionally divide reward payouts between a CN and its associated CL pool, performs:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)
	cnAmount := big.NewInt(0).Sub(amount, clAmount)
	return cnAmount, clAmount
}
``` [1](#0-0) 

`big.NewInt(int64(x))` performs an implicit `uint64`→`int64` conversion. If `c.StakingAmount` or `c.CLStakingInfo.CLStakingAmount` exceeds `math.MaxInt64` (≈9.22×10^18 KAIA), the cast silently wraps to a negative `int64`, producing a negative `cnAmountBig`/`clAmountBig`. This is used in `assignStakingRewards`/`assignStakingRewardsFlex` in [4](#0-3)  and in the proposer split path [5](#0-4) , both of which feed directly into `RewardSpec.Rewards`, the map of addresses to be credited during `FinalizeState()`/block finalization.

### Impact Explanation
If `totalAmount` becomes negative or the CN/CL ratio inverts sign due to the overflow, `clAmount`/`cnAmount` computed by `Split` can become negative or grossly disproportionate to the actual staked ratio. Since these values are directly used to credit balances during deferred reward distribution (`spec.IncRecipient`), this could redirect/misallocate portions of the block reward between a CN's reward address and its CL pool address — a concrete reward-redirection / value-movement bug reachable purely through state (staking amounts recorded on-chain) rather than a crafted transaction payload. All full nodes deterministically execute the same buggy arithmetic, so this would not by itself cause a chain split among honest nodes, but it does produce an incorrect (unintended) reward allocation for every affected block.

### Likelihood Explanation
Exploitability requires a CN or CL staking amount (in whole KAIA) to exceed `math.MaxInt64` (~9.22 quintillion KAIA). Given KAIA's actual total token supply is many orders of magnitude smaller than this threshold, this condition is not realistically reachable under current economic parameters, making practical exploitation extremely unlikely today. However, the code pattern itself is unsafe and would silently misbehave (integer overflow producing a wrong, possibly negative, split) should staking amounts ever grow astronomically or if a unit-conversion bug elsewhere fed an unexpectedly large value into `StakingAmount`. This mirrors exactly the reported bug class: an unchecked/unsafe numeric cast in a rewards-computation path that only manifests at an extreme numeric boundary.

### Recommendation
Replace the unsafe `int64(...)` casts in `consolidatedNode.Split` with safe unsigned-to-`big.Int` conversions:
```go
cnAmountBig := new(big.Int).SetUint64(c.StakingAmount)
clAmountBig := new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
```
This eliminates any possibility of sign-flip on overflow, consistent with how `SetUint64` is already used safely elsewhere in the reward/staking code (e.g. [6](#0-5) , [7](#0-6) ).

### Proof of Concept
Not independently reproducible against live Kaia mainnet parameters because it requires a CN or CL staking amount exceeding `math.MaxInt64` KAIA (~9.22×10^18 KAIA), which exceeds the entire token supply. A unit test demonstrating the underlying overflow behavior in isolation:
```go
c := consolidatedNode{
    StakingAmount: math.MaxInt64 + 1, // uint64 value just above int64 range
    CLStakingInfo: &CLStakingInfo{CLStakingAmount: 1},
}
cn, cl := c.Split(big.NewInt(1000))
// int64(math.MaxInt64+1) wraps to math.MinInt64 (negative),
// corrupting totalAmount and the resulting cn/cl split.
```
This confirms the root-cause casting defect in [1](#0-0) , though real-world triggering is bounded by economic feasibility given the current KAIA supply.
