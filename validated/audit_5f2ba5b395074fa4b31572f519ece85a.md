However, the underlying authentication pattern it exposes generalizes to a real, exploitable weakness shared by every EVM "governance-receiving" app on Hyperbridge.

### Title
Governance `onAccept` handlers authenticate only `request.source == hyperbridge`, not the dispatching module, letting any Hyperbridge-side pallet forge privileged cross-chain admin calls - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster.onAccept`, `BandwidthManager.onAccept`, and `HostManager.onAccept` each authorize inbound governance messages solely by checking `request.source == IDispatcher(host()).hyperbridge()` [1](#0-0) [2](#0-1) [3](#0-2) . `request.source` is the **chain identifier** of Hyperbridge (e.g. `Kusama(4009)`), not the identity of the specific pallet/module that dispatched the request. None of these `onAccept` handlers additionally verify `request.from` against an allowlisted governance module id.

### Finding Description
On Hyperbridge, `IsmpDispatcher::dispatch_request` can be invoked by **any pallet**, and any pallet that lets a signed extrinsic construct an outbound `DispatchPost` with an attacker-influenced `to` and `body` will have `request.source` automatically set to Hyperbridge's own `host_state_machine()` — exactly the value that `onAccept` checks for. Both `EvmHost.updateHostParams`/`withdraw` are properly locked to the specific `hostManager` contract address via `restrict(_hostParams.hostManager)` [4](#0-3) [5](#0-4) , but the *apps that receive governance themselves* (`SimplexPaymaster`, `BandwidthManager`) only check the chain-level `source`, with no equivalent check that `request.from` equals a specific trusted pallet id (e.g. the treasury/governance pallet). This is the same broken-authorization-primitive class as the seed report: the code assumes a caller-restriction is enforced ("only Hyperbridge governance can reach this"), but the actual guard (`request.source == hyperbridge`) is too coarse and doesn't bind to the *module* that is supposed to be the sole authorized sender, unlike `pallet-bandwidth`'s inbound purchase path which correctly checks `request.from == BandwidthManager::<T>::get(request.source)` [6](#0-5) .

The demonstrated `pallet_ismp_demo::dispatch_to_evm` extrinsic proves the primitive is real and reachable by any signed account today [7](#0-6) : it lets an unprivileged caller pick an arbitrary EVM `module` (`to` address) and arbitrary `destination` chain, with `request.source` on the receiving EVM host coming out to Hyperbridge's own state machine id. In this specific pallet the `body` is hardcoded to `b"Hello from polkadot"`, so it cannot itself carry a forged `RequestKind`/payload — but the codebase does not appear to prevent a different pallet, module, or future extrinsic (any code path that calls `IsmpDispatcher::dispatch_request` with a caller-controlled `to`/`body`) from targeting `SimplexPaymaster` or `BandwidthManager` with a forged `OnAcceptActions`/`RequestKind` byte plus ABI-encoded payload (e.g. `Withdraw`/`WithdrawAssets`/`UpgradeContract`).

### Impact Explanation
If any Hyperbridge-side dispatch path allows an unprivileged account to control `to` and `body` of an outbound POST request, the receiving `onAccept` on `SimplexPaymaster` or `BandwidthManager` would treat it as legitimate governance because it only checks `request.source == hyperbridge`. This could let an attacker:
- Drain `SimplexPaymaster`'s treasury via `RequestKind.WithdrawAssets` → `_withdrawAssets` (ERC-20 sweep or `entryPoint().withdrawTo`) [8](#0-7) .
- Upgrade the paymaster's implementation via `RequestKind.UpgradeContract` → `ERC1967Utils.upgradeToAndCall` [9](#0-8) , i.e. full contract takeover.
- Drain `BandwidthManager`'s accumulated fee-token balances via `OnAcceptActions.Withdraw` [10](#0-9) .

This maps directly to the required impact classes: stealing/loss of funds and unauthorized/cross-chain admin execution reachable through unauthenticated (module-unbound) message flow.

### Likelihood Explanation
Likelihood is **not fully confirmed** from the code reviewed: the one concrete unprivileged dispatch path found (`pallet_ismp_demo::dispatch_to_evm`) hardcodes its body and therefore cannot itself forge the required payload, so it does not by itself complete the exploit. What is confirmed is the structural authorization gap in `onAccept` (`source`-only check, no `from`/module-id binding) shared by `SimplexPaymaster` and `BandwidthManager`. Exploitability depends on whether any other pallet, dispatcher, or future/less-visible extrinsic in the runtime lets an unprivileged signed account set an arbitrary `to` and `body` on an outbound `DispatchPost`; this could not be exhaustively ruled out or confirmed within the indexed portion of the codebase.

### Recommendation
Harden every governance-receiving `onAccept` (`SimplexPaymaster`, `BandwidthManager`, and any future `HyperApp`-based governance receiver) to check `request.from` against a specific, pinned governance/treasury module identifier on Hyperbridge — not merely `request.source == hyperbridge` — mirroring the pattern already used correctly in `pallet-bandwidth`'s inbound-purchase check (`request.from == BandwidthManager::<T>::get(request.source)`). Additionally, audit all pallets implementing `IsmpDispatcher::dispatch_request` on Hyperbridge to confirm none permit an unprivileged signed account to fully control `to` and `body` of an outbound POST destined for a privileged EVM application.

### Proof of Concept
Not producible with full confidence from the indexed code: the only unprivileged dispatch entrypoint located (`modules/pallets/demo/src/lib.rs::dispatch_to_evm`) hardcodes the body, so it cannot alone forge a `WithdrawAssets`/`UpgradeContract` payload. A concrete PoC requires either (a) locating a Hyperbridge pallet whose dispatch path lets a signed account fully control the POST `body`, or (b) confirming no such path exists, which would downgrade this from an exploitable vulnerability to a defense-in-depth gap. This could not be conclusively resolved with the available read-only search tools, and a Devin session with full repo access (including all pallets not covered by the codebase index) would be needed to enumerate every `IsmpDispatcher::dispatch_request` call site and confirm or refute exploitability.

		pub fn dispatch_to_evm(origin: OriginFor<T>, params: EvmParams) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let post = DispatchPost {
				dest: StateMachine::Evm(params.destination),
				from: PALLET_ID.to_bytes(),
				to: params.module.0.to_vec(),
				timeout: params.timeout,
				body: b"Hello from polkadot".to_vec(),
			};
			let dispatcher = T::IsmpHost::default();
			for _ in 0..params.count {
				// dispatch the request
				dispatcher
					.dispatch_request(
						DispatchRequest::Post(post.clone()),
						FeeMetadata { payer: origin.clone(), fee: Default::default() },
					)
					.map_err(|_| Error::<T>::TransferFailed)?;
			}
			Ok(())
		}
