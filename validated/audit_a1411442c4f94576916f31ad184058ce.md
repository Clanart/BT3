### Title
Reward-Index Front-Running Allows JIT vlMGP Lockers to Steal a Share of Forfeited MGP Meant for Long-Term Lockers - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` distributes forfeited MGP (from early-unlock penalties) using a classic `rewardPerTokenStored` accumulator divided by the *live* `totalStaked()` value at the moment `queueMGP`/`_queueNewRewardsWithoutTransfer` runs, with no checkpoint tied to staking duration. [1](#0-0)  An attacker who locks MGP into `VLMGP` in the same block/immediately before a victim's forfeited-MGP harvest (`MasterMagpie._sendMGPForVlMGPPool` → `queueMGP`) inflates `totalStaked()` and is immediately eligible to claim a share of that forfeiture through `getReward`, despite holding the position for zero meaningful duration. [2](#0-1)  This is enabled because `userRewardPerTokenPaid` is only refreshed via the `updateReward`/`updateFor` code path invoked on `getReward`/`getRewards`/`updateFor`, not atomically tied to the exact block in which the staker's balance changed relative to the reward event. [3](#0-2) [4](#0-3) 

### Finding Description
`queueMGP` is called by `MasterMagpie._sendMGPForVlMGPPool` when a locker harvests forfeited MGP. [5](#0-4)  Inside `queueMGP`, the non-rewardable (forfeited) portion is queued into the pool's global index via `_queueNewRewardsWithoutTransfer`, which computes the per-token increment as `forfeitAmount * 1e18 / totalStaked()`, where `totalStaked()` simply reads `vlMGP.totalSupply()` at call time — a value fully controllable by anyone locking MGP in the same block. [6](#0-5) [1](#0-0) 

A user's claimable amount is `balanceOf(account) * (rewardPerToken - userRewardPerTokenPaid[account])`, and `userRewardPerTokenPaid` is only synced through the `updateReward`/`updateFor` modifiers, which run on `getReward`, `getRewards`, or an explicit `updateFor` call — not automatically the instant a user's underlying `vlMGP` balance changes via `VLMGP.lock`. [7](#0-6) [8](#0-7)  For any account whose `userRewardPerTokenPaid` has never been set (a fresh locker), the stored value defaults to `0`, so the very first `getReward`/`updateFor` call attributes to that account its *entire* balance multiplied by the full current `rewardPerTokenStored`, not just the increment accrued after it started staking. Combined with the ability to time a `VLMGP.lock` call immediately ahead of a pending `queueMGP` transaction in the mempool, an attacker can capture a proportional slice of another locker's forfeited MGP for a position held for effectively zero duration relative to other long-term lockers.

None of the existing guards (`onlyManager`, `nonReentrant` on `queueMGP`, `onlyMasterMagpie` on `getReward`) prevent this, because they only restrict *who* can call these functions, not *when* relative to a staking-balance change, and there is no vesting/time-weighting on the reward index itself. [9](#0-8) [10](#0-9) 

### Impact Explanation
This falls under theft of unclaimed yield: forfeited MGP that should accrue only to lockers who bore the opportunity cost/lock duration is instead diverted proportionally to a just-in-time depositor. The scoped loss is bounded by the forfeited-MGP amount queued in the harvested transaction and the attacker's relative share of post-lock `totalStaked()`.

### Likelihood Explanation
Exploitability requires: (1) observing a pending harvest transaction that will trigger `queueMGP` with a non-trivial forfeiture, and (2) having spare MGP to lock via `VLMGP.lock` and front-run it in the same block. This is a meaningfully different risk profile than a flash-loan attack because `vlMGP` is a locking token — the attacker's capital that is deposited to inflate `totalStaked()` remains locked for `VLMGP`'s standard lock duration afterward, meaning the attacker commits real capital rather than borrowing it for a single transaction. This significantly raises the capital cost of the attack and reduces repeatability compared to a pure flash-loan/JIT-liquidity exploit, but the attack remains feasible for anyone holding or willing to lock MGP, and is repeatable against every future large forfeiture event.

Note: I was not able to fully verify within the available tool budget whether `VLMGP.lock` triggers any checkpoint call into `vlMGPBaseRewarder.updateFor` at the moment of locking (which would partially, but not fully, mitigate the issue — a checkpoint at lock time would still allow the attacker to earn the very next reward increment fully, just not stale historical rewards). This is a limitation of the investigation, not evidence against the finding.

### Recommendation
Introduce a minimum staking/holding-duration requirement (e.g., snapshot-based reward distribution rather than a live-index model), or explicitly checkpoint `userRewardPerTokenPaid` to the current `rewardPerToken()` at the exact moment `balanceOf` changes (i.e., have `VLMGP.lock`/`unlock` invoke `vlMGPBaseRewarder.updateFor(account)` before the balance change is reflected), and consider batching/delaying forfeiture distribution (e.g., a short time-lock or streaming distribution) so that `totalStaked()` used as the denominator cannot be manipulated within the same block as the forfeiture event.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder` with `MasterMagpie` registered as `manager`.
2. Have Locker A lock a modest amount of MGP and wait long enough to accrue an early-unlock forfeiture scenario (or configure `getRewardablePercentWAD` to return < 100%).
3. Fund Attacker with spare MGP; do NOT let Attacker interact with the pool beforehand.
4. In a single block: Attacker calls `VLMGP.lock(largeAmount)`, then simulate Locker A's harvest which triggers `MasterMagpie._sendMGPForVlMGPPool` → `vlMGPBaseRewarder.queueMGP`.
5. Immediately (same or next block, no time elapsed) call `getReward(attacker, attacker)` or `updateFor(attacker)` then `earned(attacker, MGP)`.
6. Assert `earned(attacker, MGP) > 0` despite the attacker having zero prior staking duration, and assert the amount is proportional to `attackerBalance / totalStaked() * forfeitAmount`, confirming dilution/theft of Locker A's forfeited MGP.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
