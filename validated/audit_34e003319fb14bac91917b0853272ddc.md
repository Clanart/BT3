## Finding: Batch-wide relayer reward misattribution in `pallet-consensus-incentives`

### Title
Relayer reward for an entire consensus-message batch is paid entirely to the signer of the first message, letting an attacker steal rewards owed for other messages in the same batch - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::on_executed`, the `FeeHandler` hook invoked after `pallet-ismp` processes a batch of messages, derives a single `relayer_account` from **only the first message** in the batch, then loops over **every** `StateMachineUpdated` event produced by the whole batch and pays the reward for each state machine's height advance to that one signer. [1](#0-0) [2](#0-1) 

### Finding Description
`on_executed` receives `messages: Vec<MessageWithWeight>` and `events: Vec<IsmpEvent>` for an entire submitted batch. It only inspects `messages.get(0)`; if that first entry is a `Message::Consensus`, it recovers a public key from `consensus_msg.signer` over `keccak_256(consensus_msg.consensus_proof)` and treats the recovered key as "the relayer" for the whole call. [3](#0-2) 

It then collapses the `events` vector to the highest `latest_height` per `state_machine_id` across the *entire batch* and calls `process_message` (which transfers `reward` from the treasury to `relayer_account`) once per state machine represented in that batch. [4](#0-3) [5](#0-4) 

Consensus proofs are public, verifiable artifacts (light-client update data) — anyone can fetch a valid consensus proof for any tracked chain and re-submit it, since verification does not require any secret held by an "honest relayer." Nothing in `on_executed` checks that the signer recovered from message 0 corresponds to the message(s) that actually advanced the other state machines' heights in the same batch. An unprivileged caller can therefore construct/submit a batch (or front-run/reorder a batch containing several unrelated chains' consensus updates) where:
1. Message 0 is a cheap consensus proof (or reused proof) self-signed with the attacker's own keypair.
2. The remaining messages are legitimate, publicly obtainable consensus proofs for other state machines that other relayers were going to deliver.

Since `relayer_account` is fixed from message 0 alone, `process_message` pays out the reward for *every* `StateMachineId` whose height advanced in that batch to the attacker's account — including chains whose proof the attacker did not need to (or could not) have generated themselves. This is a wrong-beneficiary fund-movement bug, not merely a front-running concern: it is a structural flaw in how the batch attributes payment, exploitable by any account that can submit (or influence the ordering of) a multi-message consensus batch.

### Impact Explanation
This directly violates the "bridged assets/relayer rewards must move exactly once and only to the rightful beneficiary" invariant. The treasury pays the wrong account for legitimate consensus-delivery work performed elsewhere in the batch, causing loss of relayer incentive funds to an unrelated party and enabling systematic reward theft across any state machine incentivized by this pallet, without needing a compromised relayer, prover, or admin key — only the ability to submit or reorder messages within a batch.

### Likelihood Explanation
Consensus proofs for tracked light clients are public data (obtainable from the source chain's own state/consensus), so no relayer secret is needed to reconstruct message 0's payload; only a valid signature over `keccak_256(consensus_proof)` from an attacker-controlled key is required, which the attacker trivially produces themselves. Batches with more than one message are the pallet's normal expected operating mode (the code explicitly handles "a batch contains multiple `StateMachineUpdated` events"), so the vulnerable code path is on the mainline flow, not an edge case. [6](#0-5) 

### Recommendation
Attribute each `StateMachineUpdated` reward to the signer of the specific `Message::Consensus` entry that produced it, not to `messages.get(0)`. This requires correlating each consensus message in the batch to the `state_machine_id`(s)/height(s) it actually advanced (e.g., by processing messages and their resulting events pairwise, or by embedding the state-machine id in the signed payload) rather than collapsing the whole batch to one payee.

### Proof of Concept
Conceptual reproduction (pallet-level, no external actors needed beyond the caller):
1. Attacker holds a keypair `K_attacker` and constructs `Signature` over `keccak_256(proof_A)` for state machine `A`, where `proof_A` is any consensus proof they can supply (even trivial/cheap or already-known).
2. Attacker submits a batch `messages = [Consensus(proof_A, signer=K_attacker), Consensus(proof_B, signer=K_honest), Consensus(proof_C, signer=K_honest2)]` where `proof_B`/`proof_C` are legitimate, publicly available consensus updates for chains `B` and `C` that other relayers intended to submit.
3. `pallet-ismp` processes the batch and emits `StateMachineUpdated` events for `A`, `B`, and `C`.
4. `on_executed` recovers only `K_attacker` from `messages[0]`, then iterates `highest_per_state_machine` over `A`, `B`, `C` and calls `process_message` three times, each transferring the treasury reward to the attacker's account — even though the attacker only provided `proof_A`. [7](#0-6) 

Note on confidence: I was not able to fully trace, within the available context, exactly how `pallet-ismp` assembles the `Vec<Message>` passed into a single `handle_messages`-style extrinsic (i.e., whether unrelated-chain consensus messages can indeed be freely mixed into one caller-controlled batch by an ordinary account, versus being restricted to a single state machine per call). That assembly logic lives in `pallet-ismp`'s message-handling extrinsic, which was outside the scoped search results returned to me. This should be verified against `pallet-ismp`'s `handle_messages`/`handle` entrypoint before treating this as fully confirmed, though the reward-attribution logic itself (`messages.get(0)` deciding the payee for the whole batch) is confirmed directly from the code shown.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
