### Title
Missing `pair.Enabled` check in `ConvertCoinToERC20FromPacket` allows re-conversion to ERC20 after governance disables the token pair - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
The reported Aave bug is a missing-restriction-check pattern: a function that changes an asset's representation/mode fails to re-validate that the target mode is still permitted, allowing a user to reach a disallowed state via an indirect path. The Cosmos EVM analog is in the ERC20/IBC middleware: `OnRecvPacket` correctly checks `pair.Enabled` before converting an incoming IBC coin to its ERC20 representation, but the timeout/error-ack refund path, `ConvertCoinToERC20FromPacket`, does **not** check `pair.Enabled` before calling `ConvertCoinNativeERC20`.

### Finding Description
`OnRecvPacket` explicitly guards the "coin -> ERC20" conversion with an `Enabled` check: [1](#0-0) 

However, the refund-conversion path used by `OnAcknowledgementPacket` (error ack) and `OnTimeoutPacket`, `ConvertCoinToERC20FromPacket`, only checks the module-wide `EnableErc20` param and `IsDenomRegistered`, never the per-pair `Enabled` flag, before invoking `ConvertCoinNativeERC20`: [2](#0-1) 

Contrast this with `MintingEnabled`, which is the canonical checkpoint used by `ConvertCoin`/`ConvertERC20` msg handlers and explicitly rejects conversion when `!pair.Enabled`: [3](#0-2) 

`ToggleConversion` is the governance-controlled way to disable a token pair (e.g., due to a compromised/buggy ERC20 contract, a security incident, or a controlled migration), and it is expected that no further coin<->ERC20 conversions occur for that pair once disabled: [4](#0-3) 

Because `ConvertCoinToERC20FromPacket` skips the `pair.Enabled` check, an unprivileged user can bypass a governance-imposed pause on a specific token pair by triggering (or simply having in-flight) an IBC transfer of the native ERC20-backed coin that ends in a timeout or error acknowledgement. When that happens, the coin is converted back into the (supposedly disabled) ERC20 representation via `ConvertCoinNativeERC20`, exactly mirroring the `swapBorrowRateMode` pattern of reaching a disallowed mode/state through an alternate code path that lacks the same guard as the primary path.

### Impact Explanation
This is a genuine restriction bypass analogous to the seed report, but I could not confirm it rises to the Critical bar required by the impact gate. `ConvertCoinNativeERC20` still performs coin burn / ERC20 unescrow with the intended 1:1 accounting (no minting of extra value, no double-spend was found in the code read), so the direct effect is "user obtains ERC20 tokens for a disabled pair" rather than unauthorized minting, burning, or fund theft. Whether this is Critical depends on why governance disabled the pair (e.g., if the underlying ERC20 contract is compromised/self-destructing, forcing tokens back into ERC20 form via this path could indirectly enable fund loss or interact with a broken contract in the escrow/unescrow flow), but I did not verify `ConvertCoinNativeERC20`'s internals (unescrow/mint logic and its interaction checks) due to running out of tool budget.

### Likelihood Explanation
The trigger requires only an ordinary IBC transfer that times out or receives an error acknowledgement — both are conditions reachable by any unprivileged user or simply by normal relayer/network behavior (no malicious relayer needed), making the trigger itself easy to reach. The harder part is causing (or already having) governance disable a specific pair via `ToggleConversion` while the user holds an in-flight transfer, so real-world likelihood is moderate and situational.

### Recommendation
Add the same `pair.Enabled` check used in `OnRecvPacket` to `ConvertCoinToERC20FromPacket` before calling `ConvertCoinNativeERC20`, so that a disabled pair also blocks the refund-triggered conversion path:
```go
case pair.IsNativeERC20():
    if !pair.Enabled {
        return nil // no-op: pair conversion disabled
    }
    ...
```
Additionally, audit all other conversion entry points (mint/burn hooks, precompile flows) for consistent enforcement of `pair.Enabled`, matching the long-term recommendation from the seed report of systematically testing that disallowed state transitions cannot be reached via any code path.

### Proof of Concept
1. Governance registers a native ERC20 token pair and it is `Enabled = true`.
2. A user holds the ERC20 token and converts it into the native coin representation (`ConvertERC20`).
3. Governance calls `ToggleConversion` to disable the pair (e.g., due to a security concern), setting `pair.Enabled = false`.
4. The user (or any user) sends an IBC transfer of the (now-disabled) native coin denom out of the chain.
5. The transfer times out or the counterparty chain returns an error acknowledgement, invoking `OnTimeoutPacket` / `OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket`.
6. Because `pair.Enabled` is never checked in this path, `ConvertCoinNativeERC20` executes and the user receives ERC20 tokens for a pair that governance explicitly disabled — bypassing the restriction that `MintingEnabled`/`OnRecvPacket` enforce elsewhere.

Note: I was unable to fully verify the internal accounting of `ConvertCoinNativeERC20` (unescrow/burn logic) within the available tool budget, so I cannot confirm whether this bypass alone crosses the Critical threshold (e.g., unauthorized minting or fund extraction) versus being a lower-severity governance-control bypass. This should be verified with a Devin session that inspects `ConvertCoinNativeERC20` and any interaction with a disabled/compromised ERC20 contract before treating this as a definitive Critical finding.

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil
}
