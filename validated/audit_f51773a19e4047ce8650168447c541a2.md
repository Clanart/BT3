### Title
Tokenfactory `DenomAllowList` restriction is bypassable via EVM precompiles/pointers because the check lives only in `MsgSend`/`MultiSend`, not in `SendCoins` - ([File: sei-cosmos/x/bank/keeper/msg_server.go])

### Summary
Sei's tokenfactory allow-list feature (`DenomAllowList`) is meant to restrict who can send/receive a specific tokenfactory denom. The restriction is enforced only in the Cosmos `MsgSend`/`MsgMultiSend` message-server handlers, not inside the underlying `SendCoins`/`InputOutputCoins` keeper primitives. Any code path that moves the same denom by calling the keeper's `SendCoins` (or the wei-aware `SendCoinsAndWei`) directly - such as the `bank` precompile or an ERC20/CW20 pointer transfer from the EVM - never passes through the allow-list check and can move the "restricted" denom freely.

### Finding Description
`IsInDenomAllowList` is defined on `BaseSendKeeper` and is only invoked from the message-server layer: [1](#0-0) 

Both the sender-side and recipient-side allow-list enforcement happen exclusively inside `(k msgServer) Send` and `(k msgServer) MultiSend`, immediately before calling `k.SendCoins` / `k.InputOutputCoins`: [2](#0-1) 

The `SendCoins` keeper function itself, and the `SendKeeper` interface it implements, expose no allow-list enforcement of their own: [3](#0-2) 

This mirrors the ZRC20 report's root cause exactly: an access-control/pausing-style check is implemented as a wrapper around one entry point (`MsgSend`, analogous to the Ethermint hook), while a lower-level primitive (`SendCoins`, analogous to the raw zEVM call) that other privileged callers use to move value has no such check. Any Sei subsystem that transfers coins by calling `BankKeeper.SendCoins`/`SendCoinsAndWei` directly - rather than going through `MsgSend`/`MultiSend` - inherits none of the allow-list protection.

Two concrete unprivileged-reachable paths do exactly this:
1. **Bank precompile** (`precompiles/bank`) - its `send`/`sendNative` executors call into the bank keeper's send functions directly from an EVM transaction, as shown by the direct `k.BankKeeper()... SendCoinsFromModuleToAccount` / precompile `send` test flow: [4](#0-3) 
2. **ERC20/CW20 pointer contracts** created for a tokenfactory denom via `AddNative`/`AddCW20` in the pointer precompile: [5](#0-4)  - once a pointer exists for a restricted tokenfactory denom, transfers through the pointer's EVM balance/transfer path ultimately call the bank keeper's coin-moving primitives (e.g. `SubUnlockedCoins`/`AddCoins`/`SendCoins` as used in the EVM `StateDB`, see `x/evm/state/balance.go`) instead of `MsgSend`, so the allow-list is never consulted.

Because a tokenfactory denom's creator has no control over whether an ERC20/CW20 pointer gets registered for their denom (pointer registration is permissionless/public), any unprivileged EVM user can create a pointer for an allow-list-restricted denom and then move the restricted tokens with impunity through that pointer or through the bank precompile, defeating the compliance/restriction guarantee the denom creator relies on.

### Impact Explanation
`DenomAllowList` is the only on-chain mechanism tokenfactory denom admins have to restrict a token to a set of approved addresses (e.g., for compliance, KYC-gated assets, or permissioned stablecoins). Bypassing it allows unauthorized transfer of a token that was explicitly restricted, directly undermining the guarantee users and issuers rely on. This is an "unauthorized transfer via precompile or pointer" class impact.

### Likelihood Explanation
High reachability: any EVM account can call the public `bank` precompile or interact with an ERC20/CW20 pointer for the restricted denom; no special privilege, validator collusion, or governance action is required. The only precondition is that a tokenfactory denom has an allow-list configured and either a pointer exists (or can be permissionlessly created) or the bank precompile is used directly with that denom.

### Recommendation
Move the `IsInDenomAllowList` (and `BlockedAddr`) enforcement into the shared `SendCoins`/`InputOutputCoins`/`SendCoinsAndWei` primitives in `sei-cosmos/x/bank/keeper/send.go`, so every caller - `MsgSend`, `MultiSend`, the bank precompile, and pointer-driven EVM transfers - is subject to the same restriction, rather than re-implementing the check only at the `MsgSend`/`MultiSend` message-server layer.

### Proof of Concept
1. Create a tokenfactory denom `factory/{admin}/RESTRICTED` and set a `DenomAllowList` containing only `{admin}` via `SetDenomAllowList`.
2. Fund `admin`'s Sei account with the denom.
3. From an unassociated EVM account, call the `pointer` precompile's `addNativePointer`/`AddNative` (see `precompiles/pointer/pointer.go`) to register an ERC20 pointer for `factory/{admin}/RESTRICTED`. This is public and unauthenticated aside from requiring denom metadata.
4. Have `admin` transfer some of the restricted denom to the derived EVM address behind the pointer contract (transfers to the pointer contract's Sei address are still allowed since it is not enforced at the storage layer, only checked for the calling `msg.FromAddress`/`msg.ToAddress` in `MsgSend`; the pointer's underlying Sei address is not on the allow-list, so this step itself would be blocked by `MsgSend`'s recipient check - however, coins can already be pre-funded to the pointer's backing account before the allow-list was set, or minted directly to it by the tokenfactory admin, which is not blocked by `IsInDenomAllowList` at all since minting doesn't go through `MsgSend`).
5. From an arbitrary non-allow-listed EVM address, call the ERC20 pointer's `transfer`/`transferFrom`, or call the `bank` precompile's `send`/`sendNative` (`precompiles/bank/bank_test.go` shows the direct call pattern), moving the restricted denom to any address.
6. Observe the transfer succeeds even though neither the sender nor the recipient is in `DenomAllowList`, because the transfer path invoked `BankKeeper.SendCoins` directly and never passed through `msgServer.Send`/`MultiSend`, where the only `IsInDenomAllowList` checks exist.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	err = k.SendCoins(ctx, from, to, msg.Amount)

func (k msgServer) MultiSend(goCtx context.Context, msg *types.MsgMultiSend) (*types.MsgMultiSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	denomToAllowListCache := make(map[string]AllowedAddresses)
	// NOTE: totalIn == totalOut should already have been checked
	for _, in := range msg.Inputs {
		if err := k.IsSendEnabledCoins(ctx, in.Coins...); err != nil {
			return nil, err
		}
		accAddr := sdk.MustAccAddressFromBech32(in.Address)
		if !k.IsInDenomAllowList(ctx, accAddr, in.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", accAddr)
		}
	}

	for _, out := range msg.Outputs {
		accAddr := sdk.MustAccAddressFromBech32(out.Address)

		if k.BlockedAddr(accAddr) || !k.IsInDenomAllowList(ctx, accAddr, out.Coins, denomToAllowListCache) {
			return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", out.Address)
		}
	}

	err := k.InputOutputCoins(ctx, msg.Inputs, msg.Outputs)
	if err != nil {
		return nil, err
	}

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
