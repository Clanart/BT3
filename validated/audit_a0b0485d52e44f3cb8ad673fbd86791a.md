## Analysis

The external report's core broken invariant: **a contract pays a native-token fee to bridge/dispatch something, receives an unrequested native refund mid-call, but has no path to return that refund to the original payer** — the value becomes permanently stuck.

Hyperbridge's own `IntentGatewayV2`/`ExtrinsicIntents` fee-swap paths already defend against exactly this class: after calling `swapETHForExactTokens`, they explicitly refund any leftover `msg.value` back to `msg.sender`: [1](#0-0) 

`EvmHost.sol`, however, performs the identical native-fee-swap pattern in three public entrypoints — `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` — but never refunds the excess native token that the Uniswap router returns to `address(this)` after `swapETHForExactTokens`: [2](#0-1) [3](#0-2) [4](#0-3) 

Any leftover ETH from `swapETHForExactTokens{value: msg.value}(post.fee, ...)` lands in the host contract and is never routed back to `_msgSender()`. The only exit for native ETH sitting in `EvmHost` is `withdraw()`, which is restricted to `_hostParams.hostManager` (cross-chain governance) and sends to an arbitrary `params.beneficiary` chosen by governance — not necessarily the original overpaying user: [5](#0-4) 

### Title
Overpaid native fee in `EvmHost.dispatch`/`fundRequest` is permanently stuck with no user-recoverable refund path - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and swap it for the exact `feeToken` amount needed via `IUniswapV2Router02.swapETHForExactTokens`. Unlike `IntentGatewayV2`/`ExtrinsicIntents`, which explicitly refund unspent native tokens to `msg.sender` after an equivalent swap, `EvmHost` has no refund step. Any ETH sent beyond the exact fee requirement is retained by the router's refund to `address(this)` and then has no protocol-level path back to the depositor.

### Finding Description
In all three functions, the pattern is:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp);
```
`swapETHForExactTokens` only consumes as much ETH as needed to obtain the exact output amount and refunds the rest to the caller (`address(this)`, i.e. `EvmHost`) — it does not, and cannot, refund to the original `_msgSender()`. There is no subsequent line moving that residual ETH back to the caller, contrary to the pattern already established elsewhere in the same codebase for this exact scenario (`IntentGatewayV2.placeOrder`/`ExtrinsicIntents.fillOrder`, which both immediately forward any `msgValue` remainder back to `msg.sender`).

Because `EvmHost` has no user-facing withdrawal function for native balance, and the only native-ETH exit (`withdraw`) is restricted to `_hostParams.hostManager` with an arbitrary `beneficiary`, any user who overestimates the native amount required (which is likely, since callers must guess/quote an amount sufficient to cover `post.fee` given the router's current price, with no on-chain slippage protection or minimum specified by the caller) permanently loses the difference.

### Impact Explanation
This is a direct, unprivileged loss-of-funds bug: any caller of `dispatch`/`fundRequest` who sends `msg.value` even slightly above what the swap consumes has that excess locked in the host contract with no recovery path back to them. This matches the bounty's "stealing or loss of funds" impact category and requires no malicious peer, relayer, or governance actor — it triggers purely from normal usage with any overestimate of the native value to send (unavoidable in practice, since the exact ETH/feeToken price at execution time is unknown to the caller ahead of the transaction).

### Likelihood Explanation
High. Callers of `dispatch`/`fundRequest` must supply `msg.value` before knowing the exact AMM price at execution, so any reasonable safety buffer above the expected fee results in permanently locked dust-to-significant amounts of ETH per call. This is a systemic, unconditional loss on every overpaid call, not an edge case.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the actual amount consumed (`amounts[0]` returned by the router) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents.fillOrder`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = msg.value - amounts[0];
if (refund > 0) {
    (bool sent,) = _msgSender().call{value: refund}("");
    if (!sent) revert RefundFailed();
}
```

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.01 ether` worth of ETH at the current Uniswap V2 price.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, ...)` consumes `~0.01 ether` and refunds `~0.99 ether` to `address(this)` (the `EvmHost` contract).
3. `dispatch` completes normally, emitting `PostRequestEvent`; the `~0.99 ether` remains in `EvmHost`'s balance.
4. The caller has no function to reclaim this balance; only cross-chain governance via `withdraw()` can move it, and only to a beneficiary of governance's choosing — not necessarily the original caller.
5. Repeated for every `dispatch`/`fundRequest` call with any native overpayment, this accumulates unrecoverable user losses in the host contract.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
