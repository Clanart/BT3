## Analysis

The external report describes a scaling-constant bug that's only correct in one assumed regime (APR-style linear conversion) but silently breaks in the reverse/actual regime (APY-style compounding), producing an incorrect numeric result without any revert.

The closest local analog is in `pallet-hyper-fungible-token`'s decimal-scaling helpers, which convert amounts between an ERC20 token's decimals and the local Substrate asset's decimals when tokens cross the bridge. Both helpers assume one fixed direction of the decimal delta and use `saturating_sub`, which silently collapses to a no-op scale factor (`10^0 = 1`) instead of erroring or scaling in the other direction when the assumption doesn't hold — exactly the "constant correct only in the assumed direction" bug class from the report.

### Title
Asymmetric decimal-scaling in `convert_to_erc20`/`convert_to_balance` mis-prices cross-chain token amounts when local decimals exceed ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` compute their scale factor as `10^(erc_decimals.saturating_sub(local_decimals))` (or the mirror), which is only correct when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals`, `saturating_sub` returns `0`, so the scale factor becomes `1` — no scaling is applied at all, instead of scaling in the opposite direction as the doc comment for the sibling function implies. [1](#0-0) 

### Finding Description
`convert_to_erc20` is documented as "Multiplies by `10^(erc_decimals - local_decimals)` to scale up to ERC20 precision" — an assumption that `erc_decimals > local_decimals`. Its actual implementation is:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [2](#0-1) 

If the local Substrate asset has *more* decimal precision than the destination ERC20 token (e.g. local `18` vs erc `6`, a very common pairing — DOT-style assets at 10-18 decimals bridging to a 6-decimal USDC-style ERC20), `erc_decimals.saturating_sub(local_decimals)` evaluates to `0` instead of the negative exponent the comment assumes should scale the value *down*. The function then returns `value` completely unscaled, which is then embedded as the message `amount` field dispatched to the destination chain in `erc_decimals` units. Because the raw value was computed at 18-decimal precision but is interpreted by the destination as 6-decimal precision, the emitted amount is inflated by `10^(local_decimals - erc_decimals)` (e.g. `10^12`), an outbound over-mint relative to what was actually escrowed/burned on the local side.

`convert_to_balance` has the symmetric flaw in the opposite direction: when `local_decimals > erc_decimals`, the same `saturating_sub` collapses to `0`, so an inbound message amount (received in `erc_decimals` precision) is credited to the beneficiary unscaled instead of being multiplied up to `local_decimals` precision — under-crediting the beneficiary in the `on_accept` mint/transfer path. [3](#0-2) 

Both `on_accept` (inbound credit) and `on_timeout` (refund) call `convert_to_balance` with `erc_decimals` and `decimals` (the local asset's decimals) exactly as configured in `Precisions` storage — there is no on-chain guard rejecting the `local_decimals > erc_decimals` configuration, so this is reachable purely by how governance registers a token pair, not by any malicious relayer/prover assumption. [4](#0-3) [5](#0-4) 

### Impact Explanation
- Outbound (`convert_to_erc20`, presumably invoked from the dispatch path in `lib.rs`, not directly confirmed in this pass): if a registered token pair has `local_decimals > erc_decimals`, every outbound transfer embeds an amount inflated by `10^(local_decimals-erc_decimals)` in the cross-chain message, letting the destination contract release/mint far more value than was locked/burned locally — direct loss of bridged funds / custody drain.
- Inbound (`convert_to_balance`, confirmed call sites in `on_accept`/`on_timeout`): the same misconfiguration under-credits (or, depending on decimal arrangement, over-credits) beneficiaries relative to what was actually locked on the source chain, corrupting the custodial escrow's 1:1 backing invariant.

Both fall squarely within the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot — this is a false-amount/value-mismatch bug, not a "loss due to malicious relayer/prover" scenario, since the scaling function itself computes the wrong number for a category of legitimately-configured token pairs.

### Likelihood Explanation
Reachability depends on whether governance registers any token pair where the local Substrate asset's decimals exceed the source/destination ERC20's decimals — a very plausible configuration in practice (Substrate assets are frequently minted at 10, 12, or 18 decimals while many ERC20 stablecoins use 6). I was not able to confirm in this pass whether validation exists elsewhere (e.g. in the `RegisterToken`-equivalent extrinsic in `lib.rs`) that forbids `local_decimals > erc_decimals`; the `Precisions` storage and its setter were not inspected. This is the primary uncertainty in this finding — if such a decimal-ordering check exists at registration time, the bug is unreachable in production, and would need to be confirmed by reading `modules/pallets/hyper-fungible-token/src/lib.rs` in full (not retrieved within the tool budget of this session).

### Recommendation
Replace the `saturating_sub`-based single-direction scaling with an explicit branch that scales up or down correctly regardless of which side has more decimals (mirroring the `adjustDecimals` pattern already used elsewhere in the codebase, e.g. `sdk/packages/sdk/src/utils.ts:985-994`), and/or enforce at token-registration time that decimal configuration cannot silently degenerate into a no-op scale factor.

### Proof of Concept
Conceptual (not executed): register a token pair with `local_decimals = 18`, `erc_decimals = 6`. Send an outbound transfer of local `value = 1_000_000_000_000` (1 unit at 18 decimals ≈ 1e-6 of a token). `convert_to_erc20(value, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, returning `value` unscaled = `1_000_000_000_000`. The destination chain interprets this as `1_000_000_000_000` units at 6-decimal precision = `1,000,000` whole tokens — a 10^12× inflation relative to the actual value locked. [2](#0-1) 

**Caveat:** I could not confirm within this session (a) the exact outbound call site of `convert_to_erc20` in `lib.rs`, or (b) whether a decimal-ordering guard exists at token registration that would make this configuration unreachable. If the user needs full certainty, a Devin session with access to the complete `modules/pallets/hyper-fungible-token/src/lib.rs` and its registration extrinsic would resolve this.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
