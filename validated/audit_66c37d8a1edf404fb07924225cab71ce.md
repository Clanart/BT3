### Title
Path-containment check in `resolveWithin` uses a bare prefix match, allowing deep-link `filepath` to escape the repository into a sibling directory - (File: `app/src/lib/path.ts`)

### Summary
The external report's bug class is a boundary comparison that is too permissive (`>` instead of `>=`), letting a value that should be rejected slip past a guard. The Desktop analog is the containment check in `_resolveWithin`, which uses `realResolved.startsWith(realRoot)` [1](#0-0)  instead of a boundary-aware comparison (`===` or `startsWith(realRoot + sep)`). This is the same defect shape: the guard is supposed to enforce "resolved path is at-or-under root," but the actual check accepts any path whose string prefix merely *matches characters of* the root, including sibling directories like `myrepo-secrets` when the root is `myrepo`.

### Finding Description
`resolveWithin` is the app's generic "don't let attacker input escape a directory" primitive, documented as guaranteeing the resolved path "resides at, or underneath" `rootPath` [2](#0-1) . The actual containment test is:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` performs no path-separator boundary check. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, then `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa` also satisfies `startsWith(realRoot)` even though it is a completely different, sibling directory — not a subdirectory of `myrepo` at all.

This primitive is used directly on attacker/remote-influenced input in the deep-link handler `openRepositoryFromUrl`:
```
if (filepath !== null) {
  if (isAbsolute(filepath)) { ...refuse... }
  const resolved = await resolveWithin(repository.path, filepath)
  if (resolved !== null) {
    shell.showItemInFolder(resolved)
  } ...
}
``` [3](#0-2) 

The `isAbsolute(filepath)` guard only blocks absolute paths; it does nothing to stop relative traversal such as `../myrepo-secrets/id_rsa`, which is exactly the input class `resolveWithin` is supposed to catch (and is unit-tested for, e.g. `resolveWithin(root, join('..'))` returning `null` [4](#0-3) ). But the existing test suite never exercises the "sibling directory sharing a name prefix" case, so the boundary defect is not caught.

Given `resolveWithin(repository.path, '../<sibling-dir-with-same-prefix>/<file>')`:
- `join('..', '<sibling>/<file>')` normalizes to a `..`-relative path.
- `resolve(normalizedRoot, normalizedRelative)` collapses it to the sibling path.
- `realpath` resolves both, and the `startsWith` check passes because the sibling's name starts with the repo folder's name.

GitHub Desktop's default clone location groups all of a user's repositories under one parent folder (e.g. `~/Documents/GitHub/`), so sibling repos/folders sharing a name prefix (`myrepo`, `myrepo-old`, `myrepo.wiki`, `myrepo-secrets`) are a realistic, common layout — this is not a contrived filesystem arrangement.

The same unguarded `resolveWithin` primitive is also used for reading file contents that get sent to Copilot for automatic conflict resolution [5](#0-4) , meaning the same boundary flaw is reachable anywhere `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` is asked to validate an attacker-influenced relative path against a repo root.

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openRepo/...&filepath=...` deep link (or, for the Copilot path, control repository content that drives conflict file paths) can cause Desktop to resolve and act on a path *outside* the intended repository while `resolveWithin` reports success. In the deep-link case this manifests as `shell.showItemInFolder` opening/revealing a file in a sibling directory outside the repo (file existence/location disclosure of arbitrary sibling files chosen by crafting the traversal + relying on a common naming pattern). Where `resolveWithin` gates file *reads* whose content is subsequently used elsewhere (e.g., sent to an LLM backend for conflict resolution), the same boundary bug could cause out-of-repo file content to be read and exfiltrated. This matches the "file write or read outside the repo" / "credential exfiltration" impact classes named in the assignment's Valid Impact list.

### Likelihood Explanation
Exploitability requires: (1) the app default folder layout where multiple repos share a directory with a common name prefix — a very common real-world pattern for Desktop users, and (2) the victim clicking an attacker-supplied deep link (an unprivileged, no-local-access attacker primitive explicitly listed as valid). No other guard in the codebase intercepts this: `isAbsolute(filepath)` only screens fully-qualified paths, not `..`-relative escapes, and there is no secondary sanitization or separator-aware check anywhere else in the call chain before `shell.showItemInFolder`. Likelihood is medium: it depends on a matching sibling-directory naming coincidence, but that coincidence is common (e.g., `repo` and `repo.wiki`, `repo` and `repo-backup`).

### Recommendation
Change the containment check in `_resolveWithin` to be boundary-aware, e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the caller-appropriate `sep` for the `options` variant — `Path.sep`, `Path.posix.sep`, or `Path.win32.sep`). Add regression tests covering sibling directories that share a name prefix with the root (e.g., root `.../myrepo` vs. target `.../myrepo-evil/file`) to prevent regressions of this exact class.

### Proof of Concept
1. Layout on disk:
   - `/Users/victim/Documents/GitHub/myrepo` (the tracked repository, `repository.path`)
   - `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa` (an unrelated sibling directory/file)
2. Attacker sends the victim a deep link such as:
   `x-github-client://openRepo/https://github.com/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fid_rsa`
3. Desktop's `openRepositoryFromUrl` receives `filepath = "../myrepo-secrets/id_rsa"`; `isAbsolute(filepath)` is `false`, so it proceeds to `resolveWithin(repository.path, filepath)` [3](#0-2) .
4. Inside `_resolveWithin`, `resolve(normalizedRoot, normalizedRelative)` yields `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`; `realResolved.startsWith(realRoot)` evaluates `true` because `"myrepo-secrets".startsWith` shares the `myrepo` prefix with no separator check [1](#0-0) .
5. `resolveWithin` returns the sibling path instead of `null`, and `shell.showItemInFolder(resolved)` reveals/opens the out-of-repo file to the attacker-chosen location, confirming escape past the intended containment boundary.

Note: I could not fully trace every downstream consumer of `resolveWithin`/`resolveWithinPosix` in `app-store.ts` within the available search budget (2 additional call sites were found but not inspected line-by-line); if further impact validation is needed, those call sites should be reviewed to determine whether they process fully attacker-controlled paths as well.
