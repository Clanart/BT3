### Title
Payout attribution (operator reimbursement credit) is not covered by the user's withdrawal signature, allowing reimbursement misattribution - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The user's authorization signature for a withdrawal payout only commits to the withdrawal input and the user-payout output (`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`). It does **not** cover the `OP_RETURN` output that records which operator "fronted" the payout. Because reimbursement is later granted purely based on that unauthenticated `OP_RETURN` value, any third party who completes and mines a payout transaction for a pending withdrawal can write an arbitrary operator's x-only pubkey into the `OP_RETURN`, causing that operator to be credited/reimbursed for a payout it never funded.

### Finding Description
`create_payout_txhandler` builds the payout transaction with the withdrawal UTXO as input 0 (signed by the withdrawing user) and appends an `OP_RETURN` output carrying `operator_xonly_pk` — the identity that will later be credited as the payer: [1](#0-0) 

`Operator::withdraw` verifies the user's signature strictly with the `SinglePlusAnyoneCanPay` sighash type against `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)`: [2](#0-1) 

`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY` only commits the signer to input 0 and the output at the same index (output 0, the user payout). It leaves the anchor output and, critically, the `OP_RETURN` output (which encodes the crediting operator) completely unconstrained — any party can swap in a different `operator_xonly_pk` while reusing the same valid user witness, fund the transaction with their own inputs, and get it mined.

On the verifier side, this `OP_RETURN` value is trusted directly from the confirmed chain data as the payer of record, with no cross-check that the recorded operator actually supplied the funding inputs: [3](#0-2) 

This value is persisted as `payout_payer_operator_xonly_pk` and later used by the credited operator's own automation to decide whether *it* is the payer and should pursue reimbursement: [4](#0-3) 

and by verifiers to validate the kickoff as non-malicious: [5](#0-4) 

The binding that should hold is:

`operator credited (payout_payer_operator_xonly_pk from OP_RETURN) == operator that actually funded the payout (added the wallet inputs covering the payout output)`

Because the OP_RETURN is outside the signed message, this equality is not enforced by any signature or on-chain proof — it is simply whatever byte string the transaction's broadcaster chose to include.

### Impact Explanation
Any party (not necessarily a registered operator, and not requiring any private key belonging to the victim) who observes a pending/unconfirmed payout transaction for a withdrawal (e.g., in the mempool, or by independently constructing one from the same publicly-known `WithdrawParams`) can build a competing transaction that:
- reuses the exact same signed witness for input 0 (nothing to break, since the signature does not cover the parts being changed),
- keeps output 0 (the user payout) identical so the signature verifies,
- funds the transaction itself (this does cost the attacker real BTC — they must front the withdrawal amount),
- but sets the `OP_RETURN` output to an arbitrary/victim operator's `operator_xonly_pk`,
- and gets it mined ahead of the honest transaction (e.g. via a higher fee / RBF).

Once confirmed, `update_finalized_payouts` records the victim operator as `payout_payer_operator_xonly_pk`. The victim operator's own reimbursement automation (`validate_payer_is_operator` / `get_reimbursement_txs`) will treat this as "I am the payer" and pursue the full BitVM/kickoff reimbursement flow, ultimately receiving the bridge amount reimbursement for a payout it never funded — a direct instance of "an operator reimbursed for a payout it never funded," a Critical-severity impact per the bridge-custody bindings.

Note the direction of harm is unusual (it can benefit the credited operator "for free"), but it still constitutes a broken security invariant: the protocol's accounting of who paid for a withdrawal can be forged by any funded third party, undermining the entire economic model that ties reimbursement rights to whoever actually fronted a payout.

### Likelihood Explanation
Exploitability requires only: (1) knowledge of a pending withdrawal's public parameters (visible once a user has requested withdrawal / once any operator's payout tx enters the mempool), and (2) enough capital to front the payout amount and win a fee race. No cryptographic secrets, operator credentials, or N-of-N cooperation are needed to perform the swap itself — the sighash type used is explicitly documented in code as `SinglePlusAnyoneCanPay`, confirming the gap is intentional/known behavior of the signature scheme rather than an incidental bug, which is what makes it reachable in the deployed protocol rather than a theoretical edge case.

### Recommendation
Bind the crediting operator's identity into data that the user's (or an aggregator/verifier co-signed) signature actually commits to — e.g., commit to the `OP_RETURN` payload (or a hash of the full set of outputs) using `SIGHASH_ALL`/`SIGHASH_SINGLE` without `ANYONECANPAY` for that output, or otherwise require the crediting operator's own signature over the specific payout transaction (including its `OP_RETURN`) before it is accepted as proof of payment for reimbursement purposes. At minimum, verifiers/operators should not treat the plain `OP_RETURN` content as authoritative proof of payer identity without an accompanying operator signature that is bound to the exact transaction that was mined.

### Proof of Concept
1. User signs `WithdrawParams` (`in_signature`/`in_outpoint`/`out_script_pubkey`/`out_amount`) using `SinglePlusAnyoneCanPay`, as done in `sign_withdrawal_output`. [6](#0-5) 
2. Honest Operator A calls `withdraw()`, builds and broadcasts a payout tx crediting itself (`self.signer.xonly_public_key`) via `create_payout_txhandler`. [7](#0-6) 
3. Before A's tx confirms, an attacker constructs an alternate transaction reusing the same input-0 witness and output-0 payout, but with victim Operator B's `xonly_pk` in the `OP_RETURN`, funds it with attacker-controlled inputs at a higher fee, and gets it mined instead.
4. Verifier syncing records B as payer via `update_finalized_payouts`. [8](#0-7) 
5. B's automation, using `validate_payer_is_operator`, sees itself listed as payer and pursues the kickoff/reimbursement flow, ultimately receiving reimbursement it never funded. [9](#0-8)

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

            }

                return Err(eyre::eyre!(

                    kickoff_txid
                )
                .into());
            }
        };

            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,

fn sign_withdrawal_output(
    config: &BridgeConfig,
    dust_utxo: &UTXO,
    withdrawal_address: &bitcoin::Address,
    withdrawal_amount: bitcoin::Amount,
) -> (bitcoin::TxOut, taproot::Signature) {
    let signer = Actor::new(config.secret_key, config.protocol_paramset().network);
    let txin = builder::transaction::input::SpendableTxIn::new(
        dust_utxo.outpoint,
        dust_utxo.txout.clone(),
        vec![],
        None,
    );
    let txout = bitcoin::TxOut {
        value: withdrawal_amount,
        script_pubkey: withdrawal_address.script_pubkey(),
    };
    let unspent_txout = builder::transaction::output::UnspentTxOut::from_partial(txout.clone());

    let tx = builder::transaction::TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            builder::transaction::DEFAULT_SEQUENCE,
        )
        .add_output(unspent_txout.clone())
        .finalize();

    let sighash = tx
        .calculate_sighash_txin(0, sighash::TapSighashType::SinglePlusAnyoneCanPay)
        .expect("Failed to calculate sighash");

    let sig = signer
        .sign_with_tweak_data(sighash, builder::sighash::TapTweakData::KeyPath(None), None)
        .expect("Failed to sign");

    let sig = taproot::Signature {
        signature: sig,
        sighash_type: sighash::TapSighashType::SinglePlusAnyoneCanPay,
    };

    (txout, sig)
}
