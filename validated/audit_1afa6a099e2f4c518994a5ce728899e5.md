### Title
Change calculation fails to reserve fee for the OP_RETURN data output — change is overpaid and the transaction underpays its fee ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog of the farm bug — "withdrawable" value computed without reserving the amount that must stay behind — exists in `SignableTransaction::new`. The contract failed to subtract `total_shares` when paying out the pool token; here, the change output ("every leftover sat") is computed against a fee estimate whose weight calculation completely omits the OP_RETURN `data` output.

### Finding Description
In `SignableTransaction::new`, the `data` output is pushed onto `tx_outs` *before* the fee/weight is calculated, but `calculate_weight_vbytes` is invoked with `payments` only — the OP_RETURN output is never part of the weight model:

```rust
// networks/bitcoin/src/wallet/send.rs
tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }) // ~line 195
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None); // line 204
```

`calculate_weight_vbytes` (lines 62–127) builds the model transaction solely from `payments` and the optional `change`. The same omission repeats for the change path at lines 225–234: `fee_with_change = fee_per_vbyte * vbytes_with_change`, again excluding the (up-to-80-byte, plus output overhead) data output.

Consequently `change value = input_sat - payment_sat - fee_with_change` reserves a fee that is too small; the sats that should have paid for the data output are instead paid out to the change output — the exact same class as `owner_withdraw_token` transferring tokens without reserving `total_shares`. Additionally, the `TooLowFee` check (line 211) and the `MAX_STANDARD_TX_WEIGHT` check (line 241) run on the underestimated weight/vbytes, so a transaction that is actually below the minimum relay fee rate or above the standard weight limit can pass validation.

### Impact Explanation
- The signed transaction pays `fee_per_vbyte * vbytes_without_data`, i.e. an effective fee rate strictly below the caller-specified rate (by roughly `fee_per_vbyte * (11 + data_len)` sats, ~95 vbytes for 80 bytes of data).
- If `fee_per_vbyte` was at or near the minimum, the real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` despite the `TooLowFee` check passing; the transaction is rejected by the network, leaving the intended payments unsettled and requiring resigning — funds are temporarily unmovable.
- Change is inflated by the unpaid fee amount, so accounting that relies on `needed_fee()`/`fee()`-vs-outputs reasoning is skewed.
- The weight check may pass a transaction that exceeds `MAX_STANDARD_TX_WEIGHT` once the data output is included, producing a non-standard transaction that cannot be broadcast.

### Likelihood Explanation
`SignableTransaction::new` is a public API of `bitcoin-serai` gated on `data: Option<Vec<u8>>`; any caller that supplies data (the in-tree processor currently passes `None`, but the API and its tests exercise data paths) triggers the underpayment deterministically. The miscount grows with `data.len()` and is guaranteed whenever `data.is_some()`. Medium severity: no key/share leakage, but it produces transactions that silently underpay and may be unrelayable/non-standard.

### Recommendation
Include the OP_RETURN output in the weight model: pass `tx_outs` (or `payments` plus a synthesized zero-value `data` output) into `calculate_weight_vbytes` at lines 204 and 225, i.e. build the model from the actual output list rather than from `payments`. Equivalently, add `ScriptBuf::new_op_return(...)`'s serialized size to the computed weight before deriving `vbytes`, and re-run the `TooLowFee` and `MAX_STANDARD_TX_WEIGHT` checks against that corrected value.

### Proof of Concept
```rust
// Conceptual; against networks/bitcoin/src/wallet/send.rs
let data = vec![0u8; 80];
let tx_with = SignableTransaction::new(inputs.clone(), &payments, Some(change.clone()), Some(data.clone()), FEE).unwrap();
let tx_without = SignableTransaction::new(inputs, &payments, Some(change), None, FEE).unwrap();
// The data output adds ~95 vbytes but needed_fee is identical:
assert_eq!(tx_with.needed_fee(), tx_without.needed_fee());
// Effective rate of tx_with is FEE * vbytes_model / vbytes_actual < FEE.
// The change output of tx_with contains ~FEE*95 sats that should have been fee.
```
