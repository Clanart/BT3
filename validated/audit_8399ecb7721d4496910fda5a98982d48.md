### Title
Untrusted `ReceivedOutput` bytes can report outputs that are not spendable by the wallet - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, arbitrary `TxOut`, and arbitrary `OutPoint` without checking that the output’s `script_pubkey` is the address derived from the wallet key plus that offset. [1](#0-0)  This bypasses the invariant enforced by `Scanner`, which only creates a `ReceivedOutput` after finding the transaction output’s `script_pubkey` in its registered script-to-offset map. [2](#0-1) [3](#0-2) 

### Finding Description
`Scanner::register_offset` stores `p2tr_script_buf(self.key + GENERATOR * offset)` as the key in `self.scripts`, with the scalar offset as the value needed to spend it. [4](#0-3)  During scanning, `Scanner::scan_transaction` only constructs `ReceivedOutput` when `output.script_pubkey` exists in that map, thereby binding the serialized `offset`, `output`, and `outpoint` together. [3](#0-2) 

`ReceivedOutput::read` does not preserve that binding: it canonicalizes the scalar through `Secp256k1::read_F`, but then consensus-decodes whatever `TxOut` and `OutPoint` the byte stream contains. [1](#0-0)  There is no scanner key, registered-script lookup, or recomputation of the expected Taproot script during deserialization. [1](#0-0) 

### Impact Explanation
An attacker who can supply serialized `ReceivedOutput` bytes can make the wallet treat an output paying an unrelated Taproot key—or another non-wallet script—as a wallet-owned output. [1](#0-0)  The resulting object reports the attacker-selected amount through `ReceivedOutput::value`, while its offset need not correspond to the output’s script. [5](#0-4) 

This can cause funds to be reported as received even though the threshold wallet does not control the spending key, making the reported balance unspendable. [6](#0-5) [3](#0-2) 

### Likelihood Explanation
The issue is reachable wherever persisted, imported, synchronized, or otherwise attacker-controlled bytes are passed to `ReceivedOutput::read`. [1](#0-0)  Exploitation does not require a private key, malformed elliptic-curve encoding, or consensus-invalid Bitcoin data; the attacker only changes which valid `TxOut` and `OutPoint` are associated with the serialized offset. [1](#0-0) 

### Recommendation
Do not deserialize `ReceivedOutput` as an authoritative wallet-owned object without re-establishing the scanner invariant. [2](#0-1)  Change the deserialization API to require the relevant `Scanner` or wallet key, recompute `p2tr_script_buf(key + GENERATOR * offset)`, and reject bytes whose `TxOut.script_pubkey` differs from the expected script. [6](#0-5)  If the bytes cross a trust boundary before that check, additionally authenticate them with a wallet-local MAC or store only the chain-discovered `OutPoint` and reconstruct the `ReceivedOutput` by rescanning. [3](#0-2) 

### Proof of Concept
The following conceptual Rust constructs bytes that deserialize successfully while naming an output controlled by an unrelated Taproot key rather than the wallet key plus the serialized offset. [1](#0-0) 

```rust
use bitcoin::{
  consensus::encode::serialize,
  key::TweakedPublicKey,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use k256::Scalar;
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::ReceivedOutput;
use std::io::Write;

// Any canonical scalar is accepted as the spending offset.
let forged_offset = Scalar::ONE;

// This script is derived from a key unrelated to the wallet's Scanner key.
let unrelated_x_only_key = [0x02; 32];
let attacker_script = ScriptBuf::new_p2tr_tweaked(
  TweakedPublicKey::dangerous_assume_tweaked(unrelated_x_only_key.into()),
);

let claimed_output = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: attacker_script,
};

let claimed_outpoint = OutPoint::new(Txid::from_slice(&[0x11; 32]).unwrap(), 0);

let mut bytes = Vec::new();
bytes.write_all(&forged_offset.to_bytes()).unwrap();
bytes.extend(serialize(&claimed_output));
bytes.extend(serialize(&claimed_outpoint));

let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 100_000);
assert_eq!(received.offset(), forged_offset);
```

A scanner-generated output would only contain this script if `attacker_script == p2tr_script_buf(wallet_key + GENERATOR * forged_offset)`. [6](#0-5)  Because `ReceivedOutput::read` omits that comparison, deserialization accepts the mismatched association and creates a claimed spendable output whose script is actually controlled by the unrelated key. [1](#0-0)

  ///
  /// Due to Bitcoin's requirement that points are even, not every offset may be used.
  /// If an offset isn't usable, it will be incremented until it is. If this offset is already
  /// present, None is returned. Else, Some(offset) will be, with the used offset.
  ///
  /// This means offsets are surjective, not bijective, and the order offsets are registered in
  /// may determine the validity of future offsets.
  ///
  /// The offsets registered must be securely generated. Arbitrary offsets may introduce a script

  /// (not by the signature of the key).
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
