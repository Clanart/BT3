### Title
`PedPoPError::InvalidShare` blame proof leaks the ECDH shared decryption key via derived `Debug`/`Display`, unredacted - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Every other secret-bearing type in `crypto/dkg` and `crypto/dkg/pedpop` hand-implements `fmt::Debug` with `finish_non_exhaustive()` precisely so that secret material is redacted from logs and error reports (`SecretShare`, `ThresholdCore`, `SecretShareMachine`, `Encryption`, `BlameMachine`). `EncryptionKeyProof` is the sole exception: it derives `Debug`, so its `key` field — the ECDH shared point that decrypts an `EncryptedMessage<SecretShare>` — is printed in full. The proof travels inside `PedPoPError::InvalidShare { blame }`, which itself derives `Debug` and embeds `blame` in its `Display` string. Analogously to the Mattermost report (sensitive data retained in a structure that is emitted to viewers who should not see it), an attacker-controlled malformed share forces this error, and routine logging/`{:?}`/`{}` formatting of the returned error discloses the decryption key for the secret-share ciphertext.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`:

```rust
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub struct EncryptionKeyProof<C: Ciphersuite> {
  key: Zeroizing<C::G>,
  dleq: DLEqProof<C::G>,
}
``` [1](#0-0) 

`key` is produced by `Encryption::decrypt` as `ecdh::<C>(&self.enc_key, msg.key)` — the raw ECDH shared secret between the recipient's long-term encryption key and the sender's per-message key. It is exactly what `cipher()` consumes to derive the ChaCha20 key that decrypts `msg.msg` (the secret share) [2](#0-1) .

When `KeyMachine::calculate_share` rejects a share, it returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` [3](#0-2) . `PedPoPError` derives `Debug` and formats `blame` into the error message [4](#0-3) . `Zeroizing<C::G>` forwards `Debug` to the inner group element, so the shared secret point is rendered verbatim — unlike `SecretShare`, whose `Debug` impl deliberately emits nothing [5](#0-4) , and unlike `Encryption`/`BlameMachine`, which use `finish_non_exhaustive()` [6](#0-5) .

The intended distribution channel for `EncryptionKeyProof` is a blame publication broadcast to other participants for a specific accusation. The `Debug`/`Display` leak additionally pushes the key into local log files, error aggregators, RPC error responses, and `ProcessorMessage` paths — viewers who hold (or can later obtain) the ciphertext `EncryptedMessage` but were never meant to receive the decryption key.

### Impact Explanation
Anyone who observes the formatted error (logs, crash reports, monitoring, an echoed error string) and also sees the corresponding `EncryptedMessage` ciphertext — which is transmitted over the DKG channel and, per the blame protocol, republished — can run `cipher(context, proof.key)` and recover that participant's FROST secret share plaintext. Combined with `t` such disclosures, or a single disclosure of a victim's share to an attacker already holding `t-1` shares, the group key's secret share material is exposed. This is exactly the "unredacted sensitive field" bug class: data that is secret-by-design is emitted through a channel assumed to be safe because every sibling type redacts it.

### Likelihood Explanation
Triggering it requires only that an attacker, as a DKG participant, send a syntactically valid `EncryptedMessage` with a valid PoP but invalid share content (e.g., a non-canonical or commitment-inconsistent share). `calculate_share` then returns the error containing the blame proof; any downstream code that logs or propagates the error with `{:?}`/`{}` — the idiomatic way to handle `thiserror` errors — discloses the key. No broken cryptography, collusion, or privileged position is required.

### Recommendation
- Remove `Debug` (and `PartialEq`/`Eq` if unused) from `EncryptionKeyProof`, or hand-implement `fmt::Debug` using `finish_non_exhaustive()` like `SecretShare`, `Encryption`, `BlameMachine`, and `ThresholdCore` do.
- In `PedPoPError::InvalidShare`'s `#[error]` string, do not interpolate `blame`; print only `participant` and whether a blame proof exists.
- Consider encrypting/wrapping the blame payload at the protocol layer (as `CachedPreprocess` is XOR-encrypted in `coordinator/src/tributary/signing_protocol.rs` [7](#0-6) ) so the key is only materialized inside `AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// Participant 2 sends participant 1 an EncryptedMessage whose PoP verifies
// but whose plaintext is a non-canonical scalar (or commitment-inconsistent share).
// In participant 1's code:
let res = machine.calculate_share(&mut OsRng, shares); // shares[2] is malicious
// res = Err(PedPoPError::InvalidShare { participant: 2, blame: Some(proof) })
// Idiomatic handling:
eprintln!("DKG failed: {res:?}"); // or {}", res
// The output contains proof.key = enc_key_1 * msg.key_2 -> the ChaCha20 ECDH input.
// Anyone with the log line plus the wire ciphertext EncryptedMessage{key, pop, msg}:
//   cipher(context, proof.key).apply_keystream(msg.msg) -> SecretShare plaintext
```
This mirrors the existing `invalid_ecdh_blame`/`invalid_share_serialization_blame` tests in `crypto/dkg/pedpop/src/tests.rs` [8](#0-7) , which confirm that a single malformed message yields `PedPoPError::InvalidShare` carrying the live `EncryptionKeyProof` — here simply formatted rather than forwarded to a blame machine.
