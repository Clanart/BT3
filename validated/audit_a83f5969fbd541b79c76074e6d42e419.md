### Title
Unbounded per-proposal deposit iteration in gov `RefundDeposits`/`DeleteDeposits` allows attacker to stall `EndBlock` - (File: sei-cosmos/x/gov/keeper/deposit.go)

### Summary
The Cosmos SDK gov module vendored in this repo lets any account submit `MsgDeposit` for arbitrarily small amounts, and does not cap the number of distinct depositor addresses per proposal. When a proposal's deposit or voting period ends, `EndBlocker` calls `keeper.RefundDeposits` (or `keeper.DeleteDeposits` if deposits are burned) which iterates *every* deposit for that proposal in a single, unbudgeted pass, unlike the tally logic in the same `EndBlocker` which is explicitly rate-limited.

### Finding Description
`AddDeposit` accepts a deposit from any account with no minimum-per-call amount, keyed by `(proposalID, depositorAddr)` [1](#0-0) . An attacker controlling many addresses can therefore create an unbounded number of distinct dust deposits on a single proposal for negligible cost (just tx fees).

When the proposal later transitions out of the deposit/voting period, `EndBlocker` runs `RefundDeposits` or `DeleteDeposits` for that proposal id [2](#0-1) . Both functions call `IterateDeposits`, which walks every stored deposit key for the proposal and performs a bank send (or burn) per entry with no cap on the number of iterations [3](#0-2) [4](#0-3) .

Contrast this with the vote-tally path in the very same `EndBlocker`, which is explicitly budgeted via `MaxVotesProcessedPerBlock`/`remainingRecords` to avoid unbounded per-block work [5](#0-4) [6](#0-5) . The deposit refund/delete loops have no equivalent budget or pagination, so their cost scales linearly (each with its own `SendCoinsFromModuleToAccount`/`BurnCoins` call and KV write) with the number of depositor addresses an attacker chooses to create — this is directly analogous to the `BountyCore.getLockedFunds` unbounded loop over attacker-created deposits in the referenced report.

### Impact Explanation
Because `EndBlock` executes identically and synchronously on every validator, an attacker who cheaply floods a single proposal with thousands of dust deposits from many funded/associated addresses can inflate the work done by `RefundDeposits`/`DeleteDeposits` at the exact block where that proposal's deposit or voting period ends. This directly threatens block production time (risking the >2.5s block-delay threshold) and, in the worst case with a very large number of deposits, could consume enough gas/CPU/IO to stall or crash `EndBlock` processing across the validator set, since this code path runs outside of the ordinary per-tx gas metering that protects individual message execution.

### Likelihood Explanation
Submitting `MsgDeposit` is fully permissionless and requires no special privilege — only tx fees for many small transactions from distinct accounts, which is inexpensive relative to the amplified per-block cost imposed at proposal finalization. The attack window is deterministic (the attacker chooses when to stop depositing and knows the proposal's deposit/voting end time), making the trigger reliable and repeatable across many proposals.

### Recommendation
Bound per-block work in `RefundDeposits`/`DeleteDeposits` the same way `TallyIncremental` is bounded (process a fixed number of deposit entries per block and resume across blocks), or cap/aggregate the number of distinct depositor entries retained per proposal (e.g., enforce a minimum deposit amount per depositor or merge/limit entries), so that proposal finalization work can no longer be inflated by cheaply created dust deposits.

### Proof of Concept
1. Attacker controls/creates N funded accounts and submits `MsgDeposit` with a minimal `usei` amount from each account against a single proposal id, before its deposit or voting period ends — each call succeeds via `AddDeposit`, creating N separate `Deposit` records keyed by depositor address [7](#0-6) .
2. When the proposal's deposit period expires without meeting the minimum, or its voting period ends, `EndBlocker` invokes `DeleteDeposits`/`RefundDeposits` for that proposal id in the same block, unconditionally on all N stored deposits [8](#0-7) .
3. As N grows large, the single `EndBlock` call performs N bank operations and KV deletes with no rate limiting, unlike the tally path, increasing block processing time proportionally and risking missed block-time targets or resource exhaustion across all validators.

func (keeper Keeper) DeleteDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		err := keeper.bankKeeper.BurnCoins(ctx, types.ModuleName, deposit.Amount)
		if err != nil {
			panic(err)
		}

		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})

// AddDeposit adds or updates a deposit of a specific depositor on a specific proposal
// Activates voting period when appropriate
func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

	// Update proposal
	proposal.TotalDeposit = proposal.TotalDeposit.Add(depositAmount...)
	keeper.SetProposal(ctx, proposal)

	// Check if deposit has provided sufficient total funds to transition the proposal into the voting period
	activatedVotingPeriod := false

	if proposal.Status == types.StatusDepositPeriod && proposal.TotalDeposit.IsAllGTE(keeper.GetDepositParams(ctx).GetMinimumDeposit(proposal.IsExpedited)) {
		keeper.ActivateVotingPeriod(ctx, proposal)

		activatedVotingPeriod = true
	}

	// Add or update deposit object
	deposit, found := keeper.GetDeposit(ctx, proposalID, depositorAddr)

	if found {
		deposit.Amount = deposit.Amount.Add(depositAmount...)
	} else {
		deposit = types.NewDeposit(proposalID, depositorAddr, depositAmount)
	}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
