### Title
`SignableTransaction::new` omits the OP_RETURN data output from its weight/fee calculation, producing transactions with an insufficient fee and unchecked size - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to `_sendMessage` not checking that the supplied gas limit suffices for the actual work, `SignableTransaction::new` computes the transaction's weight, virtual size, required fee, and the `MAX_STANDARD_TX_WEIGHT` bound using only the payment outputs — after having already committed to appending an OP_RETURN `data` output (up to 80 bytes of caller-supplied data) to the transaction. The data output's weight is never charged for, so the resulting transaction pays less than the requested fee rate and can bypass the standardness weight check.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed to `tx_outs` at lines 194–202, before the fee calculation. The subsequent call `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) builds a mock transaction whose outputs are only `payments`; the data output is excluded. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is priced for a transaction smaller than the one actually built.
- The minimum-relay-fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) is evaluated against the understated `vbytes`, so a marginal `fee_per_vbyte` combined with a large `data` payload yields a real fee rate below the relay minimum.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) uses `weight` that excludes the data output (~90+ vbytes for a max-size payload), so an over-standard-weight transaction can be accepted.

The funded check `input_sat < payment_sat + needed_fee` (line 215) also uses the understated fee, so insufficient-input cases attributable to the data output are not caught.

### Impact Explanation
The produced `SignableTransaction` — which flows into `TransactionSignMachine::sign` where `Prevouts::All` sighashes commit to the actual outputs — represents a Bitcoin transaction whose effective fee rate is below the caller's requested `fee_per_vbyte` and potentially below the network minimum relay fee. Such a transaction will fail to relay/confirm, stalling spends, and in the boundary case a non-standard (overweight) transaction is constructed that nodes will reject outright. This is the same class as the source report: a resource bound (fee/size, the Bitcoin analog of gas) is not checked against the actual work to be performed.

### Likelihood Explanation
Reachable whenever `SignableTransaction::new` is invoked with `data: Some(..)` and `fee_per_vbyte` near the minimum, or with payments sized close to the weight limit. In the current processor integration `make_signable_transaction` passes `None` for data (`processor/src/networks/bitcoin.rs:446-452`), so in-protocol exploitation is limited to fee underestimation via the payment/change path; the public wallet API itself accepts arbitrary caller data, making this a latent Medium-severity correctness/DoS issue rather than directly attacker-triggered on-chain.

### Recommendation
Include the data output in the weight/vbytes estimate: either pass the fully-formed `tx_outs` (payments + OP_RETURN) into `calculate_weight_vbytes`, or add the OP_RETURN output's serialized weight to `weight`/`vbytes` before computing `needed_fee` and before both the `TooLowFee` and `TooLargeTransaction` checks. Re-check the minimum fee against the final weight (including any change output).

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Given inputs with input_sat >= payment_sat + needed_fee:

let data = vec![0u8; 80]; // max allowed by the TooMuchData check
let tx = SignableTransaction::new(inputs, &payments, None, Some(data), FEE).unwrap();

// The actual transaction contains payments + 1 OP_RETURN output:
assert_eq!(tx.transaction().output.len(), payments.len() + 1);

// But needed_fee was priced on `payments` only (line 204), so:
//   tx.fee() == needed_fee < FEE * tx.transaction().vsize()
// For a marginal FEE the realized rate falls below
// bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE, making the TX unrelayable,
// despite the TooLowFee check at line 211 passing.
```

Key lines: OP_RETURN push without weight accounting at `send.rs:194-202`; weight computed from `payments` only at `send.rs:204`; fee and bounds checks on the understated size at `send.rs:206-243`.
