### Title
Bank precompile `send` bypasses tokenfactory denom allow-list and blocked-recipient checks by calling `BankKeeper.SendCoins` directly instead of `MsgServer.Send` - ([File: precompiles/bank/legacy/v600/bank.go])

### Summary
In several legacy revisions of the `bank` precompile (`0x1001`), the `send` handler transfers coins by calling `p.bankKeeper.SendCoins(...)` directly. The tokenfactory denom allow-list check (`IsInDenomAllowList`) and the `BlockedAddr` check are enforced only inside `msgServer.Send`/`msgServer.MultiSend` in `sei-cosmos/x/bank/keeper/msg_server.go`, not inside `BaseSendKeeper.SendCoins` itself. Any caller that reaches `SendCoins` (or `SendCoinsWithoutAccCreation`) directly — bypassing the message server — skips those authorization checks entirely.

### Finding Description
`sei-cosmos/x/bank/keeper/msg_server.go` enforces the allow-list/blocked-address checks only at the message-handling layer: [1](#0-0) 

But the underlying `BaseSendKeeper.SendCoins` method that actually performs the transfer has no such check — it only debits/credits balances: [2](#0-1) 

The `bank` precompile's `send` function in multiple legacy versions (e.g. v552, v555, v562, v580, v600) calls `p.bankKeeper.SendCoins` directly rather than going through `bankMsgServer.Send`: [3](#0-2) 

This is structurally identical to the note-mark flaw: the "front door" (`msgServer.Send`, analogous to note-mark's `/api/books/{id}` DELETE-then-404 path) enforces the access-control predicate, while a second, still-reachable code path (`SendCoins`, analogous to the raw `Joins("JOIN books...")` query) reaches the same protected resource (denom transfer permission) without re-checking it. Later precompile revisions (v603+) were fixed by routing through `p.bankMsgServer.Send(...)`, which does perform the checks: [4](#0-3) 

This confirms the pattern was recognized and patched in some versions but the vulnerable versions remain reachable wherever those legacy precompile executors are still wired into the dispatcher for older EVM/chain upgrade heights.

### Impact Explanation
A tokenfactory denom owner can restrict transfers of their denom to an allow-list of addresses (`SetDenomAllowList`) or the bank module can block specific recipient addresses (`BlockedAddr`, e.g. module accounts). These are the chain's only enforcement points against unauthorized transfer of restricted tokenfactory denoms and against sending funds into blocked module accounts. An EVM contract or externally-owned account calling the vulnerable `bank` precompile's `send` (native ERC20 pointer transfer of a tokenfactory-created denom) bypasses both restrictions, allowing:
- Transfer of an allow-list-restricted tokenfactory denom to/from an address not on the allow list, defeating the issuer's access control.
- Sending coins to a blocked address (e.g., a module account), potentially corrupting module invariants or enabling fund lock/loss depending on the module's expectations.

This matches the "unauthorized transfer via precompile" impact category.

### Likelihood Explanation
Reachable directly by any EVM transaction that calls the bank precompile's `send` method through the associated ERC20 native pointer contract, when the chain is executing at a height mapped to one of the vulnerable legacy precompile versions (v552–v600). No special privilege is required beyond holding balance of the affected denom and knowing/controlling the ERC20 pointer contract address, which is discoverable on-chain.

### Recommendation
Ensure every legacy version of the `bank` precompile's `send` handler routes transfers through `bankMsgServer.Send` (as done in v603+) instead of calling `BankKeeper.SendCoins` directly, so the `IsInDenomAllowList` and `BlockedAddr` checks are always applied. Alternatively, move these checks into `BaseSendKeeper.SendCoins`/`SendCoinsWithoutAccCreation` itself so all callers (module keepers, precompiles, IBC transfer, wasm bindings) enforce them uniformly rather than relying on each caller to route through the message server.

### Proof of Concept
1. Create a tokenfactory denom and register an ERC20 native pointer for it via the `pointer` precompile.
2. As the denom admin, call `SetDenomAllowList` (via governance/tokenfactory keeper) restricting the denom to a specific address set.
3. Deploy/use a chain build where the active bank precompile implementation is one of the vulnerable legacy versions (v552–v600, i.e. before the v603 fix that routes through `bankMsgServer.Send`).
4. From an address not in the allow list, call the ERC20 pointer's `transfer`, which invokes the bank precompile's `send(fromAddress, toAddress, denom, amount)`.
5. Observe the transfer succeeds because `p.bankKeeper.SendCoins` is called directly, without the `IsInDenomAllowList`/`BlockedAddr` checks that `msgServer.Send` would have enforced — confirming bypass of the tokenfactory allow-list restriction reachable purely through a public EVM transaction.

Note: I was unable to fully verify from the index alone at which exact chain-upgrade heights each legacy precompile version (`v552`..`v600` vs `v603`+) is actually dispatched to in the current running binary; this depends on the `precompiles` version-selection/dispatch table, which I could not fully trace within the available search budget. A background Devin session with full repo access would be needed to confirm whether any currently-active (non-legacy-frozen) code path still calls `SendCoins` directly instead of `bankMsgServer.Send` for this precompile.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

	}

	return nil
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}
