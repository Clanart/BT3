### Title
Removing a bridge operator does not verify remaining operators still satisfy the configured vote thresholds - ([File: contracts/service_chain/bridge/BridgeOperator.sol])

### Summary
`BridgeOperator.sol` implements a multisig-style voting scheme for value-transfer and configuration requests, gated by `operatorThresholds[VoteType]`. `setOperatorThreshold()` correctly validates that a new threshold is achievable (`operatorList.length >= _threshold`), but `deregisterOperator()` removes an operator from `operatorList` without any equivalent check that the remaining `operatorList.length` is still `>=` the currently configured `operatorThresholds[ValueTransfer]` / `operatorThresholds[Configuration]`. This exactly mirrors the reported bug class: threshold-adjustment path is validated, but the "member removal" path is not.

### Finding Description
`setOperatorThreshold` enforces `operatorList.length >= _threshold` before accepting a new threshold value: [1](#0-0) 

However, `deregisterOperator` performs no analogous validation. It simply deletes the operator from the `operators` mapping and swap-removes it from `operatorList`, with no check that `operatorList.length` remains `>=` either `operatorThresholds[uint8(VoteType.ValueTransfer)]` or `operatorThresholds[uint8(VoteType.Configuration)]`: [2](#0-1) 

Voting quorum is checked in `_voteCommon`, which compares the vote count for a specific `(voteType, nonce, voteKey)` combination against `operatorThresholds[uint8(_voteType)]`: [3](#0-2) 

If the owner deregisters enough operators that `operatorList.length` falls below `operatorThresholds[VoteType.Configuration]`, then `_voteConfiguration` (used to reach quorum for `registerOperator`... actually `registerOperator`/`setOperatorThreshold`/`deregisterOperator` are direct `onlyOwner` calls, not gated by voting — but any *other* configuration action gated through `_voteConfiguration`, e.g. bridge fee/limit changes routed through configuration voting in the concrete `Bridge` contract, becomes permanently unreachable) can never reach quorum again, since no remaining path exists to lower the threshold or add new operators through the voting mechanism itself (those are `onlyOwner` gated, so the owner retains recovery capability via `registerOperator`/`setOperatorThreshold`, unlike the pure multisig case in the report). Still, the missing invariant is the same root-cause omission as the referenced report: **removal is not checked for consistency with the currently active threshold**, only threshold-adjustment is.

### Impact Explanation
If the contract owner deregisters operators such that `operatorList.length < operatorThresholds[VoteType.ValueTransfer]` or `< operatorThresholds[VoteType.Configuration]`, all subsequent configuration or value-transfer votes gated by `_voteCommon`/`_voteValueTransfer`/`_voteConfiguration` become permanently unable to reach quorum until the owner calls `registerOperator` (bounded by `MAX_OPERATOR`) or `setOperatorThreshold` to lower the threshold. This can stall value-transfer processing (bridging) or configuration changes on the affected `Bridge` contract, a denial-of-service on bridge operations reachable purely through normal owner administrative action (no attacker input required beyond the described missing invariant).

### Likelihood Explanation
This requires an owner (admin) action — deregistering operators without adjusting the threshold — which is a low-likelihood but plausible operational mistake given there is zero on-chain guardrail, unlike the threshold-setting path which is explicitly guarded. Given the codebase already recognizes and validates this exact invariant in `setOperatorThreshold`, the asymmetric omission in `deregisterOperator` indicates the check was simply forgotten there, consistent with the reported bug pattern.

### Recommendation
Add the same safety check used in `setOperatorThreshold` to `deregisterOperator`: after removing the operator, verify `operatorList.length >= operatorThresholds[uint8(VoteType.ValueTransfer)]` and `operatorList.length >= operatorThresholds[uint8(VoteType.Configuration)]` (or revert if any active threshold would become unreachable).

### Proof of Concept
1. Owner deploys `Bridge`/`BridgeOperator` with operators `[A, B, C]` and `operatorThresholds[Configuration] = 2`.
2. Owner calls `deregisterOperator(B)`, then `deregisterOperator(C)`, leaving `operatorList = [A]`.
3. `operatorThresholds[Configuration]` remains `2`, but only 1 operator (`A`) exists — `_voteConfiguration` can never reach quorum (`vote.voteCounts[_voteKey]` can be at most `1 < 2`), permanently blocking any configuration action normally routed through operator voting, with no code path to self-correct except an owner call to `setOperatorThreshold` or `registerOperator` (both of which the owner would need to remember to invoke, since `deregisterOperator` gives no warning or revert).     function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }

    // deregisterOperator deregisters the operator.
    //
    // Note that outstanding votes by the deregistered operator are not revoked.
    // This enables a subtle counterintuitive scenario.
    //
    // Suppose there are two operators A, B and C with threshold 2.
    // 1. Operator A votes on nonce N
    // 2. Owner deregisters A
    // 3. Operator B votes on nonce N, thereby executing the request N.
    // In this case the request was executed with A's vote after A is deregistered.
    //
    // The Owner shall recognize this issue and expect that operator deregistration
    // takes some time to be fully effective.
    function deregisterOperator(address _operator)
    external
    onlyOwner
    {
        require(operators[_operator]);
        delete operators[_operator];

        for (uint i = 0; i < operatorList.length; i++) {
           if (operatorList[i] == _operator) {
               operatorList[i] = operatorList[operatorList.length-1];
               operatorList.length--;
               break;
           }
        }
        emit OperatorDeregistered(_operator);
    }
