## Analysis

The report's underlying bug class is: **an "address/ownership" field gets silently reassigned in local state based on an external signal, without any check that the change is safe or consented to, breaking the invariant that the stored address matches what the system actually operates on.**

The closest GitHub Desktop analog is the automatic git-remote URL rewrite performed by `updateRemoteUrl()`, which is triggered as a side effect of ordinary repository operations and silently repoints the user's local git remote based on data returned by the GitHub API for the matched repository — with no user confirmation.

### Title
Attacker-controlled GitHub repository metadata silently rewrites the local git remote URL, redirecting future pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` compares the local `origin` remote URL to the `clone_url` reported by the GitHub API for the repository Desktop believes is associated with the working copy, and — if the protocol matches and the remote "looks unchanged" from what was last recorded — calls `gitStore.setRemoteURL()` to overwrite the local remote, with no user prompt or diff shown. [1](#0-0) 

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the repository object from the GitHub API for the account/owner/name matched against the local remote, and if a `GitHubRepository` association already exists, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`. [2](#0-1) 

Inside `updateRemoteUrl`, the only checks performed are: (1) the URL protocol (ssh vs https) hasn't changed, and (2) the local remote's URL still matches the previously-cached `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited it). If both hold, and the *new* `clone_url` differs, the function directly rewrites the git remote — no verification that the new owner/repository is the same trust domain the user originally intended to push to. [3](#0-2) 

This is invoked via `withRefreshedGitHubRepository()`, which runs during normal, unprivileged operations such as reverting a commit, whenever Desktop doesn't yet have a resolved account association for the repository. [4](#0-3) 

The invariant that breaks is the same shape as the seed report: an authoritative address (`_salesAddress` in the contract; the git remote URL in Desktop) is mutated in one place (`setRemoteURL`) based on an externally supplied value, while the code never confirms this reassignment is consistent with what the user actually intended to trust — it just accepts whatever `clone_url` the GitHub API currently reports for that owner/name pair. Since a repository owner fully controls their own repository's metadata (including renaming the repo or changing its owner via GitHub's transfer feature), the `apiRepo.clone_url` value is an attacker-controlled "GitHub API object" per the accepted impact class.

### Impact Explanation
If a user has cloned/added a repository owned by a malicious or later-compromised account, that owner can rename the repository or transfer it to a different account/name. The next time Desktop performs almost any git operation that runs through `withRefreshedGitHubRepository` (e.g., revert commit, or other flows that call `repositoryWithRefreshedGitHubRepository`), Desktop will silently rewrite the user's `origin` remote to point at the new `clone_url` — with no confirmation dialog, diff, or notice to the user. Subsequent pushes/fetches then transparently target a destination the user never explicitly approved. This matches the "silent corruption of what the user commits or pushes" impact category directly.

### Likelihood Explanation
No local access, malware, or leaked credentials are required — only that the user has previously associated the repository with a GitHub account/owner they interacted with, and that the attacker (the repository's rightful GitHub-side owner) performs a rename/ownership change, which is a completely ordinary GitHub action fully within their control. The rewrite path only requires the protocol to remain the same and the user to not have manually customized the remote — both are the common case for the vast majority of Desktop users who never touch remote settings.

### Recommendation
Do not perform automatic, silent remote URL rewrites based on API-reported `clone_url` changes. At minimum:
- Require explicit user confirmation before changing the remote URL when the owner or hostname portion changes (a rename within the same owner is lower risk than an ownership/organization change).
- Surface a visible notification/dialog showing old vs. new remote URL before applying `setRemoteURL`.
- Consider treating an owner change as untrusted by default and require re-verifying account/permissions before updating.

### Proof of Concept
1. Attacker creates a public GitHub repository `attacker/foo` and gets a victim to add/clone it in GitHub Desktop as `origin`.
2. Victim performs normal actions in Desktop (e.g., revert a commit) that invoke `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`. [5](#0-4) 
3. Attacker transfers/renames the repository (e.g., to `attacker2/foo-renamed`), which changes the `clone_url` returned by the GitHub API for that repo object.
4. On the victim's next qualifying operation, `updateRemoteUrl` detects `protocolsMatch && remoteUrlUnchanged && !urlsMatch` and calls `gitStore.setRemoteURL(...)`, silently repointing `origin` to `attacker2/foo-renamed` with no prompt. [6](#0-5) 
5. The victim's future pushes now silently go to the new (potentially fully attacker-controlled) destination.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

  private async withRefreshedGitHubRepository<T>(
    repository: Repository,
    fn: (repository: Repository) => Promise<T>
  ): Promise<T> {
    let updatedRepository = repository
    const account: Account | null = getAccountForRepository(
      this.accounts,
      updatedRepository
    )

    // If we don't have a user association, it might be because we haven't yet
    // tried to associate the repository with a GitHub repository, or that
    // association is out of date. So try again before we bail on providing an
    // authenticating user.
    if (!account) {
      updatedRepository = await this.repositoryWithRefreshedGitHubRepository(
        repository
      )
    }

    return fn(updatedRepository)
  }
