## Title
Unbounded recursion in AccountKeyRoleBased RLP decoding leads to stack-overflow node crash — ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its role slots through `rlp.DecodeBytes` into a fresh `AccountKeySerializer`, which in turn dispatches back into `AccountKeyRoleBased.DecodeRLP` if the encoded sub-key's type is again `AccountKeyTypeRoleBased`. There is no recursion-depth limit anywhere in this decode chain, so a crafted, deeply-nested `AccountKeyRoleBased` byte blob causes the Go call stack to grow without bound during decoding — the same class of bug as CVE-2018-9256 (Wireshark LWAPP dissector: unbounded recursive decapsulation depth causing a crash), just manifesting in RLP/AccountKey decoding instead of a network-protocol dissector.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes its `enc [][]byte` and then, for every byte-slice element, calls `rlp.DecodeBytes(b, &serializer)` on a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and then decodes directly into the concrete key object via `s.Decode(serializer.key)`: [2](#0-1) 

If `serializer.key` is itself an `AccountKeyRoleBased`, `s.Decode` invokes `AccountKeyRoleBased.DecodeRLP` again — recursively, with no bound on nesting depth. The only place that rejects nested composite keys (`kerrors.ErrNestedCompositeType`) is `CheckInstallable`/`CheckUpdatable`, which runs *after* the entire structure has already been fully decoded: [3](#0-2) [4](#0-3) 

Because each nesting level only costs a small constant number of encoded bytes (an outer `[][]byte` wrapper plus a 1-byte type tag), an attacker can encode extremely deep nesting (tens of thousands of levels) in a payload of a few hundred KB or less, well within normal transaction/RPC-payload size limits. There is no depth counter analogous to `params.CallCreateDepth`/`StackLimit` used for EVM call depth, and the RLP `Stream` only tracks byte-size limits per list (`willRead`/`listLimit`), not recursion depth: [5](#0-4) 

### Impact Explanation
This decode path is reachable through:
1. The public RPC method `KaiaAPI.DecodeAccountKey`, which takes arbitrary attacker-supplied hex bytes and calls `rlp.DecodeBytes` directly with no authentication or privilege required: [6](#0-5) 
2. Any `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate` (and variants) transaction submitted through normal transaction ingestion (`Transaction.DecodeRLP` → `tx_internal_data_serializer` → `AccountCommon.DecodeRLP` → `AccountKeySerializer.DecodeRLP`), i.e. before pool admission validation runs: [7](#0-6) [8](#0-7) 

A single crafted transaction or RPC call can exhaust the goroutine stack and crash the node process handling the RPC request or transaction pool insertion. Since transaction decoding also happens uniformly on every node validating blocks/pool entries, this can be used to crash multiple/all nodes in the network with one malicious payload — a straightforward unauthenticated denial-of-service.

### Likelihood Explanation
Any unprivileged public RPC caller or transaction sender can trigger this: `DecodeAccountKey` requires no authentication and takes raw bytes; `AccountUpdate` transactions are ordinary, permissionless transaction types. Constructing a deeply nested `AccountKeyRoleBased` payload is trivial and cheap in terms of encoded size (linear growth per nesting level), making exploitation practical and low-cost.

### Recommendation
Add an explicit recursion/nesting-depth counter to `AccountKeyRoleBased.DecodeRLP` (and more generally to `AccountKeySerializer.DecodeRLP`), rejecting decode attempts once nesting exceeds a small fixed bound (e.g., 1, since nested composite keys are never valid per `CheckInstallable`/`CheckUpdatable`). Enforce this check during decoding itself, not only in post-decode validation, mirroring how Wireshark's fix in `packet-lwapp.c` capped encapsulation levels before continuing to dissect.

### Proof of Concept
1. Build a minimal `AccountKeyPublic` (or `AccountKeyFail`) leaf key and RLP-encode it via `AccountKeySerializer`.
2. Wrap it in an `AccountKeyRoleBased` containing that single serialized key, RLP-encode via `AccountKeyRoleBased.EncodeRLP`, producing `enc0`.
3. Repeat step 2 thousands of times, each time wrapping the previous `AccountKeySerializer`-encoded blob as the sole element of a new `AccountKeyRoleBased`, producing `enc1, enc2, ..., encN` (N in the tens of thousands).
4. Submit the final `encN` bytes hex-encoded to the public RPC method `kaia_decodeAccountKey` (`KaiaAPI.DecodeAccountKey`), or embed it as the `Key` field of a raw `TxTypeAccountUpdate` transaction and submit via `eth_sendRawTransaction`/pool insertion.
5. Observe the node process crash with a stack-overflow/fatal error during `rlp.DecodeBytes` recursive descent through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` ... .

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// willRead is called before any read from the underlying stream. It checks
// n against size limits, and updates the limits if n doesn't overflow them.
func (s *Stream) willRead(n uint64) error {
	s.kind = -1 // rearm Kind

	if inList, limit := s.listLimit(); inList {
		if n > limit {
			return ErrElemTooLarge
		}
		s.stack[len(s.stack)-1] = limit - n
	}
	if s.limited {
		if n > s.remaining {
			return ErrValueTooLarge
		}
		s.remaining -= n
	}
	return nil
}
