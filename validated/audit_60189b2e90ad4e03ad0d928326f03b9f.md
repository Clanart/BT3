## Analysis

The Sudorandom report's core defect pattern is: **a value coming from untrusted/attacker-controlled input is validated (or extracted) using logic that silently omits a case it was supposed to guard against**, and that mis-validated value is then trusted downstream as if it were safe, causing security-relevant misbehavior.

The closest analog I can confirm in the GitHub Desktop code with concrete citations is in the deep-link (`x-github-client://` / `x-github-desktop-auth://`) URL handler for the `openrepo` action.

### Title
Deep-link `branch` parameter validation fails to reject leading `-`/`--` characters, enabling git argument injection - (File: `app/src/lib/sanitize-ref-name.ts`)

### Summary
`app/src/lib/parse-app-url.ts` parses attacker-controlled deep-link URLs (`x-github-client://openRepo/...?branch=...`) and validates the `branch` query parameter using `testForInvalidChars()` before trusting it as a git ref name. That validator's regex does not exclude a leading hyphen, unlike the sibling sanitizer `sanitizedRefName()` in the same file, which does strip leading `-`/`+` characters. This inconsistency mirrors the report's root cause: two related pieces of logic (`token()` reading position 81 vs. the correct 93; here, `testForInvalidChars` vs. `sanitizedRefName`) disagree about which bytes/characters are "safe," and the code path that is actually exercised uses the incomplete one.

### Finding Description
`parseAppURL` in [1](#0-0)  extracts `branch` from a remote-attacker-controlled deep-link URL and only rejects it when `testForInvalidChars(branch)` returns true.

`testForInvalidChars` is defined in [2](#0-1)  and only flags control characters, space, and the set `~^:?*[\|"<>`, the `@{` sequence, consecutive dots, leading/trailing dot, `.lock` suffix, or trailing `/`. It does **not** flag a leading `-`. The companion function `sanitizedRefName` in the same file explicitly strips leading `-`/`+` (`.replace(/^[-\+]*/g, '')`), showing the author was aware leading dashes are a hazard for ref names used as CLI arguments — but that stripping logic is not applied on the validation path used by `parseAppURL`.

The validated-but-not-sanitized `branch` string is then passed through `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` in [3](#0-2)  as `branchName`, ultimately reaching a `checkoutLocalBranch` call that shells out to `git checkout <branchName>`-style invocations.

### Impact Explanation
Because `testForInvalidChars` allows values beginning with `-`/`--`, an attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?branch=<flag>` link can inject a git command-line option instead of a plain branch name into the `git checkout` invocation performed by Desktop. Depending on the specific git subcommand implementation reached (not fully confirmed — see below), this class of bug historically enables option/argument injection against git (e.g., forcing use of alternate config, hooks, or pack transport options), which can lead to code execution or working-tree corruption using a completely unprivileged action (clicking a link).

### Likelihood Explanation
The `branch` query parameter is 100% attacker-controlled via a deep link, requires only that the victim click a link (no local access, no malware, no leaked credentials), and passes the app's only stated validation gate (`testForInvalidChars`) because that gate does not consider leading hyphens invalid — mirroring exactly the "checked but with an off-by-something / incomplete check" bug class described in the report. I was not able to fully trace the exact `git` argument array built by `checkoutLocalBranch`/`checkout.ts` in the final iterations, so I cannot confirm whether that specific git invocation uses a `--` separator (as `app/src/lib/git/clone.ts` correctly does for `url` at [4](#0-3) ) which would neutralize the injection. This is the one open verification gap.

### Recommendation
Make `testForInvalidChars` reject (or have `parseAppURL` additionally reject) any `branch` value starting with `-`, consistent with `sanitizedRefName`'s existing stripping behavior, and/or ensure every git invocation that consumes a deep-link-sourced ref name places a `--` separator before it, the same protection already applied to `url` in `app/src/lib/git/clone.ts`.

### Proof of Concept
1. Attacker publishes/sends a link: `x-github-client://openRepo/https://github.com/owner/repo?branch=--upload-pack=/tmp/evil`
2. Victim (with GitHub Desktop's protocol handler registered, see [5](#0-4) ) clicks the link.
3. `parseAppURL` accepts the value because `testForInvalidChars('--upload-pack=/tmp/evil')` returns `false` (no space, no control chars, none of `~^:?*[\|"<>`) — see [6](#0-5) .
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)` is invoked with the poisoned `branch` string — [7](#0-6) .
5. If the downstream git invocation does not isolate the ref argument with `--` (unverified in this session), git would interpret the value as a flag rather than a ref name.

Given the unresolved verification of step 5's exact command construction, this should be treated as a **high-confidence but not fully proven** finding — I recommend a Devin session inspect `app/src/lib/git/checkout.ts` and the `checkoutLocalBranch` implementation directly to confirm whether `--` argument separation is present before concluding severity.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
