## Title
`SignInStore` singleton state causes a race between concurrent `promptForGitHubSignIn` flows, letting a later (attacker-triggered) credential-helper request hijack the account resolved by an earlier legitimate sign-in - (File: `app/src/lib/trampoline/trampoline-ui-helper.ts`)

### Summary
`promptForGitHubSignIn` does not scope its sign-in flow to a specific request. It relies on the singleton `SignInStore`, whose `state.resultCallback` is unconditionally overwritten every time `beginDotComSignIn`/`beginEnterpriseSignIn` is called again while a flow is in progress. This lets a second, attacker-triggered credential-helper sign-in "steal" the account produced by a user's already-in-progress legitimate sign-in.

### Finding Description
`promptForGitHubSignIn` creates a `cb` closure and registers it as the `resultCallback` with the global `SignInStore` via `dispatcher.beginDotComSignIn(cb)` / `beginEnterpriseSignIn(cb)`: [1](#0-0) 

`SignInStore` keeps a single `state` object holding one `resultCallback`. If `beginDotComSignIn`/`beginEnterpriseSignIn` is invoked while `this.state !== null` (i.e., a sign-in is already in progress), it calls `this.reset()`, which resolves the *previous* callback with `{kind:'cancelled'}`, and then installs the *new* caller's `resultCallback` as `this.state.resultCallback`: [2](#0-1) [3](#0-2) 

When authentication ultimately succeeds, `emitAuthenticate` resolves `this.state.resultCallback` — whichever callback happens to be currently installed — with the successful account: [4](#0-3) 

Separately, `PopupManager.addPopup` silently refuses to add a second popup of `PopupType.SignIn` if one is already open (it just logs a warning and returns without changing the stack), so the visible dialog is not replaced: [5](#0-4) 

Combining these two facts: if a legitimate `promptForGitHubSignIn(endpointA)` is in-flight (dialog visible, `cbA` registered as `resultCallback`), and `promptForGitHubSignIn(endpointB)` is triggered from `getCredential` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (reachable whenever the trampoline `git credential get` invocation targets a GitHub host with no cached account — a path git triggers automatically for any GitHub-looking remote/host encountered during clone/fetch/push, including ones supplied by repository config or a malicious remote URL): [6](#0-5) 

then:
1. `beginDotComSignIn(cbB)` / `beginEnterpriseSignIn(cbB)` resets the in-flight state, causing `cbA` to fire with `{kind:'cancelled'}` (so promise A resolves to `undefined`) — but the dialog itself is unaffected, because the second `showPopup({type: PopupType.SignIn, ...})` call is swallowed by `addPopup`'s de-duplication.
2. `SignInStore.state.resultCallback` is now `cbB`.
3. The user, unaware anything changed, completes the visible sign-in flow (browser OAuth / credentials) for what they believe is their original request.
4. `emitAuthenticate` fires `cbB(...)`, so promise B (the attacker/second caller's promise, i.e., the second `promptForGitHubSignIn` awaited by `getCredential`) resolves with the user's real `Account`, and `cbB` calls `this.dispatcher.closePopup(PopupType.SignIn)`.

The net effect: the account the user authenticated for their intended git operation is instead handed back to whichever credential-helper request most recently called `promptForGitHubSignIn`, and the credentials get attached (`credWithAccount`) to that second request's response.

### Impact Explanation
An unprivileged, attacker-influenced git host (or a second git operation racing the trampoline credential helper) that triggers a `get` credential request for a GitHub-classified host can obtain the resolved `Account`/token from a legitimate sign-in the user is performing concurrently for a different endpoint, because `SignInStore`'s single global `resultCallback` and `PopupManager`'s de-duplication of `PopupType.SignIn` are not scoped per-request. This risks the user's GitHub token being handed to credential-fill for an unintended host/endpoint (`getCredential` -> `credWithAccount`), which is a form of unauthorized credential exfiltration/misdirection tied to `endpointB` rather than `endpointA`.

### Likelihood Explanation
Triggering `getCredential`'s sign-in prompt path requires git itself to invoke the credential helper for a host classified as GitHub/enterprise with no stored account — this occurs naturally during clone/fetch/push against attacker-supplied remotes/hosts. However, actually winning the race requires that the attacker's request occurs *while the legitimate sign-in dialog is open and before the user finishes it*, and requires the user to keep interacting with the (now-repurposed) dialog without noticing. This is a race-condition-dependent, non-trivial-to-time scenario, and I was not able to verify from the code alone whether the credential-helper path can be triggered fully unattended/automatically enough for realistic exploitation timing (e.g., whether a background fetch can be forced to race a user-initiated sign-in without other trust boundaries such as `getIsBackgroundTaskEnvironment` blocking prompts in automated contexts) [7](#0-6) .

### Recommendation
Scope each `promptForGitHubSignIn`/sign-in flow to its own request instead of relying on a shared singleton `resultCallback`: e.g., track request identity (a token/id) in `SignInStore` state and ignore/reject stale `resultCallback`s from superseded requests, or refuse to start a new sign-in flow (rather than silently reset+overwrite) while a credential-helper-initiated flow is in progress, surfacing this to the user instead. Additionally, consider making `PopupManager` explicit that a second `PopupType.SignIn` request was dropped so `trampoline-ui-helper.ts` can react (e.g., queue or reject) instead of assuming the popup shown is always associated with the request's own callback.

### Proof of Concept
1. User action A: `git fetch` against `https://github.com` triggers `trampoline-credential-helper.ts`'s `getCredential`, which calls `ui.promptForGitHubSignIn('https://github.com/...')`; `cbA` is registered via `beginDotComSignIn(cbA)` and the `SignIn` popup opens.
2. Before the user finishes step 1, a second, attacker-influenced git operation (e.g., an automatically-triggered fetch of a submodule/remote pointing to `https://attacker-controlled-ghe.example`, classified as an enterprise GitHub host per `getEndpointKind`) invokes `getCredential` again, calling `ui.promptForGitHubSignIn('https://attacker-controlled-ghe.example/...')`.
3. This calls `beginEnterpriseSignIn(cbB)`, which internally calls `reset()` (resolving `cbA` with `cancelled`) then sets `resultCallback = cbB`; the corresponding `showPopup` call is dropped silently by `PopupManager.addPopup` because a `SignIn` popup already exists.
4. The user, seeing the unchanged dialog, completes authentication as originally intended for `github.com`.
5. `SignInStore.emitAuthenticate` invokes `cbB`, resolving the *second* (attacker-triggered) `promptForGitHubSignIn` promise with the user's account, which flows into `credWithAccount` for the attacker-controlled endpoint's credential response — while the legitimate first request (`cbA`) already resolved to `undefined`.

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public reset() {
    const currentState = this.state
    this.state?.resultCallback({ kind: 'cancelled' })
    this.setState(null)

    if (currentState?.kind === SignInStep.Authentication) {
      currentState.oauthState?.onAuthError(new Error('cancelled'))
    }
  }

  /**
   * Initiate a sign in flow for github.com. This will put the store
   * in the Authentication step ready to receive user credentials.
   */
  public beginDotComSignIn(resultCallback?: (result: SignInResult) => void) {
    const endpoint = getDotComAPIEndpoint()

    if (this.state !== null) {
      this.reset()
    }

    const existingAccount = this.accounts.find(isDotComAccount)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: resultCallback ?? noop,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: resultCallback ?? noop,
      })
    }
  }

  public addPopup(popupToAdd: Popup): Popup {
    if (popupToAdd.type === PopupType.Error) {
      return this.addErrorPopup(popupToAdd.error)
    }

    const existingPopup = this.getPopupsOfType(popupToAdd.type)

    const popup = { id: ++this.popupCounter, ...popupToAdd }

    if (existingPopup.length > 0) {
      log.warn(
        `Attempted to add a popup of already existing type - ${popupToAdd.type}.`
      )
      return popupToAdd
    }

    this.insertBeforeErrorPopups(popup)
    this.checkStackLength()
    return popup
  }
