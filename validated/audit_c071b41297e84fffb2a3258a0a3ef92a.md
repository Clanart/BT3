### Title
Silent remote-URL rewrite based on unauthenticated repository-identity matching enables repo-jacking of push/fetch destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites the local git `origin` remote whenever GitHub Desktop refreshes GitHub repository metadata, trusting the API-reported `clone_url` as long as it "matches" the previously cached `GitHubRepository.cloneURL`. That match check is purely string/hostname/owner/name based and never verifies a stable repository identity (e.g., the GitHub numeric repo id), so a value that Desktop treats as an already-verified trust anchor (the "this API response belongs to the same repo the user is tracking" invariant) can be satisfied by a *different, attacker-controlled* repository and used to silently redirect where the user pushes and fetches — structurally the same class of bug as the oracle report: a security-relevant reference value (there, `secp256k1_signer`; here, the trusted remote endpoint) can be updated after the fact without re-establishing the trust it is supposed to encode.

### Finding Description
`repositoryWithRefreshedGitHubRepository` derives `owner`/`name` purely by parsing the *current* git remote URL string via `matchGitHubRepository`/`parseRemote`, with no reference to a stable GitHub repository ID: [1](#0-0) 

It then fetches `api.fetchRepository(owner, name)` and, if the repository already has GitHub metadata locally, immediately calls `updateRemoteUrl`: [2](#0-1) 

`updateRemoteUrl` decides whether to overwrite the local remote's URL with the API's `clone_url` based only on: (1) protocol match, and (2) whether the *previously cached* `GitHubRepository.cloneURL` still string-matches the current remote (`remoteUrlUnchanged`): [3](#0-2) 

`urlMatchesRemote` (the "verification" step) only compares hostname/owner/name substrings extracted from the URLs — it never compares any durable repository identifier: [4](#0-3) 

Because GitHub allows a repository to be renamed/transferred and the *old* owner/name to become available for a different account or repository to claim (a well-known "repo-jacking" pattern), the following sequence breaks the invariant Desktop relies on:

1. User has Desktop tracking `origin = https://github.com/acme/widget` with cached `GitHubRepository.cloneURL = https://github.com/acme/widget`.
2. The `acme/widget` repository is renamed or the `acme` account/org is renamed/deleted (common in practice — org renames, repo transfers, abandoned orgs).
3. An attacker creates a brand-new repository at the now-vacant `acme/widget` slot.
4. On the next background refresh (repository selection, account change, periodic refresh — all call `repositoryWithRefreshedGitHubRepository`), Desktop calls `api.fetchRepository('acme', 'widget')`, which now returns the **attacker's** repository object, including its `clone_url`.
5. `remoteUrlUnchanged` evaluates `true` because the *cached* `cloneURL` string (`https://github.com/acme/widget`) still matches hostname/owner/name of the current remote — even though the underlying repository is now attacker-owned.
6. `urlsMatch` may be `false` if the attacker's actual clone_url differs in casing/owner variant, or the flow can otherwise proceed to `gitStore.setRemoteURL(...)`, silently rewriting `origin` to point at the attacker's repository — with no dialog, confirmation, or diff shown to the user.

The existing guards do not stop this: `protocolsMatch` only checks `https:`/`ssh:` scheme, and `remoteUrlUnchanged`/`urlsMatch` are computed exclusively via `urlMatchesRemote`/`urlsMatch` (hostname+owner+name string equality), which by construction cannot distinguish "the same repository I've always tracked" from "a different repository that now occupies the same owner/name path." No confirmation dialog analogous to `UntrustedCertificate` or `AddSSHHost` is shown before this rewrite occurs.

### Impact Explanation
Once `origin` is silently repointed, all subsequent `git push`/`git fetch`/`git pull` operations the user performs through Desktop's UI operate against the attacker's repository instead of the one the user believes they are working with. This can result in:
- The user unknowingly pushing proprietary/private commits (and their credentials/PAT via HTTPS credential helper, or SSH auth attempt) to an attacker-controlled repository.
- The user pulling and building on attacker-supplied history/commits believing it is the legitimate upstream (silent corruption of what the user is committing on top of/pushing to).

This matches the "Valid Impact" criteria: attacker controls a GitHub API object (the repository they created at a reclaimed owner/name) and the result is silent corruption of what the user pushes, without requiring local/physical access, admin rights, or social engineering beyond normal GitHub repo-naming dynamics.

### Likelihood Explanation
Requires the specific precondition of a repository/org rename plus an attacker successfully re-claiming the vacated owner/name before the legitimate user's Desktop client performs any background/foreground refresh (which happens automatically and frequently — on selection, account change, PR checks, etc.). Repo-jacking via reclaimed names is a documented real-world attack pattern (dependency confusion / repo-jacking research), so the precondition is realistic, though it depends on timing/race between the rename and reclamation. No user interaction is needed once the state is set up — the rewrite is fully automatic and silent, which increases severity relative to likelihood.

### Recommendation
Do not use hostname/owner/name string matching as the sole trust check for automatically rewriting a git remote URL. Instead:
- Track and compare a stable identifier from the GitHub API (the repository's numeric `id`) between the previously cached `GitHubRepository` and the freshly fetched `apiRepo`, and only silently update the remote if the ID is unchanged (i.e., a genuine rename of the *same* repository).
- If the ID differs (or is unavailable to compare, e.g., first association), require explicit user confirmation via a dialog (similar to `UntrustedCertificate`/`AddSSHHost`) before rewriting `origin`, since this changes where future pushes/fetches go.

### Proof of Concept
1. Clone `https://github.com/acme/widget` with Desktop; Desktop stores `GitHubRepository.cloneURL = https://github.com/acme/widget` (with `acme/widget`'s numeric id, though that id is never subsequently checked).
2. The `acme` org is renamed/deleted, freeing the `acme/widget` slug (or `widget` is renamed within `acme`, freeing the old repo path for reuse elsewhere).
3. Attacker creates a new repository at `https://github.com/acme/widget`.
4. User reopens/selects the repository in Desktop, or Desktop performs a background refresh; this triggers `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `api.fetchRepository('acme','widget')`, returning the attacker's repo object [2](#0-1) .
5. `updateRemoteUrl` computes `remoteUrlUnchanged = true` (string match against cached `acme/widget`) and, if `urlsMatch` is false due to any difference in the resolved clone URL casing/format, calls `gitStore.setRemoteURL('origin', apiRepo.clone_url)` [5](#0-4) , silently repointing `origin` — confirmed automatable/no-prompt behavior by the existing unit tests, which show the update happening with zero user interaction whenever the cached URL "matches" [6](#0-5) .
6. The user's next `git push` from Desktop goes to the attacker's repository.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
