### Title
`CachedPreprocesses` context omits the signed message (`key_pair`) and `removed` set, enabling FROST nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
In `SigningProtocol::preprocess_internal`, the coordinator derives the FROST preprocess deterministically from a seed cached under `CachedPreprocesses[context]`, where `context` is only `(b"DkgConfirmer", attempt)`. The cache key does not incorporate the participant/removal set nor the message to be signed (`set_keys_message(set, removed, key_pair)`). Analogous to the reported bug — where `startSqrtPriceX96` was user-controlled yet excluded from the battle identifier — here attacker/protocol-influenced values (`key_pair`, `removed`) are excluded from the signing-context identifier, so the same nonce seed can be reused across two distinct signing sessions under one identifier. Because `seeded_preprocess` regenerates identical nonces from the cached seed, two calls to `share`/`complete` within the same `attempt` that differ in `key_pair` (or in the preprocess map after `threshold_i_map_to_keys_and_musig_i_map` re-maps participants by `removed`) produce two Schnorr signature shares over the same nonces for different challenges — classic nonce reuse that leaks the validator's secret key.

### Finding Description
`DkgConfirmer::signing_protocol` builds `context = (b"DkgConfirmer", self.attempt)` only [1](#0-0) . `preprocess_internal` stores the XOR-encrypted `ChaCha20Rng` seed under that context and regenerates identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` on every invocation [2](#0-1) . Nonces are fully determined by the seed (`Commitments::new` from `ChaCha20Rng::from_seed`) [3](#0-2) . However, `share_internal` signs `set_keys_message(set, removed, key_pair)`, where `key_pair` and the `preprocesses` map are supplied per call [4](#0-3) , and `removed` is itself not part of the context (it is folded into the MuSig participant mapping and the message). The file's own safety argument relies on the nonces being "context-bound" [5](#0-4) , yet the context fails to bind the values that actually vary per signing session.

### Impact Explanation
If `share` or `complete` is executed twice under the same `attempt` with a different `key_pair` (a different DKG result being confirmed) or a different effective preprocess set (e.g., `removed` changing the `musig_i` re-mapping), the coordinator emits a second signature share `s = d + b·ρ + λ·c·share` using identical nonces `d, e` but a different binding factor `ρ` and challenge `c`. An observer of the two shares and the published preprocess/signature data can solve for and recover the validator's Ristretto secret key — the same key that roots validator trust and MuSig-aggregates DKG confirmations. The code itself acknowledges that preprocess reuse "will enable third-party recovery of your private key share" [6](#0-5) .

### Likelihood Explanation
Triggering requires two `share`/`complete` executions under one `attempt` with divergent `key_pair`/`removed`/preprocess inputs. The design assumes BFT-ordered messages make these inputs unique per attempt, but `key_pair` originates from the DKG confirmation flow (data included in tributary transactions, not hardcoded in the context), and `removed` is re-derived per call from `removed_as_of_dkg_attempt`; any path — re-executed DKG attempt with different removals, a rebuilt coordinator re-confirming a different key pair, or a duplicate submission — reuses the nonce. The mitigations listed (BFT ordering, full-rebuild re-decision) are protocol assumptions, not enforced by the identifier itself, matching the report's pattern of an unbound parameter enabling griefing/key compromise.

### Recommendation
Include all session-varying inputs in the cache identifier: extend `context` to `(label, attempt, Hash(spec.set()), Hash(removed), Hash(key_pair))` — or store the signed message alongside the seed and assert equality — and/or bind the participant set actually passed to `musig(...)`. Concretely, make the `CachedPreprocesses` key a hash of everything that enters `preprocess_internal`/`share_internal` (`participants`, `removed`, `msg`), so any change forces a fresh seed instead of nonce reuse.

### Proof of Concept
1. Within `DkgConfirmer` attempt `A`, call `share(preprocesses, key_pair_1)`: `preprocess_internal` writes `CachedPreprocesses[("DkgConfirmer", A)]`, decrypts the seed, regenerates nonces `d, e` and signs `m1 = set_keys_message(set, removed, key_pair_1)` producing share `s1`.
2. In the same attempt (after a DKG re-run or a rebuilt coordinator confirming a different result), call `share(preprocesses', key_pair_2)` with `key_pair_2 != key_pair_1` or a `removed` set that changes `threshold_i_map_to_keys_and_musig_i_map`'s participant mapping. `CachedPreprocesses::get` hits, yielding the identical seed → identical `d, e` and identical published commitments.
3. `machine.sign(preprocesses', m2)` computes a new binding factor `ρ2` and challenge `c2` (both derive from `msg`/commitments in `sign.rs` line 315+), emitting `s2 = d + b·ρ2 + λ·c2·share` while `s1 = d + b·ρ1 + λ·c1·share`. With `s1, s2`, the known commitments, `ρ1, ρ2, c1, c2`, the observer solves for `d + b·ρi` and then the secret share `share = (s1 - s2 + b·(ρ1 - ρ2)) / (λ·(c1 - c2))`-style elimination — recovering the validator's private key from two shares the coordinator legitimately published.

  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be

  3) Sign and publish the signature share.

  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
