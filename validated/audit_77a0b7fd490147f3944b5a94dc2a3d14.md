### Title
Copilot conflict resolution writes stale, splice-reassembled content over a conflicted file that was concurrently edited on disk - ([File: app/src/lib/stores/app-store.ts])

### Summary
`_applyCopilotConflictResolutions` writes AI-generated `resolvedContent` to disk, but that content was reassembled from a snapshot of the file (`rawContent`) captured minutes earlier, before the (multi-second to 120+ second) Copilot round trip. The only guard against staleness checks whether the file is now *fully* resolved (no conflict markers left); it does not detect the case where the file is still conflicted but its content has changed since the snapshot was taken. In that case the stale Copilot resolution is written and staged, silently discarding the user's intervening edits — the same class of bug as the report: a decision computed from a "reference" state (`spotTimeWeightedPrice` / here, `rawContent`) is applied after the real state has diverged, with no re-validation before the write/commit.

### Finding Description
`buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:367-469`) reads each conflicted file from disk once, at the start of resolution, and stores the full byte-for-byte snapshot in `rawContent`: [1](#0-0) 

That snapshot is used later — only after the Copilot round trip completes (per-file/per-chunk resolution can take 15s, 30s, 60s, even 120+s, per the timing buckets tracked in `app-store.ts`) — to splice the model's per-hunk resolutions back into the original text via `reassembleResolutions` / `reassembleResolvedFile`: [2](#0-1) 

When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes this reassembled content straight to disk and stages it: [3](#0-2) 

The only staleness check present is: [4](#0-3) 

This check only fires when the file has become fully resolved externally (i.e. `hasUnresolvedConflicts` is false, meaning no conflict markers remain at all). It does nothing to detect the far more likely case: the file is *still* marked conflicted (still has `<<<<<<<`/`>>>>>>>` markers) but its content changed — e.g. the user opened the file in their editor while the (multi-second) Copilot analysis/result dialog was open and edited code inside or around the conflict markers, or an external tool/format-on-save touched the file, or the user manually adjusted one hunk but left others unresolved. In all of these cases the status check passes (`isConflictedFileStatus` is true and `hasUnresolvedConflicts` is true), so the code proceeds to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` using content that was spliced against the *old* `rawContent`, discarding whatever the user actually had on disk at write time.

This mirrors the report's broken invariant exactly: a value (`spotTimeWeightedPrice` / here `rawContent`-derived `resolvedContent`) is computed from state captured before an operation with latency (the swap / the Copilot round trip), and is then applied without re-validating against the state that actually exists when the action executes (the swap-adjusted spot price / the on-disk file at write time).

### Impact Explanation
This causes silent corruption of what the user is about to commit: their manual edits to a conflicted file (potentially resolving parts of the conflict, adding safety fixes, or reverting an incorrect part of the AI's suggestion) can be silently overwritten by stale AI-generated content and then staged and committed as part of the merge/rebase/cherry-pick continuation. Because the file is still shown as "conflicted" in status, the user has no reason to suspect their edits were discarded, and the corrupted result is what gets pushed. This falls squarely within the accepted impact category: "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Medium. It requires the user to edit a conflicted file in an external tool while the Copilot resolution dialog is open and before clicking "Continue Merge" — a workflow the app itself anticipates and partially guards against (the comment at `app-store.ts:7241` acknowledges exactly this scenario), but the guard only covers the "fully resolved" sub-case. Given that Copilot resolution can run for up to two minutes (per the `copilotConflictResolutionOver120sCount` stat) and the UI explicitly allows navigating away and returning during that window, a user editing files in their IDE in the interim is a realistic and expected interaction, not a contrived one.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the file's current on-disk content and compare it against the `rawContent` snapshot that was used to build the resolution (or re-derive/re-verify the hunk boundaries against current content). If the file content differs from what the resolution was based on, treat it the same as the "externally resolved" case and skip the AI write, prompting the user to reconcile manually rather than silently overwriting. Alternatively, hash/store the snapshot content alongside each resolution and refuse to apply it if the current file content doesn't match the snapshot exactly.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick that produces a conflicted file, open the "Resolve with Copilot" flow.
2. While Copilot is resolving (or after resolutions are shown in the result dialog but before clicking "Continue Merge"), open the still-conflicted file in an external editor and modify content inside one of the conflict hunks (leave the conflict markers for at least one other hunk/file intact so `hasUnresolvedConflicts` remains true) and save.
3. Click "Continue Merge" in the Copilot dialog.
4. Observe: `_applyCopilotConflictResolutions` passes the "still conflicted" check (since markers remain), calls `writeFile` with the stale `resolvedContent` computed from the pre-edit `rawContent`, and stages it — the user's manual edit is silently discarded from the resulting commit.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
