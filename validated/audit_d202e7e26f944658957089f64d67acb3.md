## Analysis

The KYC report's broken invariant is: **file type is trusted/allowed based on a weak or absent check, letting an attacker-controlled file reach a dangerous sink (rendering/processing) unchecked.**

The closest analog in GitHub Desktop is the **"Open with Default Program" file-extension gate**, which is a narrow platform-specific blocklist rather than a real content/type validation, and is a no-op entirely on macOS/Linux.

### Title
Weak extension blocklist lets attacker-controlled repository files be opened via OS handler ("Open with Default Program") - (File: app/src/ui/lib/context-menu.ts)

### Summary
When a user right-clicks a file in the Changes list, History, or Pull Request "Files changed" view and chooses "Open with Default Program," Desktop gates that action with `isSafeFileExtension()`. [1](#0-0)  On Windows this only blocks four extensions (`.cmd`, `.exe`, `.bat`, `.sh`); on macOS/Linux it unconditionally returns `true`, i.e. no validation at all. [2](#0-1) [1](#0-0)  The action itself calls `openFile()`, which passes the path straight to `shell.openExternal('file://' + fullPath)`, letting the OS decide how to handle it. [3](#0-2) 

### Finding Description
This gate is wired into every "open file from a repository" context menu:
- Changes list: `onOpenItem` builds the full path from `repository.path` + attacker-controlled `file.path` and calls `openFile`. [4](#0-3) 
- Commit history: same pattern, gated by `isSafeExtension`. [5](#0-4) 
- Pull request "Files changed" view: same pattern. [6](#0-5) 
- Filtered changes list (default and rebase context menus): same pattern. [7](#0-6) [8](#0-7) 

The broken invariant: `isSafeFileExtension` is treated everywhere as "this file is safe to hand to the OS default-application handler," but:
1. On macOS/Linux it is a complete no-op (`return true` unconditionally), so *any* file committed/fetched into the working tree by a malicious remote/collaborator — `.command`, `.app`(as file), `.desktop`, `.jar`, `.sh`-renamed-without-extension, `.workflow`, AppleScript-based launchers, etc. — is considered "safe."
2. On Windows the blocklist (`.cmd`, `.exe`, `.bat`, `.sh`) omits many natively-executable or auto-run extensions that Windows Explorer/Shell will execute or auto-launch on open, e.g. `.scr`, `.msi`, `.msc`, `.js`/`.jse`/`.vbs`/`.vbe`, `.ps1`, `.hta`, `.wsf`, `.pif`, `.com`, `.lnk`, `.jar` (if a JRE association exists), `.reg`. Any of these bypass the check and reach `shell.openExternal('file://...')`.

Since the file path and extension originate entirely from the cloned/fetched repository's working directory contents (untracked files, files from a checked-out branch, or files shown in a PR diff a user is reviewing), an attacker who controls repository content (a malicious PR author, or push to a branch the victim later checks out) fully controls what gets executed once a normal Desktop user right-clicks → "Open with Default Program" on that file — a completely ordinary, expected user action for reviewing changes, not a contrived one.

This is distinct from the deliberately-`UNSAFE_openDirectory`/`openPath` helpers that document "never use with non-validated paths" — those are internally constrained to app-known-safe paths. [9](#0-8)  The `isSafeFileExtension` gate, by contrast, is the *only* check standing between an attacker-supplied repo file and OS execution, and it is a weak/absent blocklist rather than a real validation.

### Impact Explanation
A successful exploitation results in code execution on the victim's machine outside the sandboxed renderer, driven entirely by content the attacker placed in a git repository (fetched, cloned, or shown in a PR diff) — matching the "attacker controls a cloned/fetched repository ... result is code execution" impact category. No admin rights, local access, or pre-existing malware are required; the only requirement is a normal user action (right-click → Open with Default Program) that Desktop actively offers and enables for the malicious file.

### Likelihood Explanation
Likelihood is moderate-to-high: reviewing a PR's changed files or browsing commit history and opening a file with the default program is a common workflow Desktop explicitly supports via the "Files changed" and "Changes"/"History" views. The macOS/Linux bypass requires no special extension at all (`isSafeFileExtension` always returns `true`), and the Windows blocklist is trivially bypassed with any extension not in the 4-item list.

### Recommendation
Replace the extension **blocklist** with an **allowlist** approach (only enable "Open with Default Program" for extensions known to be safe non-executable content — images, text, docs, etc.), and apply the same allowlist check on macOS and Linux instead of unconditionally returning `true` in `isSafeFileExtension()` (`app/src/ui/lib/context-menu.ts`). Additionally, consider checking the actual file type/executable bit (e.g., via `is-application-bundle.ts`-style metadata inspection, already used for `showFolderContents`) rather than relying solely on the file extension string, since extensions can be spoofed relative to actual content type.

### Proof of Concept
1. Attacker opens a pull request against a repository the victim uses in Desktop, adding a new file `payload.desktop` (Linux) or `payload.scr`/`payload.jar`/`payload.ps1` (Windows) with content that executes attacker code when opened by the OS default handler, or on macOS adds `payload.command` (any extension, since the check is a no-op there).
2. Victim opens the PR in Desktop ("Files changed" tab) or checks out the branch, then right-clicks the file and selects "Open with Default Program" — the menu item is enabled because `isSafeFileExtension(extension)` returns `true` for these extensions/platforms. [10](#0-9) [1](#0-0) 
3. Desktop calls `openFile(fullPath, dispatcher)` → `shell.openExternal('file://' + fullPath)`, causing the OS to execute/launch the attacker-controlled file. [11](#0-10)

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
