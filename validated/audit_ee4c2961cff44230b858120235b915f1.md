Audit Report

## Title
Unauthenticated RPC-pubsub WebSocket connections have no handshake/idle read timeout, enabling remote resource exhaustion - (File: rpc/src/rpc_pubsub_service.rs)

## Summary
`listen()` in `rpc/src/rpc_pubsub_service.rs` accepts every incoming TCP connection unconditionally and spawns a `handle_connection` task per connection, tracked only by a metrics-only `TokenCounter` with no enforced cap. `handle_connection` awaits the WebSocket handshake (`server.receive_request()`) and the main-loop idle read (`receiver.receive_data()`) with no `tokio::time::timeout` anywhere, allowing an unauthenticated client to hold connections open indefinitely and exhaust server resources (tasks, sockets, buffers).

## Finding Description
`listen()` calls `listener.accept()` in a loop and, for every accepted connection, clones the necessary state and spawns `tokio::spawn(handle_connection(...))`, incrementing a `TokenCounter` token that only emits a metric datapoint and enforces no limit. Inside `handle_connection`, the WebSocket handshake step `server.receive_request().await?` has no timeout wrapper, so a client that opens a TCP connection and never completes the handshake stalls the task forever. After a successful handshake, the main loop's `select!` awaits `receiver.receive_data(&mut data)` alongside the broadcast channel and shutdown `tripwire`; neither of the latter two fires due to client inactivity, so a client that goes silent after the handshake also holds the task open indefinitely. `PubSubConfig` (fields: `enable_block_subscription`, `enable_vote_subscription`, `max_active_subscriptions`, `queue_capacity_items`, `queue_capacity_bytes`, `worker_threads`, `notification_threads`) has no field bounding concurrent connections or idle time, unlike the QUIC/TPU path (`streamer/src/nonblocking/quic.rs`), which enforces connection-attempt timeouts, per-IP rate limiting, and a global concurrency cap via `ClientConnectionTracker`, or `net-utils/src/ip_echo_server.rs`, which enforces `MAX_CONCURRENT_CONNECTIONS`, one connection per IP, and an `IO_TIMEOUT` deadline on reads/writes. No such guard exists on the pubsub path.

## Impact Explanation
This is a non-RPC-request, non-privileged remote resource exhaustion vector reachable by any client able to reach the pubsub WebSocket port. Because there is no global or per-IP connection cap and no handshake/idle timeout, an attacker can open a large number of raw TCP connections and either stall the handshake or complete it once and go silent, causing the validator's pubsub runtime (`pubsub_config.worker_threads`) to accumulate unbounded tokio tasks, sockets, and `DashMap`/broadcast-receiver state, degrading or exhausting the RPC pubsub service. This matches the "non-RPC remote exhaustion/crash" / "single-client low-rate RPC crash/degradation" target scope.

## Likelihood Explanation
High for any validator/RPC node that exposes the pubsub WebSocket endpoint publicly. The exploit requires only opening TCP sockets (optionally without completing the WebSocket handshake, or completing it once and sending nothing further) — no valid subscription, authentication, or protocol payload is needed, and it is trivially scriptable at scale from one or a few source IPs.

## Recommendation
Wrap the WebSocket handshake (`server.receive_request()` / `server.send_response()`) in a `tokio::time::timeout`; add an idle-read timeout branch to the `select!` loop in `handle_connection` that closes the connection if no client frame arrives within a bounded window; and enforce a maximum number of concurrent pubsub connections (globally and per source IP) analogous to the protections in `streamer/src/nonblocking/quic.rs` (`ClientConnectionTracker`, rate limiters) and `net-utils/src/ip_echo_server.rs` (`MAX_CONCURRENT_CONNECTIONS`, `IO_TIMEOUT`).

## Proof of Concept
1. Start a validator/RPC node with the pubsub service enabled (`PubSubService::new` → `listen()` in `rpc/src/rpc_pubsub_service.rs`).
2. From an unprivileged client, open N raw TCP connections to the pubsub port without completing the WebSocket handshake (e.g. via raw sockets or `nc`), or complete the handshake once and then send no further frames.
3. Because the handshake await at `rpc_pubsub_service.rs:356` and the idle read await at `rpc_pubsub_service.rs:384-398` have no timeout, and `listen()` (`rpc_pubsub_service.rs:448-467`) spawns one unbounded task per accepted connection, each connection persists indefinitely, consuming a tokio task, socket, and buffer.
4. Repeating this at scale accumulates unbounded resource usage in the pubsub runtime, degrading or exhausting the validator's RPC pubsub service over time.
