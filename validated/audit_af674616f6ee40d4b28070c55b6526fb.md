### Title
DataLayer mirror coins let any unprivileged spender force a victim node to fetch attacker-chosen URLs (SSRF-style disallowed-host connection) - (File: chia/data_layer/data_layer_wallet.py, chia/data_layer/download_data.py)

### Summary
Chia's DataLayer mirror mechanism records candidate download URLs for a store as unauthenticated coin memos on a shared, generic puzzle (`create_mirror_puzzle()` / `MIRROR_PUZZLE_HASH`), not as data cryptographically bound to the store owner. Any wallet holder can create a mirror coin that "advertises" arbitrary URLs for *any* `launcher_id`, and any DataLayer node that syncs that store will treat those URLs as legitimate mirror servers and issue outbound HTTP requests to them. This mirrors the reported bug class (Appsmith Elasticsearch plugin connecting to attacker-chosen/disallowed hosts, e.g. cloud metadata endpoints) — here the "disallowed host" is reachable by any coin-spending user via the mirror-coin mechanism rather than a plugin connection string.

### Finding Description
`create_new_mirror()` builds a mirror coin by sending XCH to `create_mirror_puzzle().get_tree_hash()` with `memos=[[launcher_id, *urls]]`: [1](#0-0) 

`create_mirror_puzzle()` curries `P2_PARENT` with a fixed program (`Program.to(1)`), so it is the same puzzle hash for every mirror regardless of which store id it claims to be for: [2](#0-1) 

The `launcher_id` and URL list are only carried as `CREATE_COIN` memos, parsed by `get_mirror_info()` without any signature/ownership check tying them to the actual DataLayer singleton owner: [3](#0-2) 

Consequently, `dl_get_mirrors` / `DLGetMirrors` RPC returns these attacker-supplied URLs for a given store id to any node that asks, without any ownership validation of the launcher_id being claimed: [4](#0-3) 

`DataLayer.update_subscriptions_from_wallet()` pulls exactly these mirror URLs from wallet RPC and stores them as subscription servers for the store, with no host allow/deny-list filtering: [5](#0-4) 

During the periodic sync loop, `fetch_and_validate()` picks a server from that (attacker-poisoned) list and downloads from it via `insert_from_delta_file()` → `download_file()` → `http_download()`, all of which perform outbound HTTP(S) requests to the raw stored URL with no host restriction: [6](#0-5) [7](#0-6) 

The `add_mirror`/RPC surface that creates these coins is reachable by any local wallet RPC caller with normal spend capability: [8](#0-7) [9](#0-8) 

Because the mirror puzzle/memo scheme is not bound to actual DataLayer singleton ownership, an attacker can:
1. Spend a small amount of XCH to create a mirror coin memo-tagging any victim's public `launcher_id` (store id) with a URL such as `http://169.254.169.254/latest/meta-data/...` (AWS metadata) or an internal service address.
2. Wait for the coin to confirm on-chain.
3. Any node — including the victim's own DataLayer node, if it subscribes to or owns that store — will pick up this URL via `update_subscriptions_from_wallet()`/`dl_get_mirrors`, and its DataLayer sync loop will issue outbound HTTP requests to that host when trying to download delta/full files for the store.

### Impact Explanation
This allows a low-cost, unprivileged on-chain actor to force other Chia nodes' DataLayer subsystems to make outbound network requests to attacker-chosen hosts, including internal-only addresses (cloud metadata services, internal management interfaces, etc.), from the context of the victim node's process. This is a server-side request forgery primitive reachable purely by placing a mirror coin on-chain — no direct interaction with the victim, no privileged access, and no control over the victim's mempool/consensus behavior required. Because `download_file`/`http_download` perform real network I/O to attacker-supplied URLs with the node's own network context, this could be leveraged to probe/exfiltrate cloud-instance credentials or internal services depending on deployment environment. It does not directly cause consensus divergence or coin theft, keeping severity at Medium, matching the referenced advisory's Medium rating for the same bug class (disallowed-host connections to internal metadata endpoints).

### Likelihood Explanation
Likelihood is meaningfully high for any deployment where DataLayer nodes run inside cloud environments with metadata endpoints reachable from the node's network namespace, and where the node subscribes to or tracks stores whose mirror lists are populated by third parties. Creating the malicious mirror coin requires only a normal wallet spend (no special privilege), and the mirror-to-URL binding is trusted by the sync path without host validation. The main constraint is that the target node must actually be tracking/subscribed to the poisoned `launcher_id` (or auto-track it), which is a normal DataLayer usage pattern (subscribing to public stores).

### Recommendation
- Bind mirror URL claims cryptographically to genuine ownership of the corresponding DataLayer singleton (e.g., require the mirror coin's memo/launcher_id to be verified against the actual singleton owner, or require mirror creation to originate from a spend that proves control of the launcher coin) rather than trusting unauthenticated `CREATE_COIN` memos.
- Add host/IP allow-list or deny-list filtering (e.g., reject link-local/metadata ranges such as `169.254.169.254`, RFC1918 private ranges, and other non-routable addresses) before issuing outbound requests in `http_download()` and plugin `download_file()`/`get_uploaders()` calls.
- Consider requiring explicit user confirmation or an allow-list mechanism (`--url` opt-in) for any URLs discovered via on-chain mirror coins rather than auto-subscribing based on `update_subscriptions_from_wallet()`.

### Proof of Concept
1. Attacker runs a standard wallet RPC call: `dl_new_mirror` (or CLI `chia data add_mirror`) targeting the victim's public `launcher_id` (store id) with `urls=["http://169.254.169.254/latest/meta-data/iam/security-credentials/"]` and a small `amount`/`fee`. [9](#0-8) 
2. Once the transaction confirms, the mirror coin's memos are decoded by `get_mirror_info()` and surfaced through `dl_get_mirrors`. [3](#0-2) 
3. Any node that owns/subscribes to that store id periodically calls `update_subscriptions_from_wallet()`, adding the attacker URL to its subscription server list. [5](#0-4) 
4. On the next sync cycle, `fetch_and_validate()`/`insert_from_delta_file()`/`download_file()` issues an HTTP GET to the attacker-controlled/internal URL from the victim node's process/network context. [6](#0-5) [10](#0-9) 

Note: I could not fully trace whether any additional filtering exists elsewhere in the DataLayer server/plugin code beyond what was inspected (e.g., in `s3_plugin_service.py`), and did not verify runtime deployment specifics (e.g., whether typical mainnet deployments run inside cloud environments with reachable metadata endpoints) — these would need confirmation via a full Devin session with broader file access.

def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True

    log.info(f"Using downloader {downloader} for store {store_id.hex()}.")
    request_json = {
        "url": server_info.url,
        "client_folder": str(client_foldername),
        "filename": filename,
        "group_files_by_store": group_downloaded_files_by_store,
        "max_delta_file_size": max_delta_file_size,
    }
    try:
        async with aiohttp.ClientSession() as session:
            async with session.post(
                downloader.url + "/download",
                json=request_json,
                headers=downloader.headers,
                timeout=timeout,
            ) as response:
                res_json = await response.json()
                assert isinstance(res_json["downloaded"], bool)
                return res_json["downloaded"]
    except (asyncio.TimeoutError, aiohttp.ClientError) as e:
        log.error(f"download_file could not get response from plugin {downloader}: {type(e).__name__}: {e}")
        return False

```
