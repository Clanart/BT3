### Title
Instantaneous, non-time-weighted bonus reward accounting in `BaseRewardPool` allows sandwiching `queueNewRewards`/`donateRewards` to steal yield from real stakers - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool` distributes bonus reward tokens (WOM/other bonus tokens harvested by `WombatStaking`) into `rewardPerTokenStored` **instantly and in full** the moment `queueNewRewards`/`donateRewards` is called, based only on the pool's `totalStaked()` at that exact block. There is no per-second/streamed vesting of the injected amount (unlike `MultiRewarderPerSec`, which correctly streams via `tokenPerSec`). Any unprivileged wallet can `deposit()` a large stake into `MasterMagpie` immediately before a reward injection lands and `withdraw()` immediately after, capturing a share of the newly injected reward proportional to capital size rather than staking duration — exactly the "distribution not based on duration of ownership" flaw described in the referenced report.

### Finding Description
`_provisionReward` credits the entire incoming reward amount to `rewardPerTokenStored` in one shot: [1](#0-0) 

`rewardPerToken()` simply returns this stored (non-time-weighted) accumulator: [2](#0-1) 

A user's earned amount is `balanceOf(account) * (rewardPerToken - userRewardPerTokenPaid) / 10**decimals + userRewards`: [3](#0-2) 

`userRewardPerTokenPaid` is only reset on `_updateFor`, which runs on every `deposit`/`withdraw`/`harvest` via `MasterMagpie`: [4](#0-3) 

In `MasterMagpie`, deposits and withdrawals both call `_harvestBaseRewarder` and update `user.rewardDebt`/`userRewardPerTokenPaid` in the same transaction, with no lock-up, cooldown, or minimum holding period: [5](#0-4) 

Because `_provisionReward` uses `this.totalStaked()` at the moment of injection (which already includes whatever the attacker deposited seconds earlier), and because a staker's accrued share is computed purely from `balanceOf * Δ(rewardPerToken)` with no time weighting whatsoever, a wallet can:
1. Watch the mempool for the periodic `queueNewRewards` call that forwards harvested WOM/bonus rewards from `WombatStaking` into a given `BaseRewardPool`.
2. Front-run it with a large `deposit()` into `MasterMagpie` for that pool's staking token.
3. Let the `queueNewRewards`/`donateRewards` transaction land, which mints the attacker's proportional share of `rewardPerTokenStored` based on their now-inflated share of `totalStaked()`.
4. Immediately `withdraw()` (or `getReward`) to realize the bonus reward and exit the position.

This differs from `MultiRewarderPerSec` in the codebase, which deliberately streams rewards over elapsed time (`timeElapsed * tokenPerSec`) precisely to prevent this kind of instantaneous capture: [6](#0-5) 

`BaseRewardPool` has no equivalent streaming/vesting mechanism for its bonus rewards.

### Impact Explanation
Every legitimate long-term staker who has been accruing a share of `rewardPerToken` since the last reward injection is diluted: the attacker's flash-deposited capital immediately captures a slice of that batch of rewards proportional to size, not time-at-risk or time-staked, permanently transferring yield that should have gone to genuine stakers to the attacker. This is a direct theft of unclaimed/pooled yield from real depositors, repeatable every time a reward injection occurs (each WOM harvest cycle from `WombatStaking`), and scales with the size of capital the attacker can temporarily commit (e.g., via a large but unlevered stake, or in principle intra-block with enough capital).

### Likelihood Explanation
The attack requires no privileged role and no oracle manipulation — only an unprivileged wallet, an ordinary ERC20 balance to stake, and observation of (or attempted front-running of) the `queueNewRewards`/`donateRewards` call, both of which are routine, periodic, expected operations of the protocol (harvesting real WOM yield into `BaseRewardPool`s). `donateRewards` is even fully permissionless, meaning a reward injection event is not gated behind any unpredictable admin action; it will recur regularly per the normal reward-harvesting cadence of `WombatStaking`. Any staking pool with meaningful bonus-reward volume and no minimum holding period is exposed. The complexity is lower than the original UDT/Uniswap-oracle report because no price-oracle manipulation is needed at all — this is a pure reward-accounting timing exploit.

### Recommendation
Stream bonus rewards over time (as already done in `MultiRewarderPerSec` via `tokenPerSec`/`lastRewardTimestamp`) rather than crediting the full `_amountReward` to `rewardPerTokenStored` in a single call in `_provisionReward`. Alternatively, enforce a minimum staking duration / cooldown before a deposit becomes eligible for reward accrual, or snapshot `totalStaked()` prior to the block in which the injection is queued so freshly deposited capital cannot immediately participate in that batch's distribution.

### Proof of Concept
1. Attacker monitors for the periodic call in `WombatStaking` that forwards harvested WOM bonus rewards to a `BaseRewardPool` via `queueNewRewards` (or simply waits for/triggers `donateRewards`, which is permissionless).
2. Immediately before that call lands, attacker calls `MasterMagpie.deposit(stakingToken, largeAmount)` for the corresponding pool, which internally calls `updatePool` and sets `user.rewardDebt`/`userRewardPerTokenPaid` at the pre-injection `rewardPerTokenStored` [7](#0-6) .
3. The reward-injection transaction executes `_provisionReward`, which updates `rewardPerTokenStored` using `totalStaked()` that now includes the attacker's large deposit [1](#0-0) .
4. Attacker calls `MasterMagpie.withdraw`/`multiclaim`, which triggers `getReward`/`_harvestBaseRewarder`, computing `earned()` using the now-increased `rewardPerToken` against the attacker's large `balanceOf`, paying out a disproportionate share of the just-injected reward [8](#0-7) .
5. Attacker withdraws principal, having captured yield meant for genuine long-duration stakers with zero time-at-risk.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
