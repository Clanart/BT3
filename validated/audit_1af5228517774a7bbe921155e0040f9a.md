### Title
Shared `BalanceHandler` state across recursive/nested stateful precompile calls causes StateDB/bank balance desync - ([File: precompiles/common/balance_handler.go])

### Summary
The external report's bug class is: an operation performs a real, effectful action (token swap) and then a subsequent step's side effects are tracked via ad-hoc bookkeeping that is not atomic with the underlying operation, so when the bookkeeping is corrupted/skipped, spendable value diverges from actual state. The Cosmos EVM analog is the `BalanceHandler` mechanism used by stateful precompiles (staking, distribution, gov, slashing, ics20, erc20, debug, etc.) to translate Cosmos SDK bank events into EVM `StateDB` balance mutations. This mechanism uses a single mutable `prevEventsLen` cursor on a `BalanceHandler` instance retained by the precompile (`p.GetBalanceHandler()`), rather than a value that is properly scoped/reentrancy-safe per nested precompile invocation. The repository itself contains a dedicated regression test, `evmd/tests/integration/balance_handler/balance_handler_test.go`, whose comment explicitly states: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [1](#0-0) 

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current length of `ctx.EventManager().Events()` into `bh.prevEventsLen`, and `AfterBalanceChange` later replays `events[bh.prevEventsLen:]` to translate `CoinSpent`/`CoinReceived`/precisebank fractional events into `StateDB.SubBalance`/`AddBalance` calls: [2](#0-1) 

The precompile-call driver (`RunNativeAction`) is one place a `BalanceHandler` is created (via `p.BalanceHandlerFactory.NewBalanceHandler()`), but several concrete precompiles (distribution, erc20, gov, ics20, slashing, staking, debug) instead reference a handler obtained via `p.GetBalanceHandler()`, implying the handler is held as a retained field on the `Precompile` value rather than freshly constructed for every individual (possibly nested) invocation: [3](#0-2) [4](#0-3) 

When a Solidity contract performs a nested/recursive call into the same stateful precompile within one EVM transaction (a pattern already exercised elsewhere in the repo's test suites, e.g. `StakingReverter.performDelegation` re-entering the staking precompile via `try/catch`), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` before the outer call's `AfterBalanceChange` has run. The outer call then computes its balance delta window using the wrong (inner-call) cursor value, causing it to either replay bank events already consumed by the inner call (double-crediting `StateDB.AddBalance`) or skip events it should have processed (under/over crediting `StateDB.SubBalance`). Because `StateDB` balances are what subsequent EVM operations act on and what gets persisted via `Commit()`/`commitWithCtx`, this can desynchronize the EVM-visible balance from the actual bank-module balance for the duration of, and potentially beyond, the transaction. [5](#0-4) 

### Impact Explanation
A desync between `StateDB` balance and the real bank balance is an accounting-corruption bug matching the Critical impact class of "unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets." If the replay double-counts a `CoinReceived` event, an attacker's contract balance in `StateDB` can be inflated beyond what the bank module actually holds, letting the attacker spend/transfer more EVM-native value than they possess before the discrepancy is caught (if ever, since `StateDB.Commit()` persists dirty account balances directly to the keeper without re-checking bank invariants). This is directly analogous to the original report's "tokens stuck/mismanaged because side-effect tracking wasn't correctly reconciled with the actual token movement."

### Likelihood Explanation
Likelihood is Low, matching the original report's own severity/likelihood split (High impact / Low likelihood). It requires a purpose-built contract that recursively re-enters the same stateful precompile (staking/distribution/gov/slashing/erc20/ics20) within a single EVM call, a non-default but fully reachable and unprivileged pattern (already demonstrated feasible for `try/catch`-based recursive precompile calls elsewhere in this codebase's test suite, e.g. `StakingReverter`). I was not able to fully confirm from the indexed code whether `GetBalanceHandler()` truly returns one shared mutable instance per precompile object (vs. a fresh one per call) — the exact field/lifetime binding of `BalanceHandler` on each concrete precompile struct (distribution, staking, etc.) was outside what the index surfaced beyond the single reference per file. The repository's own test explicitly frames this as "the balance handler bug," which strongly suggests the sharing behavior is real and previously identified, but I could not independently verify the fix status (whether this is a still-open bug being regression-tested, or a fixed bug with a test guarding against regression) from the available file contents.

### Recommendation
Scope `BalanceHandler` state (in particular `prevEventsLen`) to each individual precompile invocation rather than a value retained across nested/recursive calls — e.g., use a stack of cursors or derive the window strictly from a snapshot taken at the start of that specific `Run`/`RunNativeAction` invocation, and ensure `AfterBalanceChange` for an outer call cannot be corrupted by an inner call's `BeforeBalanceChange`. Add or strengthen invariant checks that assert `StateDB` account balances match bank-module balances at the end of every precompile-touching EVM message before committing state.

### Proof of Concept
Deploy a contract analogous to `StakingReverter`/`ICS20Caller` that calls into a stateful precompile (e.g. the debug precompile, staking, or distribution) via `try { self.callback() } catch {}`, where `callback()` itself re-enters the same precompile before returning control to the outer invocation. This exact scenario is what `TestRecursivePrecompileCallsWithDebugPrecompile` sets up: it deploys `DebugPrecompileCaller`, calls `callback(0)` which nests calls into the debug precompile, and asserts on the resulting event/balance-handler behavior. // It records the current number of events in the context to later process balance changes

	bh.prevEventsLen = len(ctx.EventManager().Events())
