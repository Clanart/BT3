## Analysis

Reducing the external report to its core invariant: **a caller-controlled ERC20's transfer-outcome must be truthfully reflected in the caller's escrow accounting** — either by reverting on failure (the original bug, over-strict) or, in the inverse and more dangerous direction, by silently accepting a `false` return as success (under-strict). The Hyperbridge codebase contains exactly this inverse flaw in one specific deployment.

`evm/tron/contracts/apps/IntentGatewayV2.sol` imports `SafeERC20` and declares `using SafeERC20 for IERC20;` [1](#0-0) , and correctly uses `safeTransferFrom` when escrowing input tokens [2](#0-1) . However, the token *payout* paths — `withdraw()` (escrow redemption/refund) and the `SweepDust` handler — bypass `SafeERC20` entirely and instead perform a raw low-level `.call` that only checks whether the call itself reverted, never decoding/validating the returned boolean: [3](#0-2)

For any ERC20 token that signals failure by returning `false` rather than reverting, `token.call(...)` still returns `success = true` (the call executed without reverting), so `TransferFailed` is never triggered. The function nonetheless proceeds to decrement `_orders[body.commitment][token] -= amount` and, on `finalize`, marks `_filled[body.commitment] = beneficiary` — permanently closing out the escrow record as if the beneficiary was paid, while the actual tokens never left the contract. Since `withdraw()` requires `_orders[body.commitment][token] != 0` to even enter the loop, and it is now zeroed after the failed transfer, the beneficiary cannot re-trigger a legitimate redemption for that token — the underlying balance is stuck in the contract with no code path to recover it, while the protocol's own accounting says the order was already settled.

This directly falls under the bounty's "stealing or loss of funds" impact — the beneficiary loses their escrowed principal to a state that looks correctly settled (`EscrowReleased`/`EscrowRefunded` still emits) but the funds sit unclaimable in the contract, and no relayer, prover, or admin compromise is required — a token merely returning `false` on `transfer` (a completely standards-compliant ERC20 behavior seen historically, e.g. `ZRX`) or any wrapped/blocklist-style token used as an order input triggers it.

### Title
Unchecked ERC20 return value in `withdraw()`/`SweepDust` causes silent fund loss on Tron `IntentGatewayV2` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` imports `SafeERC20` and uses it correctly for escrow deposits, but its payout paths (`withdraw()` and the `SweepDust` handler in `onAccept`) use a raw low-level `.call` to `IERC20.transfer` and only check that the call didn't revert — never decoding the returned `bool`. Any ERC20 that returns `false` on a failed transfer (instead of reverting) is treated as a successful payout.

### Finding Description
`withdraw()` decrements `_orders[body.commitment][token]` and marks `_filled[body.commitment] = beneficiary` (finalizing the order and emitting `EscrowReleased`/`EscrowRefunded`) immediately after issuing the raw `.call`, gated only on `success` (call-level success, not the ABI-decoded boolean return value) [5](#0-4) . The same pattern is used for `SweepDust` [6](#0-5) . Compare this to the escrow-deposit path in the same contract, which correctly uses `safeTransferFrom` (reverts on falsy return) [2](#0-1) , and to the sibling non-Tron `IntentGatewayV2`/`IntentsBase` contracts, which use `safeTransfer` for payouts [7](#0-6) . The Tron variant is the outlier that reintroduces the exact "unchecked-transfer" risk class the external report describes, but inverted: instead of over-strict reverting on non-boolean-returning tokens, it under-checks and accepts `false`-returning tokens as success.

### Impact Explanation
Escrowed principal for an order input token becomes permanently unrecoverable: the accounting entry that gates redemption (`_orders[commitment][token]`) is zeroed and the order is marked filled/refunded, yet the tokens remain in the contract, and no follow-up call can re-trigger the transfer for that commitment. This is a direct loss/lock of user funds triggered by an ordinary, unprivileged interaction (placing/filling/cancelling an order with a `false`-returning ERC20), with no relayer, prover, or admin compromise required.

### Likelihood Explanation
Likelihood depends on which tokens are permitted as order inputs on the Tron deployment; several real-world ERC20s (e.g., legacy `ZRX`-style implementations) return `false` rather than reverting on failure, and Tron's own TRC20 ecosystem includes tokens with non-standard transfer semantics — this is a plausible trigger for a "just works most of the time" token whose transfer occasionally returns `false` (e.g., due to a blocklist, paused state, or insufficient allowance/balance edge case reached mid-flow).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout paths in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(...)` (the library is already imported and used elsewhere in this same contract), so that a falsy return reverts the whole state transition instead of silently finalizing escrow accounting against a failed transfer.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer()` returns `false` instead of reverting when, e.g., the recipient is on a blocklist or a threshold is exceeded (compliant with ERC20 spec).
2. Use this token as `order.inputs[i].token` in an order placed on the Tron `IntentGatewayV2`; escrow succeeds via `safeTransferFrom`.
3. Trigger `withdraw()` (via `RedeemEscrow`/`RefundEscrow` `onAccept` or `onGetResponse`) under conditions where the mock's `transfer()` returns `false` for the beneficiary.
4. Observe: `token.call(...)` returns `success = true` (no revert), so execution continues, `_orders[commitment][token]` is decremented to 0, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — while `beneficiary`'s token balance never increased and the tokens remain trapped in the `IntentGatewayV2` contract with no remaining code path to claim them.

        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));

        }

        if (isRefund) {

        } else {
