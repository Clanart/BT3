## Title
Stack exhaustion via deeply-nested outer-puzzle layers in offer/spend-bundle processing - ([File: chia/wallet/outer_puzzles.py, chia/wallet/trading/offer.py])

### Summary
The reported Go vulnerability is uncontrolled recursion in `go/parser` that panics via stack exhaustion on deeply nested input. The analogous pattern in chia-blockchain is the Python-level recursive "outer puzzle" driver chain (`match_puzzle` / `get_inner_puzzle` / `get_inner_solution` / `construct_puzzle`) used to walk nested puzzle layers (CAT, singleton, ownership, credential-restricted, etc.) when a wallet parses a `CoinSpend`/`Offer` puzzle reveal it did not create itself. Each layer of nesting consumes one Python call-stack frame with no depth limit, so an attacker (offer counterparty or malicious spend-bundle author) can hand a wallet a puzzle reveal with an arbitrarily deep chain of curried outer layers to exhaust the Python interpreter stack and crash the wallet's transaction-processing path.

### Finding Description
`chia/wallet/outer_puzzles.py` dispatches to per-asset-type driver objects (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`, etc.) via `match_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()`, and `construct_puzzle()` [1](#0-0) .

Each driver's `match()`/`get_inner_puzzle()`/`get_inner_solution()` method recurses by calling back into `self._match(...)` / `self._get_inner_puzzle(...)` / `self._get_inner_solution(...)` on the *next* uncurried inner puzzle layer, e.g. in `CATOuterPuzzle`: [2](#0-1) 
and identically in `OwnershipOuterPuzzle` and `CROuterPuzzle`: [3](#0-2) [4](#0-3) 

There is no bound on how many times a puzzle can be curried/layered inside another puzzle before it is handed to these functions — a puzzle reveal such as `CAT(CAT(CAT(...(ACS)...)))` nested tens of thousands of times is a syntactically valid CLVM program (`curry()` just wraps `(2 (1 . self) args)` recursively, as shown in `Program.curry`) [5](#0-4) . Because CLVM program parsing itself is delegated to Rust (`Program.from_bytes` runs through `run_chia_program`, deliberately avoiding the Python recursion limit) [6](#0-5) , the actual bytes and tree-hash computation are safe. However, once the resulting `Program`/`UnknownPuzzle` structure is walked by the pure-Python outer-puzzle-driver recursion, no equivalent iterative/tree-hash-style protection exists — unlike `sha256_treehash`, which the code base explicitly documents as "deliberately non-recursive ... so we don't have to worry about blowing out the Python stack" [7](#0-6) .

This recursive driver chain is directly reachable when a wallet processes an `Offer` received from an untrusted counterparty. `Offer.__post_init__` iterates every `CoinSpend` in the bundle and calls `compute_spend_hints_and_additions` [8](#0-7) , and `Offer._get_offered_coins()` explicitly calls `match_puzzle`, `get_inner_puzzle`, and `get_inner_solution` on each `parent_spend.puzzle_reveal` supplied by the offer file [9](#0-8) . The debug/dumping path `recursive_uncurry_dump` in `chia/wallet/util/debug_spend_bundle.py` exhibits the identical unbounded recursive pattern over attacker-supplied puzzle reveals [10](#0-9) .

### Impact Explanation
An offer counterparty (or a party submitting a crafted `CoinSpend`/`SpendBundle` for wallet-side inspection, e.g. via offer take/inspect flows or `debug_spend_bundle`) can construct a puzzle reveal with an extremely deep chain of nested outer-puzzle layers. When the victim wallet parses/evaluates the offer or spend bundle through `match_puzzle`/`get_inner_puzzle`/`get_inner_solution` (or the debug dump path), the unbounded Python recursion will exhaust the interpreter's call stack and raise an uncaught `RecursionError`, crashing or hanging the wallet process that is processing the offer — a spend-triggered transaction-processing halt matching the accepted impact category in the rules (denial of service on a local wallet/RPC caller, not a network-wide consensus issue).

### Likelihood Explanation
Likelihood is moderate: constructing a puzzle with many thousands of curried layers is inexpensive for an attacker (mechanical application of `curry()` in a loop) and requires no special privileges — only that a victim open/inspect an untrusted offer file or spend bundle. The exact reachable severity depends on whether any calling code wraps these operations in try/except that catches `RecursionError` (I did not find such handling in the reviewed call sites, but I was not able to exhaustively verify every caller of `Offer._get_offered_coins`/`get_inner_puzzle` due to remaining tool-call budget).

### Recommendation
- Convert the recursive `match`/`construct`/`get_inner_puzzle`/`get_inner_solution` traversal in `chia/wallet/outer_puzzles.py` and each `*OuterPuzzle` driver into an iterative loop (similar to the non-recursive `sha256_treehash` pattern already used for tree hashing).
- Alternatively, impose an explicit maximum layer-nesting depth when uncurrying puzzle reveals from untrusted sources (offers, received spend bundles) and raise a controlled `ValueError`/rejection instead of recursing unbounded.
- Apply the same treatment to `recursive_uncurry_dump` in `chia/wallet/util/debug_spend_bundle.py`.

### Proof of Concept
Conceptual PoC (not executed):
1. Build `ACS = Program.to(1)`.
2. Repeatedly wrap: `puzzle = construct_cat_puzzle(CAT_MOD, tail, puzzle)` (or equivalently nest `OwnershipOuterPuzzle`/`CROuterPuzzle` layers) tens of thousands of times to produce a single puzzle reveal with deep outer-layer nesting.
3. Embed this puzzle as `puzzle_reveal` in a `CoinSpend` within a crafted `Offer`/`SpendBundle` and send it to a victim wallet (e.g., as an offer file to be inspected via `take_offer`/`get_offer_summary`, or pass it to `debug_spend_bundle`).
4. When the victim wallet calls `Offer._get_offered_coins()` → `match_puzzle()`/`get_inner_puzzle()`/`get_inner_solution()`, or `debug_spend_bundle()` → `uncurry_dump()` → `recursive_uncurry_dump()`, the recursive calls exceed Python's stack depth and raise an unhandled `RecursionError`, crashing/hanging the wallet's transaction-processing thread.

Note: I was unable to fully trace every RPC/CLI entry point that calls `Offer._get_offered_coins`/`get_inner_puzzle` within the remaining tool budget, so the precise set of externally triggerable call paths (beyond the `Offer.__post_init__`/`_get_offered_coins` path and the `debug_spend_bundle` path shown above) is not exhaustively confirmed.

def recursive_uncurry_dump(puzzle: Program, layer: int, prefix: str, uncurried_already: UncurriedPuzzle) -> None:
    mod = uncurried_already.mod
    curried_args = uncurried_already.args
    if mod != puzzle:
        print(f"{prefix}- Layer {layer}:")
        print(f"{prefix}  - Mod hash: {mod.get_tree_hash().hex()}")
        for arg in curried_args.as_iter():
            uncurry_dump(arg, prefix=f"{prefix}  ")
        mod2, curried_args2 = mod.uncurry()
        if mod2 != mod:
            recursive_uncurry_dump(mod, layer + 1, prefix, UncurriedPuzzle(mod2, curried_args2))
    else:
        print(f"{prefix}- {bu_disassemble(puzzle)}")


def uncurry_dump(puzzle: Program, prefix: str = "") -> None:
    mod, curried_args = puzzle.uncurry()
    if mod != puzzle:
        print(f"{prefix}- <curried puzzle>")
        prefix = f"{prefix}  "

    recursive_uncurry_dump(puzzle, 1, prefix, UncurriedPuzzle(mod, curried_args))
