### Title
Pyth storage/oracle contract addresses hardcoded in market and data contracts are never updated when `pyth-governance-v3` migrates its execution plan - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`pyth-governance-v3` exposes admin functions (`update-pyth-storage-contract`, `update-pyth-oracle-contract`, `update-pyth-decoder-contract`) that change the "current execution plan" — the addresses of the live Pyth storage/oracle/decoder contracts. Zest's own `v0-4-market.clar` and `v0-1-data.clar` do not read this execution plan; they call a hardcoded literal principal for `pyth-storage-v4` directly. If the Pyth infra migrates to a new storage contract via governance, Zest keeps querying the now-frozen old contract, exactly the "parameter updated at the top level but not propagated to dependent contracts" bug class from the referenced report.

### Finding Description
`pyth-governance-v3` maintains `current-execution-plan` as the single source of truth for which storage/oracle/decoder contracts are active, and provides governance-gated setters to change it: [1](#0-0) 

`pyth-storage-v4`'s `write` function only accepts updates when called through the execution flow that matches the CURRENT plan registered in `pyth-governance-v3`: [2](#0-1) 

This means once governance calls `update-pyth-storage-contract` to point to a new storage contract, the old storage contract stops receiving new price writes — its cached `publish-time` per feed is now frozen.

However, Zest's own consuming contracts bypass this governance indirection entirely and hardcode the storage contract's literal principal: [3](#0-2) [4](#0-3) 

Neither file consults `pyth-governance-v3.get-current-execution-plan` (the mechanism `pyth-oracle-v4.get-price`/`read-price-feed` itself uses to validate the storage contract via `check-storage-contract`): [5](#0-4) 

So a top-level parameter change (the active storage contract address) at the governance layer is never propagated into `v0-4-market.clar`/`v0-1-data.clar`, which keep hardcoded references baked in at deploy time.

### Impact Explanation
Once the old, hardcoded `pyth-storage-v4` stops being written to (because the relayer network moves to writing through the new governance-designated storage contract), its per-feed `publish-time` no longer advances. Zest's own local freshness check in `price-resolve` compares the feed's `publish-time` against `stacks-block-time` and the asset's configured `max-staleness`: [6](#0-5) 

Once the frozen feed's age exceeds `max-staleness`, every operation that needs that asset's price (borrow, withdraw, and liquidation checks) will revert with `ERR-ORACLE-INVARIANT`, freezing user funds denominated in or collateralized by that asset until Zest's team manually redeploys/patches the hardcoded address. This lands in the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
This requires Pyth's governance (a legitimate, documented migration path they support) to rotate the storage/oracle/decoder contract — not a bug in Pyth itself, but a normal, expected operational event for that infrastructure. Because the trigger is entirely outside Zest's control and is a standard upgrade mechanism the third-party bridge explicitly provides, likelihood is low but non-zero, and the fix (making Zest read the governance execution plan dynamically, or at minimum having an admin path to update the hardcoded address quickly) is straightforward.

### Recommendation
Have `v0-4-market.clar` and `v0-1-data.clar` resolve the Pyth storage/oracle contract dynamically via `pyth-governance-v3.get-current-execution-plan` (or accept it as a trait-typed parameter validated against governance, as `pyth-oracle-v4` itself does) instead of embedding a literal principal, so that a legitimate upstream migration is automatically honored rather than silently stranding Zest on a deprecated, frozen feed.

### Proof of Concept
1. `pyth-governance-v3` admin submits a valid VAA calling `update-pyth-storage-contract`, moving the active storage contract from `pyth-storage-v4` to `pyth-storage-v5`.
2. The relayer network begins writing new price updates only to `pyth-storage-v5` (writes to `pyth-storage-v4` now fail `check-execution-flow`/`check-storage-contract` checks enforced by governance).
3. `pyth-storage-v4`'s cached `publish-time` for every feed stops advancing.
4. Zest's `v0-4-market.clar` `call-pyth` still hardcodes `'SP1CGXWEAMG6P6FT04W66NVGJ7PQWMDAC19R7PJ0Y.pyth-storage-v4` and keeps reading the now-frozen feed.
5. Once `stacks-block-time - publish-time > max-staleness` for the affected asset, `price-resolve` reverts with `ERR-ORACLE-INVARIANT` on every borrow/withdraw/liquidation call touching that asset, freezing user funds until Zest ships a contract update pointing at `pyth-storage-v5`.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
