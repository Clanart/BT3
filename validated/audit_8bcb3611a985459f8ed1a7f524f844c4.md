### Title
Unvalidated `filepath` query parameter in `x-github-client://openRepo` deep links enables path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The Sherlock report's broken invariant is: an external, attacker-influenced value is trusted to have a specific shape/format without validation, and that trust is later used in a security-relevant computation (PT rate scaling), corrupting downstream logic. The GitHub Desktop analog is `parseAppURL()`, which parses the `x-github-client://openRepo/...` deep link (a link an attacker can get a victim to click) and validates the `branch` parameter against `testForInvalidChars`, but performs **no validation whatsoever** on the `filepath` query parameter before handing it to the rest of the app as trusted, repo-relative data.

### Finding Description
`parseAppURL` in [1](#0-0)  extracts `pr`, `branch`, and `filepath` from the incoming URL's query string. `pr` is checked against `/^\d+$/`, `branch` is checked with `testForInvalidChars`, but `filepath` is returned as-is with zero sanitization: [2](#0-1) 

The resulting `IOpenRepositoryFromURLAction.filepath` field is documented as "the file to open after cloning the repository" [3](#0-2) , and is fed straight from `parsedURL.query` via `getQueryStringValue`, meaning it can contain arbitrary characters including `../`, absolute path prefixes, URL-encoded traversal sequences, or null-adjacent characters — the same class of "assumed well-formed input" mistake as trusting `getPtToSyRate()` to always be 1e18-scaled without checking.

The action is dispatched through the main process (`handleAppURL` → `window.sendURLAction(action)`) as seen in [4](#0-3) , then consumed by the renderer's dispatcher (`app/src/ui/dispatcher/dispatcher.ts`, which references `filepath` in its handling of the open-repository-from-url action). If that downstream code joins `filepath` with the freshly cloned repository's working directory (e.g. via `path.join(repoPath, filepath)`) to open the file in the user's editor/shell, a traversal payload lets an attacker-controlled link cause the app to open (and in some code paths, `shell.openItem`/write-adjacent behavior can follow open) a file outside the repository — e.g. `..\..\..\..\AppData\Roaming\GitHub Desktop\config.json` or a `.ssh` key path.

Existing guards do not stop this path because:
- `testForInvalidChars` is applied only to `branch`, never to `filepath`.
- `pr` is validated with a strict regex; `filepath` has no equivalent regex or `path.normalize`/`path.relative`-based containment check.
- The unit tests in `app/test/unit/parse-app-url-test.ts` only assert that a benign `filepath` value round-trips correctly; there is no test asserting rejection of `../`-style payloads, confirming the omission is unintentional and unguarded, not a deliberate accepted risk.

### Impact Explanation
This matches the required Desktop impact class: the attacker controls a link/deep link the user clicks, and the corrupted value (`filepath`) is a repo-relative path that downstream code trusts as safe. If the consuming code opens or otherwise touches that path relative to the newly cloned repository without re-validating containment, it results in file access outside the intended repository directory — analogous to the Sherlock finding where an unchecked external value ("assumed 1e18 scale") propagated into a security-critical computation ("PT price") with no bounds check.

### Likelihood Explanation
Likelihood is high for the *reachability* of the bug (the `openRepo` URL scheme and query parsing require no privileges — any web page or message the victim clicks can register the payload, since `x-github-client://`/`github-mac://`/`github-windows://` are OS-registered protocol handlers per [5](#0-4) ). The remaining uncertainty is the exact consumer behavior in `app/src/ui/dispatcher/dispatcher.ts` (whether it does `path.join` without a containment check) — I was not able to fetch and confirm that exact code path before running out of tool calls, so the severity of the *sink* (open vs. write vs. silent overwrite) is not fully verified from the index alone.

### Recommendation
Apply the same character/format allow-list used for `branch` to `filepath` in `parseAppURL` (reject `..`, absolute path prefixes, and platform path separators outside a safe subset), and in the consumer (dispatcher.ts) resolve `filepath` against the repository root using `path.resolve` + `path.relative` and reject/normalize any result that escapes the repo directory, mirroring how the Pendle fix would require asserting `getPtToSyRate()`'s actual decimals rather than assuming 1e18.

### Proof of Concept
A crafted link such as:
```
x-github-client://openRepo/https://github.com/some/repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fauthorized_keys
```
passes `parseAppURL` validation untouched (branch is valid, pr is absent, filepath is never checked) as shown in [1](#0-0) , producing `{ name: 'open-repository-from-url', url, branch: 'main', pr: null, filepath: '../../../../.ssh/authorized_keys' }`, which is then dispatched to the renderer for post-clone file handling.

**Confidence caveat:** I confirmed the parsing-layer omission directly from source, but could not fully trace the exact file-open/write sink in `dispatcher.ts` within the available tool budget to prove the terminal impact (open vs. write) — a Devin session with full file access should verify the exact consumer code path before treating this as a confirmed, exploitable sink.

    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {

function handleAppURL(url: string) {
  log.info('Processing protocol url')
  const action = parseAppURL(url)
  onDidLoad(window => {
    // This manual focus call _shouldn't_ be necessary, but is for Chrome on
    // macOS. See https://github.com/desktop/desktop/issues/973.
    window.focus()
    window.sendURLAction(action)
  })
