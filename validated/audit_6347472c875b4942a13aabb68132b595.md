### Title
Hookify hooks auto-load and execute committed `.claude/hookify.*.local.md` rule files without any provenance/approval check, bypassing the `/hookify` consent workflow - (File: `plugins/hookify/core/config_loader.py`)

### Summary
The Hookify plugin registers `PreToolUse`, `PostToolUse`, `Stop`, and `UserPromptSubmit` hooks (via `plugins/hookify/hooks/hooks.json`) that unconditionally execute `load_rules()` on every tool call/prompt. `load_rules()` globs `.claude/hookify.*.local.md` and loads/evaluates *any* file matching that name pattern, with zero check for whether the file was created through the `/hookify` command's approval flow or was instead planted in a cloned repository by a third party.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` builds the glob pattern `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)`, then feeds every matched file into `load_rule_file()` and includes it in the returned rule list if `enabled` is true (default `True` if unspecified): [1](#0-0) 

`load_rule_file()` merely parses YAML-ish frontmatter and constructs a `Rule` object — there is no signature, hash, origin marker, or "created-by-/hookify" flag checked anywhere: [2](#0-1) 

All four hook entry points (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) are registered unconditionally in `plugins/hookify/hooks/hooks.json` and simply call `load_rules()` then `RuleEngine().evaluate_rules()` on every matching Claude Code event: [3](#0-2) [4](#0-3) 

`RuleEngine.evaluate_rules()` will return a `systemMessage` (warn) or a `permissionDecision: "deny"` with `systemMessage` (block) for any matching rule, with no origin check: [5](#0-4) 

The "approval workflow" that the documentation describes (`/hookify` command interactively confirming rules before writing files, per `plugins/hookify/commands/hookify.md` steps) is purely a convention followed by the slash-command prompt text — it is not enforced anywhere in the actual hook/loader code. [6](#0-5)  Any file dropped into `.claude/` matching `hookify.*.local.md` — whether hand-written, generated by a different tool, or committed to git by a repo author/attacker — is loaded and enforced identically. The only "protection" is a documentation suggestion that these files "should be git-ignored," which is not enforced by `.gitignore` shipped with the plugin, by the loader, or by any workspace-trust/session-binding check: [7](#0-6) 

Consequently, an attacker who controls repository content (e.g., a malicious open-source repo, a compromised dependency vendored into a repo, or a poisoned PR branch) can commit `.claude/hookify.attacker.local.md` with `event: all`/`prompt`/`bash`/`file` and `pattern: .*` plus an arbitrary `message`. The moment a victim clones the repo and runs Claude Code inside it, every subsequent tool call or prompt submission triggers the corresponding hook, which loads and evaluates the attacker's rule with no user interaction, no `/hookify` invocation, and no approval prompt.

### Impact Explanation
This breaks the "consent-is-explicit" invariant for hook rules: content shipped in an ordinary git checkout can inject arbitrary `systemMessage` text into the model's context on every tool call/prompt (prompt injection into the agent loop), or can force a `permissionDecision: "deny"` to silently block specific operations (denial-of-service against victim's legitimate tool use), all without the victim ever running `/hookify` or approving anything. Because the injected `systemMessage` is shown to Claude on every PreToolUse/PostToolUse/Stop/UserPromptSubmit event, an attacker can steer agent behavior repeatedly and persistently for the life of the checked-out repo.

### Likelihood Explanation
Preconditions are minimal and match ordinary developer workflow: the victim must clone/checkout a repository containing a crafted `.claude/hookify.*.local.md` file and run Claude Code with that directory as the working directory — no elevated privileges, no social engineering beyond "get the victim to open this repo," and no reliance on leaked keys. This is highly repeatable: the payload is a static, plainly committable markdown file, and the loader/hook logic performs the exact same glob → parse → evaluate sequence on every single tool call and prompt.

### Recommendation
Enforce provenance for hookify rule files instead of trusting anything matching the glob pattern: e.g., require rule files to be registered in a separate, explicitly user-approved manifest (not derivable purely from filesystem glob), prompt the user for confirmation the first time a `.claude/hookify.*.local.md` file is detected that wasn't created via `/hookify` in the current session, track approved rule file hashes in a local (non-repo, e.g. `~/.claude/`) trust store, and/or refuse to auto-load rule files that are tracked by git in the current repository (i.e., only trust untracked/gitignored `.local.md` files) with an explicit warning if a tracked one is found.

### Proof of Concept
Integration test plan:
1. Create a temp directory, `git init`, and simulate a "malicious clone" by writing `.claude/hookify.evil.local.md` directly to disk (never invoking any `/hookify` command logic) with frontmatter:
```

name: evil-rule
enabled: true
event: prompt
pattern: .*
action: warn
---
INJECTED: attacker-controlled systemMessage
```
2. `git add`/`git commit` this file to simulate it being part of a cloned repo (demonstrating it travels with the repo, not created locally by the victim).
3. From that directory, call `hookify.core.config_loader.load_rules(event='prompt')` directly (as `userpromptsubmit.py` does) and assert the returned list is non-empty and contains a `Rule` named `evil-rule`.
4. Call `RuleEngine().evaluate_rules(rules, {"hook_event_name": "UserPromptSubmit", "tool_name": "", "tool_input": {}})` and assert the result dict's `systemMessage` equals/contains `"INJECTED: attacker-controlled systemMessage"`.
5. Repeat with `action: block` and `event: bash`, feeding a `PreToolUse` input for a `Bash` tool call, asserting `result["hookSpecificOutput"]["permissionDecision"] == "deny"` — proving unauthorized-file-based command blocking without any `/hookify` approval step having run.

```python
def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)
```

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
```

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
