### Title
Missing Zero-Address Validation for `evm_address` in Deposit Flow Causes Permanent BTC Lock — (`File: core/src/rpc/parser/mod.rs`, `core/src/verifier.rs`)

---

### Summary

The Clementine bridge accepts a deposit request with `evm_address = [0u8; 20]` (the EVM zero address) without any rejection. Every validation gate in the deposit pipeline — the gRPC parser, the aggregator's `new_deposit` handler, and the verifier's `is_deposit_valid` — passes silently. The move-to-vault transaction is signed by all N-of-N verifiers and broadcast on-chain, permanently locking the user's BTC in the vault while the corresponding Citrea tokens are minted to the zero address and are irrecoverable.

---

### Finding Description

`EVMAddress` is defined as a plain 20-byte newtype with no semantic constraints: [1](#0-0) 

The `TryFrom<Vec<u8>>` implementation only enforces the length (20 bytes); it does not reject `[0u8; 20]`.

When the aggregator's `new_deposit` gRPC endpoint receives a `BaseDeposit` message, the parser converts the raw bytes to `EVMAddress` with no zero-address guard: [2](#0-1) 

The resulting `BaseDepositData` is passed into `DepositData` and forwarded to every verifier. The verifier's `is_deposit_valid` function performs extensive checks (security council, watchtower counts, operator collateral, script-pubkey match, block height), but contains no check that the embedded EVM address is non-zero: [3](#0-2) 

The EVM address is committed into the Bitcoin deposit script via `BaseDepositScript`: [4](#0-3) 

The verifier's script-pubkey consistency check (`deposit_txout_in_chain.script_pubkey != expected_scriptpubkey`) will **pass** for a zero-address deposit because the on-chain script was generated from the same zero address. There is no mismatch to detect. [5](#0-4) 

After all verifiers sign, the aggregator broadcasts the move-to-vault transaction. The BTC leaves the user-controlled deposit UTXO (which had a timelock recovery path) and enters the N-of-N vault, from which there is no user recovery path. The Citrea layer then reads the zero EVM address from the on-chain script and mints tokens to `0x0000000000000000000000000000000000000000`.

---

### Impact Explanation

Once the move-to-vault transaction is confirmed:

1. The deposit UTXO (which carried the user's timelock recovery path) is spent — the user can no longer reclaim BTC via the `TimelockScript`.
2. The BTC is held in the N-of-N vault with no user-accessible recovery path.
3. Tokens minted to the zero address are permanently inaccessible.

The result is **permanent, irrecoverable loss of the full bridge amount** for the depositing user. This satisfies the "permanent lock of bridged BTC" impact criterion.

---

### Likelihood Explanation

The trigger requires only that a caller supply `evm_address = [0u8; 20]` in the `BaseDeposit` gRPC message. This is:

- A valid 20-byte sequence that passes all current parsing checks.
- Reachable by any external caller of the `new_deposit` RPC endpoint (no privileged role required — the aggregator is the public-facing entry point for deposits).
- Plausible as an accidental input from a buggy frontend, a misconfigured script, or a user who omits the address field (protobuf default for `bytes` is an empty/zero value).

No special permissions, no malicious deployment, and no external-system compromise are required.

---

### Recommendation

Add a zero-address check at the earliest validation boundary. The most defensive location is the gRPC parser, so the request is rejected before any state is touched:

```rust
// core/src/rpc/parser/mod.rs — inside TryFrom<clementine::deposit::DepositData> for DepositType
let evm_address: EVMAddress = data.evm_address.try_into().map_err(|e| {
    Status::invalid_argument(format!("Failed to convert evm_address: {e}"))
})?;
if evm_address.0 == [0u8; 20] {
    return Err(Status::invalid_argument(
        "evm_address must not be the zero address",
    ));
}
```

A redundant guard should also be added inside `is_deposit_valid` in `core/src/verifier.rs` for defence-in-depth, mirroring the pattern already used for other deposit-data invariants.

---

### Proof of Concept

1. Obtain the aggregator's gRPC endpoint (no authentication required for `new_deposit`).
2. Send BTC to the deposit address generated with `evm_address = [0u8; 20]` and the correct `nofn_xonly_pk`.
3. Call `new_deposit` with:
   ```
   BaseDeposit {
       evm_address: vec![0u8; 20],   // zero address
       recovery_taproot_address: "<valid taproot address>",
   }
   ```
4. Observe: all verifiers pass `is_deposit_valid`, sign the move-to-vault transaction, and the aggregator broadcasts it.
5. The BTC is now in the vault. The Citrea layer mints tokens to `0x0000000000000000000000000000000000000000`. The user's BTC is permanently locked with no recovery path.

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea: [u8; 6] = "citrea".as_bytes().try_into().expect("length == 6");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea)
            .push_slice(self.1 .0)
            .push_opcode(OP_ENDIF)
            .into_script()
    }
