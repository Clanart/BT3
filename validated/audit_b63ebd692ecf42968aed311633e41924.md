### Title
`ReplacementDepositData::old_move_txid` is never cross-checked against the actual spent move tx, allowing a self-funded fake replacement deposit citing an unrelated foreign move txid - (`core/src/deposit.rs:349-352`, `core/src/verifier.rs:659-705`)

### Summary
`Verifier::is_deposit_valid` only checks that the on-chain UTXO named in `deposit_outpoint` has the right amount and a scriptPubKey matching `create_taproot_address([ReplacementDepositScript(nofn_xonly_pk, old_move_txid), Multisig(security_council)])` [1](#0-0) . It never verifies that this UTXO was actually produced by the security council/nofn spending the specific `old_move_txid` transaction, nor that `old_move_txid` is unspent-but-flagged-for-replacement or belongs to any deposit lineage at all. Because a P2TR scriptPubKey is fully deterministic from public data (`nofn_xonly_pk`, `old_move_txid`, `security_council`), an unprivileged attacker can compute that same address for any confirmed move-to-vault txid belonging to someone else's still-open deposit, self-fund an output paying exactly `bridge_amount` to that address, and submit it as a brand-new `ReplacementDeposit`.

### Finding Description
Broken binding: the code implicitly assumes `deposit_outpoint`'s funding transaction == "the transaction by which the security council/nofn actually spent `old_move_txid` to authorize this specific replacement," i.e. `deposit_outpoint.txid`'s inputs spend `OutPoint{old_move_txid, UtxoVout::DepositInMove}` via the security-council multisig or nofn key path, as built in `create_replacement_deposit_txhandler` (`core/src/builder/transaction/mod.rs:404-446`, test-only reference implementation) [2](#0-1) . In reality, `is_deposit_valid` never inspects the inputs of `deposit_outpoint`'s transaction; it derives `get_deposit_scripts()` purely from attacker-supplied `replacement_deposit_data.old_move_txid` (`core/src/deposit.rs:206-217`) [3](#0-2) , builds the expected address, and compares only scriptPubKey and amount against the chain (`core/src/verifier.rs:659-697`) [4](#0-3) . There is no check that `old_move_txid` is spent, that it is spent by *this* `deposit_outpoint`'s parent tx, or that the security council actually authorized this replacement.

Exploit flow: attacker reads any confirmed, still-open move-to-vault txid `T` (belonging to a victim deposit they never funded), computes `Addr = TaprootAddress([ReplacementDepositScript(nofn_xonly_pk, T), Multisig(security_council)])` using the same public `nofn_xonly_pk`/`security_council` config parameters that verifiers use, sends `bridge_amount` from their own wallet to `Addr`, waits for confirmation past `start_height`, then calls the aggregator's `new_deposit`/`deposit_sign` gRPC with `Deposit{deposit_outpoint: <attacker's self-funded outpoint>, replacement_deposit: {old_move_txid: T}}`. Every verifier's `is_deposit_valid` check passes because scriptPubKey and amount match exactly what the attacker engineered, and none of the existing guards (`Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, presigned tx graph) inspect the provenance of the funding UTXO or link it to a real spend of `T`.

### Impact Explanation
This is confirmed as an insufficiently-checked binding at the Rust/gRPC layer: verifiers would sign a new N-of-N move-to-vault transaction for a `ReplacementDeposit` whose `old_move_txid` field references a foreign, unrelated, still-live move-to-vault UTXO that was never actually replaced. This corrupts the `old_move_txid` lineage that downstream logic (the Citrea bridge contract's `replaceDeposit`, referenced in `core/src/test/common/citrea/mod.rs:556-567`) relies on to mark the old deposit as replaced and associate a `deposit_id` [5](#0-4) . However, I could not fully trace or verify within this repository whether the Citrea contract's `replaceDeposit` performs its own independent verification (e.g., SPV proof that `old_move_txid`'s output was actually spent by the referenced replace transaction, or a check that only one `replaceDeposit` call is honored per `old_move_txid`) before crediting/double-counting value — that logic lives in the Citrea smart contract, which is explicitly out of scope ("Citrea contract ... defects with no path through this repository" are excluded), and I found no evidence in this repo of Citrea-side double-counting being reachable purely through this gap.

Within scope of this repo, the concrete effect is: verifiers can be induced to countersign a `ReplacementDeposit`'s move-to-vault transaction that falsely claims to replace someone else's move tx, without the security council ever having authorized it. This is a real N-of-N signing-session defect (verifiers sign for a mis-labeled replacement) but on its own does not move any BTC out of a move-to-vault UTXO, does not credit an operator, and does not freeze/burn anything — the attacker's own self-funded coins move into a legitimately-signed new deposit, and the victim's original move-to-vault UTXO remains untouched (still validly locked under nofn key + still spendable only by real nofn/security-council paths). Whether this ultimately reaches a Critical/High impact category as defined (BTC leaving without a fronted withdrawal, wrong reimbursement, frozen/burned collateral, N-of-N sig for unauthorized spend of a *specific* UTXO, etc.) depends entirely on the Citrea contract's handling of `old_move_txid`, which is out of scope and unverifiable from this repository alone.

### Likelihood Explanation
Preconditions are cheap and fully within the stated attacker capability: knowledge of a public confirmed move-to-vault txid, ability to compute a taproot address from public config (`nofn_xonly_pk`, `security_council`), and ability to fund `bridge_amount` (a fixed protocol parameter, typically nontrivial BTC) to that address, then call the aggregator's public `new_deposit`/`deposit_sign` gRPC. No verifier, operator, or security-council collusion is required. Given the required lock-in of `bridge_amount` and lack of any downstream credit within this repo, exploitation is technically straightforward but its value to the attacker is unclear without confirming Citrea-side consequences.

### Recommendation
`is_deposit_valid` should verify provenance of the `deposit_outpoint`'s funding transaction for `ReplacementDeposit`s: fetch the transaction that created `deposit_outpoint` and assert its input(s) spend `OutPoint{old_move_txid, UtxoVout::DepositInMove}` (i.e., `deposit_tx.input[0].previous_output.txid == old_move_txid`), and additionally confirm that spend used the `Multisig(security_council)` script path (e.g., by checking the witness script/leaf used matches the multisig branch) rather than accepting any output that merely matches the derived scriptPubKey regardless of its funding source. This closes the gap between "address matches" and "this specific move tx was actually replaced by the security council."
