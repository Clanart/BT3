### Title
Unbounded, attacker-controlled allocation in `ThresholdKeys::read` enables memory-exhaustion DoS - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes a threshold key set from an untrusted `io::Read` stream. The `n` (participant count) field is read directly from the attacker-controlled bytes and immediately used to pre-allocate a `Vec` and to drive a loop reading `n` scalars and `n` points, before `ThresholdParams::new` validates that `n` is sane relative to `t`/`i`. This mirrors the CVE-2021-3859 class: untrusted remote input drives resource consumption that is not bounded by the caller.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s from the stream:

```rust
// crypto/dkg/src/lib.rs:591-602
let (t, n, i) = {
  let mut read_u16 = || -> io::Result<u16> { ... };
  (
    read_u16()?,
    read_u16()?,
    Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
  )
};
```

The attacker-controlled `n` is then used for allocation before any semantic validation:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

and again to size the verification-shares loop:

```rust
// crypto/dkg/src/lib.rs:620-623
let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

Only after all of this work does `ThresholdParams::new(t, n, i)` reject inconsistent parameters (line 625-626). A `ThresholdKeys::read` call is one of the explicitly reachable untrusted-byte sinks (`read_share`/`ThresholdKeys::read` per the threat model). The elements themselves are bounded by input length (each `read_F`/`read_G` fails on EOF), but the `Vec::with_capacity(usize::from(n))` performs the allocation *before* a single element is read. With `n = 0xFFFF` (65535), a 7-byte prefix (`id_len`+`id`+`t`+`n`+`i`+interpolation tag) forces allocation of `65535 * size_of::<C::F>()` bytes — e.g. ~3.6 MB for a 56-byte Ed448 scalar, ~2 MB for a 32-byte scalar — even when the stream then ends immediately. Additionally, with interpolation tag `1` (Lagrange), no with_capacity occurs but the verification-shares `HashMap` loop is still driven by `n`; this is input-bounded so it contributes only modest amplification.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., restoring/deserializing key material supplied through a peer-facing or storage path) can force disproportionate memory allocation per call — a ~4×10⁵ amplification between bytes sent and bytes allocated for wide-field curves. Repeated requests or a loop over many such blobs exhausts process memory and crashes the node, denying service for the signing/DKG subsystem. This is a pure availability impact consistent with the Undertow CVE class (unbounded resource consumption triggered by remote input), not a correctness or secrecy break.

### Likelihood Explanation
Reachability depends on an integrator deserializing `ThresholdKeys` from an untrusted source; within Serai, `ThresholdKeys::read` is used to load key sets (e.g., `processor/src/key_gen.rs` `read_keys` deserializes via `ThresholdKeys::read` in a loop over stored bytes — that particular DB is trusted, but any deployment where serialized `ThresholdKeys` cross a trust boundary is exposed). The trigger requires only that a stream yield a valid curve ID and then a large `n`; allocation happens before any read can fail. Severity is Medium rather than High because the per-call amplification is bounded (~MBs, not GBs) and the elements themselves remain input-bounded.

### Recommendation
- Validate `n` before allocating: check `t <= n`, `n` against a protocol maximum, and `i <= n` (i.e., run `ThresholdParams::new` first, then deserialize body).
- Avoid `Vec::with_capacity(n)` on untrusted counts; grow the vector as elements are successfully read, or cap with `min(n, MAX_PARTICIPANTS)`.
- Apply the same pattern to `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`), which trusts a `u32` element count, and `Plan::read`/other readers using attacker-controlled length prefixes.

### Proof of Concept
```rust
// Feeding 7 crafted bytes to ThresholdKeys::read forces a ~2-3.6 MB allocation
// even though the stream contains no further data.
use std::io::Cursor;
use dkg::ThresholdKeys;
use ciphersuite::Ed448; // or any Ciphersuite

let mut bytes = Vec::new();
bytes.extend(&(Ed448::ID.len() as u32).to_le_bytes());
bytes.extend(Ed448::ID);
bytes.extend(&1u16.to_le_bytes());      // t = 1
bytes.extend(&0xFFFFu16.to_le_bytes()); // n = 65535 (attacker controlled)
bytes.extend(&1u16.to_le_bytes());      // i = 1
bytes.push(0);                          // Interpolation::Constant
// Vec::with_capacity(65535) executes before read_F fails on EOF
let _ = ThresholdKeys::<Ed448>::read(&mut Cursor::new(bytes));
// Repeating in a loop allocates unboundedly relative to input size.
```
