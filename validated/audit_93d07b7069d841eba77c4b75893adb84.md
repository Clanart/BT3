### Title
Blame verification swaps accuser and accused, so honest accusers are fatally slashed instead of the malicious share sender - ([File: processor/src/key_gen.rs])

### Summary
`AdditionalBlameMachine::blame`/`BlameMachine::blame` take `(sender, recipient, msg, proof)` where `sender` is the party who sent the alleged-invalid secret share and `recipient` is the accusing party. The `CoordinatorMessage::VerifyBlame` handler in `processor/src/key_gen.rs` invokes it as `.blame(accuser, accused, ...)`, passing the accuser as `sender` and the accused as `recipient`. Because the per-message Schnorr proof-of-possession binds the true sender's `Participant` index, the verification path deterministically resolves blame onto the accuser. This mirrors the reported bug class: a check that is satisfied by any protocol participant rather than binding the action/outcome to the correct specific party.

### Finding Description
The blame API is documented: the message is "a copy of the encrypted secret share from the accused sender to the accusing recipient" [1](#0-0) . Internally, `blame_internal` calls `decrypt_with_proof(sender, recipient, msg, proof)` [2](#0-1) , which verifies `msg.pop` against `pop_challenge(context, msg.pop.R, msg.key, from, ...)` where `from = sender` [3](#0-2) . At encryption time, the PoP challenge is computed with `from = self.i` — the actual sender's index [4](#0-3) .

In the `VerifyBlame` handler, the calls are:

```rust
.blame(accuser, accused, substrate_share, substrate_blame);
.blame(accuser, accused, network_share, network_blame);
``` [5](#0-4) 

So `sender = accuser`, `recipient = accused` — the reverse of the required `(accused, accuser)`. Consequences inside `blame_internal`:

1. `pop_challenge` is computed with `from = accuser`, but the message's PoP was signed binding `from = accused`. `msg.pop.verify` fails, yielding `DecryptionError::InvalidSignature`, and `blame_internal` returns `sender` — i.e., the **accuser** [6](#0-5) .
2. The handler then checks `if (substrate_blame == accused) || (network_blame == accused)` — which can now essentially never be true for a parseable share — and falls through to `ProcessorMessage::Blame { participant: accuser }` [7](#0-6) .

Even if the PoP somehow passed, `decrypt_with_proof` would verify the DLEq against `self.enc_keys[&decryptor]` = the **accused's** encryption key rather than the accuser's [8](#0-7) , so the proof path is doubly misbound.

Note the in-tree tests don't catch this: `test_blame` hardcodes `blame(ONE, TWO, ...)` while supplying messages with differing actual senders, and the assertion passes coincidentally because the PoP failure returns whatever was passed as `sender` [9](#0-8) .

### Impact Explanation
Per the code's own comment, reaching `VerifyBlame` means "someone is getting fatally slashed" [10](#0-9) . With swapped arguments:

- Any validator that honestly reports an invalid secret share (the entire purpose of the blame protocol) is itself blamed and fatally slashed.
- A malicious DKG participant can send a deliberately corrupt `EncryptedMessage` to a victim; when the victim raises blame, the victim is slashed and the attacker is exonerated — a griefing/slash-the-messenger attack reachable purely with protocol messages the attacker causes to be sent.

This inverts the security guarantee of the PedPoP blame mechanism and punishes honesty.

### Likelihood Explanation
Deterministic. The swap is unconditional: for any parseable share, the PoP check fails (challenge bound to accuser instead of sender), so `InvalidSignature` returns `sender = accuser`, and the handler emits `Blame { participant: accuser }` on every invocation. Any malicious participant can trigger it at will by sending an invalid share; any honest participant triggers it on themselves by reporting a fault. No collusion, timing, or privileged access required — just a normal DKG message.

### Recommendation
Swap the arguments in both calls so the share's sender is the accused:

```rust
.blame(accused, accuser, substrate_share, substrate_blame)
.blame(accused, accuser, network_share, network_blame)
```

Alternatively, rename `blame`'s parameters to `(accused, accuser, ...)` at the API level to prevent recurrence, and add a test asserting that a valid blame proof against a genuinely faulty sender resolves to the sender — the current `test_blame` helper masks argument-order bugs because the PoP failure coincidentally returns the asserted participant.

### Proof of Concept
1. Participants run PedPoP DKG; participant `A` (accused) sends participant `B` (accuser) an encrypted share that fails share verification (e.g., non-canonical scalar), exactly as in `invalid_share_serialization_blame` [11](#0-10) .
2. `B` produces an `InvalidShare` error with a valid `EncryptionKeyProof` (correct ECDH key and DLEq over `B`'s `enc_key` and `msg.key`) [12](#0-11) .
3. `VerifyBlame` is dispatched with `accuser = B`, `accused = A`. The handler calls `.blame(B, A, share, proof)` [13](#0-12) .
4. `decrypt_with_proof` computes `pop_challenge(..., from = B, ...)`; the PoP was signed binding `from = A`, so verification fails → `InvalidSignature` → `blame_internal` returns `B` [3](#0-2) .
5. `substrate_blame == B ≠ accused`, `network_blame == B ≠ accused`; handler returns `ProcessorMessage::Blame { participant: accuser }` — `B`, the honest reporter, is fatally slashed while `A` faces no penalty [7](#0-6) .

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };
