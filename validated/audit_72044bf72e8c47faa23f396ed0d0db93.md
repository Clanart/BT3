### Title
OAuth Sign-In State Never Expires, Allowing Delayed Replay of a Stale `x-github-client://oauth` Callback - ([File: app/src/lib/stores/sign-in-store.ts])

### Summary
The GlueX report's broken invariant is: a state-changing action (`swap()`) is missing a time-bound validity check, so it can be executed at an arbitrary point in the future after the conditions that justified it are gone. The closest reachable analog in GitHub Desktop is the OAuth browser sign-in flow: once `authenticateWithBrowser()` opens the external browser and stores a pending `oauthState` (with only a CSRF `state` token, no timestamp/expiry), `resolveOAuthRequest()`/`SignInStore.resolveOAuthRequest()` will accept and process any `x-github-client://oauth?code=...&state=...` deep link that matches that token no matter how much time has elapsed.

### Finding Description
`authenticateWithBrowser()` generates a `csrfToken` and stores it indefinitely in `this.state.oauthState.state` while waiting for the OS to invoke Desktop's custom protocol handler with the OAuth redirect: [1](#0-0) 

When the app later receives an `x-github-client://oauth` URL (via `app.on('open-url', ...)` on macOS or the `--protocol-launcher` command-line argument on Windows), it is parsed by `parseAppURL()` and dispatched without any freshness check: [2](#0-1) [3](#0-2) [4](#0-3) 

`resolveOAuthRequest()` only validates the `state` string equality; there is no timestamp captured when the OAuth flow started, and no deadline/expiry compared against `Date.now()` before honoring the callback: [5](#0-4) 

This mirrors the report's core flaw: the guard that exists (`state` matching, analogous to the swap's slippage/amount checks) is not accompanied by the deadline guard that the documented/expected security model requires. As long as `this.state.oauthState` remains populated (i.e., the user hasn't cancelled, or the app hasn't been restarted), a callback URL carrying the matching `state` and `code` can be replayed at any later time, "after market conditions have changed" in swap terms — here, after the user's session, network context, or intent has changed.

### Impact Explanation
If a stale (but still state-matching) callback URL is delivered to Desktop long after the user initiated sign-in — e.g., retained in browser history, shared/forwarded, cached by a corporate proxy/logging middlebox, or re-triggered by a malicious page that re-invokes the custom protocol handler with a previously observed URL — Desktop will attempt to complete the OAuth token exchange and bind the resulting account into the still-pending sign-in session. There is no local enforcement that the flow must complete within a bounded window, so the client entirely relies on the identity provider's own code-expiry as the sole time bound, with no defense-in-depth on the Desktop side. This exposes exfiltration/hijack of an in-progress authentication step and violates the expected "swap/sign-in must respect a deadline" invariant. The impact is comparable in nature to the finding's classification as high risk in principle (though the practical severity is dampened by GitHub's server-side OAuth code TTL, similar to how a chain's block time could bound abuse of a missing deadline check).

### Likelihood Explanation
Exploitation requires the attacker to obtain and replay a real `code`/`state` pair generated for a genuine, still-open sign-in session (e.g., via URL leakage through logs, shared links, or a lingering browser tab), and delivering it to the Desktop instance via the `x-github-client://` protocol handler — a path the app explicitly registers and processes without user interaction beyond the initial click. This does not require local/physical access, admin rights, or prior malware; it only requires that Desktop's local guard (`state` match) is satisfied and that the flow is still "pending" client-side, which the code allows indefinitely. The likelihood is nonetheless moderated by GitHub's server-side authorization code expiration, similar to how a swap deadline is nominally guarded by transaction-pool inclusion behavior even without an explicit check.

### Recommendation
Record a `createdAt` timestamp alongside `oauthState.state` when `authenticateWithBrowser()` initiates the flow, and enforce a bounded validity window in `resolveOAuthRequest()`:

```diff
 oauthState: {
   state: csrfToken,
   endpoint,
+  createdAt: Date.now(),
   onAuthCompleted: resolve,
   onAuthError: reject,
 },
```

```diff
 if (this.state.oauthState.state !== action.state) {
   ...
   return
 }
+
+if (Date.now() - this.state.oauthState.createdAt > OAUTH_STATE_TTL_MS) {
+  log.warn('OAuth callback received after the sign-in window expired')
+  this.state.oauthState.onAuthError(new Error('OAuth sign-in expired'))
+  return
+}
```

### Proof of Concept
1. User clicks "Continue With Browser" in Desktop, triggering `authenticateWithBrowser()`, which opens `getOAuthAuthorizationURL(endpoint, csrfToken)` in the system browser and stores `oauthState.state = csrfToken` with no expiry.
2. The browser redirects to `x-github-client://oauth?code=<CODE>&state=<csrfToken>`; suppose network conditions (proxy log, shared machine, forwarded link, browser history sync) let this exact URL be captured by a third party before the user's Desktop instance consumes it, or the user leaves the sign-in dialog open without completing it.
3. At an arbitrary later time, while the sign-in dialog/state is still pending in the app (`this.state.oauthState.state === csrfToken` unchanged), the captured URL is replayed to the app (e.g., via the registered protocol handler being invoked from another app/webpage).
4. `SignInStore.resolveOAuthRequest()` passes the `state` equality check with no time-bound validation and proceeds to `requestOAuthToken` / `fetchUser`, completing the sign-in as if it had just occurred. [5](#0-4) 

**Uncertainty**: I could not fully verify whether `_resolveOAuthRequest` in `app/src/lib/stores/app-store.ts` adds any additional timeout/session-binding logic beyond delegating to `SignInStore.resolveOAuthRequest`, since the file content around those matches wasn't retrievable in this session (index size limits). If a Devin session with full file access shows an existing deadline/session check there, this finding should be reassessed accordingly.

```typescript
  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
```
