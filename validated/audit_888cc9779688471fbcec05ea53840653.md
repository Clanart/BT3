### Title
Just-in-time dust-stake front-running of `queueNewRewards` allows disproportionate reward theft via unprotected `rewardPerTokenStored` formula - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2._provisionReward` (invoked from `queueNewRewards`) computes `rewardPerTokenStored += (_amountReward * 10**stakingTokenDecimals) / totalStaked()` using the live, instantaneous `totalStaked()` value with no virtual-liquidity floor, minimum stake duration, or time-weighted averaging. Because `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)` [1](#0-0) , an actor who stakes a trivial amount immediately before a large reward is queued, then withdraws right after, can claim a share of the reward vastly disproportionate to the time/capital they actually contributed.

### Finding Description
`_provisionReward` credits the entire `_amountReward` to `rewardPerTokenStored` in one lump sum at the moment `queueNewRewards` executes, using whatever `totalStaked()` happens to be at that exact block: [2](#0-1) 

`totalStaked()` and `balanceOf()` read live on-chain balances with no snapshotting or time-weighting: [3](#0-2) 

An attacker can deposit dust via `WombatPoolHelper.deposit()`/`depositFor()`, which calls `MasterMagpie.depositFor` to mint their receipt-token stake with no minimum amount or lockup: [4](#0-3) [5](#0-4) 

Then immediately withdraw and realize `getReward`/`earned` off the now-inflated `rewardPerTokenStored`, since `earned` uses only the current stored value minus the user's last-paid checkpoint, with no vesting or streaming over time: [6](#0-5) 

`queueNewRewards` on the pool's rewarder is restricted to `onlyManager` [7](#0-6) , but the manager role here is `WombatStaking`, and the *trigger* for reward flow is not always privileged: `WombatStaking.harvest(address _lpToken)` is `external` and gated only by `_onlyActivePool`, i.e. permissionless — any address (including the attacker) can call it via `WombatPoolHelper.harvest()`: [8](#0-7) 

Separately, `WombatStaking.vote()` (restricted to `bribeManager`, a privileged-but-not-malicious periodic actor) also calls `queueNewRewards` with bribe reward amounts that are not tied to the pool's own LP size: [9](#0-8) 

Mitigating factor: both `WombatStaking.deposit()` and `WombatStaking.withdraw()` call `_toMasterWomAndSendReward` (which harvests and queues WOM rewards) *before* modifying the LP/receipt-token stake for that call [10](#0-9) , [11](#0-10) . This closes the most direct version of the attack for WOM-emission rewards, because any change to `totalStaked()` forces a proportional harvest+queue at the *prior* balance first, so a large real accrual cannot sit "unharvested" while `totalStaked()` is simultaneously dust from the underlying LP's own emissions. However, this self-harvesting protection does not extend to the bribe/vote path, and the standalone permissionless `harvest()` function still lets an attacker choose the exact block to crystallize any as-yet-unqueued reward while controlling their own stake size, which remains an exploitable timing surface if `totalStaked()` is thin relative to a reward amount not strictly bound to that same LP position (e.g., bribe rewards, or externally seeded/donated reward tokens).

### Impact Explanation
If exploited, this results in direct theft of rewards from legitimate stakers: an attacker with 1 wei of stake can claim a share of `_amountReward` approaching 100% instead of their true time-weighted share, at the expense of whoever should have earned that yield. This matches the Immunefi "theft of unclaimed yield / direct theft of user funds" impact class.

### Likelihood Explanation
Feasibility depends heavily on the specific pool state at the time `queueNewRewards` fires:
- For the WOM-emission harvest path, the self-harvest-before-stake-change design in `deposit()`/`withdraw()` largely prevents a large real accrual from coinciding with dust `totalStaked()`, reducing practical severity for that path.
- For the bribe/vote path and any scenario where `queueNewRewards` amount is not strictly proportional to the pool's own current LP position (e.g., a newly registered/thin pool receiving a large bribe reward, or any manager topping up rewards while the pool is nearly empty), the attack is directly exploitable by an unprivileged actor who only needs to front-run a visible mempool transaction or call the permissionless `harvest()` at an opportunistic moment, requiring only dust capital.

### Recommendation
- Introduce a minimum-liquidity/virtual-share floor in `totalStaked()` or `_provisionReward` (similar to Uniswap V2's `MINIMUM_LIQUIDITY`) so a near-zero denominator cannot produce an outsized `rewardPerTokenStored` jump.
- Replace lump-sum crediting with time-based streaming/vesting of queued rewards (similar to Synthetix `StakingRewards`) so instantaneous stake at queue-time cannot capture rewards accrued before the stake existed.
- Add a minimum stake duration or per-block deposit/withdraw restriction (e.g., disallow claiming rewards on the same block as deposit) to prevent JIT-deposit/withdraw sandwiching of `queueNewRewards`.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2`/`BaseRewardPool`, `WombatStaking`, and `WombatPoolHelper` per `PoolHelperFactoryLib.createWombatPoolHelper` wiring, with the pool's `totalStaked()` starting at 0.
2. Have the reward manager (or a mocked `bribeManager`/`vote()` call) prepare a `queueNewRewards(largeAmount, rewardToken)` transaction but not yet mine it.
3. As the attacker, mint/acquire 1 wei of `depositToken`, call `WombatPoolHelper.deposit(1, 0)` to stake 1 wei of receipt token, ensuring this transaction is mined immediately before the manager's `queueNewRewards` transaction (simulate via ordering in the same test block).
4. Mine the manager's `queueNewRewards(largeAmount, rewardToken)` call; assert `rewardPerTokenStored` for `rewardToken` jumps to `largeAmount * 10**decimals / 1`.
5. As the attacker, call `MasterMagpie.withdraw(stakingToken, 1)` (or `WombatPoolHelper.withdraw`) with `getReward` invoked, and assert the attacker receives `reward ≈ largeAmount`, vastly exceeding any fair time-weighted share (which should be ~0 given they staked for a single block).
6. Assert conservation is broken: `attacker.claimedReward > attacker.stakeTimeWeightedShare * historicalRewards`, demonstrating other/future stakers are shortchanged relative to the `historicalRewards` accounting.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
