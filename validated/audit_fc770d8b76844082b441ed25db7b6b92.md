### Title
Expired subscriptions are not swept before FIFO eviction, allowing a live paid subscription to be evicted instead — `pallet-bandwidth::push_subscription` (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`Pallet::push_subscription` caps each `(app_chain, app)` bandwidth-allowance list at `MAX_SUBSCRIPTIONS` (1024) and, when full, evicts strictly by insertion order (`list.remove(0)`) without first sweeping already-expired entries. `BandwidthGate::try_consume` does sweep expired entries — but only for the `(source, app)` pair that happens to make a metered ISMP call, and only *when* that call occurs. Any third party can force `push_subscription` to run for an arbitrary `(app_chain, app)` pair by simply calling `purchase()` on any registered `BandwidthManager` and naming the victim's `app`/`chain` in the message body (sponsorship is explicitly by-design: "a buyer on Ethereum can credit an app on Base"). By filling the victim's bucket with cheap, short-duration subscriptions that expire but are never sept (because the victim app hasn't triggered a gate consume in between), an attacker can force eviction of the victim's oldest — but still live and non-expired — subscription, destroying bandwidth the victim already paid for.

### Finding Description
`push_subscription` in `modules/pallets/bandwidth/src/lib.rs`:
```rust
let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
    let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
        Some(list.remove(0))
    } else {
        None
    };
    let _ = list.try_push(new_sub);
    evicted
});
``` [1](#0-0) 

This mirrors the reported bug-class exactly: a stale/expired-item cleanup routine exists elsewhere in the system (`BandwidthGate::try_consume` sweeps `list.retain(|s| s.expires_at > now)` on every gate consumption) [2](#0-1)  but is never invoked from the insertion/eviction path, exactly analogous to `removeOldBids()` existing but never being called from `withdrawDeposit()`. Because `Allowance` is a `BoundedVec` keyed per `(app_chain, app)` and insertion order is purchase order (not expiry order), an entry with a long `duration_secs` purchased early can still be live while several entries purchased later with short `duration_secs` have already expired and are sitting unswept later in the same list. When the list is at the 1024 cap, the *next* push always evicts index 0 (the oldest by insertion), regardless of whether index 0 or any other entry is actually expired.

The purchase path (`on_accept`) is reachable by anyone who can call the corresponding `BandwidthManager.purchase()` on an EVM source chain; the `app_chain` and `app` fields of the `BandwidthPurchaseMsg` are attacker-controlled and explicitly documented as sponsorship-friendly (pay from any chain, credit any app on any chain): [3](#0-2) 

An attacker therefore does not need to be a relayer, prover, admin, or the app owner — an unprivileged caller who merely pays the (attacker-chosen, potentially minimal) tier price can drive the FIFO fill/evict logic for any victim `(app_chain, app)` pair.

### Impact Explanation
`SubscriptionEvicted` explicitly documents `lost_bytes` as "what the user paid for and won't get to use" [4](#0-3) . Because eviction ignores expiry, an attacker can engineer eviction of a victim's still-valid, paid-for allowance while dead (already-expired) entries remain occupying slots in the same bucket. This is a loss of a paid on-chain asset (bandwidth allowance) belonging to the rightful beneficiary (the victim app), caused directly by missing "sweep expired before evict" cleanup — the same broken invariant as the original report (missing `removeOldBids()`-style cleanup before an operation that depends on accurate live-state accounting).

### Likelihood Explanation
Reaching 1024 entries in a single victim bucket requires many purchase calls, but tier prices are governance-configured and can be arbitrarily small; nothing in the pallet enforces a minimum price or rate-limits purchases against a given `(app_chain, app)` key. An attacker who wants to grief a specific competing app (or extract value by forcing it to repurchase) only needs to fund enough cheap, short-duration purchases targeting that app's bucket. This is an economically-bounded but fully unprivileged, permissionless griefing/fund-loss path with no reliance on malicious relayers, provers, or admins.

### Recommendation
In `push_subscription`, before evicting on a full list, first sweep expired entries the same way `try_consume` does (`list.retain(|s| s.expires_at > now)`), and only evict the oldest *live* entry (or simply push into the freed space) if the list is still full after the sweep. This restores the same "remove stale accounting before it can distort a decision" invariant that `try_consume` already implements, closing the gap between the two paths — exactly the fix Reality Cards applied by reinstating the missing `removeOldBids()` call.

### Proof of Concept
1. Governance configures `TierLong` (`duration_secs` = 1 year) and `TierShort` (`duration_secs` = 1 second), both with nonzero price.
2. Victim app buys 1 unit of `TierLong` for `(app_chain, app)` → subscription `A` is inserted at index 0, live for a year.
3. Attacker (any address, any chain with a registered `BandwidthManager`) repeatedly calls `purchase()` targeting the same `(app_chain, app)`, buying `TierShort` 1023 times, filling the list to the 1024 cap. Each of these credits arrives via `on_accept` → `push_subscription`, which only checks `list.len() == MAX_SUBSCRIPTIONS`, never expiry.
4. Attacker waits >1 second so all 1023 `TierShort` entries are now expired but remain in storage (no gate consume has happened for this app in the interim to trigger the `try_consume` sweep).
5. Attacker (or anyone) submits one more cheap `TierShort` purchase. `push_subscription` sees `list.len() == 1024`, evicts `list[0]` = subscription `A` (still live, most of a year remaining), and emits `SubscriptionEvicted { lost_bytes: A.remaining_bytes }` — even though 1023 dead entries sit in the same list and could have been pruned first.
6. The victim app permanently loses its paid, non-expired bandwidth allowance, while the attacker has planted only expired garbage entries.

	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
