### Title
Direct donation of `stakingToken` to `MasterMagpie` corrupts `BaseRewardPool.totalStaked()`, permanently diluting/freezing unclaimed rewards - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.totalStaked()` does not track deposits through an internal accounting variable; instead it reads the live ERC20 balance of the staking (receipt) token held by `MasterMagpie` (the `operator`). Any unprivileged wallet can transfer the freely-transferable receipt token directly to the `MasterMagpie` contract, inflating this balance without crediting any user's stake in `MasterMagpie`'s internal `userInfo`/`stakingInfo` accounting. Because `_provisionReward` divides newly queued/donated rewards by `totalStaked()` to compute `rewardPerTokenStored`, this donation permanently dilutes the reward-per-token rate for all real stakers, causing a portion of every future reward distribution to become unclaimable — the exact "donation corrupts internal accounting and suppliers don't benefit / value gets deflated" bug class described in the report.

### Finding Description
`BaseRewardPool.totalStaked()` is defined as: [1](#0-0) 

This returns `IERC20(stakingToken).balanceOf(operator)`, i.e., the raw balance of the receipt token held by `MasterMagpie`, rather than a variable that is only mutated through the legitimate `_deposit`/`_withdraw` flow. `MasterMagpie._deposit` separately tracks `user.amount` in `userInfo[_stakingToken][_account]` and only pulls tokens via `safeTransferFrom` during an explicit deposit call: [2](#0-1) 

The `stakingToken` used by `WombatPoolHelper`/`WombatPoolHelperV2` pools is the receipt token minted by `WombatStaking` (`IMintableERC20`), which is a standard transferable ERC20 — any holder can freely `transfer()` it to `MasterMagpie` outside of the deposit flow, bypassing `userInfo` accounting entirely, similarly to how underlying tokens can be donated directly to Morpho's VaultV2 or its adapters' market positions in the analog report.

Whenever a manager calls `queueNewRewards` or anyone calls `donateRewards` on `BaseRewardPool`, the reward rate is computed as: [3](#0-2) 

`rewardPerTokenStored` is incremented by `(_amountReward * 10**stakingDecimals()) / this.totalStaked()`. If an attacker (or anyone) inflates `totalStaked()` via a direct donation of the receipt token to `MasterMagpie`, the denominator becomes larger than the sum of real stakers' `user.amount`, so the computed `rewardPerTokenStored` increment is smaller than it should be. The portion of the reward amount corresponding to the "phantom" donated balance is never attributed to any staker (no account's `balanceOf` — which is sourced from `MasterMagpie.stakingInfo`, not from the receipt-token balance — increases), yet those tokens have already been pulled into the reward pool via `safeTransferFrom` in `_provisionReward`. That fraction of every subsequently queued/donated reward becomes permanently stuck/unclaimable, since no user's `earned()` calculation can ever recover it (there is no mechanism to skim it back or correct `totalStaked()`).

This mirrors the Morpho VaultV2 report's finding "Suppliers do not directly benefit from the donated funds" / share-value deflation: the exact same root cause (an externally-controllable, non-gated balance used directly in accounting math driving value distributed to legitimate participants) exists here, just manifesting as reward-per-token dilution instead of vault share price dilution.

### Impact Explanation
Every time new rewards are queued/donated while a donation-inflated `totalStaked()` is in effect, a proportional fraction of that reward amount is permanently lost/unclaimable by any staker — it is neither returned to the donor nor claimable, and it persists for the pool's entire remaining lifetime because `totalStaked()` is derived live from balance and never resets down to real stake unless the donated tokens are later withdrawn from `MasterMagpie`'s balance (which cannot happen, since only `MasterMagpie`'s own withdraw logic can move that balance out, and it only ever moves out amounts up to accounted `user.amount`). This is a permanent freezing of unclaimed yield for legitimate stakers.

### Likelihood Explanation
The receipt token is a standard transferable ERC20 minted through normal `WombatStaking.deposit`/`depositLP` flows, so any wallet holding it (or acquiring a small amount) can trigger the issue with a single `transfer()` call to `MasterMagpie`, with no privileged role required. The dilution occurs automatically the next time `queueNewRewards`/`donateRewards` is called (a routine, expected operational event), making the negative side effect highly likely to manifest in practice.

### Recommendation
Replace `BaseRewardPool.totalStaked()`'s reliance on `IERC20(stakingToken).balanceOf(operator)` with an internally tracked total-staked accumulator that is only mutated by `MasterMagpie`'s `_deposit`/`_withdraw` functions (mirroring `userInfo[_stakingToken][_account].amount` aggregation), so that externally donated balances cannot influence `rewardPerToken` computations.

### Proof of Concept
1. Pool P has `stakingToken` = receipt token `R`, with real stakers holding a combined `user.amount` of 100 `R` recorded in `MasterMagpie`.
2. Attacker acquires 100 `R` (e.g., via normal deposit/withdraw cycles or market purchase) and calls `R.transfer(MasterMagpie, 100)` directly — no deposit call, so `userInfo` is untouched.
3. `BaseRewardPool.totalStaked()` now returns 200 (100 real + 100 donated) instead of 100.
4. A manager calls `queueNewRewards(1000e18, rewardToken)`; `_provisionReward` computes `rewardPerTokenStored += 1000e18 * 1e18 / 200` instead of the correct `1000e18 * 1e18 / 100`, halving the rate.
5. Real stakers' `earned()` amounts are computed using the diluted `rewardPerTokenStored`, so they collectively can only ever claim half of the queued 1000e18 reward; the other half remains in the contract with no corresponding claimable entitlement for any account. [1](#0-0) [3](#0-2) [2](#0-1)
