### Title
Unprivileged EVM address re-association permanently orphans staking funds and unbonding-queue entries - ([File: sei-cosmos/x/staking/keeper/delegation.go])

### Summary
Sei's dual-address model lets a user first accumulate stake/rewards under the deterministic "direct-cast" Sei address derived from their EVM address, and later call the `associatePubKey`/`Associate` EVM precompile to bind that same EVM address to a different, pubkey-derived "true" Sei address. Nothing in the association path checks whether the direct-cast address already has state (delegations, unbonding entries, validator operator role) that depends on it remaining receivable. Once re-associated, `CanAddressReceive`/`CanSendTo` permanently reject transfers to the orphaned direct-cast address, and — as demonstrated by the repo's own regression test — matured unbonding-delegation entries that fail this check are *dropped from the maturity queue while the underlying `UnbondingDelegation` and its escrowed tokens are left behind in the `NotBondedPool`*, with no other code path that revisits them. This mirrors the CVE-2017-15115 bug class: an operation that reassigns which "context" (netns / true Sei address) a resource belongs to, performed without checking that the resource's existing owner-context still matches, leaves state in a permanently inconsistent/unrecoverable position.

### Finding Description
- Address association is fully user/attacker controlled and reachable from a public EVM transaction: `precompiles/addr/addr.go` `associateAddresses` / `associatePublicKey`, or the ante-level auto-association in `x/evm/ante/preprocess.go` `AnteHandle`, call `helpers.AssociateAddresses` (utils/helpers/associate.go) which unconditionally calls `SetAddressMapping` to repoint the EVM↔Sei mapping. [1](#0-0) [2](#0-1) 
- The only existing safeguard is for EIP-7702 `SetCode` authorities (`AuthorityToPreAssociate` in `utils/helpers/address.go`), which blocks *only* the specific scenario where an authority hasn't been associated yet before delegation code is installed. It does not protect a user who has already delegated stake / created a validator under their direct-cast identity and later calls `associatePubKey` directly through the precompile. [3](#0-2) 
- Once the mapping changes, `CanAddressReceive` (`x/evm/keeper/address.go`) permanently returns `false` for the old direct-cast address because `GetSeiAddress(evmAddr)` now resolves to a different Sei address. [4](#0-3) 
- `bank.UndelegateCoins` (used both by immediate undelegation and by matured unbonding completion) checks `CanSendTo` and returns `ErrInvalidRecipient` if the recipient is unreceivable, instead of forcing the transfer. [5](#0-4) 
- `staking.Keeper.CompleteUnbonding` calls `UndelegateCoinsFromModuleToAccount` for each mature entry and returns an error immediately when that transfer fails, before removing/updating any further entries. [6](#0-5) 
- The repository's own test, `TestEndBlockRetainsUnbondingForInvalidRecipient`, proves the resulting behavior end-to-end: it re-associates an EVM address away from its direct-cast delegator address, matures an unbonding entry, and runs `staking.EndBlocker`. The result is that (a) the pool balance is unchanged (tokens stay locked in the not-bonded pool), (b) the `UnbondingDelegation` object is retained in the store, but (c) the maturity-queue iterator for that time is empty (`iterator.Valid()` is `false`) — i.e., the queue entry that would have driven a retry has already been consumed/removed by `EndBlocker` even though the underlying transfer never completed. [7](#0-6) 

Because the maturity-queue timeslice is gone but the `UnbondingDelegation` record and its locked coins remain, and there is no other scheduled job that re-scans "orphaned" `UnbondingDelegation` objects independent of the queue, the delegator's principal is permanently locked in the `NotBondedPool` module account with no on-chain path to reclaim it (short of a chain upgrade/migration).

### Impact Explanation
This causes **permanent freezing of user funds** (bonded/undelegated principal, and by the same mechanism, distribution commission/rewards routed via `GetDelegatorWithdrawAddr`, as separately shown by `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator`) with no recovery path, triggered entirely by an ordinary, unprivileged sequence of transactions (delegate/create-validator under the auto-derived address, then call the public `associatePubKey`/`Associate` precompile). This satisfies the "permanent freezing" impact bar in the validation rules. It does not itself corrupt consensus or crash nodes, but it is a concrete, reproducible loss-of-funds condition reachable by any EVM transaction sender.

### Likelihood Explanation
High likelihood: no privileged role is required. Any user can (1) delegate/create a validator using the implicit direct-cast Sei address before ever associating a pubkey (this is the default state for any address that has not yet transacted or associated), (2) undelegate to start the unbonding timer, then (3) call `associatePubKey` on the `addr` precompile to rebind their EVM address to a different true Sei address before the unbonding period matures. The precheck in `associateAddresses` only rejects re-association if the *target* Sei address is already associated — it does not check whether the *EVM address's current direct-cast identity* has pending delegations/unbondings/validator state. [8](#0-7) 

### Recommendation
Before allowing `SetAddressMapping` to repoint an EVM address away from its existing direct-cast Sei address, check for and block (or first drain/migrate) any outstanding state tied to the direct-cast address: non-zero delegations, pending `UnbondingDelegation`/`Redelegation` entries, and validator operator/self-delegation records — analogous to how `MigrateBalance` already handles plain bank balances and locked coins. Additionally, harden `CompleteUnbonding`/`staking.EndBlocker` (and the analogous distribution commission path) so that a failed transfer to an unreceivable recipient does not silently drop the maturity-queue entry; instead, either re-queue the entry for a later retry (e.g., after the recipient's address becomes receivable again) or route it to a recoverable holding account instead of leaving it permanently orphaned in the pool with no queue reference.

### Proof of Concept
1. Generate a fresh secp256k1 key; do not send any Cosmos/EVM tx from it yet, so it has no explicit association — its Sei identity is the direct-cast address `castAddr = sdk.AccAddress(evmAddr[:])`.
2. Fund `castAddr`, delegate to a validator (or self-delegate as a new validator operator) using `castAddr`/`valAddr = sdk.ValAddress(castAddr)`.
3. Submit `MsgUndelegate` (or trigger validator removal) to start an unbonding entry for `castAddr`.
4. Before the unbonding matures, call the `addr` precompile's `associatePubKey(pubkey)` (or sign any other Cosmos tx that trigger `AssociateAddresses`) to bind `evmAddr` to a new, different true Sei address. This calls `SetAddressMapping(ctx, newSeiAddr, evmAddr)`, so `GetSeiAddress(evmAddr)` now returns `newSeiAddr`, and `CanAddressReceive(castAddr)`/`CanSendTo(castAddr)` become permanently `false`.
5. Wait for the unbonding entry to mature and let `staking.EndBlocker` run. `CompleteUnbonding` attempts `UndelegateCoinsFromModuleToAccount(NotBondedPool, castAddr, amt)`, which fails `CanSendTo` and returns `ErrInvalidRecipient`; the `NotBondedPool` balance is unchanged, and the `UnbondingDelegation` record is retained, but the `UBDQueue` timeslice entry driving future retries is gone (exactly as asserted by `TestEndBlockRetainsUnbondingForInvalidRecipient`). [7](#0-6) 
6. The delegator's principal is now permanently stuck in the `NotBondedPool` account, unreachable by any subsequent transaction from `castAddr` or `newSeiAddr`.

	}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (k BaseKeeper) UndelegateCoins(ctx sdk.Context, moduleAccAddr, delegatorAddr sdk.AccAddress, amt sdk.Coins) error {
	moduleAcc := k.ak.GetAccount(ctx, moduleAccAddr)
	if moduleAcc == nil {
		return sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", moduleAccAddr)
	}

	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}
	if !k.CanSendTo(ctx, delegatorAddr) {
		return sdkerrors.ErrInvalidRecipient
	}

	err := k.SubUnlockedCoins(ctx, moduleAccAddr, amt, true)
	if err != nil {
		return err
	}

	if err := k.trackUndelegation(ctx, delegatorAddr, amt); err != nil {
		return sdkerrors.Wrap(err, "failed to track undelegation")
	}

	err = k.AddCoins(ctx, delegatorAddr, amt, true)
	if err != nil {
		return err
	}

	return nil
}

func TestEndBlockRetainsUnbondingForInvalidRecipient(t *testing.T) {
	_, app, ctx := createTestInput(t)
	maturity := time.Unix(1, 0).UTC()
	ctx = ctx.WithBlockTime(maturity)
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	delegator := sdk.AccAddress(evmAddr[:])
	app.EvmKeeper.SetAddressMapping(ctx, delegator, evmAddr)
	app.EvmKeeper.SetAddressMapping(
		ctx,
		sdk.AccAddress(common.HexToAddress("0x4444444444444444444444444444444444444444").Bytes()),
		evmAddr,
	)
	validator := sdk.ValAddress(seiapp.AddTestAddrsIncremental(app, ctx, 1, sdk.NewInt(10000))[0])
	amount := sdk.NewInt(40)
	bondDenom := app.StakingKeeper.BondDenom(ctx)
	notBondedPool := app.StakingKeeper.GetNotBondedPool(ctx)
	coins := sdk.NewCoins(sdk.NewCoin(bondDenom, amount))

	require.NoError(t, apptesting.FundModuleAccount(
		app.BankKeeper,
		ctx,
		notBondedPool.GetName(),
		coins,
	))

	unbonding := types.NewUnbondingDelegation(delegator, validator, 0, maturity, amount)
	app.StakingKeeper.SetUnbondingDelegation(ctx, unbonding)
	app.StakingKeeper.InsertUBDQueue(ctx, unbonding, maturity)
	require.False(t, app.BankKeeper.CanSendTo(ctx, delegator))

	poolBalanceBefore := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.NotPanics(t, func() {
		staking.EndBlocker(ctx, app.StakingKeeper)
	})

	poolBalanceAfter := app.BankKeeper.GetBalance(ctx, notBondedPool.GetAddress(), bondDenom)
	require.Equal(t, poolBalanceBefore, poolBalanceAfter)
	require.True(t, app.BankKeeper.GetBalance(ctx, delegator, bondDenom).IsZero())
	retained, found := app.StakingKeeper.GetUnbondingDelegation(ctx, delegator, validator)
	require.True(t, found)
	require.Equal(t, unbonding, retained)

	iterator := app.StakingKeeper.UBDQueueIterator(ctx, maturity)
	require.False(t, iterator.Valid())
	require.NoError(t, iterator.Close())
}
