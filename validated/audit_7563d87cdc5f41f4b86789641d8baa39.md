### Title
Marker-check bypass allows a stray `<<<<<<<` conflict marker to survive into the committed file - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The validation guard on a Copilot hunk's `resolvedContent` requires **both** a bare `<<<<<<<` line **and** a `=======` line to be present before it rejects the response. A resolved-content string that contains only an unpaired `<<<<<<<` marker (no `=======`) passes validation untouched and is later spliced verbatim into the reassembled file by `reassembleResolvedFile`, so the committed file ends up with a stray, unterminated conflict-marker line even though the resolution pipeline reported the file as fully resolved.

### Finding Description
`parseCopilotConflictResolution` validates each hunk's `resolvedContent` with: [1](#0-0) 

The two regexes are combined with `&&`, so rejection only fires when **both** an ours-marker line (`^<{7}\s`) and a separator line (`^={7}$`) are present anywhere in the string. A crafted `resolvedContent` such as `"<<<<<<< HEAD\nfoo"` satisfies `/^<{7}\s/m` but not `/^={7}$/m`, so the condition evaluates to `false` and no `CopilotValidationError` is thrown. The hunk is pushed into `validatedHunks` unchanged: [2](#0-1) 

This validated hunk then flows into `reassembleResolvedFile`, which only inspects the **original** `rawContent` lines to locate well-formed `<<<<<<<`/`=======`/`>>>>>>>` blocks to replace — it never re-scans the model's `resolved` string for embedded markers before splicing it in: [3](#0-2) 

So the literal text `<<<<<<< HEAD\nfoo` (with no matching `=======`/`>>>>>>>`) is written verbatim into `resultLines`, and ultimately into `resolvedContent` returned by `reassembleResolutions`, which becomes the file content the user is shown and can commit: [4](#0-3) 

### Impact Explanation
The reassembly pipeline is designed to guarantee that a "resolved" file is free of conflict markers — that is the entire purpose of the marker check at line 444 and the JSDoc contract of `reassembleResolvedFile`. Because the AND-based check can be defeated by an unpaired `<<<<<<<`, a Copilot response (an attacker-influenced/untrusted model output, since the model's output is effectively "remote response" content the app trusts to be marker-free) can silently inject a stray conflict-marker line into the file that the app presents as fully resolved and that the user may then commit and push. This is silent corruption of what the user commits: the committed file is not what it purports to be (conflict-free), and depending on file type this stray marker line can break syntax/behavior (e.g. in source files, lockfiles, or configuration), while the UI/dialog gives no indication a marker remains.

### Likelihood Explanation
This requires the Copilot model response itself to contain an unpaired `<<<<<<<`/no-separator hunk — a plausible model failure mode (e.g., partial/truncated generation, or the model echoing part of one side's diff without completing markers) rather than a scenario needing complex attacker control of remote infrastructure. Since Copilot output is not fully trusted (hence the existing marker-stripping check), this is a realistic gap in that defense rather than a purely theoretical one.

### Recommendation
Change the guard from an AND to an OR (or check for either marker independently), e.g. reject when `/^<{7}(?:\s|$)/m.test(rc) || /^={7}$/m.test(rc) || /^>{7}(?:\s|$)/m.test(rc)`, so that any single stray marker line (ours, separator, or theirs) causes the hunk to be rejected rather than requiring the full pair. Consider also re-validating the fully reassembled `resolvedContent` in `reassembleResolutions`/`reassembleResolvedFile` for any residual marker lines before returning it, as a defense-in-depth backstop independent of the per-hunk parse-time check.

### Proof of Concept
1. Craft a Copilot JSON response where one hunk's `resolvedContent` is `"<<<<<<< HEAD\nfoo"` (no `=======` or `>>>>>>>`).
2. Feed it through `parseCopilotConflictResolution` — the check at [5](#0-4)  evaluates `true && false = false`, so no `CopilotValidationError` is thrown, and the hunk is accepted as-is.
3. Call `reassembleResolutions`/`reassembleResolvedFile` with this hunk against a file containing a real, well-formed conflict block at that position — the splice logic at [6](#0-5)  inserts `"<<<<<<< HEAD"` and `"foo"` verbatim into `resultLines`.
4. Inspect the returned `resolvedContent` (used for `IFileResolution.resolvedContent`, ultimately written to disk/committed) — it contains the stray `<<<<<<< HEAD` line despite the resolution being reported as complete.
