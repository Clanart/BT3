### Title
Line-selection indices from a stale rendered diff are re-applied to a freshly re-fetched diff when staging partial commits, silently committing different content than the user selected - ([File: app/src/lib/git/apply.ts])

### Summary
`DiffSelection` (`app/src/models/diff/diff-selection.ts:122-136`) is a pure index-based bitset: `isSelected(lineIndex)` only knows "line N in whatever diff produced these hunk offsets is selected/deselected". It carries no content hash, blob OID, or timestamp binding it to the specific diff it was computed against. When the user commits a partial selection, `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) does **not** reuse the diff the user reviewed in the UI. Instead it calls `getWorkingDirectoryDiff(repository, file)` again, fetching a brand-new diff of the file's *current* on-disk contents, and then feeds that new diff plus the old (UI-rendered) `file.selection` straight into `formatPatch` (`app/src/lib/patch-formatter.ts:129`), which walks the new diff's hunks and calls `file.selection.isSelected(absoluteIndex)` for each line using the new hunk's `unifiedDiffStart` offsets.

### Finding Description
This is the analog of the Morpho bug: a value (the P2P mid-rate / here, the diff-line indices) is computed once and cached in application state ("lazy snapshot"), but the state-changing action (P2P rate freeze / here, `git apply --cached`) trusts a freshly recomputed live value (Aave pool utilization / here, the current working-directory diff) without re-validating that the cached selection still corresponds 1:1 to that live value.

Concretely:
- `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3714`) takes `state.changesState.workingDirectory.files`, i.e. the `WorkingDirectoryFileChange` objects (and their `DiffSelection`) that were computed the last time the UI rendered the diff — this can be arbitrarily stale relative to the current file content.
- These files are passed to `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`), which for any file with `DiffSelectionType.Partial` calls `applyPatchToIndex`.
- `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` against the file on disk **at commit time**, producing a diff whose hunk boundaries/offsets can differ from the diff that was on screen when the user selected lines (`app/src/lib/git/apply.ts:60`).
- `formatPatch` then maps the *old* selection indices onto the *new* hunk structure (`app/src/lib/patch-formatter.ts:143-206`), with no verification that hunk count, `unifiedDiffStart`, or line content match what the user actually selected.

If a repository the user has cloned/fetched contains a Git hook (e.g. `post-checkout`, `pre-commit`, a file-system watcher script, a build tool triggered by opening the repo in Desktop, or any process an attacker can get to run in that working tree) that rewrites the file between the moment the diff is rendered and the moment the user clicks "Commit", the attacker fully controls what content ends up between the "selected" and "unselected" hunks in the newly-fetched diff. The user's selection indices (computed from the old, reviewed diff) get silently reinterpreted against the attacker-modified diff, so lines the user never reviewed or explicitly deselected can be staged and committed (or vice versa — reviewed/selected lines silently dropped).

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes," an explicitly valid impact category. A user could review a partial diff, deselect a malicious or unwanted hunk, and unknowingly commit and push it anyway (or the reverse: an intended fix line gets dropped), because the commit-time patch generation is built from a re-fetched diff rather than the one the user actually saw and interacted with.

### Likelihood Explanation
The attacker needs only to control content inside a repository the victim has opened in Desktop (a cloned/fetched repo, satisfying the "attacker controls a cloned/fetched repository" criterion) and a mechanism that mutates a tracked file between UI diff render and the user pressing "Commit" (e.g., a Git hook or watched build script that runs on file save/checkout — a normal, unprivileged repo behavior, not requiring local/physical access, admin rights, or pre-existing host malware). Given Desktop's asynchronous diff loading and no re-fetch/validation immediately before `git apply --cached` is invoked, the race window is real, though its exact width depends on how quickly the attacker-controlled process can rewrite the file relative to user interaction — this timing dependency is the main source of uncertainty in exploitability, and I could not fully verify from the index alone how large this window typically is in practice (would require running the app in a test session against a hook-mutating fixture repo to measure).

### Recommendation
Bind a `DiffSelection` to the specific diff it was computed from (e.g., a hash of the diff text, or the `unifiedDiffStart`/line-content pairs) instead of raw hunk-offset indices. Before calling `git apply --cached` in `applyPatchToIndex`, re-verify that the newly fetched diff is structurally/content-identical to the diff that produced the current `file.selection`; if it differs, abort the partial-stage operation and force the UI to re-render the diff and require the user to re-confirm their selection rather than silently reapplying stale indices to new hunks.

### Proof of Concept
Not independently executed against a live Desktop build; the sequence below is derived from the code paths cited above:
1. Clone an attacker-supplied repository containing a `post-checkout`/file-watcher hook that appends/reorders lines in `tracked-file.md` shortly after it is modified.
2. In Desktop, modify `tracked-file.md`, open the Changes diff, and select only specific lines/hunks for commit (`DiffSelectionType.Partial`), leaving other hunks unselected.
3. Before clicking "Commit," the hook fires and mutates `tracked-file.md`'s hunk layout.
4. Click "Commit." `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now different from what was rendered) and applies the stale selection indices via `formatPatch`, producing a commit whose content does not match what the user selected in the UI. export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
