### Title
Hardcoded zero slippage protection in `ArbWomUp3._deposit` (mode 2) enables MEV sandwich extraction on WOM→mWom conversion - (File: `wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3.incentiveDeposit` lets any unprivileged wallet deposit WOM into the incentive program. For `_mode == 2`, half of the deposit is routed through `SmartWomConvert.convert(...)`, which performs a real AMM swap (WOM→mWom via `womMWomPool`) to fulfil the "buyback" portion of the conversion. `ArbWomUp3` hardcodes the `_minRec` parameter of this call to `0`, meaning the user is given no ability to protect the AMM-swap-derived portion of their own deposit from price manipulation, exactly the missing-slippage-protection pattern described in the external report (there for `redeemEarlyLv`, here for the incentive deposit's internal swap).

### Finding Description
`incentiveDeposit` is unprivileged/user-callable and forwards to `_deposit`: [1](#0-0) 

For `_mode == 2`, half the WOM is deposited 1:1 into `mWom`, and the other half is sent through the converter with the minimum-received parameter hardcoded to `0`: [2](#0-1) 

Inside `SmartWomConvert._convertFor`, that `_minRec` is the *only* protection over the AMM swap output; the swap call itself is issued with `amountOutMin = 0` and relies entirely on the post-hoc `_minRec` check to catch bad pricing: [3](#0-2) 

Because `ArbWomUp3` always passes `_minRec = 0` for this call (`IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`), the check `convertAmount + amountRec < _minRec` at `wombat/SmartWomConvert.sol#L204` can never revert, no matter how unfavorable the swap execution price is. The user has no parameter in `incentiveDeposit` to set a real minimum, so the swapped half of their deposit is fully exposed to sandwich/MEV manipulation of the `womMWomPool` before the resulting (reduced) `mWom` is locked into `mWomSV` on the user's behalf.

### Impact Explanation
An MEV actor can front-run a user's `incentiveDeposit(_amount, _convertRatio, false/true, 2)` call by moving the WOM/mWom pool price, letting the victim's swap execute at a worse rate, then back-run to restore the price and capture the difference. The victim ends up with fewer `mWom` locked than the fair-market amount would have produced, and additionally the reward tier / MGP bonus calculations in `ArbWomUp3` depend on locked amounts, so the loss compounds into reduced incentive rewards. This is a direct value extraction from an unprivileged user's own transaction with no way to opt out, matching the "theft of user funds via MEV/sandwich" impact class.

### Likelihood Explanation
`incentiveDeposit` is a normal user-facing entry point requiring no special privileges, and mode 2 is a documented/intended usage path (locking mWom via `mWomSV`). Any attacker monitoring the mempool for `incentiveDeposit(..., _mode=2)` calls can execute a standard sandwich attack against the underlying `IWombatRouter.swapExactTokensForTokens` call, which is a well-understood and cheap MEV technique, making exploitation straightforward and repeatable for every mode-2 deposit.

### Recommendation
1. Add a user-supplied minimum-received parameter to `incentiveDeposit`/`_deposit` and thread it through to `IConverter(smartWomConvert).convert(...)` instead of hardcoding `0`.
2. Alternatively, fix the underlying `SmartWomConvert._convertFor` to accept and enforce a caller-supplied `amountOutMin` directly on the AMM swap call (`wombat/SmartWomConvert.sol#L194-196`) rather than only checking the aggregate `convertAmount + amountRec` after the fact with an easily-bypassed zero minimum.

### Proof of Concept
1. Attacker observes a pending `incentiveDeposit(amount, convertRatio, bullMode, 2)` transaction in the mempool.
2. Attacker front-runs by swapping WOM→mWom (or the reverse) on `womMWomPool` to skew the price unfavorably for the upcoming swap.
3. Victim's transaction executes `_deposit` → `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` → `SmartWomConvert._convertFor`, which calls `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` at `wombat/SmartWomConvert.sol#L194-196` — no protection against the manipulated price, and the subsequent check `convertAmount + amountRec < _minRec` never trips because `_minRec == 0`.
4. Attacker back-runs to restore the pool price, pocketing the spread extracted from the victim's swap.
5. Victim's `mWomSV.lockFor` locks a reduced `mWom` amount, permanently reducing the value the victim receives for their WOM deposit.
