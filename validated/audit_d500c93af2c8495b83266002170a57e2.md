## Title
Fee-on-Transfer / Deflationary Token Escrow Over-Crediting in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` credits order escrow using the *nominal* order amount (minus protocol fee) instead of the token amount actually received by the contract. When the input token charges a transfer fee or otherwise delivers fewer tokens than requested (the same "inflationary/deflationary ERC20" bug class from the external report), the contract's internal ledger (`_orders[commitment][token]`) becomes inflated relative to its real token balance, breaking bridge-custody solvency across orders sharing that token.

### Finding Description
In the mainline EVM `IntentGatewayV2.sol`, `placeOrder` explicitly snapshots balances before and after the `transferFrom` and uses the *actual delta* to determine escrow: [1](#0-0) 

This is validated by the repo's own fee-on-transfer regression tests confirming escrow must equal the actually received amount: [2](#0-1) 

However, the Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not perform this balance measurement in the non-predispatch escrow path. It simply calls `safeTransferFrom` for the nominal `order.inputs[i].amount` and then credits `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived purely from the nominal input amount minus the protocol fee — never from the tokens actually received: [3](#0-2) 

`reducedInputs[i].amount` is computed earlier straight from `order.inputs[i].amount`: [4](#0-3) 

If the input `token` charges any transfer fee (deflationary), the gateway's actual token balance increases by less than `reducedInputs[i].amount`, yet the escrow ledger records the full nominal (pre-fee) value. This is a direct bookkeeping mismatch, exactly the invariant the external report warns about: "the bridge contract was not designed for tokens that can... transfer an unexpected number of tokens."

The corrupted value is the escrow map `_orders[commitment][token]`, which now overstates the gateway's real, redeemable balance of `token`.

### Impact Explanation
The withdrawal path (`withdraw`) trusts this ledger unconditionally and transfers out the recorded `amount` without re-checking actual contract balance: [5](#0-4) 

Because `_orders[commitment][token]` is a per-commitment slot but the underlying ERC20 balance is a single shared pool for all orders using that token, an escrow shortfall from one deflationary-token order depletes the shared pool available to *other* unrelated orders using the same token. Whichever withdrawal (fill or refund/cancel) executes later can revert due to insufficient contract balance — locking a legitimate user's funds — or, if timed adversarially, a user/solver can front-run to drain the shared pool at another order's expense. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories via unauthorized manipulation of custody accounting, not merely a testnet quirk.

### Likelihood Explanation
Exploitability requires only that the input token used in `placeOrder` charges a transfer fee (or otherwise delivers less than the nominal `transferFrom` amount) — a property of the token contract, not a malicious relayer, prover, or admin. Any ordinary unprivileged user placing an order with such a token triggers the mismatch; no elevated capability or compromised participant is needed, satisfying the "public unprivileged entrypoint" requirement.

### Recommendation
Mirror the mainline EVM logic in the Tron contract: measure `balanceOf(address(this))` before and after each `safeTransferFrom` in `placeOrder` (both predispatch and non-predispatch branches), and credit `_orders[commitment][token]` using the *actual received delta* (after applying protocol fee proportionally to what was actually received), consistent with the pattern already implemented and tested in `evm/src/apps/IntentGatewayV2.sol` and `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee, following the `FeeOnTransferToken` test contract pattern already in the repo: [6](#0-5) ) on the Tron-targeted `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0].amount = 1000` of the fee token. Gateway actually receives `990`, but `_orders[commitmentA][token] = 1000` (assuming zero protocol fee) is recorded — line 457 of `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. User B similarly places an order with the same token for `1000`; gateway again only receives `990`, but the ledger records `1000` for `commitmentB` as well.
4. Total ledger claims: `2000`; actual contract token balance: `1980`.
5. When both orders are filled/withdrawn via `withdraw`, the first withdrawal succeeds, but the second `token.call(transfer(...))` for the remaining `1000` reverts (`TransferFailed`) because only `980` remains in the contract — demonstrating direct fund lock/loss for the second beneficiary caused purely by the ledger overstatement.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
