### Title
Repeated DKG confirmation key submissions reuse a cached nonce, leaking the validator’s MuSig secret share - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`DkgConfirmer` caches a deterministic FROST preprocess under only `(b"DkgConfirmer", attempt)` and reconstructs a signing machine from it every time a key pair is processed, without marking the preprocess consumed. [1](#0-0)  Repeated `GeneratedKeyPair` messages with distinct `KeyPair` values therefore produce multiple shares derived from the same cached nonce scalars while signing different `set_keys_message` values. [2](#0-1) 

### Finding Description
`SigningProtocol::preprocess_internal` stores the generated `CachedPreprocess` if no value exists for the context, but subsequent calls reload the same seed and pass it to `AlgorithmSignMachine::from_cache`. [1](#0-0)  The context used for DKG confirmation contains only the static label and attempt number, so multiple submissions for the same attempt all use the same nonce-generating seed. [3](#0-2) 

`generated_key_pair` writes the supplied `KeyPair` into `DkgKeyPair` and immediately requests a share for it, with no check that a key pair or share was already processed for that attempt. [4](#0-3)  The coordinator accepts each processor `GeneratedKeyPair` message and publishes the returned share in a `Transaction::DkgConfirmed`. [5](#0-4) 

The loaded seed deterministically regenerates both FROST nonce scalars through `seeded_preprocess`, while the attacker-visible message changes the public binding factor and Schnorr challenge. [6](#0-5)  Each returned share has the form `s_j = d + rho_j*e + c_j*x_i`, where `d` and `e` stay fixed, `rho_j` is publicly computable, and `x_i` is the interpolated secret share. [7](#0-6)  Three distinct signed key-pair messages provide three equations that solve for `d`, `e`, and `x_i`; because MuSig stores the validator private key as the un-interpolated secret share and applies only public binding factors, the validator key can be recovered from `x_i`. [8](#0-7) [9](#0-8) 

### Impact Explanation
The disclosed value is not merely a FROST share for one attempted message: after reversing the public MuSig binding factor, it reveals the validator’s Ristretto secret used to authorize DKG confirmation signatures. [8](#0-7)  Possession of that secret lets the attacker produce validator-equivalent signing contributions beyond the originally authorized confirmation, matching the privilege-escalation class of a lower-trust input path causing an operation outside its intended authority. [5](#0-4) 

### Likelihood Explanation
No participant needs to break the BFT layer or alter committed preprocesses: the same stored `ConfirmationNonces` can be reused while only the submitted `KeyPair`, and therefore the signed message, changes. [10](#0-9)  The missing consumed/already-generated guard makes repetition possible on the ordinary processor-message path, and three repetitions are sufficient for algebraic recovery when the resulting linear system is independent. [5](#0-4) 

### Recommendation
Persist a one-time marker for each `(attempt, key_pair)` signing operation and atomically consume `CachedPreprocesses` before producing a share. [1](#0-0)  Also reject a second `GeneratedKeyPair` for an attempt when `DkgKeyPair` already exists, rather than overwriting `DkgKeyPair` and `KeyToDkgAttempt`. [4](#0-3)  The cache entry should additionally be bound to the participant set and committed message/preprocess transcript before signing. [11](#0-10) 

### Proof of Concept
For a fixed attempt `A` and fixed committed `ConfirmationNonces`, submit three otherwise-valid `ProcessorMessage::GeneratedKeyPair` calls with distinct `KeyPair` values `K1`, `K2`, and `K3`. [12](#0-11)  Each call invokes `share(preprocesses, Kj)`, which rebuilds the machine from the same `(b"DkgConfirmer", A)` cache and signs `set_keys_message(..., Kj)`. [2](#0-1) 

Let the publicly emitted shares be `s1`, `s2`, and `s3`. [13](#0-12)  From the fixed public preprocess set and each signed message, calculate the participant’s public binding factors `rho1`, `rho2`, `rho3` and Schnorr challenges `c1`, `c2`, `c3`. [14](#0-13)  Solve:

```text
s1 = d + rho1*e + c1*x
s2 = d + rho2*e + c2*x
s3 = d + rho3*e + c3*x
```

The same `d` and `e` are reused because both are regenerated from the unchanged cached seed. [6](#0-5)  The recovered `x` is the validator’s interpolated signing share; dividing it by its public MuSig interpolation factor recovers the validator private key. [9](#0-8) [8](#0-7)
