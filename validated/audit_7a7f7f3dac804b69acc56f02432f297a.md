### Title
Missing access control on `WombatStaking.convertWOM` allows any EOA to force-lock the contract's idle WOM into a 4-year veWOM position, desynchronizing `mWOM.totalAccumulated` from actual locked backing - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.convertWOM(uint256 _amount)` is `external` and gated only by `whenNotPaused`, with no restriction to `mWOM` or `smartWomConverter` as the intended callers. Any unprivileged address can call it directly whenever `WombatStaking` transiently holds WOM (e.g., harvested fees, dust, or WOM en route to a designated `isMWOM` fee split), forcing that WOM into a 1461-day veWOM lock at a time of the attacker's choosing, while the accounting increment `mWOM.totalAccumulated += mintedVeWomAmount` — which only happens inside `mWOM._lockWom` — never occurs.

### Finding Description
`convertWOM` performs the actual lock with no caller check: [1](#0-0) 

The only place that increments `mWOM.totalAccumulated` is `mWOM._lockWom`, which itself calls `IWombatStaking(wombatStaking).convertWOM(_amount)`: [2](#0-1) 

Because `convertWOM` has no `onlyMWom`/`onlySmartWomConvert`-style modifier, the bookkeeping increment in `mWOM.totalAccumulated` is entirely bypassable: an attacker who calls `WombatStaking.convertWOM(_amount)` directly consumes whatever WOM balance `WombatStaking` is holding at that instant (`IERC20(wom).safeApprove(veWom, _amount); IVeWom(veWom).mint(_amount, lockDays)`), converting it into veWOM credited to `WombatStaking`, without ever routing through `mWOM._lockWom`. This is exploitable specifically in windows where `WombatStaking` holds WOM balance not yet consumed by the atomic mWOM `_convert`/`_lockWom` sequence — such as WOM harvested from Wombat and awaiting fee-split distribution (`Fees` entries with `isMWOM = true`) or any residual/dust WOM balance.

Note: within `mWOM.convert()`/`convertAndStake()`/`lockAllWom()`, the transfer of WOM to `WombatStaking` and the subsequent call to `convertWOM` happen atomically in the same transaction (`_convert` and `_lockWom`), so front-running the exact "victim deposit" mid-transaction is not possible. The real attack surface is any WOM balance that sits in `WombatStaking` outside of that atomic call — the audit prompt's premise that WOM held "mid-harvest before fee distribution" can be grabbed is consistent with the lack of caller restriction on `convertWOM`, though the exact harvest/fee-distribution mechanics (`_toMasterWomAndSendReward`) could not be fully traced in this review due to tool/iteration limits, so the precise conditions under which such idle WOM accumulates are not fully confirmed.

### Impact Explanation
The resulting veWOM is minted to `WombatStaking` itself, not to the attacker — so this is not a direct theft of funds. The concrete impacts are:
1. **Permanent freezing of protocol funds beyond 24h**: any idle WOM balance in `WombatStaking` can be locked into a 1461-day veWOM position at a time chosen by an unprivileged attacker, rather than at the time/amount intended by the legitimate flow (`mWOM.lockAllWom` or fee distribution). This matches the "funds frozen at least 24 hours" impact class.
2. **Accounting desync**: `mWOM.totalAccumulated` (the only ledger tracking veWOM attributable to mWOM's backing) will not reflect veWOM created this way, since the increment lives solely in `mWOM._lockWom`. If the diverted WOM was WOM designated for mWOM's fee share, mWOM's internal bookkeeping will under-report actual veWOM locked on its behalf.

### Likelihood Explanation
Exploitability requires no special privileges — any EOA can call `convertWOM` — but it is conditioned on `WombatStaking` transiently holding a nonzero WOM balance outside of the atomic `mWOM._convert`/`_lockWom` call sequence. This precondition (idle WOM sitting in `WombatStaking`, e.g. from harvest before fee distribution) could not be fully verified in this pass because the fee-distribution/harvest internals (`_toMasterWomAndSendReward`) were not completely traced.

### Recommendation
Add an access-control modifier to `convertWOM` restricting callers to `mWOM` and `smartWomConverter` (the only intended callers), e.g. `onlyMWom` / `onlySmartWomConvert`, so arbitrary EOAs cannot trigger locking of the contract's WOM balance.

### Proof of Concept
Foundry fork test plan:
1. Deploy/fork `WombatStaking`, `veWom`, and `mWOM` with real addresses.
2. Fund `WombatStaking` with idle WOM (simulate harvested/pending fee WOM) via `deal`/`transfer`.
3. From an unrelated EOA (no privileged role), call `wombatStaking.convertWOM(amount)` directly.
4. Assert: `IERC20(veWom).balanceOf(address(wombatStaking))` increases by the minted veWOM amount, while `mWOM.totalAccumulated()` remains unchanged — demonstrating the bypass of `mWOM`'s bookkeeping via the unrestricted `convertWOM` entrypoint.

```text
    /// @notice convert WOM to mWOM
    /// @param _amount the number of WOM to convert
    /// @dev the WOM must already be in the contract
    function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
        uint256 veWomMintedAmount = 0;
        if (_amount > 0) {
            IERC20(wom).safeApprove(veWom, _amount);
            veWomMintedAmount = IVeWom(veWom).mint(_amount, lockDays);
        }

        emit WomLocked(_amount, lockDays, veWomMintedAmount);

        return veWomMintedAmount;
    }
```

```text
        if (_needSend)
            IERC20(wom).safeTransfer(wombatStaking, _amount);

        uint256 mintedVeWomAmount = IWombatStaking(wombatStaking).convertWOM(_amount);
        totalAccumulated = totalAccumulated + mintedVeWomAmount;
```
