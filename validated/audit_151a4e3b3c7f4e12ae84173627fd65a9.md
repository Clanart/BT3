### Title
stSTXbtc / zstSTXbtc collateral is priced with the STX/USD Pyth feed instead of a feed reflecting its actual (BTC-yield) value - (File: `mainnet/contracts/proposals/mainnet/v0-init.clar`, `mainnet/contracts/utility/v0-1-data.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `stSTXbtc` asset (aid `u10`) and its vault receipt token `zstSTXbtc` (aid `u11`, callcode `CALLCODE-ZSTSTXBTC = 0x06`) are registered with the **STX/USD Pyth feed** (`STX-FEED-ID`) as their oracle identifier, and no callcode ratio transformation is applied to convert that STX price into the token's actual economic value. Every other yield-bearing/derivative asset in the registry (`stSTX`, `zstSTX`) applies a dedicated ratio transformation (`resolve-ststx` / `CALLCODE-STSTX`) to convert the base feed price into the derivative's real value, but `stSTXbtc` — despite being described in the codebase itself as "Liquid staked STX (BTC yield)" / "BTC-denominated yield" — is priced as if 1 stSTXbtc == 1 STX.

### Finding Description
Asset registration for `stSTXbtc`/`zstSTXbtc` hardcodes the STX feed with no transformation: [1](#0-0) 

The read-model helper `get-asset-price` mirrors this: it explicitly comments the asset as "BTC price (liquid staked STX with BTC yield)" yet calls `get-pyth-price PYTH-STX`, not a BTC feed or a proper conversion ratio: [2](#0-1) 

Compare this to the correctly-handled `stSTX` case in the same function, which multiplies the STX price by a dedicated `get-ststx-ratio` conversion before use: [3](#0-2) 

In the live pricing path (`v0-4-market.clar`), the callcode dispatcher for `CALLCODE-ZSTSTXBTC` also just forwards the raw resolved price (the STX price) into `resolve-ztoken` without any ratio step, unlike `CALLCODE-ZSTSTX`, which explicitly calls `resolve-ststx` first: [4](#0-3) 

This is the callcode transformation table and its supporting constants, showing `CALLCODE-ZSTSTXBTC` has no analog to `CALLCODE-STSTX`'s ratio step: [5](#0-4) 

The `local-testing` (identical logic, mirrored deployment) versions confirm the same configuration was intentionally and consistently written twice, not a one-off typo: [6](#0-5) [7](#0-6) 

Root cause: the pricing/callcode logic that maps an asset's oracle-resolved value to its true economic price omits a needed conversion step for `stSTXbtc`, causing the market to value BTC-yield-denominated collateral entirely in terms of the STX/USD price. This is analogous to the reported bug class of "a price attached to the wrong asset" — the oracle data used to price the asset does not correspond to the asset's actual value driver.

### Impact Explanation
`stSTXbtc`/`zstSTXbtc` is accepted as collateral (`zstSTXbtc` enabled for collateral per the init script) and is used directly in `get-notional-evaluation`/`sum-collateral-usd` to compute a user's collateral USD value, which drives max-borrowable amount, health factor, and liquidation eligibility. Because the collateral is valued using the STX/USD price (a few dollars) instead of a value tracking BTC (tens of thousands of dollars) or its true index rate, the USD valuation of this collateral will be systematically and dramatically wrong versus its real backing value:
- If the true value of `stSTXbtc` is materially higher than the STX price used, deposited collateral is undervalued — freezing the ability of legitimate holders to borrow against its actual worth (temporary freezing of funds).
- If, through the ratio drift/relationship between STX and the token's real backing, the STX price ever exceeds the token's true value, users could deposit low-worth `stSTXbtc` and borrow against an inflated USD valuation, extracting more value in other assets than their collateral is worth, leaving the protocol with unrecoverable bad debt (direct theft of protocol funds / insolvency).

Given the ambiguity in exact price relationship without being able to inspect the deployed `ststxbtc-token-v2` mechanics further, the safe classification is: **High** — temporary freezing of user collateral value/borrowing capacity due to systematically wrong price attached to the asset; with potential to escalate to **Critical** (protocol insolvency) if the mispricing ever favors the borrower's side.

### Likelihood Explanation
This is not a rare edge case — every single price read for `stSTXbtc` or `zstSTXbtc` collateral, on every borrow, withdraw, liquidation, and health-factor computation, uses this mis-attributed feed. It requires no attacker action beyond normal usage of the already-supported collateral type; the bug is deterministic and always triggers whenever this asset is priced.

### Recommendation
Apply a proper conversion for `stSTXbtc` analogous to `resolve-ststx`/`CALLCODE-STSTX`: either register `stSTXbtc` with a Pyth/DIA feed that actually tracks its economic value, or add a dedicated callcode/ratio resolver (mirroring the `stSTX` pattern) that converts the raw oracle price into the token's true backing value before it is used in `resolve-callcode`/`get-asset-price`. Update `v0-init.clar` (and its `local-testing` mirror) accordingly, and add tests asserting `stSTXbtc` valuation tracks its actual redemption/backing rate rather than the STX/USD price.

2. Call `market.collateral-add` depositing `stSTXbtc`/`zstSTXbtc` as collateral.
3. Observe via `get-user-position` / `get-asset-price` (`v0-1-data.clar:588-594`) that the reported USD value of the deposited collateral equals `stSTXbtc_amount * STX_USD_price / 10^decimals` (adjusted by liquidity index for the ztoken) — i.e., completely decoupled from the token's actual backing value.
4. Compare this reported USD valuation against the token's real redemption/market value (e.g., via its underlying protocol's exchange rate or a BTC-correlated price feed) to demonstrate the divergence and its effect on `max-borrowable` / liquidation thresholds computed from `get-egroup`/`current-ltv` in `v0-4-market.clar`.

**Note on completeness:** I was unable to inspect the actual `ststxbtc-token-v2` contract's exchange-rate mechanics (external, at `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.ststxbtc-token-v2`) to determine the precise real-world magnitude/direction of the mispricing, since it is an external contract outside this repo's indexed source.
