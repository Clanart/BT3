### Title
Unpermissioned dust payments to Serai's internal offset addresses (Branch/Change/Forwarded) are reported as received outputs, forcing the validator set to spend fees forwarding attacker-controlled dust - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary

The reported bug class — an unprivileged party cheaply triggering a permissionless path that mutates shared state and forces the honest side into expensive/denied follow-on actions — maps onto Serai's Bitcoin scanner. `Scanner::scan_transaction` classifies an output purely by `script_pubkey` match against registered offsets, and the Branch/Change/Forwarded offsets are fixed public constants derived via `Secp256k1::hash_to_F(KEY_DST, ...)`. Any Bitcoin user can therefore send dust-sized payments directly to the internal Change/Branch/Forwarded addresses and have them reported to the processor as internal-kind received outputs, triggering downstream scheduling/spending of those outputs (with real fee burn by the multisig) at no meaningful cost and no rate limit — exactly analogous to `settleUpnl` accepting empty / 1-wei settlements with no cooldown.

### Finding Description

`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) iterates `tx.output` and emits a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`, with the stored `offset` — no authentication of who created the output or why. `processor/src/networks/bitcoin.rs:308-347` shows the offsets are not secrets: `BRANCH_OFFSET`, `CHANGE_OFFSET`, and `FORWARD_OFFSET` are deterministic constants (`Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch" | b"change" | b"forward")`), and `scanner()` registers each via `register_offset`, so an attacker can recompute every internal address offline (`p2tr(key + offset*G)`).

`Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-740`) then scans each non-coinbase transaction, looks up `kinds[offset_repr]` to tag the output as `External`/`Branch`/`Change`/`Forwarded`, and pushes every match with `amount >= N::DUST` into the processor's output set. Forwarded/Change-kind outputs are consumed by the multisig scheduler as protocol-owned UTXOs: Forwarded outputs must be swept into the active multisig, and Change outputs are spent as inputs — each sweep requires constructing and signing a Bitcoin transaction paying miner fees out of the multisig's own funds.

There is:
- No minimum value beyond `N::DUST` (546–1000+ sats) — a ~$1 payment suffices.
- No cooldown or per-sender rate limit — the scanner accepts unlimited matching outputs per block.
- No provenance check — an attacker-controlled deposit is indistinguishable from protocol-internal change/forward traffic.

This is the same "increment the nonce for ~free, repeatedly" primitive as the SymmIO report: a permissionless, near-zero-cost on-chain action that obligates the honest side (here, the threshold validators) to do work — building `SignableTransaction`s in `make_signable_transaction` and running FROST signing sessions to sweep/spend outputs whose only purpose is to drain fees.

### Impact Explanation

Each dust output sent to the Forwarded/Branch/Change script_pubkey becomes a protocol-owned UTXO that must eventually be spent. Spending a 546-sat input costs more in transaction fees than the input is worth, so every forwarded dust output is net-negative to the multisig — an unbounded, cheap fee drain and UTXO-set bloat vector. A sustained attacker can also push the input count toward `TooLargeTransaction` limits, degrading liveness of legitimate withdrawals, mirroring the force-close DoS (denying/degrading honest completion via spam of a permissionless function).

### Likelihood Explanation

Fully unprivileged: the attacker only needs to send ordinary Bitcoin transactions to publicly derivable addresses. No validator key, no threshold collusion, no trusted input. Cost per grief is ~dust + fees, and it can be repeated indefinitely.

### Recommendation

- Require a minimum economic value for Forwarded/Branch/Change-kind outputs (or only register the Forwarded offset on-demand per actual forward, rather than permanently scanning it).
- Where the protocol expects an internal output (e.g., change from a transaction it itself broadcast), authenticate it by expected txid/outpoint rather than by `script_pubkey` alone.
- Rate-limit or bucket dust-level received outputs so their aggregation cost cannot exceed the value they add.

### Proof of Concept

1. Compute `FORWARD_OFFSET = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")`; the attacker address is `p2tr_script_buf(key + GENERATOR*FORWARD_OFFSET)` — the same address `Bitcoin::forward_address` (`processor/src/networks/bitcoin.rs:671-674`) returns.
2. Send N transactions paying `N::DUST` satoshis each to that script.
3. `get_outputs` emits N `Output`s with `kind == OutputType::Forwarded`; the scheduler treats them as protocol-owned and must craft and FROST-sign sweep transactions spending them, paying more in fees than the dust is worth. Repeating indefinitely drains the multisig's fee budget at attacker-chosen cadence.
