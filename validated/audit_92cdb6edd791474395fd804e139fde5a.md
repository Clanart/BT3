### Title
`SignableTransaction::new` calculates fee/weight without the OP_RETURN data output, so fee checks validate a smaller transaction than the one signed - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs`, but then computes the transaction weight/vbytes — and therefore `needed_fee`, the `TooLowFee` minimum-relay check, the `NotEnoughFunds` check, and the change-output value — via `calculate_weight_vbytes`, which builds a weight-estimation transaction containing only the payment outputs and optional change. The data output's bytes are never accounted for. This is the same bug class as the Rubicon finding: a bound check (sufficient funds, sufficient fee rate, dust-safe change) is performed against a value computed *before* a component that reduces the effective result is included — here, the signed transaction is larger and pays a lower effective fee rate than what was checked.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

- The OP_RETURN output is pushed onto `tx_outs` at lines 193-202.
- Weight/vbytes are then computed with `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204), and `calculate_weight_vbytes` builds its estimation `Transaction` from `payments` and `change` only (lines 85-99). `tx_outs` — including the OP_RETURN output — is never passed in.
- `needed_fee = fee_per_vbyte * vbytes` (line 206), `TooLowFee` check (line 211), `NotEnoughFunds` check (line 215), the change value `input_sat - payment_sat - fee_with_change` (lines 225-234), and the `MAX_STANDARD_TX_WEIGHT` check (line 241) all use this underestimated size.

An OP_RETURN output adds roughly 9 + len(script) bytes of base size (8-byte value + compactsize + scriptPubKey), i.e. ~11-92+ bytes for allowed data of 1-80 bytes (~3-23+ vbytes of weight the fee never covers). None of the checks see it.

### Impact Explanation
- The produced transaction pays a fee rate strictly below the caller-specified `fee_per_vbyte` (the actual fee is still `sum(inputs) - sum(outputs)`, but spread over a larger real vsize). If `fee_per_vbyte` is at/near the minimum, the real fee falls below `DEFAULT_MIN_RELAY_TX_FEE` and the transaction will be rejected by relay despite `TooLowFee` passing — funds are committed to a non-propagating transaction requiring an out-of-band resign.
- The `MAX_STANDARD_TX_WEIGHT` check can pass a transaction that is actually over the standardness limit once the data output is included, producing a transaction that cannot be broadcast at all.
- Change is computed against the underestimated fee, so the change amount is correspondingly off (slightly over-credited to change rather than fee — the wallet underpays its intended fee).

### Likelihood Explanation
Deterministic whenever `data` is `Some` — the miscounting applies to every invocation of the public `SignableTransaction::new` API with an OP_RETURN payload. No attacker cooperation is needed; the miscalculation is inherent in the weight estimation. Severity is bounded since it degrades fee rate / propagatability rather than enabling theft, but it can strand funds in a transaction that won't relay.

### Recommendation
Include the OP_RETURN output in the weight estimation: pass the fully-constructed `tx_outs` (or `payments` plus the serialized data output) into `calculate_weight_vbytes`, for both the no-change and with-change calls, so `needed_fee`, `TooLowFee`, `NotEnoughFunds`, change sizing, and `MAX_STANDARD_TX_WEIGHT` all reflect the transaction actually signed.

### Proof of Concept
```rust
// In-networks/bitcoin test context: inputs/payments as in tests/wallet.rs
let data = vec![0u8; 80]; // maximum allowed
let tx = SignableTransaction::new(
    vec![output],
    &payments,
    Some(change_addr),
    Some(data),
    FEE, // e.g. 1 sat/vbyte, the default minimum
).unwrap();
// needed_fee() = FEE * vsize(tx_without_op_return)
// real vsize is ~90 bytes larger; tx.fee()/real_vsize < FEE
// With FEE at the minimum relay rate, the produced TX fails relay policy
// even though TooLowFee did not fire, and may exceed MAX_STANDARD_TX_WEIGHT
// without TooLargeTransaction firing.
```

Every `calculate_weight_vbytes` call (send.rs:204, 225-226) builds its template transaction from `payments`/`change` only, while the OP_RETURN `tx_outs.push` at send.rs:194-202 is excluded — so all subsequent size-derived checks validate a strictly smaller transaction than the one produced.
