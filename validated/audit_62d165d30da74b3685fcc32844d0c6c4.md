### Title
Reward double-claim in `ArbWomUp3.incentiveDeposit(_mode=2)` via manipulating `mWomSV.getUserTotalLocked` through `startUnlock`/`cancelUnlock` - (`File: wombat/ArbWomUp3.sol`)

### Summary
`ArbWomUp3.calDoubledCounted` and `getRewardAmount` compute the tier-based MGP reward using the account's **current** `mWomSV.getUserTotalLocked(_account)` balance instead of a monotonic historical high-water-mark of previously rewarded stake. Because `mWomSV.getUserTotalLocked` drops immediately when a user calls the permissionless `startUnlock` function (moving the amount into "cool down", which is excluded from `getUserTotalLocked`), an attacker can temporarily lower their counted balance, re-trigger `incentiveDeposit(_mode=2)` with a tiny top-up to re-claim almost the full tier reward, and then call `cancelUnlock` to restore their original position at no real cost.

### Finding Description
`getRewardAmount` for the lock path (`wombat/ArbWomUp3.sol:107-129`) computes:
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)
rewardAmount = f(accumulated tier bracket)
mgpReward = rewardAmount/DENOMINATOR - calDoubledCounted(_account)
```
`calDoubledCounted` (`wombat/ArbWomUp3.sol:131-144`) recomputes the "already paid" portion purely from `mWomSV.getUserTotalLocked(_account)` at call time — it is **not** a stored, monotonically increasing counter of previously rewarded stake.

`mWomSV.getUserTotalLocked` (`wombat/mWomSV.sol:113-117`) subtracts `getUserAmountInCoolDown(_user)`, and `getUserAmountInCoolDown` sums amounts placed into unlock slots via `startUnlock` (`wombat/mWomSV.sol:247-277`), which is a fully permissionless, unprivileged function requiring no waiting period to take effect on the accounting value (the balance is deducted from `getUserTotalLocked` the instant `startUnlock` is called, well before `coolDownInSecs` elapses or the actual `unlock()`/token withdrawal occurs). The user can later call `cancelUnlock` (`wombat/mWomSV.sol:305-315`) to restore the cooldown amount back into `getUserTotalLocked` at any time before the slot is finalized, with zero token movement or cost.

Exploit flow:
1. Attacker calls `incentiveDeposit(amount=X, mode=2)`. At call time locked balance is 0, so `calDoubledCounted=0`, and they receive full tier reward `R` for reaching total locked `X` in `mWomSV`.
2. Attacker calls `mWomSV.startUnlock(X - ε)` — `getUserTotalLocked(attacker)` instantly drops to `ε`, with no real withdrawal, and it can be reversed via `cancelUnlock`.
3. Attacker calls `incentiveDeposit(amount=ε', mode=2)` with a very small top-up. `getRewardAmount` now computes `accumulated ≈ X` again (same tier bracket), but `calDoubledCounted` is computed off the now-tiny `ε`, so `mgpReward ≈ R` again (minus a negligible correction for `ε`), effectively re-paying almost the entire original tier reward for stake that was never actually removed.
4. Attacker calls `mWomSV.cancelUnlock` to restore full locked balance, or lets `startUnlock` cooldown finish and re-locks, repeating the cycle to drain the MGP reward pool.

The `nonReentrant`/`whenNotPaused` modifiers on `incentiveDeposit` do not prevent this because the exploit is sequential across separate transactions, not a reentrancy attack; there is no check comparing against a stored historical total-ever-locked-and-rewarded amount.

### Impact Explanation
This allows an unprivileged attacker to repeatedly extract MGP tokens held by `ArbWomUp3` for stake that was already rewarded, i.e., theft of unclaimed MGP reward yield / drain of the reward pool (Immunefi: theft of unclaimed yield / protocol insolvency of the reward pool), capped only by `mgp` balance held in the contract (`getRewardAmount` clamps to `IERC20(mgp).balanceOf(address(this))`).

### Likelihood Explanation
Requires only owning some WOM and calling three public functions (`incentiveDeposit`, `startUnlock`, `cancelUnlock`) repeatable in a loop with negligible incremental capital (`ε`) per iteration, and no special privileges, oracle manipulation, or governance action. This is highly feasible and repeatable as long as the reward pool holds MGP.

### Recommendation
Track a persistent, monotonically increasing "reward already paid for" counter per account (e.g., `mapping(address => uint256) public rewardedLockedAmount`) that is only incremented (never derived from a value that can decrease via `startUnlock`), and compute the incremental reward against that stored counter instead of `mWomSV.getUserTotalLocked(_account)`.

### Proof of Concept
Foundry test outline:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie`, mock `mWom`/`WOM`/`MGP`, configure reward tiers/multipliers, and fund `ArbWomUp3` with MGP.
2. `attacker` calls `incentiveDeposit(X, ratio, false, 2)` — record `mgpReceived1` (via `vlMGP.lockFor` amount or MGP balance delta).
3. `attacker` calls `mWomSV.startUnlock(X - 1e18)`; assert `mWomSV.getUserTotalLocked(attacker)` dropped to `~1e18`.
4. `attacker` calls `incentiveDeposit(smallTopUp, ratio, false, 2)` — record `mgpReceived2`.
5. `attacker` calls `mWomSV.cancelUnlock(slotIndex)`; assert `getUserTotalLocked(attacker)` restored to ~`X + smallTopUp`.
6. Assert `mgpReceived1 + mgpReceived2 > getRewardAmount(X + smallTopUp, attacker, true)` computed once against the full historical total, proving the same tier bracket was paid out twice.
