## Title
Fail-open logic in `isApplicationBundle` allows a malicious app-bundle-shaped directory to bypass the macOS bundle-execution guard when `mdls` metadata isn't yet available — (File: `app/src/lib/is-application-bundle.ts`)

### Summary
`isApplicationBundle` is the only gate that decides whether `showFolderContents` opens a directory via the dangerous `UNSAFE_openDirectory` path or the safe `_showItemInFolder` path on macOS. The function only fails safe (returns `true`, treating the path as a bundle) when `execFile('mdls', …)` **throws**. It does not fail safe when `mdls` succeeds but returns metadata that doesn't contain any of the three allow-listed identifiers — which is exactly what happens for a path whose Spotlight metadata is unpopulated (e.g., right after a fresh `git clone`/checkout, before Spotlight has indexed the new file, or for paths under Spotlight-excluded volumes such as some external/network filesystems).

### Finding Description
`isApplicationBundle` builds its verdict purely from a substring/allow-list check against `mdls` output: [1](#0-0) 

There is no distinction between:
- "mdls succeeded and definitively reported this is *not* an app bundle" (stdout shows unrelated content types), and
- "mdls succeeded but returned empty/`(null)` values because Spotlight has no metadata for this path yet."

Both cases produce `probableBundleIdentifiers.some(...) === false`, i.e. `isApplicationBundle` returns `false`.

The only defense-in-depth fallback in the call site is a `.catch` on a *rejected* promise: [2](#0-1) 

That fallback (`return true` on error) does not help here because `execFile('mdls', …)` resolves successfully (exit code 0, empty/placeholder stdout) rather than rejecting — this is normal `mdls` behavior for paths whose metadata hasn't been indexed yet or that were replaced/deleted and recreated quickly (a common state right after a fresh `git clone` of an attacker-controlled repository, since freshly-created files are not indexed instantaneously by `mdworker`).

When `isApplicationBundle` returns `false`, `showFolderContents` calls `UNSAFE_openDirectory(path)` instead of `_showItemInFolder(path)`: [3](#0-2) 

`UNSAFE_openDirectory` is explicitly documented as unsafe for unverified paths because on macOS a directory can be a `.app` bundle, and opening it launches the app rather than just revealing it in Finder: [4](#0-3) 

The main process implements it via `shell.openPath`: [5](#0-4) 

`electron.shell.openPath` on macOS is equivalent to double-clicking the path in Finder — for a `.app`-shaped directory, this launches (executes) the bundle rather than opening it as a folder.

### Impact Explanation
If an attacker crafts a repository containing a directory named/structured like a `.app` bundle (with an `Info.plist`/executable inside, disguised as ordinary repo content), and the user triggers the "show in folder" action on that path immediately after cloning/checking it out (before Spotlight has indexed it), the app could call `UNSAFE_openDirectory` on the malicious bundle instead of the safe fallback, resulting in execution of attacker-supplied code on the victim's machine. This matches the "code execution from a cloned/fetched repository" impact category in scope.

### Likelihood Explanation
This is a timing-dependent condition, not a deterministic bypass. Exploitability depends on:
1. Whether `mdls` truly returns success with non-matching/empty output before indexing rather than erroring for the given macOS version/filesystem (this behavior can vary and was not verified against a live macOS `mdls` invocation in this review).
2. The user invoking the folder-reveal action on the specific attacker-controlled path within the narrow window before Spotlight indexes it (or on a volume/location excluded from Spotlight indexing, e.g. certain external volumes, network shares, or with `mdutil -i off`).
3. GitHub Desktop's own repo-clone-to-Finder-open user flow timing.

Because it depends on Spotlight indexing races and specific filesystem/index configuration rather than a value the app fully controls, likelihood is lower than a deterministic bug, but the underlying logic flaw (fail-open on "no match" rather than fail-closed on "no confirmed non-bundle") is real and independently verifiable.

### Recommendation
Change `isApplicationBundle` to fail closed (return `true`) unless `mdls` output *positively and unambiguously* confirms a non-bundle content type, or treat empty/`(null)` metadata the same as a thrown error (i.e., return `true` when `stdout` is empty or lacks a definitive `kMDItemContentType` value), so that ambiguous/unindexed metadata is never treated as "safe to execute."

### Proof of Concept
Not independently verified in this review — reproducing requires a live macOS environment: exclude a test path from Spotlight indexing (`mdutil -i off <path>` or use `sudo mdutil -X` / place file on `.noindex` location), place a `.app`-shaped directory there (crafted as if freshly cloned), and invoke the code path that leads to `showFolderContents` on that path while capturing the `mdls` stdout to confirm it is empty/non-matching without an exception being thrown, then confirm `UNSAFE_openDirectory`/`shell.openPath` is invoked. This proof step could not be executed here since only static code analysis tools were available.
