### Title
Recursive clone always disables Git's built-in clone-protection guard, reopening submodule RCE (CVE-2024-32002 class) - ([File: app/src/lib/git/clone.ts])

### Summary
`app/src/lib/git/clone.ts` explicitly forces the Git-internal environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every clone, while always passing `--recursive`. That variable is not meant to be set by callers — it is Git's own mechanism (added upstream to remediate the 2024 clone/submodule RCE family, e.g. CVE-2024-32002/32004/32020/32021/32465) for detecting unsafe recursive submodule checkouts on case-insensitive or symlink-capable filesystems, where a crafted submodule path can collide with `.git`/hooks and get Git to write attacker-controlled files (including executable hooks) outside the intended submodule directory. By forcing this flag off, GitHub Desktop unconditionally disables that safety net for every clone it performs.

`clone()` is reached from every user-initiated clone flow: `AppStore._clone` → `CloningRepositoriesStore.clone` → this function ( [2](#0-1) ), and also from the `open-repository-from-url` protocol-handler path that GitHub Desktop exposes to arbitrary deep links (`x-github-client://openRepo/...`), i.e. attacker-supplied URLs can trigger a clone with attacker-chosen `url`.

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-maintained internal marker used to detect re-entrant/nested clone invocations spawned for submodule recursion, so Git can refuse to write files that would land inside a nested `.git` directory (via case-folding collisions on case-insensitive filesystems like default macOS/Windows, or via crafted paths) — the exact primitive behind the CVE-2024-32002 class of clone RCEs. It is designed to be *set and managed by Git itself*, not overridden by a caller. Forcing it to `'false'` here removes that guard for the `--recursive` clone GitHub Desktop always performs, meaning the app relies solely on whatever Git version happens to be vendored to have no other mitigation for this class of attack, since the one Git ships explicitly for this purpose is switched off.

### Impact Explanation
An attacker who controls a cloned repository (a normal, unprivileged scenario: a public repo, a repo shared via URL, or a repo opened via a `x-github-client://openRepo/...` deep link) can craft nested/recursive submodules designed to defeat Git's clone-protection guard. With the guard disabled, cloning such a repository can result in files being written outside the intended submodule working directory — including into `.git/hooks` — leading to arbitrary code execution the next time Git runs a hook-triggering operation in that repository (which GitHub Desktop performs automatically, e.g. status refresh, fetch, commit). This matches the accepted impact class: code execution or file write outside the intended repository boundary triggered purely by cloning an attacker-controlled repository, no local/physical access or pre-existing malware required.

### Likelihood Explanation
Clone is triggered on ordinary, expected user actions (Clone Repository dialog, GitHub-provided clone URLs, and `x-github-client://openRepo/` deep links which are explicitly reachable without any privileged setup). The `--recursive` flag is unconditional, so any repository containing submodules is subject to the disabled protection. This does not require the user to take any unusual or "unnatural" steps beyond cloning a link/repository they were given — the normal expected workflow for the app.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE` at all — let Git manage this internal variable itself. If this override was added to work around some other integration issue (e.g. progress parsing, LFS, or a proxy trampoline conflict), that interaction should be root-caused and fixed without disabling Git's own submodule/clone RCE protections. At minimum, gate the vendored Git version to one that contains the CVE-2024-32002 family fixes and remove the explicit `'false'` override so the protection remains active for every `--recursive` clone.

### Proof of Concept
Exact reproduction requires constructing a nested-submodule repository crafted per the public CVE-2024-32002 advisory (submodule name/path colliding with `.git` under case-insensitive/symlink-aware filesystem semantics) and cloning it through GitHub Desktop. Locally, the misconfiguration is directly verifiable by inspecting the environment passed to Git:
1. In `app/src/lib/git/clone.ts`, note `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally set in `env` for every call to `clone()`. [3](#0-2) 
2. Confirm this path is reached from ordinary, unprivileged, attacker-influenceable entry points (Clone dialog and deep-link `open-repository-from-url` handling in the dispatcher). [4](#0-3) 
3. With this flag forced to `'false'`, replaying any of the public CVE-2024-32002/32004/32020/32021 submodule test cases against a clone performed by Desktop would bypass Git's own protection that those CVEs' patches added, whereas cloning the same payload with a stock, unmodified `git clone --recursive` (without the override) is blocked.

I was unable to run an actual exploit repository against the app in this environment (no filesystem/terminal access here), so the PoC above is based on static code inspection confirming the disabling flag and its unconditional invocation path; a background Devin session with repo/terminal access would be needed to build and clone a concrete malicious submodule payload to confirm end-to-end file write/RCE.
