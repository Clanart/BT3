## Title
Spoofed `WWW-Authenticate` header from a malicious git remote forces GitHub Desktop to bind an attacker-controlled host as a "GitHub Enterprise" endpoint and launch an OAuth sign-in flow against it - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

## Summary
This is the closest real Desktop analog to the Sherlock report's core pattern: **a value the app trusts implicitly (host classification / amount) is actually influenced by untrusted, attacker-supplied data, and no compensating check exists to catch the mismatch.** In the original report, UMA's undocumented fee silently changed the amount actually charged/returned. In Desktop, the *host-trust decision* that gates whether an origin is treated as a GitHub/Enterprise endpoint is silently driven by an HTTP response header that a malicious git server fully controls, bypassing the one real verification path (`isGitHubHost`) that would otherwise make a genuine network check.

## Finding Description
`getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 137-179) classifies a credential-helper request's target host as `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`. Before doing any authoritative check, it inspects the `wwwauth[]` fields Git forwards from the server's `WWW-Authenticate` HTTP header: [1](#0-0) 

If the server's `WWW-Authenticate` value contains `realm="GitHub"`, the endpoint is unconditionally classified as `'enterprise'` — no call is made to `isGitHubHost()`, which is otherwise the function that performs the real network-based verification for unknown hosts: [2](#0-1) 

This header is not privileged content: it is set by whatever git server (or MITM/malicious proxy on an `http://` remote) the user is cloning/fetching from. `parseCredential()` faithfully forwards any `wwwauth[]=...` line from that server's challenge into the credential map used by `getEndpointKind`: [3](#0-2) 

Once `getEndpointKind` reports `'enterprise'` for a host that has no matching stored account, `getCredential()` in the same file (lines 93-135) unconditionally calls `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

`promptForGitHubSignIn` then drives the real sign-in state machine, calling `dispatcher.beginEnterpriseSignIn` / `setSignInEndpoint(origin)` with the attacker's origin, and shows the standard GitHub sign-in dialog with that origin as the "Enterprise" endpoint: [5](#0-4) 

The corrupted value here is `endpointKind` (and downstream, `state.endpoint` in `SignInStore`) — it is supposed to represent "a verified GitHub host," but it is actually set from an unauthenticated, attacker-supplied HTTP header string, with no cross-check against the DNS/TLS identity of the remote that sent it.

## Impact Explanation
This satisfies the "unauthorized OAuth or account binding" category from the valid-impact list: a normal `git fetch`/`git clone`/`git push` against an attacker-controlled HTTP(S) remote (or an on-path proxy replying to the Git credential challenge) can cause GitHub Desktop to spontaneously open its GitHub Enterprise sign-in dialog and bind the attacker's origin as a would-be GHE endpoint (`SignInStore.setEndpoint`/`beginEnterpriseSignIn`), all triggered purely by response-header content the attacker chooses. This is a meaningful trust-boundary break: a value (`endpointKind`) that is meant to gate whether Desktop treats a host as a genuine GitHub product line is derived from attacker data instead of a verified property of the connection, and the one existing safeguard (`isGitHubHost` network probe) is bypassed entirely on this path.

I was not able to fully trace, within the available iterations, whether the subsequent OAuth code/token exchange (`getOAuthAuthorizationURL`/`requestOAuthToken` in `app/src/lib/api.ts`) sends any Desktop OAuth client secret to the spoofed `endpoint` origin, which would upgrade this into direct credential/secret exfiltration. That part of the flow needs further verification before treating it as confirmed.

## Likelihood Explanation
The attacker only needs to control the HTTP response of a git remote the user chooses to interact with (their own malicious server, or a MITM on an `http://` remote) and set a `WWW-Authenticate` header value containing `realm="GitHub"` — no local access, no prior compromise, no admin rights, and no unnatural user steps beyond the normal act of cloning/fetching from a repository, which is squarely inside the "attacker controls a git remote/proxy response" scope defined as valid.

## Recommendation
Do not let the `wwwauth[]` realm hint alone decide a `'enterprise'` classification for hosts with no stored account. At minimum, still require the `isGitHubHost()` network check (which validates against the real `/meta` or similar authoritative GitHub API response) before triggering `promptForGitHubSignIn`/`beginEnterpriseSignIn`, and clearly surface the untrusted origin to the user before any sign-in flow proceeds against it.

## Proof of Concept
1. Stand up an HTTP git server (or a MITM proxy in front of an `http://` remote) at `http://evil.example`.
2. Configure it to respond to Git's authentication probe with an HTTP `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, clone/fetch from `http://evil.example/some/repo.git` while not already signed in to any account matching that origin.
4. Git forwards the header via the credential-helper protocol as `wwwauth[]=Basic realm="GitHub"`; `getEndpointKind()` matches the regex at [6](#0-5)  and returns `'enterprise'` without ever calling `isGitHubHost('http://evil.example')`.
5. `getCredential()` sees no matching stored account for `evil.example` and invokes `ui.promptForGitHubSignIn('http://evil.example')`, which opens the GitHub Enterprise sign-in dialog bound to that attacker-chosen origin [7](#0-6) .

```typescript
export const parseCredential = (value: string) => {
  const cred = new Map<string, string>()

  // The credential helper protocol is a simple key=value format but some of its
  // keys are actually arrays which are represented as multiple key[] entries.
  // Since we're currently storing credentials as a Map we need to handle this
  // and expand multiple key[] entries into a key[0], key[1]... key[n] sequence.
  // We then remove the number from the key when we're formatting the credential
  for (const line of value.split(/\r?\n/)) {
    const eqIx = line.indexOf('=')
    if (eqIx === -1) {
      continue
    }

    const k = line.slice(0, eqIx)
    const v = line.slice(eqIx + 1)

    if (k.endsWith('[]')) {
      let i = 0
      let newKey

      do {
        newKey = `${k.slice(0, -2)}[${i}]`
        i++
      } while (cred.has(newKey))

      cred.set(newKey, v)
    } else {
      cred.set(k, v)
    }
  }

  return cred
}
```
