## Finding [1](#0-0) 

### Title
Same-chain order relayer fee escrow is misdirected to the filling solver instead of the order owner - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntentGatewayV2.placeOrder` escrows an optional Hyperbridge relayer fee (`order.fees`) under the `TRANSACTION_FEES` slot for every order, same-chain or cross-chain, with no validation that same-chain orders even need one. `_fillSameChain` never dispatches any cross-chain message (no relayer is ever used), yet on a full fill it calls `_withdraw` with `beneficiary = msg.sender` (the solver). `_withdraw`'s finalize branch unconditionally forwards the entire accumulated `TRANSACTION_FEES` balance to `beneficiary`. As a result the user's escrowed relayer fee — money that was never spent on any relayer service — is paid out to the solver instead of being returned to the order owner. This is inconsistent with `_cancelSameChain`, which correctly routes the same fee back to `order.user`, confirming the fill path is the flawed one.

### Finding Description
- `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:345-362`) escrows `order.fees` into `_orders[commitment][TRANSACTION_FEES]` unconditionally, regardless of whether the order is same-chain or cross-chain. [2](#0-1) 
- `_fillSameChain` never performs any Hyperbridge dispatch (no relayer is ever paid), but on full fill it builds `WithdrawalRequest{ beneficiary: msg.sender }` (the solver) and calls `_withdraw(body, false, isFullyFilled)`. [3](#0-2) 
- `_withdraw`'s `finalize` branch (triggered on full fill) unconditionally sweeps `_orders[commitment][TRANSACTION_FEES]` to `beneficiary`: [4](#0-3) 
- By contrast, `_cancelSameChain` correctly routes the refund (and by extension the escrowed fee) to `order.user`: [5](#0-4) 

There is no guard in `_fillSameChain`/`_withdraw` that zeroes or redirects `TRANSACTION_FEES` back to `order.user` when no cross-chain dispatch occurred. The corrupted value is `_orders[commitment][TRANSACTION_FEES]`, which is paid to the wrong recipient (`msg.sender`/solver) instead of the rightful one (`order.user`).

### Impact Explanation
This is a "wrong beneficiary/amount" fund-movement bug: escrowed user funds are transferred to a party (the filling solver) with no entitlement to them, via a fully public, unprivileged entry point (`fillOrder`). No malicious relayer, prover, or admin is required — any solver that fills a same-chain order that happens to carry `order.fees > 0` automatically receives that fee as a windfall, and the user permanently loses it. This directly parallels the seed report's core invariant break: legitimately due funds are silently diverted away from the rightful beneficiary because of a flawed state-transition/accounting path (there, `terminate()`; here, `fillOrder`'s finalize branch).

### Likelihood Explanation
Likelihood is contract-logic-inherent rather than conditional on external actors: nothing in `placeOrder` prevents a same-chain order (`order.source == order.destination`) from setting `order.fees > 0`, and any normal solver who fills such an order (a routine, expected action) automatically triggers the misdirected payout. No race condition, malicious peer, or privileged role is needed — only an order with `fees > 0` and a normal fill.

### Recommendation
In `_fillSameChain`, do not forward `TRANSACTION_FEES` to the filling solver. Either:
1. Reject/zero `order.fees` for same-chain orders in `placeOrder` (revert if `order.source == order.destination && order.fees > 0`), or
2. In `_withdraw`/`_fillSameChain`, route any escrowed `TRANSACTION_FEES` back to `order.user` (not `msg.sender`) when finalizing a same-chain fill, matching the behavior already implemented in `_cancelSameChain`.

### Proof of Concept
1. User calls `placeOrder` with `order.source == order.destination` (a same-chain order) and sets `order.fees = 1000e18` (in the protocol fee token). This amount is escrowed into `_orders[commitment][TRANSACTION_FEES]` per `evm/src/apps/IntentGatewayV2.sol:345-362`.
2. A solver calls `fillOrder` with matching outputs, fully filling the order via `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:54-149`). No Hyperbridge relayer is ever invoked for a same-chain fill.
3. `_fillSameChain` builds `WithdrawalRequest{ beneficiary: msg.sender }` and calls `_withdraw(body, false, true)`.
4. `_withdraw`'s finalize branch (`evm/src/apps/intentsv2/IntentsBase.sol:412-417`) transfers the full `1000e18` `TRANSACTION_FEES` balance to `msg.sender` (the solver), even though no relayer fee was ever owed or spent.
5. The user's escrowed relayer fee is permanently lost to the solver instead of being refunded, unlike the `_cancelSameChain` path which correctly returns it to `order.user`.
