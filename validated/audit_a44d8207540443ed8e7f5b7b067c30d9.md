### Title
Early return on non-canonical share skips batch verification, letting faulty decryption proofs escape blame non-deterministically - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` iterates `shares.drain()` — a `std::collections::HashMap` whose order is randomized per-process — and returns `PedPoPError::InvalidShare` immediately when a decrypted share fails `C::F::from_repr`. This early return abandons the `BatchVerifier` without ever calling `batch.verify_with_vartime_blame()`, so any `BatchId::Decryption(l)` statements already queued are never checked. Whether a participant who sent a malformed `EncryptedMessage` is identified therefore depends on random HashMap drain order — the same "random execution order turns a recoverable check into a nondeterministic abort" shape as the CKB `ScriptError::ExceededMaximumCycles` advisory. [1](#0-0) 

### Finding Description
For each share, `calculate_share`:

1. Queues a decryption statement into `batch` under `BatchId::Decryption(l)` via `self.encryption.decrypt(...)`, which also returns a `blame` proof object. [2](#0-1) 
2. Parses the decrypted bytes with `C::F::from_repr`; on failure it returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` — unwinding immediately. [3](#0-2) 
3. Only after the loop does it call `batch.verify_with_vartime_blame()` to actually verify the queued decryption and share-verification statements. [4](#0-3) 

Because `shares.drain()` yields entries in RandomState order, an honest participant processing messages from multiple faulty senders will:

- report whichever faulty sender happened to be drained first (nondeterministic blame attribution), and
- return before the batch is verified, so a participant `k` whose `EncryptedMessage` fails its decryption proof — but who was drained before the non-canonical share — has their `BatchId::Decryption(k)` statement silently dropped, escaping `InvalidShare` blame entirely.

### Impact Explanation
Blame proofs in PedPoP are the accountability mechanism: `PedPoPError::InvalidShare { participant, blame }` is what lets the coordinator/other validators identify and exclude a faulty party. A faulty participant can deliberately send a share whose ciphertext decrypts to non-canonical field bytes (`>= modulus`), which is trivially constructible since `SecretShare<C::F>` is just raw repr bytes fed to `from_repr`. If another participant in the same session is also faulty (or the attacker controls multiple indexes), the decryption-faulty party evades detection whenever drain order processes the non-canonical share after their message — random per execution, matching the advisory's intermittent-failure profile. In the worst case a faulty participant is never blamed and the DKG cannot be attributed, while an honest-looking error is returned against whichever participant drained "first." [5](#0-4) 

### Likelihood Explanation
Fully reachable by an unprivileged protocol participant: `shares` is a `HashMap<Participant, EncryptedMessage<...>>` of attacker-supplied round-2 messages, and the drain order is governed by std's random hasher seed. The bug triggers whenever at least one encrypted share decrypts to non-canonical bytes — no cryptographic assumption needed — and the skipped-verification window opens whenever any other participant's message is also faulty. `blame_entropy`-style ordering is not even required; HashMap iteration alone provides the randomness.

### Recommendation
Do not early-return inside the drain loop. Queue all messages, run `batch.verify_with_vartime_blame()` first so decryption faults are always attributed via `BatchId::Decryption(l)`, and only then map `from_repr` failures onto `InvalidShare` (ideally iterating `all_participant_indexes()` for deterministic ordering, as `verify_r1` already does). [6](#0-5)

```rust
// Conceptual: participant i runs calculate_share with messages from l1, l2.
// l1 sends an EncryptedMessage whose ciphertext decrypts to bytes >= modulus
//   (non-canonical C::F) -> from_repr fails.
// l2 sends an EncryptedMessage with an invalid decryption proof
//   (queues a failing BatchId::Decryption(l2) statement).
//
// If drain yields l2 first, its Decryption statement is queued, then l1's
// from_repr error returns InvalidShare { participant: l1 } WITHOUT running
// batch.verify_with_vartime_blame(). l2's decryption fault is never blamed.
// If drain yields l1 first, the same early return fires before l2's message
// is even decrypted. Outcome is random across executions because
// std::collections::HashMap uses RandomState.
```

Uncertainty note: this is the strongest in-scope analog I found for the "random ordering + premature abort" class; the concrete harm is blame evasion/misattribution rather than secret leakage, so severity is best assessed as Medium.
