## Title
Relayer fee balance is zeroed and paid out in a governance-changed `fee_token` before destination settlement, causing permanent loss of accrued relayer fees - (File: `modules/pallets/relayer/src/withdrawal.rs`)

## Summary
`pallet-ismp-relayer`'s `Fees<T>` storage tracks a relayer's accrued reward as a bare `U256` amount with no record of which ERC-20 `fee_token` it was denominated in. When a relayer withdraws, `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`) re-reads the *current* `fee_token` from `pallet-host-executive`'s `HostParams` and unconditionally zeroes the `Fees` entry before the cross-chain payout even executes. If governance updates the destination chain's `fee_token` (via `pallet_ismp_host_executive::update_host_params`) between when the relayer accrued the fee and when they withdraw it, the amount is disbursed in the wrong token (or reverts on the destination for lack of balance), and the relayer's balance is already erased on Hyperbridge with no refund path. This is the exact bug class from the external M-06 report: a value captured at one point in time (accrued fee, denominated in the fee token at accrual time) is settled using a mutable protocol parameter re-read at a later time (`fee_token` at withdrawal time), and nothing ties the two together or guards against the parameter changing in between.

## Finding Description
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads the accrued balance and immediately builds the destination payout body using whatever `fee_token` is *currently* configured for that chain: [1](#0-0) 

Note `available_amount` (line 116) is the raw `U256` accrued in `Fees<T>`; it carries no token/decimals metadata. For EVM destinations, `params.fee_token` (line 152, read from `HostParams::<T>::get(withdrawal_data.dest_chain)`) is fetched fresh at withdrawal time and embedded as `WithdrawalParams.token`. The post-dispatch step then unconditionally zeroes the relayer's balance: [2](#0-1) 

`Fees::<T>::insert(..., U256::zero())` at line 177 happens as soon as the ISMP request is *dispatched*, not after the destination chain confirms successful payout. The comment in the module header confirms this design: "The `Fees` entry is zeroed so the same balance cannot be withdrawn twice... the destination chain settles the payout when the ISMP request is delivered there" — i.e., zeroing is optimistic and there is no compensating refund if the destination-side settlement fails or pays the wrong amount.

`HostParams` for a state machine, including `fee_token`, is mutated by `pallet-host-executive::update_host_params` with no check on outstanding relayer balances for that chain: [3](#0-2) 

Contrast this with the guard that already exists on the EVM side for exactly this risk — `EvmHost.updateHostParamsInternal` refuses to switch `feeToken` while the *EvmHost contract's own* balance of the old token is non-zero: [4](#0-3) 

That guard only protects the EvmHost's own token balance sheet. It says nothing about, and cannot see, the separate `Fees<T>` balances accrued on Hyperbridge for relayers who have not yet withdrawn. So the sequence:

1. Relayer delivers a message on chain X while `fee_token = TokenA`; `pallet-ismp-relayer::accumulate` credits `Fees<T>[X][relayer] += fee` (amount denominated in `TokenA` units) via `modules/pallets/relayer/src/accumulate.rs`.
2. EvmHost's `TokenA` balance later drops to zero (e.g., after `pallet-host-executive::withdraw` sweeps protocol revenue), satisfying the EVM-side `CannotChangeFeeToken` guard.
3. Governance calls `update_host_params` to switch `fee_token` to `TokenB` for chain X — nothing in `pallet-host-executive` checks `pallet_ismp_relayer::Fees` before doing this.
4. The relayer calls `withdraw_fees`. `Pallet::withdraw` reads the *now-current* `TokenB` address, builds `WithdrawalParams{ amount: available_amount, token: TokenB, ... }`, dispatches the ISMP request, and immediately zeroes `Fees<T>[X][relayer]`.
5. On the destination, `EvmHost.withdraw` (called via `IHostManager`) transfers `available_amount` of `TokenB` — a different, unrelated ERC-20 — to the relayer. Either the relayer receives the wrong asset/value (gain or loss depending on `TokenB`'s price/decimals vs `TokenA`), or the transfer reverts for insufficient `TokenB` balance, in which case the relayer's fee is permanently lost since `Fees` was already zeroed and there is no automatic retry/credit-back for this failure mode.

## Impact Explanation
This causes unauthorized loss of relayer funds (their entire accrued, legitimately-earned balance can be erased with no on-chain path to recover it) and/or unintended fund transfer of the wrong asset/amount to relayers, both squarely within the bounty's "stealing or loss of funds" and "transaction manipulation" categories. Because zeroing happens before destination confirmation, a single ordinary governance parameter change (not an attack, not a compromised actor — the same "innocuous config update" premise as the original M-06 report) can silently and irreversibly wipe out every relayer's unclaimed balance for that destination chain.

## Likelihood Explanation
Low-to-moderate: it requires a `fee_token` change on `pallet-host-executive` for a chain that still has outstanding, unwithdrawn relayer `Fees<T>` balances. `fee_token` changes are rare operational events, but nothing in the codebase prevents or even warns about performing one while balances are outstanding — the only existing safeguard (`EvmHost.sol`'s `CannotChangeFeeToken`) checks an unrelated invariant (the EvmHost contract's own token balance), giving operators false confidence that fee-token migrations are safe.

## Recommendation
- Denominate `Fees<T>` per `(state_machine, fee_token)` rather than per bare `state_machine`, so a `fee_token` change cannot silently reinterpret an existing balance under a different token.
- Alternatively, in `pallet-host-executive::update_host_params`, reject or gate `fee_token` changes for a state machine while `pallet_ismp_relayer::Fees` has any non-zero entries for that chain (mirroring the intent of `EvmHost.sol`'s `CannotChangeFeeToken`, but scoped to the actual liability that matters — Hyperbridge's own accrued-but-unpaid relayer balances).
- Do not zero `Fees<T>` optimistically at dispatch time; only clear/decrement it after the destination-side settlement is confirmed (or track "pending withdrawal" separately and roll back on failure), so a downstream failure cannot cause unrecoverable loss.

## Proof of Concept
1. Relayer delivers messages to `StateMachine::Evm(X)` while `HostParams::<T>::get(Evm(X))` has `fee_token = TokenA`. `accumulate_fees` credits `Fees::<T>::get(Evm(X), relayer) = 1000` (TokenA-denominated units), per `modules/pallets/relayer/src/accumulate.rs`.
2. `pallet-host-executive::withdraw` sweeps `EvmHost`'s `TokenA` balance to zero (a normal revenue withdrawal), satisfying `EvmHost.sol`'s `CannotChangeFeeToken` precondition.
3. Governance calls `pallet_ismp_host_executive::update_host_params(Evm(X), EvmHostParamUpdate{ fee_token: TokenB, .. })`. This succeeds — no check against `pallet_ismp_relayer::Fees`.
4. Relayer calls `withdraw_fees` for `Evm(X)`. `Pallet::withdraw` reads `HostParams::<T>::get(Evm(X)).fee_token == TokenB`, builds `WithdrawalParams{ amount: 1000, token: TokenB }`, dispatches the request, and executes `Fees::<T>::insert(Evm(X), relayer, U256::zero())` in the same call (`modules/pallets/relayer/src/withdrawal.rs:161-177`).
5. On `Evm(X)`, `EvmHost.withdraw` (invoked through `IHostManager`) transfers `1000` units of `TokenB` (not `TokenA`) to the relayer, or reverts if `EvmHost` holds `< 1000 TokenB`. Either way, the relayer's original `TokenA`-denominated `1000`-unit claim is gone from `Fees<T>` and cannot be reclaimed or corrected.

		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(1)]
		pub fn update_host_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			update: HostParamUpdate,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			let params = HostParams::<T>::get(&state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let (HostParam::EvmHostParam(mut inner), HostParamUpdate::EvmHostParam(update)) =
				(params.clone(), update);
			inner.update(update);

			let body = inner.abi_encode_with_variant().map_err(|_| Error::<T>::DispatchFailed)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: inner.host_manager.0.to_vec(),
				timeout: 0,
				body,
			};

			let updated = HostParam::EvmHostParam(inner);

			let dispatcher = <T as Config>::IsmpHost::default();
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			HostParams::<T>::insert(state_machine, updated.clone());

			Self::deposit_event(Event::<T>::HostParamsUpdated {
				state_machine,
				old: params,
				new: updated,
			});

			Ok(())
		}
