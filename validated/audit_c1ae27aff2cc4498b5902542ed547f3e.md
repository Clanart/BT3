Based on the investigation, the strongest reachable analog is in the CR-CAT (Credential-Restricted CAT) "pending approval" mechanism.

### Title
Credential-Restricted CAT "pending approval" funds are permanently unclaimable if no VC with an authorized provider exists - (File: chia/wallet/vc_wallet/cr_cat_wallet.py)

### Summary
CR-CATs enforce a credential-restriction layer that requires a Verified Credential (VC) issued by a DID in a fixed `authorized_providers` list to authorize any CR-CAT spend, including claiming CR-CATs held in the "pending approval" state. This mirrors the report's bug class: a privileged/whitelisted-provider-gated requirement (`authorized_providers`, analogous to `thirdPartyTransfersForbidden`) is enforced at the puzzle level, and if the credential precondition cannot be satisfied at claim time, a receiver who is otherwise the rightful owner of the coin can never move it — a permanent withdrawal DoS.

### Finding Description
CR-CATs are curried with an immutable `authorized_providers` list and a `proofs_checker` [1](#0-0) . Every CR-CAT spend, including claiming coins in the "pending approval" state created by `check_for_requested_payment_modifications`/offers [2](#0-1) , must be solved with a valid VC whose `proof_provider` is one of the `authorized_providers` and whose proofs satisfy `proofs_checker` [3](#0-2) .

When a wallet later attempts to claim its pending-approval CR-CAT balance via `claim_pending_approval_balance`, it looks up a VC via `get_vc_with_provider_in_and_proofs(self.info.authorized_providers, self.info.proofs_checker.flags)`. If no such VC is currently held by the wallet (e.g. the DID never issued one, the wallet's VC was revoked/backdoor-activated by the provider via `activate_backdoor`, or the wallet simply never received a matching VC), the call raises and the pending funds cannot be claimed: [4](#0-3) 

Because `authorized_providers` is curried permanently into the on-chain puzzle (it cannot be changed post-mint) and a valid VC from one of those exact providers is mandatory to solve the puzzle at the CLVM level (via `solve_cr_layer`, enforced inside `CREDENTIAL_RESTRICTION`), there is no alternate path to move the coin out of the pending state once the credential precondition is unattainable. This is structurally identical to the reported issue: a third-party-authorization requirement (`thirdPartyTransfersForbidden`) makes a withdrawal call structurally impossible to satisfy, permanently freezing funds that are otherwise validly owned by the recipient.

### Impact Explanation
Any CR-CAT sent to a wallet's "pending approval" state (a normal, expected flow for CR-CATs received via offers or restricted-transfer payments) becomes permanently stuck if the recipient cannot obtain a VC from one of the coin's `authorized_providers` — this can happen if the DID provider revokes/never issues credentials to that wallet, or the provider's DID becomes unusable. This is a concrete, spend-triggered halt of otherwise valid coin movement (Medium severity: permanent freezing of already-received funds, not attacker-forced loss of others' funds, but a real DoS on withdrawal of legitimately owned assets).

### Likelihood Explanation
This can be triggered by ordinary, non-malicious usage: CR-CAT issuers routinely set `authorized_providers` to a small, fixed DID list at mint time, and VCs are separately-managed singleton coins under providers' control (see `activate_backdoor`/`revoke_vc`). Any receiver of a CR-CAT payment routed to the pending-approval state without already holding a compatible VC — or whose VC is later revoked before the pending balance is claimed — cannot free the coin. No malicious peer or attacker action is required, only ordinary protocol operation combined with credential unavailability.

### Recommendation
Provide an escape hatch for CR-CAT coins stuck in the pending-approval state, e.g. allow reclaiming back to the original sender's puzzle hash without requiring a VC (mirroring how CAT change/return-to-sender flows work), or add a puzzle-level timeout/fallback path that does not depend on obtaining a VC from a specific `authorized_providers` set. At minimum, document this failure mode clearly for CR-CAT issuers and wallet implementers so that "pending approval" payments are only made to wallets that can be reasonably assured of provider credential availability.

### Proof of Concept
1. Mint a CR-CAT with `authorized_providers = [did_A]` and mint a matching TAIL, as in `mint_cr_cat` [5](#0-4) .
2. Send a payment to a recipient wallet using the CR-CAT "pending approval" construction (`construct_pending_approval_state`) as done for offer-requested payments [2](#0-1) .
3. Ensure the recipient wallet never obtains (or has its) VC issued by `did_A` revoked via `activate_backdoor` [6](#0-5) .
4. Call `claim_pending_approval_balance` on the recipient's `CRCATWallet` — the lookup `get_vc_with_provider_in_and_proofs` returns `None` and the claim path raises `RuntimeError("No VC exists that can approve spends for CR-CAT wallet ...")`, and there is no other on-chain path to spend the pending-approval-wrapped coin.     def solve(self, constructor: PuzzleInfo, solver: Solver, inner_puzzle: Program, inner_solution: Program) -> Program:
        coin_bytes: bytes = solver["coin"]
        coin = Coin(bytes32(coin_bytes[0:32]), bytes32(coin_bytes[32:64]), uint64.from_bytes(coin_bytes[64:72]))
        coin_name: str = coin.name().hex()
        if "vc_authorizations" in solver.info:
            vc_info: tuple[Program, Program, bytes32, bytes32 | None, bytes32 | None] = tuple(
                solver["vc_authorizations"][coin_name]
            )
        else:
            proofs_checker = UnknownPuzzle(known_program=constructor["proofs_checker"])
            assert proofs_checker.curried_args is not None
            vc_info = (
                # TODO: This is something of a hack here, doesn't really work for proofs checkers generally.
                # The problem is that the CAT driver above us is running its inner puzzle (us) in order to get the
                # conditions that are output. This is bad practice on the CAT driver's part, the protocol should support
                # asking inner drivers for what conditions they return. Alas, since this is not supported, we have to
                # do a hack that we know will work for the one known proof checker we currently have.
                proofs_checker.curried_args[0],
                Program.NIL,
                constructor["authorized_providers"][0],  # Hack for similar reasons as above, we need a valid provider
                None,
                None,
            )

        also = constructor.also()
        if also is not None:
            inner_solution = self._solve(also, solver, inner_puzzle, inner_solution)

        return solve_cr_layer(
            *vc_info,
            coin.name(),
            inner_solution,
        )
