### Title
Unvalidated `t`/`n`/`i` header in `ThresholdKeys::read` drives attacker-controlled allocation and unbounded element parsing - ([File: crypto/dkg/src/lib.rs](https://github.com/Annirich/serai--025/blob/main/crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` is the deserialization sink for threshold key material. Like `load_level` in `coders/xcf.c` (CVE-2017-13133), it trusts an attacker-controlled length field (`n`) read directly from the input stream and uses it to drive allocation (`Vec::with_capacity`) and a loop of field/group element reads before validating anything. A crafted input a handful of bytes long forces large allocations and a long parse loop, giving a resource-exhaustion DoS wherever serialized `ThresholdKeys` are accepted from an untrusted party (the sink is explicitly listed as reachable from public inputs).

### Finding Description
The function reads `t`, `n`, `i` as raw `u16`s, then:

- For `Interpolation` tag `0` (`Constant`), it executes `Vec::with_capacity(usize::from(n))` and then loops `0..n` calling `C::read_F(reader)` — the capacity allocation of up to 65,535 scalars is committed *before* a single coefficient byte is validated.
- It then loops `for l in (1 ..= n)` inserting `C::read_G(reader)?` into a `HashMap` — up to 65,535 point decodes keyed by a wholly attacker-chosen `n`.
- Only at the end does `ThresholdParams::new(t, n, i)` reject inconsistent values, and `ThresholdKeys::new` performs the `O(t)` `group_key` multiexp — so `t`/`n` also control post-parse CPU work.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (e.g., key-material blobs relayed in DKG/recovery messages, or any API reading serialized `ThresholdKeys`) can cause repeated ~2–4 MB allocations plus tens of thousands of field/point deserialization and group operations per tiny input — memory/CPU exhaustion identical in shape to the `load_tile` exhaustion in the reference CVE. There is no size/length sanity check comparable to a transaction size limit anywhere in this reader.

### Likelihood Explanation
Reachable whenever serialized `ThresholdKeys` cross a trust boundary; the payload is trivially small (a few header bytes with `n = 0xFFFF` and tag `0`). Severity is bounded: `n` is a `u16`, so a single invocation is capped at ~65,535 elements — a Medium-severity resource-exhaustion analog rather than unbounded.

### Recommendation
Reject `n` (and `t`) above the session's expected participant count, or a sane protocol maximum, before allocating; replace `Vec::with_capacity(n)` with incremental pushes (the `HashMap` path already does this) and validate `ThresholdParams` immediately after reading `t`/`n`/`i` rather than after parsing the variable-length body.
