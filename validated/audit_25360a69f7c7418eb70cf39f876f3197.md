### Title
Tron `IntentGatewayV2.authenticate()` fails open to `address(this)` for unregistered source chains, unlike the EVM reference implementation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core defect is a fail-open default: unvalidated/unconfigured origins (dev domains, malformed subdomains) are implicitly trusted instead of being rejected. The same pattern exists in Hyperbridge's Tron `IntentGatewayV2` contract's cross-chain sender-authentication helper `instance()`, which silently defaults an unregistered source chain to `address(this)` instead of reverting — diverging from the reference EVM implementation in `IntentsBase.sol`, which correctly reverts with `UnknownInstance` when no gateway has been registered for a source chain.

### Finding Description
`authenticate()` in the Tron `IntentGatewayV2` is the gate that decides whether an incoming ISMP `PostRequest` (`RedeemEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, `RefundEscrow`) is accepted as coming from a legitimate peer gateway on `request.source`: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
...
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
```

Compare this to the canonical EVM helper used by `ExtrinsicIntents.sol`, which is the correct "fail closed" pattern: [2](#0-1) 

```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

`_instances` is only populated via governance-driven `_addDeployment` (dispatched as a `NewDeployment` cross-chain message): [3](#0-2) 

The gateway is intentionally deployed via deterministic CREATE2 so its address is identical across every supported chain — this is explicitly documented: [4](#0-3) 

Because of this, `address(this)` on the destination chain is the same fixed value that the *legitimate* gateway would have on every other chain, including chains that Hyperbridge's `EvmHost` already accepts state proofs for but for which this gateway's operator has not yet executed `_addDeployment` (a routine, expected transitional state during any new-chain rollout). In that gap window, the Tron gateway's `authenticate()` treats **any** `PostRequest` whose `from` equals `address(this)` as authenticated, for **any** unregistered `request.source` — i.e., it fails open exactly like the reported "any localhost/invalid origin is allowed" defect, instead of failing closed like the reference `_instance()`.

### Impact Explanation
This directly violates the required invariant that "cross-chain admin or host-management effects must not be reachable through ... wrong module bindings." Messages carrying `RequestKind.UpdateParams` or `RequestKind.SweepDust`/`RedeemEscrow` bodies would be processed as authenticated governance/peer traffic for any source state machine lacking an explicit `_instances` entry, letting escrowed funds be released to attacker-chosen beneficiaries or protocol parameters be corrupted — a false state/authorization acceptance leading to fund loss, matching the bounty's "false proof/state acceptance" and "unauthorized execution" classes.

### Likelihood Explanation
The bug is purely a code-path property of `authenticate()`/`instance()` and requires no relayer collusion, no consensus forgery, and no admin/governance compromise — only that a supported-but-not-yet-`_addDeployment`-registered state machine exists (a normal, temporary operational state during chain onboarding, or any state machine intentionally never registered). This is triggerable by any unprivileged party able to submit an ISMP-proven `PostRequest` from that state machine.

### Recommendation
Make `instance()` in the Tron `IntentGatewayV2` revert on an unregistered source chain, mirroring `IntentsBase._instance()`:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
Remove the `address(this)` fallback entirely so that `authenticate()` fails closed for any chain without an explicit governance-registered instance.

### Proof of Concept
1. Hyperbridge governance whitelists a new EVM/Tron state machine `X` in `EvmHost`/consensus config but has not yet called `_addDeployment` on the Tron `IntentGatewayV2` for `X` (a normal transitional state, or a chain deliberately left unmapped).
2. An attacker deploys any contract on chain `X` at the address equal to the Tron gateway's own deterministic `address(this)` (achievable since the deployment scheme is a public deterministic CREATE2 factory, per the documented cross-chain address-consistency design), or otherwise controls a contract at that exact address.
3. The attacker dispatches an ISMP `PostRequest` from that contract on chain `X`, with `request.source = X`, `request.from = address(this)-on-X` (20 bytes), and body encoding `RequestKind.RedeemEscrow`/`SweepDust`/`UpdateParams`.
4. Once relayed and proven (a normal permissionless relaying/proof step, not requiring a malicious relayer or forged consensus), `onAccept` calls `authenticate(request)`; `instance(X)` returns `address(this)` (fallback), which equals `module`, so `Unauthorized` is never raised.
5. The forged request is processed as if from a legitimate peer gateway, releasing escrowed tokens or altering protocol parameters.

Note: I was unable to trace the full `onAccept` dispatch body in the Tron contract within the remaining tool budget to confirm every `RequestKind` branch reachable through this path; the core authentication defect (`instance()` failing open vs. `_instance()` failing closed) is directly confirmed from the code shown above.
