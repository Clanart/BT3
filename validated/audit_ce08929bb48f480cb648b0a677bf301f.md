### Title
Unbounded CLVM Cost Execution in Wallet Memo Computation Allows Spend-Triggered Resource Exhaustion - (File: chia/wallet/util/compute_memos.py)

### Summary
`compute_memos_for_spend()` runs an attacker-supplied puzzle reveal with `INFINITE_COST`, removing the standard CLVM cost metering that bounds resource consumption everywhere else in the codebase. This function is reachable by any coin spender whose spend is later observed by a victim wallet (e.g. via `NotificationManager.potentially_add_new_notification`), making it possible for an unprivileged spend-bundle submitter to force victim wallets to execute an arbitrarily expensive CLVM program with no cost ceiling.

### Finding Description
Every other CLVM execution path in the codebase (mempool validation, block validation, offer computation) enforces a hard cost ceiling: `max_tx_clvm_cost` in `MempoolManager.pre_validate_spendbundle()` [1](#0-0) , and `MAX_BLOCK_COST_CLVM` in block body validation [2](#0-1) . This cost metering is the sole mechanism by which chia-blockchain bounds the CPU/memory an untrusted CLVM program can consume, as documented for the mempool/block paths [3](#0-2) .

`compute_memos_for_spend()`, however, executes the puzzle reveal of an arbitrary, attacker-supplied `CoinSpend` with `INFINITE_COST`, i.e., no cost limit at all: [4](#0-3) 

This function is invoked by `NotificationManager.potentially_add_new_notification()`, which runs on the `parent_spend` of any coin whose spend produces a coin sent to a wallet-controlled puzzle hash — i.e., on coin states the wallet is asked to process as part of ordinary sync/notification handling: [5](#0-4) 

Because the puzzle reveal and solution of the parent spend are fully attacker-controlled (any party can spend a coin with an arbitrary puzzle and solution, then send a notification-shaped coin, or otherwise cause a coin whose parent spend has this crafted puzzle to be observed by the victim's wallet), an attacker can construct a `puzzle_reveal`/`solution` pair that loops or recurses to a very large CLVM cost. Since `run_with_cost` is called with `INFINITE_COST`, execution will not be aborted by a cost limit; it will run until it either completes (after consuming attacker-chosen, effectively unbounded CPU time and intermediate atom/pair memory) or the process is killed. This mirrors exactly the axios `fetch` adapter bug class (CWE-770): a resource-consuming code path that has size/cost limiting available elsewhere in the system, but that specific call site strips the limit out, letting an attacker-controlled input dictate resource consumption.

### Impact Explanation
Any coin spend a wallet is asked to process for notification purposes can carry a puzzle designed to consume unbounded CLVM execution cost. Because the call uses `INFINITE_COST` rather than a bounded value, the victim wallet's sync-processing task (which holds a `sync_scope`/wallet state lock while it awaits `potentially_add_new_notification`) can be stalled indefinitely by a single crafted spend, halting or severely degrading wallet transaction processing for that wallet — a spend-triggered denial of service, consistent with CWE-770 "Allocation of Resources Without Limits or Throttling."

### Likelihood Explanation
Likelihood is high for any wallet with `enable_notifications` on (the default per `chia/util/initial-config.yaml`) [6](#0-5) : the trigger condition only requires a spent coin whose CREATE_COIN memo matches the notification puzzle hash format and passes the minimum-amount spam filter — no special privileges, signatures over the victim's keys, or full-node cooperation are required, only that the victim's wallet observes the spend (normal wallet sync behavior).

### Recommendation
Replace `INFINITE_COST` in `compute_memos_for_spend()` with a bounded cost (e.g., the same `max_tx_clvm_cost`/`MAX_BLOCK_COST_CLVM`-derived limit used elsewhere), and treat a `ValueError`/cost-exceeded result as "no memos" rather than propagating an unbounded computation. Audit other callers of `compute_memos`/`compute_memos_for_spend` for the same issue.

### Proof of Concept
1. Attacker crafts a `CoinSpend` whose `puzzle_reveal` is a CLVM program that recurses/loops to a very large (attacker-chosen) execution cost before returning a `CREATE_COIN` condition with a memo shaped to match `construct_notification(target, amount).get_tree_hash()` and pass `required_notification_amount`.
2. Attacker spends the coin on-chain (or via any path that lets the victim wallet observe the spend/coin state).
3. Victim wallet syncs and calls `NotificationManager.potentially_add_new_notification(coin_state, parent_spend, sync_scope)`, which calls `compute_memos_for_spend(parent_spend)` [7](#0-6) .
4. `run_with_cost(coin_spend.puzzle_reveal, INFINITE_COST, coin_spend.solution)` executes with no cost bound [4](#0-3) , consuming attacker-chosen CPU/memory and blocking the wallet's sync task for the duration of execution.
