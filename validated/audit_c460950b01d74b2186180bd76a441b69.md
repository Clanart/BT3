### Title
Unchecked Bitcoin payment aggregation can overflow and authorize a malformed transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates every payment only against the dust threshold, but then sums attacker-influenced payment amounts with unchecked `u64` arithmetic. A crafted payment list can wrap the aggregate amount to a small value, bypass the funds check, and produce a transaction containing outputs whose real serialized values greatly exceed the supplied inputs. The same unchecked arithmetic is later committed to by the FROST signing machine.

### Finding Description
`SignableTransaction::new` rejects payments below `DUST`, but does not impose a maximum on an individual payment or on their aggregate. [1](#0-0) 

It calculates `input_sat` and `payment_sat` using `Iterator::sum::<u64>()`. [2](#0-1)  In a release build, overflowing the payment sum wraps modulo `2^64`; in a debug build it panics. The fund-sufficiency check then compares `input_sat` against `payment_sat + needed_fee`, whose addition is also unchecked. [3](#0-2) 

When the wrapped comparison succeeds, the individual oversized amounts are still placed into `tx_outs`. [4](#0-3)  The resulting `SignableTransaction` preserves those outputs. [5](#0-4) 

`TransactionSignMachine::sign` subsequently calculates a Taproot key-spend sighash for every input and passes that digest to the FROST algorithm. [6](#0-5)  Therefore, once malformed payment data reaches this API, the threshold group signs a transaction encoding output amounts whose mathematical total is not the checked total.

### Impact Explanation
An attacker who can supply payment instructions can cause participants to sign an unintended, invalid Bitcoin transaction. The signature itself is valid for the malformed transaction digest, but the transaction's serialized outputs can exceed the inputs and the Bitcoin money range, making it unbroadcastable and potentially consuming a signing attempt, preprocesses, and coordinator/processor state.

This does not directly authorize withdrawal of more Bitcoin than the inputs contain because Bitcoin consensus will reject an output set exceeding its inputs or maximum money. The practical impact is transaction-construction integrity failure and denial of signing resources rather than theft.

### Likelihood Explanation
The bug is reachable wherever untrusted payment amounts are passed to `SignableTransaction::new` without an external aggregate bound. Only ordinary Rust integer wrapping is required; no malformed curve point, invalid participant index, private-key access, or protocol deviation inside FROST is needed.

Exploitation requires a caller that accepts attacker-controlled payment lists and a release configuration where `u64` arithmetic wraps. The crafted amounts must each remain at least `DUST`, which is trivial for values near `u64::MAX`.

### Recommendation
Use checked arithmetic for all monetary aggregation and comparisons:

- Accumulate `input_sat`, `payment_sat`, and output totals with `checked_add`.
- Calculate `fee_per_vbyte * vbytes` with `checked_mul`.
- Calculate `payment_sat + needed_fee` with `checked_add`.
- Reject outputs exceeding Bitcoin's consensus money limit before constructing `TxOut`s.
- Keep a separately checked aggregate of the serialized `tx_outs`, rather than relying on the wrapped payment sum.
- Make `fee()` return `Result<u64, TransactionError>` or use `checked_sub`.

### Proof of Concept
Conceptually, pass one spendable `ReceivedOutput` worth `5_000` sats and two payments:

```rust
let payments = [
  (payment_script_a, u64::MAX - 1000),
  (payment_script_b, 2000),
];

let tx = SignableTransaction::new(
  vec![received_output],
  &payments,
  None,
  None,
  1,
);
```

Both payments pass the dust check. Their aggregate wraps:

```text
(u64::MAX - 1000) + 2000 == 999 mod 2^64
```

Assuming the no-change transaction is under roughly `4_000` vbytes, `needed_fee` is below `4_001`, so this comparison succeeds:

```text
input_sat = 5_000
wrapped payment_sat + needed_fee <= 5_000
```

`new` therefore returns `Ok(SignableTransaction)` even though the serialized transaction contains outputs of `u64::MAX - 1000` and `2_000` sats. Calling `TransactionSignMachine::sign` then obtains Taproot sighashes for that malformed transaction and requests FROST shares for them. [7](#0-6)
