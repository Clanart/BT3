### Title
OP_RETURN outputs are omitted from Bitcoin fee and transaction-size accounting - (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` accepts up to 80 bytes of caller-controlled OP_RETURN data and adds it as a transaction output before calculating the transaction's weight and virtual size. However, `calculate_weight_vbytes` is only passed `payments` and `change`; the OP_RETURN output is never included in the transaction model used for fee and maximum-standard-size checks. The resulting `needed_fee` and weight checks therefore apply to a smaller transaction than the one that is actually signed and broadcast.

### Finding Description
`SignableTransaction::new` appends the OP_RETURN output to `tx_outs` at `networks/bitcoin/src/wallet/send.rs:193-202`. It then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at `networks/bitcoin/src/wallet/send.rs:204`, omitting the data output entirely. The same omission occurs when the caller supplies a change output at `networks/bitcoin/src/wallet/send.rs:224-227`.

`calculate_weight_vbytes` builds its accounting transaction exclusively from the supplied inputs, payments, and optional change script at `networks/bitcoin/src/wallet/send.rs:68-99`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is calculated from a transaction without the OP_RETURN output.
- The minimum relay-fee check at `networks/bitcoin/src/wallet/send.rs:204-213` uses the understated virtual size.
- Change accounting at `networks/bitcoin/src/wallet/send.rs:224-233` reserves too little fee and returns too much change.
- The `MAX_STANDARD_TX_WEIGHT` check at `networks/bitcoin/src/wallet/send.rs:241-243` uses the understated weight.
- The final transaction nevertheless includes the extra OP_RETURN output and is signed at `networks/bitcoin/src/wallet/send.rs:245-255` and `networks/bitcoin/src/wallet/send.rs:373-390`.

For an 80-byte payload, the omitted output contributes the fixed output overhead, compact script length, `OP_RETURN`, push opcode, and the 80-byte push. This makes the actual signed transaction materially larger and more expensive than the value used by every fee and size check.

### Impact Explanation
An unprivileged caller supplying transaction data can cause the threshold wallet to construct and sign a Bitcoin transaction whose actual fee rate is below both the requested `fee_per_vbyte` and, at the boundary, Bitcoin's minimum relay fee.

At `fee_per_vbyte == 1`, the current check can pass because `needed_fee == 1 * underestimated_vbytes`, while the finalized transaction pays that same fee across a larger actual virtual size. Its real fee rate is therefore below 1 sat/vbyte and default Bitcoin Core policy will reject it as underpaying.

The same incorrect accounting can cause change to be oversized by approximately the fee that should have covered the OP_RETURN output. Near the standardness boundary, a transaction can also pass the internal maximum-weight check while the signed transaction exceeds `MAX_STANDARD_TX_WEIGHT`.

This is an incorrect transaction-size/fee formula affecting a guard relied on before threshold signing and broadcast. Publication failure is explicitly treated as unexpected: `publish_completion` panics for non-connection RPC errors at `processor/src/networks/bitcoin.rs:844-851`.

### Likelihood Explanation
The bug is deterministic whenever `data` is supplied: the data output is always added to `tx_outs` and always omitted from `calculate_weight_vbytes`. The only limit on the attacker-controlled contribution is the existing 80-byte data limit checked at `networks/bitcoin/src/wallet/send.rs:171-173`.

The strongest concrete impact occurs when the selected fee rate is at or near the minimum relay fee, or when the transaction is near Bitcoin's standard weight limit. In those cases the discrepancy is sufficient to produce a signed transaction that normal Bitcoin policy rejects.

### Recommendation
Build the accounting transaction from the exact final output set, including the OP_RETURN output, rather than passing only `payments` and `change` into `calculate_weight_vbytes`.

Concretely, either:

1. Move OP_RETURN construction before fee calculation and pass `&tx_outs` / equivalent output descriptors into `calculate_weight_vbytes`, or
2. Add the data output's serialized size and weight to the result explicitly.

The change-output path must likewise calculate fees and weight over the exact final transaction containing payments, OP_RETURN data, and change. After fixing, add a regression test asserting:

```rust
assert_eq!(tx.needed_fee(), u64::try_from(tx.transaction().vsize()).unwrap() * fee_per_vbyte);
```

for transactions both with and without OP_RETURN data.

### Proof of Concept
The existing wallet test infrastructure already exercises OP_RETURN transactions. The following regression demonstrates the discrepancy without requiring threshold signing:

```rust
// networks/bitcoin/tests/wallet.rs
#[test]
fn op_return_is_included_in_fee_accounting() {
  let output = /* mature ReceivedOutput obtained through Scanner as in test_data */;
  let data = vec![0; 80];

  let tx = SignableTransaction::new(
    vec![output],
    &[],
    Some(p2tr_script_buf(key).unwrap()),
    Some(data),
    1, // sat/vbyte
  ).unwrap();

  let actual_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();

  // Current behavior: this fails because needed_fee was calculated without the OP_RETURN output.
  assert_eq!(tx.needed_fee(), actual_vbytes);

  // Equivalently, the actual transaction is below the requested 1 sat/vbyte rate.
  assert!(tx.fee() < actual_vbytes);
}
```

The root cause is visible directly in the constructor flow: OP_RETURN is appended to `tx_outs`, but `calculate_weight_vbytes` is called with `payments` and `change`, not `tx_outs`, so the returned weight and virtual size do not describe the transaction that `TransactionMachine` signs.
