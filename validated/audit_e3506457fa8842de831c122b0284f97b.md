### Title
`_calExpireForfeit` in mWOMSVBaseRewarder never applies a forfeit penalty, unlike the equivalent vlMGP path - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWomSV.sol` implements `getRewardablePercentWAD`, a lock/cooldown-based percentage identical in design to `VLMGP.sol`'s function of the same name, clearly intended to scale down rewards for mWOMSV holders who are mid-cooldown (i.e., not fully committed lockers). However, `mWOMSVBaseRewarder._calExpireForfeit` never calls it — `rewardableAmount` is hardcoded to `_amount`, so `forfeitAmount` is always `0`. This is confirmed dead code, directly comparable to the working implementation in `vlMGPBaseRewarder._calExpireForfeit`, which does call `vlMGP.getRewardablePercentWAD(_account)`.

### Finding Description
`vlMGPBaseRewarder._calExpireForfeit` computes the forfeit correctly: [1](#0-0) 
using `vlMGP.getRewardablePercentWAD(_account)`.

`mWOMSVBaseRewarder._calExpireForfeit`, which should follow the exact same pattern against `mWOMSV.getRewardablePercentWAD(_account)` (which exists and is implemented identically in `mWomSV.sol`), instead sets `rewardableAmount = _amount` directly and never calls the locker at all: [2](#0-1) 

Because `rewardableAmount` is always equal to `_amount`, `forfeitAmount = _amount - rewardableAmount` is always `0`, making the whole forfeit mechanism in `_sendReward` a no-op: [3](#0-2) 

This means any holder of mWOMSV-linked staking tokens receives their full pro-rata share of rewards via `getReward`/`getRewards` (both `onlyMasterMagpie`, reachable through `MasterMagpie.multiclaimFor`/`multiclaim`/`multiclaimSpec`) regardless of whether they are fully locked or mid-cooldown, with zero penalty routed back to `_queueNewRewardsWithoutTransfer` for redistribution to committed lockers. [4](#0-3) 

Note on the specific attack narrative in the question: the described chain (racing the `updateRewards`/`updateReward` snapshot, waiting for/front-running a `_provisionReward` from the reward manager, then claiming via `multiclaimFor` to a "receiver they don't own but control via approval trickery") does not add anything beyond normal, permitted usage. `multiclaimFor(_stakingTokens, _rewardTokens, _account)` in `MasterMagpie.sol` sends rewards to `_receiver = _account` itself (not an attacker-chosen address) — [5](#0-4)  — so there is no arbitrary-receiver redirection primitive to "steal" another user's yield; a caller can only trigger the claim for `_account`, and funds always go to `_account`. The reward-index snapshot logic in `updateReward`/`updateRewards` is standard and does not, by itself, allow front-running theft of other users' rewards — it only ensures a user is credited with their own share based on `balanceOf` at time of update.

The real, provable defect is narrower and simpler than the described exploit: **the forfeit/penalty mechanism is dead code**, so no staker — even one who stakes and immediately unstakes/claims — is ever penalized for lacking commitment, whereas the parallel vlMGP mechanism *does* apply a real penalty based on lock/cooldown state.

### Impact Explanation
This results in **permanent loss of expected forfeited yield for committed mWOMSV lockers**: reward funds that should be re-queued (via `_queueNewRewardsWithoutTransfer`) as bonus yield to fully-locked participants are instead paid out in full to any staker, including users mid-cooldown or those who deposit briefly. This matches the "theft of unclaimed yield that should be subject to forfeiture" impact class — the funds are not stolen from individual users' balances, but the intended value transfer from short-term/cooldown stakers to committed lockers never happens, causing committed lockers to receive less than their designed share over time. This is a real economic/logic bug in the protocol's incentive design, not merely a cosmetic issue, since `calExpireForfeit`/`_calExpireForfeit` are load-bearing in the parallel vlMGP contract for the same purpose.

### Likelihood Explanation
Trivial and always exploitable — no special capital, front-running, or timing is required. Any address holding a nonzero balance of mWOMSV (obtained by normal deposit) that has rewards accrued via `getReward`/`getRewards` will always get `forfeitAmount == 0` from `_calExpireForfeit`, 100% of the time, regardless of stake duration or cooldown status. This can be demonstrated with a single-block Foundry test with no adversarial setup needed.

### Recommendation
Fix `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`, i.e., compute `rewardableAmount` from `mWOMSV.getRewardablePercentWAD(_account)` (already implemented and available via `ILocker`/`mWomSV.sol`) instead of hardcoding `rewardableAmount = _amount`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```
This requires extending `ILocker` (currently only declares `lockFor`) to expose `getRewardablePercentWAD`, matching the interface already implemented by `mWomSV.sol`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, and `mWOMSVBaseRewarder`; register a reward token.
2. Have user A deposit mWOMSV and immediately `startUnlock` a large portion (putting most of balance into cooldown, i.e., low `getRewardablePercentWAD`).
3. As the reward manager, call `queueNewRewards`/`donateRewards` on the rewarder to inject a large reward amount.
4. Call `mWOMSVBaseRewarder.calExpireForfeit(userA, rewardToken)` and assert it returns `0` even though `mWomSV.getRewardablePercentWAD(userA)` returns a value well below `1e18` (e.g., near 0% if fully in cooldown and freshly started).
5. Call `MasterMagpie.multiclaimFor` (or `getReward` directly as `masterMagpie`) for user A and assert user A receives 100% of the pro-rata reward with no amount re-queued via `_queueNewRewardsWithoutTransfer`, confirming the forfeit mechanism is inert.

Note: I could not verify from the indexed code alone whether `multiclaimFor`'s `_account`/`_receiver` parameters can ever diverge (i.e., whether any documented "approval trickery" exists elsewhere in the codebase to redirect funds to a third-party receiver); based on the code reviewed, `_receiver` is always `_account` for user-initiated claim paths, so that portion of the described exploit is not substantiated by the code found.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
