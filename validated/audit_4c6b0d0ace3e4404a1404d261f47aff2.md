### Title
Blame proof (ECDH decryption key) is emitted before the proof-of-possession is verified, letting an unauthenticated sender force disclosure of another participant's encrypted secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the Filsnap report — where an RPC endpoint disclosed data to a caller that had never proven it was entitled to it — `KeyMachine::calculate_share` hands out an `EncryptionKeyProof` (the ECDH shared key that decrypts a message) inside `PedPoPError::InvalidShare` on the `from_repr` early-return path, *before* the queued PoP (`msg.pop`) batch verification has run. A malicious participant who copies the per-message key `X` from an honest sender's `EncryptedMessage` can make the victim publish the ECDH key for `X`, then decrypt the honest sender's real ciphertext off-band — exactly the attack the per-message PoP in `EncryptedMessage` was added to prevent.

### Finding Description
In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-501) the recipient:

1. Queues the sender's Schnorr PoP into a `BatchVerifier` (`msg.pop.batch_verify`, deferred — not yet verified).
2. Immediately computes `key = ecdh(self.enc_key, msg.key)` and builds an `EncryptionKeyProof` containing that ECDH key plus a DLEq proof binding it to the recipient's registered `enc_key`.

In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499), each share is decrypted, and if the plaintext fails `C::F::from_repr`, the function returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` at line 480-482 — short-circuiting out of the loop and never reaching `batch.verify_with_vartime_blame()` at line 493, which is the only place the queued PoP is actually checked (`BatchId::Decryption(l)` maps to `blame: None`).

The upstream design anticipates this exact attack (encryption.rs:83-90): "If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X … Bob would then … reveal bX, revealing Alice's message to Bob." The PoP is present, but because verification is batched/deferred and the non-scalar return path bypasses it, the protection is void: the blame proof is produced and broadcast (processor/src/key_gen.rs:419-425, serialized into `ProcessorMessage::InvalidShare`, and later evaluated by `AdditionalBlameMachine`/`VerifyBlame`, which any party — including non-participants — can run via `AdditionalBlameMachine::new` at lib.rs:649-662) before the PoP is ever confirmed.

### Impact Explanation
The published `EncryptionKeyProof.key` equals `ECDH(enc_key_victim, X)`, i.e., the full decryption key for *any* `EncryptedMessage` to that victim that uses per-message key `X`. An attacker who observed the honest sender's ciphertext to the victim (shares are relayed through the coordinator) recovers the plaintext secret share `f_honest(victim)` — a key share of the DKG session — without ever possessing `x` or being authorized to read that message. This is key-share/secret-share recovery and unauthorized disclosure of threshold key material, paralleling the Filsnap leak of addresses to non-allowlisted dapps.

### Likelihood Explanation
Reachable by any unprivileged DKG participant with public inputs: they feed attacker-crafted bytes into `EncryptedMessage::read` → `calculate_share`. Requirements:

- Copy `msg.key = X` from an observed `EncryptedMessage` addressed to the victim (public field).
- Supply a dummy `pop` signature and a ciphertext that decrypts under the unknown keystream to a non-canonical scalar — succeeds with ~½ probability for random bytes (non-canonical repr → `from_repr` fails). No PoP validity is needed since verification is skipped on this path.
- The victim's node emits and broadcasts the blame proof automatically as part of normal fault handling.

The constraint is that the triggered abort kills that DKG attempt, so the leaked share belongs to a discarded session; however, the disclosure primitive itself (decrypting shares addressed to others by forging blame) breaks the protocol's confidentiality guarantee and reveals share material the attacker was never entitled to.

### Recommendation
Do not emit `EncryptionKeyProof` material until the associated PoP has been verified. Specifically, in `calculate_share` the `from_repr` early-return should still run/await `batch.verify_with_vartime_blame()` (or at least verify that participant's `BatchId::Decryption` PoP) before including `blame: Some(...)`. If the PoP fails, return `blame: None` — the sender is self-evidently faulty and no decryption key should be revealed. Alternatively, verify the PoP eagerly inside `Encryption::decrypt` before computing `ecdh`/`EncryptionKeyProof`.

### Proof of Concept
```text
Setup: DKG session with participants {Alice=1, Eve=2, Bob=3} on Ristretto,
context C. Alice's SecretShareMachine produces EncryptedMessage { key = X = k*G,
pop = Sign_k(...), msg = ct } intended for Bob; Eve observes it (coordinator
relays the shares map).

Attack:
1. Eve builds EncryptedMessage { key: X,            // copied — Eve does NOT know k
                                 pop: SchnorrSignature { R: <random>, s: <random> },
                                 msg: SecretShare(<32 random bytes>) }
   and submits it as her share to Bob.
2. Bob's calculate_share -> encryption.decrypt(.., from=Eve, msg):
     - queues Eve's bogus pop into BatchVerifier (NOT verified yet)
     - computes proof = EncryptionKeyProof { key: ECDH(bob_enc_key, X), dleq }
     - keystream-decrypts msg to garbage
3. C::F::from_repr(garbage) fails (~50% for random bytes) ->
     return Err(InvalidShare { participant: Eve, blame: Some(proof) })
   — batch.verify_with_vartime_blame() is never reached, so Eve's invalid PoP
     is never checked.
4. Bob serializes blame into ProcessorMessage::InvalidShare; the coordinator /
   VerifyBlame path runs AdditionalBlameMachine::blame, which is callable by any
   observer and re-derives the same plaintext via decrypt_with_proof.
5. Eve (or any observer) takes proof.key, runs cipher(context, proof.key) and
   decrypts Alice's real ciphertext ct -> Alice's secret share f_alice(Bob).

Root cause: lib.rs:480-482 returns blame containing the ECDH key on the
from_repr failure path before the deferred PoP batch check at lib.rs:493.
```
