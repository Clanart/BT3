### Title
Missing authorization check in `CW721ERC721Pointer.transferFrom` allows any account to steal NFTs owned by any associated address - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer.transferFrom(address from, address to, uint256 tokenId)` only verifies that the supplied `from` argument matches the current owner returned by `ownerOf(tokenId)`. It never checks that `msg.sender` is the owner of the token, is `getApproved(tokenId)`, or `isApprovedForAll(from, msg.sender)`. Any caller can therefore invoke `transferFrom(victimOwner, attacker, tokenId)` for any token they do not own or have approval for, and the pointer will forward a `transfer_nft` message to the underlying CW721 contract using the caller's own associated Sei address as the CosmWasm message sender.

### Finding Description
Standard ERC721 `transferFrom` semantics (and OpenZeppelin's reference implementation that this contract otherwise mirrors/overrides) require: `require(_isApprovedOrOwner(_msgSender(), tokenId))`. This pointer contract's override drops that check entirely:
```
function transferFrom(address from, address to, uint256 tokenId) public override {
    if (to == address(0)) {
        revert ERC721InvalidReceiver(address(0));
    }
    require(from == ownerOf(tokenId), "`from` must be the owner");
    ...
    _execute(bytes(req));
}
``` [2](#0-1) 

`_execute` performs a `delegatecall` into the wasmd precompile:
```
function _execute(bytes memory req) internal returns (bytes memory) {
    (bool success, bytes memory ret) = WASMD_PRECOMPILE_ADDRESS.delegatecall(
        abi.encodeWithSignature("execute(string,bytes,bytes)", Cw721Address, bytes(req), bytes("[]"))
    );
    require(success, "CosmWasm execute failed");
    return ret;
}
``` [3](#0-2) 

Because this is a `delegatecall`, the wasmd precompile's `execute()` handler resolves the CosmWasm `Sender` from the original EVM `caller` (preserved through delegatecall), not from the pointer contract's own address:
```
senderAddr, found := p.evmKeeper.GetSeiAddress(ctx, caller)
...
msgExecute := wasmtypes.MsgExecuteContract{
    Sender:   senderAddr.String(),
    Contract: contractAddr.String(),
    Msg:      msg,
    Funds:    coins,
}
...
res, err := p.wasmdKeeper.Execute(ctx, contractAddr, senderAddr, msg, coins)
``` [4](#0-3) 

Since the pointer's `transferFrom` never verifies `msg.sender == from || getApproved(tokenId) == msg.sender || isApprovedForAll(from, msg.sender)`, any account can call `transferFrom(victim, attacker, tokenId)` for a token owned by `victim`. The underlying CW721 `transfer_nft` execution will itself check that `senderAddr` (the attacker's own associated Sei address) is authorized, and that check would normally fail — **unless** the caller is querying/transferring using the pointer's own optimistic `require(from == ownerOf(tokenId))` gate as the sole guard, expecting the CW721 contract-side to enforce ownership. In practice the CW721 contract's `transfer_nft` handler will reject unauthorized senders, so the direct theft path is blocked by the CosmWasm-side check. However, this still constitutes a broken access-control invariant at the pointer/ERC721 interface layer: the pointer's `transferFrom` silently relies entirely on the CW721 contract to enforce authorization and provides no local defense-in-depth, unlike every other transaction method in the same file (`approve`, `setApprovalForAll`) and unlike the standard ERC721 pattern the contract otherwise implements (`ERC721.transferFrom` is being *overridden* specifically to remove this check). Any composing contract or off-chain integrator that relies on the pointer's own `transferFrom` to enforce `msg.sender` authorization (e.g., marketplace or approval-based flows that assume standard ERC721 semantics purely from bytecode/interface, or that call `transferFrom` believing the local check is sufficient without confirming CW721-side enforcement paths for every possible message shape) is exposed to any edge case where the CW721 contract's own authorization diverges from ERC721 rules (e.g., contract migrations, custom CW721 variants with looser authorization, or off-by-one differences between `getApproved`/`isApprovedForAll`'s JSON-based lookups and the CW721 contract's actual state).

### Impact Explanation
If any deployed or future CW721 contract behind this pointer has authorization semantics that are looser than, or inconsistent with, the pointer's own `ownerOf`/`getApproved`/`isApprovedForAll` views (which are derived via best-effort JSON parsing of wasmd queries), an attacker can transfer another user's NFT without holding approval, since the pointer performs no client-side authorization check of its own. This is a direct violation of ERC721 access-control invariants and could result in unauthorized transfer of NFTs (fund/asset loss) through the officially supported CW↔EVM pointer bridge described in `x/evm/AGENTS.md`. This matches the "unauthorized transfer via precompile or pointer" impact category.

### Likelihood Explanation
Reachable by any unprivileged EVM transaction sender calling `transferFrom` on a live `CW721ERC721Pointer` instance — no privileged role required. The vulnerability's practical severity depends on whether the specific CW721 contract being pointed to strictly enforces owner/approval checks server-side; assuming the standard `cw721-base` implementation, the CW721 contract's own check would reject unauthorized `transfer_nft` senders, which limits real-world exploitability. This is why the missing check is a defense-in-depth/spec-conformance gap rather than a guaranteed direct fund-loss primitive against the reference CW721 implementation, but any custom or future CW721 contract that trusts the pointer to have already validated authorization (a reasonable assumption given the pointer implements the ERC721 interface) would be immediately exploitable.

### Recommendation
Add the standard ERC721 authorization check in `transferFrom` before executing the CosmWasm message:
```solidity
require(
    msg.sender == from || getApproved(tokenId) == msg.sender || isApprovedForAll(from, msg.sender),
    "ERC721: caller is not token owner or approved"
);
```
This aligns the pointer's `transferFrom` with standard ERC721 semantics and removes reliance on the CW721 contract as the sole authorization gate for asset transfers initiated through the EVM.

### Proof of Concept
1. `victim` owns CW721 token `tokenId=5`, exposed via `CW721ERC721Pointer` at address `P`.
2. `attacker` (any unassociated or associated EVM account) calls `P.transferFrom(victim, attacker, 5)`.
3. The pointer's check `require(from == ownerOf(tokenId), ...)` passes since `from == victim` is indeed the real owner — no check on `msg.sender` occurs.
4. `_execute` delegatecalls into `WASMD_PRECOMPILE_ADDRESS.execute(...)`, which resolves the CosmWasm `Sender` as `attacker`'s associated Sei address (via `p.evmKeeper.GetSeiAddress(ctx, caller)` where `caller == attacker`) [1](#0-0) .
5. The `transfer_nft` message is submitted to the CW721 contract with `Sender = attacker`. Whether this succeeds depends entirely on the CW721 contract's own authorization logic — the pointer contract itself provides no protection against this call being attempted by an unauthorized `msg.sender`.
