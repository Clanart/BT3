## Analog Found: Vesting-locked funds can be spent early by bypassing the `LockedCoins` check through the usei/wei precision bridge

### Title
Vesting-locked `usei` balance can be spent without the lock check via `BaseSendKeeper.SubWei` borrowing - (File: `sei-cosmos/x/bank/keeper/send.go`)

### Summary
The Ubiquity report describes a class of bug where a protocol tracks a "reserved" amount (`unclaimedPoolCollateral`) that is supposed to always be backed by real balance, but a separate code path can move the underlying balance below the reserved amount because it fails to re-check the invariant that the first path enforces. The sei-chain analog is the `usei`/`wei` balance-splitting bridge used by the EVM StateDB: `SubUnlockedCoins` enforces the vesting `LockedCoins` invariant for the `usei` portion of a debit, but `SubWei`, which can also mutate the `usei` balance when it needs to "borrow" a whole `usei` unit to cover a wei deficit, sets the balance directly via `k.setBalance` and never consults `LockedCoins`. This lets an EVM transaction spend tokens that are supposed to be locked under a vesting schedule.

### Finding Description
`DBImpl.SubBalance` (the `vm.StateDB` implementation used by every EVM transaction) splits the debited amount into a `usei` component and a sub-`usei` `wei` remainder, then calls two separate bank-keeper methods: [1](#0-0) 

`SubUnlockedCoins` is invariant-safe — it computes `spendable := balance.Sub(locked)` using `k.LockedCoins(ctx, addr)` and fails if the debit would eat into locked (vesting) coins: [2](#0-1) 

`SubWei`, however, when the requested wei amount exceeds the account's currently-tracked wei remainder, computes an aggregated balance (`usei*10^12 + wei`), subtracts the wei debit from it, and writes the resulting `usei`/`wei` split back with `k.setBalance` directly — with `checkNeg=true` only guarding against an overall negative balance, not against the vesting `LockedCoins` amount: [3](#0-2) 

Because `LockedCoins` is never consulted here, an account holding vesting/locked `usei` (e.g., a `ContinuousVestingAccount` or `DelayedVestingAccount`) can have its `usei` balance decremented by this path even though `SubUnlockedCoins` would have rejected the same debit. This effectively lets the account holder transfer out currently-locked (not-yet-vested) tokens through ordinary EVM transactions, defeating the vesting guarantee — the exact "invariant enforced on one path, silently bypassed on another" pattern described in the source report (there, `unclaimedPoolCollateral` was guaranteed by one check but drained through `amoMinterBorrow`, which lacked the equivalent check).

### Impact Explanation
This breaks a fund-safety invariant (vesting lock) that other Sei subsystems and integrators rely on: an account is not supposed to be able to move tokens that have not yet vested. Any unprivileged holder of a vesting account can use ordinary EVM transactions (e.g., `sendNative`/native value transfers, or any EVM call that triggers `SubBalance` with a wei remainder) to gradually convert and spend locked `usei` ahead of schedule, one `usei` unit at a time per triggering transaction. This is a genuine "unauthorized" bypass of a balance-freezing guarantee reachable purely through normal EVM transaction submission, matching the "permanent freezing"/"unauthorized transfer" bug class the original report falls under (loss of the lock guarantee is the sei-chain analog of loss of the collateral-backing guarantee).

### Likelihood Explanation
High likelihood: it requires no special privileges — any account with a vesting schedule can trigger it just by submitting EVM transactions whose value has a non-zero sub-`usei` (`wei`) component whenever their tracked `weiBalance` is smaller than that component (which is the common/default state, since `weiBalance` starts at 0 and is only nonzero after a prior partial-usei debit). This is entirely within reach of a normal, unprivileged EVM transaction sender/RPC client and requires no coordination with validators or other actors.

### Recommendation
`BaseSendKeeper.SubWei` should apply the same `LockedCoins`/spendable check that `SubUnlockedCoins` performs before it is allowed to reduce the `usei` component of the balance. Concretely, when the wei debit forces a borrow from `usei` (the `amt.GT(currentWeiBalance)` branch in [4](#0-3) ), the resulting `useiBalance` must be validated against `k.LockedCoins(ctx, addr)` for the base denom, returning `ErrInsufficientFunds` if the debit would dip into locked coins, mirroring the check already performed in `SubUnlockedCoins`.

### Proof of Concept
1. Create a vesting account (`ContinuousVestingAccount`) and fund it so that all `usei` is currently locked (nothing vested yet) and its stored `weiBalance` is `0`.
2. Associate the account with an EVM address and submit an EVM transaction whose value (or internal transfer via a contract/precompile) has a non-zero sub-`usei` remainder, e.g. transfer `1 wei` (in the 18-decimal EVM representation, i.e., an amount smaller than `10^12`).
3. `DBImpl.SubBalance` splits this into `usei=0, wei=1` and calls:
   - `SubUnlockedCoins(ctx, addr, {usei: 0})` — succeeds trivially since the `usei` portion is `0`.
   - `SubWei(ctx, addr, 1)` — since `currentWeiBalance (0) < 1`, it borrows: computes `currentAggregatedBalance = lockedUseiBalance * 10^12 + 0`, subtracts `1`, and calls `k.setBalance` directly to write `useiBalance - 1` with no check against `LockedCoins`.
4. The account's on-chain locked `usei` balance is reduced by 1 unit despite the vesting schedule, and the corresponding value is sent to the counterparty via `AddWei` on the recipient side — demonstrating that vesting-locked tokens were moved.
5. Repeating step 2 across multiple transactions (each time the account's tracked `weiBalance` is depleted back below the debited wei amount) allows the attacker to incrementally drain their entire locked balance ahead of the vesting schedule.

// SubUnlockedCoins removes the unlocked amt coins of the given account. An error is
// returned if the resulting balance is negative or the initial amount is invalid.
// A coin_spent event is emitted after.
func (k BaseSendKeeper) SubUnlockedCoins(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}

	lockedCoins := k.LockedCoins(ctx, addr)

	for _, coin := range amt {
		balance := k.GetBalance(ctx, addr, coin.Denom)
		if checkNeg {
			locked := sdk.NewCoin(coin.Denom, lockedCoins.AmountOf(coin.Denom))
			spendable := balance.Sub(locked)

			_, hasNeg := sdk.Coins{spendable}.SafeSub(sdk.Coins{coin})
			if hasNeg {
				return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%s is smaller than %s", spendable, coin)
			}
		}

func (k BaseSendKeeper) SubWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}
