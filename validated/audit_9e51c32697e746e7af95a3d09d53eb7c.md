## Analysis

The EIG‑7 report's core broken invariant is: **a unit-conversion helper silently floors/truncates an amount, and the difference between what was actually escrowed/burned and what is credited is discarded — permanently lost, with no compensation to the user.**

The `hyper-fungible-token` pallet has the exact same broken invariant on the receive path.

### Title
Truncating ERC20→local decimal conversion in `on_accept` permanently burns user principal on cross-chain deposits - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
When tokens are bridged from an EVM chain into this pallet, `on_accept` converts the raw ERC20 `message.amount` (expressed in `erc_decimals`) into the pallet's local balance denomination using `convert_to_balance`, which performs plain integer division and discards the remainder. If a user sends an amount on the EVM side that is not an exact multiple of the decimal scale factor, the discarded remainder is neither credited to the beneficiary nor tracked/refunded anywhere — it is permanently lost, exactly mirroring the EIG-7 rounding-loss pattern.

### Finding Description
`convert_to_balance` truncates via integer division and has no remainder-handling path: [1](#0-0) 

`register_token`/`update_token` only enforce `erc_decimals >= local_decimals` — a strict inequality is a normal, permitted configuration (e.g. an 18-decimal EVM token mapped to a 6- or 10-decimal local asset): [2](#0-1) 

In `on_accept`, the pallet decodes the attacker/user-controlled `message.amount` from the incoming post request and converts it directly to a local balance via the truncating helper, then mints/transfers exactly that (rounded-down) amount to the beneficiary: [3](#0-2) 

There is no code path that computes `value % scale` and returns it, accumulates it for later claim, or rejects amounts that aren't exact multiples of the scale factor. Compare with `send()` (the opposite direction), where the local→ERC20 conversion is a pure multiplication and thus lossless: [4](#0-3) 

Because the EVM-side contract escrows/burns the user's exact raw amount (`message.amount`) before dispatching the cross-chain message, but this pallet only credits `floor(message.amount / 10^(erc_decimals-local_decimals))`, the sub-scale remainder that was already locked/burned on the source chain is never accounted for on the destination chain. This is functionally identical to the EigenPod bug: `_calculateRestakedBalanceGwei` rounds the withdrawal amount down and the difference silently vanishes from user-owned funds.

### Impact Explanation
Any user bridging tokens through this pallet with an amount not divisible by the configured decimal scale factor between the EVM token and the local asset loses the truncated remainder permanently — no revert, no partial credit, no way to reclaim it. This is a direct, unauthorized loss of user principal funds triggered purely by ordinary use of the public `send`/receive flow, matching the bounty's "stealing or loss of funds" category.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — it is triggered by any ordinary user sending an amount that isn't an exact multiple of the scale factor (which is the common case for arbitrary transfer amounts, e.g. sending `123456789` wei of an 18-decimal token into a 6-decimal local asset). The precondition (`erc_decimals > local_decimals`) is an explicitly supported and unremarkable configuration, not an edge case requiring special setup.

### Recommendation
Either (a) reject `send`/incoming amounts that are not exact multiples of the decimal scale factor (revert with a clear error instead of silently truncating), or (b) compute and retain/refund the remainder — e.g., credit the truncated remainder back to the sender on the source chain before dispatch, or accumulate dust per-beneficiary on the destination chain so it can be swept/claimed rather than discarded.

### Proof of Concept
1. Register a token where the EVM contract uses 18 decimals and the local Substrate asset uses 6 decimals (`erc_decimals=18`, `local_decimals=6`, satisfying `erc_decimals >= local_decimals`) via `register_token`.
2. A user calls the EVM `HyperFungibleToken` contract's send function with `amount = 1_000_000_000_000_000_001` wei (18-decimals), which is escrowed/burned exactly on the EVM side and dispatched as `message.amount`.
3. On the Substrate side, `on_accept` calls `convert_to_balance(1_000_000_000_000_000_001, 18, 6)` → `1_000_000_000_000_000_001 / 10^12 = 1_000_000` (local units), truncating the `1` wei of ERC20-side remainder (scaled, `10^12 - 1` worth of ERC20 precision) that will never be minted/transferred to the beneficiary.
4. The beneficiary receives `1_000_000` local units instead of the exact proportional value; the remainder is unrecoverable — confirmable by inspecting `Precisions`, `convert_to_balance`, and the mint/transfer call sites shown above.

/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.

	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))

	dec_str.parse::<B>()
