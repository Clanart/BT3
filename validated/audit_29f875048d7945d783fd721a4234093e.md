### Title
Ed448 point decoding accepts torsion components, enabling forged Schnorr proofs - (File: crypto/ed448/src/point.rs)

### Summary
`Point::is_torsion_free` is mathematically a no-op: it computes `(-P) + P`, which is identity for every point. Consequently, `Ed448::read_G` accepts canonical encodings of points outside the prime-order subgroup, including low-order and mixed-order points. An unprivileged party can feed such bytes through public `read_G`, `SchnorrSignature::read`, commitment/proof decoding, or verifier APIs and cause verification equations to treat torsion terms incorrectly.

### Finding Description
`Point::from_bytes` attempts to reject non-prime-order points with `point.is_torsion_free()`, but `is_torsion_free` is implemented as `((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()`. Since `Scalar::ZERO - Scalar::ONE` is `-1`, the expression is always `-P + P == identity`, so the check accepts every successfully decoded curve point [1](#0-0) .

The generic `Ciphersuite::read_G` only requires `from_bytes` to succeed and the encoding to round-trip canonically; it does not add a subgroup check [2](#0-1) . `Ed448` uses this affected `Point` type directly as its group element [3](#0-2) .

This is analogous to an incomplete reserved-range denylist: “valid encoding” is confused with “member of the intended group.” The untrusted bytes are accepted even though they represent the excluded low-order component.

### Impact Explanation
Schnorr verification computes `R + cA - sG == identity` [4](#0-3) . If `A` contains an order-4 torsion component `T`, then `cA` only depends on `c mod 4` in that component. An attacker can select a torsion or mixed-order nonce `R` to cancel the torsion component while `s = 0`, producing a signature that verifies under a public key with no usable prime-order discrete logarithm relationship.

This can produce forged Schnorr proofs/signatures in protocols that accept Ed448 public inputs, including decoded commitment/public-key material and `SchnorrSignature::read` inputs. It also undermines the `PrimeGroup` assumption relied on by DLEq and threshold-key operations.

### Likelihood Explanation
The attack requires only public attacker-controlled bytes: a canonical Ed448 point encoding containing a low-order component and a signature/proof chosen to cancel it. Ed448 has cofactor 4, so suitable malformed inputs exist and are cheap to construct. The main environmental condition is that an in-scope verifier accepts an attacker-supplied Ed448 point or relies on a public key/commitment transported through `read_G`.

### Recommendation
Replace `is_torsion_free` with an actual prime-subgroup membership test. For Ed448, the standard check is `[q]P == identity`, where `q` is the prime subgroup order. If the intended representation permits only prime-order points, reject identity and every nonzero torsion component during `from_bytes`, then add tests for all canonical low-order encodings and mixed-order points. Do not rely on multiplication by `-1` or on canonical encoding checks to establish subgroup membership.

### Proof of Concept
Let `T` be an Ed448 point of order 4, such as the canonical encoding of the curve point `(x, y) = (1, 0)`. Choose an Ed448 public-key encoding `A = T`.

For `k ∈ {0,1,2,3}`:

1. Set `R = -kT` and `s = 0`.
2. Compute the protocol’s Fiat–Shamir challenge `c`, binding the encoded `R`, `A`, and message as required by that protocol.
3. Output signature/proof `(R, s)` when `c mod 4 == k`.

Verification then computes:

```text
R + cA - sG
= -kT + cT - 0
= (c - k)T
= identity    because c ≡ k (mod 4) and 4T = identity
```

Trying four canonical `R` values yields a matching `k` with probability approximately `1/4` per challenge/message. The malformed public key and nonce both pass decoding because `is_torsion_free` always returns true.
