Line 337 in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) only checks `_orders[commitment][token] != 0` for **each input token supplied by the user in `order.inputs`** — it never checks that `token != TRANSACTION_FEES`. The `TRANSACTION_FEES` sentinel is just `address(uint160(uint256(keccak256("txFees"))))`, an ordinary-looking address that is fully usable as an ERC-20 `token` field, exactly like `0xdeadbeef` was an ordinary-looking "special" address in the GNTDeposit report. This is the same bug class: a hardcoded/derived sentinel address is used for internal bookkeeping (there, burn destination; here, relayer-fee storage) but nothing stops that exact address from colliding with a value an untrusted actor can supply through a normal, unprivileged code path.

### Title
Unauthenticated collision between user-supplied input token address and the `TRANSACTION_FEES` sentinel corrupts escrow accounting - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentsBase` reserves the address `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` as a sentinel key in the shared `_orders[commitment][token]` mapping to store the Hyperbridge relayer fee for an order [1](#0-0) . `placeOrder` writes user input token escrow amounts into that very same mapping, keyed by whatever token address the caller supplies in `order.inputs[i].token`, and only guards against *duplicate* input tokens — not against the sentinel value [2](#0-1) . Immediately after, if `order.fees > 0`, the same slot is overwritten with the fee amount [3](#0-2) .

### Finding Description
An unprivileged user calling `placeOrder` fully controls `order.inputs[i].token` (cast from `bytes32` to `address` at line 234/284/316/335) [4](#0-3) . Nothing prevents them from setting one input's token field to exactly `TRANSACTION_FEES`. Because Phase 3 writes `_orders[commitment][token] = reducedInputs[i].amount` for that token before the fee write executes, and the fee write at line 361 unconditionally does `_orders[commitment][TRANSACTION_FEES] = order.fees`, the second write silently clobbers the first (or vice versa depending on ordering within the same transaction), corrupting the escrow bookkeeping for that commitment. This differs qualitatively from the "reject duplicate input token" check at line 337, which only compares user-input tokens against each other, never against the reserved sentinel constant.

The corrupted value is `_orders[commitment][TRANSACTION_FEES]`, which is read and paid out in `_withdraw` at fill/refund time: `uint256 fees = _orders[body.commitment][TRANSACTION_FEES]; ... IERC20(feeToken()).safeTransfer(beneficiary, fees);` [5](#0-4) . If the escrowed "input token" amount is overwritten by the fee value (or the fee is overwritten by an attacker-chosen escrow amount), the gateway will transfer `feeToken` amounts unrelated to the actual fee collected, and/or lose track of the true escrow balance for the token that collided with `TRANSACTION_FEES`, since `_orders[commitment][token]` for that colliding "token" no longer reflects reality. Because `_withdraw` transfers `feeToken()` (the protocol fee token) using whatever numeric value sits at the `TRANSACTION_FEES` key regardless of provenance, an attacker who engineers a large escrowed "input amount" to land at that key can cause `_withdraw` to attempt to pay out that inflated number in `feeToken` — a token possibly different from what was escrowed — creating an accounting mismatch that can drain the gateway's genuine fee-token balance or lock/misdirect funds during settlement.

### Impact Explanation
This hits the bounty's "logic attacks / transaction manipulation / unauthorized transaction" and "funds must move exactly once and only to the rightful beneficiary and amount" pivots. Escrow release (`_withdraw`) is a core custody path reached by every `fillOrder`/`cancelOrder` call; corrupting `_orders[commitment][TRANSACTION_FEES]` directly manipulates the amount transferred in the protocol's `feeToken` to a solver or user beneficiary, independent of what was actually deposited — a wrong-amount fund movement out of the gateway's live custody.

### Likelihood Explanation
The path is reachable by any unprivileged caller through the public `placeOrder` entrypoint with a single crafted `order.inputs[i].token = TRANSACTION_FEES` value — no relayer, prover, governance, or malicious peer involvement required. The only requirement is knowledge of the deterministic constant `keccak256("txFees")`, which is public in the deployed bytecode/ABI.

### Recommendation
In `placeOrder`, explicitly reject `token == TRANSACTION_FEES` for every entry in `order.inputs` (and any other place a user-controlled token address is cast and used as an `_orders` key), the same way duplicate-token checks already exist. More robustly, do not overload the `_orders[commitment][token]` mapping to store both real token escrow and the relayer-fee bookkeeping value — store the accumulated relayer fee in its own dedicated mapping (e.g., `mapping(bytes32 => uint256) _orderFees`) so no user-suppliable address can ever collide with it, mirroring the OpenZeppelin-style recommendation of keeping burn/fee accounting in a single, non-collidable internal representation rather than reusing a general-purpose token-address-keyed map.

### Proof of Concept
1. Attacker computes `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` (a fixed, publicly derivable constant).
2. Attacker calls `placeOrder` with `order.inputs = [{token: bytes32(uint256(uint160(TRANSACTION_FEES))), amount: X}]` and `order.fees = Y > 0`.
3. Phase 3 executes `_orders[commitment][TRANSACTION_FEES] = X` (line 338), passing the duplicate-token check since it is the only input.
4. Line 361 then executes `_orders[commitment][TRANSACTION_FEES] = Y`, overwriting `X` with `Y` (or vice versa if ordering were reversed in a variant call), so the escrow bookkeeping for the "input token" that happens to equal `TRANSACTION_FEES` is lost/replaced by the fee value.
5. On `fillOrder`/`cancelOrder` → `_withdraw`, the contract reads `_orders[commitment][TRANSACTION_FEES]` and transfers that amount in `feeToken()` to the beneficiary, and separately attempts to release the (now missing or wrong) escrow for the colliding token address, producing a fund-accounting mismatch between what was deposited and what is paid out [6](#0-5) .

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
