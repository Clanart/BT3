## Verdict: Valid finding (logic flaw), with one caveat noted below

### Title
`findContributionTargetDefaultBranch` ignores `forkContributionTarget` and can surface the parent's default branch even when the user selected "Self" - (File: `app/src/lib/branch.ts`)

### Summary
`findContributionTargetDefaultBranch` decides which "default branch" to hand to the create-branch / PR start-point logic. Its own doc comment says it should return the parent's default branch "if the user is contributing to the parent repository," implying it should consult the repository's fork contribution preference. The implementation does not do that check at all.

### Finding Description
The function only checks whether the repository has a `GitHubRepository` attached, not whether the user chose to contribute to the parent: [1](#0-0) 

```ts
export function findContributionTargetDefaultBranch(
  repository: Repository,
  { defaultBranch, upstreamDefaultBranch }: IBranchesState
): Branch | null {
  return isRepositoryWithGitHubRepository(repository)
    ? upstreamDefaultBranch ?? defaultBranch
    : defaultBranch
}
```

Contrast this with the rest of `app/src/models/repository.ts`, which does explicitly gate parent-repository behavior behind the workflow preference: [2](#0-1) 

`getNonForkGitHubRepository` and `isForkedRepositoryContributingToParent` both call `getForkContributionTarget(repository)` and branch on `ForkContributionTarget.Self` vs `ForkContributionTarget.Parent`. `findContributionTargetDefaultBranch`, despite its name suggesting equivalent semantics, has no such check — it will happily return `upstreamDefaultBranch` any time that value is non-null in `IBranchesState`, regardless of `repository.workflowPreferences.forkContributionTarget`.

The `upstreamDefaultBranch` field itself originates from `gitHubRepository.parent`, which is populated from the fetched repository metadata (the GitHub API's `parent` field on a repo object) — i.e., attacker-influenced data insofar as any repository a user forks determines what "parent" is reported.

### Impact Explanation
If `IBranchesState.upstreamDefaultBranch` is populated (which reflects `gitHubRepository.parent`'s default branch) for a fork whose owner explicitly set `forkContributionTarget = Self`, this function still returns the parent/upstream branch. Consumers of this function (`app-store.ts`, `app.tsx`, `menu-update.ts`) use its result to seed the default create-branch start point and PR base-branch defaults. This can silently default new branches/PRs to be based on/targeted at the wrong (upstream) owner's branch even though the user's explicit workflow preference says "keep contributions to my own fork" — a case of "silent corruption of what the user commits or pushes" in the sense that the base ref used for branch creation/PR flow doesn't match the user's chosen contribution target.

### Likelihood Explanation
This triggers deterministically whenever both conditions hold: (1) the repository is a fork with a `parent`, and (2) `IBranchesState.upstreamDefaultBranch` has been populated in the branches state cache — I was not able to fully confirm from `git-store.ts` whether `upstreamDefaultBranch` in `IBranchesState` is ever populated for forks where `forkContributionTarget` is `Self` (I could not inspect the exact population logic within the available iterations). If `git-store.ts` only ever sets `upstreamDefaultBranch` when the user is actively contributing to the parent, this function-level gap would be latent/unreachable in the current UI flow. This caveat should be verified directly in `app/src/lib/stores/git-store.ts` before treating this as exploitable end-to-end.

### Recommendation
Have `findContributionTargetDefaultBranch` check `isForkedRepositoryContributingToParent(repository)` (or `getForkContributionTarget(repository) === ForkContributionTarget.Parent`) before preferring `upstreamDefaultBranch`, mirroring `getNonForkGitHubRepository`'s pattern, e.g.:

```ts
return isForkedRepositoryContributingToParent(repository) && upstreamDefaultBranch
  ? upstreamDefaultBranch
  : defaultBranch
```

### Proof of Concept
Unit-test style repro (per the reporter's proof idea): construct a `RepositoryWithForkedGitHubRepository` with `workflowPreferences.forkContributionTarget = ForkContributionTarget.Self`, populate `IBranchesState.upstreamDefaultBranch` with a non-null `Branch`, and call `findContributionTargetDefaultBranch(repo, branchesState)`. Because the function never consults `forkContributionTarget`, it returns `upstreamDefaultBranch` rather than `defaultBranch`, confirmed directly by reading the implementation at `app/src/lib/branch.ts:23-25`. export function getNonForkGitHubRepository(
  repository: RepositoryWithGitHubRepository
): GitHubRepository {
  if (!isRepositoryWithForkedGitHubRepository(repository)) {
    // If the repository is not a fork, we don't have to worry about anything.
    return repository.gitHubRepository
  }

  const forkContributionTarget = getForkContributionTarget(repository)

  switch (forkContributionTarget) {
    case ForkContributionTarget.Self:
      return repository.gitHubRepository
    case ForkContributionTarget.Parent:
      return repository.gitHubRepository.parent
    default:
      return assertNever(
        forkContributionTarget,
        'Invalid fork contribution target'
      )
  }
}

/**
 * Returns a non-undefined forkContributionTarget for the specified repository.
 */
export function getForkContributionTarget(
  repository: Repository
): ForkContributionTarget {
  return repository.workflowPreferences.forkContributionTarget !== undefined
    ? repository.workflowPreferences.forkContributionTarget
    : ForkContributionTarget.Parent
}
