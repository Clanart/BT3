## Analysis

`pallet-ismp-relayer`'s `Fees<T>` storage tracks relayer earnings as a bare `U256` amount keyed only by `(StateMachine, address)` — it never records *which* fee-token that amount was denominated in when it accrued. [1](#0-0)  The amount comes from the actual fee attached to each request at the time it was dispatched on the source/EVM chain. [2](#0-1) 

When a relayer withdraws, `withdraw()` looks up the *current* `fee_token` configured for the destination chain in `HostParams::<T>` and builds the payout using that token, together with the raw accumulated `available_amount`:

```
let HostParam::EvmHostParam(params) = HostParams::<T>::get(withdrawal_data.dest_chain)...
let body = WithdrawalParams { beneficiary_address, amount: available_amount.into(), token: params.fee_token }
``` [3](#0-2) 

On the EVM side, `EvmHost.updateHostParamsInternal` only guards against changing `feeToken` while the *host's own contract balance* of the old token is non-zero (`CannotChangeFeeToken`):

```
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [4](#0-3) 

This check protects the *host contract's own token treasury*, but it has no awareness of `pallet-ismp-relayer`'s separate `Fees<T>` ledger on Hyperbridge, which represents amounts relayers are *owed* for past deliveries, denominated in whatever `feeToken` was live when those deliveries were proven and fees dispatched. Governance changing `feeToken` (a documented, expected operation — "the host stores a configurable `feeToken` address that governance can update without a redeploy") [5](#0-4)  silently re-denominates every relayer's still-unclaimed `Fees<T>` balance into the new token at 1:1 nominal value, with no re-pricing or token identity carried forward.

This is the exact structural class of bug in the referenced report: an accrual/claim system that lets an already-earned balance be paid out in a *different* token than the one it was earned in, because the storage doesn't bind claims to the token that was live at accrual time — just like Yield's rewards contract binding future claims to whatever `rewardsToken` is set at claim time rather than accrual time.

### Title
Relayer fee ledger is not token-bound, so a `feeToken` change re-denominates already-accrued balances - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Fees<T>` accumulates relayer earnings as a plain numeric balance per `(StateMachine, address)`, with no record of the ERC20 token that amount was denominated in at accrual time. `withdraw()` resolves the payout token from the *current* `HostParams::<T>::fee_token` for the destination chain at withdrawal time, not the token active when the fee was earned.

### Finding Description
`accumulate()` credits `Fees::<T>` with the raw `fee` value read from the source chain's `RequestMetadata`/`FeeMetadata` at the time the request was dispatched (denominated in whatever `feeToken` the source `EvmHost` had configured then). [6](#0-5)  This value is stored purely as a `U256` with no token tag. [7](#0-6) 

`withdraw()` later reads whichever `fee_token` is *currently* set for that destination chain and pays out the full accumulated `available_amount` in that token. [8](#0-7)  `EvmHost.updateHostParamsInternal` only verifies that the *host contract's* own balance of the old token is zero before allowing a `feeToken` swap; it has no visibility into, and does not protect, relayer claims parked in `pallet-ismp-relayer`'s independent `Fees<T>` storage on Hyperbridge. [9](#0-8) 

Consequently any legitimate `feeToken` migration (an operation the docs describe as a normal governance action, not an attack) [5](#0-4)  silently changes the economic value of every relayer's outstanding, already-earned `Fees<T>` balance for that destination chain — paid out 1:1 numerically in a token that may be worth far more or far less than the one in which the fee was actually collected from users.

### Impact Explanation
This breaks the "moves exactly once and only to the rightful beneficiary and amount" invariant for relayer rewards: the *amount* paid is numerically preserved but the *value* transferred is wrong, either overpaying relayers (draining the new fee token's balance sourced from other users' fees) or underpaying them (a relayer that delivered value in an expensive token gets shortchanged in a cheap one). Because withdrawals are unsigned/permissionless extrinsics gated only by signature+nonce checks (no fee-token binding), any relayer with a stale accrual can claim it against a since-changed token without any additional privilege.

### Likelihood Explanation
Requires only a normal, expected `feeToken` update by governance/host-manager plus at least one relayer with an outstanding, unclaimed `Fees<T>` balance at the time of the switch — a routine and even documented operational scenario, not an attacker-controlled precondition. No malicious peer, prover, relayer, or admin behavior is needed; the corrupting action is a legitimate parameter update interacting with an under-specified reward ledger.

### Recommendation
Tag each `Fees<T>` entry (or each accrual increment) with the fee-token address it was denominated in at accrual time, and have `withdraw()` dispatch per-token withdrawal instructions using that recorded token instead of re-reading `HostParams::<T>::fee_token` at withdrawal time. Alternatively, require all outstanding `Fees<T>` balances for a chain to be fully claimed/settled before `updateHostParams` is permitted to change that chain's `fee_token`, mirroring the existing "drain-before-switch" guard already applied to the `EvmHost` contract's own balance.

### Proof of Concept
1. Relayer delivers messages while `EvmHost.feeToken = TokenA`; `pallet-ismp-relayer::accumulate` credits `Fees::<T>[dest_chain][relayer] += X` based on `TokenA`-denominated fees read from source proofs.
2. Governance drains `EvmHost`'s `TokenA` balance to zero (satisfying `CannotChangeFeeToken`) and calls `updateHostParams` to set `feeToken = TokenB` (higher value) via the host-manager flow. [9](#0-8) 
3. Relayer calls `withdraw_fees`; `withdraw()` reads the now-current `params.fee_token = TokenB` and constructs `WithdrawalParams{ amount: X, token: TokenB }`. [3](#0-2) 
4. The destination `EvmHost.withdraw()` transfers `X` units of `TokenB` to the relayer — the same numeric amount originally earned in `TokenA`, but now worth substantially more (or less), with no on-chain check reconciling the token mismatch. [10](#0-9)
