### Title
Attacker-controlled `.gitmodules` in a cloned/fetched repository forces `submodule.update` with `protocol.file.allow=always`, enabling submodule clones from arbitrary local `file://` paths - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation()` conditionally runs `git submodule update --init --recursive` with `-c protocol.file.allow=always` whenever it is invoked with `allowFileProtocol: true`. [1](#0-0)  This flag is threaded through `checkoutBranch()` / `checkoutCommit()` as a caller-supplied boolean used specifically to make submodule initialization succeed for local/private forks whose `.gitmodules` reference `file://` or filesystem-path URLs. [2](#0-1) [3](#0-2)  The submodule URLs themselves, however, come entirely from the `.gitmodules` file of the branch/commit being checked out - content fully controlled by whoever pushed that branch, i.e. an untrusted remote/collaborator.

### Finding Description
`git submodule update --init --recursive` reads submodule URLs straight out of `.gitmodules` in the working tree at checkout time. When Desktop enables `protocol.file.allow=always` for this operation, Git will honor `file://` (and bare local path) URLs in `.gitmodules` without restriction, because `protocol.file.allow=always` is a blanket override, not scoped to any specific already-known-safe URL. There is no validation in `updateSubmodulesAfterOperation()` of the actual submodule URLs before running the command with this flag enabled - it just naively appends `-c protocol.file.allow=always` to the args array. [4](#0-3) 

This differs qualitatively from the Socket `Owner`-adds-arbitrary-route bug in structure but matches its broken invariant: a piece of state that is nominally "just data" (a submodule URL entry, analogous to a "route") is trusted to perform a privileged operation (a local filesystem clone) once a caller flag flips on the wrong invariant. Here the "privileged operation" is Git's `submodule update` being allowed to treat `file://` URLs as first-class, letting a hostile `.gitmodules` entry point at arbitrary local paths on the victim's machine (e.g. `file:///Users/victim/Documents/GitHub/some-other-private-repo`, or any world/user-readable directory) and have Desktop silently clone it as a "submodule" directory inside the checked-out repository.

Because the URL is attacker-supplied and unchecked, an attacker who can get a victim to fetch/checkout a branch (public fork, PR branch, or any repo the victim opens in Desktop) can point a submodule at a sibling local repository/directory the victim has on disk. Git will then populate `test-submodule/` (or whatever path chosen in `.gitmodules`) with a live clone of that local directory, which the victim may subsequently inspect, commit, or push - effectively exfiltrating file contents from other local directories on the victim's machine into the checked-out repo's working tree.

### Impact Explanation
If exploited, this results in:
- Reading files outside the intended repository boundary (the explicit "file read outside the repo" impact criterion), since Git's local-clone-via-`file://` transport can hard-link/copy the full contents of an arbitrary local repository the attacker names, subject only to OS filesystem permissions of the user running Desktop.
- Potential silent corruption of what a user later commits/pushes, if the victim doesn't notice the new submodule directory before staging/committing changes, inadvertently leaking the copied content to a remote the attacker controls.

This is a plausible but bounded impact: it does not grant arbitrary code execution by itself, and it depends on the attacker guessing/knowing paths on the victim's disk (though common paths such as the default GitHub Desktop clone root, `~/.ssh`-adjacent locations, or predictable sibling project directories make this practical).

### Likelihood Explanation
Likelihood is moderate. The `allowFileProtocol` flag must be `true` at the call site for the vulnerability to manifest; the default for `checkoutBranch`/`checkoutCommit` is `false`. [5](#0-4) [6](#0-5)  I was not able to fully trace, within the available tool budget, every UI/app-store call site that decides when `true` is passed (test fixtures show it used to support "uninitialized submodule" checkout flows for locally-forked/private repositories). If Desktop enables this flag broadly (e.g., whenever a repository is detected as a local fork, or for any repository with submodules pointing at non-HTTP(S) URLs) rather than narrowly to a specific known-safe origin, the attack surface is triggered by simply opening/checking out an attacker-crafted branch.

### Recommendation
- Never enable `protocol.file.allow=always` based on a boolean flag alone; instead validate that any `file://` submodule URL actually resolves to a path the app itself provisioned (e.g., matches the known local fork's path) before allowing it.
- Prefer an allow-list approach: pass `protocol.file.allow=always` only when Desktop can verify each submodule URL is safe (e.g., is a subpath of a trusted directory or the same repository's already-trusted remote), rather than a global toggle applied to `git submodule update --init --recursive` for the whole tree.
- Consider parsing `.gitmodules` and warning or requiring confirmation before initializing any submodule whose URL uses `file://` or a bare local path, mirroring the "unsafe repository" ownership warnings already present in `rev-parse.ts`/`add-existing-repository.tsx`. [7](#0-6) 

### Proof of Concept
1. Attacker creates/pushes a branch to a repository the victim will clone or fetch (e.g., a fork or PR branch).
2. That branch's `.gitmodules` declares a submodule with `url = file:///Users/victim/Documents/GitHub/some-private-project` (or any path likely to exist on the victim's machine) at some innocuous-looking path, e.g. `vendor/lib`.
3. Victim opens the repository in Desktop and checks out the branch. If the code path that determines `allowFileProtocol` passes `true` for this repository/branch, `updateSubmodulesAfterOperation()` runs:
   `git -c protocol.file.allow=always submodule update --init --recursive` [4](#0-3) 
4. Git clones the local directory at the attacker-specified path into `vendor/lib` inside the victim's working tree, exposing its contents.
5. If the victim doesn't notice and commits/pushes, the exfiltrated content is now pushed to whatever remote the attacker controls (e.g., their fork), completing exfiltration.

**Uncertainty:** I could not fully confirm, within the available search budget, every production call site in `app-store.ts`/`dispatcher.ts` that sets `allowFileProtocol: true` for `checkoutBranch`/`checkoutCommit`, nor the exact heuristic used to decide when it's considered "safe" to enable. This determines whether the flag is scoped narrowly (e.g., only for repositories the user explicitly forked locally) or broadly enough to be triggered by any untrusted branch checkout. I recommend a full trace of those call sites (in `app/src/lib/stores/app-store.ts` and `app/src/ui/dispatcher/dispatcher.ts`) to confirm real-world reachability before treating this as confirmed-exploitable versus a defense-in-depth concern.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
