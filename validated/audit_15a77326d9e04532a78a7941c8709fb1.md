### Title
Stale line-index diff selections are silently re-applied to a changed diff during partial commits, allowing repository-side content to be committed without user review - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The C4 report's core invariant break is: an authorization/validity check (`currentOperators`) is established once, but a later operation in the same flow reuses that stale check instead of re-validating against the current state, letting already-invalidated actors keep acting as if still valid. The closest verifiable analog in GitHub Desktop is the partial-commit ("stage selected lines") pipeline: the user's line selection is validated against a diff loaded at one point in time, but the actual patch used to stage/commit is generated from a diff re-fetched at a *later* point in time, using the *same* stale line indices without re-validating that those indices still correspond to the content the user actually reviewed.

### Finding Description
When a user stages a subset of lines in a modified file, the app records the selection as a set of *absolute line indices* into a previously loaded diff (`DiffSelection`/`file.selection`). At commit time, `stageFiles` calls `applyPatchToIndex` for any file with a partial selection: [1](#0-0) 

`applyPatchToIndex` does **not** reuse the diff the user looked at when selecting lines — it re-fetches the diff from the working directory at the moment of staging: [2](#0-1) 

That freshly-fetched diff is then fed into `formatPatch`, which decides what to include purely by testing `file.selection.isSelected(absoluteIndex)` against line *indices*, with no comparison of the line's *content* to what was originally shown to the user: [3](#0-2) 

The only "staleness" mitigation that exists is in `app-store.ts`, and it is explicitly acknowledged as incomplete: when a new diff is loaded, the code only recomputes which indices are still *selectable* (i.e., still an includeable line in the new diff, not a context line), not whether the *content* at a given index still matches what the user actually saw and chose to include: [4](#0-3) 

The comment on lines 3480-3485 states this directly: *"The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..."*

Because that gap is by design ("for now"), if the tracked file's content changes between the time the user reviews/selects lines in the Changes view and the time `_commitIncludedChanges` triggers `createCommit` → `stageFiles` → `applyPatchToIndex`, the line-index-based selection from the old diff is silently applied to the new diff content. A file in a cloned/checked-out repository can be modified during that window by anything running inside the repo's working tree that the user has already permitted to run as part of normal repo interaction (a `post-checkout`/file-watcher/build script, an IDE auto-format-on-save triggered by opening the file, a submodule update task, etc.) — this is the "attacker controls a cloned/fetched repository" primitive from the report, translated to Desktop's commit path instead of the gateway's operator path.

### Impact Explanation
This breaks the same invariant class as the report: the check ("this exact content is what the user selected to include") is performed once, but the action taken later (staging/patch application) is executed against different, unreviewed content while still treating the earlier selection as authoritative. The result is a silent corruption of what the user commits: content the user never explicitly reviewed or opted into can be swept into the commit that is subsequently pushed, purely because it landed at the same line index as something the user did select. This matches the in-scope impact "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires a race between diff-load time and stage/commit time, plus the changed file's replacement content occupying the same line-count/hunk-shape so `git apply` still succeeds — narrowing but not eliminating the window compared to the original Solidity finding (which required a signed batch with multiple `transferOperatorship` commands). Desktop's own code comment concedes the staleness gap exists ("for now"), which is stronger evidence than speculation. However, this is a race-condition-dependent path rather than a deterministic replayable exploit, so likelihood is lower than the original Medium-severity finding.

### Recommendation
When staging partial selections, do not trust index-based selection alone against a diff re-fetched at commit time. Either (a) commit using the exact diff/patch text captured at selection time (fail/re-prompt if the file has changed since, rather than silently regenerating against new content), or (b) when recomputing selectable lines as done in `app-store.ts` (lines 3478-3493), also compare line *content* (not just index) and drop/re-confirm any selection whose underlying text no longer matches what was originally selected.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`, adding a new line `A` at line 10.
2. In the Changes view, select only line 10 (`A`) for partial staging; leave the rest of the diff unselected.
3. Before clicking "Commit", have some process inside the working tree (e.g., an npm/build script triggered by `git status`/watch tooling, or simply editing the file via another already-permitted tool) rewrite line 10 in place to different content `B` (same position, same "added line" shape, so `getRepositoryType`/diff hunk counts remain compatible).
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`), and `formatPatch` includes whatever is now at index 10 (`B`) because `isSelected(absoluteIndex)` only checks the index, not the content (`app/src/lib/patch-formatter.ts:157`).
5. The resulting commit contains `B`, which the user never saw or selected, while the UI led them to believe they were committing `A`.
