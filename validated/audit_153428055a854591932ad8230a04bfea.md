This claim does not hold up under the actual code path. `SessionRepository.load_session` and `delete_session` in `lib/shopify_app/session/session_repository.rb` do parse the id string with a naive regex/`split("_")`, but the `id` they receive is never attacker-supplied raw text — it is derived by `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token(id_token:, online:)` (a `shopify_api` gem method, outside this repo's scope) from the verified JWT payload (`current_shopify_session_id` in `lib/shopify_app/controller_concerns/token_exchange.rb:44-49`), or from `ShopifyAPI::Utils::SessionUtils.current_session_id(shopify_id_token, cookies, is_online)` in `load_current_session` (`lib/shopify_app/controller_concerns/login_protection.rb:270-277`). [1](#0-0) [2](#0-1) 

The JWT (`shopify_id_token`) is parsed with `ShopifyAPI::Auth::JwtPayload.new(shopify_id_token)`, which verifies the signature against the app's `api_secret_key` and raises `ShopifyAPI::Errors::InvalidJwtTokenError` on failure — an attacker without that secret cannot forge a token asserting an arbitrary shop domain or user id. [3](#0-2) [4](#0-3) 

Additionally, `TokenExchange#activate_shopify_session` calls `reject_mismatched_requested_shopify_domain`, which compares the requested shop (`params[:shop]`) against the domain authenticated from the verified token, returning `401 Unauthorized` on mismatch — so even the `shop` query param cannot be used to redirect load/delete operations to a different tenant's session. [5](#0-4) 

Because the `offline_<domain>` / `<...>_<user_id>` string is always derived from claims (`dest`/`sub`) inside a JWT that must carry a valid HMAC signature computed with the app's secret key, the "id" that `load_session`/`delete_session` parses is cryptographically bound to the shop/user Shopify itself asserted — not attacker-controlled input. The regex-based parsing in `SessionRepository` (naive as it is) only ever operates on that trusted, already-verified string; there is no code path where an unauthenticated/unprivileged client can inject a crafted `session_id` bypassing JWT verification. The `test/shopify_app/session/session_repository_test.rb` unit tests confirm the parsing behavior in isolation but do not demonstrate any reachable exploit path from an unprivileged HTTP request.
