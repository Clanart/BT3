### Title
`SignableTransaction::new` omits the OP_RETURN data output from the size/fee calculation, producing transactions whose real fee rate falls below the relay minimum and locking funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying `data` into `tx_outs`, but then computes the transaction's weight and virtual size — and therefore `needed_fee`, the `TooLowFee` minimum-fee check, and the change amount — using only `payments`, excluding the data output. The resulting transaction is larger than accounted for, so the fee actually paid (inputs minus outputs) can be below Bitcoin's default minimum relay fee even though the `TooLowFee` check passed, or below the caller-specified `fee_per_vbyte`. Analogous to the Biconomy report (a wrong fee/amount calculation rendering funds unclaimable/unmovable), this makes the constructed transaction unbroadcastable, leaving the selected inputs unspendable. [1](#0-0) 

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs), the OP_RETURN output is appended to `tx_outs` at lines 194-202. However, the weight/vbytes calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing the `payments` slice — not `tx_outs`. The same mistake is repeated for the change-bearing variant at lines 225-226 (`payments, Some(&change)`). [2](#0-1) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a transaction that is ~90+ vbytes smaller than the real one whenever `data` is `Some` (data up to 80 bytes, checked at line 171, plus OP_RETURN overhead). [3](#0-2) 
2. The minimum-relay-fee check at line 211 compares this underestimated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` where `vbytes` is also underestimated. A caller requesting exactly the minimum relay rate produces a transaction whose actual paid fee (`needed_fee`, or `fee_with_change`) is below the true minimum for its real size — the node rejects it from the mempool. [4](#0-3) 
3. The change output value is computed as `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228), over-crediting change by exactly the unaccounted fee. The transaction still builds and signs successfully — the defect only surfaces at broadcast time. [5](#0-4) 

Additionally, the solvency check at line 215 uses `needed_fee` (no-change size) while the change path requires `fee_with_change`; the `checked_sub` silently swallows the gap, so the leftover — up to `fee_with_change - 1` satoshis, which can exceed `DUST` at high fee rates — is paid entirely as excess miner fee instead of being returned or reported. [6](#0-5) 

### Impact Explanation
The wallet produces a signed transaction that cannot be relayed/mined (actual fee rate below `DEFAULT_MIN_RELAY_TX_FEE` for its true size), so the inputs it spends are effectively frozen until the caller rebuilds the transaction with corrected accounting — directly analogous to the reference bug where wrong math makes funds unwithdrawable. In the change-suppression edge case, funds are irreversibly lost to miners as excess fees. Severity: Medium (loss is bounded by the fee region and requires `data` to be set or a specific input/fee alignment, but it is deterministic once triggered). [7](#0-6) 

### Likelihood Explanation
`SignableTransaction::new` is a public API taking `data`, `payments`, `change`, and `fee_per_vbyte` from callers, so any integration that attaches data (e.g., the processor's documented need to "embed arbitrary data") while requesting a fee rate at or near the relay minimum hits this deterministically. The change-suppression/excess-fee path triggers whenever `payment_sat + needed_fee <= input_sat < payment_sat + fee_with_change`. Likelihood: Medium. [8](#0-7) 

### Recommendation
Build the full output list (payments + optional OP_RETURN + optional change) before computing weight, or pass `tx_outs` into `calculate_weight_vbytes` so `vbytes`/`needed_fee`/`fee_with_change` and the `TooLowFee` check reflect the final transaction. Also, when `checked_sub(payment_sat + fee_with_change)` fails but the leftover exceeds `DUST`, either reduce the fee or return an explicit error rather than silently converting the entire remainder into miner fees. [9](#0-8)
