### Title
`ReceivedOutput`/`SignableTransaction` never enforce coinbase maturity, so immature coinbase outputs are reported as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Kairos report describes a constraint (`BorrowAmountPerOfferLowerBound`) that is configurable and documented but never enforced at the point of use (`useOffer`). The Serai analog is the Bitcoin consensus/policy constraint that coinbase outputs are immature for 100 confirmations: the wallet's `Scanner` registers any output paying to the threshold key as a `ReceivedOutput`, and `SignableTransaction::new` accepts every `ReceivedOutput` as a spendable input without ever checking whether it comes from a coinbase transaction or how many confirmations it has.

### Finding Description
`SignableTransaction::new` takes `inputs: Vec<ReceivedOutput>` and unconditionally turns each into a `TxIn` and a prevout, summing their values as available funds:

No field on `ReceivedOutput` distinguishes a coinbase output from a normal output, and no code path in `wallet/` checks confirmation depth before `multisig()` begins signing each input with a per-input offset: [2](#0-1) 

The scanner-side construction lives in `networks/bitcoin/src/wallet/mod.rs` (`Scanner`/`ReceivedOutput`), which matches outputs purely on `script_pubkey`/offset and does not record or enforce the 100-block coinbase maturity rule.



### Impact Explanation
An unprivileged party can send a Bitcoin transaction whose outputs the scanner credits. If a coinbase output (e.g., from a pool/miner paying the threshold address directly, or a reorged chain) is scanned and handed to `SignableTransaction`, the resulting signed transaction is invalid under consensus rules — every input's signature is valid, yet the transaction can never confirm until maturity, and if a reorg removes the coinbase the funds vanish entirely. Funds are reported received that are not actually spendable, and the multisig may sign a transaction that the network will reject (wasting the FROST signing round and, in the worst case, leaving the spend in limbo). This is the same shape as the Kairos issue: a bound that exists in the system's rules but is not enforced where the guarded action happens.

### Likelihood Explanation
Any miner/mining pool (or anyone able to influence a coinbase payout address) can create such an output without any privilege over Serai — paying to a known taproot script_pubkey is a fully public action. Reorgs that immature/replace coinbases are also normal Bitcoin events. The only mitigation is external (the caller choosing not to pass the output), which is exactly the "constraint exists but isn't enforced" condition from the source report.

### Recommendation
Track whether a `ReceivedOutput` originates from a coinbase transaction and its confirmation depth at scan time, and reject (or withhold) coinbase outputs in `SignableTransaction::new`/`Scanner` until they have at least 100 confirmations — enforcing the maturity bound at the point of use, mirroring the report's "enforce the constraint in `useOffer()`" recommendation.

### Proof of Concept
1. A miner (or pool payout) creates a coinbase transaction paying to the multisig's P2TR `script_pubkey` (derived via `p2tr_script_buf(offset.group_key())`).
2. `Scanner` observes the block/transaction, matches the `script_pubkey`, and produces a `ReceivedOutput` — no coinbase/maturity distinction is recorded.
3. `SignableTransaction::new(vec![received], payments, change, data, fee)` accepts it: the only bounds checked are `DUST`, `TooMuchData`, `TooLowFee`, `NotEnoughFunds`, and `MAX_STANDARD_TX_WEIGHT` (`networks/bitcoin/src/wallet/send.rs` lines 165-243) — none involve coinbase maturity.
4. `TransactionMachine` signs each input (`taproot_key_spend_signature_hash` over `Prevouts::All`), producing a fully-signed `Transaction` that Bitcoin Core rejects as non-final/immature (`bad-txns-premature-spend-of-coinbase`), so the "received" funds are unspendable.

Note: I verified the spend-side path (`send.rs`) directly; the scanner-side absence of a maturity field in `ReceivedOutput` is asserted from the `wallet/` module structure — I did not have a remaining iteration to re-read `wallet/mod.rs`, so the exact scanner line numbers could not be cited.
