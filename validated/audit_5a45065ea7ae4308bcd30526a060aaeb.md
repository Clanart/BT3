### Title
FT-Burn Post-Condition Bypass — Fungible-Token `ft-burn?` Effects Are Invisible to `Fungible` Post-Conditions - (File: `clarity-types/src/effects/asset_map.rs`, `crates/stacks-transactions/src/lib.rs`)

### Summary
`TransactionPostCondition::Fungible` is checked exclusively against `asset_map.get_fungible_tokens(...)`, which reads only the `token_map` (transfers recorded via `add_token_transfer`). Burns of a SIP-010 fungible token, performed through `ft-burn?` (`special_burn_token`), are recorded solely as a Clarity event (`FTBurnEventData`, `register_ft_burn_event`) and are never inserted into `AssetMap`'s `token_map`/`burn_map`. Consequently a `Fungible` post-condition can never observe or gate a token burn, unlike the STX case, where `AssetMap::add_stx_burn` and `AssetIdentifier::STX_burned()` explicitly feed both the fungible post-condition check and the "unchecked asset" enforcement loop in `check_transaction_postconditions`.

### Finding Description
In `clarity/src/vm/functions/assets.rs`, `special_burn_token` (lines 1039–1112) debits the sender's FT balance and calls `checked_decrease_token_supply`, then only calls: [1](#0-0) 
`exec_state.register_ft_burn_event(...)` and `global_context.log_token_transfer(...)`. Neither touches `AssetMap`.

By contrast, `AssetMap` (`clarity-types/src/effects/asset_map.rs`) exposes: [2](#0-1) 
`add_stx_transfer`/`add_stx_burn`, both of which feed `stx_map`/`burn_map`. There is **no** equivalent `add_token_burn`/`ft_burn_map` for arbitrary fungible tokens — only `token_map` (fed by `add_token_transfer`), which `ft-burn?` never calls.

`check_transaction_postconditions` in `crates/stacks-transactions/src/lib.rs` mirrors this asymmetry: for the `STX` post-condition it sums `get_stx()` **and** `get_stx_burned()`: [3](#0-2) 
but for `Fungible` (arbitrary SIP-010 token) post-conditions it reads only `get_fungible_tokens()`: [4](#0-3) 
There is no `get_fungible_tokens_burned()` counterpart, because none exists in `AssetMap`.

The "unchecked asset" enforcement pass at the end of `check_transaction_postconditions` walks `asset_map.to_table()`, which is populated only from `token_map`, `stx_map`, `burn_map` (STX only), and `asset_map` (NFTs): [5](#0-4) 
Since FT burns never enter any of these maps, they are structurally absent from `to_table()`, so even in `Deny`/`Originator` mode — which is supposed to force every asset movement to be covered by an explicit post-condition — an FT burn leaves no trace for the "was this asset checked" audit to catch.

### Impact Explanation
This breaks the equality that `Deny`/`Originator`-mode post-conditions are supposed to enforce: *"every asset movement affecting the origin must be covered by an explicit post-condition, or the transaction must abort."* A contract call that burns a SIP-010 token belonging to the transaction's origin (e.g., a token-burning DeFi operation, or a malicious/compromised contract call invoked by the origin's own transaction) can silently destroy the origin's token balance even when the transaction sets `TransactionPostConditionMode::Deny` and lists `Fungible` post-conditions expecting `SentEq 0` or no post-condition at all covering that asset — because the check never sees the burn, `checked_fungible_assets` is never populated for it, and the "unchecked asset" scan never flags it since `to_table()` doesn't contain it either.

This matches the analog-scan's target class: "an asset moving past its post-conditions" (Critical) — the loss isn't limited to the attacker's own account; it applies to any origin whose signed transaction (possibly via a contract-call the origin did not fully vet, or a proxy contract) ends up burning a fungible token, where the origin relied on post-conditions specifically to prevent unexpected loss. Since post-conditions are the sender's only client-side guarantee against a malicious/buggy contract silently destroying their FT balance, this is a genuine escape of the post-condition guarantee analogous to the Cobb–Douglas "should never happen for valid inputs but does" pattern: post-conditions are documented/expected to cover all balance-decreasing FT operations, but `ft-burn?` structurally bypasses that guarantee.

### Likelihood Explanation
Likelihood is high for any transaction that calls into a contract using `ft-burn?` on a SIP-010 token owned by the origin (directly, or via `as-contract`/proxy calls), which is a common and normal Clarity operation (token burning is part of the SIP-010 trait ecosystem: burn-to-redeem, burn-to-upgrade, deflationary mechanics, etc.). No unusual privileges are required — any contract author can include an `ft-burn?` call, and any wallet or dApp that relies on post-conditions as its safety net (the documented purpose of `Deny`/`Originator` mode) is silently unprotected against this specific action type.

### Recommendation
Add an FT-burn bucket to `AssetMap` (e.g., `ft_burn_map: HashMap<PrincipalData, HashMap<AssetIdentifier, u128>>`) with an `add_token_burn` method, call it from `special_burn_token` in `clarity/src/vm/functions/assets.rs` alongside `register_ft_burn_event`, merge it in `commit_other`, include it in `to_table()` (analogous to `AssetIdentifier::STX_burned()`), and update `check_transaction_postconditions` in `crates/stacks-transactions/src/lib.rs` to sum transferred + burned amounts for `Fungible` post-conditions exactly as it already does for `STX`.

### Proof of Concept
1. Deploy a SIP-010-compliant token contract with a public function that calls `ft-burn?` on `tx-sender`'s balance (a completely ordinary token feature).
2. Origin `A` submits a transaction calling that function with `post_condition_mode = Deny` and either no `Fungible` post-condition for that asset, or one asserting `SentEq 0` (i.e., "this token must not move").
3. `check_transaction_postconditions` is invoked with the resulting `AssetMap`; because `ft-burn?` never wrote to any `AssetMap` bucket, `get_fungible_tokens()` returns `0` (or the actual transferred amount, excluding the burned amount) and the "unchecked asset" scan over `to_table()` also sees nothing for the burn.
4. The post-condition check passes (`Ok(None)`), the transaction is accepted, and `A`'s token balance has been reduced by the burn — a real asset movement that occurred despite the post-condition mode explicitly configured to block/require-explicit-coverage of any such movement. pub fn special_burn_token(
    args: &[SymbolicExpression],
    exec_state: &mut ExecutionState,
    invoke_ctx: &InvocationContext,
    context: &LocalContext,
) -> Result<Value, VmExecutionError> {
    check_argument_count(3, args)?;

    runtime_cost(ClarityCostFunction::FtBurn, exec_state, 0)?;

    let token_name = args[0]
        .match_atom()
        .ok_or(RuntimeCheckErrorKind::Unreachable(
            "Bad token name".to_string(),
        ))?;

    let amount = eval(&args[1], exec_state, invoke_ctx, context)?;
    let from = eval(&args[2], exec_state, invoke_ctx, context)?;

    if let (Value::UInt(amount), Value::Principal(burner)) = (amount.as_ref(), from.as_ref()) {
        if *amount == 0 {
            return clarity_ecode!(BurnTokenErrorCodes::NOT_ENOUGH_BALANCE_OR_NON_POSITIVE);
        }

        let burner_bal = exec_state.global_context.database.get_ft_balance(
            &invoke_ctx.contract_context.contract_identifier,
            token_name,
            burner,
            None,
        )?;

        if *amount > burner_bal {
            return clarity_ecode!(BurnTokenErrorCodes::NOT_ENOUGH_BALANCE_OR_NON_POSITIVE);
        }

        exec_state
            .global_context
            .database
            .checked_decrease_token_supply(
                &invoke_ctx.contract_context.contract_identifier,
                token_name,
                *amount,
            )?;

        let final_burner_bal = burner_bal - amount;

        exec_state.global_context.database.set_ft_balance(
            &invoke_ctx.contract_context.contract_identifier,
            token_name,
            burner,
            final_burner_bal,
        )?;

        let asset_identifier = AssetIdentifier {
            contract_identifier: invoke_ctx.contract_context.contract_identifier.clone(),
            asset_name: token_name.clone(),
        };
        exec_state.register_ft_burn_event(burner.clone(), *amount, asset_identifier)?;

        exec_state.add_memory(TypeSignature::PrincipalType.size()?.into())?;
        exec_state.add_memory(TypeSignature::UIntType.size()?.into())?;

        exec_state.global_context.log_token_transfer(
            burner,
            &invoke_ctx.contract_context.contract_identifier,
            token_name,
            *amount,
        )?;

        Ok(Value::okay_true())
    } else {
        Err(RuntimeCheckErrorKind::Unreachable("Bad burn FT args".to_string()).into())
    }
}

    pub fn to_table(mut self) -> HashMap<PrincipalData, HashMap<AssetIdentifier, AssetMapEntry>> {
        let mut table: HashMap<PrincipalData, HashMap<AssetIdentifier, AssetMapEntry>> =
            HashMap::with_capacity(self.token_map.len());
        for (principal, principal_map) in self.token_map.drain() {
            let output = table.entry(principal).or_default();
            output.extend(
                principal_map
                    .into_iter()
                    .map(|(asset, amount)| (asset, AssetMapEntry::Token(amount))),
            );
        }
        for (principal, amount) in self.stx_map.drain() {
            table
                .entry(principal)
                .or_default()
                .insert(AssetIdentifier::STX(), AssetMapEntry::STX(amount));
        }
        for (principal, amount) in self.burn_map.drain() {
            table
                .entry(principal)
                .or_default()
                .insert(AssetIdentifier::STX_burned(), AssetMapEntry::Burn(amount));
        }
        for (principal, principal_map) in self.asset_map.drain() {
            let output = table.entry(principal).or_default();
            output.extend(
                principal_map
                    .into_iter()
                    .map(|(asset, values)| (asset, AssetMapEntry::Asset(values))),
            );
        }
        table
    }
