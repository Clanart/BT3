### Title
Zero-initialized `last-update` timestamp inflates the liquidity/debt index on first accrual, corrupting zToken collateral pricing - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
Each vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks a `last-update` timestamp that is used to compute the elapsed time (`time-delta`) for compounding the debt index (`index`) and liquidity index (`lindex`). This mirrors the reported Gearbox `_timestampLU == 0` pattern: a "last-update" style timestamp that can be zero is fed straight into a multiplicative interest/index calculation instead of being special-cased.

### Finding Description
`next-index` and `next-liquidity-index` compute: [1](#0-0) 

```
(time-delta (- stacks-block-time (var-get last-update)))
(multiplier (if (is-eq time-delta u0) INDEX-PRECISION (calc-multiplier-delta rate time-delta true)))
```

The code only special-cases `time-delta == u0`; it does not special-case `last-update == u0`. If `last-update` is ever `u0` (e.g., before the first `accrue()` call ever mutates it, or the variable is left at its Clarity default), `time-delta` becomes `stacks-block-time - 0`, i.e. the raw absolute Stacks block time rather than the true elapsed seconds since the vault started accruing interest. This absolute value is many orders of magnitude larger than any real accrual interval, so `calc-multiplier-delta rate time-delta true` compounds `rate` over that entire (bogus) duration, producing a wildly inflated `index`/`lindex`.

`accrue()` further only refreshes `last-update` conditionally: [2](#0-1) 

```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```

So as long as `last-update` remains at its zero-initialized state (utilization/rate stayed at 0, so `idx`/`lidx` never moved), the first block in which utilization becomes non-zero will compute `time-delta` against the zero baseline, producing an enormous one-shot multiplier.

The corrupted `lindex` (liquidity index) is not confined to the vault: it is read directly by the market/oracle layer for collateral pricing via `resolve-ztoken`: [3](#0-2) 

```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
```

Every zToken price (`zSTX`, `zsBTC`, `zUSDC`, `zUSDH`, `zstSTX`, `zstSTXbtc`) used for health/LTV checks is `underlying-price * lindex / INDEX-PRECISION`. If `lindex` is corrupted upward by the zero-timestamp bug, every position collateralized with that zToken is valued far above its real worth.

### Impact Explanation
An inflated `lindex` directly inflates the on-chain collateral price returned by `resolve-ztoken`, which feeds into LTV/health calculations in the market contract. A borrower holding the affected zToken as collateral could borrow against phantom value, or an attacker could deposit a small amount, wait for the index to become poisoned (or trigger the state), and borrow far more than the true collateral backs — this is a direct path to protocol insolvency / theft of other users' deposited funds, matching the Critical impact bucket (protocol insolvency, funds at rest).

### Likelihood Explanation
The trigger condition requires `last-update` to still be at its zero/default state at the moment utilization first becomes non-zero (i.e., the vault has taken zero deposits/borrows for some measurable period, or `last-update` is never explicitly initialized to `stacks-block-time` at deploy/enable time). Whether the deployment/initialization script for each vault sets `last-update` to the deploy-time `stacks-block-time` could not be confirmed from the indexed contract fragments retrieved (the `initialize-contract`/constructor section of `v0-vault-stx.clar` was not fully visible in the available index snippets). This uncertainty affects likelihood: if initialization always sets `last-update` to a non-zero `stacks-block-time`, the practical trigger window is narrow (deploy transaction ordering); if it is left at Clarity's zero default until the first `accrue()`, the bug is guaranteed to fire on the very first rate-changing operation.

### Recommendation
- Explicitly initialize `last-update` to `stacks-block-time` in the vault's setup/initialization transaction, guaranteeing it is never zero after deployment.
- In `next-index` / `next-liquidity-index`, treat `last-update == u0` the same as `time-delta == u0` (i.e., skip compounding and just set the multiplier to `INDEX-PRECISION`) so a never-set timestamp cannot be interpreted as "genesis of time."
- Ensure `accrue()` unconditionally updates `last-update` on every call (not only when `idx`/`lidx` change), so a zero/stale baseline cannot silently persist across multiple blocks.

### Proof of Concept
1. Deploy (or consider) a vault where `last-update` is left at Clarity's default `u0` (not explicitly set at init).
2. Do not call any borrow/repay/accrue action for a period so utilization/rate remain `0` and `last-update` is never updated (per the conditional update in `accrue`).
3. Trigger the first borrow, which changes utilization/rate to non-zero and calls `accrue()`.
4. Inside `next-liquidity-index`, `time-delta = stacks-block-time - 0` evaluates to the full absolute Stacks block timestamp (a huge number), and `calc-multiplier-delta liquidity-rate time-delta false` compounds the rate over that bogus duration, producing a grossly inflated `lindex`.
5. Any zToken price computed via `resolve-ztoken` in `mainnet/contracts/market/v0-4-market.clar` now returns an inflated collateral value, allowing over-borrowing against that zToken. [1](#0-0) [2](#0-1) [3](#0-2)
