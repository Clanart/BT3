### Title
OP_RETURN data omitted from transaction fee and weight calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new()` appends an OP_RETURN output containing attacker-controlled `data` to the final transaction, but `calculate_weight_vbytes()` is only given the payment outputs and optional change output. The missing OP_RETURN output causes the fee, minimum-relay-fee check, change amount, and maximum-standard-weight check to be calculated over an incomplete transaction. [1](#0-0) [2](#0-1) 

### Finding Description
When `data` is present, the code appends a zero-valued OP_RETURN output to `tx_outs` before calculating the transaction size. [3](#0-2)  The subsequent call to `calculate_weight_vbytes(tx_ins.len(), payments, None)` does not include either `tx_outs` or `data`, so the reconstructed transaction used for sizing omits the OP_RETURN output entirely. [4](#0-3) 

The same omission occurs when change is considered: `calculate_weight_vbytes()` receives `payments` and the change script, but still not the already-created OP_RETURN output. [5](#0-4)  Inside `calculate_weight_vbytes()`, the temporary transaction's outputs are derived only from `payments` and optional `change`, confirming that the data output is absent from the size calculation. [2](#0-1) 

The final `SignableTransaction` nevertheless contains `tx_outs`, including the omitted OP_RETURN output. [6](#0-5)  That complete transaction is then used to calculate the Taproot sighashes which the FROST participants sign. [7](#0-6) 

This is analogous to checksumming a partially populated structure: the code performs the security-relevant size and fee calculation over a version of the transaction missing attacker-controlled serialized bytes, then signs and publishes the larger canonical transaction.

### Impact Explanation
Up to 80 bytes of caller-controlled data can be embedded in the OP_RETURN output. [8](#0-7)  Including its output overhead and PUSHDATA encoding, that can add approximately 90 virtual bytes while contributing no fee allowance to the calculation.

As a result, `needed_fee()` reports a fee appropriate for a smaller transaction rather than the transaction actually signed. [9](#0-8)  The minimum-fee and maximum-standard-weight checks can likewise pass for the incomplete transaction while failing for the real transaction. [10](#0-9) 

An attacker able to influence transaction metadata can therefore cause the wallet to sign a transaction with a materially lower effective fee rate than requested, potentially making it ineligible for relay or delayed indefinitely. If change is enabled, the change amount is also calculated against the understated fee, although the total fee remains the incorrectly calculated amount rather than silently draining additional funds. [5](#0-4) 

### Likelihood Explanation
The condition is deterministic whenever the `data` argument is non-empty; no race, malformed encoding, or cryptographic assumption is required. [1](#0-0)  Exploitation requires an application flow where an untrusted party can cause an OP_RETURN payload to be included in a transaction signed by the wallet.

The impact is bounded to transaction relay/confirmation failure and incorrect fee-policy enforcement because the sighash commits to the complete transaction, not the incomplete sizing model. [7](#0-6)  This is therefore a Medium-severity availability and fee-integrity issue rather than direct theft or signature forgery.

### Recommendation
Calculate weight and virtual size from the actual `tx_outs` candidate that will be signed, including the OP_RETURN output, rather than reconstructing outputs solely from `payments` and `change`. The change calculation should also account for the OP_RETURN output by performing the estimate against the complete candidate output set or by iterating until the change amount and fee converge.

### Proof of Concept
1. Call `SignableTransaction::new()` with one funded input, `data` set to an 80-byte value, no payments, and no change.
2. The function appends an OP_RETURN `TxOut` to `tx_outs`. [3](#0-2) 
3. It calls `calculate_weight_vbytes(tx_ins.len(), payments, None)`, where `payments` is empty and `data` is not represented. [4](#0-3) 
4. Select `fee_per_vbyte = 1` and an input value equal to the resulting `needed_fee`.
5. The returned transaction contains the additional OP_RETURN output, so its actual virtual size is approximately 90 vbytes greater than the size used to calculate the fee. [6](#0-5) 
6. Its actual fee rate is therefore approximately `needed_fee / (estimated_vbytes + 90)`, below the requested 1 sat/vbyte and potentially below Bitcoin Core's default minimum relay rate even though the internal minimum-fee check passed.
