### Title
Unbounded `RefundDeposits`/`DeleteDeposits` iteration in gov `EndBlocker` allows deposit-spam block-delay DoS - (File: `sei-cosmos/x/gov/keeper/deposit.go`, `sei-cosmos/x/gov/abci.go`)

### Summary
The Cosmos SDK gov module's `EndBlocker` unconditionally calls `RefundDeposits` or `DeleteDeposits` for every proposal whose voting/deposit period ends, and those functions iterate every single deposit record for that proposal with no cap. Unlike vote tallying in the same `EndBlocker`, which is explicitly bounded by `MaxVotesProcessedPerBlock`, deposit iteration has no equivalent bound. An attacker can inflate the number of deposit records for a proposal cheaply (many small `MsgDeposit` txs from distinct addresses) and force an unbounded, unmetered iteration to run inside `EndBlocker` at the moment that proposal's period ends.

### Finding Description
`GetDeposits`/`IterateDeposits` walk every `Deposit` entry keyed by `(proposalID, depositor)` in the KV store: [1](#0-0) 

`RefundDeposits` and `DeleteDeposits` both drive this same unbounded iterator, doing a bank operation and a store delete per entry: [2](#0-1) [3](#0-2) 

`EndBlocker` calls `DeleteDeposits`/`RefundDeposits` for every proposal that becomes inactive or finishes voting, with no limit on the number of deposits processed per proposal (contrast this with the explicit `MaxVotesProcessedPerBlock` / `remainingRecords` budget used for vote tallying in the very same function): [4](#0-3) [5](#0-4) 

Each `AddDeposit` call only updates or inserts a deposit record keyed by depositor address, so a new store entry is created for every unique depositor that deposits on a proposal, and `SetDeposit`/`AddDeposit` are reachable by any unprivileged account submitting `MsgDeposit`: [6](#0-5) 

This mirrors the reported OpenQ pattern exactly: an attacker cheaply grows an array/store-set of deposit records that is later iterated in full by an unrelated, unbounded loop (`getLockedFunds`/`refundDeposit` in OpenQ vs. `RefundDeposits`/`DeleteDeposits` in sei-chain's gov module), and the victim operation (there, any refund caller; here, `EndBlocker` itself) pays the cost of the attacker-inflated collection.

### Impact Explanation
Because `EndBlocker` runs deterministically for every validator on every block and (unlike the tally path) has no per-block processed-item cap for deposits, a proposal with an artificially large number of distinct depositor records will cause every validator to spend proportionally large, unbounded time iterating and performing a bank transfer/store delete per depositor the instant that proposal's deposit or voting period elapses. This directly threatens block production time (potential block delay beyond 2.5 seconds) for all validators simultaneously, since the work is mandatory consensus-critical `EndBlocker` logic, not gas-metered per-transaction work that only the caller pays for.

### Likelihood Explanation
Any unprivileged account can submit `MsgDeposit` from many different addresses toward the same governance proposal, each depositing a minimal amount. There is no evidence of a per-message minimum deposit amount or a cap on the number of distinct depositors per proposal in the reviewed code, so the only cost to an attacker is the cumulative gas fees for many cheap `MsgDeposit` transactions (potentially from many funded addresses) — an inexpensive, permissionless setup step, after which the unbounded work is triggered automatically and for free at the deterministic time the proposal's period ends.

### Recommendation
- Bound the number of deposits processed by `RefundDeposits`/`DeleteDeposits` per `EndBlocker` invocation (mirroring `MaxVotesProcessedPerBlock`) and resume across blocks the same way tally processing does with `remainingRecords`.
- Alternatively/also enforce a minimum deposit amount per `MsgDeposit` and/or cap the number of distinct depositor records tracked per proposal, so the store-side collection an attacker can grow is bounded.
- Consider metering/charging the refund/delete work back to depositors (e.g., an escrow bond consumed on refund) so growing the set is not free.

### Proof of Concept
1. Submit a governance proposal (attacker or any account) requiring only a minimal deposit to enter the deposit period.
2. From a large number of distinct funded addresses, each submit a `MsgDeposit` of a very small amount to the same `proposalID`, creating one new `Deposit` store record per address via `AddDeposit`/`SetDeposit` (`sei-cosmos/x/gov/keeper/deposit.go:106-167`).
3. Let the proposal's deposit period or voting period elapse.
4. In the next block, `EndBlocker` (`sei-cosmos/x/gov/abci.go:38-93` or the legacy path at `173-259`) calls `DeleteDeposits`/`RefundDeposits`, which iterate all N depositor records unconditionally (`sei-cosmos/x/gov/keeper/deposit.go:53-68`, `169-192`) — with N scaled arbitrarily by step 2 — causing `EndBlocker` execution time for that block to grow linearly (unbounded) with the attacker-chosen N, unlike the capped vote-tally work in the same function.

// DeleteDeposits deletes all the deposits on a specific proposal without refunding them
func (keeper Keeper) DeleteDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		err := keeper.bankKeeper.BurnCoins(ctx, types.ModuleName, deposit.Amount)
		if err != nil {
			panic(err)
		}

		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}

// IterateDeposits iterates over the all the proposals deposits and performs a callback function
func (keeper Keeper) IterateDeposits(ctx sdk.Context, proposalID uint64, cb func(deposit types.Deposit) (stop bool)) {
	store := ctx.KVStore(keeper.storeKey)
	iterator := sdk.KVStorePrefixIterator(store, types.DepositsKey(proposalID))

	defer func() { _ = iterator.Close() }()

	for ; iterator.Valid(); iterator.Next() {
		var deposit types.Deposit

		keeper.cdc.MustUnmarshal(iterator.Value(), &deposit)

		if cb(deposit) {
			break
		}
	}
}

// AddDeposit adds or updates a deposit of a specific depositor on a specific proposal
// Activates voting period when appropriate
func (keeper Keeper) AddDeposit(ctx sdk.Context, proposalID uint64, depositorAddr sdk.AccAddress, depositAmount sdk.Coins) (bool, error) {
	// Checks to see if proposal exists
	proposal, ok := keeper.GetProposal(ctx, proposalID)
	if !ok {
		return false, sdkerrors.Wrapf(types.ErrUnknownProposal, "%d", proposalID)
	}

	// Check if proposal is still depositable
	if (proposal.Status != types.StatusDepositPeriod) && (proposal.Status != types.StatusVotingPeriod) {
		return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
	}
	if keeper.IncrementalTallyEnabled(ctx) && proposal.Status == types.StatusVotingPeriod {
		if proposal.VotingEndTime.Before(ctx.BlockTime()) || keeper.voteDelegationSnapshotFrozen(ctx, proposal) {
			return false, sdkerrors.Wrapf(types.ErrInactiveProposal, "%d", proposalID)
		}
	}

	// update the governance module's account coins pool
	err := keeper.bankKeeper.SendCoinsFromAccountToModule(ctx, depositorAddr, types.ModuleName, depositAmount)
	if err != nil {
		return false, err
	}

	// Update proposal
	proposal.TotalDeposit = proposal.TotalDeposit.Add(depositAmount...)
	keeper.SetProposal(ctx, proposal)

	// Check if deposit has provided sufficient total funds to transition the proposal into the voting period
	activatedVotingPeriod := false

	if proposal.Status == types.StatusDepositPeriod && proposal.TotalDeposit.IsAllGTE(keeper.GetDepositParams(ctx).GetMinimumDeposit(proposal.IsExpedited)) {
		keeper.ActivateVotingPeriod(ctx, proposal)

		activatedVotingPeriod = true
	}

	// Add or update deposit object
	deposit, found := keeper.GetDeposit(ctx, proposalID, depositorAddr)

	if found {
		deposit.Amount = deposit.Amount.Add(depositAmount...)
	} else {
		deposit = types.NewDeposit(proposalID, depositorAddr, depositAmount)
	}

	// called when deposit has been added to a proposal, however the proposal may not be active
	keeper.AfterProposalDeposit(ctx, proposalID, depositorAddr)

	ctx.EventManager().EmitEvent(
		sdk.NewEvent(
			types.EventTypeProposalDeposit,
			sdk.NewAttribute(sdk.AttributeKeyAmount, depositAmount.String()),
			sdk.NewAttribute(types.AttributeKeyProposalID, fmt.Sprintf("%d", proposalID)),
		),
	)

	keeper.SetDeposit(ctx, deposit)

	return activatedVotingPeriod, nil
}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
