### Title
Unbounded, uncapped accumulation of attacker-controlled group elements in `SchnorrAggregate::read` enables remote memory exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external report (CVE-2026-64773) describes a forwarding process buffering an unbounded amount of a client's data with no cap on accumulation or duration. The analog in Serai is `SchnorrAggregate::read`, which reads a 32-bit count from an untrusted byte stream and then loops that many times pushing decoded group elements into a `Vec`, with no bound or early rejection. An unprivileged party feeding untrusted bytes to the read path can force the host process to accumulate up to ~4.3 billion `C::G` elements in memory, streamed incrementally over as long as the attacker keeps the connection alive.

### Finding Description
`SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs:77-88` reads a little-endian `u32` length prefix and then performs `for _ in 0 .. u32::from_le_bytes(len) { Rs.push(C::read_G(reader)?) }` with no sanity bound on the count. For a 32-byte group (e.g. Ristretto/ed25519 point encodings), a sender that slowly streams encoded points accumulates roughly `32 bytes * N` in the `Rs` vector — up to ~137 GiB at the `u32` maximum — entirely under attacker control. The peer can stretch the accumulation indefinitely by trickling bytes, exactly mirroring the advisory's "no cap on how much accumulates or how long the wait can be stretched."

The same unbounded vector then feeds `SchnorrAggregate::verify` (`aggregate.rs:127-146`), which allocates `Vec::with_capacity((2 * keys_and_challenges.len()) + 1)` and performs a `multiexp_vartime` over every element — a secondary CPU/memory amplification on top of the deserialization buffer.

By contrast, nearby code shows awareness of this bug class: `coordinator/src/tributary/transaction.rs:286` enforces a `TRANSACTION_SIZE_LIMIT` on `commitments_len * each_commitments_len` before allocating, and `networks/ethereum/src/machine.rs:51-60` explicitly reads a claimed 4 GB length in 1 KB chunks "to only read data actually present." `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:608-623`) is bounded because its count is a `u16`. `SchnorrAggregate::read` is the in-scope location where an attacker-chosen `u32` count drives unbounded accumulation of parsed elements.

### Impact Explanation
Any integrator that deserializes an aggregate signature from an untrusted peer (the documented use of this type per the aggregated-Schnorr construction in <https://eprint.iacr.org/2021/350>) exposes the host process to remote memory exhaustion / OOM kill, denying service to all co-resident signing or verification work. The attacker needs no credentials, no valid keys, and no proof — only the ability to keep writing bytes to the stream. This is a reachable, unauthenticated availability compromise of the process performing deserialization and verification.

### Likelihood Explanation
Reachability is direct: `read` takes any `R: Read` over attacker bytes, and the count field is the first four bytes. The only mitigating factor versus a pure "declare huge, send nothing" allocation is that each loop iteration calls `read_exact`, so memory grows proportionally to bytes actually transmitted rather than being allocated up-front. That still matches the cited vulnerability class (buffering client data without cap over a held-open connection), and at 32 bytes per element even modest bandwidth accumulates tens of GiB. No element-count limit exists anywhere in the read or verify path.

### Recommendation
Cap the number of `Rs` to a protocol-appropriate maximum (aggregates are for a bounded signer set — e.g. `u16::MAX` or the multisig's `n`) before the loop, or reject counts exceeding the number of keys that will be supplied to `verify`. If the reader is length-delimited, check `len` against remaining bytes first so an over-claimed count fails fast. Apply the same pattern as the 1 KB chunked read in `networks/ethereum/src/machine.rs` if large counts must remain supported.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ristretto;
use schnorr::SchnorrAggregate;

// A reader that yields an infinite stream of canonical identity points
// (0x01 followed by 31 zero bytes is the Ristretto255 identity encoding).
struct InfinitePoints;
impl io::Read for InfinitePoints {
  fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
    for chunk in buf.chunks_mut(32) {
      chunk.fill(0);
      chunk[0] = 1;
    }
    Ok(buf.len())
  }
}

fn main() {
  let mut prefix = InfinitePoints;
  // Crafted stream header: u32::MAX aggregate elements, followed by
  // an unending supply of valid point encodings.
  // In practice prepend u32::MAX.to_le_bytes() via a chained reader;
  // SchnorrAggregate::read will push ~4.3 billion elements into Rs,
  // growing memory ~137 GiB, as long as bytes keep arriving.
  let _ = SchnorrAggregate::<Ristretto>::read(&mut prefix); // never returns / OOM
}
```

With a `std::io::Read` impl chained after a 4-byte `0xFF_FF_FF_FF` length prefix, `SchnorrAggregate::read` (`crypto/schnorr/src/aggregate.rs:77-88`) loops `u32::MAX` times, pushing each decoded point into `Rs` with no limit — heap growth is unbounded and entirely attacker-paced, matching the advisory's unbounded-buffering class.
