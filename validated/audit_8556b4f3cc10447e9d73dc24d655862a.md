## Analog Found

### Title
Incomplete Message-Condition Denylist in PlotNFT Owner Restriction — `SendMessageBanned` Blocks Only `SEND_MESSAGE`, Not Its Paired `RECEIVE_MESSAGE` Opcode - (File: `chia/wallet/puzzles/custody/send_message_banned.clsp`)

### Summary
The picklescan advisory shows a class of bug where a security check enumerates specific "dangerous" primitives instead of the full semantic category they belong to, letting an equally dangerous sibling primitive slip through undetected. The chia-blockchain analog is `send_message_banned.clsp`, the restriction wrapper used to lock down the PlotNFT owner's spend path while pooling. It walks the delegated puzzle's output conditions and rejects only the `SEND_MESSAGE` opcode, leaving its consensus-paired counterpart `RECEIVE_MESSAGE` completely unchecked, even though the two opcodes form a single semantic message-passing channel that this restriction is documented to eliminate.

### Finding Description
`chia/wallet/puzzles/custody/send_message_banned.clsp` implements the denylist: [1](#0-0) 

`check_conditions` only compares each condition's opcode against `SEND_MESSAGE` (opcode 66); every other opcode, including `RECEIVE_MESSAGE` (opcode 67), passes through unexamined. `SEND_MESSAGE`/`RECEIVE_MESSAGE` are enforced by the consensus layer as a strictly coupled pair — one cannot be included in a valid block without a matching counterpart elsewhere in the same transaction bundle: [2](#0-1) 

This `SendMessageBanned` restriction is applied to the PlotNFT/pool-singleton owner spend path specifically while the plot is pooling, alongside `FixedCreateCoinDestinations`, in order to fully close off any message-based side channel for the restricted user: [3](#0-2) 

The pool-reward-claiming mechanism itself relies on the `SEND_MESSAGE`/`RECEIVE_MESSAGE` pairing with a specific mode and a deterministically derived coin ID for the p2_singleton reward coin: [4](#0-3) 

Because the restriction's denylist only names one half of the opcode pair, the owner's normally-restricted spend path can still legally embed a `RECEIVE_MESSAGE` condition (committing to any coin id, parent id, puzzle hash, or amount it chooses) and satisfy it by pairing it with a `SEND_MESSAGE` from an attacker-controlled coin elsewhere in the same spend bundle — something the puzzle's own comment ("enforces the lack of SEND_MESSAGE conditions in the condition set") indicates was never meant to be possible for this restricted path.

### Impact Explanation
This mirrors the picklescan flaw exactly: a security-relevant check is implemented as an enumerated denylist of specific opcode bytes rather than a semantic allowlist/category check, so a sibling primitive with equivalent side-channel capability (`RECEIVE_MESSAGE`) is left reachable. Any wallet user constructing a spend bundle for a pooling PlotNFT singleton (an unprivileged, single-spend-bundle-reachable action) can attach arbitrary `RECEIVE_MESSAGE` commitments the restriction was supposed to forbid entirely, undermining the intended invariant that a pooling PlotNFT's user-controlled spend path cannot participate in any message-based coordination outside the fixed `CREATE_COIN` destination it is locked to. This weakens the security boundary the pool-participant validator relies on and could be leveraged to forge coupling with the reward-claim message protocol or other message-gated logic depending on the specific coin graph an attacker constructs.

### Likelihood Explanation
Likelihood is high for reachability (any wallet user who controls a pooling PlotNFT singleton and can craft a spend bundle can trigger this at will — no privileged network position needed), though the concrete monetary impact depends on what other logic in the system relies on the completeness of the "no messaging" invariant for this restricted path. The check itself is trivially bypassable by construction, which is the core of the CWE-184 "incomplete list of disallowed inputs" class.

### Recommendation
Change `send_message_banned.clsp`'s `check_conditions` to reject on `RECEIVE_MESSAGE` in addition to `SEND_MESSAGE` (or better, treat `SEND_MESSAGE`/`RECEIVE_MESSAGE` as a single banned category), consistent with how the picklescan fix moved from enumerating specific dangerous functions to blocking the entire semantic category (module-level wildcard) that contains them.

### Proof of Concept
1. Create a `PuzzleWithRestrictions` wrapping a pooling PlotNFT owner puzzle with `ValidatorStackRestriction(required_wrappers=[SendMessageBanned()])`, mirroring `chia/_tests/clvm/test_restrictions.py::test_send_message_banned`.
2. Instead of a `SendMessage` condition (which the existing test at [5](#0-4)  shows is correctly rejected with `GENERATOR_RUNTIME_ERROR`), embed a `RECEiveMessage` condition in the delegated puzzle's output instead, paired with a `SendMessage` condition from a second, attacker-controlled coin spent in the same `WalletSpendBundle`.
3. Push the bundle: the `SendMessageBanned` wrapper's CLVM check only scans for opcode 66 (`SEND_MESSAGE`) inside the *restricted* coin's own condition list, sees only opcode 67 (`RECEIVE_MESSAGE`), and does not raise `(x)`; the bundle is accepted by the mempool as long as the paired `SEND_MESSAGE`/`RECEIVE_MESSAGE` consensus check (`MESSAGE_NOT_SENT_OR_RECEIVED`) is otherwise satisfied by the second coin — demonstrating the restriction fails to fully close the messaging side channel it claims to eliminate.
