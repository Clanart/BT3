## Title
Deterministic `object_code_deployment::publish` seed collides across orderless (nonce-based) transactions, enabling code-object address griefing / DoS - (File: `aptos-move/framework/aptos-framework/sources/object_code_deployment.move`)

### Summary
`object_code_deployment::publish` derives the address of the newly created code object from `object_seed(publisher_address)`, which is built from `account::get_sequence_number(publisher) + 1` [1](#0-0) . This "+1" trick assumes the account's sequence number is incremented exactly once per transaction in the epilogue, immediately after the entry function body runs, so every subsequent `publish` call observes a different, already-consumed sequence number and thus produces a fresh, non-colliding object address [2](#0-1) .

However, Aptos now supports orderless transactions that use a `Nonce`-based replay protector instead of a sequence number [3](#0-2) . For orderless transactions, `unified_epilogue_v2` explicitly skips `account::increment_sequence_number` when `is_orderless_txn` is true [4](#0-3) . This means the sequence number of an account that only ever submits orderless transactions never advances (remains at its baseline value, e.g. 0).

### Finding Description
`object_seed` is the sole source of uniqueness for the named object address created in `publish`:
```
inline fun object_seed(publisher: address): vector<u8> {
    let sequence_number = account::get_sequence_number(publisher) + 1;
    ...
}
``` [1](#0-0) 

This is invoked from `publish`, which calls `object::create_named_object(publisher, object_seed)` to create the destination object before publishing the package [5](#0-4) .

Because orderless transactions never call `increment_sequence_number` [4](#0-3) , an account that exclusively submits orderless transactions will have the *same* `get_sequence_number` value on every call to `publish` — meaning `object_seed` returns an identical byte string on every attempt. `create_named_object` derives the object address deterministically from `(publisher, seed)`, so a second `publish` call (e.g., to deploy a second, distinct package/object) by such an account will attempt to create an object at the exact same address as the first deployment.

This is the direct code-safety analog of the reported "escrow reuse" bug: a value that is only correct for a single execution (`sequence_number + 1` as a proxy for "this transaction's monotonically-incrementing identity") is silently reused across multiple executions once the underlying assumption (sequence-number replay protection) no longer holds for a class of transactions (orderless/nonce-based) that the codebase explicitly supports elsewhere.

A second, related consequence: since the *first* orderless `publish` call from any given account is fully predictable ahead of time (sequence number 0 for a fresh account, or whatever fixed value it is pinned at), an attacker can pre-compute the resulting object address for a victim's future orderless `publish` transaction and pre-create an object at that same address (via `object::create_named_object` from a script that knows the seed algorithm and the victim's current, frozen sequence number), causing the victim's legitimate publish transaction to abort when it later tries to create the same named object — a griefing/DoS vector against code deployment specific to orderless transactions.

### Impact Explanation
This falls under "Native validation or write-set-publish failure that reaches protected state mutation" and "permissionless publish/upgrade flows must still preserve code ownership" pivots: an unprivileged third party can prevent (DoS) or otherwise interfere with another account's `object_code_deployment::publish` transactions purely by knowing the victim's frozen sequence number and preemptively occupying the derived object address, and legitimate publishers relying on orderless transactions can permanently be unable to deploy a second package via `object_code_deployment::publish` (every subsequent attempt aborts on `create_named_object`, since the same address is repeatedly targeted). This is a functional/availability break in the on-chain publish path rather than a fund-loss bug, but it directly corrupts the "object address" value that the publish flow's core safety invariant (unique-per-deployment code object) depends on.

### Likelihood Explanation
Likelihood depends on adoption of orderless transactions for accounts that also use `object_code_deployment::publish`. Given orderless transactions are a first-class, actively-developed replay-protection mechanism in this codebase (dedicated `Nonce` variant, dedicated skip-logic in the epilogue, `nonce_validation` module, and a 100-second max-expiration constant specifically named for orderless txns), this is not a hypothetical edge case but a maintained execution path. Any wallet/dApp that defaults new accounts to orderless transactions and later calls `deploy-object`/`upgrade-object` more than once would hit this deterministically, and the DoS pre-computation requires no special access — only knowledge of the target account's (frozen) sequence number, which is public on-chain state.

### Recommendation
`object_seed` should not rely on `account::get_sequence_number` as a substitute for a monotonic "attempt counter," since that assumption is now broken for orderless transactions. Instead, derive the seed from a value guaranteed to be unique per `publish` call regardless of replay-protection mechanism — for example, an explicit per-account, per-object monotonically increasing counter stored in a dedicated resource (similar to how `resource_account`/`account::create_resource_account` derive addresses from an explicit caller-supplied `seed` rather than sequence number), or require the caller to pass an explicit seed and enforce its uniqueness on-chain (e.g., reject if `exists<Object>(derived_address)`), so that the derivation no longer depends on unstated invariants about how/when sequence numbers are incremented.

### Proof of Concept
1. Create a fresh account `A` and configure it to submit only orderless (nonce-based) transactions (`ReplayProtector::Nonce`), so `account::get_sequence_number(A)` remains fixed at `0` because `unified_epilogue_v2` skips `increment_sequence_number` for `is_orderless_txn = true` [4](#0-3) .
2. Submit an orderless transaction from `A` calling `object_code_deployment::publish(A, metadata_1, code_1)`. This creates object `O = create_named_object(A, object_seed(A))` where `object_seed(A) = hash(DOMAIN_SEPARATOR || bcs(0+1))` [6](#0-5) .
3. Submit a second, independent orderless transaction from `A` calling `object_code_deployment::publish(A, metadata_2, code_2)` intending to deploy a second, unrelated package. Because `get_sequence_number(A)` is still `0`, `object_seed(A)` is identical to step 2, so `create_named_object` attempts to create an object at the same address `O`, which already exists and aborts the transaction — `A` can never deploy a second package via `publish` while remaining purely orderless.
4. Alternatively, an attacker who observes that `A` has sequence number `0` (public state) can, before `A`'s first `publish` transaction lands, submit their own transaction computing the same `object_seed(A)` and creating a named object at address `O` under a different signer/flow, blocking `A`'s legitimate first deployment from ever succeeding.

(Note: full exploitation depends on exact `create_named_object`/`ExistingObject` abort semantics and the precise conditions under which orderless transactions are accepted for a given account, which were not fully traced in the available index — a Devin session with full repo/build access is recommended to confirm the exact abort code and end-to-end reproduction via the transactional or e2e-move-tests harness.)

    public entry fun publish(
        publisher: &signer,
        metadata_serialized: vector<u8>,
        code: vector<vector<u8>>,
    ) {
        let publisher_address = signer::address_of(publisher);
        let object_seed = object_seed(publisher_address);
        let constructor_ref = &object::create_named_object(publisher, object_seed);
        let code_signer = &constructor_ref.generate_signer();
        code::publish_package_txn(code_signer, metadata_serialized, code);

        event::emit(Publish { object_address: signer::address_of(code_signer), });

        move_to(code_signer, ManagingRefs {
            extend_ref: constructor_ref.generate_extend_ref(),
        });
    }

    inline fun object_seed(publisher: address): vector<u8> {
        let sequence_number = account::get_sequence_number(publisher) + 1;
        let seeds = vector[];
        seeds.append(bcs::to_bytes(&OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR));
        seeds.append(bcs::to_bytes(&sequence_number));
        seeds
    }
