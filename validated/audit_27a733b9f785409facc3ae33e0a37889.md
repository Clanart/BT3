### Title
Single failing reward token transfer in `getReward()` permanently blocks withdrawal and reward claims for a user - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPool.getReward()` / `BaseRewardPoolV2.getReward()` iterate over the *entire* `rewardTokens` array and unconditionally attempt a `safeTransfer` (or `_sendReward`) for every token that has a non-zero pending balance for the account, with no isolation between tokens. This mirrors the reported bug class: a single "bad" element embedded in a batch operation causes the whole operation to revert, blocking a legitimate action for everyone who must go through that same code path. [1](#0-0) [2](#0-1) 

### Finding Description
`getReward()` is called by `MasterMagpie._claimBaseRewarder()`, which is invoked from `_multiClaim()` (used by `multiclaim`, `multiclaimSpec`, `multiclaimFor`, `multiclaimOnBehalf`) and from `_harvestAndUnstake()` (used by the normal `withdraw`/`withdrawFor` path), since a harvest is always performed before principal is released. [3](#0-2) [4](#0-3) 

The reward token list (`rewardTokens`) is a persistent, shared array populated over the pool's lifetime via `queueNewRewards`, and any of the registered reward tokens is looped over unconditionally when a user calls `getReward`: [5](#0-4) 

If the ERC20 `safeTransfer` call for **any single** registered reward token reverts for a given account — e.g. the token has a blacklist/pausable feature and the receiving address (the user or `_receiver`) is blacklisted/paused, or the token behaves unexpectedly (fee-on-transfer causing balance-accounting mismatches, or reentrancy guards) — the entire `getReward()` call reverts. Because there is no per-token try/catch or skip-on-failure logic, this one failing transfer:
1. Blocks the user from claiming *all other, otherwise-valid* reward tokens in that pool.
2. Blocks `_harvestAndUnstake()`, which is unconditionally invoked before principal withdrawal in `withdraw`/`withdrawFor`, permanently trapping the user's staked principal in the contract as long as the offending token/condition persists.

This is directly analogous to the reported issue: the state-transition function reverted the *entire* block processing because one deposit had an invalid signature, instead of skipping just that one bad item. Here, one bad reward-token transfer reverts the *entire* claim/withdraw transaction instead of skipping just that token.

### Impact Explanation
Any user affected by a reverting reward-token transfer (e.g., blacklisted by a reward token's issuer, or a reward token that becomes non-transferable) loses the ability to:
- Claim any of their earned rewards across all reward tokens in the pool, and
- Withdraw their staked principal at all, since harvesting is mandatory before withdrawal.

This constitutes a permanent freeze of user principal and unclaimed yield for the affected account, satisfying the "permanent freezing of funds" / "theft or permanent freezing of unclaimed yield" impact bar, since there is no emergency path that bypasses harvesting for non-vlMGP scenarios other than `emergencyWithdraw`, which is gated `whenPaused` (an admin-only, non-guaranteed condition). [6](#0-5) 

### Likelihood Explanation
Likelihood is moderate: it requires a reward token in the pool to have a transfer-blocking condition for a specific account (e.g., blacklisting by a centralized stablecoin issuer, a paused token, or a bugged/incompatible token). Given that reward tokens registered via `queueNewRewards` are not restricted to a vetted allow-list of "safe" ERC20 semantics at the reward-pool level, and multiple pools accumulate many different bribe/partner reward tokens over time (see `WombatBribeManager`/`BaseRewardPool` integration), the probability of at least one reward token eventually exhibiting this behavior for at least one user is non-trivial over the life of the protocol.

### Recommendation
Wrap each reward token's transfer in `getReward()`/`getRewards()` (and the equivalent `_sendReward` in `BaseRewardPoolV2.sol`, `vlMGPBaseRewarder.sol`, `mWOMSVBaseRewarder.sol`) in a try/catch (or use low-level `call` with success checks) so a failure on one token does not revert the harvest for other tokens or block withdrawal of principal. Any reward amount whose transfer fails should remain accounted for the user (not zeroed out) so it can be retried or claimed later, analogous to skipping an invalid deposit instead of halting the whole state transition.

### Proof of Concept
1. Manager calls `queueNewRewards()` to register a reward token `T` (e.g., a stablecoin with an issuer-controlled blacklist) for a pool's `BaseRewardPool`. [7](#0-6) 
2. User `A` stakes into the pool and accrues rewards in both `T` and another normal reward token `X`.
3. Token `T`'s issuer blacklists user `A`'s address (or `A`'s receiver address) for any reason, or `T` becomes paused.
4. User `A` calls `withdraw()` on `MasterMagpie`, which internally calls `_harvestAndUnstake` → `_harvestBaseRewarder` → `rewarder.getReward(A, A)`. [8](#0-7) 
5. Inside `getReward()`, the loop reaches token `T`, `IERC20(T).safeTransfer(A, reward)` reverts due to the blacklist, and the entire transaction (including the withdrawal of principal and the claim of token `X`) reverts. [9](#0-8) 
6. User `A` can never withdraw principal or claim any reward token from this pool through the normal path again, as every call to `getReward()` (directly or via harvest-before-withdraw) will always revert on token `T`.

        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
