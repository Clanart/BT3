### Title
Untrusted `ReceivedOutput` bytes can declare arbitrary UTXOs spendable by the wallet - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

`ReceivedOutput::read` deserializes the scalar offset, `TxOut`, and `OutPoint` without authenticating that the output was produced by `Scanner` or that the encoded outpoint exists. An attacker who can supply serialized `ReceivedOutput` bytes can therefore claim ownership of a nonexistent or third-party UTXO by pairing the wallet’s public P2TR script with an arbitrary value and outpoint. The wallet reports the forged object as spendable and can construct a threshold-signing session for a transaction that the Bitcoin network will reject. [1](#0-0) 

### Finding Description

`ReceivedOutput` contains three authorization-sensitive fields: the scalar `offset` used to derive the spending key, the claimed `TxOut`, and the claimed `OutPoint`. [2](#0-1)  The ordinary construction path safely derives these values by scanning a transaction and matching `output.script_pubkey` against scripts registered in `Scanner::scripts`. [3](#0-2) 

The deserialization path does not perform the equivalent check. `ReceivedOutput::read` accepts any scalar encoding returned by `Secp256k1::read_F`, any consensus-valid `TxOut`, and any consensus-valid `OutPoint`, then returns all three as a wallet-owned output. [1](#0-0)  There is no embedded scanner context, registered-script proof, blockchain lookup, or authentication tag establishing that the serialized object was previously observed on-chain.

The forged value then propagates into transaction construction. `SignableTransaction::new` sums the attacker-controlled `TxOut` values as available inputs and uses the attacker-controlled outpoints as transaction inputs. [4](#0-3)  When signing is requested, `SignableTransaction::multisig` checks only that `keys.offset(offset).group_key()` produces the encoded `prevouts[i].script_pubkey`; it does not verify that the outpoint references a real output carrying that script and value. [5](#0-4) 

For the base wallet offset `Scalar::ZERO`, an attacker can encode the wallet’s already-public `p2tr_script_buf(key)` script, so this consistency check succeeds even though the encoded outpoint is fabricated. [6](#0-5) 

### Impact Explanation

This allows funds to be reported as received when they are not spendable. A forged `ReceivedOutput` can expose an arbitrary nominal balance through `value()`, be counted as transaction input value, and drive construction and threshold signing of a transaction spending a nonexistent or unrelated outpoint. [7](#0-6) [4](#0-3) 

The resulting Bitcoin transaction cannot spend a nonexistent UTXO, and cannot spend a third-party UTXO unless its script is actually controlled by the wallet key/offset. However, the signer-facing invariant “this object is a spendable wallet output discovered by the scanner” is broken. This can corrupt wallet accounting, create unpublishable threshold-signed transactions, consume signing rounds, and block or misprice payment construction.

### Likelihood Explanation

Exploitation requires an attacker to control bytes passed to `ReceivedOutput::read`, which is an explicit untrusted-input boundary. The attacker only needs the wallet’s public P2TR address/script and can use `offset = 0`; no private key, validator compromise, malformed curve point, or peer collusion is required. Crafting the object is deterministic because the format is simply the scalar followed by consensus-encoded `TxOut` and `OutPoint`. [8](#0-7) 

The impact is bounded because Bitcoin consensus prevents the forged input from actually being spent. The finding is therefore Medium rather than High: it creates false spendable-funds state and wasted/failed signing operations, but does not directly reveal key shares or authorize theft.

### Recommendation

Do not make `ReceivedOutput::read` a trust-establishing constructor. Either:

1. Authenticate serialized outputs with a keyed MAC over the wallet identity, offset, `TxOut`, and `OutPoint`, and reject unauthenticated inputs.
2. Revalidate every deserialized output against `Scanner` and confirmed blockchain state before treating it as spendable.
3. Change the API to require the owning `Scanner`/base key and verify:
   - `p2tr_script_buf(base_key + G * offset) == output.script_pubkey`, and
   - the encoded `OutPoint` resolves to a confirmed output equal to `output`.
4. Keep raw decoded data in an unauthenticated type until those checks pass, so `ReceivedOutput` remains an invariant-bearing “spendable output” type.

The scanner should remain the sole unauthenticated path that mints `ReceivedOutput` values, since it currently binds the script match and actual transaction outpoint together. [3](#0-2) 

### Proof of Concept

Conceptual Rust PoC:

```rust
use bitcoin::{
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
  consensus::encode::serialize_hex,
  hashes::Hash,
};
use k256::Scalar;

// Wallet's known base key.
let script: ScriptBuf = p2tr_script_buf(wallet_key).unwrap();

// Claim a large output exists at an arbitrary outpoint.
let forged_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: script,
};
let forged_outpoint = OutPoint {
  txid: Txid::from_byte_array([0x41; 32]),
  vout: 0,
};

let mut encoded = Vec::new();
encoded.extend(Scalar::ZERO.to_bytes());
encoded.extend(bitcoin::consensus::serialize(&forged_txout));
encoded.extend(bitcoin::consensus::serialize(&forged_outpoint));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(forged.value(), 1_000_000);
assert_eq!(forged.offset(), Scalar::ZERO);
assert_eq!(forged.outpoint(), &forged_outpoint);

// This succeeds because the script was honestly derived from the wallet key
// at offset zero, despite the outpoint being fabricated.
let signable = SignableTransaction::new(
  vec![forged],
  &[(payment_script, 100_000)],
  None,
  None,
  1,
).unwrap();

// The offset/script consistency check succeeds; signing proceeds for a
// transaction whose input does not exist on chain.
let machine = signable.multisig(&threshold_keys).unwrap();
```

The crucial issue is that `read` returns a fully privileged `ReceivedOutput` before ownership or on-chain existence is established, while later signing validates only the relationship between the encoded offset and encoded script—not the validity of the encoded outpoint. [1](#0-0) [5](#0-4)

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

    w.write_all(&self.offset.to_bytes())?;
    w.write_all(&serialize(&self.output))?;
    w.write_all(&serialize(&self.outpoint))
  }
