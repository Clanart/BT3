### Title
Missing lower-bound validation on `kip71.gastarget` governance parameter allows division-by-zero panic in base fee calculation - ([File: params/kip71_config.go])

### Summary
The `kip71.gastarget` governance parameter, like DODO GSP's `_K_`, is documented as a value that must be meaningfully positive to be used as a divisor, but its `FormatChecker` never enforces this. A governance proposal (via `governance.govparamcontract` / contract governance per KIP-81, or a header-governance vote) can set `GasTarget = 0`, which is then propagated by `kaiax/gov` into every node's `NextMagmaBlockBaseFee` computation, causing a division-by-zero panic in a function executed by all nodes as part of consensus-critical block header verification.

### Finding Description
The governance parameter table for `Kip71GasTarget` uses `noopFormatChecker`, which unconditionally returns `true` and performs no bound checking at all: [1](#0-0) 

Compare this to the two related KIP-71 fields, `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee`, which at least get a cross-field consistency check in `checkConsistency` (lower ≤ upper) before being accepted into a header vote: [2](#0-1) 

`GasTarget` has no such consistency check — it falls into the "no more checks here" bucket: [3](#0-2) 

Once `GasTarget = 0` becomes part of the effective `ParamSet`, it flows straight into `KIP71Config.GasTarget` and is used unguarded as a divisor in `NextMagmaBlockBaseFee`, unlike `BaseFeeDenominator`, which does have an explicit zero-guard: [4](#0-3) [5](#0-4) 

If `parentGasUsed != gasTarget` (which is guaranteed whenever `gasTarget == 0` and any gas was used), execution proceeds to compute `x.Div(x, new(big.Int).SetUint64(gasTarget))` — a division by zero, which panics in Go's `math/big`. This function is called from `VerifyMagmaHeader`, i.e. block header validation performed by every node when processing any block after the parameter takes effect: [6](#0-5) 

This exactly mirrors the reported bug class: a numeric governance/config parameter that is documented/expected to be strictly positive (as a divisor) has no lower-bound enforcement at the point it is accepted, unlike its sibling parameters which do have bound checks.

### Impact Explanation
Once a `GasTarget = 0` value is accepted into the governance parameter set (either via contract governance `GovParam.setParam`/`setParamIn`, which is reachable by the GovParam contract owner/GC members per KIP-81, or via a header-governance vote from the governing node), every node — proposers and validators alike — will panic while computing/validating the next block's base fee. This is a consensus-critical shared code path, so all honest nodes are affected uniformly at the block boundary where the parameter activates, halting block production/validation network-wide until the bad parameter is manually rolled back and nodes restarted with a patched or reconfigured client.

### Likelihood Explanation
This requires the actor able to submit governance votes/contract governance parameter changes (the governing node or GC members via `GovParam`) to submit `kip71.gastarget = 0`. There is no application-level format check preventing this value from being accepted, exactly like the reported `_K_` issue where the setter (`require(k <= 10**18)`) failed to also require `k > 0`. Given governance parameter changes are a documented, expected part of network operation and go through no validation for this specific field, an accidental (or malicious) misconfiguration is plausible and has no on-chain safeguard.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (and ideally validates it's a sane fraction of `MaxBlockGasUsedForBaseFee`), mirroring the explicit `> 0` requirement recommended in the original report. Additionally, add a defensive zero-guard in `NextMagmaBlockBaseFee` for `gasTarget`, matching the existing guard already present for `baseFeeDenominator`.

### Proof of Concept
1. Governing node (single mode) or GC via `GovParam.setParamIn` proposes `kip71.gastarget = 0`.
2. `NewVoteData`/`checkConsistency` accept the value (no format or consistency check exists for `Kip71GasTarget`).
3. Once activated at the target block, `kaiax/gov.GetParamSet` returns `GasTarget = 0` and this is copied into `KIP71Config.GasTarget` via `getChainConfig`: [7](#0-6) 
4. On the next block with `parentGasUsed > 0`, every node calls `NextMagmaBlockBaseFee`, which executes `x.Div(x, new(big.Int).SetUint64(0))`, panicking and crashing block processing network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
