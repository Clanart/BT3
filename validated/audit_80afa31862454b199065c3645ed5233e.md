### Title
`WombatStaking.vote`/`WombatBribeManager.castVotes` can be permanently DoS'd by a zero-amount reward transfer to an externally-controlled bribe token - (File: wombat/WombatStaking.sol, wombat/WombatBribeManager.sol, rewards/BaseRewardPool.sol)

### Summary
`WombatStaking.vote()` forwards Wombat bribe rewards to `BaseRewardPool.queueNewRewards`, which transfers the amount with `safeTransferFrom` without ever checking that the amount is non-zero. Because bribe reward tokens are enumerated directly from Wombat's external `IWombatBribe.rewardTokens()` and fee deductions can drive the net forwarded amount to zero, a token that reverts on zero-value transfers can permanently brick vote casting / bribe harvesting for the whole pool, callable by any unprivileged wallet.

### Finding Description
`WombatBribeManager.castVotes` (and the fully public wrapper `harvestSinglePool`, callable by anyone) invokes `wombatStaking.vote(...)`: [1](#0-0) 

Inside `WombatStaking.vote`, the list of reward tokens for each pool comes straight from Wombat's own bribe contract — not from any Magpie-controlled allowlist: [2](#0-1) 

For each nonzero `rewardAmount`, the code subtracts `protocolFee` and `callerFeeAmount` and then unconditionally calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, address(rewardTokens[i][j]))` with no check that the post-fee `rewardAmount` is still greater than zero (`rewardAmount -= protocolFee; rewardAmount -= callerFeeAmount;` can round down to exactly `0` for small bribes while `bribeProtocolFee + bribeCallerFee` fees are set close to `DENOMINATOR`, or simply due to integer division rounding on small bribe amounts).

`queueNewRewards` auto-registers any never-seen token into the pool's reward-token list and then calls `_provisionReward`, which performs an unconditional `safeTransferFrom` with no zero-amount guard: [3](#0-2) 

Since the reward-token address is supplied by an external, permissionless Wombat bribe contract (any briber can create a bribe with an arbitrary ERC20, including "revert-on-zero-transfer" tokens per the weird-ERC20 list referenced in the original report), and the resulting transfer amount can be driven to zero by protocol/caller fee rounding, calling `queueNewRewards(0, weirdToken)` reverts. Because this call sits inside the single, un-catch-wrapped loop in `WombatStaking.vote`, the revert propagates and aborts the entire `castVotes`/`voteAndCast`/`harvestSinglePool` transaction for **all** pools being processed in that call, not just the offending one.

### Impact Explanation
`castVotes`/`voteAndCast`/`harvestSinglePool` are the only entry points that (a) cast votes to Wombat (affecting governance-voting-driven emission allocation) and (b) harvest/forward all bribe rewards to each pool's `BribeRewardPool`. If any pool's bribe list contains a zero-transfer-reverting token with a rounded-to-zero net amount, every call to these functions reverts, meaning:
- Bribe rewards for every voted pool become permanently unharvestable/frozen (funds stuck in the external bribe contract, inaccessible to Magpie's reward pools and thus to users), and
- Vote casting to the underlying Wombat voter is blocked, preventing correction of the voting allocation.

This satisfies both "theft or permanent freezing of unclaimed yield" and a 24-hour-plus (indefinite, until governance intervenes to remove/replace the pool or bribe) freeze of funds/functionality.

### Likelihood Explanation
Reachable entirely from an ordinary wallet transaction (`harvestSinglePool`/`castVotes` are `public`/`external` with no privileged modifier). The trigger condition (a bribe creator on Wombat listing a token that reverts on zero transfers, combined with fee rounding/very small bribe amounts driving the post-fee amount to zero) is a "low probability, externally influenced" event exactly as characterized in the referenced report, but is fully outside Magpie's control since the bribe token list is sourced from Wombat's `IWombatBribe.rewardTokens()`.

### Recommendation
Guard the transfer path against zero amounts at both layers:
1. In `WombatStaking.vote`, skip the `queueNewRewards` call when the post-fee `rewardAmount` is `0`.
2. In `BaseRewardPool._provisionReward` (and the analogous functions in `BaseRewardPoolV2.sol`, `mWOMSVBaseRewarder.sol`, `vlMGPBaseRewarder.sol`), return early / skip `safeTransferFrom`/`safeTransfer` when `_amountReward == 0`, matching the pattern already used elsewhere in the codebase (e.g. `if (reward > 0)` in `getReward`).

### Proof of Concept
1. A briber creates a Wombat bribe for a pool `lp` using a token that reverts on zero-value `transferFrom` (per https://github.com/d-xo/weird-erc20#revert-on-zero-value-transfers).
2. `bribeProtocolFee`/`bribeCallerFee` are configured (or the bribe amount is small enough) such that, after `protocolFee` and `callerFeeAmount` are subtracted in `WombatStaking.vote`, the resulting `rewardAmount` for that token rounds to `0`, while the original `rewardAmount > 0` gate at [4](#0-3)  was passed.
3. Any user calls `WombatBribeManager.harvestSinglePool([lp])` or `castVotes(...)`.
4. Execution reaches `IBaseRewardPool(_rewarders[i]).queueNewRewards(0, weirdToken)` → `_provisionReward` → `IERC20(weirdToken).safeTransferFrom(msg.sender, address(this), 0)`, which reverts.
5. The whole transaction reverts, and every subsequent call to `castVotes`/`voteAndCast`/`harvestSinglePool` that includes this pool reverts identically, freezing bribe harvesting and vote casting until the pool/bribe is removed by governance.
