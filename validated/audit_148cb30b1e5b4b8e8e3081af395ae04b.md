### Title
Payout tx OP_RETURN (operator pubkey) is not covered by the withdrawal signature, letting an attacker desynchronize `deposit_constant` and burn an honest operator's collateral - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`deposit_constant` is computed twice from two different sources that are supposed to always agree: once by the bridge circuit/host from the operator pubkey embedded in the payout transaction's OP_RETURN output (as actually confirmed on Bitcoin), and once by `create_txhandlers` from the `operator_xonly_pk` baked into the kickoff's `KickoffData` at construction time. Because the payout transaction's OP_RETURN output is not signed by the withdrawing user's `SinglePlusAnyoneCanPay` signature, its bytes can be changed after the user signs, letting an unprivileged actor confirm a payout transaction whose committed operator pubkey differs from the one the honest operator actually used to build their kickoff and disprove script.

### Finding Description
The binding that must hold is:
`deposit_constant(from confirmed payout_tx OP_RETURN)` == `deposit_constant(from KickoffData.operator_xonly_pk baked into the kickoff's additional_disprove_script)`.

- `create_payout_txhandler` builds the payout transaction with three outputs: `[0] user payout`, `[1] anchor`, `[2] OP_RETURN(operator_xonly_pk)` [1](#0-0) . Only input 0 is signed by the user, and the accepted sighash type is `TapSighashType::SinglePlusAnyoneCanPay`, which BIP-341/342 defines as committing the signing input plus **only the output at the same index (index 0)** — outputs 1 (anchor) and 2 (OP_RETURN with the operator pubkey) are not covered by this signature at all [2](#0-1) .
- The host/circuit derives `deposit_constant` purely from whatever OP_RETURN bytes end up in the **confirmed** payout transaction, with no cross-check against a committed/signed value: `parse_op_return_data(&first_op_return_output.script_pubkey)` [3](#0-2) , and the same pattern is used host-side [4](#0-3) .
- Meanwhile, `create_txhandlers` computes `deposit_constant` from `operator_xonly_pk.serialize()` taken from `KickoffData`/`ContractContext` at kickoff-construction time, independent of the eventual payout tx bytes, and this value is baked into the kickoff's `additional_disprove_script` [5](#0-4) .
- Because outputs 1 and 2 are unsigned, an attacker who observes the unconfirmed, signature-valid payout transaction in the mempool can construct a conflicting transaction that keeps input 0 and output 0 byte-identical (required by `SinglePlusAnyoneCanPay`) but substitutes arbitrary bytes into the OP_RETURN output (or a different operator pubkey entirely), and race it to confirmation. `update_finalized_payouts` will then parse this attacker-chosen operator pubkey out of the confirmed OP_RETURN and persist it in the DB as the payout's official payer [6](#0-5) .
- `Verifier::is_kickoff_malicious` explicitly trusts this DB-derived value and flags the honest operator's own correctly-built kickoff as malicious purely because the on-chain OP_RETURN (now attacker-controlled) doesn't match `kickoff_data.operator_xonly_pk` [7](#0-6) . Even independent of that specific function's call graph, the same discrepancy propagates into the zkVM bridge-circuit journal (`deposit_constant`), which is compared against the value hardcoded in the honest operator's `additional_disprove_script`, causing verifiers to treat the operator's genuine bridge-circuit proof as invalid.
- No existing guard binds the payout transaction's OP_RETURN bytes to the user's signature or to any other pre-committed/authenticated value; `is_profitable`, `SPV::verify`, `verify_storage_proofs`, and `lc_proof_verifier` all validate other fields (amounts, inclusion, storage proofs) but never authenticate the OP_RETURN payload itself.

### Impact Explanation
The honest operator who genuinely fronted the withdrawal has their kickoff's `deposit_constant` (computed from their real `operator_xonly_pk` at kickoff time) diverge from the `deposit_constant` the bridge circuit/host will compute from the tampered, confirmed payout transaction. This causes the operator's own correct proof-of-payout to fail verification against the protocol's expected constants, resulting in the operator being treated as malicious and their kickoff being disproved — burning their posted collateral for a payout they legitimately made. This is repeatable per withdrawal/operator since the attack only requires racing a replacement transaction against any operator's payout broadcast, with no special privilege, key, or collateral required by the attacker.

### Likelihood Explanation
The attack requires only network access to observe the operator's unconfirmed payout transaction and broadcast a fee-competitive conflicting transaction before it confirms — capabilities available to any unprivileged Bitcoin user. It costs only the fee needed to outbid the operator's transaction. The main uncertainty (not fully verifiable from the indexed code) is whether the payout transaction as funded via `fund_raw_transaction`/tx-sender is broadcast with RBF signaling or standard mempool policies that would make such a replacement trivial versus requiring a first-seen race against propagation — this affects feasibility but not the fundamental lack of signature coverage over the OP_RETURN output.

### Recommendation
Bind the OP_RETURN operator-pubkey output (and ideally the anchor output) to the same signature that authorizes the withdrawal input, e.g., by requiring/using `TapSighashType::All`-style coverage for a template that fixes all outputs, or by separately committing to the operator pubkey via a mechanism (e.g. a covenant, or requiring the OP_RETURN content match a value pre-registered off-chain before the payout is accepted as "confirmed" for reimbursement purposes) so that no unauthenticated third party can alter it post-signature.

### Proof of Concept
In `circuits-lib`, write a test that:
1. Builds a payout transaction as `create_payout_txhandler` does, with a real `operator_xonly_pk_A` in the OP_RETURN, and computes `deposit_constant` via `circuits_lib::bridge_circuit::deposit_constant` using `operator_xonly_pk_A.serialize()` (mirroring `create_txhandlers` in `creator.rs`).
2. Clone the same transaction but with input/output[0] unchanged and OP_RETURN replaced with `operator_xonly_pk_B` (attacker-substituted), then compute `deposit_constant` again using `parse_op_return_data` on this mutated OP_RETURN (mirroring `mod.rs`'s `bridge_circuit`).
3. Assert the two `DepositConstant` values differ, while asserting `payout_tx.output[0]` (withdrawal payout) is identical in both cases and the user's `SinglePlusAnyoneCanPay` signature verifies against both transaction variants (proving the signature does not protect the OP_RETURN bytes).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}
