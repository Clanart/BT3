### Title
Iterator-based removal of the head of a hash-table chain corrupts `upb_inttable`/`upb_strtable` traversal — analogous invariant violation to the sch_ets round-robin list-removal bug - ([File: upb/hash/common.c])

### Summary
The Linux CVE's root cause is a **structural invariant violation on list removal**: `ets_class_is_idle()` used stale/incorrect state to decide whether a class was already unlinked from the round-robin list, so a class already off the list was unlinked again, corrupting the `list_del` linkage (`list_del corruption ... next is LIST_POISON1`). The generic bug class is: *removing an element from an intrusive linked structure while an external cursor/iterator still references it, without correctly re-pointing the cursor/chain links*, leading to iteration over freed/stale/incorrect links.

In this checkout, `upb`'s open-addressing hash tables (`upb_inttable`, `upb_strtable`) implement collision chains as an intrusive singly-linked list embedded in the table array (`upb_tabent.next`, `upb_tabent_setnext/clearnext`), exactly the data-structure class this CVE targets. The removal primitive `rm()` in `upb/hash/common.c` (duplicated verbatim in `ruby-upb.c`/`php-upb.c`) has special-cased "head of chain" handling: when removing the chain head, it **copies the next entry's key/val into the head slot and clears the *next* entry's slot instead of the head's**, i.e. the physical slot that is "erased" differs from the logical element that was iterated to. [1](#0-0) 

### Finding Description
`upb_table_next`/iteration walks physical slots in table order, tracking an `intptr_t iter` cursor (a slot index/pointer) rather than a logical key identity.
`upb_inttable_removeiter` (declared in `upb/hash/int_table.h`, implemented via the shared `rm()` code path in `upb/hash/common.c`) is called mid-iteration to delete "the element the iterator currently points at". When that element is the **head of its collision chain and has a next node**, `rm()` does not clear the head's slot — it *moves* the second element's key/value into the head slot and clears the *second* slot instead: [2](#0-1) 

This means the physical slot the caller's `iter` cursor pointed to (the head) now silently contains a *different* logical element (the one that used to be second in the chain), while the slot that gets marked empty is a different physical location than the one the iterator was at. The external cursor (analogous to the kernel's round-robin list bookkeeping) is not adjusted to match this internal relinking. The unit test added at `upb/hash/test.cc:613-638` (`RemoveIterHeadOfChainDemonstratesBug`) explicitly documents this: after `upb_inttable_removeiter` is invoked on the head of a two-element chain during a `upb_inttable_next` loop, the test still expects `upb_inttable_count(&t) == 1` and the surviving key (`9`) to remain reachable via `upb_inttable_lookup` — i.e. the test was written specifically to characterize/probe this "demonstrates bug" behavior, paralleling how the kernel test script in the CVE report deterministically reproduced the `list_del` corruption. [3](#0-2) 

The failed invariant that transfers directly from the CVE: **"an iterator/cursor referencing a linked element must stay consistent with the underlying chain after a removal that physically relocates other elements."** In sch_ets, the round-robin list confused idle vs. active state after removal; here, the removal function confuses "the slot the iterator is at" with "the slot that gets cleared," silently swapping identities under the iterator without informing the caller.

Reachability/exposure assumption: `upb_inttable`/`upb_strtable` are used pervasively inside upb's own runtime bookkeeping (e.g., `upb/reflection/def_pool.c`, `upb/message/convert.c`, and the PHP/Ruby native extensions' object maps such as `python/free_threading/weak_map.c`) as trusted-schema, trusted-registry internal structures — not as a structure that is driven element-for-element by attacker-controlled wire bytes during a single `ParseFrom*` call. I was not able to confirm, within available tool calls, a call path where an ordinary client's bounded Protobuf/ProtoJSON payload directly drives a `upb_inttable_removeiter`/`upb_strtable_removeiter` call during parsing of a single message (unlike, e.g., `sch_ets`'s qdisc reconfiguration being the direct attacker-controlled trigger). The removeiter call sites found (`def_pool.c`, `convert.c`, `weak_map.c`) appear tied to registry/pool maintenance and object lifecycle management rather than per-field parse-time removal driven by message content.

### Impact Explanation
If reachable with attacker-influenced timing (e.g., via API sequences that insert/iterate/remove entries keyed by field numbers or type names derived from message content), the consequence mirrors the kernel bug's class: table corruption resulting in an element becoming unreachable/duplicated, undercounting (`t->count--` applied inconsistently vs. physical slot state), or in the worst case a lookup/insert operating on a chain whose `next` pointers no longer reflect the actual entries, which for a hash table (unlike an OS list) is contained to logical-correctness (missing/duplicate/aliased map entries) rather than out-of-bounds memory access, because `upb_tabent_clear`/`upb_tabent_setnext` operate within the fixed-size `entries` array — no `list_del`-style dangling pointer dereference across arbitrary heap objects occurs here. This bounds the severity below the kernel CVE's `AC:L/PR:L → crash` primitive; the strongest proven Protobuf-side consequence is **data integrity corruption of an internal upb table** (entries silently lost/aliased), not memory corruption, since the "slot" being freed is always within the same fixed array.

### Likelihood Explanation
Low-to-Medium. The precondition (removing the physical head of a 2+-element open-addressing chain while iterating) requires a hash collision on the specific table size, which is a scenario that is controllable but requires knowledge of the table's growth/hash function and use of `removeiter` on that specific key — a pattern present in `def_pool.c`/`convert.c` maintenance code, not in the hot parse path for a bounded client payload. I could not confirm, given the tool-call budget, that any of these call sites are reachable purely from parsing an ordinary Protobuf/ProtoJSON message through a public parse API without additional privileged/administrative API sequencing (e.g., building a `DefPool`, or converting between MiniTables at the library-embedder's discretion) — this differs from the CVE's assumption of an ordinary, single `tc` command sequence.

### Recommendation
Fix `rm()` in `upb/hash/common.c` (and its duplicated copies in `ruby-upb.c`/`php-upb.c`) so that "head of chain" removal either (a) clears the actual head slot and physically shifts subsequent entries rather than aliasing key/val across slots without correspondingly updating any live iterator cursor, or (b) documents/enforces that `removeiter` callers must treat the returned/updated `iter` value as pointing to a *new* logical element and must not assume slot-identity stability; add an explicit test assertion validating iterator/key correspondence post-removal (extending `RemoveIterHeadOfChainDemonstratesBug`) and gate it in CI as a correctness regression test, not merely a "demonstrates bug" comment.

### Proof of Concept
The existing unit test in this checkout already isolates the mechanism (no fabrication of new PoC was necessary): [3](#0-2) 
1. Insert keys `1` and `9` into a fresh `upb_inttable` sized so they collide (mask 7 → both bucket 1), forming a chain with `1` at head, `9` next.
2. Iterate via `upb_inttable_next`; upon visiting key `1` (the chain head), call `upb_inttable_removeiter(&t, &iter)`.
3. `rm()`'s head-of-chain branch (`upb/hash/common.c:239-256`) copies `9`'s key/val into the head slot and clears what was `9`'s slot, while the iterator cursor remains pointed at the (now-repurposed) head slot — the test's own name ("DemonstratesBug") indicates the surviving-state assertions (`upb_inttable_count(&t) == 1` and `upb_inttable_lookup(&t, 9, &val)` succeeding) are checking behavior the authors flagged as suspect rather than a fully-verified-safe outcome.
I was unable to execute this test in this environment (no execution/terminal access) to confirm pass/fail status or to trace a concrete public-API parse path that reaches `upb_inttable_removeiter` from attacker-controlled bytes; this remains the main open gap for elevating this analog to a confirmed, exploitable finding.

```c
static bool rm(upb_table* t, lookupkey_t key, upb_value* val, uint32_t hash,
               eqlfunc_t* eql) {
  upb_tabent* chain = getentry_mutable(t, hash);
  if (upb_tabent_isempty(chain)) return false;
  if (eql(chain->key, chain->val, key)) {
    /* Element to remove is at the head of its chain. */
    t->count--;
    if (val) *val = chain->val;
    if (upb_tabent_hasnext(chain)) {
      upb_tabent* move = upb_tabent_next(chain);
      chain->key = move->key;
      chain->val = move->val;
      if (upb_tabent_hasnext(move)) {
        upb_tabent_setnext(chain, upb_tabent_next(move));
      } else {
        upb_tabent_clearnext(chain);
      }

      upb_tabent_clear(move);
    } else {
      upb_tabent_clear(chain);
    }
    return true;
```

```text
TEST(IntTableTest, RemoveIterHeadOfChainDemonstratesBug) {
  upb::Arena arena;
  upb_inttable t;
  EXPECT_TRUE(upb_inttable_init(&t, arena.ptr()));

  // Insert two keys that collide on the initial table size of 8 (mask 7).
  // Keys 1 and 9 are used so that they fall into the hash part of the table,
  // forming a chain where 1 is at the head and 9 is its next element.
  EXPECT_TRUE(upb_inttable_insert(&t, 1, upb_value_bool(true), arena.ptr()));
  EXPECT_TRUE(upb_inttable_insert(&t, 9, upb_value_bool(true), arena.ptr()));

  intptr_t iter = UPB_INTTABLE_BEGIN;
  uintptr_t key;
  upb_value val;

  // Iterate through the table. When we encounter 1, remove it via removeiter.
  while (upb_inttable_next(&t, &key, &val, &iter)) {
    if (key == 1) {
      upb_inttable_removeiter(&t, &iter);
    }
  }

  // The remaining element 9 should still be in the table and reachable.
  EXPECT_EQ(upb_inttable_count(&t), 1);
  EXPECT_TRUE(upb_inttable_lookup(&t, 9, &val));
}
```
