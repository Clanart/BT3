### Title
Attacker-controlled scalar `offset` in `ReceivedOutput::read` is trusted as authoritative spendability metadata without being bound to `output.script_pubkey` — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The emp3r0r bug class is *untrusted metadata accepted at ingest and later used in a privileged context without validation*. In Serai's in-scope code the closest analog lives in `ReceivedOutput`, the structure processors use to describe a spendable Bitcoin output. `ReceivedOutput::read` deserializes three independent attacker-supplied fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — and returns them as a coherent "spendable output" object with no consistency check. The honest constructor, `Scanner::scan_transaction`, only ever produces a `ReceivedOutput` whose `offset` was looked up from the registered `script_pubkey → offset` map. The deserialization path bypasses that binding entirely.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`:

- `Scanner` maintains the invariant that `offset` is meaningful only relative to a specific script: `scripts: HashMap<ScriptBuf, Scalar>` maps each registered P2TR script to the offset that yields `key + offset·G` (lines 153–196). `scan_transaction` populates `ReceivedOutput.offset` exclusively from `self.scripts.get(&output.script_pubkey)` (lines 199–214), so a scanned output is guaranteed spendable by tweaking the shared key with that offset.
- `ReceivedOutput::read` (lines 122–134) performs `Secp256k1::read_F` for the offset, then consensus-decodes the `TxOut` and `OutPoint`, and returns the triple verbatim. There is no check that `p2tr_script_buf(scanner_key + GENERATOR * offset) == output.script_pubkey`, nor even that the `TxOut`'s script corresponds to any registered offset.

The result: whoever supplies the serialized `ReceivedOutput` bytes controls metadata (`offset`) that downstream code treats as the authoritative scalar needed to spend `output`. This is the same trust-shape as emp3r0r accepting agent-supplied `Transport`/`Hostname` strings at check-in and later interpolating them into an operator-side context — bytes authenticated only as "a struct that parses" are used as security-relevant facts.

### Impact Explanation
A party able to feed `ReceivedOutput::read` (e.g., a processor component reporting received outputs to co-signers, or any peer in the message flow that serializes outputs for signing) can report a real on-chain output paired with an arbitrary/incorrect offset. Signers will treat the output as spendable balance of the shared key while the derived spending key `key + offset·G` does not correspond to the output's `script_pubkey`. The funds are reported received but are not spendable under the supplied offset — minted/credited value backed by an output the validator set cannot actually sign for. This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Reachability requires an untrusted party to get bytes into `ReceivedOutput::read`. Within the Serai architecture, received outputs flow between processors and co-signing participants over authenticated channels, so the strongest realistic attacker is one who can inject or corrupt such a serialized output (a compromised external-network data path feeding the reporting processor, or any integration that deserializes `ReceivedOutput`s from storage/inputs not locally produced by `Scanner`). The fix-relevant gap is that the type itself carries an unverified invariant — any current or future caller that trusts a parsed `ReceivedOutput` inherits it. Severity: Medium.

### Recommendation
Either:
- Make `offset` derivation deterministic from authenticated data: store only `outpoint`/`output` plus a small offset index, and re-derive the scalar via `Scanner` at use time, or
- Add a `ReceivedOutput::verify(&self, key: &ProjectivePoint) -> bool` that checks `p2tr_script_buf(key + GENERATOR * self.offset) == Some(self.output.script_pubkey)`, and require callers to run it after `read`, or
- Document on `read` that the offset/script binding is unverified and must be re-established by the caller before the output is treated as spendable.

### Proof of Concept
Conceptual, from `networks/bitcoin/src/wallet/mod.rs`:

```rust
// Honest path: Scanner guarantees offset matches script_pubkey
let mut scanner = Scanner::new(group_key).unwrap();
let offset = scanner.register_offset(some_offset).unwrap();
let received = scanner.scan_transaction(&tx); // offset bound to script

// Attack path: craft bytes directly
let evil_offset = Scalar::from(12345u64); // does NOT correspond to the output's script
let mut buf = Vec::new();
buf.extend(evil_offset.to_bytes());
buf.extend(serialize(&real_txout_matching_our_script)); // real output, wrong metadata
buf.extend(serialize(&real_outpoint));
let forged = ReceivedOutput::read(&mut &buf[..]).unwrap(); // accepted, no binding check
// forged.offset() = 12345; spending key = key + 12345·G ≠ script's key
// downstream code credits forged.value() yet cannot sign for the outpoint
```

Uncertainty note: I did not trace every producer/consumer of serialized `ReceivedOutput`s across `processor/` and `message-queue/` (out of the crypto/bitcoin scope), so the exact ingress path for attacker bytes depends on how processors persist and relay outputs; the missing invariant in `ReceivedOutput` itself is verified from the file above.
