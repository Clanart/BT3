### Title
Permissionless `CallDispatcher.dispatch()` allows anyone to drain funds held or approved to the shared call-executor contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's root cause is that an untrusted/attacker-influenced byte blob is decoded into `(address target, bytes data)` and then blindly `.call()`-ed, with no restriction on who can trigger the decode-and-call path or what `target`/`data` end up being. The Hyperbridge analog is `CallDispatcher.dispatch(bytes)`, the shared "execute arbitrary calldata" utility used by the intents and token-bridging apps: it decodes an attacker-suppliable `Call[]` and executes `to.call{value}(data)` for each entry with **no caller restriction whatsoever**. Because the intended usage pattern (`IntentsBase._execute`, `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`) requires users/solvers to let the `CallDispatcher` move tokens on their behalf (via `transferFrom`-style calls or by holding transient balances before the sweep), any unprivileged caller can invoke `dispatch()` directly to execute a self-crafted `Call[]` that abuses those pre-existing allowances/balances, exactly like the original bug's unguarded decode-then-call.

### Finding Description
`CallDispatcher.dispatch` has no access-control modifier and decodes its input directly into calls to execute: [1](#0-0) 

It is used as a shared execution proxy by `IntentsBase._execute`, which dispatches `order.output.call` (attacker/solver-controlled bytes) through the dispatcher and only *afterward* sweeps any residual ERC-20/native balance left on it: [2](#0-1) 

It is also used identically by the fungible-token bridge apps to execute attacker-supplied `message.data` coming from a cross-chain `Message`: [3](#0-2) [4](#0-3) 

Both usage patterns require that funds be movable *from* solvers/users *to* the dispatcher (so it can immediately re-spend them via `to.call(data)` for swaps/DeFi composition), which in practice means either:
1. Direct ERC-20 approvals to the `CallDispatcher` address (a standing spender for token flows routed through it), or
2. Transient token/native balances sitting on the dispatcher between the `dispatch(order.output.call)` call and the subsequent sweep.

Because `dispatch()` is `external` with no `onlyIntentGateway`/`onlyApp`/`msg.sender` check, **any address** can call it directly with a completely different, self-chosen `Call[]` — for example `Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, attacker, allowance)})`. Since the resulting `transferFrom` call is made with `msg.sender == CallDispatcher`, it succeeds against any allowance a victim previously granted to the dispatcher, or drains any balance the dispatcher happens to be holding at that moment (including native ETH accepted unconditionally via its `receive()`): [5](#0-4) 

This mirrors the audited bug's core flaw: an execution primitive that decodes a byte blob into `(target, data)` and calls it without validating who supplied the blob or binding it to the legitimate caller/context.

### Impact Explanation
An unprivileged attacker can call `CallDispatcher.dispatch()` directly (it is a standalone, permissionless public entrypoint, not gated behind `IntentsBase`/the token apps) to:
- Steal any ERC-20 allowance a solver or user has granted to the `CallDispatcher` address as part of the normal order-fulfillment flow (`transferFrom(victim, attacker, amount)`), and
- Drain any native ETH or ERC-20 balance transiently sitting on the dispatcher (e.g., mid-flow before `IntentsBase._execute`'s sweep completes, or accidental transfers via the unconditional `receive()`).

This is unauthorized execution leading directly to loss of funds for any party that has interacted with the dispatcher's intended flow, satisfying the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" criteria, and requires no malicious relayer, prover, operator, or governance actor — only a plain unprivileged caller of a public contract function.

### Likelihood Explanation
High. `dispatch()` requires no privilege, no proof, and no specific state — any address can call it at any time with arbitrary `Call[]` data. The only precondition is that a victim has an outstanding allowance to the `CallDispatcher` address or that the dispatcher is holding balance at call time, both of which are inherent, expected outcomes of the documented "solvers route through DEXes/lending protocols via the CallDispatcher" design (`IntentsBase._execute`) and the "if calldata present, executes it via the CallDispatcher" design (`HyperFungibleToken`/`WrappedHyperFungibleToken`).

### Recommendation
Restrict `CallDispatcher.dispatch()` to a whitelist of trusted callers (e.g., the specific `IntentsBase`/`IntentGatewayV2` and `HyperFungibleToken`/`WrappedHyperFungibleToken` instances configured to use it), via an `onlyAuthorizedCaller` modifier set at construction/initialization. Additionally, avoid standing ERC-20 approvals to the dispatcher address; instead have solvers approve the specific app contract, which then performs a scoped `transferFrom` into the dispatcher atomically within the same authorized call, and ensure no funds are left on the dispatcher across transaction boundaries.

### Proof of Concept
1. A solver, to participate in composable order fills through `IntentsBase._execute`, grants an ERC-20 allowance directly to the deployed `CallDispatcher` address (a natural pattern to avoid re-approving per-order), e.g. `USDC.approve(callDispatcher, type(uint256).max)`.
2. An attacker (any EOA, no special role) directly calls:
```solidity
Call ;
calls[0] = Call({
  to: address(USDC),
  value: 0,
  data: abi.encodeWithSelector(IERC20.transferFrom.selector, solver, attacker, USDC.allowance(solver, callDispatcher))
});
CallDispatcher(callDispatcher).dispatch(abi.encode(calls));
```
3. Because `dispatch()` performs `to.call(data)` with `msg.sender == callDispatcher`, the `transferFrom` succeeds against the solver's allowance, moving the solver's USDC to the attacker — with no interaction with `IntentGatewayV2`/`IntentsBase`, no relayer, and no proof required.
4. Equivalently, if any native ETH or token balance is transiently present on `callDispatcher` (e.g. mid-`_execute` before the sweep, or via a direct `receive()` transfer), the attacker calls `dispatch()` with `Call({to: attacker, value: address(callDispatcher).balance, data: ""})` to sweep it out first.     function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
