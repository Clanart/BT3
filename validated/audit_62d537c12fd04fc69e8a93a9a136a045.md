## Title
`Pallet::withdraw` unconditionally zeroes the relayer's `Fees` balance, discarding any fee accrued via `accumulate` between the balance read and the zero-write - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads `available_amount` from `Fees::<T>` [1](#0-0) , dispatches an ISMP POST to disburse that amount on the destination, and then resets the entry with `Fees::<T>::insert(..., U256::zero())` [2](#0-1)  instead of subtracting the withdrawn amount. This mirrors the `cancelPromotion` bug class: state that should be decremented/partially cleared is instead wiped wholesale, permanently losing any value that accrued in between.

### Finding Description
`accumulate()` (called via the unsigned `accumulate` extrinsic, processed by any relayer submitting a valid delivery proof) adds to the same `(dest_chain, relayer_address)` `Fees` entry with `*inner += total_fee` [3](#0-2) . This call is permissionless/unsigned and can be submitted by anyone (a relayer proving their own delivery), and nothing in the pallet serializes it against a concurrent `withdraw` call for the same relayer/chain key.

`withdraw()`:
1. Reads `available_amount = Fees::<T>::get(dest_chain, address)` at line 116.
2. Performs several fallible operations (nonce increment, dispatch of the cross-chain POST) which are not synchronous settlements — they just record the intent.
3. Finally executes `Fees::<T>::insert(dest_chain, address, U256::zero())` — an unconditional **set to zero**, not `available_amount -= amount` or `saturating_sub`.

Because Substrate transactions execute in block order (not truly "concurrent" within a block, but across a block-production window an `accumulate` extrinsic for the same relayer can land in the same block, before `withdraw`'s finalization, or the runtime could process both in sequence within one block depending on extrinsic ordering chosen by the block author), any fee accrued by a fresh `accumulate` call for that `(dest_chain, address)` pair between the balance read (line 116) and the final zero-write (line 177) is silently deleted rather than preserved. The relayer already dispatched a withdrawal for the old `available_amount`, so the destination correctly pays that portion — but the newly-accumulated fee, which was never included in the dispatched `WithdrawalParams.amount` / `WithdrawalRequest.amount`, is discarded from `Fees` storage with no compensating disbursement. It is neither paid out nor recoverable: it is deleted state analogous to `delete _promotions[_promotionId]` erasing unclaimed rewards in the PoolTogether report.

Existing guards do not prevent this:
- The nonce (`Nonce::<T>`) only prevents signature replay for the *same* withdrawal request; it does not lock or snapshot the `Fees` balance.
- There is no `try_mutate`/CAS-style subtraction at the end of `withdraw` — the code comment itself states "The `Fees` entry is zeroed so the same balance cannot be withdrawn twice" [4](#0-3) , confirming the zero-out is meant only to prevent double-withdrawal of the *snapshotted* amount, but it also erases anything added afterward.
- `accumulate` has no dependency on or awareness of an in-flight withdrawal for the same relayer.

### Impact Explanation
This is a fund-loss bug that fits the bounty's "loss of funds" category: relayer-earned fees can be permanently erased from on-chain accounting with no path to recovery, because the zeroing occurs unconditionally rather than as a decrement of the exact amount that was dispatched. Any relayer whose `accumulate` extrinsic gets included in the same block window as (or interleaves with) their own `withdraw` extrinsic loses the newly accrued fee. Since `accumulate` is permissionless and can be submitted by any account proving a valid delivery, and `withdraw` is also freely callable by the relayer whenever their balance clears the minimum, this race is triggerable purely by normal usage patterns (e.g., automated relayer bots that batch `accumulate` and `withdraw` calls close together, as seen in `tesseract/messaging/relayer/src/fees.rs`) without requiring any malicious peer, prover, or admin.

### Likelihood Explanation
Moderate-to-high. Relayer tooling in this repo (`tesseract/messaging/relayer/src/fees.rs`, `auto_withdraw`) periodically calls fee accumulation and withdrawal in quick succession for the same relayer/chain pair, and nothing prevents an `accumulate` extrinsic for newly-delivered requests from landing in the same block or transaction-pool window as a `withdraw` extrinsic. No attacker coordination, relayer collusion, or prover misbehavior is required — this can occur under ordinary, honest relayer operation whenever fee accrual and withdrawal timing overlap.

### Recommendation
Change the final step of `withdraw()` from an unconditional zero-set to a saturating subtraction of exactly the `available_amount` that was dispatched:
```rust
Fees::<T>::mutate(withdrawal_data.dest_chain, address.clone(), |bal| {
    *bal = bal.saturating_sub(available_amount);
});
```
This preserves any fee accumulated after the snapshot was taken, mirroring the PoolTogether fix recommendation of decrementing state instead of deleting it outright.

### Proof of Concept
1. Relayer `R` has `Fees::<T>::get(dest_chain, R) = 100`.
2. `R` submits `withdraw` for `dest_chain`; the extrinsic reads `available_amount = 100` at [5](#0-4)  and dispatches a POST requesting disbursement of `100`.
3. Before the `withdraw` extrinsic's final storage write executes (same block, ordered after `withdraw`'s dispatch call but the runtime processes extrinsics sequentially — or more simply, a subsequent block but before `R` observes/queries the reset), `R` (or anyone proving `R`'s delivery) submits `accumulate` for a newly delivered request, adding `50` via `*inner += total_fee` in [6](#0-5) , bringing `Fees::<T>::get(dest_chain, R)` to `150`.
4. If this `accumulate` extrinsic is ordered before `withdraw`'s final `Fees::<T>::insert(..., U256::zero())` line within block execution ordering permitted by the transaction pool/author (both are ordinary signed/unsigned extrinsics with no mutual exclusion), the `withdraw` extrinsic's last line overwrites the balance to `0`, discarding the `50` that was never included in the dispatched withdrawal amount.
5. `R` receives only the originally dispatched `100` on the destination chain; the `50` is unrecoverable — it is not in `Fees` storage, not included in any dispatched request, and no event records its loss beyond the generic `AccumulateFees` event that predates the overwrite.
