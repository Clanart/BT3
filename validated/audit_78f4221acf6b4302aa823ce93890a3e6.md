### Title
Balance desync between EVM StateDB and native bank module via stale `BalanceHandler.prevEventsLen` marker in recursive/nested precompile calls - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The malt `cumulativeCashflowApr` bug is a case of a stateful "cumulative marker" (an index/accumulator meant to bound a window of state) being reused across nested/overlapping invocations without validating that the window boundaries are still consistent, corrupting the derived value. Cosmos EVM's `BalanceHandler` uses the exact same pattern: `prevEventsLen` is a marker recorded before a precompile's native action runs, and is later used as a slice-start index into `ctx.EventManager().Events()` to compute which bank/precisebank events belong to *this* precompile call and must be mirrored into the EVM `StateDB`. If a `BalanceHandler` instance's `prevEventsLen` marker gets overwritten by a nested/recursive precompile invocation before the outer call finishes processing its own events, the outer call's post-processing walks the wrong event-index window — analogous to malt's `cumulativeCashflowApr` window spanning across an epoch boundary it should not cross.

### Finding Description
`BalanceHandler.BeforeBalanceChange` snapshots `len(ctx.EventManager().Events())` into `bh.prevEventsLen` [1](#0-0) , and `AfterBalanceChange` later replays only the events appended after that marker (`events[bh.prevEventsLen:]`) to apply `StateDB.AddBalance`/`SubBalance` for coin-spent/coin-received/fractional-balance-change events [2](#0-1) .

The repository already contains developer-authored regression tests explicitly documenting this exact bug class:
- `evmd/tests/integration/balance_handler/balance_handler_test.go`: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [3](#0-2) 
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`: *"Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"* [4](#0-3) 

While `runNativeAction` in `precompiles/common/precompile.go` allocates a fresh `BalanceHandler` per call to `RunNativeAction` via `p.BalanceHandlerFactory.NewBalanceHandler()` [5](#0-4) , several precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) hold their own `BalanceHandler`-related references as struct fields (one occurrence each per `grep_search`), which can be invoked recursively — e.g. an ICS20 transfer that internally triggers a distribution withdraw/allocate precompile call, or a contract that recursively calls back into the same precompile (as reproduced by the debug-precompile "callback" test). In such nested-call flows, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` on the shared instance before the outer call's `AfterBalanceChange` runs, so the outer call ends up either (a) re-processing events already applied by the inner call — double-crediting/debiting the `StateDB` balance for an address — or (b) skipping events that were emitted before the inner call reset the marker, permanently losing a balance update in the `StateDB` relative to the bank module's ground truth.

### Impact Explanation
This directly breaks the required cross-representation balance invariant between native `x/bank`/`x/precisebank` balances and EVM `StateDB` balances that back ERC20/native token views inside the EVM (the "Asset-representation path" invariant). A stale/incorrect `prevEventsLen` window causes either duplication of a balance credit (double-crediting an attacker- or contract-controlled EVM account, i.e., unauthorized value creation as seen by the EVM) or a permanently lost credit/debit (funds appearing to vanish from the EVM-visible balance while the bank ledger says otherwise, or vice versa), both of which are Critical: irreversible accounting corruption / unauthorized duplication of spendable value across native and EVM-visible balances.

### Likelihood Explanation
The bug is reachable via ordinary, unprivileged transaction flow: any contract call that triggers a nested/recursive precompile invocation (a caller contract invoking a precompile whose native action itself calls another precompile, or calls back into itself) exercises this path. The project's own test suite (`balance_handler_test.go`, `ics20_recursive_precompile_calls_test.go`) demonstrates this is trivially triggerable with a simple caller contract and a callback precompile call — no privileged role, validator, or relayer cooperation required.

### Recommendation
- Ensure `BalanceHandler` instances are never shared across nested/recursive precompile invocations; each call frame (including inner/nested ones) must get its own instance with an independently scoped `prevEventsLen`, or the handler must maintain a stack of markers rather than a single mutable field.
- Where precompiles keep a `BalanceHandler`-related field for reuse across internal calls (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`), audit and refactor them to always obtain a fresh handler per `RunNativeAction`/native-call boundary (matching what `precompile.go`'s `runNativeAction` already does), and add reentrancy guards or explicit nested-call handling so `BeforeBalanceChange`/`AfterBalanceChange` pairs cannot interleave incorrectly.
- Add invariant checks (e.g., in integration tests / simulation) asserting that after any EVM transaction involving nested precompile calls, the sum of `StateDB` account balances for touched addresses equals the corresponding `x/bank`+`x/precisebank` balances.

### Proof of Concept
The existing test `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` in `evmd/tests/integration/balance_handler/balance_handler_test.go` reproduces the mechanics: it deploys a caller contract that recursively invokes a debug precompile (`callback(0)`), which internally triggers repeated precompile re-entry, and asserts on exact event counts (15 total events, 10 `debug_precompile` events) to make the `prevEventsLen` overwrite observable [6](#0-5) . The `ics20_recursive_precompile_calls_test.go` suite additionally targets the real-world nested case of ICS20 transfer + distribution precompile calls leaving stale bank events that get mis-aggregated into `StateDB` balance updates [7](#0-6) .

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
