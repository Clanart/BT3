## Analysis

The DODO bug's broken invariant is: **a quantity computed from a value observed at time T1 is applied to a different, attacker-shifted value at time T2, and the *shape* of the check (ratio/index) hides the substitution.** The Desktop analog to this pattern exists in the partial-commit ("stage selected lines") pipeline, where a user's *line-index* selection captured against a diff at T1 is blindly re-applied to a *freshly re-fetched* diff at T2 (staging time), with no verification that the underlying line content is unchanged.

### Title
Stale line-index diff selection allows silent corruption of partially-staged commit content - (`app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets users select individual lines of a working-directory diff to include in a commit (`DiffSelection`), storing the selection purely as a set of **numeric line indices** relative to a diff snapshot taken at selection time [1](#0-0) . When the user actually commits, `applyPatchToIndex` re-fetches a brand-new diff of the working directory from disk and applies the old, index-based selection to that new diff's hunks, without ever re-validating that the line *content* still matches what the user reviewed [2](#0-1) . If the tracked file's content changes between the time the diff was displayed/selected and the time `stageFiles`/`createCommit` runs, the same line index can now correspond to different content, which is silently included in the patch that gets staged and committed.

### Finding Description
The commit flow is:

1. When a file is selected in the Changes view, Desktop fetches a diff and records `unifiedDiffStart`/line indices for each hunk; the user's selections are stored as raw indices via `DiffSelection` [3](#0-2) .
2. The only "staleness" protection applied on refresh is computing `selectableLines` and dropping selections for indices that are no longer includeable lines — it does **not** compare line contents, only whether an index at the same position is still an add/delete line [4](#0-3) .
3. On commit, `_commitIncludedChanges` passes the working-directory files (carrying their previously-computed `DiffSelection`, by index) straight into `createCommit` → `stageFiles` [5](#0-4) [6](#0-5) .
4. For any file with a partial (line-level) selection, `stageFiles` calls `applyPatchToIndex` [7](#0-6) , which **re-runs `getWorkingDirectoryDiff` against the current on-disk file** to build the diff it will patch from [2](#0-1) .
5. `formatPatch` then walks this brand-new diff's hunks and decides whether to include each line purely by asking `file.selection.isSelected(absoluteIndex)` — an index-only lookup with no content binding to what the user actually reviewed [8](#0-7) .

The corrupted value is the **content bound to a `DiffSelection` line index**: the invariant "the byte content at index N when staged equals the byte content at index N when the user selected it" is never checked. Just like the MagicLP bug (where `balanceOf()` was read fresh at execution time instead of using the value implied at request time), Desktop re-derives the diff fresh at staging time and blindly reapplies indices computed earlier, trusting that nothing changed in between.

### Impact Explanation
This is "silent corruption of what the user commits" — one of the explicitly valid impacts. A malicious/compromised repository (or any concurrent process operating on the working tree the repo triggers, e.g. an auto-run build/format task shipped in the repo and executed by the user's editor on folder open) can rewrite the content of a tracked line between the moment the user reviews/selects lines in Desktop's diff viewer and the moment they click "Commit". Because `applyPatchToIndex` recomputes the diff live and applies the stale index-based selection with no content check, Desktop will stage and commit content the user never saw or approved at that position — potentially injecting malicious code, altering commit provenance, or silently substituting reviewed content, then pushing it upstream. Unlike a benign UI-refresh bug, this specifically breaks the "what you selected is what gets committed" guarantee the whole partial-staging feature depends on.

### Likelihood Explanation
No local/physical access, admin rights, or leaked credentials are needed — only that the user open/build a malicious repository they've cloned or fetched while doing an entirely ordinary review-then-commit action in Desktop. The window between diff display and commit click is attacker-triggerable (a background process just needs to fire during that interval, which can be arbitrarily long for a human reviewing a diff). The existing "guard" (`selectableLines` recomputation in `updateChangesWorkingDirectoryDiff`) only prunes indices that stopped being includeable lines; it does nothing to detect same-position content substitution, so it does not stop this path.

### Recommendation
Bind the selection to actual line content, not just positional index: when re-fetching the diff for staging in `applyPatchToIndex`, compare the newly-fetched diff's hunks/line text against the diff that was current when the selection was made (or hash the working-directory file's mtime/content at selection time and re-check it immediately before staging). If content differs, abort the partial-stage for that file and force the user to re-review, rather than silently applying stale index-based selections to new content.

### Proof of Concept
1. Clone a malicious repository containing a large tracked file plus a benign-looking auto-run task (e.g. `.vscode/tasks.json` with `runOn: folderOpen`) that, once triggered, periodically rewrites a specific line (same line number, same +/- type, different payload) in that file.
2. Open the repo folder in an editor that auto-runs the task, and simultaneously open the repo in GitHub Desktop.
3. In Desktop's Changes view, select the file, review the diff, and select only a specific added line (e.g. line 42) for the commit via `DiffSelection.withLineSelection` UI flow (`app/src/models/diff/diff-selection.ts`).
4. Before clicking "Commit", the malicious task rewrites line 42's content on disk (same position, same diff line-type) without changing the total line/hunk structure.
5. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff fresh, `formatPatch` (`app/src/lib/patch-formatter.ts:143-170`) includes line 42 by index without validating its content, and the newly-substituted content — not what the user reviewed and selected — is staged and committed.
