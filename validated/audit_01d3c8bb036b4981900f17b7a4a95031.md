### Title
Non-canonical `TransactionVersion` byte lets a malicious relayer/attacker mint a bit-flipped duplicate of a signed transaction with a different txid - (File: stacks-codec/src/transaction.rs)

### Summary
`StacksTransaction::consensus_deserialize_with_len` decodes the wire `version` byte by testing only bit `0x80` and discarding the other 7 bits, mirroring the report's root cause: a field's on-wire "identity" (its exact byte tag) is not preserved consistently between the two representations that are supposed to agree (the schema/wire tag vs. the value actually used for hashing/matching). Here, the wire byte and the canonical in-memory enum diverge whenever the low 7 bits are non-zero, which is exactly the same class of tag/identity inconsistency as the `RegisterConcrete` name mismatch in the original report, applied to txid computation instead of Amino type names.

### Finding Description
`consensus_deserialize_with_len` computes the parsed `version` purely from one bit of the wire byte: [1](#0-0) 

while `consensus_serialize` always re-emits the canonical value of the enum: [2](#0-1) 

and the canonical byte values are fixed at `Mainnet = 0x00`, `Testnet = 0x80`: [3](#0-2) 

This means any wire byte in `{0x01..0x7F}` decodes to `Mainnet`, and any byte in `{0x81..0xFF}` decodes to `Testnet`, but once decoded, the struct always re-serializes to `0x00`/`0x80`. Consequently, two byte-for-bit different transaction wire encodings (e.g., version byte `0x00` vs. `0x01`, or `0x80` vs. `0xFF`) parse into **semantically identical** `StacksTransaction` values — same `auth`, `payload`, `chain_id`, same signature — yet the raw bytes received over the network differ.

Because the signature (`sign_begin`/`verify_begin`/`txid()`) is computed from the in-memory, canonicalized struct rather than from the literal wire bytes, both the honest signer and any verifier that itself re-derives the tx via `consensus_deserialize` agree with each other. However, any code path that treats the *raw wire bytes* as the transaction's identity (rather than the canonicalized struct) — for example computing a byte-hash of what was received for message-dedup/relay bookkeeping, or comparing raw payloads across two peers — would see two different byte sequences for what chain-state execution treats as one and the same transaction (same nonce, same fee, same signature). This is a classic "tag not covered by the equality/verification check" bug: the wire tag byte is not canonicalized before being treated as authoritative input to hashing, so bytes that must be treated as equivalent by consensus can be observed as non-equivalent identifiers elsewhere.

### Impact Explanation
If any component (mempool ingestion, message relay bookkeeping, event/RPC layers that hash or key by raw posted bytes) uses the literal wire bytes as a transaction identifier instead of `tx.txid()` computed off the canonical struct, an attacker (or a lossy relayer) can produce a bit-flipped duplicate of a legitimately signed, still-valid transaction that is byte-different but state-machine-identical. This falls into the "mempool-versus-block admissibility divergence" / "a txid/sighash over different bytes than transmitted" category: the same logical transaction can be assigned two different identities depending on whether a node consumed the raw bytes or the canonicalized struct, which can let a duplicate be treated as distinct by one code path and as identical by another (e.g. two peers reaching different views on what "the same" transaction is).

### Likelihood Explanation
Exploitation requires only crafting the low 7 bits of the single version byte in an otherwise-valid, already-signed transaction and does not require any privileged key — this is a pure encoding manipulation on public wire bytes, so the "unprivileged sender" condition is satisfied. However, I could not confirm within this repo's currently-searchable code that any live code path actually hashes/keys transactions by raw wire bytes rather than by `tx.txid()` from the canonical struct (the search for `Txid::from_stacks_tx` / raw-byte-based identity hashing in `stackslib/src/core/mempool.rs` was inconclusive due to tool/iteration limits). Every admission path I was able to inspect (`will_admit_mempool_tx`, `process_transaction_precheck`, `postblock_proposal.rs` validate) operates on the already-deserialized `StacksTransaction` struct, which is canonicalized consistently, so the divergence may be latent/dormant rather than actively reachable today.

### Recommendation
- In `TransactionVersion` deserialization (`stacks-codec/src/transaction.rs`, `consensus_deserialize_with_len`), reject any `version_u8` whose low 7 bits are non-zero (i.e., require `version_u8 == 0x00 || version_u8 == 0x80`) instead of masking with `0x80`, so that only the two canonical byte values are ever accepted. This closes the "many wire bytes map to one struct" gap.
- Audit any code that treats raw transaction bytes (rather than `tx.txid()`) as a transaction identity key (mempool dedup, relay tracking, event dispatch) and ensure all such logic keys strictly off `tx.txid()`/the canonicalized struct, never off byte-equality of the wire payload.
- Add a codec test asserting that `consensus_deserialize` rejects non-canonical version bytes, symmetric to the existing `transaction_version_byte_values` pin test.

### Proof of Concept
1. Take any valid, signed `StacksTransaction` bytes `B` with version byte `B[0] = 0x00` (Mainnet).
2. Construct `B'` identical to `B` except `B'[0] = 0x01`.
3. `StacksTransaction::consensus_deserialize(&mut &B[..])` and `StacksTransaction::consensus_deserialize(&mut &B'[..])` (per `consensus_deserialize_with_len`, `stacks-codec/src/transaction.rs:3056-3060`) both yield a `StacksTransaction` with `version == TransactionVersion::Mainnet`, identical `auth`/`payload`/`chain_id`, and the signature still verifies (`tx.verify(...)`) because verification is computed off the canonicalized struct.
4. `B != B'` as raw byte strings, so any component that hashes or matches on raw bytes (rather than on `tx.txid()`) would treat these as two different transactions, despite the chain-state layer treating them as the exact same transaction (same nonce/fee/signature) — demonstrating the identity divergence.
