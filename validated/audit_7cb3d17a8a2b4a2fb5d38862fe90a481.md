### Title
SetCodeAuthorization replay allows any unprivileged sender to grief a victim's transaction throughput by forcibly reserving their address in the tx pool - (File: `blockchain/tx_pool.go`)

### Summary
The `LpToken` bug is a class of "shared taint state, set unilaterally by an attacker, that restricts a victim's independent operation." The Kaia tx pool has a structurally identical pattern: `SetCodeAuthorization` tuples are signed only over `(ChainID, Address, Nonce)` with no binding to the wrapping transaction or its sender, so anyone who obtains a previously-broadcast authorization from a victim can wrap it into a brand-new `TxTypeEthereumSetCode` transaction that they themselves submit and pay for. Once accepted into the pool, this forcibly caps the victim's account to a single in-flight transaction via `checkDelegationLimit`/`validateAuth`, exactly mirroring how an attacker "taints" an `LpToken` holder by sending them tokens.

### Finding Description
`SetCodeAuthorization.sigHash()` only commits to `ChainID`, `Address` (the delegation target), and `Nonce`: [1](#0-0) 

There is no signature over the sender of the wrapping `TxTypeEthereumSetCode` transaction, nor any other transaction-specific data. Consequently a single signed authorization tuple produced by victim `X` (e.g., leaked from a mempool, a relayer's broadcast, or any public source) can be extracted and reused verbatim inside a completely different transaction crafted and paid for by an unrelated attacker.

When any transaction (whether a `SetCodeTx` carrying `X` as an authority, or one where `X` already has an active delegation) reaches the pool, `checkDelegationLimit` is invoked for the authority address: [2](#0-1) 

and `validateAuth` further enforces a one-in-flight-tx cap for every address listed as an authority in `tx.SetCodeAuthorities()`: [3](#0-2) 

The net effect: an attacker who has obtained `X`'s authorization tuple can submit their own `SetCodeTx` (with a `to`/payload irrelevant to `X`, just embedding `X`'s authorization) and thereby force `pool.all.hasAuth(X)` to become true. Any subsequent transaction from `X` with a nonce different from an already-pending one is rejected with `ErrOutOfOrderTxFromDelegated`/`ErrInflightTxLimitReached` unless it happens to replace the exact pending nonce, i.e., `X` is limited to one in-flight transaction regardless of `X`'s own intent — just like a `LpToken` holder becomes unable to mint/burn after receiving an attacker-controlled transfer, without ever having authorized *that specific* griefing action.

### Impact Explanation
This allows an unprivileged third party to unilaterally restrict a victim's transaction throughput to a single in-flight transaction at will, by replaying a previously observed authorization. This can be used to:
- Block a victim's urgent transaction (e.g., liquidation protection, MEV-sensitive swap, time-boxed action) by keeping their "slot" occupied with attacker-controlled junk `SetCodeTx`s that reuse the victim's authorization.
- Prevent a victim from queuing multiple pending transactions (nonce fan-out) that they would otherwise be entitled to under normal pool limits, since the delegation/authority reservation logic hard-caps them to one in-flight tx irrespective of `ExecSlotsAccount`.

This maps to a concrete availability/griefing impact on an unprivileged transaction sender's ability to get transactions included, analogous to the reported supply/availability-affecting taint griefing in `LpToken`.

### Likelihood Explanation
Likelihood depends on the attacker being able to observe a previously signed authorization from the victim. Because EIP-7702-style authorizations are transaction-agnostic and only need `(chainId, address, nonce)` to match, any authorization that is broadcast even once (e.g., visible in a public mempool, submitted by a relayer, or leaked via any off-chain channel intended for legitimate one-time delegation) becomes permanently reusable by anyone until the authority's on-chain nonce advances past the authorized value. This requires no special access beyond normal RPC transaction submission, matching the required "unprivileged transaction sender" threat model.

### Recommendation
Consider one or more of the following:
- Track authorization tuples that have already been consumed/observed and reject resubmission by a different `from` sender than the one who first broadcast it, or require some binding between the authorization and the specific transaction/sender.
- Relax the in-flight-tx restriction so that only the account that actually signed and submitted the enclosing `SetCodeTx` (or the delegated authority itself when it is also the sender) is limited, rather than any innocent authority address referenced by an unrelated third-party's transaction.
- Allow victims to always be able to replace/cancel the attacker-inserted authorization transaction's effect on their own pending count, e.g., by not counting authorizations from a different sender toward the authority's own `ExecSlotsAccount` allocation unless the authority itself is the tx sender.

### Proof of Concept
1. Victim `X` signs a `SetCodeAuthorization{ChainID, Address: someContract, Nonce: X_nonce}` intending it to be included as part of one specific relayer transaction (standard EIP-7702 workflow). This gets broadcast to the network (visible in mempool) or is otherwise obtainable by the attacker.
2. Attacker `A` (paying their own gas, using their own private key) constructs a new `TxTypeEthereumSetCode` transaction from `A`, embedding the exact same `SetCodeAuthorization` tuple signed by `X` (this is valid because `Authority()` only checks that `(ChainID, Address, Nonce)` recovers to `X`'s pubkey; nothing ties it to `A`'s transaction): [4](#0-3) 
3. Attacker submits this transaction to the pool. `validateAuth`/`checkDelegationLimit` runs and marks `X` as having a pending authorization (`pool.all.hasAuth(X)` becomes true) and/or increments the authority-usage count checked in the `for _, auth := range tx.SetCodeAuthorities()` loop: [5](#0-4) 
4. Victim `X` then attempts to submit their own unrelated transaction with a nonce different from any already-pending nonce for `X`. Because `pool.all.hasAuth(X)` is now true, `checkDelegationLimit` returns `ErrOutOfOrderTxFromDelegated`/`ErrInflightTxLimitReached`, blocking `X`'s legitimate transaction from being pooled, even though `X` never intended for this specific `SetCodeTx` to be submitted by `A`.

Note: I was not able to fully trace how long the `hasAuth`/authority-reservation state persists relative to on-chain nonce changes for `X`, nor whether additional pool-eviction or nonce-advance conditions would clear this state faster than expected — this would need further verification via `blockchain/tx_pool_test.go`'s `TestSetCodeTransactions` suite or a live pool trace to fully confirm the griefing window length.

// Authority recovers the authorizing account of an authorization.
func (a *SetCodeAuthorization) Authority() (common.Address, error) {
	sighash := a.sigHash()
	if !crypto.ValidateSignatureValues(a.V, a.R.ToBig(), a.S.ToBig(), true) {
		return common.Address{}, ErrInvalidSig
	}
	// encode the signature in uncompressed format
	var sig [crypto.SignatureLength]byte
	a.R.WriteToSlice(sig[:32])
	a.S.WriteToSlice(sig[32:64])
	sig[64] = a.V
	// recover the public key from the signature
	pub, err := crypto.Ecrecover(sighash[:], sig[:])
	if err != nil {
		return common.Address{}, err
	}
	if len(pub) == 0 || pub[0] != 4 {
		return common.Address{}, errors.New("invalid public key")
	}
	var addr common.Address
	copy(addr[:], crypto.Keccak256(pub[1:])[12:])
	return addr, nil
}

func (pool *TxPool) checkDelegationLimit(tx *types.Transaction) error {
	from, _ := types.Sender(pool.signer, tx) // validated

	// Short circuit if the sender has neither delegation nor pending delegation.
	if pool.currentState.GetCodeHash(from) == types.EmptyCodeHash && !pool.all.hasAuth(from) {
		return nil
	}
	pending := pool.pending[from]
	if pending == nil {
		// Transaction with gapped nonce is not supported for delegated accounts
		if pool.getPendingNonce(from) != tx.Nonce() {
			return ErrOutOfOrderTxFromDelegated
		}
		return nil
	}
	// Transaction replacement is supported
	if pending.Contains(tx.Nonce()) {
		return nil
	}
	return ErrInflightTxLimitReached
}

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
