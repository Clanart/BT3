### Title
Line-selection state becomes desynchronized from diff content after hunk expansion, causing silent inclusion/exclusion of unintended lines in commits - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The bug-class in the Panoptic report is "an accounting value that is trusted to stay consistent across repeated legitimate operations, but a code path that mutates the underlying data does not correctly update that accounting value, silently corrupting later results." The GitHub Desktop analog is the interaction between `DiffSelection`'s absolute-line-index bookkeeping (`app/src/models/diff/diff-selection.ts`) and the hunk-expansion re-indexing logic (`app/src/ui/diff/text-diff-expansion.ts`). Expanding a hunk shifts the absolute indices of every hunk that comes after it, but the user's partial-selection state (`divergingLines`) is never re-indexed to match, so a selection recorded against one line can silently end up applying to a different line once the diff is patched into a commit.

### Finding Description
`DiffSelection` tracks partial (line-level) selections purely by absolute integer index (`divergingLines: Set<number>`), where the index is `hunk.unifiedDiffStart + lineIndexWithinHunk` [1](#0-0) . These indices are consumed later, when generating the actual patch that gets staged/committed, via `file.selection.isSelected(absoluteIndex)` in `formatPatch`/`formatPatchToDiscardChanges` [2](#0-1) [3](#0-2) .

When a user expands a hunk (a normal, frequently-used UI action to reveal more context around a change), `expandTextDiffHunk` recomputes the `unifiedDiffStart`/`unifiedDiffEnd` of every hunk that follows the expanded one by adding `numberOfNewDiffLines`: [4](#0-3) 

This means every line after the expansion point is now reachable at a *different* absolute index than before. However, `expandTextDiffHunk` only returns a new `ITextDiff`; it never touches the `DiffSelection` object, and the caller (`expandHunk` in `side-by-side-diff.tsx`) only calls `this.setState({ diff: updatedDiff })` — it does not call anything on the file's selection to remap `divergingLines`: [5](#0-4) 

The only place selection state is reconciled against a changed diff is `updateChangedFiles` in `app-store.ts`, and that reconciliation only recomputes the *selectable* lines set (dropping selections for lines that no longer exist) — it does not shift/remap indices that still exist, and it isn't invoked at all on hunk expansion, only when the working-directory diff is reloaded due to on-disk file changes: [6](#0-5) 

So after expansion: a line the user previously deselected at absolute index `N` (to keep it out of the commit) may now be at index `N+numberOfNewDiffLines` (or an entirely different line may now occupy index `N`). `isSelected` still consults the stale index, so the tool silently commits/excludes the wrong line content relative to what the user actually intended and last saw checked/unchecked in the UI.

### Impact Explanation
This causes **silent corruption of what the user commits or pushes**, one of the explicitly valid impact categories. A user reviewing a diff from a cloned/fetched repository, who partially selects lines in one hunk, then expands an earlier hunk to view more context (an extremely common workflow when reviewing changes from an untrusted contributor/PR), can end up staging/committing lines they intended to exclude, or excluding lines they intended to include — without any indication in the UI that the selection mapping changed. Because the corrupted commit is produced from a `git apply`-style patch built entirely from the (now-misaligned) `DiffSelection`, the resulting commit's content silently diverges from the reviewer's actual intent.

### Likelihood Explanation
The trigger (select/deselect some lines in a hunk, then expand a different hunk earlier in the same file) is a completely ordinary and encouraged workflow — it does not require local/physical access, admin rights, prior malware, or any unnatural interaction sequence. A malicious repository author only needs to structure a file so that a benign-looking hunk sits before a hunk containing an unwanted change, in a way that entices the reviewer to expand context near the front of the file after already toggling selections further down — a realistic scenario for reviewing large or noisy diffs.

### Recommendation
When `expandTextDiffHunk` / `expandWholeTextDiff` shift the absolute indices of hunks, the associated `DiffSelection` must be remapped in lockstep (translate every entry in `divergingLines` by the same `numberOfNewDiffLines` offset applied to the corresponding hunks, and add new default-selected entries for the newly-inserted context lines only if they are includeable). This remapping function should be called from `expandHunk`/`onExpandWholeFile` in `side-by-side-diff.tsx` right after the diff is updated, and the updated `DiffSelection` should be pushed through `onIncludeChanged` so downstream state (`WorkingDirectoryFileChange.selection`) stays consistent with the new diff's indexing before any patch is generated.

### Proof of Concept
1. Open a modified file in Desktop with at least two hunks separated by more than `DefaultDiffExpansionStep` (20) unchanged lines, e.g.:
   - Hunk A around line 10 (added line)
   - Hunk B around line 90 (added line)
2. In the Changes view, uncheck the added line in Hunk B (deselect it so it will not be committed) — internally this adds its absolute index to `divergingLines` via `withLineSelection` [7](#0-6) .
3. Click "Expand" on Hunk A (or an earlier hunk) to reveal more context above it. This calls `expandTextDiffHunk`, which shifts `unifiedDiffStart`/`unifiedDiffEnd` for Hunk B and all subsequent hunks by `numberOfNewDiffLines` [8](#0-7) [4](#0-3) , but the file's `DiffSelection.divergingLines` set is left untouched.
4. Commit the file. `formatPatch` calls `file.selection.isSelected(absoluteIndex)` using the new (shifted) indices [2](#0-1) ; because the stale index in `divergingLines` no longer corresponds to the line the user deselected, the previously-deselected line in Hunk B is included in the resulting commit (or a different, unintended line is excluded), with no warning to the user.

Note: I was not able to fully trace every consumer of `DiffSelection` (e.g. `seamless-diff-switcher.tsx`, `changed-file.tsx`) within the available search iterations to rule out an additional remapping step elsewhere in the codebase; if such logic exists it was not found via the searches performed, so this should be verified directly in a running Desktop session before relying solely on this analysis.

  /** Expand a selected hunk. */
  private expandHunk(hunk: DiffHunk, kind: DiffExpansionKind) {
    const contents = this.props.fileContents
    const { diff } = this.state

    if (contents === null || !this.canExpandDiff()) {
      return
    }

    const updatedDiff = expandTextDiffHunk(
      diff,
      hunk,
      kind,
      contents.newContents
    )

    if (updatedDiff === undefined) {
      return
    }

    this.setState({ diff: updatedDiff })
  }
