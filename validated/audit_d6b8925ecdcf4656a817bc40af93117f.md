### Title
`Scanner::scan_block` reports coinbase outputs as received despite consensus maturity delay — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The audit report's bug class is a boundary/wait-period check whose semantics differ from the protocol's actual rule: the code enforces a different delay than intended, so an action is gated by the wrong round count. The Serai analog lives in the in-scope Bitcoin wallet scanner: `Scanner::scan_block` scans every transaction in a block, including `block.txdata[0]` (the coinbase), and returns `ReceivedOutput`s for it even though Bitcoin consensus forbids spending coinbase outputs for 100 blocks. The required waiting-period check is absent/incorrect, so funds are reported as received that are not spendable.

### Finding Description
`Scanner::new` registers the P2TR script for the group key, and `scan_transaction` matches outputs purely by `script_pubkey` (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` then iterates the full `block.txdata` range:

```rust
// networks/bitcoin/src/wallet/mod.rs:221-227
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

Index `0` of `txdata` is always the coinbase transaction. A coinbase output paying to a registered Serai script (P2TR to the group key, or a registered offset script) is therefore emitted as a `ReceivedOutput` carrying only `offset`, `output`, and `outpoint` — with no marker distinguishing it from a normally-spendable output and no maturity check.

Notably, the protocol-aware consumer confirms the intent: `Bitcoin::get_outputs` explicitly skips `block.txdata[1 ..]`'s zeroth element with the comment "Skip the coinbase transaction which is burdened by maturity" (`processor/src/networks/bitcoin.rs:690-691`), i.e., the correct rule is "exclude coinbase," and `scan_block` fails to enforce it. Just as the report's healing check `< 2` applied the wrong bound to a required wait, `scan_block` applies no bound at all to the required 100-block wait.

### Impact Explanation
An unprivileged miner (or anyone directing a coinbase payout, e.g. a mining pool paying out to a Serai deposit address) can cause an output to be reported as a received, spendable wallet output while it is consensus-immature. Any code that feeds these `ReceivedOutput`s into the signing/spending path will construct transactions spending immature coinbase outputs, which the network rejects — or, if an aggregation/forwarding plan treats them as usable liquidity, the wallet misreports its spendable balance. This matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
Reachable via public inputs only: scanning a block is the intended API for untrusted chain data (`scan_block` takes an attacker-influenced `&Block`), and any miner/pool can create a coinbase output to a Serai-registered script_pubkey. The scanner's own doc comment acknowledges the hazard ("If received outputs must be immediately spendable, a post-processing pass is needed"), but `ReceivedOutput` exposes no flag to perform that filtering, and nothing in the API prevents the immature output from flowing to the spend path. Severity is bounded by the fact that it requires a miner to target the address and causes spend failure/balance misreporting rather than theft, so Medium.

### Recommendation
Either skip `block.txdata[0]` inside `scan_block` (matching `Bitcoin::get_outputs`), or record a coinbase/maturity flag on `ReceivedOutput` so consumers cannot treat immature outputs as spendable. If `scan_block` keeps scanning coinbase for accounting purposes, return outputs with maturity metadata and enforce the 100-block bound before the output is eligible for spending.

```rust
// networks/bitcoin/tests/wallet.rs demonstrates the primitive:

// The test must then mine 100 blocks ("Mine until maturity") before the
// output is spendable — proving scan_block emits an output that Bitcoin
// consensus does not yet allow to be spent.
```

Concretely: on regtest, `generatetoaddress(1, Address::from_script(p2tr_script_buf(group_key)))` produces a block whose `txdata[0]` pays the Serai key. `Scanner::new(group_key).scan_block(&block)` returns a `ReceivedOutput` for that coinbase output immediately. Feeding that `ReceivedOutput` into the spend path produces a transaction that nodes reject with a coinbase-maturity error for the next 99 blocks — an output reported received that is not spendable.

Caveat: `scan_block`'s doc comment warns that a post-processing pass is needed for immediate spendability; whether this disqualifies the finding as documented-misuse depends on whether any consumer can realistically perform that pass given `ReceivedOutput` carries no coinbase indicator (they can only re-derive it by cross-referencing `outpoint.txid` with `block.txdata[0]`, which `scan_block` does not surface).
