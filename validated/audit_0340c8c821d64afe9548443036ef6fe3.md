### Title
Block-revenue-sharing rewards bypass validator commission entirely, breaking the "commission applies to all stake rewards" invariant - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The external report's bug class is: a fee/skim percentage (`distributionSkimBps`) is defined by policy but silently applied at final distribution time in a code path that a separate compensation calculation never accounted for, producing a systematic mismatch between the intended split and what actually gets paid. The Agave analog is structurally the same "split applied in one reward path but silently skipped in another parallel reward path" pattern, found in the SIMD-0123 block-revenue-sharing feature: inflation rewards are split between voter (commission) and staker via `commission_split`/`commission_split_preserve_lamports`, but `calculate_block_reward` computes the block-reward portion as a pure pro-rata share of `pending_delegator_rewards` with no commission split applied at all, and that amount is credited straight through as `block_reward` alongside the inflation `stake_reward`.

### Finding Description
For inflation rewards, `redeem_delegation_rewards` fetches `commission_bps` from the vote account and calls `redeem_rewards` → `redeem_stake_rewards`, which internally applies `commission_split`/`commission_split_preserve_lamports` to divide the reward between "voter" (validator commission) and "staker" portions: [1](#0-0) [2](#0-1) 

In contrast, when `block_revenue_sharing` is active, `calculate_block_reward` computes each stake delegation's share of the vote account's `pending_delegator_rewards` purely proportionally to stake, with no commission parameter and no call into `commission_split`/`commission_split_preserve_lamports` anywhere in the function: [3](#0-2) 

That value is then attached directly as `block_reward` on `PartitionedStakeReward`, separately from (and additive to) the commission-split `inflation.stake_reward`: [4](#0-3) [5](#0-4) 

`RewardAccumulation`/`reward_commissions` — the structure used to credit the vote account's commission cut — is built only from the inflation path's `reward_commission`, never from `block_reward`: [4](#0-3) 

This is precisely analogous to the reported bug: a distribution-time percentage (skim/commission) that is defined and enforced in the "normal" reward calculation path is silently omitted from a second, parallel compensation-calculation path (block revenue rewards), so the two paths diverge from the intended split without any explicit code acknowledging or compensating for the discrepancy.

### Impact Explanation
If block-revenue-sharing rewards are meant to be subject to the same validator commission as inflation rewards (as the commission model implies — the vote account operator is compensated for running the validator via `commission_bps` on delegator rewards), then every stake delegation currently receives 100% of its block-reward share with 0% deducted for the vote account's commission, while inflation rewards continue to have commission properly withheld. This causes systematic under-payment to the validator's commission collector and over-payment to delegators for the block-reward-sharing part of total rewards, which is an unprivileged, protocol-level (non-consensus-breaking but fund-misallocation) discrepancy — funds flow to the wrong party at scale (every stake account, every epoch) rather than an attacker-controlled exploit against a single victim.

### Likelihood Explanation
This triggers deterministically, without any attacker action, whenever `block_revenue_sharing` is active and a vote account has a non-zero `pending_delegator_rewards` balance and a non-zero commission — i.e., on every normal epoch boundary for every commissioned validator once the feature is enabled. It is not a rare edge case; it is the default code path taken by `calculate_stake_rewards_and_commissions` whenever `block_revenue_sharing` is true.

### Recommendation
Verify whether SIMD-0123 intends block-revenue rewards to bypass commission by design (e.g., because commission is meant only for inflation issuance and block revenue is meant to flow 100% to delegators). If commission should apply, route `block_reward` through the same `commission_split`/`commission_split_preserve_lamports` logic used for inflation rewards before crediting `stake_reward`, and add the voter's portion into the `reward_commissions` map so it is paid to the commission collector alongside the inflation commission, keeping both reward paths "commission-aware" and consistent.

### Proof of Concept
I could not fully verify how `block_reward` is finally applied to stake accounts during distribution (that logic lives in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, which I found references block_reward 48 times but could not read within the available iterations), so I cannot conclusively confirm whether the design intends commission to apply to block rewards or whether this divergence is already documented/expected behavior. This should be verified against the SIMD-0123 specification and the `distribution.rs` code before treating this as confirmed rather than a structural analog to the reported bug class. /// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

#[cfg_attr(any(test, feature = "dev-context-only-utils"), qualifiers(pub(crate)))]
fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}
