### Title
Recursive precompile calls share a single `BalanceHandler` instance, corrupting `prevEventsLen` and desyncing EVM `stateDB` balances from the native bank keeper - (File: `precompiles/common/precompile.go`, `precompiles/common/balance_handler.go`)

### Summary
The Cosmos EVM analog of the Curves reentrancy bug (where re-entering a fee-transfer callback let a subject claim rewards using stale/incorrect accounting) is the `BalanceHandler` mechanism used by every stateful precompile (`distribution`, `staking`, `erc20`, `werc20`, `gov`, `slashing`, `ics20`). Each precompile call is wrapped in `RunNativeAction`, which creates a `BalanceHandler` to translate native bank `EventTypeCoinSpent`/`EventTypeCoinReceived` events into `stateDB.AddBalance`/`SubBalance` calls, using `prevEventsLen` as the cursor into the event log to know which events belong to that specific call. If a contract makes a **nested/recursive precompile call** during the outer call's execution (e.g., a precompile action that triggers an EVM sub-call back into another - or the same - precompile, which is explicitly exercised by the repo's own `StakingReverter`, `DistributionCaller`, and `debug` precompile test fixtures), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` on a handler instance that may be shared/aliased with the outer call's execution path, and the outer call's `AfterBalanceChange` then processes the wrong slice of `ctx.EventManager().Events()`. This exact bug is called out by name in the codebase's own test suite comment.

### Finding Description
`RunNativeAction`/`runNativeAction` in `precompiles/common/precompile.go` allocates a `BalanceHandler` per invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` [1](#0-0) , and it is intended to bracket a single precompile's native-state mutation with `BeforeBalanceChange`/`AfterBalanceChange`, using an event-log-index cursor (`prevEventsLen`) to determine which bank events (`CoinSpent`/`CoinReceived`) resulted from that call [2](#0-1) [3](#0-2) .

However, the repository's own integration test explicitly documents that this design is broken under recursion: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [4](#0-3) . The accompanying `debug` precompile fixture demonstrates a precompile that calls back into the EVM (`p.evmKeeper.CallEVMWithData`) from within its own execution, re-entering the precompile itself [5](#0-4) , which is precisely the "recursion during a native/EVM call" pattern that the Curves bug exploited (buy/sell fee transfer via `call` re-entering the contract before state finalization).

Because `prevEventsLen` is a single integer field on a `BalanceHandler`, if the *outer* call's `BeforeBalanceChange` records index N, and a nested call overwrites it with a later index N' > N before the outer call's `AfterBalanceChange` runs, the outer call will only process events from index N' onward - silently dropping the bank `CoinSpent`/`CoinReceived` events emitted between N and N' and never applying the corresponding `AddBalance`/`SubBalance` adjustments to the EVM `stateDB`. Conversely, if the balance handler instance is instead reused with a stale, earlier index, events already accounted for by the inner call are re-applied to `stateDB`, double counting a balance change. Either direction breaks the 1:1 invariant between native bank keeper coin balances and EVM `stateDB` balances that every ERC20/WERC20/distribution/staking precompile financial guarantee depends on [6](#0-5) .

This is structurally the same class of bug as the Curves finding: a callback/reentrant execution path interleaves with in-progress accounting bookkeeping (there: `cumulativeFeePerToken`/holder-fee offsets; here: `prevEventsLen`/event-log cursor), letting attacker-controlled nested calls corrupt or desynchronize a balance ledger that is supposed to be updated atomically per top-level operation.

### Impact Explanation
If exploitable end-to-end, this would let an unprivileged contract (e.g., one implementing the `debug`-style callback pattern, or any contract that triggers a precompile call which itself performs a nested EVM call, such as `staking.delegate` → hooks, `distribution.claimRewards` in a loop, or `werc20`/`erc20` transfer flows with token hooks) cause the EVM-visible balance (`stateDB.GetBalance` / ERC20-precompile `balanceOf`) to diverge from the actual native bank-module balance. This is an irreversible accounting corruption of spendable user value across native/EVM balances - matching the "Critical unauthorized minting/duplication/accounting corruption" impact category, since a stateDB balance inflated above the real bank balance is spendable within the EVM (e.g., transferable to other addresses or usable as collateral) even though the backing native funds were never received, and conversely a deflated `stateDB` balance can permanently strand a user's real funds from EVM-visible balance.

### Likelihood Explanation
Likelihood is **uncertain and unverified**. The repository explicitly ships a regression test (`TestRecursivePrecompileCallsWithDebugPrecompile`) targeting this exact scenario, which strongly suggests the maintainers identified and are actively guarding against this bug class. However, the test as currently written only asserts event counts (`len(res.Events)`, `debug_count`) and does **not** assert on final native-bank-vs-stateDB balance equality, so it is not possible from the indexed code to determine whether the underlying `prevEventsLen`-sharing bug is (a) already fixed in `BalanceHandler`/`RunNativeAction`, (b) mitigated by `BalanceHandlerFactory.NewBalanceHandler()` always allocating a fresh instance per call (which the code does show), or (c) still exploitable through some call path where a shared instance survives across nested calls (e.g., if a precompile method itself calls `p.GetBalanceHandler()`-style accessors on `p` rather than a freshly created handler, as suggested by the debug precompile's older variant in `contracts/solidity`/`testutil/testdata/debug/debug.go`, which calls `p.GetBalanceHandler()` - a method not found via search, indicating it may be from an older/vendored copy of the code, not the current `RunNativeAction` path). Given `RunNativeAction` does create a new `BalanceHandler` per top-level call [1](#0-0) , actual exploitability depends on whether nested/recursive precompile invocations within a single EVM transaction re-enter through a code path that reuses the same handler instance or otherwise corrupts the event-index bookkeeping - which requires deeper tracing of `CallEVMWithData` and how precompile dispatch nests to confirm.

### Recommendation
- Confirm with a Devin session whether `RunNativeAction`'s per-call `BalanceHandler` allocation fully isolates nested/recursive precompile calls, or whether any code path (including the legacy `GetBalanceHandler()` pattern seen in `testutil/testdata/debug/debug.go`) shares a `BalanceHandler` across nested calls.
- Strengthen `TestRecursivePrecompileCallsWithDebugPrecompile` to assert final EVM `stateDB` balance equals native bank keeper balance after recursive/nested precompile calls, not just event counts.
- Consider replacing the event-log-index (`prevEventsLen`) cursor approach with a stack-based or call-id-scoped mechanism so that concurrent/nested `BeforeBalanceChange`/`AfterBalanceChange` pairs cannot clobber each other's cursor state, removing any conditions equivalent to the External Report's "claim once per cycle" reentrancy window.

// NOTES: Balance change events involving BlockedAddresses are bypassed.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
