### Title
Unauthenticated `InternalSendTx` broadcast on the aggregator when `client_verification=false` - ([File: core/src/rpc/aggregator.rs])

### Summary
`AggregatorServer::internal_send_tx` performs no caller-identity check of its own; it relies entirely on the gRPC interceptor layer to enforce that only the aggregator's own certificate can invoke `Internal*`-prefixed methods. When `config.client_verification` is `false`, the interceptor installed for every server (including the aggregator) is `Interceptors::Noop`, and the same flag also removes the TLS `client_ca_root` requirement, so no client certificate is required at all. Any caller who can reach the aggregator's gRPC port can therefore call `InternalSendTx` and push an attacker-supplied signed transaction into the aggregator's `tx_sender` broadcast queue.

### Finding Description
The intended binding is: `caller is authorized to call an "Internal"-prefixed RPC ⇔ leaf TLS certificate == our_cert (the aggregator's own cert)`, enforced by `is_internal` and `only_aggregator_and_self` [1](#0-0) [2](#0-1) .

This binding is only wired up when `config.client_verification` is `true`. `create_grpc_server` selects between `OnlyAggregatorAndSelf` and `Noop`, and simultaneously decides whether the TLS layer even requires a client certificate (`client_ca_root`) at all: [3](#0-2) 

`create_aggregator_grpc_server` uses this exact same `create_grpc_server` helper for the aggregator's own service, with no extra hardening for `Internal*` methods specifically; it only logs a warning if verification is turned on, implying the flag is treated as optional/atypical for the aggregator: [4](#0-3) 

With `client_verification=false`, `Interceptors::Noop` is a pass-through (`Ok(req)` unconditionally) [5](#0-4) , so `is_internal`'s `Internal`-prefix gate never executes, and no TLS client certificate is even solicited from the caller.

`internal_send_tx` itself does no additional authentication — it deserializes the attacker-supplied `raw_tx`, and unconditionally inserts it into the shared send queue and commits: [6](#0-5) 

The RPC is exposed on the public `ClementineAggregator` service surface as `InternalSendTx` [7](#0-6) , and documentation explicitly notes the aggregator does not enforce client certificates in general ("The aggregator does not enforce client certificates but does use TLS for encryption"), confirming this is a realistic, exercised deployment state rather than a hypothetical one.

Attacker action: send a `SendTxRequest{ raw_tx: <any bitcoin::Transaction the attacker can validly sign, e.g. spending only their own UTXOs>, fee_type }` to `InternalSendTx` with no client TLS certificate. `internal_send_tx` accepts it, calls `tx_sender.insert_try_to_send(...)`, and commits — an unauthenticated party has caused the aggregator to broadcast/track an attacker-chosen transaction, with no proof of "internal caller" identity at all.

### Impact Explanation
This is an unauthenticated state-changing/broadcasting call reachable by any network peer that can connect to the aggregator's gRPC port when `client_verification=false` — matching the High-severity category "an unauthenticated state-changing or broadcasting call." The attacker cannot forge signatures for inputs they don't control, so they cannot steal bridge funds directly through this path, but they can freely insert arbitrary self-funded transactions into the aggregator's `tx_sender` queue that is shared with legitimate protocol transactions (Challenge/Disprove/Reimburse). Repeatable per request, with no per-caller identity or rate restriction from this code path. (Queue-starvation/fee-bumping-contention consequences are a resource-exhaustion argument that is explicitly out of scope per the rules, so the finding is graded solely on the "unauthenticated broadcasting call" category.)

### Likelihood Explanation
Requires the operator to run the aggregator with `client_verification=false` and `feature=automation` enabled. `client_verification` defaults to `true` in `.env.example` and the regtest docker config, but the code explicitly supports and only warns (not blocks) running the aggregator without it, and the aggregator's `create_aggregator_grpc_server` code path treats verification as an atypical opt-in rather than a hard requirement. Attacker cost is minimal: any network-reachable caller with no BTC, no TLS certificate, and no privileged role can invoke the RPC.

### Recommendation
Do not tie TLS client-certificate enforcement and RPC-method-prefix authorization to a single boolean. Enforce the `Internal*` self-only check unconditionally at the interceptor level (independent of `client_verification`), or require a signed/authenticated token specific to Internal RPCs regardless of TLS configuration, so `InternalSendTx`/`InternalGetEmergencyStopTx` can never be reached without proof of aggregator self-identity even when the aggregator's public methods are intentionally left open.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
