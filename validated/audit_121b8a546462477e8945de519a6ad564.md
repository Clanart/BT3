### Title
Identity/zero-valued verification shares accepted in `ThresholdKeys::read`/`ThresholdKeys::new` allow an unspendable group key - ([File: crypto/dkg/src/lib.rs])

### Summary
The audit finding is a missing zero-value check: `RFPCommitteeStrategy._allocate` accepts `address(0)` as the irrevocable `acceptedRecipientId`, forcing fund withdrawal and redeployment. The Serai analog is a missing identity/zero check on the verification shares and secret share deserialized in `ThresholdKeys::read` and accepted by `ThresholdKeys::new`. `ThresholdKeys::read` reads each verification share via `C::read_G` — the `Ciphersuite`-level reader, which enforces only canonical encoding, not non-identity [1](#0-0) . Only `frost::Curve::read_G` rejects identity [2](#0-1) . `ThresholdKeys::new` similarly validates only the *count* and *indexes* of `verification_shares`, never that any point is non-identity [3](#0-2) . The group key is then derived as the interpolation-weighted sum of `verification_shares[1..=t]` [4](#0-3) .

### Finding Description
An attacker who can influence the serialized `ThresholdKeys` byte stream (the `read` API explicitly takes `reader: &mut R` over untrusted bytes [5](#0-4) ) can encode identity points as verification shares for participants `1..=t` while giving later participants arbitrary points. Because:

- `C::read_G` accepts the canonical identity encoding,
- `ThresholdKeys::new` performs no `is_identity` rejection, and
- `secret_share` is read via `C::read_F` with no zero check [6](#0-5) ,

the constructed `ThresholdKeys` succeeds and yields a `group_key()` equal to an interpolation-weighted combination of attacker-injected points. Two harmful cases:

1. All `t` shares identity → `group_key = identity`. Downstream Bitcoin code (`x_only`, `tweak_keys`) panics or produces an unspendable output; any funds sent there are burned [7](#0-6) [8](#0-7) .
2. Some shares identity → the resulting group key is a valid, non-identity point whose discrete log is not the sum of the intended participant shares; the `secret_share` and `verification_shares` are mutually inconsistent (no check anywhere ties `secret_share * G` to `verification_shares[i]`). The scanner/address derived from `group_key()` will happily match deposits — `Scanner::scan_transaction` matches `script_pubkey` alone [9](#0-8)  — so funds are *reported received* yet can never be signed for, exactly mirroring "accepted recipient is `address(0)`".

### Impact Explanation
Funds sent to the address derived from the corrupted group key are reported received by `Scanner` but are unspendable, because no `ThresholdView`/signing operation can reconstruct a secret consistent with the injected identity/zero shares — and there is no recovery path, since `group_key` was "accepted" at `ThresholdKeys::new` time. Like the original report, the only remedy is discarding the key material and re-running key generation (analogous to redeploying the pool and re-paying fees).

### Likelihood Explanation
Requires attacker-controlled bytes reaching `ThresholdKeys::read` (e.g., a forged/malleated key-distribution payload in transit or in storage) — no signature or proof binds the verification shares in this serialization, and nothing in the read path validates internal consistency. Medium likelihood wherever `ThresholdKeys` bytes cross a trust boundary; negligible if keys are only ever locally generated.

### Recommendation
- In `ThresholdKeys::new` (or in `ThresholdKeys::read`), reject identity verification shares: `if bool::from(share.is_identity()) { Err(...) }`.
- Reject a zero `secret_share` and verify `C::generator() * secret_share == verification_shares[params.i()]` for `Interpolation::Lagrange` keys to enforce share/share-consistency.
- Reject a `group_key` that is identity before constructing `ThresholdCore`.

### Proof of Concept

```rust
// crypto/dkg: deserialize ThresholdKeys with identity verification shares
use ciphersuite::{Ciphersuite, group::GroupEncoding};
use dalek_ff_group::Ristretto;
use dkg::{ThresholdKeys, Participant};

let mut buf = vec![];
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(2u16.to_le_bytes()); // t
buf.extend(3u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend([1u8; 32]);          // secret_share = 1 (no consistency check)
// identity encoding for participants 1..=3 (canonical, so C::read_G accepts)
for _ in 0..3 { buf.extend(Ristretto::G::identity().to_bytes()); }

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // accepted: unspendable key
```

```rust
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<ThresholdKeys<C>> {
    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
```

```rust
pub fn tweak_keys(keys: ThresholdKeys<Secp256k1>) -> ThresholdKeys<Secp256k1> {
  // Adds the unspendable script path per
  // https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki#cite_note-23
  let keys = {
    use k256::elliptic_curve::{
      bigint::{Encoding, U256},
      ops::Reduce,
      group::GroupEncoding,
    };
    let tweak_hash = TapTweakHash::hash(&keys.group_key().to_bytes().as_slice()[1 ..]);
    /*
      https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki#cite_ref-13-0 states how the
      bias is negligible. This reduction shouldn't ever occur, yet if it did, the script path
      would be unusable due to a check the script path hash is less than the order. That doesn't
      impact us as we don't want the script path to be usable.
    */
    keys.offset(<Secp256k1 as Ciphersuite>::F::reduce(U256::from_be_bytes(
      *tweak_hash.to_raw_hash().as_ref(),
    )))
  };

  let needs_negation = needs_negation(&keys.group_key());
  keys
    .scale(<_ as subtle::ConditionallySelectable>::conditional_select(
      &Scalar::ONE,
      &-Scalar::ONE,
      needs_negation,
    ))
    .expect("scaling keys by 1 or -1 yet interpreted as 0?")
}
```
