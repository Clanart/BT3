### Title
Systematic floor-rounding in paymaster token pricing underprices gas reimbursement, allowing guaranteed value leakage from the paymaster on every UserOperation - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` converts the native-gas cost of a UserOperation into an ERC-20 charge using `_tokenPrice()` and (per its own doc-comment) the base `PaymasterERC20._erc20Cost = weiCost * tokenPrice / 1e18`. Both `tokenPrice` itself and the final `erc20Cost` are computed with plain Solidity integer division, which always truncates towards zero. Every truncation reduces the amount the user is charged relative to the true USD-equivalent gas cost, i.e. the rounding direction is chosen in favor of the payer and against the paymaster's reserves — the exact "rounding direction" bug class from the external report, but here it sits in live paymaster settlement rather than a lending health-factor calculation.

### Finding Description
`_tokenPrice()`: [1](#0-0) 
computes `(nativeUsd * 10^tokenDecimals * (10_000 + markupBps)) / (tokenUsd * 10_000)` — a single floor division that always rounds the token/wei exchange rate down.

That price feeds into the base contract's cost formula, documented directly above the function: [2](#0-1) 
`erc20Cost = weiCost * tokenPrice / 1e18` — a second floor division on top of the first.

The same double-floor pattern is duplicated in the public estimator: [3](#0-2) 

Both divisions always round down, never up. There is no compensating ceiling anywhere in the pricing path (unlike, e.g., a `mulDivRoundingUp`). Because `_validatePaymasterUserOp`/`_fetchDetails` are invoked by the EntryPoint on every single UserOperation for any unprivileged sender holding a registered token, this is a **repeatable, permissionless, self-triggerable** path — no relayer, prover, or admin cooperation is required. Any account can submit UserOperations through the paymaster and, on each one, extract the (small but non-zero) rounding delta between the true USD-equivalent gas cost and the floor-rounded token amount actually pulled via `transferFrom`/permit.

### Impact Explanation
The paymaster prefunds gas in native token from its EntryPoint deposit and is supposed to recoup the USD-equivalent value in ERC-20 from the sender. Because pricing always rounds down, the paymaster's ERC-20 receipts are guaranteed to be less than or equal to the native gas it actually advanced, scaled by the oracle rate — the imbalance can only run one direction, in favor of every caller and against the protocol's `treasury`-controlled paymaster balance. This is systemic value leakage from the paymaster (a bridge-adjacent, protocol-owned reserve), matching the "loss of funds" and "logic attack" categories in the impact gate: an unprivileged actor can, over many low-value UserOperations (e.g. tokens with few decimals or low unit price where the floor discount is proportionally larger relative to `weiCost`), harvest guaranteed dust that should have accrued to the treasury. Severity is bounded per-transaction (this mirrors the "Medium Risk" classification of the seed report), but it is a real, exploitable, self-inflictable asymmetry rather than a benign estimation error.

### Likelihood Explanation
High likelihood of triggering (it fires on every UserOperation, not a rare edge case), but each individual instance yields only rounding-scale value, so realized economic impact per call is small. An attacker wanting to make this meaningful would need to drive volume (many UserOps through cheap-decimal or low-price tokens) — no privileged role, malicious relayer, or governance action is needed, satisfying the "public entrypoint, unprivileged attacker" requirement.

### Recommendation
Round the paymaster's own cost calculations up (ceiling division) rather than down, consistent with the general rule that a protocol computing what it is owed should always round in its own favor:
- In `_tokenPrice()`, use a ceiling-division helper for `(nativeUsd * 10^tokenDecimals * (10_000 + markupBps)) / (tokenUsd * 10_000)`.
- Ensure the final `erc20Cost = weiCost * tokenPrice / 1e18` composition (in the inherited `PaymasterERC20`, or via an override of `_erc20Cost` if available) also rounds up rather than down.
- Apply the same ceiling treatment to `estimateTokenCost` so off-chain estimates match on-chain charging direction.

### Proof of Concept
1. Register a token with a `tokenUsd`/`nativeUsd` ratio and `tokenDecimals` chosen such that `_tokenPrice()` truncates a non-zero fractional token-per-wei unit (e.g. a 6-decimal stablecoin at a price where `(nativeUsd * 1e6 * (10_000+markupBps))` is not evenly divisible by `(tokenUsd * 10_000)`).
2. Submit a UserOperation through the EntryPoint using this paymaster with `paymasterData` mode `0x01` (pre-approved token).
3. Compute the true USD-equivalent cost off-chain (`weiCost * exact_price / 1e18` without truncation) and compare to the actual `erc20Cost` pulled via `transferFrom` in `_postOp`.
4. Observe `erc20Cost < true_cost` on every call; repeating the UserOperation N times accumulates `N × (true_cost − erc20Cost)` in guaranteed value that never reaches `treasury`, extracted purely by normal unprivileged usage of the paymaster's public entrypoint.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    function estimateTokenCost(
        address token,
        uint256 gasAmount,
        uint256 maxFeePerGas
    ) external view returns (uint256) {
        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);

        uint256 weiCost = gasAmount * maxFeePerGas + _postOpCost() * maxFeePerGas;
        return (weiCost * _tokenPrice(cfg)) / _tokenPriceDenominator();
    }
