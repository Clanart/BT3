### Title
Unbounded attacker-controlled `sender` index causes HashMap index panic in blame evaluation - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`BlameMachine::blame_internal` (reached via `BlameMachine::blame` and `AdditionalBlameMachine::blame`) indexes `self.commitments` with the attacker-supplied `sender` participant index via `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`. `commitments` only contains keys `1..=n` (built by `AdditionalBlameMachine::new` at `crypto/dkg/pedpop/src/lib.rs:656-660` or by `KeyMachine::calculate_share` over `all_participant_indexes`). `Participant` is any non-zero `u16`, so a blame claim naming a `sender` outside `1..=n` (e.g., `Participant(200)` in a 5-of-5 DKG) reaches a `HashMap` `Index` panic, crashing the process evaluating blame. This is the same bug class as CVE-2023-31619: attacker-crafted input drives the parser/handler into a crash, yielding denial of service.

### Finding Description
`blame_internal` decrypts the supplied `EncryptedMessage`/`EncryptionKeyProof` (both readable from untrusted bytes via `EncryptedMessage::read`/`EncryptionKeyProof::read`) and then, if decryption succeeds, evaluates the share against `&self.commitments[&sender]`:

Neither `blame`, `blame_internal`, nor `AdditionalBlameMachine::new` validates `sender`/`recipient` against `1..=n`; `Participant::new` accepts any non-zero `u16` (`crypto/dkg/src/lib.rs:29-35`). The analogous `self.commitments[&l]` uses in `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:490`) are safe because `validate_map` restricts `l` to `all_participant_indexes`, but the blame path performs no equivalent check. [2](#0-1) 

### Impact Explanation
Any party able to submit a blame message (in the Serai processor this machinery is used to adjudicate `Blame`/`AdditionalBlame` claims that determine fatal slashing; `AdditionalBlameMachine::new` explicitly supports non-participants evaluating blame) can crash the evaluating node by naming a `sender` index outside the participant set. A panic during blame resolution aborts the protocol/node — a remote, input-triggered denial of service equivalent in class to the CVE's crafted-statement crash.

### Likelihood Explanation
Triggering requires only that `decrypt_with_proof` return `Ok` for the claimed `sender`. Since the accuser fabricates the `EncryptedMessage` and `EncryptionKeyProof` bytes themselves, they can generate an honestly-constructed message/proof bound to any participant index they choose (the encryption transcript commits to the claimed index, which they control). A `sender` of `Participant(n + k)` then passes decryption/proof checks and hits the unchecked map index. Likelihood is moderate: the crash is deterministic once reached, but requires the blame flow to be exercised.

### Recommendation
In `BlameMachine::blame_internal` (and before `self.commitments[&sender]`/`recipient` use), validate that `sender` and `recipient` are members of the participant set (`self.commitments.contains_key(&sender)` / range check against `params.n()`) and return the accuser or an error as faulty otherwise. Alternatively store the participant bound in `BlameMachine` and reject out-of-range indexes at the `blame`/`AdditionalBlameMachine::blame` boundary.

### Proof of Concept
1. Complete or simulate a PedPoP DKG with `ThresholdParams { t, n, i }` (e.g., n = 5), producing a `BlameMachine`/`AdditionalBlameMachine` whose `commitments` map holds only `Participant(1)..=Participant(5)`.
2. As an attacker, fabricate a valid `EncryptedMessage<C, SecretShare<C::F>>` and `EncryptionKeyProof<C>` for a claimed `sender = Participant(6)` (or any index `> n` / not in the map), serializing them into untrusted bytes delivered through `EncryptedMessage::read`/`EncryptionKeyProof::read`.
3. Call `blame(sender, recipient, msg, proof)` (or `AdditionalBlameMachine::blame`). `decrypt_with_proof` succeeds because the proof is genuinely valid for the claimed index, then `self.commitments[&Participant(6)]` panics on `HashMap` indexing, aborting the evaluator.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
