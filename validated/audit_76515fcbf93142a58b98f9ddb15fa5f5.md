### Title
Malicious preprocess commitments force `R` to the point at infinity, panicking BIP-340 `Hram`/`x_only` during FROST-Bitcoin signing - (File: networks/bitcoin/src/crypto.rs)

### Summary
The `multihash` advisory class is "an input-parsing function with a `Result` return type unexpectedly panics on attacker-controlled bytes." The Serai analog lives in the FROST Secp256k1 signing path: per-participant preprocess commitments are read from untrusted bytes via `read_preprocess` → `Commitments::read` → `GeneratorCommitments::read`, which only rejects the identity point per individual commitment (`Curve::read_G`). The aggregate nonce `R` used by `sign_share`/`verify` is a linear combination of these commitments, and the BIP-340 `Hram` helper `x()`/`x_only()` calls `.expect()` on the point at infinity. A malicious signer can craft commitments so the summed `R` is identity, deterministically panicking every honest signer who calls `sign`, and any aggregator calling `complete`.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::sign` reads each participant's `Preprocess` (commitments `D, E` per generator) and computes bound nonces `R = Σ_j (D_j + rho_j · E_j)` via `BindingFactor::nonces` (crypto/frost/src/nonce.rs:194-212). `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) rejects an identity *individual* point, but nothing prevents the *sum* of bound commitments from being identity. Because each participant's `rho_j` is a public hash over the committed transcript and `D_j` is a free attacker-chosen point, an attacker who goes last can compute their own `rho_j` influence and simply set `D_j = target - rho_j·E_j` so the total `R` equals the identity element.

That `R` flows into `Algorithm::sign_share`/`verify` for the Bitcoin `Schnorr` algorithm (networks/bitcoin/src/crypto.rs:85-160), whose `Hram::hram` calls `x(R)` (crypto.rs:65), and `x` executes `key.to_encoded_point(true)` then `.x().expect("point at infinity")` (crypto.rs:13-16), and `x_only` similarly `.expect()`s (crypto.rs:21-23). The doc comment admits "This may panic if called with nonces/a group key which are the point at infinity" but incorrectly claims this is only of "negligible probability... even with malicious participants present" — it is in fact deterministically triggerable.

### Impact Explanation
A single malicious participant (or any party able to submit preprocess bytes to a signer/aggregator) causes an unhandled panic in honest nodes' signing processes — a remote, unprivileged denial of service against the threshold-signing service, identical in effect to the `multihash` panic-DoS class. Because `panic = "abort"` or an unwinding panic both terminate the signing round/process, the attacker can repeatedly crash coordinators each signing attempt, halting all Bitcoin withdrawals.

### Likelihood Explanation
Reachability is direct: `read_preprocess` consumes bytes from the peer's preprocess message, `sign` sums them into `R`, and `sign_share`/`verify` invoke `hram` on that `R` with no identity check on the aggregate. Constructing the malicious commitment is trivial (choose `E_j` arbitrarily, compute `rho_j`, set `D_j` to cancel the sum). No collusion, leaked keys, or broken transport assumptions are required — only one malicious signer in the included set, which FROST's security model explicitly tolerates up to `t-1`.

### Recommendation
Reject the aggregate `R` (and each per-generator bound nonce `Rs[n][g]`) if it is the identity in `BindingFactor::nonces`/`AlgorithmSignMachine::sign`, returning `FrostError` instead of proceeding; or make `x`/`x_only`/`Hram::hram` return `Option`/map identity to a rejected signature. A `debug_assert`+error path at the `Schnorr::verify`/`sign_share` boundary would also contain the panic.

### Proof of Concept
1. Honest signer runs `AlgorithmMachine::<Secp256k1, Schnorr>::preprocess` and advertises its preprocess.
2. Attacker reads all other parties' preprocesses (`read_preprocess`), computes each `rho_j` via the public `rho_transcript`, then serializes a preprocess whose `GeneratorCommitments` `E_j` is arbitrary and `D_j = -(Σ_{k≠j}(D_k + rho_k·E_k)) - rho_j·E_j`, i.e., a valid non-identity point passing `Curve::read_G`.
3. The victim calls `sign(preprocesses, msg)` → `B.nonces(&nonces)` yields `R = identity` → `Schnorr::sign_share` → `Hram::hram(R, A, m)` → `x(R)` → `expect("point at infinity")` → panic.

Uncertainty: I did not fully trace whether `IetfSchnorr::verify`/`sign_share` checks `R` identity before invoking `Hram` (frost/src/algorithm.rs was not read); if it does, the same attacker-controlled panic still applies at the `Hram::hram`/`needs_negation` call on `sig.R` inside `Schnorr::verify` (crypto.rs:145-149) — either way an aggregate-identity `R` reaches code documented to panic.
