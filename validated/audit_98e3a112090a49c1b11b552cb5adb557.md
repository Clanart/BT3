## Analysis

The Farcaster bug class — a transfer function that changes only the primary "owner" attribute while leaving an independent, equally-privileged "recovery" mechanism untouched, letting the previous owner reclaim the asset via that separate channel — maps onto Chia's DID (Decentralized Identity) singleton design.

A `DIDInfo` carries both the current inner puzzle (owner p2 puzzle) and a separate `backup_ids`/`num_of_backup_ids_needed` recovery list, which is baked into the on-chain DID inner puzzle (`p2_puzzle, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata`) [1](#0-0) [2](#0-1) . Backup DIDs listed in `recovery_list`/`backup_ids` retain the ability to sign an "attestment" spend (`create_recovery_message_puzzle` / `create_spend_for_message`, using `AGG_SIG_UNSAFE`) that lets the DID be recreated to a puzzle hash of the recovering party's choosing [3](#0-2) , exactly analogous to Farcaster's `recover()` acting through the `recovery` address.

`DIDWallet.transfer_did()`, the function used when selling/handing off a DID to a new owner, only changes the p2 puzzle hash (owner) while explicitly preserving `self.did_info.backup_ids` and `num_of_backup_ids_needed` in the new inner puzzle unless `reset_recovery_list()` happens to clear it: [4](#0-3) 

`reset_recovery_list()` only clears the recovery list in two narrow edge cases (already-zero verification requirement with a non-nil hash, or an already-empty `backup_ids` list); in the normal case where a seller configured a nonzero `num_of_backup_ids_needed` with real backup DIDs, the recovery list hash is carried forward unchanged into the transferred singleton: [5](#0-4) 

The code even documents awareness of this exact hazard as an operational (not enforced) requirement: [6](#0-5) 

This is the direct analog: `transfer_did()` is the `transfer()`/`transferFor()` equivalent, and it does not force clearing/updating the recovery mechanism atomically with ownership transfer — leaving that as a documentation comment ("the seller should clean the recovery list") rather than a code-enforced invariant. There is no `transferAndChangeRecovery`-style function in `DIDWallet` that atomically transfers ownership and clears/rotates the backup list in one spend.

### Title
DID transfer does not atomically clear the recovery/backup-ID list, allowing a prior owner to reclaim the singleton via the recovery attestment path - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
`DIDWallet.transfer_did()` changes only the DID's owner puzzle hash (`new_puzhash`) while carrying forward the existing `backup_ids`/`num_of_backup_ids_needed` recovery configuration unless it happens to fall into one of two narrow no-op conditions in `reset_recovery_list()`. Because the DID recovery mechanism (backup DIDs attesting via `AGG_SIG_UNSAFE`, see `create_recovery_message_puzzle`) is a fully independent, equally-privileged channel to change ownership of the DID singleton, a seller who still controls (or colludes with) an entry in the transferred DID's backup list can later drive a recovery spend and redirect the singleton to a puzzle hash they control, seizing it back from the buyer — mirroring the Farcaster `IdRegistry` bug where `transfer()`/`transferFor()` moved `owner` but left `recovery` untouched.

### Finding Description
A DID singleton's authority is split between: (1) the current inner p2 puzzle (owner), and (2) a `backup_ids` list with a `num_of_backup_ids_needed` threshold curried into the DID inner puzzle, which functions as the "recovery" channel [7](#0-6) . When a DID is sold/transferred via `transfer_did`, only the p2 puzzle hash changes; the recovery list is preserved by default: [8](#0-7) 
`reset_recovery_list()` clears the recovery hash only when `num_of_backup_ids_needed == 0` and the existing hash is non-nil, or when the wallet's local `backup_ids` list is already empty [5](#0-4) . In the ordinary "DID with active recovery configured" case (nonzero threshold, populated `backup_ids`), the list is retained unchanged across the transfer. The buyer receives a DID whose recovery set was chosen entirely by the seller. If the seller is one of (or controls) those backup identities, they can subsequently construct a recovery spend using the attestment mechanism (`create_recovery_message_puzzle`/`create_spend_for_message`) to move the singleton's inner puzzle to an address they control, effectively reversing the sale — the buyer's ownership is revocable by the seller after the sale closes, with no explicit atomic "transfer + clear recovery" primitive analogous to Farcaster's fix (`transferAndChangeRecovery`).

### Impact Explanation
This allows unauthorized coin/singleton takeover: the buyer of a DID (or of an NFT owned by that DID, since NFT ownership traces back to the DID) can lose control of the asset they paid for, because the previous owner retains an independent recovery channel that was never intended to be a persistent backdoor after a legitimate transfer. This constitutes unauthorized coin movement/ownership reversal of a paid-for DID singleton.

### Likelihood Explanation
Exploitability depends on wallet/UX behavior: a well-behaved seller wallet is expected to clear the recovery list before selling (as the code comment states), and `reset_recovery_list()` does clear it in the specific case where the local `backup_ids` are already empty. However, this is a convention enforced by wallet software, not a puzzle-level or protocol-level guarantee, and the DID transfer solution itself explicitly re-supplies `self.did_info.backup_ids` when building the transfer solution (`innersol = Program.to([2, p2_solution, [], [], [], self.did_info.backup_ids])`) — so any seller (or any tooling reusing `transfer_did` without pre-clearing the backup list) can leave stale backup IDs in place, and a buyer inspecting only the ownership puzzle hash has no straightforward guarantee the recovery set was cleared unless they separately verify it via `did_get_info`'s `recovery_list_hash`/`num_verification` fields.

### Recommendation
Enforce clearing (or requiring explicit re-confirmation) of `backup_ids`/`num_of_backup_ids_needed` as part of `transfer_did`, rather than relying on a best-effort `reset_recovery_list()` and a code comment. Consider adding an explicit "transfer and reset recovery" method that always nils out the recovery list/threshold atomically with the ownership change, and have wallet RPCs/UI surface a warning or refuse to complete a DID transfer transaction unless the recovery list is empty or explicitly reviewed/re-set by the buyer.

### Proof of Concept
1. Seller creates a DID with `backup_ids=[seller_backup_did]`, `num_of_backup_ids_needed=1` (a normal DID-with-recovery configuration).
2. Seller calls `transfer_did(new_puzhash=buyer_ph, ...)`; since `backup_ids` is non-empty, `reset_recovery_list()` returns the original (non-cleared) hash, and the new inner puzzle for the buyer still curries in `seller_backup_did` as a valid recovery identity [9](#0-8) .
3. Buyer receives/confirms the DID, believing they are the sole owner.
4. Seller, using `seller_backup_did`, constructs a recovery attestment spend (`create_recovery_message_puzzle`/`create_spend_for_message`) targeting the DID coin, and drives the recovery flow to redirect the DID's p2 puzzle hash back to an address the seller controls.
5. Seller regains full control of the DID (and any NFTs tied to it), reversing the sale without the buyer's consent.

```python
def create_innerpuz(
    p2_puzzle_or_hash: Program | bytes32,
    recovery_list: list[bytes32],
    num_of_backup_ids_needed: uint64,
    launcher_id: bytes32,
    metadata: Program = Program.to([]),
    recovery_list_hash: Program | None = None,
) -> Program:
    """
    Create DID inner puzzle
    :param p2_puzzle_or_hash: Standard P2 puzzle or hash
    :param recovery_list: A list of DIDs used for the recovery
    :param num_of_backup_ids_needed: Need how many DIDs for the recovery
    :param launcher_id: ID of the launch coin
    :param metadata: DID customized metadata
    :param recovery_list_hash: Recovery list hash
    :return: DID inner puzzle
    Note: Receiving a standard P2 puzzle hash wouldn't calculate a valid puzzle, but
    that can be useful if calling `.get_tree_hash_precalc()` on it.
    """
    backup_ids_hash: Program | bytes32 = Program.to(recovery_list).get_tree_hash()
    if recovery_list_hash is not None:
        backup_ids_hash = recovery_list_hash
    singleton_struct = Program.to((SINGLETON_TOP_LAYER_MOD_HASH, (launcher_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return DID_INNERPUZ_MOD.curry(
        p2_puzzle_or_hash, backup_ids_hash, num_of_backup_ids_needed, singleton_struct, metadata
    )
```

```python
def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle


def create_spend_for_message(
    parent_of_message: bytes32, recovering_coin: bytes32, newpuz: bytes32, pubkey: G1Element
) -> CoinSpend:
    """
    Create a CoinSpend for a atestment
    :param parent_of_message: Parent coin ID
    :param recovering_coin: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: CoinSpend
    """
    puzzle = create_recovery_message_puzzle(recovering_coin, newpuz, pubkey)
    coin = Coin(parent_of_message, puzzle.get_tree_hash(), uint64(0))
    solution = Program.to([])
    return make_spend(coin, puzzle, solution)
```

```python
    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash
```
