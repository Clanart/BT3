Unconditional indexing of unregistered participants panics during secret-share generation, share calculation, and blame evaluation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption`/`Encryption` track per-participant state in `enc_keys: HashMap<Participant, C::G>`, populated by `Decryption::register`. Analogous to the kernel bug where `__dma_async_device_channel_register()` may fail yet `__dma_async_device_channel_unregister()` unconditionally touches every channel, PedPoP's downstream paths dereference `enc_keys`/`commitments` for participants that may never have been registered — `Encryption::encrypt` uses `self.decryption.enc_keys[&participant]` (encryption.rs:466), `KeyMachine::calculate_share` uses `self.commitments[&l]` (lib.rs:490), and `BlameMachine::blame_internal`/`Decryption::decrypt_with_proof` use `self.commitments[&sender]` / `self.enc_keys[&decryptor]` (lib.rs:599, encryption.rs:388). A missing or unregistered index causes a panic.

### Finding Description
In `SecretShareMachine::verify_r1` (crypto/dkg/pedpop/src/lib.rs:313-315), registration silently skips absent participants:

```rust
let Some(msg) = commitment_msgs.remove(&l) else { continue };
let mut msg = self.encryption.register(l, msg);
```

A participant that never delivered a round-1 `EncryptionKeyMessage` is never registered in `enc_keys`, and no entry exists in `commitments` for them. `validate_map` only gates the supplied map's keys, so a participant absent from `commitment_msgs` proceeds past verification as if unregistered — mirroring `chan->local == NULL`.

Immediately after, `generate_secret_shares` (lib.rs:359-369) iterates *all* participant indexes and calls `self.encryption.encrypt(rng, l, share_bytes)`, which unconditionally evaluates `self.decryption.enc_keys[&participant]` (encryption.rs:466). Any skipped participant → index panic, aborting key generation for the honest node.

The same pattern persists in the teardown phases:

- `KeyMachine::calculate_share` (lib.rs:476-491): for each supplied share from `l`, it queues `share_verification_statements(self.params.i(), &self.commitments[&l], share)` — a panic if `l` was skipped in `verify_r1`.
- `Decryption::decrypt_with_proof` (encryption.rs:388): `self.enc_keys[&decryptor]` panics if the `decryptor`/`recipient` `Participant` index was never registered (e.g., an index `> n`, since `Participant::new` only rejects zero).
- `BlameMachine::blame_internal` (lib.rs:599): `self.commitments[&sender]` panics for an out-of-range `sender`.

`AdditionalBlameMachine::new` (lib.rs:649-661) is the "unconditional unregister" counterpart: it registers every `1..=n` participant and errors on a `MissingParticipant`, but the constructed machine still trusts caller-supplied `sender`/`recipient` indexes at `blame` time, which are not bounded against `n` anywhere in pedpop.

### Impact Explanation
A faulty DKG participant can crash honest participants:

- Withholding its `EncryptionKeyMessage`/commitments while remaining in the session causes every honest node to panic inside `generate_secret_shares` (`enc_keys[&participant]`) when it tries to encrypt that participant's share — aborting the key-generation ceremony before `ThresholdKeys` are produced.
- Sending a round-2 `EncryptedMessage` share while having withheld round-1 commitments causes a panic in `calculate_share` (`commitments[&l]`).
- A blame/accusation naming an out-of-range `accused`/`accuser` index causes `AdditionalBlameMachine::blame` to panic instead of returning a fault verdict — a crash instead of attributable abort. This is directly reachable from the processor's `VerifyBlame` handler (processor/src/key_gen.rs:504-549), which forwards `accuser`/`accused` into `blame` after only `read`ing the share bytes.

This mirrors the CVE: registration can legitimately be absent (failure/skipped channel), yet downstream unregister/decrypt/blame paths dereference the state unconditionally. The consequence is a denial of service against threshold key generation and the blame/slashing path — exactly the availability impact class of the original NULL dereference.

### Likelihood Explanation
- Reachability: the skipped-participant path is exercised by any session participant that simply does not transmit a commitments message (or whose message is dropped); the `else { continue }` branch proves the library tolerates such absence instead of erroring.
- The panic points (`enc_keys[&participant]`, `commitments[&l]`, `commitments[&sender]`, `enc_keys[&decryptor]`) are HashMap indexing operators — no graceful `None` handling exists.
- No secret material is required by the attacker; withholding a message or choosing an index suffices. The trigger executes on every honest node's secret-share generation, making a single non-sending participant sufficient to fail the ceremony for everyone.
- Caveat: whether `validate_map` (invoked at lib.rs:305 and lib.rs:468) rejects maps missing expected participants could not be fully verified from the indexed excerpt; if it enforces exact membership, the r1/r2 paths reduce to the blame-indexing variant, which remains reachable via unbounded `sender`/`recipient` parameters.

### Recommendation
- In `verify_r1`, error (`PedPoPError::MissingParticipant`) when `commitment_msgs.remove(&l)` returns `None` rather than `continue`, or record skipped participants and exclude them from `all_participant_indexes()` iteration in `generate_secret_shares`/`calculate_share`.
- Replace `enc_keys[&participant]` / `commitments[&l]` indexing with `.get()` + an explicit `InvalidParticipant`/`MissingParticipant` error, matching the "check `chan->local != NULL` before unregistering" fix upstream.
- In `BlameMachine::blame` / `AdditionalBlameMachine::blame`, validate `sender` and `recipient` against `params.n()` / `enc_keys.contains_key` before calling `decrypt_with_proof`/`blame_internal`, returning a defined error instead of panicking — mirroring the conditional guard added to `__dma_async_device_channel_unregister()`.
