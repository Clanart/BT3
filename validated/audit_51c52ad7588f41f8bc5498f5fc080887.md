### Title
`InternalSendTx` is a fully unauthenticated broadcasting call when `client_verification=false` - ([File: core/src/rpc/interceptors.rs])

### Summary
When the aggregator is deployed with `client_verification=false`, `create_grpc_server` (`core/src/servers.rs`) omits `client_ca_root` from the TLS config and selects `Interceptors::Noop`, which unconditionally forwards every request without ever calling `is_internal`/`only_aggregator_and_self`. This makes `ClementineAggregator/InternalSendTx` (`core/src/rpc/aggregator.rs`) reachable by anyone who can open a TCP connection to the aggregator's port, with no certificate, no `grpc-method` check, and no additional authorization inside the handler itself.

### Finding Description
The claimed binding is: `caller reaching an "Internal"-prefixed method == leaf_cert == our_cert`. Tracing the code shows this binding is only enforced by `only_aggregator_and_self`, which is never invoked under `Interceptors::Noop`: [1](#0-0) 

`create_grpc_server` selects `Noop` and simultaneously drops mTLS client-certificate validation entirely when `client_verification` is false: [2](#0-1) 

`internal_send_tx` performs no caller-identity check of its own; it parses the attacker-supplied `raw_tx`/`fee_type` and unconditionally forwards it to `tx_sender.insert_try_to_send`: [3](#0-2) 

So under `client_verification=false`, any network peer that can reach the aggregator's gRPC port can call `InternalSendTx` with an arbitrary `raw_tx` and have the aggregator queue/broadcast it via `TxSender`, with zero authentication of any kind (no TLS client cert, no `grpc-method` gate).

However, tracing further shows the "double-spend a Reimburse/Challenge input" impact claimed in the prompt does not follow: `insert_try_to_send` only queues/(re)broadcasts a transaction the caller already supplies fully signed. Bridge UTXOs that fund Reimburse/Challenge transactions are protected by N-of-N MuSig2 signatures or covenant script paths that the unprivileged attacker (no key share, no verifier/operator role) cannot produce. The attacker cannot forge a conflicting spend of the same protected outpoint because they cannot produce a valid signature/witness for it; `internal_send_tx` gives them a relay, not a signing oracle. Existing guards (the N-of-N presigned transaction graph, MuSig2 aggregation, and Bitcoin consensus validation of the raw tx before it can be mined) still prevent an attacker-authored transaction from validly spending a bridge-protected outpoint. Therefore no fund theft, unreimbursable payout, or burned collateral is demonstrated by this path — the Critical scope in the prompt is not substantiated.

What remains substantiated is the authentication bypass itself: `InternalSendTx` (and every other RPC on the aggregator server, including internal-prefixed ones) becomes fully unauthenticated call surface when `client_verification=false`, which matches the rubric's High-severity category "an unauthenticated state-changing or broadcasting call" independent of any demonstrated double-spend.

### Impact Explanation
Under `client_verification=false`, an unprivileged network peer can invoke a state-changing/broadcasting RPC (`InternalSendTx`) with no authentication, letting them insert arbitrary transactions into the aggregator's `TxSender` queue/broadcast pipeline. This does not, by itself, let the attacker steal bridge funds, forge an N-of-N signature, or double-spend a protected Reimburse/Challenge input, since those still require signatures the attacker cannot produce. The demonstrated impact is limited to the unauthenticated-call category (High), not fund loss (Critical).

### Likelihood Explanation
Requires the deployment to run the aggregator with `client_verification=false` — this is a real, code-supported configuration path (not merely test-only), toggled via the `CLIENT_VERIFICATION` env var / config field, and it also disables `client_ca_root`, so even standard mTLS is skipped. Given this configuration, exploitation costs the attacker nothing but a TCP connection to the aggregator's public gRPC port.

### Recommendation
Do not treat `client_verification=false` as a safe "no extra internal-method restriction" mode — it should still require baseline mTLS via `client_ca_root`, and `is_internal`-gated methods (or at minimum, mutating RPCs like `InternalSendTx`) should never be reachable without verifying the caller is the aggregator or the entity's own certificate, regardless of `client_verification`. Consider always applying `client_ca_root` and only relaxing the aggregator/self identity check under `Noop`, rather than skipping both mTLS and identity checks together.

### Proof of Concept
Not applicable as a Critical/High fund-loss PoC: a `cargo test` demonstrating a successful double-spend of a Reimburse/Challenge input via unauthenticated `internal_send_tx` cannot be constructed, because the attacker cannot produce the required N-of-N/covenant signature for that outpoint. A PoC can only demonstrate the unauthenticated-call primitive itself (connecting to an aggregator started with `client_verification=false` and successfully invoking `InternalSendTx` without any TLS client certificate), which corresponds to High, not Critical, severity.

                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
