### Title
Unbounded growth of tombstone entries in the global `ProgramCache` index - (File: `program-runtime/src/loaded_programs.rs`)

### Summary
An unprivileged user can permanently grow the validator-global `ProgramCache::index` (`IndexImplementation::V1 { entries: HashMap<Pubkey, Vec<Arc<ProgramCacheEntry>>> }`) by repeatedly creating cheap accounts owned by a BPF loader that do not contain valid program data, and referencing them as an instruction's `program_id`. Each such reference inserts a permanent tombstone entry keyed by that unique `Pubkey`, and unlike the `delegated[]` mapping bug this is analogous to — the eviction machinery in `ProgramCache` only ever unloads `Loaded` entries, never tombstones, so these entries are never removed from the top-level index.

### Finding Description
`filter_executable_program_accounts` builds the list of programs to load for a transaction batch by accepting *any* account owned by `bpf_loader`, `bpf_loader_deprecated`, `bpf_loader_upgradeable`, or `loader_v4` — with no requirement that the account actually contains a valid, executable program [1](#0-0) .

`load_program_with_pubkey` then attempts to parse the account. If the data is not a valid program (e.g. a `Buffer`/`Uninitialized`/`ProgramData` state instead of `Program`, or a v4 program that is `Retracted`), it produces `ProgramAccountLoadResult::InvalidAccountData`, which becomes a permanent `ProgramCacheEntry::new_tombstone(..., ProgramCacheEntryType::Closed)` [3](#0-2) . Similarly, actually deploying then closing a LoaderV3 program stores a `Closed` tombstone via `store_modified_entry`/`assign_program` [4](#0-3) .

This tombstone is inserted into `ProgramCache::index` keyed by the account's `Pubkey` via `assign_program`/`finish_cooperative_loading_task`, growing the `entries` `HashMap` by one new key per unique spam `Pubkey` [5](#0-4) .

Critically, the cache's eviction routines (`sort_and_unload`, `evict_using_random_selection`) call `unload_program_entry`, which **only downgrades `Loaded` entries to `Unloaded`** — it explicitly does nothing for tombstones (`Closed`/`FailedVerification`/`DelayVisibility`) [6](#0-5) . The only path that can remove a program's key entirely from `entries` is `remove_programs_with_no_entries`, which is only triggered when a program's `second_level` `Vec` becomes fully empty [7](#0-6) . But `prune()` — invoked on every rerooting via `Bank::prune_program_cache` [8](#0-7)  — always retains at least one "first ancestor" entry per program's `second_level` when the fork relationship indicates the entry is an ancestor of the new root [9](#0-8) , so `second_level` never becomes empty for spammed tombstones on the canonical fork, and the key is never removed.

Meanwhile, `prune()` fully iterates `entries.values_mut()` — i.e. **every** cached program, including every spammed tombstone — on every root advance [10](#0-9) . Growing the cache's key count therefore directly and permanently increases the cost of this per-rerooting maintenance pass, run by every validator on the network.

### Impact Explanation
This is directly analogous to the `delegated[]` bug: a value/state that should logically be dropped once it is no longer "live" (an account that never became, or is no longer, a real program) is instead kept forever, in a structure that every validator must periodically process in full (`prune()`), scaling with the number of distinct spam `Pubkey`s ever referenced as a `program_id`. Unlike `delegated[]`'s per-transaction cost, here the cost hit is per-rerooting (which happens routinely, roughly once per confirmed/rooted slot), but it still causes an ever-growing, permanent, and unrecoverable increase in validator CPU/memory overhead driven entirely by cheap, unprivileged, and repeatable user action — a materially underpriced compute/DoS class issue matching the acceptance criteria.

### Likelihood Explanation
Likelihood is high in principle: creating an account owned by `bpf_loader_upgradeable` in an invalid state (e.g. leaving it `Uninitialized`, or a `Buffer` never turned into a `Program`) is cheap (bounded by rent-exemption for a small account, recoverable by closing), and referencing it as an instruction's `program_id` only requires the account to be owned by a loader — sanitization does not require the account be executable/valid before this path runs the load attempt [11](#0-10) [1](#0-0) . Each unique account produces one permanent tombstone. The main unresolved uncertainty (not verifiable from the indexed code alone) is the exact magnitude of per-rerooting cost increase at scale, and whether any additional bound (e.g. `ProgramCache::hit_max_limit`, `MAX_LOADED_ENTRY_COUNT` mentioned in tests) caps total entries versus only compiled/`Loaded` entries — the evidence found strongly suggests such limits apply only to `Loaded`/compiled entries, not tombstones, but this could not be fully confirmed from the available snippets.

### Recommendation
Extend `remove_programs_with_no_entries`/`prune()` (or add a dedicated tombstone-eviction pass) so that stale `Closed`/`FailedVerification` tombstones for programs that are provably not live on any tracked fork are dropped from `entries` once they are older than `latest_root_slot` by some margin, rather than always retaining one "first ancestor" entry indefinitely. Alternatively, bound `entries.len()` directly (independent of the `Loaded`-entry water-level accounting) and reject/evict the oldest tombstones once a cap is hit.

### Proof of Concept
Conceptually (mirrors the confirmed code paths, not run against a live validator):
1. Use the System Program to create many small accounts and assign each to `bpf_loader_upgradeable::id()`, leaving them `Uninitialized` (cheap, rent-exempt, recoverable).
2. Submit transactions where each such account is passed as the instruction's `program_id`.
3. `filter_executable_program_accounts` treats each as `ProgramCacheEntryOwner::LoaderV3` and queues it for loading [12](#0-11) ; `load_program_with_pubkey` returns `InvalidAccountData` → `Closed` tombstone [3](#0-2) , permanently inserted into `ProgramCache::index` for that unique key.
4. Repeat with N distinct pubkeys to grow `entries` by N permanent, never-evicted keys, each subsequently scanned in full on every `prune()` call at rerooting.
