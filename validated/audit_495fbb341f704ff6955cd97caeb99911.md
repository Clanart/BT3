### Title
Cloning disables Git's submodule symlink/hook protection while GitHub Desktop auto-executes discovered repo hooks - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and passes `--recursive` on every clone [1](#0-0) . `GIT_CLONE_PROTECTION_ACTIVE` is the Git-internal flag that gates Git's clone-time symlink/case-collision protection for submodules (the class of hardening added upstream after the submodule-hooks planting attacks, e.g. CVE‑2024‑32002‑style issues where a malicious `.gitmodules`/submodule layout can place files inside `.git/hooks` of the checkout during a recursive clone). Explicitly disabling this guard for every Desktop-initiated clone, combined with Desktop's newer "run Git hooks automatically" feature (enabled by default, per `enableHooksByDefault`/`getHooksEnvEnabled`) [2](#0-1) , creates a path where an attacker-controlled repository can plant an executable hook that Desktop will detect and run on the very next commit/push/pull/merge.

### Finding Description
`clone()` builds its environment as:
```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
``` [1](#0-0) 

`--recursive` causes Git to recurse into any submodules declared by the remote repository's `.gitmodules`, and `GIT_CLONE_PROTECTION_ACTIVE=false` turns off the safety checks Git normally performs during that recursive clone to prevent a submodule from writing outside its own worktree (e.g. via crafted symlinked/case-colliding paths that resolve into the top-level `.git/hooks` directory). There is no comment in this codebase explaining the rationale for forcing this flag off, and it is applied to every clone unconditionally, not only Desktop's own internal/recursive sub-invocations.

Independently of clone, GitHub Desktop ships a hooks-execution feature that is enabled by default:
- `enableHooksByDefault` / `getHooksEnvEnabled()` gate whether Desktop intercepts and runs hooks [2](#0-1) , and `enableHooksEnvironment` is hardcoded `true` [3](#0-2) .
- Every commit, push, pull, and merge operation passes `interceptHooks` for the corresponding hook names to `git()` [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) .
- `withHooksEnv()` calls `getRepoHooks()`, which scans the resolved `core.hooksPath` (or default `.git/hooks`) for executable files matching known hook names, with no ownership/trust or origin check on those files [8](#0-7) .
- If any are found, `createHooksProxy()` actually spawns them using the user's real shell environment (`getShellEnv`) and grants them `GIT_*`/`GITHEAD_*` variables (minus a small excluded list) [9](#0-8) .

So a hook file that ends up under `.git/hooks` immediately after clone (through the disabled submodule protection) will be executed automatically the first time the user commits, pushes, pulls, or merges in that repository — all normal, expected Desktop actions performed on a freshly cloned repository — with no confirmation dialog specific to "this repository contains a hook that wasn't there before" and no re-application of Git's directory-ownership "unsafe repository" check (that check only fires for pre-existing directories being *added*, not for a repo that Desktop itself just cloned and therefore owns).

### Impact Explanation
If exploitable, this results in arbitrary code execution under the victim's own user account immediately after cloning an attacker-supplied repository URL — no local/physical access, no leaked credentials, and no unusual user action beyond the normal "Clone" + first "Commit/Push/Pull" workflow that Desktop actively encourages. This matches the accepted impact class: an attacker-controlled cloned/fetched repository leading to code execution.

### Likelihood Explanation
Likelihood cannot be fully confirmed from static code review alone: exploitation depends on whether the specific Git version vendored by Desktop (via dugite) still requires `GIT_CLONE_PROTECTION_ACTIVE=true` to reject the symlink/case-collision submodule payload, and on OS/filesystem specifics (case-insensitivity, symlink support) that determine whether such a payload can actually place a file under `.git/hooks`. I could not find any code comment, test, or changelog entry in this repository explaining why `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, nor any regression test exercising this specific combination with the hooks feature. This is a gap in the available index/coverage that a hands-on Devin session (with access to the vendored Git binary and the ability to run a PoC clone) would need to close to move this from "plausible chain via local code evidence" to "confirmed exploit."

### Recommendation
- Do not disable `GIT_CLONE_PROTECTION_ACTIVE` for user-initiated clones; only allow Git's own internal recursive-submodule invocation to manage that flag, or explicitly pass `true`/leave it unset so Git's built-in protections remain active.
- Before enabling hook execution (`getHooksEnvEnabled`) for a repository, verify the hook files were not introduced by content fetched from a remote (e.g., diff hook-directory contents against a pre-clone snapshot, or require the same ownership/trust confirmation flow used for "unsafe" repositories) rather than trusting anything present in `core.hooksPath` immediately after a clone.
- Add regression tests that attempt to clone a crafted repository containing a submodule designed to write into `.git/hooks` (mirroring the upstream CVE‑2024‑32002 test vectors) and assert that no such file is created and/or executed.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to lack of a live Git binary/test harness in this review):
1. Attacker hosts a Git repository containing a `.gitmodules` entry whose submodule path is crafted (via symlink or case-collision, depending on target OS/filesystem) to resolve outside the submodule's own worktree and into the parent repository's `.git/hooks` directory, planting an executable `pre-commit` (or `post-checkout`) script — the same technique Git's clone-time protections (gated by `GIT_CLONE_PROTECTION_ACTIVE`) were introduced to block.
2. Victim uses GitHub Desktop's "Clone a repository" flow with the attacker's URL. Desktop calls `clone()`, which runs `git ... clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` [1](#0-0) , disabling the guard that would otherwise reject the crafted submodule layout.
3. Victim makes any commit, push, pull, or merge in the newly cloned repository (a completely ordinary next step). Desktop's `withHooksEnv`/`getRepoHooks` detects the planted executable hook file [8](#0-7)  and `createHooksProxy` executes it with the user's shell environment [9](#0-8) , achieving code execution as the victim user.

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
}
```
