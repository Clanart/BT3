### Title
`ManualCompound.compound` sweeps the contract's entire token balance to `msg.sender` instead of only the caller's claimed rewards - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` is a fully unpermissioned, externally callable function. After triggering `multiclaimOnBehalf`, it distributes rewards to `msg.sender` based on `IERC20(token).balanceOf(address(this))` rather than on the amount actually claimed on behalf of the caller in that transaction, letting any wallet drain whatever ERC20 balance the contract happens to be holding.

### Finding Description
`compound()` is declared with no access control or ownership check and can be called by any address with arbitrary `_lps`/`_rewards` arguments: [1](#0-0) 

Two separate loops then move funds out of the contract using the contract's *total current balance*, not a per-caller delta:

1. The "non-compoundable reward" loop reads `IERC20(_rewards[i][j]).balanceOf(address(this))` for any token address the caller supplies and transfers the full balance to `msg.sender`, without verifying that this balance corresponds to rewards actually claimed for that caller in this call: [2](#0-1) 

2. The "compoundable reward" loop unconditionally iterates over every registered `Reward` in state (independent of what `_lps`/`_rewards` the caller passed) and forwards `IERC20(_tokenAddress).balanceOf(address(this))` to `msg.sender`, again using the raw contract balance rather than a tracked, caller-specific amount: [3](#0-2) 

Because `multiclaimOnBehalf` only credits rewards proportional to the caller's own stake in `MasterMagpie` (see the `_onlyCompounder`-gated `multiclaimOnBehalf` in `MasterMagpie.sol`), a caller with zero stake (or an empty `_lps`/`_rewards` array) triggers no real claim at all: [4](#0-3) 

Yet the subsequent balance-based sweep still executes and pays out **whatever tokens are already sitting in the `ManualCompound` contract** — e.g., rounding dust left over from `IConverter.convertFor`/`ILocker.lockFor`/`ISimpleHelper.depositFor` not consuming 100% of `receivedBalance`, or tokens mistakenly/temporarily present in the contract — to the caller, exactly mirroring the reported bug class where an unpermissioned function moves pooled funds and pays them to `msg.sender` instead of crediting only what that caller is entitled to.

### Impact Explanation
Any address can call `compound()` with empty or unrelated `_lps`/`_rewards` arrays and no prior deposit, and receive the full balance of every registered compoundable reward token (and any arbitrary token address it names that is marked non-compoundable) currently held by the contract. This is a direct theft of funds that do not belong to the caller — dust/leftover balances accumulated from legitimate users' prior `compound()` calls (integer-division rounding in `convertFor`) are diverted to the first opportunistic caller rather than remaining available or being distributed proportionally.

### Likelihood Explanation
`compound()` requires no special role, deposit, or prior interaction — it is reachable directly by an ordinary wallet transaction and the balance-based sweep pattern executes unconditionally on every call, so any accrued dust or stray balance can be swept immediately by watching the contract's token balances.

### Recommendation
Do not use `balanceOf(address(this))` as the distribution amount. Track and transfer only the delta actually received for the specific caller in the current transaction (e.g., snapshot balances before `multiclaimOnBehalf` and only forward `after - before` for that call), and restrict the "non-compoundable" sweep loop to only reward tokens that were genuinely part of the caller's own claim in `_rewards`.

### Proof of Concept
1. Attacker (with no stake in `MasterMagpie` and no prior deposits anywhere) calls `ManualCompound.compound([], [], 0, 0, false)`.
2. `multiclaimOnBehalf([], [], attacker)` performs no claim (zero-length arrays), see [4](#0-3) .
3. The second loop in `compound()` still iterates over all registered `rewards` and reads `IERC20(_tokenAddress).balanceOf(address(this))` for each, sending any non-zero balance to `attacker` via `safeTransfer`, see [3](#0-2) .
4. Any residual balance sitting in the contract (e.g., rounding remainder from a previous legitimate user's `IConverter.convertFor` call) is transferred entirely to the attacker at zero cost.
