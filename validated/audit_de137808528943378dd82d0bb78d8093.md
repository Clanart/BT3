This confirms the finding. Comparing the two contracts side by side:

`vlMGPBaseRewarder._calExpireForfeit` (the reference/correct pattern) at [1](#0-0)  computes `rewardablePercentWAD` via `vlMGP.getRewardablePercentWAD(_account)` and scales `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`.

`mWOMSVBaseRewarder._calExpireForfeit`, however, never calls `mWOMSV.getRewardablePercentWAD(_account)` at all — it just sets `rewardableAmount = _amount` unconditionally: [2](#0-1)  This means `forfeitAmount` always evaluates to `_amount - _amount = 0`, regardless of the caller's lock/cooldown state.

The `mWomSV.getRewardablePercentWAD` function does exist and is fully implemented in `mWomSV.sol`, computing a percentage based on `fullyInLock`, `inCoolDown`, and unlock timing: [3](#0-2)  — it's just never wired up to the rewarder's forfeiture calculation, unlike the `vlMGP`/`vlMGPBaseRewarder` pair.

The call path is unrestricted for any depositor: `getReward`/`getRewards` are only gated by `onlyMasterMagpie` (i.e., routed through `MasterMagpie`, which any staker can invoke via a claim call), not by any special role: [4](#0-3) . `_sendReward` invokes `_calExpireForfeit`, which is the broken function: [5](#0-4) .

### Title
Missing rewardable-percent scaling in `mWOMSVBaseRewarder._calExpireForfeit` allows full reward claim during partial unlock/cooldown, bypassing forfeiture - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` fails to call `mWOMSV.getRewardablePercentWAD(_account)` and instead always treats the full pending reward amount as rewardable, unlike the equivalent `vlMGPBaseRewarder._calExpireForfeit` which properly scales by the account's rewardable percentage. Any `mWomSV` holder who has started `startUnlock()` (partially or fully) can still claim 100% of their pending bonus rewards via `getReward()`/`getRewards()` with zero forfeiture, even while their position is mid-cooldown and should be penalized.

### Finding Description
The forfeiture mechanism is meant to reduce/eliminate reward eligibility for tokens that are mid-cooldown or unlocked (not fully locked), proportional to `getRewardablePercentWAD`. In `vlMGPBaseRewarder.sol`, `_calExpireForfeit` correctly fetches this percent and scales the rewardable amount:
```solidity
uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
```
In `mWOMSVBaseRewarder.sol`, the analogous function omits this entirely:
```solidity
uint256 rewardableAmount = _amount;
if (rewardableAmount > _amount) revert InvalidRewardableAmount(); // dead code, always false
uint256 forfeitAmount = _amount - rewardableAmount; // always 0
```
Since `rewardableAmount` is hardcoded to `_amount`, `forfeitAmount` is always `0`, and the `if (forfeitAmount < _amount/1000)` dust-ignoring branch is unreachable in any meaningful way (it always sets `forfeitAmount=0` redundantly). `mWOMSV.getRewardablePercentWAD` exists and is correctly implemented in `mWomSV.sol` but is simply never referenced by `mWOMSVBaseRewarder`, indicating a wiring omission rather than a design choice, since the sibling `vlMGP` system correctly performs the same operation.

Any attacker who is a normal `mWomSV` locker can call `mWomSV.startUnlock()` to move some or all of their locked balance into cooldown (reducing their `getRewardablePercentWAD` below `1e18`), then call `getReward()`/`getRewards()` on `MasterMagpie` (routed to `onlyMasterMagpie`-gated functions in the rewarder) to claim their full accrued bonus rewards with no forfeiture, when a fraction should have been redirected to other lockers via `_queueNewRewardsWithoutTransfer`.

### Impact Explanation
This is a theft/misallocation of unclaimed yield: rewards intended to be forfeited from partially/fully unlocking positions (and redistributed pro-rata to remaining full lockers via `_queueNewRewardsWithoutTransfer`) are instead paid out in full to the unlocking user. This directly reduces the yield available to honest full lockers and lets any cooling-down/unlocking holder capture 100% of rewards they are not economically entitled to, matching the "theft of unclaimed yield that should have been forfeited to other lockers" impact class.

### Likelihood Explanation
- Preconditions: attacker only needs to hold `mWomSV` (obtained by locking `mWOM`, a normal permissionless action) and have some pending bonus rewards accrued in `mWOMSVBaseRewarder`.
- No privileged role, flash loan, or governance action required.
- Trivially repeatable by every user, every time they call `startUnlock()`/`unlock()` and then claim, so it is not a one-off edge case but the default broken behavior of the entire forfeiture feature for this pool type.
- Capital needed is just the amount already locked; no capital outlay beyond normal usage.

### Recommendation
Mirror the `vlMGPBaseRewarder` pattern in `mWOMSVBaseRewarder._calExpireForfeit`: fetch `uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);` and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18;` before deriving `forfeitAmount`, so that partially-unlocked/cooling-down positions correctly forfeit a proportional share of rewards.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder` with a reward token.
2. Two users, A and B, each lock 100 `mWOM` into `mWomSV`; `queueNewRewards` adds bonus reward tokens so both accrue pending rewards.
3. User A calls `mWomSV.startUnlock(100e18)` (100% of their lock) to enter cooldown, without waiting for cooldown to finish.
4. Immediately (or partway through cooldown), user A triggers `getReward()` via `MasterMagpie` (or directly if test harness allows call as `masterMagpie`).
5. Assert: `mWOMSV.getRewardablePercentWAD(A) < 1e18` (confirms partial/zero eligibility expected).
6. Assert: reward token balance transferred to A equals the full `earned(A, rewardToken)` amount computed before the claim, and `forfeitAmount == 0` (via inspecting `_sendReward`/`calExpireForfeit(A, rewardToken)` returning 0), proving no forfeiture occurred despite A's cooldown status.
7. Compare against `vlMGPBaseRewarder` with an analogous scenario using `vlMGP`, where `forfeitAmount > 0` is correctly computed, showing the divergence is a bug rather than intended behavior.

        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
