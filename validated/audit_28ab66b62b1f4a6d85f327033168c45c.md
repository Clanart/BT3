### Title
Unauthenticated `harvest()` combined with instantaneous, non-time-weighted `rewardPerTokenStored` update allows flash-deposit theft of accrued yield - ([File: wombat/WombatStaking.sol], [File: rewards/BaseRewardPoolV2.sol])

### Summary
`WombatPoolHelper(V2)/AnkrBNBPoolHelper.harvest()` calls `IWombatStaking.harvest(lpToken)`, which is gated only by `_onlyActivePool` (no caller restriction), so any address can trigger it at will. `harvest()` invokes `_toMasterWomAndSendReward` → `_sendRewards` → `IBaseRewardPool.queueNewRewards`, which immediately bumps `rewardPerTokenStored` by `amount * 1e18 / totalStaked()` using the *instantaneous* `totalStaked()`/`balanceOf()` (live MasterMagpie balances), with no time-weighting, streaming, or vesting of the newly harvested reward.

### Finding Description
The reward math in `BaseRewardPoolV2._provisionReward` (and the analogous `BaseRewardPool`, `mWOMSVBaseRewarder`, `vlMGPBaseRewarder`) is: [1](#0-0) 
`rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()`, where `totalStaked()` reads the live balance at that block: [2](#0-1) 

A user's claimable amount is `earned = balanceOf(user) * (rewardPerToken - userRewardPerTokenPaid) + userRewards`, and `userRewardPerTokenPaid` is only refreshed on state-changing actions (`updateReward`/`updateRewards` modifiers) such as deposit/withdraw: [3](#0-2) [4](#0-3) 

Because the reward bump is applied instantly and pro-rata to whoever is staked *at the moment `harvest()` executes* (not time-weighted since the last harvest), the exploit path is:
1. Attacker calls `WombatPoolHelper.depositLP(amount)` → `WombatStaking.depositLP` → receipt token minted and staked into MasterMagpie, increasing `totalStaked()` and setting attacker's `userRewardPerTokenPaid` to the pre-harvest rate.
2. Attacker (or anyone) calls `WombatPoolHelper.harvest()` → `WombatStaking.harvest(lpToken)`, gated only by `_onlyActivePool`, not by `_onlyActivePoolHelper` or any staker/owner check: [5](#0-4) 
This triggers `_toMasterWomAndSendReward`, which withdraws/redeposits into MasterWombat to force a WOM harvest and forwards the entire accrued WOM (accumulated since the *last* harvest of that pool, i.e., attributable to all prior long-term stakers) into `_sendRewards` → `queueNewRewards`: [6](#0-5) [7](#0-6) 
3. `rewardPerTokenStored` jumps based on the amount harvested divided by the current `totalStaked()`, which now includes the attacker's freshly deposited balance.
4. Attacker calls `withdraw()` (or `getReward` via MasterMagpie), which runs `updateReward`/`updateFor` before reducing balance, locking in `userRewards[attacker] = balanceOf(attacker) * (new rate - old paid rate)` — a full pro-rata share of the just-harvested batch despite only having been staked for 1–2 blocks.

Existing modifiers (`nonReentrant`, `whenNotPaused`, `_onlyActivePoolHelper`/`_onlyPoolHelper` on `deposit`/`withdraw`) do not prevent this because they only gate custody/authorization of pool helpers, not time-weighting of reward accrual. There is no minimum staking duration, no linear reward streaming (e.g., a `rewardRate`/`periodFinish` mechanism like Synthetix `StakingRewards`), and no snapshot/checkpoint mechanism tying the harvested WOM to the stakers who actually earned it over the epoch.

### Impact Explanation
This is a theft-of-unclaimed-yield vulnerability: an attacker with no privileges can front-run a harvest with a deposit and back-run it with a withdrawal to capture a portion of yield that accrued to long-term stakers over the entire interval since the pool was last harvested, diluting/stealing their rightful proportional share. The magnitude scales with the size of the attacker's flash/temporary deposit relative to `totalStaked()`; a well-capitalized or flash-loan-funded attacker (if the underlying LP/receipt tokens can be sourced via flash loan and re-deposited/withdrawn same block, subject to any withdrawal delay constraints such as `unlockTime` checks in `AnkrBNBPoolHelper`) can capture a disproportionately large share of a single harvest batch.

### Likelihood Explanation
`harvest()` is completely permissionless (`_onlyActivePool` only checks the pool is registered/active, not caller identity), so any EOA can trigger it at will and combine it with their own deposit/withdraw in adjacent transactions or the same block. No special capital is required beyond enough LP tokens to make the attack profitable relative to gas costs; the attack is trivially repeatable every time meaningful pending WOM/bonus rewards have accrued in MasterWombat.

### Recommendation
Introduce time-weighted reward accounting instead of instantaneous pro-rata distribution — e.g., stream newly queued rewards linearly over a fixed duration (Synthetix-style `rewardRate`/`periodFinish`) rather than applying the full `rewardPerTokenStored` bump atomically at harvest time. Alternatively/additionally, require a minimum staking duration before a deposit's balance is eligible for reward-per-token accrual, or checkpoint `totalStaked()` prior to the harvested amount being deposited in the same transaction so freshly deposited balances in the harvesting block are excluded from that specific reward bump.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatStaking`, `BaseRewardPoolV2` (or `WombatPoolHelperV2`), `MasterMagpie`, mock WOM/MasterWombat.
2. Long-term staker A deposits LP and remains staked for N blocks while WOM accrues in MasterWombat (simulate via mock `pendingTokens`/`harvest`).
3. Attacker B calls `depositLP(smallAmount)` at block N (1 block before intended harvest).
4. Attacker B calls `WombatPoolHelperV2.harvest()` — confirm no revert/permission check blocks this call from a non-owner, non-poolHelper EOA.
5. Assert `rewardPerTokenStored` for WOM jumps in the same transaction as harvest, proportional to `(B.balance)/(A.balance + B.balance)`.
6. Attacker B calls `withdraw(smallAmount, 0)` immediately after (block N+1), then claims via MasterMagpie `claim`/`getReward`.
7. Assert: `B`'s realized WOM reward / `B`'s staking duration (2 blocks) ≫ `A`'s realized WOM reward / `A`'s staking duration (N blocks), demonstrating disproportionate yield capture violating pro-rata-to-duration conservation.
