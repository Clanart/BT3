### Title
Permissionless native-ERC20 registration lets an attacker mint unbacked native Cosmos coins because the escrow "invariant" check trusts attacker-controlled `balanceOf`/`transfer` bytecode - ([File: x/erc20/keeper/msg_server.go])

### Summary
The 1inch UniERC20 report's real risk is trusting attacker-controlled external code (`.call()`/`transfer()` targets) to behave honestly at a point where accounting decisions are made. Cosmos EVM has a structural analog: `x/erc20`'s `ConvertERC20` flow escrows tokens by calling into the registered ERC20 contract itself (`transfer` and `balanceOf`), and then trusts that same contract's return values to validate the escrow before minting native coins. Because `MsgRegisterERC20` is permissionless by default (`PermissionlessRegistration: true`), any unprivileged user can register their own malicious contract as a "native ERC20" token pair and make its `transfer`/`balanceOf` implementations return whatever they want, defeating the balance-invariance check and letting the attacker mint arbitrary native Cosmos coins with no real value ever escrowed.

### Finding Description
`RegisterERC20` in [1](#0-0)  allows any signer to register an ERC20 contract as a token pair without governance approval when `PermissionlessRegistration` is true, which is the default value: [2](#0-1) .

`registerERC20` performs no bytecode/behavior validation of the contract beyond ensuring it hasn't been registered before and reading its metadata: [3](#0-2) .

When the attacker calls `MsgConvertERC20`, `convertERC20IntoCoinsForNativeToken` executes:
1. Reads `balanceToken` via `k.BalanceOf` — calling the attacker's own contract code.
2. Calls `contract.transfer(ModuleAddress, amount)` via `k.evmKeeper.CallEVMWithData` — again executing attacker-controlled code.
3. Re-reads the module's balance via the attacker's own `balanceOf` and compares it against the expected increase.
4. If it matches, mints and sends real native Cosmos coins to the receiver. [4](#0-3) 

Since both the `transfer` execution and the `balanceOf` "invariant" read are calls into the same attacker-deployed contract, the attacker fully controls both sides of the check. A malicious contract can implement `transfer()` as a no-op that returns `true` and `balanceOf()` as a function that simply increments a counter by `amount` on every call, satisfying the `ErrBalanceInvariance` check in [5](#0-4)  without ever locking real value. The subsequent `MintCoins` + `SendCoinsFromModuleToAccount` then creates real, spendable native Cosmos coin balance for the attacker: [6](#0-5) .

This is the same underlying flaw class as UniERC20's re-entrancy risk — delegating a security-relevant invariant check to code the caller does not control-and-trust, at a point in execution where that code can arbitrarily manipulate outcomes — except here the untrusted code is invoked synchronously by the module itself rather than being reentered by the caller, and the "invariant" is defeated by having full control of both legs of the check rather than by classic reentrancy/state-inconsistency.

### Impact Explanation
This allows an unprivileged user to mint unlimited amounts of a native Cosmos coin (`erc20/<contract_address>` denom) backed by zero real escrowed value, then transfer or IBC that coin anywhere. This is unauthorized minting / accounting corruption of spendable user value on native balances, satisfying the Critical "unauthorized minting... irreversible accounting corruption of spendable user value across native balances... token-pair-backed balances" impact.

### Likelihood Explanation
High. `PermissionlessRegistration` defaults to `true`, requiring no governance action, so any address can deploy a trivial malicious Solidity contract and register it as a token pair, then call `ConvertERC20` to mint coins — no privileged role, relayer, or validator collusion is required.

### Recommendation
- Do not rely on a token-controlled `balanceOf` (or any attacker-supplied contract logic) as the sole invariant for accounting decisions; instead track escrowed balances internally in module state (e.g., record pre-registration supply/decimals and use module-tracked delta accounting), or restrict native-ERC20 registration/backing verification to contracts matching a known, audited bytecode template (as is intended for "native ERC20" pairs deployed by the module itself vs. externally-owned contracts).
- If permissionless registration of externally-owned ERC20 contracts must remain supported, ensure `ConvertERC20`/`ConvertCoin` never trust the registered contract's own `balanceOf`/`transfer` return data as proof of escrow; verify against emitted `Transfer` event data validated independently, and treat unverifiable/inconsistent event data as a hard failure rather than a soft invariant check.
- Consider disabling `PermissionlessRegistration` by default or gating externally-owned contract conversion mint amounts by additional caps/timelocks reviewable by governance.

### Proof of Concept
1. Deploy a malicious ERC20-like contract `Fake` with:
   - `transfer(address,uint256) returns (bool)` that does nothing and returns `true`.
   - `balanceOf(address account) returns (uint256)` that returns a value equal to "previously reported balance + last requested transfer amount" (tracked via a local mapping incremented on each `transfer` call), so the invariant check in step 3 above always passes.
2. Call `MsgRegisterERC20{Signer: attacker, Erc20Addresses: [Fake]}` — succeeds because `PermissionlessRegistration` is true (`x/erc20/keeper/msg_server.go:324-335`).
3. Call `MsgConvertERC20{ContractAddress: Fake, Amount: X, Sender: attacker, Receiver: attacker}`.
4. `convertERC20IntoCoinsForNativeToken` calls `Fake.transfer(module, X)` (no-op, returns true), reads `Fake.balanceOf(module)` (attacker-controlled, satisfies invariant), then executes `bankKeeper.MintCoins` and `SendCoinsFromModuleToAccount` for `X` native coins of denom `erc20/<Fake address>` to the attacker (`x/erc20/keeper/msg_server.go:71-140`).
5. Attacker now holds `X` real, spendable native Cosmos coins with zero real ERC20 backing, transferable/IBC-transferable like any other coin.

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
