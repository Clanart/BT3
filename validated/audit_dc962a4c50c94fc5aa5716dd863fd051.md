### Title
Scanner matches `script_pubkey` by byte equality, so a non-minimal-push encoding of the same P2TR witness program hides deposits from Serai - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Craft bug class is a canonicality mismatch: a check is performed on one representation (`FILTER_VALIDATE_IP` on dotted-decimal strings) while the downstream consumer (`Guzzle`/DNS) accepts an equivalent-but-differently-encoded value (hex IPs). Serai's Bitcoin `Scanner` has the same shape: it registers spendable keys as the minimal `OP_1 <32-byte key>` `ScriptBuf` and detects deposits by `HashMap` lookup on the raw `script_pubkey` bytes. Bitcoin consensus, however, treats any data push of 20–40 bytes after a version opcode as a valid witness program — a `PUSHDATA1`-encoded (non-minimal) push of the same 32-byte key commits to the same key-path spend and is spendable by Serai's group key, but compares unequal as bytes. An unprivileged sender can therefore pay Serai's key in a way the scanner never detects.

### Finding Description
`Scanner` builds its detection table from canonical `ScriptBuf`s: `p2tr_script_buf` emits `ScriptBuf::new_p2tr_tweaked(...)`, which always produces `OP_1 OP_PUSHBYTES_32 <key>` [1](#0-0) . Registration stores these byte-exact scripts as `HashMap` keys [2](#0-1)  and `register_offset` does the same for offset keys [3](#0-2) . Detection is a raw bytewise lookup: `self.scripts.get(&output.script_pubkey)` [4](#0-3) .

Under consensus rules (`CScript::IsWitnessProgram`), the witness program is defined as a version byte followed by a single data push of 2–40 bytes; the program is the *pushed data*, not the opcode used to push it. `OP_1 OP_PUSHDATA1 0x20 <key>` is a consensus-valid v1 witness program identical in effect to `OP_1 OP_PUSHBYTES_32 <key>`: both are key-path spends locked to the same tweaked x-only key under BIP341 (the taproot sighash/commitment depends only on the 32-byte program). The byte sequences differ, so the `HashMap` lookup fails and the output is silently skipped. It is standardness-nonstandard, not consensus-invalid, so a sender (or a cooperative miner) can still get it confirmed.

The same byte-equality assumption is relied on downstream: `Output::key()` parses the script and only requires the last minimal instruction to be a 32-byte push, which the non-minimal form still satisfies — so the scanner would recover the right key *if* it ever matched, but it can't [5](#0-4) . `get_outputs` iterates `scanner.scan_transaction(tx)` and only emits what matched [6](#0-5) .

### Impact Explanation
Any Bitcoin user can craft a deposit to one of Serai's P2TR addresses using a non-minimal push encoding (`OP_1 PUSHDATA1(32) <tweaked key>` instead of `OP_1 PUSHBYTES_32 <key>`). The funds land under Serai's group key and are spendable by it, yet `Scanner::scan_transaction`/`scan_block` never emit a `ReceivedOutput`, so the deposit is never credited and never enters the scheduler. The result is permanently invisible funds: the depositor loses the BTC and Serai's accounting diverges from on-chain reality. This matches the SSRF analog — a security-relevant membership check ("is this output ours") is defeated by an alternative representation the check doesn't normalize.

### Likelihood Explanation
Requires only an unprivileged party constructing a non-standard but consensus-valid transaction; no key material, no validator collusion, no malformed curve points. The barrier is getting a non-standard tx mined (needs a miner or a node policy that accepts it, e.g. via direct miner submission), which is feasible and has precedents on mainnet. Freely triggerable by any depositor who wants their deposit to vanish, or by accident via exotic wallet software.

### Recommendation
Normalize the witness program before lookup instead of comparing raw `ScriptBuf` bytes: in `Scanner::scan_transaction`, parse each `output.script_pubkey` with `is_p2tr()`/witness-program extraction (or `instructions_minimal`) to recover the 32-byte program, and key `self.scripts` by the program bytes (`[u8; 32]`) rather than the full script encoding. Alternatively, additionally test `Script::is_witness_program` + extract the program so non-minimal encodings map to the same key. A regression test should send to `OP_1 OP_PUSHDATA1 0x20 <key>` and assert the output is detected with the correct offset.

### Proof of Concept
1. Let `K` be Serai's even group key (or a registered offset key). Canonical address script: `s = OP_1 || 0x20 || x(K)` as produced by `p2tr_script_buf`.
2. Attacker crafts `s' = OP_1 || OP_PUSHDATA1 || 0x20 || x(K)` (bytes `0x51 0x4c 0x20 <32-byte key>`) and broadcasts a tx paying to `s'` (submitted directly to a miner, since it is non-standard relay-wise).
3. `s'` is a valid v1 witness program committing to the same internal/tweaked key; the output is spendable via key-path signature under Serai's group key plus the registered offset.
4. `Scanner::scan_transaction` executes `self.scripts.get(&output.script_pubkey)` where `s' != s` as `ScriptBuf`, returns `None`, and pushes nothing into `res` [7](#0-6) .
5. `get_outputs` emits no `Output`, so the deposit is never credited even though Serai holds the spending capability — demonstrating the validation-layer/canonical-form bypass.

    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };
