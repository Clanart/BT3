### Title
Missing-proof `unwrap` panic in `GeneratorPromotion::complete` crashes the validator when a participant submits a proof for the wrong index - (crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *quantity* of submitted proofs and that every key is `<= n`, then unconditionally `unwrap`s `proofs.get(&i)` for every expected participant. A proof map that includes the completing node's own index (or any duplicate effective slot) while omitting another participant passes both checks and hits `Option::unwrap` on `None`, panicking the task — analogous to CVE-2019-9706, where an error path during user-data processing (`force_rescan_user`) caused a daemon crash.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two validations on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`:

- `proofs.len() == n - 1` (lines 125-131)
- every key in `proofs` satisfies `u16::from(i) <= params.n()` (lines 132-136)

It then iterates `1 ..= n`, skipping only `params.i()` (the local participant), and indexes the map directly:

```rust
let proof = proofs.get(&i).unwrap();
```

at line 146. Because the checks never verify that the map's keys are exactly the set `{1..=n} \ {i}`, a malicious participant set (or any caller supplying an off-axis key map) can submit `n - 1` proofs where one entry is keyed by the local participant's own index `params.i()` — which passes both validators — while a genuine participant `j` is absent. The loop then reaches `proofs.get(&j)` which returns `None`, and `.unwrap()` panics.

Every other malformed-input path in the same function (`IncorrectAmountOfParticipants`, `InvalidParticipant`, `InvalidProof`) returns a `Result::Err`; only this structural mismatch is reachable as a panic. The root cause is an incomplete validation of the key set: quantity and bounds are checked, but membership is not.

### Impact Explanation
`complete` is invoked with proofs relayed from remote DKG participants — untrusted, attacker-influenced input. A single participant (or anyone able to inject a `GeneratorProof` map, e.g. via a mis-aggregated key-rotation message) can crash the promotion flow on an honest validator. Since generator promotion runs during key rotation, a panic at this point aborts the rotation session mid-protocol; repeated triggering across retries constitutes a persistent denial of service of the signing pipeline on that node. This is a remote, unauthenticated-by-consensus DoS reachable purely through public protocol messages — matching the Medium severity and `A:H` availability impact of the CVE analog.

### Likelihood Explanation
The trigger requires only that a `proofs` map of size `n - 1` contain `params.i()` (or otherwise omit some `j <= n`) — a single malformed/malicious message. No cryptographic breakage, collusion, or leaked secrets are needed; only a key set that evades the two existing cardinality/bounds checks. Any participant able to contribute or inject `GeneratorProof`s can trigger it at will during every promotion attempt.

### Recommendation
Replace the unconditional index with explicit membership validation. Either:

- check upfront that `proofs.keys().copied().collect::<BTreeSet<_>>() == (1..=params.n()).filter(|i| *i != params.i())`, or
- change line 146 to `let proof = proofs.get(&i).ok_or(PromotionError::MissingProof(i))?;` and add a `MissingProof(Participant)` error variant.

Additionally, reject any proof keyed by `params.i()` itself (a duplicate of the local share), since it can never be legitimate input to `complete`.

### Proof of Concept
```rust
// Assume params: t == n == 3, local i == 2.
// proofs.len() must be n - 1 = 2.
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), valid_proof_from_1);
// Attacker keys a proof under the *local* participant index instead of 3.
proofs.insert(Participant::new(2).unwrap(), any_proof);

// Both checks pass:
//   proofs.len() == 2 == n - 1
//   all keys (1, 2) <= n (3)
// Loop hits i = 3, proofs.get(&3) == None -> unwrap panic.
promotion.complete(&proofs); // thread panics
```

Reachable code path: `crypto/dkg/promote/src/lib.rs:125-146`. The fix boundary is the key-set membership check; no cryptographic primitive is involved.
