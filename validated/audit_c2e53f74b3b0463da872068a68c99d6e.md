### Title

Unbounded allocation in `ReceivedOutput::read` via attacker-declared `TxOut` length enables denial of service - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

`ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 122–134) deserializes the embedded `TxOut` by calling `TxOut::consensus_decode` directly on attacker-controlled bytes. The Bitcoin consensus format encodes `script_pubkey` as a compact-size varint length followed by that many bytes; the `bitcoin` crate's `Decodable` implementation for `Vec<u8>`/`ScriptBuf` allocates a buffer sized by the *declared* length before a single byte of payload is read. This is the same bug class as CVE-2018-20213 (a process crash driven purely by an attacker-controlled length/size field): the input's claimed length, not its actual content, determines resource consumption.

### Finding Description

```rust
// networks/bitcoin/src/wallet/mod.rs:122
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output =
      TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
    outpoint =
      OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Note `BufReader::with_capacity(0, r)` deliberately does zero buffering, so no clamp is applied before `consensus_decode` reaches the raw reader. Inside `TxOut::consensus_decode`, the `script_pubkey: ScriptBuf` field is decoded as a `VarInt` length `L` and then `read_slice`/`Vec` decode allocates on the order of `L` bytes (a `vec![0; len]`/`resize`-style allocation in rust-bitcoin's `ReadExt`). `L` is a varint up to `u64::MAX`; on a 64-bit target a claimed length of e.g. `0xFF_FF_FF_FF` (~4 GiB) or larger triggers an allocation that either aborts on OOM or stalls the process in allocation before `read_exact` can fail on short input.

By contrast, other parsers in this codebase already handle the identical hazard correctly: `RrCodec::read_request` in `coordinator/src/p2p.rs` (lines 261–271) bounds `len` against `MAX_LIBP2P_REQRES_MESSAGE_SIZE` *before* `vec![0; len]`, and `Call::read` in `networks/ethereum/src/machine.rs` (lines 51–60) explicitly comments that claiming 4 GB over 4 bytes is a valid DoS and therefore reads in 1 KB chunks. `ReceivedOutput::read` has no equivalent guard: it delegates to `consensus_decode`, which trusts the declared length.

The following two points could not be fully verified within the index and should be confirmed during remediation:

- The exact rust-bitcoin version pinned and whether its `Vec<u8>`/`ScriptBuf` decoder caps allocation (some versions limit `with_capacity` but still `resize` to the declared length). Either behavior satisfies the finding.
- The reachability surface: per the engagement rules, `ReceivedOutput::read` is treated as a sink for untrusted bytes (e.g., output blobs relayed between components or read from storage influenced by scanned transactions).

### Impact Explanation

An attacker who can cause a `ReceivedOutput` byte blob with a malicious `TxOut` prefix to reach `ReceivedOutput::read` forces a multi-gigabyte allocation (or abort) in the victim process. That is a remotely triggerable denial of service of the signing/scanner pipeline — functionally identical in effect to the libexcel SEGV: attacker-chosen length field → crash/unavailability of the service. If the abort occurs inside a processor handling key operations, it can repeatedly halt signing/coordination at negligible attacker cost (a handful of bytes).

### Likelihood Explanation

Triggering requires only that the attacker influence a serialized `ReceivedOutput`: the payload is ~40 bytes (`offset` scalar + `TxOut` varint declaring a huge `script_pubkey` length). There is no authentication inside `read` — it happily consumes any byte stream — and the panic/abort happens before the function can return an error, so callers' `io::Result` handling does not help. Likelihood is bounded by how untrusted bytes actually reach this API in deployment; where such blobs cross a trust boundary (relayed output records, rescan/recovery data), a single unprivileged message suffices.

### Recommendation

Do not call `TxOut::consensus_decode` directly on untrusted input. Apply the same pattern already used elsewhere in this repo:

- Wrap the reader in a bounded `io::Take`/`Read::take(MAX_TXOUT_SIZE)` before decoding, so the declared length can never exceed what the reader can actually supply, or
- Replace `consensus_decode` with chunked reading of the varint + payload (mirroring `Call::read` in `networks/ethereum/src/machine.rs:51-60`), or
- Validate the varint against a sane maximum (a Taproot `TxOut` `script_pubkey` never exceeds a few hundred bytes; `MAX_CONSENSUS`-style limits such as the block size cap are a safe upper bound) and reject before allocating.

A regression test should feed `ReceivedOutput::read` a blob whose `TxOut` declares `script_pubkey` length `u64::MAX` followed by EOF and assert a clean `Err`, not an abort.

### Proof of Concept

```rust
// Conceptual; requires a Secp256k1 offset (32 zero bytes is rejected, use 0x01..01)
// then a TxOut: u64 value || VarInt(script_len) || script bytes.
use bitcoin_serai::wallet::ReceivedOutput;

let mut blob = vec![];
// offset scalar (any valid scalar)
blob.extend_from_slice(&[1u8; 32]);
// TxOut.value = 0
blob.extend_from_slice(&0u64.to_le_bytes());
// TxOut.script_pubkey: VarInt for 0xFFFF_FFFF_FFFF_FFFF is illegal (non-canonical),
// so use u32::MAX encoded as 0xFE || u32 le
blob.push(0xFE);
blob.extend_from_slice(&u32::MAX.to_le_bytes());
// No payload bytes: decoder allocates ~4 GiB (or declared len) before read_exact fails
// or aborts on OOM inside TxOut::consensus_decode.
let _ = ReceivedOutput::read(&mut blob.as_slice()); // DoS: huge alloc / abort
```
