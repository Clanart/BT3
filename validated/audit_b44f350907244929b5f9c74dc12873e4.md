### Title
`SignableTransaction::new` omits the OP_RETURN output from fee/vsize accounting, underpaying the specified fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the reported bug class — a code path whose effects are not reflected in the object's stored accounting (`stored_balances` there; `needed_fee`/vsize here) — `SignableTransaction::new` pushes the `OP_RETURN` data output onto `tx_outs` *before* the weight/vbytes calculation, yet calls `calculate_weight_vbytes` with only `payments`, so the data output's weight is never counted. The recorded `needed_fee` and the change computation therefore correspond to a smaller transaction than the one actually produced and broadcast.

### Finding Description
`SignableTransaction::new` builds `tx_outs` by pushing the payment outputs and, if `data` is supplied, an `OP_RETURN` output (send.rs:194–202). It then computes `(weight, vbytes)` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which reconstructs a transaction containing **only** `payments` (send.rs:85–93) — the OP_RETURN output is absent. The same omission occurs in the change path (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`, send.rs:226).

Consequences inside the same function:

- `needed_fee = fee_per_vbyte * vbytes` is understated by the serialized size of the OP_RETURN output (roughly `8 + 1 + pushdata + data` ≈ up to ~92 bytes for the maximum 80-byte payload).
- The `TooLowFee` check (send.rs:211) uses this understated `vbytes`, so a transaction can pass the minimum-relay-fee check while its true vsize makes the achieved rate lower than `DEFAULT_MIN_RELAY_TX_FEE` — or simply lower than the caller-requested `fee_per_vbyte`.
- When `change` is provided, `value = input_sat - (payment_sat + fee_with_change)` (send.rs:228) likewise uses the understated `fee_with_change`, so the change output absorbs the difference and the actual fee paid equals `needed_fee`, which corresponds to a lower effective fee rate than requested.

The constructed `SignableTransaction` thus carries internally inconsistent accounting: `self.tx` includes an output whose weight was never charged for, while `needed_fee` claims to satisfy `fee_per_vbyte` over a vsize that does not exist.

### Impact Explanation
Any caller that attaches `data` produces a transaction whose actual fee rate is below the requested `fee_per_vbyte`. The transaction remains consensus-valid, but:

- It may be evicted/never confirmed if the effective rate falls below mempool minimums (the `TooLowFee` guard was bypassed by the vsize understatement).
- In a threshold-wallet context (`TransactionMachine`/`TransactionSignMachine`, send.rs:292–428), all signers sign the underpaying transaction; the incorrect fee is locked into the sighash via `Prevouts::All` and cannot be corrected without re-signing a new transaction.

This matches the report's bug class: a specific input path (the `data` argument) mutates the transaction without the corresponding update to the stored accounting (`needed_fee`), so every downstream consumer (`fee()`, `needed_fee()`, change sizing, relay checks) operates on values inconsistent with the real object.

### Likelihood Explanation
Reachable by any unprivileged caller of the public `SignableTransaction::new` API who supplies `Some(data)` — e.g., an integrator attaching metadata/memo outputs. No secrets or collusion required; deterministic given the code path. The understatement is bounded (~92 vbytes worst case), so the practical impact is degraded/ stuck transactions rather than theft of funds, consistent with a Medium severity accounting error.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either pass the fully-built `tx_outs` (or a flag for the data payload size) into `calculate_weight_vbytes` for both the no-change and with-change computations, or construct the candidate `Transaction` for weight purposes from `tx_ins` + `tx_outs` + optional change directly instead of reconstructing it from `payments` alone.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Conceptual check against SignableTransaction::new:

let payments = [(p2tr_script_buf(dest_key).unwrap(), 10_000u64)];
let data = Some(vec![0u8; 80]);
let change = Some(p2tr_script_buf(change_key).unwrap());
let fee_rate = 10;

let tx = SignableTransaction::new(vec![input], &payments, change, data, fee_rate).unwrap();

// tx.transaction().output contains: payment, OP_RETURN(80B), change
// But needed_fee was computed on a tx WITHOUT the OP_RETURN output:
let actual_vsize = tx.transaction().vsize() as u64; // includes OP_RETURN
assert!(tx.needed_fee() < actual_vsize * fee_rate);
// The TooLowFee check at send.rs:211 also used the understated vbytes,
// so a marginal-rate tx can pass validation yet underpay the relay minimum.
```

Relevant code: the OP_RETURN output is pushed at `send.rs:194-202`, while both weight calculations at `send.rs:204` and `send.rs:226` reconstruct the transaction from `payments` only (`send.rs:85-99`), never accounting for the data output.
