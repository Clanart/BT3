**Analysis:**

The `vote()` function in `WombatBribeManager.sol` performs per-pool accounting checks that prevent the described attack: [1](#0-0) 

When `delta` is negative, line 202 executes `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta)`. Since the contract is compiled under `pragma solidity ^0.8.0` [2](#0-1)  without any `unchecked` block around this subtraction, Solidity's built-in checked arithmetic causes this statement to **revert on underflow** whenever `_deltas[i]`'s magnitude exceeds the user's own recorded vote for that specific pool — regardless of what other pools' deltas are in the same call. This is a per-pool mapping check that is entirely independent of `userTotalVotedInVlmgp`, so an attacker cannot "borrow" capacity from a positive delta on another pool to cover an oversized negative delta on `poolA`; each `_lps[i]` iteration is checked in isolation before the aggregate `totalUserVote` is even evaluated at line 209-219.

As defense-in-depth, even if that manager-level check were somehow bypassed, `IBribeRewardPool.withdrawFor` (implemented in `BribeRewardPool.sol`) also performs checked subtraction on the user's own balance: `_balances[_for] = _balances[_for] - _amount;` [3](#0-2) . This mirrors `userVotedForPoolInVlmgp` exactly (both are incremented/decremented together in the same `vote()` call at lines 198-199 and 202-203), so it independently reverts if `_amount` exceeds what was actually staked for that user in that specific rewarder — there is no possibility of pulling another voter's staked balance.

Since the entire transaction reverts atomically on underflow (Solidity 0.8+ default behavior, no `unchecked` used in either contract), the attacker's crafted call `vote([poolA],[-50])` with only 10 previously voted simply reverts with no state change and no fund/yield impact.
