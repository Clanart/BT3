### Title
Repository identity keyed by filesystem path allows credential/config re-association after path reuse - ([File: app/src/lib/repository-matching.ts])

### Summary
The external report's broken invariant is: a transferable asset (LP token) is tracked by a separate, non-transferable key (depositor address), so ownership of the asset and ownership of the associated protected state (`lockData`) can diverge. The closest verifiable analog in this codebase is that GitHub Desktop treats a local filesystem `path` as a stable proxy for repository identity when re-associating a `Repository` record with its previously stored `GitHubRepository`, workflow preferences, and (indirectly) account/credential lookups, rather than verifying that the on-disk content is still the same repository (e.g. by remote URL/origin fingerprint).

### Finding Description
`matchExistingRepository` looks up a tracked repository purely by normalized `path` equality: [1](#0-0) 

`Dispatcher.openOrAddRepository` uses the same path-only match to decide whether to reuse an existing, already-known `Repository` object (with its `gitHubRepository`, `workflowPreferences`, etc.) instead of treating the folder as new: [2](#0-1) 

`RepositoriesStore.updateRepositoryPath`/`switchWorktree` similarly persist and carry forward `gitHubRepository`, `alias`, and `workflowPreferences` keyed by the stable database `repository.id`, with `path` treated as just another mutable field that can be repointed without re-validating the content at the new path: [3](#0-2) 

The "unsafe directory" ownership check (`getRepositoryType`/`addSafeDirectory`) only guards against a different OS-level file owner; it says nothing about whether the git history/remote at that path is still the repository the user originally trusted: [4](#0-3) [5](#0-4) 

So the "lock" (trust, GitHub API linkage, workflow preferences) stays bound to the *path*, not to a verified identity of the repository content — mirroring the LP token bug where the lock stayed bound to the depositor's address instead of following the transferred token.

### Impact Explanation
If an attacker can cause a different git repository to occupy the exact path Desktop previously tracked as a trusted, GitHub-linked repository (e.g., after the user deletes the folder outside of Desktop, or a sync/cleanup tool empties and repopulates it, leaving the stale DB record with `missing: true`), Desktop will silently re-bind the old `GitHubRepository` association, workflow preferences, and repository-scoped UI trust state to the new, attacker-supplied content the next time the user reopens/relocates to that path. This can misattribute pushes/PR context to the wrong GitHub repository or carry forward preferences/settings that were never validated against the new content — a silent corruption of what the user believes they are committing to/pushing to, without any additional guard beyond the OS-ownership "unsafe directory" check, which does not validate repository identity.

### Likelihood Explanation
Medium: it requires a specific sequence (existing tracked repo record + folder becomes reusable by other content at the same path) rather than an interactive step within Desktop itself, and Desktop's own "missing repository"/"relocate" flows are the only paths that re-validate at that path — but they re-validate only Git repo-type/ownership, not content identity. This is a narrower condition than the arbitrary bug-class primitive in the report (which required only a plain token transfer), so likelihood is lower than the original finding's "Medium/Medium" pairing.

### Recommendation
When re-attaching a path to an existing `Repository` record (in `matchExistingRepository`, `openOrAddRepository`, `updateRepositoryPath`, `switchWorktree`, and the "locate"/"relocate" flows), verify that the git remote/origin at the new path is consistent with the previously recorded `gitHubRepository` (e.g., compare remote URLs via `repositoryMatchesRemote`) before reusing the stored `GitHubRepository`, `workflowPreferences`, or other trust-bearing state. If the identity cannot be confirmed, treat the path as a new/unknown repository and require the user to re-link it explicitly.

### Proof of Concept
1. User adds `~/code/proj` as a Desktop repository; Desktop records `Repository.path = ~/code/proj`, links it to `GitHubRepository` for `org/proj`, and stores `workflowPreferences`.
2. User deletes `~/code/proj` outside Desktop (Desktop marks the DB record `missing: true`, keeping `id`, `gitHubRepository`, `workflowPreferences`). [6](#0-5) 
3. An attacker-controlled process (or another tool driven by attacker content, e.g. a malicious script bundled in a different downloaded/cloned project) creates a new, unrelated git repository at the exact same path `~/code/proj`.
4. User reopens Desktop or uses "Locate…"/clicks the folder again; `openOrAddRepository`/`matchExistingRepository` matches purely on `path` and returns the old `Repository` object still carrying the stale `gitHubRepository`/`workflowPreferences`, now bound to unrelated attacker-supplied content. [2](#0-1) 

Note: I was not able to fully trace every downstream consumer of the stale `gitHubRepository` linkage (e.g., exact PR/push targeting code) within the available search budget; a Devin session with full repo access would be needed to confirm the complete blast radius of this re-association.

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
