## Finding Confirmed [1](#0-0) 

### Title
Early `break` on retry-pool overflow silently drops and under-reports already-broadcast transactions mid-batch - (send-transaction-service/src/send_transaction_service.rs)

### Summary
When `receive_txn_thread` moves a just-broadcast batch of transactions from the ephemeral `transactions` map into the shared `retry_transactions` pool, it iterates `transactions.drain()` and stops with `break` as soon as `retry_transactions.len() >= retry_pool_max_size`. Because it is iterating a `HashMap::drain()`, breaking out of the loop does not "skip" the remaining items — the `Drain` iterator's `Drop` implementation still removes (and discards) every remaining entry from `transactions` when the loop exits early. Those remaining transactions were already handed to `tpu_sender.send_transactions_in_batch(...)` a few lines earlier, but they are never inserted into `retry_transactions` and never counted in `stats.retry_queue_overflow`.

### Finding Description
The relevant code path is: [2](#0-1) 

1. All transactions currently buffered in `transactions` are sent as a batch via `tpu_sender.send_transactions_in_batch(...)` at line 264, and `stats.sent_transactions` is incremented for the whole batch (line 257-259) — before any retry-pool accounting happens.
2. The code then locks `retry_transactions` and loops `for (signature, mut transaction_info) in transactions.drain()`.
3. For each transaction, `transactions_to_retry` is incremented, then `retry_len >= retry_pool_max_size` is checked. If true, the loop does `break`.
4. Rust's `HashMap::drain()` returns a `Drain` iterator whose `Drop` impl unconditionally empties the map of any elements not yet yielded — so breaking early still consumes/removes all remaining map entries, they are simply never processed by the loop body.
5. Consequently, any transaction that would have been iterated *after* the one that triggered the `break` is discarded without: (a) being inserted into `retry_transactions` (so it will never be retried by `retry_thread`), and (b) being counted in `transactions_to_retry`/`transactions_added_to_retry`, so it is not reflected in `stats.retry_queue_overflow` either.

The overflow accounting at lines 292-296 only reflects the single item that caused the break (since `transactions_to_retry` was incremented for it but `transactions_added_to_retry` was not), not the arbitrary number of remaining entries that `Drain::drop` silently discards.

### Impact Explanation
Transactions from any RPC client (not just the one causing the overflow) that happen to be batched together in the same `transactions` map when the retry-pool boundary is crossed are broadcast once via TPU but then silently vanish: they are not added to the retry pool, so `retry_thread` never resends them, and no stat counter reflects the loss beyond the single triggering entry. This degrades the reliability/throughput of `SendTransactionService` (used by the built-in `sendTransaction` RPC path) without any error being surfaced and without violating any published per-second rate limit, since the ephemeral `transactions` batch can contain transactions from multiple distinct low-rate clients.

### Likelihood Explanation
Triggering it requires the shared `retry_transactions` pool to be at or near `retry_pool_max_size` (default `MAX_TRANSACTION_RETRY_POOL_SIZE = 10_000`) at the moment a batch is drained, and for that batch to contain more than one transaction past the boundary. An attacker (or even normal load) that keeps the retry pool saturated (e.g. by submitting many low-value/never-landing transactions with high `max_retries`) can repeatedly straddle this boundary, causing collateral drops of other batched transactions.

### Recommendation
Replace `break` with `continue` in the loop, and always increment `transactions_added_to_retry`/overflow bookkeeping per skipped transaction (or otherwise stop consuming further elements from `transactions.drain()` without discarding them, e.g. by draining into a `Vec` first and iterating that, or checking pool size before entering the `drain()` loop and using `retain`/explicit removal instead of `break`).

### Proof of Concept
1. Configure a validator/test harness with a small `retry_pool_max_size` (e.g. 3) via `--rpc-send-transaction-retry-pool-max-size`.
2. Pre-fill `retry_transactions` to `retry_pool_max_size - 1` via prior benign submissions that stay unconfirmed (so they remain in the retry pool).
3. Submit a single batch (within one `batch_send_rate_ms` window) containing several new distinct transactions such that the first fills the last retry-pool slot and subsequent ones in the same `transactions.drain()` iteration order are still pending.
4. Observe: `stats.sent_transactions` counts the whole batch as sent, but `stats.retry_queue_overflow` only increments by 1 for the triggering transaction, while the remaining transactions in the batch — which were also sent over TPU — are neither present in `retry_transactions` nor reflected in `retry_queue_overflow`, i.e. they are unaccounted-for and will never be retried.
