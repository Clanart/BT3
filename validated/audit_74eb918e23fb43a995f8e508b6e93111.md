## Title
`resolveWithin()` sandbox check uses unanchored `startsWith`, allowing sibling-directory escape via a crafted deep link - (File: `app/src/lib/path.ts`)

### Summary
The `AssetLock.sol` bug is a broken invariant: a value meant to only move in a "safe" direction (lock end time can only extend) is instead accepted unchecked from user input, silently weakening a security guarantee. The closest analog in this GitHub Desktop codebase is `_resolveWithin()` in `app/src/lib/path.ts`, whose containment check is a broken invariant of the same shape: it's supposed to guarantee a resolved path stays *at or under* a root directory, but the check only verifies a string prefix without a path-separator boundary, so a path that merely shares the root's name as a prefix (e.g. a sibling directory) is silently treated as "inside" the root.

### Finding Description
`resolveWithin()` is the app's designated guard for keeping attacker-influenced relative paths (from git status, deep links, Copilot conflict resolutions) inside a trusted root directory: [1](#0-0) 

```
  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

`realResolved.startsWith(realRoot)` treats any path whose *string* begins with `realRoot` as "within" the root — it never checks that the next character after the prefix is a path separator (or that the strings are equal). This means a directory that merely shares the root directory's name as a prefix (e.g. `/Users/victim/Documents/GitHub/app` vs `/Users/victim/Documents/GitHub/app-secrets`) will incorrectly pass the containment check. This is the exact "same bug class" as the AssetLock report: a protective invariant (path must stay *under* root / lock time must only *increase*) is checked with logic that doesn't actually enforce the invariant, and the flaw is exploitable by supplying an otherwise-plausible, attacker-controlled value (a relative path / a duration) that superficially satisfies the check.

The existing test suite for `resolveWithin` explicitly exercises `..` traversal, null bytes, and symlink escapes, but never exercises the sibling-prefix case, confirming the gap was not covered by the guard's design intent: [2](#0-1) 

The most directly attacker-reachable call site is the deep-link (`x-github-client://openRepo/...`) handler, which the user triggers by clicking a link: [3](#0-2) 

```
    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(...)
      }
    }
```

`filepath` comes straight from the parsed deep-link query string with only a check for `isAbsolute`: [4](#0-3) 

The same guard is also relied on for writing AI/Copilot conflict-resolution content back to disk: [5](#0-4) 

```
      const absolutePath = await resolveWithin(repository.path, resolution.path)
      if (absolutePath === null) {
        log.warn(...)
        continue
      }
      ...
      await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
```

and for reading conflicted file content into the Copilot prompt context: [6](#0-5) 

### Impact Explanation
If a victim's repositories directory contains (or an attacker can arrange to exist, e.g. via a second cloned repo with a colliding-prefix name such as `desktop` / `desktop-secrets`, `app` / `app-backup`, common in real developer machine layouts) a sibling directory whose name has the target repository's path as a string prefix, then:
- A crafted `x-github-client://openrepo/...&filepath=../<sibling-dir-suffix>/<file>` deep link, when clicked, can cause Desktop to reveal (via `shell.showItemInFolder`) or, in the Copilot conflict-resolution path, **write attacker/model-influenced content to a file outside the intended repository** — this is a "silent corruption" / "file write outside the repo" primitive matching the exact bug class of the reference report (a value that should be strictly bounded is instead accepted because the enforcement check is logically incomplete).
- This qualifies under the stated Valid Impact criteria ("a link or deep link the user clicks... result is file write or read outside the repo").

### Likelihood Explanation
Exploitability is conditional on directory-name collisions existing on the victim's filesystem (e.g., two repos with one name being a prefix of the other, which is a realistic naming pattern for developers who keep multiple related clones side-by-side, such as `foo` and `foo-private`, or `repo` and `repo.wiki`). It does not require admin rights, local access, or pre-existing malware — only that the user click a maliciously crafted `x-github-client://` link (or a malicious repo triggering the Copilot conflict-resolution write path) while such a sibling directory happens to exist. This is a real, code-verifiable logic gap (missing separator check) rather than a speculative issue, but real-world triggerability depends on the victim's directory layout, which the attacker cannot directly control — hence Medium likelihood, mirroring the "Medium Risk" severity of the original report.

### Recommendation
Fix `_resolveWithin()` in `app/src/lib/path.ts` to require an exact match or that the character immediately following the `realRoot` prefix is the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's fix pattern (replace an incomplete comparison with one that correctly enforces the invariant, i.e. `max()` for lock time vs. a separator-anchored prefix check for path containment).

### Proof of Concept
1. On the victim's machine, two GitHub Desktop-managed clones exist side by side: `~/Documents/GitHub/app` and `~/Documents/GitHub/app-secrets` (the latter, e.g., containing sensitive files or being any other repo whose name has `app` as a prefix).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/org/app?filepath=../app-secrets/credentials.txt`.
3. Victim clicks the link; Desktop calls `dispatchURLAction` → `openRepositoryFromUrl` → `resolveWithin('~/Documents/GitHub/app', '../app-secrets/credentials.txt')`.
4. `realResolved` = `~/Documents/GitHub/app-secrets/credentials.txt`; `realRoot` = `~/Documents/GitHub/app`. `realResolved.startsWith(realRoot)` evaluates `true` because the string `app-secrets` starts with `app`, even though `app-secrets` is a sibling, not a subdirectory.
5. The check incorrectly passes, and `shell.showItemInFolder()` is invoked on a path outside the `app` repository — demonstrating the containment guard is bypassed. The same flawed check gates the Copilot conflict-resolution `writeFile` call in `app-store.ts`, where the impact escalates to an out-of-repo file write.

**Note on verification limits:** I was not able to execute this PoC in a live Desktop instance (no filesystem/terminal access in this mode), so the trigger conditions (specifically, whether `realpath` normalization or other upstream sanitization in the actual `x-github-client://` flow imposes additional restrictions not visible in the indexed snippets) should be validated by a Devin session with full repo/runtime access before treating this as a confirmed, weaponizable vulnerability.
