### Title
Unbounded recursion depth in `AccountKeyRoleBased.DecodeRLP` allows a single crafted transaction to exhaust stack/CPU/memory before composite-type validation runs - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each contained `AccountKey` through `AccountKeySerializer.DecodeRLP`, which dynamically dispatches on an attacker-controlled type tag. Because `AccountKeyTypeRoleBased` is itself a valid dispatch target, an attacker can nest `AccountKeyRoleBased` inside itself to unbounded depth in a single RLP-encoded account-key payload. The decoder has no recursion-depth counter, so the entire nested structure is walked — one non-tail-recursive call per nesting level — before the "composite key not allowed" check (`ErrNestedCompositeType`) is ever evaluated. This is the same bug class as the reported protobuf advisory: unbounded recursion in embedded/self-referential message decoding of untrusted network input.

### Finding Description
`AccountKeyRoleBased` is a slice of generic `AccountKey` values: [1](#0-0) 

Its `DecodeRLP` decodes a list of opaque byte strings and, for each one, re-decodes it through a generic `AccountKeySerializer`: [2](#0-1) 

`AccountKeySerializer.DecodeRLP` reads an attacker-controlled `keyType` tag, calls `NewAccountKey(keyType)` to allocate the corresponding concrete `AccountKey` implementation, and then decodes into it via `s.Decode(serializer.key)`: [3](#0-2) 

If the attacker sets `keyType = AccountKeyTypeRoleBased`, `NewAccountKey` returns a fresh `*AccountKeyRoleBased`, and `s.Decode` re-enters `AccountKeyRoleBased.DecodeRLP` — the exact same function — creating a self-referential decode cycle: `AccountKeyRoleBased.DecodeRLP → AccountKeySerializer.DecodeRLP → NewAccountKey → s.Decode → AccountKeyRoleBased.DecodeRLP → ...`. Each level costs only a small RLP list/byte-string header, so an attacker can drive recursion depth arbitrarily high with a payload that grows only linearly (a few bytes per level).

The only defense against nested composite keys is `CheckInstallable`/`CheckUpdatable`, which reject a role that `IsCompositeType()`: [4](#0-3) 

Critically, this check runs only *after* decoding is complete and only at the top level of validation logic — it does not prevent or bound the recursive `DecodeRLP` calls that already consumed stack frames and heap for every nesting level in the payload. This mirrors the protobuf issue precisely: the vulnerable code performs unbounded non-tail recursion driven entirely by attacker-supplied bytes, with the depth-limiting/rejection logic applied too late (after the walk, not during it), and with no recursion counter threaded through the decode call chain (`decode.go`'s `Stream.Decode` / `makeDecoder` / `decodeDecoder` dispatch to custom `DecodeRLP` implementations shown at `rlp/decode.go:544-546` and `rlp/decode.go:162-193` have no depth-tracking at all).

### Impact Explanation
Account key data of this shape is attacker-reachable from a single, unprivileged, unauthenticated transaction: any `TxTypeAccountUpdate` (or account-creation transaction carrying a `RoleBased` key) submitted via `eth_sendRawTransaction`/the tx pool will have its account-key field RLP-decoded during transaction ingestion and processing. A crafted key payload nesting `AccountKeyRoleBased` hundreds of thousands of levels deep forces the node to recurse that many times before any validation rejects it, burning CPU and memory and risking a stack/goroutine crash — a request-amplification denial of service reachable by any transaction sender, matching the severity class of the reported advisory (CWE-674, unbounded recursion from untrusted decode input).

### Likelihood Explanation
High. The attack requires only building a nested RLP byte string with a type-tag byte and length prefix per level — no privileges, no special account state, and no cryptographic material beyond a normally-signed transaction envelope are needed. The recursive decode path is exercised as soon as the transaction's account-key field is decoded, which happens for every submitted transaction of the relevant types.

### Recommendation
Thread an explicit recursion-depth counter through `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., via a bounded parameter or a depth value carried in a wrapper), and reject decoding once depth exceeds a small fixed limit (role-based keys should never legitimately nest more than one level, since composite types are explicitly disallowed as role members). Enforce the depth/composite-type check *during* decode rather than only after decode completes, so recursion cannot proceed past the first invalid nesting level.

### Proof of Concept
1. Construct a serialized `AccountKeySerializer` byte string with `keyType = AccountKeyTypeRoleBased` whose "key" payload is itself an `AccountKeyRoleBased`-encoded list containing one more `AccountKeySerializer` entry of `keyType = AccountKeyTypeRoleBased`, and repeat this nesting `N` times (build inner-to-outer to keep generation linear in `N`).
2. Wrap the innermost entry as a legal leaf key (e.g., `AccountKeyTypeLegacy`/`AccountKeyTypePublic`) so the structure is syntactically valid RLP at every level.
3. Embed the resulting bytes as the `key` field of a `TxTypeAccountUpdate` transaction (or account-creation transaction) and submit it via `eth_sendRawTransaction`.
4. During RLP decoding of the transaction, `AccountKeyRoleBased.DecodeRLP` recurses once per nesting level through `AccountKeySerializer.DecodeRLP → NewAccountKey → s.Decode`, before `CheckInstallable`/`CheckUpdatable` ever gets a chance to reject the nested composite type, consuming stack depth and memory proportional to `N`.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
