### Title
ThresholdKeys accepts a zero-value group key, enabling forgeable Schnorr signatures - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` accepts untrusted serialized threshold-key material, but `ThresholdKeys::new` does not reject a zero `secret_share`, identity verification shares, or an identity aggregate `group_key`. A crafted key with `t = 1`, `n = 1`, `i = 1`, a zero scalar, and an identity verification share is accepted and produces the identity as its group key. Signatures under that group key are forgeable because the Schnorr verification equation degenerates to the identity. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Participant::new` and `ThresholdParams::new` reject zero participant indexes, thresholds, and participant counts, so the crafted `t = 1`, `n = 1`, `i = 1` parameter set is structurally valid. [4](#0-3) [5](#0-4) 

`ThresholdKeys::new` only verifies the number and participant indexes of `verification_shares`, then derives `group_key` by interpolating the provided shares; it does not reject identity points, a zero `secret_share`, or an identity result. [2](#0-1) 

`ThresholdKeys::read` reads attacker-controlled scalars and points through `read_F`/`read_G` and passes them to `ThresholdKeys::new`; `read_G` enforces only canonical encoding, not non-identity or non-zero semantic state. [6](#0-5) [7](#0-6) 

The resulting `ThresholdKeys` reports the identity as `group_key()` because all interpolated verification shares are identity. [8](#0-7) [9](#0-8) 

Schnorr verification evaluates `R + cA - sG`; with `A = identity`, `R = identity`, and `s = 0`, this expression is identity for every challenge, so verification succeeds without knowledge of a private key. [3](#0-2) 

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` can instantiate a threshold key whose public group key has the publicly known discrete logarithm zero. Any signature algorithm using the returned `group_key` then has a forged signature for arbitrary challenges and messages, including the FROST Schnorr completion path, which delegates final acceptance to `SchnorrSignature::verify`. [10](#0-9) [3](#0-2) 

This is analogous to removing an account without checking that its balance is zero: a zero-value cryptographic state is admitted into an operational path where a non-zero secret/public-key invariant is required. [2](#0-1) 

### Likelihood Explanation
The attack requires the application to deserialize attacker-controlled `ThresholdKeys`; that input surface is explicitly exposed by `ThresholdKeys::read`. [11](#0-10) 

No malformed encodings are required: zero scalars are canonical field elements, and the identity point is a canonical group element accepted by `read_G`. [12](#0-11) [7](#0-6) 

### Recommendation
Reject zero-value key state during `ThresholdKeys::new` and `ThresholdKeys::read`: require the local `secret_share`, the participant's verification share, and the derived `group_key` to be non-zero/non-identity. [2](#0-1) [13](#0-12) 

Also verify that the local share matches its declared verification share with `C::generator() * secret_share == verification_shares[&params.i()]`; this prevents semantically inconsistent serialized key material even when the aggregate key is non-identity. [14](#0-13) [15](#0-14) 

### Proof of Concept
For a ciphersuite `C`, construct the following serialized `ThresholdKeys` payload:

```text
u32le(C::ID.len()) || C::ID ||
u16le(1) || u16le(1) || u16le(1) ||
0x01 ||                         // Interpolation::Lagrange
C::F::ZERO.to_repr() ||          // local secret share = 0
C::G::identity().to_bytes()      // verification share = identity
```

`ThresholdKeys::<C>::read` accepts this payload because the participant parameters are valid and both encoded values are canonical. [16](#0-15) [7](#0-6) 

The derived key then has:

```text
keys.group_key() == C::G::identity()
```

because `ThresholdKeys::new` sums the only interpolated identity verification share and performs no non-identity check. [8](#0-7) 

The following signature verifies for every challenge against that key:

```rust
let forged = SchnorrSignature::<C> {
  R: C::G::identity(),
  s: C::F::ZERO,
};

assert!(forged.verify(keys.group_key(), arbitrary_challenge));
```

The verification statement is `identity + challenge * identity - 0 * G`, which is always identity. [3](#0-2)
