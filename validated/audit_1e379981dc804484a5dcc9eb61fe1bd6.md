### Title
Attacker-controlled GitHub repository metadata silently rewrites local git remote URL - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl()` treats `clone_url` returned by the GitHub API as safe to write into the user's local git config whenever it differs from the previously cached value, as long as the URL scheme (`https`/`ssh`) hasn't changed. This mirrors the report's bug class: a value (`clone_url`, analogous to the yToken's `name`/`symbol`/`decimals`) that the consuming application assumes is immutable/trustworthy is in fact mutable and externally controlled, and the app blindly propagates the new value into a security-relevant local artifact (the git remote configuration that determines where future fetches/pushes go).

### Finding Description
`GitHubRepository.cloneURL` is cached locally after the repo is first added [1](#0-0) . On periodic/opportunistic refresh, `repositoryWithRefreshedGitHubRepository` in `app-store.ts` re-fetches the repo from the GitHub API and, if the app already has a linked `gitHubRepository`, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` before persisting the new API data: [2](#0-1) 

Inside `updateRemoteUrl`, the only checks performed before rewriting `origin`'s URL are:
1. the URL scheme (protocol) of the old and new URL match, and
2. the *previous* API-supplied `cloneURL` still matches the current remote (i.e., the user hasn't manually customized the remote): [3](#0-2) 

There is no check that the new `clone_url`'s **hostname** matches the endpoint the repository is supposed to belong to, nor any user confirmation before the remote is rewritten via `gitStore.setRemoteURL`. Because `clone_url` is server-supplied data (from `api.fetchRepository`) [4](#0-3) , anyone who can influence that field for a repository the user has cloned — e.g. a compromised/malicious org owner performing a repository transfer, a malicious/compromised GitHub Enterprise Server the user has configured as an endpoint, or a network-level proxy/MITM on that GHE endpoint — can cause Desktop to automatically run the equivalent of `git remote set-url origin <attacker-url>` on the user's local clone, without any prompt, as long as the scheme (e.g. `https://`) is preserved.

This is the same broken invariant as the report: code paths assume a remote-controlled metadata field (`clone_url`, like `name`/`symbol`/`decimals`) is immutable once cached, and downstream logic (writing git config, building push/fetch endpoints) is not re-validated when that value changes.

### Impact Explanation
Silently repointing `origin` allows an attacker to redirect the user's future `git push`/`git fetch` operations to an attacker-controlled remote while the Desktop UI continues to show the original, trusted repository name/owner (cached separately in `GitHubRepository.name`/`owner`). Consequences include:
- Silent corruption of what the user pushes — pushes intended for the legitimate repo can be sent to an attacker's server instead.
- Potential credential exposure if the credential helper or embedded URL now targets an attacker's host under the guise of the same scheme.
- Because there's no hostname pinning, this could also be used to swap a GitHub.com-backed remote for another `https://` host entirely, defeating user expectations built from the repository name shown in the UI.

### Likelihood Explanation
The refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically as part of normal repository housekeeping in `app-store.ts`, not requiring any unusual user action beyond having the repository open in Desktop with a linked GitHub account. The attacker precondition is realistic for enterprise scenarios (compromised/malicious GHES instance or network proxy in the corporate environment) or an org-owner/admin performing a repository transfer/rename that changes `clone_url`'s host component while keeping the same scheme — no local access, no leaked credentials, and no unnatural user steps are required beyond the app's normal background refresh.

### Recommendation
- Require that the new `clone_url`'s hostname matches the endpoint (and ideally the same authority as the previously trusted `cloneURL`) before silently rewriting the remote; only allow same-host renames (owner/name path changes) to be auto-applied.
- If the hostname changes, surface an explicit user-facing confirmation instead of silently calling `setRemoteURL`.
- Treat all GitHub API-supplied identity/URL fields as mutable, and re-validate/re-derive any locally cached security-relevant state (remote URLs, push targets) rather than blindly trusting cached values across the object's lifetime, consistent with the general recommendation in the source report to avoid assuming ERC20-style (or here, API-object-style) metadata is immutable.

### Proof of Concept
1. User adds `https://github.example.com/acme/app` (a GitHub Enterprise Server the org has configured) as a repository in Desktop; Desktop caches `gitHubRepository.cloneURL = https://github.example.com/acme/app.git`.
2. The GHES instance (compromised, or an admin with repo-transfer rights) is later observed by Desktop's periodic refresh (`repositoryWithRefreshedGitHubRepository`) to report `clone_url: https://attacker.example.com/acme/app.git` for the same repo id/owner/name via `fetchRepository` [4](#0-3) .
3. `updateRemoteUrl` sees: protocol unchanged (`https` == `https`), `remoteUrlUnchanged` is true (user's local origin still matches the previously-cached `cloneURL`), and `urlsMatch` is false (new URL differs) — all conditions in the `if` are satisfied [5](#0-4) .
4. Desktop calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/acme/app.git')`, silently rewriting the user's `.git/config` remote — with no dialog, prompt, or hostname check — redirecting all future fetches/pushes to the attacker's server while the UI still shows "acme/app" as the repository name.

Note: I was not able to fully trace `GitStore.setRemoteURL`'s exact git invocation or every caller in `dispatcher.ts`/`repository-settings.tsx` within the available search budget; those would be worth confirming in a follow-up session to verify there are no additional guard rails (e.g., a confirmation dialog inserted elsewhere in the call chain) that might mitigate this before the write actually occurs.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

  public async fetchRepository(
    owner: string,

  ): Promise<IAPIFullRepository | null> {
    try {
      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)
      if (response.status === HttpStatusCode.NotFound) {

      }

      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
      return null
    }
