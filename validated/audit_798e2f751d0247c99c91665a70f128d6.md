### Title
Scanner reports economically unspendable dust outputs as received funds, and `SignableTransaction` accepts them as inputs - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the Truflation issue — where the rewards contract's accounting advances and treats funds as disbursed even though no eligible recipient exists — the Bitcoin scanner's accounting treats *every* output paying a registered script as received value, even when the output's value is below the cost of ever spending it. An unprivileged party can send dust-valued outputs to a Serai P2TR deposit script; `Scanner::scan_transaction`/`scan_block` will report them as `ReceivedOutput`s with no minimum-value check, and `SignableTransaction::new` will accept them as inputs (its dust check only covers payments, not inputs), so sub-dust value is booked as usable balance when it is effectively distributed to nobody — it costs more in fees to move than it contains.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `script_pubkey` membership in `self.scripts` and pushes a `ReceivedOutput` carrying the matched offset, with no check of `output.value`:

```rust
// networks/bitcoin/src/wallet/mod.rs
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

`scan_block` extends this to every transaction in a block . The only amount-based guard anywhere in the crate is in `SignableTransaction::new`, and it applies solely to `payments`, never to `inputs` — `input_sat` is summed unconditionally from whatever `ReceivedOutput`s are passed in . So a 1-satoshi (or even 0-value) output to a registered script:

1. is reported by the scanner as a received deposit, and
2. is treated by transaction construction as spendable input value, even though each Taproot input adds ~57 vbytes of weight (documented in `networks/bitcoin/src/bitcoin.rs` commentary: 230 WU ≈ 57 vbytes) — at any reasonable feerate a sub-thousand-sat output costs more to spend than it contributes.

The value is nominally credited to the multisig yet is economically unreachable — the direct analog of rewards being "distributed to nobody": the ledger (scanner output/`input_sat`/`fee()` accounting) assumes the funds exist and are usable, while in practice they can never be recovered without a net loss. Because offsets are surjective and script matching is all that's required, the attacker needs no special position — any standard Bitcoin transaction paying the deposit/forwarded/change script qualifies.

### Impact Explanation
- Inflation of credited/received balance: downstream consumers of `Scanner` (the processor's `get_outputs` path builds `Output`s directly from `scan_transaction` results) treat every matched output as real inbound value. An attacker can mint "received" balance at arbitrarily low cost using dust outputs; if the accounting/crediting layer relies on the scanner's report (the in-scope crate provides no floor), value is credited that can never be spent.
- Fee drain on the multisig: each dust input included in a `SignableTransaction` contributes less than the ~57-vbyte marginal fee it forces the honest inputs to subsidize, so even when the outputs are "spent," they are net-negative — the funds were effectively dispersed to miners/nobody.
- Matches the accepted impact class "funds reported received that are not spendable."

### Likelihood Explanation
The trigger requires only that an unprivileged third party broadcast an ordinary Bitcoin transaction with a low-value output to a publicly-known Serai deposit script — no validator collusion, no leaked key, no malformed encoding. Deposit scripts are inherently public (they appear in every prior transaction and in published addresses), and dust-spamming known addresses is trivially cheap. The only mitigation (an `amount >= DUST` filter) exists in the processor integration layer, not in the in-scope crate, whose own scanner, output type, and transaction builder all lack any minimum-value enforcement — integrators using `bitcoin-serai` directly, or any path that reaches `SignableTransaction::new` before the processor-side filter, are exposed.

### Recommendation
Enforce a minimum-value check inside the in-scope crate rather than relying on callers:

1. In `Scanner::scan_transaction` (or at `ReceivedOutput` construction), reject outputs whose `value` is below the spend-cost-derived dust threshold, mirroring the `DUST` constant already documented on the `Network` trait ("this value MUST exceed the cost to spend said output").
2. Alternatively/additionally, in `SignableTransaction::new`, validate that each `input.output.value` is at least the marginal fee cost of carrying it (~57 vbytes × `fee_per_vbyte`), returning a dedicated error rather than silently subsidizing unprofitable inputs — analogous to the report's recommendation that `notifyRewardAmount()` revert when there's nobody to pay.
3. If dust inputs are ever intentionally accepted for consolidation, make it an explicit opt-in flag so the default accounting never books unspendable value as received.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs style (regtest)
let (_, key) = keys();
let mut scanner = Scanner::new(key).unwrap();

// Attacker crafts a tx paying the deposit script with 1 sat (well under the
// ~285+ sats needed to spend a Taproot input, and under the 10_000 DUST used
// by the reference processor).
let dust_tx = Transaction {
  // ...
  output: vec![TxOut {
    value: Amount::from_sat(1),
    script_pubkey: p2tr_script_buf(key).unwrap(),
  }],
  // ...
};

// Scanner reports it as a received output with offset ZERO — no value check.
let outputs = scanner.scan_transaction(&dust_tx);
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].value(), 1); // "received", yet unspendable at a profit

// Transaction builder accepts it as an input; only payments are dust-checked.
let inputs = vec![outputs[0].clone()];
let tx = SignableTransaction::new(
  inputs,
  &[(p2tr_script_buf(key).unwrap(), 1000)],
  None,
  None,
  FEE,
); // Succeeds if combined inputs cover payments+fee; the 1-sat input adds
   // ~57 vbytes of fee burden while contributing 1 sat — net-negative input
   // counted as real value.
```

The dust output is reported as received and admitted into transaction accounting despite being economically unspendable — funds "distributed" to the multisig that can never actually be claimed, mirroring rewards emitted to a contract with no stakers.
