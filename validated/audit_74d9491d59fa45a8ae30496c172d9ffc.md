### Title
Zero-amount escrow entries cause `withdraw()` to unconditionally revert, permanently locking user escrow in Tron `IntentGatewayV2` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` implements its own `withdraw()` routine that, unlike the shared EVM `IntentsBase._withdraw()`, does not skip zero-amount escrow entries. A `protocolFeeBps` value of `10000` (100%, a value inside the contract's normally accepted 0–10000 basis-point range) reduces an order's input escrow to `0` for that token at placement time. When the corresponding `RedeemEscrow`/`RefundEscrow` message later arrives and `withdraw()` iterates the order's token list, it hits the zero-balance token and reverts with `UnknownOrder()`, unwinding the entire transaction — including the transfer of every *other* legitimately-escrowed token and the transaction fee in the same call. This mirrors the referenced Popcorn bug class: a config value that is syntactically valid but semantically degenerate (`escrowPercentage`/`escrowDuration` there, `protocolFeeBps = 10000` here) causes every future claim/redeem attempt for that order to revert forever, permanently locking already-deposited funds.

### Finding Description
`placeOrder` in the Tron contract computes, per input token:
```
protocolFee = originalAmount * protocolFeeBps / 10_000
reducedAmount = originalAmount - protocolFee
``` [1](#0-0) 

and then stores the reduced amount as the tracked escrow balance for that token:
```
_orders[commitment][token] += reducedInputs[i].amount;
``` [2](#0-1) 

If `protocolFeeBps == 10_000` (100%), `reducedAmount` is exactly `0` for that token, so `_orders[commitment][token]` is recorded as `0` even though the gateway actually holds the full deposited balance (the "fee" is only ever emitted as a `DustCollected` event, not physically separated).

Later, when the order is filled or cancelled, the cross-chain settlement message triggers `withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
``` [3](#0-2) 

This check has no `amount == 0` bypass. Because `body.tokens` is built directly from `order.inputs` (the fee-reduced amounts) at redeem/refund construction time, any token whose escrow was reduced to `0` at placement will unconditionally trip `UnknownOrder()` on this loop — reverting the whole `withdraw()` call.

Contrast this with the shared, non-Tron implementation used by the main EVM contracts, which explicitly guards against this:
```solidity
if (amount == 0) continue;
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
``` [4](#0-3) 

The Tron contract's independent `withdraw()` (it does not inherit `IntentsBase`) omits this guard entirely, reintroducing the exact defect class the mainline contract was hardened against.

### Impact Explanation
Because Solidity reverts unwind the entire call, a single zero-valued token entry in an order's withdrawal poisons the redemption of *every* token in that order, plus the accumulated `TRANSACTION_FEES` transfer that happens later in the same function. Both settlement paths — `RedeemEscrow` (solver claims escrow after a successful fill) and `RefundEscrow` (user reclaims escrow after cancellation/timeout) — call the same `withdraw()`, so neither the solver nor the user can ever recover the funds for an affected order. This is a direct, permanent loss/lock of user and solver funds already custodied by the bridge contract, consistent with the "stealing or loss of funds" / "false state acceptance blocking settlement" bounty categories.

### Likelihood Explanation
Triggering the bug requires no malicious relayer, prover, or admin collusion: `protocolFeeBps` (or a per-destination override via `_destinationProtocolFees`) merely needs to be configured at `10000`, a value within the documented 0–10000 bps range, and then any ordinary user places an order — both are routine, non-privileged/non-malicious operations from the report's threat model perspective (the same way the original C4 report only needed a normal vault owner picking an in-range-but-degenerate escrow config). Given basis points commonly run in the low hundreds, a configuration or destination-override mistake landing on `10000` (or any value producing `reducedAmount == 0` for a small-value token, e.g., a token with very low decimals) is realistic operational risk, not a contrived edge case.

### Recommendation
In the Tron `IntentGatewayV2.withdraw()`, mirror `IntentsBase._withdraw()`'s guard: skip (`continue`) rather than revert when `body.tokens[i].amount == 0` (nothing to transfer for that leg), and only revert `UnknownOrder()` when a *non-zero* requested amount has no matching escrow. Additionally, consider rejecting `protocolFeeBps`/`destinationFeeBps` configuration values that would reduce any plausible input amount to `0`, or explicitly disallow `bps == 10_000`.

### Proof of Concept
1. Governance/admin sets `protocolFeeBps = 10000` (or a `DestinationFee.destinationFeeBps = 10000` override) via the standard `UpdateParams` flow.
2. A user calls `placeOrder` with an input token; `reducedAmount` computes to `0`; `_orders[commitment][token]` is stored as `0` while the contract's actual token balance still reflects the full deposit.
3. The order is filled by a solver (or times out/is cancelled), producing a `RedeemEscrow`/`RefundEscrow` message with `body.tokens` containing that token at amount `0`.
4. `onAccept` → `withdraw(body, ...)` iterates `body.tokens`; hits `_orders[commitment][token] == 0` and reverts `UnknownOrder()`, aborting the transfer of all other tokens and fees in the same order.
5. Every retry of the settlement message hits the same revert — the escrow for the entire order is permanently unredeemable by either the solver or the user.
