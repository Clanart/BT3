### Title
Operator payout tx's `SIGHASH_SINGLE|ANYONECANPAY` signature lets anyone strip the OP_RETURN and misclassify a fronted payout as optimistic - ([File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs only input0+output0 under `SIGHASH_SINGLE|ANYONECANPAY` [1](#0-0) , so the user's signature remains valid for any transaction that reuses that input and output0 while changing the remaining outputs, including dropping the mandatory OP_RETURN output that encodes the fronting operator's xonly pubkey [2](#0-1) . `update_finalized_payouts` relies solely on finding that OP_RETURN to attribute a payout to an operator, treating its absence as "must be an optimistic payout" and storing `NULL` [3](#0-2) , which can permanently strand the real fronting operator's reimbursement path.

### Finding Description
The binding claimed is: **`payout_tx has no OP_RETURN output` == `the withdrawal was authorized by N-of-N optimistic-payout MuSig2 signatures, not a single operator`**.

This binding is only sound if the OP_RETURN output is *necessarily* present whenever a single operator fronts a payout, i.e. if it's cryptographically bound to input0/output0 by the same signature that authorizes spending the withdrawal UTXO. But it is not: the operator's payout tx is signed by the withdrawing user with `TapSighashType::SinglePlusAnyoneCanPay`, which is enforced in `parse_withdrawal_sig_params` [4](#0-3) . Under `SIGHASH_SINGLE|ANYONECANPAY`, the taproot key-spend sighash for input 0 only commits to input 0 and output 0 - none of the other inputs or outputs (anchor, OP_RETURN) are covered. This is confirmed by `Operator::withdraw`, which builds a normal `payout_txhandler` (input0 = withdrawal UTXO, output0 = payout, output1 = anchor, output2 = OP_RETURN with `self.signer.xonly_public_key`) and verifies the user's signature only against `sighash_txin(0, ...)` [5](#0-4) .

Because the signature is malleable with respect to everything after output0, an unprivileged attacker who observes the operator's broadcast (but unconfirmed) payout transaction in the mempool can:
1. Copy the same input (same withdrawal outpoint) with its witness (the valid Schnorr signature + sighash byte),
2. Copy output0 exactly (same payout amount/script, required for `SIGHASH_SINGLE` binding),
3. Drop the OP_RETURN output entirely, keeping only an anchor output (2 outputs total, matching the exact shape of `create_optimistic_payout_txhandler`, which also produces exactly `[payout_output, anchor_output]` with no OP_RETURN [6](#0-5) ),
4. Attach their own additional fee input(s) if needed (permitted by ANYONECANPAY) and rebroadcast with a higher fee to get their version confirmed instead of (or racing) the operator's original.

Once this attacker-crafted transaction confirms and reaches `update_finalized_payouts`, `get_first_op_return_output` finds nothing [7](#0-6) , and the code explicitly logs "Either it is an optimistic payout or the operator constructed the payout tx wrong" and stores `operator_xonly_pk = None` in the DB [8](#0-7) . No check anywhere cross-references this against a real MuSig2/N-of-N optimistic-payout signing session (i.e. there is no verification that a genuine `Aggregator::optimistic_payout` round of signing under `sign_optimistic_payout` actually occurred for this withdrawal idx) [9](#0-8) ; the classification is based purely on transaction shape/OP_RETURN presence, which the attacker fully controls given the sighash flexibility.

### Impact Explanation
The honest operator who genuinely fronted the withdrawal's BTC (10 BTC in the example) is recorded in the database with `NULL` payer instead of their own xonly pubkey. Downstream logic that gates reimbursement/kickoff validity on matching the payer's xonly pubkey (e.g. `is_kickoff_malicious`-style logic comparing `Some(operator_xonly_pk)`) cannot match `None` to any real operator, permanently blocking that operator's `Reimburse` transaction for this withdrawal. This matches the Critical impact category: "an honest operator permanently unable to be reimbursed." Since the attack only requires observing operator payout mempool broadcasts and rebroadcasting a fee-competitive alternative, it is repeatable across every deposit/withdrawal processed by any operator that uses the normal (non-optimistic) payout path, i.e., it is not a one-off, but a systemic weakness in every non-optimistic payout.

### Likelihood Explanation
Preconditions: the attacker needs to see an operator's payout transaction before it confirms (public mempool visibility, no privileged access required) and be able to pay a higher fee to get their malleated version mined first, or exploit any confirmation race/RBF window. The attacker does not need any bridge role, key share, or collateral — only the ability to broadcast Bitcoin transactions and observe the mempool, consistent with the stated threat model. Cost is limited to fees needed to outbid the operator's payout tx (typically small relative to the multi-BTC payout amount), making this both cheap and repeatable for every operator-fronted payout observed in the wild.

### Recommendation
Do not rely solely on OP_RETURN presence/absence to distinguish optimistic vs. operator-fronted payouts. Instead, bind the payout classification to something the attacker cannot forge under `SIGHASH_SINGLE|ANYONECANPAY` malleability, e.g.:
- Require the operator's payout tx witness/signature to also cover (or be independently checked against) the OP_RETURN output (e.g. via a separate covering commitment, or use `SIGHASH_ALL` on an operator-provided second input/signature covering the full output set), or
- Cross-check in `update_finalized_payouts` whether a genuine MuSig2 N-of-N `OptimisticPayout` signing round (tracked in DB from `Aggregator::optimistic_payout`/`sign_optimistic_payout`) actually occurred for this withdrawal idx before accepting the "optimistic, no operator" classification, rather than inferring it purely from missing OP_RETURN bytes.

### Proof of Concept

Plan:
1. Set up a deposit + withdrawal as in `deposit_and_withdraw_e2e.rs`, and let an honest operator build and sign a normal `payout_tx` via `create_payout_txhandler` (input0 = withdrawal UTXO with `SinglePlusAnyoneCanPay` user sig, output0 = payout, output1 = anchor, output2 = OP_RETURN with operator xonly pk).
2. Before broadcasting the operator's tx, construct an attacker tx: same input0 (same outpoint + witness bytes), same output0, but only an anchor output (2 outputs total, no OP_RETURN) — matching `create_optimistic_payout_txhandler`'s shape.
3. Confirm the attacker's transaction (instead of the operator's).
4. Call the equivalent of `update_finalized_payouts` on the block containing it and assert `operator_xonly_pk` resolves to `None` in the payouts table (via `get_payout_txs_for_withdrawal_utxos` / `update_payout_txs_and_payer_operator_xonly_pk`).
5. Assert that downstream reimbursement logic (kickoff/reimburse validity check keyed on the payer's xonly pubkey) cannot match the honest operator's key to `None`, demonstrating the operator is permanently blocked from being reimbursed for the BTC it actually fronted.

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
