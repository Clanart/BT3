### Title
Cached FROST nonce seed is reused across multiple `sign` calls for the same attempt, enabling secret share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The Carapace bug is a failure to accumulate outstanding requests against a single resource: each withdrawal request is checked against the balance in isolation, so the same shares get pledged to multiple cycles. The Serai analog is a single secret resource — a deterministically derived FROST nonce — being consumed multiple times: `SigningProtocol::preprocess_internal` caches one preprocess seed per `(b"DkgConfirmer", attempt)` context and rebuilds the *same* nonces on every invocation, and `sign` is called more than once per attempt (`share()` and again inside `complete()`) with no check that the signed-over data is identical.

### Finding Description
`preprocess_internal` stores a `CachedPreprocess` (a ChaCha20Rng seed) keyed only by `context = (b"DkgConfirmer", self.attempt)` (signing_protocol.rs:123-145, 274-277). Every call to `share_internal` calls `preprocess_internal` again (line 156), so `AlgorithmSignMachine::from_cache` → `seeded_preprocess` regenerates bit-for-bit identical `nonces` and `commitments` (crypto/frost/src/sign.rs:121-144). `sign` then consumes this machine and produces a share over `(preprocesses, msg)` (sign.rs:283-318).

`DkgConfirmer::share` performs one `sign` (lines 288-310), and `DkgConfirmer::complete` performs a *second* `sign` via `share_internal` before assembling the signature (lines 321-326). Both signs use the same nonce pair `(d, e)` and the same published commitments `D, E`. Safety therefore depends entirely on the two calls receiving identical `preprocesses` maps and identical `msg`. Neither is enforced:

- `msg` is `set_keys_message(set, removed, key_pair)` built per call from the `key_pair` argument supplied by the tributary transaction being handled (lines 296-301). Two confirmation transactions in the same attempt carrying different `KeyPair`s produce different `msg`s under one nonce.
- `preprocesses` is rebuilt per call from transaction-supplied bytes via `threshold_i_map_to_keys_and_musig_i_map` (lines 208-250). A different signer set or different preprocess bytes changes the binding factors `ρ_i`, the `included` list, and hence the transcript challenge — while `d + ρ·e` uses the same `d, e`.

The file's own header acknowledges this is the failure mode ("the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again", lines 34-35) and admits the guard is unimplemented: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" (lines 50-54). Just as Carapace checked each request against the balance but never the sum of pending requests, each `sign` here is valid in isolation while the nonce budget is spent twice.

### Impact Explanation
Two FROST shares `z₁ = d + ρ₁e + c₁λs` and `z₂ = d + ρ₂e + c₂λs` with identical `(d, e)` but distinct binding factors or challenges let any observer solve for `e` (or `d`) and then for `λs`, the signer's secret share. Since this is the validators' MuSig key confirming DKG results on Substrate, share recovery compromises the root-of-trust signing key — equivalent to the reported bug's impact (the pledged resource — safety under the nonce — is silently double-spent). Severity: High/Critical; it produces key share recovery, which the validation rules accept.

### Likelihood Explanation
The trigger requires `share_internal` to run twice for one `attempt` with differing `preprocesses` or `key_pair`. This is not hypothetical-by-construction: `share()` and `complete()` always each invoke `sign`, and both inputs originate from tributary transaction data finalized per-attempt rather than from a stored "already-signed" record — there is no accumulation/identity check mirroring Carapace's missing total-requested check. It does require the BFT layer to admit distinct relevant messages within one attempt, which the code comments note is prevented only by consensus assumptions, not by any check in this module; the explicit TODOs confirm the defensive comparison was never written. That lowers likelihood below "always exploitable," but the missing guard is the bug, and the data path (tx-supplied `key_pair` and preprocesses) is the realistic divergence source.

### Recommendation
Before producing a share, persist what was signed: store a hash of `(sorted participants, their serialized preprocesses, msg)` alongside `CachedPreprocesses`, and make `share_internal` abort if a second call for the same context presents different bytes — i.e., account for the prior "request" against the same nonce before spending it again. This directly implements the TODO at lines 50-54 and mirrors the report's fix (check total pledged against the resource, not each request in isolation).

### Proof of Concept
1. Attempt `a` begins; `DkgConfirmer::share(preprocesses_A, key_pair_K)` runs. `preprocess_internal` creates and caches seed `S` for context `("DkgConfirmer", a)`, signs `msg₁ = set_keys_message(set, removed, K)` under nonces `(d, e)`, publishes share `z₁`.
2. In the same attempt, `DkgConfirmer::complete(preprocesses_B, key_pair_K', shares)` is reached — `share_internal` re-derives identical `(d, e)` from `S` and signs `msg₂ ≠ msg₁` (or identical msg with a different `preprocesses` map → different `ρ` values) producing `z₂`.
3. From published `z₁, z₂`, commitments, and the transcript-derived `ρ, c` values, solve the two linear equations to recover `λs`, the validator's MuSig secret share.

Caveat: I could not fully trace `handle.rs` to confirm that two txs in one attempt can present differing `key_pair`/preprocess sets to `share`/`complete` (tool iteration limit); the finding stands on the double-`sign` over one cached nonce being structurally present and explicitly unguarded per the module's own TODO.
