### Title
Git's built-in clone-time protection is explicitly disabled during recursive clone, re-opening a fixed RCE class for attacker-controlled repositories - (File: `app/src/lib/git/clone.ts`)

### Summary
Git ships an environment variable, `GIT_CLONE_PROTECTION_ACTIVE`, that Git itself sets to `true` when it invokes internal git processes (e.g. submodule clones) as part of a top-level `git clone`. This flag is part of the hardening that Git added (in the 2.45.1/2.42.3/2.39.5 etc. security releases, addressing the class of clone/submodule RCE issues such as CVE-2024-32002 "arbitrary configuration injection when cloning a specially-crafted local repository leads to arbitrary command execution during clone") to detect when git commands are running inside a clone operation and to refuse dangerous constructs (such as symlinked `.git` entries or case-folding tricks in nested/submodule repositories) that would otherwise let a malicious repository write or execute files outside the intended working tree. Desktop's `clone()` helper explicitly overrides this to `'false'` for every clone it performs, and the same call performs `--recursive` (submodule) cloning of attacker-controlled remote content.

`--recursive` means Git will also clone every submodule referenced by the top-level repository, following whatever URLs/paths the (attacker-controlled) `.gitmodules` file and tree entries specify. Git's clone-protection mechanism exists specifically to guard this operation: it is meant to prevent a maliciously crafted repository (or one of its submodules) from smuggling a `.git` file/symlink, a hooks directory, or ambiguous-case path components that get treated as live git metadata by a *nested* git invocation during the recursive clone, which historically allowed writing (and in some scenarios executing) files outside the intended repository root.

By unconditionally setting `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process's environment, Desktop tells the git binary that it should *not* apply this protection to the recursive/submodule-cloning subprocesses it spawns — effectively disabling the very hardening whose entire purpose is to defend against untrusted repository content during exactly this operation. The `isClonePathSensitive()` check immediately above it only validates the destination directory chosen by the *user*; it does nothing to constrain what a malicious remote can do to files *inside* the repository/submodule tree once the protection is turned off.

### Impact Explanation
If the underlying Git version relies on `GIT_CLONE_PROTECTION_ACTIVE` to gate the fix for the clone/submodule RCE class, a user who clones or "Open in Desktop"s an attacker-supplied repository (or a repository with an attacker-controlled fork/submodule reference, e.g. via `openRepositoryFromUrl`/CLI clone/deep link) could have that protection silently bypassed. This falls squarely in the "attacker controls a cloned/fetched repository" impact category and can lead to file writes outside the intended working tree or, on vulnerable Git builds, arbitrary command execution during the clone — i.e., the exact bug class the corresponding Git CVEs were fixed for. This is a Medium/High-severity concern because it nullifies a security control on every single clone Desktop performs, and the trigger condition (cloning any external repository with submodules) is a completely normal, unprompted user workflow.

### Likelihood Explanation
Likelihood is high in terms of reachability: every clone path in Desktop (`clone-repository.tsx` → `_clone` → `cloningRepositoriesStore` → `clone()`) goes through this exact function, including clones triggered by deep links (`x-github-client://openRepo/...`) and CLI `--cli-clone`, both of which can point at attacker-controlled URLs without requiring the user to inspect repository contents first. The actual exploitability is bounded by which Git version is bundled/available on the host — this is not verifiable from the source tree alone — and by whether upstream Git actually gates the fixed vulnerability behind this specific flag on that version (this is inferred from the known name/purpose of the variable and its documented role in Git's own security releases; I could not find a code comment or commit message in this repository confirming the original author's intent, so this should be validated against the exact `dugite`/git version Desktop bundles).

### Recommendation
- Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override entirely and let Git apply its default (protection-enabled) behavior during clone.
- If this override was added to work around a specific compatibility problem, scope it far more narrowly (e.g., only for local/trusted paths) and document the exact issue it was meant to solve, with a link to the corresponding Git/dugite issue.
- Add a regression test asserting that clones of a crafted repository containing a symlinked `.git` entry inside a submodule fail safely, rather than succeeding.
- Audit the bundled `dugite`/git version for the presence of the CVE-2024-32002-class fixes and ensure Desktop is not shipping a git version where disabling this flag has any effect.

export async function clone(

  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void

  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +

    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
