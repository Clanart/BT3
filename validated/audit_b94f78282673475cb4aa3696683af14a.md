## Analysis

**Binding claimed to hold:** `out_amount` checked by `Operator::is_profitable` at `withdraw()`-request time (`core/src/operator.rs:605-612`) == the `output[0].value` of the payout transaction that is later accepted as valid proof-of-payout by `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:137-236`) and by the operator's own on-chain payout scanner (`core/src/verifier.rs:2283-2353`, `core/src/task/payout_checker.rs`).

Tracing the code shows this binding is **not enforced anywhere after the initial `withdraw()` call**:

- `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:182-207`) only checks that `payout_spv.transaction.input[payout_input_index].previous_output` (txid+vout) matches the withdrawal outpoint proven via `verify_storage_proofs`, and that the tx has an OP_RETURN encoding *some* operator's x-only pubkey (`get_first_op_return_output`/`parse_op_return_data`). It never reads or checks `output[0].value`.
- `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) — which scans confirmed blocks and records `(payout_txid, operator_xonly_pk)` for a spent withdrawal UTXO — only reads the OP_RETURN pubkey, never the output amount.
- `is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs`) only compare `operator_xonly_pk` and the committed payout blockhash; they never re-check the amount against the amount that was validated by `Operator::is_profitable` at withdrawal time.

The withdrawal UTXO's spending authorization uses `SIGHASH_SINGLE|ANYONECANPAY` (`core/src/builder/transaction/operator_reimburse.rs:407-436`, `core/src/test/common/setup_utils.rs:499-543`), which is produced and controlled by the **withdrawing user themselves** (the party who calls `withdraw()` and supplies `in_outpoint`/`in_signature` — i.e., the unprivileged attacker in this threat model). That signature only commits to input 0 and output 0; the OP_RETURN output (which is what everything downstream keys off of to attribute the payout to an operator) is **not covered by the signature** and can be freely attached to any spending transaction of that same UTXO.

Consequently, the attacker — who owns the private key of their own withdrawal dust UTXO — can:
1. Request a withdrawal on Citrea for the full bridge amount, registering `withdrawal_utxo` = their own dust UTXO.
2. Before (or via RBF instead of) any operator's real payout confirms, broadcast their **own** self-signed transaction spending that same UTXO with `output[0]` reduced to a negligible amount (e.g., 1 sat, to themselves) and an OP_RETURN naming an arbitrary (even totally uninvolved, honest) operator's public x-only key.
3. Once mined, the honest operator's own automation (`update_finalized_payouts` → `PayoutCheckerTask` → `handle_finalized_payout`) will treat this as "operator X fronted this withdrawal" purely from OP_RETURN + outpoint match, and proceed with kickoff/reimbursement for the full bridge amount — without ever checking that `output[0].value` matches the amount `is_profitable` was supposed to gate.

This breaks the claimed binding and is independently reachable from `bridge_circuit`'s own guarantees, matching the Critical impact categories "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal" / "an operator reimbursed for a payout it never funded," and also "an honest operator permanently unable to be reimbursed" for the operator that was supposed to actually service the withdrawal (their real payout tx can no longer be confirmed once the outpoint is already spent). ### Title
Payout output amount never re-validated after `is_profitable` — attacker can spend own withdrawal UTXO with near-zero output and arbitrary operator OP_RETURN to trigger unfunded reimbursement / permanently consume the withdrawal slot - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`Operator::is_profitable` is checked only once, at `withdraw()`-request time, against the `out_amount` the caller supplies; neither `bridge_circuit` nor the operator/verifier's on-chain payout scanners (`update_finalized_payouts`, `is_kickoff_malicious`, `PayoutCheckerTask`) ever re-check the confirmed payout transaction's output value. Because the withdrawal UTXO is signed by the withdrawing user with `SIGHASH_SINGLE|ANYONECANPAY` (which does not cover the OP_RETURN output), the user can unilaterally spend that same UTXO with a negligible-value output and an arbitrary operator's OP_RETURN, permanently consuming the withdrawal slot and/or tricking that operator's automation into claiming reimbursement for a payout it never made.

### Finding Description
The binding `out_amount checked by is_profitable == output[0].value of the confirmed payout tx accepted by bridge_circuit/protocol` does not hold. `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:137-236`) only asserts that `payout_spv.transaction.input[payout_input_index].previous_output` matches the withdrawal outpoint proven by `verify_storage_proofs` (txid/vout only) and that an OP_RETURN encodes a 32-byte x-only pubkey used to compute `deposit_constant`; `output[0].value` is read nowhere in the function. The same is true of the operator-side automation: `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) records `(payout_txid, operator_xonly_pk)` from the OP_RETURN alone, and `is_kickoff_malicious`/`PayoutCheckerTask` (`core/src/verifier.rs:1857-1915`, `core/src/task/payout_checker.rs:39-111`) only compare the recorded `operator_xonly_pk` and payout blockhash, never the amount.

The withdrawal UTXO (`in_outpoint`, `in_signature`) supplied to `withdraw()` is controlled by the withdrawing user (an unprivileged attacker per the threat model): `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) spends it via `SpendPath::KeySpend` using `user_sig` with `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP-341/143 commits only to input 0 and the output at the *same index* (output 0); it does not commit to the OP_RETURN output or to any additional funding inputs the operator adds via `fund_raw_transaction`.

Exploit flow: the attacker registers a withdrawal for the full amount on Citrea using their own dust UTXO, then — instead of letting the real operator's fee-funded payout confirm — broadcasts (or RBF-replaces it with) their own fully self-signed transaction spending only that dust UTXO, with `output[0]` set to a negligible amount payable to themselves and an OP_RETURN naming any operator's x-only pubkey. This transaction requires no cooperation from any operator, since the OP_RETURN is unconstrained by the user's signature. Once mined, `bridge_circuit` accepts this as a valid payout SPV proof for that operator (all its checks pass), and the named operator's own `PayoutCheckerTask`/state machine will automatically proceed to kickoff and claim reimbursement for the full bridge amount, having never actually funded any withdrawal to the user.

Existing guards do not catch this: `Operator::is_profitable` only runs on the *operator's own* candidate `out_amount` at request time and is bypassed entirely by an attacker-authored competing transaction; `SECP.verify_schnorr` only checks the (input,output0) commitment, which the attacker validly re-signs themselves; `Verifier::is_kickoff_malicious` and `verify_storage_proofs` never inspect the payout amount.

### Impact Explanation
- BTC leaves a move-to-vault UTXO (via the reimbursement flow) without a matching real fronted withdrawal payment to the user — Critical.
- An operator (even one that never attempted the payout) is reimbursed for a payout it never funded — Critical.
- The withdrawal's designated outpoint is consumed by the attacker's own low-value transaction, so the intended/real operator can never construct a valid competing payout tx for that withdrawal afterward — an honest operator permanently unable to be reimbursed for that withdrawal — Critical.
- Repeatable per withdrawal and independent of which operator is targeted (attacker just needs any operator's public x-only key, which is public protocol data); blast radius spans all deposits/withdrawals and all operators.

### Likelihood Explanation
The only precondition is that the caller can request a withdrawal on Citrea (unprivileged) and control the private key of the dust UTXO they nominate as `in_outpoint` (which is standard, expected user behavior in this design — the user is meant to hold that key). Cost is a single dust-UTXO-funded Bitcoin transaction fee; no operator, verifier, or aggregator collusion, no privileged key, and no mainnet/live Citrea dependency is required to demonstrate the missing-amount-check defect (regtest is sufficient). This is fully feasible and repeatable.

### Recommendation
Bind the confirmed payout transaction's output amount to the amount that was actually approved (either the amount checked by `Operator::is_profitable`, stored per-withdrawal in the operator DB, or a value independently derivable/committed on the Citrea side) and re-validate it: (1) in `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`), assert `payout_spv.transaction.output[0].value` against a committed/verified expected amount before computing `deposit_constant`/journal hash; (2) in `update_finalized_payouts`/`is_kickoff_malicious` (`core/src/verifier.rs`), reject or flag as malicious any payout tx whose output value doesn't match the amount recorded for that withdrawal at the time it was accepted; (3) consider requiring the withdrawing user's SIGHASH to also cover (or otherwise binding) the OP_RETURN so third parties/other spends of the same UTXO cannot attribute payment to an arbitrary operator.

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {

            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.

                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
