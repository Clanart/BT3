Audit Report

## Title
Unbounded per-key growth in `SecondaryIndex` lets an unprivileged attacker force disproportionately expensive `getTokenAccountsByOwner`/`getProgramAccounts` scans against a victim key - (File: accounts-db/src/accounts_index/secondary.rs)

## Summary
`RwLockSecondaryIndexEntry::insert_if_not_exists` grows the `account_keys: HashSet<Pubkey>` for an outer key with no upper bound, and the outer key used in `SecondaryIndex::insert` is taken directly from unauthenticated, attacker-controlled account data (`owner`/`mint` fields) rather than any privileged or self-referential value. Because `keys()` and `SecondaryIndex::get` fully materialize the entire set into a `Vec<Pubkey>` on every lookup, an unprivileged actor can cheaply create many accounts whose `owner`/`mint` field points at an arbitrary victim pubkey, inflating that pubkey's index entry, and later force disproportionately expensive `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` scans against the victim key on any RPC node running with the corresponding secondary index enabled.

## Finding Description
`RwLockSecondaryIndexEntry` stores `account_keys: RwLock<HashSet<Pubkey>>` [1](#0-0) , and `insert_if_not_exists` unconditionally inserts new inner keys into this set with no cap on its size [2](#0-1) . `SecondaryIndex::insert` calls this for every `(key, inner_key)` pair without checking any size limit on the existing entry before inserting [3](#0-2) . The outer `key` for `IndexKey::ProgramId`/`SplTokenOwner`/`SplTokenMint` is derived from the account's own `owner`/token `owner`/`mint` byte fields, which are set by whoever creates the account and are not validated to belong to or be controlled by the entity being indexed. This lets any unprivileged party create many accounts that "point at" a victim pubkey they do not control, incrementing that pubkey's `account_keys` set each time.

The only existing size-related guard is `AccountSecondaryIndexes::include_key`, which excludes specific pre-configured keys from being indexed at all [4](#0-3)  — it is a static allow/deny-list, not a bound on how many entries an included key can accumulate. `SecondaryIndex::get` retrieves the full set at once via `inner_keys_map.keys()` [5](#0-4) , and `keys()` clones the entire `HashSet` into a `Vec<Pubkey>` in one call [6](#0-5) . This is invoked from `AccountsIndex::get_index_key_pubkeys`, reachable from `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` RPC handlers per the claim's cited call chain through `get_filtered_indexed_accounts`/`load_by_index_key_with_filter`.

I was able to fully confirm the core mechanism in `secondary.rs` (unbounded `HashSet` growth at write time, full materialization via `keys()`/`get()` at read time, and the `include_key` guard being a static allow/deny-list rather than a size cap) directly from the source. I was not able to fully re-verify the exact byte-limit semantics in `accounts.rs`'s `load_by_index_key_with_filter` or the precise RPC call chain in `rpc.rs` within the available tool budget, but the cited line ranges from the claim for those files are consistent with the general architecture (the `byte_limit_for_scan` parameter bounding only the aggregate bytes of *loaded* accounts, not the initial index-key fan-out) and match well-known Agave RPC index-scan code structure.

## Impact Explanation
An attacker can permissionlessly and cheaply (bounded only by normal, fixed, low-cost account creation) inflate the `account_keys` set for an arbitrary owner/program/mint pubkey to an arbitrarily large size. A subsequent `getProgramAccounts`, `getTokenAccountsByOwner`, or `getTokenAccountsByDelegate` request against that key on an RPC node with the corresponding index enabled (`--account-index program-id|spl-token-owner|spl-token-mint`) must clone the full set and then load/filter every referenced account, causing disproportionate CPU, memory, and latency cost on that node for what appears to be a normal read request against an innocent key. This matches the "single-client low-rate RPC crash/degradation" impact category, since it degrades a specific RPC node's ability to serve requests without requiring any validator/peer trust assumption.

## Likelihood Explanation
Likelihood is moderate and configuration-gated: the vulnerable path only executes on nodes that have opted into `AccountsIndex::ProgramId`/`SplTokenOwner`/`SplTokenMint`, which is common for RPC nodes that need to serve these exact query types efficiently. Creating attacker accounts with an arbitrary `owner`/`mint` field requires no special privilege — only the normal fixed cost of account creation via the System/SPL-Token programs — and requires no leaked keys, malicious validators, or trusted plugins.

## Recommendation
- Enforce a per-outer-key maximum on `inner_keys` in `SecondaryIndex::insert`/`RwLockSecondaryIndexEntry::insert_if_not_exists`, rejecting or evicting further insertions once a cap is reached.
- Independently, enforce a hard cap on the number of pubkeys returned by `AccountsIndex::get_index_key_pubkeys`/`SecondaryIndex::get`/`keys()` before any account-loading work begins, distinct from the existing `byte_limit_for_scan`, which only bounds total loaded-account bytes and not the initial index-key fan-out.
- Consider requiring some form of relationship/authentication between the outer key and the entries it accumulates where feasible (e.g., for `SplTokenOwner`, this is inherent to the SPL Token account model and cannot be authenticated at the index layer, so a cap is the practical mitigation).

## Proof of Concept
1. Attacker submits many transactions creating SPL-token-account-shaped accounts (or program-owned accounts) whose `owner` (or `mint`) field is set to `victim_pubkey`, an address the attacker does not control. Each insertion calls `SecondaryIndex::insert(key=victim_pubkey, inner_key=new_account)` [7](#0-6) , growing `victim_pubkey`'s `account_keys` `HashSet` without limit via `insert_if_not_exists` [2](#0-1) .
2. A test can directly exercise `SecondaryIndex::insert` in a loop with a fixed outer key and N distinct inner keys, then call `SecondaryIndex::get`/`keys()` and observe the returned `Vec<Pubkey>` length and clone cost scale linearly and unboundedly with N [5](#0-4) .
3. On an RPC node with the corresponding index enabled, any client calling `getTokenAccountsByOwner(victim_pubkey, ...)`/`getProgramAccounts(victim_pubkey, ...)` triggers a lookup that must materialize and process the entire inflated set, causing amplified CPU/memory cost for what looks like a normal request against `victim_pubkey`.

    fn insert_if_not_exists(&self, key: &Pubkey, inner_keys_count: &AtomicU64) {
        if self.account_keys.read().unwrap().contains(key) {
            // the key already exists, so nothing to do here
            return;

        }

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }
