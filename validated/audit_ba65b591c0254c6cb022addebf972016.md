### Title
Deterministic CachedPreprocess reuse signs multiple times with identical FROST nonces — key-share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a 32-byte seed in `CachedPreprocesses` and reconstructs the `AlgorithmSignMachine` via `AlgorithmSignMachine::from_cache` on *every* signing call. `seeded_preprocess` seeds `ChaCha20Rng` from that seed, so all FROST nonces `(d, e)` are deterministically regenerated identically each call. The FROST spec in this repo explicitly states a cached preprocess "MUST only be used once" and that reuse "enables recovery of your private key share" (`crypto/frost/src/sign.rs:209-224`, `spec/cryptography/FROST.md:51-55`). `DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal` → `preprocess_internal`, signing with the same nonce material more than once within a single attempt.

### Finding Description
- `preprocess_internal` writes the cache only if absent, then always loads it and calls `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (coordinator/src/tributary/signing_protocol.rs:123-145).
- `from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed(*seed.0)` → `Commitments::new` → two `C::random_nonce` calls (crypto/frost/src/sign.rs:121-144, crypto/frost/src/nonce.rs:53-71). Same seed ⇒ same `d`, `e`.
- `share_internal` calls `self.preprocess_internal(participants).0` then `machine.sign(preprocesses, msg)` (signing_protocol.rs:156-170). `DkgConfirmer::share` calls it once; `DkgConfirmer::complete` calls `share_internal` *again* to rebuild the machine (signing_protocol.rs:321-326), and both take attacker-influenced `preprocesses: HashMap<Participant, Vec<u8>>` and `key_pair` arguments.
- Each produced share is `s_i = d + ρ_i·e + c_i·λ·x` where `ρ` binds the preprocess set and `c = HRAm(R, A, msg)` (crypto/frost/src/sign.rs:362-398, crypto/frost/src/nonce.rs:180-212). The signing set and `msg = set_keys_message(..., key_pair)` are inputs to each call, so `ρ_i`/`c_i` vary across invocations while `d`, `e`, and `λ·x` are fixed.

### Impact Explanation
Any participant whose preprocess is included (or anyone who can drive a distinct signing set/message into `share` vs `complete`, e.g. differing `key_pair` or accumulated preprocess set) obtains multiple shares over the same `(d, e)`. Each share is a linear equation in the three unknowns `(d, e, λ·x)`; `λ` (Lagrange coefficient) is public, so collecting a few such shares — across `share`, `complete`, and repeated handling of the same attempt context `(b"DkgConfirmer", attempt)`, which keeps the identical seed — lets an unprivileged party solve for `λ·x` and hence the validator's MuSig secret key share `x`. This is full key-share recovery, the exact consequence the inline documentation warns about.

### Likelihood Explanation
The reuse is not conditional: `share_internal` regenerates the same nonces every call by construction, and `complete` unconditionally performs a second `sign`. Whether the emitted shares diverge depends only on the preprocess set or message differing between calls — both are externally supplied inputs (`preprocesses` map contents, `key_pair`), so a malicious participant can submit a different set for `complete` than for `share`. Additionally, on reboot or re-driven handling the DB-resident seed is reused again, providing further equations.

### Recommendation
Never re-derive a signing machine from a persisted seed after a `sign` has been produced. Either (a) persist the `AlgorithmSignatureMachine` state instead of the preprocess seed, or (b) include a monotonically increasing per-invocation counter in `context` and strictly refuse a second `share_internal` for a context already signed under — e.g., record a `SignedFor(context)` flag in `CachedPreprocesses` and abort `share_internal` if set, while keeping `complete` able to reconstruct via a stored machine rather than re-signing.

### Proof of Concept
1. `DkgConfirmer::share(preprocesses_A, key_pair)` → `share_internal` → `preprocess_internal` decrypts stored seed `s` → `from_cache` → nonces `(d, e)` → emits `s_1 = d + ρ_A·e + c_1·λ·x`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair', shares)` → calls `share_internal` again → same seed `s` → same `(d, e)` → emits `s_2 = d + ρ_B·e + c_2·λ·x`.
3. A third invocation (re-execution of `share`/`complete` under the same `(b"DkgConfirmer", attempt)` context — the cache is never deleted at signing_protocol.rs:134) yields `s_3`. Solve the 3×3 linear system in `(d, e, λ·x)`; divide by the public `λ` to recover the share `x` of the victim validator's key.
