## Title
Credential helper trusts a spoofable `WWW-Authenticate` realm header (a single self-reported "oracle") instead of a verified round-trip check, letting an attacker-controlled git host masquerade as GitHub Enterprise and trigger Desktop's native Enterprise sign-in flow - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`StableOracleWBTC` priced WBTC purely from a single, unverified data source (the BTC/USD Chainlink feed) instead of cross-checking a second, independent oracle, so if that one source diverged from reality the protocol kept trusting it. The Desktop analog is `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts`, which decides whether an unknown host git is talking to should be treated as a **GitHub Enterprise** endpoint. The function has two ways to reach that conclusion: (1) a real network round-trip to the candidate host that checks for the `x-github-request-id` response header (`isGitHubHost`, `app/src/lib/api.ts:2429-2492`), and (2) a "happy path" shortcut that simply trusts a `WWW-Authenticate` header value the remote server itself sent back during the failed git auth attempt. That header is attacker-controlled data, yet it alone is enough to flip the classification to `'enterprise'` and skip the verified check entirely.

### Finding Description
In `getEndpointKind`: [1](#0-0) 

the comment itself states the intent: *"We use them as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves."* If any `wwwauth[]` entry captured from the remote server's HTTP response contains the substring `realm="GitHub"`, the endpoint is classified `'enterprise'` immediately - the verified network check (`isGitHubHost`, which requires the server to answer with the real `x-github-request-id` header on a `/meta` request) is never reached: [2](#0-1) 

This is the single-oracle problem: the `WWW-Authenticate` header is fully controlled by whatever server git is talking to (a malicious HTTPS remote, a MITM-capable proxy, or a spoofed corporate git server a user is pointed at via a crafted remote URL). Any server can 401 a git credential request with `WWW-Authenticate: Basic realm="GitHub"` and be believed, with zero verification that it is actually GitHub Enterprise.

The consequence of being classified `'enterprise'` (i.e., not `'generic'`) shows up in `getCredential`: [3](#0-2) 

If no existing account matches that endpoint, Desktop calls `ui.promptForGitHubSignIn(endpoint)`, which routes into the app's real Enterprise sign-in UI: [4](#0-3) 

Because `hostname !== 'github.com'`, this calls `dispatcher.beginEnterpriseSignIn(cb)` and `dispatcher.setSignInEndpoint(origin)` using the attacker's origin - Desktop's own trusted, native "Sign in to GitHub Enterprise" dialog is now scoped to an arbitrary attacker-controlled host, based solely on a header that host chose to send.

### Impact Explanation
This does not require DNS hijacking or credential compromise: the attacker only needs to control (or MITM/proxy) a git remote that the victim clones/fetches from or adds. By returning one spoofed header on the initial HTTPS auth challenge, the attacker can:
- Force Desktop's built-in, trusted-looking Enterprise sign-in chrome to open against their server, increasing phishing credibility (native app UI rather than a browser tab a user might scrutinize).
- Cause Desktop to skip its only real verification step (`isGitHubHost`'s live `/meta` request that checks for the genuine `x-github-request-id` header), so the "double-oracle" safeguard the codebase already has for other classification paths is bypassed for this one.
- Any credentials/PAT the user enters in that flow, or any OAuth/device authorization the user approves believing it's for a legitimate Enterprise server, is exfiltrated to the attacker.

This maps directly to the report's impact category: token/credential exfiltration and unauthorized OAuth/account binding via an attacker-controlled git remote/proxy response, with no privileged access or pre-existing compromise required.

### Likelihood Explanation
Any git server (self-hosted, proxy, or MITM position on an unencrypted/misconfigured network) can return a `WWW-Authenticate` header value under its own control on a 401 response to a credential-fill request. The check is a plain substring match (`v.includes('realm="GitHub"')`) with no origin, TLS-certificate, or content validation tying the claim to an actual GitHub product, so triggering the vulnerable path is trivial for any attacker-run server that a user is induced to add as a remote or clone from.

### Recommendation
Do not let a self-reported `WWW-Authenticate` realm value alone elevate an unknown host to `'enterprise'` status. Treat the header as, at most, a hint to *prioritize* running the existing verified check (`isGitHubHost`) rather than as a substitute for it - i.e., require the live `/meta` request (checking `x-github-request-id`) to succeed before classifying an unrecognized host as GitHub Enterprise, mirroring the "double oracle" pattern recommended in the source report: never let a single, attacker-influenceable signal be sufficient for a security-critical trust decision.

### Proof of Concept
1. Stand up an HTTPS git server (or a MITM proxy in front of any HTTP git remote) that responds to unauthenticated `git fetch`/`git clone` requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim add this server as a remote (e.g. `git remote add origin https://attacker.example.com/foo.git`) and perform a fetch/clone in Desktop.
3. Git captures the `WWW-Authenticate` header and forwards it to Desktop's credential trampoline as a `wwwauth[]` field, per `getCredentialUrl`/`parseCredential` in the trampoline protocol.
4. `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:153-165`) matches `realm="GitHub"` and returns `'enterprise'` without ever calling `isGitHubHost`.
5. Since no account exists for `attacker.example.com`, `getCredential` (lines 109-124) invokes `ui.promptForGitHubSignIn('https://attacker.example.com')`, which opens Desktop's native "Sign in to GitHub Enterprise" dialog scoped to the attacker's origin, ready to receive/forward the victim's credentials or authorize an OAuth flow against the attacker's server.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }
