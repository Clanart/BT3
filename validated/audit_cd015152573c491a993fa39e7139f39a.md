### Title
`unvote` reverts exactly for inactive pools, permanently locking users' vlMGP voting allocation and blocking `startUnlock` - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.unvote` is documented to let users unvote from a pool that has been deactivated (e.g. when the admin removes/reconfigures a pool), so that users are never blocked from reclaiming their voting allocation. The actual guard does the opposite: it reverts precisely when the pool is inactive, so once a pool is deactivated, any user who previously voted for it can never call `unvote` on it again. Because `userTotalVotedInVlmgp` and `userVotedForPoolInVlmgp` are never decremented in this case, the user's `vlMGP` (and `mWomSV`) locked tokens tied to that vote can never be unlocked, since `startUnlock` checks the post-unlock locked amount against `userTotalVotedInVlmgp`.

### Finding Description
`unvote` is intended to allow withdrawal of vote allocation from inactive pools, per its own NatSpec: [1](#0-0) 

```solidity
/// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    if(!pool.isActive)
        revert PoolNotActive();
    ...
}
```

The check `if(!pool.isActive) revert PoolNotActive();` reverts the transaction exactly when the pool is inactive — the opposite of what the comment says the function is for. As a result, once a pool's `isActive` flag becomes `false`, no user who voted for it can ever call `unvote(_lp)` to zero out `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` or reduce `userTotalVotedInVlmgp[msg.sender]`.

This is analogous to the reported bug class: a piece of per-user/per-pool state that is supposed to be reset under a specific condition is instead never reset in that exact branch, permanently blocking a downstream operation (in the original report, `reported[poolId]`; here, the user's committed vote allocation).

The downstream impact is that `VLMGP.startUnlock` (and the analogous `mWomSV.startUnlock`) enforces that a user cannot start unlocking more vlMGP than what is not currently committed to bribe voting: [2](#0-1) 

```solidity
function startUnlock(uint256 _amountToCoolDown) external override whenNotPaused nonReentrant {
    if (_amountToCoolDown > getUserTotalLocked(msg.sender))
        revert NotEnoughLockedMPG();

    uint256 totalLockAfterStartUnlock = getUserTotalLocked(msg.sender) - _amountToCoolDown;
    if (address(wombatBribeManager) != address(0) && 
        totalLockAfterStartUnlock < IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender))
        revert NotEnoughLockedMPG();
```

Since `userTotalVotedInVlmgp[msg.sender]` can never be decreased for votes cast toward a pool that has been deactivated (because `unvote` reverts for exactly that state), the portion of a user's locked vlMGP that was voted for that pool is permanently unreachable through `startUnlock`, freezing those tokens in the locker indefinitely.

### Impact Explanation
This causes a permanent freeze of user funds: any vlMGP a user voted toward a pool that is later deactivated becomes permanently unlockable, since the accounting variable gating `startUnlock` can never be reduced for that pool. This is a direct, unprivileged-wallet-reachable freeze of funds exceeding 24 hours (permanent, absent a contract upgrade).

### Likelihood Explanation
Pool deactivation is a normal, expected lifecycle operation for bribe pools (removing stale pools, changing rewarders) and any user who voted for a pool prior to its deactivation is unconditionally affected the next time they try to unvote or unlock — no special conditions or races are needed to trigger it.

### Recommendation
Invert the guard so that `unvote` succeeds only when appropriate, e.g. remove the `!pool.isActive` revert entirely (or restrict the "active" check to `vote`, not `unvote`), so users can always reduce `userVotedForPoolInVlmgp` / `userTotalVotedInVlmgp` and reclaim the ability to unlock their vlMGP, matching the function's documented intent.

### Proof of Concept
1. User calls `vote([lp], [delta>0])`, which increases `pool.totalVoteInVlmgp`, `userVotedForPoolInVlmgp[user][lp]`, and `userTotalVotedInVlmgp[user]` [3](#0-2) .
2. Admin later deactivates pool `lp` (setting `poolInfos[lp].isActive = false`, e.g. via pool removal/reconfiguration).
3. User calls `unvote(lp)` to reclaim their vote allocation; the call reverts with `PoolNotActive()` because `pool.isActive` is now `false` [4](#0-3) .
4. `userTotalVotedInVlmgp[user]` remains permanently inflated by the amount voted for the now-dead pool.
5. User calls `VLMGP.startUnlock` for their full locked balance; the call reverts with `NotEnoughLockedMPG()` because `totalLockAfterStartUnlock` can never drop below the stuck `userTotalVotedInVlmgp[user]` value [5](#0-4) , permanently freezing that portion of the user's vlMGP.
