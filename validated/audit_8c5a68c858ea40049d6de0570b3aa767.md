### Title
Process-global `allow_oversize_protos` flag lets one thread silently disable the recursion-depth safety check for concurrent, unrelated `ParseFromString`/`MergeFrom` calls in other threads - ([File: python/google/protobuf/pyext/message.cc])

### Summary
In the CPython C-extension (`_message`) implementation of protobuf, `MergeFromStringImpl` determines the recursion depth passed into `internal::ParseContext` from a single process-wide `static bool allow_oversize_protos` variable, not from any per-call, per-thread, or per-message state. [1](#0-0) [2](#0-1) [3](#0-2) 

`SetAllowOversizeProtos()` is a public module-level function (also mirrored in the upb-backed Python extension as `PyUpb_SetAllowOversizeProtos`) that mutates this global without any synchronization or scoping to the calling thread, message, or parse operation. [4](#0-3) 

### Finding Description
The invariant that fails to hold, by analogy to the curl CVE, is: *a safety-relevant configuration toggle intended to control the behavior of one operation/handle must not leak into and affect other concurrently executing operations sharing the same process.* In curl, an LDAPS TLS option set on one `curl_easy` handle in one thread was implemented via a global OpenLDAP TLS context instead of a per-connection context, so it silently altered certificate verification for other threads' unrelated transfers.

The analog in this checkout is `allow_oversize_protos` in `python/google/protobuf/pyext/message.cc:404-408`. This boolean is read directly (not passed through any per-call argument, ContextVar, or thread-local) inside `MergeFromStringImpl`, which is the function backing the public `ParseFromString`/`MergeFromString` APIs used by ordinary client code parsing untrusted, bounded protobuf bytes: [5](#0-4) 
```
int depth = allow_oversize_protos
                ? INT_MAX
                : io::CodedInputStream::GetDefaultRecursionLimit();
...
internal::ParseContext ctx(depth, false, &ptr, ...);
```
The recursion-depth limit exists specifically "to prevent corrupt or malicious messages from causing stack overflows" during recursive/embedded-message and group parsing. [6](#0-5) 

`SetAllowOversizeProtos()` is exposed as an ordinary Python-callable module function with zero locking or thread-affinity and unconditionally overwrites this single global for the entire process: [7](#0-6) 

Because the flag is process/module-global rather than scoped to the `CMessage`, the `ParseContext`, or the calling thread, any code path in the process (a library, a dependency, test helper, or any thread) that calls `SetAllowOversizeProtos(True)` — even transiently, e.g., to parse one specific oversized-but-trusted message — removes the recursion/stack-overflow protection for every other concurrently-executing `ParseFromString`/`MergeFrom` call on *any* message class, in *any* thread, for the duration the flag is set. This mirrors the curl invariant failure exactly: a locally-scoped intent ("allow this one deep message") is implemented as a global mutable switch, so concurrent unrelated operations inherit the weakened security posture without their own knowledge or consent.

The existing test suite for this exact code path only exercises single-threaded, sequential toggling of the flag (set → parse → unset), and never validates behavior when the flag is toggled concurrently with an in-flight parse on another thread: [8](#0-7) [9](#0-8) 
This demonstrates the check was never designed with concurrent-caller isolation in mind — the same failure category (per-handle option silently becoming global) as the curl bug.

### Impact Explanation
When `allow_oversize_protos` is `True` at the moment a `ParseFromString`/`MergeFrom` call executes on any message in any thread, the recursion depth passed to `ParseContext` becomes `INT_MAX` instead of the default 100-level limit (`io::CodedInputStream::GetDefaultRecursionLimit()`), so nested/recursive message or group structures are parsed with no meaningful bound. [10](#0-9) 
An ordinary client sending a bounded but deeply-nested protobuf payload through the public `ParseFromString` API, concurrently with any other in-process thread that has (even momentarily) enabled `allow_oversize_protos` for its own purposes, would have its recursion check silently disabled — reintroducing the class of stack-overflow/crash risk that the recursion limit exists to prevent, for input the parser's own default policy was supposed to reject. This is an integrity failure of a documented safety check (analogous to CVSS C:H/I:H in the curl advisory, where a verification check silently stops applying to concurrent operations), not a resource-exhaustion/huge-input scenario, since the bypass is triggered by ordinary bounded input coinciding with another thread's legitimate use of the same API.

### Likelihood Explanation
Exploitability depends entirely on the consuming application: it requires (a) multiple threads sharing one Python process using the C++/upb-backed `_message` extension, and (b) some code path in that process calling `SetAllowOversizeProtos(True)` (even for a narrow, seemingly safe purpose) while other threads are concurrently parsing attacker-supplied bytes. This is plausible in real multi-threaded services that expose this documented but explicitly-discouraged API (`message.cc:398-403` warns "please do not enable this unless you fully understand the implications"), making it a Medium-likelihood, application-composition-dependent issue rather than a directly, unilaterally triggerable vulnerability from the parse API alone — consistent with the CVSS 6.3/Medium severity and `AC:H`/`UI:R`-style qualifiers of the source advisory.

### Recommendation
Scope the recursion-limit override to the specific `ParseContext`/call (e.g., a parameter on `MergeFromStringImpl`/`ParseFromString`, or a thread-local/ContextVar) rather than a single process-wide `static bool`. At minimum, document and enforce that `SetAllowOversizeProtos` must not be called while other threads may be parsing, and consider deprecating the flag in favor of an explicit per-call recursion-limit argument (mirroring `CodedInputStream::SetRecursionLimit`, which is at least instance-scoped) so no global toggle can affect concurrent, unrelated parse operations.

### Proof of Concept
Not independently executed in this review (no test runner available in this pass); the following reproduces the structural issue based on the existing test harness pattern:
1. Thread A calls `google.protobuf.pyext._message.SetAllowOversizeProtos(True)` to parse one large, trusted message it controls.
2. Concurrently, Thread B calls `SomeMessage().ParseFromString(attacker_supplied_bytes)` on bytes containing 10,000+ levels of nested/recursive groups that would normally be rejected by the default 100-level recursion limit (as exercised by `testAssertOversizeProto`/`testRecursiveGroupsException` in `message_test.py:2253-2263` and `message_test.py:3917-3923`, but run concurrently instead of sequentially).
3. Because `depth` in `MergeFromStringImpl` (`message.cc:2106-2108`) is read from the shared global at the moment Thread B's parse executes, Thread B's parse proceeds with `INT_MAX` depth instead of raising `DecodeError` ("too many levels of nesting"), exactly as the existing sequential tests demonstrate the flag changes acceptance/rejection behavior — the only missing element for a full empirical reproduction is running Threads A and B concurrently, which the current test suite (`minimal_test.py:129-154`) does not do.
