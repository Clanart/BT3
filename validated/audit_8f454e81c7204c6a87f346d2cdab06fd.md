## Title
Relayer fee accounting is zeroed before destination settlement is confirmed, letting withdrawals become permanently stuck against a depleted shared balance - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
This is a local analog of the USDMPegRecovery `withdraw()` bug: an internal ledger promises a balance that is redeemable from a shared token reserve, but the reserve is not earmarked per-claimant. When the reserve is insufficient at settlement time, the withdrawal fails/stalls, while the internal ledger has already been irreversibly updated as if payment succeeded.

### Finding Description
In `Pallet::withdraw` [1](#0-0) , a relayer's accrued fee balance `Fees::<T>::get(dest_chain, address)` is read, then an ISMP `DispatchPost` is fired to the destination chain's `HostManager`/module carrying a `WithdrawalParams { beneficiary_address, amount, token }` payload with `timeout: 0` [2](#0-1) . Immediately after the dispatch call succeeds (i.e., is merely *accepted* by the local ISMP router, not confirmed delivered/executed on the destination), the pallet unconditionally zeroes the relayer's ledger entry:

```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
``` [3](#0-2) 

On the EVM destination side, actual settlement happens later when `EvmHost.withdraw()` is invoked by the `HostManager`:

```solidity
function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
    if (params.token == address(0)) {
        (bool sent,) = params.beneficiary.call{value: params.amount}("");
        if (!sent) revert WithdrawalFailed();
    } else {
        IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
    }
    ...
}
``` [4](#0-3) 

`EvmHost` holds a single, communal `feeToken` balance that is not earmarked per relayer or per accrued claim — it is simply whatever balance happens to sit in the contract. There is no reservation, escrow-per-claim, or balance check performed on the Hyperbridge side before the ledger is zeroed. This is architecturally identical to `USDMPegRecovery.withdraw()`: internal per-user accounting (`userLiquidity`/`totalLiquidity` there, `Fees` here) assumes funds are always available from a pool, but the pool's actual balance can be smaller than the sum of all outstanding internal claims against it, because the pool is shared and drained by whichever withdrawal executes first (or by other legitimate consumers of the same balance, e.g. protocol-fee `Withdraw` actions routed through the very same `EvmHost.withdraw()` entrypoint via `HostManager.onAccept` [5](#0-4) ).

The relayer withdrawal documentation itself confirms the "will not timeout" design, meaning the request just sits pending forever if it cannot execute successfully:

> "This request will not timeout, allowing it to be submitted to the destination chain at any time." [6](#0-5) 

Because `Fees` is zeroed and the relayer's per-`(address, dest_chain)` `Nonce` is incremented at dispatch time (not at confirmed delivery time) [7](#0-6) , the relayer cannot re-submit a fresh `withdraw` for the same amount even if the first attempt never lands. Its only recovery path is a permissionless relayer eventually re-delivering the *same* pending, un-timeboxed POST request once `EvmHost`'s `feeToken` balance happens to be replenished — which is exactly the "withdraw() may often fail" pattern from the seed report, just shifted from a Curve pool to a shared cross-chain fee-token reserve.

### Impact Explanation
Relayers who have legitimately earned and accumulated fees can have their claim silently zeroed on Hyperbridge while the actual payout on the destination chain fails or is delayed indefinitely because the shared `feeToken` balance in `EvmHost` is insufficient at the moment of execution. This is a loss/lock of funds for the rightful beneficiary (the relayer), triggered purely by ordinary, permissionless relayer activity (concurrent withdrawals draining a shared pool) — no malicious peer, prover, or admin action is required.

### Likelihood Explanation
Multiple relayers accrue and withdraw fees against the same per-destination-chain `feeToken` balance. Any period of low fee replenishment relative to withdrawal demand (heavy relayer competition, uneven cross-chain traffic, or normal chain-balance fluctuation) causes the destination `EvmHost.withdraw()` call to revert on `safeTransfer` due to insufficient balance, while the Hyperbridge-side `Fees` entry has already been irreversibly zeroed at dispatch time. This requires no special conditions beyond normal multi-relayer operation, making it moderately likely to occur in production once fee volumes and relayer counts scale.

### Recommendation
Do not zero `Fees` (or otherwise finalize the ledger) until destination-side settlement is confirmed. Options:
- Track withdrawals as "pending" rather than zeroing balance immediately, and only clear the ledger entry once a delivery-confirmation callback/response is received from the destination.
- Alternatively, have `EvmHost`/`HostManager` emit a callback/response (success or failure) back to Hyperbridge so the relayer pallet can re-credit the `Fees` balance if the destination transfer reverts, instead of relying on indefinite retried delivery of an un-timeboxed request with an already-zeroed source-side ledger.

### Proof of Concept
1. Relayer A accrues `1000` fee-token worth of claims on Hyperbridge for `dest_chain = EVM(1)` via `accumulate_fees`.
2. Relayer B also accrues `1000` fee-token worth of claims for the same `dest_chain`. The destination `EvmHost` currently only holds `1000` fee-token total.
3. Relayer A calls `withdraw_fees` first: `Fees::<T>::get` returns `1000`, `Fees` is zeroed [8](#0-7) , and a POST request for `1000` is dispatched with `timeout: 0`.
4. Relayer A's request is delivered and executed on `EvmHost`, draining the entire `1000` balance via `safeTransfer` [4](#0-3) .
5. Relayer B calls `withdraw_fees`: `Fees` is zeroed and nonce incremented exactly as for A, and a POST request for `1000` is dispatched.
6. When B's request reaches `EvmHost.withdraw()`, `IERC20.safeTransfer` reverts (balance is `0`), so `HostManager.onAccept` reverts and delivery fails. Relayer B's `Fees` ledger is already `0` and nonce already incremented — B cannot resubmit a new withdrawal for the same amount, and can only wait for some future relayer to redeliver the same un-timeboxed pending request once/if `EvmHost` is refunded by unrelated future traffic.

        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

To initiate a withdrawal from hyperbridge, a relayer needs to submit a transaction to hyperbridge which triggers the withdrawal request.
