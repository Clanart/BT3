## Title
Stale `DiffSelection` line-index reuse in `applyPatchToIndex` allows attacker-controlled repository content changes to silently corrupt partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
`FluidEPProgramManager.cancelProgram()` breaks because it recomputes a value (`initialDeposit`) at execution time using external mutable state (governance params) instead of the value that was valid when the object was created (fund time), causing mismatches between what was expected and what actually happens. The Desktop analog is `applyPatchToIndex()` in `app/src/lib/git/apply.ts`, which recomputes the diff of a file at *staging/commit time* via `getWorkingDirectoryDiff(repository, file)` (line 60) and then reuses the `file.selection` bitmap of line indices that was captured earlier when the user reviewed and checked/unchecked lines in the Changes view. If the file content on disk has changed between the moment the user made their line selection and the moment the commit is executed, the line indices in the old selection no longer correspond to the same content in the newly-fetched diff, producing a silently wrong patch that is applied to the index and committed.

### Finding Description
`DiffSelection` in GitHub Desktop stores per-line inclusion state keyed by absolute line index into a specific diff (`hunk.unifiedDiffStart + lineIndex`), as seen in `formatPatch()`: [1](#0-0) 

That selection is built against the diff that was rendered in the UI at some earlier point. Desktop is aware that "the diff might have changed dramatically since last we loaded it" and defensively recomputes `selectableLines` when refreshing the *displayed* diff: [2](#0-1) 

However, this reconciliation only touches which lines remain *selectable*; it does not run again immediately before a commit is created. When the commit is actually performed, `stageFiles()` iterates over files with partial selections and calls `applyPatchToIndex()`: [3](#0-2) 

`applyPatchToIndex()` fetches a **fresh** diff right there, at staging time: [4](#0-3) 

and then builds the patch to `git apply --cached` using `file.selection` (the possibly-stale bitmap) against this newly-fetched diff: [5](#0-4) [6](#0-5) 

If the working-tree file was modified between "user reviews/selects lines" and "user clicks Commit" — e.g. by a build tool, file watcher, editor auto-format-on-save, or (in the threat model of this exercise) a script/hook shipped inside a cloned/fetched attacker-controlled repository that touches tracked files shortly after checkout/fetch — the hunk boundaries and absolute line indices shift. The stale bitmap is then applied against different content, silently including/excluding the wrong lines. `git apply --unidiff-zero` further reduces context validation, making the malformed patch more likely to apply without error rather than fail loudly. This exactly mirrors the underlying flaw class in the report: **recomputing a derived value from external state that is assumed static but is not**, without persisting/validating the value captured at selection time.

### Impact Explanation
This corrupts *what the user actually commits*, one of the explicitly valid impact categories: "silent corruption of what the user commits or pushes." A user could believe they are committing only reviewed/selected lines, while unrelated or attacker-influenced content is silently included in (or excluded from) the commit, without any error being surfaced, since `git apply --cached` normally succeeds when the underlying content still parses as a valid patch.

### Likelihood Explanation
The precondition is a change to a tracked file's content between the time a partial/line-level selection was made in the Changes view and the time the commit executes. This is realistic in ordinary developer workflows (auto-formatters, linters running on save, background build watchers, npm/yarn scripts triggered by an attacker-controlled `package.json`/hook in a cloned repo) and does not require local/physical access, admin rights, or leaked credentials — only that the user has the repository open and is doing a partial commit while some process (which the attacker can plant in the cloned repository, e.g. via `postinstall`/watch scripts) mutates a tracked file in the window between selection and commit.

### Recommendation
Before calling `applyPatchToIndex`, re-fetch the diff for each partially-selected file and validate/remap the `DiffSelection` against the current diff (reusing the existing `selectableLines`/line-matching logic already used for UI refresh), or abort/warn the user if the file changed since selection instead of silently applying a stale bitmap to new content. Alternatively, capture and diff-content-hash the working tree file at selection time and compare it against the content at staging time, refusing to stage (and asking the user to re-review) on mismatch.

### Proof of Concept
Not executed (analysis based on static code review only). A reproduction outline: 1) modify a tracked file with several hunks and select only some individual lines for commit in the Changes view; 2) before clicking "Commit", programmatically rewrite the same file (simulating an attacker script/hook) so that hunk boundaries shift; 3) commit — `applyPatchToIndex` (`app/src/lib/git/apply.ts:60,80-81`) fetches the new diff but reuses the old `DiffSelection` bit indices, producing a patch whose staged content does not match the lines the user actually selected.
