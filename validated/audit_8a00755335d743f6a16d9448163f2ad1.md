### Title
Attacker-controlled `_minMGPRec` combined with unprotected spot-price AMM swap in `_bullMGP()` allows self-sandwich price manipulation to inflate locked MGP beyond fair BUSD value - ([File: wombat/ArbWomUp2.sol])

### Summary
`incentiveDeposit(..., _bullMode=true)` calls `_bullMGP()`, which swaps the caller's fixed BUSD reward for MGP via `ROUTER.swapExactTokensForTokens` using a slippage parameter (`_minMGPRec`) fully controlled by the caller, and then locks `amounts[1] * bonus` MGP into `vlMGP` for `msg.sender`. Because the caller both supplies the trade's minimum-output guard and triggers the exact block/transaction in which the swap executes, they can manipulate the BUSD/MGP pool price around their own call (temporarily cheapening MGP, executing the swap, then restoring price) to make `amounts[1]` reflect far more MGP than the BUSD reward is fairly worth, and lock that inflated amount for voting/reward weight.

### Finding Description
In `_bullMGP()` (`wombat/ArbWomUp2.sol:162-181`), the swap uses `path = [busd, mgp]` and passes `_minRec` straight from the caller-supplied `_minMGPRec` argument of `incentiveDeposit` (`wombat/ArbWomUp2.sol:82-97`, `168-174`). There is no TWAP, oracle cross-check, or minimum enforced by the contract itself — the caller can legally pass `_minMGPRec = 0`, disabling all slippage protection for their own transaction.

Because `msg.sender` both (a) determines the BUSD amount being swapped (fixed by their tier reward, unaffected by MGP price) and (b) fully controls the transaction/bundle in which the swap runs, they can:
1. Move the BUSD/MGP pool price so that MGP is temporarily cheap in BUSD terms (e.g., dumping MGP into the pool, or via flash-loaned liquidity/large trade).
2. Call `incentiveDeposit(amount, 0, true)` in the same block/bundle so `ROUTER.swapExactTokensForTokens` executes at the manipulated price, making `amounts[1]` (and thus `mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR`) larger than the fair-value MGP the fixed BUSD reward should buy.
3. Restore the pool price (sell back / unwind flash loan), pocketing the trade profit while the contract has already locked the inflated `mgpAmountToLcok` into `vlMGP.lockFor(mgpAmountToLcok, _account)` for the attacker's own address.

No modifier in `incentiveDeposit` (`nonReentrant`, `whenNotPaused`, `_checkAmount`) prevents this, since none of them check trade fairness — they only guard reentrancy/pausing/zero-amount. The vulnerability's root cause is entirely internal to `ArbWomUp2`: trusting caller-supplied slippage input for a self-triggered swap with no independent fair-value check.

### Impact Explanation
This results in vote-weight inflation and unclaimed-yield theft: the attacker receives more locked MGP (and thus more `vlMGP` voting/reward weight) than their BUSD reward entitles them to, at the AMM pool's/LPs' expense, while the protocol's own incentive/reward-to-MGP conversion is bypassed. This matches the "theft or permanent freezing of unclaimed yield" and "governance voting result manipulation" impact classes.

### Likelihood Explanation
Exploitability depends entirely on the depth/manipulability of the actual BUSD/MGP pool behind `ROUTER`. If that pool has shallow liquidity relative to available flash-loan capital, an attacker can atomically bundle: manipulate price → call `incentiveDeposit` with `_minMGPRec = 0` → unwind, all unprivileged and self-triggered (no front-running of a third party required, since the attacker calls the vulnerable function themselves). This is fully repeatable per deposit up to the attacker's WOM/reward tier limits.

### Recommendation
- Do not let the caller set `_minMGPRec`; compute an on-chain minimum from a manipulation-resistant reference (e.g., time-weighted average price/oracle, or a fixed bound derived off-chain by the owner and enforced as a floor).
- Consider replacing the instantaneous router swap with a TWAP-based conversion or capping per-block deviation between `amounts[1]` and an internally tracked reference price before locking into `vlMGP`.

### Proof of Concept
Foundry fork test outline:
1. Fork BSC/Arbitrum mainnet at a block where the real BUSD/MGP Pancake-style pool exists (or deploy a mock pool with realistic reserves).
2. Deploy `ArbWomUp2`, configure `busd`, `mgp`, `vlMGP`, `bullBonusRatio`, `ROUTER` via `setup`.
3. Fund the contract with BUSD and set `rewardMultiplier`/`rewardTier` so an attacker's WOM deposit yields a known `rewardToSend`.
4. Baseline: call `incentiveDeposit(amount, fairMinRec, true)` without manipulation; record `mgpAmountToLcok` from `VLMGPRewarded` event as `baselineMGP`.
5. Attack: in one transaction (via an attacker contract that flash-loans MGP or BUSD), swap a large amount into/out of the BUSD/MGP pool to depress MGP price, then call `incentiveDeposit(amount, 0, true)`, then swap back to restore price.
6. Assert `mgpAmountToLcok` (from the `VLMGPRewarded` event) in the attack scenario is significantly greater than `baselineMGP` for the same `rewardToSend`, demonstrating locked-MGP value exceeds fair BUSD-equivalent value. [1](#0-0) [2](#0-1)

    function _bullMGP(uint256 _busdAmount, uint256 _minRec, address _account) internal {
        IERC20(busd).safeApprove(address(ROUTER), _busdAmount);
        
        address[] memory path = new address[](2);
        path[0] = busd;
        path[1] = mgp;
        uint256[] memory amounts = ROUTER.swapExactTokensForTokens(
            _busdAmount,
            _minRec,
            path,
            address(this),
            block.timestamp
        );

        uint256 mgpAmountToLcok = amounts[1] * (DENOMINATOR + bullBonusRatio) / DENOMINATOR; // get bull mode bonus
        IERC20(mgp).approve(address(vlMGP), mgpAmountToLcok);
        vlMGP.lockFor(mgpAmountToLcok, _account);

        emit VLMGPRewarded(_account, _busdAmount, mgpAmountToLcok);
    }
