## Title
Missing upper-bound/range validation in ProtoJSON `Timestamp` parsing allows syntactically well-formed but semantically invalid dates to be silently accepted — (File: `src/google/protobuf/json/internal/parser.cc`, mirrored in `upb/json/decode.c`, `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

## Summary
The reported Chainlink issue is a "check one side, forget the other" defect: `answer <= 0` is validated but the aggregator's `minPrice`/`maxPrice` sanity bounds are never checked, so an out-of-range value is silently treated as valid and propagated to callers. The Protobuf analog is `ParseTimestamp` (and its `upb`-based counterparts used by Python/Ruby/PHP), which validates that individual date components are *present* (non-empty, non-zero) but never validates that they are *in range* (month 1–12, day 1–31, hour 0–23, minute/second 0–59), and only enforces a *lower* bound on the final computed `seconds` value while never enforcing the documented *upper* bound (year 9999 / `253402300799`). A syntactically well-formed RFC3339 string with out-of-range calendar fields is accepted and silently converted into a `Timestamp.seconds` value that does not correspond to any real date, exactly mirroring the oracle's "wrong value returned as if valid" failure mode.

## Finding Description
`ParseTimestamp` in `src/google/protobuf/json/internal/parser.cc` extracts year/month/day/hour/minute/second via `TakeTimeDigitsWithSuffixAndAdvance`, checking only that year/month/day are non-zero: [1](#0-0) 
It then computes `secs` using a Julian-day-style formula that assumes valid calendar ranges, applies a timezone offset, and stores the result without ever checking the final `secs` against the documented maximum (`253402300799`, corresponding to `9999-12-31T23:59:59Z`), unlike `WriteTimestamp` in the unparser, which enforces both bounds explicitly: [2](#0-1) [3](#0-2) 

The same pattern exists in the `upb` JSON decoder shared by the Python/Ruby/PHP bindings. `jsondec_tsdigits` merely parses N raw digits with no range validation on the resulting integer: [4](#0-3) 
`jsondec_timestamp` feeds these unchecked month/day/hour/minute/second values directly into `jsondec_unixtime`/`jsondec_epochdays`, and afterwards checks only the *lower* bound, never the upper bound: [5](#0-4) 
Identical logic is vendored into the PHP and Ruby native extensions: [6](#0-5) [7](#0-6) [8](#0-7) 

By contrast, `ParseDuration` in the same C++ file does enforce both bounds symmetrically (`secs > kMaxSeconds || secs < -kMaxSeconds`): [9](#0-8) 
This asymmetry (Duration checks both bounds; Timestamp checks neither the calendar-component ranges nor the upper seconds bound) is the direct analog of the audit finding: one guard rail exists (`answer <= 0` / lower timestamp bound), but the paired guard rail (`maxPrice` / upper timestamp bound and component-range validation) is missing, so bad data is not rejected — it's silently accepted as a legitimate value.

## Impact Explanation
An ordinary client sending a bounded ProtoJSON payload containing a `google.protobuf.Timestamp` field (a Well-Known Type commonly used for expiry times, issuance times, TTLs, and replay-protection windows in consuming applications) can supply a string such as `"9999-99-99T99:99:99Z"`. This string:
- passes the `str.size < 20` length check,
- passes the fixed `-`, `T`, `:`, `Z` separator checks,
- passes the "non-zero" checks on year/month/day,
- is never checked against the documented maximum Timestamp value or valid calendar ranges,

and is converted into a `Timestamp.seconds`/`nanos` pair that does not represent the input date at all — an out-of-range, essentially "wrong" value is silently returned to the calling application as a successfully parsed `Timestamp`, exactly as the oracle silently returns `minPrice` for a crashed price. Any consuming application logic that trusts this `Timestamp` (expiry/TTL checks, cache invalidation, audit/log ordering, signature validity windows) can make incorrect decisions based on the corrupted value — this is a data-integrity failure reachable purely through the public JSON/ProtoJSON parsing API, not a crash or memory-safety issue.

## Likelihood Explanation
High likelihood of reachability: `Timestamp` is a first-class Well-Known Type parsed automatically whenever a message field of that type is present in ProtoJSON input, requiring no special configuration. The attacker fully controls the JSON string content and only needs to match the fixed digit-count/separator format — no privileged access, hostile schema, or resource exhaustion is required, satisfying the "ordinary client sending bounded ProtoJSON" threat model.

## Recommendation
Add explicit range validation for each date/time component in `TakeTimeDigitsWithSuffixAndAdvance`/`jsondec_tsdigits` call sites (month 1–12, day 1–31 depending on month/leap year, hour 0–23, minute 0–59, second 0–60), and add an explicit upper-bound check on the final computed `secs` value symmetric to the one already present in `ParseDuration`/`WriteTimestamp` (i.e., reject `secs > 253402300799` in addition to the existing `secs < -62135596800`/`secs < TakeTimeDigitsWithSuffixAndAdvance` lower check), applied consistently in `src/google/protobuf/json/internal/parser.cc::ParseTimestamp`, `upb/json/decode.c::jsondec_timestamp`, and the vendored copies in the PHP/Ruby extensions.

## Proof of Concept
Given a trusted schema with a message field `google.protobuf.Timestamp ts = 1;`, parse the following ProtoJSON via the public `JsonStringToMessage` (C++) or the equivalent Python/Ruby/PHP `Message.FromJsonString` API:
```json
{"ts": "9999-99-99T99:99:99Z"}
```
- The string is 20 characters, matches the fixed `YYYY-MM-DDTHH:MM:SSZ` shape (dashes, `T`, `Z` in the right positions), so it passes all structural checks in `ParseTimestamp`/`jsondec_timestamp`.
- `mon=99`, `day=99`, `hour=99`, `min=99`, `sec=99` are never range-checked.
- The resulting `secs` (computed via the Julian-day formula with out-of-range inputs) is never checked against the documented maximum (`253402300799`).
- The call succeeds (`absl::OkStatus()` / no `jsondec_err`), and `msg.ts()` contains a `Timestamp` whose `seconds`/`nanos` do not correspond to `9999-99-99T99:99:99Z` or any valid date, yet the API reports success — directly analogous to the oracle returning `minPrice` for a below-range price instead of reverting.

static int jsondec_tsdigits(jsondec* d, const char** ptr, size_t digits,
                            const char* after) {
  uint64_t val;
  const char* p = *ptr;
  const char* end = p + digits;
  size_t after_len = after ? strlen(after) : 0;

  UPB_ASSERT(digits <= 9); /* int can't overflow. */

  if (jsondec_buftouint64(d, p, end, &val) != end ||
      (after_len && memcmp(end, after, after_len) != 0)) {
    jsondec_err(d, "Malformed timestamp");
  }

  UPB_ASSERT(val < INT_MAX);

  *ptr = end + after_len;
  return (int)val;
}

  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

    jsondec_err(d, "Timestamp out of range");
  }
