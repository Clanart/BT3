### Title
`checkoutBranch`/`checkoutCommit` can be forced to enable `protocol.file.allow=always` for submodule updates, letting an attacker-controlled repository read arbitrary local paths into the working tree - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` runs `git submodule update --init --recursive` after every checkout/pull/clone, and optionally prepends `-c protocol.file.allow=always` when the caller passes `allowFileProtocol: true` [1](#0-0) . This flag is threaded through `checkoutBranch` and `checkoutCommit` from a boolean parameter that a caller controls [2](#0-1) [3](#0-2) . When enabled, Git's default protection against the `file://` submodule protocol (added to close the CVE-2017-1000117/2018 class of submodule protocol-confusion bugs) is disabled for that operation.

### Finding Description
The report's "broken invariant" is: **an untrusted, attacker-controlled input (a message/commit) can trigger a privileged/destructive action with no access-control gate.** The Desktop analog is: **the content of a cloned/checked-out repository (`.gitmodules`) is attacker-controlled, yet Desktop can be made to process it with Git's `file://` protocol safety-guard disabled**, allowing a submodule URL to point at an arbitrary local path (e.g. `file:///home/user/.ssh`, `file://C:/Users/<user>/AppData/...`, or any other directory readable by the OS user) instead of a legitimate remote.

Normally Git refuses `file://`/local-path submodule URLs during `submodule update --init` unless `protocol.file.allow` is explicitly set to `always`, precisely to stop a cloned repo's `.gitmodules` from being able to make Git "clone" (i.e., copy) arbitrary local paths into the working directory. Desktop's `updateSubmodulesAfterOperation` explicitly re-enables this dangerous behavior via the `allowFileProtocol` flag [4](#0-3) , and this flag is plumbed all the way from `checkoutBranch`/`checkoutCommit` [5](#0-4) [6](#0-5) , i.e. it is decided at the call site, not derived from any validation of the actual submodule URLs that will be processed. The `.gitmodules` file and submodule URLs are attacker-controlled content in a cloned/fetched repository, and there is no check anywhere in `submodule.ts` or `checkout.ts` that restricts the `file://` targets to paths inside the repository, or that the submodule points to the same host/trust domain as the parent remote.

### Impact Explanation
If `allowFileProtocol` is set to `true` for a checkout/branch-switch on a repository the attacker controls the content of (fork, malicious clone URL, or any repo whose maintainers can push `.gitmodules` changes), the attacker can direct `git submodule update` to read from any local directory the Desktop process can access (SSH keys, credential caches, config directories, other repositories on disk) and materialize that content as tracked files inside the victim's working directory. Because Desktop's UI would then show these files as ordinary "submodule content," a user could inadvertently commit and push them, resulting in **credential/token exfiltration** and **silent corruption of what the user commits/pushes** — both impact categories called out as valid in this assessment. This mirrors the "51% attack" report's theme: an untrusted, attacker-supplied artifact (there: a signed message; here: a `.gitmodules` submodule URL) is processed by a code path that has no access-control/allow-list around a destructive/sensitive operation (there: slashing; here: local-file submodule cloning).

### Likelihood Explanation
Exploitation depends on Desktop actually calling `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` for a repository whose `.gitmodules` is attacker-controlled. Verifying the exact call sites where `true` is passed (versus the default `false`) requires reading the full call graph in `app/src/lib/stores/app-store.ts` and `dispatcher.ts`, which was not fully covered in the indexed snippets — the tool results only showed the definitions in `checkout.ts`/`submodule.ts` and did not surface a caller passing `true` outside of tests. Because of this, likelihood cannot be conclusively confirmed from the index alone; it may be gated to a narrow "trusted/local repo" scenario (e.g., only used for repositories already known to be local forks) rather than being reachable from an arbitrary remote clone.

### Recommendation
- Never allow `protocol.file.allow=always` to be enabled based on caller intent alone; instead validate that any `file://` submodule URL resolves to a path inside the repository's own directory tree before permitting the update, or drop the flag entirely and require explicit user confirmation with a warning UI (similar to the existing "unsafe repository" warning in `app/src/ui/add-repository/add-existing-repository.tsx`).
- Audit all call sites of `checkoutBranch`/`checkoutCommit` and `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is never derived from data that originates in the attacker-controlled repository content, and is never set to `true` for repositories cloned from third-party/untrusted remotes.
- Add regression tests asserting that `git submodule update` fails (rather than silently reading local files) when a `.gitmodules` file points at a sensitive local path and the calling context is a remote/untrusted repository.

### Proof of Concept
Conceptual PoC (exact reachability from a remote clone in the running app could not be fully confirmed from the indexed code):
1. Attacker crafts a repository whose `.gitmodules` defines a submodule with `url = file:///Users/victim/.ssh` (or any sensitive local directory).
2. Victim clones or fetches this repository into GitHub Desktop and performs a checkout/branch switch that internally calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` [2](#0-1) .
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive` [7](#0-6) , which Git executes without its normal `file://` protection, materializing the contents of `/Users/victim/.ssh` (or other targeted path) as tracked submodule content in the victim's working directory.
4. The victim's next commit/push can leak this content to the remote.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
```
