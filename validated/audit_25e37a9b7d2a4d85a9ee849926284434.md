### Title
Shared `BalanceHandler.prevEventsLen` cursor is corrupted by recursive/nested precompile calls, causing permanent desync between `x/bank` balances and EVM `StateDB` balances - (File: `precompiles/common/balance_handler.go`)

### Summary
This is the closest scoped analog to the reported `ClientCommunityState::update` bug: a single mutable "checkpoint" value (the Deriverse `rate`, here the `BalanceHandler.prevEventsLen` event-log cursor) is read and subsequently used to compute a delta (dividends there; bank-event-to-StateDB balance deltas here) without guaranteeing the checkpoint reflects the correct scope of the *current* operation. In Deriverse, an intervening hour advances the true rate but the stale cached rate is used. Here, an intervening *nested/recursive precompile call* advances/overwrites the shared cursor, so the outer call computes its balance delta over the wrong slice of the event log.

### Finding Description
`BalanceHandler` (`precompiles/common/balance_handler.go:37-41`) is a small stateful helper used by precompiles to translate `x/bank` `EventTypeCoinSpent`/`EventTypeCoinReceived`/`precisebank.EventTypeFractionalBalanceChange` events into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) 

`BeforeBalanceChange` unconditionally overwrites `prevEventsLen` with the *current* length of the event manager's event slice, and `AfterBalanceChange` later replays only the events appended after that recorded index into the StateDB: [2](#0-1) 

If a single `BalanceHandler` instance is shared across a call chain that re-enters a precompile (e.g., a precompile call whose Cosmos-SDK message execution or callback logic triggers another EVM call into the *same* precompile, as exercised by the `StakingReverter`/nested try-catch pattern and the `DistributionCaller` "before/after" transfer patterns present in this repo's test suites), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a later index. The inner call's own `AfterBalanceChange` then consumes and applies events up to that point. When control returns to the *outer* call and it invokes its own `AfterBalanceChange`, it slices events starting from the inner call's index — which is now past some or all of the events that belong to the outer call's own balance-changing bank operation. Those outer-call bank events are silently skipped and never applied to the `StateDB`.

This is functionally identical in class to the report: a shared mutable "checkpoint" (`rate` / `prevEventsLen`) gets updated by an intervening operation, and a *different* logical unit of work (a user's dividend delta / the outer call's balance delta) is computed against the wrong checkpoint, producing incorrect final values for one party while another effectively gets a windfall or a loss.

This exact defect is already called out by name in this repository's own regression test: [3](#0-2) 

The reproduction harness registers a debug precompile and a caller contract that performs a recursive `callback` invocation, then asserts the number of debug-precompile events and the resulting native balances: [4](#0-3) 

### Impact Explanation
`AfterBalanceChange` is the mechanism that keeps the EVM-visible `StateDB` balance (used for all subsequent EVM opcodes/reads within the same transaction, and ultimately committed to consensus state) synchronized with the authoritative `x/bank` ledger updated by precompile-triggered Cosmos messages (staking delegate/undelegate, distribution reward withdrawal, WERC20 deposit/withdraw, precisebank fractional transfers, etc.). If a nested/recursive precompile invocation causes an outer call's bank-event delta to be skipped:
- The `StateDB` balance for an account can diverge irreversibly from its true `x/bank` balance for the remainder of the transaction and any state committed from it, i.e., accounting corruption of spendable user value across native and EVM balance representations.
- Depending on which side of the transfer is skipped, this can manifest as funds appearing to vanish from the EVM-visible balance (freezing/loss for the user) or, conversely, as native funds being debited from `x/bank` while the EVM `StateDB` balance is never decremented — leaving the caller with unspent EVM balance to reuse in the same or later calls, which is an extraction/duplication of spendable value.

This satisfies the Critical-impact bar ("irreversible accounting corruption of spendable user value across native balances, EVM balances... or precompile-mediated assets").

### Likelihood Explanation
Triggering requires only ordinary, unprivileged transaction flow: any external account or contract calling a precompile in a way that results in re-entrant/recursive invocation of the same (or another) precompile that shares a `BalanceHandler` instance across the call stack — the repository's own test contracts (`StakingReverter.sol` nested try/catch delegation calls, `DistributionCaller.sol` before/after-transfer patterns) demonstrate this exact call shape is already exercised in normal usage/testing, and a dedicated regression test in `evmd/tests/integration/balance_handler/balance_handler_test.go` exists specifically because this recursive-call scenario was observed to desync balances. This indicates the trigger path is realistic and not merely theoretical.

### Recommendation
- Do not share a single `BalanceHandler` instance (or its `prevEventsLen` field) across nested/recursive precompile invocations. Use a call-stack-scoped list/stack of checkpoints (push on `BeforeBalanceChange`, pop on the matching `AfterBalanceChange`) so each nesting level replays only its own slice of events, analogous to fixing the Deriverse bug by refreshing `rate` before every delta computation rather than relying on a shared stale value.
- Alternatively, create a fresh `BalanceHandler` per precompile invocation frame (via the existing `BalanceHandlerFactory`) and ensure it is threaded through recursive calls without being clobbered by inner invocations, verifying via invariant checks that `sum(StateDB balances)` equals `sum(x/bank balances)` after every top-level EVM transaction in CI.

### Proof of Concept
The repository already contains a working proof-of-concept for this class of issue: `evmd/tests/integration/balance_handler/balance_handler_test.go` deploys a "debug precompile caller" contract that performs recursive `callback` calls into a debug precompile, and asserts on the resulting event counts to detect the desync (`prevEventsLen` overwritten by inner calls). Extending this harness with real fund-moving precompiles (e.g., a contract that calls `WithdrawDelegatorReward` or the WERC20 precompile recursively from within a `try/catch` similar to `StakingReverter.sol`/`DistributionCaller.sol`), then comparing `bankKeeper.GetBalance` against the EVM `StateDB`/ERC-20-visible balance for the involved addresses after the outer call completes, would concretely demonstrate the balance divergence.

func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
