## Analysis

`FeeHandler::on_executed` in [1](#0-0)  extracts the reward beneficiary purely from `messages[0]`: if it is a `Message::Consensus`, the pallet hashes `consensus_msg.consensus_proof` with keccak256 and recovers an sr25519 public key from `consensus_msg.signer` via `Signature::verify_and_get_sr25519_pubkey`. No check ties this recovered key to:

- the extrinsic `origin` that called `handle`/`handle_messages`,
- a registered/whitelisted relayer, or
- the entity whose consensus/state proof actually produced the `StateMachineUpdated` events being rewarded.

The recovered key is then used directly as `relayer_account` and threaded through `process_message` in [2](#0-1) , which transfers the calculated reward from treasury and emits `RelayerRewarded { relayer: relayer_account, .. }` ( [3](#0-2) ), and mints reputation tokens to the same account.

Because `Signature::verify_and_get_sr25519_pubkey` only proves that *some* keypair signed keccak256 of the supplied `consensus_proof` bytes — not that this keypair produced, submitted, or paid for that proof — anyone who can see the `consensus_proof` bytes (which must be public in order to be verified on-chain at all) can trivially sign that hash with their own throwaway key and place the result in the `signer` field of a `Message::Consensus` at position 0 of a batch. Reward routing is completely decoupled from the actual proof-relaying identity. This matches the Required-Impact category of "wrong beneficiary ... broken ... reward accounting."

I could not fully verify (within available context) the exact semantics of the `handle`/`handle_messages` extrinsic in `pallet-ismp` — specifically whether it is a signed, single-origin call (in which case the caller who crafts the batch and the "attacker" are the same account, and the caller could always route rewards to themselves regardless of message authorship) or whether it permissionlessly aggregates independently-authored messages from different sources into one call. This distinction affects how directly a *third-party's* work can be hijacked versus a caller merely rewarding themselves for a batch they assembled and submitted. Given the pallet explicitly uses a `signer` field distinct from `origin` (and dispatches with `Pays::No`), the design intent appears to be that reward attribution must not depend on the calling origin — otherwise the `signer`/signature mechanism inside `Message::Consensus` would serve no purpose.

### Title
Unauthenticated `signer` field in `Message::Consensus` lets any unprivileged caller redirect relayer rewards to an arbitrary account - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`Pallet::on_executed` derives the relayer reward beneficiary solely from a self-generated signature over `keccak256(consensus_proof)` supplied in the first message of a batch, with no binding to the extrinsic origin, a registered relayer, or the party that actually produced/delivered the proof.

### Finding Description
`on_executed` ( [4](#0-3) ) treats `messages[0]` as an oracle for "who did the relaying work" purely by checking that a decodable `Signature` in `consensus_msg.signer` verifies against `keccak256(consensus_msg.consensus_proof)`. This is a self-signature: the attacker supplies both the message bytes and the signature, so any keypair can pass this check for any `consensus_proof` value they know. The proof itself does not have to be the one that produced the rewarded `StateMachineUpdated` events — the code aggregates the highest `latest_height` per state machine from `events` separately ( [5](#0-4) ) and pays whichever `relayer_account` was derived from `messages[0]`, decoupled from which message in the batch actually advanced consensus.

### Impact Explanation
The reward transfer and `RelayerRewarded` event beneficiary ( [3](#0-2) ) and the reputation mint ( [6](#0-5) ) go to whatever key the attacker chooses, regardless of who actually did the consensus-proof relaying/verification work for that batch. This directly steals treasury-funded relayer rewards and reputation credit meant for legitimate relayers.

### Likelihood Explanation
Exploitation requires only crafting a `Message::Consensus` with an arbitrary `consensus_proof` and a self-produced `Signature` over its hash — no special privilege, registered relayer status, or origin match is required. The main open question is the precise batching/authorization model of `pallet-ismp`'s `handle` extrinsic (single-origin vs. aggregated multi-origin messages), which determines whether this is exploitable against a genuinely distinct victim relayer in a single unprivileged call.

### Recommendation
Bind the reward beneficiary to a value that cannot be freely chosen by the message crafter: e.g., require `consensus_msg.signer` to match the extrinsic's `ensure_signed` origin, or require the signer to be a member of a registered relayer set, or otherwise cryptographically bind the signature to the specific proof-verification event/commitment being rewarded rather than to arbitrary attacker-supplied bytes.

### Proof of Concept
As suggested: construct a batch where a real state-machine-update message is included together with a crafted `Message::Consensus` whose `consensus_proof` is arbitrary bytes and whose `signer` is `Signature` computed by the attacker's own keypair over `keccak256(consensus_proof)`; call `on_executed`/the pallet dispatch, and assert `RelayerRewarded.relayer` is the attacker's account rather than the account of whoever actually relayed the real proof.

**Caveat:** I was unable to fully confirm from the indexed code whether `pallet-ismp`'s message-handling extrinsic allows a single unprivileged caller to combine another party's independently-authored, still-unprocessed proof messages into their own batch call (which would make the "stolen reward from a genuine relayer" scenario cleanly non-front-running), versus the caller always being the one assembling/submitting the entire batch (in which case rewarding "whoever calls the extrinsic" is closer to expected behavior). Confirming the exact call/authorization model of `handle`/`handle_messages` in `modules/pallets/ismp` would require deeper file access than what the index returned.

		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,

			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,

				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});

	fn on_executed(

	) -> DispatchResultWithPostInfo {
