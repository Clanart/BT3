### Title
Panic (assertion failure) on duplicated `EncryptionKeyMessage` registration crashes the DKG participant — denial of service via crafted PedPoP message flow - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The CVE-2018-20190 bug class is a crash on attacker-controlled input (NULL pointer dereference → process termination). In Serai's Rust codebase, the reachable analog is a panic on an invariant derived from untrusted DKG protocol messages. `Decryption::register` in `crypto/dkg/pedpop/src/encryption.rs` asserts that a participant's encryption key is registered at most once:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

A faulty participant who broadcasts a second `EncryptionKeyMessage<C, M>` under the same `Participant` index triggers this `assert!`, panicking the receiving node. The same file contains a second panic-on-untrusted-state primitive: `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (line 388), which panics if the `decryptor` participant never registered an encryption key.

### Finding Description

- `EncryptedMessage::read` / `EncryptionKeyMessage::read` (encryption.rs:57, 171) accept arbitrary untrusted bytes and deserialize them without issue — the crash is not in byte parsing but in the state transition applied afterward.
- `Encryption::register` (line 452) forwards each received `EncryptionKeyMessage` to `Decryption::register` (line 351), which enforces single registration with `assert!` rather than returning an `Err`/rejecting the message. There is no deduplication or error path; duplication is a hard abort.
- The `Commitments` documentation (crypto/dkg/pedpop/src/lib.rs:98-101) acknowledges that "any participant [sending] multiple sets of commitments... are faulty" and says networking-level deduplication "lies with the caller," but the `register` assert fires regardless of commitment-set duplication — a participant can resend only the `EncryptionKeyMessage` wrapper and still crash the callee.
- Additionally, `decrypt_with_proof` (line 366) is invoked during blame resolution with a caller-supplied `decryptor: Participant`; the expression `self.enc_keys[&decryptor]` (line 388) uses `HashMap::index`, which panics on a missing key. An accusing participant who never delivered an `EncryptionKeyMessage` (or whose registration was skipped) causes a panic instead of a `DecryptionError`.

### Impact Explanation

An unprivileged DKG participant causes a reliable panic (process abort in non-`panic=abort` builds it unwinds to a thread kill; in typical deployments the coordinator/processor task dies) on every honest node that processes their messages. This matches the CVE class exactly: availability loss via crafted protocol input, CVSS-equivalent Medium — a single malicious message stalls or repeatedly crashes the key-generation / share-decryption flow, preventing threshold key setup or blocking blame resolution. No secret material is required and no cryptographic assumption is broken.

### Likelihood Explanation

Reachability requires only that the attacker be a DKG participant able to send PedPoP messages to honest parties — precisely the "messages they cause to be processed" input surface. The panic is deterministic: `HashMap::contains_key` is true on the second registration, and `HashMap::index` unconditionally panics on absent keys. The only mitigation is out-of-scope caller behavior (the library explicitly disclaims duplicate detection), so any integrator that does not pre-deduplicate `EncryptionKeyMessage`s or pre-validate the `decryptor` set is vulnerable.

### Recommendation

Replace the `assert!` in `Decryption::register` with a fallible check returning an error/`FrostError`-style fault indicating the misbehaving participant, and replace `self.enc_keys[&decryptor]` in `decrypt_with_proof` (and `self.decryption.enc_keys[&participant]` in `encrypt`, line 466) with `get(...).ok_or(DecryptionError::InvalidProof)` or an equivalent non-panicking lookup. All state transitions driven by deserialized participant messages should fail gracefully so that faulty participants can be blamed rather than crash the node.

### Proof of Concept

```rust
// Within a PedPoP session (crypto/dkg/pedpop), an honest node processes:
//   let msg1 = EncryptionKeyMessage::<C, M>::read(&mut bytes1, params)?;
//   decryption.register(l, msg1);
// Attacker (participant `l`) sends a second EncryptionKeyMessage under the same index:
//   let msg2 = EncryptionKeyMessage::<C, M>::read(&mut bytes2, params)?;
//   decryption.register(l, msg2);   // -> assert! fires: "Re-registering encryption key"
//
// Or, during blame resolution:
//   decryption.decrypt_with_proof(from, decryptor, msg, Some(proof))
// where `decryptor` never registered -> self.enc_keys[&decryptor] panics.
```

Both paths are driven entirely by bytes the attacker supplies to `read`/`register`/`decrypt_with_proof`, and both terminate in a panic instead of an `Err`, producing a denial of service analogous to the LibSass NULL-pointer dereference.
