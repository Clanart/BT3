## Analysis

The reported bug class is a **shared-pool insolvency caused by trusting a nominal/requested amount instead of the actually-received balance when a token can silently take a cut on transfer** (fee-on-transfer / deflationary / rebasing ERC-20). Whoever settles first drains the real balance; whoever settles last gets short-paid or reverted.

Hyperbridge's `IntentGatewayV2` (via `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents`) is a shared-pool escrow contract that holds funds for many unrelated orders simultaneously, and it already anticipates this exact class of bug — but only for **input tokens**, not for the **solver-fee escrow**.

### The asymmetry

In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`), input token amounts are captured with a before/after balance diff specifically to handle fee-on-transfer tokens: [1](#0-0) 

But the solver-fee leg of the same function skips this pattern entirely — it records the **nominal requested `order.fees`** into the shared ledger, not what the contract actually received: [2](#0-1) 

At settlement time, `withdraw()` (used by both same-chain and cross-chain fill/refund/cancel paths) pays out exactly the recorded ledger value via `safeTransfer`, not a balance-derived amount: [3](#0-2) 

### Why this reproduces the report's dynamic

`_orders[commitment][TRANSACTION_FEES]` is a per-commitment key, but all commitments share **one physical ERC-20 balance** on the gateway contract (`IDispatcher(host()).feeToken()`). If that fee token ever takes a cut on transfer (fee-on-transfer, deflationary, or a governance-toggled tax as some stablecoins support), then for every order the ledger overstates the actual tokens held by exactly the transfer-tax amount. Across many concurrent orders this understates real balance vs. the sum of `TRANSACTION_FEES` entries — exactly like the reported Lockup scenario: whichever beneficiary claims first is made whole from the shared pool, and beneficiaries who claim later either receive less than recorded or have their `safeTransfer` revert outright because the contract no longer holds enough of the fee token to satisfy the sum of outstanding ledger entries.

This is reachable by any ordinary user placing orders — no relayer, prover, or governance compromise is required — the only precondition is that `feeToken()` is (or becomes) a token with any transfer-time deduction, which the contract's own code demonstrates the authors are aware can happen (hence the diff-based handling for regular inputs).

### Title
Fee-escrow ledger uses nominal `order.fees` instead of balance-diff, causing shared-pool underpayment/revert for fee-on-transfer fee tokens - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` records the user-requested `order.fees` value into the shared `_orders[commitment][TRANSACTION_FEES]` ledger via a direct `safeTransferFrom` without verifying the actual amount received, unlike the input-token path in the same function which explicitly measures actual received balance to defend against fee-on-transfer tokens.

### Finding Description
`placeOrder` transfers `order.fees` of the protocol fee token from the caller and unconditionally stores that nominal amount in the shared ledger: [2](#0-1) 

Compare this to the input-token leg of the identical function, which explicitly guards against exactly this class of token behavior by measuring `balanceOf` before and after the transfer: [1](#0-0) 

At withdrawal (fill, cancel, or refund), the ledger value is paid out directly: [3](#0-2) 

Because the fee token balance is a single shared pool across all outstanding orders, if the token ever deducts a fee on transfer, every order's `TRANSACTION_FEES` ledger entry is an overstatement of what the gateway actually holds for that order. The pool becomes insolvent relative to the sum of recorded entries, so later claimants either get a reverted `safeTransfer` (insufficient balance) or, in the mixed-token-behavior case, an inconsistent/partial settlement — the exact "first claimant made whole, later claimants shorted" dynamic from the reference report, just triggered on the escrow's fee leg rather than its principal leg.

### Impact Explanation
This directly threatens escrowed user/solver funds in the Intent Gateway, a core cross-chain settlement contract. A pool-wide shortfall means legitimate order fillers/cancellers can be denied their entitled fee payout or have transactions revert non-deterministically depending on settlement order — a fund-loss/fund-lock condition on a production bridge contract, matching "stealing or loss of funds" and "logic attacks" in the impact gate.

### Likelihood Explanation
Exploitability is gated by the fee token's actual transfer semantics: `feeToken()` is a governance-configured address (typically a stablecoin such as DAI), so the attack surface is not attacker-controlled per order. However, several fee-token candidates (e.g., upgradeable/proxy stablecoins with a togglable transfer-fee switch, or a future feeToken migration) can introduce this behavior without any code change to the gateway, and no relayer/prover/admin compromise is needed to trigger the loss once such a token is in place — normal `placeOrder`/`fillOrder`/`cancelOrder` usage is sufficient.

### Recommendation
Apply the same balance-diff pattern already used for input tokens to the fee-token leg of `placeOrder`: measure `IERC20(feeToken).balanceOf(address(this))` before and after `safeTransferFrom`, and store the actually-received delta in `_orders[commitment][TRANSACTION_FEES]` instead of the nominal `order.fees`.

### Proof of Concept
1. Governance configures (or migrates to) a fee token that deducts a percentage on transfer (fee-on-transfer/deflationary/rebasing behavior).
2. User A places an order with `order.fees = 100`; actual tokens received by the gateway are `98`, but `_orders[commitmentA][TRANSACTION_FEES] = 100` is recorded.
3. User B places a similar order; same effect, ledger again overstates real balance by the tax amount.
4. Solver fills/cancels order A first — `withdraw()` calls `safeTransfer(beneficiary, 100)`, draining more from the shared pool than order A actually contributed.
5. When order B is settled, the gateway's actual fee-token balance is insufficient to cover the recorded `100` for order B — the `safeTransfer` call reverts, or (if other orders' balances happen to cover it) order B effectively gets subsidized by yet another order's dust, propagating the shortfall down the queue until a beneficiary's payout reverts entirely.
