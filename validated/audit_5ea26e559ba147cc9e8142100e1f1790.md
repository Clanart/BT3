### Title
Tron IntentGatewayV2 `withdraw` accepts a false ERC20 `transfer` return as success, decrementing escrow accounting while zero tokens actually move - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` reimplements token transfers with a raw low-level `.call()` to `IERC20.transfer` instead of using `SafeERC20.safeTransfer`, even though `SafeERC20` is imported and used elsewhere in the same file. In `withdraw()`, the ERC20 branch only checks that the low-level call did not revert (`success`), never decoding/verifying the boolean return value that `transfer()` yields. A non-reverting `transfer()` that returns `false` (e.g., a token whose balance/allowance edge case returns `false` instead of reverting) is treated as a successful transfer, so the code decrements the escrow accounting `_orders[body.commitment][token] -= amount` even though the beneficiary received `0` tokens. This is the exact bug class from the ELFI-protocol report: accounted balance changes while the actual on-chain token balance does not, causing silent loss for whoever the escrow belonged to.

### Finding Description
`SafeERC20` is imported and aliased (`using SafeERC20 for IERC20;`) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and is used in several places in the file. However, the `withdraw()` function — which fires on `onAccept` for `RedeemEscrow`/`RefundEscrow` requests and on `onGetResponse` for cancellations — instead does: [1](#0-0) 

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call *reverted*, not whether the token contract actually performed the transfer. Per ERC20 semantics, a compliant token can legally return `false` on failure instead of reverting. `SafeERC20.safeTransfer` guards against exactly this by decoding the return data and requiring it to be `true` (or empty, for non-standard tokens that don't return a bool at all). This manual reimplementation drops that check.

Because the escrow ledger `_orders[commitment][token]` is unconditionally decremented right after the (falsely) "successful" call, the accounting is now out of sync with actual custody: the contract believes the escrow was released, but the tokens are still sitting in the contract (or wherever they were), while the beneficiary got nothing. Subsequent code paths (fee redemption, `EscrowReleased`/`EscrowRefunded` emission, `_filled[commitment]` finalization) all proceed as if the transfer succeeded.

The same file's `SweepDust` handler in `onAccept` has the identical pattern: [2](#0-1) 

so any token that can return `false` without reverting hits this bug on both the escrow-release path and the dust-sweep path.

This mirrors the ELFI M-10 bug precisely: `VaultProcess.transferOut`'s "skip-if-insufficient" behavior let storage accounting move ahead of the actual token balance, sending "0" tokens while decrementing internal bookkeeping. Here the mechanism is different (unchecked boolean return vs. explicit balance check-and-skip) but the outcome and invariant break are the same — the contract believes a transfer happened and mutates its accounting, while the real balance transferred can be zero.

### Impact Explanation
This is a direct fund-loss path that matches the bounty's "stealing or loss of funds" category. The escrowed input tokens (for `RedeemEscrow`/`RefundEscrow`) or dust reward tokens (for `SweepDust`) are permanently marked as released in `_orders`/state, but the beneficiary (solver on a fill, user on a refund/cancel, or treasury on a dust sweep) never receives them. Because `_filled[commitment]` is set and `_orders[commitment][token]` is decremented as part of the same call, there is no automatic retry path — the funds become effectively locked/lost, since the escrow can't be withdrawn a second time (`UnknownOrder` on `_orders[commitment][token] == 0`, or already-`_filled`), and the actual balance is never reconciled against the accounting.

### Likelihood Explanation
Triggering requires only a token contract whose `transfer()` returns `false` on some failure path without reverting — a legal ERC20 behavior. Because Tron's TRC20 ecosystem historically includes non-standard tokens (which is presumably why this file diverges from `IntentsBase.sol`'s consistent `safeTransfer` usage in the first place), the probability of interacting with such a token here is materially higher than on the EVM mainline. No relayer, prover, or admin compromise is needed; any user/solver placing/filling an order with a boolean-false-returning token, or any relayer submitting a routine `onAccept`/`onGetResponse` delivery for such a token, triggers the mismatch. This is a code-level logic defect present unconditionally, not dependent on rare market conditions (unlike the original ELFI scenario), making it arguably easier to hit.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and the equivalent branch in the `SweepDust` handler inside `onAccept`) with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the rest of the codebase (`IntentsBase.sol`'s `_withdraw` already does this correctly via `SafeERC20`). If a specific TRC20 incompatibility motivated the manual call, at minimum decode and check the boolean return value when `returndata.length > 0`, matching `SafeERC20`'s exact semantics, before allowing the escrow/dust accounting to be mutated.

### Proof of Concept
1. Deploy a TRC20-compatible token `T` whose `transfer()` returns `false` (does not revert) when, for example, the recipient is blacklisted or under some internal condition — this is valid ERC20 behavior and several real-world tokens implement it.
2. User places a same-chain order and escrows `T` as input: `_orders[commitment][T] = amount`.
3. Solver fills the order; the contract dispatches a `RedeemEscrow` request for `T` back through the cross-chain path (or, for the local/same-chain `withdraw` call path, the pallet/host invokes `onAccept`).
4. In `withdraw(body, false)`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, solver, amount))` returns `(success = true, returndata = abi.encode(false))` because `T.transfer` executed without reverting but returned `false`.
5. The code only inspects `success`, sees `true`, and proceeds to `_orders[commitment][T] -= amount`, marks `_filled[commitment] = solver`, and emits `EscrowReleased`.
6. The solver's `T` balance is unchanged (transfer never actually moved tokens), yet the escrow is now marked fully released/consumed — the tokens are unrecoverable through the normal withdrawal path since the escrow entry has already been zeroed out.
