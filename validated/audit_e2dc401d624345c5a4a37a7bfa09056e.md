### Title
Unvalidated PR head ref name used to construct git ref/branch names during "Open in Desktop" PR checkout - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user opens a pull request via a GitHub-served deep link or the in-app "View on GitHub"/"Open PR" flow, Desktop calls `_checkoutPullRequest` → `_findPullRequestBranch` with `headRefName` taken verbatim from the PR object returned by the GitHub API (`pullRequest.head.ref`). This value is attacker-controlled by anyone who can open a PR (including from a fork), since GitHub allows nearly arbitrary branch names. `_findPullRequestBranch` concatenates it directly into `remoteRef` and later into a locally created branch name without sanitization equivalent to the sanitization already applied elsewhere for clone-derived paths (`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`) or for URL-supplied branch names (`testForInvalidChars` in `app/src/lib/parse-app-url.ts`).

### Finding Description
`app/src/lib/stores/app-store.ts` builds `remoteRef` as a plain template-string concatenation of the remote name and the untrusted `headRefName`: [1](#0-0) 
This value flows into `_createBranch` to actually create a local branch when the remote is treated as a "fork remote": [2](#0-1) 
Compare this to the deep-link path (`parseAppURL`), where a branch supplied via URL query string *is* validated with `testForInvalidChars` before being used: [3](#0-2) 
and to the clone-path derivation logic, which explicitly sanitizes a name derived from a remote/URL before using it to build a filesystem path (`sanitizeCloneName`): [4](#0-3) 

The PR-checkout code path has no equivalent check on `headRefName` even though it originates from the same class of untrusted source (a value ultimately controlled by whoever opened the PR) and is used to build both a `remote/ref` lookup string and, in the fork case, an actual local branch name (`` `pr/${prNumber}` `` is safe, but the underlying remote ref/tracking value and subsequent branch operations rely on `headRefName` being a "normal" git ref). This is the same *class* of bug as the openbrush report: a validation guard that exists for a sibling/adjacent input (`branch` from the deep-link query string) is not applied consistently to a structurally similar input (`head.ref` from the API object) that reaches the same kind of sensitive sink (git ref construction / branch creation), so the "flawed" value slips through where a parallel code path would have rejected it.

### Impact Explanation
If `headRefName` is not constrained to a safe git refname pattern, it could allow a malicious PR author to craft a ref name that (depending on the local git version and how `remoteRef` is subsequently passed to git plumbing/porcelain commands invoked elsewhere in the codebase) results in unexpected ref creation, ref-name collisions/overwrites, or arguments being interpreted unexpectedly by underlying git invocations reachable from this code path. At minimum it represents silent corruption of the user's local branch/ref namespace driven entirely by attacker-controlled PR metadata, which matches the "silent corruption of what the user commits" impact class.

### Likelihood Explanation
Likelihood is moderate-to-low to trigger meaningfully because: (1) GitHub's own ref-name restrictions constrain what `head.ref` can contain, and (2) it's unclear from the visible code whether `remoteRef`/`headRefName` is ever passed to a raw shell string vs. an argv array (most git calls in this codebase appear to use argv arrays, which would mitigate classic injection). I could not fully verify how deep this value travels (e.g., into `_createBranch`/`createBranch` git plumbing) due to index/context limits, so this should be treated as a plausible but not fully confirmed exploitation path.

### Recommendation
Apply the same validation used for deep-link branch names (`testForInvalidChars`, or a stricter git ref-name validator) to `pullRequest.head.ref` / `headRefName` before using it to build `remoteRef` or pass it into `_createBranch`, so PR-checkout is not the only branch-name code path in the app lacking this guard.

### Proof of Concept
Not independently verified end-to-end (would require confirming how `_createBranch`/`checkoutBranch` pass `remoteRef` to the underlying `git` argv) — flagged as an area for a Devin session with terminal/full-repo access to trace `_createBranch` and `createBranch` in `app/src/lib/git/` and confirm whether a crafted `head.ref` (e.g. containing `..`, leading `-`, or control characters) can produce unexpected git ref behavior when checking out a pull request from a fork.
