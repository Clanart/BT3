Based on my research, I found a directly analogous incomplete-opcode-filter bug in the chia-blockchain custody/restriction framework.

### Title
`SendMessageBanned` restriction filters only `SEND_MESSAGE` (66), omitting `RECEIVE_MESSAGE` (67), allowing message-based logic to bypass the intended ban - ([File: chia/wallet/puzzles/custody/send_message_banned.clsp])

### Summary
The `SendMessageBanned` restriction is a custody-framework wrapper meant to disallow message-based conditions from being emitted by a delegated puzzle inside `PuzzleWithRestrictions`. Its recursive scan only checks the opcode against the `SEND_MESSAGE` constant and never checks for `RECEIVE_MESSAGE`, exactly mirroring the reported TON pattern: an opcode filter that enumerates some values in a family of related opcodes but misses one, letting a message opcode through the block that was supposed to exclude the whole message-condition category.

### Finding Description
`send_message_banned.clsp` recursively walks the condition list output by the delegated puzzle and raises (`(x)`) only when it finds opcode `SEND_MESSAGE` (66): [1](#0-0) 

`SEND_MESSAGE` and `RECEIVE_MESSAGE` are declared as adjacent, paired opcodes (66 and 67) in `condition_codes.clib`: [2](#0-1) 

and the wallet's own `SendMessage`/`ReceiveMessage` condition classes are explicitly modeled as a matched pair (`ReceiveMessage` subclasses `SendMessage` and only differs in `_opcode`), reinforcing that they are meant to be treated as one semantic category — messaging in either direction: [3](#0-2) 

Because `SendMessageBanned.check_conditions` recurses over every condition and explicitly checks only for `SEND_MESSAGE`, an `RECEIVE_MESSAGE` (opcode 67) condition passes straight through the `(check_conditions (r conditions) return)` branch untouched, exactly like the `op == 0xF` case bypassing the TON filter — the restriction's exclusion list omits a semantically-equivalent sibling opcode, so the intended "no messaging" guarantee for that custody configuration doesn't actually hold.

The Python driver `SendMessageBanned` in `restrictions.py` simply wraps this puzzle with no additional opcode checks: [4](#0-3) 

### Impact Explanation
`SendMessageBanned` is a restriction primitive in the generic `PuzzleWithRestrictions`/custody framework (used, e.g., for multi-party custody policies) intended to guarantee that a delegated spend cannot use the message protocol (`SEND_MESSAGE`/`RECEIVE_MESSAGE`) to coordinate cross-coin/cross-spend logic outside the policy's control. Since `RECEIVE_MESSAGE` is unfiltered, a member holding a key/authority under a `SendMessageBanned`-restricted policy can still emit `RECEIVE_MESSAGE` conditions. `RECEIVE_MESSAGE` requires the message to also be sent by a paired `SEND_MESSAGE` elsewhere in the same spend bundle to be valid (per `MESSAGE_NOT_SENT_OR_RECEIVED` enforcement), so this by itself doesn't directly move funds, but it defeats the restriction's stated security guarantee: any custody policy relying on `SendMessageBanned` to fully prevent message-based coordination/side-channel behavior in the delegated puzzle is only partially enforced, since one half of the message protocol remains available to a restricted spender. This is a real, reachable break of an intended custody invariant enforceable purely from the "delegated puzzle" side of a `PuzzleWithRestrictions` spend by any party permitted to author that delegated puzzle.

### Likelihood Explanation
Any wallet user or integrator relying on the custody framework's `SendMessageBanned` restriction (a documented, tested wrapper in `chia/wallet/puzzles/custody/restrictions.py` and covered by `test_send_message_banned` in `chia/_tests/clvm/test_restrictions.py`) can trivially craft a delegated puzzle/solution emitting a `RECEIVE_MESSAGE` condition instead of `SEND_MESSAGE` and have it accepted, since the check is a pure opcode-equality comparison with no logic to also test the sibling opcode. No privileged access or malicious peer is required — the delegated puzzle content is exactly what an authorized custody member controls.

### Recommendation
Update `check_conditions` in `send_message_banned.clsp` to also reject `RECEIVE_MESSAGE` (67), e.g. change the equality test to check for either `SEND_MESSAGE` or `RECEIVE_MESSAGE`:
```clsp
(if (any (= (f (f conditions)) SEND_MESSAGE) (= (f (f conditions)) RECEIVE_MESSAGE))
    (x)
    (check_conditions (r conditions) return)
)
```
and recompile `send_message_banned.clsp.hex`, updating any precalculated puzzle hashes used by `restrictions.py`/tests.

### Proof of Concept
1. Build a `PuzzleWithRestrictions` with `restrictions=[ValidatorStackRestriction(required_wrappers=[SendMessageBanned()])]`, as in `test_send_message_banned`.
2. Instead of a delegated puzzle emitting `SendMessage(...)` (which is correctly rejected per the existing test), construct a delegated puzzle emitting a lone `ReceiveMessage(msg, sender=MessageParticipant(...))` condition.
3. Submit the spend through `SendMessageBanned`'s wrapper solve path (`modify_delegated_puzzle_and_solution`).
4. Because `check_conditions` never matches opcode 67, the restriction puzzle returns normally instead of raising `(x)`, and the spend is admitted to the mempool (subject only to the unrelated `MESSAGE_NOT_SENT_OR_RECEIVED` pairing rule, which can be satisfied by a companion `SEND_MESSAGE` condition on any other coin in the same bundle) — demonstrating the restriction is bypassed for `RECEIVE_MESSAGE`.
