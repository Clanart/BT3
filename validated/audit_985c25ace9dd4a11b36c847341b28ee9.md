Found a highly relevant analog: `x/evm/keeper/abci.go` `EndBlock`, where coinbase-surplus sweeps and module-account surplus deposits use best-effort bank calls whose errors are only logged, not retried or reverted.### Title
Silent, unretried per-transaction fee-surplus sweep in EVM `EndBlock` can permanently strand user fee refunds - (File: x/evm/keeper/abci.go)

### Summary
`x/evm/keeper/abci.go`'s `EndBlock` sweeps each EVM transaction's leftover coinbase balance (the fee-surplus refund a user is owed, e.g. from EIP-1559 tip/fee-cap overpayment) from a deterministic per-tx coinbase address to the real coinbase (fee collector) with a single `SendCoinsAndWei` call. If that call errors, the code only logs the error and moves on — it never retries, never records the failed amount, and the coinbase-address funds are left un-swept with no other code path to recover or redistribute them [1](#0-0) . This mirrors the reported `RewardDistributor.sol` pattern: a payout that depends on a transfer succeeding, with no bookkeeping fallback when it doesn't, resulting in permanently lost user funds instead of a reverted transaction or a retriable claim.

### Finding Description
For every EVM transaction executed in a block, fee overpayment/surplus is accumulated at a deterministic "coinbase" address for that transaction index [2](#0-1) . At `EndBlock`, the keeper reads that address's `usei`/`wei` balances and attempts to move them to the block's real coinbase (the `fee_collector` module account in normal operation):

```go
useiBalance := k.BankKeeper().GetBalance(ctx, coinbaseAddress, denom).Amount
lockedUseiBalance := k.BankKeeper().LockedCoins(ctx, coinbaseAddress).AmountOf(denom)
balance := useiBalance.Sub(lockedUseiBalance)
weiBalance := k.BankKeeper().GetWeiBalance(ctx, coinbaseAddress)
if !balance.IsZero() || !weiBalance.IsZero() {
    if err := k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance); err != nil {
        logger.Error("failed to send usei surplus to coinbase account", "from", coinbaseAddress, "err", err)
    }
}
``` [1](#0-0) 

If `SendCoinsAndWei` returns an error (e.g. the recipient module account is temporarily `BlockedAddr`, the denom is send-disabled, or any other transient bank-layer validation failure), the funds sitting at `coinbaseAddress` are neither swept to the fee collector nor returned to the original fee payer. The same best-effort pattern (log-only on error) is repeated immediately afterward for module-account surplus deposits:

```go
if err := k.BankKeeper().AddCoins(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), sdk.NewCoins(sdk.NewCoin(k.GetBaseDenom(ctx), surplusUsei)), true); err != nil {
    logger.Error("failed to send usei surplus to EVM module account", "surplus", surplusUsei)
}
``` [3](#0-2) 

There is no persistent "pending sweep" record analogous to `RewardDistributor`'s missing bookkeeping recommendation: once `EndBlock` for that height has passed, nothing re-attempts the transfer, and the coinbase address (a synthetic, non-user-controlled account derived purely from `tx index`, per `GetCoinbaseAddress`) has no owner who can claim the stranded balance [2](#0-1) .

### Impact Explanation
Any usei/wei left at the per-tx coinbase address after a failed sweep becomes permanently stuck: it is not owned by the fee payer, is not part of the fee collector's balance for that block, and the coinbase address is regenerated identically for a *different* transaction at the same index in the *next* block, so a subsequent sweep at that index would double-count unrelated funds rather than recovering the earlier stranded amount. This is a fund-loss condition, not merely informational, matching the "Accept only concrete fund loss" bar. Because these coinbase addresses receive real user-paid transaction fees on every EVM transaction, the surface is reachable by any ordinary transaction sender, and repeated failures would degrade the fee-accounting invariants the module documentation states it maintains ("Fee surplus... is tracked per-transaction and collected into the fee collector at end-of-block") [4](#0-3) .

### Likelihood Explanation
`SendCoinsFromModuleToAccount`/`SendCoins`-style transfers in this bank keeper can fail for reasons outside the EVM module's control — e.g. `BlockedAddr` checks, `CanSendTo` recipient-checker hooks (used elsewhere for coinbase-prefixed and other special addresses, see `sei-cosmos/x/bank/keeper/send.go` `BlockedAddr`) [5](#0-4) , or denom-allowlist/send-enabled configuration changes. Because `coinbase` in `EndBlock` is the `fee_collector` module address by default, an operator misconfiguration or a future recipient-checker addition that transiently rejects the fee collector (or a bug in `LockedCoins` computation causing `balance` to be inconsistent with what `SendCoinsAndWei` will accept) would trigger this silent-loss path on every affected transaction in a block. This requires no attacker action beyond sending a normal EVM transaction; the vulnerability is triggered by an already-possible failure mode of the sweep, exactly analogous to the acknowledged Blex issue where an ordinary, non-adversarial insufficiency causes silent loss.

### Recommendation
Do not silently swallow the error from the coinbase/module-account sweep in `EndBlock`. At minimum:
1. Persist any failed-sweep amount (coinbase address, denom, amount) to durable state so it can be retried in a later block or exposed via a recovery message, mirroring the report's recommendation of additional bookkeeping for underfunded/failed payouts.
2. Consider treating a sweep failure inside `EndBlock` as unrecoverable-and-panic (matching the module's stated philosophy elsewhere that "unable to marshal deferred info is serious... panic(err)" for surplus-accounting integrity, see `x/evm/keeper/deferred.go` lines 43-47) rather than "log and continue," since silently continuing breaks the fee-collector accounting invariant just as severely as a marshal failure would.
3. Add an invariant/alert that fires if any `GetCoinbaseAddress(idx)` account retains a nonzero balance after `EndBlock` completes, so operators can detect and manually recover stranded fees before they are overwritten by the next block's reuse of that same coinbase index.

### Proof of Concept
Conceptual PoC (analysis-only; not confirmed against a live BlockedAddr trigger, since this requires either a bank-layer misconfiguration or a future recipient-checker registration to actually force `SendCoinsAndWei` to fail for the fee_collector address — I could not find a currently-registered `RecipientChecker` in this snapshot that already blocks `fee_collector`, so likelihood depends on operational/future-code conditions rather than a demonstrated exploit today):
1. Register (or have registered via `RegisterRecipientChecker`, `sei-cosmos/x/bank/keeper/send.go` lines 461-472) a recipient checker that rejects the `fee_collector` module address for a specific denom/condition, or otherwise induce `SendCoinsAndWei` to fail for that recipient.
2. Send a normal EIP-1559 EVM transaction with `maxFeePerGas` above `baseFee + tip`, generating a nonzero fee surplus that accumulates at `GetCoinbaseAddress(txIdx)`.
3. At `EndBlock`, `SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance)` returns an error; the code only calls `logger.Error(...)` and continues [6](#0-5) .
4. In the following block, a different transaction reuses the same `txIdx`, and its own surplus is added to the same `coinbaseAddress`; the earlier stranded surplus is now indistinguishable from the new transaction's surplus, and no accounting path recovers or attributes it correctly — the original fee payer's refund is permanently lost.

func GetCoinbaseAddress(txIdx int) sdk.AccAddress {
	txIndexBz := make([]byte, 8)
	binary.BigEndian.PutUint64(txIndexBz, uint64(txIdx)) //nolint:gosec
	return append(CoinbaseAddressPrefix, txIndexBz...)
}

func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}
