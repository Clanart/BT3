### Title
Scanner reports uneconomical/dust outputs as spendable funds, enabling a remote DoS on wallet spends - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` emits a `ReceivedOutput` for every transaction output whose `script_pubkey` matches a registered scan key, with no minimum-value check. The only dust filter (`DUST = 546` in `networks/bitcoin/src/wallet/send.rs:32`) is applied to outgoing payments, never to scanned inputs. An unprivileged remote party who sends low-value or dust-valued P2TR outputs to a watched Serai address can therefore poison the wallet's UTXO set: the outputs are reported as received funds but are uneconomical or impossible to spend, degrading or blocking future `SignableTransaction` construction.

### Finding Description
- `scan_transaction` matches solely on `output.script_pubkey` and pushes a `ReceivedOutput` regardless of `output.value` (mod.rs:205-211). There is no dust/economic-value floor on inputs.
- `SignableTransaction::new` validates dust only for `payments` (send.rs:165-169). Every scanned input is unconditionally added to `tx_ins` (send.rs:177-185) and contributes to `input_sat` (send.rs:175), even when its value is below the marginal fee required to spend it.
- Each input adds a fixed ~57.5 vB to `calculate_weight_vbytes` (send.rs:68-99), so an input of value `< fee_per_vbyte * input_vbytes` is a net liability. Including such inputs lowers the leftover available for payments/change, and can flip `input_sat < payment_sat + needed_fee` into `NotEnoughFunds` (send.rs:215-221) or silently burn value into fees via the change path (send.rs:224-235).
- `Scanner::register_offset` notes arbitrary scripts can be introduced via offsets (mod.rs:177-179), but here the attacker needs no offset knowledge: the base `p2tr_script_buf(key)` script is derived from the public group key, which is publicly observable on-chain after any prior spend.

### Impact Explanation
A remote, unauthenticated attacker who sends crafted Bitcoin transactions to a scanned address causes the wallet to accumulate outputs that are reported received yet cannot be profitably spent (each is worth less than the fee to spend it, or is below relay dust limits yet consensus-valid when miner-included). Once included in a `SignableTransaction`, these inputs either force an inflated fee, starve the payment/change values, or trigger `NotEnoughFunds`, denying service to the spend path. This mirrors the nova bug class — resources (here, UTXOs accepted into wallet state) that are never usable/cleaned up, causing persistent resource consumption — mapped onto Serai's scanner/spend pipeline.

### Likelihood Explanation
An attacker only needs to broadcast (or have mined) Bitcoin transactions paying small amounts to the publicly known P2TR script of a multisig key — fully within the "Bitcoin transactions they send" reachability rule. No validator compromise, collusion, or leaked secrets is required. Impact is Medium: it degrades/blocks spending rather than directly stealing funds.

### Recommendation
Enforce a minimum value on scanned outputs inside `Scanner::scan_transaction` (e.g., reject `output.value < DUST` or value below the marginal input fee at a reference rate), or have `SignableTransaction::new` skip inputs whose value is below the marginal cost `fee_per_vbyte * per_input_vbytes` before summing `input_sat`.

### Proof of Concept
1. Observe a Serai multisig's P2TR `script_pubkey` on-chain (public after any spend).
2. Send a transaction with an output paying, e.g., 100 sats (or a value below `fee_per_vbyte * 58`) to that script. `scan_transaction` returns a `ReceivedOutput` (mod.rs:199-214).
3. When the wallet later builds a spend including that output, `SignableTransaction::new` counts its value into `input_sat` (send.rs:175) while it adds full input weight to `needed_fee` (send.rs:204-211). Repeating with many such outputs inflates `needed_fee` beyond available `input_sat - payment_sat`, yielding `NotEnoughFunds` (send.rs:215-221) or excessive fee burn — the dust outputs remain permanently in the reported UTXO set with no cleanup path.
