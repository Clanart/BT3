### Title
Divide-by-zero crash in mempool block assembly when an item's cost is fully deduplicated - (File: `chia/full_node/mempool.py`)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item it considers for inclusion in a block, then immediately divides the item's fee by that value in a logging call: `fee / item_cost`. If `cost_saving` equals `cost` (i.e., the entire mempool item's CLVM cost is eliminated through fast-forward/dedup savings), `item_cost` becomes `0` and the division raises an unhandled `ZeroDivisionError`, analogous to the libtiff `JPEGSetupEncode` divide-by-zero bug class (CVE-2017-7595): an attacker-influenced value reaches an unguarded division and crashes the process.

### Finding Description
In `create_bundle_from_mempool_items`, for items not in the "priority threshold skip" branch, the code calls `dedup_coin_spends.get_deduplication_info()` to determine how much of the item's cost can be saved because some of its coin spends are eligible-for-dedup and are identical to spends already included from a higher fee-per-cost item processed earlier in the same block-assembly pass: [1](#0-0) 

`cost_saving` is derived directly from user-submitted spend bundle contents (whether each coin spend is `eligible_for_dedup`, and whether an earlier-processed higher-priority item already contains an identical spend of the same coin). Because `unique_coin_spends`/`cost_saving` come from `IdenticalSpendDedup.get_deduplication_info` in `chia/full_node/eligible_coin_spends.py`, a mempool item whose *entire* set of coin spends duplicates spends already claimed by a prior item will have `cost_saving == cost`, making `item_cost = cost - cost_saving == 0`. The very next line performs `fee / item_cost`, which raises `ZeroDivisionError`.

This function is invoked by the full node itself whenever it assembles a block from the mempool (farming path), so it is reachable purely by an unprivileged party submitting ordinary spend bundles to the mempool via the standard transaction-submission RPC — no special privileges are required, only the ability to submit a spend bundle whose coin spends are entirely dedup-eligible duplicates of coins already spent by another (higher fee-rate) mempool item.

### Impact Explanation
An unhandled `ZeroDivisionError` inside `create_bundle_from_mempool_items` will propagate up through the full node's block-building call path. Because this routine is exercised whenever the node farms a block or otherwise tries to build a bundle from the mempool, a crash here halts transaction processing for that invocation and can repeatedly disrupt block assembly if the triggering condition recurs (e.g., attacker resubmits similarly-shaped duplicate-dedup bundles). This matches the "spend-triggered transaction-processing halt" impact category — a denial-of-service against normal chain operation caused by a single crafted spend bundle, not requiring any signature forgery, privileged access, or protocol-level compromise.

### Likelihood Explanation
Reaching the trigger requires: (1) an existing higher-fee-rate mempool item containing dedup-eligible coin spends (already a normal feature exercised in offers/settlement flows), and (2) submitting a second bundle whose relevant coin spends are identical (same coin ID and same canonical solution) to those already claimed, so that 100% of its cost is deduplicated away. Both conditions are achievable by any wallet/RPC user who can observe pending mempool contents and craft a spend bundle mirroring an existing dedup-eligible spend. This is a data-shape condition rather than a cryptographic or privileged operation, making the likelihood moderate-to-high for a determined submitter, though it depends on precise mempool state timing to guarantee a full deduplication of a single item's cost.

### Recommendation
Guard against `item_cost == 0` before the division, e.g., skip logging the ratio or use a safe format when `item_cost <= 0`, and audit whether an item whose entire cost is deduplicated should still be counted as "processed" with cost 0 elsewhere in the loop (cost/fee accounting invariants). At minimum, replace:
```python
item_cost = cost - cost_saving
log.info(..., fee / item_cost, item_cost)
```
with a zero-check guard, and add a regression test that constructs two mempool items where the lower-priority item's dedup-eligible spends are a strict subset already fully covered by a higher-priority item's spends.

### Proof of Concept
Conceptual reproduction (would need to be validated end-to-end in a test harness with a running `MempoolManager`):
1. Submit spend bundle `A` containing a dedup-eligible coin spend of coin `C` with fee `F1`.
2. Submit spend bundle `B` containing only a dedup-eligible spend of the same coin `C` with an identical canonical solution, with fee `F2 < F1` (so `B` is processed after `A` in the priority-ordered cursor).
3. Call `mempool.create_bundle_from_mempool_items(...)` (as done during block farming). When item `B` is processed, `dedup_coin_spends.get_deduplication_info()` recognizes coin `C`'s spend as already included by `A`, yielding `cost_saving == B.conds.cost` and thus `item_cost == 0`, causing `fee / item_cost` to raise `ZeroDivisionError`.

Note: I was not able to fully inspect `get_deduplication_info` in `chia/full_node/eligible_coin_spends.py` within the available tool budget to confirm the exact conditions under which `cost_saving` can equal the item's *full* cost (e.g., whether an item can be composed entirely of a single dedup-eligible spend with no other spends). This should be verified directly against that file before treating this as fully confirmed exploitable. [2](#0-1) [3](#0-2)
