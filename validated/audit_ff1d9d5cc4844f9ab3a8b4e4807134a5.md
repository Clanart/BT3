### Title
Consistency-Check Abort on Re-Serialization of a Corrupted `unverified_lazy` Submessage — ([File: src/google/protobuf/message_lite.cc])

### Summary
Zebra's CVE-2026-34202 is fundamentally a **two-pass validation mismatch**: bytes that pass a cheap, lazy check at parse time are later fed into a stricter, eager computation that assumes validity and aborts (panics) when that assumption is false. Protobuf's C++ runtime has a structurally identical hazard in its `lazy`/`unverified_lazy` field machinery combined with the `ByteSizeLong()`/`Serialize` consistency check in `message_lite.cc`. A length-delimited submessage field marked `unverified_lazy = true` is stored as raw, **unvalidated** bytes at parse time [1](#0-0) . `ByteSizeLong()` for such a field trivially returns the size of those raw stored bytes (verified in the Java analog, which mirrors the C++ design intent) [2](#0-1) . If application code (via any public parse API) subsequently *touches* (materializes/parses) that lazy submessage — which is normal, legitimate usage, not "concurrent modification" — and the malformed/non-canonical bytes get re-encoded to a **different length** than the originally cached size, a later `SerializeWithCachedSizes` call detects the mismatch and calls `ByteSizeConsistencyError`, which unconditionally aborts the process via `ABSL_LOG(FATAL)` [3](#0-2) .

### Finding Description
- **Invariant that fails**: `WireFormat::SerializeWithCachedSizes` assumes the byte count produced by serialization exactly equals the size previously computed by `ByteSizeLong()` [4](#0-3) . This is only true if the message's serialized representation is stable between the two calls.
- **Attacker-controlled value**: The attacker crafts a top-level message containing an `unverified_lazy` (or ordinary `lazy`) submessage field whose length-delimited payload is syntactically valid enough to be accepted as raw bytes at the outer parse (satisfying `ParseFromString`/`MergeFrom`), but whose *inner* content is non-canonical (e.g., duplicate/overriding fields, non-minimal varints, or fields that get re-ordered/re-encoded when the lazy value is materialized and rebuilt).
- **Missing check**: Because `unverified_lazy` explicitly "does no correctness checks on the byte stream" [1](#0-0) , and even ordinary `lazy` fields only verify wire-format well-formedness/required-field presence, not byte-for-byte re-serialization stability, no check exists to guarantee that `getSerializedSize()`/`ByteSizeLong()` computed *before* the lazy value is touched remains valid once the value is touched and then reserialized.
- **Consuming-application exposure**: Any application that (a) parses an untrusted message with `ParseFromString`/`MergeFrom`, then (b) accesses/mutates the lazy submessage for business logic (a completely ordinary operation, e.g. reading a field, logging, or copying it), and then (c) serializes the outer message again, hits this path. The protobuf test suite itself acknowledges the risk and works around it by explicitly "touching" all lazy fields before re-serializing test messages that were partially rejected [5](#0-4)  — proof that this is a recognized internal hazard, not a hypothetical.
- **Impact**: `ByteSizeConsistencyError` ends in `ABSL_LOG(FATAL)`, which terminates the process [6](#0-5) . This is functionally identical to Zebra's crash: bytes that cleared the first (lazy/cheap) validation gate reach a second stage that assumes stronger invariants and aborts instead of returning a graceful error.

### Impact Explanation
A successful trigger crashes the process (`ABSL_LOG(FATAL)`), which is a Denial of Service for any long-running server process embedding protobuf and touching attacker-supplied lazy fields before re-serializing them — directly analogous to the "Remote Denial of Service" impact of the Zebra CVE. Severity would be Medium/High depending on how commonly application code re-serializes after touching lazy fields; this is a common pattern (read a field, log/transform, forward).

### Likelihood Explanation
Likelihood is constrained by several factors I could **not fully verify** in this pass given remaining iteration budget:
1. I could not directly inspect the C++ `LazyField`/`LazyRepeatedField` materialization implementation (e.g., a `lazy_field.cc`/`lazy_field.h` file) to confirm exactly when/whether a touched lazy value's cached size is refreshed versus left stale, which is the crux of whether the mismatch is actually reachable in modern C++ generated code (as opposed to the Java `LazyFieldLite`/`InternalLazyField` classes I could confirm).
2. `unverified_lazy` and `lazy` are **schema options** (`FieldOptions.lazy`/`unverified_lazy`) that must be set by the `.proto` author; per the task's trust assumptions, schemas are trusted, so this only matters if a trusted schema *chooses* to use lazy fields (a real, supported, documented feature — not a hostile schema).
3. The known regression tests (`ExplicitLazyBadLengthDelimitedSize`, `TestRegressionOverwrittenLazyOneofDoesNotLeak`, `SuccessAfterParsingFailure`'s `TouchLazy` workaround) indicate the protobuf team has already hardened multiple related edge cases, so this exact abort may already be mitigated in current releases — I could not confirm the current-state behavior definitively.

Given this uncertainty, I present this as the strongest analog found, but flag that **confirmation requires reading the current C++ `LazyField` size-caching implementation and running a live PoC**, which I was unable to complete.

### Recommendation
- Audit the C++ `LazyField`/`LazyRepeatedField` implementation to confirm whether `ByteSizeLong()` is recomputed/invalidated whenever a lazy value is materialized from unverified bytes, and whether the recomputed size can legitimately differ from the size cached before materialization.
- If a mismatch is reachable purely from attacker-controlled bytes (no concurrent mutation), replace the `ABSL_LOG(FATAL)` abort in `ByteSizeConsistencyError` for this specific case with a recoverable error return, or force eager re-validation/re-caching of size whenever a lazy field is touched, before it can be reused by `SerializeWithCachedSizes`.
- Document/require that consuming applications never call `ByteSizeLong()` before touching lazy fields if they intend to serialize afterward, or provide an API that avoids exposing the CHECK to untrusted input at all.

### Proof of Concept

namespace {

// When serializing, we first compute the byte size, then serialize the message.
// If serialization produces a different number of bytes than expected, we
// call this function, which crashes.  The problem could be due to a bug in the
// protobuf implementation but is more likely caused by concurrent modification
// of the message.  This function attempts to distinguish between the two and
// provide a useful error message.
void ByteSizeConsistencyError(size_t byte_size_before_serialization,
                              size_t byte_size_after_serialization,
                              size_t bytes_produced_by_serialization,
                              const MessageLite& message) {
  ABSL_CHECK_EQ(byte_size_before_serialization, byte_size_after_serialization)
      << message.GetTypeName()
      << " was modified concurrently during serialization.";
  ABSL_CHECK_EQ(bytes_produced_by_serialization, byte_size_before_serialization)
      << "Byte size calculation and serialization were inconsistent.  This "
         "may indicate a bug in protocol buffers or it may be caused by "
         "concurrent modification of "
      << message.GetTypeName() << ".";
  ABSL_LOG(FATAL) << "This shouldn't be called if all the sizes are equal.";
}

void TouchLazy(UNITTEST::TestAllTypes* msg) {
  if (msg->has_optional_lazy_message()) {
    TouchLazy(msg->mutable_optional_lazy_message());
  }
  if (msg->has_optional_unverified_lazy_message()) {
    TouchLazy(msg->mutable_optional_unverified_lazy_message());
  }
  for (auto& child : *msg->mutable_repeated_lazy_message()) {
    TouchLazy(&child);
  }
}

void TouchLazy(UNITTEST::NestedTestAllTypes* msg) {
  if (msg->has_child()) TouchLazy(msg->mutable_child());
  if (msg->has_payload()) TouchLazy(msg->mutable_payload());
  for (auto& child : *msg->mutable_repeated_child()) {
    TouchLazy(&child);
  }
  if (msg->has_lazy_child()) TouchLazy(msg->mutable_lazy_child());
  if (msg->has_eager_child()) TouchLazy(msg->mutable_eager_child());
}
