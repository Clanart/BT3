I found a genuine analog: `applyPatchToIndex` in `app/src/lib/git/apply.ts` re-derives the diff to apply from the *current on-disk working directory* rather than from the diff snapshot the user actually selected lines/hunks against in the UI.### Title
Silent commit corruption via stale line-selection reapplied to a re-diffed working tree in partial-commit staging - ([File: app/src/lib/git/apply.ts])

### Summary
The Compound report is fundamentally about an invariant: an action's parameters (here, a diff/selection) must be re-validated against current on-chain state before being replayed, otherwise a stale action executes against a changed state. The closest verifiable Desktop analog is in the partial-commit / hunk-selection staging path: `applyPatchToIndex` throws away the diff the user actually reviewed and rebuilds a brand-new diff from the live working directory immediately before applying the user's line-selection to it, with no check that the two diffs still line up.

### Finding Description
When a user stages a partial file (selecting specific lines/hunks instead of the whole file), `stageFiles` calls `applyPatchToIndex` for each partially-selected `WorkingDirectoryFileChange`: [1](#0-0) 

Inside `applyPatchToIndex`, the diff used to build the actual `git apply --cached` patch is **not** the diff instance that produced the selection UI the user interacted with — it is freshly recomputed from disk via `getWorkingDirectoryDiff` at apply time: [2](#0-1) 

`formatPatch` then walks `file.selection` (an index-based bitmap keyed to line offsets of the *original* diff the user saw) against this newly-fetched diff and blindly maps those offsets/line texts: [3](#0-2) 

The application already acknowledges elsewhere that diffs shift between selection-time and use-time and that stale selections are unsafe — see the comment and remediation in `updateChangesWorkingDirectoryDiff`, which explicitly revalidates `selectableLines` against a freshly loaded diff before letting the UI keep using a selection: [4](#0-3) 

That revalidation only happens for the **UI diff-loading path**, not for the **commit/staging path**. `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` fetch with no equivalent reconciliation against the selection that was computed from the diff the user reviewed on screen. If the on-disk file changes between the moment the user made their line selection (in the Changes view) and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs (e.g., a build tool, a git hook, a background sync process, or content written by a tool the repository invokes autonomously modifies the file in that window), the selection bitmap is applied to a structurally different diff. `git apply --unidiff-zero` will either fail outright, or — because `--unidiff-zero` context is minimal — succeed while staging different hunks/lines than what the user visually reviewed and intended to commit.

### Impact Explanation
This breaks the core trust invariant of a partial/interactive commit: "what I selected in the diff viewer is what gets committed." Because the patch is rebuilt from live disk state rather than the reviewed diff, and because there is no re-validation step (unlike the analogous UI code path), a user can be made to silently commit content they never selected/reviewed — a content-integrity violation of "what the user commits" that matches the impact class of "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires a source of file mutation between diff review and staging that Desktop does not control (a repo-provided hook, tool, or watcher writing to the same file), which is a real but narrower attacker-controlled-repository primitive than a purely local coincidence — the window is small (typically milliseconds to a few seconds within one `_commitChanges` call), so likelihood is moderate rather than high, and reliably engineering a specific unintended diff outcome (vs. a hard `git apply` failure) would need attacker control over hook timing and content precision.

### Recommendation
Before applying `file.selection` in `applyPatchToIndex`, re-fetch or reuse the exact diff the selection was computed against (e.g., pass the diff object down from the caller instead of re-deriving it) and validate that the file's content/hash matches what was diffed; if it has changed, abort staging that file and force the caller to refresh the diff and selection, mirroring the safeguard already implemented in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
Not independently executable from the index alone (requires timing a working-directory mutation between UI selection and commit); the code-level basis for the finding is documented above via [2](#0-1)  and the contrasting safeguard at [4](#0-3) . A full runnable PoC (e.g., a repo with a `post-checkout`/background process that rewrites the target file between selection and commit) would need to be validated in a live Desktop session, which is outside the scope of static index-based analysis.
