### Title
Missing HTML-unsafe character escaping in PHP's pure-implementation JSON string serializer allows downstream reflected XSS - (`php/src/Google/Protobuf/Internal/GPBJsonWire.php`)

### Summary
Protobuf's JSON encoders in C++, Java, C#, and upb (including the upb build bundled for the PHP C extension) deliberately escape `<`, `>`, `&`, `=`, `'` in serialized string values as `\uXXXX` sequences specifically to prevent XSS when the produced JSON is embedded into an HTML/`<script>` context by a consuming application. The pure-PHP implementation of the same JSON serialization API omits this protection, delegating directly to PHP's native `json_encode()`, which does not perform this extra escaping.

### Finding Description
Every other Protobuf JSON writer implements a documented HTML-safety invariant. The C++ writer explicitly escapes `<`/`>` "to prevent security bugs in JavaScript" [1](#0-0) , with a dedicated regression test `JsonTest.HtmlEscape` verifying `</script>` becomes `\u003c/script\u003e` [2](#0-1) . Java's `JsonFormat` explicitly escapes `<>&='` "to prevent XSS risks" [3](#0-2) , backed by `testHtmlEscape`/`testHtmlEscapeAllGsonCharacters` regression tests [4](#0-3) [5](#0-4) . C#'s `JsonFormatter.WriteString` hex-encodes `<`/`>` via `CommonRepresentations` "required for HTML security" [6](#0-5) .

The pure-PHP `GPBJsonWire::serializeSingularFieldValueToStream()` STRING case, however, calls PHP's built-in `json_encode($value, JSON_UNESCAPED_UNICODE)` and writes the result raw, with no equivalent post-processing for `<`, `>`, `&`, `=`, or `'`: [7](#0-6) . PHP's native `json_encode()` only escapes the RFC 4627-mandated control characters, quotes, and backslashes — it does not touch `<`, `>`, `&`, or `=`. The class does contain a hand-rolled `escapedJson()`/`jsonNiceEscape()` helper that also does not cover these HTML-unsafe characters [8](#0-7) , confirming the omission is structural, not incidental.

### Impact Explanation
Under the stated consuming-application-exposure assumption — an application takes attacker-controlled Protobuf message content, serializes it to JSON via the public `serializeToJsonString()` API, and embeds that JSON inline in an HTML response (a scenario Google's own comments and tests across C++/Java/C# explicitly anticipate and defend against) — the PHP pure implementation fails to neutralize `</script>`-style breakout sequences in string field values. This is precisely the reflected-XSS mechanism described in CVE-2021-38704: attacker-supplied string content flows unescaped into an HTML/script-consuming sink. Impact is limited to confidentiality/integrity within the embedding page (script injection, session/token theft potential), matching the CVE's C:L/I:L rating; there is no RCE or memory-safety impact.

### Likelihood Explanation
Reaching this requires only calling the standard, documented JSON serialization API (`Message::serializeToJsonString()`) with an attacker-influenced string field, on the pure-PHP code path. The trigger is a plain ASCII sequence (`</script>`), needs no malformed wire bytes, oversized inputs, or privileged access, and is directly exercised by the existing HTML-escape regression tests in the other language SDKs — indicating this is a well-understood, previously-fixed class of issue that the PHP pure implementation simply never received parity for.

### Recommendation
Route the PHP pure-implementation STRING serialization path through the same HTML-unsafe character escaping used by the C++/Java/C#/upb encoders (escape `<`, `>`, `&`, `=`, `'` as `\u00XX`) rather than relying solely on PHP's native `json_encode()`, and add a `testHtmlEscape`-equivalent regression test to `php/tests` mirroring the Java/C++ test suites.

    private static function jsonNiceEscape($c)
    {
      switch ($c) {
          case '"':  return "\\\"";
          case '\\': return "\\\\";
          case '/': return "\\/";
          case '\b': return "\\b";
          case '\f': return "\\f";
          case '\n': return "\\n";
          case '\r': return "\\r";
          case '\t': return "\\t";
          default:   return NULL;
      }
    }

    private static function isJsonEscaped($c)
    {
        // See RFC 4627.
        return $c < chr($k_control_char_limit) || $c === "\"" || $c === "\\";
    }

    public static function escapedJson($value)
    {
        $escaped_value = "";
        $unescaped_run = "";
        for ($i = 0; $i < strlen($value); $i++) {
            $c = $value[$i];
            // Handle escaping.
            if (static::isJsonEscaped($c)) {
                // Use a "nice" escape, like \n, if one exists for this
                // character.
                $escape = static::jsonNiceEscape($c);
                if (is_null($escape)) {
                    $escape = "\\u00" . bin2hex($c);
                }
                if ($unescaped_run !== "") {
                    $escaped_value .= $unescaped_run;
                    $unescaped_run = "";
                }
                $escaped_value .= $escape;
            } else {
              if ($unescaped_run === "") {
                $unescaped_run .= $c;
              }
            }
        }
        $escaped_value .= $unescaped_run;
        return $escaped_value;
    }
