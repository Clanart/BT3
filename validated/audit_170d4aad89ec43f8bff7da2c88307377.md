### Title
Overpaid native-token dispatch fees are refunded to the `EvmHost` contract instead of the original caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward `msg.value` directly to `IUniswapV2Router02.swapETHForExactTokens` to swap native token for the exact `feeToken` amount required, but never account for or return unspent ETH to the original caller. Because the swap call is made by `EvmHost` itself, any refund the router/wrapper issues for "extra ETH sent" goes back to `EvmHost`'s own balance, not to `_msgSender()`. This mirrors the external report's core defect — a payable bridging entrypoint that mishandles the native-currency fee mechanics of an underlying payable call — except here the mismatch causes silent, permanent loss of user funds rather than an outright revert.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

the same unguarded pattern appears in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

In each case, `msg.value` is passed wholesale to `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The router/wrapper implementation used by Hyperbridge (`UniV3UniswapV2Wrapper.swapETHForExactTokens`) computes `spent` (actual ETH consumed for the exact `feeToken` output) and refunds the difference — but the refund target is `msg.sender` of that call: [4](#0-3) 

Since `EvmHost` itself is the caller of the router (not the end user who invoked `dispatch()`), `msg.sender` in the wrapper resolves to `EvmHost`'s address. Any ETH sent by the user above the exact fee requirement is refunded into `EvmHost`'s own balance and is never forwarded back to `_msgSender()`. `EvmHost` contains no logic after the swap call to detect or return this leftover balance to the original depositor, and the only privileged native-value management visible is via `IHostManager` fee-token/param updates, not a native ETH sweep-and-refund-to-user path.

The application-level docs explicitly instruct integrators to over-provision `msg.value` because on-chain `quote()` is sandwich-vulnerable and should only be used off-chain as an estimate: [5](#0-4) 

This guidance guarantees that real-world callers will routinely send `msg.value` greater than the exact fee, and every such overpayment is siphoned into the Host contract with no recovery mechanism for the sender.

### Impact Explanation
This is a direct loss-of-funds bug on the primary EVM bridging entrypoints (`dispatch`, `fundRequest`) used by every Hyperbridge application (`HyperFungibleToken.send`, `ExtrinsicIntents`, `IntentGatewayV2`, `HyperbridgeLzEndpoint`, etc.), all of which forward `msg.value` to `EvmHost.dispatch`: [6](#0-5) [7](#0-6) 

Any unprivileged user who slightly overestimates the native fee (which the docs actively encourage to avoid reverts from price movement/sandwiching) permanently loses the excess ETH — it accumulates in `EvmHost` with no user-facing or even admin-facing withdrawal path identified. This satisfies the bounty's "stealing or loss of funds" impact criterion without requiring any malicious peer, relayer, or governance actor.

### Likelihood Explanation
High. This triggers under completely normal, expected usage — not an edge case — because:
1. The exact `feeToken` price of ETH is variable and only estimable off-chain per the project's own documentation.
2. Any caller who is cautious (sends a small buffer to avoid revert) automatically forfeits the buffer amount every single dispatch call.
3. No attacker action, front-running, or malicious infrastructure is required — the loss occurs purely from the contract's own fee-forwarding logic.

### Recommendation
After the `swapETHForExactTokens` call inside `EvmHost.dispatch`/`dispatch(DispatchGet)`/`fundRequest`, capture `EvmHost`'s ETH balance delta (or have the wrapper return the actual `spent` amount) and refund any leftover native token directly to `_msgSender()` (or the designated `payer`), rather than allowing it to be silently absorbed into the Host's own balance.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires the ETH-equivalent of 0.9 ether (either because the on-chain feeToken price is slightly better than off-chain, or the user intentionally overpaid for safety).
2. `EvmHost.dispatch` forwards the full `1 ether` to `swapETHForExactTokens{value: 1 ether}(post.fee, ...)`.
3. Inside the wrapper, `spent` (~0.9 ether) is used for the swap; the remaining ~0.1 ether refund is sent to `msg.sender`, which is `EvmHost`, per: [4](#0-3) 
4. `EvmHost.dispatch` completes successfully, emits `PostRequestEvent`, and returns — but the user's 0.1 ether excess is now permanently part of `EvmHost`'s contract balance with no code path to reclaim it for the user.
5. Repeating this over many transactions accumulates unrecoverable ETH inside `EvmHost`, confirming systemic fund loss.
