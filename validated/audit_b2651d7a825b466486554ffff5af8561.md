### Title
Scanner accepts arbitrarily low-value outputs, letting anyone force the coordinator to burn fees or stall scheduling with dust UTXOs - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a check that only constrains a per-unit value (`pricePerToken < existing`) while ignoring the total value committed (`collateral`), letting an attacker grief the protocol with a negligible-cost action. In Serai's Bitcoin stack, `Scanner::scan_transaction` accepts any output paying to a registered `script_pubkey` regardless of `value`, and the processor's `get_outputs`/`Scheduler` unconditionally ingests those outputs as spendable UTXOs. An unprivileged sender can therefore create arbitrarily many dust-value outputs to a multisig's publicly derivable addresses, forcing the coordinator to schedule and sign aggregation spends whose input values are below the cost of spending them.

### Finding Description
`Scanner::scan_transaction` matches solely on `output.script_pubkey` and pushes a `ReceivedOutput` for every match with no minimum-value check:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-214
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

`processor/src/networks/bitcoin.rs` `get_outputs` (lines 686-739) converts each match into an `Output` and hands it to the scheduler. `Scheduler::schedule` (`processor/src/multisigs/scheduler/utxo.rs`) then treats every received output as a UTXO: it sorts by value, chunks them into `N::MAX_INPUTS` (520) groups, and emits aggregation `Plan`s for all chunks beyond the first — unconditionally, with no `value >= DUST` or `value >= COST_TO_AGGREGATE` filter (lines 358-385). The `DUST`/`COST_TO_AGGREGATE` constants only gate payments the protocol *creates* (`bitcoin.rs:441`, `mod.rs` `amortize_fee`), never inputs it *receives*.

All four scanned scripts (External, Branch, Change, Forwarded) are deterministic functions of the public group key (`processor/src/networks/bitcoin.rs:333-344`, `661-674`), so anyone who knows a multisig's address can send to any of them.

### Impact Explanation
- Every dust input must eventually be spent: spending a Taproot input costs ~57 vbytes (≈ the documented `COST_TO_AGGREGATE`/fee math at `bitcoin.rs:638-646`), which exceeds a ~546-sat dust output. The coordinator signs transactions whose fee attributable to the attacker's inputs exceeds their value — a direct, forced value burn, exactly the "negligible collateral blocks/burdens the protocol" shape from the report.
- `make_signable_transaction` panics on `TooLargeTransaction` and `DustPayment` (`bitcoin.rs:460-469`) under the assumption these states are unreachable; mass dust injection plus `force_spend` (`assert!(self.utxos.len() <= N::MAX_INPUTS)`, `utxo.rs:424`) on multisig retirement can push `self.utxos` beyond limits the code asserts on.
- Cost to attacker is one transaction's fee plus dust amounts; cost to the protocol is an unbounded number of threshold-signing sessions and permanently inflated `self.utxos` state serialized to disk on every mutation (`utxo.rs:109-143` notes the reserialize cost).

### Likelihood Explanation
Requires only sending Bitcoin transactions to a public, deterministic address — fully unprivileged and reachable per the rules. It triggers whenever any `schedule`/`force_spend` runs, i.e., on routine payment processing and mandatory retirement sweeps. Consequence is economic griefing and potential scheduler stall, not key compromise — consistent with a Medium.

### Recommendation
Enforce a minimum received-value bound at ingestion: in `Bitcoin::get_outputs` (or `Scanner::scan_transaction`), skip outputs whose `value` is below `Bitcoin::DUST`/`COST_TO_AGGREGATE` (the analog of "require total collateral value to exceed the threshold, not just the per-unit price"). Outputs below the bound should be logged and ignored rather than queued as spendable, since they can never be spent profitably.

### Proof of Concept
1. Observe a live multisig's group key; derive its External/Branch/Forwarded P2TR scripts via `scanner(key)` offsets (`processor/src/networks/bitcoin.rs:333-344`).
2. In a single transaction, create N outputs of 546 sats each to those `script_pubkey`s.
3. `get_outputs` returns N `Output`s; `Scheduler::add_outputs` pushes them all into `self.utxos` (no plan matches dust amounts).
4. The next `schedule` call drains `self.utxos` into `utxo_chunks` and emits aggregation `Plan`s spending them (`utxo.rs:358-385`), or `force_spend` sweeps them on retirement — each input worth 546 sats costs ~57 vbytes × fee rate to include, so the coordinator burns more than the inputs are worth per chunk, and N > 520 risks the `assert!(self.utxos.len() <= N::MAX_INPUTS)` invariant.

Uncertainty note: I could not fully trace whether any upstream layer (e.g., the multisigs scanner event flow) filters sub-dust outputs before `schedule`; nothing in the searched code applies a value floor to received outputs, so the ingestion path appears unguarded as described.
