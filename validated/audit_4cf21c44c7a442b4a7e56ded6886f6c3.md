### Title
Disabled token pair conversion check bypassed on IBC timeout/error-ack refund path - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
The IBC callback path `ConvertCoinToERC20FromPacket`, used to refund a sender when an outbound ICS20 transfer times out or receives an error acknowledgement, converts native Cosmos coins into their ERC20 representation without checking whether the token pair's `Enabled` flag is `false`. This mirrors the RizRegistry bug pattern: a "disabled/shutdown" boolean flag that is not consistently enforced across all code paths that mutate state tied to that flag.

### Finding Description
When governance calls `ToggleConversion` to disable a token pair (analogous to a market "shutdown" in the reference report), the pair's `Enabled` field is flipped to `false` via `toggleConversion` [1](#0-0) . The two user-facing message handlers `ConvertERC20` and `ConvertCoin` route through `k.MintingEnabled(ctx, ...)` before performing any conversion [2](#0-1) [3](#0-2) , and the direct IBC receive path (`OnRecvPacket`, Case 2) also explicitly re-checks `pair.Enabled` before minting [4](#0-3) .

However, `ConvertCoinToERC20FromPacket` — invoked from `OnAcknowledgementPacket` on a failed ack and from `OnTimeoutPacket` on timeout — only checks `params.EnableErc20` (global switch) and `k.IsDenomRegistered` (existence), but never checks `pair.Enabled` before calling `k.ConvertCoinNativeERC20`: [5](#0-4) 

`ConvertCoinNativeERC20` itself performs no `Enabled` check either — it unconditionally escrows coins on the module account and calls `transfer` on the ERC20 contract to unescrow tokens to the receiver, then burns the escrowed coins [6](#0-5) .

### Impact Explanation
If a token pair is disabled by governance (e.g., because the underlying ERC20 contract is known to be malicious, buggy, has an inconsistent supply, or is being phased out — the direct analog of a "shutdown" lending market), an outbound ICS20 transfer of that denom that later times out or receives an error acknowledgement will still be converted to the ERC20 representation via the unguarded path, bypassing the governance-intended freeze. This can result in unauthorized minting/extraction of ERC20-side value for a token pair explicitly marked disabled, and can be combined with the `IsNativeERC20` self-destruct handling in `ConvertERC20`/`ConvertCoin` (which deletes the pair on a suicided contract) to interact with stale/removed pair state in ways not exercised by the guarded paths, creating accounting inconsistency between the bank-side coin supply and ERC20-side token balances for a pair the protocol intended to be frozen. This matches the Critical impact class of irreversible accounting corruption / unauthorized extraction of token-pair-backed balances.

### Likelihood Explanation
Triggering `OnTimeoutPacket` or an error acknowledgement is achievable by an ordinary user/relayer through normal IBC transfer usage (e.g., sending to a channel destined to time out, or a counterparty that returns an error ack) — no privileged access is required. The only precondition is that governance has toggled a token pair to `Enabled = false` while a native-ERC20-backed coin transfer is in flight, which is a normal expected sequence when responding to an incident.

### Recommendation
Add an explicit `pair.Enabled` check inside `ConvertCoinToERC20FromPacket`'s `IsNativeERC20` case (mirroring the check already present in `OnRecvPacket`), and/or push the `Enabled` check down into `ConvertCoinNativeERC20` itself so all callers are guaranteed consistent enforcement, similar to how the RizRegistry fix suggested centrally enforcing the shutdown flag rather than relying on each call site to remember to check it.

### Proof of Concept
1. Register a native ERC20 token pair; user holds the ERC20 tokens and sends an ICS20 transfer of the corresponding coin outbound (which triggers `ConvertERC20`-style escrow flow prior to transfer, or the coin is otherwise obtained).
2. Governance calls `MsgToggleConversion` to disable the pair, setting `Enabled = false` (e.g., in response to detecting an issue with the ERC20 contract) — verified via `toggleConversion` at [1](#0-0) .
3. The in-flight IBC transfer times out (or the counterparty returns an error acknowledgement).
4. `OnTimeoutPacket`/`OnAcknowledgementPacket` invokes `ConvertCoinToERC20FromPacket`, which reaches the `IsNativeERC20` case and calls `ConvertCoinNativeERC20` without checking `pair.Enabled` [5](#0-4) .
5. The sender receives freshly unescrowed ERC20 tokens for a pair that governance explicitly disabled, bypassing the intended freeze that is enforced everywhere else (`OnRecvPacket`, `ConvertERC20`, `ConvertCoin`).

Note: I was unable to fully verify the internals of `MintingEnabled` (in `x/erc20/keeper/mint.go`) within the available tool budget to confirm exactly which checks it performs, though its single call site confirms it gates the two direct message-based conversion paths; this does not affect the core finding since `ConvertCoinToERC20FromPacket` does not call `MintingEnabled` at all.

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil
}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}
