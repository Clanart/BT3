### Title
Forfeited vlMGP/mWomSV rewards are redistributed via an instantly-updated `rewardPerTokenStored`, allowing JIT stakers to capture value forfeited by long-term lockers - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` (and its mWomSV analog `mWOMSVBaseRewarder`) forfeits a portion of a locker's claimed reward when that account's `rewardablePercentWAD` is below 100%, and instantly re-injects the forfeited amount into the *same* pool's `rewardPerTokenStored` accumulator, which is shared by all currently-staked balances. Because staking a vlMGP/mWomSV balance is immediate (locking MGP mints vlMGP and stakes it into the rewarder with `userRewardPerTokenPaid` set to the current value) while extracting the resulting reward via `getReward()` does not require waiting out the unlock cooldown, an attacker can deposit right before a forfeiture event and immediately siphon a pro-rata share of value that was meant to be redistributed to existing, patient lockers.

### Finding Description
`vlMGPBaseRewarder.queueMGP()` computes a `forfeitAmount` for the claiming account based on `_calExpireForfeit`, which uses `vlMGP.getRewardablePercentWAD(_account)`: [1](#0-0) 

Forfeited amounts (and forfeitures arising from `getRewards`/`_sendReward` on other reward tokens) are re-queued without a fresh token transfer, directly bumping `rewardInfo.rewardPerTokenStored` in proportion to `totalStaked()` at that instant: [2](#0-1) [3](#0-2) 

Any account with a staked balance in the pool earns pro-rata from `rewardPerToken()` since the last time its `userRewardPerTokenPaid` was synced: [4](#0-3) 

`_updateFor` re-syncs `userRewardPerTokenPaid` to the *current* value on every balance-changing action (deposit/lock), meaning a brand-new staker's checkpoint starts exactly at the pre-forfeit value: [5](#0-4) 

This is structurally identical to the reported bug class: a value-distribution event that increases a shared per-unit accumulator (analogous to `assetsPerShare`) without gating who benefits by how long they've held their position. Any wallet can lock MGP into `VLMGP` (minting/staking vlMGP into the rewarder) immediately before a victim (or itself, in a self-serving pattern) triggers a reward claim that forfeits a chunk of the victim's rewards due to a low `rewardablePercentWAD`, then call `getReward()`/`getRewards()` on the rewarder to immediately withdraw its share of the freshly-redistributed forfeited tokens — without needing to wait for the vlMGP unlock cooldown, since claiming rewards is decoupled from unlocking principal. The identical pattern exists in `mWOMSVBaseRewarder.sol` for mWomSV lockers.

### Impact Explanation
Reward tokens forfeited by long-term/legitimate lockers (intended to reward patient, high-`rewardablePercentWAD` participants) can be diverted to opportunistic same-block/near-block stakers who have no real economic stake in the protocol beyond the instant needed to capture the redistribution. This is a direct theft of unclaimed yield that should have accrued to honest lockers, extractable as real ERC20 reward tokens via `getReward`/`getRewards` without needing to unwind the locked principal.

### Likelihood Explanation
Locking MGP into `VLMGP` is a normal, unprivileged, permissionless action, and staking into the rewarder happens automatically and instantly upon lock. Forfeiture events occur routinely whenever any locker with `rewardablePercentWAD < 100%` claims rewards (i.e., not just an admin-triggered rare edge case), making the "next forfeit event" a frequent, low-effort target for a bot watching the mempool/state, especially since capital deployed can remain locked and reused across many forfeiture cycles rather than needing a fresh flash-loan each time.

### Recommendation
Do not let forfeited rewards instantly bump the shared `rewardPerTokenStored` for currently-staked balances. Instead: (1) require a minimum holding duration since the last balance change before a staker's balance counts toward `totalStaked()` for the purpose of forfeit distribution, or (2) stream/vest re-queued forfeit amounts into `rewardPerTokenStored` over a time window (similar to how `queueNewRewards`/`_provisionReward` could apply a linear release), or (3) route forfeited amounts to a treasury/redistribution path gated by a time-weighted checkpoint rather than instantaneous `balanceOf`.

### Proof of Concept
1. Attacker calls `VLMGP.lockFor`/lock to mint vlMGP and get an immediate stake recorded in `vlMGPBaseRewarder` (balance set, `userRewardPerTokenPaid` synced to current `rewardPerToken`) — see `_updateFor` at [5](#0-4) .
2. A victim (or the attacker triggering a claim on a low-`rewardablePercentWAD` account through `MasterMagpie`) calls a claim path that routes into `vlMGPBaseRewarder.queueMGP` or `getReward`/`getRewards`, causing `_calExpireForfeit` to forfeit part of that account's reward: [1](#0-0) .
3. The forfeited amount is re-queued via `_queueNewRewardsWithoutTransfer`, raising `rewardPerTokenStored` for the whole pool instantly: [2](#0-1) .
4. Attacker immediately calls `getReward`/`getRewards` on `vlMGPBaseRewarder`, and `_earned`/`earned` compute a payout proportional to the attacker's balance over the newly-inflated `rewardPerToken`, letting the attacker withdraw real reward tokens sourced from the victim's forfeiture despite having just entered the pool: [4](#0-3) .

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }
