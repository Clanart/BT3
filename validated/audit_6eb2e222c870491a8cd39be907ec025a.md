## Title
Stale line-selection indices are applied to a freshly re-fetched diff at commit time, silently corrupting partial commits — (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
The reported bug class is a "value mismatch between two computations that are assumed to stay in sync": one code path computes a value (`amount + txBaseCost`), a second path independently re-derives a different value (`txBaseCost` only) and asserts them equal, causing either silent value loss or unconditional revert. GitHub Desktop has a structurally identical pattern in its **partial-commit / line-selection** pipeline: the line indices a user selects are computed against *one* rendering of `git diff`, but at commit time a **second, independently fetched** diff is used to interpret those same indices, with no re-validation that the two diffs still agree on hunk layout.

### Finding Description
When a user does a partial commit (staging only some lines/hunks of a file), the UI stores the selection as a set of **absolute line indices** (`DiffSelection`, keyed by `hunk.unifiedDiffStart + lineIndex`) computed against the diff that was fetched when the file was last (re)selected in `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

At commit time, `_commitIncludedChanges` simply takes the currently cached `WorkingDirectoryFileChange` objects (with their previously-computed `.selection`) and passes them to `createCommit`/`stageFiles`, with no diff re-validation step performed inline before staging: [2](#0-1) 

`stageFiles` routes any partially-selected file to `applyPatchToIndex`, which **independently re-fetches the working directory diff from disk right before staging**: [3](#0-2) 

`formatPatch` then reuses the *old* `file.selection.isSelected(absoluteIndex)` object against the *hunks of this newly fetched diff*: [4](#0-3) 

The only place that reconciles a selection with a changed diff (`withSelectableLines`, dropping indices that no longer exist) is `updateChangesWorkingDirectoryDiff`, which only runs when the UI actively reloads the diff for the selected file (e.g., on selection change) — it is not guaranteed to run, and is not invoked, immediately before `applyPatchToIndex` re-fetches the diff a second time: [5](#0-4) 

This is the exact broken invariant from the report: two values (the diff the selection indices were computed against, and the diff `formatPatch` actually walks) are assumed identical but are computed independently and can diverge. If the tracked file's content changes on disk between the last diff render and the "Commit" click — e.g., because the cloned repository ships a file watcher / dev server / format-on-save tooling that rewrites tracked files as part of the developer's normal workflow — hunk boundaries and `unifiedDiffStart` offsets shift. `formatPatch` then applies the stale absolute indices to the new hunk layout, silently including/excluding the *wrong* lines (or including lines the user never selected) when generating the patch fed into `git apply --cached`. Unlike the ZkStack case there is no explicit invariant check (like `mintValue == msg.value`) — so instead of a hard revert, Desktop fails softly: the patch still applies (since `git apply` only checks context-line correctness, not user intent), and the wrong content is committed without any error or warning to the user.

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes." A user reviewing and selecting specific lines to include in a commit could end up committing different lines than what they visually approved — including potentially secrets, debug code, or unrelated changes they explicitly deselected, or omitting lines they intended to include. Because `git apply --cached` succeeds without complaint as long as context lines are locally consistent, there is no error surfaced to the user; the corrupted commit is created and can be pushed before the discrepancy is noticed.

### Likelihood Explanation
This requires the tracked file to be modified on disk between the diff render and the click of "Commit" — which is a realistic occurrence in normal developer workflows for a repository that ships (as part of its normal, not "unnatural," usage) an auto-formatter, linter-on-save, or file-watching build/dev process that rewrites source files while the user reviews the diff pane. No local/physical access, admin rights, or pre-existing host compromise is required; the only requirement is that the user is using tooling bundled with/recommended by the cloned repository while Desktop is open, which is standard developer behavior. The window (time between diff load and hitting "Commit") is small but is not bounded, and larger diffs/slower typing of commit messages widen it.

### Recommendation
Before staging (`applyPatchToIndex`/`stageFiles`), re-validate that the diff used to compute `file.selection` still matches the diff about to be used to build the patch (e.g., compare diff `text`/hash, or recompute `selectableLines` and diff hunk boundaries) and abort/re-prompt the user if they differ, rather than silently applying stale indices to new hunks. Alternatively, pass the exact `ITextDiff` object already held in `changesState.selection.diff` into `applyPatchToIndex` instead of re-fetching a new diff from `git diff`, and only fall back to a fresh diff if it matches invariant checks against the working tree.

### Proof of Concept
1. Open a repository in GitHub Desktop containing a file with an npm script/dev server configured to periodically rewrite a tracked source file (e.g., a code formatter running in watch mode as documented in the project's own tooling), or manually simulate this for testing.
2. Modify the file and stage only specific lines/hunks via the Changes view (partial selection), leaving the "Commit" dialog open.
3. Let the background process rewrite the file (adding/removing lines above the selected hunk, shifting hunk boundaries) before clicking "Commit".
4. Click "Commit". Because `applyPatchToIndex` (`app/src/lib/git/apply.ts` line 60) re-fetches the diff and `formatPatch` (`app/src/lib/patch-formatter.ts` lines 143-171) reuses the stale `file.selection` indices against the new hunk offsets, inspect the resulting commit (`git show`) — it will contain lines that differ from what was visually selected in the UI, with no error reported by Desktop.
