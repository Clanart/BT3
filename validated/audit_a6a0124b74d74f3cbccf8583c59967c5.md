### Title
Committed Approval + Attacker-Controlled EVM Call Before Completion Check in `IBCReceivePacketCallback` Can Persist State Even on Callback Failure — ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
The Sablier `_cancel()` bug is a "commit state / transfer control to an untrusted party, then finalize invariant" ordering flaw. The same shape exists in `IBCReceivePacketCallback`: the function grants an ERC20 `approve` to an attacker-specified `contractAddress`, executes arbitrary, attacker-controlled EVM code with that approval **inside a cached context**, calls `writeFn()` to commit that cached context back into the real state, and only *afterwards* checks the invariant that the isolated receiver's balance must be fully drained. Because the commit (`writeFn()`) happens before the invariant is verified, a failing invariant check returns an error *after* the untrusted call's side effects (approval usage, any state it mutated) are already durably written.

### Finding Description
`IBCReceivePacketCallback` [1](#0-0)  processes an ICS-20 `dest_callback` memo pointing at an arbitrary, sender-controlled `contractAddress` on the destination chain.

The sequence is:
1. Branch a cached context: `cachedCtx, writeFn := ctx.CacheContext()` [2](#0-1) .
2. `approve(receiverHex, contractAddr, amountInt)` is executed on `cachedCtx`, granting the untrusted contract an allowance over the isolated receiver's freshly-minted/unescrowed ERC20 balance [3](#0-2) .
3. Arbitrary attacker-supplied calldata is executed against `contractAddr` via `CallEVMWithData(cachedCtx, ...)` [4](#0-3) . This is fully attacker-controlled code with an active allowance, running before any invariant is enforced.
4. `writeFn()` commits the cached context — **including whatever the untrusted contract did with its allowance** — into the real `ctx` [5](#0-4) .
5. Only *after* that unconditional commit does the code check that the isolated receiver's ERC20 balance is now zero, to "prevent funds from getting stuck" [6](#0-5) . If this check fails, the function returns an error.

Per the module's own documentation, an error returned here is translated into an `ErrAck` for the whole `OnRecvPacket` [7](#0-6) , which is exactly the ICS-20 signal that causes the **source chain to refund/unescrow** the sender's original funds (standard ICS-20 ack semantics). However, the underlying mint/unescrow of the ERC20 representation on the destination chain, and the approval usage/side effects the untrusted contract performed with `cachedCtx` in step 3, were already flushed to `ctx` via `writeFn()` in step 4 — *before* the failure was detected. Nothing in this function rolls back the `writeFn()` commit when the post-check subsequently fails.

This mirrors the Sablier pattern precisely: the guarding invariant ("recipient's callback must fully account for funds") is checked *after* control and effects have already been irreversibly handed to/committed by an untrusted party, rather than before.

### Impact Explanation
If the destination-chain state mutations performed inside `cachedCtx` (approval consumption, and any other effects the attacker-controlled contract triggers while holding that approval) are retained in `ctx` after `writeFn()`, while the overall packet is subsequently failed via `ErrAck` (triggering a refund/unescrow on the source chain), the same value effectively exists twice — once refunded to the original sender on the source chain, and once already spent/moved on the destination chain by the attacker-controlled contract before the check that was supposed to prevent this could take effect. This falls under the allowed "Critical unauthorized duplication ... of spendable user value across ... IBC escrows" impact class, since it breaks the 1:1 accounting invariant between the escrowed/minted representation and the ack-driven refund path.

### Likelihood Explanation
The `contractAddress` and calldata for `dest_callback` are fully controlled by the IBC packet sender (attacker on the counterparty chain, or a spoofed relayed packet within the callback data model documented in the README) [8](#0-7) . No privileged party is required — any user who can originate/relay an ICS-20 packet with a `dest_callback` memo pointing to their own deployed contract can control the arbitrary EVM execution described here. This gives an unprivileged actor a fully reachable path to reorder "approve → untrusted execution → commit → check" and attempt to leave commit-then-fail residue.

### Recommendation
Do not call `writeFn()` until *after* the completeness/invariant check (`receiverTokenBalance == 0`) has passed. Perform the balance check against `cachedCtx` (the uncommitted branch) before calling `writeFn()`, and only commit if the invariant holds; otherwise, discard `cachedCtx` entirely so no attacker-influenced state (including the approval and its consumption) is ever persisted to `ctx` when the callback is deemed to have failed. This restores the correct pattern of "verify effects, then commit," analogous to Sablier's recommended fix of validating/finalizing bookkeeping before yielding control/state to an untrusted party.

### Proof of Concept
Conceptual PoC (exact reachability of `ErrAck` semantics from `ibc-go`'s callbacks middleware could not be independently verified within this repository, since that middleware wiring lives in the vendored `ibc-go` dependency and `evmd/app.go`, which time did not allow fully tracing):
1. Attacker on chain B sends an ICS-20 transfer to chain A with a `dest_callback` memo whose `address` is an attacker-deployed contract and whose `calldata` triggers partial or non-standard use of the granted `approve` allowance (e.g., calls `transferFrom` for less than the full amount, or performs other side-effecting logic without fully draining `receiverHex`).
2. `IBCReceivePacketCallback` runs: `approve()` executes, the attacker contract executes with that approval inside `cachedCtx`, then `writeFn()` unconditionally commits those effects to `ctx`.
3. The post-check `receiverTokenBalance != 0` fails (attacker deliberately left a nonzero balance or performed other lasting side effects), causing the function to return an error.
4. Per the documented behavior, this failure surfaces as an `ErrAck`, causing the source chain (chain B) to refund the sender.
5. Result: chain A already has the committed (from step 2) mutations caused by the untrusted contract, while chain B independently refunds the same value — a duplication of spendable value across the two chains' escrow/mint accounting.

**Confidence caveat:** I was not able to fully verify, within this repository, the exact `ibc-go` v10 callbacks-middleware behavior for translating a `ContractKeeper` error into an ack (whether it truly overrides an already-successful ack after the underlying transfer already committed its mint/unescrow), because that logic resides in the external `ibc-go` dependency rather than in `blackvul/push-chain-evm--002`. The `writeFn()`-before-invariant-check ordering itself, however, is directly confirmed in `x/ibc/callbacks/keeper/keeper.go`, and constitutes the root-cause ordering flaw analogous to the Sablier report regardless of the exact downstream ack-handling behavior.
