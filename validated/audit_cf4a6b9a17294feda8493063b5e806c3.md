## Analysis: VWAPOracle has no observation window — every fill is a "period" (analogous to TWAP `periodSize = 0`)

Reducing the external report to its core primitive: a TWAP-style oracle that is supposed to average price observations over a *time window* was configured to update on **every single observation event** (no throttling), letting an attacker flood it with self-generated observations and instantly move the aggregate that downstream logic trusts.

The local analog is `VWAPOracle` at `evm/src/utils/VWAPOracle.sol`, used by `IntentGatewayV2` as `_params.priceOracle` to track a cumulative volume-weighted spread per `(sourceChain, token)` [1](#0-0) .

### Title
Unbounded, unthrottled cumulative VWAP in `VWAPOracle.recordSpread` lets a self-filled intent instantly manipulate the on-chain price/spread oracle - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle` is documented as a "gas-efficient oracle for tracking cumulative VWAP spreads" [2](#0-1) . Unlike a real TWAP/VWAP, it has **no window, no decay, and no minimum-volume or minimum-time gate at all** — every single `recordSpread` call (triggered automatically by `IntentGatewayV2.fillOrder`) is folded directly into an all-time cumulative sum: [3](#0-2) 

This is the same broken invariant as the H-04 report's `periodSize = 0`: the "averaging window" collapses to a single observation, so one large, freely-chosen observation dominates the reported price instead of it being smoothed over time or volume history.

### Finding Description
`fillOrder` is a permissionless, public entrypoint [4](#0-3) . When solver selection is disabled (the default unless explicitly configured), any address can both create an order (as `order.user`) and fill it themselves as the solver, since nothing binds `order.user != msg.sender` in the fill path shown. On successful fill, `IntentGatewayV2` unconditionally calls `IIntentPriceOracle(priceOracle).recordSpread(...)` with the *order's own declared* `inputs` and the *filler-supplied* `outputs.amount` [5](#0-4) .

Inside `recordSpread`, the attacker fully controls:
- `inputAmountNormalized` / `outputAmountNormalized` (the order's own token amounts, only bounded by what the attacker actually escrows/pays for a same-token swap),
- and therefore `spreadBps` and the resulting `weightedSpread = spreadBps * inputAmountNormalized` [6](#0-5) .

Because `_updateCumulativeSpread` has no time window, no cap on `volume` per update, and no decay of historical sums, a single self-filled order with an outsized `amount` (relative to all prior organic volume) can dominate `weightedSpreadSum / totalVolume` instantly and permanently move `spread()` far from the true market spread — exactly the "one block/one call flips the whole average" failure mode that made `periodSize = 0` critical in the referenced report. The contract's own tests demonstrate that VWAP is dominated by whichever single fill has the largest volume, i.e. it explicitly shows large single fills drown out prior history [7](#0-6) ; the missing piece is any limiter preventing an attacker from injecting an arbitrarily large single fill (via wash-trading their own same-token order) to weaponize that dominance.

`spread()` is exposed as the protocol's canonical price-quality signal (`IIntentPriceOracle.spread`) [8](#0-7)  intended to reflect genuine filler behavior for a token pair across chains, which is precisely the "TWAP → `getUnderlyingPrice`"-style trust chain flagged in the original report: a manipulable low-integrity average feeding decisions elsewhere in the system.

### Impact Explanation
Any unprivileged actor can, in a single transaction, create and self-fill a same-token intent order with an artificially large input/output amount and an extreme (positive or negative) spread, permanently skewing the on-chain VWAP for that `(sourceChain, token)` pair. Since there is no periodSize/window/decay analog, the manipulation is not diluted over time the way a genuine VWAP/TWAP would be — the corrupted `weightedSpreadSum`/`totalVolume` state persists and continues to distort every subsequent `spread()` read until enough organic volume swamps it (which, for a fresh or low-volume pair, may never realistically happen). Any downstream consumer of `spread()` that uses it to price fills, gate solver incentives, or flag anomalous fills is fed false state — matching the Impact Gate's "false proof/state acceptance" and "logic attacks" categories.

### Likelihood Explanation
High. `fillOrder` and `recordSpread`'s invocation from it require no special privilege — only that `solverSelection` isn't force-binding the filler to a third party, and even where solver selection is enabled, whoever is selected still fully controls the `outputs` amounts and can pick `inputs`/`outputs` to any same-token pair they choose to escrow to themselves. The cost of the attack is only the (self-returned) token amount plus gas — a wash trade — since input and output tokens are the same asset for the pair being manipulated.

### Recommendation
Introduce an actual bounded window/decay mechanism (analogous to a non-zero `periodSize`), e.g.:
- Cap the influence of a single fill via a maximum `volume`-per-update relative to a rolling total, or
- Maintain a time-decayed / fixed-window (e.g., last N fills or last T seconds) VWAP instead of an unbounded all-time cumulative sum, and
- Require `order.user != msg.sender` (or otherwise attribute/discount self-fills) before counting a fill's spread toward the oracle, to remove the wash-trade primitive entirely.

### Proof of Concept
1. Attacker deploys/holds token `T` on both `sourceChain` and `destChain` (same-token swap, as required by `VWAPOracle`'s design).
2. Attacker calls `IntentGatewayV2.fillOrder` for a same-chain order they placed themselves as `order.user`, with `inputs = [T, X]` and `options.outputs = [T, Y]` chosen so that `Y` is far from `X` (e.g., `Y = 100 * X` to produce a huge positive `spreadBps`), and `X` set to a volume that dwarfs the pair's historical `totalVolume`.
3. `fillOrder` succeeds (no check preventing `order.user == msg.sender` when solver selection is off) and unconditionally calls `priceOracle.recordSpread(...)` with these attacker-chosen values [1](#0-0) .
4. `VWAPOracle._updateCumulativeSpread` folds this single fill directly into the permanent cumulative sums with no throttling [3](#0-2) , so `spread(sourceChain, T)` [9](#0-8)  now reports a value dominated by the attacker's single fake fill, as the contract's own volume-domination tests confirm is possible with just one outsized fill [7](#0-6) .

Note: I was not able to locate (within this pass) an on-chain consumer inside `IntentGatewayV2` itself that reads `spread()` back to gate fund movement — `spread()` is exposed purely as a view for external/solver consumption per the `IIntentPriceOracle` interface. The severity of fund impact therefore depends on how off-chain solvers/relayers or other not-yet-indexed contracts consume this value; this should be verified with a full-repo search (a Devin session) before treating this as a confirmed high-severity fund-loss path, since the current evidence firmly establishes the manipulable-oracle primitive but not a directly provable "funds moved to wrong beneficiary" execution path in the indexed code.

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }

        if (_params.priceOracle != address(0)) {
            IIntentPriceOracle(_params.priceOracle)
                .recordSpread(commitment, order.source, order.inputs, options.outputs);
        }
    }

    function spread(bytes memory sourceChain, address token) external view returns (int256) {
        bytes32 chainHash = keccak256(sourceChain);
        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
        if (data.totalVolume == 0) return 0;

        return data.weightedSpreadSum / int256(data.totalVolume);
    }

    function _updateCumulativeSpread(CumulativeSpreadData storage data, int256 weightedSpread, uint256 volume) private {
        data.weightedSpreadSum += weightedSpread;
        data.totalVolume += volume;
        data.fillCount += 1;
        data.lastUpdate = block.timestamp;
    }

        // Fill 2: 1 million tokens, -10 bps
        TokenInfo[] memory inputs2 = new TokenInfo[](1);
        TokenInfo[] memory outputs2 = new TokenInfo[](1);
        inputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1_000_000 * 1e18});
        outputs2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 999_000 * 1e18});
        oracle.recordSpread(keccak256("order2"), sourceChain, inputs2, outputs2);

        int256 vwap = oracle.spread(sourceChain, address(dai));

        // VWAP: (1000*1 + -10*1000000) / 1000001 = (1000 - 10000000) / 1000001 ≈ -9.99 bps

        assertEq(vwap, -9, "VWAP should be approximately -10 bps");
