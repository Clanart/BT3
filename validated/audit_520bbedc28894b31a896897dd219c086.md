### Title
No Incentive to Send Challenge Transaction on Mainnet/Testnet4 Allows Fraudulent Operator Withdrawals to Go Unchallenged - (File: core/src/verifier.rs)

---

### Summary

On `Bitcoin` mainnet and `Testnet4`, the `Challenge` transaction is explicitly suppressed from automatic dispatch even when a malicious kickoff is detected. Verifiers must manually send it, paying `operator_challenge_amount` upfront directly to the operator with only a contingent, off-chain reimbursement path via Citrea. Without the challenge, the `KickoffStateMachine` never enters the `challenged` state, the disprove process is never triggered, and the operator can collect reimbursement for a fraudulent withdrawal, draining the bridge deposit.

---

### Finding Description

In `core/src/verifier.rs`, `handle_kickoff` detects malicious kickoffs but explicitly skips automatic challenge submission on mainnet and testnet4:

```rust
// do not automatically send challenge txs on mainnet or testnet4
if !challenged_before
    && !matches!(
        self.config.protocol_paramset().network,
        bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
    )
{
    #[cfg(feature = "automation")]
    self.tx_sender.add_tx_to_queue(
        dbtx,
        TransactionType::Challenge,
        &challenge_tx,
        ...
    ).await?;
}
``` [1](#0-0) 

The `Challenge` transaction is the mandatory gate for the entire fraud-proof pipeline. The `KickoffStateMachine` only transitions to the `challenged` state when the `Challenge` UTXO is spent by a transaction that is **not** the `ChallengeTimeout` tx:

```rust
self.matchers.insert(
    Matcher::SpentUtxoButNotTxid(
        OutPoint { txid: kickoff_txid, vout: UtxoVout::Challenge.get_vout() },
        vec![*challenge_timeout_txid],
    ),
    KickoffEvent::Challenged,
);
``` [2](#0-1) 

Only in the `challenged` state does the state machine arm watchtower challenge matchers, queue `AssertTimeout`/`OperatorChallengeNack`/`LatestBlockhashTimeout` transactions, and eventually trigger the disprove duty: [3](#0-2) 

The `Challenge` transaction itself carries a severe financial disincentive. Its output pays `operator_challenge_amount` (2 BTC in the test paramset, `operator_challenge_amount = 200000000`) directly to the **operator's reimbursement address**. The challenger's EVM address is only recorded in an `OP_RETURN` for a contingent Citrea-side reimbursement if the disprove succeeds: [4](#0-3) 

The `ChallengeTimeout` transaction, which the operator controls and queues automatically, spends the same `Challenge` UTXO after `operator_challenge_timeout_timelock` (144 blocks ≈ 1 day) if no challenge arrives. This finalizes the kickoff without fraud-proof, allowing the operator to proceed to `ReadyToReimburse` and then `Reimburse`: [5](#0-4) 

The `Reimburse` transaction spends the `MoveToVault` deposit UTXO directly, returning the full `bridge_amount` to the operator: [6](#0-5) 

The operator's own `get_reimbursement_txs` / `get_next_txs_to_send` logic confirms this path: if the challenge UTXO is **not** spent, it queues `ChallengeTimeout` and proceeds; it only errors if the challenge UTXO was already spent (i.e., a challenge was sent but automation is off): [7](#0-6) 

---

### Impact Explanation

If no verifier sends the `Challenge` transaction on mainnet/testnet4:

1. `KickoffStateMachine` stays in `kickoff_started`, never enters `challenged`.
2. No watchtower challenges, no asserts, no disprove are triggered.
3. After `operator_challenge_timeout_timelock` blocks, the operator sends `ChallengeTimeout`, spending the `KickoffFinalizer` UTXO.
4. The operator advances through `ReadyToReimburse` → `Reimburse`, spending the `MoveToVault` deposit UTXO.
5. The full `bridge_amount` (1,000,000,000 satoshis = 10 BTC per deposit) is transferred to the operator for a fraudulent withdrawal.
6. Bridge-controlled BTC is permanently lost; depositors cannot recover funds.

This is a direct loss of bridged BTC matching the "Critical/High/Medium theft, loss, permanent lock … of bridged BTC" criterion.

---

### Likelihood Explanation

The suppression is unconditional on mainnet/testnet4 — it is not a configuration flag but a hardcoded network check. Every verifier that detects a malicious kickoff on mainnet will log a warning and do nothing automatically. To challenge, a verifier must:

1. Manually identify the malicious kickoff from logs.
2. Decide to pay `operator_challenge_amount` (2 BTC) upfront to the operator.
3. Accept that reimbursement is contingent on a successful disprove **and** Citrea's collateral-reimbursement mechanism.
4. Accept that another verifier might challenge first (wasting their 2 BTC with no reimbursement path).

This is structurally identical to the Aloe `warn` problem: the party responsible for triggering the fraud-proof process faces an upfront cost with no guaranteed reward, and no party has a dominant incentive to act first. A rational verifier may wait for another to act, resulting in no challenge being sent within the timelock window.

---

### Recommendation

1. **Remove the mainnet/testnet4 suppression** or replace it with a configurable flag (`auto_challenge_on_mainnet`) that operators can enable after review, rather than a hardcoded network exclusion.
2. **Provide a direct on-chain incentive** for the challenger: route a portion of the operator's collateral (burned on disprove) to the challenger's Bitcoin address, not only via Citrea's EVM reimbursement path.
3. **Implement a rotating or threshold-based duty**: if no challenge is detected within N blocks of a malicious kickoff, the state manager should escalate and prompt all verifiers to challenge, reducing the free-rider problem.

---

### Proof of Concept

1. Operator sends a kickoff committing a fraudulent `payout_blockhash` (a block that does not contain the claimed payout tx).
2. All verifiers call `handle_kickoff` → `is_malicious = true`.
3. Network is `Bitcoin::Bitcoin` → the `if` branch is skipped; no `Challenge` tx is queued.
4. No verifier manually sends the challenge (financial disincentive: 2 BTC upfront, uncertain reimbursement).
5. After `operator_challenge_timeout_timelock` (144 blocks), the operator's pre-queued `ChallengeTimeout` tx is broadcast, spending both the `Challenge` UTXO and `KickoffFinalizer` UTXO.
6. `KickoffStateMachine` receives `KickoffFinalizerSpent` → transitions to `closed`.
7. Operator sends `ReadyToReimburse` → `Round` (next) → `Reimburse`.
8. `Reimburse` spends the `MoveToVault` deposit UTXO, transferring 10 BTC to the operator.
9. Bridge deposit is drained; no fraud-proof was ever triggered.

/// Creates a [`TxHandler`] for the `challenge` transaction.
///
/// This transaction is used to reimburse an operator for a valid challenge, intended to cover their costs for sending asserts transactions,
/// and potentially cover their opportunity cost as their reimbursements are delayed due to the challenge. This cost of a challenge is also
/// used to disincentivize sending challenges for kickoffs that are correct. In case the challenge is correct and operator is proved to be
/// malicious, the challenge cost will be reimbursed using the operator's collateral that's locked in Citrea.
///
/// # Inputs
/// 1. KickoffTx: Challenge utxo
///
/// # Outputs
/// 1. Operator reimbursement output
/// 2. OP_RETURN output (containing EVM address of the challenger, for reimbursement if the challenge is correct)
///
/// # Arguments
///
/// * `kickoff_txhandler` - The kickoff transaction handler that the challenge belongs to.
/// * `operator_reimbursement_address` - The address to reimburse the operator to cover their costs.
/// * `challenger_evm_address` - The EVM address of the challenger, for reimbursement if the challenge is correct.
/// * `paramset` - Protocol parameter set.
///
/// # Returns
///
/// A [`TxHandler`] for the challenge transaction, or a [`BridgeError`] if construction fails.
pub fn create_challenge_txhandler(
    kickoff_txhandler: &TxHandler,
    operator_reimbursement_address: &bitcoin::Address,
    challenger_evm_address: Option<EVMAddress>,
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler, BridgeError> {
    let mut builder = TxHandlerBuilder::new(TransactionType::Challenge)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Challenge,
            kickoff_txhandler.get_spendable_output(UtxoVout::Challenge)?,
            SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: paramset.operator_challenge_amount,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }));

    if let Some(challenger_evm_address) = challenger_evm_address {
        builder = builder.add_output(UnspentTxOut::from_partial(op_return_txout(
            challenger_evm_address.0,
        )));
    }

    Ok(builder.finalize())
}

/// Creates a [`TxHandler`] for the `reimburse_tx`.
///
/// This transaction is sent by the operator if no challenge was sent, or a challenge was sent but no disprove was sent, to reimburse the operator for their payout.
///
/// # Inputs
/// 1. MoveToVaultTx: Utxo containing the deposit
/// 2. KickoffTx: Reimburse connector utxo in the kickoff
/// 3. RoundTx: Reimburse connector utxo in the round (for the given kickoff index)
///
/// # Outputs
/// 1. Reimbursement output to the operator
/// 2. Anchor output for CPFP
///
/// # Arguments
/// * `move_txhandler` - The move-to-vault transaction handler for the deposit.
/// * `round_txhandler` - The round transaction handler for the round.
/// * `kickoff_txhandler` - The kickoff transaction handler for the kickoff.
/// * `kickoff_idx` - The kickoff index of the operator's kickoff.
/// * `paramset` - Protocol parameter set.
/// * `operator_reimbursement_address` - The address to reimburse the operator.
///
/// # Returns
/// A [`TxHandler`] for the reimburse transaction, or a [`BridgeError`] if construction fails.
pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
