### Title
`ThresholdKeys::read` accepts attacker-substituted key material without verifying share/verification-share consistency, allowing group-key substitution - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class of the external report — attacker-controlled content substituted at a secondary input path and consumed without an integrity check — maps onto `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg`. `read` deserializes `t`, `n`, `i`, the interpolation method, `secret_share`, and all `n` `verification_shares` purely syntactically (canonical `read_F`/`read_G` only). `ThresholdKeys::new` then derives `group_key` by interpolating `verification_shares[1..=t]` and never verifies the one relation that would bind the blob together: `C::generator() * secret_share == verification_shares[i]` for the holder's own index `i`, nor that the shares form any consistent polynomial. The serialized form carries no checksum, MAC, proof, or binding to a prior DKG transcript. The FROST code itself acknowledges this hole: `AlgorithmSignatureMachine::complete` notes that "everyone had a valid share yet the signature was still invalid" is reachable only by "deserializ[ing] a semantically invalid FrostKeys" [1](#0-0) .

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses the curve ID, params, interpolation variant (including an arbitrary `Constant` factor vector of length `n`), the secret share, and `n` verification shares, then calls `ThresholdKeys::new`. `new` (crypto/dkg/src/lib.rs:349-391) checks only:

- `verification_shares.len() == n` and each participant index `<= n` (lines 355-365),
- `Constant` interpolation implies `t == n` (lines 367-374),
- then computes `group_key = Σ verification_shares[i] * interpolation_factor(i, 1..=t)` for `i ∈ 1..=t` (lines 376-378).

Nothing authenticates the blob. An unprivileged party who can feed bytes to `ThresholdKeys::read` (an explicitly exposed deserialization entry point, used for keys imported outside PedPoP — e.g. vector import in `crypto/frost/src/tests/vectors.rs:118-131` and key-recovery/dealer flows) can construct a fully consistent-looking `ThresholdKeys` where:

- `secret_share = s_a` (attacker-chosen),
- `verification_shares[i] = G * s_a`,
- `verification_shares[j]` for `j ∈ 1..=t` all `G * s_j` for attacker-known `s_j`.

`new` accepts this and returns a `group_key` whose discrete log the attacker knows entirely. The victim node then operates a `ThresholdView` under that attacker-selected group key: `view()` interpolates `secret_share` and adds `offset` to `included[0]` normally [2](#0-1) , and FROST `sign`/`complete` produce valid signature shares and valid aggregate signatures under `group_key` (`AlgorithmSignMachine::sign`, crypto/frost/src/sign.rs:283-310; `complete` verifies against `view.group_key()`, crypto/frost/src/sign.rs:465-467).

This is the direct analog of the ZeroBrew bug: a secondary, non-primary input (the serialized key blob / verification shares rather than the protocol transcript) is substituted wholesale and "executed" (used as authoritative key material for all subsequent signing and scanning) with no integrity verification of the content.

### Impact Explanation
- **Group-key substitution**: the node's reported `group_key()` — the value Serai registers as a validator-set/network key (e.g. the key `Scanner::new`/`register_key` watch for on Bitcoin, `networks/bitcoin/src/wallet/mod.rs:162-166`, and the key asserted consistent across machines in `processor/src/key_gen.rs:484-489`) — is attacker-chosen, with an attacker-known secret. The attacker can forge any signature the system attributes to that threshold key.
- **Silent inconsistency**: if only some fields are substituted (e.g. `verification_shares` replaced while `secret_share` is the honest DKG output), the node emits shares that verify against attacker shares but produce `InternalError` or signatures under a group key unrelated to the real DKG — funds scanned to the substituted `group_key` are "reported received" under a key the honest share does not correspond to, and are either attacker-controlled or unspendable.

### Likelihood Explanation
Exploitation requires the attacker to supply bytes to `ThresholdKeys::read`. This is not reached through the PedPoP protocol messages (which build `ThresholdKeys` internally from verified shares), but is reachable wherever serialized key material is imported rather than regenerated — key recovery, backup restore, or cross-machine key migration paths — which is exactly the "secondary resource path" posture of the original CVE. Within that threat model the attack needs no collusion and no protocol participation; a single substituted blob fully determines the group key. Severity is bounded by how the integrator sources the blob; where it is attacker-influenced, the result is complete key substitution rather than mere malleability.

### Recommendation
- In `ThresholdKeys::new` (or `read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise.
- For `Interpolation::Constant`, verify the supplied factor vector is the expected binding-factor vector for the participant set rather than trusting it from the blob.
- Prefer reconstructing `verification_shares`/`group_key` from authenticated protocol output instead of serializing them; at minimum, authenticate the serialized blob (MAC or signature over it under a key established at DKG time) so `read` cannot be fed substituted material.

### Proof of Concept
```rust
// crypto/dkg: craft a ThresholdKeys blob whose group secret the attacker knows,
// with no DKG having taken place.
let n: u16 = 5; let t: u16 = 3; let i = Participant::new(1).unwrap();

// Attacker picks secret shares for the first t indexes (which define group_key)
// and the victim's own share, all with known discrete logs.
let known: Vec<C::F> = (0 .. n).map(|_| C::F::random(&mut OsRng)).collect();
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(u16::from(i).to_le_bytes());
buf.push(1); // Interpolation::Lagrange
buf.extend(known[usize::from(u16::from(i) - 1)].to_repr().as_ref()); // secret_share
for j in 1 ..= n {
    buf.extend((C::generator() * known[usize::from(j - 1)]).to_bytes().as_ref());
}

let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut buf.as_ref()).unwrap();
// Accepted. group_key interpolates verification_shares[1..=t] => attacker knows
// its discrete log (sum of Lagrange-scaled known[0..t]).
// keys.view(...).sign(...) now emits valid FROST shares under the attacker's key.
```

Note: reachability depends on an integrator feeding attacker-influenced bytes to `ThresholdKeys::read`; I could not confirm a network-reachable call site in the in-scope crates within the search budget — the finding holds wherever serialized keys are imported rather than produced by PedPoP/dealer locally.
