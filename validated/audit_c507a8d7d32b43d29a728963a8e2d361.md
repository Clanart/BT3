### Title
`BridgeTransferERC721.requestERC721Transfer` uses non-reverting `transferFrom` instead of `safeTransferFrom`/explicit success check, allowing cross-chain value creation for non-standard ERC721 tokens - (File: contracts/service_chain/bridge/BridgeTransferERC721.sol)

### Summary
`requestERC721Transfer`, a `public` function callable by any unprivileged bridge user, deposits an ERC721 into the bridge using the deprecated `transferFrom` call without checking that the token ownership actually changed, then unconditionally emits `RequestValueTransferEncoded` (and burns, in mint/burn mode) as if the deposit succeeded.

### Finding Description
`requestERC721Transfer` is a permissionless entry point reachable directly from any user-submitted transaction: [1](#0-0) 

It calls `IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId)` and then immediately proceeds to `_requestERC721Transfer`, which emits the cross-chain transfer request event and (in mint/burn mode) burns the token, with no verification that the NFT was actually moved into the bridge's custody: [2](#0-1) 

The standard `transferFrom` per OZ's `IERC721`/`ERC721` implementation used here is a `void`-returning function that is expected to revert on failure, but the bridge places blind trust in this behavior: [3](#0-2) 

Any ERC721-like contract that does not strictly revert on a failed/unauthorized transfer (e.g., a token that silently returns without effecting the ownership change, or a non-compliant/buggy implementation) will let `requestERC721Transfer` "succeed" without the bridge ever taking custody of the token, while the bridge still emits the value-transfer request that the operator set will act upon on the counterpart chain via `handleERC721Transfer`, which mints/releases the token to `_to` on the other side: [4](#0-3) 

This is the same root-cause bug class as the referenced report: reliance on a non-reverting-on-failure ERC721 `transferFrom` to gate an economically significant state transition, with no post-call ownership assertion or `safeTransferFrom`/receiver-hook enforcement.

### Impact Explanation
If a registered bridge token exhibits non-reverting-on-failure behavior, an unprivileged user can trigger `requestERC721Transfer` for a token they never actually deposited. Once operators vote and call `handleERC721Transfer` on the counterpart chain (relying on the good-faith assumption that the request corresponds to a real locked/burned deposit), a token is minted or released to the attacker's address on the destination chain without any real asset ever being locked on the source chain — a direct case of unauthorized value creation/movement across the bridge, matching this analog category's "unauthorized value movement" / "supply inflation" criteria.

### Likelihood Explanation
Likelihood is contingent on a registered ERC721 token having non-standard, non-reverting transfer-failure semantics. Token registration is owner-gated via `registerToken` (`onlyOwner`) in `BridgeTokens.sol`, so this cannot be exploited against arbitrary/no tokens — the token itself must be onboarded and must deviate from the ERC721 revert-on-failure guarantee. Given that token registration in bridge systems is typically not exhaustively audited for exotic failure-mode compliance, and the exploiting transaction itself (`requestERC721Transfer`) is fully permissionless and requires no special privilege once such a token is registered, this represents a real, moderately likely exposure rather than a purely theoretical one.

### Recommendation
Replace `transferFrom` with `safeTransferFrom` (or explicitly verify `ownerOf(_tokenId) == address(this)` after the call) in `requestERC721Transfer` before emitting `RequestValueTransferEncoded`/burning the token, so that a non-compliant token cannot cause the bridge to register a phantom deposit.

### Proof of Concept
1. Bridge owner registers a non-standard ERC721 token `T` (via `BridgeTokens.registerToken`) that does not revert when `transferFrom` fails (e.g., silently no-ops instead of reverting when the caller doesn't own or isn't approved for `_tokenId`).
2. Attacker (who does not own `tokenId=X` in `T`) calls `bridge.requestERC721Transfer(T, attackerAddressOnOtherChain, X, "")`.
3. `IERC721(T).transferFrom(attacker, bridge, X)` silently fails without reverting; execution continues to `_requestERC721Transfer`, which emits `RequestValueTransferEncoded` for token `X` as though it was deposited.
4. Bridge operators, observing the emitted event, call `handleERC721Transfer` on the counterpart chain, minting/releasing token `X` to the attacker's address there — value created without any real collateral ever entering the source-chain bridge.

    // _requestERC721Transfer requests transfer ERC721 to _to on relative chain.
    function _requestERC721Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _tokenId,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        (bool success, bytes memory uri) = _tokenAddress.call(abi.encodePacked(ERC721Metadata(_tokenAddress).tokenURI.selector, abi.encode(_tokenId)));
        if (!success) {
            uri = "";
        }
        if (modeMintBurn) {
            ERC721Burnable(_tokenAddress).burn(_tokenId);
        }
        emit RequestValueTransferEncoded(
            TokenType.ERC721,
            _from,
            _to,
            _tokenAddress,
            _tokenId,
            requestNonce,
            0,
            _extraData,
            2,
            abi.encode(string(uri))
        );
        requestNonce++;
    }

     * @dev Transfers the ownership of a given token ID to another address.
     * Usage of this method is discouraged, use `safeTransferFrom` whenever possible.
     * Requires the msg.sender to be the owner, approved, or operator.
     * @param from current owner of the token
     * @param to address to receive the ownership of the given token ID
     * @param tokenId uint256 ID of the token to be transferred

    function transferFrom(address from, address to, uint256 tokenId) public {
        //solhint-disable-next-line max-line-length
        require(_isApprovedOrOwner(msg.sender, tokenId), "ERC721: transfer caller is not owner nor approved");

    }
