Based on my investigation of `aptos-move/framework/aptos-framework/sources/code.move`, I found a specific anomaly worth reporting, though full confirmation is limited by index truncation on the file (noted below).

### Title
Missing immutable-upgrade-policy enforcement in `check_upgradability` allows republishing/overwriting packages declared `immutable` - (File: `aptos-move/framework/aptos-framework/sources/code.move`)

### Summary
`code.move` declares an error constant `EUPGRADE_IMMUTABLE` ("Cannot upgrade an immutable package") [1](#0-0)  but a repo-wide search shows this constant is referenced only once total inside `code.move` (its own declaration line) and once in a test file — i.e. it is never actually asserted anywhere in the module's publish logic. The visible body of `check_upgradability` only enforces (a) that the upgrade policy cannot be weakened via `can_change_upgrade_policy_to`, and (b) that no old module is deleted; it never checks that the *old* package's policy was not already `immutable` before allowing a republish [2](#0-1) .

### Finding Description
`publish_package` calls `check_upgradability(old, &pack, &module_names)` whenever a package with the same name already exists at the target address, and on success it overwrites the stored `PackageMetadata` in place and forwards the new bytecode to `request_publish`/`request_publish_with_allowed_deps` [3](#0-2) .

`check_upgradability`'s only policy-related assertion is:
```
assert!(can_change_upgrade_policy_to(old_pack.upgrade_policy, new_pack.upgrade_policy),
    error::invalid_argument(EUPGRADE_WEAKER_POLICY));
``` [4](#0-3) 

`can_change_upgrade_policy_to` simply checks `from.policy <= to.policy` [5](#0-4) . If `old_pack.upgrade_policy` is `immutable` (policy = 2) and the caller submits a new package that *also* declares `upgrade_policy = immutable` (policy = 2), `2 <= 2` is `true`, so this check passes even though the package is supposed to be frozen forever. No other assert in the visible function body (module-missing check only) blocks this path, and grep confirms `EUPGRADE_IMMUTABLE` — the constant whose doc comment says "Cannot upgrade an immutable package" — is never actually used in an `assert!` anywhere in `code.move`.

This is consistent with the module-level documentation elsewhere in the repo stating "the policy can be only strengthened," and with `object_code_deployment::freeze_code_object`/`code::freeze_code_object`, which mark a package immutable via ownership checks [6](#0-5) [7](#0-6)  — but nothing downstream in `publish_package`/`check_upgradability` appears to actually re-check that an already-immutable package cannot be targeted again by a subsequent `publish_package_txn`/`upgrade` call declaring the same `immutable` policy.

**Important caveat**: I was unable to fully retrieve lines 240–270 of `code.move` (the tail of `freeze_code_object` and the head of `check_upgradability`) due to index size/content limits on `read_file`. It is possible (though grep evidence argues against it) that an `EUPGRADE_IMMUTABLE` assertion exists in that exact unretrieved span. I could not independently confirm this with 100% certainty from the tools available.

### Impact Explanation
If confirmed, this breaks the fundamental "immutable means frozen forever" guarantee that the Aptos publish model documents (`immutable`: "the code is not upgradeable and is guaranteed to stay the same forever") [8](#0-7) . Any downstream protocol, `arbitrary`-dependency check, or user that relies on an address's package being permanently frozen (e.g. for security audits, hard-coded trust assumptions, `EDEP_ARBITRARY_NOT_SAME_ADDRESS`/`EDEP_WEAKER_POLICY` dependency guarantees) could have that package's bytecode silently replaced by its owner, defeating the immutability contract that other packages depend on transitively via `check_dependencies` [9](#0-8) . This is a code-safety/upgrade-policy bypass placing new (potentially "forbidden") bytecode on an address that downstream consumers assume can never change.

### Likelihood Explanation
Likelihood is uncertain without confirming the hidden lines. If the assertion is genuinely absent, exploitation only requires the package owner (who already controls the address/object) to call `publish_package`/`object_code_deployment::upgrade` again with a metadata blob declaring `upgrade_policy = immutable` and a module set that is a superset of the old modules — no special privilege beyond normal publish rights is needed, and the bug would be trivially reachable on every immutable package.

### Recommendation
Explicitly assert in `check_upgradability` (or in `publish_package` before calling it) that `old_pack.upgrade_policy.policy != upgrade_policy_immutable().policy`, aborting with `EUPGRADE_IMMUTABLE` when the existing package is already immutable, regardless of what policy the new package declares.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact missing assert):
1. Publish a package `P` at address `A` with `upgrade_policy = immutable`.
2. Later, as the same signer/object owner, call `publish_package_txn`/`object_code_deployment::upgrade` again for name `P` at `A`, submitting new bytecode plus metadata that also declares `upgrade_policy = immutable`, and includes at least the previous module names (satisfying `EMODULE_MISSING` check).
3. `can_change_upgrade_policy_to(immutable, immutable)` returns `true` (2 <= 2), and — if no dedicated `EUPGRADE_IMMUTABLE` assert exists elsewhere in the function — `check_upgradability` passes, the registry entry is overwritten, and the new bytecode is forwarded to `request_publish`, replacing code that should have been permanently frozen.

**I am not fully confident in this finding due to the tooling's inability to display lines 241–270 of `code.move`.** I recommend a Devin session with full file access to read that exact span of `check_upgradability`/`freeze_code_object` and confirm whether an `EUPGRADE_IMMUTABLE` assertion truly is absent before treating this as validated.
