### Title
Once a repository path is trusted via `addSafeDirectory`, GitHub Desktop provides no way to revoke that trust, permanently whitelisting the path for any future attacker-controlled content - (File: `app/src/lib/git/config.ts`)

### Summary
The reported bug class is a permissionless-whitelist that has an "add" primitive but no corresponding "remove" primitive, so a once-trusted entity stays trusted forever even after it becomes attacker-controlled or is found to be malicious. GitHub Desktop has a direct structural analog: the `safe.directory` git-config allow-list used to bypass Git's "dubious ownership" protection. Desktop exposes `addSafeDirectory()` to grant trust to a path, but there is no `removeSafeDirectory` (or any UI) to revoke it once added.

### Finding Description
When Desktop encounters a repository whose owner differs from the current OS user, Git refuses to operate on it and reports "dubious ownership," which `getRepositoryType` surfaces as `{ kind: 'unsafe', path }` [1](#0-0) . The user is shown a "Trust Repository" button that calls `addSafeDirectory(path)`, which appends the path to the **global** `safe.directory` git config via `addGlobalConfigValueIfMissing('safe.directory', path)` [2](#0-1) . This call site is reachable from both `AddExistingRepository` [3](#0-2)  and `MissingRepository` [4](#0-3) .

Once added, the path is trusted globally and permanently — for every future git invocation, from any application that honors this config, regardless of what later occupies that path on disk. A `grep` across the codebase for `removeSafeDirectory`/`SafeDirectory` removal logic returns no matches outside of `addSafeDirectory` itself and its call sites — there is no function, popup, or preferences UI to untrust a directory once it has been trusted. Desktop's own UI text acknowledges the risk of this whitelist: "Adding untrusted repositories may automatically execute files in the repository" [5](#0-4) .

This maps directly onto the report's broken invariant: an entry (Auctioneer / trusted path) can be added to a privileged allow-list but can never be removed, even after the security assumption that justified trusting it (single owner, benign content) no longer holds — e.g., a shared machine, USB drive, mounted network share, or reused directory path where a different, untrusted/attacker-controlled user later populates the same path with a malicious repository (malicious hooks, `.gitattributes` filters, `core.fsmonitor`, etc. that Git executes automatically for trusted repos).

### Impact Explanation
Since `safe.directory` is a Git-level trust decision (not scoped to a specific repository identity, only a filesystem path), and Desktop has no path to revoke it, an initially-legitimate trust decision becomes a standing, silent authorization for arbitrary future content at that path to be treated as "safe" — enabling Git to run repository-controlled configuration/hooks that would otherwise be blocked by the dubious-ownership protection. This can result in local code execution outside of what the user consciously chose to trust, with no in-app mechanism (no button, no menu item, no preferences pane) to undo it; the user would have to know to manually edit `~/.gitconfig` to remove the `safe.directory` entry.

### Likelihood Explanation
Likelihood is moderate: it requires a path-reuse or shared-storage scenario (e.g., corporate shared drives, VM/container reuse, external drives passed between users, CI runners with shared user home directories) where a previously-trusted path is later populated by a different/malicious owner. This is a realistic, non-exotic condition in enterprise and shared-machine environments where GitHub Desktop is used, and does not require the attacker to have prior control of the victim's host or credentials — only eventual write access to a path the victim already trusted.

### Recommendation
Add a `removeSafeDirectory(path)` function (mirroring `addGlobalConfigValueIfMissing`, but using `git config --global --unset safe.directory <path>`) and surface it in Desktop's repository settings/preferences so users can audit and revoke previously trusted directories. Consider also re-validating trust (e.g., prompting again) if directory ownership changes after the initial trust grant, rather than relying on a path-based, unbounded-lifetime allow-list.

### Proof of Concept
1. User adds a repository at shared path `/mnt/shared/project` where they are the current owner; Desktop detects "unsafe" ownership warning and the user clicks "Trust Repository," invoking `addSafeDirectory('/mnt/shared/project')`, which persists `safe.directory=/mnt/shared/project` in the user's global `~/.gitconfig`.
2. Later, the directory is repurposed/reused by another (possibly malicious) user/process, e.g., a shared VM template is reassigned, or an admin restores a different `project` repo to that same mount path, controlled by an attacker.
3. Because `safe.directory` matches by path only, Git and Desktop treat the new attacker-controlled repository at `/mnt/shared/project` as fully trusted with no re-prompt, allowing repository-level config/hooks to execute automatically.
4. There is no button, dialog, or API in Desktop (`grep` confirms no `removeSafeDirectory` exists) to remove the stale trust entry — the user's only recourse is to manually edit the git config file outside of Desktop.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
