### Title
Operator gets reimbursed for a payout it never funded via ANYONECANPAY payout tx front-running - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs, core/src/task/payout_checker.rs)

### Summary
The payout tx's user-signed input uses `SIGHASH_SINGLE|ANYONECANPAY`, which only commits to input 0 and output 0 (the user payout); the OP_RETURN naming the "fronting operator" is unsigned and can be set to anyone's key by anyone who possesses the signature. Since `update_finalized_payouts` and `is_kickoff_malicious` treat whatever xonly_pk is in the OP_RETURN as ground truth for "who fronted the withdrawal," an attacker who races the honest operator's `fund_raw_transaction` broadcast with their own self-funded transaction (naming the honest operator's key in the OP_RETURN) can get the credited operator automatically kicked off and reimbursed from the deposit's move-to-vault UTXO without that operator ever having spent a satoshi.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk` (as read by `is_kickoff_malicious`/`PayoutCheckerTask`) should equal "the operator whose own wallet funded output 0 of the payout tx," but the code only establishes `payout_payer_operator_xonly_pk == bytes-parsed-from-OP_RETURN-of-whichever-tx-first-spent-the-withdrawal-UTXO`.

- The user's signature over the payout tx is required to be `TapSighashType::SinglePlusAnyoneCanPay` [2](#0-1) , and `calculate_pubkey_spend_sighash`/`calculate_sighash_txin` builds the sighash using `Prevouts::One(txin_index, ...)` for this sighash type [3](#0-2) . This commits only to input 0 and output 0 of the transaction; all other inputs/outputs (the funding inputs, the anchor, and critically the OP_RETURN output naming the operator) are unsigned and freely modifiable by anyone holding the signature.
- `create_payout_txhandler` builds this exact structure: input 0 = withdrawal UTXO (key-spend, user sig), output 0 = user payout, output 2 = OP_RETURN with `operator_xonly_pk.serialize()` [4](#0-3) . Nothing in the signed part of the transaction ties `operator_xonly_pk` to whoever actually supplies the extra funding.
- The honest operator's normal flow (`Operator::withdraw`) verifies the user signature and then calls `fund_raw_transaction` to add its own wallet inputs before broadcasting [5](#0-4) . Anyone else in possession of the same user signature (the withdrawing user itself, who is the unprivileged attacker per the threat model) can independently build a competing payout tx spending the same input 0/output 0, add their own funding inputs, and set the OP_RETURN to name a *different* (victim) operator's xonly_pk — then broadcast first.
- `update_finalized_payouts` scans the block, finds whichever tx actually spent the withdrawal UTXO, and blindly parses the OP_RETURN bytes into `operator_xonly_pk` with no check that this key's owner funded any input: `let operator_xonly_pk = op_return_output.and_then(...).and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());` [6](#0-5) . This value is persisted as `payout_payer_operator_xonly_pk`.
- `is_kickoff_malicious` only checks `operator_xonly_pk != kickoff_data.operator_xonly_pk`, i.e., that the OP_RETURN name matches whoever eventually sends the Kickoff — it performs no check that the named operator's wallet actually funded the payout [7](#0-6) .
- The named (victim) operator's own automation, `PayoutCheckerTask`, queries `get_first_unhandled_payout_by_operator_xonly_pk` filtered by its own key and, once it finds an on-chain match, automatically calls `handle_finalized_payout` → builds and signs Kickoff → proceeds to Reimburse, with no verification that it itself broadcast/funded that payout tx [8](#0-7) .
- `create_reimburse_txhandler` then spends the move-to-vault UTXO's `DepositInMove` output directly to the operator's reimbursement address for the full deposit value [1](#0-0) , and verifiers had already pre-signed the N-of-N sigs for this whole tx graph at deposit time.

Exploit flow: attacker (the withdrawing user) holds the S+AP signature for their own withdrawal. They race the honest operator: build their own payout tx (input 0 = withdrawal UTXO + attacker's own funding inputs, output 0 = their own payout, OP_RETURN = honest operator's xonly_pk), broadcast and confirm it first. The honest operator's `fund_raw_transaction`/broadcast attempt on the same `in_outpoint` fails (double-spend). Because the OP_RETURN names the honest operator, `update_finalized_payouts` records that operator as payer, `PayoutCheckerTask` sees an "unhandled payout" for itself, and automatically drives Kickoff→Reimburse, which is not flagged malicious by `is_kickoff_malicious` and pulls the deposit's full value out of the move-to-vault UTXO to the honest operator's reimbursement address — even though that operator funded nothing.

### Impact Explanation
This breaks CUSTODY: BTC leaves the move-to-vault UTXO via `Reimburse` even though the credited operator never fronted the withdrawal from their own funds; the reimbursement value moves for free. The direct beneficiary of the reimbursement credit is the *named* operator (who did nothing and receives the bridge's deposit value), not the attacker, but it is still a real value transfer from bridge collateral triggered entirely by an unprivileged attacker's transaction-construction choice, matching the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per withdrawal/deposit, requires no privileged role, and can target any operator whose xonly_pk is known (all operator keys are public via `get_params`/round txs).

### Likelihood Explanation
Preconditions: the withdrawing user (the attacker) must win a race against the honest operator's `fund_raw_transaction`+broadcast for the same UTXO, which is plausible since the attacker can prepare and broadcast their transaction with a higher fee the instant the withdrawal is registered on Citrea, before an operator's automation reacts. Attacker cost is essentially just the withdrawal amount to their own address plus fees they'd pay anyway as the withdrawing user, plus mining fees to win the race — no bridge collateral or key compromise needed. This is feasible for any deposit/withdrawal cycle and is repeatable.

### Recommendation
Bind the OP_RETURN operator identity to the transaction's signed data, e.g. require the OP_RETURN (or a hash covering it) to be signed by the named operator, or require additional funding inputs to be provably owned/signed by that operator, or change the payout tx's sighash to `SIGHASH_ALL`/cover the OP_RETURN with a scheme where the operator co-signs before broadcast, and have `PayoutCheckerTask`/`update_finalized_payouts` cross-check that the operator claiming credit actually contributed the funding inputs (e.g., verify a designated funding input is spent from that operator's known collateral/round address) before treating a payout as fronted by them.
