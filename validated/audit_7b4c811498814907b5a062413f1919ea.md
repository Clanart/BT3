Now checking FROST nonce derivation and the encryption key transcript/context binding for possible leaks.### Title
Blame proof emitted before PoP verification leaks the ECDH key of a victim's encrypted share, decrypting a third party's secret share - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
In `KeyMachine::calculate_share`, when the decrypted share bytes fail scalar deserialization, the function returns `PedPoPError::InvalidShare { blame: Some(blame) }` immediately — before the batch-verified proof-of-possession (`msg.pop`) for that message has ever been verified. The `blame` is an `EncryptionKeyProof` revealing the ECDH shared key `enc_key_recipient * msg.key`. Because `msg.key` is an attacker-supplied public point copied verbatim from any observed `EncryptedMessage`, an unprivileged participant can cause the victim recipient to compute and publish (as blame evidence) the decryption key for *another sender's* message — the exact attack the PoP was added to prevent.

### Finding Description
`Encryption::decrypt` queues the per-message PoP into the `BatchVerifier` but returns the `EncryptionKeyProof` (containing `key = ecdh(enc_key, msg.key)`) unconditionally, before verification:

- `crypto/dkg/pedpop/src/encryption.rs:479-500` — `msg.pop.batch_verify(...)` only enqueues; `key`/`dleq` are produced and returned.
- `crypto/dkg/pedpop/src/lib.rs:477-482` — `C::F::from_repr(share_bytes.0)` fails ⇒ early `Err` with `blame: Some(blame)`; `batch.verify_with_vartime_blame()` at line 493 is never reached, so the invalid PoP is never detected.
- `crypto/dkg/pedpop/src/lib.rs:487-497` — even when the scalar is canonical, a queued `BatchId::Share(l)` failure returns `Some(blames[l])`; the PoP statement competes in the same batch, so the ECDH key can again be released without the PoP having been proven valid.

The code comments at `encryption.rs:84-90` and the spec (`spec/cryptography/Distributed Key Generation.md`) describe precisely this attack — Eve reuses Alice's per-message key `X` so that Bob's blame reveals `b·X`, decrypting Alice's message to Bob — and state the PoP exists to stop it. The PoP does stop it in `Decryption::decrypt_with_proof` (`encryption.rs:374-379`, PoP checked first), but `calculate_share` releases the blame key *before* that PoP is verified, bypassing the protection entirely.

Additionally, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`) and will panic on an unregistered accuser — a minor correctness note, not the finding.

### Impact Explanation
For each DKG attempt, attacker Eve participates as a sender. She reads victim sender Alice's `EncryptedMessage` to victim recipient Bob off the wire, copies its `key` field `X = x·G` into her own message to Bob, fills `msg` and `pop` with garbage. Bob's `calculate_share` computes `ecdh(e_bob, X)` — identical to Alice's shared key — decrypts to ~uniform bytes, and with probability ≈ 1 − ℓ/2^256 (~15/16 for 255-bit scalars) the scalar is non-canonical, triggering the early `Err` carrying `EncryptionKeyProof{key: e_bob·X}`. Bob publishes this as blame evidence (see `processor/src/key_gen.rs:504-541`, `CoordinatorMessage::VerifyBlame`), making `e_bob·X` public. Anyone can now run `cipher(context, e_bob·X)` and decrypt Alice's secret-share ciphertext to Bob — recovering `f_A(Bob)`, Alice's secret share evaluation at Bob's index. This is confidential DKG share material disclosed to an unprivileged party via a response/error path — the direct analog of the CVE's "sensitive data returned in response to a request". Repeated across attempts and combined with other faults, it degrades the confidentiality guarantees the encryption layer exists to provide and can contribute to key-share recovery when combined with partial share knowledge.

### Likelihood Explanation
The attacker needs only to be a DKG participant (unprivileged, public inputs: an `EncryptedMessage` they send). `msg.key`, `msg.pop`, `msg.msg` are all attacker-controlled bytes via `EncryptedMessage::read`. The non-canonical-scalar trigger succeeds with overwhelming probability per attempt, and DKG retries reset fresh keys, giving repeated shots at different victims. No collusion, no control over honest RNG.

### Recommendation
Do not emit the `EncryptionKeyProof` until the PoP for that message has been verified. Concretely: in `calculate_share`, run `batch.verify_with_vartime_blame()` for the decryption PoPs (or verify the PoP inline) before producing/returning `blame`; on `from_repr` failure, only attach `blame` if the message's PoP is known valid — otherwise return `blame: None` (sender fault, as an invalid PoP already proves the sender malformed). Alternatively, verify `msg.pop` synchronously inside `Encryption::decrypt` prior to computing/returning `key`.
