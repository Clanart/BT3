## Analysis

The Fei report's broken invariant: an unprivileged actor can push shared, per-key accounting state into a form that **destroys value already paid for by someone else**, using only a public entrypoint, without needing any relayer/prover/admin compromise, purely because the accounting evicts/decays state in a way that doesn't check who owns/deserves the remaining value.

The closest verified local analog is in `pallet-bandwidth`'s FIFO subscription-eviction logic.

`msg.chain` and `msg.app` in the `PurchaseMessage` body are attacker-controlled — the sponsorship model in `Pallet::on_accept` explicitly allows *any* payer on *any* registered source chain to credit *any* `(app_chain, app)` pair, keyed by the message body rather than by the caller's own identity: [1](#0-0) 

`push_subscription` stores subscriptions in a bounded FIFO capped at `MAX_SUBSCRIPTIONS` (1024) and, when full, unconditionally evicts index `0` — the oldest entry — regardless of how many bytes that entry still has remaining: [2](#0-1) 

Because eviction is purely FIFO-by-age and not by "remaining balance" or "expiry," an attacker can force-evict a victim's large, mostly-unused, still-valid subscription by cheaply sponsoring 1024 minimal purchases (e.g., the cheapest tier, `months=1`, tiny `bytes`) into the *victim's* `(app_chain, app)` key. Each purchase is a normal ISMP POST from the registered `BandwidthManager` on any source chain the attacker can call `purchase()` from — no relayer collusion, no governance, no proof forgery needed; this is the standard purchase path documented in `docs/content/developers/evm/bandwidth/overview.mdx`.

This is structurally the same class of bug as H03: a **shared, per-key accounting structure is mutated by transactions from parties other than the value owner, in a way that can destroy value that was legitimately paid for**, and the only stated mitigation (`Event::SubscriptionEvicted`) is auditability after the fact, not prevention: [3](#0-2) 

However, I could not fully verify two things needed to firmly establish exploitability at the "steal/loss of funds" bar required by the impact gate:
1. The actual cost of 1024 cheap purchases relative to the value evicted (the `$50` tier docs suggest cheap purchases are possible, but exact on-chain fee-token pricing/decimals per chain weren't traced end-to-end).
2. Whether `MAX_SUBSCRIPTIONS` is realistically reachable in practice for a live `(chain, app)` pair, i.e., whether legitimate apps typically hold anywhere near 1024 concurrent unexpired subscriptions such that an attacker's spam would need to also out-number/out-race existing legitimate churn.

Given this is a genuine, unprivileged, permissionless entrypoint (`purchase()` → `on_accept`) that lets a third party force eviction of another app's already-paid-for, non-expired bandwidth balance — a fund-loss/lock condition matching "stealing or loss of funds" in the bounty's impact gate — and the eviction logic itself provides no protection based on remaining value or ownership, this qualifies as a real local analog, though the economic feasibility (cost of spam vs. bytes destroyed) should be confirmed with concrete tier pricing during triage.

### Title
Unprivileged FIFO-eviction griefing destroys another app's paid, unexpired bandwidth allowance - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s subscription ledger is a per-`(app_chain, app)` FIFO capped at 1024 entries. Anyone can credit an arbitrary victim `(app_chain, app)` pair via the sponsorship-purchase path. When the FIFO is full, `push_subscription` always evicts the oldest entry by insertion order — never by remaining value or expiry — so a cheap flood of tiny purchases targeting a victim's key can force-evict a large, still-valid, unexpired subscription that the victim legitimately paid for.

### Finding Description
`Allowance` storage is keyed by `(app_chain, app)` taken directly from the purchase message body, not from `request.source` or any caller identity, explicitly to support "sponsorship" — anyone paying from any registered source chain can credit any app on any chain: [4](#0-3) 

`on_accept` decodes the purchase, resolves the tier, and calls `push_subscription(&msg.chain, &key, ...)` where `msg.chain` and `msg.app` are attacker-supplied fields inside the ABI-encoded body of a message the attacker's own `BandwidthManager` dispatch controls: [1](#0-0) 

`push_subscription` evicts strictly by FIFO position (`list.remove(0)`) once the bounded list hits `MAX_SUBSCRIPTIONS`, with no check on the evicted entry's `remaining_bytes` or `expires_at`: [5](#0-4) 

The gate (`try_consume`) also drains strictly from the FIFO head, meaning the head is expected to be the "oldest, most-consumed" entry under organic use — but nothing enforces that invariant against an attacker who deliberately inflates the list with 1024 fresh, low-value entries purchased *after* the victim's large legitimate subscription, pushing the victim's real balance out of the window before it's the natural head or before it's consumed.

### Impact Explanation
A victim app that pre-paid for a large bandwidth tier (e.g., the $1000/8MB tier) can have that entire remaining allocation permanently destroyed by a third party who pays only for the marginal cost of enough minimal-tier purchases to fill the FIFO to 1024 and evict the victim's entry. This is a direct loss of funds already paid to the protocol (the fee-token cost of the purchase), since the corresponding byte allowance is deleted with no refund path — `SubscriptionEvicted.lost_bytes` is only an audit event, not a compensation mechanism.

### Likelihood Explanation
The purchase path (`BandwidthManager.purchase()` → ISMP POST → `pallet-bandwidth::on_accept`) is fully public and permissionless; no relayer/prover/admin/governance role is required, and the attacker only needs enough fee-token balance to submit 1024 cheap purchases against the cheapest configured tier targeting the victim's known `(app_chain, app)` key (which is typically public, e.g., a well-known token-gateway contract address). The main uncertainty is economic: whether 1024 minimum-tier purchases cost less than the value of bandwidth destroyed, and whether an app in practice would ever accumulate near 1024 legitimate concurrent subscriptions (making the attack surface narrower against low-traffic apps but still viable for a targeted denial of a specific fresh large purchase).

### Recommendation
Do not evict purely by FIFO age. Either (a) key eviction priority by remaining value (evict least-remaining-bytes / soonest-to-expire first, never evict an entry with materially more remaining bytes than the incoming credit), or (b) increase `MAX_SUBSCRIPTIONS` substantially and/or reject further pushes once the cap is reached (forcing the buyer to wait rather than silently destroying someone else's balance), or (c) scope sponsorship so a payer can only credit their own registered app identity rather than an arbitrary `(chain, app)` pair chosen from message body content alone.

### Proof of Concept
1. Victim purchases the largest tier (`TierFour`, 8 MB) for their app on chain `X`, crediting `Allowance[X][victim_app]` with one `Subscription { remaining_bytes: 8_388_608, ... }`.
2. Attacker calls `BandwidthManager.purchase()` 1024 times from any allowed source chain, each time setting the purchase body's `chain = X`, `app = victim_app`, `tier = TierOne` (cheapest), `months = 1`.
3. Each purchase dispatches an ISMP POST to `pallet-bandwidth`; `on_accept` calls `push_subscription(X, victim_app, TierOne, ...)` 1024 times.
4. After the first 1023 attacker purchases fill the list to `MAX_SUBSCRIPTIONS`, the 1024th attacker purchase triggers `list.remove(0)`, evicting the victim's original `Subscription` (assuming it was pushed before the attacker's spam and is now at index 0), emitting `SubscriptionEvicted { lost_bytes: 8_388_608, ... }`.
5. The victim's 8 MB of pre-paid, unexpired bandwidth is permanently gone; `Allowance::allowances(X, victim_app)` no longer contains it, and `BandwidthGate::try_consume` can no longer draw against it.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
