### Title
Same-Chain Order Escrow Drain via Duplicate Input-Token Aliasing in `_fillSameChain` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain()` computes the escrow amount to release on the *final* fill of an output leg by reading the entire remaining balance of `_orders[commitment][token]` [1](#0-0) , instead of the amount proportionally attributable to that specific output leg. Escrow accounting is keyed only by `(commitment, token address)` [2](#0-1) , with no per-leg (per output-index) partition. If an order has two or more input legs that use the same token address, completing just one output leg reads and drains the *combined* escrow balance for that token — including the portion that legitimately belongs to the other, still-unfilled leg(s).

### Finding Description
For same-chain orders, `_fillSameChain` iterates over `order.output.assets`, tracking fill progress per output token in `_partialFills[commitment][outputToken]` [3](#0-2) . When a leg's cumulative fill reaches `totalRequired` for that leg, the code takes a shortcut for the escrow release amount:

```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

This reads the *entire* remaining balance recorded under `_orders[commitment][token]` rather than the amount proportionally earned by completing this particular leg. `_orders` is a single mapping keyed by `(commitment, token)` with no leg/index dimension [2](#0-1) . The intent behind this shortcut is benign for the common case (a single leg per token, sweeping up rounding dust from prior floor-divisions on that same leg). But nothing in `placeOrder`/`_orders` bookkeeping prevents an order from listing two (or more) `inputs[i].token` entries with the identical token address, each paired with a different output asset/leg. In that case both legs' escrowed amounts accumulate into the same `_orders[commitment][token]` slot.

A solver can then:
1. Fully satisfy the *cheapest* leg (say, leg 0) whose output is trivial to provide.
2. On that leg's completion (`amountFilled == totalRequired`), `escrowedAmount` is read as `_orders[commitment][token]`, which still contains leg 1's un-released escrow (because leg 1 has not been filled/decremented yet).
3. `_withdraw` transfers this *entire combined amount* to the solver and decrements `_orders[commitment][token]` to zero [4](#0-3) .
4. Because the order is only fully "filled" (`isFullyFilled`) when every leg reaches its `totalRequired`, other legs may still show `remaining > 0` — but their escrow is now zero, so any later attempt to fill or cancel those legs reverts with `UnknownOrder()` [5](#0-4) , permanently locking the user out of the rest of their principal while the attacker walked away with tokens they never paid for on the other leg.

This is structurally the same class of bug as the referenced report: a value-release computation (`escrowedAmount = full remaining balance`) that diverges from the entitlement-tracking computation used everywhere else in the same function (`(inputs[i].amount * fillAmount) / totalRequired`), and that divergence is reachable through a completely permissionless, public entrypoint (`fillOrder`/`cancelOrder`) with no privileged actor required — matching the "wrong amount released" / "loss of funds" impact class.

### Impact Explanation
An unprivileged solver can extract more escrow than they paid for by structuring, or opportunistically fulfilling, a same-chain order whose multiple input legs share a token address, capturing the full pooled escrow by completing only the smallest leg. This is a direct loss of user funds and a violation of the escrow-accounting invariant that release amounts must correspond 1:1 to what was actually paid on each leg. It requires no relayer, prover, or admin — only a same-chain order shaped with duplicate input token addresses across legs, and a single call to the public `fillOrder`/`IntentGatewayV2.fillOrder`.

### Likelihood Explanation
Likelihood depends on whether `placeOrder` permits (or a user unknowingly submits) an order whose `inputs[]` array contains the same ERC-20 token at two or more indices while their corresponding `output.assets[]` differ. If duplicate-token inputs across legs are not explicitly rejected at order placement, any solver monitoring the order book can identify and immediately exploit such an order, since exploitation is a single, ordinary `fillOrder` call using the cheapest leg.

### Recommendation
Track escrow per (commitment, output-leg index) rather than solely per (commitment, token). At minimum, the full-fill branch should compute the leg's entitled escrow the same way the partial-fill branch does — proportional to `fillAmount`/`totalRequired` plus only that leg's accumulated rounding remainder — rather than reading the aggregate `_orders[commitment][token]` balance, which can contain other legs' unreleased principal. Alternatively, reject order placement (or fills) when two or more `inputs[]` entries reference the same token address feeding distinct output legs, so the `(commitment, token)` key is always uniquely attributable to a single leg.

### Proof of Concept
1. User places a same-chain order with `inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 9000} ]` and two output legs, e.g. `outputs = [ {token: DAI, amount: 10}, {token: DAI, amount: 9000} ]` (values illustrative; the key point is both inputs use `USDC`). `_orders[commitment][USDC]` is `10000` after escrow (per shared-key mapping [2](#0-1) ).
2. Attacker (solver) calls `fillOrder` supplying `options.outputs[0].amount = 10` (fully satisfying leg 0 only) and `options.outputs[1].amount = 0` for leg 1.
3. In `_fillSameChain`, for `i = 0`: `remaining = 10 - 0 = 10`, `fillAmount = 10`, `amountFilled = 10 == totalRequired`, so `escrowedAmount = _orders[commitment][USDC] = 10000` (the whole pool, not the `1000` attributable to leg 0) [1](#0-0) .
4. `_withdraw` transfers `10000` USDC to the attacker for having paid only `10` DAI worth of leg 0, and zeroes `_orders[commitment][USDC]` [6](#0-5) .
5. Leg 1 remains unfilled (`isFullyFilled = false`), but any subsequent fill or cancellation touching the USDC input now reverts with `UnknownOrder()` since the escrow is gone, permanently stranding the user's principal with the attacker.

Note: I was not able to inspect `placeOrder`'s validation logic (not returned by the indexed search) to confirm whether duplicate-token legs are explicitly permitted or rejected at order-creation time; this is the one open verification point and should be checked directly in the repository (`evm/src/apps/intentsv2/IntentGatewayV2.sol` / the file(s) implementing `placeOrder`) before treating this as fully confirmed.

        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;

                (bool sent,) = beneficiary.call{value: amount}("");
