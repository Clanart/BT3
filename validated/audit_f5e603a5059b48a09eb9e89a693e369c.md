### Title
Uncontrolled Recursion in AccountKeyRoleBased RLP Decoding via TxTypeAccountUpdate - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested `AccountKey` values through `AccountKeySerializer` without any nesting-depth limit, and this decode path is reachable from a single, unprivileged `TxTypeAccountUpdate` transaction submitted to the public tx pool / RPC, mirroring the SurrealQL uncontrolled-recursion bug class (CWE-674) where nested statements were parsed recursively with no depth check.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes an outer `[][]byte` and, for each element, constructs a new `AccountKeySerializer` and calls `rlp.DecodeBytes(b, &serializer)`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` in turn determines the key type and calls `s.Decode(serializer.key)`, which — if `serializer.key` is itself an `*AccountKeyRoleBased` — re-enters `AccountKeyRoleBased.DecodeRLP`: [2](#0-1) 

There is no depth counter or recursion limit anywhere in this decode chain, unlike the generic `rlp.Stream`, whose only protections are byte-size/list-size limits (`willRead`, `listLimit`), not nesting-depth limits: [3](#0-2) 

The only guard against nested `RoleBased` keys — `IsCompositeType()` returning `true` and the `CheckInstallable`/`CheckUpdatable` composite-type rejection, and the API-level `checkAccountKeyZeroValues(key, isNested)` check — all run **after** the RLP structure has been fully decoded and materialized in memory: [4](#0-3) [5](#0-4) 

The `Key` field of `TxInternalDataAccountUpdate` is of interface type `accountkey.AccountKey`, decoded from raw bytes exactly through this `AccountKeySerializer`/`AccountKeyRoleBased` chain during transaction RLP decoding: [6](#0-5) 

Because Go recursion consumes stack frames with each nested `DecodeRLP`/`rlp.DecodeBytes` call, an attacker can craft a `TxTypeAccountUpdate` transaction whose `Key` bytes encode a `RoleBased` key containing a `RoleBased` key containing a `RoleBased` key, etc., to an arbitrary depth. Decoding this structure recurses without bound before the "nested RoleBasedKey is not allowed" check is ever reached, since that check is a post-decode validation step, not a decode-time guard.

### Impact Explanation
An unprivileged transaction sender can submit a single crafted `TxTypeAccountUpdate` transaction (no special authorization beyond a funded account, or even just broadcasting to the tx pool / public RPC via `SendRawTransaction`) whose RLP-encoded `Key` field contains deeply nested `AccountKeyRoleBased` structures. Decoding this transaction — which happens during tx pool ingestion (`AddRemote`) and again during block execution — recurses without a depth check and can exhaust the goroutine stack, crashing the node process. This is a denial-of-service impact matching the CVSS availability-only profile of the referenced advisory (`AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H`), reachable purely through the public transaction-submission path.

### Likelihood Explanation
Likelihood is high: constructing nested `AccountKeyRoleBased` RLP payloads requires no special privileges, only the ability to RLP-encode an `AccountKeySerializer` recursively (trivial to script), and the resulting transaction can be broadcast like any other to the tx pool or included via public RPC. The vulnerable decode path executes on every node that receives or processes the transaction (mempool ingestion and block/tx validation), so a single malicious transaction can affect multiple nodes.

### Recommendation
Enforce a maximum nesting/recursion depth in `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` (e.g., pass a depth counter through decode or track total decode stack depth) and reject/short-circuit decoding once a bound (matching the existing "no nested RoleBased" business rule) is exceeded, rather than deferring the nested-composite rejection to post-decode validation in `CheckInstallable`/`checkAccountKeyZeroValues`.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value `R0` wrapping an `AccountKeyLegacy`/`AccountKeyPublic`.
2. Recursively wrap: `R1 = AccountKeyRoleBased{R0}`, `R2 = AccountKeyRoleBased{R1}`, … up to `Rn` for large `n` (e.g., tens of thousands), each time RLP-encoding via `NewAccountKeySerializerWithAccountKey` as done in `EncodeRLP`: [7](#0-6) 
3. Embed the final encoded bytes as the `Key` field of a `TxInternalDataAccountUpdate` and sign/broadcast it as a `TxTypeAccountUpdate` transaction.
4. Submit the transaction via public RPC/tx pool `AddRemote`; RLP decoding of the `Key` field recurses `n` times through `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` before any "nested RoleBasedKey not allowed" check can run, crashing the receiving node via stack overflow once `n` is large enough.

Note: I could not fully trace every call site that invokes `CheckInstallable`/`Validate` in `blockchain/tx_pool.go` within the tool budget (no direct matches were found there), so it's possible depth-independent size limits elsewhere (e.g., max tx size) could constrain how deep `n` can practically go; this should be verified in a live/test environment to determine the exact depth needed to trigger a crash.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}

		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.

			return err
		}
	}
	return nil
}

// willRead is called before any read from the underlying stream. It checks
// n against size limits, and updates the limits if n doesn't overflow them.
func (s *Stream) willRead(n uint64) error {
	s.kind = -1 // rearm Kind

	if inList, limit := s.listLimit(); inList {
		if n > limit {
			return ErrElemTooLarge
		}
		s.stack[len(s.stack)-1] = limit - n
	}
	if s.limited {
		if n > s.remaining {
			return ErrValueTooLarge
		}
		s.remaining -= n
	}
	return nil
}

// listLimit returns the amount of data remaining in the innermost list.
func (s *Stream) listLimit() (inList bool, limit uint64) {
	if len(s.stack) == 0 {
		return false, 0
	}
	return true, s.stack[len(s.stack)-1]
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
