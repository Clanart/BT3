### Title
Participant-index panic in PedPoP blame evaluation enables remote denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP blame-resolution path (`BlameMachine::blame` / `AdditionalBlameMachine::blame` → `blame_internal` → `Decryption::decrypt_with_proof`) indexes `HashMap`s keyed by `Participant` with unchecked, caller-supplied `sender`/`recipient` indexes. `Participant` accepts any non-zero `u16` (`Participant::new` only rejects 0), so passing an index `> n` causes a `HashMap` index panic (`self.commitments[&sender]` and `self.enc_keys[&decryptor]`), crashing the evaluating process. This mirrors the bug class of ALPINE-CVE-2018-2781: an attacker-reachable input causing a complete, repeatable crash of the service.

### Finding Description
`Participant::new` permits any non-zero `u16` (`crypto/dkg/src/lib.rs:29-35`), and neither `BlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:623-632`) nor `AdditionalBlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:674-682`) bounds `sender` or `recipient` to `1 ..= n`. Inside `blame_internal`, `self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) panics if `sender` is not a registered participant, and `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`), panicking when `decryptor` (the supplied `recipient`) was never registered. Unlike `generate_secret_shares`/`calculate_share`, which funnel attacker maps through `validate_map` against `all_participant_indexes` (`crypto/dkg/pedpop/src/lib.rs:57-83`), the blame path performs no range validation before indexing. `AdditionalBlameMachine` is explicitly designed for third parties to evaluate blame on submitted data (`crypto/dkg/pedpop/src/lib.rs:638-649`), making this reachable to any unprivileged party who can submit a blame accusation message to a node evaluating it.

### Impact Explanation
A panic in these paths aborts the thread evaluating blame. In a coordinator/processor deployment, a single maliciously-indexed blame statement crashes the participant, stalling the DKG/fault-resolution flow and any downstream signing or fund-rotation dependent on it. This is a repeatable, deterministic complete denial of service (process crash) triggerable by attacker-controlled indexes, analogous to the MariaDB Optimizer crash.

### Likelihood Explanation
Likelihood depends on integrators wiring blame evaluation to network inputs, which is the intended use of the public `blame` API — an accuser supplies the sender and recipient indexes, and nothing in the type system or API prevents `Participant(k)` for `k > n`. Any participant (or observer using `AdditionalBlameMachine`) can trigger it with a single malformed accusation.

### Recommendation
Validate `sender` and `recipient` against the registered `commitments`/`enc_keys` (or `ThresholdParams::n`) before indexing, returning a defined error or `Participant` result instead of panicking; e.g., use `.get()` on the `HashMap`s and treat a missing index as a malformed accusation.

### Proof of Concept
```rust
// After a completed PedPoP DKG for t/n participants, obtaining `blame_machine`:
let bogus = Participant::new(u16::from(params.n()) + 1).unwrap();
// Any well-formed or junk EncryptedMessage suffices; the panic precedes its use:
blame_machine.blame(bogus, params.i(), msg, None); // panics at self.commitments[&sender]
// or:
blame_machine.blame(sender, bogus, msg, proof); // panics at self.enc_keys[&decryptor]
```
