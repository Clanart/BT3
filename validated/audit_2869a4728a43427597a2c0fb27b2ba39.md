Staking precompile `redelegate` panics from a double delegation-rewards withdrawal, halting the transaction whenever the delegator already has a delegation to the destination validator - (File: `precompiles/staking/staking.go`)

### Summary
The staking precompile's `redelegate`/`redelegateFor` code path explicitly pre-withdraws the delegator's pending rewards from the **destination** validator, then invokes `BeginRedelegate`, whose internal `Delegate()` call re-triggers the same withdrawal via the `BeforeDelegationSharesModified` distribution hook. Because the first, explicit withdrawal already deleted the delegator's starting info, the second (hook-triggered) withdrawal finds no starting info and returns `ErrEmptyDelegationDistInfo`, which the distribution hook turns into an unconditional `panic`. This is the same bug class as the reported issue: an operation is executed twice in one call flow, and the second invocation fails because the state consumed by the first invocation is gone.

### Finding Description
In `precompiles/staking/staking.go` (and the same pattern duplicated in `precompiles/staking/legacy/v65,v66,v640,v67/staking.go`), `redelegateFor` does: [1](#0-0) 

This calls `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, dstValAddr)` **before** executing `MsgBeginRedelegate`. That call reaches `Keeper.withdrawDelegationRewards`, which unconditionally deletes the delegator's starting info at the end of the withdrawal: [2](#0-1) [3](#0-2) 

The comment in the precompile even acknowledges this: "WithdrawDelegationRewards reinitializes the delegation's starting info, so the subsequent BeginRedelegate's internal Delegate call will see zero pending dst rewards." But the assumption is wrong — the starting info is *deleted*, not merely zeroed, and it is only recreated later by `AfterDelegationModified` → `initializeDelegation`, which runs **after** the shares-modified hook.

When `execute(msg)` runs `MsgBeginRedelegate`, the underlying staking keeper unbonds from the source validator and then calls `Delegate()` for the destination validator. If a delegation to the destination validator already exists (`found == true`), `Delegate()` invokes the distribution module's `BeforeDelegationSharesModified` hook *before* modifying shares: [4](#0-3) 

That hook unconditionally panics on any error from the second withdrawal attempt: [5](#0-4) 

Since the starting info was already deleted by the precompile's explicit pre-withdrawal, `HasDelegatorStartingInfo` returns `false`, `withdrawDelegationRewards` returns `types.ErrEmptyDelegationDistInfo`, and the hook panics — this panic propagates and aborts the entire EVM transaction (and any recover() in the precompile wrapper simply converts the panic into a returned error, still causing the whole tx/call to fail).

This mirrors the reported CouncilMember/Sablier bug exactly: an operation (`withdraw`) is invoked twice within one logical call, the first invocation consumes the state (available balance / starting info) that the second invocation depends on, and the second invocation unconditionally reverts/panics because that precondition is now empty.

### Impact Explanation
Any EVM caller who has an existing delegation to the destination validator and calls `redelegate` (or `redelegateWithAuthorization`/`redelegateFor`) on the staking precompile will have that transaction fail via panic, even though the underlying `MsgBeginRedelegate` staking operation is otherwise completely valid and would succeed via the native Cosmos tx path (which does not perform this redundant pre-withdrawal). This is a functional DoS specific to the EVM staking precompile's redelegate entry point — a common, expected user flow (redelegating additional stake to a validator you already delegate to) is unconditionally broken. It matches the "Medium/High: contract/functionality broken for a legitimate unprivileged EVM caller" bar since it denies a core precompile feature to any account performing a normal redelegation pattern.

### Likelihood Explanation
High likelihood of being triggered in normal usage: any delegator who redelegates to a validator they already have stake with (a very common scenario, e.g. consolidating delegations or re-delegating after an earlier partial redelegation) will hit this path every time, with no special conditions required beyond having a pre-existing delegation to the destination validator.

### Recommendation
Do not explicitly pre-withdraw destination-validator rewards in the precompile when the underlying `Delegate()` call will already trigger the reward withdrawal via `BeforeDelegationSharesModified`. Options:
1. Remove the explicit `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, dstValAddr)` pre-call and instead capture the destination-validator reward delta purely via balance diffing around `execute(msg)`, letting the native hook path handle the withdrawal exactly once.
2. Alternatively, if the pre-withdrawal is required for event-attribution reasons, guard it so it tolerates (rather than panics on) a subsequent `ErrEmptyDelegationDistInfo` in the distribution hook — but since the hook is a shared code path (`sei-cosmos/x/distribution/keeper/hooks.go`), the safer and more general fix is (1): never invoke a withdraw-then-rely-on-hook-withdraw double path.

### Proof of Concept
1. Associate an EVM account with a Sei address and delegate `X` usei to validator `A` via the staking precompile's `delegate` function.
2. Delegate `Y` usei to validator `B` via `delegate` as well, establishing an existing delegation and starting info for validator `B`.
3. Wait/mine at least one block so validator `B` accrues nonzero pending rewards for the delegator.
4. Call `redelegate(A, B, amount)` (redelegating more stake from `A` into the already-existing delegation to `B`).
5. Trace execution:
   - `redelegateFor` calls `p.distributionKeeper.WithdrawDelegationRewards(ctx, delegator, dstValAddr=B)` → succeeds, and internally deletes the delegator's starting info for `(B, delegator)` (`sei-cosmos/x/distribution/keeper/delegation.go:308`).
   - `execute(msg)` runs `MsgBeginRedelegate`, which unbonds from `A` and calls `Delegate()` targeting `B`. Because a delegation to `B` already exists, `Delegate()` invokes `k.BeforeDelegationSharesModified(ctx, delAddr, B)` (`sei-cosmos/x/staking/keeper/delegation.go:674-675`) before mutating shares.
   - The distribution hook `BeforeDelegationSharesModified` (`sei-cosmos/x/distribution/keeper/hooks.go:106-113`) calls `withdrawDelegationRewards` again, which now fails with `types.ErrEmptyDelegationDistInfo` because the starting info was deleted in the prior step, and the hook executes `panic(err)`.
   - The panic propagates out of `MsgBeginRedelegate`/`stakingKeeper.BeginRedelegate`, causing the entire precompile call (and the enclosing EVM transaction) to fail/revert.

This confirms that `redelegate` to a validator with an existing delegation is unconditionally broken by this double-withdrawal ordering bug.
