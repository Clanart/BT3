The Samba bug class — stale state persisting across re-authentication of a session, so updated membership isn't picked up — maps directly onto Serai's `SigningProtocol` preprocess cache: a FROST preprocess (nonce seed) is persisted under a fixed context and re-derived on every use, never invalidated.

### Title
Cached FROST preprocess seed reused across signing sessions enables secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores the FROST preprocess RNG seed in `CachedPreprocesses` keyed by `context` (e.g. `(b"DkgConfirmer", attempt)`) and reloads it on every invocation. FROST's own contract requires a cached preprocess to be used exactly once and then deleted. Here it is never deleted, so every call to `share_internal` reconstructs an `AlgorithmSignMachine` with identical nonces.

### Finding Description
- `preprocess_internal` loads `CachedPreprocesses::get(txn, &self.context)`; if absent it generates a machine, encrypts `machine.cache()` (the 32-byte seed), and stores it; it then calls `AlgorithmSignMachine::from_cache`, which deterministically regenerates the same nonces from the seed via `ChaCha20Rng::from_seed` in `seeded_preprocess` (crypto/frost/src/sign.rs:121-144, 268-274).
- `share_internal` calls `self.preprocess_internal(participants).0` fresh each time (line 156), so each invocation rebuilds a machine with the same `(d, e)` nonces.
- `DkgConfirmer::complete` calls `share_internal` again (line 322) after `share` already consumed the same context's machine — and any retry under the same `attempt` also reuses it.
- The FROST docs and code both state the cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share" (sign.rs:85-87, 211-213, 218-219), and the deletion requirement is explicit (sign.rs:216-219). `SigningProtocol` never deletes or rotates the cache entry.
- `sign` derives the binding factor `rho` and challenge from the preprocess set and `msg`; if the preprocesses map or message differs between two uses of the same cached seed (e.g. a different participant set, different submitted preprocess bytes, or a different `key_pair` in a retried confirmation), the same nonces sign different challenges — the classic FROST nonce-reuse break.

### Impact Explanation
Each signature share has the form `share = nonce + lambda * secret_share * challenge`. Two shares produced from the same nonces under different `rho`/challenge values yield a linear system that reveals the signer's secret share. Shares are broadcast to all participants, so any observer of the tributary (an unprivileged party who causes or relays these messages) can recover the victim validator's MuSig/FROST secret share and, combined with threshold data, compromise the validator key.

### Likelihood Explanation
The reuse path is structural, not edge-case: `share` then `complete` both invoke `share_internal`, and any repeated call under the same context (attempt retries, reboot + replay) regenerates identical nonces. Divergence of inputs requires only that the preprocess map or message differ between calls — both are attacker-influenced inputs read via `read_preprocess` from untrusted bytes.

### Recommendation
Delete `CachedPreprocesses` entry atomically when the machine is consumed (or include the signing-session digest — participant set + msg hash — in the context key and reject reuse), so `from_cache` can never be invoked twice on the same seed. Alternatively refuse to rebuild a signing machine from a seed whose context already produced a share.

### Proof of Concept
1. Validator runs `DkgConfirmer::share(preprocesses_A, key_pair)` → emits share `s1 = n + λ·x·c1`.
2. Same `attempt` context: run `share`/`complete` again with a different `preprocesses_B` (or different `key_pair`) → emits `s2 = n + λ·x·c2` with identical nonce `n`.
3. Solve `x = (s1 − s2) / (λ·(c1 − c2))` — secret share recovered.
