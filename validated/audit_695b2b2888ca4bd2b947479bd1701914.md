## Finding: Gasless module lend/repay accounting uses nominal `GasLimit × GasPrice`, not actual gas consumed, allowing a gasless-tx sender to siphon KAIA from the block proposer

### Title
Gasless lend/repay amount computed from `GasLimit×GasPrice` instead of actual gas used enables proposer fund drain - ([File: kaiax/gasless/impl/getter.go])

### Summary
The `kaiax/gasless` module (KIP-247) lets a block proposer "lend" KAIA to a fee-less user so the user can execute a `GaslessApproveTx`/`GaslessSwapTx` pair, then repay the loan out of the swap proceeds. The lend and repay amounts are both derived purely from the transactions' *nominal* gas cost (`tx.Gas() * tx.GasPrice()`), not from the gas that will actually be consumed. Since the standard EVM gas-refund mechanism returns any unused reserved gas to the *transaction sender* (the user), not to the proposer who funded the loan, a user can set an inflated `GasLimit` on the approve/swap pair to receive a large lend, spend only the small real gas cost, and keep the unspent reserve as pure profit while still satisfying the exact-match repay check.

### Finding Description
`GetLendTxGenerator`/`lendAmount` compute what the proposer must lend to the user: [1](#0-0) 

`repayAmount`, which is enforced to be exactly equal to what `SwapTx.AmountRepay` must declare, is likewise built from `swapTx.GasPrice() * params.TxGas` (the lend tx's own fee) plus `lendAmount`: [2](#0-1) 

The only consistency check performed before a gasless bundle is accepted (`VerifyExecutable`, condition SP4) is that the *declared* `AmountRepay` in the swap tx's calldata equals this nominal formula — there is no check relating `GasLimit` to the transaction's actual/expected gas usage: [3](#0-2) 

Both `ApproveTx` and `SwapTx` are ordinary (non fee-delegated) transactions paid for by the user's own account (funded moments earlier by the proposer's `LendTx`). Standard gas accounting reserves `Gas() * GasPrice` up front from the payer and refunds the unused portion back to that same payer at the end of execution: [4](#0-3) 

Because the *lend* amount the proposer sends equals `GasLimit_approve*GasPrice + GasLimit_swap*GasPrice` (the full reserved amount) while the *actual* on-chain gas debited from the user for those two transactions is only `GasUsed_approve*GasPrice + GasUsed_swap*GasPrice`, the EVM's own gas-refund mechanism returns the difference `(GasLimit-GasUsed)*GasPrice` straight back into the **user's** balance — money that originated from the proposer's `LendTx`, not from the user's own funds. The `AmountRepay` the router later sends back to the proposer is fixed at the nominal (GasLimit-based) figure and is funded entirely from the swapped token proceeds, so it does not claw back this leftover. The pool only validates that `Gas() <= params.UpperGasLimit`; there is no cap tying gasless-tx `GasLimit` to the expected intrinsic cost of an `approve`/`swapForGas` call, and the txpool balance/fee sanity checks for module transactions are explicitly bypassed via `GetCheckBalance`: [5](#0-4) 

An unprivileged transaction sender who is otherwise eligible to submit a gasless approve/swap pair (KIP-247) can therefore set an arbitrarily large `GasLimit` (bounded only by `params.UpperGasLimit` / block gas limit) on the `ApproveTx` and/or `SwapTx`, causing the block proposer's `LendTx` to transfer a correspondingly large amount of KAIA, most of which is refunded to the attacker's own account by ordinary EVM gas accounting instead of being reclaimed by the proposer.

### Impact Explanation
This directly drains native KAIA from the block proposer to any gasless-tx sender, up to the proposer's willingness/ability to fund the `LendTx` per bundle, repeatable every block the attacker can get a gasless bundle included. This is unauthorized value movement analogous to the LunaFi "reward calculation flaw" — a mismatch between the amount granted and the amount actually owed/consumed is exploited by an ordinary user for profit, causing real fund loss (Medium/High severity depending on proposer's exposure/balance and how many CN/proposer nodes run the gasless feature).

### Likelihood Explanation
The attack requires only the ability to submit a normal `approve` + `swapForGas` transaction pair recognized as `GaslessTx` by the txpool — no special privilege, validator role, or governance access. The `GasLimit` field is entirely attacker-controlled and unconstrained relative to actual execution cost. Any CN running the gasless/auction feature with the default configuration is exposed whenever it builds a block containing gasless bundles.

### Recommendation
- Compute `lendAmount`/`repayAmount` based on a tightly bounded gas estimate (or reconcile post-execution) instead of the raw `GasLimit * GasPrice`, or
- Cap gasless `ApproveTx`/`SwapTx` `GasLimit` to a fixed, audited value close to the intrinsic gas cost of `approve`/`swapForGas` calls, rejecting bundles whose `GasLimit` exceeds this bound in `VerifyExecutable`/`checkBalanceForApprove`/`checkBalanceForSwap`, and
- Redirect any leftover gas refund from `LendTx`-funded execution back to the proposer (e.g., via a claw-back transaction or accounting adjustment) rather than letting it accrue to the user's own balance.

### Proof of Concept
1. Attacker holds zero KAIA and some allowed ERC-20 token, satisfying the `checkBalanceForApprove`/`checkBalanceForSwap` static/token checks.
2. Attacker crafts `ApproveTx` (nonce N) with `GasLimit = 10,000,000` (near `params.UpperGasLimit`) though the real `approve()` call only consumes ~46,000 gas, and `GasPrice` = current base fee.
3. Attacker crafts `SwapTx` (nonce N+1) calling `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` where `amountRepay` is set to exactly `repayAmount(approveTx, swapTx)` per `kaiax/gasless/impl/getter.go:361-367` (required to pass `VerifyExecutable`'s SP4 check), i.e. reflecting the inflated `GasLimit`s.
4. Both txs pass `IsModuleTx`/`GetCheckBalance`/`IsReady` (kaiax/gasless/impl/tx_pool.go) since balance checks are token/allowance based, not native-KAIA based, and get bundled by `ExtractTxBundles` with a proposer-signed `LendTx` prepended whose `Value = lendAmount(approveTx, swapTx)` (kaiax/gasless/impl/getter.go:268-313), i.e. `≈ 10,000,000 * GasPrice * 2`.
5. On execution: `buyGas`/refund logic (blockchain/state_transition.go:294-376) debits the attacker only for the ~46,000 gas actually used on each tx and refunds the remainder (~9,954,000 gas worth of KAIA per tx) to the attacker's own account — money that came from the proposer's `LendTx`.
6. `swapForGas` swaps only enough of the attacker's tokens to cover `amountRepay` (sent to the proposer) and commission; the large refunded KAIA surplus from step 5 remains in the attacker's wallet as unrecovered profit, funded entirely by the proposer.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}
