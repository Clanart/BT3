### Title
Unbounded aggregate-signature deserialization enables memory exhaustion - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an attacker-controlled 32-bit count and deserializes that many group elements without a protocol limit or comparison to the expected number of signatures. A malicious input can therefore force unbounded allocation and parsing work.

### Finding Description
The reader loads a four-byte length, then loops `u32::from_le_bytes(len)` times and appends every decoded point to `Rs` before finally reading the aggregate scalar. No maximum length is enforced. [1](#0-0) 

Each iteration only requires a syntactically canonical group encoding, so the sender does not need a valid aggregate signature before resources are consumed. [2](#0-1) 

### Impact Explanation
A remote party supplying serialized aggregate signatures can retain parser resources while expanding a single vector to as many as `u32::MAX` elements. On secp256k1-sized encodings, this represents over 128 GiB of point data before vector overhead, causing memory exhaustion, excessive CPU consumption, or a stalled connection-dependent read. [3](#0-2) 

### Likelihood Explanation
Only the serialized input is attacker-controlled: the first four bytes choose the work factor, and the sender can continue supplying valid point encodings without authentication or a valid proof. The issue is reachable wherever untrusted aggregate-signature bytes are passed to `SchnorrAggregate::read`. [1](#0-0) 

### Recommendation
Do not deserialize an attacker-supplied count without a context-specific bound. Either require the expected signature count before reading, enforce a small consensus/protocol maximum, or wrap the reader in a byte-limiting adapter and reject declared lengths that cannot fit the remaining message. [3](#0-2) 

### Proof of Concept
The declared count alone drives allocation and parsing:

```rust
let mut malicious = Vec::new();
malicious.extend(u32::MAX.to_le_bytes());

// Follow with an effectively unlimited stream of canonical point encodings.
// Each 33-byte secp256k1 compressed encoding is appended to Rs until EOF.
```

Because the vector is retained throughout decoding, resource consumption grows linearly with the attacker-controlled stream rather than being bounded by the declared aggregate's protocol purpose. [4](#0-3)
