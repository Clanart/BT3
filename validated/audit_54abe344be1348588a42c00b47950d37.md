### Title
Deterministic cached-preprocess reuse lets distinct preprocess sets within one `DkgConfirmer` attempt reuse FROST nonces, enabling secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to the report's "state snapshot taken once, then reused as if it were current" bug class (totalXP frozen at `lastXP`, ignoring the accrued delta), `SigningProtocol::preprocess_internal` freezes the FROST nonce seed per `context` and deterministically re-derives the *same* nonces on every subsequent signing call within that context. When the surrounding signing session changes (different preprocess set ⇒ different binding factors ρ, different challenge c), the stale seed is replayed against new public inputs — exactly the "reused stale value instead of recomputed value" pattern — producing two signature shares over the same raw nonces. That is nonce reuse, which yields recovery of the validator's MuSig/FROST secret share.

### Finding Description
`CachedPreprocesses` is keyed only by `context`, which for the DKG confirmer is `(b"DkgConfirmer", attempt)` (signing_protocol.rs:274-277). On the first call for a context a seed is generated and stored; on every later call the same seed is decrypted and passed to `AlgorithmSignMachine::from_cache` (lines 123-145). `from_cache` → `seeded_preprocess` regenerates identical `nonces`/`commitments` from `ChaCha20Rng::from_seed` (crypto/frost/src/sign.rs:121-144).

`DkgConfirmer::share` calls `share_internal`, and `DkgConfirmer::complete` calls `share_internal` **again** (lines 321-324) with whatever `preprocesses` map the tributary layer supplies. In `SignMachine::sign`, the effective nonce is `base + ρ·actual` where ρ comes from `B.calculate_binding_factors` over a transcript committing to the *chosen* preprocess set (sign.rs:361-396, 385-394). Two invocations under the same `attempt` with different preprocess maps (different signer subsets or different addenda) therefore reuse `(base, actual)` with different ρ and a different challenge `c`, emitting:

- `s1 = base + ρ1·actual + c1·λ·x`
- `s2 = base + ρ2·actual + c2·λ·x`

Two linear equations in two unknowns (`actual`, `λ·x`) — `base` and commitments are public via the broadcast preprocess — so `λ·x`, the interpolated secret share, is recovered. If the set is identical but the bound `msg` differs, `s1 − s2 = (c1 − c2)·λ·x` gives it directly.

### Impact Explanation
Recovery of a validator's Ristretto secret share for the tributary MuSig set. Combined with threshold-many compromised/recovered shares this breaks the key; even alone it is the exact "private key share recovery" failure the `CachedPreprocess` docs warn about (sign.rs:209-219, spec/cryptography/FROST.md:51-62). The code acknowledges the danger ("recovery of it will enable recovering the private key", line 104) but only protects the seed at rest — it does not prevent deterministic reuse across the multiple `share_internal` calls permitted per attempt.

### Likelihood Explanation
The preprocess/shares maps are populated from messages of other tributary validators, and Serai validator sets are permissionless (bonded), so an unprivileged party can become a participant and supply preprocesses, or an honest re-delivery/retry path can present a different `preprocesses` map to `complete` than was used for `share`. Any divergence — different participant subset, reordered/added preprocesses, or a different `key_pair` message — triggers the reuse. Caveat: I could not fully trace `handle.rs` to confirm how often distinct preprocess maps reach `complete` versus `share`; if the coordinator always feeds byte-identical preprocesses and identical `msg`, the two shares are equal and harmless, reducing likelihood to the fault/replay paths.

### Recommendation
Key the cache by the full signing context, not just the attempt: e.g., `context = (b"DkgConfirmer", attempt, hash(sorted participants ‖ serialized preprocesses ‖ msg))`, or cache the completed `AlgorithmSignMachine` state so `complete` reuses the already-produced share rather than re-running `share_internal`. At minimum, mark the seed consumed after first use and refuse to sign twice under one seed with differing inputs. Alternatively have `DkgConfirmer::share` return the machine and have `complete` take it, eliminating the second `share_internal` call.

### Proof of Concept
1. Attempt `a` begins; `preprocess_internal` stores seed `S` under `("DkgConfirmer", a)` and derives nonces `(base, actual)` with commitments `D, E` broadcast.
2. `confirmer.share(P1, kp)` where `P1` is preprocess set `{2,3,…,t}`: emits `s1 = base + ρ1·actual + c1·λ_i·x_i`.
3. `confirmer.complete(P2, kp, shares)` with `P2` a different valid set (e.g., subset `{2,…,t-1}` plus a different participant, or any preprocess set an attacker-influenced coordinator delivers): re-derives the same `(base, actual)` but computes `ρ2 ≠ ρ1` and challenge `c2 ≠ c1`, emitting `s2`.
4. Solve: `s1 − s2 = (ρ1−ρ2)·actual + (c1−c2)·λ·x`. With `actual` recoverable from the analogous second-nonce relation (or by controlling `ρ2` such that only `x` differs — e.g., identical set, different `key_pair` gives `x = (s1−s2)/((c1−c2)·λ)` directly), the participant's interpolated secret share `λ·x` is recovered from public share values.
