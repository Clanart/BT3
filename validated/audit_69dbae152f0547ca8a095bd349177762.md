### Title
Fee-on-transfer or non-standard LP tokens break the 1:1 receipt-token backing in `WombatStaking.depositLP` - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.depositLP()` mints receipt tokens and stakes to Master Wombat using the nominal `_lpAmount` parameter instead of the amount actually received by the contract, unlike the sibling `deposit()` function which correctly measures the before/after balance delta.

### Finding Description
In `WombatStaking.deposit()` the contract carefully measures the LP tokens it actually receives before minting receipt tokens: [1](#0-0) 

However, `depositLP()` — the code path used when a user deposits an already-minted Wombat LP token directly, reachable from any unprivileged wallet via `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()` / `AnkrBNBPoolHelper.depositLP()` — skips this safety check entirely: [2](#0-1) 

It calls `IERC20(poolInfo.lpAddress).safeTransferFrom(_for, address(this), _lpAmount)` and then immediately uses the caller-supplied `_lpAmount` — not the actual received balance — both to stake into Master Wombat via `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` and to mint receipt tokens via `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, _lpAmount)`.

This is exactly the "Token Integration Checklist" bug class referenced in the external report: the code implicitly assumes the `lpAddress` token behaves like a standard, non-fee, non-rebasing ERC20 and transfers exactly the requested amount. Nothing in `registerPool()` validates or restricts the LP token's transfer semantics: [3](#0-2) 

If any registered `lpAddress` deviates from strict "transfer amount == balance delta" behavior (fee-on-transfer, deflationary, or any deduction on transfer), the contract will:
1. Receive fewer LP tokens than `_lpAmount`.
2. Mint the full `_lpAmount` of receipt tokens to the depositor — over-crediting them relative to real backing.
3. Attempt to stake the full nominal `_lpAmount` to Master Wombat, which will either revert (since the contract's real LP balance is short) causing denial of service for that pool, or, depending on Master Wombat's internal transfer semantics, silently under-collateralize the staked position.

### Impact Explanation
If the mint succeeds while staking under-delivers, the receipt token supply becomes greater than the real LP tokens custodied/staked by `WombatStaking`, breaking the 1:1 backing invariant across all users of that pool. Later withdrawals (`withdraw()` → `burnReceiptToken`) would be satisfied by whichever depositors act first, and the last depositors attempting to redeem receipt tokens would be unable to withdraw their share because insufficient real LP/underlying assets remain — a permanent freezing of funds / protocol insolvency for that pool. If staking instead reverts, the deposited LP tokens are already transferred to the contract and no receipt is issued at all, resulting in the user's LP amount being stuck (frozen) with no path to reclaim it in `depositLP`, since the function contains no rollback of the transferred tokens.

### Likelihood Explanation
Likelihood depends entirely on whether a pool is registered with a non-standard LP token. Since Wombat pools' LP ("asset") tokens are normally minted 1:1 without fees, this is not exploitable under currently-known Wombat asset tokens, but the contract provides no on-chain enforcement or check, and the owner-controlled `registerPool()` can add any LP token address as future pools are added (e.g., alternate/side pools or partner integrations with different underlying token behavior). Any ordinary depositor using `depositLP()` on such a pool — with no special privileges required — would trigger the issue.

### Recommendation
Mirror the balance-based accounting already used in `deposit()`: measure `IERC20(poolInfo.lpAddress).balanceOf(address(this))` before and after `safeTransferFrom` inside `depositLP()`, and use the delta (not the caller-supplied `_lpAmount`) for both `_toMasterWomAndSendReward` and the receipt token mint amount.

### Proof of Concept
1. Owner registers a pool via `registerPool()` whose `lpAddress` is a token with a transfer fee (e.g., deducts 1% on every transfer) — nothing in `registerPool()` prevents this.
2. User calls `WombatPoolHelper.depositLP(1000)` with an LP balance of 1000 tokens; this forwards to `WombatStaking.depositLP(lpToken, 1000, user)`.
3. `safeTransferFrom(user, address(this), 1000)` transfers only 990 tokens net to `WombatStaking` due to the fee.
4. `_toMasterWomAndSendReward(_lpAddress, 1000, true)` attempts to stake 1000 tokens to Master Wombat, but the contract only holds 990 — this either reverts (funds already pulled from user, stuck) or, if internal accounting differs, understakes while `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, 1000)` still mints 1000 receipt tokens, creating a permanent 10-token shortfall in backing that compounds with every such deposit.
