The BSC light-client verifier in this repo uses a strictly-weaker threshold than every sibling consensus verifier in the same codebase, reproducing exactly the seed bug's structure: an off-by-one that admits the exact boundary count instead of boundary+1, eliminating the guaranteed-honest-overlap property that makes a supermajority check safe.

### Title
BSC light client accepts finality proofs at exactly `2n/3` signers instead of `2n/3+1`, breaking guaranteed honest overlap and enabling double finalization - ([File: modules/consensus/bsc/verifier/src/lib.rs])

### Summary
`verify_bsc_header` in [1](#0-0)  gates finality on `participant_count < ((2 * current_validators.len()) / 3)`, which **accepts** exactly `floor(2n/3)` signers. Every other consensus verifier in this repository enforces a strict supermajority of `floor(2n/3) + 1`:
- BEEFY: `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- Pharos: `required = (total_stake * 2 / 3) + 1` [3](#0-2) 
- Sync-committee: `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` [4](#0-3) 

The BSC verifier is the only one missing the `+1`, mirroring the seed report's `div_ceil(2)` vs `(n/2)+1` off-by-one: it enforces the boundary value itself as "good enough" rather than requiring strictly more.

### Finding Description
For a BFT validator set of size `n = 3f+1` (or `n = 3f` in the boundary case), safety of a `2/3` finality rule depends on any two accepted quorums of size `Q` sharing at least one honest signer. The guaranteed overlap between two quorums of size `Q` out of `n` is `2Q - n`. With the correct rule `Q = floor(2n/3) + 1`, that overlap exceeds the maximum tolerated Byzantine count `f`, so at least one honest validator must be in both quorums — preventing equivocating validators from single-handedly producing two conflicting valid finality proofs.

With the BSC verifier's actual rule, `Q = floor(2n/3)` is sufficient. For `n = 21` (the BSC testnet shape used in this repo's own tests, e.g. `dummy_validators(21)` in [5](#0-4) ), `Q = 14`. The guaranteed overlap is `2*14 - 21 = 7`, which equals exactly the maximum tolerated Byzantine count `f = n/3 = 7`. This means it's possible for the entire required overlap between two conflicting 14-of-21 quorums to consist solely of colluding/equivocating validators — no honest validator needs to sign both attestations. Concretely: 7 Byzantine validators double-sign both a `VoteAttestationData` for header A and one for header B (conflicting forks at the same height); each proof then only needs 7 additional distinct honest signers (14 honest total, split 7/7) to reach the `14`-signer bar independently. Both `BscClientUpdate`s pass `verify_bsc_header` — including the aggregate BLS signature check on `bls::verify` at [6](#0-5)  — since the check only inspects the bit-count and the aggregate signature over the actually-participating set, never comparing across separate proofs.

### Impact Explanation
This is a false-remote-state-acceptance vulnerability in the consensus layer that all downstream state/request/response proofs for BSC rely on (per `modules/ismp/clients/bsc`). Accepting two conflicting `VerificationResult`s for the same height lets a state commitment be finalized that is not the canonical BSC state. Any state or receipt/request-response proof subsequently verified against that false commitment is falsely trusted, enabling double-settlement of cross-chain messages, replay of already-processed requests under the "other" finalized fork, or acceptance of a state root that lets an attacker fabricate inclusion proofs for asset transfers/intents that never happened on the real BSC chain — i.e., unauthorized fund movement or double-claim through the bridge.

### Likelihood Explanation
This requires collusion among BSC validators controlling exactly the tolerated-Byzantine fraction (`n/3`), which is the same threat model the protocol's own supermajority design is meant to specifically defend against (see the "51% attack"/BFT safety-margin discussion in [7](#0-6) ). It does not require a malicious Hyperbridge relayer, prover, or operator — only the exact off-by-one in this local verifier code, which is otherwise inconsistent with every sibling verifier in the same repository that correctly implements `+1`.

### Recommendation
Change the check to require a strict supermajority, matching the pattern used everywhere else in this codebase:
```rust
if participant_count < (((2 * current_validators.len()) / 3) + 1) {
    Err(Error::NotEnoughParticipants)?
}
```
This restores the guaranteed-honest-overlap property (`overlap = f+1 > f`) for any validator-set size, closing the equivocation gap without a malicious relayer/prover assumption.

### Proof of Concept
1. Configure a BSC light client with `n = 21` validators (matches this repo's own test fixture `dummy_validators(21)`).
2. Split the 21 validators into: 7 "Byzantine" (`B`), 7 honest set A (`H_A`), 7 honest set B (`H_B`).
3. Attacker constructs `VoteAttestationData` for conflicting header pair (source_A/target_A) signed by `B ∪ H_A` (14 signers) — passes `verify_bsc_header` since `participant_count = 14` is not `< 14`.
4. Attacker constructs a second, conflicting `VoteAttestationData` for (source_B/target_B) at the same height, signed by `B ∪ H_B` (14 signers) — also passes independently, same check.
5. Both `BscClientUpdate`s produce valid `VerificationResult`s with conflicting `finalized_header`/state roots, per the existing test harness pattern in [8](#0-7) , demonstrating the accept path is reachable at exactly the `14`-signer boundary with room for the entire required overlap (`7`) to be the colluding set.

	let participating_stake = validator_set.participating_stake(participants);

			required,

S = \{s_i\}_{i \in T}\\
\forall \space pk_i \in P,  VerifySig(s_i, pk_i, B_h) \in \{true, false\} \\

## Byzantine Attacks

Consensus clients rely on consensus proofs that can only be generated by a network's validators. Unfortunately, this means that these same validators can deceive consensus clients, leading to double spending attacks or, even worse, infinite minting attacks.

These attacks can be performed on both off-chain and on-chain consensus clients. Let’s explore the possible attacks on consensus clients in proof of stake systems.


### 51% Attacks

This is an attack that occurs when the supermajority of the validator set finalizes two competing chains at the same height. This situation can be devastating for consensus-verifying  bridges because both chains are valid for its consensus verification algorithm and can be used to double-spend incoming assets.

Although 51% attacks are relatively rare, they can be extremely devastating in a fully networked blockchain ecosystem where the weakest link in the chain can be exploited with a cascading effect across all its connected chains, similar to the Terra-Luna collapse. [Vitalik himself expressed this concern in a Reddit post.](https://www.reddit.com/r/ethereum/comments/rwojtk/ama_we_are_the_efs_research_team_pt_7_07_january/hrngyk8/)


> *Even if there’s a perfect ZK-SNARK-based bridge that fully validates consensus, it’s still vulnerable to theft through 51% attacks.*
>

This is a hard problem to solve and there have been no papers published addressing this major issue with consensus-verifying bridges. In order to build a **truly secure consensus-verifying bridge**, on-chain consensus clients must be resilient to 51% attacks.
