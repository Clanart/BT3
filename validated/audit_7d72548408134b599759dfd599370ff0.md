### Title
EVM/precompile usei transfers via `SendCoinsAndWei` bypass bank `BlockedAddr`/`SendEnabled` restrictions enforced on ordinary `MsgSend` - (File: sei-cosmos/x/bank/keeper/send.go)

### Summary
This is the same bug class as the C4 report: a critical authorization/state check (there: `sellable`, here: bank's `BlockedAddr`/`IsSendEnabledCoins` transfer-restriction checks) is enforced on one code path that "initiates" a transfer, but is missing on a second, equally-reachable code path that "completes" an equivalent transfer of the same asset.

### Finding Description
The Cosmos `MsgSend`/`MsgMultiSend` handlers gate ordinary bank transfers through `BlockedAddr` and `IsSendEnabledCoins` checks before calling `BaseSendKeeper.SendCoins`. However, `BaseSendKeeper.SendCoins` / `sendCoinsWithoutAccCreation` themselves perform no such checks [1](#0-0) , and neither does `SendCoinsAndWei`, the function used to move native `usei`/`wei` balances for EVM-originated transfers [2](#0-1) .

`SendCoinsAndWei` is invoked directly by the EVM bank precompile's `sendNative` entry point, which is reachable by any EVM caller holding an associated Sei address, with no intervening `BlockedAddr`/`IsSendEnabledCoins` gate: [3](#0-2) . The same pattern is repeated across every legacy version of the bank precompile (`v552`, `v562`, `v600`, `v601`, `v603`, `v605`, `v606`, `v610`, `v614`, `v630`, `v640`, `v66`, `v67`), all of which call `p.bankKeeper.SendCoinsAndWei` with no equivalent of the `MsgSend` restriction checks.

Because `usei` is a fungible base-denom asset that both the Cosmos bank module and the EVM StateDB read/write through the shared `BaseSendKeeper`, an admin who disables sending for `usei` (`SendEnabled=false`) or blocks a specific address (module accounts, sanctioned addresses, etc.) via bank params/`blockedAddrs` expects that restriction to hold chain-wide. The EVM-facing precompile path never re-checks these flags, so a transfer that would be rejected via `MsgSend` succeeds via an EVM transaction calling the bank precompile's `sendNative`.

### Impact Explanation
This allows an unprivileged EVM/precompile caller to move `usei` to or from addresses/denoms the chain operator intended to restrict (e.g., a `BlockedAddr` such as a module account, or a denom with `SendEnabled=false`), directly analogous to the original finding where a user could still purchase (transfer) an asset the admin had explicitly marked as non-transferable. This is an authorization bypass on fund movement reachable from any submitted EVM transaction, which the scan rules classify as "unauthorized transfer via precompile" — a Medium/High-severity condition.

### Likelihood Explanation
The path is trivially reachable: any address with an EVM↔Sei association can call the bank precompile's `sendNative` method (or trigger a native `usei` value-transfer EVM tx that ultimately calls `SendCoinsAndWei`) with no special privilege required. No governance, validator collusion, or malicious peer is needed — a single standard EVM transaction suffices.

### Recommendation
Add the same `BlockedAddr` and `IsSendEnabledCoins` (and any `IsInDenomAllowList`) checks that gate `MsgSend`/`MsgMultiSend` directly inside `BaseSendKeeper.SendCoinsAndWei` (and/or `SendCoins`/`sendCoinsWithoutAccCreation` itself, so all callers, including the EVM/precompile path, are protected uniformly rather than relying on each message handler to re-implement the guard).

### Proof of Concept
1. Chain operator sets `SendEnabled=false` for `usei` (or adds a target address to `blockedAddrs`) via the bank module params.
2. A normal `MsgSend` transferring `usei` to/from the restricted target correctly fails with `ErrSendDisabled`/blocked-address error, because `msg_server.go` checks `IsSendEnabledCoins`/`BlockedAddr` before calling `SendCoins`.
3. The same user instead calls the bank precompile's `sendNative(receiver)` function from an EVM transaction with `value` set to the desired `usei` amount, targeting the restricted address.
4. `sendNative` calls `p.bankKeeper.SendCoinsAndWei(...)` [4](#0-3)  which performs the balance debit/credit with no `BlockedAddr`/`IsSendEnabledCoins` check, and the transfer succeeds despite the admin-imposed restriction.

Note: I was unable to fully trace every caller of `msg_server.go`'s `SendCoins`/`SendCoinsAndWei` invocation chain within the available indexed context to confirm there is no restriction check inserted elsewhere (e.g. in an ante handler or a wrapper keeper used specifically for EVM state transitions) that might already mitigate this; a Devin session with full repo access would be needed to definitively confirm no such guard exists elsewhere in the EVM state-transition pipeline before treating this as a confirmed, unmitigated bug.

func (k BaseSendKeeper) SendCoins(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins) error {
	if err := k.SendCoinsWithoutAccCreation(ctx, fromAddr, toAddr, amt); err != nil {
		return err
	}

	// Create account if recipient does not exist.
	//
	// NOTE: This should ultimately be removed in favor a more flexible approach
	// such as delegated fee messages.
	accExists := k.ak.HasAccount(ctx, toAddr)
	if !accExists {
		defer func() {
			recordNewAccounts(ctx.Context(), 1)
		}()
		k.ak.SetAccount(ctx, k.ak.NewAccountWithAddress(ctx, toAddr))
	}

	return nil
}
