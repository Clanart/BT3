### Title
Unhandled uint32/uint64 overflow in `compute_assert_height()` from attacker-controlled relative timelock conditions crashes mempool validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`compute_assert_height()` computes the most restrictive absolute height/seconds constraint for a spend bundle by adding a coin's `confirmed_block_index`/`timestamp` to an attacker-supplied relative value (`height_relative`, `seconds_relative`, `before_height_relative`, `before_seconds_relative`) and casting the result with `uint32(...)`/`uint64(...)`. This mirrors the ref-fvm `bf.unset(u64::MAX)` bug class: an unchecked arithmetic operation on a user-controlled boundary value causes an overflow that is only detected downstream (at the `uint32()`/`uint64()` cast), producing an unhandled exception rather than a graceful validation error.

### Finding Description
`compute_assert_height()` in `chia/full_node/mempool_manager.py` performs: [1](#0-0) 

For every relative-timelock condition in a spend's `SpendBundleConditions`, the code does `removal_coin_records[...].confirmed_block_index + spend.height_relative` (and the analogous seconds arithmetic) and only afterward wraps the raw Python int in `uint32(...)`/`uint64(...)`. Because Python integers are unbounded, the addition itself never fails — the overflow is only surfaced when `uint32()`/`uint64()` tries to construct a bounded integer from a value that exceeds `UINT32_MAX`/`UINT64_MAX`. If that constructor raises (as `chia_rs.sized_ints.uint32`/`uint64` do for out-of-range values) rather than silently wrapping, the exception propagates out of `compute_assert_height()`.

This function is called directly from `validate_spend_bundle()`: [2](#0-1) 

which is invoked by `add_spend_bundle()` — the code path used both for a freshly submitted spend bundle (from an unprivileged RPC caller / peer's `send_transaction`) and for retrying items out of the pending/conflict caches on every new peak: [3](#0-2) [4](#0-3) 

Unlike the earlier, Rust-side condition validation (`check_conditions`/CLVM condition parsing) that appears to already reject clearly-oversized relative-height arguments (e.g. `0x100000000` for `ASSERT_HEIGHT_RELATIVE` returns `Err.ASSERT_HEIGHT_RELATIVE_FAILED`, not a crash, per the test table in `chia/_tests/core/full_node/test_conditions.py`), `compute_assert_height()` is pure Python arithmetic with no explicit bounds check before the cast. A relative value that is individually valid as a `uint32`/`uint64` field (i.e. up to `2**32-1` / `2**64-1`) but is added to a nonzero `confirmed_block_index`/`timestamp` can produce a sum that exceeds the target type's max, triggering the failure at the cast rather than being rejected as an ordinary validation error earlier in the pipeline.

### Impact Explanation
If the `uint32()`/`uint64()` cast raises an unhandled exception, `add_spend_bundle()` — called both during ordinary transaction submission and during the periodic re-validation of the pending/conflict caches on every `new_peak()` — would propagate that exception instead of returning a normal `FAILED`/`PENDING` result. Since `new_peak()`'s pending-cache retry loop iterates over all cached items and calls `add_spend_bundle()` for each one without a per-item try/except, a single malicious spend bundle lodged in the pending cache (via a legitimate-looking relative-height/seconds condition combined with a coin whose `confirmed_block_index`/`timestamp` is large enough to push the sum over the type bound) could throw during that unguarded iteration, potentially interrupting `new_peak()` mempool processing for the whole node — a spend-triggered transaction-processing halt / DoS on full-node transaction validation.

### Likelihood Explanation
This is reachable by an unprivileged party who can submit a spend bundle to any full node's mempool (over RPC or the P2P transaction-relay protocol) — no special privileges needed. It requires crafting a spend whose relative timelock condition, when combined with the actual confirmed height/timestamp of the coin being spent, produces a sum exceeding `uint32`/`uint64` bounds. Because `confirmed_block_index`/`timestamp` grow with the chain, exploitability of the height case improves as the chain height approaches `2**32`, while the seconds case (`uint64`) requires an already very large relative value close to `2**64`, which the test suite (`chia/_tests/core/full_node/test_conditions.py`) shows is already rejected for some absurdly large inputs at an earlier stage — this earlier rejection makes exact confirmation of reachability of `compute_assert_height()`'s specific overflow path uncertain without running the code, since I could not find or execute a concrete failing test case in the indexed codebase (only inference from the source and test tables was possible).

### Recommendation
Add explicit bounds checking before the `uint32()`/`uint64()` casts in `compute_assert_height()` (e.g. clamp to the type max or raise a proper `ValidationError`/`Err.ASSERT_HEIGHT_RELATIVE_FAILED`-style result instead of letting the constructor raise), and wrap the per-item retry loop in `new_peak()`'s pending/conflict cache drain (`chia/full_node/mempool_manager.py:1113-1127`) in a try/except so that one malformed/edge-case mempool item cannot abort processing of the rest of the batch.

### Proof of Concept
Not independently verified by executing code (index-only investigation). Conceptually: submit a spend bundle with `ASSERT_HEIGHT_RELATIVE` (or `ASSERT_BEFORE_HEIGHT_RELATIVE`/`ASSERT_SECONDS_RELATIVE`/`ASSERT_BEFORE_SECONDS_RELATIVE`) set to a value near `UINT32_MAX` (or `UINT64_MAX` for seconds) on a coin whose `confirmed_block_index`/`timestamp` is non-zero, such that `confirmed_block_index + height_relative > UINT32_MAX` (or the seconds equivalent). Submit via RPC `push_tx`/P2P transaction relay so it lands in `add_spend_bundle()` → `validate_spend_bundle()` → `compute_assert_height()` at `chia/full_node/mempool_manager.py:104/108/113/121`, and observe whether the `uint32()`/`uint64()` cast raises uncaught, propagating through `new_peak()`'s retry loop at `chia/full_node/mempool_manager.py:1116-1124`.
