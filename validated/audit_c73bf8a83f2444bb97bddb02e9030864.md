### Title
BaseRewardPool `_provisionReward` records nominal reward amount instead of actual tokens received, corrupting `rewardPerTokenStored` for fee-on-transfer/rebasing reward tokens - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool._provisionReward` pulls reward tokens via `safeTransferFrom` and then unconditionally uses the caller-supplied `_amountReward` value (not the actual balance change) to update `rewardPerTokenStored` and `historicalRewards`. This function is reachable by any ordinary wallet through the permissionless `donateRewards` entry point for any already-registered reward token.

### Finding Description
`_provisionReward` transfers `_amountReward` from `msg.sender` and then computes the new `rewardPerTokenStored` strictly from the nominal `_amountReward` parameter, never checking the pool's actual token balance before/after the transfer: [1](#0-0) 

`donateRewards` is exposed with no access-control modifier at all (unlike `queueNewRewards`, which requires `onlyManager`), so any unprivileged wallet can call it for any reward token that has already been registered via `isRewardToken`: [2](#0-1) 

If a registered reward token exhibits fee-on-transfer, rebasing, or any "balance changes outside of transfers" behavior, the amount actually received by `BaseRewardPool` will differ from `_amountReward`. Because `rewardPerTokenStored` is incremented using the nominal `_amountReward` rather than the measured balance delta, the contract's internal reward-per-share accounting becomes permanently inflated relative to its true token holdings — exactly the same root-cause bug as the referenced `StakingToken.sol` finding, just manifesting in the pool's reward-token bookkeeping (`rewards[rewardToken].rewardPerTokenStored`, `historicalRewards`) instead of `stakingToken`/`availableRewards`.

### Impact Explanation
Once `rewardPerTokenStored` overstates the actual reward token balance held by `BaseRewardPool`, every staker's `earned()` value (computed from `rewardPerTokenStored`) is overstated as well: [3](#0-2) 

When users call `getReward`, `IERC20(rewardToken).safeTransfer(_receiver, reward)` will eventually be unable to pay out the last claimants because the pool's true balance runs out before all recorded entitlements are honored: [4](#0-3) 

This causes a permanent freezing/loss of unclaimed yield for the users who claim last, since their `getReward` calls will revert (insufficient token balance) with no mechanism to reconcile the shortfall. This matches the accepted impact category of "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
The vulnerability is triggered purely by an ordinary, unprivileged wallet calling the public `donateRewards` function — no admin or governance action is required to exploit it once a non-standard reward token is registered as a reward token (which only requires one privileged `queueNewRewards` call at any point in the reward token's lifetime, consistent with the project's own README claim of in-scope "Fee on transfer" and "Balance changes outside of transfers" token behavior). Any subsequent unprivileged call to `donateRewards` for that token silently corrupts the shared reward accounting for all stakers of that pool.

### Recommendation
In `_provisionReward`, measure the actual token balance before and after `safeTransferFrom` and use the observed delta (not the caller-supplied `_amountReward`) when updating `historicalRewards` and `rewardPerTokenStored`. Alternatively, restrict `donateRewards`/reward-token support to tokens verified not to exhibit fee-on-transfer or rebasing behavior.

### Proof of Concept
1. A manager registers a reward token `R` via `queueNewRewards` at some point (satisfies `isRewardToken[R] = true`).
2. `R` is (or later becomes, e.g., via a proxy upgrade, migration, or is simply a fee-charging token) a fee-on-transfer/rebasing token.
3. Any unprivileged wallet calls `donateRewards(1000e18, R)`.
4. `_provisionReward` calls `safeTransferFrom(msg.sender, address(this), 1000e18)`, but the pool actually only receives e.g. `990e18` due to the transfer fee.
5. `rewardInfo.rewardPerTokenStored` is incremented using the full `1000e18` (via `(_amountReward * 10**stakingDecimals()) / totalStaked()`), overstating claimable rewards by `10e18` worth relative to the real balance held.
6. As stakers call `getReward`, the last claimants' `safeTransfer` calls revert once the real balance is exhausted, permanently freezing their earned yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
