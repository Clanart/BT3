### Title
Unprivileged senders can impersonate internal (Branch/Change/Forwarded) outputs because ownership is attributed solely by `script_pubkey` — ([File: processor/src/networks/bitcoin.rs])

### Summary
The source bug is an ownership-attribution error: the custody check compares `msg.sender` against `ownerOf`, but `onERC721Received` minted to `from_` (the depositor), not the operator — the protocol assigns the asset to the wrong party and every downstream identity check fails. The same bug class exists in `bitcoin-serai` / the Bitcoin processor: `Bitcoin::get_outputs` (which wraps `Scanner::scan_transaction`) attributes each received output's *kind* — and therefore its protocol role — purely from which registered `script_pubkey` it pays to. Since the Branch/Change/Forwarded offset scripts are deterministically derivable by anyone from the group key, an unprivileged Bitcoin user can send funds to an "internal-only" script and have the processor record it as a protocol-internal output of that kind, misattributing an external transaction as e.g. change or a branch output.

### Finding Description
`Scanner` stores a `HashMap<ScriptBuf, Scalar>` mapping every registered script (base key, branch, change, forwarded offsets) to a scalar offset. `scan_transaction` classifies an output solely by `self.scripts.get(&output.script_pubkey)` — no check that the transaction was produced by the protocol, no binding to a sign plan. [1](#0-0) 

The offsets are public constants: `KEY_DST = b"Serai Bitcoin Output Offset"` and the offsets are `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")`. Anyone knowing the (public) group key can compute `p2tr_script_buf(key + G*offset)` for each kind. [2](#0-1) 

`get_outputs` then assigns `output.kind` from the offset and only attaches `data` (the InInstruction payload) and relies on kind to distinguish an external deposit from an internal output: `if output.kind == OutputType::External { output.data.clone_from(&data) }`. A transaction paying to the Branch/Change/Forwarded script of a registered key is reported as `OutputType::Branch`/`Change`/`Forwarded` — the protocol-internal classifications — even though it was authored by an arbitrary third party. [3](#0-2) 

This mirrors the audit issue exactly: the code "mints" the output record to the wrong role (internal party) based on an ambient property (script match / `from_` address) instead of binding it to the actual authorizing context (a protocol-signed transaction / `operator_`), and subsequent handling then operates on a wrong assumption of provenance.

### Impact Explanation
Outputs attributed to the wrong party are pushed to the scheduler as if they were protocol-internal funds: a `Change` output is treated as change belonging to a signing operation, `Branch`/`Forwarded` as branch/forward outputs, and none receive `External` deposit handling (no InInstruction data, so the depositor is never credited). Consequences include: attacker-sent satoshis being recorded as internal wallet funds with no corresponding deposit credit (accounting inflation of internal balances), an attacker's payment to the `Forwarded` script causing the processor to attempt treating it as a forwarded output in a flow it never originated, and mis-classified change being acked through `ack_block`/`ScannerEvent::Block` without any plan that produced it. This is the analog of "commitToLiens can't execute": funds are reported received under an identity they don't have. Severity: Medium — it requires no privileged position (anyone can send a Bitcoin transaction), but the direct effect is misattribution/misaccounting rather than outright theft, since the underlying key+offset does remain spendable by the multisig.

### Likelihood Explanation
The scripts are computable entirely offline: `hash_to_F` with the fixed `KEY_DST`, plus the published group key. Any Bitcoin user who wants to grief the protocol — or simply makes an honest mistake by deriving a deposit address incorrectly — can produce a transaction hitting a Branch/Change/Forwarded script. Notably, the code itself acknowledges the danger in `register_offset`'s doc comment ("offsets are surjective... arbitrary offsets may introduce a script path"), yet nothing prevents or detects external sends to the internal scripts at classification time.

### Recommendation
Bind output classification to provenance, not just script. Concretely: only accept `Branch`/`Change`/`Forwarded` outputs when the spending transaction matches a known pending plan/eventuality (e.g., its txid is registered in `eventualities.map`, which is already tracked in `get_eventuality_completions`), or when its inputs spend previously-known protocol outputs. External transactions paying to internal offset scripts should either be rejected/ignored or surfaced as a distinct `Unexpected` kind for manual handling, rather than silently recorded as internal outputs.

### Proof of Concept
1. Obtain the multisig group key `K` (public).
2. Compute `off_change = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` and derive `script = p2tr_script_buf(K + G*off_change)` (incrementing the offset if the point is odd, per `register_offset`).
3. Broadcast any Bitcoin transaction paying `script`.
4. `Scanner::scan_transaction` matches `output.script_pubkey` and emits a `ReceivedOutput` whose offset maps (via `kinds`) to `OutputType::Change`; `get_outputs` returns it as an internal change output with `data: vec![]` and no InInstruction processing. The deposit is recorded as protocol-internal change despite never originating from a protocol-signed transaction — identical in shape to Astaria minting collateral ownership to the depositor instead of the router that must act on it.

Caveat: the exact downstream scheduler handling of an unattributed `Change`/`Branch` output (panic, silent balance credit, or mis-assignment to a pending plan) lives in processor scheduler code I did not fully trace; the root cause — unauthenticated kind assignment from `script_pubkey` alone in `scan_transaction`/`get_outputs` — is directly confirmed in the cited code.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

const KEY_DST: &[u8] = b"Serai Bitcoin Output Offset";
static BRANCH_OFFSET: OnceLock<Scalar> = OnceLock::new();
static CHANGE_OFFSET: OnceLock<Scalar> = OnceLock::new();
static FORWARD_OFFSET: OnceLock<Scalar> = OnceLock::new();

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  (scanner, offsets, kinds)
}

  async fn get_outputs(&self, block: &Self::Block, key: ProjectivePoint) -> Vec<Output> {
    let (scanner, _, kinds) = scanner(key);

    let mut outputs = vec![];
    // Skip the coinbase transaction which is burdened by maturity
    for tx in &block.txdata[1 ..] {
      for output in scanner.scan_transaction(tx) {
        let offset_repr = output.offset().to_repr();
        let offset_repr_ref: &[u8] = offset_repr.as_ref();
        let kind = kinds[offset_repr_ref];

        let output = Output { kind, presumed_origin: None, output, data: vec![] };
        assert_eq!(output.tx_id(), tx.id());
        outputs.push(output);
      }

      if outputs.is_empty() {
        continue;
      }

      // populate the outputs with the origin and data
      let presumed_origin = {
        // This may identify the P2WSH output *embedding the InInstruction* as the origin, which
        // would be a bit trickier to spend that a traditional output...
        // There's no risk of the InInstruction going missing as it'd already be on-chain though
        // We *could* parse out the script *without the InInstruction prefix* and declare that the
        // origin
        // TODO
        let spent_output = {
          let input = &tx.input[0];
          let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
          spent_tx.reverse();
          let mut tx;
          while {
            tx = self.rpc.get_transaction(&spent_tx).await;
            tx.is_err()
          } {
            log::error!("couldn't get transaction from bitcoin node: {tx:?}");
            sleep(Duration::from_secs(5)).await;
          }
          tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
        };
        Address::new(spent_output.script_pubkey)
      };
      let data = Self::extract_serai_data(tx);
      for output in &mut outputs {
        if output.kind == OutputType::External {
          output.data.clone_from(&data);
        }
        output.presumed_origin.clone_from(&presumed_origin);
      }
    }

    outputs
  }
