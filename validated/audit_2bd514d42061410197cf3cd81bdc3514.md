### Title
Forged `ReceivedOutput` records bind unrelated outpoints to signer-controlled prevouts, enabling unintended Taproot transaction signatures - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
Medium severity. `ReceivedOutput::read` accepts an attacker-chosen scalar offset, `TxOut`, and `OutPoint` as independent fields without authenticating that the `OutPoint` resolves to the supplied `TxOut` or that the signer owns it. `SignableTransaction` then treats the claimed `TxOut` as the spendable prevout while spending the attacker-selected `OutPoint`. This is the Serai analog of object-ID authorization failure: an unprivileged party can select an arbitrary object identifier while substituting data that passes the wallet's ownership check.

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` independently and returns them as a supposedly spendable output, without checking the transaction at `outpoint.txid`, its `vout`, or the actual script and amount. [1](#0-0) 

`SignableTransaction::new` trusts the supplied `output.value` when calculating available input funds and places the separately supplied `outpoint` in each transaction input. [2](#0-1) 

Before signing, `SignableTransaction::multisig` only verifies that `keys.offset(input.offset).group_key()` produces the declared `TxOut.script_pubkey`; it does not verify that this `TxOut` is the actual output referenced by `input.outpoint`. [3](#0-2) 

The transaction machine then signs Taproot key-spend hashes over the claimed `Prevouts::All`, while the transaction's inputs continue to name the attacker-selected outpoints. [4](#0-3) 

### Impact Explanation
An attacker can forge a serialized `ReceivedOutput` naming another party's UTXO, or a nonexistent UTXO, while supplying a `TxOut` paying to the signer's base key and using offset zero. The ownership check succeeds because it validates only the forged `TxOut`, so the threshold group signs a transaction it did not intend to sign and has no authority to settle. [5](#0-4) 

If a caller treats deserialized `ReceivedOutput` values as spendable inventory, this reports funds as received even though they are not spendable. The signed transaction is also unconfirmable when the real prevout's amount or script differs from the forged `TxOut`, causing incorrect balance accounting and repeated failed spend attempts. [6](#0-5) 

### Likelihood Explanation
The attack requires only control of bytes passed to `ReceivedOutput::read` and knowledge of the wallet's Taproot group key; it does not require validator access, private-key material, malformed curve encodings, or hash collisions. Its impact is bounded because consensus validation prevents the forged input from being spent when the referenced output differs, but the deserialization still produces a false spendable-output record and induces signatures over an unintended transaction. [1](#0-0) 

### Recommendation
Do not deserialize an arbitrary `OutPoint`/`TxOut` pair directly into a `ReceivedOutput` representing spendable funds. Before constructing or accepting one, fetch the transaction named by `outpoint.txid`, verify `outpoint.vout` is in range, compare the actual `TxOut` to the supplied one, and derive the offset only through `Scanner` or an equivalently authenticated mapping. [7](#0-6) 

For persisted or remote inputs, use distinct trusted and untrusted representations: the untrusted representation should contain only the outpoint or the full source transaction proof, while the trusted `ReceivedOutput` should be produced solely after chain verification. `SignableTransaction::multisig` cannot perform this verification by itself because it lacks access to the actual prevout data. [8](#0-7) 

### Proof of Concept
The forged object pairs an arbitrary `OutPoint` with a `TxOut` paying to the signer's unoffset Taproot key:

```rust
use bitcoin::{OutPoint, TxOut, Amount, consensus::serialize};
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

// `victim_outpoint` may identify another party's UTXO or a nonexistent output.
let victim_outpoint: OutPoint = attacker_supplied_outpoint();

// Claim the referenced output pays to the threshold wallet's base key.
let claimed = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: p2tr_script_buf(group_key).unwrap(),
};

// ReceivedOutput's wire format is scalar || TxOut || OutPoint.
let mut encoded = vec![];
encoded.extend(Secp256k1::F::ZERO.to_bytes().as_ref());
encoded.extend(serialize(&claimed));
encoded.extend(serialize(&victim_outpoint));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
let tx = SignableTransaction::new(
  vec![forged],
  &[(attacker_payment_script, 100_000)],
  None,
  None,
  1,
).unwrap();

// This returns Some because offset=0 and the forged TxOut script matches group_key.
let machine = tx.multisig(&threshold_keys).unwrap();
```

Completing `machine` signs the transaction input naming `victim_outpoint`, although the signature commits to the forged `claimed` amount and script rather than the referenced UTXO's real contents. [9](#0-8)
