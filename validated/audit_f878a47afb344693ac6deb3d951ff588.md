## Analysis

The Alchemix report's core flaw is a **stale/accumulated value being reapplied as if it still matched the current state**, without being revalidated against what actually changed (`epochRevenues[currentEpoch][token] += thisBalance` blindly trusts a balance that already includes old, unaccounted-for revenue). The closest structural analog in GitHub Desktop is in how partial line-selection state for the Changes/Commit view is carried forward across `git status` refreshes without validating it against the *current* diff content of the file.

### Title
Stale line-selection state is blindly reapplied across status refreshes, allowing silent inclusion/exclusion of unreviewed lines in a commit - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`WorkingDirectoryFileChange.id` is derived only from the file's status kind and path — never from its content — [1](#0-0) . When `updateChangedFiles` merges a new `git status` result into existing state, it looks a file up by that path/kind-based ID and, if found, unconditionally reapplies the *old* `DiffSelection` object (including its `divergingLines` line-index set) to the *new* file object, with no check that the diff content behind that path is still the same: `return file.withSelection(existingFile.selection)` [2](#0-1) . `DiffSelection.isSelected`/`getSelectionType` operate purely on line indices vs. a `divergingLines` set, with no notion of what content those indices actually correspond to [3](#0-2) .

### Finding Description
The only place that revalidates a stale partial selection against a changed diff is `updateChangesWorkingDirectoryDiff`, and it only does so for the single file that is **currently open in the diff viewer** — it recomputes `selectableLines` from the freshly loaded diff and calls `withSelectableLines` to drop indices that no longer exist [4](#0-3) . Every other file with a pre-existing partial selection in the working directory is merged via `updateChangedFiles` with no equivalent revalidation — the old `divergingLines` set (computed against a previous version of the file's diff) is carried forward verbatim onto the new file object [5](#0-4) .

Because the id/path/status match is the only key used to "recognize" the file as unchanged, if the on-disk content of a tracked file at that path is rewritten between two status refreshes (its status kind staying e.g. `Modified`), the previously selected/deselected *line indices* get silently reapplied to what is now a semantically different diff. `isSelected(lineIndex)` has no way to know the underlying hunk content moved — it just checks whether the index is in `divergingLines`.

This content rewrite between refreshes is realistic without any local/physical access or existing malware: git-tracked automation that Desktop itself executes as part of normal operations (git hooks configured via `core.hooksPath`, e.g. installed by tooling like Husky during a routine `npm install` on a freshly cloned attacker-controlled repository) can modify a tracked file's content on checkout/merge/commit events. An attacker who controls the cloned repository's contents thus controls this rewrite trigger.

### Impact Explanation
If a user has crafted a careful **partial** line selection on a file (e.g., intentionally excluding a suspicious block, or including only a reviewed subset of changes) and the file's content is rewritten by repo-controlled automation before the user hits "Commit", the checkboxes/highlighting shown for that file no longer correspond to the actual line indices being included. The user can end up silently committing and pushing content they never selected or reviewed — this is a direct case of "silent corruption of what the user commits or pushes," since the UI still shows the file as "partially selected" with no indication that the underlying diff shifted.

### Likelihood Explanation
Requires: (1) an attacker-controlled cloned/fetched repository with tracked automation capable of rewriting a file's contents during a git operation Desktop performs, and (2) the victim having an in-flight partial selection on that file at the time of the rewrite. This is a plausible but timing-dependent scenario — it is not attacker-triggerable on demand for an arbitrary victim action, which limits likelihood relative to a fully attacker-controlled corruption primitive.

### Recommendation
In `updateChangedFiles`, don't trust the path/status-based `id` match alone to justify reusing a `DiffSelection`. Either invalidate/clear (or re-derive `selectableLines` for) any partial selection whenever the underlying file's diff/content hash differs from what it was when the selection was captured, or extend the `withSelectableLines` revalidation performed in `updateChangesWorkingDirectoryDiff` to run for every file with a `Partial` selection, not just the one currently open in the diff viewer.

### Proof of Concept
1. Clone an attacker-controlled repository that configures `core.hooksPath` to a repo-tracked hooks directory (e.g., via a `postinstall` script run during a normal `npm install`), with a `post-checkout`/`post-merge` hook that rewrites a specific tracked file's content (same path, same status) while preserving line count/shape so the change looks unremarkable.
2. In Desktop, modify that file locally and use the diff viewer to select only specific lines to include in the next commit (`DiffSelectionType.Partial`), then navigate away so the file is no longer the actively-viewed diff.
3. Trigger a git operation that runs the malicious hook (e.g., checkout/merge/pull), causing the file's actual diff content to change while its path/status kind remain the same.
4. Observe that the working directory listing continues to show the file as "Partial" using the old `divergingLines` indices reapplied via `file.withSelection(existingFile.selection)` in `updateChangedFiles`, with no revalidation against the new diff (confirmed by the code path shown above and the absence of equivalent `withSelectableLines` handling outside `updateChangesWorkingDirectoryDiff`).
5. Commit: the actual staged content no longer matches what the user selected/reviewed, since the indices now map to different lines.

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
