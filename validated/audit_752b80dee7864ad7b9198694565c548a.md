### Title
Stale diff-selection reuse in `updateChangedFiles` can cause partial-commit line selections to be silently misapplied to changed file content - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateChangedFiles` decides whether to keep a file's previous partial line-selection (`DiffSelection`) and cached rendered `diff` purely by comparing the file's `id` (a path/status-derived identifier) for equality between the old and new `IStatusResult`, never checking whether the file's actual diff content/line layout changed. This mirrors the Hats `_removeSigner` bug pattern: a coarse equality check (`id === id`, analogous to `validSignerCount === currentSignerCount`) is used as a proxy for "nothing meaningful changed", when in fact the underlying data (line ranges/hunks) can have shifted without the identifier changing. [1](#0-0) 

### Finding Description
When Desktop refreshes working-directory status, `updateChangedFiles` merges the newly reported files with the previous state by `id`, and if a file with the same `id` existed before, it carries the old `DiffSelection` (including any partial/diverging-line state) forward onto the new file object: [2](#0-1) 

Separately, the cached rendered `diff` object shown in the UI is preserved across a refresh solely because the *same single file id* remains selected before and after: [3](#0-2) 

`DiffSelection`'s partial state (`divergingLines`) is expressed purely as line-index numbers, and `withSelectableLines` only prunes it against a *new* selectable-line set when explicitly called — it does not detect that the meaning of "line 12" has changed because the diff underneath shifted (e.g. lines added/removed above it): [4](#0-3) 

`id` equality is treated as the analogue of "nothing changed," exactly as `validSignerCount == currentSignerCount` was treated as "no invariant-relevant change" in the Hats contract, ignoring the case where the underlying quantity (line layout / diff content) moved between checks. If a file's on-disk content is rewritten between the status snapshot and the moment the cached diff/selection is reused (e.g., by a checked-in git hook such as `post-checkout`/`post-merge`, a clean/smudge filter declared in a cloned repository's `.gitattributes`, or any background process/tool operating on the working tree while Desktop is mid-refresh), the file keeps the same `id` (path-derived) while its hunks/line offsets change. Desktop will then reuse the old `DiffSelection`'s diverging-line indices and/or stale cached diff against the new content.

### Impact Explanation
Actual staging at commit time is computed by `applyPatchToIndex`/`formatPatch`, which re-fetches the diff and reapplies the `DiffSelection` by line index at that later point: [5](#0-4) 

If the selection's diverging-line indices were computed against an older hunk layout while the file content backing that path was altered by something outside the user's direct action (attacker-supplied hook/filter in a cloned repository), the indices no longer correspond to the same logical lines the user actually reviewed and checked. This can result in unintended lines being included in — or excluded from — a partial commit, i.e., silent corruption of what the user commits, without any error or warning, because the equality check (`id === id`) short-circuits any content-aware invalidation.

### Likelihood Explanation
This requires a timing condition: the working tree content for a given path must change (via a hook, filter, or external tool) in the narrow window between Desktop reading `git status`/computing `id` and the user's partial-selection/diff being reused/applied, while the file's `id` (path-based) stays the same. This is a race/logic condition rather than a straightforward, deterministic exploit, and I was not able to fully confirm the exact composition of `WorkingDirectoryFileChange.id` (whether it purely reflects the path or also incorporates status kind) within this session due to tool-call limits, which affects precise likelihood assessment. Given that, this should be treated as a plausible but not fully verified analog — likelihood is Low/Medium, and further investigation of the `id` field and the exact refresh scheduling around `_loadStatus`/`updateChangesWorkingDirectoryDiff` would be needed to confirm exploitability.

### Recommendation
Do not rely on `id` equality alone to decide whether to preserve a `DiffSelection` or cached diff across a status refresh. Instead, invalidate/re-derive the selection (and clear the cached diff) whenever the underlying diff's selectable-line set or hunk boundaries differ from what the selection was computed against — e.g., store a content fingerprint (e.g., blob SHA or diff hash) alongside the selection and only reuse it when that fingerprint matches, similar to how the Hats fix recommends deriving `signerCount` dynamically instead of trusting a potentially-stale cached count.

### Proof of Concept
Conceptual (not fully verified end-to-end in this session due to time constraints):
1. Attacker publishes/hosts a repository containing a `post-checkout` (or similar) hook, or a `.gitattributes` clean/smudge filter, that rewrites a tracked file's content when triggered.
2. Victim opens the repo in Desktop and begins partially selecting lines to commit in that file via the Changes view.
3. Desktop performs a background `_refreshRepository`/`_loadStatus` cycle (e.g., on window focus, periodic indicator refresh) while the hook/filter rewrites the file's content, shifting hunk line numbers but keeping the same file path/`id`.
4. `updateChangedFiles` reuses the old `DiffSelection`'s diverging-line indices onto the new file object because `id` matched (`app/src/lib/stores/updates/changes-state.ts:43-59`), and the cached diff is preserved because the selected file id didn't change (`changes-state.ts:90-95`).
5. When the user commits, `applyPatchToIndex`/`formatPatch` re-fetches the current diff and applies the stale line-index selection, staging different lines than the ones the user visually reviewed and checked. [6](#0-5)
