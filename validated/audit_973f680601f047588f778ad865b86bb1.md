Based on my research, I found a concrete asymmetry in the IBC callback handling code that mirrors the "report success/failure inconsistently with actual state commit" bug class from the report.

### Title
Timeout callback state changes are committed directly to the real context even when the callback is reported as failed - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`IBCOnTimeoutPacketCallback` executes the EVM callback contract call directly against the live `ctx` instead of the isolated `cachedCtx`/`writeFn` pattern used by its sibling function `IBCOnAcknowledgementPacketCallback`. This means any state mutation performed by the callback contract (balance transfers, ERC20 mints/burns, storage writes) is committed to the real store immediately, even though the function can still return an error afterward (reporting the callback as "failed") based on a post-hoc gas check.

### Finding Description
In `IBCOnAcknowledgementPacketCallback`, the pattern used is deliberately transactional: a `cachedCtx` is created via `ctx.CacheContext()`, the EVM call is executed against `cachedCtx`, and only if all checks pass (including the gas-limit check) is `writeFn()` invoked to commit the cached changes to `ctx`: [1](#0-0) 

In contrast, `IBCOnTimeoutPacketCallback` also creates a `cachedCtx`, but never uses it for the EVM call — it calls `k.evmKeeper.CallEVM(ctx, ...)` directly on the real `ctx`: [2](#0-1) 

Because the EVM call is executed and (per `commit=true`) committed directly against the live `ctx`, any state changes made by the contract's `onPacketTimeout` implementation are persisted to the chain state immediately during execution — before the subsequent `ctx.GasMeter().IsOutOfGas()` check on line 432-434 that can still cause the function to return `types.ErrCallbackFailed`. The `writeFn()` call at the end is a no-op with respect to the actual EVM effects, since `cachedCtx` was never passed to `CallEVM`.

This is analogous to the reported `SwapCallLib.call()` bug: the outer caller is told the operation failed (an error propagates up, and ibc-go's callback middleware treats `onPacketTimeout` as failed per ADR-8/callbacks spec, generally without halting the base packet-lifecycle logic), but the state changes made by the "failed" operation are not rolled back.

Compounding this, the integration test suite for timeout callbacks explicitly documents that the base IBC refund logic proceeds independently of callback success or failure: [3](#0-2) 

### Impact Explanation
Since the base timeout refund (crediting the original sender with the escrowed/sent tokens) happens regardless of whether the EVM callback reports success or failure, and the callback's own state changes (potential token transfers/mints triggered by the contract's `onPacketTimeout` logic) are committed to `ctx` unconditionally before the "failed" determination is made, a malicious contract registered as an `src_callback` timeout handler can:
1. Receive/mint/transfer value to itself or another address during `onPacketTimeout` execution (committed to the real state immediately via the direct `ctx` call).
2. Deliberately consume gas close to `cbData.CommitGasLimit` so the subsequent `ctx.GasMeter().IsOutOfGas()` check trips, causing the callback to be reported as "failed."
3. Still receive the independent timeout refund of the original escrowed amount, since that refund path does not check whether the callback succeeded.

This results in duplicated/unauthorized value: the contract obtains value both from its own (nominally "failed") callback execution and from the standard timeout refund, corrupting IBC escrow accounting — matching the "Critical unauthorized minting, burning, duplication... of spendable user value across... IBC escrows" impact category.

### Likelihood Explanation
The trigger is fully within reach of an unprivileged user: any account can initiate an ICS20 transfer with a `memo` containing a `src_callback` pointing to a contract they control, and cause (or wait for) a timeout. The attacker controls the callback contract's gas consumption precisely (e.g., via a loop or `SSTORE` operations) to land just over `cbData.CommitGasLimit`, making the "fail late" condition reliably reproducible without any privileged access, relayer collusion, or validator behavior.

### Recommendation
Mirror the transactional pattern already used in `IBCOnAcknowledgementPacketCallback`: execute `k.evmKeeper.CallEVM` against `cachedCtx` (not `ctx`) in `IBCOnTimeoutPacketCallback`, and only call `writeFn()` after the gas-limit check succeeds, so that a callback which is ultimately reported as failed cannot have any of its state effects persisted.

### Proof of Concept
Not fully executable from static analysis alone — I was unable to confirm from the available index the exact internal commit/revert semantics of `x/vm/keeper/call_evm.go`'s `CallEVM` (specifically whether `commit=true` writes state to the passed-in `ctx` even when gas is later found to exceed the caller-imposed `CommitGasLimit`, versus only being contingent on the EVM-level `vm.ErrExecutionReverted`). This distinction is important: if `CallEVM` itself always commits on `commit=true` regardless of the caller's post-hoc gas check, the vulnerability is as described. A background engineering session with full repository/build access would be needed to trace `CallEVM` → `ApplyMessage`/`ApplyMessageWithConfig` → `StateDB.Commit()` to confirm the exact commit boundary before treating this as a confirmed, exploitable Critical finding.
