## Analysis Summary

The Sherlock report's core issue is a **normalized "one-size-fits-all" check that is correct for the common case but silently fails for other cases the code claims to guard against** (decimals assumed to be 6, breaking for 18-decimal tokens). The strongest structural analog in `Annirich/desktop--005` is the shared path-containment helper `_resolveWithin`, which uses a **prefix-string comparison without a path-separator boundary check** to decide whether a resolved path stays inside a root directory. [1](#0-0) 

`realResolved.startsWith(realRoot)` returns `true` for any path that textually begins with `realRoot`, even when it is actually a **sibling** directory (e.g. root `/Users/victim/Documents/GitHub/repo` vs. sibling `/Users/victim/Documents/GitHub/repo-backup/secret.txt`) — there is no check that the character immediately following `realRoot` in `realResolved` is a path separator. This is exactly the same class of bug as the Sherlock report: the guard "looks correct" and passes every naive test (traversal via `../`), but is broken for a structurally adjacent input the guard was supposed to reject.

This helper directly gates the attacker-reachable deep-link handler for `x-github-client://openRepo/...?filepath=...`, which is parsed from a URL a user is enticed to click: [2](#0-1) 

### Title
Path-containment check in `resolveWithin` uses substring `startsWith` without a separator boundary, allowing escape to sibling directories via the `openRepo` deep-link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin`/`_resolveWithin` is the shared guard used to ensure a user- or attacker-supplied relative path stays inside a repository root before being touched by the app. Its final check, `realResolved.startsWith(realRoot)`, treats any resolved path that textually begins with the root path as "inside" the root, even when the resolved path is actually a sibling directory that merely shares a name prefix. An attacker who controls the `filepath` query parameter of an `x-github-client://openRepo/...` deep link (delivered via a normal clickable link) can supply a `filepath` value that, once joined/normalized against the victim's repository root, resolves to a path outside the repository whose absolute string happens to start with the root path.

### Finding Description
`_resolveWithin` normalizes the root and the joined relative segments, blocks null bytes, resolves to an absolute path, and then calls `realpath` on both the root and the resolved candidate before doing a **plain string prefix comparison**: [3](#0-2) . This mirrors the Sherlock bug's pattern exactly: a single "protective calculation" (there, `mulDiv` scaled to 6 decimals; here, `startsWith`) is applied uniformly under the assumption that the only unsafe case is the one the author had in mind (there, non-USDC decimals; here, `../` traversal), while a different, equally reachable case (a sibling path with an overlapping literal prefix, e.g. root `.../GitHub/repo` and sibling `.../GitHub/repo-old` or `.../GitHub/repository-secrets`) is left completely unguarded.

The reachable attacker path is the `open-repository-from-url` deep link action, parsed by `parseAppURL` (tested for `openRepo` with `filepath`) and dispatched to `openRepositoryFromUrl`, which calls `resolveWithin(repository.path, filepath)` directly with the attacker-controlled `filepath` before doing anything with the result: [2](#0-1) . Only an `isAbsolute(filepath)` check is performed before calling `resolveWithin`; there is no check that guards against the sibling-prefix collision inherent in the helper itself.

### Impact Explanation
If the victim has (or an attacker can predict/cause the victim to have) two sibling repository/folders where one name is a literal prefix of another under the same parent directory — a very plausible situation given how GitHub Desktop lays out cloned repositories in a common parent folder and disambiguates duplicate names — a crafted `filepath` value can cause `resolveWithin` to accept a path that lives outside the intended repository. The result is currently piped into `shell.showItemInFolder(resolved)`, which reveals/selects an out-of-repository file to the user in their OS file manager; because `resolveWithin` is a general-purpose containment primitive used elsewhere for path safety in the codebase, any current or future caller that uses its result to read, write, or execute a file (rather than merely reveal it) would inherit a full out-of-repository file read/write primitive. This matches the "read outside the repo" impact category via an attacker-controlled deep link.

### Likelihood Explanation
The attack requires no local access, no credentials, and no privileged assumptions — only that the victim clicks an attacker-supplied `x-github-client://openRepo/<repo-url>?filepath=<payload>` link, a flow explicitly supported and unit-tested in the codebase [4](#0-3) . The only precondition beyond that is the existence of a sibling directory whose absolute path is a superstring of the repository's path, which is a common and easily arranged file-system layout for anyone who has cloned more than one similarly named repository into the same parent folder.

### Recommendation
Change the containment check in `_resolveWithin` to require a path-separator boundary (or use `path.relative(realRoot, realResolved)` and verify the result does not start with `..` and is not absolute) instead of a raw `startsWith` string comparison:

```ts
const rel = relative(realRoot, realResolved)
return rel === '' || (!rel.startsWith('..') && !isAbsolute(rel)) ? resolved : null
```

### Proof of Concept
1. Victim has cloned two repositories into the same parent directory, e.g. `~/Documents/GitHub/app` and `~/Documents/GitHub/app-secrets` (the latter containing a sensitive file `token.txt`).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/owner/app?filepath=../app-secrets/token.txt`.
3. `parseAppURL` parses this into `{ name: 'open-repository-from-url', url: 'https://github.com/owner/app', filepath: '../app-secrets/token.txt' }`.
4. `openRepositoryFromUrl` resolves/opens the local `app` repository, then calls `resolveWithin(repository.path /* .../GitHub/app */, '../app-secrets/token.txt')`.
5. Inside `_resolveWithin`, `resolved` becomes `.../GitHub/app-secrets/token.txt`; `realResolved.startsWith(realRoot)` evaluates `'.../GitHub/app-secrets/token.txt'.startsWith('.../GitHub/app')`, which is `true` even though `app-secrets` is a sibling, not a subdirectory, of `app`.
6. `resolveWithin` incorrectly returns the out-of-repository path, and `shell.showItemInFolder` reveals it — demonstrating the containment guard's escape, exactly analogous to the Sherlock report's "protective calculation succeeds structurally but fails for the case that matters."

**Note on evidence limits:** I could not find a caller of `resolveWithin` that performs a stronger destructive action (write/execute) than `shell.showItemInFolder`; if such a caller exists elsewhere in the full codebase (not indexed here), the severity would increase from information disclosure/reveal to a genuine file write or execution primitive. I recommend a full-repository grep for all `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` call sites to rule this out, which may require a Devin session with full repository access if the index is incomplete.
