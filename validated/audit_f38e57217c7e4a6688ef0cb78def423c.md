Based on the investigation, the closest legitimate analog in GitHub Desktop is a validation gap in the deep-link URL parser (`app/src/lib/parse-app-url.ts`) that mirrors the report's core pattern: an attacker-controlled identifier that bypasses validation applied to sibling fields and is trusted downstream.

### Title
Unsanitized `filepath` parameter in `openRepo` deep links allows path traversal outside the cloned repository - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` handles the `x-github-client://openrepo/...` (and legacy `github-mac://openrepo/...`) deep link, which a user can be lured into clicking from any website, README, or chat message. The parser validates the `pr` and `branch` query parameters against `testForInvalidChars` before accepting the action, but it passes the `filepath` parameter straight through with no validation at all.

### Finding Description
`parseAppURL` extracts `branch` and `filepath` the same way, but only `branch` is checked: [1](#0-0) 

Specifically:
- `branch` is rejected via `testForInvalidChars(branch)` [2](#0-1) 
- `filepath` is read via the same `getQueryStringValue` helper but never passed through `testForInvalidChars`, `sanitizedRefName`, or any path-containment check [3](#0-2) 

The resulting `IOpenRepositoryFromURLAction.filepath` is documented as "the file to open after cloning the repository" [4](#0-3) , and is consumed by `Dispatcher` (`app/src/ui/dispatcher/dispatcher.ts`, `openRepositoryFromUrl`) after the repository has been cloned. Unlike `branch`, which is defended against ref-injection characters, `filepath` has no defense against `../` traversal sequences or absolute paths. The existing test suite confirms the value is accepted and forwarded unmodified regardless of content, e.g. `filepath=Octokit.Reactive%2FOctokit.Reactive.csproj` is passed through verbatim with no rejection test for traversal payloads: [5](#0-4) 

This breaks the same invariant as the smart-contract report: a value fully controlled by an untrusted party (here, whoever crafts the deep link, analogous to the attacker choosing the `loanId`) is checked inconsistently — some sibling parameters (`branch`, `pr`) are validated, but the one that is later used to resolve a filesystem path is not, so the "existence/validity" check that protects the rest of the action silently does not extend to `filepath`.

### Impact Explanation
If the value eventually reaches a file-open/read call joined against the freshly cloned repository path without being confined to that directory (e.g. `path.join(repoPath, filepath)` followed by opening it in the user's editor or reading it to display), a crafted deep link such as `x-github-client://openrepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa` could cause Desktop to open or read a file outside the cloned repository the moment the user clicks the "Open in Desktop" style link — satisfying the "file read outside the repo" impact class from a link the user clicks, with no prior local access or credentials needed. I was not able to retrieve the exact sink line in `dispatcher.ts`/`openRepositoryFromUrl` that consumes `filepath` in this session (tool budget exhausted), so whether this traversal is actually exploitable end-to-end (versus being sanitized right before the file-system call) is **not fully verified** and should be checked in `app/src/ui/dispatcher/dispatcher.ts` around the `openRepositoryFromUrl` and `filepath`-related matches.

### Likelihood Explanation
Deep links can be embedded in any web page, README, or message; users on GitHub Desktop are accustomed to clicking "Open in Desktop" style links, and Desktop registers itself for the relevant `x-github-client`/`github-mac`/`github-windows` protocols at startup [6](#0-5) [7](#0-6) . No authentication, local access, or malware is required — only that the victim click a link, which matches the valid-impact criteria for this scan.

### Recommendation
Apply the same `filepath` guarding as is used for `branch`: reject or sanitize any `filepath` value containing `..` path segments, absolute-path prefixes, or drive letters, and additionally re-validate at the consumption site that the resolved path is contained within the freshly cloned repository directory (e.g., via `path.resolve` + prefix check) before opening or reading it.

### Proof of Concept
1. Host or send a link: `x-github-client://openrepo/https://github.com/attacker/demo-repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim (with GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` accepts the action because only `branch`/`pr` are validated [1](#0-0) ; `filepath` is returned unmodified.
4. Desktop clones `attacker/demo-repo` and, per the documented behavior, attempts to open "the file to open after cloning" using the unsanitized `filepath` value.

Note: step 4's exact file-open call in `dispatcher.ts` could not be located within this session's tool budget; confirming the concrete sink (and whether any containment check exists there) is necessary to fully validate exploitability before treating this as conclusively confirmed.
