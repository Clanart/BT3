### Title
Front-running bribe distribution via `voteAndCast` allows an attacker to capture a share of freshly-harvested bribes with a zero-duration vote - (File: wombat/WombatBribeManager.sol)

### Summary
`voteAndCast()` calls `vote()` and `castVotes()` atomically in one transaction, and `vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, amount)` which increases `totalSupply`/`_balances` *before* `castVotes()` harvests and queues the bribe reward into `rewardPerTokenStored`. Because `_provisionReward()` divides the freshly harvested bribe by `totalStaked()` measured *after* the attacker's stake was added, the attacker is included in the denominator and simultaneously has their `userRewardPerTokenPaid` baseline frozen at the pre-harvest value, letting them capture a full proportional share of that epoch's bribe despite having held the position for zero time.

### Finding Description
The exploit path is:
1. `vote(address[] _lps, int256[] _deltas)` at [1](#0-0) : for a positive delta, it increases `pool.totalVoteInVlmgp` and calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))`.
2. `BribeRewardPool.stakeFor()` runs the `updateRewards(_for, rewardTokens)` modifier which snapshots `userRewardPerTokenPaid[_for] = rewardPerToken()` using the **old** balance/totalSupply, then increases `totalSupply` and `_balances[_for]` in the function body [2](#0-1)  and the shared modifier logic [3](#0-2) .
3. `castVotes(bool swapForBnb)` is then called in the same transaction [4](#0-3) , which computes vote deltas from the just-updated `pool.totalVoteInVlmgp` and calls `wombatStaking.vote(...)`, harvesting bribes and forwarding them into the rewarder via `queueNewRewards` → `_provisionReward()` [5](#0-4) .
4. `_provisionReward()` computes `rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()`, where `totalStaked()` already includes the attacker's brand-new stake added one call earlier in the same transaction.
5. Because the attacker's `userRewardPerTokenPaid` was frozen at the *pre-harvest* value in step 2, their subsequent `earned()`/`_earned()` computation [6](#0-5)  credits them with `balance * (new rewardPerTokenStored - old rewardPerTokenStored)`, i.e., a full proportional share of the bribe that was harvested for an epoch during which the attacker held no vote at all.

No existing check prevents this: `stakeFor`/`withdrawFor` have no cooldown or time-weighting, `updateRewards` only prevents *retroactive* claims on rewards already stored before the stake, not rewards queued in the same transaction immediately after the stake, and there is no `nonReentrant`/ordering guard between `vote()` and the reward-queuing side effect of `castVotes()`.

### Impact Explanation
This causes an economic transfer of unclaimed bribe yield: an attacker who calls `voteAndCast` immediately before a bribe harvest dilutes `totalStaked()` in the denominator of `_provisionReward()` and simultaneously captures reward accrual for the entire just-harvested amount proportional to their zero-duration stake. This siphons value away from genuine long-term voters who held their vote through the whole epoch, i.e., theft of unclaimed/queued yield from other bribe-pool participants to the attacker. This matches the "theft or permanent freezing of unclaimed yield" impact class; it does not directly touch locked principal (`vlMGP`/veWOM balances) or corrupt `getVoteForLp` vs `poolInfos[lp].totalVoteInVlmgp` reconciliation, since `castVotes()` recomputes the exact delta needed to bring the Wombat voter in line with `totalVoteInVlmgp` at cast time.

### Likelihood Explanation
The attack is fully unprivileged and repeatable: any address holding vlMGP voting power can call `voteAndCast` in the same block/transaction right before (or as) a bribe harvest occurs, requiring only enough vlMGP votable balance to make the front-run economically worthwhile and gas for one transaction. It is deterministic and does not depend on any race condition beyond ordinary transaction ordering/mempool visibility, and can be repeated every time a bribe cast is imminent.

### Recommendation
Decouple reward accrual timing from stake changes within the same transaction, e.g.: (a) apply a minimum holding/cooldown period before newly staked votes become eligible for currently-queued rewards, (b) snapshot `totalStaked()`/eligible balances at the start of the epoch rather than at `queueNewRewards()` time, or (c) restructure `voteAndCast` so that `castVotes()`'s harvested rewards are queued using the pre-vote `totalStaked()`/balances (i.e., harvest and queue rewards before applying the caller's own new `vote()` deltas, or require `castVotes()` to be called independently, disallowing atomic same-tx staking immediately before a harvest for the caller's own newly added vote).

### Proof of Concept
Foundry/Hardhat fork test outline:
1. Deploy/fork with an existing `WombatBribeManager`, `BribeRewardPool` for a target LP, and at least one long-term "victim" voter who has held a vote on that LP for a full epoch with pending bribe rewards accrued in the underlying Wombat bribe contract.
2. Snapshot `pool.rewarder.rewardPerToken(rewardToken)`, `pool.rewarder.earned(victim, rewardToken)`, and `pool.rewarder.totalStaked()` before the attack tx.
3. As an unprivileged attacker with vlMGP votable balance, call `voteAndCast([lp], [positiveDelta], false)` right before the scheduled/known keeper `castVotes()` call (or simply be the caller of that same cast).
4. After the tx, assert:
   - `IBribeRewardPool(rewarder).earned(attacker, rewardToken) > 0` despite the attacker's stake having existed for 0 blocks prior to the harvested epoch.
   - The victim's `earned(victim, rewardToken)` is lower than what it would have been had the attacker not diluted `totalStaked()` at harvest time (compute expected value as `oldRewardPerToken + harvestedAmount/oldTotalStaked` vs actual `rewardPerTokenStored` using `newTotalStaked`).
   - `getVoteForLp(lp)` (from Wombat voter) equals `poolInfos[lp].totalVoteInVlmgp` scaled by `totalVotes()/totalVlMgpInVote` after `castVotes()` completes, confirming the vote-side accounting reconciles while the reward-side accrual does not respect time-weighting.

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;
            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
        _;
    }

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
