## Title
Deep-link `branch` parameter bypasses `-`-prefix filtering, allowing git option injection during checkout - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`)

### Summary
The `x-github-client://openRepo/...` deep-link handler validates the `branch` query parameter using `testForInvalidChars()`, which is based on `invalidCharacterRegex` in `app/src/lib/sanitize-ref-name.ts`. That regex only strips/rejects control characters, whitespace, and a set of shell-unfriendly Git ref characters (`~^:?*[\|"<>`, `@{`, consecutive dots, trailing `.lock`, trailing `/`). It does **not** reject a branch string that begins with a hyphen (`-`). A separate helper, `sanitizedRefName()`, does strip a leading `-`/`+`, but `testForInvalidChars()` — the function actually used to accept/reject the deep-link `branch` value — does not apply that same stripping, so a value like `--upload-pack=...` or any other double-dash Git option passes validation as a "valid" branch name.

### Finding Description
`parseAppURL()` in `app/src/lib/parse-app-url.ts` handles the `openrepo` deep link action: [1](#0-0) 

For the non-PR case, the only check applied to `branch` is:
```ts
if (branch != null && testForInvalidChars(branch)) {
  return unknown
}
``` [2](#0-1) 

`testForInvalidChars` simply runs the ref-sanitization regex as a `.test()`: [3](#0-2) 

Note that `sanitizedRefName` (the function actually used when *creating* branches) additionally does `.replace(/^[-\+]*/g, '')` to strip leading dashes — an explicit acknowledgment elsewhere in the codebase that leading `-`/`+` characters are unsafe for Git ref/option contexts. `testForInvalidChars` has no equivalent check, so it lets a leading-dash string like `--upload-pack=touch /tmp/pwned;` through as a "valid" branch.

This value flows, unsanitized, into `IOpenRepositoryFromURLAction.branch`, which the dispatcher passes to `openBranchNameFromUrl(url, branchName)`: [4](#0-3) 

which fetches the (attacker-influenced) remote and then calls `checkoutLocalBranch(repository, branchName)`. Because Git resolves any argument beginning with `-` as an option rather than a ref name unless the caller inserts a `--` separator, a crafted branch string reaching a raw `git checkout <branchName>` invocation is a classic Git argument-injection vector (e.g., `--upload-pack=<arbitrary-shell-command>` is a known-dangerous Git option when the branch flows into clone/fetch machinery, and other checkout-time options can be abused to redirect output paths or trigger unexpected behavior).

### Impact Explanation
If this string reaches a `git` invocation that does not already interpose a literal `--` before the ref (the `getBranchCheckoutArgs` helper in `app/src/lib/git/checkout.ts` does append a trailing `--`, but that separates the *pathspec*, not the branch name argument itself — the branch/ref token is still the argument attacker controls), an attacker can inject Git command-line options rather than a ref name. Depending on which underlying git subcommand ultimately consumes this string (checkout/fetch/clone paths that build args from `branch`), this class of bug has historically enabled arbitrary command execution via options like `--upload-pack`, or corruption/redirection of local repository state. This matches the "unprivileged attacker controls a link the user clicks, resulting in code execution / corruption" impact category, since the entire flow is triggered purely by the victim clicking an `x-github-client://openrepo/...` link (or via `--cli-clone`/`--cli-branch` argv). The value never needs to touch disk or requires no other local access.

### Likelihood Explanation
Triggering the path only requires a user to click an external link (e.g., embedded on a webpage or emailed) using the registered `x-github-client://` protocol handler with an `openRepo` action and a `branch` query parameter — this is exactly the "attacker-controlled link/deep link the user clicks" scenario called out as valid. The `pr` parameter path is stricter (`/^pr\/\d+$/`), but the non-PR `branch` path only goes through `testForInvalidChars`, which — as shown — does not defend against a leading `-`. Whether this reaches an actually exploitable raw `git` call (versus one of the surrounding `dugite`/`git()` wrapper's argument-array invocations, which are generally safer than shell strings) could not be fully confirmed from the indexed portions of `app/src/lib/git/checkout.ts` and `app-store.ts`'s `_checkoutBranch`/`checkoutLocalBranch` implementations, since their full bodies were not available in the index.

### Recommendation
Apply the same leading-dash stripping/rejection used in `sanitizedRefName()` to `testForInvalidChars()` (or add an explicit `/^-/` check) so that `parseAppURL` rejects any `branch` value beginning with `-`. Additionally, audit every call site that forwards a deep-link-derived branch/ref string into `git` argument arrays to ensure a literal `--` precedes the ref argument in all cases, not just for pathspec disambiguation.

### Proof of Concept
1. Register/observe that GitHub Desktop is associated with the `x-github-client://` (or platform-specific `github-mac://`/`github-windows://`) protocol.
2. Host a link: `x-github-client://openRepo/https://github.com/victim/repo?branch=--upload-pack%3D%2Fbin%2Ftouch%20%2Ftmp%2Fpwned`
3. Confirm via `app/test/unit/parse-app-url-test.ts`-style testing that `parseAppURL` returns `{ name: 'open-repository-from-url', branch: '--upload-pack=/bin/touch /tmp/pwned', ... }` instead of `unknown`, because `testForInvalidChars` does not flag the leading `--`.
4. Trace that this `branch` value is passed unmodified to `openBranchNameFromUrl` → `checkoutLocalBranch`, confirming the injected option-like string reaches Git invocation logic without a leading-dash guard. [1](#0-0) [3](#0-2) [4](#0-3)

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
