`SmartWomConvert.smartConvert` is called with `_minRec = _amountIn` [1](#0-0) , which then flows into `_convertFor`, requiring `convertAmount + amountRec >= _amount` or it reverts with `MinRecNotMatch` [2](#0-1) . Since `amountRec` comes from a live AMM swap (`womMWomPool`) whose exchange rate is externally influenceable, an unfavorable/manipulated rate at call time makes the swap return less mWom than the wom portion swapped, violating the `_minRec` floor and reverting the whole call.

This `smartConvert` call sits inside `_sendRewards`, which is invoked from `_toMasterWomAndSendReward` [3](#0-2) , and `_toMasterWomAndSendReward` is on the direct path of `deposit`, `depositLP`, `withdraw`, and `harvest` for that pool [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) . `harvest` itself is unrestricted apart from `whenNotPaused` and `_onlyActivePool` — any address can call it [8](#0-7) . None of `nonReentrant`, `whenNotPaused`, or the pool-helper modifiers guard against this revert condition, since it's a hard revert deep in the fee-distribution branch that's unconditionally executed whenever WOM rewards are nonzero and `smartWomConverter` is set and the fee is flagged `isMWOM`.

### Title
Harvest/deposit/withdraw DoS via manipulable AMM price forcing `smartConvert` to revert - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` unconditionally routes the WOM harvest fee through `SmartWomConvert.smartConvert`, which enforces `_minRec == _amountIn` against a live AMM swap output. When the `wom`/`mWom` pool price is unfavorable (organically or via manipulation), the swap yields less than the input, `smartConvert` reverts with `MinRecNotMatch`, and because `_sendRewards` is embedded in `_toMasterWomAndSendReward`, this revert propagates and blocks `deposit`, `depositLP`, `withdraw`, and `harvest` for the affected pool.

### Finding Description
`smartConvert(_amountIn, _mode)` computes a `convertRatio` and calls `_convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode)`, i.e., `_minRec` is set equal to the full input amount regardless of how much is routed to the AMM swap leg [1](#0-0) . Inside `_convertFor`, the portion `buybackAmount` is swapped through `IWombatRouter.swapExactTokensForTokens` with `amountOutMin = 0` (no protection at the swap level), and the final check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` requires the swap output alone to cover any shortfall, i.e., effectively requires the AMM to return at least 1:1 wom-for-mWom on the swapped portion [9](#0-8) . This is entirely dependent on the current price/liquidity state of `womMWomPool`, an external, walkable AMM pool.

`WombatStaking._sendRewards` calls this whenever a fee is flagged `isMWOM` and `rewardToken == wom` and `smartWomConverter != address(0)`, with no try/catch or fallback [10](#0-9) . `_sendRewards` is called unconditionally from `_toMasterWomAndSendReward` whenever `womRewards > 0` [11](#0-10) , and `_toMasterWomAndSendReward` is invoked by `deposit`, `depositLP`, `withdraw`, and `harvest` [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) . None of the modifiers on these functions (`nonReentrant`, `whenNotPaused`, `_onlyActivePoolHelper`/`_onlyPoolHelper`/`_onlyActivePool`) guard against or bypass this revert — they only gate caller identity/pause state, not the internal fee-conversion outcome. As a result, once the `wom`/`mWom` AMM price sits at a level where the swap leg returns less than the amount swapped, every call into `deposit`, `depositLP`, `withdraw`, and `harvest` for pools accruing nonzero WOM rewards will unconditionally revert, since the reward split happens on the same call path as the user's principal action — there is no isolation between the fee-conversion side-effect and the core deposit/withdraw accounting (`IERC20(poolInfo.depositToken).balanceOf(address(this)) - beforeWithdraw` in `withdraw` is never reached because the earlier `_toMasterWomAndSendReward(_lpToken, _liquidity, false)` call reverts first) [12](#0-11) .

### Impact Explanation
While this condition persists, the affected pool's `deposit`, `depositLP`, `withdraw`, and `harvest` are all bricked, since they share the same unguarded revert path. This freezes user principal in the pool's receipt-token/LP wrapper until the AMM price recovers to a level where the swap output covers the swapped amount, or until the owner intervenes (e.g., disabling `smartWomConverter`, marking the pool fee-free, or removing the offending fee entry). This matches Immunefi's "Temporary freezing of funds" impact class, since deposits and withdrawals for the pool are blocked as long as the unfavorable price condition holds.

### Likelihood Explanation
Triggering the revert does not require any privileged role — the router swap (`amountOutMin = 0`) and `smartConvert`'s `_minRec == _amountIn` check depend purely on the live state of the public `womMWomPool`, which is influenceable by anyone trading against it, including via flash-loan-funded swaps within a block. The condition can also arise organically from normal market volatility without any attacker action, since `_minRec` is set to a strict 1:1 floor rather than a slippage-tolerant bound. Sustaining the unfavorable price long enough (e.g., 24+ hours) to produce a prolonged freeze requires capital to counteract arbitrage pressure back toward par, but repeated/targeted manipulation around each `harvest`/`deposit`/`withdraw` attempt for the pool is feasible at low cost and is repeatable indefinitely as long as `smartWomConverter` remains configured and the fee entry stays active.

### Recommendation
Decouple reward fee-conversion failures from the user-facing principal path: wrap the `smartConvert` call in a try/catch (or move fee-conversion into a separately callable/queued step) so that a revert in the WOM→mWom conversion cannot block `deposit`, `depositLP`, `withdraw`, or `harvest`. Additionally, replace the strict `_minRec == _amountIn` invariant in `smartConvert` with a slippage-tolerant bound (e.g., percentage-based, matching `estimateTotalConversion`), and pass a nonzero `amountOutMin` into the underlying router swap rather than `0`.

### Proof of Concept
Hardhat test plan:
1. Deploy `WombatStaking`, register a pool with `isPoolFeeFree` disabled, add a fee entry with `isMWOM = true`, and set `smartWomConverter` to a real `SmartWomConvert` instance wired to a real (or mock) Wombat `womMWomPool`/router.
2. Fund the pool so that `harvest`/`deposit` triggers a nonzero WOM reward from `masterWombat` (or mock `masterWombat.deposit/withdraw` to emit WOM to `WombatStaking`).
3. Manipulate `womMWomPool` (via a large swap or mock override) so that `currentRatio() < buybackThreshold` and the router's `wom -> mWom` swap returns less mWom than wom input for the `amountToSwap` portion.
4. Call `WombatStaking.harvest(_lpToken)` and assert it reverts with `MinRecNotMatch` (bubbled from `SmartWomConvert._convertFor`).
5. Call `WombatStaking.withdraw(_lpToken, _liquidity, _minAmount, _sender)` (via the pool helper) under the same manipulated price and assert it also reverts before reaching the `beforeWithdraw`/balance-diff transfer logic, confirming principal withdrawal is blocked.
6. Restore the pool price to par/favorable and confirm `harvest`/`withdraw` succeed again, demonstrating the freeze is contingent solely on the manipulable AMM price state.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
