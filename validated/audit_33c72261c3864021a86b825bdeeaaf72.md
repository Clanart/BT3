## Title
Copilot conflict-resolution writes AI-returned file paths without verifying they belong to the original conflicted-file set, enabling attacker-controlled write-anywhere-in-repo via prompt injection - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` in `app-store.ts` writes file content returned by the Copilot model to disk using the `path` field from the model's own JSON response, checked only for being inside the repository root (`resolveWithin`), never checked against the actual list of conflicted files that were sent to the model. [1](#0-0) 

### Finding Description
The Copilot conflict-resolution feature builds a prompt from attacker-influenceable data: file content surrounding conflict markers, recent commit messages from both merge sides, and PR titles/descriptions, all sourced from a repository/branch/PR that a user merges, rebases, or cherry-picks from. [2](#0-1) [3](#0-2) 

The model is instructed to reply with a JSON object whose `resolutions[].path` field identifies which file each resolution belongs to. [4](#0-3) 

The response parser (`parseCopilotConflictResolution`) validates only that `path` is a non-empty string and normalizes it; it never validates the path is one of the files that were actually part of the conflict set sent in the request. [5](#0-4) 

When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` iterates every returned resolution and calls `resolveWithin(repository.path, resolution.path)` — a containment check that only prevents the target from resolving *outside* the repository directory — then unconditionally `writeFile`s the model-supplied content to that path and stages it with `git add`. [1](#0-0) 

There is no cross-check that `resolution.path` is a member of `copilotResolutions`' originating `conflictedFiles` list (the set actually gathered by `gatherConflictResolutionContext`/`getConflictedFiles`). The only path-existence lookup performed (`state.changesState.workingDirectory.files.find(...)`) is used purely to detect if the user already resolved the conflict externally — not to restrict which paths may be written. [6](#0-5) 

Since the untrusted merge/PR content (attacker-controlled branch text, commit messages, or PR body) is fed verbatim into the model prompt, a prompt-injection payload embedded in that content could instruct the model to emit a `resolutions` entry whose `path` names an unrelated tracked file elsewhere in the same repository (e.g. `package.json`, a CI workflow file, or an npm/build config), with attacker-chosen `resolvedContent`. Because the path-containment check only prevents escaping the repo root — not restricting to the original conflict set — this file would be silently overwritten and staged for the user's next commit/push.

### Impact Explanation
This breaks the invariant that Copilot-assisted merge resolution only touches files that actually have merge conflicts. An attacker who controls one side of a merge (a malicious feature branch, a crafted PR title/description, or manipulated commit messages) can achieve a targeted, silent corruption of what the victim commits/pushes to files far outside the conflicted set — e.g., altering build/CI configuration, dependency manifests, or application logic — without the victim reviewing the change as part of the visible conflict diff. This matches the report's "unprivileged, silent corruption of what the user commits or pushes" impact category. It does not require local access, admin rights, or leaked credentials — only that the victim performs a normal merge/rebase/cherry-pick against attacker-supplied content and accepts the Copilot resolution.

### Likelihood Explanation
Exploitation requires: (1) the attacker's content to reach the model prompt (achievable by opening a PR with a crafted title/description/commit messages against a branch the victim will merge, or via a shared branch), (2) a successful prompt injection causing the model to emit a spurious `resolutions` entry for a non-conflicted path, and (3) the victim clicking "Continue Merge" in the Copilot dialog without inspecting every returned file. Model behavior against adversarial prompts is not deterministic, so likelihood is moderate rather than guaranteed, but the missing server/client-side allow-list check (constraining `resolution.path` to the actual conflicted set) removes what should be a hard technical backstop, similar to how skipping the boolean return check on `transfer`/`transferFrom` removed a hard backstop against fee-on-transfer/false-return tokens in the original report.

### Recommendation
In `_applyCopilotConflictResolutions`, before writing, validate that `resolution.path` is contained in the set of paths gathered as `conflictedFiles` for this operation (or equivalently, that `state.changesState.workingDirectory.files` contains that path AND it is currently in a conflicted state). Reject/skip and log any resolution whose path is not part of the original conflict set, the same way out-of-repo paths are already rejected via `resolveWithin`.

### Proof of Concept
Not independently executed (would require a live Copilot model call); the path is demonstrated structurally:
1. Victim merges a branch containing a crafted PR description / conflicting file content designed to prompt-inject the model, per the system prompt fields consumed in `formatConflictContextForPrompt`. [7](#0-6) 
2. The injected instruction causes the model's JSON response to include an extra `resolutions[]` entry with `"path": "package.json"` (or any other tracked, non-conflicted file) and attacker-chosen `resolvedContent`.
3. `parseCopilotConflictResolution` accepts this entry because it only checks `path` is a non-empty string. [8](#0-7) 
4. On "Continue Merge", `_applyCopilotConflictResolutions` writes and stages this file, since `resolveWithin` only confirms it is inside the repo, not that it belongs to the conflicted set. [1](#0-0) 

Note: I was unable to fully confirm whether the underlying model reliably resists this kind of injection given the "Respond ONLY with valid JSON" instruction — that mitigation is a soft (prompt-level) control, not a code-level allow-list, and is the crux of why this remains exploitable in principle even though I could not run the LLM to demonstrate a successful injection end-to-end.

    }
  }

/** Maximum number of characters of a PR body to include in the prompt. */
const MAX_PR_BODY_LENGTH = 4000

/** Append a single pull request's title and (truncated) body to the prompt. */
function appendPullRequest(
  parts: Array<string>,
  pr: IConflictContextPullRequest
): void {
  parts.push(`PR #${pr.number}: ${pr.title}`)
  if (pr.body) {
    parts.push('Description:')
    parts.push(makeFencedBlock(truncateBody(pr.body)))
  }
  parts.push('')
}

/** Truncate an over-long PR body so a single PR can't dominate the prompt. */
function truncateBody(body: string): string {
  if (body.length <= MAX_PR_BODY_LENGTH) {
    return body
  }
  return `${body.slice(0, MAX_PR_BODY_LENGTH)}\n…(truncated)`
}
