### Title
Unvalidated `x-github-enterprise-version` header cached indefinitely disables repo-rule client-side enforcement checks - ([File: app/src/lib/endpoint-capabilities.ts])

### Summary
`tryUpdateEndpointVersionFromResponse` reads the `x-github-enterprise-version` HTTP response header from every authenticated API response and persists it into `localStorage`/`versionCache` with no validation of source, no signature/authenticity check, and no expiry — the cached value is trusted forever until a different value is seen again. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`getEndpointVersion` returns whatever was last cached (in-memory `versionCache` or `localStorage`) with no timestamp/staleness check at all — analogous to `PricerInternal._latestAnswer64x64` returning `latestRoundData()` without checking `updatedAt`. [4](#0-3) 

This cached version feeds `endpointSatisfies`/`supportsRepoRules`, which is a purely client-side capability gate used by `useRepoRulesLogic` to decide whether GitHub Desktop should even attempt to fetch and enforce repo rules (required signatures, required status checks, protected branch name patterns, etc.) before letting the user commit/push: [5](#0-4) 

The header is written on every `ghRequest` (any authenticated GitHub Enterprise Server API call), including low-trust responses such as OAuth token exchange: [6](#0-5) [7](#0-6) 

Because the value is trusted with no freshness/consistency validation and survives across app restarts via `localStorage`, a single malicious response (from a compromised or MITM'd corporate proxy sitting in front of a GHES instance — squarely within the "attacker controls...a git remote/proxy response" impact category) can poison the cache with a version string below the version gate used by `supportsRepoRules` (`es: '>= X.Y.Z'` in `endpointSatisfies`), and that poisoned value persists for all future sessions until another (possibly also spoofed) header overwrites it.

### Impact Explanation
Once `supportsRepoRules(endpoint)` returns `false` due to the spoofed/older version, `useRepoRulesLogic` short-circuits and Desktop never calls `fetchRepoRulesForBranch`/`parseRepoRules`, silently suppressing the "commit signing required," "basic commit warning," and "branch name pattern" UI checks in the commit box: [8](#0-7) 

This matches the report's "silent corruption of what the user commits or pushes" criterion: the user loses the local warning that a rule (e.g., required signed commits, restricted branch names) would fail server-side, and may unknowingly attempt operations they believe are safe, or be misled about bypass status. The server still ultimately enforces the actual push, so this is a UI-trust/downgrade issue rather than remote code execution, bounding the severity to a client-side security-control bypass (misleading trust indicator) rather than a critical vulnerability.

### Likelihood Explanation
Exploitation requires an attacker who can tamper with HTTP responses between Desktop and a self-hosted GHES instance (e.g., a compromised corporate TLS-terminating proxy or a GHES appliance under attacker influence) — a scenario already implicitly trusted in enterprise deployments, similar to how the oracle stale-price issue only requires the price feed operator/relayer to be slow or malicious, not a full compromise of the chain. No user interaction beyond normal Desktop use against that endpoint is required, and the corruption persists indefinitely (`localStorage`), amplifying a single spoofed response into a long-lived downgrade.

### Recommendation
- Do not treat `x-github-enterprise-version` as an unconditionally trusted, indefinitely-cached value; associate a fetch timestamp with `updateEndpointVersion`/`versionCache` entries and require re-validation (e.g., re-confirm on a fresh request within some max-age) similar to `entryIsEligibleForRefresh` in `commit-status-store.ts`.
- Only update the version cache from responses to endpoints/hosts already established as trusted (e.g., the sign-in flow) rather than every authenticated request, and prefer a dedicated, authenticated "meta"/version endpoint over an arbitrary response header.
- Consider treating an unexpected version downgrade (e.g., version reported lower than a previously-seen higher version) as suspicious and re-verifying rather than immediately trusting it.

### Proof of Concept
1. Point GitHub Desktop at a GitHub Enterprise Server endpoint reached through an attacker-controlled or MITM'd proxy.
2. On any authenticated API call (or during the OAuth token exchange, `requestOAuthToken`), have the proxy inject `x-github-enterprise-version: 3.0.0` (below the `>= X.Y.Z` constraint required by `supportsRepoRules`).
3. `tryUpdateEndpointVersionFromResponse` calls `updateEndpointVersion`, which writes this value to `localStorage` and `versionCache` with no expiry.
4. `useRepoRulesLogic` subsequently calls `supportsRepoRules(endpoint)`, which returns `false` because of the poisoned cached version, so `parseRepoRules` is never invoked and the commit message box in `commit-message.tsx` shows no warning about required signed commits / restricted branch names / other repo rules, even though the real GHES server enforces a newer version's rules.
5. The poisoned entry persists across app restarts until another response (potentially also attacker-controlled) updates it. [9](#0-8)

export function getEndpointVersion(endpoint: string) {
  const key = endpointVersionKey(endpoint)
  const cached = versionCache.get(key)

  if (cached !== undefined) {
    return cached
  }

  const raw = localStorage.getItem(key)
  const parsed = raw === null ? null : semver.parse(raw)

  if (parsed !== null) {
    versionCache.set(key, parsed)
  }

  return parsed
}

export function updateEndpointVersion(endpoint: string, version: string) {
  const key = endpointVersionKey(endpoint)

  if (rawVersionCache.get(key) !== version) {
    const parsed = semver.parse(version)
    localStorage.setItem(key, version)
    rawVersionCache.set(key, version)
    versionCache.set(key, parsed)
  }
}

export function useRepoRulesLogic(
  account: Account | null,
  repository: Repository
): boolean {
  if (
    !account ||
    !repository ||
    !isRepositoryWithGitHubRepository(repository)
  ) {
    return false
  }

  const { endpoint, owner, isPrivate } = repository.gitHubRepository

  if (!supportsRepoRules(endpoint)) {
    return false
  }

  // repo owner's plan can't be checked, only the current user's. purposely return true
  // if the repo owner is someone else, because if the current user is a collaborator on
  // the free plan but the owner is a pro member, then repo rules could still be enabled.
  // errors will be thrown by the API in this case, but there's no way to preemptively
  // check for that.
  if (
    account.login === owner.login &&
    (!account.plan || account.plan === 'free') &&
    isPrivate
  ) {
    return false
  }

  return true
}
