### Title
Partial-commit line selection is re-applied against a re-fetched diff at staging time, allowing silent commit content corruption - ([File: app/src/lib/git/apply.ts])

### Summary
The Dutch-auction report's broken invariant is: a value the user visually reviewed and committed to (a bid amount) is silently re-evaluated against updated on-chain state at execution time, because the check (review) and the use (execution) are decoupled and nothing pins the action to the reviewed state. Reducing this to Desktop's domain: a user reviews a diff, hand-selects individual lines/hunks to include in a commit (a `DiffSelection` keyed by *line index*, not by line content), and clicks Commit. The actual patch used to stage those lines is **not** the diff the user looked at — it is a brand-new diff fetched from disk at staging time, `applyPatchToIndex` -> `getWorkingDirectoryDiff`, and the old line-index selection is blindly replayed against it.

### Finding Description
`_commitIncludedChanges` in [1](#0-0)  takes `selectedFiles` — `WorkingDirectoryFileChange` objects carrying a `DiffSelection` built from line indices computed against whatever diff was rendered in the UI at selection time — straight from cached state, with no re-check against current disk content, and passes them into `createCommit`.

`createCommit` in [2](#0-1)  immediately calls `stageFiles`, which for any partially-selected file calls `applyPatchToIndex`. That function fetches a **fresh** diff at that exact moment: [3](#0-2) . `formatPatch` then walks this new diff's hunks and asks `file.selection.isSelected(absoluteIndex)` [4](#0-3)  — a pure integer/line-index lookup with no content binding, as shown by `DiffSelection.isSelected` [5](#0-4) .

Because `DiffSelection` is indexed purely by absolute line position, if the on-disk file changes between the moment the user made their partial selection (reviewing hunk A) and the moment `stageFiles`/`applyPatchToIndex` runs (fetching hunk A′, with shifted/renumbered lines because content was appended, reformatted, or reflowed), the same numeric indices now point at different lines. `formatPatch` will silently include whatever lines happen to occupy those indices in the new diff — not the content the user visually approved — and stage/commit it without any warning, error, or diff re-confirmation.

Existing guards do not close this gap:
- `updateChangesWorkingDirectoryDiff` in `app-store.ts` does re-check staleness, but only to protect the **rendering** of the diff panel (it discards a stale diff and re-renders): [6](#0-5) . It never re-validates the `DiffSelection` object itself, nor blocks commit if the underlying diff shape has changed since the selection was made.
- `_commitIncludedChanges` performs no comparison between the diff that produced the current `selection` and the diff `applyPatchToIndex` will fetch moments later.
- Nothing in `stageFiles` [7](#0-6)  validates that the file's on-disk hash/mtime matches what was true when the selection was constructed.

### Impact Explanation
This is silent corruption of what the user commits, matching the in-scope impact category directly. A cloned/opened repository that ships a normal, unprompted background process — e.g. an npm `watch`/`dev` script, a file-watching formatter, or a `core.hooksPath`-configured hook that rewrites tracked files as part of the repo's documented workflow — can shift line offsets in a file the user is mid-review on. When the user then commits their carefully chosen partial hunk selection, Desktop will stage and commit whatever content now occupies those numeric line positions instead of what was shown and approved, without any error or re-confirmation. This can be used to smuggle attacker-authored lines into a commit the user believes only contains their reviewed subset, or to drop lines the user intended to include — a "frontrunning" of the commit's content in exact analogy to the DeFi bug's frontrunning of the bid amount.

### Likelihood Explanation
Moderate. It requires: (1) a repository whose normal, documented workflow includes an auto-running file-mutating process (very common for JS/web repos — watch/build/format-on-save tooling), and (2) the user performing a partial (hunk/line-level) commit selection rather than "select all," and (3) a window of time between making the selection and clicking Commit during which the watcher fires. Partial commits are a widely used, first-class Desktop feature, and dev-server/watch scripts are ubiquitous in real-world repos, so the preconditions are realistic without requiring local/physical access, admin rights, prior malware, or leaked credentials.

### Recommendation
Bind the `DiffSelection` to the diff it was computed from (e.g., by hashing/fingerprinting the diff or file content) and re-validate at staging time in `applyPatchToIndex`/`_commitIncludedChanges`: if the freshly fetched diff differs from the one the selection was derived from, abort the commit for that file and force the user to re-review and re-select, rather than silently replaying old line indices against new content.

### Proof of Concept
Not independently executable from static review alone (requires a live filesystem race), but the code path is fully traceable:
1. Open a repo with partial-commit UX; select specific lines/hunks of `file.md` for inclusion (creates a `DiffSelection` with divergent line indices captured against diff snapshot D1).
2. Before clicking "Commit," let an external process (e.g., `npm run watch`, a formatter-on-save, or a repo-configured `core.hooksPath` script) rewrite `file.md`, shifting line numbers (diff snapshot D2).
3. Click "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches D2 fresh (`app/src/lib/git/apply.ts:60`) and calls `formatPatch(file, D2)`, which applies the D1-derived `DiffSelection.isSelected(absoluteIndex)` to D2's hunks (`app/src/lib/patch-formatter.ts:143-157`).
4. The resulting commit contains whichever lines sit at those indices in D2, not the lines the user actually reviewed and checked in D1 — no error is raised, and the discrepancy is invisible to the user post-commit. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
