### Title
Dust-forgiveness threshold in `_calExpireForfeit` can be gamed by claiming in small increments, letting cooling-down lockers evade forfeiture entirely - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder._sendReward` computes the forfeited (penalty) portion of a claim only on the reward fragment accrued since the caller's *last checkpoint*, and forgives that forfeit entirely if it is smaller than `amount/1000`. Because `getReward` can be called repeatedly (via `MasterMagpie.claim`) and each call both resets `userRewards` and advances the checkpoint, a user in cooldown can fragment their claims across many small reward-accrual increments so that every individual forfeit calculation rounds down to zero, while the same cumulative reward claimed in one lump sum would incur a proportional, non-zero forfeit.

### Finding Description
`getReward` is guarded only by `onlyMasterMagpie` and the `updateReward(_account)` modifier [1](#0-0) . The modifier calls `_updateFor`, which recomputes `userRewards[rewardToken][_account]` as the delta accrued since the account's last recorded `userRewardPerTokenPaid` checkpoint, and immediately advances that checkpoint to the current `rewardPerToken` [2](#0-1) .

`_sendReward` then computes the forfeiture strictly on that current `userRewards` value (i.e., the fragment since the last claim), not on the account's cumulative earned rewards for the whole cooldown/unlocking period: [3](#0-2) 

`_calExpireForfeit` applies the "ignore dust" rule per call: [4](#0-3) 

Since `userRewards` is zeroed after every send and the checkpoint moves forward each time, calling `getReward` immediately after each small `rewardPerTokenStored` increase (from `queueNewRewards` / `_queueNewRewardsWithoutTransfer`) presents `_sendReward` with a tiny fragment each time. If `fragment * (1 - rewardablePercentWAD)/1e18 < fragment/1000` for every fragment, the forfeit is forced to zero on every single call — even though the same total amount claimed as one lump sum at the end of the cooldown period would have a forfeit computed against the full total, which is far more likely to exceed the 0.1% floor and thus be enforced. No modifier, cooldown-state check, or per-period claim limiter exists to prevent split claiming; `nonReentrant` is not even applied to `getReward` (only `getRewards` has it), and there is no minimum-interval or maximum-claims-per-period restriction anywhere in `MasterMagpie.claim`/`vlMGPBaseRewarder`.

### Impact Explanation
This is a theft of unclaimed yield: forfeited amounts are meant to be re-queued as rewards for other (non-cooling-down) lockers via `_queueNewRewardsWithoutTransfer`, which increases `rewardPerTokenStored` for the whole pool [5](#0-4) . By systematically avoiding forfeiture through claim-fragmentation, a cooling-down attacker keeps yield that should have been redistributed to other lockers, permanently denying that yield to the pool. This matches the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
Preconditions are modest and attacker-only: the account must have a partial `rewardablePercentWAD` (i.e., an active cooldown/unlocking slot, which is a normal, permissionless user action via `startUnlock`), and the attacker must call `getReward`/`claim` opportunistically and often. No special privileges, capital, or flash loans are needed — just repeated self-serve claim transactions, which is realistic whenever reward top-ups (`queueNewRewards`) arrive in many small increments over the cooldown duration (e.g., periodic harvests/bribes), a normal and expected operational pattern rather than an edge case.

### Recommendation
Compute and enforce the forfeit against the account's cumulative unclaimed reward accrued since it entered cooldown (or apply the dust-forgiveness threshold against a period-total/floor amount rather than the per-call fragment), so that splitting claims into many small transactions cannot reduce total forfeiture below what a single lump-sum claim would produce. Alternatively, remove the relative (`amount/1000`) dust-forgiveness rule in favor of an absolute minimum-dust cutoff independent of the claimed fragment size, and/or checkpoint forfeiture obligations at cooldown-slot creation rather than at each claim.

### Proof of Concept
Foundry test plan:
1. Set up `vlMGPBaseRewarder` with `vlMGP` mock returning `rewardablePercentWAD = 50%` for the test account (simulating mid-cooldown).
2. Scenario A (lump sum): Queue a single large reward amount `R` via `queueNewRewards`, then call `getReward` once. Assert `forfeitAmount ≈ R * 50%` is queued back via `ForfeitRewardAdded`.
3. Scenario B (fragmented): Queue the same total `R` split across N small `queueNewRewards` calls (e.g., N=100, each `R/100`), calling `getReward` immediately after each top-up. Assert that each call's `_calExpireForfeit` returns 0 (because `fragment/1000` floor rounds the 50% forfeit down to 0 for small enough fragments), and that the cumulative forfeited amount across all N calls is materially less than in Scenario A (ideally 0 vs. `R*50%`).
4. Assert the attacker's total received tokens in Scenario B exceed Scenario A by the avoided forfeit amount, demonstrating the conservation-of-forfeiture invariant is broken.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```
