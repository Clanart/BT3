### Title
Tron port of `IntentGatewayV2` lacks the reentrancy guard that protects the canonical EVM contract, reopening the fixed fill/escrow-theft class - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) inherits `ReentrancyGuardTransient` and guards `fillOrder`/`cancelOrder` with `nonReentrant`, on top of a CEI fix that sets `_filled[commitment] = msg.sender` *before* any external token transfer in `_fillSameChain`. This exact ordering was previously broken (fees/escrow could be stolen by a reentrant `fillOrder` call from a malicious beneficiary during the ETH/token payout), and the fix plus regression tests are checked into the repo. The Tron fork of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separately maintained, near-duplicate implementation that does **not** inherit `ReentrancyGuardTransient` and contains zero occurrences of `nonReentrant` anywhere in the file.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` declares: [1](#0-0) 
and its `fillOrder`/`cancelOrder` are both marked `nonReentrant`: [2](#0-1) [3](#0-2) 

The `_fillSameChain` implementation sets `_filled[commitment] = msg.sender` as the very first state write, before any beneficiary payout: [4](#0-3) 

The repo's own regression test file documents that this was a real, previously-exploitable bug (fee theft and multi-output escrow theft via a malicious beneficiary contract reentering `fillOrder` from inside the ETH `.call` payout), and that the CEI ordering plus `nonReentrant` is what closes it: [5](#0-4) [6](#0-5) 

The Tron contract, however, is declared as: [7](#0-6) 
`HyperApp, EIP712` only — no `ReentrancyGuardTransient`, no `IntrinsicIntents`/`ExtrinsicIntents` composition, and a grep for `nonReentrant` across this file returns zero matches, confirming the guard is absent from every state-changing entrypoint (`placeOrder`, `fillOrder`, `cancelOrder`). The Tron file also drives the same `CallDispatcher.dispatch()` pattern for predispatch/postdispatch calldata — `dispatch()` itself has no reentrancy protection or access control: [8](#0-7) 

This reproduces the report's core primitive: execution flow reaching an address that can call back into `execute()`/`fillOrder()` mid-flow. On Tron, that "malicious address" can be reached the same way the report describes — a hook-bearing token (Tron's TRC-20/TRC-777-equivalent tokens with transfer hooks are common), a solver-controlled `beneficiary`, or a postdispatch `Call.to` target — reentering `fillOrder`/`placeOrder` while the outer call's escrow/`_filled` bookkeeping is still in a pre-commit state, with no `nonReentrant` modifier anywhere in the call chain to stop it.

### Impact Explanation
If the same-chain fill path in the Tron contract mirrors the pre-fix ordering (payout before `_filled` is durably committed, or before partial-fill/escrow bookkeeping is finalized) — which I could not fully verify line-by-line for this fork within the remaining tool budget — a malicious beneficiary or postdispatch call target can reenter and duplicate escrow releases or drain the transaction-fee/escrow token exactly as described in the fixed EVM test cases (`testReentrancy_FeeTheft`, `testReentrancy_EscrowTheft_MultiOutput`). This is a direct "loss of escrowed/bridged funds" and "double-settlement" outcome matching the bounty's impact gate, reachable by any unprivileged user who places or fills an order with a hook/callback-capable token or contract, with no relayer, prover, or admin involvement required.

### Likelihood Explanation
Medium-to-High for reachability (any user can trigger the flow with an ordinary TRC-20-style token that supports a transfer callback, or by acting as their own solver/beneficiary contract), but the actual exploitability depends on whether the Tron fork's `_filled`/escrow bookkeeping is written before or after the external payout call — a detail in the fill functions of this specific file that I was not able to inspect before exhausting my tool-call budget. The confirmed fact is that the structural mitigation (`ReentrancyGuardTransient`/`nonReentrant`) present in the canonical contract is absent here, which removes the safety net even if the CEI ordering happens to be correct in this copy.

### Recommendation
- Add `ReentrancyGuardTransient` (or an equivalent `nonReentrant` guard) to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, `fillOrder`, and `cancelOrder`, matching the canonical EVM contract.
- Audit and, if necessary, reorder the Tron fill/withdraw functions so `_filled[commitment]` (and any partial-fill accounting) is written before any external token transfer or native-token `.call`, mirroring the CEI fix already applied to `IntrinsicIntents._fillSameChain`.
- Since `CallDispatcher.dispatch()` itself has no reentrancy guard, consider adding one there as defense-in-depth, since it is a shared, unauthenticated entrypoint used by multiple apps (`IntentGatewayV2`, `HyperFungibleToken`).
- Add the same reentrancy regression test suite (`IntrinsicIntentsReentrancyTest.sol`) against the Tron build target to close this gap with CI coverage.

### Proof of Concept
Not independently reproduced against the Tron fill functions due to tool-call exhaustion; the verifiable evidence is:
1. `evm/src/apps/IntentGatewayV2.sol:61` inherits `ReentrancyGuardTransient`; `evm/tron/contracts/apps/IntentGatewayV2.sol:55` does not.
2. A file-wide search for `nonReentrant` in `evm/tron/contracts/apps/IntentGatewayV2.sol` returns no matches.
3. The existing test suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) proves the exact same reentrancy class was previously exploitable on the canonical contract absent this guard/ordering, using a `ReentrantBeneficiary` contract that re-enters `fillOrder` from `receive()` during the ETH payout — the same PoC pattern would need to be run against the Tron contract's fill path to confirm live exploitability there.
