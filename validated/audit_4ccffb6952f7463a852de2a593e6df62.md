### Title
Reward-sniping via front-running `queueNewRewards`/`donateRewards` with instant deposit/withdraw - ([File: rewards/BaseRewardPool.sol / BaseRewardPoolV2.sol])

### Summary
`BaseRewardPool`/`BaseRewardPoolV2._provisionReward` bakes an entire reward donation into `rewardPerTokenStored` in a single lump sum, weighted only by `totalStaked()` at the exact block the donation lands, with no time-based streaming (no `periodFinish`/`rewardRate` vesting). Because `MasterMagpie.deposit`/`withdraw` have no cooldown or lock-up, an attacker can deposit a large stake one block before a manager's `queueNewRewards` (or anyone's `donateRewards`) call and withdraw immediately after, capturing a pro-rata share of the reward despite having zero time-weighted exposure.

### Finding Description
`_provisionReward` in [1](#0-0)  updates `rewardInfo.rewardPerTokenStored` instantly as `_amountReward * 10**decimals / totalStaked()`, where `totalStaked()` is the live balance in `MasterMagpie` at that instant [2](#0-1) . This is not a Synthetix-style streamed reward (no `rewardRate`/`periodFinish` accrual over time); the whole donation is priced-in at the moment `queueNewRewards`/`donateRewards` executes.

`MasterMagpie.deposit`/`withdraw` (`_deposit`/`_withdraw`) impose no minimum holding period, cooldown, or vesting [3](#0-2) . A user's `balanceOf` (used both for `totalStaked()`'s denominator context and for the user's own earned-reward numerator via `_earned`) is simply their currently deposited amount [4](#0-3) .

Exploit flow:
1. Attacker observes a pending `queueNewRewards(amount, token)` tx (mempool) from the reward manager, or simply front-runs any permissionless `donateRewards` call.
2. Attacker calls `MasterMagpie.deposit(_stakingToken, largeAmount)` in the preceding block, inflating `totalStaked()`.
3. The reward-injection tx executes; `rewardPerTokenStored` is incremented once, split across `totalStaked()` including attacker's freshly added stake — attacker is instantly credited `userRewards` proportional to their share despite 0 blocks of prior exposure (`_updateFor`/`updateReward` modifier snapshots `rewardPerToken` per account on the next interaction) [5](#0-4) .
4. Attacker calls `MasterMagpie.withdraw(_stakingToken, largeAmount)`, which triggers `_harvestAndUnstake` → `_harvestBaseRewarder` → `getReward`, paying out the reward immediately, then removes the stake in the same or next block [6](#0-5) .

No modifier (`onlyManager`, `nonReentrant`, `whenNotPaused`) prevents this because it is not a reentrancy or access-control issue — it's a legitimate sequential call from an unprivileged depositor exploiting the lack of time-weighting in reward accounting.

### Impact Explanation
This is theft of unclaimed yield from long-term stakers. Long-term stakers who held their position throughout the accrual period have their share of `rewardPerTokenStored` diluted by an attacker's transient, single-block stake, transferring value that should have accrued to them into the attacker's pocket. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Feasibility is high: the attacker only needs (a) enough of the staking token (which may be obtainable via flash loan or simply purchased/borrowed, since staking tokens are typically LP/receipt tokens or MGP-related tokens, not permissioned), and (b) visibility into the mempool to front-run `queueNewRewards`, or can act opportunistically whenever any address calls the permissionless `donateRewards`. The attack is repeatable every time a reward injection occurs and scales with the attacker's flash-available capital relative to existing `totalStaked()`.

### Recommendation
Convert reward distribution to a time-weighted streaming model (e.g., Synthetix-style `rewardRate`/`periodFinish` accrued per second) instead of an instantaneous lump-sum split by `totalStaked()` at the injection block. Alternatively, introduce a minimum stake duration/cooldown before a deposit is eligible to receive freshly queued rewards, or snapshot eligible stake prior to the donation block.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool`, staking token, and reward token; register a manager.
2. Have "Alice" (long-term staker) deposit `X` staking tokens and let several blocks pass with no other activity.
3. In block `N`, have "Attacker" call `MasterMagpie.deposit(stakingToken, Y)` with `Y >> X`.
4. In block `N+1` (or same block if manager's tx is in mempool), manager calls `queueNewRewards(amountReward, rewardToken)` (or an altruistic third party calls `donateRewards`).
5. In block `N+2`, Attacker calls `MasterMagpie.withdraw(stakingToken, Y)`, triggering `getReward` and receiving `amountReward * Y / (X+Y)`.
6. Assert Attacker's received reward / time-weighted stake (0 or 1 block) vastly exceeds Alice's received reward / her multi-block time-weighted stake, i.e., compare `attackerReward / instantaneousStakeShare` (≈1) against `attackerReward / (Y * 1 block) / totalStakeSeconds` to demonstrate reward capture disproportionate to actual staking duration, while Alice's realizable share of the same donation shrank from `amountReward` (if she were alone) to `amountReward * X/(X+Y)`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
