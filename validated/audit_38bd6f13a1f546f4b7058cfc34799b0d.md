## Title
Hookify PreToolUse guardrails fail-open for any tool outside a hardcoded allowlist, letting dangerous operations bypass user-defined block rules - (File: `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/core/rule_engine.py`)

### Summary
The `hookify` plugin's `PreToolUse` guard mirrors the `app-vault-clear-state.teal` flaw: instead of validating that a tool invocation falls under one of a small, explicitly-safe set and denying everything else by default, it only special-cases a hardcoded list of tool names (`Bash`, `Write`, `Edit`, `MultiEdit`) and silently treats every other tool as if no rule condition applies, letting the operation through unchecked regardless of the user's configured `block` rules.

### Finding Description
`pretooluse.py` derives an `event` label purely from a hardcoded tool-name check: [1](#0-0) 

That `event` is passed to `load_rules()`, but the actual enforcement gap is deeper: `RuleEngine._extract_field()` only knows how to pull the field value (`command`, `content`, `new_text`, `file_path`, etc.) that a rule's `Condition` needs for `Bash`, `Write`/`Edit`, and `MultiEdit`: [2](#0-1) 

Any tool outside that enumerated set (e.g. `NotebookEdit`, `Task`/subagent invocation, `WebFetch`, `WebSearch`, or any `mcp__*` tool that can run commands, write files, or fetch external content) causes `_extract_field` to fall through to `return None`. Back in `_check_condition`, a `None` field value immediately short-circuits the match to `False`: [3](#0-2) 

Since `_rule_matches` requires **all** conditions to match, and `evaluate_rules` returns `{}` ("allow") whenever nothing matches: [4](#0-3) 

a `block`-action rule the user wrote specifically to stop a dangerous pattern (e.g. `rm -rf`, writing to `.env`, `eval(`) is completely inert for any equivalent dangerous action reachable via a tool not in the hardcoded set — the exact same "only two operations are checked, everything else defaults to valid" pattern as the vault report, just applied to Claude Code's own tool-permission enforcement layer instead of `OnCompletion`.

The plugin's own documentation advertises this hook as a general-purpose safety net (wildcard `tool_matcher: "*"`, `event: all`), reinforcing that users rely on it to cover arbitrary tools: [5](#0-4) 

but the concrete field-extraction logic never actually reaches parity with that promise.

### Impact Explanation
An agent (or a prompt-injected/compromised model turn) that is nominally blocked from an unsafe action via a hookify `block` rule (e.g. "never run `rm -rf`", "never write secrets to disk") can achieve the same effect by routing the operation through any tool outside `{Bash, Write, Edit, MultiEdit}` — for example issuing the destructive command via an MCP shell tool, or exfiltrating/overwriting sensitive content via `NotebookEdit` or a fetch/write-capable MCP tool. The user's configured guardrail silently does nothing (no warning, no block, no log) because the condition never even evaluates to a match, giving a false sense of protection. This is a hook-bypass / capability-gate trust-boundary issue: the model is the attacker, the user is the intended enforcer/victim, matching the class of "LLM-agent capability gates" explicitly called out as always in-scope in this repo's own security-review guidance.

### Likelihood Explanation
Difficulty is low: reaching an unenumerated tool only requires the model (potentially steered by an untrusted prompt/tool-result) to prefer a different, semantically equivalent tool for the same effect (e.g. an MCP filesystem/exec tool instead of `Write`/`Bash`), which is a normal and unremarkable choice an agent could make without any special exploit engineering. No privilege escalation beyond normal tool selection is needed, and the failure is silent, so it would likely go unnoticed by the user relying on the rule.

### Recommendation
- Short term: change `_extract_field`/`_rule_matches` to fail closed for unmatched tools when a rule's `tool_matcher` is `"*"` or when `event == "all"` — i.e., generically extract candidate string fields from `tool_input` (not just a hardcoded per-tool field list) so conditions can still evaluate against arbitrary tools, and treat "field not found for this tool type" as a signal to still run generic content-based conditions rather than silently returning `None`/no-match.
- Long term: document precisely which tools/fields the hook can inspect, add an explicit test matrix (as recommended in the original report) enumerating every tool type against every rule `event`/`field` combination, and consider warning the user when a configured rule's `field` can never be satisfied by any known tool, so misconfigured "protective" rules are surfaced rather than silently inert.

### Proof of Concept
1. User creates `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-dangerous-rm
enabled: true
event: bash
action: block
pattern: rm\s+-rf
---
Blocked dangerous rm command.
```
2. Confirm it works: asking Claude to run `Bash("rm -rf /tmp/x")` is blocked (`permissionDecision: deny`), per `rule_engine.py` lines 60-84.
3. Now have the model perform the equivalent destructive action through a tool not in `{Bash, Write, Edit, MultiEdit}` — e.g., an MCP server tool that executes shell commands, or `NotebookEdit` embedding a cell that runs `!rm -rf /tmp/x` when executed.
4. `pretooluse.py` sets `event = None` (or the field lookup in `_extract_field` returns `None` for that tool), `_check_condition` returns `False`, `_rule_matches` returns `False`, and `evaluate_rules` returns `{}` — the operation proceeds with no block and no warning, defeating the user's guardrail exactly as the vault contract's missing `OnCompletion` check let non-`OptIn`/`CloseOut` operations (like `UpdateApplication`) through unchecked.
