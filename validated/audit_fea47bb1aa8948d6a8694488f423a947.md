The original report's core issue is a **broken invariant**: a proposal/spec assumes a strict 1:1 mapping (`BIT`→`MNT`), but the implementation computes that mapping through disjoint logic (numerator/denominator constants) that isn't actually guaranteed to preserve it. The Desktop analog is the Copilot merge-conflict resolution pipeline, where the code *assumes* a strict 1:1, in-order correspondence between conflict hunks identified for the LLM and conflict hunks identified when splicing the LLM's answer back into the file on disk — but these two correspondences are computed by two independently-implemented parsers that can disagree on attacker-crafted/malformed conflict-marker content.

### Title
Divergent conflict-marker parsers in Copilot conflict resolution can misalign resolved hunks, silently corrupting committed file content - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
`extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts`) is used to enumerate conflict hunks and build the prompt sent to Copilot. `reassembleResolvedFile` (in `app/src/lib/copilot-conflict-resolution.ts`) later re-scans the same raw file text with its own, separately written marker-detection logic to splice the model's per-hunk answers back in. The two parsers are matched **purely by array order**, as the code itself documents: "matched by order, not by line number".

### Finding Description
`extractConflictHunks` uses a state machine that recognizes `<<<<<<<`, `|||||||`, `=======`, and `>>>>>>>` markers and, on encountering a malformed/unterminated block, keeps scanning forward until it finds the *next* relevant marker anywhere later in the file: [1](#0-0) 

`reassembleResolvedFile` independently re-implements this same marker matching with its own regexes and its own look-ahead loop, without any awareness of the `|||||||` base marker at all: [2](#0-1) [3](#0-2) 

Because both functions greedily "scan forward for the next marker" rather than validating that a hunk terminates before the next `<<<<<<<` begins, an adjacent malformed conflict block (e.g., a first block missing its `>>>>>>>` closing marker, immediately followed by a second, well-formed block) gets silently merged by both parsers into a single, garbled hunk — but there is no cross-check anywhere in the code path that guarantees `extractConflictHunks`'s hunk count/boundaries and `reassembleResolvedFile`'s hunk count/boundaries stay identical for all inputs, since they are two distinct implementations of the same informal grammar. The reassembly explicitly documents that it trusts positional order as the correlation mechanism: [4](#0-3) 

The only validation applied to the model's output is that a hunk's `resolvedContent` doesn't still contain literal `<<<<<<<`/`=======` markers — it never verifies that the number of hunks the model resolved matches the number of marker blocks `reassembleResolvedFile` will actually encounter on disk: [5](#0-4) 

### Impact Explanation
An attacker who controls one side of a merge (e.g., a malicious branch/PR the victim merges, or a crafted file containing embedded conflict-marker-like text — e.g. copy-pasted diff snippets, minified code, or a previous unresolved conflict left in a file) can cause `extractConflictHunks` and `reassembleResolvedFile` to disagree about hunk boundaries in the working file. Since the reassembly result — an entire file's content — is what `_applyCopilotConflictResolutions` writes to disk and stages for commit: [6](#0-5) 
a resolution intended for one small conflict can be spliced across two unrelated marker blocks, causing code the user never asked the model to touch to be silently replaced or dropped from the committed file — corruption of what the user actually commits/pushes, driven entirely by attacker-controlled repository content.

### Likelihood Explanation
This requires nothing beyond a normal git workflow: cloning/fetching/merging a repository containing a specially crafted file with conflict-marker-like content, then using the built-in "Resolve with Copilot" feature. No local/admin access, malware, or leaked credentials are needed — only that the victim's merge produces a conflict in an attacker-influenced file, which is a realistic scenario for any project accepting external branches/PRs.

### Recommendation
Do not rely on independently-implemented, order-only correlation between the hunk-extraction logic used for prompting and the hunk-splicing logic used for reassembly. Use a single shared parser/AST for conflict markers, and have `reassembleResolvedFile` validate that the number and boundaries of marker blocks it finds exactly matches the number of hunks originally sent to the model (e.g., by embedding a stable hunk index/anchor per block, or refusing to apply resolutions whose count doesn't match what `extractConflictHunks` reported for that file) before writing/staging any content.

### Proof of Concept
Given the following file content, both `extractConflictHunks` and `reassembleResolvedFile` merge two logically-separate conflicts into one:
```
<<<<<<< HEAD
ours1
=======
theirs1
<<<<<<< HEAD
ours2
=======
theirs2
>>>>>>> feature
```
`extractConflictHunks` returns a single hunk whose `theirsContent` is the garbled string `theirs1\n<<<<<<< HEAD\nours2\n=======\ntheirs2` (verified via the parsing logic at [7](#0-6) ), which is what gets sent to Copilot as "one" conflict. `reassembleResolvedFile` likewise treats lines 0–7 as a single marker block (per its look-ahead logic at [8](#0-7) ) and splices the model's single `resolvedContent` over both original conflicting regions at once, discarding whichever real content (ours2/theirs2) the model didn't choose to preserve — with no separate review or resolution ever presented for the second, distinct conflict.
