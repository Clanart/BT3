The strongest local analog to the "no L2 Sequencer down check" bug class is in `evm/src/utils/SimplexPaymaster.sol`, which relies on Chainlink `AggregatorV3Interface.latestRoundData()` for pricing gas payments but only performs a raw `updatedAt` staleness check — with no L2 sequencer-uptime check, exactly the missing control the external report describes.### Title
Missing L2 sequencer-uptime check lets `SimplexPaymaster` price gas off stale Chainlink data during/just-after a sequencer outage, causing fund loss to the treasury/protocol - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster.sol` is a permissionless ERC-4337 paymaster deployed across Hyperbridge-supported EVM chains (including Optimism/Arbitrum-style rollups per `sdk/packages/indexer/src/addresses/chainlink-price-feeds.addresses.ts`) that prices ERC-20 gas payments purely from Chainlink `AggregatorV3Interface.latestRoundData()` feeds. Its only freshness guard is a raw `updatedAt` age check (`_getOraclePrice`). It never consults a Chainlink L2 sequencer-uptime feed, so an unprivileged UserOp submitted during, or in the grace window right after, a sequencer outage can settle gas payment against a price that is stale relative to the market but not stale enough to trip `maxOracleAge`.

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` is the sole gate on oracle data used for every gas-payment calculation: [1](#0-0) 

It checks only:
1. `answer > 0`
2. `block.timestamp - updatedAt <= maxOracleAge`

Both `_tokenPrice` (used in `_fetchDetails`, which sets the `tokenPrice` charged to every UserOp sender) and `swapAndDeposit` (which derives `amountOutMin` for treasury swaps) call `_getOraclePrice` for both the native/USD and token/USD legs: [2](#0-1) [3](#0-2) 

On Arbitrum/Optimism-style rollups, when the sequencer goes down, new L2 blocks stop being produced, so on-chain `updatedAt` timestamps for Chainlink feeds also stop advancing — but `block.timestamp` on the L2 can jump discontinuously once the sequencer resumes (or transactions can be force-included through the L1 inbox during the outage). This is precisely the attack Chainlink's `L2SequencerUptimeFeed` was designed to close: a transaction landing in this window can see a price that is stale relative to real market movement yet still satisfies `block.timestamp - updatedAt <= maxOracleAge`, because the `updatedAt` window computation doesn't account for how long the *sequencer* itself was unable to relay updates versus how long the feed value has actually been accurate.

`maxOracleAge` is governance-configurable up to `MAX_ORACLE_AGE = 7 days`: [4](#0-3) 

Any chain configured with a multi-hour/day `maxOracleAge` (as the code comment itself notes some price feeds legitimately have 24h heartbeats) provides a wide window in which an attacker can submit a UserOp that is force-included or queued to execute right as the sequencer resumes, paying gas in a stablecoin at a native/USD or token/USD rate that no longer reflects the real market, draining value from the paymaster/treasury (or conversely underpaying, at the treasury's expense) with no relayer, prover, or admin collusion required — only submission timing around a sequencer outage.

### Impact Explanation
This directly maps to "stealing or loss of funds" and "logic attacks" under the impact gate: the paymaster's ERC-20↔native pricing engine, which gates real fund transfers (ERC-20 `transferFrom` from the UserOp sender, and EntryPoint deposit/swap flows), can be manipulated into using inaccurate pricing without breaking any of its stated invariants (`answer > 0`, `age <= maxOracleAge`). Because `SimplexPaymaster` is explicitly documented to support "any token with a Chainlink feed" across multiple chains, and Chainlink's own documentation flags this as the standard L2 attack vector its sequencer-uptime feed exists to prevent, this is a concrete, locally provable gap rather than a generic oracle complaint.

### Likelihood Explanation
No malicious relayer, prover, governance actor, or leaked key is needed — any unprivileged user can time a UserOp (or use force-inclusion via the L1 inbox on Arbitrum/Optimism) around a sequencer outage or resumption. Sequencer downtimes on major rollups are infrequent but have occurred multiple times historically, and the exposure window scales with the configured `maxOracleAge`, which can be as long as 7 days.

### Recommendation
Add a Chainlink `L2SequencerUptimeFeed` (or chain-appropriate equivalent) check in `_getOraclePrice`/`_tokenPrice`: revert if the sequencer is currently reported down, and additionally enforce a grace period (e.g., Chainlink's recommended ~1 hour) after it comes back up before trusting any price feed reads, mirroring the mitigation pattern from Chainlink's official L2 data-feed documentation referenced in the external report.

### Proof of Concept
1. Governance registers `SimplexPaymaster` on an Arbitrum/Optimism-style chain with `maxOracleAge` set to several hours (a legitimate value per the code's own comment on BSC/Base heartbeats).
2. The chain's sequencer goes offline; Chainlink feed `updatedAt` values stop advancing while the real market price of the native asset or the registered token moves significantly.
3. During the outage (or immediately after resumption, before the feed catches up), an attacker submits a UserOp via `_validatePaymasterUserOp`/`_fetchDetails`, which calls `_tokenPrice` → `_getOraclePrice`: [5](#0-4) 
4. `block.timestamp - updatedAt` is still `<= maxOracleAge`, so `_getOraclePrice` returns the stale (now market-inaccurate) price and `_tokenPrice` computes `tokenPrice` from it.
5. `PaymasterERC20._erc20Cost` charges the UserOp sender based on this stale `tokenPrice`, transferring an incorrect (attacker-favorable or treasury-favorable) amount of ERC-20 tokens relative to actual gas cost, with no revert and no sequencer-status check anywhere in the call path.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
