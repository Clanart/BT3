### Title
`Precisions` decimal-scaling invariant is checked once at registration but decimals are read live, letting a post-registration decimals change on the local asset mint/refund inflated amounts - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `hyper-fungible-token` pallet enforces `erc_decimals >= local_decimals` only inside `register_token`/`update_token`, at the moment a chain is added. `send`, `on_accept` and `on_timeout` all re-read the *live* local asset decimals via `fungibles::metadata::Inspect` and combine them with the stored `Precisions` value using `convert_to_balance`/`convert_to_erc20`, both of which use `saturating_sub` on `(erc_decimals, local_decimals)`. If local decimals are later changed by the asset's admin so that `local_decimals > erc_decimals`, the subtraction saturates to `0`, the intended decimal-scaling divisor/multiplier collapses to `10^0 = 1`, and the bridge stops normalizing precision — directly mirroring the `TokenSaleETH.takeUSDBRaised()` bug where `unsoldTokens` silently ended up computed in the wrong decimal base.

### Finding Description
- `register_token`/`update_token` validate `config.decimals >= local_decimals` once, using the decimals observed **at registration time**: [1](#0-0) 
- `Precisions::<T>` stores only the remote ERC20 decimals; it never re-validates against the local asset's *current* decimals. [2](#0-1) 
- At `on_accept`/`on_timeout`, local decimals are fetched dynamically, not from a snapshot taken at registration, and combined with the stored `erc_decimals`: [3](#0-2) [4](#0-3) 
- The conversion helper uses `saturating_sub`, which silently drops the scaling exponent to zero instead of erroring when `local_decimals` exceeds `erc_decimals`: [5](#0-4) 

Because `local_decimals` is read live (not pinned at registration), any later increase of the local asset's `decimals` metadata (e.g. by the asset's `Admin`, which pallet-assets permits independently of this pallet's `CreateOrigin`) silently breaks the precision invariant the registration check was meant to guarantee. Once `local_decimals > erc_decimals`:
- `convert_to_balance` divides by `10^0 = 1` instead of the correct divisor, so `on_accept`/`on_timeout` credit/refund `10^(local_decimals - erc_decimals)` times more local tokens than the ERC20 amount actually represents.
- `convert_to_erc20` in `send()` similarly stops scaling up, sending an under-scaled amount to the remote EVM contract, breaking the 1:1 custody assumption between escrowed/burned local tokens and minted remote tokens.

This is the exact bug class from the report: a decimal-scaling formula that is correct only under an invariant (`erc_decimals >= local_decimals`) that is not actually maintained at the point of use, producing amounts off by a power of ten.

### Impact Explanation
An inflated `amount` minted or released from escrow in `on_accept`/`on_timeout` directly creates or unlocks tokens beyond what was legitimately locked/burned on the sending side — a fund-inflation/loss scenario matching the bounty's "stealing or loss of funds" and "false proof/state acceptance of amount" categories. Since custody parity between the two chains is a core security property of this bridging pallet (`README.md` describes escrow/mint-burn 1:1 custody), any drift lets an attacker who can move the local decimals (directly, or by choosing/registering an asset whose admin control is not the bridge's governance) redeem far more value than was ever bridged in.

### Likelihood Explanation
Triggering requires the local asset's metadata `decimals` to increase after `Precisions` was set. `register_token`/`update_token` are gated by `T::CreateOrigin` (bridge governance), but asset metadata `decimals` on `pallet-assets` is controlled by that specific asset's `Admin`, which is a separate, often non-privileged role tied to whoever created/owns the asset — not the bridge's own governance. There is no re-check of the invariant on the hot path (`send`/`on_accept`/`on_timeout`), and `saturating_sub` fails silently instead of erroring, so the condition is reachable without any relayer/prover compromise or Hyperbridge-governance action, only a change controlled by the underlying asset's admin key.

### Recommendation
- Do not read local decimals live from asset metadata at every dispatch/accept/timeout; snapshot and store the local decimals alongside `Precisions` at registration time so both sides of the ratio are pinned.
- Replace `saturating_sub` in `convert_to_balance`/`convert_to_erc20` with checked subtraction that returns an error (matching the existing `ErcDecimalsBelowLocal` error) instead of silently collapsing the scale factor to zero.
- Re-validate the `erc_decimals >= local_decimals` invariant defensively inside `send`/`on_accept`/`on_timeout`, not only at `register_token`/`update_token`.

### Proof of Concept
1. Governance registers asset `X` with `local_decimals = 6` and `erc_decimals = 18` (passes `ensure!(config.decimals >= local_decimals)`).
2. `Precisions::<T>::insert(X, chain, 18)` is stored.
3. Asset `X`'s `Admin` (a role independent of bridge governance) later calls `pallet-assets::set_metadata` to change `X`'s decimals to `20`.
4. A cross-chain `Send` message with `message.amount` denominated in 18-decimal ERC20 units arrives at `on_accept`.
5. `decimals = 20` (live), `erc_decimals = 18` (stored) ⇒ `erc_decimals.saturating_sub(local_decimals) = 0` in `convert_to_balance`, so `amount = value / 10^0 = value` — i.e., the full 18-decimal raw integer is minted as if it were already in 6-decimal-scale local units, crediting `10^14` times too many tokens to the beneficiary. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
