### Title
Missing Mandatory Caller Authentication on Operator `Withdraw` RPC Allows Any Network Peer to Trigger Payout Transactions — (`core/src/servers.rs`, `core/src/rpc/operator.rs`)

---

### Summary

The Operator gRPC server activates a `Noop` (no-op) interceptor when `client_verification=false`, stripping all mTLS certificate enforcement. Simultaneously, the `Withdraw` RPC handler applies its only remaining identity check — an ECDSA verification-signature comparison — only when `aggregator_verification_address` is configured, which is optional. When both guards are absent, any network-reachable entity can call `Withdraw` (and `InternalWithdraw`, which carries zero caller-identity check) on the operator and trigger a BTC payout transaction without aggregator authorization.

---

### Finding Description

**Layer 1 — `Noop` interceptor activated by config flag**

`core/src/servers.rs` lines 116–138 select the interceptor at server startup:

```rust
if config.client_verification {
    OnlyAggregatorAndSelf { aggregator_cert, our_cert: client_cert }
} else {
    Noop          // ← passes every request unconditionally
}
``` [1](#0-0) 

`Interceptors::Noop` is defined as:

```rust
Interceptors::Noop => Ok(req),
``` [2](#0-1) 

When `CLIENT_VERIFICATION` is absent or `false`, the entire mTLS identity check is bypassed for every RPC method on the operator server — including `Withdraw`, `InternalWithdraw`, `DepositSign`, and all `Internal*` methods.

**Layer 2 — `Withdraw` handler's only remaining guard is optional**

`core/src/rpc/operator.rs` lines 209–238:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // verify ECDSA sig …
}
// if None → falls through, no check performed
``` [3](#0-2) 

`aggregator_verification_address` is declared `Option<alloy::primitives::Address>` and parsed with `.ok()`, making it silently absent when `AGGREGATOR_VERIFICATION_ADDRESS` is unset: [4](#0-3) [5](#0-4) 

**Layer 3 — `InternalWithdraw` has no caller-identity check at all**

`core/src/rpc/operator.rs` lines 168–190 contain zero authentication logic — they parse parameters and immediately call `operator.withdraw()`: [6](#0-5) 

The proto comment explicitly says "intended for operator's own use," but the `Internal` prefix only restricts callers when `OnlyAggregatorAndSelf` is active. Under `Noop`, the prefix is meaningless. [7](#0-6) 

---

### Impact Explanation

When `CLIENT_VERIFICATION=false` (or unset) **and** `AGGREGATOR_VERIFICATION_ADDRESS` is unset, any entity that can reach the operator's gRPC TCP port can call `Withdraw` or `InternalWithdraw` with:

- A valid `withdrawal_id` (any withdrawal registered in Citrea — publicly observable)
- A valid user Schnorr `SIGHASH_SINGLE|ANYONECANPAY` signature for the withdrawal UTXO (obtainable by intercepting or replaying a prior aggregator-forwarded request, or by being the withdrawing user themselves)

The operator's `withdraw()` function will then:
1. Verify the withdrawal UTXO against Citrea DB ✓ (attacker supplies correct UTXO)
2. Verify the Schnorr signature ✓ (attacker supplies valid user sig)
3. Check profitability ✓ (attacker supplies profitable params)
4. Fund and broadcast the payout transaction — **spending operator BTC** [8](#0-7) 

The aggregator's role as the sole authorized initiator of operator payouts is completely bypassed. An attacker can:
- Force the operator to front BTC payouts at high-fee moments, increasing operator cost
- Replay any previously observed valid withdrawal request directly to the operator, circumventing any aggregator-level rate-limiting or manual review
- Exhaust the operator's liquid BTC balance across many valid pending withdrawals simultaneously

Funds are not redirected (the user's Schnorr signature covers the output), but the operator's collateral and liquid BTC are spent without its consent, and the trust boundary between aggregator and operator is broken.

---

### Likelihood Explanation

- `CLIENT_VERIFICATION=false` is not the default in `.env.example` (which sets `CLIENT_VERIFICATION=true`), but it is a valid, explicitly supported production code path — the `Noop` interceptor is production code, not test-only.
- `AGGREGATOR_VERIFICATION_ADDRESS` is documented as a transitional guard ("to force citrea to check withdrawal params manually during some time after launch"), implying operators may omit it after the launch period.
- The operator's gRPC port is reachable by the aggregator by design; any network peer on the same segment (or with firewall access) qualifies.
- A valid user Schnorr signature is obtainable by the withdrawing user themselves, or by anyone who observed a prior aggregator-forwarded `Withdraw` call.

---

### Recommendation

1. **Enforce authentication at the handler level for fund-moving RPCs.** `Withdraw` and `InternalWithdraw` should reject requests when neither mTLS (`client_verification`) nor `aggregator_verification_address` is configured, rather than silently proceeding.

2. **Make `aggregator_verification_address` mandatory when `client_verification=false`.** Add a startup check that refuses to start the operator server if both guards are absent simultaneously.

3. **Restrict `InternalWithdraw` beyond the `Internal` prefix convention.** Add an explicit self-identity check inside the handler (e.g., compare the caller's cert to `our_cert`) independent of the interceptor, so it cannot be called by external parties regardless of the interceptor in use.
