### Title
Fixed 546-satoshi dust threshold ignores script-dependent dust limits, producing unrelayable transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates every payment and every change output against a single hard-coded `DUST = 546` constant. Bitcoin's dust rule is not a fixed constant: it is a per-output function of the serialized output size and the fee rate needed to spend it (`dustRelayFee * (output_size + spend_size)`). Assuming all outputs share one scale for the minimum-value check is the same class of bug as assuming all tokens share 18 decimals: a value valid for one unit is silently treated as valid for every unit.

### Finding Description [1](#0-0) 
`DUST` is defined once as `546` sats — the dust limit for the *smallest* standard outputs. The comment acknowledges SegWit outputs differ but treats the range as "marginal". However, dust scales with `script_pubkey` length: a payment to an output with a large script (e.g., a large witness program or non-P2TR script supplied as a payment destination) has a dust limit well above 546.

At [2](#0-1)  payments are checked with `*amount < DUST`, and at [3](#0-2)  the change output is created whenever `value >= DUST`. Neither check accounts for the actual script size. The processor calls this API with attacker-influenced payment destinations (`payment.address` from batch instructions), so an unprivileged party supplying a payment whose script_pubkey pushes the real dust limit above 546 gets a transaction constructed and signed that Bitcoin Core will reject as non-standard dust — it can never be relayed or confirmed, while the wallet layer treats the funds as spent (fee + payment amounts committed).

### Impact Explanation
A transaction containing a sub-dust output relative to that output's actual dust limit fails mempool `dust` policy checks and will not propagate or confirm. The signers believe the payment was made; the underlying plan must be retried/refunded, and any change-paired plan stalls. This is a liveness/funds-in-flight loss reachable purely from attacker-chosen payment parameters — no validator collusion required.

### Likelihood Explanation
Anyone who can cause a `Payment` to be emitted toward an address whose `script_pubkey` is larger than the ~34-byte P2TR output (e.g., large `OP_RETURN`-style or exotic scripts, depending on integrator address handling) can trigger it by requesting an amount in the `[546, actual_dust)` band. The check at [2](#0-1)  gives a false sense of validation.

### Recommendation
Compute the dust threshold per output using the serialized output size (`GetDustThreshold`-equivalent: `3 * fee_rate * (serialized_output_size + input_spend_size)`), rather than the single `DUST` constant, for both the payment check and the change check. At minimum, reject non-P2TR/large-script payments or raise the bound for them.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs context
// A payment to a script_pubkey large enough that its real dust
// threshold is > 546 (e.g., a 100-byte witness program output):
let big_script = ScriptBuf::new_p2wsh(&WScriptHash::hash(&vec![0x51; 200]));
let payments = vec![(big_script, 600u64)]; // 600 >= DUST(546), passes the check
// ... but 600 < actual dust for this ~208-byte output (~1000+ sats at 3 sat/vB relay)
let tx = SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte);
// tx is built and signed; the resulting transaction is rejected by the mempool
// as dust and can never confirm.
```
The output's real dust threshold scales with `script_pubkey` size, while `send.rs` only tests `amount < 546`.
