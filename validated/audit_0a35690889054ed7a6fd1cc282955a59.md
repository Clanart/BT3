### Title
TOCTOU race on cached sender/fee-payer/gas fields of a shared `*Transaction` allows stale AccountKey validation results to be reused during execution - (File: blockchain/types/transaction.go)

### Summary
`Transaction.ValidateSender` and `Transaction.ValidateFeePayer` compute the sender/fee-payer address and gas cost by resolving the account's `AccountKey` from a caller-supplied `AccountKeyPicker` (a `StateDB` snapshot), then cache the result into shared, mutable fields (`validatedSender`, `validatedFeePayer`, `validatedGas`) on the `*Transaction` object using a check-then-set pattern guarded only per-field by `tx.mu`, not atomically across the whole validate-then-cache operation.

### Finding Description
`ValidateSender` reads the account key via `p.GetKey(from)` (or `p.GetKey(addr)` for Ethereum txs), computes gas and validity outside the lock, then does a check-then-act write: [1](#0-0) 

Similarly `ValidateFeePayer` resolves the fee payer's account key, computes `SigValidationGas`, then conditionally writes `validatedFeePayer` only if it still equals `validatedSender`: [2](#0-1) 

`AsMessageWithAccountKeyPicker` chains these two calls and additionally caches `validatedGas`, again writing under `tx.mu` but computed from values read moments earlier outside the lock: [3](#0-2) 

The same `*Transaction` pointer is shared across multiple concurrent code paths that each supply a *different* `AccountKeyPicker` (i.e., a different `StateDB` snapshot representing a different point in chain/account-key history): transaction pool validation (`pool.currentState`) and block/`ApplyTransaction` execution paths both call `AsMessageWithAccountKeyPicker` on pool-held or block-held transaction objects. The existing race-focused tests explicitly document this exact hazard: [4](#0-3) [5](#0-4) 

Because the cache write is "first writer wins" (`if tx.validatedSender == (common.Address{})`, `if tx.validatedFeePayer == tx.validatedSender`), whichever goroutine's `AccountKeyPicker` snapshot reaches the lock first permanently determines the cached sender, fee payer, and `validatedGas` (intrinsic gas including `SigValidationGas`) for the lifetime of that `*Transaction` object — later callers (e.g., block execution with the canonical/updated state after an intervening `AccountKeyUpdate` transaction) silently reuse the stale cached values instead of re-deriving them from the current state. `Execute()` unconditionally consumes these cached values without re-validation: [6](#0-5) 

and `StateTransition.buyGas` charges fees strictly based on `st.msg.ValidatedFeePayer()`/`ValidatedSender()` without recomputing them against the executing state: [7](#0-6) 

This is the same bug class as CVE-2026-14160 (TOCTOU: a security-relevant check is performed against one state snapshot, but the cached decision is later consumed as-if-current against a different, changed state) — here the "check" is AccountKey validation/gas sizing against one `StateDB`, and the "use" is fee charging/execution against a potentially different `StateDB`, mediated by a shared mutable cache with no invalidation on state change.

### Impact Explanation
If an account updates its `AccountKey` (e.g., moves from a cheap key type to a multisig/role-based key requiring higher `SigValidationGas`, or changes the fee-delegation role key) between when a transaction object is first validated by the pool (locking in `validatedGas`/`validatedFeePayer`) and when it is actually executed in a block with the updated state, the executor will use the stale, locked-in `SigValidationGas`/fee-payer determination rather than recomputing it against the current `AccountKey`. This can result in under-charged gas for signature validation (fee/gas accounting divergence) and/or fee-payer/sender mismatch relative to the account's *current* authorization state, which is a state-transition/gas-accounting integrity issue reachable purely by a transaction sender or fee-delegation counterparty submitting ordinary transactions plus an `AccountKeyUpdate`.

### Likelihood Explanation
The pool and block-building/`ApplyTransaction` paths already both operate on the same `*Transaction` object concurrently per `TestRaceBetweenTxpoolAddAndCommitNewWork` and `TestRaceAsMessageWithAccountPickerForFeePayer`, meaning the two-different-`AccountKeyPicker`-snapshot scenario is a documented, previously-observed condition in this codebase, not purely theoretical. However, I was unable to fully trace, within the remaining iteration budget, whether downstream call sites (e.g., `blockchain.go`, `state_prefetcher.go`, `node/cn/state_accessor.go`) always construct a *fresh* `*Transaction` copy per execution attempt (which would eliminate the shared-cache hazard) or reuse pool-held pointers directly into `ApplyTransaction`. This distinction is the deciding factor for real-world exploitability and requires further code review (specifically `blockchain/blockchain.go`'s single call site and `commitNewWork`/`ApplyTransaction` call chains) to confirm whether pointers are shared or txs are re-materialized from RLP/pool copies before execution.

### Recommendation
- Make the check-then-cache sequence in `ValidateSender`/`ValidateFeePayer`/`AsMessageWithAccountKeyPicker` atomic and tie the cached values to the specific state root/`AccountKeyPicker` they were derived from (e.g., cache key = state root or block number), invalidating/recomputing whenever the picker's underlying state differs from the one used to populate the cache.
- Alternatively, avoid caching validation results on a shared, mutable `*Transaction` at all for cross-context reuse (pool vs. execution); always recompute `ValidatedSender`/`ValidatedFeePayer`/`ValidatedGas` against the exact `StateDB` used for actual execution, or execute on a private copy of the transaction created fresh from raw fields for each state context.

### Proof of Concept
Conceptual PoC (cannot be fully executed without cluster access, but derivable from existing test scaffolding):
1. Submit `TxTypeFeeDelegatedValueTransfer` tx `T` from account `A` with fee payer `F`, where `A`'s current `AccountKey` is a simple key with `SigValidationGas = G1`.
2. Trigger `pool.validateTx(T)` (calls `AsMessageWithAccountKeyPicker` against `pool.currentState`), locking in `T.validatedGas = G1` and `T.validatedFeePayer = F`.
3. Before `T` is included in a block, submit and confirm an `AccountKeyUpdate` for `A` that changes its key to a multisig requiring `SigValidationGas = G2 > G1`.
4. When `T` (same object instance, if reused by the block-producing/`ApplyTransaction` path) is executed, `Execute()`/`buyGas()` reuse the stale cached `validatedGas`/`validatedFeePayer` from step 2 (`G1`), not the state after the key update (`G2`), because the cache write in `ValidateSender`/`ValidateFeePayer` is guarded by "first write wins" and never invalidated: [8](#0-7) [9](#0-8) 

This demonstrates the check (AccountKey/gas sizing against snapshot 1) and use (fee charging against snapshot 2 state) diverging — the core TOCTOU pattern analogous to CVE-2026-14160.

func (tx *Transaction) AsMessageWithAccountKeyPicker(s Signer, picker AccountKeyPicker, currentBlockNumber uint64) (*Transaction, error) {
	intrinsicGas, err := tx.IntrinsicGas(currentBlockNumber)
	if err != nil {
		return nil, err
	}

	gasFrom, err := tx.ValidateSender(s, picker, currentBlockNumber)
	if err != nil {
		return nil, ErrSender(err)
	}

	tx.mu.Lock()
	tx.checkNonce = true
	tx.mu.Unlock()

	gasFeePayer := uint64(0)
	if tx.IsFeeDelegatedTransaction() {
		gasFeePayer, err = tx.ValidateFeePayer(s, picker, currentBlockNumber)
		if err != nil {
			return nil, ErrFeePayer(err)
		}
	}

	sigValidationGas := gasFrom + gasFeePayer
	intrinsicGas = intrinsicGas + sigValidationGas

	tx.mu.Lock()
	tx.validatedGas = &ValidatedGas{IntrinsicGas: intrinsicGas, SigValidateGas: sigValidationGas}
	tx.mu.Unlock()

	return tx, err
}

// ValidateFeePayer finds a fee payer from a transaction.
// If the transaction is not a fee-delegated transaction, it returns an error.
func (tx *Transaction) ValidateFeePayer(signer Signer, p AccountKeyPicker, currentBlockNumber uint64) (uint64, error) {
	tf, ok := tx.data.(TxInternalDataFeePayer)
	if !ok {
		return 0, errUndefinedTxType
	}

	pubkey, err := SenderFeePayerPubkey(signer, tx)
	if err != nil {
		return 0, err
	}

	feePayer := tf.GetFeePayer()
	accKey := p.GetKey(feePayer)

	gasKey, err := accKey.SigValidationGas(currentBlockNumber, accountkey.RoleFeePayer, len(pubkey))
	if err != nil {
		return 0, err
	}

	if err := accountkey.ValidateAccountKey(currentBlockNumber, feePayer, accKey, pubkey, accountkey.RoleFeePayer); err != nil {
		return 0, ErrInvalidAccountKey
	}

	tx.mu.Lock()
	if tx.validatedFeePayer == tx.validatedSender {
		tx.validatedFeePayer = feePayer
	}
	tx.mu.Unlock()

	return gasKey, nil
}

func (st *StateTransition) buyGas() error {
	var (
		validatedFeePayer = st.msg.ValidatedFeePayer()
		validatedSender   = st.msg.ValidatedSender()
		feeRatio, _       = st.msg.FeeRatio()
		isOsaka           = st.evm.ChainConfig().Rules(st.evm.Context.BlockNumber).IsOsaka
	)

	// mgval is the maximum gas fee that can actually be paid in the worst case (e.g., revert)
	// st.gasPrice = tx.gasPrice (before Magma) or effectiveGasPrice (since Magma)
	mgval := new(big.Int).Mul(new(big.Int).SetUint64(st.msg.Gas()), st.gasPrice)

	// feeCap is the maximum gas fee the sender was willing to pay
	// GasFeeCap = tx.maxFeePerGas (if exists) or tx.gasPrice
	feeCap := new(big.Int).Mul(new(big.Int).SetUint64(st.msg.Gas()), st.msg.GasFeeCap())

	if isOsaka {
		if blobGas := st.blobGasUsed(); blobGas > 0 {
			// Check that the user has enough funds to cover blobGasUsed * tx.BlobGasFeeCap
			blobFeeCap := new(big.Int).SetUint64(blobGas)
			blobFeeCap.Mul(blobFeeCap, st.msg.BlobGasFeeCap())
			feeCap.Add(feeCap, blobFeeCap)
			// Pay for blobGasUsed * actual blob fee
			blobFee := new(big.Int).SetUint64(blobGas)
			blobFee.Mul(blobFee, st.evm.Context.BlobBaseFee)
			mgval.Add(mgval, blobFee)
		}
	}

	if validatedFeePayer == validatedSender {
		// 1. Non fee-delegated tx
		// 2. FeeDelegatedWithRatio with sender == feePayer
		// 3. FeeDelegated          with sender == feePayer

		// Before Osaka, only the check of the amount to be deducted is applied.
		// Therefore, all options are false.
		checkOverflow, checkWithValue := false, false
		balanceCheck := mgval
		if isOsaka {
			// Overflow will be checked from osaka onwards.
			// A value check is also performed.
			checkOverflow, checkWithValue = true, true
			balanceCheck = feeCap
		}
		if err := st.checkFeePayerBalance(balanceCheck, checkOverflow, checkWithValue); err != nil {
			return err
		}
		st.state.SubBalance(validatedFeePayer, mgval)
