### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers unbounded eager allocation (`Vec::with_capacity(n)`) enabling amplified memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::<C>::read` deserializes an attacker-supplied `n` (a `u16` read straight from the input stream) and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` arm — allocating capacity for up to 65,535 field elements (~2 MB) *before* a single scalar byte is read or any `ThresholdParams` validation of `n` occurs. This mirrors the Apollo Router bug class: memory is allocated proportional to an attacker-declared size, ignoring any external size-limiting configuration, and the allocation is held while the reader blocks waiting for the claimed elements.

### Finding Description

In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632):

- `t`, `n`, `i` are read as raw `u16`s with no bounds check (lines 591-602). `n` is fully attacker-controlled (0–65535).
- If the interpolation byte is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` at line 608, eagerly allocating `n * size_of::<C::F>()` bytes before any `read_F` call or validation that `n` is sane for the deployment's actual participant count.
- Only after this allocation (and after reading `n` scalars and `n` verification-share points) does `ThresholdParams::new(t, n, i)` (line 626) validate the parameters — far too late to bound the allocation.
- Because `read` operates on a generic `io::Read`, on any streaming/blocking reader (network-framed bytes, spooled message buffer) the allocation at line 608 is held for as long as the attacker withholds the promised scalar bytes. A ~10-byte header (curve ID + `t`/`n`/`i` + interpolation tag) therefore pins megabytes of heap indefinitely.

This is the same root cause as GHSA-x6xq-whh3-gg32: a length declared by untrusted input drives a memory commitment that bypasses whatever message/body size limits the caller believes are in force, because the allocation happens inside the deserializer before the declared content actually arrives.

### Impact Explanation

`ThresholdKeys::read` is reachable on untrusted bytes per the threat model (listed `ThresholdKeys::read` entry point). An unprivileged party can:

1. Open many concurrent input streams (or drip-feed a single serialized `ThresholdKeys` blob on a blocking reader).
2. In each, declare `n = 0xFFFF`, interpolation = `0` (Constant).
3. Each instance allocates ~2 MB (`65535 * 32` bytes, more for wider fields) before blocking in `read_F`.

Withholding the body keeps each allocation resident; a modest number of concurrent parses exhausts process memory, causing OOM termination of the signing/DKG node — a denial of service on the same availability target as the reference advisory. Even on a `&[u8]` reader the amplification is real but transient (allocation then immediate `read_exact` failure); the streaming case makes it persistent.

### Likelihood Explanation

Likelihood is moderate-to-high where `ThresholdKeys::read` (or wrappers such as `EncryptedMessage`/`ThresholdKeys` transport in the DKG flow) deserializes peer-supplied bytes on a blocking or streaming reader without a prior strict outer size cap. The trigger requires only ~10 controlled bytes, no valid signature, no curve-specific knowledge, and no collusion. The main mitigating factor is the `u16` bound on `n` (~2 MB per instance), so exploitation requires concurrent or repeated parses rather than a single message — matching a Medium/High severity posture.

### Recommendation

- Do not call `Vec::with_capacity(n)` before validating `n`. Validate `t`/`n`/`i` via `ThresholdParams::new` (and against an application-level `MAX_KEY_SHARES_PER_SET`-style bound) *before* allocating or reading any elements.
- Replace the eager allocation with incremental `push` after `read_F` succeeds, so memory growth is proportional to bytes actually received, or cap `n` (e.g., `n <= MAX_PARTICIPANTS`) immediately after reading the header.
- Apply the same audit to the `verification_shares` loop (lines 620-623), which iterates `1..=n` reading points — ensure `n` is bounded before entering it.

### Proof of Concept

```rust
use std::io;
use frost::{curve::Secp256k1, ThresholdKeys}; // conceptual

fn poc() {
    // Minimal crafted blob: curve ID len + ID for Secp256k1, then t/n/i, then Constant tag
    let mut blob = Vec::new();
    let id = Secp256k1::ID; // pseudo: curve identifier bytes
    blob.extend(&(id.len() as u32).to_le_bytes());
    blob.extend(id);
    blob.extend(&1u16.to_le_bytes());      // t = 1
    blob.extend(&u16::MAX.to_le_bytes());  // n = 65535  <-- attacker-controlled
    blob.extend(&1u16.to_le_bytes());      // i = 1
    blob.push(0u8);                        // Interpolation::Constant
    // No scalar bytes follow.

    // On a blocking/streaming reader this allocates ~65535 * 32 bytes in
    // Vec::with_capacity(n) at crypto/dkg/src/lib.rs:608 and then blocks
    // in C::read_F, holding the allocation while the attacker withholds data.
    // Repeated across connections -> heap exhaustion / OOM kill.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut io::Cursor::new(blob));
}
```
