### Title
Missing `chain_id` in `CLEMENTINE_EIP712_DOMAIN` Enables Cross-Network Signature Replay on Optimistic Payout and Operator Withdrawal Authorization — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is constructed without a `chain_id` field. This domain is used to verify the aggregator's ECDSA authorization signature on every optimistic payout and operator withdrawal. Because the domain hash is identical across all EVM chains, a signature legitimately produced on one Citrea network (e.g., testnet4, chain_id 5655) is cryptographically valid on any other Citrea deployment sharing the same domain name and version string. An attacker who captures a valid authorization signature from one network can replay it on another to trigger unauthorized BTC payouts from the bridge vault.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is declared as a static constant with only `name` and `version`:

```rust
// core/src/rpc/ecdsa_verification_sig.rs, line 42-45
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
```

The EIP-712 specification requires `chainId` in the domain separator precisely to prevent cross-chain replay. Without it, the domain separator hash is the same on every EVM chain.

This domain is consumed in `recover_address_from_ecdsa_signature` (line 125):

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
```

That function is called in two production authorization paths:

1. **`Verifier::sign_optimistic_payout`** (`core/src/verifier.rs`, lines 1602–1618): verifies the aggregator's `OptimisticPayoutMessage` signature before co-signing the MuSig2 optimistic payout transaction that spends the bridge vault UTXO.
2. **`OperatorRpc::withdraw`** (`core/src/rpc/operator.rs`, lines 210–238): verifies the aggregator's `OperatorWithdrawalMessage` signature before the operator broadcasts the payout transaction.

The `citrea_chain_id` is already present in `BridgeConfig` (line 86 of `core/src/config/mod.rs`) and is used elsewhere (e.g., to configure the EVM wallet in `CitreaClient::new`), but it is never injected into the EIP-712 domain.

---

### Impact Explanation

When `aggregator_verification_address` is configured (the intended production hardening path), the entire authorization gate reduces to: "does the recovered address match the configured address?" Because the domain hash is chain-agnostic, any signature that was legitimately produced by the aggregator on one Citrea network (testnet4, a staging fork, or a future mainnet fork) passes verification on every other network with the same `aggregator_verification_address`.

Concrete impact path:

1. Aggregator legitimately signs an `OptimisticPayoutMessage` for `withdrawal_id=N`, `input_outpoint=X`, `output_script_pubkey=P`, `output_amount=A` on Citrea testnet4.
2. An attacker observes this signature (it is transmitted in plaintext over gRPC as a hex string in `verification_signature`).
3. On a Citrea mainnet fork (or any other Citrea deployment) where the same `withdrawal_id=N` and `input_outpoint=X` exist (possible after a fork, or if deposit indices are predictable), the attacker submits the same signature.
4. `recover_address_from_ecdsa_signature` recovers the same address (domain hash is identical), the check at line 1616 passes, and the verifiers co-sign the optimistic payout.
5. The bridge vault UTXO is spent to the attacker-controlled `output_script_pubkey`.

The result is unauthorized movement of bridged BTC from the vault.

---

### Likelihood Explanation

- The `aggregator_verification_address` field is optional; deployments that omit it are unaffected by this specific path (but also have no authorization check at all).
- Deployments that set it (the production-hardened configuration shown in `.env.example` with `AGGREGATOR_VERIFICATION_ADDRESS=0x242fbec93465ce42b3d7c0e1901824a2697193fd`) are fully exposed.
- The attack requires the attacker to observe a valid signature (possible by monitoring gRPC traffic or from a compromised testnet deployment) and to find or construct a matching deposit on the target chain.
- A Citrea hard fork is the highest-likelihood trigger, as it would produce two chains sharing deposit history and the same `aggregator_verification_address`.

---

### Recommendation

Include `citrea_chain_id` from `BridgeConfig` in the EIP-712 domain. Since `CLEMENTINE_EIP712_DOMAIN` is currently a `static`, it must be changed to a runtime-constructed value:

```rust
pub fn build_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used:
- `recover_address_from_ecdsa_signature` should accept the domain (or chain_id) as a parameter.
- Both `Verifier::sign_optimistic_payout` and `OperatorRpc::withdraw` already have access to `self.config.citrea_chain_id`.

---

### Proof of Concept

The existing unit test `test_recover_address_from_signature` in `core/src/verifier.rs` (lines 3457–3520) demonstrates that the same hardcoded domain is used for both signing and verification with no chain binding. To confirm cross-chain replay:

1. Sign an `OptimisticPayoutMessage` using `CLEMENTINE_EIP712_DOMAIN` (chain_id absent) on a testnet4 instance.
2. Submit the identical `(withdrawal_id, input_outpoint, output_script_pubkey, output_amount, verification_signature)` tuple to a mainnet (or forked) instance.
3. `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` will recover the same address on both instances because `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` produces the same digest — the domain separator contains no chain discriminator.
4. The check `address_from_sig != address_in_config` at line 1616 passes, and the verifier proceeds to co-sign the optimistic payout. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
