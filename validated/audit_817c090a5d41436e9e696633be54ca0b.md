## Analysis

**Binding claimed:** `old_move_txid → {at most one valid ReplacementDeposit registration}`. In practice the code only enforces `deposit_outpoint → {at most one DepositData}` (a per-outpoint key), never a per-`old_move_txid` key.

**Trace:**

- `ReplacementDepositScript` commits only to `(nofn_xonly_pk, old_move_txid)` in its script bytes — it carries no reference to *which* UTXO must be spent to fund it: [1](#0-0)  and [2](#0-1) .
- `DepositData::get_deposit_scripts` for `DepositType::ReplacementDeposit` derives the expected script purely from `(nofn_xonly_pk, old_move_txid)` supplied in the RPC request, with no linkage to the actual prior move-to-vault UTXO: [3](#0-2) .
- `Verifier::is_deposit_valid` checks only that the on-chain tx at `deposit_outpoint` has the expected `scriptPubkey` and `value == bridge_amount` and sufficient block height — it never checks that any input of that funding transaction actually spends `OutPoint{old_move_txid, DepositInMove}`: [4](#0-3) .
- `insert_deposit_data_if_not_exists` uniqueness is keyed only by `deposit_outpoint` (`ON CONFLICT (deposit_outpoint) DO NOTHING`); there is no unique constraint or lookup on `old_move_txid`: [5](#0-4) .
- `deposit_sign` / `deposit_finalize` call `is_deposit_valid` and `insert_deposit_data_if_not_exists` scoped only to the single `deposit_data.get_deposit_outpoint()` being processed: [6](#0-5) [7](#0-6) .

So the reference/canonical flow (`create_replacement_deposit_txhandler`, spending `OutPoint{old_move_txid, DepositInMove}` with `CheckSig(old_nofn)+Multisig(security_council)`) is only a *convention* used by the test helpers/CLI — it is **not enforced** by verifier logic. Nothing stops a depositor from funding two unrelated outpoints A and B directly (their own coins, own transactions) with `ReplacementDepositScript(nofn_xonly_pk, old_move_txid)` for the same, arbitrary, publicly-known `old_move_txid`, and calling `new_deposit` twice. Each call is independently validated by every verifier and independently presigned by the N-of-N into two distinct, fully valid move-to-vault transactions, both carrying an on-chain-readable claim of replacing the same `old_move_txid`.

**Why this matters, but why it's hard to close the loop within this repo:** whether such duplicate/fabricated replacement claims actually cause the Citrea Bridge contract to double-credit or overwrite a deposit slot depends entirely on the Solidity `replaceDeposit(...)` contract logic (deposit-id lookup, SPV proof of the *committed script bytes only* vs. proof that the specific prior UTXO was spent). That contract is not present in this repository and is explicitly out of scope for defect attribution. What is squarely a repo-level defect, however, is that Clementine's verifier/aggregator layer has no `old_move_txid` uniqueness guard at all, so it will happily produce N-of-N signatures for two (or more) competing move-to-vault transactions that both assert replacement of one identical prior deposit — a guarantee the design (per the module doc "old move_to_vault txid that was replaced") clearly intends to be singular.

### Title
Verifier `is_deposit_valid` and `insert_deposit_data_if_not_exists` never enforce per-`old_move_txid` uniqueness for `ReplacementDeposit`, letting N-of-N presign two competing move-to-vault txs claiming to replace the same prior deposit - ([File: core/src/verifier.rs, core/src/database/operator.rs])

### Summary
`Verifier::is_deposit_valid` only validates that the transaction sitting at a given `deposit_outpoint` has the correct `ReplacementDepositScript(nofn_xonly_pk, old_move_txid)` scriptPubkey and bridge amount; it never checks that this funding transaction actually spends the referenced `old_move_txid`'s move-to-vault output. `insert_deposit_data_if_not_exists` deduplicates only on `deposit_outpoint`. An unprivileged depositor can therefore fund two independent outpoints with scripts committing to the same `old_move_txid` and get both registered and N-of-N presigned.

### Finding Description
The intended binding is `old_move_txid → single canonical replacement move-to-vault tx`, but the enforced binding is `deposit_outpoint → DepositData` [8](#0-7) . `is_deposit_valid` never resolves or checks the input side of the funding transaction against `old_move_txid` [4](#0-3) ; it merely rebuilds the expected scriptPubkey from `ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid)` [3](#0-2)  and compares it against whatever is on-chain at `deposit_outpoint`. Since anyone can construct a P2TR output using this publicly-computable script/address (`generate_replacement_deposit_address`) and fund it with their own coins [2](#0-1) , an attacker can create two distinct outpoints A and B, both committing to the same, attacker-chosen `old_move_txid` (e.g., a real, publicly-visible prior move txid), and call `aggregator.new_deposit` for each. Each verifier independently runs `is_deposit_valid`/`insert_deposit_data_if_not_exists` scoped to its own `deposit_outpoint` [6](#0-5) , so both pass, and the N-of-N proceeds to `deposit_finalize`/`create_movetx` for both, producing two distinct, fully signed move-to-vault transactions that each on-chain-commit an assertion of replacing the identical `old_move_txid`.

### Impact Explanation
The repo-level guarantee that only one replacement can exist per prior deposit is broken: the N-of-N produces valid partial/aggregated signatures for two competing move-to-vault transactions both claiming to supersede the same deposit. Whatever downstream system (the Citrea Bridge contract's `replaceDeposit`) consumes this data has no way to distinguish "the" legitimate replacement from the attacker's fabricated one at the Bitcoin/Clementine layer, since neither is anchored in this repo's logic to an actual on-chain spend of the true prior move-to-vault UTXO. This matches the "N-of-N partial signatures for an unauthorised spend" / "false claim proved by the bridge" impact categories at the Clementine layer; the concrete resulting harm (double credit, orphaned/frozen legitimate deposit) depends on the out-of-scope Citrea contract's handling of `replaceDeposit`, but the root cause — missing `old_move_txid` uniqueness/provenance enforcement — is squarely in this repo and is repeatable for every existing deposit and unbounded number of attempts.

### Likelihood Explanation
No privileged role is required. The attacker only needs to know a legitimate `old_move_txid` (trivially public — it's a move-to-vault txid), derive the deterministic `ReplacementDepositScript`/address via `generate_replacement_deposit_address` (exposed via `GetReplacementDepositAddress` RPC), fund two outputs with `bridge_amount` BTC each (their own funds, standard tx fees), and call the public `new_deposit` gRPC twice. No verifier, operator, or security-council cooperation is needed.

### Recommendation
In `Verifier::is_deposit_valid` (and in `insert_deposit_data_if_not_exists`), for `DepositType::ReplacementDeposit`, verify that the on-chain transaction funding `deposit_outpoint` actually spends `OutPoint{old_move_txid, UtxoVout::DepositInMove}` as one of its inputs (matching the intended `create_replacement_deposit_txhandler` shape), and add a database-level uniqueness constraint/check on `old_move_txid` so that at most one `ReplacementDeposit` can ever be registered/signed per prior move txid.

/// Struct for deposit script that replaces an old move tx with a replacement deposit (to update bridge design on chain)
/// It commits to the old move txid inside the script.
#[derive(Debug, Clone)]
pub struct ReplacementDepositScript(pub(crate) XOnlyPublicKey, Txid);

impl SpendableScript for ReplacementDepositScript {
    fn as_any(&self) -> &dyn Any {
        self
    }

    fn kind(&self) -> ScriptKind {
        ScriptKind::ReplacementDepositScript(self)
    }

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }
}
