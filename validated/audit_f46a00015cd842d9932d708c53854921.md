### Title
Fee/weight calculation snapshots `payments` before the OP_RETURN data output is added, producing an underpriced or consensus-nonstandard transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

`SignableTransaction::new` builds the final output list (`tx_outs`) including payments, an `OP_RETURN` data output, and change. However, both calls to `calculate_weight_vbytes` pass `payments` — the pre-snapshot parameter set — rather than the final `tx_outs`. The weight, vsize-derived `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` standardness check are therefore all computed against a stale transaction shape that omits the data output, exactly paralleling the reported bug class where cached parameters are not re-validated against the state actually executed. [1](#0-0) 

### Finding Description

In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150`):

1. `tx_outs` is built from `payments` and then conditionally extended with an `OP_RETURN` output carrying up to 80 bytes of `data` (lines 188–202). [2](#0-1) 
2. Weight/vbytes are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, and again with change at line 225–226 — both times over `payments` only, never including the `OP_RETURN` output or the change output's final form. [3](#0-2) 
3. `needed_fee = fee_per_vbyte * vbytes`, the `TooLowFee` minimum-relay check (line 211), and the `TooLargeTransaction` check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) all consume this understated weight. [4](#0-3) 
4. The produced `SignableTransaction` is then signed in `TransactionSignMachine::sign` with `Prevouts::All(&self.tx.prevouts)` (line 375), committing the threshold signature to the real (larger) transaction and the real (lower) effective feerate. [5](#0-4) 

An `OP_RETURN` output with 80 bytes of data adds roughly 90+ bytes (~360+ WU, ~90 vbytes) that the fee and standardness math never accounts for.

### Impact Explanation

- **Underpriced / non-relayable transaction:** when `fee_per_vbyte` is near `DEFAULT_MIN_RELAY_TX_FEE`, the check at line 211 passes against the understated vbytes while the real feerate falls below the minimum relay policy, so Bitcoin nodes drop the signed transaction. The FROST group signs and may report a plan completed, yet the transaction never confirms — the spent inputs' funds are effectively locked and "received" payments are not spendable until the plan is manually recovered.
- **Standardness violation:** a transaction legitimately just under `MAX_STANDARD_TX_WEIGHT` can exceed it by the uncounted OP_RETURN weight, making the signed transaction nonstandard and unbroadcastable. `needed_fee()` and `fee()` then return inconsistent values since `fee()` is computed from real prevouts/outputs while `needed_fee` reflects the stale estimate (lines 133–141).

### Likelihood Explanation

Reachable by an unprivileged party whenever they cause a withdrawal carrying `data` (up to 80 bytes, permitted by the `TooMuchData` check at line 171) to be constructed and signed, combined with a borderline fee rate or a near-limit transaction size. No collusion or key access is required; the discrepancy is purely a function of public transaction parameters.

### Recommendation

Compute weight, `needed_fee`, and both policy checks against the *final* output set (`tx_outs`, including the OP_RETURN and change outputs) rather than the `payments` snapshot — i.e., re-validate against current state at execution, mirroring the governance-versioning fix pattern. Concretely, pass the fully constructed `tx_outs` (with a placeholder/zero-value change before its amount is known) into `calculate_weight_vbytes`, or add the serialized size of the OP_RETURN output to `weight`/`vbytes` before deriving `needed_fee` and performing the checks at lines 211 and 241.

### Proof of Concept

```rust
// networks/bitcoin: construct a SignableTransaction whose data output is excluded
// from the fee/weight math.
let data = vec![0u8; 80]; // maximum permitted by the TooMuchData check
let tx = SignableTransaction::new(
    vec![received_output],            // a scanned Serai input
    &[(payment_script, DUST)],        // minimal payment
    Some(change_script),
    Some(data),
    1,                                // 1 sat/vbyte, near min-relay boundary
).unwrap();

// needed_fee was derived from vbytes of (inputs + payments + change) only;
// the ~92-byte OP_RETURN output in tx.transaction().output is unpriced.
let assumed_vbytes = tx.needed_fee();              // 1 sat/vB * undercounted vbytes
let real_vbytes = tx.transaction().vsize() as u64; // includes OP_RETURN output
assert!(real_vbytes > assumed_vbytes);             // real feerate < 1 sat/vB -> dropped
```

The signature produced by `TransactionSignMachine::sign` commits to `Prevouts::All` over the real transaction (send.rs:375), so the underpriced/nonstandard result is baked into an otherwise valid BIP-340 signature — the signer signs a transaction the network will not relay, and the inputs cannot be re-spent under a different plan without manual intervention.
