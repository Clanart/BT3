### Title
Prefix-based path-containment check in `resolveWithin()` allows sibling-directory escape via crafted deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
The `_resolveWithin()` helper, which is the single guard used throughout GitHub Desktop to confirm that an attacker/URL-supplied relative path stays inside a repository root, decides containment with a raw string `startsWith()` comparison instead of a path-boundary-aware comparison. Because it never checks for a trailing path separator after the prefix match, any sibling directory whose name begins with the repository's folder name (e.g. `myrepo-secret`, `myrepo.bak`, `myrepo2`) is treated as "inside" the repository. This guard is relied upon to sanitize the `filepath` parameter of the `x-github-client://openRepo/...` deep link handled by `Dispatcher.openRepositoryFromUrl`, as well as file paths read for the Copilot conflict-resolution context builder.

### Finding Description
`resolveWithin` in `app/src/lib/path.ts` resolves a caller-supplied relative path against a root and then checks containment like this: [1](#0-0) 

`realResolved.startsWith(realRoot)` is a naive string prefix check. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo` and `realResolved` is `/Users/victim/Documents/GitHub/myrepo-secret/id_rsa`, the `startsWith` check returns `true` because `"myrepo-secret"` textually starts with `"myrepo"`, even though `myrepo-secret` is a completely different, sibling directory. No `path.sep` boundary check (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`) is performed.

This function is consumed by `Dispatcher.openRepositoryFromUrl`, which handles the `filepath` query parameter of a GitHub Desktop deep link (`x-github-client://openRepo/<url>?filepath=...`), an attacker-controlled value coming from a link the victim clicks: [2](#0-1) 

The only other guard applied before `resolveWithin` is an `isAbsolute(filepath)` rejection, which does not stop the sibling-directory bypass since the crafted value (e.g. `../myrepo-secret/id_rsa`) is a relative path. The existing regression test suite in `app/test/unit/path-test.ts` only covers `..`-only escapes and symlink escapes; it does not include a sibling-directory-name test case, so the gap is untested. [3](#0-2) 

The same unsafe primitive is reused in `app/src/lib/copilot-conflict-context.ts`, which reads file contents (for submission to the Copilot conflict-resolution model) after checking `resolveWithin`: [4](#0-3) 

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?filepath=../<sibling>/...` link can cause Desktop to resolve to, and act on, files outside the intended repository as long as a sibling folder name happens to share the repository folder's name as a prefix (a very common naming pattern for people who keep `repo`, `repo-old`, `repo.bak`, `repo2`, etc. side by side in their GitHub clones directory). The `openRepositoryFromUrl` path calls `shell.showItemInFolder(resolved)` on the escaped path, revealing/opening arbitrary sibling-directory content in the OS file browser. The same broken primitive, reused via `resolveWithin` in the Copilot conflict-context builder, means any code path that constructs a "safe" path to read file content for AI submission is subject to the identical sibling-directory bypass, risking exfiltration of file content outside the repository to the Copilot backend if the file-list source (conflict file paths) can ever be influenced by repository content.

### Likelihood Explanation
Exploitation requires only a link click (the "deep link" attacker primitive explicitly listed as valid) and a directory-naming coincidence that is common in practice (repos often have `-backup`, `-old`, `.bak`, numeric suffixes, etc. as siblings). No local/physical access, no admin rights, and no pre-existing malware are required, satisfying the report's validity criteria. `resolveWithin` is a shared, security-critical primitive used in multiple trust boundaries, so any single call site that constructs a `filepath` from untrusted input inherits the flaw.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to compare with a path-separator boundary instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(with the platform-appropriate separator from the `options` argument for the win32/posix variants). Add regression tests covering sibling directories that share a name prefix (`myrepo` vs `myrepo-evil`) for both POSIX and Windows separators.

### Proof of Concept
1. Victim has cloned two repositories side by side: `/Users/victim/Documents/GitHub/myrepo` and `/Users/victim/Documents/GitHub/myrepo-secret` (the latter containing sensitive files, e.g. an `.env` or private notes).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/someorg/myrepo?filepath=..%2Fmyrepo-secret%2F.env`
3. Victim clicks the link. `parseAppURL` extracts `filepath = "../myrepo-secret/.env"`; `isAbsolute` check passes (path is relative) so it proceeds to `resolveWithin(repository.path, filepath)`.
4. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/myrepo-secret/.env`; `realRoot` is `/Users/victim/Documents/GitHub/myrepo`. Because `realResolved.startsWith(realRoot)` is true (string-prefix match, no separator check), the function returns the escaped path instead of `null`.
5. `shell.showItemInFolder(resolved)` runs on the sibling repository's `.env` file, revealing/opening it to the attacker-directed UI action despite it being entirely outside `myrepo`.

Note: I could not fully trace whether any code path allows an attacker to control the `file.path` values fed into `buildConflictContext` in `copilot-conflict-context.ts` (they normally originate from git conflict status, not directly from user/URL input); this would require further investigation before treating that call site as independently exploitable. The `resolveWithin` containment defect itself, however, is directly verifiable from the code shown above.
