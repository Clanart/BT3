### Title
Unauthenticated wallet crash when taking a malformed Offer via `Offer._get_offered_coins()` assertion (analog of CWE-476 null-pointer/None dereference) - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer._get_offered_coins()` in `chia/wallet/trading/offer.py` assumes that `get_inner_puzzle()`/`get_inner_solution()` always return a non-`None` `Program` whenever a puzzle driver is matched, and enforces that assumption with a bare `assert`. A counterparty-supplied offer file (fully attacker-controlled bytes parsed via `Offer.from_bytes()`/`Offer.from_bech32()`) can contain a CAT/singleton/NFT-style outer puzzle that `match_puzzle()` recognizes (driver `match()` succeeds) but whose nested/inner layer is malformed enough that the corresponding `get_inner_puzzle()`/`get_inner_solution()` returns `None`. This triggers `AssertionError`, an unhandled exception analogous to a null-pointer dereference crash, in the exact place the CVE report is about (an unchecked assumption that a pointer/value obtained from parsing untrusted, attacker-supplied data is non-null).

`get_inner_puzzle`/`get_inner_solution` dispatch through `driver_lookup` (see `chia/wallet/outer_puzzles.py`) to per-asset-type drivers such as `CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`. Each of these drivers' `match()` only checks the *outer* curried mod/hash (e.g. `NFT_STATE_LAYER_MOD`, singleton mod, CR layer) to decide whether the puzzle "is" that asset type, and separately, the recursive `also()` sub-driver chain can legitimately return `None` for the inner layer while the outer `match()` still succeeds — for example in `MetadataOuterPuzzle.get_inner_puzzle` and `SingletonOuterPuzzle.get_inner_puzzle`: [2](#0-1) [3](#0-2) 

Because these drivers do not perform full structural validation of every deeper layer (curried-arg counts, nested mod hashes, etc.) before recursing, a crafted offer coin spend whose puzzle reveal matches an outer asset type at the shallow level, but is corrupted or truncated at a deeper curried layer, can cause `get_inner_puzzle()`/`get_inner_solution()` to return `None` in a code path that `Offer.__post_init__`/`_get_offered_coins()` did not anticipate returning `None` for a "matched" driver. The bare `assert` then raises `AssertionError`, an unhandled exception, analogous in class to a null-pointer dereference on attacker-influenced, incompletely-validated data (CWE-476 root cause: trusting a parsed structure to be non-null/well-formed without an explicit check before use).

### Impact Explanation
`Offer.from_bytes()`/`Offer.from_bech32()` are the standard entry points for loading an offer file received from any untrusted offer-maker/counterparty (e.g. via `take_offer` RPC, CLI, or GUI import of an `.offer` file). `_get_offered_coins()` is invoked (through `get_offered_coins()`) during offer summarization/validation flows in `chia/wallet/trade_manager.py` before the taker has committed any funds. A malicious counterparty can craft an offer file that passes CLVM-level parsing (`Streamable`/`SpendBundle` decoding) but trips this internal invariant, causing the wallet process handling the RPC/CLI call to crash with an unhandled `AssertionError` while attempting to inspect or take the offer. This is a wallet-side denial-of-service ("spend-triggered transaction-processing halt") reachable by any offer counterparty without requiring any signature or on-chain broadcast — the crash occurs purely from local parsing/inspection of attacker-supplied offer bytes.

This does not directly cause unauthorized coin movement or consensus divergence; the blast radius is limited to a crash/halt of the wallet's offer-processing code path for the specific caller/process handling that offer.

### Likelihood Explanation
Medium. Triggering it requires crafting a CLVM puzzle that (a) still parses as a valid `CoinSpend`/`SpendBundle`, and (b) matches an outer-layer `match_puzzle()` check while a deeper `also()`/inner-layer helper legitimately returns `None`. This is plausible because the driver-matching functions (`match_metadata_layer_puzzle`, `match_singleton_puzzle`, etc.) validate only the specific curried slots they read and do not perform end-to-end structural verification of the whole puzzle tree; an attacker who understands the outer-puzzle layering conventions used across CAT/singleton/NFT/CR drivers has a workable path to construct such an input without needing chain access or signatures.

### Recommendation
- Replace the bare `assert inner_puzzle is not None and inner_solution is not None` in `Offer._get_offered_coins()` with an explicit check that raises a caught/handled exception (e.g. `ValueError`) so that malformed offers are rejected gracefully rather than crashing the process.
- Audit each outer-puzzle driver's `match()`/`get_inner_puzzle()`/`get_inner_solution()` (`chia/wallet/outer_puzzles.py` and its registered drivers) to ensure `match()` only returns non-`None` when the corresponding `get_inner_puzzle`/`get_inner_solution` calls are guaranteed to succeed, or make these methods consistently raise/return errors instead of `None` on structural mismatch.
- Wrap offer parsing/summarization (`Offer.from_bytes`, `get_offered_coins`, `Offer.__post_init__`) at RPC/CLI boundaries in exception handling that converts unexpected internal errors into a clean "invalid offer" response instead of propagating an unhandled exception to the caller.

### Proof of Concept
Conceptual (not a working exploit, since constructing the exact malformed curried puzzle bytes that pass outer `match()` while breaking inner extraction requires CLVM crafting not verifiable from static review alone):
1. Construct a `CoinSpend` whose `puzzle_reveal` curries as `NFT_STATE_LAYER_MOD` (or `SINGLETON_MOD`/CR layer) with a syntactically valid outer curry so `match_metadata_layer_puzzle`/`match_singleton_puzzle` returns `True`, but whose nested inner-puzzle argument is structured so that the driver's inner-extraction helper (or its `also()` sub-driver) returns `None` instead of a `Program`.
2. Embed this `CoinSpend` (with `parent_coin_info == bytes32.zeros` per the offer dummy-coin convention) inside a `WalletSpendBundle`, serialize it with `Offer.to_spend_bundle()`-compatible layout, and encode it as a bech32 offer string.
3. Have the victim load the offer via `Offer.from_bech32()` and call any flow that invokes `get_offered_coins()` (e.g. `take_offer`/`get_offer_summary` RPC).
4. Observe `AssertionError` raised from `_get_offered_coins()` (`chia/wallet/trading/offer.py:260`), crashing/halting the offer-processing call.
