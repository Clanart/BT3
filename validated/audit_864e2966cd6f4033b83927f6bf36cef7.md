### Title
Coinbase transaction outputs reported as spendable before maturity - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `txdata[0]` (the coinbase), and emits its outputs as `ReceivedOutput`s indistinguishable from normal spendable outputs. Bitcoin consensus rules forbid spending coinbase outputs until they have 100 confirmations, but `ReceivedOutput` carries no maturity marker and `SignableTransaction::new` / `TransactionSignMachine::sign` never check it. Funds scanned this way are reported as received and can be scheduled into a spend that the network will reject.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `scan_block` calls `scan_transaction` for every transaction in `block.txdata`, including the coinbase (lines 221-227). `scan_transaction` (lines 199-214) matches `output.script_pubkey` against registered scripts and constructs a `ReceivedOutput` containing only `offset`, `output`, and `outpoint` — there is no field recording that the outpoint originates from a coinbase or the block height at which it becomes spendable.

The downstream spend path in `networks/bitcoin/src/wallet/send.rs` treats every `ReceivedOutput` as immediately spendable: `SignableTransaction::new` (lines 150-256) builds `TxIn`s with `sequence: Sequence::MAX` and no maturity check, and `TransactionSignMachine::sign` (lines 355-398) produces signatures committing to those inputs. Any block producing a coinbase output paying a registered script yields a `ReceivedOutput` that cannot actually be spent until the coinbase matures (100 confirmations per Bitcoin consensus), while the scanning depth used for "final" blocks is a much smaller `CONFIRMATIONS`-style window.

This mirrors the reported bug class: the code consumes external data (block contents) without verifying the data has reached a state where acting on it is valid — the oracle's "is the sequencer up / is this fresh" check maps to Bitcoin's "has this coinbase matured" requirement, and no equivalent check exists.

### Impact Explanation
Any party capable of mining a block (a miner) can place an output to Serai's registered script in the coinbase transaction. Once that block reaches the confirmation depth used for scanning, the output is reported as a received, spendable deposit — triggering `Batch` creation and crediting of funds. When the scheduler later incorporates this output into a `SignableTransaction`, the resulting transaction spends an immature coinbase and is consensus-invalid: it cannot be broadcast or confirmed. The signed batch may also strand other outputs aggregated into the same plan, blocking payments that depend on it. This is "funds reported received that are not spendable," matching the accepted impact criteria.

### Likelihood Explanation
Reachability requires a miner to direct a coinbase output to the multisig's script, which costs the miner nothing beyond opportunity cost (they can pay the multisig from their own block reward). No collusion, malicious RPC, or leaked keys are needed — the trigger is ordinary public transaction data in a valid block, matching the allowed input surface (Bitcoin transactions an unprivileged party causes to exist on-chain).

### Recommendation
Track maturity in `ReceivedOutput` or exclude coinbase transactions from scan results. Concretely: in `Scanner::scan_block`, either skip `block.txdata[0]` (as the doc comment suggests via `block.txdata[1 ..]`) or add an `is_coinbase`/maturity flag to `ReceivedOutput` and have `SignableTransaction::new` reject immature coinbase inputs. The processor-side scanner should additionally compare the containing block's height against the required 100-confirmation maturity before emitting the output.

Root cause: `scan_block` (mod.rs:221-227) does not distinguish `txdata[0]` from spendable transactions and `ReceivedOutput` (mod.rs:89-97) has no maturity field, while `SignableTransaction::new` (send.rs:150+) assumes every provided input is immediately spendable.
