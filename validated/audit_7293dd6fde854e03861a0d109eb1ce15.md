### Title
Tokenfactory `AllowList`-restricted denom transfers can bypass admin-set access control via the EVM `bank` precompile's `sendNative` - (File: `precompiles/bank/bank.go`)

### Summary
Tokenfactory denom admins can attach a `bank.AllowList` to a `factory/...` denom, restricting who may send/receive it. This restriction is only enforced inside the Cosmos `bank` `MsgServer.Send`/`MsgMultiSend` handlers via `IsInDenomAllowList`, not inside the shared `SendCoins`/`SendCoinsAndWei` primitives. The EVM `bank` precompile's `sendNative` method calls `SendCoinsAndWei` directly, so any associated EVM account can transfer a restricted tokenfactory denom to or from an address that is not on the denom's allow list, exactly like the Nextcloud bug where an ACL enforced on one file-access path (move) did not apply to an equivalent indirect path (copy).

### Finding Description
`BaseSendKeeper.IsInDenomAllowList` is the sole gate for tokenfactory `AllowList` restrictions, and it's invoked explicitly by the `msgServer.Send` handler before calling `SendCoins`: [5](#0-4) 

`SendCoins` and its callee `sendCoinsWithoutAccCreation` never call `IsInDenomAllowList`, `BlockedAddr`, or any recipient checker — they perform an unconditional `SubUnlockedCoins`/`AddCoins`: [6](#0-5) 

The EVM `bank` precompile's `sendNative` (at address `0x...1001`) resolves the caller's associated Sei address, computes usei/wei amounts, and calls `p.bankKeeper.SendCoinsAndWei` directly — the same unguarded primitive: [7](#0-6) 

Because a tokenfactory `factory/{creator}/{subdenom}` coin can be held by an EVM-associated account (e.g., minted to it, or received before being placed on the deny side of the allow list), calling `bank.sendNative` on this precompile moves the coin using `SendCoinsAndWei`, which contains no allow-list check. The only "gate" that exists (`IsInDenomAllowList`) is bound to the `x/bank` `MsgSend`/`MsgMultiSend` message path, not to the shared transfer primitive, mirroring the Nextcloud pattern where the ACL was checked on one operation (open/move) but not on the semantically equivalent alternate operation (copy) that reaches the same underlying data.

### Impact Explanation
This allows any account holding an `AllowList`-restricted tokenfactory denom to bypass the denom admin's compliance/whitelist enforcement (used for regulated or permissioned tokens) by routing the transfer through the EVM `bank` precompile instead of a native `MsgSend`. This is an "unauthorized transfer via precompile" — assets move to/from addresses the admin explicitly intended to block, directly undermining the guarantees tokenfactory `AllowList` is documented to provide.

### Likelihood Explanation
Any EVM account that (a) is address-associated and (b) holds a restricted tokenfactory denom can trigger this by simply calling `sendNative` on the bank precompile with a non-allow-listed recipient — no special privileges, validator cooperation, or unusual state are required. This is directly reachable by an ordinary transaction sender.

### Recommendation
Move the `IsInDenomAllowList`/`BlockedAddr` checks down into the shared `SendCoins`/`SendCoinsAndWei`/`InputOutputCoins` primitives in `sei-cosmos/x/bank/keeper/send.go` (or add an equivalent check inside `precompiles/bank/bank.go`'s `sendNative`/`send`), so that every fund-movement path — native `MsgSend`, EVM precompile `sendNative`, and any future CW/IBC transfer path — enforces the denom's allow list uniformly, instead of relying on each caller to remember to check it.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/{admin}/restricted` and sets `AllowList{Addresses: [admin, allowedUser]}` via `MsgUpdateDenom`/`MsgCreateDenom`.
2. Admin mints the denom to an EVM-associated account `X` (X is in/out of the allow list is irrelevant to this step).
3. Attacker/`X` calls the `bank` precompile's `sendNative(receiverNotOnAllowList)` with `value` set to the restricted-denom-equivalent usei/wei amount (the precompile only handles usei/wei natively — confirm the restricted denom flows through `HandlePaymentUseiWei`/`SendCoinsAndWei` for the target denom scenario relevant to the deployment).
4. The transfer succeeds despite `receiverNotOnAllowList` not being present in the denom's `AllowList`, whereas the same transfer attempted via native `MsgSend` would fail with `"... is not allowed to receive funds"` as shown in the existing test `TestSendReceiverNotInAllowList`. [8](#0-7)

		defer func() {

		k.ak.SetAccount(ctx, k.ak.NewAccountWithAddress(ctx, toAddr))
	}

	return nil
}

// recordNewAccounts dual-emits the legacy new-account counter and its OTel
// counterpart (bank_new_account). Runs from consensus-critical send paths, so
// a telemetry fault here must not panic into the caller.
func recordNewAccounts(ctx context.Context, count int64) {
	if count <= 0 {
		return
	}
	defer func() {
		if e := recover(); e != nil {
			fmt.Fprintf(os.Stderr, "telemetry panic: %v\n%s", e, debug.Stack())
		}
	}()
	// TODO(PLT-353): remove once bank_new_account verified
	telemetry.IncrCounter(float32(count), "new", "account")
	bankMetrics.newAccount.Add(ctx, count)
}

func (k BaseSendKeeper) sendCoinsWithoutAccCreation(ctx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	err := k.SubUnlockedCoins(ctx, fromAddr, amt, checkNeg)
	if err != nil {
		return err
	}

	err = k.AddCoins(ctx, toAddr, amt, checkNeg)
	if err != nil {
		return err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, toAddr.String()),
			sdk.NewAttribute(types.AttributeKeySender, fromAddr.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, amt.String()),
		),
		sdk.NewEvent(
			sdk.EventTypeMessage,
			sdk.NewAttribute(types.AttributeKeySender, fromAddr.String()),
		),
	})

	return nil
}
