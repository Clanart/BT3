### Title
Same-chain `cancelOrder` permanently reverts and locks user escrow when a destination protocol fee is set - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` escrows the **protocol-fee-reduced** input amounts in `_orders[commitment][token]`, but `cancelOrder`'s same-chain path calls the shared `withdraw()` helper with the **original, un-reduced** `order.inputs` amounts. `withdraw()` unconditionally subtracts the caller-supplied `amount` from `_orders[commitment][token]` using Solidity 0.8's checked arithmetic. Whenever `protocolFeeBps > 0`, the subtracted amount is larger than what was actually escrowed, so the subtraction always underflows and reverts — permanently bricking cancellation and locking the user's escrowed funds, exactly the "subtraction assumes operand ≥ stored balance" invariant break described in the ActivePool report.

### Finding Description
In `placeOrder` (evm/tron/contracts/apps/IntentGatewayV2.sol:353-379, 456-457), when a destination protocol fee is configured, each input's escrowed amount is reduced: [1](#0-0) 
and only the reduced amount is credited to escrow: [2](#0-1) 

`cancelOrder`'s same-chain branch builds the withdrawal body directly from the caller-supplied, **unreduced** `order.inputs`: [3](#0-2) 

`withdraw()` then only checks that the escrow slot is non-zero (not that it covers `amount`), transfers `amount` to the beneficiary, and subtracts the same `amount` from the smaller stored escrow value: [4](#0-3) 

Because the contract targets `pragma solidity ^0.8.24` [5](#0-4) 
`_orders[body.commitment][token] -= amount` reverts on underflow whenever `amount` (the original pre-fee amount from `order.inputs`) exceeds the reduced value actually held in `_orders[commitment][token]`. This is unconditional for any order that had `protocolFeeBps > 0` at placement time — there is no legitimate input that avoids the revert, since `order.inputs` is fixed by the original order and can't be resubmitted with the reduced amount (the commitment hash is computed over the *reduced* inputs, so submitting reduced amounts in `order.inputs` would produce a different commitment and fail the `_filled`/`_orders` lookups instead).

### Impact Explanation
For a same-chain order placed while `protocolFeeBps > 0`, `cancelOrder` can never succeed: the low-level token transfer would send more than what is actually escrowed for that commitment (an accounting violation) and then the escrow-decrement always reverts, atomically undoing the transfer and reverting the whole call. The user's escrowed principal (and any escrowed `TRANSACTION_FEES`) becomes permanently unrecoverable if the order is never filled, since same-chain cancellation is the sole non-fill exit path in this contract for a same-chain order — there is no cross-chain `RefundEscrow`/`RedeemEscrow` message needed (and possible) here because source == destination. This is a direct, permanent loss/lock of user funds triggered by ordinary use of a documented protocol feature (destination protocol fees), reachable by any unprivileged user placing and later cancelling a same-chain order — matching the bounty's "stealing or loss of funds" / fund-lock impact class.

### Likelihood Explanation
High. Any state machine with a non-zero destination protocol fee (`_destinationProtocolFees[destinationHash]` or the fallback `_params.protocolFeeBps`) triggers this on every same-chain order that later needs cancellation (e.g., because no filler picks it up before expiry). No attacker collusion, malicious relayer, or governance compromise is needed — it is a pure logic bug reachable by a normal user through `placeOrder` + `cancelOrder`.

### Recommendation
Make `cancelOrder`'s same-chain path (and any other caller of `withdraw`) use the same protocol-fee-reduced amounts that were actually escrowed, e.g. recompute or persist `reducedInputs` and pass those into `WithdrawalRequest.tokens`, or have `withdraw()` read the amount to transfer directly from `_orders[commitment][token]` (bounded by, not overwritten by, the caller-supplied token list) rather than trusting an externally supplied `amount` at all. Additionally, `withdraw()` should validate `amount <= _orders[body.commitment][token]` (or simply transfer the full stored balance and zero it) instead of only checking for non-zero, removing the reliance on an implicit invariant that isn't guaranteed to hold.

### Proof of Concept
1. Governance sets `_destinationProtocolFees[keccak256(destination)]` (or `_params.protocolFeeBps`) to a non-zero value, e.g. 100 bps, via `RequestKind.UpdateParams`.
2. Alice calls `placeOrder` with a same-chain order (`order.source == order.destination`) and a single input of `1000` tokens.
   - `protocolFee = 1000 * 100 / 10000 = 10`
   - `reducedInputs[0].amount = 990`
   - Commitment is computed over `order.inputs = reducedInputs` (990), and `_orders[commitment][token] += 990` — escrow now holds 990.
   - `OrderPlaced` is emitted with `inputs = reducedInputs` (990), but the caller's original in-memory/calldata `order.inputs` still shows `1000` when Alice later reconstructs the same `Order` struct to cancel (she must supply the exact original `order` to reproduce the same `commitment`, since `commitment = keccak256(abi.encode(order))` was computed with `order.inputs` temporarily swapped to `reducedInputs` — but the caller must still know the original 1000-amount order for record-keeping/UI purposes, and any attempt to cancel with `order.inputs` set to 990 would produce a mismatched commitment hash and fail `_filled`/`_orders` lookups entirely, since the encoded order differs from what was hashed at placement. Only re-supplying the true original order with `inputs[0].amount = 1000` reproduces the correct `commitment`).
3. Alice (owner) calls `cancelOrder(order, options)` before the order is filled. Since `order.source == order.destination`, the same-chain branch runs and calls `withdraw({commitment, tokens: order.inputs /* amount = 1000 */, beneficiary: order.user}, true)`.
4. Inside `withdraw`: `_orders[commitment][token]` (990) is non-zero, so the check at line 691 passes; the contract sends `1000` tokens to Alice; then executes `_orders[commitment][token] -= 1000` where the stored value is `990` → underflow → revert (Solidity ^0.8 checked arithmetic).
5. The whole `cancelOrder` transaction reverts. Alice's 990 tokens remain escrowed in the contract with no way to ever successfully call `cancelOrder` again (the same underflow recurs every time), permanently locking her funds if no filler ever fills the order.
