### Title
Line-based partial-commit staging applies UI selection indices to a freshly re-fetched diff, allowing silent inclusion of unintended content in a commit - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop lets users stage a subset of a file's changes by selecting individual diff lines. The selection is stored as a set of line indices (`DiffSelection`) computed against the diff object that was rendered in the UI at selection time. When the commit is actually created, `applyPatchToIndex` in `app/src/lib/git/apply.ts` does not reuse that diff — it re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and blindly re-applies the stored line-index selection to it. If the working tree content differs between when the user made their line selection and when staging runs, the index-based selection no longer corresponds to the same lines, and the resulting patch can include or exclude the wrong content without any error — directly analogous to the report's core flaw of substituting a value computed under one context as an authoritative check/input in a different, stricter context.

### Finding Description
The commit flow is: `createCommit` (`app/src/lib/git/commit.ts:15-31`) calls `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex(repository, file)`: [1](#0-0) 

`applyPatchToIndex` re-fetches the diff independently of whatever diff the UI selection was built against: [2](#0-1) 

The patch content is generated in `formatPatch` by iterating this freshly-fetched diff's hunks and calling `file.selection.isSelected(absoluteIndex)` — i.e., the stored numeric line-index selection is applied against whatever hunk/line layout `getWorkingDirectoryDiff` returns *at commit time*, not the diff the user actually reviewed: [3](#0-2) 

Desktop's own code acknowledges that a diff "might have changed dramatically since last we loaded it" and that stale selections must be reconciled — but this reconciliation only happens opportunistically when the Changes view diff is reloaded (`updateChangesWorkingDirectoryDiff`), not immediately before staging/committing: [4](#0-3) 

There is no synchronization guarantee that the diff underlying the user's `DiffSelection` (line offsets/hunk structure) is the same diff that exists on disk at the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs. Between "user selects lines in the commit dialog" and "user clicks Commit," the working tree can change — e.g., a file watcher, an editor auto-save, a build tool, or (most importantly from a supply-chain angle) content changed by a hook or process triggered by a just-fetched/cloned repository, or a slow diff computation racing with a fast subsequent edit. Because `formatPatch` throws only if the resulting patch is completely empty (`app/src/lib/patch-formatter.ts:224-227`), a shifted-but-non-empty selection silently produces a patch for different lines than the user visually selected, and `git apply --cached` will happily apply it if it's still a valid unidiff against the new content.

### Impact Explanation
This breaks the invariant that "what the user visually selected to include in a commit is what gets committed." Because the mismatch is silent (no error unless the patch becomes completely empty or fails to apply outright), a user could commit/push content they did not intend to include — e.g., accidentally staging lines that were not visually checked, or omitting lines they thought were included. This matches the "silent corruption of what the user commits or pushes" impact category. It does not require local/physical access or malware — only a normal race between working-directory mutation and the commit action, which is well within attacker-influenceable territory for any workflow where file contents can be changed by external tooling (linters, formatters, git hooks, IDE auto-format-on-save) between diff-render and commit-click.

### Likelihood Explanation
Moderate. It requires a window where the working copy changes between the time the diff backing the UI's line selection was fetched and the time `createCommit` executes `stageFiles`. This is plausible in normal developer workflows (format-on-save, linters running in the background, slow network/disk causing UI diff staleness) and is explicitly anticipated by the code comment in `app-store.ts` about diffs changing "dramatically" — but the actual staging path in `apply.ts`/`patch-formatter.ts` performs no equivalent staleness check, so the class of bug the Desktop team already worried about for the UI selection state was never closed off for the staging code path itself.

### Recommendation
Before calling `applyPatchToIndex`/`stageFiles`, re-validate that the diff fetched for patch generation matches the diff the `DiffSelection` was computed from (e.g., by comparing a content hash/blob oid of the working file captured at selection time vs. staging time), and abort/re-prompt the user if they differ, rather than silently re-mapping line indices onto a different diff. Alternatively, pass the diff used to render the selection UI straight through to `applyPatchToIndex` instead of re-fetching, and only re-fetch (with mandatory re-validation of selection state) if that diff object was invalidated.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file so the Changes view shows a multi-hunk diff.
2. In the commit dialog, select for inclusion only specific lines from hunk A (leave hunk B unselected). Do not click Commit yet.
3. While the commit message is being typed (a window during which no diff re-fetch/selection re-validation occurs), have an external process — a save-on-format tool, a git hook, or another terminal — modify the file so that line offsets shift (e.g., insert lines above hunk A) without changing the total diff being empty.
4. Click Commit. `stageFiles` → `applyPatchToIndex` fetches a new diff reflecting the modified file and applies the old numeric-index selection (`file.selection.isSelected(absoluteIndex)`) to it.
5. Inspect the resulting commit (`git show`): it contains different line content than what was visually checked in step 2, with no error or warning shown to the user, demonstrating silent corruption of the intended commit contents.
