## Title
Webhook `shop_domain` header is not covered by HMAC verification, allowing cross-shop webhook spoofing - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

## Summary
`ShopifyApp::WebhookVerification` validates a webhook request by checking only the HMAC of the raw request body, but the `shop_domain` value that downstream app code uses to attribute the webhook to a specific merchant is read from an unauthenticated HTTP header that is never included in that HMAC computation. This is the same class of bug as the reported issue: a trusted verification step (HMAC signature check / on-chain deposit success) covers one piece of data, while a different, unverified identifier (`shop_domain` header / `inputs.owner` receiver address) is later assumed to belong to the same, correctly-authenticated party.

## Finding Description
`verify_request` computes the HMAC over `request.raw_post` only: [1](#0-0) 

`hmac_valid?` in `PayloadVerification` compares the HMAC of `data` (the raw body) against `ShopifyApp.configuration.secret`/`old_secret`: [2](#0-1) 

Critically, `shop_domain` is derived independently from the `X-Shopify-Shop-Domain` request header, which is not part of the signed payload at all: [3](#0-2) 

The gem's own documentation instructs developers to build custom webhook controllers that trust this value directly for tenant attribution, without any additional cross-check against the signed body: [4](#0-3) 

Because the shared secret used for the HMAC is a single app-level secret (not shop-specific), and the header carrying the shop identity is excluded from the signed data, a request with a **valid HMAC for shop A's payload** can be replayed with the `X-Shopify-Shop-Domain` header rewritten to shop B. `verify_request` still succeeds (the body/HMAC pair is legitimate), and any handler using the `shop_domain` helper (as the gem's own docs recommend) will process shop A's webhook data/action as if it originated from shop B — a cross-tenant confusion identical in nature to the reported bug, where a value assumed to be bound to the verified operation (owner address / signer) is actually an independent, attacker-influenced field.

## Impact Explanation
An app author following the documented `ShopifyApp::WebhookVerification` pattern will key business logic (e.g., background jobs enqueued with `shop_domain:`) on a header that is not authenticated by the HMAC check. This enables cross-shop data injection/corruption: a malicious or compromised merchant who can capture one legitimately-signed webhook for their own shop can relabel it to another shop's domain and have the app process it as that other shop's event, potentially triggering state changes, data overwrites, or unauthorized job execution scoped to a shop the attacker doesn't control.

## Likelihood Explanation
Medium: exploitation requires the attacker to have (or capture) at least one genuine, HMAC-valid webhook payload for a shop they control (trivial for any app-installing merchant, since they can install the app on their own dev/test shop and intercept the webhook their own store receives), then replay it against the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret material needs to be forged; only the unauthenticated header needs to be changed. The impact is gated by how the consuming application uses `shop_domain`, but the gem provides and documents this exact unsafe pattern for custom controllers.

## Recommendation
Do not treat the `X-Shopify-Shop-Domain` header as trusted merchant identity on its own. Either:
- Derive the shop from data that is actually covered by the HMAC (i.e., parse it out of the signed raw body, as `ShopifyAPI::Webhooks::Request#shop` does for the built-in `WebhooksController`), or
- Extend `hmac_valid?`/`verify_request` to bind the `shop_domain` header into the HMAC computation (e.g., verify `"#{shop_domain}#{data}"` or otherwise incorporate the header into the signed input) so a mismatched replay fails verification.

Update the documented custom-controller example (`docs/shopify_app/webhooks.md`) accordingly so app developers don't propagate the unsafe pattern.

## Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com` and enable a webhook topic the custom controller handles.
2. Capture a real webhook delivery from Shopify to the app's endpoint; it includes a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared secret, and an `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` header.
3. Replay the exact same request to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) recomputes the HMAC over the unmodified raw body and it still matches the shared secret, so the request passes.
5. The custom controller (as documented) calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`, where `shop_domain` now returns `"victim-shop.myshopify.com"` — the attacker's payload is processed under the victim shop's identity.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
