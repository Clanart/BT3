## Finding

The Hyperbridge analog of the audit's "missing `_owner` validation" bug-class is not the constructor-time misconfiguration itself, but a much stronger variant: **the `HostManager` module that receives cross-chain governance instructions never authenticates *which* module on the Hyperbridge parachain sent the request — only that it came from the Hyperbridge chain at all.** This lets an unprivileged sender on the source parachain forge governance actions that drain host revenue or permanently brick the host's admin role.

### Title
Missing module/app-identity binding in `HostManager.onAccept` allows arbitrary fund withdrawal and admin bricking - (File: `evm/src/core/HostManager.sol`)

### Summary
`HostManager.onAccept` is the sole entrypoint through which cross-chain governance instructions (`Withdraw` and `SetHostParam`) reach `EvmHost`. It checks only that the incoming `PostRequest.source` equals the Hyperbridge parachain id, but never checks `request.from` (the specific module/pallet address on that chain authorized to issue governance). Any account capable of dispatching an ISMP `PostRequest` from the Hyperbridge state machine to this contract's address can therefore trigger a `Withdraw` to an attacker-chosen beneficiary or a `SetHostParam` that sets `admin` to `address(0)`.

### Finding Description
`onAccept` performs a single authorization check: [1](#0-0) 

This validates the source *chain*, but not the sending *module*. Compare this with `IntentGatewayV2`, which explicitly binds request identity to a specific known module address before acting on the payload: [2](#0-1) 

`HostManager` has no equivalent `authenticate()`/`request.from` check. Once past the (incomplete) check, the decoded action is executed with no further validation: [3](#0-2) 

For `Withdraw`, `withdrawParams` (token, beneficiary, amount) is taken verbatim from the request body and forwarded to `EvmHost.withdraw`, which itself only checks that the caller is `hostManager` — it trusts that `HostManager` has already authenticated the true origin of the instruction: [4](#0-3) 

For `SetHostParam`, the decoded `HostParams` flow into `updateHostParamsInternal`, which validates `hostManager`, `handler`, and `consensusClient` (non-zero, code, ERC165) but performs **no validation whatsoever on `params.admin`**: [5](#0-4) 

This is the direct analog of the report's core defect ("missing validation of the owner argument … could permanently lock owner role"): `admin` is copied straight into storage with no zero-address or sanity check, so a `SetHostParam` action with `admin = address(0)` (or any wrong address) permanently and irreversibly removes the only privileged account that can freeze/unfreeze the host or (on `TestnetHost`) call `updateHostParams` directly — requiring a full redeploy exactly as described in the report.

### Impact Explanation
Because the module-identity check is missing, an attacker who can get *any* message accepted as coming from the Hyperbridge parachain (not necessarily the specific governance pallet — any dispatching account/pallet on that chain, or any account capable of triggering a cross-chain call routed to this dest module) can:
1. Call `Withdraw` with an arbitrary `beneficiary` and `amount`, draining the host's collected fee-token/native revenue to themselves — direct theft of bridge funds.
2. Call `SetHostParam` with `admin = address(0)`, permanently bricking the admin role (freeze/unfreeze and testnet governance paths lost), matching the report's "indefinitely lock owner role" impact but on a live production bridge contract.

Both fall squarely within the bounty's accepted impacts: stealing/loss of funds and unauthorized execution via a missing module-identity binding on the request path, which the task's pivots explicitly call out ("Request … paths must bind chain id, module/app identity … on both Substrate and EVM").

### Likelihood Explanation
The check that exists (`request.source.equals(hyperbridge)`) only constrains the source *chain*, which is a broad, multi-tenant execution environment (a full parachain hosting many pallets/accounts). Nothing in `HostManager` constrains which account/module on that chain is allowed to originate governance instructions, so the missing check is a structural gap rather than a theoretical edge case — it is reachable by any entity able to originate a recognized ISMP message from the source chain, without needing a malicious relayer, prover, or leaked admin key.

### Recommendation
Add an explicit binding of `request.from` to a known/expected governance module address (mirroring the pattern already used in `IntentGatewayV2.authenticate`), and reject any request whose `from` does not match the configured governance pallet identifier. Additionally, add zero-address/sanity validation for `params.admin` inside `updateHostParamsInternal`, consistent with the existing checks already applied to `hostManager`, `handler`, and `consensusClient`.

### Proof of Concept
1. Attacker (any account able to dispatch a recognized ISMP `PostRequest` from the Hyperbridge state machine) crafts a `PostRequest` with `source = hyperbridge`, `dest` = the target `HostManager` address, `from` = attacker-controlled bytes (unchecked), and `body = abi.encodePacked(uint8(OnAcceptActions.Withdraw), abi.encode(WithdrawParams{token: feeToken, beneficiary: attacker, amount: fullBalance}))`.
2. The relayer submits the message through the normal ISMP proof-verified `handleIncoming` path on `EvmHost`; verification succeeds because the message genuinely originates from the Hyperbridge chain (only the chain id is checked).
3. `EvmHost` calls `HostManager.onAccept`; the `restrict(_params.host)` check passes (caller is the host), and `request.source.equals(hyperbridge)` passes.
4. `HostManager` decodes the `Withdraw` action and calls `EvmHost.withdraw(withdrawParams)`, transferring the host's entire fee-token balance to the attacker's `beneficiary` address — no further authorization is performed by `EvmHost.withdraw` beyond `msg.sender == hostManager`, which is satisfied.
5. Alternatively, replace the action with `SetHostParam` and `admin = address(0)` to permanently disable the freeze/testnet-admin path, reproducing the report's "indefinitely lock owner role" outcome on-chain.

        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
