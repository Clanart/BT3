## Analog Found: VC (Verified Credential) revocation can be indefinitely front-run/blocked by the credential holder

### Title
Verified Credential holder can indefinitely evade provider revocation by front-running with self-spends of the VC coin - (File: `chia/wallet/vc_wallet/vc_wallet.py`, `chia/wallet/vc_wallet/vc_drivers.py`)

### Summary
The Telcoin bug lets a malicious staker block a privileged `slash` call forever by front-running it with a cheap `stake(1)` self-transaction that changes account state the slashing check depends on. Chia's Verified Credential (VC) revocation flow has the same structural weakness: the DID "provider" revokes a VC by building a spend that targets a *specific, currently-unspent VC coin*, but the VC holder can unilaterally and cheaply cycle/re-spend that same coin at any time (no provider cooperation required), invalidating the provider's already-built revoke spend and forcing the provider to restart the process — a race the holder can win indefinitely.

### Finding Description
`VCWallet.revoke_vc()` looks up the current VC coin from a given parent id, then builds a revocation spend against that specific coin: [1](#0-0) 

The revocation spend itself is constructed in `VerifiedCredential.activate_backdoor()`, which creates a `CoinSpend` for `self.coin` (the exact, specific VC coin identified moments earlier) using the "hidden puzzle backdoor," authorized by the provider's DID announcement: [2](#0-1) 

Meanwhile, the VC holder can spend/cycle their own VC singleton at will and cheaply via the standard (non-revoking) path, without any DID/provider cooperation, using `standard_magic_condition()`/`do_spend()`: [3](#0-2) [4](#0-3) 

This self-spend is exposed to the wallet user through `VCWallet.generate_signed_transaction()` (e.g. adding proofs, moving to a new puzzle hash, or self-revoking): [5](#0-4) 

Because the provider's `revoke_vc()` spend is built against one immutable coin (identified before broadcast), if the VC holder observes the pending revoke transaction in the mempool (or simply spends preemptively every time a provider might attempt revocation) and submits their own cheap self-spend of the same coin first, the coin the provider's revoke spend targets is consumed, and the provider's transaction becomes an unspendable/invalid double-spend on that coin. `VerifiedCredential.get_next_from_coin_spend()`, used to resync the current VC state, will simply produce a new coin state; the provider must re-fetch and rebuild the revoke transaction, targeting the new coin — and the holder can repeat the same defensive self-spend again. This mirrors Bob's `stake(1)` front-run of `slash()` exactly: an account/coin state modification, entirely controlled by the party being disciplined, is used to repeatedly invalidate the privileged party's already-constructed action.

### Impact Explanation
Revocation is the sole security mechanism intended to immediately and unilaterally strip a credential from a holder who should no longer be trusted (analogous to `slash` in the Telcoin case). A holder who can indefinitely evade revocation can continue using their VC to satisfy CR-CAT `authorized_providers`/proof checks (see `chia/wallet/vc_wallet/cr_cat_drivers.py` and `chia/wallet/trade_manager.py::check_for_final_modifications`) and participate in credential-restricted offers/trades after they should have been cut off. This is a bypass of an authorization/trust-boundary control rather than a "no impact" griefing nuisance, since it enables continued unauthorized use of CR-CAT assets/offers gated on that credential.

### Likelihood Explanation
Exploitation requires only that the VC holder monitor for provider revoke attempts (mempool visibility, exactly as in the Telcoin PoC) and hold priority to get their own cheap self-spend confirmed first — no special privileges beyond normal wallet operation and fee competition are needed. This is entirely reachable by an unprivileged VC holder against a legitimate DID/provider.

### Recommendation
Do not rely on referencing a single fixed "current" VC coin captured before broadcast. Instead:
- Have the provider always re-derive the latest unspent VC coin at broadcast time and retry automatically/atomically (e.g. within the same block via mempool composition) rather than depending on a stale coin id that a self-spend can invalidate between fetch and confirmation.
- Consider adding a puzzle-level mechanism that lets the provider commit an announcement/lock that prevents the holder's ordinary (non-revoke) cycle spend from being accepted once a revoke is in-flight for that coin, similar to how the recommendation in the Telcoin report suggests bypassing the vulnerable check specifically for the privileged action.

### Proof of Concept
1. Provider (DID holder) observes it needs to revoke a VC and calls `vc_revoke` RPC with `vc_parent_id` pointing at the VC's current parent, per `chia/cmds/wallet_funcs.py::revoke_vc` / `WalletRpcApi.vc_revoke`.
2. `VCWallet.revoke_vc()` fetches the VC's current coin state and builds a spend of that exact coin via `activate_backdoor()` [6](#0-5) , then broadcasts.
3. VC holder, monitoring the mempool, submits (with sufficiently high fee/priority) a self-spend of the same VC coin using `generate_signed_transaction()` with `self_revoke=False` and no proof changes (a trivial cycle), consuming the coin the provider's spend targets.
4. Provider's transaction fails because the targeted coin no longer exists as an unspent coin; provider must re-fetch VC state and rebuild the revoke transaction (`revoke_vc` again against the new coin).
5. Holder repeats step 3 indefinitely, always spending their own coin moments before the provider's rebuilt revoke transaction lands, permanently evading revocation while continuing to use the VC for CR-CAT/offer authorization.

        """
        Entry point for two standard actions:
         - Cycle the singleton and make an announcement authorizing something
         - Update the hash of the proofs contained within the VC (new_proof_hash is not None)

        Returns a 1 - 3 TransactionRecord objects depending on whether or not there's a fee and whether or not there's

            raise ValueError("Memos not currently supported for VC wallets")

        if coins is not None:

            potential_vc_record = await self.store.get_vc_record_by_coin_id(coin_id)

        elif potential_vc_id is not None:
            vc_record = await self.get_vc_record_for_launcher_id(potential_vc_id)
            lookup_info = ("launcher ID", potential_vc_id)
        else:
            raise ValueError("Must specify either a vc_id or a specific VC coin")

        if vc_record.confirmed_at_height == 0:

                "is not confirmed, please try again later."

        inner_puzzle: Program = await self.standard_wallet.puzzle_for_puzzle_hash(inner_puzhash)

            CreateCoin(puzzle_hashes[0], uint64(vc_record.vc.coin.amount), [puzzle_hashes[0]])

        if fee > 0:

            await self.wallet_state_manager.main_wallet.create_tandem_xch_tx(

                action_scope,
                extra_conditions=(AssertCoinAnnouncement(asserted_id=coin_name, asserted_msg=coin_name),),

            magic_condition = vc_record.vc.magic_condition_for_new_proofs(new_proof_hash, provider_inner_puzhash)
        elif self_revoke:
            magic_condition = vc_record.vc.magic_condition_for_self_revoke()
        else:
            magic_condition = vc_record.vc.standard_magic_condition()
        extra_conditions = (*extra_conditions, UnknownCondition.from_program(magic_condition))

    def do_spend(

        Note that the inner puzzle is already expected to output the 'magic' condition (which can be created above).

            self.singleton_lineage_proof,

                        inner_puzzle,
                        inner_solution,

                ]
            ),
        )

    def activate_backdoor(
        self, provider_innerpuzhash: bytes32, announcement_nonce: bytes32 | None = None
    ) -> tuple[CreatePuzzleAnnouncement, CoinSpend]:
        """
        Activates the backdoor in the VC to revoke the credentials and remove the provider's DID.

        Returns the announcement we expect from the provider's DID authorizing this, and the spend of the VC.
        Sync attempts by this class on spends generated by this method are expected to fail. This could be improved in
        the future with a separate type/state of VC that is revoked, but perfectly useful as a singleton.
        """
        vc_solution: Program = solution_for_singleton(
            self.singleton_lineage_proof,
            uint64(self.coin.amount),
            Program.to(
                [  # solve EML
                    solve_revocation_layer(
                        self.hidden_puzzle(),
                        solve_std_vc_backdoor(
                            self.launcher_id,
                            Program.to((self.proof_provider, self.proof_hash)).get_tree_hash(),
                            self.construct_transfer_program().get_tree_hash(),
                            self.inner_puzzle_hash,
                            uint64(self.coin.amount),
                            self.eml_lineage_proof,
                            provider_innerpuzhash,
                            self.coin.name(),
                            announcement_nonce,
                        ),
                        hidden=True,
                    ),
                ]
            ),
        )

        expected_announcement: CreatePuzzleAnnouncement = CreatePuzzleAnnouncement(
            std_hash(self.coin.name() + Program.NIL.get_tree_hash() + ACS_TRANSFER_PROGRAM.get_tree_hash())
        )

        return (
            expected_announcement,
            make_spend(self.coin, self.construct_puzzle(), vc_solution),
        )
