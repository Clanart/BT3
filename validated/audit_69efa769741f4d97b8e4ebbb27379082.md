### Title
Consensus-incentive reward misattribution — a batch's entire multi-chain reward is paid to whoever's message happens to sit at index 0 - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::on_executed` recovers the relayer identity to be paid from a single message — `messages[0]` — but then pays out a reward for **every** `StateMachineUpdated` event produced by the whole batch, regardless of which message in the batch actually produced that event. This is the same class of bug as the AI Arena `reRoll` issue: a parameter used to key a payout/limit computation (`fighterType` there, "the message believed to belong to the signer" here) is not bound to the actual entity that produced the value being paid out.

### Finding Description
`FeeHandler::on_executed` is invoked by `pallet-ismp` once per processed batch of messages, receiving the full `Vec<MessageWithWeight>` submitted in that call and the full `Vec<IsmpEvent>` produced by processing all of them: [1](#0-0) 

The relayer to be paid is derived **only** from `messages.get(0)`: [2](#0-1) 

The code then collapses every `StateMachineUpdated` event in the entire batch (which can span multiple, unrelated `state_machine_id`s if the batch contains multiple `ConsensusMessage`s) and pays the computed block-span reward for **each** state machine to that single signer: [3](#0-2) 

`process_message`/`calculate_reward` compute the reward purely from `(latest_height - LastRewardedHeight[state_machine_id])  × CostPerBlock[state_machine_id]` — there is no check tying the specific `state_machine_id`/height span back to a message actually signed by `relayer_account`: [4](#0-3) 

Because `handle_unsigned` accepts an arbitrary `Vec<Message>` in one unsigned extrinsic (`ensure_none` origin — no signer/permission check on who assembles the batch), any account can build a batch consisting of:
1. A trivial/cheap `ConsensusMessage` they sign themselves, placed first (`messages[0]`).
2. One or more *other, independently valid* `ConsensusMessage`s (freely obtainable/public consensus proofs, or another relayer's already-broadcast unsigned message) that advance other state machines with large `LatestHeight - PreviousHeight` spans and high `CostPerBlock`.

Each `ConsensusMessage` is validated on its own cryptographic/consensus merits (the `signer` field only proves whoever assembled the message holds a keypair whose signature covers the proof hash — it is not tied to who originally produced/discovered the proof, since "these proofs can be generated by anyone" per the protocol's own design). The pallet-ismp message handler processes and accepts each message independently; nothing requires all messages in a batch to share the same signer, and nothing ties a given `StateMachineUpdated` event back to the specific message that produced it before rewarding. The result: the attacker's `messages[0]` signature captures 100% of the reward for every `StateMachineUpdated` event in the batch, including large-span updates they did not "earn" credit for under the intended per-submission attribution model.

### Impact Explanation
This lets an unprivileged network participant redirect `$BRIDGE` treasury payouts (and the associated non-transferable reputation asset, which feeds collator selection) that should be split across the actual submitters of each consensus update to a single attacker-controlled account, by packaging a cheap self-signed consensus message alongside other genuinely-delivered, high-value consensus updates into one unsigned extrinsic. This is a direct "unauthorized transaction/wrong beneficiary" fund-diversion from the Hyperbridge treasury and a manipulation of the reputation-based collator-selection mechanism — squarely within the bounty's "stealing or loss of funds" / "logic attacks" categories, and does not require a malicious relayer, prover, or governance actor — only an ordinary user capable of submitting an unsigned extrinsic with an assembled `Vec<Message>`.

### Likelihood Explanation
Likelihood is moderate-to-high: consensus proofs are explicitly documented as public/freely obtainable, `handle_unsigned` has no origin restriction beyond `ensure_none`, and nothing in `on_executed` restricts the number or diversity of `ConsensusMessage`s in a single batch or ties the paid `state_machine_id`s to the specific message that advanced them. The main uncertainty (not fully verifiable without deeper review of `pallet_ismp::handle_unsigned`/`validate_unsigned` in `modules/pallets/ismp/src/lib.rs`, which I could not fully inspect before running out of tool calls) is whether the runtime's `validate_unsigned`/txpool rules restrict batches to a single `ConsensusMessage` per extrinsic or otherwise constrain composition; if such a restriction does not exist, the path is directly exploitable as described.

### Recommendation
In `on_executed`, attribute each `StateMachineUpdated` event's reward to the signer of the specific `ConsensusMessage` that produced it, not to `messages[0]`. Concretely: iterate `messages`, and for each `Message::Consensus` entry, recover its own signer and only credit reward for the `state_machine_id`(s)/height advances that can be attributed to that particular message's consensus proof (e.g., by matching proof height ranges/state machine ids to what each individual `ConsensusMessage` actually proves), rather than crediting one recovered signer for the union of all events in the batch.

### Proof of Concept
1. Attacker generates their own ed25519/sr25519 keypair `K_attacker` and constructs `ConsensusMessage_A`: a trivially cheap consensus proof (e.g., a state machine with `CostPerBlock` set to a low/zero value, or a span of 1 block) and signs `keccak256(consensus_proof_A)` with `K_attacker`.
2. Attacker observes (or independently reconstructs, since proofs are public) a second, unrelated, high-value `ConsensusMessage_B` for a different `state_machine_id` with a large pending `LatestHeight - PreviousHeight` and high `CostPerBlock` — e.g., copies a currently-pending unsigned consensus message from the txpool or produces their own valid proof for that chain.
3. Attacker submits a single `pallet_ismp::handle_unsigned(origin: None, messages: vec![ConsensusMessage_A, ConsensusMessage_B])` extrinsic (or equivalent through whichever entrypoint invokes `FeeHandler::on_executed` with both messages processed together).
4. `pallet-ismp` processes both messages, emits `StateMachineUpdated` for state machine A and state machine B, and invokes `on_executed(messages, events)`.
5. `on_executed` inspects only `messages[0]` (`ConsensusMessage_A`, signed by `K_attacker`) to recover `relayer_account = attacker`.
6. It then loops over `highest_per_state_machine` built from **all** events (A and B) and calls `process_message` for both, transferring the treasury-funded reward for **both** state machine A's and B's block-span to `attacker`'s account, and minting reputation for both, even though the attacker did not independently earn/attribute the B-side reward under the "first relayer to submit a proof" model documented in `docs/content/developers/explore/relayers.mdx:79-81`.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
