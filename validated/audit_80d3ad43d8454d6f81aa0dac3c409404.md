### Title
`deny_list` EVM RPC method admission control is never applied to the WebSocket transport, allowing full bypass via `ws://` connections - ([File: evmrpc/rpcstack.go])

### Summary
The EVM JSON-RPC `deny_list` feature is meant to block sensitive/expensive methods (e.g. `debug_traceBlockByNumber`) from being invoked at all, "to fail fast" per the config documentation. This access-control list is registered only on the HTTP RPC server and is never wired into the WebSocket server, so any client can bypass it completely by connecting over the WS endpoint instead of HTTP and calling the same denied method.

### Finding Description
`HTTPConfig` carries a `DenyList []string` field, and `EnableRPC` (the HTTP JSON-RPC path) explicitly registers it on the underlying `rpc.Server`: [1](#0-0) [2](#0-1) 

`WsConfig`, by contrast, has no `DenyList` field at all, and `EnableWS` creates its own independent `rpc.Server` instance and registers the same APIs on it, but never calls `srv.RegisterDenyList(...)`: [3](#0-2) [4](#0-3) 

This is confirmed by the wiring in `evmrpc/server.go`: the WS server is built with the identical API set (`NewBlockAPI`, `NewTransactionAPI`, `NewInfoAPI`, `NewSendAPI`, `NewSimulationAPI`, etc., all under the same `EthNamespace`) that the HTTP server exposes, but `wsConfig` is populated only with origins, read limits, and admission timeouts — `config.DenyList` is never copied into it or applied to the WS `rpc.Server`: [5](#0-4) 

The only place `RegisterDenyList` is invoked anywhere in `evmrpc` is inside `EnableRPC` for the HTTP path: [6](#0-5) 

Because the WS handler dispatches through go-ethereum's `rpc.Server` machinery with its own deny-list state (empty), any method an operator intends to block — including expensive `debug_*`/`eth_*` trace or simulation methods that the deny list exists specifically to fail fast on — remains fully callable over `ws://`/`wss://`. This mirrors the CVE's bug class: an access-control gate that is evaluated on one code path/transport but not consistently enforced across all paths that reach the same protected resource, letting the check be bypassed entirely by switching to the unguarded path (in the CVE, a second query on a kept-open connection; here, the WS transport instead of HTTP).

### Impact Explanation
An operator who configures `deny_list` to block resource-intensive or otherwise sensitive JSON-RPC methods on a public RPC node gets no protection against a client that simply connects via WebSocket. Since the deny list's stated purpose is to "fail fast" and shed load/risk from specific methods (e.g., trace/debug methods that are otherwise gated by separate config knobs like `MaxConcurrentTraceCalls`), a client can drive unbounded calls to denylisted methods purely by using WS, potentially causing resource exhaustion or a crash of a default-configuration public RPC node — the same outcome the deny list was deployed to prevent.

### Likelihood Explanation
High. No privilege or special access is required: any public RPC client can dial the WS endpoint (`ws_enabled` is on by default for full/archive nodes per the registry test) and issue the exact denylisted method call that would be rejected on the HTTP endpoint. There is no additional precondition beyond enabling WS, which is the node's normal, default-configuration public serving mode.

### Recommendation
Add a `DenyList []string` field to `WsConfig`, thread `config.DenyList` through in `evmrpc/server.go` when constructing `wsConfig`, and call `srv.RegisterDenyList(method)` for each entry inside `EnableWS`, exactly as `EnableRPC` does for the HTTP `rpc.Server`. Add a regression test analogous to the existing deny-list HTTP test but asserting the same rejection over the WS transport.

### Proof of Concept
1. Start a node with `evmrpc` HTTP and WS both enabled and `deny_list = ["debug_traceBlockByNumber"]` in `app.toml`.
2. Send `{"jsonrpc":"2.0","id":1,"method":"debug_traceBlockByNumber","params":[...]}` over HTTP — the request is rejected because `EnableRPC` registered the deny list on its `rpc.Server` via `srv.RegisterDenyList("debug_traceBlockByNumber")`.
3. Open a WebSocket connection to the same node's WS port and send the identical JSON-RPC payload — the call succeeds and executes normally because `EnableWS`'s `rpc.Server` never received any `RegisterDenyList` call, fully bypassing the operator-configured access control.

// EnableWS turns on JSON-RPC over WebSocket on the server.
func (h *HTTPServer) EnableWS(apis []rpc.API, config WsConfig) error {
	h.mu.Lock()
	defer h.mu.Unlock()

	if h.wsAllowed() {
		return fmt.Errorf("JSON-RPC over WebSocket is already enabled")
	}
	// Create RPC server and handler.
	srv := rpc.NewServer()
	srv.SetBatchLimits(config.batchItemLimit, config.batchResponseSizeLimit)
	readLimit := effectiveMaxRequestBodyBytes(config.readLimit)
	srv.SetReadLimits(readLimit)
	// maxConcurrentRequestBytes is passed through raw; rpc.Server.recomputeWSConcurrentBudget
	// raises it to readLimit when smaller, matching
	// newRequestSizeLimiter's max(budget, maxBody) rule on the HTTP protocol.
	srv.SetWSConcurrentRequestBytes(config.maxConcurrentRequestBytes)
	srv.SetWSAdmissionTimeout(config.wsAdmissionTimeout)
	srv.SetWSAdmissionEventHook(func(reason string) {
		// Hook carries no request context, and the fork's own connCtx is context.Background() too.
		recordWSAdmissionRejected(context.Background(), reason)
	})
	logger.Info("Registering apis for evm websocket")
	if err := RegisterApis(apis, config.Modules, srv); err != nil {
		return err
	}
	h.WsConfig = config
	h.wsHandler.Store(&rpcHandler{
		Handler: NewWSHandlerStack(srv.WebsocketHandler(config.Origins), config.JwtSecret),
		server:  srv,
	})
	return nil
}
