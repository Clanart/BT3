## Finding: Copilot conflict-resolution hunk splicer desyncs from the hunk extractor on marker-like content, causing wrong resolution text to be committed

### Title
Divergent conflict-marker parsers in Copilot merge-conflict resolution cause a hunk-resolution to be spliced into the wrong conflict block - ([File: app/src/lib/copilot-conflict-context.ts](), [File: app/src/lib/copilot-conflict-resolution.ts]())

### Summary
Desktop's Copilot-assisted conflict resolution uses two independently written line-walkers over the *same* raw conflicted file: `extractConflictHunks` (builds the prompt / hunk count) and `reassembleResolvedFile` (splices the model's per-hunk resolutions back into the file, matched purely by array order). They implement different rules for what counts as a valid `<<<<<<< / ======= / >>>>>>>` block, so a file whose ours/theirs content happens to contain a line that merely *looks like* a marker (e.g. a `>>>>>>>` sequence from quoted text, ASCII art, or `>>>>>>>` chevrons) is parsed as N hunks by one function and a different set of hunks by the other, while both report the same *count*. `validateResolutionPaths` only checks hunk counts match, not hunk identity/position, so the mismatch is never caught, and the model's resolution for one conflict is spliced into a different conflict's location.

### Finding Description
`extractConflictHunks` [1](#0-0)  ends "ours" collection only on a `baseMarker` or `separatorMarker` line; it does **not** treat a stray `>>>>>>>`-looking line inside the ours/base content as anything special.

`reassembleResolvedFile`, which walks the identical raw file to decide where to splice resolutions, does the opposite: its lookahead scans forward from `<<<<<<<` for *either* a separator or a closing marker, and stops at whichever it meets first [2](#0-1) :
```
for (let j = i + 1; j < lines.length; j++) {
  if (reassemblySeparatorMarker.test(lines[j])) { hasSeparator = true }
  else if (reassemblyTheirsMarker.test(lines[j])) { closingIndex = j; break }
}
```
If a `>>>>>>>`-shaped line appears inside the "ours" section *before* the real `=======`, this loop hits the theirs-marker pattern first, `hasSeparator` stays `false`, and the block is judged malformed: `<<<<<<<` and everything from that point up to (but not including) the real conflict resolution is instead copied through verbatim as "regular content" [3](#0-2) . The next *real* conflict block in the file is then treated by `reassembleResolvedFile` as `hunkIndex 0`, even though `extractConflictHunks` correctly counted it as the file's second (or later) hunk when building the prompt.

Because `validateResolutionPaths` only compares hunk **counts**, not identity [4](#0-3) , this desync passes validation as long as the counts happen to line up (which they will whenever the spurious marker "eats" one real block and produces one fewer detected block on the reassembly side while the extractor still reports the true count, or vice versa in adjacent-block scenarios). The result: `hunkResolutions[hunkIndex]` — content the model wrote for a *different* conflict — gets spliced into the wrong location [5](#0-4) , and the block that `reassembleResolvedFile` skipped is left in the final file with its **literal, un-resolved `<<<<<<</=======/>>>>>>>` conflict markers still present**, since nothing after reassembly re-scans the whole file for leftover markers (the marker-content check in `parseCopilotConflictResolution` only inspects each *raw* hunk's resolved text before splicing, not the final reassembled file) [6](#0-5) .

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug driven entirely by content in a repository the user merges/rebases against — a crafted PR/branch is enough. Content that legitimately contains 7+ `>` characters at line start is not exotic (chevron ASCII banners, quoted-email/chat blocks, changelog dividers, template-heavy C++/Rust generics like `Foo<Bar<Baz>>>>>>>`). An attacker who controls the incoming branch/PR content can arrange for this pattern to sit inside one conflict's "ours" text, causing:
- One conflict block's resolution to be silently applied to a different, unrelated conflict location.
- Leftover raw `<<<<<<< / ======= / >>>>>>>` markers to remain in the committed file undetected by Desktop's Copilot resolution pipeline.

This directly matches the requested impact class "silent corruption of what the user commits or pushes," since the user reviews (at best) a summary/diff generated from the model's *intended* per-hunk mapping, not a re-verified reassembled file.

### Likelihood Explanation
Requires only that the user run Copilot-assisted conflict resolution on a merge/rebase/cherry-pick against attacker-influenced content — no local access, no elevated privileges, no prior compromise. The two parsing functions were clearly written independently (different variable names, different marker precedence, no shared helper), which is exactly the kind of "two components computing the same grouping/count differently" root cause the reference report calls out, and there is no existing guard that cross-checks hunk *identity* (only count) or re-validates the final reassembled file for leftover markers.

### Recommendation
- Replace the two independent line-walkers with a single shared conflict-block parser used both to build the prompt/hunk list and to drive reassembly, so hunk indices are guaranteed to refer to the same blocks in both directions.
- Have `reassembleResolvedFile` return the number of conflict blocks it found and assert it equals `hunkResolutions.length`; throw `CopilotValidationError` on mismatch instead of silently falling back to order-based splicing.
- After reassembly, re-scan the produced file content for residual conflict-marker patterns and fail the resolution (rather than silently writing it) if any are found.

### Proof of Concept
1. Attacker opens a PR/branch where a file's content (on the branch that will become "theirs") contains, inside what will end up as an ours/theirs hunk body, a line consisting of 7+ `>` characters followed by whitespace/EOL (e.g. a quoted chat/log excerpt or `Vec<Vec<Vec<Vec<Vec<Vec<Vec<T>>>>>>>`-style nested generics split so the closing chevrons land at line-start).
2. User merges/rebases the branch locally in Desktop, producing a real merge conflict in that file plus at least one other conflict elsewhere in the same file.
3. User invokes Copilot conflict resolution. `extractConflictHunks` correctly enumerates all real conflict blocks (unaffected by the theirs-marker-shaped line), producing the true count/order and prompt.
4. `reassembleResolvedFile` misparses the block containing the spurious `>>>>>>>`-shaped line as non-conflict content (copied through with real markers intact) and mis-indexes the remaining real block(s), so `hunkResolutions[0]` (intended for the first real conflict) gets spliced into what `extractConflictHunks` numbered as a later conflict.
5. `validateResolutionPaths` passes because hunk **counts** still match; the file is written to disk and staged/committed with the wrong resolution content in the wrong location and literal conflict markers left in the skipped block.
