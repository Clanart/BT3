### Title
`SignableTransaction::new` computes the fee bound and `MAX_STANDARD_TX_WEIGHT` limit over a dummy transaction that omits the OP_RETURN data output, so both limits fail to restrict the actual signed transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Olympus `setLimit()` bug — where `circulatingOhmBurned` is added on one side of the bound but never accounted for on the other, defeating the limit — `SignableTransaction::new` enforces two bounds (`needed_fee` covering the requested fee rate, and `weight <= MAX_STANDARD_TX_WEIGHT`) that are computed by `calculate_weight_vbytes` over a synthetic transaction containing **only** the payment outputs and optional change. The OP_RETURN output carrying caller-supplied `data` (up to 80 bytes) is pushed into `tx_outs` beforehand but is never included in the weight/vbyte accounting on which both limits are based.

### Finding Description
In `SignableTransaction::new`, the `data` argument is converted into an OP_RETURN `TxOut` and appended to `tx_outs` at lines 193-202, *before* the fee/weight calculation. However, both calls to `calculate_weight_vbytes` (lines 204 and 225-226) pass `payments` — not `tx_outs` — so the synthetic transaction used to derive `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check at line 241 never contains the OP_RETURN output.

Concretely, an 80-byte OP_RETURN output adds roughly 92 bytes (~368 weight units, ~92 vbytes) that are invisible to:

- `needed_fee = fee_per_vbyte * vbytes` (line 206): the caller-specified fee rate is charged for a smaller transaction than the one actually signed, so `fee()` (line 139, computed as `sum(inputs) - sum(outputs)`) delivers a lower effective sat/vbyte than requested.
- The minimum-relay-fee check (line 211): `needed_fee` is compared against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`, so a transaction constructed at exactly the minimum relay rate will underpay the true minimum by ~92 sat.
- The `MAX_STANDARD_TX_WEIGHT` check (line 241): `weight` excludes the OP_RETURN output, so the bound passes while the real transaction's weight exceeds it.

This is the same structural flaw as the audit finding: a restriction is checked against an accounting that omits one of the components it is supposed to bound, so the limit cannot actually limit.

### Impact Explanation
An unprivileged party can supply the `data` payload (in Serai's usage this corresponds to user-provided `InInstruction`/refund data embedded via `extract_serai_data`-driven flows and the OP_RETURN path exercised in `test_data`). The result is a fully signed transaction that is either below the node's minimum relay fee or above `MAX_STANDARD_TX_WEIGHT`, causing broadcast rejection — funds selected as inputs are locked into a transaction the network will not propagate, and the intended payment is never delivered despite a valid threshold signature being produced. Because the underestimation scales with the data length, callers paying for a specific fee rate are systematically underpaying.

### Likelihood Explanation
Any transaction created with a non-`None` `data` argument undercharges the fee and undercounts weight. Crossing the standardness boundary additionally requires the transaction to be near `MAX_STANDARD_TX_WEIGHT` (many inputs) or the fee rate to sit exactly at the relay minimum — realizable but not automatic, placing this at the lower end of Medium.

### Recommendation
Include the OP_RETURN output in the transaction passed to `calculate_weight_vbytes` — e.g., construct the synthetic `tx.output` from `tx_outs` (payments + OP_RETURN + optional change) rather than only `payments`, so `needed_fee`, the minimum-relay check, and the `MAX_STANDARD_TX_WEIGHT` bound are all evaluated against the actual signed transaction. Alternatively, add the serialized size of the data output to the computed weight/vbytes.

### Proof of Concept
Conceptual, from `networks/bitcoin/src/wallet/send.rs`:

```rust
// tx_outs includes the OP_RETURN output (lines 193-202):
tx_outs.push(TxOut {
  value: Amount::ZERO,
  script_pubkey: ScriptBuf::new_op_return(/* up to 80 bytes of data */),
});

// but the weight/fee basis is built ONLY from `payments` (line 204):
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
//   ^ data output is absent from this synthetic tx
```

Concretely: call `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), 1)` with `input_sat` such that `needed_fee` equals the relay minimum for the *true* vsize. `needed_fee` is computed for a tx ~92 vbytes smaller, so the signed transaction's effective fee falls below `DEFAULT_MIN_RELAY_TX_FEE` for its real vsize and Bitcoin Core rejects it; similarly, for a tx whose real weight is within ~368 WU of `MAX_STANDARD_TX_WEIGHT`, the check at line 241 passes while `tx.weight()` on the final `self.tx` exceeds the standardness limit.
