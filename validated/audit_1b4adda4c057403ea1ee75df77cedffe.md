### Title
Variable-time scalar multiplication of the secret DKG encryption key enables a timing-oracle key recovery — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to CVE-2023-5388 (timing side channel in RSA decryption recovering private data), PedPoP's ECDH decryption multiplies the participant's long-lived secret encryption key `enc_key` by an attacker-supplied curve point `msg.key` using the variable-time `C::G * C::F` multiplication inherited from curve25519-dalek. An unprivileged party who feeds crafted `EncryptedMessage` bytes to a victim's `calculate_share` / `decrypt` can measure the multiplication time to recover `enc_key`, and thereby decrypt every secret share ever encrypted to that participant.

### Finding Description
`Encryption::decrypt` computes the ECDH shared secret as `public * private` via `ecdh`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:95-97
fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}
```

`public` (`msg.key`) is fully attacker-controlled: it is deserialized from raw bytes in `EncryptedMessage::read` (`encryption.rs:171-176`) with only `C::read_G` (canonical/torsion-free) checks. The multiplication `C::G * C::F` for the dalek ciphersuites (`EdwardsPoint`, `RistrettoPoint`) is generated by the `math_neg!` macro in `crypto/dalek-ff-group/src/lib.rs:381`, which delegates to `DEdwardsPoint::mul`/`DRistrettoPoint::mul`. In curve25519-dalek, non-basepoint `Point * Scalar` is the documented *variable-time* Montgomery ladder — its doubling/addition schedule depends on the scalar's bits, and the scalar here is the victim's secret `enc_key`.

The custom points Serai itself ships avoid this: `ed448`'s `Point::mul` (`crypto/ed448/src/point.rs:233-272`) and `Scalar::pow` (`crypto/dalek-ff-group/src/lib.rs:201-236`) both use fixed-window `conditional_select` table lookups, making them constant-time. The bug is specifically that the PedPoP decryption path relies on the ciphersuite's generic `Mul` impl, which for the most commonly deployed ciphersuite (Ed25519) is variable-time over a secret scalar.

Crucially, the timing operation happens regardless of proof validity: in `Encryption::decrypt` (`encryption.rs:479-488`), the PoP Schnorr signature is only *queued* into the `BatchVerifier`, while `ecdh(&self.enc_key, msg.key)` executes immediately — so even messages that will later fail batch verification still trigger the secret-dependent multiplication. The attacker needs only a valid `EncryptedMessage` (they can produce a genuine PoP for their own ephemeral key) and an observable timing channel (e.g., a co-located attacker measuring response/processing latency, or a malicious coordinator/participant in the DKG who times share-processing).

### Impact Explanation
`enc_key` is a long-lived per-participant key created once per `SecretShareMachine` (`Encryption::new`, `encryption.rs:438`) and reused for all incoming shares. Recovering it via the timing oracle is key-share recovery in the concrete sense of the validation criteria: every `SecretShare` ciphertext addressed to the victim — including shares contributed by *honest, non-colluding* third parties — becomes decryptable by the attacker, collapsing the threshold secrecy of the resulting `ThresholdKeys`. Unlike the documented PoP-misuse concern in the code comments, this requires no error-oracle or blame disclosure; only passive timing of a routine `calculate_share` call. Severity: Medium, matching the CVE's CVSS 6.5 profile (network-reachable, no privileges, confidentiality + availability of the DKG affected).

### Likelihood Explanation
Reachability is direct: `processor` deserializes `EncryptedMessage::<C, SecretShare<C::F>>::read` from peer-supplied bytes and immediately calls `machine.calculate_share` (`processor/src/key_gen.rs:409-416`), which loops `self.encryption.decrypt(...)` over every attacker message (`crypto/dkg/pedpop/src/lib.rs:476-478`). The attacker controls `msg.key` bit-for-bit and can repeat the measurement as many times as needed across DKG attempts, since `enc_key` is regenerated per session but each session offers `n-1` decryption queries per participant set. Practical exploitation requires a measurable timing side channel against the victim node — the same constraint as CVE-2023-5388 — hence Medium rather than High.

### Recommendation
Perform the ECDH multiplication with a constant-time primitive: use a fixed-window `conditional_select` multiplication (as already implemented in `ed448`'s `Point::mul` and `Scalar::pow`) or dalek's `multiscalar_mul`/constant-time path for `public * private` inside `ecdh` in `crypto/dkg/pedpop/src/encryption.rs:95`. Additionally, consider moving `ecdh` after PoP verification or performing it in constant time regardless, since the queue-then-compute ordering in `Encryption::decrypt` (`encryption.rs:479-488`) makes even invalid ciphertexts trigger secret-dependent work.

### Proof of Concept
1. Attacker registers in a PedPoP `SecretShareMachine` session (or feeds bytes to `EncryptedMessage::read` where the processor accepts them), obtaining the victim's registered `enc_pub_key`.
2. For each probe, attacker chooses a scalar `k`, computes `key = G * k`, produces a valid PoP `SchnorrSignature::sign(&k, ...)` for `key`, and sends `EncryptedMessage { key, pop, msg }` via `generate_secret_shares`/`calculate_share`.
3. Victim executes `ecdh(&enc_key, key)` → `key * enc_key` using variable-time `EdwardsPoint * Scalar`. The attacker measures the victim's processing time per message.
4. By varying `key` (e.g., using points that amplify early-terminating or low-Hamming-weight windows in dalek's variable-base algorithm) and collecting many timing samples per DKG session/attempt, the attacker recovers the bits of `enc_key` statistically — exactly the decryption-side-channel methodology of CVE-2023-5388.
5. With `enc_key` recovered, the attacker recomputes `cipher(context, key * enc_key)` for every `EncryptedMessage` addressed to the victim — including shares from honest participants — recovering their secret shares and reconstructing the group private key below threshold.

The root cause is `crypto/dkg/pedpop/src/encryption.rs:95-97` invoking the variable-time `Mul` impl wired through `math_neg!` in `crypto/dalek-ff-group/src/lib.rs:381`, reached from `KeyMachine::calculate_share` in `crypto/dkg/pedpop/src/lib.rs:476-478` on fully attacker-controlled bytes from `EncryptedMessage::read` (`encryption.rs:171-176`).
