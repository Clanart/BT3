### Title
`ReferralStorage.trigger()` inflates `userInfos[*].rewardAmount` ledger with no corresponding MGP transfer into the contract, causing `claimReward()` to permanently revert for legitimate referrers once balance is exhausted - ([File: rewards/ReferralStorage.sol])

### Summary
`ReferralStorage.trigger()` is called by `MasterMagpie` every time a user harvests real MGP rewards with an active referral link, and it unconditionally increments `refererInfo.rewardAmount` and `refereeInfo.rewardAmount` by percentages of the harvested amount. No MGP tokens are ever transferred into `ReferralStorage` as part of this call, so the ledger of promised rewards is not backed by any actual balance held by the contract. Because `claimReward()` performs a raw `MGP.safeTransfer` against whatever balance the contract happens to hold, whichever referrer claims first drains the limited/incidental balance, and every other referrer's legitimate, already-accrued `rewardAmount` becomes permanently unclaimable.

### Finding Description
`trigger()` is guarded by `_onlyMasterMagpie` [1](#0-0) , and is invoked from `MasterMagpie`'s harvest path whenever a referee claims real MGP rewards: `IReferralStorage(referral).trigger(_user, totalReward)` [2](#0-1) . Inside `trigger()`, `refererAmount` and `refereeAmount` are computed from tier percentages and boost, then simply added to the in-storage `rewardAmount` fields: [3](#0-2) 

Critically, none of `MasterMagpie`'s `_sendMGP`, `_sendMGPForVlMGPPool`, or `_sendVlMGPFor` helpers transfer any MGP to `ReferralStorage`; they only move MGP to the claiming user, the vlMGP rewarder, or lock it into vlMGP [4](#0-3) . There is no funding/deposit function anywhere in `ReferralStorage.sol` that tops up its own MGP balance to match the liabilities being accrued in `trigger()`.

`claimReward()` then pays out strictly from whatever balance the contract holds, with no per-user reservation, no pro-rata distribution, and no check that `MGP.balanceOf(address(this)) >= totalOutstandingRewardAmount`: [5](#0-4) 

Since `registerCode`, `useCode`, and the claim/harvest path in `MasterMagpie` are all permissionless, any unprivileged user (or an attacker controlling multiple wallets that refer each other) can stake MGP, accrue real rewards, and harvest them repeatedly over time, each harvest calling `trigger()` and growing the referral ledger without any matching inflow of MGP into `ReferralStorage`. Because the contract's MGP balance is not increased in lockstep with the ledger, the very first `claimReward()` call already risks exceeding the contract's actual balance if it was not pre-funded to a value matching all outstanding + growing liabilities; once several referrers have accrued balances, whichever ones claim first will empty the contract's balance, and subsequent `claimReward()` calls from other legitimately-earning referrers revert via `InsufficientRewardBalance`/underflow in `safeTransfer`, freezing their principal-backed (real, harvested) unclaimed yield indefinitely.

An attacker does not need any privileged role: self-referral chains via `registerCode`/`useCode` plus ordinary staking/claiming in `MasterMagpie` are enough to accelerate accrual of unbacked `rewardAmount` entries relative to organic usage, since the attacker controls both the referrer and referee side of many wallets and can repeatedly harvest genuine (not fabricated) staking rewards to pump the ledger.

### Impact Explanation
This is a **permanent freezing of unclaimed yield** for legitimate referrers (Immunefi impact class: "Theft or permanent freezing of unclaimed yield"). Because the internal accounting ledger (`userInfos[*].rewardAmount`) is not backed 1:1 by MGP actually held in `ReferralStorage`, once the contract's balance is drained by early claimants, honest referrers with a correctly-computed, real `rewardAmount` are permanently unable to withdraw their earned referral rewards — `claimReward()` will revert indefinitely unless the contract is manually re-funded by an external actor, which is outside the affected users' control.

### Likelihood Explanation
- No privileged role is required; `registerCode`, `useCode`, staking, and reward claiming through `MasterMagpie` are all public/external functions.
- The only "cost" to the attacker is capital they already intend to stake to earn real yield; self-referral chains let them control both sides of the referral relationship and repeatedly trigger `trigger()` as their genuine staking rewards accrue over time (note: because `_calNewMGP` depends on `rewardDebt` catch-up, repeated calls within the same block yield zero additional reward, so acceleration happens across blocks/time, not via unlimited same-block spam).
- The underlying flaw (ledger not backed by a matching transfer) exists for any normal user with a referral set, not just the attacker; the self-referral attack simply lets a single actor accelerate and concentrate the exploitation of this structural gap to front-run other legitimate referrers' `claimReward()` calls.
- Highly repeatable: this can be repeated indefinitely as long as the attacker keeps staking/claiming.

### Recommendation
- Ensure `ReferralStorage` actually receives the MGP corresponding to `refererAmount + refereeAmount` at the time `trigger()` is called (e.g., have `MasterMagpie` `safeTransfer`/mint that amount into `ReferralStorage` in the same transaction), rather than only incrementing an internal ledger.
- Add an invariant check/guard in `claimReward()` (or in `trigger()`) ensuring `MGP.balanceOf(address(this)) >= sum(all outstanding rewardAmount)` is maintained, or track a `totalOutstandingRewards` state variable and revert `trigger()` accrual if it can't be funded.
- Consider a pull-based escrow/queue or a global scaling factor so that if the contract is underfunded, all claimants are paid pro-rata rather than on a first-come-first-served basis that freezes latecomers entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `MGP`, and `ReferralStorage`, wiring `masterMagpie` and `referralStorage` addresses as in production deployment, leaving `ReferralStorage`'s MGP balance at 0 (default, unfunded).
2. Wallet R (referrer) calls `registerCode(codeR)`; Wallet A and Wallet B (attacker-controlled) call `useCode(codeR)` to link to R, or set up a self-referral loop where A and B refer each other via distinct codes.
3. Have A and B stake MGP into `MasterMagpie` pools, advance `block.timestamp`, and call the harvest/claim function repeatedly across multiple blocks so `_harvestMGP`/claim path calls `IReferralStorage(referral).trigger(_user, totalReward)` multiple times, growing `userInfos[R].rewardAmount` and `userInfos[A/B].rewardAmount`.
4. Assert `MGP.balanceOf(address(referralStorage)) == 0` while `userInfos[R].rewardAmount > 0` and `userInfos[A].rewardAmount > 0` (ledger not backed by balance).
5. Have attacker wallet A call `claimReward()` first — if the contract happens to hold any incidental MGP (e.g., manually funded once by an admin/test setup for realism), assert it succeeds and drains the balance.
6. Have honest referrer R call `claimReward()` afterward and assert it reverts (`InsufficientRewardBalance` / underflow in `safeTransfer`), proving R's legitimately accrued `rewardAmount` is permanently frozen since no mechanism exists to top up `ReferralStorage`'s balance to match the ledger.

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
