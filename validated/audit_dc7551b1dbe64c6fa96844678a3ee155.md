### Title
Symlink Escape via "Reveal in File Manager" / "Open with Default Program" on Attacker-Controlled Tracked Files - ([File: app/src/lib/app-shell.ts])

### Summary
GitHub Desktop already contains a path-containment primitive, `resolveWithin()` (`app/src/lib/path.ts:36-72`), which resolves a path against a root and rejects it if the *realpath* (i.e., after following symlinks) escapes that root. This guard is deliberately used in `dispatcher.ts`'s `openRepositoryFromUrl` and in `copilot-conflict-context.ts` to stop symlink-based directory-escape attacks originating from repository content. However, several other code paths that turn a git-tracked/relative `file.path` into a filesystem path for direct OS-level actions (revealing in Explorer/Finder, opening with the default program) use plain `Path.join(repository.path, path)` instead, with no symlink-aware containment check.

### Finding Description
`revealInFileManager()` in [1](#0-0)  builds `fullyQualifiedFilePath = Path.join(repository.path, path)` and passes it straight to `shell.showItemInFolder`. `Path.join`/`Path.resolve` is a purely lexical/string operation — it does not consult the filesystem, so it cannot detect that an intermediate path component is a symlink pointing outside the repository.

The same pattern (`Path.join(repository.path, file.path)` with no `resolveWithin`) is repeated for the "Open with Default Program" action in [2](#0-1) , and for context-menu "reveal"/"open" actions built from committed-file paths in [3](#0-2)  and [4](#0-3) .

Contrast this with the guarded call sites, which explicitly call `resolveWithin` (which internally calls `realpath` on both the root and the resolved target and checks that the *resolved real path* still starts with the *real root*) before touching the filesystem: [5](#0-4)  and [6](#0-5) . The dedicated unit test even documents exactly this attack class: a symlink placed inside the root directory that points outside of it is rejected by `resolveWithin`, but only when `resolveWithin` is actually invoked: [7](#0-6) .

The corrupted/attacker-controlled value is `file.path` as reported by `git status`/`git diff`/commit file lists for a *tracked symlink entry* inside a cloned or fetched repository. Git happily tracks symlink blobs (mode `120000`) whose target string is attacker-chosen (e.g. `../../../../.ssh/id_rsa` or an absolute path). After clone/checkout (assuming `core.symlinks` is enabled, the default on macOS/Linux and configurable on Windows), the working tree contains a real filesystem symlink at that path pointing outside the repository. Desktop's UI still shows this file as an ordinary entry named e.g. `notes.txt`.

### Impact Explanation
When the user right-clicks that entry and chooses "Show in Finder/Explorer" or "Open with Default Program" (or an equivalent action), Desktop computes `Path.join(repository.path, 'notes.txt')`. The OS-level call (`shell.showItemInFolder`, `shell.openExternal('file://...')`, `shell.openPath`) then follows the symlink at that path, ultimately revealing/opening the real file outside the repository (e.g., an SSH private key, a credential file, or any file readable by the OS user) in the file manager or its associated default application. This is a repository-controlled read/disclosure of arbitrary files reachable by the current user, and depending on the file's registered handler, can also result in unintended execution of file content (e.g. opening an executable/script with its default handler).

### Likelihood Explanation
Requires no local/physical access, no admin rights, and no prior compromise of the host: the only necessary "attacker action" is publishing/pushing a git repository containing a symlink blob and getting the victim to clone it and click a context-menu item ("Reveal in Finder/Explorer" or "Open with Default Program") on the resulting file — a normal, expected user action within Desktop's own UI, not a social-engineering trick outside the app. The vulnerability class is exactly the one the codebase's own `resolveWithin` guard and test suite were written to prevent, but that guard is inconsistently applied — it protects the deep-link (`openrepo://...&filepath=`) and Copilot-conflict flows but not the everyday "reveal file" / "open file" context-menu actions reachable from the Changes list, History/commit file list, and pull-request file list.

### Recommendation
Route every filesystem path built from a repository-relative `file.path` (in `app-shell.ts#revealInFileManager`, `sidebar.tsx#onOpenItem`, `selected-commits.tsx#onContextMenu`, `pull-request-files-changed.tsx#onFileContextMenu`, and any other similar call site) through `resolveWithin(repository.path, file.path)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) before invoking `shell.showItemInFolder`, `shell.openExternal`, `openFile`, or `shell.openPath`, and refuse the action (as `dispatcher.ts` already does) if the resolved real path does not stay inside the repository root.

### Proof of Concept
1. Create a repository containing a symlink entry, e.g.:
   ```
   git init evil-repo
   cd evil-repo
   ln -s ../../../../.ssh/id_rsa leaked-key.txt   # or an absolute path target
   git add leaked-key.txt
   git commit -m "add note"
   ```
2. Victim clones `evil-repo` with GitHub Desktop (`core.symlinks` enabled, the default on macOS/Linux).
3. In the Changes/History list, the victim right-clicks `leaked-key.txt` and selects "Show in Finder/Explorer" (or "Open with Default Program").
4. `revealInFileManager(repository, 'leaked-key.txt')` computes `Path.join(repository.path, 'leaked-key.txt')` and calls `shell.showItemInFolder`, which follows the symlink and reveals/opens the victim's real `~/.ssh/id_rsa` file instead of anything inside the cloned repository — without any `resolveWithin`/realpath containment check being performed, unlike the equivalent guarded flow in `dispatcher.ts#openRepositoryFromUrl`.

Note: I was not able to fully verify within the available search iterations whether Desktop's status/diff parsing (`app/src/lib/git/status.ts`, `status-parser.ts`) applies any additional filtering on symlink-mode entries before they reach the UI file lists; this should be checked to confirm no upstream mitigation already exists for this specific case.
