### Title
Reachable panic on point-at-infinity group key in `SignableTransaction::multisig` / `x_only` - (File: networks/bitcoin/src/crypto.rs)

### Summary
`SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs`) advertises returning `None` on bad keys, but before it can compare the derived key to the output's `script_pubkey`, it calls `p2tr_script_buf(offset.group_key())`, which funnels into `x_only`/`x` in `networks/bitcoin/src/crypto.rs`. Both helpers unconditionally panic on the point at infinity. Since `offsets[i]` comes from `ReceivedOutput` and the group key from `ThresholdKeys` — both deserializable from untrusted bytes via `ReceivedOutput::read`/`ThresholdKeys::read` — crafted input reaches the panic instead of a clean error. This is the same bug class as CVE-2022-31100: a reachable assertion/panic (CWE-617) on adversarial input, producing denial of service.

### Finding Description
`fn x(key)` calls `key.to_encoded_point(true)` then `.x().expect("point at infinity")`, and `x_only` calls `XOnlyPublicKey::from_slice(&x(key)).expect("x_only was passed a point which was infinity or odd")`. [1](#0-0)  `Hram::hram` documents that passing an infinity `R` or `A` panics, and `Schnorr` notes it "may panic if called with nonces/a group key which are the point at infinity". [2](#0-1)  In `multisig`, the code computes `keys.clone().offset(self.offsets[i])` and immediately feeds `offset.group_key()` to `p2tr_script_buf`, so an identity-valued key reaches `x()` and panics rather than hitting the `None?` return. [3](#0-2)  The `offset` per input is read verbatim from the `ReceivedOutput`, and `ThresholdKeys::read` accepts caller-supplied verification shares and secret share. [4](#0-3) 

### Impact Explanation
Any code path that constructs a `SignableTransaction`/`TransactionMachine` from deserialized `ReceivedOutput`s and `ThresholdKeys` — including bytes fed to `ReceivedOutput::read`/`ThresholdKeys::read` — will panic the calling thread when `group_key + offset·G` equals the identity. In a signing service, that panic kills the signing attempt (or the thread), a denial of service directly analogous to the rulex reachable-assertion advisory.

### Likelihood Explanation
An unprivileged party supplying both a `ThresholdKeys` encoding and a `ReceivedOutput` encoding can freely choose the verification shares and the offset scalar, so producing `group_key + offset·G = identity` is trivial (e.g., group key `G`, offset `-1 mod q`). No discrete-log work is needed because the attacker controls both sides of the sum. The panic triggers before the `script_pubkey` equality check that would otherwise reject the pairing, so the documented `None` failure path is unreachable for this input.

### Recommendation
In `networks/bitcoin/src/wallet/send.rs` `multisig`, check `offset.group_key()` for the identity (e.g., via `is_identity()`) before calling `p2tr_script_buf`, returning `None` instead. More defensively, make `x`/`x_only` in `networks/bitcoin/src/crypto.rs` return `Option`/reject infinity rather than `.expect()`ing, and apply the same guard where `Hram::hram` consumes a nonce `R` derived from untrusted preprocesses.

### Proof of Concept
```rust
// Using in-scope APIs only:
// frost::curve::Secp256k1, ThresholdKeys::read, ReceivedOutput::read,
// SignableTransaction::new, SignableTransaction::multisig

// 1. Serialize a ThresholdKeys whose group_key = G (attacker chooses
//    verification_shares / secret_share accordingly via ThresholdKeys::write
//    or by crafting the byte stream consumed by ThresholdKeys::read).
// 2. Serialize a ReceivedOutput whose `offset` = -1 mod q (any scalar
//    bytes accepted by C::read_F), with an arbitrary TxOut.
// 3. SignableTransaction::new(vec![received_output], &payments, None, None, fee)
//    succeeds — offsets are copied verbatim (send.rs:176).
// 4. signable_tx.multisig(&keys) computes group_key + (-1)·G = identity,
//    then p2tr_script_buf -> x_only -> x() hits
//    `.x().expect("point at infinity")` and panics (crypto.rs:15)
//    before the script_pubkey comparison that would return None.
```

Caveat I could not fully verify without further inspection: whether production callers feed attacker-controlled bytes directly into `ReceivedOutput::read`/`ThresholdKeys::read` on a hot path, and whether `p2tr_script_buf` itself pre-checks for infinity (the code in `crypto.rs` shows it does not). If those callers always use internally generated offsets, the same panic is still reachable through the documented `Schnorr`/`Hram` path when a nonce sum `R` is the identity, though crafting that requires defeating the FROST binding factor and is not shown to be feasible.
