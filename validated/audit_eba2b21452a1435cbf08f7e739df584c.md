Confirmed: unlike `Kip71BaseFeeDenominator`, which has a `FormatChecker` requiring `v != 0` [1](#0-0) , the `Kip71GasTarget` parameter uses `noopFormatChecker`, which accepts any `uint64` value including `0` [2](#0-1) . No other validation of `GasTarget != 0` exists in the codebase.

### Title
Division-by-zero panic in `NextMagmaBlockBaseFee` via unvalidated `GasTarget` governance parameter causing block-processing crash - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee`, which computes the Magma/KIP-71 dynamic base fee for every block, divides by `kc.GasTarget` without checking for zero. While `BaseFeeDenominator` is explicitly guarded against zero both in the governance parameter's `FormatChecker` and in the function itself, `GasTarget` has neither protection, allowing a governance-set `GasTarget = 0` to trigger a `big.Int` division-by-zero panic during header verification/base-fee calculation on every node.

### Finding Description
`NextMagmaBlockBaseFee` computes the next base fee based on `parentGasUsed` relative to `gasTarget`: [3](#0-2) [4](#0-3) 

In both the "gas used above target" and "gas used below target" branches, the code performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `math/big.Int.Div` panics with `"division by zero"` when the divisor is zero. Note that `BaseFeeDenominator` is defensively handled with a fallback to `64` when zero: [5](#0-4)  — but no equivalent fallback exists for `gasTarget`.

The `GasTarget` governance parameter (`Kip71GasTarget`) is registered with `noopFormatChecker` (accepts any value) [2](#0-1) , in contrast to `Kip71BaseFeeDenominator` which explicitly rejects `0` [1](#0-0) . Once a governance vote sets `GasTarget` to `0` and it becomes effective, `NextMagmaBlockBaseFee` is invoked on the very next block by header validation (`VerifyMagmaHeader`) [6](#0-5)  as well as by the gas price oracle's `SuggestPrice`/`processBlock` paths [7](#0-6) . Since `parentGasUsed == gasTarget (0)` only short-circuits when the block used exactly zero gas, any block with `GasUsed > 0` when `gasTarget == 0` falls into the `parentGasUsed > gasTarget` branch and panics on `x.Div(x, big.NewInt(0))`.

### Impact Explanation
Because header verification and base fee computation happen identically on every node, a `GasTarget = 0` governance parameter causes a deterministic panic across all nodes processing the block that activates it (or the following block), leading to a node-wide crash/halt — a consensus-critical denial of service. This is a state-divergence/liveness risk consistent with the "acceptance of an invalid transaction or block" / "state divergence" impact category, since nodes would crash rather than process the chain uniformly (and any node that doesn't crash, e.g. due to differing recover/panic handling, could diverge in behavior).

### Likelihood Explanation
Setting `GasTarget` to `0` requires a successful governance parameter change (a `Kip71GasTarget` vote reaching effect), which is a governance-parameter operation, not an arbitrary unprivileged call — this significantly limits who can trigger it (typically the governing node or governance council under the applicable `GovernanceMode`). However, since the report explicitly includes "governance parameters" as an in-scope, reachable category and no additional validation prevents this misconfiguration/vote from taking effect, likelihood is non-trivial for any deployment allowing governance votes with insufficiently validated inputs (e.g. via a compromised or careless governing node, or a governance API/RPC that doesn't perform its own zero-check before submission). I could not verify within the available context whether an additional value-sanity check exists elsewhere in the vote-application pipeline (`kaiax/gov/headergov` vote application) that would reject `GasTarget = 0` before it reaches `ParamSet`; this would need further verification in a live session.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and additionally add a defensive zero-check/fallback for `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, analogous to the existing `BaseFeeDenominator == 0` fallback, to prevent a panic even if an unexpected zero value is ever supplied.

### Proof of Concept
1. Via governance vote, set `Kip71GasTarget` (governance param key for `GasTarget`) to `0`; this passes `noopFormatChecker` validation and is accepted.
2. Once the vote takes effect at the target block, produce (or receive) any block with `GasUsed > 0`.
3. During header verification, `KIP71Config.VerifyMagmaHeader` → `NextMagmaBlockBaseFee` computes `parentGasUsed(>0) > gasTarget(0)`, entering the increase branch: `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by `big.NewInt(0)`.
4. `math/big.Int.Div` panics with `"division by zero"`, crashing the node's block processing goroutine on every node that processes this header, halting the chain.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
