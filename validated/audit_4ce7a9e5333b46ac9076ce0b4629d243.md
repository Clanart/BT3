### Title
`git clone` explicitly disables Git's own "clone protection" hardening, re-enabling RCE via a malicious/attacker-controlled recursive repository - (File: app/src/lib/git/clone.ts)

### Summary
Desktop's `clone()` helper always performs a `--recursive` clone and unconditionally forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE=false` on every invocation of `git clone`. This mirrors the exact "broken invariant" pattern in the source report: a signaling mechanism that is meant to indicate a safety condition ("protection is active" / "this is genuinely ETH, not WETH") is instead forced into the unsafe state by the caller, silently disabling a guard that upstream added specifically to stop attacker-controlled repository content from executing code or writing files outside the intended directory during clone.

### Finding Description
`clone()` builds the Git invocation and hard-codes the "protection disabled" signal into the child process environment before calling into `git`: [1](#0-0) 

```
  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }
  ...
  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]
```

`GIT_CLONE_PROTECTION_ACTIVE` is not a Desktop-invented variable — it is a signaling variable Git itself uses internally between the top-level `git clone` process and the `git submodule--helper`/nested clone processes it spawns for `--recursive` operations. It exists to let a *caller* of `git clone --recurse-submodules` communicate that clone-time protections (checks against symlinked or case/normalization-confusable `.git` paths inside submodules, which were the exact vector behind the 2024 Git security advisories covering malicious repositories executing arbitrary code or overwriting files outside the working tree during a recursive clone) are already active in the outer process, so the nested helper doesn't need to re-derive them. By exporting `GIT_CLONE_PROTECTION_ACTIVE=false` from Desktop's own top-level invocation, Desktop is telling Git's own defense-in-depth machinery that protection is *not* active for the operation it is about to perform, which is the opposite of the intended, safe default (no explicit override at all, or `true`), for every single clone — including clones of arbitrary, fully attacker-controlled URLs coming from deep links (`x-github-client://openRepo/...`, see `app/src/lib/parse-app-url.ts` and `dispatcher.openOrCloneRepository`) and from GitHub API objects (fork/PR head clone URLs consumed in `openPullRequestFromUrl`).

The corrupted value here is the process environment passed to the `git clone --recursive` child process: `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` by `envForRemoteOperation`'s caller regardless of the trustworthiness of `url`, exactly analogous to how `_depositToken()` blindly trusted an ambiguous ETH/WETH signal instead of deriving it safely.

Existing guards in the same file do not address this: `isClonePathSensitive()` only checks the destination directory against a short list of sensitive home-directory locations, and the `--` separator before `url, path` only prevents flag-injection via the clone URL argument. Neither of these guards inspects or restores the submodule-clone protection that Git's own maintainers added specifically to stop malicious repository content (crafted via nested submodules with symlinked/case-confusable `.git` entries) from executing code or writing outside the target directory during a `--recursive` clone.

### Impact Explanation
Because `--recursive` is always passed and the protection signal is always forced off, cloning *any* attacker-controlled repository (an untrusted `git@`/`https://` URL a user pastes, a deep-linked "Open in Desktop" URL, or a PR fork's `clone_url` fetched from the GitHub API) that contains a maliciously crafted submodule can bypass the client-side hardening Git ships to prevent exactly this class of attack, potentially resulting in files being written outside the intended repository directory or arbitrary code execution during the clone/checkout of the submodule content. This satisfies the "attacker controls a cloned/fetched repository ... result is code execution [or] file write ... outside the repo" impact bar.

### Likelihood Explanation
Every clone Desktop performs goes through this single code path (`app/src/lib/git/clone.ts`), and it is reachable without any special user action beyond cloning/opening a repository — including fully automated flows such as clicking an "Open in Desktop" link (`parseAppURL`/`openOrCloneRepository`) or opening a PR from a fork (`openPullRequestFromUrl`), where the clone URL originates entirely from an external, attacker-influenced source (a crafted link or a forked repository's metadata). No local access, elevated privileges, or unusual user steps are required — a normal clone action is sufficient to trigger the code path with the protection forced off.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Either omit the variable entirely (letting Git apply its own default, safe behavior) or explicitly set it to `'true'`/leave protection active for all clone operations, especially recursive/submodule clones originating from untrusted URLs (deep links, API-sourced fork URLs, user-pasted URLs). If the override was added to work around a specific compatibility issue, scope it narrowly and document the specific safe precondition, rather than applying it unconditionally to every clone.

### Proof of Concept
1. Host (or fork) a repository containing a submodule entry crafted to exploit the case/symlink confusion issues that `GIT_CLONE_PROTECTION_ACTIVE`-gated checks are designed to catch (e.g., a submodule path that resolves to `.git` on a case-insensitive filesystem, or a symlinked working-tree entry standing in for the submodule's `.git` directory).
2. Get a victim to clone the repository through any Desktop entry point that reaches `clone()` in `app/src/lib/git/clone.ts` — e.g., pasting the URL into "Clone repository," or via a crafted `x-github-client://openRepo/<attacker-url>` deep link (`app/src/lib/parse-app-url.ts` → `dispatcher.ts` `openOrCloneRepository` → `PopupType.CloneRepository` → `clone()`), or by opening a PR whose fork `clone_url` is attacker-controlled (`openPullRequestFromUrl`).
3. Because `clone()` always passes `--recursive` and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE=false` (`app/src/lib/git/clone.ts` lines 81-93), Git's client-side submodule clone-protection check is disabled for this operation, allowing the crafted submodule content to be materialized in a way Git's own hardening was designed to prevent — up to and including code execution or writes outside the intended clone directory, depending on the underlying Git version's exact protected code path.
```typescript
export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
```
