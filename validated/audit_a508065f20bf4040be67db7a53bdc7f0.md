### Title
Strict balance-invariance equality checks in ERC20↔Coin conversion permanently freeze funds for fee-on-transfer/rebasing token pairs - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`x/erc20/keeper/msg_server.go` implements the ERC20↔Coin conversion path with **strict exact-equality checks** on before/after balances, exactly the anti-pattern described in the ERC5115Form report. If a token pair is registered for an ERC20 contract whose `transfer` does not move exactly the requested amount (fee-on-transfer, rebasing, or any token with rounding on transfer, e.g. a stETH-like asset), these checks will revert every future conversion for that pair, permanently locking any coins/tokens that have already been escrowed for it.

### Finding Description
`convertERC20IntoCoinsForNativeToken` (ERC20 → Coin path) escrows the ERC20 token into the module account via a raw EVM `transfer` call and then asserts the resulting balance is *exactly* the pre-balance plus amount: [1](#0-0) 

It also enforces a second strict equality on the receiver's minted coin balance: [2](#0-1) 

The reverse path, `ConvertCoinNativeERC20` (Coin → ERC20, i.e. un-escrowing previously locked tokens), performs the mirror check after calling `transfer` from the module account to the receiver: [3](#0-2) 

Both checks use exact `Cmp`/`Equal` comparisons against the expected balance delta, with no tolerance for any deviation — the same strict-equality bug class as the reported `ERC5115Form.sol#L314`/`#L566` issue. Registration of an ERC20 contract as a token pair (`registerERC20` in `x/erc20/keeper/proposals.go`) only validates that the contract exposes standard ERC20 metadata via `QueryERC20`/`CreateCoinMetadata`; it performs no validation that `transfer` moves the exact requested amount (no fee-on-transfer/rebase check): [4](#0-3) 

If such a token pair is used:
1. A user successfully converts ERC20 → Coin once if the token's rounding/fee happens to not trigger the mismatch, or fails immediately if it always does.
2. Once ERC20 tokens are escrowed in the module account for a given pair, `ConvertCoinNativeERC20` can never successfully return those tokens if the underlying token's `transfer` doesn't move the exact `amount` (e.g., due to fee-on-transfer burn or share-rounding). Every attempt reverts with `types.ErrBalanceInvariance` before `BurnCoins` is reached, so the coin the user holds becomes permanently non-redeemable, and the ERC20 principal remains stuck in the module account forever, unreachable by any state transition available to users.

This is a stronger and more persistent version of the ERC5115Form bug: because both conversion directions gate on exact equality with no epsilon/balance-diff tolerance, a token pair with any transfer-amount deviation becomes fully bricked in one or both directions — a genuine "permanent freezing" of user value, not merely a transient revert.

### Impact Explanation
This falls under the "Critical permanent freezing, locking … of user funds, contract balances, escrowed assets… or token-pair-backed balances" impact class. Once tokens are escrowed for an affected pair, they are unrecoverable through the module's own conversion mechanism, and the corresponding Coin representation becomes worthless/unredeemable — a direct, irreversible loss of user-accessible value, triggerable purely through ordinary `MsgConvertERC20`/`MsgConvertCoin` transactions by any user who registers or interacts with such a token pair.

### Likelihood Explanation
Likelihood depends on:
- Whether `MsgRegisterERC20` is permissionless (any user can register an arbitrary ERC20 contract as `OWNER_EXTERNAL` token pair) or gated behind governance. Based on the code reviewed, `registerERC20` itself contains no authority/governance check, and the message plumbing (`MsgRegisterERC20`) is present in `x/erc20/types/msg.go` without an obvious admin-only guard in the reviewed code, suggesting the registration path may be reachable by ordinary users; however, I was not able to fully trace the top-level `MsgServer.RegisterERC20` handler and any surrounding gating logic (e.g. `authority` checks elsewhere in the module) within the available tool budget, so this is not fully confirmed.
- Real-world fee-on-transfer/rebasing ERC20 tokens deployed on the EVM side are common enough (this is precisely the bug class the external report is about) that registering one as a token pair is a realistic, low-effort attacker/user action.

### Recommendation
- Replace strict equality checks in `convertERC20IntoCoinsForNativeToken` and `ConvertCoinNativeERC20` with balance-difference-based accounting (mint/escrow based on the actual observed balance delta rather than the requested amount), analogous to the "deposit case" fix recommended in the report.
- If exact-amount semantics must be preserved for accounting integrity, reject registration of ERC20 contracts whose `transfer` does not move the exact amount (e.g. simulate a transfer during registration and compare pre/post balances) rather than discovering this only after funds are already escrowed.
- Add an escape hatch (e.g., a governance-gated "sweep"/"correct" pathway) so tokens already stuck due to this invariant are recoverable, rather than being unconditionally unrecoverable.

### Proof of Concept
1. Deploy an ERC20 contract that charges a 1-wei (or higher) fee/burn on every `transfer` (or a rebasing token akin to stETH with share-rounding).
2. Register it as a token pair via `MsgRegisterERC20` (assuming permissionless registration, per the code reviewed).
3. Call `MsgConvertERC20` to escrow tokens into the module account and mint corresponding Coins to the user; if the fee causes a mismatch, this call reverts on `types.ErrBalanceInvariance` here: [5](#0-4)  permanently preventing conversion in that direction. If it does succeed (fee only reduces received-side balance without violating this particular check due to placement), some tokens remain escrowed in the module account.
4. Call `MsgConvertCoin` to redeem the previously minted Coins back into ERC20 tokens; the reverse leg's fee/round always causes the strict equality check to fail here: [6](#0-5)  so `BurnCoins` is never reached, the user's Coins remain non-redeemable, and the escrowed ERC20 principal is permanently stuck in the module account.

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
