### Title
Deserialization accepts an empty aggregate signature, bypassing the non-empty aggregate invariant - (File: `crypto/schnorr/src/aggregate.rs`)

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero signatures, even though `SchnorrAggregator::complete` explicitly refuses to construct one. With `s = 0`, that deserialized value passes `verify` when the statement list is empty, producing a forged aggregate signature. [1](#0-0) [2](#0-1) 

### Finding Description
`SchnorrAggregate::read` reads a `u32` element count and then reads exactly that many `R` values plus the scalar `s`, but it never rejects a count of zero. [1](#0-0) 

`SchnorrAggregator::complete` establishes the intended boundary condition: aggregation of no signatures returns `None` instead of producing an aggregate. [3](#0-2) 

`SchnorrAggregate::verify` only checks that `self.Rs.len()` equals `keys_and_challenges.len()`. [4](#0-3) 

For an empty aggregate and empty statement list, verification skips all signature-specific pairs, pushes only `(-s)G`, and accepts when `s = 0` because the result is the group identity. [5](#0-4) 

This is the same boundary-condition class as the reference bug: a value at a boundary causes a term to contribute nothing, allowing the validation equation to degenerate to zero instead of being rejected.

### Impact Explanation
An attacker can provide untrusted aggregate-signature bytes representing no signatures and have them deserialize into a value that `verify` accepts for an empty verification statement list. This bypasses the implementation’s own non-empty aggregate invariant and constitutes a forged aggregate signature wherever an empty statement set can reach verification. [1](#0-0) [6](#0-5) 

### Likelihood Explanation
The attack requires only public input bytes passed to `SchnorrAggregate::read`, followed by verification with an empty `keys_and_challenges` list. No secret key, private nonce, validator control, or malformed elliptic-curve encoding is needed. Exploitability depends on an application reaching the zero-statement boundary, but once reached the forged value deterministically verifies. [1](#0-0) [6](#0-5) 

### Recommendation
Reject empty aggregates in `SchnorrAggregate::read`, matching `SchnorrAggregator::complete`’s behavior. Defense-in-depth should also make `SchnorrAggregate::verify` return `false` when `self.Rs` or `keys_and_challenges` is empty, so manually constructed or deserialized empty values cannot satisfy the identity equation vacuously. [1](#0-0) [6](#0-5) [3](#0-2) 

### Proof of Concept
For a 32-byte scalar ciphersuite such as `frost::curve::Secp256k1`, the serialized aggregate is four zero bytes for `Rs.len()`, followed by the canonical encoding of scalar zero:

```rust
use frost::curve::Secp256k1;
use schnorr::aggregate::SchnorrAggregate;

let encoded = [0u8; 36];
let mut reader = &encoded[..];

let aggregate = SchnorrAggregate::<Secp256k1>::read(&mut reader).unwrap();
assert!(aggregate.verify(b"example-domain", &[]));
```

The first four bytes decode `Rs.len()` as zero, and the remaining 32 bytes decode `s` as zero. [1](#0-0)  Verification then evaluates only `(-0)G`, which is the identity. [5](#0-4)
