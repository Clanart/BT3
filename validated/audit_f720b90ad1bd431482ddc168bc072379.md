### Title
Out-of-range blame recipient crashes decryption via unchecked registry lookup - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary

`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept attacker-controlled `sender` and `recipient` participant identifiers without validating that they belong to the DKG participant set. If the encrypted message has a valid proof-of-possession and a non-`None` `EncryptionKeyProof` is supplied, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` before validating the DLEq proof. An unprivileged party can therefore submit a blame accusation naming an unregistered recipient, such as `Participant::new(65535)`, and cause an unconditional panic. This maps the reported availability-impact bug class onto a reachable panic in Serai’s public blame-processing API.

### Finding Description

`AdditionalBlameMachine::new` registers encryption keys only for participants `1..=n` when it consumes the commitment messages. [1](#0-0) 

The public blame APIs then pass caller-supplied `sender` and `recipient` values directly into `blame_internal` without checking either identifier against that registered set. [2](#0-1) [3](#0-2) 

Inside `decrypt_with_proof`, the message PoP is checked first, then a supplied proof takes the `Some(proof)` branch and evaluates `self.enc_keys[&decryptor]` as part of the DLEq verification arguments. [4](#0-3) 

Because `enc_keys` is a `HashMap`, indexing it with an absent `Participant` panics rather than returning `DecryptionError`. [5](#0-4) 

Both `EncryptedMessage::read` and `EncryptionKeyProof::read` are public deserialization entry points for attacker-controlled wire data. [6](#0-5) [7](#0-6) 

### Impact Explanation

A remote party that can cause a node or auditor to evaluate a blame accusation can terminate the process by naming a recipient outside the registered participant set. The supplied DLEq proof does not need to be valid, because the unchecked registry lookup occurs while constructing its inputs. A single malformed blame request is therefore sufficient to crash the blame handler before it can return `InvalidProof` or otherwise reject the accusation.

### Likelihood Explanation

The trigger only requires a syntactically valid `EncryptedMessage` with a passing Schnorr PoP and any parsable `EncryptionKeyProof`. An attacker can replay an existing valid encrypted share message, preserving the original `sender`, while changing the blame-accusation metadata to use an unregistered `recipient`; the recipient is not part of the PoP challenge input. [8](#0-7) 

The bug does not depend on threshold corruption, key compromise, invalid curve encodings, or race conditions. Its practical likelihood depends on the integrator accepting blame accusations from untrusted parties and forwarding their sender/recipient identifiers to these public APIs.

### Recommendation

Validate `sender` and `recipient` before calling `blame_internal`, returning a typed error for identifiers outside `1..=n` or otherwise absent from `enc_keys`/`commitments`. Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::...)` so malformed blame requests cannot panic. The same validation should be applied consistently in `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and any other paths that index participant maps.

### Proof of Concept

```rust
use std::collections::HashMap;
use std::io::Cursor;

use dkg::Participant;
use pedpop::{
  AdditionalBlameMachine, EncryptedMessage, EncryptionKeyProof, SecretShare,
};
use ciphersuite::Ciphersuite;

fn crash_blame_machine<C: Ciphersuite>(
    context: [u8; 32],
    n: u16,
    commitment_msgs: HashMap<Participant, _>,
    valid_encrypted_share: Vec<u8>,
    any_proof_bytes: Vec<u8>,
) {
    let machine =
        AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();

    // A previously observed valid encrypted share. Its PoP remains valid when
    // evaluated with the original sender, context, ciphertext, and key.
    let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(
        &mut Cursor::new(valid_encrypted_share),
        params,
    ).unwrap();

    // Only needs to deserialize successfully; it is indexed before verification.
    let proof = EncryptionKeyProof::<C>::read(
        &mut Cursor::new(any_proof_bytes)
    ).unwrap();

    // Valid Participant representation, but outside the registered 1..=n set.
    let invalid_recipient = Participant::new(u16::MAX).unwrap();

    // Panics at self.enc_keys[&invalid_recipient].
    let _ = machine.blame(
        original_sender,
        invalid_recipient,
        msg,
        Some(proof),
    );
}
```

The panic occurs at the unchecked map access in `decrypt_with_proof`, before DLEq verification can reject the supplied proof. [9](#0-8)
