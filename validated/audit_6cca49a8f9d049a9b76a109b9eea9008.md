### Title
Unhandled `IndexError` in mempool CLVM canonical-form check causes spend-triggered transaction-processing halt - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` parse an attacker-supplied CLVM buffer's atom-length prefixes without validating that enough bytes remain in the buffer before indexing into it, mirroring the CVE-2023-0667 pattern (parsing a length field from an attacker-crafted buffer without checking it against the remaining buffer size). This function is called unconditionally on every coin spend's `puzzle_reveal` and `solution` during mempool admission, so a single crafted (and validly signed) spend bundle can raise an unhandled `IndexError` inside `MempoolManager.validate_spend_bundle()`.

### Finding Description
`is_clvm_canonical()` walks a serialized CLVM buffer token by token: [1](#0-0) 

The main loop reads `b = clvm_buffer[offset]` on every iteration but only checks `if tokens_left == 0: break` *after* consuming a token — there is no check that `offset < len(clvm_buffer)` before the next read. A truncated pair (e.g. `b"\xff\x80"`, a `FF` pair marker followed by a single atom with a missing second child) leaves `tokens_left != 0` with `offset == len(clvm_buffer)`, so the next loop iteration indexes past the end of the buffer and raises `IndexError`.

Separately, `is_atom_canonical()` reads the multi-byte length prefix without bounds-checking against the buffer length: [2](#0-1) 

The `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]` loop assumes `prefix_len` extra bytes exist after the initial descriptor byte. If the descriptor byte (e.g. `0xC0`–`0xFD`, indicating a 1–5 byte length prefix) is placed at or near the very end of the buffer, this also raises `IndexError`.

Both functions are invoked unconditionally — not only for DEDUP-eligible spends as their docstring/comments imply — on every coin spend's puzzle reveal and solution during mempool admission: [3](#0-2) 

`validate_spend_bundle()` has no `try/except` around this call, so the `IndexError` propagates out of the function uncaught.

### Impact Explanation
Any wallet user, offer counterparty, or unprivileged spend-bundle submitter can construct a coin spend whose `puzzle_reveal` or `solution` bytes are crafted so that a length-prefix byte sits at the very end of the buffer (with the rest of the CLVM structure otherwise valid/executable), triggering an `IndexError` instead of a clean `Err.INVALID_COIN_SOLUTION` rejection. Because `validate_spend_bundle()` does not catch this exception, it propagates to whatever caller handles mempool admission (RPC `push_tx`, peer transaction relay, `add_spend_bundle`), producing an unhandled exception in the transaction-processing path rather than a graceful mempool rejection. This is a spend-triggered transaction-processing fault reachable from a single submitted spend bundle, matching the "invalid spend acceptance / transaction-processing halt" impact category, though the full blast radius (whether it merely fails that one RPC call vs. crashes a long-lived processing loop/task) depends on exception handling in the specific caller path (e.g. `full_node.py` message handlers, RPC endpoint wrappers), which was not fully traced due to remaining tool budget.

### Likelihood Explanation
High likelihood of triggering the crash: constructing a truncated pair or a length-prefix byte at a buffer boundary is trivial and does not require any special privileges — only a syntactically-valid-enough CLVM buffer that is non-canonical in this specific truncated way. No signature bypass or consensus knowledge is needed since the check runs on raw serialized bytes before/independent of program execution semantics.

### Recommendation
Add explicit bounds checks in both `is_clvm_canonical()` (verify `offset < len(clvm_buffer)` before each read of `b`) and `is_atom_canonical()` (verify `offset + prefix_len < len(clvm_buffer)` before reading the length-prefix bytes), returning `False`/raising a handled `ValueError` rather than allowing raw `IndexError` to propagate. Additionally, wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` in a `try/except` that maps any parsing failure to `Err.INVALID_COIN_SOLUTION`, consistent with how malformed CLVM is otherwise rejected.

### Proof of Concept
1. Craft a `puzzle_reveal` or `solution` whose serialized bytes end with an incomplete CLVM pair, e.g. `bytes.fromhex("ff80")` truncated further to just `b"\xff"` (pair marker with no children), or with a multi-byte atom length prefix truncated, e.g. `b"\xc0"` alone (declares a 1-extra-byte length prefix but supplies zero trailing bytes).
2. Build a `CoinSpend` using this buffer as `puzzle_reveal` (with a matching, otherwise-valid `solution`), wrap it in a `SpendBundle`, and submit it through `MempoolManager.add_spend_bundle()` / `validate_spend_bundle()` (e.g. via `SimClient.push_tx()` in `chia/_tests/util/spend_sim.py`, or the wallet/RPC `push_tx` path).
3. Observe that instead of returning `MempoolInclusionStatus.FAILED` with `Err.INVALID_COIN_SOLUTION` (as happens for other non-canonical CLVM in `test_mempool_requires_canonical_clvm`, [4](#0-3) ), the call raises an unhandled `IndexError` from `is_clvm_canonical`/`is_atom_canonical`.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
