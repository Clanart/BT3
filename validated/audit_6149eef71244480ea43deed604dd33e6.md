### Title
Scanner reports coinbase outputs as spendable while they are still immature and unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including the coinbase transaction, and `Scanner::scan_transaction` matches outputs purely on `script_pubkey` without checking `Transaction::is_coinbase()` or enforcing the 100-block coinbase maturity rule. A `ReceivedOutput` produced from a coinbase output is treated identically to a spendable output, even though the Bitcoin consensus rules forbid spending it for 100 confirmations. This is the Serai analog of "operation proceeds while the guard/state (maturity) says it should be blocked": the scan path has no state check distinguishing mature from immature funds.

### Finding Description
- `scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches `output.script_pubkey` against `self.scripts` and immediately emits a `ReceivedOutput` with no check on whether `tx` is a coinbase transaction.
- `scan_block` (mod.rs:221-227) loops `for tx in &block.txdata`, which includes `block.txdata[0]` (the coinbase). The only mitigation is a doc comment (mod.rs:216-220) telling the caller to post-process or use `scan_transaction` on `block.txdata[1 ..]` — nothing in code enforces it.
- The resulting `ReceivedOutput` flows into `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), which sums `input.output.value` into `input_sat` and builds `TxIn`s referencing the immature outpoint. There is no maturity validation anywhere before signing.
- An unprivileged party (any Bitcoin miner) can cause this by mining a block whose coinbase pays to the scanner's P2TR script — they only need to send a normal Bitcoin transaction/output to the watched address.

### Impact Explanation
Funds are reported as received that are not spendable. A `SignableTransaction` built over an immature coinbase output produces a transaction that consensus rejects (BIP-113/COINBASE_MATURITY = 100), so the FROST signing round either produces an unbroadcastable transaction or counts immature value toward `input_sat` when checking `NotEnoughFunds`. In a system counting scanned outputs as balance, this overstates immediately spendable funds — the same class of harm as operating on state that should have been frozen.

### Likelihood Explanation
Reachable by any miner able to produce a block, or by anyone watching `scan_block` results on a chain with recent coinbase payouts to the registered script. No collusion, key access, or privileged position is required — only the ability to get a coinbase output paying to the target script included in a block, and a consumer that calls `scan_block` rather than manually slicing `txdata[1 ..]`. The impact is bounded by the value of immature coinbase outputs and the 100-block window.

### Recommendation
Have `scan_transaction` skip/flag coinbase transactions (check `tx.is_coinbase()`), or have `scan_block` iterate `block.txdata[1 ..]` by default and expose a separate maturity-aware API. Alternatively, record the block height on `ReceivedOutput` and reject coinbase outpoints in `SignableTransaction::new` until they have matured.

### Proof of Concept
```rust
// A block whose coinbase (txdata[0]) pays `value` to the scanner's script_pubkey
let outputs = scanner.scan_block(&block);
// outputs contains a ReceivedOutput for the immature coinbase outpoint,
// indistinguishable from a spendable one:
assert_eq!(outputs[0].outpoint().txid, block.txdata[0].compute_txid());

// SignableTransaction::new accepts it as an input:
let stx = SignableTransaction::new(outputs, &payments, change, None, fee_rate)?;
// The produced transaction is consensus-invalid for 100 blocks,
// yet `needed_fee`/`NotEnoughFunds` accounting already counted the immature satoshis.
```
Root cause: missing state (maturity/coinbase) check in `scan_transaction`/`scan_block` and absence of any downstream maturity validation in `SignableTransaction::new`.
