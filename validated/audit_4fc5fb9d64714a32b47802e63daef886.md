### Title
PedPoP blame proofs disclose the raw ECDH shared key inside a propagatable error/event, leaking DKG secret shares to unauthorized parties - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the MongoDB driver flaw (credentials emitted inside a monitoring event that logging infrastructure then ingests), `pedpop` places the raw ECDH shared point — the sole secret input to the share-decryption cipher — inside `EncryptionKeyProof`, which is embedded verbatim in `PedPoPError::InvalidShare` as `blame`. `EncryptionKeyProof` derives `Debug`, and the error type is `Clone + Debug + thiserror::Error`, so it is designed to be propagated, logged, and broadcast for dispute resolution. Whoever observes the error/blame object can reconstruct `cipher(context, key)` and decrypt the associated `EncryptedMessage<SecretShare>` ciphertext, recovering a threshold secret share they were never authorized to see.

### Finding Description
`Encryption::decrypt` computes `key = ecdh(&self.enc_key, msg.key)` — the shared point between the recipient's long-lived encryption key and the sender's per-message ephemeral key — and returns it inside `EncryptionKeyProof { key, dleq }` (`crypto/dkg/pedpop/src/encryption.rs:487-500`). `cipher()` derives the ChaCha20 key deterministically from `context` and this ECDH point alone (`encryption.rs:101-133`), so possessing `key` is equivalent to possessing the decryption key. The proof travels inside `PedPoPError::InvalidShare { participant, blame }` (`crypto/dkg/pedpop/src/lib.rs:46-47`), a `Clone + Debug` error, and `EncryptionKeyProof` itself derives `Debug` (`encryption.rs:260-264`), printing the raw `key` point when formatted.

The code's own comments acknowledge the side-effect channel: the PoP exists because otherwise "they'd reveal bX, revealing Alice's message to Bob" (`encryption.rs:84-90`). But the PoP only prevents an observer from *attributing* a foreign key; it does nothing to stop the normal blame flow from publishing `key` itself. `Decryption::decrypt_with_proof` shows the intended consumer: any party holding the proof can verify the DLEq and then run `cipher(context, &proof.key)` to decrypt the message (`encryption.rs:381-393`). There is no check that the accusation is well-founded before the shared key is disclosed — the accuser generates the proof unconditionally in `decrypt` and chooses when to emit it.

### Impact Explanation
A participant Bob can accuse an honest dealer Alice of sending an invalid share, publishing `PedPoPError::InvalidShare` with a valid `EncryptionKeyProof`. Every party that receives the blame (for dispute resolution) — and any log/monitoring infrastructure that records the `Debug`-formatted error — obtains the ECDH point and can decrypt Alice's ciphertext to Bob, exposing Alice's secret share intended solely for Bob. This directly weakens the threshold: each leaked share reduces by one the number of shares an adversary still needs to reconstruct an honest dealer's polynomial. An attacker controlling participants can combine shares they legitimately hold with publicly leaked shares to recover honest dealers' secret contributions and hence material of the group key. Even absent full key recovery, a threshold `SecretShare` (wrapped in `Zeroizing` and deliberately `Debug`-redacted at `lib.rs:242-246` precisely because it is secret) is disclosed to actors who were never meant to hold it — the same CWE-200 exposure as the reference advisory.

### Likelihood Explanation
The trigger is a routine protocol path reachable with public inputs: a participant sends/labels a share message and emits a blame-bearing error. Invalid-share handling is a first-class, non-exceptional flow (`InvalidShare` is a defined enum variant), and Rust callers conventionally propagate such errors with `?`, log them via `log`/`tracing` with `{e:?}`, or gossip blame for slashing — all of which serialize the embedded key. No collusion, broken BFT, or leaked key is required to cause the disclosure of at least one honest dealer's share.

### Recommendation
Do not carry the raw ECDH point inside the propagatable error/proof. Restructure blame so the accuser reveals the *decrypted share bytes* together with a proof of correct decryption bound to the ciphertext, or encrypt the blame artifact to the dispute-resolution set only. At minimum, implement a redacting `fmt::Debug` for `EncryptionKeyProof` (as done for `SecretShare`, `Encryption`, `KeyMachine`, and `ThresholdCore`) and document that `InvalidShare::blame` must never be logged or broadcast beyond the parties required to adjudicate, since `key` is itself secret decryption material.

### Proof of Concept
1. Participants run PedPoP; honest dealer Alice sends Bob `EncryptedMessage<SecretShare>` with ephemeral key `msg.key`.
2. Bob (malicious, or an honest node whose error path is logged) calls `Encryption::decrypt`, obtaining `(share, EncryptionKeyProof { key: b_Bob * msg.key, dleq })`, and emits `PedPoPError::InvalidShare { participant: Alice, blame: Some(proof) }` — e.g., via `format!("{e:?}")` into logs, or by broadcasting it for blame adjudication.
3. Any observer of the error takes `proof.key`, calls `cipher::<C>(context, &proof.key)` (both inputs public except `key`, now disclosed), and applies it to the wire-visible ciphertext `msg.msg`, recovering Alice's secret share for Bob — a `Zeroizing`-protected secret now held by parties with no authorization to it, without breaking any primitive.
