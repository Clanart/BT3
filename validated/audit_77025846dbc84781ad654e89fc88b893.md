### Title
Flat top-tier reward multiplier applied to entire deposit amount in non-lock mode allows oversized MGP yield extraction - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount` computes rewards differently depending on `_lock`: the lock branch (`_mode == 2`) correctly brackets the multiplier across tier boundaries, but the non-lock branch (`_mode == 0` or `1`) applies `rewardMultiplier[getUserTier(_account)]` as a flat rate on the entire `_amountToConvert`. An attacker can cheaply lock the minimum `mWomSV` to reach the top reward tier and then call `incentiveDeposit` with an arbitrarily large `_amountToConvert` in mode 0/1 to receive the top-tier multiplier on the whole deposit instead of a blended/bracketed rate.

### Finding Description
`getUserTier` in `wombat/ArbWomUp3.sol` (lines 146-155) returns the highest tier index `i` such that `mWomSV.getUserTotalLocked(_account) >= rewardTier[i]`: [1](#0-0) 

`getRewardAmount` (lines 107-129) branches on `_lock`:
- Non-lock branch: `mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR` — a flat multiplier applied to the entire deposit amount, completely independent of how the tier was reached.
- Lock branch: iterates through `rewardTier`/`rewardMultiplier` and accumulates reward per bracket (`rewardTier[i] - rewardTier[i-1]) * rewardMultiplier[i-1]`), i.e., marginal/bracketed accounting. [2](#0-1) 

`incentiveDeposit` (lines 88-105) calls `getRewardAmount(_amount, msg.sender, _mode == 2)`, so for `_mode == 0` or `_mode == 1` the flat-multiplier branch is used, and `_deposit` (mode 1) simply deposits WOM into `mWom` and forwards it to `smartWomConvert` on the caller's behalf — it does not require any locking of `mWomSV` at all: [3](#0-2) [4](#0-3) 

There is no requirement that `_amountToConvert` bear any relationship to the `mWomSV` balance used to determine the tier. An unprivileged attacker can:
1. Lock the minimal `mWomSV` amount equal to `rewardTier[topTier]` via `mWomSV.lock(...)` (a public/external function, no privileged role required) to reach the top tier cheaply.
2. Call `incentiveDeposit(hugeAmount, ratio, false, 1)` (or mode 0), which routes through the non-lock branch of `getRewardAmount`, granting `hugeAmount * rewardMultiplier[topTier] / DENOMINATOR` in MGP reward — the full top-tier rate on the entire deposit, not just the portion above the tier boundary or bracketed as in the lock path.

None of `whenNotPaused`, `nonReentrant`, or the `_checkAmount` modifier block this since it is a normal, single, non-reentrant call with legitimate inputs — the bug is purely in the reward-calculation logic itself, not a bypass of access control or reentrancy protection.

### Impact Explanation
This matches the "theft of unclaimed yield" impact class. Because the reward pool is a shared, admin-funded MGP balance (bounded by `mgpleft` in `getRewardAmount`), a single attacker exploiting this bug can drain a disproportionate share of that reward budget relative to what an honest, proportionally-computed reward accounting would allow (as demonstrated by the correctly bracketed calculation used for the lock branch). This directly harms other legitimate depositors who would have received rewards from the same pool, and represents an economic loss/insolvency risk for the reward budget.

### Likelihood Explanation
- The attacker needs only capital sufficient to lock `mWomSV` up to `rewardTier[topTier]` (a fixed, admin-configured, comparatively small threshold relative to a large `_amountToConvert`) plus enough WOM to deposit a large `_amountToConvert`.
- All calls (`mWomSV.lock`, `ArbWomUp3.incentiveDeposit`) are public/external, callable by any unprivileged EOA/contract.
- The exploit is fully repeatable up to the limits of `mgpleft` (contract's MGP balance) and the attacker's available WOM capital.
- No governance, oracle, or admin action is required — only normal user-facing functions.

### Recommendation
Make the non-lock branch of `getRewardAmount` use the same bracketed/marginal accumulation logic as the lock branch (using `_amountToConvert` combined with the account's `mWomSV` locked balance, à la `calDoubledCounted`), so that only the portion of a deposit within a given tier bracket receives that tier's multiplier, and depositing above the current tier boundary blends across brackets rather than retroactively applying the top tier's rate to the entire deposit.

### Proof of Concept
Foundry test outline:
1. Deploy/fork `ArbWomUp3` with `rewardTier = [0, T1, T2]` and `rewardMultiplier = [M0, M1, M2]` (`M2 > M1 > M0`), fund the contract with sufficient MGP.
2. Attacker calls `mWomSV.lock(T2)` (minimal lock at the top tier boundary) — confirm `getUserTier(attacker) == 2`.
3. Attacker calls `incentiveDeposit(hugeAmount, ratio, false, 1)` where `hugeAmount >> T2`.
4. Assert `rewardToSend == hugeAmount * M2 / DENOMINATOR` (flat top-tier reward on the entire deposit).
5. Compute the "intended" bracketed reward using the same formula as the lock branch for an equivalent total locked value (`T2 + hugeAmount`) minus `calDoubledCounted` for `T2`, and assert it is significantly smaller than step 4's result — demonstrating the payout discrepancy and quantifying the excess MGP extracted.
6. Assert this excess MGP reduces `mgpleft` available to other legitimate depositors, confirming yield theft from the shared reward pool.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }

            uint256 toSwap = _amount - toDeposit;

            IMWom(mWom).deposit(toDeposit);

            IERC20(wom).safeApprove(smartWomConvert, toSwap);
