## Analog Vulnerability Found

### Title
Clawback batch-claim DOS: a single unspendable coin in a claim batch permanently blocks legitimate coins bundled with it - ([File: chia/wallet/clawback_manager.py])

### Summary
`ClawbackManager.spend_clawback_coins` batches multiple independent clawback coins into a single `WalletSpendBundle` and marks every coin in the batch as "sent" *before* the aggregated bundle is actually accepted by the mempool. If any single coin in the batch is or becomes unspendable (e.g. the sender races the recipient and reclaims their own clawback coin first, causing a double-spend of one coin in the batch), the whole atomic spend bundle fails on-chain, but the other, perfectly valid coins bundled with it are already marked as "sent" and will be silently skipped on every future automatic or manual claim attempt — permanently stranding those funds, exactly like the USDC-banned-address pattern where one bad recipient in a batch DOSes withdrawal processing for everyone else in that batch.

### Finding Description
`auto_claim_coins` groups unspent clawback coins into batches of `auto_claim_batch_size` and calls `spend_clawback_coins` for each batch: [1](#0-0) 

Inside `spend_clawback_coins`, for every coin in the batch the code builds a `CoinSpend`, appends it to a single list, and **immediately calls `increment_sent`** to mark the underlying `TransactionRecord` as pending/sent — before the aggregated bundle has actually been validated or pushed to a full node: [2](#0-1) 

All of the individual `CoinSpend`s collected across the loop are then combined into one `WalletSpendBundle` and returned as a single transaction: [3](#0-2) 

Because Chia coin-set semantics are atomic, if *any single* coin in that combined bundle turns out to be already spent (for example, the original sender clawing back their own coin in a race right before the recipient's auto-claim fires) or otherwise fails on-chain validation, the entire aggregated `SpendBundle` is rejected — none of the coins in that batch get claimed. Yet every coin in the batch already had `increment_sent` called on it. The subsequent guard in the same function skips any coin whose transaction has already been marked sent, unless `force=True` is passed: [4](#0-3) 

Additionally, once the batch's `TransactionRecord` is added via `add_pending_transactions` with `push=True`, the wallet node keeps automatically retrying to push that same (permanently invalid) bundle: [5](#0-4) 

This is the direct analog of the reported bug: `netAtPrice`/`withdrawAuction` batches multiple withdrawal receipts into one loop and reverts entirely if a single blacklisted USDC recipient is hit, stranding everyone else's funds in that batch. Here, `spend_clawback_coins`/`auto_claim_coins` batches multiple independent clawback claims into one atomic spend bundle and marks all of them "sent" regardless of whether the batch as a whole ever succeeds, so one bad/racing coin permanently strands the other, legitimate coins bundled with it (auto-claim will never retry them; only a manual RPC call with `force=True` can recover them).

### Impact Explanation
This causes a spend-triggered transaction-processing halt for otherwise legitimate funds: legitimate clawback recipients who happen to be batched (by the deterministic `auto_claim_batch_size` grouping) together with one bad/racing coin will have their coins marked as sent/pending indefinitely, blocking `auto_claim_coins` from ever retrying them, and requiring the user to discover the issue and manually call `spend_clawback_coins` RPC with `force=True` — exactly the class of "spend-triggered transaction-processing halt" impact called out as acceptable in the validation criteria.

### Likelihood Explanation
This is triggerable by any unprivileged wallet user: a sender of a clawback payment can race their own recipient's auto-claim (or manual claim) by claiming back their own coin first (a legitimate operation for a sender), causing a coin already selected into another batch to become invalid at push time. Given `auto_claim_batch_size` defaults to grouping multiple coins together, this is a realistic race with everyday usage of the clawback feature, not a contrived edge case.

### Recommendation
- Only mark a coin's transaction as `sent`/pending after the aggregated `SpendBundle` has actually been confirmed accepted into the mempool (or move `increment_sent` to occur per-successful-push rather than per-coin during bundle construction).
- Alternatively, verify each coin's current spendability (e.g., via `get_coin_records_by_names`) immediately before inclusion in the batch, and exclude/retry stale coins individually instead of batching them atomically with others whose fate is unrelated.
- Consider building/pushing per-coin spend bundles when the batch fails, so a single bad coin does not affect its batch-mates' claim eligibility.

### Proof of Concept
1. Alice (sender) sends a clawback-eligible XCH payment to Bob (recipient) with a timelock.
2. Once the timelock expires, Bob's wallet's `auto_claim_coins` groups this coin together with `auto_claim_batch_size - 1` other legitimately claimable clawback coins into one batch and calls `spend_clawback_coins` (`chia/wallet/clawback_manager.py:191-205`).
3. `spend_clawback_coins` builds `CoinSpend`s for every coin in the batch and calls `increment_sent` for each one before the aggregate bundle is actually accepted (`chia/wallet/clawback_manager.py:220-263`).
4. Concurrently, Alice submits her own clawback ("send back to me") spend of the same coin, which reaches the mempool/chain first.
5. Bob's aggregated batch `SpendBundle` — which references Alice's now-already-spent coin alongside Bob's other legitimate coins — is rejected as a whole by the full node.
6. Bob's other coins in that batch remain unclaimed on-chain but their `TransactionRecord.sent` is already `>0`, so `auto_claim_coins`'s guard (`incoming_tx.sent > 0 and not force`) causes them to be skipped forever in future auto-claim cycles, permanently stranding Bob's legitimate funds unless he manually issues `spend_clawback_coins` with `force=True` via the RPC.
