## Analysis

The PartyDAO bug's core primitive: an unprivileged actor supplies a self-serving value into a proportional-distribution calculation, redirecting an economic reward to an address of their choosing without the protocol verifying who actually earned it.

The local analog is in `pallet-state-coprocessor`'s reputation-minting path.

`GetRequestsWithProof` carries a caller-supplied `address` field described as "Address that should be credited with fees": [1](#0-0) 

This message is submitted through `handle_unsigned`, which is registered as an **unsigned** extrinsic (`ensure_none(origin)`) — meaning no account signature, stake, or relayer registration is required to submit it, only that `validate_unsigned` re-executes `handle_get_requests` successfully: [2](#0-1) [3](#0-2) 

Inside `handle_get_requests`, after state-proof verification and bandwidth metering succeed, the reputation reward is minted directly to whatever `address` the submitter embedded in the message — with no check that this address corresponds to whoever actually relayed/verified the batch: [4](#0-3) 

### Title
Unauthenticated `address` field in `handle_unsigned` lets any caller redirect relayer reputation rewards to themselves - (File: modules/pallets/state-coprocessor/src/impls.rs)

### Summary
`handle_get_requests` mints `ReputationAsset` to the raw 32-byte `address` field taken verbatim from the caller-supplied `GetRequestsWithProof` payload, with no binding to a signer, registered relayer identity, or the entity that actually performed the state-proof retrieval/relay work.

### Finding Description
State proofs (`source`/`response` `Proof`) required by `handle_get_requests` are derived from publicly observable chain state — any party can independently reconstruct a valid `GetRequestsWithProof` for pending `GetRequest`s once the underlying trie data is available, without needing privileged relayer access, a leaked key, or collusion. Because the call is dispatched via `handle_unsigned` (`ensure_none` origin, gated only by `validate_unsigned` re-validating the same proof logic), there is no account authentication tying the submitter to the `address` field they choose to embed. The mint amount is computed correctly (`bytes × MintPerByte`) but is credited to an arbitrary self-chosen `address`, exactly mirroring the PartyDAO analog where a self-declared value (the attacker's chosen "price"/denominator) let the actor claim a disproportionate, unearned share of a reward pool meant to be fairly distributed among legitimate participants.

### Impact Explanation
This is a wrong-beneficiary fund-diversion bug against the relayer reward pool: any unprivileged party who can construct a valid state proof (a normal, permissionless capability, not requiring a malicious relayer/prover/operator) can mint `ReputationAsset` to their own account instead of the account that actually performed the relaying work, draining the incentive intended for legitimate relayers. This falls squarely under "stealing or loss of funds" / "unauthorized transaction or execution" since the value flow bypasses any check that the beneficiary earned it.

### Likelihood Explanation
High feasibility for a public entry point: `handle_unsigned` requires no signature, no stake, no registration — only a syntactically valid `GetRequestsWithProof` with correct state proofs, which is derivable from public chain data. There is no dedup on `address`, only on the underlying `GetRequest`/response commitments, so the first party to submit a valid batch (regardless of who did the retrieval) claims the mint.

### Recommendation
Bind the credited `address` to cryptographic proof of authorship — e.g., require the extrinsic to be signed and use `ensure_signed(origin)` as the reward recipient (dropping the free-form `address` field), or require `address` to sign over the batch's message hash so `handle_get_requests` can recover and verify it rather than trusting the caller-supplied bytes.

### Proof of Concept
1. Observer watches for pending `GetRequest`s and independently fetches the corresponding source/destination state proofs from public RPC endpoints (no special relayer role needed).
2. Observer constructs a `GetRequestsWithProof` with `address` set to their own 32-byte account.
3. Observer submits `state_coprocessor::handle_unsigned` before the legitimate relayer does.
4. `validate_unsigned` re-runs `handle_get_requests`, which succeeds (proofs are valid), mints `ReputationAsset` to the observer's `address`, and the transaction is accepted since `ensure_none` requires no signer check.
5. The legitimate relayer, who actually ran the off-chain proof-fetching service, never receives the reward — it is fully captured by the observer, mirroring the "early/self-declared value grabs majority share" primitive from the seed report.

			if let Ok(bytes32) = <[u8; 32]>::try_from(address.as_slice()) {
				let relayer: T::AccountId = bytes32.into();
				let bytes_balance: BalanceOf<T> = (total_bytes as u128).saturated_into();

							relayer,
							bytes: total_bytes,
							amount,
						}),

							"state-coprocessor: reputation mint failed for {total_bytes}b: {err:?}",
