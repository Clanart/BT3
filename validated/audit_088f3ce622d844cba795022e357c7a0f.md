## Analysis

The Solana report's root cause is a **stale invariant carried across a state change without revalidation** — `tokens_deposited` can silently reach zero while `vrt_supply` (share count) stays nonzero, and the minting code (`calculate_vrt_mint_amount`) blindly reuses a positional/ratio calculation as if the state were fresh, corrupting share ownership.

The closest structural analog in this GitHub Desktop codebase is **partial-commit line selection tracked by raw line index, which is not revalidated against actual line content when the underlying diff changes** — a TOCTOU-style stale-index reuse that can silently corrupt what a user commits.

### Title
Stale line-index reuse in partial-commit selection allows silent corruption of committed content - (File: app/src/models/diff/diff-selection.ts)

### Summary
`DiffSelection` tracks a user's line-level "include in commit" choices purely as a `Set<number>` of **absolute line indices** (`divergingLines`), computed as `hunk.unifiedDiffStart + lineIndex` [1](#0-0) . When the diff is refreshed (`updateChangesWorkingDirectoryDiff`), the code explicitly acknowledges it cannot guarantee that a previously-selected index still refers to the same content, but proceeds anyway: [2](#0-1) 

### Finding Description
`withSelectableLines` only filters `divergingLines` by **set membership** against the new set of includeable indices — it never checks that the content at that index is the same line the user actually selected: [3](#0-2) 

If a diff is reloaded after the underlying file changes (e.g. autosave/reformat by an editor, a git operation that rewrites the working tree, or a hunk-expansion/whitespace-toggle recompute), the hunk boundaries and `unifiedDiffStart` offsets shift. An index that used to point at line N of an old hunk can end up pointing at a *different* addable/deletable line in the new diff. Because `withSelectableLines` only asks "is this index still includeable?" — not "does it still represent the same text?" — that index is silently retained as "selected," and `isSelected()` will keep reporting it as selected: [4](#0-3) 

At commit time, this same index-based `isSelected(absoluteIndex)` check is what decides which lines are written into the actual patch applied to the index: [5](#0-4) 

There is no re-diffing against the content the user visually reviewed before clicking "Commit" — the commit patch is built from whatever diff is fetched at commit/stage time, filtered by the stale index set. The code comment in `app-store.ts` itself flags this as a known gap: "Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [6](#0-5) 

This is the direct analog of the vault bug: a computation (`isSelected`/`getSelectionType`) that assumes an index-to-content mapping established under a prior state remains valid, and reuses it unchanged after the underlying state (diff hunks) has shifted, with no guard that detects the mismatch.

### Impact Explanation
If exploited (e.g. a file is modified between the time the user makes a partial line selection and the time the commit patch is generated — via an external tool, editor autosave, filter/smudge driver, or any working-tree mutation that reflows line numbers while keeping similar hunk sizes), Desktop can silently include lines the user never selected, or exclude lines the user did select, in the resulting commit and any subsequent push. This is "silent corruption of what the user commits or pushes," directly matching the valid-impact class in scope. It is not a crash or hardening issue — it changes the actual bytes recorded in a git commit without user awareness.

### Likelihood Explanation
The likelihood is moderate: it requires a diff refresh to happen after a partial selection is made and before the commit patch is generated, with hunk offsets shifting in a way that overlaps old and new indices. This can occur through normal, un-suspicious workflows (external editor autosave/reformat while Desktop's file watcher refreshes the diff, or `hideWhitespaceInChangesDiff`/hunk-expansion recomputation), so no admin rights, local exploit tooling, or leaked credentials are needed — only a file that changes shape while a partial selection is pending, which is plausible when working with tooling that autoformats on save or in monorepos with build-time codegen.

### Recommendation
Track selections by durable line identity (e.g., diff-line content hash, or old/new-file line numbers derived from the hunk header) rather than a raw positional index (`unifiedDiffStart + index`), and invalidate/re-derive the entire selection whenever the diff for a file changes, instead of merely intersecting indices with `withSelectableLines`. At minimum, `updateChangesWorkingDirectoryDiff` and the commit path should detect when a diff has structurally changed since the last selection and force the file back to `DiffSelectionType.None` (or re-prompt the user) rather than silently carrying over stale indices.

### Proof of Concept
1. In the Changes view, edit a tracked file to produce a multi-hunk diff.
2. Use partial line selection to select only specific added lines for commit (leaving others unselected), matching the flow exercised in `formatPatch`/`DiffSelection.withLineSelection` [7](#0-6) .
3. While the file remains selected in Desktop (before clicking "Commit"), modify the file externally (e.g. an editor autosave that inserts/removes lines above the selected region, shifting hunk offsets by the same net line count) so Desktop's file watcher triggers `updateChangesWorkingDirectoryDiff`.
4. Observe that `withSelectableLines` preserves the numerically-same `divergingLines` indices as long as they are still "includeable" positions in the new diff, per `app/src/models/diff/diff-selection.ts:320-330`.
5. Commit. Inspect the resulting commit's diff via `git show` and confirm it includes content at those indices that differs from what was visually checked in the UI before the external edit — demonstrating that `isSelected()`/`formatPatch` committed different content than the user selected.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
