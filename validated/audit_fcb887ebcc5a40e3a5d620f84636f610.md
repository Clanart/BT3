## Title
Malicious order beneficiary can reenter `fillOrder` and steal escrowed funds in the Tron `IntentGatewayV2` (missing CEI fix) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The external report's core invariant break is: **a contract-controlled payment recipient can reenter the caller's flow during an ETH transfer, while critical "already settled" state is still unset, and drain funds meant for someone else.** In Hyperbridge's `IntentGatewayV2`, the direct analog is the order `beneficiary` address (fully attacker-controlled, just like a royalty recipient in an ERC-2981 NFT) receiving native-token output payments mid-fill, before the order is marked filled.

The EVM mainline (`evm/src/apps/intentsv2/IntrinsicIntents.sol` and `ExtrinsicIntents.sol`) was explicitly patched for exactly this bug class: both `_fillSameChain` and `_fillCrossChain` now set `_filled[commitment] = msg.sender` **before** any `beneficiary.call{value: ...}("")` is made, and a dedicated regression suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) documents the pre-fix vulnerable state and confirms the CEI ordering blocks reentrancy today. [1](#0-0) [2](#0-1) [3](#0-2) 

The Tron deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, is a separate, monolithic (non-split) copy of `IntentGatewayV2` that mirrors the pre-refactor architecture (same `RequestKind` enum, same `_filled` mapping, same `TRANSACTION_FEES` sentinel, same `onAccept`/`withdraw` dispatch pattern) rather than the patched `IntrinsicIntents`/`ExtrinsicIntents` split used on EVM mainline. [4](#0-3) [5](#0-4) 

## Finding Description
The reentrancy fix's own test comments make the vulnerable pattern explicit: prior to the fix, `_filled[commitment]` was only set inside `_withdraw(finalize=true)`, which runs **after** the beneficiary ETH transfer loop. This let a malicious `beneficiary` contract's `receive()` fallback re-enter `fillOrder` for the same commitment while `_filled` was still zero, allowing escrow theft (fee theft and multi-output escrow theft, both demonstrated in the regression tests). [6](#0-5) 

That fix was applied only to `evm/src/apps/intentsv2/IntrinsicIntents.sol` and `ExtrinsicIntents.sol` — the two abstract contracts backing the current `evm/src/apps/IntentGatewayV2.sol`. The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` retains the older monolithic structure (identical `RequestKind`, `_filled` mapping, `withdraw`/`onAccept` flow) that predates the intentsv2 split, and no `_filled[commitment] = msg.sender` write appears anywhere in that file per repository-wide search — only the patched `evm/src` files contain that CEI-ordering statement. [7](#0-6) 

Since Tron's `IntentGatewayV2` pays the order's `output.beneficiary` (an address fully chosen by the order creator, equivalent to the arbitrary royalty recipient in the Caviar report) with a raw native-value `.call`, and the "filled" guard is not established up front, a malicious beneficiary contract can re-enter `fillOrder` for the same order commitment during that transfer, exactly the primitive described in the external report (fallback-triggered reentry to drain funds meant for a legitimate settlement).

## Impact Explanation
This maps directly to the bounty's "stealing or loss of funds" and "double-settlement" categories: an unprivileged attacker who places (or controls) an order with a contract beneficiary can reenter the fill path, double-spend the escrow, or extract funds beyond the intended fill amount before `_filled` is committed — a fund-loss / wrong-beneficiary-or-amount / duplicate-settlement outcome on a production bridge contract (Tron IntentGateway), not merely a testnet or dependency issue.

## Likelihood Explanation
The attacker only needs to control the `beneficiary` field of an order they solicit fills for (a standard, permissionless action against `fillOrder`) and deploy a contract with a `receive()` fallback — no relayer, prover, governance, or admin compromise is required, matching the "public entrypoint, unprivileged attacker" requirement. The EVM team's own dedicated regression test suite for this exact scenario indicates the underlying bug was previously live and exploitable; the same code shape persists in the Tron contract.

## Recommendation
Apply the same CEI (checks-effects-interactions) fix used in `evm/src/apps/intentsv2/{IntrinsicIntents,ExtrinsicIntents}.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: set `_filled[commitment] = msg.sender` (or an equivalent lock) before performing any native-token transfer to `order.output.beneficiary`, and add a reentrancy guard consistent with the EVM mainline fix and its accompanying test suite (`IntrinsicIntentsReentrancyTest.sol`).

## Proof of Concept
Exact PoC bytecode for the Tron fill function could not be fully confirmed within the available search budget — the tool output only exposed lines 1–120 and 571–660 of `evm/tron/contracts/apps/IntentGatewayV2.sol` (the `onAccept`/dispatch logic), not the body of its `fillOrder`/fill implementation. The evidence supporting this finding is: (1) the EVM mainline's own documented "pre-fix" vulnerable pattern in `IntrinsicIntentsReentrancyTest.sol`, and (2) the repository-wide absence of the `_filled[commitment] = msg.sender` CEI statement outside `evm/src/apps/intentsv2/*.sol`. Confirming the exact vulnerable line numbers in the Tron fill function requires reading the full body of `evm/tron/contracts/apps/IntentGatewayV2.sol` (recommended: a Devin session to pull the complete file, since index size limits may have truncated it here).
