### Title
Unbounded-length numeric-string coercion via Python `int()`/`float()` in JSON parsing enables algorithmic-complexity DoS analogous to CVE-2018-12558 - ([File: python/google/protobuf/json_format.py])

### Summary
CVE-2018-12558 is an algorithmic-complexity DoS in Perl's `Email::Address::parse()`, where attacker-controlled bounded input triggers superlinear (quadratic-like) internal parsing cost due to a missing length/complexity bound on a value handed to a slow conversion routine. The closest structural analog in this Protobuf checkout is in `python/google/protobuf/json_format.py`'s scalar-value coercion path (`_ConvertScalarFieldValue` → `_ConvertInteger`/`_ConvertFloat`, lines [1](#0-0) ), which calls the builtin `int(value)` / `float(value)` on an attacker-controlled JSON string with **no length cap**, while the Java implementation of the same well-known conversion in `JsonFormat.java` explicitly caps numeric string length before doing an equivalent slow conversion (`MAX_NUMERIC_STRING_LENGTH`, lines [2](#0-1) ). This asymmetry across sibling language implementations is exactly the kind of "missing check that exists in a sibling parser" signal called for by the analog rules.

### Finding Description
`_ConvertInteger` in `python/google/protobuf/json_format.py` is reached whenever ProtoJSON is parsed into an int32/int64/uint32/uint64 field and the JSON value is a **string** (protobuf's JSON spec allows/require quoted strings for 64-bit integer fields, and permits numeric strings for 32-bit fields too): [1](#0-0) 

The attacker fully controls `value` (an arbitrary-length JSON string token) through the public `json_format.Parse()` API, and this string is passed straight into `int(value)` (and, on failure, `float(value)`) with no upper bound on its length. `_ConvertFloat`, used for float/double fields, has the same unbounded-length exposure: [3](#0-2) 

CPython's string↔integer conversion for very long decimal digit strings has historically been (and, depending on interpreter build/version, can still be) super-linear — this is precisely the bug class fixed for CPython proper as CVE-2020-10735, and is the same *bug class* as CVE-2018-12558: a bounded network-delivered string is handed unchecked to a conversion routine with worse-than-linear cost in string length, producing CPU-bound denial of service from ordinary client input.

The critical missing invariant is explicit in this very codebase: the Java `JsonFormat.parseBigDecimal` helper documents and enforces exactly this concern for the analogous numeric-string-to-BigDecimal conversion: [4](#0-3) 
That comment states verbatim: *"BigDecimal(String) has O(N^2) time complexity for N-digit strings on JDK < 18, allowing a DoS with a single long numeric JSON value."* The Python implementation of the **same** JSON→scalar coercion has no equivalent length check before calling `int()`/`float()`.

By contrast, the C++ implementation of the same logical operation (`ParseIntInner`/`ParseFp` in `src/google/protobuf/json/internal/parser.cc`) uses `absl::SimpleAtoi`/`absl::SimpleAtod`, which are linear-time and bounded by the JSON lexer's token-length limits, so C++ is not affected: [5](#0-4) 

I was unable to fully verify at what exact digit-count threshold, and on which CPython versions bundled/targeted by this repo's Python bindings, the quadratic behavior is actually present (CPython 3.11+ mitigated `int(str)`/`str(int)` conversion cost with a global digit limit, `sys.set_int_max_str_digits`, defaulting to 4300 digits, which raises `ValueError` rather than hanging — but only for the `int -> str`/`str -> int` conversion path, and only on 3.11+; `float(str)` parsing is a separate code path with different complexity characteristics that I could not fully audit here). This means the severity of the Python analog is version-dependent and I could not confirm exploitability with certainty on the interpreter/runtime versions this repository is meant to support.

### Impact Explanation
If exploitable on the target CPython runtime, an attacker who can submit ordinary ProtoJSON to any application using `google.protobuf.json_format.Parse()` (or `MessageToJson`'s inverse) with an int32/int64/uint32/uint64/float/double field could submit a single JSON value consisting of a very long digit string (bounded, not "huge input" in absolute terms — a few thousand to tens of thousands of characters is enough to matter for a quadratic algorithm) and cause disproportionate CPU consumption in a single parse call, denying service to that worker/thread. This maps to CVE-2018-12558's Denial-of-Service impact class (Availability), not Confidentiality/Integrity.

### Likelihood Explanation
Likelihood is Low-to-Medium and highly version-dependent:
- On modern CPython (3.11+) with the default `int_max_str_digits` guard, `int(very_long_digit_string)` raises `ValueError` well before quadratic blowup becomes severe, which would actually turn this into a normal parse-error path rather than a DoS.
- On CPython < 3.11 (still in wide production use), no such guard exists, and `int()`/`float()` conversion of very long digit strings can exhibit worse-than-linear cost, making the DoS class real, though the practical amplification factor is modest compared to a classical ReDoS.
- I could not confirm from static inspection whether protobuf's Python JSON parser pre-validates token length against the surrounding JSON lexer/`json.loads` limits before this stage (e.g., Python's `json` module itself does not impose a numeric-token length limit either).

### Recommendation
Add an explicit maximum length check on any string handed to `int()`/`float()` in `_ConvertInteger`/`_ConvertFloat` in `python/google/protobuf/json_format.py`, mirroring the `MAX_NUMERIC_STRING_LENGTH` guard already present in `java/util/src/main/java/com/google/protobuf/util/JsonFormat.java` (lines 2309-2321), e.g., reject values whose string length exceeds a small constant (protobuf's own valid numeric representations never need more than a few hundred characters) with a `ParseError`, before any conversion attempt. This closes the language-parity gap and removes the version-dependent risk entirely regardless of CPython version.

def _ConvertInteger(value):
  """Convert an integer.

  Args:
    value: A scalar value to convert.

  Returns:
    The integer value.

  Raises:
    ParseError: If an integer couldn't be consumed.
  """
  if isinstance(value, float) and not value.is_integer():
    raise ParseError("Couldn't parse integer: {0}".format(value))

  if isinstance(value, str) and value.find(' ') != -1:
    raise ParseError('Couldn\'t parse integer: "{0}"'.format(value))

  if isinstance(value, bool):
    raise ParseError(
        'Bool value {0} is not acceptable for integer field'.format(value)
    )

  try:
    return int(value)
  except ValueError as e:
    # Attempt to parse as an integer-valued float.
    try:
      f = float(value)
    except ValueError:
      # Raise the original exception for the int parse.
      raise e  # pylint: disable=raise-missing-from
    if not f.is_integer():
      raise ParseError(
          'Couldn\'t parse non-integer string: "{0}"'.format(value)
      ) from e
    return int(f)

template <typename T>
absl::StatusOr<LocationWith<T>> ParseIntInner(JsonLexer& lex, double lo,
                                              double hi) {
  absl::StatusOr<JsonLexer::Kind> kind = lex.PeekKind();
  RETURN_IF_ERROR(kind.status());

  LocationWith<T> n;
  switch (*kind) {
    case JsonLexer::kNum: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> x = lex.ParseRawNumber();
      RETURN_IF_ERROR(x.status());
      n.loc = x->loc;
      if (absl::SimpleAtoi(x->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*x, &n.value, lo, hi));
      break;
    }
    case JsonLexer::kStr: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
      RETURN_IF_ERROR(str.status());

      n.loc = str->loc;

      // SimpleAtoi will ignore leading and trailing whitespace, so we need
      // to check for it ourselves.
      for (char c : str->value.AsView()) {
        if (absl::ascii_isspace(c)) {
          return lex.Invalid("non-number characters in quoted number");
        }
      }
      if (absl::SimpleAtoi(str->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*str, &n.value, lo, hi));
      break;
    }
    default:
      return lex.Invalid("expected number or string");
  }

  return n;
}

template <typename Traits>
absl::StatusOr<int64_t> ParseInt(JsonLexer& lex, Field<Traits> field) {
  absl::StatusOr<LocationWith<int64_t>> n =
      ParseIntInner<int64_t>(lex, -9007199254740992.0, 9007199254740992.0);
  RETURN_IF_ERROR(n.status());

  if (Traits::Is32Bit(field)) {
    if (std::numeric_limits<int32_t>::min() > n->value ||
        n->value > std::numeric_limits<int32_t>::max()) {
      return n->loc.Invalid("integer out of range");
    }
  }

  return n->value;
}
