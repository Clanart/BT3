### Title
EVM transaction preprocessing trusts a pre-populated `Derived` sender/pubkey field without re-verifying it against the embedded signature - ([File: x/evm/ante/preprocess.go])

### Summary
`PreprocessUnpacked` (used by the EVM ante pipeline) and `EvmDeliverHandleSignatures` (used by the legacy/CheckTx EVM ante path) both contain a fallback: if the `MsgEVMTransaction.Derived` field is already non-nil (and its `PubKey` sub-field is non-nil), the code treats the message as "already preprocessed" and skips the actual ECDSA signature-recovery/verification step entirely, then calls `AssociateAddress`/`AssociateAddresses` using whatever `SenderEVMAddr`, `SenderSeiAddr`, and `PubKey` values are sitting in `Derived`. This is structurally identical to the Feathers OAuth bug class: a fallback chain that, when the "normal, verified" source of authentication data is present-but-unverified, blindly trusts attacker-reachable data instead of re-deriving/verifying it from the cryptographic source of truth (the raw signed Ethereum transaction).

### Finding Description
The Sei EVM ante pipeline derives the transaction sender's EVM/Sei address pair and public key by recovering it from the raw ECDSA signature over the embedded Ethereum transaction (`helpers.GetAddresses` / `RecoverAddressesFromTx`), then stores that result in `msg.Derived` so downstream steps (execution, EIP-7702 authority association, mempool consistency) don't need to redo the recovery.

The problem is the "is it already preprocessed" gate: [1](#0-0) 

and the parallel legacy/CheckTx path: [2](#0-1) 

Both treat `Derived != nil && Derived.PubKey != nil` as proof that the sender/pubkey/address triple was already cryptographically validated earlier in the pipeline. Neither function re-derives the address from the actual embedded signature bytes when taking this branch — they only null-check `PubKey`, then directly call `AssociateAddress`, which itself only checks that `seiAddr` isn't *already* associated: [3](#0-2) 

`MsgEVMTransaction.Derived` is a field on the protobuf message that is submitted as part of the transaction (`proto/evm/tx.proto`), i.e. it is attacker-controlled input in the submitted tx bytes, not a value guaranteed to have been computed server-side from the tx's own signature. Just like the Feathers advisory (an unauthenticated caller reaching `/oauth/:provider/callback` with a forged profile because the expected verified session data was empty, so the code fell back to trusting the raw request), this code has a fallback path that trusts a "looks-already-verified" structure (`Derived.PubKey != nil`) instead of proving that `SenderEVMAddr`/`SenderSeiAddr`/`PubKey` actually correspond to a valid signature over the transaction's own `Data`.

### Impact Explanation
If an attacker can submit a `MsgEVMTransaction` with a forged `Derived` block (arbitrary `SenderEVMAddr`, `SenderSeiAddr`, and any syntactically valid `PubKey` bytes) that reaches this "already preprocessed" branch without being re-verified, `AssociateAddress` will create a permanent Sei↔EVM address mapping for the attacker-chosen pair as long as the target `seiAddr` has no existing association yet (`x/evm/keeper/address.go` `SetAddressMapping`/`GetEVMAddress`). This lets an attacker:
- Front-run/hijack the association of any not-yet-associated Sei address to an EVM address of the attacker's choosing, corrupting the dual-address model (`x/evm/AGENTS.md` describes this bidirectional mapping as security-critical for fund routing via `CanAddressReceive`).
- Potentially forge sender identity for downstream `AssociateAuthorizationAuthorities`/EIP-7702 authority-association logic, which the preprocess.go comments themselves note is security-sensitive ("otherwise SetCode creates a mutable direct-cast EVM->Sei mapping ... can then halt the chain via the distribution validator-removal hook").

This maps to "unauthorized transfer/association via pointer/address bridge" and potential chain-halt conditions explicitly called out in the codebase's own comments about mis-association risk.

### Likelihood Explanation
This requires an attacker to be able to submit a `MsgEVMTransaction` whose `Derived` field is already populated at the point it enters the ante handler (bypassing the normal `Preprocess`/`PreprocessUnpacked` call that would set it from a verified signature). Whether this is reachable end-to-end depends on details I could not fully confirm with the tools available:
- Whether `MsgEVMTransaction.ValidateBasic()` (`x/evm/types/message_evm_transaction.go`) rejects a message that already has `Derived` set at the mempool/ValidateBasic stage before the ante handler runs.
- Whether `helpers.AssociationHelper.AssociateAddresses` performs its own independent pubkey→address consistency check that would still catch a forged triple even after the shortcut.

Both of these are plausible mitigations that may already exist in the codebase and that I was unable to verify within the available tool budget (file reads for `message_evm_transaction.go` and the full `AssociateAddresses` implementation were not completed before the iteration limit). This uncertainty should be resolved before treating this as confirmed-exploitable; if either guard exists and is airtight, the finding is not exploitable as described.

### Recommendation
- In `PreprocessUnpacked` and `EvmDeliverHandleSignatures`, never trust an inbound `MsgEVMTransaction.Derived` value as pre-verified. Either (a) always ignore/clear any externally-supplied `Derived` field before ante processing and always recompute it from the raw transaction signature, or (b) if `Derived` is only supposed to be set internally between ante decorators within a single transaction's lifecycle (never from wire bytes), enforce that via `ValidateBasic` rejecting any message where `Derived != nil`, and additionally re-verify (not just null-check) that `PubKey`, `SenderEVMAddr`, and `SenderSeiAddr` are mutually consistent (`PubkeyToEVMAddress(PubKey) == SenderEVMAddr` and pubkey-derived Sei address `== SenderSeiAddr`) at every point `Derived` is consumed for `AssociateAddress`.
- Add an explicit unit/integration test that submits a `MsgEVMTransaction` with a crafted `Derived` field pointing to an arbitrary victim `seiAddr`/attacker `evmAddr` pair and asserts the transaction is rejected rather than silently associated.

### Proof of Concept
Conceptual PoC (pending confirmation of the `ValidateBasic`/pubkey-consistency gaps noted above):
1. Craft a `MsgEVMTransaction` whose `Data` contains a normally-signed but unrelated Ethereum transaction, but whose `Derived` field is manually set to `{SenderEVMAddr: <attacker-chosen>, SenderSeiAddr: <victim's unassociated address>, PubKey: <any valid secp256k1 pubkey bytes>, Version: <valid>, IsAssociate: false}`.
2. Broadcast this transaction to the RPC/mempool.
3. If `ValidateBasic` does not strip/reject the pre-set `Derived` field, the tx reaches `PreprocessUnpacked`/`EvmDeliverHandleSignatures`, which see `Derived != nil && Derived.PubKey != nil`, skip signature recovery, and call `AssociateAddress(ctx, ek, attackerEvmAddr, victimSeiAddr, forgedPubKey)`.
4. If `victimSeiAddr` had no prior association, `SetAddressMapping` permanently binds it to `attackerEvmAddr`, hijacking the victim's Sei↔EVM identity mapping without ever proving control of a matching private key. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

func PreprocessUnpacked(ctx sdk.Context, msgEVMTransaction *evmtypes.MsgEVMTransaction, chainID *big.Int, isBlockTest bool, txData ethtx.TxData) error {
	if msgEVMTransaction.Derived != nil {
		if msgEVMTransaction.Derived.PubKey == nil {
			// this means the message has `Derived` set from the outside, in which case we should reject
			return sdkerrors.ErrInvalidPubKey
		}
		// already preprocessed
		return nil
	}

func EvmDeliverHandleSignatures(ctx sdk.Context, ek *evmkeeper.Keeper, txData ethtx.TxData, chainID *big.Int, msg *evmtypes.MsgEVMTransaction) (common.Address, sdk.AccAddress, derived.SignerVersion, error) {
	if msg.Derived != nil {
		if msg.Derived.PubKey == nil {
			return common.Address{}, nil, 0, sdkerrors.ErrInvalidPubKey
		}
		evmAddr := msg.Derived.SenderEVMAddr
		seiAddr := msg.Derived.SenderSeiAddr
		version := msg.Derived.Version
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, msg.Derived.PubKey); err != nil {
			return evmAddr, seiAddr, version, err
		}
		if ek.EthReplayConfig.Enabled {
			ek.PrepareReplayedAddr(ctx, evmAddr)
		}
		return evmAddr, seiAddr, version, nil
	}

func AssociateAddress(ctx sdk.Context, ek *evmkeeper.Keeper, evmAddr common.Address, seiAddr sdk.AccAddress, seiPubkey cryptotypes.PubKey) error {
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if !isAssociated {
		associateHelper := helpers.NewAssociationHelper(ek, ek.BankKeeper(), ek.AccountKeeper())
		if err := associateHelper.AssociateAddresses(ctx, seiAddr, evmAddr, seiPubkey, false); err != nil {
			return err
		}
	}
	return nil
}

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}
