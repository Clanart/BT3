## Title
Attacker-controlled `post-checkout` Git hook can reenter the live trampoline credential socket and exfiltrate GitHub OAuth tokens - (File: `app/src/lib/git/checkout.ts`, `app/src/lib/trampoline/trampoline-server.ts`, `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's credential trampoline exposes a live, single-purpose secret (`DESKTOP_TRAMPOLINE_TOKEN`) and TCP port (`DESKTOP_PORT`) in the environment of every spawned `git` process so that Git's askpass/credential-helper callback can "call back" into Desktop for credentials. Most Git operations (commit, merge, pull, push) explicitly proxy and sanitize native Git hook execution through `withHooksEnv`, stripping `DESKTOP_*` variables before the hook runs. `checkoutBranch`, however, never opts into hook interception, so a native `post-checkout` hook inherits the *full* process environment, including the live trampoline token/port. Because the trampoline server authorizes any command solely by token validity — not by verifying the caller is the real askpass/credential-helper binary or that the request matches the operation in progress — a repository-tracked hook script (e.g. via a common `core.hooksPath` convention such as Husky) delivered through a malicious branch/PR can reenter the trampoline mid-checkout and request the user's real GitHub credentials.

### Finding Description
`checkoutBranch()` builds its execution options via `getCheckoutOpts()`, which never sets `interceptHooks`: [1](#0-0) 

Compare this with `createCommit()`, `pull()`, `push()`, and merge operations, which all pass an explicit `interceptHooks` list to route the corresponding native hooks through `withHooksEnv`/`hooks-proxy.ts`: [2](#0-1) 

`withHooksEnv` is the only place that strips Desktop-internal environment variables before a hook executes, via a `GIT_`/`GITHEAD_` allow-list plus an `excludedEnvVars` block-list: [3](#0-2) 

Because `checkoutBranch` never engages this mechanism, `post-checkout` (a hook `hooks-proxy.ts` itself acknowledges by name in `ignoredOnFailureHooks`) runs as a normal native Git hook, inheriting the raw environment that `withTrampolineEnv` injected into the top-level `git` process for the checkout — including `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN`: [4](#0-3) 

The trampoline server accepts any connection presenting a currently-valid token, with no binding to the specific askpass/credential-helper invocation that the token was minted for: [5](#0-4) [6](#0-5) 

The credential-helper "get" handler resolves credentials purely from the requested host/protocol fields sent by the client, with no check that the request originates from the actual git subprocess handling the actual remote of the checkout in progress: [7](#0-6) [8](#0-7) 

`getGitHubCredential` merges the account's real login and OAuth token into the returned credential map: [9](#0-8) 

The broken invariant is the same as the ERC-777 report: a callback that fires as a side effect of an in-flight, trusted operation (Git spawning `post-checkout`) is treated by the "callee" (the trampoline server) as equally trustworthy as the original caller, letting it reenter shared, security-sensitive state (the live trampoline token) before the outer operation completes and obtain more than it should ever be entitled to (a cleartext OAuth token for an arbitrary requested host) — precisely mirroring reentering `depositFor`/`_swap` to withdraw more value than the pending state should allow.

### Impact Explanation
A `post-checkout` hook that reaches this window can synchronously connect to `127.0.0.1:$DESKTOP_PORT`, issue a `CREDENTIALHELPER get` trampoline command for `host=github.com`, and receive the signed-in user's GitHub OAuth token in cleartext — all without any user interaction, dialog, or indication that anything happened. This is credential/token exfiltration of the user's real GitHub account credential, which can then be used to impersonate the user against the GitHub API (read private repos, push code, modify account settings, etc.), well beyond the scope of what checking out a single branch/PR should ever expose.

### Likelihood Explanation
`core.hooksPath` pointing at a repository-tracked directory (Husky, `.githooks/`, `pre-commit` frameworks, etc.) is an extremely common, developer-endorsed convention, meaning hook scripts frequently *are* attacker-influenced repository content once a user opts into reviewing/checking out branches or forks from untrusted contributors — a first-class, unprivileged GitHub Desktop workflow (`checkoutBranch`, PR checkout). No local/admin access or pre-existing malware is required; the only prerequisite is the victim performing an ordinary checkout of attacker-supplied branch content in a repo where they've already configured a tracked hooks path, or being socially steered toward doing so as part of contributing to the project. The gap is also clearly asymmetric with the rest of the codebase: every other hook-bearing Git operation (`commit`, `pull`, `push`, `merge`) was deliberately hardened via `interceptHooks`/`withHooksEnv`, but `checkout.ts` was not, indicating an overlooked path rather than an intentionally accepted risk.

### Recommendation
Route `post-checkout` (and any other native hook triggered by `checkoutBranch`/`updateSubmodulesAfterOperation`) through the same `interceptHooks`/`withHooksEnv` proxy used by commit/pull/push/merge, so `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` are never present in the hook's environment. More generally, bind trampoline tokens to the specific credential/askpass invocation they were issued for (e.g., single-use, operation-scoped, and verified against the expected remote host) rather than accepting any command bearing a currently-valid token, so that even a leaked token cannot be replayed by an unrelated process to request credentials for an arbitrary host.

### Proof of Concept
1. Victim has a repository where `core.hooksPath` is set to a repo-tracked directory (e.g. `.githooks`), a common pattern for shared hook tooling.
2. Attacker opens a PR/branch that modifies `.githooks/post-checkout` to:
   ```sh
   #!/bin/sh
   printf 'CREDENTIALHELPER\0%s\0...get command formatted per trampoline protocol with host=github.com,protocol=https...\0' "$DESKTOP_TRAMPOLINE_TOKEN" \
     | nc 127.0.0.1 "$DESKTOP_PORT" > /tmp/exfil
   # exfiltrate /tmp/exfil (containing username+OAuth token) to attacker server
   ```
3. Victim uses GitHub Desktop to check out the attacker's branch/PR (`checkoutBranch` in `app/src/lib/git/checkout.ts`), which spawns `git checkout` with `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` in its environment (set by `withTrampolineEnv`) and, since `interceptHooks` is never set for this call, allows Git to run `post-checkout` natively with that inherited environment.
4. The hook's TCP request is accepted by `trampoline-server.ts` (token is currently valid), routed to `createCredentialHelperTrampolineHandler`'s `getCredential`, and returns the victim's real GitHub login/OAuth token, which the hook exfiltrates.

  private async processCommand(socket: Socket, command: ITrampolineCommand) {
    if (!isValidTrampolineToken(command.trampolineToken)) {
      throw new Error('Tried to use invalid trampoline token')
    }

    const handler = this.commandHandlers.get(command.identifier)

    if (handler === undefined) {
      socket.end()
      return
    }

    const result = await handler(command).catch(e =>
      log.error('Error processing trampoline command', e)
    )

    if (result !== undefined) {
      socket.end(result)
    } else {
      socket.end()
    }
  }

export const formatCredential = (credential: Map<string, string>) => {
  const lines = []
  for (const [k, v] of credential) {
    if (v.includes('\n') || v.includes('\0')) {
      throw new Error(`forbidden characters in credential value: ${k}`)
    }
    lines.push(`${k.replace(/\[\d+\]$/, '[]')}=${v}\n`)
  }

  return lines.join('')
}
