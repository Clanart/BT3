## Analysis

The vader `vestFor` bug is about an **unprivileged actor being able to trigger a state-changing action on behalf of another user's account, with no consent/auth check, that silently persists and can't be undone**. The closest analog in GitHub Desktop is the automatic, unconfirmed rewriting of a repository's `origin` remote URL based on data returned by the GitHub API (or an Enterprise/self-hosted endpoint, which is effectively a "git remote/proxy response" an attacker can control).

### How it works

When Desktop refreshes a repository's association, it fetches the repo info from the API and, if certain loose conditions are met, silently overwrites the local `origin` remote with whatever `clone_url` the API returned — with **no user confirmation dialog**: [1](#0-0) 

The actual decision logic in `updateRemoteUrl` only checks that the URL *protocol* string matches and that the previously-cached clone URL hasn't been "manually" changed — it never validates the *host* of the new URL: [2](#0-1) 

If those loose conditions pass, it directly calls `gitStore.setRemoteURL`, which executes `git remote set-url` with no prompt: [3](#0-2) [4](#0-3) 

This refresh path (`repositoryWithRefreshedGitHubRepository`) runs automatically in the background whenever a repository is selected/refreshed — there is no user action or confirmation gating it: [5](#0-4) 

### Why this matches the `vestFor` bug class

- **No auth/consent check**: just like `vestFor` let anyone lock a victim's Vader for 365 days, `updateRemoteUrl` lets whatever entity controls the API response (a malicious/compromised GitHub Enterprise Server, or a MITM proxy sitting between Desktop and `api.github.com`) silently overwrite the user's `origin` remote without any dialog or opt-out at the moment it happens.
- **The corrupted value can't be easily detected**: since only protocol (not host) is validated, the new URL can point to a completely different host while looking legitimate.
- **Downstream impact on what the user pushes/fetches**: once `origin` is silently repointed, the user's next `git push`/`fetch`/`pull` in Desktop silently talks to the attacker-chosen destination — this is explicitly one of the listed valid impacts ("silent corruption of what the user commits or pushes", "attacker controls ... a git remote/proxy response").

I'll produce the vulnerability report on this basis.

### Title
Automatic, unconfirmed rewriting of a repository's `origin` remote URL from untrusted API data - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl` is invoked automatically during background repository refresh (`repositoryWithRefreshedGitHubRepository`) and will silently execute `git remote set-url` on the user's `origin` remote based solely on the `clone_url` field of an API repository object, with no user confirmation and no validation of the target host.

### Finding Description
When Desktop refreshes the GitHub metadata for a repository (a routine background operation triggered on repository selection, not a user-initiated "change remote" action), it calls `repositoryWithRefreshedGitHubRepository`, which fetches the repository from the API (`api.fetchRepository(owner, name)`) and unconditionally passes the result into `updateRemoteUrl`: [6](#0-5) 

`updateRemoteUrl`'s only safeguards are:
1. that the *protocol scheme string* ("https:" vs "https:") of the old and new URL match — it does **not** compare hostnames,
2. that the currently configured remote URL still matches the previously-cached `clone_url` for that `GitHubRepository` record (i.e., the user hasn't "manually" diverged it).

If both loose checks pass, and the new URL differs from the current one, it calls `gitStore.setRemoteURL` directly — no popup, no dialog, no dispatcher-level user action required: [7](#0-6) 

Because this whole chain is API-response driven, any party able to influence what the API/endpoint returns for the `clone_url` field of a matched repository — a GitHub Enterprise Server instance (fully controlled by an org admin/attacker), or a network position able to tamper with API responses to a configured endpoint — can cause Desktop to silently repoint a victim's local `origin` remote to an arbitrary destination, entirely without user awareness, similar to how `vestFor` allowed an unprivileged caller to force a persistent, unconsented state change on a victim.

### Impact Explanation
Once `origin` is silently rewritten:
- Subsequent `git push` operations initiated from Desktop's UI will silently send the user's commits to the attacker-controlled destination instead of the intended repository (source/code exfiltration, or overwriting/redirecting collaboration flow).
- Subsequent `git fetch`/`pull` will silently pull refs from the attacker-controlled destination, which the user may review/merge believing it originates from the trusted upstream (supply-chain injection risk).
- The change persists in the local git config and isn't reverted, mirroring the "365-day lock with no way to update" characteristic of the original `vestFor` finding — the user has no in-app signal that their remote was changed.

### Likelihood Explanation
This requires the attacker to control (or MITM) the API/Enterprise endpoint response for a repository the user already has associated in Desktop and matching by owner/name — this is a realistic scenario for GitHub Enterprise Server deployments (where the "trusted" server itself, or a compromised/malicious instance a user is tricked into signing into, is the attack surface) or for network-level tampering scenarios. No local access, no admin rights, and no additional user interaction beyond Desktop's normal, automatic background refresh are required.

### Recommendation
- Require explicit user confirmation (a dialog, similar to other remote-URL-changing flows in `repository-settings/remote.tsx`) before ever calling `setRemoteURL` as a result of an API-driven update.
- Validate that the new URL's hostname matches the expected endpoint's hostname (not just protocol) before considering an automatic update safe.
- Consider only auto-updating the remote URL for well-known rename/transfer events reported directly by github.com, and treat GitHub Enterprise Server responses with additional scrutiny or opt-in configuration.

### Proof of Concept
1. User signs into (or is redirected to) an attacker-controlled/malicious GitHub Enterprise Server endpoint in Desktop, or is on a network where the endpoint's HTTPS responses can be tampered with.
2. User has a repository open in Desktop associated (by remote URL match) with a `GitHubRepository` record whose `clone_url` is `https://legit.example.com/org/repo`.
3. On the next background refresh (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), the attacker-controlled/tampered API response for `GET repos/org/repo` returns `clone_url: https://attacker.example.com/org/repo` (same `https:` protocol scheme, so the protocol check passes; and the DB-cached clone URL still matches the currently configured remote, so `remoteUrlUnchanged` passes).
4. `updateRemoteUrl` (app/src/lib/stores/updates/update-remote-url.ts:42-44) silently calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo')`, executing `git remote set-url origin https://attacker.example.com/org/repo` with no prompt.
5. The user's next push/fetch in Desktop now silently targets `attacker.example.com`.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
```
