### Title
Positional (not identity-based) splicing of AI conflict-resolution hunks lets a crafted merge conflict silently misplace resolved content across hunks - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` rebuilds a conflicted file by scanning for `<<<<<<<` / `=======` / `>>>>>>>` markers with its own regex-based walker and splicing in `hunkResolutions[hunkIndex]` **purely by array position**, exactly as the TWAP seed report's `syncVaderPrice` aggregates `pastLiquidityWeights[i]` purely by loop index. The only safety net, `validateResolutionPaths`, checks that the *count* of returned hunks matches the *count* the conflict-context extractor found for that path — it never verifies that hunk `i` in the LLM response corresponds to conflict block `i` as re-discovered by `reassembleResolvedFile`'s independent marker scan. If the two hunk-counting passes (context extraction vs. reassembly) ever disagree on where blocks start/end while agreeing on total count, or if a "hunk" silently disappears because it's malformed by `reassembleResolvedFile`'s stricter well-formedness check (`hasSeparator && closingIndex !== -1`) but was counted by the context extractor, resolved content is spliced against the wrong original conflict block — silently corrupting what the user commits, unattributed to any error.

### Finding Description [1](#0-0) : the doc comment itself states resolutions are "matched by order, not by line number." The reassembly loop: [2](#0-1) 
scans `rawContent` line-by-line with its own regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`) to find conflict blocks, and only treats a block as valid ("well-formed") when it later finds a `=======` line and a `>>>>>>>` line before EOF; if not, that `<<<<<<<` line is pushed through as ordinary content and **no `hunkIndex` is advanced**.

The gate that is supposed to keep the model's hunk array aligned with the actual file is `validateResolutionPaths`: [3](#0-2) 
This function compares `resolution.hunks.length` against `expectedHunkCounts.get(path)`, where the expected count comes from `IFileConflictContext.hunks` — produced by a *separate* extraction routine (`app/src/lib/copilot-conflict-context.ts`) that must independently walk the same raw file to build the "Conflict 1 of N" prompt shown to the model (referenced at line 245: `"hunks: An ordered array with one entry per conflict in the file, matching the "Conflict 1 of N"... order from the input"`).

This is the same invariant break as the TWAP bug: two loops are each expected to produce parallel, index-aligned collections over the same underlying data, but only their *aggregate size* is cross-checked, not their per-index correspondence. In the TWAP case, `_totalLiquidityWeight` (aggregate) diverged from the per-pair `pastLiquidityWeights[i]` array because some indices were left uninitialized while the loop still completed and the aggregate "looked" fine to callers. Here, if the context-extraction hunk parser and `reassembleResolvedFile`'s marker parser disagree about what counts as a discrete conflict block — e.g., a conflict block containing a `|||||||` common-ancestor section, nested/embedded marker-like strings inside file content (a code file that legitimately contains the literal string `<<<<<<<` in a string literal, comment, or test fixture, or a `.gitattributes`-style diff3 merge with extra separator lines), or a block that the context extractor accepts but `reassembleResolvedFile`'s stricter well-formedness check rejects — the **counts can still match by coincidence** while the **per-index mapping is wrong**, so `validateResolutionPaths` passes silently.

### Impact Explanation
An attacker who controls one side of a merge (a malicious branch/PR/fork the user merges, rebases, or cherry-picks, e.g. via `git remote`/fetch of an attacker repository) can craft a file whose conflict-marker structure is deliberately ambiguous between the two independent marker scanners. If exploited, the model's resolution intended for conflict block #2 gets spliced into conflict block #1's location (or vice versa), or a legitimate resolution is dropped/duplicated. Because the write path trusts `reassembleResolvedFile`'s output as the final, fully-resolved file content and writes it straight to disk before staging (`app/src/lib/stores/app-store.ts:7258`, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`), this results in **silent corruption of what the user commits and later pushes** — the defining impact category for this task. The user sees the resolution dialog, believes each hunk was resolved as summarized, and commits content that does not match either side's intent, with no error, warning, or diff shown for the misalignment itself.

### Likelihood Explanation
This requires: (1) the user has the Copilot-based conflict-resolution feature enabled and invokes it on a merge/rebase/cherry-pick against attacker-influenced content, and (2) the attacker crafts marker-like content in one branch that causes the context extractor's hunk count and `reassembleResolvedFile`'s well-formedness check to diverge while the totals coincidentally match. This is a non-trivial but realistic bar for someone who can place a branch/PR the victim later merges — it needs no local access, no admin rights, and no leaked credentials, matching the "attacker controls a cloned/fetched repository" class explicitly called out as valid. The full independent hunk-parsing routine in `copilot-conflict-context.ts` could not be retrieved within the available tool budget, so I cannot confirm with certainty that its marker-matching regex differs from `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` in a way that is already exploitable today versus merely latent/fragile-by-design; this should be verified by diffing the two parsers directly.

### Recommendation
Do not rely on hunk-count parity as the only cross-check between the context extractor and `reassembleResolvedFile`. Instead:
- Have both passes use the exact same marker-scanning function/regexes (deduplicate the logic into one shared parser used both to build `IFileConflictContext.hunks` and to drive `reassembleResolvedFile`), so a count match structurally guarantees a position match.
- Alternatively, tag each conflict block with a stable identifier (e.g., a hash of its surrounding context or its byte offset) when building the prompt, have the model/validation carry that identifier through, and splice by identifier lookup instead of raw array index.
- Add a guard in `reassembleResolvedFile` that fails closed (throws `CopilotValidationError`) rather than silently falling through to "copy through as regular content" when a `<<<<<<<` line does not resolve to a well-formed block that the context extractor also counted, so any parser disagreement surfaces as an error instead of a silent misalignment.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
