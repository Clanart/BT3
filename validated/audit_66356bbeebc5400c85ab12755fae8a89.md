### Title
Unbounded Python recursion in outer-puzzle driver matching allows an attacker-crafted offer to crash a wallet - ([File: chia/wallet/outer_puzzles.py])

### Summary
`chia/wallet/outer_puzzles.py`'s `match_puzzle()` and the individual outer-puzzle drivers (`CATOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`, `SingletonOuterPuzzle`, `CROuterPuzzle`) each recurse into their puzzle's "inner"/"also" layer with no depth bound whenever a coin's `puzzle_reveal` is parsed. This is directly analogous to the smol-toml bug class: a recursive parser walking attacker-controlled nested structure with no depth limit, causing a Python `RecursionError`/native stack overflow that crashes the process handling the input.

### Finding Description
`match_puzzle()` dispatches to each registered driver's `match()`: [1](#0-0) 

Each driver's `match()` recurses into the puzzle's inner layer and stores the recursive result under `"also"` in the constructor dict, e.g. `CATOuterPuzzle.match()`: [2](#0-1) 

and `OwnershipOuterPuzzle.match()` / `MetadataOuterPuzzle.match()`: [3](#0-2) [4](#0-3) 

None of these `match()`/`construct()`/`solve()`/`get_inner_puzzle()`/`get_inner_solution()` implementations impose any limit on how many times a puzzle can be curry-wrapped ("also"-chained) before recursion is attempted — the recursion depth is entirely determined by the structure of the untrusted `puzzle_reveal` being examined.

This is reachable from untrusted, attacker-supplied data: when a wallet processes an offer (received from a counterparty, e.g. via `chia offer take` or the offer RPC), `Offer.from_spend_bundle()` and `Offer._get_offered_coins()` call `match_puzzle()` directly on each `coin_spend.puzzle_reveal` taken from the (attacker-controlled) spend bundle inside the offer file: [5](#0-4) [6](#0-5) 

An attacker can construct a puzzle reveal that nests many layers matched by these drivers (e.g. repeated CAT/ownership/metadata/CR wrapper layers via curry), each layer adding one Python stack frame to the `match()`/`_match()` recursion chain, with no consensus cost limit preventing the nesting (this happens before/independent of CLVM execution cost accounting, purely from Python-side puzzle structure inspection).

### Impact Explanation
A wallet user or offer-file recipient who inspects (or is prompted to accept) a maliciously crafted offer can have their wallet process crash with a `RecursionError`/native stack overflow while calling `match_puzzle` during `Offer.from_spend_bundle` / `Offer._get_offered_coins`. This is a spend/offer-triggered availability/DoS issue against the wallet process (CWE-674, uncontrolled recursion), matching the reachable-path requirement of an unprivileged offer counterparty causing transaction-processing halt on the victim's wallet.

### Likelihood Explanation
Likelihood is moderate: crafting a deeply "also"-nested puzzle reveal requires only standard CLVM curry composition of existing driver-recognized mod hashes (CAT/ownership/metadata/CR/singleton) and does not require any privileged access — any party who can send an offer file or spend bundle to be parsed by a victim wallet can attempt this.

### Recommendation
Add an explicit recursion/nesting depth limit in `match_puzzle()` and each outer-puzzle driver's recursive `match`/`construct`/`solve`/`get_inner_puzzle`/`get_inner_solution` implementations (e.g., pass and decrement a `max_depth` parameter, raising a clean `ValueError` once exceeded), and wrap offer/puzzle-reveal ingestion paths (`Offer.from_spend_bundle`, `Offer._get_offered_coins`, and any RPC/CLI offer-parsing entry point) in exception handling that treats `RecursionError` as an invalid/untrusted-input error rather than letting it propagate and crash the process.

### Proof of Concept
1. Build a puzzle `P0` matched by `MetadataOuterPuzzle`/`CATOuterPuzzle`/etc. (e.g. `NFT_STATE_LAYER_MOD.curry(...)` with an ACS inner puzzle).
2. Repeat this curry-wrapping N times (e.g. N = 5,000–10,000), each time using the previous puzzle as the new inner puzzle, to produce puzzle `P_N`.
3. Embed `P_N` as a `puzzle_reveal` inside a `CoinSpend` in a `WalletSpendBundle`, and serialize it as an offer file (`Offer(...).to_bech32()`).
4. Have a victim wallet load/inspect the offer (e.g. via `cdv`/RPC `take_offer` preview or `Offer.from_spend_bundle`/`Offer._get_offered_coins`), triggering the recursive `match_puzzle()` chain and causing a Python `RecursionError` / stack overflow that terminates the wallet process.
