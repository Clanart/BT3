### Title
Wrong price feed configured/used for stSTXbtc/zstSTXbtc collateral — DIA/Pyth feed pinned to STX instead of BTC (File: `mainnet/contracts/proposals/mainnet/v0-init.clar` / `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
The reported analog is a mismatch between the intended price source and the price source actually wired into the pricing path, exactly the "price attached to the wrong asset" analog class (the report's bug class of a message/data being incorrectly attributed to the wrong source). In the Zest asset registry initialization and in the read-only pricing helper, the `stSTXbtc` / `zstSTXbtc` assets are documented, named, and capped as BTC-yield-denominated assets but are actually priced using the `STX-FEED-ID` / `PYTH-STX` Pyth feed instead of `BTC-FEED-ID` / `PYTH-BTC`.

### Finding Description
In the asset-registry initialization proposal, asset IDs 10 and 11 (`stSTXbtc` and `zstSTXbtc`, the vault-ststxbtc token) are registered with `ident: STX-FEED-ID`: [1](#0-0) 

The comment right above the code in the market's read-only pricing helper (`get-asset-price`) states the intent explicitly — "stSTXbtc - BTC price (liquid staked STX with BTC yield)" — yet the code calls `get-pyth-price PYTH-STX`, the STX/USD feed, for both `stSTXbtc` and `zstSTXbtc`: [2](#0-1) 

This is the same pattern class as the GnosisBase report: data legitimately obtained through a trusted channel (here, the Pyth oracle price-storage contract, itself correctly verified) gets bound to the wrong logical identity (the STX market instead of the BTC market) at the point of consumption, producing an incorrect valuation that is then trusted by downstream health/LTV logic exactly as `messageSender()`'s payload would be trusted as coming from the wrong `MIRROR_DOMAIN`.

By contrast, every other BTC-denominated asset in the same file (`sBTC`, `zsBTC`) is correctly wired to `PYTH-BTC`: [3](#0-2) 

### Impact Explanation
`stSTXbtc`/`zstSTXbtc` is enabled as collateral-only (no debt) in the initialization proposal: [4](#0-3) 

If STX/USD price diverges materially from BTC/USD price (which they will, being unrelated assets), collateral valued via `get-asset-price` for `stSTXbtc`/`zstSTXbtc` will be systematically wrong (either overstated or understated depending on relative price movement) in every downstream consumer of `sum-collateral-usd`/`get-user-position` in `v0-1-data.clar`, letting users borrow against collateral valued higher than its true worth, or triggering incorrect liquidation/health verdicts. This lands on the in-scope Critical impact class ("protocol insolvency" / theft of funds at rest) if the STX price is used favorably to inflate collateral value beyond the true BTC-pegged worth.

### Likelihood Explanation
This is uncertain/low-confidence as a *live* bug versus a documentation/naming artifact: `stSTXbtc` may in fact be economically pegged 1:1 to STX (a "liquid staked STX" token that merely *distributes yield* denominated in BTC, without its principal value being BTC-denominated) — in which case using `PYTH-STX` would be correct despite the comment. The comment text and asset naming strongly suggest BTC-denominated principal, but I was not able to fully verify the true economic mechanics of the underlying `ststxbtc-token-v2` contract (`SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.ststxbtc-token-v2`) since it is an external, non-in-scope contract, and the index provided does not contain its source. This is the key uncertainty that determines whether this is a real vulnerability or intentional design.

### Recommendation
Confirm with the protocol team whether `stSTXbtc`'s principal value tracks STX or BTC. If it tracks BTC (as the naming, comments, and yield-mechanism description in `docs/vaults.md` suggest — "Liquid staking with BTC-denominated yield"), update both the asset registry `ident` in `v0-init.clar` (lines 131-137) and the pricing logic in `v0-1-data.clar` (lines 581-587) to use `BTC-FEED-ID`/`PYTH-BTC` instead of the STX feed, mirroring the correct `sBTC`/`zsBTC` wiring.

### Proof of Concept
Not applicable as an exploit PoC — this is a configuration/pricing-logic mismatch, not an attacker-triggerable exploit path. Verification requires reading the on-chain `ststxbtc-token-v2` contract's redemption mechanics to confirm whether 1 `stSTXbtc` unit is meant to be valued in STX terms or BTC terms; this could not be confirmed from the indexed repository content alone.
