Based on the investigation, the closest legitimate GitHub Desktop analog to the reported "missing/incomplete validation before invoking git operations" pattern is a **git branch-name argument-injection gap in the deep-link `openrepo` flow**, where the same validation function (`testForInvalidChars`) that gates untrusted `branch` input from a clickable deep link fails to reject leading-dash values, and the downstream `git checkout` argument builder places the (still attacker-influenced) branch name *before* the `--` end-of-options marker.

### Title
Deep-link `branch` parameter is not checked for leading `-`, allowing git-argument injection into `checkout` - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/git/checkout.ts`)

### Summary
`x-github-client://openrepo/...?branch=<value>` is a custom-protocol deep link that any web page or email can trigger with a single click. The `branch` value is validated only by `testForInvalidChars()` [1](#0-0)  before being forwarded, via `Dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch`, into the git `checkout` command builder [2](#0-1) .

### Finding Description
`testForInvalidChars` reuses the same `invalidCharacterRegex` as the ref-sanitizer, but that regex only blocks control characters and git-illegal glyphs (`~^:?*[\|"<>`, `@{`, `..`, leading/trailing dot, `.lock`, trailing `/`) — it does **not** reject a leading `-` [3](#0-2) . Compare this to `sanitizedRefName`, the *sibling* function meant for actually creating refs, which explicitly strips leading `-`/`+` via `.replace(/^[-\+]*/g, '')` [4](#0-3)  — a protection that `testForInvalidChars` (used for the deep-link gate) omits.

Consequently `parseAppURL` will happily accept `branch=--orphan=pwned` or any other `--flag=value` string as a valid `IOpenRepositoryFromURLAction.branch` [5](#0-4) , confirmed by the test suite, which only exercises `<>`-style rejection and never a leading-dash case [6](#0-5) .

Downstream, `getBranchCheckoutArgs` builds the checkout invocation as `[branch.name, ...('-b', name if remote), '--']` — the untrusted name is placed **before** the `--` end-of-options marker [7](#0-6) , so if it begins with `-`, `git checkout` parses it as an option rather than a ref/pathspec, defeating the purpose of appending `--` at all.

### Impact Explanation
This breaks the invariant "the git ref supplied via an app URL is treated strictly as data, never as a command flag." An attacker-crafted deep link can inject a git checkout option (e.g., `--orphan=<name>`, `--track`, `--conflict=<style>`) instead of a real branch, silently altering repository/branch state that the victim believes is a normal "Open in Desktop" checkout — matching the "silent corruption of what the user commits or pushes" impact class for unprivileged deep-link-triggered issues. It does not require local/physical access, admin rights, or prior malware — only a link click, matching the valid-impact criteria.

### Likelihood Explanation
Likelihood is high for the injection to occur (the check is trivially bypassable with a `--` value), but the severity ceiling depends on which `git checkout` flags are reachable through this exact argument position; I could not fully verify `checkoutLocalBranch`'s intermediate logic in `app-store.ts` within the available investigation to confirm whether it passes the raw string straight into a `Branch` object consumed by `getBranchCheckoutArgs`, or performs its own additional sanitization first. This is a gap in my verification, not a claim that it's safe — the two functions I did confirm (`parse-app-url.ts`'s gate and `checkout.ts`'s arg builder) are unambiguous about the missing leading-dash rejection and the unsafe arg ordering.

### Recommendation
1. In `testForInvalidChars` (or specifically in `parse-app-url.ts`'s `openrepo` branch validation), reject values beginning with `-` the same way `sanitizedRefName` strips them, so deep-link-supplied branch names can never be interpreted as flags.
2. In `getBranchCheckoutArgs`, move `--` to appear immediately before the branch name (`['--', branch.name]`) rather than after, so git universally treats it as a pathspec/ref regardless of its content.

### Proof of Concept
1. Host a page (or send a message) containing:
   `<a href="x-github-client://openrepo/https://github.com/victim/repo?branch=--orphan=pwned">Open in Desktop</a>`
2. Victim, with GitHub Desktop installed, clicks the link.
3. `parseAppURL` accepts `branch=--orphan=pwned` because `testForInvalidChars` does not flag the leading `-` [1](#0-0) .
4. `Dispatcher.openBranchNameFromUrl` clones/opens the repo and calls `checkoutLocalBranch(repository, "--orphan=pwned")` [2](#0-1) .
5. The resulting `git checkout` invocation places this string ahead of `--` [7](#0-6) , so git interprets it as `--orphan=pwned` instead of a ref name, silently altering the checkout behavior instead of failing safely or checking out the intended (nonexistent) branch.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
