### Title
Silent auto-rewrite of a repository's `origin` remote URL to attacker-controlled GitHub API data with no user confirmation - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The reported bug pattern is: a privileged setter accepts attacker/mistake-influenced input without validating it against the invariant that protects the system from losing/corrupting a critical, hard-to-recover value, and applies the change silently and irreversibly. In `pants`, `set_mint_multisig()` sets `minting_multisig` without checking for the zero address, permanently bricking a privileged control. The closest Desktop analog is `updateRemoteUrl()` in `app/src/lib/stores/updates/update-remote-url.ts`, which silently rewrites the local `origin` remote's URL to whatever `clone_url` the GitHub API currently returns for the matched owner/name pair — with no user confirmation and no verification that the returned repository is actually the same repository the user originally added.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app/src/lib/stores/app-store.ts` re-resolves the locally tracked repository against the GitHub API purely by owner/name lookup (`matchGitHubRepository`), then calls `api.fetchRepository(owner, name)` and passes the result straight into `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

Inside `updateRemoteUrl`, if the protocol of the new `clone_url` matches the protocol of the existing remote, and the existing remote URL still matches what was last known from the API (`remoteUrlUnchanged`), the code calls `gitStore.setRemoteURL()` to overwrite the local `origin` remote with the new API-provided URL — automatically, without any dialog or user approval: [2](#0-1) 

`setRemoteURL` itself performs no validation on the URL content at all — it hands it straight to `git remote set-url`: [3](#0-2) 

This refresh path (`repositoryWithRefreshedGitHubRepository`) is invoked automatically and repeatedly during normal use — on repository selection, background fetch, push, and account-change refresh — not only on explicit user action: [4](#0-3) [5](#0-4) 

The broken invariant: Desktop assumes that "owner/name still resolves to the same repository" is a durable identity, and uses that identity match alone (rather than verifying repository/database ID continuity) to justify silently rewriting the git remote that the user pushes to and pulls from. If a GitHub repository is deleted, transferred, or renamed and the same owner/name slug is later reused/reclaimed for a different (attacker-controlled) repository, the next background refresh will fetch the attacker's `clone_url` and `setRemoteURL` will silently repoint `origin` at it — with no zero-value/identity check analogous to the missing zero-address check in the `pants` report, and no user prompt (contrast with `UpstreamAlreadyExists` dialog, which does ask the user before changing the *upstream* remote: [6](#0-5) ). There is no equivalent confirmation gate on the `origin` remote update path.

### Impact Explanation
If exploited, all subsequent `git push` operations from the affected local clone go to the attacker's repository, exfiltrating source code and history, and all subsequent `git fetch`/pull would bring in the attacker's commits, silently corrupting what the user believes they are pushing/pulling to/from their own repository. Because the credential trampoline resolves credentials by GitHub host/account rather than by specific repo, the user's own GitHub credentials could end up being used to push private code straight into the attacker-owned repository. This matches the "silent corruption of what the user commits or pushes" category of valid impact.

### Likelihood Explanation
This requires an attacker to control a specific owner/name slug that a victim previously had configured as `origin` for a GitHub-associated repository — for example, by name-squatting an org/user/repo slug after the legitimate repository is deleted, renamed, or transferred (a known, previously-exploited GitHub "repo-jacking" pattern). No local access, admin rights, prior malware, or leaked credentials are needed; the trigger is entirely a matter of API response content returned for a resolvable owner/name, and the refresh runs automatically in the background without user interaction. Existing guards (`protocolsMatch`, `remoteUrlUnchanged`) only check protocol consistency and whether the user manually changed the remote — neither check verifies the fetched repository is the *same* underlying repository (e.g., by GitHub repository ID) that was originally associated, so they do not stop this path.

### Recommendation
Before calling `setRemoteURL` in `updateRemoteUrl`, verify repository identity continuity (e.g., compare `apiRepo.id`/database id against the previously stored `GitHubRepository.dbID`/id, not just owner/name string match) and require explicit user confirmation before silently repointing the `origin` remote, mirroring the existing confirmation flow already used for the upstream remote in `UpstreamAlreadyExists`.

### Proof of Concept
1. User clones repository `github.com/victim-org/project` in Desktop; Desktop stores `gitHubRepository` metadata (owner `victim-org`, name `project`) and `origin` pointing at that clone URL.
2. `victim-org/project` is deleted or renamed, and the `victim-org/project` slug becomes available; an attacker creates a new repository at that exact `owner/name`.
3. On the next automatic refresh (repository selection, background fetch, or push — see `app/src/lib/stores/app-store.ts:4886-4907`), `matchGitHubRepository` resolves the same owner/name, `api.fetchRepository('victim-org','project')` now returns the attacker's repository object with the attacker's `clone_url`.
4. `updateRemoteUrl` sees matching protocol and an unchanged local remote URL (`app/src/lib/stores/updates/update-remote-url.ts:36-45`), and calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` (`app/src/lib/git/remote.ts:56-64`) with no prompt.
5. The victim's subsequent `git push`/`git fetch` in Desktop now silently target the attacker's repository.
