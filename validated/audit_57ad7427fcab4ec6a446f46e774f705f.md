### Title
`EncryptionKeyProof` derives `Debug`, leaking the ECDH shared decryption key (and thus the DKG secret-share plaintext) into error/log output - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2022-4415 is a "security boundary ignored" bug: `systemd-coredump` wrote process memory (including secrets) to a channel readable by a lower-privileged party, ignoring `fs.suid_dumpable`. The Serai analog is in the PedPoP encryption layer: every secret-bearing type in `crypto/dkg` carefully implements a manual, redacting `fmt::Debug` (`SecretShare`, `SecretShareMachine`, `Encryption`, `ThresholdCore`, `ThresholdView`, `BlameMachine`), yet `EncryptionKeyProof` — which contains `key: Zeroizing<C::G>`, the ECDH shared point that directly decrypts an encrypted secret share — uses `#[derive(Debug)]` at `crypto/dkg/pedpop/src/encryption.rs:260-264`. Any `{e:?}` formatting of `PedPoPError::InvalidShare { blame: Some(proof) }` (or accidental debug-printing of the proof) emits the shared decryption key into logs/panic output, subverting the crate-wide "secrets must never be diagnosable" invariant.

### Finding Description
- `EncryptedMessage` ciphertexts are encrypted with `cipher(context, ecdh)` where `ecdh = msg.key * enc_key` (`encryption.rs:95-97,154`).
- `Encryption::decrypt` computes this ECDH key and returns it inside `EncryptionKeyProof { key, dleq }` so that a recipient *may optionally* publish it to attribute blame (`encryption.rs:487-499`). The whole design is that the shared key is revealed **only by deliberate action**, because revealing it lets anyone holding the ciphertext decrypt the secret share (`decrypt_with_proof` at `encryption.rs:381-393` does exactly this with a caller-supplied `proof.key`).
- The `key` field is wrapped in `Zeroizing`, an explicit signal that it is secret material (line 262). Every neighboring secret-holding struct implements `fmt::Debug` manually and omits the secret via `finish_non_exhaustive`: `Encryption` (`encryption.rs:410-420`), `SecretShare` (`pedpop/src/lib.rs:242-246`), `SecretShareMachine` (`pedpop/src/lib.rs:285-295`), `ThresholdCore` (`crypto/dkg/src/lib.rs:266-276`).
- `EncryptionKeyProof` instead does `#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]` (line 260). `Zeroizing<C::G>` forwards `Debug` to the inner point, so `format!("{proof:?}")` prints the full group encoding of the ECDH shared secret.
- Reachability from public input: an unprivileged counterparty feeds bytes into `EncryptedMessage::read` → `KeyMachine::calculate_share` (`pedpop/src/lib.rs:463-499`), which calls `self.encryption.decrypt(...)` and stores a fully-formed `EncryptionKeyProof` per participant in `blames` (line 486), then returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }` (lines 481, 496-498). That error is returned to the integrator, whose natural handling — `log::error!("{e:?}")`, `.unwrap()`/`.expect()`, or `panic!("unknown error: {e:?}")` as done in `processor/src/key_gen.rs:256,427` — writes the shared key to stderr/log files readable by local unprivileged users, exactly the CVE's local information-leak shape.

### Impact Explanation
The logged `key` plus the publicly observable `EncryptedMessage` ciphertext (`key || pop || msg`) is sufficient to recover the secret-share plaintext: `cipher(context, key)` XOR-decrypts `msg` with no further secret. The DLEq inside the proof even lets a third party confirm correctness. This turns the blame mechanism — designed so key disclosure is an explicit, caller-authorized act — into an unconditional disclosure whenever error paths are formatted for diagnostics. Confidentiality of a DKG secret share is lost to anyone with read access to the node's logs, mirroring CVE-2022-4415's CVSS 5.5 local-confidentiality-only profile.

### Likelihood Explanation
Likelihood is moderate. The leak requires (a) a `PedPoPError::InvalidShare` carrying `blame` — triggered by any malicious participant sending a share that decrypts but fails `share_verification_statements` (`pedpop/src/lib.rs:487-499`), i.e., trivially attacker-triggerable — and (b) the integrator formatting the error or the proof with `{:?}`/`{e:?}`, which is the default Rust error-reporting idiom and is already done in-tree via `panic!("unknown error: {e:?}")`. No collusion, key access, or privileged position is needed by the attacker; they only need to send one malformed `EncryptedMessage`.

### Recommendation
Remove `Debug` from the derive on `EncryptionKeyProof` and implement a manual `fmt::Debug` that prints only non-secret context (or calls `finish_non_exhaustive`), matching `SecretShare`/`Encryption`. Optionally, also mark the type `#[zeroize(drop)]`-style handling consistent with other secret containers and add a regression test asserting `format!("{:?}", proof)` does not contain the serialized `key` bytes.

### Proof of Concept
```rust
// crypto/dkg/pedpop — concept only; requires in-crate access to construct the proof.
// 1. Attacker (participant l) sends the victim an EncryptedMessage whose ciphertext
//    decrypts but whose share fails share_verification_statements.
// 2. Victim calls KeyMachine::calculate_share(..), which builds
//    EncryptionKeyProof { key: ecdh(enc_key, msg.key), dleq } and returns
//    PedPoPError::InvalidShare { participant: l, blame: Some(proof) }.
// 3. Integrator executes the standard idiom:
      log::error!("key generation failed: {e:?}");
//    Because EncryptionKeyProof derives Debug, the log now contains the hex/bytes of
//    `key` — the ECDH shared secret.
// 4. Anyone reading the log reconstructs the cipher:
      cipher::<C>(context, &Zeroizing::new(logged_key)).apply_keystream(ciphertext.as_mut());
//    recovering the secret share plaintext without ever possessing enc_key.
```

Caveat: this is confirmed by code analysis, not execution. Residual uncertainty is whether any production integrator actually `{:?}`-formats a blame-bearing error today; the in-tree `panic!("unknown error: {e:?}")` sites show the pattern is realistic, but the proof-bearing `InvalidShare` variant is explicitly handled before those panics, so the leak requires either a non-`InvalidShare` `PedPoPError` carrying debug-printable secrets or downstream `{:?}` formatting of `InvalidShare`.
