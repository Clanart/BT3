### Title
Chainlink price division in `SimplexPaymaster._tokenPrice()` can truncate to zero, letting UserOps sponsor gas for free - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` sponsors ERC-4337 gas in exchange for ERC-20 tokens, converting the wei cost into token units via `_tokenPrice()`. The formula performs an integer division whose denominator scales with the *token's* USD price while the numerator scales with the *native asset's* USD price and the token's decimals. For any registered token whose USD value is large relative to the chain's native asset and whose decimals are not large enough to compensate, `_tokenPrice()` truncates to `0`, exactly the class of bug described in the Surge report (`_totalDebt * _borrowRate * _timeDelta / (365 days * 1e18)` truncating interest to `0`). Because `PaymasterERC20._erc20Cost` multiplies `weiCost * tokenPrice / 1e18`, a `tokenPrice` of `0` means the paymaster sponsors the UserOp's gas while charging the sender `0` tokens — a direct, unconditional loss of treasury/deposit funds with no privileged actor, malicious relayer, or governance mistake required.

### Finding Description
`_tokenPrice()`:
```solidity
function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
    uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
    uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);
    return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
}
``` [1](#0-0) 

This value is consumed unmodified by OpenZeppelin's `PaymasterERC20`, which computes `erc20Cost = weiCost * tokenPrice / 1e18` per the contract's own comment:
```solidity
///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
///      so tokenPrice must be token base units per wei, scaled by 1e18:
``` [2](#0-1) 

There is no lower bound / non-zero check anywhere on `tokenPrice` — neither in `_fetchDetails`, `_validatePaymasterUserOp`, nor in `_registerToken`/`_setParams`: [3](#0-2) [4](#0-3) 

Root cause: whenever `nativeUsd * 10^tokenDecimals * (10000+markupBps) < tokenUsd * 10000`, integer division rounds the whole expression down to `0`. This is the exact "small numerator vs. large denominator" pattern from the Surge report — the only difference is the domain (USD-price ratio + token decimals vs. interest-rate + time-delta), but the corrupted value and the resulting fund-loss mechanic are structurally identical. A concrete case: a low-value-native L2 (e.g. native token worth `$0.0001`, `nativeUsd = 1e4` at 8-decimal normalization) paired with a high-value, low-decimal registered token (e.g. an 8-decimal wrapped BTC-like asset at `$60,000`, `tokenUsd = 6e12`): `numerator = 1e4 * 1e8 * 10_000 = 1e16`, `denominator = 6e12 * 10_000 = 6e16` → `tokenPrice = 0`. Any UserOp paying with that token on that chain is sponsored for free.

Existing guards do not stop this: `_getOraclePrice` only checks staleness/positivity of the Chainlink answer, not the resulting ratio; `_registerToken` performs no sanity check that a token/chain combination is "priceable" (unlike `BandwidthManager.purchase()`, which explicitly guards the analogous division with `if (total18d % scale != 0) revert PriceNotRepresentable();` at `evm/src/apps/BandwidthManager.sol:159-161` — SimplexPaymaster has no equivalent revert-on-truncation).

### Impact Explanation
This is a direct fund-loss/unauthorized-execution path within a live Hyperbridge contract: the paymaster's ERC-20 deposit/EntryPoint stake is drained gas-payment-by-gas-payment while the token side never charges the sender. Any address can submit UserOps that pass paymaster validation and consume the paymaster's EntryPoint deposit for zero cost, repeatedly, until governance notices and deactivates the token/chain pair. This matches the bounty's "stealing or loss of funds" and "unauthorized execution" categories, executed entirely by an unprivileged UserOp sender against production paymaster logic — no relayer/prover/admin compromise required.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only a specific combination of (a) a registered ERC-20 token with a Chainlink feed and (b) a chain whose native asset's USD value, scaled by that token's decimals, is small relative to the token's USD value. Because governance registers tokens per-chain via `RegisterToken` without any onchain check that the ratio is representable, and because relative asset prices drift over time (a token could be registered when the ratio was safe and become unsafe later as prices move), this can arise both from an initial misconfiguration and organically from market movement, without any code change or malicious actor.

### Recommendation
Add an explicit non-zero (and ideally minimum-precision) check on the computed `tokenPrice`, mirroring the pattern already used in `BandwidthManager.purchase()`:
```solidity
uint256 price = (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
if (price == 0) revert PriceNotRepresentable();
return price;
```
Alternatively, increase the precision of the intermediate calculation (e.g., scale numerator up before dividing and scale back down after, using a higher fixed-point base such as 1e27) so that legitimate low-ratio token/chain combinations don't silently round to zero, and revert instead of silently returning `0` in `_fetchDetails`/`_tokenPrice` so `validatePaymasterUserOp` fails closed rather than sponsoring for free.

### Proof of Concept
1. Deploy `SimplexPaymaster` on a chain whose native asset is priced very low in USD (e.g., set a mock native oracle returning `nativeUsd` normalized to `1e4` at 8 decimals, analogous to a $0.0001 native token).
2. Register a token with `tokenDecimals = 8` and a mock oracle returning `tokenUsd = 6e12` (8-decimal-normalized, i.e., $60,000) via `RegisterToken` governance flow (`_registerToken`).
3. Call `paymaster.getTokenPrice(token)` — per the formula `(1e4 * 1e8 * 10_000) / (6e12 * 10_000) = 1e16 / 6e16 = 0` (integer division truncates).
4. Submit a `PackedUserOperation` with `paymasterData` mode `0x01` (approve) referencing that token. `_fetchDetails` returns `tokenPrice = 0`; `PaymasterERC20` computes `erc20Cost = weiCost * 0 / 1e18 = 0`.
5. The paymaster sponsors the operation's gas from its EntryPoint deposit while `transferFrom` moves `0` tokens from the sender — repeatable indefinitely, draining the paymaster's deposit with zero cost to the caller. [1](#0-0) [5](#0-4) [6](#0-5)

    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
