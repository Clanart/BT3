### Title
Path-containment bypass in `resolveWithin()` allows writes outside the repository via prefix-sharing sibling directories - (File: `app/src/lib/path.ts`)

### Summary
The bug reported for `starknet-perpetual` is a broken invariant check: a boundary condition (`total_risk == 0`) that the guard function does not correctly special-case, causing the containment/health check to behave incorrectly at the edge. GitHub Desktop's repo-root containment guard, `resolveWithin()` in `app/src/lib/path.ts`, has the same class of defect: its final containment test is a naive string-prefix comparison that does not verify a path-separator boundary, so a resolved path whose *string* begins with the root path — but which is actually a sibling directory, not a subdirectory — passes the guard.

### Finding Description
`resolveWithin()` computes the final answer with: [1](#0-0) 

```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)

return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path segments. If `realRoot` is e.g. `/Users/victim/Documents/GitHub/project`, then a `realResolved` of `/Users/victim/Documents/GitHub/project-secrets/creds.txt` (or `project-old/…`, `project.bak/…`, `project2/…`) also satisfies `startsWith(realRoot)`, even though it lives in a completely different, sibling directory. The existing unit tests only cover `..` traversal and symlink traversal cases, never the sibling-prefix case, so this gap is unverified: [2](#0-1) 

This function is the sole containment guard used in at least three attacker-reachable call sites:

1. Building AI conflict-resolution context from repository files: [3](#0-2) 

2. Writing Copilot's AI-generated conflict resolution content back to disk — the *write* path, gated only by this check before `writeFile`: [4](#0-3) 

3. Opening a file path from an `x-github-client://` deep link: [5](#0-4) 

The exploitable primitive is call site (2): `resolution.path` is not a raw git-status path but a structured field returned by the Copilot conflict-resolution model, whose *prompt context* is built directly from attacker-controlled repository content (conflicting file text, commit messages, PR metadata) via `buildConflictContext`/`gatherCommitContext`. A repository author who can influence the text seen by the model (conflict markers, code comments, commit messages included in the prompt) can attempt to make the model emit a `resolution.path` naming a sibling directory that shares the repository folder name as a string prefix (e.g. cloned as `~/Projects/app`, target `~/Projects/app-shared/…`, `~/Projects/app.bak/…` — naming conventions many users actually use for multiple checkouts, backups, or `-old`/`-2` copies). Because `resolveWithin` only checks `startsWith`, such a path is accepted as "inside the repo" and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` executes outside the true repository root.

### Impact Explanation
A successful bypass yields an unprompted, silent file write outside the intended repository boundary using content that is effectively attacker-influenced (via prompt injection from repository content into the AI conflict-resolution flow). Depending on the victim's directory layout, this can overwrite files in a sibling checkout, a backup copy, or another repository the user has cloned nearby — corrupting work outside what the user intended to touch, and in the worst case landing in credential-adjacent locations if such directories happen to share the prefix. This matches the required impact class of "file write... outside the repo" and "silent corruption of what the user commits."

### Likelihood Explanation
Exploitation requires two conditions to align: (a) the victim has a sibling directory whose name is a superstring of the repository's folder name (a common occurrence — `project`, `project-old`, `project.bak`, `project2`), and (b) the attacker can steer the Copilot conflict-resolution model's output path via content in the repository/PR that becomes part of the AI prompt (prompt injection), which is not guaranteed and depends on model behavior/guardrails. This makes the attack plausible but not trivially reliable, and it is gated behind the user opting into AI-assisted conflict resolution. It is nonetheless a genuine logic bug in a security-relevant primitive (`resolveWithin`) used as the last line of defense in multiple call sites, rather than a defense-in-depth nicety.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-separator boundary, not just a string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing the root as a string prefix (e.g. root `/tmp/foo`, candidate `/tmp/foobar/x`) is rejected.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdtemp, mkdir } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

const base = await mkdtemp(join(tmpdir(), 'root-'))     // e.g. /tmp/root-abcXYZ
const root = join(base, 'project')                        // /tmp/root-abcXYZ/project
const sibling = join(base, 'project-secrets')              // shares "project" as string prefix
await mkdir(root)
await mkdir(sibling)

// Craft a relative segment that resolves (after join/normalize) to the sibling dir
const result = await resolveWithin(root, '..', 'project-secrets', 'creds.txt')
console.log(result)
// BUG: returns a non-null path because
// "/tmp/root-abcXYZ/project-secrets/creds.txt".startsWith("/tmp/root-abcXYZ/project")
// is true, even though project-secrets is not inside project.
```
This demonstrates that `resolveWithin` fails to reject a path that escapes into a sibling directory, which is the exact guard relied upon before `writeFile` in `app/src/lib/stores/app-store.ts` (line 7258) when persisting AI-generated conflict resolution content.
