### Title
Copilot conflict-resolution writes/stages files not verified against the actual conflicted-file set - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop's Copilot-assisted merge/rebase/cherry-pick conflict resolution feature sends the set of conflicted files (paths, hunks, and PR/commit context) to a Copilot model and receives back a list of per-file resolutions, which are then written to disk and staged for commit. The code that applies these resolutions validates that each resolution's `path` resolves *within* the repository (guarding path traversal) but does not appear to validate that the resolved path is actually a member of the *original conflicted-file set* that was sent to the model for this operation.

### Finding Description
In `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7171-7270`), the function iterates `copilotResolutions` and, for content-based resolutions, does: [1](#0-0) 

The only checks performed per-resolution are: (1) `resolveWithin(repository.path, resolution.path)` — a path-traversal/symlink guard ensuring the target stays inside the repo — and (2) a "don't clobber if user already resolved externally" check based on whether the file still has unresolved conflict markers. Neither check verifies that `resolution.path` is one of the paths actually included in the conflict context sent to the model, built by `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:367-469`), which is fed by data such as PR titles/bodies and commit summaries — content that can be attacker-influenced if the incoming branch/PR being merged contains a crafted body (a GitHub API object under attacker control, per `IConflictContextPullRequest`, `app/src/lib/copilot-conflict-context.ts:78-85`, and `appendPullRequest`, lines 600-610).

This is structurally the same class of bug as the reported Solidity issue: a guard checks a *proxy condition* (path is within the repo) instead of the *actual invariant that matters* (path is a member of the specific conflicted-file set this operation is meant to touch), analogous to checking `buy.constraints[0] <= sell.constraints[0]` instead of `numConstructedItems <= sell.constraints[0]`.

### Impact Explanation
If a model response (influenced via prompt injection embedded in a PR description/commit message that gets included in the prompt, see `formatConflictContextForPrompt`, `app/src/lib/copilot-conflict-context.ts:482-594`) includes a resolution entry for a path outside the intended conflicted-file set but still inside the repository, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` (`app/src/lib/stores/app-store.ts:7258`) will silently overwrite that file's contents, and the path is added to `pathsToStage` and subsequently `git add`-ed (`app/src/lib/stores/app-store.ts:7262-7267`), meaning the corrupted content is silently included in what the user commits/pushes — without the user reviewing it as part of a legitimate conflict.

### Likelihood Explanation
I could not confirm from the available index whether `app/src/lib/copilot-conflict-resolution.ts` (the response parser) already restricts resolution entries to the known conflicted-file list before they reach `_applyCopilotConflictResolutions` — this file's content was not fully retrievable within available searches. If such a whitelist check exists in the parser, this finding would be mitigated. Given I cannot verify this, I am flagging this as an unconfirmed but structurally supported hypothesis rather than a certain finding.

### Recommendation
In `_applyCopilotConflictResolutions`, before writing/staging any resolution, explicitly check `resolution.path` against the list of conflicted files gathered for this operation (e.g. `multiCommitOperationState`'s original conflict list) and reject/skip any resolution whose path isn't a member, in addition to the existing `resolveWithin` traversal guard.

### Proof of Concept
