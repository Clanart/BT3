## Title
Gasless Module Forces Unlimited ERC20 Approval To `GaslessSwapRouter`, Creating Unbounded Standing Allowance Exploitable On Router Compromise — (File: kaiax/gasless/impl/getter.go)

## Summary
The `kaiax/gasless` module implements KIP-247 gasless transactions by validating a strict two-transaction sequence: a `GaslessApproveTx` followed by a `GaslessSwapTx`. The module's validation logic in `isApproveTx` **mandates** that any `GaslessApproveTx` promoted, bundled, and executed by the node must set the ERC20 allowance to exactly `abi.MaxUint256` — not the amount actually needed for the swap. This is the same root-cause pattern as the referenced Notional/Index-Coop finding: granting (and never revoking) allowance far larger than what is required for the immediate operation, leaving a large, permanent "residual allowance" that turns the counterparty contract (`GaslessSwapRouter`) into a single point of failure capable of draining the full token balance of every user who has ever completed a gasless swap.

## Finding Description
`GaslessModule.isApproveTx` in [1](#0-0)  enforces condition A4: `args.Amount.Cmp(abi.MaxUint256) == 0`. Any approve transaction that does not set the allowance to the maximum possible `uint256` value is rejected as an invalid gasless transaction — see the doc comment explicitly listing this as a required condition [2](#0-1) .

Because this is a hard protocol rule (used both for tx-pool promotion via `GetCheckBalance`/`IsModuleTx` and for RPC validation via `IsGaslessTx`/`VerifyExecutable`), every user who wants gasless-swap functionality is compelled to grant `type(uint256).max` allowance on their ERC20 token to the `GaslessSwapRouter` contract, even though the actual swap only needs `amountIn` [3](#0-2) . The subsequent swap consumes only the required amount via `transferFrom`, but the module never reduces or resets the allowance afterward — there is no analog to the mitigation recommended in the C4 report (approve on demand, reset to zero after use).

The `swapRouter` address itself is not a fixed, audited constant chosen once — it is re-read every block from the KIP-149 `SystemRegistry`'s `GaslessSwapRouterName` record via `updateAddresses`/`getGaslessInfo` , and can be changed by the registry owner with a scheduled activation block, as exercised in tests [4](#0-3) .

The combined effect is that (a) the module forces users into unlimited standing allowances rather than bounded, per-swap allowances, and (b) the spender of that unlimited allowance is a single shared contract whose logic (and, in principle, its registry pointer) is external to the individual user's control. Any bug, logic flaw, or malicious update affecting `GaslessSwapRouter`'s ability to call `transferFrom` on behalf of approved senders would allow draining the **entire token balance** of every user who ever executed a `GaslessApproveTx`, not just the amount intended for their swap.

## Impact Explanation
This qualifies as Medium/High because:
- The blast radius of any bug in the single whitelisted `GaslessSwapRouter` contract is amplified to the full token balances of the entire user base that used gasless swaps, rather than being limited to each individual swap amount.
- The module's own validation logic (`isApproveTx`, `IsExecutable`, `VerifyExecutable`) actively rejects bounded/limited approvals as invalid, so users cannot mitigate this themselves by approving only what is needed — the unbounded grant is a mandatory, protocol-level requirement.
- This directly mirrors the cited finding's core concern: residual/unbounded allowance held by a trusted external counterparty contract turns any future compromise or bug in that counterparty into unauthorized value movement out of user accounts, reachable by any unprivileged user simply using the documented gasless-swap flow.

## Likelihood Explanation
Likelihood is moderate: exploitation requires a bug or compromise in the `GaslessSwapRouter` contract logic (or a routing update that reuses/attacker-controls the registered spender address) to actually trigger fund loss, so this is a latent amplifier rather than an immediately triggerable drain by itself. However, because the max-approval requirement is baked into consensus-adjacent validation rules (tx pool promotion, bundling, and RPC `IsGaslessTx`), it cannot be avoided by cautious users, and the exposure persists indefinitely for every gasless-swap participant.

## Recommendation
- Change `isApproveTx`'s A4 condition to accept (and require) an allowance bounded to the amount needed for the paired swap (`swapArgs.AmountIn`) rather than mandating `abi.MaxUint256`.
- After a `GaslessSwapTx` executes, have the bundling/execution logic emit or require a follow-up reset of the allowance back to zero (or design the flow so allowances are set to the exact `amountIn` each time), eliminating the permanent unbounded allowance held by `GaslessSwapRouter`.
- If exact-amount approvals are impractical given the two-step approve/swap tx-pool design, at minimum bound the approved amount to the maximum single-swap amount plus a defined safety margin, rather than `type(uint256).max`, to reduce the blast radius of any future `GaslessSwapRouter` compromise.

## Proof of Concept
1. A user submits a `GaslessApproveTx` approving `GaslessSwapRouter` for `amount = 100 tokens` (its intended swap amount).
2. `GaslessModule.isApproveTx` rejects this because `args.Amount.Cmp(abi.MaxUint256) != 0` (see condition A4) — see [1](#0-0) . The tx is never promoted/bundled as part of the gasless flow, forcing the user to instead approve `MaxUint256`.
3. User instead submits `approve(GaslessSwapRouter, MaxUint256)` + `swapForGas(token, 100, ...)`. This passes validation and is bundled/executed, leaving the router with unlimited standing allowance on the user's token even though only 100 tokens were consumed — confirmed by `checkBalanceForSwap`'s allowance check only requiring `allowance >= amountIn`, not equality [5](#0-4) .
4. Any future logic error or exploit in `GaslessSwapRouter` that allows an unauthorized `transferFrom` call (e.g., missing access control on a swap-triggering function, or a bug reachable by any caller) can now drain the user's **entire** token balance, not just the 100 tokens from step 3, because the standing allowance is `MaxUint256`.

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}
