### Title
Conflict-marker regex collides with ordinary file content (e.g. Markdown Setext headings), causing Copilot conflict resolution to splice content into the wrong location and silently corrupt the committed merge - (File: `app/src/lib/copilot-conflict-resolution.ts`, `app/src/lib/copilot-conflict-context.ts`)

### Summary
Copilot's merge-conflict auto-resolution pipeline identifies conflict-hunk boundaries with bare line-pattern regexes (`/^<{7}(?:\s|$)/`, `/^={7}$/`, `/^>{7}(?:\s|$)/`) both when it *extracts* hunks to send to the model (`extractConflictHunks`) and when it later *reassembles* the model's per-hunk answers back into the file (`reassembleResolvedFile`). Neither function verifies that a matched "separator" or "closing" line actually belongs to the real conflict block it is inside of — it just takes the first line that matches the pattern. Ordinary, attacker-supplied file content that happens to match these 7-character patterns (most commonly a Markdown Setext heading underline of exactly `=======`, but also ASCII banners or `<<<<<<<`/`>>>>>>>`-shaped text) will be misinterpreted as a real marker. This desynchronizes where "ours" content ends and "theirs" content begins, so the reassembled file silently mixes and mis-splices real conflict content with unrelated bytes, and Copilot's suggested resolution gets written to disk, staged, and committed — without the underlying structural corruption being validated anywhere in the pipeline.

Then it keeps consuming lines as "theirs" content until it hits the first line matching `theirsMarker`: [3](#0-2) 

Separately, `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` re-implements essentially the same naive scan when splicing the model's resolved text back into the original file, using its own copies of the same regexes: [4](#0-3) [5](#0-4) 

Both scans treat *any* line that happens to match `/^={7}$/` (exactly seven `=` characters) as a real conflict separator, and any line matching `/^<{7}(?:\s|$)/` / `/^>{7}(?:\s|$)/` as a real opening/closing conflict marker. This pattern is not unique to Git conflict markers: a Markdown Setext H1 underline is conventionally written as a line of `=` characters (frequently exactly 7, e.g. under a 7-character title, or simply because an author typed `=======` as a divider), and `<<<<<<<`/`>>>>>>>`-shaped ASCII banners appear in changelogs, patch/diff examples, and code comments. If such content sits between the real `<<<<<<<` opening marker and the real `=======`/`>>>>>>>` markers of an actual merge conflict in the same file, `extractConflictHunks` will stop collecting "ours" content prematurely at the fake separator, and everything after it — including the real separator and the real "theirs" content — gets folded into what the model is told is "theirs content." The model's resolution is then generated from this corrupted view of the conflict.

Because `reassembleResolvedFile` performs an independent but structurally identical naive scan over the *same* raw file to decide where to splice the model's single resolved block back in, it locates the exact same (wrong) span, so the whole poisoned region — spanning content the user never intended to touch — is replaced verbatim by whatever the model returned for that single hunk. The only downstream validation is a check that the model's `resolvedContent` doesn't itself still contain the literal marker substrings; there is no check that the reconstructed file structurally corresponds to what a correct 3-way merge would have produced. ### Impact Explanation
An attacker who controls a branch, pull request, or fork that a victim later merges/rebases with in GitHub Desktop (i.e., a "cloned/fetched repository" scenario, no local access or credentials required) can craft an ordinary-looking file (README, docs, changelog) containing a line of exactly seven `=` characters (or `<`/`>`-based banner) positioned so that it collides with the marker-detection regexes around a genuine conflicting region. When the victim uses the Copilot conflict-resolution feature, the tool will mis-detect hunk boundaries, causing the reassembled committed file to have entire spans of code silently replaced, duplicated, or dropped relative to what either branch actually contained. This is a silent corruption of what gets committed and subsequently pushed, matching the "unprivileged repository content controls code the user later commits" impact class. The user is expected to trust Copilot's auto-resolution, and nothing in the pipeline flags that the underlying hunk boundaries were wrong — only that the model's raw text output doesn't contain literal marker strings, which does not detect this failure mode.

### Likelihood Explanation
The pattern that triggers this (`=======` as a Markdown Setext heading underline, or `<<<<<<<`/`>>>>>>>` style banners in comments/changelogs) is common in real-world repositories and does not require unusual or suspicious-looking content, making it easy to disguise as legitimate documentation. It does require that the poisoning content and a real conflict co-exist in the same file at the time of merge, which an attacker can arrange deliberately by proposing a branch/PR that touches such a file. It is a UI/data-integrity bug reachable purely from repository content the attacker controls, without any privileged access, matching the "Valid Impact" criteria in this task.

### Recommendation
- Make `extractConflictHunks` and `reassembleResolvedFile` share a single, structurally-aware conflict-marker parser (rather than two independently-implemented naive regex scans) so they can never disagree on hunk boundaries.
- Require markers to appear in the correct git-generated sequence and, ideally, validate that the "ours"/"theirs" branch labels captured after `<<<<<<<`/`>>>>>>>` match the expected `oursLabel`/`theirLabel` for the current operation, rather than accepting any line that merely matches the bare 7-character pattern.
- After reassembly, verify the reconstructed file's non-conflict regions are byte-identical to the pre-resolution working tree outside of the actual conflict hunks (as computed via `git diff` against the pre-merge blobs) before allowing it to be staged/committed, to catch any boundary-detection disagreement before it silently reaches the commit.

```
=======
alpha
```
2. On branch `feature`, the same lines are changed to:

```
Setup
=======
beta
```

```
<<<<<<< HEAD
configValue = "A"
Setup
=======
configValue = "B"
Setup
=======
alpha
>>>>>>> feature
```
   (Git will only ever emit exactly one real pair of markers around the actual conflicting hunk, but because "Setup\n=======" is real, unmodified content that sits *inside* the "ours" side of that hunk, the file on disk after a `git merge feature` looks like:)
```
<<<<<<< HEAD
configValue = "A"
Setup
=======
configValue = "B"
Setup
=======
alpha
>>>>>>> feature
```
3. Run `extractConflictHunks` on this content (`app/src/lib/copilot-conflict-context.ts:179`): the "ours" collection loop breaks at the first `=======` line (after `Setup`), so `oursContent` becomes `configValue = "A"\nSetup`, and everything after — including the real separator, `configValue = "B"`, `Setup`, `=======`, `alpha` — is folded into a single `theirsContent`.
4. export function reassembleResolvedFile(
```typescript
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
```
