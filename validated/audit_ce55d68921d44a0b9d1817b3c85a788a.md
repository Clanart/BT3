### Title
Attacker-controlled `head.repo`/`base.repo` in a Pull Request API response can poison the local GitHub-repository identity cache and silently redirect a fork's remote URL - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
The report's core pattern is: an entity (a Morpho market) is identified by a deterministic key derived from attacker-influenced parameters, and the code only checks "does an entry for this key already exist" instead of validating *who* is allowed to create/claim it — letting an attacker pre-empt the identity before the legitimate actor does. The closest verified analog in this codebase is how Desktop keys its local `GitHubRepository` cache: `_upsertGitHubRepository` in [1](#0-0)  resolves/creates a row purely by the tuple `[ownerID, name]`, regardless of the source of the API payload that produced it, and later code (`updateRemoteUrl`) trusts the cached `cloneURL` for that identity to silently rewrite a repository's git remote.

### Finding Description
`RepositoriesStore._upsertGitHubRepository` looks up an existing `GitHubRepository` row solely by `[ownerID+name]` and, if found, overwrites fields such as `cloneURL`/`htmlURL` with whatever the caller supplied: [2](#0-1) 

This method is invoked from `PullRequestStore.storePullRequests`, which upserts both the `pr.base.repo` and `pr.head.repo` objects taken directly from the GitHub API pull-request payload — including for **forks that are not owned by the user** and whose `owner.login`/`name`/`clone_url` fields describe an entity the API happens to report, not necessarily one the user has verified or added themselves: [3](#0-2) 

The key used for lookup, `[owner.login (case?), name]`, is the exact analog of the "deterministic address" in the Solidity report — it is fully predictable from public information (any attacker who knows a victim will eventually track PRs against `owner/name` can compute this key in advance).

Separately, `repositoryWithRefreshedGitHubRepository` re-uses this same identity cache when refreshing a repo the user has actually opened locally, and if the API's fresh full-repository fetch succeeds, it calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [4](#0-3) 

`updateRemoteUrl` will silently rewrite the local `origin` remote to `apiRepo.clone_url` whenever the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` and the URL protocol is unchanged: [5](#0-4) 

Because the guard `remoteUrlUnchanged` compares against the **cached** `cloneURL` (which itself can have been poisoned earlier via a crafted PR payload keyed to the same `[owner, name]`), this creates a path where: (1) an attacker gets a stale/attacker-influenced `clone_url` cached against a legitimate `owner/name` pair via pull-request sync, and (2) that value is later used as the trusted baseline to decide whether to silently repoint the user's real git remote.

### Impact Explanation
If exploited, this can lead to Desktop silently changing a repository's `origin`/`upstream` remote URL to a value influenced by attacker-controlled API data associated with an `owner/name` key the attacker does not own (e.g. via a PR whose head/base repo metadata reflects a renamed/transferred/attacker-created repo). This matches the requested impact class of "silent corruption of what the user commits or pushes," since subsequent `git push`/`git fetch` would target the corrupted remote without any user-visible confirmation dialog (contrast this with `UpstreamAlreadyExistsError`, which *does* prompt the user in the analogous "add upstream" path: [6](#0-5) ).

### Likelihood Explanation
Likelihood is Medium: it requires a PR to exist against a repository the victim has open in Desktop, with a `head.repo`/`base.repo` that an attacker can influence (e.g. a fork rename/ownership-transfer race, or the attacker creating a repo at a name the base/head previously used). Desktop already contains a dedicated safeguard for a very similar scenario (`addUpstreamRemoteIfNeeded` refusing to overwrite an existing conflicting `upstream` remote and instead popping `UpstreamAlreadyExistsError`), but `updateRemoteUrl`'s cache-vs-current comparison lacks an equivalent explicit-confirmation gate.

### Recommendation
- Before allowing `updateRemoteUrl` to silently change a remote, verify the update against a stronger signal than the previously-cached `cloneURL` (which is itself attacker-reachable through unrelated PR sync) — e.g. require the repository's stable numeric API `id` to match, not just `owner/name`, and/or prompt the user (mirroring `UpstreamAlreadyExists`) before rewriting an existing remote.
- In `_upsertGitHubRepository`/`upsertGitHubRepositoryLight`, avoid overwriting `cloneURL`/`htmlURL` for repositories that were not sourced from an API call the user directly initiated for that specific repository (e.g. keep cross-referenced PR `head`/`base` repo records read-only skeletons unless corroborated by the same numeric ID previously seen).

### Proof of Concept
Not independently executable from static analysis alone (requires live GitHub API interaction and repository ownership/rename timing); provided as a code-path trace:
1. Victim has Repository R (`owner/name`) open in Desktop and Desktop periodically syncs its PRs via `PullRequestStore.fetchAndStorePullRequests`.
2. A PR exists (or attacker opens one) whose `head.repo` (a fork) is later renamed/transferred such that the same `owner/name` pair as some other legitimate repo is reused, with a `clone_url` under attacker control — `storePullRequests` calls `upsertRepo(endpoint, pr.head.repo)` → `upsertGitHubRepositoryLight` → `_upsertGitHubRepository`, writing the attacker's `clone_url` into the DB keyed by `[ownerID, name]`.
2b. Confidence caveat: confirming end-to-end reachability (i.e., that the *same* dbID/row later gets attached to the victim's actually-open `Repository` object) requires tracing `setGitHubRepository`/`repositoryWithRefreshedGitHubRepository` call ordering across a live session, which was not directly observable through static search within the tool budget available.
3. When Desktop next calls `_refreshRepository` → `repositoryWithRefreshedGitHubRepository` for R, `updateRemoteUrl` compares the current `origin` remote against the (now-poisoned) cached `gitHubRepository.cloneURL` and, finding a match, silently rewrites `origin` to `apiRepo.clone_url` without any dialog.

Given the residual uncertainty in step 2b about whether the exact same in-memory/DB row is guaranteed to be reused for the victim's primary repository object (as opposed to only for PR-linked fork records), this should be treated as a **plausible but not fully confirmed** vulnerability requiring runtime verification.

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
