### Title
Attacker-controlled participant count in `ThresholdKeys::read` enables memory/CPU exhaustion DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::<C>::read` trusts a 16-bit participant count `n` taken directly from the byte stream before allocating and decoding that many field elements and curve points, and `ThresholdKeys::new` then performs up to `t` scalar-multiplications and interpolation work. A single crafted message with `n = 0xFFFF` forces a ~65535-element `Vec::with_capacity`, ~65535 `read_F` wide reductions, ~65535 point decompressions, and a `group_key` multiexp of up to `t` terms — all before any semantic validation rejects the input. This is Serai's analog of the CVE-2017-13060 class: a decoder that commits attacker-dictated resources to a crafted input.

### Finding Description
In `crypto/dkg/src/lib.rs:574-632`, `ThresholdKeys::read` parses `t`, `n`, and `i` as raw `u16`s from the reader (lines 591-602). `n` is attacker-controlled up to 65535. Immediately afterward:

- For `Interpolation::Constant` (tag byte `0`), it executes `Vec::with_capacity(usize::from(n))` and loops `n` times calling `C::read_F(reader)` (lines 607-613). The allocation is committed based purely on the declared count, before a single coefficient is validated.
- It then loops `1 ..= n` calling `<C as Ciphersuite>::read_G(reader)` — full point deserialization/decompression per iteration (lines 620-623).
- Finally `ThresholdKeys::new` computes `group_key` as a sum of `t` `verification_share * interpolation_factor` products (lines 376-378), where Lagrange `interpolation_factor` is itself O(`included.len()`) field operations per call (lines 229-247), giving O(t²) field work plus O(t) group scalar multiplications.

The per-message cost is bounded only by `u16::MAX`, not by the actual protocol parameters, because `ThresholdParams::new` validation happens *after* all decoding work (line 626). Unlike a correct decoder that would compare the declared count against an expected/authorized `n`, nothing ties the serialized `n` to the session's real threshold parameters.

### Impact Explanation
An unprivileged party able to feed bytes to `ThresholdKeys::read` (listed among the reachable untrusted read APIs — e.g., key material supplied through coordinator/restore or peer-forwarded data) can force each call to allocate multiple megabytes and burn seconds of CPU on point decompression and group arithmetic. Repeated submissions amplify this into sustained memory pressure and CPU exhaustion, denying service to legitimate signing/key-gen operations. While Rust prevents a literal leak (the allocations are freed on error/drop), the reachable harm of the CVE's class — denial of service via decoder resource consumption on crafted input — is present and is Medium-severity DoS.

### Likelihood Explanation
The attacker needs only to supply a byte stream beginning with a valid curve ID header, `n = 0xFFFF`, interpolation tag `0`, and enough bytes to keep the decode loops running. Every element read is pure CPU cost to the victim with no authentication required at parse time. The condition is deterministic — no negligible probability or complex precondition — though it requires a code path where key bytes arrive from an untrusted source rather than exclusively local storage.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` immediately after reading them and before performing `n`-proportional work; enforce a protocol-level maximum for `n` (matching the real deployment bound) prior to `Vec::with_capacity`; and move `ThresholdKeys::new`'s semantic checks ahead of the expensive `group_key` computation so malformed/truncated inputs are rejected before group arithmetic.

### Proof of Concept
Conceptually: construct bytes `ID_len || C::ID || t=0xFFFF || n=0xFFFF || i=0x0001 || 0x00 (Constant) || (65535 scalar encodings) || (65535 point encodings)`. Feeding this to `ThresholdKeys::<C>::read` causes a 65535-capacity `Vec` allocation, 65535 `read_F` reductions, 65535 point decodes, and (if reads succeed) a `ThresholdKeys::new` call performing ~65535 group scalar multiplications plus O(n²) interpolation field math — a deterministic per-message resource spike repeatable for cumulative DoS, mirroring the CVE's "crafted file → decoder resource exhaustion" shape.
