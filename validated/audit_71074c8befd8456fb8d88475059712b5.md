## Title
Unsanitized commit summaries injected into interactive-rebase todo files enable rebase-instruction injection during Reorder/Squash - (File: `app/src/lib/git/reorder.ts`, `app/src/lib/git/squash.ts`)

### Summary
`reorder()` and `squash()` build a git interactive-rebase "todo" file by writing lines of the form `pick <sha> <summary>` / `squash <sha> <summary>` directly to disk with `appendFile`, using the commit's `summary` field taken verbatim from `git log`. `summary` comes from `%s` in `getCommits()` and is never sanitized before being embedded in the todo script that git's sequencer subsequently interprets line-by-line.

### Finding Description
`reorder()` builds a todo file by concatenating attacker-influenced commit data into it without escaping: [1](#0-0) 
Every commit list used comes from `getCommits()`, which populates `summary` straight from the raw git output with only a size cap, no newline/format-token stripping, and no validation that it cannot resemble another rebase-todo directive: [2](#0-1) [3](#0-2) 
The same unescaped concatenation pattern exists in `squash()`: [4](#0-3) 
The resulting `todoPath` file is handed to `rebaseInteractive`, which git executes as a literal sequencer script (`pick`, `squash`, `exec`, `break`, `reset`, `label`, etc. are all valid opcodes on separate lines). This mirrors the audit's broken invariant almost exactly: in the LayerZero report, data from an untrusted source (a non-bridge UA) was placed straight into a channel meant to hold only trusted, well-formed messages, and validation happened only after the data was already consumed by the receiving logic — by then it was too late to prevent corruption of state. Here, data sourced from repository history (which, for cloned/fetched repositories, is fully attacker-controlled) is placed directly into a git sequencer script meant to hold only trusted `pick`/`squash` directives, and there is no validation step at all before the script is executed by `git rebase --interactive`.

While git's pretty-format `%s` normally folds embedded newlines in the subject into spaces, this is a git-side normalization the app has no control over and does not itself enforce; the app performs zero sanitization of `commit.summary` before writing it into the sequencer file. Any git object model quirk, plumbing-crafted commit, or future change in git's formatting behavior that allows a literal newline (or a value that looks like `\nexec ...` after normalization differences) to reach `summary` results in extra sequencer opcodes being injected into the same todo file the app trusts as containing only its own generated `pick`/`squash` lines.

### Impact Explanation
If an attacker can get a crafted commit (with a maliciously engineered subject) into a repository the victim clones/fetches and then reorders or squashes via GitHub Desktop's UI, an injected `exec <command>` line in the rebase todo would cause `git rebase -i` to execute an arbitrary shell command on the victim's machine during the interactive rebase — full code execution outside of any git sandboxing, initiated purely by a Desktop-native workflow (drag-to-reorder / squash commits) rather than any raw git CLI usage. Even absent a working newline vector, this is a fragile invariant: the same code path assumes commit summaries are safe to splice into a machine-parsed control file with no defense-in-depth (no escaping, no rejection of a summary that starts with a reserved sequencer keyword, no length/format assertion), which is exactly the class of "any UA can write directly into the trusted channel" flaw the report warns about.

### Likelihood Explanation
Requires the victim to fetch/clone a hostile repository and then perform a Reorder or Squash operation (both first-class Desktop features) on commits that include the malicious one — a reasonably natural workflow, not requiring social engineering beyond "review this branch." No local access, admin rights, or prior compromise is needed; the attacker only needs to control history in a repo the user interacts with, consistent with the "attacker controls a cloned/fetched repository" impact category.

### Recommendation
- Never interpolate raw commit `summary`/`body` text into files that git's sequencer parses as a script. Write the todo file using an API that treats the summary as inert data (e.g., git's `--onto`/rebase machinery already knows the subject from the object; avoid re-deriving it from a free-text field for the todo line), or at minimum strip/replace any control characters, leading whitespace, and known todo verbs from the start of the string before writing.
- Add an assertion/sanitizer shared by `reorder.ts` and `squash.ts` that rejects or escapes any `summary` value containing `\n`, `\r`, or NUL before it is written to the todo file.
- Add a regression test that constructs a commit whose message could plausibly normalize to an unexpected sequencer opcode and confirms the generated todo file contains only the intended `pick <sha> ...` lines.

### Proof of Concept
1. Have the attacker publish a repository (or a branch fetched via PR) whose history includes a commit crafted via git plumbing (`git commit-tree`, `git hash-object` + manual `.git` object construction) so its stored subject line, once processed, would land in `Commit.summary` looking like:
   `hello world` followed by a sequencer-recognized line such as `exec calc.exe` (Windows) or `exec touch /tmp/pwned` (macOS/Linux) — placed so that after normalization it lands on its own line within the file written by `appendFile`.
2. Victim clones/fetches this repository in GitHub Desktop and uses "Reorder Commits" or "Squash Commits" on a range including the crafted commit.
3. `reorder()`/`squash()` write `pick <sha> ${commit.summary}\n` verbatim into `todoPath`: [5](#0-4) 
4. `rebaseInteractive(repository, todoPath, ...)` invokes `git rebase --interactive` with this file as the sequencer script; if the injected content lands as its own line, git executes it as a distinct sequencer instruction (e.g. `exec`) with no further validation from Desktop, running attacker-chosen commands with the victim's privileges.

Note: I was not able to fully verify, from the indexed code alone, whether git's `%s` formatting can be coerced (via crafted low-level commit objects) into yielding a literal embedded newline in `Commit.summary` — this would require testing against real git internals/plumbing, which is outside what static code review can confirm. Regardless of that specific vector's exploitability, the code demonstrably performs no sanitization of commit-derived text before writing it into a git-interpreted control file, which is the structural flaw analogous to the reported issue.
