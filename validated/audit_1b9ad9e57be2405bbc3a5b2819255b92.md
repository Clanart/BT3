### Title
Attacker-controlled FROST preprocess with identity nonce-sum panics the signer during BIP-340 `Hram` computation - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The Argo advisory (CVE-2024-47827) is a crash-on-command DoS: an unprivileged user triggers a panic in shared code paths via attacker-controlled requests. The Serai analog is a deterministic panic in the BIP-340 `Hram` used by `bitcoin_serai::crypto::Schnorr`: `x()` / `x_only()` call `.expect("point at infinity")` / `.expect("...infinity or odd")` on `ProjectivePoint`, and `Hram::hram` computes `x(R)` where `R` is the group nonce computed from *other participants'* preprocess commitments. `frost`'s `Curve::read_G` rejects an identity *point*, but nothing prevents a malicious participant from crafting preprocess commitments whose rho-weighted sum is the point at infinity (choose hiding commitment `D`, compute `rho = hash_binding_factor(...)`, set blinding commitment `E = -rho^{-1} * D`). When the honest signer's `SignMachine::sign` → `sign_share` → `Hram::hram` runs, `x(R)` hits `encoded.x().expect("point at infinity")` and the process panics — matching the report's "panic reachable by any user who can submit work" shape.

### Finding Description
- `networks/bitcoin/src/crypto.rs:13-23` — `x()` does `(*encoded.x().expect("point at infinity")).into()` and `x_only()` does `.expect("x_only was passed a point which was infinity or odd")`. The doc comments admit "Panics on invalid input."
- `networks/bitcoin/src/crypto.rs:54-73` — `Hram::hram(R, A, m)` hashes `x(R)` and `x(A)`; its doc comment states "If either `R` or `A` is the point at infinity, this will panic," and `Schnorr`'s doc says it "MAY panic" on infinity nonces/group key.
- Reachability: an attacker submits a `Preprocess` via `read_preprocess` (`crypto/frost` machine API) with commitments whose weighted nonce-sum is identity. `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) only rejects an *individual* identity point; the sum `D + rho*E` is unchecked, and `hash_binding_factor` (`crypto/frost/src/curve/mod.rs:89-91`) is a public hash the attacker evaluates offline to solve `E = -rho^{-1} D`. `random_nonce` similarly cannot prevent a malicious *peer's* preprocess. No zero-sum check exists before `hram` is invoked, so the panic is deterministic, not negligible as the comment claims for "well-reasoned callers" — the attacker isn't well-reasoned.

### Impact Explanation
Each FROST signing session that includes the attacker's crafted preprocess crashes the local signer/processor at `expect("point at infinity")`. Repeated submissions produce a crash-loop that stalls all pending Bitcoin signatures (the same impact class as the Argo controller crash-loop DoS), with only trivial CPU needed — mirroring the report's note that resource quotas don't prevent it. This is a Medium availability bug reachable purely by untrusted bytes fed to `read_preprocess`/`sign_share`.

### Likelihood Explanation
Any participant (or anyone able to route a preprocess message) in a signing session can trigger it on demand with a few hash evaluations; no race-window, key access, or collusion is needed — unlike the Argo case, it's deterministic rather than probabilistic.

### Recommendation
In `Hram::hram` (and `x`/`x_only`), return a verification/signing error instead of panicking on the identity point, and/or have `sign_share` validate that each computed nonce sum is non-identity *before* invoking `hram` (rejecting/blaming the offending preprocess commitments), so malicious preprocesses yield a `FrostError` rather than a process abort.

### Proof of Concept
1. Build a `SignMachine`/`AlgorithmMachine` with `bitcoin_serai::crypto::Schnorr` for a `t`-of-`n` `Secp256k1` key.
2. As participant `j`, choose arbitrary hiding commitment `D`; compute `rho = Secp256k1::hash_binding_factor(binding_bytes)` for the session's serialized commitment list; set `E = -(rho^{-1}) * D`.
3. Submit `Preprocess` with `NonceCommitments(D, E)` — each point passes `read_G`'s identity check.
4. When `sign` computes the group nonce `R = D + rho*E = identity` and calls `Hram::hram(&R, &group_key, msg)`, `x(R)` executes `encoded.x().expect("point at infinity")` at `networks/bitcoin/src/crypto.rs:15`, panicking the signer.

Caveat: I verified the panic sites and the identity-check scope in `Curve::read_G`, but did not fully trace `SignMachine::sign`/`nonce.rs` to confirm no earlier aggregate-identity guard exists; if a nonce-sum identity check is added upstream, this reduces to a non-issue.
