### Title
`bank` precompile's `sendNative` bypasses `IsSendEnabledCoins`/`BlockedAddr` transfer controls enforced on the normal `MsgSend` path - (File: precompiles/bank/bank.go)

### Summary
The Blend report shows a flash-loan code path that moves funds without running the same pool-status guard (`require_action_allowed`) that the normal borrow path enforces. The Sei EVM `bank` precompile has an analogous pattern: its `send` method for ERC20-pointer transfers correctly routes through the Cosmos `msgServer.Send`, which enforces `IsSendEnabledCoins`, `IsInDenomAllowList`, and `BlockedAddr`, but its sibling `sendNative` method — the path used to move raw `usei`/wei value attached to an EVM call — calls `bankKeeper.SendCoinsAndWei` directly, skipping all of those checks.

### Finding Description
In `precompiles/bank/bank.go`, `send()` builds a `banktypes.MsgSend` and executes it via `p.bankMsgServer.Send(...)`: [1](#0-0) 

`msgServer.Send` (the code path `send()` uses) enforces the protocol's transfer controls before moving funds: [2](#0-1) 

However, `sendNative()` — invoked whenever an EVM call to the bank precompile carries `msg.value` — calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly, with no call to `IsSendEnabledCoins`, `IsInDenomAllowList`, or `BlockedAddr`: [3](#0-2) 

Checking the underlying `SendCoins`/send primitives in `sei-cosmos/x/bank/keeper/send.go` confirms these controls are NOT enforced inside the keeper itself — `SendCoins` only performs balance debits/credits and account creation, with no `IsSendEnabledCoins`/`BlockedAddr` gate: [4](#0-3) 

The `IsSendEnabledCoins`/`BlockedAddr` gate is only applied by callers, e.g. `msgServer.Send`/`MultiSend` and the CosmWasm `BankCoinTransferrer.TransferCoins` wrapper: [5](#0-4) 

Because `sendNative` calls the keeper primitive `SendCoinsAndWei` directly rather than going through `msgServer.Send`/`TransferCoins`, it is a second, unguarded transfer path — structurally the same root cause as the Blend finding, where the flash-loan implementation called the low-level borrow/asset-movement primitive directly instead of routing through `build_actions_from_request()`, which is where the pool/reserve status checks live.

### Impact Explanation
If the `usei` denom (or any denom moved through `SendCoinsAndWei`) is administratively disabled via `SendEnabledParam` (governance-controlled bank param, analogous to Blend's pool-freeze circuit breaker), or if a recipient address is on the module's `BlockedAddr` list (module accounts, reserved addresses), a caller can still move funds to/from those addresses by using `bank.sendNative(...)` with EVM `msg.value`, since that code path never checks `IsSendEnabledCoins` or `BlockedAddr`. This is an unauthorized transfer bypassing a protocol-level restriction via a precompile, matching the accepted "unauthorized transfer via precompile" impact class.

### Likelihood Explanation
Any account holding an EVM-associated address can trigger this by calling the `bank` precompile's `sendNative` method with a non-zero `msg.value` — no special privileges are required, matching the "unprivileged EVM transaction sender" reachability requirement. The bug only manifests when `DefaultSendEnabled`/`SendEnabledParam` is set to disable a denom or when the target is a blocked address, both of which are legitimate operational/governance states the protocol is expected to enforce.

### Recommendation
Route `sendNative`'s fund movement through the same guarded path as `send()` (i.e., call `msgServer.Send`/`BankCoinTransferrer`-equivalent logic, or explicitly call `IsSendEnabledCoins` for the base denom and `BlockedAddr` on the receiver) before invoking `bankKeeper.SendCoinsAndWei`, so that the EVM-native-value transfer path is subject to the identical transfer controls enforced on the standard Cosmos `MsgSend` path.

### Proof of Concept
1. Governance (or module init) disables sending for `usei` via `SendEnabledParam` (`DefaultSendEnabled=false`, no override for `usei`), or an address is present in `BlockedAddr`.
2. A normal Cosmos `MsgSend` of `usei` to/from that state fails with `ErrSendDisabled`/`is not allowed to receive funds`, per `msgServer.Send`'s checks.
3. An EVM caller instead calls the `bank` precompile at `0x0000000000000000000000000000000000001001` method `sendNative(receiverSeiAddr)` with `msg.value` set to the desired amount (usei/wei encoded). This routes to `PrecompileExecutor.sendNative`, which calls `bankKeeper.SendCoinsAndWei` directly — no `IsSendEnabledCoins`/`BlockedAddr` check is performed, so the transfer succeeds despite the disabled/blocked state.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
