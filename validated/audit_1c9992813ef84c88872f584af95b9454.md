### Title
Payout signature only covers input 0 + output 0, allowing OP_RETURN operator-attribution to be rewritten and stolen via txid malleability - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs input 0 with `TapSighashType::SinglePlusAnyoneCanPay`, which by Bitcoin consensus rules commits only to input 0 and the output at index 0 — it says nothing about output 2 (the OP_RETURN carrying `operator_xonly_pk`). Anyone who observes the user's signature (once broadcast/relayed) can construct a competing, fully-valid transaction reusing that exact signature, input 0, and output 0, while substituting an arbitrary OP_RETURN payload naming a different operator, and get it mined instead (double-spend race/first-seen or RBF if they add higher fees on their own funding inputs).

### Finding Description
The broken binding: `Verifier::update_finalized_payouts` assumes `operator_xonly_pk` parsed from the mined payout tx's OP_RETURN == the operator whose broadcast/fee-paying effort actually produced that payout tx. This binding is **not enforced by the signature**.

- `Operator::withdraw` verifies the user's signature via `SECP.verify_schnorr` over `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` [1](#0-0) , using `TapSighashType::SinglePlusAnyoneCanPay` as documented in the error message.
- `create_payout_txhandler` builds outputs `[user_payout, anchor, op_return(operator_xonly_pk)]` and sets the key-spend witness for input 0 only [2](#0-1) .
- Per BIP-341/342 sighash rules, `SIGHASH_SINGLE|ANYONECANPAY` commits only to the single input being signed (input 0) and the output at the *same index* (output 0). It does not cover any other input or output — including output 2, the OP_RETURN that names the fronting operator.
- Consequently, the signature embedded in input 0's witness remains valid for *any* transaction that preserves the exact same input-0 outpoint/prevout/witness and the exact same output-0 (scriptPubKey+value), regardless of what other inputs/outputs (change, anchor, OP_RETURN) are attached. `fund_raw_transaction`/`sign_raw_transaction_with_wallet` in `Operator::withdraw` only add/sign the *funding* inputs and possibly reposition non-zero outputs; output 0 is untouched, so the honest operator's broadcast is itself proof that this malleability is real and exploitable.
- An attacker who sees the honest operator's payout tx in the mempool (or via block-relay race) can extract input 0 (outpoint + witness) and output 0, build their own transaction with these unchanged, add their own funding input(s)/change (any operator or attacker-controlled UTXO, signed by themselves), and attach a fresh OP_RETURN with a different xonly pubkey (e.g., a genuine but uninvolved operator's pubkey), then relay/mine it first.
- `Verifier::update_finalized_payouts` blindly trusts whichever payout tx gets mined and records that OP_RETURN's pubkey as the payer: `get_first_op_return_output` + `parse_op_return_data` [3](#0-2) .
- `PayoutCheckerTask::run_once` for the true operator looks up `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` [4](#0-3) , which will return `None` because the DB row's `payout_payer_operator_xonly_pk` was overwritten with the attacker-chosen pubkey [5](#0-4) .
- Later, when the true operator sends its kickoff for this deposit, `Verifier::is_kickoff_malicious` compares the stored `operator_xonly_pk` (now the attacker-chosen one) against `kickoff_data.operator_xonly_pk` (the true operator) and flags it malicious [6](#0-5) .
- No existing guard (`SECP.verify_schnorr`, `is_deposit_valid`, `is_profitable`, storage-proof checks) constrains output 2; the check in `Operator::withdraw` only validates that input/output 0 match the withdrawal record and profitability — it never re-validates that the *mined* tx's OP_RETURN matches `self.signer.xonly_public_key` before broadcasting, and there is no consensus-level binding forcing output 2 to be covered by the signature.

### Impact Explanation
The honest operator that funded the payout (paid fees, provided change) can never satisfy `get_first_unhandled_payout_by_operator_xonly_pk`, so it never reaches `handle_finalized_payout`/`mark_payout_handled`, permanently losing its Reimburse path for that deposit. Worse, when it inevitably submits its kickoff for the deposit it fronted, `is_kickoff_malicious` will return `true`, exposing it to disprove/challenge and burning its round collateral. This matches the Critical impact category: "an honest operator permanently unable to be reimbursed" / "an honest operator's collateral burned." The attack is repeatable per withdrawal/payout event and does not require any privileged role — only observing mempool/relay traffic and being able to broadcast a competing transaction with their own funding inputs.

### Likelihood Explanation
Preconditions: an honest operator must have already constructed/broadcast (or be about to broadcast) a payout tx for a given withdrawal index. The attacker needs no special credentials — only the ability to observe the honest operator's tx (public mempool/relay data or the eventual public consensus data) and re-broadcast a variant with their own fee-paying inputs before the honest tx confirms (racing/RBF/priority relay). Attacker cost is minimal (their own fee-paying UTXO + fees); they gain no direct BTC but can grief an operator's reimbursement/collateral, which is a real economic attack against operators, and can be repeated against every operator withdrawal cycle. Because sighash malleability is deterministic Bitcoin behavior (not a bug requiring race-condition luck beyond normal mempool competition), likelihood is high whenever an attacker is motivated to target a specific operator.

### Recommendation
Change the payout transaction's user-signed sighash type to cover the OP_RETURN output (and ideally all outputs), e.g. use `SIGHASH_ALL` (not `ANYONECANPAY`) if possible, or restructure so the operator's identity commitment is bound into the same output/input that the user signs (for example, embed the committing operator pubkey into the signed message the operator obtains from the user via the off-chain protocol, and validate at mining time, not just at construction time). At minimum, add a post-broadcast/pre-`update_finalized_payouts` verification step that ties the OP_RETURN operator pubkey to some data that is cryptographically bound to input 0 + output 0 (e.g., signing the sighash with `SIGHASH_ALL|ANYONECANPAY` so all outputs, including any operator-added OP_RETURN, must be fixed prior to signing — this still allows adding fee inputs via ANYONECANPAY but locks all outputs).

Test plan (regtest, using existing e2e helpers in `core/src/test/common/citrea/mod.rs` and `core/src/test/deposit_and_withdraw_e2e.rs`):
1. Set up a deposit + withdrawal via existing e2e helpers (`generate_withdrawal_transaction_and_signature`, `withdraw`), fund the honest `operator0`'s payout tx via `Operator::withdraw`, but intercept the raw hex *before* `send_raw_transaction` (or capture it right after broadcast from the node's mempool via `getrawmempool`/`getrawtransaction`).
2. Extract input 0 (outpoint, prevout, witness) and output 0 (scriptPubKey/value) from the captured raw tx.
3. Build a second transaction reusing exactly this input 0 (with its witness untouched) and output 0, but add a different funding input (attacker/second operator's own UTXO, signed by them) and a new OP_RETURN output encoding `operator1_xonly_pk.serialize()` instead of `operator0_xonly_pk`.
4. Broadcast the second transaction first (or with a higher fee via RBF) and mine it, asserting the first (honest) tx is rejected as a double-spend.
5. Assert: `db.get_first_unhandled_payout_by_operator_xonly_pk(operator0_xonly_pk)` returns `None`.
6. Assert: `verifier.is_kickoff_malicious(...)` returns `true` when called with `operator0`'s real kickoff for this deposit (since the DB's `payout_payer_operator_xonly_pk` is now `operator1_xonly_pk`).
7. This demonstrates both sides of the equality (`stored operator_xonly_pk` vs `operator who actually funded/broadcast`) diverge after the attack, confirming the vulnerability.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
