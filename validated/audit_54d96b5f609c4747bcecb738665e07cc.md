### Title
Repository identity is bound to a mutable filesystem path, so a recreated directory silently inherits trust — analogous to CREATE2/SELFDESTRUCT address reuse - ([File: app/src/lib/stores/app-store.ts])

### Summary
The C4 report describes a broken invariant in Axelar's deposit service: a deterministic address is destroyed (`SELFDESTRUCT`) and later recreated (`CREATE2`), and the protocol implicitly trusts whatever occupies that address afterward. GitHub Desktop has a structurally identical pattern in how it tracks repositories: a `Repository` record's trusted identity (`id`, `gitHubRepository` binding, prior "safe directory" trust) is keyed by a mutable filesystem **path** string, not by any content-derived or cryptographic identity. When the directory at that path disappears ("missing") and later something reappears there, Desktop's recovery logic re-attaches the old trusted identity to whatever is now on disk, based only on shallow heuristics.

### Finding Description
Repository identity is persisted keyed by `path`: [1](#0-0) 

Lookup/matching of "is this the same repository" is done purely with a normalized string comparison of the path, with no verification of remote URL, root commit, or any other content-derived identity: [2](#0-1) 

When a tracked repository's directory vanishes, Desktop marks it `missing` but keeps its full trusted identity (`id`, `gitHubRepository` association, credentials context) alive in the local database and UI: [3](#0-2) 

The recovery path re-validates only via `getRepositoryType` (does `.git` exist / is it "regular") and whether `git status` can be loaded — not whether it's the *same* repository that was originally added: [4](#0-3) [5](#0-4) 

This recovery is triggered automatically and silently on ordinary user actions — selecting the repository, refreshing, or simply the app regaining focus/periodic background refresh — not only via an explicit "Check again" click: [6](#0-5) 

The UI's own "missing repository" recovery flow reinforces the same assumption: once a user has clicked "Trust Repository" for a path (calling `addSafeDirectory`, which writes a `safe.directory` entry to global Git config keyed by *path*), that trust persists for the path indefinitely, regardless of what content is later present there: [7](#0-6) 

**Broken invariant:** the report's core lesson is that a fixed "address" (`CREATE2` deployment address / here, a filesystem path) must not be treated as a stable identity once its underlying content can be destroyed and recreated by someone else. GitHub Desktop's guards (`getRepositoryType`, `matchExistingRepository`, `_loadStatus`) only check *shape* (is there a `.git`, does `git status` succeed) — none of them check *identity* (same origin URL, same root commit, same repository). This is the same class of gap the Axelar report flags: existence-at-address is conflated with identity-of-content.

### Impact Explanation
This corrupted value is the `Repository` record returned by `recoverMissingRepository`/`_addRepositories`/`matchExistingRepository`: Desktop believes it is operating on the user's previously-trusted repository (complete with its GitHub API binding used for push/PR/credential flows) while it is actually operating git commands (`fetch`, `checkout`, `merge`, `commit`, `push`) against attacker-supplied content at the same path. Concretely:
- On a shared/network mount, removable drive, or drive-letter-reuse scenario (Windows drive letters are explicitly treated case-insensitively as equivalent, see `matchExistingRepository`), a party who can write to the previously-occupied path can plant a git repository there before the legitimate one returns.
- Desktop's automatic recovery (triggered on window focus, repository selection, background refresh — no unusual user action required) reattaches the pre-existing trusted `id`/`gitHubRepository` binding to that attacker-controlled repository without validating remote URL or history identity.
- If the path was ever "trusted" via `onTrustDirectory`/`addSafeDirectory`, that trust is bound to the path and survives content replacement, silently bypassing Git's own ownership-mismatch protection that `safe.directory` exists to enforce.
- This can silently corrupt what the user subsequently commits/pushes (their commits/pushes now apply to the attacker's repository state/history) and can direct credentialed GitHub API operations at the wrong content.

### Likelihood Explanation
Requires no local/physical access, admin rights, or pre-existing malware on the host — only that the user has (at some point) tracked a repository on a location whose ownership/content can change out-of-band from Desktop's knowledge (network share, removable media, container/VM mount, CI runner reusing workspace paths, or drive-letter reuse on Windows). This is a plausible, realistic condition for many real users (shared drives, USB, cloud-sync folders) and requires zero unusual interaction by the victim — recovery fires automatically on refresh/focus.

### Recommendation
Do not treat a filesystem path as a durable identity for a tracked repository:
- When recovering a "missing" repository, verify content identity, not just shape: compare the recovered repository's remote URL(s) (or the initial commit / a stored fingerprint) against what was recorded when the repository was first added, and require explicit user confirmation before silently reattaching the old `gitHubRepository` binding, credentials, and `safe.directory` trust if they don't match.
- Scope `safe.directory` trust grants to be re-validated (or invalidated) whenever the underlying repository's identity markers (e.g., first commit SHA, `.git` directory inode/creation metadata, or remote URL) change, instead of trusting the path indefinitely.
- Surface a clear warning ("this path used to contain repository X, but now appears to be a different repository") instead of transparently resuming background fetch/push/PR flows.

### Proof of Concept
1. User adds `/mnt/shared/proj` (or `Z:\proj` on Windows) as a GitHub-linked repository in Desktop; Desktop records `{ id, path: '/mnt/shared/proj', gitHubRepository, missing: false }` [8](#0-7) .
2. The share becomes unavailable (unmounted/disconnected); Desktop marks the repository `missing: true` via `_updateRepositoryMissing` in `_refreshRepository` [9](#0-8) .
3. An attacker with write access to that mount point (a different local/network user, or a process reusing the same drive letter) creates a fresh, unrelated git repository at the exact same path, optionally with a malicious remote and/or hooks.
4. The share becomes available again; on the next window focus, manual "Check again", or background refresh, `_refreshOrRecoverRepository` → `recoverMissingRepository` calls `getRepositoryType(path)` and `_loadStatus(repository)`, both of which succeed against the attacker's repo, so Desktop calls `_updateRepositoryMissing(repository, false)` and resumes normal operation [10](#0-9) .
5. Desktop now shows the original repository name/GitHub association in the UI while all git operations (fetch, checkout, commit, push) act on the attacker's repository content — with no prompt indicating the underlying repository changed.

**Note on unverified aspects:** I was not able to fully trace whether Desktop applies any hook-disabling or `core.hooksPath` sandboxing uniformly across all git invocations from within `app-store.ts` (grep hits were spread across multiple files: `get-repo-hooks.ts`, `commit.ts`, `merge.ts`, `pull.ts`, `push.ts`, `rebase.ts`, `tag.ts`), so I cannot confirm whether attacker-supplied hooks at the recreated path would execute during Desktop-initiated git operations; this would need direct inspection in a Devin session to determine whether it upgrades the impact from "silent commit/push corruption + trust bypass" to full code execution.

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}

  private async recoverMissingRepository(
    repository: Repository
  ): Promise<Repository> {
    if (!repository.missing) {
      return repository
    }

    const type = await getRepositoryType(repository.path)

    const foundRepository =
      type.kind === 'regular' && (await this._loadStatus(repository)) !== null

    if (foundRepository) {
      let recovered = await this._updateRepositoryMissing(repository, false)
      if (type.kind === 'regular' && recovered.gitDir !== type.gitDir) {
        recovered = await this.repositoriesStore.updateRepositoryGitDir(
          recovered,
          type.gitDir
        )
      }
      return recovered
    }

    const recoveredWorktree = await this.recoverMissingWorktree(repository)
    if (recoveredWorktree !== null) {
      return recoveredWorktree
    }

    return repository
  }

  /** This shouldn't be called directly. See `Dispatcher`. */
  public async _refreshRepository(repository: Repository): Promise<void> {
    if (repository.missing) {
      return
    }

    // if the repository path doesn't exist on disk,
    // set the flag and don't try anything Git-related
    const exists = await pathExists(repository.path)
    if (!exists) {
      const recoveredWorktree = await this.recoverMissingWorktree(repository)

      if (recoveredWorktree !== null) {
        if (
          this.selectedRepository instanceof Repository &&
          this.selectedRepository.id === repository.id
        ) {
          await this._selectRepository(recoveredWorktree)
        } else {
          await this._refreshRepository(recoveredWorktree)
        }

        return
      }

      this._updateRepositoryMissing(repository, true)
      return
    }
