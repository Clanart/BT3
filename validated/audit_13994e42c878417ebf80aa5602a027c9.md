### Title
Domain-separation-free "sign message" RPC lets a phished signature be replayed as a valid AGG_SIG_ME authorization to steal a standard coin - (File: chia/wallet/util/signing.py)

### Summary
`sign_message_by_address` / `sign_message_by_id` can sign an arbitrary caller-supplied byte string with the exact same synthetic secret key that authorizes spending the user's standard coin, using signing modes (`BLS_MESSAGE_AUGMENTATION_HEX_INPUT` / `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT`, selected via `safe_mode=False`) that apply **no domain separation prefix** at all. Because Chia's standard coin puzzle requires an `AGG_SIG_ME` signature over exactly `delegated_puzzle_hash + coin_name + AGG_SIG_ME_ADDITIONAL_DATA`, an attacker who can get a wallet/RPC caller to "sign a message" equal to that byte string obtains a signature that is directly reusable to authorize spending that coin with an attacker-chosen delegated puzzle — this is the same cross-context signature-replay bug class described in the ERC1271 report (a generic "verify/sign this data" primitive lacking domain separation, whose output is reusable to authorize unrelated privileged actions).

### Finding Description
The wallet RPC message-signing flow determines the signing mode from the `is_hex`/`safe_mode` flags: [1](#0-0) 

When `safe_mode=False`, the mode resolves to `BLS_MESSAGE_AUGMENTATION_UTF8_INPUT` or `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`: [2](#0-1) 

`sign_message` then signs the raw bytes directly with no CHIP-0002 prefix in those modes (unlike the default `CHIP_0002` mode, which wraps the message in `("Chia Signed Message", message)` before hashing): [3](#0-2) 

Critically, the key used for this signature is the *same* synthetic secret key used to authorize spending the user's coins: [4](#0-3) 

The synthetic key is derived from the wallet's private key via `convert_secret_key_to_synthetic`, i.e. `calculate_synthetic_secret_key` — the exact key whose signature the standard puzzle (`p2_delegated_puzzle_or_hidden_puzzle`) requires via an `AGG_SIG_ME` condition over `delegated_puzzle_hash + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA`: [5](#0-4) 

Because `BLS_MESSAGE_AUGMENTATION_HEX_INPUT`/`UTF8_INPUT` sign the raw bytes with no prefix, if the attacker controls the `message` parameter passed to `sign_message_by_address`/`sign_message_by_id` (e.g. via a malicious dApp or site driving the local wallet RPC, or a UI that lets a user paste/hex-sign arbitrary data), the attacker can set:

```
message = <delegated_puzzle_hash of attacker's chosen conditions> + <target coin_name> + AGG_SIG_ME_ADDITIONAL_DATA
```

and request the user "sign this hex message." The returned `AugSchemeMPL.sign(synthetic_secret_key, message)` is *bit-for-bit* the signature the standard coin puzzle expects to authorize spending that coin with the attacker's delegated puzzle (e.g. one that does `CREATE_COIN <attacker_address> <amount>`). The attacker then assembles a `SpendBundle` with that puzzle reveal/solution and the phished aggregated signature and pushes it to the mempool — an unauthorized, fully signed coin movement, with no interaction from the coin owner other than the earlier "message sign."

This mirrors the ERC1271 report precisely: a general-purpose signature-producing entry point that lacks domain separation from the “real” authorization message format, allowing signatures obtained under an innocuous pretext to be replayed to authorize a sensitive, unrelated action.

### Impact Explanation
Successful exploitation results in unauthorized coin movement / theft of the victim's XCH (or CAT if similarly reachable) without the coin owner ever intending or reviewing a transaction — a direct wallet fund-theft primitive. This satisfies "concrete unsigned or unauthorized coin movement."

### Likelihood Explanation
Exploitation requires: (1) knowledge of the target coin id/puzzle hash (public), (2) the ability to get the victim's wallet to call `sign_message_by_address`/`sign_message_by_id` with `safe_mode=False` and attacker-chosen hex `message` (plausible via a malicious dApp/site that talks to the local wallet RPC, or a "verify you own this wallet" phishing flow that instructs the user to run `chia wallet sign_message` with a supplied hex blob), and (3) the coin still exists unspent by the time the crafted bundle is submitted. The `safe_mode` default is `True` (safer CHIP-0002 prefixed mode), so exploitation requires convincing the user/integration to explicitly opt into the unsafe raw-signing modes — this lowers but does not eliminate likelihood, since these modes exist specifically for "raw BLS sign" compatibility (e.g. `chia keys sign`) and are exposed identically over RPC for wallet addresses tied to real spendable coins.

### Recommendation
- Do not allow the *same* key used for coin-spend authorization (`AGG_SIG_ME`/synthetic secret key) to be used for generic message signing without a domain-separating, unambiguous prefix in every mode, or derive a distinct non-spending key/path for message signing.
- If raw/unsafe signing modes must be retained for compatibility, restrict them to non-owner-derived keys, or explicitly disallow `safe_mode=False` for `sign_message_by_address`/`sign_message_by_id` (which sign with real coin-owning synthetic keys), reserving raw modes only for `chia keys sign` on keys never used for coin ownership.
- Where raw modes remain necessary, enforce a length/format check rejecting messages of exactly `32+32+len(AGG_SIG_ME_ADDITIONAL_DATA)` bytes ending in the network's `AGG_SIG_ME_ADDITIONAL_DATA` (mirroring the existing `AGG_SIG_UNSAFE` collision guard in `pkm_pairs_for_conditions_dict`) so that a "message to sign" cannot double as a valid `AGG_SIG_ME` payload.

### Proof of Concept
1. Attacker learns the victim's standard-coin puzzle hash/address and an unspent `coin_name` for it (public chain data).
2. Attacker builds a malicious delegated puzzle `D` (e.g. `(q (51 <attacker_ph> <amount>))`) and computes `delegated_puzzle_hash = D.get_tree_hash()`.
3. Attacker computes `message_hex = (delegated_puzzle_hash + coin_name + AGG_SIG_ME_ADDITIONAL_DATA).hex()`.
4. Attacker lures the victim (e.g. through a dApp/site or support-style phishing instructions) into calling:
   `sign_message_by_address(address=<victim address>, message=message_hex, is_hex=True, safe_mode=False)`
   — matching the `BLS_MESSAGE_AUGMENTATION_HEX_INPUT` code path in [3](#0-2) .
5. Wallet returns `signature = AugSchemeMPL.sign(synthetic_secret_key, bytes.fromhex(message_hex))` via [4](#0-3) .
6. Attacker builds `CoinSpend(coin, standard_puzzle_reveal, solution_for_delegated_puzzle(D, ()))` and `SpendBundle([coin_spend], signature)`, then submits it via `push_tx`.
7. The standard puzzle's required `AGG_SIG_ME` check passes because the signature matches `delegated_puzzle_hash + coin.name() + AGG_SIG_ME_ADDITIONAL_DATA` exactly, and the coin is spent to the attacker's address without further victim interaction.

```python
def signing_mode_enum(request: SignMessageByAddress | SignMessageByID) -> SigningMode:
    if request.is_hex and request.safe_mode:
        return SigningMode.CHIP_0002_HEX_INPUT
    elif not request.is_hex and not request.safe_mode:
        return SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT
    elif request.is_hex and not request.safe_mode:
        return SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT
```

```python
def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
```

```python
    async def sign_message_by_address(self, request: SignMessageByAddress) -> SignMessageByAddressResponse:
        """
        Given a derived P2 address, sign the message by its private key.
        :param request:
        :return:
        """
        synthetic_secret_key = self.service.wallet_state_manager.main_wallet.convert_secret_key_to_synthetic(
            await self.service.wallet_state_manager.get_private_key(decode_puzzle_hash(request.address))
        )
        signing_response = sign_message(
            secret_key=synthetic_secret_key,
            message=request.message,
            mode=request.signing_mode_enum,
        )
        return SignMessageByAddressResponse(
            pubkey=signing_response.pubkey,
            signature=signing_response.signature,
            signing_mode=request.signing_mode_enum.value,
        )
```
