### Title
`smartConvert` hardcodes `_minRec = _amountIn`, so buyback slippage/manipulation reverts every reward-triggered `deposit`/`depositLP`/`withdraw` on the pool - (File: wombat/SmartWomConvert.sol)

### Summary
`smartConvert()` forces `_minRec` to equal the full `_amountIn` regardless of how much of that amount is routed through the AMM buyback leg, so any negative slippage on the `wom -> mWom` swap causes `_convertFor` to revert with `MinRecNotMatch`. Because the only caller of `smartConvert` is `WombatStaking._sendRewards`, invoked from `_toMasterWomAndSendReward` inside `WombatStaking.deposit`, `depositLP`, and `withdraw`, this revert bubbles up and blocks principal deposits/withdrawals on the affected pool whenever a WOM reward fee happens to be harvested in the same transaction.

### Finding Description
In `wombat/SmartWomConvert.sol`:
```
function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
    ...
    return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
}
``` [1](#0-0) 

`_minRec` is hardcoded to `_amountIn`, and `_convertFor` reverts if the sum of the 1:1-deposited portion (`convertAmount`) and the swapped portion (`amountRec`) is below that:
```
if (convertAmount + amountRec < _minRec)
    revert MinRecNotMatch();
``` [2](#0-1) 

`convertRatio`/`buybackAmount` sizing depends on `currentRatio()` (a spot-price read from `IWombatRouter.getAmountOut` on `womMWomPool`) and `maxSwapAmount()` (derived from `IAsset(womAsset).cash()`/`.liability()`), both of which are influenced by ordinary swap activity on the public Wombat pool: [3](#0-2) 
Because these read live AMM state, an actor swapping on `womMWomPool` can push `currentRatio()` below `buybackThreshold` and widen the cash/liability gap that feeds `maxSwapAmount()`, increasing the size of `buybackAmount` that must be swapped through `_convertFor`. If the resulting swap execution (subject to pool fees/slippage) returns less than the nominal `buybackAmount`, `obtainedmWomAmount` falls short of `_minRec` and the whole call reverts.

The real (verified) call site for `smartConvert` is `WombatStaking._sendRewards`, not `ArbWomUp3._deposit`:
```
if (feeInfo.isMWOM && rewardToken == wom) {
    if (smartWomConverter != address(0)) {
        ...
        IConverter(smartWomConverter).smartConvert(feeAmount, 0);
``` [4](#0-3) 
`_sendRewards` is called from `_toMasterWomAndSendReward`, which itself is invoked unconditionally inside `deposit`, `depositLP`, and `withdraw`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Note: the specific precondition asserted in the question — "the call arrives from `ArbWomUp3._deposit` mode two with `_minRec` hardcoded to zero" — does not match the code. `ArbWomUp3._deposit` mode 2 calls `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`, not `smartConvert`, and it explicitly passes `_minRec = 0`, which is immune to this issue: [9](#0-8) 
The genuine vulnerable path is `WombatStaking._sendRewards` calling `smartConvert(feeAmount, 0)`, which reuses the hardcoded `_minRec = _amountIn` behavior described above. `nonReentrant`/`whenNotPaused` guards on `deposit`/`depositLP`/`withdraw` do not prevent this revert — they only block reentrancy/pausing, not the internal revert from `_convertFor`.

### Impact Explanation
If `smartConvert` reverts inside `_sendRewards`, the enclosing `_toMasterWomAndSendReward` call reverts, which reverts the entire `WombatStaking.deposit`, `depositLP`, or `withdraw` transaction for that pool. Since this only triggers when a nonzero WOM reward fee is realized in the same call (i.e., `womRewards > 0` and the mWOM fee is active/nonzero), it is conditional rather than always-on, but when triggered it can block all principal deposits and withdrawals for the affected pool until pool/AMM conditions change or an owner adjusts `ratio`/`buybackThreshold`. This matches a temporary freezing-of-funds impact if sustained for 24+ hours.

### Likelihood Explanation
Exploitability requires: (1) a WOM reward fee being harvested at the moment of the call (dependent on emission schedule, not attacker-controlled precisely), and (2) the attacker moving `womMWomPool` state (via ordinary swaps, no special privilege) so that the buyback leg's realized output falls short of the swapped-in amount. This requires capital to move AMM state and favorable timing with reward accrual, making it feasible but not trivial or fully attacker-timed; it is a design flaw (over-strict `_minRec`) rather than a straightforward, always-repeatable single-transaction exploit.

### Recommendation
Do not hardcode `_minRec = _amountIn` in `smartConvert`. Compute a slippage-tolerant minimum output based on `estimateTotalConversion`/`getAmountOut` with an explicit tolerance, or decouple the reward-fee buyback path so a swap shortfall reduces the reward queued to `_sendRewards` instead of reverting the caller's `deposit`/`depositLP`/`withdraw`. Wrap the `smartConvert`/`_sendRewards` mWOM conversion in a try/catch (or pre-check) so failures degrade to sending unconverted WOM rather than reverting principal-affecting flows.

### Proof of Concept
1. Deploy/fork with `WombatStaking`, `SmartWomConvert`, and the real `womMWomPool`/`womAsset`.
2. Set `smartWomConverter` and an active `isMWOM` fee in `WombatStaking`.
3. Manipulate `womMWomPool` (large swap of mWom for wom) to push `currentRatio()` below `buybackThreshold` and widen `womAsset.cash()`/`liability()` gap so `maxSwapAmount()` is large relative to expected `feeAmount`.
4. Trigger a `WombatStaking.deposit`/`depositLP`/`withdraw` call that causes `masterWombat` to pay out WOM rewards (`womRewards > 0`), driving `_sendRewards` to call `smartConvert(feeAmount, 0)`.
5. Assert the transaction reverts with `MinRecNotMatch` due to `convertAmount + amountRec < _amountIn`, and assert that subsequent legitimate user `deposit`/`depositLP`/`withdraw` calls on the same pool also revert under the same pool conditions, remaining blocked until pool state/parameters change.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
