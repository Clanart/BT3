### Title
Missing synchronization in `upb_Message_GetOrPromoteExtension` lazy unknown→extension promotion allows concurrent-getter race/corruption - (File: `upb/message/promote.c`)

### Summary
CVE-2023-28466 describes a Linux kernel bug where `do_tls_getsockopt` — a read-style accessor — mutates/reads shared socket state without calling `lock_sock`, letting a concurrent `setsockopt` race it into a use-after-free. The closest Protobuf analog is `upb_Message_GetOrPromoteExtension` [1](#0-0) , a "get"-style accessor that, as a documented side effect, mutates the message's internal unknown-field list and extension table (deleting unknown entries, inserting a new extension) [2](#0-1)  — with **no internal locking** at the core upb C level.

### Finding Description
`upb_Message_GetOrPromoteExtension` looks up an extension; if not already promoted, it scans the message's unknown-field storage, parses matching bytes into a new sub-message, then calls `_upb_Message_GetOrCreateExtension` and `upb_Message_DeleteUnknown2` to splice the promoted extension into the message and remove the corresponding unknown entries [3](#0-2) . This function mutates message-owned data structures (the unknown list and extension table) but takes no lock of its own — it only `UPB_ASSERT`s the message isn't frozen [1](#0-0) .

The codebase itself documents this exact hazard. `hpb/internal/message_lock.h` states the API "uses lazy promotion from unknown data to upb_MiniTableExtension" and introduces a temporary, opt-in locking hook specifically to "avoid race conditions" for `GetOrPromoteExtension`, `Serialize`, and related calls [4](#0-3) . The implementation wraps calls with a `MessageLock` RAII guard that only takes effect if `upb_extension_locker_global` has been set by the embedder [5](#0-4) . This lock is exercised by a dedicated concurrency-reproduction test (`TestConcurrentExtensionAccess`) that races extension gets, serialization, and copy construction from multiple threads on the same message [6](#0-5)  — confirming the race is real and was previously observable without the lock.

However, this locking is a *hpb-only, opt-in, "TODO: temporary" mitigation* (explicitly "Will be replaced by a core runtime solution in the future") [7](#0-6) . The core `upb_Message_GetOrPromoteExtension` in `upb/message/promote.c` itself has no lock, and I could not confirm (within available tooling) that the Python C extension (`python/message.c` / `python/extension_dict.c`) or Ruby/PHP bindings route extension access through an equivalent lock — `extension_dict.c`'s subscript path calls `PyUpb_Message_GetFieldValue`, whose internal handling of unknown-extension promotion I was unable to inspect directly due to tool-call exhaustion.

### Impact Explanation
If two threads concurrently call an extension getter (or otherwise trigger `GetOrPromoteExtension`) on the same shared, not-yet-promoted message instance without an application-level lock, both can race through the "not present, scan unknowns, parse, create extension, delete unknown entries" sequence concurrently. Because `upb_Message_DeleteUnknown2` and `_upb_Message_GetOrCreateExtension` mutate shared arena-backed lists, a lost update or double-delete could corrupt the unknown-field linked structure or extension table, producing use-after-free/double-free-class memory corruption analogous to the kernel CVE's outcome — the maintainers' own "TODO" and dedicated race-test file corroborate that this is a recognized, non-hypothetical hazard class in this codebase.

### Likelihood Explanation
Lower than the kernel CVE. Reaching this race requires the *consuming application* to concurrently invoke extension accessors on the same shared message object without synchronization — Protobuf's own docs (e.g. `LazyFieldLite`'s Javadoc: "explicit synchronization is needed under read/write situations") place the synchronization burden on the caller for anything that isn't a pure, already-materialized read. This weakens the "ordinary client through a supported public parse API" framing required by the task, since the race is only reachable through multi-threaded application misuse of a documented-as-caller-synchronized API, not through a single bounded-input parse call. The core upb team clearly still considers this an open gap (per the "TODO...core runtime solution" comment), but it is mitigated today only in the hpb C++ surface, not proven-exploitable purely from untrusted wire bytes in a single-threaded parse call.

### Recommendation
- Move the `MessageLock`/locking mechanism (or an equivalent internal mutex) into the core `upb_Message_GetOrPromoteExtension`/`upb_MiniTable_PromoteUnknownToMessage*` implementations in `upb/message/promote.c`, rather than leaving it as an opt-in hook only wired up by the hpb layer.
- Audit Python (`python/message.c`, `python/extension_dict.c`), Ruby, and PHP native bindings to confirm whether they route through the same unsynchronized promotion path, especially under Python's free-threaded (`Py_GIL_DISABLED`) builds where the GIL no longer serializes these mutations.
- Extend the existing `TestConcurrentExtensionAccess`-style fuzzing/race tests to run without embedder-supplied locks to detect regressions in the core (non-hpb) path.

### Proof of Concept
I could not produce/execute a concrete local repro within available tooling for this pass (no code execution available; the existing `hpb/internal/message_lock_test.cc` `TestConcurrentExtensionAccess` test [6](#0-5)  is the closest existing artifact demonstrating the race pattern when the lock hook is *not* installed — this is the maintainers' own reproduction of the exact hazard class described above, but I did not verify a crash/UAF outcome myself in this session.

**Caveat / confidence**: This finding is evidence-supported but not fully proven exploitable purely from a bounded, single "supported public parse API" call as strictly required by the task's threat model — it additionally requires the consuming application to violate documented thread-safety contracts by concurrently accessing a shared message. I was unable, within remaining tool iterations, to confirm whether Python/Ruby/PHP bindings expose this specific unprotected core-C code path without any caller-side lock, so I cannot assert this as a definitively confirmed exploitable vulnerability — only as the strongest structurally analogous, code-evidenced candidate found in this repository.

class MessageLock {
 public:
  explicit MessageLock(const upb_Message* msg) : msg_(msg) {
    UpbExtensionLocker locker =
        upb_extension_locker_global.load(std::memory_order_acquire);
    unlocker_ = (locker != nullptr) ? locker(msg) : nullptr;
  }
  MessageLock(const MessageLock&) = delete;
  void operator=(const MessageLock&) = delete;
  ~MessageLock() {
    if (unlocker_ != nullptr) {
      unlocker_(msg_);
    }
  }

 private:
  const upb_Message* msg_;
  UpbExtensionUnlocker unlocker_;
};

bool HasExtensionOrUnknown(const upb_Message* msg,
                           const upb_MiniTableExtension* eid) {
  MessageLock msg_lock(msg);
  if (upb_Message_HasExtension(msg, eid)) return true;

  const uint32_t number = upb_MiniTableExtension_Number(eid);
  return upb_Message_FindUnknown2(msg, number, 0).status == kUpb_FindUnknown_Ok;
}

bool GetOrPromoteExtension(const upb_Message* msg,
                           const upb_MiniTableExtension* eid, upb_Arena* arena,
                           upb_MessageValue* value) {
  // TODO: Fix const correctness issues.

  MessageLock msg_lock(mutable_msg);
  upb_GetExtension_Status ext_status =
      upb_Message_GetOrPromoteExtension(mutable_msg, eid, 0, arena, value);
  return ext_status == kUpb_GetExtension_Ok;
}
