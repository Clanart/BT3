### Title
Fixed-window scalar multiplication drops the scalar's low `NUM_BITS % 4` bits, producing an incorrect verifier formula - ([File: crypto/ed448/src/point.rs])

### Summary
`Mul<Scalar> for Point` in `crypto/ed448/src/point.rs` implements a 4-bit fixed-window scalar multiplication by iterating the scalar's bits MSB-first and flushing a window every time `(i + 1) % 4 == 0`. Because Ed448's scalar field has `NUM_BITS = 446` (which is not a multiple of 4), the final partial window — the lowest 2 bits of the scalar — is accumulated into `bits` but never applied after the loop ends. The routine therefore computes `P * (s & !0b11)` instead of `P * s`. This is the same bug class as the reference finding: a right-shift/bit-truncation that silently discards (or includes) the wrong bits when interpreting a packed value.

### Finding Description [1](#0-0) 

The loop enumerates `i` over `0 .. NUM_BITS` on the MSB-first iterator:

```rust
for (i, mut bit) in other.to_le_bits().iter_mut().rev().enumerate() {
  bits <<= 1;
  ...
  if ((i + 1) % 4) == 0 {
    if i != 3 { for _ in 0 .. 4 { res = res.double(); } }
    ... res += add_by; bits = 0;
  }
}
```

The `if i != 3` special case encodes the assumption that the first window completes exactly at `i == 3`, i.e. that `NUM_BITS` is a multiple of 4. When `NUM_BITS % 4 != 0`, the loop terminates with the last `NUM_BITS % 4` bits sitting in `bits`, never added into `res`. For Ed448 (`NUM_BITS = 446`), every scalar multiplication `point * scalar` silently clears the scalar's two lowest bits. `Scalar::pow` in `crypto/dalek-ff-group/src/lib.rs:210-235` and `FieldElement::pow` in `crypto/dalek-ff-group/src/field.rs:244-268` contain the identical pattern and exhibit the same drop for fields whose `NUM_BITS` isn't a multiple of 4 (e.g. the Ed25519-base-field `pow` used by `sqrt_ratio_i` via `MOD_5_8`).

Reachability: `Point * Scalar` is invoked on attacker-influenced values wherever ed448 is used as a ciphersuite — FROST nonce commitments (`generator * nonce` in `crypto/frost/src/nonce.rs:65-68`), binding-factor-bound nonces, and signature-share/signature verification statements. An unprivileged participant supplies preprocesses and shares through `read_preprocess`/`read_share`, and verifiers evaluate `s·G` and `c·A` under the truncated formula.

### Impact Explanation
The verifier's Schnorr equation `s·G == R + c·A` is evaluated with `s` and `c` both truncated to `s & !3` / `c & !3`. This is an incorrect verifier formula: signatures valid under the real equation are rejected, and the accepted relation is `s·G = R + (c & ~3)·A`, which is not the Schnorr relation for the honest challenge `c`. Depending on how the signature binds `s` to `c`, this enables signature malleability/forgery variants (equivalent signatures under truncated challenge scalars) and breaks FROST ed448 share verification, where honestly computed nonce commitments map to `r & ~3` while shares carry the exact `r`, causing valid shares to be blamed as invalid.

### Likelihood Explanation
Likelihood of the defect is certain whenever `NUM_BITS % 4 != 0` — Ed448 scalars (`NUM_BITS = 446`) always lose 2 bits. Exploitation as a forgery depends on the calling algorithm's structure; at minimum, any untrusted share, preprocess commitment, or `SchnorrSignature` over ed448 is verified against the wrong formula, an impact reachable purely from public inputs to `read_share`/`verify`. The same defect is latent in `Scalar::pow`/`FieldElement::pow` for any caller with a non-multiple-of-4 exponent length.

### Recommendation
Make the window handling length-agnostic: flush the accumulated `bits` after the loop when `NUM_BITS % 4 != 0` (with the appropriate final `double`s), or pad the iteration so window boundaries align with bit positions rather than enumeration index. Apply the same fix to `Scalar::pow` (`crypto/dalek-ff-group/src/lib.rs:210`) and `FieldElement::pow` (`crypto/dalek-ff-group/src/field.rs:244`). Add a test asserting `Point::generator() * Scalar::from(1) == Point::generator()` and `pow` against known vectors on each in-scope curve.

### Proof of Concept
On Ed448, `Scalar::NUM_BITS = 446 ≡ 2 (mod 4)`. For `s = Scalar::ONE`, the loop processes bits MSB-first; completions occur only at `i ∈ {3, 7, ..., 443}` (111 windows = 444 bits). The bits enumerated at `i = 444` and `i = 445` — which carry the value of `s`'s two lowest bits — are folded into `bits` after the last flush and never applied. Therefore `Point::generator() * Scalar::ONE` returns `Point::identity()` instead of the generator, and in general `P * s == P * (s & ~3)`, making distinct scalars `s, s+1, s+2, s+3` (low bits varying) collide under verification while honestly-derived signatures fail to verify.
