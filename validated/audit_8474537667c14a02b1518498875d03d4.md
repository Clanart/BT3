### Title
Front-runnable `initialize()` on `HyperFungibleTokenUpgradeable` / `WrappedHyperFungibleTokenUpgradeable` lets an attacker seize `Ownable` control of a bridge token before the deployer - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` are OZ-upgradeable bridge-token contracts meant to be deployed behind a proxy and then `initialize()`d exactly once, with the caller-supplied `initialOwner` becoming the sole `Ownable` admin who later calls `configure()` (binding the ISMP host/dispatcher) and `addChain()` (binding the cross-chain peer registry). `initialize()` itself performs no caller/owner check other than the reentrancy-style `initializer` modifier, which only guarantees "callable once," not "callable only by the deployer." This is the exact bug class from the external report: whoever's transaction reaches `initialize()` first wins control of the contract's privileged configuration.

### Finding Description
`HyperFungibleTokenUpgradeable.initialize(string name, string symbol, address initialOwner)` [1](#0-0)  and `WrappedHyperFungibleTokenUpgradeable.initialize(address initialOwner)` [2](#0-1)  are both `public` and gated only by OZ's `initializer` modifier, which enforces single-call semantics but does not restrict *who* the caller is or what `initialOwner` value they may supply.

Both contracts do call `_disableInitializers()` in their constructors [3](#0-2) [4](#0-3) , which correctly locks the raw *implementation* contract against direct initialization — this defends against the "implementation takeover" variant of the bug. However, that only protects the implementation; it does nothing for the **proxy**. Once a proxy is deployed pointing at the implementation, its storage is uninitialized until someone calls `initialize()` on the proxy, and that call is open to anyone.

Compare this to the safe pattern used elsewhere in the same repo:
- `IntentGatewayV2.initialize()` is only ever invoked atomically via the proxy's constructor init-data (`ERC1967Proxy(address(implementation), initData)`), so no window exists between proxy deployment and initialization [5](#0-4) , and this atomicity is explicitly tested and documented as the production path [6](#0-5) .
- `SimplexPaymaster.initialize()` is likewise wired through `abi.encodeCall(...)` passed directly into the `ERC1967Proxy` constructor [7](#0-6) .

By contrast, `HyperFungibleTokenUpgradeable` / `WrappedHyperFungibleTokenUpgradeable` have **no deployment script or documentation in this repo enforcing the atomic proxy+init pattern** — the only shipped deployment scripts for HFT/WrappedHFT (`DeployHFT.s.sol`, `DeployWrappedHFT.s.sol`) deploy the *non-upgradeable* `HyperFungibleToken`/`WrappedHyperFungibleToken` variants whose constructors take `admin` directly, avoiding the race entirely [8](#0-7) [9](#0-8) . The upgradeable variants exist in the SDK for third-party integrators to deploy themselves (e.g. via `new ERC1967Proxy(address(implementation), "")` followed by a separate `initialize()` call, exactly as the test harness for the unrelated `IntentGatewayV2` shows the *insecure* two-step pattern is a known idiom in this codebase's own tests: `ERC1967Proxy proxy = new ERC1967Proxy(address(implementation), "")` then a separate `.initialize(...)` call [10](#0-9) ). If an integrator follows that same two-transaction deployment style for `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` — deploy proxy, then separately call `initialize()` — the second transaction is a public mempool target with zero access control.

### Impact Explanation
Whoever's `initialize()` transaction lands first becomes the `Ownable` owner of the token/bridge-app proxy. That owner immediately gains exclusive rights to:
- `configure()` — bind an attacker-controlled `host`/`dispatcher` address (host is one-shot: `if (_host == address(0)) { _host = options.host; }`) [11](#0-10) , which fully determines which ISMP host is trusted for cross-chain mint/unlock authorization.
- `addChain()` — register attacker-controlled peer module IDs for arbitrary state machines [12](#0-11) , meaning the attacker can later forge `onAccept` messages "from" a chain of their choosing that this contract will treat as authentic and mint tokens or unlock custody for.

Since `WrappedHyperFungibleTokenUpgradeable` custodies real ERC-20/native funds (lock/unlock model) and `HyperFungibleTokenUpgradeable` controls mint authority for a bridged asset, owner takeover is a direct path to unauthorized minting, wrong-beneficiary token issuance, or diversion of locked collateral — squarely matching "stealing or loss of funds" / "unauthorized transaction or execution" under the bounty's impact gate.

### Likelihood Explanation
This requires no privileged actor, relayer, or governance compromise — only an unprivileged attacker racing a public mempool transaction against the legitimate deployer's `initialize()` call, precisely the "PoC: call initializer as low-priv user" scenario in the source report. The only mitigating factor is that a careful integrator who atomically bundles proxy deployment + init calldata (as `IntentGatewayV2`/`SimplexPaymaster` do) avoids the window entirely; but nothing in the contract itself enforces that pattern, and no deployment script for these two upgradeable contracts exists in this repo to guide integrators toward the safe path.

### Recommendation
- Bind `initialize()` to a value fixed at deploy time (e.g., an immutable `deployer`/`factory` address set in the constructor, similar to how `IntentGatewayV2`'s constructor takes `owner` and later checks it), or
- Ship (and document) only the atomic proxy-construction deployment pattern (`ERC1967Proxy(address(impl), abi.encodeCall(initialize, (...)))`) for these upgradeable contracts, exactly as already done for `IntentGatewayV2` and `SimplexPaymaster`, and add an explicit doc/script under `evm/script/` so integrators don't fall back to the two-step pattern demonstrated in the test suite.

### Proof of Concept
1. Attacker monitors the mempool for a `CREATE`/`CREATE2` deployment of an `ERC1967Proxy` pointing at the `HyperFungibleTokenUpgradeable` (or `WrappedHyperFungibleTokenUpgradeable`) implementation with empty/no init data (the exact pattern shown in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:67-70`, transplanted to these contracts by an integrator following that idiom).
2. As soon as the proxy address is known/mined, attacker submits `proxy.initialize("X","X", attacker)` (or `proxy.initialize(attacker)` for the wrapped variant) with higher gas, front-running the legitimate deployer's own `initialize()` call.
3. `initializer` modifier only rejects a *second* call — it does not reject the attacker's *first* call — so `_owner` (via `__Ownable_init(attacker)`) becomes the attacker.
4. Attacker calls `configure()` to set `_host`/`_dispatcher` to contracts they control, and `addChain()` to register peer module IDs of their choosing, then exercises `onAccept` mint/unlock paths to extract value or issue unauthorized tokens to arbitrary beneficiaries.

    /// @dev Production deploy path: the proxy initializes atomically via its init data, so the
    /// `initialize` call arrives through the proxy constructor (not from `_owner`). Must succeed.
    function testAtomicInitialization() public {
        IntentGatewayV2 implementation = new IntentGatewayV2(address(this));
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: 10000,
            protocolFeeBps: 0,
            priceOracle: address(0)
        });
        bytes[] memory peers = new bytes[](1);
        peers[0] = bytes("SOURCE_CHAIN");

        bytes memory initData = abi.encodeCall(IntentGatewayV2.initialize, (intentParams, peers));
        ERC1967Proxy proxy = new ERC1967Proxy(address(implementation), initData);
        IntentGatewayV2 gateway = IntentGatewayV2(payable(address(proxy)));

        assertEq(gateway.params().host, address(host), "params set via atomic init");
        assertEq(gateway.instance(bytes("SOURCE_CHAIN")), address(gateway), "peer bound to address(this)");

        vm.expectRevert();
        gateway.initialize(intentParams, peers);
    }
