### Title
Unauthenticated `withdraw` RPC bypasses aggregator gatekeeping when `aggregator_verification_address` is unset - (File: core/src/rpc/operator.rs)

### Summary
`ClementineOperator::withdraw` in `core/src/rpc/operator.rs` only validates the ECDSA `verification_signature` (proving the request came from the aggregator) inside an `if let Some(address_in_config) = self.operator.config.aggregator_verification_address` block. When that config value is `None` — a supported deployment configuration — the entire authentication branch is skipped and `Operator::withdraw` is invoked directly on attacker-supplied parameters, with no check that the caller is the aggregator.

### Finding Description
The intended binding is: `party_invoking_state_mutation == aggregator` (the protocol's caller-authority model routes withdrawal orchestration exclusively through the aggregator, which is the entity trusted to sequence/gate operator payouts).

Tracing the code: [1](#0-0) 
shows that the verification-signature check that would enforce `caller == aggregator` is entirely conditioned on `self.operator.config.aggregator_verification_address` being `Some(...)`. If it is `None`, no branch executes and control falls straight through to: [2](#0-1) 
which calls `self.operator.withdraw(withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount)` — the state-mutating call that (per the operator implementation) constructs and broadcasts the payout transaction.

Because the RPC parameters (`input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) are exactly the values that are publicly observable once a user registers a withdrawal (e.g., after calling `withdraw` on the Citrea Bridge contract, or after an aggregator/operator has already broadcast/logged them), any unprivileged party who has observed this tuple can construct a `WithdrawParamsWithSig` (with `verification_signature: None`) and call the operator's public gRPC `withdraw` endpoint directly, bypassing the aggregator entirely.

I was not able to fully inspect the body of `Operator::withdraw` in `core/src/operator.rs` within the available tool budget, so I cannot confirm with certainty whether it independently re-derives caller authority (e.g., by requiring a fresh musig2/aggregator session, or by validating `input_signature` cryptographically against `input_outpoint`'s scriptPubKey in a way that inherently constrains who may trigger the broadcast). If `input_signature` is a valid Bitcoin-level signature that only the legitimate withdrawer could have produced for that specific `output_script_pubkey`/`output_amount`, then the payout destination is still fixed to the intended recipient and funds cannot be redirected — but the RPC call itself remains reachable, unauthenticated, and state-changing/broadcasting, regardless of destination-correctness.

### Impact Explanation
Per the rules, "an unauthenticated state-changing or broadcasting call" is itself an enumerated High-impact category. The `withdraw` RPC clearly falls into this category when `aggregator_verification_address` is unset: an unprivileged caller can trigger `Operator::withdraw`'s broadcast of a payout transaction without any authentication, which is a direct violation of the intended caller-authority model (aggregator-only orchestration). This is repeatable for every operator instance deployed without `aggregator_verification_address` configured, and for every withdrawal whose parameters the attacker can observe.

Whether this escalates to a Critical fund-diversion or reimbursement-mismatch bug depends on internal validation inside `Operator::withdraw` that I could not fully verify (e.g., whether the payout destination/amount are strictly bound to a legitimately signed user request, and whether replay/duplicate-broadcast is prevented by DB uniqueness constraints on `withdrawal_id`). Absent that confirmation, the demonstrable impact is the unauthenticated broadcast itself.

### Likelihood Explanation
The only precondition is a deployment where the operator's `aggregator_verification_address` config field is left unset — a supported and plausible configuration per `core/src/config/mod.rs`. No BTC, fees, or special privileges are required beyond observing publicly-derivable withdrawal parameters and sending a single gRPC request to the operator's public port.

### Recommendation
Make the aggregator-verification check mandatory and unconditional in `withdraw` (`core/src/rpc/operator.rs`), rather than gated behind `aggregator_verification_address.is_some()`. If unauthenticated fallback must be supported, restrict it via mutual TLS/allowlisting or require the config to be non-optional, and fail closed (reject the RPC) rather than skip validation when the config is absent.
