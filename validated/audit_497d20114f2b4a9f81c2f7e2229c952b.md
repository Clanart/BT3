### Title
Unbounded attacker-controlled allocation in `ReceivedOutput::read` enables memory-exhaustion crash (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The CVE-2016-5403 bug class — trusting an unverified, attacker-supplied size to allocate memory, causing unbounded memory consumption and process crash — maps directly onto `ReceivedOutput::read` in `bitcoin-serai`. The function feeds untrusted bytes to rust-bitcoin's `TxOut::consensus_decode`/`OutPoint::consensus_decode` via a `BufReader`, and the `TxOut` encoding includes a CompactSize/varint length for `script_pubkey` that the consensus decoder uses to size a `Vec` allocation before reading the data. An attacker who supplies serialized `ReceivedOutput` bytes can claim a script length of up to u64::MAX, forcing a multi-gigabyte allocation and aborting the process.

### Finding Description
`ReceivedOutput::read` reads a scalar offset, then decodes a `TxOut` and an `OutPoint` directly from the caller's reader:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
}
``` [1](#0-0) 

A `TxOut` on the wire is `value (8 bytes) || CompactSize(script_len) || script`. rust-bitcoin's consensus decoding of the script buffer allocates a `Vec` sized by the declared `script_len` before consuming the bytes, so a 9-byte header like `FF FF FF FF FF FF FF FF` (varint 0xFFFFFFFFFFFFFFFF) causes an allocation request of ~18 exabytes. Rust's allocator aborts the process on allocation failure, so this is not a recoverable `io::Error` — it is a hard crash.

The same class of issue is acknowledged elsewhere in the codebase: `networks/ethereum/src/machine.rs:51-60` explicitly comments "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and chunks the read to mitigate it, and `coordinator/src/p2p.rs:264-270` caps the request length before allocating. `ReceivedOutput::read` has no equivalent guard, and `BufReader::with_capacity(0, r)` provides no protection — it only avoids buffering; the oversized allocation happens inside the decoder.

By contrast, other in-scope length-prefixed readers are safe or bounded: `SchnorrAggregate::read` (crypto/schnorr/src/aggregate.rs:77-88) pushes decoded points in a loop without pre-sizing, `Commitments::read` (crypto/dkg/pedpop/src/lib.rs:110-127) is bounded by `params.t()`, and `EncryptedMessage::read`/`ThresholdKeys::read` derive their sizes from `ThresholdParams` (u16-bounded `n`), not from attacker bytes.

### Impact Explanation
`ReceivedOutput` bytes are deserialized on the processor side when handling scanned/registered outputs; per the threat model, untrusted bytes may reach `ReceivedOutput::read`. An attacker submitting a ~40-byte payload (`scalar || 8-byte value || 0xFFFFFFFFFFFFFFFF varint`) triggers an allocation of up to 2^64 bytes, aborting the process via allocation failure. This is memory consumption and process crash from a public, unauthenticated input — exactly the CVE-2016-5403 shape (unbounded virtqueue allocation → QEMU crash). Crashing the signing/processor path denies service to the Bitcoin multisig pipeline and can be repeated cheaply on restart by resubmitting the same bytes.

### Likelihood Explanation
Any code path that deserializes a `ReceivedOutput` from bytes not produced by the local `Scanner` is exploitable — `write`/`serialize`/`read` is a public round-trip API on an in-scope crate, and received outputs are inherently derived from data originating in transactions and messages outside local control. The exploit requires no valid signatures, no threshold position, and only tens of bytes of input. Likelihood is limited only by whether a given deployment exposes a byte-deserialization path for `ReceivedOutput` to untrusted input; where it does, exploitation is trivial and deterministic.

### Recommendation
Do not hand the raw reader to `consensus_decode` on untrusted input. Either:

- Bound the `script_pubkey` length before decoding: read the CompactSize prefix manually and reject values above a sane maximum (Bitcoin consensus caps scripts at 10,000 bytes; the mempool standard is far lower), then `take(len).read_to_end` and `ScriptBuf::from_bytes`.
- Or wrap the reader in a size-limited adaptor (`r.take(MAX_TXOUT_LEN)`) so a claimed length that exceeds the bytes actually present fails with `io::Error` instead of an oversized allocation, and additionally reject declared lengths above the protocol maximum.

Apply the same audit to any other `consensus_decode` call fed from a `read` function reachable by untrusted bytes.

### Proof of Concept
```rust
use std::io;
use serai_bitcoin::wallet::ReceivedOutput;

// Builds: 32-byte scalar || TxOut { value: 0, script_len = u64::MAX }
fn malicious_serialized_output() -> Vec<u8> {
    let mut bytes = vec![0u8; 32];          // Secp256k1 scalar (any valid repr)
    bytes[0] = 1;                            // offset = 1 (canonical)
    bytes.extend([0u8; 8]);                  // TxOut value = 0 sats
    bytes.push(0xFF);                        // CompactSize marker for u64
    bytes.extend(u64::MAX.to_le_bytes());    // script_len = 2^64 - 1
    bytes
}

fn main() -> io::Result<()> {
    // Aborts the process on allocation failure rather than returning Err
    let _ = ReceivedOutput::read(&mut malicious_serialized_output().as_slice())?;
    Ok(())
}
```

The `read_F` and 8-byte value reads succeed; `TxOut::consensus_decode` then interprets `0xFF || le(u64::MAX)` as a script length and attempts a ~2^64-byte allocation, aborting the process — memory exhaustion from a 50-byte untrusted input.
