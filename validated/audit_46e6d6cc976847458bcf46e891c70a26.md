### Title
Unwrapping WSEI via `withdraw()` can permanently fail for contract holders due to `transfer()`'s 2300 gas stipend - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol`'s `withdraw()` function sends native SEI back to the caller using Solidity's `.transfer()`, which forwards only a fixed 2300-gas stipend to the recipient. Any contract (e.g., a multisig, proxy wallet, or any contract with a non-trivial `receive()`/`fallback()`) that holds WSEI and attempts to unwrap it will have its balance permanently locked whenever its native-SEI receive path needs more than 2300 gas.

### Finding Description
`withdraw()` burns the caller's WSEI balance and then relays the native asset with `payable(msg.sender).transfer(wad)`: [2](#0-1) 

`.transfer()` hard-codes a 2300 gas stipend for the callee's `receive`/`fallback` execution. This is the exact bug class flagged in the external report about `RetrieveAsset.sol::retrieveNative()`: if the recipient is a contract whose fallback logic does more than emit a trivial log (e.g., writes storage, forwards funds, uses a proxy dispatch), the inner call reverts, and the `.transfer()` call bubbles up that revert, reverting the whole `withdraw()` transaction. Because `balanceOf[msg.sender]` was already decremented before the transfer inside the same transaction, the revert simply rolls that back — but the practical effect is the caller can never successfully unwrap their WSEI through this path as long as their receiving code exceeds the stipend, permanently freezing their wrapped funds relative to that specific contract account (no way to retrieve the underlying native SEI from this WSEI contract).

This contract is not a test fixture only — it is compiled and embedded directly into the chain binary at `x/evm/artifacts/wsei/artifacts.go`, with its bytecode in `WSEI.bin`, and is exposed for deployment via the `seid tx evm deploy-wsei` CLI command implemented in `CmdDeployWSEI`: [1](#0-0) 

Once deployed by anyone (deployment is unprivileged and reachable by any transaction sender), `WSEI` acts as the chain's canonical wrapped-native-token contract that other EVM contracts/pointer-based tooling are expected to interoperate with, since sei-chain ships its bytecode/ABI as first-class artifacts rather than as a standalone example.

### Impact Explanation
Any smart-contract account (proxy wallets, DeFi vaults, multisigs, or any contract using more complex fallback/receive logic) that deposits native SEI into WSEI and later calls `withdraw()` risks having its funds permanently stuck if its own receiving logic requires more than 2300 gas. Because the WSEI contract holds the aggregate native SEI backing all outstanding WSEI, this is a fund-freezing bug reachable by ordinary unprivileged contract callers, consistent with the "permanent freezing of funds" impact class for Medium severity in the same manner the original report describes for `RetrieveAsset.sol`.

### Likelihood Explanation
Likelihood is moderate to high in practice: any contract wallet, DeFi protocol contract, or upgradeable proxy that integrates with WSEI as a wrapped-native token and calls `withdraw()` from its own contract code (rather than an EOA) is affected any time its `receive()`/`fallback()` logic exceeds the 2300-gas stipend (which is trivial to exceed with even a single storage write or event emission plus branch logic). EOAs are unaffected since a plain EOA doesn't execute code on receiving a transfer, but any protocol wiring WSEI unwrap logic through contract-to-contract calls is at risk.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `withdraw()` with a low-level `.call{value: wad}("")` and explicitly check/require the boolean success value, mirroring the pattern already used elsewhere in the repo's own `TransferHelper.safeTransferETH()`: [3](#0-2) 

### Proof of Concept
1. Deploy `WSEI` via `seid tx evm deploy-wsei` (or have it already deployed as the chain's canonical instance).
2. Deploy an attacker/victim contract `C` whose `receive()` function performs a state-changing operation costing more than 2300 gas (e.g., `mapping[msg.sender] += 1;` plus an `emit`).
3. From `C`, call `WSEI.deposit{value: X}()`, then call `WSEI.withdraw(X)`.
4. The internal `payable(msg.sender).transfer(wad)` inside `withdraw()` reverts because `C.receive()` runs out of the 2300 gas stipend, reverting `withdraw()` entirely.
5. `C` can never unwrap its WSEI back to native SEI through this contract, even though it correctly holds a positive WSEI balance — its funds remain a permanently unusable balance-only entry, unless it can find another consumer of WSEI (e.g., transferring the ERC-20 balance to an EOA), demonstrating the freezing condition described by the bug class.
