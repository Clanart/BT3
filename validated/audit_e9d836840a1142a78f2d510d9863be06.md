### Title
Farming rewards paid to a melted PlotNFT's reward address become permanently unclaimable - ([File: chia/pools/plotnft_drivers.py])

### Summary
`PlotNFT.melt()` lets a self-custody Plot NFT owner permanently destroy their singleton (no child coin is recreated), yet the fixed `reward_puzhash()` address that receives future farming rewards for that `launcher_id` is a `SingletonMember`-gated `RewardPuzzle` whose only spend path requires a `SEND_MESSAGE` approval that only the still-live singleton can emit. Once the singleton is melted, no such approval can ever be produced again, so any reward coin subsequently paid to that address is permanently stuck — the same "value keeps arriving into an account with no live redeemer" bug class as the reported `EsEMBR.sol` `receive()`/`totalEthPerEsembr` issue, where ETH sent when `totalSupply == 0` cannot be retrieved.

### Finding Description
`PlotNFTPuzzle.reward_puzhash()` derives a fixed reward address purely from `launcher_id`, independent of whether the singleton is alive: `RewardPuzzle(singleton_id=self.launcher_id).puzzle_hash()` [2](#0-1) . The `RewardPuzzle`/`PoolReward` spend path is gated entirely by `SingletonMember`, which requires the current singleton's inner-puzzle-hash approval delivered via a `SEND_MESSAGE`/`RECEIVE_MESSAGE` pair originating from a real singleton spend [3](#0-2) [1](#0-0) .

`PlotNFT.melt()` is reachable by any self-custody Plot NFT owner and permanently destroys the singleton by creating an odd melt condition without recreating an odd child (`[51, None, -113, ...]`), so no singleton spend can ever exist again for that `launcher_id` [4](#0-3) . `claim_pool_rewards()`/`forward_pool_reward()` both operate through `singleton_action_spend()`, which requires the live singleton coin object to exist, so after melt there is no legitimate way to sign the `SEND_MESSAGE` approval that `RewardPuzzle.solve()` needs [5](#0-4) [6](#0-5) .

Meanwhile plots referencing the pre-melt `launcher_id` are not guaranteed to be pulled or replotted immediately by the harvester, so block/pool reward coins for that launcher can continue to be paid to `reward_puzhash()` for some period after the melt spend confirms. This exactly mirrors the report's root cause: an address keeps receiving value ("ETH sent as `msg.value`" / here, farming reward coins) after the corresponding accounting entity ("totalSupply" / here, the live singleton) has ceased to exist, and the protocol provides no mechanism to detect this at receipt time or to recover the funds afterward.

### Impact Explanation
Reward coins delivered to a melted Plot NFT's `reward_puzhash()` become permanently unspendable XCH — there is no `SingletonMember` proof that can ever be generated again for that `launcher_id`. This is a real, irreversible loss of farming rewards for the affected user, reachable purely through their own legitimate, unprivileged wallet actions (self-custody exit followed by melt) combined with normal continued farming/plotting behavior outside the wallet's control.

### Likelihood Explanation
Likelihood is moderate: it requires a self-pooling/self-custody Plot NFT owner to melt their singleton while plots tied to that `launcher_id` are still being farmed (a common real-world sequencing mistake, since plot removal/replotting is not atomic with the melt transaction). No malicious third party is required — this is a self-inflicted but protocol-permitted fund-loss scenario, analogous in severity to the reported medium-severity contract issue.

### Recommendation
Either (a) block or warn against `melt()` when reward coins might still be inbound (e.g., require confirmation that no plots reference the launcher, or provide a grace/escrow period before allowing melt), or (b) make the reward address recovery-capable independent of singleton liveness — e.g., allow melted-singleton owners to claim residual `reward_puzhash()` coins via a fallback authorization (such as a signature from the original owner key) instead of requiring a `SingletonMember` `SEND_MESSAGE` proof that becomes permanently impossible to produce.

### Proof of Concept
1. Create a self-custody Plot NFT (`launcher_id = L`) and start farming plots keyed to `L`'s `reward_puzhash()`.
2. Call `PlotNFT.melt()` and confirm it on-chain — the singleton coin is destroyed with no child recreated [4](#0-3) .
3. Before plots for `L` are pulled/replotted, farm a block that wins with one of those plots; the reward coin is paid to `RewardPuzzle(singleton_id=L).puzzle_hash()`.
4. Attempt `claim_pool_rewards()`/`forward_pool_reward()` — both require `singleton_action_spend()` against a live singleton coin for `L`, which no longer exists [7](#0-6) .
5. The reward coin has no valid spend path (`SingletonMember` can never receive a genuine `SEND_MESSAGE` from `L` again) and is permanently stuck.

@dataclass(kw_only=True, frozen=True)
class RewardPuzzle:
    singleton_id: bytes32

    @property
    def singleton_member(self) -> SingletonMember:
        return SingletonMember(singleton_id=self.singleton_id)

    def puzzle_with_restrictions(self) -> PuzzleWithRestrictions:
        return PuzzleWithRestrictions(nonce=0, restrictions=[], puzzle=self.singleton_member)

    def puzzle(self) -> Program:
        return self.puzzle_with_restrictions().puzzle_reveal()

    def puzzle_hash(self) -> bytes32:
        return self.puzzle().get_tree_hash()

    def solve(
        self, singleton_inner_puzzle_hash: bytes32, delegated_puzzle_and_solution: DelegatedPuzzleAndSolution
    ) -> Program:

            [],
            [],
            self.singleton_member.solve(singleton_inner_puzzle_hash),
