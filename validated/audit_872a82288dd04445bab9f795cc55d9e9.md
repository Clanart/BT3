### Title
Torsioned Ed448 points accepted by `read_G` because `Point::is_torsion_free` is a tautology - (File: crypto/ed448/src/point.rs)

### Summary
The TypeBot bug is a validation check that exists for the protected code path but is silently absent on an alternate path reachable with untrusted input. Serai's Ed448 group exhibits the same shape: `GroupEncoding::from_bytes` for `Point` invokes `is_torsion_free`, but the implementation computes `(-P) + P == identity`, which is true for *every* point. The subgroup/torsion check is therefore a no-op, and `Ed448::read_G` — used by `Commitments::read`, `read_share`, `ThresholdKeys::read`, `SchnorrSignature::read`, `DLEqProof::read`, etc. — accepts attacker-controlled points with a non-trivial torsion component (Ed448 has cofactor 4) that every other part of the stack assumes are prime-order.

### Finding Description
In `crypto/ed448/src/point.rs`, `Point::is_torsion_free` is defined as:

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

`Scalar::ZERO - Scalar::ONE` is `-1`, so the expression is `(-self) + self`, which is the identity for any group element whatsoever. The check can never fail. `from_bytes` ANDs `not_negative_zero & point.is_torsion_free()` into its `CtOption` validity, so the only effective filters are canonical y-encoding, x recovery, and the negative-zero rule — no torsion exclusion.

Contrast with `Ciphersuite::read_G` in `crypto/ciphersuite/src/lib.rs:91-100`, which carefully enforces canonical encodings (`point.to_bytes() != encoding` is rejected). Canonical serialization does not exclude torsion: a point `Q = P + T` with `T` of order 2 or 4 has a perfectly canonical encoding that round-trips. So the canonicality gate that protects other paths is intact, while the subgroup gate on this path is dead code — the same "protected here, bypassed there" pattern as the SSRF control bypassed through the sandboxed `fetch`.

Reachability is unprivileged: every deserialization sink listed as in-scope on Ed448 routes through this `from_bytes`:

- `SignMachine::read_preprocess` → `Commitments::read` → `NonceCommitments::read` → `GeneratorCommitments::read` → `C::read_G` (`crypto/frost/src/nonce.rs:34-36`, `:74-80`, `:133-139`; `crypto/frost/src/sign.rs:276-281`).
- `ThresholdKeys::read` reads `n` verification shares via `read_G` (`crypto/dkg/src/lib.rs:620-623`) and then calls `ThresholdKeys::new`, which computes `group_key` by interpolating shares 1..=t — a torsioned share produces a torsioned group key and a torsioned `ThresholdView::secret_share`/`scalar` relationship.
- `SchnorrSignature::<Ed448>::read`, `SchnorrAggregate::read`, `DLEqProof`/`SchnorrPoK::read` all accept torsioned `R`/`A`/generator points.

### Impact Explanation
All downstream verification math in `crypto/schnorr` and `crypto/frost` uses `multiexp_vartime` / `BatchVerifier` *without* cofactor clearing — the library is documented as strict (`crypto/schnorr/src/lib.rs:36-41`). When a counterparty feeds a torsioned point into one of these strict verifiers while another verifier (e.g., RFC 8032-style `8R = 8sG - 8cA`, or any cofactor-clearing implementation) interprets the same bytes, the two verifiers disagree on validity — an undocumented cross-implementation verification divergence.

Concretely, for a malicious FROST participant:

1. They submit a preprocess whose `GeneratorCommitments` contain `D' = D + T` (or `E' = E + T`) for a low-order `T`. `Commitments::read` accepts it.
2. The aggregate nonce `R = Σ(D_i + ρ_i·E_i)` computed by `BindingFactor::nonces` (`crypto/frost/src/nonce.rs:194-211`) is shifted by `T` (or `ρ·T`), which the attacker controls modulo the binding factor.
3. In `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:462-489`), the attacker can satisfy the strict per-share equation `R_i + c·V_i − s_i·G = 0` against the *torsioned* bound nonce while influencing whether the final aggregate `(R, s)` verifies strictly — letting a single malicious signer selectively abort sessions or produce a signature `(R + T', s)` that strict Ed448 verification rejects but cofactor-cleared verification accepts for the same key. Equivalently, submitting torsioned verification shares through `ThresholdKeys::read` yields a group key outside the prime-order subgroup, so signatures verified under it are bound to `x mod ord` but ambiguous in the torsion component — enabling malleability/forgery against any verifier that folds torsion, and inconsistent acceptance between strict and clearing verifiers on the same `(R, s, A, m)`.

This is an incorrect-verifier-formula / missing-validation class bug reachable purely by public bytes an unauthenticated counterparty supplies to `read_preprocess` / `read_share` / `ThresholdKeys::read`.

### Likelihood Explanation
Any Ed448 deployment using `modular-frost` with peer-supplied preprocesses or serialized `ThresholdKeys` is exposed; a malicious (not colluding-threshold) participant alone can inject the torsion component. Triggering is deterministic — no grinding required, since `is_torsion_free` never fails. Impact severity depends on the consuming protocol: at minimum it is a reliable integrity/availability break of FROST-Ed448 sessions and a verification-consistency break; where any verifier in the system clears the cofactor (standard EdDSA semantics), it is a signature-validity ambiguity exploitable as malleability/forgery.

### Recommendation
Implement a real torsion check in `Point::is_torsion_free` in `crypto/ed448/src/point.rs` — e.g., multiply by the prime subgroup order `q` and require identity (`(self * Scalar::from(q)).is_identity()`), or double the point twice (cofactor 4) and verify the result is not identity while consistent subgroup membership holds. Additionally, reject the identity point in `GeneratorCommitments::read`/`Commitments::read` so a torsioned or identity commitment cannot zero out a nonce contribution.

### Proof of Concept
```rust
// crypto/ed448 — demonstrate is_torsion_free is a tautology
use group::{Group, GroupEncoding, ff::Field};

// T: a low-order point, e.g. the order-2 point (x=0, y=-1) on Ed448,
// or an order-4 point obtained by doubling it. Construct bytes for
// Q = P + T where P is any prime-order point with a canonical encoding.

let p = Ed448Point::generator();                    // prime-order
let t = point_of_order_4();                          // (q * t) != identity
let q = p + t;                                       // has torsion component

// is_torsion_free(q) computes (-q) + q == identity  => always true
assert!(bool::from(q.is_torsion_free()));            // BUG: returns true

// Therefore read_G accepts a torsioned point:
let bytes = q.to_bytes();                            // canonical encoding
let decoded = Ed448::read_G::<&[u8]>(&mut bytes.as_ref()).unwrap();
assert_eq!(decoded, q);                              // torsioned point accepted

// Feeding these bytes as a FROST preprocess commitment (or as a
// verification share inside serialized ThresholdKeys) injects the
// order-4 component T into R / group_key, which strict multiexp-based
// verification treats as part of the point while any cofactor-clearing
// verifier ignores it — divergent signature validity on identical input.
```
