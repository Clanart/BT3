## Title
Asymmetric decimal scaling in `hyper-fungible-token`'s `convert_to_balance`/`convert_to_erc20` mints/credits wrong token amounts when a local asset has more decimals than its registered remote ERC20 precision - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `hyper-fungible-token` pallet converts amounts between a local Substrate asset's decimals and the registered remote-chain ERC20 decimals using `Precisions::<T>::get(asset_id, chain)`. The conversion helpers only scale correctly when `erc_decimals >= local_decimals`; when `local_decimals > erc_decimals`, `saturating_sub` clamps the exponent to zero and the amount is passed through unscaled instead of being divided/multiplied by the correct factor.

### Finding Description
The two conversion primitives are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This is a one-directional formula: it is only mathematically correct when `erc_decimals >= local_decimals` (division shrinks a higher-precision ERC20 amount down to a lower-precision local balance, or multiplication grows a lower-precision local balance up to a higher-precision ERC20 amount). When `local_decimals > erc_decimals`, `saturating_sub` returns `0`, so `10^0 = 1` is used — i.e. **no scaling is applied at all**, even though the correct factor should be `10^(local_decimals - erc_decimals)` applied in the opposite direction (multiply in `convert_to_balance`, divide in `convert_to_erc20`).

`erc_decimals` comes from governance-configured `Precisions::<T>::get(asset_id, chain)` per `(asset, destination chain)`, exactly analogous to the token-gateway's "Updating Asset Precision" mechanism (`precision: BTreeMap<StateMachine, u8>`), which explicitly exists to support **different decimal configurations per chain** (e.g. "10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum"). [2](#0-1) 

`local_decimals` is either the native currency's fixed `T::Decimals::get()` or the local `pallet-assets` decimals via `Inspect::decimals`, used in both the outbound `send()` path and the inbound `on_accept`/`on_timeout` paths: [3](#0-2) [4](#0-3) 

Both `on_accept` (credits an incoming transfer to a beneficiary) and `on_timeout` (refunds the original sender) call `convert_to_balance` using the same asymmetric formula: [5](#0-4) [6](#0-5) 

If a local asset is registered with more decimals than its remote ERC20 counterpart's registered precision (e.g. a locally 18-decimal wrapped asset paired with a 6-decimal remote ERC20 like a USDC-style token), the outbound `convert_to_erc20` call in `send()` fails to divide down by `10^12`, over-encoding the ERC20 `amount` in the dispatched cross-chain message by `10^12`, and the inbound `convert_to_balance` in `on_accept`/`on_timeout` fails to multiply up by the same factor, under-crediting/under-refunding the local balance by `10^12`. Existing guards (`Precisions::<T>::get(...).ok_or(...)`, `DecimalsNotConfigured`) only check that a precision value exists — they never validate the *relative ordering* of `erc_decimals` vs `local_decimals`, so nothing stops this asymmetric case from being configured and exploited.

This mirrors the external report's core pattern exactly: two quantities meant to carry the same "amount per unit of asset" dimension diverge because a decimals difference is applied in only one direction, silently, with no revert.

### Impact Explanation
This directly threatens fund custody in the bridge's escrow/mint model:
- **Outbound (`send`)**: user's tokens are locked/burned at full local value, but the ERC20 amount encoded to the destination chain contract is inflated by `10^(local_decimals-erc_decimals)` — the destination-chain minting/unlocking logic (`WrappedHyperFungibleToken`/`HyperFungibleToken` contracts, not shown here but consuming `message.amount`) would attempt to mint/release a wildly incorrect (typically far larger) amount than was escrowed, a direct fund-safety violation for the bridge's custody invariant ("bridged assets... must move exactly once and only to the rightful beneficiary and amount").
- **Inbound (`on_accept`)**: the beneficiary receives `10^-(local_decimals-erc_decimals)` times too few tokens — a fund loss for the recipient (locked/burned real value elsewhere, but credited near-zero locally, since dividing raw units by 1 while denominations differ by 10^12 yields an economically negligible result).
- **Timeout refund (`on_timeout`)**: refunds the original sender by the same undersized (or oversized on the erc>local side, already handled) amount — a genuine "loss of funds" scenario for refund/timeout handling, one of the explicitly in-scope impact categories.

### Likelihood Explanation
The trigger condition (`local_decimals > erc_decimals` for some registered `(asset_id, chain)` pair) is not a malicious-actor requirement — it is a normal, foreseeable governance configuration state, since the entire purpose of `Precisions`/asset-precision-per-chain is to support assets with differing decimals across chains, and the docs explicitly cite the DOT 10-vs-18-decimal case as the motivating example (which happens to be the "safe" direction here, but any newly bridged asset pairing a locally-high-decimal asset with a lower-decimal remote token, e.g. 18-decimal local wrapped USDC vs 6-decimal remote USDC precision entry, hits the broken branch). No relayer collusion, no proof forgery, and no privileged bypass is needed by the end user triggering `send()`/receiving `on_accept`/`on_timeout` — the bug fires automatically whenever this asset/chain combination is configured and any user transacts through it.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling with a signed comparison that scales in the correct direction regardless of which side has more decimals:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit tests explicitly covering `local_decimals > erc_decimals` in both directions, and consider adding round-trip invariant tests (`convert_to_balance(convert_to_erc20(x, e, l), e, l) == x`, modulo truncation) to `pallet_hyper_fungible_token` tests.

### Proof of Concept
1. Governance registers a local pallet-asset with 18 decimals (`local_decimals = 18`) and sets `Precisions::<T>::set(asset_id, dest_chain, 6)` for a destination EVM chain (`erc_decimals = 6`).
2. User calls `send()` with `amount = 1_000_000_000_000_000_000` (1.0 token in local 18-decimal units). Local balance/asset is correctly locked/burned for this full amount.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18` unchanged instead of `1e18 / 10^12 = 1_000_000` (the correct 6-decimal "1.0 token" ERC20 amount) — the dispatched message encodes an amount 10^12 times too large.
4. Symmetrically, if an inbound message from that chain carries `message.amount = 1_000_000` (1.0 token at 6-decimal ERC20 precision), `on_accept` calls `convert_to_balance(1_000_000, erc_decimals=6, local_decimals=18)`, again computing `saturating_sub = 0`, returning `1_000_000` unchanged instead of `1_000_000 * 10^12 = 1e18` — the beneficiary is credited 10^12 times too little, and the same shortfall applies to `on_timeout` refunds.

This confirms the invariant break: the escrowed/burned local value and the credited/encoded remote value diverge by exactly `10^|local_decimals - erc_decimals|` whenever `local_decimals > erc_decimals`, with no revert or bound check to prevent it.
