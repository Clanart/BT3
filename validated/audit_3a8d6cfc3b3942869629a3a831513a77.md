### Title
Payout transaction's operator-attribution `OP_RETURN` is unsigned, letting anyone hijack or poison credit for a fronted withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The `Payout` transaction that fronts a Citrea withdrawal is only partially authenticated by the withdrawing user's signature. The user signs with `TapSighashType::SinglePlusAnyoneCanPay`, which commits *only* to input index 0 and the output at the same index (the user's payout output). The transaction's remaining outputs — critically the `OP_RETURN` output that records which operator's x-only pubkey "fronted" the withdrawal — and any extra funding inputs are completely unauthenticated. Whoever actually gets the transaction mined can freely choose the `OP_RETURN` payload, decoupling "the operator credited" from "the party that actually paid."

### Finding Description
`create_payout_txhandler` builds three outputs: the user payout, an anchor, and an `OP_RETURN` with the fronting operator's x-only pubkey, but only signs input 0 with the user-supplied signature: [1](#0-0) 

The protocol explicitly documents and enforces `SinglePlusAnyoneCanPay` for this signature: [2](#0-1) [3](#0-2) 

Per BIP-341/342, `SIGHASH_SINGLE|ANYONECANPAY` binds only the signed input and the output sharing its index; it places **no** constraint on other inputs or outputs of the final transaction. `Operator::withdraw` confirms this by verifying the signature against sighash of input 0 only, and then funds the transaction with bitcoind's wallet (adding arbitrary additional inputs) before broadcast: [4](#0-3) 

Once *any* version of this payout transaction confirms on-chain, the verifier's block-sync logic derives "who fronted the withdrawal" purely by parsing the confirmed transaction's `OP_RETURN`, with no cross-check against the additional funding inputs or the original broadcaster: [5](#0-4) 

That parsed `operator_xonly_pk` is persisted as `payout_payer_operator_xonly_pk` and later trusted verbatim to gate which operator's automation is authorized to run the kickoff/reimbursement flow: [6](#0-5) 

and to release the vault funds via `create_reimburse_txhandler`, which pays to that operator's configured reimbursement address: [7](#0-6) 

**Root cause / broken binding:** the equality that should hold is `party who funded the payout output == operator credited in OP_RETURN`. Because the `OP_RETURN` output and any auxiliary funding inputs sit outside the `SinglePlusAnyoneCanPay` commitment, this equality is not enforced by any signature — it is enforced only by convention/whichever party gets a transaction mined first.

### Impact Explanation
Any unprivileged party who observes an in-flight payout transaction in the mempool (or who is the withdrawing user constructing their own competing transaction) can reuse the reusable `ANYONECANPAY` input, add their own funding inputs, and substitute an arbitrary `OP_RETURN` payload:
- Embedding a **garbage / unregistered x-only pubkey** causes `validate_payer_is_operator` to never match any real operator for that deposit (kickoff transactions are only pre-signed for the operator set chosen at deposit time), so no operator can ever claim the `Reimburse` transaction for that `MoveToVault` UTXO — permanently freezing that vault UTXO's reimbursement while the withdrawal itself has already been paid by the attacker's own funds via the confirmed transaction. This matches the Critical impact "a vault UTXO permanently frozen."
- Embedding an **existing, uninvolved operator's** public key misattributes credit ("a misattributed... reimbursement") for a payout that operator never funded, letting that transaction's confirmed `OP_RETURN` alone drive that operator's automation into the reimbursement flow it did not earn.

### Likelihood Explanation
The only prerequisite is possession of the withdrawing user's `SinglePlusAnyoneCanPay` signature (available to the withdrawing user themselves, or observable once a legitimate operator's payout transaction is broadcast to the mempool) plus enough BTC to cover the fixed, signature-bound user-payout output. No verifier, operator, watchtower, aggregator, security-council, or sequencer role is required to mount the attack; it exploits a pure signature-scoping gap in transaction construction.

### Recommendation
Bind the operator-attribution data to the signature that authorizes the payout, e.g. by having the user's signature cover all outputs (or at minimum the `OP_RETURN`) via `SIGHASH_ALL|ANYONECANPAY` restricted to a template, or by having the fronting operator co-sign/commit to the specific `OP_RETURN` content, and by validating on the verifier side that the party who supplied the additional funding inputs corresponds to the `OP_RETURN` operator (e.g., requiring the change/anchor-adjacent inputs to originate from that operator's known collateral/reimbursement key).

### Proof of Concept
1. Withdrawing user (or an observer) obtains the `SinglePlusAnyoneCanPay`-signed input/output pair used to authorize a specific payout (either self-created, or lifted from a mempool-broadcast `Payout` transaction from a legitimate operator).
2. Attacker constructs a new transaction reusing that exact input/output pair (required by the signature), adds their own funding inputs to cover the fixed payout amount and fee, and sets the `OP_RETURN` output to an arbitrary or unregistered x-only pubkey instead of the legitimate operator's.
3. Attacker broadcasts this transaction with a competitive/RBF fee so it confirms instead of (or before) any honestly-constructed version.
4. `update_finalized_payouts` parses the confirmed transaction's `OP_RETURN` and records the attacker-chosen pubkey as `payout_payer_operator_xonly_pk` [8](#0-7) .
5. Since no registered operator's kickoff data matches this bogus pubkey, `validate_payer_is_operator` never succeeds for any real operator [9](#0-8) , so the corresponding `MoveToVault` UTXO's `Reimburse` path can never be triggered, freezing that vault UTXO's funds while the withdrawal itself was already paid out by the attacker.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
