## Analysis: Division-by-zero analog found

The CVE describes an unchecked integer division in Xpdf's `PostScriptFunction::exec` (`psOpIdiv`) causing a floating-point exception (crash). The Kaia codebase has a directly analogous unchecked division in the KIP-71 dynamic base-fee calculation, reachable through a governance parameter that lacks the zero-value guard its sibling parameter has.

### Title
Division-by-zero panic in `NextMagmaBlockBaseFee` via unguarded `Kip71GasTarget` governance parameter - (File: `params/kip71_config.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` in two branches without checking for zero, unlike the adjacent `BaseFeeDenominator` which is explicitly guarded against zero. The governance parameter registry `Kip71GasTarget` in `kaiax/gov/param.go` uses `noopFormatChecker` (no validation), while `Kip71BaseFeeDenominator` explicitly requires `v != 0`. This asymmetry allows `GasTarget` to be set to `0` via a governance vote, which is subsequently divided into by every block's base-fee computation.

### Finding Description
In `params/kip71_config.go`, `NextMagmaBlockBaseFee` computes: [1](#0-0) 

Note that `BaseFeeDenominator` is defensively defaulted to `64` if zero, but `gasTarget` has no such fallback: [1](#0-0) 

When the parent block's gas used differs from `gasTarget` (almost always true if `gasTarget == 0`), the code performs: [2](#0-1) 
and in the decreasing branch: [3](#0-2) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `big.Int.Div` panics on division by zero when `gasTarget == 0`.

The root cause is that the governance parameter validator for `Kip71GasTarget` performs no format check, unlike `Kip71BaseFeeDenominator` which explicitly rejects zero: [4](#0-3) 

This function is invoked on every block during header validation (`VerifyMagmaHeader` → `NextMagmaBlockBaseFee`), as confirmed by the block validator's use of the governance parameter set: [5](#0-4) [6](#0-5) 

It is also exercised in fee estimation/RPC paths such as `node/cn/gasprice/feehistory.go`: [7](#0-6) 

### Impact Explanation
If `GasTarget` is voted to `0` (a value not rejected by the parameter's format checker), every node computing the next Magma base fee — during header validation, block assembly, and `eth_feeHistory`/gas price RPC calls — will hit an unrecovered `panic` on integer division by zero. Since this code runs in the consensus-critical header-validation path, this is a chain-halting denial of service across all honest nodes (not a resource-only DoS, but a hard crash/panic in core state-transition/block-validation logic), satisfying the "acceptance of an invalid transaction or block" / state-divergence class of impact once triggered.

### Likelihood Explanation
Reaching this requires a governance parameter update setting `Kip71GasTarget` to `0`. This is normally a governance-only action, but it is explicitly reachable through the governance-parameter voting mechanism listed as in-scope ("governance parameters"), and — critically — the code contains no defensive validation to prevent it, in stark contrast to the sibling `BaseFeeDenominator` parameter which the developers did guard. This inconsistency indicates the omission is an oversight rather than an intentional restriction, and once the value is set, the panic is deterministic and triggers on the very next block for every full node.

### Recommendation
Add a `FormatChecker` requiring `v != 0` for `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`), and/or add a defensive zero-fallback for `gasTarget` inside `NextMagmaBlockBaseFee` (analogous to the existing `baseFeeDenominator` zero-fallback) so a zero value cannot reach the `Div` call.

### Proof of Concept
1. Submit/pass a governance vote setting `kip71.gastarget` (`Kip71GasTarget`) to `0`. The parameter's `FormatChecker` is `noopFormatChecker`, so the value is accepted: [8](#0-7) 
2. Once the vote takes effect at the target block, any block whose `parentGasUsed != 0` (virtually always true) causes `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))`, panicking: [9](#0-8) 
3. This panic occurs inside header validation/base fee computation on every node, halting block processing chain-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
