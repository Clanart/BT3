### Title
PlotNFT owner's already-accrued p2-singleton pool rewards can be permanently swept by the pool during the `LEAVING_POOL` (exiting) window - ([File: chia/pools/plotnft_drivers.py])

### Summary
`PlotNFTPuzzle.forward_pool_reward()` allows the pool's delegated puzzle path to sweep any p2-singleton reward coin belonging to the PlotNFT as long as `self.pool_config is not None` (`pooling == True`). This condition remains true for the entire `LEAVING_POOL` window (`exiting=True` but `pool_config` still set), so a pool can continue collecting rewards the user farmed during that window, even though the user has already signaled intent to leave and reclaim self-custody of future rewards. `PlotNFT.claim_pool_rewards()` explicitly refuses to run while `pooling` is true, so the owner has no way to reclaim these coins first. This is directly analogous to the reported Tokemak issue where value legitimately owed to a user can be swept away by a privileged/counterparty action before the user gets a chance to claim it, with no timelock or grace period protecting the user's already-accrued rewards.

### Finding Description
`forward_pool_reward()` is gated only on `self.pooling`, i.e., `pool_config is not None`: [1](#0-0) 

`pooling` is a property purely derived from whether `pool_config` is set: [2](#0-1) 

Critically, `claim_pool_rewards()` (the owner-only self-custody claim path) is blocked with the exact same `pooling` check: [3](#0-2) 

The `LEAVING_POOL` state (`exiting=True`) does **not** clear `pool_config` - it is only cleared once the second-stage exit transaction executes after the heightlock: [4](#0-3)  and [5](#0-4) 

So from the moment the user calls `leave_pool()` until the heightlock-gated `exit_waiting_room` spend confirms, the PlotNFT is still "pooling" from the puzzle's perspective. Any p2-singleton reward coin farmed to this PlotNFT during that window (which can span many blocks, since `heightlock` is pool-configurable) is still sweepable via `forward_pool_reward`, and the owner is explicitly forbidden from claiming it via `claim_pool_rewards` in the same window. The wallet-level test `test_plotnft_lifecycle` labels this behavior directly as "LOSE REWARDS (while leaving)": a reward earned/tracked in `plotnft2_store` is swept by `forward_pool_reward` even after `leave_pool()` was called, decreasing the plotnft wallet's confirmed balance to zero for that reward: [6](#0-5) 

The companion "LOSE REWARDS (while pooling)" test shows the same sweep mechanic applies broadly whenever `pool_config` is set: [7](#0-6) 

`claim_pool_reward_dpuz_and_solution`/`forward_pool_reward_inner_solution` show the delegated-puzzle authorization is bound to the pool's own puzzle/memoization curried into `forward_to_pool_puzzle_hash_dpuz`, i.e. the pool (or anyone possessing that delegated puzzle) - not the plot owner - is the actor who authorizes and benefits from the sweep: [8](#0-7) [9](#0-8) 

There is no timelock, grace period, or "in-flight rewards belong to the owner" carve-out analogous to what the Tokemak report recommends - the moment a reward coin lands at the p2-singleton address while `pool_config` is still non-null, it is fully claimable by the pool side, and the owner has no competing claim path.

### Impact Explanation
A PlotNFT owner who initiates `leave_pool()` (e.g. because the pool is misbehaving, has bad terms, or the owner simply wants to go self-custody) continues farming to the pool's payout address for the entire heightlock duration set by that pool. Any block rewards landed on the p2-singleton puzzle hash during that window remain claimable exclusively by the pool via `forward_pool_reward`, while the owner is blocked from claiming them via `claim_pool_rewards` (`ValueError: Cannot claim rewards while pooling...`). This directly parallels the Tokemak-analog impact of "unclaimed rewards may be lost/redirected due to a state change the user cannot preempt" - here, farmed XCH block rewards belonging economically to the plot's owner are redirected to the pool operator with no recourse, for a duration entirely controlled by pool configuration (`heightlock`), which can be set arbitrarily high.

### Likelihood Explanation
This triggers under completely benign, expected usage - any owner-initiated `leave_pool()` while the plot continues farming (which is normal, since farming isn't stopped and plots keep winning blocks during the leaving window). No malicious peer or adversarial network condition is required; the pool operator merely needs to continue exercising its already-granted delegated-puzzle authority during the leaving window, which is exactly what `forward_pool_reward` is designed to let it do. The wallet's own test suite documents and asserts this exact loss scenario as expected behavior, indicating it is a real, reachable condition rather than a hypothetical edge case.

### Recommendation
Introduce a mechanism so that rewards farmed after a `leave_pool()` transition (i.e., once `exiting=True`) are not claimable by the pool via `forward_pool_reward`, or route rewards accrued during the `LEAVING_POOL` window to a puzzle the owner can also claim from (mirroring the timelock-based remediation suggested in the original report: give the owner a window to reclaim in-flight rewards before the pool's sweep right becomes exclusive). At minimum, `claim_pool_rewards()` should be permitted for rewards received on/after the height at which `exiting` was set, even while `pool_config` remains non-null, so the owner retains a competing claim path for rewards farmed during their own exit process.

### Proof of Concept
Exercised by the existing wallet test suite itself:
1. Owner's `PlotNFT2Wallet` is farming to a pool (`pool_config` set).
2. Owner calls `leave_pool()`, setting `exiting=True` while `pool_config` remains set. [4](#0-3) 
3. A block reward lands on the PlotNFT's p2-singleton puzzle hash and is tracked in `plotnft2_store.pool_reward2s`.
4. Owner attempts `claim_rewards()` and is rejected with `"Cannot claim rewards while pooling..."`: [10](#0-9) 
5. The pool (or anyone with the delegated puzzle) instead calls `forward_pool_reward(pool_reward)` and pushes the spend bundle, successfully sweeping the reward to the pool, confirmed by the balance delta of `-POOL_REWARD_AMOUNT`: [6](#0-5) 

This confirms rewards earned by the owner during the owner-initiated leaving window are irretrievably swept by the pool.
