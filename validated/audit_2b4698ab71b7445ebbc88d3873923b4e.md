### Title
Quadratic Lagrange interpolation in `ThresholdKeys::read`/`new` enables amplified CPU exhaustion from untrusted bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `n` verification-share points from an attacker-controlled byte stream, then calls `ThresholdKeys::new`, which computes the group key via Lagrange interpolation whose cost is `O(t²)` in scalar operations plus `t` field inversions. Because `t` and `n` are u16 fields taken directly from the input, a ~2 MB buffer forces ~4×10⁹ field multiplications — a resource-consumption amplification analogous to CVE-2026-3592's "small query, disproportionate work" shape.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` from the reader, then reads `n` group elements via `C::read_G` (one point per participant index `1..=n`) and passes them to `ThresholdKeys::new`. [1](#0-0) 

`ThresholdKeys::new` validates only counts (`verification_shares.len() == n`, indices `<= n`, `t <= n`) and then computes `group_key` as `sum_{i=1..=t} verification_shares[i] * interpolation_factor(i, t)`. [2](#0-1) 

`interpolation_factor` for `Interpolation::Lagrange` is a nested loop over all `t` included participants performing numerator/denominator products plus one scalar inversion per factor — so building `group_key` costs `t` inversions, `t` point-scalar multiplications, and `Θ(t²)` field multiplications. [3](#0-2) 

The input size is `O(n)` points (`n` ≤ 65535), while the work is `O(t²)`. With `t = n = 65535`, a ~2.1 MB input (for 32-byte points) triggers ~4.3×10⁹ field multiplications, 65,535 field inversions, and 65,535 scalar-point multiplications — roughly a 2000× work-per-byte amplification, with no bound enforced anywhere in `read` or `new`.

The same quadratic pattern is reachable a second time at signing: `ThresholdKeys::view` calls `interpolation_factor` once per included signer, again `Θ(|included|²)`. [4](#0-3) 

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (a serialized key blob is untrusted input in any deployment that loads keys it did not itself generate, e.g. coordinator-distributed key material, backup restore, or peer-supplied DKG output) can force the victim to burn orders of magnitude more CPU than the input size justifies — stalling the deserialization path and, in an async/networked setting, a worker thread or request handler. Medium severity matches the source class: availability impact only, no secret leakage.

### Likelihood Explanation
Reachability is real but conditional: the victim must deserialize a `ThresholdKeys` blob originating from an untrusted party, and the heavy path requires a legitimately large `n`/`t` (the input still must contain `n` valid encoded points, so the attacker's own cost is `O(n)` — the asymmetry comes purely from the quadratic interpolation). `Participant::new` rejects 0 and `view` rejects duplicates, so no cheaper trigger exists; the cost is structural. Deployments that only ever load self-produced keys with modest `n` are not exposed.

### Recommendation
Compute the group key incrementally or bound deserialization: enforce a sane maximum `n`/`t` in `ThresholdKeys::read`/`new` (e.g. reject `n` above a documented ceiling such as 1024), and/or compute `group_key` using a linear-time scheme (e.g. accumulate the Lagrange basis via a running product / precomputed prefix–suffix products) so `O(t²)` scalar work becomes `O(t)`. At minimum, document that `read` performs work quadratic in `t`.

### Proof of Concept
```rust
// In-scope entry point: ThresholdKeys::<C>::read on attacker bytes
// Crafted input: t = n = 65535, i = 1, interpolation = Lagrange (byte 1),
// secret_share = any valid F encoding, then n valid point encodings.
//
// Structure:
//   [4B ciphersuite ID len][ID][u16 t][u16 n][u16 i][0x01][F secret_share][n × G]
//
// ThresholdKeys::new then evaluates, for each i in 1..=t:
//   interpolation_factor(i, t): Θ(t) field muls + 1 inversion
//   verification_shares[i] * factor
// Total: Θ(65535²) ≈ 4.3e9 field muls + 65535 inversions + 65535 point muls
// from ~2.1 MB of input — ~2000× amplification of work per input byte.

let t: u16 = u16::MAX;
let n: u16 = u16::MAX;
let mut buf = id_header();                     // C::ID len + C::ID
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(1u16.to_le_bytes());                // i = 1
buf.push(1);                                   // Interpolation::Lagrange
buf.extend(scalar_repr(C::F::ONE));            // secret_share
let point = C::generator().to_bytes();
for _ in 0 .. n { buf.extend(point.as_ref()); }

// CPU-bound for ~minutes on this single call:
let _keys = ThresholdKeys::<C>::read(&mut &buf[..]);
```
