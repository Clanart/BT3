### Title
Improper Restriction of Excessive Keyring-Passphrase Authentication Attempts via Daemon `unlock_keyring`/`set_keyring_passphrase` RPC - ([File: chia/daemon/server.py])

### Summary
The Chia daemon's `unlock_keyring` command (and related passphrase commands) validate the master keyring passphrase on every call with no attempt counter, delay, or lockout at the RPC layer. The only throttling that exists (`MAX_RETRIES = 3` and `FAILED_ATTEMPT_DELAY`) is implemented purely in the *interactive CLI prompt* helper `obtain_current_passphrase()` in `chia/util/keyring_wrapper.py`, which is never invoked by the daemon's WebSocket RPC dispatcher. Any client that can reach the daemon's local RPC endpoint can call `unlock_keyring` repeatedly and automate unlimited passphrase guesses, exactly mirroring the caddy-security CVE-2024-21500 pattern where a client-visible "blocking" step is bypassed by automating the full multistep flow directly against the underlying handler instead of the guarded UI path.

### Finding Description
`obtain_current_passphrase()` is the only place enforcing a maximum retry count before raising `KeychainMaxUnlockAttempts`: [1](#0-0) [2](#0-1) 

This limiter is only exercised by interactive callers (e.g. `chia/cmds/start_funcs.py` calling `get_current_passphrase` in a `ThreadPoolExecutor`) and by `dump_keyring.py`'s local decrypt loop: [3](#0-2) [4](#0-3) 

The actual daemon-side RPC handler that performs the real passphrase check, `WebSocketServer.unlock_keyring()`, has no retry counter, no delay, and no lockout state — it simply calls `Keychain.master_passphrase_is_valid()` on every invocation and returns `success`/`error` directly: [5](#0-4) 

The same pattern applies to `remove_keyring_passphrase()`, which checks `current_passphrase` against the keyring with no attempt limiting either: [6](#0-5) 

`chia/daemon/server.py` imports no rate-limiting, counter, or lockout utility at all (confirmed by its import list), and there is no `MAX_RETRIES`/`FAILED_ATTEMPT_DELAY`-style symbol anywhere in the daemon module: [7](#0-6) 

The underlying validation path, `FileKeyring.check_passphrase()`, is a pure stateless decrypt-and-compare with no counter either: [8](#0-7) 

Because the daemon's WebSocket route dispatch treats `unlock_keyring` as an ordinary command (see `.cursor/context/daemon.md` describing `unlock_keyring` mutating "global keyring cache/state" with no mention of attempt tracking), any local RPC caller that reaches this websocket — whether via a compromised local client, a malicious script using a retained daemon certificate, or any process capable of issuing repeated `unlock_keyring`/`remove_keyring_passphrase`/`set_keyring_passphrase` calls — can brute-force the keyring master passphrase without ever triggering the `KeychainMaxUnlockAttempts` guard that protects the interactive/CLI path, because that guard lives in a different code path entirely (`obtain_current_passphrase`) that the RPC dispatcher never calls. [9](#0-8) 

### Impact Explanation
Successful brute-forcing of the master keyring passphrase exposes the encrypted private keys stored in the keyring (`FileKeyring`), which back all wallet, farmer, and pool secret keys managed by the daemon. Since the CLI-visible protection (`KeychainMaxUnlockAttempts` after 3 tries) gives users a false sense of protection against passphrase guessing, but the same underlying capability is exposed without any limit through the daemon RPC surface, an attacker who can reach the daemon socket (e.g., a lower-privileged local process holding client certs, or an application-layer client automating the "multistep" unlock/hint/validate flow) can defeat the passphrase entirely given enough attempts, compromising private key confidentiality — impacting confidentiality of the wallet's spend authority in line with the Medium severity of the original CWE-307 report.

### Likelihood Explanation
Exploitation requires the ability to open a session against the local daemon websocket (mutual TLS with the daemon's private client cert, as documented in `.cursor/context/daemon.md`), which is a semi-trusted local/admin boundary rather than a public network path. This limits the likelihood versus a fully unauthenticated network vulnerability, but any process with daemon connectivity (GUI compromise, malicious local script re-using extracted daemon certs, or a compromised RPC client) can automate unlimited passphrase attempts programmatically since no server-side attempt counter, delay, or lockout exists in `chia/daemon/server.py`.

### Recommendation
Add server-side attempt tracking and lockout/backoff directly in `WebSocketServer.unlock_keyring()` (and `remove_keyring_passphrase()`/`set_keyring_passphrase()`), independent of the CLI-only `obtain_current_passphrase()` limiter — e.g., track failed attempt counts and timestamps per daemon connection/keyring, enforce an exponential backoff or hard lockout after N consecutive failures, and raise `KeychainMaxUnlockAttempts` (or an equivalent RPC error) from the daemon handler itself so the protection cannot be bypassed by calling the RPC command directly instead of going through the guarded interactive prompt.

### Proof of Concept
1. Start the daemon with a master passphrase set (`Keychain.set_master_passphrase`).
2. Open a WebSocket connection directly to the daemon (bypassing any CLI prompt), as done in `chia/_tests/core/daemon/test_daemon.py::test_validate_keyring_passphrase_rpc` and the `unlock_keyring` `RouteCase`s.
3. Programmatically send repeated `unlock_keyring` payloads with different guessed passphrases in a loop, e.g.:
```python
for guess in candidate_passphrases:
    await ws.send_str(create_payload("unlock_keyring", {"key": guess}, "test", "daemon"))
    resp = await ws.receive()
    if resp["data"]["success"]:
        break
``` [10](#0-9) 
4. Observe that no attempt count, delay, or `KeychainMaxUnlockAttempts`-style rejection is ever returned by `chia/daemon/server.py`, allowing unlimited automated guesses, unlike the client-side `obtain_current_passphrase()` path which halts after `MAX_RETRIES = 3`.

    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"
