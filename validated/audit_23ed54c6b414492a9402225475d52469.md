### Title
GaslessSwapRouter owner can front-run `updateCommissionRate` to siphon value from in-flight `swapForGas` gasless transactions - (File: `kaiax/gasless/impl/tx_pool.go`, contract `GaslessSwapRouter`)

### Summary
The KIP-247 `GaslessSwapRouter` system contract exposes an owner-only `updateCommissionRate(uint256)` function that is applied immediately, with no timelock, no rate-change cap, and no user-controlled slippage protection against the commission itself. A gasless user's `swapForGas` transaction is validated in the mempool by `checkBalanceForSwap()` using the commission rate implied by `GetAmountIn`/`GetAmountsOut` *at admission time*, but the actual commission applied is whatever `commissionRate` is set to at execution time. This mirrors the referenced NFTX finding: a privileged pool/contract role can raise a fee parameter with no delay between a user's value-bearing action being queued and it being executed, extracting value from users who already committed to a transaction based on the old fee.

### Finding Description
`GaslessSwapRouter` stores a mutable `commissionRate` and lets the owner update it at will via `updateCommissionRate`, emitting `CommissionRateUpdated(oldRate, newRate)`: [1](#0-0) 

The `swapForGas` entry point performs the DEX swap, deducts a commission, repays the transaction's gas lender (proposer), and forwards the residual to the user, as reflected by the `SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)` event: [2](#0-1) 

The gasless module's admission checks in `kaiax/gasless/impl/tx_pool.go` only validate:
- `minAmountOut >= amountRepay`
- `amountIn >= gsr.GetAmountIn(token, minAmountOut)` (computed against the *current* on-chain state, including the *current* `commissionRate`) [3](#0-2) 

Nowhere in this check, nor in `VerifyExecutable`/`IsExecutable` (`kaiax/gasless/impl/getter.go`), is the user's `finalUserAmount` (i.e., what the user keeps after the router deducts its own commission) constrained by a user-supplied minimum. `minAmountOut` only bounds the DEX-leg slippage and the repay amount; it says nothing about the commission taken by the router on the output.

Because `commissionRate` can be changed by the owner in the same block or an earlier block than the user's already-signed `swapForGas` transaction is finally executed by a block proposer, the sequence "user signs and broadcasts `swapForGas` based on the currently observed commission" → "owner submits `updateCommissionRate` to raise the rate" → "user's swap executes at the new, higher rate" lets the owner extract materially more value from every user's already-broadcast gasless swap without the user's consent, exactly as described in the referenced report where the pool manager front-runs the fee before a large deposit executes.

### Impact Explanation
Every user relying on the gasless-swap-for-gas flow (paying gas by pre-committing a token swap) is exposed: the owner (or anyone controlling the owner key/governance timelock, if any) can raise `commissionRate` up to whatever cap the implementation allows and apply it retroactively to transactions already broadcast/pending, reducing `finalUserAmount` below what the user reasonably expected when signing. Since `minAmountOut` does not bound the post-commission user payout, users have no on-chain protection against this specific value extraction path, even though they believe `minAmountOut` fully protects them. This is a direct value-extraction/fee-abuse vector against gasless users, matching the "Accept ... fee ... abuse" acceptance criteria.

### Likelihood Explanation
The precondition is a privileged action (owner calling `updateCommissionRate`), so likelihood depends on how trusted/timelocked that owner key is — this could not be fully confirmed because the Solidity source of `GaslessSwapRouter` was not available in the indexed codebase (only the generated Go bindings and bytecode were found), so I could not verify whether `updateCommissionRate` is guarded by a maximum rate constant, a timelock, or a governance delay before it takes effect. Based on the binding surface (`Ownable`-style `onlyOwner`, `transferOwnership`, `renounceOwnership`, and an immediate `CommissionRateUpdated` event with no queued/pending-rate mechanism visible), no timelock is evident, making the exploit low-friction for whoever controls the owner key. This is analogous to, but weaker than, the original NFTX finding (where *any* untrusted user could become a pool manager); here the actor is a fixed, presumably governance-controlled owner, which likely lowers real-world likelihood but does not eliminate the underlying design gap.

### Recommendation
- Add a timelock/delay (e.g., N blocks or a governance voting period) between `updateCommissionRate` being called and the new rate taking effect, so in-flight `swapForGas` transactions are settled at the rate the user observed when signing.
- Alternatively/additionally, let `swapForGas` accept a user-specified `maxCommissionRate` (or a `minFinalUserAmount`) parameter and revert if the effective commission/final payout at execution time violates it, giving users on-chain protection independent of governance trust.
- Emit and enforce a `MAX_COMMISSION_RATE` cap (similar to the `PublicDelegation` contract's `MAX_COMMISSION_RATE`) to bound the maximum possible extraction even if the timelock is bypassed.

### Proof of Concept
1. User `U` holds ERC-20 tokens and no KAIA; wants to gaslessly obtain KAIA via `swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)`.
2. `U` queries current `commissionRate()` and DEX price, computes `minAmountOut = amountRepay + expectedResidual`, signs and broadcasts the `swapForGas` tx (and optional `approve` tx) as a gasless bundle.
3. The router owner observes the pending bundle (via mempool/API) and submits `updateCommissionRate(newHighRate)` so that it lands in the same or an earlier block than `U`'s swap.
4. `checkBalanceForSwap` (`kaiax/gasless/impl/tx_pool.go:107-142`) only validated `minAmountOut >= amountRepay` and `amountIn >= GetAmountIn(minAmountOut)` against state at admission time — it does not re-validate against `commissionRate` at execution and does not bound `finalUserAmount`.
5. When `swapForGas` executes on-chain, it still satisfies `minAmountOut` (which only covers the DEX output, not the commission), successfully repays the proposer, but the router now deducts the elevated commission from the swap output, as reflected in `SwappedForGas.commission`, resulting in a smaller `finalUserAmount` delivered to `U` than `U` expected — matching the "front-run fee to steal value" bug class from the reference report.

func (g *GaslessModule) checkBalanceForSwap(swapArgs *SwapArgs, swapNonce uint64) error {
	token := swapArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	g.gaslessInfoMu.RLock()
	swapRouter := g.swapRouter
	g.gaslessInfoMu.RUnlock()

	// tx.minAmountOut >= tx.amountRepay
	minAmountOut := swapArgs.MinAmountOut
	amountRepay := swapArgs.AmountRepay
	if minAmountOut.Cmp(amountRepay) < 0 {
		return fmt.Errorf("insufficient minAmountOut: minAmountOut=%s, amountRepay=%s", minAmountOut.String(), amountRepay.String())
	}

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(swapArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckSwapAmount() {
		// tx.amountIn >= gsr.getAmountIn(minAmountOut)
		routerContract, err := kip247.NewGaslessSwapRouterCaller(swapRouter, bc)
		if err != nil {
			return err
		}
		// Required token amountIn, given the current exchange rate and the declared minAmountOut.
		requiredAmountIn, err := routerContract.GetAmountIn(nil, token, minAmountOut)
		if err != nil {
			return err
		}
		if swapArgs.AmountIn.Cmp(requiredAmountIn) < 0 {
			return fmt.Errorf("insufficient amountIn: have=%s, want=%s", swapArgs.AmountIn.String(), requiredAmountIn.String())
		}
	}
