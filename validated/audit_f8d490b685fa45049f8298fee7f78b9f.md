### Title
Deep-link `branch` parameter bypasses ref-name validation used for git argument injection - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`)

### Summary
The external report's broken invariant is: a validation/parsing routine (salt type) is narrower/looser than the real spec of the value it feeds, letting attacker-influenced input reach a downstream consumer in a way the guard did not anticipate. The Desktop analog is the `branch` query parameter of the `x-github-client://openRepo/...` deep link, which is validated with `testForInvalidChars` from `app/src/lib/sanitize-ref-name.ts`, a regex that rejects control characters, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix and trailing slash — but does **not** reject a leading `-`/`+`.

### Finding Description
`parseAppURL` in `app/src/lib/parse-app-url.ts` accepts a `branch` query parameter from an externally-clickable URL and only rejects it if `testForInvalidChars(branch)` matches: [1](#0-0) . That function is defined in `app/src/lib/sanitize-ref-name.ts` and its `invalidCharacterRegex` never blocks a leading dash: [2](#0-1) .

Contrast this with the UI-facing text box used for user-typed branch names, `sanitizedRefName`, which explicitly strips a leading `-`/`+` from names the user types: [3](#0-2) . This shows the codebase authors were aware that leading dashes are unsafe for names later used as git command-line arguments, but that protection is only applied to the manual-entry path, not the deep-link path.

The parsed `branch` value flows to `Dispatcher.openRepositoryFromUrl` → `openBranchNameFromUrl(url, branchName)` → `this.checkoutLocalBranch(repository, branchName)`: [4](#0-3) . Ultimately branch checkouts are executed via `checkoutBranch` in `app/src/lib/git/checkout.ts`, where the branch name is placed as a bare positional argument to `git checkout` and the `--` path-separator is appended only at the *end* of the argument list, not immediately before the branch name: [5](#0-4) [6](#0-5) . Because the branch string precedes the `--` separator, a value beginning with `-` is not guaranteed to be treated as a literal ref name by `git checkout`; it can instead be parsed by git as a command-line option.

I was not able to fully verify the exact body of `Dispatcher.checkoutLocalBranch` in `app/src/ui/dispatcher/dispatcher.ts` (only match counts were returned by the search tool, not the code itself), so I cannot confirm with certainty whether it wraps the raw string in a `Branch` object that is subsequently passed unchanged into `checkoutBranch`'s `branch.name` positional argument, or whether there is an additional validation/sanitization step in between. This is the main open question for this analog.

### Impact Explanation
If the raw, unsanitized branch string is passed straight into `git checkout <branch>` args as shown in `checkout.ts`, then a maliciously crafted "Open in Desktop" deep link (`x-github-client://openRepo/<url>?branch=-<option>`) that a user clicks could inject a git option instead of a branch name. Depending on which git checkout option is reachable this way, this is a git-argument-injection primitive triggered purely by clicking a link — matching the "unprivileged, attacker controls a link/deep link" impact class explicitly called out as valid in this task's scope, and could plausibly cause corruption of the user's working tree/checkout, unwanted file writes, or command behavior divergent from the user's intent.

### Likelihood Explanation
Medium. The `openRepo` deep-link handler is a first-class Desktop feature ("Open in Desktop" links on github.com and other sites embed this protocol), so the attack surface (attacker-controlled `branch=` parameter) is real and requires only a user click, no local access. However, exploitability depends on (a) confirming that `checkoutLocalBranch` does not otherwise re-validate/sanitize the branch string before it becomes `branch.name` in `checkout.ts`, and (b) finding a `git checkout` option reachable via the leading-dash string whose effects are actually harmful (this was not verified further due to tool limits).

### Recommendation
- Apply the same leading `-`/`+` stripping used in `sanitizedRefName` to the deep-link `branch` (and `pr`) parameters in `parseAppURL`, or reject them outright via `testForInvalidChars`-style hardening that also flags a leading dash.
- In `app/src/lib/git/checkout.ts`, always place `--` immediately before the branch/ref positional argument (not just at the end of the args array) so git will never interpret it as an option regardless of upstream validation gaps.
- Confirm and, if necessary, harden `Dispatcher.checkoutLocalBranch` to reject or sanitize branch names before using them as git command arguments.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--upload-pack%3D%2Ftmp%2Fmalicious.sh`.
2. Victim clicks the link; `parseAppURL` accepts it because `testForInvalidChars` does not flag a leading `-` [7](#0-6) .
3. `Dispatcher.openRepositoryFromUrl` routes to `openBranchNameFromUrl` and then `checkoutLocalBranch` with the raw string [4](#0-3) .
4. If unsanitized, the string reaches `checkoutBranch`'s argument list before the `--` terminator [5](#0-4) , letting git interpret it as an option rather than a ref name.

Note: step 3→4 data flow through `checkoutLocalBranch` could not be fully confirmed in this session due to search-tool truncation; this should be verified directly in `app/src/ui/dispatcher/dispatcher.ts` before treating this as a confirmed, exploitable issue.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
