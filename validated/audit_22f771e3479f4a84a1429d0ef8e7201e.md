## Analysis

The Liquity report's broken invariant is: **untrusted external data flows into a security-relevant selection/decision (price selection) without adequate provenance validation, and downstream code trusts it as if it were locally verified.** The closest structural analog in GitHub Desktop is not price data but **git remote URLs derived from a GitHub API pull-request object (or a deep-link URL) that flow unvalidated into `git remote add`/git network operations**. [1](#0-0) 

`openPullRequestFromUrl` takes the `url`/`pr` fields straight out of the `x-github-client://openRepo/...` deep link, fetches the PR object from the API, and forwards `pullRequest.head.repo.clone_url` into `_checkoutPullRequest`: [2](#0-1) 

That in turn calls `_findPullRequestBranch`, which — if no existing remote matches — adds a brand-new git remote using the API-supplied `headCloneUrl` verbatim: [3](#0-2) 

```

if (remote === undefined) {
  const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
  remote = await addRemote(repository, forkRemoteName, headCloneUrl)

```

### Title
Unvalidated `clone_url` from PR/deep-link data flows into `git remote add`, enabling remote-URL argument/scheme injection - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`headCloneUrl` originates from either (a) an `x-github-client://openRepo/...` deep link the user clicks (fully attacker-controlled string, parsed by `parseAppURL`), or (b) a GitHub/GHES API pull-request JSON object's `head.repo.clone_url` field. Neither `parseAppURL` nor `_findPullRequestBranch`/`addRemote` appears to constrain this value to a well-formed `https://`/`ssh://`/`git://` URL before it is handed to the underlying `git remote add` invocation.

### Finding Description
`parseAppURL` only validates the `branch`/`pr`/`filepath` query parameters (via `testForInvalidChars` and numeric regexes); the `url` path segment itself is passed through unchanged as the "remote repository location": [4](#0-3) 

That `url` reaches `openOrCloneRepository`/`openPullRequestFromUrl`, and for the PR-checkout path, the API's `head.repo.clone_url` — which is itself just JSON supplied by whatever endpoint the deep link or CLI action points at — is passed to `_findPullRequestBranch` and then `addRemote` with no scheme/format check: [1](#0-0) [5](#0-4) 

This is structurally identical to the audited bug's root cause: a value from an external, attacker-influenceable source ("market"/"API" data in Liquity; a PR JSON object/deep link in Desktop) is consumed by security-sensitive logic (`min()` price selection in Liquity; `git remote add` argument construction in Desktop) with an implicit — and here unconfirmed — assumption that the value is already well-formed and safe.

Git remote URLs beginning with `-` (e.g. `-oProxyCommand=...` for `ssh://`-style ambiguous URLs) are a known injection class (cf. CVE-2017-1000117), because Git can misinterpret a leading-dash "URL" as a command-line option to the transport helper it invokes. Whether this specific Desktop code path is exploitable depends entirely on whether `addRemote`'s underlying git invocation inserts a `--` argument separator (or otherwise validates the URL) before the user-controlled string — **I was not able to retrieve the body of `addRemote` in `app/src/lib/git/remote.ts` before running out of tool calls, so I cannot confirm or rule out this specific injection vector.** No `--`/allowlist/scheme-validation logic was found via grep for `ext::`, `--upload-pack`, `isValidGitRemoteUrl`, or `validateRemoteUrl` anywhere in the indexed codebase, which is suggestive but not conclusive given index coverage limits.

### Impact Explanation
If `addRemote` does not defensively separate the URL argument, an attacker who can get a victim to click a crafted `x-github-client://openRepo/...` deep link, or who controls the PR JSON returned by a (possibly proxied/MITM'd or malicious Enterprise) GitHub API endpoint, could smuggle a hostile "URL" into a `git remote add`/subsequent `git fetch` invocation, potentially achieving argument injection against the ssh/git transport and, in the worst case, command execution outside the sandboxed renderer trust boundary. This matches the requested impact class: "a GitHub API object... and the result is code execution... credential/token exfiltration... or silent corruption of what the user commits."

### Likelihood Explanation
Medium-low, and explicitly uncertain: the attacker-controlled value must reach `addRemote` (confirmed data flow), but exploitability hinges on an implementation detail of `addRemote`/`git remote.ts` that I could not verify with the tools available in this session. If Desktop already inserts a `--` separator or validates the scheme there (a common and simple mitigation Desktop is known to have applied for similar clone-URL flows elsewhere, e.g. `sanitizeCloneName` for path traversal), this reduces to a non-issue.

### Recommendation
Regardless of the current state, harden defensively at the boundary: validate that `clone_url`/deep-link `url` values match an expected `https://`, `http://`, `ssh://`, or `git://` scheme (or a `user@host:path` SCP-like form) before calling `addRemote`/`git remote add`, and ensure the git invocation always separates options from the URL argument with `--`. This should be verified directly against `app/src/lib/git/remote.ts`'s `addRemote` implementation, which I could not inspect in this session — a Devin session with full repo access should confirm whether the existing implementation already mitigates this.

### Proof of Concept
Not producible with certainty from the available evidence, since the decisive code (`addRemote` in `app/src/lib/git/remote.ts`) could not be retrieved in this session. Conceptually: an attacker crafts either (1) a link `x-github-client://openRepo/<hostile-url>?pr=1` for a victim to click, or (2) a PR response (via a malicious/compromised GHES instance) whose `head.repo.clone_url` is a hostile string beginning with `-`; when Desktop resolves the PR and no matching remote exists, it calls `addRemote(repository, forkRemoteName, headCloneUrl)` with that value un-sanitized. [6](#0-5) 

**This finding is a candidate, not a confirmed vulnerability** — its validity is contingent on `addRemote`'s exact implementation, which the current tool session could not surface. I recommend a follow-up Devin session with full file access to inspect `app/src/lib/git/remote.ts` (`addRemote`) and `app/src/lib/remote-parsing.ts` to confirm or refute exploitability before treating this as a verified issue.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {

      } catch (e) {

          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`

        )

      }
