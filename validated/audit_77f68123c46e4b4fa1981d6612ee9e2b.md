### Title
Cached-preprocess reuse lets a malicious signing peer re-trigger `sign` on identical nonces across share/complete rounds, recovering the victim's secret share - (File: coordinator/src/tributary/signing_protocol.rs; crypto/frost/src/sign.rs)

### Summary
The external report describes a state machine in which an attacker can re-enter a privileged state (`start_recovery`) before the honest party can remediate, because remediation required two separate transactions. The Serai analog is the inverse of the same structural flaw: the honest party's signing state is *non-atomically re-entered* by design. `SigningProtocol::share_internal` rebuilds the FROST `AlgorithmSignMachine` from the same `CachedPreprocesses` seed every time it is invoked for a given `context`, and both `DkgConfirmer::share` and `DkgConfirmer::complete` call it — each time with attacker-influenced `preprocesses`/`shares` maps. Because the nonce is deterministically re-derived, each re-entry signs under the *same* nonces while the binding factors, signing set, and challenge are controlled by the byte strings fed to `read_preprocess`. Two distinct invocations therefore produce two signature shares `s = d + b·e·ρ + λ·x·c` with identical `d + b·e·ρ` but different `c`/`λ`, yielding the secret share by subtraction — the classic FROST nonce-reuse (ROS-adjacent) key recovery.

### Finding Description
`preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs` only generates a fresh preprocess seed when `CachedPreprocesses::get(self.txn, &self.context)` is `None`; otherwise it decrypts and reloads the identical seed and calls `AlgorithmSignMachine::from_cache` with it (lines 123–145). `from_cache` reconstructs the machine via `seeded_preprocess`, which deterministically re-derives `nonces` and `commitments` from `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:121–144). The context for `DkgConfirmer` is `(b"DkgConfirmer", self.attempt)` — constant for all signing calls within an attempt (line 275).

`share()` calls `share_internal(preprocesses, key_pair)`, and `complete()` calls `share_internal(preprocesses, key_pair)` *again* before `complete_internal` (lines 304–327). Both calls run `machine.sign(preprocesses, msg)` on freshly reconstructed machines holding identical `nonces`. The `preprocesses` map is built from untrusted `Vec<u8>` supplied by peers and parsed via `machine.read_preprocess` (lines 160–168); which participants are included, and the exact commitment bytes per participant, determine `included`, the per-signer binding factors ρ (sign.rs:361–371) and the Lagrange coefficients/challenge. There is no check that the `preprocesses` set used in `share` is the same set used in `complete`, and nothing invalidates the cached seed after `share` runs.

A malicious peer therefore provides one preprocess set for the `share` round and a different set (different included participants, or re-ordered/modified commitment bytes for itself) for the `complete` round. Both rounds sign `set_keys_message` under the same victim nonces but with different effective challenges, producing two shares sufficient to solve for the victim's FROST secret share `x` — and, via the DLEq-bound nonce structure, the nonce itself, enabling full private-key-share recovery.

### Impact Explanation
Recovery of the victim validator's MuSig/FROST secret share (`self.key`, the tributary signing key) used for `DkgConfirmer` signatures over `set_keys_message`. Combined with threshold-many compromised peers, this enables forging validator-set confirmations and arbitrary tributary signatures; even alone it is a permanent compromise of a key the design explicitly treats as secret-material-sensitive (the preprocess seed is XOR-encrypted in the DB precisely because "recovery of it will enable recovering the private key", line 104). This is the "key share recovery" accept criterion.

### Likelihood Explanation
Reachable by any participant able to submit `preprocesses`/`shares` byte maps to the DKG-confirmation signing flow, which are parsed through `read_preprocess`/`read_share` — explicitly listed untrusted-byte entry points. The attacker only needs to vary the preprocess map between the two invocations; no control over the victim's RNG, timing races against block production, or collusion is required, and the state machine guarantees both `sign` executions occur (`complete` unconditionally re-runs `share_internal`). The window is wide because the cached seed persists across the entire attempt and across reboots.

### Recommendation
Make nonce consumption atomic with the signing decision: after `share_internal` produces a share for a given `context`, either (a) delete/rotate the `CachedPreprocesses` entry so `complete` cannot re-derive the same nonces, or (b) persist the machine (or at minimum the exact `preprocesses` map and resulting `AlgorithmSignatureMachine`) from the `share` call and have `complete` reuse that machine instead of rebuilding via `share_internal`. Rebuilding from cache must be restricted to byte-identical inputs: commit the serialized `preprocesses` map and `msg` into `context` (e.g. store their hash in `CachedPreprocesses`) and assert equality before re-signing. This mirrors the report's fix — collapsing the vulnerable two-step sequence into a single atomic operation — applied to nonce consumption.

### Proof of Concept
1. Honest validator V participates in DKG confirmation for attempt `a`; `preprocess_internal` stores seed `S` under context `(b"DkgConfirmer", a)` and V's commitments `C_V` are derived from `ChaCha20Rng::from_seed(S)`.
2. Attacker A submits preprocess set `P1` (participants `{A, V, ...}`) to V's `share` handler → V computes `s1 = d_V + b_V·e_V·ρ_V(P1) + λ_V(P1)·x_V·c1` and returns it.
3. A submits a *different* preprocess set `P2` (e.g. including an extra participant or modified commitments, so `included`/transcript differ) to V's `complete` handler → `share_internal` reloads `S`, regenerates identical `d_V, e_V`, and signs again: `s2 = d_V + b_V·e_V·ρ_V(P2) + λ_V(P2)·x_V·c2` with `c2 ≠ c1`.
4. From `s1`, `s2`, the known `ρ` factors (recomputable from the public `P1`/`P2`), and `λ` values, A solves the two-equation linear system for `x_V` (and `d_V + b_V·e_V`), recovering V's secret share. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
