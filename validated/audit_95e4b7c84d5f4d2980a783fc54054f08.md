### Title
`ThresholdKeys::read` accepts attacker-crafted key files without verifying the secret share matches the verification shares — untrusted serialized keys can silently install an attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary

`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the secret share, and `n` verification shares, then hands them to `ThresholdKeys::new`, which only validates counts, participant ranges, and interpolation applicability before computing `group_key` from the first `t` verification shares. It never checks that `secret_share` is consistent with `verification_shares[i]`, nor that the caller has any knowledge of the shares at all. Like the PraisonAI `config.toml` issue, a file the user treats as trusted configuration (a serialized `ThresholdKeys` blob on disk or in a repo) fully determines where "output" — signatures and funds under the resulting `group_key` — goes, with no integrity check.

### Finding Description

In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads all key material from the byte stream and calls `ThresholdKeys::new` [1](#0-0) . `ThresholdKeys::new` performs only structural validation — share count equals `n`, participant indexes ≤ `n`, `Constant` interpolation requires `t == n` — then derives `group_key` by interpolating `verification_shares[1..=t]` [2](#0-1) . Nothing binds `secret_share` to `verification_shares[i]` (the natural check `C::generator() * secret_share == verification_shares[i]` is absent), and nothing authenticates the file at all.

An attacker who can supply or modify the serialized keys file (an untrusted checkout, a shared artifact, a tampered config — the same trust position as the report's `.praisonai/config.toml`) writes a self-consistent `(t, n)` Shamir sharing for which they know every share, encoded via `write`/`serialize`. `read` accepts it, `group_key()` returns a key whose discrete log the attacker knows, and `view()`/`sign` proceed normally.

### Impact Explanation

If an application loads `ThresholdKeys` from a file and then receives funds to, or honors signatures from, `keys.group_key()` (e.g., a Bitcoin address derived via `tweak_keys(keys)` [3](#0-2) ), the attacker controls the group key outright: funds are sweepable and signatures forgeable. Even a partially-consistent malicious file (valid verification shares, mismatched `secret_share`) causes the honest signer to emit signature shares that fail `verify_share`, enabling a griefing/blame vector — but the primary impact is total key substitution, equivalent to the traversal primitive's "write to an unintended location" mapped onto "the group key funds/signatures are attributed to."

### Likelihood Explanation

Requires the attacker to control the bytes passed to `ThresholdKeys::read`, matching the report's precondition (a project-local file influencing behavior). Serialized key material is typically generated locally, which lowers likelihood, but the format carries no MAC, checksum, or self-consistency proof, so any channel supplying the blob (backup restore, repo, artifact store) is a viable delivery path. Medium-severity analog consistent with the source CVE's 6.0 rating.

### Recommendation

In `ThresholdKeys::new` (or at minimum `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` for `Interpolation::Lagrange`-compatible single shares, or document that the serialized form is integrity-sensitive and must be authenticated. Preferably, authenticate the whole serialized blob (MAC/signature) since `secret_share` consistency alone does not prevent substituting an entirely attacker-known key set.

### Proof of Concept

```rust
// Attacker produces a keys blob for a fully known (t=2, n=3) sharing.
let secret = Zeroizing::new(<C as Ciphersuite>::F::random(&mut rng)); // attacker-known
// Build shares f(1), f(2), f(3) of a degree-1 polynomial with f(0) = secret.
let shares: Vec<Zeroizing<C::F>> = /* known Shamir shares */;
let vshares: HashMap<Participant, C::G> = (1..=3)
    .map(|i| (Participant::new(i).unwrap(), C::generator() * shares[i - 1].deref()))
    .collect();

// Serialize exactly as ThresholdKeys::write does for i = 1.
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(2u16.to_le_bytes()); // t
blob.extend(3u16.to_le_bytes()); // n
blob.extend(1u16.to_le_bytes()); // i
blob.push(1);                    // Interpolation::Lagrange
blob.extend(shares[0].to_repr().as_ref());
for i in 1..=3u16 {
    blob.extend(vshares[&Participant::new(i).unwrap()].to_bytes().as_ref());
}

// Victim loads the attacker-supplied file.
let keys = ThresholdKeys::<C>::read(&mut blob.as_ref()).unwrap();
// keys.group_key() == G * secret, whose discrete log the attacker knows.
// Funds sent to tweak_keys(keys) / the group key's address are spendable by the attacker,
// and signatures under group_key are forgeable without the victim's participation.
```

The attack succeeds because `read` → `ThresholdKeys::new` performs only structural checks and computes `group_key` from the supplied verification shares [4](#0-3) ; no consistency or authenticity check on the deserialized material exists.

pub fn tweak_keys(keys: ThresholdKeys<Secp256k1>) -> ThresholdKeys<Secp256k1> {
  // Adds the unspendable script path per
  // https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki#cite_note-23
  let keys = {
    use k256::elliptic_curve::{
      bigint::{Encoding, U256},
      ops::Reduce,
      group::GroupEncoding,
    };
    let tweak_hash = TapTweakHash::hash(&keys.group_key().to_bytes().as_slice()[1 ..]);
    /*
      https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki#cite_ref-13-0 states how the
      bias is negligible. This reduction shouldn't ever occur, yet if it did, the script path
      would be unusable due to a check the script path hash is less than the order. That doesn't
      impact us as we don't want the script path to be usable.
    */
    keys.offset(<Secp256k1 as Ciphersuite>::F::reduce(U256::from_be_bytes(
      *tweak_hash.to_raw_hash().as_ref(),
    )))
  };
