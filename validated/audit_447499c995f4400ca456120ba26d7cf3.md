## Analysis

The Super DCA bug class — **overwriting a rate variable before applying it to the already-elapsed interval, causing the new rate to be misapplied retroactively to old, unpriced time** — has a direct structural analog in `pallet-consensus-incentives`.

### Location [1](#0-0) 

`calculate_reward` computes `blocks = latest_height - baseline` (the span of remote-chain blocks that haven't yet been paid for, tracked via `LastRewardedHeight`), then multiplies that entire un-rewarded span by whatever `block_cost` is **currently** stored in `StateMachinesCostPerBlock` at call time: [2](#0-1) 

The rate is updated in-place with no snapshot/checkpoint of the old rate against the already-accrued-but-unpaid span: [3](#0-2) 

This is the exact same defect as the Super DCA report: `mintRate = newMintRate` overwrites the rate before the pending elapsed interval is priced at the old rate. Here, `StateMachinesCostPerBlock::mutate` overwrites `block_cost` with no prior call to settle/checkpoint the reward for blocks already accrued since `LastRewardedHeight`. The next `on_executed` call — triggered by **any relayer** delivering a `ConsensusMessage` — then prices the *entire* un-rewarded block span at whatever the *current* rate is, not the rate(s) that were actually in effect while those blocks accrued.

### Title
Consensus-incentive rewards apply the current `cost_per_block` retroactively to the entire un-rewarded block span, allowing over/underpayment from the treasury - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::calculate_reward` prices the whole unpaid block span `latest_height - baseline` using the `block_cost` value read at call time from `StateMachinesCostPerBlock`, rather than the rate(s) that were in force while those blocks were actually accruing. Any rate change made via `update_cost_per_block` is retroactively applied to the backlog of un-rewarded blocks the next time a relayer delivers a `ConsensusMessage`.

### Finding Description
`process_message` → `calculate_reward` [4](#0-3)  reads:
- `baseline` = `LastRewardedHeight` (or `previous_commitment_height` on first reward),
- `latest_height` = current on-chain commitment height,
- `reward = (latest_height - baseline) * block_cost`, where `block_cost` is read fresh from storage at call time.

There is no mechanism that settles/pays out the reward owed for the backlog *before* `update_cost_per_block` changes the rate, and no per-block or per-checkpoint rate history is kept — only a single mutable `StateMachinesCostPerBlock` value. Consequently, whenever the rate is changed while there is an outstanding, un-rewarded block span (i.e., no `ConsensusMessage` has been delivered since the last reward), the entire backlog gets paid at the *new* rate rather than the rate(s) actually in effect while it accrued — mirroring the root cause in the Super DCA report where `mintRate = newMintRate` overwrote the rate before `_updateRewardIndex()` settled the old interval.

Because the payout is triggered by `FeeHandler::on_executed`, which fires for **every** delivered `ConsensusMessage` from **any relayer** [5](#0-4) , an ordinary (unprivileged) relayer controls the timing of when the backlog gets settled — they can simply hold back submitting a consensus proof they already have until after they observe (or anticipate) a rate increase, then submit it and collect the inflated reward for blocks that accrued under the old, lower rate. No collusion with governance, no malicious prover, and no compromised relayer assumption is required — governance performing an ordinary, well-intentioned rate update is sufficient to create the exploitable backlog window; the attacker only needs to control submission timing of a message they are already entitled to submit.

### Impact Explanation
Funds move from `TreasuryAccount` to a relayer at the wrong amount: [6](#0-5) 
This is a direct case of "reward claims ... must move exactly once and only to the rightful beneficiary and amount" being violated — the treasury pays out based on a rate that never applied to the blocks being rewarded, resulting in overpayment (treasury drain) if the rate increases, or underpayment (relayer shortchanged) if the rate decreases. Because the watermark (`LastRewardedHeight`) only prevents double-payment of the *same* height span, not mispricing of that span, this is a real fund-movement bug, not merely a griefing/DoS issue.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: rate updates via `update_cost_per_block` are a normal, expected operational action (not a rare governance emergency), and any relayer that already has a valid consensus proof in hand can trivially choose *when* to submit it relative to a known or anticipated rate change. No special privileges, front-running, or malicious infrastructure roles are needed — only control over submission timing, which every relayer inherently has.

### Recommendation
Before `update_cost_per_block` mutates `StateMachinesCostPerBlock`, force settlement of the outstanding backlog at the *old* rate (analogous to calling `_updateRewardIndex()` before `mintRate = newMintRate` in the referenced fix): e.g., iterate/pay out (or checkpoint) the currently-accrued-but-unrewarded span for the affected `state_machine_id` using the rate about to be replaced, advance `LastRewardedHeight` to the current `latest_height`, and only then store the new `cost_per_block`. Alternatively, maintain a rate history keyed by height/timestamp so `calculate_reward` can integrate the correct rate over each sub-interval of the backlog instead of applying a single current rate to the whole span.

### Proof of Concept
1. Governance sets `cost_per_block(state_machine_id) = 10` via `update_cost_per_block`. [3](#0-2) 
2. Remote chain progresses 1,000 blocks (`latest_height` advances by 1,000 relative to `LastRewardedHeight`/baseline), but no relayer submits a `ConsensusMessage` for this state machine during that window — the accrued-but-unrewarded backlog builds up.
3. Governance later increases the rate: `update_cost_per_block(state_machine_id, 1000)`.
4. A relayer (who has been holding a valid, already-verifiable consensus proof, or simply delivers the message now) submits a `ConsensusMessage`. `on_executed` → `process_message` → `calculate_reward` computes `blocks = 1000`, `block_cost = 1000` (the new rate), `reward = 1,000,000` — instead of the `10,000` that should have been paid had the backlog been settled at the old rate of `10` per block. [2](#0-1) 
5. `TreasuryAccount` transfers `1,000,000` to the relayer, and `ReputationAsset::mint_into` mints the same inflated amount as reputation. [7](#0-6)

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
