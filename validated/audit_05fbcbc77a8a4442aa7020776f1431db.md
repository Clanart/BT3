### Title
TextFormat `PrintAny` embeds attacker-controlled `type_url` unescaped into structural bracket syntax, enabling TextFormat output corruption/injection - (File: `src/google/protobuf/text_format.cc`, `java/core/src/main/java/com/google/protobuf/TextFormat.java`)

### Summary
The Netty CVE's root cause is that an attacker-controlled string (filename) is concatenated directly into a structural delimiter context (`Content-Disposition` header, itself delimited by CRLF) without checking for characters that have special meaning in that context (`\r`, `\n`, `"`). The Protobuf analog is `TextFormat::Printer::PrintAny` (C++) and `TextFormat.Printer.printAny` (Java), which print the `Any.type_url` field literally inside the `[...]` bracket syntax used to denote an expanded `Any` message, without validating or escaping the string, even though `type_url` is an ordinary attacker-controlled string field populated by parsing untrusted binary/JSON input.

### Finding Description
`google.protobuf.Any.type_url` is a plain `string` field (wire type length-delimited, field 1). Nothing in the binary or ProtoJSON parser enforces the comment-only restriction in `any.proto` that the type URL "must consist only of alphanumeric characters, percent-encoded escapes, and characters in [/-.~_!$&()*+,;=]". `internal::GetAnyFieldDescriptors` only checks that field 1 is a `string` and field 2 is `bytes`: [1](#0-0) 

Consequently, any bytes that are valid UTF-8 (or even arbitrary bytes, depending on the language binding) can end up in `type_url` after an ordinary `ParseFromString`/`MergeFrom` on a bounded, well-formed message.

When such a message is later rendered with `TextFormat::PrintToString` / `DebugString` / `Printer::PrintAny`, the code prints the raw `type_url` between `[` and `]` with no escaping function applied (contrast with `PrintFieldValue`'s `STRING` case, which always calls `HardenedPrintString`/`FastFieldValuePrinter::PrintString`, doing `CEscape`): [2](#0-1) 

The Java implementation does the same thing — it prints `typeUrl` straight into the generator with no call to `TextFormatEscaper`/`escapeText`: [3](#0-2) 

Compare this to the normal STRING field-printing path, which *always* escapes quotes, backslashes and control characters before emitting the value inside `"..."`: [4](#0-3) [5](#0-4) 

The invariant that fails: TextFormat's syntax uses structural delimiters (`[`, `]`, `{`, `}`, newlines, and `"..."` quoting for scalar strings) to separate a field name/extension marker from its value. Every value-printing code path escapes control/structural characters before emission — except the "expand Any" bracket path, which is the *only* place a raw attacker-controlled string is spliced into the output stream without quoting or escaping. If `type_url` contains `]`, `\n`, `{`, or another `[...]` sequence, the printed TextFormat output no longer round-trips to the original message and can be made to look like arbitrary additional fields/extension markers, or to prematurely terminate/reopen the Any-value block — analogous to how Netty's unescaped filename let an attacker break out of the `Content-Disposition` header value and inject a new MIME header/body section.

### Impact Explanation
Impact is confined to **integrity of TextFormat output**, not confidentiality/availability of the process itself (no crash, no memory corruption is claimed here). Concretely:
- Logging/debugging tools, audit logs, or any downstream system that captures `DebugString()`/`TextFormat.printToString()` output and re-parses or greps it can be fed a corrupted rendering: the attacker can inject characters that make the printed text look like it contains additional (fake) fields, or break the bracket nesting so log-scraping/parsing tools misattribute data — the same "structural desync" class as MIME header/CRLF injection, just against the TextFormat grammar rather than MIME/HTTP.
- Because `HardenedPrintString`/`FastFieldValuePrinter::PrintString` exist specifically to prevent exactly this kind of raw string emission for STRING fields, but are bypassed for the Any type-url bracket, this is a genuine "missed escaping" gap rather than an intended design choice — the intended output grammar assumes `[...]` contains only well-formed type-url text, which is not actually enforced.
- This does **not** enable RCE, buffer overflow, or resource exhaustion, and there is no equivalent to Netty's "downstream Content-Type override enabling stored XSS" unless a consuming application specifically trusts and re-parses `DebugString()` output as another format (uncommon), which limits severity below the original Medium-CVSS Netty case whose value is directly re-served as HTTP content.

### Likelihood Explanation
High likelihood of reachability: any application that (a) accepts untrusted binary/ProtoJSON input containing an `Any` message, (b) later logs or debug-prints that message via `TextFormat`/`DebugString`, exercises this path deterministically. No privileged access or malicious schema is needed — `type_url` is a normal string field populated through the standard public `ParseFrom*` API. The character-set restriction on `type_url` documented in `any.proto` is comment-only and not enforced by the parser: [6](#0-5) 

### Recommendation
- In `TextFormat::Printer::PrintAny` (C++) and `TextFormat.Printer.printAny` (Java), escape/validate `type_url` before emitting it inside `[...]` — e.g., reuse `HardenedPrintString`/`TextFormatEscaper.escapeText` logic (stripped of the surrounding quotes) or explicitly reject/escape control characters (`\n`, `\r`) and the delimiter characters `[`/`]` that are meaningful to the TextFormat grammar, falling back to the non-expanded `type_url: "..."` form (already properly escaped) when the URL contains illegal characters.
- Apply the same fix to the equivalent Python/Ruby/PHP/C# `PrintAny`-style helpers referenced by `_TryPrintAsAnyMessage` in `python/google/protobuf/text_format.py`, since it interpolates `message.type_url` directly: [7](#0-6) 

### Proof of Concept
Conceptual reproduction outline (a background Devin session would be needed to actually compile/run this against the checkout; not executed here):
1. Build an `Any` message where `type_url = "type.googleapis.com/foo.Bar]\nfake_field: 1  # "` and `value` is a valid serialization of `foo.Bar{}`.
2. Serialize this `Any` as a field of a normal wrapping message using `SerializeToString()` (bounded, well-formed binary — no malformed wire data required).
3. Parse it back with `ParseFromString()` on the wrapping message (ordinary public parse API) — parsing succeeds because `type_url` has no character restrictions.
4. Call `TextFormat::PrintToString(message)` (C++) or `TextFormat.printer().printToString(message)` (Java) with a `TypeRegistry`/`Finder` that resolves `foo.Bar`.
5. Observe that the rendered TextFormat output contains the injected `]` and `fake_field: 1` as if they were legitimate structural tokens, rather than the literal (would-be-escaped) type URL string — demonstrating the same "attacker breaks out of the delimiter context" primitive as the Netty CRLF injection, translated to the TextFormat grammar.

This could not be executed in this environment (no code execution / build access here); a Devin session with the checkout should be used to run the actual repro and confirm the exact escaped/unescaped rendering difference.
