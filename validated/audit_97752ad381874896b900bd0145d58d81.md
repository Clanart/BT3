### Title
Working-directory diff for staged renamed files hides already-staged content changes from the commit review UI - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryDiff()` normally diffs a changed file against `HEAD` so the Changes view shows exactly what will end up in the next commit. For files whose status is `AppFileStatusKind.Renamed`, the function deliberately diffs the file against the index instead of `HEAD`, and the code even documents that this is wrong: [1](#0-0)  The result is a "stale baseline" bug analogous to the RToken report: instead of a stale liquidity index causing unscaled transfers, Desktop uses a stale diff baseline (index instead of HEAD) causing an unscaled/incomplete diff to be shown to the user right before they commit.

### Finding Description
`AppFileStatusKind.Renamed` (and `Copied`) entries carry a `renameIncludesModifications` flag, meaning the index already differs from `HEAD` in both path and content [2](#0-1) . This state is not exotic — it is exactly what `git` produces when a merge, rebase, or cherry-pick auto-detects a rename and merges content without any conflict markers.

When Desktop builds the diff to show in the Changes tab for such a file, it takes this branch:

```
} else if (file.status.kind === AppFileStatusKind.Renamed) {
  // NB: Technically this is incorrect, the best kind of incorrect.
  // In order to show exactly what will end up in the commit we should
  // perform a diff between the new file and the old file as it appears
  // in HEAD. By diffing against the index we won't show any changes
  // already staged to the renamed file which differs from our other diffs.
  args.push('--', ensureRelativePath(file.path))
}
``` [3](#0-2) 

Because no `HEAD` argument is passed, `git diff -- <path>` compares the **working tree to the index**, not the index to `HEAD`. Any content that is already staged (i.e., that differs from `HEAD` and *will* be committed) is completely absent from the rendered diff. If the working tree matches the index exactly (the common case right after an auto-merged rename), the diff is empty, and the Changes view shows "no changes" for a file that in fact carries a full content rewrite relative to `HEAD`.

This directly parallels the reported bug class: a value/reference that is supposed to represent "what will actually be applied" (liquidity index / commit baseline) is not kept in sync with the authoritative source (normalized income / `HEAD`), so a downstream scaling/diff operation silently produces an incorrect (here: empty) result instead of reflecting reality.

### Impact Explanation
This fits the "silent corruption of what the user commits or pushes" impact category. An attacker who controls a branch, PR, or repository that the victim fetches and merges can craft history so that a benign-looking rename auto-resolves during merge with attacker-controlled content differences from `HEAD` (a common, conflict-free git outcome for renamed+modified files). When the victim reviews the merge/changes in Desktop before committing (e.g., finalizing a merge commit or making an additional small commit while the rename sits staged), the file shows **no diff** for its actual content change, even though that content will be included verbatim in the next commit and subsequently pushed to remotes/PRs the victim controls. The user is misled into believing the file is an unmodified rename, defeating the entire purpose of the pre-commit diff review and enabling stealthy injection of attacker content into the victim's commit/push history.

### Likelihood Explanation
The precondition — a `Renamed` status entry with `renameIncludesModifications: true` and index content equal to working tree — arises from ordinary git operations (merge/rebase/cherry-pick auto-rename-detection) that a remote/attacker-controlled branch can be crafted to trigger deterministically. No local/admin access, malware, or unnatural user steps are required beyond the victim performing a normal merge/pull and then committing, which is standard Desktop usage. The code comment itself acknowledges the discrepancy is real and intentional, indicating no existing guard mitigates it.

### Recommendation
For `AppFileStatusKind.Renamed`/`Copied` files, diff the working tree against `HEAD` (with rename detection, e.g. via `git diff -M HEAD -- <path>`) rather than against the index, so the UI always reflects exactly what will be committed, consistent with the function's own doc comment: "Render the diff for a file... The file will be compared against HEAD" [4](#0-3) . If a full `HEAD`-relative diff is infeasible for performance reasons, at minimum surface a warning in the UI when `renameIncludesModifications` is true and the rendered diff is empty, so users aren't shown an inaccurate "no changes" state for content that will be committed.

### Proof of Concept
1. Attacker prepares a branch `evil` where a file `notes.txt` is renamed to `report.txt` with additional attacker-controlled lines, structured so that merging it into `main` triggers git's rename detection and auto-merges without conflicts (e.g., no overlapping hunks with the victim's local edits).
2. Victim, using Desktop, fetches and merges `evil` into `main` (`git merge evil` succeeds cleanly; `report.txt` is staged in the index as `Renamed` from `notes.txt` with modified content relative to `HEAD`).
3. Victim opens the Changes tab in Desktop to review before finalizing the merge commit. Desktop calls `getWorkingDirectoryDiff()` for `report.txt`; because `file.status.kind === AppFileStatusKind.Renamed`, it runs `git diff -- report.txt` (working tree vs. index) via [3](#0-2) , not `git diff HEAD -- report.txt`.
4. Since the working tree equals the index, this diff is empty — Desktop shows no content diff for `report.txt`, even though it differs substantially from the pre-merge `HEAD` version.
5. Victim commits, believing `report.txt` is an unmodified rename; the attacker's injected content is silently included in the commit and can be pushed upstream without ever having been visible in the reviewed diff.
