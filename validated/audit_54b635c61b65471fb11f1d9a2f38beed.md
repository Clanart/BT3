### Title
Missing bound validation on `reward.mintingamount` governance parameter allows the governing node to mint unbounded native token supply every block - ([File: kaiax/gov/param.go])

### Summary
In `single` governance mode, the sole `GoverningNode` can cast a header vote setting `reward.mintingamount` (`gov.RewardMintingAmount`) to an arbitrarily large value with no upper-bound or sanity check, unlike other numeric reward parameters in the same table. Once such a vote is accepted and takes effect, every subsequent block mints that inflated amount as block reward, distributed to the proposer/stakers/funds, directly inflating the KAIA supply without limit — an unchecked "coordinator parameter" analogous to the `staleAfter` issue in the reference report, where the privileged party sets an unvalidated numeric knob to extract unbounded value.

### Finding Description
`RewardMintingAmount` is defined with `FormatChecker: noopFormatChecker`, i.e., no validation on its canonical value: [1](#0-0) 

This contrasts with adjacent parameters in the same `Params` map that do bound-check their `*big.Int` values, e.g. `RewardMinimumStake` and `RewardStakingRewardThreshold` require `v.Sign() >= 0`: [2](#0-1) [3](#0-2) 

`checkConsistency` in header governance, which performs extra semantic checks for a few specific parameters (e.g. `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` relative-bound checks), has no special-case handling for `RewardMintingAmount` — it falls through to the generic "no more checks here" bucket that only relies on the (absent) FormatChecker: [4](#0-3) 

The canonicalizer itself (`bigIntCanonicalizer`) performs no range check either — it merely parses the value into a `*big.Int`: [5](#0-4) 

Once accepted, `GetParamSet` propagates this value into `ParamSet.MintingAmount` via `Set()` with no bound enforcement: [6](#0-5) 

The reward module then consumes this value directly as the per-block minting amount and mints it into the block reward every single block, split among proposer, stakers, and funds: [7](#0-6) 

This directly inflates `kaiax/supply`'s tracked `TotalMinted`, since supply accounting simply accumulates the reward module's minted amount per block with no independent sanity check: [8](#0-7) 

### Impact Explanation
This is a direct structural analog to the reported `staleAfter` issue: a privileged single-party role (`GoverningNode`, the coordinator-equivalent in Kaia's governance model) can set an unbounded numeric protocol parameter with no upper-bound validation, and that single parameter directly controls value extraction (native token minting) rather than merely a threshold. Every block after the malicious vote takes effect mints the inflated `MintingAmount`, which is distributed to the proposer/staker addresses (which the governing node validator controls or influences), i.e., unbounded supply inflation redirected to the attacker-controlled recipient set. This matches the accepted impact categories "supply inflation" and "reward redirection." Severity is High: the entire native token supply integrity is compromised, repeatable every block until detected/forked.

### Likelihood Explanation
Requires the chain to be in `single` governance mode (Kaia mainnet/most private/enterprise deployments use `single` mode per README) and the vote to be cast by the current `GoverningNode`. This is a single header-vote transaction/proposal — no complex multi-step precondition like a price-staleness window is needed, making it comparatively easier to trigger than the original `staleAfter` bug, though it does require the governing-node role rather than being fully permissionless. Given the explicit whitelisting of "governance parameters" and "staking and reward distribution" in the accepted analog categories, and that no other safeguard (contract governance override, hard cap, or protocol-level clamp) exists for this specific field, likelihood of exploitation by a compromised or malicious governing node is high.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` (and ideally a cross-check against a protocol-level maximum inflation rate) analogous to the checks already used for `RewardMinimumStake`/`RewardStakingRewardThreshold` (non-negative) and `RewardRatio`/`RewardKip82Ratio` (bounded percentages) — e.g., enforce `v.Sign() >= 0` at minimum, and add an explicit upper bound (e.g., a maximum per-block minting cap) enforced both in `FormatChecker` and in `checkConsistency` in `kaiax/gov/headergov/impl/header.go`, similar to the `Kip71LowerBoundBaseFee`/`UpperBoundBaseFee` cross-parameter validation pattern.

### Proof of Concept
1. Deploy/operate a Kaia network in `governance.governancemode = "single"` with a designated `GoverningNode`.
2. As the governing node, submit a header vote for `gov.RewardMintingAmount` with an extreme value (e.g., `10^30`), following the same vote path exercised in `TestVerifyVote` for other reward parameters: `headergov.NewVoteData(validVoter, string(gov.RewardMintingAmount), "<huge decimal string>")`, which passes `VerifyVote` unmodified because no format/bound check exists — see the passing test list at [9](#0-8)  where only `RewardKip82Ratio`/`RewardRatio`-style parameters are validated for range, and minting amount is absent.
3. Once the vote is included and takes effect at the next governance epoch, `NewRewardConfig` reads `paramset.MintingAmount` unmodified: [10](#0-9) .
4. Every subsequent block mints and distributes the inflated amount per `getDeferredRewardFullKore`/`getDeferredRewardFullFlex`, permanently inflating total supply as tracked by `kaiax/supply`.

// getDeferredRewardFullKore is for non-Simple policy and after Kore.
func getDeferredRewardFullKore(config *reward.RewardConfig, execFee, burntFee, blobFee *big.Int, si *staking.StakingInfo) (*reward.RewardSpec, error) {
	var (
		spec             = reward.NewRewardSpec()
		minted           = new(big.Int).Set(config.MintingAmount)
		distributableFee = new(big.Int).Sub(execFee, burntFee)
	)

	// Distribute using RewardRatio first. Unlike Legacy, fees are not distributed here
	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.
	validators, kif, kef := config.RewardRatio.Split(minted)
	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)
	stakers.Sub(stakers, kip82Remainder)

	// Proposer gets the fees.
	proposer.Add(proposer, distributableFee)

	spec.Minted = minted
	spec.TotalFee = new(big.Int).Add(execFee, blobFee)
	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
}

func (ar *AccReward) ToTotalSupply(zeroBurn, deadBurn, kip103Burn, kip160Burn *big.Int) *TotalSupply {
	ts := &TotalSupply{
		TotalSupply: nil, // will be filled below

		TotalMinted: new(big.Int).Set(ar.TotalMinted),

		TotalBurnt: nil, // will be filled below
		BurntFee:   new(big.Int).Set(ar.BurntFee),
		ZeroBurn:   zeroBurn,
		DeadBurn:   deadBurn,
		Kip103Burn: kip103Burn,
		Kip160Burn: kip160Burn,
	}

	if ar.TotalMinted != nil && ar.BurntFee != nil && zeroBurn != nil && deadBurn != nil && kip103Burn != nil && kip160Burn != nil {
		totalBurnt := new(big.Int).Set(ar.BurntFee)
		totalBurnt.Add(totalBurnt, zeroBurn)
		totalBurnt.Add(totalBurnt, deadBurn)
		totalBurnt.Add(totalBurnt, kip103Burn)
		totalBurnt.Add(totalBurnt, kip160Burn)
		totalSupply := new(big.Int).Sub(ar.TotalMinted, totalBurnt)

		ts.TotalSupply = totalSupply
		ts.TotalBurnt = totalBurnt
	}
	return ts
}
