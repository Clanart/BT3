## Title
Command Injection via Unescaped Repository Path in "Open in Shell" (Windows) - (File: `app/src/lib/shells/win32.ts`)

## Summary
The report's broken invariant is: an attacker-controlled string (a SQL alias) is spliced verbatim into a query/command string that is later parsed by an interpreter that treats a special character (`"`) as a delimiter, and no code path escapes or rejects that character before use. The same broken invariant exists in GitHub Desktop's Windows "Open in Shell" feature: a repository folder name derived from an attacker-controlled clone URL is interpolated, unescaped, into a double-quoted argument of a command that Node spawns with `shell: true` (i.e., through `cmd.exe`). A folder name containing a `"` breaks out of the quoted argument, and any following `cmd.exe` metacharacters (`&`, `|`) are then executed as separate commands.

## Finding Description
When a user clones a non-GitHub ("generic") repository, the destination folder name is derived from the URL by `parseRemote`/`parseRepositoryIdentifier` and then `sanitizeCloneName`: [1](#0-0) 

`sanitizeCloneName` only strips path separators (`/`, `\`, `:`) and rejects traversal (`..`, `.`); it does **not** strip or reject quote characters (`"`) or `cmd.exe` metacharacters (`&`, `|`, `^`, `%`): [2](#0-1) 

This sanitized (but not shell-escaped) name is joined into the local clone path in the Clone dialog: [3](#0-2) 

Note the comment in the sibling "create repository" path explicitly acknowledges that `"` must be stripped on Windows for filesystem safety, but that sanitizer (`safeDirectoryName`) is a *different* function used only by `repository-path.tsx`, not by the clone flow: [4](#0-3) 

Once cloned, `repository.path` becomes the working directory name (`Repository.name` = `Path.basename(path)`): [5](#0-4) 

When the user invokes "Open in Shell" (a normal, expected post-clone action), the path flows unchanged through the dispatcher and store to the shell launcher: [6](#0-5) [7](#0-6) [8](#0-7) 

On Windows, `launch()` interpolates `path` directly into double-quoted strings that are passed to `spawn(..., { shell: true })`, which Node executes via `cmd.exe /d /s /c`: [9](#0-8) [10](#0-9) [11](#0-10) 

None of `parseRemote`'s capture groups (`[^/]+?`) exclude `"`, so a URL such as `https://example.com/owner/foo" & calc.exe & ".git` yields a `name` of `foo" & calc.exe & "`, which survives `sanitizeCloneName` unchanged (it contains no `/`, `\`, or `:`) and becomes the literal folder name on disk. Existing guards do not stop this: `sanitizeCloneName` only defends against path traversal, and `safeDirectoryName` (the one function that does strip `"`) is never called in the clone flow.

## Impact Explanation
An attacker who controls a git remote URL — shared as a link, a README instruction, or via GitHub Desktop's own `x-github-client://` clone deep link — can cause arbitrary command execution on the victim's machine the moment they use "Open in Shell" (GitBash, Cygwin, PowerShell Core, Warp, Alacritty cases) on a cloned repository whose folder name contains the crafted payload. This satisfies the required impact class: attacker controls a git remote/clone target, and the result is code execution outside any git sandbox, entirely via a natural Desktop workflow (clone → open in shell).

## Likelihood Explanation
"Clone repository via URL" is a first-class, prominently documented Desktop feature and "Open in Shell" is one of the most common post-clone actions, reachable from the Repository menu and the repository list context menu. No local access, admin rights, or prior compromise is required — only that the victim clones a URL the attacker controls (or is directed to) and later opens a shell for it, both of which are ordinary, expected user actions.

## Recommendation
Apply the same character-stripping/escaping used by `safeDirectoryName` (or stronger) to `sanitizeCloneName`, rejecting/removing `"` and other `cmd.exe`/shell metacharacters (`&`, `|`, `^`, `%`) regardless of platform. Additionally, `win32.ts`'s `launch()` should never interpolate untrusted paths directly into a `shell: true` command line; it should use `spawn(cmd, args)` without `shell: true`, or properly escape arguments using the existing `shell-escape.ts` quoting helpers (`cmd`/`powershell` quote functions) before embedding them in a shell-executed string.

## Proof of Concept
1. Attacker hosts (or has Desktop clone) a URL such as `https://example.com/owner/repo" & calc.exe & ".git` (or an equivalent crafted URL/deep link `x-github-client://openRepo?url=...` that resolves to that string).
2. Victim clones it via Desktop's "Clone repository" → "URL" tab; Desktop derives the local folder name via `parseRepositoryIdentifier` + `sanitizeCloneName`, producing `repo" & calc.exe & "` as the clone folder name (verifiable via the logic in `app/src/lib/remote-parsing.ts:88-116`).
3. Victim selects the repository in Desktop and chooses "Open in Git Bash" (or PowerShell Core/Warp/Alacritty) from the Repository menu.
4. `win32.ts`'s `launch()` builds `spawn(gitBashPath, ['--cd="' + path + '"'], { shell: true })`; because `path` contains an embedded `"`, the resulting `cmd.exe` command line closes the quoted argument early and executes the trailing `& calc.exe & "` as a separate command, achieving arbitrary code execution.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

// We use this instead of sanitizedRepositoryName because it deals with
// valid repository names on GitHub.com but here we only care about whether
// we'll be able to create a directory with the given name. If a user
// creates a repository with a name that GitHub.com doesn't like here it'll
// get sanitized in the Publish dialog later on.
//
// Note that we don't sanitize `\` or `/` here since we use `Path.join` to
// create the full path and that will handle those characters appropriately
// letting users type something like OrgA\RepoB and have the new repo be
// created in the OrgA folder.
//
// macOS and Linux are way more allowing so there's no need to sanitize
const safeDirectoryName = (name: string) => {
  return __WIN32__ ? name.replace(/[<>:"|?*]/g, '-').replace(/\s+$/, '') : name
}
