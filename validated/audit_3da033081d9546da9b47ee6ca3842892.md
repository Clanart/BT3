### Title
Blacklist-triggered permanent fund lock in `IntentGatewayV2.withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in `IntentGatewayV2.sol` unconditionally pushes escrowed order tokens (and the accumulated tx fee) to a single `beneficiary` in a loop, reverting the entire call if any one transfer fails. [1](#0-0)  This mirrors the `RngRelayAuction.rngComplete()` pattern: a push-based payout to an externally influenced recipient address, where a blacklist-capable token (e.g. USDC) or a maliciously crafted token contract can be used to permanently DoS the payout, locking escrowed funds instead of just failing gracefully.

### Finding Description
`withdraw()` is invoked from two paths:
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests arriving cross-chain, which decodes a `WithdrawalRequest{commitment, tokens, beneficiary}` from untrusted request bodies (only authenticated to originate from a known `IntentGateway` instance, not validated for the beneficiary/token values themselves). [2](#0-1) 
- `onGetResponse()` for GET-based refund flows. [3](#0-2) 

Inside `withdraw()`, for each token in `body.tokens`, funds are pushed to `beneficiary` via a low-level `.call`, and if the call fails the whole function reverts with `TransferFailed`:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
``` [4](#0-3) 

After looping all `tokens`, the accumulated `TRANSACTION_FEES` are also pushed to the same `beneficiary` in the same atomic call. [5](#0-4)  Because a single order can escrow multiple distinct tokens for one beneficiary, a blacklist on **any one** of those tokens (e.g. USDC) — or a deliberately malicious token contract used as one of the order's input tokens — causes the ERC-20 `transfer` call to revert, which propagates up and reverts the entire `withdraw()` call, blocking redemption of **all** other (non-blacklisted) tokens and the fee payout for that commitment as well.

`_filled[body.commitment] = beneficiary` is set at the top of the function before any transfer, so on revert that state change is rolled back too — the order remains permanently redeemable-looking but every retry hits the same blacklist condition, since nothing in the code offers an alternate claim path (no `claimable` mapping/pull-based withdrawal exists, unlike the report's recommended mitigation). [6](#0-5) 

### Impact Explanation
This is a genuine fund-lock/loss vector on bridge custody (escrowed intent tokens): the order creator picks the input token(s) escrowed on the source chain when creating an order, while the beneficiary of `RedeemEscrow` is the filler who already delivered the requested output on the destination chain in good faith. If any escrowed input token is (or later becomes) blacklist-capable and the filler's beneficiary address gets blacklisted, or the order includes a token intentionally crafted to always revert transfers to specific addresses, the filler can never redeem the escrowed reward for a fill they already honored — a direct loss of funds locked in the `IntentGatewayV2` contract with no pull-based recovery mechanism.

### Likelihood Explanation
Order creation allows arbitrary caller-specified input tokens (the exact validation logic lives in `IntrinsicIntents.sol`, which time constraints prevented me from fully tracing in this session — this should be verified before treating the finding as fully proven). Assuming tokens aren't restricted to a vetted allowlist, any unprivileged actor can construct an order using USDC (or a custom malicious token) as an input, making this reachable without any privileged, relayer, or prover assumptions — matching the bounty's "unprivileged attacker" bar.

### Recommendation
Adopt the same mitigation the original report recommends: replace the push-transfer loop in `withdraw()` with a pull-based `claimable[token][beneficiary] += amount` accounting update, and add a separate `claim()` entry point so a single frozen/blacklisted token cannot block settlement of the other tokens or the fee in the same order, and cannot permanently strand funds that would otherwise be recoverable.

### Proof of Concept
1. Attacker (order creator) opens an order via `IntentGatewayV2` on chain A, escrowing two input tokens: a normal token `X` and `USDC`.
2. A filler fills the order on chain B, delivering the requested outputs to the order's `user`.
3. The filler submits proof of fill; `onAccept` decodes `RedeemEscrow` and calls `withdraw(body, false)` with `beneficiary = filler`. [2](#0-1) 
4. If the filler's address is on USDC's blacklist (or the attacker deployed a bespoke malicious "input token" whose `transfer()` always reverts for the filler's address), the `token.call(...)` for that token returns `success = false`, and `withdraw()` reverts with `TransferFailed`. [7](#0-6) 
5. The revert unwinds the entire transaction, including the release of token `X` and the transaction fee, both of which the filler was legitimately owed — the filler has delivered value on chain B but can never redeem the corresponding escrow on chain A through this function.

Note: I was not able to fully trace `IntrinsicIntents.sol`'s order-creation validation (token allowlisting, if any) before the tool budget ran out; this should be confirmed to fully establish attacker-controlled token selection as the entry vector.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
