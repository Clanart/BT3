### Title
Symlink swap between `resolveWithin` validation and file read/write allows escape of the repository sandbox in Copilot conflict resolution - ([File: app/src/lib/path.ts])

### Summary
`resolveWithin` (and its callers `buildConflictContext` and `_applyCopilotConflictResolutions`) validate a repository-relative path by calling `fs.realpath` on the resolved path and checking that the real path starts with the real root, then return the (pre-realpath) `resolved` path string for later use. The actual file I/O (`stat`/`readFile` in `copilot-conflict-context.ts`, and `writeFile` in `app-store.ts`) happens in a *separate* step, after the check has already passed. Between the `realpath` check and the actual `readFile`/`writeFile` call, nothing re-verifies that the path still points inside the repository. This is structurally the same "check now, act later" gap the external report flags for `deauthorizeAccount`/`hasTransactions` — the guard is evaluated once, and the guarded resource is mutated afterward, defeating the guard.

### Finding Description
`resolveWithin` in [1](#0-0)  resolves a candidate path, `realpath`s both the root and the resolved candidate, and returns the pre-realpath `resolved` string if the real path is contained within the real root — it does not return a file descriptor or otherwise pin the resource.

This is consumed in two places that matter:

1. `buildConflictContext` in `copilot-conflict-context.ts` calls `resolveWithin`, then later `stat` and `readFile` on the *same path string* in separate awaited calls: [2](#0-1) 
2. `_applyCopilotConflictResolutions` in `app-store.ts` calls `resolveWithin(repository.path, resolution.path)` and then, after further async work (looking up `onDiskFile`, awaiting nothing else problematic), calls `writeFile(absolutePath, ...)` on the same string: [3](#0-2) 

Because a working directory inside a cloned/fetched repository can legitimately contain a regular file at the conflicted path at the moment `resolveWithin` is checked, and because Desktop performs numerous background filesystem operations during merge/rebase/cherry-pick flows (status refresh, `git checkout-index`, submodule updates, LFS filters, hooks) concurrently with the user driving the Copilot conflict UI, an attacker who controls the repository content (e.g., a crafted merge commit, a pre-commit/post-checkout hook, or a submodule) can arrange for the path to be replaced by a symlink pointing outside the repository between the `resolveWithin` check and the subsequent `readFile`/`writeFile`. The check only inspects the state of the filesystem at check-time; the write path never re-checks that `absolutePath` is still not a symlink pointing outside the root when it performs the actual I/O.

### Impact Explanation
- In `buildConflictContext`, a successful race allows the attacker-controlled repository to have Desktop read arbitrary files outside the repository (e.g., SSH keys, `.netrc`, Desktop's own credential store) and send their contents to the Copilot backend as "conflict context," resulting in read-outside-repo and potential credential exfiltration through the Copilot session/network path.
- In `_applyCopilotConflictResolutions`, a successful race allows Desktop to write Copilot's resolved content to an arbitrary path outside the repository chosen by the attacker (e.g., overwriting a startup script, shell profile, or Desktop config), resulting in file write outside the repo / potential code execution when that path is later executed.
- Both outcomes match the "Valid Impact" criteria: the attacker controls a cloned/fetched repository, and the result is file read/write outside the repository boundary — no local/physical access, admin rights, or pre-existing malware is required beyond the attacker's ability to shape the repository content the victim clones/merges.

### Likelihood Explanation
Exploitation requires winning a race between the `resolveWithin` check and the subsequent `stat`/`readFile`/`writeFile`, which is a narrow window but a classic TOCTOU pattern. It can be widened by the attacker: git hooks (`post-checkout`, `post-merge`), submodule initialization, or LFS smudge filters triggered by Desktop during the same merge/rebase flow could be used to swap the file for a symlink at a controlled moment, similar to how the front-running shareholder in the report reliably wins the race by triggering the state change themselves rather than relying on pure timing luck. This raises likelihood from "theoretical TOCTOU" to "attacker-triggerable via git-native hooks the repository itself can define."

### Recommendation
- Short term: after `resolveWithin` succeeds, re-validate immediately before use, or better, avoid the check-then-open pattern entirely: open the file with `O_NOFOLLOW`-equivalent semantics (Node's `fs.open`/`fs.realpath` combined with `fs.lstat` on the final path component to reject symlinks) and perform `stat`/`read`/`write` on the resulting file descriptor rather than re-resolving the path string. On Windows where `O_NOFOLLOW` isn't available, at minimum re-run `realpath` immediately before the `readFile`/`writeFile` call and abort if it no longer matches.
- Long term: audit all call sites that use `resolveWithin` followed by a later `fs` operation on the returned path string (`copilot-conflict-context.ts`, `app-store.ts`'s `_applyCopilotConflictResolutions`, and any future consumers) to ensure the validation and the I/O happen atomically, or that hook/filter execution is disabled during any window where a validated-but-not-yet-used path exists.

### Proof of Concept
Conceptual PoC (requires winning the TOCTOU window, e.g. via a `post-checkout` hook defined in the malicious repository):
1. Attacker crafts a repository/branch that, when merged in Desktop, produces a conflicted file `evil.txt` at a normal (non-symlink) path.
2. The repository defines a `post-checkout` (or equivalent) hook that Desktop's merge/checkout flow triggers, which replaces `evil.txt` with a symlink to `/Users/victim/.ssh/id_rsa` (for read) or to a path like `~/.bash_profile` (for write) at the moment Desktop is between the `resolveWithin` check and the `readFile`/`writeFile` call in `buildConflictContext` / `_applyCopilotConflictResolutions`.
3. If the hook fires within the TOCTOU window, `readFile(absolutePath)` reads the victim's SSH key content into the Copilot prompt context, or `writeFile(absolutePath, resolution.resolvedContent)` overwrites `~/.bash_profile` with attacker-influenced content, despite `resolveWithin` having reported the path as safely inside the repository at check time. async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
