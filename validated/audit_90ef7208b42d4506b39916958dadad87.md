Attacker-controlled Commit Status `target_url` opens arbitrary URL/deeplink via "View on GitHub"/"Details" link with no scheme restriction - ([File: app/src/lib/ci-checks/ci-checks.ts])

### Summary
The Nextcloud report shows that a client-controlled `objectId` field is rendered as a clickable link and, once clicked, opens whatever URL/scheme the attacker put in it. GitHub Desktop has a structurally identical primitive: the legacy Commit Status API field `target_url` (`IAPIRefStatusItem.target_url`) is fully attacker-controlled (settable by anyone with push access, or by CI systems/apps with a repo token, e.g. via a malicious fork's status check or an untrusted CI integration) and is copied verbatim into Desktop's internal `IRefCheck.htmlUrl` with no validation of its content, then surfaced in the UI as a "View on GitHub" / "Details" link that the user clicks, ultimately reaching `shell.openExternal` unfiltered.

### Finding Description
`apiStatusToRefCheck` takes the raw `target_url` string straight from the GitHub Commits Status API response and assigns it to `htmlUrl` with no URL/scheme validation: [1](#0-0) 

`IAPIRefStatusItem.target_url` is documented as `string | null`, coming straight off the wire: [2](#0-1) 

That `htmlUrl` is then used directly to build the "Details"/"View on GitHub" URL in the CI check popover and in the "Checks failed" notification dialog, with no scheme check performed before opening it: [3](#0-2) [4](#0-3) 

The job-step URL helper also concatenates `checkRun.htmlUrl` directly into a URL string with no validation: [5](#0-4) 

All of these funnel into `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal(url)`, which performs **no scheme allow-listing** at all — it opens whatever string is handed to it: [6](#0-5) 

This is materially different from — and weaker than — the guard that exists for markdown-rendered links, where `SandboxedMarkdown` explicitly checks `/^https?:/.test(a.protocol)` before invoking the click callback: [7](#0-6) 

No equivalent check exists on the CI-check/"view details" code path. The main-process `open-external` IPC handler also does not restrict the scheme; it only logs when the value looks like `http(s)`, but proceeds to call `shell.openExternal` regardless of protocol: [8](#0-7) 

### Impact Explanation
Any user or automation with the ability to create/update a commit status on a repository the victim has cloned in Desktop (e.g., a contributor on a public repo, a CI bot, a compromised third-party status-check integration, or someone opening a PR from a fork against a repo with a permissive Actions/status token) can set `target_url` to any string, including non-`http(s)` schemes: `file://`, `javascript:` is not exploitable in Electron's `shell.openExternal` context, but OS-registered custom protocol handlers (`x-github-client://`, `steam://`, `ms-word:`, arbitrary vendor-installed handlers, or Desktop's own `x-github-client://oauth?...` deep link) can be triggered. `shell.openExternal` with attacker-chosen values can also point to `file://` paths to trigger native file handlers, or to phishing pages that spoof GitHub. Since the UI presents this as "View on GitHub"/"Details", a user is naturally led to click it, believing it opens the corresponding GitHub commit-status/check page.

### Likelihood Explanation
Likelihood is moderate: it requires that the victim be viewing CI checks (popover or the "Checks failed" notification) for a commit/PR whose repository has a status with an attacker-controlled `target_url`. This is a very ordinary, unprivileged action for anyone (or any bot/integration) with permission to POST a commit status — a common scenario in open-source repos with external contributors and third-party CI tools. No local access, admin rights, or social engineering beyond the normal "click the details link" UX is required — this matches the same interaction pattern as the original Nextcloud report.

### Recommendation
Validate `htmlUrl`/`target_url` before using it to build a clickable link or before passing to `openInBrowser`/`shell.openExternal`. Apply the same `https:`-only allow-list currently used in `SandboxedMarkdown.setupLinkInterceptor` (`/^https?:/.test(...)`) to `apiStatusToRefCheck`, `getCheckRunStepURL`, and ideally centrally in `AppStore._openInBrowser`/the main-process `open-external` handler, rejecting or stripping non-`http(s)` URLs before invoking `shell.openExternal`.

### Proof of Concept
1. As a user with permission to set a commit status (e.g., a contributor, bot, or third-party CI integration) on a repository the victim has open in GitHub Desktop, call `POST /repos/{owner}/{repo}/statuses/{sha}` with `target_url` set to an attacker-chosen deep link, e.g. `x-github-client://oauth?code=...&state=...` or `file:///C:/Windows/System32/some.exe` or another OS-registered protocol handler.
2. In GitHub Desktop, the victim opens the PR/commit and views CI checks; the status is surfaced via `apiStatusToRefCheck` as `htmlUrl` unmodified.
3. Victim clicks "View Details"/"View on GitHub" in the CI check popover (`ci-check-run-popover.tsx`) or the "Checks Failed" notification (`pull-request-checks-failed.tsx`).
4. `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal(url)` executes with the attacker-supplied value verbatim, launching whatever handler is registered for that scheme/path, with no `https:`-only check as exists for markdown links.

export function apiStatusToRefCheck(apiStatus: IAPIRefStatusItem): IRefCheck {
  let state: APICheckStatus
  let conclusion: APICheckConclusion | null = null

  if (apiStatus.state === 'success') {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Success
  } else if (apiStatus.state === 'pending') {
    state = APICheckStatus.InProgress
  } else {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Failure
  }

  return {
    id: apiStatus.id,
    name: apiStatus.context,
    description: getCheckRunShortDescription(state, conclusion),
    status: state,
    conclusion,
    appName: '',
    checkSuiteId: null,
    htmlUrl: apiStatus.target_url,
  }

export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}
