## Analysis

The external report's core broken invariant: **code that treats a token-transfer call as successful based solely on the low-level call not reverting, without verifying the ERC20 return value**. Non-standard tokens (like USDT) can either omit the `bool` return or, more importantly for fund-safety, **return `false` instead of reverting** on a failed transfer. Code that checks only `success` (the call didn't revert) and ignores the returned boolean will treat a failed transfer as successful.

I found a direct, exploitable analog of exactly this pattern in Hyperbridge's Tron IntentGateway contract, in contrast to the safe pattern used in the canonical EVM contract.

### Title
Silent-failure token transfers in Tron IntentGatewayV2's `withdraw()`/`_execute()`/`_sweepDust()` cause escrow to be marked released without funds actually moving - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical EVM `IntentsBase._withdraw()` correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which validates both call success and the ERC20 return data. [1](#0-0) 

The Tron variant of the same contract instead performs a raw low-level `.call()` with the `transfer` selector and only checks that the call itself did not revert (`success`), never inspecting the returned boolean: [2](#0-1) 

The same pattern recurs for dust-sweeping and refund/timeout paths in the same file. [3](#0-2) 

### Finding Description
In `withdraw()`, before any transfer is attempted, the function unconditionally mutates finalized state:
- `_filled[body.commitment] = beneficiary` marks the order as finalized (one-time settlement).
- `_orders[body.commitment][token] -= amount` decrements the escrow accounting.

Only then does it move funds via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

`success` here only reflects whether the *call itself* reverted, not whether the token actually transferred value. Any TRC20/ERC20 token that returns `false` on a failed transfer (rather than reverting) — a common, standards-compliant behavior on Tron's TRC20 and for USDT-style tokens generally — will make `success == true` even though `beneficiary`'s balance never increased. The function then proceeds to emit `EscrowReleased`/`EscrowRefunded`, leaving `_filled` and `_orders` permanently updated as if the withdrawal succeeded, with no way to retry or reclaim: the commitment is already marked filled, and the escrow balance already decremented.

This is the exact bug class from the report — non-standard `bool`-returning-but-non-reverting token semantics being trusted by code that checks only "did the call revert," not "did the operation actually succeed" — but here it corrupts one-time settlement/escrow state (`_orders`, `_filled`) rather than an approval, causing genuine fund loss instead of a mere approve revert.

### Impact Explanation
This directly falls under "stealing or loss of funds" and "replay/double-claim/double-settlement" pivots: the escrow accounting (`_orders[commitment][token]`) is decremented and the order is irreversibly marked `_filled` even though the beneficiary (solver on `RedeemEscrow`, or user on `RefundEscrow`) receives nothing. Because same-chain/cross-chain settlement already delivered the counter-value (e.g., the solver already paid out the order's output before this escrow release runs), the result is asset loss for the legitimate counterparty with no recovery path — the commitment can't be replayed since `_filled` is already set.

### Likelihood Explanation
No malicious relayer, prover, or admin is required. An unprivileged user places an order (or a solver fills one) using an ERC20/TRC20 input or output token that returns `false` rather than reverting on failed transfers — a token property entirely under the placing user's control since arbitrary token addresses are accepted as `order.inputs`/`order.output.assets` (as already exercised for `FeeOnTransferToken` test tokens in the test suite). Any circumstance that makes the contract's balance of that token insufficient at withdrawal time (fee-on-transfer shortfalls, rounding, or a token that returns false on a call it doesn't like) turns into permanent fund loss instead of a revert-and-retry.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern throughout `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `_execute`'s dust-sweep, and the input-escrow branch) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, exactly as already done in the canonical `evm/src/apps/intentsv2/IntentsBase.sol`. `SafeERC20` decodes the return data and reverts on `false`, which is the direct fix recommended in the original report (`forceApprove`/`safeApprove` for the approve case; `safeTransfer` for the transfer case here).

### Proof of Concept
1. Deploy a TRC20/ERC20-like token whose `transfer()` returns `false` on a failed transfer instead of reverting (a legal ERC20 implementation, and the exact same class of behavior called out in the source USDT report).
2. User places a same-chain or cross-chain order using this token as an input, escrowing it in the Tron `IntentGatewayV2`.
3. A solver fills the order, delivering the promised output to the user.
4. `RedeemEscrow`/settlement triggers `withdraw()`. If the token's `transfer()` to the solver returns `false` (e.g., due to an internal condition, blacklist, or fee-on-transfer shortfall) instead of reverting:
   - `success == true` (the low-level call did not revert),
   - `_orders[commitment][token]` is already decremented,
   - `_filled[commitment]` is already set,
   - `EscrowReleased` is emitted,
   - but the solver's token balance is unchanged — funds are stuck in the contract with no path to reclaim them, while the solver has already paid out the order's output.
