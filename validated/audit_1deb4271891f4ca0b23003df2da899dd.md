### Title
Wallet hang via algorithmic-complexity DoS in `Offer.get_cancellation_coins()` when processing an untrusted offer - (File: chia/wallet/trading/offer.py)

### Summary
`chia/wallet/trading/offer.py`'s `get_cancellation_coins()` and its helper `detect_dependent_coin()` iterate over every coin spend, every dependency, and every announcement in nested loops, and this scan is itself repeated in an outer `while True` loop that re-runs after each partial removal. A specially crafted offer with many coin spends and cross-referencing coin announcements can drive this to worst-case polynomial blow-up, and because the whole computation is synchronous Python code with no `await` points, it blocks the wallet's single-threaded asyncio event loop for the whole duration.

### Finding Description
`get_cancellation_coins()` builds `dependencies`/`announcements` maps for every non-ephemeral coin spend in the offer bundle: [1](#0-0) 

It then repeatedly calls `detect_dependent_coin()`, which is itself a triple-nested loop over `names`, `deps[name]`, and `announcement_dict.items()`: [2](#0-1) 

Each time a dependent coin is found, an inner `while True` loop scans the *entire* remaining `dependencies` dict again to find anything referencing the just-removed announcements, and this repeats until no more removable announcements are found, then the outer `while True` loop restarts `detect_dependent_coin` from scratch over the (possibly still large) remaining set: [3](#0-2) 

None of these loops are bounded by a hard cap; they scale with however many coin spends/announcements the offer's spend bundle contains, which is attacker-controlled (an offer's `puzzle_reveal`/`solution` contents, including `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions, are fully attacker-chosen). By constructing a long chain (or dense mesh) of coins that each assert one another's announcements, an attacker can force many iterations of the outer `while True` loop, each re-scanning the full remaining coin/dependency sets, producing complexity that grows much faster than linearly in the number of coins/announcements in the offer.

This method is invoked from `TradeManager.cancel_pending_offers()`: [4](#0-3) 

A trade record (and therefore the ability to later call `cancel_pending_offers` on it) is created both when a user makes an offer and when a user takes ("responds to") an offer received from a counterparty, via `save_trade()`. This means a malicious offer counterparty can hand a wallet user a crafted offer file; once the user's wallet accepts and later attempts to cancel that trade (a normal wallet operation), the vulnerable code executes over attacker-supplied data.

### Impact Explanation
Because `get_cancellation_coins()` runs synchronously with no `await` yielding points, a pathological offer can make this call take an extremely long time, blocking the wallet process's single asyncio event loop. While blocked, the wallet cannot process any other pending spend bundles, RPC calls, or network messages — effectively a spend-triggered halt of the wallet's transaction processing until the computation finishes (which, for a sufficiently large/dense malicious offer, could be an impractically long time). This is a local wallet availability impact triggered entirely by attacker-supplied offer data reachable through the offers/trade counterparty flow named in-scope.

### Likelihood Explanation
Exploitability requires only that a user accept (or otherwise persist as a trade record) a maliciously crafted offer file and later invoke `cancel_pending_offers` on it — both are standard user-facing wallet operations, and constructing an offer with a dense announcement/dependency mesh across many coins does not require any special privileges, only knowledge of the CAT/settlement puzzle format used for offers. The number of coins in an offer is bounded by CLVM cost limits for a spend bundle, but that budget still allows enough spends/announcements to make the nested/looping structure costly.

### Recommendation
Bound the size of offers accepted for cancellation-coin computation, or rewrite `get_cancellation_coins()`/`detect_dependent_coin()` to use single-pass graph-traversal algorithms (e.g., build reverse announcement→coin indexes once and process removal candidates via a work queue) instead of repeatedly rescanning the full dependency/announcement maps on every removal. Also consider making this computation cooperative (yielding periodically) or moving it off the main event loop so a slow computation cannot stall all other wallet processing.

### Proof of Concept
Construction (conceptual, not executed): create an offer whose spend bundle contains N non-offered coin spends, each spend creating one `CREATE_COIN_ANNOUNCEMENT` and asserting (`ASSERT_COIN_ANNOUNCEMENT`) the announcement of a different coin in the set, forming either a long dependency chain or a dense web of cross-dependencies. Persist this as a trade record (e.g., by taking the offer via `respond_to_offer`), then call `TradeManager.cancel_pending_offers([trade_id], ...)`. The nested-loop restart behavior in `get_cancellation_coins()`/`detect_dependent_coin()` causes the wallet to spend disproportionately long, blocking wall-clock time processing this single call as N grows, stalling the wallet's event loop. I was not able to run this PoC in this environment to obtain concrete timing numbers; this should be validated by a background agent with the actual codebase and test harness to measure real growth rates and confirm the severity/threshold at which this becomes a practical DoS.

def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
