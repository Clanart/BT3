## Finding [1](#0-0) 

GitHub Desktop already has a dedicated `resolveWithin()` utility that safely joins an untrusted relative path with a root directory and rejects the result if it escapes that root (checked via `realpath` comparison). It is used, for example, to validate the `filepath` parameter of the `x-github-client://openRepo` deep link before revealing it in the file manager: [2](#0-1) 

However, several other UI code paths that build file-system paths out of **attacker-influenced file names** (git diff/status/commit file paths, or GitHub PR "files changed" entries from the API) skip this check entirely and just do a raw `Path.join(repository.path, path)`:

- `revealInFileManager()` itself performs no validation and its own doc comment warns "Do not use this method with non-validated paths": [3](#0-2) 
- The Changes sidebar's "Open with default program" handler: [4](#0-3) 
- The commit history file-list context menu ("Reveal in Finder", "Open in external editor", "Open with default program"), all keyed off `file.path` taken directly from the commit's changed-file list: [5](#0-4) 
- The Pull Request "Files Changed" view, where `file.path` originates from the GitHub API PR files payload: [6](#0-5) 
- The Copilot merge-conflict resolution dialog's overflow menu: [7](#0-6) 

None of these call sites use `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, only `isSafeFileExtension()` gates the "Open with default program" menu entry, which filters by extension, not path containment. `isSafeFileExtension` and `pathExists` checks do not verify that the resolved path is still inside `repository.path`.

### Title
Unvalidated attacker-controlled diff/PR file paths allow directory traversal in "Open"/"Reveal"/"Open in external editor" actions - (File: app/src/ui/history/selected-commits.tsx, app/src/ui/open-pull-request/pull-request-files-changed.tsx, app/src/ui/changes/sidebar.tsx, app/src/lib/app-shell.ts)

### Summary
GitHub Desktop has an established mitigation pattern — the `resolveWithin` family in `app/src/lib/path.ts` — that is applied when handling untrusted paths coming from `x-github-client://` deep links (`app/src/ui/dispatcher/dispatcher.ts`), but the same validation is missing from the much more commonly used "changed file" context menus that reveal/open a file, or open it in the external editor/default program. These paths (`file.path`) come from git diff/commit metadata of a cloned/fetched repository, or from a GitHub Pull Request "files changed" API response — both attacker-influenced sources. This is directly analogous to the `TokenTransmuter` bug: a balance/bounds invariant is enforced on one code path (`transmuteLinear`/deep-link `filepath`) but omitted on a sibling path that operates on the same kind of untrusted input (`transmuteInstant`/diff or PR file paths), letting the attacker bypass the intended containment guarantee.

### Finding Description
`Path.join(repository.path, path)` does not prevent `path` from containing `..` segments (or, depending on platform semantics, an absolute path/drive letter) that walk the result outside of `repository.path`. The `path`/`file.path` values consumed by `onOpenItem`, `onOverflowMenuClick`, `onContextMenu`, and `onFileContextMenu` are not names the user typed — they are taken verbatim from:
1. Git tree/diff data of a commit that was fetched or cloned from an attacker-controlled remote, or
2. The GitHub REST API's PR "files changed" payload (`CommittedFileChange` built from `IAPIPullRequest`), which for a PR opened by any GitHub user is entirely attacker-controlled.

Desktop already recognizes this class of risk and mitigated it once, for the deep-link `filepath` parameter, with `resolveWithin(repository.path, filepath)` plus an `isAbsolute()` rejection (`dispatcher.ts` lines 1957-1972). That same discipline is not applied at the other call sites that build a full path from `repository.path` + an externally-sourced relative path before calling `shell.showItemInFolder`, `shell.openExternal('file://...')`, or launching the external editor.

### Impact Explanation
If a crafted diff/tree file name (or PR file entry) resolves outside the repository directory, "Reveal in Finder/Explorer", "Open with default program", and "Open in external editor" will operate on a path outside the intended repo sandbox. Depending on OS file-type association this can lead to unintended execution of an attacker-placed or attacker-referenced file (e.g. an `.exe`/`.lnk`/`.desktop`/`.app` outside the repo tree resolved via traversal), or disclosure/interaction with sensitive files elsewhere on the user's disk — matching the "file write/read outside the repo" and "code execution" impact classes for this task.

### Likelihood Explanation
Exploitation requires only that the victim clone/fetch a malicious repository or view/open a malicious pull request's "Files Changed" tab and use a normal context-menu action ("Open", "Reveal in Finder", "Open in external editor") — no local access, admin rights, or pre-existing malware needed. This mirrors the deep-link scenario Desktop already treats as untrusted enough to require `resolveWithin`, so the same threat model applies to diff/PR file names. The main uncertainty is how strictly the local `git` version's tree/diff plumbing prevents `..`-containing path components from appearing in reported paths versus the GitHub API PR file list, which is not filtered by Desktop at all.

### Recommendation
Route every `Path.join(repository.path, path)` (or equivalent) built from git diff/commit file paths or PR API file paths through `resolveWithin`/`resolveWithinPosix` (as already done for the deep-link `filepath` in `dispatcher.ts`) before passing the result to `shell.showItemInFolder`, `shell.openExternal`, or the external editor launcher, and refuse the action (as `openRepositoryFromUrl` already does) when the resolved path falls outside `repository.path`.

### Proof of Concept
1. Publish/serve a repository (or open a PR against any repo) containing a commit whose tree records a file path crafted to traverse out of the working directory when reported by `git diff`/`git log --name-status`, or submit a PR whose changed-file listing (via the GitHub API) contains such a path.
2. Victim clones/fetches the repository in GitHub Desktop, or opens the PR's "Files Changed" tab.
3. Victim right-clicks the file entry and selects "Open with default program" / "Reveal in Finder" / "Open in external editor".
4. `Path.join(repository.path, path)` in `app/src/ui/history/selected-commits.tsx` (or `pull-request-files-changed.tsx`, `sidebar.tsx`, `copilot-conflicts-dialog.tsx`) resolves to a location outside `repository.path`, and the corresponding `shell`/editor action is performed on that out-of-repo path without any containment check, unlike the equivalent deep-link handler which calls `resolveWithin` and aborts on escape.

/**
 * Resolve one or more path sequences into an absolute path underneath
 * or at the given root path.
 *
 * The path segments are expected to be relative paths although
 * providing an absolute path is also supported. In the case of an
 * absolute path segment this method will essentially only verify
 * that the absolute path is equal to or deeper in the directory
 * tree than the root path.
 *
 * If the fully resolved path does not reside underneath the root path
 * this method will return null.
 *
 * @param rootPath     The path to the root path. The resolved path
 *                     is guaranteed to reside at, or underneath this
 *                     path.
 * @param pathSegments One or more paths to join with the root path
 * @param options      A subset of the Path module. Requires the join,
 *                     resolve, and normalize path functions. Defaults
 *                     to the platform specific path functions but can
 *                     be overridden by providing either Path.win32 or
 *                     Path.posix
 */
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
