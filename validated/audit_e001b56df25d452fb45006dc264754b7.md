## Finding: `object::root_owner()` Has No Cycle/Depth Bound, Causing Unbounded Looping When Reached From the Code-Publish Owner-Recording Path

### Title
Unbounded loop in `object::root_owner()` reachable from `code::publish_package`'s lazy-init owner recording, unlike the depth-capped `owns()`/`verify_ungated_and_descendant()` — ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
The external report is about a Move contract omitting the modifier used elsewhere to gate an internal function, letting untrusted callers reach code that skips validation performed by the "safe" entrypoint. The closest Aptos-native analog found through local code review is not a missing-modifier issue but a missing-bound issue in the same invariant class: every other object-ownership traversal function in `object.move` caps its walk at `MAXIMUM_OBJECT_NESTING`, but `root_owner()` — the function `code::publish_package` and `init::assert_may_self_initialize` rely on for the new lazy-module-initialization "deploy owner" security check — does not.

### Finding Description
`object.move` defines `MAXIMUM_OBJECT_NESTING = 8` and enforces it in both `owns()` and `verify_ungated_and_descendant()`: [1](#0-0) [2](#0-1) 

But `root_owner()` walks the ownership chain with no counter and no bound at all: [3](#0-2) 

A self-owned object is trivially reachable on current mainnet semantics: `verify_ungated_and_descendant` only starts counting *after* the initial direct-owner check, so transferring an object to its own address succeeds in one call because `owner == current_address` immediately (0 iterations, no cycle check triggered). This is confirmed by the module's own test showing the *second* self-transfer is what aborts on a cyclic-ownership error, meaning the *first* self-transfer (creating the 1-cycle) succeeds: [4](#0-3) 

`root_owner()` is invoked from the new publish-path owner-recording logic added for lazy module initialization: `code::publish_package` calls `object::address_to_object<object::ObjectCore>(addr).root_owner()` whenever the feature is enabled and the publish target is an object, in order to record the "deploy owner" that gates later self-initialization: [5](#0-4) 

And `init::assert_may_self_initialize` calls the same `root_owner()` again on every self-init check: [6](#0-5) 

If the object at `addr` is self-owned (owner == addr, a 1-cycle) — or owned through any cycle among nested objects — `root_owner()`'s `while (is_object(obj_owner)) { obj_owner = ...owner() }` loop never terminates because `is_object(obj_owner)` is always true and `owner()` always returns the same address. Unlike `owns`/`verify_ungated_and_descendant`, there is no depth counter to break out.

### Impact Explanation
This directly touches the publish/upgrade path and the new module-init validation invariant called out in the Publish Pivots ("bytecode verifier, loader, module-init handling ... must agree on what is legal"). A package publisher who (deliberately, e.g. via a resource-account/object flow) makes the target object self-owned before publishing under `LAZY_MODULE_INITIALIZATION`, or who allows a cycle to form among nested objects that later host published code, will cause:
- `code::publish_package` to hang/consume unbounded gas mid-publish (denial of the publish transaction, and since it acquires `PackageRegistry` for write, this blocks legitimate package-registry mutation for that address), and/or
- Every subsequent call to `init::internal_maybe_initialize` on that module's address to hang/consume unbounded gas, permanently denying self-initialization for that module.

This is a state-mutation-reaching failure in the module-init/publish invariant chain, not merely an event or cosmetic issue, and it can permanently deny a legitimate self-init/publish flow for the affected object address (until gas limits abort the transaction, but the write is never applied — an availability failure of the publish/init capability, not merely a query DoS).

### Likelihood Explanation
Creating a self-owned object requires only one ordinary, unprivileged `object::transfer(owner, obj, obj_address)` call — no special permission — so the precondition is fully attacker/publisher reachable. Reaching `root_owner()` via `code::publish_package` requires the `LAZY_MODULE_INITIALIZATION` feature (currently transient/gated) to be enabled; likelihood on mainnet today is therefore contingent on that feature flag's rollout state, which could not be confirmed from the index. This uncertainty tempers the finding to Medium/High rather than a confirmed Critical mainnet-active bug — the code path exists and is unguarded, but whether the feature flag is currently active on mainnet was not verifiable from the available files.

### Recommendation
Add the same depth cap used in `owns()` and `verify_ungated_and_descendant()` to `root_owner()`, aborting with `EMAXIMUM_NESTING` once `MAXIMUM_OBJECT_NESTING` hops are exceeded, so a cyclic or self-owned object degrades to a bounded abort instead of an unbounded loop.

### Proof of Concept
1. Create an object `obj1` owned by `creator` (`object::create_object` or `create_named_object`).
2. Call `object::transfer(creator, obj1, obj1.object_address())` — succeeds because the direct-owner check in `verify_ungated_and_descendant` passes with zero loop iterations, per the module's own cyclic-ownership test: [4](#0-3) 
3. Enable `LAZY_MODULE_INITIALIZATION` and publish a package to `obj1`'s address via `code::publish_package` (or `object_code_deployment::publish`, which calls `code::publish_package_txn` under the hood at an object address): [7](#0-6) 
4. Because `object::is_object(addr)` is true and the feature is enabled, `publish_package` calls `object::address_to_object<object::ObjectCore>(addr).root_owner()` on the self-owned object, which loops forever (`is_object(obj1) == true`, `owner() == obj1` every iteration), exhausting gas and aborting the publish transaction without applying the state mutation. [5](#0-4) 

Note: full verification that `LAZY_MODULE_INITIALIZATION` is active on current mainnet (vs. still gated off) could not be completed from the indexed files; a Devin session with full repo/feature-flag config access would be needed to confirm current activation status before treating this as an immediately live mainnet issue.

        let current_address = destination;

        );

        let object = borrow_global<ObjectCore>(current_address);

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));

        };

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
