## Title
Stale diff-based line selections are re-applied against a freshly re-fetched diff during staging, allowing silent corruption of partial commits — (File: `app/src/lib/git/apply.ts`)

### Summary
The report's core bug pattern is a **duplicated computation over an untrusted value with an intervening external event**: a total is computed once from state A, then a second pass acts on state B (which the attacker can move in between), and nothing reconciles the two. GitHub Desktop's partial-commit ("stage selected lines") flow has the same structural flaw: the user's line/hunk selection is captured against one snapshot of a file's diff, but at commit time the diff is **independently re-fetched from disk** and the old selection indices are blindly re-applied to it, with no check that the two diffs still agree.

### Finding Description
When the user stages only some lines/hunks of a modified file, Desktop stores the choice as a bitset of `absoluteIndex` positions relative to the diff that was rendered in the Changes view (`WorkingDirectoryFileChange.selection`, populated while viewing a diff computed earlier).

At commit time, `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) calls `applyPatchToIndex` for every file with a partial selection: [1](#0-0) 

`applyPatchToIndex` does **not** reuse the diff the user actually looked at — it fetches the diff a second time, fresh from the working directory, and formats a patch from it using the previously captured line-index selection: [2](#0-1) [3](#0-2) 

`formatPatch` (`app/src/lib/patch-formatter.ts`) then walks the hunks of this *newly fetched* diff and decides which lines to include purely by comparing `absoluteIndex` (a position in the *new* diff) against `file.selection.isSelected(absoluteIndex)` (indices captured from the *old* diff): [4](#0-3) 

There is no verification anywhere in this path that the diff used to build the selection and the diff used to build the patch are the same. If the file's on-disk content mutates between the moment the user makes their selection in the UI and the moment `applyPatchToIndex` runs (e.g., seconds later when they click "Commit"), hunk boundaries and line offsets shift, and the same `absoluteIndex` values now point at different lines. The resulting patch is applied with `git apply --cached --unidiff-zero`, which explicitly relaxes context-line verification (`-U0`-style diffs), making it more likely that a patch built from mismatched offsets will still apply successfully rather than fail loudly: [5](#0-4) 

This is functionally identical to the Caviar bug's root cause: a value (royalty fee / here, "which lines are selected") is computed once against one read of untrusted/mutable state, and is later *consumed* against a second, independent read of that same state, with an untrusted actor able to change the state in between and no reconciliation performed.

### Impact Explanation
A malicious or compromised repository can arrange for tracked files to be rewritten between diff render and commit (for example via a `post-checkout`/`post-merge` Git hook shipped in the repository — which Git, and therefore Desktop, executes automatically on clone/checkout/merge — or any other automated process touching the working tree). Because Desktop reuses stale, position-based selection state against a freshly recomputed diff with reduced context checking, the user can end up **silently committing and pushing lines they never selected** (or omitting lines they did select) without any warning, directly matching the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Partial staging (selecting individual lines/hunks) is a core, frequently used Desktop feature, and the window between viewing a diff and clicking "Commit" is normal, unforced user behavior — no unnatural steps are required. The only attacker-controlled ingredient needed is a file mutation event sourced from the cloned/fetched repository (e.g., a repo-shipped Git hook or build tooling invoked as part of normal repo usage) landing inside that window. This does not require local malware, admin rights, or leaked credentials — only content control over the cloned repository, matching the accepted threat model.

### Recommendation
Do not re-fetch the diff independently at staging time. Either:
- Persist and reuse the exact diff (or its content hash) that the user's selection was computed against, and abort/re-prompt if the current working-tree diff for that file no longer matches it before calling `applyPatchToIndex`, or
- Recompute the user's line selection against the freshly fetched diff by content (not by positional index) before building the patch, and fail closed (refuse to stage) if the file changed in a way that invalidates the selection.

### Proof of Concept
1. Attacker publishes a repository containing a `post-checkout` (or `post-merge`) hook that, after a short delay, appends/removes a line near the top of a tracked file (shifting all subsequent hunk offsets).
2. Victim clones/checks out the repository in Desktop, modifies the file, opens the Changes view, and selects only specific lines/hunks to stage (captured as `absoluteIndex` positions against the diff rendered at that moment).
3. Before the victim clicks "Commit", the hook fires and mutates the file, shifting line offsets.
4. On commit, `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches the diff from the now-mutated file and `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`) applies the stale `absoluteIndex` selection to the new hunks, producing a patch that stages different content than what the victim reviewed and intended, which is then silently committed via `createCommit` (`app/src/lib/git/commit.ts:15-72`).
