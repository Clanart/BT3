Based on my research, the closest structural analog to the "overwrite instead of accumulate" bug class in the Tidal report exists in GitHub Desktop's changes-state reconciliation logic, where per-file selection state is blindly carried forward across status refreshes without validation against the new diff content, except for a single "currently open" file.

### Title
Stale partial line-selection state is silently reused across working-directory status refreshes for non-focused files - (File: app/src/lib/stores/updates/changes-state.ts)

### Summary
When GitHub Desktop refreshes the working directory status (e.g., after a fetch, checkout, or any background git operation that changes file contents), `updateChangedFiles` reconciles the new file list against the previous one by re-attaching each file's *old* `DiffSelection` object onto the *new* `WorkingDirectoryFileChange` instance, via `existingFile.withSelection(existingFile.selection)`, with no check that the underlying diff/line numbers are still valid for that file.

### Finding Description
`updateChangedFiles` builds a lookup of the previous files by id and merges the new status entries against it: [1](#0-0) 

For every file that still exists (matched only by `id`, which for ordinary changes is `status.kind + path`), the code unconditionally does `file.withSelection(existingFile.selection)` — carrying forward the *entire* previous `DiffSelection`, including its `selectableLines` set and per-line inclusion bitmap, onto a file whose actual diff content may have changed completely between the two status calls.

Contrast this with `updateChangesWorkingDirectoryDiff` in `app-store.ts`, which *does* recompute `selectableLines` from the freshly loaded diff and calls `withSelectableLines` — but only for the single file that is currently selected and open in the diff viewer: [2](#0-1) 

Every other file with a `Partial` selection in the working directory (i.e., all files the user is not actively looking at) never goes through this revalidation path. Its old `DiffSelection` — an object indexed by line number — is reused verbatim against the new diff content. This is structurally the same invariant violation as the Tidal `coverageMap` bug: a value meant to track cumulative/consistent user intent (`amount`/selection) is silently overwritten or reused across state transitions instead of being properly merged/revalidated, and existing guards (the `clearPartialState` path) only cover the case of committing after resolving conflicts, not general status refreshes: [3](#0-2) 

### Impact Explanation
If a user has partially staged a file (selected specific lines via `_changeFileLineSelection`) and, before committing, the working tree content for that path changes underneath them — e.g., an attacker-controlled `.gitattributes`/smudge filter, a merge/checkout driven by a malicious remote, a background fetch that triggers a working-directory refresh, or any git hook/filter that rewrites the file — Desktop keeps applying the stale line-index selection to the new content. When the user commits, the partial-selection commit path builds a patch from `DiffSelection` indices against content that has shifted, which can silently stage/commit different lines than the ones the user actually reviewed and intended to include. This is a "silent corruption of what the user commits" scenario matching the accepted impact criteria — no admin rights or local access are required beyond normal repository interaction (fetch/checkout of attacker-controlled content).

### Likelihood Explanation
This requires only that (a) the user has an outstanding partial line selection on a file, and (b) a status refresh happens (which Desktop triggers routinely — after fetch, checkout, branch switch, or file system watcher events) while that file's content changes for reasons outside the user's direct edit (e.g., driven by remote/checkout content an attacker controls). No unusual user action is needed beyond ordinary use of partial-commit staging combined with routine background refreshes.

### Recommendation
When reconciling `mergedFiles` in `updateChangedFiles`, do not unconditionally reuse `existingFile.selection` for files with `DiffSelectionType.Partial`. Instead, either (a) clear/downgrade partial selections to `None`/`All` similarly to the `clearPartialState` branch whenever the file's diff is not being actively revalidated, or (b) recompute `selectableLines` for every file with a partial selection against fresh diff data before allowing it to be committed, matching the safeguard already applied to the single actively-viewed file in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. Stage file `A.txt` with a `Partial` selection of specific lines via the Changes view.
2. Without committing, trigger a working-directory content change to `A.txt` that alters line numbers/content (e.g., via a smudge/clean filter, checkout from a remote, or another process editing the file), followed by a Desktop status refresh (fetch, branch switch, or automatic file-watcher-triggered refresh).
3. Observe that `updateChangedFiles` reattaches the old `DiffSelection` (old line indices) to the new file entry rather than invalidating it.
4. Commit the partial selection — the resulting commit patch is built from stale line indices against new content, differing from what the user intended to stage.

I was not able to fully verify the exact downstream patch-construction code path used at commit time for partial selections within the available index, so I cannot cite the precise line-application logic that turns `DiffSelection` into the final staged patch; a Devin session with full repo access would be needed to trace `git apply`/`stageFiles` consumption of `DiffSelection` end-to-end and confirm exploitability with a concrete diff/line-shift scenario.
