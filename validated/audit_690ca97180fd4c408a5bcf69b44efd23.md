### Title
Anyone can steal tokens accidentally sent to `ManualCompound` via the `compound()` function's raw `balanceOf` sweep - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` sweeps the contract's *entire* token balance to `msg.sender` twice: once for "non-compoundable" reward tokens passed in via the caller-controlled `_rewards` array, and once for each registered reward token that has no `convertor`/`locker`/`helper` configured. Because both sweeps use `IERC20(token).balanceOf(address(this))` instead of tracking the amount actually received from the specific claim, any token balance that ends up in the contract for any reason (mistaken transfer, unclaimed dust, leftover reward remainder) can be drained in full by any unprivileged wallet.

### Finding Description
In `compound()`: [1](#0-0) 
the "send none compoundable reward back to caller" loop iterates over the caller-supplied `_rewards[i][j]` addresses — which are arbitrary calldata values, not validated against what `_lps[i]` actually pays out — and for any token not in the `compoundableRewards` mapping it transfers the contract's **entire** `balanceOf` that token to `msg.sender`.

Similarly, for each registered compoundable reward token: [2](#0-1) 
`receivedBalance` is computed via `balanceOf(address(this))` rather than a before/after delta of the specific claim, and if the reward's `convertor`, `locker`, and `helper` are all unset, the full balance is transferred directly to `msg.sender` (line 157).

This mirrors the reported bug class exactly: a legitimate, permissionless "claim/compound" style function pays out based on the contract's whole token balance rather than the amount actually attributable to the caller's claim, and lets the caller choose the destination (`msg.sender`). Any ERC20 tokens that land in `ManualCompound` — whether by user error, a stuck/partial claim, or any other reason — become claimable in full by the next caller of `compound()`, who can target that exact token by including its address in `_rewards[i][j]` (paired with any `_lps[i]`, since there is no check that the token is actually a reward for that pool) or by simply waiting for `rewards[i].tokenAddress` balance to be nonzero.

### Impact Explanation
Direct theft of funds: any wallet holding any amount of any ERC20 token balance held by `ManualCompound` can be swept to an attacker by simply calling `compound()` with the target token address listed in `_rewards`. This is not limited to protocol-owned dust — since `masterMagpie.multiclaimOnBehalf` is called first and the sweep loop runs unconditionally afterward regardless of what was actually claimed, an attacker can drain the contract's balance of any token at will, at no cost beyond gas.

### Likelihood Explanation
Fully reachable from an ordinary wallet: `compound()` is `external` with no access control, and `_lps`/`_rewards` are fully attacker-controlled calldata. No special privilege, timing, or governance action is required — the attacker only needs the contract to hold a nonzero balance of the target token at call time.

### Recommendation
Do not use raw `balanceOf(address(this))` as the amount to forward. Track the exact amount returned/received from `multiclaimOnBehalf` for each specific `(pool, token)` pair (e.g., via before/after balance deltas scoped strictly to the claim call, or by having `MasterMagpie` return per-token claimed amounts), and only forward that delta rather than the full contract balance. Additionally, validate that `_rewards[i][j]` tokens actually correspond to real reward tokens for `_lps[i]` before crediting them to `msg.sender`.

### Proof of Concept
1. Any ERC20 token `X` balance becomes present in `ManualCompound` (e.g. a user mistakenly sends `X` to the contract, or `X` is left over from a prior partial claim).
2. Attacker calls `compound(_lps, _rewards, _convertRatio, _minRec, _lockMgp)` where `_rewards[0] = [X]` and `_lps[0]` is any valid pool address (it need not actually reward `X`).
3. Inside `compound()`, `compoundableRewards[X]` is `false` (assuming `X` was never registered as a reward), so the loop at [3](#0-2)  reads `IERC20(X).balanceOf(address(this))` and transfers the entire balance to `msg.sender` (the attacker), regardless of whether the attacker had any legitimate claim to it.

    function compound(address[] calldata _lps, address[][] calldata _rewards, uint256 _convertRatio, uint256 _minRec, bool _lockMgp) external {
        uint256 rewardTokensLength = rewards.length;        
        IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
        // send none compoundable reward back to caller
        for(uint256 i; i < _lps.length; i++) {
            uint256 rewardLength = _rewards[i].length;
            if (rewardLength > 0) {
                for (uint j; j < rewardLength; j++) {
                    if (!compoundableRewards[_rewards[i][j]]) {
                        uint256 rewardBalance = IERC20(_rewards[i][j]).balanceOf(address(this));
                        if (rewardBalance > 0)
                            IERC20(_rewards[i][j]).safeTransfer(msg.sender, rewardBalance);
                    }
                }
            }
        }
