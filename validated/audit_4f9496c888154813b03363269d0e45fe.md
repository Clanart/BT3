Based on the evidence gathered, I found a concrete, locally-provable analog. I was not able to fully read `HandlerV2.sol`'s exact height-monotonicity gate before my tool budget ran out (noted as a limitation below), but the storage-layer defect itself is fully confirmed from `EvmHost.sol` and its Substrate counterpart.

### Title
Vetoing the latest state machine commitment resets the trusted height floor to `1` instead of the last-known-good height, re-opening replay of stale/rolled-back remote state - (File: `evm/src/core/EvmHost.sol`)

### Summary
When a fisherman vetoes the *latest* state commitment for a counterparty state machine, `EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight[stateMachineId]` to the constant `1` rather than to the last verified, non-vetoed height. This is the exact class of bug described in the external report: a stored "checkpoint" value that gates future acceptance of remote state is not properly restored to its pre-fault value after a revert/veto, allowing subsequent (legitimately-proven, but stale) heights to be recommitted as the new "latest" trusted state.

### Finding Description
`EvmHost.storeStateMachineCommitment` unconditionally overwrites the latest-height pointer with whatever height it is given, with no monotonicity check inside this function itself: [1](#0-0) 

The only place a height floor can meaningfully be enforced is via the previously-stored `_latestStateMachineHeight` value, which callers (the handler) are expected to check before invoking `storeStateMachineCommitment`. That floor is precisely what gets corrupted on veto: [2](#0-1) 

Line 720 resets `_latestStateMachineHeight[height.stateMachineId] = 1` whenever the vetoed height was the latest recorded one — a hardcoded sentinel, not the actual last-known-good height.

Compare this to the equivalent Substrate-side logic in `pallet-ismp`, which the codebase itself documents as the correct behavior: reset to a **tracked previous height**, not to a floor value: [3](#0-2) 

The Substrate implementation stores and restores `PreviousStateMachineHeight`, guaranteeing the trust floor only ever rolls back to the last verified-good height. The EVM implementation has no equivalent "previous height" storage slot at all — it simply drops the floor to `1`. This is functionally identical to the original report's flaw: `l2SystemContractsUpgradeBlockNumber` (a gating checkpoint) wasn't reset to a safe value on revert, allowing recommitment of blocks with incorrect/stale values "before" the point they should logically occur.

The practical effect on `EvmHost`: after a veto of the latest height for a given `stateMachineId`, any subsequent `storeStateMachineCommitment` call from the handler needs only satisfy `height > 1` (assuming that's the height-ordering check used upstream in `HandlerV2`), instead of `height > <last known-good height>`. This permits a permissionless relayer to resubmit a legitimately-proven-but-old consensus/state update for an arbitrarily low height as the new "latest" state for that chain, discarding all height progress made prior to the vetoed height. Because `_stateCommitmentsUpdateTime` is also reset to `block.timestamp` for that low height, it appears freshly finalized and enters a brand-new challenge period as if it were the newest state, even though it corresponds to a chain height far in the past relative to true progress.

### Impact Explanation
This breaks the Hyperbridge invariant that "consensus proofs, state proofs, challenge periods, and state commitments must never let false/stale remote state become trusted." Rolling the trust floor back to `1` instead of the pre-fault height allows an old (previously-superseded) state root to be re-anointed as the canonical "latest" state for a state machine. Any request/response proof verification keyed off `latestStateMachineHeight()`/`stateMachineCommitment()` for that ID can now be satisfied against this stale root, undermining the monotonic-height assumption the rest of the protocol (timeouts, overlay-root freshness, relayer/fisherman tooling) relies on. This is a false-state-acceptance class defect, directly in scope of the bounty.

### Likelihood Explanation
The path to trigger the reset is the intended, permissionless veto/fisherman flow (`deleteStateMachineCommitment`, called by the handler on a successful state-commitment veto) — no malicious relayer, prover, or admin is required, only a legitimate veto of the current latest height followed by an ordinary relayer submitting a valid (but old) consensus/state update. The only uncertainty is the exact monotonicity check inside `HandlerV2.sol` that gates calls into `storeStateMachineCommitment`; I could not fully inspect that file's logic before running out of tool calls, so I cannot confirm with 100% certainty that no additional floor value is checked elsewhere. The storage-level discrepancy between the EVM and Substrate implementations, however, is fully confirmed and is the root cause regardless of what additional checks (if any) exist in `HandlerV2`.

### Recommendation
Track a `_previousStateMachineHeight` (or equivalent) mapping in `EvmHost.sol`, mirroring `PreviousStateMachineHeight` in `modules/pallets/ismp/src/host.rs`, and update `deleteStateMachineCommitmentInternal` to reset `_latestStateMachineHeight[stateMachineId]` to that tracked previous height instead of the hardcoded `1`.

### Proof of Concept
1. Attacker/fisherman submits a valid fraud/veto proof against the current latest state commitment for `stateMachineId` at height `H` (this is the normal, permissionless veto path).
2. `deleteStateMachineCommitmentInternal` executes; since `H == _latestStateMachineHeight[stateMachineId]`, the floor is reset to `1` (`evm/src/core/EvmHost.sol:718-721`).
3. A relayer submits any legitimately-signed consensus/state update at height `H' < H` (e.g., an old, already-superseded height) through the normal handler path.
4. Because the floor is now `1`, `H' > 1` passes whatever monotonicity check gates entry, and `storeStateMachineCommitment` unconditionally sets `_latestStateMachineHeight[stateMachineId] = H'` (`evm/src/core/EvmHost.sol:693`), rolling the trusted state height backward and re-arming a stale state commitment as canonical with a fresh challenge-period timer.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
