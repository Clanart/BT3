### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows stack exhaustion when parsing attacker-crafted CREATE_COIN memo data - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody-puzzle tree (members/restrictions, including nested `MofN` structures) from a `Program` memo that originates from on-chain `CREATE_COIN` memo data supplied by whoever creates the coin. There is no depth limit on this recursion. A coin creator (any spend-bundle submitter) fully controls the memo bytes attached to a coin they create, so they can encode an arbitrarily deep nested `MofN` structure that, when parsed by `PuzzleWithRestrictions.from_memo()`/`PlotNFT.get_next_from_coin_spend()`, causes unbounded Python recursion and can crash the parsing process (`RecursionError` / native stack exhaustion) in wallet/pool-client code that processes that coin.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is a classmethod that recursively parses a `Program` memo tree: [1](#0-0) 

When `further_branching` is true, it builds a `MofN` puzzle whose `members` list is populated by calling `PuzzleWithRestrictions.from_memo(memo)` recursively for each member memo, with no bound on nesting depth: [2](#0-1) 

This function is exercised on untrusted, attacker-supplied on-chain data through `PlotNFT.get_next_from_coin_spend()`, which extracts the memo directly from the `CREATE_COIN` condition's `memo_blob` of a coin spend being processed (a coin spend that any user can construct/broadcast, since `CREATE_COIN` memos are free-form data chosen by whoever creates the coin): [3](#0-2) 

Unlike `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py`, which is explicitly implemented iteratively "so we don't have to worry about blowing out the python stack" (as documented in that module's docstring), `from_memo()` has no such protection and has no maximum nesting/size check before recursing. [4](#0-3) 

This is directly analogous to the reported Go `go/parser` bug class: a deeply nested input structure drives unbounded recursive descent in a parser/deserializer, causing a stack-exhaustion panic/crash rather than a graceful error.

### Impact Explanation
An attacker who can create a coin (any wallet/full-node user, no special privileges needed) can embed a maliciously deep `MofN` memo chain in a `CREATE_COIN` condition. Any Chia client whose wallet or pool-NFT code later processes that coin spend via `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()` (e.g., a wallet syncing plotnft/pool-participant state, per the plotnft/pool-transition flow reachable via `chia/wallet/plotnft_wallet/plotnft_wallet.py`) will recurse without bound while reconstructing the puzzle tree, resulting in a `RecursionError` or native stack overflow. This is a spend-triggered halt of transaction/state processing for the affected local process — a denial-of-service against wallet clients that sync/process plotnft-related coin state, matching the "spend-triggered transaction-processing halt" impact category.

The mempool/consensus-critical CLVM parsing path itself (`Program.from_bytes()` via Rust `run_chia_program`, and `sha256_treehash()`) is protected/iterative, so this does not affect full-node block/mempool admission directly; the affected surface is wallet/pool-driver-side memo reconstruction of coins already accepted on chain.

### Likelihood Explanation
Likelihood is high for triggering the crash once a vulnerable client processes the crafted coin: constructing the nested memo requires no special access — any spend-bundle submitter can create a coin with an arbitrary memo. The remaining uncertainty is exactly which wallet call paths route arbitrary/attacker-created coins into `PlotNFT.get_next_from_coin_spend()` during normal sync (this was not fully confirmed beyond `chia/wallet/plotnft_wallet/plotnft_wallet.py` referencing `get_next_from_coin_spend`); if it is only invoked on coins the wallet already expects to be its own singleton lineage, the attacker would need to get such a coin recognized as part of a tracked plotnft/singleton lineage, which narrows exploitation to targeting a specific wallet's tracked singleton coin.

### Recommendation
- Add an explicit recursion/nesting-depth limit (and/or convert to an iterative worklist algorithm, mirroring `sha256_treehash()`) in `PuzzleWithRestrictions.from_memo()` in `chia/wallet/puzzles/custody/custody_architecture.py`, rejecting memos that exceed a sane maximum nesting depth with a normal `ValueError` instead of recursing unbounded.
- Enforce the same bound in any other custody/`MofN` memo-parsing code paths that recurse over attacker-controlled `Program` data (e.g., `unknown_puzzles`, `fill_in_unknown_puzzles`) since these also recurse over `MofN.members` without depth checks.
- Wrap `PlotNFT.get_next_from_coin_spend()`'s call into `from_memo()` so that a `RecursionError`/stack-depth violation is caught and converted into `GetNextPlotNFTError` rather than propagating as an uncaught fatal error.

### Proof of Concept
Conceptually (matching the pattern in the existing test `test_pwr_errors`, which already calls `PuzzleWithRestrictions.from_memo()` directly on crafted `Program` data): [5](#0-4) 

Build a deeply nested memo program equivalent to nested `MofN` hints, e.g. recursively wrap `MofNHint(m=1, member_memos=[inner_memo])` thousands of levels deep, each wrapped in the `(spec_namespace, [nonce, [], 1, mofn_hint])` envelope produced by `PuzzleWithRestrictions.memo()`: [6](#0-5) 

Then call `PuzzleWithRestrictions.from_memo(deeply_nested_program)` (or feed such a program as the `memo_blob` of a `CREATE_COIN` condition consumed by `PlotNFT.get_next_from_coin_spend()`), which should raise `RecursionError` / crash the interpreter rather than a controlled `ValueError`.

    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
