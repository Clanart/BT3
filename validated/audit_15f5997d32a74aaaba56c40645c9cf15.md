### Title
Recursive/nested precompile calls sharing a single `BalanceHandler` instance corrupt `stateDB` balances via overwritten `prevEventsLen` — (File: `precompiles/common/balance_handler.go`)

### Summary
This is the same bug class as GMX H-2: a stale/incorrectly-scoped state variable is used instead of the value that reflects the current call context, corrupting an accounting result. In GMX, `getTotalBorrowingFees` read a stale `cumulativeBorrowingFactor` instead of the freshly computed one, corrupting LP share pricing. In Cosmos EVM, `BalanceHandler.prevEventsLen` — a single mutable field on a shared handler instance — is overwritten by any nested/recursive precompile invocation before the outer invocation reads it back, causing `AfterBalanceChange` to process the wrong slice of `ctx.EventManager().Events()` and desynchronize `x/bank`/`x/precisebank` state from the EVM `stateDB` balances. This is explicitly reproduced by the repository's own test, `evmd/tests/integration/balance_handler/balance_handler_test.go`, which is titled/commented as testing exactly this bug.

### Finding Description
`BalanceHandler` records a "before" event-log length and later diffs against the "after" event log to translate bank/precisebank events into `stateDB.AddBalance`/`SubBalance` calls: [1](#0-0) [2](#0-1) 

`prevEventsLen` is a single mutable field on the handler struct, not a stack or per-call-frame value. If the same `BalanceHandler` instance is reused for a precompile call that recursively/re-entrantly triggers another precompile call (e.g., a contract that calls a precompile method whose EVM execution path itself invokes another precompile, or the same precompile is called again during nested execution as demonstrated by the `DebugPrecompileCaller` contract in the test), the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` to a larger index. When the outer call's `AfterBalanceChange` subsequently executes, it slices `events[bh.prevEventsLen:]` using the *inner* call's recorded length rather than its own, causing:
- Events emitted by the outer/earlier bank operation to be skipped entirely (never applied to `stateDB`), or
- Events belonging to the inner call to be replayed/misattributed to the outer call's balance delta application.

The repository's own regression test explicitly documents and reproduces this: [3](#0-2) 

and drives it through a contract that recursively calls a precompile: [4](#0-3) 

`BalanceHandler` is used by essentially every stateful precompile that moves native/bank value on behalf of EVM callers (staking, distribution, erc20, gov, ics20, slashing all call into this shared logic): [5](#0-4) 

I was not able to fully verify from the index whether a *new* `BalanceHandler` is always freshly constructed per top-level precompile invocation (via `BalanceHandlerFactory.NewBalanceHandler`) or whether an existing instance can genuinely be reused/shared across a nested call within the same EVM message execution (e.g., passed down through a shared keeper/precompile struct field rather than being call-local). The test title itself ("recursive precompile calls share the same BalanceHandler instance") indicates the repository authors identified and reproduced sharing in at least one code path, but I could not trace every precompile's instantiation path in the available index depth to confirm all affected precompiles or whether a fix has already landed elsewhere (the test could be a regression test for an already-fixed bug, or a demonstration of an existing one — this could not be conclusively determined from the excerpts available).

### Impact Explanation
If `stateDB` balances diverge from the true `x/bank`/`x/precisebank` state:
- Events skipped ⇒ a bank-side debit/credit occurs but the EVM-visible balance (`stateDB`) is never decremented/incremented, meaning an EVM account can retain (or gain) `stateDB` balance not backed by an actual bank balance — this is unauthorized duplication of spendable value from the EVM's perspective, and any subsequent EVM-level transfer or `SELFDESTRUCT`/balance read based on that stale `stateDB` value could allow spending value that no longer exists on the bank side.
- Events double-applied ⇒ `stateDB.AddBalance`/`SubBalance` could be invoked with amounts belonging to the wrong call, corrupting the balance ledger and potentially crediting one account with funds debited from another, i.e., unauthorized minting/duplication or theft of spendable value.

Either direction breaks the 1:1 accounting invariant between native bank balances and EVM-visible balances that the codebase's asset-representation layer depends on (this is the same invariant class flagged in the "Asset-representation path" pivot). This matches the Critical-impact gate for "unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets."

### Likelihood Explanation
Triggering requires an EVM contract that performs a bank-affecting precompile call, and within the execution of that precompile call (or its EVM sub-call), triggers another bank-affecting precompile call — a pattern reachable by any ordinary, unprivileged contract deployer/caller (no privileged keys needed), as demonstrated by the repository's own `DebugPrecompileCaller` test contract producing the corrupted event count (`debug_count == 10` instead of the expected count matching outer/inner call structure). Because this only requires deploying and calling a contract, likelihood is high assuming the sharing condition is genuinely reachable in production precompiles (staking/distribution/erc20/gov/ics20/slashing), not just the test-only debug precompile.

### Recommendation
- Make `prevEventsLen` (and the "before" event count) local to each call frame rather than a mutable field on a possibly-shared `BalanceHandler` instance — e.g., have `BeforeBalanceChange` return the recorded length and require callers to pass it explicitly to `AfterBalanceChange`, removing shared mutable state entirely.
- Alternatively, guarantee that a brand-new `BalanceHandler` is constructed for every precompile invocation (including nested/recursive ones) via `BalanceHandlerFactory.NewBalanceHandler`, and audit all precompiles (`distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`) to confirm none holds a long-lived handler reference across nested calls.
- Add an invariant check post-execution comparing the aggregate `stateDB` balance delta for all touched addresses against the aggregate bank-module balance delta for the same addresses within a transaction, failing the transaction if they diverge.

### Proof of Concept
The repository's existing test demonstrates the reachable trigger path: [6](#0-5) 
It deploys a `DebugPrecompileCaller` contract, funds it, and calls `callback(0)`, which recursively invokes the debug precompile; the test asserts on the resulting event structure to surface the mismatch caused by the shared `prevEventsLen`. To weaponize this against a real asset-moving precompile (e.g., `staking` or `distribution`) instead of the debug precompile, an attacker would deploy a contract that, from within one precompile call's EVM sub-execution, triggers a second precompile call that also moves bank funds, then observe/exploit the resulting `stateDB` vs bank-ledger divergence to extract value via a subsequent EVM transfer based on the inflated `stateDB` balance. Full exploitation to a moved-funds PoC was not completed here because the exact call graph needed to trigger genuine instance-sharing (as opposed to always-fresh handler construction) in a non-debug precompile could not be confirmed from the available index.

type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")
