Confirmed: `git push` in `push.ts` executes `git push <remote.name> ...` (using the actual local git config for that remote name to determine the URL that Git itself connects to), while `envForRemoteOperation(remote.url)` independently derives the *proxy* to use from a separately-passed `remote.url` string [1](#0-0) . These two values (`remote.name` used by git itself, and `remote.url` used only for env/proxy resolution) are supposed to refer to the same remote, but `app-store.ts`'s `performPush` constructs them from two independently-refreshed pieces of state that the code's own comment admits can be out of sync.

### Title
Mismatched remote name/URL pairing in push path can route auth/proxy negotiation to the wrong host - (File: app/src/lib/stores/app-store.ts)

### Summary
`performPush` builds the object passed to the low-level `push()` function by taking the remote **name** from the checked-out branch's upstream tracking info (`branch.upstreamRemoteName`) but the remote **URL** from a separately-cached `state.remote` object (derived from `GitStore.currentRemote`/`defaultRemote`). The in-code comment explicitly acknowledges these two values "could be out of sync" and adds a non-fatal-exception telemetry call when detected, but the mismatched pairing is still used to proceed with the push instead of being blocked or corrected.

### Finding Description
`GitStore.loadRemotes()` computes `_currentRemote` from the current tip's `upstreamRemoteName`, falling back to `_defaultRemote` (the `origin` remote or first remote alphabetically) whenever the tracked remote can't be resolved [2](#0-1) . This value is cached in `repositoryStateCache` as `state.remote` and refreshed independently from the `Tip`/branch state, which is refreshed by a separate status-loading path.

In `performPush`, the code reads `remote` (`state.remote`, i.e. `GitStore.currentRemote`) and separately computes `remoteName` from `branch.upstreamRemoteName || remote.name`, then builds:
```ts
const safeRemote: IRemote = { name: remoteName, url: remote.url }
``` [3](#0-2) 

If `branch.upstreamRemoteName` (the name from the tip/branch, which can be stale relative to `state.remote` because they are refreshed at different times, as the comment states) differs from `remote.name`, the code only fires `sendNonFatalException('remoteNameMismatch', ...)` for telemetry — it does **not** abort or re-resolve the URL for the actual `remoteName` being used. The resulting `safeRemote` object then has a `name` belonging to one git remote but a `url` belonging to a *different* remote object.

This inconsistent object is passed into `pushRepo` → `push()` in `app/src/lib/git/push.ts`. There, `git push <remote.name> ...` is executed, which correctly resolves the destination from `.git/config` using `remote.name` — so the code content is not misdirected. However, `envForRemoteOperation(remote.url)` [4](#0-3)  uses `remote.url` (from the *other*, mismatched remote) to decide the proxy environment variables via `envForProxy` [5](#0-4) . If a repository has multiple remotes with different hosts (e.g. `origin` pointing at an attacker-influenced fork/mirror added as an additional remote, and a legitimate `upstream`), a stale/mismatched `remote.url` can cause git to authenticate/proxy the push using settings resolved for a **different host** than the one git is actually connecting to.

### Impact Explanation
The invariant "the remote name and remote URL used for a push always refer to the same git remote" is not strictly enforced; the code detects violations but proceeds anyway. Because `envForProxy` resolves and injects `http_proxy`/`https_proxy` based on the mismatched URL [6](#0-5) , an attacker who controls one of the multiple configured remotes (e.g., a malicious fork/mirror URL added by the user or automatically as an "upstream" for a fork) could cause proxy resolution logic to be computed against their controlled host while the actual git push still targets the legitimate remote — enabling redirection of the push's network traffic through an attacker-influenced proxy, exposing credentials/headers negotiated for that connection. This aligns with the "silent corruption / credential exfiltration via mismatched remote configuration" impact class.

### Likelihood Explanation
The developers' own comment calls this only a "theoretical possibility," and the telemetry event (`remoteNameMismatch`) exists specifically to detect if it ever occurs in the wild, implying it has not been confirmed to happen under normal conditions [7](#0-6) . It requires a repository with multiple remotes (e.g. forks with an `upstream` remote, as set up by `addUpstreamRemoteIfNeeded`) and a timing window where the branch's tracked remote and the cached `state.remote` diverge between two independent refresh cycles. This is a real, exploitable race condition, but it depends on natural multi-remote repository states rather than requiring any unusual user action, so likelihood is low-to-moderate and unconfirmed in practice.

### Recommendation
Do not construct `safeRemote` by mixing fields from two independently-sourced remote objects. When `branch.upstreamRemoteName !== remote.name` is detected, either: (1) look up the actual `IRemote` object matching `remoteName` from the currently loaded `remotes` list and use its `url`, or (2) abort the push and force a refresh of remote/tip state before retrying, rather than silently proceeding with a name/URL pair that may not correspond to the same git remote. More broadly, treat "remote name + remote URL must be sourced from the same snapshot" as a hard invariant enforced by a single accessor rather than two independently cached fields.

### Proof of Concept
1. Clone/fork a GitHub repository so an `upstream` remote is auto-added via `addUpstreamRemoteIfNeeded` in addition to `origin` [8](#0-7) .
2. Trigger a scenario where the branch's tracked remote (`branch.upstreamRemoteName`) and the app's cached `state.remote` diverge — e.g., change the branch's upstream remote (`git branch --set-upstream-to=upstream/main`) via an external tool at the moment Desktop is mid-refresh, so `GitStore`'s cached `_currentRemote` (still pointing at `origin`) has not yet been reconciled with the tip's new `upstreamRemoteName` (`upstream`).
3. Trigger a push from Desktop. `performPush` computes `remoteName = 'upstream'` (from branch) but `remote.url` from the stale `origin` `IRemote` object [9](#0-8) .
4. `push()` executes `git push upstream ...` (correct destination) but calls `envForRemoteOperation(originUrl)`, resolving proxy settings for `origin`'s host rather than `upstream`'s [4](#0-3) .
5. If `origin` is attacker-controlled (or resolves to an attacker-influenced proxy), the push's network environment is configured based on the attacker's host, not the legitimate `upstream` target — while telemetry (`remoteNameMismatch`) merely logs the event and lets the push continue.

```typescript
export async function envForProxy(
  remoteUrl: string,
  env: NodeJS.ProcessEnv = process.env,
  resolve: (url: string) => Promise<string | undefined> = resolveGitProxy
): Promise<Record<string, string | undefined> | undefined> {
  const protocolMatch = /^(https?):\/\//i.exec(remoteUrl)

  // We can only resolve and use a proxy for the protocols where cURL
  // would be involved (i.e http and https). git:// relies on ssh.
  if (protocolMatch === null) {
    return
  }

  // Note that HTTPS here doesn't mean that the proxy is HTTPS, only
  // that all requests to HTTPS protocols should be proxied. The
  // proxy protocol is defined by the url returned by `this.resolve()`
  const proto = protocolMatch[1].toLowerCase() // http or https

  // We'll play it safe and say that if the user has configured
  // the ALL_PROXY environment variable they probably know what
  // they're doing and wouldn't want us to override it with a
  // protocol-specific proxy. cURL supports both lower and upper
  // case, see:
  // https://github.com/curl/curl/blob/14916a82e/lib/url.c#L2180-L2185
  if ('ALL_PROXY' in env || 'all_proxy' in env) {
    log.info(`proxy url not resolved, ALL_PROXY already set`)
    return
  }

  // Lower case environment variables due to
  // https://ec.haxx.se/usingcurl/usingcurl-proxies#http_proxy-in-lower-case-only
  const envKey = `${proto}_proxy` // http_proxy or https_proxy

  // If the user has already configured a proxy in the environment
  // for the protocol we're not gonna override it.
  if (envKey in env || (proto === 'https' && 'HTTPS_PROXY' in env)) {
    log.info(`proxy url not resolved, ${envKey} already set`)
    return
  }

  const proxyUrl = await resolve(remoteUrl).catch(err => {
    log.error('Failed resolving Git proxy', err)
    return undefined
  })

  return proxyUrl === undefined ? undefined : { [envKey]: proxyUrl }
}
