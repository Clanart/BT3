### Title
BIP-340 signatures produced without negating the key for odd-Y group keys are invalid, making received funds unspendable - ([File: networks/bitcoin/src/crypto.rs, networks/bitcoin/src/wallet/send.rs])

### Summary
`Schnorr::verify` / the FROST `Algorithm` impl in `networks/bitcoin/src/crypto.rs` only handles BIP-340 parity for the nonce point `R` (negating the challenge in `Hram::hram` and negating `s` when `R` has odd Y). It never handles the *key* parity: BIP-340 requires signing with `-d` when the x-only public key's even-Y lift differs from the actual group key. `SignableTransaction::multisig` in `send.rs` passes `keys.clone().offset(...)` straight into `AlgorithmMachine::new` without any conditional negation. Whenever the tweaked/offset group key has an odd Y coordinate (~50% of keys, including any key produced by `Scanner::register_offset` with a random scalar), the emitted 64-byte signature fails on-chain verification, so the transaction is unspendable.

### Finding Description
- `Hram::hram` binds `x(R)` and `x(A)` and conditionally negates the challenge when `R` is odd-Y (`crypto.rs:59-73`). [1](#0-0) 
- `verify` negates `s` when `sig.R` is odd-Y and strips the sign byte (`crypto.rs:145-149`). This produces an internally-consistent `(R_x, s)` under the raw `group_key`, but BIP-340 verification implicitly uses the even-Y lift of `x(A)`. [2](#0-1) 
- `multisig` builds each input's machine with `keys.clone().offset(self.offsets[i])` and only checks `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — an x-only comparison that ignores parity and never negates `d` (`send.rs:273-285`). [3](#0-2) 
- `Scanner::register_offset` accepts an arbitrary scalar with no parity adjustment, so offset keys are odd-Y half the time.

Result: for any input whose effective tweaked group key is odd-Y, `s = r + c·d` is computed against the wrong sign of `d`; the BIP-340 verifier computes `sG - c·P_even ≠ R`. Analogous to the reported bug (a call whose parameters don't match what the callee expects, so it always reverts), the signature bytes are well-formed but never valid for the key the chain expects — the produced transaction can never be accepted.

### Impact Explanation
Outputs received at an odd-Y tweaked/offset key are unspendable: `TransactionSignMachine::sign` produces signatures that fail `SIGHASH` verification on the Bitcoin network, permanently burning the inputs. This is "funds reported received that are not spendable," a High-severity outcome, reachable purely from public on-chain data (anyone can send to a registered offset address whose key happens to be odd-Y).

### Likelihood Explanation
Key parity is unbiased, so ~50% of generated group/offset keys are affected. `register_offset(Scalar::random)` and any taproot tweak yielding an odd-Y result hit the path deterministically — the failure is not probabilistic per-signature, it fails every time for such keys.

### Recommendation
Before signing in `multisig` (and equivalently for the base key path), conditionally negate the secret material when `needs_negation(group_key)` is true — e.g., apply a scalar of `-1` via `keys.clone().offset(...).scale(<Secp256k1 as Ciphersuite>::F::ZERO - C::F::ONE)` so the effective secret corresponds to the even-Y x-only key. Verify by constructing a `SignableTransaction` spending an output whose tweaked key is odd-Y and checking the witness signature with a BIP-340 verifier.

### Proof of Concept
1. `let offset = scanner.register_offset(Scalar::random(rng))` such that `key + offset·G` is odd-Y (retry until `needs_negation` is true).
2. Receive funds at `p2tr_script_buf(offset_key)`.
3. Build `SignableTransaction::new(vec![output], &payments, None, None, fee)` and sign via `multisig`/`TransactionSignMachine::sign` (`send.rs:373-397`).
4. Submit to a Bitcoin node / BIP-340 verifier: `sG - c·x_only_even(P) ≠ R_x`, so the input script fails and the transaction is rejected — funds at that output are unspendable.

Uncertainty note: I could not inspect `processor/src/networks/bitcoin.rs` (`tweak_keys`, out of the listed in-scope paths) within the available iterations to rule out a parity-normalizing offset being applied upstream; the in-scope wallet code itself (`crypto.rs`, `wallet/send.rs`, `wallet/mod.rs` offset handling) performs no key-parity negation, so the flaw stands within the reviewed surface.

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }

    fn verify(
      &self,
      group_key: ProjectivePoint,
      nonces: &[Vec<ProjectivePoint>],
      sum: Scalar,
    ) -> Option<Self::Signature> {
      self.0.verify(group_key, nonces, sum).map(|mut sig| {
        sig.s = <_>::conditional_select(&sum, &-sum, needs_negation(&sig.R));
        // Convert to a Bitcoin signature by dropping the byte for the point's sign bit
        sig.serialize()[1 ..].try_into().unwrap()
      })
    }

  pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
    let mut sigs = vec![];
    for i in 0 .. self.tx.input.len() {
      let offset = keys.clone().offset(self.offsets[i]);
