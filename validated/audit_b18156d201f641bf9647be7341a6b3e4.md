### Title
Division-by-zero panic in `consolidatedNode.Split` when both CN and CL staking amounts are zero - (File: `kaiax/staking/staking_info.go`)

### Summary
`consolidatedNode.Split`, which apportions block rewards between a validator's CNStaking amount and its Consensus-Liquidity (CL) staking amount, divides by `totalAmount = StakingAmount + CLStakingInfo.CLStakingAmount` without checking that this sum is non-zero. If a validator's CN stake and its registered CL stake are both zero while it still has a `CLStakingInfo` attached (i.e., it remains registered in the CL registry), calling `Split` triggers a `big.Int` division-by-zero panic, which is unconditionally reachable from the normal block-reward finalization path.

### Finding Description
`consolidatedNode.Split` computes: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)  // <-- panics if totalAmount == 0
	...
```

`totalAmount` is only guarded to be non-nil when `CLStakingInfo != nil`; there is no check that `StakingAmount` and `CLStakingInfo.CLStakingAmount` are not both zero. A `consolidatedNode` can legitimately have `StakingAmount == 0` while `CLStakingInfo` is still populated, as confirmed by the repository's own test fixture ("2 nodes under minStaking have CLs", where node `n4` has `StakingAmount = a0 = 0` and a non-nil `CLStakingInfo`): [2](#0-1) 

`CLStakingInfo` attachment in `consolidateNodes()` only requires the node ID to appear in the AddressBook (`nToR`); it does not require any minimum CN or CL stake: [3](#0-2) 

Critically, `Split` is invoked for the block **proposer** in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` **without any staking-amount eligibility check** — it only checks that the proposer's `CLStakingInfo` is non-nil: [4](#0-3) [5](#0-4) 

This differs from the staker-reward distribution paths (`assignStakingRewards`/`assignStakingRewardsFlex`), which only call `Split` after confirming a positive `totalExcess`/eligible stake, so those paths are safe. The proposer path has no such guard, so if the block's proposer (`config.Rewardbase`) corresponds to a consolidated node whose CN stake has fallen to zero (e.g., after normal unstaking via CNStaking contract) while its CL pool also holds zero stake but remains registered in the CL registry (Prague `CLRegistry`), `Split(proposer)` divides by zero and panics.

### Impact Explanation
This code executes during `GetDeferredReward` / `FinalizeState`, i.e., **every block's deterministic state-transition/reward-finalization step** once Prague hardfork rules apply and a CL registry is configured. A panic here is not caught anywhere in the call chain (`getDeferredRewardFullKore`/`getDeferredRewardFullFlex` → `specWithProposerAndFunds(Flex)` → `Split`) — it will crash node processes attempting to finalize the block where the affected validator is the proposer. Because every honest full/consensus node runs the identical deterministic logic, this results in a simultaneous chain-wide halt (all nodes panic while processing the same block), which is a severe availability/liveness impact reachable purely through normal staking/unstaking activity by unprivileged stakers, without any node compromise or malicious validator collusion.

### Likelihood Explanation
Reaching zero CN stake for a registered node is achievable by any staker withdrawing/unstaking their entire CNStaking balance through the standard CNStaking contract flow while the node remains listed in the AddressBook. Achieving simultaneous zero CL stake requires the corresponding CL pool to also be fully withdrawn while remaining registered in `CLRegistry`. Both conditions are driven by ordinary, unprivileged staking transactions rather than any privileged or malicious action, and the repository's own test data demonstrates that `StakingAmount == 0` with a populated `CLStakingInfo` is an expected/handled state elsewhere in the codebase — showing the state is reachable, only the `Split` function (and its safety check) is missing the zero-total guard for the proposer path.

### Recommendation
In `consolidatedNode.Split` (and/or before invoking it from `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`), explicitly check whether `totalAmount.Sign() == 0` and short-circuit — e.g., return `(amount, big.NewInt(0))` or `(big.NewInt(0), big.NewInt(0))` as appropriate — before performing the division, mirroring the zero-denominator guard style recommended for `EmissionManagerV1._calculateRebaseEmission`.

### Proof of Concept
1. Register a validator node `N` in the AddressBook with `RewardAddr = R`, and let `R` be `config.Rewardbase` for a given block (i.e., `N`/`R` is the block proposer).
2. Have the validator fully unstake its CNStaking contract so that `StakingAmounts` for `N` resolves to `0` (`consolidatedNode.StakingAmount == 0`) while `N` remains listed in the AddressBook.
3. Register/keep `N`'s node ID in the Prague `CLRegistry` with a CL pool whose staked amount is `0` (fully withdrawn CL position) so that `CLStakingInfo.CLStakingAmount == 0`, matching the test-verified pattern in `kaiax/staking/staking_info_test.go` lines 151-180 (`a0`/zero StakingAmount with non-nil `CLStakingInfo`).
4. When this validator is selected as the block proposer post-Prague hardfork, `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` calls `specWithProposerAndFunds(Flex)`, which finds `cn.RewardAddr == config.Rewardbase` and `cn.CLStakingInfo != nil`, then calls `cn.Split(proposer)`.
5. Inside `Split`, `totalAmount = 0 + 0 = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with a division-by-zero runtime error, crashing every node finalizing this block.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
