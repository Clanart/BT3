### Title
`SignableTransaction::new` computes weight/fee without the OP_RETURN output, letting user-supplied data produce an under-funded, potentially non-relayable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to a missing `minAmountOut` bound, the transaction builder determines the fee from a weight calculation that excludes the user-controlled `data` (OP_RETURN) output. The signed transaction therefore pays a lower effective fee rate than the caller-specified `fee_per_vbyte`, and the `TooLowFee` check is evaluated against an underestimated vsize. A transaction carrying ~80 bytes of attacker/user-supplied data can pass all checks yet be below the minimum relay fee, leaving the multisig's funds committed to a transaction the network will not relay or confirm.

### Finding Description
`SignableTransaction::new` appends the OP_RETURN output to `tx_outs` (send.rs:194-202) but then computes the transaction weight/vbytes via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204, which builds a template transaction containing *only* `payments` — the OP_RETURN output is never included. Both `needed_fee` (send.rs:206) and the `TooLowFee` minimum-relay check (send.rs:211) use this underestimated `vbytes`. The same omission occurs in the change-branch weight recomputation at send.rs:225-227. An OP_RETURN output costs ~9 + data_len vbytes (up to ~89 vbytes for the 80-byte maximum enforced at send.rs:171). Because `Prevouts::All` and `TapSighashType::Default` commit the signature to the exact output set (send.rs:373-390), the undersized fee cannot be bumped after signing; the entire FROST signing round must be redone with a rebuilt transaction.

### Impact Explanation
The `data` field is populated from untrusted instruction data supplied by the depositor/payment initiator. By attaching a large `data` payload, that party causes the produced transaction to pay materially less than the requested fee rate — including below `DEFAULT_MIN_RELAY_TX_FEE` when `fee_per_vbyte` is near the minimum. The result is a fully signed transaction that Bitcoin nodes reject from the mempool, so the underlying UTXOs are effectively unspendable until the honest signers coordinate a fresh signing round. This is a funds-availability/integrity failure reachable purely by public inputs (the `data` bytes), matching the "user receives a worse outcome than specified with no control" class.

### Likelihood Explanation
Any instruction flow that embeds user data into the OP_RETURN (the `data: Option<Vec<u8>>` parameter) reaches this path; no privileged position is needed. The worst case (fee below relay minimum) requires `fee_per_vbyte` near the relay floor and a near-maximal data payload, which is plausible for refund/forward transactions built at minimum fee; the general case (fee rate lower than requested) is unconditional whenever `data` is present.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either build the template `tx.output` list from the final `tx_outs` (payments + data + change) inside `calculate_weight_vbytes`, or add `data.len()` overhead (`~9 + data_len` vbytes) to the computed vbytes before deriving `needed_fee` and performing the `TooLowFee` check.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte` is chosen so `needed_fee` just passes the `TooLowFee` bound at send.rs:211 using the underestimated `vbytes` (payments-only). The returned transaction contains an extra ~89-vbyte OP_RETURN output, so its real fee rate is `needed_fee / (vbytes + ~89)` — below `DEFAULT_MIN_RELAY_TX_FEE`. Submitting the signed transaction via `sendrawtransaction` on a node with default policy yields a `min relay fee not met` rejection, demonstrating funds committed to an unbroadcastable transaction.
