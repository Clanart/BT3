### Title
Empty aggregate signature verifies successfully - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero `Rs`, and `verify` only checks that its length matches `keys_and_challenges` before evaluating the weighted equation. [1](#0-0) [2](#0-1) 

### Finding Description
When the encoded length is zero and `s` is zero, an attacker can call `verify(dst, &[])`, producing one statement `-0 * G`, which reduces to identity and returns `true`. [3](#0-2)  The aggregation API explicitly refuses to construct an empty aggregate, indicating that zero signatures are not an intended valid state. [4](#0-3) 

### Impact Explanation
An untrusted party can submit bytes decoding to an empty aggregate and have it accepted as a valid aggregated signature without possessing any signer key or nonce. [1](#0-0) [2](#0-1) 

### Likelihood Explanation
The payload is fully attacker-controlled and deterministic: a zero `u32` count followed by the canonical encoding of scalar zero. [1](#0-0)  Exploitation requires a caller to invoke verification for an attacker-supplied aggregate with no expected signature entries, so the impact is medium rather than universal. [2](#0-1) 

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`, and reject empty `keys_and_challenges` even if `Rs` is empty. [1](#0-0) [2](#0-1) 

### Proof of Concept
For a 32-byte scalar field, the serialized forgery is `00 00 00 00` followed by `32` zero bytes; `SchnorrAggregate::read` decodes it as `Rs = []` and `s = 0`, after which `verify(dst, &[])` returns `true`. [1](#0-0) [3](#0-2)
