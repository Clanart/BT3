### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable received funds, enabling an unprivileged miner to lock protocol funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase transaction), and returns matching outputs as ordinary `ReceivedOutput`s. Coinbase outputs are bound by Bitcoin's 100-block maturity rule (consensus rule, `COINBASE_MATURITY`), so any output a miner pays to the scanner's watched script is reported as a received, spendable output while it cannot actually be spent. This is the Serai analog of the "capital committed but unrecoverable/unusable" class: funds are reported received yet are not spendable, with no field on `ReceivedOutput` allowing a downstream consumer to distinguish the coinbase-sourced output.

### Finding Description
`scan_block` calls `scan_transaction` on all of `block.txdata` with no special-casing of the coinbase:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
``` [1](#0-0) 

`scan_transaction` matches only `output.script_pubkey` against the registered script map and immediately constructs a `ReceivedOutput` carrying the outpoint and offset needed to spend it: [2](#0-1) 

`ReceivedOutput` contains only `offset`, `output`, and `outpoint` — nothing records that the outpoint belongs to a coinbase transaction: [3](#0-2) 

The only mitigation is a doc comment stating "a post-processing pass is needed," but the API gives the caller no way to perform that pass from the returned data alone — a `ReceivedOutput` for a coinbase output is byte-identical in shape to a normal one, and `ReceivedOutput::read`/`write`/`serialize` round-trip it the same way: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged miner can include a coinbase output paying to any of the scanner's watched Taproot scripts (the base key script or any registered offset). `scan_block` then reports it as a spendable `ReceivedOutput`. If the coordinator selects it as an input to a threshold-signed transaction, the resulting spend is consensus-invalid for 100 blocks — the signed transaction is rejected by the network and the fee/change plan built on that input fails. Repeated across successive blocks, a miner can keep poisoning the output set. This is "funds reported received that are not spendable," a per the validation criteria an accepted impact class.

### Likelihood Explanation
Any miner can do this whenever they win a block, at zero cost beyond the coinbase output value itself (which they can pay to a key they do not control only if willing — more realistically, natural protocol addresses receiving coinbase donations/dust occur organically). Reaching the buggy path requires only that the integrator use the convenient `scan_block` API rather than manually slicing `block.txdata[1 ..]`, which is the path of least resistance.

### Recommendation
Have `scan_block` skip `block.txdata[0]`, or better, add a `is_coinbase`/`maturity` flag to `ReceivedOutput` (persisted in `write`/`read`) so consumers can enforce maturity policy. Alternatively, take the block height as a parameter and annotate each output with its confirmation/maturity status.

### Proof of Concept
1. Protocol registers key `K` via `Scanner::new` (and optionally offsets via `register_offset`), producing script set `scripts`.
2. An unprivileged miner wins block `B`. In `B.txdata[0]` (the coinbase), they add an output `{ value: v, script_pubkey: p2tr_script_buf(K) }`.
3. The integrator calls `scanner.scan_block(&B)`; the coinbase output is returned as a `ReceivedOutput { offset: ZERO, output, outpoint }` indistinguishable from a spendable output.
4. The coordinator builds a transaction spending that outpoint and runs the FROST `Schnorr` signing flow over its sighash.
5. The fully signed transaction is broadcast and rejected by every node: coinbase outputs are immature until `B + 100`. The protocol's signed transaction is unusable and the reported "received" funds are locked.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
