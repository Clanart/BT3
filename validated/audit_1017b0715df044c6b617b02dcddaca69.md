Confirmed: `discardChanges` in `git-store.ts` computes the on-disk path via plain `Path.resolve`/`Path.join` (no symlink-aware containment check), while other newer code paths in the same codebase (`resolveWithin` in `app/src/lib/path.ts`, used at `app-store.ts:7233` and `dispatcher.ts:1963`) explicitly call `realpath` on both the root and the resolved path to defeat symlink escapes. This inconsistency is the exploitable gap.

### Title
Symlink-based path traversal in Discard Changes allows file deletion/exfiltration outside the repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` resolves the on-disk location of a file to discard using `Path.resolve(this.repository.path, file.path)` (trash path) and `Path.join(this.repository.path, file.path)` (permanent-delete fallback), where `file.path` is a value reported by `git status` for the working directory of a repository the user cloned/checked out. Unlike other sensitive path-consuming code in this codebase, `discardChanges` never validates that the final resolved path stays inside the repository once symlinks are taken into account.

### Finding Description
`file.path` originates from parsing `git status --porcelain=v2` output in `app/src/lib/status-parser.ts` (e.g. `parseUntrackedEntry`, `parseChangedEntry`), which is then turned into a `WorkingDirectoryFileChange` by `buildStatusMap` in `app/src/lib/git/status.ts`. Git happily reports untracked/modified paths that traverse through a symlinked directory that is itself tracked/checked out inside the repository (e.g. a tracked symlink `evil -> /Users/victim/Documents` combined with an untracked file `evil/notes.txt`). Such a symlink can be committed by anyone and delivered to a victim simply by them cloning or fetching/checking out a branch of a malicious repository.

When the user selects that file in the Changes list and chooses "Discard Changes", `discardChanges` (`app/src/lib/stores/git-store.ts:1545-1584`) does:
```
await this.shell.moveItemToTrash(
  Path.resolve(this.repository.path, file.path)
)
```
`Path.resolve` performs purely lexical resolution: it never dereferences the intermediate `evil` symlink, so the string `"<repoPath>/evil/notes.txt"` is syntactically "inside" the repo, but the OS will actually operate on `/Users/victim/Documents/notes.txt` when the trash operation (or the `rm` fallback for the "no confirmation" / trash-failure path) opens/removes it.

This is exactly the class of bug that `resolveWithin` (`app/src/lib/path.ts:36-72`) was built to prevent — it calls `realpath` on both the repository root and the candidate path and rejects the result if the *real* path escapes the root. That helper is already used to guard `copilotConflictResolution` writes (`app/src/lib/stores/app-store.ts:7233`) and `openRepositoryFromUrl`'s "show in folder" action (`app/src/ui/dispatcher/dispatcher.ts:1963`), showing the project is aware of this attack surface — but `discardChanges` was never updated to use it.

The underlying invariant that is broken: "Discard Changes only ever touches files inside the user's repository." A malicious repository controls exactly the primitive needed to violate that invariant (a tracked symlink plus a reported untracked/modified path underneath it), and no existing guard (`resolveWithin`, submodule check, or realpath comparison) is applied on this path.

### Impact Explanation
Discarding what appears to be a harmless untracked/modified file inside a freshly cloned repository can actually cause GitHub Desktop to move an arbitrary file the OS user can access (SSH keys, `.aws/credentials`, other project files, etc.) to the trash, or — in the "always discard permanently" configuration, or when trash fails and the user previously accepted the "discard permanently" prompt — permanently delete it via `rm(Path.join(...))`. This is silent destructive file access outside the repository directory triggered purely by opening/interacting with an attacker-supplied repository, matching the "file write/delete outside the repo" impact class.

### Likelihood Explanation
The only actions required are: clone or fetch a malicious repository (a completely normal Desktop workflow), see the crafted symlink+file show up as changes, and click "Discard changes" — the default and most common remediation action a user takes on unwanted/unexpected changes. No admin rights, local pre-existing malware, or unnatural steps are needed.

### Recommendation
In `app/src/lib/stores/git-store.ts`, replace the raw `Path.resolve`/`Path.join` calls in `discardChanges` with `resolveWithin(this.repository.path, file.path)` (and the equivalent for `file.status.oldPath`), skipping/erroring on any file whose resolved real path escapes the repository root, mirroring the guard already applied in `copilotConflictResolution` and `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates and pushes a repository containing a tracked symlink `evil` pointing to a sensitive directory (e.g. `..` several levels up to the user's home directory, or an absolute path outside common clone locations) and commits it.
2. Victim clones the repository with GitHub Desktop and, in a follow-up commit/fetch, an untracked file appears to `git status` as `evil/id_rsa` (or similar) because the attacker also drops a file with that name inside the symlinked target on the victim's machine through a separate script, OR the attacker simply relies on an existing file already present under the symlink target on the victim's disk being reported as "modified/untracked" once the symlink is checked out.
3. Victim opens the Changes tab, sees `evil/id_rsa` listed, and clicks "Discard Changes" (a routine cleanup action).
4. `GitStore.discardChanges` executes `Path.resolve(repoPath, "evil/id_rsa")`, which the OS/Electron trash API resolves through the symlink, and moves/deletes the *real* file outside the repository — with the victim believing they only discarded a repo-local change. async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
