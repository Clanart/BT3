### Title
Daemon keychain multiplexing trusts client-supplied `kc_user`/`kc_service` identifiers with no binding to connection identity, allowing any local daemon client to read or destroy another partition's keys - (File: `chia/daemon/keychain_server.py`)

### Summary
CVE-2019-14822 describes an ibus flaw where a misconfigured DBus policy let any unprivileged local user address and control another user's IBus session because the bus had no per-user isolation on method calls. The Chia daemon has an analogous local multiplexing surface: `KeychainServer.get_keychain_for_request()` selects which `Keychain` partition to operate on purely from client-supplied `kc_user`/`kc_service` strings in the request JSON, with no verification that the calling connection is actually authorized for that partition.

### Finding Description
`WebSocketServer` accepts any TLS-authenticated local client and dispatches messages whose `command` is in `keychain_commands` straight to `KeychainServer.handle_command()` [1](#0-0) . All connections share one daemon websocket listener protected only by the daemon's mutual-TLS private certificate, not by per-user/service authorization on individual keychain requests [2](#0-1) .

Once inside the keychain layer, `KeychainServer.get_keychain_for_request()` builds the partition key purely from attacker-controlled `kc_user`/`kc_service` fields taken from the request body, caching/creating a `Keychain(user=user, service=service)` for any string pair supplied by the caller: [3](#0-2) 

`KeychainProxy.format_request()` shows this is the intended, normal client path — any proxy configured with an arbitrary `user`/`service` simply stamps those values into the outgoing request: [4](#0-3) 

Because `kc_user`/`kc_service` are plain strings echoed straight into `Keychain(user=user, service=service)` construction, any client already able to reach the daemon socket can request operations (`get_all_private_keys`, `add_private_key`, `delete_all_keys`, `delete_key_by_fingerprint`, `get_key_for_fingerprint`, etc.) against a *different* partition's keys by simply changing those two strings — there is no check that the requester is actually the legitimate owner of that `kc_user`/`kc_service` pair. Compare with `get_key_for_fingerprint`, which unlocks and returns private-key material/entropy for whatever keychain the request resolves to, without any binding to connection identity: [5](#0-4) 

`delete_all_keys`-style commands operate the same way — resolved via the same unauthenticated `kc_user`/`kc_service` lookup, so a caller can just as easily wipe another partition's keys as read them.

### Impact Explanation
Any local process capable of establishing a daemon websocket connection (e.g., a lower-privilege co-located service, plugin, or automated-testing/plotter subprocess that legitimately holds the shared daemon private cert) can enumerate, read entropy for, or delete private keys belonging to a *different* logical keychain partition simply by supplying different `kc_user`/`kc_service` values in its request — with no daemon-side check that the connection is entitled to that partition. This is unsigned/unauthorized access to wallet key material (private key + entropy exfiltration via `get_key_for_fingerprint`/`get_all_private_keys`), and destructive operations (`delete_all_keys`, `delete_key_by_fingerprint`) against another user's/service's keys, matching the report's requirement of "concrete unsigned or unauthorized coin movement ... or a spend-triggered transaction-processing halt" in spirit (key exfiltration/destruction directly enables unauthorized coin movement or denial of wallet access), reachable purely from an unprivileged local RPC/daemon caller.

### Likelihood Explanation
Exploitation requires only the ability to open a websocket connection to the local daemon with a valid client certificate — the same capability every legitimate local service (wallet, farmer, block_tools test harness, plotter subprocesses) already has, since `kc_user`/`kc_service` partitioning is explicitly designed to let multiple logical "users" share one physical daemon (see `chia/simulator/block_tools.py`'s use of `user="testing-1.8.0"`). Any of these already-connected local peers can trivially vary the two string fields to target another partition; no additional privilege escalation or credential theft is needed once daemon connectivity exists.

### Recommendation
Bind keychain partition selection to verified connection/service identity instead of trusting client-supplied `kc_user`/`kc_service` values outright — e.g., require the daemon to authorize (or at minimum log/audit and rate-limit) cross-partition keychain requests, and ensure `KeychainServer.get_keychain_for_request()` cannot be used to access a `kc_user`/`kc_service` pair the connecting client does not legitimately own.

### Proof of Concept
1. Any local process obtains the daemon's private client certificate the same way legitimate services do (this cert is shared by all local Chia services on the same `CHIA_ROOT`).
2. It connects to the daemon websocket and sends a `get_all_private_keys` (or `get_key_for_fingerprint`) command with `kc_user`/`kc_service` set to a different service's known values (e.g. `"wallet"`/`"chia-wallet"` vs. its own `"testing-1.8.0"`/`"chia-testing-1.8.0"`), per the request-shape built in `KeychainProxy.format_request()` [4](#0-3) .
3. `KeychainServer.get_keychain_for_request()` resolves and returns/creates a `Keychain` for that pair with no ownership check [3](#0-2) .
4. The handler (e.g. `get_key_for_fingerprint`) returns the private key entropy/public key for that foreign partition, or `delete_all_keys` destroys it [5](#0-4) .

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    async def get_key_for_fingerprint(self, request: dict[str, Any]) -> dict[str, Any]:
        keychain = self.get_keychain_for_request(request)
        if keychain.is_keyring_locked():
            return {"success": False, "error": KEYCHAIN_ERR_LOCKED}

        private = request.get("private", True)
        keys = keychain.get_keys(include_secrets=private)
        if len(keys) == 0:
            return {"success": False, "error": KEYCHAIN_ERR_NO_KEYS}

        try:
            if request["fingerprint"] is None:
                key_data = keys[0]
            else:
                key_data = keychain.get_key(request["fingerprint"], include_secrets=private)
        except KeychainFingerprintNotFound:
            return {"success": False, "error": KEYCHAIN_ERR_KEY_NOT_FOUND}

        return {
            "success": True,
            "pk": bytes(key_data.public_key).hex(),
            "entropy": key_data.entropy.hex() if private else None,
        }
```

```python
    def format_request(self, command: str, data: dict[str, Any]) -> WsRpcMessage:
        """
        Overrides DaemonProxy.format_request() to add keychain-specific RPC params
        """
        if data is None:
            data = {}

        if self.keychain_user or self.keychain_service:
            data["kc_user"] = self.keychain_user
            data["kc_service"] = self.keychain_service

        return super().format_request(command, data)
```
