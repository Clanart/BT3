## Summary

The Telcoin `StakingModule` bug is about a component (a "plugin") whose external code is required to succeed for a larger state-machine operation to proceed. When that external code becomes malicious/broken, and the module has already begun mutating state before calling it, the mutation cannot be undone and the whole flow gets stuck/corrupted.

Cosmos EVM's `x/erc20` IBC middleware has a structurally identical pattern: it invokes an externally-owned, permissionlessly-registered ERC20 contract to complete a Coin↔ERC20 conversion in the middle of an already-committed IBC receive, without wrapping the multi-step conversion in an isolated/cached context and without the same self-destruct/liveness guard that the msg-server conversion path uses.

### Title
Irreversible escrow of IBC-received coins when native ERC20 auto-conversion fails mid-flight in `OnRecvPacket` - (File: x/erc20/keeper/ibc_callbacks.go)

### Finding Description
`x/erc20/ibc_middleware.go`'s `OnRecvPacket` first lets the underlying ICS20 transfer app credit the recipient (this already commits a real bank-balance mutation), then unconditionally hands off to `k.keeper.OnRecvPacket`, whose returned acknowledgement **overwrites** the original success ack: [1](#0-0) 

Inside the keeper's `OnRecvPacket`, for the "native ERC20" case, it calls `k.MintingEnabled` and then directly `k.ConvertCoinNativeERC20`, with **no check** that the target ERC20 contract still has code (self-destructed) — unlike the message-server conversion paths: [2](#0-1) 

Compare this to `ConvertERC20`/`ConvertCoin` in the msg server, which explicitly guard against a self-destructed/broken native ERC20 contract by deleting the token pair *before* attempting any state mutation: [3](#0-2) 

`ConvertCoinNativeERC20` itself performs the escrow step (`SendCoinsFromAccountToModule`) **before** attempting the EVM call that unescrows the ERC20 token and **before** burning the escrowed coin: [4](#0-3) [5](#0-4) 

None of this sequence is wrapped in `ctx.CacheContext()` (unlike the separate `x/ibc/callbacks` module, which explicitly uses a cached context specifically to keep EVM callback failures from corrupting outer state): [6](#0-5) 

Because `x/erc20`'s `OnRecvPacket` runs on the raw `ctx`, if `ConvertCoinNativeERC20` fails after the `SendCoinsFromAccountToModule` escrow step but before the compensating `CallEVM("transfer", ...)`/`BurnCoins` complete — e.g., because the native ERC20 contract (registered permissionlessly, per `params.PermissionlessRegistration`) has since self-destructed, been paused, or otherwise made to revert its `transfer` — the escrow mutation is **not rolled back**, while the function returns an error that becomes the final Acknowledgement for the whole packet: [7](#0-6) 

An error acknowledgement causes the **source** chain to refund the original sender (treating the transfer as failed), while on **this** chain the recipient's coin has already been irreversibly moved into the `erc20` `ModuleName` account with no corresponding ERC20 issued and no burn performed — i.e., the value is duplicated: the sender gets it back on the source chain, and an equivalent amount sits permanently trapped in this chain's `erc20` module account, since nothing subsequently retries or refunds the trapped coins.

### Impact Explanation
This breaks the 1:1 accounting invariant between native Cosmos coins and their ERC20 representation, mediated across IBC escrow: value becomes duplicated across chains (refunded to the sender on the source chain while irreversibly stuck in the destination chain's erc20 module account), and the trapped Coins are permanently frozen with no code path to recover or reprocess them. This matches the "Critical unauthorized duplication... across native balances... IBC escrows" and "Critical permanent freezing... of escrowed assets... or token-pair-backed balances" impact classes.

### Likelihood Explanation
Registration of native ERC20 token pairs is permissionless by default (`PermissionlessRegistration`), so any unprivileged user can register an ERC20 contract they fully control, convert coins into it, route them through an IBC round-trip (a normal, permissionless IBC flow between any two chains/channels), and then make their own contract's `transfer` revert or self-destruct the contract right before the return packet is processed — deterministically triggering the failure window described above.

### Recommendation
- In `x/erc20/keeper/ibc_callbacks.go` `OnRecvPacket` (and the corresponding `OnAcknowledgementPacket`/`OnTimeoutPacket`/`ConvertCoinToERC20FromPacket` paths), add the same self-destruct/`HasCodeHash` liveness check used in `ConvertERC20`/`ConvertCoin` before attempting `ConvertCoinNativeERC20`.
- Execute the escrow + EVM transfer + burn sequence inside a `ctx.CacheContext()` (as already done in `x/ibc/callbacks/keeper/keeper.go`) and only call the write-back function if every step succeeds, so a failed conversion leaves the pre-conversion coin balance intact for the recipient rather than losing it in the module account.

### Proof of Concept
1. With `PermissionlessRegistration` enabled, an attacker deploys a native ERC20 contract with a `transfer` function they can make revert (e.g., pausable) or that they can self-destruct.
2. Attacker registers it via `MsgRegisterERC20`, mints/owns tokens, and converts some to the Cosmos coin representation via `MsgConvertERC20` (escrowing ERC20 tokens in the erc20 module account, minting Coins to themselves).
3. Attacker IBC-transfers the Coins to another chain/channel they control (or simply back to themselves through a round trip), so a return packet will hit `OnRecvPacket` case 2 (native ERC20) on this chain.
4. Before the return packet is relayed/received, attacker pauses/self-destructs their ERC20 contract.
5. When `OnRecvPacket` executes: the standard ICS20 transfer credits the coin to the recipient (attacker) — then `k.keeper.OnRecvPacket` → `ConvertCoinNativeERC20` escrows that coin into the `erc20` module account, then `CallEVM("transfer", ...)` fails because the contract is dead/paused, and the function returns an error, becoming the final acknowledgement for the packet.
6. The source chain sees the error ack and refunds the sender their original amount, while on this chain, the escrowed coin sits permanently in the `erc20` module account with no burn and no ERC20 issued — value has been duplicated and part of it is now permanently frozen.

// ConvertERC20 converts ERC20 tokens into native Cosmos coins for both
// Cosmos-native and ERC20 TokenPair Owners
func (k Keeper) ConvertERC20(
	goCtx context.Context,
	msg *types.MsgConvertERC20,
) (*types.MsgConvertERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Error checked during msg validation
	receiver := sdk.MustAccAddressFromBech32(msg.Receiver)
	sender := common.HexToAddress(msg.Sender)

	pair, err := k.MintingEnabled(ctx, receiver, msg.ContractAddress)
	if err != nil {
		return nil, err
	}

	// Check ownership and execute conversion
	if pair.IsNativeERC20() {
		// Remove token pair if contract is suicided
		acc := k.evmKeeper.GetAccountWithoutBalance(ctx, pair.GetERC20Contract())
		if acc == nil || !acc.HasCodeHash() {
			k.DeleteTokenPair(ctx, pair)
			k.Logger(ctx).Debug(
				"deleting selfdestructed token pair from state",
				"contract", pair.Erc20Address,
			)
			// NOTE: return nil error to persist the changes from the deletion
			return nil, nil
		}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}
