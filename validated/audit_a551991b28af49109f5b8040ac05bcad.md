### Title
Destination-side order cancellation can permanently strand escrowed funds with no time-bound recovery path - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2.cancelOrder()` routed through `_cancelFromDest` irreversibly marks a cross-chain order as settled on the destination chain *before* the corresponding `RefundEscrow` message reaches the source chain, and dispatches that message with `timeout: 0`. Because the request never times out, and the destination-side commitment can never be un-set once written, a `RefundEscrow` message that is never delivered leaves the user's escrowed funds locked on the source chain forever, with no time-bound fallback mechanism — the same missing-timelock defect flagged in the external `Perpetual` report, but here it strands unprivileged users' own funds rather than an admin choosing to prolong emergency mode.

### Finding Description
`_cancelFromDest` sets the local "filled" marker immediately, before any cross-chain confirmation of refund exists: [1](#0-0) 

The dispatched `RefundEscrow` `DispatchPost` explicitly sets `timeout: 0`: [2](#0-1) 

On the source chain, `withdraw()` is only invoked once via `onAccept` when the `RefundEscrow`/`RedeemEscrow` message is actually delivered: [3](#0-2) 

The recovery route for a cross-chain order that never gets filled or refunded is `_cancelFromSource`, which relies on proving via a GET response that `_filled[commitment]` is *empty* on the destination: [4](#0-3) 

Because `_cancelFromDest` already wrote a non-zero value into `_filled[commitment]` at the moment of cancellation (independent of whether the `RefundEscrow` message is ever delivered), the source-side non-membership proof will always show the slot as occupied, and `onGetResponse` on the source chain would revert with `Filled()` — permanently blocking the alternate recovery path documented for this exact scenario: [5](#0-4) 

Because the `RefundEscrow` POST is dispatched with `timeout: 0`, ISMP's built-in timeout/refund mechanism (`dispatchTimeOut`, which requires message expiry) never applies to it, so there is no protocol-level time bound after which a user (or anyone) can force the stuck escrow open. This mirrors the `Perpetual` finding precisely: an operation transitions state into a "point of no return" with no fixed duration after which normal recovery resumes — except here the state is `_filled[commitment]` on an unprivileged, per-order basis rather than a global admin-controlled `Status.SETTLING`.

### Impact Explanation
If the `RefundEscrow` message is never delivered (e.g. the caller-supplied `relayerFee` is too low to attract a relayer, the destination-registered gateway instance changes, or delivery simply never completes for any reason), the user's escrowed input tokens on the source chain become permanently unrecoverable:
- `_cancelFromDest` has already committed the order as "settled" on the destination, so no solver can ever fill it and no future retry of the refund dispatch is exposed by the contract.
- `_cancelFromSource` cannot succeed either, since the destination-side `_filled` slot is non-empty, causing state-proof verification to interpret the order as filled and revert.
- There is no timeout, admin sweep, or re-dispatch entrypoint visible in `IntentGatewayV2`/`ExtrinsicIntents` to recover escrow once this specific state combination occurs.

This is a direct loss/lock of user bridge-escrowed funds, matching the "stealing or loss of funds" / "logic attacks" impact category, and is reachable by the order's own owner (or, post-deadline, by any third party) performing a normal, intended action — not by a malicious admin, relayer, or prover.

### Likelihood Explanation
Likelihood depends on the `RefundEscrow` message actually failing to deliver after `_cancelFromDest` has already committed the settlement marker. Given `timeout: 0` there is no automatic recovery even under benign relayer downtime, fee misconfiguration, or destination gateway address changes/misregistration — situations that require no adversarial behavior at all, only an unfavorable but realistic delivery failure. The order owner (or the destination-deadline "anyone" caller) directly controls when this state transition is committed, but does not control whether the subsequent cross-chain delivery succeeds, so the vulnerable window opens on every destination-side cancellation and there is no code path to close it later.

### Recommendation
- Do not treat the destination-side cancellation as final before the refund is durably confirmed; alternatively, allow the `RefundEscrow` dispatch to be retried/re-dispatched if it was never delivered.
- Give the `RefundEscrow` message a real timeout, and implement `onPostRequestTimeout` handling on `IntentGatewayV2` for this message kind so that an undelivered refund still returns control (e.g., re-open the order for a fresh cancellation attempt) rather than becoming permanently unrecoverable.
- Consider allowing the source-side path to also finalize a refund via a governance-independent, permissionless retry mechanism keyed off the destination commitment, decoupled from ISMP delivery guarantees.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2` with source chain A, destination chain B.
2. Order is not filled by any solver before `order.deadline`.
3. Anyone calls `cancelOrder(order, options)` on chain B's `_cancelFromDest`, which sets `_filled[commitment] = order.user` and dispatches a `RefundEscrow` `DispatchPost` to chain A with `timeout: 0` and a caller-chosen `options.relayerFee`. [1](#0-0) 
4. If `relayerFee` is insufficient (or delivery otherwise never completes), no relayer submits the message to chain A; `withdraw()` is never called and the escrow stays locked in the chain-A gateway.
5. The user attempts the alternative recovery route, `_cancelFromSource` on chain A: it dispatches a `DispatchGet` to prove `_filled[commitment]` is empty on chain B, but the slot is already non-empty (set in step 3), so `onGetResponse` reverts with `Filled()`, permanently denying this recovery path. [4](#0-3) 
6. Because the original `RefundEscrow` message was dispatched with `timeout: 0`, no ISMP timeout ever fires to release/re-open the pending request, leaving the user's escrowed tokens on chain A stuck indefinitely with no available function to reclaim them.

Note: I was not able to fully trace how ISMP's core (`evm/src/core/EvmHost.sol` / `HandlerV2.sol`) semantically treats a POST request with `timeout == 0` at the protocol level (whether it is simply "never eligible for `dispatchTimeOut`" or handled some other special way) within the tool budget available, nor did I find an admin/governance sweep function scoped specifically to `IntentGatewayV2` stuck escrows. Confirming the exact `timeout == 0` handling in `HandlerV2.handlePostRequestTimeouts` (`evm/src/core/HandlerV2.sol`) and checking for any hidden admin recovery entrypoint in `IntentGatewayV2`/`IntentsBase` would further substantiate or narrow this finding.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.
