## Title
`resolveWithin` containment check uses a raw string `startsWith` prefix comparison, allowing an attacker-controlled symlink to escape the repository into a sibling directory that shares a name prefix - ([File: app/src/lib/path.ts])

### Summary
`_resolveWithin` in [1](#0-0)  resolves the candidate path, `realpath()`s both the root and the candidate, and then decides containment with `realResolved.startsWith(realRoot)`. This is a classic boundary-check bug: `startsWith` on a bare string, without appending the platform path separator, treats any path whose *string* begins with `realRoot` as "inside" the root — even when it is actually a sibling directory that merely shares a name prefix (e.g. root `/Users/victim/Documents/GitHub/app` vs. an unrelated sibling `/Users/victim/Documents/GitHub/app-secrets`).

### Finding Description
The two `realpath()` calls do correctly resolve symlinks, and the existing unit tests in [2](#0-1)  confirm that a symlink pointing straight to `../..` (i.e., a real ancestor directory) is rejected. However, that test only exercises the "ancestor" case. It does not cover the case where a symlink (or an absolute path segment) resolves to a directory that is a *sibling* of the root but whose name happens to have the root's basename as a literal string prefix.

Because `normalizedRoot`/`realRoot` never has a trailing separator appended before the comparison, `"<root>-suffix/...".startsWith("<root>")` evaluates to `true`, so `_resolveWithin` will happily return a path that lives entirely outside the repository's working tree.

A repository author fully controls the tree contents that a victim clones, including symlinks (per the target's own attacker model: "repository the user merely clones, fetches, checks out, or opens - paths, symlinks..."). By placing a symlink inside the repo (e.g. `escape -> ../<reponame>-something/target-file`), the attacker can cause `resolveWithin(repository.path, 'escape')` to resolve and return a path outside the repository, provided a directory sharing that literal name prefix already exists next to the cloned repo on the victim's disk.

This is used as a security boundary in several sinks:
- [3](#0-2)  — writes Copilot-resolved conflict content to `absolutePath` returned by `resolveWithin`.
- [4](#0-3)  — reads file content from the resolved path to send to the model.
- [5](#0-4)  — calls `shell.showItemInFolder(resolved)` on the resolved path from a deep-link `filepath`.

A minimal reproduction of the underlying string-prefix flaw (independent of any exploit chain):
```ts
const tempDir = await mkdtemp(join(tmpdir(), 'path-test')) // e.g. /tmp/path-testABC123
const siblingDir = tempDir + 'evil'                        // /tmp/path-testABC123evil (NOT under tempDir)
await mkdir(siblingDir)
await writeFile(join(siblingDir, 'secret.txt'), 'top secret')
await symlink(join(siblingDir, 'secret.txt'), join(tempDir, 'escape'))

const result = await resolveWithin(tempDir, 'escape')
// BUG: result !== null, even though siblingDir is not a subdirectory of tempDir
```
Here `realRoot` = `/tmp/path-testABC123` and `realResolved` = `/tmp/path-testABC123evil/secret.txt`; the latter literally starts with the former as a string, so the check incorrectly passes.

### Impact Explanation
If exploited, a caller of `resolveWithin` (e.g. the Copilot conflict resolver's file-write path in `app-store.ts`, or the `Open path in Finder/Explorer` deep-link handler in `dispatcher.ts`) can be tricked into operating on a file outside the intended repository working tree, matching the "arbitrary file write/replace... outside the working tree" impact class described by the target. The write-capable sink (`writeFile(absolutePath, resolution.resolvedContent, 'utf8')` in `app-store.ts`) is the most severe, since it lets attacker-influenced content overwrite a file in a sibling directory.

### Likelihood Explanation
Exploitability is constrained: it requires a directory to already exist on the victim's filesystem, adjacent to the (attacker-named) cloned repository, whose name is a strict superstring-prefix of the repo's directory name (e.g. cloning `app` next to a pre-existing `app-old`, `app2`, `app-secrets`, etc.). The attacker chooses the repository name (and can pick a short/common name to increase the odds of matching an existing sibling on typical developer machines that group many repos in one folder), but they cannot directly choose or guarantee the exact sibling directory name on any given victim's machine. This makes the bug a real containment-check defect and a violation of the stated invariant ("every path Desktop writes, reads, or executes stays inside the selected repository working tree"), but its reliable exploitability depends on filesystem layout coincidence rather than being deterministically triggerable from repository content alone.

### Recommendation
Fix the boundary check to require the separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator matching the `options` passed in, i.e. `Path.win32.sep` / `Path.posix.sep`). Also add a unit test alongside the existing ones in [2](#0-1)  covering the sibling-directory-with-shared-prefix case to prevent regression.
