### Title
Global gasless bundle-queue slot exhaustion via dust-balance approve transactions - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The gasless module (KIP-247) admits a `GaslessApproveTx` into its shared `knownTxs` bundle-queue as soon as it structurally matches the approve pattern and the sender holds a **nonzero** (dust) balance of a whitelisted token. Since the queue-fullness check `numQueue() >= GetMaxBundleTxsInQueue()` is a single global counter shared by every sender, an attacker can cheaply spin up many addresses, each with 1-wei of an allowed token and zero KAIA (native-balance checks are explicitly skipped for gasless txs), submit one dust-value approve tx per address, and saturate the entire global bundle queue. Once full, `PreAddTx` returns `ErrBundleTxQueueFull` for every subsequent legitimate `GaslessApproveTx`/`GaslessSwapTx`, blocking honest users from using the gasless feature at effectively zero cost to the attacker.

### Finding Description
`PreAddTx` gates entry of any tx recognized as a "bundle tx" using a single global counter, not a per-account one: [1](#0-0) 

`IsBundleTx`/`IsModuleTx` only requires the tx to *structurally* match `IsApproveTx` or `IsSwapTx` — token whitelisted, spender is the swap router, amount `== MaxUint256`: [2](#0-1) 

The only "value" gate applied before admission is `checkBalanceForApprove`, invoked via `GetCheckBalance()`, and it merely requires the ERC20 balance to be **strictly greater than zero** — no minimum amount, no dust threshold: [3](#0-2) 

Critically, per the module's own documentation, the normal native-KAIA balance check (which would otherwise force an attacker to fund gas for every spam tx) is *omitted* for gasless transactions, since the proposer is expected to lend the gas via `LendTxGenerator`: [4](#0-3) 

Consequently, an attacker only needs: (1) many addresses, (2) 1 wei of a single whitelisted ERC20 token distributed to each, and (3) an `approve(router, MaxUint256)` call from each address. Each such tx satisfies `isApproveTx` and `checkBalanceForApprove`, gets accepted into `knownTxs` at `TxStatusQueue`, and consumes one of the default 200 global slots (`MaxBundleTxsInQueueFlag` default): [5](#0-4) 

Once `numQueue()` reaches `MaxBundleTxsInQueue`, all further gasless-pattern transactions — including from legitimate users trying to perform a real `swapForGas` — are rejected with `ErrBundleTxQueueFull` by `PreAddTx`, denying them the gasless feature entirely.

This is directly analogous to the reported OpenQ bug: a shared, finite admission "slot" resource (there: token-address-limit per bounty; here: `MaxBundleTxsInQueue` shared across all senders) can be exhausted by an unprivileged actor submitting near-worthless ("dust") value, permanently blocking legitimate use of the feature for everyone else.

### Impact Explanation
This breaks the core promise of KIP-247 gasless transactions: users without any KAIA balance are supposed to be able to submit approve/swap transactions and have gas fronted by the proposer. By flooding the shared queue with dust-value approve transactions from freshly generated, unfunded addresses, an attacker can continuously deny this capability to all legitimate gasless users at negligible cost (no KAIA required at all, and only 1 wei of a whitelisted token per attacking address). This is a protocol-availability/DoS impact on a public-facing feature reachable by any unprivileged transaction sender.

### Likelihood Explanation
High likelihood: the attack requires no privileged access, no compromise of validators/nodes, and no significant capital — only cheap generation of throwaway addresses and negligible amounts of a whitelisted ERC20 token (which the attacker can self-mint/transfer in dust quantities). The gas cost of gasless-pattern approve transactions is itself not required to be paid by the attacker in KAIA since balance checks are bypassed for these transaction types, making sustained, repeated attacks very cheap (each queue entry expires after `QueueTimeout` = 10s, but can be trivially refilled).

### Recommendation
- Enforce a per-sender cap in addition to (or instead of) the global `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` counters in `kaiax/gasless/impl/tx_pool.go`, so a single attacker (or a set of freshly-generated addresses) cannot monopolize the shared queue.
- Require a meaningful minimum token balance/value (not merely `> 0`) in `checkBalanceForApprove`/`checkBalanceForSwap`, or otherwise weight queue admission by some cost/reputation signal (e.g., minimum swap amount, minimum lend amount) rather than treating any nonzero token balance as legitimate.
- Consider requiring some minimal KAIA stake/balance from the sender even for gasless transactions, to raise the cost of generating throwaway spam addresses.

### Proof of Concept
1. Attacker deploys/controls N (e.g. 200, the default `MaxBundleTxsInQueue`) fresh EOAs with zero KAIA balance.
2. Attacker distributes 1 wei of any single governance-whitelisted ERC20 token (`allowedTokens`) to each of the N addresses.
3. From each address, attacker submits `approve(swapRouter, type(uint256).max)` on that token as a legacy transaction.
4. Each transaction passes `IsApproveTx` (structural match) and `checkBalanceForApprove` (`tokenBalance.Sign() > 0` — satisfied by 1 wei), and is admitted to `g.knownTxs` via `PreAddTx`, incrementing `numQueue()`.
5. After N such transactions, `numQueue() >= MaxBundleTxsInQueue`, so `PreAddTx` starts returning `ErrBundleTxQueueFull` for any further `GaslessApproveTx`/`GaslessSwapTx`, including from legitimate gasless users, denying them the gasless swap functionality until the attacker's dust entries expire (`QueueTimeout` = 10s) — at which point the attacker simply resubmits to keep the queue full indefinitely.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (g *GaslessModule) checkBalanceForApprove(approveArgs *ApproveArgs) error {
	token := approveArgs.Token
	bc := backends.NewBlockchainContractBackend(g.Chain, nil, nil)

	if g.GaslessConfig.ShouldCheckSenderCode() {
		if g.getCurrentHasCode(approveArgs.Sender) {
			return errors.New("sender with code is not allowed")
		}
	}

	if g.GaslessConfig.ShouldCheckToken() {
		tokenContract, err := sc_erc20.NewERC20(token, bc)
		if err != nil {
			return err
		}

		// tx.token.balanceOf(sender) > 0
		tokenBalance, err := tokenContract.BalanceOf(nil, approveArgs.Sender)
		if err != nil {
			return err
		}
		if tokenBalance.Sign() <= 0 {
			return fmt.Errorf("insufficient sender token balance: token=%s, have=%s, want=nonzero", token.Hex(), tokenBalance.String())
		}
	}
	return nil

// IsApproveTx checks following conditions:
// A1. tx.to is a whitelisted ERC20 token.
// A2. tx.data is `approve(spender, amount)`.
// A3. spender is a whitelisted SwapRouter contract.
// A4. amount is MaxUint.
func (g *GaslessModule) IsApproveTx(tx *types.Transaction) bool {
	args, ok := decodeApproveTx(tx, g.signer)
	return ok && g.isApproveTx(args)
}

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}
