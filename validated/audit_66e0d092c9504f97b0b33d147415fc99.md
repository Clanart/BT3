### No vulnerability found for this question.

Analysis confirms the described behavior is expected/safe, not a vulnerability. In `TokenVesting.sol`, `vestedAmount(ts, receiver)` computes a cumulative `percentSum` over all schedule indices up to `_releasableIdx(ts)` [1](#0-0) , and `getClaimable` simply subtracts the beneficiary's cumulative `released` amount from this vested total [2](#0-1) . `release()` immediately adds the full `claimable` to `_beneficiary.released` before any subsequent call can execute [3](#0-2) .

Because `released` tracks the cumulative amount ever paid out (not per-schedule-index), a second `release()` call at the same timestamp/index computes `vestedAmount(ts) - released`, which equals `vestedAmount(ts) - vestedAmount(ts) = 0` since `vestedAmount` did not change (same `ts`, same `_releasableIdx`). This is exactly the conservation property the question itself describes as the expected/tested invariant — no double payout occurs.

Regarding the underflow concern for `_releasableIdx(ts) < 0`: `block.timestamp` is monotonically non-decreasing across blocks, so an attacker cannot make `ts` regress below a previously-crossed `_schedule[0]` entry after `released > 0` has been set. Thus the "getClaimable returning 0 before schedule[0]" and "full first-tranche after crossing schedule[0]" scenario is simply correct, sequential vesting behavior — not an underflow or double-claim exploit. There is no reachable path for an unprivileged attacker to extract more than their entitled vested amount via repeated or reordered `release()` calls.

    function vestedAmount(uint256 ts, address receiver) public view returns (uint256) {
        int256 unreleasedIdx = _releasableIdx(ts);
        if(unreleasedIdx < 0) return 0;
        
        uint256 percentSum = 0;
        for (uint256 i = 0; i <= uint256(unreleasedIdx); i++) {
            percentSum += _percent[i];
        }

        return _beneficiaries[receiver].amount * percentSum / DENOMINATOR;
    }
