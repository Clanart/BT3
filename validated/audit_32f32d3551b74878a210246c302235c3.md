### Title
OP_RETURN data output is omitted from fee/weight calculation, so transactions carrying `data` underpay the intended fee rate and may fall below the minimum relay fee — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Allo `baseFee` boundary bug (a fee check that does not account for everything the payer must cover), `SignableTransaction::new` computes the transaction weight and required fee using only the payment outputs. The OP_RETURN output created from the `data` argument is pushed into `tx_outs` but is never included in `calculate_weight_vbytes`, so the computed `needed_fee` (and the minimum-relay-fee check) are based on a smaller transaction than the one actually signed and broadcast.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` when `data` is provided:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
```

However, both weight calculations ignore it:

- `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);` (line 204)
- `Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226)

`calculate_weight_vbytes` builds its template transaction solely from `payments` and the optional change output — it never receives `tx_outs`, so the OP_RETURN output's bytes (roughly 9 + `data.len()` serialized bytes, up to ~89 bytes for the maximum 80-byte payload) are excluded. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` is computed on an underestimated `vbytes`, so the transaction pays less than the caller-requested fee rate.
2. The minimum relay fee check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` uses the same underestimated `vbytes`, so a transaction whose *actual* fee rate is below the relay minimum can pass this check and be produced.
3. The change decision `input_sat.checked_sub(payment_sat + fee_with_change)` uses the underestimated `fee_with_change`, so a change output may be created with more sats than truly remain after paying the requested rate — but since `fee = inputs - outputs` regardless, the change itself is what shrinks; the payment amounts are still honored.

Any unprivileged caller of `SignableTransaction::new` who supplies `data` (a public input — arbitrary bytes up to 80 bytes) triggers this; the resulting transaction is then signed by the FROST `TransactionMachine` as-is.

### Impact Explanation
A transaction created with `data` systematically pays a lower effective fee rate than `fee_per_vbyte` requested. At the margin — when `fee_per_vbyte` is chosen near the relay minimum — the produced transaction will be below `DEFAULT_MIN_RELAY_TX_FEE` for its real vsize and will not relay, or will be stuck in mempools until fees drop. Since Serai signs these transactions via an interactive threshold protocol, a non-propagating transaction can strand the spent inputs: the prevouts are consumed as far as signers are concerned, and funds are effectively locked until a replacement is constructed and re-signed. This is the same bug class as the external report — the fee accounting does not match what the transaction actually costs the payer — except here it under-reserves the fee rather than over-charging it.

### Likelihood Explanation
Any usage of the `data` parameter hits this deterministically; the fee shortfall scales with `data.len()`. Whether it causes a relay failure depends on how close the chosen fee rate is to the minimum, but the paid rate is always strictly lower than requested, and the change output is correspondingly inflated/deflated relative to the intended rate.

### Recommendation
Include the OP_RETURN output in the weight template. Either pass the finalized `tx_outs` (or `payments` plus the OP_RETURN `ScriptBuf`) into `calculate_weight_vbytes`, or compute the OP_RETURN output's weight separately and add it to `weight`/`vbytes` before deriving `needed_fee`. Apply the same correction to the `fee_with_change` path.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with a data payload
let payments = vec![(dest_script, 10_000)];
let data = Some(vec![0xaa; 80]); // max allowed payload
let st = SignableTransaction::new(inputs, &payments, Some(change_script), data, fee_per_vbyte)
  .unwrap();

// The produced transaction includes an OP_RETURN output (~89 bytes, ~89+ WU),
// but needed_fee() was computed from a template without it:
assert_eq!(st.transaction().output.len(), payments.len() + 2); // payment + OP_RETURN + change
// st.needed_fee() == fee_per_vbyte * vbytes(template_without_op_return)
// Actual fee paid == st.fee(), which equals the underestimated needed_fee only
// because change absorbs the difference; the effective sat/vbyte rate is below
// fee_per_vbyte and can fall under DEFAULT_MIN_RELAY_TX_FEE.
```
