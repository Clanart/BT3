### Title
Fee-on-transfer / non-standard ERC20 tokens cause under-collateralized bridge value transfer requests, enabling supply inflation on the counterpart chain - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
`BridgeTransferERC20.requestERC20Transfer()` pulls the nominal `_value + _feeLimit` from the caller via `safeTransferFrom`, but never verifies that the bridge contract actually received that exact amount. It then proceeds to record/emit a `RequestValueTransfer` event carrying the *nominal* `_value`, which the counterpart bridge later honors 1:1 in `handleERC20Transfer` — either by minting `_value` new tokens (mint/burn mode) or transferring `_value` out of its token reserve (lock/release mode). For any ERC20 token that deducts a fee or otherwise delivers less than the requested amount on `transferFrom` (deflationary/fee-on-transfer/rebasing tokens, which are explicitly the class of token this report's bug class targets), the bridge will have received strictly less than `_value + _feeLimit`, yet will commit to release/mint the full `_value` on the other side.

### Finding Description
`requestERC20Transfer` is a `public` function reachable by any unprivileged EOA that has approved the bridge for the token:

```solidity
function requestERC20Transfer(...) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

`safeTransferFrom` only reverts if the ERC20 call itself reverts or returns `false`; it does not check the resulting balance delta of the bridge contract. `_requestERC20Transfer` then unconditionally treats `_value` as the ground truth: it pays/refunds fee using `_payERC20FeeAndRefundChange` (which itself blindly `safeTransfer`s `_feeLimit`/`fee` amounts back out, further depleting whatever was actually deposited), optionally burns `_value` in mint/burn mode, and emits `RequestValueTransfer(..., _value, ..., fee, ...)`. [2](#0-1) [4](#0-3) 

The counterpart bridge's operators later call `handleERC20Transfer` using the `_value` recorded from the `RequestValueTransfer` event, and — since token registration (`onlyRegisteredToken`) does not validate that a token is a compliant, fee-free, non-rebasing ERC20 — will either mint `_value` fresh tokens or release `_value` from its own token reserve to `_to`:

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [5](#0-4) 

Because the deposit side never measures `balanceBefore`/`balanceAfter` to determine the actually-received amount, a discrepancy between the amount promised (`_value`) and the amount actually escrowed/burned is silently created whenever the registered token applies any transfer fee or non-1:1 transfer semantics.

### Impact Explanation
In mint/burn mode, this results in unconstrained cross-chain token supply inflation: the counterpart chain mints `_value` tokens for every request, while the source chain never actually collected/burned that full amount, permanently inflating total token supply relative to backing. In lock/release mode, repeated requests using a fee-on-transfer token progressively drain the bridge's real token reserve below what it has promised to release to legitimate `_to` recipients on the other chain, eventually causing insolvency/DoS for other bridge users who cannot redeem their locked value. Any bridge operator that registers a fee-on-transfer, rebasing, or otherwise non-standard ERC20 as a bridged token (a normal, permissionless `registerToken`-style operation many bridges perform for community tokens) exposes the bridge to this unauthorized value creation, reachable purely by ordinary unprivileged senders calling the public `requestERC20Transfer`/`onERC20Received` entry points.

### Likelihood Explanation
Likelihood is high wherever a fee-on-transfer or rebasing token is registered on the bridge, since triggering the bug requires nothing more than calling the already-public `requestERC20Transfer` with a normal token approval — no special privileges, timing, or race conditions are needed. The severity is directly proportional to the registered token's transfer fee percentage and transfer volume.

### Recommendation
In `requestERC20Transfer` (and `onERC20Received`), measure the bridge contract's actual token balance before and after the `transferFrom`/receipt, and use that balance delta (not the caller-supplied `_value`/`_feeLimit`) as the amount that is subsequently burned, fee-deducted, and emitted in `RequestValueTransfer`. Alternatively, restrict `onlyRegisteredToken` to explicitly disallow tokens whose `transferFrom` does not deliver the exact requested amount (e.g., via a self-test on registration), consistent with the referenced Gearbox `PoolService` fix of using balance differences instead of the nominal transfer amount.

### Proof of Concept
1. Deploy (or select) a fee-on-transfer ERC20 token `T` that deducts, e.g., 1% on every `transfer`/`transferFrom`, and register it on `BridgeTransferERC20` via the token registration flow.
2. An unprivileged user `Alice` approves the bridge for `1000` `T` and calls `requestERC20Transfer(T, aliceOnOtherChain, 1000, 0, "")`.
3. `safeTransferFrom(Alice, bridge, 1000)` moves `1000` nominal tokens, but the bridge's actual `T` balance only increases by `990` due to the token's built-in fee — this is never checked.
4. `_requestERC20Transfer` proceeds using `_value = 1000`; if `modeMintBurn` is true, `ERC20Burnable(T).burn(1000)` is invoked (burning more `T` than the bridge net-received, further depleting reserves elsewhere), and `RequestValueTransfer(..., 1000, ...)` is emitted.
5. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer(..., 1000, ...)`, which either mints `1000` new `T` tokens to `aliceOnOtherChain` (mint/burn mode) or releases `1000` `T` from the counterpart bridge's own reserve (lock/release mode) — in both cases `10` tokens' worth of value is created/released without having been actually backed by Alice's deposit, repeatable indefinitely to drain reserves or inflate supply.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
