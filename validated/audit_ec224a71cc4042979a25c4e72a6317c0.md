### Title
Out-of-range blame participant causes unauthenticated panic - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`AdditionalBlameMachine::blame` accepts attacker-controlled `sender` and `recipient` participant IDs without checking that they are within `1 ..= n`. [1](#0-0) 

### Finding Description
`AdditionalBlameMachine::new` only registers encryption keys for participants `1 ..= n`. [2](#0-1)   
`blame` passes caller-supplied `sender` and `recipient` values directly to `blame_internal`. [1](#0-0)   
For a validly signed encrypted message and any deserializable proof, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` when constructing the DLEQ verification points. [3](#0-2)   
If `recipient` is `Participant::new(n + 1)`, the `HashMap` indexing panics instead of returning `InvalidProof`, crashing the task or process handling the blame message. [3](#0-2) 

### Impact Explanation
An unprivileged party can serialize an `EncryptedMessage` with a fresh ephemeral key and valid proof-of-possession, then invoke blame resolution with an out-of-range recipient to trigger a deterministic panic. [4](#0-3) [5](#0-4)   
This is a remotely reachable denial of service analogous to the mvfst “packet of death”: public message bytes cause a failed invariant lookup rather than being handled as a protocol error. [3](#0-2) 

### Likelihood Explanation
The attacker does not need a valid DLEQ proof or a valid secret share; the out-of-bounds map lookup occurs before `dleq.verify` is invoked. [3](#0-2)   
The only substantive requirement is an `EncryptedMessage` whose Schnorr proof-of-possession verifies under the attacker-selected `sender` in the bound challenge. [6](#0-5) [5](#0-4) 

### Recommendation
Validate `sender` and `recipient` in `BlameMachine::blame`, `AdditionalBlameMachine::blame`, or `blame_internal` before calling `decrypt_with_proof`, returning a typed `PedPoPError` for IDs outside `1 ..= n`. [7](#0-6) [1](#0-0)   
Also replace indexing such as `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with checked `get` accesses so malformed accusations cannot panic. [3](#0-2) [8](#0-7) 

### Proof of Concept
```rust
// Assume n = 3 and `machine` was built with commitment messages for 1..=3.
let sender = Participant::new(1).unwrap();
let invalid_recipient = Participant::new(4).unwrap();

// Serialize/read an EncryptedMessage containing:
//   key = G * k
//   pop = valid SchnorrSignature for `k` under pop_challenge(context, R, key, sender, msg)
//   msg = arbitrary SecretShare-sized bytes
let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(
    &mut attacker_controlled_bytes,
    params,
).unwrap();

// Any syntactically valid proof suffices because evaluation panics before DLEQ verification.
let proof = Some(
    EncryptionKeyProof::<C>::read(&mut attacker_controlled_proof_bytes).unwrap()
);

// Panics at self.enc_keys[&decryptor] because participant 4 was never registered.
machine.blame(sender, invalid_recipient, msg, proof);
```

The triggering path is `AdditionalBlameMachine::blame` → `blame_internal` → `decrypt_with_proof` → `self.enc_keys[&decryptor]`. [1](#0-0) [9](#0-8) [3](#0-2)
