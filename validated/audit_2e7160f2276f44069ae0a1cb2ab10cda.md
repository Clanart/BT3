## Title
Partial commit/discard staging trusts stale line-index `DiffSelection` against a freshly re-fetched diff, silently committing/discarding the wrong hunks — (File: `app/src/lib/git/apply.ts`, `app/src/models/diff/diff-selection.ts`)

### Summary
The bug class in the External Report is a **TOCTOU mismatch between the value a user approves and the value actually settled on-chain** (approved amount vs. current debt share value). GitHub Desktop has a structurally identical pattern in its partial-staging/partial-discard flow: the user's line selection is captured as a set of **abstract numeric indices** (`DiffSelection`) against a diff rendered at time T0, but that same index set is later applied against a diff **re-fetched fresh at commit/discard time** (T1) with no verification that the content at those indices is unchanged.

### Finding Description
`DiffSelection.isSelected(lineIndex)` operates purely on a `Set<number>` of line indices with no binding to the actual line content: [1](#0-0) 

When staging a partial file for a commit, `applyPatchToIndex` re-fetches the diff from disk/index immediately before building the patch: [2](#0-1) 

and then builds the patch by calling `file.selection.isSelected(absoluteIndex)` against the **hunks of this freshly fetched diff**, not the diff the user actually looked at when making the selection: [3](#0-2) 

The commit flow confirms the file objects (carrying their `.selection`) come straight from in-memory `changesState`, are never re-diffed/re-validated before being handed to `createCommit`: [4](#0-3) 

`createCommit` clears the index and calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex` (the fresh-diff refetch point): [5](#0-4) [6](#0-5) 

The same untethered-index pattern exists in the discard path, where `formatPatchToDiscardChanges` applies a `selection` against a `diff` object that is passed down from the UI (`props.diff`) and may be older than the working tree at the moment "Discard" is confirmed: [7](#0-6) [8](#0-7) 

App-store's own comment acknowledges that diffs can change "dramatically" between loads and only patches up *selectable* line indices, not the correctness of already-diverging selections tied to old content: [9](#0-8) 

**The broken invariant:** a `DiffSelection` index set is only meaningful relative to the exact diff it was created against. Nothing checks that the diff used to *build the patch* (fresh, at T1) is the same diff the user *selected against* (at T0). If the tracked file's content changes between T0 and T1 — e.g., via a build tool, a formatter/linter running on save, a smudge/clean filter, a `post-checkout`/`post-merge` hook in an attacker-controlled repository, or any background process writing to a tracked file — the hunk boundaries and `unifiedDiffStart` offsets shift, so the same index set now denotes **different, unrelated lines**. `git apply` with `--unidiff-zero` will happily apply a syntactically valid but semantically wrong patch as long as context/line counts line up, or partially fail only for the mismatched hunks while succeeding for others.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": a user who reviewed and selected specific lines/hunks can end up committing (or discarding) different content than what they approved, without any error or warning, because the app never re-validates the stale selection against the newly-generated diff content. In a scenario where the working tree is being mutated by something the attacker influences (a hook, generated file, or tool triggered by opening/checking out a malicious repository), this can be leveraged to smuggle unintended content into a commit that the user believes only contains their reviewed lines, or to make "discard" destroy unintended changes.

### Likelihood Explanation
This requires a race between the diff shown/selected in the UI and the moment `applyPatchToIndex`/`discardChangesFromSelection` executes — a window that exists on every partial commit/discard operation and is widened by anything that writes to the working tree asynchronously (editors, linters, git hooks such as `post-checkout`/`smudge` filters shipped with an untrusted repository). It does not require local/physical access, admin rights, or leaked credentials — only that the user perform an ordinary partial-stage/partial-discard action in a repository where file content can shift underneath the app between diff render and action commit.

### Recommendation
Do not reuse an index-based selection across two different diff snapshots. Either:
- Re-fetch the diff and re-derive/validate the user's selection against it immediately before rendering the commit/discard confirmation and abort (with a clear error) if the diff has changed since the selection was made, or
- Bind selections to line content (e.g., hash of the line text) rather than raw indices, so a mismatch is detected instead of silently misapplied, or
- Re-diff right before staging and diff that result against the diff that was actually shown to the user; if they differ, force the user to re-review before committing/discarding.

### Proof of Concept
1. Open a repository in Desktop, modify `file.md` producing hunks A and B, and in the Changes view select only hunk A for commit (leaving `DiffSelection` divergent line indices tied to hunk A's `unifiedDiffStart` positions).
2. Before clicking "Commit", have a background process (e.g., a `post-checkout`/file-watcher/formatter, or in an attacker-controlled repo a git hook triggered by another Desktop-initiated git command) rewrite the top of `file.md`, shifting all line numbers so hunk A's old index range now overlaps what used to be (or newly is) part of hunk B / unrelated content.
3. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff, and `formatPatch` (`app/src/lib/patch-formatter.ts:129`) applies the old index-based selection to it, producing and applying a patch that stages different lines than the ones the user reviewed and checked — with no warning shown to the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
