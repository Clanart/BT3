### Title
`build_refute_prompt` blindly slices diff text to 8000 bytes with no per-file anchoring, letting attacker-controlled diff size/ordering push the flagged `+` line out of the prompt and trigger the model's own PRE-EXISTING refute rule - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`build_refute_prompt` truncates the entire diff passed to the self-refute LLM stage with a raw `diff_text[:8000]` slice, unlike `cap_diff_for_prompt`/`build_investigate_prompt`, which cap per-file and insert explicit truncation markers. An attacker who controls the diff (e.g., by padding a PR/commit with large or numerous unrelated file changes ahead of the actually dangerous hunk) can push the vulnerable `+` line past the 8000-character cutoff, causing the refute model to invoke its own documented "PRE-EXISTING" rule and mark a real, dangerous finding as refuted/dropped.

### Finding Description
`build_refute_prompt` builds the stage-2 prompt as: [1](#0-0) 
It concatenates the JSON candidates and then appends `diff_text[:8000]` verbatim, with no per-file capping, no truncation marker, and no guarantee that the file/line associated with any candidate remains inside the visible window. Contrast this with the stage-1 path, where `cap_diff_for_prompt` explicitly caps per-file and total bytes and inserts a `"... [truncated by security-guidance: ...]"` marker so the reviewer knows content is missing: [2](#0-1) 

The refute system prompt instructs the model to REFUTE a candidate whenever:
"PRE-EXISTING: the cited vulnerableCode does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file. The diff did not introduce it." [3](#0-2) 

Because the diff block the model sees is an unmarked, blindly-truncated prefix of the full diff, an attacker who controls the diff content (any repo content that will be reviewed — a PR, a commit, or agent-generated changes) can make the dangerous file's `+` lines fall after byte 8000 by front-loading the diff with large/verbose but harmless file changes. The model then has no visibility into the actual `+` line, satisfies its own PRE-EXISTING criterion (since it cannot see the line "in the DIFF block above"), and refutes an otherwise valid, dangerous finding — with no marker in the prompt indicating truncation occurred, so the model has no signal to treat the missing evidence as inconclusive rather than as proof of absence.

This directly breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes": the size/ordering of attacker-authored diff content (fully within the attacker's control, since diffs are the artifact under review) determines whether a genuine, correctly-flagged vulnerability survives to be surfaced to the user via `format_findings`, or is silently dropped.

### Impact Explanation
A successful manipulation causes the self-refute stage to drop a true-positive, security-critical finding (e.g., a backdoor, credential leak, or RCE-enabling change) from the final report shown to the developer/agent, so the dangerous change proceeds unreviewed. This matches "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" in the sense that it defeats the guardrail whose entire purpose is to catch and surface exactly these disclosure/compromise patterns before they merge, effectively neutering the security-guidance review for any diff engineered to exceed the truncation point.

### Likelihood Explanation
This requires no privilege beyond the ability to produce a diff that will be reviewed (a normal PR/commit/agent change) — no admin access, no leaked keys. The attacker only needs to control diff size/content ordering, which is trivially achievable (padding with a large auto-generated file, vendor dump, or verbose unrelated diff before the real change). It is fully repeatable and deterministic given the fixed 8000-character cutoff and lack of per-file anchoring.

### Recommendation
In `build_refute_prompt`, replace the blind `diff_text[:8000]` slice with the same per-file capping/anchoring logic used in `cap_diff_for_prompt` (or reuse it directly), ensuring:
1. Each candidate's cited `filePath` diff hunk is guaranteed to be included (anchor-first packing) even if other files must be truncated more aggressively or omitted.
2. Any truncation inserts an explicit marker, and the refute system prompt is updated so the "PRE-EXISTING" rule only applies when the file was NOT truncated/omitted — otherwise the model should treat the candidate as indeterminate (default SURVIVES) rather than refuted.

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py`:
1. Construct `diff_files` with one large "padding" file (>8000 bytes of benign `+` lines) followed by a small file containing a clearly dangerous `+` line (e.g., `+ os.system(user_input)`).
2. Build `diff_text` by concatenating in that order (as the real diff would appear) and call `build_refute_prompt(candidates=[{"filePath": "danger.py", "vulnerableCode": "os.system(user_input)", ...}], diff_text=diff_text)`.
3. Assert that the string `"os.system(user_input)"` is present in the returned prompt. In the current implementation this assertion FAILS once the padding file exceeds 8000 bytes, proving the dangerous `+` line is silently dropped with no truncation marker.
4. After applying the recommended fix (per-file anchored capping), re-run the same test and assert the dangerous line's file is always present and marked if truncated elsewhere, and add a system-prompt-level test verifying the PRE-EXISTING rule is gated on "not truncated."

```python
def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```
