### Title
`EvmHost.dispatch()`/`fundRequest()` permanently trap excess ETH sent for fee swaps, causing silent user fund loss - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` swap user-supplied native tokens into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens()`, using `msg.value` as the max input and `post.fee`/`amount` as the exact output. Uniswap's `swapETHForExactTokens` refunds any unused ETH to `msg.sender` of the call — but the caller of the router here is `EvmHost` itself (`address(this)` is only the recipient argument for the ERC20 leg; the ETH refund goes to whoever called the router, i.e. the host contract), not the end user who sent `msg.value`. Because `EvmHost` has no logic to forward that refund back to `_msgSender()`, any ETH sent above the exact amount consumed by the swap is permanently stranded in the host contract with no path for users to reclaim it.

### Finding Description
In `dispatch()`: [1](#0-0) 
the contract calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This is an exact-output swap: it consumes only as much ETH as needed to produce exactly `post.fee` units of `feeToken` at current pool reserves, and refunds the remainder to the caller of the router. Since `EvmHost` is the caller, the refund lands back in `EvmHost`'s own balance rather than being returned to `_msgSender()`, who supplied the `msg.value`.

The same pattern recurs in `fundRequest()`: [2](#0-1) 

There is no code anywhere in `EvmHost.sol` that forwards leftover ETH from these swaps back to the user, and no user-facing withdrawal path exists for this stranded value — the file contains no `receive()`/generic ETH-sweep for users, only internal admin/governance-gated fee mechanisms.

Because the exact ETH needed depends on live Uniswap V2 pool reserves (`path[0] = WETH, path[1] = feeToken`) at the moment of execution, and there is no `amountOutMin`/slippage or exact-consumption accounting protecting the user, any user who (a) reasonably overestimates `msg.value` to guard against price movement between quoting and submission, or (b) is sandwiched by an attacker who moves the pool price down right before the user's transaction (making the swap cheaper than expected), will have the unspent ETH siliently absorbed by the contract instead of refunded. This mirrors the referenced DODO report's root cause — trusting a spot AMM quote (`getAmountsIn`-style) for a settlement-critical swap without protecting the payer's leftover value — except here the loss is deterministic and guaranteed by the missing refund-forwarding logic, not merely a manipulation risk.

### Impact Explanation
Every call to `dispatch()` or `fundRequest()` with `msg.value` greater than the ETH actually required by the AMM at execution time results in permanent, unrecoverable loss of the difference for the dispatching user — the funds are trapped in `EvmHost` with no mechanism to return them. This is a direct "loss of funds" impact matching the bounty's accepted impact class (fund loss / wrong beneficiary), triggerable by any ordinary user through the public `dispatch`/`fundRequest` entry points, and is worsened (not caused) by adversarial reserve manipulation — an unprivileged attacker can front-run a `dispatch()` call to shrink the AMM's required input, guaranteeing a larger stranded refund for every subsequent victim transaction in the same block/mempool window, extracting no direct profit for themselves but permanently damaging the payer.

### Likelihood Explanation
High: any user who provides a safety margin above the current quoted fee (standard practice to avoid reverts from price drift, per the project's own documentation warning that `quote()` is "vulnerable to sandwich attacks" and should only be used off-chain) will trigger this loss on every single dispatch call using native-token payment. No special privileges, timing races, or malicious infrastructure are required — the bug fires deterministically whenever `msg.value` exceeds the exact swap cost.

### Recommendation
After calling `swapETHForExactTokens`, compute `address(this).balance` before/after (or capture the returned `amounts[0]` actually spent) and refund `msg.value - amountSpent` back to `_msgSender()` via a low-level call, in both `dispatch()` and `fundRequest()`. Alternatively, switch to computing the exact required input off-chain and reverting on mismatch, or track and expose a per-caller ETH credit balance that users can withdraw.

### Proof of Concept
1. Attacker (or natural price drift) leaves the WETH/feeToken pool such that 1 ETH buys more than `post.fee` feeToken units.
2. User calls `dispatch(post)` with `msg.value = 1 ether` intending to cover `post.fee` plus a safety buffer for slippage.
3. `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(post.fee, [WETH, feeToken], address(this), block.timestamp)` consumes, say, `0.6 ether` and refunds `0.4 ether` — but the refund goes to `msg.sender` of the router call, which is `EvmHost`, not the user. [1](#0-0) 
4. `EvmHost`'s ETH balance increases by `0.4 ether`; there is no function in `EvmHost.sol` that lets the user reclaim this amount — it is permanently lost to them.
