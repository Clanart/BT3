### Title
Unbounded loop in `object::root_owner` allows a self-owned (cyclic) object to permanently deny lazy module self-initialization and root-owner-dependent publish bookkeeping — ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`object::root_owner` walks the ownership chain of an object with an unbounded `while` loop, unlike every other ownership-chain walker in the same module (`owns`, `verify_ungated_and_descendant`), which explicitly cap traversal at `MAXIMUM_OBJECT_NESTING = 8` to defend against cyclic ownership. `object::transfer_raw` allows an object to be transferred to itself (a documented, tested edge case: `test_cyclic_ownership_transfer_should_fail`), producing a self-owned `ObjectCore` whose `owner` field points back to its own address. `root_owner` is called directly from the new publish-path code in `code::publish_package` and `init::assert_may_self_initialize` (lazy module initialization / code-object ownership gating). Once a code object is self-owned, any call into these functions loops until gas is exhausted, aborting the transaction — a permanent denial of publish bookkeeping and of lazy self-init for that object.

### Finding Description
The `root_owner` function:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

has no bound on the number of hops it will traverse, whereas the module's other traversal functions cap at `MAXIMUM_OBJECT_NESTING` (8) precisely because "objects may have cyclic dependencies": [2](#0-1) [3](#0-2) 

A self-loop is achievable and is even exercised by an existing test: transferring an object to itself succeeds on the *first* call (the pre-transfer ownership chain does not yet contain the cycle, so `verify_ungated_and_descendant` passes), after which `ObjectCore.owner == self`: [4](#0-3) 

`root_owner` is used in the new lazy-module-initialization / object code-publish flow to determine (and later re-check) the "transitive root owner" of a code object:
- In `code::publish_package`, when publishing to an object address, the root owner is computed and recorded per module via `init::record_deploy_owner`: [5](#0-4) 
- In `init::assert_may_self_initialize`, the recorded owner is compared against the *current* `root_owner()` to decide whether a module hosted at an object may lazily self-initialize: [6](#0-5) 

If the object at that address has a self-referential (or otherwise cyclic) `owner` chain, `root_owner`'s `while` loop never terminates on its own; it can only be stopped by gas exhaustion, aborting the enclosing transaction (publish, upgrade, or lazy self-init).

### Impact Explanation
This breaks a code-safety invariant that the same module deliberately protects elsewhere (bounded ownership traversal to tolerate cycles). Concretely:
- Publishing or upgrading a package at an object address whose ownership chain is cyclic will abort every time `code::publish_package` reaches the `root_owner()` computation, permanently blocking further code publication/upgrade bookkeeping tied to that object once the feature (`LAZY_MODULE_INITIALIZATION`) is enabled and the object is a cyclic owner.
- Any module deployed at that object that relies on `init::internal_maybe_initialize` will permanently fail to self-initialize (`assert_may_self_initialize` calls `root_owner()`), denying legitimate initialization indefinitely for that code object.
- Because gas metering bounds the loop, this is not a network-wide DoS, but it is a durable, unauthorized-triggerable failure of a protected state-mutation path (object code ownership / lazy init gating) that the codebase's own design intends to guard against cyclic-ownership edge cases (as shown by the capped loops elsewhere).

### Likelihood Explanation
Creating a self-owned object requires only a single ordinary `object::transfer` call by the object's current owner (no special privilege), and this is already demonstrated as achievable in the framework's own test suite. Any account (or object) controlling a code object could transfer it to itself before or after publishing, and the `LAZY_MODULE_INITIALIZATION` feature path (`code::publish_package` object branch, `init::assert_may_self_initialize`) would then hit the unbounded loop on the very next publish/upgrade/self-init interaction with that object. This makes the trigger low-effort and fully reachable through existing public entry points once the feature is live.

### Recommendation
Bound `root_owner`'s traversal the same way `owns` and `verify_ungated_and_descendant` are bounded, using `MAXIMUM_OBJECT_NESTING`, and either return the best-effort owner after the cap or abort with `EMAXIMUM_NESTING`/a dedicated error instead of looping unbounded:
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Apply the same fix to any other caller path that assumes acyclic ownership chains for computing a "root owner" (`code::publish_package`, `init::assert_may_self_initialize`).

### Proof of Concept
1. Create object `obj1` owned by `creator` (`object::create_object`), then call `object::transfer(creator, obj1, obj1.object_address())`. This succeeds — the pre-transfer chain check in `verify_ungated_and_descendant` passes because at call time `obj1.owner == creator`, and afterward `ObjectCore[obj1].owner == obj1` (self-loop), exactly as exercised in `test_cyclic_ownership_transfer_should_fail`: [4](#0-3) 
2. With `LAZY_MODULE_INITIALIZATION` enabled, publish a package to `obj1` via `object_code_deployment::publish`/`code::publish_package`. When the object branch executes: [5](#0-4) 
the call `object::address_to_object<ObjectCore>(addr).root_owner()` enters the unbounded loop in `root_owner`, since `obj_owner` (== `obj1`) satisfies `is_object(obj_owner)` and `owner()` of `obj1` returns `obj1` again on every iteration — the loop never naturally terminates and the transaction runs until it runs out of gas and aborts.
3. Equivalently, any subsequent call to a module at `obj1` using `init::internal_maybe_initialize`, which invokes `assert_may_self_initialize` → `root_owner()`, will hit the same unbounded loop and abort on out-of-gas, permanently denying lazy self-initialization for that object: [7](#0-6) 

**Note on verification limits:** I was not able to execute the Move code directly (no sandbox access) to empirically confirm the exact gas-exhaustion behavior or check for any not-yet-indexed guard that might exist elsewhere in the codebase; this conclusion is based on static reading of `object.move`, `code.move`, and `init.move`. I recommend a Devin session with full repo/test access to confirm via an e2e test (e.g., extending `object_code_deployment.rs` or `init_module_api.rs`) that self-owned objects indeed cause publish/self-init transactions to abort due to gas exhaustion in `root_owner`.

    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
