### Title
`clone()` explicitly disables Git's built-in submodule clone protection via `GIT_CLONE_PROTECTION_ACTIVE=false` - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` function unconditionally sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` when invoking `git clone --recursive`, and also passes `--recursive` unconditionally to auto-fetch submodules. [1](#0-0) 
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself uses to gate the hardening added after CVE-2024-32002 (a `git clone --recursive` RCE where a malicious repository's submodule configuration could place a symlinked/embedded `.git` directory or hooks such that cloning recursively caused arbitrary hook execution, especially on case-insensitive filesystems). Setting this variable to `'false'` disables that protection path in Git rather than relying on Git's default-safe behavior.

### Finding Description
The broken invariant here mirrors the report's pattern: a piece of state that is supposed to gate a dangerous, irreversible operation is turned off/bypassed by processing attacker-controlled input (a malicious repository), and there is no separate safety check in Desktop to compensate.

`clone()` builds the arguments as `['-c', 'init.defaultBranch=...', 'clone', '--recursive', ...]` and merges an environment that always includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. [1](#0-0) 
This means every clone performed through Desktop — including clones of arbitrary user-supplied URLs — runs with Git's submodule-clone hardening turned off, while `--recursive` still causes Git to immediately fetch and check out any submodules the malicious repository declares. A crafted repository (attacker-controlled remote content) can declare a submodule whose path/config attempts to write into or through `.git`/`.git/hooks` (e.g., a maliciously cased path colliding on case-insensitive/case-preserving filesystems such as default macOS/Windows installs, or a submodule path containing a symlink component) which the disabled protection would normally reject.

The only local guard present, `isClonePathSensitive()`, checks the *destination* directory against a fixed deny-list (home dir, `.ssh`, `.gnupg`, `.config`, `.gitconfig`, `%APPDATA%`) — it says nothing about the *contents* of the remote repository being cloned, so it does not stop this path at all. [2](#0-1) 

### Impact Explanation
If exploitable, this allows an attacker who controls a Git remote (a public repo the victim is lured to clone, or a compromised/malicious fork) to achieve file writes outside the intended working tree or execution of an attacker-supplied hook during a normal `Clone repository` action in Desktop — a supported, unprivileged, no-extra-steps user action (paste URL/click "Clone" or use a `x-github-client://` clone deep link). This matches the report's "attacker controls a cloned/fetched repository ... result is code execution or file write outside the repo" impact class.

### Likelihood Explanation
Likelihood depends on the currently bundled Git version's exact protection behavior and whether `GIT_CLONE_PROTECTION_ACTIVE=false` fully disables the check versus only some legacy sub-check; I could not confirm the exact Git version bundled or verify against upstream Git source in this pass, so this should be validated by (a) confirming the bundled `dugite`/git version's implementation of this flag, and (b) reproducing a clone of a crafted repository with a symlinked/cased submodule to see if the hook/write escapes. If the flag fully reverts to pre-CVE-2024-32002 behavior, likelihood is high since it triggers on every clone with no user interaction beyond initiating the clone.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's default (protection-enabled) behavior applies during `clone()`. If `--recursive` submodule fetching needs different handling, do it via `git submodule update` after inspecting/allow-listing submodule paths rather than disabling the clone-time hardening. Add a regression test that clones a crafted fixture repository containing a symlinked `.git`/hook-colliding submodule path and asserts the clone fails safely instead of succeeding.

### Proof of Concept
1. Set up a malicious remote repository containing a `.gitmodules` entry and a submodule commit whose path is crafted to collide with `.git` on a case-insensitive filesystem (the class of repository described in CVE-2024-32002), with an embedded hook file.
2. In GitHub Desktop, use "Clone repository" (or a `x-github-client://openLocalRepo`/clone-style deep link) pointing at that URL — this invokes `clone()` in `app/src/lib/git/clone.ts`.
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for this call [3](#0-2) , Git's submodule-clone hardening is skipped for the operation, while `--recursive` still causes immediate submodule checkout [4](#0-3) .
4. Observe (in an isolated VM) whether the crafted submodule's hook executes or writes outside `path` during the clone, since `isClonePathSensitive()` only validates the destination path and not remote repository content [2](#0-1) .

Note: I was not able to inspect the exact bundled Git/dugite version or upstream Git's current semantics for `GIT_CLONE_PROTECTION_ACTIVE` within this session, so step 3's outcome should be empirically verified before treating this as confirmed-exploitable; the code-level fact that Desktop deliberately disables this named protection variable for all clones is confirmed from local source.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
