### Title
SignableTransaction::new underestimates vbytes/fee by omitting the OP_RETURN output from the weight calculation, so transactions carrying `data` pay less than the requested fee rate and may fail to relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends the OP_RETURN `data` output to `tx_outs` before computing the fee, but calls `calculate_weight_vbytes` with only `payments`, so the OP_RETURN output (up to ~91 bytes: ~9-byte output overhead + push opcode + 80-byte payload) is excluded from both the weight and the vbytes used to derive `needed_fee`. The resulting transaction therefore pays `fee_per_vbyte * vbytes` where `vbytes` is too small, silently underpaying relative to the caller-specified fee rate — the analog of minting shares on a stale asset amount while ignoring a portion of what is owed.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` at lines 195–202. Immediately after, the fee is derived from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, which builds a mock transaction whose `output` vector is populated **only** from `payments` (lines 85–93) plus an optional change output (lines 95–99). The OP_RETURN output is never included in the mock transaction, so `weight`/`vbytes` — and consequently `needed_fee = fee_per_vbyte * vbytes` at line 206 — are computed for a strictly smaller transaction than the one actually produced and signed. The same omission affects the `fee_with_change` computation at lines 225–227 (the change-amount subtraction at line 228 uses the too-small fee, so change is slightly over-credited and the actual paid fee equals the underestimated value), and the `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses the under-counted weight. This mirrors the Carousel bug: a value owed to the consumer (here, the network fee / the correctness of the change amount) is computed on an incomplete accounting of the outputs actually created. ### Impact Explanation
The transaction's actual fee rate is `paid_fee / actual_vsize`, which is strictly below `fee_per_vbyte`. With an 80-byte payload the underestimate is ~25+ vbytes; against a ~150–200 vbyte transaction that is a 10–15% fee shortfall. At low `fee_per_vbyte` values (e.g. minimum relay), the paid fee can fall below `DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes / 1000` even though the TooLowFee check at line 211 passed — the check validates against the underestimated `vbytes` too. The result is a signed transaction the Bitcoin network will not relay/confirm, leaving the input funds effectively unspendable via this transaction, plus a `needed_fee()` accessor that reports an incorrect value to callers (the processor's fee accounting in `prepare_send`/`median_fee` relies on this figure). Additionally, the weight check can pass a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT`.

### Likelihood Explanation
Reachable by any caller of the public `SignableTransaction::new` API passing `data: Some(..)` (up to 80 bytes is explicitly allowed and tested in `networks/bitcoin/tests/wallet.rs` `test_data`). No special privileges are needed; the miscomputation triggers deterministically whenever `data` is `Some`, scaled by the payload size. Severity is bounded because the underpayment is capped at ~91 bytes of output (~23–30 vbytes), so it primarily matters at fee rates near the minimum or when the caller relies on `needed_fee()` being exact.

### Recommendation
Include the OP_RETURN output in the mock transaction inside `calculate_weight_vbytes` (or pass the already-built `tx_outs`/an additional `data_len` into it), so `weight`, `vbytes`, `needed_fee`, and `fee_with_change` all reflect the final transaction. E.g., extend `calculate_weight_vbytes` to accept `data: Option<&[u8]>` and push a `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) }` before computing weight.

### Proof of Concept
Construct `SignableTransaction::new(inputs, &[], Some(change), Some(vec![0; 80]), fee_per_vbyte)`. The signed transaction's `tx.vsize()` exceeds the `vbytes` used for `needed_fee` by the size of the OP_RETURN output (~90 weight units ≈ 23 vbytes plus output overhead), so `tx.fee() / tx.vsize() < fee_per_vbyte`. With `fee_per_vbyte` chosen so that `needed_fee` just passes the `DEFAULT_MIN_RELAY_TX_FEE` check on the underestimated vbytes, the produced transaction's real fee rate is below the minimum relay fee and bitcoind rejects it with `min relay fee not met`, while `needed_fee()` reports a value ~13% lower than `tx.vsize() * fee_per_vbyte`.
