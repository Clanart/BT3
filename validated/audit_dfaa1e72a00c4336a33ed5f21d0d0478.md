Based on my research, I found a genuine analog in the upb JSON decoder's Timestamp parsing that mirrors the reported invariant: an attacker-controlled value pulled from an external input is not fully range-validated before being stored and used downstream, unlike sibling implementations that do perform the equivalent check.

### Title
Missing upper-bound range validation on ProtoJSON `Timestamp.seconds` in the upb JSON decoder allows out-of-range Timestamp values to be silently accepted - (File: `php/ext/google/protobuf/php-upb.c`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

### Summary
The report's core invariant is: an externally-supplied numeric value (Chainlink `exchangeRate`) is used in downstream calculations without validating it against the full set of bounds the application relies on (only a zero-check was done; staleness/negativity were not checked), leading to silently-accepted invalid values feeding critical math. The Protobuf analog is `jsondec_timestamp()` in the upb runtime as embedded in the PHP and Ruby native extensions: the client-controlled ProtoJSON `Timestamp` string is decoded into a `seconds` value, but only the lower bound of the valid `google.protobuf.Timestamp` range is checked; the upper bound is never checked, so an out-of-range `seconds` value is accepted and written into the message unaltered.

### Finding Description
`google.protobuf.Timestamp` is documented and enforced elsewhere in the codebase to be valid only in the range `[-62135596800, 253402300799]` seconds (year 0001-01-01T00:00:00Z to 9999-12-31T23:59:59.999999999Z). This is verified by the conformance suite, which expects `TimestampJsonInputTooLarge` (`"10000-01-01T00:00:00Z"`) to fail parsing [1](#0-0) , and by other language implementations that explicitly enforce both bounds, e.g. C#'s `MergeTimestamp` checking `timestamp.Seconds < Timestamp.UnixSecondsAtBclMinValue || timestamp.Seconds > Timestamp.UnixSecondsAtBclMaxValue` [2](#0-1) , and PHP's own `GPBUtil::formatTimestamp` (bccomp against `253402300800`) [3](#0-2) .

However, `jsondec_timestamp()` in the amalgamated upb runtime shipped inside the PHP native extension only checks the lower bound: [4](#0-3) 
There is no corresponding `seconds.int64_val > 253402300799` check anywhere in the function [5](#0-4) . The same `jsondec_timestamp` symbol and structure exist in the Ruby native extension's amalgamated upb copy [6](#0-5) , indicating the same code pattern is present there as well, though I was not able to directly read its `jsondec_timestamp` body in this session to confirm the exact line content (see caveat below).

The attacker-controlled input is the ProtoJSON string for a `Timestamp`-typed field (e.g. `{"optionalTimestamp": "999999-01-01T00:00:00Z"}` or any year value that computes a `seconds` value far above `253402300799`), submitted through the ordinary public ProtoJSON parse API (`Message::mergeFromJsonString` in PHP, `JSON.parse`/`decode` in Ruby). Because only the lower bound is enforced, this value is accepted and stored directly into the message's `seconds` field via `upb_Message_SetFieldByDef` without further clamping [7](#0-6) .

### Impact Explanation
Once accepted, this out-of-range `Timestamp` message is available to trusted consuming application code, which is documented/expected to treat `Timestamp` as bounded within the AD 1-9999 range (the well-known-type's own spec, and every other runtime, enforce this). Application code that converts the value to native date/time types, performs date arithmetic, or serializes it back to text (e.g. via `strftime`, native `DateTime` objects, or downstream comparison logic) may encounter integer overflow, incorrect date computations, or crashes when handed a value outside the type's documented invariant — mirroring the original report's "wrong calculations" impact from consuming an unvalidated numeric value. This is a parser-level integrity/invariant violation reachable purely from bounded client-supplied ProtoJSON, not a resource-exhaustion or memory-safety issue.

### Likelihood Explanation
Low-to-Medium. Exploitation requires: (1) an application accepting arbitrary ProtoJSON via PHP or Ruby's protobuf JSON parsing API with a `Timestamp`-typed field, and (2) that application performing timestamp-sensitive calculations without its own additional bounds check on `seconds`. The trigger itself is trivial (a single crafted JSON string with a large year), similar to how the oracle staleness bug required only an oracle round becoming stale — the underlying validation gap is deterministic and always reachable, but downstream impact depends on how the consuming application uses the `Timestamp`.

### Recommendation
Add the missing upper-bound check to `jsondec_timestamp()` in the upb sources bundled with PHP and Ruby (and audit the canonical `upb/json/decode.c` for the same gap, since these files are typically generated/amalgamated from it):
```c
if (seconds.int64_val < -62135596800 || seconds.int64_val > 253402300799) {
  jsondec_err(d, "Timestamp out of range");
}
```
This aligns the upb-backed PHP/Ruby JSON decoder with the behavior already enforced by the conformance suite, the C++ `ParseTimestamp` path's documented invariant, and the C#/Java/Python implementations.

### Proof of Concept
Using the PHP protobuf extension (native upb-backed), parse a message containing a `google.protobuf.Timestamp` field from JSON with a `seconds` value far beyond `253402300799`, e.g.:
```json
{"optionalTimestamp": "99999-01-01T00:00:00Z"}
```
Trace: `jsondec_timestamp` computes `seconds.int64_val` from `jsondec_unixtime()` (year, month, day, hour, min, sec) [8](#0-7) , and only tests `seconds.int64_val < -62135596800` [4](#0-3)  before committing the value with `upb_Message_SetFieldByDef` [9](#0-8) . No upper-bound rejection occurs, so parsing succeeds and produces a `Timestamp{seconds: <huge value>}` that the conformance suite's `TimestampJsonInputTooLarge` test expects to be rejected [10](#0-9) .

**Caveat/uncertainty**: I could not directly retrieve the body of `jsondec_timestamp` in `upb/json/decode.c` (the canonical, non-amalgamated source) or in `ruby-upb.c` during this session due to a tool read failure on the final iteration, so I cannot 100% confirm the identical gap exists verbatim in those two files — only that the same function name/structure is present. This should be independently verified by a follow-up read of those exact functions before treating the finding as confirmed across all three files; the PHP `php-upb.c` instance is confirmed directly from the retrieved source.

static int64_t jsondec_unixtime(int y, int m, int d, int h, int min, int s) {
  return (int64_t)jsondec_epochdays(y, m, d) * 86400 + h * 3600 + min * 60 + s;
}

static void jsondec_timestamp(jsondec* d, upb_Message* msg,
                              const upb_MessageDef* m) {
  UPB_ASSERT(!upb_Message_IsFrozen(msg));
  upb_MessageValue seconds;
  upb_MessageValue nanos;
  upb_StringView str = jsondec_string(d);
  const char* ptr = str.data;
  const char* end = ptr + str.size;

  if (str.size < 20) goto malformed;

  {
    /* 1972-01-01T01:00:00 */
    int year = jsondec_tsdigits(d, &ptr, 4, "-");
    int mon = jsondec_tsdigits(d, &ptr, 2, "-");
    int day = jsondec_tsdigits(d, &ptr, 2, "T");
    int hour = jsondec_tsdigits(d, &ptr, 2, ":");
    int min = jsondec_tsdigits(d, &ptr, 2, ":");
    int sec = jsondec_tsdigits(d, &ptr, 2, NULL);

    seconds.int64_val = jsondec_unixtime(year, mon, day, hour, min, sec);
  }

  nanos.int32_val = jsondec_nanos(d, &ptr, end);

  {
    /* [+-]08:00 or Z */
    int ofs_hour = 0;
    int ofs_min = 0;
    bool neg = false;

    if (ptr == end) goto malformed;

    switch (*ptr++) {
      case '-':
        neg = true;
        /* fallthrough */
      case '+':
        if ((end - ptr) != 5) goto malformed;
        ofs_hour = jsondec_tsdigits(d, &ptr, 2, ":");
        ofs_min = jsondec_tsdigits(d, &ptr, 2, NULL);
        ofs_min = ((ofs_hour * 60) + ofs_min) * 60;
        seconds.int64_val += (neg ? ofs_min : -ofs_min);
        break;
      case 'Z':
        if (ptr != end) goto malformed;
        break;
      default:
        goto malformed;
    }
  }

  if (seconds.int64_val < -62135596800) {
    jsondec_err(d, "Timestamp out of range");
  }

  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 1),
                                   seconds, d->arena));
  jsondec_checkoom(
      d, upb_Message_SetFieldByDef(msg, upb_MessageDef_FindFieldByNumber(m, 2),
                                   nanos, d->arena));
  return;

malformed:
  jsondec_err(d, "Malformed timestamp");
}
