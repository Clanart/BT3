### Title
Unauthenticated caller can force the aggregator to broadcast an arbitrary transaction via `InternalSendTx` - (File: core/src/rpc/aggregator.rs)

### Summary
The `ClementineAggregator` gRPC service exposes `internal_send_tx`, which takes a caller-supplied raw transaction and hands it directly to the tx-sender queue for fee-bumping and broadcast, with no check that the transaction is part of the bridge protocol. Per the documented deployment model, the aggregator's gRPC server does not enforce client TLS certificates, so this state-changing/broadcasting call is reachable by any network caller, not just the aggregator/self party it is meant for.

### Finding Description
The gRPC access-control model in this repository is mTLS-based: `Interceptors::OnlyAggregatorAndSelf` restricts non-"Internal" methods to the aggregator's certificate and restricts "Internal"-prefixed methods to the entity's own certificate [1](#0-0) . This interceptor is wired into `create_grpc_server`/`create_verifier_grpc_server`/`create_operator_grpc_server` for verifiers and operators [2](#0-1) .

For the aggregator, however, the documented and intended configuration is different: "The aggregator does not enforce client certificates but does use TLS for encryption," and enabling client verification there is explicitly flagged as unusual (a `tracing::warn!`) [3](#0-2) . That means, per design, `create_aggregator_grpc_server` runs with the `Noop` interceptor path in the general server builder for the normal/documented case, i.e. no certificate-based caller identity check is applied to any RPC on the aggregator, including ones named with the `Internal` convention that on verifier/operator servers is strictly self-only.

`InternalSendTx` is one such method: `rpc InternalSendTx(SendTxRequest) returns (Empty)` is described as "Send a pre-signed tx to the network" [4](#0-3) . Its implementation takes the caller's `raw_tx` bytes, converts them into a `bitcoin::Transaction` with no validation that the transaction belongs to any bridge flow (move-tx, kickoff, round, payout, etc.), and inserts it straight into the tx-sender's send/fee-bump queue: [5](#0-4) 

`insert_try_to_send` performs no protocol-membership check either - it simply deduplicates by txid and persists the transaction plus its requested `fee_paying_type` for the tx-sender's background CPFP/RBF loop to pick up and broadcast [6](#0-5) .

The binding that should hold is: *only the aggregator itself (self) may enqueue a transaction for broadcast via the "Internal" API* - exactly the same binding enforced for verifiers/operators via `is_internal`/`only_aggregator_and_self` [7](#0-6) . Because the aggregator's server does not apply that certificate check by design, the binding "caller == self" is not actually enforced on the aggregator's gRPC surface, and any network caller reaching the aggregator's port can act as if it were "self."

### Impact Explanation
This satisfies the explicitly listed High-severity bucket: "an unauthenticated state-changing or broadcasting call." An unauthenticated party can cause the aggregator's tx-sender infrastructure to accept and attempt to broadcast/fee-bump an arbitrary transaction of the caller's choosing, using the aggregator's own transaction-management resources (CPFP/RBF), a capability that is meant to be restricted to the aggregator/self, not exposed to arbitrary external callers. This is a state-changing (queue insertion into the DB) and network-broadcasting primitive reachable without any authentication.

### Likelihood Explanation
Likelihood is high whenever the automation feature is enabled and the aggregator's gRPC port is reachable, which is the documented normal configuration (client certificates intentionally not enforced on the aggregator). No credentials, keys, or roles are required - only network reachability to the aggregator's `ClementineAggregator/InternalSendTx` endpoint.

### Recommendation
Enforce the same "Internal implies self-only" invariant on the aggregator server that is already enforced on verifier/operator servers: apply an `OnlyAggregatorAndSelf`-equivalent (or a dedicated self-only) interceptor to `InternalSendTx` (and any other `Internal*` aggregator RPCs) regardless of the aggregator's general client-verification setting, or gate `internal_send_tx` behind an explicit authentication/authorization check independent of the general TLS policy.

### Proof of Concept
1. Deploy the aggregator per the documented configuration (`client_verification` disabled for the aggregator, as recommended in `docs/usage.md`).
2. As any TLS client (no valid client certificate required), connect to the aggregator's gRPC endpoint and call:
   `ClementineAggregator/InternalSendTx` with a `SendTxRequest { raw_tx: <attacker-chosen signed tx>, fee_type: <RBF/CPFP> }`.
3. Observe `internal_send_tx` accepts the request, converts `raw_tx` into a `Transaction`, and calls `tx_sender.insert_try_to_send(...)` with no check that the transaction is part of the bridge protocol [8](#0-7) , causing the aggregator's tx-sender background task to attempt to broadcast/fee-bump it.

fn is_internal(req: &Request<()>) -> bool {

    #[tracing::instrument(skip(self), err(level = tracing::Level::ERROR))]
    async fn internal_send_tx(
        &self,
        request: Request<clementine::SendTxRequest>,
    ) -> Result<Response<Empty>, Status> {
        #[cfg(not(feature = "automation"))]
        {
            Err(Status::unimplemented("Automation is not enabled"))
        }
        #[cfg(feature = "automation")]
        {
            let send_tx_req = request.into_inner();
            let fee_type = send_tx_req.fee_type();
            let signed_tx: bitcoin::Transaction = send_tx_req
                .raw_tx
                .ok_or(Status::invalid_argument("Missing raw_tx"))?
                .try_into()?;
            tracing::warn!(
                "Internal send tx rpc called with feetype: {:?}, tx hex: {}",
                fee_type,
                bitcoin::consensus::encode::serialize_hex(&signed_tx)
            );

            let mut dbtx = self.db.begin_transaction().await?;
            self.tx_sender
                .insert_try_to_send(
                    &mut dbtx,
                    None,
                    &signed_tx,
                    fee_type.try_into()?,
                    None,
                    &[],
                    &[],
                    &[],
                    &[],
                )
                .await
                .map_to_status()?;
            dbtx.commit()
                .await
                .map_err(|e| Status::internal(format!("Failed to commit db transaction: {e}")))?;
            Ok(Response::new(Empty {}))
        }

    pub async fn insert_try_to_send(
        &self,
        dbtx: &mut crate::TxSenderTransaction,
        tx_metadata: Option<TxMetadata>,
        signed_tx: &Transaction,
        fee_paying_type: FeePayingType,
        rbf_signing_info: Option<RbfSigningInfo>,
        cancel_outpoints: &[OutPoint],
        cancel_txids: &[Txid],
        activate_txids: &[ActivatedWithTxid],
        activate_outpoints: &[ActivatedWithOutpoint],
    ) -> Result<u32, BridgeError> {
        let txid = signed_tx.compute_txid();

        // do not add duplicate transactions to the txsender
        let tx_exists = self
            .db
            .check_if_tx_exists_on_txsender(Some(dbtx), txid)
            .await?;
        if let Some(try_to_send_id) = tx_exists {
            return Ok(try_to_send_id);
        }

        tracing::info!(
            "Added tx {} with txid {} to the queue",
            tx_metadata
                .as_ref()
                .map(|data| format!("{:?}", data.tx_type))
                .unwrap_or("N/A".to_string()),
            txid
        );

        let try_to_send_id = self
            .db
            .save_tx(
                dbtx,
                tx_metadata,
                signed_tx,
                fee_paying_type,
                txid,
                rbf_signing_info,
            )
            .await?;
