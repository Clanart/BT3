### Title
Deterministic reuse of cached FROST preprocess enables private key share recovery via nonce reuse - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`SigningProtocol::preprocess_internal` caches a single 32-byte `CachedPreprocess` seed in the DB keyed only by `context` and regenerates the FROST sign machine from that same seed on every call. Since `AlgorithmMachine::seeded_preprocess` derives the signing nonces deterministically via `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:121-144), every signing session under a given context reuses identical nonce commitments `D, E`. If `share` / `complete` are ever invoked with different effective signing sessions (different peer preprocess sets or different messages, e.g. a different `KeyPair` under the same `("DkgConfirmer", attempt)` context), the produced signature shares satisfy `s = d + b·e·λ·x` with the same `d, e` but different binding factors `b` — two such shares let anyone solve for the validator's secret key share `x`.

### Finding Description
In `preprocess_internal`, the seed is written once via `CachedPreprocesses::set` only when absent, then loaded and decrypted identically on every invocation for the same `context` (lines 123-145). `share_internal` rebuilds the machine from that same seed (line 156) before calling `machine.sign(preprocesses, msg)`. `seeded_preprocess` in `crypto/frost/src/sign.rs:127-133` uses `ChaCha20Rng::from_seed(*seed.0)` to generate the nonces and addendum deterministically — same seed means same nonces. The FROST docs explicitly warn reuse "will enable recovery of your private key share" (crypto/frost/src/sign.rs:211-213, spec/cryptography/FROST.md:51-55), and the API contract for `from_cache` requires the cached preprocess be deleted after use (sign.rs:216-224) — this contract is violated because the seed persists in the DB forever. The context `("DkgConfirmer", attempt)` in `DkgConfirmer::signing_protocol` (line 275) is reused across the `share()` and `complete()` paths; `complete()` re-runs `share_internal` (lines 312-327), and `msg` depends on caller-supplied `key_pair` and the attacker-controlled peer `preprocesses` map which feeds the binding factor via `hash_msg`/`hash_commitments` (crypto/frost/src/curve/mod.rs:61-91). Two calls with differing preprocess sets or differing `key_pair` produce two shares under identical nonces.

### Impact Explanation
Reuse of FROST nonces with different binding factors yields a linear system solvable for the signer's secret share: with shares `s₁ = d + b₁·e·λ·x` and `s₂ = d + b₂·e·λ·x` and publicly computable `b₁, b₂, λ`, the MuSig key share `x` (the validator's Ristretto signing key used by `musig(...)`) is recovered. Compromise of this key breaks the tributary validator multisig — the attacker can forge confirmations/signatures attributed to that validator — analogous to the report's escalation from limited authenticated access to full system compromise.

### Likelihood Explanation
An authenticated participant (any validator able to submit DKG confirmation transactions) can induce multiple `share`/`complete` invocations under one `attempt` by supplying different preprocess maps or by observing `share()` then `complete()` being invoked with a changed `key_pair`. Because the local preprocess is byte-identical each time (deterministic seed), the attacker detects reuse trivially and only needs two differing sessions. Reachability requires no privileged access beyond normal protocol participation; exploitation reduces to algebra on publicly broadcast shares.

### Recommendation
Rotate the cached preprocess after each use: in `share_internal`, after building the machine, overwrite `CachedPreprocesses` with a fresh `machine.cache()` (i.e., generate a new preprocess per signing session rather than per context), or delete the cached entry once a share has been produced and force `preprocess()` to be re-run. Alternatively, bind the seed to the full session (context + sorted peer preprocess set + msg hash) so identical inputs reproduce identical nonces while any differing session derives fresh ones.

### Proof of Concept
1. Validator V calls `DkgConfirmer::preprocess()` → returns deterministic preprocess `P` derived from seed `S` stored under `("DkgConfirmer", attempt)`.
2. Attacker submits a confirmation path causing `share(preprocesses_A, key_pair_A)` → V emits `s₁ = d + b₁·e·λ·x` where `b₁ = hash_binding_factor(msg_A ‖ commitments_A)`.
3. Attacker causes a second invocation `share(preprocesses_B, key_pair_B)` (different peer set or different key pair under the same attempt) → V emits `s₂ = d + b₂·e·λ·x` with the same `d, e` because the seed `S` was never rotated.
4. From `s₁ − s₂ = (b₁ − b₂)·e·λ·x` (with `e` eliminated by first combining shares appropriately per the binomial nonce structure `R = D + b·E`), solve `x = (s₁·b₂ − s₂·b₁) / (λ·(e·(b₂ − b₁)))`-style linear relations; concretely `s₁ − s₂` removes `d`, and a third share or the `D` commitment structure removes `e`, yielding `x`.
