### Title
Unbounded regex evaluation in hookify `RuleEngine._regex_match` allows a repo-committed `.claude/hookify.*.local.md` rule to ReDoS the PreToolUse hook into a fail-open timeout, silently disabling `action: block` rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._regex_match` compiles and executes attacker-supplied regex patterns from `.claude/hookify.*.local.md` rule files with no timeout, length cap, or catastrophic-backtracking guard. A rule file checked into a repository with a pattern like `(a+)+$` (or any classic ReDoS pattern) will hang `re.search` on ordinary tool-call text, forcing the hook process past its configured timeout and defeating the very `action: block` protection the rule file was meant to provide.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` globs every file matching `.claude/hookify.*.local.md` in the current working directory and loads it unconditionally - there is no allowlist, signature check, or "trusted author" distinction between a rule file the user wrote and one that arrived as ordinary repository content (e.g., committed by a contributor, or brought in via a PR/clone) [1](#0-0) .

Each matched file is parsed into a `Rule`/`Condition` via `Rule.from_dict`, and the `pattern` field is taken verbatim from YAML frontmatter with no regex complexity validation [2](#0-1) .

On every Bash/Edit/Write/MultiEdit tool call, `pretooluse.py` calls `load_rules(event=...)` and `RuleEngine.evaluate_rules(rules, input_data)` [3](#0-2) . Inside `_rule_matches` → `_check_condition` → `_regex_match`, the pattern is compiled with `compile_regex` (a bare `re.compile(pattern, re.IGNORECASE)`, LRU-cached) and matched with `regex.search(text)` - with no timeout, no `signal.alarm`, no separate process, and no length/complexity guard on either the pattern or the input text [4](#0-3) . `compile_regex` itself is equally unguarded [5](#0-4) .

`text` is attacker-influenced indirectly (it's the bash `command` or file `new_text`/`content` of whatever tool call is in flight) and does not need to be crafted maliciously - a catastrophic-backtracking pattern like `(a+)+$` will exhibit exponential worst-case behavior against any sufficiently long run of repeated characters that appears in ordinary commands or file content, which is common in real usage (e.g., long strings of the same character, repeated whitespace, base64 blobs, etc.).

The `hooks/hooks.json` configures a 10s timeout for the PreToolUse/PostToolUse/Stop/UserPromptSubmit command hooks [6](#0-5) . The hookify scripts are explicitly designed to fail open: `pretooluse.py` wraps evaluation in try/except and states in a comment "ALWAYS exit 0 - never block operations due to hook errors," always emitting `sys.exit(0)` regardless of outcome [7](#0-6) . If the regex engine is stuck in catastrophic backtracking, this in-process error handling never even executes - the process is killed externally by Claude Code once the 10s timeout elapses, before it can emit any `permissionDecision: "deny"` output. A hook that does not return a JSON decision in time cannot express a `deny`, so the enforcement effectively lapses for that tool call, consistent with this plugin's own fail-open design philosophy for every other error path.

No part of `config_loader.py` or `rule_engine.py` validates regex complexity, imposes an evaluation budget, or falls back to `re2`/timeout-wrapped matching, so nothing stops an attacker-controlled pattern from reliably starving the hook.

### Impact Explanation
This is a policy-enforcement bypass caused by resource exhaustion: an unprivileged contributor who can get a `.claude/hookify.*.local.md` file into a victim's working tree (via a PR, a cloned malicious repo, or any repository content ingestion flow) can neutralize all `action: block` rules defined in that same file for `bash` or `file` tool calls, because the hook process hangs and is killed by timeout instead of returning a `deny` decision. This defeats a user-configured safety control (e.g., a rule meant to block `rm -rf` or sensitive-file edits) without any explicit approval from the victim, matching a hook/approval-bypass class of impact.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs write access to a file matching `.claude/hookify.*.local.md` under the project root the victim later opens with Claude Code (no admin/maintainer rights on the victim's machine are required - just ordinary repository content). The pattern `(a+)+$` (or equivalents) is a well-known, trivially reproducible ReDoS trigger, and the matched text only needs to contain a moderately long repeated-character run, which is common in normal tool-call arguments/content. The bug is deterministic given such input.

### Recommendation
- Run regex matching in `_regex_match`/`compile_regex` under a hard wall-clock budget (e.g., a worker subprocess/thread with `join(timeout=...)`, or `signal.alarm` on POSIX) well under the hook's configured timeout, and treat a timeout as **deny/ask**, never allow, for `action: block` rules.
- Alternatively/additionally, validate patterns at load time with a ReDoS-safe engine (e.g., Google `re2`) or a static analyzer that rejects nested-quantifier constructs before caching them in `compile_regex`.
- Cap input length passed to `_regex_match` and reject unbounded backtracking constructs, or compile with `re.NOFLAG`/timeout-capable libraries instead of stdlib `re`.
- Ensure the PreToolUse/Stop hook's overall exit path defaults to a safe `deny`/`ask` decision (not silent allow) whenever the hook could not complete evaluation within budget.

### Proof of Concept
Fuzz/invariant test plan for `plugins/hookify/core/rule_engine.py`:
```python
import time
import pytest
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

@pytest.mark.parametrize("evil_pattern", [
    r"(a+)+$",
    r"(a|a)+$",
    r"(a|aa)+$",
    r"([a-zA-Z]+)*$",
])
def test_regex_evaluation_is_bounded(evil_pattern):
    rule = Rule(
        name="evil",
        enabled=True,
        event="bash",
        action="block",
        conditions=[Condition(field="command", operator="regex_match", pattern=evil_pattern)],
        message="blocked",
    )
    engine = RuleEngine()
    # 40 'a's followed by a non-matching char triggers catastrophic backtracking
    evil_text = "a" * 40 + "!"
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": evil_text},
    }

    start = time.monotonic()
    try:
        result = engine.evaluate_rules([rule], input_data)
    except Exception:
        result = None
    elapsed = time.monotonic() - start

    # Assert bounded evaluation time (e.g., under the hook's own budget)
    assert elapsed < 2.0, f"regex evaluation took {elapsed}s - unbounded ReDoS"

    # If it did time out/hang instead, the harness-level contract must be
    # deny/ask, not allow - verify evaluate_rules never silently returns {}
    # (empty dict == allow) for a blocking rule whose evaluation was aborted.
    if result is not None:
        assert result != {}, "Blocking rule silently resolved to allow"
```
Run this with a wall-clock watchdog around `RuleEngine.evaluate_rules` (e.g., via `multiprocessing` with a timeout) to demonstrate that current code has no internal bound, then assert that the harness must map "timed out" to `deny`/`ask` rather than `allow`.

```python
def compile_regex(pattern: str) -> re.Pattern:
    """Compile regex pattern with caching.
```

```python
    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
```
