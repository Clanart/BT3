### Title
Integer truncation in `TimeUtil::FromString` (Duration) allows attacker-controlled string to produce a `Duration` with a `nanos` value unrelated to (and of opposite sign from) the input fractional digits - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`google::protobuf::util::TimeUtil::FromString(absl::string_view, Duration*)` parses the fractional ("nanos") part of a Duration string without bounding its length before doing arithmetic scaling and before narrowing the 64-bit intermediate result into the 32-bit `nanos` field. When the fractional digit string is long enough to make the scaling exponent negative, the helper `Pow()` silently becomes a no-op, and the subsequent `static_cast<int32_t>(nanos)` truncates the unmodified `int64_t` value. This lets a client-supplied Duration string produce a `Duration` whose stored `seconds`/`nanos` bear no relation to (and can have the opposite sign of) what the input digits actually represent, while still passing the library's own validity check. This mirrors the Envoy bug class: an attacker-controlled numeric string is fed into unchecked arithmetic used for time/duration calculations, producing a wildly different, attacker-influenced result that downstream logic (timeouts, deadlines, expirations) will silently trust.

### Finding Description
`TimeUtil::FromString` for `Duration` splits the trailing `s`-suffixed value into `seconds_part` and `nanos_part` at the decimal point, with no bound on how many digits `nanos_part` may contain: [1](#0-0) 

It then parses both parts with `strtoll` and scales the fractional part to nanosecond precision using a locally defined `Pow` helper: [2](#0-1) [3](#0-2) 

Two unchecked invariants combine here:
1. `Pow(10, 9 - nanos_part.length())` is called with a **negative** exponent whenever `nanos_part.length() > 9`. `Pow`'s `for (int i = 0; i < y; ++i)` loop never executes for negative `y`, so it silently returns `1` instead of erroring or scaling down — this is the "missing check" analogous to Envoy's missing bound on the untrusted `grpc-timeout` value before its arithmetic.
2. `nanos` (an `int64_t` that can be as large as `strtoll` will return, up to `LLONG_MAX`, since digit strings up to 19+ characters are accepted) is then narrowed via `static_cast<int32_t>(nanos)` with no overflow check. Because step 1 already failed to rescale it, this cast performs an unchecked 64→32-bit truncation, taking the low 32 bits of an attacker-chosen 64-bit integer.

The attacker fully controls the digit string after the decimal point, and thus can choose a value whose low 32 bits are an essentially arbitrary signed 32-bit integer (including negative), completely decoupled from and even opposite in sign to the actual fractional value the digits represent (e.g. a string that visually encodes "almost 1 second" can decode to `nanos = -1`).

`IsDurationValid` is invoked afterward, but it only checks that `nanos` lies in `[-999999999, 999999999]` and that sign(`seconds`) and sign(`nanos`) agree — a truncated small value (e.g. `-1`) trivially passes both checks, especially when `seconds == 0` (zero has no enforced sign), so the corrupted `Duration` is accepted and returned as valid: [4](#0-3) 

### Impact Explanation
`TimeUtil::FromString` is a supported public parsing API that applications use to convert untrusted duration strings (e.g. from JSON payloads, config, or headers relayed through a service) into `google.protobuf.Duration` messages. A successfully-parsed `Duration` is then typically fed into time arithmetic (`DurationToNanoseconds`, `DurationToMillis`, timeout/deadline computations, etc.) with `ABSL_DCHECK`-only validation, meaning in release builds no additional bounds re-check occurs: [5](#0-4) . If a crafted duration string that looks like a large, "safe" value is silently reinterpreted as a tiny or negative duration (or vice versa), downstream timeout/expiry logic built on top of this API can compute an unexpectedly short or long effective timeout — the same class of impact ("remotely exploitable integer overflow... leads to unexpected timeout calculations") described in the Envoy advisory. This is a data-integrity failure in the parsed value, not a memory-safety crash, but it directly affects any time-sensitive decision built on the parsed `Duration`.

### Likelihood Explanation
Reaching this path only requires calling `TimeUtil::FromString(value, &duration)` with an attacker-controlled string containing an excessively long fractional part (more than 9 digits, up to ~19 digits before `strtoll` itself saturates). No special privileges, malformed schema, or memory corruption is required — a single call with a well-formed-looking string such as `"0.9223372036854775807s"` triggers the truncation deterministically. The existing unit test suite only exercises 10-digit fractional overflow (`time_util_test.cc:519`, rejected because the untruncated 10-digit value already exceeds `999999999`), and does not cover the case of 19-digit strings that wrap through the `int32_t` cast, so this specific truncation path is not covered by current tests.

### Recommendation
- Reject `nanos_part` inputs with more than 9 digits up front (mirroring what the JSON `ParseDuration` path in `src/google/protobuf/json/internal/parser.cc` effectively guards against via bounded digit consumption), instead of relying on `Pow` with a possibly-negative exponent.
- Change `Pow` to `ABSL_CHECK`/return an error for negative exponents rather than silently returning `1`.
- Avoid the unchecked narrowing `static_cast<int32_t>(nanos)`; validate that the intermediate `int64_t` fits in `int32_t` range before assignment, and fail parsing (return `false`) rather than truncating.

### Proof of Concept
Conceptual (not run — narrative reproduction based on code trace):
1. Call `TimeUtil::FromString("0.9223372036854775807s", &d)`.
2. `seconds_part = "0"`, `nanos_part = "9223372036854775807"` (19 digits, exactly `INT64_MAX`).
3. `strtoll("9223372036854775807")` → `nanos = INT64_MAX = 0x7FFFFFFFFFFFFFFF` (no overflow at this step).
4. `Pow(10, 9 - 20) == Pow(10, -11)` → loop body never runs → returns `1`; `nanos` remains `INT64_MAX`.
5. `duration->set_nanos(static_cast<int32_t>(INT64_MAX))` → truncates to low 32 bits → `nanos = -1`.
6. `duration->set_seconds(0)`.
7. `IsDurationValid(*duration)` — `nanos == -1` is within `[-999999999, 999999999]`, and `seconds == 0` has no enforced sign — validation passes.
8. Result: `TimeUtil::FromString` returns `true` with `duration.seconds() == 0`, `duration.nanos() == -1`, even though the input string's digits encode a value close to (and intended to be) one full second, not `-1` nanosecond.

  }

}
