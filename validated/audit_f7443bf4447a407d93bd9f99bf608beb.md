## Title
`popStashEntry` deletes the desktop stash entry based on an unverified heuristic, permanently destroying uncommitted user changes when the heuristic's assumption is wrong - (File: `app/src/lib/git/stash.ts`)

### Summary
The report's broken invariant is: *code assumes a specific "successful" outcome and permanently disposes of a user asset (tokens) without verifying that the asset was actually delivered before doing so; when the assumed outcome fails to hold (a revert), the asset is destroyed/lost with no recovery path.*

The Desktop analog is `popStashEntry` in [1](#0-0) , which interprets `git stash pop` exiting with code `1` and empty `stderr` as proof that the stash was "popped successfully" and then unconditionally deletes the desktop stash ref via `dropDesktopStashEntry`, without ever checking that the stashed content actually landed in the working directory.

### Finding Description
`popStashEntry` runs `git stash pop --quiet <name>` and only treats `GitError.MergeConflicts` as an expected error via `expectedErrors`: [2](#0-1) 

When the git call rejects with any other `GitError`, the `.catch` handler applies a heuristic:

```
if (
  e instanceof GitError &&
  e.result.exitCode === 1 &&
  e.result.stderr.length === 0
) {
  // "bye bye" — drop the stash, assuming it was already applied
  return dropDesktopStashEntry(repository, stashSha)
}
```

The comment itself admits the fragility: *"Not the greatest approach but stash isn't very communicative."* The code never re-checks `getStatus()`/working-directory contents to confirm the stashed files are actually present before calling `dropDesktopStashEntry`, which runs `git stash drop <name>` and permanently removes the only reference to that stash's blob tree from the reflog-backed stash list (see `dropDesktopStashEntry` at [3](#0-2) ). Once dropped, `git stash pop` provides no other retrievable handle to the entry (barring manual `git fsck`/reflog forensics that Desktop's UI does not expose).

This mirrors the `XC20Wrapper` flaw exactly: the guard is written under the assumption that a particular failure signature ("exit 1, empty stderr") can only mean "the operation actually succeeded, just didn't clean up," so it proceeds to a destructive, irreversible action (mint the wrapped token / drop the stash) instead of verifying the actual state of the asset first.

### Impact Explanation
Any code path, filesystem condition, filter/hook, or dugite/git version quirk that can cause `git stash pop` to exit with code `1` and produce no stderr output **without actually restoring the stashed changes** to the working directory will cause Desktop to silently and permanently delete the user's stash entry - which is often the only copy of uncommitted work that a user explicitly asked Desktop to preserve (e.g. via "Stash changes and switch branches"). This is a silent corruption/loss of what the user was about to commit, satisfying the "silent corruption of what the user commits" impact category, with no error surfaced to the user (the catch path returns normally instead of rejecting).

### Likelihood Explanation
The exit-code/stderr heuristic is inherently unreliable because it is keyed off dugite/git process output shape rather than a verified post-condition. `git stash pop` internally performs a merge of the stash's tree into the working directory, which is influenced by repository content pulled from a remote/fork (file modes, symlinks vs. files, case-sensitivity conflicts, partial-clone/sparse-checkout interactions, or platform-specific I/O errors triggered by adversarial file names/paths in a cloned repository). Because the heuristic accepts *any* exit-1/empty-stderr failure as "success," a cloned or fetched repository crafted to make the merge step fail in that exact shape (rather than the expected `MergeConflicts` shape) is sufficient to trigger the destructive drop, without requiring local/physical access, admin rights, or prior malware.

### Recommendation
Do not infer success from exit code/stderr shape alone. After a non-conflict failure of `git stash pop`, call `getStatus()`/diff the working directory against the stash's tree to positively confirm the stashed changes were applied before invoking `dropDesktopStashEntry`. If verification cannot be performed, surface the error to the user and leave the stash entry intact (fail closed, analogous to the `_safeMint`-style mitigation adopted for the original report, which checks the actual outcome instead of assuming success).

### Proof of Concept
1. Set up a repository with a desktop stash entry (`createDesktopStashEntry`) whose contents, when merged back via `git stash pop`, are forced by repository/filesystem conditions to fail the internal merge step with exit code `1` and no stderr output (e.g., by engineering a working-directory/file-mode condition — such as a directory/file type conflict introduced by cloning a crafted repository — that causes the underlying `git merge-recursive`/`read-tree` step invoked by `stash pop` to abort in that exact signature instead of emitting the standard conflict markers Desktop expects via `GitError.MergeConflicts`).
2. Call `popStashEntry(repository, stashSha)` as done in `_popStashEntry` ( [4](#0-3) ).
3. Observe that `.catch` in [5](#0-4)  matches the exit-code-1/empty-stderr branch and calls `dropDesktopStashEntry`, deleting the stash even though the working directory does not contain the previously stashed changes — the user's uncommitted work is now unrecoverable through the Desktop UI.

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
