Confirmed: `mWomSV.sol` has a fully-implemented `getRewardablePercentWAD()` function (mirroring `VLMGP.sol`) that computes the fraction of a user's `mWomSV` balance that is *not* subject to forfeiture based on their unlock/cooldown schedule [1](#0-0) . The companion reward contract, `vlMGPBaseRewarder.sol`, correctly calls this analog (`vlMGP.getRewardablePercentWAD(_account)`) inside `_calExpireForfeit()` to compute the forfeited share of a user's pending reward [2](#0-1) .

However, `mWOMSVBaseRewarder.sol`'s `_calExpireForfeit()` — the equivalent function meant to forfeit `mWomSV` holders' unclaimed rewards for locked/cooling-down balances — never calls `mWomSV.getRewardablePercentWAD()`. Instead it sets `rewardableAmount = _amount` unconditionally, making `forfeitAmount = _amount - rewardableAmount` always `0`, regardless of the account's actual unlock state [3](#0-2) .

### Title
Forfeiture logic in mWOMSVBaseRewarder is dead code, permanently freezing forfeited yield owed to other stakers - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit()` is supposed to mirror `vlMGPBaseRewarder._calExpireForfeit()` and reduce a user's claimable reward based on how much of their `mWomSV` balance is still locked vs. in cooldown/unlocked, redistributing the forfeited portion to remaining stakers via `_queueNewRewardsWithoutTransfer()`. Because it hardcodes `rewardableAmount = _amount` instead of using `mWOMSV.getRewardablePercentWAD(_account)`, the forfeiture check is a tautology (`rewardableAmount > _amount` can never be true) and `forfeitAmount` is always `0`.

### Finding Description
`_calExpireForfeit()` in `mWOMSVBaseRewarder.sol` [3](#0-2)  is called from `_sendReward()` every time a reward is paid out via `getReward`/`getRewards` [4](#0-3) . The intended design — visible in the parallel `vlMGPBaseRewarder` implementation — is to compute `rewardableAmount` as a fraction of `_amount` scaled by `getRewardablePercentWAD(_account)`, which accounts for the locker's `userUnlockings` cooldown slots [2](#0-1) . `mWomSV.sol` exposes the exact same `getRewardablePercentWAD()` helper needed for this [1](#0-0) , but `mWOMSVBaseRewarder` never calls it. As written, `rewardableAmount` is simply assigned `_amount`, so `forfeitAmount` is always `_amount - _amount = 0` for every account, no matter how much of their stake is in cooldown/unlocked and no longer entitled to full boosted yield.

### Impact Explanation
Users who start unlocking (or have already unlocked) their `mWomSV` are still able to claim 100% of newly accrued rewards through `mWOMSVBaseRewarder.getReward`/`getRewards`, when a portion of that yield was meant to be forfeited and redistributed to users who remain fully locked (via `_queueNewRewardsWithoutTransfer`). This results in permanent misallocation/freezing of yield intended for long-term lockers — the forfeited share never accrues to `rewardPerTokenStored` for other stakers because it is never computed or queued. This is a protocol-level accounting defect affecting unclaimed yield distribution for every `mWomSV` reward claim, not a one-off or negligible edge case.

### Likelihood Explanation
The defective code path executes on every single call to `getReward`/`getRewards` on `mWOMSVBaseRewarder` for any `mWomSV` holder with any reward token, i.e., on the standard user claim flow, with no special preconditions required. Likelihood is effectively certain (100%) since it is unconditional dead code, not dependent on any adversarial input.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit()` to mirror `vlMGPBaseRewarder._calExpireForfeit()`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```
This requires `ILocker` (the interface typed as `mWOMSV`) to expose `getRewardablePercentWAD`, consistent with how `vlMGPBaseRewarder` consumes `vlMGP.getRewardablePercentWAD(...)`.

### Proof of Concept
1. User locks `mWOM` via `mWomSV.lock()`, accruing `mWomSV` balance and staking it through `MasterMagpie`.
2. User calls `mWomSV.startUnlock(fullAmount)`, moving their entire balance into a cooldown slot (`userUnlockings`), which per `getRewardablePercentWAD()` should drop their rewardable percent toward 0% while still in cooldown (unless already past `endTime`) [5](#0-4) .
3. Reward tokens continue to accrue to the pool via `queueNewRewards`/`donateRewards` while the user is in cooldown, increasing `rewardPerTokenStored`.
4. User (still in cooldown, well before `endTime`) calls `MasterMagpie` → `mWOMSVBaseRewarder.getReward()`/`getRewards()`, which invokes `_sendReward()` → `_calExpireForfeit()` [4](#0-3) .
5. Because `_calExpireForfeit()` always returns `0`, the user receives 100% of `userRewards[_rewardToken][_account]` with no forfeiture, and no amount is queued back to `rewardInfo.rewardPerTokenStored` via `_queueNewRewardsWithoutTransfer()` for remaining long-term lockers — permanently denying them the yield share the protocol's forfeiture design entitles them to.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
