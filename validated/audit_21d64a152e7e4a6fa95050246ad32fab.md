## Analog Found

### Title
Attacker-controlled `WWW-Authenticate` realm header spoofs GitHub host classification in credential helper, triggering trusted "Sign in to GitHub" UI for arbitrary remotes - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The escrow bug's broken invariant is: an optional/attacker-influenceable input (`i_arbiter == address(0)`) is used as the sole gate for a security-relevant state transition, and the guard is trusted without an independent verification path, leaving the system in an unrecoverable/mistrusted state. The closest Desktop analog is `getEndpointKind()` in the git-credential trampoline, which classifies an unknown remote as a trusted `'enterprise'`/`'ghe.com'` GitHub endpoint purely by string-matching a `WWW-Authenticate` header value that is fully controlled by the remote server Desktop is talking to, instead of doing the network-verified `isGitHubHost()` check that exists lower in the same function for exactly this purpose. [1](#0-0) 

### Finding Description
`getEndpointKind()` is called by `getCredential()` while Git is authenticating an HTTPS remote. Git forwards any `WWW-Authenticate` response headers it received from the remote to the credential helper as `wwwauth[]` fields, and Desktop reads these directly out of attacker-controlled HTTP response data: [2](#0-1) 

If the value contains the substring `realm="GitHub"`, Desktop unconditionally classifies the endpoint as `'enterprise'` — skipping the legitimate, network-verified `isGitHubHost()` check that exists later in the same function (line 178) specifically to guard against exactly this kind of host-classification error: [3](#0-2) 

This misclassification then flows into `getCredential()`. Because the endpoint is no longer treated as `'generic'`, and no existing account matches this new/attacker host, Desktop calls `ui.promptForGitHubSignIn(endpoint)` instead of the plain generic-git-auth username/password prompt: [4](#0-3) 

`promptForGitHubSignIn` then drives the real "Sign in to GitHub"/GitHub Enterprise OAuth flow, using the attacker's own host as the OAuth endpoint (`beginEnterpriseSignIn` + `setSignInEndpoint(origin)`), and opens the OS browser to that host's `/login/oauth/authorize` URL: [5](#0-4) [6](#0-5) 

The corrupted value is the `endpointKind` classification (`'enterprise'` vs `'generic'`), which is derived entirely from attacker-supplied header text rather than a network-verified fact. The existing guard that should stop this (`isGitHubHost()`, which performs a real HTTP round-trip and checks the `x-github-request-id` response header) is bypassed entirely because the header-matching branch returns early before that check is ever reached.

### Impact Explanation
An attacker who controls the HTTP server/proxy behind any git remote (a URL a user is asked to clone, fetch from, or push to — no elevated privileges needed) can respond to an authentication challenge with `WWW-Authenticate: Basic realm="GitHub"`. This causes Desktop's own credential trampoline to surface its native, trusted "Sign in to GitHub"/"Sign in to your GitHub Enterprise Server instance" dialog and OAuth browser flow for that attacker's domain, lending Desktop's own UI trust indicators to what is otherwise an arbitrary phishing endpoint. This is a real path for credential/token phishing initiated purely by connecting Desktop to an attacker-controlled remote, matching the report's "unprivileged, attacker-controlled remote/proxy response" and "credential/token exfiltration" categories.

### Likelihood Explanation
Triggering the header requires nothing beyond the victim performing a normal Desktop operation (clone/fetch/push/pull) against a URL the attacker controls or has compromised (e.g., a malicious or hijacked self-hosted git server, a corporate proxy under attacker control, or a spoofed "GitHub Enterprise" URL shared with the victim). No local access, malware, or leaked credentials are needed — only a crafted HTTP response header, which is a very low-effort attacker action.

### Recommendation
Do not treat the `wwwauth[]`/`realm` header as authoritative for classifying a host as GitHub/GHE. Either remove the header-based shortcut entirely and always fall back to the network-verified `isGitHubHost()` check, or require that the shortcut only be used to *skip a network round-trip when the endpoint has already been independently verified*, not to *promote* an unknown/new endpoint straight to the trusted GitHub sign-in flow.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM-capable proxy) at `https://attacker.example.com/victim/repo.git`.
2. Victim runs `git clone`/`fetch`/`push` against this URL from within GitHub Desktop.
3. When Desktop's trampoline credential helper asks for credentials, the attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Git forwards this as a `wwwauth[0]=Basic realm="GitHub"` field to Desktop's `git credential fill` invocation, landing in `getEndpointKind()`.
5. `getEndpointKind()` returns `'enterprise'` for `attacker.example.com` without ever calling `isGitHubHost()`.
6. `getCredential()` sees `endpointKind !== 'generic'` and no matching account, and calls `ui.promptForGitHubSignIn('https://attacker.example.com/...')`, which opens Desktop's native GitHub sign-in dialog and browser-based OAuth flow pointed at the attacker's domain — a much more convincing phishing vector than the plain generic-credential username/password prompt that should have been shown instead.

Note: I was not able to find a corresponding published GitHub Desktop advisory/CVE for this exact code path in the available index, and the exact downstream consequence (whether attacker's OAuth page can fully harvest a working GitHub.com token vs. only phish attacker-domain credentials) depends on how the OAuth callback is completed, which I could not fully trace within the available tool budget. This should be verified further (e.g., whether `resolveOAuthRequest`'s endpoint/account binding could allow cross-endpoint token confusion) before treating severity as High.

  // use them as a happy-path to determine if the host is a GitHub host without

  for (const [k, v] of cred.entries()) {

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
