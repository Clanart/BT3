### Title
Silent error-swallowing in EVM EndBlock surplus reconciliation causes silent usei/wei loss instead of failing hard - ([File: x/evm/keeper/abci.go])

### Summary
`Keeper.EndBlock` reconciles the per-block "surplus" (leftover usei/wei generated by EVM fee/balance accounting during transaction execution and the ante handler) by crediting it back to the EVM module account and to per-tx coinbase escrow accounts. Just like the Stellar-core `ConservationOfLumens` bug, every failure path here only calls `logger.Error(...)` and continues execution instead of propagating the error and halting/failing the block, allowing balance/supply corruption to pass silently.

### Finding Description
In `EndBlock`, for every deferred EVM tx, the coinbase escrow balance is swept to the block's fee collector/coinbase account: [1](#0-0) 
and the aggregated ante+execution surplus is credited to the EVM module account: [2](#0-1) 

In both cases, if `SendCoinsAndWei`, `AddCoins`, or `AddWei` returns an error (e.g. a blocked-address check, invalid coin validation, or any other keeper-level failure), the code only logs the error via `logger.Error` and continues — it never returns an error from `EndBlock`, never panics, and never aborts the block. This means the usei/wei that was already debited from the per-tx coinbase escrow account (via `SubUnlockedCoins`/`SubWei` inside `x/evm/state/balance.go`, `AddBalance`/`SubBalance`) is not properly re-credited to the module account/coinbase, effectively vanishing from the visible balance graph while `x/bank`'s `Supply` field is unaffected — i.e., a class of corruption identical in spirit to the Stellar bug: an accounting reconciliation step that is supposed to enforce "money is conserved" but instead silently no-ops on error.

This is not purely theoretical: the codebase contains a dedicated migration, `x/evm/migrations/fix_total_supply.go`, explicitly created "to fix total supply mismatch caused by mishandled ante surplus" [3](#0-2) , confirming that this exact surplus-reconciliation code path has previously caused real on-chain supply/balance corruption in production.

### Impact Explanation
If any of the `AddCoins`/`AddWei`/`SendCoinsAndWei` calls in this reconciliation path fail for a triggerable reason (e.g. an EVM module or coinbase address becoming blocked, or a validation failure introduced by any future upstream `bank` change), the debited surplus/escrow usei or wei is permanently lost from any account — a permanent, silent token destruction that breaks the `x/bank` `TotalSupply` invariant without halting the chain or alerting operators in-band (only a log line). Because `EndBlock` runs unconditionally every block for every EVM transaction with nonzero coinbase escrow or ante surplus, this can compound over many blocks, causing systemic value loss.

### Likelihood Explanation
The escrow accounts (`state.GetCoinbaseAddress(idx)`) and the EVM module account are both derived, low-entropy addresses; the `BlockedAddr` check in the bank keeper's `SendCoinsAndWei` blocks certain protected/derived address shapes (e.g. `CoinbaseAddressPrefix`-based addresses) from being *sent to*. If any future change (or existing edge condition) causes the coinbase target itself, or the EVM module account, to be treated as blocked/negative/invalid by the bank keeper checks reached from these calls, every affected block silently drops real value with no on-chain signal, matching the "logs but doesn't fail" pattern from the Stellar report. The precondition is narrower than a fully generic bug (it requires the underlying `bank` call to actually fail), which is why this is Medium rather than Critical, but the error-handling defect itself is present and unconditionally reachable from ordinary EVM transaction processing.

### Recommendation
Do not swallow errors from `SendCoinsAndWei`, `AddCoins`, and `AddWei` in `EndBlock`. Propagate the error out of `EndBlock` (panicking/halting the block, consistent with how other supply-critical operations in this codebase — e.g. `app/invariance.go`'s light invariance checks — panic on inconsistency) rather than merely logging, so that surplus/escrow reconciliation failures cannot silently corrupt account balances or total supply.

### Proof of Concept
1. Construct or identify a state where the EVM module account address or a `coinbaseAddress` (`state.GetCoinbaseAddress(idx)`) is rejected by `BaseSendKeeper.BlockedAddr`/`CanSendTo` checks invoked transitively by `SendCoinsAndWei`/`AddWei` (see `giga/deps/xbank/keeper/send.go` / `sei-cosmos/x/bank/keeper/send.go` `AddWei`, which calls `CanSendTo` and returns `ErrInvalidRecipient` if blocked).
2. Submit an ordinary EVM transaction that generates positive `Surplus`/coinbase escrow balance (e.g. any tx that pays fees, per `x/evm/ante/fee.go`'s `AddAnteSurplus` and `x/evm/state/balance.go`'s surplus tracking).
3. At `EndBlock`, the debit from the escrow/coinbase account already occurred during tx execution, but the credit-back call fails and is only logged at `x/evm/keeper/abci.go:130-132` and `x/evm/keeper/abci.go:139,144`.
4. Observe that `x/bank`'s recorded total supply invariant (`sei-cosmos/x/bank/keeper/invariants.go` `TotalSupply`) will diverge from the sum of on-chain balances, confirming silent value loss — the same failure mode the historical `FixTotalSupply` migration was written to repair.

// This migration is to fix total supply mismatch caused by mishandled

func FixTotalSupply(ctx sdk.Context, k *keeper.Keeper) error {
	balances := k.BankKeeper().GetAccountsBalances(ctx)
	correctSupply := sdk.ZeroInt()
	for _, balance := range balances {
		correctSupply = correctSupply.Add(balance.Coins.AmountOf(sdk.MustGetBaseDenom()))
	}
