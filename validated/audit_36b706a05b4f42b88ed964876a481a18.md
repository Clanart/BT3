### Title
Decimal-precision invariant is enforced only at registration time, allowing bridge-value amplification when an asset's decimals change afterward — (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `register_token`/`update_token` enforce `config.decimals >= local_decimals` (`ErcDecimalsBelowLocal`) only once, at registration time [1](#0-0) . The actual local decimals used at transfer time are fetched dynamically from the underlying `fungibles::metadata::Inspect` implementation on every `send`, `on_accept`, and `on_timeout` call [2](#0-1) [3](#0-2) , while the ERC-side decimals (`Precisions`) are a static value set once at registration. The decimal-scaling helpers use `saturating_sub` instead of an explicit invariant check, silently clamping to zero rather than reverting [4](#0-3) . This is a Notional-style "parameter never re-validated against the actual object it is being combined with" analog: the registration-time guard silently stops protecting the system the moment the fetched local decimals value diverges from what was true at registration.

### Finding Description
`register_token` computes `local_decimals` once and requires `config.decimals >= local_decimals` before storing `erc_decimals` in `Precisions` [1](#0-0) . `update_token` repeats the same one-time check when adding chains [5](#0-4) .

However, at actual transfer time — `send()`, `on_accept()`, `on_timeout()` — `local_decimals` is *not* the value captured at registration; it is re-read live from `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(asset_id)`:

- `send()`: `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(params.asset_id.clone())` [6](#0-5) 
- `on_accept()`: `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(local_asset_id.clone())` [7](#0-6) 
- `on_timeout()`: same pattern [8](#0-7) 

If the underlying asset's decimals metadata is later changed (e.g. via `pallet-assets::set_metadata`, callable by that asset's own owner/admin — a role entirely separate from this pallet's `CreateOrigin`) so that `local_decimals > erc_decimals`, the scaling functions do not detect or reject the now-violated invariant:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```
`erc_decimals.saturating_sub(local_decimals)` clamps to `0` instead of reverting, so `convert_to_erc20` stops scaling down entirely and forwards the raw local balance value unscaled as the ERC20 amount [9](#0-8) . Since `local_decimals` now exceeds `erc_decimals`, one raw local unit is worth far less than one raw ERC20 unit at `erc_decimals`, so the message sent to the destination chain claims an amount many orders of magnitude larger than what was actually locked/burned.

### Impact Explanation
`send()` burns/locks the caller's local asset and then embeds `convert_to_erc20(...)` output directly as the cross-chain `amount` dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract [10](#0-9) . Once the decimals invariant is silently broken post-registration, a user burning a small amount of the local asset can cause the destination chain to mint or unlock an amount many orders of magnitude larger — a direct amplification/inflation of bridged value, i.e., unauthorized minting/unlocking of funds on the destination side backed by an inadequate local burn/lock. This matches the bounty's "stealing or loss of funds" / "false state acceptance" categories, since the bridge's custody/backing invariant (1 destination unit == 1 correctly-scaled locked/burned local unit) is violated.

### Likelihood Explanation
This requires that some non-`CreateOrigin` actor be able to change the decimals metadata of an asset already registered in `TokenContracts`/`NativeAssets`/`Precisions` after registration. Whether this is realistically reachable depends entirely on runtime configuration of the `Assets` pallet (whether asset metadata is permissionless, owned by an entity distinct from this bridge's admin, or lockable). The pallet itself provides no runtime-enforced guarantee (e.g. freezing metadata, or re-checking the invariant on every transfer) that this can never happen — the `saturating_sub` clamp guarantees silent, non-reverting mis-scaling instead of a hard failure if it does.

### Recommendation
- Store `local_decimals` at registration time in the same way `erc_decimals` is stored (rather than re-reading it live from the asset registry), or re-validate `erc_decimals >= local_decimals` on every `send`/`on_accept`/`on_timeout` call and hard-error (not `saturating_sub`) if the invariant no longer holds.
- Replace `saturating_sub` in `convert_to_erc20`/`convert_to_balance` with a checked subtraction that returns an error instead of clamping to zero.
- Consider requiring the bridged asset's metadata to be frozen/immutable (or owned by the same `CreateOrigin`) for any asset registered with this pallet.

### Proof of Concept
1. `CreateOrigin` registers asset `A` (non-native/imported) via `register_token` with `local_decimals = 6` and `config.decimals (erc) = 6` on chain `Evm(X)`; the `ErcDecimalsBelowLocal` check passes and `Precisions[A, X] = 6` is stored [11](#0-10) .
2. Asset `A`'s owner (a separate, non-privileged actor relative to this pallet's `CreateOrigin`) later calls `pallet-assets::set_metadata` to change `A`'s decimals to `18`.
3. Attacker (holder of asset `A`) calls `send()` with `asset_id = A`, `amount = 1_000_000` (raw units, i.e. 1 token at the new 18-decimal reading is a dust amount, but is still meaningful at the stored erc precision).
4. `send()` fetches `decimals = 18` live from the assets pallet while `erc_decimals = 6` remains from `Precisions` [12](#0-11) .
5. `convert_to_erc20(1_000_000, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1_000_000` is dispatched unscaled, instead of being divided down by `10^12`, to the destination `HyperFungibleToken` contract, which mints/unlocks `1_000_000` raw ERC20 units (a 10^12x amplification versus the correctly-scaled amount) to the attacker's chosen recipient [13](#0-12) .

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
