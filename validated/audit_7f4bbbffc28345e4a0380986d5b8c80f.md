### Title
Deterministic nonce reuse across `share`/`complete` calls leaks the validator's MuSig secret share — (`coordinator/src/tributary/signing_protocol.rs`)

### Summary
Analogous to the Nudge report — where an unrestricted path lets anyone repeatedly drive a privileged actor (`Executor`) into performing a self-destructive privileged action — the tributary's `SigningProtocol` deterministically regenerates its FROST sign machine from a DB-cached seed on **every** call, keyed only by a coarse context. Each subsequent `share()`/`complete()` invocation within the same context signs a potentially distinct message with the **same nonce**, enabling third-party recovery of the validator's private key share (the root-of-trust MuSig key used for `set_keys` confirmation and slash reports).

### Finding Description
`preprocess_internal` loads a `CachedPreprocess` seed from `CachedPreprocesses` keyed by `self.context`, decrypts it, and rebuilds the sign machine via `AlgorithmSignMachine::from_cache`. The seed is set once per context and never rotated:

```rust
// coordinator/src/tributary/signing_protocol.rs
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  let (machine, _) = AlgorithmMachine::new(...).preprocess(&mut OsRng);
  ... CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
```

`from_cache` → `seeded_preprocess` derives the FROST nonces from `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:121-144`), so identical seeds always produce identical nonces and identical published commitments `R`.

For `DkgConfirmer`, the context is `(b"DkgConfirmer", self.attempt)` (`signing_protocol.rs:274-277`) — it does **not** bind:
- the message being signed (`set_keys_message(set, removed, key_pair)`, where `key_pair` and `removed` can vary),
- nor the set of preprocesses used to compute the FROST binding factors `rho`.

`share_internal` calls `preprocess_internal` again (`signing_protocol.rs:156`) and then `machine.sign(preprocesses, msg)`. `DkgConfirmer::share` (`:304-310`) and `DkgConfirmer::complete` (`:312-327`, which itself re-calls `share_internal`) therefore regenerate the same nonces for every distinct invocation within one attempt. The module's own safety argument (`:25-48`) relies on received messages being identical under BFT re-execution — but that only holds if every re-invocation signs *byte-identical* messages with *byte-identical* preprocess sets. Any second call with a different `key_pair` (a `KeyPair` covers multiple network keys per set), a changed `removed` set, or a different accumulated preprocess set produces a second Schnorr share `s'` under the same nonce:

`s = d + e·share`, `s' = d + e'·share` → `share = (s - s')/(e - e')`.

The FROST binding factor `rho` is a transcript challenge over the preprocesses (`crypto/frost/src/sign.rs:315+`), so even signing the *same* message with different counterparties' preprocesses yields a different `rho` and hence a different effective nonce/message pair — a classic ROS/deterministic-nonce failure.

### Impact Explanation
Recovery of a validator's Ristretto secret share — the coordinator's root-of-trust signing key for MuSig confirmations. Since the MuSig aggregate key is what authorizes `set_keys` on Substrate, leaking shares degrades the supermajority assumption underpinning all DKG confirmations and slash reports. The preprocesses and shares are published publicly on-chain, so anyone observing two distinct shares under identical `R` commitments recovers the share.

### Likelihood Explanation
The trigger does not require a malicious validator: any code path that calls `share()` more than once per `(b"DkgConfirmer", attempt)` context with differing `key_pair`, `removed`, or accumulated preprocess set suffices — e.g., re-execution after a partial rebuild (acknowledged in the file's own commentary as not fully guarded, `:45-48`), or confirming multiple keys within one attempt. I could not fully enumerate every caller of `DkgConfirmer::share`/`complete` in `handle.rs` within the tool budget, so the exact triggering sequence is partially verified; the deterministic reuse itself is fully confirmed in `signing_protocol.rs` and `crypto/frost/src/sign.rs`.

### Recommendation
Bind the cached-preprocess context (and/or a DB flag) to the exact message and preprocess-set hash being signed, and refuse — via a persistent "already signed" marker keyed by context — any second `share`/`complete` invocation under a consumed context rather than silently re-deriving the same nonces. Alternatively, derive the nonce seed as `H(context || msg || sorted_preprocesses)` so distinct inputs never reuse nonces.

### Proof of Concept
Conceptual: within one `attempt`, cause `DkgConfirmer::share(preprocesses_A, key_pair)` to run, then cause it to run again with `preprocesses_B ≠ preprocesses_A` (or a distinct `key_pair`/`removed`). Both calls rebuild `AlgorithmSignMachine` from the identical `CachedPreprocess` seed, emitting shares `s`, `s'` under identical nonce commitments `R` but different binding factors/challenges. Given both published shares, compute `share = (s - s')·(e - e')⁻¹` mod the Ristretto group order to recover the validator's MuSig secret share. [1](#0-0) [2](#0-1) [3](#0-2)

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
