## Verdict: Valid vulnerability found

### Title
Relayer reward payout is not rolled back when `ReputationAsset::mint_into` fails, permanently freezing the `LastRewardedHeight` watermark and enabling repeated/duplicate treasury reward payouts for the same block span - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::<T>::process_message` transfers the relayer reward from the Treasury **before** minting the reputation token, but only advances the `LastRewardedHeight` watermark **after** the mint succeeds. If `T::ReputationAsset::mint_into` fails deterministically (e.g. because the relayer account is kept below the reputation asset's existential deposit), the treasury payment is irreversibly executed while the watermark used to prevent double-payment is never updated.

### Finding Description
In `process_message`: [1](#0-0) 

the order of operations is:
1. `T::Currency::transfer` moves `reward` from the Treasury account to `relayer_account` (irreversible, unconditioned on later steps).
2. `T::ReputationAsset::mint_into` is called; if it errors, `process_message` returns `Err(Error::ReputationMintFailed)` **before** reaching `LastRewardedHeight::<T>::mutate`.
3. Only on full success does `LastRewardedHeight` advance to `state_machine_height.height`.

The caller in `on_executed` discards this error explicitly: [2](#0-1) 

so the Treasury debit already happened, is never reverted, and the failure is silently swallowed.

Because `calculate_reward` computes the payable span using `LastRewardedHeight` as the baseline: [3](#0-2) 

if the watermark never advances (because mint keeps failing), every subsequent successful consensus update for that `state_machine_id` recomputes the reward from the same stale baseline to the new `latest_commitment_height`. This causes the same already-paid block span to be paid again (and again, cumulatively growing) each time the chain advances, rather than being scoped strictly to newly delivered blocks as the watermark comment promises: [4](#0-3) 

The consensus handler prevents literally resubmitting the *same* height twice (`state_machine_commitment` dedup / monotonic height check): [5](#0-4) 

but this does not stop the exploit — the attacker just needs the chain to keep advancing (which happens naturally/legitimately over time) while their own reputation-asset account remains permanently unmintable. Every new legitimate `StateMachineUpdated` event for that state machine will then re-pay from the frozen baseline, growing every relayer reward payout well beyond the actual newly-relayed span.

### Impact Explanation
This breaks the "reward paid at most once per block-span" invariant and lets an unprivileged attacker who merely (a) submits/attributes themselves as the relayer for consensus messages (permitted — the `signer` field just needs a valid signature, not privileged access) and (b) keeps their `ReputationAsset` account under the existential deposit, drain the Treasury's `T::Currency` reward pool repeatedly for spans that were already nominally paid. This is unauthorized/duplicate settlement of treasury funds to an attacker-chosen beneficiary — squarely within the "stealing or loss of funds" and "replay/double-claim/double-settlement" impact categories.

### Likelihood Explanation
High. No privileged action is required. The attacker only needs to be the entity submitting consensus messages (already permissionless via unsigned extrinsic + self-attributed signer) and control their own reputation-asset account balance, which is trivial (simply never fund it above ED).

### Recommendation
Make the reward transfer and watermark update atomic: either (1) advance `LastRewardedHeight` before or regardless of the `ReputationAsset::mint_into` outcome (treating minting as best-effort/non-critical), or (2) perform the mint (or reserve funds) before the currency transfer and roll back the `Currency::transfer` if any subsequent step fails, ensuring the watermark and payout state change together transactionally (e.g. wrap both mutations so a later `Err` cannot leave the transfer applied without the accounting update, using `frame_support::storage::with_transaction` or by computing/mutating the watermark first and only transferring once success is guaranteed).

### Proof of Concept
1. Configure a mock `ReputationAsset::mint_into` that always returns `Err` for a given account (or use an asset with an existential deposit greater than the computed reward, and never fund the relayer's reputation-asset account).
2. Set `StateMachinesCostPerBlock` for a `state_machine_id`.
3. Advance state machine height to `H1`, call `on_executed` — treasury is debited for `H1 - baseline`, `LastRewardedHeight` stays unset (mint failure short-circuits before the mutate).
4. Advance state machine height further to `H2`, call `on_executed` again — treasury is debited again for `H2 - baseline` (same stale baseline), i.e., the span up to `H1` is paid a second time as part of the new reward.
5. Assert Treasury balance decreases on both calls by overlapping amounts, and `LastRewardedHeight::<T>::get(state_machine_id)` remains `None` after both calls despite two successful transfers — confirming reward accounting decoupled from watermark advancement.
