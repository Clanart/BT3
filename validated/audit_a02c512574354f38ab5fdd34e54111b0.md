## Analysis

The Tokemak bug's core invariant break is: **a monotonic watermark keeps accumulating state across a discontinuity (full exit) instead of being rebased, so a later legitimate accrual event is measured against a stale baseline and the payout for that accrual is wrong.**

The closest local analog in Hyperbridge is the `LastRewardedHeight` watermark in `pallet-consensus-incentives`, which gates relayer reward payouts for consensus-update delivery.### Title
Stale `LastRewardedHeight` watermark lets a single relayer drain the treasury for the entire unpaid block backlog after `StateMachinesCostPerBlock` is toggled off/on - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives` pays a relayer `blocks_since_last_payout × cost_per_block` for delivering a consensus update, using `LastRewardedHeight` as a monotonic watermark baseline. The watermark is only ever advanced when a reward is actually paid (`process_message`, `modules/pallets/consensus-incentives/src/impls.rs:70-72`). If reward accrual is interrupted for a state machine (governance disables incentives with `remove_incentives`, or simply never configures `StateMachinesCostPerBlock` for a period), the underlying ISMP consensus client keeps advancing `latest_commitment_height` for free (relayers deliver consensus updates regardless of whether a reward is configured, since consensus delivery is required for the bridge to function). When incentives are (re-)enabled, `calculate_reward` (`modules/pallets/consensus-incentives/src/impls.rs:78-100`) computes `blocks = latest_height - baseline` using the **stale** `LastRewardedHeight`, not the height at which incentives resumed. The very next relayer to submit a single consensus message is paid for the **entire backlog span**, even though they delivered only the marginal update.

### Finding Description
The reward computation is:

```rust
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
let reward = blocks_as_balance.saturating_mul(block_cost);
``` [1](#0-0) 

`LastRewardedHeight` is designed as a high-water mark: it "only ever moves forward" and is meant to stop double payment for the same span after a rollback-and-resubmit, which is exactly what the test `reward_covers_only_unpaid_heights_after_rollback` verifies. [2](#0-1) 

But the watermark is never rebased when there is a *gap in paid accrual* that is not caused by a rollback — specifically when `StateMachinesCostPerBlock` is unset (via `remove_incentives`) or was never configured, and consensus updates for that state machine keep landing (as they must, to keep the light client live) without any reward being paid and, critically, without `LastRewardedHeight` being advanced (it is only bumped inside the `if let Some(block_cost) = ...` branch in `process_message`, `modules/pallets/consensus-incentives/src/impls.rs:46-72`).

This is the direct structural analog of the Tokemak bug: `navPerShareHighMark` is a monotonic "already accounted for" marker that should be rebased to the current state whenever the position it tracks is reset/discontinued (full exit), but isn't — causing later legitimate profit to be measured against a stale baseline. Here, `LastRewardedHeight` is a monotonic "already paid up to" marker that should be rebased to the height at which paid incentives resume, but isn't — causing the next relayer's single delivery to be measured against a stale, much older baseline.

Concretely:
1. Governance calls `remove_incentives(state_machine_id)`, clearing `StateMachinesCostPerBlock` (`modules/pallets/consensus-incentives/src/lib.rs:152-166`). `LastRewardedHeight` remains at whatever it was, e.g. height 1000.
2. Over the following period, the chain's light client on Hyperbridge advances via ordinary consensus message delivery (unrelated relayers, unpaid) from height 1000 to height 50,000. No reward accrues because `StateMachinesCostPerBlock::get` returns `None`, so `process_message` short-circuits before ever touching `LastRewardedHeight` (`modules/pallets/consensus-incentives/src/impls.rs:46`).
3. Governance calls `update_cost_per_block(state_machine_id, cost)` to re-enable incentives (`modules/pallets/consensus-incentives/src/lib.rs:130-150`). This does not touch `LastRewardedHeight` either.
4. The very next relayer whose consensus message triggers a `StateMachineUpdated` event for that chain has `calculate_reward` compute `blocks = 50,000 - 1,000 = 49,000`, and is paid `49,000 × cost_per_block` from the treasury (`T::TreasuryAccount`) for a delivery that only advanced the tip by a handful of blocks.
5. No existing guard prevents this: the `saturating_sub` only prevents negative underflow, `Preservation::Expendable` transfer succeeds as long as treasury solvency permits, and there is no check that `latest_height - baseline` corresponds to blocks the *paying relayer* (or any relayer) actually delivered during a paid window.

### Impact Explanation
This is a direct, unauthorized loss of treasury funds: an ordinary (unprivileged) relayer receives a reward vastly disproportionate to the work performed in the transaction that triggered payment, funded by `T::TreasuryAccount`. Depending on `cost_per_block` and the length of the incentive-off window, this can drain a large fraction of the treasury balance for the reputation asset and native currency in a single extrinsic, to whichever relayer happens to submit next. It requires no malicious relayer/prover/operator collusion, no forged proof, and no privileged role beyond the routine, expected governance action of toggling `StateMachinesCostPerBlock` — a supported operational lever (`remove_incentives` / `update_cost_per_block`).

### Likelihood Explanation
Medium-High. Toggling incentive configuration off and back on is a normal, documented governance operation (both extrinsics exist precisely for this purpose), and consensus updates for a state machine continue to be delivered regardless of whether a reward is configured (light client liveness is required independent of incentives). Any relayer merely needs to be the one whose consensus message lands first after re-enabling — this requires no special privilege or timing manipulation beyond normal relaying, so it is realistically triggerable, not merely theoretical.

### Recommendation
Rebase `LastRewardedHeight` whenever paid accrual is interrupted or resumed, mirroring the "reset the high-water mark on full exit" fix from the referenced report:
- On `remove_incentives`, clear (or snapshot to `latest_commitment_height` at that moment) the `LastRewardedHeight` entry for the state machine so no backlog accrues while disabled.
- On `update_cost_per_block` re-enabling a previously-disabled state machine, reset `LastRewardedHeight` to the current `latest_commitment_height` so the next reward is computed only over the span delivered *after* incentives resumed, not the entire unpaid gap.
- Alternatively, track reward eligibility per-block-range at the time `StateMachinesCostPerBlock` is set/unset (an explicit "incentives active since height X" marker) instead of relying solely on the payout watermark as a stand-in baseline.

### Proof of Concept
Using the existing test harness pattern from `reward_covers_only_unpaid_heights_after_rollback` (`modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs:121-219`):

1. `update_cost_per_block(state_machine_id, BLOCK_COST)`; drive `latest_commitment_height` to 1000; submit a consensus message so `LastRewardedHeight = Some(1000)` and the treasury pays `BLOCK_COST` for that span (as in the existing test).
2. `remove_incentives(state_machine_id)` — `StateMachinesCostPerBlock` becomes `None`.
3. Advance `latest_commitment_height` to 50,000 via `host.store_state_machine_commitment` / `store_latest_commitment_height` (simulating ordinary, un-incentivized consensus delivery) without calling `on_executed`'s reward path succeeding (it no-ops because cost is unset).
4. `update_cost_per_block(state_machine_id, BLOCK_COST)` again.
5. Submit one more consensus message and call `on_executed` with a `StateMachineUpdated { latest_height: 50000 }` event.
6. Assert the treasury balance decreases by `(50000 - 1000) * BLOCK_COST` and the relayer/reputation-asset balance increases by the same — i.e., one relayer is paid for 49,000 blocks after submitting a single message, confirming the disproportionate treasury drain.
