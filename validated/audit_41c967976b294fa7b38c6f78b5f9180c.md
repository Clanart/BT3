### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` enables sandwich attack on Wombat pool deposit - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor` hardcodes `_minimumLiquidity = 0` when calling `_deposit`, unlike the public `deposit` function which lets the caller specify a slippage-protection value. This removes the only guard against Wombat pool imbalance during LP minting, letting an attacker sandwich a `depositFor` call to depress `lpReceived` and capture the difference via arbitrage, while the victim's `_for` address is credited a permanently reduced stake in MasterMagpie.

### Finding Description
`depositFor` pulls `_amount` of `depositToken` from `msg.sender` and calls `_deposit(_amount, 0, _for, address(this))`, in contrast to `deposit(uint256 _amount, uint256 _minimumLiquidity)` which forwards a caller-supplied minimum. [1](#0-0) 

`_deposit` forwards this zero minimum straight into `IWombatStaking(wombatStaking).deposit(lpToken, _amount, _minimumLiquidity, _for, _from)`. [2](#0-1) 

`WombatStaking.deposit` in turn calls `IWombatPool(poolInfo.depositTarget).deposit(...)` with that same `_minimumLiquidity`, and mints the receipt token 1:1 with whatever `lpReceived` the pool returns: [3](#0-2) 

Since Wombat's stableswap LP minting amount depends on the pool's current coverage ratio/imbalance, an attacker can:
1. Flash-loan capital and swap into the target Wombat pool to skew its coverage ratio away from 1 (imbalance it) right before the victim's `depositFor` transaction.
2. Let the victim's `depositFor` execute with `_minimumLiquidity = 0`, so `IWombatPool(...).deposit` mints a reduced `lpReceived` (since Wombat penalizes deposits that increase imbalance, or gives less favorable haircut-adjusted LP amount depending on pool state) with zero revert protection.
3. Reverse the swap to restore the pool and extract the resulting arbitrage, while the victim's `_for` address is permanently staked in MasterMagpie (via `_stake`/`IMasterMagpie.depositFor`) with the reduced LP/receipt amount.

Because `_minimumLiquidity` is hardcoded to `0` in `depositFor`, there is no mechanism (revert threshold) for the transaction to fail even under maximal adverse pool conditions, unlike the regular `deposit` path where a caller can protect themselves. `nonReentrant`/`whenNotPaused` on `WombatStaking.deposit` do not prevent this because the attack is sandwich/front-running based, not reentrancy-based, and pausing is not attacker-triggerable.

### Impact Explanation
This is a direct theft of user funds: the victim (`_for`) ends up with fewer LP-backed receipt/staking tokens than the fair-value deposit would produce, while the attacker captures that lost value through the imbalance-then-restore arbitrage. This matches the "direct theft of user funds via frontrunning/sandwich of an unprotected deposit" impact class.

### Likelihood Explanation
The attack requires only public capabilities: flash-loan capital (freely available on-chain), the ability to swap in the target Wombat pool, and observing a pending `depositFor` transaction in the mempool to front-run/back-run it. No privileged role is needed. It's repeatable for every sizeable `depositFor` call, and the larger the deposit, the more profitable the sandwich, since attacker profit scales with the amount of imbalance they can safely inject while remaining net profitable after fees.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) so the caller (or `_for`, via signed authorization) can specify acceptable slippage, and propagate it through `_deposit` instead of hardcoding `0`. Optionally also enforce a maximum allowed pool coverage-ratio deviation check before depositing, or require deposits to route through a safe internal minimum computed from the pool's current quote.

### Proof of Concept
Foundry test plan (fork test against BNB/Wombat mainnet fork):
1. Deploy/fork `WombatStaking`, `WombatPoolHelperV2`, and the real `WombatPool` for a stable pool (e.g., USDT/BUSD).
2. Baseline: call `depositFor(amount, victim)` in an untouched pool state; record `lpReceived` from the `NewDeposit` event / receipt token minted.
3. Attack: 
   - Flash-loan a large amount of one pool asset.
   - Swap it into the Wombat pool to skew the coverage ratio.
   - Call `depositFor(amount, victim)` from the victim's relayer (simulate front-run ordering within same block).
   - Reverse the swap to restore the pool, repay flash loan.
   - Record attacker's net profit and victim's actual `lpReceived`.
4. Assert: `lpReceived_attackScenario < lpReceived_baseline` and attacker's post-attack balance shows positive profit (`> flash loan fee`), proving fund extraction at the victim's expense with `_minimumLiquidity = 0` providing no protection.
