### Title
Zero-slippage WOM→mWOM buyback swap in `ArbWomUp3.incentiveDeposit` (mode 2) enables sandwich theft of user funds - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.incentiveDeposit()` with `_mode == 2` routes half of the depositor's WOM through `SmartWomConvert.convert()` with `_minRec` hardcoded to `0`, and the underlying Wombat router swap inside `SmartWomConvert._convertFor()` always passes `amountOutMin = 0` to the DEX call itself. The only slippage guard is a post-swap check against `_minRec`, which is neutered because `ArbWomUp3` passes `0`. An MEV searcher can sandwich the buyback swap and extract essentially all of the swap's value from the depositor's own converted WOM.

### Finding Description
In `_deposit()`, the mode-2 branch splits the user's deposited WOM and sends half to be swapped for mWOM via the smart convertor: [1](#0-0) 

The call `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` passes `_minRec = 0`. Inside `SmartWomConvert`, `convert()` forwards straight into `_convertFor()`: [2](#0-1) 

The buyback swap itself is executed with a hardcoded `0` as the router's `minAmountOut`, regardless of the caller-supplied `_minRec`: [3](#0-2) 

Slippage protection is only applied *after* the swap has already executed, via an aggregate check: [4](#0-3) 

Because `ArbWomUp3` supplies `_minRec = 0`, this post-swap check can never revert (`convertAmount + amountRec < 0` is never true), so there is no effective slippage protection whatsoever for the `toSwap` portion of the user's WOM. This is the exact bug class in the reported `Burner.convertAndBurn` "sandwich ack" issue: an ordinary, unprivileged-caller-reachable function performs an on-chain DEX swap with `amountOutMin` fixed at `0`, letting an MEV bot manipulate the pool price immediately before the swap and reap the difference.

### Impact Explanation
Any unprivileged wallet calling `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` has half of its deposited WOM routed through a swap with zero slippage protection. A searcher can front-run with a large trade against the `womMWomPool` to depress the mWOM output, let the victim's swap execute at the manipulated price, then back-run to restore the price and capture the difference. This is a direct theft of user funds (the victim receives far less mWOM/locked value than the fair-price amount, and the difference is extracted by the attacker), satisfying the "direct theft of user funds" impact bar.

### Likelihood Explanation
The path is reachable by any ordinary wallet with WOM tokens simply by calling `incentiveDeposit` with `_mode == 2`, with no privileged role required. Wombat's WOM/mWOM pool liquidity is finite and swap sizes from `ArbWomUp3` deposits are visible in the mempool, making this economically viable and detectable for MEV searchers/sandwich bots, analogous to the referenced `Burner` incident.

### Recommendation
Do not hardcode `_minRec = 0` in `ArbWomUp3._deposit()`'s mode-2 branch. Either let the depositor supply a caller-specified minimum acceptable output for the swap portion (validated on-chain, e.g. via `incentiveDeposit`'s parameters) and thread it through to `IConverter(smartWomConvert).convert(...)`, or have `SmartWomConvert._convertFor()` apply a genuine `amountOutMin` on the router call itself (not just a post-hoc aggregate check) derived from an on-chain TWAP/oracle-independent minimum rather than accepting `0` as valid input.

### Proof of Concept
1. Attacker monitors mempool for a pending `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)` transaction from a victim wallet (unprivileged caller). [5](#0-4) 
2. Attacker front-runs with a large WOM→mWOM (or mWOM→WOM) swap against `womMWomPool` via the Wombat router to skew the pool price unfavorably for the upcoming buyback swap.
3. Victim's transaction executes: `_deposit` computes `toSwap = _amount - toDeposit` and calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)`. [6](#0-5) 
4. Inside `_convertFor`, the router swap executes with `amountOutMin = 0`, receiving a heavily reduced `amountRec` due to the manipulated pool state; the subsequent check `convertAmount + amountRec < _minRec` never reverts since `_minRec == 0`. [7](#0-6) 
5. Attacker back-runs to reverse their initial swap, restoring the pool price and pocketing the difference extracted from the victim's conversion — the victim's `mWomBal` locked via `mWomSV.lockFor()` is correspondingly diminished. [8](#0-7)
