### Title
Ed448 `is_torsion_free` always returns true — small-order points accepted as valid keys/nonces - ([File: crypto/ed448/src/point.rs])

### Summary
`Point::is_torsion_free` in `crypto/ed448/src/point.rs` computes `(*self * (Scalar::ZERO - Scalar::ONE)) + self`, i.e. `P·(−1) + P`, which equals the identity for *every* point — including points of order 2 and 4 (Ed448 has cofactor 4). The check is therefore a tautology and `GroupEncoding::from_bytes` accepts non-prime-order points. This mirrors the Bouncy Castle advisory class: an arithmetic/validation defect in curve code that lets attacker-chosen curve points carry spurious low-order components through verification.

### Finding Description
`Point::from_bytes` decodes `y`, recovers `x`, rejects negative-zero, and then relies on `point.is_torsion_free()` as the sole prime-order-subgroup gate [1](#0-0) :

```rust
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
``` [2](#0-1) 

`Scalar::ZERO - Scalar::ONE` is `−1 mod q`, so the expression is `P·(−1) + P = identity` unconditionally, on any curve point, torsion or not. The correct check would be `P·q == identity` (or `mul_by_cofactor` into the prime subgroup). The comment in `crypto/schnorr/src/lib.rs` explicitly states the library requires strict, canonical, prime-order inputs and will not do RFC 8032's cofactored `8R = 8s − 8cA` verification [3](#0-2)  — yet the decoding layer that was supposed to enforce that premise silently accepts any coset representative.

Reachability: `Ed448::read_G` → `Point::from_bytes` is hit by `SchnorrSignature::<Ed448>::read`, `Commitments::read`, `EncryptedMessage::read`, `ThresholdKeys::read`, and FROST preprocess/share reading for the Ed448 ciphersuite (`crypto/frost/src/curve/ed448.rs` wires `minimal_ed448::{Scalar, Point}` into `Curve` [4](#0-3) ). All attacker-controlled bytes (public keys, nonces, DKG commitments, verification shares) reach this decoder.

### Impact Explanation
Any Ed448 point with a 2- or 4-torsion component is accepted wherever the protocol assumes a prime-order point:

- **Public-key malleability / equivocation**: a key `A = a·G + T` (T torsion) is byte-distinct from `a·G`, both decode successfully, and torsion survives `to_bytes` (`to_bytes` encodes x-sign and y directly [5](#0-4) ). The same secret key yields multiple accepted "public keys", breaking key uniqueness assumptions in DKG registries and FROST `included` sets.
- **Forged signature acceptance**: with `A = a·G + U` (U of order 4), an attacker knowing `a` can produce `R = r·G + T` passing `s·G == R + c·A` whenever `T == c·U` in the torsion subgroup. Since `c = hram(R, A, m)`, grinding the nonce/message gives `c·U` hitting the needed torsion with probability ≈1/4 per attempt — feasible. The resulting `(R, s)` verifies under `A`, a key the verifier believes is prime-order but which is not `a·G`.
- **DKG/FROST share math**: commitments and nonce commitments with torsion components distort `R = Σ D_i + ρ_i·E_i` sums and `Σ λ·C` verification-share checks in ways the prime-order model excludes, enabling inconsistent views of the group key/nonce across honest parties.

This is "an incorrect verifier formula" and enables "concrete signing … a forged signature" acceptance per the validation criteria.

### Likelihood Explanation
Deterministic and attacker-reachable: any unprivileged party submitting bytes through `read_G`/`SchnorrSignature::read`/`Commitments::read` on the Ed448 ciphersuite controls the torsion component. Constructing a 4-torsion-compatible `(R, s, A)` forgery requires only ~4 hash iterations of grinding on average. No collusion, leaked keys, or malicious node behavior is required — only messages the verifier decodes.

### Recommendation
Replace the tautological check with a real subgroup check, e.g. `(*self * Scalar::from(4u64)).mul_by…`— concretely, verify `self * q == identity` (scalar mul by the prime subgroup order) or multiply by the cofactor 4 and reject non-prime-order results, matching dalek's `is_torsion_free` semantics used for Ed25519 [6](#0-5) . Add a test that decoding a known 4-torsion Ed448 point fails.
