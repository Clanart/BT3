### Title
Use-after-free in Python C-extension `ParseFromString`/`MergeFromString` for oneof fields with pre-existing composite wrappers - (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The ImageMagick MSL bug is a use-after-free where an interpreted directive (`<map>`) causes an object to be freed while a live reference to it is still used elsewhere in the interpreter. The closest structural analog in this Protobuf checkout is the `MergeFromStringImpl` function backing the Python C-extension's public `ParseFromString`/`MergeFromString` APIs, where the code explicitly documents (and partially works around) a known class of use-after-free caused by C++ freeing a oneof member object while a Python wrapper object still references it [1](#0-0) . This is not a newly-discovered vulnerability but a pattern the maintainers are actively guarding against with a mitigating temp-message design; I was not able to fully verify (due to running out of tool iterations) whether the `is_cleared` fast-path still leaves a gap for nested/child composite wrappers.

### Finding Description
`MergeFromStringImpl` (invoked from the public `ParseFromString`/`MergeFromString` Python message methods) parses attacker-controlled binary bytes via `_InternalParse` into a C++ `Message`. The comment at lines 2087-2092 states the *reason* a temporary heap message is used for the merge path (`is_cleared == false`): parsing directly into the target message could switch an active oneof case, causing C++ to `delete` the previously-active submessage/string object — while a Python wrapper object (`self->composite_fields` entry) still holds a raw pointer to that now-freed C++ object [2](#0-1) . The corresponding C++-level operation that performs the free is `Reflection::ClearOneof`, which calls `delete *MutableRaw<Message*>(message, field)` when the arena is null and the oneof case changes [3](#0-2) , and equivalently `TcParser::ChangeOneof` deletes the previous oneof member during table-driven binary parsing [4](#0-3) .

For the `is_cleared == true` path (the direct `ParseFromString` case), the code parses straight into `message` without constructing a temp message, relying on the invariant `ABSL_DCHECK_EQ(message->ByteSizeLong(), 0)` — i.e., that the target message is already empty so there is no live oneof member to free during parsing [5](#0-4) . This invariant is only a debug-mode check (`ABSL_DCHECK`), not enforced in release builds, and it says nothing about whether Python-level `composite_fields` wrapper objects for nested message fields still exist even though the underlying C++ storage was cleared (Python composite wrappers can outlive `Clear()` of the C++ field they wrap if not properly detached). `CopyFrom` explicitly acknowledges this class of bug by calling `Clear(self)` first specifically because "`CopyFrom` on the message will not clean up `self->composite_fields`, which can leave us in an inconsistent state" [6](#0-5) . `MergeFrom` (the message-to-message API, not the byte-string API) separately calls `MaybeReleaseOneofBeforeMerge` before performing the merge, indicating the fix for that path is a distinct, deliberate step taken to detach Python wrappers before the C++ oneof switch can free memory out from under them [7](#0-6) .

### Impact Explanation
If the `is_cleared` fast path's assumption is violated (a stale Python composite wrapper referencing a nested message that is not part of the top-level oneof-switch protection, e.g. a wrapper for a *sub-message field within* a message that gets reparsed by `_InternalParse` while `self->composite_fields` for that nested object is not cleared by `Clear()`), a subsequent Python-level access to that wrapper (`msg.sub_field.x`) would dereference freed heap memory, resulting in memory corruption/use-after-free reachable from ordinary Python application code calling `ParseFromString` on attacker-supplied bytes. This matches CWE-476 and the "impact: C:N/I:N/A:L" profile of the original CVSS vector (availability impact via crash, not code execution) since arena allocation (`arena == nullptr` branch) is required to trigger the `delete` call.

### Likelihood Explanation
Likelihood is limited: (1) the code already has the temp-message mitigation for the merge (non-cleared) path, closing off the most direct trigger; (2) the `is_cleared` path relies on `ByteSizeLong() == 0`, which in practice holds after Python's `Clear()`/fresh-object construction; (3) I could not, within the remaining budget, trace whether `Clear(self)` (the Python wrapper cleanup routine) actually invalidates *all* nested composite wrappers recursively before `ParseFromString`, or find a concrete call sequence that leaves a dangling wrapper reachable via the `is_cleared` fast path. This is a real historical bug class the maintainers document and defend against, but I cannot produce a proven, reproducible bypass of the current mitigations with the evidence gathered.

### Recommendation
- Verify that `Clear(self)` (Python wrapper-side clear, called before `ParseFromString`) recursively invalidates/detaches all entries in `self->composite_fields`, including nested sub-message and map/repeated wrappers, not just the top-level oneof case, before relying on the `is_cleared` fast path in `MergeFromStringImpl`.
- Consider promoting the `ByteSizeLong() == 0` invariant from `ABSL_DCHECK` to a release-mode check, or unconditionally applying the temp-message merge strategy regardless of `is_cleared`, removing the reliance on caller-supplied invariants for a memory-safety-critical decision.
- Add a fuzz/regression test that constructs a Python message, accesses a nested oneof/message field to create a Python wrapper, then calls `ParseFromString` (not `MergeFrom`) with new bytes that would otherwise switch oneof state, and asserts the old wrapper is either detached or the operation is rejected — to close the residual gap symmetric to what `CopyFrom` already patches explicitly.

  // We parse into a temporary message first to detect oneof switches before
  // modifying the target message. This allows us to release the wrappers
  // for switching oneof fields in the target message before they are deleted
  // by C++ during the merge, preventing use-after-free bugs.
  // We use heap allocation (nullptr arena) for the temporary message so that
  // it is collected immediately after the merge, avoiding wasting arena memory.
  std::unique_ptr<Message> temp_message;
  Message* merge_dst;

  if (is_cleared) {
    // Check that it is really empty.
    ABSL_DCHECK_EQ(message->ByteSizeLong(), 0);
    merge_dst = message;
  } else {
    temp_message.reset(message->New(nullptr));
    merge_dst = temp_message.get();
  }
