## Analysis

The external CSRF report's core pattern is: a state-changing endpoint performs a privileged action while relying on only a partial/weak authentication check, letting an unauthorized caller trigger fund-moving logic. Reducing this to Hyperbridge: an ISMP module callback that authenticates only the *source chain* of an incoming message but not the *sending module/app* on that chain is functionally the same broken invariant — any application on the trusted chain can forge the privileged call.

That pattern exists in `HyperbridgeWithdrawalModule::on_accept`.

### Title
Missing `from` (module-identity) check on protocol fee withdrawal callback allows any module on the coprocessor chain to drain `RELAYER_FEE_ACCOUNT` - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`HyperbridgeWithdrawalModule::on_accept` authenticates an inbound `WithdrawRelayerFees` message solely by checking `request.source == T::Coprocessor::get()`. It never checks `request.from`, i.e. it never verifies *which* module/pallet on the coprocessor chain sent the message. [1](#0-0) 

### Finding Description
Every other ISMP-receiving module in this codebase treats "chain-level" and "module-level" identity as two independent checks that must both pass before a privileged action executes:

- `pallet_hyper_fungible_token` looks up `ContractToAsset::<T>::get(source, &from)` — both `source` *and* `from` key the authorization. [2](#0-1) 
- `pallet_bandwidth::on_accept` checks the registered manager address in `request.from` in addition to `request.source`. [3](#0-2) 
- `BandwidthManager.sol`'s `onAccept` requires `request.source.equals(hyperbridge)` (chain-level) — and, symmetrically, `pallet-bandwidth` verifies `request.from == manager` on the way in. [4](#0-3) 
- `HyperFungibleToken` docs explicitly document this as the security model: "Every incoming message is verified against the registered peer" via both `source` and `from`. [5](#0-4) 

`HyperbridgeWithdrawalModule` breaks this pattern. `T::Coprocessor` is a `StateMachine` (a whole chain identifier), not a specific module/pallet id. The `from` field of the `PostRequest`, which identifies *which* pallet/contract on that chain dispatched the message, is read but never compared against an expected coprocessor module id: [6](#0-5) 

Because the router dispatches purely on the destination module id (`HYPR-FEE`) irrespective of which pallet on the coprocessor chain originated the request, *any* pallet or application deployed on the coprocessor chain that can dispatch an arbitrary ISMP `PostRequest` to `to = "HYPR-FEE"` with a SCALE-encoded `Message::WithdrawRelayerFees { account, amount }` body will pass the module's only check (`source == Coprocessor`) and trigger a real currency transfer out of `RELAYER_FEE_ACCOUNT` to an attacker-chosen `account` for an attacker-chosen `amount`.

This mirrors the CSRF finding precisely: a state-mutating handler exists behind a check that authenticates the wrong granularity (session/cookie ⇔ chain-level source) while omitting the check that actually authorizes the specific caller (CSRF token ⇔ module/app identity via `from`).

### Impact Explanation
`RELAYER_FEE_ACCOUNT` funds protocol/relayer fee accounting across the entire chain. A forged `WithdrawRelayerFees` message drains this account to an arbitrary beneficiary chosen by the attacker, with the amount also attacker-controlled (bounded only by the account's balance). This is direct, unauthorized loss of protocol funds — squarely inside the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories, and requires no relayer, prover, or admin compromise: only the ability to get a message dispatched with `to = HYPR-FEE` from the already-trusted coprocessor chain.

### Likelihood Explanation
Likelihood depends on whether any pallet/contract on the coprocessor chain besides the intended intents-coprocessor logic can originate a `PostRequest` with an attacker-influenced `to`/`body` targeting `HYPR-FEE`. Given the coprocessor chain hosts multiple pallets (intents-coprocessor, demo pallets, bandwidth, etc.) that all dispatch through the same generic `IsmpDispatcher`, and none of those dispatch paths are shown to restrict destination `to` values, the missing `from` check removes what should be the last line of defense. Even absent a currently-known dispatchable path, this is a latent authorization gap that any future or existing module misuse (accidental or malicious) on the coprocessor chain can exploit, unlike the analogous checks intentionally implemented everywhere else in the codebase.

### Recommendation
Add a check for the expected sender module id (analogous to `T::Coprocessor` for the chain) against `request.from`, mirroring the pattern used in `pallet_hyper_fungible_token` and `pallet_bandwidth`:
```rust
if Some(source) != T::Coprocessor::get() || request.from != EXPECTED_COPROCESSOR_MODULE_ID {
    Err(...)?
}
```
Define `EXPECTED_COPROCESSOR_MODULE_ID` as a configurable/constant module id bound to the specific intents-coprocessor pallet, not the whole chain.

### Proof of Concept
1. Any pallet on the chain configured as `T::Coprocessor` calls the local `IsmpDispatcher::dispatch_request` with `DispatchPost { dest: <this chain>, to: b"HYPR-FEE".to_vec(), body: Message::WithdrawRelayerFees(WithdrawalRequest { account: attacker_account, amount: X }).encode(), .. }`.
2. The request is relayed and delivered; `handle::<H>` in `modules/ismp/core/src/handlers/request.rs` routes it via `router.module_for_id(b"HYPR-FEE")`, which resolves to `HyperbridgeWithdrawalModule` [7](#0-6) .
3. `on_accept` checks only `request.source == T::Coprocessor::get()` — true, since the dispatch originated from that chain — and never inspects `request.from`.
4. `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &attacker_account, X, ...)` executes, moving funds to the attacker.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}

### Source Verification

Every incoming message is verified against the registered peer:

```solidity lineNumbers
bytes memory expectedSource = _supportedChains[request.source];
if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();
```

Only messages from registered peer contracts are accepted. An attacker cannot spoof messages from unregistered chains or impersonate the peer contract address on a registered chain — ISMP provides cryptographic proof that the message was actually dispatched on the source chain.
