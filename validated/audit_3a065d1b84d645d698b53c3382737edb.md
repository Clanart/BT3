Based on the evidence gathered, I can identify a legitimate, narrowly-scoped analog in Protobuf's own ProtoJSON string-serialization layer, though it maps to a **Medium**-severity, defense-in-depth XSS gap rather than the Critical/RCE class of the SiYuan report — the exploitation chain crosses into the *consuming application's* rendering logic, so I state that assumption explicitly below.

### Title
Inconsistent HTML/XSS-safety escaping in ProtoJSON string encoding across language implementations - (File: `src/google/protobuf/json/internal/writer.cc`, `python/google/protobuf/internal/json_format.py`, `upb/json/encode.c`, `php/src/Google/Protobuf/Internal/GPBJsonWire.php`, `ruby/ext/google/protobuf_c/ruby-upb.c`)

### Summary
Google Protobuf's Java and C# `ToJsonString`/`JsonFormatter` implementations deliberately escape `<`, `>`, `&`, `=`, `'` in string field values as an explicit anti-XSS measure, documented in-line as "escaped to prevent XSS risks." [1](#0-0)  The C++ core JSON writer only escapes `<` and `>`, omitting `&`, `=`, `'`. [2](#0-1)  The upb-based encoder — shared by the PHP extension and the Ruby extension, and structurally identical to `upb/json/encode.c` — performs *no* HTML-specific escaping at all, only the RFC-mandated JSON escapes. [3](#0-2) [4](#0-3) [5](#0-4)  The pure-Python `json_format` implementation matches this: its own regression test confirms `<` and `&` are emitted verbatim, unescaped. [6](#0-5)  The PHP path additionally delegates to PHP's stock `json_encode()` without `JSON_HEX_TAG`/`JSON_HEX_AMP`, which is the same gap. [7](#0-6) 

### Finding Description
The failed invariant is the one Protobuf's own Java/C# maintainers established: ProtoJSON string output should not contain raw `<`, `>`, `&`, `=`, `'` characters, specifically so that JSON produced by `ToJsonString`/`MessageToJson` can be embedded into an HTML document (e.g. inline in a `<script>` tag to hydrate client state, a extremely common server-side rendering pattern) without a second escaping pass. This is precisely analogous to the SiYuan bug class: an attacker-controlled string (there, an AV cell value; here, a Protobuf string field populated from an ordinary client's ProtoJSON/binary request) flows unmodified through a serialization/rendering function that other, "hardened" sibling implementations already sanitize, into a sink (`innerHTML` in SiYuan; an HTML/`<script>` embedding context for ProtoJSON) that interprets it as markup.

The attacker-controlled value is any string field set via a supported public parse API (`ParseFromString`, `Merge`, ProtoJSON `Parse`) — trusted schema, bounded payload, no malformed wire data required. The missing check is the same escape table (`<>&='`) that exists in `JsonFormat.java` and (partially) in `JsonFormatter.cs`, but is absent from the C++ core writer (missing `&`, `=`, `'`), and completely absent from the upb-based encoder used by Python, PHP, and Ruby, and from the pure-Python implementation.

Consuming-application exposure assumption: a trusted server-side application receives a protobuf message (possibly containing an attacker-supplied string field from an earlier request), calls the language's ProtoJSON serializer, and embeds the result directly into an HTML response (e.g., `<script>var initialState = <?php echo $jsonString; ?>;</script>`), relying on the documented XSS-hardening behavior that Java/C# provide. Any Python-, PHP-, Ruby-, or C++-based service doing the same thing does not get that protection.

### Impact Explanation
If a consuming web application embeds ProtoJSON output produced by the Python, PHP, Ruby, or (partially) C++ implementations directly into an HTML/`<script>` context — a pattern implicitly sanctioned by protobuf's own Java/C# design intent — a string field containing `</script><script>alert(document.domain)</script>` (or `"onmouseover="alert(1)` for `&`/`'`-sensitive attribute contexts) breaks out and executes attacker-controlled JavaScript in the victim's browser. This is a stored/reflected XSS in the consuming application, not remote code execution in Protobuf itself, and severity is capped at Medium: it requires the consuming application to adopt the specific (if common) "embed protojson directly in HTML" pattern, and does not on its own grant native/host code execution the way the Electron `nodeIntegration:true` chain did in SiYuan.

### Likelihood Explanation
Likelihood is moderate. Embedding server-rendered JSON directly into HTML (SSR hydration, JSONP-style payloads) is a well-known and still-common pattern, which is exactly why Java's implementation added this hardening with an explicit code comment referencing XSS. Any Protobuf consumer relying on cross-language behavioral parity — reasonably assuming ProtoJSON output is uniformly safe because one official binding documents it as an XSS mitigation — is silently exposed when they use Python, PHP, Ruby, or C++ instead.

### Recommendation
Add the same `<`, `>`, `&`, `=`, `'` escaping (as `\u003c`, `\u003e`, `\u0026`, `\u003d`, `\u0027`) to: the C++ `MustEscape` function in `src/google/protobuf/json/internal/writer.cc`, the upb `jsonenc_put_escaped_char`/`jsonenc_stringbody` path in `upb/json/encode.c` (which is shared by the PHP and Ruby native extensions), and the pure-Python `json_format.py` string-printing path, so all officially-supported ProtoJSON serializers apply the same anti-XSS escaping already present in Java's `JsonFormat` and (partially) C#'s `JsonFormatter`. Alternatively, if this hardening is not meant to be a documented invariant, remove the misleading "prevent XSS risks" claim from `JsonFormat.java` and clearly document, once per language, that ProtoJSON output is not safe for direct HTML embedding without independent escaping.

### Proof of Concept
Using the checked-out Python `json_format` test target directly (no fuzzing/wire-format tricks needed — this is a straight output-encoding check):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb

m = pb.TestMessage()
m.string_value = '</script><script>alert(1)</script>'
print(json_format.MessageToJson(m))
# {
#   "stringValue": "</script><script>alert(1)</script>"
# }
```
This mirrors the repo's own `testJsonEscapeString` [6](#0-5) , which already asserts `<` and `&` are emitted literally (`"&\\n<\\"\\r>..."`), confirming no HTML-context escaping occurs. If a server embeds this output as `<script>var m = {ABOVE_JSON};</script>`, the `</script>` sequence terminates the legitimate script block and the injected `<script>alert(1)</script>` executes — the same "raw string breaks out of surrounding markup" primitive as `genAVValueHTML()`'s unescaped `text`/`url` branches in the SiYuan advisory. The identical unescaped behavior is reproducible in the C++, PHP, and Ruby encoders by inspection of `MustEscape` [8](#0-7)  and `jsonenc_put_escaped_char` [3](#0-2) , contrasted with Java's escape table which explicitly covers this case [9](#0-8) .

```text
static bool MustEscape(uint32_t scalar, absl::string_view& custom_escape) {
  switch (scalar) {
    // These escapes are defined by the JSON spec. We do not escape /.
    case '\n':
      custom_escape = R"(\n)";
      return true;
    case '\r':
      custom_escape = R"(\r)";
      return true;
    case '\t':
      custom_escape = R"(\t)";
      return true;
    case '\"':
      custom_escape = R"(\")";
      return true;
    case '\f':
      custom_escape = R"(\f)";
      return true;
    case '\b':
      custom_escape = R"(\b)";
      return true;
    case '\\':
      custom_escape = R"(\\)";
      return true;

    case kErrorSentinel:
      // Decoding failure turns into spaces, *not* replacement characters. We
      // handle this separately from "normal" spaces so that it follows the
      // escaping code-path.
      //
      // Note that literal replacement characters in the input string DO NOT
      // get turned into spaces; this is only for decoding failures!
      custom_escape = " ";
      return true;

    // These are not required by the JSON spec, but help
    // to prevent security bugs in JavaScript.
    //
    // These were originally present in the ESF parser, so they are kept for
    // legacy compatibility (and because escaping most of these is in good
    // taste, regardless).
    case '<':
    case '>':
    case 0xfeff:      // Zero width no-break space.
    case 0xfff9:      // Interlinear annotation anchor.
    case 0xfffa:      // Interlinear annotation separator.
    case 0xfffb:      // Interlinear annotation terminator.
    case 0x00ad:      // Soft-hyphen.
    case 0x06dd:      // Arabic end of ayah.
    case 0x070f:      // Syriac abbreviation mark.
    case 0x17b4:      // Khmer vowel inherent Aq.
    case 0x17b5:      // Khmer vowel inherent Aa.
    case 0x000e0001:  // Language tag.
      return true;
```

```c
static void jsonenc_put_escaped_char(jsonenc* e, char ch) {
  switch (ch) {
    case '\n':
      jsonenc_putstr(e, "\\n");
      break;
    case '\r':
      jsonenc_putstr(e, "\\r");
      break;
    case '\t':
      jsonenc_putstr(e, "\\t");
      break;
    case '\"':
      jsonenc_putstr(e, "\\\"");
      break;
    case '\f':
      jsonenc_putstr(e, "\\f");
      break;
    case '\b':
      jsonenc_putstr(e, "\\b");
      break;
    case '\\':
      jsonenc_putstr(e, "\\\\");
      break;
    default:
      if ((uint8_t)ch < 0x20) {
        jsonenc_printf(e, "\\u%04x", (int)(uint8_t)ch);
      } else {
        /* This could be a non-ASCII byte.  We rely on the string being valid
         * UTF-8. */
        jsonenc_putbytes(e, &ch, 1);
      }
      break;
  }
}
```
