### Title
Quadratic-cost JSON field-name resolution via linear `json_name` fallback scan - ([File: src/google/protobuf/json/internal/descriptor_traits.h])

### Summary
The CVE's failed invariant is: a per-candidate string operation (`strings.Split`) that should be computed once on the attacker-controlled input was instead re-executed inside a loop over an attacker-influenced list (SAN entries), turning a linear operation into `O(entries × labels)`. The closest structural analog in this checkout is `Proto2Descriptor::FieldByName` in `descriptor_traits.h`, used by the ProtoJSON parser (`json/internal/parser.cc`) to resolve every JSON object key to a `FieldDescriptor`. Its two fast paths are O(1) hash lookups, but when they miss, it falls back to a **linear scan over every field of the message** comparing `json_name()` to the attacker-supplied key. This scan runs once per JSON key that fails the fast paths, and with `ignore_unknown_fields=true` parsing continues past failed lookups, so a JSON object with many unmatched keys against a message with many fields reproduces the same `O(keys × fields)` blow-up pattern as the CVE's `O(SAN_entries × labels)`.

### Finding Description
`Proto2Descriptor::FieldByName`: [1](#0-0) 
first tries `FindFieldByCamelcaseName` and `FindFieldByName`, both O(1) hash-table lookups backed by lazily-built sets (see `FileDescriptorTables::FindFieldByCamelcaseName` / the lazy-init hash sets in `descriptor.cc`): [2](#0-1) 
When both fail (i.e., the JSON key matches neither the field's snake_case name nor its computed camelCase name — which happens for any field with a custom `json_name` option, or simply for any unrecognized/attacker-chosen key), it falls through to a linear `for` loop over `d.field_count()` fields comparing each `field->json_name()` against the query string.

This function is invoked from the ProtoJSON parser once per object key via `ParseField`: [3](#0-2) 
If the lookup fails and `ignore_unknown_fields` is enabled, the parser calls `lex.SkipValue()` and continues to the next key rather than aborting: [4](#0-3) 

The invariant that fails to transfer safely: field-name resolution is assumed to be amortized O(1) per key (that's why two hash-table fast paths exist), but the `json_name` fallback silently degrades to O(n) per key with no bound, and nothing prevents it from being invoked repeatedly across many keys in a single payload, exactly mirroring the CVE's redundant per-entry `strings.Split` that should have been hoisted/cached.

### Impact Explanation
For a message descriptor with `N` fields and a ProtoJSON payload containing `M` keys that miss both fast-path lookups (e.g., keys chosen not to match any field's snake_case/camelCase form, or simply misspelled/unknown keys when `ignore_unknown_fields=true`), the fallback scan cost is `O(M × N)` string comparisons purely from attacker-controlled key content — CPU cost scaling with the product of payload key count and message field count, not with payload byte size. This matches the CVE's severity class (algorithmic-complexity CPU exhaustion during untrusted-input validation, before any semantic decision is made about the data), reachable through the public `JsonStringToMessage` / `util::JsonStringToMessage` ProtoJSON parsing API when the consuming application enables `ignore_unknown_fields` (a common, supported configuration for API gateways tolerating schema evolution).

### Likelihood Explanation
Reaching the vulnerable path requires: (1) a public ProtoJSON parse entry point, (2) `ignore_unknown_fields=true` (or a single message with a field whose `json_name` diverges from the camelCase/snake_case forms, forcing the fallback on a specific legitimate key), and (3) a message descriptor with many fields exposed to JSON parsing. `ignore_unknown_fields` is an explicit, documented, commonly-enabled option (unlike arbitrary custom code), and large-field-count messages are common in real-world `.proto` schemas, making this readily triggerable by an ordinary client sending a bounded JSON payload — no privileged access, hostile schema, or malicious plugin required.

### Recommendation
Precompute a hash map (e.g., `absl::flat_hash_map<absl::string_view, Field>`) from each field's declared `json_name` to its `FieldDescriptor` at message-type registration time (mirroring the existing `fields_by_lowercase_name_` / `fields_by_camelcase_name_` lazy-init pattern in `descriptor.cc`), and have `Proto2Descriptor::FieldByName` consult that map instead of doing a linear `field_count()` scan. This removes the per-key O(n) fallback entirely, bounding JSON field-name resolution to O(1) per key regardless of how many keys are unmatched or how large the message descriptor is.

### Proof of Concept
Conceptual reproduction (not executed — requires a build/run environment unavailable to this analysis):
1. Define a `.proto` message `M` with `N` (e.g., 5,000) scalar fields, each with a distinct snake_case name (no custom `json_name`).
2. Construct a JSON payload `{"unknown_key_1": 1, "unknown_key_2": 2, ..., "unknown_key_M": M}` with `M` (e.g., 5,000) keys that don't correspond to any field of `M`.
3. Call `google::protobuf::json::JsonStringToMessage` (or `util::JsonStringToMessage`) with `JsonParseOptions.ignore_unknown_fields = true`.
4. Each of the `M` keys fails both `FindFieldByCamelcaseName` and `FindFieldByName`, falling into the `for (int i = 0; i < d.field_count(); ++i)` loop in `Proto2Descriptor::FieldByName` (`descriptor_traits.h:179-184`), yielding `~M × N` (≈25,000,000) string comparisons for a payload whose serialized size is only tens of kilobytes — demonstrating the algorithmic-complexity mismatch between input size and CPU cost, structurally identical to the `VerifyHostname` SAN-list analog in the report.

                                           absl::string_view name) {
    if (const auto* field = d.FindFieldByCamelcaseName(name)) {
      return field;
    }

    if (const auto* field = d.FindFieldByName(name)) {
      return field;
    }

    for (int i = 0; i < d.field_count(); ++i) {
      const auto* field = d.field(i);
      if (field->json_name() == name) {
        return field;
      }
    }

    return absl::nullopt;
  }

inline const FieldDescriptor* FileDescriptorTables::FindFieldByLowercaseName(
    const void* parent, absl::string_view lowercase_name) const {
  absl::call_once(fields_by_lowercase_name_once_,
                  &FileDescriptorTables::FieldsByLowercaseNamesLazyInitStatic,
                  this);
  const auto* fields =
      fields_by_lowercase_name_.load(std::memory_order_acquire);
  auto it = fields->find(
      std::pair<const void*, absl::string_view>(parent, lowercase_name));
  if (it == fields->end()) return nullptr;
  return *it;
}

void FileDescriptorTables::FieldsByCamelcaseNamesLazyInitStatic(
    const FileDescriptorTables* tables) {
  tables->FieldsByCamelcaseNamesLazyInitInternal();
}

void FileDescriptorTables::FieldsByCamelcaseNamesLazyInitInternal() const {
  auto* set = new FieldsByCamelcaseNameSet;
  for (auto symbol : symbols_by_parent_) {
    const FieldDescriptor* field = Resolve(symbol).field_descriptor();
    if (!field) continue;
    auto [it, inserted] = set->insert(field);
    if (!inserted && (*it)->number() > field->number()) {
      // If we already have a field with this camelCase name, keep the field
      // with the smallest field number. This way we get a deterministic
      // mapping.
      set->erase(it);
      set->insert(field);
    }
  }
  fields_by_camelcase_name_.store(set, std::memory_order_release);
}

inline const FieldDescriptor* FileDescriptorTables::FindFieldByCamelcaseName(
    const void* parent, absl::string_view camelcase_name) const {
  absl::call_once(fields_by_camelcase_name_once_,
                  FileDescriptorTables::FieldsByCamelcaseNamesLazyInitStatic,
                  this);
  auto* fields = fields_by_camelcase_name_.load(std::memory_order_acquire);
  auto it = fields->find(
      std::pair<const void*, absl::string_view>(parent, camelcase_name));
  if (it == fields->end()) return nullptr;
  return *it;
}
