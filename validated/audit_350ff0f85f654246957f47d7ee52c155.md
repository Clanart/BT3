The self-acknowledged, index-based (not content-hash-based) partial-selection reconciliation in `app-store.ts` is the clearest analog to the reported bug class: a tracked incremental value (here, a line-index-based selection state) is carried forward and reused against a *new* diff without being validated against the actual content it now maps to — exactly like the uninitialized/stale `lastVaultDistributedWethRewardPerShareX18` being blindly diffed against a new value. In Desktop this can be triggered by anything that mutates the working tree between the initial diff render and the moment the patch is generated (e.g. a repository-controlled Git hook, filter/smudge driver, or LFS pointer resolution that rewrites file contents asynchronously), silently causing the wrong lines to be included/excluded from the user's commit.

### Title
Partial commit line-selection is reconciled by absolute line index, not content, allowing silent corruption of what gets committed - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user has partially selected lines of a modified file for commit and the working-directory diff for that file is reloaded (e.g., because a background hook, filter driver, or the user's editor mutated the file while the diff was open), Desktop reconciles the user's previous line selection against the *new* diff purely by numeric line index via `DiffSelection.withSelectableLines()`. It does **not** verify that the previously selected line still represents the same content the user reviewed and intended to include.

### Finding Description
`updateChangesWorkingDirectoryDiff` in `app-store.ts` explicitly acknowledges this limitation in a comment while implementing only a partial mitigation: [1](#0-0) 

The code only removes selection state for lines that are no longer "includeable" (i.e., turned into context or removed entirely). If a new diff has the *same number of includeable lines at the same absolute indices* but those indices now correspond to entirely different textual content (e.g., a hook rewrote line 5 to something else while a previous "line 5" was what the user reviewed and selected), the stale `divergingLines` set in `DiffSelection` is carried forward unchanged and silently applied to the new content.

`DiffSelection` itself is fundamentally index-based, not content-based — `divergingLines` is a bare `Set<number>` with no association to the text it was computed against: [2](#0-1) [3](#0-2) 

When the commit is finally created, `formatPatch` (in `patch-formatter.ts`) walks the *current* diff's hunks and simply asks `file.selection.isSelected(absoluteIndex)` for each line — with no comparison against the line text that was selected originally: [4](#0-3) 

This is structurally the same invariant violation as the reported smart-contract bug: a tracked delta/selection state (`divergingLines`, analogous to `lastVaultDistributedWethRewardPerShareX18`) is computed against one snapshot of underlying data and then blindly reused/diffed against a newer, different snapshot, because the reconciliation logic only checks "does this index still exist" rather than "does this index still mean what it meant before."

### Impact Explanation
If the working directory file is mutated between the diff being displayed/selected and the patch being generated — which is plausible for repository-controlled Git attributes/hooks (`clean`/`smudge` filters, `post-checkout`, editor auto-format-on-save triggered by file watchers, or LFS content resolution) — Desktop can generate a patch that stages/commits lines the user never reviewed or intended, while excluding lines they did select. This is a silent corruption of what the user commits and pushes: the committed content diverges from the reviewed diff without any warning to the user, and could be leveraged by a malicious repository configuration (e.g., a committed `.gitattributes` filter or hook shipped in a cloned repo) to smuggle attacker-chosen content into a user's commit under the guise of an innocuous selected change.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires a window between diff load and commit during which file content changes at the same line offsets (not just length change, which is already partially handled), and requires the user to have a partial (not "select all") selection. Git smudge/clean filters and hooks configured by a cloned/fetched repository are a realistic attacker-controlled trigger for such content-changing-without-reload races, and the code comment itself confirms the developers are aware validation is incomplete ("Ideally we would be more clever about validating that any partial selection state is still valid... but for now we'll settle on just updating the selectable lines").

### Recommendation
Make `DiffSelection` reconciliation content-aware rather than purely index-based: when a new diff is loaded for a previously-selected file, invalidate (or re-map) `divergingLines` whenever the underlying line text/type at that absolute index differs from what was last observed, not merely when the index becomes non-includeable. This could be done by snapshotting a lightweight content fingerprint (e.g., line text + type) alongside each diverging index and comparing on reconciliation in `updateChangesWorkingDirectoryDiff`, falling back to clearing the partial selection entirely if any selected line's content has changed.

### Proof of Concept
1. Clone a malicious repository containing a `.gitattributes`-configured `clean`/`smudge` filter (or a `post-checkout`/file-watcher-triggered script) that silently rewrites a specific line of a tracked file shortly after checkout.
2. In Desktop, modify the file and open the Changes view; the diff loads and the user partially selects specific lines to include in the commit (leaving others unstaged).
3. Before the user clicks "Commit," the attacker-controlled filter/hook fires and rewrites content at the same absolute line indices without changing the total line count.
4. Desktop's `updateChangesWorkingDirectoryDiff` reloads the diff, sees the same set of includeable indices, and reuses the stale `divergingLines` via `withSelectableLines` unchanged.
5. `formatPatch` generates a patch based on stale indices, and `createCommit`/`stageFiles` commits the new, attacker-modified content at those lines — even though the user only ever reviewed and approved the earlier text — with no indication to the user that the committed content differs from what they selected.
