### Title
Naive `content.split('---', 2)` frontmatter boundary parsing silently downgrades `action: block` to `action: warn` when a frontmatter value contains a literal `---` sequence - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` locates the frontmatter block by naively splitting the raw file content on the literal substring `---` with `maxsplit=2`, rather than parsing line-anchored `^---$` delimiters. If any frontmatter field value (e.g. a regex `pattern`) contains an embedded `---` sequence before the intended closing delimiter, the split misidentifies that embedded text as the closing boundary, truncating the parsed frontmatter and pushing everything after it — including `action: block` — into the free-text `message` body. Since `Rule.from_dict` defaults `action` to `'warn'` when the key is absent from the frontmatter dict, the rule silently becomes non-blocking despite visually appearing to declare `action: block`.

### Finding Description
`extract_frontmatter` checks only that content starts with `---`, then does `parts = content.split('---', 2)` and treats `parts[1]` as the entire frontmatter text and `parts[2]` as the message [1](#0-0) . This is a plain substring search across the whole file, not a delimiter-aware YAML frontmatter parser — it does not require the `---` markers to appear alone on their own line, and it stops at the *first* occurrence of `---` after the opening marker, wherever that occurs in the raw text.

A rule file such as:
```
---
name: test-rule
enabled: true
event: bash
pattern: "foo---bar"
action: block
---

Dangerous command detected!
```
contains an embedded `---` inside the `pattern` value. `content.split('---', 2)` will use that embedded occurrence as the second delimiter (since it's simply the next raw `---` substring in the file), so `parts[1]` ends at `pattern: "foo` and `parts[2]` begins with `bar"\naction: block\n---\n\nDangerous command detected!\n`. The custom line-based YAML-ish parser that follows only operates on `parts[1]`, so `action: block` never enters the `frontmatter` dict, and the rest is treated as literal message text.

`Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [2](#0-1) , defaulting to `warn` because the `action` key is missing. This rule flows through `RuleEngine.evaluate_rules`, which only treats a rule as blocking if `rule.action == 'block'`; otherwise it is placed in `warning_rules`, which only emits a `systemMessage` and allows the operation (`permissionDecision` is never set to `deny`) [3](#0-2) . A rule file that a maintainer reads (or a diff a reviewer approves) as declaring `action: block` — visually present in the raw text — is silently enforced as `warn`, defeating the intended deny/block control without any error being surfaced (the file parses successfully, `frontmatter` is non-empty, so `load_rule_file` does not flag it as malformed) [4](#0-3) .

### Impact Explanation
This breaks the deny-means-deny guarantee that hookify's `action: block` is supposed to provide for `PreToolUse`/`Stop` enforcement (e.g., blocking dangerous `rm -rf`, blocking edits to secrets files, or stopping a session). A hookify rule contributed via a PR (rule files live under `.claude/hookify.*.local.md`, ordinary repository content) that appears to enforce blocking behavior can be crafted to silently degrade to non-blocking `warn` behavior due to an incidental or deliberately placed `---` inside a pattern/value field earlier in the frontmatter. This is a genuine logic/parsing bug in a security-relevant component (a hook-based "deny" control), matching the class of "silent failure" issues the `silent-failure-hunter` agent is designed to catch, and results in an unauthorized/uncontrolled operation proceeding when the author/reviewer intended it to be blocked.

### Likelihood Explanation
Highly feasible and fully reproducible: no special privileges are needed beyond the ability to author or contribute a hookify rule `.md` file (e.g., via `/hookify` command output, a PR, or a shared/checked-in rule file). Any rule whose `pattern` or other frontmatter value legitimately or maliciously contains a `---` substring (common in regex patterns using en-dash-like separators, or artificially inserted by an adversary aiming to weaken review-time visible blocking rules) will trigger this misparse deterministically — it's not probabilistic, it happens on every load of that file via `load_rules`/`load_rule_file`.

### Recommendation
Replace the naive `content.split('---', 2)` boundary detection with a delimiter-aware parser that requires the `---` markers to appear alone on their own line (e.g., use `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or iterate lines and only treat a line that is exactly `---` after stripping as a boundary). Additionally, consider using a real YAML parser (e.g., `yaml.safe_load`) for the frontmatter block instead of the hand-rolled line-based parser, and add a validation step in `load_rule_file` that warns/rejects when a frontmatter value appears to contain an unterminated quote or when `action` is textually present in the raw file but absent from the parsed dict, to catch future parser drift.

### Proof of Concept
Differential unit test in `plugins/hookify/core/config_loader.py`'s test module (or a new `tests/test_config_loader.py`):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_embedded_dash_dash_dash_in_pattern_preserves_block_action():
    content = (
        "---\n"
        "name: test-rule\n"
        "enabled: true\n"
        "event: bash\n"
        'pattern: "foo---bar"\n'
        "action: block\n"
        "---\n\n"
        "Dangerous command detected!\n"
    )
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (author's intent): action stays 'block'
    assert frontmatter.get('action') == 'block'
    assert rule.action == 'block'
```
Running this against the current implementation fails: `frontmatter.get('action')` is `None` (missing) and `rule.action` resolves to the default `'warn'`, while `message` unexpectedly contains the leftover `bar"\naction: block\n---\n\nDangerous command detected!` text — demonstrating the boundary misparse and the resulting silent downgrade from `block` to `warn`. A companion integration test can feed the resulting `Rule` into `RuleEngine.evaluate_rules` with a matching `command` and assert that `permissionDecision` is `"deny"` (expected) but observe it never blocks (actual), confirming the enforcement bypass.
