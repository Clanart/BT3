### Title
Attacker-controlled `n` in `ThresholdKeys::read` drives unchecked allocation and decode loops before parameter validation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::<C>::read` deserializes the threshold parameters `t`, `n`, `i` directly from the input byte stream and then uses the attacker-chosen `n` to size `Vec::with_capacity` and to bound two deserialization loops (constant-interpolation scalars and per-participant verification-share points), all *before* `ThresholdParams::new` validates anything at the end of the function. An unprivileged party feeding crafted bytes to `ThresholdKeys::read` can force a large speculative allocation and tens of thousands of field/point decodings in a single call, causing excessive CPU and allocator pressure.

### Finding Description
In `crypto/dkg/src/lib.rs`:

```rust
// lines 591-623
let (t, n, i) = { ... read_u16() ... };        // attacker-controlled u16s

let mut interpolation = [0];
reader.read_exact(&mut interpolation)?;
let interpolation = match interpolation[0] {
  0 => Interpolation::Constant({
    let mut res = Vec::with_capacity(usize::from(n));  // alloc sized by untrusted n
    for _ in 0 .. n {                                  // up to 65535 read_F iterations
      res.push(C::read_F(reader)?);
    }
    res
  }),
  1 => Interpolation::Lagrange,
  ...
};

let secret_share = Zeroizing::new(C::read_F(reader)?);

let mut verification_shares = HashMap::new();
for l in (1 ..= n).map(Participant) {                  // up to 65535 read_G decodes
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}

ThresholdKeys::new(
  ThresholdParams::new(t, n, i).map_err(io::Error::other)?,  // validation only happens here
  ...
)
```

The same pattern exists in `Commitments::<C>::read` (`crypto/dkg/pedpop/src/lib.rs`, lines 110-127), which does `Vec::with_capacity(params.t().into())` and iterates `0 .. params.t()` calling `read_G`, where `t` comes from the `ThresholdParams` the caller built — for the PedPoP share-verification path (`KeyMachine::calculate_share`) these params originate from session configuration, so the attacker-controlled amplification is smaller there; the `ThresholdKeys::read` case is worse because `n` is fully byte-stream-controlled.

The resource consumption has two components:

1. **Speculative allocation:** `Vec::with_capacity(usize::from(n))` commits `n * size_of::<C::F>()` bytes (up to ~2 MiB for secp256k1/Ristretto-class fields at `n = 0xFFFF`) before a single scalar is read. A header of ~11 bytes (curve ID length + ID + `t`/`n`/`i` + interpolation tag) is enough to trigger it, and the allocation can abort the process on OOM or be repeated in a loop for allocator churn.
2. **Decode amplification:** each trailing 32-byte chunk causes one `read_F` canonical check, and each 32/33-byte chunk causes one `read_G` canonical point decompression plus a canonicality re-encode comparison (`crypto/ciphersuite/src/lib.rs` lines 91-100). Roughly 4 MiB of attacker bytes yields ~131k group decodings — several seconds of CPU per call with no length cap.

There is no upper bound or prefix length check on `n`, and `ThresholdParams::new` (which would reject nonsensical `t`/`n`/`i` combinations) is only consulted after all the work is done.

### Impact Explanation
Any endpoint, message handler, or stored blob that passes attacker-influenced bytes through `ThresholdKeys::read` (explicitly in scope) — e.g., key material or machine-state deserialization during coordinator/processor flows — lets a remote party burn CPU and transient memory far disproportionate to what they send. Repeated calls can degrade or stall the victim (excessive resource consumption rendering the instance less responsive), the same consequence class as the reference advisory (unbounded parameter sizes on staff endpoints). The amplification is bounded by `u16::MAX` iterations per call, so this is a Medium-severity DoS rather than unbounded corruption.

### Likelihood Explanation
- Reachable by an unprivileged party wherever serialized `ThresholdKeys` bytes cross a trust boundary (the audit scope itself lists `ThresholdKeys::read` as an untrusted-byte sink).
- Exploitation needs no valid signature, proof, or threshold relationship — the expensive work happens before `ThresholdParams::new` validation and before any consistency check between `n` and the actual buffer length.
- No secret material or special role is required; the payload is pure serialization bytes.

### Recommendation
- Validate `t`/`n`/`i` via `ThresholdParams::new` **immediately after reading them**, before any allocation or decode loop.
- Replace `Vec::with_capacity(usize::from(n))` with a bounded default capacity and push incrementally, or cap `n` at a protocol-appropriate maximum (e.g., the deployment's `MAX_PARTICIPANTS`).
- Apply the same early-validation fix to `Commitments::read` / `EncryptedMessage::read` callers so `params.t()` used for `with_capacity` and loop bounds is confirmed sane before use.
- Prefer readers that bound work by the actual remaining input length (e.g., `BufRead::fill_buf().len()` checks) so iteration count cannot exceed supplied bytes.
