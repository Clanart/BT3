### Title
Division by zero in `KIP71Config.NextMagmaBlockBaseFee` when governance sets `GasTarget` to 0 - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee`, which computes the next block's base fee under the Magma/KIP-71 dynamic fee mechanism, divides by `gasTarget` without checking that it is non-zero. The `Kip71GasTarget` governance parameter is registered with a no-op format checker that accepts any `uint64` value, including `0`, so a governance vote (or malformed/edge-case configuration) can set `GasTarget` to `0` and cause a `big.Int` division-by-zero panic when computing every subsequent block's base fee.

### Finding Description
`NextMagmaBlockBaseFee` in `params/kip71_config.go` uses `gasTarget := kc.GasTarget` and, when the block's gas usage differs from the target, computes: [1](#0-0) 

Specifically, in the "gas used > target" branch:
```
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))
``` [2](#0-1) 

and symmetrically in the "gas used < target" branch:
```
gasUsedDelta := new(big.Int).SetUint64(gasTarget - parentGasUsed)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, gasTarget)
``` [3](#0-2) 

Both branches call `x.Div(x, ...gasTarget)`, dividing directly by `gasTarget`. If `gasTarget == 0`, `math/big.Int.Div` panics with a runtime "division by zero" error (Go's `big.Int` does not return an error for zero divisor — it panics), unlike the `baseFeeDenominator` case a few lines above, which explicitly special-cases zero: [4](#0-3) 

The `GasTarget` value itself comes from the `Kip71GasTarget` governance parameter, whose `FormatChecker` is `noopFormatChecker` — i.e., no validation is performed, so `0` is an accepted value: [5](#0-4) 

This mirrors the reported Balancer bug class exactly: an array/parameter value (`balances[i]` there, `gasTarget` here) is used as a divisor without a zero-check, and there is no other validation layer that guarantees non-zero-ness before the division executes.

### Impact Explanation
`NextMagmaBlockBaseFee` is called by every node during block header verification (`VerifyMagmaHeader`) and fee-history/gas-price RPC processing for every block once Magma is active. A panic here is not merely a local DoS: every honest full node and consensus-participating node that validates a block under a `GasTarget == 0` governance configuration will panic during block processing, since header validation is mandatory consensus-critical code executed identically by all nodes. This causes a chain-wide processing halt / crash (node-wide DoS) that is reproducible deterministically by any node processing the affected chain configuration, rather than a benign single-node crash — satisfying the "state divergence / DoS impacting acceptance of a block" criterion.

### Likelihood Explanation
Governance parameters are explicitly permitted as a valid attack-surface category per the rules. The `Kip71GasTarget` parameter accepts arbitrary `uint64` values (including `0`) with no format validation, so a single governance vote/parameter update to `0` — or a governance parameter set inherited by an incorrect config/migration — reliably triggers the panic on the very next block once the new value takes effect, since block base-fee computation runs unconditionally for every block after Magma activation.

### Recommendation
Add an explicit zero-check for `gasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `baseFeeDenominator == 0` fallback (lines 71-76), e.g., falling back to a safe default or short-circuiting the computation when `gasTarget == 0`. Additionally, tighten the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` to reject `0` (similar to `Kip71BaseFeeDenominator`'s checker, which requires `v != 0`).

### Proof of Concept
1. Governance sets `Kip71GasTarget` to `0` (accepted because `FormatChecker: noopFormatChecker` performs no validation — [5](#0-4) ).
2. On the next block after Magma activation, any node with `parentGasUsed != 0` calls `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentGasUsed)`.
3. Since `parentGasUsed > gasTarget` (0) is true whenever any gas was used, the function proceeds to `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing `math/big` to panic with "division by zero" — [2](#0-1) .
4. This panic occurs inside block header validation/base-fee computation, crashing every node that processes the block, producing a chain-wide DoS.
