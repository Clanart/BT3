### Title
Relayer reward double-payment via `LastRewardedHeight` watermark that isn't updated atomically with the treasury transfer - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::FeeHandler::on_executed` pays a relayer for the block-span between a persisted watermark (`LastRewardedHeight`) and the newly observed `latest_commitment_height`, exactly the same broken pattern as the reported `StakingContract._calculateRewards()` bug: the reward range is computed from `[baseline, latest]` and only `baseline` should be advanced once the payment is made final. Here, the transfer to the relayer and the watermark advance are **two separate, non-atomic steps**, and the second (`mint_into` reputation token) can fail and abort the whole function *after* the treasury funds have already moved but *before* the watermark is updated.

### Finding Description
`process_message` in [1](#0-0)  executes, in order:
1. `calculate_reward` — computes `reward = (latest_height - baseline) * block_cost`, where `baseline = LastRewardedHeight::get(state_machine_id).unwrap_or(previous_height)`.
2. `T::Currency::transfer(treasury, relayer_account, reward, ...)` — the actual fund movement.
3. `T::ReputationAsset::mint_into(&relayer_account, reward)` — a **second**, independent side effect that can fail (`Error::ReputationMintFailed`), using `?`/`map_err(...)?` which returns early on failure.
4. `LastRewardedHeight::mutate(...)` — only reached if steps 2 and 3 both succeeded.

Because `mint_into` is called *after* the treasury transfer but *before* the watermark update, any deterministic failure of `mint_into` (e.g. a brand-new `relayer_account` whose reward amount is below the reputation asset's existential deposit, or any pallet-assets rejection tied to that specific account) causes the function to return `Err`. The caller `on_executed` swallows this error unconditionally: [2](#0-1) 

`let _ = Self::process_message(...)` discards the error, so the extrinsic that dispatched the consensus message still succeeds, the relayer already has the treasury funds in hand, but `LastRewardedHeight` was never advanced past `baseline`. On the *next* successful consensus-message batch for that same `state_machine_id`, `calculate_reward` recomputes the reward from the **same stale `baseline`** up to the new `latest_height` — which re-includes the block span that was already paid out in the failed-watermark call. The relayer is paid twice (or more, on every subsequent failure) for the same delivered block range.

This is structurally identical to the reported bug: the reward-accumulation loop keeps referencing a range boundary (`epochId` there, `latest_height`/`baseline` here) that is not exclusively advanced once consumed, letting a claimant collect rewards for an already-rewarded span more than once.

### Impact Explanation
Every duplicate payment is a direct, unauthorized transfer from `T::TreasuryAccount` to a relayer-controlled account for work that was already compensated — this is fund loss from the protocol treasury and a duplicate/double-settlement of a reward that should only ever be paid once per block span, matching the bounty's "stealing or loss of funds" / "double-claim" impact categories. Because `relayer_account` is recovered purely from the sr25519 signature embedded in the unsigned `ConsensusMessage` (see the pubkey recovery in `on_executed`, lines 112-122), an attacker fully controls which account receives the reward and can trivially generate a fresh keypair for every submission, deliberately keeping the reward below the reputation asset's minimum balance to force `mint_into` to fail deterministically, thereby forcing the watermark to never advance while still collecting the treasury transfer every single time.

### Likelihood Explanation
The attacker only needs to be a permissionless relayer submitting real consensus proofs (an unprivileged, expected participant) — no malicious admin, prover compromise, or leaked key is required. The only requirement is causing `mint_into` to fail on a per-account basis, which is a normal, reachable condition for `fungible::Mutate` implementations (e.g. below-existential-deposit mint into a freshly generated account), fully controllable by the attacker choosing the reward-amount/account pairing (via `block_cost` config and using disposable signer keys).

### Recommendation
Make the reward transfer and watermark advance atomic and reorder side effects so that any failure rolls back or is contained without leaving funds paid but the ledger not updated:
- Advance `LastRewardedHeight` (or otherwise durably commit the paid range) in the *same* transactional step as the currency transfer, before performing any additional, independently-fallible operation like `mint_into`.
- Make `mint_into` failures non-fatal to the overall extrinsic (e.g., log-and-continue) rather than aborting after the treasury transfer has already executed, or wrap the whole sequence in `frame_support::storage::with_transaction` so a `mint_into` failure reverts the transfer too.
- Consider using `<` boundary semantics / explicit inclusive-exclusive range checks, mirroring the same class of off-by-one/replay fix recommended in the source report.

### Proof of Concept
Conceptual sequence (pallet-level, matches the code path directly):
1. Configure `StateMachinesCostPerBlock` for some `state_machine_id` via `update_cost_per_block` (governance-set, standard operation).
2. Attacker generates a fresh sr25519 keypair `K1`, submits a valid unsigned `ConsensusMessage` signed by `K1` that advances `latest_commitment_height` for `state_machine_id` from height `H0` to `H1`.
3. In `process_message`: `calculate_reward` computes `reward = (H1 - H0) * block_cost`; `T::Currency::transfer` succeeds, paying `K1`'s account `reward`; `T::ReputationAsset::mint_into(K1, reward)` fails (fresh account below reputation-asset existential deposit) → function returns `Err(ReputationMintFailed)`; `on_executed` discards the error; `LastRewardedHeight` remains at `H0`.
4. Attacker submits a second valid consensus message (using `K1` again, or a new key `K2`) advancing height from `H1` to `H2`.
5. `calculate_reward` reads `baseline = LastRewardedHeight::get() = H0` (unchanged) and computes `reward' = (H2 - H0) * block_cost`, which re-includes the `[H0, H1]` span already paid in step 3.
6. Treasury pays out for `[H0, H1]` a second time inside `reward'`, and if `mint_into` again fails (e.g. attacker keeps using a fresh disposable key or an account intentionally kept below ED), the watermark still doesn't advance and the cycle repeats indefinitely, draining the treasury for the same delivered blocks on every batch.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}
