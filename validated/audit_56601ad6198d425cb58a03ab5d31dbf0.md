### Title
Duplicate `ReceivedOutput` inputs double-count funds and produce a consensus-invalid transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs` never deduplicates its `inputs: Vec<ReceivedOutput>`. The same outpoint can be supplied multiple times; its value is summed once per occurrence into `input_sat`, one `TxIn` per occurrence is emitted into the transaction, and one FROST signing machine is created per occurrence. This is the Serai analog of the `drm_put_dev()` double-free: the same resource (a UTXO) is consumed/decremented twice because two code paths treat the duplicated object as independent — mirroring devres and the driver both releasing the device.

### Finding Description
`SignableTransaction::new` performs all validity checks on the *summed* inputs:

- `input_sat` is computed as `inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>()` (send.rs:175), so a duplicated `ReceivedOutput` counts its satoshis twice.
- `tx_ins` is built by mapping every element of `inputs` to a `TxIn` (send.rs:177-185), so a duplicated outpoint produces a transaction that spends the same UTXO twice — consensus-invalid under Bitcoin rules (a transaction may not contain duplicate inputs).
- `prevouts` and `offsets` are likewise collected per element (send.rs:176, 253), and `multisig` spawns one `AlgorithmMachine` per input index (send.rs:275-282), so the threshold group produces a signature share for each duplicated input.

There is no check that `input.outpoint` values are distinct anywhere in `new`, `multisig`, or `TransactionSignMachine::sign`. `ReceivedOutput` is freely attacker-constructible via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`), which reads an arbitrary offset scalar and arbitrary consensus-decoded `TxOut`/`OutPoint` — nothing binds the outpoint to an actual on-chain output.

### Impact Explanation
An unprivileged party that supplies transaction data for signing (the accepted reachability model: untrusted bytes deserialized via `ReceivedOutput::read` and passed to `SignableTransaction::new`/`multisig`/`sign`) can:

1. **Bypass `NotEnoughFunds`**: `input_sat` is inflated by each duplicate, so `input_sat < payment_sat + needed_fee` (send.rs:215) passes when real funds are insufficient. The change calculation (send.rs:228-234) then fabricates a change output of up to `k * value` phantom satoshis.
2. **Cause signing of an unintended, consensus-invalid transaction**: the multisig signs a TX whose input list contains the same outpoint twice. Every Bitcoin node rejects it, so the intended payments never confirm even though `fee()`/`needed_fee()` and all internal accounting report a valid spend. Combined with (1), the fabricated change/payment amounts mean the group signs outputs it cannot actually fund — a burn of a signing session and a liveness failure where operators believe funds moved.
3. Since each duplicated input gets its own Schnorr machine (send.rs:281), participants expend real preprocesses (which are single-use secrets) on a doomed transaction.

The parallel to the advisory: `drm_put_dev()` was invoked on an object already released by devres, corrupting refcount state; here, the same outpoint is "spent" (consumed into `tx_ins` and into `input_sat`) twice with no ownership/refcount guard, corrupting the transaction's accounting.

### Likelihood Explanation
Reachability requires an integrator/processor path to feed externally deserialized `ReceivedOutput`s into `SignableTransaction::new` — exactly the pattern the scanner→wallet pipeline uses (scanner outputs are deserialized and passed as inputs). A duplicate is trivially produced: two identical serialized `ReceivedOutput` blobs. No cryptographic break, no collusion, and no special curve/hash assumptions are needed — only the absence of an outpoint-uniqueness check. Impact is bounded to producing unconfirmable transactions and wasted single-use preprocesses rather than key/share recovery, so Medium.

### Recommendation
In `SignableTransaction::new` (send.rs:150+), reject duplicate outpoints before summing:

```rust
{
  let mut seen = std::collections::HashSet::with_capacity(inputs.len());
  for input in &inputs {
    if !seen.insert(input.outpoint) {
      Err(TransactionError::DuplicateInput)?;
    }
  }
}
```

Add a `DuplicateInput` variant to `TransactionError`. Optionally also defensively assert uniqueness of `prevouts` outpoints in `multisig`.

### Proof of Concept
```rust
// networks/bitcoin wallet context (regtest)
let output = send_and_get_output(&rpc, &scanner, key).await; // one real UTXO
// Attacker-controlled deserialization can also just clone/re-read the same bytes:
let dup = ReceivedOutput::read(&mut output.serialize().as_ref()).unwrap();
assert_eq!(dup.outpoint(), output.outpoint());

// Only ONE UTXO of value V exists, yet:
let tx = SignableTransaction::new(
  vec![output.clone(), dup],            // same outpoint twice
  &[(p2tr_script_buf(key).unwrap(), output.value() + 1000)], // > V payment
  None, None, FEE,
);
// Succeeds: input_sat = 2*V >= payment + fee, but the transaction has two
// identical TxIns and is consensus-invalid; the multisig will sign it anyway.
assert!(tx.is_ok());
```

Root cause confirmed at `networks/bitcoin/src/wallet/send.rs:175-185` (sum and `TxIn` construction with no uniqueness check) and `send.rs:275-282` (per-input signing machines for the duplicated outpoint).
