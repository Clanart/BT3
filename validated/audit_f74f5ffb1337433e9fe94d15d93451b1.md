## Analysis: Complexity budget scales with attacker-controlled byte length, but many bytecode instructions are metered at zero cost

The budget computation and check happen together at the point modules are unpacked for publishing: [1](#0-0) 

For each `(module, blob)` pair, `budget = 2048 + blob.code().len() as u64 * 20` is derived purely from that module's own serialized byte length, and is then spent against `check_module_complexity`, which meters: [2](#0-1) 

Inside `meter_code`, only instructions that reference generic-instantiation tables (`CallGeneric`, `PackGeneric`, `ExistsGeneric`, field/variant generic instructions) or signature/vector-index instructions actually call `self.charge(...)`: [3](#0-2) 

A large class of straight-line, non-generic instructions — `Pop`, `Ret`, `Branch`, `BrTrue`/`BrFalse`, all `Ld*`/`Cast*` ops, non-generic `Call`/`Pack`/`Unpack`, `ReadRef`/`WriteRef`/`FreezeRef`, arithmetic/bitwise ops, etc. — fall into the exhaustive match arm that has **no corresponding `self.charge()` call**, i.e. they cost `0` toward the complexity budget: [4](#0-3) 

This confirms the exploit primitive the question describes: an attacker can append fully reachable, stack-balanced, zero-cost instructions (e.g. `LdTrue; Pop` pairs, 2 bytes each) to a function body. Each such pair adds 2 bytes to `blob.code().len()`, granting `+40` complexity budget (`2 * 20`) while charging `0` against that same budget. This surplus can then be spent elsewhere in the *same* module on genuinely expensive constructs — specifically deeply nested generic instantiations (`CallGeneric`/`PackGeneric`/`StructDefInstantiation`/`FieldInstantiation` type-parameter signatures), which are the only constructs this checker is actually designed to bound.

It's worth noting there is a second, independent complexity check gated behind `SAFER_METADATA`: [5](#0-4) [6](#0-5) 

but this metadata-level check uses a fixed `COMPLEXITY_BUDGET` (not scaled by byte length) and only walks signatures, function/struct handles, struct-def fields, and locals signatures — it never meters `function_instantiations`, `struct_def_instantiations`, or `field_instantiations` tables referenced from generic bytecode instructions. So it does **not** act as a backstop for the specific generic-instantiation complexity that `check_complexity.rs` is meant to police, and does not close this gap.

### Verdict

This is a legitimate weakness in the size-proportional budget design: the correlation the budget formula assumes (larger byte size → proportionally larger legitimate complexity) is broken because a broad set of bytecode instructions are metered at zero cost while still contributing to `blob.code().len()`. An attacker can therefore inflate `budget` arbitrarily cheaply (bytes-in for budget-out at a fixed, attacker-favorable ratio) and use the surplus to smuggle genuinely deep generic-instantiation complexity past `check_module_complexity` that would otherwise be rejected.

### Title
Zero-cost bytecode padding inflates size-proportional complexity budget, allowing genuinely complex generic instantiations to bypass `check_module_complexity` - (File: `aptos-move/aptos-vm/src/aptos_vm.rs`, `third_party/move/move-binary-format/src/check_complexity.rs`)

### Summary
`AptosVM` computes a per-module complexity budget as `2048 + blob.code().len() * 20` and checks it against `check_module_complexity` before publishing. Several common bytecode instructions (`Pop`, `Ret`, `Branch`, loads/casts, non-generic `Call`/`Pack`/`Unpack`, ref ops, arithmetic) are metered at zero cost in `meter_code`, yet still count toward `blob.code().len()`. An attacker can pad a module with cheap, reachable, zero-charge instructions to inflate the budget without spending any of it, then use the resulting surplus to hide legitimately-too-complex generic type instantiations elsewhere in the same module.

### Finding Description
See analysis above: [1](#0-0) [4](#0-3) 

### Impact Explanation
`check_module_complexity` is the only guard bounding generic instantiation complexity (`FunctionInstantiation`/`StructDefInstantiation`/`FieldInstantiation` type-parameter signatures) that can cause verifier/loader resource blowup. Defeating its intended size-to-complexity ratio via cheap padding lets modules with excessive generic-type complexity be published/upgraded on mainnet, undermining the resource-bound guarantee this check exists to provide.

### Likelihood Explanation
Any unprivileged account submitting a module publish/upgrade transaction can construct such padding; no special privileges or ownership are required, and the padding instructions are ordinary, valid, reachable Move bytecode that will pass all other verifier stages (stack balance, typing, control flow).

### Recommendation
Charge a non-zero baseline cost per bytecode instruction (proportional to instruction count, not just size-derived budget), or decouple the budget from `blob.code().len()` and instead derive it from a metric that itself is fully accounted for by the meter (e.g., total metered cost of a reference/baseline module), so that padding cannot manufacture budget without spending it.

### Proof of Concept
Construct a Move module function body consisting of many `LdTrue; Pop` pairs (or similar zero-cost instruction pairs) appended before a legitimate `Ret`. Each pair adds ~2 bytes to `blob.code().len()` (thus `+40` to `budget`) while calling `self.charge()` for `0`. Separately embed deeply nested generic struct/function instantiations sized so they would fail `check_module_complexity` under the baseline budget of `2048 + (unpadded_len * 20)`. Verify that after adding sufficient padding pairs to inflate `blob.code().len()`, the same generic-instantiation-heavy module now passes `check_module_complexity` at `aptos_vm.rs:1675` where it previously failed at the true (unpadded) size-to-complexity ratio.

pub fn check_module_complexity(module: &CompiledModule, budget: u64) -> PartialVMResult<u64> {
    let meter = BinaryComplexityMeter {
        resolver: BinaryIndexedView::Module(module),
        cached_signature_costs: RefCell::new(BTreeMap::new()),
        balance: RefCell::new(budget),
    };

    meter.meter_signatures()?;
    meter.meter_function_instantiations()?;
    meter.meter_struct_def_instantiations()?;
    meter.meter_field_instantiations()?;

    meter.meter_function_handles()?;
    meter.meter_struct_handles()?;
    meter.meter_function_defs()?;
    meter.meter_struct_defs()?;

    let used = budget - *meter.balance.borrow();
    Ok(used)
}

/// Checks the complexity of a module.
fn check_module_complexity(module: &CompiledModule) -> Result<(), MetaDataValidationError> {
    let mut meter: usize = 0;
    for sig in module.signatures() {
        for tok in &sig.0 {
            check_sigtok_complexity(module, &mut meter, tok)?
        }
    }
    for handle in module.function_handles() {
        check_ident_complexity(module, &mut meter, handle.name)?;
        for tok in &safe_get_table(module.signatures(), handle.parameters.0)?.0 {
            check_sigtok_complexity(module, &mut meter, tok)?
        }
        for tok in &safe_get_table(module.signatures(), handle.return_.0)?.0 {
            check_sigtok_complexity(module, &mut meter, tok)?
        }
    }
    for handle in module.struct_handles() {
        check_ident_complexity(module, &mut meter, handle.name)?;
    }
    for def in module.struct_defs() {
        match &def.field_information {
            StructFieldInformation::Native => {},
            StructFieldInformation::Declared(fields) => {
                for field in fields {
                    check_ident_complexity(module, &mut meter, field.name)?;
                    check_sigtok_complexity(module, &mut meter, &field.signature.0)?
                }
            },
            StructFieldInformation::DeclaredVariants(variants) => {
                for variant in variants {
                    check_ident_complexity(module, &mut meter, variant.name)?;
                    for field in &variant.fields {
                        check_ident_complexity(module, &mut meter, field.name)?;
                        check_sigtok_complexity(module, &mut meter, &field.signature.0)?
                    }
                }
            },
        }
    }
    for def in module.function_defs() {
        if let Some(unit) = &def.code {
            for tok in &safe_get_table(module.signatures(), unit.locals.0)?.0 {
                check_sigtok_complexity(module, &mut meter, tok)?
            }
        }
    }
    Ok(())
