### Title
Forfeiture-avoidance via cancelUnlock/startUnlock toggling around MGP reward claim - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`queueMGP` computes the forfeiture on harvested MGP purely from the *current* on-chain cooldown state of `_account` via `_calExpireForfeit` → `vlMGP.getRewardablePercentWAD(_account)` [1](#0-0) . Since `getRewardablePercentWAD` treats any amount currently sitting in a cooldown slot as partially/fully "not rewardable" [2](#0-1) , and since `cancelUnlock`/`startUnlock` are permissionless, unrestricted, and freely callable by the account owner at any time [3](#0-2) [4](#0-3) , a user can zero out their cooldown state immediately before triggering their own reward claim, harvest 100% of the rewardable MGP with no forfeiture, then re-enter the same cooldown slot right after — completely defeating the anti-gaming forfeiture mechanism.

### Finding Description
`getUserTotalLocked` = `amountInMasterMagpie - amountInCoolDown` [5](#0-4) , and `getRewardablePercentWAD` weights the forfeiture percentage based on how much of a user's vlMGP is "fully locked" vs. "in cooldown" at the moment of the call [2](#0-1) . `cancelUnlock` unconditionally zeroes `slot.amountInCoolDown` and decrements `totalAmountInCoolDown`, with no cooldown-elapsed or minimum-holding-time requirement other than that the slot must currently be in cooldown [4](#0-3) . `startUnlock` can then immediately recreate an equivalent cooldown slot for the same amount [3](#0-2) .

Exploit flow (attacker is `_account` and `_receiver` for their own claim, e.g. via `multiclaimFor`/`multiclaim` → `MasterMagpie._multiClaim` → `_sendMGPForVlMGPPool` → `queueMGP` [6](#0-5) [7](#0-6) ):
1. Attacker has an open cooldown slot with `amountInCoolDown = X`.
2. Attacker calls `cancelUnlock(slotIndex)` — cooldown amount is reset to 0, so `getUserTotalLocked` increases by `X`, making `getRewardablePercentWAD` return (near) 100%.
3. Attacker triggers their reward claim (`multiclaim`/`multiclaimSpec`), which routes into `queueMGP(amount, attacker, attacker)`. Since `_calExpireForfeit` now sees 100% rewardable percent, `forfeitAmount = 0` and the *entire* harvested MGP is transferred to the attacker instead of a portion being redirected to `_queueNewRewardsWithoutTransfer` for other vlMGP stakers [8](#0-7) .
4. Attacker calls `startUnlock(X)` again to restore their original cooldown position, with no economic penalty for having briefly cancelled it.

This is not blocked by any existing check: `cancelUnlock`/`startUnlock` are `whenNotPaused` only (no rate limit, no minimum time-in-cooldown, no forced forfeiture-lock), and `queueMGP`'s `nonReentrant` guard does not protect against sequential/cross-contract calls in the same or adjacent transactions [1](#0-0) . Because `_account` and `_receiver` are attacker-controlled in this normal self-claim path (the manager parameter itself is not the vulnerability — the arbitrary-receiver framing is a red herring since `_account == _receiver` here), the root cause is that forfeiture is a point-in-time snapshot rather than integrated/committed state.

### Impact Explanation
This results in theft of unclaimed yield: MGP that should be forfeited (redirected as extra reward to honestly-locked vlMGP stakers via `_queueNewRewardsWithoutTransfer`) is instead retained in full by the attacker, at the expense of all other vlMGP stakers who rely on the forfeiture-redistribution mechanism. This matches "theft of unclaimed yield" in the specified scope.

### Likelihood Explanation
Fully permissionless and repeatable: any vlMGP holder with an open cooldown slot can perform this sequence around every reward claim, at no capital cost beyond gas, and can repeat it indefinitely for every future harvest. No special privileges, flash loans, or front-running are required — `cancelUnlock` → claim → `startUnlock` can be done by the attacker themselves in sequential transactions (or bundled via a smart-contract wallet in one transaction), since none of these are `onlyEOA`-restricted or time-locked against each other.

### Recommendation
Base the forfeiture calculation on a time-weighted/committed measure rather than instantaneous state — e.g., snapshot the user's rewardable percentage at accrual time per reward-per-token update instead of at claim time, or impose a minimum dwell time before `cancelUnlock` can reverse a cooldown, or make `cancelUnlock` itself trigger a mandatory `queueMGP`-equivalent forfeiture settlement for pending unclaimed rewards before resetting cooldown state.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, MGP token; set up attacker as staker with locked vlMGP and pending MGP rewards accrued in another pool routed through `MasterMagpie`.
2. Baseline: attacker calls `startUnlock(X)` to place `X` into cooldown, waits, then calls `multiclaim` to harvest MGP without cancelling — record `forfeitAmount` emitted in `MGPHarvested` (should be > 0 given `getRewardablePercentWAD < 100%`).
3. Exploit: reset state, attacker calls `cancelUnlock(slotIndex)`, then `multiclaim` (same pending reward amount), then `startUnlock(X)` again in the same or immediately following transactions.
4. Assert: in the exploit run, `forfeitAmount == 0` and attacker receives the full `rewardableAmount == amount`, versus baseline where `forfeitAmount > 0` and a smaller amount is received — proving that forfeiture is bypassable and diverted yield is retained by the attacker instead of being queued as forfeit reward for other stakers.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
