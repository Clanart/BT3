### Title
Attacker-controlled duplicate `EncryptionKeyMessage` triggers `assert!` panic aborting PedPoP key generation - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2017-18252 is an assertion-failure/abort denial of service: a crafted input reaches a code path that crashes the process rather than returning an error. The Serai analog is `Decryption::register` in the PedPoP DKG encryption layer, which enforces "one registration per participant" with `assert!` instead of a fallible check. An untrusted `EncryptionKeyMessage` (read via the in-scope `EncryptionKeyMessage::read` path) is passed to `register` keyed by its claimed sender; a second message attributed to the same `Participant` panics the honest party's process mid-DKG. This is the same bug class: a reachable panic on externally supplied message data where a `Result` should have been returned.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption::register` performs:

```rust
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

(`encryption.rs:351-361`, reached through `Encryption::register` at `encryption.rs:452-458`).

The `participant` key is attacker-controlled: it is the sender index associated with a received `EncryptionKeyMessage<C, M>`, which is deserialized from untrusted bytes via `EncryptionKeyMessage::read` (`encryption.rs:57-59`, calling `M::read` and `C::read_G`). The PedPoP `Commitments` docs explicitly note the library "does not handle networking" and cannot deduplicate messages per participant (`crypto/dkg/pedpop/src/lib.rs:98-101`), so nothing upstream guarantees `register` is invoked at most once per participant.

The same shape exists elsewhere in this module on attacker-influenced keys: `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` (`encryption.rs:388`) — a panic if the accused names a `decryptor` that never registered — and `encrypt` indexes `self.decryption.enc_keys[&participant]` (`encryption.rs:466`).

For contrast, all other deserialization paths examined (`Commitments::read`, `SchnorrSignature::read`, `DLEqProof::read`, `ThresholdKeys::read`, `Transaction::read`) return `io::Error` on malformed input; this `assert!` is the reachable non-fallible check on peer-supplied state.

### Impact Explanation
An assertion failure aborts (or unwinds-panics across the DKG driver) the honest participant's process while processing PedPoP messages, killing the in-progress key-generation session and, depending on how the integrator drives the library, the whole signer task. There is no error to recover from — the `assert!` cannot be handled by the caller's `io::Result`/`FrostError` handling. This matches the CVE's availability impact (CVSS 6.5, `A:H`, requires a party to send input, `PR:N/UI:R` analog). No secret material is leaked.

### Likelihood Explanation
Reachability requires the attacker to be a participant in a PedPoP key-generation session (or be able to get a second message attributed to an existing `Participant` index delivered to a victim's `register`). Within that threat model the trigger is trivial: send any two `EncryptionKeyMessage`s for the same sender index — the bytes need not even be valid beyond parsing, since the map check happens before any cryptographic verification of `msg.enc_key` or `msg.msg`. No race, no expensive computation, no valid proof required. Likelihood is bounded by the requirement to be a DKG counterparty, hence Medium rather than High.

### Recommendation
Replace the `assert!` in `Decryption::register` with a fallible check returning a distinct error (e.g., extend a `PedPoPError`/`DkgError` variant or return `io::Error::other("duplicate encryption key registration")`), and have callers treat it as evidence of a faulty/malicious participant for blame purposes rather than crashing. Similarly, replace the `HashMap` indexing at `encryption.rs:388` and `encryption.rs:466` (`enc_keys[&participant]`) with `get()` + error return so a blame proof or encrypt request naming an unregistered `Participant` yields a protocol error instead of a panic.

### Proof of Concept
Conceptual, against a node running `PedPoP`:

1. Join a PedPoP session as participant `j`. Let the honest victim create `Encryption::new(context, i, rng)` and begin collecting `EncryptionKeyMessage`s.
2. Send message `M1` = `EncryptionKeyMessage::<C, M>::read`-able bytes `{ msg: valid_msg_bytes, enc_key: valid_point_bytes }` attributed to participant `j`. Victim calls `decryption.register(j, M1)` → `enc_keys.insert(j, ...)`, success.
3. Send message `M2` = any second `EncryptionKeyMessage` attributed to `j` (the inner `msg`/`enc_key` bytes may be arbitrary valid encodings — they are never verified before the panic).
4. Victim calls `decryption.register(j, M2)` → `self.enc_keys.contains_key(&j)` is `true` → `assert!` fails → process panics/aborts mid-DKG, identical in effect to the `ReplaceImageInList` assertion abort in CVE-2017-18252.

No nonce reuse, no valid signatures, and no threshold collusion are required — only a repeated sender index on the unauthenticated message stream the library explicitly delegates to the caller.
