### Title
Fee/weight calculation omits the OP_RETURN data output, underpaying the actual vsize - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts an optional `data` parameter which is turned into an OP_RETURN `TxOut` and pushed onto the transaction's output list. However, the weight/vbyte estimation used to compute `needed_fee` is performed by `calculate_weight_vbytes`, which rebuilds a transaction containing only `payments` and optionally `change` — the OP_RETURN output is never included. The resulting `needed_fee` therefore corresponds to a smaller transaction than the one actually produced, so the real fee rate (`fee() / vsize`) is lower than the caller-specified `fee_per_vbyte`, and can fall below the minimum relay fee even when `fee_per_vbyte` was chosen to satisfy it. This is the same bug class as the USSD report: a value formula (`calculateMint` / `needed_fee`) that produces an incorrect amount because an input to the computation was dropped.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before any fee accounting:

```
// networks/bitcoin/src/wallet/send.rs
193|    // Add the OP_RETURN output
194|    if let Some(data) = data {
195|      tx_outs.push(TxOut {
196|        value: Amount::ZERO,
197|        script_pubkey: ScriptBuf::new_op_return(...)
198|      });
```

but the fee is derived from:

```
204|    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
206|    let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs a fresh `Transaction` whose `output` list is built only from `payments` (lines 85–93) plus an optional `change` output (lines 95–99). The `data` output is never passed to it. The same omission occurs in the change branch at lines 224–235, which again calls `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`.

The consequence is twofold:

1. The actual transaction is `OP_RETURN output size` (≈ 12–91 bytes for the allowed ≤80-byte payload) larger than estimated, so `needed_fee` underpays relative to `fee_per_vbyte`. The public `needed_fee()`/`fee()` getters report a fee that does not achieve the requested rate.
2. More critically, the `TooLowFee` check at line 211 validates `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *underestimated* vbytes. A caller who sets `fee_per_vbyte` exactly to the minimum relay rate produces a transaction whose true fee rate is below the relay minimum. Such a transaction will not be relayed/confirmed by default policy — the spent inputs' funds are effectively locked behind an unbroadcastable transaction (fixable only by reconstructing and re-signing a new transaction through the full FROST signing ceremony).

Additionally, `weight` used for the `MAX_STANDARD_TX_WEIGHT` check at line 241 excludes the data output's weight, so the size bound is also checked against an underestimated weight.

### Impact Explanation
Any consumer of `bitcoin-serai`'s wallet that passes `Some(data)` receives a `SignableTransaction` whose paid fee rate is strictly lower than requested, by up to ~90 vbytes worth of satoshis. At borderline fee rates the resulting transaction is non-relayable under Bitcoin Core's default minimum-fee policy, so the multisig's funds committed in the inputs cannot move until a corrected transaction is re-signed — a funds-frozen/loss-of-liveness condition caused purely by an incorrect amount calculation, mirroring the USSD "users receive a fraction of the computed value" defect.

### Likelihood Explanation
Reachable by any caller supplying the optional `data` argument to `SignableTransaction::new` — a public input to the API. Triggering the relay failure requires choosing a fee rate at or near the minimum, which is the natural choice when the `TooLowFee` guard exists precisely to enforce that floor. The underpayment itself occurs on every call that includes `data`, regardless of fee rate.

### Recommendation
Include the data output in the transaction constructed inside `calculate_weight_vbytes` (e.g., pass the already-built `tx_outs` — including the OP_RETURN output — into the estimator, or append a `TxOut` with the correct `script_pubkey` length), and re-derive both `needed_fee` and `weight` from that complete output set. Concretely: compute `tx_outs` (payments + OP_RETURN) first, then estimate weight from those outputs, then optionally append change and re-estimate.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin/src/wallet/send.rs
let data = vec![0xAA; 80]; // max allowed OP_RETURN payload
let st = SignableTransaction::new(
    vec![input],
    &payments,
    None,
    Some(data),
    MIN_FEE_PER_VBYTE, // e.g. 1 sat/vbyte equivalent passing the TooLowFee check
).unwrap();
// The real tx contains an extra ~91-byte OP_RETURN output that was never
// included in calculate_weight_vbytes, so:
//   st.fee() / st.transaction().vsize() < MIN_FEE_PER_VBYTE
// The transaction is below the default minimum relay fee and will be rejected
// by Bitcoin Core nodes, freezing the inputs.
```

The bug is directly visible in the code: `calculate_weight_vbytes` at `networks/bitcoin/src/wallet/send.rs:62-99` builds its estimation transaction from `payments` and `change` only, while the actual `tx_outs` (built at lines 188–202) include the additional OP_RETURN output — so every estimate at lines 204 and 225–226 omits bytes that appear in the final signed transaction.
