### Title
Unbounded `governance.unitprice` vote allows base gas price to be set to any value with no upper-bound check - ([File: kaiax/gov/param.go])

### Summary
The reported bug class is a fee-setter with no upper bound (`TokenBridgeBase.sol` `setBrc20TransferFee`/`setRunesTransferFee`/`setBtcTransferFee`). The same class of issue exists in Kaia's governance parameter system: `GovernanceUnitPrice` (the `governance.unitprice` parameter, which corresponds to the network's fixed/base gas price) is validated only by a no-op format checker, with no maximum-value check, unlike other numeric governance parameters that at least cross-validate against a companion bound (e.g. `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`).

### Finding Description
`governance.unitprice` is defined in the governance parameter table with: [1](#0-0) 

`noopFormatChecker` always returns `true` regardless of input: [2](#0-1) 

Compare this to `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which are also `noopFormatChecker` at the `Param` definition level, but are given an *additional* consistency check in `checkConsistency` at header-governance-vote time, cross-checking lower against upper: [3](#0-2) 

`GovernanceUnitPrice`, however, falls into the catch-all "no more checks here" branch of `checkConsistency`, alongside other numeric governance parameters that lack any format/range validation beyond canonicalization to `uint64`: [4](#0-3) 

Because the canonicalizer is `uint64Canonicalizer`, any value up to `2^64-1` is accepted as a valid vote value and later merged into the effective `ParamSet.UnitPrice`: [5](#0-4) 

`UnitPrice` directly acts as the minimum/base transaction gas price enforced by the tx pool and used in gas price computations (`node/cn/gasprice/gasprice.go`, `blockchain/tx_pool.go`, `blockchain/error.go` reference `UnitPrice` heavily), so an extreme value effectively prices every ordinary transaction sender out of the network or, in pre-Magma/legacy fee mode, forces senders to pay an attacker-chosen arbitrarily high fee per unit of gas.

### Impact Explanation
If `governance.unitprice` is voted to an extreme value (e.g., near `uint64` max), all subsequent transactions built against that parameter set must pay gas price ≥ that value, causing a denial-of-service on the network (no ordinary transaction can practically be included) or, conversely, if used as a fixed fee multiplier elsewhere, could cause fee/value overflow-adjacent effects during `mgval`/`feeCap` computation in `buyGas`. This is analogous to the reported "fees can grow to infinite" issue: the network fee parameter has no protocol-level ceiling, and unlike KIP-71 base fee bounds (which are cross-checked against each other), `UnitPrice` has zero range validation.

### Likelihood Explanation
This can only be triggered via a governance vote (by validator council members / the governing node in `single` governance mode), which is explicitly listed as an in-scope reachable actor class ("governance parameters"). The vote path itself performs no additional bounds checking beyond canonicalization, so a colluding or compromised governing node/validator majority can set this without any protocol-level rejection — this mirrors the acknowledged status of the original report (client accepted no upper-bound enforcement for a similarly unconstrained fee parameter).

### Recommendation
Add an explicit `FormatChecker` (or a `checkConsistency` case) for `GovernanceUnitPrice` that enforces a sane maximum value (and possibly a minimum), similar to the `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` cross-check pattern, to prevent a single governance vote from setting an unbounded fee/gas price value that can degrade network usability or create fee-computation edge cases.

### Proof of Concept
1. As governing node (single mode) or via validator council vote, submit a header vote for `governance.unitprice` with value `uint64(math.MaxUint64)` (or any impractically large number), following the same vote mechanics tested in: [6](#0-5) 
2. Because `GovernanceUnitPrice`'s `FormatChecker` is `noopFormatChecker` and it is not covered by any special case in `checkConsistency` (falls into the "no more checks" branch), the vote is accepted without any upper-bound rejection.
3. Once finalized, `ParamSet.UnitPrice` is updated to the extreme value via `ParamSet.Set`, and this value is subsequently used by the tx pool / gas price logic as the enforced gas price floor, pricing out all ordinary transactions network-wide.
