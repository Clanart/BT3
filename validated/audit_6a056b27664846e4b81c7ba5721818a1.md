### Title
`SignableTransaction::new` computes weight/vbytes (and thus fee and max-weight check) on a transaction missing the OP_RETURN output, so the signed transaction is larger than what the fee was priced for - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/bsaldua/serai--019/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the reported bug — a value produced in one "scale"/view being consumed by a caller that expects a different view — `SignableTransaction::new` adds an `OP_RETURN` data output to `tx_outs`, but then calculates the transaction's weight and vbytes via `calculate_weight_vbytes(inputs, payments, change)`, which builds a template transaction containing *only* the payments (and optional change). The fee (`needed_fee = fee_per_vbyte * vbytes`), the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check are all evaluated against a transaction that is smaller than the one actually signed and broadcast.

### Finding Description
- At `send.rs:194-202`, if `data` is `Some`, a `TxOut` with the OP_RETURN script is pushed to `tx_outs`.
- At `send.rs:204` and `send.rs:225-226`, `calculate_weight_vbytes` is called with `payments` only; its internal template `Transaction` (lines 68-99) has outputs = payments + optional change. The `data` output is never included.
- The resulting `vbytes` feeds `needed_fee` (line 206), `fee_with_change` (line 227), and the dust/change decision (`input_sat.checked_sub(payment_sat + fee_with_change)`, line 228) — all priced for a transaction that omits the OP_RETURN output (~11-93 vbytes for up to 80 bytes of data, plus output overhead).
- The `TooLowFee` check (line 211) and the `MAX_STANDARD_TX_WEIGHT` check (line 241) are likewise validated against the understated size.

The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()`, line 138-141). When a change output is created, the change absorbs the shortfall: change is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` was priced for a smaller vbytes, so the effective fee rate of the final transaction is strictly lower than the requested `fee_per_vbyte`. When no change is created, the transaction still carries more bytes than priced, and the `TooLowFee` guard may pass a transaction that is actually under the default minimum relay fee once the real size is accounted for.

### Impact Explanation
The produced transaction's effective sat/vbyte rate is lower than the caller-specified `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite the explicit guard intended to prevent exactly that. Consequences:
- Transactions that are non-standard/under-fee will be rejected or stuck in mempools, delaying or preventing spends of multisig-controlled funds.
- Change outputs are reduced by the unpriced bytes' worth of fee only in effect; more importantly, a transaction can be constructed which fails relay, causing funds to be unspendable until a new transaction is built.
- The `MAX_STANDARD_TX_WEIGHT` check can be bypassed by up to the size of the OP_RETURN output (80-byte data + output/serialization overhead ≈ ~93 vbytes / ~372+ WU), allowing a transaction that exceeds standard weight to be accepted for signing.

### Likelihood Explanation
Any caller passing `data` to `SignableTransaction::new` (e.g., payment metadata/OP_RETURN for batched outputs) triggers the discrepancy; it is deterministic whenever `data.is_some()`. Whether the underpayment causes relay failure depends on margin between `fee_per_vbyte` and the relay minimum — but the fee is *always* lower than requested, and the weight check is *always* validated against the wrong transaction.

### Recommendation
Include the OP_RETURN output in the size estimate: pass the actual output list (or a `data: Option<&PushBytesBuf>`/`script_pubkey` parameter) into `calculate_weight_vbytes` so the template transaction matches the final one. Concretely, build the OP_RETURN `TxOut` before computing weight and extend `calculate_weight_vbytes` to accept extra outputs, then use the corrected `vbytes` for `needed_fee`, the `TooLowFee` check, `fee_with_change`, and the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
let data = vec![0xaa; 80];
let tx = SignableTransaction::new(
    vec![input],                       // ReceivedOutput
    &[(payment_script, payment_amt)],  // payments
    Some(change_script),               // change
    Some(data.clone()),                // OP_RETURN output added to tx_outs (L194-202)
    fee_per_vbyte,
).unwrap();

// calculate_weight_vbytes (L204, L225) was called with `payments` only;
// its template tx (L85-93) has outputs = payments (+ change), no OP_RETURN.
// Therefore tx.needed_fee() == fee_per_vbyte * vbytes(without OP_RETURN)
// while the real transaction is ~93 vbytes larger.
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));
// tx.fee() / real_vbytes < fee_per_vbyte  -> effective feerate is understated,
// and the L211 TooLowFee / L241 MAX_STANDARD_TX_WEIGHT checks used the wrong size.
```
