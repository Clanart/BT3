### Title
Unauthenticated `ReceivedOutput` bytes are committed into the threshold-signed sighash via `Prevouts::All`, letting an attacker forge prevout values the multisig signs over - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
CVE-2026-12249's class is "unauthenticated network-supplied data installed into a trust anchor and then relied upon for all subsequent security decisions". In `bitcoin-serai`, the analog is the `ReceivedOutput` / `SignableTransaction` pipeline: a `ReceivedOutput` is a purely self-claimed tuple `(offset, TxOut, OutPoint)` deserialized from untrusted bytes by `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) with no binding to on-chain reality, and `SignableTransaction` then treats the embedded `TxOut` as ground truth — both for solvency/fee math in `SignableTransaction::new` (`send.rs:175-235`) and as the `Prevouts::All` data every FROST signer commits to in the BIP-341 sighash (`send.rs:373-390`).

### Finding Description
`ReceivedOutput::read` accepts an arbitrary `Scalar` offset, an arbitrary `TxOut` (value + script_pubkey), and an arbitrary `OutPoint` from an untrusted reader (`networks/bitcoin/src/wallet/mod.rs:122-133`). The only consistency check anywhere is in `SignableTransaction::multisig`, which verifies that `key + G*offset` produces a P2TR script equal to `prevouts[i].script_pubkey` (`send.rs:275-279`). Nothing validates that:

- the `outpoint` actually exists on-chain,
- the claimed `output.value` equals the real UTXO's value, or
- the claimed `output.script_pubkey` equals the real UTXO's script.

`SignableTransaction::new` computes `input_sat`, change, and the fee from the *claimed* values (`send.rs:175`, `send.rs:228-233`), and `TransactionSignMachine::sign` builds `Prevouts::All(&self.tx.prevouts)` from the same claimed `TxOut`s, so every participant's Schnorr share is a BIP-340 signature over a `taproot_key_spend_signature_hash` that commits to attacker-chosen prevout amounts (`send.rs:373-390`). Any party able to feed serialized `ReceivedOutput`s into an input-selection/signing path (the data "received" by the scheduler) can therefore cause the threshold to produce shares over a sighash describing prevouts that do not match the real UTXO set.

### Impact Explanation
Two concrete consequences:

1. **Funds reported received/spent that are not spendable.** With an inflated `output.value`, `SignableTransaction::new` reports sufficient funds, emits payments/change, and all honest signers produce a fully valid-looking signed `Transaction` — which the Bitcoin network permanently rejects because BIP-341 sighash commits to the (wrong) prevout amounts. The protocol has signed and "spent" nonexistent value; the plan/eventuality completes while no spendable transaction exists.
2. **Signing of an unintended message.** The sighash is attacker-malleable via the claimed `TxOut`s; distinct signer subsets fed distinct forged `ReceivedOutput`s sign divergent messages, and a uniformly-forged input yields a signature bound to fabricated amounts — the signature itself is authentic, the committed semantics are not. Value can also be silently redirected into fee (deflated claims push the difference to miners) or fabricated change.

### Likelihood Explanation
`ReceivedOutput` is a serialization boundary explicitly meant to cross trust domains (it is `read`/`write`-able precisely so outputs can be relayed between components). An unprivileged party who can inject or tamper with these bytes — the same MITM/untrusted-channel posture as the reference CVE — needs no key material and no collusion; the forged data fails no signature check because none exists. The only precondition is reaching the input-provisioning path rather than the scanner-produced path.

### Recommendation
Treat `ReceivedOutput` as a claim, not a fact: before signing, re-derive the prevout `TxOut` from a trusted source (the scanner's view of the chain) keyed by `outpoint`, or require the producer to prove the UTXO (e.g., include the confirmed output in an authenticated transcript). At minimum, `SignableTransaction::new`/`multisig` should verify `prevouts[i]` against the real UTXO set and reject mismatched `value`/`script_pubkey`, since `Prevouts::All` makes those bytes consensus-critical.

### Proof of Concept
```rust
// networks/bitcoin context: attacker-controlled bytes -> trust boundary
let forged = {
    let mut b = vec![];
    // offset that maps to the real group key's script (public knowledge)
    b.extend(real_offset.to_bytes());
    // TxOut: real script_pubkey, but inflated value (e.g., real UTXO is 100_000 sats,
    // attacker claims 1_000_000_000 sats)
    b.extend(serialize(&TxOut {
        value: Amount::from_sat(1_000_000_000),
        script_pubkey: real_serai_script.clone(),
    }));
    // OutPoint of a REAL Serai-owned UTXO worth only 100_000 sats
    b.extend(serialize(&real_outpoint));
    b
};
let input = ReceivedOutput::read(&mut forged.as_slice()).unwrap(); // accepted unchecked
let tx = SignableTransaction::new(vec![input], &payments, Some(change), None, fee)
    .unwrap(); // solvency computed on forged value
// multisig() passes: script_pubkey check only binds offset->script, not value
let machine = tx.clone().multisig(&keys).unwrap();
// TransactionSignMachine::sign commits Prevouts::All([forged TxOut]) into the
// BIP-341 sighash; all signers emit shares; complete() returns a "signed" tx the
// network will reject forever -> reported spend is unspendable
```
Key lines: `ReceivedOutput::read` accepts unauthenticated bytes (`networks/bitcoin/src/wallet/mod.rs:122-133`); solvency/fee derived from claimed values (`send.rs:175`, `send.rs:228-233`); only script-vs-offset is checked (`send.rs:275-279`); forged values committed via `Prevouts::All` into every signed sighash (`send.rs:373-390`).
