### Title
Fee/vsize estimation omits the OP_RETURN `data` output, producing under-priced transactions that fail relay and lock funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The `transfer`-class bug here maps to a silent accounting mismatch: `SignableTransaction::new` computes transaction weight/vbytes — and therefore the required fee and the change amount — using only `payments`, while the actual transaction also contains an OP_RETURN output carrying up to 80 bytes of `data`. The emitted transaction is larger than estimated, so its real fee rate is lower than the caller-specified `fee_per_vbyte` and can fall below the network minimum relay fee, producing a transaction which is signed and broadcast but rejected/stuck — funds neither delivered nor recoverable as-received.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then appends an OP_RETURN output when `data` is `Some` [1](#0-0) . However, the weight and vbyte estimate is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, passing only `payments` — the OP_RETURN output is never included in the template transaction [2](#0-1) . The same omission occurs in the change path, which again passes `payments` rather than the full output set [3](#0-2) .

`calculate_weight_vbytes` derives `weight` and `vbytes` by building a real `Transaction` from the given outputs and calling `tx.weight()` [4](#0-3) . An OP_RETURN output adds roughly 89 serialized bytes (~9 base bytes + up to 80 data bytes + script length pushes), all counted at full weight — approximately 89+ vbytes omitted from the estimate when `data` is maximal.

The minimum-relay-fee check is also performed against the underestimated `vbytes` [5](#0-4) , so a transaction legitimately constructed at the minimum relay fee will actually be below the minimum once the OP_RETURN output is included. Signing then proceeds normally: `sign` computes `taproot_key_spend_signature_hash` over the real transaction including all prevouts and outputs [6](#0-5) , so a fully valid threshold signature is produced for an under-priced transaction.

### Impact Explanation
When `data` is set (the mechanism used to carry `InInstruction` payloads on Bitcoin), the signed transaction pays `needed_fee` computed on a smaller virtual size than the actual transaction. If `fee_per_vbyte` is at or near the minimum relay rate, the resulting fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`, so nodes reject it with "min relay fee not met" and it never confirms. The consumed `ReceivedOutput` inputs remain committed to a tx that cannot propagate; the multisig has already produced a signature for a transaction that is unspendable on the network, and the change/forwarded accounting baked into `needed_fee` and the change `TxOut` value is wrong by the omitted fee. More generally, even above min-relay, every OP_RETURN-carrying transaction silently pays a lower fee rate than requested — the same class of "transfer executed without checking the real result" failure as the reference report, with funds appearing sent while being effectively stuck.

### Likelihood Explanation
The trigger requires the caller to supply `data` (OP_RETURN payload) plus a `fee_per_vbyte` low enough that the ~89-vbyte underestimate pushes the real rate below relay minimum — reachable by any user whose instruction embeds data on the Bitcoin path when the scheduler uses a low fee rate. No malicious validator or broken primitive is needed; this is a deterministic arithmetic omission in fee estimation.

### Recommendation
Include the OP_RETURN output in the weight/vsize estimation — e.g., build the estimate from the fully-formed `tx_outs` (payments + data output) rather than `payments` alone, both for the base fee computation and for the change-output fee computation in `SignableTransaction::new`.

### Proof of Concept
```rust
// networks/bitcoin: construct a SignableTransaction with a large `data`
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![received_output],        // inputs
    &[(payment_script, 1000)],    // payments
    Some(change_script),          // change
    Some(data),                   // OP_RETURN output
    1,                            // fee_per_vbyte at min relay
).unwrap();
// tx.needed_fee() == fee_per_vbyte * vbytes(tx WITHOUT the ~89-byte OP_RETURN output)
// The signed tx's actual vsize is larger, so its real fee rate < 1 sat/vbyte,
// below DEFAULT_MIN_RELAY_TX_FEE — the signed transaction is rejected by relay.
```
