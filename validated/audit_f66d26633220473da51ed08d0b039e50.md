## Title
Unconstrained genesis `ChainState` in `header_chain_circuit` allows a false total-work claim to be proved - (File: circuits-lib/src/header_chain/mod.rs)

### Summary
The `binary.pil` bug is a class of "boundary value left unconstrained": at the RESET boundary of a state machine, a value (`cIn`) that should be forced to a fixed value (0) is instead left free for the prover to choose, letting them prove a false statement (`0+0==1`). The analogous boundary in Clementine's Bitcoin header-chain circuit is the genesis `ChainState` supplied via `HeaderChainPrevProofType::GenesisBlock(genesis_state)`. At this "RESET" point (start of a header chain), the circuit accepts whatever `ChainState` the prover supplies as the starting state without asserting it equals the canonical genesis state, and then chains verifiable block headers on top of it.

### Finding Description
`header_chain_circuit` reads its input and, for the genesis case, directly adopts the caller-supplied `ChainState` with no validation: [1](#0-0)

`ChainState` carries `total_work`, `best_block_hash`, `current_target_bits`, `block_height`, etc. [2](#0-1)  There is no assertion in this branch that `genesis_state == ChainState::genesis_state()` (the canonical, agreed-upon zero state) or that its hash matches a hard-coded/expected constant. The circuit simply hashes whatever `ChainState` was supplied and continues to apply subsequent (legitimately validated) block headers on top of it via `apply_block_headers`, which only checks chain continuity/PoW/difficulty relative to the attacker-chosen starting state, not the starting state itself: [3](#0-2) 

The resulting `genesis_state_hash` and `chain_state.total_work` are committed to the journal as `BlockHeaderCircuitOutput`, and this is exactly the value the bridge circuit trusts for two critical checks: comparing operator `total_work` against watchtower `max_total_work` [4](#0-3) , and binding `genesis_state_hash` into the `deposit_constant`, which is what the pre-signed N-of-N/BitVM setup ultimately commits to. Because the genesis boundary itself is unconstrained inside the guest, an attacker who can get an arbitrary `genesis_state` accepted (e.g., by controlling or corrupting the host-side genesis derivation, or by any code path that ends up invoking `header_chain_circuit` with a crafted `GenesisBlock` variant instead of the canonical one) can inflate `total_work` from a bogus starting point and pass the "operator work > watchtower work" check even without possessing the real chain's total accumulated work — the on-circuit analog of proving `0+0==1`.

The mitigating factor (why this is a "hint-class" analog rather than a proven exploit) is that off-chain, honest hosts always call `ChainState::genesis_state()` / `get_chain_state_from_height` for the true genesis, and `core/src/config/mod.rs::check_general_requirements` cross-checks the derived genesis chain state hash against a configured `genesis_chain_state_hash` [5](#0-4) . However, that check is a **host-side/off-chain configuration sanity check**, not a **zkVM circuit constraint**. The header-chain circuit itself — the piece whose Groth16 proof is actually verified inside the bridge circuit and ultimately checked on-chain via BitVM2 disprove scripts — never asserts the genesis value. This mirrors the underconstrained-`cIn` pattern precisely: the "trusted" invariant (canonical genesis) is enforced by convention/off-chain tooling rather than by the circuit's own arithmetic/logical constraints.

### Impact Explanation
If any component in the proving pipeline (the header-chain-prover service, a compromised/buggy database, or a modified guest input path) supplies a non-canonical `GenesisBlock` `ChainState` — whether through misconfiguration, a bug, or a malicious host—the header-chain circuit will still produce a *verifiably accepted* Groth16 proof with an unconstrained, attacker-influenced `total_work`/`genesis_state_hash`. Since the bridge circuit's core soundness claim ("the operator's claimed Bitcoin work exceeds all watchtower challenges") rests entirely on `hcp.chain_state.total_work` sourced from this unverified starting state, this could let a Groth16 proof falsely assert sufficient chain work, defeating the watchtower-challenge mechanism that is supposed to catch a dishonest operator (Critical: a false circuit claim proved).

### Likelihood Explanation
This requires reaching the `GenesisBlock` code path with a non-canonical `ChainState`, which in normal, correctly configured operation is prevented by convention (only `ChainState::genesis_state()`/`get_chain_state_from_height` results are ever passed in) and by the separate off-chain config check in `check_general_requirements`. There is no on-circuit enforcement, so likelihood depends on whether any unprivileged, non-operator caller can influence which `ChainState` reaches this guest input — which was not confirmed within the indexed code available (the genesis-block invocation path is only exercised by the header-chain-prover service and test code found in the index). This should be treated as a soundness gap to close defensively (add an in-circuit assertion `assert_eq!(genesis_state.to_hash(), EXPECTED_GENESIS_HASH)` or `assert_eq!(genesis_state, ChainState::genesis_state())`), rather than a confirmed unprivileged exploit given current evidence.

### Recommendation
Add an explicit in-circuit constraint in `header_chain_circuit` binding the genesis `ChainState` to the network's canonical/expected genesis hash (a compile-time or method-ID-bound constant), analogous to how `cIn` was hard-bound to `cOut * (1 - RESET')` in the PIL fix — i.e., move the genesis-hash check from `core/src/config/mod.rs` (off-chain, advisory) into `circuits-lib/src/header_chain/mod.rs` (on-circuit, enforced), for example:
```rust
HeaderChainPrevProofType::GenesisBlock(genesis_state) => {
    assert_eq!(genesis_state.to_hash(), EXPECTED_GENESIS_CHAIN_STATE_HASH, "Invalid genesis chain state");
    genesis_state_hash = genesis_state.to_hash();
    genesis_state
}
```

### Proof of Concept
Conceptual (no full exploit executed against a live node; this is a code-level soundness gap identified from the header-chain circuit source):
1. Construct a `HeaderChainCircuitInput` with `prev_proof: HeaderChainPrevProofType::GenesisBlock(ChainState { total_work: <huge value>, best_block_hash: <arbitrary>, ..ChainState::genesis_state() })` as shown in the test harness pattern [6](#0-5) .
2. Run `header_chain_circuit`/prove it — nothing in `header_chain_circuit` rejects this because the `GenesisBlock` arm performs no validation [7](#0-6) .
3. Chain a few legitimately-mined headers on top via `apply_block_headers`, which only checks relative continuity/PoW from the (poisoned) starting state [8](#0-7) .
4. Feed the resulting `BlockHeaderCircuitOutput` (with inflated `total_work`) into `bridge_circuit`, which will pass the `total_work < max_total_work` check regardless of real watchtower-reported work [4](#0-3) .

pub fn header_chain_circuit(guest: &impl ZkvmGuest) {
    // Read the input from the host
    let input: HeaderChainCircuitInput = guest.read_from_host();
    let genesis_state_hash: [u8; 32];
    let mut chain_state = match input.prev_proof {
        HeaderChainPrevProofType::GenesisBlock(genesis_state) => {
            genesis_state_hash = genesis_state.to_hash();
            genesis_state
        }
        HeaderChainPrevProofType::PrevProof(prev_proof) => {
            assert_eq!(prev_proof.method_id, input.method_id, "Method ID mismatch, the input method ID must match the previous proof's method ID to ensure the same circuit is always used. Previous proof method ID: {:?}, input method ID: {:?}", prev_proof.method_id, input.method_id);
            guest.verify(input.method_id, &prev_proof);
            genesis_state_hash = prev_proof.genesis_state_hash;
            prev_proof.chain_state
        }
    };
