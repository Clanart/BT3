### Title
Reward Front-Running in `WombatBribeManager`/`BribeRewardPool` Lets Users Time Votes Around Bribe Harvests to Steal Yield - (File: wombat/WombatBribeManager.sol, rewards/BribeRewardPool.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`WombatBribeManager.vote()`/`unvote()` immediately mutate a user's staked balance in `BribeRewardPool` via `stakeFor`/`withdrawFor`, and reward accrual in `BribeRewardPool` (inherited from `BaseRewardPoolV2`) is computed purely from the instantaneous `totalStaked()`/`balanceOf()` at the moment new rewards are injected, with no time-weighting. Because `castVotes()` — the function that harvests bribes and injects them into the reward pool via `queueNewRewards` — is permissionless and its effect is visible in the mempool, any unprivileged wallet holding locked vlMGP can call `vote()` to inflate their pool balance immediately before a pending `castVotes()` call lands, then call `unvote()`/`vote()` with a negative delta immediately after to withdraw, capturing a share of the freshly harvested bribes without having voted for any meaningful duration.

### Finding Description
`vote()` credits the caller's balance in the pool's `BribeRewardPool` synchronously and without delay: [1](#0-0) 

`castVotes()` is a public, unprivileged function that harvests bribes from Wombat and forwards the harvested tokens into the pool rewarder via `wombatStaking.vote(...)`, which ultimately calls `IBaseRewardPool(_rewarder).queueNewRewards(...)`: [2](#0-1) [3](#0-2) 

`BribeRewardPool` (a `BaseRewardPoolV2`) updates each user's stake instantly via `stakeFor`/`withdrawFor` with no lock or cooldown period between the two calls: [4](#0-3) 

Reward accrual (`_provisionReward`) increases `rewardPerTokenStored` proportionally to `totalStaked()` **at the instant new rewards arrive**, i.e. a snapshot-style, non-time-weighted distribution identical in mechanism to the off-chain "daily snapshot" flaw described in the report: [5](#0-4) 

A search of the contract for any per-user vote cooldown or minimum holding period between `vote()` and `unvote()` calls found none — only a global `lastCastTime` bookkeeping variable exists, which does not restrict individual users from voting immediately before and unvoting immediately after a `castVotes()` call. This is the on-chain equivalent of the reported bug class: instead of timing `stake()`/`cancleStake()` around an off-chain snapshot, a user times `vote()`/`unvote()` around the on-chain, permissionlessly-triggerable `castVotes()` reward-injection event.

### Impact Explanation
Any wallet already holding locked vlMGP (an ordinary, unprivileged position obtainable by anyone) can inflate its `BribeRewardPool` balance right before a bribe harvest and withdraw immediately after, extracting a disproportionate share of the harvested bribe yield that should have accrued to voters who genuinely committed their vote weight over the epoch. This dilutes and effectively steals unclaimed yield from honest, long-term voters — each successful timing round transfers real value (bribe tokens) from genuine stakers to the opportunistic actor.

### Likelihood Explanation
`castVotes()` is a permissionless, unauthenticated function whose calls are visible in the mempool before execution, making it straightforward to front-run with a `vote()` call and back-run with an `unvote()`/negative `vote()` call (or bundle both in the same block via MEV). No cooldown, lock-up, or time-weighting mechanism prevents this, so the attack is repeatable every time bribes are harvested, and it is profitable to any user already holding sufficient locked vlMGP for gas cost to be worth it.

### Recommendation
Introduce time-weighted reward accrual in `BribeRewardPool`/`BaseRewardPoolV2` (e.g., snapshotting balances at the start of each voting epoch, or requiring a minimum holding duration for a vote to be reward-eligible) so that rewards distributed via `queueNewRewards` are apportioned based on time-integrated stake rather than the instantaneous balance at the moment of injection. Alternatively, enforce a cooldown between `vote()` and `unvote()`/negative `vote()` calls that exceeds the typical interval between bribe harvest calls.

### Proof of Concept
1. Attacker holds locked vlMGP with unused voting power.
2. Attacker monitors the mempool for a pending `castVotes()` transaction (or the imminent point where enough bribes have accumulated to make harvesting worthwhile).
3. Immediately before that transaction, attacker calls `vote(_lps, _deltas)` with a large positive delta, which calls `BribeRewardPool.stakeFor(attacker, delta)` and inflates `totalSupply`/`_balances[attacker]`.
4. `castVotes()` executes, triggers `wombatStaking.vote(...)`, harvests bribes, and calls `queueNewRewards`, which raises `rewardPerTokenStored` based on the current (attacker-inflated) `totalStaked()`.
5. Immediately after, attacker calls `unvote(_lp)` (or `vote()` with a matching negative delta), which calls `withdrawFor(attacker, currentVote, true)`, claiming the freshly accrued reward share and withdrawing the vote weight — having held the position for only the span of two adjacent transactions.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
