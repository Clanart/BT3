### Title
Unrestricted URL scheme forwarded from renderer to `shell.openExternal` via `open-external` IPC handler - ([File: app/src/main-process/main.ts])

### Summary
The Sushi Trident report is fundamentally about an inconsistency between sibling code paths: several pools apply a protective invariant (fee collection to `barFeeTo`) while `IndexPool` silently skips it, letting an attacker/user bypass a safeguard the rest of the system relies on. The GitHub Desktop analog with the same shape is the `open-external` IPC handler, which — unlike other URL-consuming paths in the app (`parseAppURL`, `openRepositoryFromUrl`) that validate scheme/host/characters before acting — performs no scheme allow-listing before calling `shell.openExternal`.

### Finding Description
`ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts` receives an arbitrary string `path` from the renderer and passes it straight to `shell.openExternal(path)`. It only *logs* when the string starts with `http://`/`https://`; it does not reject or sanitize any other scheme: [1](#0-0) 

Compare this to the analogous deep-link/custom-protocol path, `parseAppURL`, which enforces a strict allow-list of hostnames (`oauth`, `openrepo`), validates the PR number format, branch name characters, and query values before any action is dispatched: [2](#0-1) 

and the `filepath` handling in `dispatcher.ts`, which explicitly guards against path traversal/absolute paths with `resolveWithin` and `isAbsolute` checks before touching the filesystem: [3](#0-2) 

The `open-external` handler has no equivalent scheme validation — it will forward `file://`, `javascript:`, vendor-registered custom URI schemes (e.g. `ms-word:`, `steam:`, `vscode:`), or crafted UNC/`\\` style paths on Windows to the OS shell without restriction. `shell.openExternal` is documented as dangerous with untrusted, non-`http(s)` input because many OS-registered protocol handlers accept command-line-like arguments, and on Windows in particular certain URL forms have historically enabled remote code execution through `openExternal` (this is Electron Security Checklist item #13, and the reason renderer code should never pass unsanitized third-party content to it).

The renderer-facing wrapper that calls into this channel does no additional filtering either: [4](#0-3) [5](#0-4) 

Any renderer-reachable value that ends up in a `LinkButton`, PR body, commit message, issue reference, or other GitHub API-sourced string rendered as a clickable link can reach `shell.openExternal` through this exact call chain: [6](#0-5) 

### Impact Explanation
This is the same "missing guard on one path while sibling paths enforce it" class as the Sushi report: `parseAppURL` and the `filepath`-in-URL handler enforce strict validation before acting on attacker-influenced input, but the general-purpose `open-external` IPC channel — reachable from any content rendered in the renderer, including text sourced from a cloned repository's PR/issue/commit bodies via the GitHub API — does not. An attacker who controls a PR title/body, issue comment, or repository content that GitHub Desktop renders as a link can supply a non-`http(s)` URI that is passed unmodified to the OS shell, potentially invoking arbitrary registered protocol handlers or (on some Electron/OS combinations) achieving code execution or unintended local file/dialog interactions outside the repository the user is working in.

### Likelihood Explanation
Likelihood depends on what upstream renderer code passes user/attacker-controlled strings into `shell.openExternal`/the `open-external` channel without its own scheme check (e.g. `LinkButton`, PR/issue link rendering). I was not able to fully audit every caller of `shell.openExternal` from the index to confirm an unsanitized attacker-controlled string reaches it end-to-end (some callers may already restrict to `https://` links themselves). This uncertainty means the exploitability is plausible but not proven from the available code alone.

### Recommendation
Add a single, shared scheme allow-list check (mirroring the discipline already used in `parseAppURL`) inside the `open-external` IPC handler (and/or centrally in `shell.openExternal`'s wrapper in `app/src/lib/app-shell.ts`), rejecting any URL whose parsed protocol is not `http:` or `https:` (with a narrow, explicit exception list if `mailto:` or similar is intentionally supported). Reject or `false`-return instead of forwarding the raw string to the OS.

### Proof of Concept
Not fully verifiable from indexed code alone — a concrete PoC requires confirming which renderer surface (PR link rendering, commit message links, etc.) passes attacker-controlled non-`http(s)` strings to `shell.openExternal`/`open-external` without prior validation. Given index-size limits on this codebase, I recommend starting a full Devin session with filesystem access to grep every `shell.openExternal` call site and its input provenance to build a concrete end-to-end PoC before treating this as confirmed.

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
