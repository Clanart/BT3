## Analysis

The seed report describes a broken invariant: a value that's supposed to be validated/declared before use, but isn't — causing the "guard" to silently fail. The closest real analog in `desktop--010` is a boundary-check flaw in the path-containment helper used to validate the `filepath` parameter of the `openRepo` deep link.

### Title
Path-containment check in `_resolveWithin` uses unanchored `startsWith`, allowing deep-link `filepath` to escape the repository root - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` (used by `resolveWithin`, exercised from the `x-github-client://openRepo` deep-link handler) validates that a resolved path is inside a repository by testing `realResolved.startsWith(realRoot)`. This is a string-prefix comparison with no trailing path-separator check, so any sibling directory whose name is prefixed by the repository's folder name (e.g. `repo` vs. `repo-secrets`) passes the "is inside repo" check even though it is a completely different directory.

### Finding Description
The deep-link parser `parseAppURL` extracts an attacker-supplied `filepath` query parameter from `openRepo` URLs and only rejects it if it is absolute: [1](#0-0) 

`Dispatcher.openRepositoryFromUrl` then only checks `isAbsolute(filepath)` before calling `resolveWithin(repository.path, filepath)` and, if it returns non-null, immediately reveals the resolved path with `shell.showItemInFolder`: [2](#0-1) 

The actual containment check lives in `_resolveWithin`: [3](#0-2) 

`resolve(normalizedRoot, normalizedRelative)` correctly collapses `..` segments arithmetically, so a relative `filepath` like `../repo-secrets/token.txt` (where the current repo's folder is `repo`) resolves to a path *outside* `repository.path`. The code then only checks `realResolved.startsWith(realRoot)` — since the string `"…/repo-secrets/token.txt"` literally starts with the substring `"…/repo"`, the check passes even though `repo-secrets` is a sibling directory, not a subdirectory of `repo`. There is no separator-boundary check (`realResolved === realRoot || realResolved.startsWith(realRoot + sep)`), so the guard does not actually enforce "at or underneath" as documented in the function's own comment.

### Impact Explanation
A malicious `openRepo` deep link (delivered via a webpage, README link, or "Open in Desktop" button that a user is lured into clicking) can point `filepath` at a relative path such as `../<repo-name-with-a-suffix>/<any-file>`. If any sibling directory on the victim's machine happens to share the repo folder name as a prefix (a common real-world occurrence — e.g. `project`, `project-backup`, `project-old`, `project2`, or cloud-sync duplicate folders like `repo (1)`), Desktop will call `shell.showItemInFolder` on a file outside the intended repository, revealing its existence/location and opening the OS file manager focused on it. This is a containment/guard bypass that lets a remote, unprivileged party (via a link the user clicks) cause Desktop to read/expose filesystem paths and file locations outside the repository root that the guard was explicitly designed to prevent.

### Likelihood Explanation
Likelihood is moderate: it requires (1) the user to click a crafted `x-github-client://openRepo/...` link, and (2) a sibling directory with a name prefixed by the target repo folder name to exist on disk. Given common naming conventions for backups/forks/duplicates, this precondition is not unusual, and no other user interaction, credentials, or local access is required beyond the initial click, which is within the accepted "link/deep link" attacker model.

### Recommendation
Fix the boundary check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a match followed by the platform path separator, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This should be applied to all three variants (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) since they share `_resolveWithin`.

### Proof of Concept
1. Victim has cloned a repository into `/Users/victim/Projects/repo` and separately keeps an unrelated folder `/Users/victim/Projects/repo-secrets/token.txt`.
2. Victim's Desktop app is registered as the handler for the `x-github-client://` protocol (as set up in `app.on('ready', …)` calling `setAsDefaultProtocolClient`) — see main-process wiring: [4](#0-3) .
3. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/victim/repo?filepath=..%2Frepo-secrets%2Ftoken.txt`
4. `parseAppURL` accepts this because `filepath` is not absolute and contains no invalid ref characters.
5. `openRepositoryFromUrl` finds/opens the existing `repo` and calls `resolveWithin('/Users/victim/Projects/repo', '../repo-secrets/token.txt')`.
6. `_resolveWithin` computes `resolved = '/Users/victim/Projects/repo-secrets/token.txt'`; `realRoot = '/Users/victim/Projects/repo'`; the check `realResolved.startsWith(realRoot)` evaluates to `true` (string prefix match), so the function returns the resolved path instead of `null`.
7. Desktop calls `shell.showItemInFolder(resolved)`, opening the OS file explorer at `/Users/victim/Projects/repo-secrets/token.txt`, disclosing a file/path entirely outside the intended repository.
