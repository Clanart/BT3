### Title
Silent git remote hijack via GitHub API `clone_url` value in `updateRemoteUrl` - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's git remote URL whenever the `clone_url` field returned by the GitHub API differs from the currently configured remote (e.g. to follow a rename/transfer). The function trusts the API-supplied `clone_url` as long as a same-protocol, loosely-parsed hostname/owner/name pattern is satisfied — it never restricts the new host to the account's configured GitHub.com/GHE endpoint. A malicious or compromised API response (attacker-controlled GitHub API object, or a MITM'd/rogue GHE/proxy response) can therefore cause Desktop to silently repoint the user's `origin` remote at an attacker-controlled host.

### Finding Description
`updateRemoteUrl` is invoked from `app-store.ts` with an `IAPIRepository` object obtained from the GitHub API. Its guard logic is: [1](#0-0) 

The three checks performed are:
1. `protocolsMatch` — only that the URL scheme (https/ssh) is unchanged.
2. `remoteUrlUnchanged` — the current remote still matches the *previously stored* `cloneURL` for this `GitHubRepository` (i.e., the user hasn't manually edited it).
3. `!urlsMatch` — the new API `clone_url` differs (by hostname/owner/name) from the current remote.

None of these checks validate that the new `clone_url`'s **hostname** belongs to the same GitHub/GHE endpoint the repository was associated with. `urlMatchesRemote`/`parseRemote` only compare structural components (hostname, owner, name) between two URLs — they never compare the resulting hostname against `gitHubRepository.endpoint` or the account's configured API host: [2](#0-1) [3](#0-2) 

`parseRemote`'s regexes accept any hostname (`https://<anything>/owner/name`, `git@<anything>:owner/name`, etc.), so an attacker-supplied `clone_url` pointing at `evil.example.com` parses successfully and is treated as a legitimate "repository moved" signal. If all three guards pass, `gitStore.setRemoteURL` is called and the remote is rewritten without any user confirmation or prompt, unlike the analogous but user-facing "upstream URL changed" dialog (`UpstreamAlreadyExists`) used elsewhere in the app: [4](#0-3) 

The test suite confirms the intended behavior — automatically updating the remote purely based on a changed `clone_url` from the API, with no host-pinning assertion: [5](#0-4) 

### Impact Explanation
If an attacker can influence the `clone_url` value returned for a repository the user is tracking (e.g., a compromised/malicious GitHub Enterprise server, a network-level MITM of API traffic, or a permissive/attacker-controlled API proxy the app has been pointed at), Desktop will silently repoint `origin` to an attacker-chosen host. Subsequent `git push`/`fetch`/`pull` operations then target that host. Because Desktop's trampoline credential helper resolves credentials by inspecting the remote's hostname (see `getEndpointKind` in `trampoline-credential-helper.ts`), pushing/fetching against the new host can result in the user's stored credentials being offered to, or requested by, a non-GitHub endpoint, and any commits the user believes they're syncing to their real repository are instead silently sent to (or fetched from) the attacker's host. This is silent corruption of what the user pushes/fetches, with a path to credential exposure.

### Likelihood Explanation
The precondition is control over an `IAPIRepository`/`IAPIFullRepository` object returned to Desktop's API client (a MITM of the API endpoint, or a malicious/compromised GHE instance the user has added). Desktop makes many background/foreground API calls that surface `IAPIRepository`-shaped data (this specific path is exercised whenever the repository's cached GitHub info is refreshed with a `clone_url` differing from the stored one). Given the app's own comments ("Verify that protocol hasn't changed... we don't want to alter the protocol… just to be safe") show the authors were already reasoning about safety here but explicitly did not add a hostname/endpoint pin, this is a plausible oversight rather than a deliberately defended-against threat model, making it moderately likely to be reachable in the GHE / compromised-network scenario.

### Recommendation
In `updateRemoteUrl`, additionally require that the new `clone_url`'s hostname matches `gitHubRepository.endpoint`'s host (i.e., pin updates to the same GitHub.com/GHE instance the repository is already associated with), and/or surface a confirmation dialog to the user before silently changing `origin`'s URL, mirroring the existing `UpstreamAlreadyExists` UX pattern used for upstream remote changes.

### Proof of Concept
1. User has a repository tracked on GHE endpoint `https://ghe.example.com`, with `origin` pointing at `https://ghe.example.com/org/repo.git`.
2. Attacker compromises the GHE server (or performs a MITM on the API call) and returns an `IAPIRepository` object whose `clone_url` is `https://attacker-controlled.example.com/org/repo.git` (or a same-hostname-with-different-owner/name value crafted to still parse via `parseRemote`).
3. On the next refresh where `updateRemoteUrl` is invoked with this API object, `protocolsMatch` is true (both https), `remoteUrlUnchanged` is true (user hasn't manually edited `origin`), and `urlsMatch` is false (URLs differ) — all guard conditions pass.
4. `gitStore.setRemoteURL('origin', 'https://attacker-controlled.example.com/org/repo.git')` executes silently; no dialog is shown to the user, unlike `UpstreamAlreadyExists`.
5. On the user's next `git push`, Desktop pushes to `attacker-controlled.example.com`, and the trampoline credential helper may present or request credentials for that host.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
