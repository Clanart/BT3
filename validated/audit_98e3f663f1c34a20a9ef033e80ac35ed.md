### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Vault CVE class is a scope/privilege mismatch: a check granting a narrow capability (`read` on a glob path) silently conferred a broader one (issuing credentials). In Serai, `Scanner` is the component that decides what the wallet "may" treat as received, spendable funds. `Scanner::scan_transaction` grants that capability to any output whose `script_pubkey` appears in `self.scripts` — and `scan_block` applies it to every transaction in a block, including `txdata[0]`, the coinbase. A coinbase output matched this way is returned as a `ReceivedOutput` indistinguishable from a mature payment, yet it is consensus-unspendable for 100 blocks. The scanner's "match" confers a privilege (spendable funds) the chain does not actually grant.

### Finding Description
`Scanner::scan_transaction` iterates `tx.output`, looks up `output.script_pubkey` in `self.scripts`, and on a hit pushes a `ReceivedOutput { offset, output, outpoint }` [1](#0-0) . `scan_block` extends this to `block.txdata[0]` — the coinbase — with no maturity check [2](#0-1) . `ReceivedOutput` carries only `offset`, `output`, `outpoint`; nothing records that the source transaction is a coinbase or that the outpoint is immature [3](#0-2) . Downstream, `SignableTransaction::new` accepts these outputs as ordinary inputs (it validates amounts, dust, and fees, but has no maturity concept, per `networks/bitcoin/tests/wallet.rs` exercising `send_and_get_output` which explicitly mines 100 extra blocks to work around this) [4](#0-3) . The doc comment acknowledges the gap — "If received outputs must be immediately spendable, a post-processing pass is needed" — but the API provides no flag on `ReceivedOutput` and no enforcement; a caller that doesn't know to filter gets silently wrong data.

### Impact Explanation
Any miner (unprivileged, public inputs only: a Bitcoin transaction they send) can pay the multisig's P2TR script — or any registered offset script — in a coinbase. The wallet/scanner then reports those funds as received and spendable. If they are fed to `SignableTransaction` as inputs, the resulting funding/spend transaction commits to an immature coinbase outpoint and is rejected by consensus; worse, the spent "balance" was counted as real. This matches the accepted impact "funds reported received that are not spendable". Severity: **Medium** — attacker-influenceable incorrect fund reporting / guaranteed-invalid transaction construction, not key or signature compromise.

### Likelihood Explanation
The trigger requires a miner to include a payment to a scanned script in a coinbase — cheap and fully within an unprivileged party's reach, though it costs the miner real subsidy/fees. Exploitation additionally requires a downstream consumer that calls `scan_block` and does not perform the undocumented-in-type "post-processing pass". The in-repo test itself demonstrates the hazard: `send_and_get_output` must mine 100 blocks before scanning because otherwise the scanned output would be immature [4](#0-3) . Because `ReceivedOutput` exposes no maturity marker, a correct-by-type consumer cannot distinguish the case without re-fetching the transaction — the incorrect privilege assignment is baked into the returned data.

### Recommendation
In `scan_block` (`networks/bitcoin/src/wallet/mod.rs`), skip `block.txdata[0]` (or check `tx.is_coinbase()`) so coinbase outputs are never reported, and/or extend `ReceivedOutput` with a `maturity`/`coinbase` flag so callers can enforce spendability. Prefer making the safe behavior the default (`scan_block` skips coinbase) and offering an explicit `scan_block_including_coinbase` for callers that want raw data.

### Proof of Concept
1. `let scanner = Scanner::new(key).unwrap();`
2. Miner builds a block whose coinbase pays `p2tr_script_buf(key).unwrap()` (or `key + G*offset` for any registered offset).
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` for `(coinbase_txid, vout)` with a valid `offset` — indistinguishable from a mature UTXO, per the assertion in `test_scanner`-adjacent code that `scan_block` equals `scan_transaction` on `txdata[0]` [5](#0-4) .
4. `SignableTransaction::new(vec![that_output], &payments, ...)` succeeds and produces a transaction referencing an immature coinbase input; `send_raw_transaction` rejects it (bad-txns-inputs-spent / coinbase maturity), and any accounting that credited the scanned value is wrong for 100 blocks.

Caveat: the doc comment on `scan_block` warns that a post-processing pass is needed, which mitigates this to Medium and may lead a maintainer to classify it as documented behavior; however the returned `ReceivedOutput` type carries no maturity information, so the privilege mismatch (reporting unspendable funds as spendable) is encoded in the API itself rather than just the documentation.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```

```rust
    let mut res = Vec::new();

    }
    res
  }
```
