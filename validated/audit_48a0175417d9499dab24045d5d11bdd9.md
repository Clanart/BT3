### Title
DataLayer mirror-coin URLs are auto-fetched by peers without SSRF host validation, allowing an unprivileged spend to trigger internal-network requests - (File: chia/data_layer/download_data.py)

### Summary
Any wallet holder can create a "mirror" coin for **any** DataLayer store id (not necessarily their own) by calling `create_new_mirror()`/`dl_new_mirror`, embedding arbitrary attacker-controlled URL strings as coin memos with no ownership check on the target `launcher_id`. Every DataLayer node that subscribes to (or owns/tracks) that store id will, on its periodic management cycle, pull these on-chain mirror URLs via `update_subscriptions_from_wallet()` and then issue outbound HTTP requests to them via `http_download()` with no validation of scheme, host, or destination address (no blocking of loopback, link-local/metadata, or private-network addresses).

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a spend that creates a coin with the mirror puzzle and encodes `launcher_id` plus arbitrary `urls` as memos, with no check that the caller owns or controls that `launcher_id`: [1](#0-0) 

This is directly reachable from the wallet RPC `dl_new_mirror` endpoint, requiring only a standard signed spend and a small XCH amount/fee — no elevated privilege, no relationship to the target store: [4](#0-3) 

When the mirror coin confirms, any peer's `DataLayerWallet.coin_added()` records the mirror (launcher_id, urls) purely from parsing the coin spend, again without checking whether the local node owns that store: [5](#0-4) 

The `DataLayer` service's background loop (`periodically_manage_data()`) iterates over subscribed AND owned/tracked stores and, for each, calls `update_subscription()` → `update_subscriptions_from_wallet()`, which pulls all current mirror URLs from wallet RPC and inserts them straight into the local subscription table: [2](#0-1) [6](#0-5) 

`fetch_and_validate()` then randomly selects one of these server URLs and downloads a delta file from it via `http_download()`: [7](#0-6) 

`http_download()` performs an unrestricted `aiohttp` GET against `server_info.url` with no allow-list, no DNS/IP validation, and no restriction on private/loopback/link-local ranges: [3](#0-2) 

This mirrors the MobSF SSRF pattern (CVE-2024-31215): an unprivileged, attacker-supplied value (there: a Firebase DB URL from an uploaded app; here: a mirror URL memo from a submitted spend) is later used server-side to make a network connection without validating the destination, allowing requests into internal-only infrastructure (e.g., cloud metadata endpoints, internal admin services, or other loopback-bound services on the node's host).

### Impact Explanation
Any user who can broadcast a standard spend bundle (minimal XCH cost) can force every full-node/DataLayer operator who tracks or subscribes to the targeted store — including their own owned stores automatically pseudo-subscribed — to make outbound HTTP requests to attacker-chosen hosts/ports on a recurring basis (every `manage_data_interval`, default 60s). This can be used to probe or interact with internal-only services (metadata endpoints, internal RPC/admin panels, or arbitrary local ports) reachable from the DataLayer host, and can be weaponized for internal network reconnaissance, port scanning, or triggering side effects on unauthenticated internal HTTP services. It also enables persistent unwanted outbound traffic/DoS against arbitrary third-party hosts using victim infrastructure as an amplifier.

### Likelihood Explanation
High likelihood: creating a mirror coin only requires a normal wallet spend with `dl_new_mirror`/`create_new_mirror`, there is no validation tying the `launcher_id` to the sender's own store, and the background sync loop processes mirror URLs for owned/tracked/subscribed stores automatically and periodically without operator interaction, making exploitation straightforward and repeatable by any wallet holder.

### Recommendation
- Validate mirror URLs before storing/using them: enforce an allow-list of schemes (http/https), reject requests to loopback, link-local, private, and multicast address ranges, and resolve/verify the destination IP at request time (not just parse the string) to prevent DNS-rebinding.
- Consider requiring that `create_new_mirror`/`dl_new_mirror` only tag mirrors for `launcher_id`s the wallet already owns/tracks, or otherwise gate which mirrors are auto-merged into `update_subscriptions_from_wallet()`.
- Add an operator-configurable mirror URL policy (e.g., require manual approval or an explicit URL allow-list) before a discovered on-chain mirror URL is used for outbound `http_download()` requests.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` (via `chia data add_mirror` or the wallet RPC) targeting a victim's DataLayer `store_id` (any known/public launcher id) with `urls=["http://169.254.169.254/latest/meta-data/iam/security-credentials/","http://127.0.0.1:<internal-port>/admin"]` and a minimal `amount`/`fee`.
2. Once the transaction confirms, any node (including the victim's) that owns/tracks/subscribes to that `store_id` picks up the mirror via `DataLayerWallet.coin_added()` → `dl_store.add_mirror()`.
3. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` merges the attacker URLs into that node's local subscription table, and `fetch_and_validate()` → `http_download()` issues a GET to the attacker-chosen internal URL/port from the victim's server, with no destination validation.
