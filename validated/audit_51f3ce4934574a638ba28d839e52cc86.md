### Title
Attacker-controlled `n`/`t` in serialized `ThresholdKeys` causes quadratic-to-quartic CPU exhaustion before parameter validation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t`, `n`, and `i` fields, deserializes `n` verification shares, and then calls `ThresholdKeys::new`. `ThresholdKeys::new` derives the group key by evaluating the interpolation factor for each participant `1..=t`; with `Interpolation::Lagrange`, every evaluation iterates over all `t` included participants. This makes group-key reconstruction approximately O(t²) scalar operations, while the input needed to trigger it is only O(n) bytes. Since `t` and `n` are unprivileged serialized fields, a crafted key blob can force billions of field operations from roughly a few megabytes of input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the input before checking them with `ThresholdParams::new` [1](#0-0) . It then reads `n` public verification shares from the same untrusted stream [2](#0-1) .

`ThresholdKeys::new` constructs `included = 1..=t` and sums `verification_shares[i] * interpolation_factor(i, included)` for every threshold participant [3](#0-2) . Under `Interpolation::Lagrange`, `interpolation_factor` itself loops over every included participant and performs field multiplications plus an inversion [4](#0-3) .

With serialized `t = n = 65535`, the input needs to contain only 65,535 point encodings, but construction performs 65,535 outer iterations, each scanning up to 65,535 participants. That is about 4.29 billion participant-factor steps before object construction completes. The parameter validity checks are only reached after this expensive work, and even a fully valid `t = n` parameter set can trigger the behavior.

### Impact Explanation
An unprivileged party able to submit serialized `ThresholdKeys` bytes to `ThresholdKeys::read` can cause disproportionate CPU consumption. The crafted object is compact relative to the resulting computation and can monopolize a worker, verification, or signing-related thread for an extended period. Repeated submissions can deny service to legitimate key loading, recovery, signing, or protocol-processing operations.

This is analogous to the reported vulnerability class: a relatively small crafted input causes processing work far beyond what its size implies.

### Likelihood Explanation
The attacker only needs to reach a code path that deserializes `ThresholdKeys` or otherwise invokes `ThresholdKeys::new` with attacker-controlled serialized parameters. Both `n` and `t` are serialized as `u16`, allowing the maximum size of 65,535 participants. Public verification shares may repeat the same valid group generator encoding because shares are keyed by participant index, not by distinct point values. No secret key material, malformed cryptography, malicious validator assumption, or internal access is required.

The flaw is deterministic once the parsed parameters use Lagrange interpolation and a large `t`; no race or special environmental condition is needed.

### Recommendation
Bound `t` and `n` to a protocol-supported maximum before allocating vectors or parsing participant-dependent data. Validate `ThresholdParams` immediately after reading `t`, `n`, and `i`, before reading `n` scalars or verification shares. In `ThresholdKeys::new`, avoid the O(t²) participant-factor calculation—for example, batch-compute Lagrange coefficients with an O(t) prefix/suffix algorithm or enforce a much smaller hard participant limit. Also consider explicit serialized-key size limits at external deserialization boundaries.

### Proof of Concept
The following Rust-shaped payload demonstrates the amplification. It serializes a syntactically valid `ThresholdKeys` with `t = n = u16::MAX` and Lagrange interpolation, using the group generator as every verification share:

```rust
use std::io::Cursor;

use ciphersuite::{Ciphersuite, group::GroupEncoding};
use frost::{Participant, ThresholdKeys, curve::Secp256k1};

fn malicious_threshold_keys() -> Vec<u8> {
    let n = u16::MAX;
    let mut bytes = Vec::new();

    // C::ID length and ID
    bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
    bytes.extend(Secp256k1::ID);

    // t, n, i = 65535, 65535, 1
    bytes.extend(n.to_le_bytes());
    bytes.extend(n.to_le_bytes());
    bytes.extend(Participant::new(1).unwrap().to_bytes());

    // Interpolation::Lagrange
    bytes.push(1);

    // secret_share: scalar one
    bytes.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());

    // n verification shares. Repeated generator points are sufficient because the
    // HashMap is keyed by Participant index, not by distinct points.
    let generator = Secp256k1::generator().to_bytes();
    for _ in 0..n {
        bytes.extend(generator.as_ref());
    }

    bytes
}

fn trigger() {
    let bytes = malicious_threshold_keys();
    let mut cursor = Cursor::new(bytes);

    // Triggers approximately t*t participant-factor work inside ThresholdKeys::new.
    let _ = ThresholdKeys::<Secp256k1>::read(&mut cursor);
}
```

The payload contains only one byte for the interpolation variant plus 65,535 compressed verification-share encodings, while `ThresholdKeys::new` performs 65,535 calls to `interpolation_factor`, each iterating over up to 65,535 participants.
