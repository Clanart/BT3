### Title
Diff-parser trusts unvalidated hunk-header line counts, causing hunk-expansion to pull mismatched file content into commits - (File: `app/src/lib/diff-parser.ts`, `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
GitHub Desktop's unified-diff parser has the same class of bug as the RLP report: a "declared length" field (the `l,s` counts in a `@@ -l,s +l,s @@` hunk header) is parsed and stored, but the parser never validates it against the number of lines it actually decodes for that hunk. A second, independent piece of code (the hunk-expansion feature) later trusts the declared, unverified count to compute offsets into the real file content. When the two values diverge, the offset math is wrong and the diff view/patch generator can silently splice in the wrong lines of the working file.

### Finding Description
`DiffParser.parseHunkHeader` extracts `oldLineCount`/`newLineCount` straight from the regex match on the `@@ ... @@` line and stores them in `DiffHunkHeader` with no further checks: [1](#0-0) 

`parseHunk` then independently determines how many lines actually belong to the hunk by looping until a line no longer starts with one of the diff prefix characters (`+`, `-`, ` `, `\`) — it never compares the number of lines consumed against `header.oldLineCount`/`header.newLineCount`: [2](#0-1) [3](#0-2) 

This is structurally identical to the RLP bug: one code path ("header declares the length") and a second, independent code path ("actual content is decoded by scanning") disagree, and nothing reconciles them.

The unvalidated `oldLineCount`/`newLineCount` are later trusted as ground truth by the hunk-expansion feature (used when a user clicks "Expand" in the diff view to reveal more context around a hunk before staging/committing). The expansion math computes the boundary of the current hunk purely from the header counts and uses it to slice the *actual on-disk file* content: [4](#0-3) [5](#0-4) 

and the new line numbers assigned to the injected context lines are also derived from the same untrusted `oldLineCount`/`newLineCount`: [6](#0-5) 

If the declared count in the hunk header does not match the number of lines the parser actually consumed for that hunk (e.g. header says `+10,3` but only 2 `+`/context/`-` lines follow before the next hunk or EOF), `parseHunk` will still build a `DiffHunk` with the wrong `header.newLineCount`/`oldLineCount` relative to what it actually parsed. Any later boundary computation that trusts these numbers — expansion offsets today, and potentially any future consumer of `DiffHunkHeader` — computes an incorrect position in the real file. The resulting "expanded" context lines are of type `Context`, which `formatPatch`/`formatPatchToDiscardChanges` always includes verbatim in the outgoing patch that is fed to `git apply --cached` for partial commits: [7](#0-6) 

Because `formatPatch` recomputes `oldCount`/`newCount` by counting the (already potentially mis-offset) lines rather than re-deriving them from the real file, an off-by-N header/content mismatch introduced during parsing/expansion is never re-detected before the patch is written and applied to the index.

### Impact Explanation
A malicious or compromised git remote/proxy (or a crafted repository the user opens) that returns diff output where a hunk header's declared `l,s` counts do not match the number of lines actually present for that hunk can cause GitHub Desktop's diff renderer to display, and its patch generator to stage/commit, content taken from the wrong offset in the working file when the user uses the "expand hunk" UI before committing. This falls squarely under "silent corruption of what the user commits or pushes" — the user believes they are reviewing and staging one set of lines, but the tool's internal line-number bookkeeping has drifted due to the unchecked header/body mismatch.

### Likelihood Explanation
Exploitability requires an attacker to control the diff text Desktop parses (e.g., via `git diff`/`git log --patch` output against attacker-influenced repository content, a crafted merge/rebase conflict, or a manipulated proxy response), and it also requires the user to interact with the hunk-expansion feature on the affected hunk before committing — a common workflow but not automatic. No local access, admin rights, or pre-existing malware is required, matching the valid-impact criteria; however, the attacker still needs to engineer a diff whose textual hunk header disagrees with its literal body content, which git itself is not designed to emit under normal operation (this would typically require an actively malicious diff source rather than merely unusual repository content). This nuance means real-world reachability, while plausible, is not fully confirmed from the code alone.

### Recommendation
In `DiffParser.parseHunk` (`app/src/lib/diff-parser.ts`), after the line-scanning loop completes, validate that the number of old/new lines actually consumed matches `header.oldLineCount`/`header.newLineCount` and throw a parse error (treat the diff as malformed) on mismatch, mirroring how the RLP report recommends reconciling declared length against actual decoded length. Additionally, `expandTextDiffHunk` in `app/src/ui/diff/text-diff-expansion.ts` should not blindly trust `hunk.header.oldLineCount`/`newLineCount` for offset math without this upstream guarantee; consider deriving hunk boundaries from the actually parsed line list rather than the header fields, or bounds-check the computed slice against the source file's real line count/hunk boundaries before use.

### Proof of Concept
1. Construct (or intercept via a malicious remote/proxy) a unified diff whose hunk header overstates its span, e.g.:
```
--- a/file.md
+++ b/file.md
@@ -1,5 +1,5 @@
 line1
+line2
 line3
```
Here the header claims 5/5 lines but only 3 are actually present before the next hunk marker or EOF.
2. Feed this into `DiffParser.parse` (as happens for any `git diff`/`git log` output processed by `diffFromRawDiffOutput`, `app/src/lib/git/diff.ts:788-796`). `parseHunk` will build a `DiffHunk` whose `lines.length` (3 body lines + header) does not match `header.newLineCount`/`oldLineCount` (5), and no error is raised.
3. In the diff view, trigger hunk expansion on this hunk (`expandTextDiffHunk`). The `from`/`to` slice bounds computed at `app/src/ui/diff/text-diff-expansion.ts:209-214` use the inflated `newLineCount`, pulling extra/incorrect lines from `newContentLines` (the real, current file content) as injected `Context` lines with recalculated (wrong) old/new line numbers.
4. Stage/commit with the resulting selection; `formatPatch` (`app/src/lib/patch-formatter.ts:151-218`) writes these mis-offset context lines verbatim into the patch applied via `git apply --cached`, so the committed content or index no longer accurately reflects what the user believes they reviewed and selected in the UI.
