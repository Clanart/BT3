### Title
Unvalidated UTF-8 decoding of attacker-controlled NFT metadata URIs causes wallet crash - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
`get_nft_info_from_puzzle()` decodes NFT `data_uris`, `meta_uris`, and `license_uris` atoms straight from an NFT's on-chain curried metadata using `str(uri, "utf-8")` with no exception handling, unlike other atom-decoding call sites in the codebase (e.g. the CAT memo decode in `chia/_tests/util/run_block.py`) that explicitly wrap `.decode("utf-8", errors="strict")` in a `try/except UnicodeError`. Because NFT metadata (including the URI lists) is attacker-controlled — any party can mint or transfer an NFT with an arbitrary curried metadata program — a crafted non-UTF8 byte string in these fields raises an unhandled `UnicodeDecodeError` wherever `get_nft_info_from_puzzle` is invoked.

### Finding Description
`UncurriedNFT.uncurry()` extracts `data_uris`, `meta_uris`, and `license_uris` directly as CLVM `Program` atoms from the curried NFT puzzle without validating their byte content in any way. [1](#0-0) 

`get_nft_info_from_puzzle()` then iterates these atoms and blindly decodes them as UTF-8: [2](#0-1) 

There is no `try/except` around these three `str(uri, "utf-8")` calls. This is the same bug class as the Mattermost advisory: attacker-controlled data whose type/encoding is not validated before being consumed by client-side logic, causing a crash. Notably, the codebase already recognizes this exact failure mode elsewhere and defends against it — the CAT memo-decode path explicitly catches `UnicodeError` and falls back to an empty string rather than propagating the exception: [3](#0-2) 

But the NFT URI-decoding path in `nft_puzzle_utils.py` lacks this same protection, so any NFT whose puzzle contains a non-UTF8-decodable byte sequence in the `u` (data_uris), `mu` (meta_uris), or `lu` (license_uris) metadata keys will throw when a wallet tries to build an `NFTInfo` for it.

### Impact Explanation
`get_nft_info_from_puzzle()` is called from the wallet RPC layer (`wallet_rpc_api.py`) whenever a caller requests NFT info/listing, and from `wallet_state_manager.py` during NFT search/lookup flows (`manual_nft_search`) that construct `NFTInfo` from a freshly uncurried puzzle fetched from a peer. An unprivileged party can send (transfer) or mint an NFT to a victim wallet with a metadata program containing invalid UTF-8 bytes in a URI field; the recipient's wallet then throws an unhandled `UnicodeDecodeError` the moment it tries to display or process that NFT's info (e.g. via `list_nfts`/`get_nft_info` RPCs or internal NFT discovery), halting that operation. This is a denial-of-service against the victim's wallet NFT-handling path, not a fund-loss or consensus issue.

### Likelihood Explanation
Likelihood is high for triggering the crash: constructing an NFT with non-UTF8 bytes in the metadata URI fields requires no special privileges — any wallet user can mint an NFT with arbitrary CLVM metadata, or send/gift one to another user's wallet. The victim only needs to have that NFT coin appear as part of their tracked NFTs (via receipt, offer, or sync) and then have any code path call `get_nft_info_from_puzzle`.

### Recommendation
Wrap the URI-decoding loops in `get_nft_info_from_puzzle()` in `try/except UnicodeDecodeError` (mirroring the pattern already used for CAT memo decoding in `run_block.py`), falling back to a safe representation (e.g., hex string or empty string) instead of letting the exception propagate, so malformed/attacker-crafted metadata cannot crash wallet NFT processing.

### Proof of Concept
1. Mint (or take an offer for) an NFT whose curried metadata program includes a key `b"u"` (or `b"mu"`/`b"lu"`) mapped to a byte string that is not valid UTF-8, e.g. `b"\xff\xfe"`.
2. Have a victim wallet receive/track this NFT coin (standard NFT transfer/offer flow).
3. Trigger any code path that calls `get_nft_info_from_puzzle` for that coin (e.g. `list_nfts` RPC, `manual_nft_search`, or internal wallet NFT info construction).
4. Observe `str(uri, "utf-8")` raise `UnicodeDecodeError`, uncaught, at: [4](#0-3) 
causing the request/operation to fail/crash instead of gracefully handling the malformed field.

**Note on verification limits:** I was unable to fully trace, within the remaining tool budget, every concrete call site in `wallet_rpc_api.py` that reaches `get_nft_info_from_puzzle` from an unauthenticated/unprivileged RPC context versus only privileged local calls — this should be confirmed by inspecting `chia/wallet/wallet_rpc_api.py` directly for the exact RPC endpoints (`list_nfts`, `get_nft_info`, etc.) and their authorization requirements before treating this as fully validated for production triage.
