## Analysis

The external report's core pattern: a user submits an amount computed to satisfy a requirement, the contract internally deducts/consumes a fee, and the leftover accounting is not properly closed out, so committed user funds are effectively lost even though the user provided the correct amount up front.

The closest verified local analog is in the Tron variant of the Intent Gateway's order-placement flow.

### Title
`placeOrder` in the Tron `IntentGatewayV2` permanently locks native-token change left over after the `order.fees` swap - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
When a user pays `order.fees` with native token, `placeOrder()` swaps the *entire remaining* `msgValue` through `swapETHForExactTokens` for an *exact* amount of fee token, and never captures or refunds the ETH that Uniswap's router sends back as change. The main EVM implementation of the same function explicitly tracks and refunds this leftover; the Tron contract does not.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol` the fee-escrow branch captures the router's return value and decrements `msgValue` by the amount actually spent, and the function ends with an explicit refund of any leftover `msgValue` to the caller: [1](#0-0) 

The Tron contract's `placeOrder()` performs the same `swapETHForExactTokens{value: msgValue}(order.fees, ...)` call but discards the return value, never adjusts `msgValue`, and — critically — has no post-fee "refund unspent native tokens" step at all before emitting `OrderPlaced` and returning: [2](#0-1) 

`swapETHForExactTokens` only spends as much of the supplied `value` as needed to buy the exact `order.fees` output and refunds the rest back to the caller (the gateway contract itself). Because the Tron contract neither tracks that refund nor forwards it to the user, the refunded ETH lands on the gateway's own balance and is never credited to any escrow slot or returned — it is permanently stranded in the contract, unreachable by the user who paid it and by any of the contract's normal accounting paths (`_orders[commitment][...]`, `TRANSACTION_FEES`, or a native-token refund).

### Impact Explanation
This is directly reachable by any unprivileged user calling the public `placeOrder()` entrypoint whenever they pay `order.fees` in native token — which is the documented, SDK-supported flow (the SDK's `quoteOrderFees`/`AWAITING_PLACE_ORDER` intentionally adds a buffer, e.g. a documented 2% margin on `nativeValue`, precisely because the exact fee-token cost cannot be predicted on-chain). Every such placement leaves the buffer amount permanently locked in the contract instead of being refunded, resulting in real, silent fund loss for ordinary users — the same "computed correctly but still comes up short/lost due to fee mechanics" pattern as the source report, just manifesting as a stuck refund instead of a liquidatable position.

### Likelihood Explanation
High: this triggers on essentially every `placeOrder()` call on the Tron deployment that pays the solver fee in native token with any overestimate of the required amount (which is the normal, recommended usage pattern), with no attacker action or malicious peer required.

### Recommendation
Mirror the EVM implementation: capture the `amounts` return value from `swapETHForExactTokens`, decrement `msgValue` by the amount actually spent, and add the same "refund any unspent native tokens to the user" step at the end of `placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` that exists in `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. On the Tron-deployed `IntentGatewayV2`, call `placeOrder(order, graffiti)` with `order.fees > 0` and `msg.value` set to (native input amounts) + (a native amount larger than what the Uniswap V2 router actually needs to buy `order.fees` worth of fee token — e.g. the SDK's documented buffered `nativeValue`).
2. `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` executes, spending less than `msgValue` and refunding the difference back to `address(this)` (the gateway).
3. The function proceeds straight to `_orders[commitment][TRANSACTION_FEES] = order.fees;` and `emit OrderPlaced(...)` — there is no code path that forwards the refunded ETH back to `msg.sender` or credits it to escrow.
4. The refunded ETH remains on the gateway's balance indefinitely, with no storage reference tying it back to the user who overpaid — a permanent, unrecoverable loss for that user.
