### Title
Empty statement set makes `SchnorrAggregate::verify` / `DLEqProof::verify` accept trivially forged proofs - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The referenced bug class is a caller-controlled dynamic array which may be empty, allowing a required verification/update step to be skipped entirely while the surrounding code still returns success. The same shape exists in Serai's verification APIs: `SchnorrAggregate::verify` and `DLEqProof::verify`/`MultiDLEqProof::verify` accept attacker-influenced statement lists (`keys_and_challenges`, `generators`/`points`) and attacker-controlled proof bytes (`SchnorrAggregate::read`, `DLEqProof::read`). When the statement list is empty — matching an empty `Rs` vector supplied via `SchnorrAggregate::read` — verification reduces to checking `0 * G == identity` and returns `true`, i.e., a forged aggregate signature verifies.

### Finding Description
In `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-146`), the only length check is `self.Rs.len() != keys_and_challenges.len()`. `Rs` is fully attacker-controlled via `SchnorrAggregate::read` (`aggregate.rs:77-88`), which accepts a length prefix of `0`. If `keys_and_challenges` is empty (e.g., the verifier's key set is derived from attacker-supplied or filtered data that ended up empty), the loop pushes no pairs, leaving only `(-self.s, C::generator())`. An attacker sets `s = 0`, and `multiexp_vartime` over `[(-0, G)]` is the identity, so `verify` returns `true` — a forged aggregate signature is accepted without satisfying any per-key statement.

The same vacuous-success pattern exists in `DLEqProof::verify` (`crypto/dleq/src/lib.rs:160-180`): when `generators`/`points` are empty, no statements are transcripted, and the attacker only needs `c` equal to the challenge of the bare `domain_separate(b"dleq")` transcript — fully computable offline — with any `s`. `DLEqProof::read` (`lib.rs:191-193`) places both scalars under attacker control. `MultiDLEqProof::verify` (`lib.rs:264-294`) likewise accepts empty inner `generators[i]`/`points[i]` series (only outer lengths are checked), leaving `s[i]` unconstrained for that index. `BatchVerifier::verify` (`crypto/multiexp/src/batch.rs:93-95`) returns `true` on an empty batch by design, and callers such as PedPoP's `calculate_share` rely on upstream map validation rather than the verifier itself.

### Impact Explanation
Any code path that feeds untrusted bytes to `SchnorrAggregate::read` / `DLEqProof::read` and then calls `verify` with a statement list that can be empty (or empty per-index) accepts a forged proof/signature. In the FROST/PedPoP flows this is currently gated by `validate_map`, but the verify APIs themselves do not enforce non-emptiness, so any consumer that derives `keys_and_challenges`/`generators` from attacker-influenced data is exposed to trivial forgery.

### Likelihood Explanation
Reachable by an unprivileged party wherever serialized aggregate signatures or DLEq proofs are accepted (the APIs are public and take `&mut impl Read`). Exploitation requires the verifier's statement list to be empty for the checked item — plausible when lists are built by filtering attacker-supplied inputs — which lowers the likelihood relative to a direct forgery. Medium.

### Recommendation
Reject empty statement sets in `SchnorrAggregate::verify` (`if self.Rs.is_empty() { return false }`), in `DLEqProof::verify`/`MultiDLEqProof::verify` (error when `generators.is_empty()` or any inner series is empty), matching the precedent of `SchnorrAggregator::complete` which already returns `None` when nothing was aggregated (`aggregate.rs:175-178`).

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }

  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[Vec<G>],
    points: &[Vec<G>],
  ) -> Result<(), DLEqError> {
    if points.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }
    if self.s.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"multi_dleq");
    for (i, (generators, points)) in generators.iter().zip(points).enumerate() {
      if points.len() != generators.len() {
        Err(DLEqError::InvalidProof)?;
      }

      transcript.append_message(b"discrete_logarithm", i.to_le_bytes());
      for (generator, point) in generators.iter().zip(points) {
        DLEqProof::verify_statement(transcript, *generator, *point, self.c, self.s[i]);
      }
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
  }
