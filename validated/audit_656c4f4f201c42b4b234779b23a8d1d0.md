## Title
Unvalidated URI scheme reaches `shell.openExternal` via `LinkButton`/GitHub API `html_url` fields, bypassing the app's own `https?:`-only guard - ([File: app/src/ui/lib/link-button.tsx])

## Summary
The external report describes an "arbitrary external call" bug class: a struct field (`executor`) supplied by an untrusted party is passed unchecked into a dangerous external call. The closest reachable analog in GitHub Desktop is `LinkButton`, which invokes `shell.openExternal(uri)` on click with no scheme validation, and is fed `html_url`/API-derived strings (e.g. `comment.html_url` from a GitHub/GHE PR comment) that are not filtered.

## Finding Description
Desktop deliberately restricts markdown-rendered links to `http(s)` before invoking `openExternal`: [1](#0-0) 

This is the app's documented safety invariant ("attempts to parse the link href as a url and verifies it to be https"): [2](#0-1) 

However, `LinkButton` — a separate, widely-reused component — performs **no such check**. Its click handler calls `shell.openExternal(uri)` unconditionally for whatever string is passed as `uri`: [3](#0-2) 

`LinkButton` is used with server-supplied data, most notably `comment.html_url`, taken directly from the GitHub/GHE API response for a PR review comment, with no scheme/URL validation applied before it reaches the component: [4](#0-3) 

Finally, `shell.openExternal` (both the renderer-side wrapper and the main-process IPC handler) does not enforce a scheme allow-list either — it only *logs* when the value looks like http/https, but takes no action to reject other schemes: [5](#0-4) 

The broken invariant: Desktop assumes all externally-clickable content is filtered to `https?:` before reaching `openExternal` (as enforced in `sandboxed-markdown.tsx`), but `LinkButton` — used elsewhere with API-controlled `html_url` fields — has no equivalent guard, so that invariant does not actually hold app-wide.

## Impact Explanation
If an attacker can influence the `html_url` (or similarly-sourced) field returned by the GitHub API endpoint the user's Desktop instance talks to — realistic for GitHub Enterprise Server users pointed at a compromised/malicious GHE instance, or via any MITM/compromise of the API response path — they can supply a non-`http(s)` URI (e.g. a custom/dangerous OS protocol handler, a `file://` UNC path, or handlers known to enable code execution through installed local applications). Clicking the resulting "Open in Browser" link in the PR-comment dialog invokes `shell.openExternal()` with that raw value, with no scheme restriction, unlike the markdown link path which is deliberately hardened. This can result in local file access/execution outside the repo or invocation of arbitrary OS protocol handlers under attacker control, matching the "arbitrary external call" impact class (unvalidated target of a privileged call).

## Likelihood Explanation
Requires the user to be connected to a malicious or compromised GitHub/GHE endpoint (not local/physical access, not admin, not pre-existing malware) and to click a link surfaced from that endpoint's API data inside a normal Desktop workflow (viewing a PR comment notification). This is a plausible unprivileged network-position/data-source attack rather than a purely theoretical one, but it does depend on the user interacting with a non-github.com endpoint or the response being tampered with, which somewhat limits likelihood relative to a same-origin exploit.

## Recommendation
Apply the same scheme validation used in `sandboxed-markdown.tsx`'s `setupLinkInterceptor` (`/^https?:/`) inside `LinkButton.onClick` before calling `shell.openExternal`, or centralize URL-scheme validation in the `shell.openExternal` wrapper (`app/src/lib/app-shell.ts` / `app/src/main-process/main.ts`'s `open-external` IPC handler) so every call site is protected regardless of which UI component initiates it, rather than relying on each caller to pre-filter.

## Proof of Concept
1. Point GitHub Desktop at a malicious/compromised GitHub Enterprise Server endpoint (or intercept/tamper with an API response, e.g. via a compromised proxy the user already trusts for that endpoint).
2. Craft a pull-request review comment whose `html_url` field is set to a non-`https` URI (e.g. a locally-installed dangerous protocol handler or a crafted `file://` path).
3. Have the comment surface via Desktop's PR notification flow, rendering `PullRequestComment` (`app/src/ui/notifications/pull-request-comment.tsx:123-129`).
4. User clicks "Open in Browser" in the footer; `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:76-92`) calls `shell.openExternal(comment.html_url)` with no scheme check, unlike the markdown-body link path in the same dialog which is restricted to `https?:` only.

Note: I could not fully verify from the indexed code whether the GitHub API client (`app/src/lib/api.ts`) applies any independent sanitization to `html_url` before it's stored on the comment model — this would need to be checked in a full Devin session to confirm end-to-end exploitability versus a defense-in-depth gap.
