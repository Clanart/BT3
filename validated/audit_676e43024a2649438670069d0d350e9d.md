### Title
`InternalWithdraw` gRPC Endpoint Bypasses `aggregator_verification_address` Authorization Check Enforced by `Withdraw` — (`File: core/src/rpc/operator.rs`)

### Summary

The Operator gRPC service exposes two endpoints that both ultimately call `Operator::withdraw()`: `InternalWithdraw` (takes `WithdrawParams`) and `Withdraw` (takes `WithdrawParamsWithSig`). When `aggregator_verification_address` is configured, `Withdraw` enforces a mandatory ECDSA signature from Citrea/aggregator before processing any withdrawal. `InternalWithdraw` calls the identical underlying logic with zero verification-signature enforcement, creating a direct bypass of the authorization gate.

This is the native analog of the ERC4626 M-06 bug: two entry points for the same state-changing operation, one enforcing a critical constraint and one silently omitting it.

---

### Finding Description

`Withdraw` in `core/src/rpc/operator.rs` (lines 193–258) enforces the following guard when `aggregator_verification_address` is set in config:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... parse verification_signature ...
    if let Some(verification_signature) = verification_signature {
        let address_from_sig =
            recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)?;
        if address_from_sig != address_in_config {
            return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
        }
    } else {
        return Err(BridgeError::ECDSAVerificationSignatureMissing).map_to_status();
    }
}
```

`InternalWithdraw` in the same file (lines 169–190) calls the identical `operator.withdraw()` function with no such check:

```rust
async fn internal_withdraw(
    &self,
    request: Request<WithdrawParams>,
) -> Result<Response<RawSignedTx>, Status> {
    let (...) = parser::operator::parse_withdrawal_sig_params(request.into_inner())?;
    let payout_tx = self.operator.withdraw(...).await?;
    Ok(Response::new(RawSignedTx::from(&payout_tx)))
}
```

Both endpoints are registered on the same `ClementineOperator` gRPC service and are reachable by any mTLS-authenticated client (the aggregator holds a valid client cert for this service).

The `aggregator_verification_address` field is documented as:

> "The ECDSA address of the citrea/aggregator that will sign the withdrawal params after manual verification of the optimistic payout and operator's withdrawal. Used for both an extra verification of aggregator's identity and to force citrea to check withdrawal params manually during some time after launch." [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

When `aggregator_verification_address` is set (the security-critical deployment mode), the intended invariant is: **no withdrawal is processed by an operator unless Citrea/aggregator has manually signed off on the exact withdrawal parameters**. This prevents operators from processing withdrawals that Citrea would reject during manual review.

By calling `InternalWithdraw` instead of `Withdraw`, an operator (or any mTLS-authenticated caller) can:

1. Submit any valid `WithdrawParams` (withdrawal registered in Citrea's DB, correct UTXO, profitable) directly to the operator.
2. The operator's `withdraw()` function executes: verifies the user's Schnorr signature, checks `is_profitable()`, and broadcasts the payout transaction — all without Citrea's manual approval.
3. The operator fronts BTC to the user and initiates the reimbursement chain (kickoff → payout → reimburse) against the bridge vault.

The `aggregator_verification_address` authorization gate — the only control that enforces Citrea's manual review of withdrawal parameters — is rendered completely ineffective. Any withdrawal that passes the Citrea DB check (`get_withdrawal_utxo_from_citrea_withdrawal`) can be processed without the required authorization. [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

- The operator controls their own service and can call `InternalWithdraw` at any time from their own automation or CLI.
- The aggregator, which holds a valid mTLS client certificate for the operator's service, can also call `InternalWithdraw` directly.
- The proto comment explicitly states `InternalWithdraw` is "intended for operator's own use," confirming it is a reachable, production endpoint — not a test artifact.
- No additional privilege escalation is required beyond what the operator already possesses. [6](#0-5) [7](#0-6) 

---

### Recommendation

Apply the same `aggregator_verification_address` check inside `internal_withdraw` that is already present in `withdraw`. If `InternalWithdraw` is truly intended only for the operator's own automation (not for external callers), it should either:

1. **Enforce the same verification-signature check** as `Withdraw`, or
2. **Restrict `InternalWithdraw` to loopback/self-originated calls only** at the mTLS layer (e.g., only accept the operator's own certificate, not the aggregator's certificate), and document that `aggregator_verification_address` does not apply to self-initiated withdrawals.

Option 1 is the safer fix and directly mirrors the recommended mitigation from the ERC4626 M-06 report: make both entry points enforce the same constraint. [1](#0-0) 

---

### Proof of Concept

1. Deploy operator with `AGGREGATOR_VERIFICATION_ADDRESS=<citrea_address>` set in config.
2. Confirm that calling `Withdraw` without a valid verification signature returns `ECDSAVerificationSignatureMissing`.
3. Call `InternalWithdraw` with the same `WithdrawParams` (no `verification_signature` field exists in the message type):

```
grpcurl -cert client.pem -key client.key -cacert ca.pem \
  operator:17000 clementine.ClementineOperator/InternalWithdraw \
  '{"withdrawal_id": 0, "input_signature": "...", "input_outpoint": {...}, \
    "output_script_pubkey": "...", "output_amount": 999760000}'
```

4. Observe: the payout transaction is broadcast and the withdrawal is processed — with no Citrea/aggregator verification signature ever checked.

The bypass is unconditional: `internal_withdraw` contains zero references to `aggregator_verification_address`. [1](#0-0) [8](#0-7)

        tracing::info!("Withdraw rpc called");
        let params = request.into_inner();
        let withdraw_params = params.withdrawal.ok_or(Status::invalid_argument(
            "Withdrawal params not found for withdrawal",
        ))?;
        let (withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount) =
            parser::operator::parse_withdrawal_sig_params(withdraw_params)?;

        tracing::warn!(
            "Parsed withdraw rpc params, withdrawal id: {:?}, input signature: {:?}, input outpoint: {:?}, output script pubkey: {:?}, output amount: {:?}, verification signature: {:?}", withdrawal_id, input_signature, input_outpoint, output_script_pubkey, output_amount, params.verification_signature
        );

        // if verification address is set in config, check if verification signature is valid
        if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
            let verification_signature = params
                .verification_signature
                .map(|sig| {
                    PrimitiveSignature::from_str(&sig).map_err(|e| {
                        Status::invalid_argument(format!("Invalid verification signature: {e}"))
                    })
                })
                .transpose()?;
            // check if verification signature is provided by aggregator
            if let Some(verification_signature) = verification_signature {

                    recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(

                        input_outpoint,
                        output_script_pubkey.clone(),
                        output_amount,
                        verification_signature,
                    )?;

                    return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();

//! # ECDSA Verification Signature
//!
//! This module contains the ECDSA verification signature for the Clementine protocol.
//! It is for additional verification that the request for optimistic payout and withdrawal is coming from the aggregator, which
//! is the owner of the address in operator/verifiers config.
//!
//! The address who signed the signature is retrieved by calculating the EIP-712 hash of the withdrawal params.
//! The address is then compared to the address in the config.
//!

use alloy::sol_types::Eip712Domain;

        bytes input_signature;
        bytes32 input_outpoint_txid;
        uint32 input_outpoint_vout;
        bytes output_script_pubkey;
        uint64 output_amount;
    }
