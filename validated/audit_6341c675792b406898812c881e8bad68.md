## Title
Governance can set KIP-71 base fee bounds without any absolute cap, allowing an unbounded/instant spike in transaction fees - (File: `kaiax/gov/param.go`, `kaiax/gov/headergov/impl/header.go`, `params/kip71_config.go`)

### Summary
The `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` governance parameters, which bound the dynamic KIP-71 base fee that every transaction sender must pay, are validated only against each other (lower ≤ upper) and never against an absolute ceiling. Combined with how `NextMagmaBlockBaseFee` clips the previous block's base fee to the *current* bounds before computing the next fee, a governing node can force an immediate, unbounded jump in the fee every sender must pay, mirroring the referenced report's "no limit on the amount of fees users have to pay."

### Finding Description
The two KIP-71 bound parameters are registered with `noopFormatChecker`, meaning any `uint64` value (up to `~1.8e19`) is accepted as long as the canonicalizer succeeds: [1](#0-0) 

The only cross-check performed is relative consistency between the two bounds, evaluated against the *currently effective* `ParamSet`, with no absolute maximum: [2](#0-1) 

Critically, `NextMagmaBlockBaseFee` does not gradually converge the base fee toward a newly-changed bound — it first *clips* the parent block's actual base fee into the new `[LowerBoundBaseFee, UpperBoundBaseFee]` range before applying the incremental delta: [3](#0-2) 

This means as soon as a governance vote raising `LowerBoundBaseFee` (or `UpperBoundBaseFee`) takes effect, the very next block's base fee is instantly clamped up to that new floor — there is no per-block rate limiting for governance-driven bound changes, only for organic gas-usage-driven fee changes (`baseFeeDelta` division by `baseFeeDenominator`). Since there is no absolute cap on the bound values themselves, the governing node can, across one or two votes, push `LowerBoundBaseFee`/`UpperBoundBaseFee` toward the `uint64` maximum, instantly and permanently forcing every transaction sender to pay an arbitrarily large fee with no smoothing or ceiling protection, directly analogous to the reported Allo.sol issue where fee percentage lacked an upper bound.

### Impact Explanation
Every unprivileged transaction sender is forced to pay whatever base fee results from governance-controlled bounds; because there is no absolute cap and the clipping is instantaneous rather than gradual, a malicious or compromised governing node can cause an immediate, network-wide fee shock that can drain sender balances on the very next block, or effectively deny service to normal users by pricing all transactions out of feasibility. This is a concrete unauthorized value-extraction / fee-abuse scenario reachable by governance vote transactions that gate the fee every subsequent transaction sender pays.

### Likelihood Explanation
Requires control of governance voting rights (the single governing node in `single` governance mode, or majority in `ballot` mode), so it is not exploitable by an arbitrary unprivileged sender directly — but it requires no code bug beyond the missing bound check; a single malformed/malicious governance vote is sufficient, and the acceptance logic (`checkConsistency`) will validate it as long as internal relative ordering holds, regardless of how extreme the absolute values are.

### Recommendation
Add an absolute sanity ceiling (and floor) to `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` `FormatChecker`s in `kaiax/gov/param.go` (e.g., a protocol-defined maximum base fee), and/or rate-limit how much these bounds can change per governance epoch, and consider making `NextMagmaBlockBaseFee`'s bound-clipping gradual rather than instantaneous so that a bound change cannot cause an immediate fee spike in the very next block.

### Proof of Concept
1. Governing node submits a vote `Kip71UpperBoundBaseFee = X` where `X` is a very large `uint64` (e.g., near `math.MaxUint64`); `checkConsistency` only requires `X >= LowerBoundBaseFee`, so it passes: [4](#0-3) 
2. Governing node submits a subsequent vote `Kip71LowerBoundBaseFee = Y` where `Y` is close to `X` (still satisfies `Y <= UpperBoundBaseFee`): [5](#0-4) 
3. Once these votes take effect, `NextMagmaBlockBaseFee` clips the parent's (much lower) actual base fee up to the new `lowerBoundBaseFee = Y` immediately in the very next block: [6](#0-5) 
4. All subsequent transaction senders must now pay this arbitrarily high base fee with no smoothing period and no protocol-level maximum to prevent it.
