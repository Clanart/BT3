### Title
Server-Side Request Forgery via unrestricted DataLayer mirror URLs - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can register an on-chain "mirror" record for any DataLayer store they merely track (not necessarily own), embedding an arbitrary URL. Once other nodes with DataLayer enabled sync mirrors for that store and attempt to fetch delta/full-tree files, they issue an outbound HTTP request to the attacker-chosen URL, exactly matching the SSRF bug class described in CVE-2022-43140 (arbitrary URL fetch via a user-controlled parameter).

### Finding Description
`create_mirror_puzzle()` returns a fixed, non-owner-restricted puzzle (`P2_PARENT.curry(Program.to(1))`), and `MIRROR_PUZZLE_HASH` is public. `DataLayerWallet.create_new_mirror()` lets any wallet holder send a standard coin to `MIRROR_PUZZLE_HASH` with memos `[launcher_id, *urls]` for **any** `launcher_id`, without proving ownership of that store's singleton. When such a coin is created and spent on chain, any node's `DataLayerWallet.coin_added()` handler decodes `launcher_id`/`urls` via `get_mirror_info()` and persists the mirror as long as the launcher is tracked locally (`is_launcher_tracked`) — no additional authorization or URL validation is performed. Later, `DataLayer.fetch_and_validate()` retrieves `available_servers_for_store` (which include these attacker-supplied mirror URLs), shuffles them, and for the plain-HTTP path calls `download_data.http_download()`, which performs `session.get(server_info.url + "/" + filename, ...)` — an unrestricted outbound request to attacker-controlled infrastructure (including internal/private IPs, cloud metadata endpoints, etc.), with no scheme/host allow-listing.

### Impact Explanation
This is a genuine SSRF: an unprivileged wallet user can force any DataLayer-enabled peer that syncs the targeted store to make arbitrary outbound HTTP requests, including to internal network services or cloud metadata endpoints, potentially leaking credentials/tokens or being used to probe/attack internal infrastructure of node operators (exchanges, block explorers, etc. running DataLayer). It does not directly cause consensus divergence or fund loss, but qualifies as a reachable, unauthenticated network-request-forgery primitive triggered purely by an on-chain spend.

### Likelihood Explanation
Likelihood is High for any node that has DataLayer enabled and is tracking/subscribed to a store also being watched by an attacker: creating the malicious mirror coin only costs a standard transaction fee and requires no special privilege, ownership, or coordination with the store's actual owner.

### Recommendation
Restrict mirror creation/acceptance to be scoped by proof of store ownership (or at least require operator opt-in per mirror URL/host), validate/allow-list mirror URL schemes and hosts before an HTTP fetch is attempted, and consider resolving/filtering destination IPs (block private/loopback/link-local ranges such as `169.254.169.254`) in `http_download()` before issuing requests.

### Proof of Concept
1. Attacker wallet calls `dl_new_mirror` RPC (or `DataLayerWallet.create_new_mirror`) with `launcher_id` set to a victim's public DataLayer store id and `urls=["http://169.254.169.254/latest/meta-data/"]` (or an internal service URL), paying only the standard mirror coin amount + fee.
2. Once confirmed on chain, any peer's `DataLayerWallet.coin_added()` picks up the `CREATE_COIN` to `MIRROR_PUZZLE_HASH`, decodes the memos, and stores the mirror for that `launcher_id` because it is tracked.
3. During the next `periodically_manage_data()` cycle, `DataLayer.fetch_and_validate()` selects this malicious `ServerInfo` and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, causing the peer's server to issue an HTTP GET to the attacker-chosen URL.
