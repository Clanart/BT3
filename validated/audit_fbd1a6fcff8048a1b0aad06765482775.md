### Title
Use of `payable(msg.sender).transfer()` in `WSEI.sol` `withdraw()` can permanently lock user funds — (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol` is the Wrapped-SEI ERC20 contract whose bytecode/ABI is embedded and shipped by the chain itself via `x/evm/artifacts/wsei/artifacts.go`, and is deployed/instantiated through the EVM module tooling (referenced from `x/evm/client/cli/tx.go`). Its `withdraw()` function uses the hard-coded 2300-gas `.transfer()` primitive to send native value back to the caller, which is exactly the bug class described in the referenced report.

### Finding Description
`withdraw()` decrements the caller's WSEI balance and then sends native SEI to `msg.sender` using `payable(msg.sender).transfer(wad)`: [1](#0-0) 

`.transfer()` forwards a fixed 2300 gas stipend to the recipient. If `msg.sender` is a smart contract (e.g., a DeFi protocol, multisig, or proxy-based wallet) whose `receive`/`fallback` function requires more than 2300 gas to execute, the low-level call inside `.transfer()` fails and the entire `withdraw()` transaction reverts, exactly as described in the original report. Because Solidity's `.transfer()` has no way to forward custom gas, there is no way to work around this from the calling contract side other than not holding WSEI at all.

The WSEI contract is not a throwaway test fixture: it is compiled and embedded into the sei-chain binary itself for deployment as a first-class wrapped-native-token contract: [2](#0-1) 
and is referenced by the EVM module's CLI tooling for genesis/setup: [3](#0-2) 

### Impact Explanation
Any smart contract (AMM pool, vault, multisig, proxy wallet, etc.) that acquires WSEI and later calls `withdraw()` to unwrap it back to native SEI can have its funds permanently stuck if its receive/fallback logic consumes more than 2300 gas. Since `deposit()`/`transfer()` of the ERC20 balance itself succeeds unconditionally, a contract can accumulate WSEI but then be unable to ever unwrap it, resulting in a permanent freezing of funds for that holder. Given WSEI's role as the canonical wrapped-native token that other protocols on Sei are expected to integrate with (analogous to WETH), this is a systemic risk affecting any downstream integrator's contract, not just isolated user error.

### Likelihood Explanation
Reachable by any unprivileged account: a contract holding WSEI just needs to call `withdraw()`. Many common contract patterns (Gnosis-Safe-style multisigs, contracts with non-trivial `receive()` logic, proxies) exceed the 2300 gas stipend, so this is not a purely theoretical edge case — it is the same well-documented `.transfer()` pitfall responsible for real fund lockups in other wrapped-native-token implementations (e.g., some WETH forks).

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `withdraw()` with a low-level `.call{value: wad}("")` and check the boolean success return value, following the checks-effects-interactions pattern already used (balance is decremented before the external call):
```solidity
function withdraw(uint wad) public {
    require(balanceOf[msg.sender] >= wad);
    balanceOf[msg.sender] -= wad;
    (bool success, ) = payable(msg.sender).call{value: wad}("");
    require(success, "SEI transfer failed");
    emit Withdrawal(msg.sender, wad);
}
```
Add reentrancy protection (e.g., `nonReentrant` or ensure state changes fully precede the external call, which is already the case here) since `.call` forwards all remaining gas.

### Proof of Concept
1. Deploy a contract `Attacker` whose `receive()` function contains a loop or storage write that consumes more than 2300 gas (e.g., `mapping(uint=>uint) m; receive() external payable { m[block.number] = 1; }`).
2. `Attacker` calls `WSEI.deposit{value: 1 ether}()`, receiving 1 WSEI.
3. `Attacker` calls `WSEI.withdraw(1 ether)`.
4. The internal `payable(msg.sender).transfer(wad)` call reverts because the `receive()` function exceeds the 2300 gas stipend, causing the entire `withdraw` transaction to revert.
5. `Attacker` (and any similarly structured contract) can never unwrap its WSEI back to native SEI, permanently freezing those funds inside the WSEI contract for that holder.
