### Title
Missing FormatChecker on `kip71.gastarget` allows governance-set value of 0, causing a division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
The KIP-71 (Magma) dynamic base-fee parameter `GasTarget` is registered in the governance parameter table with `FormatChecker: noopFormatChecker`, meaning any `uint64` value—including `0`—is accepted as valid when set through governance. `NextMagmaBlockBaseFee` divides by `gasTarget` without checking for zero, so once `GasTarget = 0` is active, every node computing the next block's base fee panics on a division by zero in `math/big`.

### Finding Description
`Kip71GasTarget` is defined with a `noopFormatChecker`, unlike its sibling `Kip71BaseFeeDenominator` which explicitly rejects zero: [1](#0-0) 

This means a governance vote/param update setting `kip71.gastarget` to `0` will pass validation (`param.FormatChecker(cv)` in `PartialParamSet.Add`) and be accepted into the `ParamSet`, which is then converted into a `KIP71Config` via `ToKip71Config()`: [2](#0-1) 

`NextMagmaBlockBaseFee` uses `gasTarget` directly as a divisor with no zero-guard, unlike `BaseFeeDenominator`, which does have a zero fallback (`if kc.BaseFeeDenominator == 0 { ... set default ... }`): [3](#0-2) 

Specifically, once `gasTarget == 0`:
- If `parentGasUsed == 0`, the code returns early (`parentGasUsed == gasTarget` branch), so no panic occurs.
- But if `parentGasUsed > 0` (true for essentially every real block with any gas usage), the code enters the "above target" branch:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // = parentGasUsed
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 → panic: division by zero
```
`math/big.Int.Div` panics (not a Go `error`) when the divisor is zero, crashing the calling goroutine.

This function is called on the consensus-critical path in block validation/finalization/fee-history/tx-pool/worker code (`blockchain/block_validator.go`, `blockchain/chain_makers.go`, `blockchain/tx_pool.go`, `work/worker.go`, `node/cn/gasprice/*`), so **every full node** computing or verifying the base fee for a new block would panic once this governance value is active.

### Impact Explanation
This is a state-transition / consensus availability bug: once a governance vote sets `kip71.gastarget = 0` (accepted validly since no format check rejects it), all nodes that compute `NextMagmaBlockBaseFee` for the following block (header preparation, header verification, mempool pricing, fee history, tx pool base-fee checks) hit an unrecovered `panic` from `big.Int.Div`. This is capable of halting block production and/or crashing full nodes network-wide — a chain-halting denial-of-service triggered purely by a governance parameter that is supposed to be validated but isn't. This qualifies under the allowed categories "KIP-71 pricing", "governance parameters", and "state transition and gas/burn accounting."

### Likelihood Explanation
The likelihood depends on a governance parameter change being approved (via the standard governance vote mechanism for `kip71.gastarget`), which is a legitimate, permitted operation type in Kaia's governance system — no external validation or additional bounds are enforced by the parameter-set layer (`FormatChecker: noopFormatChecker`) before it is written to `ParamSet`/`KIP71Config`. Compared to the other three related KIP-71 fields (`LowerBoundBaseFee`, `UpperBoundBaseFee`, `MaxBlockGasUsedForBaseFee`), which are also `noopFormatChecker`, `GasTarget` is uniquely used as an unconditional divisor with no runtime zero-fallback (unlike `BaseFeeDenominator`), making it the concretely exploitable one.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (mirroring `Kip71BaseFeeDenominator`) that rejects `0`, e.g. `func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`. Additionally, as defense-in-depth, add a zero-guard/fallback for `gasTarget` inside `NextMagmaBlockBaseFee` (similar to the existing fallback for `BaseFeeDenominator`) so that a zero value can never reach the `Div` calls.

### Proof of Concept
1. Through the governance mechanism, submit and have approved a parameter vote setting `kip71.gastarget = 0`. `PartialParamSet.Add` accepts it because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` (`kaiax/gov/param.go:324-334`).
2. Once the new `ParamSet` becomes active at the target block, any code path computing the base fee for the next block calls `KIP71Config.NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)` (`params/kip71_config.go:58`) with `GasTarget = 0`.
3. For any block where `parentGasUsed != 0` (essentially all blocks with transactions), the function enters the `parentGasUsed > gasTarget` branch and executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing `math/big` to panic with "division by zero".
4. Because this function is invoked in header preparation and validation (`blockchain/block_validator.go`), the panic propagates through core block-processing code paths on every full node, resulting in a crash/halt.
