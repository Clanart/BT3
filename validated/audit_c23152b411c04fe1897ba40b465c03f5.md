### Title
Unbounded allocation from attacker-controlled length in `ReceivedOutput::read` enables memory-exhaustion DoS - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary

The reported bug class is "missing size limit on attacker-controlled input → memory exhaustion DoS." Serai's analog lives in `ReceivedOutput::read`, which is explicitly listed as an entry point for untrusted bytes. It decodes a `TxOut` via `TxOut::consensus_decode` on the raw attacker-supplied stream. `TxOut` consensus decoding reads a CompactSize (`VarInt`) length for `script_pubkey` and then allocates a `Vec`/`ScriptBuf` of that declared length before reading the bytes — a declared length of up to 2⁶⁴−1. No bound check exists between the length prefix and the allocation, exactly mirroring the Astro advisory's unbounded body buffer.

### Finding Description

`ReceivedOutput::read` reads a 32-byte scalar offset, then hands the reader to Bitcoin consensus decoding:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-133
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      ...
```

`TxOut` consensus encoding is `value:u64 || CompactSize(len) || script_pubkey[len]`. The decoder trusts `len` (an attacker-chosen `u64` reaching up to `usize::MAX` on 64-bit) and allocates a buffer of that size prior to `read_exact`. A tiny crafted input — a valid scalar plus `value` plus a `VarInt` of e.g. `0xffffffffffffffff` — is sufficient to trigger a multi-exabyte allocation request, causing an immediate allocation-failure abort of the process. `read_exact` never gets a chance to fail gracefully; the abort precedes it.

Unlike the Serai in-scope crypto deserializers — `Commitments::read` (bounded by `generators.len()`, crypto/frost/src/nonce.rs:133-139), `EncryptedMessage::read` (fixed-size fields, crypto/dkg/pedpop/src/encryption.rs:171-177), and PedPoP `Commitments::read` (bounded by `params.t()`, crypto/dkg/pedpop/src/lib.rs:110-128) — this path has no protocol-implied size bound. Contrast with `coordinator/src/p2p.rs:261-270`, where an equivalent length-prefixed read explicitly enforces `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating.

### Impact Explanation

Unauthenticated, pre-validation memory-exhaustion DoS. Any code path that feeds adversary-influenced bytes into `ReceivedOutput::read` (scanner output deserialization, DB/network round-trips of received outputs in the Bitcoin processor) can be crashed by a sub-100-byte payload. A single malicious peer or upstream data source forces a crash; in a restart-looping deployment this is a persistent denial of service, matching the advisory's availability impact.

### Likelihood Explanation

Reachable by any party able to supply bytes to `ReceivedOutput::read` — which the threat model treats as untrusted input. The payload is trivially constructible (no valid signature, proof, or on-chain funds needed). On 64-bit platforms the huge `usize` allocation aborts deterministically rather than erroring. One caveat: the abort behavior depends on rust-bitcoin's `Vec`/`ScriptBuf` decode path allocating upfront (which `TxOut::consensus_decode`/`ScriptBuf` decoding does), and on the OS/allocator failing rather than overcommitting — on Linux with overcommit the allocation may succeed lazily, converting this into an OOM-on-touch scenario that is still reliably fatal once `read_exact` begins filling pages, though an early EOF error would limit it to a large one-shot allocation. This dependency on the upstream crate's decode internals is the main residual uncertainty.

### Recommendation

Cap the `TxOut` decode before allocating: wrap the reader in `io::Read::take` with a sane maximum (e.g. Bitcoin's maximum standard `script_pubkey` size, ~10 KB, or the max `TxOut` serialized size), or decode `script_pubkey` length manually, reject values above the bound, and only then allocate/read. Alternatively use rust-bitcoin's bounded-consensus-decode helpers (`consensus_decode_from_finite_reader` / a `Vec` decode with a `MAX_VEC_SIZE`-style cap) rather than raw `TxOut::consensus_decode` on an unbounded stream.

### Proof of Concept

```rust
// Crafted ReceivedOutput bytes:
//   offset: 32-byte valid Secp256k1 scalar (non-zero, < order)
//   TxOut.value: 8 bytes (e.g. 0)
//   TxOut.script_pubkey: VarInt(0xffffffff_ffffffff) with no following bytes
let mut payload = Vec::new();
payload.extend_from_slice(&[1u8; 32]);            // offset scalar
payload.extend_from_slice(&0u64.to_le_bytes());   // value
// CompactSize VarInt encoding u64::MAX:
payload.push(0xff);
payload.extend_from_slice(&u64::MAX.to_le_bytes());

let mut slice = payload.as_slice();
// Triggers an attempted allocation of ~usize::MAX bytes inside
// TxOut::consensus_decode -> ScriptBuf decode -> Vec::with_capacity(len)
let _ = ReceivedOutput::read(&mut slice); // process aborts on allocation failure
```
