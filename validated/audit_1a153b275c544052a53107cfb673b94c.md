The `withdraw()` function's gate is confirmed exactly as described: when `remaining_balance == 0` (closing the account), it unconditionally rejects the operation if `pending_delegator_rewards() > 0`, returning `InstructionError::InsufficientFunds` with no override path. [1](#0-0)

The only writer that increases `pending_delegator_rewards` is `add_pending_delegator_rewards` (called from `deposit_delegator_rewards`), which strictly checked-adds to the field; there is no corresponding decrement/reset function elsewhere in `handler.rs` or `mod.rs` other than the reward-distribution codepath referenced above and the full-account deinitialization in `withdraw()` itself. Existing unit tests (`test_withdraw_pending_delegator_rewards`) explicitly document and exercise this exact gate — confirming a nonzero `pending_delegator_rewards` blocks full closure and is only bypassed once `pending_delegator_rewards` is manually reset to `0`. [5](#0-4) [6](#0-5)

Given the confirmed code paths, this matches the report's claim precisely: `withdraw()`'s unconditional `pending_delegator_rewards > 0` gate on full account closure, combined with `calculate_block_reward`'s zero-payout-on-zero-active-stake behavior, creates a permanent fund-lock condition once all delegated stake is withdrawn from a vote account with an outstanding `pending_delegator_rewards` balance — reachable via ordinary, permissionless stake deactivation/withdrawal by delegators.

Audit Report

## Title
Vote account becomes permanently unclosable when `pending_delegator_rewards` is stranded after all delegated stake is withdrawn - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`withdraw()` refuses to fully close a vote account whenever `pending_delegator_rewards > 0`. The only mechanism that reduces this field is block-reward distribution via `calculate_block_reward`, which pays `0` whenever the vote account's `total_active_stake` is `0`. Once all delegators withdraw their stake from a vote account with a nonzero pending balance — an ordinary, permissionless action — `pending_delegator_rewards` can never be paid down, permanently blocking the vote account's `authorized_withdrawer` from closing it and reclaiming the remaining lamports.

## Finding Description
`withdraw()` enforces: if the withdrawal would zero the account's balance (full close), it requires `pending_delegator_rewards == 0`, otherwise returning `InstructionError::InsufficientFunds` [1](#0-0) . The field is increased only through `deposit_delegator_rewards`/`add_pending_delegator_rewards`, which strictly checked-adds and has no complementary decrement/reset function [3](#0-2) [4](#0-3) . The sole payout/decrement path is `calculate_block_reward`, which returns `0` when `total_active_stake` for the vote account's delegation is `0`, meaning no reward accrues and nothing offsets `pending_delegator_rewards` for that epoch [2](#0-1) . `total_active_stake` is derived from the reward epoch's delegated stakes to that vote account, which are entirely controlled by delegators who can freely deactivate and withdraw stake through the stake program at will. Once all such stake is removed while `pending_delegator_rewards > 0`, no future epoch can ever reduce the balance, and the `withdraw()` gate permanently blocks full closure. Existing tests explicitly confirm this exact behavior: `test_withdraw_pending_delegator_rewards` shows the withdraw instruction failing with `InstructionError::InsufficientFunds` while `pending_delegator_rewards > 0`, and succeeding only once the field is externally reset to `0` [5](#0-4) [6](#0-5) .

## Impact Explanation
The vote account's rent-exempt-minimum-plus-`pending_delegator_rewards` lamports become permanently locked and unrecoverable by the legitimate `authorized_withdrawer`. This is a fund-accounting/lock defect in the runtime's reward-distribution and vote-program withdrawal logic, falling squarely within the "fund theft/loss" impact category for built-ins/runtime code.

## Likelihood Explanation
The trigger requires only ordinary, unprivileged, permissionless actions: delegators calling `deactivate_stake`/`withdraw_stake` on their own stake accounts delegated to a vote account that still carries an outstanding `pending_delegator_rewards` balance. No attacker collusion, privileged access, or protocol exploit is required — it is a natural consequence of normal validator churn (e.g., delegators leaving after a reward deposit but before it's fully distributed).

## Recommendation
Add a fallback mechanism to drain `pending_delegator_rewards` when `total_active_stake` becomes `0` (e.g., redirect the balance to the vote account's own available balance, the commission collector, or burn it), or relax the `withdraw()` full-closure gate to permit closure once no active stake remains delegated, since the reward can no longer legitimately be attributed to any delegator.

## Proof of Concept
1. Deposit delegator rewards into vote account `V` via `DepositDelegatorRewards`, setting `pending_delegator_rewards = X > 0` [4](#0-3) .
2. Have all stake accounts delegated to `V` deactivated and withdrawn by their owners, driving `total_active_stake` for `V` to `0`.
3. Advance an epoch; `calculate_block_reward` returns `0` for `V`'s delegation since `total_active_stake == 0`, leaving `pending_delegator_rewards` unchanged [7](#0-6) .
4. `V`'s `authorized_withdrawer` submits `Withdraw(V.lamports)` to fully close the account; `withdraw()` rejects it with `InstructionError::InsufficientFunds` due to the `pending_delegator_rewards > 0` check [8](#0-7) , matching the pattern already exercised by `test_withdraw_pending_delegator_rewards` [5](#0-4) .
5. Repeat across subsequent epochs — no code path exists to reduce `pending_delegator_rewards` absent active delegated stake, so the account and its stranded balance remain permanently locked.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
