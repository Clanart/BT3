### Title
PedPoP proof-of-possession does not bind the encryption key, allowing `EncryptionKeyMessage` reuse with a substituted `enc_key` - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the reference report (a request signature that does not cover the payload, so it can be reused with different parameters), the PedPoP round-1 message is authenticated by a Schnorr proof of knowledge whose challenge covers only the participant index, the PoK nonce, and the serialized Feldman commitments. The `enc_key` field of `EncryptionKeyMessage` — the ECDH public key under which the participant's incoming secret shares will be encrypted — is not covered by that signature. Any party able to influence the bytes delivered to `EncryptionKeyMessage::read` / `Decryption::register` for another participant (or any transport that authenticates the sender's identity rather than the full message body) can swap the `enc_key` while the PoK still verifies.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:86-94`, `challenge` transcripts `context`, `participant`, `nonce` (`R`), and `commitments` (`Am` = `cached_msg`). `cached_msg` is built in `Commitments::read` (`lib.rs:110-128`) from the commitment points only; the signature is created in `generate_coefficients` over that same `cached_msg` (`lib.rs:176-184`) before the encryption key is even attached. `EncryptionKeyMessage` then appends `enc_key` outside the signed region (`crypto/dkg/pedpop/src/encryption.rs:50-64`).

On the receiving side, `verify_r1` calls `self.encryption.register(l, msg)` (`lib.rs:315`), which stores `msg.enc_key` unconditionally in `Decryption::enc_keys` (`encryption.rs:351-362`) before the PoK is batch-verified (`lib.rs:323-334`). No check binds `enc_key` to the signed commitments. Later, `Encryption::encrypt` (`encryption.rs:460-467`) encrypts each victim's secret share to `decryption.enc_keys[&participant]`, and `calculate_share` (`lib.rs:476-491`) decrypts incoming shares via `ecdh(self.enc_key, msg.key)`.

Because the signature verifies regardless of `enc_key`, a replaced `enc_key` is silently accepted: the sender's share to that participant is encrypted under an attacker-known ECDH private key. Since `cipher` derives its key solely from `context` and the ECDH point (`encryption.rs:101-133`), the attacker decrypts the victim's secret-share bytes directly.

### Impact Explanation
All secret shares addressed to the victim participant are readable by the attacker, yielding the victim's final secret share (`self.secret += share` in `calculate_share`). Knowledge of a participant's threshold secret share is key-share recovery; combined with the attacker's own participation, it degrades the threshold security of the generated key and can enable forging the victim's signature shares in FROST signing sessions. Additionally, honest protocol completion breaks (victim's share verification may still pass since commitments are intact, but the victim itself received nothing decryptable), and blame machinery can be steered, since `AdditionalBlameMachine::new` (`lib.rs:649-662`) consumes `EncryptionKeyMessage`s and registers their `enc_key`s with the same unauthenticated path.

### Likelihood Explanation
Exploitation requires influencing the delivered `enc_key` of a victim's round-1 message while preserving the signed `Commitments`. The library assumes an externally authenticated channel, but it only binds identity expectations via `participant` in the PoK; any channel that authenticates the sender without integrity over the whole serialized `EncryptionKeyMessage`, or any relay/coordinator path that deserializes and re-forwards fields, suffices. No collusion, malicious validator set, or leaked keys are required — only the ability to substitute an unauthenticated field, exactly the "reuse a valid signature with a different payload" shape of the reference bug.

### Recommendation
Include `enc_key` in the signed/committed transcript: extend `cached_msg` (or the `challenge` inputs) to cover `enc_key.to_bytes()`, so the Schnorr PoK authenticates the entire `EncryptionKeyMessage`. Alternatively, move `enc_key` inside `Commitments` so `Commitments::read` absorbs it into `cached_msg` automatically. This mirrors the report's proper fix — bind the payload into the signed data so replay with modified parameters is impossible.

### Proof of Concept
1. Victim `l` broadcasts `EncryptionKeyMessage { msg: Commitments{commitments, cached_msg, sig}, enc_key: K_l }`; `sig` verifies under `challenge(context, l, sig.R, cached_msg)`, which never references `K_l`.
2. Attacker rewrites the message to `enc_key: K_a` (attacker-known scalar `a`, `K_a = a·G`) and delivers it to the group / blame consumer.
3. `Decryption::register(l, msg)` (`encryption.rs:351-362`) stores `K_a`; `verify_r1` batch-verifies `sig` successfully since the challenge is unchanged.
4. Every sender calls `encrypt(rng, l, share)` → `cipher(context, ecdh(k_msg, K_a))` (`encryption.rs:154, 460-467`). The attacker computes `ecdh(a, msg.key)` = same point and applies `ChaCha20` keystream to recover each share plaintext.
5. Attacker sums the recovered shares (`polynomial` shares destined for `l`) to obtain participant `l`'s secret share — key-share recovery without breaking any signature or proof.
