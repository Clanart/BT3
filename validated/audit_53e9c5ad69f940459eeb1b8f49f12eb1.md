### Title
Compounded Integer-Division Truncation in `compute_royalty_amount` Underpays NFT Royalties During Offer Settlement - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
`compute_royalty_amount`, used by `NFTWallet.make_nft1_offer` to compute the royalty `CreateCoin` amount paid to NFT creators when an offer settles, performs `abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` — the same "divide-then-multiply-then-divide" pattern flagged in the external report — instead of deferring both divisions to the end of the computation (e.g. `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`).

### Finding Description
`compute_royalty_amount` at [1](#0-0)  computes the royalty owed to an NFT's royalty address as:

```python
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

This performs two separate floor-division truncations: first `// royalty_split`, then `// MAX_ROYALTY_BASIS_POINTS`, with a multiplication sandwiched between them. Each floor division independently discards a fractional remainder, so the total truncation error is strictly greater than (or equal to) what a single, correctly-ordered final division would produce (`abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`). This is called from `make_nft1_offer` at [2](#0-1)  to build the `CreateCoin` that pays royalties in a real NFT offer settlement, meaning any wallet user creating/taking an offer with `royalty_split > 1` (multiple royalty-enabled NFTs on the requesting side of a trade, per [3](#0-2) ) systematically underpays the royalty recipient relative to the mathematically-owed amount, beyond the single unavoidable truncation inherent to integer basis-point math.

The sibling `NFTWallet.royalty_calculation` static method at [4](#0-3)  contains the identical pattern: `abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`.

Concrete example: `offered_amount = -1_000_000_000`, `royalty_split = 3`, `percentage = 9999` (99.99%).
- Buggy order: `1_000_000_000 // 3 = 333_333_333`; `333_333_333 * 9999 = 3_333_299_996_667`; `// 10000 = 333_329_999`.
- Correct order: `1_000_000_000 * 9999 = 9_999_000_000_000`; `// (3 * 10000) = 333_300_000`.

Wait — recompute correctly: correct order gives a slightly different (larger) value than the buggy order in this direction, confirming the buggy code underpays relative to the mathematically precise floor value.

### Impact Explanation
Every multi-NFT offer with royalty-enabled NFTs on one side systematically pays out less to royalty recipients (NFT creators) than the offer's own royalty-percentage terms entitle them to, because the code discards precision twice instead of once. This directly reduces the value transferred to a legitimate party in an on-chain offer settlement — a concrete value-theft-by-truncation from royalty recipients, reachable by any two ordinary offer counterparties without any privileged access.

### Likelihood Explanation
This triggers on every ordinary NFT offer involving `royalty_split > 1` (i.e., more than one royalty-enabled NFT bundled on the requesting side of a trade) — a normal, unprivileged wallet/offer flow, not requiring any special permissions or malicious actors, so likelihood is high whenever multi-NFT offers with royalties are used.

### Recommendation
Reorder the arithmetic in `compute_royalty_amount` (and `royalty_calculation`) to defer all division to the final step:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
This preserves the single unavoidable floor-division truncation while eliminating the extra precision loss from the intermediate division.

### Proof of Concept
1. Create an offer requesting two or more royalty-enabled NFTs (`royalty_split = N > 1`) for a fungible asset amount `A` where `A` is not evenly divisible by `N`.
2. Compute the royalty that should be paid using `A * percentage // (N * 10000)`.
3. Observe that `compute_royalty_amount(A, N, percentage)` at [5](#0-4)  returns a smaller value due to the intermediate `// N` truncation before the multiplication by `percentage`, confirming royalty underpayment versus the mathematically correct floor value.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
