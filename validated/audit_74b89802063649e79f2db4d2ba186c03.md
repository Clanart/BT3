### Title
Overpaid native-token dispatch/fund fees are permanently trapped in `EvmHost` instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH and forward the full `msg.value` to a Uniswap-V2-compatible `swapETHForExactTokens` wrapper to buy an exact amount of fee tokens. [1](#0-0) [3](#0-2) [4](#0-3)  The wrapper contracts (`UniV3UniswapV2Wrapper`, and the V2/V4 variants) do refund any unspent ETH — but they send it back to the function's immediate `msg.sender`, which is `EvmHost`, not the end user. [5](#0-4)  `EvmHost` never receives/forwards this refund to `_msgSender()`, so the excess ETH becomes stuck in `EvmHost`'s balance.

### Finding Description
The SDK's own documentation admits the off-chain `quote()` used to compute `msg.value` is only an estimate subject to slippage/sandwiching, and explicitly warns users to add a buffer (the SDK adds a 1% buffer) because the on-chain quoter can move between quoting and execution. [6](#0-5)  This is architecturally identical to the external report's root cause: callers cannot precisely determine the exact native fee needed, so they must overpay to guarantee success — normal, expected behavior, not user error.

The critical difference from a "harmless failure" is what happens to the overpayment. Elsewhere in this same codebase (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`), any leftover `msg.value` after a fee swap is explicitly refunded to the caller via `msg.sender.call{value: msgValue}("")`. [7](#0-6) [8](#0-7) 

`EvmHost.dispatch()`/`fundRequest()` have no such logic. They pass `msg.value` straight through to the wrapper and never check the wrapper's return value (`amounts[0]` = ETH actually spent) or handle a refund. The wrapper's internal refund call succeeds and returns ETH to `EvmHost`'s own balance (since `EvmHost` is `msg.sender` from the wrapper's perspective), but `EvmHost` has no code path that returns that value onward to the original caller. The ETH is absorbed into the contract and is not tracked as belonging to any specific depositor. [9](#0-8) 

### Impact Explanation
Every real-world caller who pays the native-token dispatch fee — required to add slippage buffer per the SDK/docs — will systematically forfeit the unused portion of `msg.value` on every dispatch, GET request, or `fundRequest` call. This is a direct, unauthorized loss of user funds baked into the standard, documented usage flow (not a misuse edge case), affecting the core `dispatch`/`fundRequest` entrypoints used by every application built on `EvmHost`.

### Likelihood Explanation
High. This triggers on ordinary use whenever a user pays fees in native token with any buffer above the exact swap cost — which the SDK itself recommends (1% buffer) and which is unavoidable given AMM price movement between off-chain quoting and on-chain execution. No malicious actor, relayer, or governance action is required; it is a self-inflicted loss on the honest, expected happy path.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` via a low-level call (matching the pattern already used in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol`), reverting if the refund transfer fails.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1.05 ether}(post)` where `post.fee` (in fee-token terms) only actually costs `1.0 ether` worth of ETH via the wrapper at execution time (buffer added per SDK guidance/off-chain quote drift).
2. `EvmHost.dispatch` forwards the entire `1.05 ether` into `swapETHForExactTokens{value: 1.05 ether}(post.fee, ...)`. [10](#0-9) 
3. Inside the wrapper, only `1.0 ether` is spent on the V3 swap; the wrapper computes `refund = 0.05 ether` and sends it back via `msg.sender.call{value: refund}("")` — `msg.sender` here is `EvmHost`. [2](#0-1) 
4. `EvmHost.dispatch()` never reads the wrapper's return value or forwards any ETH back to the user; the `0.05 ether` refund simply increases `EvmHost`'s own ETH balance permanently. [11](#0-10) 
5. The user's transaction completes successfully (request dispatched), but `0.05 ether` is unrecoverably lost from the user's perspective.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }
