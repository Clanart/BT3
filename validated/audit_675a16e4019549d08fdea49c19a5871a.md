## Title
Unbounded shared notification queue lets `logsSubscribe`/`logsUnsubscribe` churn from a single client starve all other pubsub notification types - (File: rpc/src/rpc_subscriptions.rs)

## Summary
`logsSubscribe`/`logsUnsubscribe` do not use a dedicated queue; every subscribe/unsubscribe request for any subscription type is funneled into one process-wide `crossbeam_channel::unbounded()` channel that also carries `Slot`, `SlotUpdate`, `Vote`, `Root`, `Bank`, `Gossip`, and `SignaturesReceived` entries for every other pubsub client, and this channel is drained sequentially by a single logical consumer loop in `RpcSubscriptions::process_notifications`. A tight `logsSubscribe`/`logsUnsubscribe` churn loop from one unprivileged client both grows this unbounded queue and repeatedly write-locks `transaction_log_collector_config`, which is read-locked on every transaction batch in `Bank::collect_logs`.

## Finding Description
`RpcSolPubSubImpl::subscribe`/`unsubscribe` call `SubscriptionControl::subscribe` and rely on `Drop` of `SubscriptionTokenInner` for unsubscribe [1](#0-0) . Both paths push into the same shared channel: `subscribe` sends `NotificationEntry::Subscribed` [2](#0-1) , and `Drop` sends `NotificationEntry::Unsubscribed` [3](#0-2) .

The channel is created unconditionally as `crossbeam_channel::unbounded()`, independent of the `queue_capacity_items`/`queue_capacity_bytes` config (those only bound the separate, downstream `broadcast_sender` used for delivering already-processed notifications to websocket clients) [4](#0-3) . It is drained by `process_notifications`, a single sequential `loop`/`match` that processes `Subscribed`, `Unsubscribed`, `Slot`, `SlotUpdate`, `Vote`, `Root`, `Bank`, `Gossip`, and `SignaturesReceived` entries strictly in order [5](#0-4) . Even though `t_cleanup` builds a rayon pool sized by `notification_threads`, `pool.install()` only runs the closure body (this same sequential loop) — there is no `par_iter`/fan-out inside `process_notifications` itself, so the loop is effectively single-threaded regardless of the configured thread count [6](#0-5) .

Processing a `Subscribed`/`Unsubscribed` entry for `SubscriptionParams::Logs` invokes `LogsSubscriptionsIndex::add`/`remove`, both of which call `update_config()` [7](#0-6) . `update_config()` takes a write lock on `transaction_log_collector_config` [8](#0-7) , the same `RwLock` read-locked on every processed transaction batch in `Bank::collect_logs` [9](#0-8) .

`max_active_subscriptions`/`SubscriberCountGuard` bounds concurrently-held subscriptions but does not throttle subscribe→unsubscribe churn, since a subscribe immediately followed by drop frees the slot instantly [10](#0-9) . I reviewed `rpc/src/rpc_pubsub_service.rs` end-to-end (`handle_connection`, `listen`) and found no per-connection request-rate limiter, message-rate throttle, or backpressure governing how fast a client can call `logsSubscribe`/`logsUnsubscribe`; the only bounds set there are `max_message_size`/`max_frame_size` (4096 bytes) on the websocket frames themselves, which does not limit request rate [11](#0-10) . `PubSubConfig`'s configurable knobs (`queue_capacity_items`, `queue_capacity_bytes`, `worker_threads`, `notification_threads`, `max_active_subscriptions`) all confirmed to not bound or throttle the `notification_sender`/`notification_receiver` channel itself [12](#0-11) .

## Impact Explanation
A single unprivileged websocket client repeatedly calling `logsSubscribe` followed by `logsUnsubscribe` (or reconnecting to trigger token drop) can grow the unbounded `notification_sender`/`notification_receiver` channel with heap-allocated `TimestampedNotificationEntry` items without any configured limit, and because the consumer is a single sequential loop shared across all notification kinds for the entire node, this delays delivery of `slotSubscribe`/`voteSubscribe`/`rootSubscribe`/`accountSubscribe`/`programSubscribe`/`signatureSubscribe` notifications for every other connected client. It also contends for the `transaction_log_collector_config` `RwLock`, which is read-locked on the hot transaction-execution path in `Bank::collect_logs` for every transaction batch, in both banking stage (leader) and replay stage (all validators). This is a "single-client low-rate RPC crash/degradation" pattern: an unprivileged client degrades pubsub notification delivery for unrelated subscribers and can grow node memory unbounded.

## Likelihood Explanation
`logsSubscribe`/`logsUnsubscribe` are unprivileged, publicly reachable RPC pubsub methods, and I confirmed no rate limiter or backpressure mechanism exists in `rpc/src/rpc_pubsub_service.rs` (nor in `PubSubConfig`) that throttles per-connection subscribe/unsubscribe churn — the concurrent-subscription cap (`max_active_subscriptions`) is trivially bypassed by immediate unsubscribe. The underlying channel is genuinely unbounded (`crossbeam_channel::unbounded()`), unconditionally, and its single consumer loop handles all notification types for the whole node in one sequential path, confirmed by direct code reading. This is readily reproducible by any client capable of opening one websocket connection and sending frames as fast as the transport allows.

## Recommendation
- Rate-limit or debounce per-connection subscribe/unsubscribe churn (not just concurrent-subscription count) at the point `SubscriptionControl::subscribe`/`SubscriptionTokenInner::drop` enqueue notifications.
- Bound the `notification_sender`/`notification_receiver` channel (e.g., `crossbeam_channel::bounded`) or separate control-plane (`Subscribed`/`Unsubscribed`) traffic from data-plane (`Slot`/`Bank`/`Gossip`/etc.) traffic so churn in one cannot starve delivery of the other.
- Debounce `LogsSubscriptionsIndex::update_config()` so it only recomputes/writes when the resulting `TransactionLogCollectorConfig` actually changes, reducing write-lock contention with `Bank::collect_logs`.

## Proof of Concept
1. Open one websocket connection to a validator's RPC pubsub endpoint.
2. In a tight loop, send `logsSubscribe` with `RpcTransactionLogsFilter::All` immediately followed by `logsUnsubscribe` for the returned id, as fast as the client can serialize/send frames.
3. From a second websocket connection, subscribe to `slotSubscribe`/`voteSubscribe`/`accountSubscribe` and measure notification latency/backlog while step 2 runs.
4. Instrument `notification_receiver.len()` inside `RpcSubscriptions::process_notifications` and observe queue growth correlating with the first client's churn rate, along with increased latency for the second client's notifications.

            .fetch_update(Ordering::Relaxed, Ordering::Relaxed, |current| {
