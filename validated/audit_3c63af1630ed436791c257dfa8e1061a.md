### Title
`SignableTransaction::new` excludes the OP_RETURN output from the weight/vbyte calculation, underpaying the fee — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The analog to "excess value accepted but never refunded" is Serai's fee/change accounting: the transaction's declared value budget (inputs = payments + fee + change) is computed from an incorrect weight formula. When a `data` payload is supplied, `SignableTransaction::new` pushes an OP_RETURN output into the real transaction but `calculate_weight_vbytes` builds its sizing transaction from `payments` only, so the OP_RETURN output's weight (up to ~360 WU for an 80-byte payload) is never counted. The result is a transaction whose effective fee rate is lower than the caller-specified `fee_per_vbyte`, and which can fall below the minimum relay fee even though the code explicitly checks for that.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the OP_RETURN output is appended to `tx_outs` (the outputs of the real transaction) before weight calculation:

```rust
// lines 194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

But `calculate_weight_vbytes` (lines 62-99) reconstructs a transaction whose `output` list contains only `payments` plus an optional change output — the `data` output is never passed to it. Therefore:

- `vbytes`, and hence `needed_fee = fee_per_vbyte * vbytes` (line 206) and `fee_with_change` (line 227), are underestimated by `8 + 1 + data_len` bytes of serialized output weight (~10-89 bytes → ~250-360 weight units).
- The minimum-relay-fee guard at lines 211-213 uses the same undercomputed `vbytes`, so a caller who specifies exactly the minimum relay rate produces a transaction that actually relays *below* `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected by standard mempools.
- The change amount at line 228 (`input_sat - payment_sat - fee_with_change`) is inflated by the missing fee, so the change output refunds the un-paid fee to the sender while the miners' fee is short — the same "value accounting doesn't match intent" shape as the original report, inverted into change.

The bug is reachable purely from public inputs: `data` is an untrusted `Option<Vec<u8>>` parameter to `SignableTransaction::new`.

### Impact Explanation
A transaction constructed with `data` pays a strictly lower effective fee rate than requested. If the requested rate is at or near the minimum relay fee, the signed transaction is non-standard and will not propagate — the FROST threshold signing round produces a transaction the network rejects, and the plan/inputs cannot be spent via that TXID. Funds remain recoverable only by discarding the signed transaction and re-running the whole signing protocol. This is an incorrect fee formula causing a constructed-and-signed transaction to fail to achieve its purpose (Medium: liveness/availability of the funds, not permanent loss).

### Likelihood Explanation
Any caller combining `data` with `change`/`payments` triggers the undercount; it is deterministic whenever `data.is_some()`. The failure to relay only manifests when the intended fee rate is within ~`(8 + 1 + len) * 4 WU` of the minimum relay threshold, which is exactly the regime the `TooLowFee` check is meant to guard, making the edge case plausible rather than exotic.

### Recommendation
Pass the OP_RETURN output into `calculate_weight_vbytes` (e.g., include `data` in the sizing transaction's `output` vector alongside `payments` and `change`), or compute vbytes over the actual `tx_outs` list so the fee, the minimum-relay check, and the change amount all reflect the true serialized transaction.

### Proof of Concept
```rust
// 1 input of 10_000 sats, one payment, change, and an 80-byte OP_RETURN payload.
let tx = SignableTransaction::new(
    vec![input],                 // ReceivedOutput worth 10_000 sats
    &[(payment_script, 5_000)],
    Some(change_script),
    Some(vec![0u8; 80]),
    MIN_FEE_PER_VBYTE,           // e.g., 1 sat/vbyte
).unwrap();

// The real transaction contains 3 outputs (payment, OP_RETURN, change),
// but `needed_fee` was priced for 2 outputs (payment + change).
let real_vsize = tx.transaction().vsize() as u64;      // includes OP_RETURN
let priced_fee = tx.needed_fee();                      // missing ~89 bytes of weight

// Effective rate < requested rate:
assert!(tx.fee() < real_vsize * MIN_FEE_PER_VBYTE);
// With MIN_FEE_PER_VBYTE at the relay minimum, the TX falls below
// DEFAULT_MIN_RELAY_TX_FEE and is rejected by send_raw_transaction,
// despite the TooLowFee guard having passed.
```
