### Title
Leftover change below the dust threshold is silently burned as miner fee and never returned to the Serai wallet's users, while `prepare_send` still amortizes that loss (and operating costs) out of user payments - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs), [File: processor/src/networks/mod.rs](processor/src/networks/mod.rs))

### Summary
Analogous to the Periphery report (where excess PT/YT tokens remained in the contract after `combine` instead of being returned), Serai's Bitcoin pipeline computes a change amount that frequently cannot be returned on-chain. `SignableTransaction::new` silently drops the change output whenever the leftover is below `DUST`, converting the entire remainder into fee. The fee estimator, however, always prices a change output in, so `prepare_send` reduces user payments by a fee the transaction never needs, and the non-returned surplus — including operating costs that were supposed to be "recouped" via change — is paid to miners instead.

### Finding Description

`SignableTransaction::new` only appends a change output if the leftover after paying `fee_with_change` is `>= DUST`: [1](#0-0) 

If `0 < input_sat - payment_sat - fee_with_change < DUST`, no change output is created and the entire leftover becomes fee — there is no error, no flag, nothing propagated to the caller indicating funds were surrendered.

The fee used by the scheduler comes from `make_signable_transaction(..., calculating_fee = true)`, which replaces every payment amount with `DUST`: [2](#0-1) 

Because all payments are priced at dust during estimation, the leftover is always large, so the estimated `needed_fee` **always includes the vbytes of a change output**. In `prepare_send`, that fee — plus `operating_costs` — is subtracted from the users' payments: [3](#0-2) 

The assumption that these costs are recoverable is baked in: when `change.is_some()`, `operating_costs` is reset to `0` on the belief the change output recoups them: [4](#0-3) 

Only afterward does the code check the on-chain change, and if it is below dust it books `theoretical_change_amount` as a cost — but this uses the *pre-amortization* payment sum (`input - original_payments`), whereas the amount actually burned is `input - post_fee_payments - tx_fee = theoretical_change_amount + operating_costs`: [5](#0-4) 

So the real burn (`theoretical_change_amount + operating_costs`) exceeds the booked cost, and the mis-estimated fee itself (`fee_with_change` vs. the smaller change-less transaction) is also overpaid to miners. The "excess" — the would-be change plus amortized operating costs plus the change-output fee delta — is never returned to the pool's users, mirroring the Periphery issue where `min(ptBal, amountIn)` left residual tokens stranded in the contract.

### Impact Explanation
Every plan whose leftover lands in `(0, DUST)` after amortization permanently burns that value as fee. Additionally, user payments are reduced by `operating_costs` on the premise the change output returns them; when change is dropped, those funds are lost too, and the accounting under-reports the loss by exactly `operating_costs`. Per-incident loss is bounded by roughly `DUST + operating_costs + change-output fee overhead`, making this a recurring, user-fund-draining Medium-severity leak rather than a one-time loss. It also breaks the invariant that a change address in the plan means leftover value returns to Serai's custody, which downstream accounting (`post_fee_branches`, `operating_costs`) relies on.

### Likelihood Explanation
The leftover equals `sum(inputs) - sum(payments) - fee`, a continuous function of attacker-influenceable payment amounts and UTXO sizes. Any user requesting a withdrawal whose remainder after fees falls below the dust threshold (330 sats for P2TR) triggers the silent burn. This is a routine, reachable condition — it requires only that the protocol operate with typical UTXO/payment sizes — analogous to the Periphery case where non-equal PT/YT balances are the norm, not the exception.

### Recommendation
In `SignableTransaction::new`, surface the dropped-change condition (e.g., return the leftover amount or a `ChangeDropped` flag) instead of silently converting it to fee. In `prepare_send`, reconcile accounting against the actual transaction outputs (e.g., via `SignableTransaction::fee()` vs. `needed_fee()`) rather than the pre-amortization `theoretical_change_amount`, and do not zero out `operating_costs` until a change output is confirmed present in the built transaction. Alternatively, reduce the final payment to absorb a sub-dust leftover only up to the amount already amortized, or carry the remnant forward into the next plan's change.

### Proof of Concept
1. Construct a `Plan` with `change = Some(addr)`, inputs summing to `I`, and payments summing to `P` such that `0 < I - P - fee_with_change < DUST`.
2. `prepare_send` calls `needed_fee`, which uses `calculating_fee = true`; with payments priced at `DUST`, the estimator at `send.rs:224-235` always sees leftover `>= DUST` and reports `needed_fee = fee_with_change`.
3. Amortization reduces payments by `tx_fee + operating_costs` (`mod.rs:461-494`) and resets `operating_costs` to `0` (`mod.rs:544`).
4. The real `SignableTransaction::new` call computes `value = I - P_post_fee - fee_with_change < DUST`, so no change output is pushed (`send.rs:228-234`).
5. The signed transaction's actual fee is `I - P_post_fee = tx_fee + (theoretical_change_amount + operating_costs)`; the would-be change and the amortized operating costs go to miners, while `mod.rs:589-590` books only `theoretical_change_amount`, under-recording the loss. Test scaffolding in `networks/bitcoin/tests/wallet.rs:209-288` demonstrates the change path and can be adapted: choose input/payment values so `change_amount < DUST`, and observe `tx.output` contains no change while `fee() > needed_fee` for the change-less size.
