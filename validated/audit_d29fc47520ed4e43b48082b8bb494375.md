## Title
Escrow release/refund can be permanently bricked by tokens whose balance can drift downward after escrow (dynamic-balance/rebasing tokens) — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` snapshots the *actual* received balance only once, at `placeOrder` time, to build the escrow ledger `_orders[commitment][token]`. From that point until the cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered — an interval with no upper bound guaranteed by the protocol beyond the order deadline plus relayer availability — the contract assumes the token balance it holds stays static. If the escrowed token's balance can decrease on its own after deposit (any dynamic-balance/rebasing/interest-accruing ERC20 whose `balanceOf` is not solely driven by explicit `transfer` calls the gateway controls), `_withdraw` will try to pay out a fixed nominal `amount` that the contract no longer actually holds, causing the payout transaction to revert and permanently stranding the escrow — the exact "recorded balance deviates from actual dynamic balance" defect described in the wibBTC report, transplanted onto Hyperbridge's intent-escrow custody model.

### Finding Description
`placeOrder` explicitly measures actual balance deltas to cope with balance-changing tokens **at deposit time**: [1](#0-0) 

This produces the ledger entry `_orders[commitment][token]` that is trusted verbatim later — no live balance is ever re-checked again. `_withdraw` (shared by redeem, refund, and partial-fill paths) decrements the ledger and then unconditionally calls `safeTransfer`/`call` for the recorded `amount`: [2](#0-1) 

The recorded `amount` is baked into the `WithdrawalRequest` and ultimately into the order `commitment` hash, so it cannot be adjusted downward later without breaking commitment integrity — there is no re-measurement step analogous to the one in `placeOrder`. The Tron variant shows the identical pattern, just with a plain low-level `call` that also reverts the whole `onAccept` on transfer failure: [3](#0-2) 

`_withdraw`/`withdraw` is only reachable through `onAccept`, which is `onlyHost` and processes an inbound ISMP `RedeemEscrow`/`RefundEscrow` message that can arrive an unbounded amount of time after `placeOrder` (bounded only loosely by `order.deadline`, and cancellation/timeout flows also route through the same `_withdraw`): [4](#0-3) 

If the input token's `balanceOf(gateway)` can fall below the amount recorded at deposit time during that window — e.g. a negative-rebasing token, an interest-bearing wrapper that can mark down on adverse yield/slashing, or any ERC20 whose balance is not a pure function of explicit transfers into/out of the gateway — the `IERC20.safeTransfer(beneficiary, amount)` call in `_withdraw` reverts because the contract no longer holds enough tokens. Since this call happens inside `onAccept`, the entire inbound message processing reverts. There is no fallback path that pays out the actually-available (lower) balance instead: the amount is fixed by the commitment, and `_orders[commitment][token]` cannot be topped up by anyone.

This is the direct Hyperbridge analog of the wibBTC/Curve bug: the pool (escrow) records a static balance for an asset whose real balance is dynamic and can diverge from what was recorded, and the code path that depends on the recorded value (`_withdraw`) has no mechanism to reconcile the discrepancy — except here divergence causes an outright revert/lock rather than a silent mispricing, which is a stronger failure mode (total fund lock rather than partial value leakage).

### Impact Explanation
When the escrowed token balance drops below the ledger's recorded amount before the redeem/refund message lands, the beneficiary (either the solver who is owed redemption, or the user who is owed a refund) can never receive their funds through the intended path: `onAccept` will keep reverting on every delivery attempt of that specific `WithdrawalRequest`, since the amount is fixed by the commitment hash. This is a genuine, unrecoverable loss/lock of user or solver funds triggered purely by ordinary token behavior — no malicious relayer, prover, or admin action is required.

### Likelihood Explanation
Likelihood depends on whether any token registered/used with `IntentGatewayV2` can have its balance decrease automatically post-escrow (negative rebase, slashing-adjusted wrapped tokens, interest-bearing tokens with negative accrual, etc.). Given the intent gateway is designed to be permissively token-agnostic (as evidenced by the fee-on-transfer accommodation already built into `placeOrder`), and cross-chain settlement latency is externally determined (relayer availability, destination chain finality), the exposure window is realistic and not attacker-controlled — meaning this is a passive, self-triggering vulnerability rather than requiring an attacker to engineer conditions.

### Recommendation
- At `_withdraw` time, clamp the outgoing transfer to `min(recorded amount, actual balanceOf(this))` for each token, and reconcile the shortfall via an explicit, auditable deficit-tracking mechanism rather than reverting the whole message.
- Alternatively, restrict registrable/eligible input tokens to those with balance-stability guarantees (no negative rebasing / no external balance mutation), and document this constraint explicitly for integrators.
- Add a governance-gated recovery path (distinct from `SweepDust`) specifically for stuck `WithdrawalRequest`s whose recorded amount now exceeds actual balance, so funds are not permanently unrecoverable.

### Proof of Concept
1. Register/accept a hypothetical negative-rebasing ERC20 `RBT` as an order input token (nothing in `placeOrder`/`IntentsBase` rejects such tokens).
2. User calls `placeOrder` with `RBT` as an input; `_orders[commitment][RBT]` is set to the actually-received amount (e.g., 1000 `RBT`), matching the balance the gateway holds at that instant — see `evm/src/apps/IntentGatewayV2.sol:282-298`.
3. Before the cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered (this window is entirely a function of relayer timing/chain finality, not attacker-controlled), `RBT`'s rebase mechanism reduces every holder's balance, including the gateway's, so `RBT.balanceOf(gateway)` is now less than 1000 (e.g., 950).
4. The relayer delivers the `RedeemEscrow`/`RefundEscrow` message; `onAccept` → `_withdraw` attempts `IERC20(RBT).safeTransfer(beneficiary, 1000)` per `evm/src/apps/intentsv2/IntentsBase.sol:403-408`.
5. The transfer reverts because the gateway only holds 950 `RBT`; the whole `onAccept` call reverts. Because the withdrawal amount is fixed by the commitment hash, no retry with a corrected (lower) amount is possible — the escrow for this order is permanently unredeemable/unrefundable, matching the wibBTC-style "recorded balance ≠ actual dynamic balance" failure but manifesting as a hard fund lock instead of a silent mispricing.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
