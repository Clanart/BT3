Based on the evidence gathered, the strongest local analog to the PoolTogether `setHooks` bug class (arbitrary, unprivileged, uncapped-gas external call auto-executed during a fund-moving flow) is in the Hyperbridge intents pipeline, in `CallDispatcher.dispatch()` combined with `IntentsBase._execute()`.

### Title
Unrestricted `CallDispatcher.dispatch()` lets order-creator-controlled calldata self-invoke the dispatcher and drain in-flight settlement funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever, and `IntentsBase._execute()` feeds it fully attacker-controlled calldata (`order.output.call`, set by the order creator at placement time) during order settlement, before the post-execution "dust sweep" runs. Because a `Call` entry inside that attacker-controlled batch can target the `CallDispatcher` contract itself, the order creator can instruct the dispatcher to call `dispatch()` on itself again with a second, self-authored batch that transfers out whatever token/native balance the dispatcher is holding at that moment — including tokens the solver just deposited into the dispatcher to fulfill the order for the beneficiary.

### Finding Description
`CallDispatcher.dispatch()` executes an arbitrary `Call[]` with no access control: [1](#0-0) 

`IntentsBase._execute()` invokes this dispatcher with `order.output.call` — calldata that is part of the `Order` struct set unilaterally by the (unprivileged) order creator at `placeOrder` time — automatically, as part of settlement, and only sweeps residual dispatcher balances back to the gateway *after* that arbitrary call completes: [2](#0-1) 

The documentation confirms the intended pattern is for solvers/output tokens to be routed *through* the shared `CallDispatcher` (`to` set to the dispatcher address) so downstream calls in the batch can spend them: [3](#0-2) 

Because the dispatcher is a single shared, address-persistent contract used across orders/gateways (also referenced from the intent-gateway docs and Tron deployment scripts) and `dispatch()` performs no reentrancy lock and no `msg.sender`/caller check, a `Call` inside `order.output.call` whose `to` is the dispatcher's own address and whose `data` is `dispatch(maliciousCalls)` is fully valid per `CallDispatcher`'s logic: it only checks `extcodesize(to) != 0` and that each sub-call succeeds, exactly the same "arbitrary external call with unbounded gas and no state-change protection" pattern the referenced report flags for `Vault.setHooks`/`beforeClaimPrize`. This lets the order creator (an unprivileged party, exactly like the PoolTogether hook-setter) redirect any token balance sitting in the dispatcher mid-settlement — including the solver's just-delivered output tokens — before `_execute`'s own sweep-and-accounting step runs.

### Impact Explanation
This maps directly to the bounty's "unauthorized transaction or execution" / "transaction manipulation" / "stealing or loss of funds" categories: an order creator can author `order.output.call` such that solver-delivered output tokens intended for the order's `beneficiary` are diverted to an address of the order creator's choosing via a self-reentrant `dispatch()` call, instead of reaching the beneficiary or being correctly swept as protocol dust. No relayer, prover, or admin compromise is required — the order creator is an ordinary, unprivileged user interacting with the public `placeOrder`/settlement path.

### Likelihood Explanation
High: `order.output.call` is attacker-supplied data at order-placement time with no validation of its target addresses, `CallDispatcher.dispatch()` is a public entrypoint with zero access control, and `_execute()` calls it unconditionally whenever `order.output.call.length > 0`. No special network conditions, front-running, or malicious infrastructure participant is needed — the entire exploit is encoded once, at order creation, by the attacker themselves.

### Recommendation
- Add an access-control check to `CallDispatcher.dispatch()` restricting callers to the specific gateway/HFT contracts that are supposed to invoke it, and/or add a reentrancy guard so a call within a dispatch batch cannot re-enter `dispatch()`.
- In `IntentsBase._execute()`, validate/whitelist the `to` addresses inside `order.output.call` to disallow targeting the dispatcher itself (or the gateway), or snapshot and diff balances strictly attributable to the current order rather than sweeping the dispatcher's *entire* current balance.
- Consider deploying a fresh, single-use `CallDispatcher` (or an isolated escrow sub-account) per settlement rather than a long-lived shared singleton, mirroring PoolTogether's mitigation direction of bounding what an externally-supplied "hook"/calldata payload can reach.

### Proof of Concept
1. Order creator places an order via `placeOrder` with `order.output.call` ABI-encoding a `Call[]` where one entry is `Call({to: address(callDispatcher), value: 0, data: abi.encodeWithSelector(ICallDispatcher.dispatch.selector, abi.encode(stealCalls))})`, with `stealCalls` transferring the output token's full balance from the dispatcher to an attacker-controlled address.
2. A solver fills the order, sending the required output tokens to the `CallDispatcher` address (per the documented "set `to` to the CallDispatcher" pattern) as part of fulfilling `order.output.assets`.
3. `IntentsBase._execute()` calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`; inside that batch, the nested `dispatch()` call fires with the attacker's `stealCalls`, transferring out the solver's just-delivered tokens before `_execute`'s own post-call sweep loop runs.
4. `_execute`'s subsequent balance check for `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` now finds nothing (already drained), so no dust event or beneficiary payout reflects the loss — the beneficiary never receives the intended output, while the order is still finalized as filled via `_withdraw`.

Note: I was not able to view the full `IntentGatewayV2.sol` `fillOrder` function (only grep hits for `nonReentrant`) within available tool budget, so I cannot fully confirm or rule out whether an outer `nonReentrant` modifier on `fillOrder` blocks a second entry into `fillOrder` itself — however, this does not affect the finding above, since the exploit path does not re-enter `fillOrder`; it re-enters `CallDispatcher.dispatch()` directly, which carries no reentrancy protection of its own.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
