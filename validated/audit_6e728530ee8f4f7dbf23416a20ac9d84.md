### Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows unauthenticated remote denial of service via recursively nested AccountKey shapes - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each embedded role-key byte slice through `AccountKeySerializer.DecodeRLP`, without any check that the decoded key type is itself non-composite. If a decoded role key's type is `AccountKeyTypeRoleBased`, the decode recurses into `AccountKeyRoleBased.DecodeRLP` again. Since the only place that rejects a nested composite key (`ErrNestedCompositeType`) is `CheckInstallable`/`CheckUpdatable`, which runs *after* RLP decoding completes, an attacker can craft an `AccountUpdate`-type transaction whose account-key payload is deeply, self-similarly nested and cause uncontrolled Go-stack recursion during decode, mirroring the smithy-rs recursive-shape deserialization bug class (CVE-2026-15957).

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte-strings and, for each one, calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is an `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type, allocates the concrete key via `NewAccountKey`, and calls `s.Decode(serializer.key)` — if that concrete key is again `AccountKeyRoleBased`, this recurses into the function above: [2](#0-1) 

There is no depth check anywhere in this decode path. The only rejection of composite-in-composite nesting (`kerrors.ErrNestedCompositeType`) happens in `CheckInstallable`/`CheckUpdatable`, which are semantic checks executed *after* the RLP decode has already fully completed (or crashed): [3](#0-2) [4](#0-3) 

A dedicated regression test confirms nested `RoleBased` keys are semantically rejected only at the tx-pool/state-transition validation stage (`ErrNestedCompositeType`), i.e., after the transaction (and its account key) has already been RLP-decoded: [5](#0-4) 

Because each recursion level consumes an RLP list/string header (minimum ~2–3 bytes of overhead) but decoding depth is otherwise unbounded, an attacker controls recursion depth directly via input size: a transaction payload of moderate size (tens to low hundreds of KB) can encode thousands of nesting levels of `AccountKeyRoleBased → AccountKeySerializer → AccountKeyRoleBased → ...`, each adding Go call frames (`DecodeRLP` → `rlp.DecodeBytes` → `Decode` → `DecodeRLP` ...) before any composite-type check is reached.

### Impact Explanation
This is reachable by any unauthenticated party who can submit a transaction to the network: an `AccountUpdate` or `FeeDelegatedAccountUpdate`(WithRatio) transaction whose `AccountKey` field is RLP-encoded with deeply nested `AccountKeyRoleBased` values. Decoding such a transaction (e.g. via `eth_sendRawTransaction`/`klay_sendRawTransaction`, p2p tx propagation, or block processing) triggers unbounded Go-stack recursion in the RLP decoder, which can exhaust the goroutine stack and crash (`fatal error: stack overflow`, unrecoverable via `recover()`) the node process handling the transaction — a straightforward, low-cost, unauthenticated remote denial-of-service against any public-RPC node, transaction-pool node, or validator that decodes the malicious transaction.

### Likelihood Explanation
Likelihood is high: it requires only a single crafted transaction (no valid signature is strictly required to trigger the decode path itself, since decoding of the account key precedes signature verification in transaction ingestion), can be submitted via any public RPC endpoint, and needs no special privileges, staking, or prior state.

### Recommendation
Add an explicit recursion/nesting-depth guard in `AccountKeyRoleBased.DecodeRLP` (and generally in `AccountKeySerializer.DecodeRLP`) that rejects a decoded key whose `Type()` is `AccountKeyTypeRoleBased` (or otherwise composite) immediately during decode, rather than deferring the check to `CheckInstallable`/`CheckUpdatable`. Alternatively, track and enforce a maximum decode-recursion depth in the RLP `Stream`/decoder framework itself (analogous to smithy-rs's fix), so that any recursively-defined shape (not just `AccountKeyRoleBased`) is bounded independent of downstream semantic validation.

### Proof of Concept
Conceptually:
1. Build an `AccountKeySerializer` for `AccountKeyTypeRoleBased` whose single "role key" byte-string is itself the RLP encoding of another `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, and repeat this nesting N times (e.g., N = 50,000), each level minimally sized.
2. Wrap this in an `AccountUpdate` (or `FeeDelegatedAccountUpdate`) transaction's `AccountKey` field and RLP-encode the full transaction.
3. Submit the raw transaction via `eth_sendRawTransaction`/`klay_sendRawTransaction` to a node, or gossip it over p2p.
4. The node calls `rlp.DecodeBytes`/`Transaction.DecodeRLP` → ... → `AccountKeyRoleBased.DecodeRLP`, which recurses N times before `CheckInstallable`/`CheckUpdatable` is ever invoked, exhausting the stack and crashing the process.

Note: I was not able to fully trace the exact byte-size/tx-size caps enforced before RLP decoding begins (e.g., `blockchain/tx_pool.go`'s size checks were only partially inspected due to tool-call limits), so the precise minimum transaction size needed to reach a crash-inducing recursion depth is not confirmed and would need empirical verification.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
