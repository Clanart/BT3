### Title
Excess native value sent to `EvmHost.dispatch()` for fee-swaps is permanently lost, not refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the direct Hyperbridge analog of the C4 "Possible lost msg.value" report: any contract or user that pays Hyperbridge dispatch fees in native token and slightly overpays loses the excess forever, because the Uniswap V2 refund goes to the wrong party.

### Finding Description
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept payment for cross-chain message fees either in the fee ERC20 token or in native currency. When `msg.value > 0`, the host swaps the incoming native value for an exact amount of fee token via Uniswap V2: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        ...
```

The same pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

The canonical `UniswapV2Router02.swapETHForExactTokens` implementation refunds any unused ETH (`msg.value - amounts[0]`) to `msg.sender` — but in this call chain, `msg.sender` from the router's perspective is `EvmHost` itself (`address(this)` calling the router with `{value: msg.value}`), **not** the original depositor who funded the transaction (e.g. `IntentGatewayV2`, `WrappedHyperFungibleToken`, or any `HyperApp` consumer). This is structurally identical to the C4 finding's core defect: a payable entrypoint accepts `msg.value` without validating it equals the exact required amount, and any surplus is misdirected instead of refunded to the payer.

Every upstream caller that forwards native value for fee payment inherits this defect because none of them compute the exact Uniswap-quoted amount at call time — they only cap `msgValue` to the caller-supplied amount and forward it wholesale: [3](#0-2) [4](#0-3) 

In `WrappedHyperFungibleToken.send()`, the developer docs explicitly instruct users to pre-compute `nativeFee` via `quote()` and send `amount + nativeFee`, but between the `quote()` call and the on-chain `send()` execution, Uniswap V2 reserves can shift (any pending swap in the same block/mempool, or simply AMM price drift) such that less ETH is actually needed to obtain `post.fee` fee-tokens. Any such delta is not refunded to the `WrappedHyperFungibleToken` contract or the end user — it is absorbed into `EvmHost`'s own ETH balance via the router's `msg.sender`-based refund, with no code path returning it to the depositor.

### Impact Explanation
This causes an unprivileged user (or any `HyperApp` on behalf of its users) to permanently lose native-token value on every dispatch call where the exact fee-swap input amount is even slightly less than the value forwarded — a routine, unprivileged occurrence given AMM price volatility between quote-time and execution-time. The lost funds accumulate in `EvmHost`'s native balance with no user-facing withdrawal path, matching the bounty's "loss of funds" impact class exactly, since the value moves to an unintended beneficiary (the host contract) rather than being returned to the rightful payer.

### Likelihood Explanation
High likelihood: this triggers on the ordinary, documented usage flow (quote-then-send with native fee) any time the AMM price moves favorably between the `quote()` call and the `send()`/`dispatch()` transaction, requiring no malicious relayer, prover, or admin — only normal market conditions or MEV/latency between quoting and execution.

### Recommendation
After the `swapETHForExactTokens` call, capture the returned `amounts[0]` (actual ETH consumed) and refund `msg.value - amounts[0]` to `_msgSender()` (the original caller of `dispatch`, i.e., the app contract) rather than relying on the router's own refund semantics, which targets the immediate caller of the router (`EvmHost`) instead of the ultimate depositor. Equivalently, require exact-value equality (`require(msg.value == quotedFee)`) before performing the swap, consistent with the C4 recommendation to validate `msg.value` strictly against the expected amount rather than silently absorbing any surplus.

### Proof of Concept
1. `WrappedHyperFungibleToken` or `IntentGatewayV2` (or any custom `HyperApp`) computes `nativeFee` via `quote()` and calls `IDispatcher(host).dispatch{value: nativeFee}(request)`.
2. Between quoting and the transaction being mined, the Uniswap V2 `WETH/feeToken` pool reserves shift slightly (a common, permissionless, unprivileged occurrence), such that `amounts[0] < nativeFee` is now sufficient to obtain `post.fee` fee tokens.
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: nativeFee}(post.fee, path, address(this), ...)` executes; the router refunds `nativeFee - amounts[0]` ETH to its immediate caller, `EvmHost` (`address(this)`).
4. The refunded dust is added to `EvmHost`'s native balance permanently; the original depositor (app contract/user) never receives it back, and no function in `EvmHost.sol` exposes this residual balance to depositors. [1](#0-0)
