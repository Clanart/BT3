### Title
`GetStakingInfo` halts block processing chain-wide if any single CL pool or AddressBook read reverts - (File: kaiax/staking/impl/getter.go)

### Summary
`StakingModule.getFromState` performs a single aggregate on-chain read (`MultiCallStakingInfo` / `MultiCallStakingInfoPermissionless` and, since Prague, `MultiCallDPStakingInfo` for consensus-liquidity pools) and propagates *any* failure of these calls as a hard error out of `GetStakingInfo`. Since `GetStakingInfo` is a mandatory input to every block's reward computation and validator-set determination, one bad/broken read (analogous to the reported Vault case where one broken market blocks `settle`/`update` for the whole vault) blocks staking-info retrieval for the *entire* validator set on *every* block, not just the offending node.

### Finding Description
`GetStakingInfo` reads a single combined snapshot for all validators through the `MultiCallContract` and returns whatever error the EVM call to system/CL contracts yields: [1](#0-0) 

Specifically:
- If `MultiCallStakingInfo`/`MultiCallStakingInfoPermissionless` fails, the function returns `staking.ErrAddressBookCall(err)` and aborts — no partial result is produced for the other, unaffected validators.
- If `MultiCallDPStakingInfo` (aggregating CL pool balances via the CLRegistry, added for KIP-226 consensus liquidity) fails, `staking.ErrCLRegistryCall(err)` is returned and again aborts the whole `GetStakingInfo` call, even though the CL failure concerns only one validator's optional consensus-liquidity pool.

This mirrors the reported pattern precisely: instead of iterating per-market/per-validator and skipping/reporting the broken one, the code aggregates everything into one call whose failure poisons the result for all participants. Since consensus liquidity pools (`CLPool`) are external contracts associated with individual validators/stakers (registered via the CLRegistry, KIP-226), a staker who registers a pool that reverts on read (e.g. `balanceOf`) — whether due to a bug, upgrade, or deliberate self-sabotage/griefing — would make `MultiCallDPStakingInfo` revert for *every* node, not just their own.

`GetStakingInfo` is consumed by both reward calculation (`kaiax/reward`) and validator set determination (`kaiax/valset`), both required for `FinalizeState`/block processing on every node, so an error here is not merely a getter failure — it can propagate into block execution failure.

### Impact Explanation
If any single validator's registered CL pool (or in general, any account read via the aggregate MultiCall) is broken/reverting, `GetStakingInfo` fails entirely, which blocks reward computation and validator-set resolution for **all** validators on **every** block that needs that StakingInfo (not just the block belonging to the offending staker). This is a liveness-affecting bug for block processing/finalization across the whole network, analogous in class to the referenced Vault issue (one broken component blocks the shared aggregate operation for everyone).

### Likelihood Explanation
Reaching this requires a validator/staker to register (or have registered) a CL pool contract at the `CLRegistry` whose view functions revert when queried by `MultiCallDPStakingInfo`. I was **not able to fully verify** the exact registration/permission model of the production `CLRegistry` contract (only mock contracts — `contracts/testing/reward/CLRegistryMock.sol` — were found in the indexed code; the real `CLRegistry` implementation referenced by KIP-226 was not present in the indexed files). Whether CL pool registration is fully permissionless for any staker, or gated by validator-manager-only access, could not be confirmed with the available index. This uncertainty materially affects whether the "one broken market" analog is reachable by an ordinary staker versus requiring a validator-privileged action, so likelihood should be treated as uncertain pending manual review of the real `CLRegistry` contract (outside the indexed set).

### Recommendation
- In `getFromState`/`readCLInfo` (kaiax/staking/impl/getter.go), do not let a single failing CL-pool read (or any single validator's staking-address read) abort the aggregate `StakingInfo` computation for the whole validator set. Consider per-node fault isolation: catch/skip an unreadable CL entry (treat its CL staking amount as zero and log/alert) rather than propagating `ErrCLRegistryCall`/`ErrAddressBookCall` and failing the entire call.
- Alternatively, harden the `MultiCallContract`'s aggregate view functions to use low-level calls with try/catch (`staticcall` + return-data length checks) per external target instead of composing multiple external calls that all fail together on one revert.

### Proof of Concept
Not independently reproducible from the indexed code alone because the real `CLRegistry` contract implementation (registration/permission logic and the pool balance-read logic invoked by `multiCallDPStakingInfo`) is not present in the index — only mocks (`contracts/testing/reward/CLRegistryMock.sol`) were found. Conceptually, the failure mode is directly demonstrated by the code path: [2](#0-1)  — any revert from `contract.MultiCallDPStakingInfo(callOpts)` (e.g., a CL pool whose `balanceOf`-like function reverts) causes `GetStakingInfo` to return an error for the entire chain state at that block, blocking reward/validator computations for all validators, not just the one associated with the broken pool.

	contract, err := system.NewMultiCallContractCaller(statedb, s.Chain, header)
	if err != nil {
		return nil, staking.ErrMultiCallCall(err)
	}

	callOpts := &bind.CallOpts{BlockNumber: header.Number}

	// Helper to read CL registry info, shared by permissioned and permissionless paths.
	// Permissionless is ordered after Prague (Randao <= Kaia <= Prague <= Permissionless),
	// so permissionless blocks always need CL registry info too.
	readCLInfo := func() (clRegistryResult, error) {
		var clRes clRegistryResult
		// If Registry is not installed, do not handle CL staking info.
		// In private network, Randao and Prague hardfork can be activated at the same block.
		// It leads to staking info inconsistency between block processing and rpc query since the Registry hasn't been installed when finalizing the header.
		// Note that Randao can't be activated after Prague according to fork ordering (Randao <= Kaia <= Prague).
		if statedb.GetCode(system.RegistryAddr) == nil || s.ChainConfig.IsRandaoForkBlockParent(header.Number) {
			logger.Trace("Registry not installed", "sourceNum", num)
			return clRes, nil
		}
		// Note that if CLRegistry is not registered in Registry,
		// it will return empty result and no error.
		clRes, err = contract.MultiCallDPStakingInfo(callOpts)
		if err != nil {
			return clRes, staking.ErrCLRegistryCall(err)
		}
		return clRes, nil
	}

	// Permissionless: read from AddressBookV2 (effective stake, reward-eligible only).
	if isForPermissionless {
		res, err := contract.MultiCallStakingInfoPermissionless(callOpts)
		if err != nil {
			return nil, staking.ErrAddressBookCall(err)
		}
		clRes, err := readCLInfo()
		if err != nil {
			return nil, err
		}
		return parsePermissionlessCallResult(num, res.Profiles, res.StakingAmounts, res.KefAddr, res.KifAddr, res.KpfAddr, clRes)
	}

	// Permissioned: read from legacy AddressBook.
	abRes, err := contract.MultiCallStakingInfo(callOpts)
	if err != nil {
		return nil, staking.ErrAddressBookCall(err)
	}

	var clRes clRegistryResult
	if isForPrague {
		clRes, err = readCLInfo()
		if err != nil {
			return nil, err
		}
	}
