### Title
Payout OP_RETURN attribution is unauthenticated and can be rewritten by anyone via RBF replacement, letting an attacker credit reimbursement to an operator who never funded the payout - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds a 0-sat OP_RETURN output carrying the operator's xonly pubkey with no signature over it, and the only signature on the payout tx (the withdrawer's `SinglePlusAnyoneCanPay`) covers only the withdrawal input and output index 0 [1](#0-0) . Because the funded tx that operators broadcast is explicitly signaled RBF-replaceable and processed with Bitcoin Core's `psbtbumpfee`/`fund_raw_transaction` workflow [2](#0-1) , an attacker who sees the unconfirmed payout tx in the mempool can replace its funding inputs and OP_RETURN output with arbitrary values (any xonly pubkey, including an existing operator's) while keeping the same withdrawal input and its still-valid signature. `update_finalized_payouts` then blindly parses whatever OP_RETURN ends up confirmed on-chain and records it as the "payer" with no check that the attributed operator actually supplied any funding UTXO [3](#0-2) .

### Finding Description
Claimed binding: `payout_payer_operator_xonly_pk` (written by `update_finalized_payouts`) == the operator whose own Bitcoin funds actually paid the withdrawal fronting amount.

Code path:
1. `create_payout_txhandler` signs only input 0 (the withdrawal UTXO) with the user's key-spend witness (`SinglePlusAnyoneCanPay`) and appends an OP_RETURN output containing the calling operator's xonly pubkey with **no signature of any kind** over that output [4](#0-3) .
2. `Operator::withdraw` funds this template via `fund_raw_transaction` (own wallet) and hands it to the RBF sender [5](#0-4) .
3. `TxSender`'s RBF path explicitly marks the funded PSBT `replaceable: Some(true)` and reuses `psbtbumpfee`-style bumping [2](#0-1) , so the broadcast transaction opts into standard BIP-125 replacement.
4. Because `TapSighashType::SinglePlusAnyoneCanPay` on input 0 commits only to input 0 and output 0 (`Prevouts::One`) [6](#0-5) , any third party can build a *new* transaction spending the same withdrawal outpoint with the identical signature, dropping the original operator's funding inputs/OP_RETURN and substituting their own funding inputs and any OP_RETURN payload (an arbitrary xonly pubkey), then relay it with a higher fee so it replaces the original in mempools/miners.
5. Once this substituted transaction confirms, `update_finalized_payouts` parses whatever pubkey sits in the first OP_RETURN output and writes it as `payout_payer_operator_xonly_pk`, with no cross-check that this operator's own UTXOs paid anything [3](#0-2) .
6. The attributed operator's `PayoutCheckerTask` filters unhandled payouts strictly by its own key from the DB (already trusting the OP_RETURN) and unconditionally calls `handle_finalized_payout` to build a kickoff and claim reimbursement [7](#0-6) .
7. The only consistency checks that exist — `send_asserts`'s `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` [8](#0-7)  and verifier's `is_kickoff_malicious` `operator_xonly_pk != kickoff_data.operator_xonly_pk` [9](#0-8)  — only verify that the OP_RETURN-recorded pubkey matches the pubkey declared in the kickoff. Since the attacker's forged OP_RETURN can be set to the exact pubkey of whichever operator the attacker chooses, both checks pass trivially; neither checks that the funding UTXOs behind the confirmed payout tx were actually spent by that operator's wallet.

### Impact Explanation
The attribution field that gates who is allowed to be reimbursed from bridge collateral can be forged by anyone with the ability to see the mempool and pay a competitive fee, with no cryptographic tie to the actual funding inputs. This directly enables:
- **An operator reimbursed for a payout it never funded** (Critical): attacker funds the withdrawal themselves but stamps another operator's pubkey in the OP_RETURN; that operator's automation later claims a Reimburse tx from the round transaction for money it never spent.
- **An honest operator permanently unable to be reimbursed** (Critical): if an attacker front-runs/replaces an honest operator's already-broadcast, unconfirmed payout tx with a version carrying garbage/invalid OP_RETURN bytes, `update_finalized_payouts` records `NULL` payer, and no operator's presigned kickoff can ever be matched to that payout, permanently orphaning that fronting.

This is repeatable per withdrawal, requires no verifier/operator privileges, and its blast radius spans every withdrawal for which the payout tx has not yet reached sufficient confirmations before an attacker can craft and relay a fee-competitive replacement.

### Likelihood Explanation
Preconditions are modest: the attacker needs to observe an unconfirmed, RBF-opted-in payout transaction (which `clementine-tx-sender` always constructs this way) and be able to relay a conflicting transaction with a higher fee — a capability explicitly granted to the modeled attacker ("anyone who can broadcast Bitcoin transactions and pay fees"). No key compromise, no majority hashrate, and no protocol-level access are required. The only cost is the marginal fee premium needed to win the RBF race, which is cheap relative to bridge withdrawal amounts. This is deployable against any withdrawal in the window between the operator's initial broadcast and its confirmation.

### Recommendation
Bind the OP_RETURN attribution to the funding inputs cryptographically instead of trusting unsigned bytes:
- Either require the operator's OP_RETURN pubkey to be committed inside the sighash of the withdrawal input itself (e.g., embed a commitment to the operator's pubkey in the message the user signs, so `SinglePlusAnyoneCanPay` effectively pins the fronting operator), or
- Require the fee/funding inputs used to complete the payout tx to be provably spent from that operator's registered collateral/identity key (e.g., have the operator co-sign a fee output/anchor with their operator key using `SIGHASH_ALL`, and have `update_finalized_payouts`/`is_kickoff_malicious` verify that signature rather than trusting the raw OP_RETURN bytes), and additionally disable RBF opt-in signaling once a valid attribution-committing payout tx has entered the mempool, or use presigned/committed funding UTXOs known to verifiers ahead of time.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
