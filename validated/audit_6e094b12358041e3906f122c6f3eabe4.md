### Title
Webhook HMAC verification does not bind the `X-Shopify-Shop-Domain` header, allowing cross-shop webhook spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates only the raw POST body of an incoming webhook via HMAC, but the `shop_domain` value that downstream application code uses to attribute the webhook to a specific merchant is read from an unauthenticated request header, never covered by the HMAC computation. This mirrors the root cause of the Balancer flash-loan finding: a caller-identity/authenticity check is performed (`msg.sender == _balancerVault` / valid `X-Shopify-Hmac-Sha256`), but a critical piece of the accompanying data (`originalCallData` / `X-Shopify-Shop-Domain`) is never validated against, or bound to, that authenticity check, so it can be swapped out independently.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes the expected signature only from `request.raw_post`: [1](#0-0) 

`ShopifyApp::WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)` and, separately, exposes a `shop_domain` helper that simply reads the `X-Shopify-Shop-Domain` request header — a value that is never part of the HMAC digest: [2](#0-1) 

The gem's own documentation instructs app developers building custom webhook controllers to trust this helper to scope work to "the" shop, once `verify_request` has passed: [3](#0-2) 

Because `shop_domain` is derived from a header outside the signed payload, the HMAC check only proves the *body* was signed with the app's client secret at some point — it proves nothing about which shop the request is currently claiming to be for. An attacker who has legitimately received one valid `(body, HMAC)` pair for their own shop (which is trivial — any merchant who installs the app can trigger webhooks against their own store, e.g. via `orders/create`) can replay that exact body and HMAC to the app's webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain`. `verify_request` will still pass (the HMAC only covers `raw_post`), and `shop_domain` will return the attacker-chosen value, exactly analogous to how the `BalancerFlashLender` case validates `msg.sender` while trusting an unvalidated payload to decide which "borrower"/action to run.

### Impact Explanation
Any custom webhook handler built on `ShopifyApp::WebhookVerification` (as documented in `docs/shopify_app/webhooks.md`) that uses `shop_domain` to look up/update a merchant's data, credit records, enqueue background jobs, or make Admin API calls "for that shop" can be tricked into performing that action against/on behalf of a different, victim shop, since the authenticity check (HMAC) and the attribution field (`shop_domain`) are not cryptographically bound together.

### Likelihood Explanation
Requires only an unprivileged/uninvolved actor who has installed the app on any shop (or otherwise obtained one valid signed webhook body/HMAC pair) and can send arbitrary HTTP requests to the webhook endpoint with modified headers — no special privileges, secrets, or dependency internals are needed beyond normal app installation.

### Recommendation
Include the shop-identifying header(s) (e.g., `X-Shopify-Shop-Domain`, `X-Shopify-Webhook-Id`, `X-Shopify-Topic`) as part of the data covered by the HMAC verification, or otherwise cryptographically bind the shop domain to the verified payload (e.g., derive/validate shop identity strictly from the signed body content rather than from an unauthenticated header) before exposing it via `shop_domain`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., creates an order), causing Shopify to POST a body `B` with a valid `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint.
2. Attacker captures `(B, H)` and replays the same POST to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `hmac_valid?(B)` in `payload_verification.rb` still succeeds because it only checks `B` against `H`.
4. Any custom controller/job using `shop_domain` (per `docs/shopify_app/webhooks.md` guidance) attributes/executes the webhook's effects against `victim-shop.myshopify.com` instead of the attacker's own shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
