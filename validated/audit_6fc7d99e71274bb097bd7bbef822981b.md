### Title
Loss of ERC721 tokens on `send_nft` due to use of `transferFrom` instead of `safeTransferFrom` in the EVM `HandleERC721TransferPayload` bridge - (File: x/evm/client/wasm/query.go)

### Summary
The CW721 wrapper contract's `send_nft`/`transfer_nft` execution path builds an EVM call payload via `HandleERC721TransferPayload`, which always packs the ERC721 `transferFrom(address,address,uint256)` selector rather than `safeTransferFrom`. This mirrors the reported bug class (unsafe `transferFrom` used where a safe transfer is semantically expected), and can permanently strand an ERC721 token if the resolved EVM recipient is a contract that does not implement `onERC721Received`.

### Finding Description
`x/evm/client/wasm/query.go`'s `HandleERC721TransferPayload` resolves the CW `from`/`recipient` bech32 addresses to their associated EVM addresses and ABI-encodes a plain `transferFrom` call against the underlying ERC721 contract: [1](#0-0) 

This payload is used by the CW721-wrapper-for-ERC721 contract's `transfer_nft` helper, which is invoked by both `execute_transfer_nft` and, critically, `execute_send_nft`: [2](#0-1) [3](#0-2) 

`send_nft` is the CW721 semantic analog of ERC721's `safeTransferFrom` — it is meant to be used when sending an NFT to a contract that should be notified/validated as capable of handling it (the CW721 side does emit a `Cw721ReceiveMsg` to the CW recipient, but the actual custody transfer on the EVM side of the underlying real ERC721 token uses the unsafe `transferFrom` selector, not `safeTransferFrom`). Since the recipient's EVM address is derived from Sei/EVM address association and can be any contract (including one instantiated without ever calling `onERC721Received`), the underlying ERC721 transfer bypasses the receiver-capability check entirely.

This is analogous to the audited `CollateralEscrowV1._withdrawCollateral` issue: an internal path forwards ERC721 custody to an arbitrary recipient using `transferFrom` instead of `safeTransferFrom`, with no verification that the recipient contract can handle ERC721 tokens.

### Impact Explanation
If a CW721-wrapped ERC721 token is transferred (via `transfer_nft` or `send_nft`) to a recipient EVM address that is a contract lacking `onERC721Received` support (or which reverts on unexpected transfers), the underlying real ERC721 token becomes permanently locked in that contract with no CW721/ERC721 method available to recover it (since the pointer/wrapper contract no longer holds a reference path back). This satisfies the "permanent freezing of funds" criterion for a valid Medium/High-severity finding.

### Likelihood Explanation
Any unprivileged CW721 message sender (e.g., a wallet or dApp interacting with the CW-wrapped ERC721 pointer contract) can trigger `send_nft`/`transfer_nft` to any Sei address, including one associated with a smart contract. No special privileges are required — this is reachable directly through a submitted CosmWasm execute message against the wrapper contract.

### Recommendation
Change `HandleERC721TransferPayload` (or add a dedicated safe-transfer payload handler) to ABI-encode `safeTransferFrom(address,address,uint256)` for the `send_nft` code path (and consider using it for `transfer_nft` as well, consistent with typical ERC721 wrapper safety practices), so that recipient contracts that cannot handle ERC721 tokens cause the transaction to revert instead of silently locking the asset.

### Proof of Concept
1. Deploy a real ERC721 contract and register the example CW721-wrapper contract (`example/cosmwasm/cw721`) pointing at it via `ERC721_ADDRESS`.
2. Deploy an arbitrary contract `C` on the EVM side that has no `onERC721Received` implementation, and associate `C`'s EVM address with a Sei address `SeiC` (via normal address association flow).
3. As the current CW721 wrapper token owner, execute `send_nft { contract: SeiC, token_id: X, msg: ... }` (or `transfer_nft { recipient: SeiC, token_id: X }`) against the wrapper contract.
4. The wrapper contract calls `querier.erc721_transfer_payload(...)`, which invokes `HandleERC721TransferPayload`, producing a raw `transferFrom(owner, C, X)` call, delegatecalled to the real ERC721 contract.
5. Because `transferFrom` (not `safeTransferFrom`) is used, the transfer succeeds unconditionally even though `C` cannot handle ERC721 tokens, permanently locking token `X` inside `C`.

```go
func (h *EVMQueryHandler) HandleERC721TransferPayload(ctx sdk.Context, from string, recipient string, tokenId string) ([]byte, error) {
	abi, err := cw721.Cw721MetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	fromEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(from))
	if !found {
		return nil, types.NewAssociationMissingErr(from)
	}
	toEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	t, ok := sdk.NewIntFromString(tokenId)
	if !ok {
		return nil, errors.New("invalid token ID for ERC721, must be a big Int")
	}
	bz, err := abi.Pack("transferFrom", fromEvmAddr, toEvmAddr, t.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
```

```rust
        .add_attribute("recipient", recipient)
        .add_attribute("token_id", token_id);
    Ok(res)
}
```

```rust
fn transfer_nft(
    deps: DepsMut<EvmQueryWrapper>,
    info: &MessageInfo,
    recipient: &str,
    token_id: &str,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(recipient)?;

    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let owner = querier.erc721_owner(info.sender.to_string(), erc_addr.to_string(), token_id.to_string())?.owner;
    let payload = querier.erc721_transfer_payload(owner, recipient.to_string(), token_id.to_string())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new().add_message(msg);

    Ok(res)
}
```
