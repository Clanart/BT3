### Title
Single-step tokenfactory denom admin transfer allows permanent loss of admin control - ([File: x/tokenfactory/types/msgs.go])

### Summary
`MsgChangeAdmin` in the `x/tokenfactory` module transfers admin rights over a denom in a single, unilateral step, mirroring the "No Transfer Of Ownership Pattern" reported in the external Y2K audit. The current admin can move the denom's admin authority to any syntactically valid bech32 address without any acceptance step from the new admin, and there is no way to recover if that address is unreachable, uncontrolled, or mistyped.

### Finding Description
`MsgChangeAdmin.ValidateBasic` only checks that `NewAdmin` parses as a valid bech32 address — it does not verify that the address is reachable or controlled by anyone: [1](#0-0) 

The keeper's `ChangeAdmin` message handler then immediately overwrites the denom's authority metadata with the new admin in one step, with the only extra guard being that the new admin differs from the current one: [2](#0-1) 

This is the same architectural flaw as `VaultFactoryV2.changeOwner()` in the referenced report: a privileged role is transferred via a single call with only a basic format/zero-address-style check, with no `acceptAdmin`/two-step handshake to confirm the nominee is a live, controlled account. Once the admin of a tokenfactory denom is set to a typo'd address, a burned/unrecoverable key, or any address whose private key the sender does not actually control, every admin-gated action for that denom — `Mint`, `Burn`, further `ChangeAdmin`, `UpdateDenom`, `SetDenomMetadata` — becomes permanently unreachable, since all of these are gated on `msg.Sender == authorityMetadata.GetAdmin()`: [3](#0-2) 

### Impact Explanation
Any tokenfactory denom creator/admin is one erroneous `MsgChangeAdmin` transaction away from irrecoverably losing all administrative control of their denom: they can never mint additional supply, never burn misdirected balances, never update the denom's allow list/metadata, and can never re-designate an admin, since `ChangeAdmin` itself requires being the current admin. This is a permanent, protocol-level freezing of denom administration that a normal unprivileged tokenfactory user can trigger on themselves with a single transaction (or be tricked into via a copy-paste/typo'd address), matching the "permanent freezing" acceptance criterion.

### Likelihood Explanation
Likelihood is non-trivial: address transposition errors, copy/paste mistakes, or use of a wrong-network/wrong-format address (that still happens to be valid bech32) are common human errors, and the module provides no safety net (no pending-admin/accept-admin step, no error/warning, no way to recover). Since this action is fully reachable by any ordinary token creator using standard `MsgChangeAdmin` transactions, no special privilege beyond being the current denom admin is required.

### Recommendation
Implement a two-step admin transfer for tokenfactory denoms, analogous to `Ownable2Step`: add a `nominateAdmin`/`ProposeChangeAdmin` step that stores a pending admin, and require a subsequent `AcceptAdmin` message signed by the nominee before `authorityMetadata.Admin` is actually updated. This guarantees the new admin address is live/controlled before authority is transferred, closing the freezing vector described above.

### Proof of Concept
1. Denom admin `A` creates a tokenfactory denom via `MsgCreateDenom`, becoming its admin.
2. `A` submits `MsgChangeAdmin{Sender: A, Denom: denom, NewAdmin: B}` where `B` is a validly-formatted bech32 address but one whose private key nobody possesses (e.g., mistyped, or an address derived without a known key).
3. `msg_server.go`'s `ChangeAdmin` handler validates only that `A == authorityMetadata.Admin` and `B != A`, then calls `setAdmin(ctx, denom, B)` — see [4](#0-3) .
4. From this point, no account can produce a valid signature for `B`, so `Mint`, `Burn`, `ChangeAdmin`, `UpdateDenom`, and `SetDenomMetadata` for `denom` are permanently unusable — the denom's supply and metadata are frozen in their current state indefinitely.

func (m MsgChangeAdmin) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(m.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	_, err = sdk.AccAddressFromBech32(m.NewAdmin)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid address (%s)", err)
	}

	_, _, err = DeconstructDenom(m.Denom)
	if err != nil {
		return err
	}

	return nil
}

func (server msgServer) Burn(goCtx context.Context, msg *types.MsgBurn) (*types.MsgBurnResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Amount.GetDenom())
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	err = server.burnFrom(ctx, msg.Amount, msg.Sender)
	if err != nil {
		return nil, err
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgBurn,
			sdk.NewAttribute(types.AttributeBurnFromAddress, msg.Sender),
			sdk.NewAttribute(types.AttributeAmount, msg.Amount.String()),
		),
	})

	return &types.MsgBurnResponse{}, nil

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgChangeAdmin,
			sdk.NewAttribute(types.AttributeDenom, msg.GetDenom()),
			sdk.NewAttribute(types.AttributeNewAdmin, msg.NewAdmin),
		),
	})

	return &types.MsgChangeAdminResponse{}, nil
}
