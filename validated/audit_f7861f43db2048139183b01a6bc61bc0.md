### Title
`ThresholdKeys::read` accepts fully attacker-controlled key material without consistency checks, enabling silent wallet-key substitution on import — ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the `secret_share`, and all `verification_shares` from a byte stream, then hands them to `ThresholdKeys::new`. Neither function verifies that `secret_share` corresponds to `verification_shares[i]`, nor that the resulting `group_key` is bound to anything previously agreed upon. The entire public identity of the threshold wallet — `group_key` — is recomputed purely from attacker-supplied bytes (`verification_shares[1..=t]` scaled by attacker-supplied interpolation factors). A malicious serialized keys blob therefore yields `ThresholdKeys` for a group key the attacker fully controls, which the importing node will treat as its own multisig wallet: scanning for deposits to it and signing transactions under it.

### Finding Description
The deserialization path is:

1. `ThresholdKeys::read` reads the curve ID, then `t`, `n`, `i` (`Participant::new` only checks non-zero), an interpolation selector (`0` = `Constant` with `n` free scalars, `1` = `Lagrange`), the `secret_share` scalar, and `n` verification-share points (`crypto/dkg/src/lib.rs:574-623`).
2. `ThresholdKeys::new` only checks `verification_shares.len() == n`, that all indexes are `<= n`, and (for `Constant`) `t == n` (`crypto/dkg/src/lib.rs:355-374`).
3. `group_key` is then computed as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` over `1..=t` (`crypto/dkg/src/lib.rs:376-378`) — with `Interpolation::Constant`, these factors are the arbitrary scalars read from the file.

Nowhere is `C::generator() * secret_share == verification_shares[i]` checked (contrast with `PedPoP`'s `calculate_share`, which batch-verifies every share against the committed coefficients at `crypto/dkg/pedpop/src/lib.rs:487-499`, and `GeneratorPromotion::complete`, which DLEq-verifies each share at `crypto/dkg/promote/src/lib.rs:147-154`). The serialized format includes no MAC, checksum, or binding to the coordinator-established key. The `scalar`/`offset` tweaks are the only fields excluded from serialization, so the imported `group_key()` is exactly the attacker-chosen point.

Because the rules scope `ThresholdKeys::read` as a reachable sink for untrusted bytes, an attacker who can get a node/operator to load a crafted keys file (the analog of the malicious `.stigqter` file being opened and acted on) produces a `ThresholdKeys` object where:
- `group_key()` is an arbitrary point `G_a = s_a·B` for an attacker-known `s_a` (e.g., `t = 1`, `Lagrange`, `verification_shares[i] = s_a·B`, `secret_share = s_a`), and
- all signing operations (`view()`, FROST `sign`/`complete`) behave normally and produce valid signatures — for `s_a`, which the attacker already knows.

The node will register `G_a` as its wallet key: `Scanner::new(key)`/`register_offset` in `networks/bitcoin/src/wallet/mod.rs:162-196` build P2TR script keys from this group key, and the processor scanner emits received-output events for deposits to `G_a` (`processor/src/multisigs/scanner.rs:550-567`).

### Impact Explanation
Silent substitution of the validator set's wallet identity. After loading the crafted file, the node credits deposits sent to the attacker's Taproot key as multisig funds and will co-sign/sign spends from them as if they were its own. Any downstream accounting that credits depositor balances against outputs the scanner reports (`scanner.rs` `get_outputs`/`emit` path) credits funds the attacker alone can move on Bitcoin. Additionally, a file can be crafted with the honest `verification_shares` but a mismatched `secret_share`, making every signature share the node produces fail FROST verification — a persistent liveness fault indistinguishable from, and blameable on, the victim (the victim's shares verify against `verification_shares[i]`, so the victim is provably "faulty" to honest peers, enabling a griefing/slashing-adjacent attack). This mirrors the report's pattern: a single attacker-crafted file, once imported, repurposes privileged functionality (here: threshold signing and fund crediting) for the attacker.

### Likelihood Explanation
Requires the victim to load attacker-supplied serialized keys into `ThresholdKeys::read` — comparable to the report's required "open file + run action" interaction. There is no integrity or authenticity protection on the serialized format (`write`/`read` are a raw field dump, `crypto/dkg/src/lib.rs:538-632`), so any channel that delivers or restores key files (backup restore, migration tooling, shared storage, compromised-but-untargeted file transfer) reaches this code. The cryptographic check that would detect tampering (`secret_share` ↔ `verification_shares[i]` consistency) is simply absent, so exploitation is deterministic once the file is read. Attack complexity is low: constructing a valid self-consistent blob requires only choosing a scalar and writing fields in the documented order.

### Recommendation
In `ThresholdKeys::new` (so both `read` and programmatic construction are covered), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. Additionally:
- Authenticate serialized `ThresholdKeys` (e.g., sign the serialization under the validator's identity key, or store a commitment to `group_key` established during the DKG and verify on load).
- Reject zero `Constant` interpolation factors at index positions within `1..=t` if a non-degenerate group key is required, and document that the serialized format is not integrity-protected.

### Proof of Concept
```rust
// Attacker constructs a ThresholdKeys blob for a key they fully control.
// ThresholdKeys::read accepts it; group_key() == attacker key; signing works.
use dalek_ff_group::{Scalar, EdwardsPoint as RistrettoPoint};
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;
use frost::curve::Curve;
use dkg::{ThresholdKeys, Participant, ThresholdParams};
use zeroize::Zeroizing;
use rand_core::OsRng;

fn craft_malicious_keys() -> Vec<u8> {
    let s_a = Zeroizing::new(Scalar::random(&mut OsRng)); // attacker-known secret
    let vs  = Ristretto::generator() * *s_a;              // verification share

    let mut blob = vec![];
    blob.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
    blob.extend(Ristretto::ID);
    blob.extend(1u16.to_le_bytes()); // t = 1
    blob.extend(1u16.to_le_bytes()); // n = 1
    blob.extend(1u16.to_le_bytes()); // i = 1
    blob.push(1u8);                  // Interpolation::Lagrange
    blob.extend(s_a.to_repr().as_ref());
    blob.extend(vs.to_bytes().as_ref());
    blob
}

fn main() {
    let blob = craft_malicious_keys();
    // No verification of secret_share vs verification_shares[1]:
    // ThresholdKeys::new only checks counts/indexes and computes
    // group_key = verification_shares[1] * interpolation_factor(1, [1]) = vs.
    let keys = ThresholdKeys::<Ristretto>::read(&mut blob.as_slice()).unwrap();
    // group_key() is the attacker's key; the node will scan and sign for it.
    // With t = 1, keys.view(vec![Participant::new(1)]) yields a working signer
    // whose signatures validate under a public key the attacker alone controls.
    let view = keys.view(vec![Participant::new(1).unwrap()]).unwrap();
    assert_eq!(view.group_key(), keys.group_key());
}
```

A second crafted variant keeps `t`, `n`, and `verification_shares` copied from a victim node's public DKG output but substitutes `secret_share` with an attacker scalar — `read` accepts it, `group_key()` still equals the honest wallet key, and every FROST share the victim later produces fails `share_verification_statements`-style checks, pinning provable blame on the victim.
