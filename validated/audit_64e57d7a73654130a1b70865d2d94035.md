### Title
`SignableTransaction` fee calculation omits the OP_RETURN data output, undercharging the fee rate and producing transactions that may not relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight/vbytes — and therefore `needed_fee` — from `payments` only, even though the final transaction also includes an OP_RETURN output carrying up to 80 bytes of attacker/integrator-supplied `data`. Analogous to the Banana Gun oracle-bug class (untrusted externally supplied message bytes influencing what gets signed/broadcast), the caller-controlled `data` field silently inflates the signed transaction's size beyond what the fee was computed for.

### Finding Description
In `SignableTransaction::new`:

- The OP_RETURN output is pushed onto `tx_outs` at `send.rs:194-202` with a script containing `data` (up to 80 bytes per the check at `send.rs:171-173`).
- The weight and vbytes used for `needed_fee` are computed at `send.rs:204` via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a template transaction from `payments` only — the `data` output is never included.
- When change exists, the recomputation at `send.rs:225-226` (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`) again excludes the data output.

`calculate_weight_vbytes` (`send.rs:62-127`) constructs the template `tx.output` solely from `payments` plus optional change, so any output added afterward — here the OP_RETURN — is invisible to the weight estimate. The result: `needed_fee` (returned by `needed_fee()` at `send.rs:133-135` and enforced by the `NotEnoughFunds` check at `send.rs:215-221`) is systematically too low whenever `data` is present. The actual fee paid is `sum(inputs) - sum(outputs)` (`fee()` at `send.rs:138-141`), so the effective fee rate of the transaction that `TransactionSignMachine::sign` (`send.rs:355-398`) signs is lower than the `fee_per_vbyte` requested.

### Impact Explanation
The signed transaction's real vsize exceeds the estimate by roughly the OP_RETURN output size (~8-byte amount + ~1-83-byte push + script overhead, up to ~90 vbytes). Consequences:

- The effective sat/vbyte is lower than the caller-specified `fee_per_vbyte`, so an urgent withdrawal/payment underpays miners.
- In the worst case, the true fee can fall below the node minimum relay fee even though the `TooLowFee` check at `send.rs:211-213` passed, producing a signed transaction that will not propagate — funds locked in an unconfirmable plan requiring reconstruction.
- `needed_fee()` reports a value that does not correspond to the transaction actually signed, so accounting/budgeting based on it is wrong.

### Likelihood Explanation
Any transaction constructed with `data` (Serai `InInstruction` payloads are embedded via OP_RETURN) triggers the miscalculation; the discrepancy scales with data length. No attacker sophistication is needed — supplying the maximum 80-byte payload maximizes the shortfall. Whether the resulting fee falls below relay minimums depends on how close `fee_per_vbyte` was to the floor, but the fee rate is always lower than requested.

### Recommendation
Include the data output in the weight template: pass the fully constructed `tx_outs` (payments + OP_RETURN) into `calculate_weight_vbytes`, or add an explicit `data_len`/extra-output parameter so the OP_RETURN output contributes to `weight`/`vbytes` in both the no-change and with-change computations at `send.rs:204` and `send.rs:225-226`.

### Proof of Concept
```rust
// Conceptual: construct two SignableTransactions identical except data
let payments = vec![(dest_script.clone(), 10_000u64)];
let tx_no_data = SignableTransaction::new(inputs.clone(), &payments, None, None, 10).unwrap();
let tx_data = SignableTransaction::new(
    inputs.clone(),
    &payments,
    None,
    Some(vec![0xaa; 80]), // max allowed data
    10,
).unwrap();

// tx_data carries an ~90-vbyte larger output set, yet:
assert_eq!(tx_no_data.needed_fee(), tx_data.needed_fee()); // same estimate
// while tx_data.transaction() is strictly larger and pays the same fee,
// i.e. a lower effective sat/vbyte than the requested 10.
```
