Based on the investigation, the closest structural analog in GitHub Desktop to the "approve `type(uint256).max` instead of only the necessary amount" bug class is the `safe.directory` trust-exception mechanism used to resolve Git's "dubious ownership" (unsafe repository) warning. Like `universalApproveMax`, it grants a **persistent, global** exception instead of a **scoped, per-operation** one — and, critically, it is never revoked when the thing it was granted for (the repository at that path) goes away.

### Title
Permanent, unscoped `safe.directory` trust grant is never revoked when a repository is removed or relocated - (File: `app/src/lib/git/config.ts`)

### Summary
When Desktop detects a repository is "unsafe" (owned by a different user than the current process), it offers the user a "Trust Repository" action. This calls `addSafeDirectory(path)` [1](#0-0)  which permanently appends the path to the user's **global** `.gitconfig` `safe.directory` list [2](#0-1) . This is functionally the same pattern as `universalApproveMax`: rather than granting the minimum trust needed (e.g., a single verified operation, or an allowance tied to the specific git object-store identity of that repository), Desktop grants a blanket, indefinite exception keyed only on a filesystem **path string**.

### Finding Description
`addSafeDirectory` writes directly to the global config via `git config --global --add safe.directory <path>` [3](#0-2) , and this exception is consulted by `addGlobalConfigValueIfMissing`, which only checks whether the literal path string is already present — it has no concept of "this trust belongs to *this* repository's identity/remote and should expire when the repo is removed" [4](#0-3) . Once added, any future git repository that ends up located at that same path — even one Desktop never cloned, and even one an attacker planted there — is treated as fully trusted, with Git allowed to read local config, hooks, and other repo-controlled content without re-prompting the user, since `getRepositoryType` will simply return `'regular'` instead of `'unsafe'` for that path going forward [5](#0-4) .

The invariant that should hold — "the amount of trust granted should be scoped to what's actually needed, for as long as it's needed" — is broken the same way it is in `universalApproveMax`: a maximal, indefinite grant is issued when a scoped, revocable one would suffice. Desktop's own UI acknowledges the severity of what this exception permits: "Adding untrusted repositories may automatically execute files in the repository" [6](#0-5) , yet the exception is never removed when the repository is deleted, relocated, or "Remove"d from Desktop's repository list — `_relocateRepository` only updates the recorded path on `'unsafe'`, it never revokes the previously granted `safe.directory` entry for the *old* path [7](#0-6) .

### Impact Explanation
On a shared machine, in a CI/build agent context, or any scenario where a directory can be reused (temp dirs, mount points, restored backups, container volumes reused across sessions), once a path has been "trusted" once, it stays trusted forever in the user's global gitconfig regardless of what later occupies that path. An attacker who can place a malicious `.git` repository (with malicious hooks, `core.fsmonitor`, `core.pager`, or other config-driven code-execution primitives) at a path the victim previously trusted gets Git to treat it as safe without any further prompt, enabling code execution outside Desktop's own sandboxing/consent flow — directly matching the requested impact class of "code execution... outside the repo" driven by attacker control of a filesystem location the user interacts with via Desktop.

### Likelihood Explanation
Requires: (1) the victim has previously trusted at least one unsafe-owned path (a documented, common flow — see changelog entries for "Trust Repository" / "Surface Git's warning about unsafe directories" [8](#0-7) ), and (2) that same path is later reused by attacker-controlled content (shared workstation, container reuse, restored disk image, or network share as referenced by the Windows UNC-path handling in `addSafeDirectory` [9](#0-8) ). This is a plausible, low-interaction path since Desktop performs no re-verification of "is this the same repository I originally trusted" (e.g., no binding to the original `.git` object hash, remote URL, or first-commit SHA) — it only ever checks the path string.

### Recommendation
Bind the trust exception to something stronger than a bare path — e.g., prompt again if the repository's origin remote / initial commit differs from what was recorded when trust was granted — and proactively revoke the corresponding `safe.directory` entry when a repository is removed or relocated in `_relocateRepository`/repository removal flows, rather than leaving a stale, indefinite, maximal-trust grant in the global gitconfig.

### Proof of Concept
1. User opens a shared/reused directory `D` in Desktop; Git reports it "unsafe" (different owner) and Desktop shows the "Trust Repository" prompt via `MissingRepository`/`AddExistingRepository`.
2. User clicks "Trust Repository" → `onTrustDirectory` → `addSafeDirectory(D)` → `git config --global --add safe.directory D` is executed permanently.
3. User later removes the repository from Desktop (or it's deleted/reformatted), but the global gitconfig still lists `D` under `safe.directory`.
4. An attacker (or a different user with write access to path `D`, e.g. on a shared machine, CI runner, or restored snapshot) places a malicious Git repository at `D`, containing a repo-local hook/config-based code execution payload.
5. The victim (or Desktop performing background scans of known/previous repository paths) opens or interacts with `D` again. Because `D` is already listed in `safe.directory`, Git no longer refuses it as unsafe, and no new consent prompt is shown, silently allowing repo-controlled behavior (hooks/config) to execute in a context the user never re-approved.

export async function addGlobalConfigValue(
  name: string,
  value: string
): Promise<void> {
  await git(
    ['config', '--global', '--add', name, value],
    __dirname,
    'addGlobalConfigValue'
  )
}

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
