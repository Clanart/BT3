## Finding: valid — marker-scanning divergence between `extractConflictHunks` and `reassembleResolvedFile` can leave unresolved conflict markers in the "resolved" file

The originally proposed root cause (a **nested `oursMarker`** appearing inside the "theirs" section) does **not** actually cause divergence: both `extractConflictHunks` and `reassembleResolvedFile` independently resolve the hunk boundary to "the first `>>>>>>>` line found after the initial `<<<<<<<`," so a stray `<<<<<<<` swallowed as literal content is consumed identically by both functions.

However, tracing the two implementations line-by-line reveals a **different, real divergence**: the two functions disagree about the *order* in which `=======` and `>>>>>>>` must appear. [1](#0-0) 
`extractConflictHunks`'s ours/base-collecting loops only test for `baseMarker`/`separatorMarker` — they never test for `theirsMarker`. So a line that looks like `>>>>>>> ...` appearing *before* the real `=======` separator is silently absorbed as ordinary `oursLines`/`baseLines` content, and the loop keeps going until it later finds a genuine `=======` and then the *next* `>>>>>>>` in the theirs-collecting loop. [2](#0-1) 
`reassembleResolvedFile`'s look-ahead does the opposite: it scans forward and breaks as soon as it hits the **first** `>>>>>>>`-shaped line, regardless of whether `hasSeparator` has been set yet. If that first `>>>>>>>` occurs before any `=======` was seen, `hasSeparator` is still `false`, so the block is classified as malformed and copied through **verbatim**, markers included — the corresponding hunk resolution from the model is discarded, never spliced in.

### Finding Description
For input such as:
```
<<<<<<< HEAD
oursA
>>>>>>> stray
oursB
=======
theirsA
>>>>>>> branch-real
```
- `extractConflictHunks` reports **one well-formed hunk** — `oursContent = "oursA\n>>>>>>> stray\noursB"`, `theirsContent = "theirsA"` — with `hunkEnd` at the `branch-real` line. This is what gets sent to Copilot, and `validateResolutionPaths` [3](#0-2)  confirms the model returned exactly one hunk for this file.
- `reassembleResolvedFile`, re-scanning the *same raw content independently*, hits `>>>>>>> stray` first (before `hasSeparator` is ever set true), decides the block is malformed, and copies the entire block — including the original `<<<<<<<`, `=======`, `>>>>>>>` lines — through unchanged. The valid hunk resolution Copilot produced for this block is never spliced in.

The net result: the file returned as "resolved" still contains literal, unresolved conflict markers for that region, even though the pipeline reports the file as successfully resolved. Nothing re-checks the *final spliced output* for leftover conflict markers — the only marker check present operates on the model's raw per-hunk `resolvedContent` string during parsing [4](#0-3) , not on the post-reassembly file content.

### Impact Explanation
If the user commits/pushes the "resolved" file without noticing the raw `<<<<<<<`/`=======`/`>>>>>>>` markers left in place, this is silent corruption of what the user commits — an in-scope impact ("silent corruption of what the user commits or pushes"). A file that legitimately contains a `>>>>>>>`-shaped line as data (e.g. within a heredoc, patch/diff sample, changelog referencing git markers, or documentation) that also happens to be genuinely conflicted is attacker-repo-controlled content, satisfying the scope's "repository content" condition.

### Likelihood Explanation
This requires a fairly specific corpus condition: a real merge conflict in a file whose *ours* (or *base*) section contains a line that itself matches `^>{7}(?:\s|$)`. That's uncommon in ordinary source but plausible in text/documentation/config files that discuss or embed conflict-marker examples, or in previously-corrupted merge output re-conflicted by a subsequent operation. This is a lower-likelihood, edge-case parsing bug rather than a broadly exploitable path — I could not verify from the index whether `app-store.ts`'s write/commit path performs any additional marker sanity check before staging the reassembled content, since that file's full contents were not available; a Devin session with full file access would be needed to confirm whether any downstream guard exists.

### Recommendation
Make `reassembleResolvedFile`'s block-boundary detection structurally identical to `extractConflictHunks`'s (require `=======` before `>>>>>>>` and use the *same* first-separator/first-theirs-marker ordering the extractor uses), or better, avoid duplicating the scanning logic entirely — extract a single shared marker-scanning routine used by both functions so they can never diverge. Additionally, add a final assertion after `reassembleResolvedFile` that the output contains no remaining `<<<<<<<`/`=======`/`>>>>>>>` lines, failing loudly (as a `CopilotValidationError`) rather than silently shipping a corrupted file.

### Proof of Concept
1. Construct a file with the pattern above (`<<<<<<< HEAD`, `oursA`, `>>>>>>> stray`, `oursB`, `=======`, `theirsA`, `>>>>>>> branch-real`).
2. Run `extractConflictHunks(content)` — observe it returns exactly 1 hunk with the boundaries described.
3. Independently run reassembleResolvedFile's marker-scanning logic (or `reassembleResolvedFile(content, [{resolvedContent: 'RESOLVED'}])`) on the same content — observe the output still contains the original `<<<<<<<`/`=======`/`>>>>>>>` lines verbatim instead of `RESOLVED`, confirming the boundary/consumption divergence between the two functions.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}
