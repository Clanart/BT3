### Title
Stale EVM contract storage not purged when destructed contract never set code, enabling storage-slot poisoning of a future contract at the same address - ([File: x/evm/state/state.go])

### Summary
The Alpine/Xen CVE describes a p2m mapping that is only cleared conditionally ("valid bit" check) when tearing down a guest page, letting the guest retain access to memory that should have been reclaimed. Sei's EVM `StateDB` implementation has the same conditional-clear pattern for per-account storage: it only purges an account's storage keyspace if the account has a `CodeHash` entry, which is not guaranteed to exist for every account whose storage was written.

### Finding Description
`clearAccountState` is the single function responsible for wiping an EVM account's persisted storage. It is called both when an account is (re)created (`CreateAccount`, used for CREATE/CREATE2 address reuse) and when an account self-destructs (`clearAccountStateIfDestructed`, invoked from `Finalize`): [1](#0-0) 

The purge of the storage prefix (`s.k.PurgePrefix(s.ctx, types.StateKey(acc))`) is gated entirely on `deleteIfExists(s.k.PrefixStore(s.ctx, types.CodeHashKeyPrefix), acc[:])` returning `true`, i.e. on whether a `CodeHash` key currently exists for that address: [2](#0-1) 

The `CodeHash` key is only ever written inside `Keeper.SetCode`, which the EVM interpreter calls after a `CREATE`/`CREATE2` init-code sequence finishes successfully and returns its runtime bytecode: [3](#0-2) 

However, `SetState`/`SSTORE` writes go straight to the keeper's state store independent of whether code has been set yet: [4](#0-3) 

Per EVM semantics, constructor (init) code can execute `SSTORE` before it ever `RETURN`s (which is what triggers `SetCode`). If the constructor instead terminates via `SELFDESTRUCT` (a case explicitly modeled and tested here via `selfDestructCode`/`initCode` helpers and the `createAndDestroyChildRuntime` test fixture), the account is marked `AccountDeleted` and `Finalize` runs `clearAccountStateIfDestructed` → `clearAccountState` for it, but because `SetCode` was never called, `CodeHashKeyPrefix` has no entry for that address, `deleteIfExists` returns `false`, and `PurgePrefix(types.StateKey(acc))` is skipped entirely. The `SSTORE`d slots from the destructed constructor therefore remain permanently persisted in the state store under that address's key space, exactly like the Xen p2m entries that survive `guest_physmap_remove_page` because the "valid bit" check short-circuits the actual teardown.

### Impact Explanation
An EVM address whose lifecycle is "constructor writes storage → constructor self-destructs (no code ever deployed)" is left with orphaned, non-purged storage slots. If that same address is later reused for a legitimate contract deployment (a very common pattern for CREATE2 factories, minimal-proxy/clone factories, and permissionless pointer/ERC20/ERC721 deployment flows that recompute deterministic addresses), the new contract's `SLOAD`s at that address will read the leftover attacker-chosen values instead of the pristine zero storage that Solidity/EVM semantics guarantee for a freshly created account. Since most Solidity contracts assume unwritten slots read as zero (owner/admin fields, balances, allowances, reentrancy guards, initialization flags), an attacker who controls the "seed" contract deployed first at a target address can pre-poison storage slots that a subsequently deployed, unrelated contract will trust as legitimate initial state — enabling unauthorized privilege/ownership takeover or balance/allowance forgery in the newly deployed contract, i.e. fund loss or unauthorized transfer.

### Likelihood Explanation
Reaching this is fully permissionless: any address can submit an EVM transaction deploying a contract whose constructor performs `SSTORE`s and then `SELFDESTRUCT`s before returning runtime code (self-destruct-in-constructor is legal, EIP-6780-compatible behavior explicitly exercised by this codebase's own tests). Getting a second, victim contract deployed at that exact address requires a deterministic address scheme (CREATE2 with attacker-chosen salt, or predicting a factory's next CREATE nonce), which is a standard and widely used deployment pattern (proxy factories, permissionless pointer registration, counterfactual deployments) rather than an exotic requirement.

### Recommendation
Purge an account's storage keyspace (`PurgePrefix(types.StateKey(acc))`) unconditionally whenever `clearAccountState` runs for account creation or self-destruction finalization, rather than gating it on the presence of a `CodeHash` entry. If avoiding the purge cost for genuinely empty/never-written accounts is desired for performance, track "has any storage been written" explicitly (e.g., via the same `PrepareReplayedAddr`/account-touched bookkeeping) instead of overloading the `CodeHash` existence check, which does not correlate with whether `SetState` was ever called for that address.

### Proof of Concept
1. Attacker deploys (via `CREATE2` with a chosen salt, or by controlling a factory's next nonce) a "seed" contract whose init code does: `SSTORE(slot0, attackerValue)` then `SELFDESTRUCT(attacker)` (no `RETURN`, so no runtime code and no `SetCode` call ever occurs). This matches the `createAndDestroyChildRuntime`/`selfDestructCode`/`initCode` test helpers already present in the codebase's test suite.
2. On `Finalize`, `clearAccountStateIfDestructed` → `clearAccountState(acc)` runs for this address; because `CodeHashKeyPrefix` was never set, `deleteIfExists` returns `false` and `PurgePrefix(types.StateKey(acc))` is skipped, so slot0's `attackerValue` remains in the keeper's state store.
3. Later, a legitimate protocol/factory deploys a real contract at the same address (same `CREATE2` salt/init-code-hash, or the same predicted `CREATE` nonce) that assumes `slot0` starts at zero (e.g., an `owner`/initialization flag).
4. `GetState`/`GetCommittedState` for that address return the stale `attackerValue` instead of zero, letting the attacker's pre-set value influence the new contract's logic (e.g., bypass an initialization check or forge a privileged value) without ever calling `SSTORE` themselves in the new contract.

func (s *DBImpl) clearAccountState(acc common.Address) {
	s.k.PrepareReplayedAddr(s.ctx, acc)
	// Drop any simulation-local storage override so a recreated/cleared account
	// reads empty storage rather than the frozen overlay. Journaled so a revert restores the overlay.
	if ov, ok := s.tempState.storageOverrides[acc]; ok {
		s.journal = append(s.journal, &storageOverrideRemove{account: acc, prev: ov})
		delete(s.tempState.storageOverrides, acc)
	}
	if deleteIfExists(s.k.PrefixStore(s.ctx, types.CodeHashKeyPrefix), acc[:]) {
		s.k.PurgePrefix(s.ctx, types.StateKey(acc))
		s.clearAccountCodeAndNonce(acc)
	}
}

func deleteIfExists(store storetypes.KVStore, key []byte) bool {
	if store.Has(key) {
		store.Delete(key)
		return true
	}
	return false
}

func (k *Keeper) SetCode(ctx sdk.Context, addr common.Address, code []byte) {
	if code == nil {
		code = []byte{}
	}
	k.PrefixStore(ctx, types.CodeKeyPrefix).Set(addr[:], code)
	length := make([]byte, 8)
	binary.BigEndian.PutUint64(length, uint64(len(code)))
	k.PrefixStore(ctx, types.CodeSizeKeyPrefix).Set(addr[:], length)
	h := crypto.Keccak256Hash(code)
	k.PrefixStore(ctx, types.CodeHashKeyPrefix).Set(addr[:], h[:])
	// set association with direct cast Sei address for the contract address
	if _, ok := k.GetSeiAddress(ctx, addr); !ok {
		k.SetAddressMapping(ctx, k.GetSeiAddressOrDefault(ctx, addr), addr)
	}
}
