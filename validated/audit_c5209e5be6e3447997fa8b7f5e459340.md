### Title
Re-enabling `protocol.file.allow=always` for submodule updates permits attacker-controlled `.gitmodules` URLs to read arbitrary local files - (File: `app/src/lib/git/submodule.ts`)

### Summary
The bug-class in the report is "a value the attacker fully controls is used to satisfy the very check meant to protect against that attacker" (USDs backing its own USDs loan). The closest verifiable analog in this Desktop codebase is `updateSubmodulesAfterOperation`, which conditionally re-enables git's `file://` transport for submodule cloning via `-c protocol.file.allow=always` [1](#0-0) . The `.gitmodules` file (including each submodule's `url =` entry) is fully attacker-controlled content that ships inside the cloned/fetched repository itself, so if this flag is passed based on anything short of an explicit, informed user action, the untrusted repo content is effectively deciding its own trust level for local-filesystem access — the same "self-referential trust" pattern as the report.

### Finding Description
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol: boolean` parameter and, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [2](#0-1) . This flag is threaded through `checkoutBranch` and `checkoutCommit`, both of which default it to `false` but allow callers to pass `true` [3](#0-2) [4](#0-3) .

Git upstream disabled `file://`/local-path submodule cloning by default (the fix for `CVE-2022-39253`) precisely because a submodule URL is data that arrives with the untrusted repository — a malicious repo can point a submodule at an arbitrary path on the victim's disk (e.g. `../../../../etc` style paths, or hardlink-based tricks) and have git "clone" it locally, leaking file contents into the working tree or a `.git` link file that can be abused. Any code path that flips `protocol.file.allow=always` back on for a `git submodule update --init --recursive` invocation re-opens this exact primitive: the submodule URL is chosen by the untrusted repo, not the user, and its value is what determines whether/how local files get pulled into the checkout.

### Impact Explanation
If reachable without deliberate, informed user opt-in, this allows a malicious repository (cloned or fetched by a normal, unprivileged Desktop user) to have its own `.gitmodules` content authorize local-filesystem `file://` submodule fetches, potentially exfiltrating or corrupting local files outside the intended repo boundary during an ordinary "check out a branch/commit" action — matching the report's "read/write outside the repo" and "silent corruption of what the user has on disk" impact classes.

### Likelihood Explanation
Uncertain / not fully verified. I could not, within the remaining tool budget, confirm every call site that passes `allowFileProtocol: true` into `checkoutBranch`/`checkoutCommit` (the grep for callers in `app-store.ts`, `dispatcher.ts`, `stash-and-switch-branch-dialog.tsx`, `branches-container.tsx`, `confirm-checkout-commit.tsx`, `compare.tsx`, and `overwrite-stashed-changes-dialog.tsx` returned matches, but I was not able to read those call sites before the iteration limit) [5](#0-4) [6](#0-5) . If Desktop only ever passes `true` after the user has already been shown and explicitly accepted a specific "trust this local/unsafe submodule" warning (analogous to the existing "unsafe directory" trust dialog seen in `app/src/ui/missing-repository.tsx` and `app/src/ui/add-repository/add-existing-repository.tsx`), then this is not exploitable without an explicit user step and would not qualify. I was not able to confirm which scenario applies.

### Recommendation
Confirm every call site that can set `allowFileProtocol: true` and verify it is gated behind an explicit, per-submodule-URL user confirmation (not a blanket "this repository/session" toggle), mirroring the unsafe-directory trust model. Never derive the decision to re-enable `protocol.file.allow` from anything contained in the untrusted repository (branch name, commit metadata, `.gitmodules` content itself).

### Proof of Concept
Not constructed — doing so requires confirming the exact caller-supplied trigger for `allowFileProtocol: true`, which was not verified within the available tool budget. A concrete PoC would clone a malicious repo containing a `.gitmodules` entry with a `file://<absolute-local-path>` URL, trigger whichever Desktop action passes `allowFileProtocol: true` into `checkoutBranch`/`checkoutCommit`, and observe that `git submodule update --init --recursive -c protocol.file.allow=always` clones local filesystem content into the submodule path.

**Note on confidence:** Because the exact gating logic for `allowFileProtocol` could not be verified before the tool-call limit, this should be treated as a lead requiring one more verification pass (reading `app-store.ts`, `dispatcher.ts`, and the UI call sites) rather than a confirmed, unprompted-user-step vulnerability.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
