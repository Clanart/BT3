## Title
Deep-link branch parameter accepted with leading `-` characters, enabling git argument injection - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`)

## Summary
The external report's broken invariant is: a validation/calculation step is supposed to account for *all* relevant inputs before producing a value that is trusted downstream, but it silently omits one category (referral fees), letting a larger-than-intended value flow through unguarded. The Desktop analog is `testForInvalidChars` in `app/src/lib/sanitize-ref-name.ts`, used by `parseAppURL` in `app/src/lib/parse-app-url.ts` to validate the `branch` query parameter of an `x-github-client://openRepo/...` deep link. The character blocklist enumerates control characters and several git-unsafe symbols but never rejects a leading `-`, so a branch value that looks like a git command-line flag (e.g. `--upload-pack=...`) passes validation.

## Finding Description
`parseAppURL` accepts a `branch` query parameter from an externally triggered URL (a link the user clicks, handled by `app.on('open-url', ...)` / `--protocol-launcher` in `app/src/main-process/main.ts`) and validates it with: [1](#0-0) 

The validator delegates to `testForInvalidChars`, whose blocklist is: [2](#0-1) 

The regex rejects control characters, space, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing slash — but it does **not** reject a string starting with `-`. This mirrors the fee-calculation bug's structure exactly: the guard was written to cover "the known-bad set" (invalid ref characters) but omits an equally important class (git-flag-like tokens), so a value that should have been rejected/neutralized is instead passed through as if it were a "clean" branch name. The value continues to `openBranchNameFromUrl` (invoked from `dispatcher.ts`'s `openRepositoryFromUrl`): [3](#0-2) 

If the branch string is later passed as a positional argument to a `git` invocation (e.g. `git checkout <branch>`) without a preceding `--` separator, a value such as `--upload-pack=/tmp/evil.sh` or `-c core.fsmonitor=/tmp/evil.sh` is interpreted by git as a flag rather than a ref name — classic git argument/option injection, potentially leading to command execution. This is distinct from `sanitizedRefName` (used for *creating* refs, which strips leading `-`/`+`) — `testForInvalidChars` is the *validation-only* path used for attacker-supplied deep-link input and lacks that stripping/rejection step.

Note: I was not able to fully trace the exact `git` argument-assembly code inside `openBranchNameFromUrl`/`openPullRequestFromUrl` to confirm whether a `--` separator is present at every call site before the iteration budget ran out. This should be verified directly; the regex gap itself, however, is confirmed in the code.

## Impact Explanation
If the branch-name string ultimately reaches a `git` command without a `--` terminator, an attacker who controls a deep link (`x-github-client://openRepo/...?branch=...`) or a hosted "Open in Desktop" URL can inject arbitrary git flags. Depending on which flags are reachable, this can range from information disclosure/config tampering (e.g. `-c` injection) to code execution via hook- or protocol-related flags (`--upload-pack`, `-c core.fsmonitor=...`). This satisfies the valid-impact bar: an unprivileged, attacker-controlled deep link causing code execution/file write without any local access, admin rights, or prior compromise.

## Likelihood Explanation
Moderate-to-high if unconfirmed call sites lack `--`: deep links are a documented, user-facing input surface for Desktop (`github-mac://openRepo/...`, `x-github-client://...`), require only a single click, and the branch parameter is explicitly designed to be attacker-influenced (it names the branch to check out after cloning/opening a repo tied to a forked PR). The only gate protecting it is the character blocklist shown above, which does not defend against leading-dash "flag" values.

## Recommendation
Mirror the report's fix pattern (account for the missing category before trusting the derived value):
- In `testForInvalidChars`/`sanitizedRefName`, reject or strip values beginning with `-` (as `sanitizedRefName` already partially does via `.replace(/^[-\+]*/g, '')`, but `testForInvalidChars` does not enforce this — align the two).
- Defense in depth: ensure every `git` invocation that takes a deep-link-derived branch/ref argument places `--` before it, so even a flag-like string is treated as a positional pathspec/ref, not an option.

## Proof of Concept
1. Attacker hosts or sends a link: `x-github-client://openRepo/https://github.com/victim/repo?branch=--upload-pack=%2Ftmp%2Fevil.sh`.
2. User clicks the link; OS invokes GitHub Desktop with this URL, triggering `handleAppURL` → `parseAppURL`.
3. `parsedURL.query.branch` = `--upload-pack=/tmp/evil.sh`. `testForInvalidChars(branch)` returns `false` (no invalid chars matched, since leading `-` is not in the blocklist), so the action is *not* rejected as `unknown`.
4. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)` receives the attacker string as the trusted branch name.
5. If the downstream git call for checkout/fetch passes this value as a bare argument (no `--` separator), git interprets it as the `--upload-pack` option instead of a ref name — enabling execution of an attacker-specified helper program during a subsequent fetch/clone operation.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
