### Title
Unbounded ownership-chain walk in `object::root_owner` enables denial-of-service on lazy module self-initialization and object-hosted code publish - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner` walks the object ownership chain without any nesting bound, unlike the two other chain-walking functions in the same module (`owns` and `verify_ungated_and_descendant`), which both enforce `MAXIMUM_OBJECT_NESTING`. `root_owner` is now a security-critical primitive: it is called by `code::publish_package` (to record the deploy-time owner of an object-hosted module) and by `init::assert_may_self_initialize` (to gate every lazy module self-initialization call). Because Aptos's own `object::transfer_raw` API allows an owner to construct a 2-object ownership cycle, an attacker (or the object owner themselves) can make `root_owner` loop until the transaction runs out of gas, permanently preventing `code::publish_package` and `init::internal_maybe_initialize` from completing for that object address.

### Finding Description
`root_owner` is defined as: [1](#0-0) 

```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```

This loop has no iteration cap. Compare this to the two other ownership-chain traversal functions in the same file, `owns` and `verify_ungated_and_descendant`, which both explicitly bound the walk with `MAXIMUM_OBJECT_NESTING` and abort if exceeded: [2](#0-1) [3](#0-2) 

Ownership cycles between two objects are constructible with the existing public API. `transfer_raw` only verifies that the chain from the *destination* object back up to the calling signer is intact and ungated — it never checks whether the *source* object being transferred is itself an ancestor of the destination: [4](#0-3) 

An owner `alice` who controls two objects `A` and `B` (both initially owned by `alice`) can:
1. `transfer(alice, A, B)` — sets `A.owner = B` (allowed: `verify_ungated_and_descendant(alice, B)` succeeds because `B.owner == alice`).
2. `transfer(alice, B, A)` — at this point `B.owner` is still `alice`, so `verify_ungated_and_descendant(alice, A)` succeeds; sets `B.owner = A`.

Now `A.owner == B` and `B.owner == A`: a 2-cycle. Any subsequent call to `root_owner()` on either `A` or `B` loops forever (bounded only by gas exhaustion, not by `MAXIMUM_OBJECT_NESTING`).

This directly affects two new publish/init-path invariants:
- `code::publish_package` calls `root_owner()` on the destination address for every module in an object-hosted package, on every (re)publish, to record the deploy owner used by lazy self-init: [5](#0-4) 
- `init::assert_may_self_initialize`, invoked from `init::internal_maybe_initialize` on every lazy module self-init call, also calls `root_owner()` to validate the caller's object hasn't changed owner since deploy: [6](#0-5) 

If either `A` or `B` (or any object whose root-owner chain passes through the cycle) hosts a package using object-code-deployment, then any `object_code_deployment::upgrade`/`publish` transaction touching it, and any entry function that calls `init::internal_maybe_initialize`, will loop in `root_owner` until it runs out of gas and aborts.

### Impact Explanation
This breaks the module-init / write-set-publish invariant: the intended write-set mutation (recording deploy owner in `code::publish_package`, or minting the lazily-initialized signer in `init::internal_maybe_initialize`) can never be committed for the affected object address once a cycle exists in its ownership chain, because the transaction always aborts with an out-of-gas error before completing. This is a denial-of-service specifically on the protected state-mutation path introduced by the new lazy-module-initialization / object-code-deployment feature — code that was published as upgradable can be effectively bricked (unable to be upgraded or to complete self-init) for as long as the cycle exists, with no way to reverse it since `object::transfer_raw` provides no mechanism to detect or refuse to create such cycles. The severity is elevated because the vulnerable function (`root_owner`) is asymmetric with respect to its sibling functions in the very same file that already anticipated and guarded against exactly this scenario (`MAXIMUM_OBJECT_NESTING`), indicating a missed/incomplete migration of the depth-bound invariant to the newly added `root_owner` consumer paths.

### Likelihood Explanation
Constructing the 2-object cycle requires only two ordinary `transfer` calls by the object's own owner, using only public, unprivileged, already-shipped APIs (`object::transfer` / `transfer_raw` / `transfer_call`). No governance, privileged signer, or race condition is needed. The trigger conditions (lazy module initialization feature enabled, and an object-hosted package using `init::internal_maybe_initialize`, or any call to `object_code_deployment::publish`/`upgrade` on such an object) are part of the newly introduced, currently-relevant feature set exercised in `aptos-move/e2e-move-tests/src/tests/init_module_api.rs` and `object_code_deployment.rs`.

### Recommendation
Bound the traversal in `object::root_owner` the same way `owns` and `verify_ungated_and_descendant` are bounded, using `MAXIMUM_OBJECT_NESTING`, and abort (or return a well-defined value) if the bound is exceeded rather than looping unbounded:
```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    let count = 0;
    while (is_object(obj_owner)) {
        count += 1;
        assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```
Additionally, consider preventing the creation of ownership cycles at `transfer_raw` time (e.g., reject a transfer if the destination's root-owner chain already passes through the source object), since cycles are unsound state independent of this particular bug and could affect other current or future consumers of `root_owner`/ownership traversal.

### Proof of Concept
1. As `alice`, create two objects `A` and `B` (e.g. via `object::create_named_object`), each initially owned by `alice`, with `allow_ungated_transfer = true`.
2. Deploy an object-hosted package to `A` via `object_code_deployment::publish`, with a module that calls `init::internal_maybe_initialize` (as in `aptos-move/e2e-move-tests/src/tests/init_module_api.rs` `OBJECT_MODULE_SRC`), so that `code::publish_package` records `A`'s deploy owner via `root_owner()`.
3. Call `object::transfer(alice, A, B)` then `object::transfer(alice, B, A)`, forming the cycle `A.owner == B`, `B.owner == A`.
4. Invoke the object-hosted module's entry function that calls `init::internal_maybe_initialize`, or call `object_code_deployment::upgrade` on `A`: both paths call `root_owner()` on the cyclic chain, causing the VM to loop indefinitely (charging gas per iteration via repeated `borrow_global<ObjectCore>` reads) until the gas limit is exhausted and the transaction aborts, permanently denying self-init/upgrade for the object.

(Note: I was not able to independently execute this PoC in a sandbox — this is a code-review-derived scenario based on the read source; the described API sequence and function bodies were directly observed in the repository.)

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));

            // object's owner is not an object. So we return a more sensible error.

            assert!(

                error::permission_denied(ENO_UNGATED_TRANSFERS),

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        };

    }
