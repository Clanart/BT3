### Title
Unchecked u64 accumulation on attacker-controlled `ReceivedOutput`/`payments` values overflows, breaking the `NotEnoughFunds` check or panicking — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The Nibbl bug class is "cumulative accumulator arithmetic that must wrap (or be checked) instead overflows and permanently halts the system." In Serai's in-scope Bitcoin wallet code, `SignableTransaction::new` and `SignableTransaction::fee` accumulate `u64` satoshi values with plain `sum::<u64>()` / `+` / `-` over values that originate from untrusted deserialization (`ReceivedOutput::read` decodes a raw `TxOut` via consensus_decode, so `output.value` is fully attacker-controlled up to 2^64-1 sats) and from the `payments`/`fee_per_vbyte` parameters. Neither a wrapping nor a checked policy is applied, so these sums overflow.

### Finding Description
Three unchecked accumulations exist in `SignableTransaction`:

- `input_sat` sums every input's `output.value.to_sat()` (networks/bitcoin/src/wallet/send.rs:175). `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) is an untrusted-byte sink that consensus-decodes `TxOut` and `OutPoint` with no bound on `value`, so a single crafted input can carry `u64::MAX` sats and two such inputs overflow the sum.
- `payment_sat` sums the payment amounts and is then used in `payment_sat + needed_fee` (send.rs:187, 215), which can itself overflow.
- `fee_per_vbyte * vbytes` (send.rs:206) and `fee_per_vbyte * vbytes_with_change` (send.rs:227) are unchecked multiplications; `fee_per_vbyte` is a caller parameter, so a large rate makes `needed_fee` wrap to a small value, defeating both the `TooLowFee` minimum-relay-fee check and the `NotEnoughFunds` comparison.
- `fee()` (send.rs:138-141) computes `sum(prevouts) - sum(outputs)` unchecked; if the wrapped `input_sat` check passed for a tx whose outputs exceed inputs, this subtraction underflows.

With overflow-checks enabled (debug builds, or `overflow-checks = true` in the profile) each of these panics — the exact analog of the Solidity revert that "breaks the contract," i.e., a permanent halt of the wallet-signing path reachable purely from crafted bytes fed to `ReceivedOutput::read`. Without overflow-checks the sums wrap silently: `input_sat < payment_sat + needed_fee` is bypassed, producing a `SignableTransaction` that misreports `needed_fee`/`fee()` and commits real prevouts (via the Taproot `Prevouts::All` sighash, which binds input amounts) into a transaction whose economics were never actually validated.

### Impact Explanation
- DoS: any consumer that parses untrusted `ReceivedOutput`s and feeds them into `SignableTransaction::new` panics on the overflowing sums — same failure mode as the Nibbl cumulative-price revert.
- Silent wraparound: the `NotEnoughFunds` and `TooLowFee` guards are defeated, so a transaction is constructed and marked signable whose fee accounting is wrong by ~2^64 sats; every signature over it uses `sighash` commitments to amounts that were never honestly checked.

### Likelihood Explanation
The panic path only requires two `ReceivedOutput`s with large `TxOut.value` reaching `SignableTransaction::new`; `ReceivedOutput::read` performs no sanity bound on the decoded `Amount`. The wraparound path requires a caller-controlled `fee_per_vbyte` or crafted inputs to push a `sum`/`product` past `u64::MAX`. Triggering depends on build overflow-check settings and on whether an attacker can inject crafted `ReceivedOutput` bytes into a signing flow — but the arithmetic itself is unconditionally unchecked, which is the defect, mirroring the report's acknowledgment that the cumulative lines simply needed `unchecked`/checked handling.

### Recommendation
Replace the raw sums/products with checked arithmetic and return `TransactionError` on failure: use `checked_add`-folds (or `try_fold`) for `input_sat`, `payment_sat`, and both `sum`s in `fee()`; use `fee_per_vbyte.checked_mul(vbytes)` / `checked_mul(vbytes_with_change)` for `needed_fee`; and compare `input_sat` against `payment_sat.checked_add(needed_fee)`. This matches the report's spirit (explicit overflow semantics on cumulative accumulators) while choosing fail-closed errors rather than wrapping, since unlike TWAV cumulative prices, satoshi totals are not designed to wrap.

### Proof of Concept
1. Construct two `ReceivedOutput`s via `ReceivedOutput::read` where each consensus-decoded `TxOut.value` is `u64::MAX - 100` (offset arbitrary scalar, outpoint arbitrary).
2. Call `SignableTransaction::new(inputs, &[(script, DUST)], Some(change), None, 1)`.
3. `input_sat` = sum of the two values overflows: panic under overflow-checks, or wraps to a small value under wrapping semantics.
4. Alternatively, a single input plus `fee_per_vbyte = u64::MAX` makes `needed_fee = fee_per_vbyte * vbytes` wrap to a tiny value, passing `TooLowFee` and `NotEnoughFunds` while the true required fee is enormous; `fee()` then underflows when reporting.

Relevant code: `input_sat`/`payment_sat`/`needed_fee` accumulation and the `NotEnoughFunds` check at send.rs:175-221, `fee()` at send.rs:138-141, and the unbounded `TxOut::consensus_decode` in `ReceivedOutput::read` at mod.rs:122-134.
