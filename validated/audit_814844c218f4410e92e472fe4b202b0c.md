### Title
Contract-in-construction bypasses ERC1155/ERC721 safe-transfer receiver check via `code.length` isContract pattern - (File: contracts/src/CW1155ERC1155Pointer.sol)

### Summary
The `CW1155ERC1155Pointer` and the bundled `ERC721`/`MyNFT` example contract in `contracts/src/` use the classic `to.code.length == 0` / `to.code.length > 0` pattern to decide whether a transfer recipient is a "contract" and therefore requires the `onERC1155Received`/`onERC721Received` callback check. This is the exact bug class flagged in the external report for `Address.isContract`: during a contract's own constructor execution, `extcodesize`/`code.length` for that address still returns `0`, so the check incorrectly treats an in-construction contract as an EOA.

### Finding Description
`CW1155ERC1155Pointer.safeTransferFrom` and `safeBatchTransferFrom` gate the ERC1155 receiver-interface check purely on code size: [1](#0-0) 

Likewise, the bundled `ERC721.safeTransferFrom` implementations use the same pattern: [2](#0-1) 

If a contract calls `safeTransferFrom`/`safeBatchTransferFrom` targeting `address(this)` (or another contract under construction) from within its own constructor, `to.code.length` is `0` at that point in EVM execution, so the pointer contract skips the `onERC1155Received`/`onERC721Received` callback entirely and completes the transfer as if the recipient were an EOA.

### Impact Explanation
Because these pointer contracts bridge CW1155/CW721 (CosmWasm) token ownership into the EVM side via the wasmd precompile (`_execute` → `WasmdPrecompile`), a successful transfer to a contract that cannot actually handle ERC1155/ERC721 tokens (because it never implements the receiver interface, or implements it only after construction) can result in the underlying CW-side asset becoming permanently locked/unrecoverable by that contract if it has no functions to move the token back out. This matches the "permanent freezing of funds" impact category.

However, the actual severity is bounded: it requires the *attacking contract's own deployer* to intentionally target `address(this)` (or a colluding not-yet-deployed contract address) during construction, and any resulting lock-up primarily harms the constructing party's own assets rather than a third party's, unless combined with a scenario where a third party is tricked into sending tokens to a not-yet-deployed contract address (e.g., a CREATE2 precomputed address) before deployment completes.

### Likelihood Explanation
Low-to-moderate. Exploitation requires a specific and somewhat unusual call pattern (transferring to a not-yet-fully-constructed contract, typically only reachable by the deployer within the constructor itself, or via a precomputed CREATE2 address before deployment). It is not exploitable by an arbitrary third party against an already-deployed contract.

### Recommendation
Do not rely solely on `code.length`/`extcodesize` to distinguish EOAs from contracts in `CW1155ERC1155Pointer.sol` and `ERC721.sol`. Where feasible, always require and check the receiver callback's return value regardless of code size (OpenZeppelin's newer `ERC1155`/`ERC721` implementations already do this by always attempting the callback and only special-casing based on a `try/catch` rather than pre-checking code size), or document/accept the known limitation explicitly since it mirrors long-standing OpenZeppelin behavior.

### Proof of Concept
1. Deploy an attacker contract `Evil` whose constructor computes its own address via `address(this)`.
2. Inside `Evil`'s constructor, call `CW1155ERC1155Pointer.safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` (assuming `Evil`'s deployer has approved/owns the CW1155 balance being pointed to).
3. Because `address(this).code.length == 0` during construction, the pointer skips the `onERC1155Received` check at: [3](#0-2) 
4. The CW-side `send` message executes and the token is credited to `Evil`, even though `Evil` may never implement `onERC1155Received`/`onERC1155BatchReceived` after construction, leaving the underlying token permanently unrecoverable through the standard ERC1155 receiver-safety guarantee.

**Note**: I could not locate an equivalent `code.length` pattern in `CW721ERC721Pointer.sol` (no matches found for `code.length`/`onERC721Received` in that file), so the CW721 pointer does not appear to share this exact issue — only the bundled example `ERC721.sol`/`MyNFT` contracts and `CW1155ERC1155Pointer.sol` do. Given the index size limits, I was not able to fully confirm whether `CW721ERC721Pointer.sol` implements safe-transfer receiver checks by another mechanism; a full read of that file via a Devin session would confirm this.
