[1](#0-0) ### Title
Malformed per-input FROST preprocess vector causes a remote signing panic - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`TransactionSignMachine::sign` assumes every participant supplied one FROST `Preprocess` for every transaction input. It indexes `commitments[c]` without checking the vector length, so a participant can submit a structurally valid preprocess vector for a shorter transaction and panic the signer. [1](#0-0) 

### Finding Description
For a transaction with `self.sigs.len()` inputs, `TransactionSignMachine::sign` builds a separate participant map for each input by iterating `0 .. self.sigs.len()` and indexing each participant’s `Vec<Preprocess>` at `c`. [2](#0-1)  Although `read_preprocess` parses exactly one preprocess per input when successful, the public `sign` API accepts caller-supplied `HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>>` values and does not verify that each vector has `self.sigs.len()` elements. [3](#0-2) 

A participant can therefore replay or otherwise provide a valid preprocess vector from a transaction with fewer inputs. During a two-input signing session, the panic occurs deterministically when `c == 1` evaluates `commitments[1]` on a vector containing only index `0`. [1](#0-0) 

The same missing-per-input-field pattern exists in `TransactionSignatureMachine::complete`, which calls `shares.remove(0)` for each input without checking that every participant supplied enough signature shares. [4](#0-3) 

### Impact Explanation
A remote participant can crash the local signing task or process before the FROST `validate_map` checks in the inner `AlgorithmSignMachine::sign` are reached. [5](#0-4)  Repeating the malformed preprocess prevents completion of affected multisignature transactions. This is a denial of service consistent with a Medium severity availability impact; it does not appear to disclose key material or forge a signature.

### Likelihood Explanation
Any party allowed to submit a preprocess for a multi-input Bitcoin spend can trigger the panic by supplying a valid but short `Vec<Preprocess>`. No secret access or cryptographic break is required. The malformed value must reach `TransactionSignMachine::sign` as an object; a truncated byte stream passed directly to `read_preprocess` returns an I/O error instead. [3](#0-2) 

### Recommendation
Before indexing participant preprocesses, reject any participant whose vector length differs from `self.sigs.len()`, returning `FrostError::InvalidPreprocess(participant)` or `FrostError::InvalidParticipantQuantity`. Apply the same length check to each participant’s `Vec<SignatureShare>` in `complete` before calling `remove(0)`.

### Proof of Concept
```rust
use std::collections::HashMap;

use frost::{Participant, sign::SignMachine};

// `sign_machine` is a TransactionSignMachine for a transaction with two inputs.
// `short_preprocess` is a syntactically valid Vec<Preprocess> containing only
// one element, such as a clone obtained from a one-input signing session.
fn crash(
  sign_machine: impl SignMachine<
    bitcoin::Transaction,
    Preprocess = Vec<frost::sign::Preprocess<frost::curve::Secp256k1, ()>>,
  >,
  attacker: Participant,
  short_preprocess: Vec<frost::sign::Preprocess<frost::curve::Secp256k1, ()>>,
) {
  assert_eq!(short_preprocess.len(), 1);

  let mut commitments = HashMap::new();
  commitments.insert(attacker, short_preprocess);

  // Panics at networks/bitcoin/src/wallet/send.rs:368 while evaluating
  // `commitments[c]` for c == 1.
  let _ = sign_machine.sign(commitments, b"");
}
```
