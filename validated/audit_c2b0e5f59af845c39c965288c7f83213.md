### Title
Unhandled `AssertionError` when parsing a malformed offer with duplicate coin spends causes a spend-triggered processing halt - ([File: chia/wallet/trading/offer.py])

### Summary
Similar to CVE-2023-37020, where an Open5GS MME crashes on a malformed S1AP message missing a required field, the chia-blockchain `Offer` class contains a bare `assert` statement that fires on attacker-controlled, unvalidated input during offer parsing. In `Offer.__post_init__`, every coin spend in the offer's underlying bundle is checked with `assert cs.coin not in adds` before any exception-handling wraps it, so a malicious offer containing a duplicate `CoinSpend` (same parent id, puzzle hash, and amount) raises an unhandled `AssertionError` rather than a graceful validation error. [1](#0-0) 

### Finding Description
`Offer` objects are constructed from fully attacker-controlled bytes via `Offer.from_bech32()` → `try_offer_decompression()` → `from_bytes()` → `from_spend_bundle()`, which is the standard path any wallet takes to inspect an offer file received from a counterparty (e.g. `chia offer take`, `get_offer_summary`, `check_offer_validity`). [2](#0-1) 

Once the `WalletSpendBundle` is decoded, the dataclass `__post_init__` hook iterates the coin spends to populate the additions/hints cache. Before any cost-limited CLVM execution or exception handling occurs, it performs:
```python
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
    try:
        hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
        ...
``` [3](#0-2) 

This `assert` is not inside the subsequent `try/except` block, and Python's `AssertionError` is not caught anywhere upstream in the offer-parsing call chain (`from_bech32`, `from_bytes`, `from_spend_bundle`). Because `Coin` equality/hash is based on its content (parent id, puzzle hash, amount), an attacker can trivially construct an offer file whose serialized `WalletSpendBundle` contains two identical `CoinSpend` entries for the same coin. Parsing that offer through `Offer.__post_init__` (invoked implicitly by the `@dataclass` machinery every time an `Offer` instance is constructed) immediately raises `AssertionError`, which is not a `ValueError`/`ValidationError` and therefore is not handled by the `try/except ValueError` / `except Exception: continue` guard that only wraps the inner CLVM execution, not the assert itself.

This is directly analogous to the CVE-2023-37020 bug class: a required-invariant check implemented as a raw assertion, triggered by attacker-supplied, malformed protocol data, resulting in an unhandled crash of the message-processing code path rather than a controlled rejection.

### Impact Explanation
Any code path that calls `Offer.from_bech32()` on untrusted input — `get_offer_summary`, `check_offer_validity`, `take_offer` RPCs, or CLI commands that display/verify an offer before accepting it — will raise an unhandled `AssertionError` when fed a malicious offer file. Depending on how the RPC/CLI layer handles unexpected exception types (as opposed to the expected `ValueError`/`ValidationError`), this can manifest as a request failure or, in the worst case, an uncaught exception bubbling out of the async task handling the wallet RPC connection, effectively halting processing of that request repeatedly if the offer is retried or shared with multiple wallets (denial of service for anyone who examines the malicious offer, i.e. any offer counterparty). It does not appear to allow direct fund theft or coin-state divergence; the primary consequence is unauthorized denial of service against a wallet user or wallet RPC caller who inspects a hostile offer, matching the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Likelihood is high for a targeted DoS: any user who receives and inspects (not even accepts) a maliciously-crafted offer file via the normal `get_offer_summary`/`check_offer_validity`/`take_offer` workflow triggers the crash. No signature or spend authorization is required to build the malformed offer — only crafting a `WalletSpendBundle` with a duplicated `CoinSpend` entry, which is fully within the control of anyone producing an offer file.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit input-validation check that raises a caught, well-typed exception (e.g. `ValidationError` or `ValueError`) consistent with the rest of the parsing logic, and ensure it is included within (or ahead of and covered by) the surrounding exception handling so that malformed/duplicate coin spends in an offer are rejected gracefully instead of raising an unhandled `AssertionError`. More broadly, audit other bare `assert` statements reachable from untrusted offer/spend-bundle parsing paths (e.g. `assert asset_id is not None` at line ~644 of the same file) and convert them to proper validation with typed exceptions.

### Proof of Concept
1. Construct two identical `CoinSpend` objects (same `Coin(parent_coin_info, puzzle_hash, amount)`, arbitrary/valid puzzle reveal and solution).
2. Build a `WalletSpendBundle` containing both duplicate `CoinSpend`s plus a valid aggregated signature (or `G2Element()` if the code path used only decodes without signature validation before failure).
3. Serialize via `Offer(requested_payments={}, _bundle=bundle, driver_dict={})`-equivalent construction, or directly craft the serialized bytes matching the format expected by `Offer.from_bytes`, and encode with `to_bech32()`.
4. Feed the resulting bech32 string to `Offer.from_bech32()` (e.g. via the `get_offer_summary` or `check_offer_validity` wallet RPC).
5. Observe that construction of the `Offer` object raises `AssertionError` from `Offer.__post_init__` at `assert cs.coin not in adds`, uncaught by the surrounding parsing logic.

Note: I was not able to directly inspect `chia/rpc/rpc_server.py`'s top-level exception-handling behavior for RPC endpoints in this session (tool access to that file failed), so I cannot confirm with certainty whether the RPC framework converts this `AssertionError` into a benign error response or whether it can crash/hang the request-handling task; this should be verified in the full codebase before treating the DoS as service-wide rather than per-request.
