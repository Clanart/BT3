### Title
Attacker floods the multisig with dust outputs that become mandatory inputs, inflating every spend until transactions are unpayable/unrelayable - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Surge `deploySurgePool` array-filling DoS, any unprivileged party can grow Serai's effective "pool" — the set of UTXOs the Bitcoin wallet treats as spendable — simply by sending Bitcoin transactions to the multisig's P2TR script. `Scanner::scan_transaction` returns every output paying to a registered script with no minimum-value or per-transaction limit, and `SignableTransaction::new` has no coin selection: it unconditionally packs *every* `ReceivedOutput` it is given into a single transaction as an input. An attacker who repeatedly dusts the wallet forces either (a) `TooLargeTransaction` once the input count pushes the transaction past `MAX_STANDARD_TX_WEIGHT`, or (b) net-negative spends where the marginal fee per input exceeds the dust's value.

### Finding Description
`Scanner::scan_transaction` iterates all outputs of every transaction and pushes a `ReceivedOutput` for any whose `script_pubkey` matches a registered script, with no amount check (`wallet/mod.rs:199-214`). The only dust filter lives in the out-of-scope processor (`processor/src/multisigs/scanner.rs:564` filters `< N::DUST`); `bitcoin_serai::wallet::Scanner` itself accepts even 1-sat outputs.

`SignableTransaction::new` consumes the entire `inputs: Vec<ReceivedOutput>` — `input_sat`, `offsets`, and `tx_ins` are all built from the full vector (`send.rs:175-185`) — and `TransactionMachine::multisig`/`sign` create one FROST `AlgorithmMachine` and one `Prevouts::All` key-spend signature *per input* (`send.rs:273-285`, `send.rs:373-395`). The only bound is the `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241-243`, which produces a hard error rather than dropping excess inputs.

Two consequences:
1. **Oversized-transaction DoS.** Once the wallet's UTXO set exceeds ~1,700 inputs (Taproot key-spend input ≈ 58 vB vs `MAX_STANDARD_TX_WEIGHT` = 400,000 WU), `SignableTransaction::new` fails with `TooLargeTransaction` for any spend that includes all received outputs — and since the API provides no input selection, nothing in-crate lets the caller shed inputs.
2. **Economic griefing.** Each added input contributes its value to `input_sat` but adds its weight to `needed_fee = fee_per_vbyte * vbytes` (`send.rs:204-206`). An input worth 546 sats (the in-scope `DUST` constant) costs ~58 vB to spend; whenever `fee_per_vbyte` exceeds ~9.4 sat/vB, every attacker-created input burns more than it contributes, draining wallet funds into fees on every withdrawal.

### Impact Explanation
An unprivileged attacker who knows the (public) multisig address can permanently degrade the wallet: spends either fail outright with `TooLargeTransaction` or pay super-linearly inflated fees, since every attacker's output becomes a mandatory input in the next transaction. Each input also forces an additional FROST signing session (`sigs` vector, `send.rs:274-282`), multiplying coordinator signing work per transaction. This maps directly onto the report's "fill the array to DoS the protocol" class: the array is the wallet's UTXO/inputs set, and there is no upper bound or admission cost beyond one dust output per input slot.

### Likelihood Explanation
The attack requires only sending Bitcoin transactions to the multisig's script_pubkey — no validator status, no key material, no protocol participation. Cost is ~546 sats per input (recoverable neither by attacker nor wallet), so raising the input count to the weight cap costs under ~0.01 BTC, while the DoS/griefing persists for the wallet's lifetime since outputs are never excludable at the wallet layer.

### Recommendation
- Add coin selection / an explicit input bound to `SignableTransaction::new` (e.g., greedily include inputs by value until `payments + fee` is covered, or cap `inputs.len()` so weight stays below `MAX_STANDARD_TX_WEIGHT`), rather than always spending all provided inputs.
- Reject inputs whose value is below the marginal spend cost (`input_weight_vbytes * fee_per_vbyte`) inside the wallet, not only via the processor's `N::DUST` check.
- Consider filtering sub-dust outputs in `Scanner::scan_transaction` itself so the wallet crate never reports economically unspendable outputs as received.

### Proof of Concept
Conceptual (library-level):
1. From the public multisig key `K`, compute `script = p2tr_script_buf(K)` (`wallet/mod.rs:164`) and broadcast `N` Bitcoin transactions each paying ≥546 sats to `script`. No offset registration is needed — the base script is always in `Scanner::scripts`.
2. The node's `Scanner::scan_block` returns all `N` `ReceivedOutput`s (`wallet/mod.rs:221-227`).
3. Construct `SignableTransaction::new(all_outputs, &[(dest, amount)], Some(change), None, fee_per_vbyte)`. For `N` large enough that `N * ~232 WU + outputs > 400_000 WU`, the call returns `Err(TransactionError::TooLargeTransaction)` (`send.rs:241-243`) — the wallet cannot spend despite holding sufficient balance.
4. Alternatively, at `fee_per_vbyte = 100`, each 546-sat attacker input adds ~58 vB ≈ 5,800 sats of fee for 546 sats of value (`send.rs:175`, `send.rs:204-206`), so the forced-inclusion of attacker outputs makes `input_sat < payment_sat + needed_fee` → `NotEnoughFunds`, or silently burns the difference as fee.

Relevant code: `Scanner::scan_transaction` at `networks/bitcoin/src/wallet/mod.rs:199-214`; `SignableTransaction::new` input handling at `networks/bitcoin/src/wallet/send.rs:150-185`, fee/weight checks at `send.rs:204-243`, per-input signature machines at `send.rs:273-285` and `send.rs:373-395`.
