### Title
Missing reentrancy protection in `BridgeTransferERC20._requestERC20Transfer` allows registered ERC20/ERC777-hybrid tokens to reenter the Kaia value-transfer bridge before `requestNonce` is finalized - (File: `contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary
`BridgeTransferERC20` performs multiple external calls to an arbitrary (but owner-"registered") ERC20 token contract — `safeTransfer` for fee refund/collection and `ERC20Burnable(_tokenAddress).burn(_value)` — inside `_requestERC20Transfer`, with no `nonReentrant` guard, unlike the sibling KLAY path which is explicitly documented and implemented as reentrancy-safe.

### Finding Description
`_requestERC20Transfer` in [1](#0-0)  executes, in order: `_payERC20FeeAndRefundChange` (which does `IERC20(_token).safeTransfer(...)` to both `feeReceiver` and back to `from`, see [2](#0-1) ), then `ERC20Burnable(_tokenAddress).burn(_value)` when `modeMintBurn` is set, and only afterwards emits `RequestValueTransfer` and increments `requestNonce`. None of `_requestERC20Transfer`, `requestERC20Transfer`, or `onERC20Received` carry a `nonReentrant` modifier.

This is the same bug class as the Agave Finance exploit in the report: an external call embedded in a token transfer/burn operation (which, for ERC777/ERC677-style or hook-bearing tokens, invokes a callback such as `tokensToSend`/`tokensReceived` before the caller's bookkeeping is finalized) lets the callee re-enter the caller contract while state (`requestNonce`, handled-request bookkeeping) is stale.

By contrast, `BridgeTransferKLAY._requestKLAYTransfer` explicitly inherits `ReentrancyGuard` and is marked `nonReentrant` ( [3](#0-2) ), and `BridgeFee.sol`'s own comment states the precondition "Caller of this function must be nonReentrant. - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant" ( [4](#0-3) ) — but no equivalent guard/comment exists for `_payERC20FeeAndRefundChange`'s ERC20 caller. `BridgeTransferERC20` is declared as `contract BridgeTransferERC20 is BridgeTokens, IERC20BridgeReceiver, BridgeTransfer` with no `ReentrancyGuard` in its inheritance list ( [5](#0-4) ), confirming the asymmetry with the KLAY path.

The registration model (`onlyRegisteredToken`) requires the token address to be added by the bridge owner via `registerToken` ( [6](#0-5) ), so this is not exploitable by an arbitrary attacker-supplied token unless the owner registers a token whose `burn`/`transfer` implementation performs callbacks (e.g., an upgradeable/proxy token, or a token with post-transfer hooks) — a realistic scenario for third-party bridged ERC20s where the registering operator does not fully control or audit the token's bytecode/upgrade path.

### Impact Explanation
If a registered token contains a transfer/burn hook that calls back into the bridge (`requestERC20Transfer`/`onERC20Received`) mid-execution, an attacker can reenter before `requestNonce` is incremented and before the burn/fee flow of the outer call completes. Depending on exact reentry point, this can lead to duplicated `RequestValueTransfer` events with the same `requestNonce` (nonce collision/desync between the two bridge sides), inconsistent burn accounting (tokens burned once but two transfer requests recorded), or draining of the fee-refund path (`_payERC20FeeAndRefundChange` transferring more than intended) — all of which constitute unauthorized value movement or state divergence between the two ends of the bridge, satisfying the "Medium/High" bar for financial-impact bugs.

### Likelihood Explanation
This requires the bridge operator to register a token with a transfer/burn hook back into the bridge — not attacker-controlled by default, so likelihood is lower than a fully public unauthenticated path, but the surface (`onERC20Received`, `requestERC20Transfer`) is reachable by any unprivileged sender once such a token is registered, and no code-level control (like `nonReentrant`) currently prevents exploitation if that precondition is met. Given ERC20 bridges commonly wrap third-party or upgradeable tokens outside the bridge deployer's control, this is a plausible operational scenario.

### Recommendation
Add `ReentrancyGuard`/`nonReentrant` to `BridgeTransferERC20`'s `_requestERC20Transfer`, `requestERC20Transfer`, `onERC20Received`, and `handleERC20Transfer` (mirroring `BridgeTransferKLAY`), and apply the check-effects-interactions pattern: increment `requestNonce`/emit event before performing the external `burn`/`safeTransfer` calls, or use a global mutex shared across the ERC20/ERC721/KLAY transfer paths.

### Proof of Concept
Conceptual PoC (mirroring the Agave PoC structure): the bridge owner registers `EvilToken` (compliant with `ERC20Burnable`) whose `burn()` override calls back into `bridge.requestERC20Transfer(EvilToken, attacker, amount, 0, "")` before returning. A user calls `requestERC20Transfer(EvilToken, to, amount, 0, "")` on the bridge with `modeMintBurn = true`; inside `_requestERC20Transfer`, `ERC20Burnable(EvilToken).burn(amount)` reenters `requestERC20Transfer` again before `requestNonce++` from the outer call executes, causing two `RequestValueTransfer` events to be emitted referencing overlapping/duplicate nonces and/or amounts burned only once while two withdrawal requests are recorded, which the counterpart chain's operator would then honor as two separate value-transfer handles from a single burn.

```text
    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
