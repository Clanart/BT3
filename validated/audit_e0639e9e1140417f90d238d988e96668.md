### Title
Unauthenticated cross-chain bandwidth purchase lets any payer evict another app's paid subscriptions before expiry - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
The core broken invariant in the external report is that a party can force a *committed* position (Rider's lock, which Horse's delegated voting power depends on) to unwind early through an action that is nominally "someone else's" (the blocklist), without the forcing mechanism honoring the original commitment terms. The local analog is `pallet-bandwidth`'s sponsorship model: any account, on any chain, can dispatch a `BandwidthPurchaseMsg` naming an arbitrary victim `(app_chain, app)` pair. Because the FIFO subscription list is capped at 1024 and a push onto a full list evicts the *oldest* entry regardless of who purchased it or how much of its committed duration/bytes remain unused, an unrelated, unprivileged actor can force early termination of another app's already-paid-for bandwidth commitment.

### Finding Description
`pallet-bandwidth` keys its `Allowance` storage by `(app_chain, app)` taken from the purchase message body, not by `request.source`, explicitly to support "sponsorship" — a buyer on one chain crediting an app on another chain: [1](#0-0) 

This is also documented as intentional multi-tenant behavior: "The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`... a treasury on a single chain can sponsor bandwidth for an app deployed across many chains" [2](#0-1) 

Each purchase appends a new `Subscription` row to a `BoundedVec` capped at 1024 entries. A subscription's `expires_at` is fixed at purchase time and can never be extended — it is immutable, and a repurchase does not "renew" an existing entry, it always queues a new one: [3](#0-2) 

Critically, pushing onto a full (1024-entry) list evicts the **oldest** entry, unconditionally, and this loss is only logged via an event — there is no protection based on remaining value, ownership, or who is doing the pushing: "Pushing onto a full list (1024 entries) evicts the oldest entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain." [4](#0-3) 

Because `(app_chain, app)` is attacker-controlled (any purchaser can name any `app_chain`/`app` in the message body dispatched from `BandwidthManager.sol`), and there is no check binding the purchaser to the app being credited, an attacker can flood a victim's `(app_chain, app)` queue with 1024 cheap (e.g. `TierOne`) purchases. This evicts the victim's legitimately-purchased, still-live, higher-tier subscriptions (larger byte allowance, longer remaining duration) before they were consumed or expired — an outcome functionally identical to forcing early termination of someone else's paid-up commitment, the same broken invariant as `forceUndelegate()` truncating Horse's committed lock via an externally triggerable, unprivileged action (Rider's own block).

### Impact Explanation
This is a loss-of-funds / bandwidth-balance impact: the victim app paid real ERC-20/native fee tokens for a tier's `(bytes, duration_secs)` allowance, and an unrelated third party can force that allowance to be forfeited early via `SubscriptionEvicted`, with no recourse or refund path (`force_credit` is admin-only and would require governance intervention to compensate). This directly matches the bounty's "bandwidth balances must move exactly once and only to the rightful beneficiary and amount" pivot — here, a paid-for balance is destroyed rather than consumed by its owner.

### Likelihood Explanation
Likelihood is moderate: the attack is fully permissionless (no relayer collusion, no admin, no leaked keys — a plain `purchase()` call on any registered source chain), but it does require the attacker to fund 1024 real purchases (at whatever the cheapest configured tier costs) to fully drain the FIFO cap for a targeted `(app_chain, app)`. This is an economic cost, not a technical barrier, and the cost scales with tier price, not with the value of the victim's evicted subscription — so it is profitable whenever a high-value target's subscription value exceeds `1024 × cheapest_tier_price`.

### Recommendation
- Bind bandwidth purchase eligibility to require the purchase either come from the app's own registered/authorized `request.source`+`from`, or explicitly opt the app into third-party sponsorship (e.g., an allowlist of approved sponsor chains per app, similar to the existing `Allowlist` gate-bypass mechanism).
- Alternatively, remove or bound eviction risk: instead of unconditionally evicting the oldest entry on overflow, reject the push (or require the *purchasing* account to pay to evict only its *own* prior entries), so a subscription can only be evicted by its rightful subscriber or after it is fully consumed/expired.
- At minimum, weight eviction by remaining value (bytes × time-to-expiry) so cheap spam purchases cannot force out high-value, long-lived allowances.

### Proof of Concept
1. Victim app buys a `TierFour` subscription (8 MB / long duration) via `BandwidthManager.purchase()` for `(app_chain = Base, app = VictimApp)`; `pallet-bandwidth::on_accept` appends this `Subscription` to `Allowance[(Base, VictimApp)]`.
2. Attacker, from any registered source chain (does not need to be Base or control VictimApp), calls `BandwidthManager.purchase()` 1024 times, each time setting the purchase payload's `chain = "EVM-Base"`, `app = VictimApp`, with the cheapest configured tier (e.g. `TierOne`).
3. Each purchase message is delivered to `pallet-bandwidth::on_accept`, which pushes a new `Subscription` onto `Allowance[(Base, VictimApp)]` per the documented FIFO/cap logic [5](#0-4) .
4. Once the list reaches 1024 entries, each further attacker purchase evicts the oldest entry — including the victim's original `TierFour` subscription — emitting `SubscriptionEvicted { app_chain: Base, app: VictimApp, tier: TierFour, lost_bytes }`.
5. VictimApp's paid-for, unconsumed, unexpired bandwidth allowance is destroyed with no refund, while the attacker only spent cheap `TierOne` purchase fees to force the eviction.

Note: I could not directly inspect the `on_accept`/credit push implementation inside `modules/pallets/bandwidth/src/lib.rs` (tool budget exhausted before retrieving that exact code region), so the precise storage-mutation call (e.g. `BoundedVec::force_push` vs. manual `remove(0)`+`push`) is inferred from the pallet's own doc comments and the public documentation rather than confirmed line-by-line in the eviction function itself. The FIFO/cap/eviction behavior itself is explicitly documented in both the pallet's module doc [6](#0-5)  and the public overview docs cited above, and the `(app_chain, app)` keying being independent of `request.source` is directly evidenced by the storage definition [1](#0-0) .

//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s
//! (`BoundedVec`, capped at 1024). Every purchase appends a new
//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains
//! the oldest live subscription first; once empty it moves to the
//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit
//! [`Event::SubscriptionEvicted`].
//!
//! [`BandwidthGate`] is the hook the runtime's ISMP router consults
//! for every message; insufficient balance → rejected.
```

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

/// drains via the gate, `expires_at` is fixed at purchase time and
/// never extends. Repurchases append a new row instead of stacking.
#[derive(
	Encode, Decode, DecodeWithMemTracking, TypeInfo, MaxEncodedLen, Clone, PartialEq, Eq, Debug,
)]
pub struct Subscription {
	/// SKU this subscription was bought against; for analytics/events
	/// only — the gate doesn't look at it during drain.
	pub tier: TierIndex,
	/// Bytes left to spend. Decrements as the gate drains; the entry
	/// is popped once this hits zero.
	pub remaining_bytes: BandwidthBytes,
	/// Unix seconds. Gate sweeps entries where `expires_at <= now`.
	pub expires_at: u64,
	/// Unix seconds at insertion — fixes FIFO order under same-block buys.
	pub purchased_at: u64,
}
