I found a concrete accounting-mismatch analog in the Tron `IntentGatewayV2` escrow-withdrawal path that mirrors the yAxis bug class: a state variable used as a lock/accounting gate (`_orders[commitment][token]`) is checked with the wrong predicate (`== 0`, not `< amount`) relative to what is actually deducted, letting per-token escrow desync from what a caller can actually drain across repeated legs.

### Title
Tron `IntentGatewayV2.withdraw` checks `escrowed == 0` instead of `escrowed >= amount`, allowing escrow-state corruption when settlement legs are mis-sequenced - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of the Intent Gateway diverged from the audited/tested main-EVM `IntentsBase._withdraw` logic. The main EVM contract stores `escrowed` in a local variable and computes `_orders[commitment][token] = escrowed - amount` [1](#0-0) , whereas the Tron variant re-reads and decrements the mapping directly, guarding only with `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` before transferring `amount` and only afterward subtracting it: [2](#0-1) .

### Finding Description
This is the same bug shape as the yAxis `setCap` report: a balance/escrow ledger is decremented by a value that isn't validated against what's actually available before the transfer executes, and the guard checks the wrong condition (`== 0` presence check instead of a sufficiency check). In the Tron contract's `withdraw()`, for every `body.tokens[i]`, the code performs the external transfer (`beneficiary.call{value: amount}` or `token.call(transfer, amount)`) unconditionally once `_orders[...][token] != 0`, and only then does `_orders[body.commitment][token] -= amount`. Because Solidity 0.8's checked arithmetic will revert on underflow, a single-leg call is “safe” in the sense that it won't overflow silently — but the sequencing is a direct regression compared to the hardened same-chain path, which was specifically patched (see the regression test comment "same-chain partial fills over-release repeated input escrow") [3](#0-2) . The Tron contract's `withdraw` has no equivalent duplicate-token guard and no local snapshot of `escrowed` before mutating state, meaning the same order type of drift that the `setCap` bug exemplifies — using a stale/insufficiently-checked quantity to update an accounting map — is reintroduced in this codepath.

### Impact Explanation
If `body.tokens` (attacker/relayer-controlled via the decoded `WithdrawalRequest` on an authenticated but externally-triggered `onAccept`/`onGetResponse` path) contains a duplicate token entry, the first iteration transfers `amount` and decrements escrow to `escrowed - amount`; the second iteration re-reads the now-reduced value, and because the guard is only "escrowed != 0" (not "escrowed >= amount"), it will attempt another full-`amount` transfer against a smaller balance. The transfer call for tokens uses a raw low-level `.call(...)` return-value check rather than `safeTransfer`, so a token that returns `false` on insufficient balance rather than reverting would let the second leg's transfer silently no-op while the code still proceeds to underflow-revert only for standard ERC20s — for non-standard/permissive tokens this can desynchronize on-chain token balance versus the internal `_orders` ledger, exactly the "wrongly handles balance" pattern in the report (deducting a fixed amount rather than the actual delta), risking either a stuck/locked order (permanent revert path once `_orders` and real balances diverge) or a double-payout for tokens with non-reverting transfer semantics.

### Likelihood Explanation
This is reachable through the ordinary `onAccept`/`onGetResponse` cross-chain settlement paths that any relayer can deliver once a valid Hyperbridge message exists (`RedeemEscrow`/`RefundEscrow`), not through a malicious peer/operator — the vulnerable code executes on **every** withdrawal, and the missing sufficiency check plus missing duplicate-token protection (present as an explicit test/regression fix in the mainline EVM contract but absent on Tron) is a straightforward divergence bug rather than a theoretical one. Exploitability depends on whether an order can be constructed with duplicate `TokenInfo` entries and whether the specific token deviates from strict ERC20 revert-on-failure semantics — this narrows but does not eliminate likelihood, and I could not fully verify from the indexed excerpt whether `_orders` population (the Tron equivalent of `placeOrder`) has the same duplicate-input rejection that the main EVM `IntentGatewayV2.sol` was patched with (`if (_orders[commitment][token] != 0) revert InvalidInput();`, [4](#0-3) ). This is the key open question for confirming full exploitability.

### Recommendation
Mirror the main EVM `IntentsBase._withdraw` pattern exactly in the Tron contract: snapshot `escrowed = _orders[commitment][token]`, require `escrowed >= amount` (not just `!= 0`) before any transfer, update the mapping before the external call (checks-effects-interactions), and reject duplicate input tokens at order-placement time the same way the main `IntentGatewayV2.sol` does.

2. If not rejected, construct an `Order` whose `inputs`/`WithdrawalRequest.tokens` contains the same token address twice with escrow `E` and request two legs each of amount `A` where `E < 2*A` but `E >= A`.
3. Deliver a `RedeemEscrow`/`RefundEscrow` message through `onAccept` referencing this order; trace whether the first leg transfers `A`, decrements `_orders` to `E-A`, and the second leg's guard (`_orders[...] == 0`) passes since `E-A != 0`, then either reverts (locking the order permanently, matching the "fund locked" impact in the seed report) or, for a non-reverting-on-failure token, silently drops the second transfer while other invariants (fees, `_filled`) still finalize — desynchronizing escrow accounting from on-chain balances.

**Uncertainty flag:** I was not able to fully confirm from the indexed code alone (a) whether Tron order placement enforces the same duplicate-input-token rejection as the mainline EVM contract, and (b) the exact token set deployed on Tron and whether any deviate from strict revert-on-failure ERC20 semantics. A background Devin session with full repo/tool access would be needed to trace the Tron `placeOrder` implementation and confirm end-to-end exploitability before treating this as fully proven.
