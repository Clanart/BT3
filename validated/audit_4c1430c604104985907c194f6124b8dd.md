### Title
Stale-height non-membership proof lets a timed-out request be refunded on the source chain after it was already delivered on the destination — double-settlement of bridged funds - ([File: evm/src/core/HandlerV2.sol])

### Summary
`handlePostRequestTimeouts` accepts a non-membership proof against *any* retained historical state commitment of the destination chain, as long as that commitment's timestamp exceeds the request's `timeoutTimestamp` and the configured challenge period has elapsed. It never requires the proof height to be the destination chain's *latest* verified height, nor checks whether a *later*, already-verified state commitment shows the request was in fact delivered. Because Hyperbridge retains a bounded but long window of historical state commitments per chain (hours, per `RETENTION_WINDOW_SECS` / `StateMachineCommitmentCap`), an attacker can submit a stale-but-valid non-membership proof for a request that has since been legitimately delivered, triggering the timeout refund path a second time on top of the successful delivery.

### Finding Description
`handlePostRequestTimeouts` in [1](#0-0)  performs these checks only:
1. Challenge period elapsed for `message.height`.
2. `state.stateRoot != 0` (the commitment is retained).
3. `request.timeout() > state.timestamp` is false, i.e. the destination chain's clock at `message.height` is past the request's `timeoutTimestamp`.
4. A non-membership proof of `REQUEST_RECEIPTS_STORAGE_PREFIX || commitment` against `state.stateRoot`.

It never checks that `message.height` is the destination chain's latest known height, nor that no later-verified commitment already records the receipt. The equivalent Substrate handler has the same shape — no freshness requirement is enforced in `timeout.rs`: [2](#0-1) .

Hyperbridge deliberately retains many historical state commitments rather than only the latest one, precisely so old proofs remain usable within a retention window: [3](#0-2) , with per-chain caps sized for multi-hour retention windows, e.g. `RETENTION_WINDOW_SECS = 6 * 60 * 60` [4](#0-3) .

This means: if a relayer delivers a `PostRequest` to the destination chain (writing its receipt at destination height `H2`, and honestly calling `onAccept`), the same request may still be provably absent from an *earlier* destination height `H1 < H2` that is still retained on the source chain and whose timestamp already exceeds the request's timeout (e.g. because the relayer was slow, or delivery happened right at the timeout boundary). Any permissionless caller — `handlePostRequestTimeouts` requires no special role, as documented ("Access: Permissionless") [5](#0-4)  — can submit a valid non-membership proof anchored at `H1` even after `H2`'s delivery has already occurred, and the source-chain host will accept it, since the code only checks the state at the caller-supplied height, not against the chain's most-recently verified state.

Once accepted, `host.dispatchTimeOut()` invokes `onPostRequestTimeout` on the source-chain app, which unconditionally re-credits the funds that were already burned/escrowed at dispatch time. For `HyperFungibleToken`, this re-mints the tokens to the original sender: [6](#0-5) . Because the destination side already minted the equivalent tokens to the beneficiary via `onAccept` [7](#0-6) , the net effect is that the same transfer is credited twice — once on each chain — inflating the token's cross-chain-backed supply. The IntentGateway's escrow-refund path (`_withdraw` / `onPostRequestTimeout`-analog cross-chain cancel flow) is exposed to the identical pattern wherever escrow release is gated purely by a timeout non-membership proof: [8](#0-7) .

The app-level timeout handler has no way to defend against this on its own: it cannot see the destination chain's delivery state — that information exists only in the light-client-verified state commitments the Handler chooses to accept, and the Handler does not enforce recency.

### Impact Explanation
This is a direct double-settlement / duplicate-claim vulnerability against bridged funds: value is credited on the destination chain (legitimate delivery) and again refunded on the source chain (stale timeout), for a single dispatched request. For `HyperFungibleToken` this mints tokens out of thin air on the source chain while the destination-chain mint also stands, breaking the 1:1 backing invariant of the bridged asset. For escrow-based flows (IntentGateway cross-chain fills/cancels) the analogous pattern would double-release escrowed funds. No malicious relayer, prover, or admin is required — the non-membership proof at the stale height is cryptographically valid and permissionlessly submittable by anyone monitoring chain state, which meets the "unauthorized transaction/execution" and "double-claim/double-settlement" impact categories in the bounty gate.

### Likelihood Explanation
The precondition is realistic and requires no adversarial relayer: any request whose delivery lands close to or shortly after its `timeoutTimestamp` (slow relayer, congested destination chain, or a relayer delivering right at the boundary) creates a window where an older, still-retained destination-chain commitment proves non-delivery while a newer one proves delivery. Given multi-hour commitment retention windows, this window is not a narrow single-block race — a permissionless caller has ample time to construct and submit the stale-height timeout proof after observing delivery. `handlePostRequestTimeouts` is explicitly permissionless, so no privileged role is needed to trigger it.

### Recommendation
Require the timeout handler to prove non-membership against the destination chain's *latest* verified state commitment (or at minimum, require the caller to additionally attest/verify that no state commitment more recent than `message.height` and more recent than the request's dispatch already contains the receipt), rejecting proofs anchored at superseded heights. Alternatively, once a request is delivered on the destination chain (receipt written), have the destination-chain host emit that fact into a channel the source-chain host can check before honoring any timeout for that commitment, or restrict valid timeout-proof heights to be monotonically the latest known height for that state machine at proof-submission time.

### Proof of Concept
1. Dispatch a `PostRequest` (e.g., `HyperFungibleToken.send()`) from Chain A to Chain B with `timeout = T`; tokens are burned on Chain A [9](#0-8) .
2. Chain B's finality advances; at height `H1` (timestamp `T1 > T`), the request has not yet been delivered (`requestReceipts[commitment] == 0`). A consensus update on Chain A stores and retains this commitment for `H1`.
3. Shortly after, a relayer delivers the request at Chain B height `H2 > H1` via the normal `handlePostRequests` flow, writing the receipt and calling `onAccept`, which mints the equivalent tokens to the beneficiary on Chain B.
4. Because Chain A still retains the `H1` state commitment (within its multi-hour retention window) and `handlePostRequestTimeouts` only validates against the caller-supplied height, anyone submits a `PostRequestTimeoutMessage` with `height = H1` and a valid non-membership proof of the receipt at `H1` (test pattern shown in [10](#0-9) , adapted to use a stale height retained after a later delivery height exists).
5. `handlePostRequestTimeouts` passes all its checks (challenge period elapsed, `state.stateRoot != 0`, `request.timeout() > state.timestamp`, valid non-membership proof at `H1`) and calls `dispatchTimeOut`, which invokes `onPostRequestTimeout`, re-minting the burned tokens to the original sender on Chain A [11](#0-10) .
6. Result: tokens now exist both as the beneficiary's mint on Chain B (step 3) and the sender's re-mint on Chain A (step 5) — a duplicated credit from a single burn.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }

| Parameter | Type | Description |
|-----------|------|-------------|
| `host` | `IHost` | The IHost contract |
| `message` | `GetTimeoutMessage` | Struct containing timed-out GET requests, height, and proof |

**Access:** Permissionless (can be called by anyone)

**Process:**
1. Validates challenge period has elapsed for the state commitment
2. Fetches state commitment at the specified height
3. For each timed-out request:
   - Verifies timeout timestamp has passed
   - Verifies request commitment exists
   - Verifies non-membership proof (request was not processed on destination)
   - Calls `onGetTimeout()` on source application via `host.dispatchTimeOut()`

**Important:**
- Requires a non-membership proof showing the request was not processed on the destination chain
- GET requests have no relayer fees, so no refunds occur
- Primarily for cleanup and state management

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) external override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
