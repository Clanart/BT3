## Finding: Missing MMR-leaf freshness check in the classic (ECDSA) BEEFY verifier path allows stale-leaf replay that stalls authority-set rotation

### Title
Classic BEEFY verifier (`verify_mmr_update_proof` / `verify_mmr_leaf`) accepts a stale `latest_mmr_leaf` paired with a fresh `signed_commitment`, allowing replay of an outdated `beefy_next_authority_set` — (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
The Rust BEEFY verifier has two code paths: the SP1 path (`sp1.rs`) and the classic ECDSA path (`lib.rs`). The SP1 path explicitly checks leaf freshness: [1](#0-0) 

The classic path's `verify_mmr_leaf` has no equivalent check — it only validates that exactly one leaf index was supplied and that the leaf's merkle inclusion proof verifies against `mmr_root`: [2](#0-1) 

Because an MMR is append-only, a historical leaf's inclusion proof against the *current, later* `mmr_root` is just as valid as a fresh leaf's proof — the same property the SP1 path's doc comment and the `Error::StaleMmrLeaf` doc comment both explicitly call out: [3](#0-2) 

Yet `Error::StaleMmrLeaf` is never constructed or checked for anywhere in `lib.rs`/`verify_mmr_update_proof`/`verify_mmr_leaf` — it is only used by `sp1.rs`. `grep` across the repo confirms `StaleMmrLeaf` only appears in `sp1.rs`, `SP1Beefy.sol`, and their respective tests/docs, never in the classic path or `EcdsaBeefy.sol`'s equivalent `verifyMmrLeaf`.

### Finding Description
`verify_mmr_update_proof` performs the update as follows: [4](#0-3) 

`verify_mmr_leaf` is called before the `beefy_next_authority_set` rotation logic, but it never compares `mmr.latest_mmr_leaf.parent_number_and_hash.0` (or any field derived from it) to `mmr.signed_commitment.commitment.block_number`. It only checks:
1. `leaf_indices.len() == 1`
2. The supplied `leaf_index`'s merkle proof verifies against `mmr_root` (which comes from the fresh, correctly-signed `signed_commitment`).

An unprivileged relayer can therefore submit a `ConsensusMessage` where:
- `signed_commitment` is fresh, correctly signed by the real (current or next) authority set, with `block_number` far ahead of `trusted_state.latest_beefy_height` (passes `StaleHeight` check).
- `latest_mmr_leaf` and `mmr_proof.leaf_indices` reference a genuinely old leaf (from an earlier block), together with the correct merkle proof of that old leaf's inclusion in the *current* MMR (computable by anyone with public archive/RPC access to the relay chain, since MMR proofs against later roots for older leaves are just normal append-only merkle arithmetic — no forgery of signatures or hashes required).

Since the old leaf's inclusion proof is cryptographically valid against the current `mmr_root`, `verify_mmr_leaf` succeeds. The subsequent authority-rotation check:

```rust
if mmr.latest_mmr_leaf.beefy_next_authority_set.id > trusted_state.next_authorities.id {
    trusted_state.current_authorities = trusted_state.next_authorities.clone();
    trusted_state.next_authorities = mmr.latest_mmr_leaf.beefy_next_authority_set.clone();
}
trusted_state.latest_beefy_height = latest_height;
```

only compares the *id*, not whether the leaf is the correct latest one for `block_number`. `latest_beefy_height` is unconditionally advanced to the new (fresh) `latest_height` regardless of whether the paired leaf is stale. This lets an attacker repeatedly push `latest_beefy_height` forward using fresh signed commitments while continuing to smuggle old leaves whose `beefy_next_authority_set.id` lags behind the real relay chain's rotation schedule (e.g., replaying any leaf from within the current session, all of which carry the same, now out-of-date, `next_authorities` id once the relay chain has moved further ahead). Because `StaleHeight` is keyed only off `latest_beefy_height`, once that height is advanced past the point where a legitimate, up-to-date leaf would be needed, honest relayers submitting the correct newer leaf for an even later block can still succeed later, but the light client can be kept perpetually "one session behind" — or, if driven far enough, the relay chain's authority sets can rotate past what the light client's `current_authorities`/`next_authorities` pair covers, causing `Error::UnknownAuthoritySet` on all subsequent proofs and permanently stalling the consensus client.

### Impact Explanation
This breaks the core "false remote state must never become trusted" invariant for consensus proofs. Suppressing/desynchronizing authority-set rotation on the light client either (a) freezes progress until the trusted authority sets fall permanently out of sync with the real relay chain (denial of service on the bridge's consensus updates, blocking all downstream cross-chain messaging), or (b) in combination with other assumptions, risks trusting a validator set the relay chain no longer relies on for finality if the classic verifier is used to gate cross-chain messages.

### Likelihood Explanation
The attacker only needs unprivileged relayer access to submit a `ConsensusMessage` (a normal, permissionless action in the bridge's message-handling flow) plus public RPC/archive access to the relay chain to fetch a genuinely old leaf and recompute its inclusion proof against the current MMR root — no validator collusion, no signature forgery, and no privileged operator access is required.

### Recommendation
Add the same freshness check present in `sp1.rs` to `verify_mmr_leaf` / `verify_mmr_update_proof` in `lib.rs`:
```rust
if mmr.latest_mmr_leaf.parent_number_and_hash.0.saturating_add(1) != latest_height {
    Err(Error::StaleMmrLeaf { parent_number: ..., block_number: latest_height })?;
}
```
Apply the equivalent check to `EcdsaBeefy.sol`'s `verifyMmrLeaf`, which has the identical gap (it computes `leafCount` from `relay.latestMmrLeaf.parentNumber` but never asserts `parentNumber + 1 == commitment.blockNumber`).

### Proof of Concept
The Rust test suite already demonstrates this exact bug pattern is caught for SP1 but not for the classic path: `rejects_sp1_proof_carrying_a_stale_mmr_leaf` in [5](#0-4)  asserts `Err(Error::StaleMmrLeaf { .. })` when `parent_number` is set 500 blocks behind `block_number`. No analogous test exists for `verify_mmr_update_proof`/`verify_mmr_leaf` in `lib.rs`, and manually constructing the equivalent scenario (fresh `signed_commitment`, old `latest_mmr_leaf` + valid append-only merkle proof against the fresh `mmr_root`) would pass `verify_mmr_leaf` and update `ConsensusState` with the stale `beefy_next_authority_set`.

```rust
fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}
```

```rust
#[test]
fn rejects_sp1_proof_carrying_a_stale_mmr_leaf() {
	use beefy_verifier_primitives::Sp1BeefyProof;

	const SET_ID: ValidatorSetId = 42;
	const BLOCK_NUMBER: u32 = 1_000;
	// Mainnet SP1Beefy verification key, as in the fixture test above.
	const VKEY: &str = "0x007d1720c695842ed647a1a72e981751f9b5e26fc5ca038523b23430a1292f08";

	let trusted_state = ConsensusState {
		latest_beefy_height: BLOCK_NUMBER - 1,
		beefy_activation_block: 0,
		mmr_root_hash: H256::zero(),
		current_authorities: authority_set(SET_ID, 100),
		next_authorities: authority_set(SET_ID + 1, 100),
	};

	let mut proof = Sp1BeefyProof {
		block_number: BLOCK_NUMBER,
		validator_set_id: SET_ID,
		mmr_leaf: MmrLeaf {
			version: MmrLeafVersion::new(0, 0),
			parent_number_and_hash: (BLOCK_NUMBER - 1, H256::zero()),
			beefy_next_authority_set: BeefyNextAuthoritySet {
				id: SET_ID + 1,
				len: 100,
				keyset_commitment: H256::zero(),
			},
			leaf_extra: H256::zero(),
		},
		headers: vec![],
		proof: vec![],
		nonce: H256::zero(),
	};

	// The leaf appended at `BLOCK_NUMBER` clears the freshness check and is only rejected
	// later, by the Groth16 verifier — so the check discriminates on leaf freshness alone.
	let fresh = sp_io::TestExternalities::default().execute_with(|| {
		crate::sp1::verify_sp1_consensus::<TestHost>(trusted_state.clone(), proof.clone(), VKEY)
	});
	assert!(matches!(fresh, Err(Error::Sp1VerificationFailed)), "got {fresh:?}");

	// Swap in a leaf from an earlier block, as an attacker replaying a historical leaf would.
	proof.mmr_leaf.parent_number_and_hash.0 = BLOCK_NUMBER - 500;
	let stale = sp_io::TestExternalities::default().execute_with(|| {
		crate::sp1::verify_sp1_consensus::<TestHost>(trusted_state, proof, VKEY)
	});
	assert!(matches!(stale, Err(Error::StaleMmrLeaf { .. })), "got {stale:?}");
}
```
