### Title
Cached FROST preprocess seed is never deleted, enabling deterministic nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The coordinator's `SigningProtocol::preprocess_internal` caches a FROST preprocess seed under `CachedPreprocesses` keyed only by `context`, then regenerates the identical nonces via `from_cache` on every subsequent call — including inside `share_internal` — and never deletes the entry. The bug class from the PCI advisory is "object still referenced/used after it should have been destroyed due to missing lifecycle ownership"; here the consumed preprocess seed is the resource that is logically freed (single-use nonce material) yet retained and reused. Because `seeded_preprocess` deterministically derives nonces from the seed, any second signing pass under the same context with a different effective challenge leaks the validator's MuSig secret key share. [1](#0-0) [2](#0-1) 

### Finding Description
`preprocess_internal` writes `CachedPreprocesses::set(txn, context, seed)` only when absent, then reads it back and calls `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:137-145`). A `grep` for `CachedPreprocesses` across the repo shows it is only ever `set`/`get` — it is never removed. `share_internal` calls `preprocess_internal` (`signing_protocol.rs:156`), so each call to `share()`/`complete()` reconstructs a machine with the *same* nonces. `DkgConfirmer::share` and `DkgConfirmer::complete` both invoke `share_internal`, with `msg = set_keys_message(set, removed, key_pair)` and the preprocess map supplied from untrusted on-tributary data (`signing_protocol.rs:288-327`). The FROST challenge depends on `msg` and on the included preprocesses/binding factors (`sign.rs:283-318`), so a second `share_internal` execution that sees a different `key_pair` or a different assembled preprocess set produces a second Schnorr share `s2 = k + c2·x` over the same nonce `k`, directly yielding `x = (s1 − s2)/(c1 − c2)`. The FROST API contract explicitly requires the cached preprocess be deleted after `from_cache` ("the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share"), which this code violates. [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
Both shares and the final signature are published onto the tributary blockchain / emitted as coordinator messages, i.e. they are public data. Recovery of the validator's `key` (the MuSig participant secret used for `DkgConfirmer` and other `SigningProtocol` contexts) lets an attacker forge that validator's contributions and, combined with the threshold structure, undermines the signing quorum's security assumptions. This is key-share recovery caused purely by data the attacker can influence (the preprocess set fed to `share_internal` is built from bytes broadcast by participants and assembled by the coordinator's accumulation logic). [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The precondition is two signing passes under the same `(context, attempt)` with differing challenge inputs. `share()` and `complete()` each re-run `share_internal` (and hence `from_cache` on the same seed), and the coordinator's accumulation may call `share` and `complete` against different preprocess sets or different `key_pair` values for the same DKG confirmation attempt (e.g. competing confirmation data accumulated across `handle_data` rounds). Any such path deterministically reuses nonces. Uncertainty: I could not fully read `handle.rs` to confirm whether `share` and `complete` are invoked for the same attempt with differing inputs in normal flow; however the retained seed makes *any* divergence catastrophic, and the missing deletion is verifiably unconditional (severity: High if a divergent re-sign path is reachable by participants submitting preprocess data; at minimum a latent nonce-reuse primitive). [1](#0-0) 

### Recommendation
Delete the `CachedPreprocesses` entry when it is consumed (e.g. `txn.del` the key inside `preprocess_internal`/`from_cache` path, or delete it in `share_internal` once the machine is built), so a second pass must generate fresh nonces. Alternatively, keep the constructed `AlgorithmSignMachine` in memory for reuse within a confirmation flow instead of re-deriving it from the seed, and persist a "consumed" marker so reboots cannot re-sign with the same seed. [8](#0-7) [9](#0-8) 

### Proof of Concept
1. Coordinator reaches a DKG confirmation attempt; `DkgConfirmer::share`/`complete` is invoked for context `(b"DkgConfirmer", attempt)`.
2. `preprocess_internal` creates and caches seed `s` under `CachedPreprocesses`, builds nonces `k` from `ChaCha20Rng::from_seed(s)`.
3. A later `share_internal` call for the same context (different `key_pair` in `set_keys_message`, or a different preprocess set assembled from participant data) re-loads `s`, rebuilds identical nonces, and emits share `s_i = k + c'·x` where `c'` differs from the earlier `c`.
4. An observer collects the two public shares/signatures and computes `x = (s_i − s_j)·(c − c')^{-1}` mod the group order, recovering the validator's secret key share — possible because `seeded_preprocess` is fully deterministic given the seed and the seed is never removed. [2](#0-1) [1](#0-0)

    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )

# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
