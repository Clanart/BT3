## Confirmed vulnerability

Confirmed: `evm/tron/contracts/apps/IntentGatewayV2.sol` uses `IERC20(token).safeTransferFrom(...)` directly (not the OZ `SafeERC20` library wrapper with `using SafeERC20 for IERC20`), calling the interface method on an arbitrary attacker-supplied `token` address with no code-existence check beforehand, combined with `+=` accumulation into the same storage slot (`TRANSACTION_FEES`) used for real escrowed protocol fees.

### Title
Fake escrow inflation via `TRANSACTION_FEES` sentinel-address input token drains real fee-token reserves - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in the Tron `IntentGatewayV2` lets a user supply an arbitrary `order.inputs[i].token` address and credits `_orders[commitment][token] += reducedInputs[i].amount` [1](#0-0) . There is no check preventing `token` from being the reserved `TRANSACTION_FEES` sentinel address (`address(uint160(uint256(keccak256("txFees"))))`) [2](#0-1) , and no contract exists at that address so `IERC20(token).safeTransferFrom(...)` is a no-op call to an EOA-like address that trivially "succeeds" without moving any value. This lets an attacker inflate `_orders[commitment][TRANSACTION_FEES]` for free, which is the exact slot later paid out as real fee-token to the beneficiary in `withdraw()` [3](#0-2) .

### Finding Description
1. In `placeOrder`, for each `order.inputs[i]`, if `token != address(0)` the code does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits escrow with `_orders[commitment][token] += reducedInputs[i].amount` [4](#0-3) .
2. An attacker sets one `order.inputs[i].token = TRANSACTION_FEES` (the sentinel address) with an arbitrary large `amount`, and sets `order.fees = 0` (so the later fee-escrow assignment at line 481, which uses `=` not `+=`, never overwrites the inflated value) [5](#0-4) .
3. `TRANSACTION_FEES` is a hash-derived address with no deployed contract code, so the call made by `safeTransferFrom` executes against an address with no code — this is treated as a successful, no-value-moved transfer, and no real tokens are ever escrowed.
4. `_orders[commitment][TRANSACTION_FEES]` is now non-zero without any deposit having occurred.
5. When the order is later filled/refunded and the destination gateway receives the `RedeemEscrow`/`RefundEscrow` request via `onAccept` → `withdraw()`, the function reads `fees = _orders[body.commitment][TRANSACTION_FEES]` and transfers that amount of the **real** fee token (e.g., DAI, `IDispatcher(host()).feeToken()`) to `beneficiary` [3](#0-2) . Since the gateway never actually received those tokens for this order, this payout is funded out of the pooled real fee-token balance escrowed by *other* legitimate orders — a direct value-extraction/insolvency bug.
6. This differs materially from the mainnet `evm/src/apps/IntentGatewayV2.sol`, which assigns escrow with `=` after an explicit "reject duplicate input token" check (`if (_orders[commitment][token] != 0) revert InvalidInput();`) [6](#0-5)  — the Tron variant lacks this guard and uses `+=`, which is what enables the exploit.

### Impact Explanation
This is a direct "loss of funds" / "false state acceptance" bug in the Hyperbridge bounty scope: an unprivileged user can mint fictitious fee-token escrow entries and later redeem real fee tokens they never deposited, draining the shared fee-token balance held by the `IntentGatewayV2` contract on Tron. This affects other users'/solvers' legitimately escrowed transaction fees and can fully drain the pool depending on available balance.

### Likelihood Explanation
High. It requires only calling the permissionless `placeOrder` entrypoint with a crafted `Order.inputs` array (choosing `token = TRANSACTION_FEES`), no privileged role, relayer collusion, or malformed proof is needed — the attacker's own order data flows unauthenticated through their own escrow lifecycle (`placeOrder` → fill/cancel → `onAccept`/`withdraw`), and the destination-side authentication (`authenticate(incoming.request)`) legitimately validates that the message originates from the attacker's own order/gateway instance, not that the token list is sane.

### Recommendation
- Reject `token == TRANSACTION_FEES` (and `token == address(0)` misuse, if not already handled) as a valid `order.inputs[i].token` in `placeOrder`.
- Switch escrow crediting from `+=` to a guarded assignment (`revert if already set`) as done in the mainnet `IntentGatewayV2.sol`, to prevent both this sentinel-collision attack and general duplicate-token accumulation issues.
- Use OpenZeppelin's `SafeERC20.safeTransferFrom` (with `using SafeERC20 for IERC20;`, already imported but apparently not applied consistently in the Tron variant per the `IERC20(token).safeTransferFrom` call style) which reverts on calls to addresses with no code, closing off similar no-op-transfer griefing vectors on any other input token address that happens to have no contract code.

### Proof of Concept
1. Attacker calls `placeOrder` with:
   - `order.inputs = [{token: address(0x0), amount: 1 wei}, {token: TRANSACTION_FEES_ADDR, amount: 1_000_000e18}]` (or any single non-fee input to satisfy `inputs.length != 0`, plus the sentinel entry), and `order.fees = 0`.
2. Since `TRANSACTION_FEES_ADDR` has no deployed code, `IERC20(TRANSACTION_FEES_ADDR).safeTransferFrom(msg.sender, address(this), 1_000_000e18)` succeeds without moving value [7](#0-6) .
3. `_orders[commitment][TRANSACTION_FEES] += 1_000_000e18` is recorded [8](#0-7) .
4. Attacker fills/cancels their own order to trigger a `RedeemEscrow`/`RefundEscrow` request back to this gateway; `onAccept` → `withdraw()` executes and pays out `fees = 1_000_000e18` of the real `feeToken` to `beneficiary` [3](#0-2) , draining the contract's real fee-token balance far beyond what the attacker ever deposited.

Note: I was unable to fully confirm within the tool budget whether `authenticate(incoming.request)` or any upstream module-binding check on the counterparty gateway (source-chain `IntentGatewayV2`) additionally validates the `body.tokens`/order-fee consistency before dispatching the `WithdrawalRequest`; if such a check exists on the *sending* side it could partially mitigate this, but no such validation was found in the `withdraw()` function itself, which is the code path directly responsible for the payout.
