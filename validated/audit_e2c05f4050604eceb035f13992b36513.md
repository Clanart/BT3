Based on my investigation, the strongest analog I found is in the "Open in Desktop" deep-link handler, where the `filepath` parameter is not sanitized against path traversal even though the sibling `branch` parameter explicitly is.

### Title
Unsanitized `filepath` parameter in `x-github-client://openRepo` deep link allows path traversal outside the cloned repository - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL()` parses the `openRepo` deep-link action (triggered by GitHub.com's "Open in Desktop" button or any attacker-crafted `x-github-client://openRepo/...` / `github-mac://openRepo/...` link) and extracts `url`, `branch`, `pr`, and `filepath` query parameters to later clone the repo and open a file inside it.

### Finding Description
In `parseAppURL`, the `branch` parameter is explicitly validated with `testForInvalidChars(branch)` and the `pr` parameter is validated with a strict digit regex, but the `filepath` parameter is passed through completely unvalidated: [1](#0-0) 

The `IOpenRepositoryFromURLAction` interface documents `filepath` as "the file to open after cloning the repository": [2](#0-1) 

The existing test suite confirms `branch` is rejected for invalid/traversal-like characters (`branch=%3C%3E` → `unknown`), while `filepath` is only tested with a benign, well-formed relative path (`Octokit.Reactive%2FOctokit.Reactive.csproj`) — there is no test, and by extension no code path, that rejects a `filepath` containing `../` sequences or an absolute path: [3](#0-2) 

This is the same broken-invariant pattern as the original report: a value supplied by an untrusted, attacker-controlled input (here, a clickable deep link instead of a constructor argument) is trusted downstream without an ownership/sanity check, unlike its sibling parameter (`branch`) which does get validated. This is a clear asymmetry in the guard logic.

### Impact Explanation
If the value consumed downstream to "open a file after cloning" joins `repository.path` with the unsanitized `filepath` (e.g. via `Path.join`) and then opens it in the user's editor/shell (or worse, if any renderer/file-read logic trusts this path), a malicious link such as:

`x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`

could cause Desktop to open/read a file outside the freshly cloned repository directory — e.g. SSH keys, `.git-credentials`, or other sensitive files on the victim's machine, potentially exfiltrating them or exposing their contents in the UI. This satisfies the required impact class: "attacker controls ... a link or deep link the user clicks ... and the result is ... file read outside the repo."

### Likelihood Explanation
Likelihood is meaningful but not certain, because I could not trace within index limits the exact downstream consumer of `filepath` (i.e., the function in `app-store.ts` / `dispatcher.ts` that actually opens the file after `openRepositoryFromUrl` completes) to confirm whether an additional guard exists there. The `branch` field's traversal check strongly suggests the developers were aware of and mitigated deep-link injection for that field but did not apply the equivalent protection to `filepath`. This requires only a single click by the victim on a malicious link (a normal, expected Desktop workflow, since "Open in Desktop" links are a first-class, documented feature), which is a low-friction attack vector.

### Recommendation
Apply the same validation used for `branch` (or a stricter check disallowing `..`, absolute paths, and drive letters) to `filepath` inside `parseAppURL`, and/or re-validate and constrain the resolved path to remain inside the cloned repository root (e.g., using `Path.resolve` + `startsWith(repoPath)` checks, similar to the `isClonePathSensitive` guard already used for the clone destination in `app/src/lib/git/clone.ts`) at the point the file is actually opened.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=main&filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim clicks the link (e.g. embedded in a webpage or README as an "Open in Desktop" button).
3. `parseAppURL` accepts it because only `branch`/`pr` are validated: [4](#0-3) 
4. Desktop clones `attacker/repo` and then attempts to open the file at `filepath`, which — absent a containment check downstream — resolves outside the cloned repository directory.

**Caveat:** I was not able to locate and confirm the exact downstream code (in `app-store.ts`/`dispatcher.ts`) that consumes `openRepo.filepath` to open the file, due to tool-call limits in this session. Confirming exploitability requires tracing that specific call path; if it turns out that a containment check already exists there, this finding would be reduced to a defense-in-depth gap rather than a directly exploitable file-read bug. I recommend starting a full Devin session with complete repository access to trace that path definitively.
