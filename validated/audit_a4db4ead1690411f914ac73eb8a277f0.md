### Title
Quadratic CPU exhaustion in `ThresholdKeys::read` via attacker-controlled `n`/`t` parameters triggering O(t²) Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
The Tornado advisory (CVE-2024-52804) describes a parser whose algorithm has quadratic complexity on attacker-controlled input, causing CPU exhaustion in the event-loop thread. The same bug class exists in Serai: `ThresholdKeys::read` accepts a fully attacker-controlled `t`/`n` from the byte stream and then calls `ThresholdKeys::new`, which computes the group key via `interpolation_factor` for each of the `t` participants — an O(t) Lagrange loop per participant, i.e. O(t²) field multiplications. With the u16 maximum (t = n = 65535), a single ~2 MB crafted buffer forces ~4.3 billion field multiplications plus 65535 group scalar multiplications, all inside a `read` API reachable from untrusted bytes.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, and `i` directly from the reader with no bound beyond `u16` and no relationship to the number of bytes actually supplied:

- crypto/dkg/src/lib.rs:591-602 reads `t`, `n`, `i` from raw bytes.
- crypto/dkg/src/lib.rs:607-616 reads `Interpolation::Constant` as `n` scalars, or `Lagrange` as a single tag byte.
- crypto/dkg/src/lib.rs:620-623 reads `n` verification-share points (`read_G`), i.e. input size is only ~32–64 bytes per participant.
- crypto/dkg/src/lib.rs:625-631 then calls `ThresholdKeys::new(...)`.

Inside `ThresholdKeys::new`, the group key is computed as:

```rust

let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```
(crypto/dkg/src/lib.rs:376-378)

`interpolation_factor` for `Interpolation::Lagrange` iterates over the entire `included` slice, performing one field multiplication for `num` and one for `denom` per element, plus a field inversion:

```rust
for l in included {
  if i == *l { continue; }
  let share = F::from(u64::from(u16::from(*l)));
  num *= share;
  denom *= share - i_f;
}
num * denom.invert().unwrap()
```
(crypto/dkg/src/lib.rs:234-246)

So the total work is `t × (t−1)` field multiplications, `t` field inversions, and `t` scalar multiplications — strictly quadratic in the attacker-chosen `t`. The same O(n²) pattern also appears in `ThresholdKeys::view`, which calls `interpolation_factor` once per included participant (crypto/dkg/src/lib.rs:500-507), so any subsequently-deserialized key operating on a large `included` set re-triggers the quadratic loop. For `Interpolation::Constant`, `new` still indexes `c[usize::from(u16::from(i) - 1)]` and interpolates over the `t`-element set at crypto/dkg/src/lib.rs:376-378.

### Impact Explanation
An unprivileged party who can cause a node to call `ThresholdKeys::read` on bytes they control (key-share/backup ingestion, DKG result reconstruction, or any deserialization sink enumerated for this code path) can send ~2 MB of mostly-dummy point encodings with `t = n = 0xFFFF`. This forces ~4.3 billion field multiplications and ~65k field inversions and scalar multiplications on a single linear-size input, monopolizing a CPU core for a sustained period — the exact availability impact of CVE-2024-52804 (CWE-400/CWE-770, uncontrolled resource consumption blocking the processing of other work). Repeating the input or fanning it across parallel connections compounds the stall.

### Likelihood Explanation
Exploitation requires only that the attacker reach a `ThresholdKeys::read` (or equivalent borsh `ThresholdParams`/`Participant` deserialization feeding `ThresholdKeys::new`) call with untrusted bytes — the bytes are attacker-formattable with no signature or secret material needed to reach the quadratic path, since `ThresholdKeys::new` runs *inside* `read` before any validity check beyond `t ≤ n`. Cost to the attacker is one small message; cost to the victim is quadratic.

### Recommendation
- Enforce a sane upper bound on `t`/`n` in `ThresholdKeys::read` (and `ThresholdParams` borsh deserialization) before constructing the object — Serai validator sets are far smaller than u16::MAX.
- Alternatively, precompute Lagrange denominators incrementally (O(t) total via prefix/suffix products) so `view`/`new` are linear, or cache factors.
- Consider validating `verification_shares`/`interpolation` consistency cheaply before the interpolation pass.
