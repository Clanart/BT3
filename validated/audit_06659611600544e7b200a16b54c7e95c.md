## Title
`unsafe-open-directory` IPC channel bypasses the safety checks performed by `showFolderContents`, allowing execution of attacker-controlled directories/app-bundles opened from cloned repository content - (File: `app/src/main-process/main.ts`, `app/src/main-process/shell.ts`, `app/src/ui/main-process-proxy.ts`)

### Summary
`shell.UNSAFE_openDirectory` calls Electron's `shell.openPath`, which — for a "directory" that is actually an application bundle or executable — will launch it rather than merely reveal it. The codebase has exactly one safety wrapper, `showFolderContents()` in `app/src/ui/main-process-proxy.ts`, which checks whether a path is a macOS app bundle (`isApplicationBundle`) before deciding to call the unsafe primitive versus the safe `showItemInFolder`. However, the underlying primitive is exposed as its own standalone IPC channel, `unsafe-open-directory`, registered with `ipcMain.on` in `app/src/main-process/main.ts`. Any code executing in the renderer (not only the `showFolderContents` wrapper) can invoke this channel directly with an arbitrary path, exactly mirroring the CDPVault pattern where a "guarded" public entry point (`deposit`/`withdraw`) wraps an unguarded public function (`modifyCollateralAndDebt`) that can be called directly to skip the guard.

### Finding Description
`UNSAFE_openDirectory` is explicitly documented as dangerous: [1](#0-0) 
its docstring states: "CAUTION: This method should never be used to open user-provided or derived paths. It's sole use is to open _directories_ that we know to be safe, no verification is performed to ensure that the provided path isn't actually an executable."

The intended safe caller is `showFolderContents`, which performs an app-bundle check (macOS) before calling `UNSAFE_openDirectory`: [2](#0-1) 

But the main process registers the underlying primitive as its own reachable IPC entry point, independent of that wrapper's checks: [3](#0-2) 

`ipcMain.on('unsafe-open-directory', ...)` accepts any path from any code with access to the renderer's `ipcRenderer.send`, and calls straight into `UNSAFE_openDirectory(path)`, which passes the path to `shell.openPath` without any verification: [4](#0-3) 

This is structurally identical to the CDPVault bug: `deposit`/`withdraw` are the "guarded" entry points wrapping the "unguarded" `modifyCollateralAndDebt`, but because `modifyCollateralAndDebt` is `public`, an attacker can call it directly and skip the `whenNotPaused` check. Here, `showFolderContents` is the "guarded" caller wrapping the "unguarded" `UNSAFE_openDirectory`, but because the latter is wired to its own IPC channel (`unsafe-open-directory`) rather than being an unexported internal function only reachable through the guarded wrapper, any renderer-side code path (including code operating on attacker-influenced data derived from a cloned/fetched repository, such as a directory or file name inside the working tree) can send directly to that channel and skip the app-bundle/executable check entirely.

The `isTrustedIPCSender` check in `ipc-main.ts` only verifies the IPC message came from the app's own renderer frame — it does not validate *what* the message contains, so it provides no protection against a malicious *path value* originating from repository content that legitimate application code might forward to this channel (e.g., "reveal/open" actions on paths derived from files inside a cloned repository).

### Impact Explanation
If any code path forwards a repository-derived directory name (attacker controls via a crafted commit, e.g. a folder named `something.app` on macOS, or a Windows directory shadowing an executable) to `unsafe-open-directory` instead of going through the guarded `showFolderContents`, the guard (`isApplicationBundle` check / fallback to `showItemInFolder`) is skipped and `shell.openPath` will execute the bundle/executable outside the sandbox — remote code execution triggered merely by a user browsing/opening content from a cloned or fetched repository. Even absent such a caller today, the exposed raw channel is a latent bypass: any future or existing UI code that calls `sendProxy('unsafe-open-directory', 1)` (or the underlying `send('unsafe-open-directory', path)`) with a repository-derived path silently reintroduces execution-as-open, with no compile-time or runtime signal that the safety contract documented in `shell.ts` was violated.

### Likelihood Explanation
Moderate-to-high: the guard exists specifically because `shell.openPath` on a directory that is secretly an app bundle/executable results in execution, and the codebase already treats this as a known risk (hence the explicit `UNSAFE_` naming and the `isApplicationBundle` check in the one legitimate caller). The vulnerability class is exactly the one flagged as valid in this task (attacker controls a cloned/fetched repository, resulting in code execution outside expectations) and the guard is bypassable simply by using the raw, always-available IPC channel instead of the vetted wrapper — no user interaction beyond what is already expected for "show folder contents" style UI actions.

### Recommendation
- Do not register `unsafe-open-directory` as an independently invokable IPC channel reachable from arbitrary renderer code. Fold the app-bundle/verification check into the main-process handler itself so the safety gate cannot be bypassed by calling the primitive channel directly (mirrors "make `modifyCollateralAndDebt` internal" — collapse the unguarded primitive into the guarded function).
- Alternatively, perform the `isApplicationBundle`/executable check in the main process before calling `shell.openPath`, rather than solely in the renderer-side `showFolderContents` wrapper, so the guarantee holds regardless of which channel/caller reaches it.
- Audit all current and future callers of `showFolderContents`/`UNSAFE_openDirectory`/`sendProxy('unsafe-open-directory', ...)` to ensure none pass repository-derived (attacker-controlled) paths without going through the vetted check.

### Proof of Concept

The core structural weakness — the safety-critical primitive being exposed as its own IPC channel independent of its only vetting wrapper — is confirmed directly from the source:

1. `app/src/main-process/main.ts:640-642` registers `unsafe-open-directory` as a raw, always-reachable channel.
2. `app/src/main-process/shell.ts:1-31` shows `UNSAFE_openDirectory` performs zero validation and documents that it must never receive user/derived paths.
3. `app/src/ui/main-process-proxy.ts:98-144` shows the *only* safety check (`isApplicationBundle`) lives in `showFolderContents`, not in the IPC handler, so any caller using `send('unsafe-open-directory', path)` (or a hypothetical future feature wiring a repo-derived path to this proxy) bypasses that check exactly as `modifyCollateralAndDebt` bypasses `whenNotPaused` in the CDPVault report. import { shell } from 'electron'

/**
 * Wraps the inbuilt shell.openItem path to address a focus issue that affects macOS.
 *
 * When opening a folder in Finder, the window will appear behind the application
 * window, which may confuse users. As a workaround, we will fallback to using
 * shell.openExternal for macOS until it can be fixed upstream.
 *
 * CAUTION: This method should never be used to open user-provided or derived
 * paths. It's sole use is to open _directories_ that we know to be safe, no
 * verification is performed to ensure that the provided path isn't actually
 * an executable.
 *
 * @param path directory to open
 */
export function UNSAFE_openDirectory(path: string) {
  // Add a trailing slash to the directory path.
  //
  // On Windows, if there's a file and a directory with the
  // same name (e.g `C:\MyFolder\foo` and `C:\MyFolder\foo.exe`),
  // when executing shell.openItem(`C:\MyFolder\foo`) then the EXE file
  // will get opened.
  // We can avoid this by adding a final backslash at the end of the path.
  const pathname = __WIN32__ && !path.endsWith('\\') ? `${path}\\` : path

  shell.openPath(pathname).then(err => {
    if (err !== '') {
      log.error(`Failed to open directory (${path}): ${err}`)
    }
  })
```

const UNSAFE_openDirectory = sendProxy('unsafe-open-directory', 1)

export async function showFolderContents(path: string) {
  const stats = await stat(path).catch(err => {
    log.error(`Unable to retrieve file information for ${path}`, err)
    return null
  })

  if (!stats) {
    return
  }

  if (!stats.isDirectory()) {
    log.error(`Trying to get the folder contents of a non-folder at '${path}'`)
    await _showItemInFolder(path)
    return
  }

  // On Windows and Linux we can count on a directory being just a
  // directory.
  if (!__DARWIN__) {
    UNSAFE_openDirectory(path)
    return
  }

  // On macOS a directory might also be an app bundle and if it is
  // and we attempt to open it we're gonna execute that app which
  // it far from ideal so we'll look up the metadata for the path
  // and attempt to determine whether it's an app bundle or not.
  //
  // If we fail loading the metadata we'll assume it's an app bundle
  // out of an abundance of caution.
  const isBundle = await isApplicationBundle(path).catch(err => {
    log.error(`Failed to load metadata for path '${path}'`, err)
    return true
  })

  if (isBundle) {
    log.info(
      `Preventing direct open of path '${path}' as it appears to be an application bundle`
    )

    await _showItemInFolder(path)
  } else {
    UNSAFE_openDirectory(path)
  }
}
```
