### Title
Missing lower-bound validation on `challengePeriod` in `updateHostParamsInternal` allows the state-commitment dispute window to be silently disabled - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` validates several `HostParams` fields (`hostManager`, `handler`, `consensusClient`, `hyperbridge`, `stateMachines.length`, and enforces `unStakingPeriod >= 1 days`) but performs **no validation whatsoever on `challengePeriod`**. Every consumer of `challengePeriod` in `HandlerV2.sol` treats `0` as a sentinel meaning "challenge period disabled" (`if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();`). Because the field is unbounded, setting it to `0` (or any value below the intended safety margin) via a normal, correctly-authenticated `updateHostParams` call permanently disables the dispute window for every request/response/timeout path on that host, with no client-side notion of what a "safe" minimum value would be.

### Finding Description
`updateHostParamsInternal` is the single choke point that mutates `_hostParams`, reachable either from cross-chain governance via `HostManager.onAccept` → `IHostManager(_params.host).updateHostParams(...)`, or (on `TestnetHost`) directly by the configured admin: [1](#0-0) 

Every other timing/identity field is checked, but `params.challengePeriod` is copied into storage unconditionally with no lower bound: [2](#0-1) 

The `challengePeriod` is then used in `HandlerV2.sol` as the sole gate that enforces a mandatory delay between when a state commitment is stored (`host.stateMachineCommitmentUpdateTime`) and when it can be used to admit post requests, get responses, and post/get timeouts: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

In every one of these four functions the check is written as `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` — i.e. `challengePeriod == 0` is treated as "check disabled" rather than "always pass with zero delay". This means a value of `0` is not merely a degenerate edge case (as it would be with a strict `>` comparison), it is an explicit off-switch for the entire dispute/challenge mechanism baked into the comparison logic itself.

The challenge period exists specifically to give fishermen/verifiers time to detect and veto a fraudulent state commitment (see `_vetoes` bookkeeping in `EvmHost.sol`) before it can be relied upon to admit cross-chain requests or prove timeouts. If `challengePeriod` is `0`, a state commitment stored by `handleConsensus` can be used in the very same block to admit post requests/responses or to prove timeouts, eliminating any window during which a false or premature state commitment (e.g. from a short-lived fork, misbehaving light-client update, or consensus client bug) could be disputed.

This is the direct analog of the seed report: a governance-tunable timing parameter (`warmUp`/`coolingOff` there, `challengePeriod` here) has no floor enforced at the point of mutation, and the invariant the rest of the system implicitly assumes ("challengePeriod represents a meaningful minimum delay") is not enforced when the value is changed.

### Impact Explanation
If `challengePeriod` is ever set to `0` — whether by a misconfigured governance proposal, a parameter-migration bug, or simply because `HostParams.challengePeriod` defaults to the Solidity zero-value and is not corrected before being echoed back in a param update — every downstream `HandlerV2` entrypoint stops enforcing any delay between state-commitment storage and use. This directly weakens the "false proof/state acceptance" guard the challenge period is meant to provide: a state commitment can be relied upon instantly, removing the safety margin that the whole request/response/timeout dispatch pipeline (and by extension all bridged asset movement gated on it) depends on. This is a protocol-level loss of a core security control, not a cosmetic issue.

### Likelihood Explanation
The path to trigger this is a normal, correctly-authenticated `updateHostParams` call — no malicious relayer, prover, or forged proof is needed. The bug is that the validation logic in `updateHostParamsInternal` simply omits a check that exists for every other sensitive field (`unStakingPeriod` has an explicit `>= 1 days` floor at line 615 of `EvmHost.sol`, but `challengePeriod` has none). Given that `HostParams` is a large struct passed wholesale on every update (as shown in the `HostManagerTest.sol` and `host_manager.rs` tests, which construct full `HostParams`/`EvmHostParamsAbi` structs), a single field mismanaged in an off-chain parameter-construction pipeline, a copy-paste default, or a partial-update tool bug is enough to zero out `challengePeriod` while all other fields pass validation.

### Recommendation
Add an explicit minimum-value check for `challengePeriod` in `updateHostParamsInternal`, mirroring the existing `unStakingPeriod` guard, e.g.:
```solidity
if (params.challengePeriod == 0) revert InvalidChallengePeriod();
```
Additionally, change the `HandlerV2.sol` comparisons from `challengePeriod != 0 && challengePeriod > delay` to `challengePeriod > delay`, so that even if `challengePeriod` were ever legitimately `0`, it would fail closed (no window) rather than fail open (no check).

### Proof of Concept
1. Hyperbridge governance (or the `TestnetHost` admin) submits an `updateHostParams` call whose `HostParams.challengePeriod` field is `0`, keeping every other field valid so all existing checks (`InvalidHostManager`, `InvalidHandler`, `InvalidConsensusClient`, `InvalidHyperbridgeId`, `InvalidStateMachinesLength`, `InvalidUnstakingPeriod`) pass: [1](#0-0) 
2. `_hostParams.challengePeriod` is now `0`.
3. A relayer submits `handleConsensus` with a valid consensus proof, storing a new state machine commitment at `block.timestamp = T`.
4. In the same block (or immediately after), the relayer calls `handlePostRequests` (or `handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts`) referencing that height. `delay = 0`, and since `challengePeriod == 0`, the check `challengePeriod != 0 && challengePeriod > delay` evaluates to `false`, so `ChallengePeriodNotElapsed` never reverts: [7](#0-6) 
5. Requests/timeouts are dispatched off a state commitment that had zero time to be challenged or vetoed, defeating the purpose of the fisherman/veto mechanism tracked via `_vetoes` in `EvmHost.sol`.

        if (
