### Title
`fund_message` refunds top-up contributions to the original payer, not the funder — silent fund misdirection - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp::fund_message` lets **any signed account** add funds to an existing request/response's escrowed relayer fee, but the escrow's `payer` field is never updated to reflect the new contributor. On timeout, the *entire* accumulated fee — original amount plus every top-up — is refunded to the single, original `payer`, not to whoever actually contributed the funds. This mirrors the StakingRewards.sol bug-class: the contract's escrow-accounting invariant ("the recorded balance always corresponds to the party entitled to reclaim it") is broken by a permissionless top-up path that mutates a shared balance without updating entitlement, so funds silently end up misdirected to the wrong beneficiary.

### Finding Description
`fund_message` is a public, signed extrinsic: [1](#0-0) 

It:
1. Accepts `ensure_signed(origin)` from **any** account — no relationship to the original request required.
2. Looks up the existing `RequestMetadata`/`FeeMetadata` for the commitment via `RequestCommitments::<T>::get` or `ResponseCommitments::<T>::get`.
3. Transfers `message.amount` from the caller into `RELAYER_FEE_ACCOUNT`.
4. Increments `metadata.fee.fee += message.amount` and writes the metadata back — **without touching `metadata.fee.payer`**.

The `FeeMetadata` struct only tracks a single `payer`: [2](#0-1) 

On timeout, the refund path pays the *entire* `fee.fee` back to the single stored `fee.payer`: [3](#0-2) 

So once a second account calls `fund_message` to top up an existing commitment, their contribution is merged into the same pot as the original payer's fee. If the request later times out, the *original* payer receives the whole pot (original fee + all top-ups); the funder who called `fund_message` gets nothing back. Conversely, if the request is delivered instead of timing out, the relayer collects the whole pot including the top-up — which may be the intended "fund_message" use case (someone else sponsoring a stuck delivery) — but the timeout-refund path was never adjusted to reflect multi-payer contributions, so the failure path always misattributes funds to the wrong party.

The pallet's own doc-comment acknowledges a related but narrower risk ("Should not be called on a message that has been completed... those funds will be lost forever") — but it does not address, and the code does not guard against, the timeout-refund misdirection to the *original* payer instead of the funder.

### Impact Explanation
This falls squarely under the bounty's "refunds ... must move exactly once and only to the rightful beneficiary and amount" pivot. Any unprivileged account that funds someone else's stuck/underfunded request (a legitimate, intended use of `fund_message` — e.g. a dApp backend topping up a user's message to guarantee relayer pickup) permanently loses their contributed funds to the original payer if the request subsequently times out. This is a direct, protocol-level loss-of-funds / wrong-beneficiary bug reachable by any signed account with no privileged role, relayer collusion, or front-running required.

### Likelihood Explanation
High for anyone using `fund_message` as documented (topping up someone else's request to help it get delivered). The path requires no coordination with a malicious actor — the *existing* payer benefits passively from a stranger's top-up whenever a timeout occurs, and the funder has no way to prevent or reverse it once submitted. The only "mitigation" is the doc-comment warning users to not use the extrinsic at all on already-completed messages, which does not cover the live, in-flight case that is the extrinsic's actual purpose.

### Recommendation
Track fee contributions per-account (e.g. `BTreeMap<AccountId, Balance>` or an additional `Vec<(AccountId, Balance)>` on `FeeMetadata`) instead of a single `payer`/`fee` pair, and have `on_request_timeout`/`on_response_timeout` refund each contributor their own share. Alternatively, restrict `fund_message` so that it can only be called by the original `payer` (or require the caller to specify a distinct refund beneficiary that is honored proportionally on timeout).

### Proof of Concept
1. Account `A` dispatches a `PostRequest` with `fee = 10`, `payer = A`. This is recorded in `RequestCommitments[commitment] = RequestMetadata { fee: FeeMetadata { payer: A, fee: 10 }, claimed: false, .. }`.
2. Account `B` (unrelated to `A`, e.g. a service trying to help ensure delivery) calls `fund_message(MessageCommitment::Request(commitment), amount = 50)`. `B`'s 50 tokens are transferred to `RELAYER_FEE_ACCOUNT`; `metadata.fee.fee` becomes `60`; `metadata.fee.payer` is still `A`. [4](#0-3) 
3. The request times out before being delivered. `on_request_timeout` refunds the full `60` from `RELAYER_FEE_ACCOUNT` to `A` only. [3](#0-2) 
4. `B` has permanently lost `50` tokens to `A`, with no on-chain path to reclaim them — a false/wrong-beneficiary fund movement triggered entirely by unprivileged, public entrypoints (`fund_message` + normal timeout processing).

		/// Add more funds to a message (request or response) to be used for delivery and execution.
		///
		/// Should not be called on a message that has been completed (delivered or timed-out) as
		/// those funds will be lost forever.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(5))]
		#[pallet::call_index(4)]
		pub fn fund_message(
			origin: OriginFor<T>,
			message: FundMessageParams<T::Balance>,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
				MessageCommitment::Response(commitment) =>
					ResponseCommitments::<T>::get(commitment),
			};

			let Some(mut metadata) = metadata else {
				return Err(Error::<T>::MessageNotFound.into());
			};

			T::Currency::transfer(
				&account,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				message.amount,
				Preservation::Expendable,
			)?;

			match message.commitment {
				MessageCommitment::Request(commiment) => {
					metadata.fee.fee += message.amount;
					RequestCommitments::<T>::insert(commiment, metadata);
				},
				MessageCommitment::Response(commiment) => {
					metadata.fee.fee += message.amount;
					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

			Ok(())
		}
