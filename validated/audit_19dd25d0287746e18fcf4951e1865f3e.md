### Title
Unchecked u64 arithmetic on attacker-controlled amounts overflows the fund-sufficiency check in `SignableTransaction::new`, bypassing `NotEnoughFunds` and producing consensus-invalid transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` computes `payment_sat` and the sufficiency check `input_sat < payment_sat + needed_fee` (and the change check `payment_sat + fee_with_change`) with plain `u64` arithmetic. Just as GMX's `Calc.boundedSub` overflows when negating `type(int256).min` inside a routine meant to bound arithmetic, these "did we collect enough funds" guards wrap to small values for extreme, externally-supplied payment amounts, silently defeating the check.

### Finding Description [1](#0-0) 
- Line 187: `payment_sat` is `payments.iter().map(|p| p.1).sum::<u64>()` over caller-controlled `u64` amounts. Two payments above `u64::MAX/2` wrap the sum to a tiny value.
- Line 215: `input_sat < (payment_sat + needed_fee)` — the `+` is unchecked. With `payment_sat` near `u64::MAX`, the addition wraps to near zero, so the `NotEnoughFunds` guard passes even though the payments vastly exceed the inputs.
- Line 228: `input_sat.checked_sub(payment_sat + fee_with_change)` — again the inner `+` can wrap, yielding an enormous bogus "change" value that is pushed as an output at line 230.
- Line 206: `fee_per_vbyte * vbytes` is also an unchecked multiplication and can wrap, weakening the minimum-fee check at line 211.

In debug builds these wrap into panics (`attempt to add with overflow`), a reachable crash; in release builds they wrap silently.

### Impact Explanation
An unprivileged party who can cause a withdrawal/spend to be constructed (payment scripts and amounts are attacker-chosen transaction data fed to a signing API) can force `SignableTransaction::new` to succeed while `tx_outs` sum to more than the inputs. The resulting transaction is consensus-invalid (`bad-txns-in-belowout`) and can never confirm — the FROST ceremony signs and "completes" a transaction that funds are reported spent on but which is unspendable/unbroadcastable. Alternatively, inflated wrapped change values create outputs the wallet treats as its own. In debug builds the overflow panics, giving a direct remote DoS of the signer/coordinator path.

### Likelihood Explanation
Triggering only requires requesting payments whose `u64` amounts sum past `u64::MAX` (e.g., two payments of `u64::MAX`), or one payment large enough that `payment_sat + needed_fee` wraps. Each individual payment trivially passes the `DUST` check (line 165–169) and no per-payment upper bound exists. Anywhere this constructor is driven by user-submitted withdrawal data, the bug is reachable with public inputs alone.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`:
- `payment_sat`: fold with `checked_add`, erroring with `NotEnoughFunds`/`TooMuchData` on overflow.
- Line 215: compare `input_sat.checked_sub(payment_sat).map_or(true, |r| r < needed_fee)` or check each component with `checked_add`.
- Line 228: compute `input_sat.checked_sub(payment_sat).and_then(|r| r.checked_sub(fee_with_change))`.
- Line 206/227: `fee_per_vbyte.checked_mul(vbytes)` and reject on overflow.

### Proof of Concept
```rust
// In debug builds: panics at the `sum::<u64>()` / `payment_sat + needed_fee`.
// In release builds: `payment_sat` wraps to ~0, `NotEnoughFunds` is bypassed,
// and a consensus-invalid TX (outputs >> inputs) is produced.
let payments = vec![
    (any_valid_script.clone(), u64::MAX),
    (any_valid_script.clone(), u64::MAX),
];
let inputs = vec![received_output_with_value(1_000_000)]; // small real UTXO
let tx = SignableTransaction::new(inputs, &payments, Some(change_script), None, 10);
// release: Ok(...) — a TX whose outputs exceed inputs; will never confirm.
```

A milder single-payment variant: `payments = [(script, u64::MAX)]` makes `payment_sat + needed_fee` wrap at line 215, then `payment_sat + fee_with_change` wraps at line 228 so `checked_sub` returns a huge `value >= DUST`, adding a bogus change output worth nearly `u64::MAX` satoshis.
