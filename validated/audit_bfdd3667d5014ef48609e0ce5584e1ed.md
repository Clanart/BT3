### Title
Unchecked ERC20 return-data in `withdraw()`/`SweepDust` lets escrow be marked settled while the token transfer silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` on the Tron variant of the IntentGateway release escrowed ERC20 tokens using a raw low-level `call` and only check that the call itself did not revert (`success`), never decoding/validating the boolean return value that the ERC20 standard requires. This is exactly the bug class the external report flagged for `HifiPool.sol`/`HifiProxyTarget.sol` — using an unsafe transfer path that ignores the token's own success/failure signal — except here it still exists in the Tron fork of the settlement path that the main EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol`) already fixed with `SafeERC20.safeTransfer`.

### Finding Description
In `withdraw()`: [1](#0-0) 
the escrow balance `_orders[body.commitment][token]` is decremented and, for ERC20 tokens, the release is performed via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted — it does **not** decode the `returndata` to check the boolean the ERC20 standard mandates `transfer()` return. Per the ERC20 spec (and the exact issue raised in the external report), a compliant-but-non-reverting token can return `false` on failure (insufficient balance, paused, blacklisted recipient, etc.) instead of reverting. In that case `success == true`, the `if (!success)` guard never fires, and the function proceeds to finalize:
- `_filled[body.commitment] = beneficiary` is already set before the transfer even executes (line 684),
- `_orders[body.commitment][token] -= amount` unconditionally runs after the call (line 701),
- `EscrowReleased`/`EscrowRefunded` is emitted (lines 716-720),

even though no tokens actually moved to `beneficiary`. The same unchecked pattern is used for fee-token payout at lines 707-714, and for the `SweepDust` handler: [2](#0-1) 

This contrasts with the hardened path used on `placeOrder`'s escrow intake, which correctly uses `IERC20(token).safeTransferFrom(...)`: [3](#0-2) 
and with the main (non-Tron) intents implementation which already uses `SafeERC20.safeTransfer` for the equivalent withdraw path: [4](#0-3) 

The `token` address in an order's `inputs`/fee token is attacker/solver-controlled input to `placeOrder`, so any order can name a token contract that returns `false` (without reverting) under certain conditions, guaranteeing this path is reachable by an ordinary, unprivileged user/solver — no relayer, prover, or admin compromise is required.

### Impact Explanation
`withdraw()` is the function that finalizes cross-chain settlement, invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse()` for cancellation-driven refunds. If the token transfer silently fails (returns `false`, no revert), the contract still:
1. Marks the order `_filled` (blocking any future/legit fill or refund attempt for that commitment),
2. Zeroes out the internal escrow accounting for that token,
3. Emits a success event,

while the actual tokens remain stuck in the contract with no owner able to reclaim them — a direct, unrecoverable loss of the escrowed funds for the rightful beneficiary (the solver claiming payment, or the user being refunded). This matches the bounty's "loss of funds" and "false state acceptance" categories, since on-chain state (`_filled`, `_orders`) falsely records the settlement as completed when the value transfer never occurred.

### Likelihood Explanation
The vulnerable code path is reached on every ordinary settlement (`RedeemEscrow`/`RefundEscrow`/`SweepDust`) and requires no privileged actor — only a token contract (which the order creator freely chooses as an input token) that returns `false` instead of reverting under some condition (a well-documented, non-exotic ERC20 behavior pattern, and notably common precisely on Tron/TRC20 tokens which this file is written for). No malicious relayer, prover, or governance action is needed.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` uses in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, matching the pattern already used for `safeTransferFrom` in the escrow-intake path and in the main `IntentsBase.sol` withdraw logic, so that both call-reversion and return-data-`false` failures cause the transaction to revert instead of being treated as success.

### Proof of Concept
1. Deploy a token `EvilToken` implementing ERC20 such that `transfer()` returns `false` when, e.g., the recipient is blacklisted or a specific flag is set, without reverting (this is legal per the ERC20 interface and used by real-world non-compliant tokens).
2. Place a cross-chain order via `placeOrder` using `EvilToken` as an `inputs[]` token; escrow succeeds via `safeTransferFrom`.
3. Have a solver fill the order on the destination chain; the settlement message triggers `onAccept -> withdraw` on the source chain.
4. Configure `EvilToken.transfer` to return `false` for the solver's beneficiary address at settlement time (e.g., toggling an internal blacklist flag right before settlement, which the order creator/attacker controls since they deployed the token).
5. `withdraw()` executes `token.call(...)`, gets `success == true` (call didn't revert) even though the returned data decodes to `false`; the `if (!success)` check passes, `_orders[...][token]` is decremented, `_filled` is set, and `EscrowReleased` is emitted — while `EvilToken` balance of the solver never increased. The escrowed tokens are now permanently stranded in the `IntentGatewayV2` contract with no valid recovery path.
