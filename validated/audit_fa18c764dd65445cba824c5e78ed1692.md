### Title
`SignableTransaction` fee/weight calculation omits the OP_RETURN data output, producing transactions larger than estimated that underpay the requested feerate and can exceed standard weight limits - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Perennial issue where `collateralAfterFees` omitted the current position's fees — letting a check pass on an incomplete accounting — `SignableTransaction::new` appends the OP_RETURN output to `tx_outs` but calls `calculate_weight_vbytes` with only `payments`, so the fee, sufficiency, dust and max-weight checks are all computed against a transaction that is missing a real output.

### Finding Description
The OP_RETURN output is pushed onto `tx_outs` before any size estimation: [1](#0-0) 

However, both weight calls pass `payments` — which does not include the OP_RETURN output: [2](#0-1) 

Inside `calculate_weight_vbytes`, `tx.output` is built solely from `payments` (plus optional change), so the serialized OP_RETURN output (up to 83 bytes) is absent from the weight/vbytes estimate: [3](#0-2) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` uses the underestimated vbytes; the real transaction is larger, so the effective feerate is below the requested `fee_per_vbyte`.
2. The `TooLowFee` check compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes` using the same underestimated vbytes — a transaction requesting exactly minimum relay feerate will end up paying below minimum relay fee and be rejected by the network.
3. The change calculation `input_sat - payment_sat - fee_with_change` over-credits the change output, further reducing the actual fee.
4. The `MAX_STANDARD_TX_WEIGHT` check uses `weight` that excludes the OP_RETURN output, so a transaction can pass the check yet exceed standard weight and be non-relayable once signed: [4](#0-3) 

### Impact Explanation
Any user of the wallet who attaches `data` (untrusted bytes of up to 80 bytes, exactly the surface this crate exposes to callers) receives a `SignableTransaction` whose `needed_fee()`, `fee()`, and weight checks were validated against a smaller transaction than the one actually built. The signed transaction either underpays the requested feerate (risking non-propagation/eviction and unspendable change-locked funds until re-signed), or exceeds `MAX_STANDARD_TX_WEIGHT` and cannot be relayed at all. This is a wrong-accounting check accepting a result it was meant to reject — the same class as the omitted current-position fee, where the invariant is evaluated without the current item's cost.

### Likelihood Explanation
Deterministic: any `SignableTransaction::new` call with `data: Some(_)` triggers it. The defect requires no adversarial cooperation; it is purely a function of the caller-supplied `data` length and `fee_per_vbyte`. Severity is Medium: it yields a transaction failing relay/standardness policy (funds not spendable via that transaction), not direct theft.

### Recommendation
Include the OP_RETURN output in the transaction used by `calculate_weight_vbytes`. Either build the `TxOut` list first (payments + OP_RETURN + optional change) and pass it in, or add a `data: Option<&PushBytesBuf>` parameter so the weight estimate reflects the final output set for both the no-change and with-change branches.

### Proof of Concept
```rust
// In networks/bitcoin: construct inputs/payments such that
// input_sat == payment_sat + fee_per_vbyte * vbytes (no change),
// with data: Some(vec![0u8; 80]).
//
// SignableTransaction::new computes vbytes over payments-only outputs.
// The returned tx includes an extra ~83-byte OP_RETURN output that was
// never counted. With fee_per_vbyte == 1 (minimum relay), the actual
// feerate is ~ (needed_fee) / (vbytes + ~21) < min relay fee, so the
// transaction is rejected by relay policy despite passing TooLowFee.
//
// Equivalently, pick inputs/payments so weight is just below
// MAX_STANDARD_TX_WEIGHT; the OP_RETURN pushes the real weight over
// the limit while `weight > MAX_STANDARD_TX_WEIGHT` still passes,
// yielding a permanently non-standard transaction.
```
