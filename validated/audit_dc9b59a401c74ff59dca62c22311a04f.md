### Title
`convertWOM` is callable by anyone and permanently locks the contract's WOM into veWOM without any matching mWOM accounting - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.convertWOM(uint256 _amount)` only carries the `whenNotPaused` modifier and has no caller/role restriction, allowing any address to force the WombatStaking contract to lock its own WOM balance into `veWOM` for `lockDays`. [1](#0-0)  Because minting `mWOM.totalAccumulated` only happens through `mWOM._lockWom` -> `IWombatStaking(wombatStaking).convertWOM(_amount)`, a direct call bypasses that accounting path entirely, desynchronizing `mWOM.totalAccumulated` from the actual `veWom` balance held by `WombatStaking`. [2](#0-1) 

### Finding Description
`convertWOM` approves and calls `IVeWom(veWom).mint(_amount, lockDays)` unconditionally for any `_amount > 0`, with no check on `msg.sender`: [3](#0-2) 

`convertAllWom()` similarly is callable by anyone and sweeps the entire WOM balance of the contract into the lock. [4](#0-3) 

The only legitimate path meant to trigger this locking is `mWOM._lockWom`, which mints `mWOM` shares to the depositor and tracks `totalAccumulated` in lockstep with what gets locked: [2](#0-1) 

Since `convertWOM` has no access control, any unprivileged address can call it directly on `WombatStaking`, causing WOM sitting in the contract (which may be pooled deposits, harvested rewards, or fees awaiting distribution — the contract has multiple flows, e.g. `deposit`, `withdraw`, `harvest`, that leave WOM balances in the contract) to be committed into a `veWOM` lock without any `mWOM` being minted to compensate. This breaks the invariant that `mWOM.totalAccumulated` should reconcile with the `veWom` balance of `WombatStaking`.

Critically, examining `WombatStaking.sol` in full shows there is **no function that calls `IVeWom(veWom).burn(...)`** anywhere in the contract — the only interaction with `veWom` is the `mint` call inside `convertWOM` and the view helper `accumelatedVeWom()`. [5](#0-4)  This means once WOM is locked via `convertWOM`, there is no code path in the deployed contract to unlock/reclaim it even after `lockDays` (1461 days, i.e. ~4 years, by default) elapses. [6](#0-5)  Any WOM balance sitting in the contract that an attacker times a `convertWOM`/`convertAllWom()` call against is therefore permanently locked/unrecoverable, independent of whether the attacker gains anything personally.

No existing modifier stops this: only `whenNotPaused` is present, no `onlyOwner`, no pool/role restriction, no `nonReentrant` needed here since there's no reentrancy vector, but the missing authorization check is the root cause.

### Impact Explanation
Any unprivileged caller can force-lock the contract's spare/held WOM balance into `veWOM` for `lockDays`, with no `mWOM` minted and no recovery mechanism (`burn` is never called from `WombatStaking`). This causes:
- Permanent desynchronization between `mWOM.totalAccumulated` and the actual `veWom` balance of `WombatStaking`, breaking protocol accounting used for reward/backing calculations.
- Permanent freezing of any WOM balance transiently held by `WombatStaking` (e.g., un-forwarded harvested rewards, fees, or deposits in transit) for the lock duration, and effectively forever since no unlock path exists in this contract.

This matches Immunefi's Critical — Permanent freezing of funds classification, since funds legitimately belonging to depositors/reward recipients can be irrecoverably committed by any outsider with no economic benefit required and no way for governance to reverse it (short of an upgrade).

### Likelihood Explanation
- Requires no capital: `_amount` can be `0` to `type(uint256).max`; the call only requires the target `WombatStaking` contract to hold a non-zero WOM balance at call time (a common transient state given `deposit`/`harvest` flows moving WOM through the contract).
- Fully repeatable: any address, at any time the contract isn't paused, can call `convertWOM` or `convertAllWom()`.
- No special preconditions besides the contract holding WOM, which is a normal operating state, not an edge case.

### Recommendation
Restrict `convertWOM` (and `convertAllWom`) to only be callable by the designated `mWom` contract (or another authorized role), e.g.:
```solidity
function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
    if (msg.sender != mWom) revert OnlyMWom();
    ...
}
```
Additionally, add a `burnWom`/unlock function gated to an authorized role so that WOM can be reclaimed from `veWOM` after `lockDays`, restoring a way to reconcile `mWOM.totalAccumulated` with `veWom` balance.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatStaking` (or fork mainnet pool), `VeWomMock`/real `veWOM`, and `mWOM`, wired per `__WombatStaking_init` and `mWOM.setWombatStaking`. [6](#0-5) 
2. Fund `WombatStaking` with WOM directly (simulate a transient balance from `deposit`/`harvest`) without going through `mWOM`.
3. Snapshot `mWOM.totalAccumulated()` and `IERC20(veWom).balanceOf(address(wombatStaking))`.
4. From an unprivileged EOA with no roles, call `wombatStaking.convertWOM(amount)` directly.
5. Assert:
   - `IERC20(veWom).balanceOf(address(wombatStaking))` increased by the minted veWOM amount.
   - `mWOM.totalAccumulated()` is unchanged (still equal to the pre-call snapshot), proving desynchronization.
   - No `burn`/unlock function on `WombatStaking` exists to recover the locked WOM (grep for `IVeWom(...).burn` calls in `WombatStaking.sol` — none found).
   - The attacker's own token balance did not increase, confirming this is a freezing/griefing vector rather than direct theft, but still results in permanently locked WOM belonging to the protocol/depositors.

```text
    /// @notice convert WOM to mWOM
    /// @param _amount the number of WOM to convert
    /// @dev the WOM must already be in the contract
    function convertWOM(uint256 _amount) whenNotPaused external returns(uint256) {
        uint256 veWomMintedAmount = 0;
        if (_amount > 0) {
            IERC20(wom).safeApprove(veWom, _amount);
            veWomMintedAmount = IVeWom(veWom).mint(_amount, lockDays);
        }

        emit WomLocked(_amount, lockDays, veWomMintedAmount);

        return veWomMintedAmount;
    }
```
