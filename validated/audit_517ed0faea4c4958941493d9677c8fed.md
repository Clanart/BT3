### Title
Unhandled exception from out-of-bounds array access when parsing attacker-crafted commit diffs desynchronizes raw/numstat entries - (File: `app/src/lib/git/log.ts`)

### Summary
`parseRawLogWithNumstat` in `app/src/lib/git/log.ts` walks two logically-parallel data streams produced by `git log -z --raw --numstat` (the "raw" entries pushed into `files`, and the "numstat" lines counted by `numStatCount`) under the implicit invariant that both streams describe the same ordered set of file changes. [1](#0-0)  Just like the `HoneyJarONFT` bug where a second loop assumed the `tokens` array processed by `_creditTill` would always be in a consistent, gas-safe state, this function assumes `files[numStatCount]` will always exist by the time the numstat branch of the loop executes.

### Finding Description
The loop iterates over `\0`-separated tokens from `git log` output. When a line does not start with `:` it is treated as a numstat line, and the code immediately indexes into `files[numStatCount]` to check `isCopyOrRename(files[numStatCount].status)` before incrementing `numStatCount`: [2](#0-1) 
This access is not bounds-checked against `files.length`. The `files` array is only populated inside the `:`-prefixed ("raw") branch of the same loop, using `forceUnwrap` helpers that themselves throw when regex parsing fails on unexpected path/mode content in a commit's raw diff line. [3](#0-2)  If the number of numstat entries exceeds the number of successfully parsed raw entries — which can happen when the diff output contains an unusual commit (e.g. constructed via unusual file modes, embedded control characters, or a crafted merge/rename commit fetched from an attacker-controlled remote) that fails to match the raw-entry regex, or when the two counts otherwise desync — `files[numStatCount]` is `undefined` and accessing `.status` throws a `TypeError`.

This mirrors the report's broken invariant: a second pass over "the same" attacker-influenced dataset assumes state established by a first pass, and no code path protects the mismatch case, so the exception is unhandled at the point it occurs.

### Impact Explanation
`parseRawLogWithNumstat` is consumed by `app/src/lib/git/diff.ts` (commit-diff computation) and `app/src/lib/git/stash.ts` (stash file listing). [4](#0-3)  An uncaught exception here means Desktop fails to enumerate the files changed by a commit/stash after the underlying git object (fetched from a remote, or created by a prior git operation) already exists on disk. As in the LayerZero bug — where NFTs were already burned on the source chain before the local credit loop failed — the git-level state (a commit, a stash entry) is already real, but Desktop's bookkeeping of "what changed" can throw and never surface, risking the app misrepresenting or dropping file-change information for that commit/stash in the UI that a user relies on when deciding what to commit or push.

### Likelihood Explanation
Triggering this requires the user to clone/fetch a repository containing an attacker-crafted commit whose raw-diff line fails `changedEntryRe`/`renamedOrCopiedEntryRe` in `log.ts`/`status-parser.ts`, while still producing a numstat line — an unprivileged action possible via a malicious remote or crafted repository object, consistent with the accepted attacker model (repository content controlled by attacker). I was not able to fully confirm, within the remaining iterations, the exact crafted-diff conditions that desynchronize the two counters, nor trace every caller's error handling (e.g. whether `diff.ts`/`stash.ts` wrap calls in try/catch that could downgrade this to a silent no-op versus a crash) — this would need further investigation of `app/src/lib/git/diff.ts` and `app/src/lib/git/stash.ts` call sites.

### Recommendation
Bound-check `numStatCount` against `files.length` before indexing, and treat any mismatch between the raw and numstat entry counts as a parse failure that is handled explicitly (e.g., returning a partial/degraded result or a clear error) rather than allowing an unguarded `TypeError` to propagate from deep within diff/stash processing.

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
