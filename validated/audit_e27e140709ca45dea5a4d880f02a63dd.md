Audit Report

## Title
Unprivileged `DepositDelegatorRewards` instruction lets anyone inflate `pending_delegator_rewards` on any vote account, permanently locking funds and blocking withdrawal/closure - ([File: programs/vote/src/vote_state/mod.rs])

## Summary
`deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs` only requires the lamport sender to sign the transaction, with no check tying the caller to the target vote account's `authorized_withdrawer`. This lets any unprivileged account permanently inflate a victim vote account's `pending_delegator_rewards` field, which `withdraw()` later uses to reject full account closure and raise the minimum balance required for partial withdrawals.

## Finding Description
`deposit_delegator_rewards` verifies only `verify_authorized_signer(&source_address, signers)` — the signer of the lamport-source account — before performing a CPI transfer and calling `vote_state.add_pending_delegator_rewards(deposit)` on the target vote account, with no relationship check between `source_address` and the vote account's `authorized_withdrawer`: [1](#0-0) 

This state is consumed by `withdraw()`, which unconditionally rejects full closure (`remaining_balance == 0`) when `pending_delegator_rewards > 0`, and otherwise enforces a minimum remaining balance of `rent_exempt_minimum + pending_delegator_rewards` for partial withdrawals: [2](#0-1) 

`pending_delegator_rewards` is only reduced via `calculate_block_reward` in the runtime's reward-distribution path, and that function returns `0` (no reduction) whenever the vote account has no active delegated stake for the epoch (`total_active_stake == 0`) or Alpenglow epoch data is unavailable: [3](#0-2) 

The only guard present — `verify_authorized_signer(&source_address, signers)` — checks that the depositor authorized spending their own lamports, but does nothing to prevent an unrelated party from choosing an arbitrary victim vote account to credit. There is no signer/authority check against the vote account's `authorized_withdrawer` in this instruction path.

## Impact Explanation
An unprivileged attacker can repeatedly raise the floor of lamports the `authorized_withdrawer` must leave in a victim vote account and, while the account lacks qualifying active stake, permanently block full closure — a non-consensual restriction/lock on validator funds reachable through ordinary transactions with no privileged assumptions, matching the accounts/runtime fund-lock impact category.

## Likelihood Explanation
The attack requires only submitting a `VoteInstruction::DepositDelegatorRewards` instruction against any target vote account pubkey, signed by an attacker-controlled funding account with a trivial lamport balance — no timing, races, or special access are needed, and it is cheaply repeatable against any vote account on the network.

## Recommendation
Require that `deposit_delegator_rewards` also be authorized by the vote account's `authorized_withdrawer` (or add an opt-in/cap mechanism) before crediting `pending_delegator_rewards`, so a vote account owner's withdrawable balance cannot be restricted without their consent. Additionally, define and enforce guaranteed eventual reduction of `pending_delegator_rewards` independent of active-stake conditions, to avoid indefinite blocking of withdrawal/closure.

## Proof of Concept
1. Identify any vote account `V` with `authorized_withdrawer = W`.
2. As unprivileged attacker `A`, submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with accounts `[V (writable), A (signer, writable), system_program]`, matching the account layout read in `deposit_delegator_rewards`: [4](#0-3) 
3. The instruction succeeds because only `A`'s signature is checked, incrementing `V.pending_delegator_rewards` via `add_pending_delegator_rewards`: [5](#0-4) 
4. `W` then calls `VoteInstruction::Withdraw` attempting full closure of `V`; it is rejected with `InstructionError::InsufficientFunds` since `pending_delegator_rewards > 0`: [6](#0-5) 
5. If `V` has no active delegated stake for the relevant epoch, `calculate_block_reward` returns `0`, so no reduction of `pending_delegator_rewards` occurs, leaving the lock in place indefinitely: [7](#0-6)

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
