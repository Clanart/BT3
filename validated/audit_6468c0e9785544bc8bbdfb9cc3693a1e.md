### Title
Malicious DKG participant can panic honest nodes via unvalidated `Participant` indexes in blame evaluation - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to GHSA-hg58-rf2h-6rr7 (a malicious peer able to panic / permanently stall a node during a sync protocol by supplying untrusted data), Serai's PedPoP DKG lets an unprivileged protocol peer trigger a panic in an honest participant's `blame` path by submitting a blame accusation that names a `Participant` index never registered in the encryption-key or commitments maps. The code indexes `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly, panicking on absent keys instead of returning an error.

### Finding Description
`Decryption::decrypt_with_proof` looks up the accused-recipient's registered encryption key with a panicking HashMap index, with no check that `decryptor` is a participant of the DKG session (crypto/dkg/pedpop/src/encryption.rs):

```rust
proof
  .dleq
  .verify(
    &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key],
    &[self.enc_keys[&decryptor], *proof.key],
  )
```

The same pattern exists in `BlameMachine::blame_internal`, which indexes `self.commitments[&sender]` when evaluating share validity (crypto/dkg/pedpop/src/lib.rs).

Both entry points are public and driven by peer-supplied data:

- `BlameMachine::blame(self, sender, recipient, msg, proof)` — `msg` is an `EncryptedMessage` deserialized via `EncryptedMessage::read` (untrusted bytes: `key` via `C::read_G`, `pop` via `SchnorrSignature::read`), and `sender`/`recipient` are attacker-influenced indices taken from the accusation.
- `AdditionalBlameMachine::new(context, n, commitment_msgs)` followed by `AdditionalBlameMachine::blame(...)` — explicitly designed so even a non-member can evaluate blame, registering keys only for `1 ..= n`. Any accusation whose `recipient` is outside `1 ..= n` (or whose `sender` is outside the commitments map) reaches a bare `[&key]` index on an empty/absent entry and panics.

`Participant::new` only rejects zero; nothing bounds a supplied index to `n` before the map lookups. The malicious peer needs no secret knowledge: to get past the `msg.pop.verify` gate in `decrypt_with_proof`, they craft an `EncryptedMessage` with a self-chosen `key = generator * k` and a valid Schnorr PoP for `pop_challenge(context, R, key, from, msg)` — fully computable with public inputs — and set `recipient`/`sender` arguments (or in `blame`, arrange for the accusation to name) an index absent from `enc_keys`.

### Impact Explanation
A single peer message deterministically panics the honest participant executing the blame-determination step. In a deployment where DKG completion and blame adjudication gate the validator/multisig set (and where, as in `networks/ethereum/relayer`, panics are escalated to process aborts), this kills the node or permanently stalls the key-generation/blame protocol — precisely the denial-of-service / stuck-state condition described in the CometBFT advisory, mapped onto the DKG's peer-driven state machine. Panics may also cross FFI or drop held `Zeroizing` secrets without the machine's orderly abort path.

### Likelihood Explanation
Low-to-moderate effort: the attacker only needs to be a DKG participant (or accuser, for `AdditionalBlameMachine`, which needs no membership at all) and submit a blame accusation naming a non-registered participant index while providing a valid self-generated PoP — no forgeries, no threshold collusion, and no unusual timing required. The only mitigating factor is that honest flow reaches `blame` only after `calculate_share` reported a fault; however `AdditionalBlameMachine` is reachable unconditionally by any party evaluating an accusation.

### Recommendation
Replace the panicking map indexes with fallible lookups:

- In `Decryption::decrypt_with_proof` (encryption.rs), use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` (or a dedicated `UnknownParticipant` variant).
- In `BlameMachine::blame_internal` (lib.rs), fetch `self.commitments.get(&sender)` and treat absence as the accuser's fault (`return recipient`) rather than panicking.
- Validate `sender`/`recipient` against `params.all_participant_indexes()` at the top of `blame`/`blame_internal` so out-of-range accusations are rejected with a typed error.

### Proof of Concept
```rust
// C = Ristretto (or any Ciphersuite); attacker controls an EncryptedMessage
// and submits a blame accusation naming a recipient index > n.

// 1. Build an AdditionalBlameMachine for a DKG with n = 2 participants
//    (commitment_msgs for participants 1 and 2 registered normally).
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, 2, commitment_msgs).unwrap();

// 2. Craft a message with a valid PoP under a key the attacker knows.
//    pop binds `from`, so sign pop_challenge(context, R, key, attacker_i, ciphertext)
//    with the private key behind `key` — all public inputs.
let msg: EncryptedMessage<Ristretto, SecretShare<Scalar>> = forged_msg_with_valid_pop();

// 3. Call blame with recipient = Participant::new(3) (never registered).
//    decrypt_with_proof indexes self.enc_keys[&decryptor] -> panic.
let _ = machine.blame(attacker_i, Participant::new(3).unwrap(), msg, Some(proof));
```

Result: thread panic at `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs` (line ~388) — an out-of-map HashMap index — instead of a returned `DecryptionError`. The equivalent path via `BlameMachine::blame` panics at `self.commitments[&sender]` in `crypto/dkg/pedpop/src/lib.rs` (line ~599) when `sender` names an unregistered index.
