### Title
Unbounded `FilterCriteria.Addresses` (and `Topics`) in `eth_getLogs`/`eth_newFilter`/`eth_logs` enables RPC DoS - (File: `node/cn/filters/api_kaia_filter.go`)

### Summary
Kaia's JSON-RPC filter API (`GetLogs`, `NewFilter`, and `Logs`) accepts a `FilterCriteria` whose `Addresses` and `Topics` fields have no upper bound on length, unlike the upstream fix that limits `Topics` to `maxTopics`. A public RPC caller can submit a single request with hundreds of thousands of addresses/topics that must be linearly scanned against every block's bloom filter and every log, exhausting server CPU with a single call and no authentication required.

### Finding Description
`KaiaFilterAPI.GetLogs` builds a `Filter` directly from the caller-supplied `crit.Addresses` and `crit.Topics` with no size validation whatsoever: [1](#0-0) 

The same unbounded pass-through of `crit.Addresses`/`crit.Topics` also occurs in `NewFilter` (installs a persistent subscription filter) and `Logs` (creates an event subscription): [2](#0-1) [3](#0-2) 

`UnmarshalJSON` for `FilterCriteria` decodes an arbitrary-length JSON array into `args.Addresses` and `args.Topics` with no length cap enforced during decoding: [4](#0-3) 

Downstream, `NewRangeFilter` iterates the addresses to build bloom-bit filter clauses, and per matching block `filterLogs`/`includes` does an `O(addresses)` linear scan (`slices.Contains`) for every log in every block in range: [5](#0-4) [6](#0-5) 

Notably, Kaia's test suite explicitly documents that it does **not** enforce the topic limit that upstream go-ethereum added: the comment `// topics more than 4 // NOTE: Kaia doesn't support errExceedMaxTopics` shows the intended `success: true` for a criterion with 5+ topic slots: [7](#0-6) 

This means Kaia is in an even weaker position than the original minievm report: both `Addresses` and `Topics` are unbounded, whereas minievm at least limited `Topics`.

### Impact Explanation
Any unauthenticated public RPC caller can send a single `eth_getLogs`/`kaia_getLogs` (or `eth_newFilter`/`eth_logs` subscription) request with a very large `Addresses` (and/or `Topics`) array. Because `FilterCriteria.Addresses` is stored (in the `NewFilter` case, persisted per-filter in `api.filters`) and iterated per block/log during matching (`includes`/`filterLogs`, `bloomFilter`), a modest request payload (well within the default HTTP body size limits) can consume disproportionate CPU/memory on the node's RPC goroutine, degrading or halting the JSON-RPC service for all legitimate public RPC callers, transaction senders needing to poll logs, gasless/auction participants relying on RPC availability, etc. This is a direct, low-cost availability/DoS vector against public infrastructure, matching the severity rationale accepted in the original minievm report (Medium/High, judged effectively High due to ease and near-zero cost).

### Likelihood Explanation
Trivially reachable by any external, unprivileged caller of the public JSON-RPC endpoint — no special permissions, funds, or preconditions are needed beyond crafting a large JSON array of addresses/topics, which is well documented and requires no special tooling.

### Recommendation
Enforce an explicit maximum on `len(crit.Addresses)` (and add a cap on `len(crit.Topics)`, matching or exceeding upstream's `maxTopics`) at the entry points `KaiaFilterAPI.GetLogs`, `KaiaFilterAPI.NewFilter`, and `FilterAPI.Logs` in `node/cn/filters/api_kaia_filter.go`, returning an RPC error when exceeded — mirroring the mitigation applied upstream (initia-labs/minievm PR #165) for `Addresses`, plus restoring/adding the topics bound that the current test suite explicitly disables.

### Proof of Concept
1. Send `eth_getLogs`/`kaia_getLogs` with `{"address": [<200,000 distinct or repeated hex addresses>], "fromBlock": "0x0"}`.
2. `KaiaFilterAPI.GetLogs` (node/cn/filters/api_kaia_filter.go:402) constructs a `NewRangeFilter` with the full unbounded `crit.Addresses` slice.
3. `NewRangeFilter` (node/cn/filters/filter.go:90) builds a bloombits filter clause of size `len(addresses)`, and for every matching block, `checkMatches`→`filterLogs`→`includes` performs an `O(n)` scan per log against the address list.
4. Repeating this request (or issuing it as a persistent `NewFilter`/`Logs` subscription, which additionally retains the criteria in `api.filters` for the filter's lifetime) allows an attacker to repeatedly or continuously degrade RPC responsiveness for all callers, analogous to the demonstrated PoC in the linked minievm report where a 200k-address request took multiple seconds per call.

// NewRangeFilter creates a new filter which uses a bloom filter on blocks to
// figure out whether a particular block is interesting or not.
func NewRangeFilter(backend Backend, begin, end int64, addresses []common.Address, topics [][]common.Hash) *Filter {
	// Flatten the address and topic filter clauses into a single bloombits filter
	// system. Since the bloombits are not positional, nil topics are permitted,
	// which get flattened into a nil byte slice.
	var filters [][][]byte
	if len(addresses) > 0 {
		filter := make([][]byte, len(addresses))
		for i, address := range addresses {
			filter[i] = address.Bytes()
		}
		filters = append(filters, filter)
	}
	for _, topicList := range topics {
		filter := make([][]byte, len(topicList))
		for i, topic := range topicList {
			filter[i] = topic.Bytes()
		}
		filters = append(filters, filter)
	}
	// Assemble and return the filter
	size, _ := backend.BloomStatus()

	// Create a generic filter and convert it into a range filter
	filter := newFilter(backend, addresses, topics)

	filter.matcher = bloombits.NewMatcher(size, filters)
	filter.begin = begin
	filter.end = end

	return filter
}

// filterLogs creates a slice of logs matching the given criteria.
func filterLogs(logs []*types.Log, fromBlock, toBlock *big.Int, addresses []common.Address, topics [][]common.Hash) []*types.Log {
	var ret []*types.Log
Logs:
	for _, log := range logs {
		if fromBlock != nil && fromBlock.Int64() >= 0 && fromBlock.Uint64() > log.BlockNumber {
			continue
		}
		if toBlock != nil && toBlock.Int64() >= 0 && toBlock.Uint64() < log.BlockNumber {
			continue
		}

		if len(addresses) > 0 && !includes(addresses, log.Address) {
			continue
		}
		// If the to filtered topics is greater than the amount of topics in logs, skip.
		if len(topics) > len(log.Topics) {
			continue Logs
		}
		for i, topics := range topics {
			match := len(topics) == 0 // empty rule set == wildcard
			if slices.Contains(topics, log.Topics[i]) {
				match = true
			}
			if !match {
				continue Logs
			}
		}
		ret = append(ret, log)
	}
	return ret
