### Title
Stale `GitHubRepository` association (owner/private/parent) is never cleared or re-validated after a remote is repointed, letting it silently keep granting API-account/credential trust and PR/branch-checkout trust to a different, attacker-controlled repository - (File: `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop attaches a `GitHubRepository` record (owner, name, `private` flag, `parent`/fork relationship, `endpoint`) to a local `Repository` the first time it matches the local `origin` remote to a known account host. This mirrors the `PRBProxy` bug pattern: a piece of trust state (there: plugins/permissions tied to a proxy; here: the GitHub identity/ownership tied to a local repo) is established once and then **never invalidated** when the underlying "ownership" changes - here, when the git remote is later repointed to a different repository/host. The code contains an explicit acknowledgment of this: [1](#0-0) 

### Finding Description
`repositoryWithRefreshedGitHubRepository` is the only place that tries to keep the `gitHubRepository` association in sync, but it explicitly bails out and keeps the old association when a match can't be made: [2](#0-1) 

The association is derived purely from a hostname match against the current remote URL via `matchGitHubRepository`, which only checks that the remote's hostname equals one of the signed-in accounts' endpoint hostname - it does not verify that the owner/name still correspond to the previously-associated repository, and it never clears a *previous* mismatched association: [3](#0-2) [4](#0-3) 

This stale `gitHubRepository` object is then relied on for security-relevant decisions:
1. **Account/token selection for API calls** - `getAccountForRepository` returns the account tied to the *cached* `gitHubRepository.endpoint`, with no re-check that the current remote still points at that account's repo: [5](#0-4) 
This account is then used to drive Copilot-based commit-message generation and conflict resolution (`getAccountForCommitMessageGeneration`, `getAccountForCopilotConflictResolution`), meaning repository content/diffs can be sent under an account context that no longer matches the actual remote the code is being pulled from/pushed to.
2. **Deep-link ("Open in Desktop") repository matching** - `doesRepositoryMatchUrl` decides whether an incoming `x-github-client://openRepo` URL matches an *existing* local repository by comparing the link's URL to the cached `gitHubRepository.htmlURL`/`parent.htmlURL`, not to the actual current git remote: [6](#0-5) 
If that local repo's `origin` has since been silently repointed (e.g., by a build script, a compromised submodule/hook, or a user pasting a different remote in Repository Settings), Desktop will still treat the link as authoritative for that repo and proceed to `openPullRequestFromUrl` / `_checkoutPullRequest`, which adds a new remote and fetches/checks out branches from attacker-supplied `headCloneUrl`: [7](#0-6) [8](#0-7) 
3. **Remote URL "trust-and-follow" behavior** - `updateRemoteUrl` will automatically rewrite the local `origin` URL to whatever the (stale) `gitHubRepository` association's API record says the clone URL should be, as long as the *old* stored URL still superficially "matches" the previous association: [9](#0-8) 

None of these code paths re-derive or reset `repository.gitHubRepository` from the actual, current remote before trusting it; the TODO at `app-store.ts:4880-4882` documents that this has been a known, unresolved gap since desktop/desktop#1144.

### Impact Explanation
This is the same broken invariant as the PRBProxy report: a trust/ownership record (`gitHubRepository`, analogous to `plugins`/`permissions`) survives a change of the underlying "owner" (the actual remote/repo) without being reset. Concretely:
- Desktop may keep using a previously-authenticated account's token/endpoint to authenticate API requests and Copilot features (commit message generation, conflict resolution) for a repository whose remote no longer corresponds to that account/repo, risking sending private code/diff content to the wrong context or attaching the wrong identity to API calls.
- Deep links (`x-github-client://openRepo`, clickable from any web page or forwarded link) can be routed to a local repository whose remote has been quietly changed, causing Desktop to auto-add a remote and fetch/checkout branches (`_checkoutPullRequest` → `addRemote` + `_fetchRemote`) from a URL supplied by the PR/link payload without re-validating that the local repo's *actual* git identity still matches what the user expects.
- Because these mappings are per in-memory/`Repository` object state with no user-visible way to inspect or force-reset them, the previous "owner" of the trust relationship (or anyone able to influence the remote URL or the PR head data) can keep leveraging stale association silently, similar to how the reported `PRBProxyStorage` plugins/permissions kept working after proxy ownership changed hands.

### Likelihood Explanation
Medium. It requires a precondition where the local repo's remote is repointed to a different (potentially attacker-controlled) URL/host after the initial `gitHubRepository` association was made - via normal user actions such as editing the remote in Repository Settings, via `_convertRepositoryToFork`, or via any external process that edits `.git/config` (e.g. build tooling, a compromised dependency-installed git hook, or a shared/cloned "template" repo whose remote is later swapped). No admin rights or local-malware assumption is required beyond the repo/remote being attacker-influenced, which is within the stated valid-impact scope (attacker controls a fetched/cloned repository or a git remote/proxy response, or a link the user clicks). The explicit unresolved TODO referencing desktop/desktop#1144 confirms this is a known, long-standing gap rather than a hypothetical.

### Recommendation
- Re-derive (or at minimum re-validate) `repository.gitHubRepository` from the *current* default remote every time it is used for a trust decision (account/token selection, deep-link matching, PR checkout), instead of only opportunistically refreshing it and falling back to the stale value on any lookup failure (`app-store.ts:4880-4885`).
- When the default remote's host/owner/name no longer matches the cached `gitHubRepository`, clear the association (set it to `null`) rather than silently keeping the old one, forcing re-authentication/re-matching before any account-token or deep-link trust decision is made.
- In `doesRepositoryMatchUrl`, cross-check against the live remote (via `gitStore.defaultRemote`) rather than only the cached `GitHubRepository.htmlURL`/`parent.htmlURL`.
- In `updateRemoteUrl`, avoid auto-rewriting the local remote based on a stale API-fetched clone URL without confirming the current remote actually still resolves to the same repository/owner.

### Proof of Concept
1. Clone `https://github.com/victim-org/project` with GitHub Desktop while signed in as `alice`; Desktop matches it and stores `repository.gitHubRepository = { owner: victim-org, name: project, endpoint: alice's endpoint, private: true/false, ... }`.
2. Outside of Desktop (e.g., via a build script, a "helpful" setup tool, or a maintainer action script bundled with the repo) change `origin` to `https://github.com/attacker-org/project-fork` (same hostname `github.com`, so `matchGitHubRepository`'s hostname check would still pass on next refresh, but even before any refresh happens the stale association is used as-is).
3. Before any explicit re-match happens (e.g., app hasn't called `repositoryWithRefreshedGitHubRepository` for that repo, or the refresh fails/returns non-matching and hits the early-bail branch at `app-store.ts:4883-4885`), Desktop still exposes `repository.gitHubRepository` pointing at `victim-org/project`.
4. Send the user (or have the attacker's malicious page auto-navigate to) a deep link `x-github-client://openRepo/https://github.com/victim-org/project?pr=123`. `doesRepositoryMatchUrl` matches this to the local repo based on the stale `htmlURL`, and `_checkoutPullRequest` is invoked using PR head data that can point `headCloneUrl` at an attacker-controlled fork, causing Desktop to add a new remote and fetch/checkout attacker-authored code into the user's working directory believing it is operating on `victim-org/project`.

Note: I was not able to execute this end-to-end in a live app instance (no runtime access), so this PoC is based on tracing the exact code paths above; the missing invalidation (`app-store.ts:4880-4885`) and the identity checks in `doesRepositoryMatchUrl`/`updateRemoteUrl`/`getAccountForRepository` are directly verifiable in the cited source.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

): Account | null {
  const gitHubRepository = repository.gitHubRepository

  }

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
