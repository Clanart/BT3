### Title
Payout attribution binding is broken: attacker-controlled OP_RETURN in a payout tx forces an arbitrary operator's automation to claim a reimbursement it never funded - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` derives `payout_payer_operator_xonly_pk` purely from parsing the OP_RETURN output of whatever transaction spends the `withdrawal_utxo`, with no check that the named operator actually supplied the funds that paid the withdrawer. Because the withdrawer's authorization signature uses `TapSighashType::SinglePlusAnyoneCanPay` (only committing to the withdrawal input and the single payout output), any party who can construct a valid withdrawal — including an unprivileged attacker who is simply the withdrawer calling Citrea's `withdraw()` themselves — can add their own funding inputs, pay the withdrawer correctly, and embed an arbitrary (real) operator's xonly pubkey in the unsigned OP_RETURN output. This causes `PayoutCheckerTask` on that operator's node to automatically call `handle_finalized_payout` and proceed toward reimbursement for a payout the named operator never fronted.

### Finding Description
Broken binding (stated as equality that should hold but doesn't):
`withdrawals.payout_payer_operator_xonly_pk` (recorded value) == the xonly pubkey of the operator whose own wallet funds were actually spent as inputs to the payout transaction.

In reality the code only guarantees:
`withdrawals.payout_payer_operator_xonly_pk` == whatever xonly pubkey bytes appear in the first OP_RETURN output of the transaction that happens to spend `withdrawal_utxo`.

Trace:
1. `Operator::withdraw` (`core/src/operator.rs:560-680`) builds a payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) whose sole *signed* input is the user's withdrawal UTXO, signed with `SinglePlusAnyoneCanPay` (only input 0 and output 0 are committed by the signature — see enforcement in `core/src/rpc/parser/operator.rs:161-203`). The OP_RETURN output (embedding `operator_xonly_pk`) and the anchor output are **not covered** by the signature.
2. To actually fund the payout, the operator's node calls `self.rpc.fund_raw_transaction(..., add_inputs: Some(true), ...)` (`core/src/operator.rs:652-674`), which appends the operator's *own* wallet UTXOs as additional inputs and signs them. This is the real "fronting" step.
3. Because the user's signature is `SinglePlusAnyoneCanPay`, *anyone* holding a valid withdrawal signature (in particular, the withdrawer themselves, who is unprivileged per the threat model and creates this signature when calling Citrea's `withdraw()`) can independently construct an alternate transaction spending the same `withdrawal_utxo`, correctly paying the committed output, adding their own funding inputs (or none, if the UTXO itself already covers the amount), and placing an arbitrary xonly pubkey — e.g., a real operator X's pubkey — in the OP_RETURN output. Nothing in the protocol requires the OP_RETURN pubkey to match whoever supplied the completing inputs.
4. `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) parses whichever transaction ends up spending `withdrawal_utxo` and blindly extracts `operator_xonly_pk` from `get_first_op_return_output`/`parse_op_return_data`, storing it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) with no validation against the transaction's actual inputs.
5. `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) on operator X's own node queries `get_first_unhandled_payout_by_operator_xonly_pk` filtered by `self.operator.signer.xonly_public_key` (`core/src/database/verifier.rs:282-313`), finds the forged entry, and automatically calls `Operator::handle_finalized_payout` (`core/src/operator.rs:839+`), which allocates a kickoff connector and proceeds toward reimbursement — all without X's consent or actual expenditure.
6. `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) only checks that the DB's `operator_xonly_pk` equals `kickoff_data.operator_xonly_pk` (i.e., that X's own kickoff matches the forged DB entry it was tricked into creating) — it never verifies that X's wallet actually funded the payout tx's inputs. This guard is self-referential and does not catch the forgery.

### Impact Explanation
An unprivileged attacker can attribute a Bitcoin payout tx to an arbitrary operator by simply controlling the OP_RETURN output (unsigned, uncommitted by the withdrawer's `SinglePlusAnyoneCanPay` signature). This forces that operator's automated `PayoutCheckerTask` to run `handle_finalized_payout`, consuming one of the operator's limited kickoff connectors for a round and driving the protocol toward the operator being reimbursed via the presigned kickoff/reimburse transaction graph from the deposit's move-to-vault funds — for a payout the operator never funded. This matches "an operator reimbursed for a payout it never funded" (Critical). The attack is repeatable across every withdrawal and can target any operator whose real xonly pubkey is attacker-known (operator pubkeys are public protocol data).

### Likelihood Explanation
The attacker only needs to be a withdrawer able to call Citrea's `withdraw()` (explicitly listed as an unprivileged capability), choose the withdrawal UTXO bytes and their own Schnorr signature/sighash flag, and construct/broadcast a Bitcoin transaction with a crafted OP_RETURN — all capabilities explicitly granted to the unprivileged attacker in the threat model. No operator cooperation, key compromise, or majority hashrate is needed. Cost is limited to normal Bitcoin transaction fees.

### Recommendation
Do not derive payer attribution solely from the unsigned OP_RETURN output. Instead, cryptographically bind attribution to the operator by requiring the OP_RETURN (or another committed field) to be covered by a signature/commitment that can only be produced by the true funding operator (e.g., include the OP_RETURN in the sighash of an operator-specific input, or require the completing/funding inputs of the payout tx to be verifiably tied to the claimed operator's known UTXO set/address before crediting `payout_payer_operator_xonly_pk`).

### Proof of Concept
`cargo test` plan (regtest, no mainnet/live Citrea):
1. Set up a deposit and a withdrawal registered on the (mock) Citrea client, producing a valid `withdrawal_utxo` and a valid `SinglePlusAnyoneCanPay` user signature (as the test harness already does in `core/src/test/common/clementine_utils.rs`).
2. Instead of calling operator X's `Withdraw` RPC, directly build a payout transaction spending `withdrawal_utxo`, paying the committed output correctly, but using attacker-supplied additional funding inputs (from a wallet other than operator X's), and embed operator X's real xonly pubkey in the OP_RETURN output. Broadcast it and mine to finality.
3. Run the verifier's block sync / `update_finalized_payouts` path and assert `payout_payer_operator_xonly_pk == X` in the `withdrawals` table even though X's wallet balance/UTXOs were untouched.
4. Run operator X's `PayoutCheckerTask::run_once` and assert it returns `true` and calls `handle_finalized_payout`, i.e., X's kickoff connector gets consumed and reimbursement flow proceeds — asserting the binding `payout_payer_operator_xonly_pk == actual funder of payout_tx inputs` is violated (LHS = X, RHS = attacker).
