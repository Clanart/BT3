## Title
Payout attribution to an operator xonly-pubkey is not cryptographically bound to the fronting party, allowing an unfunded operator to be credited as the payer of a withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
The bug class from the report (SALT reused after unstake/transfer breaks the binding between "who staked" and "who voted") maps onto Clementine's `Payout` transaction: the binding between "the party who actually fronted a withdrawal" and "the operator xonly-pubkey credited for reimbursement" is not cryptographically enforced. The user's authorization signature only covers the payout output, not the OP_RETURN attribution output, so anyone in possession of the withdrawal signature can construct and fund a valid payout transaction while writing an arbitrary (but valid, pre-registered) operator's x-only public key into the attribution OP_RETURN.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user's payout output (index 0), an anchor output (index 1), and an OP_RETURN output carrying `operator_xonly_pk` (index 2) [1](#0-0) . The only witness produced for this transaction is the user's key-spend signature on input 0 [2](#0-1) .

Crucially, the parser enforces that this user signature must use `SIGHASH_SINGLE|ANYONECANPAY` [3](#0-2) , and `operator::withdraw` verifies the signature only against `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` [4](#0-3) . Under `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits only to the single input being spent and the output at the *same index* (index 0, the user's payout output). It does **not** commit to the anchor output or, critically, to the OP_RETURN output that names which operator is credited as the payer.

Later, when the chain is scanned, `update_finalized_payouts` extracts the attributed operator purely by reading the OP_RETURN bytes of whatever payout transaction spent the withdrawal UTXO — with no signature check tying that pubkey to the party who actually broadcast/funded the transaction: [5](#0-4) 
This value is persisted as `payout_payer_operator_xonly_pk` [6](#0-5)  and later drives `get_first_unhandled_payout_by_operator_xonly_pk` / `mark_payout_handled`, which is exactly the query the operator's own automation (`PayoutCheckerTask`) uses to discover a payout it should be reimbursed for [7](#0-6) , [8](#0-7) .

Because the OP_RETURN attribution is unauthenticated, any party who has the withdrawal user's `input_signature` (which, per the code's own doc comment, is "given to operators off-chain" — i.e., shared with multiple potential fronting parties, not bound to one specific operator) can independently build the exact `Payout` transaction, choose an arbitrary pre-registered operator's x-only pubkey for the OP_RETURN output, fund the transaction from their own wallet (or via any other means outside Clementine's gRPC surface — the transaction only needs a valid Bitcoin broadcast, not a call through `internal_withdraw`/`withdraw`), and broadcast it directly to the Bitcoin network. This bypasses Clementine's own `operator::withdraw` code path entirely (that code is only invoked when an operator is the one choosing to front — but nothing stops a third party from constructing the same transaction shape and broadcasting it directly via Bitcoin RPC).

This breaks exactly the binding highlighted in the task's rules: "the operator credited versus the party that paid."

### Impact Explanation
This maps to the Critical impact category "an operator reimbursed for a payout it never funded." Once the chain scanner records a `payout_payer_operator_xonly_pk` for a withdrawal, that named operator's `PayoutCheckerTask` will pick it up as an unhandled payout and drive it through `handle_finalized_payout` → the reimbursement pipeline (`get_reimbursement_txs`), ultimately releasing bridge-locked/collateral funds to that operator's `Reimburse` transaction — even though the actual BTC that satisfied the user's withdrawal came from a different, unaccountable party. The protocol's core custody invariant (operator reimbursed ⇔ operator actually fronted) is broken because the attribution mechanism has no cryptographic authorization step.

### Likelihood Explanation
The attacker does not need any privileged role (verifier/operator/aggregator/watchtower) — they only need the withdrawal's off-chain `input_signature`, which by the code's own documentation is distributed "to operators" generically (plural, off-chain), not scoped or bound to a single specific operator's identity. Constructing the alternate `Payout` transaction requires only standard Bitcoin transaction construction (same shape, different OP_RETURN payload) and broadcasting it directly to the Bitcoin network, entirely bypassing Clementine's gRPC/authorization layers. I could not fully trace whether `validate_payer_is_operator`/`handle_finalized_payout` (in `core/src/operator.rs`, functions not fully retrieved before the final iteration) perform any additional cross-check (e.g., requiring the operator to have separately signed/acknowledged this specific withdrawal) that might reduce exploitability — this remains a caveat on precise likelihood, though the OP_RETURN-parsing code path itself (`update_finalized_payouts`) performs no such check.

### Recommendation
Bind the OP_RETURN attribution output to the same authorization that governs the payout, or add an operator-signed commitment: e.g., require the operator to co-sign (or MuSig2-sign, similar to the optimistic-payout flow) a message that includes the operator's own x-only pubkey together with the withdrawal outpoint/output before the chain scanner accepts `payout_payer_operator_xonly_pk`. Alternatively, change the user's signature sighash type (or add a second signature) so that it commits to all outputs (including the OP_RETURN), removing the ability for a third party to swap the attributed operator without invalidating the signature.

### Proof of Concept
Conceptual (no test harness available in the indexed context to fully execute end-to-end, but the construction is directly supported by the cited code paths):
1. Obtain a user's off-chain `input_signature` for a pending Citrea withdrawal (shared "to operators" per doc comment in `operator_reimburse.rs:392`).
2. Independently call `create_payout_txhandler(input_utxo, output_txout, victim_operator_xonly_pk, user_sig, network)` with `victim_operator_xonly_pk` set to any pre-registered operator's pubkey (not the caller's own key) [1](#0-0) .
3. Since the signature only covers `SIGHASH_SINGLE|ANYONECANPAY` on output index 0, it remains valid regardless of which pubkey is placed in the OP_RETURN output.
4. Fund and broadcast this transaction directly via Bitcoin RPC (outside Clementine's gRPC service).
5. When verifiers process the block, `update_finalized_payouts` will attribute the payout to `victim_operator_xonly_pk` purely from the OP_RETURN bytes [5](#0-4) , and that operator's `PayoutCheckerTask` will subsequently claim reimbursement for a withdrawal it never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
