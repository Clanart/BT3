### Title
Panic on missing/short per-participant preprocess/share vectors crashes the Bitcoin signing machine - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` index and `remove(0)` from per-participant `Vec`s supplied inside the caller-provided `HashMap`s, assuming each vector has exactly one entry per transaction input. That invariant is only enforced by `read_preprocess`/`read_share`; the `sign`/`complete` APIs themselves accept attacker-influenced `HashMap<Participant, Vec<...>>` values and perform no length check. A participant supplying a vector shorter than the number of inputs triggers an out-of-bounds panic, crashing the signer — the same unchecked-assumption crash class as CVE-2015-8720 (improper validation of a parsed value leading to application crash).

### Finding Description
In `TransactionSignMachine::sign`, the coordinator-supplied `commitments: HashMap<Participant, Vec<Preprocess<Secp256k1>>>` is transposed by indexing `commitments[c]` for each input index `c` in `0 .. self.sigs.len()`:

```rust
// networks/bitcoin/src/wallet/send.rs:364-371
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```

If any participant's `Vec<Preprocess>` has fewer than `self.sigs.len()` elements, `commitments[c]` panics with an index-out-of-bounds.

Symmetrically, in `TransactionSignatureMachine::complete`, `shares.remove(0)` is called once per transaction input on every participant's `Vec<SignatureShare>`:

```rust
// networks/bitcoin/src/wallet/send.rs:417-420
let sig = schnorr.complete(
  shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>(),
)?;
```

An empty or short `Vec<SignatureShare>` causes `Vec::remove(0)` to panic. Unlike `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs:447-452`, which runs `validate_map(&shares, self.view.included(), params.i())` before consuming shares, the Bitcoin wrapper performs no validation of either the map's participant set or the per-participant vector lengths before indexing/removal.

### Impact Explanation
An unprivileged counterparty in the multisig (or a coordinator feeding a signer malformed preprocess/share collections) causes an unconditional panic in the signing process. In Rust this aborts the signing task — and under `panic = "abort"` or an uncaught panic in the processor, the whole node — producing a denial of service of the threshold-signing pipeline for that transaction and any further work on the same process. This matches the CVE's impact (remote crash via attacker-influenced input) and requires no key compromise, collusion, or protocol violation beyond sending a malformed collection to a public API.

### Likelihood Explanation
The vectors are attacker-shaped values crossing the `sign`/`complete` API boundary. The only thing keeping them well-formed is the convention that they were produced by `read_preprocess` (send.rs:351-353) / `read_share` (send.rs:409-411), which read exactly `self.sigs.len()` entries per participant. Nothing in `sign` or `complete` enforces this; a peer or relaying coordinator that deserializes these collections through any other path — or truncates/duplicates entries — reaches the panic directly. The vulnerable lines are on the unconditional happy path of every multi-input Bitcoin spend.

### Recommendation
Validate the `commitments` and `shares` maps before use, mirroring `validate_map` usage in `crypto/frost/src/sign.rs`:

- In `TransactionSignMachine::sign`, check `commitments.len()` per participant equals `self.sigs.len()` (or collect with `get(c)`/`ok_or`/`?` instead of indexing) before transposing.
- In `TransactionSignatureMachine::complete`, verify each participant's share vector has exactly `self.sigs.len()` elements before `remove(0)`, and return a `FrostError` instead of panicking.
- Alternatively, make `Vec<SignatureShare>`/`Vec<Preprocess>` an opaque fixed-size type so malformed collections cannot be constructed outside `read_share`/`read_preprocess`.

### Proof of Concept
```rust
// Conceptual: signer with a 2-input SignableTransaction -> TransactionSignMachine
// having sigs.len() == 2.

// Path 1 (sign): a participant l sends a preprocess Vec with only 1 entry
let mut commitments: HashMap<Participant, Vec<Preprocess<Secp256k1, ()>>> = HashMap::new();
commitments.insert(Participant(1), vec![preprocess_a]);        // len 1
commitments.insert(Participant(2), vec![preprocess_b]);        // len 1
// sign() iterates c in 0..2; commitments[c] with c == 1 indexes out of bounds
// -> thread panics: index out of bounds: the len is 1 but the index is 1
let _ = sign_machine.sign(commitments, b"");

// Path 2 (complete): a participant sends an empty share Vec
let mut shares: HashMap<Participant, Vec<SignatureShare<Secp256k1>>> = HashMap::new();
shares.insert(Participant(2), vec![]);  // empty
// complete() calls shares.remove(0) on the empty Vec -> panic
let _ = sig_machine.complete(shares);
```

Both panics occur before any `FrostError` can be returned, aborting the caller rather than failing gracefully.
