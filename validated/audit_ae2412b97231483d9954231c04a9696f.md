### Title
Unchecked ERC20 return value in `IntentGatewayV2` dust-sweep and escrow withdrawal lets a non-standard token silently fail transfer while state is marked settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` pays out escrowed order funds and swept dust with a raw low-level `.call()` to the token's `transfer` selector, and only checks that the *call itself* did not revert (`success`). It never decodes/validates the ABI-encoded boolean return value. Standard tokens that return `false` on failed transfer (rather than reverting) — a well-known non-conforming ERC20 pattern (the exact bug class from the linked report) — will make this code treat the transfer as successful even though no tokens moved, while internal escrow accounting is unconditionally decremented and completion events are emitted.

### Finding Description
In `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests) and in the `SweepDust` handler, token payouts are performed like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

and identically in the `SweepDust` branch of `onAccept`: [2](#0-1) 

`token.call(...)` only reports `success = false` when the callee reverts or the call fails at the EVM level (e.g., no code, out of gas). For a token contract that is present and executes normally but returns `abi.encode(false)` on a failed transfer (a documented non-conforming pattern, e.g. some deflationary/paused/blacklist tokens), `success` is `true`, `TransferFailed()` is never raised, `_orders[commitment][token] -= amount` proceeds, `EscrowReleased`/`EscrowRefunded`/`DustSwept` events fire, and `_filled[commitment]` is marked — all while the beneficiary received zero tokens.

This is precisely the bug class from report M-13: the code checks the low-level call's `success` bit but never inspects the encoded boolean return value, so a token that "fails silently" is counted as a successful, one-time settlement. This directly contradicts the `_orders` escrow accounting invariant and the one-time-settlement guarantee the contract relies on (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();` at line 691 only checks non-zero balance, not that funds actually left the contract).

By contrast, the deposit/input side of the same contract, and the non-Tron `evm/src/apps/IntentGatewayV2.sol`, consistently use OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` (which decode and require the boolean return), e.g.: [3](#0-2) 

That inconsistency confirms the raw `.call()` payout path in `withdraw()`/`SweepDust` is the deviation, not an intentional design choice for Tron TRC-20 compatibility (Tron's TRC-20 standard tokens still return a boolean the same way).

### Impact Explanation
This is a direct fund-loss/fund-lock bug against the live bounty's "stealing or loss of funds" and "false state acceptance / logic attacks" categories: when the configured escrow/output token is one that returns `false` instead of reverting, the beneficiary (solver, order filler, or refund recipient) receives nothing while the protocol's internal ledger (`_orders[commitment][token]`) is decremented and the commitment is marked filled/refunded via `_filled[body.commitment] = beneficiary`, permanently preventing any retry or recovery of the escrowed funds. No malicious relayer, prover, or governance actor is required — this is triggered purely by the properties of the configured token, reachable through the normal `onAccept` message path once a `RedeemEscrow`/`RefundEscrow`/`SweepDust` request is delivered by any relayer following the standard ISMP flow.

### Likelihood Explanation
Likelihood is conditioned on the intent gateway being deployed with, or later configured for, a non-standard ERC20/TRC20 token that returns `false` rather than reverting on failed transfers (common among tokens with pausable/blacklist/fee-on-transfer logic). Given `IntentGatewayV2` is explicitly designed to support arbitrary tokens as order inputs/outputs (mirroring the "Launch event token can be any token" framing of the original report), this condition is realistic rather than contrived, and requires no privileged or malicious actor to exploit — it manifests automatically the first time such a token's transfer legitimately fails (e.g., beneficiary blacklisted, contract paused, insufficient balance edge cases).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout pattern in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the contract (`using SafeERC20 for IERC20;` is already imported), so that both call failure and a `false` boolean return revert the transaction before escrow accounting is mutated or completion events are emitted.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an order whose output/escrow token is a non-standard ERC20/TRC20 that returns `false` on failed `transfer` (e.g., a token that blacklists a recipient or is paused, per its own logic, without reverting).
2. Have a relayer deliver a valid `RedeemEscrow` `WithdrawalRequest` (or `SweepDust`) for that order/commitment, authenticated normally through `onAccept`.
3. Have the token's transfer to `beneficiary` internally hit its no-revert-false-return condition (e.g., beneficiary is blacklisted or contract paused).
4. Observe: `token.call(...)` returns `success = true` (call executed, just returned `false`), so `TransferFailed()` is never reverted; `_orders[body.commitment][token] -= amount` executes; `_filled[body.commitment] = beneficiary` is set; `EscrowReleased`/`EscrowRefunded` event emits — yet `beneficiary`'s token balance is unchanged and the escrowed funds are now unrecoverable (order is marked filled/refunded with `UnknownOrder()` guard now bypassed on retry since `_orders` was already decremented).
