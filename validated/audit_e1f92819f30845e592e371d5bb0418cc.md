## Finding

### Title
`code::publish_package` never binds a package's declared `source`/`source_digest` metadata to the actual bytecode it publishes, making the CLI's `VerifyPackage` command a false assurance of on-chain code integrity - (File: `aptos-move/framework/aptos-framework/sources/code.move`, `aptos-move/cli/src/stored_package.rs`, `aptos-move/cli/src/commands.rs`)

### Summary
The external report's root cause is a unit/value mismatch that a downstream consumer (the reserve payout) blindly trusted without verifying the exchange rate implied by the underlying data. The Aptos analog is structurally identical: the on-chain `PackageMetadata` struct carries `source`, `source_map`, and `source_digest` fields that describe what the published bytecode is supposed to be, but nothing in the publish path (`code::publish_package`, the native `request_publish[_with_allowed_deps]`, or `validate_publish_request` in `aptos_vm.rs`) actually checks that these fields correspond to the real compiled module bytes being stored. Only module *names* are cross-checked. The Aptos CLI's `VerifyPackage` command and `docs/cli-deploy.md` explicitly tell users/dependents to run `aptos move verify-package` to confirm "the on-chain copy matches" local source, but the implementation (`CachedPackageMetadata::verify`) only diffs metadata fields against each other and never fetches or compares the actual deployed bytecode.

### Finding Description
`PackageMetadata` and `ModuleMetadata` are defined with self-reported, publisher-controlled fields: [1](#0-0) 

`publish_package` computes only the module *name list* (`get_module_names`) to pass to the native publishing call; it never derives or checks anything from `pack.modules[i].source` / `source_map` / `source_digest`: [2](#0-1) 

On the native/VM side, `validate_publish_request` in `aptos_vm.rs` cross-checks module *names* against `expected_modules`, dependency addresses/names against `allowed_deps`, and calls `verify_module_metadata_for_module_publishing` (which validates Move-level annotations like resource groups/events) — none of which touch the `source`/`source_map`/`source_digest` fields at all: [3](#0-2) 

Consequently, the `source`, `source_map`, and `source_digest` fields stored in `PackageRegistry` are pure metadata with no cryptographic or verifier-enforced link to the actual bytecode bytes in the same transaction. A publisher can submit any `code: vector<vector<u8>>` alongside any `PackageMetadata` as long as module names line up; the Move VM will not detect a mismatch between the claimed source and the real logic.

The CLI's dependency-safety tool relies on exactly these unverified fields. `VerifyPackage::execute` fetches the on-chain `PackageMetadata` (explicitly with `with_bytecode = false`, i.e. it never downloads the real `.mv` bytes) and calls `package.verify(&compiled_metadata)`: [4](#0-3) 

`verify()` only performs field-by-field equality checks between the locally-built metadata and the on-chain metadata (name, deps, `modules` i.e. name+source+source_map, manifest, upgrade_policy, extension, `source_digest`) — it never compares the actual bytecode: [5](#0-4) 

The documentation tells users this command is the way to confirm "the on-chain copy matches" local source, and the framework's own dependency-security guidance recommends relying on exactly this kind of verification before depending on an upgradeable package: [6](#0-5) [7](#0-6) 

Because `source_digest`/`source`/`source_map` are self-reported and unchecked against bytecode by the protocol, a malicious or compromised package owner (of a `compatible`-policy package that others depend on) can:
1. Publish an initial version with benign source/bytecode that a user reviews and "verifies" via `verify-package`.
2. Later republish (upgrade) reusing the *exact same* `PackageMetadata` blob (same `source`, `source_map`, `source_digest`, same module names) while substituting a different, malicious `code` bundle that still passes the Move bytecode compatibility check (since `public(friend)`/private internals and non-public logic can change arbitrarily under the `compatible` policy) — or even bypass compatibility by using an `arbitrary`-adjacent trick with private functions.
3. Anyone who runs `aptos move verify-package` against this address will see "Successfully verified source of package" because the metadata still matches, even though the actual executing bytecode logic differs from the reviewed source.

This exactly mirrors the report's pattern: a downstream trust boundary (`VaderReserve`/CLI verifier) consumes a value (VADER amount / metadata fields) that was computed/declared under a different semantic domain than what is actually enforced (USDV loss / real bytecode), with no on-chain or tool-side reconciliation.

### Impact Explanation
This breaks a documented, security-relevant code-safety invariant: the ability to trust "verified" on-chain source as a proxy for actual bytecode behavior before depending on or interacting with a package. Since Aptos explicitly recommends this workflow for assessing `compatible`-policy dependencies (which are common and even used for the framework itself, per `is_policy_exempted_address`), a false-positive "verified" result can lead users/auditors/protocols to trust and integrate with malicious upgraded code, believing it matches previously-reviewed source. This is a code-safety/verification-bypass issue in the publish/verification pipeline, not a UI cosmetic bug — it undermines the integrity guarantee the compatibility/upgrade-policy model is supposed to provide to dependents.

### Likelihood Explanation
High likelihood of exploitation feasibility: any account owner with a `compatible` (non-immutable) package can trivially reuse an old metadata blob while swapping in different bytecode of the same module names, since nothing enforces the source-to-bytecode link. The `VerifyPackage` command is a first-class, documented CLI feature that downstream consumers are explicitly told to run, so the misplaced trust is a realistic and repeatable operational failure mode, not a contrived edge case.

### Recommendation
- On-chain: consider deriving/checking a binding between `ModuleMetadata.source`/`source_map` (or a hash of the actual compiled module bytes) and the bytecode being published in the same `publish_package` call, or at minimum have the framework compute and store a bytecode digest that the CLI verifier can check instead of relying purely on publisher-supplied `source_digest`.
- CLI: make `VerifyPackage` fetch actual on-chain bytecode (`with_bytecode = true`) and compare it byte-for-byte (or via hash) against the locally compiled modules, in addition to the existing metadata-field comparison in `CachedPackageMetadata::verify`.
- Documentation: until bytecode verification exists, `cli-deploy.md`/`modules-and-packages.md` should explicitly warn that `verify-package` only checks self-reported metadata fields, not actual bytecode equivalence, mirroring the honesty already present in `verify_framework_deployment.rs`'s TODO comment.

### Proof of Concept
1. Publisher `P` publishes package `X` at address `A` with `upgrade_policy = compatible`, honest module `m.move`, and metadata `M1` (containing `source`, `source_map`, `source_digest` computed from the honest source).
2. A dependent runs `aptos move verify-package --account A` — builds `m.move` locally, gets metadata `M1'` equal to `M1`, calls `package.verify(&M1')`, which succeeds ("Successfully verified source of package").
3. `P` later calls `code::publish_package_txn(owner, metadata_serialized = M1_bytes, code = [malicious_bytecode_for_m])`, where `malicious_bytecode_for_m` still declares module name `m`, and is Move-compatible per `check_upgradability`/native `compatibility.check` (e.g., changes only internal/private logic, which compatibility checks do not constrain).
4. On-chain, `validate_publish_request` only checks module names against `expected_modules` and dependency addresses against `allowed_deps` — it never inspects `M1.modules[0].source`/`source_map` against the new bytecode, so the transaction succeeds.
5. The dependent (or anyone) re-runs `aptos move verify-package --account A`; since the on-chain `PackageMetadata` is still `M1` (unchanged, matching the honest local source), `verify()` again reports success, even though the actually-executing module bytecode at `A::m` is the malicious version from step 3.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }

### Security considerations for dependencies

applications that depend on the upgraded code. These effects can come from bugs,
but they can also be the result of malicious upgrades. For example,
an upgraded dependency can suddenly make all functions abort, breaking the
operation of your Move code. Alternatively, an upgraded dependency can make
