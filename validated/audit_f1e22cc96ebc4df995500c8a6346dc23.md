### Title
Graduated liquidation curve exponent formula truncates fractional exponents, potentially over- or under-penalizing borrowers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` computes `factor^(exp/BPS)` for graduated liquidation penalties, but implements this using integer (floor) division on the exponent itself rather than a fractional power, which is structurally the same class of error as the PoolTogether report: a formula involving `pow`/exponent scaling that silently drops a component of the exponent, producing a numeric result systematically different from the documented/intended value.

### Finding Description
The function is: [1](#0-0) 

```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS)))))
```

`factor` is a BPS-scaled value in `[0, BPS]` representing the liquidation progress ratio, and `exp` is meant to represent a BPS-scaled exponent (alpha), e.g. `exp = 15000` should mean `alpha = 1.5`. When `exp > BPS`, the code computes `n = exp / BPS` using **integer division**, then evaluates `factor^n / BPS^(n-1)`. This is only mathematically equivalent to `factor_real^(exp/BPS) * BPS` when `exp/BPS` is an exact integer. Any fractional part of the intended exponent (e.g., alpha = 1.5, 2.25, etc.) is silently truncated to the next-lower integer, exactly analogous to how the PoolTogether `_numberOfPrizesForIndex` formula silently dropped intermediate terms from a multi-term exponential formula, causing the calculated value to permanently and systematically diverge from the documented formula.

### Impact Explanation
`calc-liq-factor-exp`'s output feeds `calc-liq-factor-bound`, which sets `liq-penalty`, which is then used in `calc-liq-collateral-repay` to determine how much collateral (with liquidator bonus) is seized during liquidation: [2](#0-1) 

Since `factor <= BPS` (i.e., the real-valued base is `<=1`), truncating the exponent downward (using `floor(alpha)` instead of the true fractional `alpha`) always produces a **larger** `factor^n` than the mathematically correct `factor^alpha` whenever `alpha` has a non-zero fractional part greater than its floor. A larger computed `liq-factor` inflates `liq-penalty`, which inflates the collateral seized from the borrower and paid to the liquidator beyond the protocol's intended graduated curve — a direct mispricing of collateral seizure that benefits liquidators at the expense of liquidated borrowers.

### Likelihood Explanation
I could not confirm within the available tool budget whether the `exp` (alpha) parameter configured for egroups in `v0-egroup.clar` / `v0-init.clar` is ever set to a non-integer multiple of `BPS` (e.g., 1.5x, 2.25x) — this is essential to know whether the truncation bug is actually triggered in production or is a latent/theoretical defect that never manifests because all configured curve exponents happen to be whole-number multiples of `BPS`. Without being able to inspect the actual deployed/configured `LIQ-CURVE`-type values for exponent, I cannot assert with confidence that this is an actively reachable, exploitable miscalculation versus a dead code path.

### Recommendation
Verify what exponent values are actually configured for liquidation curves across egroups. If any configured `exp` value is not an exact multiple of `BPS`, the formula in `calc-liq-factor-exp` needs to be corrected to properly support fractional exponents (e.g., via a fixed-point exponentiation routine), rather than truncating via integer division on `exp / BPS`.

### Proof of Concept
Given `factor = 5000` (0.5, BPS = 10000) and an intended `alpha = 1.5` (`exp = 15000`):
- Correct value: `0.5^1.5 ≈ 0.3536` → BPS-scaled ≈ `3536`.
- Code's computed value: `n = exp / BPS = 15000 / 10000 = 1` (integer division) → `factor^1 / BPS^0 = 5000` (i.e., no reduction applied at all — equivalent to `alpha = 1` instead of `1.5`).

This is a ~41% inflation of the liquidation factor for this example, which propagates through `calc-liq-factor-bound` to over-inflate `liq-penalty` and the resulting collateral seized in `calc-liq-collateral-repay`.

---
**Caveat:** This analog is offered with moderate confidence only. I was unable to verify, within my remaining search budget, that the `exp` parameter is ever configured as a non-integer multiple of `BPS` in the actual egroup/proposal configuration files (`mainnet/contracts/registry/v0-egroup.clar`, `mainnet/contracts/proposals/mainnet/v0-init.clar`). If all deployed exponents are whole-number multiples of `BPS`, this finding would not be practically exploitable and should be treated as a latent/theoretical defect rather than a live vulnerability.
