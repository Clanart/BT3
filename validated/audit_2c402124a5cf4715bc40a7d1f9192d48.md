### Title
Unbounded quadratic/cubic-complexity dependency resolution when cancelling an attacker-crafted Offer causes wallet transaction-processing halt - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` in `chia/wallet/trading/offer.py` resolve coin-announcement dependencies inside an offer's `SpendBundle` using nested Python loops with no CLVM-cost accounting and no bound on iteration count. A malicious offer counterparty can construct an offer whose coin spends create a long chain of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` dependencies, driving this dependency-resolution algorithm into worst-case polynomial blowup when the victim's wallet processes cancellation for that trade. This mirrors the Django `strip_tags()` CVE-2024-53907 bug class: unbounded CPU consumption from adversarial input structure processed outside any cost/complexity limit.

### Finding Description
`detect_dependent_coin()` is a triple-nested loop over `names × deps[name] × announcement_dict.items()`: [1](#0-0) 

It is invoked repeatedly inside `get_cancellation_coins()`, which builds `dependencies`/`announcements` dictionaries from every non-ephemeral coin spend in the offer bundle (each coin's `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions are extracted by fully re-running each puzzle with `INFINITE_COST`), then drives an outer `while True` loop that calls `detect_dependent_coin` again and again, followed by an inner `while True` loop that scans `dependencies.items()` against the removed announcement set: [2](#0-1) 

None of this dependency-graph resolution is bounded by CLVM cost, block cost, or any size cap comparable to the mempool's `TOO_MANY_ANNOUNCEMENTS` limit that is enforced elsewhere for on-chain conditions (visible in `chia/_tests/core/full_node/test_conditions.py` tests for the 1024-per-spend announcement cap). Coin-spend counts and announcement counts inside an offer are only limited by an aggregate `MAX_BLOCK_COST_CLVM` check in `Offer.__post_init__` (used just for `_additions`/`_hints` computation, not for `get_cancellation_coins`): [3](#0-2) 

An attacker can therefore pack many coin spends (each cheap, well under `MAX_BLOCK_COST_CLVM`) that create long assert/create announcement dependency chains between each other. Because `detect_dependent_coin` restarts its full triple-nested scan from the beginning of the (slowly shrinking) `names` list on every iteration of the outer `while True` in `get_cancellation_coins`, and the inner cleanup loop is itself another nested scan over all remaining dependencies/announcements per removal step, the overall work is at least quadratic and can be driven towards cubic in the number of chained coins, with no circuit breaker.

### Impact Explanation
This is a spend-triggered transaction-processing halt on the wallet side: if a victim's wallet accepts or is asked to build a cancellation transaction (`trade_manager.py` calls `get_cancellation_coins`) for an attacker-supplied offer with a crafted dependency chain, the wallet's single-threaded call into `get_cancellation_coins()` can consume disproportionate CPU/time relative to the small size of the offer, stalling wallet RPC processing (and, depending on concurrency model, other wallet operations) — the same class of algorithmic-complexity denial of service as the Django advisory, just realized in Chialisp/Python coin-announcement dependency graph resolution instead of HTML entity parsing.

### Likelihood Explanation
Likelihood is moderate: constructing such an offer requires only standard spend-bundle/puzzle construction skills (no privileged access, no malicious peer/node behavior), and offers are explicitly a data type designed to be exchanged with untrusted counterparties. However, the attack requires the victim to actually invoke `get_cancellation_coins()` on the attacker's offer (i.e., accept the offer into a trade and later attempt a cancellation flow), which narrows the exploitation window compared to a bug hit on every offer parse.

### Recommendation
Bound the dependency-resolution work in `get_cancellation_coins()`/`detect_dependent_coin()`: cap the number of coin spends/announcements considered, use indexed lookup structures (e.g., a reverse map from announcement to producing coin) to avoid O(n) scans inside the loops, and/or enforce a per-offer conditions/announcement cap analogous to the on-chain `TOO_MANY_ANNOUNCEMENTS` limit before entering this algorithm.

### Proof of Concept
I was unable to fully construct and time an end-to-end proof-of-concept spend bundle within this analysis (no code execution/tooling access was available to me in this session). A concrete PoC would need to: (1) build N coin spends each emitting one `CREATE_COIN_ANNOUNCEMENT` and one `ASSERT_COIN_ANNOUNCEMENT` referencing the next coin in a chain, (2) wrap them into an `Offer`/`WalletSpendBundle`, and (3) call `Offer.get_cancellation_coins()` while measuring wall-clock time growth as N increases, to empirically confirm super-linear scaling of `detect_dependent_coin`'s repeated triple-nested scans. This would need to be validated experimentally (e.g., by a Devin session with code execution) before treating the complexity/DoS claim as fully proven rather than root-cause-supported.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

```python
    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
