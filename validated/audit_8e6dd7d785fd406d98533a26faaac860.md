Based on my investigation, the strongest local analog to the reported bug class (an attacker-controlled input reaching state/validation logic whose guard has a gap, causing unintended and unsafe behavior downstream) is the **branch-name validation gap in the `x-github-client://openRepo` deep-link handler**, which forwards an insufficiently-sanitized, attacker-controlled string into a `git checkout` invocation.

### Title
Insufficient validation of attacker-controlled `branch` parameter in `x-github-client://openRepo` deep links allows git argument injection via leading-dash branch names - (File: `app/src/lib/sanitize-ref-name.ts`, `app/src/lib/parse-app-url.ts`, `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
GitHub Desktop registers OS-level custom protocol handlers (`x-github-client`, `github-mac`, `github-windows`) that any web page or link can invoke without user confirmation beyond the OS "open in Desktop" prompt [1](#0-0) . The `openRepo` action accepts a `branch` query parameter that is validated only against `testForInvalidChars`, a regex that rejects control characters and Git ref-format special characters but does **not** reject a leading `-`/`+` [2](#0-1) . This validated-but-not-fully-sanitized branch string then flows into `openBranchNameFromUrl`, which fetches the remote and calls `checkoutLocalBranch(repository, branchName)` directly [3](#0-2) .

### Finding Description
`parseAppURL` builds an `IOpenRepositoryFromURLAction` from a fully attacker-controlled URL. It validates `branch` with `testForInvalidChars(branch)` before accepting it [4](#0-3) . Compare this to the companion function `sanitizedRefName`, which explicitly strips a leading run of `-`/`+` characters via `.replace(/^[-\+]*/g, '')` — an acknowledgment elsewhere in the same file that leading dashes are dangerous and must be stripped [5](#0-4) . `testForInvalidChars`, however, only tests the same `invalidCharacterRegex` without that extra leading-dash strip/rejection, so a value like `--orphan=x` or `--pathspec-from-file=…` passes validation cleanly.

Once accepted, `dispatchURLAction` routes to `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)`, which fetches the remote and calls `this.checkoutLocalBranch(repository, branchName)` with the raw, unescaped string [3](#0-2) . This is the exact broken invariant analogous to the report: a guard exists ("filter attacker input before it reaches a sensitive operation") but the guard's coverage is incomplete for one specific class of dangerous value (leading-dash tokens), causing the downstream sensitive call (a `git checkout` invocation from `app/src/lib/git/checkout.ts`) to potentially receive that value as a flag rather than a ref name — i.e., Git argument/option injection instead of a benign branch-name lookup.

Note: I was not able to inspect `app/src/lib/git/checkout.ts` in this session to confirm whether the branch string is passed after a `--` separator (which would neutralize the injection) or as a bare positional argument to `git checkout`. This is the critical remaining verification step — if `checkout.ts` does not insert an explicit `--` before the branch argument, this is directly exploitable exactly as described; if it does, the guard gap is real but not reachable through this path.

### Impact Explanation
If the branch argument is passed to `git checkout` without an explicit `--` separator, an attacker who gets a user to click one crafted `x-github-client://openRepo/<url>?branch=<hostile-flag>` link (e.g. embedded in a website, README, or chat message) can cause GitHub Desktop to run `git checkout` with attacker-chosen flags in the context of a repository the app just cloned/fetched on the attacker's behalf. Depending on the exact flag, outcomes range from working-directory corruption (e.g. forcing an orphan branch, silently altering what gets checked out and thus what the user later commits/pushes) to reading arbitrary local files as a pathspec source. This matches the "attacker controls a deep link the user clicks" and "silent corruption of what the user commits or pushes" categories in the valid-impact scope.

### Likelihood Explanation
The protocol handlers are globally registered and reachable from any link a user clicks, browser page, or IPC-triggered `second-instance`/`open-url` event [6](#0-5) . The `parse-app-url-test.ts` suite exercises `branch` validation but only tests characters that are already blocked by `invalidCharacterRegex` (e.g. `<>`), never a leading-dash payload [7](#0-6) , which is consistent with the gap being untested and unnoticed. Exploitability strictly depends on the unverified `checkout.ts` argument construction noted above.

### Recommendation
Align `testForInvalidChars` with `sanitizedRefName`'s handling of leading `-`/`+`: either reject (return `true`) when `/^[-+]/`.test(name) is true, or reuse `sanitizedRefName` and compare against the original to detect mutation. Additionally, in `app/src/lib/git/checkout.ts`, ensure branch/ref arguments derived from any external or URL-provided source are always passed after an explicit `--` separator to git, as defense in depth against argument injection regardless of upstream validation.

### Proof of Concept
1. Attacker hosts/sends a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--orphan%3Dpwned`.
2. User clicks it; OS invokes GitHub Desktop with this URL, which `handleAppURL`/`parseAppURL` parses. `testForInvalidChars('--orphan=pwned')` returns `false` (no blocked characters), so the action is accepted with `branch: '--orphan=pwned'` [4](#0-3) .
3. `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` clones/opens the repo, fetches, and calls `checkoutLocalBranch(repository, '--orphan=pwned')` [3](#0-2) .
4. **Unverified step**: if the underlying `git` invocation in `checkout.ts` places this string as a bare argument (no `--` separator), the `git checkout` process receives `--orphan=pwned` as a flag instead of a ref, producing attacker-controlled repository state changes rather than a checkout failure or safe no-op.

This step 4 needs confirmation against `app/src/lib/git/checkout.ts`, which I could not retrieve before running out of tool budget. I recommend a follow-up session start explicitly to read `app/src/lib/git/checkout.ts` and confirm the argument array construction before treating this as a confirmed, immediately exploitable issue.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
