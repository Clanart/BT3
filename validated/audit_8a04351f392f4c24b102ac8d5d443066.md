## Title
Unauthenticated OP_RETURN operator attribution in `Payout` transaction lets anyone frame an operator for reimbursement it never funded - ([File: core/src/builder/transaction/operator_reimburse.rs])

## Summary
`create_payout_txhandler` builds the `Payout` transaction using a `SIGHASH_SINGLE | ANYONECANPAY` user signature that only commits to the user's withdrawal output (index 0). The OP_RETURN output carrying the `operator_xonly_pk` — the field that the entire reimbursement pipeline (`PayoutCheckerTask`, `handle_finalized_payout`, `validate_payer_is_operator`) trusts to decide *which operator gets reimbursed for fronting a withdrawal* — is completely outside the scope of the user's signature and is not bound to whoever actually supplies/broadcasts the transaction. [1](#0-0) 

## Finding Description
`create_payout_txhandler` constructs:
- Input 0: the user's withdrawal UTXO, spent via key-spend with the user's `taproot::Signature`.
- Output 0: the user payout (this is what `SIGHASH_SINGLE|ANYONECANPAY` binds).
- Output 1: anchor.
- Output 2: `op_return_txout(operator_xonly_pk)` — an unsigned, caller-supplied field. [1](#0-0) 

Because the sighash type is `SIGHASH_SINGLE | ANYONECANPAY`, the user's signature only commits to the input it spends and the output at the same index (output 0). It says nothing about output 2's OP_RETURN content, and `ANYONECANPAY` explicitly allows arbitrary other inputs/outputs to be added by whoever assembles the final transaction. This matches the "no order/order-field validation" root cause pattern of the 0x-adaptor bug: a value that determines a custody/attribution outcome (there: `recipient`; here: `operator_xonly_pk`) is taken directly from caller-supplied data with no cryptographic binding to the party that is supposed to own it.

Downstream, this field is trusted as ground truth for "who paid the user":
- `update_finalized_payouts` parses the OP_RETURN from the on-chain `Payout` tx and stores it as `payout_payer_operator_xonly_pk` [2](#0-1) .
- `PayoutCheckerTask::run_once` looks up "the first unhandled payout by **my own** `operator_xonly_pk`" and, if found, unconditionally starts the reimbursement flow (`handle_finalized_payout`) for that withdrawal [3](#0-2) .
- `handle_finalized_payout` allocates a kickoff connector and drives the operator into sending a `Kickoff`/`Reimburse` sequence to reclaim `bridge_amount` from the vault via its own collateral/round machinery [4](#0-3) .
- The only later cross-check (`validate_payer_is_operator`, `is_kickoff_malicious`) merely re-derives the same untrusted OP_RETURN value and compares it to itself/`kickoff_data.operator_xonly_pk` — it never verifies that the named operator actually funded output 0 [5](#0-4) [6](#0-5) .

Equality that should hold but is broken: `operator credited via OP_RETURN == operator whose funds actually paid output 0`. Nothing enforces this equality; the OP_RETURN is attacker-controlled metadata attached to a transaction whose funding party can be anyone with access to the user's `(input_outpoint, in_signature, output_script_pubkey, output_amount)` tuple.

## Impact Explanation
An unprivileged party who can construct a valid `Payout` transaction for a pending withdrawal (fronting the user's payout amount out of pocket, or racing/replacing a legitimate operator's payout via the `ANYONECANPAY` malleability) can set the OP_RETURN operator pubkey to any operator of their choosing — including a completely uninvolved, honest operator that never saw or approved this withdrawal. That operator's `PayoutCheckerTask` will then autonomously treat the withdrawal as one it fronted and drive its own kickoff/reimburse machinery to withdraw `bridge_amount` from the vault's collateral for a payout it never made — i.e. "the operator credited versus the party that paid" binding is broken. This directly maps to the Critical impact class: an operator reimbursed for a payout it never funded, at the expense of vault/collateral funds, while the true fronting party (the attacker) can be a completely different, possibly self-controlled address that pocketed nothing extra — or worse, the attacker never truly funds the user at all if they can win a race against the legitimate operator's own broadcast by replacing the OP_RETURN via `ANYONECANPAY` before the legitimate one confirms.

Whether this is exploitable end-to-end also depends on whether the raw `in_signature`/withdrawal parameters are practically obtainable by a third party (e.g., visible on the public Citrea withdrawal registration transaction, or observable in the mempool once any operator broadcasts a `Payout` tx). I could not fully confirm from the indexed code whether the `in_signature` is embedded in the public Citrea `safeWithdraw`/`withdraw` contract call data (which would make it trivially public) — the relevant Citrea contract call sites (`get_citrea_safe_withdraw_params`, `contract.withdraw(...)`) were only partially visible in the index. If the signature is public via Citrea, the attack requires no privileged access at all; if it is only ever transmitted privately to the specific operator that should front it, the primary exploit path narrows to mempool replacement of an already-broadcast (unconfirmed) `Payout` transaction, which is still a low-cost, unprivileged action given the `ANYONECANPAY` input flag.

## Likelihood Explanation
Given `ANYONECANPAY|SINGLE`, any party who obtains the signed withdrawal tuple can trivially build an alternative `Payout` transaction that pays the same user output but redirects OP_RETURN attribution — this requires no cryptography breaking, no operator/verifier role, and no majority collusion. The main uncertainty is *how* the attacker obtains the tuple; assuming any plausible public/mempool visibility, likelihood is high.

## Recommendation
Bind the OP_RETURN operator attribution cryptographically to the operator, e.g. by:
- Widening the payout signature's sighash to `SIGHASH_ALL` (or otherwise cover the OP_RETURN output) so the *user* commits to a specific operator's pubkey when authorizing the fronting operator, or
- Requiring an additional operator-signed commitment (separate from the user's withdrawal signature) that must match the OP_RETURN content before `update_finalized_payouts`/`PayoutCheckerTask` treats a payout as "mine to reimburse", or
- Having verifiers validate that the named operator in the OP_RETURN actually controls the funding input(s) of the `Payout` transaction (e.g., require the operator's own signature on an additional input) before recording `payout_payer_operator_xonly_pk`.

## Proof of Concept
1. User withdraws on Citrea and signs `(input_outpoint, output_script_pubkey, output_amount)` with `SIGHASH_SINGLE|ANYONECANPAY`, intending operator A to front the payout.
2. Before operator A's `Payout` tx confirms (or if the signed tuple is otherwise obtainable), an attacker crafts their own `Payout` transaction reusing the same signed input/output-0, but sets the OP_RETURN (output 2) to operator B's `xonly_pk` instead of A's, per `create_payout_txhandler` [1](#0-0) .
3. Attacker broadcasts/replaces with this transaction (using `ANYONECANPAY` to add their own fee-paying input if needed) so it confirms first.
4. Verifier's `update_finalized_payouts` records `payout_payer_operator_xonly_pk = B` for this withdrawal [2](#0-1) .
5. Operator B's `PayoutCheckerTask` picks up the unhandled payout under its own key and calls `handle_finalized_payout`, starting the kickoff/reimburse sequence to reclaim `bridge_amount` from the vault, even though B never funded the withdrawal [3](#0-2) [4](#0-3) .

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn handle_finalized_payout<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",
                    current_round_index, round_idx, deposit_outpoint
                ).into());
            }
            tracing::info!(
                "Operator: Starting next round to be able to get reimbursement for the payout"
            );
            // start the next round to be able to get reimbursement for the payout
            self.end_round(dbtx).await?;
        }

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
