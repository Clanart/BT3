Based on my investigation, I found a genuine security-relevant mechanism in the submodule handling code, but I was unable to fully verify all call sites before running out of tool budget. I'll present what is solidly confirmed and flag what remains unverified.

### Title
Desktop deliberately re-enables `protocol.file.allow=always` for submodule updates during checkout, overriding Git's CVE-2022-39253 hardening - (File: `app/src/lib/git/submodule.ts`, `app/src/lib/git/checkout.ts`)

### Summary
Modern Git (≥2.38.1) blocks `file://` submodule URLs by default (`protocol.file.allow=user`) specifically to stop a known attack class (CVE-2022-39253) where a malicious repository's `.gitmodules` points a submodule at a local path, causing `git submodule update --init --recursive` to silently "clone" arbitrary local files/directories into the working tree. Desktop's `updateSubmodulesAfterOperation` explicitly reintroduces this disabled protocol via an `allowFileProtocol` flag that, when true, prepends `-c protocol.file.allow=always` to the submodule update invocation. [1](#0-0) 

### Finding Description
`updateSubmodulesAfterOperation` is the single choke point Desktop uses after `checkout`/`clone`/`pull` operations to run `git submodule update --init --recursive`, and it accepts an `allowFileProtocol` boolean that toggles Git's own safety gate for `file://` submodule sources: [2](#0-1) 

`checkoutBranch` and `checkoutCommit` both thread an `allowFileProtocol` parameter (defaulting to `false`) straight through to this function without any independent validation of whether the branch/commit being checked out originates from a trusted source: [3](#0-2) [4](#0-3) 

This mirrors the structure of the original report's broken invariant: a security-relevant guard (here, Git's built-in `protocol.file.allow` block) exists but is explicitly overridable by a boolean flag threaded through call sites, and the correctness of the whole system now depends entirely on every caller of `checkoutBranch`/`checkoutCommit` correctly deciding when `true` is safe to pass — analogous to how `approve()` depended on every ERC20 entry point remembering to call `transferSanity()`.

**Unverified/uncertain aspect:** I located 8 call sites of `checkoutBranch`/`checkoutCommit` in `app/src/lib/stores/app-store.ts` and additional call sites in UI components (`branches-container.tsx`, `confirm-checkout-commit.tsx`, `compare.tsx`, `stash-and-switch-branch-dialog.tsx`, `overwrite-stashed-changes-dialog.tsx`), but I was not able to inspect all of them within the available tool budget to confirm the exact condition under which `allowFileProtocol=true` is passed (e.g., whether it's gated on the repository being the user's own vs. checking out a branch/commit that originated from a fetched fork or PR ref, whose `.gitmodules` content is attacker-controlled). [5](#0-4) 

### Impact Explanation
If `allowFileProtocol=true` is reachable for a checkout of a ref whose tree (including `.gitmodules`) is attacker-influenced (e.g., a branch fetched from a fork, or a PR checkout), the attacker can point a submodule URL at a `file://` path (including relative paths that escape to sibling directories, or absolute paths like `/etc` or the user's home directory) and have Desktop "clone" that local content into the working tree as a tracked submodule — silently corrupting what the user commits/pushes and potentially exfiltrating local file contents that get added into version control. This is precisely the class of attack Git 2.38.1 patched (CVE-2022-39253) by defaulting `protocol.file.allow` to disallow this.

### Likelihood Explanation
Likelihood depends on confirming that `allowFileProtocol=true` is actually passed for checkouts of untrusted refs (e.g., viewing/checking out a fork's pull request) rather than only for trusted, locally-authored branches. This could not be confirmed with certainty from the files inspected, so likelihood is Uncertain pending review of the `app-store.ts` call sites.

### Recommendation
Audit every call site that passes `allowFileProtocol=true` into `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` and ensure it is never enabled when checking out a ref whose content (specifically `.gitmodules`) is not fully controlled/trusted by the local user (e.g., forked PR branches, remotely fetched refs). Prefer leaving Git's default `protocol.file.allow` protection intact for any checkout path reachable from untrusted repository content.

### Proof of Concept
Not constructed — a concrete PoC requires confirming a reachable call path where `allowFileProtocol=true` is passed for an untrusted ref, which I could not verify within the available tool budget. If such a call site exists, the PoC would be: clone/fetch a hostile fork containing a branch whose `.gitmodules` defines a submodule with `url = file:///Users/<victim>/.ssh`, then have the victim check out that branch through the vulnerable call path, causing the local `.ssh` directory to be "cloned" into the submodule's working tree path.

  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false

  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(

    title,
    branch.name,

    repository,
    currentRemote,

          1,
          progressCallback
        )
