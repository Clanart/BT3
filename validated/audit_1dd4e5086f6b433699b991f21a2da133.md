## Analysis

The audit's underlying pattern — address-type parameters (URLs) accepted and consumed by privileged operations without validating their shape/scheme — has a direct analog in how GitHub Desktop resolves and adds git remotes for pull-request checkouts.

### Title
Unvalidated `clone_url` from GitHub API PR object is used as a git remote URL for `fetch` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user checks out a pull request (including via the `open-repository-from-url` deep-link path), Desktop takes `pullRequest.head.repo.clone_url` — a string field returned by the GitHub API — and passes it unvalidated into `addRemote()` and then `_fetchRemote()`. [1](#0-0) [2](#0-1) 

### Finding Description
`_findPullRequestBranch()` looks for an existing remote matching `headCloneUrl` and, if none is found, calls `addRemote(repository, forkRemoteName, headCloneUrl)` followed by `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)`. [3](#0-2) [4](#0-3) 

There is no check anywhere in this path that `headCloneUrl` is an `https://` or `ssh://` GitHub-style URL before it is registered as a git remote and fetched — the exact class of gap the report calls out ("functions lack complete validation for input parameters, specifically for address-type parameters"). The `open-repository-from-url` deep-link handler feeds the same unvalidated `url` string into `openPullRequestFromUrl`, which calls `appStore.fetchPullRequest(url, pr)` and then reaches this same `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`/`fetch` chain using `pullRequest.head.repo.clone_url` taken straight from the API response. [5](#0-4) 

By contrast, other parameters accepted from the same deep link (`branch`, `pr`) are explicitly regex-validated (`testForInvalidChars`, `/^\d+$/`) before use, and the `filepath` parameter is defended with an `isAbsolute()` check plus `resolveWithin()` containment. [6](#0-5) [7](#0-6) 
The `url`/`clone_url` value that is ultimately handed to git as a remote receives no equivalent scheme/format validation anywhere in this call chain.

### Impact Explanation
`git fetch`/`git remote add` treat the remote URL as a transport specification. Git supports transport helpers invoked via URL scheme (e.g. `ext::`, `fd::`, or exotic `ssh` option-injection forms) that can result in local command execution if an unvalidated, attacker-influenced string reaches the git CLI as a remote URL. Because this code path never restricts the accepted scheme/format of `headCloneUrl`/`url` before calling `addRemote` and fetching it, any component able to influence that string — a manipulated GitHub API response (e.g. from a compromised or MITM'd GitHub Enterprise Server endpoint), or the raw `url` query parameter of an `x-github-client://openrepo/...` deep link a user is convinced to click — has a path to having Desktop execute `git remote add` and `git fetch` against an attacker-chosen string, unlike the sibling `branch`/`pr`/`filepath` parameters, which are all explicitly validated.

### Likelihood Explanation
Exploitation requires the attacker to control the content of the `clone_url`/`url` value that flows into this specific code path — either through a crafted deep link the user clicks (a supported "Valid Impact" vector) or a tampered GitHub API/proxy response. I was not able to fully confirm, within the available search iterations, whether `addRemote()` in `app/src/lib/git/remote.ts` or Desktop's API client (`app/src/lib/api.ts`) perform additional scheme/host restrictions further down the stack before invoking the underlying `git` binary, nor whether git's own remote-helper allowlisting (`protocol.allow`) is configured elsewhere in `app/src/lib/git/environment.ts` to block unsafe transports. This limits confidence in the exploitability of this specific path and should be verified directly against `app/src/lib/git/remote.ts` (`addRemote`) and the git invocation options in `app/src/lib/git/core.ts`/`environment.ts`.

### Recommendation
- Validate `headCloneUrl`/`url` against the same `remote-parsing.ts` regexes (or an explicit protocol allowlist of `https`/`ssh`) before calling `addRemote()` or performing any fetch, mirroring the existing validation already applied to `branch` and `pr`.
- Confirm `git` is invoked with `-c protocol.ext.allow=never` (and similarly for other unsafe transport helpers) globally in `app/src/lib/git/environment.ts` as defense in depth.
- Apply the same scheme/format validation to the top-level `url` parameter parsed in `app/src/lib/parse-app-url.ts`, consistent with how `branch` is already sanitized there.

### Proof of Concept
Conceptual (pending confirmation of downstream `addRemote`/git invocation safeguards):
1. Trigger `openPullRequestFromUrl`/`_findPullRequestBranch` with a `headCloneUrl` value that is not a normal `https://`/`ssh://` GitHub URL, e.g. a git "ext" transport string.
2. If no scheme validation exists downstream, `addRemote(repository, forkRemoteName, headCloneUrl)` registers it and `_fetchRemote()` executes `git fetch` against it, which — absent a `protocol.allow` restriction — can invoke the transport helper specified in the URL. [8](#0-7) 

**Caveat:** This analog's real-world exploitability hinges on parts of the codebase (`app/src/lib/git/remote.ts` `addRemote`, and git transport hardening in `app/src/lib/git/environment.ts`) that I was unable to fully inspect before running out of tool-call budget. If those layers already enforce `protocol.allow=never` for risky transports or otherwise sanitize the URL, this finding would be downgraded to informational (defense-in-depth only) rather than exploitable.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )
