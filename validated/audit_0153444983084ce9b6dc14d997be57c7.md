### Title
Unpriced OP_RETURN data produces underfunded transactions that may become stuck - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends a caller-supplied OP_RETURN output but excludes it from every virtual-size and fee calculation. A data-bearing transaction can consequently be signed with a fee below both the requested rate and Bitcoin's minimum relay rate, leaving the transaction unbroadcast or unconfirmed while its inputs remain allocated to that spend attempt.

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of caller-controlled `data` and adds it to `tx_outs` as a zero-value OP_RETURN output. [1](#0-0) [2](#0-1) 

The initial fee estimate calls `calculate_weight_vbytes` with only `payments`, omitting the OP_RETURN output already placed in `tx_outs`. [3](#0-2) 

Inside `calculate_weight_vbytes`, the modeled transaction likewise constructs outputs solely from `payments`. [4](#0-3) 

The change-output path repeats the same omission by estimating `vbytes_with_change` from the input count, `payments`, and change output, while still ignoring `data`. [5](#0-4) 

The resulting `SignableTransaction` contains the unpriced OP_RETURN output, while `fee()` reports only input value minus all output values and does not detect that the requested rate was based on a smaller transaction. [6](#0-5) [7](#0-6) 

### Impact Explanation
An 80-byte OP_RETURN adds roughly 90 virtual bytes to the transaction, but contributes zero sats to `needed_fee`. For small Taproot transactions and a requested fee rate of 1 sat/vbyte, this can reduce the actual fee rate to approximately half of the intended rate. [8](#0-7) 

Bitcoin nodes can reject such a transaction under minimum-relay-fee policy even though the constructor accepted it, causing the signed spend to remain unconfirmed and the selected inputs to remain unavailable until a replacement transaction is coordinated and signed. [9](#0-8) 

This maps the reported failure mode to Serai: a transaction component is omitted from the recorded/accounted cost of a transfer, causing funds involved in the attempted transfer to become stuck rather than correctly delivered.

### Likelihood Explanation
The `data` argument is a public input to `SignableTransaction::new`, so any caller or upstream transaction flow that lets an untrusted party attach transaction data can trigger the condition. [10](#0-9) 

The issue is deterministic whenever an OP_RETURN is present; its practical effect is most likely at low requested fee rates, where the omitted output can push the completed transaction below the minimum relay threshold. [11](#0-10) 

### Recommendation
Build the final output list before fee estimation, including the OP_RETURN output, and calculate both the no-change and with-change weights from that complete transaction shape. After constructing the transaction, verify `fee() >= fee_per_vbyte * actual_vsize` and `fee() >= minimum_relay_fee(actual_vsize)`; otherwise return `TooLowFee` or recalculate the change amount using the final size. [12](#0-11) 

### Proof of Concept
Construct a transaction with one spendable input, one payment, no change, `fee_per_vbyte = 1`, and `data = Some(vec![0; 80])`, choosing the input amount as `payment + needed_fee`. [10](#0-9) 

```rust
let tx = SignableTransaction::new(
  vec![input],
  &[(payment_script, payment)],
  None,
  Some(vec![0; 80]),
  1,
)?;
```

`needed_fee` is calculated from a transaction containing only the payment output, while the returned transaction additionally contains the serialized OP_RETURN output. [13](#0-12) [14](#0-13) 

Because the input amount was selected to leave only `needed_fee`, `tx.fee()` remains the underestimated value even though the actual virtual size is larger by the OP_RETURN output's serialized size. [7](#0-6) 

The signed transaction therefore has a materially lower fee rate than requested and can fail relay policy despite passing the constructor's `TooLowFee` check. [9](#0-8)
