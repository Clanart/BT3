### Title
Path Traversal via Symlinks in `revealInFileManager` Allows Untrusted Repository Content to Point File-Manager/Editor Actions Outside the Repo - (`app/src/lib/app-shell.ts`)

### Summary
The GitHub Desktop analog of the "unchecked destination address used for a sensitive operation" bug class from the Tapioca report is the `revealInFileManager` helper. It builds a filesystem path from repository-relative file names that ultimately originate from a cloned/fetched repository's tree (e.g. conflict file paths, changed-file paths) using a plain `Path.join`, with **no** boundary/real-path validation, even though the codebase has a purpose-built guard (`resolveWithin`) for exactly this scenario and uses it elsewhere.

### Finding Description
`revealInFileManager` resolves an attacker-influenceable relative `path` against `repository.path` with a simple string join and passes the result straight to `shell.showItemInFolder`: [1](#0-0) 

Compare this to the sibling deep-link handler that performs the conceptually identical operation ("resolve an untrusted relative path against the repo root, then reveal it in the file manager") but does it safely, first rejecting absolute paths and then verifying the resolved path is still inside the repository via `resolveWithin`: [2](#0-1) 

`resolveWithin` is the codebase's dedicated defense against this exact issue: it calls `realpath()` on both the root and the resolved candidate and only accepts the result if the *real* (symlink-resolved) path is still nested under the *real* root: [3](#0-2) 

`revealInFileManager`, however, is invoked with paths taken directly from git-reported file lists — e.g. conflicted files enumerated during merge/rebase conflict resolution — without ever going through `resolveWithin`: [4](#0-3) 

Because `Path.join` performs pure string manipulation and never touches the filesystem, it does not detect the case where an intermediate path component is a symlink. Git fully supports committing symlinks (mode `120000`) as part of a tree, so a malicious/attacker-controlled repository can contain a tracked symlink such as `evil -> /` (or any absolute/relative target outside the repo). When Desktop subsequently reports a "changed" or "conflicted" path underneath that symlinked directory (e.g. `evil/some/file`), `Path.join(repository.path, 'evil/some/file')` yields a path that, once resolved by the OS through the symlink, points completely outside the repository. This is passed to `shell.showItemInFolder`/`shell.openPath`, which will happily reveal or open the out-of-repo target.

This mirrors the audited bug's broken invariant precisely: a value that should be validated to be "one of a known-good, trusted set of destinations" (here: "must resolve inside the repository working directory") is instead taken from attacker-controlled/untrusted state and used directly in a security-sensitive operation, while a correct guard for the identical primitive (`resolveWithin`) already exists in the same codebase and is applied at a sibling call site but not here.

### Impact Explanation
An attacker who gets a victim to clone/fetch a crafted repository (or open a PR/branch containing a crafted symlink plus a conflicting file under it) can cause GitHub Desktop's "Reveal in Finder/Explorer" action — reachable from the merge-conflict resolution UI — to open or reveal arbitrary files/directories outside the cloned repository, including sensitive user directories, SSH keys, or credential stores. Depending on OS shell behavior for `showItemInFolder`/`openPath` on the resolved target, this can also facilitate execution if the symlink points at an executable, since `openPath`-style APIs can launch files, not just reveal them.

### Likelihood Explanation
The primitive required — a cloned/fetched repository controlled by the attacker containing a tracked symlink — is exactly within the threat model of "attacker controls a cloned/fetched repository." No local access, admin rights, or social engineering beyond the normal act of cloning/opening a repository and encountering a conflict is required, matching the valid-impact criteria for this scan.

### Recommendation
Route `revealInFileManager` (and any other consumer of git-reported relative paths) through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` before calling into `shell.showItemInFolder`/`shell.openPath`, mirroring the pattern already used in `openRepositoryFromUrl`. Reject or refuse to reveal paths whose real (symlink-resolved) location falls outside the repository root.

### Proof of Concept
1. Attacker creates a repository containing a symlink `link -> /` (or any host path outside the repo) and commits it.
2. Attacker creates a divergent branch that introduces a merge conflict for a path underneath `link/`, e.g. `link/secret.txt`, and gets the victim to attempt to merge/rebase, surfacing the conflict in the Copilot conflicts dialog.
3. Victim clicks the "Reveal in Finder/Explorer" action for the conflicted item shown by `onOverflowMenuClick`: [4](#0-3) 
4. `revealInFileManager` joins `repository.path` with `link/secret.txt` and hands the result to `shell.showItemInFolder` without any real-path/boundary check, revealing a file outside the cloned repository's working directory: [1](#0-0)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
