## Finding

### Title
Deep-link branch name bypasses dash-prefix filtering used elsewhere, enabling git argument injection - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`GITHUB DESKTOP` validates a `branch` query-string value coming from an attacker-controlled `x-github-client://openRepo/...` deep link with `testForInvalidChars()`, a different (and weaker) filter than the one used for user-typed branch names (`sanitizedRefName()`). The deep-link value is passed on to git-branch operations without ever being run through the stricter filter, so a crafted link can smuggle a value that git's own argument parser will treat as a flag rather than a ref name — the same "derived value skips a check that exists elsewhere in the code but wasn't applied on this path" pattern described in the source report.

### Finding Description
`app/src/lib/parse-app-url.ts` parses the `branch` parameter of an `openRepo` deep link and only rejects it if `testForInvalidChars()` matches: [1](#0-0) 

`testForInvalidChars` is backed by the same regex used to *sanitize* manually-entered branch names, but that regex does not exclude a leading `-`/`+`: [2](#0-1) 

Contrast this with the dedicated stripping step, `.replace(/^[-\+]*/g, '')`, applied in `sanitizedRefName` (used by the UI's `RefNameTextBox`/create-branch flow) — this stripping is exactly what's missing on the deep-link path. The unit tests even document that this stripping is a required invariant for branch names ("does not allow name to start with minus"): [3](#0-2) 

The deep link's `branch` value, having only passed the weaker `testForInvalidChars` check, flows into `Dispatcher.openBranchNameFromUrl`, which checks out (and, if absent, will create) a local branch of that exact name: [4](#0-3) 

The underlying branch creation call builds the git argv with the untrusted name in a positional slot and with no `--` end-of-options separator: [5](#0-4) 

Because dugite invokes `git` via `execFile` (argv array, not a shell), this isn't shell injection — but git's own argument parser still treats any token beginning with `-`/`--` as an option regardless of its position in argv, unless a literal `--` separator precedes it. Since the branch name never passes through `sanitizedRefName`'s dash-stripping and `createBranch`/checkout call sites don't insert a `--` separator, a crafted deep link value like `--upload-pack=...`, `--template=...`, or other git-branch/checkout flags can be injected as an actual CLI flag to the underlying `git` invocation.

### Impact Explanation
This is an unprivileged, remotely-triggerable primitive: the user only has to click a link (`x-github-client://openRepo/<url>?branch=<payload>`), which Desktop's own protocol handler feeds straight into `parseAppURL`/`openBranchNameFromUrl` with no further sanitization: [6](#0-5) 

Argument injection into `git branch`/checkout invocations can corrupt what gets committed/checked out (e.g., forcing template directories, alternate object stores, or other option-driven behavior) without the user's knowledge — this matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as valid in the task's scope. Depending on which flags are reachable at each call site, the practical severity ranges from repository-state corruption to a stronger primitive if any invoked git flag can reference attacker-controlled paths/executables (git has historically had `--upload-pack`/`-c`-style option abuse in ext:: transport style; this report only demonstrates the guard gap, not a full weaponized RCE chain, since I could not fully trace every downstream call site in the available index).

### Likelihood Explanation
Likelihood is moderate-to-high for state corruption: the deep-link handler is registered as the default protocol client (`x-github-client`, plus legacy `github-mac`/`github-windows` protocols) and is reachable purely by getting a victim to click a link, with no local access or prior compromise needed. The specific validation gap (missing leading-dash filtering) is concretely demonstrable by comparing `parse-app-url.ts`'s regex use against `sanitizedRefName`'s explicit stripping and the dedicated unit test asserting that a leading `-` must be removed.

### Recommendation
Apply `sanitizedRefName()` (or an equivalent explicit rejection of leading `-`/`+`) to the `branch` value parsed in `parseAppURL`, in addition to (or instead of) `testForInvalidChars`. Additionally, harden the git wrapper call sites (`createBranch` in `app/src/lib/git/branch.ts`, and the checkout path invoked by `checkoutLocalBranch`) to always insert a literal `--` separator before ref-name arguments so that even a filter bypass cannot be interpreted as a flag by git.

### Proof of Concept
1. Register/observe that Desktop is the default handler for `x-github-client://`.
2. Send the victim a link such as:
   `x-github-client://openRepo/https://github.com/octocat/Hello-World?branch=--orphan`
   (or another `git branch`/checkout flag of the attacker's choosing that doesn't hit the `invalidCharacterRegex`).
3. `parseAppURL` accepts the value because `-`/leading dash is not in `invalidCharacterRegex`.
4. `Dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch` → `createBranch`/checkout git call executes with the attacker-supplied token in a flag-eligible position with no `--` separator, causing git to interpret it as an option rather than a branch name.

Note: I was unable to retrieve the exact source of `checkoutLocalBranch` within the tool budget available (only its call sites in `dispatcher.ts` were indexed), so the exact downstream git subcommand invoked when the branch doesn't exist locally could not be fully confirmed from local code alone; this should be verified in a live session before treating the impact as more than repository-state corruption.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

      return null
    }

    // ensure a fresh clone repository has it's in-memory state

export async function createBranch(
  repository: Repository,
  name: string,
  startPoint: string | null,
  noTrack?: boolean
): Promise<void> {
  const args =
    startPoint !== null ? ['branch', name, startPoint] : ['branch', name]

  // if we're branching directly from a remote branch, we don't want to track it
  // tracking it will make the rest of desktop think we want to push to that
  // remote branch's upstream (which would likely be the upstream of the fork)
  if (noTrack) {
    args.push('--no-track')
  }

  await git(args, repository.path, 'createBranch')
}
