## Title
Missing bounds validation on `reward.mintingamount` governance parameter permits unbounded native-token supply inflation via a single governance vote - (File: kaiax/gov/param.go)

### Summary
Unlike the TSD incident where DAO governance was used to inject a malicious `Mint` implementation that created 11.8B tokens, Kaia's on-chain governance parameter `reward.mintingamount` — which directly controls how many KAIA tokens are minted every block — has **no upper-bound or sanity-range validation**. Its `FormatChecker` is a no-op, so a single ratified vote can set the minting amount to an arbitrarily large value, and the block reward pipeline will faithfully mint and distribute that amount every block thereafter, unboundedly inflating the KAIA supply.

### Finding Description
The `RewardMintingAmount` parameter definition uses `noopFormatChecker`, which accepts any value that survives canonicalization, with no range or sanity check: [1](#0-0) 

The canonicalizer for this parameter, `bigIntCanonicalizer`, merely parses the input into a `*big.Int` without any bound, sign, or magnitude restriction: [2](#0-1) 

When a vote for `gov.RewardMintingAmount` reaches `checkConsistency` (the function responsible for validating votes against chain-state consistency), it falls into the catch-all branch that trivially returns `nil` — i.e., no additional validation is performed beyond the no-op format checker: [3](#0-2) 

Once ratified (via `header.Governance` in header governance, following the single-vote-per-epoch ratification flow described in the module docs), the parameter feeds directly into block reward computation. `RewardConfig.MintingAmount` is copied verbatim as the block's minting amount and distributed to the proposer/stakers/funds every block: [4](#0-3) 

The distributed amounts are then unconditionally credited to state balances in `FinalizeState`: [5](#0-4) 

Governance votes are cast via the public `governance_vote` RPC, and in `single` mode only the `governance.governingnode` account can have votes ratified — but crucially, ratification is a matter of chain state (the current designated governing node), which can itself be altered/succeeded through other governance votes, and no code path enforces any economic sanity bound (e.g., a maximum inflation cap or percentage-of-supply cap) on the minting amount itself. This mirrors the TSD root cause: a governance mechanism that is trusted to only make "reasonable" parameter/logic changes has no on-chain guardrail preventing a single vote from creating unbounded new supply.

### Impact Explanation
If a malicious or compromised governing node (or a governance-mode transition that hands control to an attacker-influenced address, analogous to TSD's DAO takeover) casts a `reward.mintingamount` vote with an extreme value (e.g., `10^30`), then starting from the next epoch every block will mint that amount natively into circulation via `FinalizeState`/`AddBalance`, distributed to validators/funds and immediately transferable/sellable — a direct, catastrophic native-token supply inflation event, matching the "unauthorized value movement / supply inflation" impact class explicitly targeted by this scan.

### Likelihood Explanation
Exercising this requires control of the governing node's voting key (in `single` mode) or majority/governing consensus in `none` mode — a non-trivial but realistic threat model directly analogous to the TSD attacker's accumulation of 33% DAO voting power. Given that `governance_vote` is a normal, unprivileged-at-the-API-layer RPC call for whichever account is authorized to vote, and that **no software-level safety cap exists** regardless of who casts the vote, likelihood is elevated relative to a properly bounded parameter — the only protection is procedural/social (trusting the governing node), not code-enforced.

### Recommendation
Add a `FormatChecker` for `RewardMintingAmount` that enforces a sane upper bound (e.g., a hard cap or a percentage-of-current-supply/-previous-minting-amount cap) similar to how `RewardRatio`/`RewardKip82Ratio` are validated to sum to 100, and similar to the `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` cross-consistency checks in `checkConsistency`. Consider also adding a `checkConsistency` case for `gov.RewardMintingAmount` that rejects changes exceeding some multiple of the previous value, preventing a single vote from causing a step-change supply inflation.

### Proof of Concept
1. As the governing node (or via `none`-mode majority), call:
   ```
   curl "http://localhost:8551" -X POST -H 'Content-Type: application/json' --data '
     {"jsonrpc":"2.0","id":1,"method":"governance_vote","params":[
       "reward.mintingamount",
       "1000000000000000000000000000000"
     ]}'
   ```
2. This passes `NewVoteData` (canonicalizer succeeds, `noopFormatChecker` always true) and `checkConsistency` (falls into the no-op default case), so the vote is accepted and, once ratified at the next epoch boundary, becomes the effective `reward.mintingamount`.
3. From the activation block onward, `getDeferredRewardFullKore`/`getDeferredRewardFull` uses this value as `minted` every block, and `FinalizeState` credits it to the reward recipients' balances via `state.AddBalance`, permanently and repeatedly inflating the KAIA total supply with no cap.

// Distribute the deferred rewards at the end of block processing.
func (r *RewardModule) FinalizeState(header *types.Header, state *state.StateDB, txs []*types.Transaction, receipts []*types.Receipt) error {
	if r.GovModule.GetParamSet(header.Number.Uint64()).ProposerPolicy == uint64(istanbul.WeightedRandom) && common.EmptyHash(header.Root) {
		qualified, err := r.ValsetModule.GetQualifiedValidators(header.Number.Uint64())
		if err != nil {
			return err
		}
		useRewardAddress := valset.NewAddressSet(qualified).Contains(r.NodeAddress)

		if rewardAddr := r.GetRewardAddress(header.Number.Uint64(), r.NodeAddress); useRewardAddress && rewardAddr != (common.Address{}) {
			header.Rewardbase = rewardAddr
			logger.Trace("Use reward address for nodeValidator", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		} else {
			logger.Trace("No reward address for nodeValidator. Use node's rewardbase.", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		}
	}

	spec, err := r.GetDeferredReward(header, txs, receipts)
	if err != nil {
		return err
	}
	if err := spec.Validate(); err != nil {
		return err
	}
	for addr, amount := range spec.Rewards {
		state.AddBalance(addr, amount)
	}
	return nil
}
