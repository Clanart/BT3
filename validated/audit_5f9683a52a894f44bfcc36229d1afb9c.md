## Finding [1](#0-0) 

`resolveWithin()` is Desktop's generic guard against path-traversal: it's supposed to guarantee that a resolved path is contained within a given root directory before the caller is allowed to touch it. Its containment check is a raw string prefix test, exactly the same bug class as the reported OpenSSL `ossl_x509name_cmp` flaw — a comparison routine that is supposed to enforce a strict relationship (name equality / path containment) but instead only checks a character-prefix, with no boundary/terminator check.

### Title
Path-traversal via missing path-separator boundary check in `resolveWithin` allows reveal of files outside repository root - (File: app/src/lib/path.ts)

### Summary
`resolveWithin` (and its `resolveWithinPosix`/`resolveWithinWin32` variants) is used throughout Desktop as the security boundary that keeps user- or remote-supplied relative paths from escaping a trusted root directory. The final check, `realResolved.startsWith(realRoot)`, is a naive string-prefix comparison. Just like `a == b` incorrectly returning true for `www.example.com` vs `www.example.co` in the OpenSSL report because the comparison ignored the extra trailing character, this check ignores the fact that a sibling directory whose name simply starts with the same characters as the root (e.g. `repo` vs `repo-evil`) will also satisfy `startsWith`, even though it is not a subdirectory of `repo` at all.

### Finding Description
`_resolveWithin` computes:
```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

If `pathSegments` contains enough `..` traversal, `resolved`/`realResolved` can point to a directory that lives next to `rootPath` rather than under it (e.g. root `/Users/victim/Documents/GitHub/repo` and a crafted segment `../repo-evil/secret`). `realResolved` (`/Users/victim/Documents/GitHub/repo-evil/secret`) shares a full character prefix with `realRoot` (`/Users/victim/Documents/GitHub/repo`) because `"repo-evil"` starts with `"repo"`, so `startsWith` returns `true` and the function returns the escaped path as "safe."

The codebase already demonstrates the correct pattern is known: `isClonePathSensitive` in `app/src/lib/git/clone.ts` deliberately guards against exactly this class of bug by checking `clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)`, i.e. it appends the platform separator before doing the prefix check. [3](#0-2) 
`resolveWithin` has no equivalent separator-boundary check, meaning the exact off-by-one/boundary omission that made the OpenSSL name comparison exploitable is reproduced here.

### Impact Explanation
`resolveWithin` gates a genuine attacker-reachable primitive: `openRepositoryFromUrl` in the dispatcher resolves a `filepath` supplied via GitHub Desktop's deep-link/protocol handler (`x-github-client://openRepo?url=...&filepath=...`) against the repository root and then reveals it to the user with `shell.showItemInFolder`:
```
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
}
``` [4](#0-3) 
An attacker who controls a deep link (a webpage, README, or GitHub UI action that opens `x-github-client://openRepo?...&filepath=...`) can point `filepath` at traversal segments that land in a sibling directory whose name happens to share the repository's name as a prefix (an attacker who also controls the repository name/clone target, or targets a commonly-named folder such as `github` next to `github-secrets`), causing Desktop to reveal/open a file outside the intended repository boundary. `resolveWithin` is also relied on by `app/src/lib/stores/app-store.ts` and `app/src/lib/copilot-conflict-context.ts`, so the same broken invariant may be reachable through those paths as well (not fully verified due to remaining search budget).

### Likelihood Explanation
The bug requires only that the attacker control a clickable deep link and that a sibling directory with a matching character prefix exist next to the target repository's working directory — no local access, malware, or elevated privileges needed, matching the "link/deep link the user clicks" attacker model. The reliability depends on the victim having a suitably-prefixed sibling directory, which somewhat limits practical exploitation but the logic flaw itself is deterministic and unconditional.

### Recommendation
Change the containment check to also verify a path-separator boundary (or that the paths are exactly equal), e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
using the separator appropriate to the `options` (`Path.sep`, `Path.posix.sep`, or `Path.win32.sep`) rather than the platform default, mirroring the safe pattern already used in `isClonePathSensitive`.

### Proof of Concept
1. Attacker hosts a page with a link: `x-github-client://openRepo?url=https://github.com/owner/repo&filepath=..%2Frepo-exfiltrated-secrets%2Fid_rsa`.
2. Victim has previously cloned `owner/repo` into `~/Documents/GitHub/repo`, and separately has (or is tricked into having) a sibling folder `~/Documents/GitHub/repo-exfiltrated-secrets` containing sensitive files (e.g. a folder created by a separate malicious clone with a lookalike name).
3. Clicking the link causes Desktop to call `resolveWithin('~/Documents/GitHub/repo', '../repo-exfiltrated-secrets/id_rsa')`.
4. `realResolved` = `~/Documents/GitHub/repo-exfiltrated-secrets/id_rsa`; `realResolved.startsWith(realRoot)` (`realRoot` = `~/Documents/GitHub/repo`) evaluates `true` due to the shared `"repo"` prefix.
5. `resolveWithin` returns the escaped path as valid, and `shell.showItemInFolder` reveals/opens the file outside the intended repository, despite the traversal guard being in place.
