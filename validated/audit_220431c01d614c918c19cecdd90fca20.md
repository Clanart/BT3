### Title
Dust and zero-value outputs are registered as spendable funds, letting attackers deposit economically unspendable value - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reported bug class is "a minimum threshold enforced on one side of a flow but not the other, so an amount below the denominator silently rounds the fee/check to zero." In `bitcoin-serai`, `SignableTransaction::new` enforces `amount >= DUST` (546 sat) on every *payment* output, but `Scanner::scan_transaction` registers *received* outputs with no value check at all. An unprivileged sender can create a P2TR output worth 0–545 sat to a scanned script; the wallet reports it as a `ReceivedOutput`, yet spending it costs more in marginal fee than it returns — or returns literally nothing at value 0.

### Finding Description
`Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) matches outputs purely on `script_pubkey` and pushes a `ReceivedOutput` carrying `output.value` verbatim — no `>= DUST` check:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

Meanwhile, the only dust enforcement in the spend path is on payments, `networks/bitcoin/src/wallet/send.rs:165-169`:

```rust
for (_, amount) in payments {
  if *amount < DUST { Err(TransactionError::DustPayment)?; }
}
```

Each input contributes ~68 vbytes of weight (see `calculate_weight_vbytes`, `send.rs:68-99`), so the `needed_fee` computed at `send.rs:206` (`fee_per_vbyte * vbytes`) grows by `fee_per_vbyte * ~68` per input. For any received output whose value is below that marginal cost — always true for values < 546 sat at any sane fee rate, and exactly zero for a 0-value output — the "contribution" of that input to `input_sat` rounds to zero or negative economically. This is the Serai analogue of `amount / feenominator == 0`: a value below the effective denominator produces a net contribution of zero, and no code path rejects it. The value is added to `input_sat` at `send.rs:175` and counted toward covering `payment_sat + needed_fee` (`send.rs:215`), so the wallet's accounting treats the dust as real funds even though consensus economics render it a liability.

### Impact Explanation
Funds reported received that are not spendable at their face value. A downstream protocol crediting deposits based on `scan_transaction`/`scan_block` results will credit an attacker for outputs that can never pay for their own inclusion as inputs. At value 0, the deposit is pure fee burn on the wallet; at 1–545 sat the credited amount exceeds what the input can recover. It also inflates `input_sat`, causing `NotEnoughFunds` accounting and change-splitting at `send.rs:224-235` to treat phantom value as available (a dust input can tip `value >= DUST` for the change-output decision while contributing less than the fee it imposes).

### Likelihood Explanation
Fully reachable by an unprivileged party: anyone can send a Bitcoin transaction paying a P2TR output to a published/scanned address (or any offset-registered script, since matching is by `script_pubkey` alone). Creating a sub-dust output is consensus-valid — dust is a relay/standardness policy, not a consensus rule, so a miner or any transaction that reaches a block suffices. No malicious validator, leaked key, or collusion is required.

### Recommendation
Enforce the same `DUST` constant symmetrically. Either drop outputs with `output.value.to_sat() < DUST` inside `Scanner::scan_transaction` (`mod.rs:205-211`), or reject dust-valued `ReceivedOutput`s in `SignableTransaction::new` alongside the payment check (`send.rs:165-169`) — ideally both, since scanning and spending are decoupled. At minimum, account for each input's marginal weight cost so inputs whose value is below `fee_per_vbyte * marginal_vbytes` are excluded rather than counted toward `input_sat`.
