### Title
Scanner reports immature coinbase outputs as spendable, enabling signing of invalid spends - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` iterates over every transaction in a block, including `block.txdata[0]` (the coinbase), and returns any matching outputs as `ReceivedOutput`. Coinbase outputs are encumbered by Bitcoin's 100-block maturity rule and cannot be spent until then. `SignableTransaction`/`TransactionMachine` then treat these `ReceivedOutput`s identically to ordinary confirmed outputs: `SignableTransaction::new` builds a transaction referencing the coinbase outpoint, and `TransactionSignMachine::sign` produces a valid Taproot key-spend signature over it. The resulting transaction is consensus-invalid (a coinbase spend before maturity is rejected by all nodes), so funds are reported received and a spend is signed for outputs that are not yet spendable — the same failure shape as Cooler recording a successful collateral deposit for a failed `transferFrom`.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script [1](#0-0) . `scan_block` calls `scan_transaction` on every entry in `block.txdata`, including index 0 [2](#0-1) . A doc comment notes coinbase outputs are "bound by maturity" and need a post-processing pass, but the code performs no such filtering, and `ReceivedOutput` carries no maturity metadata — `offset`, `output`, and `outpoint` only [3](#0-2) .

Downstream, `SignableTransaction::new` counts the coinbase output's value in `input_sat` and includes its outpoint in `tx.input` with no maturity or input-type check [4](#0-3) . `TransactionSignMachine::sign` then produces a real FROST/BIP-340 signature share committing to that input via `taproot_key_spend_signature_hash` with `Prevouts::All` [5](#0-4) .

The reachable trigger is untrusted block/transaction data fed to `scan_block`/`scan_transaction`: any miner (or any party supplying blocks to the scanner) can place a coinbase output paying to a registered script, which the wallet reports as a spendable `ReceivedOutput` and which the signing machine will sign a spend for.

### Impact Explanation
Funds are reported received that are not spendable. Beyond the accounting error, the signing protocol produces signatures for a transaction that cannot ever be included in a block until the coinbase matures — burning a FROST signing session (and its nonces/preprocesses) on a DOA transaction and potentially crediting a deposit that cannot be moved. Because `ReceivedOutput` exposes no way to distinguish coinbase provenance, a downstream consumer cannot detect the condition without re-querying the chain.

### Likelihood Explanation
Any mined block paying a coinbase output to a Serai deposit address (mining-pool payouts, or a miner deliberately targeting the deposit script to poison the wallet's UTXO set) triggers it whenever `scan_block` is used. Scanning whole blocks is the documented bulk-scanning API, so the path is exercised in normal operation.

### Recommendation
In `scan_block`, skip `block.txdata[0]` (or track coinbase provenance on `ReceivedOutput` and reject such inputs in `SignableTransaction::new` until maturity), rather than relying on callers to perform a post-processing pass.

### Proof of Concept
```rust
// Conceptual: a block whose coinbase pays to the scanner's script
let mut scanner = Scanner::new(group_key).unwrap();
// block.txdata[0] is a coinbase tx containing an output to scanner's script
let received = scanner.scan_block(&block);
// `received` contains a ReceivedOutput for the immature coinbase output,
// indistinguishable from a normal spendable UTXO.
let stx = SignableTransaction::new(received, &payments, change, None, fee_rate).unwrap();
// Signing proceeds normally and produces a signature spending the coinbase
// outpoint; the final transaction is rejected by the network (immature coinbase).
let (machine, preprocess) = stx.multisig(&keys).unwrap().preprocess(&mut rng);
```

The analog holds: like Cooler's `request()` recording a loan request on a failed `transferFrom`, `scan_block` records a spendable receipt for an output that cannot actually be spent, and the downstream spend path performs no validity check on the recorded claim.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
