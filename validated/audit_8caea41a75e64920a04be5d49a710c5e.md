### Title
Header-controlled allocation in `ThresholdKeys::read` allows attacker-triggered memory exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reads a participant count `n` from a 2-byte field and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before a single element has been read or validated. This is the same bug class as CVE-2017-14137: memory allocation that depends only on a length field in a header, not on data actually present.

### Finding Description
In `ThresholdKeys::read`, after the curve-ID check, `t`, `n`, and `i` are read as raw `u16`s [1](#0-0) . Then, if the interpolation tag byte is `0`, the code does `Vec::with_capacity(usize::from(n))` — an allocation of up to 65535 field elements (~2–4 MB depending on the ciphersuite's `F::Repr`) — before attempting to read any of those elements [2](#0-1) . The same `n` then drives a `HashMap` fill loop of `n` `read_G` calls [3](#0-2) . No bound on `n` is enforced against the actual input length, and `ThresholdParams::new(t, n, i)` validation happens only after all reads complete [4](#0-3) .

The in-scope sibling `SchnorrAggregate::read` reads a `u32` count but pushes elements only as `read_G` succeeds, so its footprint stays proportional to bytes supplied [5](#0-4) . The exact analog of the CVE — allocation sized purely by an untrusted header field — is the `with_capacity(n)` in `ThresholdKeys::read`. (The strongest such pattern in the repo, `Block::read`'s `Vec::with_capacity(u32)` in `coordinator/tributary/src/block.rs:92`, is outside the in-scope crate list.)

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as a reachable untrusted-byte sink) can force an ~2–4 MB allocation plus a `HashMap` pre-sizing attempt per call, with only a handful of input bytes required — the allocation occurs even if the stream ends immediately after the header. Repeated calls amplify this into a memory-exhaustion denial of service against the process deserializing keys, matching the CVE's availability impact (allocation failure → abort/panic via OOM).

### Likelihood Explanation
Reachability depends on a deployment deserializing `ThresholdKeys` from untrusted input (e.g., recovering keys or loading peer-supplied key material). Where reachable, it is trivially triggered: a constant-size crafted prefix causes maximum allocation. Per-call cost is bounded by `u16::MAX` elements, so exploitation requires repetition; hence Medium rather than High.

### Recommendation
Do not pre-size containers from untrusted length fields. Replace `Vec::with_capacity(usize::from(n))` with a `Vec::new()` + push loop (allocation grows only as elements are actually read), and validate `n` against `ThresholdParams` bounds *before* performing the interpolation/verification-share reads. Optionally enforce a hard cap on `n` consistent with `MAX_KEY_SHARES_PER_SET`.

### Proof of Concept
```rust
// Against ThresholdKeys::<C>::read with interpolation tag 0.
// Construct a byte stream:
//   [4-byte id_len][C::ID bytes][t: u16 = 1][n: u16 = 0xFFFF][i: u16 = 1][0x00]
// `read` then executes:
//   crypto/dkg/src/lib.rs:608  Vec::with_capacity(65535)   // ~2-4 MB allocated immediately
//   crypto/dkg/src/lib.rs:609  loop over 0..n { read_F }   // errors on EOF, AFTER the alloc
// Only ~15 bytes of input produce a multi-MB allocation; issue N calls to force
// N * ~3 MB of transient allocation / OOM pressure.
// No coefficient bytes need to be supplied at all.
```

**Uncertainty note:** I was unable to inspect `EncryptedMessage::read` in `crypto/dkg/pedpop/src/encryption.rs` before finalizing; if it performs a `with_capacity`/`vec![0; len]` on a ciphertext length field, it may present the same pattern with a wider (`u32`) bound and would warrant the same fix.
