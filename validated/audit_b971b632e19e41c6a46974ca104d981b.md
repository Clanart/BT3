### Title
`ThresholdKeys::read` trusts fully attacker-controlled interpolation parameters and never checks share consistency, allowing altered serialized parameters to silently replace the issued key configuration - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2020-7224 describes a client that loads cryptographic parameters which were altered from the issued value set, causing unintended components to be used. The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: the serialized blob carries every load-determining parameter — `t`, `n`, `i`, the interpolation *method selector*, the full `Interpolation::Constant` coefficient vector, the `secret_share`, and all `verification_shares` — and `ThresholdKeys::new` consumes them without verifying that the secret share corresponds to the verification shares, or that the interpolation parameters reproduce the issued group key. Altered bytes are therefore loaded as a valid key configuration.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` from the stream, then a single-byte tag choosing `Interpolation::Constant` — in which case it reads `n` attacker-supplied scalars as coefficients — or `Interpolation::Lagrange`. It then reads `secret_share` and `n` verification shares and calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:591-632). [1](#0-0) 

`ThresholdKeys::new` only checks `verification_shares.len() == n`, participant indexes `<= n`, and `t == n` for Constant interpolation. It derives `group_key` as `Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i)` directly from the supplied coefficients/shares, and never verifies `C::generator() * secret_share == verification_shares[i]` or any binding between the loaded parameters and the originally issued DKG output (crypto/dkg/src/lib.rs:355-390). [2](#0-1) 

Consequently `view()` interpolates the (possibly replaced) `secret_share` with the supplied coefficients and produces a `ThresholdView` whose `group_key`, `secret_share`, and `verification_shares` are a coherent-but-altered configuration (crypto/dkg/src/lib.rs:493-532). [3](#0-2) 

The loaded keys are then used for signing and their `group_key()` is reported to the coordinator as the deposit/withdrawal key: in `processor/src/key_gen.rs` keys are loaded via `ThresholdKeys::read` in `GeneratedKeysDb::read_keys`, tweaked, and their `group_key()` is emitted in `ProcessorMessage::GeneratedKeyPair` as the `substrate_key`/`network_key` used to derive network deposit addresses (processor/src/key_gen.rs:56-62, 494-501). [4](#0-3) 

### Impact Explanation
An unprivileged party who can feed bytes into `ThresholdKeys::read` (one of the explicitly accepted untrusted-input surfaces) causes the node to silently adopt a key configuration that was never the issued DKG output:

- **Signing under an unintended group key**: altered `Interpolation::Constant` coefficients or verification shares change `group_key` while the node still produces validly-aggregating signature shares for that key — signatures over real messages are issued for a group key that does not correspond to the legitimately generated threshold key.
- **Funds reported received that are not spendable**: `GeneratedKeyPair` reports `generated_network_key` derived from the altered parameters; deposits to that address are controlled by no correctly-interpolating quorum, rendering received funds unspendable.
- **Silent misattribution of blame/shares**: a secret share inconsistent with `verification_shares[i]` makes every signature share from this participant invalid under the stated shares while no deserialization error is raised, corrupting the signing set without a key-level indication.

This is the direct analog of the CVE: parameters altered from the issued value set are loaded and used as authoritative, with no integrity or consistency check tying them to the issued configuration.

### Likelihood Explanation
The serialized `ThresholdKeys` format contains no MAC, no checksum over the issued commitment transcript, and no proof tying `secret_share` to `verification_shares`. Any path that supplies deserialized key bytes — key restoration, DB-supplied blobs via `GeneratedKeysDb::read_keys`, or any API accepting `ThresholdKeys::read` input — is sufficient; no threshold of colluding participants, no leaked keys, and no malicious-observer assumptions are required. The only integrity check performed is the ciphersuite `ID` string (crypto/dkg/src/lib.rs:575-589), which constrains the curve, not the parameter set.

### Recommendation
- On `ThresholdKeys::new` / `read`, verify `C::generator() * secret_share == verification_shares[params.i()]` (after interpolation for Constant mode) and reject on mismatch.
- Bind the serialized parameter set to the issued configuration: either persist/verify a hash of the DKG commitment transcript, or store an expected `group_key` and recompute it from `verification_shares` + `interpolation` at load time, erroring on divergence.
- Treat `Interpolation::Constant` coefficient vectors as untrusted input requiring validation rather than loadable configuration.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ThresholdKeys::read:
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(t.to_le_bytes());          // arbitrary t
blob.extend(n.to_le_bytes());          // arbitrary n
blob.extend(i.to_le_bytes());          // arbitrary participant index
blob.push(0);                          // Interpolation::Constant
for _ in 0 .. n {
  blob.extend(attacker_chosen_F.to_repr().as_ref());  // arbitrary coefficients
}
blob.extend(attacker_chosen_F.to_repr().as_ref());    // secret_share, unchecked
for _ in 1 ..= n {
  blob.extend(attacker_chosen_G.to_bytes().as_ref()); // verification shares
}
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap(); // accepted
// keys.group_key() is now a function purely of attacker bytes; keys.view(...) signs with it.
```
No error is raised because `ThresholdKeys::new` performs only count/bounds checks and never reconciles `secret_share` with `verification_shares` or the issued group key.
