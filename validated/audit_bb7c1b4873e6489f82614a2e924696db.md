This confirms the SSRF-analog chain. The mirror creation puzzle `create_mirror_puzzle()` is a `P2_PARENT` puzzle spendable by anyone who owns/creates that coin, and `get_mirror_info()` parses the `CREATE_COIN` condition's memos to extract arbitrary attacker-controlled `urls` bytes with zero validation (no scheme/host allow-listing) [1](#0-0) . Any node tracking that launcher id ingests these mirror URLs into its local DL wallet store purely from on-chain coin data [2](#0-1) , and the DataLayer service periodically pulls those mirror URLs via `update_subscriptions_from_wallet()`/`dl_get_mirrors` and merges them into its subscription table without any URL sanitization [3](#0-2) [4](#0-3) .

### Title
Server-Side Request Forgery via unsanitized DataLayer mirror/subscription URLs - (File: chia/data_layer/download_data.py)

### Summary
The DataLayer service automatically issues outbound HTTP(S) requests to URLs that are fully attacker-controlled: either supplied directly by any local RPC caller via `subscribe`, or — more importantly — embedded on-chain in a `mirror` coin's memos that anyone can create for any tracked store/launcher id and which every node tracking that store ingests without validation.

### Finding Description
`create_mirror_puzzle()` produces a generic `P2_PARENT` puzzle; any party can spend a coin to this puzzle hash with `CREATE_COIN` memos of the form `[launcher_id, url1, url2, ...]` [5](#0-4) . When a wallet is tracking that `launcher_id`, `DataLayerWallet.coin_added()` detects the mirror coin, calls `get_mirror_info()` to decode the memos, and stores the URLs verbatim in `dl_store` with no scheme/host/port allow-listing, no rejection of `file://`, loopback, link-local, or internal-network addresses [2](#0-1) .

The DataLayer service (`chia/data_layer/data_layer.py`) periodically calls `update_subscriptions_from_wallet()`, which fetches these on-chain mirror URLs via `dl_get_mirrors` RPC and merges them into the local `subscriptions` table as legitimate server URLs for that store [3](#0-2) , persisted via `DataStore.update_subscriptions_from_wallet()` [4](#0-3) .

During the sync loop, `fetch_and_validate()` randomly selects one of these server URLs and passes it to `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an `aiohttp.ClientSession.get(server_info.url + "/" + filename, ...)` request from the DataLayer server process itself [6](#0-5) [7](#0-6) . Additionally, `get_downloader()` will POST JSON containing the attacker-controlled `url` field to any configured plugin, and mirror URLs are also usable as plugin download targets [8](#0-7) .

The same class of issue also exists on the purely local-RPC path: `DataLayerRpcApi.subscribe()` accepts an unauthenticated (RPC-scoped) list of `urls` directly from the caller with no validation before they are used identically by the fetch loop [9](#0-8) [10](#0-9) .

### Impact Explanation
Because mirror URLs originate from an on-chain coin spend that any user can create for any `launcher_id` (paying only the mirror amount + fee, no special coin ownership of the DL singleton is required — mirrors are separate coins tracked by relationship to the launcher id, not owned by the singleton), an attacker can force any node that tracks/subscribes to that store's DataLayer singleton to make outbound GET/POST requests to attacker-chosen hosts (e.g. internal metadata services, internal RPC ports, or arbitrary internet hosts) at a schedule and cadence controlled by `manage_data_interval`. This can be used to probe internal network topology, hit internal-only HTTP services reachable from the DataLayer host, or exfiltrate data via request timing/side channels — the classic SSRF impact pattern cited in the external report, now reachable purely through a DataLayer/Data-Layer-client trust boundary rather than an admin panel.

### Likelihood Explanation
Likelihood is Medium: it requires the victim node to be actively tracking/subscribed to the attacker-influenced store id (a normal DataLayer usage pattern for shared/public stores), and creating a mirror coin costs a small fee plus the mirror coin amount, but requires no special privilege — any wallet that can spend XCH can create the mirror coin for any launcher id it can identify. The purely local `subscribe` RPC vector requires only local RPC access (already an assumed-trusted boundary in this scan's rules, but is a valid Data-Layer-client-reachable equivalent).

### Recommendation
- Validate and restrict mirror/subscription URLs before they are used for outbound requests: enforce an allow-listed scheme (`http`/`https` only), reject loopback/link-local/private-network/metadata-service addresses unless explicitly configured, and consider resolving+checking the destination IP at request time (not just DNS name) to prevent DNS-rebinding style SSRF.
- Treat mirror URLs sourced from on-chain data (`get_mirror_info()` / `coin_added()`) as untrusted external input, and apply the same validation used (or newly added) for local `subscribe` URLs.
- Consider making outbound mirror/subscription fetches opt-in per store or require explicit operator confirmation before a newly-discovered on-chain mirror URL is added to the active subscription/download rotation.

### Proof of Concept
1. Attacker creates a DL launcher/store (or targets an existing store id that a victim tracks).
2. Attacker spends any coin to `create_mirror_puzzle()`'s puzzle hash with `CREATE_COIN` memos `[victim_tracked_launcher_id, b"http://169.254.169.254/latest/meta-data/", ...]`, per `get_mirror_info()`'s expected memo layout [1](#0-0) .
3. Once confirmed on-chain, any victim node whose wallet tracks that launcher id ingests the mirror via `DataLayerWallet.coin_added()` [2](#0-1) .
4. The victim's DataLayer service's next `update_subscription()` cycle calls `update_subscriptions_from_wallet()` then `fetch_and_validate()`, which will eventually select the attacker's URL and issue `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` from the DataLayer host [11](#0-10) [7](#0-6) .
5. Attacker observes/exfiltrates the request (e.g. via an attacker-controlled HTTP endpoint logging request headers/timing) to confirm SSRF, or targets internal-only endpoints reachable from the victim host.

def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (

        ):

            return launcher_id, [url for url in memos[1:]]

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
