## Analysis

The FantiumAG report is about a missing existence-validation check (`onlyValidCollectionId()`) before a state-changing operation is allowed to run on an attacker-suppliable ID. Searching Hyperbridge for the equivalent pattern — a function operating on a commitment/order ID that skips the "does this ID actually exist" check that its sibling function performs — surfaces a concrete asymmetry in the cross-chain Intent Gateway cancellation flow.

### Title
Missing order-existence check in `_cancelFromDest()` allows permanent pre-emptive lock of a not-yet-placed order commitment - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromSource()` validates that every input token of the order actually has non-zero escrow recorded in `_orders[commitment][token]` before proceeding (`revert UnknownOrder()` if any is `0`) [1](#0-0) . Its sibling, `_cancelFromDest()`, performs no equivalent existence check at all before mutating state and dispatching a cross-chain message [2](#0-1) .

### Finding Description
`cancelOrder()` routes to `_cancelFromDest()` whenever the caller is on the order's destination chain [3](#0-2) . For cross-chain orders, escrow only ever exists on the **source** chain — the destination chain has no `_orders[commitment][...]` bookkeeping to check against — so `_cancelFromDest()` accepts *any* well-formed `Order` struct whose fields resolve `order.destination` to the current chain, without ever confirming that such an order was legitimately placed on the source chain.

The only gate is:
```
if (order.deadline >= _blockNumber()) {
    if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
}
```
Before the deadline, only the claimed `order.user` may call it; **after the deadline, anyone can call it for any order**, real or fabricated [4](#0-3) .

Once called, it unconditionally does:
```
_filled[commitment] = address(uint160(uint256(order.user)));
```
This is the exact same storage slot that `fillOrder()` checks to reject double-fills: `if (_filled[commitment] != address(0)) revert Filled();` [5](#0-4) .

Because `commitment = keccak256(abi.encode(order))` is fully attacker-computable from public order-struct fields (user, source, destination, deadline, nonce, fees, session, predispatch, inputs, output), an attacker can pre-compute the commitment of an order a victim is *about to place* (e.g. a low, predictable `nonce`, or a repeat order with identical parameters), wait until `order.deadline` has elapsed relative to some `blockNumber` value they control in `options.height`... more directly: an attacker can pick **any future deadline already in the past relative to their own submitted `_blockNumber()`**, i.e., craft an `Order` with `deadline` set below the current block, and call `_cancelFromDest()` for that commitment before the user ever places it. This poisons `_filled[commitment]` on the destination chain and dispatches a `RefundEscrow` message back to `order.source` paid for by the attacker (relayer fee).

Downstream, `_withdraw()`'s per-token check (`if (_orders[commitment][token] == 0) revert UnknownOrder()`, mirrored in the tron fork at [6](#0-5) ) prevents the attacker from directly draining funds via this path when the order was never actually placed — the RefundEscrow message will simply fail to deliver on the source chain. **However**, the destination-side `_filled[commitment]` entry is now permanently poisoned. If the victim later places the *exact* order on the source chain (same deterministic fields — a realistic scenario for repeat/automated orders, or if an attacker front-runs by observing the order in the mempool before it's placed on the source chain but before the fill window on the destination chain), a legitimate solver's subsequent `fillOrder()` call on the destination chain will revert with `Filled()` forever, even though the order was never actually filled. The user's input tokens remain escrowed on the source chain with no solver able to fill the order — a permanent fund lock reachable by an unprivileged, un-relayed, un-proven caller.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary" invariant by making an order **un-fillable via forgery of the `_filled` mapping**, without any proof of prior fill, cross-chain message, or state proof — a pure local state write triggered by an attacker-supplied struct. The result is denial-of-service / fund lock on legitimate cross-chain orders, and it also lets anyone force a real message dispatch (paid via `dispatchWithFeeToken`/native value) referencing a commitment that has no corresponding escrow, unlike the source-side function which validates existence first.

### Likelihood Explanation
Exploitation only requires knowledge of the order's public fields (which are often predictable — sequential nonces, same user/token/amount for repeat integrations) and no privileged role, prover, or relayer collusion — matching the "unprivileged attacker" requirement. The main constraint is that `order.deadline < _blockNumber()` must hold at call time, meaning the attacker must front-run with a deadline value already expired from their own perspective, which is directly craftable since `deadline` is a caller-chosen field of the `Order` struct, not derived from prior placement.

### Recommendation
Add an existence/consistency check to `_cancelFromDest()` mirroring `_cancelFromSource()` — e.g. require a valid non-empty proof-of-placement or otherwise gate the `_filled[commitment]` write so it cannot be set for commitments that were never associated with an actual fill attempt or a verified source-chain escrow, and/or require the caller to first prove (via the source chain's `_orders` state) that the order exists before the destination-side cancellation path can poison `_filled`.

### Proof of Concept
1. Attacker observes (or predicts) a user's upcoming order fields: `user`, `source`, `destination = currentChain`, a small `nonce`, `inputs`, `output`.
2. Attacker crafts an `Order` struct identical to the one the user will place, but is free to choose any `deadline` value in the struct as long as `deadline < _blockNumber()` at call time (this field is not checked against a source-chain record).
3. Attacker calls `cancelOrder(order, options)` on the destination chain. Since `order.deadline < _blockNumber()`, the `Unauthorized` check is skipped, and `_cancelFromDest()` executes:
   - `_filled[commitment] = order.user` is set [7](#0-6) .
   - A `RefundEscrow` post request is dispatched to `order.source` (fails harmlessly there due to `UnknownOrder` in `_withdraw`).
4. Later, the victim places the identical order on the source chain and a solver calls `fillOrder(order, options)` on the destination chain.
5. `fillOrder()` reverts with `Filled()` because `_filled[commitment] != address(0)` from step 3 [8](#0-7) , even though the order was never actually filled — permanently locking the user's escrowed input tokens on the source chain.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))

            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,

            payer: msg.sender

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
