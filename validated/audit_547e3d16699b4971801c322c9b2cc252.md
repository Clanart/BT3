### Title
Hookify hook executors fail open on any rule-evaluation error, silently bypassing configured `block` rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The `hookify` plugin implements `PreToolUse`, `PostToolUse`, `Stop`, and `UserPromptSubmit` hooks that are meant to run user-authored `.claude/hookify.*.local.md` rules (e.g. "block `rm -rf`", "block writes to `.env`") before Claude Code allows a tool call or session action to proceed. Just as the L2 `deposit.go` message loop omits the `validateBasicTxMsgs()` step that `BaseApp.runTx` normally performs — causing messages to execute without the validation the RPC path guarantees — every hookify entrypoint wraps its entire rule-loading/evaluation logic in a blanket `try/except Exception` that, on ANY failure, discards the validation result and unconditionally exits `0` (allow), the Claude Code equivalent of "let the message execute without `ValidateBasic`."

### Finding Description
Each hook entrypoint (`plugins/hookify/hooks/pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) follows the identical pattern: [1](#0-0) 

The `main()` function reads the hook input, calls `load_rules()` and `RuleEngine.evaluate_rules()`, and prints the JSON decision. Critically:
- The whole body is inside a bare `except Exception as e`, which converts ANY unexpected failure (a malformed rule file surfacing through `load_rules`'s broad `except Exception` in `plugins/hookify/core/config_loader.py` lines 236-239, a regex compile error not caught in `RuleEngine._regex_match`, a `KeyError`/`TypeError` in `_extract_field`, a JSON decode error on `sys.stdin`, etc.) into a benign `systemMessage` output.
- The `finally: sys.exit(0)` block unconditionally exits 0 — the "allow" exit code — regardless of whether the exception happened before, during, or after rule evaluation.

This means that if a crafted or malformed tool input (e.g. an unusual `tool_input` field, non-UTF8 content, or a regex-breaking pattern in a rule file) throws an exception anywhere inside `evaluate_rules`/`_check_condition`/`_extract_field`, the hook that was supposed to `block` a dangerous `Bash` command or file write never returns its `deny` decision — it returns an `systemMessage`-only allow response, and Claude Code proceeds to execute the tool call. This is architecturally identical to the reported bug: a step that is supposed to gate execution (`ValidateBasic`/rule evaluation) is bypassed on an execution path that should have failed closed but instead fails open. ### Impact Explanation
A user who has configured hookify `block` rules to enforce guardrails (e.g. deny `rm -rf`, deny writes to `.env`/system paths) relies on those rules being enforced on every matching tool call. Any input that triggers an unhandled exception in the rule pipeline — which is plausible given the hand-rolled YAML-like frontmatter parser in `extract_frontmatter` and the loose field extraction in `_extract_field` — causes the PreToolUse hook to fail open, silently allowing an operation the user explicitly intended to block. This is a hook-bypass trust-boundary violation: the security control (deny-listing dangerous commands/paths) is defeated without any visible error to the user beyond a generic `systemMessage`.

### Likelihood Explanation
Likelihood is moderate: it requires a specific malformed rule file or edge-case tool input to trigger an unhandled exception (e.g. a bad regex pattern, unexpected non-string field, or file I/O race). The current code does defensively catch many specific exception types, but the outermost catch-all combined with `finally: sys.exit(0)` guarantees that no matter what fails, the net effect is "allow," which is the fail-open design flaw itself — the mitigation gap doesn't need a specific trigger to exist, it's baked into the control-flow.

### Recommendation
Mirror the Cosmos SDK fix pattern: distinguish "hook infrastructure failure" from "rule evaluation result," and default the former to fail-closed (deny/ask) for `block`-type rules rather than fail-open, or at minimum surface the failure loudly (non-zero exit with a clear denial reason) instead of silently exiting 0. Concretely:
- In `plugins/hookify/hooks/pretooluse.py` (and the other three hook scripts), on exception, check whether any loaded rules are `action == 'block'` type before defaulting to allow; if rule loading/evaluation could not complete, prefer exiting 2 (deny/ask) for `PreToolUse` rather than 0.
- In `plugins/hookify/core/rule_engine.py`, catch condition-evaluation exceptions per-rule (already partially done for regex) so a single malformed rule cannot abort evaluation of all other rules silently.

### Proof of Concept
1. Create `.claude/hookify.bash.local.md` with an invalid regex pattern designed to raise `re.error` outside the caught path, or a `conditions` entry whose `field` triggers a `TypeError` in `_extract_field` (e.g. a non-string `tool_input` value that isn't handled).
2. Configure the rule as `action: block` for `Bash` commands matching `rm -rf`.
3. Run a `Bash` tool call with `rm -rf /some/path`.
4. Because the exception is caught by the outer `except Exception` in `pretooluse.py` main(), the hook prints a generic `systemMessage` and `finally: sys.exit(0)` executes — Claude Code treats this as "allow," and the destructive command that should have been blocked is executed. [4](#0-3)

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

        # If only warnings, show them but allow operation
        if warning_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in warning_rules]
            return {
                "systemMessage": "\n\n".join(messages)
            }

        # No matches - allow operation
        return {}
