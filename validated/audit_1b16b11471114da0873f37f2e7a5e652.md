No vulnerability found for this question.

**Reasoning:**

The claimed exploit path fails at the exact guard the question describes. `Verifier::is_deposit_valid` at [1](#0-0)  indeed only re-reads `deposit_tx.output[vout]` and checks `value == bridge_amount` and `script_pubkey == expected_scriptpubkey`, without querying spent/UTXO status. But the second-layer guard, `Database::insert_deposit_data_if_not_exists`, does an equality check between the new `DepositData` and any existing row keyed by `deposit_outpoint` (a UNIQUE column) via `ON CONFLICT (deposit_outpoint) DO NOTHING` followed by an explicit comparison, per [2](#0-1) .

Critically, `DepositData::eq` at [3](#0-2)  compares `self.deposit.deposit_type == other.deposit.deposit_type`, and `DepositType`/`BaseDepositData` derive full-value `PartialEq` (including `evm_address` and `recovery_taproot_address`) at [4](#0-3)  and [5](#0-4) . So a second `Deposit` request for the same `deposit_outpoint` but a different `evm_address` produces a `DepositData` that is *not* equal to the stored one, causing `insert_deposit_data_if_not_exists` to return `BridgeError::DepositDataMismatch` exactly as the question anticipates — the attack is rejected before any second signing session can proceed, in both `deposit_sign`/`deposit_finalize` ( [6](#0-5) , [7](#0-6) ) and `set_operator_keys` ( [8](#0-7) ).

The only way to actually defeat this binding is if the verifier's DB row for that `deposit_outpoint` is lost (e.g., DB wipe/restart) — but that is an operational/deployment failure of the verifier operator, not something reachable by an unprivileged attacker who can only broadcast Bitcoin transactions and call public gRPC endpoints. The threat model explicitly excludes such scenarios (no privileged/verifier access, no local/physical access to infrastructure). Since the DB-level equality check (which does include `evm_address`) correctly rejects the described replay, and the attacker has no means to induce verifier DB loss, the binding "one unspent bridge_amount deposit output ⇒ exactly one presignable move txid" is not broken under the given attacker capabilities.

            "INSERT INTO deposits (deposit_outpoint, deposit_params, move_to_vault_txid)
                VALUES ($1, $2, $3)
                ON CONFLICT (deposit_outpoint) DO NOTHING
                RETURNING deposit_id",
        )
        .bind(OutPointDB(deposit_data.get_deposit_outpoint()))
        .bind(DepositParamsDB(deposit_data.clone().into()))
        .bind(TxidDB(move_to_vault_txid));

        let result =
            execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, fetch_optional)?;

        if let Some((deposit_id,)) = result {

        }

impl PartialEq for DepositData {
    fn eq(&self, other: &Self) -> bool {
        // nofn_xonly_pk only depends on verifiers pk's so it can be ignored as verifiers are already compared
        // for security council, order of keys matter as it will change the m of n multisig script,
        // thus change the scriptpubkey of move to vault tx

            && self.deposit.deposit_outpoint == other.deposit.deposit_outpoint

            // get() functions already return sorted lists
            && self.get_operators() == other.get_operators()
            && self.get_verifiers() == other.get_verifiers()
            && self.get_watchtowers() == other.get_watchtowers()
            && self.deposit.deposit_type == other.deposit.deposit_type
