## Analysis

Reducing the Venus report to its core invariant: **a short, fixed-length block window determines which bids are counted toward a final on-chain value, and an attacker who can dominate block inclusion during that window can become the sole (or dominant) contributor to that value, skewing an outcome the protocol/users then rely on.**

The Hyperbridge analog is the Phantom Order price-oracle mechanism in the intents-coprocessor pallet. `IntentsPhantomOrderBidWindow` is set to **25 blocks** on the Nexus runtime [1](#0-0) , and `place_bid` only admits phantom-order bids while `block_number <= created_at_block + window` [2](#0-1) . When the window closes, `PhantomBidWindowExhausted` fires and the indexer aggregates **whatever bids made it into that window** into a `PhantomOrderPriceSnapshot`, computing a liquidity-weighted median price from the surviving bids [3](#0-2) . That snapshot's `medianPrice` is then used directly by the SDK to price **real user orders** with real escrowed funds via `PhantomSnapshotIntentQuoteStrategy.quote()` [4](#0-3) .

This is structurally identical to the Shortfall bug: a narrow window (25 blocks vs. 10 blocks) gates which bids count toward a value (auction winner vs. median price) that then moves real funds. A solver capable of saturating Hyperbridge block weight/extrinsic inclusion during the 25-block window can crowd out competing solver bids, leaving only its own bid to be counted — becoming the sole contributor to `medianPrice` for that snapshot (the aggregation logic explicitly supports and records a single-bidder case, `bidCount: quotes.length` with no floor other than `> 0`, see `phantom-aggregation.ts`). Because `quoteOrderFees`/`quoteIntent` consumers price real swap orders directly off this median with no on-chain sanity bound beyond `medianPrice > 0` and `bidCount > 0` [5](#0-4) , an attacker-dominated window lets that single solver dictate the exchange rate quoted to real users, who then place under-priced orders that the same (or colluding) solver fills at the manipulated rate — a direct, repeatable fund-loss vector for users relying on the Phantom quote strategy.

I was not able to fully verify Hyperbridge's per-block extrinsic weight limits or the real-world cost of crowding out competing `place_bid` extrinsics within 25 blocks (this would require live network/weight-limit data not present in the indexed code), so the concrete economic feasibility of the block-stuffing griefing step is not fully provable from local code alone — only the missing invariant (no minimum-bidder-count or price-deviation guard before a snapshot is trusted) is.

### Title
Phantom-order price snapshot trusts a single dominant bid within a short, unguarded block window - (File: `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
The Phantom Order oracle used to price real IntentGateway swaps aggregates whatever solver bids land within a fixed 25-block window and accepts a snapshot with as few as one contributing bid, with no minimum-bidder or price-deviation safeguard.

### Finding Description
`place_bid` enforces only that a bid arrives before `created_at_block + phantom_bid_window` [6](#0-5) . The window (`IntentsPhantomOrderBidWindow = 25`) is short and fixed per configuration [1](#0-0) . When it closes, the indexer aggregates all bids seen for that commitment into a single `PhantomOrderPriceSnapshot`, requiring only `quotes.length > 0` (i.e., at least one verified bid) before publishing a median price [7](#0-6) . Real orders quote off this snapshot with no independent price-sanity check beyond `medianPrice > 0` [5](#0-4) . An attacker who can exclude competing bids from the narrow window (analogous to block-stuffing in the Venus report) ends up as the sole price-setter for that snapshot.

### Impact Explanation
Users who quote swaps via the `phantom_snapshot` strategy get pricing dictated entirely by a single attacker-controlled bid, letting that party set an unfavorable exchange rate and then fill the resulting under-priced order themselves — extracting value from users' escrowed funds. This is a false/manipulated state (price) acceptance feeding directly into fund-moving order placement.

### Likelihood Explanation
Requires an unprivileged solver to win a race to be the sole (or dominant) bidder within a 25-block window repeatedly — feasible for any solver with modest liquidity and no need for a compromised relayer, prover, or admin. Exact cost of crowding out competitors could not be fully confirmed from local code (depends on Hyperbridge's per-block weight limits), so likelihood is plausible but not fully quantified.

### Recommendation
Require a minimum number of independent, verified solver bids (not just `> 0`) before publishing a snapshot; reject or flag snapshots whose price deviates significantly from the prior snapshot or from an independent reference price; consider widening/randomizing the window or making it react to bid arrival similar to the auction-window mitigations proposed in the source report.

### Proof of Concept
1. Governance-configured window: `IntentsPhantomOrderBidWindow = 25` blocks.
2. Attacker solver monitors `PhantomOrderRegistered` and submits its own `place_bid` immediately.
3. Attacker prevents/outraces other solvers' `place_bid` extrinsics from landing within the remaining ~24 blocks (analogous to block-stuffing).
4. Window closes; `PhantomBidWindowExhausted` fires; the indexer's `aggregatePhantomBids` finds only the attacker's bid (`quotes.length === 1`) and writes a `PhantomOrderPriceSnapshot` with `medianPrice` equal to the attacker's quoted rate.
5. A user calls `quoteIntent` with `strategy: "phantom_snapshot"`; `PhantomSnapshotIntentQuoteStrategy.quote()` accepts the snapshot (passes all `validateSnapshot` checks) and returns amounts based on the attacker's rate.
6. The user places a real order at that rate; the attacker (or a colluding solver) fills it, capturing the spread between the manipulated rate and the fair market rate.
