## Summary

The external report's core issue is: an on-chain swap function that doesn't return unspent/unused native value to the party who supplied it, allowing value to be captured by someone other than the depositor when swap execution consumes less than what was sent. The Hyperbridge analog is in `EvmHost.sol`'s native-token payment path used by `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

## Finding Description

When a caller pays Hyperbridge dispatch/funding fees with native token (`msg.value > 0`), `EvmHost` swaps exactly enough native token for the required `feeToken` amount using Uniswap V2's exact-output swap: [1](#0-0) 

```
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        ...
```

`swapETHForExactTokens(amountOut, path, to, deadline)` in Uniswap V2's router computes the minimal ETH input needed to obtain exactly `post.fee` tokens, and **refunds any unspent `msg.value` to the router's caller** — which, in this call chain, is `EvmHost` itself (since `EvmHost` is the account invoking the router), not the end user who called `dispatch()`/`fundRequest()`. The same pattern repeats verbatim in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

None of these three functions contain any logic to forward the router's ETH refund back to `_msgSender()`. The docs explicitly acknowledge that off-chain fee estimation via `quote()` is sandwich-attack-prone and must only be used as an estimate, implying callers routinely send `msg.value` with headroom above the exact quoted amount to avoid reverts from price movement between quoting and execution: [4](#0-3) 

Any such headroom — whether from normal price movement, a sandwich attack that shifts the AMM price between quote-time and execution, or simple user over-provisioning — is captured silently by the `EvmHost` contract with no code path returning it to the payer.

## Impact Explanation

This is an unauthorized loss of user funds: native token sent by an unprivileged caller to pay for a legitimate dispatch/fee-funding operation is partially retained by the protocol contract instead of being returned to the payer, with no consent or accounting mechanism tying that excess back to the depositor. Because the amount retained scales with the gap between the price at quote/estimation time and the price at execution time, an attacker who front-runs a `dispatch()`/`fundRequest()` call (sandwiching the AMM pool) can widen this gap and increase the amount of ETH silently absorbed by the host contract from ordinary users, systematically diverting value that belongs to bridge users into protocol-held balance without any explicit acceptance of that outcome.

## Likelihood Explanation

Likelihood is high for the "silent forfeiture of overpaid ETH" baseline case: it occurs on every native-token payment where `msg.value` exceeds the exact swap requirement, which is expected any time users apply a safety margin (as the documentation recommends) or when normal price movement occurs between the client-side `quote()` call and on-chain execution — no attacker action is required to trigger loss. The sandwich-amplified variant requires only a public mempool transaction and standard front/back-running, not a malicious relayer, prover, or privileged role, keeping it within the unprivileged-attacker bar.

## Recommendation

After calling `swapETHForExactTokens`, capture the router's returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` directly to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`. Alternatively, use `swapExactETHForTokens` with an off-chain-computed minimum-output guard and refund any leftover token/ETH dust to the caller, ensuring value that belongs to the payer is never redirected to the protocol by default.

## Proof of Concept

1. Attacker observes a pending `dispatch(DispatchPost)` (or `fundRequest`) transaction in the mempool with `msg.value` set based on an off-chain `quote()` estimate plus a safety margin (as the docs recommend, since `quote()` "is vulnerable to sandwich attacks. Only use it off-chain").
2. Attacker front-runs with a large ETH→feeToken swap on the same Uniswap V2 pair used by `_hostParams.uniswapV2`, moving the price so that fewer feeToken units are obtained per ETH.
3. The victim's `dispatch()` call executes `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)`. Because the price has moved, less of the victim's `msg.value` is required to obtain `post.fee` tokens than the victim expected when sizing their headroom — but more than a no-manipulation baseline, meaning the "wasted"/unused ETH margin retained by `EvmHost` is larger than in the unmanipulated case.
4. Attacker back-runs, restoring the price and extracting the sandwich profit from the AMM pool as usual; separately, the excess ETH from the victim's transaction remains stuck in `EvmHost`'s balance, credited to no one and returned to no one, since neither `dispatch()` nor `fundRequest()` forward the Uniswap refund to `_msgSender()`.
5. Repeating this for every native-token payer permanently accumulates unaccounted ETH in the `EvmHost` contract at the direct expense of users, with no on-chain path for those users to reclaim it.
