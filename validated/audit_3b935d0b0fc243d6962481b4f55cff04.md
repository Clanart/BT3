### Title
Missing-participant panic in PedPoP blame evaluation via unvalidated `recipient`/`sender` index - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The bug class in the external report is a nested-map dereference assumed to succeed: `GetInitOp` checks the outer map, then blindly dereferences the result of a second `.find`. The Serai analog lives in PedPoP's blame/decryption path: `Decryption::decrypt_with_proof` performs a `HashMap` index (`self.enc_keys[&decryptor]`) on a `Participant` index that is never validated against the registered participant set. Combined with `blame_internal` doing `self.commitments[&sender]`, any accusation naming an out-of-range participant crashes the evaluating node, rather than returning a blame verdict.

### Finding Description

`Decryption` maintains `enc_keys: HashMap<Participant, C::G>` populated only for the `n` real DKG participants via `register` (encryption.rs:351-362). In `decrypt_with_proof`, after the per-message proof-of-possession is verified, the code builds the DLEq statement as:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```
`crypto/dkg/pedpop/src/encryption.rs:381-390`

`decryptor` here is the `recipient` argument passed into `BlameMachine::blame` / `AdditionalBlameMachine::blame` (lib.rs:623-632, 674-682), which forwards both `sender` and `recipient` verbatim into `blame_internal` (lib.rs:575-609). Nothing bounds `recipient` or `sender` to `1..=n`. `Participant` is just a non-zero `u16`, so an accusation naming `recipient = Participant::new(n + 1)` — or a `sender` not in the `commitments` map (lib.rs:599, `self.commitments[&sender]`) — hits a missing map entry and panics on `HashMap`'s `Index` impl, exactly mirroring the TensorFlow pattern where the second `.find` result is dereferenced unconditionally.

Notably, the panic at `enc_keys[&decryptor]` occurs while *constructing* the arguments to `dleq.verify`, so it triggers even with a garbage `EncryptionKeyProof`. The only prerequisite is `msg.pop.verify` succeeding (encryption.rs:374-379), which any party can satisfy because the PoP is a Schnorr proof over a fresh ephemeral `msg.key` whose discrete logarithm the attacker chooses — `pop_challenge` binds `from` and the message bytes, not a registered key (encryption.rs:302-324).

### Impact Explanation

Evaluating a blame accusation is a public-input-driven path: the accusation `(sender, recipient, msg, proof)` is a message any participant (or third party, via `AdditionalBlameMachine`, which explicitly supports non-members: lib.rs:639-661) causes the node to process. A single crafted accusation deterministically panics the honest node mid-DKG, aborting the key-generation session on that node — an availability failure directly analogous to the reference advisory's CVSS A:H null-deref. Because `blame` consumes/inspects state machines, repeated crashes prevent an honest validator from completing the DKG or attributing fault, and `AdditionalBlameMachine::blame` can be invoked by integrations adjudicating accusations from parties that were never registered.

### Likelihood Explanation

The attacker needs only to trigger a blame evaluation with an out-of-range index — no valid DKG membership, threshold cooperation, or correct proof is required. Crafting a valid `pop` is free (pick `key`, sign a Schnorr PoP over the transcript). This is reachable whenever the deployment exposes blame adjudication over accusations it did not itself originate — the documented purpose of `AdditionalBlameMachine` is precisely third-party blame evaluation.

### Recommendation

Validate `sender` and `recipient` against the registered set before indexing: in `decrypt_with_proof`, use `enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`; in `blame_internal`, use `commitments.get(&sender)` and return the accuser (`recipient`) as faulty when the sender isn't a known participant. `AdditionalBlameMachine::new` should also reject `sender`/`recipient` indexes outside `1..=n` at the `blame` entry point.

### Proof of Concept

```rust
// n = 4 participants run a PedPoP DKG to BlameMachine state, or a third
// party builds AdditionalBlameMachine::new(context, 4, commitment_msgs).

// Attacker (any party, member or not) crafts an EncryptedMessage:
let key = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let pub_key = C::generator() * key.deref();
let nonce = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let pub_nonce = C::generator() * nonce.deref();
// pop verifies because the attacker knows `key`'s discrete log:
let pop = SchnorrSignature::sign(&key, nonce,
  pop_challenge::<C>(context, pub_nonce, pub_key, sender_label, &msg_bytes));
let msg = EncryptedMessage { key: pub_key, pop, msg: arbitrary_bytes };

// Accusation names a recipient that was never registered (5 > n = 4):
let recipient = Participant::new(5).unwrap();
// blame() -> blame_internal() -> decrypt_with_proof():
//   msg.pop.verify(...) passes (valid PoP)
//   proof is Some(anything) -> self.enc_keys[&5] -> PANIC: key not found
machine.blame(Participant::new(2).unwrap(), recipient, msg, Some(fake_proof));
```

Root-cause lines: `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388` and `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599`, reached via `blame_internal` (lib.rs:575-609) from `BlameMachine::blame` / `AdditionalBlameMachine::blame`.

Caveat: I could not fully trace how higher layers route accusation fields into `blame()` (the `processor/` callers are outside the permitted scope), so whether an accuser can freely choose `recipient` in the deployed wiring is inferred from the library API surface — within the in-scope crates, the missing bounds check and the panic itself are confirmed.
