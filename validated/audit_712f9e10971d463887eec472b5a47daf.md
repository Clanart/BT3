### Title
Unbounded first-reward payout from uninitialized `PreviousStateMachineHeight` baseline in `pallet-consensus-incentives` - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`Pallet::calculate_reward` computes a relayer's consensus-update reward as `(latest_height - baseline) * block_cost`, where `baseline` falls back through two uninitialized-default layers: `LastRewardedHeight::get(id).unwrap_or(previous_height)` and, on the host side, `previous_commitment_height` itself is seeded from `PreviousStateMachineHeight::<T>::get(height.id).unwrap_or_default()` (i.e. `0`) the first time any commitment is stored for that `StateMachineId`. This mirrors the reported bug class exactly: a variable (`time2fullredemption` there, `PreviousStateMachineHeight`/`LastRewardedHeight` here) is left at its zero default and only gets meaningfully initialized after the first execution, causing wildly different — and here, exploitable — behavior on the very first reward computation for a state machine.

### Finding Description
`store_latest_commitment_height` in `modules/pallets/ismp/src/host.rs:229-234` runs on every consensus update:
```rust
fn store_latest_commitment_height(&self, height: StateMachineHeight) -> Result<(), Error> {
    let previous_height = LatestStateMachineHeight::<T>::get(height.id).unwrap_or_default();
    PreviousStateMachineHeight::<T>::insert(height.id, previous_height);
    LatestStateMachineHeight::<T>::insert(height.id, height.height);
    Ok(())
}
``` [1](#0-0) 

On the very first `StateMachineUpdated` ever recorded for a given remote chain, `LatestStateMachineHeight` is unset, so `previous_height = 0` gets written into `PreviousStateMachineHeight` regardless of what the actual remote-chain block height is (remote heights are typically large, e.g. millions for an Ethereum-style chain, since they reflect the source chain's own block counter, not a local index starting at 0).

`pallet-consensus-incentives::calculate_reward` then uses this same zero-seeded value as the reward baseline whenever `LastRewardedHeight` is also unset (i.e., before this state machine has ever been rewarded):
```rust
let previous_height =
    host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
let reward = blocks_as_balance.saturating_mul(block_cost);
``` [2](#0-1) 

This is invoked from `process_message`/`on_executed`, which pays out directly from the treasury with no upper bound check:
```rust
T::Currency::transfer(
    &T::TreasuryAccount::get().into_account_truncating(),
    &relayer_account,
    reward,
    Preservation::Expendable,
)
``` [3](#0-2) 

So whenever governance configures `StateMachinesCostPerBlock` for a state machine (new chain onboarding, or re-adding a chain via `update_cost_per_block` after `remove_incentives` cleared it), the *very first* consensus update processed afterward computes `blocks = latest_height - 0 = latest_height` — the raw remote block height itself — instead of the small span actually delivered since the last update. Multiplied by `block_cost`, this can produce a reward orders of magnitude larger than intended, paid to whichever relayer happens to submit that first update.

### Impact Explanation
This is a treasury drain / incorrect fund transfer: an ordinary, unprivileged relayer submitting a legitimate consensus proof (no malicious peer, prover, or admin required) can trigger a single payout sized to the entire historical block height of the remote chain rather than the actual delta covered by the proof. `Preservation::Expendable` on the transfer means it will drain the treasury account up to its full reducible balance for one lucky/opportunistic relayer, and `LastRewardedHeight` is then set to `latest_height`, permanently consuming the "first reward" window — the bug cannot self-correct after the fact. This matches the bounty's "stealing or loss of funds" and "logic attacks" categories, since the corrupted value is `PreviousStateMachineHeight`/the derived `baseline`, not any compromised off-chain actor.

### Likelihood Explanation
The trigger condition is a standard, expected operational sequence rather than an edge case: any time governance calls `update_cost_per_block` for a state machine that has already produced at least one `StateMachineUpdated` event before incentives were configured (the normal onboarding order — a chain's light client is typically live before its relayer-incentive economics are turned on), or after a prior `remove_incentives` + re-add cycle, the next relayer to deliver a consensus message collects the inflated reward. No special privileges or race conditions beyond "be the relayer who submits the next message" are needed.

### Recommendation
Do not fall back to `0`/`unwrap_or_default()` as an implicit baseline. When `LastRewardedHeight` is unset for a state machine, either (a) seed `LastRewardedHeight` to `latest_height` at the moment `update_cost_per_block` is called (so the first reward window is empty and rewards only accrue from that point forward), or (b) explicitly reject/zero-cap `calculate_reward` when no prior watermark exists rather than substituting `previous_commitment_height`'s own zero-default. `PreviousStateMachineHeight` should likewise avoid writing `0` as a sentinel for "no previous height" — use an `Option`/`OptionQuery` end-to-end so "never seen before" is distinguishable from "previous height was legitimately 0".

### Proof of Concept
1. Governance registers a new state machine's consensus client; a relayer submits several consensus updates over time (normal operation), advancing `LatestStateMachineHeight[id]` to, say, height `5,000,000` (a realistic Ethereum block height), with `PreviousStateMachineHeight[id]` correspondingly non-zero-but-unused since incentives aren't configured yet.
2. Governance calls `pallet-consensus-incentives::update_cost_per_block(id, cost_per_block)` to turn on incentives for the chain — this only writes `StateMachinesCostPerBlock`, it does not touch `LastRewardedHeight`, which remains `None`. [4](#0-3) 
3. Any relayer submits the next legitimate consensus proof, advancing the height slightly (e.g., to `5,000,050`). `store_latest_commitment_height` sets `PreviousStateMachineHeight[id] = 5,000,000` (the true previous height, fine here) — but if instead this is the chain's very *first-ever* commitment (fresh state machine onboarding with cost pre-configured), `previous_commitment_height` returns the `unwrap_or_default() = 0` value shown at `modules/pallets/ismp/src/host.rs:230`.
4. `calculate_reward` computes `baseline = LastRewardedHeight::get(id).unwrap_or(previous_height) = 0` (since no reward has ever been recorded), then `blocks = latest_height.saturating_sub(0) = latest_height` (e.g., `5,000,000`), and `reward = 5,000,000 * block_cost` — paid in full from the treasury to the submitting relayer in one transaction. [5](#0-4) 
5. `LastRewardedHeight[id]` is then set to `5,000,000`, so the inflated payout cannot be reproduced again, but the one-time drain has already occurred.
