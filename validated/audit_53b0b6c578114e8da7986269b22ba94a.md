## Finding: SSRF via unauthenticated on-chain DataLayer mirror coin URLs

### Title
Server-Side Request Forgery via Attacker-Controlled Mirror URLs in DataLayer Subscription Sync - (File: `chia/data_layer/data_layer_wallet.py`, `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`)

### Summary
Any unprivileged chain participant can create a "mirror coin" for **any** DataLayer store id (launcher id) that a victim node is subscribed to, embedding arbitrary attacker-chosen URLs in the coin's memos. The victim `DataLayerWallet` picks up this coin purely because the launcher id is tracked — with no check that the spender owns or controls that store — and persists the URLs as legitimate mirror servers. The `DataLayer` service subsequently uses these URLs verbatim in outbound HTTP GET requests (`http_download`) during its periodic sync loop, giving an attacker SSRF against any host/port reachable from the victim's DataLayer/wallet process, analogous to the SSRF in mudler/localai's `/models/apply` endpoint (CVE-2024-6095), where an attacker-supplied URL is fetched by the server without validating the destination.

### Finding Description
`create_new_mirror()` builds a `CREATE_COIN` to the fixed, well-known `create_mirror_puzzle()` puzzle hash with memos `[launcher_id, *urls]` [1](#0-0) . This puzzle hash is public/derivable by anyone (`P2_PARENT.curry(Program.to(1))`), so **any wallet** can spend its own coins to create a mirror coin naming **any** launcher id and **any** URLs — there is no signature or ownership check tying the mirror to the actual DataLayer singleton owner.

When such a coin appears, `DataLayerWallet.coin_added()` decodes the mirror info from the parent spend and, if `is_launcher_tracked(launcher_id)` is true (i.e., the node is merely subscribed to that store — not necessarily the owner), inserts it as a trusted `Mirror` record with no URL validation: [2](#0-1) 

`DataLayer.update_subscriptions_from_wallet()` then pulls these URLs directly from wallet RPC and stores them as subscription servers for that store, with no scheme/host allow-listing: [3](#0-2) 

During the periodic `fetch_and_validate()` sync loop, one of these attacker-controlled URLs is selected (`random.shuffle(servers_info)`) and passed into `insert_from_delta_file()` → `download_file()` → `http_download()`: [4](#0-3) 

`http_download()` performs an unrestricted `aiohttp` GET to `server_info.url + "/" + filename` with no scheme or destination restriction: [5](#0-4) 

This is the exact bug class in the reference CVE: a server-side component fetches attacker-supplied URLs without restricting destination, enabling SSRF (and here, since `filename` is attacker-influenceable indirectly via the root-hash/generation naming scheme, potential probing of internal services). Unlike the localai case, this is not directly reachable via a single RPC call, but is reachable purely from chain data — an unprivileged spend-bundle submitter can trigger it against any DataLayer node that tracks/subscribes to the targeted store, without any interaction from the store owner.

### Impact Explanation
An attacker with only the ability to submit a spend bundle (create a coin to `create_mirror_puzzle()` with chosen memos) can cause any DataLayer node subscribed to the targeted store to issue outbound HTTP requests to attacker-chosen hosts/ports (e.g., internal admin services, cloud metadata endpoints, or other DataLayer/plugin servers on the private network). This is a network-reachable SSRF against DataLayer operators/subscribers, achieved entirely through normal on-chain coin creation with no privileged access, and does not require the attacker to control or own the targeted store's singleton.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment where DataLayer nodes subscribe to third-party/public stores (the intended use case for DataLayer mirrors/subscriptions). Creating the malicious mirror coin requires only a small amount of XCH for the coin creation and fee, and no coordination with the store owner. The victim's periodic `periodically_manage_data()` / `update_subscription()` loop will automatically pull and act on the malicious URL without any operator action.

### Recommendation
- Validate mirror URLs' scheme (restrict to `http`/`https`) and reject non-routable/internal address ranges (loopback, link-local, RFC1918 private ranges, cloud metadata IPs) before persisting them as subscription servers, similar to standard SSRF mitigations.
- Consider only trusting mirror URLs that come from mirror coins created/authorized by the DataLayer singleton owner (e.g., cross-check against `DataLayerStore`'s owned/`ours` bit) for automatic sync, and require explicit operator opt-in (e.g., via existing manual `subscribe` command) for third-party mirror URLs.
- Add configurable network egress restrictions (deny-list for private/link-local ranges) in `http_download()` and `get_downloader()`.

### Proof of Concept
1. Attacker identifies a DataLayer store `launcher_id` that a victim node tracks (e.g., by observing the victim's public offer activity or subscription list, or simply by owning/publishing a well-known dataset that victims subscribe to).
2. Attacker spends a small-value coin with `puzzle_reveal = create_mirror_puzzle()`, and a solution producing `CREATE_COIN` with memos `[launcher_id, b"http://169.254.169.254/latest/meta-data/", ...]` (or any internal victim-reachable host/port).
3. Once confirmed on-chain, the victim's `DataLayerWallet.coin_added()` stores this as a legitimate `Mirror` for `launcher_id` (no ownership check) [6](#0-5) .
4. On the victim's next `update_subscription()`/`fetch_and_validate()` cycle, the malicious URL may be selected as `server_info.url`, and `http_download()` issues a GET to that internal/attacker-chosen destination [7](#0-6) .

        self, coin: Coin, height: uint32, peer: WSChiaConnection, coin_data: object | None, sync_scope: WalletSyncScope

            parent_state: CoinState = (

            )[0]
            parent_spend = await fetch_coin_spend(height, parent_state.coin, peer)
            assert parent_spend is not None
            launcher_id, urls = get_mirror_info(parent_spend.puzzle_reveal, parent_spend.solution)

                ours: bool = await self.wallet_state_manager.get_wallet_for_coin(coin.parent_coin_info) is not None
                await self.wallet_state_manager.dl_store.add_mirror(
                    Mirror(
                        coin.name(),
                        launcher_id,
                        uint64(coin.amount),
                        Mirror.decode_urls(urls),
                        ours,
                        height,
                    )
                )
                await self.wallet_state_manager.add_interested_coin_ids([coin.name()])

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
