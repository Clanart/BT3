## Title
Offer additions-cache silently drops CoinSpend entries on exception, causing `Offer.additions()`/`fees()`/`arbitrage()` to under-report offer contents - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.__post_init__` builds a per-coin-spend "additions" cache (`self._additions`) by calling `compute_spend_hints_and_additions()` for every `CoinSpend` in the offer's `SpendBundle`. If that call raises any exception other than `ValidationError` or the specific "cost exceeded" `ValueError`, the exception is silently swallowed and the loop `continue`s, leaving that coin spend entirely absent from `self._additions`.

### Finding Description
In `chia/wallet/trading/offer.py`: [1](#0-0) 
each `CoinSpend` is processed with:
```
try:
    hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
    ...
except ValidationError:
    raise
except ValueError as e:
    if e.args and e.args[0] == "cost exceeded or below zero":
        raise ValidationError(...)
    continue
except Exception:
    continue
```
Any other exception raised inside `compute_spend_hints_and_additions()` (`chia/wallet/util/compute_hints.py`) — for example an `AssertionError` from `assert rf is not None` on line 53, or an `IndexError`/`StopIteration` from malformed condition atoms produced by an adversarially crafted puzzle — is caught by the bare `except Exception: continue` and the coin spend is dropped from `adds`, with no error surfaced to the caller.

`self._additions` is treated as authoritative downstream:
- `additions()` [2](#0-1)  flattens it to compute all offer additions.
- `fees()` [3](#0-2)  computes `amount_in - amount_out` using `additions()`, explicitly documented as "Unsafe to use for fees validation!!!" but still used elsewhere as a heuristic.
- `_get_offered_coins()` indexes `self._additions[parent_spend.coin]` directly by dict key [4](#0-3) , and `get_offered_amounts()`/`arbitrage()` build the offered/requested summary that a wallet user reviews before accepting an offer [5](#0-4) .

This is structurally the same bug class as CVE-2021-26930: an error encountered while establishing per-object state (grant mapping in Xen; per-coin-spend additions here) is discarded, and the caller's cached/committed view silently proceeds as if the operation succeeded for that entry — later code (offer summary, fee/arbitrage computation, offered-coin matching) then operates on an incomplete view without ever being told an error occurred.

### Impact Explanation
If a malicious offer counterparty can craft a `CoinSpend` whose puzzle produces a `CREATE_COIN` condition that trips the specific `assert` in `compute_spend_hints_and_additions` (e.g. a condition where `rf` legitimately fails the atom assumption, or the CLVM structure otherwise raises a generic Python exception rather than a `ValidationError`), that coin spend's real coin creations vanish from `Offer._additions`. Since `_bundle.additions()`/actual on-chain execution would still create those coins (the bundle itself is unaffected — only the wallet-side cache is wrong), the offer summary shown to the accepting wallet (`get_offered_amounts()`, `arbitrage()`, `fees()`) can misrepresent what the offer actually does, potentially hiding additional value extraction or additional requested/offered coins from the receiving party's review before they sign/accept. This falls under "offer settlement theft" via a spend-triggered mismatch between the accepted/displayed offer state and true chain effects.

### Likelihood Explanation
Exploitability depends on being able to reliably trigger a raw (non-`ValidationError`, non-cost) exception from `compute_spend_hints_and_additions()` via puzzle/solution content controlled by the offer creator — e.g. hitting the `assert rf is not None` at line 53 of `compute_hints.py`, or other unhandled `Program.at()` failures on unusual condition shapes. I could not fully verify from the available code whether `condition.at("rf")` can actually be coerced to `None` (and thus trip the assertion) for a crafted-but-otherwise-valid CREATE_COIN condition produced by a standard puzzle a wallet would agree to display/parse; this requires further testing/fuzzing of `compute_spend_hints_and_additions()` with adversarial CLVM condition trees to confirm exploitability, which is a known limitation of static review here.

### Recommendation
- Do not use a bare `except Exception: continue` when populating `Offer._additions`. Any exception other than the explicitly handled cost-exceeded case should be treated as a hard failure (raise), matching the intent already shown by the `ValidationError` re-raise path, so an offer whose additions cannot be fully computed is rejected rather than silently under-represented.
- Apply the same fix to the analogous swallow-and-continue pattern in `Offer.conditions()` [6](#0-5) , which has the identical `except Exception: continue` pattern feeding `valid_times()`/`absolute_valid_times_ban_relatives()`.
- Add tests that construct a `CoinSpend` whose puzzle triggers each specific exception path in `compute_spend_hints_and_additions()` and assert that `Offer` construction fails closed instead of silently omitting the spend's additions.

### Proof of Concept
Not independently confirmed end-to-end; conceptual PoC requires constructing an `Offer` whose bundle includes a `CoinSpend` with a puzzle/solution producing a `CREATE_COIN` condition where `condition.at("rf")` is `None` (or another spot in `compute_spend_hints_and_additions` raises a bare exception), then showing that `offer.additions()` / `offer.get_offered_amounts()` omit the coin(s) actually created by that spend when the bundle is executed on-chain — i.e. that the wallet-displayed offer summary diverges from the bundle's real effects. Constructing such a puzzle and confirming the divergence was not completed within the scope of this review.

    def arbitrage(self) -> dict[bytes32 | None, int]:
        """
        Returns a dictionary of the type of each asset and amount that is involved in the trade
        With the amount being how much their offered amount within the offer
        exceeds/falls short of their requested amount.
        """
        offered_amounts: dict[bytes32 | None, int] = self.get_offered_amounts()
        requested_amounts: dict[bytes32 | None, int] = self.get_requested_amounts()

        arbitrage_dict: dict[bytes32 | None, int] = {}
        for asset_id in [*requested_amounts.keys(), *offered_amounts.keys()]:
            arbitrage_dict[asset_id] = offered_amounts.get(asset_id, 0) - requested_amounts.get(asset_id, 0)
