### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new`/`view()` lets a small untrusted serialization cause billions of scalar operations - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts an attacker-controlled `n` (a `u16` up to 65535) and then calls `ThresholdKeys::new`, which evaluates a Lagrange `interpolation_factor` — an `O(included.len())` loop of field multiplications — once per participant in `1..=t`, giving `O(t·n)` work. `ThresholdKeys::view` repeats the same per-participant interpolation for every member of `included`. An unprivileged party feeding crafted bytes to `ThresholdKeys::read` therefore induces CPU work quadratic in a value they choose, directly analogous to the OBI replay loop whose cost scaled with an uncapped recorded count rather than the size of the input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` from the byte stream and, for `Interpolation::Lagrange`, reads `n` verification shares before calling `ThresholdKeys::new` [1](#0-0) . Inside `new`, the group key is computed by summing `verification_shares[i] * interpolation_factor(i, t-list)` over `1..=t` [2](#0-1) , where `interpolation_factor` for `Lagrange` iterates over every element of `included`, performing two field multiplications and a final inversion per call [3](#0-2) . The same `O(len²)` pattern recurs in `view()`, which recomputes `interpolation_factor` once for the local share and once per included participant [4](#0-3) .

`n` is bounded only by `u16::MAX` (`Participant` is a non-zero `u16` [5](#0-4) ; `ThresholdParams::new` only checks `t <= n` [6](#0-5) ). With `t = n = 65535`, a ~2 MB input causes ~4.3×10⁹ field multiplications plus 65535 inversions inside a single `read` call — CPU cost scales with the square of the declared participant count, not with the bytes consumed.

### Impact Explanation
Any service that deserializes `ThresholdKeys` (or calls `view()` on a deserialized key) from bytes influenced by an untrusted party — e.g., key material or signing-set data relayed in a protocol message — can be forced to spend CPU time quadratic in the attacker-chosen `n`. Repeated submissions amplify this into a persistent denial of service of the threshold-signing/key-management path, matching the availability impact of the original advisory (CPU exhaustion in a privileged component driven by attacker-controlled counts).

### Likelihood Explanation
Reachability requires the deployment to call `ThresholdKeys::read`/`view` on attacker-influenced bytes, which is the explicit untrusted-input surface contemplated for these APIs. No secret, signature position, or honest-participant cooperation is needed — only control of the serialized parameters `t` and `n` and enough trailing bytes to satisfy `n` point reads (~2 MB at max). Work factor is high (quadratic blowup from a small input), but each request is cheap to produce, and verification-equivalent CPU work in `view()` is additionally re-done on every signing attempt.

### Recommendation
Enforce a protocol-level maximum on `n`/`t` (and on `included.len()`) well below `u16::MAX` in `ThresholdParams::new`, `ThresholdKeys::new`, `ThresholdKeys::read`, and `ThresholdKeys::view`. Alternatively, precompute all Lagrange interpolation factors in `O(n)` via the standard prefix-product/total-product trick instead of an `O(n)` inner loop per participant, reducing `new`/`view` to linear work.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dalek_ff_group::Ed25519; // any in-scope ciphersuite
use frost::{Participant, ThresholdKeys}; // dkg::ThresholdKeys

fn malicious_bytes() -> Vec<u8> {
    let mut buf = vec![];
    // curve ID len + ID
    buf.extend(&(Ed25519::ID.len() as u32).to_le_bytes());
    buf.extend(Ed25519::ID);
    // t = n = 65535, i = 1
    buf.extend(&65535u16.to_le_bytes());
    buf.extend(&65535u16.to_le_bytes());
    buf.extend(&1u16.to_le_bytes());
    // Interpolation::Lagrange
    buf.push(1);
    // secret_share + n verification shares (generator encodings)
    buf.extend(Ed25519::generator().to_bytes().as_ref()); // secret_share bytes (F repr)
    for _ in 0 .. 65535u32 {
        buf.extend(Ed25519::generator().to_bytes().as_ref());
    }
    buf
}

// ~2 MB input triggers ~4.3e9 field multiplications + 65535 inversions
// inside ThresholdKeys::new's group_key loop.
let _ = ThresholdKeys::<Ed25519>::read(&mut &malicious_bytes()[..]);
```

The same quadratic cost is re-incurred by `keys.view(included)` for a full `included` set, since each of the `n` verification shares gets an `O(n)` `interpolation_factor` evaluation [7](#0-6) .

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
