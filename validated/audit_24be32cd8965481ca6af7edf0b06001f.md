## Analog Identified: BalanceHandler Event-Index Desync on Nested/Reentrant Precompile Calls

### Title
StateDB/bank-ledger balance desync from nested precompile calls corrupting `BalanceHandler` event bookkeeping - (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The original report shows that HydraDX's EMA oracle only updates its internal state via *hooks* fired on specific entrypoints, and a bypass of that hook path (direct transfer) leaves the tracked state stale/inconsistent with real pool state. The Cosmos EVM analog is the `BalanceHandler` mechanism used to keep the EVM `StateDB` balances synchronized with `x/bank` ledger balances whenever a precompile performs a Cosmos-native balance change. That mechanism also relies on a "hook"-like bookmark (`prevEventsLen`) into the shared `sdk.Context` event log, and that bookmark can be silently invalidated when precompile execution nests (one precompile call triggering another precompile invocation before it finishes), producing a state where the `StateDB` balance diverges from the real `x/bank` balance.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current length of `ctx.EventManager().Events()` as `prevEventsLen`, and `AfterBalanceChange` later replays every bank `coin_spent`/`coin_received` (and precisebank fractional) event emitted after that index to update `StateDB` balances: [1](#0-0) 

This design implicitly assumes a single, non-reentrant Before/After cycle per EVM-visible balance-affecting call. However, `ctx.EventManager()`'s event slice is a single, continuously growing log shared across the whole transaction execution, and it is **not truncated or partitioned** when a precompile's native action itself triggers another precompile call (e.g., via `evmKeeper.CallEVMWithData`/`CallEVM` to an address that resolves to a precompile, including the same precompile recursively). If that happens while the outer call's `AfterBalanceChange` has not yet run, the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` cycle will consume and apply a sub-range of events `[N1:]`, and then the **outer** call's `AfterBalanceChange` — still holding its earlier bookmark `N0 < N1` — will iterate `events[N0:]` again, which **re-includes the same bank events already applied by the inner call**. This causes `stateDB.AddBalance`/`SubBalance` to be invoked twice for the same underlying bank coin movement, permanently desyncing `StateDB` balances from the real `x/bank` ledger (double-credit or double-debit).

The repository itself documents and reproduces exactly this defect: [2](#0-1) 

The reproduction wires a caller contract to recursively re-enter a precompile (`Call0` re-invokes the precompile address via `p.evmKeeper.CallEVMWithData`), each entry calling `p.GetBalanceHandler().BeforeBalanceChange`/`AfterBalanceChange`: [3](#0-2) [4](#0-3) 

Production precompiles (`staking`, `distribution`, `gov`, `ics20`, `slashing`, `erc20`) instead route through `Precompile.runNativeAction`, which allocates a **new** `BalanceHandler` per invocation via `BalanceHandlerFactory.NewBalanceHandler()` rather than reusing a stored instance: [5](#0-4) 

Because a fresh handler instance is used, the "shared instance" framing of the bug (as demonstrated by the debug precompile) is specific to that test-only helper (explicitly documented as "*not* for use in production"). What is **not shared** across calls (each nested call gets its own `prevEventsLen` bookmark), but what **is** shared and never partitioned, is the underlying `ctx.EventManager().Events()` slice itself. Any production precompile whose native action nests into another precompile invocation before its own `AfterBalanceChange` runs would hit the same double-application-of-events pattern described above, because the outer bookmark is computed *before* the nested call and the events slice is not sliced/cleared after the nested call finishes.

### Impact Explanation
If reachable from a production precompile's native action (i.e., any code path where a precompile's execution internally triggers `CallEVM`/`CallEVMWithData` to another precompile address, or itself, before returning), this results in `StateDB` balances being credited or debited twice relative to the actual `x/bank` movement for the same coins. This is a duplication/corruption of spendable value: an account's EVM-visible balance can become permanently inflated beyond what is actually backed in `x/bank`, letting it be spent in subsequent EVM operations without real backing — or a sender's balance could be double-debited, effectively destroying/freezing funds relative to the real ledger. Both outcomes fall squarely under "unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances/EVM balances" and "permanent freezing/theft of user funds."

### Likelihood Explanation
Confirmed root cause and reproduction exist in-tree via the debug precompile test, showing the underlying defect is real and exercisable through an ordinary EVM transaction (a contract calling a precompile that recursively/nestedly calls a precompile again). However, I could not, within the available search budget, conclusively identify a production (non-debug) precompile code path where a precompile's own native action nests into another precompile call before its `AfterBalanceChange` executes — the production precompiles inspected (`staking`, `distribution`, `gov`, `ics20`, `slashing`, `erc20`) appear to call bank/erc20 *keepers* directly rather than re-entering the EVM through `CallEVM` into another precompile address mid-action. Confirming or ruling out a concrete production trigger (e.g., an ERC20-token-pair precompile address being called from within another precompile's native action, or a contract-orchestrated reentrant sequence across two different precompiles within one nested call frame) requires deeper tracing of `x/vm` keeper's precompile dispatch and `CallEVM` call sites, which I was unable to complete before the iteration limit.

### Recommendation
- Make the event-index bookmark reentrancy-safe: instead of a raw index into a shared, ever-growing event log, snapshot and consume (e.g., truncate/mark-processed) exactly the events produced by the current call, or use a call-depth-aware stack of bookmarks so a nested call's processed range is excluded from the outer call's range.
- Add an explicit reentrancy guard preventing precompiles from being re-entered (directly or via another precompile) while a `BeforeBalanceChange`/`AfterBalanceChange` cycle is still open for a given EVM call stack.
- Promote `evmd/tests/integration/balance_handler` into a required regression test also exercised against production precompiles that can trigger nested `CallEVM` invocations, not only the debug-only helper.

### Proof of Concept
The in-repo `TestRecursivePrecompileCallsWithDebugPrecompile` test is the working PoC vehicle for the underlying mechanism: [6](#0-5) 

It deploys a caller contract that invokes the debug precompile's `callback` method, which recursively re-enters the same precompile address via `CallEVMWithData`, each entry running its own `BeforeBalanceChange`/`AfterBalanceChange` cycle against the same growing `ctx.EventManager()` event log — demonstrating the exact desync mechanism that would corrupt `StateDB` balances relative to `x/bank` if triggered on a real value-transferring precompile path.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}
