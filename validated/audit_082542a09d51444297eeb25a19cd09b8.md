### Title
Ed448 point decoding accepts non-prime-order torsion points - (File: crypto/ed448/src/point.rs)

### Summary
Ed448 point deserialization intended to reject torsion components, but `Point::is_torsion_free` computes `(-1)P + P`, which is identity for every curve point. As a result, any canonically encoded valid curve point, including non-prime-order points, is accepted while `Point` still claims the `PrimeGroup` contract.

### Finding Description
`Point::is_torsion_free` evaluates `self * (Scalar::ZERO - Scalar::ONE) + self`. Since `Scalar::ZERO - Scalar::ONE` is `-1` modulo the prime subgroup order, this expression is always `-P + P = identity`, independent of whether `P` has a torsion component. [1](#0-0) 

`GroupEncoding::from_bytes` gates acceptance on this always-true check after decoding `y`, recovering `x`, and rejecting negative zero. [2](#0-1) 

The accepted type is explicitly marked as a prime-order group even though the decoder can return points outside the prime-order subgroup. [3](#0-2) 

This reaches untrusted input through `Ciphersuite::read_G`, which accepts any point returned by `from_bytes` whose re-encoding is canonical. [4](#0-3) 

### Impact Explanation
An unprivileged party can submit canonically encoded Ed448 torsion points to public-key, commitment, proof, or signature decoding paths. Those points violate the `PrimeGroup` assumption used by Schnorr verification, DLEq proofs, and FROST nonce/commitment processing.

In particular, Schnorr verification assumes the equation `R + cA - sG = 0` is evaluated over a prime-order group. [5](#0-4)  Accepted torsion components introduce a small-order subgroup not represented by the scalar field, invalidating that verifier formula and permitting torsion-adjusted statements that cannot exist under the advertised prime-group model. This is an incorrect verifier validation formula rather than an integrator-misuse issue.

### Likelihood Explanation
The malformed input is only a valid canonical Ed448 point encoding with a nonzero torsion component. `read_G` performs no independent subgroup or cofactor clearing check, and Ed448’s `Curve::read_G` wrapper rejects only the identity. [6](#0-5) 

The repository already contains a torsion-bearing Ed448 test case, demonstrating that such points are constructible from public information. [7](#0-6)  Exploitation requires a protocol path that accepts attacker-controlled Ed448 public inputs and relies on prime-order verification semantics.

### Recommendation
Replace `is_torsion_free` with a check that multiplies the candidate point by the actual prime subgroup order and verifies the result is identity, or equivalently multiply by the Ed448 cofactor and verify the result is nonzero/prime-subgroup-consistent according to the encoding policy. Add a regression test asserting that the existing torsion fixture and all nonzero small-order encodings are rejected by `Ed448::read_G`.

### Proof of Concept
The defect is directly visible in the validation expression:

```rust
// crypto/ed448/src/point.rs
fn is_torsion_free(&self) -> Choice {
  ((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
}
```

Because scalar arithmetic is modulo the subgroup order:

```text
Scalar::ZERO - Scalar::ONE = -1

(-1)P + P = identity
```

Therefore `is_torsion_free(P)` returns true for every `P`, including a nonzero point of order dividing the Ed448 cofactor. A canonical encoding of such a point passes `Point::from_bytes`, then passes `Ciphersuite::read_G` because its canonical re-encoding matches. The resulting `Point` is treated as `PrimeGroup` and enters `SchnorrSignature::read`, `DLEqProof::read`, FROST `Commitments::read`, and verification paths even though it is outside the prime-order subgroup.
