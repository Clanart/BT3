## Title
Silent local git remote hijack via stale GitHub-repository association after upstream owner/name squatting - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop automatically rewrites a local repository's `origin` remote URL whenever it detects that the associated GitHub repository's `clone_url` (fetched from the API) differs from what's stored locally, under the assumption this only happens on legitimate repository renames. The repository lookup that feeds this logic (`matchGitHubRepository`) is performed by re-parsing the **existing, potentially stale** local remote URL's `owner/name`, not by any stable GitHub repository ID. If the real `owner/name` combination is abandoned (e.g., the original owner renames their account/repo or deletes it) and later re-registered by an attacker, Desktop's periodic re-association logic will fetch the attacker's repository data and silently rewrite the user's local git remote to point at it.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` re-associates a tracked repository with a GitHub repository by calling `matchGitHubRepository`, which parses the **current local remote URL** to extract `owner`/`name`: [1](#0-0) 

It then fetches that repository from the API strictly by `owner`/`name` (not by the previously stored `dbID`): [2](#0-1) 

The fetched `apiRepo` (an attacker-influenceable "GitHub API object" if the `owner/name` has been re-registered by someone else) is passed straight into `updateRemoteUrl`, which decides whether to silently rewrite the local git remote: [3](#0-2) 

The guard logic only checks:
1. That the git protocol (http vs ssh) of old/new URLs match,
2. That the *previous* cached `gitHubRepository.cloneURL` still matches the *current* local remote (i.e. the user hasn't manually edited the remote),
3. That the new URL differs from the current one.

There is no check that the underlying GitHub repository is *the same repository* (e.g. via a stable numeric ID) across the old and new state — it is purely inferred by string-matching `owner/name` from the remote URL. The `TODO` comment at the association callsite even acknowledges this limitation explicitly: [4](#0-3) 

This function is invoked from multiple normal-usage triggers, including sign-in/account changes, background repository refreshes, and after fetch operations, without prompting the user: [5](#0-4) 

### Impact Explanation
If the `owner/name` pair previously associated with a legitimate GitHub repository becomes squattable (owner renames their account, repository is renamed/deleted/transferred and someone else claims the old name), the next time Desktop performs this GitHub-repository re-association, it fetches an attacker-controlled repository object and silently sets the user's real `origin` remote to the attacker's clone URL — with no dialog or confirmation, unlike the explicit `AddSSHHost`/`GenericGitAuthentication` prompts used for genuinely trust-sensitive changes elsewhere in the codebase. All subsequent pushes from Desktop (and, since the underlying git config is modified, subsequent CLI operations) will go to the attacker's repository instead of the intended one, silently corrupting/exfiltrating what the user pushes (`_performPush` uses `gitStore.defaultRemote`/`currentRemote` derived straight from git config, with no independent verification against the previously known-good URL): [6](#0-5) 

This matches the "silent corruption of what the user commits or pushes" impact category, since the compromise is invisible to the user — the UI shows the repository under its familiar name/dbID, while the actual git remote now points elsewhere.

### Likelihood Explanation
The trigger conditions require the attacker to control the `owner/name` slot previously used by the real repository (classic "repo/account name squatting" / rename hijack) — this does not require local access, malware, or leaked credentials, only that the victim's Desktop performs this normal automatic re-association at some point after the takeover (which happens routinely on account sign-in/out and periodic repository refresh, per `refreshSelectedRepositoryAfterAccountChange`). This is a realistic and previously well-known class of GitHub abuse (dependency/URL "repo-jacking"), making the likelihood moderate rather than purely theoretical, though it depends on external conditions (name being freed and re-claimed) outside Desktop's control.

### Recommendation
Do not silently trust `owner/name`-based re-matching as proof of repository identity continuity. When re-associating and considering an automatic remote URL rewrite:
- Verify the fetched API repository's stable numeric `id` (and/or `node_id`) matches the one previously stored for the local `GitHubRepository.dbID` mapping before treating the new `clone_url` as a legitimate rename.
- If the ID does not match (or was never recorded), require explicit user confirmation before rewriting `origin`, similar to the confirmation dialogs already used for `AddSSHHost`/`GenericGitAuthentication`.

### Proof of Concept
1. Victim clones `https://github.com/legituser/legitrepo` in GitHub Desktop; Desktop stores the `GitHubRepository` association (dbID, cloneURL, etc.).
2. `legituser` renames their account or the repository, freeing `legituser/legitrepo` (or deletes the account/repo entirely).
3. Attacker registers a new GitHub account/repo reusing the freed `legituser/legitrepo` slug, with any `clone_url` they control.
4. Victim's Desktop later performs any operation that calls `repositoryWithRefreshedGitHubRepository` (e.g., signs out/in, or Desktop performs a background refresh) — `matchGitHubRepository` re-parses the *still-unchanged local remote URL* `https://github.com/legituser/legitrepo`, fetches this owner/name from the API, and gets the attacker's repository data.
5. `updateRemoteUrl` finds `remoteUrlUnchanged === true` (local remote still matches old cached cloneURL) and `urlsMatch === false` (attacker's actual clone_url differs), satisfying `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, and silently calls `gitStore.setRemoteURL('origin', attackerCloneUrl)`.
6. Victim's next `git push` (via Desktop or CLI, since `.git/config` was modified) sends code to the attacker-controlled repository without any warning.

This chain could not be fully verified end-to-end in a live environment (no execution sandbox available), and the exact set of user actions that trigger `repositoryWithRefreshedGitHubRepository` in the current build is inferred from the callers found in `app-store.ts`; a Devin session with repo access should confirm reachability from a normal user flow (e.g., app relaunch/sign-in) to fully validate exploitability.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
