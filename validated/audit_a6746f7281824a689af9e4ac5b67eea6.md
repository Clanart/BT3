### Title
`rewards()` view method in the distribution precompile lacks a non-payable check, permanently stranding any native value sent with the call - (`precompiles/distribution/distribution.go`)

### Summary
The `distribution` precompile (`0x0000000000000000000000000000000000001007`) dispatches every state-changing and query method through `Execute`. Every other query/tx method validates that `msg.value == 0` via `pcommon.ValidateNonPayable` (directly, or through the shared `p.validateInput` helper), but the `RewardsMethod` branch calls `p.rewards(ctx, method, args)` directly with no such check, so a value-bearing call to `rewards(address)` succeeds instead of reverting.

### Finding Description
In `Execute`, each dispatch case guards against unexpected value transfers: [1](#0-0) [2](#0-1) 

`ValidatorOutstandingRewardsMethod`, `ValidatorCommissionMethod`, `DelegationRewardsMethod`, etc. all route through `p.validateInput`, which calls `pcommon.ValidateNonPayable(value)`: [3](#0-2) 

But `RewardsMethod` calls `p.rewards(ctx, method, args)` — `value` isn't even passed into the function, and `p.rewards` itself never checks it: [4](#0-3) 

This gap is explicitly documented as a known quirk in the precompile integration-test suite (the test author chose to skip the standard "view rejects value" assertion for exactly this reason): [5](#0-4) 

When an EOA or contract sends an EVM transaction with `value > 0` to `0x…1007` calling `rewards(address)`, the EVM's normal `CALL`-with-value semantics move the wei/usei balance from the caller to the precompile's associated account before the precompile logic runs. Since `rewards()` is a pure query that only reads and packs `DelegationTotalRewardsRequest` data — it never forwards, refunds, or otherwise accounts for the received value — the transferred value settles on the precompile address and is never recoverable by the sender or by any subsequent logic path, since the precompile address is not a normal contract/module account that any withdrawal message can target.

### Impact Explanation
This is a direct fund-loss analog to the reported bug class: the report's core defect is a code path that lets value move into a location from which it can never be extracted, because the responsible validation/handoff was omitted. Here, any usei sent alongside a `rewards()` call is permanently and unrecoverably locked, matching the "concrete fund loss or permanent freezing" acceptance criterion. Every unassociated or associated EVM caller who accidentally (or via a buggy dApp/wallet integration that attaches value to all precompile calls) sends value with a `rewards()` query loses that value permanently.

### Likelihood Explanation
Likelihood is moderate: the `rewards()` view is a commonly-called read method (used by wallets/dashboards to display delegator rewards), and any integration that defaults to attaching `msg.value` (e.g., a generic contract wrapper that forwards `msg.value` to every call, or a fee/tip pattern) will trigger the loss without any revert warning the caller that something is wrong. Because the call succeeds and returns valid data, there's no error signal — the sender has no indication that their attached value was lost.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` at the top of `RewardsMethod` dispatch in `Execute` (or inside `p.rewards`), consistent with every other query/tx method in this precompile, and add a `TxNode`/`ValidateNonPayable` doc requirement + a regression test asserting `rewards()` reverts when called with nonzero value.

### Proof of Concept
1. Associate an EVM account and fund it with usei.
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and `msg.value = 1000000000000` wei (1 usei) attached.
3. Observe the transaction succeeds and returns valid `Rewards` data.
4. Observe that the sent usei is deducted from the sender's balance and is not reflected anywhere retrievable — no corresponding module/account balance increase that any message can withdraw, confirming the funds are permanently stranded.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
