### Title
Merge executes against the live branch ref instead of the previewed commit, allowing a stale/attacker-influenced merge preview - (File: `app/src/lib/stores/app-store.ts`, `app/src/lib/git/merge.ts`)

### Summary
### Finding Description
`MergeChooseBranchDialog` computes a merge preview (clean/conflicted, conflicted file list, commit count) via `determineMergeability` against a specific branch tip, and only refreshes it if `this.state.selectedBranch?.tip.sha !== branch.tip.sha` [2](#0-1) . When the user clicks "Merge," `start()` calls `dispatcher.mergeBranch(repository, selectedBranch, mergeStatus, ...)` passing the `Branch` object captured at preview time [3](#0-2) .

That flows into `AppStore._mergeBranch`, which calls `gitStore.merge(sourceBranch, ...)` [4](#0-3) , which in turn calls `merge(this.repository, branch.name, ...)` in `git-store.ts` [5](#0-4) . Critically, the underlying `merge()` git wrapper invokes `git merge <branch.name>` — i.e., it resolves the branch **by name**, not by the specific SHA that was validated during the preview [6](#0-5) .

Between the moment the preview is computed and the moment the user clicks "Merge," `BackgroundFetcher` can silently fetch and update the same remote-tracking ref (e.g. `origin/feature`) that is the merge source [7](#0-6) , and `fastForwardBranches`/`_refreshRepository` update local tracking state without any user interaction [8](#0-7) . Because the merge operation resolves `branch.name` at execution time rather than pinning to `sourceBranch.tip.sha`, the actual commits merged into the user's history can differ from what the "clean merge / N conflicted files" preview showed and what the user approved — with no final check that the ref still points at the previewed SHA before executing the merge.

This is the direct structural analog of the reported issue: the preview (`determineMergeability`/`getAheadBehind`, analogous to `getAmountsOut`) computes an "expected outcome" that the user approves, but the actual state-changing operation (`git merge <name>`, analogous to `pair.swap`) re-resolves the mutable underlying value (the ref, analogous to reserves) at execution time with no `minAmountOut`-style guard comparing execution-time state to the previewed value.

### Impact Explanation
An attacker who controls the git server/remote/proxy for a branch the user is about to merge (e.g. a fork remote, a compromised or MITM'd `origin`, or a malicious upstream contributor with push access to the branch being merged) can update that branch between the time Desktop shows the merge preview and the time the user clicks "Merge." Since `git merge` re-resolves the branch name, GitHub Desktop will silently merge and commit whatever commits are present on the ref at execution time — potentially different, attacker-supplied content than what was reviewed as "clean" or "N conflicted files." This corrupts what the user actually commits/pushes without any error or warning, matching the report's core concern (execution-time value silently diverging from the value the user approved, with no guard to catch it).

### Likelihood Explanation
Requires no local access or credentials: it only requires the attacker to control content on a remote the user has added (a common scenario when merging feature/fork branches), or a MITM position on the git transport for that remote. `BackgroundFetcher`'s default polling interval (as low as 5 minutes, `MinimumInterval` in `background-fetcher.ts:17`) combined with the dialog remaining open while the user reviews the merge preview provides a realistic window for the ref to change before the user commits. This is not a DoS, not a dependency CVE, and does not require social engineering beyond the user's routine act of clicking "Merge" on a branch whose remote is attacker-influenced.

### Recommendation
Pin the merge target to the specific commit SHA that was validated by `determineMergeability`, not the mutable branch name. Either merge by SHA (`git merge <sha>`) or re-verify immediately before executing the merge that the branch's current tip SHA still equals `sourceBranch.tip.sha`, and abort/re-prompt the user if it has changed, analogous to a `minAmountOut` check.

### Proof of Concept
1. Add a remote/fork branch `origin/feature` at commit A with content that resolves the merge preview to "clean, no conflicts."
2. Open GitHub Desktop's Merge dialog and select `feature`; `MergeChooseBranchDialog.updateStatus` computes and displays a clean-merge preview for commit A.
3. While the dialog remains open (or during the momentary gap between click and execution), have the attacker-controlled remote force-update `feature` to point to commit B (malicious payload) — this can happen via the periodic `BackgroundFetcher` fetch, which runs independently of user action [9](#0-8) .
4. User clicks "Merge." `_mergeBranch` executes `git merge feature`, which now merges commit B, not the previously reviewed commit A, with no revalidation against the SHA shown in the preview [6](#0-5) .

  public start(withInitialSkew: boolean) {
    if (this.stopped) {
      fatalError('Cannot start a background fetcher that has been stopped.')
    }

    const gitHubRepository = this.repository.gitHubRepository
    if (!gitHubRepository) {
      return
    }

    if (withInitialSkew) {
      this.timeoutHandle = window.setTimeout(
        () => this.performAndScheduleFetch(gitHubRepository),
        skewInterval()
      )
    } else {
      this.performAndScheduleFetch(gitHubRepository)
    }
  }

  /**
   * Stop background fetching. Once this is called, the fetcher cannot be
   * restarted.
   */
  public stop() {
    this.stopped = true

    const handle = this.timeoutHandle
    if (handle) {
      window.clearTimeout(handle)
      this.timeoutHandle = null
    }
  }

  /** Perform a fetch and schedule the next one. */
  private async performAndScheduleFetch(
    repository: GitHubRepository
  ): Promise<void> {
    if (this.stopped) {
      return
    }

    const shouldFetch = await this.shouldPerformFetch(this.repository)

    if (this.stopped) {
      return
    }

    if (shouldFetch) {
      try {
        await this.fetch(this.repository)
      } catch (e) {
        const ghRepo = this.repository.gitHubRepository
        const repoName =
          ghRepo !== null ? ghRepo.fullName : this.repository.name

        log.error(`Error performing periodic fetch for '${repoName}'`, e)
      }
    }

    if (this.stopped) {
      return
    }

    const interval = await this.getFetchInterval(repository)
    if (this.stopped) {
      return
    }

    this.timeoutHandle = window.setTimeout(
      () => this.performAndScheduleFetch(repository),
      interval
    )
  }
