### Title
Legacy `pattern` field inference in `Rule.from_dict` silently misdirects block-rule matching to the wrong field for `file` events - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` infers the `Condition.field` for legacy `pattern:` frontmatter purely from the `event` value, mapping `event: file` to `field='new_text'` (edit/write content) rather than `field='file_path'`. An explicit `conditions:` block, by contrast, lets the author pick any field, including `file_path`. This creates a semantic gap between the two parsing paths so that a `pattern:`-based block rule that visually targets a file path is silently enforced against the write's *content* instead, weakening or misdirecting the intended block.

### Finding Description
`Rule.from_dict` has two code paths for building `conditions`: [1](#0-0) 

For the legacy `pattern` path, the field to match against is inferred solely from `event`: `bash` → `command`, `file` → `new_text`, anything else → `content`. There is no `file_path` inference option in the legacy path at all, even though `Condition`/`_extract_field` in `rule_engine.py` fully supports `field: file_path` for `Write`/`Edit`/`MultiEdit` tools. [2](#0-1) 

Consequently, a rule authored (or generated by `/hookify` generation, or shipped in a repo) as:
```
event: file
pattern: "/etc/passwd"
action: block
```
is intended by a plausible reading (“block operations related to /etc/passwd”) to block edits/writes to that file, but `Rule.from_dict` silently converts it into a condition on `new_text` (the new content being written), not `file_path`. The evaluator (`_rule_matches` → `_check_condition` → `_extract_field`) then checks whether the string `/etc/passwd` appears in the new content, not whether the target file is `/etc/passwd`. [3](#0-2) 

This differs from the explicit-conditions form, where the same intent can be (and must be) expressed unambiguously with `field: file_path`. No validation, warning, or cross-check exists in `Rule.from_dict` (or `load_rule_file`) to detect that a `file`-event legacy pattern rule might be intended as a path filter, nor is there any indication to the rule author that `pattern` is being silently bound to content instead of path.

### Impact Explanation
If a user (or an automated `/hookify` rule-generation flow) authors a legacy-style `pattern` block rule intending to protect a specific file/path, the rule as parsed will not actually match on `file_path`. An operation that writes to the targeted path with content that does not literally contain the pattern string will not be blocked, while the block rule may falsely trigger on unrelated files whose new content happens to mention the pattern text. This is a "believed-protected but actually unprotected" condition: enforcement is weaker than the rule author intended, and a subsequent Write/Edit to the nominally protected path (driven by any other attack vector, e.g., prompt injection) would not be denied by this rule, potentially resulting in an unauthorized file write. The impact is bounded to whatever `Write`/`Edit`/`MultiEdit` actions the false sense of protection was meant to prevent.

### Likelihood Explanation
This requires a `file`-event, `pattern`-style (legacy) block rule to exist in `.claude/hookify.*.local.md`, either hand-authored, produced by `/hookify` generation, or shipped in a repository and loaded via `load_rules()`/`load_rule_file()`. Given that the `pattern` legacy syntax is documented as the simple/basic authoring style (vs. `conditions` for advanced use), and that `event: file` + `pattern: <path-looking-string>` is a natural but incorrect way to attempt path-based blocking, this is plausible to occur without any adversarial intent, and is trivially reproducible by any party who can place such a rule file (including via `/hookify` generation output).

### Recommendation
- In `Rule.from_dict`, do not silently default the legacy `pattern` field mapping for `event: file` to `new_text`. Either: (a) require an explicit `field:` alongside `pattern:` for `file` events, or (b) add a dedicated `path_pattern`/`file_pattern` frontmatter key mapped explicitly to `file_path`, separate from content-matching `pattern`.
- Emit a warning (or refuse to load) when a `file`-event legacy-pattern rule cannot unambiguously infer whether the pattern targets `file_path` vs. content.
- Add regression tests comparing legacy vs explicit-condition semantics for the same intended policy to ensure they produce identical enforcement behavior.

### Proof of Concept
Unit test plan (extends the pattern used in `config_loader.py`'s `__main__` self-test and `rule_engine.py`):
1. Build frontmatter:
```python
frontmatter = {
    "name": "block-etc-passwd",
    "enabled": True,
    "event": "file",
    "pattern": "/etc/passwd",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Blocking write to /etc/passwd")
```
Assert `rule.conditions[0].field == 'file_path'` — this **fails**, since it currently equals `'new_text'`, demonstrating the semantic gap.
2. Run through `RuleEngine.evaluate_rules`:
```python
tool_input = {"file_path": "/etc/passwd", "content": "harmless data"}
input_data = {"tool_name": "Write", "tool_input": tool_input, "hook_event_name": "PreToolUse"}
result = engine.evaluate_rules([rule], input_data)
```
Expected (intended) behavior: `result` denies the write (`permissionDecision: deny`). Actual behavior: `result == {}` (no match), because the condition checks `new_text`/content instead of `file_path`, proving the write to `/etc/passwd` is not blocked despite the rule's apparent intent.
3. Contrast with the explicit form to show the discrepancy:
```python
frontmatter_explicit = {
    "name": "block-etc-passwd-explicit",
    "enabled": True,
    "event": "file",
    "conditions": [{"field": "file_path", "operator": "regex_match", "pattern": "/etc/passwd"}],
    "action": "block",
}
rule2 = Rule.from_dict(frontmatter_explicit, "Blocking write to /etc/passwd")
result2 = engine.evaluate_rules([rule2], input_data)
```
Expected: `result2` correctly denies the operation, confirming that only the explicit-conditions path enforces the intended path-based block, while the legacy-pattern path silently does not.

    def _rule_matches(self, rule: Rule, input_data: Dict[str, Any]) -> bool:
        """Check if rule matches input data.

        Args:
            rule: Rule to evaluate
            input_data: Hook input data

        Returns:
            True if rule matches, False otherwise
        """
        # Extract tool information
        tool_name = input_data.get('tool_name', '')
        tool_input = input_data.get('tool_input', {})

        # Check tool matcher if specified
        if rule.tool_matcher:
            if not self._matches_tool(rule.tool_matcher, tool_name):
                return False

        # If no conditions, don't match
        # (Rules must have at least one condition to be valid)
        if not rule.conditions:
            return False

        # All conditions must match
        for condition in rule.conditions:
            if not self._check_condition(condition, tool_name, tool_input, input_data):
                return False

        return True
