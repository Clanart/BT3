### Title
Submodule updates unconditionally re-enable `file://` protocol, exposing repos to CVE‑2022‑39253‑style arbitrary local file read/exfiltration via malicious submodule URLs - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` builds its `git submodule update --init --recursive` invocation with an optional `-c protocol.file.allow=always` flag controlled by an `allowFileProtocol` boolean parameter: [1](#0-0) 

Git upstream disabled the `file://` transport for recursive submodule operations by default (fixed in CVE‑2022‑39253) precisely because a malicious repository can define a submodule whose URL is a `file://` path (optionally combined with symlinks/hardlinks in the working tree) to make `git submodule update --recursive` read and copy arbitrary files from the host filesystem into the checked-out working directory. Desktop explicitly re-opts into the vulnerable behavior whenever `allowFileProtocol` is `true`.

### Finding Description
The attacker primitive here is directly analogous to the "1 wei donation poisons a permissive invariant" pattern from the smart-contract report: a low-cost, attacker-controlled artifact (here, a `.gitmodules` entry with a `file://` submodule URL inside a cloned/fetched repository) is fed into logic that trusts it because a caller has pre-authorized an unsafe mode (`protocol.file.allow=always`), and the downstream check (git's normal protection against `file://` submodules) is deliberately bypassed.

- The corrupted value is the effective git configuration for the submodule operation: `protocol.file.allow` is forced to `always` for the whole `submodule update --init --recursive` invocation, which recurses into every submodule defined in the attacker's `.gitmodules`, not just ones the user intended to trust.
- Because `--recursive` is always passed, a malicious top-level repository can nest an arbitrary-depth submodule chain, each with `file://` URLs pointing at sensitive host paths (SSH keys, browser profiles, credential stores, etc.), and have that content materialized inside the working directory that Desktop subsequently shows/diffs/stages.
- git's own hardening (disallowing `file://` for recursive submodule fetches unless explicitly permitted) is the "invariant" being bypassed. Desktop's `-c protocol.file.allow=always` override neutralizes that guard globally for the operation, mirroring how the frontrunning donation neutralized the leverage check in the original report.

### Impact Explanation
If `allowFileProtocol` can be set to `true` for a checkout/pull/clone flow that runs against an untrusted, attacker-supplied repository (e.g., opening a URL via "Open in Desktop", cloning a public repo, or checking out a PR branch containing a malicious `.gitmodules`), the result matches the accepted impact categories: file read outside the repository (arbitrary host files pulled in via `file://` submodules) and silent corruption of what the user later commits/pushes (the exfiltrated file contents become part of the working tree and can be staged/committed/pushed without the user realizing the content originated outside the repo).

### Likelihood Explanation
The severity depends entirely on the conditions under which `allowFileProtocol=true` is passed by callers in `app/src/lib/git/checkout.ts` (7 references were found there, but their exact call sites/conditions were not confirmed within this investigation due to iteration limits). If this flag is enabled unconditionally, or enabled for any checkout/pull that can be triggered against a freshly cloned/fetched untrusted repository (rather than being scoped strictly to local, user-initiated same-machine clones), the likelihood is high since it only requires the victim to open/clone/checkout a malicious repository — a normal, low-friction user action, consistent with the "unprivileged... attacker controls a cloned/fetched repository" threat model.

### Recommendation
- Verify every call site in `app/src/lib/git/checkout.ts` that sets `allowFileProtocol: true` and confirm it is restricted only to trusted, explicitly local operations (e.g., updating submodules for a repo the user cloned via `file://` themselves), never for submodules discovered inside a remotely fetched/cloned repository's `.gitmodules`.
- Default `allowFileProtocol` to `false` and require an explicit, narrowly-scoped opt-in (e.g., per-submodule allow-list) rather than a blanket `protocol.file.allow=always` for the entire recursive operation.
- Consider passing `protocol.file.allow=user` (git's safer default) instead of `always`, and avoid `--recursive` re-enabling the override for nested/untrusted submodules.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file with a submodule entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.ssh
   ```
2. Victim opens/clones the repository in GitHub Desktop and Desktop performs a checkout/pull that calls `updateSubmodulesAfterOperation(repository, remote, ..., allowFileProtocol=true)` as seen in `app/src/lib/git/submodule.ts` lines 29-51.
3. Because `-c protocol.file.allow=always` is passed, `git submodule update --init --recursive` fetches from the local `file://` path, copying the victim's `~/.ssh` contents into the `leak/` directory of the working tree.
4. The victim, unaware, may stage/commit/push this directory, or an attacker with any read access to the repo state (e.g., via a subsequent diff view or built-in file browser in Desktop) can retrieve the exfiltrated files.

**Caveat:** I was not able to confirm, within tool-call limits, the exact conditions under which `app/src/lib/git/checkout.ts` sets `allowFileProtocol` to `true` (whether it's scoped to explicitly trusted, user-initiated local clones or can be reached for arbitrary remote/fetched repositories). This is the key fact that determines whether this is remotely exploitable by an untrusted repository author versus only reachable in already-trusted local-clone scenarios. A Devin session with full file access should inspect `app/src/lib/git/checkout.ts` to confirm the call sites before treating this as confirmed-exploitable.
