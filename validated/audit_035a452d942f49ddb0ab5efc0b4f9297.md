## Finding: Unbounded recursive `MofN` memo parsing causes wallet-side resource exhaustion / DoS (CHIP-0043 custody architecture)

### Title
Unbounded recursive `PuzzleWithRestrictions.from_memo()` parsing of attacker-controlled `MofN` memos causes wallet-side stack/resource exhaustion - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody puzzle tree from an on-chain `CREATE_COIN` memo. When the memo indicates "further branching" (an `MofN` node), it recursively calls itself once per declared member, with **no limit on nesting depth or breadth**. Since the memo is attacker-controlled data embedded in a coin's `CREATE_COIN` condition, any coin creator can construct a memo that nests `MofN` structures deeply enough to exhaust the Python call stack (or, before hitting the stack limit, blow up CPU/memory) in any wallet client that later parses that memo — this is directly analogous to the GitLab CVE-2021-22181 pattern where an attacker-controlled recursive relationship (there: pipeline triggers; here: `MofN` member memos) is walked without a depth/cycle bound, exhausting resources.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is the parser used to resync unknown custody puzzles from on-chain data: [1](#0-0) 

The recursive branch is:
```python
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
    )
``` [2](#0-1) 

`MofNHint.from_program()` simply reads `m` and an arbitrary list `member_memos` straight from the CLVM program with no size cap: [3](#0-2) 

Nothing in `from_memo()` bounds recursion depth or the total number of nodes visited — each element of `member_memos` can itself declare `further_branching=1` with its own `member_memos` list, allowing an attacker to construct an arbitrarily deep (or wide) tree in a single memo blob. The only validation of `MofN` shape (`m <= n`, `m >= 1`, no duplicate nodes) happens in `MofN.__post_init__`, which runs only *after* the full recursive `from_memo()` call chain for that node has already executed — i.e., after the damage (stack growth / CPU work) is already done: [4](#0-3) 

This parser is reachable by any local wallet that syncs an on-chain coin using this memo format. Concretely, `chia/pools/plotnft_drivers.py` calls `PuzzleWithRestrictions.from_memo()` directly on the `memo_blob` taken from a `CREATE_COIN` condition emitted by a singleton spend it is trying to catch up on: [5](#0-4) 

The `CREATE_COIN` memo content is fully attacker-controlled: any spend bundle submitter can create a coin (e.g. a plotNFT-shaped singleton output, or any coin a syncing wallet chooses to inspect for `PuzzleWithRestrictions` state) whose memo encodes a deeply/widely nested `MofN` hint. When a wallet later syncs this coin and calls `from_memo()` (or `get_next_from_coin_spend()`), the wallet process performs unbounded Python-level recursion purely from parsing untrusted memo data — this is not CLVM execution, so it is not subject to the mempool/CLVM cost-limit protections described for the rest of the puzzle-execution pipeline.

### Impact Explanation
A wallet client (including PlotNFT-syncing wallets or any code path that resyncs `PuzzleWithRestrictions` custody state from chain, per `.cursor/context/testing/clvm.md`'s note that `from_memo()` "must reconstruct unknown members/restrictions, including recursive `MofN`") that encounters such a malicious memo will either:
- hit Python's recursion limit and raise `RecursionError`, potentially crashing or halting the wallet sync/background processing thread, or
- spend excessive CPU/memory walking and materializing the nested structure before validation ever runs.

Either outcome halts transaction/state processing for the affected wallet, denying service to the user syncing that coin — the same class of impact as the GitLab recursive-pipeline DoS (unbounded resource consumption from an attacker-defined recursive relationship).

### Likelihood Explanation
Any unprivileged party can create a coin (no special privileges, no signature requirements on the memo field, memos are free-form) with a `CREATE_COIN` condition carrying a maliciously deep/wide `MofN` memo tree. A wallet only needs to attempt to sync/resolve that coin's custody puzzle (e.g., while tracking PlotNFTs or other custody-architecture puzzles) to trigger the recursive parse. This requires no cooperation from the victim beyond normal wallet sync behavior.

### Recommendation
Add explicit depth and/or node-count limits to `PuzzleWithRestrictions.from_memo()` (and `MofNHint.from_program()`) before recursing, rejecting memos that exceed a sane bound (e.g., matching whatever depth real custody deployments are expected to use). Validate `m`/`n` and member-count constraints incrementally during parsing rather than only in `MofN.__post_init__` after full recursive construction, and consider converting the recursion to an iterative/worklist algorithm with an explicit depth counter so malformed on-chain memos cannot exhaust the Python call stack.

### Proof of Concept
1. Construct a `CREATE_COIN` condition whose memo is `Program.to(("CHIP-0043", [0, [], 1, [1, [<deeply nested MofNHint blob repeated N times>]]]))`, i.e. a memo where `further_branching=1` and each `member_memos` entry is itself another `further_branching=1` node, nested N ≈ Python recursion limit (~1000) or deep enough to cause severe slowdown.
2. Submit a spend bundle creating a coin with this memo (e.g., shaped to be picked up by PlotNFT sync logic, or any code path that calls `PuzzleWithRestrictions.from_memo()`/`get_next_from_coin_spend()` on discovered coins).
3. Any wallet that later processes this coin's `CREATE_COIN` memo via `chia/pools/plotnft_drivers.py`'s `get_next_from_coin_spend()` (`unknown_inner_puzzle = PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())`) triggers unbounded recursive `from_memo()` calls, resulting in a `RecursionError` or excessive CPU/memory use in that wallet process.
