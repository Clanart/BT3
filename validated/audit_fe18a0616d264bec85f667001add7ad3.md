Based on my analysis, I found a genuine analog vulnerability in this codebase. Let me present my findings.

### Title
Hookify PreToolUse/Stop hooks fail-open on any internal error, allowing attacker-controlled input to bypass `block` rules - (File: `plugins/hookify/hooks/pretooluse.py`)

### Summary
The Sherlock report describes users controlling protocol state by making a hook revert selectively, since the calling contract treats a hook failure as "safe" rather than as a signal to halt the sensitive operation. The same trust-boundary pattern exists in the `hookify` plugin: `PreToolUse` (and `Stop`/`PostToolUse`/`UserPromptSubmit`) hook scripts wrap all rule evaluation in a blanket `except Exception` handler and unconditionally call `sys.exit(0)` in a `finally` block, which Claude Code interprets as "allow." Any attacker-influenced value that causes rule evaluation to throw therefore defeats configured `block` rules instead of erring safely toward denial.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` reads the hook's JSON payload (`tool_name`, `tool_input`, etc. — attacker-influenced through file contents, prompts, or MCP tool outputs that get echoed into subsequent tool calls) and passes it to `RuleEngine.evaluate_rules`. [1](#0-0) 

Whatever exception is raised while loading/evaluating rules is swallowed, the operation's `systemMessage` is replaced with a generic error string, and the process still exits with code `0`: [2](#0-1) 

Only when evaluation completes *without* throwing does `RuleEngine.evaluate_rules` get the chance to return `permissionDecision: "deny"` for a matched `block` rule: [3](#0-2) 

The rule-parsing and matching code path is broad and includes YAML-like frontmatter parsing (`extract_frontmatter`), field extraction with `str()` coercions, and transcript file reads — several of these paths already required their own defensive `try/except` blocks for `IOError`, `UnicodeDecodeError`, etc., which is evidence the authors were aware exceptions occur here but chose to make the *hook process* fail open rather than fail closed. [4](#0-3) [5](#0-4) 

This mirrors the Sherlock issue's root cause: a security-relevant callback (`ClaimHook`/here, the PreToolUse rule engine) can be made to fail via attacker-influenced input, and the caller (the vault contract / here, Claude Code's hook runner) treats that failure as equivalent to "no objection," rather than surfacing it as a denial. Since `.claude/hookify.*.local.md` rules are explicitly the mechanism recommended by this plugin (and its `hookify`/`plugin-dev` skills) for enforcing `block` on dangerous `Bash` commands (`rm -rf`, `chmod 777`, `dd if=`) and sensitive file writes (`.env`, credentials), causing this hook to error out defeats the intended safety control for that session. [6](#0-5) 

### Impact Explanation
This is a "hook bypass" trust-boundary issue: a user (or a Claude session under prompt injection from untrusted file/tool content) can construct a `tool_input` value that trips an unhandled exception in the rule-matching pipeline (e.g., a `Condition` object with a malformed/missing `field` combined with a tool type not covered by `_extract_field`'s branches, or non-string values in `tool_input` that break `str()`/`.startswith()`/`.endswith()` calls used by other operators such as `contains`, `starts_with`, `ends_with` when `pattern` is `None` or a non-string type from a hand-crafted `conditions` block). Because the hook fails open, a configured `block` rule meant to prevent destructive `Bash` commands or edits to secret files silently does not fire for that tool call, while the operator/administrator believes protection is active. This does not compromise the wider claude-code binary or escalate privileges, but it is a concrete "unauthorized shell/file action" bypass of an admin-configured guardrail, consistent with the accepted trust-boundary categories (hook bypass).

### Likelihood Explanation
Likelihood is limited by two mitigations: (1) the plugin's regex/condition matching in `_regex_match` already catches `re.error`, and file/parsing errors in `config_loader.py` are also caught with specific exception types, narrowing the practical exception surface to gaps in `_extract_field`/`_check_condition`'s untyped operator branches; and (2) the attacker must control or influence `tool_input` content passed to a tool while a `block` rule is configured, which requires the victim to have already set up hookify rules. This is a real but narrow condition, similar to the Sherlock finding being rated informational/low-to-medium rather than critical — it requires a specific state (an active `block` rule plus a value that raises inside evaluation) and its worst outcome is a bypassed local guardrail, not a full sandbox escape.

### Recommendation
Change the fail-open `finally: sys.exit(0)` in `pretooluse.py` (and the analogous `stop.py`/`posttooluse.py`/`userpromptsubmit.py`) to fail closed for `PreToolUse`: on unexpected exceptions during rule evaluation, emit `permissionDecision: "ask"` (or `"deny"` for `block`-configured rules) instead of unconditionally allowing, and surface the exception message to the user/transcript so silent bypass isn't possible. Additionally, harden `_check_condition`/`_extract_field` in `rule_engine.py` to coerce/validate `pattern` and `field_value` types before calling string operators, removing the main source of unexpected exceptions rather than relying on a blanket catch-all.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-rm
enabled: true
event: bash
conditions:
  - field: command
    operator: starts_with
    pattern: 
---
Blocked dangerous rm.
```
   (Note the empty `pattern:` value — via `Condition.from_dict`, `pattern` defaults to `''` normally, but a hand-edited/generated rule file with a non-string YAML list value, e.g. `pattern: [rm, -rf]`, parsed through `extract_frontmatter`'s simplistic list handling, can produce a `pattern` that is a `list` rather than `str`.)
2. Trigger a `Bash` tool call with `command: "rm -rf /important"`.
3. In `_check_condition` (`plugins/hookify/core/rule_engine.py:174-177`), `field_value.startswith(pattern)` raises `TypeError: startswith first arg must be str... not list`.
4. This exception propagates up through `_rule_matches` → `evaluate_rules` → `main()`'s `except Exception` in `pretooluse.py`, which prints a generic error `systemMessage` and calls `sys.exit(0)` — Claude Code treats this as "allow," and the `rm -rf` command executes despite the configured `block` rule.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
