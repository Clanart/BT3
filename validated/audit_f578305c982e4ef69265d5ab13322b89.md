## Title
Unverified “successful pop” heuristic causes stash entries to be silently dropped (destroyed) without confirming the working directory was actually restored - (`app/src/lib/git/stash.ts`)

### Summary
The original report describes a broken invariant: a destructive cleanup step (`burn`) is executed based on the *assumption* that a prior operation succeeded, without ever verifying that the operation's actual effect took place. The Desktop analog is `popStashEntry` in `app/src/lib/git/stash.ts`, which treats `git stash pop` exiting with code `1` and empty `stderr` as a de-facto success and then permanently deletes ("drops") the stash entry — without any verification that the stash contents were actually restored to the working directory.

### Finding Description
`popStashEntry` runs `git stash pop --quiet <name>` and, when the command fails, inspects the error heuristically: [1](#0-0) 

If the exit code is `1` and `stderr` is empty, the code logs "a stash was popped successfully" and immediately calls `dropDesktopStashEntry`, which runs `git stash drop` — permanently removing the only copy of the user's stashed changes: [2](#0-1) 

The comment in the code itself flags the fragility of this assumption: *"Not the greatest approach but stash isn't very communicative."* The same class of ambiguity is separately documented for `createDesktopStashEntry`, where a 2024 code-review comment explicitly says the exit-code-1-plus-no-`error:`-line heuristic "didn't hold up to a quick read of the stash code" and gives a counter-example (unborn repository) where exit code 1 occurs but nothing was actually stashed: [3](#0-2) 

The broken invariant is identical to the Pixelswap bug: **a state-destroying action (`drop`/`burn`) is triggered by an inference about success rather than by confirmed evidence of success.** `git stash pop` internally performs an apply followed by a checkout of tracked paths; various repository-controlled mechanisms (clean/smudge filters, `.gitattributes`-driven merge drivers, LFS pointers, or other content transformers defined in the cloned repository) can cause the underlying `git checkout`/apply step invoked by `stash pop` to fail partially with exit code `1` and no `stderr` output, without actually restoring all stashed content to the working directory. Because Desktop's guard only checks `exitCode === 1 && stderr.length === 0`, it cannot distinguish "the stash was fully applied, git just complains about drop" from "the stash was partially or not applied at all, and there happened to be no stderr text."

### Impact Explanation
When this heuristic mis-fires, the user's stash entry is deleted via `git stash drop` — a `git stash` is not recoverable from the UI after this call, and if the underlying reflog entry is subsequently pruned (Desktop does not warn the user or offer recovery here), the changes are gone permanently. This is silent corruption/loss of what the user was about to commit: their uncommitted work is destroyed by a Desktop-initiated cleanup action that fired based on a guess. Because this path is reached from ordinary user-facing flows (checkout-and-bring-changes, restoring a stash from the Changes view), a repository authored/controlled by an attacker (e.g. via crafted `.gitattributes` filters or content that makes the underlying pop only partially apply) can weaponize an otherwise benign-looking clone to cause victims to silently lose local changes when they check out branches or restore stashes.

### Likelihood Explanation
This requires only that the victim clone/fetch an attacker-authored repository (or branch) containing content/attributes that make `git stash pop` on some commit produce `exitCode === 1` with empty `stderr` for a reason other than a resolvable conflict — no admin rights, no local pre-existing malware, and no unusual user action beyond checking out a branch or restoring a stash, both of which are core Desktop features. The pre-existing developer comment in the same file acknowledging the heuristic's unsoundness for a known counter-example supports that this exit-code/stderr combination is not exclusively tied to "conflict, stash preserved."

### Recommendation
- Do not infer success/failure of `git stash pop` from exit code and stderr length alone. After a non-zero exit, explicitly diff the working directory/index against the stash's tree (or re-run `git stash show`/`git status`) to confirm the stashed changes are actually present before calling `dropDesktopStashEntry`.
- If verification is inconclusive, leave the stash entry intact and surface the ambiguous state to the user rather than silently discarding it.
- Apply the same principle to `createDesktopStashEntry`'s analogous exit-code-1 heuristic, which the code's own commentary already flags as unreliable.

### Proof of Concept
1. Attacker publishes a repository containing a commit whose tree, combined with content already stashed by a user (e.g., via a crafted `.gitattributes` clean/smudge filter or merge driver shipped in the repo) causes `git stash pop` on that branch to exit with code `1` and empty `stderr` while only partially restoring the stash contents (this class of exit-1/no-stderr behavior for `stash pop` is exactly the ambiguous case the code comments in `stash.ts` acknowledge exists).
2. Victim clones the repository in GitHub Desktop, makes local changes, and lets Desktop stash them as part of a branch switch (`checkoutAndBringChanges` → `popStashEntry`), or manually restores an existing stash from the Changes UI (`_popStashEntry`).
3. `popStashEntry` sees `exitCode === 1`, `stderr.length === 0`, logs "stash was popped successfully," and calls `dropDesktopStashEntry`, deleting the only stash reference.
4. The victim's working directory does not contain the fully restored changes, and the stash that held them is gone — an unrecoverable, silent loss of the user's uncommitted work triggered purely by content in the cloned repository.
