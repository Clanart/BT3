### Title
Attacker-controlled `.gitmodules` `file://` submodule URL allows arbitrary local file read via `git submodule update` with `protocol.file.allow=always` - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` conditionally re-enables Git's `file://` transport for submodule operations by passing `-c protocol.file.allow=always` to `git submodule update --init --recursive` whenever the caller sets `allowFileProtocol = true` [1](#0-0) . This flag is threaded through `checkoutBranch` and `checkoutCommit`, both of which accept `allowFileProtocol: boolean = false` as a caller-supplied parameter [2](#0-1) [3](#0-2) . Since Git 2.38 (backported to 2.35.5), `protocol.file.allow` defaults to `user`/restricted specifically to prevent submodule URLs from pointing at arbitrary local paths — a hardening measure against exactly this class of bug. When Desktop overrides this with `always`, a `.gitmodules` file coming from an untrusted, attacker-controlled repository (the "attacker controls a cloned/fetched repository" primitive) can declare a submodule URL such as `file:///etc` or `file://../../../../Users/victim/.ssh`, and `git submodule update --init --recursive` will copy the contents of that arbitrary local path into the submodule's working directory inside the user's repo.

### Finding Description
`.gitmodules` is fully attacker-controlled content — it is fetched/cloned as part of a repository and is never validated by Desktop before submodule operations run. The invariant that Git 2.38+ restores by default (`protocol.file.allow=user`, which still blocks recursive submodule file:// clones by default under `protocol.file.allow` interacting with `submodule.recurse`/`clone.protectNTFS`/`fsck` protections) is broken independently by Desktop when `allowFileProtocol=true` forces `protocol.file.allow=always` for the whole `submodule update --init --recursive` invocation [1](#0-0) . Because `--recursive` is used, nested submodules declared by the attacker's `.gitmodules` (or by any transitively-fetched submodule's own `.gitmodules`) are also updated under the relaxed policy, giving the attacker repeated opportunities to specify `file://` targets. The corrupted value is the working-tree contents of the submodule directory: instead of content pulled from the declared remote, it becomes an uncontrolled copy of whatever local path the attacker's `.gitmodules` names.

### Impact Explanation
If the local path resolves to sensitive data (SSH keys, cloud credential files, other private repositories on disk, etc.), that data is copied into the victim's working tree as tracked submodule content. From there it can be viewed in Desktop's file browser/diff view, and if the user stages/commits/pushes (a completely ordinary workflow after "checking out a branch"), the exfiltrated content is silently pushed to a remote the attacker may control — satisfying the "credential/token exfiltration" and "silent corruption of what the user commits or pushes" impact categories in scope.

### Likelihood Explanation
The path requires (1) the user to open/clone/fetch a malicious repository and (2) Desktop to invoke checkout with `allowFileProtocol=true`. I was not able to fully confirm, within the available tool budget, every call site in `app/src/lib/stores/app-store.ts` that sets this flag to `true` versus `false` for ordinary branch checkouts — the earlier directory-scoped search reported 8 matches for `allowFileProtocol` there, but a follow-up grep restricted to that exact file returned no matches, which is inconsistent and suggests the file may be large or partially outside indexed range. This is a real gap: the exploitability hinges on whether `allowFileProtocol=true` is only used for known-safe/local-only flows (e.g., fixture/test setups, as seen in `app/test/helpers/repositories.ts` and `app/test/unit/git/checkout-test.ts`) or is also reachable from ordinary "checkout branch/commit from an untrusted, attacker-supplied repository" UI flows. Given the index size limits, I could not conclusively verify the production call sites; a Devin session with full file access would be needed to confirm exactly which checkout paths pass `true` for arbitrary/untrusted repositories.

### Recommendation
- Never pass `allowFileProtocol=true` for repositories that are not explicitly trusted/local-only; do not derive this flag from anything influenced by remote/fetched content.
- If `file://` submodules must be supported for legitimate local-clone workflows, scope `protocol.file.allow` per-submodule to paths known to be within the same trusted directory tree rather than `always` for the whole recursive operation.
- Add an explicit allow-list/validation step that rejects `.gitmodules` entries with `file://` URLs (or path-like URLs resolving outside expected remote hosts) before invoking `git submodule update --init --recursive` on untrusted repositories.

### Proof of Concept
1. Attacker publishes a repository containing:
   ```
   [submodule "leak"]
       path = leak
       url = file:///Users/victim/.ssh
   ```
2. Victim clones/opens this repository in Desktop and checks out the branch containing this `.gitmodules`, reaching a code path where `checkoutBranch`/`checkoutCommit` is invoked with `allowFileProtocol=true` [4](#0-3) .
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, and Git copies `/Users/victim/.ssh` into `leak/` inside the repository working tree [5](#0-4) .
4. The victim, browsing the "leak" folder or committing/pushing the checkout state, exposes the copied private key material.

**Note on verification limits:** Due to inconsistent search results (8 matches vs. 0 matches for `allowFileProtocol` in `app-store.ts` across two queries), I could not fully confirm the exact conditions under which production code sets this flag to `true`. I recommend starting a Devin session with full repository access to inspect `app/src/lib/stores/app-store.ts` in its entirety and confirm whether any checkout flow reachable from an untrusted/attacker-supplied repository sets `allowFileProtocol=true`.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
