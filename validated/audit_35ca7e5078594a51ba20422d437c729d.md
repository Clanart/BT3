### Title
Cached FROST preprocess seed is never invalidated, causing deterministic nonce reuse across signing sessions - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The bug class is "stale authorization/state surviving a state transition it should have been invalidated by" — in the source report, an owner's approvals persist after ownership changes. In `SigningProtocol::preprocess_internal`, the coordinator persists a FROST preprocess seed (`CachedPreprocess`) under a fixed context key and reconstructs the identical deterministic nonces on every `share`/`complete` invocation, but never deletes the entry after `from_cache` consumes it. Because FROST nonce reuse across distinct signing sessions directly leaks the signer's secret share, the persistent stale state converts a second use of the cached seed into key compromise.

### Finding Description

`SigningProtocol::preprocess_internal` encrypts and stores a 32-byte preprocess seed in `CachedPreprocesses` keyed by `context` (`(b"DkgConfirmer", attempt)` for the DKG confirmer path). If the entry already exists, no new seed is generated; the existing seed is decrypted and passed to `AlgorithmSignMachine::from_cache`. `from_cache` calls `seeded_preprocess`, which derives the FROST nonces deterministically via `ChaCha20Rng::from_seed(*seed.0)` (crypto/frost/src/sign.rs:121-144).

`share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)`, consuming those nonces to produce a signature share (lines 150-181). The cached DB entry is never deleted: there is no `CachedPreprocesses::del` call anywhere in `share_internal`, `sign`, or `complete_internal`. The `create_db!` macro provides get/set/del, but only get/set are used here.

The reuse is reachable through `DkgConfirmer`:

- `DkgConfirmer::share` calls `share_internal` once (line 304-310).
- `DkgConfirmer::complete` calls `share_internal` again (line 321-324), unconditionally rebuilding the machine from the same cached seed and re-signing.

If the `preprocesses` map differs between the two calls — different participant subset, different ordering into the MuSig index map via `threshold_i_map_to_keys_and_musig_i_map`, or a different `key_pair`/msg — the FROST binding factors, interpolation coefficients, and challenge change while the validator's nonces `d_i, e_i` remain bit-for-bit identical. Each published share is `s_i = d_i + e_i·ρ_i + λ_i·x_i·c`; two shares with the same `d_i, e_i` but different `c`/`λ_i` give linear equations solvable for `x_i` by anyone who observes both.

### Impact Explanation

Recovery of a validator's Ristretto MuSig secret share for the DKG-confirmation signing protocol. Combined with the public set-keys signatures (Schnorrkel aggregate), an attacker who collects two shares under the same attempt context with different signing sets recovers the validator's contribution to the validator-set MuSig key, degrading the threshold by one. Repeated across validators (any participant can induce differing preprocess sets), this erodes the `t-of-n` security of the set-keys signature that authorizes new validator sets — the most critical signature in the system. Analogous to the source report, the stale persisted state silently authorizes/permits an action (signing under identical nonces) that the signer only consented to once.

### Likelihood Explanation

The state is reachable by untrusted public inputs: `preprocesses` are `[u8; 64]` blobs broadcast by other validators over the tributary, read via `read_preprocess`. Both `share` and `complete` go through `share_internal`, and neither deduplicates the consumed seed. Any divergence in the preprocess set between calls — a peer publishing preprocesses late, a coordinator calling `complete` after the share path already ran with a subset, or a retry path reconstructing `DkgConfirmer` for the same `attempt` — produces nonce reuse. The comment at lines 104-106 acknowledges the secret sensitivity of the cache yet omits the deletion step the `SignMachine::from_cache` contract explicitly demands ("After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share.", crypto/frost/src/sign.rs:217-219). Whether divergence occurs in a given run depends on coordinator scheduling details in `handle.rs` I could not fully verify, so likelihood is conditional rather than deterministic — hence Medium-High rather than guaranteed.

### Recommendation

Delete `CachedPreprocesses` for the context as soon as `from_cache` consumes the seed — i.e., call `CachedPreprocesses::del(txn, &self.context)` inside `share_internal` after loading, or rotate the context with a monotonically increasing counter/commitment to the exact preprocess set (e.g., include a hash of the sorted preprocess map and msg in the context key) so any changed session derives a fresh seed. Additionally, enforce in `complete` that the machine rebuilt via `share_internal` is supplied the identical preprocess map that produced the published share, or persist the consumed machine rather than re-deriving it.

### Proof of Concept

1. Validator V participates in `DkgConfirmer` for `attempt = A`. `share` is invoked with preprocess set `P1` (subset S1 of participants). `preprocess_internal` reads seed `s` from `CachedPreprocesses[("DkgConfirmer", A)]`, `seeded_preprocess` derives nonces `d, e` and commitments, `sign` produces share `s_V = d + e·ρ_1 + λ_V·x_V·c_1` for `msg_1`. The DB entry remains.
2. `complete` (or a second `share`) is invoked with a different preprocess set `P2` — e.g., one additional/fewer participant, changing the MuSig reindexing in `threshold_i_map_to_keys_and_musig_i_map`. `preprocess_internal` reads the same undeleted `s`; `Commitments::new` in `seeded_preprocess` produces identical `d, e`.
3. `sign` emits `s'_V = d + e·ρ_2 + λ'_V·x_V·c_2`. With `s_V`, `s'_V`, and the public commitments `D = d·G, E = e·G`, an observer eliminates `d, e`: `s_V - s'_V = e·(ρ_1 - ρ_2) + x_V·(λ_V·c_1 - λ'_V·c_2)`, and since `e` is recoverable from `D, E` only if nonces differ — with identical nonces the two equations in unknowns `(d, e, x_V)` plus the known verification share `x_V·G` reduce to solving for `x_V` directly when `λ_V·c_1 ≠ λ'_V·c_2`.
4. `x_V` recovered: one honest validator's MuSig share is compromised without any malicious behavior beyond supplying public preprocess bytes.
