### Title
Silent origin-remote hijack via GitHub repo-name/owner squatting during background repository refresh - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Desktop periodically re-resolves the GitHub repository associated with a local clone using only the **mutable** owner/name pair parsed from the current git remote URL, then trusts the GitHub API response enough to silently rewrite the user's `origin` remote to whatever `clone_url` that API call returns — without ever comparing a stable GitHub repository ID or prompting the user.

### Finding Description
`matchGitHubRepository` derives `{owner, name}` purely from parsing the text of the current git remote URL [3](#0-2) . `repositoryWithRefreshedGitHubRepository` uses that owner/name pair to call `api.fetchRepository(owner, name)` — a live lookup keyed on a mutable, re-assignable identifier — and if a repo is returned, unconditionally forwards it into `updateRemoteUrl` [4](#0-3) .

`updateRemoteUrl` then decides whether to rewrite the local `origin` remote based only on:
1. protocol match between old and new URL,
2. whether the **stale, locally cached** `gitHubRepository.cloneURL` (from the last successful association) still matches the current git remote (`remoteUrlUnchanged`),
3. whether the current remote differs from the freshly fetched `apiRepo.clone_url`.

If all three hold, it silently calls `gitStore.setRemoteURL(...)` to point `origin` at the new `clone_url` [5](#0-4) . No comparison is made against the previously known **stable numeric GitHub repository id** — only the mutable `owner/name` strings are ever checked, exactly mirroring the oracle report's flaw of trusting a value that can be manipulated by an outside actor within a time window instead of validating against an immutable ground truth.

Owner logins and repository names on GitHub are not permanent: accounts and repos can be renamed, transferred, or deleted, freeing the name for registration by anyone (a well-known "repo-jacking"/dependency-confusion style class of attack). If the original `owner/name` becomes available and an attacker claims it and creates a repository there, the next background refresh (`refreshSelectedRepositoryAfterAccountChange`, triggered on account/sign-in changes, or any of the several call sites of `withRefreshedGitHubRepository` for fetch/pull/push flows) will resolve that owner/name to the attacker's `IAPIRepository` object and rewrite `origin` to the attacker's `clone_url` with zero user interaction or confirmation.

### Impact Explanation
Once `origin` silently points at an attacker-controlled repository, subsequent user-initiated `git push` will send the user's commits/history to the attacker's server (source and credential/secret exfiltration), and subsequent `git pull`/fetch/checkout can merge attacker-controlled content into the user's working tree, which can lead to execution of malicious build/config files opened later by other tooling. This satisfies "silent corruption of what the user commits or pushes" and, depending on subsequent pull/merge, could feed attacker content back into the workspace — both explicitly listed as valid impact categories.

### Likelihood Explanation
This requires no local access, no leaked credentials, no unusual user action, and no social engineering step beyond the normal passive use of Desktop (background refresh happens automatically). The only precondition is that the original `owner/name` pair used for a tracked repository becomes available for re-registration (deleted/renamed account or repo) and an attacker claims it — a scenario documented in real-world repo-jacking incidents. `updateRemoteUrl`'s test suite confirms the update path is exercised specifically when "the github url changes" with no additional identity check [1](#0-0) , so the guard rails (`protocolsMatch`, `remoteUrlUnchanged`) are all satisfiable by an attacker who simply re-registers the same owner/name and creates a repo with a matching protocol clone URL.

### Recommendation
Before silently rewriting `origin`, compare the freshly fetched `apiRepo`'s immutable numeric `id` against the previously stored `gitHubRepository`'s `dbID`/API id (not just owner/name/URL text). If the ids differ, treat this as a repository identity change and require explicit user confirmation (similar to the existing `AddSSHHost`/"unsafe repository" trust-prompt patterns already used elsewhere in Desktop [6](#0-5) ) instead of auto-updating the remote.

### Proof of Concept
1. User adds/clones `https://github.com/OwnerA/project` in Desktop; Desktop caches `GitHubRepository.cloneURL` for this owner/name.
2. `OwnerA` account is renamed/deleted (or the repo is deleted/renamed), freeing the `OwnerA/project` slug.
3. Attacker registers `OwnerA` and creates a repo named `project`, setting its `clone_url` to their own malicious remote.
4. On the user's next sign-in/account refresh or scheduled repository refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository('OwnerA','project')`, which now returns the attacker's `IAPIRepository` [7](#0-6) .
5. `updateRemoteUrl` finds `remoteUrlUnchanged === true` (local remote still matches the stale cached cloneURL) and `urlsMatch === false` (attacker's URL differs from current remote), so it calls `gitStore.setRemoteURL('origin', <attacker clone_url>)`, silently repointing the user's `origin` [8](#0-7) .
6. The user's next `git push` sends their code to the attacker's repository.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
