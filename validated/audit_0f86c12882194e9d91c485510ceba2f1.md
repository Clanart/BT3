## Analysis

I traced the exact call path described. The vulnerability is real and stems from how reward distribution works in `BaseRewardPoolV2`/`BribeRewardPool`.

**Root cause**: `vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` which increases `totalSupply` and the attacker's `_balances` immediately, with `userRewardPerTokenPaid` snapshotted to the *current* `rewardPerTokenStored` [1](#0-0) . There is no cooldown or minimum holding period enforced on `vote()` or `unvote()` [2](#0-1) .

When `castVotes()` is subsequently called, it triggers `WombatStaking.vote()` → `IBaseRewardPool(_rewarders[i]).queueNewRewards(...)` [3](#0-2) , which calls `_provisionReward` and instantly credits the entire new reward into `rewardPerTokenStored` proportional to `totalStaked()` at that single instant [4](#0-3) . This is a lump-sum/instantaneous distribution model, not a streamed/time-weighted rate model — so whoever holds stake at the exact moment `queueNewRewards` executes captures reward pro-rata to their balance, regardless of how briefly they've held it.

The attacker then calls `unvote()`, which calls `IBribeRewardPool(rewarder).withdrawFor(msg.sender, currentVote, true)` [5](#0-4) , triggering `_getReward` → `earned()` computed via `_earned` using the now-increased `rewardPerToken(_rewardToken)` minus the attacker's pre-harvest-snapshotted `userRewardPerTokenPaid` [6](#0-5) , allowing full pro-rata claim of the newly queued reward in the same or next block.

No modifier, nonReentrant guard, or time-weighting mechanism in `BribeRewardPool`/`BaseRewardPoolV2` prevents this — the `updateRewards` modifier only settles balances at snapshot time, it doesn't gate against instantaneous stake/unstake around a distribution event [7](#0-6) .

### Title
Instant reward sniping via vote()/castVotes()/unvote() sequence dilutes long-term voter bribe yield - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.vote()` allows any vlMGP holder to instantly increase their staked weight in a specific pool's `BribeRewardPool` immediately before `castVotes()` harvests and queues new bribe rewards, then withdraw via `unvote()` right after, capturing a full pro-rata share of the just-harvested reward despite holding the position for only one transaction/block.

### Finding Description
`vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` with no cooldown, immediately increasing `totalSupply` and the caller's balance in the target rewarder [1](#0-0) . `castVotes()`/`harvestSinglePool()` then triggers `wombatStaking.vote()`, which calls `queueNewRewards` on the rewarder, crediting `rewardPerTokenStored` as `(_amountReward * 10**decimals) / totalStaked()` computed at that instant [4](#0-3) . Because the attacker's stake is already included in `totalStaked()` when this happens, and their `userRewardPerTokenPaid` was frozen at the pre-harvest value during `vote()`, calling `unvote()` immediately after lets them claim the full pro-rata share of that lump-sum reward via `withdrawFor(msg.sender, currentVote, true)` → `_getReward` [8](#0-7) [9](#0-8) . This dilutes the reward available to voters who kept their vote allocated to that pool for the entire accrual period, since the distribution model is instantaneous rather than time-weighted/streamed.

### Impact Explanation
This is a theft/dilution of unclaimed yield: long-term voters who kept vlMGP locked in a pool's rewarder over time have their pro-rata share of harvested bribes diluted by a flash voter who only holds the position for the harvest transaction. This matches the Immunefi impact class "theft of unclaimed yield" for existing depositors/voters, since capital is redirected from legitimate long-term voters to opportunistic flash voters with no time-weighted commitment.

### Likelihood Explanation
The precondition is that the attacker already holds/controls enough locked vlMGP voting power to redirect (no new capital lock or flash loan of vlMGP is required within the transaction — vlMGP itself typically requires prior locking, but existing legitimate vlMGP holders can repeat this every harvest cycle by pointing votes at whichever pool is about to be harvested). There is no cooldown on `vote()`/`unvote()` in `WombatBribeManager.sol`, and the attack is fully repeatable each time `castVotes()`/`harvestSinglePool()` is called on a pool with meaningful pending bribes. The main capital requirement is temporarily holding vlMGP voting power large enough to matter relative to `totalStaked()` in the target rewarder, and calling `vote()`→(wait for/trigger `castVotes`)→`unvote()`, which can even be atomic if the attacker is also the caller of `castVotes()`/`harvestSinglePool()`.

### Recommendation
Change the bribe reward distribution model from instantaneous/lump-sum crediting to time-weighted streaming (e.g., a `rewardRate` distributed linearly over a fixed duration as in standard `StakingRewards`/Synthetix designs), or add a minimum holding/cooldown period between `vote()` and `unvote()` for a given pool so a voter must have held their allocation for a minimum duration (e.g., since `lastCastTime`) before being eligible to claim newly queued rewards from that harvest.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `WombatStaking`, and a `BribeRewardPool` for a test pool, with two vlMGP holders: `longTermVoter` (votes for the pool many blocks/harvest-cycles in advance) and `flashVoter` (has vlMGP power available but has not voted for this pool yet).
2. Advance time/blocks so `longTermVoter`'s position has been staked in the rewarder well before the next harvest.
3. Immediately before calling `castVotes(false)` (or `harvestSinglePool`), have `flashVoter` call `vote([lp], [+X])` where `X` equals `longTermVoter`'s existing stake (to make their share ~50%).
4. Call `castVotes(false)` (as any caller), which internally calls `wombatStaking.vote()` → `queueNewRewards()` on the pool rewarder, crediting a known bribe reward amount `R`.
5. Immediately after, have `flashVoter` call `unvote(lp)`.
6. Assert: `flashVoter` receives ~`R * X / totalStaked` in reward tokens despite having staked for 0 elapsed blocks before the harvest, and this is non-zero and comparable to `longTermVoter`'s share when `claimBribe` is later called by `longTermVoter`.
7. Assert that `longTermVoter`'s claimable reward is correspondingly reduced compared to a control scenario where `flashVoter` never participated.

        if (_lps.length != _deltas.length)
            revert LengthMismatch();

        uint256 length = _lps.length;
        int256 totalUserVote;

        for (uint256 i; i < length; i++) {
            Pool storage pool = poolInfos[_lps[i]];
            if (!pool.isActive)
                revert PoolNotActive();
            int256 delta = _deltas[i];
            totalUserVote += delta;
            if (delta != 0) {
                if (delta > 0) {
                    pool.totalVoteInVlmgp += uint256(delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] += uint256(delta);
                    IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta));
                } else {
                    pool.totalVoteInVlmgp -= uint256(-delta);
                    userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] -= uint256(-delta);
                    IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(-delta), false);
                }
            }
        }

        if (msg.sender != delegatedPool) {
            if (totalUserVote > 0) {
                userTotalVotedInVlmgp[msg.sender] += uint256(totalUserVote);

    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
