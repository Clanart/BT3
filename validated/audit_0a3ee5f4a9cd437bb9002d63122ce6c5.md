### Title
Unclaimed Plot NFT pool rewards become permanently unclaimable when the pool state changes before the forwarding spend confirms - (File: chia/wallet/plotnft_wallet/plotnft_wallet.py, chia/pools/plotnft_drivers.py)

### Summary
`PlotNFT2Wallet` requires that pending farming rewards received while pooling be moved into the singleton via `forward_pool_reward()` (a per-reward-coin spend built against the *current* plot-NFT puzzle/state), because `claim_rewards()` explicitly refuses to run while pooling [1](#0-0) . If the owner switches configuration — calling `leave_pool()` / `join_pool()` — while a pool reward has not yet been forwarded/claimed, the round-based state transition proceeds without first settling (forwarding) the outstanding reward, and that reward becomes stranded, mirroring the ClaggBaseAdapter `setIncentive` bug where switching to a new incentive round without checking/compounding unclaimed incentives locks funds.

### Finding Description
`PlotNFT2Wallet.claim_rewards()` is only reachable when the plot NFT is not pooling; it raises `"Cannot claim rewards while pooling. If you're a pool, try forward_pool_rewards"` otherwise [2](#0-1) . `PlotNFT.claim_pool_rewards()` (used by `claim_rewards`) itself also guards with `if self.pooling: raise ValueError(...)` [1](#0-0) . The only path to settle a reward while pooling is `forward_pool_reward()`, which builds a spend committed to the *current* singleton puzzle/inner-puzzle hash and a `SEND_MESSAGE` referencing the specific reward coin.

`leave_pool()` transitions the plot NFT to `exiting=True` and immediately produces a new spend that advances the singleton tip (`plotnft.exit_to_waiting_room(...)`) without checking for, or forwarding, any outstanding un-forwarded pool rewards recorded in `plotnft2_store` [3](#0-2) . This is functionally identical to the reported bug: the action that changes the "round"/configuration (pool state) is not gated on first draining/compounding pending incentives (rewards) tied to the previous configuration.

The wallet's own test suite documents the resulting fund loss directly: sections explicitly titled `# LOSE REWARDS (while pooling)` and `# LOSE REWARDS (while leaving)` show a pool reward being forwarded concurrently with/after a state transition, and the reward amount is deducted from the plot NFT balance as `confirmed_wallet_balance -= POOL_REWARD_AMOUNT` with no corresponding credit anywhere else in the wallet [4](#0-3) , and again [5](#0-4) .

### Impact Explanation
A plot-NFT owner (single wallet user, no malicious peer required) who calls `leave_pool()`/`join_pool()` while a pool reward has been farmed but not yet forwarded/claimed will permanently lose that reward's value, since (a) it can no longer be forwarded because the singleton state it was built against has moved on, and (b) `claim_rewards()`/`claim_pool_rewards()` cannot run for it until pooling stops, by which point the coin/commitment tied to the now-stale singleton spend is invalid. This is concrete unauthorized loss of value for the plot-NFT owner — funds become stuck at the p2-singleton reward address, unreachable by any documented recovery path in the wallet API.

### Likelihood Explanation
This requires no adversarial actor: any plot-NFT owner who is actively pooling and receives a farming reward, then decides to leave/switch pools before forwarding that reward (a plausible, even common, sequence of user-initiated wallet actions), triggers the loss. The wallet's own regression tests reproduce this exact scenario, confirming it is a reachable, non-contrived condition rather than a purely theoretical or mocked-only path.

### Recommendation
Before performing a pool-state-changing action (`leave_pool`/`join_pool`), the wallet should check `plotnft2_store` for any outstanding, un-forwarded pool rewards for the plot NFT and either automatically forward/compound them into the same spend bundle, or block the transition until the caller explicitly forwards/claims them — analogous to calling `compound` before `setIncentive` in the referenced report.

### Proof of Concept
The existing test `test_plotnft_lifecycle` in `chia/_tests/wallet/plotnft_wallet/test_plotnft_wallet.py` already demonstrates the loss end-to-end: pool rewards are farmed while pooling, `forward_pool_reward` is raced against/interleaved with `join_pool`/`leave_pool` state transitions, and the post-condition balance assertions show the reward amount being subtracted from the plot NFT wallet with no compensating credit [6](#0-5) [7](#0-6) .

Note: I was not able to fully inspect the body of `forward_pool_reward()` (only confirmed its presence via `grep_search`) within the available tool budget, so the exact CLVM-level mechanism of why the stale spend can no longer settle after a state transition (e.g., `SEND_MESSAGE`/`ASSERT_MY_PUZZLEHASH` commitments becoming invalid) is inferred from the sibling `claim_pool_rewards()` implementation and the test evidence rather than directly read line-by-line; a full review of `chia/pools/plotnft_drivers.py`'s `forward_pool_reward` and `exit_to_from_waiting_room_inner_solution` would be needed to state the precise CLVM condition that fails.
