### Title
`aptos move verify-package` never fetches or compares on-chain bytecode, so "verified source" claims can be spoofed by publishing bytecode that does not match the claimed source metadata - ([File: aptos-move/cli/src/commands.rs], [File: aptos-move/cli/src/stored_package.rs])

### Summary
The `VerifyPackage` CLI command is documented as downloading a package "and verifies the bytecode matches a local compilation of the Move code," but its implementation only compares `PackageMetadata` fields (name, deps, module source text, manifest, upgrade policy, extension, `source_digest`) — it never downloads or diffs the actual on-chain compiled module bytes against a local build. [1](#0-0) [2](#0-1) 

### Finding Description
`VerifyPackage::execute` creates a `CachedPackageRegistry` with `with_bytecode = false`, meaning `registry.bytecode` is never populated with the deployed module bytes: [3](#0-2) . It then calls `package.verify(&compiled_metadata)`, whose full implementation only checks equality of `name`, `deps`, `modules` (which is `ModuleMetadata`, containing only `name`, gzipped `source`, `source_map`, and `extension` — not raw bytecode), `manifest`, `upgrade_policy`, `extension`, and `source_digest`: [4](#0-3) . Nowhere in this path is `registry.get_bytecode(...)` invoked, even though that method exists specifically to fetch on-chain module bytecode via `get_account_module` when `with_bytecode = true`: [5](#0-4) [6](#0-5) .

Compounding this, the on-chain `code::publish_package` Move function never checks that `ModuleMetadata.source` (the human-readable, gzipped source text carried in metadata) corresponds in any way to the actual `code: vector<vector<u8>>` bytecode bundle passed to `request_publish`/`request_publish_with_allowed_deps`: [7](#0-6) . On-chain validation (`validate_publish_request`) only checks module *names* against the metadata's declared module list and dependency addresses/names — never source-text-to-bytecode correspondence: [8](#0-7) .

Combining these two facts: a publisher can attach arbitrary/benign-looking Move source text and a matching `source_digest` to metadata while deploying a bytecode bundle that was compiled from entirely different (malicious) source, as long as module names line up. Anyone relying on `aptos move verify-package` (e.g., an explorer, auditor, or end user checking "this contract's source is verified") will see `"Successfully verified source of package"` even though the deployed bytecode was never compared to, and may not match, the claimed source.

### Impact Explanation
This breaks the code-safety invariant that "verified bytes, package metadata... and committed module bytes" agree, per the publish-path threat model. A malicious or compromised publisher can present clean, auditable Move source in on-chain metadata (satisfying `verify-package`) while shipping different bytecode that performs malicious logic (e.g., backdoored admin functions, hidden fee siphons, or logic diverging from displayed source). This is a genuine trust/verification bypass on the publish path affecting any tooling or user that relies on Aptos's package metadata/verify flow as a substitute for bytecode-level audit, which is the core purpose advertised by the command. However, the impact is client-tooling / off-chain trust degradation rather than a direct on-chain fund-loss or consensus-safety bug; it does not itself let an attacker seize ownership, bypass upgrade policy, or write illegal bytecode into a *protected* address — it undermines the verification signal, not access control.

### Likelihood Explanation
High likelihood of occurrence in practice: any publisher (fully permissionless — no elevated privileges required) can supply mismatched `source`/`source_digest` alongside arbitrary bytecode today, since neither the Move VM publish path nor the CLI's `verify-package` command performs a bytecode-level comparison. Exploitation requires no special access; it is a natural consequence of the current design where `ModuleMetadata.source` is purely advisory and `verify-package` defaults to `with_bytecode = false`.

### Recommendation
- Change `VerifyPackage::execute` to always fetch on-chain bytecode (`CachedPackageRegistry::create(..., true)`) and compare each downloaded module's bytes byte-for-byte against the bytecode produced by locally compiling the fetched/claimed source, rejecting on any mismatch.
- Consider adding a native/on-chain check (or at minimum documenting prominently) that `ModuleMetadata.source`/`source_digest` are *not* cryptographically bound to the published bytecode, so downstream integrators (explorers, wallets) do not treat a successful `verify-package` result as bytecode-level proof unless bytecode was actually diffed.
- Rename/adjust the success message (`"Successfully verified source of package"`) and doc comments to accurately reflect what was verified, avoiding the misleading claim that "bytecode matches."

### Proof of Concept
1. Publish a package at address `0xcafe` with `code::publish_package_txn`, supplying:
   - `metadata.modules[0].source` = gzip("public fun withdraw(...) { /* benign, audited-looking logic */ }")
   - `metadata.source_digest` = sha256 hash matching that benign source
   - `code[0]` = actual compiled bytecode of a *different* module with the same module name but containing a backdoored `withdraw` that transfers funds to attacker (module names must match; the VM only checks names/dependencies, not source-to-bytecode correspondence — `validate_publish_request` in `aptos-move/aptos-vm/src/aptos_vm.rs:1804-1843`).
2. Transaction succeeds because `code::publish_package` and `validate_publish_request` never inspect `ModuleMetadata.source` versus the compiled bytecode.
3. A third party runs `aptos move verify-package --account 0xcafe` against the local (benign) source tree.
4. `VerifyPackage::execute` builds locally, calls `CachedPackageRegistry::create(client, account, false)` (bytecode never fetched) and `package.verify(&compiled_metadata)`, which only compares metadata/source-digest fields — both of which the attacker deliberately made consistent with the benign source.
5. The CLI prints `"Successfully verified source of package"`, falsely certifying that the deployed bytecode matches the shown benign source, while the actual on-chain module executes the backdoored logic.

impl CliCommand<&'static str> for VerifyPackage {
    fn command_name(&self) -> &'static str {
        "VerifyPackage"
    }

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }

    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    public fun publish_package(owner: &signer, pack: PackageMetadata, code: vector<vector<u8>>) acquires PackageRegistry {
        // Disallow incompatible upgrade mode. Governance can decide later if this should be reconsidered.
        assert!(
            pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy,
            error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED),
        );

        let addr = signer::address_of(owner);
        if (!exists<PackageRegistry>(addr)) {
            move_to(owner, PackageRegistry { packages: vector::empty() })
        };

        // Checks for valid dependencies to other packages
        let allowed_deps = check_dependencies(addr, &pack);

        // Check package against conflicts
        // To avoid prover compiler error on spec
        // the package need to be an immutable variable
        let module_names = get_module_names(&pack);

        // Record, per module in this package, the object's transitive root owner at (re)publish, so
        // lazy self-init can detect a later transfer of the object or an ancestor since that module
        // was published (see `init::internal_maybe_initialize`). Objects only; feature-gated.
        if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
            let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
            module_names.for_each_ref(|name| {
                init::record_deploy_owner(addr, *name.bytes(), owner);
            });
        };
        let package_immutable = &borrow_global<PackageRegistry>(addr).packages;
        let len = package_immutable.length();
        let index = len;
        let upgrade_number = 0;
        package_immutable.enumerate_ref(|i, old| {
            let old: &PackageMetadata = old;
            if (old.name == pack.name) {
                upgrade_number = old.upgrade_number + 1;
                check_upgradability(old, &pack, &module_names);
                index = i;
            } else {
                check_coexistence(old, &module_names)
            };
        });

        // Assign the upgrade counter.
        pack.upgrade_number = upgrade_number;

        let packages = &mut borrow_global_mut<PackageRegistry>(addr).packages;
        // Update registry
        let policy = pack.upgrade_policy;
        if (index < len) {
            pack.modules.for_each_ref(|m| {
                let m: &ModuleMetadata = m;
                init::reset_initialized(addr, *m.name.bytes());
            });
            *packages.borrow_mut(index) = pack
        } else {
            packages.push_back(pack)
        };

        event::emit(PublishPackage {
            code_address: addr,
            is_upgrade: upgrade_number > 0
        });

        // Request publish
        if (features::code_dependency_check_enabled())
            request_publish_with_allowed_deps(addr, module_names, allowed_deps, code, policy.policy)
        else
        // The new `request_publish_with_allowed_deps` has not yet rolled out, so call downwards
        // compatible code.
            request_publish(addr, module_names, code, policy.policy)
    }
