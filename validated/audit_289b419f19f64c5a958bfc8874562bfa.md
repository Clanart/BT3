### Title
Fee/vsize calculation omits the OP_RETURN data output, undercharging the transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output carrying caller-supplied `data` onto `tx_outs`, but then computes the transaction's weight/vbytes via `calculate_weight_vbytes`, which is only passed `tx_ins.len()` and `payments` — the data output is never included. The result is an underestimated `vbytes`, hence an underestimated `needed_fee` and an underestimated `weight`, while the serialized transaction actually contains the extra output.

### Finding Description
The reported bug class is a conversion/aggregation that accounts for only one side of the value being transformed. Here, the size-to-fee conversion accounts for payment outputs and (later) the change output, but not the OP_RETURN output:

```rust
// networks/bitcoin/src/wallet/send.rs:193-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a mock `Transaction` solely from `payments` and an optional `change` script — there is no parameter for data outputs:

```rust
// networks/bitcoin/src/wallet/send.rs:62-99
fn calculate_weight_vbytes(inputs, payments, change) -> (u64, u64) {
  let mut tx = Transaction { ..., output: payments.iter().map(...).collect() };
  if let Some(change) = change { tx.output.push(...); }
  ...
}
```

The minimum-fee check and the change-amount calculation both reuse these understated figures:

- `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` — checks against a too-small `vbytes`.
- `input_sat.checked_sub(payment_sat + fee_with_change)` — `fee_with_change` also excludes the data output's size, so change absorbs the sats that should have paid for those bytes.
- `weight > MAX_STANDARD_TX_WEIGHT` — the weight check can pass even though the real transaction is up to ~90 bytes heavier.

### Impact Explanation
The produced transaction pays `needed_fee` sats, but its real vsize is larger than `vbytes` because the OP_RETURN output (up to 80 bytes of data plus ~10 bytes of output overhead) was never counted. Consequently:

1. The effective fee rate is strictly lower than the caller-requested `fee_per_vbyte`.
2. A transaction that the `TooLowFee` guard was meant to reject can be emitted with a true fee rate below the 1000 sat/kilo-vbyte minimum relay fee; standard nodes will refuse to relay/accept it, leaving the constructed spend unbroadcastable and the inputs unspendable by this TX until reconstructed.
3. The change output is overvalued by the missing fee amount (the fee difference is swept into change rather than paid), misreporting what the change will actually be worth relative to intent.

An unprivileged caller reaches this purely through public inputs: `data: Option<Vec<u8>>` (≤ 80 bytes) passed to `SignableTransaction::new`.

### Likelihood Explanation
Any signing flow that passes `Some(data)` — the processor uses OP_RETURN `Shorthand` payloads for batched sends — triggers the miscalculation. The discrepancy is deterministic and grows with the data length; with a marginal `fee_per_vbyte`, the effective rate falls below relay minimums.

### Recommendation
Include the OP_RETURN output in the size estimation. Either build the data `TxOut` before calling `calculate_weight_vbytes` and pass a combined output list, or extend `calculate_weight_vbytes` to accept additional outputs:

```rust
let mut all_outputs: Vec<(ScriptBuf, u64)> = payments.to_vec();
if let Some(data) = &data {
  all_outputs.push((
    ScriptBuf::new_op_return(PushBytesBuf::try_from(data.clone())?),
    0,
  ));
}
let (mut weight, vbytes) =
  Self::calculate_weight_vbytes(tx_ins.len(), &all_outputs, None);
```

Apply the same for the `vbytes_with_change` computation so `fee_with_change`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the true transaction.

### Proof of Concept
Call `SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte)` with `fee_per_vbyte` chosen just above the relay minimum relative to the underestimated `vbytes`. The function returns `Ok` with `needed_fee = fee_per_vbyte * vbytes`, but the real transaction serializes the extra ~90-byte OP_RETURN output, so `fee() / tx.vsize() < fee_per_vbyte` and can fall below `DEFAULT_MIN_RELAY_TX_FEE / 1000`, producing a transaction standard nodes reject — despite the constructor having "validated" the fee.
