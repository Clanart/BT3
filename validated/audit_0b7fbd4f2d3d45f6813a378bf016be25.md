Confirmed and critical: `dispatch_request` (via `pallet_ismp::Pallet::<T>::dispatch_request`) accepts an attacker-supplied `from: Vec<u8>` with **no validation that the caller is authorized to use that module id**. Any pallet, including a generic `send_message`/`dispatch_to_evm` extrinsic callable by `ensure_signed(origin)` (as shown in the docs' example pallet and `pallet-demo`), can construct a `DispatchPost{ dest: StateMachine::Evm(X), from: <anything>, to: <hostManagerAddress>, body: <SetHostParam payload> }`. On the EVM side, `HostManager::onAccept` only validates `request.source == hyperbridge` (i.e., that it came from the Hyperbridge parachain state machine) — it never checks `request.from` against an expected pallet id, unlike e.g. `pallet-bandwidth`'s manager which validates `request.from` matches the registered manager address.

### Title
Unauthenticated `from` field lets any Hyperbridge-chain pallet/user take over `EvmHost` via `HostManager.onAccept` - (File: evm/src/core/HostManager.sol)

### Summary
`HostManager.onAccept` authorizes governance-only actions (`SetHostParam`, `Withdraw`) solely by checking `request.source == hyperbridge`, never checking `request.from` (the sending module/pallet id on Hyperbridge). Since any pallet on the Hyperbridge parachain can dispatch a POST request with a caller-chosen `from` value via `IsmpDispatcher::dispatch_request`, any account able to reach a generic dispatch extrinsic can forge a request that appears to originate from Hyperbridge and target the `HostManager` contract, triggering `updateHostParams` or `withdraw`.

### Finding Description
`HostManager::onAccept` [1](#0-0)  only enforces:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
```
It decodes `request.body` and dispatches to `IHostManager(_params.host).updateHostParams(...)` or `.withdraw(...)` based purely on the action byte — with no check of `request.from` against a specific, expected pallet/module id (e.g. `HostExecutive`'s `PALLET_ID`). Compare this to `pallet-bandwidth`'s manager pattern, which explicitly validates `request.from` matches the registered manager address before crediting [2](#0-1) , and `BandwidthGate`'s purchase-message identification which keys off `request.from` matching the registered manager.

On the Hyperbridge chain, `IsmpDispatcher::dispatch_request` builds the outgoing `PostRequest` directly from caller-supplied `DispatchPost.from`, with no verification tying `from` to the calling pallet's own identity: [3](#0-2) . Any pallet exposing a signed-origin dispatch extrinsic (the documented pattern is exactly this, e.g. `send_message`/`dispatch_to_evm` in the developer docs and `pallet-demo::dispatch_to_evm`) lets a caller set `to = <HostManager address>` and `body = 0x01 (SetHostParam) || abi.encode(HostParams{admin: attacker, hostManager: attacker, handler: attacker, consensusClient: attacker, ...})`. Because `HostManager.onAccept` never checks `from`, the forged request is accepted as legitimate governance, and `EvmHost.updateHostParamsInternal` only validates structural well-formedness of the new params (non-zero addresses with matching interfaces) [4](#0-3)  — not that the caller was authorized to submit them. This allows full takeover of `admin`, `hostManager`, `handler`, and `consensusClient`, or a direct `Withdraw` action draining `feeToken`/native balances to an attacker beneficiary via `EvmHost.withdraw` [5](#0-4) .

### Impact Explanation
This breaks the Impact Gate's "unauthorized transaction or execution" and "cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow" criteria directly. A successful forged `SetHostParam` gives the attacker full control of the `EvmHost` (new `consensusClient` → false state acceptance for all future messages; new `handler`/`admin` → arbitrary message processing), and a forged `Withdraw` drains host-held bridge revenue to an attacker-chosen address — direct fund loss with no reliance on a malicious relayer, prover, or governance actor.

### Likelihood Explanation
Requires only a signed extrinsic on the Hyperbridge parachain reaching some pallet's `dispatch_request`/`dispatch_to_evm`-style call that lets the caller set `to` freely (the documented dispatching pattern shown in `docs/content/developers/polkadot/dispatching.mdx` and mirrored by `pallet-demo`). **Uncertainty**: I could not fully confirm from the index whether the production runtime (`gargantua`/`nexus`) exposes a permissionless pallet whose `to`/`body` are fully attacker-controlled in the currently deployed runtime, versus this pattern existing only in docs/demo pallets for developer education. If no production pallet allows an unprivileged, fully-controlled `to`+`body` POST dispatch, the practical reachability is lower and would need confirmation against the live runtime configuration — worth flagging to the team regardless, since the missing `request.from` check in `HostManager.onAccept` is a genuine defense-in-depth gap independent of current dispatch surface.

### Recommendation
In `HostManager::onAccept`, additionally validate `request.from` equals the expected, hard-coded/pre-registered `HostExecutive` pallet id (mirroring how `pallet-bandwidth`'s manager validates the counterpart's `from`/registered address), rejecting any request whose `from` does not match.

### Proof of Concept
1. On Hyperbridge parachain, from any signed account, call a pallet extrinsic that internally invokes `T::IsmpDispatcher::dispatch_request` with attacker-chosen `DispatchPost{ dest: StateMachine::Evm(hostChainId), from: <arbitrary bytes>, to: <HostManager address bytes>, timeout: 0, body: 0x01 || abi.encode(HostParams{ hostManager: attackerHostManager, admin: attacker, handler: attackerHandler, consensusClient: attackerConsensusClient, feeToken: existingFeeToken, uniswapV2: existing, unStakingPeriod: existing, challengePeriod: existing, stateMachines: existing, hyperbridge: existingId }) }`.
2. A relayer (unprivileged, just performing normal message relaying) delivers the request+proof to `EvmHost` on the destination chain; the ISMP handler routes it to `HostManager.onAccept`.
3. `onAccept` passes the `source == hyperbridge` check (it is genuinely from the Hyperbridge chain) and, seeing action byte `0x01`, calls `IHostManager(host).updateHostParams(hostParams)`.
4. `EvmHost.updateHostParamsInternal` only checks structural validity of the new addresses (non-zero, correct interface) [6](#0-5) , so it accepts the attacker's params, and `_hostParams.admin`/`hostManager`/`handler`/`consensusClient` are overwritten to attacker-controlled addresses [7](#0-6) .
5. The attacker now controls the host: they can freeze/unfreeze the bridge as `admin`, accept forged consensus (`consensusClient`), or immediately call `withdraw` as the new `hostManager` to drain `feeToken` balances to themselves.

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
