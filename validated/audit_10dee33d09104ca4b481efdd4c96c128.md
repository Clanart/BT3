### Title
`ThresholdKeys::new`/`ThresholdKeys::read` never validate that the secret share and verification shares form a consistent Shamir sharing, so crafted key bytes yield a `group_key` whose funds are unspendable - (File: crypto/dkg/src/lib.rs)

### Summary
The external report's class is a constructor/setter that stores a structured parameter object without checking internal semantic validity (`isValid()`), letting crafted field combinations produce a broken yet accepted state. The Serai analog is `ThresholdKeys`: its constructor performs only cardinality and index-range checks, never verifying that `verification_shares` lie on a single degree-`t-1` polynomial, nor that `G * secret_share == verification_shares[i]`. `ThresholdKeys::read` — explicitly reachable with untrusted bytes — routes through `ThresholdKeys::new`, so any deserialized blob satisfying the shallow checks is accepted as valid signing keys.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new` validates only:
- `verification_shares.len() == params.n()` (lines 355–360),
- each key `<= params.n()` (lines 361–365),
- `Interpolation::Constant` only when `t == n` (lines 367–374).

It then derives `group_key` by Lagrange-interpolating **only** the verification shares of participants `1..=t` (lines 376–378). Nothing checks:
1. That `C::generator() * secret_share == verification_shares[&params.i()]` — the secret share is never bound to its own verification share.
2. That verification shares for participants `t+1..=n` lie on the same polynomial as `1..=t` — they are indexed into `verification_shares` at `view()` time (line 502) and interpolated there, but the group key was fixed by the first `t` shares only.

`ThresholdKeys::read` (lines 574–632) reads `t`, `n`, `i`, an `Interpolation`, `secret_share`, and `n` arbitrary points via `read_G`/`read_F` (which enforce only canonical encodings, per `ciphersuite/src/lib.rs` lines 74–101), then calls `ThresholdKeys::new`, re-exporting the result as valid keys. `Participant::new` and `ThresholdParams::new` only enforce `i <= n` range checks (lines 591–602, 625–631).

Contrast with `recovery::recover_key` (`crypto/dkg/recovery/src/lib.rs` lines 80–82), which explicitly verifies `G * recovered_secret == group_key` — the codebase itself recognizes that this consistency invariant is not otherwise guaranteed, yet the trusted constructor never establishes it.

### Impact Explanation
An attacker who controls the serialized bytes consumed by `ThresholdKeys::read` (key-exchange/backup/reshare material, or any pipeline deserializing threshold keys from an untrusted channel) supplies `n` arbitrary verification-share points plus an arbitrary `secret_share`. The resulting `ThresholdKeys` reports a `group_key` computed solely from shares `1..=t` — that key is what downstream code (e.g., `tweak_keys`/`Scanner` in `networks/bitcoin/src/wallet/mod.rs` lines 46–166) advertises as a deposit address. Because shares `t+1..=n` need not satisfy the same polynomial, any signing set other than exactly `1..=t` interpolates a *different* discrete log at `view()` (lines 494–507); and because `secret_share` is never checked against `verification_shares[i]`, even set `1..=t` may hold shares inconsistent with the group key. The consequence is funds reported received under `group_key()` that no quorum can ever sign for — accepted as impact "funds reported received that are not spendable". Additionally, `ThresholdView::verification_share` uses the same unverified points during FROST share verification, so a malformed set silently aborts or mis-attributes honest signers.

### Likelihood Explanation
Likelihood depends on an integrator feeding attacker-influenced bytes to `ThresholdKeys::read`, which the scan rules explicitly treat as in-reach for `read_*` entry points. The inputs required are trivially constructible (any `n` valid compressed points and any canonical scalar), unlike the original report's merely-revert impact — here the invalid object is *accepted and used*, making the outcome strictly worse than the upstream bug class.

### Recommendation
In `ThresholdKeys::new` (and thereby `ThresholdKeys::read`), enforce full consistency:
1. Require `C::generator() * secret_share == verification_shares[&params.i()]`; reject otherwise.
2. Verify the verification shares form a single degree-`t-1` polynomial — e.g., check that the `group_key` recomputed by interpolating a *second* distinct `t`-subset (or each share against the polynomial via the `exponential`/multiexp check already used in `pedpop`'s `share_verification_statements`, `crypto/dkg/pedpop/src/lib.rs` lines 430–449) matches.
3. Reject identity/zero verification shares explicitly.

### Proof of Concept
```rust
// Against crypto/dkg/src/lib.rs ThresholdKeys::read/new.
// Craft n points: set shares 1..=t to G*k_j for chosen scalars k_j on a
// degree-(t-1) polynomial P, set shares t+1..=n to arbitrary points NOT on P,
// and set secret_share to any scalar (e.g. 1), regardless of P(i).
//
// Then:
//   let keys = ThresholdKeys::<C>::read(&mut blob).unwrap();   // accepted
//   let gk = keys.group_key();          // = P(0)*G  -> deposit address
//   let view = keys.view(vec![2..=t+1]);// Ok — no error
//   // view interpolates share t+1's off-polynomial point:
//   // effective secret != P(0), so FROST aggregate signatures under `gk`
//   // fail verification; additionally G*secret_share != verification_shares[i]
//   // means this participant's own share never verifies.
// Result: group_key is a valid, scannable address whose outputs no t-of-n
// signing set (other than exactly 1..=t, and not even that if secret_share
// was mismatched) can spend.
```
The concrete divergence is guaranteed by lines 376–378 (group key fixed from `1..=t` only) versus lines 494–507 (`view` interpolating over the caller-chosen `included` set using unchecked shares), with no bridging validity check anywhere in `new`.
