### Title
`ThresholdKeys::read` performs attacker-controlled pre-allocation of the `Interpolation::Constant` coefficient vector before validating that the bytes actually exist - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` is explicitly an untrusted-bytes entry point (deserialization of key material received over the wire / from storage). After reading the `t`, `n`, `i` header fields it reads a one-byte interpolation selector. When the selector is `0` (`Interpolation::Constant`), it immediately executes `Vec::with_capacity(usize::from(n))` and then attempts to read `n` field elements — with `n` being a fully attacker-controlled `u16` up to `65535` [1](#0-0) . The allocation is committed before a single coefficient byte is required to be present, and `ThresholdParams::new(t, n, i)` validation happens only at the very end, after all the work is done [2](#0-1) .

### Finding Description
This is the same bug class as CVE-2021-20298 (OpenEXR B44Compressor): a crafted input causes the decoder to commit memory/work disproportionate to — and prior to validation of — the data actually supplied.

- At `crypto/dkg/src/lib.rs:608`, `Vec::with_capacity(n)` allocates `n * size_of::<C::F>()` (≈ 2 MB for a 32-byte field with `n = 65535`) driven by a two-byte field, before any of the coefficient bytes are read. A ~7-byte input (`0` interpolation tag + `n = 0xFFFF`) forces this allocation; the subsequent `C::read_F` fails at EOF but the oversized allocation has already been made and the `Vec` is only dropped on unwind/drop of the error path.
- The same `n` then drives the `verification_shares` loop at `crypto/dkg/src/lib.rs:620-623`, inserting up to 65535 entries into a `HashMap` and calling `read_G` per entry — again bounded only by `u16`, not by any relationship to available input or to a sane protocol parameter.
- Critically, parameter sanity (`t <= n`, `i <= n`, `t != 0`) is enforced only inside `ThresholdKeys::new`/`ThresholdParams::new` at the end (`crypto/dkg/src/lib.rs:625-631`), so all malicious shapes of `n` reach the allocation sites.
- The `n` value is never cross-checked against the actual byte length of the message; there is no `TRANSACTION_SIZE_LIMIT`-style guard as exists elsewhere (compare `coordinator/src/tributary/transaction.rs:286` which checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` before allocating).

Related code in the same file shows the pattern could trivially be worse-guarded: `borsh_deserialize_validators` in `coordinator/src/tributary/spec.rs:28-40` deserializes a u16 length and pushes items without a capacity bound — the same class.

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` (the prompt's rules explicitly include `ThresholdKeys::read` as an attacker-reachable entry point) can force repeated ~2 MB transient allocations per invocation with inputs of under a dozen bytes. In a service that repeatedly deserializes key material (e.g., during DKG re-keying, recovery flows, or validator-set churn), an attacker issuing many such requests concurrently turns this into a memory-exhaustion denial of service — the exact availability impact of the reference CVE. Impact: availability of the signing/DKG process.

### Likelihood Explanation
- Reachability: high — `ThresholdKeys::read` is a documented public deserialization API reachable with pure attacker bytes.
- Amplification: moderate — each call amplifies a handful of bytes into a ~2 MB committed allocation (plus `HashMap` growth attempts); this is a real but bounded (u16-limited) amplification factor of roughly 10⁵, sufficient for exhaustion when invoked in loops or concurrently.
- This is a Medium-severity analog: meaningful availability impact, bounded per-call amplification, requiring repeated invocations for full memory exhaustion.

### Recommendation
- In `ThresholdKeys::read`, validate `t`/`n`/`i` via `ThresholdParams::new` *before* the interpolation branch, and enforce a protocol maximum on `n` (the system already constrains participant sets to `MAX_KEY_SHARES_PER_SET`-sized bounds elsewhere).
- Replace `Vec::with_capacity(n)` with incremental `push` (allocation proportional to bytes actually present), matching the chunked-read mitigation style used in `networks/ethereum/src/machine.rs:51-60`.
- Optionally prefix the serialized form with a total-length field and reject reads where `n` implies more bytes than supplied.

### Proof of Concept
```rust
// Feeds ThresholdKeys::<C>::read a minimal malicious payload:
//   C::ID len + C::ID, then t=1, n=0xFFFF, i=1, interpolation=0 (Constant)
// Result: Vec::with_capacity(65535) commits ~2 MB for a 32-byte field
// before read_F fails on EOF — no prior parameter validation occurred.
let mut payload = vec![];
payload.extend(&(C::ID.len() as u32).to_le_bytes());
payload.extend(C::ID);
payload.extend(&1u16.to_le_bytes());      // t
payload.extend(&u16::MAX.to_le_bytes());  // n = 65535
payload.extend(&1u16.to_le_bytes());      // i
payload.push(0);                          // Interpolation::Constant
// Truncated: no coefficient bytes present
let _ = ThresholdKeys::<C>::read(&mut payload.as_slice()); // allocates ~2MB, then errors
```
