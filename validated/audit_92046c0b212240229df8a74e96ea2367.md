### Title
Inverted fee difference in `created_output` underflows and silently drops all child payments - (File: processor/src/multisigs/scheduler/utxo.rs)

### Summary
The external bug concerns a value that was already scaled by the partial-close fraction being scaled a second time inside an aggregate calculation, corrupting `settledMargin`/`poolPnlToken`/`recordPnlToken`. The analogous shape in Serai is the fee-amortization step in `Scheduler::created_output`: an already fee-reduced quantity is combined with the pre-fee quantity in the wrong direction, producing a corrupted "fee to amortize" that drives every downstream payment amount to the wrong value (here: zero — all payments dropped).

### Finding Description
When Serai cannot fulfill all queued payments in one transaction, it creates "branch" outputs which later fund child payments. `queued_plans` maps the *expected* branch amount to the payments it must fund, and `created_output` is called with the *actual* amount the branch output was created with after fees:

```rust
// Amortize the fee amongst all payments underneath this branch
let mut to_amortize = actual - expected;
```
(processor/src/multisigs/scheduler/utxo.rs:485)

The fee incurred is `expected - actual` (the output was created for `expected`, fees reduced it to `actual`). The code computes `actual - expected`, which underflows whenever `actual < expected` — the normal case, since a fee is always paid. The result is either a panic (debug / overflow-checks builds) or a wrapped, astronomically large `to_amortize` (release without overflow checks). In the wrapped case, the next check `payments sum < to_amortize` is immediately true and the function returns, dropping every child payment:

```rust
if payments.iter().map(|payment| payment.balance.amount.0).sum::<u64>() < to_amortize {
  return;
}
```
(utxo.rs:487–489)

This is confirmed wrong by the invariant immediately above: `assert_eq!(expected, payments.sum())` (utxo.rs:474), so the amount to subtract from the payments must be `expected - actual`, not `actual - expected`. As in the ELFI bug, an already-adjusted quantity (the post-fee `actual`) is fed back into a computation that treats it as the unadjusted baseline, corrupting every value derived from it.

### Impact Explanation
All payments beneath any branch output that paid a nonzero fee are silently dropped. The users' burns were already consumed from the global queue to create the branch output, so the underlying funds are spent but the corresponding external-network payments are never scheduled — a direct loss of user funds at scale (an entire branch's worth of payments per occurrence). In builds with overflow checks enabled, the underflow panics the processor instead, a liveness failure on a deterministic scheduler path. This is reachable via ordinary public inputs: any user burn that lands in a subtree deep enough to require branch outputs triggers `created_output`.

### Likelihood Explanation
Branch outputs are the normal mechanism for handling more payments than fit in one transaction (spec/processor/UTXO Management.md, "Output Frequency"), so any busy tick exercises this path. Every branch-creation transaction pays a fee, so `actual < expected` always holds when it matters; the bug triggers deterministically on the first branched plan, not probabilistically.

### Recommendation
Change line 485 to `let mut to_amortize = expected - actual;` and add a regression test asserting that child payments under a branch output are reduced by exactly the fee difference rather than dropped.

### Proof of Concept
1. Queue more burns than fit in a single Bitcoin transaction so the scheduler creates a branch output of amount `expected = sum(child payments)` (enforced by the assert at utxo.rs:474).
2. The branch-creation transaction pays fee `f`, so the created output is `actual = expected - f`.
3. `created_output` computes `to_amortize = actual - expected = -f`, which underflows to `u64::MAX - f + 1` (or panics).
4. The guard at utxo.rs:487 sees `sum(payments) < to_amortize` and returns, dropping all child payments while the branch funds remain locked in the scheduler's UTXO set.
