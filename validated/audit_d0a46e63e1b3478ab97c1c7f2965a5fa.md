### Title
Nested/recursive precompile calls cause double-application of bank balance-change events to the EVM StateDB, duplicating balances relative to the real `x/bank`/`x/precisebank` ledger - (File: precompiles/common/precompile.go, precompiles/common/balance_handler.go)

### Summary
This is the Cosmos EVM analog of the `veRAACToken` bug class: a second, independently-tracked piece of state (here, the *event-log offset* used to reconcile `x/bank` events into the EVM `StateDB`) can become inconsistent with the authoritative source of truth (the shared `sdk.Context` event manager), causing balance updates to be computed from stale/overlapping data. In `veRAACToken`, `_updateBoostState` read from an unused, always-zero mapping. Here, `BalanceHandler.AfterBalanceChange` reads from a shared, monotonically-growing event log using a per-call `prevEventsLen` cursor that does not account for events already consumed and applied to `StateDB` by a nested precompile call executed within the same `RunNativeAction` window.

### Finding Description
`Precompile.runNativeAction` in [1](#0-0)  wraps every stateful precompile call:
1. It fetches the shared `cacheCtx` via `stateDB.GetCacheContext()` [2](#0-1) .
2. Creates a **fresh** `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` and calls `BeforeBalanceChange(ctx)`, which snapshots `prevEventsLen = len(ctx.EventManager().Events())` [3](#0-2) .
3. Executes `action(ctx)` — the actual precompile logic, which may itself invoke another stateful precompile (e.g., a Solidity caller contract that calls precompile A, whose native action performs a call that re-enters the EVM and calls precompile B, or a precompile that internally triggers another precompile through a keeper call).
4. Calls `AfterBalanceChange(ctx, stateDB)`, which replays **all events since `prevEventsLen`** — `events[bh.prevEventsLen:]` [4](#0-3)  — applying `stateDB.AddBalance`/`SubBalance` for every `CoinSpent`/`CoinReceived`/`FractionalBalanceChange` event found.

Because `ctx.EventManager()` is shared across the entire call (the cache context is reused via `GetCacheContext()`/`writeCache`, per [5](#0-4) ), a nested precompile invocation that occurs **between** the outer call's `BeforeBalanceChange` and `AfterBalanceChange` will:
- record its own `prevEventsLen` cursor at nested-call start,
- emit bank/precisebank events for its own balance change,
- apply those events to `StateDB` in its own `AfterBalanceChange` (correctly, once),
- **but leave those same events physically present in the shared event log**.

When control returns to the outer call and it executes its own `AfterBalanceChange`, its slice `events[outerPrevEventsLen:]` starts *before* the nested call began and therefore **includes the nested call's already-applied events a second time**, causing the outer handler to call `AddBalance`/`SubBalance` again for the same underlying bank transfer. The real `x/bank`/`x/precisebank` state was only moved once, but the EVM `StateDB` balance is adjusted twice — creating a value duplication (extra credited balance) or duplicate debit (extra unauthorized deduction), depending on transfer direction, purely from an unprivileged sequence of nested precompile calls.

This mirrors the `veRAACToken` root cause precisely: a bookkeeping offset/mapping (`prevEventsLen` / the dead `locks` mapping) is not correctly synchronized with the real authoritative accounting path (the shared event log / the real `_lockState.locks`), producing incorrect derived balances.

The included regression test, `evmd/tests/integration/balance_handler/balance_handler_test.go`, explicitly documents this exact defect class ("recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten... leads to balance desync between native bank keeper and EVM stateDB") and exercises a caller contract that recurses into a debug precompile 10 times in one transaction [6](#0-5) . Although the current code creates a *new* `BalanceHandler` object per call (mitigating literal instance-sharing of the `prevEventsLen` field), the deeper issue — that the shared event log is not sliced/consumed exclusively per call frame, so overlapping ranges are re-processed by outer frames — is not visibly addressed by that change alone, since `AfterBalanceChange` still just re-scans `ctx.EventManager().Events()` from an outer, earlier-recorded offset that doesn't skip past nested regions already consumed by an inner handler.

### Impact Explanation
If exploitable via genuinely nested precompile-to-precompile calls in a single EVM transaction (e.g., an ERC20/WERC20/ICS20 precompile call whose native action triggers a further keeper operation that itself surfaces through another precompile-mediated balance change, or a caller contract chaining precompile calls), an unprivileged user could cause the EVM-visible balance (`StateDB`, used for `eth_getBalance`, ERC20 balance views, and subsequent EVM-level transfers within the same or later transactions) to diverge from the real `x/bank`/`x/precisebank` ledger — either inflating a balance (duplication of spendable value, mintable-like effect for the attacker) or improperly debiting a victim twice. This is a Critical “unauthorized duplication ... of spendable user value across ... EVM balances ... precompile-mediated assets” per the impact gate, since it corrupts the 1:1 accounting invariant between native coins and EVM-visible balances that `x/precisebank`/`x/vm` are specifically designed to preserve [7](#0-6) .

### Likelihood Explanation
Requires a specific but plausible trigger: any code path where one stateful precompile's native action results in a second, nested stateful-precompile invocation (or bank-event-emitting keeper call) within the same outer `RunNativeAction` window while both go through `BalanceHandler`. Given the module explicitly ships a test scaffold for “recursive precompile calls,” this pattern is treated as reachable/production-relevant by the maintainers themselves, though I was not able to execute the test suite to confirm whether the current fix (fresh `BalanceHandler` per call) fully closes the overlapping-event-range gap, or only the literal shared-instance aspect.

### Recommendation
Ensure each call frame's `AfterBalanceChange` consumes and effectively "checks out" the exact sub-slice of events it is responsible for, and prevent an outer frame from re-processing events already consumed by an inner nested call — e.g., by tracking a global monotonically-advancing "last consumed" watermark on `StateDB` itself (not per-`BalanceHandler` local state) that every `AfterBalanceChange` call advances past, rather than relying on each call frame's own snapshot of `len(events)` taken before nested calls occurred.

### Proof of Concept
Conceptual reproduction (matches the shipped `BalanceHandlerTestSuite`):
1. Deploy a caller contract that invokes a stateful precompile whose native action performs a bank-balance-changing operation, then internally makes a nested call into another (or the same) stateful precompile that also changes balances and completes its own `Before/AfterBalanceChange` cycle.
2. After the transaction, compare `StateDB`-derived EVM balance (`eth_getBalance` / ERC20 `balanceOf`) against the real `x/bank`/`x/precisebank` ledger balance for the involved addresses.
3. Expect the EVM-visible balance to reflect the nested transfer twice (or once too many/too few), while the underlying bank ledger only moved once — the accounting divergence.

I was unable to execute this against the live test harness to confirm current exploitability (it may already be closed by the "fresh handler per call" change visible in `precompile.go`), so this should be verified dynamically with the existing `BalanceHandlerTestSuite` before treating it as confirmed-exploitable.

func (p Precompile) runNativeAction(evm *vm.EVM, contract *vm.Contract, action NativeAction) (bz []byte, err error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.New(ErrNotRunInEvm)
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	if err := stateDB.AddPrecompileFn(snapshot, events); err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	initialGas := ctx.GasMeter().GasConsumed()

	defer HandleGasError(ctx, contract, initialGas, &err)()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)

	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	var balanceHandler *BalanceHandler
	if p.BalanceHandlerFactory != nil {
		balanceHandler = p.BalanceHandlerFactory.NewBalanceHandler()
	}

	if balanceHandler != nil {
		balanceHandler.BeforeBalanceChange(ctx)
	}

	bz, err = action(ctx)
	if err != nil {
		return bz, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	if balanceHandler != nil {
		if err := balanceHandler.AfterBalanceChange(ctx, stateDB); err != nil {
			return nil, err
		}
	}

	return bz, nil
}

// GetCacheContext returns the stateDB CacheContext.
func (s *StateDB) GetCacheContext() (sdk.Context, error) {
	if s.writeCache == nil {
		err := s.cache()
		if err != nil {
			return s.ctx, err
		}
	}
	return s.cacheCtx, nil
}

// MultiStoreSnapshot snapshots stateDB CacheMultiStore
// and returns snapshot index
func (s *StateDB) MultiStoreSnapshot() int {
	return s.snapshotter.Snapshot()
}

func (s *StateDB) RevertMultiStore(snapshot int, events sdk.Events) {
	s.snapshotter.RevertToSnapshot(snapshot)
	s.writeCache = func() {
		s.ctx.EventManager().EmitEvents(events)
		s.cacheCtx.MultiStore().(storetypes.CacheMultiStore).Write()
	}
}
