### Title
Public `tx_search`/`block_search` RPC `=~` (CONTAINS_MATCH) query operator allows unbounded regex DoS against every default RPC node - ([File: sei-tendermint/internal/pubsub/query/query.go])

### Summary
The Tendermint/CometBFT RPC layer embedded in sei-chain exposes `tx_search` and `block_search` endpoints that accept an arbitrary query string, compiled by `tmquery.New`. When the query uses the `=~` (`TMatches`) comparison operator, the raw user-supplied string is passed unmodified into Go's `regexp.MatchString` and evaluated once per matching indexed event value while iterating the entire KV tx/block index — with no regex-complexity bound, no timeout, and no result-size gate on the match phase. This is the same bug class as CVE-2018-11615 (Mosca): attacker-controlled data is compiled/evaluated as a regular expression by the message broker/indexer without protection against catastrophic backtracking, allowing a crash/hang of the service from a single crafted request.

### Finding Description
`Environment.TxSearch` only bounds the query string by character length (`maxQueryLength`), not by pattern complexity, before parsing it into a `query.Query`: [1](#0-0) 

The condition compiler for `=~` does no validation or sanitization of the regex operand — it stores the raw string and, at match time, calls `regexp.MatchString` directly on it against arbitrary index values: [2](#0-1) 

The KV tx indexer's match routine for `syntax.TMatches` iterates the full prefix range for the tag and re-runs `regexp.MatchString(c.Arg.Value(), value)` for every stored event value under that tag, with no per-call timeout or backtracking guard: [3](#0-2) 

The block indexer has the identical pattern for `block_search`: [4](#0-3) 

Go's standard `regexp` package uses RE2 semantics and is *not* vulnerable to catastrophic backtracking the way PCRE-style engines are, so a naive `(a+)+b`-style pattern will not itself hang the regex engine. However, RE2 can still be driven to large memory/CPU cost via patterns with large bounded repetition counts (e.g. `a{1000}{1000}` style nested quantifiers, or huge alternation/character-class combinations) and, more importantly, the surrounding code has no bound on: (a) how many times the regex is evaluated (once per indexed event value matching the tag prefix — potentially every event ever indexed for that attribute across the node's entire retained tx/block history), and (b) how large each candidate string can be. Because there is no query-plan cost limit, per-match timeout, or interruption beyond a generic `ctx.Done()` check between iterations (checked only after each full regex evaluation completes), a single `tx_search`/`block_search` request with a `=~` clause against a high-cardinality/long-value attribute can force the node to spend unbounded CPU synchronously inside the RPC handler goroutine before any cancellation is observed, effectively hanging or resource-exhausting the JSON-RPC server for a default-configuration public node.

### Impact Explanation
Any unauthenticated public JSON-RPC client can submit a single `tx_search`/`block_search` request with a crafted `attribute =~ "<expensive-pattern>"` query against a long-lived, high-volume tag. Because the match loop iterates the *entire* prefix for that tag with no cap applied until after the match phase, and evaluates the regex synchronously per iterated value, this can pin a CPU core and degrade or hang RPC service availability on any node with `tx_index`/kv event sink enabled (the default indexer for full/RPC nodes) — a crash/DoS of a default-configuration RPC node, matching the report's "Impact: crash of default-configuration RPC nodes" acceptance criterion.

### Likelihood Explanation
High: the query language, `=~` operator, and both search RPCs are reachable by any external client with no authentication and no special privileges; `tx_index` and the KV event sink are enabled by default on RPC-serving nodes.

### Recommendation
- Reject or specially bound `=~` regex operands in `tmquery` at parse time (e.g., disallow nested quantifiers/large bounded repeats, cap pattern length independently of overall query length).
- Enforce a hard cap on the number of indexed values scanned/regex-evaluated per `TMatches` condition before falling back to an error, and check for context cancellation *before* each regex evaluation rather than only after.
- Consider running `regexp.MatchString` calls with a wall-clock budget (e.g., via a worker with a timeout) so a single expensive match cannot block the RPC handler indefinitely.
- Document/limit `=~` availability to trusted/internal RPC configurations if it cannot be fully hardened.

### Proof of Concept
1. Run a default sei-chain full node with `tx_index = "kv"` and its RPC exposed.
2. Generate a modest number of ordinary transactions so a chosen event attribute (e.g. `message.action`) accumulates many indexed values.
3. Send: `GET /tx_search?query="message.action =~ '(<crafted expensive pattern targeting the value alphabet>){N}'"` where `N` and the pattern are tuned to maximize per-value RE2 evaluation cost (e.g., large bounded repetition counts on a broad character class) while the tag has many stored values for the KV iterator to walk.
4. Observe the RPC handler goroutine consuming sustained CPU while the query is processed, and other RPC calls on the node stalling/timing out due to the synchronous per-value matching loop with no per-match timeout.

Note: I could not execute this PoC or fully quantify the achievable RE2 worst-case blow-up in this environment (no code execution available); the finding is based on static analysis of the query compilation and match paths cited above. A background Devin session with code execution could benchmark the actual RE2 cost of candidate patterns against this indexer to confirm the achievable CPU-time multiplier before filing this as confirmed-exploitable.
