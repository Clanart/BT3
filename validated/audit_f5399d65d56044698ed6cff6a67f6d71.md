### Title
MultiEdit `content`/`new_text` field extraction can be desynchronized from actual file content, allowing block/warn rules to be bypassed by splitting dangerous strings across edit boundaries - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` builds the value checked for `content`/`new_text` conditions on `MultiEdit` calls by naively joining each edit's `new_string` with a single space, rather than reflecting the actual resulting file content. An attacker who can influence what content Claude Code writes (e.g. via prompt injection from untrusted repository content) can split a dangerous token across multiple `edits` entries so the concatenated string used for regex/contains matching never contains it contiguously, while the real file written to disk does.

### Finding Description
For `MultiEdit`, `_extract_field` does: [1](#0-0) 
```
elif tool_name == 'MultiEdit':
    ...
    elif field in ['new_text', 'content']:
        # Concatenate all edits
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
```
This is reached from `_check_condition`, which calls `_extract_field` and then applies `regex_match`/`contains`/etc. against the returned string: [2](#0-1) 

The join has two independent problems that make it desynchronized from the real applied content:
1. It inserts an artificial `' '` separator between edits that does not exist in the real file (each `new_string` is inserted at its own `old_string` location, not concatenated with a space at file-write time). A dangerous contiguous token can be deliberately split across two `edits` entries (e.g. `new_string: "API_KEY"` and `new_string: "=xyz123"`), producing checked text `"API_KEY =xyz123"` which no longer matches a regex like `API_KEY=`, even though the two edits are adjacent in the real file and produce `API_KEY=xyz123` after being applied.
2. `e.get('new_string', '')` silently defaults to `''` for any edit entry missing `new_string` (e.g. malformed/extra-keyed edit item), meaning entries can be dropped from the string used for matching without affecting what `MultiEdit` actually writes, further desynchronizing the checked field from ground truth.

Because block/warn rules operate purely off this extracted string, a rule intended to block dangerous content in file writes (e.g. secrets, `rm -rf`, backdoor markers) can be defeated by structuring the `edits` array so the dangerous substring only becomes contiguous after real application, not in the space-joined check string. There is no separate validation step that re-checks the tool's actual resulting file content; `evaluate_rules` only trusts `_extract_field`'s output.

The realistic reachable path is via prompt injection: untrusted repository content, issue/PR text, or other agent-visible content can instruct/lead Claude Code to perform a `MultiEdit` with a payload deliberately split into multiple `edits` entries, bypassing a hookify block rule meant to stop that exact content from being written.

### Impact Explanation
This is a "deny means deny" bypass of hookify's block/warn enforcement for `MultiEdit` operations: content that should be blocked (secrets exfiltration markers, destructive commands embedded in files, malicious code patterns) can be written to disk without triggering the rule, because the concatenation used for detection does not match what is actually written. This corresponds to an unauthorized file-write/hook-bypass class of impact — the enforcement gate silently fails open for a specific, reproducible input shape.

### Likelihood Explanation
Exploitation only requires control over the `edits` array of a single `MultiEdit` tool call (i.e., getting Claude Code to issue a `MultiEdit` with attacker-chosen content split across multiple entries), which is realistically achievable via prompt injection from repository content that Claude Code processes during normal automation. No special privileges are needed beyond the ability to influence agent behavior through content it reads, and the bypass is deterministic/repeatable given the `' '.join` implementation.

### Recommendation
Change `_extract_field` for `MultiEdit` to reconstruct (or approximate) the actual resulting content rather than naively space-joining `new_string` fragments — e.g., concatenate with no separator (`''.join(...)`) matching real adjacency, or better, apply the edits against `old_string`/`file_path` context (or check the full post-edit file content on disk after the tool executes, in a `PostToolUse` check) so regex/contains conditions operate on the true written content. Additionally, validate that each edit entry contains expected keys and reject/flag malformed `edits` items instead of silently defaulting missing fields to `''`.

### Proof of Concept
Unit test targeting `RuleEngine._extract_field` and `RuleEngine._check_condition`:
```python
def test_multiedit_split_bypass():
    engine = RuleEngine()
    tool_input = {
        "file_path": "/tmp/x.py",
        "edits": [
            {"old_string": "a", "new_string": "API_KEY"},
            {"old_string": "b", "new_string": "=xyz123"},
        ],
    }
    field_value = engine._extract_field("content", "MultiEdit", tool_input, {})
    # Actual resulting file content after edits applied would contain "API_KEY=xyz123"
    assert "API_KEY=" not in field_value  # demonstrates desync (space inserted)

    condition = Condition(field="content", operator="regex_match", pattern=r"API_KEY=")
    matched = engine._check_condition(condition, "MultiEdit", tool_input, {})
    assert matched is False  # bypass: block rule fails to trigger despite dangerous content being written
```
Expected result: `matched` is `False`, proving a rule written to block `API_KEY=` disclosure fails to fire for this `MultiEdit` payload even though the real file write produces the exact dangerous string contiguously.
