### Title
Silent zero-share mint on deposit lets a depositor's principal be absorbed with no shares issued - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Zest's tokenized vaults (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) compute shares to mint on `deposit` via `convert-to-shares-preview`, which performs `mul-div-down amount ts ta` and can legitimately round to `u0`. Unlike `redeem`, which explicitly reverts when the computed output is zero (`ERR-OUTPUT-ZERO`), `deposit` has no equivalent check — it only guards against zero *input* (`ERR-AMOUNT-ZERO`) and checks `inkind >= min-out`, which defaults to `u0` if the caller doesn't set slippage protection. This mirrors the Allbridge Core Yield root cause: `_mintAfterTotalChanged` returning silently instead of reverting when `realAmount == 0`.

### Finding Description
`convert-to-shares-preview` in `v0-vault-usdc.clar`: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

`deposit` uses this value as `inkind` and mints it directly to the recipient: [2](#0-1) 

The only guards present are `ERR-AMOUNT-ZERO` (checks the input `amount`, not the output) and `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`. If the caller passes `min-out = u0` (the trivial/default case for a naive integration or UI that doesn't compute slippage), a deposit whose computed `inkind` rounds down to `u0` due to `mul-div-down` will still pass every check: the underlying token transfer executes (`receive-underlying`), `assets` is incremented by the full deposited amount, but `ft-mint?` mints `u0` shares to the recipient. The depositor's principal is absorbed into `assets` and proportionally redistributed to all existing shareholders on the next `redeem`, while the depositor receives nothing.

By contrast, `redeem` in the same contract explicitly reverts on the equivalent zero-output condition: [3](#0-2) 

This asymmetry — a zero-output check present on the exit path but missing on the entry path — is precisely the "return instead of revert" defect flagged in the external report, just triggered by rounding (`mul-div-down`) instead of by pool-manipulation math.

The share/asset ratio `ts/ta` naturally shrinks over time as `total-assets-preview` grows via accrued interest (`total-debt`/`debt-preview`) while `total-supply-preview` stays fixed absent new mints: [4](#0-3) 

so the window in which small deposits round to zero shares widens as the vault accrues interest, and is not merely a first-depositor edge case — it recurs continuously for any depositor whose `amount * ts < ta`.

### Impact Explanation
This is theft of user principal at rest: the depositor's underlying tokens are pulled into the vault (`receive-underlying`, `assets` incremented) but the depositor receives zero vault shares (`zft`) representing a claim on those assets. The value is not destroyed — it inflates the redemption value for existing shareholders — so it constitutes direct redistribution of one user's principal to all other current holders without consent or recourse. This lands in the Critical impact bucket: "direct theft of user funds at rest ... other than unclaimed yield."

### Likelihood Explanation
Likelihood depends on the depositor/integrator not supplying a nonzero `min-out`. Any front-end, bot, or contract-to-contract integration that calls `deposit` with `min-out = u0` (a very common default when slippage isn't expected on a "1:1-ish" vault deposit) is exposed once `ts/ta` has shrunk enough for a given deposit size to round to zero. As the vault's index/interest grows over its lifetime, the range of dust/small deposit amounts that round to zero widens, making this a persistent, not merely theoretical, risk across all six vault instances that share this identical `deposit`/`convert-to-shares-preview` pattern.

### Recommendation
Add an explicit zero-output check on `deposit`, mirroring the check already present in `redeem`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other deposit assertions, so that any deposit which would mint zero shares reverts instead of silently absorbing the depositor's underlying tokens.

### Proof of Concept
Conceptual trace (no PoC harness was found in the repo for this contract; reasoning is based on the code paths above):
1. Vault has been live long enough that `total-assets-preview` (`ta`) has grown substantially relative to `total-supply-preview` (`ts`) due to accrued interest.
2. A user calls `deposit` with a small `amount` and `min-out = u0` (no slippage protection).
3. `convert-to-shares-preview` computes `mul-div-down amount ts ta`, which rounds down to `u0` because `amount * ts < ta`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `u0 >= u0`.
5. `receive-underlying` pulls the user's tokens into the vault; `assets` is incremented by the full `amount`; `ft-mint? zft u0 recipient` mints zero shares.
6. The user's principal is now part of `assets`, redistributed pro-rata to all other zft holders on future redemptions, while the user holds no shares and has no way to recover the deposited amount.
