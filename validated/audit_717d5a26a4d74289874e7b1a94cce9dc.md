### Title
Unhandled `AssertionError` on malformed offer file crashes offer parsing/take-offer flow - (File: chia/wallet/trading/offer.py)

### Summary
The CVE bug class is a bare `assert` in a data-parsing path that, given attacker-crafted input, raises an uncaught `AssertionError` instead of being validated/rejected cleanly, terminating the operation. `Offer.__post_init__` in [1](#0-0)  contains exactly this pattern: `assert cs.coin not in adds` is executed while iterating over the coin spends of a spend bundle built directly from untrusted, externally supplied offer data.

### Finding Description
An `Offer` object is constructed from attacker-controlled bytes (a bech32-encoded offer file received from an offer counterparty, or a raw `SpendBundle` via `Offer.from_spend_bundle`). During `__post_init__`, for every `CoinSpend` in `self._bundle.coin_spends` the code asserts uniqueness of the spent coin: [2](#0-1) 

```
adds: dict[Coin, list[Coin]] = {}
...
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
    try:
        hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
```

This `assert` is a bare Python assertion, not a `ValueError`/`ValidationError` raised through the normal offer-validation error path (unlike other conditions checked in the same constructor, e.g. duplicate-payment or missing-driver checks which raise `ValueError`). If a malicious counterparty crafts an offer whose underlying `WalletSpendBundle` contains the same `Coin` (same parent id, puzzle hash, and amount) spent twice — trivially achievable since this is parsed before any consensus/mempool validation — the constructor raises an unhandled `AssertionError` rather than a typed exception.

Because callers of the offer-processing pipeline (`Offer.from_bech32`/`from_bytes`, `TradeManager.respond_to_offer` in [3](#0-2) , and the `take_offer`/`get_offer_summary` RPC entry points in `wallet_rpc_api.py`) generally catch `ValueError`/`ValidationError`, an `AssertionError` from deep inside offer construction is a different exception type and will not be handled the same way, propagating as an unexpected crash of the offer-processing request instead of a clean "invalid offer" rejection. This mirrors the CVE-2025-54350 pattern: a `Base64Decode` *assertion* failure on malformed authentication input causes the process to exit uncleanly rather than reject gracefully.

### Impact Explanation
This is reachable by any offer counterparty who sends a crafted offer file to a wallet user (e.g. via `take_offer`, `get_offer_summary`, or offer-parsing RPCs). It causes a spend-triggered halt/crash of the offer-handling code path in the targeted wallet, a denial-of-service against the wallet RPC/service consistent with "a spend-triggered transaction-processing halt" in the accepted-impact list. It does not, by itself, cause fund loss or state divergence, but it satisfies the medium-severity DoS bug class analog to the CVE.

### Likelihood Explanation
Likelihood is moderate: constructing a spend bundle with a duplicated `Coin` entry across two `CoinSpend`s (same parent_coin_info, puzzle_hash, amount) is fully within attacker control when hand-crafting an offer file/bech32 blob, and no signature or consensus check occurs before `__post_init__` runs. It requires no special privileges — only that a user (or an automated market/offer-processing service) attempts to parse or inspect the offer.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with a proper input-validation check that raises `ValueError` (or `ValidationError`) consistent with the other checks in the same constructor, so malformed/duplicated offers are rejected cleanly instead of crashing via an uncaught `AssertionError`. Audit other bare `assert` statements reachable from untrusted offer/spend-bundle parsing (e.g., in `to_valid_spend`, `get_offered_coins`) for the same class of issue.

### Proof of Concept
Conceptually: craft a `WalletSpendBundle` whose `coin_spends` list contains two `CoinSpend` entries with identical `Coin` (same `parent_coin_info`, `puzzle_hash`, `amount`) — this is possible directly at the Python/bytes level when building or tampering with a serialized offer, since nothing prevents duplicate coin entries in a raw bundle before offer construction. Passing this bundle to `Offer.from_spend_bundle(bundle)` or deserializing it via `Offer.from_bech32`/`Offer.from_bytes` triggers `__post_init__`, which raises `AssertionError` at the `assert cs.coin not in adds` line instead of a handled `ValueError`, crashing whichever caller (RPC handler, CLI, or wallet flow) does not specifically catch `AssertionError`.

**Uncertainty note:** I was not able to fully trace the exact `Streamable.from_bytes`/`from_bech32` deserialization call chain for `Offer` (only partial matches were found for `Offer.from_bytes`/`from_bech32` in the indexed code), nor confirm with full certainty which exact exception types are caught at each RPC boundary (`wallet_rpc_api.py`, `trade_manager.py`). This limits precise confirmation of exactly where in the RPC stack the `AssertionError` would surface unhandled. Since this analog relies on file/code details the index does not fully expose, verification of the exact call path would benefit from a full Devin session with complete repository access.

    def __post_init__(self) -> None:
        # Verify that there are no duplicate payments
        for payments in self.requested_payments.values():
            payment_programs: list[bytes32] = [p.name() for p in payments]
            if len(set(payment_programs)) != len(payment_programs):
                raise ValueError("Bundle has duplicate requested payments")

        # Verify we have a type for every kind of asset
        for asset_id in self.requested_payments:
            if asset_id is not None and asset_id not in self.driver_dict:
                raise ValueError("Offer does not have enough driver information about the requested payments")

        # populate the _additions cache
        adds: dict[Coin, list[Coin]] = {}
        hints: dict[bytes32, bytes32] = {}
        max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)
        for cs in self._bundle.coin_spends:
            # you can't spend the same coin twice in the same SpendBundle
            assert cs.coin not in adds
            try:
                hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
                max_cost -= cost
                adds[cs.coin] = [hc.coin for hc in hinted_coins.values()]
                hints = {**hints, **{id: hc.hint for id, hc in hinted_coins.items() if hc.hint is not None}}
            except ValidationError:
                raise
            except ValueError as e:
                if e.args and e.args[0] == "cost exceeded or below zero":
                    raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_additions for CoinSpend") from e
                continue
            except Exception:
                continue
            if max_cost < 0:
                raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_additions for CoinSpend")
        object.__setattr__(self, "_additions", adds)
        object.__setattr__(self, "_hints", hints)
        object.__setattr__(self, "_conditions", None)
