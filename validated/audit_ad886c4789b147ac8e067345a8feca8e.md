### Title
Scanner reports attacker-sent dust outputs as received funds that are unspendable/economically negative - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` treats any output paying to a registered script as a spendable `ReceivedOutput`, with no minimum-value check. Analogous to the referenced finding — where an exact equality between expected and actual amounts broke the protocol's assumptions — Serai's Bitcoin wallet assumes every scanned output is worth spending, while the send-side (`SignableTransaction`) enforces a `DUST` floor of 546 sats on outputs it *creates*. An unprivileged attacker can violate that assumption from the outside by sending a dust output to the multisig's P2TR script. The output is reported as received balance yet costs more in fee weight (~57 vbytes/input) than it is worth, and may even be below the relay dust limit, making it effectively unspendable.

### Finding Description
`scan_transaction` matches purely on `script_pubkey`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), outpoint: ... });
}
```

`networks/bitcoin/src/wallet/mod.rs` lines 199–213.

The same crate defines `pub const DUST: u64 = 546` and refuses to *construct* payments below it (`TransactionError::DustPayment`, `send.rs` lines 32, 41), and refuses to create change below dust (`send.rs` lines 228–233). So the codebase's own invariant — "an output under 546 sats is not a real payment" — is enforced on construction but not on reception. There is no `output.value` check anywhere in the scan path, and `ReceivedOutput::read`/`write` faithfully round-trip the attacker's dust output into wallet state.

### Impact Explanation
Any output the scanner returns is treated as a usable input by downstream consumers (scheduler/wallet logic feeding `SignableTransaction::new`). A dust input contributes ~57 vbytes of weight (per the documented accounting in `processor/src/networks/bitcoin.rs`: 230 WU/input) while contributing only 1–545 sats of value. At fee rates ≥ ~10 sat/vB the input is strictly value-negative — spending it *destroys* funds relative to ignoring it. Below the dust relay threshold the output is additionally non-standard to spend in some configurations, i.e. funds reported received that are not spendable at all. An attacker can also stuff many dust outputs to inflate transaction weight/fees or push a transaction over `MAX_STANDARD_TX_WEIGHT`/`TooLargeTransaction`, repeatedly degrading the wallet's effective balance and blocking plan construction.

### Likelihood Explanation
Fully reachable by an unprivileged party: the attacker only needs to broadcast a valid Bitcoin transaction paying dust to the multisig's publicly known P2TR `script_pubkey` (or any registered offset address). Cost is the dust amount plus a minimal fee — a few hundred sats per poisoned output, repeatable indefinitely, and requires no cooperation from any validator.

### Recommendation
Apply the existing `DUST` bound on reception, mirroring `send.rs`: in `Scanner::scan_transaction`, skip outputs where `output.value.to_sat() < DUST` (and document that coinbase/immature or sub-dust outputs require post-processing, consistent with the existing `scan_block` maturity caveat). Consumers spending `ReceivedOutput`s should also sanity-check `value() >= DUST` before selecting them as inputs.

### Proof of Concept
1. Derive the vault's script: `p2tr_script_buf(tweaked_group_key)` — public information.
2. Broadcast a transaction with a `TxOut { value: 546 sats or less, script_pubkey: <vault script> }`. Once confirmed, `Scanner::scan_block`/`scan_transaction` returns a `ReceivedOutput` for it (`mod.rs` lines 205–211).
3. The wallet treats it as spendable balance; `SignableTransaction::new` includes it as an input, adding ~57 vbytes of weight. At any meaningful fee rate, `needed_fee` increases by more than the input's value — funds reported received are not economically spendable, and fee spend is inflated per attacker's choosing.
