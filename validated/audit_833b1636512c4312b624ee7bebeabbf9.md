### Title
KIP-71 `GasTarget` governance parameter accepted without validation causes division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
Analogous to BondBaseSDA.setDefaults not validating cross-field relationships between market parameters, Kaia's governance parameter system accepts a `kip71.gastarget` value of `0` with no format validation, and this value is later used as a divisor in `KIP71Config.NextMagmaBlockBaseFee`, causing a `division by zero` panic that is reachable by every node computing/verifying a block's base fee.

### Finding Description
The `Kip71GasTarget` governance parameter is registered with a no-op format checker, unlike its sibling `Kip71BaseFeeDenominator`, which explicitly rejects zero: [1](#0-0) 

```go
Kip71BaseFeeDenominator: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: noopFormatChecker,
    ...
},
```

Neither the headergov consistency check (`checkConsistency` in `kaiax/gov/headergov/impl/header.go`) nor the contractgov path (`kaiax/gov/contractgov/impl/getter.go`, which calls `ParseContractCall`/`PartialParamSet.Add`, which only calls the same `Canonicalizer`/`FormatChecker` pair) adds a cross-check preventing `GasTarget == 0`: [2](#0-1) 

The `GasTarget` value ultimately flows into `params.KIP71Config.NextMagmaBlockBaseFee`, where it is used unconditionally as a divisor without a zero check: [3](#0-2) 

```go
parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)
if parentGasUsed == gasTarget {
    return makeEvenByFloor(parentBaseFee)
} else if parentGasUsed > gasTarget {
    ...
    y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divisor is 0 → panic
    ...
} else {
    ...
    y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // divisor is 0 → panic
    ...
}
```

`(*big.Int).Div` panics when the divisor is zero. Since any real block will have `parentGasUsed != 0` (any block containing at least one transaction), setting `GasTarget = 0` guarantees the "greater than" or "less than" branch is taken, hitting the zero-divisor `Div` call and panicking. This function is invoked both during block assembly (`work/worker.go`) and header verification (`VerifyMagmaHeader`), meaning both the block producer and every node validating the resulting header will panic/crash once the malicious governance value takes effect.

### Impact Explanation
Once `kip71.gastarget` is voted to `0` and the vote takes effect at the epoch boundary (headergov) or is committed via the `GovParam` contract (contractgov, callable through a `setParam` transaction), any block whose parent used nonzero gas causes a panic in `NextMagmaBlockBaseFee`. Because this function runs both during block production and during every node's block/header verification, this leads to a chain-wide halt (all consensus/endpoint nodes crash processing the next block) — a critical, network-wide state-divergence/availability failure, directly analogous to the reported bug class of unvalidated governance-style setters breaking core protocol logic.

### Likelihood Explanation
The root cause is a simple missing input-validation check that is inconsistent with the neighboring, correctly-guarded `Kip71BaseFeeDenominator` parameter (which does check `v != 0`), showing this was an oversight rather than an intentional design choice. Governance parameter changes are an explicitly in-scope class for this analysis, and the value flows through the exact same `Canonicalizer`/`FormatChecker` validation pipeline used for both headergov votes and the on-chain `GovParam` contract path, so the invalid value can reach the base-fee computation via either channel.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` that rejects `0`, mirroring the existing check for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
},
```
Additionally, consider adding a defensive zero-check directly in `NextMagmaBlockBaseFee` (as already done for `BaseFeeDenominator == 0`) so that a stale or corrupted config can never cause a division-by-zero panic regardless of upstream validation gaps.

### Proof of Concept
1. Governing node (or, post-Kore, whoever controls the `GovParam` contract's authorized setter) submits a vote/`setParam` transaction setting `kip71.gastarget = 0`.
2. The vote passes validation because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker` and `checkConsistency` performs no cross-check for this parameter [2](#0-1) .
3. At the epoch boundary the new `GasTarget = 0` becomes effective in `ParamSet`/`KIP71Config` via `ToKip71Config` [4](#0-3) .
4. On the next block whose parent has nonzero `GasUsed` (i.e., virtually every real block), `NextMagmaBlockBaseFee` executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, causing `(*big.Int).Div` to panic [5](#0-4) .
5. This panic occurs both in the block producer (`work/worker.go` computing the new block's base fee) and in every node verifying the resulting header (`VerifyMagmaHeader`), halting the entire network.
