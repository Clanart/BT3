### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers pre-allocation of a 65535-element scalar vector before any input bytes are consumed - ([File: crypto/dkg/src/lib.rs])

### Summary
The deserialization routine for `ThresholdKeys` trusts a 16-bit participant count `n` read from untrusted bytes and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient list. An unprivileged party supplying bytes to `ThresholdKeys::read` can force a multi-megabyte heap allocation with only a handful of input bytes, enabling memory-exhaustion denial of service — the direct analog of CWE-404-style improper resource management (unbounded/unvalidated resource allocation driven by an attacker-controlled length).

### Finding Description
In `crypto/dkg/src/lib.rs` (`ThresholdKeys::read`), after the curve-ID check, three `u16` values are read: `t`, `n`, and `i` (lines 591-602). `n` is fully attacker-controlled (any value up to 65535, since validation via `ThresholdParams::new` only happens at line 626, after the allocations). When the interpolation tag byte is `0` (`Interpolation::Constant`), the code executes:

```rust
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

(lines 607-613). `Vec::with_capacity(usize::from(n))` allocates `n * size_of::<C::F>()` bytes of heap memory before a single field element is read from the stream. For a 32-byte scalar field, `n = 0xFFFF` forces a ~2 MiB allocation from roughly 11 bytes of attacker input (4-byte ID len + ID + 6 bytes of params + 1 tag byte). The subsequent loop fails fast on EOF, but the allocation has already been committed (and under memory pressure, the allocation itself can abort the process on OOM).

Additionally, lines 620-623 iterate `(1 ..= n)` performing `read_G` per participant into a `HashMap`; this portion is bounded by bytes actually present, but each iteration still inserts into a `HashMap`, so a small input containing many valid point encodings scales linearly — that part is bounded, but the `with_capacity` amplification is not.

The reachable surface is exactly the class the bug maps to: `ThresholdKeys::read` is listed as a sink for untrusted bytes, and the same `n`-driven read pattern is shared by DKG key material handling throughout the DKG crate (`crypto/dkg`).

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` (e.g., via serialized key material processed during DKG/key-rotation flows) causes an out-of-proportion memory allocation per call — ~2 MiB per ~11-byte message for the constant-interpolation arm, per invocation. Repeated submissions exhaust allocator memory, terminating the process (alloc failure aborts under Rust's default allocator behavior) or degrading all co-located signing/verification work. This is a remote, unauthenticated resource-exhaustion DoS against validator/processor components that deserialize key material.

### Likelihood Explanation
The primitive is trivially reachable: set `id_len`/`id` to the real `C::ID`, then `t = 1`, `n = 0xFFFF`, `i = 1`, interpolation tag `0`. No valid scalars need to be supplied at all — the allocation happens before reads. The only caveat is reachability depends on an integrator piping untrusted bytes into `ThresholdKeys::read`; within Serai, serialized `ThresholdKeys` are handled in DKG and processor key-management paths. Impact is availability-only, consistent with a Medium severity assessment.

### Recommendation
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), avoid pre-allocating from the untrusted `n`:
- Replace `Vec::with_capacity(usize::from(n))` with `Vec::new()` and let the `read_F` loop grow it only as bytes are actually consumed.
- Enforce a sane maximum on `n` (e.g., the protocol's real max participant count) immediately after reading it, before any allocation or loop, rather than deferring validation to `ThresholdParams::new` at the end.
- Apply the same pattern wherever a count is read before allocation in the DKG/frost deserialization paths.

### Proof of Concept
```rust
// Attacker-controlled bytes for ThresholdKeys::<C>::read
// Layout: id_len (4B) || C::ID || t (2B) || n (2B) || i (2B) || interpolation (1B)
let mut bytes = Vec::new();
bytes.extend_from_slice(&(C::ID.len() as u32).to_le_bytes());
bytes.extend_from_slice(C::ID);
bytes.extend_from_slice(&1u16.to_le_bytes());        // t = 1
bytes.extend_from_slice(&u16::MAX.to_le_bytes());    // n = 65535
bytes.extend_from_slice(&1u16.to_le_bytes());        // i = 1
bytes.push(0u8);                                     // Interpolation::Constant
// No scalar bytes follow. read() still executes
// Vec::with_capacity(65535) -> ~2 MiB heap allocation,
// then fails on the first read_F with an EOF error.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

Each ~11-byte payload forces a ~2 MiB allocation (F = 32 bytes); looping it exhausts memory.
