Confirmed via code inspection: the `action` field is never normalized (no `.lower()`/`.strip()` applied) in `config_loader.py` and `rule_engine.py` compares with strict equality `rule.action == 'block'`.

### Title
Case/whitespace-sensitive `action` field comparison silently downgrades intended `block` rules to `warn`, allowing dangerous operations to proceed - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`Rule.from_dict` reads the frontmatter `action` key verbatim with `frontmatter.get('action', 'warn')` and stores it without normalization. `RuleEngine.evaluate_rules` then checks `if rule.action == 'block':` using strict, case-sensitive string equality. Any variance in the configured value (`Block`, `BLOCK`, `block ` with trailing whitespace, etc.) causes the rule to fall into the `warning_rules` branch instead of `blocking_rules`, so a rule authored to hard-block a dangerous `Bash`/`Write` pattern only emits a warning `systemMessage` while the tool call is still allowed to execute.

### Finding Description
`config_loader.py` line 81: `action=frontmatter.get('action', 'warn')` — no `.strip()` or `.lower()` normalization is applied to the raw YAML value. `rule_engine.py` line 55: `if rule.action == 'block':` is an exact string comparison. If a rule file in `.claude/hookify.*.local.md` contains `action: Block`, `action: BLOCK`, or `action:  block` (extra internal/trailing whitespace not stripped by the minimal hand-rolled YAML parser's `value.strip()` at line 138 handles surrounding whitespace, but any capitalization difference is untouched), the comparison `'Block' == 'block'` is `False`. The rule is appended to `warning_rules` rather than `blocking_rules` in `evaluate_rules`. Consequently, when this warn-only rule is the only match, execution reaches the `if warning_rules:` branch (`rule_engine.py` lines 87–91), which returns only a `systemMessage` and no `hookSpecificOutput.permissionDecision: deny`, so `PreToolUse` allows the tool call to proceed. Since `.claude/hookify.*.local.md` rule files are ordinary repository content (loaded via `glob.glob` in `load_rules`), an attacker who can influence such a file (e.g., via a PR that adds/modifies a hookify rule, or a shared/checked-in ruleset merged without careful review of the exact casing) can cause an intended hard block on a dangerous `Bash`/`Write`/`Edit` pattern to be silently reduced to a non-blocking warning, with no error, exception, or log message indicating the misconfiguration — the loader treats the value as valid and does not validate it against an enum of allowed actions.

### Impact Explanation
This breaks the "deny means deny" invariant for `PreToolUse` hook enforcement: a rule file that appears from its `message` text to hard-block a dangerous pattern (e.g. `rm -rf`, credential-writing `Write` calls) will, due to a single capitalization typo in `action`, permit the operation to execute while merely printing a warning. This maps to an approval/permission-decision bypass in the hook enforcement layer of Claude Code, since the security control that should stop dangerous tool calls is silently neutralized.

### Likelihood Explanation
The precondition is a rule file with a malformed `action` value (e.g. `Block`, `BLOCK`) reaching `load_rules()`. No validation or normalization exists anywhere in `config_loader.py` to catch this, so the misconfiguration is silent and will reliably reproduce for any rule authored with inconsistent capitalization — a common real-world typo given YAML frontmatter conventions vary. This is fully deterministic/repeatable given the exact-match comparison at `rule_engine.py:55`.

### Recommendation
Normalize `action` at load time in `config_loader.py` (`action=str(frontmatter.get('action', 'warn')).strip().lower()`) and/or validate it against an allow-list (`{'block', 'warn'}`), raising a warning to stderr and failing safe (defaulting unrecognized/invalid values to `block`, not `warn`) when the value doesn't match. Additionally, change `rule_engine.py`'s comparison to use the normalized value or add `rule.action.strip().lower() == 'block'` as defense in depth.

### Proof of Concept
Unit test in `plugins/hookify/core` test suite:
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

for variant in ["Block", "BLOCK", " block", "block "]:
    rule = Rule(
        name="dangerous-rm",
        enabled=True,
        event="bash",
        conditions=[Condition(field="command", operator="regex_match", pattern=r"rm\s+-rf")],
        action=variant,
        message="Blocked dangerous rm!"
    )
    engine = RuleEngine()
    result = engine.evaluate_rules([rule], {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /"}
    })
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", f"action={variant!r} failed to block"
```
