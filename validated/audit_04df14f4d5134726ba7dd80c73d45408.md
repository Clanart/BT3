### Title
Attacker-controlled deposits to publicly-derivable internal offset addresses are misclassified by the Bitcoin scanner, bypassing external-output handling - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary

The referenced Cilium bug class is *selector confusion*: an object is matched by a policy other than the intended one because matching keys on attacker-influenceable attributes. In Serai, the analogous shape is the `Scanner`, which classifies incoming Bitcoin outputs purely by `script_pubkey` equality against a `HashMap<ScriptBuf, Scalar>` of registered offsets.

The processor registers four output kinds — `External` (offset `0`), `Branch`, `Change`, and `Forwarded` — where the three non-external offsets are deterministically derived as `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch"/"change"/"forward")` [1](#0-0) . These are public constants: anyone can compute `key + hash_to_F(...)*G` and hence the corresponding P2TR `script_pubkey` via `p2tr_script_buf` [2](#0-1) .

`scan_transaction` returns a `ReceivedOutput` for *any* on-chain output whose `script_pubkey` matches, carrying only the offset [3](#0-2) . `get_outputs` then assigns `OutputType` solely by looking up that offset in `kinds`, with no way to distinguish a protocol-created change/forward/branch output from an output any third party created by paying to the same address [4](#0-3) .

### Finding Description

The "label" an attacker can craft is the destination address of a Bitcoin transaction they send. Since `Branch`/`Change`/`Forwarded` addresses are pure functions of the (public) group key and fixed public strings, an unprivileged party can send funds to them. The scanner "selects" such an output into the wrong class:

- Serai instruction data (`InInstruction`) is only attached to outputs classified `External`; outputs classified `Change`/`Forwarded`/`Branch` get empty `data` [5](#0-4) . A depositor — or a victim tricked into depositing to the forward/change address (these are ordinary, publishable P2TR addresses, e.g. `forward_address` exposes the Forwarded address directly [6](#0-5) ) — has their deposit recorded as an *internal* output. The accompanying instruction embedded in the transaction is silently discarded, so the deposit is never credited even though the multisig received the funds.
- `presumed_origin` is also unconditionally populated from `tx.input[0]`'s prevout script — fully attacker-chosen — for every matched output [7](#0-6) .
- Because the outputs are classified as protocol-internal (`Change`/`Forwarded`), downstream processor logic that treats such outputs as already-accounted-for (change re-entry, forwarding pipelines, balance reconciliation) will act on attacker-injected outputs. `register_offset`'s own documentation acknowledges that the registered scripts assume key-only spending and that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" — the scheme relies on offsets being unpredictable/unguessable in effect, yet the three internal offsets are `hash_to_F` of fixed public strings [8](#0-7) .

This mirrors GHSA-pfhr-pccp-hwmh exactly: a value the attacker crafts (labels / destination script) causes the system to match the entity against an unintended policy/output-type rather than the expected one.

### Impact Explanation

Funds paid to the Serai multisig are reported received under the wrong `OutputType`. For `Forwarded`-kind outputs in particular, processor handling diverges from `External` (no instruction data, no normal deposit crediting), so a depositor's real payment is absorbed into internal plumbing — funds are received by the group key yet the depositor is never credited and the output may be swept/consumed by unrelated internal flows. This is integrity/availability of funds reachable by any unprivileged Bitcoin sender: CVSS-style integrity loss on externally supplied transaction data. Severity: Medium.

### Likelihood Explanation

The attack requires only that the attacker compute `p2tr_script_buf(group_key + hash_to_F(KEY_DST, kind)*G)` — all inputs are public — and broadcast an ordinary Bitcoin transaction. No privileges, no collusion, no malformed encodings needed. The `register_offset` surjectivity (offset incremented until an even point results [9](#0-8) ) does not help the attacker here but doesn't hinder them either; the used offset is computable by the same public procedure.

### Recommendation

Distinguish self-generated internal outputs from externally-created ones. Options:

- Mark `Change`/`Forwarded`/`Branch` outputs as expected only when they appear in transactions the processor itself constructed (track created txids/outpoints), rather than trusting script match alone.
- Commit the kind into the address in a non-public way: derive internal offsets as `hash_to_F(KEY_DST, kind || secret-or-session-data)` or use a per-multisig-session salt so external parties cannot compute the internal addresses, while keeping `External` at offset 0.
- Alternatively, treat any output at an internal-kind address that arrives in a transaction not authored by the processor as `External` (attach `data`, run normal deposit handling) to fail safe.

### Proof of Concept

1. Observe the Serai Bitcoin group key `K` (published; `external_address` is derived from it).
2. Compute `off = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")`, incrementing by 1 while `K + off*G` is odd (exactly what `register_offset` does) [9](#0-8) .
3. Build `script = ScriptBuf::new_p2tr_tweaked(TweakedPublicKey::dangerous_assume_tweaked(x_only(K + off*G)))`.
4. Broadcast a transaction paying to `script`, optionally embedding an `InInstruction` (OP_SHA256 hash commitment) that requests a credit.
5. `get_outputs` scans the block, matches `script_pubkey`, finds `kinds[off]` = `OutputType::Forwarded`, emits an `Output` with `kind = Forwarded` and `data = []` because only `External` outputs receive the extracted instruction data [10](#0-9) .
6. Result: the multisig received spendable BTC, but the deposit is processed under the internal `Forwarded` class — the attached instruction is dropped and the depositor is not credited, with `presumed_origin` also attacker-forged from `tx.input[0]`.

const KEY_DST: &[u8] = b"Serai Bitcoin Output Offset";
static BRANCH_OFFSET: OnceLock<Scalar> = OnceLock::new();
static CHANGE_OFFSET: OnceLock<Scalar> = OnceLock::new();
static FORWARD_OFFSET: OnceLock<Scalar> = OnceLock::new();

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
  );

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
