### Title
Front-runnable dust-stake attack lets attacker steal entire queued reward payload via BaseRewardPool._provisionReward's div-by-totalStaked() rounding - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool._provisionReward` branches on `this.totalStaked() == 0`: if zero, the reward is deferred into `queuedRewards`; otherwise it is immediately baked into `rewardPerTokenStored` proportional to the *current* `totalStaked()`. `totalStaked()` is simply `IERC20(stakingToken).balanceOf(operator)` (MasterMagpie's live token balance), not a time-weighted supply. An attacker who front-runs a manager's `queueNewRewards` call with `MasterMagpie.deposit(_stakingToken, 1)` when the pool is otherwise empty converts the "defer to queuedRewards" path into the "distribute now" path, becomes the sole (1‑wei) staker, and captures the entire reward amount instantly regardless of holding period.

### Finding Description
`_provisionReward` computes:
```solidity
if (this.totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    ...
    rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
}
``` [1](#0-0) 

`totalStaked()` reads the live ERC20 balance of the staking token held by `operator` (MasterMagpie), not an internally tracked accumulator: [2](#0-1) . `balanceOf(_account)` reads the user's tracked stake from MasterMagpie's `stakingInfo`: [3](#0-2) . `earned()` computes `balanceOf(_account) * (rewardPerToken - paid) / 10**stakingDecimals() + userRewards`: [4](#0-3) .

Exploit flow, assuming a pool with zero current stakers at the moment the manager submits `queueNewRewards(amount, token)`:
1. Attacker sees the manager's pending `queueNewRewards` transaction in the mempool and front-runs it with `MasterMagpie.deposit(_stakingToken, 1)`, calling `_deposit` which transfers 1 wei of stakingToken into MasterMagpie and sets `user.available = 1`: [5](#0-4) .
2. Now `totalStaked() == 1`, so when the manager's transaction executes `_provisionReward`, it takes the `else` branch instead of deferring to `queuedRewards`, and sets `rewardPerTokenStored += amount * 10**decimals / 1` — i.e. the full reward divided among a supply of 1 wei.
3. Attacker calls `MasterMagpie.withdraw(_stakingToken, 1)` (or any claim flow), which calls `_harvestAndUnstake` → `_harvestBaseRewarder` → `rewarder.updateFor(_account)` (or `getReward` in the multiclaim path) → `_claimBaseRewarder`: [6](#0-5) [7](#0-6) .
4. `earned(attacker, token) = 1 * (amount*10**dec) / 10**dec = amount` — the attacker captures the entire queued reward, having held the staking token for a single block, instead of the reward being deferred (`queuedRewards`) for genuine future stakers to share pro-rata.

No existing check prevents this: `queueNewRewards` is `onlyManager`-gated on the *caller*, but has no minimum-stake, no cooldown, and no protection against `totalStaked()` being manipulated between mempool submission and execution; `nonReentrant`/`whenNotPaused` on `MasterMagpie.deposit`/`withdraw` do not address this because the attacker isn't reentering, they are simply front-running with a normal deposit.

### Impact Explanation
Direct theft of unclaimed yield / reward funds intended for the protocol's future genuine stakers of that pool. This matches the Immunefi "theft of unclaimed yield" / "direct theft of user funds" class, since the entire reward payment that would otherwise sit in `queuedRewards` (to be fairly distributed pro-rata once real depositors arrive) is instead drained atomically by an attacker who staked a negligible, non-time-weighted amount for a single transaction/block.

### Likelihood Explanation
- Preconditions: the target pool must have zero stakers at the moment the manager's `queueNewRewards` transaction is included (i.e., `totalStaked() == 0`, which routes reward into `queuedRewards` if untouched). This is a realistic situation right after a new reward pool/pair is deployed or after all stakers have withdrawn before the first `queueNewRewards` call.
- Capital needed: 1 wei of the staking token (negligible) plus gas for a front-run/back-run.
- Feasibility: standard mempool front-running (no special privileges required); attacker only calls public `deposit`/`withdraw`.
- Repeatability: exploitable every time a manager queues rewards for a freshly-created or fully-drained pool, making it a recurring risk across new pool launches.

### Recommendation
Do not rely on live, gameable `IERC20.balanceOf(operator)` as `totalStaked()`; track staked supply as an internal state variable updated only by MasterMagpie's `_deposit`/`_withdraw` (already tracked in `PoolInfo`/`UserInfo`), and additionally consider a minimum bootstrap-stake or a time-locked/streamed reward release (rather than instant `rewardPerTokenStored` mutation) so that reward entitlement is weighted by staking duration, not just balance at the single block when `queueNewRewards` executes.

### Proof of Concept
Hardhat test plan:
1. Deploy `MasterMagpie`, a `BaseRewardPool` for a mock ERC20 `stakingToken`, and a mock reward token; register the rewarder as a manager-eligible pool with 0 current stakers.
2. Have `rewardManager` prepare (but not yet send) a `queueNewRewards(1000e18, rewardToken)` call.
3. Attacker calls `MasterMagpie.deposit(stakingToken, 1)`.
4. Execute the manager's `queueNewRewards(1000e18, rewardToken)`.
5. Assert `rewardPerTokenStored` for that token equals `1000e18 * 10**stakingDecimals()` (i.e., computed against `totalStaked()==1`), not deferred into `queuedRewards`.
6. Attacker calls `MasterMagpie.withdraw(stakingToken, 1)` (or `getReward`) and asserts they receive the full `1000e18` reward tokens.
7. Compare against expected fair outcome: if `totalStaked()` had remained 0 at queue time, `queuedRewards` should equal `1000e18` and be distributed only once genuine stakers deposit, pro-rata to their stake and duration — demonstrating the attacker captured 100% of a reward they held for less than one block, disproportionate to any fair pro-rata/time-weighted share.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
