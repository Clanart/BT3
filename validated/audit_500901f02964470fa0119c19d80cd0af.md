Based on my research, there's a solid structural analog to this report in Chia's pool-reward absorption path. I'll lay out the finding.

### Title
Unprivileged party can grief batched pool-reward absorb claims via permissionless partial absorb spends - (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet.claim_pool_rewards()` builds a single `WalletSpendBundle` that chains together many sequential singleton "absorb" spends, one per unclaimed `p2_singleton` reward coin, in order to sweep multiple farming rewards in one transaction. Absorb spends against a pool-member (or self-pooling) singleton are permissionless by design — no owner signature is required when `fee == 0` — so anyone, not just the wallet owner, can construct and broadcast a valid absorb spend for any individual reward coin belonging to that singleton.

### Finding Description
`create_absorb_spend()` builds a `CoinSpend` pair (singleton spend + `p2_singleton` reward-coin spend) using only publicly known data: the singleton's last solution/lineage, the pool state, the reward coin's height, and `calculate_pool_reward(height)`. [1](#0-0)  None of these inputs require a private key, and `PoolWallet.claim_pool_rewards()` explicitly notes that "If fee is 0, no signatures are required to absorb." [2](#0-1) 

When the wallet owner wants to claim several outstanding rewards at once, `claim_pool_rewards()` chains the absorb spends sequentially through the singleton's lineage into one `all_spends` list and wraps them all into a single `WalletSpendBundle` (`claim_spend`): [3](#0-2) 

Because every absorb spend in the chain depends on the exact previous singleton coin (`last_solution`) and consumes a specific `p2_singleton` reward coin, if any single one of those reward coins is spent out from under the transaction before it is confirmed — which an unprivileged third party can do by independently constructing and broadcasting their own (signature-free) absorb spend for that one coin — the wallet's whole aggregated multi-reward `SpendBundle` becomes invalid (its assumed singleton lineage and/or one of its listed removals no longer match chain state) and will be rejected by the mempool as a conflict/double-spend of that coin.

### Impact Explanation
This mirrors the reported bug class: a legitimate actor batches many independent claims into one transaction to save relaying/confirmation overhead, but any of those individual claims can be permissionlessly triggered out-of-band by someone else, causing the whole batch to fail validation and be rejected. The pool wallet owner must then rebuild and resubmit a smaller/adjusted spend bundle, repeatedly, spending gas/fees and delaying claim consolidation — a spend-triggered transaction-processing halt of the owner's aggregated claim, analogous to the "reserved token minters prevented from minting all their tokens" pattern in the original report. Funds are not stolen (the p2_singleton puzzle still forces payout to the singleton's puzzle hash), but the intended one-shot multi-reward claim can be reliably obstructed.

### Likelihood Explanation
Absorb spends are intentionally permissionless (by design, so pools/farmers can sweep rewards without the owner's key), so the "attacker" capability required — constructing a valid absorb `CoinSpend` for one reward coin — needs no privileged access, no owner key, and no special network position beyond normal mempool visibility of the target singleton's public state (chain-observable). This is reachable by any wallet-RPC/mempool submitter, matching the "unprivileged spend-bundle submitter" reachability bar.

### Recommendation
Consider making `claim_pool_rewards()` resilient to partial completion: build/submit absorb spends in smaller independent transactions (already partially supported via `max_spends_in_tx`), or detect stale/already-absorbed reward coins immediately before submission and re-plan the bundle around only currently-unspent coins rather than failing the whole batch atomically. Alternatively, decouple lineage-chained absorption so a single already-claimed reward coin doesn't invalidate the rest of the batch's coin spends.

### Proof of Concept
1. Wallet W operates a pool-member (or self-pooling) `PoolWallet` singleton with several unclaimed `p2_singleton` reward coins.
2. W calls `claim_pool_rewards()`, which builds one `WalletSpendBundle` chaining N absorb spends for N reward coins [4](#0-3) , and begins broadcasting it.
3. Attacker A observes the pending transaction (or simply monitors W's singleton/reward coins independently, since absorption doesn't require any special knowledge beyond public chain state) and, without needing any private key, builds its own single-reward absorb `CoinSpend` for one of the reward coins included in W's batch via `create_absorb_spend()` [1](#0-0) , and gets it confirmed first.
4. W's original batched `SpendBundle` now references a stale singleton lineage and/or an already-spent `p2_singleton` coin, causing the mempool to reject it (double-spend/conflict).
5. W must rebuild the whole batch, repeating the loss each time A repeats step 3 against a newly rebuilt batch — preventing W from claiming all rewards in one transaction.

def create_absorb_spend(
    last_coin_spend: CoinSpend,
    current_state: PoolState,
    launcher_coin: Coin,
    height: uint32,
    genesis_challenge: bytes32,
    delay_time: uint64,
    delay_ph: bytes32,
) -> list[CoinSpend]:
    inner_puzzle: Program = pool_state_to_inner_puzzle(
        current_state, launcher_coin.name(), genesis_challenge, delay_time, delay_ph
    )
    reward_amount: uint64 = calculate_pool_reward(height)
    if is_pool_member_inner_puzzle(inner_puzzle):
        # inner sol is (spend_type, pool_reward_amount, pool_reward_height, extra_data)
        inner_sol: Program = Program.to([reward_amount, height])
    elif is_pool_waitingroom_inner_puzzle(inner_puzzle):
        # inner sol is (spend_type, destination_puzhash, pool_reward_amount, pool_reward_height, extra_data)
        inner_sol = Program.to([0, reward_amount, height])
    else:
        raise ValueError
    # full sol = (parent_info, my_amount, inner_solution)
    coin: Coin | None = get_most_recent_singleton_coin_from_coin_spend(last_coin_spend)
    assert coin is not None

    if coin.parent_coin_info == launcher_coin.name():
        parent_info: Program = Program.to([launcher_coin.parent_coin_info, launcher_coin.amount])
    else:
        p = Program.from_bytes(bytes(last_coin_spend.puzzle_reveal))
        last_coin_spend_inner_puzzle: Program | None = get_inner_puzzle_from_puzzle(p)
        assert last_coin_spend_inner_puzzle is not None
        parent_info = Program.to(
            [
                last_coin_spend.coin.parent_coin_info,
                last_coin_spend_inner_puzzle.get_tree_hash(),
                last_coin_spend.coin.amount,
            ]
        )
    full_solution: SerializedProgram = SerializedProgram.to([parent_info, last_coin_spend.coin.amount, inner_sol])
    full_puzzle: SerializedProgram = create_full_puzzle(inner_puzzle, launcher_coin.name()).to_serialized()
    assert coin.puzzle_hash == full_puzzle.get_tree_hash()

    reward_parent: bytes32 = pool_parent_id(height, genesis_challenge)
    p2_singleton_puzzle = create_p2_singleton_puzzle(
        SINGLETON_MOD_HASH, launcher_coin.name(), delay_time, delay_ph
    ).to_serialized()
    reward_coin: Coin = Coin(reward_parent, p2_singleton_puzzle.get_tree_hash(), reward_amount)
    p2_singleton_solution = SerializedProgram.to([inner_puzzle.get_tree_hash(), reward_coin.name()])
    assert p2_singleton_puzzle.get_tree_hash() == reward_coin.puzzle_hash
    assert full_puzzle.get_tree_hash() == coin.puzzle_hash
    assert get_inner_puzzle_from_puzzle(Program.from_bytes(bytes(full_puzzle))) is not None

    coin_spends = [
        CoinSpend(coin, full_puzzle, full_solution),
        CoinSpend(reward_coin, p2_singleton_puzzle, p2_singleton_solution),
    ]
    return coin_spends
