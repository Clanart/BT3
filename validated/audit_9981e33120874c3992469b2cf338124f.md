### Title
Renamed-file diff view can hide already-staged content changes, letting a user unknowingly commit/push attacker-influenced content - (File: app/src/lib/git/diff.ts)

### Summary
`getWorkingDirectoryDiff()` in `app/src/lib/git/diff.ts` computes the diff shown to the user for a renamed file by running `git diff -- <path>` (working tree vs. index) instead of diffing the index against `HEAD`. The code itself documents that this is wrong: [1](#0-0) . When the content changes accompanying a rename are already staged (index already matches the working tree), this computation yields zero hunks even though the file differs substantially from `HEAD` and will be committed with those changes. This is structurally analogous to the StakeWise bug: a "good enough" check (`isHarvestRequired` tolerating one stale nonce) is trusted as a gate before a sensitive action, while the actual up-to-date state (the true diff against `HEAD`) is never consulted, letting an attacker exploit the gap between the trusted check and the real state.

### Finding Description
`getWorkingDirectoryDiff` branches on `AppFileStatusKind.Renamed` and diffs the file with no ref argument, i.e. working tree vs. index: [1](#0-0) . Independently, `renameIncludesModifications` is computed in the status parser from Git's own rename score/working-tree state: [2](#0-1) . These two pieces of state are not derived from the same comparison: the flag can correctly report "yes, there are modifications" (via rename score < 100), while the diff computation reports 0 hunks because it only looks at working-tree-vs-index, missing changes that are already fully staged.

The UI trusts the empty-hunks state at face value: [3](#0-2) . When `hunks.length === 0` and `renameIncludesModifications` is true, the user only sees the text "The file was renamed and includes changes" with **no actual diff content** to review. If it's false, the user sees "The file was renamed but not changed." In both cases the user has no way to inspect the real content delta before committing, yet `createCommit`/`stageFiles` will still commit whatever is in the index for that file: [4](#0-3) [5](#0-4) .

The "broken invariant" mirrors the report: a staleness/incompleteness in a check (`isHarvestRequired` tolerating 1-nonce staleness vs. Desktop's diff view tolerating "already-staged" content) is used as if it reflected the true state right before a critical, hard-to-reverse action (a deposit vs. a commit/push). Existing guards (the `renameIncludesModifications` flag, and the "renamed and includes changes" warning banner) do not stop the path because they don't force the diff itself to be recomputed against `HEAD` — they merely display a generic warning without content, and the commit path re-reads whatever is on disk/in the index regardless of what the (broken) diff displayed.

### Impact Explanation
Because the working-directory status is derived from `git status --porcelain -z` (not tracked purely from Desktop's own staging actions), any external actor influencing the index prior to Desktop reading status — e.g. a `post-checkout`/`post-merge` hook shipped in a cloned/fetched repository, a rebase/cherry-pick/merge against an attacker-controlled branch that auto-resolves a rename+content change and leaves it staged, or another Git client/IDE action triggered while working in an attacker-influenced repo — can result in a `Renamed` file whose real content differs from `HEAD` but whose Desktop diff view shows **zero visible changes**. If the user reviews the (empty) diff, believes nothing meaningful changed, and commits/pushes, attacker-influenced content is silently included in the commit that gets pushed to the remote — meeting the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This requires a scenario where content changes to a renamed file are already staged (index == working tree) before Desktop's diff is generated — normally Desktop stages files itself right before diffing/committing, so the ordinary UI flow (rename + edit, not yet staged) is unaffected. The higher-likelihood trigger is a git operation that stages a rename+modification atomically without Desktop being the one to stage it (merge/rebase/cherry-pick auto-resolution from a fetched branch, or a repository-provided hook). This narrows applicability somewhat, so likelihood is best characterized as **moderate**, pending confirmation of the exact end-to-end trigger; I could not fully verify a hook/merge scenario that leaves the index in exactly this state without further live testing.

### Recommendation
- Change `getWorkingDirectoryDiff` to diff the renamed/copied file against `HEAD` (not just the index) so any staged content differences are always shown, matching the approach already used for other status kinds (`args.push('HEAD', '--', ...)`), and remove the acknowledged incorrect shortcut.
- Ensure the "renamed and includes changes" UI state always has actual diff hunks to display; never present a security/content-relevant warning without the underlying content for review.
- Consider re-validating the working directory diff (against `HEAD`) immediately before staging/creating a commit, similar to re-checking a repository's rewards/harvest state right before a sensitive operation, rather than relying on a diff calculated under different comparison semantics.

### Proof of Concept
1. In a test repo: `git mv foo bar && echo "malicious payload" >> bar && git add bar` (fully staging both the rename and the content change in one step, simulating what a merge/rebase/hook could do without Desktop's own staging).
2. Open the repository in Desktop; the Changes list shows `bar` as `Renamed`.
3. Because `git diff -- bar` (working tree vs. index) is now empty, `getWorkingDirectoryDiff` returns 0 hunks: [1](#0-0) .
4. Because the rename score is <100% (content differs from the original), `renameIncludesModifications` is `true`: [2](#0-1) .
5. The Diff pane shows only the text "The file was renamed and includes changes" with no visible lines: [6](#0-5) .
6. The user, seeing no reviewable content, commits and pushes — the injected "malicious payload" content is committed and pushed without ever being visibly reviewed in Desktop.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}
