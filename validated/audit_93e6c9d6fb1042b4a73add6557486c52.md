### Title
ReceivedOutput deserialization accepts output/outpoint unbound to the spend offset, reporting unsendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Chainlink report (returned data used without validating it is well-formed/consistent for its intended use), `ReceivedOutput::read` ingests fully attacker-controlled bytes — a spend `offset` scalar, a `TxOut`, and an `OutPoint` — and reconstructs a `ReceivedOutput` with no check that the `output`'s `script_pubkey` is actually the tweaked P2TR key derived from `offset` (i.e., that the offset genuinely permits spending this output). `scan_transaction` always produces this binding internally, but `read` reconstructs the struct without ever re-establishing it.

### Finding Description
`ReceivedOutput` is the value passed to the spend-building code: the `offset` is the scalar added to the base key to obtain the spending key, and `output`/`outpoint` describe what is being spent. In `Scanner::scan_transaction`, the binding is guaranteed because outputs are only recorded after `self.scripts.get(&output.script_pubkey)` matches a registered offset (`networks/bitcoin/src/wallet/mod.rs:199-214`).

`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) performs only syntactic decoding:

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no structural way for `read` to verify `output.script_pubkey == p2tr(key + offset·G)`, because `ReceivedOutput` does not store the base key and `read` takes no key parameter. Any serialized `ReceivedOutput` transported between components (e.g., scanner → signer/wallet) is therefore trusted blindly: an unprivileged party who can feed bytes to `read` can claim an arbitrary `TxOut`/`OutPoint` is spendable under a chosen offset.

### Impact Explanation
A crafted `ReceivedOutput` whose `output` pays to a script_pubkey not reachable from `offset` (or whose `outpoint` does not exist / has a fabricated `value`) is accepted as a legitimately received coin. Downstream signing derives the spend key from `offset`, so the produced signature will not correspond to the output's actual key — the wallet/coordinator reports funds as received that are not spendable, and may commit them into a spend plan that can never be validly signed, or account a fabricated `value`. This matches the report's core failure mode: externally supplied data consumed as authoritative without validating it is consistent for the operation it will drive.

### Likelihood Explanation
Reachable by any party able to supply bytes to `ReceivedOutput::read` (e.g., a peer/component relaying scanned outputs). No key compromise or collusion is needed; only control of the serialized blob.

### Recommendation
Bind the output to the spend key at deserialization or use time: carry/accept the base `ProjectivePoint` (as `Scanner` does) and verify `output.script_pubkey == p2tr_script_buf(key + G·offset)` before accepting a `ReceivedOutput`, mirroring the check `scan_transaction` already performs implicitly. Additionally, treat `value`/`outpoint` as unverified until confirmed against chain data.

### Proof of Concept
1. Pick any victim-controlled P2TR output `O` (script_pubkey for key `K_victim`), any `OutPoint`, and offset `0`.
2. Serialize `ReceivedOutput { offset: 0, output: O, outpoint }` via the `write` format (32-byte scalar || consensus TxOut || consensus OutPoint).
3. Feed the bytes to `ReceivedOutput::read`. It returns `Ok`, yielding an output the wallet believes is spendable under the registered offset, though signing with `key + offset` cannot satisfy `K_victim`'s script — funds reported received are not spendable.
