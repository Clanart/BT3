### Title
`ThresholdKeys::read` deserializes inconsistent key material without validating `secret_share` against its verification share or constraining `group_key` derivation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` (crypto/dkg/src/lib.rs:574) accepts untrusted serialized bytes and constructs a `ThresholdKeys` whose `secret_share`, `verification_shares`, and implied `group_key` are never checked for internal consistency. The bug class — user-controlled input driving security-relevant object state without validation (analogous to CVE-2019-16676's unvalidated input reaching a sensitive call) — maps onto Serai as attacker-controlled bytes fed to `ThresholdKeys::read` producing a semantically invalid key set that is then used for FROST signing.

### Finding Description
`ThresholdKeys::read` performs only syntactic validation:

- It checks the curve `C::ID` tag (lines 575-589).
- It checks `t != 0`, `n != 0`, `t <= n`, `i <= n` via `ThresholdParams::new` (lines 166-179, called at 625-631).
- It checks the interpolation discriminant is 0 or 1 (lines 604-616).
- `read_F`/`read_G` enforce canonical encodings (crypto/ciphersuite/src/lib.rs:74-100).

It does **not** verify that:

1. `secret_share * C::generator() == verification_shares[i]` — the deserialized secret share is never bound to the participant's own verification share. `verification_shares` is built unconditionally for indexes `1..=n` (lines 620-623) and `ThresholdKeys::new` only checks the map's length and that no index exceeds `n` (lines 355-365).
2. The group key is consistent with anything besides the first `t` verification shares. `group_key` is derived solely from `verification_shares[1..=t]` interpolated over the set `{1..=t}` (lines 376-378). The remaining `n - t` verification shares are arbitrary attacker-controlled points that never influence `group_key`, `original_group_key()`, or `view().group_key()`.
3. Verification shares are non-identity or otherwise sane points; `read_G` only enforces canonical encoding.

The codebase itself acknowledges this hole: `AlgorithmSignatureMachine::complete` comments that "the only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494), i.e., the authors know deserialization can produce inconsistent keys, but `read` still accepts them.

Reachability: the threat model for this scan explicitly includes untrusted bytes passed to `ThresholdKeys::read`. A malformed blob (e.g., tampered key material delivered to a node) is silently accepted and the resulting `ThresholdKeys` is usable by `AlgorithmMachine::new` / `SignMachine::sign` / `SignatureMachine::complete`.

### Impact Explanation
Two concrete consequences, both triggered purely by crafted input bytes:

1. **Self-blame / denial of service with false attribution.** With `secret_share` not equal to the discrete log of `verification_shares[i]`, every signing session in which this participant's share is individually checked fails. In `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:447-495), when aggregate verification fails, `verify_share` queues per-participant statements; the honest victim's share fails `s*G == R_i + c*V_i` because `V_i` was attacker-chosen, so `FrostError::InvalidShare(i)` attributes fault to the victim participant. An honest node is provably "faulty" and can be blamed/slashed by integrator logic, or the multisig livelocks.
2. **Silent group-key divergence.** Because `group_key` is computed only from `verification_shares[1..=t]`, an attacker can produce two serializations with identical `t, n, i, secret_share` but different `verification_shares[t+1..=n]`, yielding the same `group_key` yet divergent per-participant verification shares; or alter `verification_shares[1..=t]` to change `group_key` entirely while keeping `secret_share` fixed. Any security assumption that the serialized form commits to the participants' keys is violated — the encoding carries `n` shares but only `t` of them determine the key signed under.

Additionally, `Interpolation::Constant` coefficients are read as `n` scalars but `ThresholdKeys::new` rejects `Constant` when `t != n` (lines 367-374), so that path is consistently checked; the Lagrange path has no equivalent semantic check on `secret_share`/`verification_shares` consistency.

### Likelihood Explanation
Medium-low. Exploitation requires an attacker to supply or tamper with serialized `ThresholdKeys` — not a pure network message, but explicitly within this scan's reachable surface (untrusted bytes to `ThresholdKeys::read`). There is no MAC or integrity tag on the serialization: `write`/`read` (lines 538-632) emit raw fields with only a curve-ID check. If key material passes through any untrusted channel or storage, no consistency check stands between the bytes and the FROST signing machine. The severity is bounded: an attacker cannot extract the victim's true secret share this way (signatures fail rather than leak), so the realistic impact is denial of service, false blame of an honest participant, and group-key/verification-share divergence.

### Recommendation
In `ThresholdKeys::new` (or `ThresholdKeys::read`), add a consistency check: reject keys where `C::generator() * *secret_share != verification_shares[&params.i()]`. Optionally also reject identity verification shares, and document that the serialized format carries no integrity protection, so callers sourcing `ThresholdKeys` bytes from untrusted channels must authenticate them externally.

### Proof of Concept
```rust
// Construct a serialized ThresholdKeys blob for a 2-of-3 (t=2, n=3) Ristretto setup.
// Layout per ThresholdKeys::write (crypto/dkg/src/lib.rs:538-562):
//   u32 id_len | C::ID | u16 t | u16 n | u16 i | u8 interp | secret_share | n points
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(2u16.to_le_bytes());           // t = 2
buf.extend(3u16.to_le_bytes());           // n = 3
buf.extend(3u16.to_le_bytes());           // i = 3 (not in 1..=t)
buf.push(1);                              // Interpolation::Lagrange
// Victim's real secret share s_v — attacker doesn't know it, doesn't matter
buf.extend(s_v.to_repr().as_ref());
// verification_shares[1..=3]: set shares 1,2 to attacker-known points a1*G, a2*G,
// and share 3 to an ARBITRARY point X != s_v*G (e.g., identity is canonical).
buf.extend((C::generator() * a1).to_bytes().as_ref());
buf.extend((C::generator() * a2).to_bytes().as_ref());
buf.extend(C::G::identity().to_bytes().as_ref()); // verification_shares[3]

// read() succeeds: all checks pass
let keys = ThresholdKeys::<C>::read(&mut buf.as_ref()).unwrap();

// group_key = a1*G*λ1 + a2*G*λ2 over set {1,2} — attacker knows its discrete log
// keys.view({1,2,3}) succeeds; signing produces a share that fails verify_share
// for participant 3 -> FrostError::InvalidShare(3) blames the honest holder.
```

The deserialize-then-sign path accepts this blob without error, and only fails later — at `complete`'s per-share blame step (crypto/frost/src/sign.rs:475-489) — where the honest participant is reported as the faulty one.
