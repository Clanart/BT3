### Title
`associatePubKey` accepts a raw public key with no proof-of-possession, letting anyone force address association and orphan the direct-cast account - (File: `precompiles/addr/addr.go`)

### Summary
The `addr` precompile's `associatePubKey` method derives both the EVM and Sei addresses directly from a caller-supplied raw public key and immediately links them, without requiring any signature proving the caller actually controls the corresponding private key. This is the same class of flaw as the Grafana advisory: an identity claim (here, "I own this pubkey/address pair") is accepted and acted upon without cryptographic proof, unlike the sibling `associate` method which does require a signature.

### Finding Description
`PrecompileExecutor.associatePublicKey` in `precompiles/addr/addr.go` takes a single hex-encoded compressed public key argument, parses it, and derives `evmAddr`/`seiAddr`/`pubkey` purely from the bytes: [1](#0-0) 

Contrast this with `associate`, which requires an ECDSA signature (`v, r, s`) over a message, so the recovered pubkey provably belongs to whoever is calling: [2](#0-1) 

Both paths funnel into `associateAddresses`, which only checks that the target `seiAddr` isn't already associated - it never checks that the caller possesses the private key for the pubkey being submitted to `associatePubKey`: [3](#0-2) 

The actual state mutation is performed by `AssociationHelper.AssociateAddresses`, which sets the EVM↔Sei address mapping, installs the pubkey on the target account, and migrates balances/wei from the "direct-cast" account (`sdk.AccAddress(evmAddr[:])`) to the real pubkey-derived Sei address, deleting the direct-cast account if it holds no locked coins: [4](#0-3) 

Because a target account's compressed public key becomes publicly visible the moment it broadcasts any Cosmos-side transaction (it is stored in `BaseAccount.PubKey` and exposed via account queries), any third party can extract it and call `associatePubKey` on behalf of the victim before the victim ever calls `associate` themselves. The codebase's own comments acknowledge the danger of exactly this kind of unsolicited re-association: the EIP-7702 authority pre-association logic in the ante handler was added specifically because "a later `associatePubKey` call can remap, orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [5](#0-4) 

That mitigation only pre-associates EIP-7702 `SetCode` authorities; it does not add any possession check to `associatePubKey` itself. Any account that has accrued staking/distribution state under its direct-cast identity (an EVM address that has delegated or been used as a validator operator via the direct byte-cast Sei address before ever calling `associate`) remains exposed: an unprivileged caller who front-runs the legitimate association by submitting that account's already-public compressed pubkey to `associatePubKey` triggers `RemoveAccount` on the direct-cast address once its spendable/locked balance is drained, while any staking/distribution bookkeeping keyed to that direct-cast account is left dangling - precisely the orphaning scenario the code comment warns can "halt the chain via the distribution validator-removal hook."

### Impact Explanation
This lets an unprivileged transaction sender force an address association for a victim without the victim's consent or any proof the caller owns the private key. Beyond the DoS/griefing angle of an unwanted mapping/account remap, the codebase's own documented failure mode is that orphaning a direct-cast identity's underlying account (via balance migration + `RemoveAccount`) while it still has active staking/distribution state can trigger the distribution module's validator-removal hook against a now-missing/altered account, which the maintainers explicitly call out as a chain-halt risk. Both are High-severity outcomes (validator halt / consensus-critical state corruption) reachable from a single EVM transaction calling the public `addr` precompile.

### Likelihood Explanation
Likelihood is moderate: the attacker needs (a) the target's compressed public key, which is trivially obtainable once the target has broadcast any signed Cosmos-side message from that account, and (b) the target to have accumulated staking/distribution state under the un-associated, direct-cast identity before calling `associate`/`associatePubKey` themselves - a realistic scenario for early adopters of the EVM/Cosmos dual-addressing model who delegate or run a validator using a fresh EVM key before formally associating it.

### Recommendation
Require proof-of-possession for `associatePubKey` (e.g., accept it only via an on-chain signed authorization the same way `associate` does, or restrict it to self-association derived from `msg.sender`/tx signer context), and audit `AssociateAddresses`/`MigrateBalance` to ensure a direct-cast account with outstanding staking, delegation, or validator state cannot be removed or have its identity remapped by a third party without the legitimate owner's signed consent.

### Proof of Concept
1. Victim generates a fresh EVM keypair and, without ever calling `associate`, uses it to sign a Cosmos-side `MsgDelegate` (or validator-creation message) against the direct-cast Sei address `sdk.AccAddress(evmAddr[:])`, accruing staking/distribution state under that identity.
2. Victim's compressed public key becomes visible on-chain (e.g., via the account's `BaseAccount.PubKey` once any signed message is processed, or from the EVM tx's recovered pubkey).
3. Any third party extracts that pubkey and calls `addr.associatePubKey(pubKeyHex)` (`precompiles/addr/addr.go:205-237`) - no signature over any message is required.
4. `associateAddresses`/`AssociateAddresses` migrates spendable/wei balances off the direct-cast account and calls `RemoveAccount` on it once its locked-coin balance is zero, orphaning the account backing the victim's pre-existing staking/distribution state, matching the failure mode described in `app/ante/evm_checktx.go:251-267`.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associatePublicKey(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	// Takes a single argument, a compressed pubkey in hex format, excluding the '0x'
	pubKeyHex := args[0].(string)

	pubKeyBytes, err := hex.DecodeString(pubKeyHex)
	if err != nil {
		return nil, 0, err
	}

	// Parse the compressed public key
	pubKey, err := btcec.ParsePubKey(pubKeyBytes)
	if err != nil {
		return nil, 0, err
	}

	// Convert to uncompressed public key
	uncompressedPubKey := pubKey.SerializeUncompressed()

	evmAddr, seiAddr, pubkey, err := helpers.GetAddressesFromPubkeyBytes(uncompressedPubKey)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).
//
// This is the legacyabci counterpart of x/evm/ante's EVMPreprocessDecorator so both ante
// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions
// carry no authorizations and are a no-op.
