### Title
Context-scoped `CachedPreprocesses` reuse lets a single FROST nonce sign across multiple sessions, enabling key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` stores a deterministic FROST preprocess seed in `CachedPreprocesses` keyed only by `context` (e.g. `(b"DkgConfirmer", attempt)`), and every subsequent `share_internal` call re-derives identical nonces `(d, e)` from that seed. The nonce scope is therefore the whole attempt context — broader than any individual signing session — so any second `sign` executed under the same context with a different effective message or different preprocess set reuses the nonce. This is the Serai analogue of CVE-2018-1267: an overlapping scope (the shared cache context) collapses the isolation boundary (one-preprocess-one-signature) that the security policy depends on. [1](#0-0) 

### Finding Description

`preprocess_internal` checks `CachedPreprocesses::get(self.txn, &self.context)`; if unset it generates one seeded preprocess and stores it, and on every call — including `DkgConfirmer::preprocess`, `share`, and the `share_internal` re-execution inside `complete` — it loads the *same* seed and calls `AlgorithmSignMachine::from_cache`, which regenerates identical nonces via `Commitments::new` from `ChaCha20Rng::from_seed(*seed.0)`. [2](#0-1) [3](#0-2) 

The file's own header acknowledges the hazard and rests safety entirely on the assumption that re-execution sees byte-identical inputs: "it is explicitly unsafe to reuse nonces across signing sessions… Safety is derived from the nonces being context-bound under a BFT protocol… In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again," with the guarding check left as a TODO. [4](#0-3) 

Two reachable divergence paths exist:

1. **Multiple messages under one context.** `DkgConfirmer::share`/`complete` sign `set_keys_message(set, removed, key_pair)` where `key_pair` is caller-supplied per call. If the same attempt context confirms more than one key pair (the DKG produces a `KeyPair` per network it supports), the same `(d, e)` and identical published commitments produce identical binding factors `rho`, and two shares `s_i = d + e·rho + λ·x·c_i` over distinct challenges `c_1 ≠ c_2` yield the secret share directly: `x = (s_1 − s_2) / (λ·(c_1 − c_2))`. [5](#0-4) 

2. **Distinct preprocess sets.** An unprivileged participant fully controls their preprocess bytes, which are parsed via `read_preprocess` and feed `rho` through `BindingFactor::calculate_binding_factors`. Any call pattern that runs `sign` twice under the same context with differing peer preprocesses (e.g., `share` followed by `complete` re-execution over a different parsed set, or retried signature-collection rounds) produces ROS-style parallel shares on the same nonce; accumulating such shares solves for `d`, `e`, and then `x`. Nothing in `preprocess_internal` or `share_internal` enforces that the preprocess map match the one used when the nonce commitment was published — the author notes this consistency check is still a TODO. [6](#0-5) [7](#0-6) 

### Impact Explanation

Recovery of the signer's FROST secret share for the validator MuSig key. The seed cache is per context, so the reused nonce is not limited to re-emitting an identical share — any second distinct signing session under `(b"DkgConfirmer", attempt)` leaks share equations to whoever collects them. The code itself states the consequence: "Reusing preprocesses would enable a third-party to recover your private key share." [8](#0-7)  Compromise of a validator's key share undermines the threshold root-of-trust used to confirm DKG results on-chain.

### Likelihood Explanation

The trigger requires a second distinct `sign` under the same context. `complete` unconditionally re-executes `share_internal`, so `share` + `complete` already produce two `sign` calls per confirmation; they are only safe because the message and peer preprocesses are expected identical. The exposure materializes if (a) more than one `key_pair` is confirmed per attempt, or (b) the preprocess set presented to `complete` differs from the one presented to `share` — both reachable from data a participant influences (submitted preprocess bytes) and neither guarded in code, with the guard explicitly deferred as a TODO. [9](#0-8)  I could not fully verify whether `handle.rs` currently feeds divergent preprocess sets across these calls (index coverage limits), so the exact exploitability depends on the calling flow, but the missing check means the invariant is enforced by assumption, not code.

### Recommendation

Bind the cached preprocess to the full signing session, not just the context: store alongside the seed a transcript commitment of the message and the sorted participant set, and refuse `share_internal` (or regenerate with a fresh seed) when they differ. Implement the deferred check that the locally derived commitments match the on-chain published preprocess before emitting any share, and never re-run `sign` inside `complete` — cache the `AlgorithmSignatureMachine` output of `share` instead.

### Proof of Concept

1. `DkgConfirmer::new(key, spec, txn, attempt)` → `share(preprocesses, key_pair_A)` emits share `s₁` with nonces from `CachedPreprocesses["DkgConfirmer"||attempt]`.
2. Same context, `share(preprocesses, key_pair_B)` (or `complete` over a modified preprocess map) emits `s₂` with the same `d, e`.
3. With identical commitments, `rho` is identical; solve `x = (s₁ − s₂)·(λ·(c₁ − c₂))⁻¹` mod ℓ where `c_i` are the public Schnorr challenges derivable from the published commitments and messages.
4. Verify recovered `x` against the signer's published MuSig verification share.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
