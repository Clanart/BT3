### Title
Unbounded/combinatorial Python-level loop in `Offer.get_cancellation_coins()` allows a malicious offer counterparty to DoS a wallet on cancellation - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` computes, in pure Python (outside CLVM cost accounting), a fixed point over coin dependency/announcement graphs by repeatedly calling `detect_dependent_coin` and re-scanning all remaining coins. An adversarial offer counterparty can craft an `Offer`/`WalletSpendBundle` with many coin spends and a dense web of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions to make this computation blow up combinatorially, freezing the victim wallet process when it later cancels the trade.

### Finding Description
`get_cancellation_coins` builds `dependencies` and `announcements` maps for every non-ephemeral coin spend in the offer [1](#0-0) , then enters an outer `while True` loop that repeatedly calls `detect_dependent_coin`, which itself is a triple-nested loop over `names`, `deps[name]`, and `announcement_dict.items()` with an `in` membership check [2](#0-1) . Each time a dependency is found, an inner `while True` loop rescans all remaining `dependencies.items()` against a growing `removed_announcements` set, potentially repeating multiple times per outer iteration [3](#0-2) .

Unlike CLVM puzzle execution, which is bounded by `MAX_BLOCK_COST_CLVM` and enforced per spend in `Offer.conditions()` [4](#0-3) , this post-processing logic in `get_cancellation_coins` has no cost or size limit tied to the number of coin spends, announcements, or dependency edges. An attacker who is simply an offer counterparty can construct an offer with many settlement/notarized-payment coins each creating multiple `CREATE_COIN_ANNOUNCEMENT` conditions and cross-referencing `ASSERT_COIN_ANNOUNCEMENT` dependencies, driving up the number of outer/inner loop iterations and the per-iteration triple-nested scan cost well beyond what the CLVM cost limit alone would suggest is "cheap."

`get_cancellation_coins` is only invoked from `TradeManager.cancel_pending_offers`, which is called from the `cancel_offer` and `cancel_offers` wallet RPC endpoints [5](#0-4) . Because this runs under `wallet_state_manager.lock` (an async lock guarding wallet state) [6](#0-5) , a long-running synchronous computation here blocks the wallet's ability to process any other wallet state operation for the duration of the call.

### Impact Explanation
This is a spend-bundle/offer-content-triggered processing halt reachable by any offer counterparty without requiring malicious-peer, malicious-node, or privileged access: the victim only needs to accept (`respond_to_offer`) and later attempt to cancel a maliciously crafted offer. Because the computation runs while holding `wallet_state_manager.lock`, it can stall the victim's wallet (blocking other RPCs, syncing, and transaction processing) for an extended period, which is a legitimate availability/DoS impact on the wallet subsystem — matching the "spend-triggered transaction-processing halt" acceptance criterion.

### Likelihood Explanation
Medium: the attacker must get the victim to accept a crafted offer and then trigger cancellation of it, which requires normal trade-manager usage but no special privileges or trust from the victim beyond accepting an offer (a routine wallet action). The complexity multiplier depends on how many coin spends/announcements the attacker can pack into a single valid offer under the standard block cost limit, which still allows a large number of spends.

### Recommendation
Bound the work performed by `get_cancellation_coins`/`detect_dependent_coin` independently of CLVM cost — e.g., cap the number of coin spends/dependency edges processed, replace the O(n) repeated linear/triple-nested scans with an indexed graph structure (e.g., precomputed reverse-announcement index) to make the fixed-point computation near-linear, and/or impose an explicit iteration or time budget with a safe fallback (e.g., treat all removal coins as cancellation coins) when the graph is too complex to resolve cheaply.

### Proof of Concept
1. Construct a malicious `Offer` (as an offer counterparty) whose underlying `WalletSpendBundle` contains N settlement/notarized-payment coin spends, each emitting several `CREATE_COIN_ANNOUNCEMENT` conditions and `ASSERT_COIN_ANNOUNCEMENT` conditions referencing other coins in the same bundle in a densely interlinked pattern (still within `MAX_BLOCK_COST_CLVM`).
2. Have the victim wallet accept the offer via `respond_to_offer` (a normal trade flow) so it is stored via `save_trade`.
3. Have the victim (or an automated cancellation flow) call the `cancel_offer`/`cancel_offers` RPC on that trade, which invokes `Offer.from_bytes(trade.offer).get_cancellation_coins()` inside `cancel_pending_offers` [7](#0-6) .
4. Observe that the nested loops in `detect_dependent_coin` and the outer/inner `while True` loops in `get_cancellation_coins` cause CPU-bound processing time to scale super-linearly with the crafted dependency graph size, stalling the wallet under `wallet_state_manager.lock`.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```

```python
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
```

```python
        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
```
