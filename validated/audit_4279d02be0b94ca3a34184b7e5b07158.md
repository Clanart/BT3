### Title
No mechanism to revoke `safe.directory` trust exceptions once granted - (File: `app/src/lib/git/config.ts`)

### Summary
GitHub Desktop lets a user permanently "trust" a repository directory that Git flags as unsafe (owned by a different user) by writing an entry to the global `safe.directory` Git config via `addSafeDirectory`. There is no corresponding function or UI path anywhere in the codebase to remove that trust entry once granted, so an exception, once created, is permanent for the lifetime of the user's global Git config — directly analogous to the `P2pSsvProxyFactory` report's "no revoke" flaw.

### Finding Description
When Desktop detects a repository owned by a different user, it treats it as `unsafe` [1](#0-0) , and the UI offers a "Trust Repository" action in both the add-existing-repository flow and the missing-repository view that calls `addSafeDirectory` [2](#0-1) [3](#0-2) .

`addSafeDirectory` appends the path to the global `safe.directory` git config permanently via `addGlobalConfigValueIfMissing`, which only adds the value if it's missing but never removes it: [4](#0-3) .

The broken invariant: once a directory is trusted (added to `safe.directory`), Git will unconditionally treat any repository at that path as safe from then on, including any future content placed there by another user or process — and Desktop provides no `onlyOwner`-equivalent (i.e., no UI or API call) to remove the entry. Searching the codebase for a revocation counterpart (`removeSafeDirectory`, `--unset safe.directory`) turns up nothing; `addSafeDirectory` has no paired "untrust" function, and "Remove" repository in `MissingRepository`/`RepositoriesStore` only removes the repository from Desktop's own list — it does not touch the global Git config [5](#0-4) .

### Impact Explanation
`safe.directory` is a strong Git trust boundary specifically meant to prevent Git from executing configuration-driven code (hooks, `core.fsmonitor`, etc.) from directories owned by another user — the same directories can later be repurposed (e.g., a shared machine, a re-cloned malicious repo at the same path, or a directory reused after another user/process writes to it) and Git will now silently trust it forever because Desktop already stamped it in the global config. Since this is a global (not per-repository-instance, and not tied to Desktop's internal repository list) and persistent config change with no revoke path in the app, a single mistaken or attacker-induced "Trust Repository" click creates a durable exception outside of Desktop's own security model, matching the "irreversibility of incorrectly granted access" class of the original report.

### Likelihood Explanation
Any user who encounters the "unsafe" warning dialog (common on shared machines, USB drives, or after certain path/ownership changes) and clicks "Trust Repository" one time creates a permanent exception. There is no in-app way to review or revoke previously trusted directories, so a mistaken click, or trust granted based on stale assumptions about a path's ownership, cannot be undone through Desktop — the user would need to manually edit `~/.gitconfig` outside of Desktop, which is not part of the expected trust-management workflow.

### Recommendation
Add a paired `removeSafeDirectory`/`--unset safe.directory` function in `app/src/lib/git/config.ts` and expose a UI surface (e.g., in Desktop's Git settings) that lists currently trusted directories from `safe.directory` and allows the user to revoke individual entries, mirroring the recommended `onlyOwner` revoke functions from the original report.

### Proof of Concept
1. Open a repository at a path Desktop flags as `unsafe` (owned by a different user), and click "Trust Repository", which calls `addSafeDirectory(path)` [3](#0-2) .
2. This adds `path` to the global `[safe] directory = ...` config permanently [6](#0-5) .
3. Later, that same path is repopulated by another user/process/attacker with a different, potentially malicious repository (e.g., malicious hooks or `.gitattributes`-driven filters).
4. Because the path is still listed in `safe.directory`, Git treats it as trusted again and Desktop will not re-prompt the unsafe-directory warning — there is no menu, setting, or command anywhere in the codebase to remove the previously granted trust, so the exception silently persists indefinitely.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

/** Set the global config value by name. */
export async function addGlobalConfigValueIfMissing(
  name: string,
  value: string
): Promise<void> {
  const { stdout, exitCode } = await git(
    ['config', '--global', '-z', '--get-all', name, value],
    __dirname,
    'addGlobalConfigValue',
    { successExitCodes: new Set([0, 1]) }
  )

  if (exitCode === 1 || !stdout.split('\0').includes(value)) {
    await addGlobalConfigValue(name, value)
  }
}
