### Title
Stale MasterWombat Reference Permanently Freezes Previously Staked LP Tokens After `setMasterWombat` Update - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking` stores a single global `masterWombat` address used for **all** pools, for both staking new deposits and withdrawing/harvesting existing ones. `setMasterWombat()` lets the owner repoint this address with no migration of already-staked LP positions, mirroring the `TalentirTokenV1.setMarketplace()` bug class where updating a stored address leaves previously created state pointing at the old address.

### Finding Description
The `masterWombat` address is a single contract-wide state variable [1](#0-0) , used both when staking newly deposited LP tokens: [2](#0-1)  and when withdrawing/harvesting a user's already-staked LP: [3](#0-2) .

`setMasterWombat()` simply overwrites this address with no logic to migrate existing LP positions out of the old contract: [4](#0-3) .

Because there is no per-position record of which `masterWombat` instance a given deposit actually resides in, once the address is changed, any LP tokens staked under the old `masterWombat` become orphaned: subsequent user-initiated `withdraw()` calls (reachable via `WombatPoolHelperV2.withdraw` → `WombatStaking._toMasterWomAndSendReward`) target the *new* `masterWombat` contract, which has no knowledge of that user's/that pool's previously staked balance under the pid recorded in `pools[_lpToken].pid`. This is directly analogous to the reported `TalentirTokenV1.setMarketplace()` issue, where changing a stored trusted address leaves prior state (approvals in the original report, staked balances here) bound to the stale address, and ordinary users have no path to reconcile it themselves.

### Impact Explanation
Any LP tokens staked prior to a `setMasterWombat` call are effectively locked in the old `masterWombat` contract with no code path in `WombatStaking` to reach them (since the contract only ever calls out to the current `masterWombat`). Ordinary users calling `withdraw()` through the pool helper cannot recover their principal, which is a permanent freezing of user funds, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
`setMasterWombat` is a normal, foreseeable maintenance operation (e.g., migrating to an upgraded Wombat Exchange `MasterWombat` deployment), not a malicious act — it is comparable in nature to the benign marketplace-address rotation described in the original report. Any pool with active LP staked at the time of the switch is affected, and the freeze persists indefinitely (well past 24 hours) until the team manually intervenes, which is outside of what an ordinary user's own transactions can resolve.

### Recommendation
Track `masterWombat` per-pool (or per-position) rather than as a single global variable, and/or add an explicit migration function that unstakes all LP from the old `masterWombat` and re-stakes it into the new one atomically as part of `setMasterWombat`, before the address pointer is switched.

### Proof of Concept
1. User A deposits into `WombatPoolHelperV2`, which routes to `WombatStaking._stakeToWombatMaster`, staking LP into `masterWombat` (v1): [5](#0-4) .
2. Owner calls `setMasterWombat(masterWombatV2)` to point at a new Wombat deployment: [4](#0-3) .
3. User A calls `withdraw()`; `WombatStaking` now calls `IMasterWombat(masterWombat).withdraw(poolInfo.pid, lpAmount)` against `masterWombatV2` [3](#0-2) , which has no record of User A's stake (it was staked in v1) — the call reverts or withdraws nothing, and User A's LP remains permanently stuck in `masterWombatV1` with no user-facing recovery path.

Note: I was not able to view the full `withdraw`/`deposit` function bodies of `WombatStaking.sol` in this session due to tool-call limits, so I could not trace every downstream revert/success path exhaustively; the analysis above is based on the confirmed use of the single global `masterWombat` variable in both the staking and reward-harvesting internal functions shown above.
