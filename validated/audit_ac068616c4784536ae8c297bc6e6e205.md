### Title
Path traversal via crafted repository file path in "Reveal in Finder/Explorer" bypasses the containment check used elsewhere for the same shell.showItemInFolder sink - (File: app/src/lib/app-shell.ts)

### Summary
`revealInFileManager` computes the path to open with `Path.join(repository.path, path)` and passes it directly to `shell.showItemInFolder`, without verifying that the resulting path stays inside the repository working directory. [1](#0-0) 
Elsewhere in the same codebase, when a comparable value (a path string) reaches the very same sink (`shell.showItemInFolder`), Desktop explicitly rejects absolute paths and calls `resolveWithin(repository.path, filepath)` to guarantee the resolved path — after following any symlinks — is contained within the repository root before invoking the shell: [2](#0-1) 

The `resolveWithin` helper is explicitly designed to defeat both `..` traversal and symlink-based escapes: [3](#0-2) 

### Finding Description
The broken invariant is: "any path value that is derived from repository/attacker-controlled content and passed to a filesystem-shell sink (`shell.showItemInFolder`) must be validated to resolve inside the repository root." One code path (the `openrepo://...&filepath=` deep-link handler) enforces this invariant with `resolveWithin` plus an `isAbsolute` check. Another code path that reaches the identical sink — `revealInFileManager`, invoked from the Changes list and History file list context menus with `file.path` taken directly from `WorkingDirectoryFileChange`/`CommittedFileChange` objects — does not perform any such check, instead trusting `Path.join(repository.path, path)`. [4](#0-3) [5](#0-4) 

`file.path` values originate from `git status`/`git diff` output for files that exist in the working tree or in a commit — i.e., content that can be shaped by a repository the user clones, fetches, or checks out (for example via crafted renames/copies, or paths containing `..`-like sequences that `git` will still report verbatim in certain edge cases, or via symlinked directories committed to the tree that Desktop resolves as ordinary working-directory entries). `Path.join` normalizes `..` segments but does not prevent the final path from landing outside `repository.path`, and it performs no symlink resolution, so a tracked symlink inside the repo pointing outside of it, combined with a "changed file" path traversing through that symlink, is not caught the way it explicitly is in the `resolveWithin`-based path. The `IAppShell` interface's own documentation acknowledges this danger ("Do not use this method with non-validated paths") yet `revealInFileManager` violates that contract by passing an unvalidated, attacker-influenced path straight through. [6](#0-5) 

Existing guards do not stop this path because:
- The `resolveWithin` containment/symlink check exists only in the deep-link `filepath` handler, not in `revealInFileManager`.
- `isSafeFileExtension` and the "File Does Not Exist on Disk" check in `selected-commits.tsx` only gate whether the menu item is *enabled*; they do not constrain *where* the resolved path may point. [7](#0-6) [8](#0-7) 

### Impact Explanation
`shell.showItemInFolder` on Windows/macOS/Linux opens the OS file manager and highlights the target path, which is generally viewed as low severity by itself, but here it demonstrates a genuine loss of the "stay within the repo" invariant that Desktop's own security model treats as important enough to enforce explicitly on the identical sink elsewhere. If any other path-supplying call site of `file.path` (or similarly attacker-shaped paths) is added to `revealInFileManager`, `openFile` (`app/src/ui/lib/open-file.ts`, which also does no containment check before calling `shell.openExternal("file://"+fullPath)`), or a future higher-impact sink that reuses `revealInFileManager`'s assumption that repository-derived paths are safe, the missing check becomes directly exploitable for revealing/opening files outside the intended repository. This mirrors the report's core lesson: a security check enforced on one code path handling a given value is silently absent on a sibling path handling the same class of (attacker-influenced) value, and that omission is a design defect independent of how severe today's concrete sink is.

### Likelihood Explanation
Reaching `revealInFileManager`/`openFile` requires the user to right-click a changed or committed file and choose "Reveal in Finder/Explorer" or "Open with Default Program" — a normal, expected interaction after cloning/fetching a repository, satisfying the "attacker controls a cloned/fetched repository" impact criterion without any unnatural steps. The attacker only needs to craft file/rename paths (or a tracked symlink) in the repository content; no local/physical access, admin rights, or prior compromise is required.

### Recommendation
Route `revealInFileManager` (and `openFile`) through the same `resolveWithin(repository.path, path)` containment/symlink check that `openRepositoryFromUrl` already uses before calling `shell.showItemInFolder`, and refuse to call the shell sink (logging an error instead, as `dispatcher.ts` does) when the resolved path falls outside the repository root or cannot be resolved.

### Proof of Concept
1. Clone or fetch a repository that contains a tracked symlink `escape` pointing to a directory outside the repo root (e.g. `ln -s / escape`), or a working-directory entry whose reported path allows escaping the repo root once joined with `repository.path`.
2. In Desktop's Changes or History view, right-click the corresponding file entry and select "Reveal in Finder"/"Show in Explorer".
3. `revealInFileManager` computes `Path.join(repository.path, path)` and calls `shell.showItemInFolder` on it without calling `resolveWithin`, unlike the equivalent `filepath` handling in `dispatcher.ts`'s `openRepositoryFromUrl`, so the file manager opens/reveals a location outside the intended repository directory instead of being rejected as "outside of the repository root." async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
