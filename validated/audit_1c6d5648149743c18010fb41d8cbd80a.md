### Title
Unchecked ERC-20 return value in `withdraw()` / `SweepDust` silently loses escrowed funds while marking escrow as redeemed - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` replaced the `SafeERC20`-based transfers used everywhere else in the intents codebase with raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls in `withdraw()` and in the `SweepDust` branch of `onAccept()`. These calls only check that the low-level call did not revert (`success`), but never decode and check the ERC-20 boolean return value. This is exactly the "silent fail" bug class from the external report, transplanted into Hyperbridge's intent-settlement escrow logic.

### Finding Description
Throughout `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/*`, and the `HyperFungibleToken*`/`WrappedHyperFungibleToken*` contracts, all ERC-20 movements use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, e.g. [1](#0-0)  and [2](#0-1) .

The Tron port of the same contract, however, uses unchecked-return low-level calls in two places:

In `withdraw()`, which redeems escrowed input tokens/fees to a beneficiary after `RedeemEscrow` or `RefundEscrow`: [3](#0-2) 

And in the `SweepDust` handler: [4](#0-3) 

Both only check `success` from the raw `.call`, meaning the call did not revert. They never inspect the ABI-decoded boolean returned by `transfer()`. Any ERC-20 implementation that signals failure by returning `false` instead of reverting (a standard-compliant pattern, not just non-compliant tokens like USDT) will make `success == true` while the beneficiary receives nothing. Despite this silent failure, the code unconditionally proceeds to:
- decrement `_orders[body.commitment][token] -= amount` (escrow accounting says funds were paid out), and
- set `_filled[body.commitment] = beneficiary` (marks the cross-chain order as permanently settled).

`withdraw()` is reached via `onAccept()`, gated by `onlyHost` and `authenticate(incoming.request)` for module/source binding [5](#0-4) , so this is not a spoofable message path — the vulnerability is purely in the unchecked-transfer logic, identical in spirit to the reported bug class (silent ERC-20 failure mishandled in settlement bookkeeping).

### Impact Explanation
Once `withdraw()` runs, the escrow ledger entry for that commitment/token is permanently zeroed and the order is marked filled/refunded, regardless of whether the token transfer actually succeeded. If the underlying token returns `false` on transfer failure (e.g., due to a paused token, blacklist, or any standard-compliant failure-by-return-value implementation), the beneficiary never receives the escrowed funds, yet the protocol's internal state says the order was already settled. The funds become permanently stuck/lost inside the contract with no remaining accounting path to recover them (the escrow slot is already zeroed and the order is already marked filled, so the withdrawal cannot be legitimately retried). This is a direct loss-of-funds condition inside the bridge's intent-settlement escrow.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — it is triggered purely by the properties of the escrowed ERC-20 token during a completely normal, correctly-authenticated `RedeemEscrow`/`RefundEscrow`/`SweepDust` flow. Any token listed for intents that follows the return-false-on-failure convention (common for older/simpler ERC-20s, and reachable any time a transfer would legitimately fail, e.g., temporary pause or blacklist at redemption time) will trigger this silently, making the likelihood non-trivial for a production deployment with permissionless token listings.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `evm/tron/contracts/apps/IntentGatewayV2.sol` with `SafeERC20.safeTransfer`, matching the pattern already used consistently elsewhere in the codebase (`IntentsBase.sol`, the mainline `IntentGatewayV2.sol`, `HyperFungibleToken.sol`, etc.), so that any non-successful transfer reverts the entire `onAccept` call instead of allowing escrow state to advance without the funds actually moving.

### Proof of Concept
1. List a token for intents whose `transfer()` returns `false` on failure instead of reverting (standard-compliant behavior, e.g., a token that pauses transfers to a blacklisted/paused beneficiary and returns `false`).
2. Create and fill a cross-chain order that escrows this token; get the `RedeemEscrow` request correctly proven and dispatched through the host to the destination `IntentGatewayV2` (Tron), landing in `onAccept()` → `withdraw()` at [6](#0-5) .
3. At execution time, the beneficiary is paused/blacklisted by the token contract so `transfer()` returns `false` without reverting; `success` is still `true`.
4. `withdraw()` proceeds to `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary`, permanently marking the order redeemed even though the beneficiary balance never increased — the escrowed tokens remain stuck in the contract with no accounting path left to reclaim them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
