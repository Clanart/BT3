### Title
Referral rebate computed on pre-forfeiture gross reward instead of post-forfeiture net transfer, allowing inflated referral payouts - ([File: rewards/MasterMagpie.sol])

### Summary
`MasterMagpie._multiClaim` computes `totalReward = vlMGPPoolAmount + mWOmPoolAmount + defaultPoolAmount` before any forfeiture deduction and passes this gross figure to `IReferralStorage(referral).trigger(_user, totalReward)`, while the vlMGP-pool portion is actually reduced by `_calExpireForfeit` inside `vlMGPBaseRewarder.queueMGP` before anything is transferred to the receiver. This lets a self-referring attacker who deliberately incurs forfeiture receive a referral rebate calculated on the inflated gross amount rather than the smaller amount actually paid out.

### Finding Description
In `_multiClaim` [1](#0-0) , `vlMGPPoolAmount` is accumulated from `_calNewMGP` (the user's gross, un-forfeited MGP entitlement for the vlMGP pool). It is then passed to `_sendMGPForVlMGPPool`, which calls `vlMGPRewarder.queueMGP(_amount, _account, _receiver)` [2](#0-1) .

Inside `queueMGP`, the actual amount transferred to `_receiver` is `rewardableAmount = _amount - forfeitAmount`, where `forfeitAmount` is computed from `vlMGP.getRewardablePercentWAD(_account)` — i.e., the user's early-unlock/vesting penalty — and the forfeited portion is redirected back into the pool's reward stream for other vlMGP stakers via `_queueNewRewardsWithoutTransfer`, not paid to the claimant [3](#0-2) .

Back in `_multiClaim`, `totalReward` (line 576) still uses the pre-forfeiture `vlMGPPoolAmount`, and this gross value is what is forwarded to `ReferralStorage.trigger(_user, totalReward)` [4](#0-3) . `trigger` uses `_amount` directly to compute `refererAmount`/`refereeAmount` as percentages of that gross value and credits them to `rewardAmount` balances that are later paid out in real MGP via `claimReward` (`MGP.safeTransfer`) [5](#0-4) . No downstream check reconciles the referral basis with the amount actually transferred to the claimant, so the mismatch is never corrected.

An attacker can exploit this by: (1) registering a referral code with one address, (2) using that code from a second address they control (`useCode` only blocks a code owner referring themselves directly, not a second attacker-controlled account) [6](#0-5) , (3) locking into vlMGP and then claiming under conditions that trigger a large forfeiture (e.g., early unlock reducing `getRewardablePercentWAD`), so `vlMGPPoolAmount` (gross) is much larger than the actual amount received. The referral commission is then calculated on the inflated gross figure rather than the net amount that was actually paid.

### Impact Explanation
The referral rebate is paid from `ReferralStorage`'s own MGP balance (a separately funded pool), not the same escrow that was forfeited (which is redirected to other vlMGP stakers). The bug therefore does not directly drain other users' locked principal, but it does allow the attacker's own referral cut to be computed on funds that were never actually delivered to the referee — a real conservation violation and unbacked payout from the referral reserve, proportional to `forfeitAmount * refererPercentage/refereePercentage`. This is a genuine, but percentage-bounded (fraction of `basic + boosted` tier rate, out of `DENOMINATOR`), leakage rather than an unbounded drain, and it only affects the referral reward pool rather than user staking principal or the vlMGP pool's solvency.

### Likelihood Explanation
Exploitation requires no privileged role: any EOA can register/use a referral code across two self-controlled addresses and then intentionally trigger vlMGP forfeiture (e.g., locking and unlocking early) before claiming. It is repeatable per claim cycle and scales with the size of the claimant's forfeited MGP and the referrer's tier rate, so a well-capitalized attacker with a high-tier referral code could repeat this to accumulate meaningful excess rewards from the referral pool over time.

### Recommendation
Compute `totalReward` for the referral trigger using the actually-transferred (post-forfeiture) amounts rather than the pre-forfeiture gross sums. This requires `queueMGP` (and the mWOM/default-pool equivalents, if they also apply forfeiture) to return the net `rewardableAmount` back to `_multiClaim`, and for `totalReward` in `MasterMagpie._multiClaim` to be built from those net values before calling `IReferralStorage(referral).trigger(_user, totalReward)`.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder`, `ReferralStorage`, and `MGP` token with test wiring (referral set on MasterMagpie, ReferralStorage pre-funded with MGP).
2. Address A calls `registerCode(codeA)`; Address B calls `useCode(codeA)`.
3. Address B locks MGP into vlMGP, then triggers conditions causing `vlMGP.getRewardablePercentWAD(B)` to be low (e.g., early unlock/partial relock) so a nonzero forfeiture will occur on claim.
4. Address B calls `multiclaim([vlMGP pool])`.
5. Assert: `ERC20(MGP).balanceOf(B)` (or receiver) equals `rewardableAmount` (net, post-forfeiture) transferred by `queueMGP`, confirmed via `MGPHarvested` event's `forfeitAmount`.
6. Assert: `ReferralStorage.userInfos(A).rewardAmount` / `userInfos(B).rewardAmount` were incremented using the pre-forfeiture gross `vlMGPPoolAmount` (i.e., `RefererRewardHarvested`/`RefereeRewardHarvested` amounts computed off a base larger than the net amount B actually received) — verifying `totalReward` passed to `trigger` did not match the net transferred amount.
7. Show that `refererAmount + refereeAmount` computed off gross exceeds what would be computed off net by exactly `forfeitAmount * (basic+boosted)/DENOMINATOR`, demonstrating the excess payout basis.

    function queueMGP(uint256 _amount, address _account, address _receiver) override external onlyManager nonReentrant returns (bool) {
        IERC20(vlMGP.MGP()).safeTransferFrom(msg.sender, address(this), _amount);
        
        uint256 forfeitAmount = _calExpireForfeit(_account, _amount);
        uint256 rewardableAmount = _amount - forfeitAmount;
        
        if (forfeitAmount > 0)
            _queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()));

        if (rewardableAmount > 0) {
            IERC20(vlMGP.MGP()).safeTransfer(_receiver, rewardableAmount);
            emit MGPHarvested(_account, rewardableAmount, forfeitAmount);
        }

        return true;
    }
