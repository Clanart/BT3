### Title
Desynchronized per-participant preprocess count causes index-out-of-bounds panic, permanently aborting the Bitcoin signing session - (File: networks/bitcoin/src/wallet/send.rs)

### Summary

The external report's bug class — two interdependent values that are set/updated independently, such that a mid-flight desynchronization causes a hard revert with no recovery path — maps onto `TransactionSignMachine::sign` in `networks/bitcoin/src/wallet/send.rs`. The number of inputs (`self.sigs.len()`, fixed locally at `SignableTransaction::new` time) and the number of preprocesses each participant supplies (`commitments[c]`, deserialized from untrusted remote bytes via `read_preprocess`) are interdependent but independently controlled. When a participant's preprocess vector is shorter than the input count, `commitments[c]` panics with an index-out-of-bounds, killing the signing session after remote preprocesses have already been consumed. There is no rescue path and the preprocesses cannot be cached or reused.

### Finding Description

`SignableTransaction::new` fixes the input count and derives `offsets`/`prevouts` from the caller-supplied `Vec<ReceivedOutput>` [1](#0-0) . `preprocess` then produces exactly one `Preprocess` per signature machine, i.e. per input [2](#0-1) . In `sign`, remote preprocesses are read per participant via `read_preprocess`, which collects `self.sigs.len()` entries **only for the local machine's own reads** — each remote participant's submitted `Vec<Preprocess>` is read with whatever count `read_preprocess` actually pulled, but nothing validates that a participant's committed vector length equals `self.sigs.len()`:

```rust
// networks/bitcoin/src/wallet/send.rs
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))  // panics if commitments.len() <= c
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
``` [3](#0-2) 

`commitments[c]` is indexed by the input index `c` with no bounds check. A participant whose `SignatureShare`/`Preprocess` vector has fewer than `self.sigs.len()` elements (e.g. because their view of the transaction, or their `read_preprocess` stream, desynced from the coordinator's input list — exactly the "one value updated without the other" shape of the L1Gateway `counterpartyFee`/`finalizationFee` desync) causes a panic rather than a clean `FrostError`.

Because `TransactionMachine`/`TransactionSignMachine` explicitly forbid `cache`/`from_cache` (`unimplemented!` panics) [4](#0-3) , the consumed preprocesses cannot be recovered; the signing session must be torn down and restarted with fresh nonces.

### Impact Explanation

- Any single participant (or a coordinator/transport layer that mis-serializes preprocesses) can deterministically panic `sign` for every honest signer evaluating the commitment map, aborting the Bitcoin spend.
- Since signing a transaction requires threshold participation and preprocesses are single-use (nonce reuse across sessions is exactly the ROS/FROST danger this design avoids by banning caching), each abort burns the preprocess round; a persistent desync between "locally scanned input count" and "remotely committed preprocess count" makes the vault's `ReceivedOutput`s unspendable for that session — funds stuck, mirroring the report's `finalizeTransfer` revert with no rescue path.
- This is a panic inside library code (index OOB), so integrators cannot catch it as a `Result` error; depending on runtime configuration it aborts the whole signing process.

### Likelihood Explanation

Reachable by an unprivileged party: any participant who submits preprocess bytes through `TransactionSignMachine::read_preprocess`/`sign` controls the length of their `Vec<Preprocess>` [5](#0-4) . The interdependence (`sigs.len()` vs per-participant preprocess count) is never validated — analogous to the fee pair being updated independently. It requires no collusion: a single desynced or malicious participant suffices. Severity is bounded to session-level DoS (Medium): funds are not stolen and can be recovered by restarting with consistent preprocesses, but there is no in-protocol mitigation, rescue path, or graceful error.

### Recommendation

Validate the interdependent values before use, mirroring the report's recommendation:

1. In `TransactionSignMachine::sign`, check `commitments.len() == self.sigs.len()` for every participant's preprocess vector and return a `FrostError` (e.g. `FrostError::InvalidPreprocess` / a new `InvalidCommitmentQuantity`) instead of indexing blindly.
2. Alternatively, bound-check with `commitments.get(c)` and propagate an error, so a desynchronized participant is blameable rather than fatal to the process.

```rust
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| {
        commitments
          .get(c)
          .cloned()
          .map(|p| (*l, p))
          .ok_or(FrostError::InvalidCommitment(*l)) // explicit blame, no panic
      })
      .collect::<Result<HashMap<_, _>, _>>()
  })
  .collect::<Result<Vec<_>, _>>()?;
```

### Proof of Concept

Construct a `SignableTransaction` with two inputs (two `ReceivedOutput`s), run `preprocess` on each participant machine, but for one participant transmit/truncate their `Vec<Preprocess>` to length 1 (equivalent to a desynced peer whose input list was shorter, or a `read_preprocess` buffer that yielded fewer items). When any honest participant calls `TransactionSignMachine::sign` with the `HashMap<Participant, Vec<Preprocess>>` containing that short vector, `commitments[c]` for `c == 1` panics with `index out of bounds`:

```rust
// inside TransactionSignMachine::sign, with self.sigs.len() == 2
// malicious/desynced participant sent commitments.len() == 1
commitments[c].clone() // c == 1 -> panic: index out of bounds: len is 1 but index is 1
```

The panic occurs at `networks/bitcoin/src/wallet/send.rs` line ~368 before any signature share is produced, and `cache`/`from_cache` `unimplemented!` [4](#0-3)  means the session's preprocesses are unrecoverable — the spend is stuck for that session with no rescue function, directly analogous to the reported `finalizeTransfer` revert.

  fn preprocess<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
  ) -> (Self::SignMachine, Self::Preprocess) {
    let mut preprocesses = Vec::with_capacity(self.sigs.len());
    let sigs = self
      .sigs
      .drain(..)
      .map(|sig| {
        let (sig, preprocess) = sig.preprocess(rng);
        preprocesses.push(preprocess);
        sig
      })
      .collect();

    (TransactionSignMachine { tx: self.tx, sigs }, preprocesses)
  }
