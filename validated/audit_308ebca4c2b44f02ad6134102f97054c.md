### Title
Malformed `EncryptedMessage` triggers early-return blame that leaks the recipient's ECDH key for an arbitrary `msg.key`, decrypting an honest participant's share — (`File: crypto/dkg/pedpop/src/lib.rs`)

### Summary
`Encryption::decrypt` always returns an `EncryptionKeyProof` containing the ECDH shared point `enc_key * msg.key` for whatever `msg.key` the attacker supplies, before the Schnorr proof-of-possession on `msg.key` is verified — that check is only queued into a `BatchVerifier`. In `KeyMachine::calculate_share`, a deserialized share that fails `C::F::from_repr` returns `PedPoPError::InvalidShare` with `blame: Some(...)` via `?`, so `batch.verify_with_vartime_blame()` never runs and the PoP is never checked. This reintroduces the exact key-co-option attack the PoP exists to prevent (documented in `spec/cryptography/Distributed Key Generation.md` and the comments in `encryption.rs`): an attacker copies the per-message key `X` from an honest Alice→Bob share message, attaches a garbage PoP and arbitrary ciphertext, and Bob — upon failing to deserialize — publishes `bX`, the shared key that also decrypts Alice's real ciphertext.

### Finding Description
The reference bug class is "a crafted input field causes an unauthorized party to receive a response disclosing sensitive data." Serai's analog lives in the PedPoP blame path.

`Encryption::decrypt` at `crypto/dkg/pedpop/src/encryption.rs:469-501` computes `key = ecdh(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }` unconditionally; the PoP is only *queued* via `msg.pop.batch_verify(...)` (line 479). In `KeyMachine::calculate_share` at `crypto/dkg/pedpop/src/lib.rs:476-499`, the decrypted bytes are passed through `C::F::from_repr` at line 480, and failure returns early with `blame: Some(blame)` — skipping `batch.verify_with_vartime_blame()` at line 493 entirely. The PoP that would have caught the forged `msg.key` is therefore never verified.

`pop_challenge`/`msg.pop.verify` is only checked inside `Decryption::decrypt_with_proof` (`encryption.rs:374-379`), which runs later when the coordinator adjudicates blame — by which time `proof.key = bX` has already been broadcast inside `ProcessorMessage::InvalidShare` (`processor/src/key_gen.rs:419-425`) and ultimately reaches `VerifyBlame` (`processor/src/key_gen.rs:504-563`). Even though the attacker is then correctly blamed and slashed, the ECDH point `bX` is public, and anyone holding Alice's public `EncryptedMessage` to Bob (whose `key` field is `X`) can run `cipher(context, bX)` to recover Alice's secret share for Bob.

Reliability: the attacker does not control the plaintext after ChaCha20 keystream under unknown key `bX`, but for Ristretto/ed25519 only ~1/16 of random 32-byte strings are canonical scalars, so a random ciphertext produces a non-canonical `from_repr` failure with ~94% probability, deterministically triggering the early-return blame.

### Impact Explanation
An unprivileged DKG participant causes an honest victim to publicly disclose the ECDH key that decrypts another honest participant's secret share. This is unauthorized disclosure of a threshold secret share: an attacker who additionally compromises or collects enough such leaked shares (or colludes within the permitted threshold-adversary model) recovers honest participants' polynomial contributions, degrading or breaking the confidentiality of the resulting `ThresholdKeys` secret.

### Likelihood Explanation
Requires only participation in a DKG session and sending one crafted `Shares` message; no honest-party misbehavior needed beyond Bob processing the malformed share. The attacker is eventually blamed and slashed when the forged PoP fails adjudication, but the disclosure is irreversible — the ECDH key is published in the blame message before validation.

### Recommendation
Verify `msg.pop` (and/or bound the decrypt attempt to it) *before* constructing the `EncryptionKeyProof`, or defer generation of the blame proof until after `batch.verify_with_vartime_blame()` confirms the PoP. Concretely, in `KeyMachine::calculate_share`, do not attach the `blame` returned by `decrypt` to the `from_repr` early-return path unless the PoP for that message has already been verified; alternatively make `decrypt` synchronously verify the PoP before computing/returning `ecdh(...)`.

### Proof of Concept
1. Observe Alice's `EncryptedMessage` to Bob; copy its `key` field `X`.
2. Attacker (participant Eve) sends to Bob a `SecretShare` `EncryptedMessage` with `key: X`, a garbage `pop: SchnorrSignature`, and random `msg` bytes.
3. Bob's `KeyMachine::calculate_share` calls `decrypt`, which queues (never runs) PoP verification and computes `key = ecdh(b_enc, X)`; `from_repr` fails with high probability → `PedPoPError::InvalidShare { participant: Eve, blame: Some(EncryptionKeyProof{ key: bX, ... }) }`.
4. Bob broadcasts `ProcessorMessage::InvalidShare` containing `blame.serialize()` → `bX` is public.
5. Anyone computes `cipher::<C>(context, bX)` and applies it to Alice's public ciphertext for Bob, recovering Alice's share `f_alice(bob)`. Blame adjudication blames Eve, but only after disclosure.
