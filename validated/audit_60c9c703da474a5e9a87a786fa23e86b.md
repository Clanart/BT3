### Title
Verification shares for participants beyond `t` are never bound to the group key, so a `ThresholdKeys` deserialized with a tampered share silently keeps a stale/attacker-controlled share that is later trusted as authoritative - (crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` derives `group_key` by interpolating only `verification_shares[1..=t]` and never checks that the remaining `n - t` entries correspond to the same polynomial (or even to the stored `secret_share`). `view()` then unconditionally uses `self.core.verification_shares[i]` for every participant in an `included` signing set. This mirrors the audited bug class: a per-element record that is skipped during the global update keeps a stale value while the shared invariant (the group key, analogous to `nominal * multiplier`) is recomputed and treated as correct.

### Finding Description
In `crypto/dkg/src/lib.rs`:

```rust
// ThresholdKeys::new only interpolates participants 1..=t
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

The only validation of the full map is a length and index-bound check:

```rust
if verification_shares.len() != usize::from(params.n()) { ... }
for participant in verification_shares.keys().copied() {
  if u16::from(participant) > params.n() { ... }
}
```

There is no check that `verification_shares[i]` for `i > t` equals `G * share_i` of the same polynomial, nor that `verification_shares[i()] == G * secret_share`. Later, `view()` trusts every entry:

```rust
let verification_share = self.core.verification_shares[i] *
  self.scalar * self.core.interpolation.interpolation_factor(*i, &included);
```

`ThresholdKeys` is deserializable (`ThresholdKeys::read`, listed in-scope) and is re-materialized from stored bytes in `GeneratedKeysDb::read_keys` (`processor/src/key_gen.rs:56-60`) before being used to sign. Any consumer feeding it untrusted bytes (the allowed input surface) can pass a key whose `group_key` is perfectly valid while one or more post-`t` verification shares are attacker-chosen.

### Impact Explanation
Two concrete consequences, depending on how the tampered entry is set:

- If `verification_shares[i]` (`i > t`) is replaced with a wrong point while `secret_share` is left intact, any signing set containing `i` produces shares that fail verification against the interpolated verification share — the honest participant `i` is identified as faulty (`FrostError::InvalidShare(i)` → `ProcessorMessage::InvalidParticipant`), enabling targeted false-blame/slashing of an honest signer, persistently, since the corrupted key is stored.
- The analog of the vault accounting drift: the signing protocol's "bookkeeping" (which participant is honest) is permanently skewed by a record that was skipped during key validation.

This is analogous to the skipped-token `nominal` bug: an element excluded from the consistency update retains a stale value that is later consumed as if it had been updated.

### Likelihood Explanation
Requires an attacker to supply or corrupt the serialized `ThresholdKeys` (or any upstream DKG transcript that produces inconsistent `verification_shares` past index `t` — PedPoP constructs them consistently, but `ThresholdKeys::new`/`read` do not enforce it). Reachable through the explicitly in-scope `ThresholdKeys::read` surface; internal use is honest. Medium.

### Recommendation
In `ThresholdKeys::new` (and therefore `read`), verify consistency for all `n` shares — e.g., check that interpolating the group key over several distinct `t`-subsets yields the same point, or at minimum verify `verification_shares[params.i()] == C::generator() * secret_share` plus a spot-check that the map reconstructs `group_key` for participants beyond `t` (e.g., require the caller to pass `n` shares derived from a degree `t-1` polynomial and verify a second `t`-subset). Reject keys where any skipped entry is inconsistent rather than silently ignoring them.

### Proof of Concept
```rust
// For t=2, n=3: build honest dealer keys, then tamper share for participant 3.
let mut keys = key_gen::<_, C>(&mut rng, 2, 3)?;
let mut shares = keys[&Participant::new(1)].core-verification_shares-clone();
shares.insert(Participant::new(3).unwrap(), C::G::identity()); // stale/garbage entry

let forged = ThresholdKeys::new(
  ThresholdParams::new(2, 3, Participant::new(1).unwrap()).unwrap(),
  Interpolation::Lagrange,
  keys[&1].original_secret_share().clone(),
  shares,
).unwrap();

assert_eq!(forged.group_key(), keys[&1].group_key()); // group key unaffected

// Signing with included = [1, 3] now produces a share for participant 3 that
// fails verification against identity — participant 3 is blamed despite being
// honest, persistently, for every signing set containing it.
```

The exact lines: `crypto/dkg/src/lib.rs` `ThresholdKeys::new` (~lines 355-391: bound checks only, group key from `1..=t`) and `view` (~lines 500-507: unguarded use of `verification_shares[i]` for all `included`).
