### Title
Missing zero-value validation in `ThresholdKeys::read` allows identity group keys and zero secret shares - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-influenced bytes into a usable threshold key, but performs no zero/identity validation on the three security-critical values it reads: the `Constant` interpolation coefficients (`C::read_F`), the `secret_share` (`C::read_F`), and the `verification_shares` (`Ciphersuite::read_G`, which does *not* reject the identity point). An all-zero `Constant` coefficient vector — or all-identity verification shares — yields `group_key == identity`, a key under which Schnorr signatures are trivially forgeable by anyone, and for which the funded output is either unspendable or spendable by an arbitrary party.

### Finding Description
The audit-issue bug class is "a public input is accepted without rejecting the zero value, leading to unexpected/insecure behavior." In Serai, the analog lives in `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:574-632`:

- Interpolation coefficients are read with `C::read_F` (canonical scalar only, zero permitted) at lines 607-612.
- `secret_share` is read with `C::read_F` at line 618 — a zero share is accepted, whereas `Ciphersuite::random_nonzero_F` exists precisely because zero scalars are dangerous (`crypto/ciphersuite/src/lib.rs:62-68`).
- `verification_shares` are read with `<C as Ciphersuite>::read_G` at line 622. Note this deliberately bypasses `Curve::read_G` (`crypto/frost/src/curve/mod.rs:123-131`), which rejects identity points; the generic `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only enforces canonicality, not non-identity.

`ThresholdKeys::new` then computes the group key as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` (lines 376-378). For `Interpolation::Constant`, `interpolation_factor` returns the raw deserialized coefficient `c[i-1]` (lines 227-229). Setting every coefficient to zero forces `group_key = identity` regardless of how strong the verification shares are. `ThresholdKeys::new` checks share counts, participant indexes, and that `t == n` for Constant interpolation — but never checks that the resulting `group_key`, the coefficients, or the secret share are non-zero.

### Impact Explanation
A `ThresholdKeys` with `group_key == identity` is catastrophic wherever it is used:

- Schnorr verification `R + c·A − s·G == 0` (`crypto/schnorr/src/lib.rs:88-110`) with `A = identity` reduces to `R == s·G`, satisfiable by anyone for any challenge — universal forgery against that "group key."
- For Bitcoin (Secp256k1), `x_only`/`x` panic on the point at infinity (`networks/bitcoin/src/crypto.rs:13-23`), so a tweaked identity key is a guaranteed panic/DoS at minimum, and any successful signature produced under it is key-independent.

A zero `secret_share` is separately accepted: the holder produces signature shares `s_i = c·0·λ_i + nonce = nonce`, contributing no key material — shares that verify against an attacker-chosen view while the "participant" holds no secret.

### Likelihood Explanation
Reachability requires adversarial bytes to reach `ThresholdKeys::read` — a path the engagement scope explicitly enumerates as untrusted-input-reachable. Within that path, the attacker fully controls every byte (params, interpolation variant and coefficients, secret share, all verification shares), so triggering the identity group key is deterministic, not probabilistic. The main constraint is deployment-dependent: the key blob must actually be consumed for signing/verification rather than only stored. Given the deterministic control once reached, this is a solid Medium.

### Recommendation
In `ThresholdKeys::new` (which `read` calls), reject:

1. Any `secret_share` equal to `C::F::ZERO`.
2. `Interpolation::Constant` vectors containing a zero coefficient (or at minimum, reject a resulting `group_key` that `is_identity()`).
3. Identity `verification_shares` — enforce non-identity either by using a `read_G` variant that rejects identity or by an explicit `is_identity()` check inside `ThresholdKeys::new`, which also protects programmatic callers such as `musig()` whose `keys` list is not identity-screened (`crypto/dkg/musig/src/lib.rs:46-63` only checks for duplicates).

### Proof of Concept
```rust
// Conceptual PoC against ThresholdKeys::<C>::read with t == n = 1
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&1u16.to_le_bytes()); // t
buf.extend(&1u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes()); // i
buf.push(0);                     // Interpolation::Constant
buf.extend(C::F::ZERO.to_repr().as_ref());          // coefficient c[0] = 0
buf.extend(C::F::ZERO.to_repr().as_ref());          // secret_share = 0
buf.extend((C::generator()).to_bytes().as_ref());   // verification share

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// group_key = share * c[0] = identity
assert!(bool::from(keys.group_key().is_identity()));
// Any Schnorr signature (R = s*G, arbitrary s) now verifies for this group key.
```

With `n > 1`, set every `Constant` coefficient (or every verification share, via the identity-encoding bytes) to zero/identity to obtain the same result; alternatively a zero `secret_share` alone produces a participant that signs without contributing key material.
