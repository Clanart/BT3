### Title
Wildcard sentinel asset name `"*"` collides with a legitimately named fungible token, allowing `restrict-assets?`/`as-contract?` FT allowances to escape their post-conditions - (File: `clarity/src/vm/functions/post_conditions.rs`)

### Summary
`check_allowances` implements the FT-allowance-matching logic for the `restrict-assets?` and `as-contract?` special forms. To support "wildcard" allowances that cover every fungible token in a contract, it treats the literal `AssetIdentifier` whose `asset_name` equals the string `"*"` as a magic sentinel value, and merges its allowance amount into the check for *every* other fungible token moved from that contract. [2](#0-1) 

The problem: `"*"` is not a reserved token in the Clarity grammar. The `ClarityName` validation regex explicitly allows a lone `"*"` as a valid name (it matches the `^[-+=/*]$` branch), so any contract may define a real fungible token named exactly `*` via `define-fungible-token`. [1](#0-0) [3](#0-2) 

### Finding Description
`with-ft` allowances are evaluated by `eval_allowance` and stored as an `AssetIdentifier { contract_identifier, asset_name }` pair with no special-casing of the asset name at construction time. [4](#0-3) 

Later, in `check_allowances`, allowances are indexed into `ft_allowances: HashMap<AssetIdentifier, Vec<(usize, u128)>>` keyed by the exact `AssetIdentifier` supplied by the caller — including one whose `asset_name` is `"*"`. [5](#0-4) 

When checking actual FT movement for each asset moved from the protected owner, the code builds a `merged` allowance list consisting of (a) allowances keyed by the exact `asset` moved, and (b) allowances keyed by `AssetIdentifier { contract_identifier: asset.contract_identifier.clone(), asset_name: "*" }`, unconditionally treating any allowance entry with `asset_name == "*"` as a wildcard that covers all FTs in that contract: [2](#0-1) 

Because the lookup is purely a `HashMap` key match on `AssetIdentifier{contract_identifier, asset_name: "*"}`, the code cannot distinguish between:
1. An allowance the developer *intended* as a wildcard (`with-ft` for a token that does not exist, meant to cover "any FT in this contract"), and
2. An allowance for a *real, distinct* fungible token whose asset name happens to be the literal string `"*"` — a name that is fully valid per the Clarity name grammar.

This breaks the equality the post-condition system is supposed to enforce: "the amount of asset X moved must not exceed the amount explicitly allowed for asset X." Instead, an allowance entry for the specific token `*` is silently promoted into blanket permission for every other, unrelated fungible token in the same contract that the caller never explicitly authorized.

### Impact Explanation
This is a post-condition/allowance escape: an `as-contract?` or `restrict-assets?` block that includes `(with-ft .some-contract "*" amount)` — intending to authorize movement of only the actual token named `*` — unintentionally authorizes movement of *every* fungible token defined in `.some-contract` up to `amount`, even ones with entirely different (and possibly much higher-value) semantics. If the contract being called mints/moves a different, more valuable FT in the same contract instead of (or in addition to) the intended one, that movement is not flagged as a violation, and funds move past the caller's actual post-conditions/allowances without authorization. This matches the "asset moving past its post-conditions" Critical impact category: the caller's protective scope is bypassed and assets it did not intend to expose can be drained by a called contract, without the caller's signature covering that specific asset movement.

### Likelihood Explanation
Likelihood is limited by an unusual precondition: a contract must define (or have already defined) a fungible token whose Clarity name is exactly the single character `*`, and a caller must write an allowance list that names that same literal token. This requires either (a) an attacker-authored contract intentionally naming a token `*` to bait callers who write a `with-ft` allowance believing they're restricting to that one token, or (b) accidental construction of such a name. Because `*` is a valid, unremarkable-looking identifier under the grammar, and `with-ft`/`restrict-assets?`/`as-contract?` are newly introduced Clarity constructs, this is a plausible trap for contract authors, but it is not automatically triggered by every normal post-condition usage — it requires this specific naming collision to be present.

### Recommendation
Do not overload a valid Clarity identifier as a semantic wildcard sentinel inside `AssetIdentifier`. Wildcard-FT/NFT allowances should be represented as a distinct enum variant (e.g. `Allowance::FtWildcard { contract_identifier, amount }`) instead of a magic `asset_name == "*"` string, so a legitimately-named token `*` can never be confused with "any FT in this contract." If backward compatibility requires keeping the string-based signal, reject `"*"` as a valid token name in `define-fungible-token`/`define-non-fungible-token`, or require an unambiguous distinguishing syntax (e.g. a dedicated `with-ft-any`/`with-nft-any` native) for wildcard allowances.

### Proof of Concept
1. Deploy contract `evil.token` that defines two fungible tokens: `(define-fungible-token * u1000000)` (the "decoy") and `(define-fungible-token valuable-token u1000000)`.
2. Caller writes: `(as-contract? ((with-ft 'SP...evil.token "*" u10)) (contract-call? 'SP...evil.token drain-valuable-token))`, intending to allow moving up to 10 units of the token literally named `*`.
3. Inside `check_allowances`, the FT allowance for `AssetIdentifier{contract: evil.token, asset_name: "*"}` is placed in `ft_allowances`.
4. `evil.token`'s `drain-valuable-token` function transfers a large amount of `valuable-token` (not `*`) out of the caller's account.
5. When `check_allowances` processes the FT movement for `valuable-token`, it looks up `ft_allowances.get(&AssetIdentifier{contract: evil.token, asset_name: "*"})` as the wildcard fallback and finds the caller's `*`-named allowance, merging it in as if it authorized `valuable-token` movement too.
6. Because the merged allowance amount (`u10`) may still be less than the amount moved, this specific PoC may or may not trip `amount_moved > allowance`; however, if the caller's `*` allowance amount is set high enough to cover the decoy token realistically, `valuable-token` movement up to that same amount is now silently permitted — despite the caller never having named `valuable-token` in any allowance. The core equality break is demonstrated at [6](#0-5) , where any allowance keyed with `asset_name: "*"` is unconditionally merged into every other asset's check within the same contract, regardless of whether the developer meant it as a true wildcard or as a specific token name.
