Confirmed vulnerability: `CW721ERC721Pointer` overrides `transferFrom` to actually execute the CW721 `transfer_nft` message via the wasmd precompile [1](#0-0) , but does **not** override the standard OpenZeppelin `safeTransferFrom(address,address,uint256[,bytes])` functions. Since `CW721ERC721Pointer` inherits `ERC721` from OpenZeppelin, calling `safeTransferFrom` on the pointer goes through OZ's own internal `_transfer`/`_safeTransfer` (which mutate OZ's local `_owners`/`_balances` storage and perform the `onERC721Received` check) instead of calling `_execute` to submit the `transfer_nft` message to the real CW721 contract on the Cosmos side. The contract's constructor and state confirm it holds no local canonical ownership data of its own — `ownerOf`/`balanceOf`/`getApproved` are all overridden to query the underlying CW721 contract live via the wasmd precompile [2](#0-1) , meaning the OZ base-contract's internal bookkeeping is dead/unused state that is inconsistent with the real source of truth.

### Title
CW721ERC721Pointer `safeTransferFrom` bypasses CW721 execution, causing loss/desync of NFT ownership - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer` is an ERC721 EVM pointer contract that lets EVM users interact with a native CosmWasm CW721 NFT collection. It overrides `transferFrom`, `approve`, and `setApprovalForAll` to route the call to the real CW721 contract through the wasmd precompile via `_execute`. However, it never overrides `safeTransferFrom(address,address,uint256)` or `safeTransferFrom(address,address,uint256,bytes)`, both of which are still provided by the parent OpenZeppelin `ERC721` implementation.

### Finding Description
The OZ `ERC721.safeTransferFrom` implementation internally calls `_transfer`, which updates OZ's own `_owners`/`_balances` mappings and then performs the ERC721 `onERC721Received` check — it does **not** call `_execute`, and therefore never sends the `{"transfer_nft":...}` message to the underlying CW721 contract at `Cw721Address` [3](#0-2) . Meanwhile, every read function (`ownerOf`, `balanceOf`, `getApproved`, `isApprovedForAll`) queries the live CW721 state through `WasmdPrecompile.query` [4](#0-3) , completely ignoring the OZ base-contract's local storage.

As a result, when any unprivileged EVM user (funder, marketplace contract, wallet, etc.) calls `safeTransferFrom` on a `CW721ERC721Pointer` instance instead of `transferFrom`:
- The `require(from == ownerOf(tokenId), ...)` check present in the overridden `transferFrom` is skipped entirely.
- No `transfer_nft` CosmWasm message is ever executed, so the real owner recorded by the CW721 contract on the Cosmos side never changes.
- OZ's internal state is mutated as if the transfer succeeded (emitting a `Transfer` event and updating dead `_owners`/`_balances` storage that no other function in the contract reads).
- The transaction succeeds and returns success to the caller, giving the false impression that the NFT was transferred, while `ownerOf`/`balanceOf` (which hit the real CW721 contract) still show the token belonging to the original owner.

This is directly analogous to the reported bug class (a contract path that receives/transfers an NFT via `safeTransferFrom` inconsistently with the intended custody logic), except here the root cause is override omission causing state desync/fund loss rather than a missing `onERC721Received` implementation.

### Impact Explanation
Any contract or user that relies on `safeTransferFrom` (the canonical, safety-checked ERC721 transfer method commonly used by marketplaces, wallets, and other DeFi integrations such as the repo's own `NftMarketplace.sol`, which calls `IERC721(nftAddress).safeTransferFrom(...)` [5](#0-4) ) against a `CW721ERC721Pointer` token will experience a silent no-op transfer on the actual CW721 asset while their local EVM view diverges. This can lead to:
- Permanent desynchronization between the pointer's ERC721 view and the real CW721 owner (though reads always re-query the CW721 side, so the "phantom" OZ state is largely unobservable — but any code path relying on ERC721 standard event logs, e.g. an indexer, marketplace escrow logic, or off-chain listing service that trusts the `Transfer` event, will be misled).
- If any code within the pointer contract (or a future upgrade) ever reads OZ's internal `_owners`, it would report incorrect ownership, and combined with the emitted `Transfer` event, third parties (marketplaces, custodial bridges) could be tricked into believing an NFT changed hands when it has not, enabling fund-loss scenarios (e.g., a marketplace paying out proceeds based on a spoofed successful transfer).

### Likelihood Explanation
High reachability: `safeTransferFrom` is a standard, widely-used public ERC721 entry point that any unprivileged EVM transaction sender or integrating contract (e.g., marketplaces, wallets) would naturally call instead of `transferFrom`, especially since it is considered the "safer" standard method. No special privileges are required — a normal user holding a pointer NFT can trigger this by simply using `safeTransferFrom`, or unknowingly be affected when a marketplace contract uses it on their behalf.

### Recommendation
Override both `safeTransferFrom(address,address,uint256)` and `safeTransferFrom(address,address,uint256,bytes)` in `CW721ERC721Pointer` to perform the same `ownerOf` check and `_execute` call as `transferFrom` (optionally followed by an `onERC721Received` check against the recipient), rather than allowing the OZ base implementation to execute unrelated to the real CW721 contract.

### Proof of Concept
1. Deploy a `CW721ERC721Pointer` for an existing CW721 collection via `RegisterPointer`/`deployErc721PointerForCw721`.
2. As the token owner (an unprivileged EVM account), call `pointer.safeTransferFrom(owner, attacker, tokenId)`.
3. Observe: the call succeeds and emits `Transfer(owner, attacker, tokenId)`, but `pointer.ownerOf(tokenId)` (which queries the live CW721 contract) still returns `owner`, because no `transfer_nft` message was ever executed on the CW721 side — confirming the transfer was a no-op on the actual asset despite emitting a successful transfer event.
