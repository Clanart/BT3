### Title
OP_RETURN `data` output is excluded from fee/weight accounting, so `SignableTransaction` silently underpays the requested fee rate — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the OpenQ issue — where a second value-carrying input (`msg.value`) is silently dropped once the ERC20 branch is taken — `SignableTransaction::new` accepts a second output-carrying input (`data`) that is pushed into the real transaction's outputs yet silently excluded from every subsequent weight, vbyte, fee, and size calculation. The "extra" output is accepted but never paid for.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then appends an `OP_RETURN` output when `data` is `Some` (`send.rs:194-202`). However, the very next line computes the fee over a reconstruction that contains only `payments`: [1](#0-0) 

`calculate_weight_vbytes` rebuilds the transaction from `inputs`/`payments`/`change` only — the OP_RETURN output is never modeled: [2](#0-1) 

The same omission occurs in the change branch (`send.rs:224-234`), so `vbytes`, `needed_fee`, `weight` (used for the `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241`), and the `TooLowFee` minimum-relay check at `send.rs:211` are all computed on a smaller transaction than the one actually constructed. Just as `BountyCore.receiveFunds` accepted native value it never accounted for, `SignableTransaction::new` accepts output bytes it never accounts for.

### Impact Explanation
- The effective fee rate is strictly lower than the caller-specified `fee_per_vbyte`, by `(OP_RETURN output weight) * fee_per_vbyte` — up to ~90 vbytes for the max 80-byte payload.
- The `TooLowFee` guard can pass for a transaction whose true size puts it below `DEFAULT_MIN_RELAY_TX_FEE`, producing a signed transaction that peers reject; the spent inputs' funds are effectively unmovable until a new signing round with different parameters.
- The `MAX_STANDARD_TX_WEIGHT` check can pass for a transaction that exceeds the standard weight once the OP_RETURN output is included.
- `needed_fee()` misreports the fee, and `fee()` (inputs − outputs) will exceed `needed_fee` only in the no-change case; with change, the shortfall comes out of the change output, silently paying less than intended.

### Likelihood Explanation
Any caller that supplies `data` triggers it deterministically — the miscount is unconditional, not edge-case. Whether it becomes a consensus/relay failure depends on how close the requested fee is to the minimum, but the incorrect-fee outcome occurs on every invocation with `data.is_some()`. Reachable with purely public inputs (`data` is an untrusted byte vector parameter). Medium severity: accounting incorrectness producing under-priced transactions and potential stuck funds, without secret leakage.

### Recommendation
Include the OP_RETURN output in the size model. Pass `data` (or the already-built `tx_outs`) into `calculate_weight_vbytes`, e.g. extend its signature to `calculate_weight_vbytes(inputs, payments, change, data_len)` and push the same `TxOut` used at `send.rs:195-201` into the dummy transaction, in both the initial call (`send.rs:204`) and the change call (`send.rs:225-226`).

### Proof of Concept
```rust
// Conceptual: construct with data = Some(vec![0u8; 80])
let st = SignableTransaction::new(inputs, &payments, change, Some(vec![0; 80]), 1).unwrap();
// st.tx.output contains 3 outputs (payment, OP_RETURN, change),
// but needed_fee was computed over a 2-output transaction.
// Actual serialized size exceeds the vbytes used for needed_fee by the OP_RETURN's ~90 bytes,
// so st.transaction() pays ~90 sat * fee_per_vbyte less than requested.
```
Verified statically: `tx_outs` gains the OP_RETURN at `send.rs:194-202` while `calculate_weight_vbytes` at `send.rs:204,225` is invoked with only `payments`, and its internal builder (`send.rs:85-98`) never models the data output. I did not fully trace how the coordinator/processor feeds `data` into `SignableTransaction::new` (out of the indexed scope shown), so the exact production caller is unverified, but the arithmetic defect is self-contained in the in-scope file.
