### Title
Stale line-index reuse in `DiffSelection`/`formatPatch` can silently stage/commit content the user never selected - ([File: app/src/lib/patch-formatter.ts])

### Summary
The Weiroll report's core flaw is an unvalidated numeric index used to write into a shared array, where the index is trusted to still refer to the same logical slot it referred to when it was computed. GitHub Desktop has a structurally similar pattern: `DiffSelection` stores user line selections as *bare absolute line-number keys* (a `Set<number>`), and `formatPatch`/`formatPatchToDiscardChanges` re-derive `absoluteIndex = hunk.unifiedDiffStart + lineIndex` from a **freshly parsed diff** and blindly look that number up in `selection.isSelected(absoluteIndex)` with no check that the diff structure (hunks/line count/content) is still the same one the selection was computed against. [1](#0-0) [2](#0-1) 

### Finding Description
`DiffSelection` is an "efficient, storage object for tracking selections of indexable lines" that has "no notion of how many lines exists or what it is that is being selected" — it only knows integer line indices. [3](#0-2) 

The UI computes this selection against one `IRawDiff` produced by `DiffParser.parse()`, where each line's absolute index is `linesConsumed` accumulated hunk-by-hunk purely from the previously parsed hunk's `lines.length`: [4](#0-3) 

Later, when the file is actually staged, `applyPatchToIndex` re-fetches the diff independently via `getWorkingDirectoryDiff` and feeds the **same, previously-captured** `file.selection` object into `formatPatch` against this **newly parsed** diff: [5](#0-4) 

`formatPatch` then re-derives `absoluteIndex` from the new diff and looks it up in the old selection with no validation that the new diff's hunk/line layout (and thus its index-to-content mapping) matches the one the selection was built from: [2](#0-1) 

This is exactly the Weiroll pattern: an index computed at time T0 is trusted, without re-validation, to still address the same logical element at time T1. In Weiroll, `idx & IDX_VALUE_MASK` could point past `state.length` after the array changed; here, `absoluteIndex` can point to a completely different line (different hunk boundaries, different `DiffLineType`, different content) if the working-directory file changes between the two diff computations — for instance via a `.gitattributes` clean/smudge filter, a `post-checkout`/`pre-commit` hook, or any other repository-controlled mechanism that runs automatically on `git diff`/`git add`/`git status` and rewrites file content non-deterministically. None of these mechanisms require local/physical access or prior malware — they are properties of a cloned/fetched repository that Desktop trusts to invoke transparently.

### Impact Explanation
If the diff structure shifts between the moment the user makes their line selection (interactive diff view) and the moment `applyPatchToIndex`/`discardChangesFromSelection` re-parses the diff to build the actual patch, the reused integer indices can silently resolve to different lines than the ones the user visually selected. Because `formatPatch` unconditionally trusts `file.selection.isSelected(absoluteIndex)` for whatever hunk/line the new diff produces at that index, this can cause Desktop to stage or discard lines the user never chose — a silent corruption of what is committed/pushed, without any error or warning to the user. This matches the "silent corruption of what the user commits or pushes" impact category directly.

### Likelihood Explanation
The likelihood depends on an attacker-controlled repository being able to change working tree content between the two diff computations (e.g., via clean/smudge filters or git hooks defined in the repo's `.gitattributes`/`.git/hooks` after clone). Desktop does invoke `git diff`/`git status` multiple times over the lifecycle of a single "stage & commit" operation, so the window exists, but exploiting it reliably requires the repository-provided filter/hook to fire non-deterministically or based on external state, which is a real but somewhat narrower attack surface than a straightforward in-process bug. I was not able to find in the indexed code any explicit re-validation (e.g., comparing `maxLineNumber`, a diff hash, or hunk headers) between selection-capture time and patch-generation time to rule this out, but I also could not fully trace every UI call site that constructs `file.selection` to confirm whether some higher-level guard exists elsewhere (e.g., a diff diffing check before staging) that the index scope did not surface.

### Recommendation
Bind `DiffSelection` to the diff it was computed against — e.g., by tagging the selection (or the `WorkingDirectoryFileChange`) with a content hash or hunk-header fingerprint of the source diff, and having `formatPatch`/`applyPatchToIndex` verify that the freshly fetched diff matches the fingerprint before trusting `absoluteIndex` lookups. If the diff has changed, Desktop should refuse to apply the stale selection and force the user to re-review/re-select, analogous to Enso's Weiroll fix of validating `idx & IDX_VALUE_MASK < state.length` before ever using the index.

### Proof of Concept
Conceptual (not verified end-to-end from the index alone, since it requires runtime git hook/filter behavior):
1. Clone a malicious repository that defines a `.gitattributes` clean/smudge filter (or a `post-checkout`/`pre-commit` hook) which rewrites a tracked file's content deterministically on each `git diff`/`git status` invocation, changing the number/size of hunks.
2. In Desktop, open the file's diff, and select specific lines to include in the commit (e.g., only an "Add" line at absolute index 12).
3. Trigger the filter/hook to fire again (e.g., by any git operation Desktop performs internally between diff-render and staging), altering hunk boundaries so that absolute index 12 now maps to a different, unrelated line.
4. Commit the partial change; observe (via `git show`/`git log -p`) that the staged/committed content differs from what was visually selected in the Desktop UI, i.e., unintended lines were staged/committed. [6](#0-5)

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}
