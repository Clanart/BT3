### Title
Attacker-controlled `.gitmodules` URL enables local file read / SSRF-style trust bypass via `protocol.file.allow=always` on submodule checkout — ([File: app/src/lib/git/submodule.ts])

### Summary
This is a plausible Desktop analog of the Frax report's core pattern — an attacker-controlled, unvalidated value being fed directly into a security-relevant decision. In the smart-contract report, `calc_withdraw_one_coin`'s manipulable spot price is trusted for a collateralization decision. In Desktop, `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` conditionally injects `-c protocol.file.allow=always` into `git submodule update --init --recursive` based on a boolean `allowFileProtocol` flag, without inspecting the actual submodule URL(s) declared in the attacker-controlled `.gitmodules` file of a cloned/fetched/checked-out repository. [1](#0-0) 

### Finding Description
`.gitmodules` is committed content — fully controlled by whoever authored the repository/branch/PR a user clones, fetches, or checks out in Desktop. When Desktop performs a checkout (`checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts`) with `allowFileProtocol = true`, it calls `updateSubmodulesAfterOperation`, which unconditionally appends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation: [2](#0-1) 

This flag disables Git's default protections (added upstream after CVE-2017-1000117/CVE-2018-11235/CVE-2021-21300-class submodule attacks) around `file://` submodule URLs, meaning any submodule entry with a `file://` (or bare local path) URL in `.gitmodules` will be honored and cloned locally without restriction, as long as `allowFileProtocol` was set to `true` by the caller. Nowhere in `submodule.ts` is the actual submodule URL parsed or validated (e.g., checked to be `https/ssh` and pointed at the repository's own trusted remote) before this flag is applied — the decision to relax the protocol policy is based purely on a caller-supplied boolean, not on the content of the untrusted `.gitmodules` file that will actually be interpreted by Git.

This mirrors the Frax bug's broken invariant: a security-sensitive gate (`protocol.file.allow`) is decided from a coarse signal (a boolean flag from the calling code path) rather than validating the actual attacker-supplied data (`.gitmodules` submodule URLs) that will be consumed. If `file://` URLs (e.g., `file:///home/victim/.ssh` or a UNC path) are allowed to be cloned as a "submodule," a malicious repository can direct Git to copy/hardlink arbitrary local files under paths that Desktop will then display/manage as part of the repository's working directory, which the user might subsequently commit, view, or share — a form of local file disclosure/exfiltration mediated entirely by content in the repository, not by any local/admin/physical access from the attacker.

### Impact Explanation
If an attacker can get a victim to check out a branch/PR/clone that reaches this code path with `allowFileProtocol = true`, and Desktop does not otherwise sandbox or validate the resulting submodule URL scheme against an allow-list tied to the repository's real remote, the victim's Desktop process (running with the user's own file-system permissions) can be induced to read files outside the intended repository directory (e.g., SSH keys, config files) into the working tree as a "submodule" clone. This could lead to data exfiltration if the victim later pushes/shares that submodule content, and represents "silent corruption of what the user commits" if the malicious submodule reference ends up staged.

### Likelihood Explanation
Likelihood depends on exactly which call sites set `allowFileProtocol = true` for arbitrary/untrusted branches (e.g., checking out a PR branch from an unknown fork) versus only for locally-created submodules under the user's own control. I was not able to fully trace every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` with `allowFileProtocol = true` before running out of tool iterations, so I cannot confirm whether this flag is ever set to `true` when checking out attacker-supplied (fork/PR) branches versus only for trusted, locally-authored test/demo repositories. This is the key uncertainty that determines whether this is exploitable end-to-end or is dead code reachable only in already-trusted contexts.

### Recommendation
- Before ever passing `protocol.file.allow=always`, parse `.gitmodules` submodule URLs and reject/ignore any `file://` or path-like URL that does not match the repository's own trusted remote origin.
- Prefer never allowing `file://` submodule protocol for repositories obtained from a network remote (clone/fetch/PR checkout); scope any "allow file protocol" override strictly to test/first-party tooling paths, not user-facing checkout flows for arbitrary/untrusted repositories.
- Add regression tests asserting that checking out a branch containing a `.gitmodules` file with a `file://` URL pointing outside the repository (e.g., to the user's home directory) is rejected or sandboxed even when `allowFileProtocol` is set.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm call sites (tool budget exhausted). Conceptual repro:
1. Attacker publishes a repository/branch with `.gitmodules` containing a submodule whose `url` is `file:///Users/victim/.ssh` (or a Windows UNC/local path).
2. Victim uses Desktop to check out that branch/PR through a code path that invokes `checkoutBranch`/`checkoutCommit` with `allowFileProtocol = true` (per `app/src/lib/git/checkout.ts`), which calls `updateSubmodulesAfterOperation` with `-c protocol.file.allow=always` (`app/src/lib/git/submodule.ts:45-51`).
3. Git clones the local `file://` path as a submodule into the working directory without further validation of the URL's origin.

This PoC requires confirming, via further code review, that a reachable/untrusted-branch checkout path in the Desktop UI actually sets `allowFileProtocol = true`; I could not confirm this within the available searches, so treat the above as a plausible-but-unconfirmed analog rather than a fully verified vulnerability.
