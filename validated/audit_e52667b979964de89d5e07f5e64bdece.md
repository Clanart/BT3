Based on my research, I found a genuine "dropped/threaded security-gating parameter" pattern in Desktop's submodule handling that is structurally analogous to the Llama bug (a value/flag that must be correctly forwarded through a call chain to preserve a protocol invariant).

### Title
`allowFileProtocol` flag re-enables `protocol.file.allow=always` for submodule updates on untrusted checkouts, permitting file:// submodule URLs - (File: app/src/lib/git/submodule.ts, app/src/lib/git/checkout.ts)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol: boolean` parameter that, when `true`, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This flag is threaded down from `checkoutBranch`/`checkoutCommit`, both of which default it to `false` but expose it as a caller-controlled parameter that is passed straight through to `updateSubmodulesAfterOperation` without any re-validation against the origin of the branch/commit being checked out [2](#0-1) [3](#0-2) .

`protocol.file.allow=always` is the exact Git config knob that was hardened after CVE-2022-39253, where a malicious repository's `.gitmodules` could declare a submodule URL of `file:///path/to/local/file`, causing `git submodule update` to "clone" arbitrary local files/directories into the submodule's working tree. Modern Git defaults `protocol.file.allow` to `user` (blocked for automated recursive clones) specifically to prevent this. Passing `allowFileProtocol=true` deliberately overrides that protection for that invocation.

### Finding Description
The broken invariant is: *content originating from an untrusted, attacker-controlled branch/commit (e.g., a fork branch checked out via "Checkout PR" or "Open in Desktop") must never be allowed to re-enable `protocol.file.allow=always`.* The flag exists in the codebase purely as an opt-in escape hatch (used elsewhere for legitimate local-fixture / same-machine submodules, as seen in test helpers using `protocol.file.allow=always` for local submodule test setup [4](#0-3) ), but `checkoutBranch`/`checkoutCommit` accept and forward it as a plain boolean parameter with no origin/trust check tying it to whether the branch being checked out came from a verified same-repo ref versus a PR from an unknown fork [5](#0-4) .

This mirrors the Llama bug's root cause: a parameter (`value` in Llama's case, `allowFileProtocol` here) is passed through several layers of function calls without the security-relevant part of that value being independently re-derived or checked at the point where it matters. In Llama, `value` was silently dropped, breaking the "action must have funds" invariant. In Desktop, `allowFileProtocol` is silently *forwarded as true* by any caller in the checkout call chain, breaking the "untrusted content cannot re-enable local file cloning" invariant.

Whether this is currently reachable end-to-end depends on which UI/dispatcher call sites pass `true` for `allowFileProtocol` when checking out PR branches or "Open in Desktop" branches (e.g., `dispatcher.ts`'s `checkoutBranch`/`openBranchNameFromUrl`/`openPullRequestFromUrl` flows shown earlier [6](#0-5) ). I was not able to fully trace every call site that supplies `allowFileProtocol=true` before running out of tool iterations, so I cannot confirm with certainty that an attacker-controlled fork/PR checkout currently reaches this code path with the flag set to `true`.

### Impact Explanation
If an untrusted checkout path (PR-from-fork checkout, "Open in Desktop" branch checkout, or any future caller) passes `allowFileProtocol=true`, an attacker who controls the target repository's `.gitmodules` could declare a submodule with a `file://` URL pointing at sensitive local paths (e.g., SSH keys, `.netrc`, cloud credential files) relative to the victim's filesystem. `git submodule update --init --recursive` would then copy that content into the submodule directory inside the cloned repository's working tree, which the victim could subsequently view, commit, or push — turning local file read into cross-boundary disclosure/exfiltration, consistent with the "valid impact" criteria (attacker-controlled repository content → file read outside the repo / silent corruption of what gets committed).

### Likelihood Explanation
Medium-to-low confidence without confirming the exact call sites that set `allowFileProtocol=true`. The mechanism itself (config override reachable via a boolean parameter threaded through `checkoutBranch → updateSubmodulesAfterOperation`) is confirmed and unguarded by any trust check on the branch's origin. The remaining uncertainty is purely about which callers currently pass `true`, which I could not fully enumerate in the time available.

### Recommendation
- Never allow `allowFileProtocol=true` to be used for checkouts originating from branches/commits associated with a fork or any repository the user does not own/control.
- Tie the flag to a verified trust signal (e.g., only allow it for local, same-origin submodule test/dev flows) rather than passing a bare boolean through the public `checkoutBranch`/`checkoutCommit` API.
- Add a regression test asserting that PR/fork checkout flows never invoke `updateSubmodulesAfterOperation` with `allowFileProtocol=true`.

### Proof of Concept
Conceptual (not fully verified against a live call site due to incomplete trace of dispatcher call sites):
1. Attacker crafts a public GitHub repository with a branch containing a `.gitmodules` entry: `url = file:///Users/victim/.ssh`.
2. Victim uses a Desktop flow that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` for that branch.
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, copying `~/.ssh` into the submodule path inside the checked-out repo.
4. Victim's working tree now contains the exfiltrated files, which can be viewed/committed/pushed by Desktop.

Because I could not confirm the exact caller passing `true` for untrusted content within the remaining tool budget, I present this with the above caveat rather than full certainty. If a Devin agent needs to verify further, it should grep `checkoutBranch(` and `checkoutCommit(` call sites across `app/src/ui/dispatcher/dispatcher.ts` and `app/src/lib/stores/app-store.ts` for any invocation passing a literal `true` in the `allowFileProtocol` position, especially in PR-checkout or "Open in Desktop" code paths.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
