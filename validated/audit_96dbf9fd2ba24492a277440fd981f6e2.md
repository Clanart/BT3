## Analysis

The Vader report's core broken invariant is: **a shared reserve is accounted for at an aggregated/coarse granularity, while claims against it are settled per-leg/per-position — letting one party extract value belonging to another leg out of the same shared pot, when contributions/withdrawals across legs are asymmetric.**

The direct local analog is in the Intent Gateway's same-chain fill path. `IntentsBase._orders` escrows input tokens keyed only by `(commitment, token)` — **not per output leg/index** — even though an order can have multiple output legs (`order.output.assets[i]`) that are each paired with their own `order.inputs[i]`, and multiple legs can legitimately share the same input token address (e.g., a user funds two different output-asset legs from the same USDC balance).

### The bug

In `IntrinsicIntents._fillSameChain` (evm/src/apps/intentsv2/IntrinsicIntents.sol:116-121):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

When a specific output leg `i` becomes fully filled, the contract releases the **entire current balance** of `_orders[commitment][token]` for that token — not the proportional share belonging to leg `i`. Because `_orders` is keyed only by token address, this balance is the *sum* of escrow for every leg that shares that token, including legs that are still unfilled.

A solver can call `fillOrder` providing `options.outputs[i]` sufficient to fully complete only the cheap leg `i` while passing `0` for another leg `j` that shares the same input token. Leg `i`'s branch then reads `_orders[commitment][token]` **before** any decrement has happened for this call, pulling the full aggregate balance (covering both legs) as `escrowedInputs[i]`. `_withdraw` (evm/src/apps/intentsv2/IntentsBase.sol:390-410) then transfers that full amount to `msg.sender` (the solver) and zeroes the ledger entry, even though leg `j` was never filled and its rightful escrow share is gone. `isFullyFilled` stays `false` because leg `j` is untouched, so the order remains open but with `_orders[commitment][token] == 0`: leg `j` can never be filled by anyone (subsequent `_withdraw` hits `UnknownOrder`) and same-chain cancellation refunds nothing for that token to the user.

This requires no privileged role, prover, relayer, or malicious peer — any solver interacting with an ordinary multi-leg order that happens to share an input token across legs can trigger it in one transaction.

### Title
Escrow ledger keyed only by (commitment, token) lets a partial same-chain fill drain funds reserved for an unfilled sibling leg - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2`/`IntrinsicIntents` supports multi-leg orders where several output legs can be funded from the same escrowed input token. `_orders[commitment][token]` tracks escrow per token only, not per leg. `_fillSameChain`'s full-fill branch releases the *entire* remaining balance for that token whenever any one leg referencing it completes, letting a solver extract escrow that belongs to a sibling, still-unfilled leg.

### Finding Description [1](#0-0) 
computes `escrowedAmount` as the full `_orders[commitment][token]` balance whenever the current output leg's cumulative fill equals its `totalRequired`, instead of a proportional share tied to that leg's own input allocation. [2](#0-1)  shows the escrow ledger is keyed only by `(commitment, token)`, aggregating all legs that use the same input token. [3](#0-2)  (`_withdraw`) then unconditionally transfers whatever amount was computed and decrements the same shared counter, with no leg-level bookkeeping to prevent over-release.

A solver calling `fillOrder` for an order whose two (or more) output legs share an input token can pass a nonzero `options.outputs[i]` for the cheap leg and `0` for the other leg(s). The cheap leg completes, `amountFilled == totalRequired` triggers, and the *entire* current token balance — covering both legs — is paid to the solver, while the order stays open (`isFullyFilled = false`) because the sibling leg is untouched.

### Impact Explanation
The solver receives escrow value far in excess of what it delivered outputs for, at the expense of the order's user. The sibling leg becomes permanently unfillable (`UnknownOrder` on the zeroed escrow) and unrefundable via same-chain cancellation, since `_cancelSameChain` also reads the same drained `_orders[commitment][token]` balance. This is direct, unauthorized fund extraction from escrow and a loss/lock of the remaining user funds — matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
No privileged actor, relayer, or cross-chain proof is required — a single unprivileged `fillOrder` call on the source chain triggers it. The only precondition is an order whose output legs share an input token address, which is a normal, unremarkable order shape (e.g., paying for two different output assets out of the same USDC allocation) rather than an attacker-crafted edge case.

### Recommendation
Track escrow per output-leg index (or per `(commitment, outputToken)` rather than per raw input-token address), or compute the full-fill release as `order.inputs[i].amount - alreadySettledForThisLeg` instead of reading the aggregate `_orders[commitment][token]` balance. Alternatively, disallow/normalize orders whose legs share an input token so the aggregate-balance shortcut is always safe.

### Proof of Concept
1. User places a same-chain order with two output legs: leg A requires 100 tokenOut-A for 400 USDC input, leg B requires 100 tokenOut-B for 600 USDC input; both legs' `order.inputs[i].token == USDC`, so `_orders[commitment][USDC] = 1000`.
2. Solver calls `fillOrder` with `options.outputs = [100 tokenOut-A, 0]` — fully satisfying leg A, providing nothing for leg B.
3. In `_fillSameChain`, leg A's `amountFilled == totalRequired` branch executes: `escrowedAmount = _orders[commitment][USDC] = 1000` (full aggregate, not the 400 belonging to leg A).
4. `_withdraw` transfers 1000 USDC to the solver and sets `_orders[commitment][USDC] = 0`. `isFullyFilled` is `false` (leg B untouched), so the order stays "open" but leg B's escrow is gone.
5. Leg B can never be filled (any future `_withdraw` call on it hits `UnknownOrder` since `escrowed == 0`), and `_cancelSameChain` refunds 0 USDC for that token — the user's 600 USDC share for leg B is permanently lost to the solver's step-2 withdrawal.
