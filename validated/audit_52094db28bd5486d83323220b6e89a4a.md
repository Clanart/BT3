## Analysis

The Sherlock finding is a **boundary-check mismatch**: two logically related guards (`<` vs `>`) don't agree on the boundary value, leaving a gap where an in-range/edge-case input slips past validation. The equivalent bug class in GitHub Desktop is a **containment check that uses a bare string-prefix comparison instead of a path-segment boundary check**, which has the identical failure mode — an attacker-controlled value that merely shares a string prefix with the "safe" boundary slips through validation that was supposed to reject it.

### Title
Path-containment check in `resolveWithin()` uses a raw string prefix comparison, allowing sibling-directory escape via deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is Desktop's central guard used to ensure an attacker-influenced relative path cannot escape a trusted root directory. Its final check is:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` has no concept of path-segment boundaries, so `"/Users/victim/Documents/GitHub/repo-secrets"` legitimately "starts with" `"/Users/victim/Documents/GitHub/repo"`. This mirrors the report's bug class exactly: the check was written to gate a boundary (`resides within root`) but the comparison operator (string prefix) does not correctly encode that boundary, letting a value it should reject pass.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` resolves `pathSegments` against `rootPath`, then verifies containment by comparing the real (symlink-resolved) paths with `startsWith`, with no trailing-separator normalization on either side [2](#0-1) .

This function is invoked from `dispatcher.ts`'s `openRepositoryFromUrl`, which handles the `x-github-client://openrepo` deep link. The `filepath` query parameter is fully attacker-controlled (no traversal filtering — only `pr` and `branch` are validated in `parseAppURL`) [3](#0-2) . After cloning/opening the repository, Desktop resolves the attacker-supplied `filepath` against `repository.path` and, if `resolveWithin` returns non-null, reveals it in the OS file browser:

```ts
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
}
``` [4](#0-3) 

Because of the prefix bug, a `filepath` such as `../<reponame-with-shared-prefix>/secret.txt` resolves outside the repository directory yet still satisfies `realResolved.startsWith(realRoot)` whenever any sibling directory name shares the repo folder name as a prefix (e.g. cloning `foo` while a `foo-backup`, `foo.bak`, or `foobar` directory already exists next to it, which is common for repos users have forked/renamed/backed up locally). The intended invariant — "resolved path must be at or beneath the repository root" — is silently violated, exactly as `block.timestamp == order.expiry` silently violated the intended "settled XOR reclaimable" invariant in the report.

The other caller, `copilot-conflict-context.ts`'s `buildConflictContext`, relies on the same `resolveWithin` guard before reading file contents and forwarding them to the Copilot conflict-resolution model [5](#0-4) , so the same class of prefix bypass could, in principle, cause file content outside the intended file set to be read — though that path is less directly attacker-triggerable than the deep-link flow.

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openrepo?url=...&filepath=...` link can cause Desktop to resolve and act on a path outside the cloned repository whenever a sibling directory/file name happens to share the repo directory name as a string prefix. The immediate consequence via `shell.showItemInFolder` is disclosure/navigation to file-system locations outside the repository the user did not intend to expose, breaking the trust boundary the `resolveWithin` guard exists to enforce. This falls under "attacker controls ... a link or deep link the user clicks" and "file ... read outside the repo" per the Valid Impact scope.

### Likelihood Explanation
Exploitation requires only that the victim click a link (standard Desktop deep-link handling, no local access, no admin rights, no prior malware) and that a sibling path exists whose name is a superstring of the repository directory's name — a realistic scenario given common local naming patterns (`repo`, `repo-old`, `repo.bak`, `repo2`). No credential leakage or social engineering beyond a single click is required.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require a path-segment boundary, not just a string prefix, e.g.:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

### Proof of Concept
1. Victim has cloned a repo to `/Users/victim/Documents/GitHub/foo` and separately has an unrelated folder `/Users/victim/Documents/GitHub/foo-secrets` (or any name where `foo` is a prefix).
2. Attacker sends the victim a link: `x-github-client://openrepo/OWNER/foo?filepath=..%2Ffoo-secrets%2Fsensitive.txt`.
3. `parseAppURL` extracts `filepath = "../foo-secrets/sensitive.txt"` unfiltered [3](#0-2) .
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)` [6](#0-5) ; `resolve()` yields `/Users/victim/Documents/GitHub/foo-secrets/sensitive.txt`, and `realResolved.startsWith(realRoot)` (`realRoot = ".../foo"`) evaluates `true` due to the missing separator boundary [1](#0-0) .
5. Desktop calls `shell.showItemInFolder(resolved)`, revealing the out-of-repo file/folder to the attacker's chosen path — the exact "resides within root" invariant the function's docstring promises is broken.
