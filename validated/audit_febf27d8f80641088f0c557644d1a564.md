### Title
Panic on unregistered recipient index in PedPoP blame path crashes the node - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2021-2038 (unauthenticated-reachable denial of service against a server component), `Decryption::decrypt_with_proof` performs an unchecked `HashMap` index on the `decryptor` participant index when evaluating a blame proof. `BlameMachine::blame` / `AdditionalBlameMachine::blame` pass a caller/network-supplied `recipient` straight into this indexing operation with no bounds check against the DKG's participant set, so a blame accusation naming an out-of-range recipient panics the process instead of returning an error.

### Finding Description
`Decryption::register` only inserts keys for participants that were actually registered (1..=n, populated in `SecretShareMachine::verify_r1` or `AdditionalBlameMachine::new`). In `decrypt_with_proof`, when a proof is supplied, the code evaluates `self.enc_keys[&decryptor]` — a `HashMap` index that panics on a missing key — before any validity check on `decryptor`:

- `crypto/dkg/pedpop/src/encryption.rs:381-390`: `proof.dleq.verify(&mut encryption_key_transcript(self.context), &[C::generator(), msg.key], &[self.enc_keys[&decryptor], *proof.key])` — the `enc_keys[&decryptor]` lookup panics if `decryptor` was never registered.
- `crypto/dkg/pedpop/src/lib.rs:575-609` (`blame_internal`) forwards the `recipient` argument to `decrypt_with_proof` without validating it against `self.params`/`self.commitments`.
- `crypto/dkg/pedpop/src/lib.rs:623-632` (`BlameMachine::blame`) and `crypto/dkg/pedpop/src/lib.rs:674-682` (`AdditionalBlameMachine::blame`) are public APIs taking `sender`, `recipient`, an `EncryptedMessage` (parsable by attackers via `EncryptedMessage::read`, in-scope untrusted bytes), and an optional `EncryptionKeyProof`. `AdditionalBlameMachine::blame` is explicitly usable by parties who were not DKG members, so the accusation's `recipient` value is attacker-influenced.
- To reach the panicking line, the attacker needs `proof: Some(_)` and a valid per-message PoP signature, which is trivially satisfiable: `msg.pop.verify` at `encryption.rs:374-379` is checked against `msg.key`, a public key whose scalar the attacker chose when constructing the `EncryptedMessage`.

A separate instance of the same pattern exists at `crypto/dkg/pedpop/src/lib.rs:599`, where `self.commitments[&sender]` panics on an out-of-range `sender` index — reachable only after a successful decrypt, but again with no participant-bounds validation in `blame_internal`.

### Impact Explanation
Any party able to submit a blame accusation (or any message routed into `blame`/`AdditionalBlameMachine::blame`) can deterministically panic the victim's process by naming a `recipient` participant index that isn't registered (e.g., `Participant(u16::MAX)`). In Rust this unwinds/aborts the executing task; in a validator/coordinator context that is a repeatable remote crash — the same availability impact class as CVE-2021-2038 (complete DoS via hang or frequently repeatable crash). No key material is required: the crash precedes DLEq verification.

### Likelihood Explanation
The trigger requires a valid-format `EncryptedMessage` with a correct PoP (attacker-constructible), `proof: Some(anything)`, and a `recipient` outside the registered set. Whether integrators validate participant indexes before calling `blame` is not enforced by the library — the API accepts any `Participant` and documents no precondition on `sender`/`recipient` range. `Participant::new` accepts all non-zero u16 values, so out-of-range values are representable. This is medium likelihood: it requires the deployment to route accusation-supplied indexes into `blame`, which is exactly the designed usage.

### Recommendation
Validate `sender` and `recipient` against the registered participant set in `blame_internal` before use (returning them as faulty or an explicit error), and replace `self.enc_keys[&decryptor]` / `self.commitments[&sender]` indexing with `.get()` lookups that return `DecryptionError`/identify the accusing party as faulty.

### Proof of Concept
```rust
// Setup: any honest DKG completing to a BlameMachine, or:
// let machine = AdditionalBlameMachine::<C>::new(context, n, commitment_msgs).unwrap();
// with n = 3 participants registered.

// Attacker constructs a well-formed EncryptedMessage with a valid PoP
// (they pick the encryption scalar, so msg.pop.verify passes), e.g. by
// reusing encrypt() output for their own key or hand-crafting one.

// Attacker submits a blame accusation claiming recipient = participant 9999
let bogus = Participant::new(9999).unwrap();
let blame_proof: Option<EncryptionKeyProof<C>> = Some(crafted_proof); // any parseable proof

// Inside blame_internal -> decrypt_with_proof:
//   proof.dleq.verify(..., &[self.enc_keys[&bogus], *proof.key])
//                                          ^^^^^^
//   HashMap index on missing key -> panic!("key not found")
machine.blame(sender, bogus, msg, blame_proof); // process crashes
```
No valid DLEq proof is needed: the panic occurs while evaluating the `enc_keys[&decryptor]` argument, before `dleq.verify` is invoked.
