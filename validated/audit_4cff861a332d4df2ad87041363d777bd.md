### Title
Unauthenticated `params[:shop]` triggers Shopify Admin API call using victim's stored offline access token - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
`ShopifyApp::EnsureInstalled#validate_non_embedded_session` resolves a shop's stored offline session purely from the attacker-controllable `params[:shop]` query parameter and, for any non-embedded request, uses that session to build a `ShopifyAPI::Clients::Rest::Admin` client and issue a live `GET shop` request. No verification of the requester's identity (cookie, session token, HMAC, or JWT) is performed before the victim's access token is used.

### Finding Description
The concern's flow is:

1. `check_shop_domain` only requires `params[:shop]` to be a syntactically valid domain via `ShopifyApp::Utils.sanitize_shop_domain` [1](#0-0) .
2. `check_shop_known` loads `@shop = installed_shop_session`, which is `SessionRepository.retrieve_shop_session_by_shopify_domain(current_shopify_domain)` — i.e., the victim's stored offline session, looked up solely by the attacker-supplied domain string [2](#0-1) .
3. `validate_non_embedded_session` returns early only `if loaded_directly_from_admin?`, which is `ShopifyApp.configuration.embedded_app? && params[:embedded] == "1"` — itself just another attacker-controlled param, so an attacker simply omits `embedded=1` to keep this false [3](#0-2) .
4. The method then executes `ShopifyAPI::Clients::Rest::Admin.new(session: installed_shop_session)` and calls `client.get(path: "shop")` using the victim's offline access token [4](#0-3) .

No before_action in this concern verifies a session token/JWT, HMAC, or cookie binding the request to the named shop — this is confirmed by the gem's own documentation, which explicitly warns: "This concern does not authenticate the request. The shop is resolved from the shop query string parameter, which is user-controllable. Do not use this concern to gate access to shop data, access tokens, or Shopify API calls" [5](#0-4) . Despite that warning to consumers, the concern's own internal implementation (`validate_non_embedded_session`) violates the exact same principle by making a real Admin API call with the victim's token based only on `params[:shop]`.

This is directly proven by the existing test suite, which stubs `SessionRepository.retrieve_shop_session_by_shopify_domain` to return an arbitrary session and asserts `ShopifyAPI::Clients::Rest::Admin.new` is called with that session using only `params[:shop]` [6](#0-5) .

### Impact Explanation
An unauthenticated attacker who knows (or guesses/enumerates) a victim's `*.myshopify.com` domain can force the app server to issue an authenticated Shopify Admin API request (`GET /admin/api/.../shop.json`) using the victim's offline access token, merely by hitting any controller action that includes `EnsureInstalled` with `?shop=victim.myshopify.com`. The response body is discarded and not shown to the attacker (it's only used to detect `401` and trigger re-auth), so this does not directly exfiltrate shop data to the attacker. The concrete impact is: (a) unauthorized/uncontrolled use of another tenant's credentials to call the Shopify API (consuming API rate limit, generating spurious API traffic attributable to the victim shop), and (b) a cross-tenant confused-deputy primitive — the app acts on behalf of a shop the requester does not control and presents no credential of their own. This matches Shopify's "cross-tenant data/action without authorization" impact class, though bounded in this specific path because the API response itself is not surfaced back to the attacker.

### Likelihood Explanation
Highly likely and trivially repeatable: the request requires no credentials, no HMAC, no JWT — just a `GET` to any route using `EnsureInstalled` with `?shop=<installed-shop>`. Preconditions are exactly as stated in the question (non-embedded request, victim already installed), which are satisfied by default (omitting `embedded=1`). This is deterministic and reproducible via the existing test harness.

### Recommendation
Do not resolve or use a shop's stored session/access token based solely on unauthenticated `params[:shop]`. Either remove the API validation call entirely from `EnsureInstalled` (matching its documented "installation check only, no API calls" contract), or require verified proof of the request's origin (signed session token, HMAC, or App Bridge context) before using `installed_shop_session` to construct any `ShopifyAPI::Clients::Rest::Admin` client.

### Proof of Concept
Existing repo test demonstrates the exact exploit primitive:
```ruby
# test/controllers/concerns/ensure_installed_test.rb
test "returns :ok if the shop is installed" do
  session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain).returns(session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: session).returns(client)
  client.expects(:get)

  shopify_domain = "shop1.myshopify.com"

  get :index, params: { shop: shopify_domain }   # only attacker-controlled input

  assert_response :ok
end
``` [6](#0-5) 
This confirms `ShopifyAPI::Clients::Rest::Admin.new(session: session)` is invoked using only the value supplied in `params[:shop]`, with no other credential presented by the caller.

## EnsureInstalled — Installation Check Only
Use this concern to verify that the app has been installed on a given shop. It is designed for unauthenticated entry points in embedded apps, such as serving the app shell or redirecting to OAuth.

> ⚠️ **This concern does not authenticate the request.** The shop is resolved from the `shop` query string parameter, which is user-controllable. Do not use this concern to gate access to shop data, access tokens, or Shopify API calls. For authenticated actions, use `EnsureHasSession`.
