### Title
`ThresholdKeys` deserialization accepts semantically invalid parameters — verification shares are never checked against the secret share or for identity - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the AeraVault constructor accepting unvalidated deployment parameters (`manager_`, `validator_`, `noticePeriod_`), `ThresholdKeys::new` — and therefore the untrusted-byte entry point `ThresholdKeys::read` — validates only the *shape* of its parameters (counts and participant index bounds) while never validating their *semantics*: it accepts any `verification_shares` map, derives `group_key` from the attacker-controlled points, and never checks that `C::generator() * secret_share == verification_shares[i]` or that the shares are non-identity. The result is a "successfully constructed" keys object whose group key bears no relation to the secret share it is supposed to represent — an inconsistency the FROST layer itself acknowledges can only be detected at signing time (`crypto/frost/src/sign.rs:492-494`: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys").

### Finding Description
`ThresholdKeys::new` performs only three checks: the count of `verification_shares` equals `n`, every participant index is `<= n`, and `Constant` interpolation is only used when `t == n` (`crypto/dkg/src/lib.rs:355-374`). It then computes the group key by interpolating the first `t` verification shares — fully attacker-controlled points in the deserialization path (`crypto/dkg/src/lib.rs:376-378`). `ThresholdKeys::read` reconstructs keys from untrusted bytes: it reads `t`, `n`, `i`, the interpolation variant, the `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:591-631`). Nowhere is consistency between the secret share and `verification_shares[i]` verified, and no share is rejected for being the identity or a torsion-adjacent point beyond what `read_G` enforces canonically.

A crafted serialized blob therefore produces `ThresholdKeys` where `group_key()` is an arbitrary group element — potentially a point with no known discrete log — while `original_secret_share()` is unrelated garbage. Downstream, `ThresholdView::view` interpolates these shares and adds offsets (`crypto/dkg/src/lib.rs:463-533`), and `AlgorithmSignatureMachine::complete` verifies each signature share against the injected `verification_shares` map (`crypto/frost/src/sign.rs:475-489`). Shares produced honestly from the stored `secret_share` will fail verification under the substituted verification shares, causing honest participants to be mis-blamed via `FrostError::InvalidShare`, or `complete` to hit the `InternalError` at `crypto/frost/src/sign.rs:494` that the code itself attributes to "deserializ[ing] a semantically invalid FrostKeys".

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` (storage restore, key transport, or any pipeline passing serialized keys) obtains a keys object that reports an attacker-chosen `group_key()`. In the bitcoin-serai flow, the scanner attributes outputs paying to `group_key()` as received funds; with a substituted group key for which no consistent threshold of secret shares exists, those funds are reported received but are not spendable — any signature produced aggregates under the *true* verification shares (or fails outright), never under the reported key. Alternatively, inconsistent shares cause deterministic signing failure with honest participants mis-identified as faulty, corrupting blame/slashing attribution. This mirrors the report's core issue: trusting constructor inputs that downstream logic silently assumes are coherent.

### Likelihood Explanation
Reachability requires an attacker-influenced serialized `ThresholdKeys` blob. `ThresholdKeys::read` is an explicitly exposed untrusted-input surface, and the format is self-describing (curve ID, `t/n/i`, interpolation tag, secret share, `n` points). The defect requires no collusion, no threshold compromise, and no protocol participation — just one crafted byte string. Impact caps at Medium: no secret material is leaked (the secret share is itself part of the input), but the integrity guarantees "valid deserialization ⇒ coherent keys" is broken, enabling unspendable-fund attribution and false blame.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), add semantic validation after the structural checks:
- Verify `C::generator() * *secret_share == verification_shares[&params.i()]`, rejecting keys whose own share doesn't match its public commitment.
- Reject identity verification shares (`share.is_identity()`), which would otherwise zero a participant's contribution to the interpolated group key.
- For `Interpolation::Constant(c)`, assert `c.len() == usize::from(params.n())` so `interpolation_factor` indexing (`crypto/dkg/src/lib.rs:228`) can never panic on a malformed vector.
- Consider additionally validating that `group_key()` is non-identity, since a sum of attacker-chosen shares can cancel to identity, collapsing the multisig to a publicly known key (zero secret).

//   verification_shares[2] = arbitrary point                   <- not checked
let keys = ThresholdKeys::<Ristretto>::read(&mut crafted.as_ref()).unwrap();
// Succeeds: only counts/index bounds are checked (lib.rs:355-365).
// keys.group_key() is now attacker-chosen, unrelated to original_secret_share().

// Signing: view interpolates injected shares; honest share fails verify_share,

Confidence is moderate on impact rather than existence: the missing validation is direct in the code, but whether a given deployment actually pipes attacker-controlled bytes into `ThresholdKeys::read` determines real-world reachability; on-disk key stores writable only by privileged operators would reduce this to defense-in-depth hardening.
