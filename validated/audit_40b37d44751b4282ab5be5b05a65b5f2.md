### Title
Untrusted `ThresholdKeys` serialization accepts identity/mismatched verification shares, yielding a publicly-signable group key - ([File: crypto/dkg/src/lib.rs])

### Summary
The analog of "deserialization of untrusted data" in Serai is the byte-level `Read` implementations used for key material. `ThresholdKeys::read` deserializes the secret share and `n` verification shares using `Ciphersuite::read_G`, which enforces canonical, torsion-free encodings but explicitly does *not* reject the identity point — unlike `Curve::read_G` in FROST, which does. `ThresholdKeys::new` then computes the group key purely as the interpolated sum of the attacker-controlled verification shares for participants `1..=t`, without checking that the secret share matches its verification share, and without rejecting an identity result.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) reads `t`, `n`, `i`, an interpolation blob, a secret share via `C::read_F`, and then `n` verification shares via `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:620-623`). `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) only checks decode + canonicality; identity is a perfectly canonical encoding and passes. The identity check lives only in `Curve::read_G` (`crypto/frost/src/curve/mod.rs:123-131`), which is not used here.

Inside `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:347-390`), the only checks are share-count/`n` bounds and the Constant-interpolation `t == n` restriction. It then derives `group_key` as the interpolation-weighted sum of `verification_shares[1..=t]` (`crypto/dkg/src/lib.rs:376-378`). There is no check that `G * secret_share == verification_shares[i]`, no consistency check among shares, and no identity rejection on the shares or the resulting group key.

Consequently, fully attacker-controlled bytes can be deserialized into a `ThresholdKeys` whose `original_group_key()` / `group_key()` (`crypto/dkg/src/lib.rs:434-447`) is the identity element (or an arbitrary attacker-chosen point with known discrete log, by picking consistent shares), while the embedded `secret_share` is anything the attacker likes.

### Impact Explanation
- If all of `verification_shares[1..=t]` are identity, `group_key` is identity. A Schnorr signature under public key `A = 0` verifies `sG == R + cA` for the trivially-known private key `x = 0`: anyone can produce valid signatures for this "threshold key". Any funds/outputs controlled by that group key are spendable by anyone — i.e., the validator reports/uses a group key it does not exclusively control.
- Alternatively, the attacker sets verification shares consistent with a secret they know, producing a valid-looking `ThresholdKeys` where the victim's local `secret_share` is a decoy. The victim then produces signature shares that fail verification (availability loss), or — worse — the derived group key corresponds to a key the attacker alone controls, so funds deposited to it are unspendable by the honest set.
- This reaches production only if serialized `ThresholdKeys` (backup/recovery/handoff material) is treated as untrusted input — precisely the `ThresholdKeys::read` surface called out as reachable.

### Likelihood Explanation
The deserialization path accepts all crafted bytes without error: canonical identity points decode cleanly, `Participant::new`/`ThresholdParams::new` bounds checks pass for normal `t/n/i`, and the `interpolation` byte `0`/`1` are both accepted. The gap is purely the missing post-deserialization consistency/identity validation. Exploitation requires the attacker to supply or corrupt the serialized key material, which is a realistic precondition for restore/recovery flows but not for in-protocol DKG messages (PedPoP/`EncryptedMessage` have their own checks).

### Recommendation
In `ThresholdKeys::new` (or in `ThresholdKeys::read`), after computing `group_key`:
1. Reject identity verification shares and an identity `group_key` (mirror `Curve::read_G` semantics, e.g., `is_identity()` check).
2. Verify `C::generator() * secret_share == verification_shares[&params.i()]` so the embedded share is consistent with the public shares.
3. Optionally verify the verification shares lie on a degree-`t-1` polynomial (pairwise interpolation consistency over `1..=n`) so `group_key` is independent of which `t` shares are used.

### Proof of Concept
Conceptual, for any ciphersuite `C` with 32-byte points (e.g., `Ed25519`):

```rust
// t = 1, n = 1, i = 1, Lagrange interpolation
let mut bytes = vec![];
bytes.extend(&(C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(&1u16.to_le_bytes()); // t
bytes.extend(&1u16.to_le_bytes()); // n
bytes.extend(&1u16.to_le_bytes()); // i
bytes.push(1);                     // Interpolation::Lagrange
bytes.extend(C::F::ONE.to_repr().as_ref());            // arbitrary secret_share
bytes.extend(C::G::identity().to_bytes().as_ref());    // identity verification share

let keys = ThresholdKeys::<C>::read(&mut bytes.as_slice()).unwrap();
assert!(bool::from(keys.original_group_key().is_identity()));
// group_key() == identity ⇒ discrete log 0 is public ⇒ signatures forgeable by anyone
```

`read` succeeds because `Ciphersuite::read_G` never rejects identity, and `ThresholdKeys::new` never validates the secret share or the resulting group key. The crafted bytes differ only in that every point is the canonical identity encoding — no malformed encoding is required.
