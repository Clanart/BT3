### Title
Attacker can permanently freeze MGP reward accrual in WomUp by spamming the permissionless `getReward()` call to force `rewardPerToken()` increments to round to zero - ([File: wombat/WomUp.sol])

### Summary
`WomUp` distributes MGP rewards to WOM/mWOM stakers using a Synthetix-style linear-rate accumulator, `rewardPerToken()`, computed as `timeDelta * rewardRate * 1e18 / totalSupply()` [1](#0-0) . Because `getReward()` is callable by *any* address with no funds or stake required, and it unconditionally advances `lastUpdateTime` to `block.timestamp` via the `updateReward` modifier [2](#0-1) [3](#0-2) , an attacker can call it every block to keep `timeDelta` (and thus the reward increment) truncated to zero via integer division, exactly mirroring the reported Surge bug class where `timeDelta * rate / duration` rounds to zero under frequent small updates.

### Finding Description
`rewardRate` is fixed once at `initializeRewards()` as `rewardsAvailable / duration` (a 7‑day duration) and can never be re-set afterward (`initializeRewards` reverts if `rewardRate > 0`) [4](#0-3) . The accrual formula is:

```
rewardPerToken() = rewardPerTokenStored + (lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / totalSupply()
``` [1](#0-0) 

`getReward()` is a fully public function that any wallet can call at zero cost (no stake, no tokens required) — if the caller has no pending reward, `rewards[msg.sender]` is simply `0` and nothing is transferred, but the `updateReward` modifier still executes and sets `lastUpdateTime = lastTimeRewardApplicable()` (i.e., `block.timestamp`) [3](#0-2) .

If `totalSupply()` (total staked WOM/mWOM, which can easily be a large 18-decimal number as TVL grows) is large enough relative to `rewardRate`, and the caller invokes `getReward()` every block (or very frequently), `timeDelta` stays small enough that `timeDelta * rewardRate * 1e18 / totalSupply()` truncates to `0` on every call. Since `rewardPerTokenStored` is only ever updated by adding this (always-zero) increment, and `lastUpdateTime` is continually reset forward, the accumulated reward index for the entire 7-day distribution period can be permanently prevented from advancing. Because `rewardRate`/the reward campaign cannot be reinitialized, this freezes the entire MGP reward distribution for all WOM/mWOM stakers in this contract for the whole `duration`.

This is the direct analog of the M-3 Surge bug: an unprivileged actor griefing a linear rate accumulator via high-frequency, low-cost calls that force the per-period `timeDelta * rate / denominator` term to always round to zero, stalling the mechanism indefinitely.

### Impact Explanation
All WOM/mWOM stakers who rely on `WomUp` to earn MGP rewards lose their yield for the duration of the campaign (up to 7 days, satisfying the 24h+ freeze bar), since the reward index never advances while the attack is sustained, and the reward configuration (`rewardRate`) cannot be corrected/re-initialized once set. This constitutes theft/permanent freezing of unclaimed yield belonging to depositors.

### Likelihood Explanation
`getReward()` is unauthenticated, requires no token balance, no approval, and no capital outlay beyond gas [3](#0-2) . An attacker only needs to submit a transaction every block (trivial and cheap, especially on L2 deployments with short block times) to sustain the freeze for the entire reward period. The precondition (`rewardRate * 1e18 < totalSupply()` per block-time window) is realistic for any pool with meaningful TVL and a modest reward budget spread over 7 days.

### Recommendation
Avoid resetting `lastUpdateTime` fully to `block.timestamp` when the computed increment rounds to zero, or track/accumulate the reward increment with higher internal precision (e.g., scale `rewardRate` up before division and only truncate at final read time) so that repeated small-`timeDelta` calls cannot cause permanent loss of the fractional accrual. Alternatively, restrict how frequently `lastUpdateTime` can be advanced, or require a minimum elapsed time before committing an update.

### Proof of Concept
1. Owner calls `initializeRewards()`, setting `rewardRate = rewardsAvailable / 7 days`.
2. Multiple users stake WOM via `stake()`, growing `totalSupply()` to a size where `rewardRate * 1e18 / totalSupply()` is less than `1` per second.
3. Attacker (any wallet, no stake required) calls `getReward()` in every block for the duration of the campaign.
4. Each call: `timeDelta` (block time, e.g. 1–12s) is multiplied by `rewardRate * 1e18` and divided by `totalSupply()`, truncating to `0` in Solidity integer division; `rewardPerTokenStored` never increases, while `lastUpdateTime` keeps advancing to the current block.
5. At `periodFinish`, `rewardPerTokenStored` remains at (or near) its initial value, so `earned()` for all real stakers returns approximately zero — the entire MGP reward budget is stranded/unclaimable via normal accrual for that campaign.

    function initializeRewards() external onlyOwner returns (bool) {
        if(rewardRate > 0) revert MustZero();

        uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
        if(rewardsAvailable == 0) revert MustNotZero();

        rewardRate = rewardsAvailable / (duration);

        lastUpdateTime = block.timestamp;
        periodFinish = block.timestamp + (duration);
