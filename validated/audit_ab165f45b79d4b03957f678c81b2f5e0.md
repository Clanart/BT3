### Title
Path-containment check in `resolveWithin` uses prefix `startsWith` without a path-boundary check, allowing writes to sibling directories - (File: `app/src/lib/path.ts`)

### Summary
The shared path-containment helper `_resolveWithin` (backing `resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) validates that a resolved path is "inside" a root directory using `realResolved.startsWith(realRoot)` with no trailing separator normalization. [1](#0-0) 
This is the classic "prefix without boundary" containment bug: a sibling directory whose name simply begins with the same characters as the repository root (e.g. `repo-evil` next to `repo`) will satisfy `startsWith(realRoot)` even though it is not a descendant of the root. This mirrors the report's underlying bug class — a numeric/precision guard ("is this value proportionally inside range X") that looks correct but silently fails at the boundary, letting an out-of-range value slip through undetected.

### Finding Description
`_resolveWithin` is meant to guarantee that a caller-supplied relative path can never escape a given root directory — it is the app's core defense against path traversal when combining a trusted root with an untrusted relative path. [2](#0-1) 
It correctly blocks `..`-only segments and null bytes, and it resolves symlinks via `realpath` before comparing. [3](#0-2) 
However, the final containment test is a bare string-prefix comparison:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [4](#0-3) 
Because `realRoot` has no trailing path separator appended before the comparison, any resolved path whose string representation begins with the exact characters of `realRoot` — but is actually a different, sibling entry on disk — passes the check. For example, if `rootPath` resolves to `/Users/victim/Documents/GitHub/repo`, a resolved candidate of `/Users/victim/Documents/GitHub/repo-secrets/token.txt` (produced by joining a `../repo-secrets/token.txt`-style relative segment) also `startsWith` `/Users/victim/Documents/GitHub/repo` and is treated as "inside" the repository, when it is not.

This helper is consumed by `_applyCopilotConflictResolutions` in `app-store.ts`, which uses it to gate where AI-generated (Copilot) merge-conflict resolution content is written to disk: [5](#0-4) 
followed by an unguarded `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. [6](#0-5) 
`resolveWithin` is also used in `copilot-conflict-context.ts` and `dispatcher.ts` for similar containment checks; I was not able to fully inspect all call sites within this pass to determine whether the untrusted path components reaching those call sites are string-constrained against the sibling-prefix collision described above.

### Impact Explanation
If any code path allows an attacker-influenced relative path segment (e.g., a repository/file name or model-echoed path) that resolves to a sibling of the repository root sharing a name prefix, the `startsWith` check silently reports "contained" for a location outside the repository. Combined with a write sink like the Copilot conflict-resolution writer, this could result in file writes outside the intended repository tree — corrupting unrelated project files or, depending on directory layout, sensitive sibling paths — without any user-visible warning, since the guard is expected to (and believed to) prevent exactly this.

### Likelihood Explanation
For the specific call site I examined (`_applyCopilotConflictResolutions`), the resolution `path` values are pre-validated against a set of `expectedPaths` derived from the actual conflicted files in the working directory before this check runs, [7](#0-6) 
which likely constrains `resolution.path` to real repository-relative paths and reduces (but does not by itself eliminate, since the underlying helper is still flawed) exploitability at this specific call site. Because `resolveWithin` is a shared, generically-named containment primitive used at multiple call sites (`copilot-conflict-context.ts`, `dispatcher.ts`) whose upstream input validation I could not fully verify in this pass, the flawed boundary check is a latent, reusable weakness rather than a confirmed end-to-end exploit through a specific attacker-controlled entry point.

### Recommendation
Change the containment comparison in `app/src/lib/path.ts` to require a path-separator boundary, e.g.:
```ts
const rootWithSep = realRoot.endsWith(Path.sep) ? realRoot : realRoot + Path.sep
return realResolved === realRoot || realResolved.startsWith(rootWithSep) ? resolved : null
```
Apply the equivalent fix to the POSIX/Win32 variants (using the appropriate `sep`), and add regression tests asserting that a sibling directory sharing a name prefix with the root (e.g. `repo` vs `repo-evil`) is correctly rejected.

### Proof of Concept
Unit-test-level PoC against `resolveWithin` (add to `app/test/unit/path-test.ts` style):
```ts
// realRoot = /tmp/victim/repo
// candidate segment resolves to /tmp/victim/repo-evil/token.txt
const result = await resolveWithin('/tmp/victim/repo', '../repo-evil/token.txt')
// Expected: null (outside root)
// Actual: '/tmp/victim/repo-evil/token.txt' (passes, because
// '/tmp/victim/repo-evil/token.txt'.startsWith('/tmp/victim/repo') === true)
```
I was unable to execute this test in this pass to confirm runtime behavior (e.g., exact `realpath`/normalization interplay on the target OS); this should be validated with an actual filesystem fixture (create `/tmp/victim/repo` and `/tmp/victim/repo-evil`, then call `resolveWithin`) before treating it as fully confirmed at every call site.
