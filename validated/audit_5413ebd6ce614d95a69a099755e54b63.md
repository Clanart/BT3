### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows a crafted PlotNFT/singleton memo to crash wallet sync via uncaught `RecursionError` - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` reconstructs a custody tree from an attacker-supplied CLVM memo blob, recursing once per `MofN` nesting level with no depth or size limit. The only call site that consumes on-chain data, `PlotNFT.get_next_from_coin_spend()`, catches `ValueError` but not `RecursionError`, so a maliciously deep memo triggers an unhandled exception in wallet sync.

### Finding Description
`PuzzleWithRestrictions.from_memo()` parses the `further_branching_prog` field of a memo and, if set, recursively parses each member's memo via `MofNHint.from_program()` and a list comprehension calling `PuzzleWithRestrictions.from_memo(memo)` for every member [1](#0-0) . Nothing in this function bounds the nesting depth of `further_branching_prog`/`MofNHint.member_memos`, so the recursion depth is entirely attacker-controlled by the shape of the memo blob attached to a `CREATE_COIN` output.

This memo is consumed in production by `PlotNFT.get_next_from_coin_spend()`, which is the only path reading `PuzzleWithRestrictions.from_memo()` from on-chain data: it takes `singleton_create_coin.memo_blob.rest()` from a spent singleton's `CREATE_COIN` condition and passes it directly to `from_memo()`, wrapping the call in a `try/except ValueError` only [2](#0-1) . Python's `RecursionError` (a subclass of `RuntimeError`, not `ValueError`) is not caught here.

`get_next_from_coin_spend()` is invoked from `PlotNFT2Wallet.identify()` during normal wallet-sync processing of any coin whose puzzle uncurries to the plot-NFT singleton mod [3](#0-2) , which in turn is called unconditionally from `WalletStateManager.determine_coin_type()` for every synced coin matching that singleton mod hash [4](#0-3) . Because singleton puzzle-hash matching happens before ownership is verified, any spend of *any* singleton sharing the plot-NFT mod (not just coins the wallet owns) reaches this parser during sync.

An attacker can create such a coin spend (e.g., spend a plot-NFT-mod singleton, or otherwise get a matching coin confirmed/observed) with a `CREATE_COIN` memo encoding thousands of nested `MofN` levels. When any wallet syncs past that block (or receives the coin state from a peer), `from_memo()` recurses until Python's interpreter recursion limit is hit, raising an uncaught `RecursionError` that propagates out of `identify()`/`determine_coin_type()`/`_add_coin_state()`, halting wallet-sync transaction processing for that wallet.

### Impact Explanation
This matches the CVE-2022-21253 bug class: a reachable, attacker-influenced input path causes a "hang or frequently repeatable crash" rather than data corruption. Here the analog is a spend-triggered processing halt on the wallet-sync path — an unhandled `RecursionError` propagating out of `_add_coin_state()` can crash or repeatedly fail the wallet's coin-state ingestion loop for any wallet that observes the crafted spend, effectively a denial of service against wallet sync/transaction processing triggered by a single crafted spend.

### Likelihood Explanation
Medium. The attacker needs only to get one singleton coin spend confirmed (or otherwise relayed to victim wallets) whose puzzle mod matches the plot-NFT singleton mod and whose `CREATE_COIN` memo encodes deep `MofN` nesting; no privileged access, signature forging, or consensus rule violation is required, and the recursive parsing runs before any ownership check. The `pragma: no cover` and narrow `except ValueError` in the surrounding code suggest this failure path was not considered during development.

### Recommendation
Bound recursion depth (and/or total memo size/branching factor) in `PuzzleWithRestrictions.from_memo()` before recursing into `MofNHint.member_memos`, raising a `ValueError`-derived error on excess depth. Additionally, widen the exception handling in `PlotNFT.get_next_from_coin_spend()` to catch `RecursionError`/`Exception` around the `from_memo()` call so malformed memos degrade to `GetNextPlotNFTError` instead of crashing the sync loop.

### Proof of Concept
1. Construct a `Program` memo tree with the `CHIP-0043` namespace where `further_branching_prog` is non-nil at every level, nesting `MofNHint(m=1, member_memos=[...])` several thousand levels deep (well past Python's default recursion limit, e.g. 5,000+ levels), terminating in a minimal `MemberHint`.
2. Attach this memo as the second element of a `CREATE_COIN` condition's memo list in the solution of a coin spend whose puzzle reveal uncurries to `PlotNFT.singleton_puzzles.singleton_mod` (the plot-NFT singleton mod).
3. Get this spend confirmed on-chain (or relayed to a victim wallet's `WalletStateManager` via `_add_coin_state`), causing the wallet to call `WalletStateManager.determine_coin_type()` → `PlotNFT2Wallet.identify()` → `PlotNFT.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo()`.
4. Observe that `from_memo()`'s recursive call for each `MofN` member overflows Python's recursion limit, raising `RecursionError`, which is not caught by `except ValueError` in `get_next_from_coin_spend()` and propagates out of the wallet-sync coin-state handling code.
