### Title
mWOMSVBaseRewarder._calExpireForfeit hardcodes zero forfeiture, permanently diverting yield from locked mWomSV stakers to unlocking/cooling-down stakers - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries the mWomSV lock/cooldown state and always sets `rewardableAmount = _amount`, so `forfeitAmount` is unconditionally `0`. This is in stark contrast to the sibling `vlMGPBaseRewarder._calExpireForfeit`, which computes `rewardableAmount` from `vlMGP.getRewardablePercentWAD(_account)` — a function that does exist on `mWomSV` (`wombat/mWomSV.sol`) but is never wired into `mWOMSVBaseRewarder` because `ILocker` only exposes `lockFor`.

### Finding Description
`getReward`/`getRewards` in `mWOMSVBaseRewarder.sol` are gated by `onlyMasterMagpie` and `updateReward(_account)`, which calls `_updateFor` to snapshot `userRewards` at the current `balanceOf` before `_sendReward` computes forfeiture: [1](#0-0) 

`_sendReward` calls `_calExpireForfeit`, which in this contract is: [2](#0-1) 
`rewardableAmount` is set equal to `_amount` on line 386 and never adjusted by any lock/cooldown percentage, so `forfeitAmount = _amount - rewardableAmount` is always `0`.

Compare with the working analog, `vlMGPBaseRewarder._calExpireForfeit`, which fetches the actual rewardable percent from the locker contract based on lock/cooldown state: [3](#0-2) 

Critically, `mWomSV.sol` itself implements the equivalent function, `getRewardablePercentWAD`, which computes a reduced percentage for tokens in cooldown/unlocking based on elapsed cooldown time: [4](#0-3) 

However, `ILocker` (the interface type used for `mWOMSV` in `mWOMSVBaseRewarder`) only declares `lockFor`, not `getRewardablePercentWAD`: [5](#0-4) 

So the forfeiture logic for mWomSV rewards is structurally disconnected from the lock state — it is dead/no-op code, not merely "rarely triggered." No modifier, `nonReentrant` guard, or reward-index update mitigates this because the bug is in the forfeiture math itself, not in access control or reentrancy.

The premise in the question — that repeated same-block claims via a wrapper "yield no additional benefit since forfeiture is always 0" — is correct but understates the actual impact: this is not a frequency-independent non-issue, it is a permanent, single-call-sufficient bypass of the intended forfeiture mechanism for every mWomSV holder who enters `startUnlock`/cooldown, on every claim, indefinitely.

### Impact Explanation
Any user who calls `startUnlock` (moving part of their `mWomSV` into cooldown) is, by design intent mirrored from `vlMGPBaseRewarder`/`VLMGP`, supposed to forfeit a share of pending rewards proportional to time remaining in cooldown, with the forfeited amount redistributed via `_queueNewRewardsWithoutTransfer` to accounts that remain fully locked. Because `_calExpireForfeit` always returns `0` for mWomSV, unlocking/cooling-down users keep 100% of their accrued rewards instead of forfeiting the intended share, and the pool of continuously-locked stakers never receives the redistribution. This is a continuous misallocation of protocol yield among stakers — an "unclaimed yield theft/misallocation" class impact — that recurs on every reward epoch for every account with an active unlock/cooldown position, not a one-off issue.

### Likelihood Explanation
No special privileges are required: any holder of `mWOM` can `lock`, then `startUnlock` a portion, then claim through `MasterMagpie`'s public claim path (reaching `getReward`/`getRewards`) to realize full, unforfeit rewards while in cooldown. This is standard, expected user behavior (locking/unlocking is a core supported flow), so the bug triggers deterministically and repeatably for every user who uses `startUnlock`, with no capital requirements beyond normal staking amounts.

### Recommendation
Add `getRewardablePercentWAD` to `ILocker` (or a dedicated interface) and update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder`:
```solidity

    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
```

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` per existing test harness.
2. User A locks `X` mWomSV; wait for reward accrual (via `queueNewRewards`) so `earned(A, token) > 0`.
3. User A calls `startUnlock(X)` to move the full position into cooldown (rewardable percent should now be < 100% per `getRewardablePercentWAD`, since `endTime > block.timestamp`).
4. User A calls `MasterMagpie`'s public claim path (e.g., `multiclaim`) which reaches `mWOMSVBaseRewarder.getReward`.
5. Assert: `RewardPaid` amount equals the FULL `earned` amount pre-unlock (no reduction), and `ForfeitRewardAdded` is never emitted or is `0`, despite `getRewardablePercentWAD(A) < 1e18`.
6. Contrast: repeat identical steps against `vlMGPBaseRewarder`/`VLMGP` with an account in cooldown — assert `ForfeitRewardAdded` emits a non-zero amount and `RewardPaid` is strictly less than `earned` pre-claim, proving the sibling contract behaves as designed while `mWOMSVBaseRewarder` does not.

        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;

            forfeitAmount = 0;

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
