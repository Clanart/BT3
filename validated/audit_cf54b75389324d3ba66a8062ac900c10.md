### Title
Deterministic RNG seeded at init causes DLEq nonce reuse in blame proofs, leaking the DKG encryption key and enabling secret share recovery - (File: processor/src/key_gen.rs)

### Summary
The bug class in the external report is "random values fixed once at initialization and then reused on every call" (salt/IV bound as default arguments). In Serai, the RNG used to generate the PedPoP blame-proof randomness is derived deterministically from `entropy` — a secret set once in `KeyGen::new` — plus a public context string. If `calculate_share` is ever executed a second time for the same `KeyGenId` (which the code explicitly supports by rebuilding the machines from the DB), the same RNG stream is replayed, and `DLEqProof::prove` inside `Encryption::decrypt` reuses the same proof nonce for a *different* attacker-controlled message key. Classic nonce reuse across two Schnorr/DLEq proofs leaks the participant's static `enc_key`, which decrypts every secret share ever sent to that participant — a threshold secret-share recovery.

### Finding Description
`KeyGen` stores a fixed `entropy: Zeroizing<[u8; 32]>` created once at startup. All key-gen randomness is a pure function of that entropy and the public `KeyGenId`:

```rust
let rng = |label, id: KeyGenId| {
  let mut transcript = RecommendedTranscript::new(label);
  transcript.append_message(b"entropy", &self.entropy);
  transcript.append_message(b"context", context(&id, "rng"));
  ChaCha20Rng::from_seed(transcript.rng_seed(b"rng"))
};
let share_rng = |id| rng(b"Key Gen Share", id);
``` [1](#0-0) 

When a `CoordinatorMessage::Shares` arrives and the session's machines aren't in `active_share`, they are reconstructed deterministically and `calculate_share` is re-run with `share_rng(id)` — the identical RNG stream as the first attempt:

```rust
let (machines, our_shares) = self.active_share.remove(&id.session).unwrap_or_else(|| {
  let prior = key_gen_machines(id, params, share_quantity).0;
  let (machines, shares) =
    secret_share_machines(id, params, prior, CommitmentsDb::get(txn, &id).unwrap())
      .expect("got Shares for a key gen which faulted");
  (machines, shares)
});
let mut rng = share_rng(id);
``` [2](#0-1) 

`calculate_share` passes that rng into `Encryption::decrypt` for every participant's share, which produces a fresh `DLEqProof` per message using rng-drawn nonces:

```rust
let key = ecdh::<C>(&self.enc_key, msg.key);
cipher::<C>(self.context, &key).apply_keystream(msg.msg.as_mut().as_mut());
(msg.msg, EncryptionKeyProof {
  key,
  dleq: DLEqProof::prove(rng, &mut encryption_key_transcript(self.context),
    &[C::generator(), msg.key], &self.enc_key),
})
``` [3](#0-2) 

Because `encryption_key_transcript` commits only to `context` (same across retries), and the nonce comes from the replayed RNG, the second run produces DLEq proofs with the **same nonce `k`** but over a **different `msg.key`** supplied by the attacker in the new shares batch. Each proof yields `s = k − e·enc_key`; with `k` fixed and challenges `e₁ ≠ e₂` (the challenged generators differ via `msg.key`), the honest participant's static encryption key is recovered as `enc_key = (s₁ − s₂)/(e₂ − e₁)`.

### Impact Explanation
`enc_key` is the participant's ECDH private key for the DKG (`Encryption::new` generates it once per key-gen; the public half is registered by all counterparties). Anyone holding `enc_key` can compute `ecdh(enc_key, msg.key)` for every `EncryptedMessage` addressed to that participant and strip the ChaCha20 keystream (`cipher` uses a fixed IV `"DKG IV v0.2\0"`, safe only because the per-message key is unique — a leaked `enc_key` removes that protection). This reveals every secret share sent to the victim, yielding the victim's final `ThresholdKeys` secret share and contributing directly to threshold key/share recovery — the highest-severity impact class for this library. The attacker's lever is exactly the in-scope input path: untrusted bytes parsed by `EncryptedMessage::read` and fed to `calculate_share` across a repeated `Shares` message for the same `KeyGenId`.

### Likelihood Explanation
Reachability requires the same `KeyGenId`'s `Shares` handler to execute twice with attacker-modified share payloads. The code deliberately supports the rebuild path for fault recovery (`unwrap_or_else` reconstructs machines and re-executes `secret_share_machines`), so a crash, restart, or coordinator redelivery between the first and second handling triggers it. Whether the coordinator layer deduplicates `Shares` messages per `id` could not be confirmed within the indexed scope; if deduplication exists at the message layer, likelihood drops accordingly. Given the deterministic re-execution path exists, Medium–High likelihood; impact is share recovery, so overall severity is High if duplicate handling is reachable, Medium otherwise.

### Recommendation
Do not derive proof/blame randomness solely from a fixed `entropy || id` seed that is replayed on re-execution. Either:
- Mix in fresh `OsRng` entropy on each `calculate_share` invocation (the RNG is needed only for the DLEq proof and batch verifier weights), or
- Persist a monotonically increasing counter in `CommitmentsDb`/`KeyGenDb` per `KeyGenId` and fold it into `rng_seed`, guaranteeing a distinct RNG stream per execution even under retries.

Additionally, consider binding the message key into `encryption_key_transcript` (appending `msg.key` to the transcript inside `DLEqProof::prove` callers) so that even a replayed RNG cannot produce a valid second proof over a different statement.

### Proof of Concept
1. Attacker `A` participates in a key-gen session (a valid `KeyGenId` with honest participant `P`). `A` sends its commitments honestly so `CommitmentsDb` is populated.
2. `A` submits `CoordinatorMessage::Shares` for `id` containing an `EncryptedMessage` with ephemeral key `K₁` and an invalid share body, forcing `P`'s `calculate_share` to run `decrypt` and emit `EncryptionKeyProof { dleq: (s₁ over [G, K₁]) }` (blame path, `PedPoPError::InvalidShare { blame }`, returned via `ProcessorMessage::InvalidShare`).
3. `A` causes the same `id`'s `Shares` handler to run again (redelivery/restart rebuild via `CommitmentsDb`), this time sending `msg.key = K₂ ≠ K₁`. Because `share_rng(id)` is identical, `DLEqProof::prove` draws the same nonce `k`, producing `s₂ = k − e₂·enc_key`.
4. From `s₁, s₂` and the recomputed challenges `e₁, e₂` (the transcript is fully public: context + generator list), `A` solves `enc_key = (s₁ − s₂)·(e₂ − e₁)⁻¹`.
5. `A` computes `ecdh(enc_key, msg.key)` for every share message addressed to `P`, applies the fixed-IV ChaCha20 keystream, and recovers all of `P`'s received secret shares → `P`'s final secret share.

Key caveat: step 3 depends on the coordinator delivering a second `Shares` for the same `KeyGenId`; the rebuild fallback in `key_gen.rs:376-382` makes the honest node re-execute with identical randomness whenever that happens.
