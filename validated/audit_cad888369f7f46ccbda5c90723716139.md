### Title
Custom YAML frontmatter parser silently degrades `action: block` to a non-blocking warning when the value line contains a trailing comment or other formatting variants - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`extract_frontmatter` (lines 87-195) implements a hand-rolled line-based YAML parser instead of using a real YAML library. For top-level scalar keys it does: [1](#0-0) 

Specifically, `key, value = line.split(':', 1)` then `value = value.strip().strip('"').strip("'")`. There is no handling of inline YAML comments (`#`), so a line such as `action: block  # blocks dangerous rm -rf` yields `value == "block  # blocks dangerous rm -rf"` rather than `"block"`. That string is stored verbatim in the frontmatter dict.

`Rule.from_dict` simply copies this value through with `action=frontmatter.get('action', 'warn')` (line 81), with no validation that it is exactly `"block"` or `"warn"`.

Downstream, `RuleEngine.evaluate_rules` performs an exact string comparison: [2](#0-1) 

Because `rule.action` is `"block  # blocks dangerous rm -rf"` and not the literal string `"block"`, the rule is routed into `warning_rules` instead of `blocking_rules`. Per `evaluate_rules`, if only warning rules match, the operation is still allowed with just a `systemMessage`: [3](#0-2) 

The full call chain is `load_rules` → `load_rule_file` → `extract_frontmatter` → `Rule.from_dict` → `RuleEngine.evaluate_rules`, invoked from `pretooluse.py`'s `main()`, which never validates the resulting `action` value and always allows the tool call unless `blocking_rules` is non-empty. No allowlist, schema validation, or fail-closed check exists anywhere in this chain to catch a malformed/degraded `action` field.

The exploitable scenario is not that an attacker who already controls the rule file needs a trick to make it non-blocking (they could just write `action: warn`) — it's that this parser bug lets a maliciously modified rule *appear* unchanged to a code reviewer (the text `action: block` is still visibly present, just with an added trailing comment, extra indentation, or similar cosmetic change) while functionally becoming a no-op warning. This defeats the intended purpose of code review/diff inspection on security-relevant `.claude/hookify.*.local.md` files.

### Impact Explanation
A rule author or reviewer believes a rule with `action: block` is actively blocking dangerous `Bash`/`Write`/`Edit` operations (e.g., blocking `rm -rf`), but due to the parser's failure to strip inline comments (or due to indentation that causes the `action` key to be silently dropped entirely, defaulting to `"warn"` via `frontmatter.get('action', 'warn')`), the rule only emits a warning message and the dangerous tool call proceeds via `permissionDecision` never being set to `"deny"`. This is a fail-open trust-boundary bypass in the hook enforcement mechanism, allowing intended-to-be-blocked dangerous commands or file writes to execute.

### Likelihood Explanation
Preconditions are narrow but realistic: an attacker needs write access to add/modify a `.claude/hookify.*.local.md` file in a repository that will later be checked out and have `pretooluse.py` invoked against it (e.g., via a PR to a shared repo, or a maliciously crafted fork/clone containing a "security" rule file). Given that access, crafting the trailing-comment or indentation variant is trivial and deterministic — no race conditions or timing dependencies. The main barrier is that such a change might be caught by a careful line-by-line reviewer, but the visual similarity to a correct `action: block` line makes it a plausible review-evasion technique.

### Recommendation
Replace the hand-rolled parser with a proper YAML library (e.g., `yaml.safe_load`) for parsing frontmatter, or at minimum: (1) strip inline `#` comments from scalar values before quote-stripping, (2) validate `action` against an explicit allow-list (`{"warn", "block"}`) in `Rule.from_dict`, raising/logging an error and failing closed (treating ambiguous/invalid values as `"block"` or rejecting the rule) rather than silently defaulting to `"warn"`, and (3) add explicit handling for indentation variants so unexpected indentation of a top-level key raises a parse error instead of being silently dropped.

### Proof of Concept
Add a unit/fuzz test in the style of `plugins/hookify/core/config_loader.py`'s `__main__` block:

```python
import itertools
from hookify.core.config_loader import extract_frontmatter, Rule

variants = [
    "action: block",
    "action: block  # blocks rm -rf",
    "action: block ",
    "action:block",
    "action: \"block\" # comment",
    " action: block",  # leading-space indentation
]

for v in variants:
    content = f"---\nname: test\nenabled: true\nevent: bash\npattern: \"rm -rf\"\n{v}\n---\nmsg\n"
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    assert rule.action == "block", f"Degraded action for variant {v!r}: got {rule.action!r}"
```

Expected: the assertion fails for the trailing-comment and leading-indentation variants, demonstrating that `Rule.action` is not `"block"` and that `RuleEngine.evaluate_rules` (per [2](#0-1)  ) would route the rule to `warning_rules`, allowing the operation instead of denying it.
