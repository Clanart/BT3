### Title
Webhook shop attribution (`shop_domain`) is taken from an unauthenticated header, decoupled from the HMAC-verified body, enabling cross-shop webhook confusion - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates a webhook request's authenticity by checking the HMAC over the raw request body only, but the shop identity attached to the downstream job (`shop_domain`) is read from a separate, unsigned HTTP header. The verification (analogous to the `UnionToken` whitelist check) is performed on the wrong "entity" — the payload's integrity/secret possession — while the tenant attribution used to act on data (analogous to `from`, the true owner) is taken from an attacker-controllable header that is never cryptographically bound to the verified payload.

### Finding Description
`WebhookVerification#verify_request` computes the HMAC exclusively over `request.raw_post`: [1](#0-0) 

and separately exposes: [2](#0-1) 

`shop_domain` is read straight from `HTTP_X_SHOPIFY_SHOP_DOMAIN`, a header that is never included in the HMAC computation performed by `hmac_valid?`: [3](#0-2) 

The same disconnect exists in the default `WebhooksController` and in every generated webhook job template, all of which trust `shop`/`shop_domain` (sourced from `ShopifyAPI::Webhooks::Request`/`WebhookHandler.handle`, itself derived from the shop-domain header) as the tenant key for destructive or data-scoping operations, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the signature only authenticates the body and the shop attribution header sits outside that signed scope, anyone who possesses one legitimately-signed webhook body+HMAC pair (trivially true for the operator of their own installed shop, who receives real Shopify webhooks) can resend that exact body/HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` value. `hmac_valid?` still passes (it only checks the body against the shared secret), so `verify_request` accepts the request, and the app then attributes/acts on the payload for the attacker-chosen shop instead of the shop that actually produced it. This mirrors the `UnionToken` flaw exactly: the "whitelist"/authenticity check is anchored to the wrong identity (the body/secret, akin to `msg.sender`) instead of the identity the action is actually performed on behalf of (the shop domain, akin to `from`).

### Impact Explanation
Depending on which webhook job is targeted, this confused-deputy allows cross-shop data corruption, unauthorized deletion, or forged privacy-webhook triggers: e.g. `AppUninstalledJob` destroying a victim shop's record, or `ShopRedactJob`/customer-redact jobs running redaction against a shop that never actually uninstalled or requested redaction, purely because the attacker replayed their own valid HMAC with a relabeled shop-domain header. It is a cross-shop/tenant-confusion vulnerability triggered from an unrelated-merchant HTTP request, consistent with an accepted forged signed request.

### Likelihood Explanation
Any developer using the built-in `WebhooksController`, the `WebhookVerification` concern directly, or the generator-produced controllers/jobs is affected, since none of them bind the shop-domain header to the signed payload. An attacker only needs their own (non-privileged) app-installed shop to obtain one valid HMAC/body pair, then can freely swap the shop header on replay — no secret knowledge or privileged access is required beyond having any shop install the app.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or `Webhooks::Request#shop`) as the tenant/authorization key unless it is cryptographically bound to the verified payload. Bind the shop identity to the verification step itself — e.g., include the shop domain header in the HMAC-covered data, or verify the shop derived from the payload/webhook body against an out-of-band trusted mapping (installed session for that shop) rather than the raw header — before dispatching any job that mutates or discloses shop-scoped data.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate Shopify webhook (e.g. `app/uninstalled` or `shop/redact`) with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared secret.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks the body against the secret — it succeeds because the body/HMAC pair is genuinely valid.
4. `ShopifyAPI::Webhooks::Registry.process` (or the custom job, using `shop_domain`) is invoked with `shop_domain: "victim-shop.myshopify.com"`, causing e.g. `AppUninstalledJob`/`ShopRedactJob` to run destructive/redaction logic against the victim shop's records instead of the attacker's own shop.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
