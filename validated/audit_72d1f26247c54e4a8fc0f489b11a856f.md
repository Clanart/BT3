### Title
Empty `getRewards` implementation in `BaseRewardPool` silently drops user reward claims - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool.getRewards(address _account, address _receiver, address[] memory _rewardTokens)` is defined but its body is completely empty, so it neither reverts nor performs any reward transfer or accounting update [1](#0-0) . This is a stronger analog of the reported bug class ("unchecked/ignored failure that lets execution silently continue without performing the expected state change"), since here the entire operation is a silent no-op that the caller has no way to detect.

### Finding Description
`MasterMagpie._claimBaseRewarder` is the internal routine used by all user-facing claim/multiclaim flows to pull bonus rewards from a pool's `IBaseRewardPool`. When the caller supplies a non-empty `_rewardTokens` array (i.e. requests specific reward tokens rather than "claim all"), it calls `rewarder.getRewards(_account, _receiver, _rewardTokens)`: [2](#0-1) 

For pools that use the plain `BaseRewardPool` contract (as opposed to `BaseRewardPoolV2` or `mWOMSVBaseRewarder`, which do implement `getRewards` with real logic — see e.g. `_sendReward` calls in `mWOMSVBaseRewarder.sol` [3](#0-2) ), this call reaches the empty stub: [4](#0-3) 

Because the function has no `updateReward` modifier and no body, calling it:
1. Does not call `_updateFor(_account)`, so `userRewards`/`userRewardPerTokenPaid` are not refreshed.
2. Does not transfer any reward token to `_receiver`.
3. Does not revert, so the outer `multiclaim`/`multiclaimFor` transaction in `MasterMagpie` completes successfully as if the claim happened.

This is the same bug class as the referenced Allora `ResetChurnableTopics` finding: an operation whose failure/no-op is not surfaced, allowing the caller and the rest of the transaction to proceed under an incorrect assumption that the intended state change (reward distribution) occurred.

### Impact Explanation
Any ordinary wallet interacting with `MasterMagpie.multiclaim`/`multiclaimFor` and specifying explicit reward tokens for a pool backed by `BaseRewardPool` will have that leg of the transaction silently do nothing — no revert, no event, no transfer. From the emitted-events/tx-receipt perspective it looks like a successful claim, but the user's reward tokens are not paid out. Since `_updateFor` also isn't invoked, `userRewards`/`userRewardPerTokenPaid` bookkeeping for the affected tokens is not refreshed either, which can affect subsequent `earned()`/claim calculations for that account and reward token. This falls under "theft or permanent freezing of unclaimed yield" for users who rely on this call path.

### Likelihood Explanation
Reachable directly and unprivileged: any regular user calling `MasterMagpie`'s multiclaim entrypoints with a token-filtered claim against a pool whose rewarder is `BaseRewardPool` triggers this path deterministically, with no special preconditions besides having a nonzero `_rewardTokens` array. The only uncertainty is whether any currently-configured production pool actually uses `BaseRewardPool` (rather than `BaseRewardPoolV2`) as its rewarder — the codebase index does not show the live pool-to-rewarder wiring/deployment config, so this cannot be confirmed with full certainty from static analysis alone; `BaseRewardPool` is referenced in `MasterMagpie.sol`, `WombatStaking.sol`, and the pool helper contracts, indicating it is an actively integrated, non-dead contract type [2](#0-1) .

### Recommendation
Implement `getRewards` in `BaseRewardPool.sol` analogously to `BaseRewardPoolV2`/`mWOMSVBaseRewarder`: apply the `onlyMasterMagpie` and `updateRewards`/`updateReward` modifiers, iterate `_rewardTokens`, zero out `userRewards[rewardToken][_account]` for each and `safeTransfer` the pending amount to `_receiver`, emitting `RewardPaid`. Alternatively, if the token-filtered claim path is intentionally unsupported for this contract, make it explicitly revert (e.g. `revert NotImplemented()`), matching the recommendation pattern from the source report of never letting an unhandled/no-op path succeed silently.

### Proof of Concept
1. Deploy `MasterMagpie` with a pool whose `rewarder` is a `BaseRewardPool` instance (not `BaseRewardPoolV2`), and provision reward tokens via `queueNewRewards`.
2. A user stakes into the pool and accrues rewards over time as `userRewards[rewardToken][user]` in the rewarder.
3. User calls `MasterMagpie.multiclaimFor` (or `multiclaim`) with `_rewardTokens[i]` non-empty for that pool's index, per `_claimBaseRewarder`: [5](#0-4) 
4. Because `getRewards` in `BaseRewardPool.sol` is empty, the call returns successfully without reverting and without transferring any tokens: [1](#0-0) 
5. User's on-chain reward token balance is unchanged and `userRewards` state for that reward token is not cleared/updated, while the transaction shows as successful — the accrued reward is neither paid out nor safely preserved with correct downstream accounting for this call path.

        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

    /// @notice Harvest reward token in BaseRewarder for an account. NOTE: Baserewarder use user staking token balance as source to
    /// calculate reward token amount
    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
