### Title
Heuristic in `popStashEntry` can permanently delete an unrecoverable stash entry that was never actually applied - (File: `app/src/lib/git/stash.ts`)

### Summary
`popStashEntry` treats *any* `git stash pop` failure with exit code `1` and empty `stderr` as proof that the stash was "popped successfully but with conflicts," and unconditionally drops the underlying stash object via `dropDesktopStashEntry`. This mirrors the Swapnet pattern exactly: an operation that only partially (or not at all) applies its effect returns a result that is not faithfully communicated to the caller, and the caller destroys the source data believing the operation fully succeeded.

### Finding Description
`popStashEntry` runs `git stash pop --quiet <name>` and, on failure, applies this heuristic: [1](#0-0) 

```
if (
  e instanceof GitError &&
  e.result.exitCode === 1 &&
  e.result.stderr.length === 0
) {
  ...
  // bye bye
  return dropDesktopStashEntry(repository, stashSha)
}
return Promise.reject(e)
```

The comment itself acknowledges the fragility: *"popping a stashes that create conflicts in the working directory report an exit code of `1` and are not dropped after being applied... Not the greatest approach but stash isn't very communicative."*

This check only inspects `exitCode === 1` and `stderr.length === 0`. It never verifies that:
- the working directory actually received the stash's changes,
- conflict markers were written,
- the index reflects a merge in progress.

`git stash pop` internally runs `apply` then, only on success, `stash drop`. Git's own logic distinguishes "applied with conflicts" (drop deliberately skipped, changes present) from other failure modes that also exit non-zero with no textual `stderr` output (e.g., messages routed to `stdout`, or apply aborting before writing anything to the working tree). Desktop's heuristic collapses all of these into a single "assume applied" branch and calls `dropDesktopStashEntry`, which unconditionally removes the stash ref: [2](#0-1) 

Because `dropDesktopStashEntry` performs `git stash drop` without first confirming the stash's contents are present in the working tree/index, any failure path that satisfies `exitCode===1 && stderr==''` — but did *not* actually merge the stash's content — results in silent, permanent loss of the user's stashed changes. Unlike `git stash drop` run manually by a user (an explicit, intentional action), this drop is an automatic side effect of a heuristic guess.

This routine is reached from multiple flows, including automatic checkout branch-switching that stashes/pops behind the scenes without the user ever running `stash pop` directly: [3](#0-2) [4](#0-3) 

### Impact Explanation
If the "exit 1 / empty stderr" condition is ever produced by a genuine failure (not a resolvable merge conflict where content was actually merged), the user's stashed changes are deleted from `.git` with no way to recover them — the working directory will not reflect the stash contents, yet the stash entry that was the only remaining copy of that work has been dropped. This is silent, irreversible data loss of user work, directly analogous to the reported bug's core defect: an operation's true (partial/failed) outcome is not propagated to the caller, and the caller destroys state based on the wrong assumption about how much succeeded.

### Likelihood Explanation
The check is coarse (`exitCode===1 && stderr===''`) and is explicitly flagged in the code's own comment as an unreliable inference ("Not the greatest approach but stash isn't very communicative"). Git failure modes that produce non-zero exit with all diagnostic text on `stdout` (rather than `stderr`) are known to exist for stash/merge operations, and the exact set of conditions that satisfy this predicate without content actually being merged has not been enumerated or defended against in this code path — the developers' own comment shows they were aware the signal is ambiguous but chose to treat it as "success" rather than verifying the resulting repository state (e.g., checking for conflict markers/REBASE state via `getStatus`, as is done elsewhere in the codebase for cherry-pick/rebase). Because this path is exercised automatically during common "switch branch and bring my changes" flows (not just an explicit "pop stash" click), a user does not need to take any unusual action to hit it.

### Recommendation
Do not infer success from `exitCode`/`stderr` shape alone. After a `stash pop` failure, call `getStatus` (or equivalent) to confirm that the stash's changes are actually present (e.g., conflicted files exist, or the working tree diff matches the stash diff) before calling `dropDesktopStashEntry`. If verification is inconclusive, surface the raw error to the user and leave the stash entry intact rather than deleting it — mirroring the general fix pattern from the referenced report, where the truncated/actual amount processed must be explicitly returned and consulted before mutating account/receiver state.

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
