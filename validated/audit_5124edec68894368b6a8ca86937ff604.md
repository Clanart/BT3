## Title
Consensus-incentive rewards attribute all `StateMachineUpdated` events in a batch to the signer of the *first* message, letting an attacker steal rewards for consensus updates delivered by other messages in the same batch - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet_ismp::Pallet::execute` processes a `Vec<Message>` in one unsigned extrinsic call and hands the *entire* combined list of messages and the *entire* combined list of resulting events to `FeeHandler::on_executed` in a single call. [1](#0-0)  `pallet-consensus-incentives`'s implementation of `on_executed` derives the relayer to be rewarded from `messages.get(0)` only — the signer of the *first* message in the batch — and then rewards that single account for **every** `StateMachineUpdated` event produced anywhere in the batch, regardless of which `Message::Consensus` entry actually produced each event. [2](#0-1) 

### Finding Description
`execute()` in `pallet-ismp` accepts an arbitrary `Vec<Message>` supplied by whoever submits the extrinsic (unsigned), maps every message through `handle_incoming_message`, flattens all resulting events across the whole batch, and invokes the fee handler once with the full `messages_with_weights` vector and the full flattened `events` vector: [3](#0-2) 

`pallet-consensus-incentives::on_executed` only inspects `messages[0]` to recover the relayer's public key from the sr25519 signature carried on that single `ConsensusMessage`: [4](#0-3) 

It then collapses **all** `StateMachineUpdated` events in the entire batch (across every state machine, produced by every `Message::Consensus` entry in the batch, not just `messages[0]`) and pays the reward for every one of them to that single `relayer_account`: [5](#0-4) 

The per-state-machine collapsing logic (comment at lines 125-132) was added specifically to stop the same relayer from being paid multiple times for repeated events targeting the *same* chain within one batch, but it does not address the orthogonal problem: the batch can legitimately contain **multiple independent `Message::Consensus` messages for different state machines**, each carrying its own signer. Because the submission extrinsic itself is unsigned (`handle_unsigned`) and the `messages: Vec<Message>` ordering is fully attacker-controlled, an unprivileged party can:

1. Take one or more *already-valid* `ConsensusMessage`s that would independently update other state machines (these could be pulled from public transaction pools/observed proofs, no cooperation from another relayer required — the payload is public consensus data anyone can source, and re-verification only needs a valid `consensus_proof`).
2. Prepend their own trivially cheap `ConsensusMessage` (signed with their own key, updating any state machine, even a state machine with a tiny/negligible progressed height) as `messages[0]`.
3. Submit the whole batch as a single unsigned extrinsic.

`execute()` validates and applies every message (each is independently checked via `handle_incoming_message`/consensus-proof verification, so no fraudulent state acceptance is needed — this attacks the *reward attribution*, not proof validity). All resulting `StateMachineUpdated` events, including ones produced by the other (not-first) consensus messages, are then paid entirely to the attacker's account because `on_executed` only ever looks at `messages[0]`'s signer.

This directly mirrors the analog bug class in the external report: a value that should be computed/attributed **per unit of work** is instead derived from a **shared position in the batch** (there: `startGasPerOrder` recomputed relative to loop position; here: reward recipient fixed to `messages[0]`'s signer), causing later batch members' due compensation to be misallocated to an unrelated party.

### Impact Explanation
This is a direct fund-theft / wrong-beneficiary vulnerability against `pallet-consensus-incentives`'s treasury-funded relayer rewards: `T::Currency::transfer(&TreasuryAccount, &relayer_account, reward, ...)` and the accompanying reputation-asset mint are both misdirected to the attacker for work (consensus delivery) actually represented by other messages in the batch. [6](#0-5)  The attacker pays only the transaction cost of resubmitting already-valid consensus proofs (extremely cheap — this is not a race against a legitimate relayer's submission, since the pallet accepts any correctly-formed batch) and collects treasury rewards proportional to the full batch's progressed block height for *all* included state machines, not just their own. This matches the required impact class: "stealing or loss of funds" / "wrong beneficiary or amount" against the live reward pool.

### Likelihood Explanation
High. The only preconditions are: (a) the ability to submit an unsigned extrinsic containing a `Vec<Message>` (available to anyone), and (b) access to at least one other valid, still-payable `ConsensusMessage` for a state machine whose height has progressed since `LastRewardedHeight`. Consensus proofs are public data by design (the report itself notes "proofs... are freely provided by its connected chains"), so an attacker does not need a compromised relayer key or any privileged role — they simply need to observe/collect any pending valid consensus messages and repackage them behind their own trivial consensus message in one call.

### Recommendation
`on_executed` must attribute each `StateMachineUpdated` event's reward to the signer of the specific `Message::Consensus` that produced it, not to `messages[0]`'s signer. Concretely: iterate `messages`, and for each `Message::Consensus` entry, recover its own signer, then only aggregate/reward `StateMachineUpdated` events that can be attributed to that specific message (e.g. by processing consensus messages and their resulting events in lockstep rather than decoupling `messages` from the flattened `events` vector), instead of applying one globally-derived relayer account to the entire batch's event set.

### Proof of Concept
1. Relayer B broadcasts (or has already broadcast) a valid `Message::Consensus` proof `M_B` that will progress `StateMachineId::X` from height 100 to height 200 (a large, valuable reward span) and is publicly observable (e.g. via the mempool, tesseract's offchain proof storage, or previously failed/pending submission).
2. Attacker A crafts `M_A`, a trivially cheap valid `Message::Consensus` for `StateMachineId::Y` that only advances the height by 1 block (small cost, minimal own reward), signed with A's own key.
3. Attacker A submits `execute(vec![M_A, M_B])` via the unsigned `handle_unsigned` path.
4. `execute()` in `modules/pallets/ismp/src/impls.rs:40-78` processes both messages, producing two `StateMachineUpdated` events (for X and Y), and calls `T::FeeHandler::on_executed(messages_with_weights, events)` with the combined list.
5. `pallet-consensus-incentives::on_executed` (`modules/pallets/consensus-incentives/src/impls.rs:108-157`) reads `messages[0] == M_A`, recovers `relayer_account = A`, then iterates over **both** `StateMachineUpdated` events (X and Y) and calls `Self::process_message(..., A)` for each — crediting attacker A with the reward for the height-100-to-200 advance on chain X that B's proof actually delivered, in addition to A's own trivial reward on chain Y.
6. Relayer B, who produced and would normally claim the X reward, receives nothing; `LastRewardedHeight` for X is now advanced, so B cannot claim it later either.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {

				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()

				log::debug!(target: "ismp", "Handling Error {:#?}", err);

				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
