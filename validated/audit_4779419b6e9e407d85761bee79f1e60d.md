### Title
Symlink-based arbitrary file deletion in `GitStore.discardChanges` via untracked path from attacker-controlled repository - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` resolves the file path to delete/trash purely lexically with `Path.resolve(repository.path, file.path)`, using a path string taken directly from `git status` output. It never verifies, via `realpath`, that the resolved path actually stays inside the repository working directory, unlike other file-touching code paths in the app that use the `resolveWithin` helper.

### Finding Description
`file.path` values come from parsing `git status --porcelain=2 -z` in [1](#0-0)  and [2](#0-1) , which simply echoes whatever path exists as an untracked/modified entry in the working tree — this includes files reachable through a symlink that is itself part of the tracked/untracked working tree content (e.g., a symlink committed by, or introduced via, a cloned/fetched attacker repository, or created as part of an untracked entry under a symlinked directory).

In `discardChanges`, this untrusted `file.path` is joined with the repository root using a purely lexical `Path.resolve`, then handed to the OS-level shell/file APIs: [3](#0-2) 

`Path.resolve` does not consult the filesystem, so if any path segment (e.g. a directory component) is a symlink pointing outside the repository, the string `Path.resolve(repository.path, file.path)` is lexically "inside" the repo, but the OS calls made by `shell.moveItemToTrash` (Electron's `shell.trashItem`, invoked via IPC in `app/src/main-process/main.ts` at line 635, and `app-shell.ts`) and by `rm(Path.join(...))` will follow that symlink and operate on the real, attacker-chosen target outside the repository.

This is exactly the missing-restriction pattern from the original report: `reclaimErc721Tokens()` let the owner pass any `tokenAddress` including the protected `nftContract` itself, because there was no check confining the operand to a safe set. Here, `discardChanges` lets any working-directory path reachable from `git status` be used as a deletion/trash target, because there is no check confining the *resolved, real* path to the repository root — even though the codebase already has and uses exactly such a check (`resolveWithin` in `app/src/lib/path.ts`, which explicitly calls `realpath` and verifies containment) in other code paths like [4](#0-3) .

### Impact Explanation
An attacker who controls a cloned/fetched repository can plant a symlink in the working tree whose target points outside the repository (e.g., to a sibling directory, an SSH key, or another repository's `.git` folder). If that symlink (or a path nested through it) shows up as an untracked/new/modified entry in `git status`, and the victim uses Desktop's "Discard Changes" feature on it, Desktop will call `shell.moveItemToTrash` (or `rm` as a fallback) on the real target, deleting or moving to trash a file outside the intended repository — a controlled destructive file operation triggered purely by opening/interacting with an attacker-supplied repository.

### Likelihood Explanation
Discard Changes is a routine, everyday Desktop action (right-click a changed file → "Discard Changes", or discard-all). No unusual steps are required beyond the normal workflow of cloning/opening a repository containing the crafted symlink and discarding an entry that resolves through it. The codebase's own existence of `resolveWithin` for guarding exactly this class of symlink escape (used in the Copilot conflict-context reader) confirms this is a recognized risk category that `discardChanges` does not apply the same guard to.

### Recommendation
Before calling `shell.moveItemToTrash` or `rm` in `GitStore.discardChanges` (and `removeConflictedFile` in `app/src/lib/git/rm.ts`, and other file-touching paths driven by `file.path`), resolve the target with `resolveWithin(repository.path, file.path)` (already implemented in `app/src/lib/path.ts`) and refuse the operation (surfacing an error instead) if it returns `null`, mirroring the guard already applied in `app/src/lib/copilot-conflict-context.ts`.

### Proof of Concept
1. Attacker publishes a repository containing a symlink `evil -> ../../..` (or any path escaping the repo) as a tracked or otherwise-innocuous file, plus content such that a file under `evil/` appears as an **untracked**/new entry when the victim opens the repo (untracked files are trivially attacker-influenced since Desktop shows whatever exists in the working directory).
2. Victim clones/opens the repository in GitHub Desktop; Desktop's Changes view lists `evil/some-file` as untracked based on `git status` parsing in [2](#0-1) .
3. Victim selects "Discard Changes" on that entry (or "Discard All Changes"), invoking `Dispatcher._discardChanges` → `AppStore._discardChanges` → `GitStore.discardChanges`.
4. `GitStore.discardChanges` computes `Path.resolve(repository.path, 'evil/some-file')` and calls `shell.moveItemToTrash` on it: [5](#0-4)  — because `evil` is a symlink, the OS resolves this to a file outside the repository, which gets moved to trash/deleted without the victim intending to touch anything outside the cloned folder.
