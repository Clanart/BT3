## Finding: Discarding a renamed/copied file silently destroys a recreated file at the old path without moving it to the Trash

### Title
Discarding a renamed/copied file can permanently delete a recreated file at the old path without the promised Trash backup - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The underlying pattern in the Sherlock report is: a value that legitimately belongs to the user (`Pa`) is set aside "temporarily" by one code path, but a second code path that reconciles/cleans up state never accounts for it, so it is silently lost. `GitStore.discardChanges()` has the same structural flaw: it decides what to move to the Trash based on `file.path` only, but for `Copied`/`Renamed` files it also force-checks-out `file.status.oldPath` — a path that is never sent through the Trash step — and can therefore silently overwrite/destroy a file the user created there.

### Finding Description
`GitStore.discardChanges` in [1](#0-0)  iterates over the files to discard and:
1. Moves `file.path` to Trash (or deletes it if untracked) unless the file is `Deleted` or a submodule.
2. For `Copied`/`Renamed` files specifically, it additionally schedules `file.status.oldPath` for both reset and forced checkout: [2](#0-1) .

The Trash step above only ever operates on `file.path` — `oldPath` is never passed to `shell.moveItemToTrash` or `rm`. Yet `checkoutIndex`, invoked at the end of the function, force-overwrites every path in `necessaryPathsToCheckout` (which includes `oldPath`) using `git checkout-index -f -u`: [3](#0-2) .

This is exactly the scenario `stageFiles`' own comments describe as a normal, expected user workflow: a file is renamed (`foo -> bar`) and then a *new* file is created at the original path (`foo`) — an ordinary untracked/new file that Desktop reports separately: [4](#0-3) . If the user then discards the *rename* change (`bar`, with `oldPath: foo`) while that recreated `foo` exists on disk, `discardChanges` will:
- Trash `bar` (fine, backed up).
- Force `git checkout-index -f -u` on `foo`, silently clobbering the newly created `foo` file with the pre-rename index content, with **no Trash step ever having touched `foo`**.

The application's own documentation states the discard flow's entire safety guarantee is "move files to Trash... as a way to preserve changes, in case the user wishes to recover them later": [5](#0-4) . That guarantee is violated for this specific path.

### Impact Explanation
This causes silent, unrecoverable loss of uncommitted user work (the recreated file at the old path) with no confirmation, no Trash recovery option, and no error — the user is told changes were "discarded" (and can supposedly be "restored by retrieving them from the Trash," per `discard-changes-dialog.tsx`'s copy at [6](#0-5) ) but for this path that promise is false. This matches the "silent corruption of what the user commits" class: the file the user believed was safely trashed and recoverable is actually gone, and any future commit including that path will reflect stale content instead of what the user actually wrote.

### Likelihood Explanation
This requires only ordinary, unprivileged local Desktop usage (rename a tracked file, recreate a file at the old name, then discard the rename via the normal "Discard Changes" UI) — no attacker-controlled repository content, admin rights, or malware is needed to trigger the code path, though the report's "unprivileged" framing is best read here as: no special repo/API/remote content is required to hit the bug, it's inherent to the discard implementation whenever this common rename+recreate pattern occurs, so it will be hit by ordinary users during normal workflows without any need for unusual steps.

### Recommendation
In `GitStore.discardChanges`, when queueing `file.status.oldPath` for checkout, first check whether a file currently exists on disk at `oldPath` and, if so, route it through the same Trash/`rm` handling applied to `file.path` before calling `checkoutIndex`/`resetPaths` on it.

### Proof of Concept
1. Commit a file `foo`.
2. `git mv foo bar` (Desktop shows `bar` as Renamed, `oldPath: foo`).
3. Create a new file `foo` with new content (Desktop shows it as an additional untracked/new file).
4. In Desktop, select only the renamed `bar` entry and choose "Discard Changes."
5. Observe: `bar` is moved to the OS Trash (recoverable), but `foo` (the new file) is forcibly overwritten by `git checkout-index -f -u` with the old committed content of `foo` — with no Trash entry created for it, i.e., the new `foo` content is unrecoverably lost, contradicting the documented discard-changes guarantee.   public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
