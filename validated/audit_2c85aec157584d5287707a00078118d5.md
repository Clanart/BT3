### Title
Path-prefix boundary check in `resolveWithin` allows deep-link `filepath` parameter to escape the cloned repository into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`OmnichainGovernanceExecutor`'s bug is a guard that *looks* like it fully blocks an action but has a gap that lets the guarded state change go through anyway. `app/src/lib/path.ts`'s `resolveWithin` has the same shape of flaw: it is the sole gate used by the `x-github-client://openRepo/...?filepath=...` deep-link handler to keep the attacker-controlled `filepath` parameter confined to the cloned repository, but the containment check is a naive string `startsWith` comparison rather than a real path-boundary comparison, so a path that merely shares a common prefix with the repository directory (a sibling folder) passes the check.

### Finding Description
The deep-link handler `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` accepts a `filepath` value taken directly from an `x-github-client://` / `github-mac://openRepo/...` URL (fully attacker-controlled, since anyone can craft and distribute such a link): [1](#0-0) 

The only guard preventing the `filepath` from pointing outside the repository is `resolveWithin`, defined in `app/src/lib/path.ts`: [2](#0-1) 

The containment check is:
```
return realResolved.startsWith(realRoot) ? resolved : null
```
`startsWith` is a plain string comparison with no path-separator boundary check. If the repository lives at `/Users/alice/GitHub/project` and the attacker supplies `filepath=../project-secrets/id_rsa`, the resolved real path is `/Users/alice/GitHub/project-secrets/id_rsa`. That string *starts with* `/Users/alice/GitHub/project` even though `project-secrets` is a completely different, sibling directory. The check incorrectly treats this as "inside the repo" and lets it through to `shell.showItemInFolder(resolved)`.

This is the exact bug class described in the report: the "pause"/containment check exists and is invoked, but a boundary condition (here, requiring a path-separator or exact-equality after the prefix match) is missing, so the invariant "resolved path must be inside `rootPath`" is not actually enforced.

`isAbsolute(filepath)` is checked before `resolveWithin` is called, but that only blocks absolute paths — it does nothing to stop `../`-relative escapes that land in a same-prefixed sibling directory, which is precisely the case `resolveWithin` is supposed to catch and fails to.

### Impact Explanation
An attacker-controlled deep link (no local access, no prior compromise, just a link the victim clicks) can cause GitHub Desktop to reveal/open a file located outside the boundaries of the repository that was ostensibly the target of the link, as long as a directory sharing the repository's path as a string prefix exists on disk (e.g., `project-secrets`, `project.bak`, `project2`, `project` vs `project-old`). This is a directory-traversal / sandbox-escape of the exact type the report flags as valid ("read outside the repo"). The severity is bounded by the fact that `shell.showItemInFolder` only reveals the file's location in the OS file manager rather than exfiltrating its contents directly to the attacker, but it still discloses the existence/location of files outside the intended repo tree to whatever process/session receives focus, and the underlying containment primitive (`resolveWithin`) is reused elsewhere in the codebase (`app-store.ts`, `copilot-conflict-context.ts`) wherever repo-relative paths need to be safely resolved, so the same boundary defect could be more severely exploitable in those other call sites.

### Likelihood Explanation
Reachability is straightforward: `parseAppURL` in `app/src/lib/parse-app-url.ts` already parses and passes through the `filepath` query parameter with essentially no traversal filtering (only `branch` is checked with `testForInvalidChars`), and `openRepositoryFromUrl` calls `resolveWithin` unconditionally whenever `filepath` is present. The precondition (a same-prefixed sibling directory existing next to the cloned repo) is a real-world common pattern given how users tend to organize project folders (`myapp`, `myapp-old`, `myapp2`, `myapp.bak`), which raises likelihood above a purely theoretical edge case, though it is not universally guaranteed for every victim.

### Recommendation
Fix the containment check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a proper path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the appropriate separator for the `posix`/`win32` variants). Add a regression test asserting that a sibling directory sharing a path prefix (e.g. root `/a/b` vs. target `/a/b-evil/file`) is rejected.

### Proof of Concept
1. Victim has previously cloned a repository to `~/GitHub/project`.
2. Somewhere on disk (common in practice) there exists a sibling directory `~/GitHub/project-secrets` containing sensitive files (or the attacker can get the victim to have any similarly-prefixed folder, e.g. by naming their malicious/target repo `project` when the victim already has `project-old`).
3. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/attacker/project?filepath=../project-secrets/id_rsa`
4. `parseAppURL` (`app/src/lib/parse-app-url.ts`) parses this into `{ name: 'open-repository-from-url', url, filepath: '../project-secrets/id_rsa' }` with no traversal check on `filepath`.
5. `dispatcher.openRepositoryFromUrl` resolves/opens the repo at `~/GitHub/project`, then calls `resolveWithin('~/GitHub/project', '../project-secrets/id_rsa')`.
6. `_resolveWithin` normalizes/resolves to `~/GitHub/project-secrets/id_rsa`, `realpath`s both, and checks `realResolved.startsWith(realRoot)` — `~/GitHub/project-secrets/id_rsa`.startsWith(`~/GitHub/project`) is `true`, so the function returns the resolved path instead of `null`.
7. `shell.showItemInFolder(resolved)` is invoked on the out-of-repo file, revealing it to the user/OS shell despite the intended containment to the repository directory.
