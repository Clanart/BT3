I found a concrete, reachable analog to the report's bug class in `x/erc20`. Any user can permissionlessly register an arbitrary ERC20 contract (when `PermissionlessRegistration` is enabled) as a "native ERC20" token pair, and the module's `ConvertCoin`/`ConvertERC20` flow relies on a fixed, non-updatable address (`types.ModuleAddress`, the `erc20` module account) as the escrow holder for that ERC20 token, exactly like the immutable `STADIUM_ADDRESS` in the report.

### Title
Blacklisting of the fixed erc20 module escrow address by a malicious/compliant ERC20 permanently locks escrowed Coins - ([File: x/erc20/keeper/msg_server.go])

### Summary
`x/erc20` lets any ERC20 contract be registered as a "native ERC20" token pair [1](#0-0)  and, when `PermissionlessRegistration` is true, registration requires no privileged signer [2](#0-1) . `ConvertCoin`/`ConvertCoinNativeERC20` escrow native Coins by burning/holding them in the bank module and then attempt to move the corresponding ERC20 tokens FROM the fixed `types.ModuleAddress` TO the user via an EVM `transfer` call [3](#0-2) . If the registered ERC20 implements an admin-controlled blacklist/pause (as many real tokens, e.g. USDC-style tokens, do) and the token's controller blacklists `types.ModuleAddress`, this `transfer` call reverts permanently, mirroring the Sparkn `Distributor._commissionTransfer` finding where a hardcoded recipient (`STADIUM_ADDRESS`) getting blacklisted caused an unrecoverable revert.

### Finding Description
- Coins are first escrowed to the `erc20` module account via `SendCoinsFromAccountToModule` [4](#0-3) .
- The keeper then calls the ERC20 contract's `transfer` function with `types.ModuleAddress` (the erc20 module's EVM address) as the caller/sender [5](#0-4) .
- `types.ModuleAddress` is a fixed, hardcoded module account address (not configurable per-token, not upgradable per-pair) [6](#0-5) .
- The reverse flow (`convertERC20IntoCoinsForNativeToken`) similarly requires the user to `transfer` tokens INTO `types.ModuleAddress` to escrow them [7](#0-6) .
- Because token-pair registration for "native ERC20" tokens is permissionless (governed only by the `PermissionlessRegistration` param, not by admin vetting of the token's logic) [2](#0-1) , any user can register a compliant/pausable ERC20 (or a token that later becomes compliant/pausable via upgradeable proxy or governance) whose owner can later blacklist arbitrary addresses.
- Once `types.ModuleAddress` is blacklisted by the token's own access-control logic, `ConvertCoinNativeERC20`'s `transfer` call will always revert (`CallEVM` returns an error) [5](#0-4) , since the fixed sender address can never be replaced. Coins already escrowed via `SendCoinsFromAccountToModule` prior to blacklisting, or ERC20 tokens already escrowed under `types.ModuleAddress` via `convertERC20IntoCoinsForNativeToken`, become permanently unreachable — there's no code path that lets governance or any admin re-point the escrow to a different, non-blacklisted address, since the address is a hardcoded keeper constant used across the whole ERC20 module (not parameterized per pair).

### Impact Explanation
This matches "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances." ERC20 tokens escrowed under the erc20 module's fixed address, and/or native Coins already burned/escrowed pending an ERC20 unescrow, become permanently stuck once the token's issuer blacklists the module address — with no admin recovery path in the current code (the module address is not upgradable and is shared across all "native ERC20" token pairs, so this could even affect the escrow used by other, unrelated token pairs going forward, though the direct fund loss is scoped to the blacklisted pair's escrowed balances).

### Likelihood Explanation
Likelihood depends on: (1) permissionless registration being enabled and/or a malicious/compliant token being approved through governance registration, and (2) the token issuer/owner (a third party, not a Cosmos EVM validator or privileged Cosmos EVM role) later blacklisting the fixed escrow address. This requires an external, honest-appearing ERC20 contract to later exercise owner-controlled blacklist logic against the hardcoded module address — this is a normal, foreseeable behavior for any compliance-token (USDC/USDT-style) that a user or governance registers, not a contrived edge case. However, because it depends on interaction with an external ERC20's admin/owner (not an "honest external chain" but an external contract's compliance owner) rather than a fully unprivileged, purely on-chain trigger by an ordinary user, likelihood is moderate rather than trivially always exploitable.

### Recommendation
- Avoid a single hardcoded escrow address (`types.ModuleAddress`) as the exclusive holder/sender of externally-controlled ERC20 tokens. Consider per-pair escrow sub-accounts, or a governance-controlled ability to rotate/recover escrow for a specific token pair if the module address becomes blocked by the token's own access control.
- Add a governance-only, rate-limited "rescue" path (e.g., `MsgRescueEscrow`) that can move stuck ERC20/Coin balances for a specific pair to a new address, restoring 1:1 backing without granting arbitrary minting rights.
- Before permissionless registration, consider validating/flagging tokens that expose known "blacklist"/"pausable" patterns, or clearly document and restrict `PermissionlessRegistration` given this systemic risk, since one hardcoded address is shared by every native ERC20 pair.

### Proof of Concept
1. Enable `PermissionlessRegistration` (governance param) [8](#0-7) .
2. Deploy and register (`MsgRegisterERC20`) a compliant ERC20 contract that exposes an owner-only `blacklist(address)` function which causes `transfer`/`transferFrom` to revert for blacklisted addresses.
3. User calls `MsgConvertCoin` to convert Coins into the ERC20 token; `ConvertCoinNativeERC20` escrows Coins to the `erc20` module account and calls `transfer(receiver, amount)` from `types.ModuleAddress` [3](#0-2) ; also perform a `MsgConvertERC20` first so ERC20 tokens are already escrowed under `types.ModuleAddress` [7](#0-6) .
4. Token owner calls `blacklist(types.ModuleAddress)` on the ERC20 contract (an ordinary, expected admin action for a compliance token, external to Cosmos EVM).
5. Any subsequent `MsgConvertCoin` for this pair now permanently reverts inside `CallEVM(..., types.ModuleAddress, contract, true, nil, "transfer", receiver, amount)` [5](#0-4) , leaving both the escrowed Coins (backing the minted/burned accounting) and any previously escrowed ERC20 balance under `types.ModuleAddress` permanently unrecoverable, with no existing admin or governance instruction path to move or rescue them.

```go
// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
```

```go
// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}
```
