### Title
Operator Registration Is Permanent With No Admin Removal Path — Permanently Blocks All New Deposits If Any Registered Operator Goes Offline With Unspent Collateral - (File: `core/src/verifier.rs`, `core/src/database/operator.rs`)

### Summary

Once an operator is registered in a verifier's database via `set_operator()`, there is no mechanism — neither an admin RPC nor a database function — to remove that operator record. The verifier's deposit validation enforces that every operator stored in its DB with usable on-chain collateral must be present in every new deposit. If a registered operator goes permanently offline while their collateral UTXO remains unspent, all new deposits are permanently blocked across the entire bridge.

### Finding Description

**Registration is append-only.** `insert_operator_if_not_exists()` uses `ON CONFLICT (xonly_pk) DO NOTHING`, making every operator record permanent. A `grep` across the entire repository for `DELETE FROM operators` returns zero matches — there is no code path that removes an operator from the DB. [1](#0-0) 

**Deposit validation enforces a strict DB-vs-deposit-data consistency check.** During every `deposit_sign` call, `verifier.rs` iterates over every operator in its DB, runs `collateral_check` on each, and rejects the deposit if any DB-resident operator with usable collateral is absent from the aggregator-supplied deposit data: [2](#0-1) 

**The only exit mechanism requires the operator to act.** `collateral_check` returns `false` (allowing the operator to be excluded from deposits) only when the operator's collateral UTXO has been spent outside the protocol round-tx chain: [3](#0-2) 

If the operator is permanently offline, they cannot spend their collateral, so `collateral_check` keeps returning `true`, and the verifier keeps rejecting every new deposit.

**The codebase itself acknowledges this gap.** A test comment explicitly states:

> "remove an operator and try a deposit, it should fail because the operator is still in verifiers DB. To make it not fail, operator data needs to be removed from verifiers DB." [4](#0-3) 

The test's only workaround is to manually spend the operator's collateral — an action that requires the operator's private key and an online node.

### Impact Explanation

If any single registered operator becomes permanently unreachable (key loss, infrastructure failure, legal seizure) while their collateral UTXO remains unspent on Bitcoin:

- The aggregator cannot include that operator in deposit data (it cannot reach them).
- Every verifier rejects every new deposit because the operator is in the DB with usable collateral but absent from the deposit.
- **All new BTC deposits into the bridge are permanently blocked.** Existing deposits and withdrawals in flight are unaffected, but no new BTC can be bridged to Citrea.

This is a bridge liveness failure with material fund impact: users cannot peg in BTC, and the bridge is effectively frozen for new entrants.

### Likelihood Explanation

The scenario requires a registered operator to go permanently offline with unspent collateral. This is a realistic operational risk: hardware failure, key loss, regulatory action, or a deliberate griefing attack where an operator registers, locks collateral, and then goes dark. Because there is no admin override, the bridge has no recovery path short of waiting for the operator to voluntarily spend their collateral — which is impossible if they are offline.

### Recommendation

Add a privileged admin function (callable only by the security council or a governance multisig) that removes an operator from the verifier's DB when the operator's collateral has been provably spent outside the protocol or when a governance vote approves removal. At minimum, add a `DELETE FROM operators WHERE xonly_pk = $1` database function gated behind appropriate authorization, and expose it via a restricted gRPC endpoint. The removal should only be permitted when `collateral_check` returns `false` (collateral already spent) to prevent premature removal of active operators.

### Proof of Concept

1. Deploy the bridge with two operators (Op0, Op1) and one verifier.
2. Call `aggregator.setup()` — both operators are registered in the verifier's DB via `set_operator()`.
3. Confirm `get_operators()` returns both operators.
4. Take Op1 permanently offline (kill the process, discard keys). Op1's collateral UTXO remains unspent on Bitcoin.
5. Attempt `aggregator.new_deposit(...)`. The aggregator calls `fetch_operator_keys()`, which fails to reach Op1 and either errors or omits Op1 from the deposit data.
6. The verifier's `deposit_sign` handler calls `get_operators(None)` → finds Op1 in DB. Calls `collateral_check` for Op1 → returns `true` (collateral unspent). Checks `operators_in_deposit_data.contains(&op1_pk)` → `false`. Returns `BridgeError::InvalidDeposit`.
7. All subsequent deposit attempts produce the same error. The bridge is frozen for new deposits indefinitely.

The test at `core/src/test/deposit_and_withdraw_e2e.rs` lines 444–458 already demonstrates steps 4–6 and confirms the deposit fails, with the only documented recovery being to spend the operator's collateral — impossible if the operator is offline. [5](#0-4) [6](#0-5)

    pub async fn insert_operator_if_not_exists(
        &self,
        mut tx: Option<DatabaseTransaction<'_>>,
        xonly_pubkey: XOnlyPublicKey,
        wallet_address: &bitcoin::Address,
        collateral_funding_outpoint: OutPoint,
    ) -> Result<(), BridgeError> {
        let query = sqlx::query(
            "INSERT INTO operators (xonly_pk, wallet_reimburse_address, collateral_funding_outpoint)
             VALUES ($1, $2, $3)
             ON CONFLICT (xonly_pk) DO NOTHING",
        )
        .bind(XOnlyPublicKeyDB(xonly_pubkey))
        .bind(AddressDB(wallet_address.as_unchecked().clone()))
        .bind(OutPointDB(collateral_funding_outpoint));

        let result = execute_query_with_tx!(self.connection, tx.as_deref_mut(), query, execute)?;

        // If no rows were affected, data already exists - check if it matches
        if result.rows_affected() == 0 {
            let existing = self.get_operator(tx, xonly_pubkey).await?;
            if let Some(op) = existing {
                if op.reimburse_addr != *wallet_address
                    || op.collateral_funding_outpoint != collateral_funding_outpoint
                {
                    return Err(BridgeError::OperatorDataMismatch(xonly_pubkey));
                }
            }
        }

        Ok(())
    }

    pub async fn set_operator(
        &self,

        operator_xonly_pk: XOnlyPublicKey,
        wallet_reimburse_address: Address,
        operator_winternitz_public_keys: Vec<winternitz::PublicKey>,
        unspent_kickoff_sigs: Vec<Signature>,
    ) -> Result<(), BridgeError> {
        tracing::info!("Setting operator: {:?}", operator_xonly_pk);
        let operator_data = OperatorData {
            xonly_pk: operator_xonly_pk,
            collateral_funding_outpoint,
            reimburse_addr: wallet_reimburse_address,
        };

        let kickoff_wpks = KickoffWinternitzKeys::new(
            operator_winternitz_public_keys,
            self.config.protocol_paramset().num_kickoffs_per_round,
            self.config.protocol_paramset().num_round_txs,
        )?;

        if !self
            .rpc
            .collateral_check(
                &operator_data,
                &kickoff_wpks,
                self.config.protocol_paramset(),

            .await?
        {
            return Err(eyre::eyre!(
                "Collateral utxo of operator {:?} does not exist or is not usable in bitcoin, cannot set operator",
                operator_xonly_pk,
            )
            .into());
        }

        let tagged_sigs = self.verify_unspent_kickoff_sigs(
            collateral_funding_outpoint,
            operator_xonly_pk,
            operator_data.reimburse_addr.clone(),
            unspent_kickoff_sigs,
            &kickoff_wpks,
        )?;

        let operator_winternitz_public_keys = kickoff_wpks.get_all_keys();
        let mut dbtx = self.db.begin_transaction().await?;
