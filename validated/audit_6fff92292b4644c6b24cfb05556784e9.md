## Finding: Stale, position‑based diff selection can silently corrupt partial commits when the working file changes mid‑operation

The `Booster` bug is a classic "checked amount ≠ used amount" TOCTOU: an intervening state change between the initial read and the later action silently changes what gets processed. GitHub Desktop has a structurally identical pattern in its **partial-commit (line selection) staging path**.

### Root cause

When a user stages part of a file (via the "select lines to commit" UI), Desktop stores the selection as a **positional index set**, not as content: [1](#0-0) 

That selection is later replayed against a diff that is **re-fetched from disk at commit time**, independent of the diff the user actually looked at when making the selection: [2](#0-1) 

`formatPatch` then walks the *freshly fetched* diff's hunks and asks the *old* selection object whether each `absoluteIndex` (computed purely from `hunk.unifiedDiffStart + lineIndex`) is selected: [3](#0-2) 

The resulting synthetic patch is applied with `git apply --cached --unidiff-zero`, which relaxes git's normal context-line validation: [4](#0-3) 

This is the exact analog of the `Booster` bug: `_amount` (the diff/selection the user reviewed) is decoupled from `bal` (the diff actually consumed when the patch is built), and the intervening index-to-content mapping is never re-validated by content, only by index.

### Existing guard is insufficient

Desktop does try to reconcile stale selections when a diff reload happens, but only by *pruning indices that no longer exist* — it does not verify that a still-existing index still refers to the same logical line: [5](#0-4) 

The comment even acknowledges the risk ("The diff might have changed dramatically since last we loaded it") but the mitigation is purely existence-based, not content-based, so a shifted-but-still-valid index silently carries the old selection state onto different content.

### Attacker-controlled trigger

Desktop automatically executes repository-defined git hooks as part of routine, unprivileged operations it performs on a cloned/fetched repository (fetch/pull/merge/checkout), and explicitly wires up hook interception/plumbing for this: [6](#0-5) [7](#0-6) [8](#0-7) 

A hostile/compromised repository can ship a `post-merge`/`post-checkout` hook that rewrites a tracked file on disk as part of a routine pull/checkout the victim performs from Desktop. If the user has already opened the Changes view and picked specific lines to include/exclude (e.g., deliberately deselecting a suspicious line before committing) while this hook fires, the next diff recomputation used at commit time (`applyPatchToIndex`) can shift hunk boundaries/line indices. Because selection is purely positional, the deselected/selected status silently migrates onto different content — resulting in a commit (and possible subsequent push) that includes content the user explicitly chose to exclude, or vice versa, with no error or warning.

### Impact / Likelihood

This is a **silent corruption of what the user commits or pushes** — the class of impact explicitly called out as valid. Likelihood is moderate: it requires the victim to interact with a hostile repository (clone/pull/checkout, normal unprivileged workflow) and to be mid-way through a partial-commit selection when the hook-driven modification lands; large/complex diffs where users deliberately exclude specific lines (e.g., excluding a malicious snippet) are the highest-value target.

### Recommendation

- Store selections against diff content identity (e.g., hash of hunk/line content), not raw positional indices, and refuse/re-prompt when the diff used to build the patch differs from the diff the selection was made against.
- In `applyPatchToIndex` (`app/src/lib/git/apply.ts`), compare the diff fetched at commit time against the diff last shown to the user for that file; if they differ, force the user to re-review/re-select before staging.
- Avoid relying on `--unidiff-zero` to paper over structural mismatches; treat a hunk-shape mismatch as a hard failure rather than silently reapplying a stale selection. [9](#0-8)

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}
