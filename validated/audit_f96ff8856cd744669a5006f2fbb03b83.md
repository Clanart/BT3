### Title
Type-confusion "false-for-None" sentinel in `get_template_singleton_inner_puzzle()` can crash pool-wallet processing of a crafted p2_singleton/pool inner puzzle - (File: chia/pools/pool_puzzles.py)

### Summary
The iccDEV advisory describes a null-pointer dereference in `CIccTagLut16::Write()` that is reachable when a crafted, malformed profile causes an "expected-but-absent" value to be blindly dereferenced downstream. The equivalent bug class in chia-blockchain is a function that is supposed to signal "could not parse this data" with `None`, but instead returns the boolean `False` on the failure path, while its return type is annotated as `Program`. Every caller of that function treats the return value as if it were always a valid `Program`/comparable object, so a crafted puzzle that fails to uncurry causes the sentinel `False` to flow into code that expects `Program` semantics.

### Finding Description
`get_template_singleton_inner_puzzle()` is documented to return `Program`, but on the `uncurry()` failure path it returns `False` instead of `None` or raising: [1](#0-0) 

This same anti-pattern is repeated in `get_seconds_and_delayed_puzhash_from_p2_singleton_puzzle()`, which is annotated to return `tuple[uint64, bytes32]` but also returns `False` on failure: [2](#0-1) 

`get_template_singleton_inner_puzzle()` is used directly by `is_pool_singleton_inner_puzzle()` and `is_pool_waitingroom_inner_puzzle()`: [3](#0-2) 

These predicate helpers are consumed by `chia/pools/pool_wallet.py`, which is the pool-wallet coin-spend/state-transition parser used while processing pool/plotnft singleton coin spends fetched during wallet sync — i.e., it processes puzzle reveals that originate from spends observed on-chain/relayed by peers rather than data the local wallet itself constructed. Because `is_pool_singleton_inner_puzzle()` compares the return value of `get_template_singleton_inner_puzzle()` (`Program` or, on the bug path, `False`) against `POOL_WAITING_ROOM_MOD`/`POOL_MEMBER_MOD`, a crafted inner puzzle that fails to uncurry produces `False` instead of a `Program`, silently short-circuiting the identity comparison and returning `False` from the predicate rather than surfacing a well-defined "not a pool puzzle" signal through the same type as the success path. Elsewhere in the same module the correct, safe pattern is used (raising `ValueError` or returning `None` and letting callers check explicitly), e.g. in `uncurry_pool_member_inner_puzzle()`: [4](#0-3) 

The inconsistency (`False` vs. `None`/exception) is exactly the "unchecked sentinel propagates into a code path expecting the exception-free type" defect class the CVE describes for `CIccTagLut16::Write()`, where an unexpected null was dereferenced after a crafted-input parse failure instead of being handled by an explicit contract.

### Impact Explanation
If any downstream pool/plotnft transition logic in `pool_wallet.py` treats the return of these helpers as always a `Program` (e.g., subsequently calling `.get_tree_hash()`, `.uncurry()`, or iterating it) after a crafted singleton inner puzzle fails to uncurry, the pool-wallet's state-transition handling for that coin can throw an unhandled `AttributeError`/`TypeError` on a value that is a bare `bool` instead of a `Program`. In wallet sync/plotnft transition code this halts processing of that wallet's state machine (a spend/coin-set processing halt for the affected pool wallet), which matches the "spend-triggered transaction-processing halt" impact category. The severity is bounded by the fact I was not able to fully trace every call site inside `chia/pools/pool_wallet.py` to confirm an actual unguarded `Program`-only operation is invoked on the `False` sentinel in the current version of this analog scan (index only surfaced the definitions and 4 usage matches in `pool_wallet.py`, not their full bodies).

### Likelihood Explanation
This code path is reached automatically by ordinary plotnft/pool wallet users during normal wallet sync of pool-singleton coin state, without any privileged capability — any counterparty who can get a pool-associated coin observed by the wallet (e.g., via a spend on chain, which any unprivileged spend-bundle submitter can create) controls the shape of the inner puzzle being uncurried. However, likelihood of the crash actually firing depends on whether a live caller dereferences the return value in a `Program`-only manner, which I could not fully confirm from the available index.

### Recommendation
Change `get_template_singleton_inner_puzzle()` and `get_seconds_and_delayed_puzhash_from_p2_singleton_puzzle()` to return `None` (and update their type annotations to `Program | None` / `tuple[uint64, bytes32] | None`) instead of `False` on the `uncurry()` failure path, and update all call sites (`is_pool_singleton_inner_puzzle`, `is_pool_waitingroom_inner_puzzle`, and any pool_wallet.py consumers) to explicitly check for `None` before use, consistent with the safe pattern already used in `uncurry_pool_member_inner_puzzle()` and `get_inner_puzzle_from_singleton()`.

### Proof of Concept
1. Construct a coin spend whose puzzle reveal curries to a singleton whose inner puzzle is a non-curried (or malformed-curry) `Program` — i.e., one for which `Program.uncurry()` returns `None` per its own documented failure contract: [5](#0-4) 
2. Submit/broadcast the spend so an unprivileged full node/wallet observes the resulting coin as part of normal chain sync.
3. When the local pool wallet processes this coin's puzzle via `is_pool_singleton_inner_puzzle()`/`is_pool_waitingroom_inner_puzzle()`, `get_template_singleton_inner_puzzle()` returns the boolean `False` instead of `None`.
4. Any subsequent code in `chia/pools/pool_wallet.py` that assumes a `Program` was returned (e.g., attempts `.get_tree_hash()` or further uncurry/compare against `Program` objects) raises an unhandled exception, halting processing of that pool wallet's state transition for the crafted coin.

Note: I was unable to fully inspect every call site inside `chia/pools/pool_wallet.py` within the available indexing/tool budget to prove a concrete unguarded dereference occurs; this should be verified directly against that file's full body before treating this as confirmed-exploitable rather than a latent type-confusion defect.

def get_seconds_and_delayed_puzhash_from_p2_singleton_puzzle(puzzle: Program) -> tuple[uint64, bytes32]:

    if r is None:
        return False
    _, args = r
    _, _, _, seconds_delay_prog, delayed_puzzle_hash_prog = args.as_iter()
    seconds_delay = uint64(seconds_delay_prog.as_int())
    delayed_puzzle_hash = bytes32(delayed_puzzle_hash_prog.as_atom())

    def uncurry(self) -> tuple[Program, Program]:
        def match(o: CLVMStorage, expected: bytes) -> None:
            if o.atom != expected:
                raise ValueError(f"expected: {expected.hex()}")

        try:
            # (2 (1 . <mod>) <args>)
            ev, quoted_inner, args_list = self.as_iter()
            match(ev, b"\x02")
            if TYPE_CHECKING:
                # this being False is presently handled in the TypeError exception handler below
                assert quoted_inner.pair is not None
            match(quoted_inner.pair[0], b"\x01")
            mod = quoted_inner.pair[1]
            args = []
            while args_list.pair is not None:
                # (4 (1 . <arg>) <rest>)
                cons, quoted_arg, rest = args_list.as_iter()
                match(cons, b"\x04")
                if TYPE_CHECKING:
                    # this being False is presently handled in the TypeError exception handler below
                    assert quoted_arg.pair is not None
                match(quoted_arg.pair[0], b"\x01")
                args.append(quoted_arg.pair[1])
                args_list = rest
            match(args_list, b"\x01")
            return Program.to(mod), Program.to(args)
        except ValueError:  # too many values to unpack
            # when unpacking as_iter()
            # or when a match() fails
            return self, self.to(0)
        except TypeError:  # NoneType not subscriptable
            # when an object is not a pair or atom as expected
            return self, self.to(0)
