### Title
Escrow release performs external token transfer before decrementing `_orders` accounting, violating checks-effects-interactions — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The bug report's core lesson is: state-changing accounting must be finalized through the canonical bookkeeping step *before* any external effect is allowed to run, so that a re-entrant or malicious counterparty can never observe/exploit a stale balance. The Tron variant of `IntentGatewayV2.withdraw()` violates exactly this invariant: it reads `_orders[commitment][token]`, transfers the tokens out, and only *then* decrements the escrow mapping — the opposite order used by the corresponding, hardened `IntentsBase._withdraw()` implementation shipped for standard EVM chains.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (lines 682–721) releases escrowed order inputs to a beneficiary: [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The token/native transfer (an external call that can trigger arbitrary attacker-controlled code — a native `call` to `beneficiary`, or an ERC-20 `transfer` on an arbitrary listed token) executes **before** `_orders[body.commitment][token] -= amount`. This is a textbook checks-effects-interactions violation: the escrow ledger entry for that `(commitment, token)` pair is stale (still showing the full un-decremented amount) for the entire duration of the external call.

Compare this to the equivalent, corrected logic in the newer `IntentsBase._withdraw()` (used by the current EVM `IntentGatewayV2`/`intentsv2` contracts), which decrements the escrow mapping *before* making the external transfer: [2](#0-1) 

```
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

This shows the codebase's own maintainers recognized and fixed this exact accounting-ordering defect in the mainline EVM contract, but the Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` still contains the vulnerable, pre-fix ordering — directly analogous to the external report's point that balance-affecting state must be updated through the correct, invariant-preserving path (here: decrement-then-transfer) rather than leaving the ledger stale while an external call is in flight.

### Impact Explanation
`_orders[commitment][token]` is the sole on-chain accounting of how much of a given token is still escrowed for a given order commitment. Because the decrement happens only *after* the external call returns, any code path reachable during that external call which reads or mutates `_orders[commitment][token]` (or the aggregate escrow for that commitment) will see the pre-decrement (stale, too-high) balance. If the destination token or the beneficiary contract can trigger any re-entrant call into this contract before the state mutation lands, the escrow guard check `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` will incorrectly pass again against the stale non-zero balance, enabling a double release of the same escrowed funds (fund loss for the protocol/other order participants) and violating the "moves exactly once" bridge invariant called out in the impact gate.

### Likelihood Explanation
This is a structural CEI-ordering bug in a production, publicly-reachable code path — `withdraw()` is triggered by `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow`) and `onGetResponse` (cancel-from-source flow), both of which are ultimately triggered by legitimate protocol proof delivery, not requiring a malicious relayer or admin. The exploitability hinges only on control over the *token contract* or *beneficiary address* used in an order's inputs — both of which are attacker-choosable at order-placement time by any ordinary user, satisfying the "unprivileged attacker" bar. The fact that the sibling EVM contract was already patched to decrement-before-transfer strongly suggests this ordering was a known real issue, just not backported to the Tron variant.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to mirror `IntentsBase._withdraw()`: decrement (or delete) `_orders[body.commitment][token]` **before** issuing the native/`ERC20` transfer, for both the token loop and the `TRANSACTION_FEES` release block. Add a re-entrancy guard as defense-in-depth given the low-level `.call()` usage for ERC-20 transfers (no `SafeERC20`) in this contract.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the code shown):
1. User places a cross-chain order on the Tron `IntentGatewayV2` whose `order.inputs` includes a malicious ERC-20 token `EvilToken` deployed by the attacker, with `EvilToken.transfer()` overridden to re-enter the gateway.
2. A solver fills the order on the destination chain; a legitimate `RedeemEscrow` message is relayed and delivered via `onAccept` → `withdraw()`.
3. Inside `withdraw()`'s loop, `_orders[commitment][EvilToken]` is read (non-zero), then `EvilToken.call(transfer(beneficiary, amount))` is invoked. Because `EvilToken.transfer` is attacker-controlled, it can call back into any externally reachable function of the gateway that also inspects/uses `_orders[commitment][EvilToken]` (e.g., attempting a duplicate withdrawal path or a state-query flow) while the mapping still shows the pre-decrement balance.
4. Only after the reentrant path returns does `_orders[commitment][EvilToken] -= amount` finally execute, by which point a second release may have already been paid out against the stale balance.

Note: full exploitability depends on identifying a second externally-reachable call path back into escrow logic for the same commitment during the callback window (e.g., via a second in-flight `RedeemEscrow`/`RefundEscrow` message processed re-entrantly, or another public function reading the same mapping); this could not be fully traced to a second entry point within the available review, so this should be validated in a Devin/foundry session before being treated as a confirmed double-spend rather than a CEI-hygiene defect. The ordering flaw itself is unambiguous and directly regressed relative to the fixed `IntentsBase.sol` implementation.
