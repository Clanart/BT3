## Analog identified: relayer reward permanently orphaned when the request commitment backing it is deleted by timeout handling

### Title
Outbound request delivery reward becomes permanently unclaimable after request timeout deletes the local commitment - (File: `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
The ALCX report's broken invariant is: a claim path requires an on-chain entity (the veNFT) to still exist, but a separate lifecycle action (merge) destroys that entity without settling the value owed against it, permanently orphaning the reward. Hyperbridge's outbound-request relayer-reward mechanism has the same shape: the claim path requires `pallet_ismp::child_trie::RequestCommitments[commitment]` to still exist, but the timeout lifecycle path independently deletes that same commitment as "replay protection," with no coupling to whether a relayer already delivered (and is owed a reward for) that request.

### Finding Description
`process_outbound_request_delivery_claim` pays a relayer for proving delivery of a hyperbridge-originated request (from `pallet-host-executive`, `pallet-intents-coprocessor`, `pallet-token-governor`, or the relayer pallet's own withdrawal path) to a destination chain. Step 3 of its verification pipeline hard-requires the commitment to still be present in local storage: [1](#0-0) 

before any state-proof verification and payout logic runs: [2](#0-1) 

Separately, `IsmpHost::delete_request_commitment` is the mechanism used whenever a request times out — its own documentation states it is "used when a request is timed out" and instructs implementors to refund the *fee payer's* relayer fee there, but it says nothing about the *destination-delivery reward* claim path that keys off the same commitment: [3](#0-2) 

The timeout-driven deletion is demonstrated directly in the pallet-ismp test suite, showing the commitment is deleted from storage as part of ordinary timeout processing, independent of whether a delivery reward claim has been made: [4](#0-3) 

The two code paths — reward-claim eligibility (requires the commitment to still exist) and timeout processing (deletes the commitment) — are not coordinated. If a relayer delivers a hyperbridge-originated request to its destination near its timeout boundary (the receipt lands in `RequestReceipts[commitment]` on the destination, satisfying steps 8–10 of the claim pipeline), but the timeout window elapses before the relayer's `claim_outbound_request_delivery_reward` extrinsic lands on Hyperbridge, anyone can permissionlessly submit the timeout message. That timeout handling invokes `delete_request_commitment`, wiping `RequestCommitments[commitment]`. From that point on, step 3 of the claim pipeline fails with `OutboundRequestNotKnown` forever — the reward for a request that was, in fact, successfully and provably delivered becomes permanently unclaimable, even though the relayer did the work and the destination-side proof of delivery still exists.

### Impact Explanation
This falls squarely within "permanent freezing/loss of relayer reward funds owed for delivered service" — the reward sits in the treasury PalletId account and can never be paid out for that commitment because the on-chain gate (`RequestCommitments::get(commitment).is_some()`) can never again be satisfied. This is not a bounded/temporary DoS: once the commitment is deleted, `OutboundRequestsClaimed` is never set and the reward for that specific delivered request is lost permanently, exactly mirroring the ALCX pattern where burning the source entity makes the accrued value structurally unclaimable through the existing claim function.

### Likelihood Explanation
This requires no malicious relayer, prover, or admin — it is triggerable by ordinary, permissionless protocol operation: any hyperbridge-originated request with a non-zero timeout that is delivered close to its timeout boundary, combined with any third party (or the timeout-monitoring infrastructure itself) submitting the timeout proof before the relayer's claim lands. Both actions (timeout submission and reward claim submission) are unsigned/permissionless extrinsics racing against each other, so this is a structural, protocol-level race rather than an adversarial precondition. I was not able to fully confirm within this session whether every current hyperbridge-originated dispatcher (host-executive, intents-coprocessor, token-governor) uses a non-zero timeout for its `DispatchPost` calls — the pallet-relayer withdrawal path explicitly uses `timeout: 0` (never times out) and is therefore not exposed — so the practical blast radius depends on which system-message dispatch sites use non-zero timeouts, which should be verified directly in `modules/pallets/host-executive/src/lib.rs`, `modules/pallets/intents-coprocessor/src/lib.rs`, and `modules/pallets/token-governor/src/impls.rs`.

### Recommendation
Decouple reward-claim eligibility from commitment presence, or make timeout deletion aware of pending reward claims:
- Track delivery/claim eligibility in a separate, append-only structure that is populated at dispatch time and is not purged by `delete_request_commitment`, or
- Before deleting a request commitment on timeout, check destination-side delivery status (or simply refuse to delete commitments for the incentivized module allowlist / require the reward to be claimed or explicitly forfeited first), or
- Change step 3 of `process_outbound_request_delivery_claim` to accept a proof that the commitment *was* dispatched (e.g., via the MMR leaf/consensus proof already used elsewhere) instead of requiring current presence in local storage, since the request having ever been dispatched should be sufficient once destination delivery is separately proven.

### Proof of Concept
Conceptual sequence (pallet-level), analogous to the ALCX PoC:
1. Governance sets `OutboundRequestDeliveryReward[module_id] > 0` for a system module (e.g., host-executive).
2. The module dispatches a `PostRequest` with a non-zero timeout via `IsmpDispatcher::dispatch_request`, creating `RequestCommitments[commitment]`.
3. A relayer delivers this request to the destination chain just before the timeout timestamp, producing `RequestReceipts[commitment]` on the destination (state-proof provable).
4. Before the relayer's `claim_outbound_request_delivery_reward(claim)` extrinsic is included, a timeout message for this same commitment is submitted to Hyperbridge and processed, invoking `delete_request_commitment(&req)` and removing `RequestCommitments[commitment]`.
5. The relayer submits `claim_outbound_request_delivery_reward` with a valid destination-delivery proof; it reverts at step 3 with `Error::<T>::OutboundRequestNotKnown`, permanently, since `RequestCommitments::<T>::get(commitment)` will never again return `Some`. [5](#0-4)

	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);
