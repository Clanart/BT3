Let me confirm the panic path in `blame_internal` and how `Decryption::decrypt_with_proof` indexes by participant.### Title
Unvalidated `Participant` indices in PedPoP blame evaluation panic on attacker-supplied IDs — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame`, `AdditionalBlameMachine::blame`/`::new`, and the shared `blame_internal` helper accept `sender`/`recipient` `Participant` values derived from untrusted blame-accusation input and index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` without any membership or bounds check. A `Participant` ID outside `1..=n` (or a `sender` that was never registered) causes a HashMap indexing panic, aborting the process — a reachable denial of service analogous to CVE-2016-3695's "dangerous primitive left ungated" class.

### Finding Description
`AdditionalBlameMachine::new(context, n, commitment_msgs)` builds `commitments` and registers ECDH keys only for `Participant` IDs `1..=n` [1](#0-0) . `blame(sender, recipient, msg, proof)` then calls `blame_internal` with caller-supplied `sender` and `recipient` [2](#0-1) .

Inside `blame_internal` there are two unchecked index operations on attacker-controlled participants:

1. `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)` indexes `self.enc_keys[&decryptor]` inside `Decryption::decrypt_with_proof` whenever a `proof` is supplied — a `recipient`/`decryptor` not in `1..=n` panics [3](#0-2) .
2. If decryption succeeds and the share deserializes, `&self.commitments[&sender]` panics for any `sender` not among the registered participants [4](#0-3) .

There is no `Participant::new`-style validation, no `validate_map` call, and no `HashMap::get` fallback on this path — unlike `calculate_share`, which validates its input map against `all_participant_indexes()` before use [5](#0-4) . The doc comment for `AdditionalBlameMachine::new` even acknowledges that invalid inputs "may cause everything from inaccurate blame to panics," confirming the absent guard is a known gap rather than an enforced precondition [6](#0-5) .

The untrusted `EncryptedMessage` and `EncryptionKeyProof` bytes are parsed via the in-scope `EncryptedMessage::read` / `EncryptionKeyProof::read` APIs [7](#0-6) [8](#0-7) , and `Participant`, `sender`, and `recipient` are carried in the blame accusation itself, so an unprivileged party feeding crafted accusation data to a node evaluating blame reaches the panic.

### Impact Explanation
A single crafted blame evaluation kills the host process (Rust panic across `HashMap` indexing). Because blame evaluation runs when deciding who is fatally slashed for a failed DKG, crashing at that point aborts the blame protocol and halts DKG resolution — a liveness failure affecting the key-generation pipeline, matching the CVE class (unprivileged input reaches a dangerous operation that should have been rejected, causing denial of service).

### Likelihood Explanation
Reachability requires only that the caller evaluate a blame accusation containing an out-of-range `sender`/`recipient` `Participant` and a message whose PoP verifies for that `sender` (the accuser can construct this themselves, since `pop_challenge` merely binds whatever `from` is passed [9](#0-8) ). Caveat: in Serai's deployment the accusation is routed through authenticated tributary/coordinator handling (e.g., `VerifyBlame` in `processor/src/key_gen.rs`), so the practical attacker is a protocol participant rather than a fully anonymous party; as a library-level robustness bug reachable through the in-scope public `read`/`blame` APIs, it is best assessed Medium.

### Recommendation
In `blame_internal` (and `Decryption::decrypt_with_proof`), reject `sender`/`recipient` values not present in `commitments`/`enc_keys` before indexing — e.g., `let Some(commitments) = self.commitments.get(&sender) else { return sender }` (treating an unregistered accuser as faulty) — or enforce `Participant <= n` up front in `AdditionalBlameMachine::blame`/`BlameMachine::blame`. A regression test should pass `Participant::new(n + 1)` as `sender`/`recipient` and assert a graceful result rather than a panic.

### Proof of Concept
```rust
// crypto/dkg/pedpop (conceptual; assumes n = 2 DKG already completed)
let mut machine = AdditionalBlameMachine::new::<Ristretto>(
  CONTEXT,
  2,                       // n
  commitment_msgs,         // valid msgs for participants 1..=2
).unwrap();

// Attacker submits an accusation naming a non-existent participant 3.
let bad_sender = Participant::new(3).unwrap();
let bad_recipient = Participant::new(3).unwrap();

// msg is an EncryptedMessage crafted by the attacker with a valid PoP
// bound to `from = bad_sender` (attacker knows the ephemeral key).
// With proof = Some(proof), decrypt_with_proof indexes
// self.enc_keys[&bad_recipient] -> PANIC (encryption.rs:388).
// With a decryptable msg, blame_internal indexes
// self.commitments[&bad_sender] -> PANIC (lib.rs:599).
let _ = machine.blame(bad_sender, bad_recipient, msg, proof); // process aborts
```

Uncertain aspects: I did not fully trace how `Participant` values in blame accusations are constrained upstream in the coordinator's `InvalidDkgShare` handling (`coordinator/src/tributary/handle.rs:461` onward), which is outside the in-scope crates; if the tributary layer bounds `accuser`/`faulty` to the validator set, the panic is unreachable in deployment but remains a latent library defect.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
