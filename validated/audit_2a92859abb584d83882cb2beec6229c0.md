### Title
Stale conflict snapshot lets Copilot conflict resolution silently overwrite the user's own edits during a long-running AI turn - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated file content computed from a `rawContent` snapshot taken minutes earlier (before the Copilot turn ran), and only skips the write if the file's git status shows *no remaining* conflict markers at all. Any file that still has conflict markers — including one the user has since hand-edited — is unconditionally overwritten with the stale AI resolution, silently discarding the user's intervening work before it is committed.

### Finding Description
`buildConflictContext` reads each conflicted file once and stores its full text in `IFileConflictContext.rawContent`, which is later spliced with the model's per-hunk output in `reassembleResolvedFile`: [1](#0-0) 

That resolution flow can take a long time — up to a 10-minute timeout per chunk, plus a retry — while the model streams a response: [2](#0-1) 

When the user finally clicks "Continue Merge", `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` (built from the old `rawContent`) straight to disk. The only guard against clobbering user edits checks whether the file is *still reported as conflicted with unresolved markers* — it does not compare the current on-disk bytes to the `rawContent` that was actually used to compute the resolution: [3](#0-2) 

If the user edits the conflicted file in their own editor while the AI call is in flight (e.g., fixing part of a hunk, adding a line, or resolving one conflict block but leaving another marker-block untouched), `git status` still reports the file as conflicted with unresolved markers, so `hasUnresolvedConflicts(onDiskFile.status)` remains true and the skip branch is never taken. The stale, pre-edit AI resolution is written over the user's live edits and then staged with `git add`, with no diff/merge of the two versions and no warning to the user.

### Impact Explanation
This results in silent corruption of what the user ultimately commits: their manual, in-progress conflict-resolution edits are discarded without notice and replaced with content computed from an outdated file snapshot. Because the write happens automatically as soon as "Continue Merge" is clicked and the result is immediately staged and folded into the merge/rebase/cherry-pick commit, the user has no opportunity to notice or recover the lost edits before the operation completes.

### Likelihood Explanation
The race window is real and can be widened by an adversarial "theirs" side: a malicious/complex incoming branch or PR that produces large or numerous conflicts increases the time Copilot needs to resolve them (chunking, longer turns, retries up to the 600s timeout), increasing the probability that the user makes manual edits to the working tree during that window. The only requirement is that the user interacts with the conflicted file (a completely normal, expected action during a long-running dialog) before confirming — no privileged access or local malware is needed, and the flow is reachable purely by merging/rebasing against a repository/branch an attacker controls.

### Recommendation
Before writing `resolution.resolvedContent`, re-read the file's current on-disk content and compare it to the `rawContent` captured at context-build time; if they differ, treat the file as externally modified (same as the already-existing "fully resolved externally" skip) and surface it to the user instead of silently overwriting it. Alternatively, hash `rawContent` at context-gathering time and store the hash alongside the resolution, then verify the hash of the current file content matches before writing.

### Proof of Concept
1. Start a merge/rebase against a branch with several real conflicts (can be a hostile PR branch designed to have many/large conflicts to slow down AI resolution).
2. Click "Resolve with Copilot" and, while the request is streaming (verifiably up to minutes given `timeoutMs: 600_000` and a retry pass — see `copilot-store.ts:1394-1480`), open one of the conflicted files in an external editor and make a manual change inside one of the still-unresolved conflict blocks (leave the markers so `git status` still reports it as conflicted).
3. Once Copilot's dialog returns results, click "Continue Merge".
4. Observe that `_applyCopilotConflictResolutions` (`app-store.ts:7233-7259`) writes the AI's resolution computed from the original `rawContent`, silently discarding the manual edit made in step 2, and stages the result via `git add`.

Note: this analysis is based on static code review only (no runtime/dev-build reproduction was performed), so exact timing thresholds and UI-level warnings (if any exist elsewhere in the dialog) could not be independently confirmed beyond what is shown in the cited files.
