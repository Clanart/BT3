## Title
Stale full-file overwrite in Copilot merge-conflict resolution silently restores attacker-controlled content the user manually removed — ([File: app/src/lib/stores/app-store.ts])

## Summary
`AppStore._applyCopilotConflictResolutions` writes a full-file `resolvedContent` string to disk that was reconstructed at context-gathering time (`buildConflictContext`/`reassembleResolutions`), but only re-validates the current on-disk state well enough to detect the case where the file is *fully* resolved. If the file still contains any unresolved conflict marker at apply time, the code unconditionally overwrites the entire file with the stale snapshot, discarding any partial manual edits the user made in the interim — including edits that intentionally stripped out attacker-supplied conflicting content.

## Finding Description
The Copilot conflict-resolution flow spans three points in time:

1. **Snapshot (T1)** — `buildConflictContext` reads each conflicted file from disk and stores the raw content (including conflict markers) in `IFileConflictContext.rawContent`: <cite repo="Kirstentat/desktop--008" path="app/src/lib/copilot-conflict-context.ts" start="429="438" /> Actually see below. [1](#0-0) 

2. **Reconstruction** — later, `reassembleResolutions` splices the model's per-hunk output back into that *same stale* `ctx.rawContent` to build the full-file `resolvedContent` used for the eventual write: [2](#0-1) 

3. **Apply (T2)** — potentially much later (after Copilot has finished streaming, after the user has reviewed the result dialog, and after the user may have opened the file in an external editor), `_applyCopilotConflictResolutions` performs a single staleness check — whether the file has *no remaining* conflict markers — and if that check doesn't trip, it blindly writes the T1-based `resolvedContent` over the current file: [3](#0-2) 

The guard comment even acknowledges the intent ("Overwriting it with Copilot's stored content would silently clobber their work, so skip it") but the check only fires when `hasUnresolvedConflicts` is `false` (i.e., the whole file is fully clean). It does not compare current on-disk content to the snapshot used to build `resolvedContent`, so any file that still has *at least one* unresolved marker anywhere is written wholesale from the T1 snapshot — clobbering any manual changes made to that file's other hunks or non-conflict regions since T1.

The broken invariant mirrors the report's pattern precisely: the write path trusts an externally/asynchronously produced value (`resolvedContent`, derived from a point-in-time read) instead of re-deriving it from the current authoritative state (current on-disk content) immediately before the write, and the one guard that exists only covers a single edge case rather than the general race window.

## Impact Explanation
Because `resolvedContent` is reconstructed from the file content read *before* the (potentially long-running) Copilot turn and result-review UI, and the on-disk file can change during that window (background auto-refresh runs `git status`, the user can open the file in an external editor to hand-fix one hunk, etc.), the final `writeFile` call can silently discard those interim edits and restore content that came from the conflicting branch — including content contributed by an attacker whose branch/commit is what's being merged/rebased/cherry-picked. This is a silent corruption of what the user ultimately commits, matching the "silent corruption of what the user commits or pushes" impact category: the user believes they fixed a hunk (e.g., stripped a malicious line the attacker's branch introduced), but the applied write can reintroduce the pre-fix full-file snapshot for any file where the conflict wasn't marked as *fully* clean elsewhere in that same file.

## Likelihood Explanation
Likelihood is moderate: it requires a multi-hunk conflicted file, a Copilot resolution flow in progress, and the user (or an automatic background action) mutating the file's on-disk content between context-gathering and confirmation — a realistic sequence for a user reviewing/adjusting a Copilot-suggested merge before clicking "Continue," but it does depend on user interaction with the file mid-flow rather than being a pure zero-interaction remote exploit.

## Recommendation
Before writing `resolution.resolvedContent`, re-read the current on-disk content and re-derive/validate that the parts outside the model's resolved hunks are unchanged from the T1 snapshot (or re-run hunk extraction against current content and only splice the model's resolution into the *current* file rather than the stale one). Alternatively, treat any modification detected since context-gathering (not just "fully resolved") as a reason to skip the write for that file, surfacing it to the user for manual reconciliation instead of silently overwriting.

## Proof of Concept
1. Start a merge/rebase against a branch controlled by an attacker that introduces a multi-hunk conflict in `file.txt` (hunk A with malicious content, hunk B benign).
2. Trigger "Resolve with Copilot"; `buildConflictContext` snapshots `file.txt` (with both hunks still marked) as `rawContent`.
3. While Copilot is processing / the result dialog is open, open `file.txt` in an external editor and manually resolve hunk A only (removing the attacker's malicious content), leaving hunk B's markers in place.
4. Click "Continue Merge." `_applyCopilotConflictResolutions` finds `onDiskFile` still `isConflictedFileStatus` with `hasUnresolvedConflicts === true` (because of hunk B), so it does not skip the write, and calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` using the T1 `resolvedContent` — silently restoring the attacker's content in hunk A that the user had just removed.
