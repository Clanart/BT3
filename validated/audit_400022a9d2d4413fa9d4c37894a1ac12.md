### Title
Symlink/traversal escape when revealing or opening working-directory files outside the repository root - ([File: app/src/lib/app-shell.ts])

### Summary
GitHub Desktop already contains a dedicated guard, `resolveWithin()` (`app/src/lib/path.ts:36-100`), whose explicit purpose is to prevent an attacker-controlled repository from using directory-traversal segments or a symlinked directory to make a nominally "in-repo" relative path resolve to a location outside the repository. This guard is correctly applied in `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`) and in `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:390-407`, which even comments "Guard against path traversal and symlink escapes"). However, the much more commonly used file-action code paths — reveal-in-Finder/Explorer, "Open with default program", and "Open in external editor" — never call `resolveWithin`. They instead build the full path with a raw `Path.join(repository.path, path)` and hand it straight to the OS shell.

### Finding Description
`revealInFileManager()` in `app/src/lib/app-shell.ts:56-64` computes:
```
const fullyQualifiedFilePath = Path.join(repository.path, path)
return shell.showItemInFolder(fullyQualifiedFilePath)
```
`Path.join` normalizes `..` segments syntactically but performs no filesystem-aware containment check and does not resolve symlinks. If any path component underneath `repository.path` is a symlink pointing outside the repository (which can be committed/checked out from a cloned/fetched repo, or introduced by an untracked file inside a symlinked directory), the joined path silently escapes the repository root even though it "looks" relative.

`path` here is `WorkingDirectoryFileChange.path` / `CommittedFileChange.path`, which is fully attacker-controlled: it comes from parsing `git status --porcelain=2` (`app/src/lib/git/status.ts:207-297`) or committed tree entries — i.e., content of a repository the user cloned, fetched, or checked out, satisfying the "attacker controls a cloned/fetched repository" precondition.

The same unguarded `Path.join(repository.path, path)` pattern is repeated in every UI call site that ultimately invokes `revealInFileManager`, `openFile`, or the external editor:
- `app/src/ui/changes/sidebar.tsx:282-284` (`onOpenItem` → `openFile(fullPath, dispatcher)`)
- `app/src/ui/changes/filter-changes-list.tsx:628-655` (Reveal in File Manager / Open in External Editor menu items)
- `app/src/ui/history/selected-commits.tsx:371-455` (context menu on committed files)
- `app/src/ui/open-pull-request/pull-request-files-changed.tsx:154-226`
- `app/src/ui/lib/conflicts/unmerged-file.tsx:396-436`
- `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx:212-236`
- `app/src/ui/app.tsx:3429-3437` (`onOpenInExternalEditor`)

None of these call `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, unlike the two locations that already implement this exact defense. `openFile()` (`app/src/ui/lib/open-file.ts:4-17`) then passes the resulting (potentially out-of-repo) path to `shell.openExternal('file://' + fullPath)`, and `revealInFileManager` passes it to `shell.showItemInFolder`, both of which operate on whatever absolute path they are given, with no repository-boundary awareness.

`isSafeFileExtension` (referenced in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`) only inspects the extension of the string `file.path` as reported by git — it does not resolve symlinks and cannot detect that the underlying target has escaped the repository, so it provides no protection against this specific primitive.

### Impact Explanation
An attacker who controls a cloned/fetched repository can plant a symlinked directory entry (e.g., a tracked symlink named `x` pointing to `/` or to a sensitive directory such as the user's home folder) together with an untracked or tracked file that appears, in `git status`/tree listing, to live under that directory (e.g., `x/.ssh/id_rsa`, or `x/Documents/secret.docx`). When the victim opens the Changes/History/PR-files view and uses ordinary UI actions ("Open with default program", "Open in external editor", or even "Reveal in File Manager"), Desktop computes the joined path, which the OS resolves through the symlink to a file outside the repository, and opens/reveals it via the OS shell. This lets the attacker cause Desktop to read/open arbitrary files outside the intended repository sandbox (file disclosure) and, since the OS may treat some file types by executable association ("Open with default program"), can escalate to unwanted execution of attacker-influenced content residing outside the repo, without requiring local/physical access, admin rights, or any credential. This matches the "file write or read outside the repo" and "code execution" impact classes explicitly listed as valid.

### Likelihood Explanation
Moderate-to-high. The precondition (a symlink checked out from an untrusted, cloned repository plus an entry that resolves underneath it) is entirely achievable via ordinary git operations (`ln -s /target x && git add x` on POSIX, or a crafted status/rename entry) and requires only that the victim clone/fetch the repo and use a single, everyday context-menu action ("Reveal in Finder/Explorer" or double-click to open with default program) that Desktop already supports and encourages. The fact that the maintainers already built and applied `resolveWithin` for two other, less-frequently-hit code paths (`openRepositoryFromUrl`, Copilot conflict resolution) confirms the team recognizes this exact class of risk, but the far more frequently used file-open/reveal actions in Changes/History/PR views were left unguarded — precisely the "modifier is missing here but present elsewhere" pattern described in the seed report.

### Recommendation
Apply the existing `resolveWithin()` (or `resolveWithinPosix`/`resolveWithinWin32` as platform-appropriate) guard, exactly as done in `dispatcher.ts` and `copilot-conflict-context.ts`, to every place that turns a `WorkingDirectoryFileChange`/`CommittedFileChange` relative path into an absolute path before handing it to the shell:
- `revealInFileManager()` in `app/src/lib/app-shell.ts`
- `openFile()` / its callers in `app/src/ui/lib/open-file.ts`
- All `Path.join(repository.path, file.path)` call sites in `filter-changes-list.tsx`, `selected-commits.tsx`, `pull-request-files-changed.tsx`, `unmerged-file.tsx`, `copilot-conflicts-dialog.tsx`, `sidebar.tsx`, and `app.tsx`

If `resolveWithin` returns `null` (path escapes the repository root), refuse the action and surface an error/log message, mirroring the handling already present in `openRepositoryFromUrl`.

### Proof of Concept
1. Attacker creates and publishes a repository:
   ```
   mkdir evil-repo && cd evil-repo && git init
   ln -s / escape          # symlink pointing at filesystem root
   git add escape && git commit -m "innocuous change"
   ```
2. Attacker adds a second commit/branch (or relies on `git status` showing an untracked entry) referencing a path underneath the symlink, e.g. a rename/copy detected by git as `escape/etc/passwd`, or simply has the victim's working tree contain an untracked file at that location once the symlink is checked out (any file physically present at `/etc/passwd` will now appear to git as living at `evil-repo/escape/etc/passwd`).
3. Victim clones the repository in GitHub Desktop and opens the Changes or History tab, where the entry `escape/etc/passwd` is listed as a normal file (`WorkingDirectoryFileChange`/`CommittedFileChange` with `path = "escape/etc/passwd"`).
4. Victim right-clicks the entry and selects "Reveal in Finder/Explorer" or "Open with default program".
5. Desktop executes `Path.join(repository.path, "escape/etc/passwd")`, which the OS resolves through the `escape` symlink to `/etc/passwd`, and passes this path to `shell.showItemInFolder` / `shell.openExternal('file://...')`, revealing/opening a file entirely outside the cloned repository — demonstrating file access outside the intended repository sandbox driven solely by attacker-controlled repository content. async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
