### Title
Division-by-zero panic in consensus liquidity (CL) reward split during proposer reward finalization - ([File: kaiax/staking/staking_info.go])

### Summary
`consolidatedNode.Split()` divides a reward amount by `StakingAmount + CLStakingAmount` without checking that this sum is non-zero. This value is called unconditionally on the block proposer's `consolidatedNode` during deferred-reward finalization (`specWithProposerAndFunds` / `specWithProposerAndFundsFlex`), with no `minStake` eligibility guard, unlike the analogous `assignStakingRewards`/`assignStakingRewardsFlex` staker-reward paths which do guard against a zero denominator. If a proposer's CN staking amount and CL staking amount both fall to zero at the same block, `big.Int.Div` panics, analogous to the ImageMagick `ConvertXYZToJzazbz()` division-by-zero (CVE-2021-20310): both are cases where an unguarded division on attacker/user-influenced input triggers undefined behavior in a security-critical code path.

### Finding Description
`consolidatedNode.Split()`: [1](#0-0) 
computes `totalAmount := cnAmountBig + clAmountBig` and then does `clAmount.Div(clAmount, totalAmount)` with no check that `totalAmount != 0`.

This function is called for the block proposer without any minimum-stake precondition in both the Kore and Flex reward paths: [2](#0-1) [3](#0-2) 

Contrast this with the staker-reward distribution functions `assignStakingRewards`/`assignStakingRewardsFlex`, which explicitly gate `cn.Split()` behind `cnTotalStakingAmount > minStake` / `excessInt[...] <= 0` checks (`kaiax/reward/impl/getter.go:514-532`, `460-483`), and are documented in the reward README as guaranteeing "If no validator has staked more than the minimum staking amount, all staking rewards are sent to the proposer." No equivalent guard exists for the proposer's own `Split()` call.

A `consolidatedNode` with `StakingAmount == 0` and a non-nil `CLStakingInfo` is a state the codebase itself explicitly represents/tests (`StakingAmounts: []uint64{a2, aM, aL, a0}` paired with a CLStakingInfo entry) — i.e., it is not considered an invalid/unreachable configuration: [4](#0-3) 

Under `RoundRobin`/`Sticky` proposer policies (both are supported, production-legal configurations, e.g. used in `tests/gasless_test.go`), **all council members remain qualified proposers regardless of staking amount** — only `WeightedRandom` after Istanbul demotes under-staked validators: [5](#0-4) 

So a validator can withdraw its CN stake down to zero via its `CnStaking` contract (a normal, unprivileged staker action) and, independently, the consensus-liquidity depositors can withdraw their pooled stake from that validator's CL pool down to zero. Neither action requires malicious/privileged behavior; both are ordinary staker/depositor operations. If both amounts are zero for the current proposer's `RewardAddr` when `FinalizeState`/`GetDeferredReward` runs, `Split()` divides by zero and panics.

### Impact Explanation
`FinalizeState`/`GetDeferredReward` execute deterministically on every full node and validator when processing the block. A panic here is not merely one node's local failure — every honest node reaches the identical zero-denominator condition and panics identically, which halts block processing network-wide (a liveness-breaking DoS at the protocol level), analogous in class to the reachable, unauthenticated-input division-by-zero in the referenced CVE. This exceeds a simple resource-DoS because it is a deterministic consensus-halting condition triggered by ordinary staking/CL actions, not a targeted single-node crash.

### Likelihood Explanation
Reachability depends on:
1. The chain using `RoundRobin`/`Sticky` proposer policy (or `WeightedRandom` pre-Istanbul/before minStake demotion), which are legitimate supported configurations but not necessarily Kaia mainnet's actual configuration.
2. Both the CN staking amount and the CL pool amount for the same `RewardAddr` reaching exactly zero at the same source block used for reward calculation.
3. A newer permissionless valset transition (`kaiax/valset/impl/transition_context.go`) does implement automatic demotion of validators whose `StakingAmount < MinStake`, which — if applicable to the active configuration — could reduce or eliminate the practical likelihood of a zero-stake node remaining an eligible/active proposer. I was not able to fully confirm whether this permissionless valset transition is exclusive of or coexists with the classic AddressBook-based `RoundRobin`/`Sticky` no-demotion path in the currently examined code, so the actual likelihood on Kaia mainnet is uncertain and requires further confirmation of the deployed governance/valset configuration.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split()` (return `(amount, 0)` or `(0, 0)` when `totalAmount.Sign() == 0`), mirroring the existing eligibility guards used in `assignStakingRewards`/`assignStakingRewardsFlex`, and/or add a minStake-equivalent guard before calling `cn.Split(proposer)` in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`.

### Proof of Concept
1. Configure a chain (or identify a running one) with `istanbul.policy` = RoundRobin or Sticky (or WeightedRandom pre-Istanbul), and Prague HF active (so CL staking applies).
2. As the operator of a registered council node (staker), withdraw the entire `CnStaking` balance to 0 via the staking contract's normal withdrawal flow, while remaining registered in the AddressBook/council.
3. Have the consensus-liquidity depositors withdraw their full CL stake from that validator's CL pool to 0 (an independent, unprivileged action available to any CL depositor).
4. Wait for this validator's round to come up as proposer (guaranteed to occur periodically under RoundRobin/Sticky).
5. When `GetDeferredReward`/`FinalizeState` computes the block reward, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` calls `cn.Split(proposer)` for this validator's `consolidatedNode`, where `StakingAmount == 0` and `CLStakingInfo.CLStakingAmount == 0`, causing `totalAmount.Sign() == 0` and a `big.Int` division-by-zero panic in every node processing that block.

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
