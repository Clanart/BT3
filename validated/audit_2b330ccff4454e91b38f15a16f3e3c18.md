### Title
Unauthenticated `WWW-Authenticate` realm spoofing lets a malicious Git remote trigger a trusted "GitHub" sign-in flow against an attacker-controlled endpoint - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Wormhole report's root cause is that Desktop/LiFi trusted an externally-supplied identifier (`toChainId`) at face value, conflating two different namespaces (EVM chain IDs vs Wormhole chain IDs) without validating it against a canonical mapping, leading to funds being misdirected to an untrusted destination. The equivalent broken invariant in GitHub Desktop is in the credential-helper's endpoint classification logic: it trusts an attacker-controlled HTTP response header (`WWW-Authenticate: realm="GitHub"`) to decide that an arbitrary remote host is a genuine "GitHub" endpoint, and immediately escalates the trust level of that host from "generic git server" to "enterprise GitHub", triggering GitHub-branded sign-in UI pointed at the attacker's origin.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies a credential-request's target host. After checking hardcoded dotcom/GHE/gist hosts, it falls back to trusting the `wwwauth[...]` credential fields that Git forwards verbatim from the remote server's HTTP response: [1](#0-0) 

Any HTTPS git remote/proxy fully controls this header and can claim `realm="GitHub"` even though the host has no relationship to github.com or any GitHub Enterprise Server instance. Once classified as `'enterprise'`, `getCredential` checks whether an existing account already matches that host; if not, it calls `promptForGitHubSignIn(endpoint)` with the attacker's own endpoint string: [2](#0-1) 

`promptForGitHubSignIn` then routes non-`github.com` hostnames straight into the Enterprise sign-in flow, feeding the attacker-chosen origin as the sign-in endpoint: [3](#0-2) 

`beginEnterpriseSignIn` → `setEndpoint` accepts this string, validates only that it's a well-formed HTTPS URL (`validateURL`), and uses it directly as the OAuth authorization endpoint: [4](#0-3) [5](#0-4) 

The resulting dialog is titled generically ("Sign in" / "Sign in Using Your Browser") and only shows the raw URL string via a `<Ref>` element, without any distinct warning that the host was inferred from an untrusted, spoofable server-supplied header rather than something the user typed or a resolved GitHub identity: [6](#0-5) 

This mirrors the Wormhole bug's pattern exactly: a value from an untrusted external channel (`_wormholeData.toChainId` there, the `wwwauth[...]` realm string here) is accepted as an authoritative identifier for a trust decision (destination chain vs. "is this GitHub") without cross-checking against a canonical, verified source (a chain-ID mapping there, an actual GitHub identity/certificate check here).

### Impact Explanation
A user cloning/fetching from, or being redirected by, an attacker-controlled HTTPS remote (or a malicious proxy sitting between the user and any HTTPS git server) can cause Desktop to present what looks like a legitimate "Sign in" flow branded as GitHub authentication, but which is actually configured to complete OAuth/browser sign-in against the attacker's own domain. Since `getOAuthAuthorizationURL(endpoint, csrfToken)` builds the browser URL from this same attacker-supplied `endpoint`, the browser is opened to a URL on the attacker's infrastructure while the in-app dialog implies a trusted GitHub-branded flow. This can be used to phish the user's GitHub Enterprise/PAT-equivalent credentials or to get the user to complete an OAuth consent against an attacker-hosted "GitHub Enterprise" look-alike, matching the "unauthorized OAuth" and "credential/token exfiltration" impact categories — the resulting account object is even merged back into stored credentials via `credWithAccount`, so a successful phish is persisted into the app's account store.

### Likelihood Explanation
Any git server (including one impersonated via a MITM/monkeyed proxy on non-pinned HTTPS traffic, or one the user is enticed to add as a remote/clone URL) can trivially return a custom `WWW-Authenticate` header — this requires no special privilege on the attacker's part, only that Desktop performs a credential-fetching git operation (`clone`, `fetch`, `push`) against the attacker's host, which is a completely ordinary user action already covered by the "Valid Impact" scope (attacker-controlled git remote/proxy response). No local access, admin rights, or pre-existing malware is required.

### Recommendation
Do not treat the `WWW-Authenticate` realm claim as sufficient by itself to classify a host as `'enterprise'` (GitHub-flavored). At minimum, require a positive verification step (e.g., the same `isGitHubHost` metadata/`x-github-request-id` probe already used later in the function) before elevating trust, and make the sign-in UI clearly distinguish "GitHub-verified" endpoints from ones inferred purely from a server-asserted header, so users aren't shown a GitHub-branded prompt for a domain that was never actually confirmed to run GitHub software.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://evil.example.com/repo.git` and configures it to respond to unauthenticated Git Smart HTTP requests with `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim clones/fetches `https://evil.example.com/repo.git` in GitHub Desktop (e.g., via a link the victim was persuaded to open, or a remote already present in a cloned repo).
3. Git invokes Desktop's credential helper (`trampoline-credential-helper.ts`); `getEndpointKind` matches the spoofed realm string and returns `'enterprise'`. [7](#0-6) 
4. Since no account is registered for `evil.example.com`, `promptForGitHubSignIn('https://evil.example.com')` is invoked, which calls `dispatcher.beginEnterpriseSignIn(cb)` and `setSignInEndpoint('https://evil.example.com')`. [8](#0-7) 
5. Desktop shows the "Sign in" dialog with a browser-based auth continuation button; clicking it opens the victim's browser at an OAuth-looking URL rooted at `evil.example.com`, where the attacker can harvest credentials or complete a bogus OAuth grant that gets stored as a Desktop account.

        credentialHelperUrl: endpoint,
      })

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    }
  }

export function validateURL(address: string): string {
  // ensure user has specified text and not just whitespace
  // we will interact with this server so we can be fairly
  // relaxed here about what we accept for the server name
  const trimmed = address.trim()
  if (trimmed.length === 0) {
    const error = new Error('Unknown address')
    error.name = InvalidURLErrorName
    throw error
  }

  let url = URL.parse(trimmed)
  if (!url.host) {
    // E.g., if they user entered 'ghe.io', let's assume they're using https.
    address = `https://${trimmed}`
    url = URL.parse(address)
  }

  if (!url.protocol) {
    const error = new Error('Invalid URL')
    error.name = InvalidURLErrorName
    throw error
  }

  if (url.protocol !== 'https:') {
    const error = new Error('Invalid protocol')
    error.name = InvalidProtocolErrorName
    throw error
  }

  return address
}
