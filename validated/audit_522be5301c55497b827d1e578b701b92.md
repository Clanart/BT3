### Title
`ReceivedOutput::read` accepts an unbound `offset`/`script_pubkey` pair, letting funds be attributed to the wrong key - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`v2InventoryToXNFT`'s bug is a function taking two caller-supplied identifiers that must correspond (a v2 vault address and its vault ID), never checking their correspondence, and crediting whatever `balanceOf` shows afterward — a mismatch leaves value stuck and attributable to a later, correctly-paired call. Serai's Bitcoin wallet has the same shape: `ReceivedOutput` is a pair `(offset, script_pubkey)` where `script_pubkey` must equal `p2tr(key + offset·G)` for the output to be spendable by the intended key. `ReceivedOutput::read` deserializes both fields independently from untrusted bytes with no consistency check, and downstream `Output::key()` silently derives `script_key - offset·G`, crediting the output to whatever key the mismatch yields.

### Finding Description
`ReceivedOutput` stores three independently deserialized fields:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  let output;
  let outpoint;
  {
    let mut buf_r = BufReader::with_capacity(0, r);
    output = TxOut::consensus_decode(&mut buf_r)...;
    outpoint = OutPoint::consensus_decode(&mut buf_r)...;
  }
  Ok(ReceivedOutput { offset, output, outpoint })
}
``` [1](#0-0) 

The only producer that binds `offset` to `script_pubkey` is `Scanner::scan_transaction`, which looks up the offset in `self.scripts` keyed by `output.script_pubkey` [2](#0-1) . Nothing enforces that invariant on the deserialization path — exactly like the NFTX report, where nothing forced `vTokenV2 == nftxVaultFactory.vault(vaultId)`.

The consumer that turns the pair into an accounting identity is `Output::key()`:

```rust
// processor/src/networks/bitcoin.rs:112-122
fn key(&self) -> ProjectivePoint {
  let script = &self.output.output().script_pubkey;
  ...
  Secp256k1::read_G(&mut key.public_key(Parity::Even).serialize().as_slice()).unwrap() -
    (ProjectivePoint::GENERATOR * self.output.offset())
}
``` [3](#0-2) 

For scanner-produced outputs this equals the multisig key because `script_pubkey` commits to `key + offset·G`. For a `ReceivedOutput::read`-produced output, an attacker controls `offset` and `output` independently, so `key()` returns `actual_script_key − offset·G` — an arbitrary point under attacker control relative to the real key. The output's `balance()` is still credited at full face value (`self.output.value()`) [4](#0-3) .

The one place the correspondence is enforced is `SignableTransaction::multisig`, which rejects when `p2tr_script_buf(keys.offset(offset).group_key()) != prevout.script_pubkey` [5](#0-4)  — but that check runs at spend time, after the output was already accounted as received under a key derived from the mismatched pair.

### Impact Explanation
An output is reported received (balance credited, `key()` attribution computed) from a `(offset, script_pubkey)` pair that was never verified to correspond. Two concrete consequences:

- **Funds reported received that are not spendable**: bytes claiming a real on-chain output with an attacker-chosen offset produce `key() = script_key − offset·G ≠` the multisig key, so the value is credited to the wrong key and can never be gathered under the intended multisig — the analog of tokens left "stuck on the contract balance."
- **Misattribution / front-running**: because `key()` is fully determined by the attacker-controlled pair, a crafted record can attribute an output to a different registered key, analogous to a back-running `v2InventoryToXNFT` call claiming the stuck tokens under the correct `vTokenV2`.

### Likelihood Explanation
Requires untrusted bytes to reach `ReceivedOutput::read` (e.g., via `Output::read` at processor/src/networks/bitcoin.rs:145-166, which reads `kind`, `presumed_origin`, `output`, `data` all without cross-checks) in a flow where the output is accepted without re-deriving it through `Scanner::scan_transaction`/`get_outputs` (the latter does `assert_eq!(output.key(), key)` on internally scanned outputs at processor/src/multisigs/scanner.rs:562-563, providing no protection for externally-supplied records). Severity: Medium — same as the source report: a mismatch precondition with high loss-of-attribution impact.

### Recommendation
Bind the pair at the trust boundary, mirroring the report's two options:

1. In `ReceivedOutput::read`/`Output::read`, take the expected multisig `key` (or make `read` verification context-dependent) and reject unless `p2tr_script_buf(script_key_in_output)` corresponds to `key + offset·G`; or
2. In `Output::key()`, verify `p2tr_script_buf(key + offset·G) == script_pubkey` and treat failure as an invalid output rather than silently returning a derived key.

### Proof of Concept
```rust
// Attacker crafts bytes for ReceivedOutput::read: pick any victim output's
// real TxOut/OutPoint (script_pubkey commits to Q_victim = K + o_victim*G),
// but set the serialized offset to an arbitrary o' != o_victim.
let forged = ReceivedOutput {
  offset: o_prime,          // attacker-chosen scalar
  output: victim_txout,     // real on-chain output
  outpoint: victim_outpoint,
};
// Output::key() then returns K + (o_victim - o_prime)*G,
// crediting victim_txout.value() to a key the multisig never generated.
// The output is reported received yet SignableTransaction::multisig will
// never sign for it under the intended key.
```

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

          output: output.clone(),

        });

    }
