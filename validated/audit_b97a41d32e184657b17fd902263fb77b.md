### Title
`SignableTransaction` adds the OP_RETURN data output to the transaction but excludes it from the weight/vsize/fee and standardness accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` (including the OP_RETURN data output) first, but then computes `weight`, `vbytes`, `needed_fee`, the `TooLowFee` minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` standardness check using `payments` only — the data output is never included in `calculate_weight_vbytes`. Like the LToken bug (reserves excluded from `totalAssets` yet still lendable via `lendTo`), an amount that materially affects the transaction is excluded from the accounting view while still being included in the committed transaction.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

```rust
// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...)
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (`send.rs:62-127`) reconstructs a transaction using only `tx_ins` and `payments` (plus optional `change`). The OP_RETURN output pushed into `tx_outs` at lines 194–202 is absent from that reconstruction. Consequently:

- `vbytes`/`weight` are underestimated by roughly `8 (value) + 1 (script len) + ~2 (OP_RETURN push) + data_len` bytes, i.e. up to ~91 vbytes / ~364 WU for the maximum 80-byte payload.
- `needed_fee = fee_per_vbyte * vbytes` under-reports the fee required to achieve the caller-requested fee rate.
- The `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` (line 211) passes a transaction that may actually be below minimum relay fee once the data output is counted.
- The `weight > MAX_STANDARD_TX_WEIGHT` check (line 241) may pass a transaction whose real weight exceeds the standardness limit.

The same omission occurs in the change branch: `fee_with_change = fee_per_vbyte * vbytes_with_change` (lines 225–227) also omits the data output, so the computed `change` amount leaves only `fee_with_change` as the actual fee — the transaction genuinely pays a lower sat/vbyte than requested.

### Impact Explanation
A `SignableTransaction` produced with a `data` payload systematically pays a lower effective fee rate than the `fee_per_vbyte` the caller specified, and can be constructed that violates mempool standardness (weight limit / minimum relay fee) while passing all internal checks. `needed_fee()` then reports a value that does not correspond to the true transaction size. Result: the threshold-signed Bitcoin transaction may be rejected by relaying nodes or stall in the mempool — outputs the scanner credited as spent are effectively locked behind a non-propagating transaction.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` triggers it — this path is exercised by Serai's `InInstruction` data flow, where transaction data ultimately derives from user-submitted instructions (`processor/src/networks/bitcoin.rs` uses `SignableTransaction` via `BSignableTransaction`). The bug is deterministic whenever `data` is present; no adversarial timing is needed.

### Recommendation
Include the OP_RETURN output in the weight/vsize reconstruction. Pass the already-built `tx_outs` (or the data length) into `calculate_weight_vbytes` rather than `payments`, e.g. add `data_len` as a parameter and push a matching zero-value OP_RETURN output inside the weight-estimation transaction. Then both `needed_fee`/`fee_with_change` and the `TooLowFee`/`MAX_STANDARD_TX_WEIGHT` checks will reflect the real transaction.

### Proof of Concept
```rust
// Conceptual: inside networks/bitcoin tests
let output = send_and_get_output(&rpc, &scanner, key).await;
let data = vec![0u8; 80]; // maximum allowed
let tx = SignableTransaction::new(
  vec![output],
  &[],                                    // no payments
  Some(p2tr_script_buf(key).unwrap()),    // change
  Some(data),                             // OP_RETURN output added to tx_outs
  FEE,
).unwrap();

// tx.output includes the OP_RETURN output, yet:
// needed_fee was computed from a vsize that excludes it.
let estimated_vbytes = tx.needed_fee() / FEE;
let actual_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();
// actual_vbytes > estimated_vbytes by ~91
assert!(actual_vbytes > estimated_vbytes);
// Effective fee rate < requested FEE
assert!(tx.fee() < FEE * actual_vbytes);
```

The discrepancy grows with `data.len()`: at the 80-byte cap the fee is under-charged by ~91 vbytes × `fee_per_vbyte`, and a transaction near the standardness boundary can exceed `MAX_STANDARD_TX_WEIGHT` while still passing the check at line 241. [1](#0-0) [2](#0-1) [3](#0-2)

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
