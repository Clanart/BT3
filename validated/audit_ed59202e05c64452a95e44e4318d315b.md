### Title
Owner of `GaslessSwapRouter` can steal any KAIA sent to the contract via `claimCommission()` using raw self-balance instead of tracked commission accounting - ([File: contracts/bindings/kip247/GaslessSwapRouter.go])

### Summary
The KIP-247 gasless-transaction system contract `GaslessSwapRouter` exposes a payable `receive()` function that accepts native KAIA from any address, and an owner-only `claimCommission()` function that sweeps the contract's *entire* native balance (via the `SELFBALANCE`/`0x47` opcode) to the owner, rather than withdrawing only the commission amount actually accrued from `swapForGas` operations. This mirrors the reported Chainlink pattern where an unprivileged party can fund a contract and a privileged owner can withdraw the entire pool, including funds that were never legitimately owed to them.

### Finding Description
`GaslessSwapRouter` is deployed and registered as a Kaia system contract through the `Registry` (KIP-149), and is used by the `kaiax/gasless` module to let block proposers lend KAIA to users, who then repay via `swapForGas`, with the router keeping a commission.

The contract implements:
- A public `receive() payable` function [1](#0-0) , which allows *any* unprivileged account to send native KAIA directly to the router with no restriction on sender or amount.
- `claimCommission()` (selector `0xfad99f98`), callable only by `owner` [2](#0-1) . Decompiling the constructor/runtime bytecode shows the function body uses the `SELFBALANCE` opcode (`0x47`) to read `address(this).balance` directly and transfers that entire balance to the stored owner address, rather than referencing an internal `commission`/accrued-fee accounting variable: `...346101c257826003193601126101c2576100e86115d5565b479182156101805783808080866001600160a01b038254165af1...` [3](#0-2) .
- A `CommissionClaimed(uint256 amount)` event is emitted with whatever balance amount was swept [4](#0-3) .

Because `claimCommission()` sweeps the router's raw native balance instead of a segregated commission ledger, any KAIA that lands in the contract — whether from a legitimate `swapForGas` commission, an accidental direct transfer via `receive()`, or a deliberate "donation"/overpayment by any third party — becomes claimable by the owner. This is structurally identical to the reported Chainlink issue: an unprivileged party can fund a shared contract balance that only the privileged owner can withdraw, and the owner's withdrawal path does not distinguish between rightfully-earned funds and externally deposited funds.

The `swapForGas` flow itself computes `commission` as an event field (`SwappedForGas(proposer, amountRepaid, user, finalUserAmount, commission)` [5](#0-4) ), but this is only an emitted amount for observability — the withdrawal function itself does not check against a per-operation accrual total, it just takes everything currently held by the contract.

### Impact Explanation
Any user (searcher, proposer, or arbitrary EOA) who sends native KAIA to the `GaslessSwapRouter` address — either accidentally, through a rounding/overpayment in `swapForGas`, or a direct transfer to the contract's `receive()` — has those funds unconditionally exposed to owner appropriation. Since the router is a live system contract wired into block building (the gasless module reads it every block to determine allowed tokens), and is intended to hold WKAIA/KAIA as part of the lend/repay cycle, an owner (or a compromised owner key/governance-controlled owner) can extract value that does not belong to them beyond the legitimate commission earned from swaps. This constitutes unauthorized value movement out of a contract that unprivileged transaction senders can fund.

### Likelihood Explanation
Likelihood is limited primarily by owner trust assumptions (the owner is presumably a semi-trusted deployer/governance address), but the vulnerability requires no special privilege from the attacker/depositor side — any account can trigger the exposure simply by sending KAIA to the router (via `receive()` or slight overpayment in `swapForGas`). The owner needs only one transaction (`claimCommission()`) to realize the value. No consensus-level or validator-level compromise is needed; this is purely a contract-level control-flow issue reachable from a single transaction.

### Recommendation
Track commission accrual in a dedicated state variable (e.g., `accruedCommission`) that is incremented only within `swapForGas` by the computed commission amount, and have `claimCommission()` transfer and reset only that tracked value rather than `address(this).balance`. Additionally, consider rejecting or explicitly handling unsolicited native-KAIA transfers via `receive()` (e.g., revert unless called internally, or route excess balance to a separate sweep mechanism that is not conflated with commission accounting).

### Proof of Concept
1. Any account (e.g., attacker or unrelated user) sends KAIA directly to the deployed `GaslessSwapRouter` contract address, either via the exposed `receive()` payable fallback [1](#0-0)  or by supplying a slightly larger `amountIn`/output than required in a `swapForGas` call, leaving a residual native balance in the contract.
2. The router's balance now includes funds beyond the legitimately-earned commission.
3. The `owner` calls `claimCommission()` [6](#0-5) ; the underlying bytecode reads `SELFBALANCE` and transfers the router's *entire* native balance to `owner`, not just the intended commission [3](#0-2) .
4. The `CommissionClaimed` event fires with the full swept amount [4](#0-3) , and the externally-deposited/overpaid KAIA is now irrecoverably transferred to the owner.

Note: The `GaslessSwapRouter` Solidity source is not present in this repository (only the ABI/bytecode Go bindings under `contracts/bindings/kip247/GaslessSwapRouter.go`), so exact variable names and full control flow could not be fully verified from source — the finding is based on ABI method signatures, emitted events, and manual EVM bytecode disassembly of the `claimCommission` selector branch. A Devin session with full repository/source access (if the `.sol` source exists elsewhere or needs to be requested from the contract authors) would be needed to confirm the precise implementation details before remediation.
