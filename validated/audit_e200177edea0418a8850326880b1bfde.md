This confirms the analog: the `shop_domain` used by generated webhook jobs (e.g. `AppUninstalledJob`, `CustomersDataRequestJob`, `ShopRedactJob`, and the documented custom controller pattern) comes from the `X-Shopify-Shop-Domain` header via `ShopifyApp::WebhookVerification#shop_domain`, which is never included in the HMAC computation (`hmac_valid?` only signs `request.raw_post`). This is structurally the same bug class as the Across report: a value that downstream logic treats as authenticated (the "witness"/order data) is not actually covered by the signature that is supposed to attest to it.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-shop data/job spoofing - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates the request body against the app's shared secret via `hmac_valid?(data)`, but the `shop_domain` helper reads `X-Shopify-Shop-Domain` directly from request headers, which is not part of the HMAC-signed data. Generated jobs (e.g. `AppUninstalledJob`, `CustomersRedactJob`, `ShopRedactJob`, `CustomersDataRequestJob`) and the documented custom-controller pattern use this unauthenticated header value to look up and mutate/destroy shop records.

### Finding Description
`hmac_valid?` computes the HMAC exclusively over `request.raw_post`: [1](#0-0) 
`verify_request` only checks this body-derived HMAC, while `shop_domain` is read straight from the `X-Shopify-Shop-Domain` header with no cryptographic binding to it: [2](#0-1) 
Because the HMAC secret (`ShopifyApp.configuration.secret`) is the app's single client secret shared across every merchant that installs the app (not a per-shop secret), any actor who legitimately installs the app on their own store receives real webhooks with valid HMACs for arbitrary bodies of their choosing (e.g., by triggering `shop/redact`-adjacent or other webhook-producing actions on their own shop, or via `orders/create` with attacker-controlled content). That attacker can then replay the same raw body and valid HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop that also installed the app. `verify_request` will still pass because the header is not part of the signed data, and the generated jobs will act on `shop_domain` (the header value) using the attacker-controlled body.

### Impact Explanation
This allows cross-shop request forgery: an authenticated HMAC (proving only "some install of my app sent this body") is accepted as also asserting "this event belongs to shop X," which it does not attest to. Depending on which webhook job is targeted, this can be used to inject attacker-controlled webhook payloads that get processed as belonging to a victim shop, e.g. triggering `Shop.find_by(shopify_domain: shop_domain)`-scoped destructive/side-effecting logic in the generated `AppUninstalledJob`, `CustomersRedactJob`, or `ShopRedactJob` templates against a shop the attacker does not own. [3](#0-2) 

### Likelihood Explanation
Requires the attacker to have installed the app on at least one shop they control (a normal, unprivileged, unrelated-merchant capability) and knowledge of the victim's `myshopify.com` domain (public information). No secret leakage or privileged access is needed — only the ability to send an HTTP POST with a captured body/HMAC pair and a modified header.

### Recommendation
Bind the shop domain (and any other header-derived trust decision) into the HMAC-verified data, or independently verify that the `shop_domain` header matches a shop identifier embedded in the verified webhook body/topic before using it to key data lookups. At minimum, cross-check the header shop domain against the session/shop record used to install the specific webhook subscription, rather than trusting it unconditionally post-HMAC-check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, and triggers/receives a legitimate webhook (e.g. `orders/create`) with a body they influence (order note/attributes) — capturing the raw body and the corresponding `X-Shopify-Hmac-Sha256` value, both valid against the shared app secret.
2. Attacker POSTs this exact raw body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. [4](#0-3) 
3. `verify_request` passes because it only checks the body against the secret; `shop_domain` returns `victim-shop.myshopify.com`.
4. The corresponding webhook job is enqueued with `shop_domain: "victim-shop.myshopify.com"` and the attacker-controlled body, and executes shop-scoped logic against the victim's shop record. [5](#0-4)
