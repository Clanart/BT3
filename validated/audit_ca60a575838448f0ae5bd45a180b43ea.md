Confirmed: `Kip71GasTarget` uses `noopFormatChecker` (no validation that it's non-zero) while `Kip71BaseFeeDenominator` explicitly checks `v != 0`. This is the analog vulnerability.

### Title
Missing zero-check on `GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
`GasTarget` is a governance-settable KIP-71 parameter used as a divisor in the post-Magma base fee calculation `NextMagmaBlockBaseFee`. Unlike `BaseFeeDenominator`, which is explicitly checked to reject the value `0` (`v != 0` in its `FormatChecker`), `GasTarget`'s `FormatChecker` is `noopFormatChecker`, allowing `0` to be voted and accepted into the governance parameter set. Once `GasTarget` is `0` and any block consumes any gas (which happens on essentially every non-empty block, since ordinary unprivileged transactions consume gas), the `big.Int.Div` call divides by the zero-valued `gasTarget`, which panics in Go, crashing every node that computes or verifies the header. This mirrors the reported CollateralBook issue where an admin-set numeric parameter without adequate bounds checking causes a core invariant/calculation to become permanently broken, but here it manifests as a chain-halting panic reachable by any subsequent ordinary transaction rather than a revert.

### Finding Description
`Kip71GasTarget`'s parameter definition omits any non-zero validation: [1](#0-0) 

Compare this to `Kip71BaseFeeDenominator`, which correctly guards against zero: [2](#0-1) 

`checkConsistency` in the header governance verification path treats `Kip71GasTarget` (along with `Kip71BaseFeeDenominator` and `Kip71MaxBlockGasUsedForBaseFee`) as requiring "no more checks here" beyond the format checker's pass/fail: [3](#0-2) 

`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` directly and, when the parent block's gas used differs from `gasTarget` (which is nearly guaranteed if `gasTarget == 0` and any transaction runs), performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`, dividing by zero: [4](#0-3) 

Note that `BaseFeeDenominator == 0` is defensively handled with a fallback (`baseFeeDenominator = 64`) inside this same function, showing the developers were aware of the zero-divisor risk for one parameter but did not apply the same defense — nor an admission-time format check — to `GasTarget`: [5](#0-4) 

### Impact Explanation
`NextMagmaBlockBaseFee` is called during block header preparation and verification on every node computing the next block's base fee, e.g. in `makeHeader`/chain building and header verification paths: [6](#0-5) 

A `big.Int` division by zero panics in Go and is not a normal EVM revert — it is an unrecovered runtime panic in node process code that executes on the block-production/verification hot path. Once `GasTarget=0` is voted in through governance and becomes active (governance parameter change itself requires validator/governing-node voting, matching the allowed "governance parameters" analog category), the very next block that uses any nonzero amount of gas (i.e., processes any ordinary, unprivileged transaction) triggers the panic on every node computing that header, halting block production/validation chain-wide — a consensus-halting denial of service, analogous in severity to the reported "lock all funds forever" impact, since the entire chain becomes unable to progress.

### Likelihood Explanation
Requires a governance vote to set `GasTarget` to `0`, which is gated by validator/governing-node participation rather than any account, so likelihood depends on validator/governance behavior (misconfiguration or malicious governing node in single mode). However, once set, the trigger condition (any block gas usage) is met by ordinary, unprivileged user transactions with no additional adversarial coordination — the actual DoS trigger step is fully reachable by any public transaction sender.

### Recommendation
Add a non-zero format checker to `Kip71GasTarget` in `kaiax/gov/param.go`, mirroring `Kip71BaseFeeDenominator`'s `v != 0` check, so that a `0` value is rejected before it can be voted into governance. Additionally, consider adding a defensive zero-guard fallback for `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, consistent with the existing fallback already implemented for `baseFeeDenominator == 0`.

### Proof of Concept
1. Governance vote sets `kip71.gastarget` to `0` (accepted since `FormatChecker` is `noopFormatChecker`).
2. Vote is included and takes effect at the next epoch, updating the active `KIP71Config.GasTarget` to `0`.
3. Any subsequent ordinary transaction is included in a block, making `parentGasUsed > 0`.
4. On the next block, all nodes call `NextMagmaBlockBaseFee(parentNumber, parentBaseFee, parentGasUsed)`; since `parentGasUsed != gasTarget (0)` and `parentGasUsed > gasTarget`, the code computes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, causing a runtime panic in every node attempting to build or verify that header, halting the chain.
