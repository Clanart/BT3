## Analysis

The external report's core invariant is: **ERC20 `transfer`/`transferFrom` can return `false` without reverting, and any contract that checks only the outer call success (not the decoded boolean) will treat a failed transfer as successful.** OpenZeppelin's `SafeERC20` exists precisely to close this gap by decoding and requiring `true`.

Hyperbridge's own codebase demonstrates it knows this: inbound/escrow-funding paths consistently use `SafeERC20.safeTransferFrom` [1](#0-0) , and `SafeERC20 for IERC20` is imported and used throughout [2](#0-1) . But the outbound settlement path — the one that actually pays out escrowed funds to a beneficiary — bypasses `SafeERC20` entirely and uses a raw low-level `.call` that only checks the outer call's success flag, never decoding the ERC20 return value.

## Title
Unsafe raw `.call` with `IERC20.transfer.selector` in `withdraw()`/`SweepDust` accepts non-reverting `false` ERC20 returns as successful settlement, causing silent fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, which is invoked from `onAccept` (`RedeemEscrow`/`RefundEscrow`) and `onGetResponse` (GET-timeout refund) to pay out escrowed order funds, moves tokens via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks the low-level `success` boolean [3](#0-2) . It never inspects the ABI-decoded return data. The same unsafe pattern is used for `SweepDust` payouts [4](#0-3)  and fee redemption [5](#0-4) .

### Finding Description
For any ERC20-compliant-but-non-standard token that returns `false` from `transfer()` instead of reverting (a well-documented real-world category of tokens), `token.call(...)` still returns `success = true` (the external call itself did not revert) even though `abi.decode(returndata, (bool))` would be `false` — meaning no tokens actually moved. Because `withdraw()` only checks `success`, it proceeds to:
- decrement `_orders[commitment][token]` [6](#0-5) 
- set `_filled[body.commitment] = beneficiary` [7](#0-6) 
- emit `EscrowReleased`/`EscrowRefunded` as if settlement succeeded [8](#0-7) 

This is a false-success state acceptance: the contract's accounting is permanently updated as "settled" while the beneficiary never received the tokens, which remain stuck in the `IntentGatewayV2` contract with no escrow record left to reclaim them (`_orders[...][token]` is now zero, and `_filled` blocks any retry via `onGetResponse`'s `Filled()` check) [9](#0-8) .

This is inconsistent with the rest of the same contract, which correctly uses `SafeERC20.safeTransferFrom` for escrow funding [1](#0-0)  and [10](#0-9) , proving the project's own security expectation for ERC20 correctness, which is violated specifically in the fund-release/withdraw path.

### Impact Explanation
This causes direct, permanent loss of escrowed user/solver funds: a rightful beneficiary (order filler on `RedeemEscrow`, or the original user on `RefundEscrow`/GET-timeout refund) never receives their tokens, yet the protocol's internal state marks the order as filled/refunded — an unrecoverable false settlement. This satisfies the bounty's "stealing or loss of funds" and "false ... state acceptance" categories, since it requires no malicious peer, relayer, or prover — only a token that is non-compliant with strict boolean-revert semantics on the whitelisted input/fee-token set.

### Likelihood Explanation
Any token registered/used in orders that does not strictly revert on failed transfer (paused tokens, blacklist-style tokens, or any token returning `false` under certain conditions instead of reverting) triggers this on the very next settlement attempt for that order. No attacker action beyond using such a token as an order asset is required; the flow through `onAccept`/`onGetResponse` is a standard, authenticated part of order fulfillment.

### Recommendation
Replace the raw `.call(...)` + `success`-only check pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in this file), which decodes and requires the ERC20 return value to be `true` (or absent, per EIP-20/EIP-1363 semantics), reverting on any transfer that does not genuinely succeed.

### Proof of Concept
1. Attacker/user places an order whose input token is a custom ERC20 contract (`EvilToken`) that implements `transfer()` to return `false` (no revert) when, e.g., the contract's own balance check fails internally, while remaining otherwise spec-compliant for `safeTransferFrom` pulls at order placement.
2. Order times out or is filled normally; cross-chain flow calls `onAccept`/`onGetResponse` → `withdraw(body, isRefund)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` at the call level but the token internally returns `false` and does not move funds.
4. `withdraw()` decrements `_orders[commitment][token]`, sets `_filled[commitment]`, and emits `EscrowReleased`/`EscrowRefunded` — the beneficiary's tokens remain trapped in `IntentGatewayV2` with no further code path to reclaim them, since the escrow slot is now zero and the order is marked filled.
