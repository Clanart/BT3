## Analysis

Found a concrete native analog to the "Swapper left-over token balance" bug class: the ICS20 → IBC-Callbacks EVM middleware permanently strands unescrowed user funds while the source chain simultaneously refunds the sender, producing a duplication of spendable value.

### Title
Failed IBC recv-callback permanently traps un-escrowed/minted tokens in the isolated address while the source chain refunds the sender, duplicating user value - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`ContractKeeper.IBCReceivePacketCallback` [1](#0-0)  runs strictly **after** the core ICS20 `OnRecvPacket` logic has already un-escrowed (or minted) tokens to a deterministic "isolated address" [2](#0-1) . If the attacker-supplied `dest_callback` contract call fails for any reason (insufficient conversion, `SendEnabled=false`, revert, partial pull, out-of-gas), the callback returns an error and the packet acknowledgement is a failure ack, exactly like the underlying, un-reverted token transfer remains applied on the destination chain. This is demonstrated directly by the repo's own test: `evmd/tests/ibc/ibc_middleware_test.go:786-808`, where after a failed callback the funds are **not** returned to escrow, but remain "trapped" as bank coins in the isolated address [3](#0-2) , and the repo's own documentation explicitly acknowledges these funds become permanently unreachable: "If tokens are deposited back into the isolated address, they are unreachable" [4](#0-3) .

### Finding Description
The intended, atomic pattern (like the Swapper contract, which should never hold leftover balances) is broken here because the ICS20 token movement and the EVM callback execution are not part of the same all-or-nothing state transition from the perspective of the *acknowledgement*:

1. The transfer stack processes `OnRecvPacket` bottom-up: `channel.RecvPacket → callbacks.OnRecvPacket → erc20.OnRecvPacket → transfer.OnRecvPacket` [5](#0-4) . The core ICS-20 `transfer.OnRecvPacket` unescrows/mints tokens to the packet's `receiver` (the isolated address) as an ordinary, committed state change on `ctx`.
2. `x/erc20` keeper's `OnRecvPacket` then optionally auto-converts the bank coin to its ERC20 representation [6](#0-5) .
3. `IBCReceivePacketCallback` then attempts to `approve` the attacker-supplied `contractAddress` for the full amount and call it with attacker-controlled calldata, using a **separate cached context** (`ctx.CacheContext()`), only writing that cache back on success [7](#0-6) . If the EVM call errors, the function returns an error and the callback machinery converts this into an error acknowledgement.
4. Crucially, the error acknowledgement only rolls back the *callback's own* cached sub-context — it does **not** roll back the earlier, already-committed unescrow/mint performed by steps 1–2, which live on the real `ctx`, not `cachedCtx`.
5. The counterparty (source) chain receiving this error acknowledgement will process it as a failed transfer and refund the original sender (re-mint / un-escrow on the source side), per standard ICS-20 ack semantics.
6. Net effect: the same value now exists twice — refunded to the sender on the source chain, and stranded (but not burned) as a real bank/ERC20 balance sitting in the destination chain's isolated address, which by design (per `GenerateIsolatedAddress`, deterministic on `(channelID, sender)`, no private key exists for it) is permanently unreachable/unspendable by the legitimate owner [8](#0-7) .

This is precisely analogous to the Swapper report's core defect ("left-over balances after a swap can be exploited/lost because the operation isn't atomic") — here the IBC transfer + EVM callback + acknowledgement is not atomic, so a mid-flight failure leaves real, already-moved value behind while the rest of the system (source-chain refund) behaves as if the transfer never completed.

### Impact Explanation
This directly matches the required Critical impact categories:
- **Duplication of spendable user value**: the same transferred amount becomes simultaneously refunded on the source chain and present (non-burned) on the destination chain.
- **Permanent freezing/locking of user funds**: the destination-side copy is stuck forever in an isolated address with no controlling key, as explicitly acknowledged in the module's own README [4](#0-3) .

Any condition that makes the destination EVM call fail after the underlying transfer commits — a temporary `SendEnabled=false`, a contract that reverts, insufficient gas, an ERC20 mint cap, or simply a malicious/broken `dest_callback` contract chosen by the packet's own sender or a relayer manipulating memo via PFM (explicitly called out as untrusted in the module's own docs) — triggers this outcome. Because the attacker (the IBC packet sender) fully controls the `dest_callback.address`/`calldata`, they can deliberately craft a contract that intentionally leaves a nonzero balance or reverts after the approval step, guaranteeing the fail-ack/duplication scenario at will, without needing any privileged access.

### Likelihood Explanation
Reachable by any unprivileged user who can send an ICS-20 transfer with `memo.dest_callback` set (standard packet-sender capability), no validator/relayer collusion or special privileges required. The repo's own integration test suite already reproduces the exact "trapped balance" condition using nothing more than toggling `SendEnabled`, confirming the bug is trivially triggerable, and no compensating mechanism (revert of the underlying transfer, retry, or reconciliation) is implemented for it — the documentation frames the unreachable balance as an accepted "limitation" rather than mitigating it.

### Recommendation
Make the whole receive-and-callback flow atomic with respect to acknowledgement generation: wrap the underlying ICS-20 unescrow/mint together with the destination callback execution in a single cached context that is only committed if the callback succeeds; if the callback fails, revert the underlying transfer application state too (not just the EVM sub-call), so that a failed callback and a refund on the source chain are consistent with a fully-reverted receive on the destination chain. Alternatively, if atomic rollback of the underlying transfer is not feasible, do not return an application-level error acknowledgement when the callback fails after tokens have already been irrevocably delivered — instead, always return success acknowledgement (as in ibc-hooks) and leave the funds recoverable via a rescue path from the isolated address, rather than silently creating irreconcilable double state.

### Proof of Concept
1. Register a token pair for a denom `X`, ensure a channel is open between chain B (sender) and chain A (evmChainA).
2. Deploy a malicious/naive EVM contract at address `C` that either reverts unconditionally after being approved, or accepts the approval without pulling the full amount (e.g., leaves 1 wei) — as the repo's test does by toggling `SendEnabled=false` [9](#0-8) .
3. From chain B, send an ICS-20 transfer of amount `N` of denom `X` to the isolated address `GenerateIsolatedAddress(channelID, sender)` [8](#0-7)  with `memo.dest_callback.address = C`.
4. Relay the packet; observe: `errAck.Success() == false` returned to chain B (triggering a refund of `N` to the original sender on chain B), while chain A's escrow account is drained by `N` and that `N` sits, un-recoverable, in the isolated address [10](#0-9) .
5. Total circulating value increased by `N` across the two chains — the sender got their `N` back on chain B, and an unrecoverable `N` now also exists on chain A.

```markdown
## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
```
