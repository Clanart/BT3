Based on the local codebase evidence, the strongest analog to the GMX "attacker-controlled callback picks execution timing to get a stale/favorable price" bug is the gas-unbounded, delete-and-retry delivery pattern in `EvmHost.dispatchIncoming`.

### Title
Unbounded-gas `onAccept`/`onGetResponse` callback with delete-and-retry semantics lets an attacker-controlled destination app choose *when* its own cross-chain message finalizes, based on favorable on-chain conditions - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming` delivers verified cross-chain messages to a destination application via a low-level `.call()` that forwards all remaining gas, with no calldata length/complexity cap on the destination and no gas stipend limit. If the call fails, the request receipt is deleted specifically "so that it can be retried" [1](#0-0)  - the exact same "fail now, succeed later, at will" primitive the GMX report exploited via the attacker-supplied callback contract.

### Finding Description
Any unprivileged user can be both the source and destination of a message: they can call `IDispatcher.dispatch()` (permissionless) with `to` set to a contract they control on the destination chain [2](#0-1) . Once a relayer (or the attacker self-relaying, which is explicitly supported [3](#0-2) ) submits the proof via `HandlerV2.handlePostRequests`, delivery goes through `dispatchIncoming`:

```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
if (!success) {
    // so that it can be retried
    delete _requestReceipts[commitment];
    return;
}
``` [4](#0-3) 

The same delete-and-retry pattern exists for `dispatchIncoming(GetResponse)` [5](#0-4)  and both `dispatchTimeOut` variants [6](#0-5) . Crucially, an individual failed `onAccept`/`onGetResponse` does not revert the surrounding `handlePostRequests`/`handleGetResponses` batch transaction - the handler explicitly "early return[s] here" instead of reverting the whole batch [7](#0-6) . This is documented protocol design ("Handler Must Succeed for Refund... can be called multiple times until it succeeds") [8](#0-7) , i.e. it is intentional that the destination app fully controls, at essentially zero cost, whether "acceptance" of a given cross-chain fact happens now or later.

This mirrors the GMX primitive exactly: the callback target is attacker-controlled, the call is gas-unbounded, and a failed call is designed to be *silently retryable* rather than final. An attacker's `onAccept` can read any on-chain price/liquidity/state condition and deterministically `revert()` when unfavorable (consuming a small, controlled amount of gas to fail cheaply) or fully process (mint funds, release escrow-bound accounting, etc.) when favorable, then have the exact same commitment redelivered later once conditions turn in their favor - with the relayer/self-relayer paying gas each attempt, at no capital risk to the attacker.

### Impact Explanation
Any Hyperbridge application whose `onAccept`/`onGetResponse` effect is price- or state-sensitive at the moment of acceptance (e.g. mint-on-accept token bridges such as `HyperFungibleToken`, or any custom `IApp` built on `HyperApp`) inherits this optionality for free: the attacker who deploys the destination app decides the finalization block by choosing when to let the call succeed. This is a "logic attack"/"transaction manipulation" primitive that can be composed with any price-dependent settlement logic reachable through a user-deployed `IApp`, giving risk-free selective execution exactly analogous to the GMX finding, without requiring a malicious relayer, prover, or governance actor - the relayer is doing its job correctly and honestly; the exploit is entirely in the unbounded, retryable callback contract the attacker controls.

### Likelihood Explanation
Likelihood is moderate-to-high for any third-party `IApp` built on this delivery primitive: dispatching to an arbitrary destination address is a normal, permissionless operation [2](#0-1) , self-relay is a documented supported feature [3](#0-2) , and the delete-on-failure retry is unconditional and gas-unbounded at the protocol level, requiring no special privileges to trigger.

### Recommendation
- Forward a bounded gas stipend to the destination `onAccept`/`onGetResponse`/timeout callbacks (similar in spirit to the GMX fix that capped attacker-controlled input rather than letting it consume unbounded gas), so failures are deterministic gas-exhaustion events rather than attacker-selected conditional reverts.
- Consider requiring `IApp` implementations that hold price-sensitive settlement logic to snapshot/commit any price-dependent decision *before* the retryable callback point, rather than allowing indefinite re-attempts of the same commitment.
- Document and, where feasible, enforce a maximum retry count or minimum backoff/finality condition, so that a message cannot be indefinitely held pending until an attacker-favorable state occurs.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept`, restricted with `onlyHost`, whose logic:
   - reads a cheap on-chain condition (e.g., `block.timestamp % N`, a DEX price, or a mapped flag it controls via a separate `flipSwitch()` function it owns), and
   - `revert()`s immediately (burning minimal gas) if the condition is "unfavorable", or performs the state-changing effect (e.g., calls into a bridged mint/settlement function) if "favorable".
2. Attacker calls `dispatch()` on the source `EvmHost` with `to = address(EvilApp)` and a payload encoding a value-bearing action (e.g., a mint request to a bridging `IApp` composed with `EvilApp`, or `EvilApp` itself minted balance) [2](#0-1) .
3. Once finalized on Hyperbridge, attacker self-relays and calls `HandlerV2.handlePostRequests` repeatedly (no cooldown enforced) [9](#0-8) .
4. Each call reaches `EvmHost.dispatchIncoming`, which calls `EvilApp.onAccept` with unlimited forwarded gas; while the condition is unfavorable, `EvilApp` reverts, the receipt is deleted, and the message remains pending indefinitely at zero cost beyond gas [10](#0-9) .
5. When the attacker observes a favorable on-chain condition, they flip the internal switch (as in the GMX PoC's `flipSwitch()`) and resubmit the same proof; `onAccept` now succeeds and the value-bearing effect finalizes at the attacker's chosen moment, with `PostRequestHandled` emitted as if delivery were normal [11](#0-10) .

## Self Relayed Requests

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
