### Title
Sensitive field values embedded in parser error/exception messages bypass Protobuf's own `debug_redact` protection - ([File: src/google/protobuf/text_format.cc], [File: python/google/protobuf/json_format.py], [File: src/google/protobuf/json/internal/parser.cc])

### Summary
Protobuf's TextFormat and ProtoJSON parsers (and several language-binding conversion layers) build human-readable parse-error/exception messages that directly interpolate the raw, attacker/caller-supplied field value (e.g. `Expected double, got: "hello"`, `Cannot convert '%s' to %s`, `Couldn't parse integer: "{0}"`). This is the same failed invariant as the OpenBao/mapstructure report: a type-conversion failure message embeds the actual value instead of a generic description, so if the calling application logs the returned error (a very common pattern for parse failures), the value ends up in plaintext logs. Critically, Protobuf itself has already recognized this exact class of risk and implemented a mitigation — the `debug_redact` field option and `TextFormat::Printer::TryRedactFieldValue`/`GetRedactionState` machinery — but that redaction is applied only on the *printing* path (`DebugString`), not on the *parsing/error* path, so a field explicitly marked sensitive by the schema author can still have its literal value leaked via a parse-error message.

### Finding Description
The failed invariant in the OpenBao report is: "error messages produced during type-conversion of untrusted/sensitive input must not embed the raw value," because such messages are commonly persisted to server/audit logs (CWE-532). Protobuf constructs conceptually identical messages in multiple parsing/conversion code paths that reflect the offending value verbatim:

- TextFormat parser field-value errors embed the literal token text, e.g. `"Expected double, got: \"hello\""`, `"Expected integer, got: \"hello\""`, and `"Invalid value for boolean field \"optional_bool\". Value: \"meh\"."` as exercised in [1](#0-0) .
- ProtoJSON parsing in C++ embeds the raw value on map-key/bool conversion failure: `absl::StrFormat("expected bool string, got '%s'", key.value.AsView())` [2](#0-1) .
- Python `json_format.py` embeds the value directly into `ParseError` messages, e.g. `"Couldn't parse integer: {0}".format(value)` and `"Bool value {0} is not acceptable for integer field"` [3](#0-2) , and similarly in `_ConvertScalarFieldValue`/enum handling [4](#0-3) .
- Java `JsonFormat.java` embeds the JSON element in `InvalidProtocolBufferException`: `"Invalid enum value: " + json + " for enum type: ..."` and `"Invalid value: " + json + " for expected type: " + field.getType()` [5](#0-4) .
- PHP native extension raises `"Cannot convert '%s' to %s"` with the actual stringified value on int64 conversion failure [6](#0-5) .
- Ruby JRuby `Utils.checkType` embeds a `given <class>` (less severe, only the class name, not the value) [7](#0-6) .

Meanwhile, Protobuf explicitly acknowledges the general risk class via the `debug_redact` field option, whose entire purpose is to prevent sensitive field values from being written into human-readable/debuggable output (logs). This is implemented in `TextFormat::GetRedactionState` / `TextFormat::Printer::TryRedactFieldValue`, which is consulted only when *printing* a message with `DebugString`/`PrintToString` [8](#0-7) . None of the parsing error-message construction sites above consult `debug_redact` (or any equivalent) before embedding the value, so a schema author who has annotated a field as sensitive gets no protection when that field's malformed value flows into a parser error that the calling application logs — the exact scenario the advisory describes.

### Impact Explanation
If a consuming application logs parse/conversion errors returned by Protobuf's TextFormat or JSON parsers (a routine and encouraged practice for debugging malformed-input incidents), a sensitive field value supplied in the request — including one the schema explicitly marks `debug_redact` — can be written verbatim into server logs, audit logs, or error-tracking systems with broader read access than the original request path. This matches CWE-532 exactly: confidentiality impact only, no integrity/availability impact, consistent with the CVSS vector in the report (C:H/I:N/A:N). The impact is bounded to Medium because it requires (a) the calling application to log the raised exception/error string, and (b) the offending field to actually be interpretable as sensitive (schema-annotated or otherwise).

### Likelihood Explanation
Likelihood is Medium: triggering the error paths only requires an ordinary client to submit a syntactically-parseable-but-type-mismatched value (e.g., a string where a bool/int/double is expected) through public `Parse`/`MergeFrom` JSON or TextFormat APIs — no privileged access needed. The remaining variable is whether the host application logs the returned exception, which is common but not guaranteed, and this is precisely the same caveat noted in the original OpenBao report (exposure is realized through server/audit logs, not the API return value itself).

### Recommendation
Extend the existing `debug_redact` / `TryRedactFieldValue` mechanism to cover error-message construction on the parsing side, not just printing, across TextFormat and JSON parsers (`text_format.cc`, `json/internal/parser.cc`, `json_format.py`, `JsonFormat.java`, and the PHP/Ruby native converters). Concretely: before formatting a conversion-failure message with the value, check `FieldDescriptor::options().debug_redact()` (or an option that's applicable more generally when the concrete field is known) and substitute a placeholder (e.g., `<redacted>`) instead of the raw text; for cases where the target field type is not yet resolved (e.g., generic type errors before field identification), consider omitting the value from the message by default or gating its inclusion behind a caller-provided verbosity flag.

### Proof of Concept
1. Define a proto message with a `debug_redact`-annotated string/bytes field intended to carry a secret, e.g. `string password = 1 [debug_redact = true];`.
2. Send TextFormat input where that field is assigned a type-incompatible value, e.g. `password: true` for a message whose builder expects a `string`, or send JSON `{"password": {"actualSecret": "..."}}` against a schema expecting a scalar string.
3. Observe that `TextFormat::Parser::ParseFromString` (or `json_format.Parse` / `JsonFormat.parser().merge`) returns/raises an error string that contains the literal offending value (e.g., `Expected string, got: true` in C++ per [9](#0-8) , or the Python `ParseError` at [10](#0-9) ), despite the field being marked `debug_redact`.
4. Confirm (by inspection of `TextFormat::GetRedactionState`) that this redaction check is invoked only from the print/`DebugString` path [11](#0-10)  and never from the parse-error-construction call sites in step 3 — demonstrating the exact bypass: the sensitivity annotation exists but the value still reaches a message the caller is likely to log.

Note: I was unable to fully execute this PoC or search every downstream logging call site (e.g., how each language's server frameworks typically log these exceptions) due to tool/time limits; this assessment is based on static code inspection of the parser/exception-construction sites and the redaction machinery shown above, not a live log-capture experiment.

def _ConvertInteger(value):
  """Convert an integer.

  Args:
    value: A scalar value to convert.

  Returns:
    The integer value.

  Raises:
    ParseError: If an integer couldn't be consumed.
  """
  if isinstance(value, float) and not value.is_integer():
    raise ParseError("Couldn't parse integer: {0}".format(value))

  if isinstance(value, str) and value.find(' ') != -1:
    raise ParseError('Couldn\'t parse integer: "{0}"'.format(value))

  if isinstance(value, bool):
    raise ParseError(
        'Bool value {0} is not acceptable for integer field'.format(value)
    )

  try:
    return int(value)
  except ValueError as e:
    # Attempt to parse as an integer-valued float.
    try:
      f = float(value)
    except ValueError:
      # Raise the original exception for the int parse.
      raise e  # pylint: disable=raise-missing-from
    if not f.is_integer():
      raise ParseError(
          'Couldn\'t parse non-integer string: "{0}"'.format(value)
      ) from e
    return int(f)

TextFormat::RedactionState TextFormat::GetRedactionState(
    const FieldDescriptor* field) {
  auto options = field->options();
  auto state = TextFormat::RedactionState{options.debug_redact(), false};
  std::vector<const FieldDescriptor*> field_options;
  const Reflection* reflection = options.GetReflection();
  reflection->ListFields(options, &field_options);
  for (const FieldDescriptor* option : field_options) {
    auto result = TextFormat::IsOptionSensitive(options, reflection, option);
    state = TextFormat::RedactionState{state.redact || result.redact,
                                       state.report || result.report};
  }
  return state;
}
bool TextFormat::Printer::TryRedactFieldValue(
    const Message& message, const FieldDescriptor* field,
    BaseTextGenerator* generator, bool insert_value_separator) const {
  TextFormat::RedactionState redaction_state =
      DescriptorPool::MemoizeProjection(
          field, [](const FieldDescriptor* field) {
            return TextFormat::GetRedactionState(field);
          });
  if (redaction_state.redact) {
    if (redact_debug_string_) {
      IncrementRedactedFieldCounter();
      if (insert_value_separator) {
        generator->PrintMaybeWithMarker(MarkerToken(), ": ");
      }
      generator->PrintString(kFieldValueReplacement);
      if (insert_value_separator) {
        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {
          generator->PrintLiteral("\n");
        }
      }
      return true;
    }
  }
  return false;
}
