Based on my investigation, I found a concrete local analog in `IntentGatewayV2.sol`'s escrow-cancellation logic, where the same-chain cancel path bypasses the freeze/pause guard that gates all cross-chain escrow release paths.

### Title
Same-chain order cancellation bypasses host freeze state, allowing escrow withdrawal while the bridge is paused - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` releases escrowed order funds through the internal `withdraw()` function [1](#0-0) . For cross-chain orders, `withdraw()` is only reachable through `onAccept` (`RequestKind.RedeemEscrow`/`RefundEscrow`) or `onGetResponse`, both restricted to `onlyHost` and, critically, only invokable after a message has passed through `HandlerV2`'s `notFrozen(host)` modifier [2](#0-1)  which is applied to `handlePostRequests`, `handleGetResponses`, and both timeout handlers [3](#0-2) . This means whenever `EvmHost.setFrozenState` is set to `Incoming`/`All` (the bridge's emergency pause), cross-chain escrow redemption/refund is blocked [4](#0-3) .

However, `cancelOrder`'s same-chain branch (`orderSource == orderDest`) calls `withdraw(body, true)` **directly**, as a plain internal Solidity call within the same transaction — with no dependency on the host, the handler, or any frozen-state check at all [5](#0-4) . It only checks that the order hasn't already been filled and that the caller is the order owner.

### Finding Description
This mirrors the SYMM-IO bug class exactly: a newly-added/alternate execution path (`internalTransfer` in the original report; here, the same-chain leg of `cancelOrder`) performs the same fund-moving effect as the guarded primary paths (`RedeemEscrow`/`RefundEscrow` via ISMP), but omits the guard (`whenNotAccountingPaused` there; the host's `FrozenStatus` / `notFrozen` gate here). The guard exists specifically to halt fund movement system-wide during an incident, but this alternate path was not wired into that gate.

### Impact Explanation
When Hyperbridge operators freeze the host (e.g., in response to a detected proof-forgery or consensus attack) via `setFrozenState(FrozenStatus.All)` or `Incoming`, order owners can still call `cancelOrder` for same-chain orders and immediately pull their escrowed tokens/native value out of `IntentGatewayV2` through `withdraw()`, completely sidestepping the pause. This is unauthorized execution of a fund-release path during a state the protocol explicitly intended to be halted, matching the required impact class of "stealing or loss of funds / unauthorized transaction execution during a security pause."

### Likelihood Explanation
The path requires no relayer, prover, or privileged role — any unprivileged order owner (or an attacker who has placed a same-chain order) can trigger it at any time, including during an active freeze, since the only preconditions are `_filled[commitment] == address(0)` and caller-is-owner, both fully controllable by the attacker.

### Recommendation
Gate the same-chain `withdraw()` call in `cancelOrder` behind the same freeze-state check that protects the cross-chain paths — e.g., add a check against `IHost(host()).frozen()` (rejecting `Outgoing`/`All`, or whichever states are meant to also halt local settlement) before calling `withdraw(body, true)` in the `isSameChain` branch.

### Proof of Concept
1. User places a same-chain order via `placeOrder`, escrowing tokens in `IntentGatewayV2` [6](#0-5) .
2. Protocol admin detects an incident and calls `EvmHost.setFrozenState(FrozenStatus.All)` to halt bridge operations [4](#0-3) .
3. Any cross-chain redeem/refund attempt now reverts with `FrozenHost` because `HandlerV2.handlePostRequests`/`handleGetResponses` are guarded by `notFrozen(host)` [7](#0-6) .
4. The order owner instead calls `cancelOrder(order, options)` with `order.source == order.destination` (same-chain order). This enters the `isSameChain` branch, which only checks `_filled[commitment] == address(0)` and ownership, then calls `withdraw(body, true)` directly — releasing escrowed funds with the host still fully frozen [8](#0-7) .

Note: I was unable to fully inspect `HyperApp.sol`'s `onlyHost` modifier body in this session (only located that it exists, 9 references) to confirm it never independently checks frozen state; this doesn't affect the finding since the same-chain `cancelOrder` branch bypasses `onlyHost`/host entirely by calling the internal `withdraw()` directly.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
