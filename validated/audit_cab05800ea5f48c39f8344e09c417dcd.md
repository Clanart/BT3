### Title
Stale-state balance/amount check for GaslessSwapTx in tx pool admission causes gasless swap failure and un-repaid gas lending - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The gasless module validates a `GaslessSwapTx`'s repayment feasibility (`checkBalanceForSwap`) against the **current** chain state at the moment the transaction enters the tx pool, using a `GetAmountIn` call against the swap router's live exchange rate. This exactly mirrors the audited Rio bug pattern: a value is computed from a "current" but transient market/exchange state and is relied upon later, at a different point in time (block building/execution), without being re-validated against the state that actually exists at execution time.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` computes `requiredAmountIn` from `routerContract.GetAmountIn(nil, token, minAmountOut)` and compares it against the sender's declared `AmountIn`, and separately checks `tokenContract.BalanceOf`/`Allowance`: [1](#0-0) [2](#0-1) 

This check is done at tx-pool admission time (`GetCheckBalance`), when a module recognizes the tx and the pool skips its own generic balance check: [3](#0-2) [4](#0-3) 

However, actual execution of the bundle (`LendTxGenerator`, optional `ApproveTx`, `SwapTx`) happens later, during block building, via `ExtractTxBundles`: [5](#0-4) 

Between admission (pool `Ready`/`AddLocal`) and inclusion in a block, the pool's `updateAddresses`/state can change (other swaps against the same DEX pool alter the exchange rate that `GetAmountIn` depends on, or the sender's token balance/allowance can decrease from other pending/queued transactions). Because there is no re-validation of `minAmountOut`/`amountRepay`/`amountIn` sufficiency at execution time beyond what the EVM itself naturally reverts on, a swap that passed the pool's admission check can fail at execution once actually run, exactly analogous to `requestWithdrawal()`'s stale `availableShares` check versus `rebalance()`'s later re-check in the Rio report — the check-time state and the settlement-time state diverge.

Critically, the `LendTxGenerator` transaction that fronts the gas fee for the user is prepended in the bundle before the swap: [6](#0-5) 
The `GaslessTx` design fundamentally depends on the swap succeeding so the lender (block proposer) is repaid through `swapForGas`'s `amountRepay`. If the swap tx, once actually executed against block-time state, reverts (e.g. because the DEX price moved unfavorably relative to the stale `minAmountOut`/`amountRepay` bound checked at admission, or because balance/allowance dropped due to other transactions from the same sender queued earlier in the same block), the `LendTxGenerator` transaction that already paid gas on the user's behalf executes regardless — this is a fee-delegation/gas-lending settlement whose repayment guarantee (verified via a stale check) can fail to materialize at settlement time.

### Impact Explanation
This is a fee-delegation/gasless-settlement analog of the "stale computed value used across a time-of-check/time-of-use gap" bug class in the report. If a `GaslessSwapTx` is admitted based on a `checkBalanceForSwap` that passed against block N's state, but is later included in block N+k (or after other txs mutate router/token state within the same block), the proposer's lent gas is not repaid, resulting in a stuck/failed gasless flow and potential unrecoverable value transfer to the proposer (gas spent lending) without repayment — a fee-delegation abuse/loss vector reachable by any unprivileged gasless-transaction submitter (or an adversarial submitter deliberately racing state changes to exploit the gap).

### Likelihood Explanation
The condition requires only that DEX-related state (exchange rate, sender balance/allowance) change between tx-pool admission and block inclusion — a naturally occurring and even adversarially triggerable condition (e.g., a user or third party submitting a competing swap against the same pool, or manipulating the sender's own balance/allowance via another transaction) since `checkBalanceForSwap`'s `GetAmountIn` call reads live, mutable DEX contract state rather than a value pinned/re-verified at execution.

### Recommendation
Re-validate the swap's amount sufficiency (or fail gracefully without penalizing the lender) at actual execution time within the bundle, not solely at tx-pool admission. Options include: (1) re-checking `GetAmountIn`/balance/allowance immediately before block inclusion in `ExtractTxBundles`, (2) making the lend transaction's repayment atomic/conditional on the swap's success within the same bundle so a failed swap does not leave the lender uncompensated, or (3) tightening the KIP-247 `GaslessSwapRouter` contract logic so `swapForGas` can only be included/settled if the check performed at proposal time still holds at inclusion time (e.g., bounding staleness with a stricter deadline/tolerance check inside the contract itself rather than relying on the client-side pool check).

### Proof of Concept
Conceptual: (1) User submits `GaslessApproveTx` + `GaslessSwapTx` with `minAmountOut` computed against current DEX price; `checkBalanceForSwap` passes because `requiredAmountIn <= AmountIn` at that instant. (2) Before this bundle is included in a block, another transaction (attacker or unrelated user) trades against the same pool, shifting the exchange rate so that, at actual execution, the router's real `amountOut` for `AmountIn` falls below `minAmountOut`, causing `swapForGas` to revert per its own internal checks. (3) The prepended `LendTxGenerator` transaction (funding the user's gas) still executes and is included, since bundle execution order does not roll back on a later tx's revert unless explicitly designed to. (4) Proposer is left unrepaid for the fronted gas, or the whole bundle is dropped, denying the user's transaction inclusion despite having passed all pool-level admission checks — precisely the check/use timing mismatch described in the reference report.

Note: The exact atomicity/rollback semantics of a multi-tx bundle in the presence of a mid-bundle revert (whether `LendTxGenerator`'s effect persists if a later tx in the same bundle reverts) could not be fully confirmed from the indexed code alone; the block-building/worker bundle-execution logic (`work/builder/builder.go`, `work/worker.go`) governs this and should be reviewed directly to confirm whether such partial-bundle-failure states are possible in practice.

func (g *GaslessModule) GetCheckBalance() func(tx *types.Transaction) error {
	return func(tx *types.Transaction) error {
		if approveArgs, ok := decodeApproveTx(tx, g.signer); ok {
			return g.checkBalanceForApprove(approveArgs)
		}
		if swapArgs, ok := decodeSwapTx(tx, g.signer); ok {
			return g.checkBalanceForSwap(swapArgs, tx.Nonce())
		}
		return errors.New("not a gasless transaction") // should not happen because IsModuleTx is called before GetCheckBalance
	}
}

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
