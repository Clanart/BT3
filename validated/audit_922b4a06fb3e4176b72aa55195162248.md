### Title
`is_deposit_valid` Accepts Deposit Transactions Below `finality_depth` Confirmations, Enabling Reorg-Induced Move-Tx Invalidation - (File: `core/src/verifier.rs`)

### Summary

`Verifier::is_deposit_valid` only checks that the deposit transaction is confirmed (has a blockhash) and that its block height is ≥ `start_height`. It never checks that the deposit has reached `finality_depth` confirmations. Because `new_deposit` can be called immediately after a single confirmation, a Bitcoin reorg of any depth ≥ 1 that occurs before the move-tx is confirmed will remove the deposit UTXO from the canonical chain, making the already-signed move-tx unspendable and locking the user's bridged BTC for up to `user_takes_after` blocks (~33 hours on mainnet).

### Finding Description

`ProtocolParamset.finality_depth` is the bridge's canonical reorg-safety parameter. It is correctly enforced in the bitcoin-syncer event pipeline and in the tx-sender confirmation tracker, but it is **never consulted** during deposit validation.

In `core/src/verifier.rs`, `is_deposit_valid` (called from both `deposit_sign` and `deposit_finalize`) performs the following on-chain checks for the deposit transaction:

```rust
// line 712 – only checks "is it in any block at all?"
let blockhash = tx_info.blockhash.ok_or_else(|| {
    BridgeError::InvalidDeposit("Deposit transaction is not confirmed".to_string())
})?;
// line 724 – only checks height >= start_height
if (block_height as u32) < start_height { ... }
``` [1](#0-0) 

There is no guard of the form `tx_info.confirmations >= self.config.protocol_paramset().finality_depth`. The `finality_depth` field is defined and documented in `ProtocolParamset`: [2](#0-1) 

and is correctly used in the tx-sender: [3](#0-2) 

and in the bitcoin-syncer consumer: [4](#0-3) 

but is absent from the deposit-signing gate.

The aggregator's `new_deposit` handler also calls `get_blockhash_of_tx` (a single-confirmation check) to derive `deposit_blockhash` for the sighash stream, with no finality guard before dispatching to verifiers: [5](#0-4) 

The deployed testnet4 paramset sets `finality_depth = 6`: [6](#0-5) 

and the `REGTEST_PARAMSET` constant sets it to 5: [7](#0-6) 

meaning a deposit with only 1 confirmation passes `is_deposit_valid` even when the operator has configured a 5- or 6-block finality requirement.

### Impact Explanation

When a reorg of depth ≥ 1 removes the deposit transaction from the canonical chain after verifiers have signed the move-tx:

1. The deposit UTXO no longer exists on the canonical chain.
2. The move-tx (which spends that UTXO) is permanently invalid until the deposit tx is re-mined.
3. The tx-sender cannot broadcast the move-tx; the deposit is stuck.
4. The user's BTC remains locked in the deposit taproot address until the `user_takes_after` timelock (200 blocks, ~33 hours on mainnet) expires, at which point the user can reclaim via the recovery path.

If the deposit tx is never re-included (e.g., the UTXO was double-spent in the reorg), the user must wait the full `user_takes_after` window to recover their BTC. This constitutes a temporary but material lock of bridged BTC controlled by a bridge-managed UTXO.

### Likelihood Explanation

Bitcoin mainnet reorgs of depth ≥ 1 are rare but documented. On testnet4, reorgs are more frequent. Because `new_deposit` can be called by any user immediately after a single confirmation (the CLI and backend impose no additional wait), the window between "1 confirmation" and "finality_depth confirmations" is always open. Any reorg within that window triggers the impact. The likelihood is low on mainnet but non-negligible on testnet4 and any future deployment on chains with higher reorg rates.

### Recommendation

Add a confirmation-depth guard inside `is_deposit_valid` in `core/src/verifier.rs`, immediately after the existing `blockhash` check:

```rust
let confirmations = tx_info.confirmations.unwrap_or(0);
let required = self.config.protocol_paramset().finality_depth;
if confirmations < required {
    return Err(BridgeError::InvalidDeposit(format!(
        "Deposit transaction has only {confirmations} confirmation(s); \
         {required} required (finality_depth)"
    )));
}
```

Apply the same guard in the aggregator's `new_deposit` before dispatching to verifiers, so the error is surfaced early without consuming verifier resources.

### Proof of Concept

1. Deploy the bridge with `finality_depth = 6` (testnet4 config).
2. User broadcasts a deposit tx; it receives exactly 1 confirmation.
3. User (or backend) immediately calls `new_deposit` on the aggregator.
4. `is_deposit_valid` passes: `blockhash` is set, `block_height >= start_height`. No confirmation-count check is performed.
5. All verifiers sign the move-tx via `deposit_sign` / `deposit_finalize`.
6. A Bitcoin reorg of depth 1 occurs (removes the block containing the deposit tx).
7. The deposit UTXO no longer exists on the canonical chain.
8. The tx-sender attempts to broadcast the move-tx; it is rejected by all nodes (`missing inputs`).
9. The move-tx can never be confirmed; the user's BTC is locked in the deposit address for `user_takes_after` = 200 blocks (~33 hours).

The root cause is the missing `confirmations >= finality_depth` check at: [1](#0-0)
