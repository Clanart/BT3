### Title
Unchecked KIP-71 `LowerBoundBaseFee`/`UpperBoundBaseFee` governance parameters allow inverted or degenerate base-fee bounds - (File: kaiax/gov/param.go)

### Summary
The Kaia governance parameter registry (`kaiax/gov/param.go`) defines `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` with `FormatChecker: noopFormatChecker`, meaning any `uint64` value submitted through a governance vote is accepted as-is, with no check that `LowerBoundBaseFee <= UpperBoundBaseFee` or that either value is sane relative to `BaseFeeDenominator`/`GasTarget`. This is analogous to the reported `ConcentratedLiquidityPool.initialPrice` bug: a governance-set boundary parameter that feeds directly into a core pricing/state-transition function without range validation, capable of putting the pool (here, the base-fee mechanism) into a state where downstream logic misbehaves for all subsequent blocks/transactions.

### Finding Description
`Params[Kip71LowerBoundBaseFee]` and `Params[Kip71UpperBoundBaseFee]` both use `noopFormatChecker`, which always returns `true` [2](#0-1) , unlike other parameters that do enforce format/range checks, e.g., `IstanbulCommitteeSize` requires `v > 0` and `GovernanceGovernanceMode` restricts to enumerated strings [3](#0-2) . These two KIP-71 values are accepted independently and stored into `ParamSet`, which is later converted with `ToKip71Config()` [4](#0-3)  and consumed directly by `KIP71Config.NextMagmaBlockBaseFee`, the core Magma dynamic-base-fee calculation used both to build blocks and to validate headers (`VerifyMagmaHeader`) [5](#0-4) .

If governance approves `LowerBoundBaseFee > UpperBoundBaseFee` (a "PGA" analog of `initialPrice` outside `[MIN_SQRT_RATIO, MAX_SQRT_RATIO]`), the clamping logic in `NextMagmaBlockBaseFee` becomes internally inconsistent:
- `parentBaseFee` is clamped: `if parentBaseFee >= upperBoundBaseFee { parentBaseFee = upperBoundBaseFee } else if parentBaseFee <= lowerBoundBaseFee { parentBaseFee = lowerBoundBaseFee }` [6](#0-5) .
- With `lowerBoundBaseFee > upperBoundBaseFee`, this branch can force `parentBaseFee` to the (now larger) `lowerBoundBaseFee` even though it is "above" the nominal upper bound, and the subsequent increase/decrease branches (lines 92-128) compare against mismatched bounds, producing a `nextBaseFee` outside any sane range or oscillating unpredictably block-to-block.
- Every subsequent block's header validation via `VerifyMagmaHeader` recomputes the same (inconsistent) `expectedBaseFee` from `NextMagmaBlockBaseFee`, so it will still "agree" with itself deterministically across honest nodes — but the resulting base fee can be economically nonsensical (e.g., permanently pinned to an extreme value), which can lock out normal transactions whose gas price cannot satisfy the base fee, or make fees trivially cheap, both of which alter fee-payment economics network-wide.

The `param.go` FormatChecker mechanism is the sole gate before a governance vote is accepted into `ParamSet` (see `PartialParamSet.Add`, which calls `Canonicalizer` then requires `param.FormatChecker(cv)` before storing the value) [7](#0-6) . Because `noopFormatChecker` unconditionally passes, no single-field or cross-field bound is enforced at admission time for these two parameters.

### Impact Explanation
An inconsistent or degenerate base-fee bound pair is a governance-level parameter change (reachable via any authorized governance vote transaction, which in a "single" governance mode is a normal transaction path from the governing node, or via `GovParamContract`/`headergov` votes) that corrupts the base-fee derivation used for every block after the fork activation. This can result in:
- Base fee locked to an economically extreme value, effectively pricing out ordinary transactions (denial of normal fee-based transaction admission) or making blocks arbitrarily cheap (fee-avoidance), both of which are fee-accounting abuses network-wide, not merely a resource/DoS issue local to one node.
- Divergent economic behavior versus intended KIP-71 design, since `NextMagmaBlockBaseFee` and `VerifyMagmaHeader` are core to both block assembly and header validation of every full node — an incorrect (but self-consistent) invariant would still be accepted by all honest nodes, i.e. the chain would silently operate on invalid fee economics without any consensus-level error being raised.

This rises to Medium/High severity because it affects the economic integrity of every transaction's fee handling chain-wide following a governance parameter change, analogous to how an unchecked `initialPrice` locked an entire pool from usability in the original report.

### Likelihood Explanation
The likelihood depends on governance being willing/able to submit such a vote. In "single" governance mode, a single governing node's vote transaction is sufficient; there is no automatic validation preventing `LowerBoundBaseFee > UpperBoundBaseFee`, no minimum/maximum sanity bound, and no cross-parameter validation, so a compromised, buggy, or malicious governing account (a normal transaction sender in the governance path, not a privileged consensus role) could set these values in a single transaction. Given the existing pattern in `param.go` where other params (e.g., `IstanbulCommitteeSize`, `RewardRatio`) do enforce such checks, the absence here appears to be an oversight rather than an intentional design decision.

### Recommendation
Add a `FormatChecker` for `Kip71LowerBoundBaseFee` and `Kip71UpperBoundBaseFee` (or a cross-field validation step in `PartialParamSet.Add`/`ParamSet` finalization) that enforces `LowerBoundBaseFee <= UpperBoundBaseFee`, and ideally bounds both against sane minimum/maximum absolute values (analogous to checking `MIN_SQRT_RATIO <= initialPrice <= MAX_SQRT_RATIO` in the original report), before the vote is accepted into `ParamSet`.

### Proof of Concept
1. As the governing node (single governance mode), submit a governance vote setting `kip71.lowerboundbasefee = 750000000000` and `kip71.upperboundbasefee = 25000000000` (i.e., swapped relative to the sane defaults) [1](#0-0) .
2. Because both use `noopFormatChecker`, `PartialParamSet.Add` accepts both values without complaint [7](#0-6) .
3. Once the vote is finalized into `ParamSet` and applied to `KIP71Config`, subsequent blocks call `NextMagmaBlockBaseFee` with `lowerBoundBaseFee=750000000000` and `upperBoundBaseFee=25000000000` [8](#0-7) ; the clamp logic at lines 82-86 now clamps toward the (larger) "lower" bound whenever `parentBaseFee < 25000000000`, and the increase/decrease branches compare against mismatched thresholds, producing a stable but incorrect (extremely high) base fee for all subsequent blocks — verifiable by unit-testing `NextMagmaBlockBaseFee` with swapped bound values and observing the returned base fee exceeds any economically intended value, matching the pattern already exercised by `TestEvenBaseFee`'s "monkey test" cases with arbitrary bound values [9](#0-8) .
