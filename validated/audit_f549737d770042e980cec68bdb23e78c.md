### Title
Permissionless `donateRewards` lets an attacker force premature reward flushing to snipe bribe yield - (File: `rewards/BaseRewardPoolV2.sol`, inherited by `rewards/BribeRewardPool.sol`)

### Summary
`BaseRewardPoolV2.donateRewards` has no access control beyond requiring the token to already be a registered reward token, and it immediately calls `_provisionReward`, which flushes `rewards[_rewardToken].queuedRewards` into `rewardPerTokenStored` using whatever `totalStaked()` (i.e. `totalSupply`) happens to be at that instant. Since `BribeRewardPool.totalSupply` is driven purely by `WombatBribeManager.vote()` calling `stakeFor`/`withdrawFor` with no lock or cooldown, an attacker can vote a large delta into a pool holding a large unsettled `queuedRewards` balance, immediately call `donateRewards` to force the flush while they dominate `totalStaked()`, claim the reward, and then unvote — capturing yield that should have accrued to genuine, sustained voters.

### Finding Description
`donateRewards` is public and only checks `isRewardToken[_rewardToken]`: [1](#0-0) 

It forwards straight into `_provisionReward`, which — when `totalStaked() != 0` — drains all of `queuedRewards` into `rewardPerTokenStored`, weighted by whatever `totalStaked()` is at that exact call: [2](#0-1) 

`BribeRewardPool` inherits this unchanged and defines `totalStaked()` as `totalSupply`, which is only ever mutated by `stakeFor`/`withdrawFor`, both restricted to `onlyOperator` (the `WombatBribeManager`): [3](#0-2) 

Critically, `stakeFor`/`withdrawFor` are reachable by any vlMGP holder through `WombatBribeManager.vote()`, with no minimum holding period, cooldown, or restriction preventing a same-block stake-then-unstake: [4](#0-3) 

Exploit flow:
1. A pool accumulates a large `queuedRewards` balance for a bribe token (e.g., because `totalStaked()` was 0, or bribes queued via the manager's `queueNewRewards` path have not yet been flushed by `castVotes`).
2. Attacker calls `vote(lp, +largeDelta)`, which invokes `IBribeRewardPool(pool.rewarder).stakeFor(attacker, largeDelta)`. This runs `updateRewards` first (snapshotting the attacker's `userRewardPerTokenPaid` at the pre-flush value) and then inflates `totalSupply`.
3. Attacker calls `donateRewards(tinyAmount, _rewardToken)` on the pool's rewarder. Since `totalStaked() != 0`, this immediately flushes the entire pre-existing `queuedRewards` into `rewardPerTokenStored`, weighted by `totalStaked()` which is now dominated by the attacker's fresh, large stake.
4. Attacker's `earned()` for that token jumps because `rewardPerToken(_rewardToken)` increased sharply while their `userRewardPerTokenPaid` was still at the old, low value.
5. Attacker claims via the manager's `claimBribe`/`getReward` path, then calls `vote(lp, -largeDelta)` to unvote and reclaim their vlMGP — all within the same transaction/block or a very short window.

No existing modifier prevents this: `donateRewards` has no `onlyManager`/`onlyOperator` restriction, `stakeFor`/`withdrawFor` have no time lock, and the `_provisionReward` accounting has no protection against being triggered opportunistically at a caller-chosen `totalStaked()` value.

### Impact Explanation
This lets an unprivileged attacker redirect a disproportionate share of previously-queued bribe rewards to themselves by momentarily inflating their vote share right before forcing a flush, at the expense of the legitimate, sustained voters who should have earned that yield through the normal `castVotes` cadence. This matches "High - Theft of unclaimed yield": the attacker extracts value that was economically owed to other stakers/voters, and those voters permanently lose their proportional share of the already-provisioned reward.

### Likelihood Explanation
The precondition (a pool holding a large unsettled `queuedRewards` balance) is a normal, expected state in this system since bribes are periodically queued and only flushed on `castVotes`/next `_provisionReward` call, and `totalStaked()` for a given pool can be small or zero between voting cycles. The attacker only needs enough vlMGP voting power to dominate `totalStaked()` at the moment of the flush and a small amount of the reward token to satisfy `donateRewards`'s transfer, both of which are attacker-obtainable without any privileged role. The attack is repeatable across pools and reward tokens, and there's no rate limit or cooldown blocking repeated exploitation.

### Recommendation
Restrict `donateRewards` (and any code path reaching `_provisionReward`) so that the flush of `queuedRewards` cannot be triggered by an arbitrary caller at an arbitrary moment — e.g., require `onlyManager`/`onlyOperator` for `donateRewards`, or decouple "accepting a donation" (transfer only) from "flushing/distributing" so that distribution logic is only ever invoked from the protocol's controlled harvest/vote-casting path. Additionally, consider adding a minimum vote-holding duration or preventing the same-transaction stake→flush→unstake sequence to eliminate flash-vote sniping.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`/`WombatBribeManager`/`BribeRewardPool` stack (or a minimal harness around `BribeRewardPool` + `BaseRewardPoolV2`) with a bribe reward token registered.
2. Simulate a state where `rewards[_rewardToken].queuedRewards` is large (e.g., call `queueNewRewards` while `totalSupply == 0`, or as the manager while another pool holds zero votes).
3. Run scenario A ("split calls"): attacker calls `vote(lp, +X)` (stakes X), then immediately calls `donateRewards(1, _rewardToken)`, then reads `earned(attacker, _rewardToken)` and captures `rewards[_rewardToken].queuedRewards`/`rewardPerTokenStored`/`totalSupply` at that point; then attacker calls `vote(lp, -X)` to unvote and claims reward.
4. Run scenario B ("single settled call"): same total economic action but performed by the legitimate flow only (e.g., `queueNewRewards` flushed naturally via `castVotes` after normal voter participation, without attacker's opportunistic stake/donate/unstake sequence).
5. Assert that in scenario A the attacker's claimed reward and the `rewardPerTokenStored`/`queuedRewards` state diverge from scenario B — showing the attacker captured yield disproportionate to their actual voting duration/share, confirming `queuedRewards` and `totalStaked()`-at-flush are not reconciled against a consistent, vote-driven invariant.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
