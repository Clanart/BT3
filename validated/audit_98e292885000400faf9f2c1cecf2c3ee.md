### Title
`ThresholdKeys::read` enables quadratic-CPU denial of service via attacker-controlled `n`/`t` with Lagrange interpolation - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` (each a u16, up to 65535) and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for every participant `1..=t`. Under `Interpolation::Lagrange`, each `interpolation_factor` call is O(t) field multiplications plus one inversion, making `ThresholdKeys::new` O(t²) — roughly 4.3 billion field multiplications plus 65535 inversions for a maximally crafted ~2 MB input, with no rate limiting or size cap beyond the byte stream itself.

### Finding Description
The deserialization path is:

- `ThresholdKeys::read` reads `t`, `n`, `i` as three u16s, then the interpolation tag, then `n` scalars/points, and finally calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:591-631`).
- `ThresholdKeys::new` builds `t = 1..=params.t()` and computes `group_key` by summing `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` for each of the `t` participants (`crypto/dkg/src/lib.rs:376-378`).
- `Interpolation::Lagrange::interpolation_factor` loops over every entry in `included` (length `t`), performing ~2 field multiplications per entry and one `invert()` per call (`crypto/dkg/src/lib.rs:229-247`).

For a crafted message declaring `n = 65535`, `t = 65535`, interpolation byte `1` (Lagrange), followed by `n` validly-encoded group elements and one scalar, the reader performs t × t ≈ 4.3×10⁹ scalar multiplications and t ≈ 65535 field inversions before returning. The only structural requirement is `t <= n` (`ThresholdParams::new`, `crypto/dkg/src/lib.rs:171-173`), so the worst case is fully reachable. The input cost to the attacker is ~2 MB of (arbitrary, since only encoding-validity is checked) point encodings; the victim's cost is quadratic in `t`.

This mirrors the referenced Mealie bug class: a single small, unauthenticated request triggers CPU-bound work far disproportionate to its size, and there is no rate limiting, work budget, or sanity cap on `n`/`t` anywhere on this path. Repeated submissions trivially saturate all cores allocated to a process that deserializes `ThresholdKeys` from untrusted bytes.

### Impact Explanation
Any code path feeding untrusted bytes into `ThresholdKeys::read` (or equivalently `ThresholdKeys::new` with an attacker-chosen `ThresholdParams` and Lagrange interpolation) can be driven into ~10⁹–10¹⁰ field operations per call. An unprivileged party supplying such bytes — e.g., wherever serialized `ThresholdKeys` or DKG material is consumed — can pin a CPU core per request and sustain the load indefinitely by repeating the input, denying service to signing, verification, or DKG completion for all other participants. No secret material or protocol privilege is required: the payload consists solely of public-parameter-shaped bytes.

### Likelihood Explanation
Exploitation requires only that the attacker can cause a target to deserialize attacker-controlled bytes via `ThresholdKeys::read`, which is explicitly one of the exposed untrusted-input entry points. The crafted input is trivially constructible: valid `t`/`n`/`i` u16s, a `1` interpolation tag, and `n` canonical point encodings (even repeated generator encodings suffice — the interpolation cost is paid before any share validity matters). Cost asymmetry is extreme: ~2 MB in, ~4.3×10⁹ field multiplications plus 65535 inversions out. No conditions on protocol state are needed since the expensive work happens inside the constructor before any semantic use of the keys.

### Recommendation
- Enforce a hard upper bound on `n`/`t` accepted from untrusted inputs (a protocol-level `MAX_PARTICIPANTS`) inside `ThresholdKeys::read` and `ThresholdParams::new`, well below the point where O(t²) interpolation becomes prohibitive.
- Alternatively, compute the group key incrementally / with a single multiexp, and batch the Lagrange denominator inversions via a Montgomery trick so `ThresholdKeys::new` is O(t) rather than O(t²), removing the quadratic amplification even if large `n` is permitted.
- Cap the total byte length consumed by `ThresholdKeys::read` before allocating `Vec::with_capacity(n)` and reading `n` group elements.

### Proof of Concept
```rust
// Conceptual PoC: craft a ThresholdKeys blob that forces ~4.3e9 field muls.
// For a Ciphersuite C with 32-byte encodings:
let n: u16 = u16::MAX;           // 65535
let t: u16 = u16::MAX;           // t <= n required
let mut buf = Vec::new();
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(1u16.to_le_bytes());  // i = Participant(1)
buf.push(1u8);                   // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 1 ..= n {
  buf.extend(C::generator().to_bytes().as_ref()); // verification_shares
}
// ThresholdKeys::read(&mut buf.as_slice())
//   -> reads n points (cheap), then ThresholdKeys::new computes
//      interpolation_factor(i, 1..=t) for all t participants:
//      t iterations x O(t) muls + one invert() each
//      => ~4.3e9 scalar muls + 65535 inversions per ~2 MB input.
```
The same quadratic cost is re-incurred by `ThresholdView::view`, which calls `interpolation_factor` once per included participant over an `included` list of length up to `n` (`crypto/dkg/src/lib.rs:500-507`), so any subsequent view construction repeats the denial-of-service amplification.
