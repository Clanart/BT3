### Title
`ReceivedOutput::read` accepts an attacker-supplied offset/script/outpoint tuple with no consistency check, letting funds be reported received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The RFP bug class is a registered value (`proposalBid`) that can be swapped after selection because `_allocate` never re-checks the committed value. The Serai analog is `Scanner`/`ReceivedOutput`: `Scanner::register_offset` binds a scalar offset to a specific `script_pubkey` at registration time, but `ReceivedOutput::read` deserializes `(offset, TxOut, outpoint)` from untrusted bytes without re-deriving or verifying that `offset` actually produces `output.script_pubkey`, or that the `outpoint` exists. The pairing decided at registration is therefore not enforced when the object is later consumed, exactly like `_allocate` trusting `recipient.proposalBid` instead of the bid accepted at selection time.

### Finding Description
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` table populated by `register_offset`, which only inserts offsets after computing `p2tr_script_buf(self.key + GENERATOR * offset)` (mod.rs:180-196). `scan_transaction` only ever emits `ReceivedOutput`s whose `offset` genuinely derives the output's `script_pubkey` (mod.rs:199-214). However, the serialized `ReceivedOutput` is also a network/IPC message: `ReceivedOutput::read` (mod.rs:122-134) calls `Secp256k1::read_F` for the offset and consensus-decodes an arbitrary `TxOut` and `OutPoint`, then returns the tuple verbatim. There is no check that `p2tr_script_buf(key + G*offset) == output.script_pubkey`, no check that the outpoint was ever observed in a scanned block, and no binding between the three fields. Whoever consumes a deserialized `ReceivedOutput` (the `send` path in `networks/bitcoin/src/wallet/send.rs` applies `offset` as the signing-key tweak for the claimed prevout) will sign for a key that does not match the real output's script, or for an outpoint that never carried the claimed value.

### Impact Explanation
An unprivileged party able to feed bytes to `ReceivedOutput::read` (an explicitly in-scope untrusted-input surface) can report outputs that were never validly received: either a fabricated `outpoint`/`value` pair claiming deposits that do not exist, or a mismatched `offset`/`script_pubkey` pair whose claimed funds cannot be spent because the offset does not derive the output's key. In the first case the system credits/mints against phantom UTXOs; in the second, real outputs are recorded with an unusable spend key, producing funds reported received that are not spendable and requiring an out-of-band recovery path. Both are the direct analog of a recipient receiving funding under terms (`proposalBid`) other than those the allocator approved.

### Likelihood Explanation
Reachability is high: `ReceivedOutput::read` is a public deserialization API over bytes the caller does not authenticate, and the struct itself documents no invariant binding the fields. Exploitation only requires control of the byte stream between scanner and consumer (relay, queue, or reconstructed message); no validator key, collusion, or secret knowledge is needed. Whether downstream code fully trusts the claimed value determines whether the result is phantom crediting or merely unspendable outputs; the missing check makes both possible, so a Medium rating matches the source report.

### Recommendation
Bind the registration-time mapping to the deserialized object, mirroring the report's Option 2: after `ReceivedOutput::read` (or before use in the spend path), recompute `p2tr_script_buf(scanner.key + GENERATOR * offset)` and reject the output unless it equals `output.script_pubkey`, and require proofs/confirmation that the claimed `outpoint` was actually produced by `scan_transaction`/`scan_block` (e.g., only accept `ReceivedOutput`s constructed by the scanner, or carry the scanner key context and enforce `output.script_pubkey == scripts[...]` lookup). Alternatively serialize only the `outpoint` and resolve `offset`/`TxOut` from the scanner's own verified table at use time, so the "accepted bid" cannot be swapped between registration and allocation.

### Proof of Concept
Conceptual: an attacker serializes `ReceivedOutput { offset: s_a, output: TxOut { value: 1_000_000_000, script_pubkey: P }, outpoint: fake }` where `s_a` is a registered offset whose derived script is `S_a != P`, or where `fake`/`P` simply never appeared on-chain. `ReceivedOutput::read` returns it without error (mod.rs:122-134). A consumer applying `offset` as the spend tweak produces a signature for key `key + G*s_a`, which does not control `P`; if `P` was fabricated entirely, the system has recorded a deposit that cannot be spent and does not exist — i.e., value allocated under terms different from what was committed, with no check equivalent to `acceptedRecipientProposalBid == recipient.proposalBid`.
