### Title
Permissionless `BandwidthManager.purchase()` lets any unrelated caller evict a victim app's paid bandwidth subscriptions via the shared FIFO cap - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`purchase()` on `BandwidthManager.sol` is a fully public, unauthenticated entry point that lets **any address** credit a subscription into an **arbitrary** `(chain, app)` bucket on `pallet-bandwidth`, because the target bucket is keyed purely from attacker-supplied `app`/`chain` fields in the message body, not from `msg.sender` or `request.source`. [1](#0-0)  Each `(chain, app)` bucket is a `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024`; once full, every new push unconditionally evicts the oldest entry regardless of its value or owner. [2](#0-1)  Because the write path into a victim's bucket is open to anyone, an attacker can spam cheap purchases targeting a victim app's bucket until it fills to the cap, then continue pushing to permanently evict the victim's real, already-paid-for subscriptions. This mirrors the SafeGuardFactory bug's core invariant break: an unprivileged actor pre-writes into a shared ledger/registry that a legitimate party depends on remaining intact, destroying the legitimate entry.

### Finding Description
The pallet's `Allowance` storage map is keyed by `(app_chain, app)` — deliberately *not* by payer — to support the "sponsorship" feature (any chain can top up any app anywhere). [3](#0-2)  `purchase()` takes `app` and `chain` as plain calldata parameters with no validation tying them to the caller, and dispatches a credit message that lands in that exact bucket. [1](#0-0)  On the pallet side, `push_subscription` appends every purchase into `Allowance::<T>::mutate(app_chain, app, ...)`; when the list is already at 1024 entries, it unconditionally removes index 0 (the oldest entry) — with no check on who purchased it or how much value it holds — before pushing the new one. [4](#0-3)  This is the same purchase path used for both real purchases and `force_credit`, so there is exactly one insertion routine and one eviction policy. [2](#0-1) 

The documentation itself only anticipates *self*-inflicted eviction from "pathological repeat-buy behavior" by the app's own operator, [5](#0-4)  but the sponsorship model explicitly allows a payer on any chain to target any `(chain, app)` bucket, and nothing restricts that payer's relationship to the app being credited. [6](#0-5)  An attacker therefore does not need to compromise, front-run, or collude with anyone — they simply call the public `purchase()` function 1024+ times with cheap tier/month combinations addressed at the victim's `(chain, app)` pair to force the victim's real, larger subscriptions out of the front of the queue.

### Impact Explanation
This is a direct loss-of-funds bug matching the bounty's "bandwidth balances must move exactly once and only to the rightful beneficiary" criterion. A victim app that paid real fee-token amounts for a large/long-duration tier can have that entire allowance silently evicted and destroyed (`SubscriptionEvicted`) by a completely unrelated, unprivileged third party, at a cost the attacker controls (minimal tier price × 1 month per push). The victim's paid funds converted into bandwidth are permanently lost with no recourse — the pallet gives no priority, ownership check, or minimum-value floor to protect existing entries from a griefer, unlike a normal escrow/registry design that should bind writes to the rightful party. This is not front-run-only: the attack works at any time against any already-credited or future bucket, independent of transaction ordering against a specific victim transaction.

### Likelihood Explanation
Likelihood is high for any moderately funded attacker: the entry point (`purchase()`) is completely public, requires no special role, no relayer/prover/admin collusion, and no knowledge of a pending transaction to race. The only cost is the cheapest tier's price × the number of pushes needed to fill/roll the target bucket (bounded, deterministic, and paid in the host fee token) — an economic cost that is generally far smaller than the value of a competitor's or victim's larger, longer-duration subscription being destroyed, especially if timed against an app whose bucket is only lightly populated.

### Recommendation
- Restrict who may credit a given `(app_chain, app)` bucket, e.g., require the purchase to originate from (or be explicitly authorized by) the app itself, or maintain per-payer sub-buckets rather than one shared FIFO list writable by arbitrary third parties.
- Alternatively, remove blind index-0 eviction and instead reject the purchase (or require an explicit governance/admin override, similar to `force_credit`) when the bucket is full, rather than silently destroying a potentially higher-value legitimate entry.
- If cross-chain sponsorship must remain fully permissionless, consider giving evicted subscriptions a pro-rata refund path back to whichever payer's tokens were displaced, or separate "self" vs "sponsored" quotas so a griefer cannot touch entries they did not pay for.

### Proof of Concept
1. Victim buys a large Tier 4 subscription for app `A` on chain `C` via `BandwidthManager.purchase(A, TierFour, 12, C)`, paying a large fee-token amount; this lands as entry `k` in `Allowance[C][A]`. [7](#0-6) 
2. Attacker (no relationship to app `A`) repeatedly calls `BandwidthManager.purchase(A, TierOne, 1, C)` from any chain with a manager deployed, each time paying only the cheapest tier price. [1](#0-0) 
3. Each purchase message reaches `pallet-bandwidth::on_accept`, calling `push_subscription(C, A, ...)`, which appends to `Allowance::<T>[C][A]`. [8](#0-7) 
4. Once the bucket reaches 1024 entries, every further attacker purchase evicts the current head (oldest) entry via `list.remove(0)`. [9](#0-8) 
5. After enough pushes, the victim's Tier-4 entry reaches the front and is evicted, emitting `SubscriptionEvicted { app_chain: C, app: A, tier: TierFour, lost_bytes }` — the victim's fully paid-for, unused bandwidth allowance is permanently destroyed by a party with no authorization over app `A`'s bucket. [10](#0-9) 

This confirms an unprivileged, public-entrypoint path causing loss of funds/value for a victim through unauthorized manipulation of a shared ledger — the direct local analog of the external Registry pre-registration/freezing report.

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();

                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),

            })

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

### Eviction

Pushing onto a full list (1024 entries) evicts the **oldest** entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain. In practice this only happens under pathological repeat-buy behavior — at the default of one purchase per cycle, 1024 buys is years of headroom.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
