## Finding

### Title
Escrow withdrawal accepts failed ERC20 `transfer` calls as successful due to unchecked return-value pattern - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` settles escrowed intent funds using a raw low-level `.call` with the `IERC20.transfer.selector`, checking only that the call did not revert (`success`), while never decoding/validating the returned boolean. Meanwhile the escrow accounting and order-finalization state (`_orders[...]`, `_filled[...]`) are updated unconditionally as if the transfer definitely delivered funds. This is the same class of bug as the referenced report — using an unsafe/raw primitive (`_mint`) instead of the hardened, return-value-checking variant (`safeMint`/`safeTransfer`) — except here it can lead to permanent loss of escrowed bridge funds rather than a frozen NFT.

### Finding Description
In `withdraw()`, which is invoked by `onAccept()` for both `RedeemEscrow` and `RefundEscrow` cross-chain settlement messages, tokens are released via: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
```

The same unchecked pattern is used in the `SweepDust` handling path inside `onAccept()`: [2](#0-1) 

The `success` boolean from a low-level `.call` only reflects whether the callee's code executed without reverting — it says nothing about whether the ERC20 `transfer` actually moved tokens. Any token whose `transfer()` implementation returns `false` on failure instead of reverting (a well-documented ERC20 edge case, and exactly the class of non-standard token behavior `SafeERC20` exists to guard against) will make this call return `success = true` with no tokens transferred. The contract nonetheless:
1. Marks the order `_filled[body.commitment] = beneficiary` — finalizing settlement.
2. Decrements `_orders[body.commitment][token] -= amount` — destroying the accounting record of the escrow.
3. Emits `EscrowReleased`/`EscrowRefunded` — signaling successful settlement.

This contradicts the pattern used correctly elsewhere in the same codebase: the primary EVM `IntentsBase.sol` `_withdraw()` uses `IERC20(token).safeTransfer(beneficiary, amount);` (via OpenZeppelin's `SafeERC20`, which decodes and requires the boolean return value), and `IntentGatewayV2` on Tron itself imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`) but deliberately bypasses it for the withdraw/sweep money paths, reverting to the unsafe raw-call pattern. [3](#0-2) 

### Impact Explanation
Because `_filled` and `_orders` are updated regardless of whether the token transfer truly succeeded, a non-standard/malicious ERC20 token registered as an order's input asset can cause escrowed user or solver funds to be irrevocably marked as settled/refunded while remaining permanently locked in the `IntentGatewayV2` contract — there is no other code path to re-attempt withdrawal once `_filled` is set and `_orders[...]` is zeroed. This is a direct loss-of-funds / false-state-acceptance bug in the bridge custody and intent-settlement flow, matching the bounty's "stealing or loss of funds" and "false proof/state acceptance" categories.

### Likelihood Explanation
This does not require a malicious relayer, prover, or admin — only that one of the tokens configured for an intent (input/output asset) exhibits the well-known "return false instead of revert" ERC20 behavior, or that its `transfer` implementation can be made to fail silently under specific conditions (e.g., paused/blocklisted transfer semantics common on some real-world stablecoins). The settlement path (`onAccept` → `withdraw`) is a normal, unprivileged cross-chain message path triggered by legitimate order fills/cancellations, so the vulnerable code executes on every escrow release for any token that doesn't strictly revert on failure.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`), so that both call-reversion and false boolean returns cause the transaction to revert instead of silently finalizing escrow state.

### Proof of Concept
1. Register/escrow an input token whose `transfer()` implementation returns `false` on some failure condition instead of reverting (standard ERC20 edge case).
2. Trigger a normal cross-chain `RedeemEscrow` or `RefundEscrow` message so `onAccept()` calls `withdraw()`.
3. Have the token's `transfer` fail (return `false`) under the triggering condition while the low-level `.call` itself does not revert.
4. Observe `success == true`, so no revert occurs; `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, and `EscrowReleased`/`EscrowRefunded` fires — while the beneficiary's balance never increased and the tokens remain stuck in the `IntentGatewayV2` contract with no remaining path to reclaim them.
