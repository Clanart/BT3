## Title
Corrupted MessageSet lazy extension silently resolves to the default instance instead of surfacing a parse error - (`java/core/src/main/java/com/google/protobuf/InternalLazyField.java`)

## Summary
The zkSync finding's failed invariant is: a two-step "construct → finalize" operation skips the finalize step under attacker/operator-influenced control, leaving the object in an intermediate state that *looks* valid to callers (no revert) but silently behaves incorrectly, causing downstream logic (and funds) to be lost with no error signal. The Protobuf analog with the same shape — parse succeeds, presence looks valid, but the actual content is silently replaced by an incorrect placeholder without any exception — is `InternalLazyField`'s handling of corrupted `MessageSet` extension payloads.

## Finding Description
`InternalLazyField.getValue()` defers parsing of a `MessageSet` extension's bytes until first access (`ensureInitialized()`), and if the deferred parse fails (`InvalidProtocolBufferException`), it marks the field `corrupted = true` [1](#0-0) . When accessed via `getValue()`, if `extensionRegistry.lazyExtensionEnabled()` is false (the legacy/default path for MessageSet extensions), the corruption is swallowed and the **default instance** is returned instead of throwing: [2](#0-1) 

This is the same invariant violation as the zkSync bug: the "finalize/validate" step (raising a decode error) is skipped, and the object is left in a state that pretends to be normally constructed (`hasExtension()` still reports `true`, the extension is "present") but its actual content has been silently substituted with an inert placeholder (default instance) rather than surfacing failure to the caller. Just as `forceDeployOnAddress` leaves the deployed contract in a permanently "constructing" (inert) state that other contracts can call without reverting, a corrupted lazily-parsed `MessageSet` extension leaves the message in a permanently "default" (inert) state that calling code can read without any exception, indistinguishable from a legitimately-empty/zero extension value.

The top-level `parseFrom` call for the containing message succeeds normally (no exception at parse time) because the extension bytes are not eagerly parsed — this mirrors `forceDeployOnAddress` completing without reverting even though `_constructContract` was skipped. Only a later, separate access to the extension (`getExtension()`/`getValue()`) is where the corruption would have manifested, and that access is designed to swallow the error and return a default value instead of propagating a decode failure.

## Impact Explanation
Consuming applications that use `hasExtension()` to gate logic (e.g., "if this extension is present, treat this message as authorized/verified/carrying a specific payload") could be misled: the extension is present, but a malicious or corrupted encoding of its inner bytes causes the actual value to collapse to the type's default (e.g., empty string, zero-valued fields, empty repeated fields) without any indication that parsing failed. This is analogous to the zkSync scenario where a contract call succeeds and funds are sent, but the contract silently behaves as an empty/no-op, causing loss without an error being raised — the "consuming-application exposure" (validation logic, business decisions, or fund/permission checks keyed off extension content) can be bypassed or produce wrong results.

The severity is bounded because: this legacy silent-fallback path only applies to `MessageSet` extensions (`WireFormat.MESSAGE_SET_*`), a fairly narrow/legacy wire format; and the library provides `LazyExtensionMode.LAZY_VERIFY_ON_ACCESS` specifically to convert this into a thrown `InvalidProtobufRuntimeException` instead, indicating protobuf maintainers already recognize the risk of the silent-default-instance path and provide (but do not force) a fix. This keeps the finding at Medium, similar to the zkSync judge's downgrade rationale — it is real, "not behaving in the intended way," but mitigated by an opt-in stricter mode and narrow applicability.

## Likelihood Explanation
Any attacker sending a bounded, otherwise well-formed binary Protobuf message that uses `MessageSet` wire format (`repeated group Item = 1 { required uint32 typeId = 2; required bytes message = 3; }`) can supply a syntactically valid outer item (correct `typeId`, correct length-prefixed inner bytes) whose inner bytes are semantically invalid for the target extension's schema. `MessageSetSchema.java`/`GeneratedMessageLite.java` route such items through `eagerlyMergeMessageSetExtension`/`mergeMessageSetExtensionFromCodedStream` and ultimately into `InternalLazyField`, which defers validation [3](#0-2) . No special privileges are required — this is reachable through the ordinary public `parseFrom` API on a trusted schema using `MessageSet` semantics with a default (non-`LAZY_VERIFY_ON_ACCESS`) `ExtensionRegistryLite`.

## Recommendation
- Default `ExtensionRegistryLite` MessageSet extension handling to `LAZY_VERIFY_ON_ACCESS` (throw on first access to corrupted lazy fields) instead of silently substituting the default instance, closing the gap between "presence" and "valid content," analogous to zkSync's fix of always finalizing the constructed/finalized state rather than leaving it ambiguous.
- Where backward compatibility requires keeping the silent-fallback behavior, document prominently (and expose programmatically, e.g. via a "corrupted" query API) that `hasExtension()==true` does not guarantee the returned value reflects the wire bytes, so consuming applications performing security- or fund-relevant decisions do not treat presence as proof of valid parsed content.

## Proof of Concept
Existing repository tests already demonstrate the exact behavior (silent default-instance fallback on corrupted lazily-parsed extension bytes) under the legacy (non-`LAZY_VERIFY_ON_ACCESS`) mode: [4](#0-3) 
and [5](#0-4)  — `testInvalidProto` explicitly comments "Silently fails and uses the default instance." A minimal reproduction: construct a `MessageSet`-style outer message whose `Item` group has a valid `typeId` for a known extension but whose `message` bytes are corrupted/undecodable for that extension's type, feed it through the containing message's ordinary `parseFrom`, then call `getExtension(...)` — parsing succeeds, `hasExtension()` returns true, and `getExtension()` returns the extension's default instance rather than raising a decode error.

**Caveats/uncertainty:** I could not fully verify from the index (a) whether `FieldSet`/`MessageReflection` always route MessageSet extension access through `InternalLazyField`'s "old behavior" path for all trusted-schema configurations, or whether some code paths default to `LAZY_VERIFY_ON_ACCESS`, and (b) whether this "silent default" behavior is considered a documented/intended legacy contract by upstream (given the presence of the opt-in stricter mode) rather than a bug eligible for a security advisory. If it is purely documented legacy behavior with an available strict opt-in, this would more appropriately be classified as a hardening recommendation than a novel vulnerability. Given the index's file-size limits, a Devin session with full repository access is recommended to confirm the exact default registry configuration and all call sites feeding into `InternalLazyField`.

  private void ensureInitialized() throws InvalidProtocolBufferException {
    if (value != null) {
      return;
    }

    synchronized (this) {
      if (corrupted) {
        throw new InvalidProtocolBufferException("Repeat access to corrupted lazy field");
      }
      try {
        // `bytes` is guaranteed to be non-null since `value` was null.
        CodedInputStream input = bytes.newCodedInput();
        input.enableAliasing(/* enabled= */ true);
        // When lazyExtensionEnabled() returns true, it means all extensions including MessageSet's
        // will be fully parsed. When it returns false, it basically implies this can only be a
        // MessageSet extension, and we should fall back to the old behavior of silently returning
        // the default instance on corrupted extensions i.e. a full parse.
        value =
            extensionRegistry.lazyExtensionEnabled()
                ? defaultInstance.getParserForType().parsePartialFrom(input, extensionRegistry)
                : defaultInstance.getParserForType().parseFrom(input, extensionRegistry);
        input.checkLastTagWas(0);
      } catch (InvalidProtocolBufferException e) {
        corrupted = true;
        throw e;
      }
    }
  }
