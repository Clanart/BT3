Confirmed vulnerability. `BandwidthManager.onAccept` only validates the *chain-level* source (`request.source == IDispatcher(_host).hyperbridge()`), and never checks the *module-level* sender (`request.from`) against `PALLET_BANDWIDTH_MODULE_ID`. This is explicitly acknowledged in the project's own docs: "The `to` field is the manager's address — no module-id lookup" [1](#0-0) , and confirmed in code where the only auth check is the source-chain equality test before branching on `SetTiers`/`Withdraw` [2](#0-1) .

Crucially, `DispatchPost.from` (module identifier) is fully caller-controlled and is copied verbatim into the on-chain `PostRequest` by the low-level dispatcher, with no validation that the caller is actually the claimed module [3](#0-2) . Multiple production-pattern pallets in this codebase expose signed (non-privileged) extrinsics that let ordinary users pick an arbitrary destination `to` address and body for a `DispatchPost` to any EVM chain — e.g. `dispatch_to_evm` (`ensure_signed`, attacker picks `params.module`) [4](#0-3) , and the equivalent in `modules/pallets/demo/src/lib.rs` [5](#0-4) , plus other apps like `hyper-fungible-token`'s `send` that build fully attacker-influenced bodies and dispatch to attacker/config-chosen destination contracts [6](#0-5) . Since `request.source` will always equal the Hyperbridge chain id for any message dispatched from a pallet running on that chain — regardless of which pallet/account initiated it — an unprivileged signed account that can reach any generic "dispatch-to-EVM" extrinsic can set `to = BandwidthManager address` and `body = [ACTION_SET_TIERS | ACTION_WITHDRAW, attacker-payload]`, and `onAccept` will process it as legitimate governance.

### Title
Missing module-identity (`request.from`) check in `BandwidthManager.onAccept` allows forged `SetTiers`/`Withdraw` governance messages - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`onAccept` authenticates inbound governance messages solely by chain identity (`request.source == hyperbridge`) and never verifies that `request.from` equals `PALLET_BANDWIDTH_MODULE_ID` ("BWMARKET"), the pallet-bandwidth module identifier. Any account able to dispatch a generic cross-chain POST message from the Hyperbridge chain to an arbitrary EVM destination (a routine, unprivileged capability provided by multiple pallets in this codebase) can address the message `to` the deployed `BandwidthManager` contract and supply an attacker-chosen `body`, since nothing on the EVM side checks who (which module) on Hyperbridge actually sent it.

### Finding Description
`onAccept` decodes `request.body[0]` into `OnAcceptActions` and executes `SetTiers` (line 207) or `Withdraw` (line 213) after only checking `request.source.equals(hyperbridge)` [7](#0-6) . It never asserts `request.from == PALLET_BANDWIDTH_MODULE_ID`. On the Substrate side, `DispatchPost.from` is an arbitrary caller-supplied `Vec<u8>` copied straight into the committed `PostRequest` with no cross-check against the calling pallet's true identity [3](#0-2) . Since ordinary signed extrinsics on other pallets can set `to` to any EVM address (including the manager's) and craft any `body`, this allows a forged governance message to be legitimately relayed and verified by the ISMP host (correct consensus/state proof — it genuinely was committed on Hyperbridge), yet arrive at `BandwidthManager.onAccept` as if it were pallet-bandwidth's own governance dispatch. This breaks the invariant documented for the round-trip: "the pallet enforces this on inbound messages" refers to the *reverse* direction (pallet checking `request.from` on purchases) but is asymmetric — the manager's `onAccept` has no equivalent check [8](#0-7) .

### Impact Explanation
Both `OnAcceptActions` branches are affected identically since both are gated by the same single (insufficient) check:
- `SetTiers`: attacker sets `tierPrice[tier] = 0` (or any low value) unboundedly for any of the four tiers, letting subsequent `purchase()` calls mint bandwidth credit essentially for free.
- `Withdraw`: attacker sets `beneficiary` to their own address and `amount` up to the manager's full fee-token/native balance, draining funds escrowed from honest purchasers directly via `IERC20.safeTransfer` or a native `call{value:}` [9](#0-8) .

Chaining both in one exploit sequence (forged `SetTiers` then forged `Withdraw`) compounds the loss: free/near-free bandwidth minting plus treasury drain, both using the same attacker-controlled `request.from`/`request.body` and the same missing check.

### Likelihood Explanation
The attack requires only an unprivileged, signed extrinsic capable of dispatching an arbitrary POST to an arbitrary EVM destination address — a documented, generic capability of the ISMP dispatch pattern used across multiple pallets in this codebase (`dispatch_to_evm`-style calls). No relayer collusion, no privileged origin, and no proof forgery are needed; the underlying consensus/state proof is genuinely valid because the message really was dispatched from the Hyperbridge chain. The only defect is that the EVM contract cannot distinguish "dispatched by pallet-bandwidth" from "dispatched by any other account/pallet on the same chain."

### Recommendation
In `onAccept`, additionally verify `request.from.equals(PALLET_BANDWIDTH_MODULE_ID)` (or the pallet-bandwidth sovereign account bytes) before branching on `OnAcceptActions`, mirroring the check the pallet already performs on inbound purchases (`request.from` must equal the registered `BandwidthManager` address). This closes the asymmetry and ensures only the intended pallet, not any account on the Hyperbridge chain, can trigger `SetTiers`/`Withdraw`.

### Proof of Concept
1. Deploy/find any pallet on the Hyperbridge parachain that exposes a signed, non-privileged extrinsic wrapping `IsmpDispatcher::dispatch_request(DispatchRequest::Post(...))` with attacker-controlled `to` and `body` (pattern shown in `modules/pallets/demo/src/lib.rs::dispatch_to_evm` [5](#0-4) ).
2. Call it with `to = <BandwidthManager address>`, `body = bytes.concat(bytes1(0x00), abi.encode([Tier{tier:1, price:0}, ...]))` (SetTiers action) — relay the message; `onAccept` accepts it since `request.source == hyperbridge` and mints free-tier pricing.
3. In the same test/session, dispatch a second POST with `body = bytes.concat(bytes1(0x01), abi.encode(Withdrawal{token: feeToken, beneficiary: attacker, amount: manager.balance}))` — `onAccept` accepts and transfers the full treasury to the attacker.
4. Assert `tierPrice[tier] == 0` and `feeToken.balanceOf(attacker) == drained_amount` both succeed, using only the (missing) `request.from`/module-identity gap as the root cause — matching the existing test harness pattern in `evm/tests/foundry/BandwidthManagerTest.t.sol` (`_governanceRequestFor`, `testGovernanceCanSetMultipleTiers`, `testGovernanceCanWithdrawAcrossTokenSwap`) but substituting an attacker-chosen `request.from` instead of the legitimate pallet identifier [10](#0-9) .

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }

    function testGovernanceCanSetMultipleTiers() public {
        Tier[] memory updates = new Tier[](3);
        updates[0] = Tier({tier: 1, price: 5e18});
        updates[1] = Tier({tier: 2, price: 50e18});
        updates[2] = Tier({tier: 3, price: 500e18});

        bytes memory body = bytes.concat(

        manager.onAccept(req);
