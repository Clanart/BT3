### Title
Aggregator gRPC server installs `Interceptors::Noop` when `client_verification` is false, exposing all methods (including `Internal*`) to unauthenticated callers - (File: core/src/servers.rs)

### Summary
`create_grpc_server` chooses between `Interceptors::OnlyAggregatorAndSelf` and `Interceptors::Noop` purely based on `BridgeConfig.client_verification`, and `client_verification` defaults to `false` (`read_string_from_env("CLIENT_VERIFICATION").is_ok_and(|s| s == "true" || s == "1")` in `core/src/config/env.rs`). When `client_verification` is `false`, the server-side TLS config also omits `client_ca_root`, so the server neither requires nor validates a client certificate, and `Interceptors::Noop::call` unconditionally returns `Ok(req)` for every request. This means the only mechanism that distinguishes "internal" (self-only) calls from ordinary aggregator-facing calls - `is_internal` inside `only_aggregator_and_self` - is bypassed entirely, and any TCP peer that can reach the port can invoke every RPC on `ClementineAggregatorServer`, `ClementineOperatorServer`, or `ClementineVerifierServer` depending on which service is configured this way.

### Finding Description
The binding claimed to hold is: `caller_identity_required_by(method) == caller_identity_presented_by_caller`, enforced by `only_aggregator_and_self` via leaf-certificate comparison (`core/src/rpc/interceptors.rs:62-76`). The code path is:

`create_grpc_server` (`core/src/servers.rs:106-138`) branches on `config.client_verification`:
- `true` → sets `client_ca_root` in `ServerTlsConfig`, loads `client_cert_path`/`aggregator_cert_path`, and installs `Interceptors::OnlyAggregatorAndSelf { aggregator_cert, our_cert }`.
- `false` → server TLS is configured with only its own identity (no client CA), and `Interceptors::Noop` is installed.

`Interceptors::Noop::call` (`core/src/rpc/interceptors.rs:30`) does `Ok(req)` with no certificate check at all, so `is_internal` (line 12-20) - the function that gates `Internal*`-prefixed methods to same-node callers - is never invoked. Any connection, with or without a client certificate, reaches the underlying service handlers (`AggregatorServer`, `OperatorServer`, `VerifierServer`) directly through `AddMethodMiddlewareLayer` → `InterceptedService::call` → `Interceptors::Noop::call` → handler.

`client_verification` is read from the `CLIENT_VERIFICATION` env var and defaults to `false` when unset (`core/src/config/env.rs:181-182`), and `create_aggregator_grpc_server` (`core/src/servers.rs:293-317`) only emits a `tracing::warn!` when verification is *enabled* - there is no warning, refusal, or fallback behavior for the (default) disabled case, confirming this is a plausible, unremarked-upon deployment posture rather than a test-only toggle.

### Impact Explanation
This is a real gap in the interceptor design, but I could not confirm from available code that it independently causes a bridge-value-moving, reimbursement-miscrediting, or collateral-burning outcome distinct from "unauthenticated access to internal RPCs" — the impact category matching the rules is: **High - an unauthenticated state-changing or broadcasting call**. Whether `internal_send_tx` specifically lets an attacker broadcast an arbitrary attacker-signed transaction through the aggregator's fee-bumping wallet (as the question claims) could not be verified within the available tool budget: I was unable to read the body of `internal_send_tx` in `core/src/rpc/aggregator.rs` / `core/src/aggregator.rs` to confirm whether it validates the transaction's provenance/signatures against the aggregator's own signing sessions before handing it to the tx-sender (many `tx_sender`-backed internal RPCs in this codebase re-derive or re-verify the transaction from stored state rather than trusting caller-supplied bytes verbatim, but this specific handler was not inspected).

### Likelihood Explanation
The precondition is real and plausible: `client_verification` defaults to `false` unless the `CLIENT_VERIFICATION` env var is explicitly set to `"true"`/`"1"`, and the aggregator startup path only warns when verification is *on*, not when it is off — so a deployer who does not explicitly set this env var runs with `Interceptors::Noop` and no client TLS requirement. Reaching the port requires no BTC cost, no key, and no certificate — only network access to `host:port`.

### Recommendation
1. Do not allow `Interceptors::Noop` to be silently selected as a default; require `client_verification` (or an explicit "insecure mode" flag with a loud, unavoidable warning/abort in production builds) before disabling caller identity checks.
2. Independently of TLS/cert checks, add method-level authorization inside handlers for `Internal*`-prefixed and state-mutating RPCs (`InternalSendTx`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`, `Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`) so that identity is enforced even if the interceptor layer is misconfigured, e.g. re-validate that any transaction passed to `internal_send_tx` was actually produced/signed by this node's own signing sessions rather than trusting attacker-supplied `RawSignedTx` bytes.
3. Change the default of `client_verification` to `true`, requiring an explicit, logged opt-out.
