## Title
Unbounded Recursion in `PuzzleWithRestrictions.from_memo()` on Attacker-Supplied `MofN` Memo Data - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs a custody structure (member/`MofN` tree) from a CLVM `Program` memo, matching the CVE-2017-9617 bug class (uncontrolled recursion while parsing deeply nested attacker-supplied data leading to stack exhaustion). This is analogous but weaker: it is Python-level recursion in a client-side wallet-sync helper, not consensus code, and its exact untrusted reachability could not be confirmed from the indexed code.

### Finding Description
`PuzzleWithRestrictions.from_memo()` is explicitly documented as "the on-chain/exported synchronization contract" used to "reconstruct unknown members/restrictions, including recursive `MofN`, so later wallet code can fill known puzzle implementations by puzzle hash" [1](#0-0) . The implementation recurses without any depth bound: when `further_branching` is true it calls itself once per `MofN` member via a list comprehension `[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]` [2](#0-1) . A single `MemberHint`/`RestrictionHint`/`MofNHint` can itself be nested, embedding another `PuzzleWithRestrictions` memo inside `memo` fields, so a maliciously constructed memo `Program` can chain arbitrarily many `MofN` layers, each adding one Python stack frame per `from_memo` call, one per `RestrictionHint.from_program`, and one for the corresponding `MofNHint.from_program` call [3](#0-2) [4](#0-3) .

This mirrors the `dissect_daap_one_tag` bug class: parsing of externally supplied, self-referential/nested data with recursion whose depth is controlled entirely by the untrusted input, with no depth limiter. By contrast, the codebase's own CLVM `tree_hash.py` and `data_layer` insertion code were deliberately rewritten to be *iterative* specifically to avoid "blowing out the python stack" on deeply nested untrusted trees [5](#0-4) , and Data Layer even enforces `chia_rs.datalayer.RecursionDepthExceededError` for deep untrusted graphs [6](#0-5) . `custody_architecture.py`'s `from_memo`/`from_program` chain has no equivalent protection.

### Impact Explanation
If this memo is ever parsed from data an unprivileged party fully controls (e.g., a custom `additional_memos`/`CREATE_COIN` hint field on a coin, or an offer/RPC-supplied memo blob passed to `from_memo`), a Python `RecursionError` would be raised inside wallet sync or RPC handling, potentially crashing or hanging the wallet's coin-processing pipeline for that peer/coin — a spend-triggered halt of transaction/coin processing. This matches the "spend-triggered transaction-processing halt" impact category. However, I could not find, within the indexed code, the exact call site that feeds untrusted, attacker-controlled on-chain memo bytes into `PuzzleWithRestrictions.from_memo()` during normal wallet sync (only test callers were found: `chia/_tests/clvm/test_custody_architecture.py`). Its reachability from a live coin/spend-bundle-processing path (as opposed to being invoked only by a wallet explicitly managing its own custody structure) is unconfirmed.

### Likelihood Explanation
Constructing a deeply nested `MofN`/`PuzzleWithRestrictions` memo `Program` is cheap and entirely under attacker control (no cost/size limit is visibly enforced on `memo` structure before `from_memo` recurses). If this parser is invoked on untrusted, attacker-supplied on-chain memo data (this is the custody framework's stated purpose — "sync an unknown inner puzzle from on chain" [7](#0-6) ), likelihood is high; if it is only invoked by a wallet on its own previously-constructed custody data, likelihood is low. This ambiguity keeps the finding at Medium confidence pending verification of the production call site.

### Recommendation
- Convert `PuzzleWithRestrictions.from_memo()`, `MofNHint.from_program()`, and `RestrictionHint.from_program()` to an iterative (explicit-stack) implementation, following the same pattern already used in `sha256_treehash()` [8](#0-7) .
- Alternatively/additionally, enforce an explicit maximum nesting depth for `MofN` member trees during memo parsing, raising a clean `ValueError` rather than allowing Python recursion to hit the interpreter's recursion limit.
- Audit and document every caller path that supplies memo/hint data to `from_memo()` from wallet sync/RPC to confirm whether it is reachable with attacker-controlled data; if so, prioritize the fix as security-relevant, otherwise downgrade to a robustness hardening task.

### Proof of Concept

2. Call `PuzzleWithRestrictions.from_memo(deeply_nested_memo)` as done in `chia/_tests/clvm/test_custody_architecture.py::test_back_and_forth_hint_parsing` (`assert PuzzleWithRestrictions.from_memo(cwr.memo()) == cwr`) [9](#0-8) , or through whatever production wallet-sync code path consumes on-chain memos for this puzzle type.
3. Observe a Python `RecursionError` (stack exhaustion) once `N` exceeds the interpreter's recursion limit, analogous to Wireshark's stack exhaustion on deeply nested DAAP tags.

**Note**: I was unable to locate, within the available index, the specific production (non-test) code path that calls `PuzzleWithRestrictions.from_memo()` on untrusted on-chain data during wallet sync, so full end-to-end reachability from a single submitted spend bundle/coin is not fully confirmed. If precise verification of this call graph is needed, a Devin session with full repository access would be required to trace all callers of `from_memo`/`from_program` in `custody_architecture.py` and confirm whether they process attacker-supplied coin memos.

```python
def sha256_treehash(sexp: CLVMStorage, precalculated: set[bytes32] | None = None) -> bytes32:
    """
    Hash values in `precalculated` are presumed to have been hashed already.
    """

    if precalculated is None:
        precalculated = set()

    def handle_sexp(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        # just trusting it is right, otherwise we get an attribute error
        sexp: SExp = sexp_stack.pop()  # type: ignore[assignment]
        if sexp.pair:
            p0, p1 = sexp.pair
            sexp_stack.append(p0)
            sexp_stack.append(p1)
            op_stack.append(handle_pair)
            op_stack.append(handle_sexp)
            op_stack.append(roll)
            op_stack.append(handle_sexp)
        else:
            # not a pair, so an atom
            atom: bytes = sexp.atom  # type: ignore[assignment]
            if atom in precalculated:
                r = atom
            else:
                r = std_hash(b"\1" + atom)
            sexp_stack.append(r)

    def handle_pair(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        # just trusting it is right, otherwise we get a type error
        p0: bytes = sexp_stack.pop()  # type: ignore[assignment]
        p1: bytes = sexp_stack.pop()  # type: ignore[assignment]
        sexp_stack.append(std_hash(b"\2" + p0 + p1))

    def roll(sexp_stack: ValueStackType, op_stack: OpStackType, precalculated: set[bytes32]) -> None:
        p0 = sexp_stack.pop()
        p1 = sexp_stack.pop()
        sexp_stack.append(p0)
        sexp_stack.append(p1)

    sexp_stack: ValueStackType = [sexp]
    op_stack: list[Op] = [handle_sexp]
    while len(op_stack) > 0:
        op = op_stack.pop()
        op(sexp_stack, op_stack, precalculated)
    # just trusting it is right, otherwise we get some error, probably
    result: bytes = sexp_stack[0]  # type: ignore[assignment]
    return bytes32(result)
```
