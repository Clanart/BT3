### Title
Unhandled Exception via Non-Bounds-Checked Atom Length Prefix in `is_atom_canonical()` During Mempool Spend Bundle Validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the CLVM serialization of a submitted coin spend's puzzle reveal and solution, reading a declared length-prefix from an attacker-controlled byte buffer without validating that the declared prefix length or resulting atom length fits within the remaining buffer, mirroring the FreeRDP `GLYPH_FRAGMENT_ADD` pattern of trusting a declared size field over the buffer's actual bounds.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the control byte at `offset`, determines `prefix_len` (0-5 additional bytes) from its high bits, then loops `prefix_len` times indexing further into `clvm_buffer` to build `atom_len`: [1](#0-0) 

Nothing here checks that `offset + prefix_len` stays within `len(clvm_buffer)` before indexing `clvm_buffer[offset]` for each of the `prefix_len` iterations. `is_clvm_canonical()`, the caller, similarly advances `offset += atom_len` after computing the atom length without checking that `offset` (and the atom body it implicitly represents) is within the buffer bounds before the next loop iteration re-indexes `clvm_buffer[offset]`: [2](#0-1) 

This is invoked directly on attacker/wallet-supplied bytes during spend bundle admission to the mempool, for every coin spend's puzzle reveal and solution: [3](#0-2) 

`validate_spend_bundle()` is reached from `add_spend_bundle()`, which is the standard entry point for an unprivileged spend-bundle submitter (full node RPC / P2P transaction relay) to get a `SpendBundle` considered for mempool inclusion: [4](#0-3) 

A crafted `puzzle_reveal` or `solution` blob can present a control byte declaring a long length prefix (up to 5 extra bytes) or a declared atom length that extends past the end of the actual buffer. Because Python raises an `IndexError` on out-of-bounds sequence indexing rather than silently reading adjacent memory (unlike the C heap OOB read in FreeRDP), the practical effect in this codebase is an unhandled `IndexError` propagating out of `is_atom_canonical`/`is_clvm_canonical` inside `validate_spend_bundle()`, rather than memory disclosure.

### Impact Explanation
If the `IndexError` is not caught anywhere between `is_clvm_canonical()` and the top-level bundle admission/RPC handler, a single malformed `SpendBundle` submitted by any unprivileged peer/wallet client can throw an unhandled exception during `validate_spend_bundle()`, which is exercised on every mempool admission attempt (P2P relay, `push_tx` RPC, wallet resubmission during `new_peak()` mempool rebuilds). This matches the "spend-triggered transaction-processing halt" impact category: a malicious but syntactically-permitted spend bundle could crash or destabilize mempool processing for any full node that attempts to validate it, rather than being cleanly rejected with `Err.INVALID_COIN_SOLUTION`.

I was not able to fully trace whether `add_spend_bundle()` / the RPC and P2P call sites wrap `validate_spend_bundle()` in a broad exception handler that converts this specific `IndexError` into a graceful `FAILED` status — the visible code in `add_spend_bundle()` only handles the `(err, item, remove_items)` tuple return path and does not show a try/except around the call to `validate_spend_bundle()`. This is the key remaining uncertainty; if some outer caller (e.g., the P2P message handler or RPC endpoint) does catch generic exceptions around bundle processing, the practical impact would be reduced to a per-request rejection rather than a halt.

### Likelihood Explanation
Likelihood is high for reachability: any unprivileged spend-bundle submitter can set `puzzle_reveal`/`solution` bytes arbitrarily, and `is_clvm_canonical()` runs unconditionally on every coin spend during admission — it does not require the transaction to reach CLVM execution first. Constructing a buffer whose final bytes are a truncated multi-byte length-prefix atom-length is a small, deterministic manipulation (e.g., ending the buffer immediately after a `0xF8` control byte with fewer than 4 trailing bytes) that would trigger the unguarded index read.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each byte read in the prefix-length loop (verify `offset < len(clvm_buffer)` prior to indexing), and in `is_clvm_canonical()` verify `offset < len(clvm_buffer)` at the top of each loop iteration before dereferencing `clvm_buffer[offset]`, raising/returning a controlled "not canonical" result instead of allowing an `IndexError` to propagate. Additionally, confirm and, if missing, add a try/except around the canonical-serialization check in `validate_spend_bundle()` so any parsing failure maps deterministically to `Err.INVALID_COIN_SOLUTION` rather than an unhandled exception.

### Proof of Concept
Submit a `SpendBundle` containing a `CoinSpend` whose `puzzle_reveal` (or `solution`) SerializedProgram bytes end immediately after a multi-byte atom control byte, e.g. bytes `b"\xf8"` alone (declares a 5-byte-following length prefix per the `0b11111000` mask branch) with no trailing bytes. When `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))`, the loop in `is_atom_canonical()` attempts `clvm_buffer[offset]` for `offset` beyond the 1-byte buffer, raising `IndexError` inside mempool admission processing.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
