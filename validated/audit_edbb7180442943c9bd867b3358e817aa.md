Front-running an unprivileged registration function does exist in this codebase, and it carries a real economic consequence via the referral-reward mechanism.

### Title
Referral code registration can be frontrun, permanently diverting referral rewards to an attacker - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.registerCode(bytes32 _code)` lets any wallet claim an arbitrary `bytes32` referral code on a strict first-come-first-served basis, with no cost, no stake, and no commit/reveal step. An attacker watching the mempool can observe a legitimate service provider's/influencer's `registerCode` transaction, front-run it with the identical `_code`, and permanently claim the code for themselves.

### Finding Description
`registerCode` performs no ownership binding to the caller beyond `msg.sender`, and the only guard is a simple "not already taken" check: [1](#0-0) 

Because `_code` is chosen entirely by the caller (e.g., a human-readable/branded value hashed off-chain) and the transaction is public in the mempool before inclusion, a malicious actor can copy the `_code` parameter from a pending transaction and resubmit it with a higher gas price. The attacker's transaction will be mined first, `codeOwners[_code]` becomes non-zero, and the original submitter's transaction reverts with `CodeOccupied()`: [2](#0-1) 

Unlike Audius's `ServiceProviderFactory.register`, there is no stake requirement here at all — registration is free, so the attack has zero cost and no slashing risk to deter it.

Once the attacker owns the code, any user who later calls `useCode(_code)` believing it belongs to the legitimate referrer is instead bound to the attacker as their referrer: [3](#0-2) 

All subsequent referral rewards computed in `trigger()` — driven by `myReferer[referee]` — are then paid to the attacker's `rewardAmount` instead of the legitimate referrer's: [4](#0-3) 

The binding `myReferer[msg.sender]` is permanent once set (`HasReferral()` blocks changing it), and there is no unprivileged way for a referee to revert a stolen code back to the intended owner. The only remedy, `forceSetCodeOwner`, is `onlyOwner` and out of scope as an unprivileged fix path.

### Impact Explanation
Because the code identifier is squatted for free and permanently, all referral traffic and referral yield (a share of harvested rewards accrued via `trigger`) intended for the legitimate referrer is redirected to the attacker indefinitely, i.e. a permanent theft of the referrer's unclaimed yield stream and a permanent freeze of the legitimate referrer's ability to use their intended identity/code. This meets the "theft or permanent freezing of unclaimed yield" bar, since the diverted `refererAmount` in `trigger()` is claimable by the attacker via `claimReward()`: [5](#0-4) 

### Likelihood Explanation
The attack is trivial and costless: no stake, no whitelist, no cooldown — just observe the mempool for `registerCode` calls and resubmit the same `_code` with higher gas. Any unprivileged wallet can perform it against any other unprivileged wallet's registration attempt.

### Recommendation
Bind code ownership to the intended registrant at submission time so it cannot be copied and replayed by a third party, e.g. require `_code` to be derived as `keccak256(abi.encodePacked(msg.sender, desiredLabel))`, or implement a commit/reveal scheme (commit `keccak256(code, salt, msg.sender)`, then reveal after a delay) before writing to `codeOwners`.

### Proof of Concept
1. Alice (legitimate referrer) submits `registerCode(codeHash)` to register her brand code.
2. Mallory observes this pending transaction in the mempool, extracts `codeHash`, and submits her own `registerCode(codeHash)` with a higher gas price.
3. Mallory's transaction mines first: `codeOwners[codeHash] = Mallory`.
4. Alice's transaction reverts with `CodeOccupied()`.
5. Any user who later calls `useCode(codeHash)` (believing it is Alice's code) becomes bound to Mallory via `myReferer[user] = Mallory`.
6. When `trigger()` is invoked by MasterMagpie on that user's reward claim, referral rewards accrue to Mallory's `rewardAmount`, which Mallory withdraws via `claimReward()` — permanently diverting yield that should have gone to Alice.

    function registerCode(bytes32 _code) external {
        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] != address(0)) revert CodeOccupied();

        codeOwners[_code] = msg.sender;
        userInfos[msg.sender].myCode = _code;
        userInfos[msg.sender].tier = 1; // tier 1 as default

        emit RegisterCode(msg.sender, _code);
    }

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
