## Analysis

The report's core bug class is a **faulty authorization check that lets an attacker-supplied value hijack an approval/credential flow meant for someone else** — i.e., a "confused deputy" where custom logic trusts attacker-controlled input to decide who gets access.

The closest verified analog in this codebase is in the **credential-helper endpoint classification logic**, `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`. When Git performs an HTTPS operation against a remote (which is fully attacker-controlled if the user adds/clones from a malicious remote or is redirected via a proxy), Git captures any `WWW-Authenticate` response headers from that server and forwards them to Desktop's credential helper as `wwwauth[...]` fields: [1](#0-0) 

The code treats the mere presence of the string `realm="GitHub"` in a header **the remote server itself supplied** as authoritative proof that the host is a GitHub Enterprise endpoint: [2](#0-1) 

If that classification returns `'enterprise'`, and no existing account matches, `getCredential` calls `ui.promptForGitHubSignIn(endpoint)`, where `endpoint` is the attacker's own remote URL: [3](#0-2) 

`promptForGitHubSignIn` then binds the resulting real GitHub/OAuth `Account` to that attacker-chosen `origin` via `setSignInEndpoint(origin)`: [4](#0-3) 

Once the account is created for that endpoint, `credWithAccount` will hand Git the account's `login`/`token` (the user's real GitHub Enterprise OAuth token) to authenticate against **the attacker's host**, because `getCredential`/`findGitHubTrampolineAccount` matches purely on URL origin: [5](#0-4) [6](#0-5) 

### Why existing guards don't stop it
- The `WWW-Authenticate` header is entirely attacker-controlled since it originates from the remote/proxy server responding to the git request — there's no cryptographic or DNS-based verification that the host is actually a GitHub instance.
- `isDotCom`/`isGHE` checks only cover `github.com`/`ghe.com`, so any other hostname is classified purely by the header heuristic [7](#0-6) .
- There is no confirmation step showing the user the *actual* untrusted hostname is being trusted as "GitHub Enterprise" before initiating a real OAuth/sign-in flow and persisting an account binding for it.

### Impact
A malicious git remote/proxy the user is tricked into adding or fetching from can pose as a GitHub Enterprise server via a spoofed `WWW-Authenticate: realm="GitHub"` header. This triggers a real GitHub sign-in dialog and, once the user signs in (an expected, in-flow action — not a self-XSS or social-engineering trick, since the app itself is initiating the "official-looking" sign-in prompt), binds that authenticated account/token to the attacker's endpoint. Subsequent credential-helper lookups will then transmit the user's real GitHub credentials to the attacker's server, i.e., **token exfiltration** and **unauthorized account/endpoint binding**.

### Uncertainty
I could not fully trace how `beginEnterpriseSignIn`/`SignInStore` finalizes and persists the endpoint-to-account mapping (e.g., whether there's a later validation step comparing the entered endpoint against real GHE API responses) because that logic lives outside the indexed snippets. This should be confirmed by inspecting `app/src/lib/stores/sign-in-store.ts` and `app/src/ui/sign-in` flow in full before treating this as conclusively exploitable — the index has size limits and didn't surface those files' full bodies. I'd recommend a Devin session to pull the complete `sign-in-store.ts` and related sign-in dialog code to verify whether any endpoint-authenticity check exists downstream before the account is persisted.

### Title
Attacker-Controlled `WWW-Authenticate` Header Triggers Spoofed GitHub Enterprise Sign-In and Credential Binding - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The git credential-helper trampoline classifies a remote as "GitHub Enterprise" solely based on an attacker-suppliable `WWW-Authenticate` response header (`realm="GitHub"`), then invokes the real GitHub sign-in flow and binds the resulting account to the attacker's endpoint.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` (lines 137-178) inspects `wwwauth[...]` credential fields forwarded by Git from a remote server's HTTP response and returns `'enterprise'` if any contains `realm="GitHub"`, with no other verification. This return value flows into `getCredential`, which for `endpointKind !== 'generic'` and no existing matching account calls `ui.promptForGitHubSignIn(endpoint)` using the attacker's own remote URL as `endpoint`. `promptForGitHubSignIn` (`trampoline-ui-helper.ts`) sets the sign-in endpoint to that URL's origin and starts a real enterprise OAuth/sign-in flow, ultimately producing an `Account` bound to the attacker's host.

### Impact Explanation
Once bound, the credential helper (`credWithAccount`) will supply the user's real GitHub token as HTTP Basic Auth credentials to the attacker-controlled host on future git operations against that origin, per `getGitHubCredential`. This is credential/token exfiltration and unauthorized endpoint/account binding driven entirely by attacker-controlled server response headers.

### Likelihood Explanation
Requires only that the user perform a normal git operation (fetch/push/clone) against a remote controlled by, or proxied by, the attacker — no local access, no leaked credentials, and no unusual user action beyond completing what looks like a legitimate GitHub sign-in prompt.

### Recommendation
Do not classify a host as GitHub Enterprise based solely on an unauthenticated `WWW-Authenticate` header value. Cross-check via an authenticated, out-of-band API probe (e.g., existing `isGitHubHost` HTTPS check) before initiating a real sign-in flow, and prominently disclose the actual raw hostname being bound to the account instead of relying on the header-derived classification alone.

### Proof of Concept
1. Stand up a malicious HTTPS git server (or MITM proxy) at `https://evil.example.com/repo.git` that responds to unauthenticated Git requests with `WWW-Authenticate: Basic realm="GitHub"`.
2. Have the victim add/clone `https://evil.example.com/repo.git` in GitHub Desktop.
3. Desktop's credential helper (`getEndpointKind`) classifies the host as `'enterprise'` due to the realm string match.
4. Desktop shows a GitHub Enterprise sign-in popup with `credentialHelperUrl: 'https://evil.example.com/...'`; the endpoint is set to `evil.example.com`'s origin via `setSignInEndpoint`.
5. Victim completes sign-in (legitimate OAuth to their real GHE/GitHub.com, since the sign-in flow itself is genuine); Desktop stores an `Account` associated with `evil.example.com`.
6. On the next credential-helper `get` request for that origin, Desktop supplies the real token as password to `evil.example.com`.

    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}

export const isDotCom = (ep: string) => {
  if (ep === getDotComAPIEndpoint()) {

  }

  return hostname === 'api.github.com' || hostname === 'github.com'
