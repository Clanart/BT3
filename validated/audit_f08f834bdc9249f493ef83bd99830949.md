### Title
NFT royalty payments in offers are undercalculated due to division-before-multiplication precision loss - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()`, which computes the exact mojo amount paid to an NFT's royalty address when an offer is settled, performs integer division (`// royalty_split`) *before* multiplying by the royalty `percentage`, then divides again by `MAX_ROYALTY_BASIS_POINTS`. This ordering causes unnecessary compounded truncation, analogous to the KyberSwap `ReinvestmentMath.sol` bug where `rMintQty` was computed with an early division that truncated precision before the final multiply/divide, giving users fewer tokens than the correct formula would.

### Finding Description
The royalty amount actually paid out on-chain is computed here: [1](#0-0) 

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    ...
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

The mathematically correct royalty is `abs(offered_amount) * percentage / (royalty_split * MAX_ROYALTY_BASIS_POINTS)`. The current code instead does `(abs(offered_amount) // royalty_split) * percentage // MAX_ROYALTY_BASIS_POINTS` — an early floor-division by `royalty_split` discards a remainder that a later multiplication by `percentage` could otherwise have preserved, before a second floor-division by `10000`. This is the same class of bug as the report: floor-dividing early instead of multiplying first causes avoidable precision loss and a systematically lower result than intended.

`compute_royalty_amount` is called directly when constructing the royalty `CreateCoin` payments embedded in the offer settlement spend bundle: [2](#0-1) 

`royalty_split` (`request_side_royalty_split`) is attacker/offer-maker-controlled — it is simply the count of royalty-enabled NFTs being requested together in a single offer (see `request_side_royalty_split` accumulation at lines 890-894). Any wallet user constructing or accepting an offer bundling multiple royalty-enabled NFTs against a single fungible asset can trigger this path.

Concretely, for `offered_amount = -7`, `royalty_split = 3`, `percentage = 9999`:
- Current (buggy) formula: `7 // 3 = 2`, `2 * 9999 = 19998`, `19998 // 10000 = 1`
- Correct formula: `7 * 9999 = 69993`, `69993 // 3 = 23331`, `23331 // 10000 = 2`

The royalty recipient receives `1` mojo instead of the correct `2` — a 50% shortfall in this example, and the discrepancy grows with larger `royalty_split` values and larger offered amounts (since the discarded remainder from the first division can be up to `royalty_split - 1`, and that error compounds through the multiply/divide by percentage).

Note that this differs from `NFTWallet.royalty_calculation()` (used only for the informational RPC "preview" of expected royalties shown to users before accepting an offer), which has the identical operation order: [3](#0-2) 

Because both the preview and the actual settlement use the same flawed order, the displayed "expected" royalty and the actually-paid royalty are self-consistent in this codebase (unlike a case where preview and settlement diverge), but both are lower than the mathematically correct amount an NFT creator/royalty holder is entitled to.

### Impact Explanation
NFT creators/royalty holders systematically receive fewer mojos of royalty payment than the correct proportional share whenever an offer request-side bundles more than one royalty-enabled NFT (`royalty_split > 1`). This is a real, on-chain, spend-triggered fund-shortfall affecting every party relying on the royalty mechanism in offers/trades — a core NFT/DID and offers/trades feature explicitly in scope. Since royalty percentages and splits are attacker-controlled by whoever structures the offer, the shortfall can be made non-trivial by choosing values that maximize the truncation error.

### Likelihood Explanation
High likelihood of triggering: any wallet user (maker or taker) constructing a multi-NFT offer bundle with royalty-enabled NFTs will hit this path via the standard `NFTWallet.make_nft1_offer()` offer-construction flow — no special privileges or malicious peer/node behavior needed, just normal offer creation with more than one royalty-enabled NFT on one side of the trade.

### Recommendation
Reorder the arithmetic in `compute_royalty_amount()` to multiply before dividing, minimizing truncation to a single floor operation:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Apply the same fix to `NFTWallet.royalty_calculation()` so the previewed royalty summary matches the corrected payout.

### Proof of Concept
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# Offer requesting 2 royalty-enabled NFTs (royalty_split=3 simulates 3-way split)
# against an offered fungible amount of 7 mojos, with a 99.99% royalty rate.
buggy = compute_royalty_amount(offered_amount=-7, royalty_split=3, percentage=9999)
assert buggy == 1  # current behavior

# Mathematically correct royalty (multiply-before-divide):
correct = abs(-7) * 9999 // (3 * 10000)
assert correct == 2

assert buggy < correct  # royalty recipient is shorted 50% of the correct payout
```

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
