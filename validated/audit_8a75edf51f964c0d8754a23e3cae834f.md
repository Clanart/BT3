Based on my investigation, I've confirmed a real, provable analog to the Taiko "false proof economic gain" pattern in Hyperbridge's `pallet-consensus-incentives`.

### Title
Consensus relayer reward misattribution allows an attacker to be paid for other relayers' work when a batch contains multiple consensus updates - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` identifies the reward recipient by cryptographically recovering the signer from only the **first** message in a processed batch, but then pays that single recovered account for **every** `StateMachineUpdated` event present anywhere in the whole batch, regardless of which consensus message actually produced each event.

### Finding Description
The `FeeHandler::on_executed` hook is called once per batch of processed ISMP messages (`Vec<MessageWithWeight>`, `Vec<Event>`) [1](#0-0) . In `pallet-consensus-incentives`, the relayer to be rewarded is derived exclusively from `messages.get(0)` — if it is a `Message::Consensus`, the signer is recovered from its signature [2](#0-1) .

The code then builds `highest_per_state_machine` by scanning **all** `StateMachineUpdated` events in the entire `events` vector passed to the hook — not just the ones caused by `messages[0]` — and pays the single relayer recovered from message 0 a reward for every one of those state machines' height advances [3](#0-2) . The reward itself is computed from `latest_height - baseline` for each state machine and transferred from `TreasuryAccount` [4](#0-3) .

Because a single extrinsic (`handle_unsigned`) can carry a `Vec<Message>` containing several independent `Message::Consensus` entries for different state machines, and `pallet_ismp` processes and emits `StateMachineUpdated` events for each one before invoking `on_executed` once for the whole batch, the reward-attribution logic collapses multiple distinct relayers' work into a single payee: whoever happens to be `messages[0]`.

### Impact Explanation
An attacker can be paid the treasury-funded `$BRIDGE` reward (plus minted reputation, which also feeds collator selection [5](#0-4) ) for consensus updates they did not produce, simply by ensuring their own trivial/cheap consensus message for state machine A occupies index 0 of a batch that also contains a legitimate, larger consensus update for state machine B submitted by someone else. This is a genuine "false proof economic gain" analog: the wrongdoer performs disproportionately little real work (or none, if the relayer role that assembles/orders unsigned extrinsics into a block is the attacker) while diverting treasury funds and reputation intended for the actual relayer who advanced state machine B. This is a direct fund-diversion / wrong-beneficiary bug in a production reward-claim path, matching the bounty's "stealing or loss of funds" and "logic attacks" categories.

### Likelihood Explanation
Likelihood depends on how unsigned consensus messages get batched into a single call before `on_executed` fires once for the whole set. I was not able to fully trace, within the available tool budget, the exact call site in `modules/pallets/ismp/src/lib.rs` that constructs the `Vec<Message>` batch and invokes `on_executed` (e.g., whether it is per-extrinsic, i.e., attacker-controlled ordering within their own submitted call, or per-block, i.e., requiring block-author/collator collusion). If batching happens per-extrinsic and an untrusted, unsigned caller can freely order multiple `Message::Consensus` entries in one call (which the `TimeoutMessage`/`ConsensusMessage` handler code strongly suggests, since these are unsigned/permissionless submissions), the attack requires no special privilege and is directly exploitable by any relayer. This should be verified against `modules/pallets/ismp/src/lib.rs`'s dispatch/execute logic, which the available index did not surface in full.

### Recommendation
Change `on_executed` to attribute each `StateMachineUpdated` event to the specific `Message::Consensus` entry that produced it (e.g., by pairing events with their originating message via index/ordering guarantees from `pallet_ismp`, or by having the core handler return `(state_machine_id, relayer)` tuples directly) rather than recovering a single signer from `messages[0]` and applying it to the union of all events in the batch.

### Proof of Concept
1. Attacker (or any relayer) submits an unsigned batch containing two `Message::Consensus` entries: `msg_A` (attacker's own consensus proof for state machine A, signed by attacker, minimal height advance) at index 0, and `msg_B` (a legitimate consensus proof for state machine B, signed by a different, honest relayer, large height advance) at index 1.
2. `pallet_ismp` processes both messages, emitting `StateMachineUpdated` for state machine A and state machine B.
3. `on_executed` recovers only the attacker's signature from `messages[0]` (`msg_A`) as `relayer_account`.
4. The event-collapsing loop in `on_executed` [6](#0-5)  picks up the `StateMachineUpdated` for both A and B.
5. `process_message` is called for both state machines with `relayer_account` = attacker, transferring treasury funds to the attacker for both the A and B height advances — even though the attacker did not submit `msg_B`. [4](#0-3) [7](#0-6)

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
