This confirms the contrast: for the `upstream` remote, GitHub Desktop explicitly prompts the user with the `UpstreamAlreadyExists` dialog before touching an existing remote when the parent repo's clone URL doesn't match [1](#0-0) , but the `origin`/default remote's URL is instead auto-rewritten with **no dialog at all** whenever the cached GitHub API `clone_url` disagrees with the current remote [2](#0-1) .

### Title
Silent, unconfirmed rewrite of the default git remote URL from GitHub API data enables remote-hijack of push/fetch destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` is invoked every time Desktop refreshes a repository's GitHub association (on repo selection, background fetch, add-repository, push, account refresh, etc.) via `repositoryWithRefreshedGitHubRepository()` [3](#0-2) . If the `clone_url` returned by the GitHub/GHES API for the matched repository differs from the locally configured `origin` remote, and the previously cached `clone_url` matched the local remote (i.e. the user hasn't manually customized it) and the URL scheme is unchanged, Desktop automatically calls `git remote set-url` to point `origin` at the new API-supplied URL — with **no user confirmation, no hostname pinning, and no diff/warning UI** [4](#0-3) .

### Finding Description
The invariant that should hold is: the destination of `origin` (where the user's commits are pushed and where fetched refs are trusted from) must only change with explicit user awareness/consent. `updateRemoteUrl` breaks this invariant by trusting a single upstream-controlled field (`apiRepo.clone_url`) as authoritative and applying it directly to the git config:

```javascript
const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)
...
if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
``` [5](#0-4) 

`urlMatchesRemote` only rejects the update if the *hostname stays the same but owner/name differ*; it does nothing to prevent the hostname itself from being redirected to any different host, since a hostname mismatch is exactly the `!urlsMatch` condition that triggers the rewrite [6](#0-5) . The only safeguard is that the URL scheme (`https`/`ssh`) must stay the same — the host, owner, and path are unconstrained [7](#0-6) .

This is the direct structural analog of the `BathPair`/`BathHouse` bug: a security-relevant address (`RubiconMarketAddress` there, the git remote URL here) is cached in one component (`BathPair` / the local git config) but can be silently changed by another authority (`BathHouse.setMarket` / the GitHub API response) without the dependent component being made aware in a controlled way. Here it's worse than the original finding because the update path is not merely "out of sync" passively — it's an *active, automatic write* to the git remote configuration triggered by untrusted network data, whereas the smart-contract case was merely a stale read.

Contrast with the sibling `upstream` remote flow: when the *upstream* remote (fork parent) needs to be created/changed and an existing remote named `upstream` conflicts, Desktop stops and shows the user the `UpstreamAlreadyExists` dialog, explicitly listing "Current" vs "Expected" URLs and requiring the user to click "Update" [8](#0-7) [1](#0-0) . No equivalent confirmation exists for the far more consequential `origin` remote rewrite in `updateRemoteUrl`.

### Impact Explanation
`origin` is the remote used for the user's day-to-day `git push`/`git fetch`, and it's also the URL resolved by the credential/trampoline layer to decide which stored token or credential-helper entry to hand over for authentication (`findGitHubTrampolineAccount`/`findGenericTrampolineAccount` match by URL origin) [9](#0-8) . If a GHES/proxy response (an attacker-controlled "git remote/proxy response," which is in-scope per the valid-impact definition) supplies a different `clone_url` for the repository, Desktop will silently retarget `origin` to that URL. Subsequent pushes go to, and fetched content is trusted from, the attacker's host, and Desktop's own credential resolution logic will subsequently look for/prompt for credentials scoped to that new host — corrupting what the user believes they are pushing to/fetching from without any visible warning.

### Likelihood Explanation
The rewrite runs unconditionally on very common code paths — selecting a repository, background fetch/indicator refresh, and immediately after every push (`repositoryWithRefreshedGitHubRepository` called via `_selectRepositoryRefreshTasks` and `withRefreshedGitHubRepository`) [10](#0-9) [11](#0-10) . Any attacker capable of influencing the `clone_url` field of the API response for a repository the user has open (malicious/compromised GHES instance, on-path proxy for the configured API endpoint) can trigger the silent remote rewrite the next time Desktop refreshes — no unusual user action is required beyond normal use of the app.

### Recommendation
Do not silently apply `set-url` based on API data. At minimum, require the new hostname to match the existing remote's hostname (i.e., treat cross-host changes as out of scope for auto-sync) and surface a confirmation dialog analogous to `UpstreamAlreadyExists` whenever `updatedRemoteUrl`'s host differs from the current `origin` host, rather than applying `gitStore.setRemoteURL` unconditionally in `updateRemoteUrl`.

### Proof of Concept
1. User has a repository whose `origin` remote and stored `GitHubRepository.cloneURL` both point to `https://ghes.corp.example/org/repo.git` (a GHES instance).
2. Attacker controls or performs a on-path response for the GHES API endpoint used by `api.fetchRepository(owner, name)` (called from `repositoryWithRefreshedGitHubRepository`), returning a full-repository payload with `clone_url: "https://attacker.example/org/repo.git"` but the same scheme (`https`).
3. On the next repository refresh (opening the app, switching to the repo, background indicator fetch, or immediately after a push), `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [3](#0-2) .
4. Since `protocolsMatch` is true, `remoteUrlUnchanged` is true (the stored cloneURL still matches the pre-attack remote), and `urlsMatch` is false (different host), the condition passes and `gitStore.setRemoteURL('origin', 'https://attacker.example/org/repo.git')` executes with no prompt [12](#0-11) .
5. The user's subsequent `git push`/`git fetch` operations, and Desktop's credential lookup, now target `attacker.example` silently.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
