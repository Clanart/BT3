In `evmrpc/block.go`, `countBlockTxsLikeEncodeTmBlock` calls `m.AsTransaction()` on a `*types.MsgEVMTransaction` and immediately dereferences the result via `ethtx.Hash()` without checking whether `AsTransaction()` returned `nil` — which it explicitly can, per its own documented contract and per the nil-guards used everywhere else in the same package (`evmrpc/simulate.go`, `evmrpc/tx.go`, `evmrpc/utils.go`).

### Title
Nil pointer dereference in `eth_getBlockTransactionCount*` RPC via unguarded `AsTransaction()` result - (File: evmrpc/block.go)

### Summary
`AsTransaction()` on `MsgEVMTransaction` can return a `nil` `*ethtypes.Transaction` when `UnpackTxData` fails to unpack the transaction's `Data` field [1](#0-0) . Nearly every other call site in `evmrpc` explicitly checks for this nil case before dereferencing (e.g. `if ethtx == nil { continue }` in `BlockByNumber` [2](#0-1) , and the `getEthTxForTxBz` helper used across the package [3](#0-2) ). However, `countBlockTxsLikeEncodeTmBlock` does not perform this check.

### Finding Description
`countBlockTxsLikeEncodeTmBlock`, which backs the public `eth_getBlockTransactionCountByNumber`/`eth_getBlockTransactionCountByHash` RPC methods via `getEvmTxCount`, iterates over the messages returned by `filterTransactions` and, for `*types.MsgEVMTransaction`, calls `m.AsTransaction()` and immediately dereferences the returned transaction pointer: [4](#0-3) 

Unlike its sibling in `simulate.go` (`BlockByNumber`), which checks `if ethtx == nil { continue }` before use, this path calls `ethtx.Hash()` unconditionally. `filterTransactions` itself does the same unguarded pattern when building its result set [5](#0-4) , so a transaction that reaches this stage already had `AsTransaction()` called once without a nil check to compute its hash for the receipt lookup — meaning any tx that got this far and made it into `msgs` already had a non-nil transaction the first time. That reduces (but doesn't eliminate outright) the immediate reachability of a crash purely through `countBlockTxsLikeEncodeTmBlock`, since a message that failed to decode into a transaction the first time in `filterTransactions` would already have panicked earlier at line 244 of `utils.go`. The actual root vulnerability is therefore in `filterTransactions` itself: `ethtx := ... ; hash := ethtx.Hash()` with no nil guard, executed against attacker-controlled `Data` field content that only needs to fail `UnpackTxData` unpacking (e.g. a corrupted embedded tx-type Any) to return `nil, nil` from `AsTransaction()`.

### Impact Explanation
A crash here occurs in `evmrpc`, the public JSON-RPC surface, when processing any historical block containing a `MsgEVMTransaction` whose `Data` payload fails to unpack into a known `ethtx.TxData` variant (for example, an unregistered/garbled `Any` type). Because `filterTransactions` is invoked from many hot RPC paths (`eth_getBlockByNumber`, `eth_getBlockTransactionCount*`, `eth_getTransactionByBlockNumberAndIndex`, log/receipt encoding, etc.), a single such transaction included in a committed block would cause every public RPC node's goroutine handling that request to panic on `ethtx.Hash()` against a nil pointer. Depending on whether the recover/metrics wrapper present on some but not all of these call paths catches it, this can degrade to a crash of default-configuration RPC nodes when serving reads for that block — a denial-of-service against the public EVM JSON-RPC surface, which is within scope.

### Likelihood Explanation
Reaching `filterTransactions`'s unguarded path requires a `MsgEVMTransaction` to already be included in a committed block (i.e., it passed `ValidateBasic`/ante-handling) yet still fail `AsTransaction()`'s unpack at query time. `MsgEVMTransaction.Data` is a serialized proto `Any`; whether the ante handler enforces successful unpacking prior to inclusion determines whether this is truly reachable on mainnet blocks, and is not fully confirmed from the code inspected in this pass. This bounds confidence to moderate rather than confirmed-exploitable.

### Recommendation
Add a nil check identical to the pattern already used in `evmrpc/simulate.go` and `evmrpc/tx.go`'s `getEthTxForTxBz` immediately after every `m.AsTransaction()` call in `evmrpc/utils.go`'s `filterTransactions` and `evmrpc/block.go`'s `countBlockTxsLikeEncodeTmBlock`, skipping (or erroring) the message instead of dereferencing a potentially nil `*ethtypes.Transaction`.

### Proof of Concept
1. Submit/replay a block whose `MsgEVMTransaction.Data` `Any` cannot be unpacked by `UnpackTxData` (e.g., a stale/altered type URL that decodes as a message but fails typed extraction), such that it still passes ante/inclusion but `AsTransaction()` returns `(nil, nil)` at query time.
2. Call `eth_getBlockByNumber`/`eth_getBlockTransactionCountByNumber` (or any RPC method that calls `filterTransactions`) against that block height.
3. `ethtx := ... ; hash := ethtx.Hash()` at `evmrpc/utils.go:243-244` dereferences the nil `*ethtypes.Transaction`, panicking the request-handling goroutine. [6](#0-5)

		return nil
	}
	ethtx, _ := evmTx.AsTransaction()
	return ethtx
}
