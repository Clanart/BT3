### Title
Stale `ContractToAsset` reverse mapping bricks `on_timeout` refunds after `update_token`, permanently locking user funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` stores a token's cross-chain contract address in two coupled maps, `TokenContracts` (asset → contract) and `ContractToAsset` (contract → asset). `update_token` mutates both maps together, but any `send` that is already in-flight when `update_token` runs was dispatched with the *old* contract address baked into the outgoing `PostRequest.to` field. When that request eventually times out, `on_timeout` looks the asset back up via `ContractToAsset::get(dest, &to)` using the old (now-deleted) contract address, fails, and the user's escrowed/burned funds cannot be refunded — mirroring the SY-minter/YT-minter desynchronized-address bug in the external report.

### Finding Description
`send()` locks (native asset) or burns (non-native asset) the caller's tokens and dispatches an ISMP `PostRequest` whose `to` field is the token contract address read from `TokenContracts` at that moment: [1](#0-0) [2](#0-1) 

`update_token` is later used to change the configured contract address for that same `(chain, asset)` pair. It fetches the *current* `TokenContracts` entry, deletes the corresponding `ContractToAsset` reverse entry, and inserts the reverse mapping only for the *new* contract address: [3](#0-2) 

If a `send` was dispatched to the old contract address before `update_token` runs, and the destination chain never delivers it (liveness failure, or it is simply outside the timeout window), the request eventually times out. `on_timeout` re-derives the asset purely from `ContractToAsset::get(dest, &to)`, where `to` is the *old* contract address embedded in the original request: [4](#0-3) 

Because `update_token` already deleted that reverse-mapping entry, `ContractToAsset::get` returns `None` and `on_timeout` returns `Err(HftError::UnknownContractOnTimeout)` before any refund logic executes.

Per `pallet-ismp`'s timeout handler, when a module's `on_timeout` callback fails, the request commitment is deliberately restored rather than deleted so the timeout "can be retried later": [5](#0-4) 

This means the failure is not a one-off revert — it is a durable, structural failure: the reverse mapping that `on_timeout` needs was permanently removed and there is no extrinsic that restores a `ContractToAsset` entry without also repointing `TokenContracts` to the exact old address (defeating the purpose of `update_token`). The escrowed native asset or already-burned non-native asset therefore has no code path back to the sender; every retry of the timeout hits the same `UnknownContractOnTimeout` error.

This is the direct structural analog of the report: two related address/config mappings (`TokenContracts` / `ContractToAsset`, playing the role of `sy_minter_address` / `sy_wallet_address`) are updated together for the *new* state but not reconciled for messages already in flight under the *old* state, and the in-flight message's completion path (here, `on_timeout`, there, `mint_pt_yt`) depends on the now-stale linkage.

### Impact Explanation
Any user who calls `send()` shortly before governance/`CreateOrigin` calls `update_token` to rotate a chain's contract address for that asset has their locked or burned funds become permanently unrecoverable — the on_timeout refund path is guaranteed to fail for that specific in-flight request forever, since retries hit the identical missing-mapping condition. This is direct loss/lock of user funds through the pallet's own request/timeout accounting, not a hypothetical griefing vector, and matches the "stealing or loss of funds" / "timeout paths must bind ... one-time receipt handling" impact categories.

### Likelihood Explanation
`update_token` is a normal, expected maintenance operation (e.g., redeploying/migrating the `HyperFungibleToken`/`WrappedHyperFungibleToken` contract on an EVM chain, or fixing a misconfigured address) rather than a rare or adversarial admin action. Given that `send` requests can legitimately sit in flight for the full `timeout` window (attacker/user does not need to do anything special — merely have an ordinary transfer pending when the routine reconfiguration happens), the race window is realistic and will recur any time the token contract address is rotated for a chain that has outstanding transfers.

### Recommendation
- Short term: `update_token`'s `add_chains`/`remove_chains` paths should not delete the old `ContractToAsset` entry immediately. Instead, retain historical `(chain, old_contract) -> asset` mappings (e.g., keyed by a generation/epoch, or simply never removed, only superseded) so that `on_timeout`/`on_accept` for messages dispatched under a prior configuration can still resolve the correct asset.
- Alternatively, encode the local `AssetId` directly inside the dispatched `Message`/`PostRequest` body at `send`-time so that `on_timeout` and `on_accept` do not need to re-derive it from a mutable reverse-lookup table at all.
- Long term: audit every pallet/contract that keeps two or more coupled address/config mappings updated by separate admin calls (`TokenContracts`/`ContractToAsset`, `sy_minter_address`/`sy_wallet_address`-style pairs) to ensure in-flight request/response/timeout completion never depends on a mapping that can be unilaterally invalidated mid-flight.

### Proof of Concept
1. Register asset `A` for `StateMachine::Evm(X)` with contract `C1` via `register_token`.
2. Call `send(params)` for `A` to `Evm(X)`, targeting `C1`. This burns (or escrows) `params.amount` from the caller and dispatches an ISMP `PostRequest` with `to = C1`.
3. Before the destination processes the message (or before it can possibly be delivered, e.g., destination is unreachable), governance calls `update_token` for `A`/`Evm(X)` with `add_chains` pointing to a new contract `C2`. This deletes `ContractToAsset::(Evm(X), C1)` and inserts `ContractToAsset::(Evm(X), C2)`.
4. After `timeout_timestamp` elapses, a relayer submits the timeout proof for the step-2 request. `pallet-ismp`'s timeout handler calls `Pallet::<T>::on_timeout` with `to = C1`.
5. `ContractToAsset::<T>::get(Evm(X), C1)` returns `None` → `Err(HftError::UnknownContractOnTimeout)`.
6. Per `modules/ismp/core/src/handlers/timeout.rs`, the failed callback causes the commitment to be restored for retry, but every future retry repeats step 5/6 identically — the user's burned/escrowed funds from step 2 are never returned.
