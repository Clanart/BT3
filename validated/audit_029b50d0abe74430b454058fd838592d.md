### Title
Partial-commit staging re-diffs the file at apply-time, letting a repo-controlled content change between diff-render and commit silently corrupt what is staged/committed - (File: app/src/lib/git/apply.ts)

### Summary
The Sherlock finding is about a reward calculation that uses a timestamp captured *before* the value it depends on is actually available (`startDrawAuction.closedAt`) instead of the timestamp of the real event (randomness availability), so a stale reference point is used to compute something that is later acted upon. GitHub Desktop has a structurally identical "stale reference used at a later point in time" flaw in the partial-commit (line-selection) staging path: the user's line selection is captured against one rendering of a file's diff, but the patch that is actually applied to the index/commit is built from a **freshly re-fetched diff** computed later, at `stageFiles`/commit time, with no validation that the two diffs still agree.

### Finding Description
When a user stages only some lines/hunks of a file, Desktop stores an index-based `DiffSelection` (bitmap keyed by `absoluteIndex` positions within the diff hunks) on the `WorkingDirectoryFileChange` object. This selection is computed while the diff is displayed in the Changes view via `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts` (lines 3404-3513), which does attempt to reconcile selectable lines if the diff changes *while it is being viewed*.

However, when the commit is actually created, `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3681-3759`) passes the in-memory `selectedFiles` (with their previously-computed `selection`) straight into `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-169`). For any file with a partial selection, `stageFiles` calls `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`), which does this: [1](#0-0) 

```
const applyArgs: string[] = [ 'apply', '--cached', ... ]
const diff = await getWorkingDirectoryDiff(repository, file)
```

This **re-computes the diff from the working directory at the moment of staging**, not the diff that was on screen when the user made the selection. That freshly fetched diff is then fed into `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`), which walks the *new* diff's hunks/lines and decides inclusion purely via: [2](#0-1) 

```
const absoluteIndex = hunk.unifiedDiffStart + lineIndex
...
} else if (file.selection.isSelected(absoluteIndex)) {
```

`file.selection.isSelected(absoluteIndex)` blindly reuses **line-position indices from the old diff** against the **new diff's line layout**. There is no check that the diff hasn't changed (no hash/mtime/line-count comparison, no re-validation, no abort) between the moment the selection was formed and the moment the patch is generated and `git apply --cached` is run.

### Impact Explanation
If the tracked file's on-disk content changes between the time the user views/selects lines in the diff and the time `applyPatchToIndex` re-fetches the diff, the index positions no longer correspond to the same logical lines. The resulting patch can therefore:
- stage/commit lines the user never selected (including content the user explicitly deselected/excluded), or
- omit lines the user did select, or
- desynchronize hunk boundaries such that unrelated content is silently written into the commit.

This is "silent corruption of what the user commits" per the accepted impact class: the user believes they are committing exactly what they saw and checked off in the diff viewer, but the actual staged/committed content can diverge without any warning, confirmation, or error surfaced to them. Because commits are then typically pushed, this can propagate unintended/attacker-influenced content into the remote history under the user's authorship.

### Likelihood Explanation
The window between diff display and commit is attacker-influenceable because Desktop's diff/status refresh cadence, background repository refresh (`_refreshRepository`, `refreshIndicatorForRepository`), and any external process able to touch working-directory files inside a fetched repository (build tooling, editors, watchers, or filter/hook-driven content normalization triggered by files present in the cloned repository) can mutate a file's content in that gap. No local/admin access is required beyond normal use of Desktop on a repository whose content or tooling can cause the working copy to change asynchronously — this is a normal, expected occurrence in real repositories (e.g. line-ending or generated-file changes triggered by build/watch processes bundled with the repo), not a contrived environment. The bug is deterministic once the working-directory content differs from what was diffed for selection purposes: there is no code path that detects or rejects the mismatch.

I was not able to fully trace whether `getWorkingDirectoryDiff` employs any content/mtime-based caching that might mask the mismatch in common cases (index results only showed the exported symbol, not its full body), so the exact frequency of divergence in practice is uncertain; this is a caveat on likelihood, not on the existence of the code-level flaw itself, since `applyPatchToIndex` unconditionally re-fetches and never compares against the diff used to build `file.selection`.

### Recommendation
Before generating the patch in `applyPatchToIndex`, verify that the diff used to build `file.selection` is still valid against the working directory (e.g., compare a content hash/oid or the full diff structure of the newly fetched diff against the one that produced the selection). If they differ, abort the partial-stage/commit operation and force Desktop to refresh the diff and require the user to re-confirm their selection, rather than silently applying stale line-index selections to a different diff.

### Proof of Concept
1. In a repository, modify a tracked file so it has multiple hunks of changes.
2. In Desktop's Changes view, open the diff and deselect specific lines/hunks (partial selection) that you do not want committed.
3. Before clicking "Commit," cause the file's on-disk content to change in a way that shifts hunk boundaries/line counts (e.g., an external process/editor autosave appends or reformats lines, or a repository-provided build/watch script rewrites the file) — this does not require touching Desktop's UI or refreshing the diff view.
4. Click "Commit." `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and calls `formatPatch` using the **stale** `file.selection` indices from step 2 against the **new** diff.
5. Inspect the resulting commit: it can contain lines that were never selected (or omit lines that were), diverging from what was shown/approved in the UI, with no error or warning from Desktop. [3](#0-2) [4](#0-3) [5](#0-4)

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)

  if (diff.kind !== DiffType.Text && diff.kind !== DiffType.LargeText) {
    const { kind } = diff
    switch (diff.kind) {
      case DiffType.Binary:
      case DiffType.Submodule:
      case DiffType.Image:
        throw new Error(
          `Can't create partial commit in binary file: ${file.path}`
        )
      case DiffType.Unrenderable:
        throw new Error(
          `File diff is too large to generate a partial commit: ${file.path}`
        )
      default:
        assertNever(diff, `Unknown diff kind: ${kind}`)
    }
  }

  const patch = await formatPatch(file, diff)
  await git(applyArgs, repository.path, 'applyPatchToIndex', { stdin: patch })

  return Promise.resolve()
}

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
}
