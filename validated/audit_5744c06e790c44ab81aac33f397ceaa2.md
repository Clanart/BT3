### Title
Attacker-controlled royalty-split denominator causes integer-division truncation to zero, letting an offer counterparty strip NFT creator royalties - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` and the `offer_side_royalty_split` / `request_side_royalty_split` counters computed in `NFTWallet.make_nft1_offer()` divide the fungible trade amount by the *count* of royalty-enabled NFTs bundled on one side of an offer **before** applying the royalty percentage. Because this is plain integer division, an offer counterparty can inflate that count with cheap, self-created royalty-enabled NFTs to drive the per-NFT trade price (and therefore the royalty owed) to `0`, even though the real underlying trade moves substantial value. This is the exact same root cause as Derby's H-8: `nominator / denominator` truncates to zero when the denominator is adversarially or incidentally large relative to the numerator, silently zeroing out a payment that should be owed.

### Finding Description

`trade_prices` computed this way is fed as `trade_prices_list` into the offered NFT's ownership-layer spend: [4](#0-3) 

and this value is not merely informational — it is what the NFT's on-chain `NFT_TRANSFER_PROGRAM_DEFAULT` puzzle uses to derive the required royalty payment and puzzle-announcement it asserts against the paying coin, as demonstrated in the CLVM-level test: [5](#0-4) 

There, `royalty = trade_price * percentage // 10000` (e.g., `100 * 5000 // 10000 = 50`), and the payer coin must create a matching puzzle announcement for the spend bundle to be accepted. Because both the trade price (`amount // split`) and the royalty (`trade_price * percentage // 10000`) are computed with the same truncating integer division on both the taker and maker side, if `split` is made large enough that `amount // split == 0`, the required royalty becomes `0` — legitimately, by consensus rules — and the code even explicitly skips creating a royalty coin in that case: [6](#0-5) 

### Impact Explanation
A counterparty to an NFT offer can bundle the real, valuable royalty-enabled NFT together with many cheap/self-issued royalty-enabled NFTs (which the attacker fully controls the creation of) on the same side of the trade to inflate `offer_side_royalty_split` or `request_side_royalty_split`. This forces `amount // split` to floor to `0`, which zeroes the royalty owed to the legitimate NFT creator regardless of the actual price paid for their NFT. The trade still completes successfully on-chain (all announcement assertions match because both sides compute the same zero value), so from consensus's perspective nothing is invalid — but the creator is deprived of a royalty payment they are economically entitled to under the NFT1 royalty convention. This is a reward/fee-redirection-style loss reachable by any unprivileged offer counterparty using only a self-constructed spend bundle/offer, with no special privileges required.

### Likelihood Explanation
Creating extra low-cost NFTs (e.g., minting a batch of throwaway singletons with a royalty transfer program attached) is cheap and fully within reach of any wallet user constructing an offer. No cooperation from the honest counterparty beyond accepting a seemingly normal multi-asset offer is required, and the resulting spend bundle is entirely valid by consensus rules, so it will be accepted by any full node. The main constraint is the number of NFTs that must be bundled to make `amount // split` truncate to zero, which scales with trade size but is trivially achievable for small-to-medium trade amounts and remains achievable for larger amounts by bundling more NFTs.

### Recommendation
Avoid dividing the fungible trade amount by the royalty-NFT count before multiplying by the royalty percentage. Instead, compute each NFT's royalty independently from its own share of value (e.g., multiply first by percentage, then divide, and/or track any truncation remainder across the split so that the sum of paid royalties is bounded below by the mathematically expected total), or add a scaling factor (analogous to the recommended `BASE_SCALE` in the referenced report) throughout `compute_royalty_amount()`, `royalty_calculation()`, and the `trade_prices` computation in `make_nft1_offer()` so that per-NFT truncation cannot drive the aggregate royalty to zero when trade value and percentage are both nonzero.

### Proof of Concept
1. Attacker mints a legitimate-looking royalty-enabled NFT `X` (percentage `P`) that they intend to sell, plus `N` additional throwaway royalty-enabled NFTs (`Y1..YN`) they also control, cheaply.
2. Attacker creates (or accepts) an offer requesting `X, Y1..YN` together for `amount` mojos/CAT such that `amount // (N+1) == 0` (choose `N+1 > amount`).
3. `make_nft1_offer()` computes `offer_side_royalty_split = N+1` (`chia/wallet/nft_wallet/nft_wallet.py:888-894`), so `trade_prices = [(amount // (N+1), ...)] = [(0, ...)]` (`nft_wallet.py:896-902`).
4. The per-asset filter at `nft_wallet.py:1027-1031` computes `0 * P // 10000 == 0` and therefore passes an empty `trade_prices_list` to `generate_signed_transaction()`, meaning no royalty condition/coin is required or created for `X`.
5. The resulting spend bundle validates fully on-chain (all NFT ownership-layer transfer-program assertions are satisfied because both sides agree on a `0` royalty), and `X`'s creator receives no royalty despite `X` changing hands as part of a trade worth `amount` mojos.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
