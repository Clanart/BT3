### Title
Integer-truncated exponent in `calc-liq-factor-exp()` causes abrupt, misconfigured jumps in graduated liquidation severity - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp()` is meant to apply a DAO-configured curve exponent (`LIQ-CURVE-EXP`, in BPS units where `10000` = exponent `1.0`) to the linear liquidation factor, producing a graduated liquidation severity curve as `LTV` moves from `LTV-LIQ-PARTIAL` to `LTV-LIQ-FULL`. Because the exponent is applied via integer division `(/ exp BPS)`, any configured exponent strictly between `10000` and `19999` collapses to the same integer power (`n = 1`), producing results identical to a pure linear curve (`exp = 10000`) regardless of how the DAO actually tuned it. At `exp = 20000` the result abruptly becomes quadratic. This is the same class of bug as the reported `_calculate_service_fee()` issue: a value that should vary smoothly with a configuration parameter instead stays flat across a wide "dead zone" and then snaps discontinuously at an integer-multiple threshold.

### Finding Description
`calc-liq-factor-exp` at [1](#0-0) :

```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

- For `exp > BPS`, the code computes `n = exp / BPS` using Clarity integer division. For any `exp` in `(10000, 19999]`, `n = 1`, so the formula reduces to `factor^1 / BPS^0 = factor` — mathematically identical to the `exp == BPS` linear branch. The DAO's intended "slightly aggressive" curve (e.g. `exp = 12000`, `15000`, `19000`) is silently ignored and treated as perfectly linear.
- At `exp = 20000` the formula suddenly jumps to `factor^2 / BPS` (quadratic), and stays flat again for the entire range `(20000, 29999]` before jumping to cubic at `30000`, etc.
- For any `exp < BPS` (the "gentle curve" branch), the code ignores the actual exponent value entirely and always applies a fixed `sqrti(factor * BPS)` (equivalent to exponent `0.5`), regardless of whether the DAO configured `9999` or `100`.

This value, `liq-pct-scaled`, is then fed directly into the liquidation math in `calc-liquidation-params` [2](#0-1) , which determines:
- `liq-penalty` via `calc-liq-factor-bound` (the liquidator's bonus rate), and
- `max-debt-usd` via `calc-liq-debt-repay` (the maximum debt that can be liquidated in a single call), used inside `liquidate` at [3](#0-2) .

Direction of the error and who profits: whenever the DAO configures `LIQ-CURVE-EXP` intending a moderately super-linear curve (any value in `(10000, 20000)`, `(20000, 30000)`, etc.), the actual computed `liq-pct-scaled` is larger than intended for early-stage (low-factor) liquidations, because a true `factor^1.x` (x>0) curve for `factor < 1` (BPS-scaled fraction) is smaller than pure linear `factor`. This means liquidators are allowed to seize more collateral and receive a higher penalty/bonus than the DAO intended as soon as a position crosses `LTV-LIQ-PARTIAL`, at the direct expense of the borrower whose collateral is over-liquidated. Liquidators (any address calling the public `liquidate` function) are the ones who profit; borrowers are the ones harmed.

### Impact Explanation
This is a genuine calculation bug in the liquidation-severity pricing path, not a third-party oracle or DAO-registry-configuration issue — the DAO setting `LIQ-CURVE-EXP` to any value other than exactly `10000`/`20000`/`30000`... is legitimate, documented usage (per `docs/egroups.md`), and the contract silently miscomputes the curve for the vast majority of that legitimate configuration space. The result is over-liquidation of borrower collateral (excess collateral/penalty transferred to liquidators beyond what the DAO's risk parameters intended), which constitutes theft of user funds during liquidation events. Given the currently-deployed egroups all use `LIQ-CURVE-EXP: u10000` (exactly `BPS`, the trivially-correct linear case) [4](#0-3) , the bug is currently dormant, but any future governance-approved curve change to a "graduated" exponent (which the parameter and docs explicitly support) reintroduces it silently.

### Likelihood Explanation
The bug triggers automatically and deterministically the moment the DAO sets any `LIQ-CURVE-EXP` value that is not an exact multiple of `10000` (or below `10000`, where the exponent value is ignored entirely). No attacker action or oracle manipulation is required — any liquidator calling the public `liquidate` function benefits from the miscalculated, more-lenient-than-intended `liq-pct-scaled`/`liq-penalty` automatically. Likelihood is tied to whether/when the DAO actually configures a non-trivial curve exponent, which the parameter's existence and documentation indicate is expected future usage.

### Recommendation
Replace the integer-division-based exponentiation in `calc-liq-factor-exp` with a fixed-point power function that scales continuously with `exp` (e.g., using a proper `bps`-scaled `pow` via repeated squaring/logarithm approximation, or restrict `LIQ-CURVE-EXP` at `egroup.clar` insert/update validation time to only the discrete set of exponents the formula can correctly represent, such as `{5000 (sqrt), 10000, 20000, 30000, ...}`, rejecting all other values with an explicit error).

### Proof of Concept
1. DAO governance calls `egroup insert`/`update` with `LIQ-CURVE-EXP = u15000` (intending exponent 1.5, a moderately aggressive graduated curve).
2. A borrower's position LTV crosses `LTV-LIQ-PARTIAL`, producing `liq-pct-linear = factor` (e.g., `2000` bps = 0.2, a small early-liquidation factor).
3. `calc-liq-factor-exp(factor=2000, exp=15000)` computes `n = 15000 / 10000 = 1` (integer division), so it returns `factor^1 / BPS^0 = 2000` — identical to the pure-linear case, instead of the intended smaller value that a true `factor^1.5` curve would produce (`0.2^1.5 ≈ 0.089`, i.e. ~890 bps).
4. This inflated `liq-pct-scaled` flows into `calc-liq-factor-bound` (higher `liq-penalty`) and `calc-liq-debt-repay` (higher `max-debt-usd`) inside `calc-liquidation-params`, letting the liquidator liquidate roughly 2.2x more debt/collateral than the DAO's configured curve intended, at the borrower's expense.
5. Repeating with `exp = 19999` produces the exact same (wrong) result as `exp = 15000`; bumping to `exp = 20000` produces a sudden jump to the quadratic branch — demonstrating the discontinuous, misconfigured-threshold behavior analogous to the reported `_calculate_service_fee()` cliff.

;; Graduated liquidation parameter calculation
;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
      max-debt-usd: max-debt-usd
    }))
