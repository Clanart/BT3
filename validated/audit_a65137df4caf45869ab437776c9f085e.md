### Title
`Kip71GasTarget` governance parameter accepts zero via `noopFormatChecker`, causing division-by-zero panic in `NextMagmaBlockBaseFee` - (File: kaiax/gov/param.go, params/kip71_config.go)

### Summary
The Kaia governance-parameter framework validates parameter values with a `FormatChecker` function that is invoked at vote-creation/insertion time, far away from where the value is actually consumed. `Kip71GasTarget` is registered with `noopFormatChecker` (no validation at all), while the sibling parameter `Kip71BaseFeeDenominator` explicitly checks `v != 0`. The consumer of `GasTarget`, `params.KIP71Config.NextMagmaBlockBaseFee`, divides by `gasTarget` without any defensive zero-check, unlike its handling of `BaseFeeDenominator` (which has an explicit `== 0` fallback). This is the same "validation lives away from the point of use, and an assumption of prior validation is silently wrong" pattern described in the Trail-of-Bits report about `LoanState`/`LoanFactoryBase`.

### Finding Description
Governance parameters are registered in a table with a `Canonicalizer` and `FormatChecker`: [1](#0-0) 

`Kip71BaseFeeDenominator` explicitly rejects zero (`v != 0`), but `Kip71GasTarget` uses `noopFormatChecker`, which performs no validation at all: [1](#0-0) 

This `FormatChecker` is the only gate applied when a vote is created/canonicalized, both through `PartialParamSet.Add` and through `headergov.NewVoteData`: [2](#0-1) [3](#0-2) 

Once a vote is included in a block header and processed by `HandleVote`/`AddVote`, the raw (unchecked) value becomes part of the active `ParamSet`, and is later converted directly into a `KIP71Config` via `ToKip71Config()` with no re-validation: [4](#0-3) [5](#0-4) 

The consumer, `KIP71Config.NextMagmaBlockBaseFee`, assumes `GasTarget` was already validated upstream. It defends against `BaseFeeDenominator == 0` with an explicit fallback, but performs no equivalent check for `GasTarget`, dividing by it unconditionally when `parentGasUsed != gasTarget`: [6](#0-5) 

If `GasTarget` is voted to `0` (accepted because `noopFormatChecker` never rejects it) and any block thereafter has `parentGasUsed > 0`, the code path `parentGasUsed > gasTarget` is taken and `x.Div(x, new(big.Int).SetUint64(gasTarget))` divides by zero, panicking (`big.Int.Div` panics on divide-by-zero) inside consensus-critical block-header verification (`VerifyMagmaHeader`) and fee-history/fee-oracle code paths.

### Impact Explanation
`NextMagmaBlockBaseFee` is called both when producing a block (base-fee calculation) and when verifying a block header (`VerifyMagmaHeader`), and additionally in the `eth_feeHistory` RPC computation path (`node/cn/gasprice/feehistory.go`). A panic here during block verification/import would crash node processes running Magma/KIP-71, i.e., a chain-halting bug reachable purely by successfully getting a `GasTarget=0` governance value into the active parameter set — something the validation framework is nominally supposed to prevent but silently fails to enforce for this specific parameter due to using `noopFormatChecker` instead of the correct non-zero check that its sibling `BaseFeeDenominator` uses. This matches "acceptance of an invalid transaction or block" / state divergence between nodes (crash vs. non-crash depending on code path) permitted under the assessment scope for governance parameters.

### Likelihood Explanation
Reaching this bug requires a governance vote for `Kip71GasTarget` with value `0` to be accepted into a block header and processed. This is gated by the governing/voting mechanism (single-governance-mode `GoverningNode` or committee voting in other modes), so it is not exploitable by a fully unprivileged public caller, but it lies squarely in the "governance parameters" category explicitly listed as in-scope. The core defect — a validation helper (`FormatChecker`) that is supposed to guard a value at declaration time but doesn't, for a parameter that is unconditionally used as a divisor at its point of consumption without any local re-check — is a direct structural analog to the reported `LoanState`/`LoanFactoryBase` issue: validation is assumed to have happened elsewhere and doesn't actually occur.

### Recommendation
- **Short term:** Change `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` to reject `v == 0`, matching the pattern already used for `Kip71BaseFeeDenominator`.
- **Long term:** Add a defensive zero-check directly inside `KIP71Config.NextMagmaBlockBaseFee` (`params/kip71_config.go`) before dividing by `gasTarget`, mirroring the existing `BaseFeeDenominator == 0` fallback, so the consensus-critical function does not rely solely on upstream governance-vote validation.

### Proof of Concept
1. As the governing node (or via committee vote in the applicable governance mode), submit a governance vote setting `governance.kip71.gastarget` (i.e. `Kip71GasTarget`) to `0`. Because its `FormatChecker` is `noopFormatChecker`, the vote is accepted by `NewVoteData`/`PartialParamSet.Add` with no rejection.
2. Once the vote is embedded in a block header and processed via `PostInsertBlock`/`HandleVote`/`AddVote`, the active `ParamSet.GasTarget` becomes `0`, and any subsequent `ParamSet.ToKip71Config()` call yields a `KIP71Config{GasTarget: 0, ...}`.
3. On the next Magma-enabled block whose parent has `GasUsed > 0`, `NextMagmaBlockBaseFee` computes `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)`; since `parentGasUsed > gasTarget (0)`, it executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, causing a runtime panic in `big.Int.Div`.
4. This panic occurs both during block production (base fee calculation for the next block) and during block header verification (`VerifyMagmaHeader`), crashing the node process — a consensus-critical denial-of-service condition traceable directly to the missing validation identified above.

func (p PartialParamSet) Add(name string, value any) error {
	param, ok := Params[ParamName(name)]
	if !ok {
		return ErrInvalidParamName
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		return err
	}

	if !param.FormatChecker(cv) {
		return ErrInvalidParamValue
	}

	p[ParamName(name)] = cv
	return nil
}

// NewVoteData returns a valid, canonical vote data.
// If return is not nil, the name and the value is valid.
// The format of the value is checked, but consistency and deprecation are NOT checked.
// Deprecation (gov.DeprecatedAt) is the caller's responsibility — see Vote() and VerifyVote().
func NewVoteData(voter common.Address, name string, value any) VoteData {
	param, ok := gov.Params[gov.ParamName(name)]
	if !ok {
		param, ok = gov.ValidatorParams[gov.ParamName(name)]
		if !ok {
			logger.Error("Invalid vote name", "name", name)
			return nil
		}
	}

	cv, err := param.Canonicalizer(value)
	if err != nil {
		logger.Error("Canonicalize error", "name", name, "value", value, "err", err)
		return nil
	}

	if !param.FormatChecker(cv) {
		logger.Error("Format check error", "name", name, "value", value)
		return nil
	}

	return &voteData{
		voter: voter,
		name:  gov.ParamName(name),
		value: cv,
	}
}
