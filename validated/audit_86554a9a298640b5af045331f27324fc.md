### Title
Non-String or query/body-divergent `shop` param bypasses sanitization in `sanitized_params`, leaking unsanitized value into trust-sensitive redirect/login URLs - (File: `lib/shopify_app/controller_concerns/sanitized_params.rb`)

### Summary
`sanitized_params` only overwrites the `:shop` key in its returned copy when the top-level, Rails-merged `params[:shop]` is a `String`; it also selects the parameter set to copy based on `request.post?` (`request.request_parameters` vs `request.query_parameters`), which can diverge from the merged `params` used for the sanitization decision. This lets an attacker supply a non-`String` (or query-string, on a POST) `shop` value that is copied verbatim into the object returned by `sanitized_params`, without ever passing through `ShopifyApp::Utils.sanitize_shop_domain`.

### Finding Description
`sanitized_params` is defined as: [1](#0-0) 

It picks the parameter hash to clone based on `request.post?` — for POST requests this is `request.request_parameters` (body only), for GET it is `request.query_parameters`. It then only calls `sanitize_shop_param` (which internally invokes `ShopifyApp::Utils.sanitize_shop_domain`) when `params[:shop]` — the framework's *merged* params (query + body + route) — `is_a?(String)`: [2](#0-1) 

Two independent gaps exist:
1. **Non-String bypass**: If an attacker sends `shop` as an array or hash (e.g. `shop[]=evil.myshopify.com` or `shop[foo]=bar`), `params[:shop].is_a?(String)` is `false`, so the `if` branch is skipped entirely. The un-sanitized `shop` key already present in the cloned body/query hash (`params_copy`) is returned as-is, with no call to `sanitize_shop_param` / `sanitize_shop_domain` ever validating it.
2. **request_parameters vs query_parameters divergence**: For POST requests the method clones only `request.request_parameters` (body), while the guard condition and the sanitized replacement value are both derived from the framework's merged `params`. If the attacker places a `shop` value only in the query string of a POST request, it is absent from the cloned body hash, so nothing in the returned copy reflects that value — but any caller relying on `sanitized_params` to fully represent "the acted-on request data" gets an incomplete/inconsistent view compared to what `params` (used elsewhere, e.g. `session_shop_conflicts_with_params`, `parse_shop_from_jwt` fallback, `params[:shop]` checks in `login_protection.rb`) would report.

These sanitized (or unsanitized-but-passed-through) values are consumed directly in trust-affecting flows:
- `login_url_params` in `lib/shopify_app/controller_concerns/login_protection.rb` builds `query_params[:shop] = sanitized_params[:shop]` and uses it to construct the `login_url_with_optional_shop` redirect target. [3](#0-2) 
- `redirect_uri_for_embedded` in `lib/shopify_app/controller_concerns/redirect_for_embedded.rb` merges `sanitized_params` into the redirect query string sent back to the app-bridge redirect URL. [4](#0-3) 

`referer_sanitized_shop_name` does correctly always run the referer's `shop` query value through `sanitize_shop_param`/`sanitize_shop_domain` regardless of type, since `Rack::Utils.parse_query` values are always strings: [5](#0-4) 
so the referer path itself is not directly exploitable the same way, but `sanitized_params` remains the weak link because it is the one method whose output is spliced wholesale into redirect/login URLs without a per-value type/format guard beyond the flawed `is_a?(String)` check.

### Impact Explanation
An attacker can craft a request with a malformed (non-String) `shop` parameter that skips the `ShopifyApp::Utils.sanitize_shop_domain` validation entirely, yet still flows into the query string of `login_url_with_optional_shop` / `redirect_uri_for_embedded`. Depending on how `to_query`/`CGI` serializes the array/hash and how the receiving `login_url` or embedded-redirect endpoint parses it, this can result in an attacker-controlled string reaching a `shop=` query parameter that was never checked against the `.myshopify.com` domain allow-pattern enforced by `sanitize_shop_domain`. This maps to the "cross-shop access / open redirect from an unsanitized shop value" impact class: a value that should have been constrained to a valid shop domain can instead carry arbitrary attacker content into a redirect target or into shop-scoped lookups performed later by controllers trusting `sanitized_params`/`sanitized_shop_name`.

### Likelihood Explanation
The precondition is minimal: any unauthenticated request to a controller including `ShopifyApp::LoginProtection` or `ShopifyApp::RedirectForEmbedded` (both of which mix in `SanitizedParams`) with a crafted `shop` param (array/hash instead of scalar string, or shop supplied only in the query string of a POST) is sufficient — no session, token, or HMAC is required to trigger the branch. This is trivially repeatable and requires no privileged access, matching the "unprivileged attacker" scope of the audit.

### Recommendation
- In `sanitize_shop_param`, coerce/validate the type explicitly (e.g., `return unless params[:shop].is_a?(String)` before calling `sanitize_shop_domain`, and treat any non-String value as absent/invalid rather than leaving it unsanitized in the output).
- In `sanitized_params`, always overwrite (or delete) the `:shop` key in `params_copy`, whether or not the merged `params[:shop]` is a String — i.e., if it's not a valid String, remove the `:shop` key from `params_copy` instead of silently passing through whatever was cloned from `request_parameters`/`query_parameters`.
- Base the parameter source and the sanitization decision on the *same* parameter set (e.g., always derive both from `request.parameters`, or explicitly merge `query_parameters` and `request_parameters` before deciding), to eliminate the `request.post?` branching divergence.

    def sanitized_params
      parameters = request.post? ? request.request_parameters : request.query_parameters
      parameters.clone.tap do |params_copy|
        if params[:shop].is_a?(String)
          params_copy[:shop] = sanitize_shop_param(params)
        end
      end
    end
