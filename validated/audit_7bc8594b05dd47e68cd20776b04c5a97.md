### Title
Blame proof reveals ECDH shared key before the per-message proof-of-possession is verified, decrypting a co-opted victim's share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts every incoming `EncryptedMessage` and immediately produces an `EncryptionKeyProof` (the ECDH shared key plus a DLEq proof over it), while the sender's Schnorr proof-of-possession for the per-message key is only queued into a `BatchVerifier`. If the decrypted share bytes fail `C::F::from_repr`, the function returns `Err(InvalidShare { blame: Some(..) })` early — before `batch.verify_with_vartime_blame()` ever runs — so a blame proof revealing the ECDH shared key is emitted for a message whose PoP was never verified.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Encryption::decrypt` queues `msg.pop` into the batch verifier (lines 479-485) and then unconditionally computes `key = ecdh(self.enc_key, msg.key)` and constructs `EncryptionKeyProof { key, dleq }` (lines 487-499). The whole point of `pop` is documented in `EncryptedMessage` (lines 83-90): without it, Eve can copy Alice's per-message key `X` into a message to Bob, causing Bob to publish `bX` in a blame argument, which decrypts Alice's real share to Bob.

In `crypto/dkg/pedpop/src/lib.rs` `calculate_share` (lines 476-499), the loop does:

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
...
}
batch.verify_with_vartime_blame().map_err(...)?;
```

The `?` inside `ok_or_else` exits the function *before* `batch.verify_with_vartime_blame()`. The `BatchId::Decryption(l)` → `blame: None` mapping at lines 493-496 is dead code for this path: a malformed-share error never reaches the batch verification that would reject an invalid PoP. The same holds for any participant whose `share_verification_statements` were queued — actually for the failing participant the batch is simply never checked.

An attacker therefore:
1. Observes victim Alice's `EncryptedMessage` to Bob on the authenticated channel (key `A_key`, PoP, ciphertext).
2. Sends Bob a message copying `key = A_key` and Alice's `pop`, but with `msg` bytes malleated to a non-canonical field encoding (e.g. all `0xFF`, exactly as `invalidate_share_serialization` does in the test suite).
3. Bob's `decrypt` computes `ecdh = b·A_key`, returns the blame proof containing it; `from_repr` fails; `calculate_share` returns `InvalidShare { blame: Some(...) }` — which the protocol intends to be published.
4. The published ECDH shared key decrypts Alice's *original, valid* share ciphertext to Bob, leaking Alice's contribution to Bob's FROST secret share.

### Impact Explanation
A FROST secret share (`polynomial(&self.coefficients, i)` output) is disclosed to anyone who sees the blame proof and the ciphertext. Depending on the threshold configuration, leaking shares to unauthorized parties reduces the effective security of the multisig; combined with shares leaked the same way for other victims, it can enable reconstruction of the group private key or individual shares the adversary has no right to — the analog of "querying metadata for a database he has no access to": decryption material the sender never authorized is obtained via a specially crafted input.

### Likelihood Explanation
Reachable by any unprivileged DKG participant (or anyone able to feed bytes into `EncryptedMessage::read` → `calculate_share`), using only public channel data (the victim's encrypted share message). No collusion, no key compromise needed; requires only copying a point encoding and PoP bytes and overwriting the ciphertext with a non-canonical scalar encoding. ChaCha20 keystream malleation also offers a second variant: flipping ciphertext bits so the share deserializes to a *wrong but canonical* scalar still produces a blame proof for the copied key after batch failure — but note in that variant the PoP *is* verified (batch runs), so only the non-canonical-early-return path bypasses the PoP.

### Recommendation
Verify the per-message PoP before releasing decryption material. Concretely: either verify `msg.pop` eagerly inside `Encryption::decrypt` (or immediately after the loop, before any early return can carry a blame proof out), or restructure `calculate_share` so `from_repr` failures are accumulated and the batch verification still runs, returning blame only for shares whose PoP verified. Ensuring `EncryptionKeyProof` is never constructed/returned for a message with an unverified PoP preserves the invariant documented in `EncryptedMessage`'s comments.

### Proof of Concept
1. Run a PedPoP DKG over `dalek-ff-group` `Ristretto` with `t=2, n=3`. Alice (P1) sends Bob (P2) `EncryptedMessage { key: A_key, pop, msg }` containing Alice's share `f_a(2)`.
2. Eve constructs `EncryptedMessage::read` bytes: `A_key || pop || msg'` where `msg'` is 32 bytes of `0xFF` (non-canonical scalar, mirroring `invalidate_share_serialization`, crypto/dkg/pedpop/src/encryption.rs:217-239).
3. Bob calls `KeyMachine::calculate_share` with Eve's message in place of (or alongside) Alice's under Eve's participant index — or simply feeds the crafted message as any sender. `decrypt` computes `shared = ecdh(b, A_key)`, builds `EncryptionKeyProof { key: shared, dleq }`; `from_repr` fails; the function returns `InvalidShare { blame: Some(proof) }` before `batch.verify_with_vartime_blame()` executes — Eve's lack of knowledge of `a_key` is never detected.
4. The blame proof is published (its protocol purpose). Anyone applies `cipher::<C>(context, &shared).apply_keystream(...)` to Alice's original `msg` ciphertext, recovering Alice's share `f_a(2)` — a secret Alice encrypted only for Bob, disclosed via a message Eve never possessed the key for.
