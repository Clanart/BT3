### Title
Missing-map-entry panic in `GeneratorPromotion::complete` allows a participant to crash promotion - ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary
Analogous to the ksmbd `smb_lock` bug — where bookkeeping checks pass but a later unconditional dereference of a "guaranteed present" object crashes the kernel — `GeneratorPromotion::complete` validates only the *count* and *upper bound* of the `proofs` map, then unconditionally `unwrap()`s `proofs.get(&i)` for every expected participant index. A `proofs` map that passes both checks while omitting one non-self participant causes a panic (Rust's NULL-deref analog), aborting the promotion.

### Finding Description
`complete` performs two validations on the caller-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`: [1](#0-0) 

1. `proofs.len() == n - 1`
2. every key `i` satisfies `u16::from(i) <= params.n()`

It then iterates `1 ..= params.n()`, skips `params.i()`, and dereferences each entry without checking presence: [2](#0-1) 

The two checks do not imply that `proofs` contains every index `1..=n` except `params.i()`. A map containing `params.i()` as a key (or simply omitting some other index `j` while including a duplicate-free set of `n-1` valid-but-wrong indexes) satisfies both checks. When the loop reaches the omitted `j`, `proofs.get(&j)` returns `None` and `unwrap()` panics — the same shape as the kernel bug: validation state (size/bounds) diverged from the actual set contents, and a later "invariant" dereference faults.

This mirrors the CVE's case 3 precisely: a code path assumes an object is present because prior checks "should" have guaranteed it, but the checks tracked only cardinality/bounds, not identity of the entries.

### Impact Explanation
`complete` is a listed public-input API: the `proofs` map is populated from `GeneratorProof`s supplied by other participants (`GeneratorProof::read` is explicitly an untrusted-bytes entry point). A single faulty/malformed submission — a proof filed under `params.i()`'s index, or a set missing one participant — deterministically panics every node that runs `complete` on it. That aborts generator promotion for the whole set, stalling any signing pipeline that depends on the promoted `ThresholdKeys` (e.g., Bitcoin `Schnorr` half-aggregate signing over a promoted generator). Funds whose spend path requires the promoted key become temporarily unspendable — a remote, input-triggered availability failure, matching the CVE's A:H impact.

### Likelihood Explanation
Reachable by any party able to submit a `GeneratorProof` into the `complete` map — the exact "untrusted bytes fed to a complete API" surface in scope. No threshold cooperation or collusion is required; one malformed map entry suffices, and the panic is deterministic rather than dependent on allocation failure (unlike the kernel's `smb_flock_init` OOM precondition).

### Recommendation
Replace the unconditional `unwrap()` with a checked lookup returning `PromotionError`, e.g. `proofs.get(&i).ok_or(PromotionError::MissingParticipant(i))?`, or validate upfront that the key set equals `all participants minus params.i()` (rejecting `params.i()` itself as a key) before iterating. This converts the panic into a blameable `InvalidProof`/`MissingParticipant` error, consistent with how `dkg` surfaces `DuplicatedParticipant`/`NotParticipating` via `view()`.

### Proof of Concept
```rust
// Setup: n participants, self is params.i() == Participant(1).
// Attacker-controlled `proofs` map has len == n - 1 and all keys <= n,
// but contains key Participant(1) (self) and omits Participant(2).

let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), proof_for_1); // self index — invalid
for i in 3 ..= n {
    proofs.insert(Participant::new(i).unwrap(), proof_for_i);
}
assert_eq!(proofs.len(), usize::from(n) - 1); // check 1 passes
// all keys <= n                              // check 2 passes

promotion.complete(&proofs);
// loop: i = 1 skipped (i == params.i())
//       i = 2 => proofs.get(&Participant(2)) == None => unwrap() PANICS
```
