### Title
`LoginProtection#current_shopify_domain` trusts the unauthenticated `shop` request parameter over the authenticated session domain, mirroring the unfixed `_onWithdraw`-style bug - (File: `lib/shopify_app/controller_concerns/login_protection.rb`)

### Summary
The reported LoopFi bug is a "half-fix": one code path (`_onDeposit`) was corrected to operate on the caller-supplied, validated target (`position`) while the parallel path (`_onWithdraw`) was left using the wrong, untrusted target (`address(this)`). The `shopify_app` gem shows the exact same pattern in shop-domain resolution: the **new** Token Exchange auth path was hardened (per `CHANGELOG.md` entry for PR #2081) so that `current_shopify_domain` no longer reflects the unauthenticated `shop` query parameter and instead always resolves from the verified ID token/session. The **legacy** OAuth/cookie-based path (`ShopifyApp::LoginProtection`, used whenever `use_new_embedded_auth_strategy?` is false) was never updated to match, and still resolves `current_shopify_domain` by preferring the unauthenticated, user-controllable `shop` parameter over the authenticated session's shop.

### Finding Description
In `lib/shopify_app/controller_concerns/login_protection.rb`: [1](#0-0) 

```ruby
def requested_shopify_domain
  sanitized_shop_name
end

def authenticated_shopify_domain
  current_shopify_session&.shop
end

def current_shopify_domain
  shopify_domain = requested_shopify_domain || authenticated_shopify_domain
  ShopifyApp::Logger.info("Installed store  - #{shopify_domain} deduced from user session")
  shopify_domain
end
```

`requested_shopify_domain` is just the sanitized `params[:shop]` value — fully attacker-controlled on any request. `current_shopify_domain` prefers this value over the value derived from the actual authenticated `current_shopify_session`.

Compare this to the analogous, already-hardened logic in the Token Exchange concern (`lib/shopify_app/controller_concerns/token_exchange.rb`), which the changelog explicitly calls out as fixed: [2](#0-1) 

```ruby
def current_shopify_domain
  authenticated_shopify_domain_from_token
rescue *INVALID_SHOPIFY_ID_TOKEN_ERRORS => e
  respond_to_invalid_shopify_id_token(e)
end
...
def reject_mismatched_requested_shopify_domain
  requested_domain = requested_shopify_domain
  return false if requested_domain.blank?

  authenticated_domain = authenticated_shopify_domain_from_token
  return false if authenticated_domain.blank? || authenticated_domain == requested_domain

  ShopifyApp::Logger.debug("Shop context validation failed")
  head(:unauthorized)
  true
end
``` [3](#0-2) 

The changelog entry states this exact intent: `current_shopify_domain` should never reflect the `shop` query parameter, and `requested_shopify_domain` should be reserved for bootstrap/routing use only — this rule was applied to the token-exchange concern but not `LoginProtection`.

`current_shopify_domain` in the legacy path is documented and used as an authorization/context signal, e.g. in `fullpage_redirect_to` and `return_address`: [4](#0-3) 

Note that `login_again_if_different_user_or_shop`'s `session_shop_conflicts_with_params` check (which forces a re-login/redirect when `params[:shop] != current_shopify_session.shop`) does provide a mitigating control against this specific flow in `EnsureHasSession`, but `current_shopify_domain` is a public, reusable helper (used in generators like `unauthenticated_home_controller.rb`, `fullpage_redirect_to`, `return_address`, and any app-level code calling it directly) that does not benefit from that same guard and can be invoked outside of that action lifecycle or overridden/called independently.

### Impact Explanation
Any code path — first-party app code or gem-internal helpers — that relies on `current_shopify_domain` for tenant-scoping decisions in a `LoginProtection`-based (legacy, non-token-exchange) controller can be tricked into treating a request for shop A's authenticated session as being "for" attacker-chosen shop B simply by adding `?shop=B` to the request, since the resolution order favors the unauthenticated parameter. This is the same class of bug as the original report: use of the wrong, less-trusted contextual value (query param) instead of the correct, verified value (authenticated session) — undermining per-tenant isolation guarantees the gem is supposed to provide.

### Likelihood Explanation
Likelihood is moderate: `LoginProtection`/legacy OAuth is still the default flow unless `use_new_embedded_auth_strategy?` is enabled, so this code executes for a large share of apps built on this gem. The `login_again_if_different_user_or_shop` before_action reduces exposure specifically within `EnsureHasSession`-protected actions, but `current_shopify_domain` remains callable elsewhere (custom controllers, generator templates, `fullpage_redirect_to`, `return_address`) without that guard, and the asymmetry with the just-fixed token-exchange path is a strong signal this was an intentional fix that was not backported to the legacy path.

### Recommendation
Mirror the fix applied to `ShopifyApp::TokenExchange` in `ShopifyApp::LoginProtection`: change `current_shopify_domain` to resolve from `authenticated_shopify_domain` (the verified session) first, falling back to `requested_shopify_domain` only when no session exists (e.g., pre-auth bootstrap), and reserve `requested_shopify_domain` strictly for bootstrap/routing use, never for authorization or tenant scoping — consistent with the documented convention:
```ruby
def current_shopify_domain
  shopify_domain = authenticated_shopify_domain || requested_shopify_domain
  ...
end
```

### Proof of Concept
1. Configure an app using the legacy (non-token-exchange) OAuth flow with `ShopifyApp::LoginProtection`/`EnsureHasSession` included in a custom controller that calls `current_shopify_domain` directly (e.g., for logging, redirect URL construction, or a custom authorization check) outside of an action guarded by `login_again_if_different_user_or_shop`.
2. As an authenticated merchant on `shop-a.myshopify.com` with a valid session cookie/session token, issue a request to that controller with `?shop=shop-b.myshopify.com` appended.
3. Observe `current_shopify_domain` returns `shop-b.myshopify.com` (the attacker-supplied value) rather than `shop-a.myshopify.com` (the actual authenticated shop), despite `current_shopify_session` still referring to shop A's valid session — demonstrating the same "wrong context/target used" flaw as the unfixed `_onWithdraw` case in the source report.
