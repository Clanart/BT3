### Title
Path Traversal via Unvalidated `filepath` Parameter in Deep-Link `open-repository-from-url` Action - ([File: app/src/lib/parse-app-url.ts])

### Summary
`parseAppURL()` validates the `branch` and `pr` query parameters of the `x-github-client://openRepo/...` deep link with strict regex/character checks, but it extracts the `filepath` parameter with **no validation whatsoever** before returning it in the `IOpenRepositoryFromURLAction` payload, which is later dispatched to open a file in the context of the cloned repository.

### Finding Description
`parseAppURL()` parses the OS-level protocol handler URL (`x-github-client://openRepo/...` or `github-mac://openRepo/...`) that any website or process can trigger via a clicked link, without any interaction beyond a click. [1](#0-0) 

Inside the `openrepo` branch, `pr` is checked against `/^\d+$/`, `branch` is checked with `testForInvalidChars` (which rejects characters invalid in git ref names, implicitly blocking `..`/traversal-style refs), but `filepath` — extracted at line 101 via `getQueryStringValue(query, 'filepath')` — is passed straight through to the returned action object with zero sanitation: [2](#0-1) 

This is the exact analog of the reported bug class: a value that flows into a security-sensitive state transition (here, "which file gets opened after clone") is accepted from an untrusted, attacker-controlled input (the deep-link query string) without an ownership/bounds check — mirroring how `enableSessionKey()` accepted an attacker-supplied session key and overwrote `sessionKeyToWallet` without checking whether it was already owned.

The `filepath` value is subsequently consumed by `Dispatcher.dispatchURLAction()` in the `'open-repository-from-url'` case, which calls `this.openRepositoryFromUrl(action)`: [3](#0-2) 

I was unable to retrieve the full body of `openRepositoryFromUrl()` before running out of tool calls, so I cannot confirm with certainty the exact file-system API used to open the path (e.g. `shell.openPath`, `Path.join(repoPath, filepath)`, etc.), and therefore cannot definitively confirm whether the traversal reaches an out-of-repo file read/open. This is a gap in verification, not a claim about the sink's behavior.

### Impact Explanation
If `openRepositoryFromUrl()` joins `repository.path` with the unsanitized `filepath` (which is the typical pattern for "open file after clone" features, and is the documented purpose of this parameter, per the field comment "the file to open after cloning the repository"), a value like `../../../../etc/passwd` or a Windows UNC/absolute path would let an attacker-controlled webpage force GitHub Desktop to open an arbitrary file outside the cloned repository, directly matching the accepted impact category "attacker controls ... a link or deep link the user clicks, and the result is ... file read outside the repo." At minimum, no guard exists at the parsing layer that is present for the sibling `branch` field, which is the concrete missing-validation gap.

### Likelihood Explanation
The `openRepo` action is reachable purely by a user clicking a link (no local access, no admin rights, no prior malware, no leaked credentials required), satisfying the "unprivileged" and "link the user clicks" criteria. The asymmetry between the strict `branch` validation (`testForInvalidChars`) and the complete absence of validation for `filepath` in the same function is a clear, code-level inconsistency indicating the guard was forgotten for this field, just as `enableSessionKey()` forgot the ownership check while presumably having other checks elsewhere in the resource-lock validation flow.

### Recommendation
Apply the same input-sanitization discipline used for `branch` to `filepath` in `parseAppURL()`:
```ts
if (filepath != null && (testForInvalidChars(filepath) || Path.isAbsolute(filepath) || filepath.includes('..'))) {
  return unknown
}
```
Additionally, wherever `filepath` is ultimately consumed (in `openRepositoryFromUrl`), resolve it against the repository root and verify with `Path.resolve`/`Path.relative` that the resulting path stays within the repository directory before opening it — do not trust that validation happened only in the parser.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo/https://github.com/some/repo?branch=main&filepath=../../../../.ssh/id_rsa`
2. Victim (with GitHub Desktop installed and the protocol handler registered) clicks the link.
3. `parseAppURL()` accepts the URL, returning `{ name: 'open-repository-from-url', url: 'https://github.com/some/repo', branch: 'main', pr: null, filepath: '../../../../.ssh/id_rsa' }` — no rejection occurs because `filepath` is never checked. [4](#0-3) 
4. `Dispatcher.dispatchURLAction()` routes this to `openRepositoryFromUrl(action)`. [3](#0-2) 
5. (Unverified due to tool-call exhaustion) If `openRepositoryFromUrl` joins the repo path with `action.filepath` without normalizing/bounding it, the application opens the attacker-chosen out-of-repo file — confirm this sink in a follow-up review of `openRepositoryFromUrl`'s implementation in `app/src/ui/dispatcher/dispatcher.ts`.

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }
