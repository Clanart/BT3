## Finding

### Title
Cross-function signature replay between `withdraw_fees` and `accumulate_fees` beneficiary redirect drains a relayer's full fee balance - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-relayer` uses one shared `Nonce<T>` counter and two structurally identical signed-message hashes for two semantically different, differently-scoped actions: redirecting a single `accumulate_fees` delivery's fee to a beneficiary, and withdrawing a relayer's *entire* accumulated `Fees` balance for a chain. Because both signatures hash `(nonce, state_machine, beneficiary)` with no domain separator, a signature the relayer intended only for a small, single-delivery fee redirect is bit-for-bit valid to authorize a full-balance `withdraw_fees` call, and anyone who observes the signature can replay it into the higher-impact call before the legitimate one lands.

### Finding Description
`withdraw_fees` signs and verifies: [1](#0-0) 

`accumulate_fees`'s beneficiary redirect signs and verifies: [2](#0-1) 

When `beneficiary` is `Some`, `message(nonce, dest_chain, Some(beneficiary))` in `withdrawal.rs` and `beneficiary_message(nonce, state_machine, beneficiary)` in `accumulate.rs` compute the exact same `keccak256((nonce, state_machine, beneficiary).encode())`. Both flows also read/increment the *same* `Nonce<T>` storage keyed by `(address, state_machine)`:

- `accumulate.rs`: `let nonce = Nonce::<T>::get(&delivery_address, state_machine);` … `Nonce::<T>::try_mutate(&delivery_address, state_machine, |value| { *value += 1; ... })` [3](#0-2) 
- `withdrawal.rs`: `let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);` … `Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| { *value += 1; ... })` [4](#0-3) 

Consequently a signature produced by a relayer `R` to authorize *one* `accumulate_fees` call's beneficiary redirect (over a specific, small `total_fee` from one delivery batch) is also a fully valid signature for `withdraw_fees`, which pays out `Fees::<T>::get(dest_chain, address)` — `R`'s entire outstanding balance on that destination — to the same beneficiary, and zeroes it: [5](#0-4) 

There is no field in either signed payload identifying which call (accumulate-redirect vs. full withdrawal) or which specific delivery/commitment set the signature authorizes, so the verification code in both call sites cannot distinguish the intended scope: [6](#0-5) 

### Impact Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned, permissionless extrinsics (`ensure_none(origin)`), so any unprivileged account can submit either call once it has the signature bytes: [7](#0-6) 

An attacker who observes a relayer's beneficiary-redirect signature (visible in the mempool or a mined block as part of the public `WithdrawalProof`) can submit `withdraw_fees` with the same signature/nonce/beneficiary before the intended `accumulate_fees` call executes. Because `withdraw_fees` withdraws the *entire* `Fees[dest_chain][R]` balance rather than the single delivery amount the relayer authorized, this results in the relayer's full accumulated fee balance being sent to a beneficiary the relayer only meant to receive a much smaller, specific amount — an unauthorized transfer of funds beyond the signer's intended authorization scope.

### Likelihood Explanation
Exploitation requires no compromised relayer, prover, admin, or leaked key — only observing a legitimately-broadcast signature (which is necessarily public, since it must be embedded in an on-chain `WithdrawalProof`/`WithdrawalInputData`) and submitting a competing transaction before the original lands. This is a straightforward, always-available cross-function replay stemming from a missing domain separator, not a front-running-only griefing scenario — the amount mismatch (full balance vs. intended delivery amount) is the core exploitable defect.

### Recommendation
Add a domain separator (e.g., a distinct action tag or the specific commitment set / fee amount) into both signed payloads so a signature for `accumulate_fees`'s beneficiary redirect cannot be replayed into `withdraw_fees`, and vice versa. Consider using separate nonce spaces per action, or binding the signature to the exact fee amount/commitment batch being authorized rather than only `(nonce, state_machine, beneficiary)`.

### Proof of Concept
1. Relayer `R` delivers a batch of requests to destination `X`, accruing `Fees[X][R] = 10,000` over time from many unrelated deliveries.
2. For a new delivery batch worth `100`, `R` signs `beneficiary_message(N, X, B)` intending only to redirect that `100` to `B` via `accumulate_fees`'s `beneficiary_details`.
3. Before `R`'s `accumulate_fees` transaction is included, an unprivileged observer copies the signature from the mempool/block and submits `withdraw_fees(WithdrawalInputData { signature, dest_chain: X, beneficiary: Some(B) })`.
4. `message(N, X, Some(B))` equals `beneficiary_message(N, X, B)`, and `Nonce[R][X]` is still `N`, so signature verification succeeds and recovers `R`.
5. `withdraw_fees` sends the full `Fees[X][R] = 10,000` to `B` (not the intended `100`), zeroes the balance, and bumps `Nonce[R][X]` to `N+1`, causing `R`'s original `accumulate_fees` (still keyed to nonce `N`) to fail — but the 10,000 is already unrecoverably sent to `B`.
