## Title
Consensus-incentive reward attribution binds to `messages[0]`'s signer but pays for every `StateMachineUpdated` event in the batch, letting an unrelated submitter steal other relayers' rewards - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::FeeHandler::on_executed` identifies "the relayer" to reward by decoding a signature carried only in `messages[0]`, then transfers a treasury-funded reward for *every* `StateMachineUpdated` event found anywhere in the whole processed batch to that single extracted account. Nothing ties later state-machine updates in the same batch to the signer of the message that actually produced them, so a batch that bundles a cheap self-signed consensus message at index 0 alongside genuinely valuable consensus updates lets the submitter collect rewards that belong to whoever supplied those other updates — the same class of bug as pSTAKE's `calculateRewards`, where a caller who should not be the reward recipient ends up receiving funds meant for someone else because the function lacks a binding check between "who is authorized" and "what is being rewarded."

### Finding Description
`on_executed` is the `FeeHandler` hook invoked after `pallet-ismp` executes a batch of messages: [1](#0-0) 

It only inspects `messages.get(0)`, decodes the `Signature` embedded in that single message's `signer` field, and verifies it against `keccak256(consensus_msg.consensus_proof)` to recover `relayer_account`. There is no requirement that this signer correspond to any of the other messages in the batch.

It then walks **all** `IsmpEvent::StateMachineUpdated` events across the entire `events` vector passed in for the whole batch, and pays the reward for each collapsed per-state-machine update to that single `relayer_account`: [2](#0-1) 

`process_message`/`calculate_reward` then transfer treasury funds and mint reputation to `relayer_account` for the full block-span reward of each state machine that advanced in the batch: [3](#0-2) 

Consensus proofs are explicitly permissionless in this protocol — "these proofs can be generated by anyone, as they are freely provided by its connected chains" — so any account can wrap an already-public, otherwise-attributable consensus proof (or a trivial no-op one) with its own signature and place it first in a submitted batch: [4](#0-3) 

Since `pallet_ismp`'s `handle`-style dispatch accepts a `Vec<Message>` in one unsigned call, and reward attribution only reads index `0`, whoever controls the batch ordering controls who gets paid for *all* the `StateMachineUpdated` events the batch produces, regardless of which message in the batch actually advanced which state machine.

### Impact Explanation
This directly causes stealing/wrong-beneficiary payout of protocol treasury funds: an unrelated party can insert its own message at index 0 of a submitted batch and collect the reward for state-machine advances it did not itself relay, at the expense of the relayer who actually supplied the corresponding proof. This matches the required impact classes ("stealing or loss of funds", "logic attacks", "unauthorized ... execution") because the treasury→relayer transfer and reputation mint execute for a beneficiary the code never actually verified was responsible for the rewarded state advance.

### Likelihood Explanation
The extrinsic path is unsigned (`ensure_none`)/permissionless by design for consensus messages, and consensus proofs are described in the docs as freely obtainable by anyone. Constructing a batch is a normal, unprivileged action available to any address that can submit a `pallet-ismp` message batch — no malicious relayer/prover/admin collusion or leaked keys are required, only ordinary batch construction using publicly available proof data.

### Recommendation
Attribute each `StateMachineUpdated` reward to the signer of the specific `Message::Consensus` entry that produced it (matching by message/consensus-client or by re-deriving the signer per message that emits the update), rather than defaulting to `messages[0]`. If multiple consensus messages appear in one batch, either reward each one's own signer per state machine it actually advanced, or reject/ignore updates whose originating message cannot be unambiguously matched to `relayer_account`.

### Proof of Concept
1. Observe a valid, publicly-relayable consensus proof for chain X (per documentation, any relayer can construct/obtain one) that legitimate relayer B is about to (or has just) submitted for delivery.
2. Attacker A crafts their own `Message::Consensus` wrapping the same or a trivial/no-op consensus proof, signing it with A's key (`consensus_msg.signer` verifiable via `Signature::decode`/`verify_and_get_sr25519_pubkey`) — this only needs to pass `on_executed`'s signature check at [5](#0-4) , not full proof validity elsewhere.
3. Attacker A submits a single unsigned extrinsic/batch to `pallet-ismp` with `messages = [A's message, ...other messages that will emit StateMachineUpdated for chain X and/or additional chains during processing]`.
4. `on_executed` reads `messages[0]` → recovers `relayer_account = A`, then iterates `events` for the whole batch ( [6](#0-5) ) and pays A the full computed reward for every state machine that advanced in that batch, even though A did not supply the proofs for those other advances.
5. Legitimate relayer B, who actually produced/relayed the other consensus updates, receives nothing for that batch.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {

# Pallet Relayer

The Hyperbridge protocol is uniquely enabled by cryptographic proofs which certify the integrity of cross-chain transactions. These proofs can be generated by anyone, as they are freely provided by its connected chains. However, the Hyperbridge protocol provides a mechanism to incentivize the generation and submission of these proofs. This is where relayers come in.

Relayers are responsible for collecting and transmitting proofs of cross-chain messages across connected chains. In return, relayers are rewarded with the associated transaction fees that were provided by users and applications. The `pallet-ismp-relayer` module is responsible for tracking the accrued fees and distributing them to the relayers. The module permits relays to withdraw their fees at any time, the module works in conjunction with the [`pallet-host-executive`](/developers/explore/nexus/host-executive) to perform fee withdrawals on the destination chain.
