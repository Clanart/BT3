## Title
Governance-triggered challenge period decreases retroactively shrink the fraud-proof window for already-committed (unverified) state commitments - (File: `modules/ismp/core/src/handlers.rs`, `modules/pallets/ismp/src/host.rs`, `modules/pallets/ismp/src/utils.rs`)

### Summary
The Hyperbridge equivalent of `unstakingDelay` is the per-state-machine `challenge_period`. It gates when a committed (but still unverified) `StateCommitment` can be used to process requests/responses/timeouts. Exactly like the StRSR bug, the delay is keyed only by identity (`StateMachineId`), not by the specific state commitment/height it applies to. When governance lowers the `challenge_period`, the new (shorter) value is retroactively applied to all state commitments already stored, including ones that landed under the old, larger challenge period and are still within their original fraud-proof window.

### Finding Description
`verify_delay_passed` computes elapsed time using the height's stored `update_time` and the *current* `challenge_period` value read live from storage: [1](#0-0) 

The `challenge_period` itself is stored per `StateMachineId` only — not per commitment/height: [2](#0-1) 

Governance can update it at any time via `UpdateConsensusState.challenge_periods`: [3](#0-2) 

The EVM side has the identical pattern: `HandlerV2.handlePostRequests`/`handleGetResponses`/timeout handlers all compute `delay = timestamp - host.stateMachineCommitmentUpdateTime(height)` and compare it against the *live* `host.challengePeriod()`, which is itself mutable via `setHostParams`: [4](#0-3) [5](#0-4) 

Because the delay is a *live*, single global value per state machine rather than a value snapshotted at the time each state commitment was stored, a legitimate governance action to shrink the challenge period (e.g. from 6 hours to 10 minutes for performance reasons) instantly reduces the safety margin for every state commitment already sitting in the pending/challenge window — including ones a fisherman is still in the middle of auditing under the original, longer-promised window. Relayers/handlers can then immediately submit `handlePostRequests`/`handleGetResponses`/timeout messages referencing that pre-existing, not-yet-fully-vetted `StateCommitment` as soon as the new shorter delay is satisfied, well before the originally advertised challenge period elapses.

This directly matches the `StateMachineUpdated` event's documented security assumption: "Relayers will wait for the configured `challenge_period`... If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical," as stated in the docs: [6](#0-5) 

That safety property is broken the instant the delay is shortened for a commitment that already exists, because fishermen sized their auditing/veto timelines against the challenge period that was active at commit time, not a value that can be shrunk after the fact.

### Impact Explanation
If a malicious or faulty state commitment landed shortly before a challenge-period decrease, requests/responses can be dispatched and executed (funds moved, cross-chain calls executed) against that state before the fisherman veto window that was originally promised has elapsed — i.e. false/unverified remote state gets trusted and acted upon, exactly the impact class the bounty prioritizes ("false proof/state acceptance", "unauthorized execution", "transaction manipulation"). This is a direct analog of the StRSR M-19 pattern: a legitimate parameter change by the responsible party retroactively invalidates the time-based guarantee that other participants (unstakers / fishermen) were relying on for already-pending items.

### Likelihood Explanation
This does not require a malicious actor, relayer, or prover — it only requires the normal governance/parameter-update flow to lower `challenge_period` (or `challengePeriod` on EVM) while any `StateCommitment` is still within its original window, which is a routine operational action (tuning parameters, cost optimization, etc.), making it a realistic and repeatable scenario rather than a contrived edge case.

### Recommendation
Snapshot the challenge period alongside each stored `StateCommitment`/`state_machine_update_time` at the moment it's recorded, and use that snapshotted value (not the live/current `challenge_period`) in `verify_delay_passed` and the EVM handler checks. Alternatively, enforce that a newly-lowered `challenge_period` only applies to commitments recorded after the update, while pre-existing commitments continue to honor the challenge period that was active when they were stored.

### Proof of Concept
1. Governance sets `challenge_period` for state machine `X` to 6 hours.
2. A (possibly fraudulent) `StateCommitment` for `X` at height `H` is stored via `update_client`, recording `update_time = t0` (`modules/ismp/core/src/handlers/consensus.rs` lines 68-70).
3. One hour later (`t0 + 1h`), governance lowers `challenge_period` for `X` to 10 minutes via `UpdateConsensusState`.
4. Any relayer can now call `handlePostRequests`/`handleGetResponses` (EVM) or dispatch the equivalent Substrate message referencing height `H`: `verify_delay_passed`/the EVM delay check computes `elapsed = 1h > 10m`, passes, and the request/response is executed — despite the commitment having only been "safe" per the original 6-hour promise for 1 of the 6 hours, well before any fisherman would have finished auditing it.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
