### Title
Attacker-forced point-at-infinity aggregate nonce panics the signer via unhandled `None` in `x()` — ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The reported bug class is a helper (`av_color_primaries_name`) that can return `NULL` for an input-derived value, which callers do not anticipate, causing a NULL dereference. In Serai's in-scope code, `x()` in `networks/bitcoin/src/crypto.rs` is the direct analog: `ProjectivePoint::to_encoded_point(true).x()` returns `None` when the point is the identity, and `x()` unconditionally `.expect()`s on it. `x()` is reached from `Hram::hram` on the FROST aggregate nonce `R` and group key `A` during `sign_share`/`verify`. The aggregate nonce is computed from per-participant commitments that arrive as untrusted bytes through `read_preprocess`, so a participant can contribute a cancelling commitment forcing `R` to the point at infinity and deterministically panic the honest signer's process.

### Finding Description
`x()` extracts the x-coordinate of a compressed point and panics if it is `None`:

```rust
// networks/bitcoin/src/crypto.rs:13-16
fn x(key: &ProjectivePoint) -> [u8; 32] {
  let encoded = key.to_encoded_point(true);
  (*encoded.x().expect("point at infinity")).into()
}
```

`Hram::hram` calls `x(R)` and `x(A)`:

```rust
// networks/bitcoin/src/crypto.rs:59-72
fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
  ...
  data.input(&x(R));
  data.input(&x(A));
```

The `Schnorr` algorithm's docstring acknowledges this panic ("If either `R` or `A` is the point at infinity, this will panic") but claims it has "a negligible probability ... even with malicious participants present" (`crypto.rs:54, 78-80`). That probability claim is wrong for `R`: `R` is the sum of binding-factor-weighted nonce commitments from all signers. A participant who sees every other participant's preprocess (delivered via `TransactionSignMachine::sign` → `commitments` HashMap built from `read_preprocess` bytes, `send.rs:351-371`) can choose their own commitments so the weighted sum cancels to the identity element. This is deterministic, not negligible. `verify` then calls `hram` with `R = identity`, `x()` returns `None`, and `.expect("point at infinity")` panics inside the signing/verification path of `AlgorithmMachine` (`send.rs:383-391`).

### Impact Explanation
An unprivileged participant in a Bitcoin FROST signing session can deterministically panic every honest signer that reaches `verify`/`sign_share` for a transaction, aborting the signing attempt. Across retries the same party can repeat the attack on each new session since they control their commitments each round, giving a sustained denial of signing service for the affected multisig/transaction. This is the exact NULL-return-not-anticipated shape of CVE-2017-14225: `to_encoded_point().x()` legitimately returns `None` for a value an attacker can induce, and the caller treats it as impossible.

### Likelihood Explanation
- Reachable purely from public inputs: the attacker only submits preprocess commitments (untrusted bytes to `read_preprocess`), a documented in-scope input channel.
- Deterministic: the commitment cancellation does not rely on probability, contrary to the docstring's assumption.
- No privilege required beyond being a signing participant contributing a preprocess; the attack also works if preprocess bytes are relayed by an untrusted party.
- Impact is limited to signing liveness (panic), not key/share recovery, so it does not rise above Medium.

### Recommendation
Make `x()`/`x_only`/`Hram::hram` handle the identity element without panicking, or — preferably — reject identity aggregate nonces upstream: in `verify`/`sign_share` (or when summing nonce commitments), check `R.is_identity()` / `group_key.is_identity()` and return `FrostError`/`None` instead of calling `hram`. At minimum, replace the `.expect("point at infinity")` with an error propagated to the caller, and fix the misleading "negligible probability" comment, since malicious commitment selection makes the condition attacker-controlled.

### Proof of Concept
1. Honest signers each publish preprocesses (nonce commitments `D_i, E_i`) for a `TransactionMachine` signing session (`send.rs:302-317`).
2. The attacker computes the binding factors `rho_j` (deterministic functions of the message and commitment list) and selects their own commitments such that the aggregate `R = sum_j rho_j * (D_j + E_j)` equals `ProjectivePoint::IDENTITY` — e.g., set their nonce commitment to the negation of all other weighted terms. Since commitments are just group elements read from bytes, any value including the needed negation is encodable via `read_preprocess`.
3. Each honest signer reaches `TransactionSignMachine::sign` → `sig.sign(commitments[i], sighash)` (`send.rs:383-390`) → `Schnorr::verify`/`sign_share` → `Hram::hram(R, A, m)` (`crypto.rs:59`) → `x(R)` on the identity → `encoded.x()` returns `None` → `.expect("point at infinity")` panics (`crypto.rs:15`), killing the signing attempt.

Note: I could not fully trace `frost::algorithm::IetfSchnorr::verify`/`sign_share` internals in this pass to confirm the exact call ordering into `hram` versus an existing identity check in `crypto/frost`; if `frost` already rejects identity `R` before invoking `Hram`, the panic is unreachable and this reduces to a latent footgun. The identity-commitment cancellation itself is standard FROST behavior and the panic site is confirmed in the in-scope file.
