## Analog Found: Attacker-crafted commit identity can spoof GitHub's "web-flow" bot indicator, hiding the true committer from Desktop's avatar/authorship display

### Summary
The `ERC721OnChain` report is fundamentally about an untrusted party (the token owner) being able to overwrite metadata (`tokenURI`) that the rest of the system implicitly trusts as authoritative, letting them spoof another entity's identity/data. The closest reachable analog in GitHub Desktop is that **commit author/committer identity fields — fully attacker-controlled in any cloned or fetched repository — are used to decide whether a commit was made via GitHub's official "web-flow" editor**, and that decision determines which avatar/identity is shown to the user for a commit.

### Finding Description
When Desktop renders the list of avatars/identities associated with a commit, it calls `getAvatarUsersForCommit`, which special-cases commits whose committer identity matches GitHub's built-in web editor bot (`isWebFlowCommitter`). If a commit is judged to be a "web-flow" commit, Desktop suppresses showing the actual committer as a separate identity in the UI, on the theory that GitHub's web UI committer is not an interesting distinct identity to display: [1](#0-0) 

The identity used for this decision — `commit.committer` (name/email) — comes straight from the commit object parsed out of `git log`, with no cryptographic verification (`--no-show-signature` is explicitly passed): [2](#0-1) [3](#0-2) 

Because any commit's author/committer name and email are plain text fields that can be set to *arbitrary values* by whoever creates the commit (`git commit --author=... `, `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`), an attacker who controls a cloned/fetched repository, fork, or pull-request branch can fabricate a commit whose committer identity is engineered to satisfy whatever match `isWebFlowCommitter` performs (this repo's index does not surface the full body of `app/src/lib/web-flow-committer.ts`, so the exact matching rule could not be fully verified here — this should be confirmed in a full checkout). If the match is based on committer name/email pattern alone (as its use here, without any GitHub API cross-check visible in this code path, suggests), an attacker gets to unilaterally decide that Desktop hides their own committer identity and instead treats the commit's provenance as "made by GitHub's web editor," a data field that a legitimate collaborator would expect to be trustworthy since it normally implies commits made through the official GitHub web UI (e.g. "Merge/edit via web").

### Impact Explanation
This is a spoofing/trust-indicator bug in the same class as the seed report: an unprivileged party (anyone who can author a commit, including a PR author from a fork) controls a value (`committer` identity in a plain-text commit) that the client blindly trusts to alter what identity information is surfaced to reviewers. A user reviewing a fork's history or a PR in Desktop could be misled into believing a suspicious commit came from GitHub's automated web-flow committer rather than the actual (possibly malicious) author, weakening the human review step that a maintainer relies on before merging or pushing — this can facilitate social-engineering a maintainer into trusting/merging a commit they would otherwise scrutinize.

### Likelihood Explanation
Any attacker capable of pushing to a fork or crafting a repository/branch that a Desktop user opens or fetches (the same threat model as the original C4 SKALE finding — an "owner" of an on-chain/off-chain object controlling metadata) can set arbitrary committer name/email on their commits with zero special privileges; no signature verification gates this UI decision (`--no-show-signature`) as shown above.

### Recommendation
- Verify `isWebFlowCommitter` (`app/src/lib/web-flow-committer.ts`) does not rely solely on matching committer name/email text; if it does, require corroborating GitHub API/commit-verification data (e.g. `verified` status from the API, or GPG/SSH signature verification) before suppressing the committer identity in `getAvatarUsersForCommit`.
- At minimum, never fully hide a mismatched author/committer identity based purely on unauthenticated commit metadata; if signature verification is unavailable, always surface the raw committer identity alongside any "possibly GitHub web editor" hint rather than replacing it.

### Proof of Concept
1. Attacker creates a fork and crafts a commit with `git commit --author="Attacker <attacker@evil.com>"` and sets `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` to whatever pattern `isWebFlowCommitter` looks for (needs confirmation from `app/src/lib/web-flow-committer.ts`, e.g. a `*@users.noreply.github.com` web-flow-style address).
2. Attacker opens a PR from this fork; a maintainer using Desktop checks out the PR branch (`_checkoutPullRequest` → `_findPullRequestBranch`, which adds the fork's remote and fetches it) [4](#0-3) .
3. When the maintainer views the commit history/changes in Desktop, `getAvatarUsersForCommit` evaluates `isWebFlowCommitter(commit, gitHubRepository)` on the untrusted commit and, if it matches, hides the actual committer identity from the avatar/author display [1](#0-0) .
4. The maintainer sees a misleading provenance signal for a commit that was never actually made through GitHub's web editor, reducing scrutiny before merge/push.

**Note on completeness:** I could not directly inspect the full contents of `app/src/lib/web-flow-committer.ts` (only its import/usage surfaced in the index), so the exact matching heuristic for "web-flow committer" is unconfirmed. If it already cross-checks against a verified GitHub API field rather than raw commit text, this specific analog would not hold and a Devin session with full repository access would be needed to confirm the implementation before treating this as a confirmed vulnerability.
