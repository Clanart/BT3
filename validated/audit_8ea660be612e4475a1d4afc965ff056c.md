## Title
`checkoutIndex()` accepts Git exit code 1 as success, silently leaving un-discarded/attacker-controlled content in the working directory that gets committed - (`app/src/lib/git/checkout-index.ts`)

## Summary
The `checkout-index` call used by Desktop's "Discard Changes" flow treats git exit code `1` as a *successful* result (`successExitCodes: new Set([0, 1])`) without inspecting which of the requested paths were actually restored from the index. If `git checkout-index` refuses to write one of the requested paths (e.g., because Git itself detects the path would need to replace a symlink/collide with a protected component — the same class of safety check Git added after CVE-2019-1349/1387-style symlink and case-collision attacks), Desktop's `discardChanges()` still reports the operation as completed. Combined with the fact that the original file content is moved to the trash *before* the checkout-index call runs, the working directory can be left containing attacker-supplied content for that path while the UI and app state believe the discard succeeded — so that content is what the user subsequently stages and commits/pushes.

## Finding Description
`checkoutIndex()` in `app/src/lib/git/checkout-index.ts` accepts a list of paths and forces the working directory to match the index for those paths: [1](#0-0) 

Note the `successExitCodes: new Set([0, 1])` — any exit code of `1` from `git checkout-index -f -u -q --stdin -z` is treated identically to a full success, and the caller never checks `stdout`/`stderr` per-path to determine which of the requested paths were actually rewritten.

This is invoked from `GitStore.discardChanges()`: [2](#0-1) 

The broader flow, per Desktop's own documentation, is: (1) move the modified file to the OS trash, (2) `git reset` the index, (3) `git checkout-index` to restore the pre-modification content from the index into the working directory: [3](#0-2) 

The `git()` core wrapper (`app/src/lib/git/core.ts`) only distinguishes acceptable vs. unacceptable exit codes at the whole-command level, via `opts.successExitCodes` supplied by the caller — it has no concept of "this specific path in a multi-path invocation failed": [4](#0-3) 

So if a repository (cloned or fetched from an attacker-controlled remote) is crafted such that `checkout-index` cannot safely materialize one of the paths being discarded — for example because doing so would require replacing a path component that Git's own protections refuse to overwrite (symlink-in-path, case-folding collision on case-insensitive filesystems, etc.) — the command can exit with code `1` for that specific path while still succeeding for all others. Desktop's wrapper swallows this as a full success. The file that was moved to the trash in step (1) is never actually replaced with the trusted HEAD/index content, yet `GitStore.performFailableOperation` records no error, the UI clears the file from the changed-files list (since the git status logic depends on what actually exists on disk vs. index, and the malicious/left-behind entry may or may not still show as changed depending on exactly how the checkout failed), and the user is never told the discard was incomplete.

## Impact Explanation
This breaks the invariant that "Discard Changes" is either a safe no-op or a verified full reversion to the last committed state for every selected file. A repository under attacker control (the primitive explicitly allowed by scope: a cloned/fetched repository) can be engineered so that discarding a specific file silently fails while being reported as successful, leaving attacker-influenced content resident in the working directory. Because Desktop treats the operation as fully successful, that content is exactly what will end up staged and committed/pushed on the next commit — i.e., silent corruption of what the user commits, which is one of the explicitly valid impact categories for this exercise.

## Likelihood Explanation
No local/physical access, admin rights, or pre-existing malware is required — only that the victim clones/fetches a repository the attacker controls and later uses Desktop's normal "Discard Changes" action on a file within it, which is an ordinary Desktop workflow. The bug is a direct, unconditional code-level acceptance of exit code `1` as success with no per-path verification, so no probabilistic race condition or unusual configuration is needed for the *acceptance* to occur — only that Git itself refuse to write a specific path (which is a documented Git safety behavior, not something Desktop controls or double-checks).

## Recommendation
`checkoutIndex()` should not blanket-accept exit code `1` as success. At minimum:
- Capture and parse `stdout`/`stderr` from `checkout-index` to determine exactly which paths were not restored, and surface that as an error/warning rather than silently succeeding.
- Prefer running `checkout-index` without `--quiet` (or additionally without folding exit code 1 into the success set) so any refusal for any requested path causes `GitStore.discardChanges()`'s `performFailableOperation` to actually catch and report the failure.
- After the checkout step, re-verify (via `git status`/`git diff --stat` on the specific paths) that each discarded file's on-disk content now matches the index/HEAD blob before treating the discard as complete, especially for files that were already moved to the trash.

## Proof of Concept
1. Attacker publishes/serves a Git repository (or a branch/PR the victim fetches) containing a committed file at a path `P` such that, on the victim's platform, restoring `P` via `git checkout-index -f -u -q` requires overwriting a path component that Git's own safety checks refuse to replace (e.g., a directory-vs-symlink collision engineered through case-folding on a case-insensitive filesystem, or a path whose parent was previously a symlink in the working tree due to another tracked entry).
2. Victim clones/fetches the repository in GitHub Desktop and modifies `P` locally (or the malicious state is already present as an uncommitted/untracked variant of `P`).
3. Victim selects "Discard Changes" on `P`. `GitStore.discardChanges()` moves the current on-disk file to the trash, resets the index, then calls `checkoutIndex(repository, [P])`.
4. `git checkout-index` exits with code `1` for `P` (unable to safely restore it) but Desktop's `successExitCodes: new Set([0, 1])` treats this as success; `performFailableOperation` reports no error.
5. The working directory now contains no valid restored copy of `P` from the index (only what remained from the failed operation, potentially attacker-influenced), yet the UI reports the discard as successful.
6. The user proceeds to stage/commit/push, incorporating the corrupted/attacker-influenced state of `P` without ever being warned.

```typescript
export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
}
```
