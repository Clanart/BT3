## Analysis

I traced the "attacker-controlled input reaching a security-relevant path/URL check" pattern in Desktop, focusing on the `x-github-client://openrepo/...` deep-link handler, since it is the closest analog to an externally-triggerable, unprivileged control-flow path (comparable to the report's "attacker-influenced governance parameter bypasses an invariant check").

The relevant chain is:

- `parseAppURL` in `app/src/lib/parse-app-url.ts:98-125` parses `openrepo` deep links and passes through an attacker-supplied `filepath` query parameter with only a "no invalid chars" check on `branch`, not on `filepath`.
- `Dispatcher.openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts:1940-1972` rejects absolute `filepath` values, then calls `resolveWithin(repository.path, filepath)` and, if non-null, calls `shell.showItemInFolder(resolved)`.
- The actual containment check lives in `_resolveWithin` in `app/src/lib/path.ts:36-71`. After resolving the path it does:
```
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

## Finding Description

The invariant `_resolveWithin` is supposed to enforce is "the resolved path resides *underneath* the root path." What it actually implements is "the resolved path's string representation has the root path's string as a prefix." These are different invariants: a plain `String.prototype.startsWith` check does not verify a path-separator boundary after the prefix, so a **sibling directory whose name extends the root directory's name as a string** (e.g. root `/Users/x/repo` and sibling `/Users/x/repo-secrets`) will incorrectly pass the check, because `"/Users/x/repo-secrets".startsWith("/Users/x/repo")` is `true` even though `repo-secrets` is not inside `repo`.

An attacker who gets a victim to click a crafted `x-github-client://openrepo/<url>?filepath=../repo-secrets/token.txt` deep link (or `github-mac://openRepo/...`) supplies a relative `filepath`. The `isAbsolute(filepath)` guard in `dispatcher.ts` only blocks absolute paths, not `..`-relative escapes to sibling directories. If the victim's checked-out repository directory name is a prefix of a sibling directory that exists on disk (a realistic scenario when repos are cloned into a common parent, e.g. `~/GitHub/project` and `~/GitHub/project-secrets`, or `project` and `project.bak`), the traversal check silently passes and `shell.showItemInFolder(resolved)` reveals/opens a file outside the intended repository root.

## Impact Explanation

This breaks the "commands triggered by attacker-controlled deep links can only touch files inside the target repository" guarantee that `resolveWithin` is meant to provide. It allows an attacker-crafted link to cause the Desktop app to open/reveal an arbitrary file on disk that merely shares a directory-name prefix with a repository the user has cloned, i.e. a file read/disclosure outside the repo boundary triggered purely by clicking a link — matching the "link/deep link" attacker-control category in the valid-impact list.

## Likelihood Explanation

Exploitation depends on the victim having a sibling directory whose name is a superstring of an existing repository's directory name (a common naming pattern: `repo`, `repo-old`, `repo.bak`, `repo2`), and on the victim clicking a malicious `x-github-client://openrepo/...?filepath=...` link. This is a real but conditional path — it requires no local access, admin rights, or prior compromise, only a link click, which satisfies the required attacker model, though the exact outcome depends on the victim's directory layout.

## Recommendation

Fix `_resolveWithin` in `app/src/lib/path.ts` to check for a real path-boundary match instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
using the appropriate `sep` for the `options` variant (`Path.win32.sep` / `Path.posix.sep`).

## Proof of Concept

1. Victim has cloned `https://github.com/foo/repo` to `~/GitHub/repo` and separately has `~/GitHub/repo-secrets/token.txt` on disk.
2. Attacker sends victim a link: `x-github-client://openrepo/https://github.com/foo/repo?filepath=..%2Frepo-secrets%2Ftoken.txt`.
3. `parseAppURL` (`app/src/lib/parse-app-url.ts:98-124`) accepts it since only `branch`/`pr` are validated, not `filepath`.
4. `Dispatcher.openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1971`) sees `filepath` is not absolute, calls `resolveWithin(repository.path, '../repo-secrets/token.txt')`.
5. Inside `_resolveWithin` (`app/src/lib/path.ts:66-71`), `resolved` normalizes to `~/GitHub/repo-secrets/token.txt`, and `realResolved.startsWith(realRoot)` (`realRoot = ~/GitHub/repo`) evaluates `true` due to the shared string prefix.
6. `shell.showItemInFolder(resolved)` reveals the out-of-repo file to the attacker's target link. [1](#0-0) [2](#0-1) [3](#0-2)

    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
