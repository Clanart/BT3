## Title
Attacker-controlled `.gitmodules` combined with app-forced `protocol.file.allow=always` enables local-file disclosure via `git submodule update` - ([File: app/src/lib/git/submodule.ts])

### Summary
The Gelato report's broken invariant is: a value that a security check depends on (gas used to compute the fee) is produced by executing attacker-controlled logic *before* the check is applied, so the attacker can corrupt that value at effectively no cost to themselves. The closest structural analog in GitHub Desktop is `updateSubmodulesAfterOperation`, which — when invoked with `allowFileProtocol = true` — appends `-c protocol.file.allow=always` to `git submodule update --init --recursive` [1](#0-0) . This re-enables the `file://` transport for submodules whose URLs come straight from the attacker-controlled `.gitmodules` file in a cloned/checked-out repository, letting a malicious repo point a submodule at an arbitrary local path and have Desktop silently clone it into the working tree.

### Finding Description
`checkoutBranch` and `checkoutCommit` accept an `allowFileProtocol` flag that is forwarded unchanged to `updateSubmodulesAfterOperation`, which builds the submodule-update command with `-c protocol.file.allow=always` whenever that flag is true [2](#0-1) [3](#0-2) . Modern Git normally blocks `file://` submodule URLs by default (Git ≥2.38, following the `git submodule` local-clone disclosure fixes, e.g. GHSA/CVE-2022-39253-class issues) specifically because a repository's own tracked `.gitmodules` file — fully attacker-controlled content coming from a clone/fetch — can specify a submodule URL like `file:///etc` or `file:///Users/victim/.ssh`. When the file protocol is force-re-enabled, `git submodule update --init --recursive` will happily perform a local "clone" of that path into the submodule directory inside the user's working tree.

The security guard that normally exists in Git itself (the `protocol.file.allow=user` default that refuses file-protocol submodules unless the user opts in per invocation) is exactly the "hard cap" analog to the gas check in the report — and Desktop's own code path unconditionally overrides it with `always` rather than scoping it to a genuinely-trusted, non-repo-controlled path. `.gitmodules` content is fully attacker-controlled (it is part of what gets cloned/checked out), so once `allowFileProtocol` is true for any checkout code path reachable from an untrusted repository, the guard is defeated by the exact same mechanism the report criticizes: trusted-looking plumbing (`claimExecutionFees`/here, `updateSubmodulesAfterOperation`) executes attacker-supplied instructions (fee-token contract code / here, a `file://` submodule URL) before any hard limit is enforced.

### Impact Explanation
If `allowFileProtocol` is reachable on a checkout/branch-switch/stash flow performed against an untrusted or forked repository, a malicious `.gitmodules` entry can cause Desktop to locally "clone" sensitive directories on the victim's machine (SSH keys, other private repos, config files) into a submodule path inside the working tree. Because that content now lives inside the tracked repository, a subsequent `git add`/commit/push by the unsuspecting user would exfiltrate those local files to the attacker's remote — this satisfies the "silent corruption of what the user commits or pushes" and "file read outside the repo" impact categories.

### Likelihood Explanation
Exploitability hinges entirely on whether any UI-reachable call passes `allowFileProtocol = true` for a checkout/branch switch that operates on a URL/commit originating from an attacker-influenced repository (e.g., forks, or "Checkout" while resolving a PR/branch from an untrusted contributor). I was not able to fully confirm, from the index alone, every caller and the exact condition under which `true` is passed — call sites exist in `app/src/lib/stores/app-store.ts`, `app/src/ui/dispatcher/dispatcher.ts`, `app/src/ui/stash-changes/stash-and-switch-branch-dialog.tsx`, `app/src/ui/checkout/confirm-checkout-commit.tsx`, `app/src/ui/history/compare.tsx`, and `app/src/ui/branches/branches-container.tsx`, but the index truncation prevented tracing each call's `allowFileProtocol` argument value back to its trust boundary. This is the key open question that determines whether the flag is scoped only to local same-machine forks (lower severity) or can be reached for arbitrary remote/forked repositories (high severity, matching the report's "little cost, arbitrary execution" pattern).

### Recommendation
- Never force `protocol.file.allow=always` based on a flag threaded through UI code; instead validate/allowlist the specific local path expected (e.g., only the repository's own known local-fork path used in tests) rather than blanket-enabling `file://` for the whole submodule graph.
- If `allowFileProtocol` exists to support legitimate local-fork/test scenarios, gate it behind an explicit, narrowly-scoped mechanism (e.g., pass the exact allowed local root via `protocol.file.allow=<pathspec>`-style safelist or pre-validate each submodule URL against that root) rather than passing `always` to Git.
- Audit every call site of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` for repositories the user already owns/created locally, never for cloned/forked/PR-sourced content.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "leak"]
     path = leak
     url = file:///home/victim/.ssh
   ```
2. Victim clones/forks this repository in GitHub Desktop and performs an action that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol = true` (exact triggering UI flow unconfirmed from available code — see Likelihood).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, causing Git to locally "clone" `/home/victim/.ssh` into `leak/` inside the working tree [1](#0-0) .
4. If the victim later stages and pushes changes (or the app auto-refreshes and surfaces the new files), the private key material becomes part of the tracked repository and can be exfiltrated to the attacker's remote. [3](#0-2) [4](#0-3)

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
