### Title
Payout `OP_RETURN` operator-credit tag is unauthenticated when a withdrawer chooses `SIGHASH_SINGLE|ANYONECANPAY`, letting a third party redirect reimbursement credit from the funding operator to another operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` places the fronting operator's x-only pubkey in a standalone `OP_RETURN` output (output index 2) that is separate from the signed user output (index 0) [1](#0-0) . Whether that `OP_RETURN` is cryptographically bound to the transaction depends entirely on the `sighash_type` embedded in the user's `taproot::Signature`, which `Operator::withdraw` accepts unchecked from the withdrawer [2](#0-1) . Later, `Verifier::update_finalized_payouts` trusts whatever `OP_RETURN` bytes end up in the *mined* payout tx to decide which operator gets credited for the withdrawal, with no other authentication [3](#0-2) .

### Finding Description
Binding that must hold: `payout_payer_operator_xonly_pk[withdrawal i] == operator_who_actually_funded_output_0[withdrawal i]`, exactly once.

- `create_payout_txhandler` builds three outputs: user payout (0), anchor (1), `OP_RETURN` with the operator's x-only pubkey (2) [4](#0-3) . The witness for input 0 is `set_p2tr_key_spend_witness(&user_sig, 0)`, i.e., a single Taproot key-path signature whose `sighash_type` is embedded in `user_sig` and fully attacker-controlled by the withdrawer (per the threat model, the withdrawer chooses the signature and its sighash flag when calling `withdraw`).
- Unlike the *optimistic* payout path, which the aggregator explicitly forces to `SinglePlusAnyoneCanPay` and rejects otherwise (`"Ensure the signature uses SinglePlusAnyoneCanPay sighash type."`) [5](#0-4) , `Operator::withdraw` performs no such check on `in_signature.sighash_type` [2](#0-1) . If the withdrawer supplies `SIGHASH_SINGLE|ANYONECANPAY`, the signature commits only to input 0 and output 0 - the anchor output and the `OP_RETURN` (operator credit tag) are left completely uncommitted.
- Downstream, `Verifier::update_finalized_payouts` reads the operator pubkey straight from the first `OP_RETURN` output of whatever payout transaction is actually mined for that withdrawal index, with `parse_op_return_data` + `XOnlyPublicKey::from_slice`, and stores it as `payout_payer_operator_xonly_pk` [6](#0-5) [7](#0-6) . There is no check that this pubkey corresponds to whoever actually put the spendable input UTXO into the mempool or funded the fee.
- `PayoutCheckerTask::run_once` for operator B then looks up `get_first_unhandled_payout_by_operator_xonly_pk(pk_B)` [8](#0-7) , and if a row exists (because the mined tx's `OP_RETURN` decoded to `pk_B`), calls `handle_finalized_payout` and `mark_payout_handled`, crediting B [9](#0-8) .
- `is_kickoff_malicious` (the verifier's fraud check invoked later, at kickoff time) only compares `kickoff_data.operator_xonly_pk` against the `payout_payer_operator_xonly_pk` already stored in the DB from `update_finalized_payouts` [10](#0-9)  - it does not re-derive who actually funded the withdrawal, so it cannot detect that the stored value was tampered with before confirmation; it simply propagates the wrong operator identity.

Exploit outline: Operator A broadcasts a payout tx for a withdrawal whose input signature uses `SIGHASH_SINGLE|ANYONECANPAY` (choosable by the withdrawer, who may be the attacker or collude with the attacker). While the tx is unconfirmed, an attacker copies input 0 (same outpoint, same witness signature - still valid because it only commits to input 0/output 0) and output 0 verbatim, replaces output 2's `OP_RETURN` with operator B's public x-only pubkey (public via `OperatorConfig`/`GetParams`), and rebroadcasts as an RBF replacement (the `Payout` transaction type is explicitly enqueued with `FeePayingType::RBF` [11](#0-10) , i.e., explicitly marked replaceable). If the replacement is mined first, `update_finalized_payouts` records `pk_B`, and B's `PayoutCheckerTask` claims and is reimbursed for a withdrawal it never funded, while A - who actually paid the user - can never be credited (the DB row is already marked handled for a different operator).

Caveat / unverified detail: I could not fully confirm from the available context whether `TxSender`'s RBF funding path (`fund_raw_transaction` + `sign_raw_transaction_with_wallet`, used when broadcasting/bumping the `Payout` tx type) always adds an operator-wallet-signed input under default `SIGHASH_ALL`, which would re-commit the whole transaction (including the `OP_RETURN`) and block a naive third-party swap unless the attacker can still satisfy that additional input's signature. If such an input is always added on every broadcast/bump, the practical exploitability of the *mempool-replacement* variant needs re-verification in a live regtest test. The underlying design flaw - the `OP_RETURN` operator tag has no binding to the withdrawal-funding input inside the protocol's own transaction construction/verification code, and `Operator::withdraw` does not restrict the sighash type of the withdrawer-supplied signature - is independent of that caveat and is directly demonstrated by the cited code.

### Impact Explanation
If exploited, operator B is reimbursed (via `Reimburse`, gated by `mark_payout_handled`/`get_first_unhandled_payout_by_operator_xonly_pk`) for a withdrawal it never funded, while operator A - who genuinely paid the user out of pocket - is permanently blocked from reimbursement because the DB withdrawal row is already marked `is_payout_handled = TRUE` for a different `kickoff_txid`/operator. This matches the Critical categories "an operator reimbursed for a payout it never funded" and "an honest operator permanently unable to be reimbursed." The blast radius is per-withdrawal and repeatable across any withdrawal fronted under a weak sighash, and across any pair of registered operators (attacker only needs public knowledge of operator xonly pubkeys).

### Likelihood Explanation
Preconditions: (1) a withdrawal's user signature must use `SIGHASH_SINGLE|ANYONECANPAY` (or any sighash that excludes the OP_RETURN output) - a value the withdrawer freely chooses and `Operator::withdraw` does not reject; (2) the payout tx must still be unconfirmed/replaceable when the attacker acts, which is normal given the RBF fee-bumping design for `Payout` transactions; (3) whether an unmodified/attacker-crafted replacement can actually be relayed and mined depends on node-level RBF/full-RBF policy and on whether operator A's broadcast tx contains additional wallet-signed inputs (the caveat above) - this determines whether the mempool-swap variant is trivially exploitable versus requiring a race at broadcast time. The structural gap (no sighash restriction, no cross-check between OP_RETURN and funding source) is unconditionally present in the code regardless of that caveat.

### Recommendation
- Enforce a fixed, non-`ANYONECANPAY` sighash type (e.g., `SIGHASH_DEFAULT`/`SIGHASH_ALL`) for the standard `Operator::withdraw` payout signature, or otherwise ensure all outputs of `create_payout_txhandler` (including the `OP_RETURN`) are covered by the signature domain, exactly as already done for the optimistic payout path.
- Do not treat the mined `OP_RETURN` as sole source of truth for operator credit; verify that the funding operator's collateral/kickoff process independently derives or commits to the same operator identity (e.g., by requiring the `OP_RETURN` to be signed/committed with the withdrawal signature, or by having the operator pre-register/commit the intended `OP_RETURN` pubkey off-chain before broadcast and reject payouts whose mined `OP_RETURN` mismatches).
- Reject/ignore RBF replacements of a tracked `Payout` tx whose non-committed outputs (`OP_RETURN`, anchor) differ from the original broadcast, at the `TxSender` layer.

4. Mine to finality depth.
5. Assert `db.get_payout_info_from_move_txid` for the deposit returns `pk_B`, not `pk_A` (binding violated: `payout_payer_operator_xonly_pk != operator_who_funded_output_0`).
6. Run `PayoutCheckerTask` for both operators; assert B's `db.mark_payout_handled` fires (kickoff/reimburse issued for B) and A's does not, and that A's withdrawal index remains permanently `is_payout_handled = TRUE` under B's `kickoff_txid`, making A unable to ever be credited for the withdrawal it funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
