### Title
Reachable assertion in `Offer.__post_init__` allows DoS of wallet offer processing via a crafted offer with a duplicated coin spend - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.__post_init__` contains a bare `assert cs.coin not in adds` while iterating over the coin spends of an `Offer`'s underlying `SpendBundle`. This code path runs whenever an `Offer` object is constructed from externally supplied data (e.g. `Offer.from_bech32` / `Offer.from_bytes` / `Offer.from_spend_bundle`), which is the standard entry point for accepting an offer string sent by an untrusted counterparty. This mirrors the bug class in CVE-2024-24427 (Open5GS `amf_ue_set_suci`): a reachable `assert`/invariant check placed in a code path that processes attacker-supplied, unauthenticated input, causing an unhandled `AssertionError` instead of a graceful validation error.

### Finding Description
`Offer.__post_init__` populates the `_additions` cache by iterating `self._bundle.coin_spends` and guards against processing the same `Coin` twice with: [1](#0-0) 

```
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
    ...
```

This is a Python `assert` statement, not a `raise ValueError`/`raise ValidationError`. `Offer` objects are constructed directly from untrusted, attacker-controlled bytes via `Offer.from_bech32`/`Offer.from_bytes` (deserializing a `WalletSpendBundle` supplied as an "offer file" string by a trade counterparty) and via `Offer.from_spend_bundle`, both of which unconditionally invoke `__post_init__` (a `@dataclass` hook) with no pre-filtering of duplicate `CoinSpend` entries. Unlike the mempool/consensus layer where duplicate coin spends within a bundle are explicitly checked and converted into a typed `Err.DOUBLE_SPEND`/`ValidationError`, the wallet-side `Offer` parsing path has no such guard prior to `__post_init__`, so a crafted offer whose spend bundle contains two `CoinSpend` entries with an identical `Coin` (same `parent_coin_info`, `puzzle_hash`, `amount` — trivially producible since these are just serialized bytes under attacker control) reaches the bare `assert` and raises an unhandled `AssertionError`. [2](#0-1) 

`Offer.from_spend_bundle` similarly constructs an `Offer(...)` from an arbitrary `bundle: WalletSpendBundle`, triggering the same `__post_init__` path.

Any code that materializes an `Offer` from a counterparty-supplied offer blob — the offer-accept RPC flow (`TradeManager.respond_to_offer` calling into `Offer` parsing, and `check_offer_validity`) — is a reachable path for an unprivileged offer counterparty to trigger this assertion.

### Impact Explanation
Python's `assert` is intended for internal invariant checking, not external input validation; when it fires against attacker-controlled data it produces an unhandled `AssertionError` instead of a typed, catchable error such as `ValueError`/`ValidationError`. Depending on how deep in the call stack this is invoked (RPC handler, wallet CLI, or automated trade-taking logic without a broad `except Exception` wrapper), this can crash the request handler, corrupt wallet-side offer-processing flow, or abort the process handling the offer, denying the ability to process offers — the same "reachable assertion causing a spend/message-triggered processing halt" bug class described in the CVE. This satisfies the "spend-triggered transaction-processing halt" acceptance criterion for a wallet/offer counterparty threat actor with no privileges beyond sending an offer string.

### Likelihood Explanation
Likelihood is high given the low bar for the attacker: an offer counterparty only needs to construct a spend bundle containing two identical `CoinSpend` entries (trivial to encode — same coin fields, same puzzle reveal/solution bytes duplicated) and share it as a normal offer file/bech32 string, a completely standard interaction pattern (offers are routinely exchanged out-of-band and loaded by the receiving wallet). No signature validity, on-chain state, or special privilege is required merely to reach `Offer.__post_init__`; only accepting/inspecting the malformed offer (e.g. `get_offer_summary`, `check_offer_validity`, `respond_to_offer`) is needed.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit, catchable validation error (e.g. `raise ValueError("Offer spend bundle contains a duplicate coin spend")`), consistent with how other structural violations in this same method (duplicate requested payments, missing driver info) are already handled via `raise ValueError(...)` rather than `assert`. Additionally, audit `Offer.from_spend_bundle` and other `Offer` construction entry points for similar unvalidated assumptions before they process externally supplied `WalletSpendBundle` data, and ensure Python is not run with `-O` (which strips asserts) in any code path relying on such checks as security boundaries.

### Proof of Concept
1. Craft a `CoinSpend` `cs1` with `Coin(parent, puzzle_hash, amount)`, a valid-looking `puzzle_reveal`, and a `solution`.
2. Craft a second `CoinSpend` `cs2` using the identical `Coin(parent, puzzle_hash, amount)` (same three fields) but a different/duplicate solution, so `cs1.coin == cs2.coin`.
3. Build `WalletSpendBundle([cs1, cs2], G2Element())`, wrap it as the settlement bundle of an offer (or directly call `Offer.from_spend_bundle(bundle)` / serialize via `Offer(...).to_bech32()`), and deliver it to a victim wallet as an "offer".
4. When the victim wallet parses the offer (e.g., via `Offer.from_bech32(offer_str)` or any code constructing `Offer(...)` from this bundle), `__post_init__` iterates `coin_spends`; on the second entry `cs.coin in adds` is `True`, and `assert cs.coin not in adds` raises `AssertionError`, propagating as an unhandled exception in the offer-processing call path instead of a typed validation error.

Note: I was not able to fully trace every call-site of `Offer.from_bech32`/RPC dispatch (`wallet_rpc_api.py`) within the available context to confirm the exact exception-handling wrapper at each entry point (some RPC layers may catch broad `Exception` and convert to an error response, which would reduce impact to a benign error rather than a crash); this should be verified against the live `wallet_rpc_api.py` handlers for `take_offer`/`get_offer_summary` before treating this as a full process-crash DoS versus a request-level failure.
