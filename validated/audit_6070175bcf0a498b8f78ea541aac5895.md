### Title
`ThresholdKeys::new`/`read` never checks the secret share corresponds to the claimed verification share, letting attacker-supplied key material define an attacker-controlled group key - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, `secret_share`, and all `verification_shares` purely from the input byte stream, and `ThresholdKeys::new` accepts them without ever checking that `C::generator() * secret_share == verification_shares[i]`. Like the OpenSTAManager flaw — where arbitrary user-supplied statements are executed verbatim — whatever bytes an attacker supplies become the operative secret share and group key of the node.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` (lines 574-632) reads a curve ID, `t`/`n`/`i`, an `Interpolation` variant (an attacker-chosen `Constant(Vec<F>)` list of coefficients, or `Lagrange`), a raw `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (lines 349-391) only validates:

- `verification_shares.len() == n` and all indices `<= n` (lines 355-365),
- `Constant` interpolation requires `t == n` (lines 367-374),
- then computes `group_key` from the supplied verification shares and interpolation factors (lines 376-378).

Nowhere is the consistency relation `C::generator() * secret_share == verification_shares[&i]` enforced, and `group_key` is computed exclusively from the attacker-controlled `verification_shares` and `Interpolation::Constant` coefficients — both read from the wire. `read` additionally performs no check that `i <= n` relative to the shares map beyond `Participant::new` non-zeroness (line 600), and `interpolation_factor` for `Constant` indexes `c[i-1]` directly (line 228), trusting the supplied coefficient vector.

Concretely, an attacker who feeds crafted bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-byte sink) can construct a `ThresholdKeys` where:

- `interpolation = Constant(vec![1, 0, 0, ...])` or any weights they choose,
- `verification_shares` are points with known discrete logs (e.g., `k_j * G` for attacker-chosen `k_j`),
- `secret_share` is any scalar the attacker picks.

`ThresholdKeys::new` then certifies a `group_key` whose discrete logarithm `Σ factor_j * k_j` is fully known to the attacker, while the honest node's `view()`/`sign` path happily produces shares under a `secret_share` consistent with `verification_shares[i]` — i.e., a completely valid, attacker-unilaterally-spendable key that the victim believes is a distributed threshold key.

### Impact Explanation
Any funds or trust anchored to the deserialized `group_key()` are controlled entirely by the attacker: they know the full group private key and can sign/spend alone, while the node's honest signing path produces signatures that verify under that same key (since `ThresholdView` scales the supplied secret share and verification shares consistently). This matches the report's class: unvalidated attacker-supplied "statements" (here: the full statement of the key's algebraic structure — secret share, verification shares, and interpolation coefficients) are executed/instated verbatim, with no validation binding them to any ground truth. Even in the weaker variant where `secret_share` simply doesn't match `verification_shares[i]`, the node produces shares that fail aggregate verification while `blame` machinery attributes fault incorrectly, and any deposit address derived from `group_key()` is unspendable by the intended threshold.

### Likelihood Explanation
Reachable wherever `ThresholdKeys::read` is applied to bytes not fully trusted by the caller — e.g., key-share blobs transmitted, restored, or loaded from an attacker-influenced source. The prompt's scope explicitly names `ThresholdKeys::read` as an untrusted-byte sink. Exploitation requires no valid signature, no protocol participation, and no DKG — just the ability to supply the serialized keys. Severity is bounded by how the integrator obtains the blob; if it can be attacker-influenced, the impact is total key compromise, warranting High under the reachability assumptions given.

### Recommendation
In `ThresholdKeys::new`, add the consistency check `if C::generator() * secret_share != verification_shares[&params.i()] { Err(DkgError::...) }`. Additionally, for `Interpolation::Constant`, enforce `c.len() == n` (currently unchecked; `interpolation_factor` can panic or silently mis-weight), and consider rejecting degenerate/identity verification shares. This is the analog of the report's Option B: do not let the client state arbitrary structure — derive or verify it server-side.
