### Title
Wallet `sign_message_by_address`/`sign_message_by_id` non-safe mode allows an arbitrary-message BLS signing oracle usable for AGG_SIG forgery - (File: `chia/wallet/util/signing.py`)

### Summary
`WalletRpcApi.sign_message_by_address` and `sign_message_by_id` derive the wallet's **synthetic secret key** (the same key that authorizes on-chain coin spends via `AGG_SIG_ME`/`AGG_SIG_UNSAFE`) and hand it to `sign_message()` [1](#0-0) . When the caller sets `safe_mode=False` with `is_hex=True` (`SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT`), `sign_message()` signs the raw attacker-supplied bytes directly with `AugSchemeMPL.sign(secret_key, hex_message)` — no CHIP-0002 domain prefix, no coin binding [2](#0-1) .

### Finding Description
The safe default (`safe_mode=True`, `CHIP_0002`) wraps the message in `("Chia Signed Message", message)` before hashing, which is meant to prevent the signature from colliding with any valid consensus message format such as an `AGG_SIG_ME` payload (`delegated_puzzle_hash + coin_id + AGG_SIG_ME_ADDITIONAL_DATA`, as constructed in `WalletSigner.gather_signing_info` [3](#0-2) ). The RPC exposes an explicit opt-out (`safe_mode=False`) that removes this domain separation and signs the caller-controlled bytes verbatim with the wallet's real spend-authorizing key. Because `AGG_SIG_ME`/`AGG_SIG_UNSAFE` conditions are validated purely by checking `AugSchemeMPL.aggregate_verify` against `pubkey || message` pairs, any signature produced over a message that happens to equal `delegated_puzzle_hash + coin_id (+ additional_data)` for some coin owned by that key is fully valid as a spend authorization for that coin, regardless of which endpoint produced it. A local caller (e.g. a browser extension, CLI script, or any process holding wallet-RPC credentials that is expected only to obtain a message signature, not to move funds) can therefore choose a hex message equal to a target `delegated_puzzle_hash + coin_name` and obtain a raw signature that a CLVM inner puzzle would accept as `AGG_SIG_ME` for that coin — with no confirmation that this is a coin spend, no coin selection accounting, no fee/change checks, and no `WalletActionScope` mediation. This mirrors the Mailvelope flaw: an API meant for a narrow purpose (sign a message with cached key material) can be steered, without additional user interaction, into performing a raw private-key signing operation over attacker-chosen data.

### Impact Explanation
If any inner puzzle guarded by this key accepts `AGG_SIG_ME`/`AGG_SIG_UNSAFE` with a message an attacker can pre-compute (e.g. delegated-puzzle hash + coin name for a coin they know the ID of), obtaining such a signature via the "message signing" RPC is equivalent to obtaining unsanctioned spend authorization — i.e., unauthorized coin movement bypassing the normal `create_signed_transaction`/action-scope path. This is a signing-oracle problem: a component with access to "just sign this message" capability can escalate to full spend authority for that key.

### Likelihood Explanation
Exploitation requires: (1) RPC access to the wallet (the standard threat model for any local RPC caller, browser/dApp bridge, or overly-broad grant), and (2) knowledge of a target coin id and its guarding delegated-puzzle hash (both public on-chain data). No wallet-side confirmation UI or additional check exists in `sign_message_by_address`/`sign_message_by_id` to prevent `safe_mode=False` from producing a consensus-shaped payload; `is_hex=True` gives the caller byte-exact control of the signed message. This makes the attack straightforward for any caller who can invoke these two RPCs without also being trusted with `create_signed_transaction`.

### Recommendation
- Reject or heavily gate `safe_mode=False` combined with `is_hex=True` for `sign_message_by_address`/`sign_message_by_id`; at minimum, always domain-separate arbitrary-message signing from the exact byte layout used by `AGG_SIG_ME`/`AGG_SIG_UNSAFE` (`coin_id`/`AGG_SIG_ME_ADDITIONAL_DATA`-shaped payloads), e.g. by refusing to sign hex payloads whose length/structure could match a spend-authorization message, or by mixing in a fixed prefix unconditionally regardless of `safe_mode`.
- Consider requiring the caller to explicitly opt into "raw BLS signing" via a separate, clearly-labeled and non-default RPC/CLI path rather than a boolean flag on the general-purpose message-signing endpoint.

### Proof of Concept
1. Attacker identifies a coin `C` (puzzle hash `P`, coin id `C_id`) owned by victim's wallet key `sk`, guarded by the standard `p2_delegated_puzzle_or_hidden_puzzle` (accepts `AGG_SIG_ME` on `delegated_puzzle_hash || C_id || AGG_SIG_ME_ADDITIONAL_DATA` under `sk`'s synthetic key), and crafts a `delegated_puzzle` (e.g., "pay to attacker") whose tree hash is `D_h`.
2. Attacker computes `message_hex = (D_h + C_id + AGG_SIG_ME_ADDITIONAL_DATA).hex()`.
3. Attacker, having access only to the wallet RPC (not to `create_signed_transaction`), calls:
   `sign_message_by_address({address: victim_address, message: message_hex, is_hex: true, safe_mode: false})` [1](#0-0) 
4. `sign_message()` returns `AugSchemeMPL.sign(sk, D_h + C_id + AGG_SIG_ME_ADDITIONAL_DATA)` verbatim [4](#0-3) .
5. Attacker assembles a `CoinSpend(C, puzzle_reveal, solution=[D, D_h_conditions...])` with `D` producing `AGG_SIG_ME(pubkey, D_h||C_id||...)` and attaches the obtained signature; this spend bundle passes CLVM/consensus signature verification and moves coin `C` to the attacker without the victim wallet ever constructing or approving a transaction through its normal signing/action-scope flow.

def sign_message(secret_key: PrivateKey, message: str, mode: SigningMode) -> SignMessageResponse:
    public_key = secret_key.get_g1()
    if mode == SigningMode.CHIP_0002_HEX_INPUT:
        hex_message: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, bytes.fromhex(message))).get_tree_hash()
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        hex_message = bytes(message, "utf-8")
    elif mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        hex_message = bytes.fromhex(message)
    else:
        hex_message = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    return SignMessageResponse(
        pubkey=public_key,
        signature=AugSchemeMPL.sign(secret_key, hex_message),
    )
