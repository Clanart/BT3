### Title
Unprivileged senders can inject outputs misclassified as reserved internal types (Branch/Change/Forwarded), triggering unintended multisig aggregation transactions — (`networks/bitcoin/src/wallet/mod.rs`, `processor/src/networks/bitcoin.rs`)

### Summary
The Sealos advisory is a missing-authorization bug: a resource field the user fully controls (the Payment's namespace) is trusted as if it were system-owned. The Serai analog lives in the Bitcoin output scanner: the classification of a scanned output into `External` vs. the internally-reserved `Branch`, `Change`, and `Forwarded` kinds is decided purely by `script_pubkey` match against offsets derived from *public, fixed* constants. Any unprivileged party can compute the reserved offset addresses and send a Bitcoin transaction whose outputs are then treated by the processor as internally-generated outputs, with no check that the reserved offsets were ever legitimately used.

### Finding Description
`Scanner::register_offset` maps `script_pubkey → offset`, and `Bitcoin::get_outputs` maps `offset → OutputType` via the `kinds` table built in `scanner()`. The three reserved offsets are deterministic and publicly computable:

- `BRANCH_OFFSET = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")`
- `CHANGE_OFFSET = hash_to_F(KEY_DST, b"change")`
- `FORWARD_OFFSET = hash_to_F(KEY_DST, b"forward")`

The corresponding addresses are `key + G*offset`, where `key` is the (public) group key of the active multisig. Because `register_offset` auto-increments the scalar until `p2tr_script_buf` yields an even-Y point, the *effective* offsets are still deterministic given only the group key — an attacker can reproduce `scanner(key)` entirely offline.

`scan_transaction` then credits any output whose `script_pubkey` is in the map:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) { ... }
```
(`networks/bitcoin/src/wallet/mod.rs:205`)

and `get_outputs` classifies it with no further authorization:

```rust
let kind = kinds[offset_repr_ref];
```
(`processor/src/networks/bitcoin.rs:695`)

Nothing distinguishes "a Branch/Forwarded output the multisig itself produced" from "an output an arbitrary third party sent to a reserved address". Additionally, the Serai instruction payload (`data`) is only attached to `External` outputs, and `presumed_origin` is taken from attacker-controlled `tx.input[0]`'s spent output (`processor/src/networks/bitcoin.rs:707-735`), so injected outputs carry a fully attacker-controlled origin.

### Impact Explanation
- **Fee drain / forced signing:** Outputs classified `Forwarded`/`Branch` are inputs the multisig scheduler is designed to aggregate and spend (per `COST_TO_AGGREGATE` ≈ 800 sat). An attacker can repeatedly send dust-sized outputs to the `Forwarded`/`Branch` addresses; each is a real UTXO the multisig will sign a transaction to aggregate. Aggregation of an output worth less than `COST_TO_AGGREGATE` is net-negative — the multisig burns more in fees than the output is worth, and these are signatures over transactions the system never intended to make on inputs it never created.
- **Accounting misattribution:** A `Branch` output signals the rotation/branch funding path; injected `Branch` outputs can cause the processor to treat unsolicited funds as part of key-rotation flows, with attacker-chosen `presumed_origin` (e.g., impersonating another chain's refund address).
- This is a reachable, unprivileged analog of the Sealos flaw: a field entirely under the sender's control (the destination `script_pubkey` of their own transaction) grants the transaction a privileged internal classification, exactly as the user-controlled Payment namespace granted control over the billing account.

### Likelihood Explanation
Trivially reachable: the DST string, offset constants, group key, and the increment-until-even rule are all public. The attack requires only standard Bitcoin transactions — no collusion, no malicious validator, no leaked keys. Cost is bounded by the dust the attacker spends, while the cost imposed on the multisig is `COST_TO_AGGREGATE` per injection plus processing of misclassified events.

### Recommendation
Distinguish self-generated reserved outputs from externally-sent ones. Options: (a) commit the reserved-offset usage internally — only treat an output as `Branch`/`Change`/`Forwarded` if the processor previously created/expected it (track outpoints or txids it issued); or (b) include a private/secret component in the reserved offsets (e.g., `hash_to_F` over a seed known only to the processor set) so reserved addresses are not externally computable; or (c) at minimum, treat outputs at reserved offsets that arrive in transactions not authored by the multisig as `External` and still parse their `InInstruction`.

### Proof of Concept
```rust
// Attacker, knowing only the public group key `key`:
let mut scanner = Scanner::new(key).unwrap();
// Reproduce the processor's deterministic registrations:
let branch  = scanner.register_offset(Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")).unwrap();
let forward = scanner.register_offset(Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"forward")).unwrap();
let fwd_addr = p2tr_script_buf(key + ProjectivePoint::GENERATOR * forward).unwrap();

// Broadcast any tx paying 546+ sat (or even sub-COST_TO_AGGREGATE dust) to fwd_addr.
// In Bitcoin::get_outputs the scanned ReceivedOutput gets `kind == OutputType::Forwarded`,
// is fed to the multisig scheduler for aggregation, and carries an attacker-chosen
// presumed_origin taken from tx.input[0]. No authorization check ever verifies the
// output was produced by the multisig.
```
