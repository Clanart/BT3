### Title
Git-argument injection via unsanitized branch name in `push()` allows a maliciously-named remote branch to be interpreted as a `git push` flag (e.g. `--force`) - (File: `app/src/lib/git/push.ts`)

### Summary
`push()` builds the `git push` argv by directly interpolating `localBranch` (and `remoteBranch`) into the args array without validating that the branch name doesn't begin with `-`/`--`, and without an `--` "end of options" separator to stop git from parsing it as a flag.

### Finding Description
When `remoteBranch` is `null` (the code path taken the first time a new, unpublished local branch is pushed/"published"), the argv is: [1](#0-0) 

i.e. `['push', remote.name, localBranch]`. If `localBranch` is the single, unquoted string `--force`, this becomes a bare `git push origin --force`-style token that git's option parser recognizes as the `--force` flag rather than as a ref name, instead of the intended `git push origin --force` *ref*. Combined with the subsequent `args.push('--set-upstream')` (added because `remoteBranch` is null), the effective command becomes `git push origin --force --set-upstream`, which force-pushes the current HEAD to whatever the default push target resolves to (per `push.default`), bypassing the app's normal force-push consent flow (`askForConfirmationOnForcePush` / `ConfirmForcePush` popup) entirely: [2](#0-1) 

Such a branch name can originate from an attacker-controlled remote: git's low-level ref database does not forbid a ref component beginning with `-` (only certain git porcelain commands, and GitHub Desktop's own `sanitizedRefName`, defensively strip a leading `-`/`+`), so a malicious server can publish a branch literally named `--force` (or `-f`) via ref-level plumbing. GitHub Desktop's own leading-dash stripping is only applied when the *user types* a new branch/worktree name in the UI, not to branch names discovered by fetch/checkout: [3](#0-2) [4](#0-3) 

When the user checks out that remote branch, Desktop creates a local branch with the same short name (`nameWithoutRemote`): [5](#0-4) 

and this unsanitized `branch.name` is later passed straight into `push()`: [6](#0-5) 

Note that once the branch has been pushed once and has an upstream, `remoteBranch` is no longer `null`; in that case the refspec becomes the single joined token `` `${localBranch}:${remoteBranch}` `` (e.g. `--force:--force`), which does not match any known git-push long option and therefore fails safely with an "unknown option" error rather than being silently misinterpreted. The exploitable window is specifically the **first ("publish") push of a newly-checked-out, attacker-named branch**, where `remoteBranch` is `null`.

### Impact Explanation
A successful exploitation causes the user's current HEAD to be silently force-pushed to the remote (bypassing the `--force-with-lease` safety check and the app's own force-push confirmation dialog), potentially destroying remote history the user did not intend to overwrite. This is a "silent corruption of what the user pushes" impact as defined in scope.

### Likelihood Explanation
Requires: (1) attacker controls a remote/repository containing a branch whose ref name begins with `--` (achievable via git plumbing without needing to go through porcelain restrictions), and (2) the victim fetches, checks out, and then publishes that branch through GitHub Desktop's normal UI flow (Fetch → checkout remote branch → "Publish branch"). No unusual local steps are required beyond ordinary interaction with an attacker-supplied remote, matching the "repository content" attacker model in scope, though it does depend on git accepting `-b --force` as a literal branch name during checkout, which needs independent confirmation.

### Recommendation
Use git's `--end-of-options`/`--` separator before ref arguments in `push()` (and reject/validate branch names against `git check-ref-format` including a leading-dash check) so that `localBranch`/`remoteBranch` can never be interpreted as an option, e.g. build the refspec as `` `refs/heads/${localBranch}` `` fully qualified and insert `--` before the refspec token in the argv, mirroring the mitigation already present for `checkout` (`getBranchCheckoutArgs` appends `--`).

### Proof of Concept
1. On an attacker-controlled server, create (via low-level plumbing, e.g. `git update-ref refs/heads/--force <sha>` on the bare repo) a branch literally named `--force`.
2. Victim adds this remote in GitHub Desktop, fetches, and checks out the `--force` branch (Desktop creates a local branch named `--force` via `checkout.ts`'s `getBranchCheckoutArgs`).
3. Victim clicks "Publish branch" (first push, no upstream yet) → `performPush` → `pushRepo`/`push()` is invoked with `localBranch = '--force'`, `remoteBranch = null`.
4. `push()` builds `args = ['push', 'origin', '--force', '--set-upstream']` at `app/src/lib/git/push.ts:57-70`, and dugite's `exec` receives `--force` as a genuine flag argument instead of a ref name, resulting in an unconfirmed force push of `HEAD`.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
