### Title
Path-containment check in `resolveWithin` uses a naive string-prefix comparison, allowing sibling-directory escape - ([File: app/src/lib/path.ts])

### Summary
The bug report's core defect is a "containment" check that is weaker than it needs to be: instead of verifying that a sub-sequence lies strictly inside a bounded region (with the correct offset/boundary), the code merely checks numeric bounds that can be satisfied by adjacent, unintended data. GitHub Desktop has the exact same class of bug in its path-containment helper `_resolveWithin`, which decides whether a resolved filesystem path is safely "inside" a root directory by using a raw string `startsWith` comparison instead of verifying a path-separator boundary.

### Finding Description
`_resolveWithin` resolves a path and then checks containment like this: [1](#0-0) 

The check `realResolved.startsWith(realRoot)` is a pure string-prefix test. It does not verify that the next character after `realRoot` is a path separator. Consequently, any sibling directory whose name has the repository directory's name as a string prefix will pass the containment check even though it is not inside the repository at all.

For example, if the repository lives at `/Users/victim/Documents/GitHub/my-repo` and a sibling folder `/Users/victim/Documents/GitHub/my-repo-secrets` exists, then `realResolved = "/Users/victim/Documents/GitHub/my-repo-secrets/passwords.txt"` satisfies `realResolved.startsWith(realRoot)` because the string `"my-repo-secrets"` starts with `"my-repo"`. The function was designed to guarantee the resolved path is "at, or underneath" the root, per its own documentation: [2](#0-1) 
but the implementation does not enforce that guarantee across sibling-name collisions.

This helper is relied upon as the safety boundary in at least two attacker-reachable code paths:

1. Deep-link driven file reveal — `openRepositoryFromUrl` takes a `filepath` argument from an `x-github-client://` deep link (fully attacker-controlled, since it's a link the user is enticed to click), rejects only absolute paths, and then trusts `resolveWithin` to keep it inside the repo before calling `shell.showItemInFolder`: [3](#0-2) 

2. Conflict-file reading for Copilot — `buildConflictContext` uses the same `resolveWithin` guard before reading arbitrary file contents from disk and forwarding them into the Copilot conflict-resolution prompt: [4](#0-3) 

Both call sites explicitly comment that `resolveWithin` is the guard against path traversal, so the weakness in the guard itself directly undermines both usages, mirroring the external report's finding that a boundary/containment assertion is "weaker than it could and should be."

### Impact Explanation
Because the containment check can be defeated with a same-prefix sibling directory name (a very plausible real-world condition — e.g., cloning a fork of `my-repo` next to `my-repo` results in directories like `my-repo` and `my-repo-2`, or any user-created folder such as `my-repo-backup`), an attacker who controls:
- a crafted `x-github-client://` deep link (per the accepted impact scope, "a link or deep link the user clicks"), or
- crafted conflict file paths surfaced during a merge/rebase from a malicious remote,

can cause Desktop to resolve and act on a path outside the intended repository root while `resolveWithin` reports success. Depending on the call site this leads to file disclosure outside the repository boundary (revealing arbitrary files/folders via `shell.showItemInFolder`) or to unintended file contents outside the repo being read and sent off-device to the Copilot service. This satisfies the required impact category of "file … read outside the repo" driven by "a link or deep link the user clicks."

### Likelihood Explanation
The pre-condition (a sibling directory whose name is a prefix-superset of the repository directory name) is common in normal GitHub Desktop usage patterns (forks, duplicate clones, backup folders, `repo`, `repo-2`, `repo-old`, etc. commonly placed under the same GitHub Desktop base clone directory). No local/physical access, admin rights, or prior malware is required — only that the user clicks a crafted deep link or that Desktop processes conflict data from an attacker-influenced remote/repo, both of which are within the accepted attacker model.

### Recommendation
Change the containment check in `_resolveWithin` to require a path-separator boundary (or exact equality) rather than a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's recommendation of replacing a loose bounds check with one that explicitly accounts for the structural boundary (the separator between the root and the rest of the path), rather than a purely numeric/string containment test.

### Proof of Concept
1. Have GitHub Desktop with a repository cloned at `~/Documents/GitHub/my-repo`.
2. Create (or have pre-existing) a sibling directory `~/Documents/GitHub/my-repo-secrets/passwords.txt`.
3. Construct a deep link: `x-github-client://openRepo/<repoURL>?filepath=..%2Fmy-repo-secrets%2Fpasswords.txt`.
4. User clicks the link; `openRepositoryFromUrl` calls `resolveWithin(repository.path, '../my-repo-secrets/passwords.txt')`.
5. Because `"...my-repo-secrets".startsWith("...my-repo")` is true, `_resolveWithin` returns the resolved path instead of `null`, and `shell.showItemInFolder` reveals the out-of-repo file in the OS file browser — demonstrating the boundary check failed to keep the resolution confined to the repository directory tree.
