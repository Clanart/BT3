### Title
SignableTransaction fee calculation omits the OP_RETURN data output, producing a transaction whose realized fee rate is below the requested rate and potentially below minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to M-4 (pricing WBTC via the BTC/USD feed — valuing a thing by a proxy that is assumed equivalent but can diverge), `SignableTransaction::new` estimates the transaction's weight/vbytes — and therefore its fee — using only `payments` (and optionally `change`), while the already-appended OP_RETURN `data` output is excluded from the weight model. The constructed transaction is larger than the transaction the fee was priced for, so the actual fee rate diverges from the requested `fee_per_vbyte` and from the minimum-relay-fee check.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes an OP_RETURN output carrying caller-supplied `data` into `tx_outs` before performing fee estimation:

- `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })` (send.rs:194-202)
- The fee is then priced from a synthetic transaction built by `calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which serializes only the payment outputs — the data output is never included in the weight model (`calculate_weight_vbytes`, send.rs:62-127).
- The same omission occurs in the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226).

Because the real transaction includes the OP_RETURN output (up to ~80 bytes of data plus output overhead), its actual vsize exceeds `vbytes`/`vbytes_with_change` by roughly `9 + data.len()` vbytes. Two consequences follow:

1. The realized fee is `fee_per_vbyte * vbytes` (or `fee_with_change`), but the transaction is larger, so the effective sat/vbyte is strictly less than `fee_per_vbyte`. When change exists, the change output absorbs `input_sat - payment_sat - fee_with_change`, so the shortfall is fully borne as a reduced fee rate.
2. The minimum-relay-fee gate `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (send.rs:211) is evaluated against the underestimated `vbytes`, so a transaction can pass this check while its actual fee rate is below the network minimum.

An unprivileged party reaches this via the `data` field: `extract_serai_data` in `processor/src/networks/bitcoin.rs:493-524` pulls up to `MAX_DATA_LEN` bytes from OP_RETURN/witness data of inbound transactions, and `TransactionMachine`/`TransactionSignMachine` feed the resulting `SignableTransaction` into FROST signing (`taproot_key_spend_signature_hash` with `Prevouts::All`, send.rs:373-390). The `data` length directly controls the size of the unpriced output.

### Impact Explanation
Requests carrying larger `data` payloads produce transactions with a systematically lower fee rate than the protocol specified. At low `fee_per_vbyte` settings, the realized fee can fall below `DEFAULT_MIN_RELAY_TX_FEE` for the transaction's true size, causing relay/mempool rejection or indefinite non-confirmation of a threshold-signed spend — freezing funds that the protocol believes it has dispatched. The signed transaction is valid and consensus-correct, so the failure is silent at signing time.

### Likelihood Explanation
The divergence is deterministic and proportional to `data.len()`: any spend carrying a non-trivial OP_RETURN payload underpays relative to the intended rate. Whether it crosses the relay-fee floor depends on the configured `fee_per_vbyte` and payload size, so it is a degradation that becomes a stall at the margin rather than a guaranteed failure — consistent with a Medium.

### Recommendation
Include the OP_RETURN output in the weight model: build `tx_outs` (payments + data + change) first, then call `calculate_weight_vbytes` over the full output set, or pass an explicit data-output placeholder into the synthetic transaction so `vbytes`/`vbytes_with_change` reflect the serialized transaction that will actually be signed.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)`. The resulting `self.tx` contains payments + OP_RETURN + change outputs, while `needed_fee` was priced from a transaction containing only payments + change. Compare `tx.weight()`/`vsize()` of `self.tx` against `needed_fee / fee_per_vbyte`: the actual vsize exceeds the priced vsize by the OP_RETURN output size, and `fee()` (send.rs:138-141) equals `fee_per_vbyte * vbytes_underestimated`, confirming the realized rate is below the requested rate.
