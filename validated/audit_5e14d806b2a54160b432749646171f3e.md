### Title
Outputs sent to a multisig address before the key's `activation_number` (or after retirement) are silently never scanned, permanently losing the funds - ([File: processor/src/multisigs/scanner.rs])

### Summary
`PriceTierVesting` locks/unlocks tokens based on the *current* oracle price: tokens are only claimable while the transient condition (price > tier) holds, so users who don't act inside the window lose their entitlement. Serai's processor `Scanner` has the same shape: an on-chain output is only detected if it appears in a block scanned *while the receiving key is registered and not yet retired*. Since a key is only applied to blocks with `block_being_scanned >= activation_number`, any funds sent to the (deterministic, publicly derivable) address before activation — or after the retirement block — are permanently invisible to the processor and can never be credited or spent.

### Finding Description
In `ScannerHandle::register_key`, the new key is stored with an `activation_number` and it is asserted that `activation_number > scanner.ram_scanned` — i.e., the activation block must not already have been scanned. There is no back-scanning of earlier blocks for the new key. [1](#0-0) 

In the main scan loop, each key is skipped for any block before its activation:

```rust
for (activation_number, key) in scanner.keys.clone() {
  if activation_number > block_being_scanned {
    continue;
  }
  ...
  for output in network.get_outputs(&block, key).await { ... }
}
``` [2](#0-1) 

Symmetrically, `ack_block` retires a key at its `retirement_block`, after which blocks are no longer scanned for it. [3](#0-2) 

The receive address is a pure function of the group key: `external_address`/`forward_address` derive a P2TR script from `key + G*offset` where offsets are deterministic `hash_to_F(KEY_DST, ...)` values (`processor/src/networks/bitcoin.rs:308-346`). Anyone who knows or can predict the next multisig group key (e.g., a participant, or anyone observing a planned rotation) can compute the address and send funds *before* the key's activation block is reached by the scanner. The scanner iterates `(ram_scanned + 1) ..= latest_block_to_scan` and never revisits blocks for keys that weren't active then.

### Impact Explanation
Funds confirmed on-chain to a Serai multisig address are never emitted as `ScannerEvent::Block` outputs, never enter `ram_outputs`/the DB, and are therefore never credited nor spendable by the protocol — a permanent loss of those coins, analogous to vesting tokens that permanently re-lock when the price dips. The same applies to outputs arriving after `retire_key` runs: a late-arriving or reorg-adjacent payment to a retired key is dropped silently.

### Likelihood Explanation
Reachable by any unprivileged party who can send a Bitcoin transaction: the external/branch/change/forward addresses are deterministic given the group key, and the group key of a *pending* multisig is known to its participants (and to observers of the DKG/rotation flow) before the scanner activates it. A user or attacker sending to the address even one block before `activation_number` — an easy race, since key registration and on-chain funding are not atomic — causes permanent loss. Also triggers on benign timing: an integrator pre-announcing a deposit address before activation.

### Recommendation
Latch the "seen" state rather than gating on a transient window: when registering a key at `activation_number`, back-scan blocks from the earliest point the address could have been known (or at least emit a documented warning/refuse registrations where `activation_number` is far in the future while funds may already exist). Alternatively, on activation, perform a one-shot historical `get_outputs`/rescan over blocks `< activation_number` for the new key, and similarly continue scanning retired keys for a bounded confirmation horizon before dropping them. At minimum, document that addresses MUST NOT be shared/publishable before activation.

### Proof of Concept
1. Complete a DKG producing group key `K`; compute `addr = p2tr_script_buf(K)` (offset `Scalar::ZERO`) via `networks/bitcoin/src/wallet/mod.rs:80-86` / `Bitcoin::external_address`.
2. Before calling `scanner.register_key(txn, activation_number, K)`, broadcast a Bitcoin tx paying `addr`; let it confirm in block `B < activation_number`.
3. Call `register_key`. The scanner's loop at `processor/src/multisigs/scanner.rs:550-567` only applies `K` to blocks `>= activation_number`; block `B` was already passed (`ram_scanned >= B`), and `activation_number > block_being_scanned` would skip it anyway if revisited.
4. No `ScannerEvent::Block` containing the output is ever emitted; the output is absent from `ScannerDb` and cannot be included in a `SignableTransaction`, so the coins are unspendable by Serai despite being on-chain to Serai's key.

This mirrors the reported bug exactly: entitlement (detection of received funds) is evaluated against the state at scan time (is the key active *now*?) rather than the maximal state ever reached (did this output ever pay to a key we control?), penalizing anyone who didn't act inside the transient window.
