## Analog Found: Unbounded, Gas-Unmetered Loop Over EIP-7702 Authorization List in the EVM Ante Handler

### Title
Unbounded per-authorization loop in the EVM ante preprocessing decorator runs under an infinite gas meter, allowing a single SetCode (EIP-7702) transaction to force unmetered CPU work on every node during CheckTx/DeliverTx - ([File: x/evm/ante/preprocess.go])

### Summary
The Sherlock report describes unbound loops that iterate over unbounded-size collections tied to user actions, causing gas usage/CPU cost to grow without limit and potentially halting the protocol. The same bug class is reachable in `sei-chain` through the EVM ante handler's EIP-7702 `SetCodeTx` authorization-list processing, which loops over every authorization in the transaction while the ante context is under an **infinite gas meter**, before any per-item gas cost (intrinsic gas for authorizations) is actually charged.

### Finding Description
`EVMPreprocessDecorator.AnteHandle` sets an infinite gas meter for the entire EVM ante pipeline because "EVM handles gas checking from within": [1](#0-0) 

It then calls `associateAuthorizationAuthorities`, which iterates over **every** authorization in an EIP-7702 `SetCodeTx`'s `AuthList` — a field fully controlled by the transaction sender/sponsor — performing, for each entry: RLP encoding, a Keccak256 hash, and a full secp256k1 ECDSA public-key recovery (`RecoverAddressesFromAuthorization`), plus up to three state-store reads (`GetCode`, `GetNonce`, `GetEVMAddress`) and a `ctx.CacheContext()` allocation: [2](#0-1) [3](#0-2) 

`validateAuthList` (called during tx decoding) only rejects an **empty** list — there is no cap on the number of authorizations a `SetCodeTx` may carry: [4](#0-3) 

The only practical bound on list size is the overall Cosmos/Tendermint transaction byte-size limit, not a per-authorization gas or count cap. Because each authorization is compact (chain ID, 20-byte address, nonce, v/r/s), an attacker can pack many thousands of authorizations into a single transaction that still fits under typical mempool tx-size limits.

Critically, this loop executes **before** go-ethereum's intrinsic-gas accounting for the authorization list (which happens later, inside `core.StateTransition`/`BuyGas`, i.e., after the ante decorators finish) and while the ante context's gas meter is infinite. This means the ECDSA-recovery/state-read cost of an attacker-chosen number of authorizations is performed completely unmetered, in both `CheckTx` and `DeliverTx`, by every node that processes the transaction. The identical unmetered pattern exists in the legacyabci ante path (`AssociateAuthorizationAuthorities`): [5](#0-4) 
and is also referenced from the giga executor's authority-association check: [6](#0-5) 

This mirrors the reported bug class exactly: an unbounded loop over a user-controlled collection, executed as part of mandatory per-transaction protocol processing, with no per-iteration gas/resource cap enforced at the point the loop runs.

### Impact Explanation
A single crafted `SetCodeTx` with a very large authorization list forces every validator/full node's ante pipeline (both mempool admission via `CheckTx` and block execution via `DeliverTx`) to perform thousands of expensive ECDSA recoveries and state reads with no corresponding gas charge at that stage. Submitted broadly (e.g., broadcast to many nodes' mempools, or included in a block), this can materially slow down transaction admission and block processing across the network — a validator-halt/block-delay risk — while the attacker pays only the transaction's declared (and comparatively cheap, since the real per-authorization intrinsic gas cost is only charged later during EVM execution, and a transaction can also fail before then) gas price for a single transaction.

### Likelihood Explanation
Any unprivileged EVM transaction sender can construct and submit such a transaction — no special privileges, precompile access, or governance action are required. `SetCodeTx` is a fully supported transaction type on Sei's EVM per the module's supported-type table: [7](#0-6) 
This makes the finding directly and repeatably reachable from the public transaction-submission surface.

### Recommendation
- Enforce a maximum authorization-list length in `validateAuthList` (or in EVM tx admission logic) consistent with what go-ethereum's gas-based limits would allow, rejecting oversized lists before any per-authorization work is done.
- Charge a per-authorization gas/computation cost (or otherwise bound iteration cost) in `associateAuthorizationAuthorities`/`AssociateAuthorizationAuthorities` before the infinite gas meter is installed, or move authority pre-association after a length-bounded, metered checkpoint.
- Apply the same length cap consistently across `x/evm/ante/preprocess.go`, `app/ante/evm_checktx.go`, and the giga executor's authority-association path so no ante path remains unmetered.

### Proof of Concept
1. Craft an EIP-7702 `SetCodeTx` whose `AuthList` contains the maximum number of authorization tuples that still fits under the node's configured max transaction size (each tuple is compact: chain ID + 20-byte address + nonce + v/r/s), populated with syntactically valid but otherwise arbitrary/random signature values (they need not recover to a real, funded account to make the loop execute the expensive path — `AuthorityToPreAssociate` still performs RLP encoding, hashing, and `crypto.Ecrecover`/pubkey derivation for each entry before failing later checks).
2. Submit this transaction to a node's `CheckTx` (mempool admission) or via `broadcast_tx_sync`.
3. Observe that `EVMPreprocessDecorator.AnteHandle` → `associateAuthorizationAuthorities` iterates the full authorization list under an infinite gas meter, performing one ECDSA recovery and up to three state reads per entry, consuming CPU disproportionate to the fee paid, before any gas-based rejection can occur.
4. Repeating this from multiple senders/transactions concurrently amplifies aggregate CPU load across the network's nodes during block processing.

Note: I was not able to fully confirm the exact configured max-tx-bytes limit for Sei's default mempool/Tendermint config (this affects the precise max authorization count achievable per transaction) or measure real-world timing impact; that would require running the built binary/mempool configuration, which is out of scope for static/code-index review. A Devin session with terminal access could benchmark the actual worst-case wall-clock cost of `associateAuthorizationAuthorities` for a maximally sized `SetCodeTx` to quantify the achievable block-delay impact.

func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}

func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
}

func validateAuthList(authList AuthList) error {
	if len(authList) == 0 {
		return fmt.Errorf("auth list cannot be empty")
	}
	for _, auth := range authList {
		if auth.ChainID == nil {
			return fmt.Errorf("auth list chain id cannot be nil")
		}
		if err := validateHexAddress("auth list address", auth.Address); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list v", auth.V, 1); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list r", auth.R, 32); err != nil {
			return err
		}
		if err := validateSignatureValue("auth list s", auth.S, 32); err != nil {
			return err
		}
	}
	return nil
}

func AssociateAuthorizationAuthorities(ctx sdk.Context, ek *evmkeeper.Keeper, etx *ethtypes.Transaction) {
	auths := etx.SetCodeAuthorizations()
	if len(auths) == 0 {
		return
	}
	associateHelper := helpers.NewAssociationHelper(ek, ek.BankKeeper(), ek.AccountKeeper())
	for _, auth := range auths {
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, ek, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
