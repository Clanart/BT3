### Title
Missing Domain Separation in `associate` Precompile Allows Third-Party Replay of Off-Domain Signatures to Force Address Association and Fund Migration - (File: precompiles/addr/addr.go)

### Summary
The `associate` method of the `addr` precompile recovers a public key from a caller-supplied `(v, r, s)` triple over `keccak256(customMessage)`, where `customMessage` is an arbitrary, attacker-controlled string with no chain ID, contract address, or purpose tag baked into the hashing performed by the contract itself. This mirrors the reported `onchain-firewall` bug class: a modifier/entrypoint accepts arbitrary caller-supplied bytes as the "authorization context" instead of binding to a properly scoped, domain-separated payload, which lets one piece of signed data be misused to authorize an unrelated, privileged action.

### Finding Description
`PrecompileExecutor.associate` in [1](#0-0)  takes `v`, `r`, `s`, and `customMessage` directly from the caller's ABI arguments, computes `customMessageHash := crypto.Keccak256Hash([]byte(customMessage))`, and calls `helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)` to `ecrecover` a public key [2](#0-1) . The contract does not add any EIP-191/EIP-712-style domain separator, chain ID, contract address, or "Sei association" purpose string to the hash it computes — the intended convention (visible only in tests, not enforced on-chain) is that the caller pre-builds a personal_sign-style string (`"\x19Ethereum Signed Message:\n" + len + data`) before calling, but the precompile accepts **any** string and blindly hashes+recovers from it [3](#0-2) .

Because ECDSA signatures are valid for the exact hash they were produced over, any (message, signature) pair a user has produced anywhere — off-chain personal_sign flows for unrelated dApps or chains that happen to follow this exact prefixed-message format — can be resubmitted by any third party to `associate` on Sei, with no proof the user ever intended to interact with Sei.

The recovered public key drives `associateAddresses`, which is irreversible once set (`already associated` guard) [4](#0-3) , and which unconditionally migrates the victim's *entire* spendable balance and wei balance from their cast address to the newly associated Sei address, and removes the cast `BaseAccount`: [5](#0-4) 

This is state-changing (permanent account/pubkey binding + fund movement) yet is gated only by a signature over unscoped, attacker-suppliable data — the same "confusion" the external report flags: a security-critical entrypoint accepts a caller-chosen byte string as the thing being "verified," instead of a properly bound call context.

### Impact Explanation
A third party who obtains any personal_sign-style `(message, signature)` from a victim (e.g., from an unrelated web3 login flow, a signed message on another chain, or any public source) can front-run the victim and force an association and balance migration on Sei without the victim ever submitting a Sei transaction. Because the recovered address pair is mathematically tied to the same public key, the attacker cannot redirect funds to themselves, but they can: (a) forcibly consolidate/migrate the victim's cast-address balance at an attacker-chosen time, (b) permanently lock the account's pubkey/association state (via the "already associated" check) at a moment the victim did not choose, blocking any dApp/UX flow that expects the user to control when/if association happens, and (c) interact with `x/evm` code paths that assume association is a user-driven, deliberate action (per the "Dual Address Model" design notes) [6](#0-5) . This is a griefing/consent-bypass vector on an otherwise fund-moving, irreversible operation rather than direct fund theft, since actual value stays with the same key holder.

### Likelihood Explanation
Exploitability depends on an attacker obtaining a personal_sign-formatted `(message, signature)` pair from the target that was never intended for Sei. Personal_sign is an extremely common wallet interaction pattern (logins, off-chain attestations), and such artifacts are frequently observable or leak-able (e.g., posted publicly, stored in app logs, or shared as proof-of-ownership in other protocols). No special privileges are required by the attacker — this is reachable by any unprivileged EVM caller invoking the `associate` precompile method with data they intercepted elsewhere.

### Recommendation
Enforce domain separation inside `associate`/`associatePublicKey`: require `customMessage` to include a fixed, Sei-specific prefix/purpose string plus the chain ID (and ideally a nonce or the caller's intended `seiAddr`/`evmAddr`), and reject any message that doesn't match this exact template before hashing and recovering. This closes the arbitrary-data replay path by making it impossible for an off-domain signature to satisfy the association precompile's expected payload.

### Proof of Concept
1. Victim uses `personal_sign` in an unrelated dApp on any chain to sign `message = "\x19Ethereum Signed Message:\n32" + <32 arbitrary bytes>`, producing `(v, r, s)`.
2. Attacker observes this `(message, v, r, s)` (e.g., from a public API response, browser storage leak, or another chain's on-chain data).
3. Attacker calls the Sei `addr` precompile's `associate(v, r, s, message)` from any EVM account (no funds/permissions of the victim required) — see `PrecompileExecutor.associate` [1](#0-0) .
4. The precompile recovers the victim's public key from `keccak256(message)` and the signature, then unconditionally calls `AssociateAddresses`, which migrates all of the victim's cast-address `usei`/wei balances to the newly associated Sei address and removes the cast account [5](#0-4)  — all without the victim ever sending a transaction on Sei or intending to associate at that time.

Note: I was not able to fully trace every downstream consumer of the association state (e.g., all fee/refund or gas-normalizer code paths that key off "is address associated") within the available indexed context, so I cannot rule out additional higher-severity consequences of forced/premature association beyond the balance-migration and consent-bypass effects documented above.

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

## Dual Address Model

Every account can have both a Sei (bech32) address and an EVM (hex) address. The module maintains a bidirectional mapping between them.

- **Explicit association** — users can link their addresses via an Associate transaction or by signing any Cosmos/EVM transaction (the EVM address is derived from their secp256k1 public key).
- **Default (cast) addresses** — when no explicit association exists, the module falls back to a deterministic byte-cast. Cast addresses have limitations on receiving funds compared to fully associated addresses.

- **Why** - cast addresses will result in two views of the same account (e.g. two balances, etc.)
