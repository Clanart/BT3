### Title
CW20-to-ERC20 pointer trusts underlying CW20 contract's self-reported transfer amount, allowing fee-on-transfer/deflationary CW20 tokens to desynchronize ERC20 pointer accounting from real balances - (File: contracts/src/CW20ERC20Pointer.sol, app/receipt.go)

### Summary
`CW20ERC20Pointer.sol` is a Sei-provided ERC20 wrapper that lets any EVM contract interact with an arbitrary, permissionlessly-registered CW20 token as if it were a standard ERC20. Its `transfer`/`transferFrom` functions submit a `transfer`/`transfer_from` CosmWasm message with the caller-requested `amount` and unconditionally return `true` on success, without ever comparing the underlying CW20 balance before and after the call.

### Finding Description
`CW20ERC20Pointer.transfer` and `transferFrom` build a wasm `execute` payload with the requested `amount` and call `_execute`, returning `true` as soon as the wasm call succeeds: [1](#0-0) 

Nothing in this path verifies that the CW20 contract actually moved `amount` tokens; it only checks that the wasm execute call did not revert. Since any Sei user can permissionlessly deploy an arbitrary CW20 contract and register an ERC20 pointer for it (as shown by the pointer-registration test flow), a malicious CW20 author can implement `transfer`/`transfer_from` with a "tax"/fee-on-transfer or deflationary mechanic — e.g., crediting the recipient with less than the requested amount and burning/redirecting the difference — while the CW20's own wasm event still reports whatever `amount` attribute the (malicious) contract chooses to emit.

This same self-reported "amount" attribute from the CW20 wasm event is also what Sei's EVM receipt/log translation layer uses to synthesize the ERC20 `Transfer` log seen by EVM tooling, again without cross-checking real balance deltas: [2](#0-1) 

Any downstream EVM protocol (an "Allo"-style pool/vault, AMM, lending pool, etc.) that is built to accept arbitrary user-supplied ERC20 tokens and trusts either (a) the boolean return of `transfer`/`transferFrom`, or (b) `amount` requested equals `amount` actually received, will have its internal accounting (e.g., a `poolAmount`/deposit-ledger variable incremented by the nominal `amount`) desynchronize from the pointer's real `balanceOf`. Because `balanceOf` on the pointer is a live query into the CW20 contract (not a locally cached ledger) this does not corrupt the pointer's own state, but it does corrupt any consuming contract's internal accounting that assumes `transferFrom(..., amount)` moves exactly `amount` — exactly the bug class in the referenced Allo report, reachable here via a CosmWasm contract deployment plus permissionless ERC20-pointer registration, both doable by a single unprivileged user/transaction sequence.

### Impact Explanation
Any EVM protocol on Sei that accepts a CW20-backed ERC20 pointer as a depositable/poolable asset without doing its own balance-delta check can have its internal fund-accounting variables inflated relative to the tokens it actually received, leading to some depositors/recipients being unable to withdraw their full allocated share — a concrete loss of funds for legitimate users of that downstream protocol, mirroring the "High" severity Allo finding.

### Likelihood Explanation
Deploying a custom CW20 contract with attacker-controlled transfer semantics and registering an ERC20 pointer for it are both permissionless, single-transaction operations reachable by any user; the only precondition is that a victim protocol accepts arbitrary/unvetted CW20-pointer ERC20 tokens without validating actual balance changes, which is a realistic integration pattern for generic "any ERC20" pool/vault contracts.

### Recommendation
Consider having `CW20ERC20Pointer` (and any Sei tooling/guides for integrating pointer tokens) explicitly document that `transfer`/`transferFrom` return values and the `amount` parameter are not guaranteed to reflect the actual balance change, and/or have downstream protocols measure `balanceOf` before/after any pointer-token transfer rather than trusting the nominal `amount`. On the pointer side, `transfer`/`transferFrom` could optionally read the CW20 balance immediately before and after the wasm `execute` call and revert (or return the actual moved amount) if it diverges from the requested `amount`, so EVM contracts built against the standard ERC20 assumption are not silently exposed to fee-on-transfer/deflationary CW20 semantics.

### Proof of Concept
1. Deploy a malicious CW20 contract on Sei whose `execute_transfer`/`execute_transfer_from` handler moves `amount - fee` tokens to the recipient (and burns or redirects `fee`), but still emits a wasm `transfer` event/attribute claiming `amount` was transferred (or simply relies on the generic CW20 event translation in `app/receipt.go` reading whatever `amount` value the contract logs).
2. Call `seid tx evm register-evm-pointer CW20 <malicious_cw20_address>` to permissionlessly deploy a `CW20ERC20Pointer` for it, as exercised in the integration test harness: [3](#0-2) 
3. Deploy a victim EVM contract (a simple "pool") that calls `pointerToken.transferFrom(depositor, address(pool), amount)` and, on success, increments an internal `poolAmount += amount` ledger, exactly mirroring the Allo `Allo.sol` fund-pool pattern.
4. Have a depositor call the pool's deposit function with the malicious pointer token; the pool's `transferFrom` call succeeds and returns `true` per `CW20ERC20Pointer.transferFrom`, so `poolAmount` is incremented by the full requested `amount`, while `pointerToken.balanceOf(pool)` only increased by `amount - fee`.
5. When later recipients try to withdraw their allocated share based on `poolAmount`, the pool's actual pointer-token balance is insufficient, causing some recipients to be unable to withdraw their entitled funds — the same fund-loss outcome as the original Allo report.
