## Title
Silently swallowed error in binary-conflict detection can misclassify an unresolved binary merge conflict as "Resolved", allowing it to be silently committed - (File: `app/src/lib/git/status.ts`)

## Summary
In `app/src/lib/git/status.ts`, the function `getWorkingDirectoryConflictDetails` wraps the call to `getBinaryPaths` in a bare `try { } catch (error) {}` that discards any error and falls back to an empty `binaryFilePaths` array [1](#0-0) . This is structurally the same bug class as the esLBR report: a state-syncing call (`refreshReward()` / here, binary-detection) is allowed to fail silently, and the rest of the pipeline proceeds using a stale/incorrect derived value (esLBR balance snapshot / here, "is this conflicted file binary"), producing an incorrect but persisted result that downstream logic trusts.

## Finding Description
`getConflictDetails` computes `ConflictFilesDetails` (`conflictCountsByPath` and `binaryFilePaths`) used by `parseConflictedState` to decide, for each conflicted file, whether it is a text conflict (`ConflictsWithMarkers`, carrying a `conflictMarkerCount`) or a binary/manual conflict (`ManualConflict`) [2](#0-1) .

For the "stash popped into a conflicted working directory" path, `getWorkingDirectoryConflictDetails` calls `getBinaryPaths(repository, 'HEAD', conflictedFilesInIndex)`, which itself shells out twice via `git diff --numstat` and `git check-attr --stdin ... merge` [3](#0-2) . If either of those git invocations throws (e.g. a crafted `.gitattributes`, pathological path, or any other condition that makes the child process fail unexpectedly), the surrounding `try/catch` swallows it entirely and `binaryFilePaths` silently defaults to `[]` [1](#0-0) .

Because `binaryFilePaths` is empty, `parseConflictedState` treats the file as a **text** conflict and assigns it `conflictMarkerCount` from `getFilesWithConflictMarkers` (a text-marker scanner) instead of classifying it as `ManualConflict` [4](#0-3) . A binary file's raw bytes generally won't match the `<<<<<<<`/`=======`/`>>>>>>>` marker scan, so `conflictMarkerCount` ends up `0`.

That fabricated `conflictMarkerCount: 0` then flows into `hasUnresolvedConflicts`, `mapStatus`, and the conflict-resolution UI, all of which treat "`isConflictWithMarkers` && `conflictMarkerCount === 0`" as **resolved** [5](#0-4) . The unmerged-file renderer uses exactly this check to decide whether to show the resolution UI or render the file as already resolved [6](#0-5) .

## Impact Explanation
A file that is genuinely still conflicted (its on-disk content is an unresolved binary artifact from the stash pop, not something the user actually chose) is displayed and treated by Desktop as fully resolved. When the user proceeds to commit, `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` and stages/commits them via `createCommit`/`stageFiles` with no additional binary-conflict gate at commit time [7](#0-6) [8](#0-7) . This is a silent corruption of what the user commits: unresolved/incorrect binary content is committed (and can subsequently be pushed) as if the user deliberately resolved it, without any warning that the resolution status was fabricated by a swallowed error.

## Likelihood Explanation
The trigger requires only that `getBinaryPaths`'s git subprocess calls fail during status computation on a repository state the user already interacted with (popping a stash that reintroduces conflicts) — no elevated privileges, local access, or social engineering beyond the user working with a repository/stash whose content or attributes cause the `check-attr`/`diff --numstat` calls to error. Because the catch block is unconditional (`catch (error) {}`), any failure mode — not just the documented "HEAD doesn't exist" case — is absorbed, widening the window for this misclassification.

## Recommendation
Do not treat a failed `getBinaryPaths` call as equivalent to "no binary files." Distinguish the documented benign case (no HEAD) from unexpected errors: only swallow the specific "unborn branch" condition and propagate/log other failures, falling back to marking affected files as `ManualConflict` (safe/conservative) rather than defaulting to "text conflict with 0 markers" (which resolves to "no conflict"). At minimum, `getConflictDetails`/`getWorkingDirectoryConflictDetails` should never allow a caught exception to produce a `conflictMarkerCount: 0` result for files it could not actually verify.

## Proof of Concept
1. Create a repository and reproduce the "stash introduces conflicts" scenario covered by the existing test at `app/test/unit/git/status-test.ts` (`'parses conflicted files resulting from popping a stash'`) [9](#0-8) , but make the conflicted path a binary file whose `.gitattributes` `merge=binary` check would normally be detected by `getFilesUsingBinaryMergeDriver`.
2. Arrange for the `git check-attr --stdin` or `git diff --numstat` invocation inside `getBinaryPaths` to throw (e.g., inject a path/environment condition that causes the child process to fail) while `getWorkingDirectoryConflictDetails` is executing [10](#0-9) .
3. Observe that `getStatus` returns the file as `ConflictsWithMarkers` with `conflictMarkerCount: 0` instead of `ManualConflict`, because the exception was swallowed at `app/src/lib/git/status.ts:440-447`.
4. Observe the Desktop UI (`renderUnmergedFile`) shows the file as resolved (`defaultConflictsResolvedMessage`) even though the on-disk content is still an unresolved binary conflict artifact.
5. Commit — `_commitIncludedChanges` includes the file unchanged, silently persisting the unresolved/incorrect binary content into history.

  entry: UnmergedEntry,
  path: string,
  conflictDetails: ConflictFilesDetails

  switch (entry.action) {
    case UnmergedEntrySummary.BothAdded: {
      const isBinary = conflictDetails.binaryFilePaths.includes(path)
      if (!isBinary) {
        return {
          kind: AppFileStatusKind.Conflicted,
          entry,
          conflictMarkerCount:

          entry,
        }

export async function getBinaryPaths(
  repository: Repository,
  ref: string,
  conflictedFilesInIndex: ReadonlyArray<IStatusEntry>
): Promise<ReadonlyArray<string>> {
  const [detectedBinaryFiles, conflictedFilesUsingBinaryMergeDriver] =
    await Promise.all([
      getDetectedBinaryFiles(repository, ref),
      getFilesUsingBinaryMergeDriver(repository, conflictedFilesInIndex),
    ])

  return Array.from(
    new Set([...detectedBinaryFiles, ...conflictedFilesUsingBinaryMergeDriver])
  )
}

/**
 * Runs diff --numstat to get the list of files that have changed and which
 * Git have detected as binary files
 */
async function getDetectedBinaryFiles(repository: Repository, ref: string) {
  const { stdout } = await git(
    ['diff', '--numstat', '-z', ref],
    repository.path,
    'getBinaryPaths'
  )

  return Array.from(stdout.matchAll(binaryListRegex), m => m[1])
}

const binaryListRegex = /-\t-\t(?:\0.+\0)?([^\0]*)/gi

async function getFilesUsingBinaryMergeDriver(
  repository: Repository,
  files: ReadonlyArray<IStatusEntry>
) {
  const { stdout } = await git(
    ['check-attr', '--stdin', '-z', 'merge'],
    repository.path,
    'getConflictedFilesUsingBinaryMergeDriver',
    {
      stdin: files.map(f => f.path).join('\0'),
    }
  )

  return createLogParser({ path: '', attr: '', value: '' })
    .parse(stdout)
    .filter(x => x.attr === 'merge' && x.value === 'binary')
    .map(x => x.path)
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
