### Title
`_fetchRefspec` deliberately bypasses the single-network-operation lock, letting an attacker-controlled fork PR race a push/pull and corrupt repo state - (`app/src/lib/stores/app-store.ts`)

### Summary
The external Salty.io finding is a broken uniqueness invariant: a comment says "only one X can be open/running at a time," but the guard that is supposed to enforce it was silently made non-exclusive, letting multiple concurrent operations exceed the intended resource limit. GitHub Desktop has a structurally identical pattern: `withPushPullFetch` is the documented, single mutual-exclusion gate for all network/git operations on a repository ("Don't allow concurrent network operations"), but `_fetchRefspec` explicitly opts out of it, as the code comment admits.

### Finding Description
`AppStore.withPushPullFetch` is the invariant that is supposed to hold for the whole class of push/pull/fetch operations: [1](#0-0) 

Every normal entry point (`_push`, `_pull`, `_fetch`, `_fetchRemote`, the background fetcher, the repository-indicator fetch) routes through this gate, so `state.isPushPullFetchInProgress` is expected to be a reliable single-writer lock over the on-disk `.git` directory for a given `Repository`.

`_fetchRefspec`, however, is explicitly documented as *not* participating in that lock: [2](#0-1) 

This is called from the dispatcher's `fetchRefspec`, which in turn is reachable from pull-request/fork-branch flows (e.g. `_findPullRequestBranch` fetches a fork remote, and the PR/fork head data — clone URL, ref name — is attacker-controlled content coming from the GitHub API/PR object): [3](#0-2) [4](#0-3) 

Because `_fetchRefspec` neither checks nor sets `isPushPullFetchInProgress`, it can run concurrently with a user-initiated `_push`/`_pull`/`_fetch` that *did* take the lock. `git fetch` writes to shared repository metadata (`FETCH_HEAD`, `packed-refs`, loose refs under `.git/refs/`, and it can trigger `git gc`/repacking side effects) in the same `.git` directory that a concurrently running push/pull is also mutating (fast-forwarding branches, reconciling history, refreshing branch protection state) — see the overlapping git surface touched by `performPush`/`performPull`: [5](#0-4) [6](#0-5) 

This is exactly the Salty.io bug class: an invariant comment ("only one X at a time") exists, but one code path was carved out to bypass the shared mutual-exclusion mechanism, so the "at most one" guarantee the rest of the system relies on no longer holds for the full operation set.

### Impact Explanation
Two concurrent `git` processes racing on the same working directory/`.git` metadata can corrupt refs (e.g., a `packed-refs` rewrite racing with a push's fast-forward of tracking branches), leave the branch in an unexpected state, or cause the user-visible push/pull operation to report success/failure based on stale state read while `_fetchRefspec`'s fetch was concurrently mutating refs underneath it. Since `_fetchRefspec` is reachable via fork/PR data that is attacker-influenced (a malicious fork owner controls when/if their branch exists, forcing repeated fetch attempts, and controls the clone URL/ref), this gives a remote actor a way to reliably trigger the racing fetch while a victim's legitimate push/pull is in flight, silently corrupting what the user believes they just committed/pushed (their local view of tracking-branch tips, or the state used to decide fast-forward eligibility). This lines up with the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The race requires a victim to be viewing/interacting with a pull request from a fork (triggering `_fetchRefspec`/`_fetchRemote` for that fork's remote) at roughly the same moment they push or pull in the same repository — a plausible, unprivileged, no-malware scenario since Desktop actively fetches PR/fork data in the background while the user works. The comment in the code itself acknowledges the gap and that it "might require some rework," which corroborates that this is a known, unresolved concurrency hole rather than a speculative one. However, actually observing a *corrupting* (vs. merely redundant) race requires precise timing, which lowers likelihood from certain to moderate.

### Recommendation
Route `_fetchRefspec` (and any other network/git action affecting the same working directory) through `withPushPullFetch`, or introduce a queueing mechanism (as the code comment suggests — "This might require some rework in the future to chain these actions") so that fork/PR-triggered fetches are serialized with user-initiated push/pull/fetch operations instead of bypassing the lock outright.

### Proof of Concept
1. Open a repository in Desktop that has an open pull request from a fork.
2. Trigger `_findPullRequestBranch`/`_fetchRefspec` (e.g., by viewing the PR's files or checking it out) at the same time the user issues `_push` or `_pull` on the same repository.
3. Because `withPushPullFetch`'s `isPushPullFetchInProgress` guard is bypassed by `_fetchRefspec`, both `git fetch <fork-remote> <refspec>` and the push/pull's own `git fetch`/`git push`/ref-update sequence run concurrently against the same `.git` directory.
4. Observe (via logging/timing) that ref state (`packed-refs`, `FETCH_HEAD`, tracking branch tips) can be updated out of order relative to the push/pull's fast-forward and refresh steps, since there is no serialization between the two code paths — confirming the invariant described in the `_fetchRefspec` comment is violated in practice, not just in theory.

I was unable to fully verify the exact git-level failure mode (e.g., an actual `index.lock` collision or ref corruption message) because reproducing concurrent git process races requires runtime/dynamic testing beyond static code search; the codebase evidence establishes the broken invariant and the reachable, attacker-influenced trigger, but the precise on-disk corruption artifact would need to be confirmed by a background agent running the app with instrumented git calls.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

        return
