### Title
`ReceivedOutput::read` accepts attacker-controlled offset/value/outpoint with no consistency or on-chain checks, allowing phantom funds to be reported as received and spent into an invalid transaction — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` is Serai's representation of a spendable Bitcoin output. Its deserializer, `ReceivedOutput::read`, accepts a scalar `offset`, a `TxOut` (value + script_pubkey), and an `OutPoint` verbatim from untrusted bytes, with no check that (a) the offset actually derives the key committed in `script_pubkey`, (b) the outpoint exists on-chain, or (c) the claimed value matches reality. `SignableTransaction::new` then trusts `input.output.value` for its funds accounting and uses the outpoint as a real input, producing a transaction that either cannot be signed (offset mismatch) or is consensus-invalid (phantom prevout). This is the Bitcoin analog of the reported bug class: the subsystem computes a `value` it will commit/spend while lacking the ability to actually receive or hold those funds — the contract claimed a `value` for `call` it could never possess; here the wallet claims input value for a sighash it can never validly satisfy.

### Finding Description
`ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`) performs only raw deserialization:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ...
  output = TxOut::consensus_decode(&mut buf_r)...
  outpoint = OutPoint::consensus_decode(&mut buf_r)...
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

The struct exposes `offset()`, `output()`, `outpoint()`, and `value()` as authoritative (lines 99-118), and `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`) consumes them directly:

- `input_sat` is summed from `input.output.value` (line 175),
- `previous_output: input.outpoint` becomes a real `TxIn` (line 180),
- `prevouts` — which feed `Prevouts::All` in the BIP-341 sighash (send.rs:375-386) — are taken from `input.output` (line 253).

The only consistency check anywhere is in `SignableTransaction::multisig` (send.rs:273-285): `p2tr_script_buf(offset.group_key()) != self.prevouts[i].script_pubkey` returns `None`. That check catches a mismatched offset but does nothing for a fabricated outpoint or inflated value. Two failure modes result:

1. **Mismatched offset**: An attacker supplies bytes where `offset` does not derive the script's key. The output is treated as received funds, yet `multisig()` returns `None` — funds reported received that are permanently unspendable, stalling transaction construction.
2. **Fabricated outpoint/value**: An attacker supplies a `ReceivedOutput` whose `script_pubkey` legitimately matches the multisig key (anyone can compute it) but whose `outpoint` never existed or whose `value` exceeds the real output. `input_sat` is inflated, `SignableTransaction::new` succeeds, the FROST signing ceremony runs and produces signatures over `Prevouts::All` committing to the false amount — yielding either a consensus-invalid transaction (nonexistent prevout) or invalid signatures (wrong amount committed in sighash, since BIP-341 binds amounts).

### Impact Explanation
Funds reported received that are not spendable — an explicitly in-scope impact. An unprivileged party who can feed bytes to `ReceivedOutput::read` (a listed untrusted-bytes API in the rules) can inject phantom inputs into the wallet's accounting, causing `SignableTransaction::new` to emit transactions burning real fee budget or stalling signers, and to compute `fee()`/`input_sat` on fictitious value. There is no on-chain revalidation anywhere between `read` and `multisig`.

### Likelihood Explanation
Requires an attacker to supply the serialized `ReceivedOutput` bytes rather than the scanner populating them from `scan_transaction`. Wherever outputs are round-tripped through `serialize`/`read` across a trust boundary (e.g., deserialized from peer/coordinator-supplied data rather than local scan results), this is directly reachable. Impact is capped at invalid transactions / unspendable reported funds rather than key compromise, matching Medium severity.

### Recommendation
Either (a) re-derive and verify `p2tr_script_buf(key + G*offset) == output.script_pubkey` inside `ReceivedOutput::read` (requires carrying the base key, e.g., a `Scanner`-contextual reader), or (b) document that `read` must only consume locally-scanned data and add a `verify`/`validate` step that confirms the outpoint exists on-chain with the claimed value before it enters `SignableTransaction::new`. At minimum, perform the offset/script consistency check at `read` time rather than at `multisig` time, so malformed inputs are rejected at deserialization.

### Proof of Concept
```rust
use bitcoin_serai::{bitcoin::*, wallet::{ReceivedOutput, SignableTransaction}};
use k256::{ProjectivePoint, Scalar};
use frost::curve::{Secp256k1, Ciphersuite};

// key: the multisig group key the wallet scans for.
let mut buf = Vec::new();
// Claim offset ZERO with a script_pubkey matching key + 0*G (attacker-computable),
// but a fabricated value and an outpoint that does not exist on-chain.
buf.extend(Scalar::ZERO.to_bytes());
let fake_out = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: bitcoin_serai::wallet::p2tr_script_buf(key).unwrap(),
};
buf.extend(bitcoin::consensus::serialize(&fake_out));
buf.extend(bitcoin::consensus::serialize(&OutPoint::null()));

let phantom = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// Reports 1,000,000 sats "received" that were never sent.
assert_eq!(phantom.value(), 1_000_000);

// SignableTransaction::new happily accounts the phantom input and emits a TX
// spending a nonexistent prevout — consensus-invalid, and the BIP-341 sighash
// commits to the fabricated amount via Prevouts::All.
let tx = SignableTransaction::new(
  vec![phantom],
  &[(payment_script, 546)],
  None, None, 10,
).unwrap();
```
