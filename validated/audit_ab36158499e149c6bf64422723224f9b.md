### Title
Fee-token pool has no reserved-liability accounting, causing relayer fee refunds/rewards to revert and lock cross-chain message state - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` collects and pays all relayer fees from a single, shared `feeToken` balance rather than per-request escrow. Governance withdrawals via `HostManager.onAccept` → `IHostManager(_params.host).withdraw()` are not checked against the sum of outstanding `_requestCommitments[...].fee` liabilities, so the pool can be drawn below what is owed to pending requests. When that happens, the unconditional `IERC20.safeTransfer` calls that pay relayers/refund payers in `dispatchIncoming(GetResponse,...)` and `dispatchTimeOut(...)` revert, which unwinds the entire external call — including the replay-protection state writes made earlier in the same call. This is the same root cause as the GMX report: a fee payment executed without first checking the paying contract actually holds the funds, causing the whole handling flow (and its state bookkeeping) to fail atomically.

### Finding Description
`EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)` / `fundRequest` all pull `feeToken` into the shared host balance and only track the payer/fee in `_requestCommitments[commitment]` [1](#0-0) , [2](#0-1) . There is no separate escrow accounting; the fee simply becomes part of the contract's total `feeToken` balance.

`HostManager.onAccept` allows a `Withdraw` action to pull `feeToken` out of the host with no check against total outstanding committed fees [3](#0-2) . The rust integration test suite explicitly proves that the corresponding `withdraw`/callback path reverts if the host balance is insufficient at the time of an `onAccept` transfer, confirming there is no guard rail preventing over-withdrawal relative to reserved liabilities [4](#0-3) .

Downstream, the functions that pay out these fees perform an unconditional `safeTransfer` after a successful application callback, exactly mirroring the `GmxAdapter.withdrawClosedSize()` pattern (transfer fee without verifying sufficient balance first):
- GET response relayer reward: [5](#0-4) 
- GET timeout refund: [6](#0-5) 
- POST timeout refund: [7](#0-6) 

In all three cases, the pattern is: write replay-protection/receipt state → call the destination app's callback → if callback succeeds, `safeTransfer` the fee. If the transfer reverts (insufficient `feeToken` balance in the host), the *entire* external call reverts, because Solidity unwinds the whole call frame on failure — this rolls back the receipt/commitment-deletion writes made earlier in the same call, not just the transfer. This is functionally identical to the seed bug: "the position may not have enough funds to send... resulting in the transaction reverting and the position state not being correctly handled."

### Impact Explanation
If the shared `feeToken` pool ever falls below the sum of fees owed on pending/in-flight requests (which is entirely possible since withdrawals are not checked against reserved liabilities), then:
- `handleGetResponses()` can never successfully deliver a legitimate, correctly proven GET response for the affected commitment, because `dispatchIncoming(GetResponse,...)` will always revert at the final `safeTransfer`, discarding the state changes (`_responseReceipts`) and leaving the message permanently un-processable.
- `handlePostRequestTimeouts()`/GET-timeout handling analogously can never complete: the app's timeout callback keeps re-running (idempotently, per design) but the fee refund step keeps reverting, so `payer` funds are permanently unrecoverable and the request commitment can never be cleared.

This matches the required impact classes: loss/lock of bridged relayer-fee funds and unauthorized-execution-adjacent state corruption (a correctly verified, legitimate proof can be permanently prevented from taking effect on-chain because of an unrelated, unchecked balance dependency).

### Likelihood Explanation
The triggering condition (feeToken balance dropping below outstanding fee liabilities) is realistic because: (1) the pool commingles all pending-request fees with protocol-owned "bridge revenue" with no bookkeeping distinguishing the two, and (2) the withdrawal path performs no check against total committed liabilities before transferring out `feeToken`, as demonstrated by the existing insufficient-balance test which shows the transfer simply reverts rather than being prevented up front [4](#0-3) . Any legitimate, routine sweep of "protocol revenue" that doesn't account for currently-pending request fees can trigger this state, and once triggered it affects every pending GET response / timeout for as long as the pool remains underfunded.

### Recommendation
Track reserved liabilities explicitly (e.g., a running total of all outstanding `_requestCommitments[...].fee` amounts) and:
1. Cap `withdraw()` to only the surplus above total reserved fees, so governance/withdrawal actions can never dip into funds owed for pending requests.
2. In `dispatchIncoming(GetResponse,...)` and both `dispatchTimeOut` overloads, check `IERC20(feeToken()).balanceOf(address(this))` against the fee owed before transferring; if insufficient, pay out whatever is available (partial payment) rather than reverting the whole call, so replay-protection/state bookkeeping is not rolled back and delivery/timeout processing can still complete.

### Proof of Concept
1. Multiple users dispatch POST/GET requests with relayer fees, each fee added to the host's shared `feeToken` balance via `dispatch()`/`fundRequest()` [1](#0-0) .
2. Governance sends a `Withdraw` action through `HostManager.onAccept`, withdrawing an amount up to the full host balance — nothing in `HostManager.onAccept` checks it against the sum of fees still owed to pending requests [3](#0-2) .
3. A relayer submits a valid, correctly proven GET response for one of the still-pending requests via `handleGetResponses()` → `EvmHost.dispatchIncoming(GetResponse,...)`. The app callback (`onGetResponse`) succeeds, but the trailing `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts because the host balance is now less than `fee` [8](#0-7) .
4. The revert unwinds the whole `dispatchIncoming` call, including the `_responseReceipts` write, so the correctly-proven response is never recorded as delivered and can never be retried to success while the pool remains underfunded — reproducing the exact "callback succeeds, fee transfer fails, resulting state mishandling" pattern from the seed report, confirmed feasible by the existing `test_host_manager_insufficient_balance` test showing the same underlying `safeTransfer`-reverts-on-insufficient-balance behavior [4](#0-3) .

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }

fn test_host_manager_insufficient_balance() {

	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);

}
