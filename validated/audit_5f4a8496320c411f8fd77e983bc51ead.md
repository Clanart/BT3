### Title
Attacker-controlled `ReceivedOutput` with a maximal `value` permanently panics transaction construction via unchecked `u64` addition - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`ReceivedOutput::read` accepts a consensus-decoded `TxOut` whose `value` is an arbitrary `u64` up to `u64::MAX` (`networks/bitcoin/src/wallet/mod.rs:122-134`). `SignableTransaction::new` then performs unchecked `u64` additions over attacker-influenced amounts — `payment_sat + needed_fee`, `input_sat < (payment_sat + needed_fee)`, and `payment_sat + fee_with_change` (`send.rs:215`, `send.rs:228`) — and `SignableTransaction::fee` does an unchecked `sum(inputs) - sum(outputs)` subtraction (`send.rs:139-140`). A single poisoned `ReceivedOutput` (e.g., `value = u64::MAX`) makes these additions/subtractions overflow and panic, permanently bricking any signing attempt that includes the output — the exact analog of a `type(uint256).max` `expiration` permanently reverting `refundDeposit()`.

### Finding Description
In the source report, an unprivileged funder submits an extreme `_expiration`, and the later `depositTime + expiration` addition overflows inside `getLockedFunds()`, so `refundDeposit()` reverts for everyone forever. Here, `ReceivedOutput::read` performs no sanity bound on `output.value` (any 8-byte value up to `u64::MAX` deserializes successfully, well above the 21M BTC / ~2.1e15 sat cap). Once such a `ReceivedOutput` is included in `inputs`:

- `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();` (`send.rs:175`) overflows if the poisoned output is combined with any other input.
- `input_sat < (payment_sat + needed_fee)` (`send.rs:215`) and `input_sat.checked_sub(payment_sat + fee_with_change)` (`send.rs:228`) panic on the inner `payment_sat + ...` overflow regardless of `checked_sub`.
- Even if construction were reached, `self.prevouts...sum::<u64>() - self.tx.output...sum::<u64>()` in `fee()` (`send.rs:139-141`) underflows when the fabricated input value exceeds real outputs.

Because the poisoned `ReceivedOutput` is indistinguishable at scan/serialization time, every `SignableTransaction::new` / `TransactionSignMachine` path that selects it panics rather than returning a `TransactionError`, permanently denying the signing flow for those funds — the same "one tiny malicious record blocks everyone" shape as the OpenQ report.

### Impact Explanation
Any call site that reads untrusted `ReceivedOutput` bytes (peer-supplied or RPC-ingested data funneled into `ReceivedOutput::read`) can inject one record that makes all subsequent spend attempts panic. This is a persistent denial of service on the wallet's transaction-signing path for affected inputs, not a transient revert.

### Likelihood Explanation
The attacker only needs to get one crafted `ReceivedOutput` byte string consumed by `ReceivedOutput::read` and selected as an input — no key material, no threshold collusion, and minimal cost. Construction panics deterministically on overflow in debug builds and produces silently wrong `input_sat`/fee values in release builds (wrapping arithmetic can also mint an understated `needed_fee`, yielding an unbroadcastable or over-fee transaction).

### Recommendation
Validate `output.value` in `ReceivedOutput::read`/`scan_transaction` against the Bitcoin supply cap (`Amount::MAX_MONEY` / `Amount::from_sat` checks, and `Amount::to_sat` already bounds `TxOut` values to `u64`), and use `checked_add`/`saturating_add` for `input_sat`, `payment_sat`, and the `sum::<u64>() - sum::<u64>()` fee computation, mapping overflow to `TransactionError::NotEnoughFunds` instead of panicking.

### Proof of Concept
```rust
// Construct ReceivedOutput bytes: offset = Scalar::ZERO, TxOut.value = u64::MAX,
// arbitrary script_pubkey + outpoint. After ReceivedOutput::read succeeds:
let inputs = vec![poisoned_output, any_real_output];
// send.rs:175 -> sum::<u64>() overflows u64 -> panic
// or with a single poisoned input:
// send.rs:215 -> payment_sat + needed_fee overflows -> panic
let _ = SignableTransaction::new(inputs, &[(script, DUST)], None, None, 1);
```
Every retry panics identically, mirroring `refundDeposit()` always reverting once a max `expiration` deposit exists.

Confidence caveat: I verified the read path and the unchecked arithmetic in `wallet/mod.rs` and `wallet/send.rs`; I could not fully trace every upstream caller feeding `ReceivedOutput::read`, so reachability rests on the prompt's stated untrusted-bytes surface.
