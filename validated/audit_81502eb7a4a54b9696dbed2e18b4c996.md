## Title
Attacker-controlled `.git` file redirection lets a cloned repository trick "Trust Repository" into granting global Git trust to an arbitrary attacker-chosen path - (File: `app/src/lib/git/rev-parse.ts`, `app/src/ui/add-repository/add-existing-repository.tsx`, `app/src/lib/git/config.ts`)

### Summary
The report's broken invariant is: a value the user *believes* they are approving (allowance amount / spender) is not the value actually acted upon, because an attacker can control the state between the check and the act. In GitHub Desktop, the analogous "approve → act" pair is `getRepositoryType()` (check: "is this directory unsafe, and if so, what path is unsafe?") followed by `addSafeDirectory()` (act: grant a persistent, global trust exception for that path). The path that gets trusted is taken verbatim from Git's own dubious-ownership error message, which Desktop does not validate against the directory the user actually opened. Because GitHub Desktop already treats `.git` "gitdir:" redirection files as a normal, expected repository artifact (used for submodules/worktrees), a malicious cloned/fetched repository can ship a `.git` file that redirects Git's repository discovery to an attacker-chosen path elsewhere on disk (including a UNC network path, per the app's own changelog support for "trusting repositories on network shares"). When Git reports that redirected path as having "dubious ownership," Desktop's UI surfaces it and, on user confirmation, silently adds that attacker-chosen path — not the folder the user opened — to the user's **global** `safe.directory` allow-list.

### Finding Description
`getRepositoryType()` runs `git rev-parse --is-bare-repository --show-cdup --git-dir` inside the folder the user is opening, and if Git refuses due to ownership mismatch, extracts the path directly from Git's stderr: [1](#0-0) 

That extracted `path` is untrusted, attacker-influenceable text echoed straight out of `unsafeMatch[1]` with no validation that it corresponds to the directory the user selected.

`.git` "gitdir:" pointer files are a normal, first-class mechanism already parsed elsewhere in Desktop (submodules/worktrees), proving that a checked-out repository can legitimately contain a `.git` file that redirects to an arbitrary relative (and therefore, via `../..` traversal, arbitrary absolute) location: [2](#0-1) [3](#0-2) 

Git's own repository discovery follows the same `.git` file redirection before performing its ownership/safe-directory check, so a redirected target with different ownership than the current user triggers the "detected dubious ownership" error reporting the *redirected* target, not the folder the user opened.

When the UI surfaces this as "unsafe," it shows the (attacker-controlled) path and offers a one-click "Trust Repository" action that calls `addSafeDirectory(repositoryUnsafePath)`: [4](#0-3) [5](#0-4) 

The same pattern exists for repositories already tracked by Desktop: [6](#0-5) 

`addSafeDirectory()` writes the path into the **global** Git configuration (`~/.gitconfig`), which is used for every future Git invocation by that OS user, on every repository — not just the one being opened: [7](#0-6) 

Desktop's own changelog confirms UNC/network-share paths are a supported, real-world case for this trust flow, which is exactly the kind of attacker-reachable location a `.git` redirection could point to: [8](#0-7) 

### Impact Explanation
`safe.directory` exists specifically to stop Git from treating a dubious-ownership directory (which can execute arbitrary code via local `.git/config`, hooks, or `core.fsmonitor`/`core.hooksPath` settings) as trusted. Here, the attacker — merely by having the victim clone/open a crafted repository — can cause the *victim's own client* to add an attacker-selected directory (potentially an attacker-controlled network share, or a path the attacker can later populate/control, e.g. a mount point, redirected profile folder, or shared/synced directory) to that global allow-list, without the victim's informed consent as to *which* path is actually being trusted (the dialog text is technically accurate but the discrepancy between the opened folder and the trusted path is easy to overlook, especially with a crafted deep relative path or truncated UI text). Once trusted, if Git is later pointed at that path by any means (another tool, a future clone target reused by the attacker, symlink, or config include), Desktop/Git will skip the dubious-ownership protection there, reopening the arbitrary-code-execution class of bug that `safe.directory` was introduced to close (config/hooks execution). This is a genuine privilege-widening / trust-scope-confusion outcome triggered purely by opening an attacker-authored repository.

### Likelihood Explanation
Requires only that the victim clone or open a malicious repository in Desktop (no local access, no admin rights, no leaked credentials) and click the single "Trust Repository"/"add an exception" affordance that Desktop itself presents as the expected remediation path for this exact warning — a normal, encouraged user action, not an unnatural step. `.git` redirection files are unremarkable repository content that Desktop already parses without suspicion elsewhere in the codebase, so no existing guard inspects or restricts the redirect target before it is echoed back from Git's stderr and handed to `addSafeDirectory()`.

### Recommendation
Before calling `addSafeDirectory()`, verify that the path Desktop is about to trust is the same path (after resolving `.git` redirection safely) as the directory the user explicitly selected/opened, and reject or specially warn when they diverge (e.g., when the "unsafe" path reported by Git is not equal to, or not an ancestor of, the folder the user chose). Consider resolving and displaying the fully-canonicalized target path prominently and refusing one-click trust when the target lies outside the repository directory tree entirely (e.g., a UNC path or an unrelated absolute path), directing the user to a more explicit, path-echoing confirmation flow instead.

### Proof of Concept
1. Attacker creates a public repository whose working tree contains, at its root, a file named `.git` (not a directory) with content: `gitdir: ../../../../attacker-target` (or a UNC path such as `//attacker-server/share/.git`), chosen so the resolved target exists and is owned by a different user/principal on the victim's system (or is a network path the attacker controls).
2. Victim clones/opens this repository in GitHub Desktop via "Add existing repository" or a normal clone flow.
3. Desktop calls `getRepositoryType(path)` → `git rev-parse ...` in the checked-out folder; Git follows the `.git` redirection, hits ownership mismatch, and fails with `fatal: detected dubious ownership in repository at '<attacker-target>'`.
4. `unsafeMatch[1]` captures `<attacker-target>` verbatim; Desktop's UI shows "The Git repository at `<attacker-target>` appears to be owned by another user... add an exception for this directory."
5. Victim clicks "Trust Repository" (the recommended remediation), triggering `addSafeDirectory(repositoryUnsafePath)`, which runs `git config --global --add safe.directory <attacker-target>` — silently granting global trust to the attacker-chosen path rather than the repository folder the victim actually opened.

```typescript
function resolveGitDirectories(gitPath: string): IGitDirectories {
  // eslint-disable-next-line no-sync
  const gitPathStat = Fs.statSync(gitPath)

  if (gitPathStat.isDirectory()) {
    return { gitDir: gitPath, commonGitDir: gitPath }
  }

  // eslint-disable-next-line no-sync
  const gitFileContents = Fs.readFileSync(gitPath, 'utf8')
  const gitDirMatch = /^gitdir:\s*(.+)\s*$/m.exec(gitFileContents)

  if (gitDirMatch === null) {
    throw new Error(
      `Invalid .git file contents in ${gitPath}: ${gitFileContents}`
    )
  }

  const gitDir = Path.resolve(Path.dirname(gitPath), gitDirMatch[1])
```

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
