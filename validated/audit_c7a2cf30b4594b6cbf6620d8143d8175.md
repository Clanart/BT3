## Analysis

The bug-class hint (silent 0-price from an unchecked oracle read) has a direct analog in Zest's off-chain-facing data/health-reporting contract, not in the core market accounting path.

**Core path is safe:** In `mainnet/contracts/market/v0-4-market.clar`, `resolve-pyth` (lines 312-320) propagates any Pyth call failure via `unwrap!`/`try!` in `call-pyth` (`ERR-ORACLE-PYTH`), and `price-resolve` (lines 373-395) additionally enforces `oracle-price-legal` (`> p u0`) and staleness/confidence gating before any price is used for borrow/liquidate/withdraw logic. ### Title
Unchecked Pyth oracle failure silently defaults to a 0 price in the health/liquidation-reporting utility contract - (File: `mainnet/contracts/utility/v0-1-data.clar`)

### Summary
`get-pyth-price` in `v0-1-data.clar` catches any failure from `pyth-storage-v4.get-price` (e.g. `ERR_PRICE_FEED_NOT_FOUND` or a stale/never-published feed) and returns `none`, which `get-asset-price` immediately converts to `u0` via `default-to u0`. This zero price is used, unguarded, in `sum-debt-usd` and `sum-collateral-usd` to compute `total-debt-usd`, `total-collateral-usd`, `current-ltv`, `health-factor`, and `is-liquidatable` inside the public `get-user-position` function — the exact same "silently return 0" pattern flagged for Chainlink's `latestAnswer` in the external report, just for Pyth reads in a non-core contract.

### Finding Description
Unlike the production accounting path in `v0-4-market.clar` (`resolve-pyth`/`price-resolve`), which uses `unwrap!`/`try!` to propagate oracle errors and additionally asserts `oracle-price-legal` (price `> 0`) plus confidence/staleness checks before using a price, `v0-1-data.clar`'s parallel price-resolution helper has none of these guards. If the debt asset's feed is temporarily missing/errors, `get-pyth-price` returns `none`, `get-asset-price` defaults it to `u0`, and `sum-debt-usd` contributes `0` to `total-debt-usd` for that asset. The resulting `health-factor` is computed as if the account has less (or no) debt, and `is-liquidatable` is computed as `false` even though the account may actually be deeply underwater. [3](#0-2) [7](#0-6) [8](#0-7) 

Direction of error and who profits: when a debt-asset price feed errors, `debt-usd` is understated, so `health-factor` is overstated and `is-liquidatable` flips from `true` to `false`. Since `get-user-position` is the canonical read function keepers/liquidators/front-ends consume to decide which accounts to liquidate, this masks a genuinely liquidatable, underwater position — the borrower benefits (avoids liquidation) while the protocol/depositors are exposed to growing uncollateralized bad debt that goes undetected until the feed recovers (by which time collateral value may have fallen further, worsening the shortfall).

### Impact Explanation
This lands on temporary/permanent freezing of funds via undetected bad-debt accumulation: liquidators relying on `is-liquidatable`/`health-factor` from this contract will not act on a genuinely unhealthy position during the outage window, allowing the position's debt to continue growing (or collateral to keep falling) unchecked, increasing the protocol's insolvency risk and the eventual shortfall socialized across lenders.

### Likelihood Explanation
Low-to-medium: it requires a transient Pyth feed failure (feed not yet written, or any error path from `pyth-storage-v4.get-price`) at the moment a keeper/front-end queries this data contract — plausible during oracle downtime, network congestion, or before initial feed seeding for the specific identifier, mirroring the "malfunctioning price feed" precondition in the original Chainlink report.

### Recommendation
Do not silently default to `u0` on an oracle read failure in `v0-1-data.clar`. Propagate the error (or mark the affected data explicitly, e.g. a `price-unavailable: true` flag) so `get-user-position` cannot report a false "healthy"/non-liquidatable verdict, and align the staleness/confidence handling with the guarded logic already present in `v0-4-market.clar`.

### Proof of Concept
1. The Pyth feed for a borrowed asset (e.g. `PYTH-BTC`) stops receiving updates or the identifier is momentarily absent from `pyth-storage-v4`'s `prices` map, so `contract-call? ... get-price feed-id` returns `(err ERR_PRICE_FEED_NOT_FOUND)`.
2. `get-pyth-price` matches the error branch and returns `none`.
3. `get-asset-price` (line 544, sBTC branch) evaluates `(default-to u0 (get-pyth-price PYTH-BTC))` → `u0`.
4. `sum-debt-usd` computes `(/ (* actual u0) (pow u10 decimals))` = `0` for that debt entry, understating `total-debt-usd`.
5. `get-user-position` computes `health-factor` using the understated `debt-usd`, and sets `is-liquidatable: (>= current-ltv ltv-liq-partial)` to `false` even though the true (unmasked) LTV would exceed `ltv-liq-partial`.
6. A keeper/liquidator polling `get-user-position` skips this account; the position accrues further interest/losses unliquidated until the feed error resolves.
