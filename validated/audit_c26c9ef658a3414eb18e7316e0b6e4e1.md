### Title
`ThresholdKeys::read` accepts fully attacker-chosen key material (interpolation coefficients, secret share, and verification shares) with no consistency check, enabling substitution of the multisig group key - (File: crypto/dkg/src/lib.rs)

### Summary
The Yii2 bug class is "deserialization/`__set` constructs object state from untrusted input without validating that the supplied values are legitimate." The Serai analog is `ThresholdKeys::<C>::read` (crypto/dkg/src/lib.rs:574-632), which reconstructs a threshold keypair entirely from a byte stream — threshold params, an `Interpolation` variant (including a list of `Constant` coefficients), a `secret_share`, and `n` verification shares — and passes it to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391). `ThresholdKeys::new` validates only *shape* (share count, participant bounds, `t == n` for `Constant`) and then **computes `group_key` from the supplied verification shares** without checking that `secret_share` is consistent with `verification_shares[i]`, without rejecting identity shares (`<C as Ciphersuite>::read_G` is used at line 622 rather than `Curve::read_G`, which is the only reader that rejects identity — crypto/frost/src/curve/mod.rs:125-131), and without binding the blob to any expected key. The caller receives a `ThresholdKeys` whose effective `group_key()` is whatever public key the byte supplier chose.

### Finding Description
The `read` function parses:

1. `t`, `n`, `i` (crypto/dkg/src/lib.rs:591-602)
2. An interpolation tag; `0` reads `n` arbitrary scalars as `Interpolation::Constant` (604-616)
3. An arbitrary `secret_share` scalar (618)
4. `n` arbitrary group elements as `verification_shares` (620-623)

`ThresholdKeys::new` then derives `group_key = Σ verification_shares[i] * interpolation_factor(i, 1..=t)` (crypto/dkg/src/lib.rs:376-378). Nothing verifies:
- `generator * secret_share == verification_shares[i]` (the deserialized secret is never related to the deserialized verification shares),
- that any verification share or the resulting `group_key` is non-identity,
- that the deserialized `Constant` coefficients correspond to a legitimate key-generation output (any `n` scalars are accepted for `t == n`).

Like the Yii2 `__set` flaw, the deserializer trusts structurally well-formed but semantically arbitrary values: the byte supplier fully determines the resulting object's security-relevant state, including the group key under which the node will later verify external signatures/outputs and the secret share under which it will produce FROST signature shares (`AlgorithmSignMachine` consumes `ThresholdKeys` via `params.keys`, crypto/frost/src/sign.rs:246-281).

### Impact Explanation
Any component that loads `ThresholdKeys` from an input an attacker can influence (recovery import, misdirected message, replayed/alternate key blob) ends up with an attacker-defined group key and an attacker-defined secret share. Two concrete consequences follow:

- **Funds reported received that are not spendable by the group**: downstream logic that derives deposit addresses or verifies received outputs against `keys.group_key()` will use the substituted key. If the attacker chose `verification_shares` such that the resulting `group_key` is a key they alone control, outputs "received" under it belong to the attacker, not the threshold group — the group cannot spend them even though the node's state reports a valid group key.
- **Inconsistent signing state**: the accepted `secret_share` is unrelated to `verification_shares[i]`, so any signature share produced is garbage relative to the claimed key — undetectable at load time because no consistency check is ever performed (the same gap allows loading a `secret_share` of `0` or an identity-committed share set).

This maps precisely to the report's shape: unchecked deserialization → object instantiated with attacker-specified configuration → security decisions (here: which public key represents the multisig, and which secret represents our share) made on forged state.

### Likelihood Explanation
Reachability depends on an integrator feeding attacker-influenced bytes to `ThresholdKeys::read`, which the scan rules enumerate as an in-scope untrusted-byte sink. The bug requires no cryptographic break — the deserializer is behaving exactly as written; the missing validation is the vulnerability. The attacker needs only structural knowledge of the serialization format (visible in tests at crypto/frost/src/tests/vectors.rs:117-131), making crafted blobs trivial to produce.

### Recommendation
In `ThresholdKeys::new` (or in `read` before calling it):

1. Verify `C::generator() * secret_share == verification_shares[&params.i()]` to bind the secret share to the committed verification shares.
2. Reject identity points for every verification share (use the identity-rejecting reader semantics from `Curve::read_G`) and reject an identity/zero `group_key`.
3. Consider authenticating the serialized blob (e.g., carrying the expected `group_key` or a MAC) so deserialization alone cannot substitute key material.

### Proof of Concept
```rust
// Attacker constructs a ThresholdKeys blob for their own key:
let attacker_secret = C::F::random(rng);              // scalar only attacker knows
let attacker_pub = C::generator() * attacker_secret;  // attacker-controlled group key

let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(1u16.to_le_bytes()); // t = 1
blob.extend(1u16.to_le_bytes()); // n = 1
blob.extend(1u16.to_le_bytes()); // i = 1
blob.push(1);                    // Interpolation::Lagrange
blob.extend(C::F::random(rng).to_repr().as_ref()); // arbitrary "secret_share", never checked
blob.extend(attacker_pub.to_bytes().as_ref());     // sole verification share = attacker's key

// Victim deserializes; no error is raised.
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice().as_ref()).unwrap();

// group_key() is the attacker's solo public key. Any funds/outputs associated with
// keys.group_key() are controlled by the attacker, not the threshold group,
// and the bogus secret_share was never validated against verification_shares[1].
assert_eq!(keys.group_key(), attacker_pub);
```

Note: I was unable to fully confirm whether `Ciphersuite::read_G` in `crypto/ciphersuite` rejects identity points for all in-scope curves; the finding does not depend on that detail, since the core defect is the missing secret-share/verification-share consistency check and the unauthenticated substitution of the group key.
