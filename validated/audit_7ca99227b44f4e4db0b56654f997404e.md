## Title
Unvalidated `clone_url` from PR head-repository API data is passed directly to `git remote add`, enabling malicious git transport (e.g. `ext::`) execution when checking out a fork PR - (File: `app/src/lib/stores/app-store.ts`)

## Summary
`AppStore._findPullRequestBranch` takes `headCloneUrl` — a string that ultimately originates from `pullRequest.head.repo.clone_url`, a field returned by a GitHub API response for the PR's head repository — and passes it, completely unvalidated, into `addRemote()`, which shells out to `git remote add <name> <url>` [1](#0-0) . That remote is then fetched via `_fetchRemote` [2](#0-1) . Nowhere in this path is the URL checked to be a well-formed `https://`/`ssh://`/`git@` GitHub remote (the kind of check that exists for a different purpose in `parseRemote`/`urlMatchesRemote`, which is only used for string-matching, not gatekeeping) [3](#0-2) . Nor is any `protocol.*.allow`/`GIT_ALLOW_PROTOCOL` restriction applied anywhere in the codebase (confirmed absent by search).

This mirrors the reported bug class exactly: a value that should be validated against a "registered"/expected form (`s.vaults[...]` in the Solidity report; a canonical `https`/`ssh` GitHub clone URL here) is instead trusted blindly and fed straight into a privileged operation (`commitToLien` in the report; `git remote add` + `git fetch`, which can invoke arbitrary git "remote helper" transports, here).

## Finding Description
- `_checkoutPullRequest`/`_findPullRequestBranch` receive `headCloneUrl` from the caller `openPullRequestFromUrl`, which reads it straight from the API object: `pullRequest.head.repo.clone_url` [4](#0-3) .
- `addRemote()` performs no validation of the URL's scheme or shape before invoking git: `git(['remote', 'add', name, url], repository.path, 'addRemote')` [5](#0-4) .
- Git supports "remote helper" transports invoked via a URL prefix, most notably `ext::<command>`, which executes an arbitrary shell command as part of the fetch/push transport. Git's built-in protection for this (disallowing `ext`/`file`-style transports unless explicitly permitted) is normally enforced through `protocol.<name>.allow` / `GIT_ALLOW_PROTOCOL`, which this codebase never sets — confirmed by an exhaustive search for `GIT_ALLOW_PROTOCOL`/`protocol.allow`/`ext::`, all of which returned zero matches in `envForRemoteOperation` or anywhere else in `app/src/lib/git/*` [6](#0-5) .
- Once the remote is added, `_fetchRemote(repository, remote, FetchType.UserInitiatedTask)` shells out via `fetch()` in `app/src/lib/git/fetch.ts`, which simply runs `git fetch <remote-name>` with only proxy/auth environment additions — nothing scheme-restricting [7](#0-6) .
- The comparable `urlMatchesRemote`/`parseRemote` machinery that exists elsewhere in the codebase (used for detecting whether a URL is a real GitHub owner/repo URL) is never invoked as a gate before `addRemote` is called in `_findPullRequestBranch`; it's only used afterward for informational matching purposes [8](#0-7) .

## Impact Explanation
If the attacker can influence the `clone_url` field returned for a pull request's head repository (the "attacker controls…a GitHub API object" scenario explicitly listed as valid impact — e.g. a compromised/malicious GitHub Enterprise Server instance, or a MITM'd/spoofed API response that the victim's Desktop instance is pointed at), Desktop will:
1. Silently call `git remote add github-desktop-<owner> "ext::sh -c '<attacker command>'"` with no scheme validation.
2. Silently call `git fetch github-desktop-<owner>`, which invokes the `ext` remote helper and executes the attacker's shell command with the current user's privileges — full remote code execution outside of any repo/file-write sandbox, satisfying the "code execution … outside the repo" impact bucket.

This is triggered automatically as part of the normal "checkout a pull request from a fork" / "Open PR from browser" flow with no separate confirmation of the remote URL contents, i.e., no "unprompted unnatural user steps" are required beyond the intended use of the feature (clicking to check out or open a PR).

## Likelihood Explanation
Requires the attacker to control the head-repo `clone_url` value the app receives for a PR, which is realistic in the accepted threat model for a malicious/compromised GHES server or a spoofed API endpoint (an explicitly valid scenario per the task's impact criteria), but not exploitable against the genuine github.com API (which always returns accurate, GitHub-hosted clone URLs). Given that scope, the likelihood is high once that precondition is met, since there is zero validation code standing between the API field and the shell-invoking `git remote add`/`git fetch` calls.

## Recommendation
Before calling `addRemote`/`setRemoteURL` with any URL sourced from API data (`clone_url`, `ssh_url`, `htmlURL`, etc.), validate it against `parseRemote()` (already present) and reject anything that doesn't match a well-formed `https://`/`git@`/`ssh://` GitHub remote shape. Additionally, explicitly restrict allowed git transports for all remote operations by setting `protocol.allow=never` combined with `protocol.{http,https,ssh,git}.allow=always` (or the equivalent `GIT_ALLOW_PROTOCOL=http:https:ssh:git`) in `envForRemoteOperation`, so that `ext`, `file`, and other dangerous transports can never be reached regardless of what a compromised/malicious API endpoint supplies.

## Proof of Concept
1. Point Desktop at (or have it MITM'd to talk to) a malicious/compromised GitHub Enterprise-style API endpoint.
2. Have that endpoint return a pull request object where `head.repo.clone_url` is `ext::sh -c "touch$IFS/tmp/pwned"` (or a Windows equivalent command).
3. In Desktop, open that PR from a URL/deep-link or the "Open PR from Desktop" browser action, or check it out from the Pull Requests list — this drives `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`.
4. `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` with the malicious `ext::` URL and no validation, then calls `_fetchRemote`, which executes `git fetch github-desktop-<owner>` and triggers the `ext` transport, running the attacker's command on the victim's machine.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function fetch(
  repository: Repository,
  remote: IRemote,
  progressCallback?: (progress: IFetchProgress) => void,
  isBackgroundTask = false
): Promise<void> {
  let opts: IGitStringExecutionOptions = {
    successExitCodes: new Set([0]),
    env: await envForRemoteOperation(remote.url),
  }

  if (progressCallback) {
    const title = `Fetching ${remote.name}`
    const kind = 'fetch'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true, isBackgroundTask },
      new FetchProgressParser(),
      progress => {
        // In addition to progress output from the remote end and from
        // git itself, the stderr output from pull contains information
        // about ref updates. We don't need to bring those into the progress
        // stream so we'll just punt on anything we don't know about for now.
        if (progress.kind === 'context') {
          if (!progress.text.startsWith('remote: Counting objects')) {
            return
          }
        }

        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({
          kind,
          title,
          description,
          value,
          remote: remote.name,
        })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0, remote: remote.name })
  }

  const args = await getFetchArgs(remote.name, progressCallback)

  await git(args, repository.path, 'fetch', opts)

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
