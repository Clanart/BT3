## Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is trapped in the contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `payable` calls and swap the supplied `msg.value` for `feeToken()` via `swapETHForExactTokens`, but none of them check the actual amount spent by the swap or refund the difference to the original caller. The overpaid native token becomes permanently stuck in the `EvmHost` contract, matching the "[M-04] Excess ETH is not refunded" bug class from the external report.

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The identical pattern is used in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`swapETHForExactTokens` on Uniswap V2 only spends up to `post.fee`/`get.fee`/`amount` worth of ETH; if `msg.value` exceeds what is needed, the standard router implementation refunds the unused ETH to `msg.sender` of the swap call — which here is `EvmHost` itself, not the end user who called `dispatch`/`fundRequest`. None of these three functions capture the `amounts` return value of the swap or forward any leftover balance back to `_msgSender()`. The codebase itself demonstrates the correct pattern elsewhere: `IntentGatewayV2.placeOrder` and `ExtrinsicIntents` capture `amounts[0]` from `swapETHForExactTokens` and explicitly refund `msgValue - amounts[0]` to `msg.sender`: [4](#0-3) [5](#0-4) 

`EvmHost.dispatch`/`fundRequest` lack this same refund logic entirely, so any ETH sent above the exact swap requirement is silently absorbed by the host contract with no mechanism found in this file to return it to the sender.

### Impact Explanation
This is a direct, unprivileged loss-of-funds bug: any user calling `dispatch()` or `fundRequest()` on `EvmHost` with `msg.value` greater than the exact ETH needed to acquire the relayer/GET fee in `feeToken` permanently loses the difference. Given that client-side fee estimation (documented in the SDK/dev docs) typically pads `msg.value` for slippage safety, this scenario is expected to occur routinely in normal operation, not just as an edge case, resulting in continuous fund loss trapped in the core `IsmpHost` contract.

### Likelihood Explanation
Likelihood is high: `dispatch()` and `fundRequest()` are the primary, unauthenticated, publicly documented entry points for dispatching POST/GET requests and topping up relayer fees using native tokens (per the docs referencing `IDispatcher(_host).dispatch{value: msg.value}(...)`). Any caller who slightly overestimates the ETH required (a normal and recommended practice to avoid reverts from price movement) will trigger the loss on every call.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents.fillOrder`.

### Proof of Concept
1. Caller estimates the fee-token cost of a `DispatchPost` with `post.fee = X` but pads the transaction with `msg.value = 2 * expectedEthCost` to protect against price slippage.
2. Calls `EvmHost.dispatch{value: msg.value}(post)`.
3. Inside `dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes, spending only `actualEthCost < msg.value` and refunding `msg.value - actualEthCost` to `EvmHost` (the caller of the swap).
4. `dispatch` never reads the swap's returned `amounts[0]` nor forwards any ETH back to the original `_msgSender()`.
5. The overpaid ETH remains in `EvmHost`'s balance indefinitely, with no refund path exposed to the depositor in this contract.
