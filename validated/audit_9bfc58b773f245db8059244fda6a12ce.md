### Title
Hookify frontmatter value parser fails to strip inline comments/case, silently downgrading `action: block` rules to warn-only - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` is a hand-rolled YAML-subset parser that only strips surrounding quotes and normalizes literal `true`/`false` for scalar values; it does not strip trailing inline comments (`# ...`) or normalize case for other string values. Because `rule_engine.py`'s blocking check is a strict `rule.action == 'block'` string comparison, any frontmatter line like `action: block  # <comment>` or `action: Block` parses to a value that is no longer the literal string `'block'`, causing an intended blocking rule to be silently reclassified as a warning, allowing the dangerous tool call it was meant to stop.

### Finding Description
`load_rule_file` calls `extract_frontmatter(content)` to split a `.claude/hookify.*.local.md` file into a frontmatter dict and message body [1](#0-0) . Inside `extract_frontmatter`, top-level scalar values are parsed with:
```
value = value.strip()
...
value = value.strip('"').strip("'")
if value.lower() == 'true':
    value = True
elif value.lower() == 'false':
    value = False
frontmatter[key] = value
``` [2](#0-1) 
No inline-comment stripping (`#`) and no case normalization is performed on non-boolean scalar strings. `Rule.from_dict` then stores this raw value directly: `action=frontmatter.get('action', 'warn')` [3](#0-2) .

`RuleEngine.evaluate_rules` decides whether a matched rule blocks or only warns using a strict string equality check:
```
if rule.action == 'block':
    blocking_rules.append(rule)
else:
    warning_rules.append(rule)
``` [4](#0-3) 

If a rule file contains `action: block  # prevent accidental deletion` (a natural, human-readable style that visually communicates a blocking rule and comments explaining why), the parsed value becomes the literal string `"block  # prevent accidental deletion"`, which fails the `== 'block'` check and the rule is routed into `warning_rules` instead of `blocking_rules`. The same silent downgrade occurs with a differently-cased value such as `action: Block`. In the `warning_rules` path, `evaluate_rules` returns only a `systemMessage` and allows the tool call to proceed [5](#0-4) , whereas the `blocking_rules` path issues `permissionDecision: deny` for `PreToolUse`/`PostToolUse` and `decision: block` for `Stop` [6](#0-5) .

This is reachable on every dangerous tool invocation because `pretooluse.py`, `posttooluse.py`, and `stop.py` all call `load_rules()` → `load_rule_file()` → `extract_frontmatter()` on every Bash/Edit/Write/MultiEdit/Stop event [7](#0-6) [8](#0-7) . Rule files are attacker-influenceable repository content: they can be introduced via a pull request, or generated by the `/hookify` slash command itself, whose documentation encourages exactly this authoring style (`action: {warn|block}` inline with plain values, with message bodies containing free-form annotations) [9](#0-8) . No allowlist, schema validation, or canonicalization exists anywhere in `config_loader.py` to catch this mismatch between file content and parsed `Rule.action` before enforcement.

### Impact Explanation
A block rule intended to stop dangerous operations (e.g., `rm -rf`, writes to `.env`/credential files, or unsafe `Stop` conditions) is silently converted into a non-blocking warning due to a single trailing comment or capitalization difference that is invisible or looks purely cosmetic to a human reviewer of the `.local.md` file. This breaks the stated invariant that "rule semantics must not change because of formatting ambiguity" and results in unauthorized execution of the exact dangerous command/file operation the user configured hookify to block — i.e., unauthorized file read/write or command execution outside the intended safety boundary, matching the "Unauthorized file read or write outside the user-approved workspace or target scope" impact class.

### Likelihood Explanation
The precondition is only that an attacker (or an innocent contributor influenced by attacker-supplied instructions/PR content) can add or modify a `.claude/hookify.*.local.md` file in the repository — no privileged access, secrets, or social engineering of Claude's execution is required beyond normal repo-content contribution, matching the "repository-controlled content" threat model. The bug is deterministic and trivially reproducible: any rule author who adds an inline comment after `action: block` (a very natural documentation habit) or capitalizes the value will unknowingly disable enforcement, and an attacker aware of this parser quirk can deliberately craft such files to look like hardened block rules while functioning only as warnings.

### Recommendation
Replace the hand-rolled scalar value parser with comment-stripping and case-insensitive/canonicalized handling before assignment (e.g., strip everything from an unquoted `#` to end of line, then `value.strip()`), and normalize `action` to `{'warn','block'}` with an explicit validation/`ValueError` on unrecognized values instead of defaulting silently. Additionally, change `rule_engine.py`'s check to compare against a canonicalized `rule.action.strip().lower()` and fail closed (treat unrecognized/malformed `action` values as `block`, or reject the rule file entirely with a loud warning) rather than silently defaulting to warn-only behavior.

### Proof of Concept
Unit test to add to a test suite exercising `config_loader.extract_frontmatter` and `rule_engine.RuleEngine`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule
from hookify.core.rule_engine import RuleEngine

content = """---
name: block-rm-rf
enabled: true
event: bash
pattern: rm\\s+-rf
action: block  # prevent accidental deletion
---

Blocked dangerous rm -rf command.
"""

fm, msg = extract_frontmatter(content)
rule = Rule.from_dict(fm, msg)

# Bug: action is not the literal string 'block'
assert rule.action != 'block', "expected downgrade due to inline comment"

engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /important/data"}
}
result = engine.evaluate_rules([rule], input_data)

# Expected (secure) behavior: operation should be denied
# Actual (vulnerable) behavior: only a systemMessage warning is returned, no deny
assert "hookSpecificOutput" not in result or result.get("hookSpecificOutput", {}).get("permissionDecision") != "deny"
```
This demonstrates that a rule file whose visible content unambiguously declares `action: block` is parsed and enforced as a non-blocking warning, allowing the dangerous `rm -rf` Bash command to execute unhindered.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
