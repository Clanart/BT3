### Title
mWOMSVBaseRewarder._calExpireForfeit never applies cooldown forfeiture, allowing full reward claim while in cooldown - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally instead of scaling it by `mWOMSV.getRewardablePercentWAD(_account)` (as the analogous `vlMGPBaseRewarder._calExpireForfeit` does with `vlMGP.getRewardablePercentWAD`). As a result, `forfeitAmount` is always `0`, and any user in cooldown (i.e., `getRewardablePercentWAD < 1e18`) still receives 100% of accrued bonus rewards through `MasterMagpie.multiclaim()` → `getReward()` → `_sendReward()`.

### Finding Description
`_sendReward` computes `forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account])` and sends `userRewards - forfeitAmount` to the receiver, queuing only `forfeitAmount` back as forfeited rewards [1](#0-0) . The intended design (mirrored in `vlMGPBaseRewarder._calExpireForfeit`) is to compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` where `rewardablePercentWAD` comes from the locker's `getRewardablePercentWAD(_account)`, reducing payout while a user is in cooldown [2](#0-1) .

In `mWOMSVBaseRewarder`, this logic is broken: `rewardableAmount` is just set equal to `_amount`, `mWOMSV.getRewardablePercentWAD` is never called, and the subsequent `if (rewardableAmount > _amount) revert` check is dead code (it can never be true since `rewardableAmount == _amount` by construction) [3](#0-2) . Consequently `forfeitAmount` is always `0` regardless of the user's cooldown state.

Reachable attacker path: an unprivileged user calls `SmartWomConvert.convertFor(..., mode=2)`, which calls `mWomSV.lockFor(obtainedmWomAmount, _for)` [4](#0-3) , crediting mWomSV balance in `MasterMagpie`. The user then calls `mWomSV.startUnlock(_amountToCoolDown)`, moving locked balance into a cooldown slot, which reduces `getRewardablePercentWAD` below `1e18` while in cooldown [5](#0-4) , [6](#0-5) . Any bonus reward accrued on the `mWOMSVBaseRewarder` for this staking token and later claimed via `MasterMagpie.multiclaim()` → `getReward()` will be paid in full, with `forfeitAmount == 0`, even though the user is mid-cooldown and should have part of it forfeited to remaining stakers.

### Impact Explanation
This is theft/permanent redirection of unclaimed yield: the forfeiture mechanism exists specifically to redistribute a cooling-down/exiting user's proportional reward share back into the pool for continuing stakers (as implemented correctly in the vlMGP counterpart). Because forfeiture never triggers for mWomSV-based rewards, users in cooldown (partially exiting the system) keep 100% of bonus token rewards that should have been partially forfeited, diluting/stealing yield that would otherwise accrue to loyal stakers still fully locked.

### Likelihood Explanation
No special privileges are required — any address can call `SmartWomConvert.convertFor` (or `lockFor` directly) and `startUnlock`, both of which are permissionless external functions, and then claim rewards through `MasterMagpie.multiclaim()`. The exploit is deterministic and repeatable for every claim cycle as long as any bonus reward token is queued to `mWOMSVBaseRewarder`.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to mirror `vlMGPBaseRewarder._calExpireForfeit`: fetch `mWOMSV.getRewardablePercentWAD(_account)` and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder`, `SmartWomConvert` with a bonus reward token.
2. Attacker calls `SmartWomConvert.convertFor(amountIn, ratio, minRec, attacker, mode=2)` to lock `mWom` into `mWomSV`, crediting stake in `MasterMagpie`.
3. Queue bonus rewards into `mWOMSVBaseRewarder` via `queueNewRewards`, and advance block/reward accrual so attacker has `earned(attacker, rewardToken) > 0`.
4. Attacker calls `mWomSV.startUnlock(fullAmount)` — assert `mWomSV.getRewardablePercentWAD(attacker) < 1e18`.
5. Attacker calls `MasterMagpie.multiclaim()` (routes to `mWOMSVBaseRewarder.getReward`).
6. Assert attacker received the full `earned` amount and `mWOMSVBaseRewarder.calExpireForfeit(attacker, rewardToken)` (or the forfeit event) shows `forfeitAmount == 0`, proving no proportional forfeiture despite being in cooldown.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
