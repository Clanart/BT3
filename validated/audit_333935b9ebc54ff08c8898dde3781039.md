## Analysis

The Ditto report's core pattern: a critical, security-relevant decision path trusts a **coarse, cached signal** instead of checking the **specific, authoritative data point** it's actually deciding about. The local Hyperbridge analog is in `EvmHost.sol`'s state-machine-height bookkeeping, which is used by `HandlerV2` to gate whether a newly-verified consensus intermediate state may be persisted as a `StateMachineCommitment`.

`HandlerV2.handleConsensus` only accepts a new intermediate state if it is *numerically greater* than the single cached pointer `_latestStateMachineHeight`, rather than checking whether **that specific height already has a stored commitment** — which is what the Substrate/pallet-ismp consensus handler does: [1](#0-0) 

versus the pallet-side per-height dedup: [2](#0-1) 

The `_latestStateMachineHeight` cache is precisely what breaks: when a fisherman successfully vetoes the current latest commitment via `deleteStateMachineCommitment`, EvmHost resets the pointer unconditionally to `1`, unlike the pallet, which restores the true `PreviousStateMachineHeight`: [3](#0-2) [4](#0-3) 

### Title
Post-veto reset of `_latestStateMachineHeight` to `1` on EvmHost allows re-acceptance/overwrite of already-committed state heights - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` (called from `deleteStateMachineCommitment`, the fisherman veto path) resets `_latestStateMachineHeight[stateMachineId]` to the hardcoded value `1` whenever the vetoed height equals the current latest, rather than restoring the actual previous verified height. The pallet-ismp equivalent (`delete_state_commitment`) correctly restores `PreviousStateMachineHeight`. `HandlerV2.handleConsensus` relies solely on `intermediate.height > latestStateMachineHeight` — a single cached pointer — to decide whether a newly-verified intermediate state may be persisted, instead of checking per-height existence the way the Substrate consensus handler does (`host.state_machine_commitment(state_height).is_ok()`).

### Finding Description
`storeStateMachineCommitment` unconditionally overwrites `_stateCommitmentsUpdateTime` and `_latestStateMachineHeight` for whatever height is passed to it: [5](#0-4) 

The only gate preventing arbitrary/duplicate heights from reaching this function is `HandlerV2`'s `intermediate.height > latestHeight` check. That check is sound only as long as `_latestStateMachineHeight` monotonically reflects the true highest verified height. The veto path breaks this invariant: instead of rolling the pointer back to the actual prior valid height (as the pallet does via `PreviousStateMachineHeight`), it collapses to `1` — discarding the boundary that previously blocked re-acceptance of any already-committed height. After a veto of the current latest height, any subsequent consensus proof whose consensus-client-verified intermediate states include an *older, already-committed* height will pass the `intermediate.height > latestHeight` check again (since `latestHeight == 1`), causing that height's `StateCommitment` and `_stateCommitmentsUpdateTime` to be silently re-written, and `_latestStateMachineHeight` to regress downward to that older height — re-arming/derailing the challenge-period bookkeeping that `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` depend on (`stateMachineCommitmentUpdateTime`), and destroying the monotonic-height invariant that the "duplicate protection" logic assumes exists.

### Impact Explanation
This corrupts the authoritative `_latestStateMachineHeight` cache used to gate all future consensus updates for that state machine on this host. It removes the only overwrite/duplicate-acceptance protection EvmHost has (EVM has no per-height existence check, unlike the pallet), letting an already-settled commitment's timestamp and content be silently re-written after any veto event — undermining the state-commitment freshness/monotonicity guarantee that request, response, and timeout processing rely on for challenge-period enforcement.

### Likelihood Explanation
Requires a prior successful fraud-proof veto of the current latest height (an actual byzantine event, which the protocol is explicitly designed to handle safely) followed by a routine, permissionless consensus submission. No relayer/prover collusion or privileged access is needed to trigger the corrupted reset itself — any legitimate fisherman veto activates it, and any subsequent, otherwise-honest consensus proof can then land on an unintended height because of the incorrect pointer.

### Recommendation
Track and restore the true previous verified height on veto (mirroring pallet-ismp's `PreviousStateMachineHeight`) instead of hardcoding `1`. Additionally, make `HandlerV2`'s acceptance check per-height (e.g., reject if `_stateCommitments[stateMachineId][height]` is already non-zero) rather than relying solely on the single `_latestStateMachineHeight` cache, matching the Substrate consensus handler's explicit duplicate-height check.

### Proof of Concept
1. Consensus client verifies intermediate states for heights `[..., 150, 200]` for state machine `X`; `_latestStateMachineHeight[X] = 200`.
2. A fisherman submits a valid fraud proof and calls `deleteStateMachineCommitment` on height `200` (the current latest) via the handler.
3. `deleteStateMachineCommitmentInternal` executes `_latestStateMachineHeight[X] = 1` (see `evm/src/core/EvmHost.sol:719-721`), losing the fact that `150` was the true prior valid height.
4. Any subsequent legitimate `handleConsensus` call whose consensus client returns an intermediate state at height `150` (already committed and possibly already used to process/settle requests) now satisfies `150 > 1` and is passed to `storeStateMachineCommitment`, rewriting `_stateCommitments[X][150]` and `_stateCommitmentsUpdateTime[X][150] = block.timestamp`, and setting `_latestStateMachineHeight[X] = 150` — a regression of the tracked latest height and a reset of that height's challenge-period clock, contrary to the monotonic-height invariant the pallet-side implementation preserves.

    /**
     * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.
     */
    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
