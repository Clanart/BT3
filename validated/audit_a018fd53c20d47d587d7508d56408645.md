## Analog Found

### Title
Unsanitized GitHub profile display name is embedded into `Co-Authored-By` git trailers, allowing forged co-author/attribution injection in commits - (File: `app/src/ui/changes/commit-message.tsx`)

### Summary
The external report describes a class of bug where an untrusted "field name" string is trusted to delimit a structured record (header name / colon / value) without validating that it doesn't itself contain the delimiter or control characters, letting the untrusted value corrupt the boundaries of the parsed structure. The same class of bug exists in GitHub Desktop's co-author trailer construction: the free-text `name` field from a GitHub user's public profile (fully attacker-controlled, since any GitHub account can set it) is interpolated verbatim into a git commit trailer value with no validation that it excludes newlines, colons, or the literal string `Co-Authored-By:`.

### Finding Description
When a user adds a co-author to a commit via the co-author picker, Desktop converts the picked `IMentionableUser`/`UserHit` into an `Author` via `authorFromUserHit`, which copies the GitHub API's free-text `name` field unmodified: [1](#0-0) . That `name` originates directly from `IAPIMentionableUser.name`, a field the report explicitly says is "the name that the user has configured to be shown" — i.e., entirely attacker-controlled: [2](#0-1) .

This `Author.name` is then interpolated directly into the trailer value string with no escaping or character validation: [3](#0-2) .

That trailer is passed through `formatCommitMessage` into `mergeTrailers`, which appends it as a single `--trailer token=value` argv entry to `git interpret-trailers`: [4](#0-3) [5](#0-4) . Nowhere in this chain is `trailer.token` or `trailer.value` checked for embedded newlines, colons, or trailer-like substrings before being embedded into the eventual commit message bytes.

This mirrors the report's root cause exactly: a function (`getCoAuthorTrailers` / `mergeTrailers`) that treats an untrusted string as an opaque "value" that will safely occupy one slot in a structured record, without validating that it can't contain the delimiter/newline that would let it spill into — or fabricate — additional structure. The codebase's own trailer-parsing code even documents an identical missing-validation smell (`isCoAuthoredByTrailer` "Does not validate the token value"): [6](#0-5) , and `parseSingleUnfoldedTrailer` similarly trusts a naive `indexOf` boundary: [7](#0-6) .

### Impact Explanation
An attacker who controls their own (or a compromised) GitHub account can set their public profile "name" to a string containing a newline plus a forged trailer line, e.g. `Evil <e@e.com>\nCo-Authored-By: Someone Else <someone@example.com>`. If a victim who is collaborating with that account (the attacker need only be a mentionable/collaborator or matched via the manual "@username" search, both of which are unprivileged interactions) adds them as a co-author and commits, the resulting commit's raw message body will contain the attacker-fabricated line as literal committed content. This silently corrupts what the user actually commits and later pushes: the local git history (and the public commit once pushed to GitHub) can end up containing forged attribution lines the user never typed or reviewed, since the co-author UI only displays the intended author list, not the raw trailer bytes that get written to the commit object.

### Likelihood Explanation
No special privileges are required — setting a GitHub display name is available to any account, and being added as a co-author only requires being a collaborator/mentionable user or being looked up by exact username via the manual entry path (`attemptUnknownAuthorSearch`) [8](#0-7) . The vulnerable code path (`getCoAuthorTrailers` → `formatCommitMessage` → `mergeTrailers`) is exercised on every commit made with a co-author, which is a common, everyday Desktop feature.

### Recommendation
Validate/sanitize `Author.name` (and `email`) before it is used to build a trailer value: reject or strip characters not allowed in a single trailer line (at minimum `\n`, `\r`, and the trailer separator characters returned by `getTrailerSeparatorCharacters`), and reject values containing the literal pattern `token:`/`token=` for any known trailer keys. This should be enforced both in `authorFromUserHit`/`attemptUnknownAuthorSearch` (where the untrusted GitHub API name is first ingested) and defensively in `mergeTrailers`/`getCoAuthorTrailers` before the value is embedded in the `--trailer` argument.

### Proof of Concept
1. Attacker sets their GitHub account's public "name" field to:
   `Evil <e@e.com>\nCo-Authored-By: Linus Torvalds <torvalds@linux-foundation.org>`
2. Attacker is added as a collaborator (or is otherwise mentionable) on a shared repository, or the victim manually types the attacker's exact username in the co-author box.
3. Victim opens GitHub Desktop, selects the attacker from the co-author autocomplete (`CoAuthorAutocompletionProvider` → `authorFromUserHit`), and commits.
4. `getCoAuthorTrailers()` builds `{ token: 'Co-Authored-By', value: 'Evil <e@e.com>\nCo-Authored-By: Linus Torvalds <torvalds@linux-foundation.org> <e@e.com>' }` and `mergeTrailers` passes it straight through to `git interpret-trailers --trailer ...` with no validation.
5. The resulting commit body contains the attacker-forged line as committed content, without the victim ever seeing or approving that literal text, and it is pushed as part of the victim's normal push flow.

```typescript
export async function formatCommitMessage(
  repository: Repository,
  context: ICommitContext
) {
  const { summary, description, trailers } = context

  // Git always trim whitespace at the end of commit messages
  // so we concatenate the summary with the description, ensuring
  // that they're separated by two newlines. If we don't have a
  // description or if it consists solely of whitespace that'll
  // all get trimmed away and replaced with a single newline (since
  // all commit messages needs to end with a newline for git
  // interpret-trailers to work)
  const message = `${summary}\n\n${description || ''}\n`.replace(/\s+$/, '\n')

  return trailers !== undefined && trailers.length > 0
    ? mergeTrailers(repository, message, trailers)
    : message
}
```

```typescript
export function parseSingleUnfoldedTrailer(
  line: string,
  separators: string
): ITrailer | null {
  for (const separator of separators) {
    const ix = line.indexOf(separator)
    if (ix > 0) {
      return {
        token: line.substring(0, ix).trim(),
        value: line.substring(ix + 1).trim(),
      }
    }
  }

  return null
}
```

```typescript
export async function mergeTrailers(
  repository: Repository,
  commitMessage: string,
  trailers: ReadonlyArray<ITrailer>,
  unfold: boolean = false
) {
  const args = ['interpret-trailers']

  // See https://github.com/git/git/blob/ebf3c04b262aa/Documentation/git-interpret-trailers.txt#L129-L132
  args.push('--no-divider')

  if (unfold) {
    args.push('--unfold')
  }

  for (const trailer of trailers) {
    args.push('--trailer', `${trailer.token}=${trailer.value}`)
  }

  const result = await git(args, repository.path, 'mergeTrailers', {
    stdin: commitMessage,
  })

  return result.stdout
}
```
