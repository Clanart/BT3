Based on the evidence gathered, I found a structurally similar analog to the Morpho bug: **code that reduces a security boundary meant to gate a specific circumstance, without verifying the invariant that justified reintroducing the unsafe behavior still holds** — very close to "assume supply implies collateral" pattern (act performed → protection assumed intact, unverified).

### Title
Desktop re-enables `protocol.file.allow=always` for submodule updates during checkout without validating the submodule target - (File: `app/src/lib/git/submodule.ts`)

### Summary
Git deliberately restricted `protocol.file.allow` to `user` (rather than `always`) as a hardening measure, because an attacker-controlled `.gitmodules` entry pointing to a `file://` URL can be used to make a victim's Git client clone/read arbitrary local paths on their filesystem when the submodule is initialized. `updateSubmodulesAfterOperation` in Desktop deliberately re-widens this restriction back to `protocol.file.allow=always` whenever it is invoked with `allowFileProtocol=true`, and this flag is threaded through `checkoutBranch`/`checkoutCommit` as a plain boolean with no re-validation of the actual `.gitmodules` content of the commit/branch being checked out.

### Finding Description
`updateSubmodulesAfterOperation` builds the `git submodule update --init --recursive` invocation and conditionally prepends `-c protocol.file.allow=always` based on a caller-supplied boolean: [1](#0-0) 

This flag is passed straight through from `checkoutBranch` and `checkoutCommit`, which default it to `false` but allow callers to override it to `true`: [2](#0-1) [3](#0-2) 

The invariant this design assumes is: *"if `allowFileProtocol=true` is passed, it is safe to override Git's default local-file-read hardening for the submodules declared in the commit being checked out."* But the branch/commit content being checked out — including `.gitmodules` — can be entirely attacker-controlled (e.g., a branch or commit fetched from a hostile remote, or a checked-out PR ref). Unlike the Morpho case where the code assumed "supply succeeded → collateral is set" without checking Aave's actual isolation-mode state, here the code assumes "flag is true → this checkout is trustworthy for file:// submodule resolution" without checking what `.gitmodules` in the target commit actually contains. There is no code path here that inspects the `.gitmodules` submodule URLs for `file://` schemes pointing outside the repo's original clone directory (e.g., `/etc`, `~/.ssh`, other local repos) before re-enabling `protocol.file.allow=always`.

Because `git submodule update --init` with `protocol.file.allow=always` will happily perform a local filesystem "clone" of any `file://` path (subject to normal FS permissions), a submodule URL crafted by an attacker who controls the checked-out ref could cause Desktop to copy the contents of an arbitrary readable local path into the submodule working directory inside the user's repository.

### Impact Explanation
If reachable from checkout of an attacker-influenced branch/commit (e.g., PR checkout flow driven by `openPullRequestFromUrl`/`_checkoutPullRequest`, which ultimately calls the checkout code paths), this allows:
- Reading arbitrary local files/directories the Desktop process has FS access to, by declaring a submodule with `url = file:///path/to/target`, then having the contents copied into the tracked working directory where the user could subsequently view, commit, and push them (exfiltration to a remote the attacker controls).
- Silent corruption of what the user commits, since files from outside the intended repo end up staged/tracked without the user realizing the provenance.

This matches the "Valid Impact" criteria: attacker controls a cloned/fetched repository content (`.gitmodules` in a branch/PR/commit), and the result is file read outside the repo and potential credential/token exfiltration if e.g. SSH keys or config files are pulled in as a "submodule."

### Likelihood Explanation
I was only able to confirm the sink (`updateSubmodulesAfterOperation`) and its default-off, caller-controlled boolean (`allowFileProtocol`) in `checkout.ts`/`submodule.ts`. I was **not able to fully trace all 8 call sites in `app-store.ts`** (and additional call sites in `dispatcher.ts`, `branches-container.tsx`, `stash-and-switch-branch-dialog.tsx`, `compare.tsx`, etc.) within the available tool budget to confirm precisely which of them pass `allowFileProtocol=true` and under what trust condition (e.g., only for the user's own already-cloned local repo, vs. for a freshly fetched PR/branch ref from an untrusted contributor). This is a material gap: if `allowFileProtocol=true` is only ever passed for repositories the user already explicitly owns/trusts and never for content freshly introduced by a PR checkout or clone-from-URL flow, the practical exploitability is much lower (comparable to a normal Git CLI user manually running the equivalent command). Confirming this requires enumerating the call sites, which should be done by an engineer with full codebase access.

### Recommendation
- Before allowing `allowFileProtocol=true` to reach `updateSubmodulesAfterOperation`, validate the `.gitmodules` file of the target commit and reject/flag any submodule `url` entries using `file://` schemes that resolve outside of directories the app already trusts (e.g., other repositories previously added by the user).
- Prefer keeping Git's default `protocol.file.allow=user` behavior and only using `=always` for narrowly-scoped, explicitly user-confirmed scenarios (e.g., re-checking out a submodule the user has already manually vetted), with an explicit UI prompt rather than a silent boolean threaded through internal checkout plumbing.
- Audit all call sites of `checkoutBranch`/`checkoutCommit` that pass `allowFileProtocol=true` to confirm none of them are reachable from attacker-influenced refs (PR checkout, clone-and-open flows, fetched branches from arbitrary remotes).

### Proof of Concept
1. Attacker creates a public repository/branch with a `.gitmodules` entry: `url = file:///Users/victim/.ssh` (or any other locally-readable sensitive path), plus a corresponding gitlink entry.
2. Victim uses Desktop to check out this branch/PR (via a code path that reaches `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which "clones" the local path into the submodule directory inside the victim's repository.
4. The victim's repository working tree now contains a copy of the sensitive local files; if the victim commits and pushes (or Desktop's changes view surfaces the content), the data is exposed/exfiltrated.

*(Exact exploitability depends on confirming — via further code review not completed here due to tool-call limits — that `allowFileProtocol=true` is reachable from an attacker-influenced checkout path rather than only from operations on repositories the user already trusts.)*

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
