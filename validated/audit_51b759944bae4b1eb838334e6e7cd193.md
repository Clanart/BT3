### Title
`associatePubKey` allows re-mapping an EVM address already used as a validator/delegator operator identity, orphaning staking/distribution state and halting the chain - (File: precompiles/addr/addr.go)

### Summary
The `addr` precompile's `associatePubKey`/`associate` methods only guard against re-association on the **Sei-address** side (`p.evmKeeper.GetEVMAddress(ctx, seiAddr)`), but never check whether the **EVM address** side already has a permanent binding that is relied upon elsewhere (e.g. as a validator operator/delegator identity created under the direct-cast address). This lets a user permanently rebind an EVM address's Sei-side identity after other modules (staking/distribution) have already built state keyed to the old direct-cast mapping — the address-association analog of "unhalting" something meant to be a one-time, irreversible action.

### Finding Description
`GetEVMAddress`/`SetAddressMapping` implement a bidirectional EVM↔Sei address mapping that is supposed to be assigned once per identity. The only anti-replay guard in `associateAddresses` (`precompiles/addr/addr.go:239-244` and every legacy version, e.g. `precompiles/addr/legacy/v630/addr.go:203-238`) checks only:

```go
_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
if found {
    return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
}
``` [1](#0-0) 

This prevents the **caller's own** Sei address from being re-associated, but does nothing to stop a *different* Sei address from claiming the EVM address side of a mapping that other modules already depend on. `SetAddressMapping` (`x/evm/keeper/address.go:10-22`) simply overwrites both directions of the mapping unconditionally: [2](#0-1) 

The codebase itself documents that this remapping is dangerous. In `x/evm/ante/preprocess.go`, the comment explains that an EIP-7702 `SetCode` transaction "creates a mutable direct-cast EVM->Sei mapping that a later `associatePubKey` call can remap, orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [3](#0-2) 

The same warning is repeated in `app/ante/evm_checktx.go:251-267` and `app/ante/evm_delivertx.go:42-48`, and `utils/helpers/address.go:149-188` (`AuthorityToPreAssociate`) implements a targeted mitigation — but only for the EIP-7702 authorization-authority path, not for the general `associatePubKey`/`associate` precompile entry points. [4](#0-3) [5](#0-4) 

A concrete demonstration of the fallout exists in the test suite itself: `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator` shows that once a validator operator's direct-cast address is re-associated (`app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)`), the original operator address can no longer receive funds (`CanAddressReceive` returns false), and any subsequent bank-transfer to that address (e.g. commission withdrawal) fails: [6](#0-5) 

That specific commission case was hardened to fall back to the community pool, but the underlying primitive — an unrestricted, permanent remap of an EVM address's Sei-side identity via `associatePubKey` — remains generally reachable by any EVM caller and is exactly the class of defect the external report describes: a state transition ("halt"/finalize an identity binding) that should be irreversible is instead reversible, and reversing it corrupts downstream accounting that assumed permanence.

### Impact Explanation
Any account that has already accumulated state under a direct-cast Sei address derived from an EVM address (e.g. an operator/delegator identity used by staking or distribution, or any other module that persists data keyed to the direct-cast address) can have that binding silently remapped by a third party calling `associatePubKey`/`associate` with a pubkey that hashes to the same EVM address's counterpart chain semantics is not required — the check only inspects the Sei-address side of the mapping being written, not the EVM-address side. Once remapped:
- Funds and state that were reachable at the direct-cast address become permanently unreachable through normal bank transfers (`CanAddressReceive` returns false), which is the "permanent freezing" class of impact explicitly in scope.
- The code's own comments state this exact remap path "can then halt the chain via the distribution validator-removal hook" for validator-created identities, which lands squarely in the in-scope "validator halt" category.

### Likelihood Explanation
Reaching `associatePubKey`/`associate` requires only a normal EVM transaction call to the `addr` precompile (address `0x1002` family) with a pubkey/signature the caller controls — no special privilege is needed. The precondition (a direct-cast identity already holding state, e.g. via prior EIP-7702 `SetCode` usage or any flow that creates state under a not-yet-associated direct-cast address) is realistic given the codebase explicitly built (partial) defenses against it for the SetCode authority case, indicating this is a known, previously-triggered risk surface that was only partially mitigated.

### Recommendation
Extend the association guard in `associateAddresses` (`precompiles/addr/addr.go` and its legacy variants) to also reject the call when the target `evmAddr` already has an existing Sei-address mapping (via `GetSeiAddress`) that differs from the direct-cast address, mirroring the check already applied for `seiAddr`. Alternatively, apply the same `AuthorityToPreAssociate`-style safety checks used for EIP-7702 authorities to the general-purpose `associate`/`associatePubKey` precompile entry points so a mapping already relied upon by staking/distribution/bank cannot be remapped after the fact.

### Proof of Concept
1. Create/derive a validator operator address as the direct-cast Sei address of some `evmAddr` (no prior association), and have staking/distribution accrue rewards/commission under that identity, as modeled in `TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator` (`sei-cosmos/x/distribution/keeper/keeper_test.go:103-123`).
2. From any account, call the `addr` precompile's `associatePubKey(pubkey)` with a pubkey whose derived Sei address differs from the direct-cast address, but which the precompile accepts because only the caller's own Sei-address side is checked for prior association (`precompiles/addr/addr.go:239-244`).
3. Observe that `GetEVMAddress`/`GetSeiAddress` for the original direct-cast identity now resolve to the new mapping, `CanAddressReceive` for the original direct-cast address returns `false`, and any subsequent bank operation or `AfterValidatorRemoved`-triggered payout to that address fails/reroutes — demonstrating the "unhalt"-style permanent-binding reversal and its downstream freezing/halt effects described in `x/evm/ante/preprocess.go:103-112`.

// AssociateAuthorizationAuthorities pre-associates every EIP-7702 SetCode authorization
// authority in the transaction with its true (pubkey-derived) Sei address before EVM
// execution installs delegation code for it. Authorities are distinct accounts from the tx
// sender, so the sender association performed by the caller does not cover them. Without
// this, SetCode creates a mutable direct-cast EVM->Sei mapping that a later associatePubKey
// call can remap, orphaning any staking/distribution state created under the direct-cast
// identity (which can then halt the chain via the distribution validator-removal hook).
//
// This is the legacyabci counterpart of x/evm/ante's EVMPreprocessDecorator so both ante
// paths associate authorities identically. It is best-effort: only authorities whose
// authorization the EVM will actually apply are pre-associated — helpers.AuthorityToPreAssociate
// enforces the same chain-id/nonce/account-code checks go-ethereum uses, which also prevents
// replaying a publicly-visible authorization a user signed for another chain to force-associate
// them. Each association runs in its own cache context and is only committed on success, so an
// already-associated, skipped, or failing authority affects only itself and never rejects the
// transaction (matching go-ethereum, which would still accept it). Non-SetCode transactions
// carry no authorizations and are a no-op.

func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
	// Nonce must not overflow (EIP-2681).
	if auth.Nonce+1 < auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	evmAddr, seiAddr, pubkey, err := RecoverAddressesFromAuthorization(auth)
	if err != nil {
		return common.Address{}, nil, nil, false
	}
	// Cross-check against go-ethereum's authoritative recovery so we only ever act on the
	// exact address SetCode would target during execution.
	if authAddr, aerr := auth.Authority(); aerr != nil || authAddr != evmAddr {
		return common.Address{}, nil, nil, false
	}
	// Authority must have no code, or only an existing delegation designator.
	if code := k.GetCode(ctx, evmAddr); len(code) != 0 {
		if _, ok := ethtypes.ParseDelegation(code); !ok {
			return common.Address{}, nil, nil, false
		}
	}
	// Authority account nonce must match the authorization nonce.
	if k.GetNonce(ctx, evmAddr) != auth.Nonce {
		return common.Address{}, nil, nil, false
	}
	// Already-associated authorities need no pre-association (and cannot be re-mapped).
	if _, associated := k.GetEVMAddress(ctx, seiAddr); associated {
		return common.Address{}, nil, nil, false
	}
	return evmAddr, seiAddr, pubkey, true
```

// TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator covers the
// case where the validator operator address itself cannot receive funds — its EVM
// address was re-associated (e.g. via associatePubKey) away from the direct-cast Sei
// address it was created under. The withdraw-address fallback in GetDelegatorWithdrawAddr
// resolves back to that same unreceivable operator address, so the commission
// force-withdraw fails. AfterValidatorRemoved runs during EndBlock, so it must not panic:
// the commission is routed to the community pool instead, which conserves value because
// the coins already back the distribution module account.
func TestAfterValidatorRemovedRoutesToCommunityPoolForUnreceivableValidator(t *testing.T) {
	app := seiapp.Setup(t, false, false, false)
	ctx := app.BaseApp.NewContext(false, tmproto.Header{})

	// The validator operator is the direct-cast Sei address of an EVM address.
	evmAddr := common.HexToAddress("0x3333333333333333333333333333333333333333")
	castAddr := sdk.AccAddress(evmAddr[:])
	valAddr := sdk.ValAddress(castAddr)
	valAccAddr := sdk.AccAddress(valAddr) // == castAddr

	require.True(t, app.BankKeeper.CanSendTo(ctx, castAddr))

	// Re-associate the EVM address to a different true Sei address, mirroring
	// associatePubKey after a validator was created under the direct-cast address.
	associatedAddr := seiapp.AddTestAddrs(app, ctx, 1, sdk.NewInt(1000000000))[0]
	app.EvmKeeper.SetAddressMapping(ctx, associatedAddr, evmAddr)

	// The operator/delegator address can no longer receive funds, and the
	// withdraw-address fallback resolves back to that same unreceivable address.
	require.False(t, app.BankKeeper.CanSendTo(ctx, castAddr))
	require.Equal(t, valAccAddr.String(), app.DistrKeeper.GetDelegatorWithdrawAddr(ctx, valAccAddr).String())
