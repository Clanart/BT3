This confirms the vulnerability mechanism: `OrderedWebRequest.onBeforeSendHeaders` runs listeners sequentially, and each listener's returned `requestHeaders` **fully replace** `details.requestHeaders` for the next listener in the chain [1](#0-0) . In `main.ts`, `installSameOriginFilter` (which strips `Authorization`/`Cookie` on cross-origin redirects) is registered *before* `installAuthenticatedImageFilter` (which re-adds `Authorization: token <PAT>` based solely on `origin` + `pathname` matching) [2](#0-1) . Since the authenticated-image filter re-injects the header independent of whether the same-origin filter just stripped it for a redirect, a same-origin-filter-approved case ("no redirect yet") is fine, but the ordering means the authenticated-image-filter runs on every step of every redirect chain and will re-add the token whenever the *current* hop's URL happens to be one of the known account origins (e.g., `github.com`) and the path matches the asset regex — including on a redirect **hop that is itself the trusted origin but ultimately redirects further to an attacker host**, because the origin-scoping filter for the *initial* leg is irrelevant to filter #2, which only checks the current `details.url`'s origin/pathname, not whether this leg is itself a redirect target from an untrusted source.

### Title
Authorization token can leak to non-whitelisted (attacker) hosts because origin-scoping and asset-path-based token injection are checked independently across request legs - (File: app/src/main-process/authenticated-image-filter.ts)

### Summary
`installAuthenticatedImageFilter` re-attaches the user's PAT as an `Authorization: token <token>` header to any request whose **current URL origin** is a known signed-in account origin and whose **path** matches a broad regex for enterprise avatars or repo/user-attachment assets [3](#0-2) . This filter is applied independently, on a per-hop basis, inside `OrderedWebRequest`, which chains listener results by literally replacing `details.requestHeaders` with whatever the previous listener returned before invoking the next one [1](#0-0) . `installSameOriginFilter` is meant to be the guard that prevents credentials from surviving a cross-origin redirect by tracking the *initial* origin of a request id and stripping `authorization`/`cookie`/`authentication` headers when the *current* leg's origin differs from that initial origin [4](#0-3) . Because the two filters run one after another on the *same* `details` object for the same redirect hop, and the authenticated-image-filter's decision to attach the token is based purely on that hop's own origin/pathname (not on whether that hop is itself a redirect target that will be followed further to an untrusted host), any GitHub-hosted asset URL that an attacker can get the app to fetch and then 3xx-redirect elsewhere (e.g., a malicious file uploaded as a "user-attachment" or GHES asset whose underlying storage 302s to attacker infrastructure, or a compromised/malicious GHES instance) can result in the PAT being sent to the *next* hop before the same-origin filter has a chance to see that hop as a mismatch (the same-origin filter only strips it on the immediately following request, but the authenticated-image-filter will simply reapply it on the retry to the same known origin, and more importantly the regex `isGitHubRepoAssetPath` is permissive enough — `/^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/` and `/^\/user-attachments\/assets\/[^/]+\/?$/` — that it accepts any path shaped like `/owner/repo/assets/id/guid` on the matched origin, regardless of whether the corresponding resource actually belongs to a repository the user has access to).

This is the structural analog of the Sherlock report: two independently-maintained security-relevant collections/decisions (there, `tokenAddresses` set + `TOKEN_ADDRESS_LIMIT` check; here, "is this origin/pathname a place we should attach the token" + "is this origin still the same as where the request started") are not kept consistent with each other, so a guard that looks sufficient in isolation (asset-path whitelist) can defeat a guard meant to bound risk (same-origin credential stripping) simply because of unlucky ordering/independence of the two checks.

### Impact Explanation
If exploitable, this results in exfiltration of the user's real GitHub PAT (not just a scoped avatar token) to a non-GitHub host, since `Authorization: token <PAT>` is the header attached — matching the explicitly in-scope "credential/token exfiltration" impact category. The blast radius is the full PAT for the affected account (dotcom or GHE), not a request-scoped credential.

### Likelihood Explanation
This requires that: (1) the attacker controls, or can get the app to load, a resource URL on a real GitHub/GHE host that is shaped like a repo asset or enterprise avatar path, and (2) that resource actually issues an HTTP redirect to an attacker-controlled host. This is a plausible but not fully confirmed path from local code alone — GitHub's asset/attachment CDN endpoints are generally same-origin proxies rather than 302 redirectors, and I was not able to verify from the codebase whether the underlying `github.com`/GHES asset endpoints actually 3xx-redirect cross-origin in practice (that's server-side GitHub.com behavior, outside this repo). I also could not fully trace whether `onBeforeRedirect` (which is synchronous and separate from `onBeforeSendHeaders`) resets `requestOrigin` tracking in `same-origin-filter.ts` in a way that would close this gap before `authenticated-image-filter.ts` runs on the subsequent hop. This uncertainty is the main reason likelihood cannot be rated higher than "possible, unverified end-to-end."

### Recommendation
Make `installAuthenticatedImageFilter` aware of the same request-id-based origin tracking that `installSameOriginFilter` already maintains, so that the token is only reattached if the *current* hop's origin equals the *original* request's origin (not just "is a known account origin"). Concretely, thread the `requestOrigin` map (or an equivalent "is this still the first-party origin for this request id" signal) into the authenticated-image-filter, and refuse to attach `Authorization` if the request has already been redirected away from its original origin, even if the new origin happens to also be a "known" GitHub host.

### Proof of Concept
Conceptual PoC (not independently verified against live GitHub redirect behavior):
1. An attacker crafts or compromises a resource reachable at a URL matching `isGitHubRepoAssetPath`, e.g. `https://github.com/attacker-org/attacker-repo/assets/123/guid` or `https://github.com/user-attachments/assets/guid`, embedded as an `<img>` src in a PR/issue/comment rendered inside GitHub Desktop's webview.
2. GitHub Desktop's renderer requests this URL; `installAuthenticatedImageFilter` matches `origin === 'https://github.com'` (a known signed-in account origin) and the asset pathname, and attaches `Authorization: token <PAT>` [5](#0-4) .
3. If the server response for that URL is an HTTP redirect to an attacker-controlled host (e.g., a stale/attacker-influenced asset-storage redirect), `installSameOriginFilter` only strips the header on the *next* onBeforeSendHeaders invocation for that same request id when it detects the origin mismatch [6](#0-5)  — but because listeners in `OrderedWebRequest.onBeforeSendHeaders` are re-invoked per hop, and `installAuthenticatedImageFilter` is registered after `installSameOriginFilter` in `main.ts` [2](#0-1) , the exact interleaving of "sanitize because origin changed" vs. "re-add because this new origin is a known GitHub host" for that new hop needs to be traced against real GHE/GitHub.com redirect responses to confirm the token reaches the attacker host.

Given that I could not fully confirm step 3 end-to-end purely from the client-side code in this repository (it depends on server-side redirect behavior of github.com/GHES asset storage, which is outside the indexed codebase), I recommend a Devin session with network-tracing/browser access to validate whether any GitHub-hosted asset/avatar endpoint actually issues a cross-origin redirect, which would confirm or refute exploitability of this ordering gap.

  orderedWebRequest: OrderedWebRequest

  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,

    }

    return {}
  })

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
