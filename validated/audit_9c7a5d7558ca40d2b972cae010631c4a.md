### Title
Line-indexed partial-commit selection is applied against a re-read, potentially different working-directory diff, silently corrupting staged/committed content - (File: `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user stage only a subset of the changed lines in a file ("partial commit"). The selection the user makes in the UI is stored as a set of line *indices* (`DiffSelection`) computed against the diff object that was displayed to them at that moment. At commit time, however, Desktop does **not** reuse that reviewed diff to build the patch — it silently re-reads the working directory and regenerates a brand-new diff, then re-applies the old index-based selection to it. If the file content changes between "user reviews/selects lines" and "user clicks Commit," the old line indices no longer refer to the same content, and the wrong lines are staged/committed without any warning. This is the git-client analog of the Hypervisor "sandwiching" bug: an operation is executed against state that can be mutated between the moment the user evaluates/authorizes it and the moment it is actually settled, with no min/expected-value check to detect the drift.

### Finding Description
The UI diff shown to the user is loaded and cached in `updateChangesWorkingDirectoryDiff`, which reads the working directory diff once and stores it plus a `selectableLines` set on the file's `DiffSelection`. [1](#0-0) 

`DiffSelection` (the "selected lines" model) only tracks integer line *indices* that diverge from the default selection — it has no concept of the actual diff content, only positions relative to whatever diff it was built against. [2](#0-1) [3](#0-2) 

When the user commits, `createCommit` unstages everything and calls `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex`. [4](#0-3) [5](#0-4) 

`applyPatchToIndex` performs a **second, independent** read of the working-directory diff (`getWorkingDirectoryDiff`) rather than reusing the diff object the user actually reviewed in the Changes view, and then builds the patch by asking `file.selection.isSelected(absoluteIndex)` against that freshly-read diff: [6](#0-5) 

`formatPatch` walks the (new) diff's hunks and, for each line, decides inclusion purely by `absoluteIndex` membership in the old selection's diverging-line set: [7](#0-6) 

The only place Desktop attempts to keep the selection "in sync" with a changed diff is `withSelectableLines`, invoked from `updateChangesWorkingDirectoryDiff` when the *displayed* diff is refreshed — it merely prunes indices that are no longer selectable; it does not detect that the same index now maps to semantically different content, and it is not guaranteed to run again immediately before the commit-time re-diff in `apply.ts`. [8](#0-7) [9](#0-8) 

The broken invariant: the patch actually applied to the git index is generated from a diff object that is not proven to be the same one the user visually reviewed and selected lines against. No hash/mtime/content check ties the applied patch back to the reviewed diff, analogous to the missing `amountMin`/slippage check in the Hypervisor report that let pool state drift between call and settlement.

### Impact Explanation
If a file changes on disk between the moment the user reviews a diff and selects specific lines and the moment they press "Commit" (a window Desktop does not close — no re-validation, no lock, no diff-hash comparison), the committed patch can contain different content than what the user selected: lines the user explicitly excluded can be silently included, and/or lines they included can silently map to different code. This is a silent corruption of what the user commits, which can then be pushed to a shared/public branch — matching the specified impact category exactly. The attacker-controlled trigger for such a disk mutation is plausible from a cloned repository (e.g., a repo-provided git hook such as `post-checkout`/`post-merge`, or an editor/build-tool auto-format-on-save/lint-fix task wired into the workspace) that runs asynchronously while the user is reviewing the Changes tab.

### Likelihood Explanation
Desktop already watches the working directory and frequently triggers status/diff refreshes, and the codebase's own comment in the syntax-highlighting code explicitly acknowledges "someone rapidly modifies the file on disk" as a real race condition it has had to design around, indicating this class of race is not merely theoretical in this codebase. [10](#0-9) 
The race window between selecting lines and clicking Commit is arbitrarily long (limited only by user think time), which increases the practical likelihood of an attacker-triggered background process winning the race compared to a blockchain sandwich attack that must land within one block.

### Recommendation
- At commit time, do not silently re-read and re-diff the working directory for a file with a `Partial` selection. Instead, re-use (or hash-compare) the exact diff object the selection was built against, and if the on-disk content has changed since that diff was generated, abort staging that file and surface an explicit error/refresh prompt to the user (the git-client equivalent of an `amountMin`/slippage check).
- Alternatively, immediately before calling `applyPatchToIndex`, recompute the diff and diff it against the diff the selection was validated on; if hunk boundaries/content differ, invalidate the stale selection instead of blindly reapplying old indices to new content.
- Add an integration test that mutates the working file between diff-load and commit and asserts the commit either fails safely or matches the originally reviewed selection, rather than silently committing different content.

### Proof of Concept
1. Open a repository in Desktop that contains a modified tracked file with multiple hunks.
2. In the Changes view, partially select only some lines of one hunk for commit (leaving other lines unselected), causing `DiffSelection` divergent-line indices to be computed against the currently displayed diff (`updateChangesWorkingDirectoryDiff`).
3. Before pressing "Commit", trigger (e.g., via a repo-provided git hook, editor auto-format-on-save, or a background script the repo caused to run) a modification to the same file that changes line count/positions elsewhere in the file (shifting subsequent hunks), without altering the selected hunk's on-screen appearance yet.
4. Click "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-reads the diff fresh (`app/src/lib/git/apply.ts:60`) and applies the stale `DiffSelection` indices (`app/src/lib/patch-formatter.ts:157`) to this new diff.
5. Inspect the resulting commit (`git show`): it contains content different from what was visually selected in step 2 — e.g., extra unrelated hunks partially staged, or the intended lines omitted — with no warning shown to the user.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }

  /**
   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).
   */
  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
