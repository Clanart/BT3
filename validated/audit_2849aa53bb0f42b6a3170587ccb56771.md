### Title
Permissionless `donateRewards` can zero out `queuedRewards` while the `rewardPerTokenStored` increment rounds to zero, permanently stranding backlog rewards - (File: rewards/BaseRewardPool.sol)

### Summary
`donateRewards(uint256 _amountReward, address _rewardToken)` is callable by anyone for any already-registered reward token and forwards straight into `_provisionReward()`. When `totalStaked() > 0` and `rewards[token].queuedRewards` holds a backlog accumulated while `totalStaked()` was previously zero, `_provisionReward()` merges that backlog into `_amountReward`, unconditionally resets `queuedRewards` to `0`, and then computes the `rewardPerTokenStored` increment via integer division by `totalStaked()`. If `totalStaked()` is large enough relative to `(backlog + _amountReward) * 10**stakingDecimals()`, the division rounds down to `0`, so the whole backlog is wiped out of `queuedRewards` without ever being reflected in `rewardPerTokenStored`.

### Finding Description
`_provisionReward()` in [1](#0-0)  performs:
1. `safeTransferFrom(msg.sender, address(this), _amountReward)` — pulls the caller's tokens.
2. Adds `_amountReward` to `historicalRewards`.
3. If `totalStaked() == 0`, it just accumulates into `queuedRewards` (correct deferral).
4. Otherwise, it does `_amountReward += rewardInfo.queuedRewards; rewardInfo.queuedRewards = 0;` and then `rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()`.

The bug is in step 4: `queuedRewards` is zeroed **unconditionally**, regardless of whether the subsequent division actually produces a non-zero increment. Because Solidity integer division truncates, if `totalStaked()` (denominated in the staking token's raw units) is large relative to `(backlog + _amountReward) * 10**stakingDecimals()`, the increment computed is `0`, yet the backlog that produced it has already been reset to `0` and is never retried.

`donateRewards()` in [2](#0-1)  has no access control — any unprivileged EOA can call it for any token satisfying `isRewardToken[_rewardToken]`, with `_amountReward` as low as `1`. This gives an attacker full control over exactly when the queued-backlog reconciliation is triggered: they can wait until `totalStaked()` (i.e., total staked balance of the staking token, in `stakingToken` decimals, from `IMasterMagpie(operator)`) grows large enough that `(backlog+1) * 10**stakingDecimals() / totalStaked()` rounds to zero, then call `donateRewards(1, token)`. This flips the branch, merges and erases `queuedRewards`, and produces a zero increment to `rewardPerTokenStored` — permanently stranding the backlog: it remains counted in `historicalRewards` (and physically sits in the contract's token balance) but is never distributed to any staker via `earned()`/`rewardPerToken()`.

No existing modifier or check prevents this: `donateRewards` has no `onlyManager`/`onlyMasterMagpie` guard, and `_provisionReward` never verifies that the computed increment is non-zero before discarding `queuedRewards`.

### Impact Explanation
This is a permanent freezing of unclaimed yield: the queued backlog of a reward token accumulated during a zero-`totalStaked()` period becomes forever unclaimable by any staker once an attacker triggers the zero-rounding reconciliation. The tokens remain locked in the `BaseRewardPool` contract with no code path to re-credit them to `rewardPerTokenStored`, matching Immunefi's "High - Permanent freezing of unclaimed yield" class. The scale of loss equals the size of the pre-existing `queuedRewards` backlog for that token.

### Likelihood Explanation
The attack is cheap (as little as 1 wei of the reward token) and requires only a permissionless call to `donateRewards`, so it is trivially repeatable whenever the precondition holds. The precondition — a non-trivial `queuedRewards` backlog built up while `totalStaked() == 0`, followed later by a large enough `totalStaked()` to force zero-rounding — is a realistic operational scenario (e.g., rewards queued before/at pool launch before staking ramps up, or during any period with temporarily zero stakers). The attacker fully controls the timing and the donation amount, making exploitation deterministic once the numeric condition is met.

### Recommendation
Only zero out (or reduce) `queuedRewards` by the portion actually converted into a non-zero `rewardPerTokenStored` increment, e.g., compute the increment first, and only clear/decrement `queuedRewards` if the increment is non-zero (or track/carry any dust remainder rather than discarding the whole backlog). Alternatively, guard the branch so that `queuedRewards` is only reset when `(_amountReward * 10**stakingDecimals()) / totalStaked() > 0`, retaining the remainder for future provisioning otherwise.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `BaseRewardPool` with a mock `IMasterMagpie` and mock staking/reward ERC20s (stakingDecimals = 18).
2. With `totalStaked() == 0` (no stakers registered in mock master magpie), have the reward manager call `queueNewRewards(largeBacklogAmount, rewardToken)` — confirm `rewards[rewardToken].queuedRewards == largeBacklogAmount` and `rewardPerTokenStored == 0`.
3. Configure the mock master magpie so `totalStaked()` returns a very large value (e.g., such that `(largeBacklogAmount + 1) * 1e18 / totalStaked() == 0`), and register a victim account with some staked balance in the mock.
4. From an unrelated attacker EOA holding 1 wei of `rewardToken`, call `donateRewards(1, rewardToken)`.
5. Assert: `rewards[rewardToken].queuedRewards == 0` (backlog wiped), `rewards[rewardToken].rewardPerTokenStored` unchanged (still `0`), and `earned(victim, rewardToken)` unchanged/still `0` despite `historicalRewards` having increased by `largeBacklogAmount + 1` — demonstrating the backlog is permanently unclaimable.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
