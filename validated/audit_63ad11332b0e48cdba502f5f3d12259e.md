## Title
Tron `IntentGatewayV2.withdraw()` treats a call to a non-existent (self-destructed) token as a successful transfer, permanently finalizing escrow release without paying the beneficiary - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

## Summary
The external report's core invariant is: a settlement/exercise path that "succeeds" (does not revert) must actually move the promised value, otherwise the paying party is charged (premium, escrow, fill) for nothing. In PuttyV2, the failure mode was the opposite (an unwanted revert blocking exercise). In Hyperbridge's Tron `IntentGatewayV2`, the analogous but more dangerous failure mode is the inverse: the withdrawal path can appear to *succeed* while transferring zero value, and irreversibly marks the order as settled.

## Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and uses OpenZeppelin's `SafeERC20`/`IERC20` for the escrow-in path in `placeOrder()`: [1](#0-0) 

`safeTransferFrom` from OZ's `SafeERC20` verifies the call target has code (via `Address`'s return-data verification), so a token address with no bytecode reverts at deposit time — this path is safe.

However, the escrow-out path, `withdraw()`, does **not** use `SafeERC20`. It performs a raw low-level `.call` and treats a bare `success == true` as proof of a completed ERC20 transfer: [2](#0-1) 

In the EVM, a `.call()` to an address with **no contract code** always returns `success = true` with empty return data — this is standard EVM semantics, not a revert. Since `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` only checks `success`, this line silently "succeeds" for a no-code target, no tokens move, yet the code proceeds to:
- Decrement `_orders[body.commitment][token] -= amount;`
- Set `_filled[body.commitment] = beneficiary;` unconditionally at the top of the function
- Emit `EscrowReleased`/`EscrowRefunded` as if funds were paid out

This is a direct behavioral regression relative to the primary EVM contract, `IntentsBase.sol`, whose `_withdraw()` correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`: [3](#0-2) 

OZ's `safeTransfer` verifies the target has code and reverts otherwise, so the primary contract cannot silently no-op a transfer. The Tron fork loses this guarantee entirely for the withdrawal path while still relying on it for the deposit path — an inconsistent, and here strictly weaker, safety check within the very same file.

The trigger does not require a malicious relayer, prover, or admin: any ERC20 token used as an order input that legitimately has bytecode at `placeOrder()` time but loses it before settlement (e.g., self-destructed pre-Dencun implementation, an unsafe upgradeable/minimal-proxy pattern that is later bricked, or a token migration that leaves the old address empty) causes this. The order creator only needs to reference such a token as one of `order.inputs`; the Hyperbridge protocol's own proof/authentication logic (`_authenticate`, commitment binding) executes exactly as designed and is not what fails here — the failure is purely in `withdraw()`'s unchecked low-level call.

## Impact Explanation
When the target token has no code at settlement time:
- `withdraw()` does not revert.
- `_filled[commitment]` is set, permanently finalizing the order (no retry, no re-dispatch possible).
- `_orders[commitment][token]` is decremented as though funds were paid.
- The beneficiary (the solver on `RedeemEscrow`, or the user on `RefundEscrow`) receives **zero** tokens for that asset, with no on-chain signal of failure (the `TransferFailed()` revert branch is never triggered because `success` is `true`).

This is a direct, irreversible loss of escrowed funds for the rightful beneficiary — exactly the "stealing or loss of funds" / "false ... acceptance of settlement" impact class in scope, reachable without any privileged or malicious infrastructure actor.

## Likelihood Explanation
Likelihood depends on encountering an input token whose bytecode disappears between order placement and settlement. This is more plausible than it may first appear given: (a) `SELFDESTRUCT` was fully functional pre-Dencun and remains functional in many EVM-compatible/Tron-style environments, (b) proxy-based or migratable tokens can be intentionally "sunset," and (c) the time window between placement and settlement in a cross-chain order (which involves relayer-mediated proof delivery) can be arbitrarily long, widening the window for such an event. Regardless of exact likelihood, the code path itself is a clear, provable logic defect: an unchecked low-level call is used to represent a critical fund-moving operation, and finalization occurs unconditionally on `success` alone.

## Recommendation
Replace the raw low-level `.call()` in `withdraw()` (and the identical pattern in `_cancelFromDest`/`sweepDust`-style transfers in the same Tron contract) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the guarantee already used in `placeOrder()` and in the primary EVM `IntentsBase.sol._withdraw()`. This ensures a transfer to a non-existent contract reverts instead of being recorded as a successful, finalized settlement.

## Proof of Concept
1. User places a cross-chain order via `placeOrder()` with `order.inputs` containing token `T`, which has valid bytecode at this time — `IERC20(T).safeTransferFrom` succeeds and `_orders[commitment][T] += amount`. [4](#0-3) 
2. Before the order is filled or cancelled, token `T`'s contract self-destructs (or its proxy implementation is bricked), leaving no code at address `T`.
3. Solver fills the order on the destination chain (delivering real output value); Hyperbridge relays a legitimate, correctly-authenticated `RedeemEscrow` message back to the source chain.
4. `onAccept` invokes `withdraw(body, false)`: [5](#0-4) 
5. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (no-code call semantics), so the `TransferFailed()` branch is never hit, `_orders[commitment][T]` is decremented, `_filled[commitment]` is set, and `EscrowReleased` is emitted. [6](#0-5) 
6. The solver, who already delivered real output tokens to the beneficiary on the destination chain, receives nothing in return, and the order is now permanently marked filled — no further redemption is possible.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
