### Title
Registration-time-only decimals check + live asset metadata reads let an asset owner shrink `erc_decimals - local_decimals` to zero and corrupt cross-chain amount scaling - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`convert_to_balance` computes the scaling divisor as `10^(erc_decimals.saturating_sub(local_decimals))`. [1](#0-0) 
The invariant `erc_decimals >= local_decimals` is enforced only inside `register_token`/`update_token`, at the moment those privileged calls run, using the asset's decimals value read at that instant: [2](#0-1) 
But `Precisions` only ever stores `erc_decimals`; `local_decimals` is never snapshotted. Every subsequent conversion point (`send`, `on_accept`, `on_timeout`) re-reads `local_decimals` live from `T::Assets::decimals(...)`, i.e. from the asset's mutable metadata, instead of using the value that was validated at registration time: [3](#0-2) [4](#0-3) 

### Finding Description
The design assumes `erc_decimals >= local_decimals` holds for the lifetime of a registered token, but nothing re-checks or freezes `local_decimals` after `register_token`/`update_token` run. `local_decimals` for non-native assets comes straight from `pallet-assets`' (or whatever `T::Assets` implementation is wired in) metadata, which is typically owner-controlled via `set_metadata` — an unprivileged, per-asset permission distinct from the pallet's own `CreateOrigin` (root/governance) that gates `register_token`. Because asset creation in `pallet-assets` is normally permissionless (any signed account can create an asset and become its `Owner`), an attacker can:

1. Create (or already own) a fungible asset with `decimals = D1`.
2. Get it registered as a bridged HFT token with `erc_decimals = D1` (satisfying the registration-time check).
3. Later call `Assets::set_metadata` (owner-authorized, no HFT-pallet involvement) to raise the asset's decimals to `D2 > D1`.
4. `Precisions` still stores the old `erc_decimals = D1`; `local_decimals` now reads as `D2`.
5. `erc_decimals.saturating_sub(local_decimals)` underflows to `0`, so the divisor collapses to `10^0 = 1`, and `convert_to_balance` returns the raw, unscaled ERC20 `U256` amount as the local balance.

This corrupts the amount by orders of magnitude (typically ERC20 uses 18 decimals) in both `on_accept` (mint/transfer to beneficiary) and `on_timeout` (refund from `pallet_account`), leading to massive over-minting of the wrapped asset or draining the escrow custody account with a tiny bridged amount.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" / "wrongful asset movement / wrong amount" categories. An attacker can mint arbitrary amounts of the local wrapped asset, or drain `pallet_account`'s native-asset escrow on refund/timeout, using only a trivial cross-chain message (or even a single legitimate small transfer that then times out) once the decimals mismatch is engineered.

### Likelihood Explanation
Likelihood depends on how the runtime's `Assets` implementation gates metadata mutation and how token registration is operationalized (e.g., whether HFT only registers assets it creates/owns itself, versus allowing registration of pre-existing, user-owned assets). In this repository the `CreateOrigin` for `register_token`/`update_token` is `EnsureRoot` in the reference runtime wiring, but that only gates the HFT pallet's own storage — it does not gate the separate `pallet-assets` `Owner`/`set_metadata` permission for the underlying asset. If governance ever registers a pre-existing, user-owned asset (a common flow for onboarding community tokens), the asset's owner retains unilateral, unprivileged control over its decimals metadata after registration, making this readily exploitable without any relayer/prover compromise.

### Recommendation
Snapshot `local_decimals` into `Precisions` (or a new storage item) at `register_token`/`update_token` time instead of re-reading live asset metadata on every `send`/`on_accept`/`on_timeout` call. Alternatively, re-validate `erc_decimals >= local_decimals` on every conversion path and hard-fail (rather than silently saturating to zero) when the live decimals violate the registered configuration.

### Proof of Concept
1. Governance calls `register_token` for asset `X` (owned by attacker) with `native = false`, `config.decimals (erc_decimals) = 6`, while `Assets::decimals(X) = 6` at that time — passes the `ensure!(config.decimals >= local_decimals, ...)` check.
2. Attacker, as `X`'s owner, calls `Assets::set_metadata` to change `X`'s decimals to `18`.
3. A counterpart EVM contract (or a message crafted to look like one from a registered contract address) sends an `on_accept` message with `message.amount` scaled at 6-decimal ERC20 precision (e.g. `1_000_000` representing `1.0` token at old precision).
4. In `on_accept`, `decimals = 18` (live), `erc_decimals = 6` (stored) → `erc_decimals.saturating_sub(local_decimals) = 0` → `convert_to_balance` divides by `10^0 = 1`, minting `1_000_000` raw units to the beneficiary instead of the intended `1` unit at correct precision — a 10^6x amplification (and worse if the gap is bigger, e.g. 18 vs 6 → up to 10^18x).
5. Assert the minted/transferred `amount` equals the corrupted raw value rather than the properly down-scaled amount, and that repeating via `on_timeout` similarly drains `pallet_account`. [1](#0-0) [5](#0-4) [6](#0-5)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
