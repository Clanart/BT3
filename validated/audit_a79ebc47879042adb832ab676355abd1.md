### Title
Missing zero-value validation on `kip71.gastarget` governance parameter causes division-by-zero panic in base fee calculation - ([File: params/kip71_config.go])

### Summary
The `Kip71GasTarget` governance parameter is registered with a `noopFormatChecker` that accepts any `uint64` value including `0`, and no additional consistency check rejects zero at header-verification time. Once such a value is ratified through governance and activated, `KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` without a zero-check, causing a runtime panic on every node computing/verifying the next block's base fee.

### Finding Description
The `Kip71GasTarget` parameter definition uses `noopFormatChecker`, unlike `Kip71BaseFeeDenominator` which explicitly rejects zero (`v != 0`): [1](#0-0) 

When a `header.Vote` for `Kip71GasTarget` is processed, `checkConsistency` in the header-gov module performs no additional validation for this parameter — it falls into the case that returns `nil` unconditionally: [2](#0-1) 

This contrasts with `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which do have cross-parameter consistency checks (`ErrLowerBoundBaseFee`/`ErrUpperBoundBaseFee`), but no equivalent check exists to ensure `Kip71GasTarget != 0`.

Once the `GasTarget = 0` value becomes active (via `ParamSet`), `KIP71Config.NextMagmaBlockBaseFee` reads it into a local `gasTarget` variable and, unlike `BaseFeeDenominator` which has an explicit `== 0` fallback, performs no such guard: [3](#0-2) 

Concretely: if `gasTarget == 0` and `parentGasUsed > 0` (essentially guaranteed on any active chain), the code enters the "gas used above target" branch and executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e. `big.Int.Div` by zero, which panics in Go.

### Impact Explanation
`NextMagmaBlockBaseFee` is invoked by every node — both when generating a block as proposer and when validating headers via `VerifyMagmaHeader` — to compute/verify the base fee of the next block. A panic here is not contained to a single account or contract call; it crashes the node process itself. Since this parameter is part of consensus-critical governance state that all nodes converge on identically, a `GasTarget = 0` value that gets ratified on-chain will deterministically crash every full node and consensus node the moment it activates, halting the entire chain. This is a severe availability/DoS impact matching the class of "division-by-zero from missing validation on a governance-set divisor" described in the referenced report (`setBondPercentDiv`/`bondForRebalance`).

### Likelihood Explanation
Reaching this bug requires a governance vote for `kip71.gastarget = 0` to be cast and ratified, which in "single" governance mode only requires the governing node's vote (a legitimate, in-scope governance-parameter path per the reachable-paths list). Because neither `NewVoteData`'s `FormatChecker` nor `checkConsistency`'s per-parameter switch rejects `0` for this parameter, there is no protocol-level barrier preventing this value from being accepted and activated — the only barrier is operator diligence, which is precisely the class of risk the referenced report calls out (owner/governance privilege misuse causing DoS).

### Recommendation
Add an explicit zero-rejection `FormatChecker` for `Kip71GasTarget`, mirroring the pattern already used for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Alternatively/additionally, add a defensive `if gasTarget == 0 { gasTarget = params.DefaultGasTarget }` fallback in `NextMagmaBlockBaseFee`, consistent with the existing `BaseFeeDenominator == 0` fallback, so that even historically-persisted or externally-crafted zero values cannot crash the node.

### Proof of Concept
1. In single governance mode, the governing node casts `governance_vote("kip71.gastarget", 0)`. `NewVoteData` accepts it because `Kip71GasTarget.FormatChecker` is `noopFormatChecker` [4](#0-3) .
2. `VerifyVote`/`checkConsistency` accept the vote without further checks since `Kip71GasTarget` falls in the no-op case [2](#0-1) .
3. At the next epoch, the vote is ratified into `header.Governance`, and the resulting `ParamSet.GasTarget` becomes `0`.
4. On the following Magma-enabled block, any node calls `NextMagmaBlockBaseFee` with `parentGasUsed > 0` (normal network activity), entering the `parentGasUsed > gasTarget` branch and executing `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [5](#0-4) , causing a `big.Int` division-by-zero panic that crashes the node, reproducible deterministically on every node in the network.
