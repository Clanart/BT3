### Title
Unchecked `u64` sum of attacker-chosen payment amounts overflows, bypassing the insufficient-funds check and producing an unspendable/panicking transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` totals user-supplied payment amounts with a bare `u64` `sum()` (`networks/bitcoin/src/wallet/send.rs:187`) and then performs a bare `payment_sat + needed_fee` comparison (`send.rs:215`, `send.rs:228`). Unlike the analogous Solidity `18 - decimals` underflow, which always reverts, Rust arithmetic here either panics (debug/overflow-checks builds) or silently wraps (release builds), and both the wrap and the panic are reachable purely through the `payments: &[(ScriptBuf, u64)]` public argument.

### Finding Description
The relevant arithmetic: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

- `payment_sat` is `payments.iter().map(|p| p.1).sum::<u64>()` with no bound on each `amount` other than `amount >= DUST` (`send.rs:165-169`). Two payments of `u64::MAX - 1000` wrap the sum to a small value.
- `input_sat < (payment_sat + needed_fee)` (line 215) can then pass despite the outputs astronomically exceeding inputs, and `input_sat.checked_sub(payment_sat + fee_with_change)` (line 228) similarly operates on the wrapped value, so a change output can be appended on top.
- The resulting `SignableTransaction` has `sum(outputs) >> sum(inputs)`. Any later call to `fee()` (line 139-141) performs `sum(inputs) - sum(outputs)` as a bare `u64` subtraction, which underflows — panicking under overflow checks and wrapping to ~u64::MAX otherwise. The transaction itself is consensus-invalid, so if it is signed and broadcast it will never confirm; the multisig wastes a FROST signing round on garbage and may panic the processor (`make_signable_transaction` in `processor/src/networks/bitcoin.rs:446-470` panics on most error paths and calls `signable.fee()`/related accounting downstream).

In debug builds, or at the earlier `sum::<u64>()`/`payment_sat + needed_fee` sites, the overflow panics outright — a direct analog of the `18 - decimals` revert: attacker-controlled input exceeding an assumed bound turns arithmetic into an abort instead of a graceful `TransactionError`.

### Impact Explanation
An unprivileged party who can cause a payment of arbitrary `u64` value to reach `SignableTransaction::new` (e.g., a burn/withdrawal request whose amount is not validated against supply before scheduling, or any direct caller of this public API) can:

- crash the coordinator/signer task via integer-overflow panic or the `fee()` underflow, and/or
- cause a FROST threshold signature to be produced over a consensus-invalid transaction, burning a signing session and leaving the intended payment unprocessed (signing of an unintended message / unrecoverable DoS of the send pipeline).

The `amount` field is entirely attacker-chosen; no upstream check caps it to the 21M BTC supply or to `input_sat`.

### Likelihood Explanation
Medium-low in the honest pipeline (the processor normally builds payments from real balances), but the function is a public, documented transaction-building API and the panic/invalid-tx is deterministic once triggered — any caller reaching it with unvalidated amounts hits it 100% of the time, matching the "always reverts" character of the source bug.

### Recommendation
Replace the bare `u64` arithmetic on untrusted amounts with checked operations and surface a `TransactionError`:

```rust
let payment_sat = payments.iter().try_fold(0u64, |acc, p| acc.checked_add(p.1))
  .ok_or(TransactionError::NotEnoughFunds { inputs: 0, payments: u64::MAX, fee: 0 })?;
let total = payment_sat.checked_add(needed_fee).ok_or(TransactionError::NotEnoughFunds {
    inputs: input_sat, payments: payment_sat, fee: needed_fee })?;
if input_sat < total { /* existing error */ }
```

Also make `fee()` use `checked_sub` and document/return an error rather than relying on invariant that outputs ≤ inputs.

### Proof of Concept
```rust
// payments attacker-controlled; each >= DUST (546)
let payments = vec![
  (script_a, u64::MAX - 1000),
  (script_b, u64::MAX - 1000),
];
// input_sat: one real 10_000-sat ReceivedOutput
let stx = SignableTransaction::new(vec![input], &payments, None, None, 10);
// debug/overflow-checks build: panic inside sum::<u64>() or at `payment_sat + needed_fee`
// release build: payment_sat wraps to ~u64::MAX-2000 -> still fails, but pick
//   amounts summing to wrap below input_sat (e.g., u64::MAX - 1000 and 11_001
//   wrap to 10_000) -> NotEnoughFunds check passes; tx_outs total ~u64::MAX*2
//   >> inputs; stx.fee() then underflows: sum(inputs) - sum(outputs)
```

Specifically `payments = [(a, u64::MAX), (b, 11_000)]` gives `payment_sat == 10_999` (wrapped), which passes `input_sat < payment_sat + needed_fee` for a small real input, while the constructed `tx_outs` request ~u64::MAX in outputs — an invalid transaction that the FROST machine will happily sign a sighash for, after which `fee()` underflows.
