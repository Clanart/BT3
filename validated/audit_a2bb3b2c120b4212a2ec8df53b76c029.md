### Title
`SignableTransaction` fee calculation omits the `OP_RETURN` data output from transaction weight, underpaying the intended fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `AuraVault::totalAssets()` omitting unclaimed rewards from the asset total (causing every dependent computation — shares, assets — to be understated), `SignableTransaction::new` computes the required fee from a weight/vbytes measurement that omits the `OP_RETURN` output carrying user-supplied `data`. The output is pushed onto `tx_outs` before the weight is calculated, yet `calculate_weight_vbytes` is invoked with `payments` (the list without the data output), so `needed_fee` and the change amount are computed against a smaller transaction than the one actually constructed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` appends the `OP_RETURN` output to `tx_outs` when `data` is supplied, but then calculates `weight`/`vbytes` using only `payments`:

```rust
// data output added to tx_outs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
// weight measured WITHOUT the OP_RETURN output
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds a mock `Transaction` whose `output` list is built solely from `payments` (plus optional change), so the serialized length of the extra `OP_RETURN` output — which grows with `data` length — is never included. The same omission occurs in the change branch, which again passes `payments` rather than `tx_outs`. Consequently:

- `needed_fee` is `fee_per_vbyte * vbytes` for a transaction smaller than the real one.
- The change amount is `input_sat - payment_sat - fee_with_change`, so the *actual* fee paid equals that underestimated `needed_fee`, while the real vsize is larger.

Like `totalAssets()` returning `balanceOf` without `earned`, the "total" (vbytes) fed into every downstream value (fee, change) is missing a real component.

### Impact Explanation
Any caller of `SignableTransaction::new` that supplies `data` produces a transaction whose effective fee rate is strictly below `fee_per_vbyte`. With a large `data` payload (the code only bounds it via `PushBytesBuf` limits) the gap is arbitrarily large. Two concrete harms:

- The check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` is evaluated on the understated `vbytes`, so a transaction can pass that check yet broadcast at a fee rate below the minimum relay fee and be rejected/never relayed.
- Even if relayed, the transaction pays less than the requested rate, making confirmation unreliable and the "change" output over-credited relative to the true cost — funds are misreported as change when they should have been fee.

This is reachable by any unprivileged caller of the wallet API, since `data` is an untrusted public input to `SignableTransaction::new` (e.g., a user embedding arbitrary bytes). It yields funds that are reported allocated (change/fee math) but result in a non-spendable/non-relayable transaction — a Medium-severity economic discrepancy, matching the report's "incorrect share/asset calculation" class.

### Likelihood Explanation
The bug triggers deterministically whenever `data: Some(_)` is passed: the miscalculation does not depend on timing, other actors, or edge cases. The only attenuating factor is that Serai's own processor passes `data: None`, so exploitation requires integrator/user use of the data path — but that path is a public, documented parameter, not misuse.

### Recommendation
Compute weight over the actual output set being constructed. Pass `tx_outs`' script pubkeys (or include the OP_RETURN output explicitly) to `calculate_weight_vbytes` in both call sites:

```diff
- let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
+ let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), &tx_outs_scripts, None);
```

and similarly for the `fee_with_change` computation at the change branch, so the measured transaction matches the one placed in `SignableTransaction.tx`.

### Proof of Concept
1. Construct inputs with `input_sat` and payments such that `input_sat == payment_sat + fee_per_vbyte * vbytes_real`, where `vbytes_real` includes a large `data` payload.
2. Call `SignableTransaction::new(inputs, payments, None, Some(large_data), fee_per_vbyte)`.
3. `needed_fee` is computed against `vbytes` excluding the OP_RETURN output; `fee()` (`prevouts - outputs`) equals that underestimated value.
4. `tx.vsize() > vbytes`; the effective rate `fee() / tx.vsize() < fee_per_vbyte`. For sufficiently large `data`, it falls below `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction that passes `new`'s checks yet is non-standard/non-relayable — the analog of shares/assets minted from a `totalAssets()` that omitted unclaimed rewards.
