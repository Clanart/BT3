### Title
Unbounded EIP-7702 authorization-list loop in `EVMPreprocessDecorator.associateAuthorizationAuthorities` runs with an infinite gas meter in the ante handler - ([File: x/evm/ante/preprocess.go])

### Summary
Every EVM transaction goes through `EVMPreprocessDecorator.AnteHandle`, which first sets the context gas meter to infinite (`ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))`) and then, for `SetCodeTx` (EIP-7702) transactions, iterates over *all* authorization tuples in the transaction with `for _, auth := range ethTx.SetCodeAuthorizations()`, performing signature recovery and a state-write association attempt (via a cache context) for each one. [1](#0-0) [2](#0-1) 

### Finding Description
This is structurally the same bug class as the reported `MainRewarder._processRewards` issue: a loop over a caller-controlled array (`extraRewards` there, `SetCodeAuthorizations()` here) that grows the cost of a single call linearly with array length, with no explicit cap on the loop iteration count in this function.

Here, the loop runs unconditionally for every `SetCodeTx` submitted by any transaction sender (an unprivileged, single-transaction reachable path), during the ante pipeline (`CheckTx` and `DeliverTx`), which is executed on every full node/validator that processes the transaction. Each iteration:
1. Calls `helpers.AuthorityToPreAssociate`, which recovers the signer address (an ECDSA recover, i.e., `ecrecover`-equivalent CPU-bound operation) from the authorization tuple.
2. On success, opens a `ctx.CacheContext()` and calls `associateHelper.AssociateAddresses(...)`, a state-touching operation (account/address-mapping writes), then conditionally commits with `write()`.

Crucially, this all happens *after* the gas meter was switched to an infinite gas meter (line 65), meaning the EVM's own per-authorization gas accounting (`PER_EMPTY_ACCOUNT_COST` in EIP-7702) does not bound this ante-time work — the number of authorizations is limited only by transaction size/gas-limit checks applied elsewhere (e.g. block gas limit for calldata), not by an explicit cap in this loop itself.

### Impact Explanation
Because the loop executes signature recovery and cache-context state operations per authorization with no explicit bound checked in `associateAuthorizationAuthorities`, a transaction with a very large `authorization_list` can make ante-handler processing disproportionately expensive relative to its priced gas, since this work runs under an infinite gas meter. If the number of authorizations that can be packed into a single transaction is large enough (bounded only by block/tx size limits rather than this function's own gas-metered cost), this could measurably slow down `CheckTx`/`DeliverTx` processing across nodes, contributing to block-processing delay. This matches the reported bug class (unbounded loop → DoS/high gas cost) but the severity is capped by whatever transaction-size/mempool limits exist elsewhere in the stack, which I was not able to fully confirm before running out of tool calls.

### Likelihood Explanation
Likelihood is limited by two unconfirmed factors that I could not verify given the remaining budget: (1) whether an explicit cap exists elsewhere in the codebase (e.g., `semantic_validation.go` referenced `AuthList`/`authorizationList` matches) that bounds the number of authorizations per `SetCodeTx` before it reaches the ante handler, and (2) the real-world cost multiplier of `ecrecover` + cache-context writes per authorization at scale. Because of this uncertainty, I cannot confidently assert this crosses the "Medium/High" bar (e.g., causing >2.5s block delay) without further investigation into `x/evm/types/ethtx/semantic_validation.go` and mempool/tx-size limits, which reference `AuthList` but whose bounding logic I did not get to read in full.

### Recommendation
- Enforce and verify an explicit maximum authorization-list length in `associateAuthorizationAuthorities` (or upstream in `PreprocessUnpacked`/semantic validation) before iterating, independent of any go-ethereum-side EVM gas accounting, since this ante-time loop is unmetered by the transaction's own gas.
- Consider bounding or gas-metering the pre-association loop itself (e.g., consume gas per authorization from a real, finite meter before switching to the infinite meter, or count against a hard constant cap) so a large `authorization_list` cannot make ante-handler processing disproportionately expensive.

### Proof of Concept
Not independently verified with a live cap check due to tool budget exhaustion; the reasoning is based on the following observed code path:
1. Attacker crafts and submits an EIP-7702 `SetCodeTx` (`x/evm/types/ethtx/set_code_tx.go`) with as many entries in `authorization_list` as transaction-size/block-gas limits allow.
2. The transaction enters the ante pipeline; `EVMPreprocessDecorator.AnteHandle` sets an infinite gas meter, then calls `associateAuthorizationAuthorities`. [3](#0-2) 
3. The function loops over every authorization, performing signature recovery and a cache-context state write attempt per entry, with no bound-check visible in this function. [4](#0-3) 

**Uncertainty flag:** I was unable to confirm within the remaining tool budget whether `x/evm/types/ethtx/semantic_validation.go` (which references `AuthList`) already imposes a hard cap on authorization-list length before this ante code runs. If such a cap exists and is sufficiently small, this finding would be downgraded to informational/no-impact. func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
```go
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
```
