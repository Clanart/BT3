### Title
Tokenfactory denom AllowList restriction bypassed via EVM bank precompile and CosmWasm bank sends - ([File: precompiles/bank/bank.go])

### Summary
Tokenfactory allows a denom creator to attach a `Denom.AllowList` restricting which addresses may send or hold that denom [4](#0-3) . This restriction is enforced by explicit `IsInDenomAllowList` checks that were added only to the Cosmos SDK `x/bank` `MsgSend`/`MsgMultiSend` message handlers [5](#0-4) . The check is not embedded in the lower-level `BaseSendKeeper.SendCoins`/`SendCoinsAndWei` functions that actually move balances [6](#0-5) . Because the allowlist gate lives only at the outer `msg_server.go` layer (the analog of `DisableForwarding=yes` being applied in only one code path), any other transaction-reachable entry point that calls `SendCoins`/`SendCoinsAndWei` directly bypasses the restriction entirely — exactly like `PermitTunnel` silently overriding `DisableForwarding` in the CVE because the "disable" check wasn't applied at every reachable path.

### Finding Description
Two concrete unprivileged, transaction-reachable bypasses exist:

1. **EVM bank precompile `sendNative`**: an EVM contract/EOA holding a restricted tokenfactory denom (represented as `usei`/`wei` value inside the precompile call) can call `sendNative(address)` on the bank precompile (`0x...1001`). This handler calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly, with no call to `IsInDenomAllowList` anywhere in the precompile. [7](#0-6)  Since this pattern is repeated across every legacy precompile version, the bypass exists for the entire deployed history of the precompile. [8](#0-7) 

2. **CosmWasm contract `BankMsg::Send`**: wasmd's `BankCoinTransferrer.TransferCoins`, used to dispatch `CosmosMsg::Bank(BankMsg::Send)` from any CosmWasm contract, only checks `IsSendEnabledCoins` and `BlockedAddr` before calling `c.keeper.SendCoins(...)` — it never calls `IsInDenomAllowList`. [3](#0-2)  Any CosmWasm contract can therefore move a restricted tokenfactory denom to/from an address that is not on the denom's allowlist.

By contrast, the intended restriction is proven to work only through the SDK message path: `TestSendReceiverNotInAllowList` and `TestSendCoinsWithAllowList`/`TestMultiSendAllowList` show enforcement solely for `MsgSend`/`MsgMultiSend`. [9](#0-8) [10](#0-9) 

### Impact Explanation
A tokenfactory denom creator's allowlist is a security control meant to restrict transfers of a compliance-sensitive or permissioned asset (e.g., only KYC'd addresses). By routing the transfer through the EVM bank precompile (`sendNative`) or a CosmWasm contract's `BankMsg::Send`, any holder of the restricted denom can send it to — or receive it from — an address that was never authorized by the denom admin, defeating the entire purpose of the allowlist. This is an unauthorized-transfer/access-control-bypass class issue reachable from a plain EVM transaction or a CosmWasm contract call, matching the "unauthorized transfer via precompile or pointer" impact category.

### Likelihood Explanation
High likelihood: no special privileges are required — any address holding a restricted tokenfactory denom balance and any EVM address, or any deployed CosmWasm contract capable of emitting a `BankMsg::Send`, can trigger this path in a single transaction. The bug is a straightforward missing-check omission that is consistent across every version of the bank precompile examined.

### Recommendation
Move the `IsInDenomAllowList` (and ideally also `BlockedAddr`) checks into the shared `BaseSendKeeper.SendCoins`/`SendCoinsAndWei` implementations (or into a common `SendRestrictionFn` hook invoked by all transfer paths) so that every caller — `msg_server.go`, the EVM bank precompile's `sendNative`/`send`, and wasmd's `BankCoinTransferrer` — enforces the same allowlist regardless of entry point.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/<admin>/restricted` and sets `SetDenomAllowList(ctx, denom, AllowList{Addresses: [addrA, addrB]})`, then mints/sends balance to `addrA`.
2. `addrA` associates its Sei address with an EVM address and calls the bank precompile's `sendNative(addrC)` (where `addrC` is not in the allowlist) with the restricted denom's usei/wei value. `PrecompileExecutor.sendNative` calls `bankKeeper.SendCoinsAndWei` directly with no allowlist check, so the transfer to `addrC` succeeds. [7](#0-6) 
3. Equivalently, deploy a CosmWasm contract holding the restricted denom and have it emit `CosmosMsg::Bank(BankMsg::Send{to_address: addrC, ...})`; `BankCoinTransferrer.TransferCoins` moves the funds to `addrC` without consulting `IsInDenomAllowList`. [3](#0-2) 
4. In both cases the transfer to the disallowed address succeeds, whereas the equivalent `MsgSend`/`MsgMultiSend` via the standard bank message server would be rejected with "is not allowed to receive funds". [11](#0-10)

	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
