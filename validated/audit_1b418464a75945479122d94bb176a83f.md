## Finding: Valid

### Title
Unvalidated `shell.openExternal` Call Allows Arbitrary URI Scheme Launch via Attacker-Controlled Check-Run `htmlUrl` - (File: `app/src/main-process/main.ts`)

### Summary
The `open-external` IPC handler in the main process only *logs* when a URL starts with `http://`/`https://` but does not reject or sanitize any other scheme before calling `shell.openExternal`. An attacker-controlled `htmlUrl` field on a check-run/job-step object (sourced from the GitHub Checks/Actions API) flows unmodified from `getCheckRunStepURL` through `dispatcher.openInBrowser` and the `openExternal` IPC proxy into this handler, letting a crafted API object trigger `shell.openExternal` with an arbitrary custom URI scheme.

### Finding Description
`ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts` performs a case-insensitive prefix check only to decide whether to write an info log line; it never branches on the result to block anything, and unconditionally calls `shell.openExternal(path)` afterward: [1](#0-0) 

On the renderer side, `openExternal` is a thin IPC proxy with no scheme filtering: [2](#0-1) 

The URL reaching this call for job steps is built by `getCheckRunStepURL`, which concatenates the check run's `htmlUrl` (a field populated from the GitHub Actions/Checks API response, e.g., `matchingJob.html_url` in `getLatestPRWorkflowRunsLogsForCheckRun`) with a step fragment, with no validation of the scheme: [3](#0-2) [4](#0-3) 

`CICheckRunPopover.onViewJobStep` (and the equivalent handler in `pull-request-checks-failed.tsx`) passes this URL straight to `dispatcher.openInBrowser`, which ultimately invokes the `open-external` IPC channel: [5](#0-4) [6](#0-5) 

Because `htmlUrl` for check runs is populated from third-party Check Runs API objects (any GitHub App with check-run write access to a repository can set an arbitrary `details_url`/`html_url`), a malicious or compromised check-run/app author can set `htmlUrl` to a non-http(s) URI such as `myapp://exploit` or a Windows search/`ms-` handler URI. That value survives unmodified to `shell.openExternal`.

### Impact Explanation
`shell.openExternal` with an attacker-chosen, unrestricted scheme can invoke any URI handler registered on the host OS. Depending on what handlers are installed (e.g., vulnerable custom protocol handlers used by other installed applications, `ms-search:`/`search-ms:`-style handlers on Windows historically used to open arbitrary UNC/file paths, or other IPC-capable app protocol handlers), this can lead to unintended local application execution or file access outside GitHub Desktop's control. This aligns with the "code execution / renderer-sandbox escape via IPC" impact category since the vulnerable sink is a privileged main-process IPC handler with no allow-list.

### Likelihood Explanation
Reaching the sink requires the attacker to control a check-run object's `htmlUrl`/`details_url` (achievable via a GitHub App or CI integration with check-run write permission on a repo, which is a realistic actor for a "PR checks" attack surface) and requires the user to click "View job step" in the CI checks popover or the "Checks failed" notification. No other confirmation/allow-listing exists between the click and `shell.openExternal`.

### Recommendation
In `app/src/main-process/main.ts`'s `open-external` handler, actively reject (return `false`/throw) for any URL whose scheme is not `http:`/`https:` (and any other explicitly-supported scheme), rather than only logging. Alternatively/additionally, validate and allow-list the scheme in `getCheckRunStepURL` / `onViewCheckDetails` / `onViewJobStep` before calling `dispatcher.openInBrowser`, so only `http(s)` URLs pointing at expected hosts (e.g., `github.com`/enterprise host) are ever passed to `shell.openExternal`.

### Proof of Concept
1. Simulate an API response where a check run's job step has `matchingJob.html_url = 'myapp://exploit'` (as set in `getLatestPRWorkflowRunsLogsForCheckRun`, `app/src/lib/ci-checks/ci-checks.ts:349-353`).
2. `getCheckRunStepURL(checkRun, step, repository, prNumber)` returns `'myapp://exploit/#step:1:1'` (`app/src/lib/ci-checks/ci-checks.ts:582-588`) since it does not validate the scheme.
3. User clicks a job step in the CI checks popover, triggering `CICheckRunPopover.onViewJobStep` (`app/src/ui/check-runs/ci-check-run-popover.tsx:171-183`), which calls `dispatcher.openInBrowser(url)`.
4. This resolves to the `open-external` IPC call, and `ipcMain.handle('open-external', ...)` in `app/src/main-process/main.ts:581-597` calls `shell.openExternal('myapp://exploit/#step:1:1')` unconditionally — the `http(s)` check only affects logging, not execution.

```typescript
export function getCheckRunStepURL(
  checkRun: IRefCheck,
  step: IAPIWorkflowJobStep,
  repository: GitHubRepository,
  pullRequestNumber: number
): string | null {
  if (checkRun.htmlUrl === null && repository.htmlURL === null) {
    // A check run may not have a url depending on how it is setup.
    // However, the repository should have one; Thus, we shouldn't hit this
    return null
  }

  const url =
    checkRun.htmlUrl !== null
      ? `${checkRun.htmlUrl}/#step:${step.number}:1`
      : `${repository.htmlURL}/pull/${pullRequestNumber}`

  return url
}
```
