### Title
Identity public keys enable universal Schnorr signature forgery - (File: crypto/schnorr/src/lib.rs)

### Summary
`SchnorrSignature::verify` does not reject the identity public key or identity nonce commitment. The verification equation `R + cA - sG = 0` degenerates when `A` is identity, allowing anyone to choose an arbitrary scalar `r`, set `R = rG` and `s = r`, and produce an accepted signature for any challenge. `SchnorrSignature::read` parses both components but likewise performs no semantic public-key validation because the supplied public key is passed separately. [1](#0-0) [2](#0-1) 

### Finding Description
The signature reader accepts a caller-controlled encoded point for `R` and scalar for `s`, while `verify` accepts a caller-controlled `public_key`. Neither API enforces that the public key is a non-identity group element. Unlike FROST's `Curve::read_G`, which explicitly rejects identity points, this API operates on the more general `Ciphersuite` trait and relies entirely on the three-term verification equation. [3](#0-2) [4](#0-3) 

For an identity public key `A = 0`, verification reduces to checking `R - sG = 0`. An attacker therefore controls the remaining equality directly: choose `r`, compute `R = rG`, and submit `(R, r)`. The challenge is multiplied by the identity key and contributes nothing. [5](#0-4) 

### Impact Explanation
Any protocol that admits an attacker-supplied or improperly validated identity Schnorr public key accepts a forged signature for every message and challenge. This is not merely a malformed encoding rejection issue: the serialized forged signature contains a valid non-identity `R` and canonical scalar `s`; the vulnerability is the missing semantic validity check on the public key used by the verifier. [6](#0-5) 

### Likelihood Explanation
An unprivileged party can reach the vulnerable path by submitting `SchnorrSignature::read` bytes and causing verification against an identity key accepted from an untrusted key registry, proof statement, participant message, or deserialized object. The attack requires no private key, discrete-log knowledge, timing condition, or malformed field encoding. Exploitation is limited to integrations that fail to reject identity public keys before calling `verify`, so the appropriate severity is Medium unless such keys are actually admissible in a production caller. [7](#0-6) 

### Recommendation
Reject identity public keys in `SchnorrSignature::verify` and `batch_statements`, or provide a mandatory checked public-key constructor/deserializer that callers must use. Also consider rejecting identity `R` for strict signature semantics, although the public-key check alone prevents the universal forgery described here. Add a regression test asserting that every `(R = rG, s = r)` forgery fails against `C::G::identity()` for arbitrary challenges. [8](#0-7) 

### Proof of Concept
```rust
use zeroize::Zeroizing;
use group::{Group, ff::Field};

fn forge_for_identity_key<C: ciphersuite::Ciphersuite>(challenge: C::F) {
    let public_key = C::G::identity();

    // Choose an arbitrary scalar. A nonzero scalar is used only for clarity;
    // r = 0, R = 0, s = 0 also satisfies the degenerate equation.
    let r = C::F::random(&mut rand_core::OsRng);
    let signature = SchnorrSignature::<C> {
        R: C::generator() * r,
        s: r,
    };

    // Equation checked by verify:
    //   R + cA - sG
    // = rG + c * 0 - rG
    // = 0
    assert!(signature.verify(public_key, challenge));

    // The same forged signature can be supplied through the public byte API
    // because its R and s encodings are canonical.
    let encoded = signature.serialize();
    let parsed = SchnorrSignature::<C>::read(&mut encoded.as_slice()).unwrap();
    assert!(parsed.verify(public_key, challenge));
}
```

The verifier evaluates `R + cA - sG`; with `A = 0`, the forged pair `(rG, r)` always sums to identity regardless of `challenge`. [5](#0-4)
