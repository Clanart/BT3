Confirmed: `DeleteAddressMapping` writes directly to the KVStore in `SelfDestruct` and is **not journaled**, while every other piece of state that `SelfDestruct` touches (balance via `SubBalance`, account status via `MarkAccount`) is journaled and revertible. This is the same bug class as the reported CVE: an object (here, the EVM↔Sei address association) is torn down/removed from its lookup registry outside of the transaction's undo/commit discipline, so a later abort or revert leaves the removal in effect while everything else rolls back — producing a permanently corrupted, inconsistent registry entry reachable directly by a contract calling `SELFDESTRUCT`.

### Title
Unrevertable address-association deletion on SELFDESTRUCT causes permanent Sei↔EVM mapping loss on transaction/call revert - (File: x/evm/state/state.go)

### Summary
`DBImpl.SelfDestruct` calls `s.k.DeleteAddressMapping(s.ctx, seiAddr, acc)` directly against the store, without creating a journal entry. Every other state mutation performed inside `SelfDestruct` (`SubBalance`, `MarkAccount`) is journaled via `s.journal = append(...)` and is undone by `RevertToSnapshot`. The address-mapping deletion is not, so if the self-destructing call frame is later reverted (e.g., an outer call reverts, a subsequent statement in the same transaction fails, or the EVM call stack unwinds due to an error after the `SELFDESTRUCT` opcode executes), the account's `AccountDeleted` status and balance are correctly restored by the journal, but its EVM↔Sei address association remains permanently deleted.

### Finding Description
`SelfDestruct` in [1](#0-0)  performs:
1. `GetSeiAddress` / `DeleteAddressMapping` — direct, unjournaled store writes.
2. `SubBalance` — journaled (go-ethereum's tracing/journal integration records balance changes, undoable).
3. `MarkAccount(acc, AccountDeleted)` — explicitly journaled via `accountStatusChange`, see [2](#0-1)  and its revert handler [3](#0-2) .

`RevertToSnapshot` walks the journal in reverse and calls `entry.revert(s)` for each entry to undo state back to a snapshot [4](#0-3) . Because `DeleteAddressMapping` never appended a journal entry, no `revert` call can restore the deleted `EVMAddressToSeiAddressKey` / `SeiAddressToEVMAddressKey` mapping. This mirrors the reported kernel bug class exactly: a lookup-table entry removal that is not properly coordinated with the object's actual (reversible) teardown lifecycle, so a party that later looks up the "torn-down" identifier finds it permanently gone even though the surrounding operation didn't actually complete/commit.

`DeleteAddressMapping` itself is a direct two-key store delete with no compensating logic [5](#0-4) .

### Impact Explanation
An address association is the sole binding between a user's EVM address and their true, pubkey-derived Sei address; it gates fund transfers to that account (`CanAddressReceive` checks it), and governs how that account interacts with the bank/staking/tokenfactory subsystem going forward. If this association is deleted as a side effect of a `SELFDESTRUCT` executed inside a call that ultimately reverts (or inside one transaction/message among several batched atomically, e.g., a Cosmos multi-message tx executing an EVM tx then failing on a later message and reverting the whole tx, or nested calls where an outer revert should have restored the destructed account), the account permanently loses its association. This can:
- Freeze funds: after the mapping is gone, sends to the account's cast address are blocked (`CanAddressReceive` treats it as un-associated) or funds are misrouted to the raw EVM-derived cast address instead of the true owner's Sei address, since the direct-cast/real-address disambiguation depends entirely on this mapping.
- Force the affected user through the costly, and not always available, re-association flow, and can corrupt validator/staking/distribution bookkeeping tied to that identity (a scenario the codebase's own comments flag elsewhere as capable of halting the chain — see the SetCode/authority association comments in `x/evm/ante/preprocess.go`).

This satisfies "permanent freezing" of funds / identity for the affected account, triggered purely by a transaction that legitimately reverts a `SELFDESTRUCT`.

### Likelihood Explanation
Any EVM contract account that (a) has an active address association (i.e., was created via/associated with a real Sei pubkey) and (b) executes `SELFDESTRUCT` inside a code path that can revert (e.g., a `CALL` whose caller uses `try/catch`-style low-level call and reverts a wrapping frame, or a batched Cosmos transaction where the EVM message succeeds but a later message in the same atomic transaction fails) triggers this. No special privilege is needed — any transaction sender/contract deployer can construct and execute such a call. This is reachable purely from EVM bytecode with a `SELFDESTRUCT` opcode inside a revertible sub-call.

### Recommendation
Journal the address-association deletion the same way `MarkAccount`/`SubBalance` are journaled: introduce an `addressMappingChange` journal entry in `SelfDestruct` that records the deleted `(seiAddr, evmAddr)` pair, and implement its `revert` to call `k.SetAddressMapping` (restoring the mapping) if the enclosing snapshot is rolled back. Apply the same audit to any other direct, unjournaled keeper writes performed from `DBImpl` methods that are supposed to participate in EVM call-frame revert semantics.

### Proof of Concept
1. Associate a Sei address with an EVM address via the `addr` precompile or an EVM tx (`SetAddressMapping` invoked), so `GetSeiAddress(evmAddr)` returns `(seiAddr, true)`.
2. Deploy a contract at `evmAddr` (or have that address be a contract account) whose code executes `SELFDESTRUCT`.
3. From another contract, `CALL` into this self-destructing contract, then deliberately revert the outer call (e.g., via a subsequent `REVERT` opcode in the calling frame after the sub-call returns), so that from the EVM's perspective the self-destruct never took effect and `RevertToSnapshot` is invoked for that call depth.
4. After the transaction is applied, query `GetSeiAddress(evmAddr)` / `GetEVMAddress(seiAddr)`: the mapping is missing even though the account's balance and `AccountDeleted` status were correctly restored by the journal — demonstrating the desynchronized, unrevertable side effect.

func (s *DBImpl) SelfDestruct(acc common.Address) uint256.Int {
	s.k.PrepareReplayedAddr(s.ctx, acc)
	if seiAddr, ok := s.k.GetSeiAddress(s.ctx, acc); ok {
		// remove the association
		s.k.DeleteAddressMapping(s.ctx, seiAddr, acc)
	}
	b := s.GetBalance(acc)
	s.SubBalance(acc, b, tracing.BalanceDecreaseSelfdestruct)

	// mark account as self-destructed
	s.MarkAccount(acc, AccountDeleted)
	return *b
}

func (s *DBImpl) RevertToSnapshot(rev int) {
	// Add bounds checking
	if rev < 0 || rev >= len(s.snapshottedCtxs) {
		panic("invalid revision number")
	}

	s.ctx = s.snapshottedCtxs[rev]
	s.snapshottedCtxs = s.snapshottedCtxs[:rev]

	// The layer we just re-exposed becomes the writable top again, so it must no
	// longer be treated as a frozen (skippable) layer: writes may now land here,
	// and Snapshot() froze it when it was superseded. Unfreezing also drops the
	// skip on any store whose parent is this layer, so reads see the new writes.
	if f, ok := s.ctx.MultiStore().(interface{ Unfreeze() }); ok {
		f.Unfreeze()
	}

	// Find the watermark index to truncate the journal
	watermarkIndex := -1
	for i := len(s.journal) - 1; i >= 0; i-- {
		entry := s.journal[i]
		entry.revert(s)
		if wm, ok := entry.(*watermark); ok && wm.version == rev {
			watermarkIndex = i
			break
		}
	}

	// Truncate the journal to remove reverted entries. codeCache mutations are
	// journaled per address (codeCacheChange), so unrelated warmed entries survive.
	if watermarkIndex >= 0 {
		s.journal = s.journal[:watermarkIndex]
	}
}

func (s *DBImpl) MarkAccount(acc common.Address, status []byte) {
	prev, ok := s.tempState.transientAccounts[acc.Hex()]
	if !ok {
		prev = nil
	}
	s.tempState.transientAccounts[acc.Hex()] = status
	s.journal = append(s.journal, &accountStatusChange{account: acc, prev: prev})
}

func (e *accountStatusChange) revert(s *DBImpl) {
	accts := s.tempState.transientAccounts
	if e.prev == nil {
		delete(accts, e.account.Hex())
	} else {
		accts[e.account.Hex()] = e.prev
	}
}
