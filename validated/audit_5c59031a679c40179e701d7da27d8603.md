### Title
Unattributable panic on duplicate/unregistered DKG encryption-key messages crashes honest participants - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

The external report describes a fault that escapes the protocol's attributable-error path (`FailedOpWithRevert`): an untrusted party supplies bytes that decode-fail outside the `try/catch`, so the caller aborts without being able to blame the sender. The same shape exists in Serai's PedPoP DKG: `Decryption::register` and `Decryption::decrypt_with_proof` cross a trust boundary (a deserialized `EncryptionKeyMessage` / `EncryptionKeyProof` from another participant) and then hit `assert!`/unchecked `HashMap` indexing that panic instead of returning an attributable `io::Error`. A malicious participant sending a second `EncryptionKeyMessage` (or triggering blame against a participant whose key was never registered) causes an uncatchable panic in the victim's DKG process rather than a `Participant`-attributed fault.

### Finding Description

`Decryption::register` panics on re-registration instead of returning an error identifying the faulty participant:

```rust
// crypto/dkg/pedpop/src/encryption.rs:356-359
assert!(
  !self.enc_keys.contains_key(&participant),
  "Re-registering encryption key for a participant"
);
self.enc_keys.insert(participant, msg.enc_key);
```

`participant` is the claimed sender index attached to the peer-supplied `EncryptionKeyMessage` (read via `EncryptionKeyMessage::read` at `encryption.rs:57`, which itself only returns `io::Result` for malformed bytes). Because `register` is invoked once per received registration message, a participant who submits two registration messages — or whose message is replayed — converts a peer-attributable fault into a process-aborting panic. Like the report's `validatePaymasterUserOp` revert, the failure happens *after* the byte-level decode succeeded, at the semantic-handling boundary, and bypasses every `io::Result`/`DkgError` path designed to carry blame.

The same unchecked-index pattern appears in `decrypt_with_proof` (`encryption.rs:388`), where `self.enc_keys[&decryptor]` panics if the accused decryptor never successfully registered an encryption key — reachable during blame resolution when a participant's registration message was malformed or never delivered. `Encryption::encrypt` (`encryption.rs:466`) has an identical `enc_keys[&participant]` index.

### Impact Explanation

An unprivileged DKG participant can crash an honest participant's node with a duplicate registration message, or trigger a panic during the blame/decryption protocol. This aborts the DKG without producing a `Participant`-tagged error, so the victim (and any orchestrating layer) cannot programmatically attribute the fault — the exact harm class of the reference bug (fault escapes the error-reporting channel, forcing expensive re-runs / manual log inspection). During DKG this means an attacker can repeatedly abort key-generation sessions; during blame it can prevent `ThresholdKeys`/share recovery for the accused session. This is a Medium-severity liveliness/attributability defect; I did not find a path to signature forgery or share recovery from this specific class — the panic occurs before any secret material is produced to the attacker.

### Likelihood Explanation

High reachability, moderate impact. The trigger is a single extra protocol message (a repeated `EncryptionKeyMessage`), which any session participant can send. The only mitigations are external: the caller would have to pre-filter duplicate senders, and the DKG networking layer would have to catch the panic. The in-scope code documents that "if any participant sends multiple sets of commitments, they are faulty" (`crypto/dkg/pedpop/src/lib.rs:98-101`) yet enforces this via `assert!`, i.e., a panic the library explicitly tries to avoid elsewhere ("this library is expected not to panic", `crypto/frost/src/curve/mod.rs:88`).

### Recommendation

Replace the `assert!` in `Decryption::register` with an `Err`/`Option` return (or an overwrite-rejecting `Result<M, DkgError::DuplicatedParticipant>`-style error) so the caller can attribute the fault to `participant`. Similarly, replace `self.enc_keys[&decryptor]` and `enc_keys[&participant]` indexing with `.get()` + error propagation, returning a typed error naming the missing participant. Pattern-wise, this mirrors the report's recommendation: check preconditions explicitly at the boundary instead of relying on a panic/revert that escapes the attributable-error channel.

### Proof of Concept

1. Participant `k` sends a valid `EncryptionKeyMessage` (parses via `EncryptionKeyMessage::read`, `encryption.rs:57-58`) and the victim calls `register(k, msg)`, inserting `enc_keys[k]`.
2. Participant `k` sends a second `EncryptionKeyMessage` (any valid encoding; the bytes decode fine, so no `io::Error` is produced).
3. The victim calls `register(k, msg2)`; `assert!(!self.enc_keys.contains_key(&k))` at `encryption.rs:356-359` fails and panics, unwinding/aborting the victim's DKG task with no `Participant`-attributed error — analogous to the uncatchable revert that bypasses `FailedOpWithRevert`.

Blame-path variant: a participant is accused before their `EncryptionKeyMessage` is registered (e.g., they sent a malformed one that `read` rejected). `decrypt_with_proof` at `encryption.rs:388` evaluates `self.enc_keys[&decryptor]` and panics on the missing key instead of returning `DecryptionError`, crashing the blame resolution flow.

Caveat: I verified the panic sites in `encryption.rs` and the message-read entry points; the exact call chain from the pedpop session driver (`crypto/dkg/pedpop/src/lib.rs`) into `register`/`decrypt_with_proof` was not fully traced, so the precise framing of where the panic is caught (if at all) by an embedding caller is partially inferred.
