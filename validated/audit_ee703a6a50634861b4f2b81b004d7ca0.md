### Title
Missing hunk-count validation lets crafted conflict-marker content in a repository silently corrupt what Copilot writes and commits - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The 1inch bug came from trusting an attacker-controlled recomputation without validating it against the invariant the taker actually asked for. The Desktop analog is in the "Resolve conflicts with Copilot" feature: the number of conflict hunks a model is asked to resolve (derived from parsing the on-disk conflict-marked file) is never cross-checked against the number of hunk resolutions actually spliced back into that same file. Because splicing is done "by order, not by line number," a mismatch between the count used when *extracting* hunks and the count encountered when *reassembling* them causes resolved content to land in the wrong conflict block or causes conflict content to be silently dropped, and the corrupted result is then written to disk and `git add`-ed without any additional integrity check.

### Finding Description
`buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` reads each conflicted file's raw content from disk and extracts conflict hunks to send to the model: [1](#0-0) 

The model returns a JSON payload with one `resolvedContent` entry per hunk. `parseCopilotConflictResolution` validates the *shape* of each hunk entry (it must be a string, must not still contain conflict markers) but never validates that the number of returned hunks for a file matches the number of conflicts actually present in that file: [2](#0-1) 

The actual application of the model's output happens in `reassembleResolvedFile`, which walks the raw on-disk content line-by-line and matches conflict marker blocks using its own independent regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`), splicing in `hunkResolutions[hunkIndex]` purely by encounter order: [3](#0-2) 

Note the explicit statement in the docstring: *"matched by order, not by line number"*, and that a malformed/stray `<<<<<<<` marker (no matching `=======`/`>>>>>>>`) is passed through as ordinary content rather than treated as an error. This means the effective hunk count used to build the model prompt (from `buildConflictContext`) and the effective hunk count used when splicing the model's answer back into the file (from `reassembleResolvedFile`) are computed by two independently-maintained pieces of logic operating over content that originates from the repository itself (i.e., from branches being merged/rebased, which can come from a remote, a fork, or a PR head the user is checking out). If a file in the repository contains conflict-marker-*like* sequences that are counted differently by the extraction path than by the reassembly path (e.g., additional bare `<<<<<<<`/`=======`/`>>>>>>>` sequences embedded in file content, unusual nesting, or edge cases in marker detection), the two counts diverge.

When `reassembleResolutions` combines the model's per-hunk output with the original raw content, it looks up the file context and reassembles without ever comparing `raw.hunks.length` to the actual number of conflict blocks in `ctx.rawContent`: [4](#0-3) 

If `hunkIndex >= hunkResolutions.length` for a later conflict block, `reassembleResolvedFile` simply removes the conflict markers and injects nothing for that block — silently deleting content — while conversely if the model returned more hunks than the file actually needs, the extra ones are dropped without any error, and any misalignment in the *middle* of the file (from a mismatched count) causes the wrong hunk's resolution to be spliced into the wrong location.

This corrupted content is then written straight to disk and staged for the user's commit with no further verification: [5](#0-4) 

### Impact Explanation
This lets a malicious or compromised repository/branch that the user merges, rebases, or cherry-picks against — content the attacker fully controls, satisfying the "attacker controls a cloned/fetched repository" bar — cause Desktop's AI-assisted conflict resolution to write code into a file at the wrong location or silently drop resolved lines, all while telling the user the conflicts were correctly resolved. The user then commits and pushes this corrupted result, believing it reflects their intended merge. This is a silent corruption of what the user commits/pushes, which is an explicitly valid impact category for this task.

### Likelihood Explanation
Exploitability depends on finding an input to the extraction path (`buildConflictContext`, not fully visible in the retrieved snippets) that is counted differently than the marker-detection regexes used in `reassembleResolvedFile`. I was not able to inspect the exact implementation of `extractConflictHunks` in this session, so I cannot confirm with certainty that its marker matching diverges from `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` for some crafted input — this is the main uncertainty in this finding. What is confirmed by the code is the structural weakness: there is no cross-check anywhere in the pipeline (`parseCopilotConflictResolution`, `validateResolutionPaths`, `reassembleResolutions`) that the number of hunk resolutions for a file equals the number of conflict blocks actually present in that file's raw content, which is exactly the missing "threshold/bounds check" pattern described in the 1inch report — the code recombines two independently-derived values without ever reconciling them.

### Recommendation
Add an explicit invariant check before reassembly: count the conflict marker blocks in `ctx.rawContent` using the same detection logic as `reassembleResolvedFile` and reject (or fall back to leaving the file unresolved with a clear error, similar to `CopilotValidationError`) if `raw.hunks.length` does not exactly equal that count for the given file, rather than silently splicing by order regardless of count. Ensure `buildConflictContext`'s hunk-extraction regex and `reassembleResolvedFile`'s marker regexes are implemented via one shared, single source of truth so they cannot diverge.

### Proof of Concept
Not independently verified end-to-end in this session because the exact hunk-counting logic inside `extractConflictHunks` (in `app/src/lib/copilot-conflict-context.ts`) was not available to inspect. The verifiable part of the chain is:
1. A repository is set up with a real merge/rebase conflict in a file, plus additional attacker-authored lines elsewhere in the same file that resemble conflict markers (e.g., stray `<<<<<<<`, `=======`, or `>>>>>>>` sequences that are not part of a real conflict block, or a malformed conflict block missing its closing marker).
2. If `buildConflictContext`'s hunk extraction counts these markers differently than the `reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker` regexes in `reassembleResolvedFile`, the model is prompted with a hunk list that doesn't line up 1:1 with what `reassembleResolvedFile` will later encounter.
3. `reassembleResolutions` → `reassembleResolvedFile` splices resolutions "by order, not by line number" per [6](#0-5) , so a divergent count causes wrong-location splicing or silent content loss when `hunkIndex >= hunkResolutions.length`.
4. `_applyCopilotConflictResolutions` writes this result directly to disk and stages it for commit per [7](#0-6) , with no post-write integrity check.

Because I could not confirm the divergence in step 2 against `extractConflictHunks`'s actual implementation, this should be treated as a structurally-confirmed missing-invariant finding rather than a fully demonstrated exploit; a Desktop engineer with full repo access should inspect `extractConflictHunks` directly to confirm or rule out the marker-counting mismatch.

// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
