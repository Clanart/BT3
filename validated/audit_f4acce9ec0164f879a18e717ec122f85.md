### Title
Cross-validator-set DKG confirmation reuses cached FROST preprocess - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores encrypted FROST preprocess seeds in `CachedPreprocesses` using only `self.context` as the database key. `DkgConfirmer` sets that context to `(b"DkgConfirmer", self.attempt)`, omitting the tributary genesis, validator-set/network identity, participant roster, generated `KeyPair`, and message. If the same coordinator participates in more than one DKG confirmation context with the same attempt number, the second execution loads the first context’s cached seed and deterministically regenerates the same FROST nonce material for a different signing session/message.

### Finding Description
`CachedPreprocesses` is keyed only by `context`. In `preprocess_internal`, the context is mixed with the local MuSig secret key to decrypt the stored seed, then `AlgorithmSignMachine::from_cache` reconstructs a FROST signing machine from it. `DkgConfirmer::signing_protocol` narrows the context to `(b"DkgConfirmer", self.attempt)`, while the actual signing operation is additionally parameterized by `self.spec`, its validator roster, `removed`, and `key_pair`. Those parameters affect both the MuSig threshold keys and the signed `set_keys_message`, but none are committed in the cache key.

This is analogous to a user-controlled session identifier indexing a process-global session store: the cache entry is not bound to the full protocol session that created it. A matching `(label, attempt)` from another DKG confirmation retrieves the prior seed rather than generating a fresh preprocess. `seeded_preprocess` deterministically derives nonce commitments and signing nonces from that seed, and `sign` later combines those nonces with binding factors and the caller-supplied message.

### Impact Explanation
FROST preprocess reuse can expose the signer’s secret contribution when the same nonce material is used for distinct signing sessions/messages. The code explicitly documents that cached preprocesses “MUST only be used once” and that reuse enables private-key-share recovery. Here, the protocol-level cache key fails to enforce that requirement across distinct validator-set confirmation sessions. Confirmation shares are published in `DkgConfirmed` transactions, so reused nonce/shares become publicly observable.

### Likelihood Explanation
A party does not need to compromise the coordinator database or send malformed cryptographic bytes. The prerequisite is causing or awaiting two DKG confirmation executions reachable by the same coordinator with equal `attempt` values but different sets/messages, such as separate validator-set/network DKGs sharing the same underlying coordinator DB. The design already treats `attempt` as only a per-protocol counter, not as a globally unique session identifier.

### Recommendation
Bind every cached preprocess to the complete signing session. At minimum, include the tributary genesis, validator-set specification/session/network, participant roster or MuSig transcript context, generated `KeyPair` or signed-message digest, and attempt in `CachedPreprocesses` key and encryption-key preimage. Alternatively, make the cache single-use by deleting the entry when loaded and refusing to sign again for the same context.

### Proof of Concept
1. Instantiate `DkgConfirmer` for validator-set `A` at attempt `0`.
2. Call `preprocess`/`share`; this stores a seed under `CachedPreprocesses` keyed by `(b"DkgConfirmer", 0)`.
3. Instantiate `DkgConfirmer` for validator-set `B` at attempt `0` in the same DB namespace, with a different validator roster and `KeyPair`.
4. Call `preprocess`/`share`; because the context is unchanged, it loads `A`’s cached seed and reconstructs deterministic nonce material rather than generating a fresh preprocess.
5. The two published confirmation shares are produced for different `set_keys_message` values while reusing the same cached FROST preprocess state, satisfying the nonce-reuse precondition for key-share recovery.
