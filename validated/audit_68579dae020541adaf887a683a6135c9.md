### Title
Missing lower-bound validation of signing-set participants causes a panic (DoS) in `AlgorithmSignMachine::sign` - (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmSignMachine::sign` builds the `included` signer set from the keys of the attacker-influenced `preprocesses` map, validates the maximum index and duplicates, but never validates the minimum index. A `Participant(0)` passes all checks and reaches `self.params.keys.view(included).unwrap()`, where `view`/`interpolation_factor` index `verification_shares` keyed only by `1 ..= n`, causing a panic — the Rust analog of the CVE-2022-3116 null-dereference crash class.

### Finding Description
In `crypto/frost/src/sign.rs` (lines 290–313):

```rust
included.sort_unstable();
if included.len() < usize::from(multisig_params.t()) { ... }          // t check
if u16::from(included[included.len() - 1]) > multisig_params.n() { ... } // upper bound only
for i in 0 .. (included.len() - 1) { /* dup check */ }
let view = self.params.keys.view(included.clone()).unwrap();
```

Only the upper bound (`<= n`) is enforced; `included[0]` may be `Participant(0)`. `ThresholdView`/`ThresholdCore` in `crypto/dkg/src/lib.rs` key `verification_shares` by `Participant::new(l)` for `l in 1 ..= n` (e.g., `original_verification_share`/`verification_share` index `self.verification_shares[&l]`, documented as panicking for invalid participants, lines 669–682). During `view()`/interpolation, resolving shares for `Participant(0)` hits a missing map key or an `Err` consumed by `unwrap()` — both panic.

`Participant` is SCALE-decoded from network/preprocess maps in downstream callers (e.g., `preprocesses: HashMap<Participant, _>`), and a derived `Decode` does not apply the `Participant::new` non-zero check, so an index-0 entry supplied by a remote signer reaches this path with otherwise-valid bytes.

### Impact Explanation
A single invalid signing-set entry deterministically panics the signing process mid-protocol. Every honest participant fed the malicious preprocess map crashes (or aborts via panic), denying signing of the transaction — an availability failure on a reachable code path, matching the reported null-deref crash class. Severity: Medium (DoS without secret leakage).

### Likelihood Explanation
Requires an attacker able to attach a preprocess/share keyed as `Participant(0)` into the `sign` map — i.e., control of an entry in the per-participant message map that honest code does not re-validate against `1 ..= n`. The library performs no zero-index rejection itself, so any caller that decodes participant indexes from peer messages without the `Participant::new` check is exposed. No key material, collusion, or malformed curve points are needed.

### Recommendation
In `AlgorithmSignMachine::sign`, reject any `included` member equal to `Participant(0)` / not constructible via `Participant::new`, and return `FrostError::InvalidParticipant` instead of relying on `view().unwrap()`. Also make `Participant`'s `Decode` implementation enforce the non-zero invariant so index 0 can never be deserialized.

### Proof of Concept
1. Create a `HashMap<Participant, Preprocess>` containing an entry under `Participant(0)` (constructible via SCALE `Decode` of `0u16`, which bypasses `Participant::new`).
2. Ensure `included.len() >= t` and max `<= n` so lines 298–310 pass.
3. Call `sign(preprocesses, msg)`. At line 312, `keys.view(included)` either returns `Err` (unwrapped → panic) or internally indexes `verification_shares[&Participant(0)]`, which is absent because shares exist only for `1 ..= n` (`crypto/dkg/src/lib.rs` lines 556–560, 620–623) → panic (`index out of bounds`/`unwrap on Err`).

Note: the exact panic site (`view` returning `Err` vs. a `HashMap` index panic inside interpolation) depends on `dkg` internals not fully indexed here; both outcomes are unrecoverable panics reachable from the unchecked `Participant(0)` input.
