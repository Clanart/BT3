Based on my research, the strongest local analog to the Alchemix "threshold computed as zero" griefing bug is the `challengePeriod` guard in the ISMP message handler, which is silently disabled whenever the value is `0`.

### Title
Challenge period value of `0` collapses the fraud-proof/veto window to zero, letting messages be finalized before fishermen can veto a fraudulent state commitment - (File: `evm/src/core/HandlerV2.sol`)

### Summary
The Alchemix report shows a threshold value that, when `0`, silently disables the protection it exists to provide (anyone becomes a "qualified" proposer). Hyperbridge has a structurally identical pattern: `challengePeriod` is meant to guarantee a mandatory waiting window between a state commitment landing on a destination host and that commitment being usable to process requests/responses/timeouts — this window is what gives fishermen time to call `veto_state_commitment` before fraud is acted upon (`docs/content/protocol/ismp/consensus.mdx:215`, `modules/pallets/fishermen/src/lib.rs:167-193`). But every EVM handler treats `challengePeriod == 0` as "no delay required at all," exactly mirroring `proposalThreshold() == 0` meaning "anyone qualifies."

### Finding Description
`HandlerV2.sol` gates every message class (posts, get-responses, post-timeouts, get-timeouts) with the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` — when `challengePeriod == 0` the condition short-circuits to `false` and the delay check is skipped entirely, regardless of how recently the state commitment for that height landed. This is the exact same shape as the reported bug: a security threshold is compared with `!= 0` as a precondition, so the value `0` doesn't just mean "no minimum wait," it means "the entire guard is off."

`challengePeriod` is a single host-wide field on `HostParams`, settable only by cross-chain governance via `hostManager` (`evm/src/core/EvmHost.sol:565-575`, `HostManager.sol:95-108`). `updateHostParamsInternal` validates several fields (`hostManager`, `handler`, `consensusClient`, `hyperbridge`, `stateMachines.length`, and explicitly enforces `1 days > params.unStakingPeriod` reverts) but performs **no minimum-value check on `challengePeriod`** — see the full guard list in `evm/src/core/EvmHost.sol:581-621`, where `unStakingPeriod` has an explicit floor but `challengePeriod` has none. The consensus documentation itself states the challenge window is load-bearing for safety: "safety in on-chain consensus clients will require the use of a challenge window, even after consensus proof verification" (`docs/content/protocol/ismp/consensus.mdx:27`), and fishermen are explicitly told to act "while [the state commitment] is still in its challenge period" (`modules/pallets/fishermen/src/lib.rs:158-161`). A `challengePeriod` of `0` removes that window on the EVM side entirely — any state commitment can be acted on in the same block it lands, before a fisherman/relayer byzantine-check pass (`tesseract/messaging/evm/src/byzantine.rs`) has any chance to run and submit `veto_state_commitment`.

### Impact Explanation
If `challengePeriod` is ever `0` for a destination `EvmHost` — whether by an oversight in the initial `updateHostParams` call (no floor is enforced, unlike `unStakingPeriod`) or a governance misconfiguration — every request, get-response, and timeout handler on that chain loses its fraud-proof grace period. A relayer can deliver messages built against a just-landed, still-unverified state commitment before any fisherman quorum check completes, allowing a fraudulent/eclipsed state commitment to be acted upon and processed as if final. This directly matches the required impact class "false proof/state acceptance" since it removes the mechanism ("Consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted") that the fisherman/veto design explicitly depends on to catch byzantine state before it's used.

### Likelihood Explanation
This does not require a compromised relayer/prover/admin key or a governance takeover to become dangerous once triggered — the risk is that **no code path enforces a minimum non-zero `challengePeriod`**, so a single governance parameter update that omits or zeroes this field (plausible given there's no revert like `InvalidUnstakingPeriod` for it) silently disables safety for every message on that host from that point forward, with no separate confirmation step. Compare this to `unStakingPeriod`, which the same function explicitly floors at `1 days` — the asymmetry (one parameter is defended, the structurally-identical other is not) is the concrete missing guard.

### Recommendation
Add a minimum-value check for `challengePeriod` in `updateHostParamsInternal`, mirroring the existing `unStakingPeriod` floor (e.g. `revert InvalidChallengePeriod()` if `params.challengePeriod == 0` or below a protocol-defined minimum), so the `!= 0` bypass in `HandlerV2.sol` can never be reached in production. On the Substrate side, keep `ChallengePeriod` as `OptionQuery` (already safe — it fails closed with `ChallengePeriodNotConfigured` rather than defaulting to 0) as the reference pattern for the EVM side to match.

### Proof of Concept
1. Deploy `EvmHost` and call `updateHostParams` (as `hostManager`) with `challengePeriod = 0` — this succeeds today because `updateHostParamsInternal` has no check comparable to `if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();` for `challengePeriod` (`evm/src/core/EvmHost.sol:581-621`).
2. Have the consensus client commit a new (possibly fraudulent/eclipsed) state root for a tracked state machine via `handleConsensus`.
3. Immediately, in the same or next block — with `delay == 0` — call `handlePostRequests` (or any of the other three handlers). The check `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` evaluates to `false` and is skipped (`evm/src/core/HandlerV2.sol:181-186`), so the request is dispatched to its destination module before any fisherman byzantine check (`tesseract/messaging/evm/src/byzantine.rs:73-172`) has a realistic window to run and submit a veto.

**Note on confidence**: I was unable to fully confirm (due to running out of iterations) whether `challengePeriod` has any deployment-time default enforced outside `updateHostParamsInternal` (e.g., in `initialize()` or deployment scripts), which would determine whether a *freshly deployed, never-configured* host is also exposed to this zero-value window before governance ever calls `updateHostParams`. That additional bootstrap-time angle should be verified directly against `evm/script/DeployIsmp.s.sol` and the `initialize()`/constructor path in a follow-up session.
