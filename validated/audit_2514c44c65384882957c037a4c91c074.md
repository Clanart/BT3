### Title
`SchnorrAggregate::verify` accepts a forged empty aggregate signature (divergence from aggregator behavior at n=0) - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate` is intended to represent an aggregate of `n ≥ 1` Schnorr signatures: the producing side, `SchnorrAggregator::complete`, explicitly refuses to emit an aggregate when no signatures were aggregated (`return None`). However, the verification path `SchnorrAggregate::verify` does not enforce this invariant. An aggregate deserialized via `SchnorrAggregate::read` with `Rs.len() == 0` and `s == 0` verifies as valid whenever the caller supplies an empty `keys_and_challenges` list — a signature the honest aggregator can never produce. This is the same bug class as the zkSync report: an edge case where the component diverges from its intended/guaranteed behavior ("aggregates always contain ≥1 signature"), which protocols relying on that invariant do not anticipate.

### Finding Description
- `SchnorrAggregate::read` (crypto/schnorr/src/aggregate.rs:77-88) reads a `u32` count and happily accepts `0`, then reads `s`. Fully attacker-controlled bytes.
- `SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146) checks `self.Rs.len() != keys_and_challenges.len()` — satisfied for `0 == 0` — then builds `pairs` containing only `(-self.s, C::generator())`. With `s = 0`, `multiexp_vartime` yields the identity, and `verify` returns `true`.
- The intended invariant is documented on the producing side: `SchnorrAggregator::complete` returns `None` if `self.sigs.is_empty()` (line 175-178), i.e., the honest API defines an aggregate over zero signatures as non-existent. The verifier contradicts this by treating the zero-aggregate as a *valid* signature.
- Reachability: untrusted bytes → `SchnorrAggregate::read` → `verify(dst, &[])` returns `true`. Any integrator that batch-verifies aggregates whose expected signer set is attacker-influenceable to the empty set (e.g., filtering out-of-set signers, deduplicating, or building `keys_and_challenges` from the same attacker message) will accept a signature nobody produced.

### Impact Explanation
A forged aggregate signature is accepted: verification of `(Rs=[], s=0)` against an empty key/challenge list returns `true` even though no party signed anything and the honest aggregator refuses to construct this object. In a system that treats a passing `verify` as "the listed signers endorsed these messages", an attacker obtains unanimous consent of an empty set — which downstream logic may interpret as authorization when the signer list is derived dynamically and can degenerate to empty. This violates the library's own stated contract (aggregates exist only over ≥1 signature) in exactly the way the referenced report describes: intended behavior differs from actual behavior on an edge case reachable with public inputs.

### Likelihood Explanation
Medium, matching the source report's reasoning. Exploitation requires a calling context where the expected `keys_and_challenges` slice can be empty at verification time while the `verify` result is still consumed as meaningful. That is a real integration pattern (verifying aggregates per-subset of a message list), not exotic. The attacker needs no secret material and no honest-party cooperation — only the ability to submit serialized bytes to `SchnorrAggregate::read`. The fix is a single-line check, and the discrepancy is a genuine inconsistency between the crate's own producer and verifier.

### Recommendation
Mirror the mitigation of adding the missing check to the edge-case path: reject the empty aggregate in `verify` (and ideally in `read`, since a zero-length `Rs` can never be a legitimately produced aggregate):

```rust
pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
  if self.Rs.is_empty() || (self.Rs.len() != keys_and_challenges.len()) {
    return false;
  }
  ...
}
```

Optionally also reject `self.s == 0` (an honest `s` is a sum of nonzero-weighted scalars). This restores the invariant `complete() == None ⇒ verify() == false`.

### Proof of Concept
```rust
// C: any Ciphersuite, e.g. Ed25519
let mut bytes = 0u32.to_le_bytes().to_vec();          // Rs.len() == 0
bytes.extend(C::F::ZERO.to_repr().as_ref());          // s == 0
let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();

// Returns true despite no signature ever being produced or aggregated:
// SchnorrAggregator::new(dst).complete() == None for this same input set.
assert!(agg.verify(b"some_dst", &[]));
```
Root cause: `verify` (aggregate.rs:127-146) omits the non-emptiness check that `complete` (aggregate.rs:175-178) enforces, so the multiexp over `pairs = [(-0, G)]` trivially reduces to identity.

Caveat: I did not enumerate all in-repo call sites of `SchnorrAggregate::verify` to confirm a concrete caller reachable with an empty challenge list (iteration limit reached); the severity rests on the verifier accepting a signature form the producer explicitly defines as unproducible, reachable purely via attacker-controlled bytes.
