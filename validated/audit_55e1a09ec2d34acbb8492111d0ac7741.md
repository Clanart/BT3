### Title
Reward accounting in `BaseRewardPool`/`BaseRewardPoolV2` relies on raw `balanceOf(operator)` instead of tracked stake accounting, allowing permanent dilution/freezing of staker rewards - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`)

### Summary
`totalStaked()` in both `BaseRewardPool.sol` and `BaseRewardPoolV2.sol` is computed as the raw ERC20 balance of the staking token held by the `operator` (MasterMagpie), rather than from tracked/accounted stake. This is the same root-cause pattern as the reported `_checkNoLiquidity` bug: using a manipulable `balanceOf()` read as a critical accounting input instead of an internal ledger. Any ordinary wallet holding the pool's staking (receipt) token can directly `transfer()` it to the MasterMagpie contract address, inflating `totalStaked()` without going through the tracked deposit flow, and permanently corrupt reward-per-token accounting for all legitimate stakers.

### Finding Description
`totalStaked()` is defined identically in both reward pool implementations: [1](#0-0) [2](#0-1) 

This value is used directly as the divisor when new rewards are provisioned: [3](#0-2) 

The staking tokens tracked by these reward pools are ordinary, freely transferable ERC20 tokens (e.g. the receipt tokens minted by `ERC20FactoryLib.createERC20` in `WombatStaking.registerPool`, or `vlMGP`/`mWomSV` share tokens). [4](#0-3)  A user who legitimately holds this staking token (e.g., by depositing through the normal flow, or acquiring it on the open market) can bypass `MasterMagpie`'s tracked deposit path and simply call `IERC20(stakingToken).transfer(operator, amount)` directly. Because `totalStaked()` reads the raw balance rather than an internally maintained sum of tracked deposits (`stakingInfo`), this inflates `totalStaked()` without increasing any individual user's tracked `balanceOf(_account)` (which is sourced from `IMasterMagpie(operator).stakingInfo(...)`, not the raw token balance): [5](#0-4) 

This exactly mirrors the reported bug class: an unprivileged actor manipulates a `balanceOf()`-based liquidity/accounting check that should instead be based on a robust internal ledger (analogous to using `scaledTotalSupply()` instead of `balanceOf()` in the original report's recommendation).

### Impact Explanation
Once `totalStaked()` is inflated via a direct token donation to the `operator` address, any subsequent call to `queueNewRewards` (by a manager) or `donateRewards` (callable by anyone) computes:
```
rewardPerTokenStored += (amountReward * 10**decimals) / totalStaked()
```
With an artificially inflated `totalStaked()`, `rewardPerTokenStored` increases by far less than it should. Since `rewardPerTokenStored` is a monotonically increasing accumulator used for all future `earned()` calculations [6](#0-5) , this loss is permanent and irrecoverable for every staker in the pool — legitimate stakers permanently lose (are unable to claim) the diluted portion of yield. This satisfies "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
The action requires only an ERC20 `transfer()` call from any wallet holding the staking token to the `operator` address — no privileged role, admin action, or governance step is needed. The staking tokens in scope (Wombat LP receipt tokens, `vlMGP`, `mWomSV`) are all standard transferable ERC20/ERC20Votes-style tokens held by ordinary users, so acquiring them is trivial (e.g., via a normal deposit first, or by purchasing on a market if traded). The main constraint is timing it around a `queueNewRewards`/`donateRewards` call, which happens routinely as part of protocol operation (harvests), making this practically exploitable by any user monitoring pending reward distributions.

### Recommendation
Replace the `balanceOf(operator)`-based `totalStaked()` with an internally tracked accounting variable that only increases/decreases via the legitimate stake/withdraw code paths (e.g., a `totalSupply`-style counter maintained in `MasterMagpie` or in each `BaseRewardPool`/`BaseRewardPoolV2`, similar to how `BribeRewardPool` already tracks `totalSupply` internally instead of reading raw balances): [7](#0-6) 

### Proof of Concept
1. Attacker deposits a small amount into a Wombat pool through `WombatStaking`/`MasterMagpie`, receiving the pool's receipt (staking) token and being tracked in `stakingInfo`.
2. Attacker acquires a large amount of the same staking token (e.g. via additional legitimate deposits, or purchase if liquid) and calls `stakingToken.transfer(masterMagpieAddress, largeAmount)` directly — bypassing `MasterMagpie`'s deposit accounting.
3. `IERC20(stakingToken).balanceOf(operator)` is now inflated by `largeAmount`, so `totalStaked()` in the associated `BaseRewardPool`/`BaseRewardPoolV2` reflects this inflated value while no user's `stakingInfo`-tracked balance changed.
4. A manager calls `queueNewRewards(rewardAmount, rewardToken)` (or anyone calls `donateRewards`), and `rewardPerTokenStored` is updated using the inflated `totalStaked()` as divisor, permanently under-crediting all real stakers for that reward distribution.
5. Attacker can withdraw their donated tokens is not possible (transfer is one-way to `operator`, no refund mechanism), but the point of the attack is griefing/permanent dilution of rewards for other stakers rather than direct profit extraction; the yield is permanently lost/frozen for legitimate depositors.
