Audit Report

## Title
Global (non-per-IP) DoS of QUIC connection-tracker capacity via slow-handshake burst - (File: streamer/src/nonblocking/quic.rs)

## Summary
In `run_server`, the global `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) is granted before either the overall or per-IP rate limiter is actually consumed; both limiters are only debited on the handshake *success* path inside `setup_connection`. An unprivileged, unstaked attacker can therefore open a burst of QUIC connections and withhold the handshake-completing packets, holding each tracker slot for the full 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` without ever being throttled, then immediately repeat, to occupy the shared global handshake headroom and degrade legitimate connection establishment.

## Finding Description
`run_server` checks `overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(&ip)` before calling `ClientConnectionTracker::new`, but both are peek-only: `TokenBucket::current_tokens()` (net-utils/src/token_bucket.rs L66-70) never consumes tokens, and `ConnectionRateLimiter::is_allowed` returns `true` whenever no record exists for the IP yet (connection_rate_limiter.rs L34-40). Actual token consumption (`rate_limiter.register_connection`, `overall_connection_rate_limiter.consume_tokens(1)`) happens only inside `setup_connection`'s success branch, i.e., after `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` returns `Ok`. The only admission gate applied to in-flight, incomplete handshakes is `ClientConnectionTracker::new`, which compares a single global `open_connections` atomic against `max_concurrent_connections` with no per-IP partitioning (quic.rs L236-252). This value is deliberately sized with only 25% headroom over `max_staked_connections` (simple_qos.rs L422-425) specifically to accommodate in-flight handshakes. An attacker who opens connections and stalls before completing the handshake consumes this shared headroom for up to 2 seconds per attempt, never triggering either rate limiter, and can repeat indefinitely.

## Impact Explanation
A single unprivileged, unstaked attacker can occupy a meaningful fraction of the global `max_concurrent_connections` pool indefinitely by cycling through stalled handshake attempts, degrading the server's ability to accept new legitimate (staked or unstaked) QUIC/TPU connections during the attack window. This is a resource-exhaustion/availability degradation at the connection-admission layer — a non-RPC remote exhaustion/degradation impact, within scope. It does not cause fund loss, false execution, or consensus impact, and does not crash the validator; once a connection is established, existing per-peer caps and stream throttling still apply.

## Likelihood Explanation
No authentication, stake, or special network position is needed. The attacker only needs to send UDP packets that make quinn yield an `Incoming`/`Connecting` object and then withhold the packets that complete the handshake — no IP spoofing is required, since a normal client that simply stalls after its Initial flight suffices. Because both the overall and per-IP rate limiters are only exercised on the successful-handshake path, the described attack cycle is not throttled by either existing mitigation, making the attack straightforward and repeatable using ordinary client-side QUIC/UDP capability.

## Recommendation
- Reserve/consume rate-limiter tokens (per-IP and/or overall) at admission time, before or at `ClientConnectionTracker::new`, rather than only upon handshake success, so stalled attempts are throttled the same as completed ones.
- Add a per-IP cap on concurrent outstanding (tracker-held) connection attempts, independent of the existing per-IP completed-connection rate limiter.
- Consider reducing `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or making it adaptive under load, and/or dynamically scaling handshake headroom based on observed incomplete-handshake rates.

## Proof of Concept
Using `setup_quic_server` test scaffolding (similar to `test_client_connection_tracker`/`test_quic_server_multiple_connections_on_single_client_endpoint`): repeatedly open QUIC client endpoints that send only an Initial packet (or a raw UDP socket sending a single Initial-shaped datagram) in bursts sized near `qos.max_concurrent_connections()`, while concurrently issuing a legitimate `endpoint.connect(...).await`. Observe `stats.refused_connections_too_many_open_connections` increasing and legitimate connection latency/failure rate rising while `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain at 0 for the attacker's stalled attempts, demonstrating that the rate limiters never engage against the attack while global connection-tracker capacity is exhausted.
