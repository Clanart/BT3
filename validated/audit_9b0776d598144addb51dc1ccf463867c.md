### Title
Unchecked ERC20 boolean return value in escrow withdrawal marks orders as settled even when the token transfer silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` pays out escrowed tokens using a raw low-level `.call` to the ERC20 `transfer` selector and only checks that the *call itself did not revert* (`success`), never decoding or checking the returned `bool`. For ERC20 tokens that follow the "return false on failure" convention (H01's "type 2" tokens, e.g. ZRX-style tokens), a failed transfer returns cleanly with `success == true` but an ABI-encoded `false` payload that is never inspected. The contract then unconditionally decrements escrow accounting and emits `EscrowReleased`/`EscrowRefunded`, permanently marking the order settled while the beneficiary received nothing.

### Finding Description
`withdraw()` handles both `RedeemEscrow` and `RefundEscrow` requests delivered via `onAccept`: [1](#0-0) 

For every token in `body.tokens`, the payout uses:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted at the EVM level — it says nothing about the boolean the ERC20 `transfer` function returned in its return data. A "type 2" ERC20 token (returns `false` instead of reverting on failure — insufficient balance in the gateway due to a bug, a paused/blacklist-style token, etc.) makes this branch treat the failed transfer as a success.

Immediately after, regardless of whether the tokens actually moved:
```solidity
_orders[body.commitment][token] -= amount;
```
and at the top of the function, unconditionally:
```solidity
_filled[body.commitment] = beneficiary;
```
is set before any transfer is attempted. Once this function returns without reverting, the ISMP host records the request as successfully processed (this is the `onAccept` handler invoked by `onlyHost`), so there is no retry path — the request commitment is consumed. The same unguarded pattern is also used for `TRANSACTION_FEES` payout in the same function, and for `SweepDust` handling in `onAccept`: [2](#0-1) 

This is a direct structural analog to H01's second example — the `harvest` function assuming a transfer succeeded because it didn't revert, when the returned boolean must be checked — except here the corrupted value is escrow state (`_orders[commitment][token]` and `_filled[commitment]`) rather than a yield accounting variable, and the consequence is permanent loss of the user's/solver's bridged funds rather than a temporary shortfall.

### Impact Explanation
Once escrow is marked filled/refunded and decremented while the beneficiary got nothing, the tokens are stranded in the `IntentGatewayV2` contract with no code path to re-trigger payout for that commitment (the withdrawal request has already been consumed/authenticated once via `authenticate(incoming.request)` and ISMP's one-time receipt handling). This is exactly the "stealing or loss of funds" / "false state acceptance" category in scope: the on-chain state falsely records a completed settlement while the actual asset transfer failed, and the beneficiary permanently loses the escrowed input or output tokens (or fee token) that were rightfully theirs.

### Likelihood Explanation
No malicious relayer, prover, governance actor, or leaked key is required — this is triggerable end-to-end using nothing but an intent order or fee-token configuration that references a legitimate ERC20 token following the widely-used "return false, don't revert" convention. Because `IntentGatewayV2` accepts arbitrary `token` addresses supplied by users/solvers in `order.inputs`/`order.output.assets`, and the fee token is host-configured, any deployment on a chain using such a token (or any future host fee-token change to one) hits this path on every completed or refunded intent involving that token.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value (or absence of return data) uniformly, reverting on any transfer failure instead of silently continuing to mutate escrow state and mark the request filled.

### Proof of Concept
1. Configure/deploy the fee token (or have a solver create an order whose input/output token) as a "type 2" ERC20 that returns `false` on failed transfers instead of reverting (e.g., balance temporarily insufficient in the gateway due to a race, or the token has a blacklist that silently no-ops and returns `false`).
2. A legitimate `RedeemEscrow`/`RefundEscrow` request is delivered to `onAccept` → `withdraw()`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting but returns `false` in its return data.
4. `success` is `true` (call didn't revert), so `if (!success) revert TransferFailed();` does not trip.
5. `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment] = beneficiary;` was already set, and `EscrowReleased`/`EscrowRefunded` is emitted.
6. The beneficiary's token balance never increased; the tokens remain locked in `IntentGatewayV2` with no remaining code path to redeem them for that commitment. [1](#0-0)

```text
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
