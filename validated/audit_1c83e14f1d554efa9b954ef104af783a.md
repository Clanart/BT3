## Finding: Unbounded PlotNFT pool-reward claim can create an oversized spend bundle that permanently blocks reward withdrawal

### Title
Unbounded pool reward aggregation in `PlotNFT2Wallet.claim_rewards` can produce a spend bundle that exceeds the mempool/block cost limit, permanently blocking withdrawal of farmed rewards - (File: `chia/wallet/plotnft_wallet/plotnft_wallet.py`)

### Summary
`PlotNFT2Wallet.claim_rewards` collects **every** unclaimed pool-reward coin recorded for a plot NFT and folds them all into a single, monolithic `WalletSpendBundle` with no batching or size cap, unlike the legacy `PoolWallet.claim_pool_rewards`, which explicitly limits the number of reward coins claimed per transaction (`max_spends_in_tx` / `DEFAULT_MAX_CLAIM_SPENDS`) specifically "so the SpendBundle fits into the block." [1](#0-0) 

### Finding Description
`claim_rewards` fetches the full, unbounded list of pending rewards via `plotnft2_store.get_pool_rewards`: [2](#0-1) 

It then calls `plotnft.claim_pool_rewards(rewards_to_claim=rewards_to_claim, ...)`, which curries a `SEND_MESSAGE` condition into the singleton's delegated puzzle for **every single reward coin** and appends one `CoinSpend` per reward coin to the resulting list: [3](#0-2) 

All of these `CoinSpend`s are aggregated into one `WalletSpendBundle` and pushed as a single transaction: [4](#0-3) 

Compare this with the older, non-Plot-NFT-v2 `PoolWallet.claim_pool_rewards`, which explicitly caps the number of reward coins absorbed per spend bundle to avoid exceeding the block cost limit: [5](#0-4) 

Because `claim_rewards` has no equivalent cap, if the number of accumulated, unclaimed reward coins for a plot NFT grows large enough (e.g., a long-running or low-payout pool/self-pooling setup that accrues many small reward coins over time before the user claims), the resulting spend bundle's CLVM execution cost can exceed `max_tx_clvm_cost`/`MAX_BLOCK_COST_CLVM`. The mempool enforces this hard limit during admission: [6](#0-5) 

Since `claim_rewards` cannot partially claim (all pending reward coins are consumed with a single singleton advance in one atomic bundle, and the code does not implement any batching/splitting logic the way `PoolWallet` does), an oversized reward set means the resulting transaction can **never** be accepted into the mempool at all — `Err.BLOCK_COST_EXCEEDS_MAX` will be returned every time it's submitted, with no path in the wallet code to reduce the claim to a smaller batch.

### Impact Explanation
This is directly analogous to the reported bug class: an unbounded collection (deposits / reward coins) is iterated in full within a single settlement operation, and once that collection grows past the resource/cost limit, the withdrawal/claim operation for the affected party becomes permanently unexecutable (mempool rejects the oversized spend bundle every time). For `PlotNFT2Wallet`, this results in a spend-triggered transaction-processing halt: the owner's farmed/pool rewards become permanently unclaimable, since there is no fallback path to claim in smaller batches. This is a coin-movement-halting condition (funds become effectively stuck), matching the accepted "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Reaching this condition does not require a malicious peer or privileged access — it only requires normal usage over time (a plot NFT accumulating many farmed/pool reward coins without being claimed, e.g. due to low payout frequency, high fees discouraging frequent claiming, or a user simply not claiming for an extended period) or an attacker relentlessly waiting for accumulation before front-running claim attempts. The complete absence of any per-transaction reward-count cap (in contrast to the already-mitigated legacy `PoolWallet` path) means this is a straightforward oversight in the newer PlotNFT v2/`PlotNFT2Wallet` code path.

### Recommendation
Add a batching limit to `PlotNFT2Wallet.claim_rewards` analogous to `PoolWallet.claim_pool_rewards`'s `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`, so that only a bounded number of reward coins are claimed per spend bundle, allowing the remainder to be claimed in subsequent transactions. This requires reworking `PlotNFT.claim_pool_rewards` (in `chia/pools/plotnft_drivers.py`) to support partial/chunked reward claiming while correctly advancing/tracking the singleton lineage across the truncated batch, mirroring the existing truncation logic used by the legacy pool wallet.

### Proof of Concept
1. Create a `PlotNFT2Wallet` (self-pooling or pooled) and let it accumulate a large number of small pool-reward coins at its `p2_singleton_puzzle_hash` over time (each block reward adds one entry via `coin_added` → `plotnft2_store.add_pool_reward`, see `chia/wallet/plotnft_wallet/plotnft_wallet.py:651-657`).
2. Once the number of unclaimed reward coins is large enough that the resulting `SEND_MESSAGE`-laden singleton spend plus per-reward `CoinSpend`s exceed `max_tx_clvm_cost` (`MAX_BLOCK_COST_CLVM / 2`), call `claim_rewards`.
3. Observe that `wallet_rpc_api`/mempool submission of the resulting `WalletSpendBundle` fails with `Err.BLOCK_COST_EXCEEDS_MAX` (`chia/full_node/mempool_manager.py:819-820`), and because `claim_rewards` has no batching fallback, the rewards remain permanently unclaimable through this endpoint.
