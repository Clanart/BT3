### Title
Unchecked u64 overflow in payment summation bypasses the funds check and underflows fee computation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` sums attacker-influenced payment amounts with `sum::<u64>()` (line 187) and later computes `payment_sat + needed_fee` / `payment_sat + fee_with_change` (lines 215, 228). In release builds these additions wrap modulo 2^64 rather than saturating. A wrapped `payment_sat` can make `input_sat < payment_sat + needed_fee` evaluate false even though the true output total vastly exceeds the inputs, so a `SignableTransaction` is produced whose outputs exceed its inputs. Any later call to `fee()` (lines 139–141) performs `sum(inputs) - sum(outputs)` with a plain `-`, which underflows and panics — and, before the panic, the change-calculation branch can also derive a nonsensical change output.

### Finding Description
The analog to the GoBGP MRT parser underflow (untrusted length arithmetic underflowing and corrupting parse/validation logic) is unvalidated integer arithmetic on amounts that originate in payment/withdrawal requests:

- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` — `Iterator::sum` wraps on overflow in release mode.
- `if input_sat < (payment_sat + needed_fee)` — `payment_sat + needed_fee` can itself overflow.
- `input_sat.checked_sub(payment_sat + fee_with_change)` — the `checked_sub` guards `input_sat`, but the inner `payment_sat + fee_with_change` can still wrap to a small value before the subtraction.
- `self.prevouts...sum::<u64>() - self.tx.output...sum::<u64>()` in `fee()` underflows once outputs exceed inputs.

There is no `checked_add`/`saturating_add` and no cap tying `payment.1` to the real Bitcoin supply (21M·10^8) anywhere in this function; the only amount check is `*amount < DUST` (line 166).

### Impact Explanation
- A crafted payment set whose true total exceeds `u64::MAX` (e.g., two payments of `u64::MAX/2 + k`) wraps `payment_sat` near zero, bypassing `NotEnoughFunds`.
- The resulting `SignableTransaction` commits to outputs worth far more than the inputs; `SignableTransaction::fee()` then panics on u64 underflow, crashing the signing process (availability loss in the threshold-signing path).
- In the change-address branch, the wrapped subtraction can also produce a change output of nearly `input_sat`, yielding a transaction the network will reject after the threshold group has produced signatures for it — i.e., signatures generated for a malformed, unspendable transaction.

### Likelihood Explanation
Reachable only if the caller of `SignableTransaction::new` places attacker-influenced amounts into `payments` without an upper bound; within bitcoin-serai's own construction the arithmetic is unchecked, so the overflow/underflow is a genuine defect in the in-scope code. Impact is limited to a panic/invalid transaction rather than fund theft, consistent with a Medium finding.

### Recommendation
Use `checked_add`/`saturating_add` (or accumulate into `u128`) for `payment_sat`, `payment_sat + needed_fee`, and `payment_sat + fee_with_change`, and compute `fee()` with `checked_sub`, returning `TransactionError::NotEnoughFunds`/`TooLargeTransaction`-style errors instead of wrapping/panicking. Optionally bound each payment amount to the Bitcoin money range.
