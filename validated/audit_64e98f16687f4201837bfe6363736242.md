Based on my investigation, the grep found no matches for `output_script_pubkey`/`output_amount` anywhere in `circuits-lib/`, confirming that the bridge circuit (`circuits-lib/src/bridge_circuit/mod.rs::bridge_circuit`) never validates that the confirmed payout transaction actually pays the withdrawal's requested amount/destination — it only checks that the transaction's input at `payout_input_index` matches the withdrawal-identity outpoint committed on Citrea via `verify_storage_proofs` [1](#0-0) , and that the OP_RETURN-embedded pubkey is used purely as `deposit_constant` input, not cross-checked against any operator-specific proof of funding.

### Title
Unauthenticated OP_RETURN operator attribution lets any withdrawal-UTXO owner frame an arbitrary operator as payer, letting that operator claim reimbursement for a payout it never funded - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` attributes a withdrawal's `payout_payer_operator_xonly_pk` purely by parsing the OP_RETURN output of whatever transaction happens to spend the registered withdrawal-identity UTXO [2](#0-1) , with no cryptographic proof that the named operator actually constructed, signed, or funded that transaction. Since the withdrawal-identity UTXO is a dust output fully owned and controlled by the withdrawing user (their own taproot key, `SinglePlusAnyoneCanPay`) [3](#0-2) [4](#0-3) , that same user can spend it themselves with an arbitrary OP_RETURN naming any victim operator's x-only pubkey, poisoning the `withdrawals` DB row and causing that operator's automated `PayoutCheckerTask` to bind a kickoff to a payout it never made.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk` for index `i` == the operator who actually funded/broadcast the payout transaction for index `i`. In reality it equals: whatever x-only pubkey is parsed from the first OP_RETURN output of *whichever transaction the chain syncer observes spending* `withdrawal_utxo_txid:withdrawal_utxo_vout` for index `i`.

Path:
1. The withdrawal-identity UTXO's outpoint is registered by whatever the withdrawing user supplied to Citrea's `withdraw()` contract call, then synced into `withdrawals.withdrawal_utxo_txid/vout` [5](#0-4) . This UTXO is required to be a taproot output the user themselves controls (their own key produces the `SinglePlusAnyoneCanPay` signature) [6](#0-5) , so the attacker (any bridge user who deposited and can call `withdraw`) always holds the spending key for it.
2. `get_payout_txs_for_withdrawal_utxos` simply returns whichever transaction the bitcoin syncer recorded as spending that exact outpoint in a given block [7](#0-6) , `core/src/database/bitcoin_syncer.rs:334-353`.
3. `update_finalized_payouts` parses that transaction's OP_RETURN for an x-only pubkey and stores it verbatim as `payout_payer_operator_xonly_pk`, with an explicit comment acknowledging it can be `None` "if... the operator constructed the payout tx wrong" — i.e. no validation that the embedded key corresponds to whoever actually funded the tx [2](#0-1) .
4. `PayoutCheckerTask::run_once` (run independently per-operator, using `self.operator.signer.xonly_public_key`) queries `get_first_unhandled_payout_by_operator_xonly_pk` and, upon a match, unconditionally calls `handle_finalized_payout`, `end_round`, and `mark_payout_handled` [8](#0-7) , entering the kickoff/reimbursement machinery for a payout the operator never made.
5. `is_kickoff_malicious` (the verifier-side guard) only checks that the DB's recorded operator matches the kickoff's operator and that the committed blockhash matches the DB's recorded `payout_tx_blockhash` [9](#0-8)  — both of these are self-consistent with the same poisoned DB row, so this guard does not catch forged attribution.
6. `verify_storage_proofs`/`bridge_circuit` (the eventual dispute-resolution ground truth) only checks that the payout transaction's referenced input outpoint/vout matches the withdrawal identity UTXO committed on Citrea [1](#0-0) ; it never checks that the transaction's output amount/script_pubkey matches the amount/address the withdrawing user actually requested (`output_script_pubkey`/`output_amount` do not appear anywhere in `circuits-lib/`). So even at the deepest verification layer, there is no check that the named operator paid the withdrawing user anything.

Exploit: the attacker (a user who has an existing deposit/withdrawal index `i`) calls Citrea's `withdraw()` naming a dust UTXO they own as the withdrawal-identity UTXO. Before (or instead of) any real operator payout, they spend that dust UTXO themselves in a transaction whose OP_RETURN embeds an arbitrary victim operator's x-only pubkey. If this transaction confirms for index `i` (trivial since the attacker holds the only spending key and simply needs to broadcast/RBF it ahead of, or instead of, any real operator payout), the victim operator's own `PayoutCheckerTask` will pick it up and drive a kickoff, believing it fronted withdrawal `i`.

### Impact Explanation
An operator can be made to believe it fronted a withdrawal it never paid, driving it to spend its own resources (kickoff tx, round advancement, eventual reimbursement claim from its Round UTXO) for a payout that never happened — matching "an operator reimbursed for a payout it never funded" (Critical). Symmetrically, if the same forged attribution names `None` or a wrong-but-real operator, the honest operator that *did* actually front the payout can be permanently blocked from reimbursement, since the withdrawal-identity UTXO is already spent by the attacker's transaction and `payout_txid`/`payout_payer_operator_xonly_pk` in the DB is now fixed to the attacker's forged data — matching "an honest operator permanently unable to be reimbursed" (Critical). This is repeatable per withdrawal index and requires no special privilege beyond being a withdrawing bridge user with an in-flight withdrawal.

### Likelihood Explanation
Preconditions: the attacker must be a legitimate bridge depositor/withdrawer who can register a withdrawal on Citrea (standard user action, no special role), must control the private key of the dust UTXO they register as the withdrawal-identity UTXO (guaranteed by protocol design), and must win the race to have their self-spend confirmed for that outpoint instead of, or before, any genuine operator payout. Attacker cost is minimal — a small dust amount plus a competitive tx fee. No verifier, operator, or aggregator collusion required, and no reliance on hashrate/reorg attacks — only ordinary mempool fee competition on an outpoint the attacker exclusively controls.

### Recommendation
Do not trust OP_RETURN-embedded operator attribution alone. Require cryptographic proof binding the payout transaction to the named operator (e.g., verify that at least one additional input of the payout transaction is provably funded/signed by the claimed operator's key, or require the operator to co-sign/commit to the payout txid through an authenticated channel before `update_finalized_payouts` records `payout_payer_operator_xonly_pk`). Additionally, have the bridge/verifier logic (and ideally the bridge circuit) validate that the confirmed payout transaction's output amount and destination script actually match what the withdrawing user requested on Citrea (`output_amount`/`output_script_pubkey`), not merely that some transaction spent the identity UTXO.

### Proof of Concept

Test plan:
1. Set up a deposit and corresponding withdrawal index `i` for a "victim" user, insert `withdrawal_utxo_txid/vout` pointing at a UTXO owned by an "attacker" key (not the real operator's funding wallet).
2. Have the attacker (not any operator) construct and broadcast a transaction spending that UTXO with an OP_RETURN containing an honest, uninvolved operator `Op_X`'s x-only pubkey, paying the attacker's own address (no real payout to the withdrawing user).
3. Mine/sync this block, call `update_finalized_payouts`.
4. Assert `db.get_payout_info_from_move_txid(...)` returns `(Some(Op_X_xonly_pk), block_hash, attacker_txid, i)` — showing the DB now falsely attributes the payout to `Op_X`.
5. Call `db.get_first_unhandled_payout_by_operator_xonly_pk(Op_X_xonly_pk)` and assert it returns `(i, move_to_vault_txid, block_hash)` — proving `Op_X`'s `PayoutCheckerTask` would proceed to `handle_finalized_payout` for a payout `Op_X` never made.
6. Assert that `Op_X` never broadcast/funded any transaction (no wallet balance change), confirming the binding "payer_operator_xonly_pk == actual funder" is broken.

    async fn collect_withdrawal_utxos(

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }
