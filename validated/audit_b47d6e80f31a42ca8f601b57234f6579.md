### Title
Panic in `BlameMachine::blame_internal` on out-of-range `sender` index allows remote DoS - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`BlameMachine::blame` (and `AdditionalBlameMachine`) blindly index `self.commitments[&sender]` when adjudicating an accusation. `sender` is a `Participant` parsed from attacker-supplied bytes (`Transaction::InvalidDkgShare` carries `accuser`/`faulty` as bare `Participant::new(u16)`, which only rejects zero, not values > n). A Participant index that is nonzero but greater than the DKG's `n` is not present in `self.commitments`, so the HashMap index panics — the exact analog of CVE-2020-25465's null-deref crash: unvalidated external input used as an unchecked lookup.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs:575-608`, `blame_internal` computes blame by first decrypting the message and then indexing the commitments map:

```rust
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],   // panics if sender not a real participant
    ...
```

`self.commitments` is populated only for the `n` actual DKG participants (`Participant(1)..=Participant(n)`). `Participant::new` (`crypto/dkg/src/lib.rs`) accepts any nonzero `u16`, so a serialized accusation naming `sender = Participant(n + 1)` … `u16::MAX` parses successfully at the transport layer (`Signed`/`InvalidDkgShare` transactions in `coordinator/src/tributary/transaction.rs:341-353` validate only `Participant::new(...) != 0`), and reaches `blame()`/`blame_internal` where `self.commitments[&sender]` dereferences a missing key and panics.

This is the same bug class as the reference advisory: an index/lookup derived from unvalidated input reaching code that assumes it is in-range.

### Impact Explanation
A single crafted blame/accusation message causes an unconditional panic (`HashMap` index on absent key) inside the DKG's fault-adjudication path. Any honest node evaluating the blame crashes, aborting key generation / participant-removal handling and killing the processor/coordinator task. This is a remote, unauthenticated-input-reachable denial of service — matching the advisory's SEGV/DoS impact class.

### Likelihood Explanation
Blame transactions are consensus-visible data any participant (or anyone who can get such a transaction included) can cause an honest node to evaluate. No collusion, leaked keys, or misuse is required: the path `Transaction::read` → `InvalidDkgShare { accuser, faulty, ... }` → `BlameMachine::blame(sender, recipient, msg, proof)` → `self.commitments[&sender]` requires only that `sender` be nonzero and out of `1..=n`, which no layer validates. (Note: I was unable to inspect the exact `processor/src/key_gen.rs` call site in this pass — the matches there confirm `blame` is invoked with transaction-derived participant indexes, but the precise check (if any) applied to `faulty`/`sender` before the call could not be verified; if callers do bound-check, the panic remains a latent crash in the public `blame` API, which takes `sender`/`recipient` without validating them against `self.commitments`.)

### Recommendation
In `BlameMachine::blame`/`blame_internal`, validate `sender` (and `recipient`) against `self.commitments` before indexing — e.g. `self.commitments.get(&sender)` returning an error or treating an unknown sender as faulty — and/or validate that both indexes are `<= n` when parsing `InvalidDkgShare` transactions. Prefer returning a `Result`/blame verdict over panicking on adversarial input.

### Proof of Concept

                 Participant(1), Participant(2) */;

let forged_sender = Participant::new(3).unwrap();   // valid Participant, not in set
let recipient     = Participant::new(1).unwrap();

// decrypt_with_proof returns InvalidSignature or InvalidProof first only if the
// signature/proof is bad; even with early return on InvalidSignature, reaching the
// `self.commitments[&sender]` line just requires decryption to succeed. With a validly

Even in the minimal variant, `blame` with `sender = Participant(n + k)` is accepted by all upstream `Participant`/transaction deserialization checks and reaches the unchecked `self.commitments[&sender]` index whenever `decrypt_with_proof` does not return `InvalidSignature` early — the panic is deterministic once execution reaches `crypto/dkg/pedpop/src/lib.rs:599`.
