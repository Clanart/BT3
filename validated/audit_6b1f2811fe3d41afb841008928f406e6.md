### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys enables a DoS via a single `AccountUpdate` transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each role-key entry by calling `rlp.DecodeBytes` on nested byte blobs, which in turn instantiates `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → (if the sub-key type is itself `AccountKeyTypeRoleBased`) → `AccountKeyRoleBased.DecodeRLP` again. This mirrors the xgrammar bug class (CWE-674, uncontrolled recursion via attacker-supplied nested structure): a single crafted `TxTypeAccountUpdate` (or fee-delegated variant) transaction containing a deeply-nested `RoleBased` account key can be submitted through public RPC (`eth_sendRawTransaction`) or gossiped into the tx pool, and the node will recurse once per nesting level while merely decoding the transaction — before any semantic "nested composite type" rejection is ever reached.

### Finding Description
The role-based account key is decoded as follows: [1](#0-0) 

Each element is independently re-decoded through `AccountKeySerializer.DecodeRLP`, which reads the key type tag and then dispatches to the matching concrete-type decoder via `NewAccountKey`: [2](#0-1) 

If the decoded `keyType` is `AccountKeyTypeRoleBased` again, `s.Decode(serializer.key)` re-enters `AccountKeyRoleBased.DecodeRLP`, closing the recursive cycle with no depth counter, no nesting-level cap, and no early rejection. The only place a "no nested RoleBased key" rule is enforced is a *post-decode* semantic check (`ErrNestedCompositeType`, surfaced in `blockchain/state_transition.go` and exercised in `tests/account_keytype_test.go`), which only fires once the full (already recursively decoded) structure has been built. Decoding itself is therefore unconstrained in depth and executes fully before any validation can short-circuit it — exactly the pattern behind the xgrammar advisory, where deep nesting is parsed/recursed before any structural limit is applied.

The underlying generic RLP decoder (`rlp/decode.go`) also has no explicit maximum-nesting-depth guard for lists/interfaces (`decodeListSlice`, `decodeInterface`, `makeListDecoder` all recurse per RLP nesting level with no `stack` depth ceiling other than available memory/goroutine stack), so this is not a defense that would already catch the attack at the generic decoding layer either: [3](#0-2) 

### Impact Explanation
An unprivileged sender can submit (or have accepted into the mempool/gossip) a single `AccountUpdate`-type transaction carrying an `AccountKeyRoleBased` value with many levels of self-nesting. Every node that decodes this transaction — during RPC ingestion (`eth_sendRawTransaction`), tx-pool admission, or block processing/re-execution — performs one Go function-call recursion (`AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → back into `AccountKeyRoleBased.DecodeRLP`) per nesting level before the `ErrNestedCompositeType` rejection is ever reached. This causes excessive CPU consumption and stack growth proportional to attacker-chosen nesting depth on every node that processes the transaction (RPC nodes, all txpool peers that receive it, and block-producing/validating nodes), which is a Denial-of-Service condition consistent in class with GHSA-7rgv-gqhr-fxg3 (uncontrolled recursion from attacker-controlled nesting depth). Depending on how large the size-limit permits nesting to be encoded (transaction size caps bound this but each nesting layer only adds a small constant overhead, permitting potentially thousands of nesting levels within ordinary max-tx-size limits), this can degrade node performance across the network or crash goroutines whose stacks cannot grow further.

### Likelihood Explanation
The nested key can be constructed entirely off-chain by any user with a valid EOA key and submitted as an ordinary `TxTypeAccountUpdate` (or fee-delegated variant) transaction — no special privileges, prior on-chain state, or governance/validator access is required. The only limiting factor is the maximum permitted transaction/RLP payload size enforced elsewhere in the tx pool, which I was not able to fully verify within the available investigation budget (i.e., whether the existing max transaction size effectively caps nesting depth to a level too small to matter, or still allows a damaging depth). This uncertainty should be resolved before assigning a final severity.

### Recommendation
- Add an explicit nesting-depth counter/limit to `AccountKeyRoleBased.DecodeRLP` (and generally to `AccountKeySerializer.DecodeRLP`) that rejects decoding as soon as a nested `AccountKeyTypeRoleBased` is encountered, instead of allowing full recursive decode and only rejecting via `ErrNestedCompositeType` after the fact.
- Alternatively/complementarily, add a global recursion-depth guard to the RLP `Stream`/decoder machinery for interface and custom-`Decoder` types, similar to hardened RLP implementations that cap list nesting depth (e.g., a `maxListDepth` check in `rlp.Stream.List`), to defend against this bug class more broadly rather than only for account keys.
- Verify and, if necessary, reduce the maximum allowed nesting achievable within current transaction size limits to confirm the practical exploitability window.

### Proof of Concept

   Repeat this nesting pattern N times (`RoleBased{ RoleBased{ RoleBased{ ... simple key } } }`) to build an `AccountKeyRoleBased` with N levels of self-nesting.
2. RLP-encode the resulting `AccountKeySerializer` via `EncodeAccountKey`/`rlp.EncodeToBytes` as shown in `api/api_kaia.go` (`EncodeAccountKey`), producing raw bytes.
3. Build a `TxTypeAccountUpdate` transaction using this nested key as `TxValueKeyAccountKey`, sign it with a valid key, and RLP-encode the full transaction.
4. Submit the raw transaction via `eth_sendRawTransaction` (public RPC) or broadcast it for tx-pool admission.

Observe that `AccountKeyRoleBased.DecodeRLP` recurses N times purely to decode the transaction/account key before `ErrNestedCompositeType` is raised — for sufficiently large N (bounded only by max tx/RLP size), this consumes disproportionate CPU/stack resources on every receiving node, analogous to the `xgrammar` 30,000-parenthesis PoC.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
}
