### Title
Incorrect read-lock usage allows concurrent unsynchronized writes to `GaslessModule.knownTxs`, causing map corruption/crash and gasless queue-limit bypass - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
The `i40e` CVE-2024-50041 root cause is unsynchronized concurrent mutation of a shared hash table (`mac_filter_hash`) used to track filter state, leading to inconsistent state and leaked entries. The `kaiax/gasless` module in Kaia has the same class of bug: `GaslessModule.PreAddTx()` takes only a **read** lock (`knownTxsMu.RLock()`) on `g.knownTxsMu` yet performs a **write** into the shared `knownTxs` map (`g.knownTxs.add(...)`), which is a plain `map[common.Hash]*knownTx`, not a concurrency-safe type.

### Finding Description
`knownTxs` is defined as a raw Go map [1](#0-0) , and `add()` mutates it directly with no internal synchronization [2](#0-1) .

`PreAddTx`, which is invoked by the transaction pool for every incoming transaction (including from any unprivileged sender), acquires only `g.knownTxsMu.RLock()` and then calls `g.knownTxs.add(tx, TxStatusQueue)`, mutating the map while holding merely a shared/read lock: [3](#0-2) 

By contrast, the other mutators of the same map correctly take the exclusive lock: `IsReady()` [4](#0-3) , `PreReset()` [5](#0-4) , and `PostReset()` [6](#0-5) .

Because `sync.RWMutex.RLock()` permits multiple simultaneous holders, any two concurrent calls to `PreAddTx()` (which can occur whenever multiple gasless bundle transactions — `GaslessApproveTx`/`GaslessSwapTx` per KIP-247 — are submitted at the same time via public RPC, e.g. concurrent `eth_sendRawTransaction`/`AddRemotes` calls) are allowed to execute `g.knownTxs.add()` in parallel with each other, and are not exclusive with respect to a `PreAddTx` call racing an `IsReady`/`PreReset`/`PostReset` write elsewhere. This is a direct analog of the mac_filter_hash bug: the lock intended to protect the table only enforces mutual exclusion for some paths (`Lock()`), while a hot path (`PreAddTx`) uses the wrong lock mode (`RLock()`) for a write, defeating the synchronization entirely for concurrent `PreAddTx` invocations.

Unsynchronized concurrent writes to a native Go map are undefined behavior; the Go runtime detects many such races and calls `fatal("concurrent map writes")`, which is unrecoverable and crashes the entire node process (not just the goroutine). Short of a hard crash, races can also silently corrupt map internals, causing entries to be lost/duplicated — i.e., a `knownTx` "leak" analogous to the macvlan filter leak, where the size/status bookkeeping (`numQueue()`, `numPending()`, `numExecutable()`) used to enforce `GetMaxBundleTxsInQueue()`/`GetMaxBundleTxsInPending()` becomes wrong, and the replay-guard (`ErrUnableToAddKnownBundleTx`, based on `g.knownTxs.get(tx.Hash())`) can be silently bypassed.

### Impact Explanation
- A crash of the map data structure triggered by the Go runtime's race detector for maps (`fatal error: concurrent map writes`) terminates the entire kaia node process — this is reachable by any public-RPC caller submitting ordinary gasless transactions, without requiring a malicious peer/validator/node.
- Short of a full crash, corruption of `knownTxs` bookkeeping can let an attacker exceed the configured `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` caps or bypass the "known bundle tx" replay-protection check, which is the flow-control and anti-abuse mechanism for KIP-247 gasless transactions (fee-delegation-like settlement where the block proposer fronts gas and expects repayment via `GaslessSwapTx`). Bypassing these caps enables resource exhaustion of the gasless subsystem and could enable state divergence between honest nodes that experience the race differently (some crash/panic, others proceed with corrupted counters), affecting consensus-relevant execution ordering of gasless bundles.

### Likelihood Explanation
Any unprivileged party can trigger this by submitting multiple gasless bundle transactions (`GaslessApproveTx`/`GaslessSwapTx`) concurrently through the public RPC (`eth_sendRawTransaction` for multiple accounts, or batched submissions), which is a normal, permissionless capability. No special privileges, validator status, or peer-level access are required — only that `PreAddTx` be invoked concurrently for multiple senders' gasless transactions, which is plausible under realistic RPC load.

### Recommendation
Change `PreAddTx()` in `kaiax/gasless/impl/tx_pool.go` to acquire `g.knownTxsMu.Lock()` (exclusive) instead of `RLock()`, since it performs a write (`g.knownTxs.add(...)`) whenever `g.IsBundleTx(tx)` is true. More generally, audit all accessors of `knownTxs` to ensure every code path that calls `add`, `addKnownTx`, or `delete` holds the exclusive lock, and that read-only paths (`get`, `has`, `numQueue`, etc. used purely for read) are the only ones permitted to use `RLock()`. Consider replacing the bespoke locking scheme with a single `sync.Mutex` guarding all `knownTxs` operations to eliminate ambiguity between read/write access.

### Proof of Concept
1. Configure a node with the `gasless` module enabled (KIP-247).
2. From two or more distinct externally-owned accounts, concurrently submit valid `GaslessApproveTx`/`GaslessSwapTx` bundle transactions via public RPC (`eth_sendRawTransaction`) fast enough that multiple `TxPool.add()` → `GaslessModule.PreAddTx()` invocations overlap in time.
3. Because `PreAddTx` takes `g.knownTxsMu.RLock()` (line 39 of `tx_pool.go`) rather than `Lock()`, two goroutines can simultaneously execute `g.knownTxs.add(tx, TxStatusQueue)` (line 50), both mutating the same underlying Go map concurrently.
4. Under Go's race detector or under sufficient scheduling contention, this manifests as `fatal error: concurrent map writes`, crashing the node; without detection, it can silently corrupt the `knownTxs` map's internal bucket structure, causing lost/duplicated tracking entries that let the attacker exceed `MaxBundleTxsInQueue`/`MaxBundleTxsInPending` or resubmit an already-known bundle tx that should be rejected by the `ErrUnableToAddKnownBundleTx` check (line 42-44).

Note: I was not able to fully confirm from the indexed code whether every current call path into `PreAddTx` is already serialized by the outer `TxPool.mu` (which would reduce, but not eliminate given the read-lock design flaw itself, the practical exploitation window). This should be verified against the full `blockchain/tx_pool.go` call graph in a live session, since the index has size limits and some call-site details could not be retrieved.

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}
