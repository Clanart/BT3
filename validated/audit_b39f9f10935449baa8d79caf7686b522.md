## Title
Incomplete `.gitignore` special-character escaping allows `\n`-based rule injection via crafted file paths - (File: `app/src/lib/git/gitignore.ts`)

### Summary
`escapeGitSpecialCharacters` only escapes `[`, `]`, `!`, `*`, `#`, and `?`, but does not escape the newline character (`\n`). Since `appendIgnoreFile` writes the "escaped" path directly as a `.gitignore` line, a file path containing a newline is not neutralized, and everything after the `\n` becomes a new, attacker-controlled line in the repository's `.gitignore`.

### Finding Description
`escapeGitSpecialCharacters` builds its escaping regex from a fixed character class: [1](#0-0) 

This regex (`/[\[\]!\*\#\?]/g`) does not include `\n` (or `\r`). `appendIgnoreFile` calls this function on the untrusted `filePath` argument and then passes the "escaped" string straight to `appendIgnoreRule`, which concatenates it into the `.gitignore` file contents with no further sanitization: [2](#0-1) [3](#0-2) 

Because `.gitignore` is a line-oriented format, any `\n` embedded in the supposedly single "pattern" splits it into multiple independent lines when written to disk. If a repository contains a tracked/untracked entry whose name embeds a newline (Git itself supports newline characters in path names; they are only escaped in the *porcelain quoted* format, not disallowed on the filesystem), and that path string reaches `appendIgnoreFile` (e.g., via the "Ignore file" context-menu action in the Changes list, wired through `app-store.ts` / `dispatcher.ts` / `sidebar.tsx`), the attacker-chosen substring after the `\n` is written verbatim as a new `.gitignore` rule — for example `!*.git/hooks/*` or a blanket unignore (`!*`) — without any indication to the user beyond a single "ignore this file" action.

I was not able to fully trace, within the available tool budget, the exact status-parsing code path that produces the string ultimately handed to `appendIgnoreFile` from the Changes sidebar (i.e., whether GitHub Desktop's `git status -z`/porcelain parsing preserves a literal `\n` in a filename or already normalizes/rejects it before it reaches this function). That parsing layer would need to be reviewed to fully confirm end-to-end exploitability from a cloned malicious repository.

### Impact Explanation
If exploitable end-to-end, this allows silent corruption of the user's `.gitignore` — the user believes they are ignoring a single crafted-name file, but the repository's ignore rules are actually being rewritten with attacker-chosen content. This can be used to un-ignore sensitive paths (e.g., `.git/hooks`, credential files) or otherwise manipulate what gets tracked/ignored, matching the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Exploitability depends on whether an attacker can get a newline-containing path string routed unmodified into `appendIgnoreFile` via the UI (e.g., "Ignore file" on an untracked file with a crafted name). This requires the repository status/parsing layer to preserve the raw newline rather than displaying it in quoted/escaped porcelain form, which I could not confirm within this review. Absent that confirmation, likelihood is uncertain.

### Recommendation
Extend `escapeGitSpecialCharacters` (or add a dedicated check in `appendIgnoreFile`) to also escape/reject `\n` and `\r` characters (and any other line-terminating sequences) before the pattern is written to `.gitignore`, e.g. by escaping them as `\n`/`\r` literal escape sequences or refusing to ignore paths containing control characters.

### Proof of Concept
```ts
import { appendIgnoreFile } from '../../src/lib/git/gitignore'
// filePath containing an embedded newline and injected rule
await appendIgnoreFile(repository, 'innocuous.txt\n!*.git/hooks/*')
// resulting .gitignore now contains two lines:
// innocuous.txt
// !*.git/hooks/*
```
Because `escapeGitSpecialCharacters` at `app/src/lib/git/gitignore.ts` lines 103-109 never touches `\n`, this string passes through unmodified and is written as two separate `.gitignore` lines by `formatGitIgnoreContents`/`saveGitIgnore`.

**Caveat:** This finding is based on static analysis of `gitignore.ts`; I could not verify within this session whether the git-status parsing code that feeds file paths into `appendIgnoreFile` (from `app-store.ts`, `dispatcher.ts`, `sidebar.tsx`) actually preserves literal newlines from an attacker-controlled repository, which is required to trigger this from a cloned/fetched malicious repo without other user action.

```typescript
export async function appendIgnoreRule(
  repository: Repository,
  patterns: string | string[]
): Promise<void> {
  const text = (await readGitIgnoreAtRoot(repository)) || ''

  const currentContents = await formatGitIgnoreContents(text, repository)

  const newPatternText =
    patterns instanceof Array ? patterns.join('\n') : patterns
  const newText = await formatGitIgnoreContents(
    `${currentContents}${newPatternText}`,
    repository
  )

  await saveGitIgnore(repository, newText)
}
```

```typescript
export async function appendIgnoreFile(
  repository: Repository,
  filePath: string | string[]
): Promise<void> {
  if (filePath instanceof Array) {
    const escapedFilePaths = filePath.map(path =>
      escapeGitSpecialCharacters(path)
    )

    return appendIgnoreRule(repository, escapedFilePaths)
  }

  const escapedFilePath = escapeGitSpecialCharacters(filePath)
  return appendIgnoreRule(repository, escapedFilePath)
}
```

```typescript
export function escapeGitSpecialCharacters(pattern: string): string {
  const specialCharacters = /[\[\]!\*\#\?]/g

  return pattern.replaceAll(specialCharacters, match => {
    return '\\' + match
  })
}
```
