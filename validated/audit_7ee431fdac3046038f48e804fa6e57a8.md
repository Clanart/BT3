### Title
Change outputs between 546 and 10,000 sats are created but never scanned, permanently stranding funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Bitcoin wallet library creates change outputs whenever the leftover amount is at least `DUST = 546` sats, while the Serai processor's output scanner discards any received output worth less than `Bitcoin::DUST = 10_000` sats. Any change output in the [546, 10_000) range is placed on-chain at a consumed offset address yet is never reported as received, so it can never be respent — the protocol "receives" fewer sats than the transaction actually returned, mirroring the fee-on-transfer "recipient receives less than the recorded amount" class.

### Finding Description
In `SignableTransaction::new`, after fee accounting, leftover input value is pushed as a change output if `value >= DUST` where `DUST` is the wallet-local constant `546` (`networks/bitcoin/src/wallet/send.rs:32`, `send.rs:224-234`).

```rust
// networks/bitcoin/src/wallet/send.rs
pub const DUST: u64 = 546;   // line 32
...
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
  if value >= DUST {         // 546 sats
    tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
```

The processor, however, filters scanned outputs by its own much larger dust threshold in `processor/src/multisigs/scanner.rs:562-566`:

```rust
for output in network.get_outputs(&block, key).await {
  assert_eq!(output.key(), key);
  if output.balance().amount.0 >= N::DUST {   // Bitcoin::DUST = 10_000
    outputs.push(output);
```

with `Bitcoin::DUST = 10_000` defined at `processor/src/networks/bitcoin.rs:638`.

Additionally, `prepare_send` in `processor/src/networks/mod.rs:579-591` computes `on_chain_expected_change` and, if it is below `Self::DUST` (10,000), adds the theoretical change to `operating_costs` — i.e., it models the change as not coming back. But the actual `BSignableTransaction::new` call (`processor/src/networks/bitcoin.rs:446-452`) still passes `change`, so the wallet happily emits a real change output of e.g. 5,000 sats. That output sits on a registered offset script: the offset is consumed (`register_offset` is surjective and rejects re-registration, `wallet/mod.rs:180-196`), the scanner drops it, and no code path ever constructs a spend of it.

### Impact Explanation
Funds equal to the change amount (anywhere in the 546–9,999 sat range) are burned from the protocol's perspective on every send whose leftover falls in that window: they exist on-chain under a key Serai controls but are invisible to the scanner and unreachable by the planner. This is exactly the report's shape — value deducted/retained in transit such that the credited/receivable amount is less than what the transfer actually carried — except here the "fee" is a hard-coded threshold mismatch rather than a token mechanic. The loss is bounded to ~9,454 sats per transaction but recurs deterministically.

### Likelihood Explanation
Triggering requires only that `sum(inputs) - sum(payments) - fee_with_change` lands in [546, 10_000), which happens whenever inputs closely match payments — a common case when a plan's inputs are selected to roughly cover its payments. No adversary is needed; normal operation produces it. Reachability by an unprivileged party is satisfied because payment amounts and the resulting change are driven by public burn/withdrawal instructions any user can cause the protocol to sign.

### Recommendation
Use a single dust threshold: either lower `Bitcoin::DUST`/`scanner` filtering to the wallet's `DUST = 546` bound, or raise the wallet's change-creation check to the network's dust constant (`Self::DUST`) by parameterizing `SignableTransaction::new`. At minimum, make `SignableTransaction::new` accept the caller's minimum-change value so `prepare_send`'s `on_chain_expected_change < Self::DUST` accounting matches what the transaction builder actually does — leftover below the processor's dust should be folded into the fee (no change output) instead of being emitted as an unscannable output.

### Proof of Concept
1. Processor calls `make_signable_transaction` with inputs of `payment + fee_with_change + 5_000` sats and a `change` address (`processor/src/networks/bitcoin.rs:446-452`).
2. `SignableTransaction::new` computes `value = 5_000 >= 546` and appends a change `TxOut` of 5,000 sats (`send.rs:228-233`).
3. The signed transaction confirms; `get_outputs` returns the change `ReceivedOutput` (`processor/src/networks/bitcoin.rs:691-700`).
4. The scanner drops it: `5_000 < N::DUST (10_000)` (`processor/src/multisigs/scanner.rs:564`).
5. The 5,000 sats are on-chain, spendable only via the consumed change offset, and never scheduled for any future input set — permanently stranded while the fee accounting only recorded it as an operating cost estimate, not an actual locked output.
