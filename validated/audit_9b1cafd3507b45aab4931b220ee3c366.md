### Title
Argument/option injection via attacker-controlled remote URL in `addRemote`/`setRemoteURL` — missing `--` separator that `clone()` already has (File: `app/src/lib/git/remote.ts`)

### Summary
GitHub Desktop's `clone()` function explicitly guards against a git command-line argument-injection primitive by placing `--` before the URL and destination path so that a hostile value cannot be parsed as a git option: `args.push('--', url, path)` [1](#0-0) . The equivalent guard is missing from `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts`, which pass the raw, attacker-influenceable URL directly as a positional argument to `git remote add`/`git remote set-url` with no `--` terminator: [2](#0-1) [3](#0-2) .

### Finding Description
This is the same bug class as the Olympus report: a security check ("treat this URL as untrusted CLI input, isolate it with `--`") is applied to one high-risk operation (`clone`) but not consistently applied to the other operations that consume the exact same class of attacker-controlled input (adding/rewriting a remote URL). The invariant that should hold — "any external, attacker-influenced git remote URL must never be interpretable as a git command-line flag" — is broken for `addRemote`/`setRemoteURL`.

These functions are reachable with attacker-influenced URLs:
- `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, headCloneUrl)` where `headCloneUrl` originates from a pull request's `head.repo.clone_url`, a value coming from the GitHub API response (an "attacker controls a GitHub API object" scenario, e.g. a malicious/compromised GHES instance or a MITM'd API response) [4](#0-3) .
- `updateRemoteUrl` rewrites the default remote's URL to `apiRepo.clone_url` fetched from the API [5](#0-4) .

No other code path in the repository re-applies the `--` (or any dash-prefix rejection) guard — a search for the pattern (`startsWith('-')`, "ambiguous argument", etc.) across the codebase found no matches, confirming `clone.ts` is the only place this class of check exists.

### Impact Explanation
If a crafted `clone_url` value begins with `-` it is passed as the second positional argument to `git remote add <name> <url>` / `git remote set-url <name> <url>` without a `--` terminator, so git will attempt to parse it as an option to the `remote add`/`set-url` subcommand instead of a URL. Depending on the git/dugite version, this can trigger unexpected subcommand option behavior (e.g. `-f`, `-t`, `-m`, `--mirror`) or, on older/vulnerable git builds affected by the historical ambiguous-argument/SSH option-injection class of bugs (the same family `--` was added in `clone.ts` to defend against), can be leveraged toward command execution once the resulting malformed/attacker-chosen remote URL is later used for `fetch`/`push`/`pull`. At minimum, it silently corrupts the repository's remote configuration (what the user will subsequently fetch/push against) without the explicit backstop that `clone()` receives — directly matching the report's theme of "high-risk action not covered by the existing check."

### Likelihood Explanation
Medium. The trigger requires the user to have a pull request open from a fork whose `head.repo.clone_url` (or, for `updateRemoteUrl`, the tracked repository's `clone_url`) is attacker-influenced — i.e., the attacker controls the GitHub API response consumed by Desktop, which is one of the explicitly valid attacker models for this exercise. No local access, malware, or leaked credentials are required; the user simply views/opens a PR or lets Desktop refresh repository metadata.

### Recommendation
Apply the same `--` separator (or equivalent strict validation rejecting URLs beginning with `-`) used in `clone()` to `addRemote` and `setRemoteURL` in `app/src/lib/git/remote.ts`, e.g. `git(['remote', 'add', name, '--', url], ...)` and `git(['remote', 'set-url', name, '--', url], ...)` (verify dugite/git version support for `--` placement in these subcommands), and audit any other git subcommand invocations that accept externally-sourced URLs for the same gap.

### Proof of Concept
1. Attacker controls (or MITMs) a GitHub/GHES API response for a pull request such that `head.repo.clone_url` is set to a value starting with `-`, e.g. `-t maliciousbranch` or `--mirror=/tmp/x`.
2. Victim opens/views that pull request in Desktop; Desktop's `_findPullRequestBranch` cannot find an existing remote matching the URL and calls `addRemote(repository, forkRemoteName, headCloneUrl)` [4](#0-3) .
3. `addRemote` runs `git(['remote', 'add', name, url], ...)` with the malicious `url` value unguarded by `--` [2](#0-1) , causing git to parse the attacker-chosen string as a command option instead of a URL — unlike `clone()`, which would have rejected/neutralized this same input via its `--` separator [1](#0-0) .

Note: I was unable to determine the exact dugite/git version bundled with this build of Desktop, which affects whether the resulting option parsing escalates to code execution versus simply corrupting remote configuration; a Devin session with full repo/dependency access would be needed to pin down the exact git version and confirm exploitability level.
