### Title
Panic (indexing/assertion) on untrusted participant identifiers in PedPoP decryption/blame path causes denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2020-23273 is a heap-buffer-overflow DoS triggered by a crafted input file (`randomize_iparp` in tcpreplay). The Serai analog class is "memory-safety/abnormal-termination on attacker-supplied bytes". Rust prevents raw OOB access, but the equivalent reachable fault is an unconditional panic on untrusted input. `Decryption::register` and `Decryption::decrypt_with_proof` in the PedPoP encryption layer panic on `HashMap` lookups/assertions indexed by participant identifiers that originate from deserialized peer messages.

### Finding Description
`Decryption::register` asserts that a participant has not already registered an encryption key: `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")` at `crypto/dkg/pedpop/src/encryption.rs:356-359`. The `participant` value comes from a peer-supplied `EncryptionKeyMessage` delivered over the DKG channel (readable via `EncryptionKeyMessage::read`, which takes only `reader` and `params`, performing no deduplication itself, lines 57-59). Any participant that re-sends a registration message — trivially achievable since `Participant` is just a `u16` transmitted in plaintext — triggers `assert!` and aborts the host thread/process.

Similarly, `decrypt_with_proof` indexes `self.enc_keys[&decryptor]` at line 388. `decryptor` is the accusing participant supplied on the blame path; if the accusation names a participant index that never registered an encryption key (e.g., a spoofed/malformed blame naming an unregistered `Participant`), the `HashMap` indexing operator panics on the missing key. `encrypt` has the same pattern at line 466 (`self.decryption.enc_keys[&participant]`).

The reachable path is: attacker-controlled serialized DKG/blame bytes → `EncryptionKeyMessage::read` / `EncryptedMessage::read` → `register` / `decrypt_with_proof` → panic. This mirrors the CVE: a crafted input reaching a parsing/processing routine causes abnormal termination, i.e., denial of service.

### Impact Explanation
A panic in the DKG encryption/decryption path aborts the participant's DKG session (and, depending on runtime, the whole node process). For a threshold validator, crashing during key generation or blame resolution removes it from the protocol, which can stall the DKG (halting new-set creation) or abort blame resolution. This is a pure availability impact — the same impact class as the reference CVE (CVSS 5.5, A:H).

### Likelihood Explanation
Any participant able to send DKG protocol messages can trigger it: re-sending an `EncryptionKeyMessage` for the same `Participant` index hits the `assert!`, and a blame/accusation naming an unregistered `decryptor` index hits the unchecked `enc_keys[&decryptor]` lookup. No cryptographic break, key access, or special positioning is required — only the ability to send a duplicate or malformed participant index, which is within the normal reach of a DKG peer sending public protocol bytes.

### Recommendation
Replace panicking constructs on untrusted-derived identifiers with error returns:
- In `Decryption::register`, return `Err`/`DecryptionError` (or ignore/idempotently accept identical re-registrations) instead of `assert!`.
- In `decrypt_with_proof` (line 388) and `encrypt` (line 466), use `enc_keys.get(&decryptor)`/`get(&participant)` and map `None` to a defined error rather than indexing.
- Validate `Participant` indices against `ThresholdParams` (`1..=params.n()`) at deserialization boundaries before they reach these maps.

### Proof of Concept
```rust
// 1) register() double-registration panic:
let mut dec = Decryption::<Ed25519>::new(context);
let msg = EncryptionKeyMessage::read(&mut peer_bytes, params)?; // attacker-controlled
dec.register(p, msg.clone());          // first registration ok
dec.register(p, msg);                  // assert! fires -> panic

// 2) decrypt_with_proof missing-key panic:
// accuser supplies a blame whose `decryptor` Participant index never registered a key
dec.decrypt_with_proof(faulty, Participant(0xffff_0001 & 0xffff).into(), msg, Some(proof));
// self.enc_keys[&decryptor] at encryption.rs:388 -> index panic
```
Both faults are reachable purely from bytes the peer transmits; no secret material or collusion is needed.

Note on scope: this is a panic-based DoS analog (Rust cannot express the literal heap-buffer-overflow). The panic sites at `encryption.rs:356-359`, `:388`, and `:466` were verified directly; I did not fully trace the coordinator-side call chain that feeds `decryptor` into `decrypt_with_proof`, so reachability of the second site rests on the blame path passing an attacker-chosen participant index, which the function signature (`from`/`decryptor` as `Participant` arguments) supports.
