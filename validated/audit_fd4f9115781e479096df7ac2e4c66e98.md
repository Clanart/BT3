### Title
Webhook HMAC Verification Does Not Bind the Signature to the `X-Shopify-Shop-Domain` Header, Enabling Cross-Shop Webhook Replay - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an incoming webhook solely by HMAC-validating the raw request body against the app's shared secret. The `shop_domain` value that downstream jobs use to identify *which merchant* the webhook belongs to is read from the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC computation. This mirrors the "AssignmentHook does not sign over metaHash" bug class: a field that determines execution context (here, shop attribution) is left outside the signed payload, so it can be manipulated without invalidating the signature.

### Finding Description
`hmac_valid?` computes the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls this with only the body, and separately exposes `shop_domain` straight from the unauthenticated header: [2](#0-1) 

The default `WebhooksController#receive` builds a `ShopifyAPI::Webhooks::Request` from `raw_post` and `request.headers`, and the job templates use the resulting `shop`/`shop_domain` value (sourced from the same header) to look up the target shop and act on its data: [3](#0-2) [4](#0-3) 

Because the shared app secret is identical for every shop that installs the app (it is the app's API secret, not a per-shop secret), any merchant that installs the app can trigger a legitimate webhook on their own store, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — which is a validly-signed payload — and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `X-Shopify-Shop-Domain` header. Verification still succeeds because the header is not part of the signed data, so the forged shop attribution is accepted and the job is queued as if the payload came from the victim shop.

### Impact Explanation
This allows a malicious but validly-installed merchant to have their own webhook payloads processed as if they belong to a different (victim) shop, i.e., a cross-shop access/forged-attribution issue. Depending on which webhook topic is abused, the impact ranges from data corruption (feeding forged `orders/create`/`products/update` bodies into a victim shop's job) to more severe outcomes such as triggering `shop/redact` or `customers/redact` handling logic with attacker-controlled body content attributed to the victim shop's domain, since the job templates trust the header-derived `shop_domain` to find and act on the corresponding `Shop` record.

### Likelihood Explanation
Any account holder able to install the app on a store they control (a normal, "unrelated-merchant" capability, not a developer/host-operator privilege) can generate a validly-signed webhook and replay it with a modified header, since the header is not covered by the signature. No secret leakage or elevated privileges are required.

### Recommendation
Bind the shop attribution to the signed payload instead of trusting an unauthenticated header:
- Verify the `shop` value against the shop domain encoded inside the webhook body payload (Shopify includes shop-identifying fields in most webhook bodies), or
- Compute the HMAC over a canonical representation that includes the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) header values alongside the body, rejecting requests where the header-derived shop does not match data embedded in the verified payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates a product) causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, where `H = HMAC(app_secret, B)`.
3. Attacker intercepts/replays this exact request to the same endpoint but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `hmac_valid?` still validates because `H` matches `HMAC(app_secret, B)` — the header change does not affect the check in [1](#0-0) .
5. `WebhooksController#receive`/job templates process `B` attributing it to `victim-shop.myshopify.com`, as shown in [4](#0-3) .

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
```
