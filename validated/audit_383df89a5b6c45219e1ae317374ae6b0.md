Based on the investigation, I found `openBranchNameFromUrl` in the dispatcher, which is reachable from an unauthenticated deep link (`x-github-client://openRepo/...`) and passes an attacker-controlled string almost directly into a `git checkout` argument vector — a pattern structurally analogous to the report's core flaw: **a value that one code path validates is consumed unchecked by a different path**, corrupting downstream behavior.

### Title
Deep-link branch name is checked out via `checkoutLocalBranch` without re-validating that the resolved ref is a safe, non-flag-like value passed to `git checkout` - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
`parseAppURL` validates the `branch` query parameter from an `x-github-client://openRepo/...` deep link with `testForInvalidChars`, but this only rejects a specific blacklist of characters (control/invalid ref characters), not leading-dash "flag-like" strings. That value is passed all the way from `openBranchNameFromUrl` to `checkoutLocalBranch`, and ultimately into git argument arrays such as `getBranchCheckoutArgs`/`checkoutBranch`. Because the invariant "this string is safe to place as a bare CLI argument to git" is enforced only loosely at the parse boundary and never re-checked at the point of actual command construction, a link can supply a branch value that git or dugite's argument handling treats specially before the `--` separator is appended.

### Finding Description
`parseAppURL` in [1](#0-0)  accepts a `branch` parameter and only rejects values that fail `testForInvalidChars`, which is a character-class based ref-name check, not a check for shell/CLI-flag-style prefixes (e.g., `--upload-pack=`, `-o`, `--exec=`). This action flows into `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` [2](#0-1) , which calls `this.checkoutLocalBranch(repository, branchName)` with the raw string from the URL.

Contrast this with the clone URL path, which is explicitly hardened against this exact class of injection: `clone()` in `app/src/lib/git/clone.ts` appends `--` before the `url`/`path` arguments [3](#0-2) , and `getFetchArgs`/`fetchRefspec` place the remote name/refspec as trailing positional arguments after fixed flags [4](#0-3) . The `checkout` argument builder, however, does not add a `--` before the branch-derived name at every stage; `getBranchCheckoutArgs` puts the branch/name arguments before pushing `'--'` only at the end, and depends on the branch object's `name`/`nameWithoutRemote` fields having been produced by trusted local `git branch -vv`/`for-each-ref` output rather than the untrusted string coming straight from the URL [5](#0-4) .

I was not able to fully trace `checkoutLocalBranch` in the dispatcher to confirm whether it creates a `createBranch`/`createBranch`-based flow that ultimately invokes `git branch <name>` or `git checkout -b <name>` with the deep-link string as a raw positional argument before any `--` separator, because that specific implementation was not returned by my searches and the file's full content around that helper is not indexed. **This is the key open question**: if `checkoutLocalBranch` (or the underlying `createBranch`/`checkoutBranch` git calls it triggers when the named branch does not yet exist locally) ever places the untrusted branch string as an argument to `git` before a `--` terminator, then a branch value like `--upload-pack=touch${IFS}/tmp/pwned;` or similar argument-injection payload could be interpreted as a git flag rather than a ref name, since `testForInvalidChars` does not block leading dashes.

### Impact Explanation
If the ref/name argument-injection path is confirmed, an attacker who gets a victim to click a single `x-github-client://openRepo/...?branch=...` link (no cloned/malicious-repo access needed beyond crafting the link) could inject arbitrary git command-line flags into a local git invocation running with the victim's privileges, potentially resulting in code execution (e.g., via git flags that execute helper programs) or corruption of the target repository state — satisfying the "code execution" and "silent corruption of what the user commits" impact categories from the Valid Impact policy.

### Likelihood Explanation
Likelihood is currently **unconfirmed** rather than demonstrated: the report `dir` for `checkoutLocalBranch`'s exact git invocation was not retrievable from the index, so I cannot confirm whether `--` separation or additional sanitization (beyond `testForInvalidChars`) is applied at that specific call site before the branch string reaches `git`. Given how consistently and defensively other parts of this codebase (clone, fetch, path resolution, hooks proxying, OAuth CSRF state) add explicit hardening with dedicated unit tests (e.g., `clone-path-safety-test.ts`, `path-test.ts`, `parse-app-url-test.ts`), it's plausible this path is already equally hardened but simply wasn't captured in my search results.

### Recommendation
- Verify (with direct file reads of `dispatcher.ts`'s `checkoutLocalBranch`/`createBranch` call chain and `app/src/lib/git/branch.ts`'s `createBranch`) whether the deep-link-supplied branch name is ever passed to a `git` invocation as a bare argument before a `--` terminator.
- If so, either add a `--` separator immediately before the branch name in every git invocation that consumes it, or extend `testForInvalidChars`/`parseAppURL` to reject any branch value starting with `-`.

### Proof of Concept
Not independently verified — would require confirming the exact argument construction inside `checkoutLocalBranch`'s underlying git call, which was not available in the indexed code I could retrieve.   private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
