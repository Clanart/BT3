Confirmed: mirror URLs are entirely unvalidated free-form strings (`DLNewMirror.urls: list[str]` in `chia/wallet/wallet_request_types.py`), stored on-chain via `create_mirror_puzzle()` memos, and later fetched directly via `http_download()`'s `session.get(server_info.url + "/" + filename, ...)` with no scheme, host, or IP-range restriction.

### Title
Unauthenticated blind SSRF via unvalidated DataLayer mirror URLs fetched by `http_download` - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can call `dl_new_mirror` (RPC `/dl_new_mirror`, `DataLayerWallet.create_new_mirror`) to publish arbitrary attacker-controlled strings as "mirror URLs" for a DataLayer singleton they own, with zero validation of scheme, hostname, or IP range. Any other DataLayer node/client that subscribes to that store id (a normal, low-privilege DL client action) will automatically have its DataLayer service issue outbound HTTP requests to those attacker-supplied URLs when syncing (`fetch_and_validate` → `insert_from_delta_file` → `download_file` → `http_download`). This is structurally the same bug class as the GeoServer WMS `sld=<url>` SSRF: a user-controlled URL parameter is consumed by a server-side HTTP client with no allow-list/deny-list/URL check, enabling blind SSRF against the fetching node's internal network.

### Finding Description
- `DLNewMirror.urls: list[str]` is taken verbatim from RPC input in `chia/wallet/wallet_request_types.py` (lines 1853-1858) and passed to `DataLayerWallet.create_new_mirror()` [1](#0-0) , which encodes the URLs as memos on a `create_mirror_puzzle()` coin with no validation whatsoever.
- `DataLayer.add_mirror()` only checks the list is non-empty, no URL/scheme/host checks: [2](#0-1) 
- Any DataLayer client independently decides to subscribe to a given `store_id` via `/subscribe`: [3](#0-2) . Once subscribed, mirror URLs are pulled straight from the wallet/chain data with only trailing-slash trimming: [4](#0-3) 
- The periodic sync loop (`fetch_and_validate`) then iterates these server URLs and calls `insert_from_delta_file` → `download_file` → `http_download`, which performs an unrestricted `aiohttp` GET to `server_info.url + "/" + filename`: [5](#0-4) 
- There is no scheme allow-list (e.g., rejecting non-`http(s)`), no check against private/loopback/link-local/metadata IP ranges, and no restriction preventing URLs that resolve to internal infrastructure (e.g., cloud metadata endpoints, internal admin panels, or other local services) from being targeted. The project's own `.cursor/context/data-layer.md` documents this as a known trust boundary: "Plugin and mirror URLs are external trust inputs... file path/name validation must stay strict," but no equivalent enforcement exists for the URL host/scheme itself. [6](#0-5) 

### Impact Explanation
This allows an unprivileged DataLayer store owner (any wallet user who can afford the mirror coin amount + fee) to force any other DL client that subscribes to their store to make outbound HTTP requests to attacker-chosen destinations — a classic blind SSRF. This can be used to: probe/attack internal services reachable only from the victim's host/network, hit cloud metadata endpoints (e.g., `http://169.254.169.254/...`) to attempt credential exfiltration, or perform request smuggling/port scanning of internal infrastructure, all triggered automatically by the victim's own background sync loop (`periodically_manage_data`) without any user interaction beyond having subscribed to the store.

### Likelihood Explanation
Likelihood is high for any operator running a DataLayer client that subscribes to third-party stores (a normal, encouraged DL workflow), since publishing a malicious mirror URL requires only a standard `dl_new_mirror` wallet transaction — no special privilege, no consensus rule violation, and no interaction beyond the victim choosing to subscribe to the attacker's `store_id`.

### Recommendation
Validate mirror/server URLs before storing and before use in `http_download`/`download_file`: enforce an allowed scheme list (`http`/`https` only), resolve and reject requests targeting loopback, link-local, private, and cloud-metadata IP ranges (unless explicitly configured for testing), and consider adding an opt-in URL-check mechanism analogous to GeoServer's "URL Checks" feature (regex allow-lists) before a subscribed store's mirrors are dereferenced.

### Proof of Concept
1. Attacker creates a DataLayer store and runs `chia data add_mirror --id <store_id> --url http://169.254.169.254/latest/meta-data/ -a 1` (or targets an internal service URL) via `chia/cmds/data.py`/`add_mirror_cmd` [7](#0-6) , publishing the mirror on chain.
2. Victim, running a DataLayer node, subscribes to `store_id` via `/subscribe` [3](#0-2) .
3. Victim's `periodically_manage_data` background loop calls `update_subscriptions_from_wallet` then `fetch_and_validate`, which reads the attacker's mirror URL and issues an HTTP GET to it via `http_download` [5](#0-4) , with no validation preventing the request from targeting internal/metadata endpoints.

        """
        subscribe to singleton
        """

        if store_id is None:
            raise Exception("missing store id in request")

        store_id_bytes = bytes32.from_hexstr(store_id)

    """

        async with session.get(
