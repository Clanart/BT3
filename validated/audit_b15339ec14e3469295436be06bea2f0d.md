## Finding: Git's clone directory-collision protection is explicitly disabled during recursive clones

The strongest local analog to the reported "using an indirect/weak proxy instead of enforcing the real safety check" pattern is in `app/src/lib/git/clone.ts`. GitHub Desktop performs `git clone --recursive` for every clone, and explicitly forces the environment variable that disables Git's own clone-time collision/escape protection: [1](#0-0) 

### Title
Recursive clone disables Git's built-in clone-protection guard against malicious submodule/`.git` path collisions - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` builds the environment for the `git clone` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while also always passing `--recursive`. [1](#0-0)  This is the same env var upstream Git introduced as a safety gate (paired with symlink/case-collision detection for nested `.git`/`hooks` paths during recursive clones of untrusted repositories). By forcing it to `'false'`, Desktop trusts the *appearance* of a normal repository/submodule layout rather than letting Git actually enforce the check that prevents a malicious remote from placing files where they can clobber the outer repository's `.git` directory or hooks during checkout — the same "trust an indirect signal instead of enforcing the real guard" pattern as the seed report's `balanceOf()` check standing in for an actual lock.

### Finding Description
`clone()` in `app/src/lib/git/clone.ts` constructs its execution environment like this:
```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
```
`envForRemoteOperation` only sets up authentication/proxy env vars [2](#0-1)  — it does not touch clone protection. The `GIT_CLONE_PROTECTION_ACTIVE=false` override is added unconditionally on top, for every clone Desktop performs, including cloning arbitrary/untrusted URLs entered by the user or opened via `x-github-client://openRepo` deep links (`openOrCloneRepository` / `openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`). [3](#0-2) 

Because `--recursive` is always passed, submodules referenced by an attacker-controlled remote are fetched and checked out automatically as part of the clone, with the exact Git-side guard that would refuse dangerous path layouts turned off. This mirrors `updateSubmodulesAfterOperation`, which similarly runs `git submodule update --init --recursive` and can additionally pass `protocol.file.allow=always`, further loosening the submodule fetch surface. [4](#0-3) 

The broken invariant: Desktop assumes it doesn't need Git's clone-time layout/collision protection because it separately checks `isClonePathSensitive()` for the *destination* directory. [5](#0-4)  That check only guards against the top-level clone target being a sensitive host path (home dir, `.ssh`, `.gnupg`, etc.) — it says nothing about what a malicious repository can do *inside* the clone via nested submodule/gitlink paths that collide with `.git`, `hooks`, or similar special-cased Git paths on case-insensitive or path-normalizing filesystems (macOS/Windows). Turning off Git's own protection removes the layer that would have stopped that regardless of the destination-path check.

### Impact Explanation
If a crafted repository (attacker-controlled clone URL, e.g. from a phishing link, a malicious org, or a deep link) contains a submodule/gitlink path designed to collide with the outer repository's `.git` directory contents (a known class of Git clone vulnerabilities), disabling `GIT_CLONE_PROTECTION_ACTIVE` removes Git's own defense against this on the very first `git clone --recursive`, before the user has had any chance to inspect the repository. That can result in files/hooks being written outside the intended checkout tree or overwriting the outer repo's Git metadata, which can lead to arbitrary command execution the next time Git operations run in that repository (e.g. via `core.hooksPath`/`post-checkout` style hooks). This satisfies the "attacker controls a cloned repository → code execution / file write outside the repo" impact category.

### Likelihood Explanation
Cloning attacker-supplied URLs is a core, unprivileged Desktop workflow — via the Clone dialog, "Open in Desktop" GitHub buttons, or the `x-github-client://openRepo?url=...` protocol handler that reaches `openOrCloneRepository`. [3](#0-2)  No special user action beyond initiating a normal clone/open-in-Desktop flow is required, and `--recursive` + the disabled protection apply to every such clone unconditionally, not just ones the user has vetted.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let Git's built-in protection run during `clone --recursive`; if it rejects a repository, surface that as an error to the user rather than silently overriding the safety check. If there is a legitimate compatibility reason for the override (e.g. false positives on certain layouts), it should be scoped narrowly and only after Desktop performs its own equivalent validation of submodule paths — not a blanket disable applied to every clone of untrusted content.

### Proof of Concept
1. Attacker publishes/hosts a repository containing a submodule (or nested gitlink) whose path is engineered to alias the outer repository's `.git` directory (or a subpath under it) on a case-insensitive/normalizing filesystem — this is the standard technique the `GIT_CLONE_PROTECTION_ACTIVE` guard exists to catch.
2. Victim clicks a link ("Open in Desktop" / `x-github-client://openRepo?url=<attacker-url>`) or pastes the URL into the Clone dialog.
3. Desktop calls `clone(url, path, options)` in `app/src/lib/git/clone.ts`, which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` forced in the environment. [1](#0-0) 
4. Because the protection is disabled, Git performs the recursive submodule checkout without refusing the colliding path, allowing the attacker's crafted content to land inside/alongside the outer repository's `.git` metadata instead of being rejected as it would be with the protection enabled.

```typescript
/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
