### Title
Partial-fill escrow release rounds down to zero, letting a solver's real output transfer go uncompensated - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrowed input tokens released to a solver on a non-completing partial fill via plain integer division, `(order.inputs[i].amount * fillAmount) / totalRequired`. When `order.inputs[i].amount * fillAmount < totalRequired`, this floors to `0`: the solver transfers real output tokens to the beneficiary but receives zero input tokens in return. This is the same broken invariant as the SecondSwap `StepVesting` finding — an integer division whose numerator can be smaller than its denominator, rounding a legitimate participant's entitlement down to zero and causing an uncompensated loss of funds.

### Finding Description
In `IntrinsicIntents._fillSameChain`, non-final partial fills compute the escrow release as: [1](#0-0) 

Only the *completing* fill (`amountFilled == totalRequired`) is special-cased to release the entire remaining escrow balance, avoiding rounding dust: [2](#0-1) 

Every other (non-completing) partial fill instead uses the raw floor-division formula `escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired`. There is no check that this result is non-zero, and no revert when it is. Meanwhile the beneficiary transfer of `fillAmount`+`beneficiaryShare` output tokens happens unconditionally before this computation: [3](#0-2) 

This is structurally identical to the reported `StepVesting._createVesting` bug: `releaseRate = (totalAmount - amountClaimed) / (numOfSteps - stepsClaimed)` can floor to `0` whenever the numerator is smaller than the denominator, silently destroying the claimant's entitlement. Here, `order.inputs[i].amount * fillAmount` plays the role of the numerator and `totalRequired` the denominator — whenever the input escrow amount is small relative to the required output amount (e.g. a low-decimal or low-value input token paired against a large/high-precision output requirement), any partial fill that isn't the exact completing one can legitimately compute to `escrowedAmount == 0` while the solver has already paid the beneficiary in full for that increment.

Unlike the vesting report's beneficiary who was passive, here the affected party is the solver, but this is a normal, permissionless protocol participant (any address calling `fillOrder`), not an admin/relayer/prover, and it happens through ordinary use of the documented partial-fill feature — no malicious peer or governance actor is required.

### Impact Explanation
A solver performing a legitimate partial fill on an order where `order.inputs[i].amount` is small relative to `order.output.assets[i].amount` (e.g. `inputAmount=1` unit of a coarse-decimals token vs. a large `totalRequired` on a fine-decimals output token) transfers real ERC-20/native output tokens to the beneficiary but receives `escrowedAmount == 0` back. The tokens sent to the beneficiary are unrecoverable by the solver (the beneficiary is a normal user, not a refund path), so the solver suffers an outright, uncompensated loss of funds. This maps to the "stealing or loss of funds" bounty category. Because the escrow contract itself never reverts or floors-with-minimum, the loss is silent — the fill still succeeds, emits `PartialFill`, and advances `_partialFills` state as if payment had been made.

### Likelihood Explanation
Any order creator (the user placing the order, who fully controls `order.inputs[i].amount` and `order.output.assets[i].amount`) can construct input/output amount pairs that make this rounding-to-zero condition trivially reachable — analogous to the vesting report's "malicious user can abuse this bug ... with carefully selected amount". A solver who is unaware of the exact integer ratio (or who is quoting a partial fill against a not-yet-fully-informed order) can be lured into filling a small increment of such an order and losing the corresponding escrow entitlement. No relayer, prover, or privileged actor is needed — only an ordinary `fillOrder` call under normal, permissionless conditions.

### Recommendation
Apply the same "release-the-actual-remaining-amount" pattern used for the completing-fill branch to intermediate partial fills as well, or explicitly guard against zero-value releases:
- Track cumulative released escrow (`releasedSoFar`) per `(commitment, inputToken)` and compute each fill's release as `floor(inputs[i].amount * amountFilled / totalRequired) - releasedSoFar`, which guarantees the *cumulative* released amount tracks the true proportional entitlement and never strands dust on any individual solver.
- Alternatively, revert the fill (`InvalidInput`/`DustFill`) if the computed `escrowedAmount` for a non-completing fill would be `0`, forcing solvers to fill in increments large enough to be compensated, rather than silently absorbing the loss.

### Proof of Concept
1. User places an order with `inputs[0].amount = 1` (e.g. a token unit) and `output.assets[0].amount = 1_000_000` (a large, fine-grained `totalRequired`).
2. A solver calls `fillOrder` with `outputs[0].amount = 500_000` (a legitimate 50% partial fill, well below `totalRequired`).
3. Inside `_fillSameChain`: `fillAmount = 500_000`, `amountFilled = 500_000 != totalRequired (1_000_000)`, so the non-completing branch computes `escrowedAmount = (1 * 500_000) / 1_000_000 = 0` (floor).
4. The solver's `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` at line 107 still sends the solver's 500,000 output tokens to the beneficiary.
5. `escrowedInputs[0] = {token, amount: 0}` is what gets released to the solver via `_withdraw` — the solver receives nothing for real value delivered. [4](#0-3)
