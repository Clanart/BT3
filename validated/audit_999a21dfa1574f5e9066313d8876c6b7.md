## Title
Escrow release/refund silently succeeds on non-standard ERC20 return values, permanently burning escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and elsewhere correctly uses `SafeERC20`/`safeTransferFrom` for inbound token movement [1](#0-0) , but the escrow-release path `withdraw()` and the `SweepDust` handler pay out tokens with a raw low-level `.call` to the ERC20 `transfer` selector and only check that the call did not revert — the returned `bool success` payload from the token is never decoded or verified.

### Finding Description
In `withdraw()`, once a `RedeemEscrow`/refund request is authenticated via Hyperbridge, the contract pays the beneficiary using: [2](#0-1) 
The same unchecked pattern is used for protocol/transaction fee payout and in the `SweepDust` incoming-request handler: [3](#0-2) [4](#0-3) 

`token.call(...)` only returns `success == true` when the external call did not revert (e.g., target has code and doesn't throw). Per EIP-20, a non-compliant token is allowed to return `false` instead of reverting on a failed transfer; some tokens also return no data at all in success cases but could still return `false` on a specific failure path (e.g., paused/blacklisted state, insufficient balance under certain implementations). Since the return data is discarded, `success` is `true` even when the token itself reports `amount == 0` sent, i.e., `false`.

Immediately after the unchecked transfer, the contract irreversibly updates accounting as if the transfer succeeded: [5](#0-4) 
`_filled[body.commitment] = beneficiary;` and `_orders[body.commitment][token] -= amount;` are both applied unconditionally after the `.call`, and the function emits `EscrowReleased`/`EscrowRefunded`. Once this fires, the corresponding Hyperbridge GET-response replay guard (`Filled()` check in `onGetResponse`) prevents any retry: [6](#0-5) 
so there is no path to re-attempt the payout once escrow bookkeeping has been zeroed.

Note the contract already declares `using SafeERC20 for IERC20;` and uses `safeTransferFrom` for inbound transfers elsewhere in the same file [7](#0-6) , confirming the intended, safe pattern was not applied consistently to the escrow-payout path.

### Impact Explanation
This is an intent-settlement / bridge-custody fund-loss bug: the escrowed input tokens (locked on behalf of a solver/user awaiting redemption) can be marked as released or refunded — deleting the internal accounting and emitting the terminal event — while the beneficiary receives zero tokens, whenever the underlying ERC20 is a non-standard token that signals failure via a `false` return rather than a revert. The tokens remain stuck in the contract with no accounting entry pointing to them and no retry mechanism, resulting in permanent loss of the escrowed funds for the rightful beneficiary.

### Likelihood Explanation
This is triggered purely by the ERC20 token type used for an order's input/fee token — no malicious relayer, prover, or admin action is required. Any user/solver who creates or fills an intent using a non-fully-compliant ERC20 (returns `false` on failure instead of reverting; several real, non-esoteric tokens deviate from strict EIP-20 semantics in similar ways) will trigger this on the ordinary settlement path.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payouts in `withdraw()`, fee redemption, and `SweepDust` handling with `IERC20(token).safeTransfer(beneficiary, amount)` (the library is already imported and used elsewhere in the file), so a `false` return value reverts the transaction instead of being silently treated as success.

### Proof of Concept
1. Create/fill an order whose input token is a non-standard ERC20 that returns `false` on a failed `transfer` (rather than reverting) under some condition (e.g., recipient blacklisted, contract paused, insufficient allowance edge-case).
2. Trigger the redeem-escrow flow so Hyperbridge delivers the authenticated `RedeemEscrow`/refund request, invoking `withdraw()`.
3. At line 697, `token.call(...)` returns `success = true` (the call itself doesn't revert) even though the token internally returned `false` and moved no funds.
4. `_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` execute, `EscrowReleased`/`EscrowRefunded` is emitted.
5. The beneficiary never receives the tokens; the tokens remain locked in the contract with no accounting reference, and the replay guard in `onGetResponse` blocks any future retry — permanent fund loss.
