This confirms the mechanism precisely. The `DiffSelection` object stores selected lines by **absolute index positions** derived from the diff hunks that were rendered when the user made their selection [1](#0-0) . When the working directory diff is reloaded (e.g. because the file changed on disk), the code explicitly acknowledges that "the diff might have changed dramatically since last we loaded it" but only prunes indices that no longer exist as includeable lines — it does not revalidate that a surviving index number still corresponds to the same logical line [2](#0-1) . Then, at commit time, `applyPatchToIndex` re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and feeds it straight into `formatPatch` together with the file's stale `selection` object [3](#0-2) , and `formatPatch` builds the patch purely by testing `file.selection.isSelected(absoluteIndex)` against the hunk/line positions of that freshly fetched diff [4](#0-3) .

### Title
Stale line-selection indices are replayed against a freshly re-fetched diff during partial commit, silently corrupting which lines are staged - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` (used by `stageFiles`, invoked from `_commitIncludedChanges`) discards the diff the user actually reviewed and re-fetches a brand-new working-directory diff from disk right before building the commit patch, then reuses the `DiffSelection` object computed against the *old* diff to decide which lines to include. Line selection is tracked purely by numeric line-offset ("absolute index"), not by line content or hash, so if the file on disk changes between diff-render/selection time and commit time, the offsets silently point at different logical lines in the new diff.

### Finding Description
`DiffSelection.isSelected(lineIndex)` only knows about integer indices — it has no concept of the actual line content it was originally applied to [5](#0-4) . The `updateChangesWorkingDirectoryDiff` refresh path (triggered on every status refresh, e.g. background auto-fetch or file-watcher events) explicitly documents the gap: it only removes indices that no longer exist as includeable lines, but does **not** verify the remaining selected indices still map to the same lines: "The diff might have changed dramatically since last we loaded it. Ideally we would be more clever about validating that any partial selection state is still valid by ensuring that selected lines still exist but for now we'll settle on just updating the selectable lines..." [6](#0-5) .

At actual commit time this stale-selection problem is worse: `applyPatchToIndex` never uses the diff shown in the UI at all. It independently calls `getWorkingDirectoryDiff(repository, file)` again just before formatting the patch [7](#0-6) , and `formatPatch` walks the hunks of *that* new diff, testing `file.selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` from the new hunk layout [8](#0-7) . If line count/positions shifted (insertions/deletions elsewhere in the file, hunks merging/splitting, whitespace-mode toggles, or content changed by another process/git hook/smudge filter between the time the user selected lines and the time they click "Commit"), the same numeric indices now correspond to different lines. The generated patch is then applied straight to the index with `git apply --cached` with no re-confirmation to the user [3](#0-2) .

Existing guards do not stop this: the only mitigation is in the read/render path (`updateChangesWorkingDirectoryDiff`), which prunes indices no longer "includeable" — it does nothing to protect the commit path, since `applyPatchToIndex` re-fetches its own independent diff copy and never consults the sanitized/pruned selection state from `updateChangesWorkingDirectoryDiff`.

### Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug class. A user reviewing a diff and selecting specific lines for a partial commit can end up committing (and later pushing) different lines than what they visually selected and believed they were including — potentially staging unreviewed/unwanted content (e.g. secrets, debug code, or lines from a different hunk) or omitting content they intended to include, without any error or warning. Because this silently mutates the commit content rather than failing loudly, it directly matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Desktop actively polls/refreshes repository status in the background (auto-fetch, focus events, file-system watcher) while the Changes view is open, so the working tree diff for a selected file can legitimately change between the time a user reviews/selects lines and the time they press "Commit" — this is a normal, not contrived, workflow window. Any process that touches the file in that window (a build tool, another editor, an auto-formatter, or content mutated by a git clean/smudge filter defined in a cloned/fetched malicious repository's `.gitattributes`) can shift line offsets and trigger the mismatch, without any admin rights or local malware needed beyond normal repository content.

### Recommendation
Before generating the commit patch, `applyPatchToIndex`/`formatPatch` should validate the selection against the newly-fetched diff (e.g., by re-deriving selectable lines the same way `updateChangesWorkingDirectoryDiff` does, or ideally by matching lines using content/hash rather than raw numeric index) and abort/refresh-and-reprompt the user if the diff has materially changed since the selection was made, rather than silently mapping old indices onto new hunks.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file, producing a diff with several hunks.
2. In the Changes view, select only specific lines (e.g., lines 10–12) for a partial commit — this creates a `DiffSelection` with diverging line indices `{10,11,12}` relative to the currently rendered diff/hunks [9](#0-8) .
3. Before clicking "Commit", cause the file's diff shape to shift without changing the total selectable line count in a way Desktop would prune (e.g., another process/editor inserts and removes an equal number of lines earlier in the file, or a `.gitattributes` filter transforms content on `git diff`/`git status` calls) so hunk boundaries move but indices 10–12 remain "includeable."
4. Click "Commit". `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` fetches a fresh diff and calls `formatPatch(file, diff)`, which tests `file.selection.isSelected(10..12)` against the new hunk layout [8](#0-7) [7](#0-6) .
5. Inspect the resulting commit: the staged/committed lines correspond to different logical content than what the user visually selected in step 2, with no warning shown.
