### Title
Secret-dependent table indexing in "constant-time" `straus`/`pippenger` and variable-time batch verification leaks secret share bits via cache side-channel - ([File: crypto/multiexp/src/straus.rs](crypto/multiexp/src/straus.rs))

### Summary
Analogous to CVE-2018-0498 (cache-based side-channel enabling partial secret recovery in mbed TLS), Serai's multiexponentiation routines index lookup tables and buckets directly by secret scalar digits. The non-vartime `straus` and `pippenger` functions perform `tables[s][usize::from(groupings[s][b])]` and `buckets[usize::from(bits[p][n])] += pairs[p].1` — memory accesses whose addresses are a function of secret bits, exactly the bug class of the mbed TLS CBC/record-decryption table lookups.

### Finding Description
`multiexp` (the constant-time entry point) dispatches to `straus` for <50 pairs and `pippenger` for larger inputs (`crypto/multiexp/src/lib.rs:183-189`). Both implementations build per-point tables and then index them by windowed chunks of the scalar:

- `crypto/multiexp/src/straus.rs:42-44`: `res += tables[s][usize::from(groupings[s][b])]` — the table row selected is `groupings[s][b]`, a nibble of the secret scalar produced by `prep_bits` (`crypto/multiexp/src/lib.rs:54-74`).
- `crypto/multiexp/src/pippenger.rs:24-27`: `buckets[usize::from(bits[p][n])] += pairs[p].1` — a secret-dependent write address across up to 256 bucket entries.

Unlike `ed448`'s `Point::mul` and `dalek-ff-group`'s `pow`, which iterate all 16 table entries with `conditional_select` (`crypto/ed448/src/point.rs:258-266`, `crypto/dalek-ff-group/src/lib.rs:223-232`), Straus/Pippenger touch only the secret-selected cache line. A co-located unprivileged observer (Prime+Probe / Flush+Reload, the same AV:L model as CVE-2018-0498) recovers scalar nibbles per window position.

The reachable secret-bearing path is PedPoP share verification: `KeyMachine::calculate_share` queues `share_verification_statements(self.params.i(), &self.commitments[&l], share)` — where `share` is the received secret share accumulated into `self.secret` (the victim's private key share) — into a `BatchVerifier` that runs `verify_with_vartime_blame()` (`crypto/dkg/pedpop/src/lib.rs:487-499`). The batch verifier evaluates statements of the form `share * G == expected` via multiexp, so the secret scalar's nibbles drive table/bucket selection on every DKG execution. An attacker who can induce repeated DKG/share-verification runs (as a participant submitting `EncryptedMessage`s) and observe cache state on the same machine accumulates partial scalar bits, degrading the key share's entropy.

### Impact Explanation
Cache-observable leakage of secret scalar digits during share verification and any other `multiexp`/`BatchVerifier` evaluation over secret scalars reduces the effective security of the FROST threshold key share — the same "partial plaintext/key recovery" impact rated Medium (CVSS 4.7) in CVE-2018-0498. Leakage of nonce-adjacent scalars is additionally amplified by Schnorr-style signature equations where partial nonce/secret bits plus lattice reduction can yield full key recovery.

### Likelihood Explanation
Requires local co-residency with the signing/verification process (matching the CVE's AV:L vector) and repeated observations; single-trace leakage is partial. The defect is unconditional in the code — the "constant-time" label is violated on every call — so likelihood is bounded by deployment environment, not by triggerability. Medium.

### Recommendation
- For scalars that may be secret, replace secret-indexed lookup with constant-time selection over all table entries (as `pow`/`Point::mul` already do), or route secret-scalar multiexp through complete-form scalar multiplication per pair.
- Never feed secret scalars into `*_vartime`/batch-verification paths; in `calculate_share`, verify shares with `share * C::generator()` (constant-time scalar mul) compared against the public expectation instead of queueing the secret into `BatchVerifier`, or bind a random blinding scalar before batching.
- Document explicitly that `straus`/`pippenger` are only safe for public scalars.

### Proof of Concept
Root cause demonstrated at `crypto/multiexp/src/straus.rs:42-44` and `crypto/multiexp/src/pippenger.rs:24-27`: the memory index into `tables`/`buckets` is `groupings[s][b]` / `bits[p][n]`, populated from `pair.0.to_le_bits()` in `prep_bits` (`crypto/multiexp/src/lib.rs:66-70`). Any call chain reaching `multiexp()` or `BatchVerifier::verify_*` with a secret `C::F` scalar — e.g., the secret `share` queued at `crypto/dkg/pedpop/src/lib.rs:490` — emits a cache-line access pattern that encodes the scalar's windowed digits, observable to a local attacker identical to the mbed TLS CBC cache attack.
