### Title
Stale-selection patch application in `applyPatchToIndex` allows silent corruption of partial commits - (File: app/src/lib/git/apply.ts)

### Summary
`createCommit`/`stageFiles`/`applyPatchToIndex` re-derive the working-directory diff at commit time and apply the user's previously-captured line-selection indices against that freshly-fetched diff without verifying the diff content still matches what the selection was computed from. If the working tree content of a file changes between the moment the user reviews/selects lines in the Changes view and the moment Desktop actually stages/commits (a window that is trivially widenable — background processes, editors with autosave, git hooks, or a malicious build/watch script inside the very repo the user is working in), the byte offsets/line numbers in `DiffSelection` no longer correspond to the same logical content, and `formatPatch`/`applyPatchToIndex` will silently synthesize and apply a patch that stages/commits different content than what the user saw and approved.

### Finding Description
This mirrors the `DstSwapper._processTx` invariant break: the contract validated an *increase* using a snapshot comparison (`balanceBefore`/`balanceAfter`) without accounting for the fact that shared/mutable state could have moved between the time an amount was decided and the time it was consumed, letting stale accounting be reused across operations. Here, `DiffSelection` (an array of line indices/ranges) is decided by the renderer based on a `diff` object obtained via `getWorkingDirectoryDiff` and shown to the user in `Changes`/`SeamlessDiffSwitcher` (`app/src/ui/changes/changes.tsx:69-100`). That selection object, tied to `WorkingDirectoryFileChange`, is passed down through `Dispatcher._commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`.

`applyPatchToIndex` does **not** reuse the diff the user actually reviewed. It calls `getWorkingDirectoryDiff(repository, file)` again (`apply.ts:60`), producing a new diff from the current on-disk state, and then calls `formatPatch(file, diff)` (`apply.ts:80`), which walks `diff.hunks` and asks `file.selection.isSelected(absoluteIndex)` for each line based on positional index (`patch-formatter.ts:143-206`). If the file's content on disk has changed (extra/removed lines, reordering, or any edit that shifts hunk offsets) between the original diff-render and this second fetch, the same numeric line indices from the stale selection will now point at different lines/hunks in the new diff. `formatPatch` will happily construct a syntactically valid patch mapping the *old* selection indices onto the *new* diff content, and `git apply --cached` will apply it without any content-equality check tying it back to what was displayed.

Unlike `updateChangesWorkingDirectoryDiff` in `app-store.ts`, which explicitly re-validates `selectableLines` and prunes selections that no longer make sense whenever the diff is reloaded *for display* (`app-store.ts:3478-3497`), there is no equivalent revalidation step performed in the actual staging/commit path (`stageFiles`/`applyPatchToIndex`/`createCommit`). The existing "negative-slippage"-style guard that exists for display is simply not present where it matters — at the point the patch is generated and applied to the index.

### Impact Explanation
This falls in the "silent corruption of what the user commits or pushes" impact category. An attacker who can influence file contents inside the working directory during the (however brief) window between diff generation and stage/commit — e.g., via a repo-embedded file watcher/build script, a VCS hook, or another tool the victim also has running against the same repository — can cause Desktop to stage and commit content the user never selected or reviewed, while the UI shows a commit that appears to match the user's intended selection. This can be used to smuggle unreviewed/malicious changes into a commit that later gets pushed, bypassing the entire "partial staging visual review" trust model that Desktop's UI is built around.

### Likelihood Explanation
Likelihood is moderate-to-low because it requires a specific timing window and some other process able to modify the file in the working directory concurrently with user interaction (this is not "prior local malware" in the traditional sense, since the mutating process can itself be triggered by content already inside the cloned/legitimate-looking repository, e.g., an npm `postinstall`/watch script, git hook, or IDE auto-format-on-save triggered by opening the file) — it does not require the attacker to have any prior control over the user's machine, only to have gotten code that runs locally and mutates tracked files (a very ordinary thing in JS/build tooling repos). No explicit race-condition guard exists to prevent it in the reviewed code paths.

### Recommendation
Thread the exact `diff` object the user's selection was validated against through to `stageFiles`/`applyPatchToIndex` instead of re-fetching a new diff at apply time, or, if a fresh diff must be fetched (e.g. to avoid staleness from the reverse direction), compare a content hash/signature of the diff used for the selection against the freshly fetched diff and abort/re-prompt the user if they differ, mirroring the `selectableLines` revalidation logic already used in `app-store.ts` when re-rendering.

### Proof of Concept
1. In a repository open in Desktop, modify `foo.md`, causing several hunks; open the Changes view and partially select a subset of added/removed lines for hunk 2.
2. Before clicking "Commit", trigger (via a script, git hook, editor autosave, or another tool the same repo ships with) an edit to `foo.md` that shifts line offsets around hunk 2 (e.g., add lines above it) without refreshing the Desktop UI's diff view.
3. Click "Commit" in Desktop. `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (now reflecting the new content) and applies the stale `file.selection` indices against it via `formatPatch`.
4. Inspect the resulting commit with `git show`: the staged/committed hunk content differs from what was visually selected/reviewed in the Desktop UI before the on-disk edit occurred, demonstrating silent corruption of the commit contents.

```typescript
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
```
