### Title
Attacker-controlled worktree metadata in an opened repository can silently repoint an existing trusted repository record to a different git directory - ([File: app/src/ui/dispatcher/dispatcher.ts])

### Summary
The `bulls`/`bears` bug is about a value being **overwritten via a key an attacker can influence** because the key-derivation function doesn't bind the value to a unique, trusted identity. The closest Desktop analog is `dispatchCLIAction`'s "open-repository" / shared-worktree matching logic, which uses the *output of `git worktree list` run inside the folder the user is opening* — a value fully controlled by whatever `.git/worktrees/*/gitdir` admin files exist in that folder — to decide that an **already-registered, trusted `Repository` record** should be re-pointed (`switchWorktree`) to a different working directory and `gitDir`.

### Finding Description
In `dispatchCLIAction` (open-repository branch), Desktop lists worktrees from the folder being opened and uses the reported paths to decide whether the folder shares a common git directory with an existing repository already tracked in Desktop: [1](#0-0) 

`listWorktrees(path)` simply runs `git worktree list --porcelain -z` inside the opened folder: [2](#0-1) 

The "worktree" entries git reports are driven by the admin files under `<repo>/.git/worktrees/<id>/{gitdir,HEAD,...}`. These are ordinary files inside the repository's `.git` directory. A crafted/downloaded folder that is a real, valid git repository but ships a hand-crafted `.git/worktrees/<id>/gitdir` file (pointing at the absolute path of an already-known/likely Desktop repository location, e.g. a predictable `~/Documents/GitHub/<name>` clone path) will cause `git worktree list --porcelain` to report a worktree entry whose `path` equals the victim's existing, trusted repository path.

The dispatcher then matches that attacker-influenced path list against the paths of repositories already tracked by Desktop:
```
const sharedCommonDirRepository = repositories.find(
  r => matchExistingRepository(worktrees, r.path) !== undefined
)
if (worktree && sharedCommonDirRepository instanceof Repository) {
  await this.switchWorktree(sharedCommonDirRepository, worktree)
```
If a match is found, Desktop calls `switchWorktree` on the **victim's real, already-registered `Repository` object**, passing in the `worktree` derived from the newly opened (attacker-controlled) folder: [3](#0-2) 

`_switchWorktree` re-derives the type/`gitDir` of `worktree.path` (the attacker's folder) and calls `repositoriesStore.switchWorktree(repository, worktree.path, missing, gitDir, mainWorktreePath)`, which persists the new path/`gitDir` onto the pre-existing trusted `Repository` record. It then copies over cached state (`defaultBranch`, `openPullRequests`, `commitAuthor`, `tip`, etc.) from the old identity into the new one via `seedFromWorktree`: [4](#0-3) 

Nothing in this path verifies that the reported worktree admin metadata actually originates from (or was created by) the trusted repository's own `.git` directory — it is trusted purely because the reported path string matches. This is structurally the same class of bug as the Sherlock finding: an attacker-influenced identifier (`hashOrder`/order fields there, worktree-reported `path` here) is used as the sole key to decide whether to overwrite an existing, trusted record, without any binding to a value the attacker cannot forge (a signature/nonce there, a verified common `.git` object-store identity here).

### Impact Explanation
If exploited, an existing repository the user trusts (with its own remotes, push access, possibly containing credentials in config) gets its `path`/`gitDir` silently swapped to point at the attacker's directory while the UI still shows the original repository's name/branch/PR/author cache (carried over by `seedFromWorktree`). Subsequent commits, pulls, and pushes the user performs — believing they're operating on their known repository — are executed against the attacker-controlled git directory instead, satisfying "silent corruption of what the user commits or pushes" and potentially credential/token exposure if the attacker's remote is configured to receive a push.

### Likelihood Explanation
Requires the victim to open (drag-and-drop, "Add Local Repository", or `github desktop <path>` CLI) an attacker-supplied folder that is a legitimate git repository containing crafted `.git/worktrees/*/gitdir` files, and requires the crafted path to match an existing Desktop-tracked repository's path (predictable given common clone locations like `~/Documents/GitHub/<repo>` or `~/repos/<org>/<repo>`). This is a real, unprivileged "attacker controls a cloned/fetched repository" scenario per the task's valid-impact criteria, but the path-guessing requirement and the need to also match `matchExistingRepository`'s exact comparison logic (not fully visible in the excerpts reviewed) make exploitation somewhat dependent on environment specifics. I was not able to inspect `matchExistingRepository`'s exact matching rules (case sensitivity, symlink resolution, or a common-gitdir check) or the full body of `repositoriesStore.switchWorktree`, so the precise conditions under which the match succeeds are not fully confirmed from the index; a Devin session with full repo access should verify these before treating this as final.

### Recommendation
Before calling `switchWorktree` in `dispatchCLIAction`, verify that the worktree entry actually shares the same underlying `.git` common directory as the existing repository (e.g. by resolving and comparing the real, canonicalized `--git-common-dir` of both paths via `git`, not by trusting the `path` string reported by `git worktree list` on the newly-opened, untrusted folder). Reject the match if the two `.git` common directories do not resolve to the same real path.

### Proof of Concept
1. Attacker prepares a folder `evil-repo/` that is a valid git repository (`git init && git commit ...`) and hand-writes `evil-repo/.git/worktrees/fake/gitdir` containing the absolute path `<victim-home>/Documents/GitHub/some-repo/.git` (a predictable/likely location for an existing Desktop-tracked repository), plus a plausible `HEAD` file in the same admin directory.
2. Victim downloads/receives `evil-repo/` (e.g. as a zip attachment, not necessarily via `git clone`, which is why arbitrary `.git` contents can be smuggled in) and opens it in GitHub Desktop via "Add Local Repository" or `github-desktop evil-repo`.
3. `dispatchCLIAction`/`AddRepository` flow calls `listWorktrees(evil-repo path)`; `git worktree list --porcelain` reports a worktree entry whose path equals the victim's real `some-repo` path.
4. `matchExistingRepository(worktrees, r.path)` finds the victim's already-tracked `some-repo` `Repository` object as `sharedCommonDirRepository`, and `this.switchWorktree(sharedCommonDirRepository, worktree)` is invoked with `worktree.path` == `evil-repo`.
5. `_switchWorktree` persists `evil-repo`'s path/gitDir onto the trusted `some-repo` `Repository` record and copies over cached branch/PR/author state via `seedFromWorktree`, so the UI continues to show `some-repo`'s history/remotes while all git operations now target `evil-repo`'s git directory.

export async function listWorktrees(
  repositoryOrPath: Repository | string
): Promise<ReadonlyArray<WorktreeEntry>> {
  const result = await git(
    ['worktree', 'list', '--porcelain', '-z'],
    typeof repositoryOrPath === 'string'
      ? repositoryOrPath
      : repositoryOrPath.path,
    'listWorktrees'
  )

  return parseWorktreePorcelainOutput(result.stdout)
}

  public async _switchWorktree(
    repository: Repository,
    worktree: WorktreeEntry
  ): Promise<Repository> {
    const type = await getRepositoryType(worktree.path).catch(e => {
      log.error('Could not determine repository type', e)
      return { kind: 'missing' } as RepositoryType
    })

    if (type.kind !== 'regular' && type.kind !== 'unsafe') {
      throw new Error(
        `The worktree path '${worktree.path}' does not appear to be a valid Git repository.`
      )
    }

    // If the repository path isn't trusted we'll mark the repository as
    // missing. The missing repository view knows how to add a path to the
    // allow list.
    const missing = type.kind === 'unsafe'
    const gitDir = type.kind === 'regular' ? type.gitDir : undefined

    // Record the main worktree while the worktree set is still readable.
    // Removing a worktree can take its git metadata with it, leaving nothing to
    // resolve it from afterwards. Only attempted for a regular repository —
    // git won't run at all in one it considers unsafe — and `switchWorktree`
    // keeps the previously recorded path when this is undefined.
    const mainWorktreePath =
      type.kind === 'regular'
        ? await this.findMainWorktreePath(worktree.path)
        : undefined

    const result = await this.repositoriesStore.switchWorktree(
      repository,
      worktree.path,
      missing,
      gitDir,
      mainWorktreePath
    )

    this.repositoryStateCache.seedFromWorktree(
      result.repository,
      repository,
      worktree
    )

    await this._selectRepository(result.repository)

    this.statsStore.increment('worktreeSwitchCount')

    return result.repository
  }

  public seedFromWorktree(
    target: Repository,
    source: Repository,
    worktree: WorktreeEntry
  ) {
    const sourceState = this.repositoryState.get(source.hash)
    if (sourceState === undefined) {
      return
    }

    const targetState = this.get(target)

    this.repositoryState.set(target.hash, {
      ...targetState,
      branchesState: {
        ...targetState.branchesState,
        defaultBranch: sourceState.branchesState.defaultBranch,
        upstreamDefaultBranch: sourceState.branchesState.upstreamDefaultBranch,
        allBranches: sourceState.branchesState.allBranches,
        recentBranches: sourceState.branchesState.recentBranches,
        openPullRequests: sourceState.branchesState.openPullRequests,
        forcePushBranches: sourceState.branchesState.forcePushBranches,
        tip: tipFromWorkTreeEntry(worktree, sourceState.branchesState),
      },
      worktrees: sourceState.worktrees,
      commitLookup: sourceState.commitLookup,
      remote: sourceState.remote,
      lastFetched: sourceState.lastFetched,
      commitAuthor: sourceState.commitAuthor,
      localTags: sourceState.localTags,
    })
  }
