### Title
Reward donations can be permanently lost due to rounding-down in `rewardPerTokenStored` calculation - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool._provisionReward` (also duplicated in `BaseRewardPoolV2.sol`, `vlMGPBaseRewarder.sol`, `mWOMSVBaseRewarder.sol`, and `DelegateVoteRewardPool.sol`) computes `rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()`. When `totalStaked()` is large relative to `_amountReward * 10**stakingDecimals()`, this integer division rounds down to `0`, silently discarding the reward increment while the tokens themselves are already pulled into the contract via `safeTransferFrom`.

### Finding Description
`_provisionReward` is invoked from `queueNewRewards` (restricted to `onlyManager`) and from `donateRewards`, which is a fully public, unrestricted function callable by any wallet: [1](#0-0) 

Inside `_provisionReward`, the reward-per-share accumulator update divides by `totalStaked()`, which is simply the staking token balance held by the operator (`MasterMagpie`): [2](#0-1) [3](#0-2) 

If `totalStaked()` grows large enough compared to `_amountReward * 10**stakingDecimals()`, the division truncates to zero: `rewardInfo.rewardPerTokenStored` does not increase, yet `historicalRewards` is bumped and the tokens are already transferred into the contract (`IERC20(_rewardToken).safeTransferFrom(msg.sender, address(this), _amountReward)`). Because the `queuedRewards` re-injection path (`if (rewardInfo.queuedRewards > 0)`) is only triggered when `totalStaked() == 0`, a nonzero-but-insufficient reward amount is neither credited to `rewardPerTokenStored` nor re-queued — it becomes permanently stuck in the contract, unclaimable by any staker.

This exact rounding pattern is repeated identically across: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The unprivileged reachability path is `donateRewards`, which any wallet can call directly with an arbitrary `_amountReward` for any already-registered reward token, with no minimum-amount guard: [8](#0-7) 

### Impact Explanation
Any wallet that calls `donateRewards` with an amount small enough relative to `totalStaked() / 10**stakingDecimals()` causes its transferred tokens to be permanently locked in the reward pool with no `rewardPerTokenStored` increase — the funds cannot be claimed by any staker and cannot be recovered by the donor. As `totalStaked()` (total value staked into a pool) grows over the protocol's life, the threshold amount that triggers this rounding-to-zero grows too, meaning even legitimate operator-driven `queueNewRewards` reward injections (from `onlyManager`) become increasingly susceptible to partial or full loss for smaller reward tranches — this is a permanent freeze/loss of unclaimed yield intended for legitimate stakers, not just the donor's own funds.

### Likelihood Explanation
Likelihood scales with pool TVL and reward token decimals: for a staking token with 18 decimals, once `totalStaked()` exceeds roughly `_amountReward * 1e18`, the reward is entirely lost. For high-TVL pools or reward tokens donated/queued in small increments (e.g., frequent small bribe/incentive top-ups), this condition is realistically reachable without any privileged action, since `donateRewards` has no minimum-amount check and is open to any caller.

### Recommendation
Add a check in `_provisionReward` (and its duplicates in `BaseRewardPoolV2.sol`, `vlMGPBaseRewarder.sol`, `mWOMSVBaseRewarder.sol`, `DelegateVoteRewardPool.sol`) to either revert or re-queue the reward when the computed increment would round down to zero, e.g.:
```solidity
uint256 increment = (_amountReward * 10**stakingDecimals()) / totalStaked();
if (increment == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    rewardInfo.rewardPerTokenStored += increment;
}
```

### Proof of Concept
1. A `BaseRewardPool` is deployed for a staking token with 18 decimals, and `totalStaked()` (i.e., `IERC20(stakingToken).balanceOf(operator)`) is, e.g., `2e30` (achievable in a high-TVL pool over time through normal deposits).
2. Any wallet calls `donateRewards(1e11, rewardToken)` (a plausible small reward donation).
3. `_provisionReward` computes `(1e11 * 1e18) / 2e30 = 0` due to integer truncation.
4. `rewardInfo.rewardPerTokenStored` remains unchanged, but `1e11` reward tokens have already been transferred into the contract via `safeTransferFrom` and `historicalRewards` is incremented.
5. No staker's `earned()` value increases (since `rewardPerToken()` is unchanged), and the `1e11` tokens remain permanently stuck in the contract, unclaimable by anyone — a permanent freeze of that yield.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
