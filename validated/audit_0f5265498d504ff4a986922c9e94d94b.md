### Title
Index-Based Diff Selection Silently Commits/Discards Wrong Lines When Working Directory File Changes Between Selection and Commit - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop's partial-commit and discard-selection features store a user's line selection as a set of **positional line indices** (`DiffSelection`), not as content-addressed selections. When the working tree file is modified by an external process between the moment the user makes their selection (against a previously rendered diff) and the moment the patch is generated/applied (against a freshly re-computed diff), the same indices can now point to different actual line content. This causes `formatPatch`/`applyPatchToIndex` and `formatPatchToDiscardChanges` to stage or discard content the user never reviewed or approved, silently corrupting what gets committed or pushed — the same "stale value applied against updated state" invariant break described in the source report.

### Finding Description
`DiffSelection` tracks selected/unselected lines purely by their absolute index in the diff's line array, and `formatPatch` uses `file.selection.isSelected(absoluteIndex)` to decide, line-by-line, whether to include a hunk line in the generated patch: [1](#0-0) 

`applyPatchToIndex` re-fetches the diff from disk immediately before formatting and applying the patch: [2](#0-1) 

The `file` object (and its `selection`) passed into `applyPatchToIndex`/`stageFiles`/`createCommit` is the state captured when the user made their line selections in the UI — it is not guaranteed to correspond to the diff freshly read from disk at apply time: [3](#0-2) [4](#0-3) 

The app itself acknowledges this gap. When the working-directory diff is reloaded (e.g. because the file changed on disk), the code only prunes indices that are "no longer includeable" (turned into context lines or out of range) — it explicitly does **not** verify that the content at a still-includeable index is the same content the user originally selected: [5](#0-4) 

The same index-based mechanism is used for discarding changes via `discardChangesFromSelection`, which also takes a `diff` argument that may be stale relative to the actual working tree file: [6](#0-5) 

**Broken invariant:** a `DiffSelection` (a bag of line indices) is only valid for the exact diff/hunk layout it was computed against. If any process external to the user's deliberate action (a build tool, formatter, linter, git hook, or any file-watch-triggered rewrite of a tracked file coming from the cloned/fetched repository's own tooling) mutates the file between selection and commit/discard, the index-to-content mapping shifts, and Desktop applies the user's old selection to new content without re-validating equivalence — exactly mirroring the contract bug where `userWithdraw.withdrawAmount`/`shares` recorded at `initiateWithdrawal()` are blindly reused against a `withdraw()`-time price without being re-derived from the current state.

### Impact Explanation
This can result in **silent corruption of what the user commits or discards**:
- Lines the user explicitly deselected (e.g., a suspicious/malicious line inserted into a tracked file by a repo-provided build script, husky/lint-staged hook, or auto-formatter) could still be included in the resulting commit if the shift in hunk layout causes an unrelated but now-includeable index to be treated as "selected."
- Conversely, lines the user intended to keep could be silently dropped via `discardChangesFromSelection`, causing unintended data loss in the working directory.
- Because the commit is created from a patch, not from a full snapshot review, the user has no clear signal that the staged/committed diff differs from what they last visually verified, and the corrupted commit can then be pushed upstream.

This falls squarely under "silent corruption of what the user commits or pushes," and the attacker's foothold is a cloned/fetched repository that ships build/format tooling capable of mutating tracked files during the user's review-to-commit window.

### Likelihood Explanation
Exploitability requires the repository (attacker-controlled, cloned/fetched by the victim) to include tooling that rewrites tracked files asynchronously relative to user interaction — for example an npm `postinstall`/watch script, a `husky` pre-commit-style hook, or a background formatter triggered by Desktop's own file-system watcher refreshing the diff. This is a realistic and unprivileged scenario since Desktop users routinely clone repositories with build tooling and leave editors/build watchers running while reviewing diffs. The existing mitigation in `updateChangesWorkingDirectoryDiff` (line-existence-only revalidation) does not close this gap, since it does not check content equivalence at the surviving indices — only structural includeability.

### Recommendation
Decouple the line selection from purely positional indices — the same class of fix recommended in the source report (store the value/entity that was validated, and use it directly rather than re-deriving it against fresh state). Concretely:
- When the working directory diff is refreshed, re-validate selected indices by comparing the actual line **content** (not just line type/includeability) against what was previously selected, and drop/re-map selections whose underlying content changed.
- Alternatively, invalidate the entire partial selection (falling back to "no selection" or prompting the user to re-review) whenever the file's on-disk diff has changed since the selection was last computed, rather than silently reusing indices.
- Ensure `applyPatchToIndex` and `discardChangesFromSelection` fail loudly (or re-diff and re-prompt) if the diff/patch application against the freshly-read file does not match the diff the selection was originally computed from, instead of silently applying a best-effort patch.

### Proof of Concept
1. Clone a malicious repository containing a tracked file `foo.txt` and a package.json/husky hook (or any process the repo can trigger) that appends/edits a line in `foo.txt` a few seconds after file-save events.
2. In GitHub Desktop, modify `foo.txt` locally, open the Changes view, and partially select lines to include in the next commit (e.g., deselect a newly appearing malicious line while selecting your own legitimate edits) — this computes a `DiffSelection` bound to the current hunk layout, per `formatPatch`'s `absoluteIndex` scheme: [1](#0-0) .
3. Before clicking "Commit", the attacker-controlled hook/tool rewrites `foo.txt`, shifting hunk boundaries (e.g., inserting/removing an unrelated line above the reviewed hunk).
4. GitHub Desktop's background diff refresh runs `updateChangesWorkingDirectoryDiff`, which only prunes indices that became "not includeable" — indices that remain includeable (even if pointing at different content now) stay selected: [5](#0-4) .
5. The user clicks "Commit"; `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff from disk and applies the stale index-based `file.selection` against it: [2](#0-1) , [3](#0-2) .
6. The resulting commit includes/excludes lines the user did not actually approve in their final review, and this commit can be pushed, silently propagating attacker-influenced or unintended content.

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
