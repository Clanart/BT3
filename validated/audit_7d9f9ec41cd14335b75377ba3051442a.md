## Finding

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain residual tokens/ETH left in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated entrypoint that executes arbitrary `to`/`value`/`data` calls with the dispatcher's own balance and allowances. The contract is a single, shared, publicly-known instance used by multiple apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`/`IntentsBase`/`ExtrinsicIntents`) that legitimately route tokens and ETH through it during cross-chain calldata execution. Because sweeping of residual balances after execution is scoped only to the tokens explicitly declared in the order/message (e.g. `order.output.assets`), any token or ETH that ends up in the dispatcher outside that declared set — from postdispatch/predispatch side effects, direct transfers, or partial failures — is never swept back and sits there indefinitely. Since `dispatch()` has no access control, any unprivileged attacker can call it directly with a crafted `Call[]` (e.g. `IERC20.transfer(attacker, balance)` or `IERC20.approve(attacker, type(uint256).max)`) to steal those funds. This is the same root cause as the reported Connext `Executor.execute` bug: an arbitrary-call primitive with no destination/calldata restrictions on a contract that holds unclaimed value.

### Finding Description
`CallDispatcher.sol` exposes: [1](#0-0) 

`dispatch(bytes memory encoded)` is `external` with no modifier, no `onlyOwner`/`onlyGateway` restriction, and no caller check whatsoever — literally any address can invoke it with an arbitrary ABI-encoded `Call[]`. The `receive()` function also accepts arbitrary ETH.

The `ICallDispatcher` interface confirms this is the intended shape (`dispatch` is meant to "dispatch untrusted call(s)"), and it is deliberately shared across the protocol's applications rather than deployed per-caller: [2](#0-1) 

Multiple apps route tokens/ETH through this same dispatcher and then only sweep tokens they explicitly know about:

- `HyperFungibleToken.onAccept` mints tokens then forwards `message.data` to the dispatcher for execution, with no sweep of anything the dispatcher doesn't spend: [3](#0-2) 

- `IntentsBase._execute` dispatches the order's postdispatch calls, then sweeps back only balances of the tokens listed in `order.output.assets` — any other token balance left on the dispatcher (e.g. an intermediate swap token, a reward/referral token picked up by a DEX call, or dust from an unrelated concurrent flow through the same shared dispatcher) is never accounted for or swept: [4](#0-3) 

- `IntentGatewayV2.placeOrder`'s predispatch flow similarly moves assets to the dispatcher, invokes `dispatch()`, and only sweeps the tokens declared in `order.inputs`: [5](#0-4) 

Because the same `CallDispatcher` address is reused by all these apps (per the docs, it is a fixed, listed deployment address) and `dispatch()` has zero access control, once any token/ETH balance is left on the dispatcher between transactions — whether from an untracked side-effect of a postdispatch swap, a direct/mistaken transfer to the well-known dispatcher address, or a race where a legitimate `dispatch()` call from one app leaves dust that a different app's sweep logic doesn't know to look for — an attacker can immediately call `dispatch()` themselves with a `Call` that transfers or grants an allowance over that balance to themselves. Unlike the intended callers (the apps), the attacker's call is not required to match any known token list.

### Impact Explanation
This directly causes theft/loss of funds from a live bridge component: any ERC20 or native balance that ends up on the shared `CallDispatcher` — including protocol-relevant dust, unswept intermediate tokens from DeFi routing calls, or accidental transfers — is permissionlessly stealable by any address, with no relayer/prover/admin compromise required. This matches the required impact category "stealing or loss of funds" / "unauthorized transaction or execution."

### Likelihood Explanation
The attack requires only observing a non-zero balance on the publicly known `CallDispatcher` address (documented and listed as a fixed deployment) and submitting one transaction calling `dispatch()` with a malicious `Call[]`. No privileged role, proof forgery, or timing race with a relayer is needed — the documentation itself acknowledges the dispatcher "holds tokens temporarily during execution," and the sweep logic is scoped only to declared token sets, so any token/ETH outside that set accumulates as a standing, exploitable balance.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g. only the registered app/gateway contracts that are expected to use it), or deploy per-call, ephemeral/minimal-proxy dispatcher instances instead of a single shared, permissionless dispatcher. Additionally, ensure sweep logic accounts for *all* residual balances (not just declared output/input tokens) after every dispatch, or adopt Connext's stated mitigation explicitly and document/enforce that any balance left on the dispatcher is unsafe by design (in which case access control on `dispatch()` becomes mandatory rather than optional, since here — unlike Connext's Executor — nothing currently limits who can invoke it at all).

### Proof of Concept
1. Locate the shared `CallDispatcher` deployment address (public, listed in contract-addresses docs, used by `HyperFungibleToken`/`IntentGatewayV2`/etc).
2. Observe (via block explorer/token balance query) that the dispatcher holds a non-zero ERC20 balance — e.g. left over from a postdispatch swap in `IntentsBase._execute` where the swap produced a reward token not listed in `order.output.assets`, or from a solver/user mistakenly sending tokens directly to the known dispatcher address.
3. Call `CallDispatcher.dispatch(encoded)` directly (no permission required) with:
```solidity

calls[0] = Call({
    to: strandedToken,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(strandedToken).balanceOf(address(dispatcher)))

dispatcher.dispatch(abi.encode(calls));
```

4. The `to.call{value: call.value}(call.data)` in `CallDispatcher.dispatch` (evm/src/utils/CallDispatcher.sol:59) executes unconditionally since `to` (the token contract) has code, transferring the stranded balance to the attacker with no check that the caller was an authorized app.

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
