### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accept semantically inconsistent key material (secret share not bound to verification share, interpolation not checked against group key), producing `FrostError::InternalError` panics in callers during signing - (crypto/dkg/src/lib.rs)

### Summary
The DKG crate's `ThresholdKeys` deserialization and constructor perform only structural validation (participant range, share count, `t <= n`, `t == n` for `Constant` interpolation). They never check that the deserialized `secret_share` actually corresponds to `verification_shares[i]`, that any verification share is non-identity, or that the supplied `Interpolation::Constant` coefficients actually interpolate the verification shares to a consistent group key. The FROST completion path explicitly acknowledges this gap: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" before returning `FrostError::InternalError`, which downstream callers treat as `unreachable!`. An attacker who can feed crafted bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-bytes sink) can therefore deterministically crash a signer/coordinator mid-protocol — a missing-validation bug directly analogous to the referenced report.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, an interpolation variant (including a fully attacker-controlled `Vec` of `Constant` coefficients), a raw `secret_share` scalar, and `n` verification-share points, then calls `ThresholdKeys::new` (crypto/dkg/src/lib.rs:574-632). `ThresholdKeys::new` only checks `verification_shares.len() == n`, each key `<= n`, and `t == n` for `Constant`; it then derives `group_key` by interpolating shares `1..=t` (crypto/dkg/src/lib.rs:349-391). Notably absent:

- No check that `C::generator() * secret_share == verification_shares[i]` — the secret share is never bound to its claimed verification share.
- No identity rejection on verification shares (`<C as Ciphersuite>::read_G` is used, not the identity-rejecting `Curve::read_G` from crypto/frost/src/curve/mod.rs:125).
- No check that `Interpolation::Constant` coefficients are consistent (that they reproduce the group key over `1..=t`), even though `interpolation_factor` for `Constant` ignores the included set entirely and indexes `c[i-1]` (crypto/dkg/src/lib.rs:226-249).

During `AlgorithmSignatureMachine::complete`, every share is verified against the (attacker-chosen) `verification_shares` via `algorithm.verify_share`, so individually "valid" shares can still fail to combine into a valid group signature; the code then hits `Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))` (crypto/frost/src/sign.rs:487-494). Callers explicitly assume this is impossible: `complete_internal` in coordinator/src/tributary/signing_protocol.rs maps `FrostError::InternalError` to `unreachable!` (lines 193-200), and processor/src/signer.rs likewise marks it `unreachable!` (lines 533-539). The result is a deterministic panic.

### Impact Explanation
A crafted `ThresholdKeys` blob (e.g., `Constant` interpolation with coefficients that don't reproduce the group key, or a `secret_share` mismatched with `verification_shares[i]`) passes all deserialization checks, is used to produce a FROST signature share that verifies against the corrupted view, and then triggers the "everyone had a valid share yet the signature was still invalid" `InternalError` in `complete`. Because callers handle `InternalError` with `unreachable!`, this becomes a panic that kills the signer/coordinator thread during an active signing session — a remotely triggerable liveness failure gated only on the attacker's ability to supply the serialized key bytes.

### Likelihood Explanation
Exploitation requires feeding crafted bytes to `ThresholdKeys::read`, which the scope rules explicitly classify as an untrusted-bytes sink. Once read, no further attacker interaction is needed: the inconsistency is only detected at the `InternalError` fallback, after which the panic is deterministic. It does not require threshold collusion or a malicious peer in the DKG — only malformed key material reaching the deserializer.

### Recommendation
In `ThresholdKeys::new` (and therefore `ThresholdKeys::read`), add semantic validation:

- Verify `C::generator() * secret_share == verification_shares[&params.i()]` and return a `DkgError` otherwise.
- Reject identity verification shares (use the identity-rejecting reader or check `is_identity`).
- For `Interpolation::Constant`, verify the coefficients are consistent — e.g., that interpolating the verification shares over `1..=t` with the supplied coefficients yields the same `group_key` computed by the standard derivation, or reject `Constant` blobs that don't round-trip.
- Defensively, replace `denom.invert().unwrap()` in `interpolation_factor` and the `unreachable!`/`unwrap()` on `view()`/`InternalError` in callers with error returns, so inconsistent inputs degrade to `FrostError`/`DkgError` rather than panics.

### Proof of Concept
1. Construct a valid `key_gen` output for `(t = 2, n = 3)` and serialize participant 1's `ThresholdKeys` via `serialize()` (crypto/dkg/src/lib.rs:567).
2. Flip the interpolation tag byte to `0` (Constant) and rewrite the coefficient region, or swap two verification-share encodings / perturb the `secret_share` field, keeping `t`, `n`, `i` valid so `ThresholdParams::new` and the length/range checks in `ThresholdKeys::new` still pass.
3. Feed the blob to `ThresholdKeys::read` — it returns `Ok`.
4. Build an `AlgorithmMachine` with the corrupted keys, run `preprocess`/`sign` with an honest peer set, then `complete` with honestly-computed shares. `algorithm.verify` fails for the summed share, every individual share verifies under the corrupted `verification_shares`, and `complete` returns `FrostError::InternalError`, which `complete_internal` (coordinator/src/tributary/signing_protocol.rs:194) and signer.rs handle via `unreachable!` — panicking.
