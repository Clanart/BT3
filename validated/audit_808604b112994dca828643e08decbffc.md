### Title
Unhandled exception in `FullNode._handle_transactions` silently kills the sole transaction-processing loop, halting all mempool admission - (File: chia/full_node/full_node.py)

### Summary
`FullNode._handle_transactions()` is the single consumer loop draining `TransactionQueue` and dispatching each entry to `_handle_one_transaction()`. It is started once via `create_referenced_task` and never restarted or monitored. [2](#0-1) 

### Finding Description
`_handle_one_transaction` itself is carefully wrapped in a broad try/except (`CancelledError`, `ValidationError`, `Exception`) so per-transaction validation failures cannot kill it. [3](#0-2)  However, the outer `_handle_transactions()` loop that calls `self.add_transaction_semaphore.acquire()`, iterates `self._tx_task_list`, and calls `await self.transaction_queue.pop()` has no exception handling at all: any unhandled exception raised inside `pop()` — e.g., from `TransactionQueue.pop()`'s internal invariants such as `assert num_peers != 0` or `assert len(top_txs_advertised_costs) != 0` in `chia/full_node/tx_processing_queue.py` — propagates out of the loop and terminates the task permanently. [4](#0-3) [5](#0-4) 

The task is created with `create_referenced_task`, whose only completion callback (`_task_done`) removes internal bookkeeping and never logs, inspects, or restarts the task on failure. [6](#0-5)  No other code checks `self._transaction_queue_task.done()` or its exception to detect and recover from this silent death; it is only ever `cancel()`-ed during shutdown. [7](#0-6) 

This is structurally analogous to the EVerest `TbdController` bug: a critical, single-instance processing loop that is not defended against exceptions escaping it, causing the loop (and the service it drives — here, all future transaction/SDP-equivalent processing) to silently terminate with no supervisory restart.

### Impact Explanation
If `_handle_transactions()` dies, `TransactionQueue.put()` calls from `respond_transaction` and `send_transaction` keep succeeding (queue is unbounded from the producer's perspective aside from per-peer limits), but nothing ever pops from the queue again. Every subsequent submitted spend bundle — from wallets, offer counterparties, or peers — sits in `TransactionQueueEntry.done` forever un-set, so callers relying on `await queue_entry.done.wait()` (e.g., `send_transaction`) will only get the 45-second timeout PENDING response, and no transaction will ever be validated or added to the mempool for the remainder of the node's uptime. [8](#0-7)  This is a spend-triggered denial of service against the entire node's transaction-processing pipeline, not just a single request.

### Likelihood Explanation
Reaching `pop()`'s internal `assert` failures requires a specific queue-state race (e.g., a peer's queue becoming empty/removed between the round-robin selection and the deficit check), which is plausible under concurrent access from a queue that is mutated by multiple call sites (`put()` from message handlers, `pop()` from the loop) without a lock other than the semaphore count. I was not able to fully verify from the code inspected here whether such a race is actually reachable in practice (this would require deeper concurrency analysis of `TransactionQueue`), so likelihood is assessed as moderate rather than certain.

### Recommendation
Wrap the body of `_handle_transactions()`'s while loop in a try/except that logs unexpected exceptions and continues the loop (mirroring the defensive pattern already used in `_handle_one_transaction`), or supervise the task with a done-callback that restarts it on unexpected failure, consistent with the pattern in `chia/util/async_pool.py`'s `AsyncPool._handle_done_worker`, which does log and can react to worker task exceptions. [9](#0-8) 

### Proof of Concept
Not independently reproduced; the reasoning above is based on static code review of `_handle_transactions`, `TransactionQueue.pop`, and `create_referenced_task`. Confirming exploitability would require constructing a queue state (e.g., interleaved `put`/`pop` calls from concurrent peers) that triggers one of the `assert` statements in `TransactionQueue.pop()`, converting it into an uncaught `AssertionError` that kills `_handle_transactions`.

    async def _handle_transactions(self) -> None:
        while not self._shut_down:
            # We use a semaphore to make sure we don't send more than 200 concurrent calls of respond_transaction.
            # However, doing them one at a time would be slow, because they get sent to other processes.
            await self.add_transaction_semaphore.acquire()

            # Clean up task reference list (used to prevent gc from killing running tasks)
            for oldtask in self._tx_task_list[:]:
                if oldtask.done():
                    self._tx_task_list.remove(oldtask)

            item: TransactionQueueEntry = await self.transaction_queue.pop()
            self._tx_task_list.append(create_referenced_task(self._handle_one_transaction(item)))
