## Title
Unchecked ERC-20 return value in `withdraw()` lets escrow accounting finalize even when the token transfer silently fails - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` (Tron deployment) releases escrowed order funds using a raw low-level `.call()` to the ERC-20 `transfer` selector and only checks the **call-level** success flag, never decoding the token's returned boolean. `_orders[commitment][token]` is decremented and `_filled[commitment]` is set to "complete" regardless of whether the token actually moved. This is the exact bug class from the external report ("freeTokens decreased even though transfer fails") transplanted into escrow settlement: any non-reverting-on-failure ERC-20 (returns `false` instead of reverting) causes the contract to treat an order as fully and finally settled while the beneficiary receives nothing.

### Finding Description
In `withdraw()`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    _orders[body.commitment][token] -= amount;
    ...
}
```

`success` here reflects only whether the low-level `.call()` did not revert — it does **not** decode the ABI-encoded `bool` that a compliant `transfer()` returns. Non-standard ERC-20 tokens that return `false` on failure (rather than reverting) will make `success == true` even though no tokens moved. The function then:
1. Decrements `_orders[body.commitment][token]`, marking the escrow as spent.
2. Has already unconditionally set `_filled[body.commitment] = beneficiary` at function entry, finalizing the order before any transfer is even attempted.

Since `_filled` is set once and the order becomes non-retryable/non-refundable, the escrowed value is permanently stuck in the contract while the accounting and emitted events (`EscrowReleased`/`EscrowRefunded`) claim delivery succeeded.

The same unchecked pattern recurs in the same file for `SweepDust` and transaction-fee redemption: [2](#0-1) [3](#0-2) 

By contrast, the mainline EVM implementation of the same logic correctly uses `safeTransfer`, which reverts on a `false` return: [4](#0-3) 

and the core `EvmHost` fee-refund paths follow the safe "delete-then-retry" pattern with `safeTransfer` for exactly this reason: [5](#0-4) 

The Tron `IntentGatewayV2.sol` variant lacks both protections: no `safeTransfer`/return-data check, and `_filled` is set before the transfer attempt rather than being restorable on failure.

### Impact Explanation
This directly causes loss of funds for the rightful beneficiary (solver on `RedeemEscrow`, or user on `RefundEscrow`): escrowed input tokens are permanently locked in the gateway contract, the commitment is marked filled so it can never be retried or re-settled, and the protocol emits a false "success" event. This matches the required impact category "stealing or loss of funds" via wrong/false state acceptance in escrow settlement — no malicious relayer, prover, or governance actor is needed; only an order that references a non-standard ERC-20 that returns `false` instead of reverting.

### Likelihood Explanation
The order's input token is attacker/user-controlled at `placeOrder` time — any ERC-20 that returns `false` on failure (a well-documented, non-rare legacy pattern) reaching a full-balance/allowance edge case (e.g., temporarily insufficient contract balance, blacklist, paused state) triggers the bug on the very next `withdraw()` call, with no privileged actor required.

### Recommendation
Replace the raw `.call` + `IERC20.transfer.selector` pattern in `withdraw()`, the `SweepDust` branch, and the fee-redemption branch with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the return value (or reverts). Additionally, do not set `_filled[body.commitment]` until all transfers in the loop have succeeded, mirroring the "delete-then-retry" idiom already used in `EvmHost.sol`.

### Proof of Concept
1. User places an order on the Tron gateway (`placeOrder`) using a non-standard ERC-20 as an input token — one that returns `false` on a failed `transfer` (common for tokens ported from older ERC-20 templates) instead of reverting.
2. Destination fill triggers a `RedeemEscrow`/`RefundEscrow` `onAccept` → `withdraw(body, isRefund)`.
3. Have the token return `false` for the transfer call (e.g., insufficient balance edge, paused/blacklisted state at settlement time) — `token.call(...)` still returns `success = true` because the call did not revert.
4. `withdraw()` proceeds: `_orders[commitment][token] -= amount` executes, `_filled[commitment]` was already set, `EscrowReleased`/`EscrowRefunded` is emitted.
5. Beneficiary's balance is unchanged; the escrowed tokens remain stuck in the gateway with no code path left to retry or refund, since the commitment is already finalized.

        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();
