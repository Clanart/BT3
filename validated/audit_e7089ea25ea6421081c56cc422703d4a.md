## Analysis

The external report's core invariant is: **a withdraw/cancel/refund path unconditionally pushes funds to a caller-supplied recipient, and if that transfer can never succeed, the escrowed value is locked with no recovery path.**

In Hyperbridge's Solidity intents system, the analogous flow is the `RedeemEscrow` / `RefundEscrow` settlement messages dispatched by `ExtrinsicIntents.sol` back to the source chain, which are received by `IntentsBase._withdraw` and processed via `EvmHost.dispatchIncoming`.

### The corrupted-state path

1. On fill, `ExtrinsicIntents.fillOrder` dispatches a `RedeemEscrow` `DispatchPost` back to the source chain with `beneficiary = msg.sender` (the filling solver) and, critically, **`timeout: 0`**: [1](#0-0) 
Same pattern for destination-initiated cancellation (`RefundEscrow`, `beneficiary = order.user`): [2](#0-1) 

2. On the source chain, `EvmHost.dispatchIncoming` calls the module's `onAccept`. If it reverts, the receipt is deleted "so it can be retried" — but a permanently reverting call will simply be retried forever and never succeed: [3](#0-2) 

3. `IntentsBase._withdraw` performs an unconditional push transfer to `beneficiary` — a raw `.call{value:...}` for native tokens or `safeTransfer` for ERC-20 — with no fallback and no recipient-capability check (no analog of `is_account_registered`): [4](#0-3) 

Because the outbound `DispatchPost` for both `RedeemEscrow` and `RefundEscrow` is sent with `timeout: 0` (no timeout), the message can **never** time out and fall back to a timeout-refund path. If `beneficiary` can never accept the transfer (an ERC-20 with an on-chain blocklist such as USDC/USDT blacklisting the address, or a filler/solver address that is a contract with no payable fallback for the native-token case), `_withdraw` reverts every single time it is retried, and the escrowed input tokens (deposited by the order's original user) remain locked in the `IntentGatewayV2` contract permanently — there is no governance sweep, no alternate beneficiary path, and no timeout escape hatch.

This is the direct structural analog of the reported bug: a forced transfer to an unvalidated recipient with no registration/capability check, compounded here by the removed timeout safety net, turns a routine settlement/cancellation into a permanent fund lock. Contrast this with `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which the team explicitly hardened against exactly this scenario by falling back to WETH delivery if the native push fails "so the refund path doesn't permanently lock funds": [5](#0-4) 
No equivalent fallback exists in `IntentsBase._withdraw` / the Tron `IntentGatewayV2.withdraw`, and the `timeout: 0` choice for these two `RequestKind`s removes even the generic ISMP timeout recovery.

### Title
Permanent Escrow Lock in Intent Gateway Settlement/Cancellation Due to Zero-Timeout, Unvalidated-Recipient Withdraw Path - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._fillOrder`/`_cancelFromDest` dispatch `RedeemEscrow`/`RefundEscrow` POST messages with `timeout: 0`. `IntentsBase._withdraw`, invoked from `onAccept` on the source chain, performs an unconditional native `call` or `safeTransfer` to the embedded `beneficiary` with no capability check and no fallback delivery path. If the beneficiary (solver address for redemption, or user address for refund) can never accept the asset — e.g. an ERC-20 blocklist, or a non-payable contract for native transfers — `onAccept` reverts every retry indefinitely, and because the message can never time out, the escrowed input tokens are permanently trapped in the gateway contract.

### Finding Description
See analysis above; the flow lacks any analog of `coin::is_account_registered` or a fallback/wrap mechanism that the team has already implemented elsewhere in the same codebase (`WrappedHyperFungibleToken`).

### Impact Explanation
User-deposited escrow (input tokens on the source chain) can become permanently unrecoverable — no sweep, no re-target of beneficiary, no timeout — constituting a loss-of-funds condition once a beneficiary's ability to receive the asset is revoked or was never viable.

### Likelihood Explanation
Realistic for common stablecoins (USDC/USDT) that support post-hoc address blacklisting, or for any solver/filler using a smart-contract wallet without a receive/fallback function for native-asset orders. No malicious relayer, prover, or governance actor is required — only that the already-embedded beneficiary becomes unable to receive the asset before settlement completes.

### Recommendation
Give `RedeemEscrow`/`RefundEscrow` dispatches a bounded timeout so failed deliveries can fall back to a recovery path, and/or add a pull-based claim/rescue mechanism (or a WETH-style fallback wrap, mirroring `WrappedHyperFungibleToken`) in `IntentsBase._withdraw` so a reverting beneficiary cannot indefinitely lock escrowed funds.

### Proof of Concept
1. Solver fills a cross-chain order using a contract address with no payable fallback (or an ERC-20 output whose beneficiary later gets blocklisted by the issuer) as `msg.sender`.
2. `ExtrinsicIntents._fillOrder` dispatches `RedeemEscrow` with `beneficiary = msg.sender` and `timeout: 0` [1](#0-0) .
3. On the source chain, `EvmHost.dispatchIncoming` invokes `onAccept` → `IntentsBase._withdraw`, whose native `.call` or `safeTransfer` to `beneficiary` reverts [6](#0-5) .
4. `dispatchIncoming` deletes the request receipt to allow retry [7](#0-6) , but every subsequent retry fails identically; since `timeout: 0` was used, no timeout path ever becomes available to release the escrow another way — the input tokens are permanently stuck in the `IntentGatewayV2` contract.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
