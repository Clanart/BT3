### Title
Empty aggregate signatures bypass Schnorr verification - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero signatures when the caller supplies an empty `keys_and_challenges` list and a zero `s` scalar. This is analogous to accepting `amountOutMinimum == 0`: a missing nonzero lower bound converts verification of a required output into verification of nothing. Severity: Medium.

### Finding Description
`SchnorrAggregate::read` accepts a serialized `Rs` length of zero without checking that at least one nonce/commitment was encoded. [1](#0-0) 

`SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()`; it does not reject the case where both lengths are zero. [2](#0-1) 

With no keys or challenges, the verification loop adds no weighted nonce/key pairs and queues only `(-s, G)`. [3](#0-2) 

For `s == 0`, that sole pair is `(0, G)`, whose multiexponentiation result is the identity, so verification returns true. [3](#0-2) 

The legitimate constructor path already treats an empty aggregate as invalid by returning `None` from `SchnorrAggregator::complete`, but the verifier accepts the same empty statement when it is supplied through deserialization. [4](#0-3) 

### Impact Explanation
An attacker able to submit serialized aggregate bytes to `SchnorrAggregate::read`, and to reach `verify` with an empty `keys_and_challenges` input, can produce a successful verification result without possessing any private key or signing any message. This is a forged aggregate signature rather than merely a caller selecting weak slippage protection.

Because the verifier returns `true` for a statement containing no public keys and no signatures, any protocol layer that interprets that boolean as proof that the requested signatures were verified can accept an authorization with no actual signer approval.

### Likelihood Explanation
The attack requires the verifier-facing API to allow an attacker-controlled empty `keys_and_challenges` list while accepting attacker-controlled aggregate bytes. Both conditions are exposed by public APIs: `read` accepts a zero count, and `verify` accepts the empty list as matching the zero-length `Rs` vector.

No malicious validator, leaked key, invalid curve implementation, or collusion is required; the attacker only needs to supply the four-byte zero length followed by the canonical encoding of scalar zero.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` before the length-equality check. For defense in depth, also reject a serialized `Rs` length of zero in `SchnorrAggregate::read`, matching the producer-side invariant enforced by `SchnorrAggregator::complete`.

### Proof of Concept
```rust
use ciphersuite::{Ciphersuite, group::ff::PrimeField};
use schnorr::aggregate::SchnorrAggregate;

fn empty_aggregate_verifies<C: Ciphersuite>() {
  // SchnorrAggregate serialization:
  //   u32 little-endian number of R values || s scalar encoding
  let mut encoded = 0u32.to_le_bytes().to_vec();
  encoded.extend_from_slice(C::F::ZERO.to_repr().as_ref());

  let aggregate =
    SchnorrAggregate::<C>::read(&mut encoded.as_slice()).unwrap();

  // There are no public keys or per-signature challenges, yet
  // verification succeeds because (-0) * G is the identity.
  assert!(aggregate.verify(b"example-domain", &[]));
}
```
