## Confirmed analog

The bidding-refund push-payment bug maps onto Clementine's payout-attribution mechanism.

### Title
Unsigned OP_RETURN operator attribution in `create_payout_txhandler` lets any funder misattribute reimbursement credit to an uninvolved operator - (`core/src/builder/transaction/operator_reimburse.rs`)

### Summary
The `Payout` transaction that fronts a Citrea withdrawal embeds the operator's `xonly_pk` in an `OP_RETURN` output so that, later, the verifier network and the operator's own automation attribute reimbursement rights to whichever key appears there. The user's authorization signature over the payout transaction uses `SIGHASH_SinglePlusAnyoneCanPay`, which only commits to input #0 and its matching output #0 (the user's payout). The `OP_RETURN` output carrying the operator attribution is a *later* output and is never covered by that signature, so it can be freely set by whoever actually constructs and funds the transaction.

### Finding Description
`Operator::withdraw` builds the payout transaction via `create_payout_txhandler`, hard-coding `self.signer.xonly_public_key` into the `OP_RETURN`: [1](#0-0) 

The witness for the sole signed input uses `SinglePlusAnyoneCanPay`, and `withdraw()` only checks that this signature covers input #0 (the user's payout output at index 0); outputs 1 (anchor) and 2 (`OP_RETURN`) are not part of the signed sighash: [2](#0-1) 

`fund_raw_transaction` is then used with `add_inputs: Some(true)` to top up the transaction from the operator's own wallet — i.e. whoever runs this code path funds the real BTC that reaches the user: [3](#0-2) 

Once mined, the verifier syncer determines the payer purely by parsing the (unsigned) `OP_RETURN` bytes of whichever payout transaction actually confirmed: [4](#0-3) 

This value is persisted as `payout_payer_operator_xonly_pk` and later consumed automatically: `PayoutCheckerTask` picks up "unhandled payouts" credited to an operator's own key and drives that operator into the kickoff/reimbursement flow without any additional proof that *this* operator actually broadcast/funded the specific transaction: [5](#0-4) [6](#0-5) 

The only cross-check performed anywhere is that the operator sending the *kickoff* matches the OP_RETURN-recorded key (`is_kickoff_malicious`) — it never verifies that the credited operator actually paid the inputs of the payout transaction: [7](#0-6) 

**The binding that should hold:** `payout_payer_operator_xonly_pk (OP_RETURN, unsigned) == the operator whose own funds were spent to pay the user`. Because the OP_RETURN field is outside the scope of the only signature attached to the transaction, any party capable of constructing and funding a transaction matching the user's `SIGHASH_SINGLE|ANYONECANPAY` commitment (input #0 / output #0) can write an *arbitrary* registered operator's `xonly_pk` into the `OP_RETURN`, decoupling "who is credited" from "who paid."

The withdrawal parameters (including this reusable, ANYONECANPAY signature) are broadcast by the aggregator to every matching operator simultaneously via `ClementineAggregator::withdraw`, and the whole design intentionally makes this signature shareable so any operator can race to complete it: [8](#0-7) 

Nothing in this flow restricts who else may reuse that signature outside the operator gRPC path (directly on the Bitcoin network), since the signature's scope was designed only to bind the user's payout output, not the identity of the payer.

### Impact Explanation
Because the credited operator's own automation (`PayoutCheckerTask` → `handle_finalized_payout`) blindly trusts the on-chain `OP_RETURN`, an attacker (or a rival operator acting maliciously) who actually funds the payout to the user can write a *different*, uninvolved operator's `xonly_pk` into the `OP_RETURN`. The framed operator is never asked and never funded anything, yet:
- The true funder (whoever paid the user) is not the one who is credited and thus can never claim the vault's `MoveToVaultTx` reimbursement for money it fronted — an honest operator that did the real funding is **permanently unable to be reimbursed** for that withdrawal.
- The uninvolved credited operator's automation will instead pursue the kickoff/reimburse flow and pull real BTC from the deposit's `MoveToVaultTx` UTXO for a payout it never made — i.e. **an operator reimbursed for a payout it never funded**.

Both are explicitly listed Critical impacts (custody/attribution binding broken between "the operator credited" and "the party that paid").

### Likelihood Explanation
Exploitation requires only capital to fund the payout transaction's added inputs (via any standard PSBT/`fund_raw_transaction`-equivalent tooling) plus the withdrawal's `SinglePlusAnyoneCanPay` signature and public withdrawal parameters, all of which are intentionally shared/broadcast across the operator set by the aggregator's `withdraw` RPC by design (to allow a competitive multi-operator race). No verifier, operator credential, key compromise, or protocol role is needed to construct and broadcast such a transaction — an unprivileged party with BTC can do it. This is not a rate-limiting/DoS issue; it is a data-authenticity gap in the transaction format itself.

### Recommendation
Bind the operator attribution into the same signature scope that authorizes the withdrawal, e.g.:
- Have the user sign a payload (in the Citrea withdrawal registration, or via a second commitment) that includes the specific operator `xonly_pk` allowed to claim credit, or
- Change the payout transaction's sighash to `SIGHASH_ALL` (or otherwise cover the `OP_RETURN` output) so the operator identity is cryptographically bound to the same signature that authorizes the spend, or
- Require the operator to additionally prove it funded the specific transaction (e.g. via wallet-derived proof of the extra inputs) before automation acts on the `OP_RETURN` attribution, rather than trusting the field unconditionally.

### Proof of Concept
1. User signs a withdrawal payout with `SinglePlusAnyoneCanPay` for `input #0`/`output #0`, and registers it (this becomes visible to the operator set via the aggregator's broadcast `withdraw` RPC).
2. Attacker (or Operator A, acting maliciously toward Operator B) independently builds a transaction spending the same withdrawal UTXO with the same signature at input/output index 0, adds its own funding inputs via a standard PSBT funding call (equivalent to `fund_raw_transaction`), and sets the `OP_RETURN` output to Operator B's `xonly_pk` instead of its own.
3. Attacker broadcasts and gets this transaction mined before any tx from Operator B.
4. `update_finalized_payouts` in `core/src/verifier.rs` reads the OP_RETURN and records Operator B as `payout_payer_operator_xonly_pk`.
5. Operator B's `PayoutCheckerTask` (`core/src/task/payout_checker.rs`) sees an "unhandled payout" credited to its own key and automatically drives `handle_finalized_payout`, pursuing kickoff/reimbursement for a withdrawal it never funded — pulling BTC from the vault for the attacker's payment, while the true funder can never be reimbursed for that outpoint.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,

        .finalize();

    /// Checks if the operator who sent the kickoff matches the payout data saved in our db
    /// Payout data in db is updated during citrea sync.
    async fn is_kickoff_malicious(
        &self,
        kickoff_witness: Witness,
        deposit_data: &mut DepositData,
        kickoff_data: KickoffData,
        dbtx: DatabaseTransaction<'_>,
    ) -> Result<bool, BridgeError> {
        let move_txid =
            create_move_to_vault_txhandler(deposit_data, self.config.protocol_paramset())?
                .get_cached_tx()
                .compute_txid();

        let payout_info = self
            .db
            .get_payout_info_from_move_txid(Some(dbtx), move_txid)
            .await?;
        let Some((operator_xonly_pk_opt, payout_blockhash, _, _)) = payout_info else {
            tracing::warn!(
                "No payout info found in db for move txid {move_txid}, assuming malicious"
            );
            return Ok(true);
        };

        let Some(operator_xonly_pk) = operator_xonly_pk_opt else {
            tracing::warn!("No operator xonly pk found in payout tx OP_RETURN, assuming malicious");
            return Ok(true);
        };

        if operator_xonly_pk != kickoff_data.operator_xonly_pk {
            tracing::warn!("Operator xonly pk for the payout does not match with the kickoff_data");
            return Ok(true);
        }

        let wt_derive_path = WinternitzDerivationPath::Kickoff(
            kickoff_data.round_idx,
            kickoff_data.kickoff_idx,
            self.config.protocol_paramset(),
        );
        let commits = extract_winternitz_commits(
            kickoff_witness,
            &[wt_derive_path],
            self.config.protocol_paramset(),
        )?;
        let blockhash_data = commits.first();
        // only last 20 bytes of the blockhash is committed
        let truncated_blockhash = &payout_blockhash[12..];
        if let Some(committed_blockhash) = blockhash_data {
            if committed_blockhash != truncated_blockhash {
                tracing::warn!("Payout blockhash does not match committed hash: committed: {:?}, truncated payout blockhash: {:?}",
                        blockhash_data, truncated_blockhash);
                return Ok(true);
            }
        } else {
            return Err(eyre::eyre!("Couldn't retrieve committed data from witness").into());
        }
        Ok(false)
    }
