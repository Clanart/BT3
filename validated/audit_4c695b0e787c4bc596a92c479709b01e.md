### Title
Missing timestamp freshness check allows indefinite replay of App Proxy signed requests - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb](lib/shopify_app/controller_concerns/app_proxy_verification.rb))

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates the HMAC signature of an App Proxy request but never checks the freshness of the `timestamp` query parameter that Shopify includes in every signed proxy request. This is the same bug class as the reported Pyth `publishTime` staleness issue: a value intended to bound the validity window of signed data (`timestamp` here, `publishTime` there) is present in the payload but is never compared against the current time, so a previously valid signed request/price can be reused indefinitely.

### Finding Description
`query_string_valid?` in [1](#0-0)  only recomputes the HMAC over the query parameters (including `timestamp`) and compares it to the supplied `signature`:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?
  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
```
`calculated_signature` in [2](#0-1)  simply HMACs all sorted query params, which includes `timestamp`, but nothing in `verify_proxy_request` ( [3](#0-2) ) ever checks that this timestamp is recent. There is no equivalent to a "stale price" tolerance window — the code accepts a signature computed at any point in the past, forever, as long as the byte-for-byte query string (including `timestamp`) is replayed. This is confirmed by the test suite, which asserts that a fixed, years-old `timestamp=1466106083` with its matching signature is still accepted as valid: [4](#0-3) .

### Impact Explanation
Because there is no expiry/staleness check, any App Proxy request that an attacker manages to capture in full (e.g., via browser history, referrer headers, shared/forwarded links, server logs, or a man-in-the-middle before TLS termination) remains a valid, accepted signed request indefinitely. This lets an anonymous attacker replay that exact captured request against the app's App Proxy endpoint at any future time and have it treated as an authentic, Shopify-signed request — a forged/replayed signed request being accepted, matching the "accepted forged signed request" impact category. Depending on what the app does with app-proxy data (e.g., trusting `shop`/`logged_in_customer_id` params from the signed query string for authorization decisions), this could enable actions to be performed under a stale, no-longer-current context.

### Likelihood Explanation
Exploitation requires the attacker to have obtained one legitimate, fully-signed proxy query string at some point (no secret knowledge needed) — a realistic bar for URLs shared through referrer leakage, logging systems, or browser history, especially since storefront-triggered App Proxy requests are GET requests with everything in the URL. Once captured, the replay works with zero rate limiting or expiry, unlike Shopify's own webhook validation utilities which typically also don't enforce a timestamp for the library's HMAC helper but this affects only the app-proxy verification path shipped in this repo.

### Recommendation
Extract the `timestamp` parameter from the query string in `verify_proxy_request`/`query_string_valid?` and reject the request if `Time.now.to_i - timestamp.to_i` exceeds a small tolerance (e.g., a few minutes), mirroring the recommendation in the referenced report: compare the signed timestamp to the current time and enforce a bounded staleness window before accepting the signature as valid.

### Proof of Concept
1. Capture a legitimate App Proxy request URL sent by Shopify to the app, e.g.
   `GET /app_proxy/basic?shop=some-random-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=f5cd7233558b1c50102a6f33c0b63ad1e1072a2fc126cb58d4500f75223cefcd`
2. Replay this exact URL against the app at any later time (days, months, or years later).
3. `ShopifyApp::AppProxyVerification#verify_proxy_request` recomputes the same HMAC over the same query params and accepts it as valid, exactly as the existing test demonstrates [4](#0-3) , because no code path checks that `timestamp=1466106083` is stale.

```ruby
    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
