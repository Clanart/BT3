### Title
Unauthenticated `ReceivedOutput` deserialization permits fabricated non-spendable deposits - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts a caller-supplied scalar offset, `TxOut`, and `OutPoint` without authenticating the tuple or checking that the output belongs to the scanner’s registered script set. A normally scanned output carries an offset selected from `Scanner::scripts` only after the transaction’s `script_pubkey` matched a registered script. Deserialization bypasses that confinement and lets an attacker associate any offset with any claimed output and outpoint. [1](#0-0) [2](#0-1) 

### Finding Description
The scanner-created invariant is that `ReceivedOutput.offset` is the offset returned by `self.scripts.get(&output.script_pubkey)`, while `output` and `outpoint` describe a transaction output which matched that registered script. [3](#0-2) 

`ReceivedOutput::read` instead parses three independent attacker-controlled fields and returns them unchanged: `Secp256k1::read_F` supplies `offset`, consensus decoding supplies `output`, and consensus decoding supplies `outpoint`. [4](#0-3) 

No check verifies that `output.script_pubkey` belongs to the scanner, that the supplied offset is the offset registered for that script, or that `outpoint` identifies a confirmed output containing the supplied `TxOut`. The accessors then expose the attacker-selected offset and amount through `offset()` and `value()`. [5](#0-4) 

### Impact Explanation
A downstream consumer that treats a deserialized `ReceivedOutput` as equivalent to scanner output can report funds as received even though the encoded `OutPoint` does not identify a spendable wallet output. It can also drive transaction construction with an unrelated `TxOut`/outpoint while requesting use of an unrelated threshold-key offset, producing signatures over an unintended or invalid spend. [5](#0-4) 

The concrete security invariant violated is “funds reported received must correspond to a chain output spendable using the returned offset.” The scanner establishes this by deriving the offset from the script registry, but the deserializer accepts an unauthenticated tuple that crosses that boundary. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The attack requires an unprivileged party to supply serialized `ReceivedOutput` bytes to a caller that uses them as wallet outputs or signing inputs. Such serialized outputs are explicitly exposed through `ReceivedOutput::read`, and the crafted bytes are only a canonical scalar followed by consensus-encoded `TxOut` and `OutPoint` values. [1](#0-0) 

No hash collision, validator compromise, secret disclosure, or malformed curve encoding is needed because `read` itself returns the fabricated object successfully. [4](#0-3) 

### Recommendation
Do not use `ReceivedOutput::read` as an authenticated wallet-output source. Re-scan the referenced on-chain transaction with `Scanner`, derive `offset` from `Scanner::scripts` based on the actual `script_pubkey`, and compare the decoded `TxOut` and amount with the confirmed chain output. [8](#0-7) [2](#0-1) 

If serialized scanner results must cross an untrusted storage or IPC boundary, authenticate them at that boundary and document that `ReceivedOutput::read` is only a trusted-state decoder. A safer API can take the `Scanner` and transaction as inputs and rebuild the `ReceivedOutput` through `scan_transaction` rather than trusting an embedded offset/outpoint pair. [2](#0-1) 

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs
use bitcoin::{
  consensus::serialize,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use frost::curve::Secp256k1;
use ciphersuite::{Ciphersuite, group::ff::PrimeField};

// Attacker-controlled bytes passed to ReceivedOutput::read.
let mut forged = vec![];

// Claim the output is spendable with scanner offset 1.
forged.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr().as_ref());

// Claim an arbitrary value and script; this script need not be registered
// with the Scanner and need not correspond to the supplied offset.
forged.extend(serialize(&TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: ScriptBuf::new(),
}));

// Reference an arbitrary, potentially nonexistent, outpoint.
forged.extend(serialize(&OutPoint {
  txid: Txid::all_zeros(),
  vout: 0,
}));

let output = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
assert_eq!(output.offset(), <Secp256k1 as Ciphersuite>::F::ONE);
assert_eq!(output.value(), 1_000_000);
assert_eq!(output.outpoint().vout, 0);
```

The bytes decode successfully because `read` only parses each field; it never reconstructs the scanner lookup that created the legitimate relationship among offset, script, output, and outpoint. [4](#0-3) [7](#0-6)
