### Title
Deserializing `ThresholdKeys` with a large `n` triggers quadratic Lagrange interpolation in `ThresholdKeys::new`, causing blocking CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts attacker-controlled `t` and `n` parameters (each a u16, so up to 65535) and then calls `ThresholdKeys::new`. For `Interpolation::Lagrange`, `ThresholdKeys::new` computes the group key by iterating over `t` participants and calling `interpolation_factor` for each — and `interpolation_factor` itself loops over all `t` participants. This makes deserialization of a crafted `ThresholdKeys` an O(t²) sequence of point multiplications and field inversions/multiplications, consuming excessive blocking CPU from untrusted bytes — the direct analog of the aiohttp chunked-message CPU exhaustion bug.

### Finding Description
In `ThresholdKeys::read`, `t`, `n`, and `i` are read from the wire, followed by `n` verification-share points, before `ThresholdKeys::new` is invoked [1](#0-0) . `ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation_factor(i, t)` over `1..=t` [2](#0-1) . For `Interpolation::Lagrange`, each `interpolation_factor` call performs a loop over every included participant doing field multiplications, a subtraction, and a field inversion [3](#0-2) . The result is O(t²) field operations plus t scalar-point multiplications, all performed on blocking CPU during what is nominally a parsing operation.

The same quadratic cost is reachable again via `ThresholdKeys::view`, which calls `interpolation_factor` once per included participant after only checking `included.len() <= n` [4](#0-3) .

### Impact Explanation
An unprivileged party who can feed untrusted bytes to `ThresholdKeys::read` (a reachable path per scope) can specify `interpolation = Lagrange` with `t = n = 65535` and supply `n` valid group points (~2 MB input). `ThresholdKeys::new` then performs ~4.3×10⁹ field multiplications and 65535 inversions plus 65535 point multiplications — minutes of blocking CPU on a single thread — before returning any result. In an async/blocking context this stalls the executor or thread, denying service to all other work on that node. Like the aiohttp advisory, the input is small relative to the CPU consumed, and the cost is quadratic in attacker-controlled parameters.

### Likelihood Explanation
Any context where a `ThresholdKeys` blob is deserialized from untrusted input (e.g., keys or shares relayed, recovered, or loaded from externally supplied data) is reachable with a ~2 MB payload. `n` is only bounded by u16 and by the presence of that many encoded points; there is no semantic cap tied to real validator set sizes. `ThresholdParams::new` only checks `t <= n` and `t, n != 0` [5](#0-4) , so `t = n = 65535` passes validation for Lagrange interpolation.

### Recommendation
Enforce a reasonable upper bound on `n` (e.g., the maximum validator set size actually supported) inside `ThresholdKeys::read` and `ThresholdParams::new` before performing any interpolation work. Alternatively, compute the group key with a single multiexp and precompute Lagrange denominators once (O(t) total via batch inversion) rather than per-participant O(t) loops.

### Proof of Concept
1. Build a buffer: `C::ID` length (u32 LE) + `C::ID`, then `t = 0xFFFF`, `n = 0xFFFF`, `i = 1` (u16 LE each), then interpolation byte `1` (Lagrange), then a valid scalar encoding for `secret_share`, then 65535 valid encoded `G` points.
2. Feed the buffer to `ThresholdKeys::<C>::read`.
3. `ThresholdKeys::new` executes `65535 × 65535` field multiplications plus inversions and 65535 point multiplications inside the group-key summation, blocking the thread for an extended period while parsing a ~2 MB input.
