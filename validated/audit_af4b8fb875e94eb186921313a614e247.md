### Title
Submodule `protocol.file.allow=always` override may allow attacker-controlled `.gitmodules` to read local filesystem paths - ([File: app/src/lib/git/submodule.ts])

### Summary
`git`, by default (since the CVE-2022-39253 fix), refuses to honor `file://` submodule URLs discovered in a cloned/fetched repository's `.gitmodules`, precisely to stop a malicious repo from tricking a client into copying arbitrary local directories into the submodule path. GitHub Desktop's `updateSubmodulesAfterOperation` explicitly re-enables that disabled protection by passing `-c protocol.file.allow=always` when `allowFileProtocol` is `true` [1](#0-0) , and this flag is threaded through `checkoutBranch`/`checkoutCommit` in `app/src/lib/git/checkout.ts` [2](#0-1) .

### Finding Description
`updateSubmodulesAfterOperation` runs `git submodule update --init --recursive` and, when `allowFileProtocol` is set, prepends `-c protocol.file.allow=always` to the args [3](#0-2) . This is a direct override of the git-core default (`protocol.file.allow=user`/`never`) that was added upstream specifically to prevent submodule URLs pointing at `file:///...` from being honored automatically, because a `.gitmodules` file is fully attacker-controlled content in any cloned/fetched repository. If `allowFileProtocol=true` is reachable on a checkout of a branch/commit fetched from a repository the user doesn't fully trust, an attacker can craft a `.gitmodules` entry such as `url = file:///Users/victim/.ssh` (or any other sensitive local path) and have Desktop's `git submodule update --init` clone that directory's contents into the repository's working tree.

### Impact Explanation
If reachable from an untrusted/attacker-influenced repository (i.e., not requiring the user to have manually opted into "allow file protocol" for a repo they already fully control locally), this would let a hostile repository/branch pull arbitrary local files/directories into the working copy under `<submodule-path>/`, where they become visible in Desktop's diff/history views and could be committed and pushed to a remote — turning a passive "clone/checkout" action into disclosure of local files outside the repository boundary, mirroring the report's "SSRF causes disclosure of resources the operator didn't intend to expose" pattern but via `file://` instead of a network endpoint.

### Likelihood Explanation
This is **uncertain** and depends entirely on the caller-side gating of `allowFileProtocol` in `app/src/lib/stores/app-store.ts`, which has 8 references to this parameter that I was unable to fully review before running out of tool budget. If the flag is only ever set to `true` for repositories whose primary remote is itself `file://` (i.e., a repo the user already has full local control over), this does not meet the "unprivileged, attacker-controlled remote content" bar and would not be a valid analog — it would just be intentional dev/test convenience. If instead it can be set based on repository metadata or default behavior independent of trust boundary, it would be a valid analog.

### Recommendation
Verify in `app/src/lib/stores/app-store.ts` exactly which call sites pass `allowFileProtocol: true` to `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation`, and confirm this is strictly limited to repositories that are already local-filesystem-only (not remotely fetched/cloned from an untrusted GitHub host). If any path allows `allowFileProtocol=true` on a repo with a GitHub-hosted or otherwise untrusted remote, restrict it to only known-safe (local) remotes, or drop the `protocol.file.allow=always` override entirely and surface a user-facing prompt before ever cloning a `file://` submodule URL discovered in fetched content.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file with `[submodule "x"] path = x` and `url = file:///Users/victim/.ssh` (or any sensitive absolute path reachable on the victim's machine).
2. Victim clones/fetches this repository in GitHub Desktop and checks out the branch/commit containing this `.gitmodules`.
3. If the checkout path that runs with `allowFileProtocol=true` is reached (per `app/src/lib/git/checkout.ts` lines 102–207 [4](#0-3) ), Desktop invokes `git -c protocol.file.allow=always submodule update --init --recursive`, cloning the victim's local `~/.ssh` directory content into the repository's working tree at `x/`.
4. The contents are now visible in Desktop's file browser/diff and can be committed/pushed by the (unwitting) user, exfiltrating local files.

**Uncertainty**: I could not confirm within the tool-call budget whether `allowFileProtocol=true` is ever reachable for a checkout originating from an untrusted/attacker-controlled remote versus only for repos the user already added as pure local (`file://`) repositories. This distinction determines whether this is a genuine unprivileged analog or an intentional, already-trusted local-only feature. I recommend a follow-up review of `app/src/lib/stores/app-store.ts` (8 references) and `app/src/ui/dispatcher/dispatcher.ts` (6 references) to settle this before treating the finding as confirmed.
