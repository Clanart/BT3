### Title
Dust-denom griefing causes unbounded gas cost on victim's balance reads (`GetAllBalances`/`SpendableCoins`) - ([File: sei-cosmos/x/bank/keeper/view.go])

### Summary
`x/bank`'s `GetAllBalances` iterates every distinct denom key stored under an account's balance prefix in the KV store, and `SpendableCoins` (used for locked-coin computation) calls `GetAllBalances` internally. Because any account can costlessly send dust amounts of arbitrarily many distinct denoms to a victim (e.g. via repeated `tokenfactory` `MsgCreateDenom` + `MsgMint` + `bank send`, or wasm/IBC-originated denoms), an attacker can inflate the number of KV entries under the victim's balance prefix without bound. This mirrors the Beanstalk "Plot spam" bug class: an unbounded, attacker-growable per-account collection that a core operation must fully scan, causing quadratic/linear gas blow-up for the victim on every subsequent read of that collection.

### Finding Description
`BaseViewKeeper.GetAllBalances` calls `IterateAccountBalances`, which iterates every key under the account's balance store prefix and unmarshals each `sdk.Coin`: [1](#0-0) [2](#0-1) 

`SpendableCoins`/`spendableCoins` (used to determine what an account can spend, e.g. by the EVM precompile `all_balances`/`spendableBalances` and elsewhere) directly depends on `GetAllBalances`: [3](#0-2) 

The repository's own test demonstrates the scaling problem directly: populating an account with 100,000 distinct denoms and calling `GetAllBalances` produces a result set proportional to that count, confirming the operation is O(number of distinct denoms held): [4](#0-3) 

An attacker can grow this count on a victim's account for free (relative to victim impact) using the permissionless `tokenfactory` module: any account may call `MsgCreateDenom` to mint a new, uniquely-named `factory/<creator>/<subdenom>` denom and then send an arbitrarily small (even zero-value-adjacent) amount of it to the victim via `bank send`: [5](#0-4) [6](#0-5) 

Each `MsgCreateDenom`/`bank send` pair costs the attacker only the standard tx fee, while each resulting denom permanently occupies a KV entry in the victim's balance prefix (analogous to Beanstalk's `plotIndexes` array entries). There is no per-account cap on distinct denoms a victim can be forced to hold, and no eviction mechanism for dust/zero-adjacent balances.

### Impact Explanation
Once a victim's account accumulates a large number of distinct denoms, any code path that calls `GetAllBalances`/`SpendableCoins` for that account incurs gas/CPU cost proportional to the number of denoms. This directly affects:
- EVM precompile calls that surface all balances (`bank.all_balances`, `bank.spendableBalances`), which could revert with out-of-gas for the victim when querying/using their own balances. [7](#0-6) 
- Any internal `SpendableCoins`/locked-coins computation the victim's account triggers (vesting checks, transfer validations, etc.), which walks the full balance set every time.

This is a griefing/DoS vector against a specific victim's ability to use bank-balance-dependent functionality without their consent, at attacker cost far lower than victim's remediation cost — the same asymmetry flagged in the original Beanstalk report.

### Likelihood Explanation
Likelihood is moderate-to-high: `tokenfactory` denom creation and native/IBC/CW20 sends are permissionless, require no counterparty approval, and the attack is a straightforward, repeatable transaction pattern (create denom → mint → send dust) that can be scripted and run at scale by any unprivileged account. The main constraint is the attacker's own transaction fees per denom created/sent, which is a bounded, attacker-controlled cost (not a protocol-imposed limiter tied to the victim's exposure), and Sei explicitly targets low fees ("Protocol will operate on L2 with cheap gas" — the same rationale cited in the original report applies here since Sei is a low-fee, high-throughput chain).

### Recommendation
- Cap the number of distinct denoms trackable per account in `x/bank` view keeper operations, or require an explicit opt-in/registration before an account's balance for a new denom is created via transfer (reject implicit `AddCoins` for new denoms below a dust threshold unless previously registered).
- Consider bounding `GetAllBalances`/`SpendableCoins` with pagination in all call sites, and disallow unauthenticated dust transfers of newly created tokenfactory denoms into an address that has not opted in.
- Add a minimum transferable amount or an explicit anti-dust rejection at `SendCoins`/`AddCoins` for denoms an account has zero pre-existing relationship with.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` N times with unique subdenoms (permissionless, `x/tokenfactory/keeper/createdenom.go`), each producing `factory/<attacker>/<subdenom>_i`.
2. Attacker mints a minimal amount of each denom to itself and sends it to `victim` via `bank send`.
3. Each successful send calls `BaseSendKeeper.AddCoins`, adding a new KV entry under `victim`'s balance prefix.
4. Repeat for large N (e.g. tens of thousands, matching the scale shown feasible in `TestKeeperGetAllBalances`).
5. `victim` (or any contract/precompile call on their behalf) subsequently calls `bank.all_balances`/`spendableBalances` or triggers `SpendableCoins`, and the operation's cost/latency scales with N, potentially exceeding available gas and causing failures for the victim.

**Uncertainty note:** I was unable to fully trace whether `SpendableCoins`/`GetAllBalances` is invoked inside the core `SendCoins`/fee-deduction hot path in a way that would make *every* transaction from the victim revert (as opposed to only explicit balance-query call sites like the `bank` precompile), because reading `sei-cosmos/x/bank/keeper/send.go` in full was cut short by the iteration limit. This affects the precise severity classification (pure query-path DoS vs. transaction-blocking DoS); a Devin session with full repo access would be needed to confirm whether `SubUnlockedCoins`/`AddCoins` in the hot send path also depend on the unbounded iteration, which would elevate this from a query-availability issue to a transaction-blocking one directly analogous to the original Beanstalk Plot-transfer DoS.

func (k BaseViewKeeper) GetAllBalances(ctx sdk.Context, addr sdk.AccAddress) sdk.Coins {
	balances := sdk.NewCoins()
	k.IterateAccountBalances(ctx, addr, func(balance sdk.Coin) bool {
		balances = append(balances, balance)
		return false
	})

	return balances.Sort()
}

// IterateAccountBalances iterates over the balances of a single account and
// provides the token balance to a callback. If true is returned from the
// callback, iteration is halted.
func (k BaseViewKeeper) IterateAccountBalances(ctx sdk.Context, addr sdk.AccAddress, cb func(sdk.Coin) bool) {
	accountStore := k.getAccountStore(ctx, addr)

	iterator := accountStore.Iterator(nil, nil)
	defer func() { _ = iterator.Close() }()

	for ; iterator.Valid(); iterator.Next() {
		var balance sdk.Coin
		k.cdc.MustUnmarshal(iterator.Value(), &balance)

		if cb(balance) {
			break
		}
	}
}

// spendableCoins returns the coins the given address can spend alongside the total amount of coins it holds.
// It exists for gas efficiency, in order to avoid to have to get balance multiple times.
func (k BaseViewKeeper) spendableCoins(ctx sdk.Context, addr sdk.AccAddress) (spendable, total sdk.Coins) {
	total = k.GetAllBalances(ctx, addr)
	locked := k.LockedCoins(ctx, addr)

	spendable, hasNeg := total.SafeSub(locked)
	if hasNeg {
		spendable = sdk.NewCoins()
		return
	}

	return
}

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.

func (p PrecompileExecutor) all_balances(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) ([]byte, uint64, error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	addr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}

	coins := p.bankKeeper.GetAllBalances(ctx, addr)

	// convert to coin balance structs
	coinBalances := make([]CoinBalance, 0, len(coins))

	for _, coin := range coins {
		coinBalances = append(coinBalances, CoinBalance{
			Amount: coin.Amount.BigInt(),
			Denom:  coin.Denom,
		})
	}

	bz, err := method.Outputs.Pack(coinBalances)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
