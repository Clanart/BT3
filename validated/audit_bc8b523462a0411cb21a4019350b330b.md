### Title
`checkoutBranch`/`checkoutCommit` can re-enable `protocol.file.allow=always` for attacker-controlled submodule URLs during branch checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` flag which, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation it runs after a checkout [1](#0-0) . `git`'s default of restricting `file://`/local-path submodules (the fix for CVE‑2022‑39253) exists specifically because a repository under attacker control can declare a submodule pointing at an arbitrary local path on the victim's machine; re-enabling `protocol.file.allow=always` reintroduces that class of issue for any checkout performed with `allowFileProtocol: true`.

### Finding Description
`checkoutBranch` and `checkoutCommit` both take an `allowFileProtocol` parameter (default `false`) that is forwarded unchanged into `updateSubmodulesAfterOperation` [2](#0-1) [3](#0-2) . When `true`, the submodule update command is run with `protocol.file.allow=always` [1](#0-0) , which is exactly the setting git hardened by default (in git ≥2.38.1) to stop malicious repositories from declaring submodules with `file://` (or bare local path) URLs that reference sensitive files/directories elsewhere on disk (CVE-2022-39253). With this override, an attacker-controlled repository (or an attacker-controlled branch a victim checks out, e.g. via a PR checkout, "Open in Desktop" clone, or a normal `git checkout` of an untrusted remote branch) that ships a `.gitmodules` entry with a `file://` URL pointing at a local path can have that path's contents linked/cloned into the working tree of the repository the victim already has open, without any additional prompt beyond the initial checkout action.

I could not fully confirm within the available searches which specific UI/dispatcher call sites pass `allowFileProtocol: true` (only `submodule-test.ts`/`checkout-test.ts` unit-test helpers were found exercising it directly), so it's unverified whether a completely unprivileged, attacker-controlled trigger currently reaches this code path in the shipped app, or whether it is gated behind a scenario that already requires the user to have manually initialized an uninitialized submodule. This is a meaningful gap in the evidence.

### Impact Explanation
If reachable from an ordinary "checkout branch"/"open pull request"/"clone" flow without additional user confirmation, this allows disclosure of local files (e.g., dotfiles, SSH keys, config files) into a tracked git object during submodule init, which the user could subsequently and unknowingly commit/push, exfiltrating file contents to a remote the attacker controls. This matches the allowed impact category of "silent corruption of what the user commits or pushes" / credential exfiltration.

### Likelihood Explanation
Likelihood is contingent on whether the flag is actually wired to a code path an attacker's repository content can trigger without extra user consent (e.g. automatically during "checkout branch with submodules" flows) versus only via an explicit "trust this submodule"-style user action. Based on the code I could inspect, the flag exists in production code (`checkout.ts`, `submodule.ts`) and is not obviously behind a distinct confirmation dialog at the call site level shown, but I was unable to trace all callers of `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` to determine the actual trigger condition.

### Recommendation
Audit every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` that passes `allowFileProtocol: true`, and require an explicit, submodule-URL-scoped user confirmation (showing the actual `file://` path/URL) before ever re-enabling `protocol.file.allow=always`, consistent with the upstream git security fix's intent. Consider limiting the override to a per-submodule allow-list validated against the working directory's own trusted root rather than a blanket flag.

### Proof of Concept
Given the incomplete verification of the reachable UI trigger, I cannot provide a fully confirmed end-to-end PoC. The mechanical PoC for the underlying primitive is:
1. Attacker creates a repository/branch with `.gitmodules` containing `url = file:///home/victim/.ssh` (or similar).
2. Victim's Desktop performs a checkout that internally calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true`, which runs `git -c protocol.file.allow=always submodule update --init --recursive` [1](#0-0) .
3. Git would normally refuse this submodule URL by default; with the override it clones/hardlinks the local path content into the submodule working directory of the victim's already-open repository.

Because I could not confirm the exact unprivileged UI trigger that sets `allowFileProtocol: true` for an attacker-supplied branch/commit in this pass, treat this as a **candidate** finding requiring further verification of call sites before treating it as fully confirmed.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )
```
