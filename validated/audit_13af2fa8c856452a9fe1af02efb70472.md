### Title
Unrestricted token sweep via caller-supplied `_rewards` array in `compound` - (rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` sweeps "non-compoundable" rewards by directly reading `IERC20(_rewards[i][j]).balanceOf(address(this))` and transferring the entire balance to `msg.sender`, where `_rewards[i][j]` is a fully caller-supplied address with no validation that it is an actual reward token owed to that specific caller for the specific `_lps[i]` pool. The only check performed is against `compoundableRewards`, a mapping the owner uses to flag which tokens should instead go through conversion/locking, not a registry of which tokens are legitimately claimable for a given pool/user.

### Finding Description
In `compound()`:
<cite repo="Annirich/contracts--013" path="rewards/ManualCompound.sol" start="123|138" end="123|138" /> [1](#0-0) 
the loop iterates the caller-supplied `_rewards[i][j]` list (the exact same array passed into `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`), and for any address not present in `compoundableRewards`, it reads the contract's *entire current balance* of that token and transfers it to `msg.sender`. There is no cross-check that:
- the named address is a valid reward token for the given `_lps[i]` pool, or
- the balance being swept was actually produced by *this caller's* claim in *this* call.

The second loop, over the contract's own `rewards` registry (`rewards.length`), has a similar structural weakness: it sweeps whatever `balanceOf(address(this))` currently is for each registered reward token to `msg.sender`, regardless of whether that balance corresponds to the calling user's entitlement: [2](#0-1) 

Because `multiclaimOnBehalf` requires the `ManualCompound` contract itself to hold the `_onlyCompounder` role on `MasterMagpie` [3](#0-2) , an unprivileged EOA cannot call `multiclaimOnBehalf` directly, but can freely invoke it indirectly through `ManualCompound.compound()`, supplying any `_lps`/`_rewards` combination.

The `_multiClaim` internal claim path is `nonReentrant` [4](#0-3) , and I was not able to fully trace `_claimBaseRewarder`'s per-user accounting logic within the available tool budget to confirm whether claimed transfers are strictly bounded to the calling user's own accrued share. However, independent of that, the balance-sweep logic itself is a design flaw: it does not tie the swept amount to anything computed from this specific claim — it simply reads whatever ERC20 balance the contract currently holds for the named address. Any token balance sitting in the contract for a reason unrelated to the caller's own claim (e.g., tokens accidentally/directly transferred to the contract, dust left from rounding in prior claims, or reward tokens forwarded to the contract by other mechanisms) can be fully drained by any caller simply by naming that token address in `_rewards`, as long as it is not in `compoundableRewards`.

### Impact Explanation
Any balance of a non-flagged ERC20 token held by `ManualCompound` can be swept in full by an arbitrary caller who merely references that token address in the `_rewards` argument, without the contract verifying that the balance is attributable to that caller's own claim. This matches "a caller must not be able to name an arbitrary token and receive the contract's entire balance of it" — the invariant is violated at the code level. If such a balance mismatch occurs (via leftover dust, misdirected transfers, or timing between separate legitimate claims), this results in direct theft of funds that rightfully belong to another party or to the protocol.

### Likelihood Explanation
Exploitability is unconditional on the caller side (no privilege required, only knowledge of a target token address), but realizing an actual *loss of another user's funds* depends on the contract holding a residual/misattributed balance of a given token at the time of the call. Within a single `compound()` transaction, MasterMagpie's claim path and both sweep loops execute atomically, so a self-caller's own funds are normally fully swept out in the same transaction, leaving no reachable window for a second transaction to steal them under the exact atomic ordering. I could not fully confirm within the available time whether `_claimBaseRewarder`/the underlying rewarder can ever forward more than a specific user's precisely accrued share into `ManualCompound`'s balance (which would make the "large honest claim leaves reconciled reward unswept" precondition concretely reachable). This aspect remains unverified due to tool-call budget limits.

### Recommendation
- Validate `_rewards[i][j]` against the actual reward tokens registered for `_lps[i]` (e.g., query the rewarder/pool for its valid reward token list) before sweeping, rather than only checking `compoundableRewards`.
- Track and sweep only the *delta* balance produced by the specific `multiclaimOnBehalf` call (e.g., snapshot balances before/after the claim per token) instead of the raw `balanceOf(address(this))`, in both the non-compoundable sweep loop and the compoundable-rewards processing loop.
- Add `nonReentrant` to `compound()` itself as defense in depth.

### Proof of Concept
Not fully reproducible with confirmed exploit conditions given the unresolved question of `_claimBaseRewarder`'s per-user accounting (see Likelihood section). A Foundry/Hardhat test plan to validate the code-level flaw:
1. Deploy `ManualCompound` with a mock `MasterMagpie` whose `multiclaimOnBehalf` is a no-op (to isolate the sweep logic).
2. Directly transfer an arbitrary ERC20 token (not in `compoundableRewards`) into `ManualCompound`'s balance, simulating a residual/misattributed balance.
3. Call `compound(_lps=[dummyLp], _rewards=[[thatToken]], 0, 0, false)` from an unprivileged EOA with no stake in `dummyLp`.
4. Assert the EOA receives the entire token balance despite having no legitimate claim to it, confirming the sweep loop is unchecked against per-user entitlement (lines 127–138 of `ManualCompound.sol`).

Further work is needed against the real `MasterMagpie`/rewarder claim implementation to determine whether an honest user's large claim can ever leave a reconciled-but-unswept balance reachable by a subsequent attacker transaction in the same block.
