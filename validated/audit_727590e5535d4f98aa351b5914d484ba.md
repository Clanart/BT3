### Title
Debug-only logging of full message contents/raw payloads on JSON⇄binary parse paths - (File: `src/google/protobuf/json/internal/parser.cc`)

### Summary
CVE-2023-1550 describes NGINX Agent inserting sensitive data (private keys) into log files, but only when non-default trace-level logging is enabled — a case of a diagnostic/debug logging path bypassing the normal "don't persist secrets" invariant. The Protobuf analog is the `PROTOBUF_DEBUG` / `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` build-time flag, which — when enabled — causes the JSON parser/unparser to log complete input/output payloads (including field values from attacker-supplied or application data) via `ABSL_DLOG(INFO)`.

### Finding Description
`port_def.inc` defines the macro explicitly named to acknowledge the risk: [1](#0-0) 

When this compile-time flag is set, `PROTOBUF_DEBUG` evaluates to `true`, and several code paths in `json/internal/parser.cc` and `json/internal/unparser.cc` then log the entire raw input bytes and/or fully-formatted output/message content at `INFO` level via `ABSL_DLOG`:
- `JsonStreamToMessage` logs the parsed message's `DebugString()` (i.e., every field value, unredacted, unless `debug_redact` annotations are present and honored by that code path) after parsing a JSON payload into a message: [2](#0-1) 
- `JsonToBinaryStream` buffers and hex-dumps the entire raw JSON input and the resulting binary output: [3](#0-2) [4](#0-3) 

This is functionally identical to the NGINX Agent case: an operationally-gated verbose/trace logging mode is the *only* thing standing between attacker-supplied payload contents and a log sink that may be readable by lower-privileged local users or shipped to a centralized log aggregator. The "invariant" that fails is: sensitive field values (private keys, tokens, credentials carried in a `bytes`/`string` field) should never be persisted to logs regardless of build configuration, but this flag makes that persistence a supported, if non-default, mode.

Protobuf does have a mitigating mechanism — `debug_redact` field options and `TextFormat`'s `enablingSafeDebugFormat`/`shouldRedact` machinery (Java: `TextFormat.java` `Printer.shouldRedact`) — but that redaction only applies to the C++/Java `TextFormat::Printer` "safe debug format" path invoked explicitly (e.g. `DebugFormat`). The `ABSL_DLOG` calls in `parser.cc`/`unparser.cc` use plain `message->DebugString()` and raw byte dumps (`absl::CHexEscape`, `absl::BytesToHexString`), which do **not** go through the redaction-aware safe debug format, so `debug_redact`-tagged fields (and raw bytes generally) are not protected on this path.

### Impact Explanation
If a consuming application enables `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` in production (e.g., for troubleshooting, mirroring the "non-default trace level logging" condition in the original CVE), any JSON↔binary conversion of attacker-controlled or sensitive application data (API keys, credentials, PII carried in protobuf messages) will be written verbatim to logs. An attacker with local log-file read access (same threat model as the original CVE: "authenticated attacker with local access to read agent log files") could recover secrets that were never intended to be persisted. This matches the CVE's Medium severity rationale — it requires (a) the non-default debug flag to be enabled and (b) local log access, not remote exploitation.

### Likelihood Explanation
Low-to-moderate: `PROTOBUF_DEBUG` is off by default and must be explicitly compiled in via `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII`, exactly analogous to NGINX Agent's non-default trace-level logging precondition. The macro name itself acknowledges the PII-leak risk, indicating this is a known, intentionally-gated tradeoff rather than an unrecognized bug. Exploitation requires an operator/application to have turned this on and an attacker to already have local access to the resulting log files — no memory-safety or remote impact.

### Recommendation
- Ensure `debug_redact`-annotated fields are also redacted when `PROTOBUF_DEBUG` logging paths call `message->DebugString()` in `JsonStreamToMessage`, e.g. by routing through `TextFormat::Printer` configured with `SetRedactDebugString(true)`/`SetReportSensitiveFields` instead of the plain `DebugString()`.
- For the raw-byte tee logging in `JsonToBinaryStream`/`BinaryToJsonStream`/unparser equivalents, avoid hex-dumping the entire input/output; consider truncation, hashing, or gating this even further behind an explicit separate flag distinct from general "-debug" builds.
- Document prominently (in `port_def.inc` and build docs) that `PROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII` must never be enabled in production builds that process sensitive data, consistent with how the CVE's remediation was to avoid trace-level logging in production NGINX Agent deployments.

### Proof of Concept
Conceptual reproduction (not executed in this environment — flagged per instructions):
1. Build protobuf with `-DPROTOBUF_ENABLE_DEBUG_LOGGING_MAY_LEAK_PII=1` (per `cmake/protobuf-module.cmake.in` references) so `PROTOBUF_DEBUG` is `true`.
2. Enable Abseil `DLOG` output (debug build or `ABSL_MIN_LOG_LEVEL`/vlog settings that surface `LOG(INFO)`/`DLOG(INFO)`).
3. Call `google::protobuf::json_internal::JsonToBinaryStream(...)` or `JsonStreamToMessage(...)` with a JSON payload containing a `string`/`bytes` field holding a fake "private key" value.
4. Observe the log output contains lines `json2/input: ...` / `json2/output: ...` with the full hex/plain-text payload, per: [3](#0-2) [4](#0-3) 
This demonstrates the secret value is written to the log sink solely due to the debug flag, with no redaction applied even if the field carries a `debug_redact = true` option, since `DebugString()`/hex-dump paths bypass the safe-debug-format redaction machinery used elsewhere (`text_format.cc` `shouldRedact`/`kFieldValueReplacement`) — verified by inspecting: [5](#0-4) [2](#0-1)
