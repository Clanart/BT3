### Title
Interlocking expiry/policy preconditions permanently blocked `claude auth login`/`logout`/`status` with no recovery path - (File: credential/auth-refresh subsystem, not indexed)

### Summary
The reported veRWA bug class is: a state-transition guard checks a *secondary* object's expiry condition (`toLocked.end > block.timestamp`) before allowing the primary actor to perform the one action needed to escape a bad state (`undelegate`/`withdraw`), and once that secondary condition can never be satisfied, the actor is permanently locked out with no recovery path. The `claude-code--025` changelog documents a directly analogous logic bug: `claude auth login`/`logout`/`status` — the exact commands an unprivileged local user needs to *recover* from a broken credential state — were themselves gated behind a check that could never succeed once triggered.

### Finding Description
Per the changelog entry for v2.1.140: "Fixed a deadlock where expired credentials and the `forceRemoteSettingsRefresh` policy setting blocked `claude auth login`/`logout`/`status` with no way to recover." [1](#0-0)  The `forceRemoteSettingsRefresh` policy setting is documented elsewhere as blocking CLI startup until remote managed settings are freshly fetched, and exiting if the fetch fails (fail-closed): "Added `forceRemoteSettingsRefresh` policy setting: when set, the CLI blocks startup until remote managed settings are freshly fetched, and exits if the fetch fails (fail-closed)" [2](#0-1) .

The structural parallel to the veRWA finding is precise:
- veRWA: `undelegate()` requires `toLocked.end > block.timestamp` on the delegatee's lock — but the delegatee's lock is the user's own, already-expired lock, so the condition is permanently false and the escape action (`delegate`) can never run, which blocks `withdraw()`.
- claude-code: the remote-settings-refresh fetch requires valid credentials to succeed, but credentials are expired — so the fetch permanently fails (fail-closed policy exits the CLI), and the fail-closed exit blocks the very commands (`auth login`/`logout`/`status`) that exist to *fix* expired credentials.

Both are the same root-cause shape: a precondition check that depends on the broken state itself, applied to the recovery/escape-hatch action, with no bypass path once the precondition becomes permanently unsatisfiable.

### Impact Explanation
Any local, unprivileged user of the CLI whose org enabled `forceRemoteSettingsRefresh` and whose local credentials expired would be locked out of the tool entirely — `claude auth login` (the fix path), `logout`, and `status` all failed closed. This is a local denial-of-service / unrecoverable-lockout on the user's own machine requiring a manual workaround (e.g., manually deleting credential files or the policy setting) rather than using the tool's own designed recovery command, directly matching the "permanently locked out, no way to recover through the intended interface" impact class from the source report (there, permanently locked voting-power/tokens; here, a permanently locked CLI session).

### Likelihood Explanation
This required no attacker — it is a self-inflicted trap triggered by the ordinary combination of an admin-set policy (`forceRemoteSettingsRefresh`) and a normal credential-expiry event, which is a common, expected occurrence (tokens expire routinely). The changelog wording ("with no way to recover") confirms this was reliably reproducible in production for any user under that policy configuration, not a rare edge case.

### Recommendation
The general mitigation pattern from the source report applies directly: recovery/escape-hatch actions (here, `auth login`/`logout`/`status`; in veRWA, `delegate`-to-self/`undelegate`) must never be gated behind a precondition that is itself broken by the state the action is meant to fix. Concretely, credential-recovery commands should be exempted from fail-closed policy checks that depend on valid credentials, or the fail-closed check should special-case "no valid credentials to refresh with" as a state that routes to the login flow rather than a hard exit. Anthropic's own fix (v2.1.140) presumably implements exactly this exemption, though the specific code change is not present in the indexed context — a Devin session with full repository access would be needed to review the actual auth/credential-refresh implementation for regressions or residual edge cases (e.g., other fail-closed managed-settings checks that might reintroduce the same trap for a different command).

### Proof of Concept
No PoC can be constructed from indexed content — the underlying `forceRemoteSettingsRefresh`/credential-refresh implementation is not present in the available file index (only the changelog entry describing the historical bug and fix is indexed). This is a documented, already-fixed issue (pre-v2.1.140); reproducing it today would require checking out the pre-fix commit and exercising `claude auth login/logout/status` with an org-level `forceRemoteSettingsRefresh` policy and expired local credentials.
