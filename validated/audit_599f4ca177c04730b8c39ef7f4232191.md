### Title
Missing participant coverage check in `GeneratorPromotion::complete` enables unprivileged panic/DoS - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The TensorFlow bug class — a `CHECK` failure triggered by input tensors whose declared sets don't match what the operator assumes — maps onto `GeneratorPromotion::complete` in `crypto/dkg/promote/src/lib.rs`. The function validates the *count* of the `proofs` map and that every key is `<= n`, but never validates that the map actually contains every required participant `1..=n` (excluding `self`). It then unconditionally unwraps `proofs.get(&i)` for each required index, so an attacker-controlled `proofs` map containing `n - 1` entries that includes an entry keyed under the victim's own participant index (or any duplicate set coverage) reaches an `unwrap()` on `None` and panics.

### Finding Description
`complete` performs exactly two validations on the untrusted `HashMap<Participant, GeneratorProof<C1>>`: [1](#0-0) 

It checks `proofs.len() == n - 1` and `u16::from(i) <= params.n()` for each key. It does **not** check that no key equals `params.i()` (the local participant, whose share comes from `self.proof` at line 139) nor that every required index `1..=n` minus `self` is present. The subsequent loop then unwraps each required entry: [2](#0-1) 

With `n = 3`, `i = 1`, a map `{1: proof_a, 2: proof_b}` (3rd participant's proof replaced by one keyed under the victim's own index) passes both checks: `len() == 2 == n - 1`, and both keys `<= 3`. The loop reaches `i = 3`, `proofs.get(&3)` returns `None`, and `.unwrap()` panics. This is a direct analog of `DenseBincount` trusting a shape/contents invariant it never enforced: the count and bound checks are satisfied while the set membership assumption is violated, converting malformed peer input into a process crash instead of a `PromotionError`.

### Impact Explanation
`GeneratorProof::read` exists precisely to deserialize proofs received from other participants, and `complete` is the entry point consuming all peers' proofs. A single malicious or mislabeled entry in the promotion set aborts the entire key-promotion ceremony by crashing the participant — a denial of service against threshold key maintenance/rotation. If panic = abort or the panic propagates through an FFI/executor boundary, it kills the validator process; otherwise it at minimum aborts the promotion attempt, which a single faulty participant can repeat each round, permanently livelock-freezing generator promotion.

### Likelihood Explanation
Reachability requires that the `proofs` map keys be attacker-influenced — i.e., that the integrator inserts proofs under a participant index carried in or inferred from the peer's message rather than strictly from authenticated sender identity. If a malicious participant can submit a `GeneratorProof` that lands in the map under the victim's own `Participant` index (or the integrator builds the map from a serialized key→proof list via `GeneratorProof::read`), one crafted message triggers the panic deterministically. Unlike the FROST path (`validate_map` in `crypto/frost/src/lib.rs:50` correctly checks per-index membership and returns `MissingParticipant`/`DuplicatedParticipant`), `promote` implements its own incomplete validation, so the gap is real in this crate even though the analogous check exists elsewhere in the codebase. Severity is Medium: availability loss only, no secret leakage or forgery — matching the CVSS A:H/C:N/I:N profile of the reference advisory.

### Recommendation
Replace the count-and-bound checks with a full set-membership validation equivalent to `frost::validate_map`: reject any key equal to `params.i()`, and for each `i in 1..=params.n()` with `i != params.i()`, return `PromotionError::InvalidParticipant` (or a new `MissingParticipant` variant) when `proofs.get(&i)` is `None` instead of unwrapping. Concretely:

```rust
// crypto/dkg/promote/src/lib.rs, in complete()
for i in proofs.keys().copied() {
  if (u16::from(i) > params.n()) || (i == params.i()) {
    Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
  }
}
// then in the loop use .get(&i) with an error return, not .unwrap()
```

### Proof of Concept
```rust
// Victim has params: t = 3, n = 3, i = 1
// Attacker arranges proofs map: { Participant(1): valid_proof, Participant(2): valid_proof }
// len() == 2 == n - 1  => passes IncorrectAmountOfParticipants check
// all keys <= 3        => passes InvalidParticipant check
// Loop: i=1 skipped (self), i=2 OK, i=3 => proofs.get(&3) == None => .unwrap() panics
let mut proofs = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), attacker_proof_a); // keyed under victim's index
proofs.insert(Participant::new(2).unwrap(), attacker_proof_b);
let _ = promotion.complete(&proofs); // panic: unwrap on None at lib.rs:146
```

Note: the PoC assumes the integrator keys the `proofs` map by a participant index supplied alongside the message rather than strictly by authenticated sender identity; if keys are always bound to verified senders, the attacker's index is fixed and the missing slot reduces to the already-handled `len()` mismatch, so the reachable impact in that deployment model is weaker. The defensive fix is still warranted since `complete` accepts the map as a caller-constructed input and makes an undocumented set-coverage assumption.
