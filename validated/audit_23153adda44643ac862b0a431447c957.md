### Title
`ReceivedOutput::read` trusts a stored scalar offset without re-deriving it against the output's `script_pubkey`, so mismatched (stale) offsets produce outputs reported as received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Malt bug class is "value derived from authoritative state once, then trusted later after the state changed" (stale `globalIC` used in `_distributeProfit` because `syncGlobalCollateral` was not called first). The analog in `bitcoin-serai` is the split between derivation and consumption of the per-output scalar offset: `Scanner::scan_transaction` pairs an output with the offset stored when its `script_pubkey` was registered, and `ReceivedOutput::read` deserializes `{offset, output, outpoint}` with no re-derivation of `key + offset*G` against `output.script_pubkey`. A `ReceivedOutput` whose offset is stale/mismatched is accepted as spendable, and the inconsistency is only detected much later — and only as a silent `None` — in `SignableTransaction::multisig`.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` keyed by the P2TR script derived from `key + offset*G` (mod.rs:153-196). `scan_transaction` looks up `output.script_pubkey` and emits `ReceivedOutput { offset, output, outpoint }` trusting that the stored offset is the one that produces the script (mod.rs:199-214). `ReceivedOutput::read` (mod.rs:122-134) accepts attacker-controlled bytes for `offset`, `output` (a `TxOut` including `script_pubkey`), and `outpoint` with zero consistency checks — it never re-derives the script from the offset because the scanner key is not part of the serialized object. The only place consistency is ever checked is `SignableTransaction::multisig` (send.rs:273-285), which re-derives `p2tr_script_buf(offset.group_key())` and returns `None` on mismatch — treated identically to "wrong keys," with no error distinguishing a corrupted/malicious offset.

Concretely: any `ReceivedOutput` obtained via `read` (the explicitly in-scope untrusted-bytes entry point) with `offset` and `output.script_pubkey` that do not correspond is accepted as a received, spendable output. When fed to `SignableTransaction::new`/`multisig`, `multisig` returns `None`, so the funds counted as received cannot actually be spent — the mirror of Malt's incorrect distribution computed from unsynced state.

### Impact Explanation
Funds reported received (via deserialized `ReceivedOutput`s) are not spendable: `SignableTransaction::multisig` aborts with `None` because the stored offset no longer corresponds to the output's `script_pubkey`. Any accounting layer treating deserialized `ReceivedOutput`s as owned value will overstate spendable balance and produce transactions that can never be signed, stranding the associated UTXOs until corrected by re-scanning (the equivalent of Malt's missing `syncGlobalCollateral`).

### Likelihood Explanation
Reachable by an unprivileged party through untrusted bytes fed to `ReceivedOutput::read` — e.g., any peer- or storage-supplied serialization. Constructing a mismatched record requires only choosing an arbitrary scalar and an unrelated `TxOut`; no key knowledge is needed because `read` performs no derivation. The failure is deterministic.

### Recommendation
Bind the offset to the output at validation time. Options: (a) make `ReceivedOutput::read` take the scanner key (or a `&Scanner`) and reject records where `p2tr_script_buf(key + offset*G) != output.script_pubkey`; (b) store only the script and look the offset up in `Scanner::scripts` during `multisig`/`scan` rather than trusting a serialized scalar; (c) at minimum, surface a distinct `TransactionError::InconsistentOutput` from `multisig` instead of conflating mismatch with wrong keys.

### Proof of Concept
In `networks/bitcoin/src/wallet`:

```rust
// Build a ReceivedOutput whose offset does not derive output.script_pubkey.
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());           // arbitrary offset
buf.extend(serialize(&TxOut {                 // output paying to an unrelated script
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new_p2tr_tweaked(
    TweakedPublicKey::dangerous_assume_tweaked(/* unrelated x-only key */)
  ),
}));
buf.extend(serialize(&OutPoint::default()));

let received = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // accepted unconditionally

// accepted as received; not spendable:
let tx = SignableTransaction::new(vec![received], &payments, None, None, fee_rate).unwrap();
assert!(tx.multisig(&keys).is_none()); // stale offset -> silent None, funds unspendable
```

Contrast with `scan_transaction` (mod.rs:205-211), which only emits outputs whose script maps to a registered offset — the invariant `read` fails to enforce for deserialized records, mirroring how `_distributeProfit` used the unsynced `globalIC` deficit instead of re-synced collateral.
