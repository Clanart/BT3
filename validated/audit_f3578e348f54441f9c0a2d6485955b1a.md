### Title
Referral/referee reward accounting in `ReferralStorage` is never backed by an actual MGP transfer, permanently freezing accrued referral yield - ([File: rewards/ReferralStorage.sol])

### Summary
`MasterMagpie._multiClaim` pays out the full MGP harvest to the claiming user and, in addition, calls `ReferralStorage.trigger()` to credit a referrer/referee bonus computed as a percentage of that same harvested amount. `ReferralStorage.trigger()` only increments an internal `rewardAmount` accounting field — no MGP tokens are ever transferred into the `ReferralStorage` contract to back this liability. When a referrer/referee later calls `claimReward()`, `MGP.safeTransfer` will fail (or eventually run out) because the contract never received the underlying tokens.

### Finding Description
In `rewards/MasterMagpie.sol`, `_multiClaim` distributes MGP to the caller via `_sendMGP`, `_sendMGPForVlMGPPool`, or `_sendVlMGPFor` and then unconditionally calls the referral hook with the full reward amount: [1](#0-0) 

That hook lands in `ReferralStorage.trigger`, which is only reachable by `masterMagpie` but is triggered on every ordinary user's `multiclaim`/`multiclaimFor`/`multiclaimOnBehalf`/`multiclaimSpec` call — an unprivileged action. `trigger` computes referrer/referee shares of the harvested `_amount` and simply increments their `rewardAmount` bookkeeping entries: [2](#0-1) 

Crucially, nowhere in this call path (`_multiClaim` → `trigger`) is any MGP token actually transferred into the `ReferralStorage` contract. The only place MGP leaves the accounting system is when a referrer/referee calls `claimReward()`, which attempts a real `safeTransfer` out of `ReferralStorage`'s own balance: [3](#0-2) 

`ReferralStorage.sol` exposes no deposit/fund function reachable by anyone (owner or user) that tops up its MGP balance to match the `rewardAmount` liabilities being accrued by `trigger()`. The full initializer and admin surface of the contract confirms this — `registerCode`, `useCode`, `setTier`, `setSharePercent`, `forceSetCodeOwner`, `setReferrerTier`, `updateTotalFactor` — none of these move MGP into the contract: [4](#0-3) 

This is the same bug class as the Augur report: an internal balance/entitlement (`marketCreatorFeesAttoCash`/affiliate fee in Augur, `rewardAmount` here) is credited to a party's withdrawable balance without the corresponding real token transfer actually happening, so the accounting and the real custody of funds diverge.

### Impact Explanation
Every ordinary user who has been referred and triggers a claim (via `deposit`/`withdraw`/`multiclaim*`) causes the protocol to accrue a `rewardAmount` liability toward the referrer and referee in `ReferralStorage`, but the contract is never funded with the MGP needed to honor it. As soon as any referrer or referee calls `claimReward()`, the `MGP.safeTransfer` call will revert due to insufficient balance (or succeed only for the first few claimants until the (nonexistent/incidental) balance is exhausted), permanently freezing all subsequently accrued referral/referee yield for the rest of users relying on the referral incentive. This is a protocol-wide, unprivileged-path freeze of unclaimed yield, not a one-off edge case.

### Likelihood Explanation
High. This triggers automatically on the ordinary, unprivileged `multiclaim`/`multiclaimFor`/`multiclaim` flow whenever `referral != address(0)` and any user has been referred — no special preconditions, malicious actors, or governance/admin manipulation are required. It is a design/implementation gap that manifests the very first time referral rewards are claimed against an unfunded (or under-funded) `ReferralStorage` balance.

### Recommendation
Mirror the fix applied to the referenced Augur bug: ensure the actual token movement matches the accounting. Specifically, in `MasterMagpie._multiClaim`, transfer the referrer/referee share of MGP into `ReferralStorage` (or mint/approve it there) at the same time `trigger()` is called, rather than only recording it in `rewardAmount`. Alternatively, have `ReferralStorage.trigger` pull the required MGP from `MasterMagpie` via `transferFrom`/`safeTransferFrom` so the credited balance is always fully backed. Add unit/integration tests asserting that `ReferralStorage`'s MGP balance is always >= the sum of outstanding `rewardAmount` entries after any `trigger()` call.

### Proof of Concept
1. Owner sets `referral` to a deployed `ReferralStorage` and configures a nonzero `sharePercent`/tier reward percentage.
2. User B registers a referral code; User A calls `useCode` to link to B.
3. User A stakes and later calls `multiclaim`. `_multiClaim` in `rewards/MasterMagpie.sol` (lines 576-580) sends the full MGP harvest to A and calls `IReferralStorage(referral).trigger(A, totalReward)`.
4. `ReferralStorage.trigger` (lines 173-195) increments `userInfos[B].rewardAmount` and `userInfos[A].rewardAmount` — no MGP is transferred to the `ReferralStorage` contract at this point.
5. User B calls `claimReward()` (lines 158-168). Because `ReferralStorage` was never funded with MGP corresponding to the credited `rewardAmount`, `MGP.safeTransfer(msg.sender, userInfo.rewardAmount)` reverts (or drains whatever incidental balance exists, leaving later claimants unable to withdraw) — demonstrating the permanent freeze of the referral/referee yield.

        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
