## Analysis

The Sherlock finding's core defect is: an operation that extends/updates accumulated state recomputes a value using only the *new* increment and then blindly overwrites the previously-accumulated value, without re-validating that the recomputed value is still consistent with what was actually recorded before.

The equivalent pattern in GitHub Desktop is the `manualResolutions` map used to drive conflict-resolution during multi-step operations (rebase, cherry-pick, squash). This map is keyed **only by file path**, and it is carried forward, unmodified, from one step of the operation to the next — even though each step in a rebase/cherry-pick replays a *different* commit, which can produce a *different* conflict on the *same path*.

### Title
Manual conflict resolutions are silently reapplied to unrelated per-commit conflicts on the same path during rebase/cherry-pick - (File: `app/src/lib/stores/updates/changes-state.ts`, `app/src/lib/git/rebase.ts`, `app/src/lib/git/cherry-pick.ts`)

### Summary
When Desktop performs a multi-commit rebase or cherry-pick and the user resolves a conflict manually (choosing "ours" or "theirs" for a given file path), that decision is stored in a `Map<string, ManualConflictResolution>` keyed purely by path. This map is preserved as-is across subsequent steps of the same operation and is re-applied automatically to any later conflict that happens to touch the same path — even though the later conflict comes from a completely different commit/diff and the user never reviewed it.

### Finding Description
`getConflictState` in [1](#0-0)  constructs the conflict state for the *current* rebase/cherry-pick/merge step using whatever `manualResolutions` map was passed in. `updateConflictState` explicitly carries the previous state's map forward unchanged as long as the operation is still classified as the same kind of conflict (rebase→rebase, merge→merge): [2](#0-1) 

When the user clicks "Continue" on a step, `continueRebase` (and analogously `continueCherryPick`) iterate that same map and, for every path present in it, unconditionally call `stageManualConflictResolution` using the *stored* resolution against whatever file the working directory currently has at that path — with no check that this is the same conflict, same blobs, or same commit that the resolution was originally made for: [3](#0-2) [4](#0-3) 

Since a rebase/cherry-pick onto a repository replays multiple commits sequentially, and the same file path can conflict independently at each step for unrelated reasons, this key-by-path map is the direct analog of the audit finding: a value meant to represent a *specific, reviewed* decision is reused/"overwritten" onto a *new* accumulation state (the next commit's conflict) without recomputation or fresh user validation, because the code trusts the stale keyed entry instead of the current conflict content.

### Impact Explanation
A maliciously crafted repository (the attacker fully controls its commit history, since the fetched/cloned repo is attacker-controlled) can be constructed so that:
1. Commit A conflicts on `path/to/file` with content requiring the user to pick "theirs" to get correct/intended output.
2. Commit B (a later commit in the same rebase/cherry-pick range) also conflicts on the exact same path, but this time "theirs" resolves to attacker-controlled or malicious content (e.g., a modified script, CI config, or dependency manifest) that the user never sees or approves.

Because the resolution map is reapplied per-path automatically, Desktop will silently stage and commit the attacker's version for commit B's conflict using the resolution the user chose for commit A, without prompting review. This is a silent corruption of what the user commits/pushes — meeting the stated valid-impact bar.

### Likelihood Explanation
This requires only: (1) the user rebasing/cherry-picking a range of commits from an attacker-influenced branch/fork (a common workflow, e.g. reviewing a PR or rebasing on top of an updated base with contributor commits), and (2) more than one conflicting commit touching the same file path within that operation — a scenario an attacker crafting the source commits can engineer deliberately. No admin rights, local access, or unnatural steps are needed beyond the normal "resolve conflicts and continue" UI flow.

### Recommendation
Do not key manual conflict resolutions purely by file path across steps. Either:
- Clear/invalidate resolutions for a path once the step advances to a new commit (only reuse if the underlying conflicting blobs/oids for `path` at the new step match those the resolution was made for), or
- Scope `manualResolutions` per commit/step instead of per whole-operation, and force the user to explicitly re-confirm resolutions when the conflict content changes even if the path is identical.

### Proof of Concept
1. Attacker crafts a branch with two commits, A and B, both modifying `config.yml` such that each independently conflicts against the target branch when rebased/cherry-picked in sequence.
2. Victim rebases onto this branch in Desktop. On commit A's conflict, victim picks "Use theirs" (intending to accept commit A's benign values), which is stored as `manualResolutions.set('config.yml', theirs)`.
3. Rebase continues via `continueRebase`, which stages via `stageManualConflictResolution` and moves to commit B.
4. Commit B produces a fresh conflict on `config.yml` with a completely different (malicious) "theirs" content, but because `manualResolutions` in `getConflictState`/`updateConflictState` still contains the prior `path -> theirs` entry, Desktop's next `continueRebase` call ( [3](#0-2) ) reapplies "theirs" to commit B's conflict automatically, without ever showing the new diff to the user, committing the attacker's payload silently.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  // Otherwise we transitioned from a merge conflict to a rebase conflict or
  // vice versa, and we should avoid any side effects here

  return newConflictState
}
