### Title
Keychain user/service cache-key collision causes RPC keychain requests to be served against the wrong keyring partition - (File: chia/daemon/keychain_server.py)

### Summary
`KeychainServer.get_keychain_for_request()` builds the cache key for its `_alt_keychains` map by naively concatenating the `kc_user` and `kc_service` strings from the request with no separator: `key = (user or "unnamed") + (service or "")`. Two distinct `(user, service)` pairs can produce the same concatenated string (e.g. `user="A", service="BC"` and `user="AB", service="C"` both yield `"ABC"`), causing the daemon to hand back a previously cached `Keychain` instance bound to a *different* user/service partition than the one the caller actually requested.

### Finding Description
`KeychainServer` is the daemon-side authority for all keychain RPC commands (`get_key`, `get_keys`, `add_key`, `delete_key_by_fingerprint`, `get_first_private_key`, etc. — see `keychain_commands` and `handle_command()` in `chia/daemon/keychain_server.py`). Every command resolves which `Keychain` object to operate on via: [1](#0-0) 

The comment states the intent explicitly: "user and service strings are used to partition those data stores. We attempt to maintain a mapping of user/service pairs to their corresponding Keychain." The partitioning key on the wire is the pair `(kc_user, kc_service)`, sourced directly from the untyped JSON RPC request dict on `KeychainProxy.format_request()`: [2](#0-1) 

But the in-memory cache key collapses that pair into a single string via bare concatenation with no delimiter, so `(user, service)` and `(user', service')` where `user + service == user' + service'` alias to the same `_alt_keychains[key]` entry. Because `Keychain(user=..., service=...)` in turn determines which underlying keyring namespace (`self.service`, `get_private_key_user(self.user, index)`) is read/written on every key operation: [3](#0-2) 

a collision means a caller supplying one `(kc_user, kc_service)` pair transparently receives (and can mutate — `add_key`, `delete_key_by_fingerprint`, `set_label`, `delete_all_keys`) the keychain partition that was actually created for a different, colliding `(kc_user, kc_service)` pair. This is the same bug class as ALPINE-CVE-2025-30189: a cache keyed on an under-specified/ambiguous composite identity causes cached state (here, an entire keychain instance holding private keys) to be shared across identities that were supposed to be isolated.

### Impact Explanation
Any local daemon RPC caller that can supply arbitrary `kc_user`/`kc_service` values (this field is a plain request dict entry consumed with `request.get("kc_user", ...)`, not validated or length-delimited) can, given a colliding pair, cause the daemon to read from or write to another partition's keychain: exposing another partition's private keys via `get_key`/`get_keys`/`get_first_private_key`/`get_key_for_fingerprint`, or mutating another partition's keys via `add_key`/`delete_key_by_fingerprint`/`delete_all_keys`/`set_label`. Exposure or corruption of another keychain partition's private keys is a direct path to unauthorized signing/spending of that partition's coins, matching the "unauthorized coin movement" impact class required by the validation rules. The `_alt_keychains` map is a long-lived, process-wide daemon cache, so once a colliding key is created for one client it persists and silently answers all subsequent requests using either colliding string.

### Likelihood Explanation
Reaching this code requires only a local RPC call authenticated with the daemon's mutual-TLS client cert (i.e., any local process/service/CLI/GUI that can already talk to the daemon — the same trust tier the codebase treats as a legitimate "local RPC caller"), and does not require any peer, farmer, or operator-only privilege beyond that. The multi-user/multi-service keychain partitioning feature exists specifically to let multiple local network/testing instances or services share one daemon while keeping their keys isolated, so colliding pairs are a realistic occurrence whenever `kc_user`/`kc_service` values are not fixed constants (e.g. testing harnesses, multiple simulated networks, or any caller composing these strings from variable components).

### Recommendation
Use a collision-free composite key for `_alt_keychains`, e.g. a tuple `(user, service)` instead of string concatenation, or join with a delimiter that cannot appear in either component (or hash the length-prefixed pair). Also validate/normalize `kc_user`/`kc_service` inputs before using them as cache/keyring identifiers.

### Proof of Concept
1. Start the daemon and, via two `KeychainProxy`/RPC clients, send `get_key` (or `add_key`) requests with `kc_user="A", kc_service="BC"` for client 1, and `kc_user="AB", kc_service="C"` for client 2.
2. In `KeychainServer.get_keychain_for_request()`, both resolve to `key = "A" + "BC" = "ABC"` and `key = "AB" + "C" = "ABC"` respectively — the same `_alt_keychains["ABC"]` entry.
3. Client 2's first request creates and caches a `Keychain(user="AB", service="C")` under key `"ABC"`.
4. Client 1's subsequent request with `kc_user="A", kc_service="BC"` looks up `_alt_keychains["ABC"]` and receives client 2's `Keychain(user="AB", service="C")` instance, exposing/operating on client 2's keys under client 1's request.

Note: I was not able to find production call sites that currently vary `kc_user`/`kc_service` per request from a single running daemon (most call paths use fixed default constants such as `DEFAULT_USER`/`DEFAULT_SERVICE`), so I could not fully confirm real-world reachability from an unprivileged actor beyond the local-RPC-caller trust tier explicitly named in scope; this should be verified against how `kc_user`/`kc_service` are actually populated across all daemon clients before treating this as exploitable in a default deployment.

```python
    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
```

```python
    def format_request(self, command: str, data: dict[str, Any]) -> WsRpcMessage:
        """
        Overrides DaemonProxy.format_request() to add keychain-specific RPC params
        """
        if data is None:
            data = {}

        if self.keychain_user or self.keychain_service:
            data["kc_user"] = self.keychain_user
            data["kc_service"] = self.keychain_service
```
