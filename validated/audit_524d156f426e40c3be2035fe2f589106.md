### Title
Undersized fee/weight accounting: `calculate_weight_vbytes` omits the OP_RETURN data output, producing an underpaid fee and an oversized transaction — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The analog of the reported "precision loss in a division that mis-sizes a value" bug class maps onto Serai's Bitcoin fee/weight math in `SignableTransaction::new`. The transaction's weight/vsize — which determines both `needed_fee` and the standardness check — is computed over the payment outputs only, even though an OP_RETURN output carrying `data` is appended to `tx_outs` beforehand. Additionally, the min-relay check truncates (`* vbytes / 1000`), lowering the required floor. The result is a signed transaction whose actual fee rate and weight differ from what was validated.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed into `tx_outs` before the weight calculation:

- `networks/bitcoin/src/wallet/send.rs:194-202` appends the data output to `tx_outs`.
- `send.rs:204` then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing only `payments`, never the data output.
- `send.rs:225-226` does the same when a change output exists.

`calculate_weight_vbytes` (send.rs:62-127) builds a scratch `Transaction` solely from `payments` plus an optional change output, so the serialized size of the OP_RETURN output (its 8-byte value, compactsize script length, and up to 83 bytes of script) contributes zero weight units to `weight`/`vbytes`.

Consequences in `new`:

1. `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is computed on the too-small vsize, and `fee_with_change` (send.rs:227) likewise. The actual fee paid (`input_sat - payment_sat - change`) equals `needed_fee`, but the real transaction is larger, so the achieved sat/vbyte rate is below `fee_per_vbyte`.
2. The min-relay guard `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000)` (send.rs:211) compares the underpriced fee against an underestimated vbytes term, and the `/ 1000` truncation further lowers the floor — so a transaction that fails Bitcoin Core's real `DEFAULT_MIN_RELAY_TX_FEE` (1000 sat/kvB) test on its actual size can pass this check.
3. The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (send.rs:241) uses `weight` excluding the OP_RETURN output, so a transaction that exceeds `MAX_STANDARD_TX_WEIGHT` (400,000 WU) once the data output is included is accepted and signed.

The data bytes (`Option<Vec<u8>>`, up to 80 bytes per send.rs:171) and the payment set are caller-supplied public inputs to `SignableTransaction::new`/`TransactionSignMachine::sign`, so this path is reachable by the untrusted bytes fed into the signing pipeline.

### Impact Explanation
Any transaction built with `data` set pays a lower effective fee rate than the caller requested and than the min-relay check intends. In the exact-funding edge case (`input_sat == payment_sat + needed_fee`, or the change-omission path where `input_sat - payment_sat - fee_with_change < DUST`), the realized fee is exactly `needed_fee`, which can sit below Bitcoin's real minimum relay fee for the transaction's true size — the signed transaction will not relay or mine. In the worst case, a transaction sized just under `MAX_STANDARD_TX_WEIGHT` without the data output exceeds the standardness limit once included, making the signed transaction unconditionally non-standard and unspendable without re-signing. This matches the report's class: arithmetic that mis-sizes a real quantity (there, truncated decimal scaling; here, omitted-output weight plus truncated division) causing a financially relevant value to be wrong.

### Likelihood Explanation
Medium likelihood. It triggers deterministically whenever `data` is provided and the input set is tight (little surplus over payments + fee), which is the natural usage pattern for a yield/bridge wallet sweeping exact amounts. It requires no collusion — only that the constructed transaction land near the min-relay or weight boundary, which an unprivileged party choosing payment amounts and data can arrange.

### Recommendation
Include the data output (and generally all of `tx_outs`) in the weight/vsize calculation — e.g., pass the fully constructed `tx_outs` to `calculate_weight_vbytes` instead of `payments`, or add the OP_RETURN output's serialized size to the computed weight. Also round the min-relay fee up (`(fee_rate * vbytes + 999) / 1000`) rather than truncating, and recompute `weight` after all outputs are finalized before comparing against `MAX_STANDARD_TX_WEIGHT`.
