Confirmed: the canonical `evm/src/apps/IntentGatewayV2.sol::placeOrder` protects against fee-on-transfer/deflationary tokens by measuring `balBefore`/`balanceOf` deltas and computing the commitment and escrow credit (`_orders[commitment][token]`) from the **actually received** amount [1](#0-0) , then crediting escrow from that same received-amount-derived `reducedInputs` in Phase 3 [2](#0-1) . The Tron deployment of the identical protocol (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does **not** have this protection: it calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits escrow with `reducedInputs[i].amount` — the fee-adjusted **declared** amount, never checked against the contract's actual token balance [3](#0-2) . The predispatch branch has the same gap for the swap-then-escrow path [4](#0-3) .

### Title
Tron IntentGatewayV2 credits escrow from declared order amounts instead of actually-received token balance, allowing insolvent escrow inflation with fee-on-transfer/deflationary tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The bug-class seed is: a value used for accounting (TVL / share price in the Hyperliquid report) is derived from a party's *declared* transfer amount rather than the actually-settled balance across a boundary (EVM↔L1 there; a token transfer boundary here), creating a mismatch an attacker can exploit for profit or to drain shared pooled funds. The local, provable analog is in the Tron build of `IntentGatewayV2.placeOrder`, where escrow bookkeeping (`_orders[commitment][token]`) is credited using the user-declared `order.inputs[i].amount` (minus protocol fee) rather than the token amount the contract actually received via `safeTransferFrom`. The sibling canonical EVM contract in the same repository explicitly fixes this exact issue by measuring the balance delta before crediting escrow, proving the maintainers recognize this as the correct invariant and that the Tron variant is missing it.

### Finding Description
`placeOrder` in the Tron variant computes `reducedInputs[i].amount = originalAmount - protocolFee` purely from the caller-supplied `order.inputs[i].amount`, then does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [5](#0-4) 

For any ERC-20 with a transfer fee, rebase, or blacklist-style deduction, the contract's real token balance increases by less than `order.inputs[i].amount`, but the internal escrow ledger `_orders[commitment][token]` is credited with the full advertised (fee-reduced but not balance-checked) amount. This is structurally identical to the Hyperliquid bug's broken invariant: **the accounting ledger records value that has not actually landed on this side of a boundary.** Just as HyperliquidEscrow's `tvl()` trusted an assumed balance state that didn't match the real cross-ledger state during the pre-credit window, the Tron IntentGatewayV2 trusts the caller's declared transfer amount instead of verifying the real post-transfer balance.

The predispatch (swap-then-escrow) branch has the identical gap: it checks `balance = IERC20(token).balanceOf(dispatcher)` only against `requiredAmount` (the *original* pre-fee amount) as a floor, then still credits `reducedInputs[i].amount`, again decoupled from any true measurement tied to what was actually escrowed for *this* order versus dust left from calldata execution [4](#0-3) .

`withdraw()` and `_withdraw()` later pay out based on these `_orders[commitment][token]` entries without re-checking real contract balance [6](#0-5) , so the overstated escrow bookkeeping is realized as an actual token transfer at settlement time. Because all orders for a given token share the same pooled contract balance, an overstated commitment for one order can be paid out of tokens that were actually deposited by other users' orders for the same token, causing the last claimants to face insufficient balance (fund loss/lock) — a direct violation of the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivot.

### Impact Explanation
This is a High-impact bug class: it lets an unprivileged user (no relayer, prover, or admin required) create escrow entries that overstate what was actually deposited whenever a non-standard token (fee-on-transfer, deflationary, or one with a variable-fee governance switch) is used as an input asset. Because settlement (`withdraw`/`_withdraw`) pays out of the shared token-balance pool keyed only by commitment, this directly causes loss of other users' or the protocol's escrowed funds once the pool is drawn down beyond what was truly deposited.

### Likelihood Explanation
Medium-to-High: it requires only that an IntentGatewayV2 instance on Tron accept an ERC-20 whose transfer semantics don't guarantee `amount transferred == amount received` (Tron's TRC-20 ecosystem includes such tokens). No privileged actor, relayer collusion, or governance action is needed — a normal user placing an order with such a token triggers the mismatch, and any solver/filler completing settlement realizes the loss on other depositors.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after every `safeTransferFrom` (and after the predispatch dispatcher round-trip) and derive `order.inputs[i].amount`/`reducedInputs[i].amount` — and therefore the commitment hash and the escrow credit — from the *actual received delta*, never from the caller-declared amount. Apply the equivalent fix to the predispatch dust-sweep path so `_orders[commitment][token]` always reflects tokens genuinely held for that specific order.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a TRC-20 token that deducts a 5% fee on every `transfer`/`transferFrom` (fee-on-transfer).
2. User A calls `placeOrder` with `order.inputs[0].amount = 1000` of this token. `safeTransferFrom` moves only 950 tokens into the contract, but `_orders[commitmentA][token] += reducedInputs[0].amount` credits (approximately) 1000 minus protocol fee — i.e., the ledger believes ~995 tokens are escrowed for order A while only 950 actually arrived.
3. User B places a legitimate order with a normal token or the same token, correctly depositing, say, 1000 tokens for order B (`_orders[commitmentB][token] = 1000`, contract balance now 950 + 1000 = 1950, but ledger sum is 995 + 1000 = 1995 — a 45-token shortfall against contract balance).
4. Both orders get filled/withdrawn (`withdraw()` pays `_orders[commitment][token]` from the shared contract balance). Whichever settlement processes first successfully drains its overstated share; the later settlement's `IERC20.transfer` can fail or leave insufficient balance for the rightful beneficiary, causing fund loss/lock for that user while the ledger still claims the funds "exist."
5. No relayer misbehavior, admin action, or malformed proof was required — only placing an order with a non-standard token, which any user can do permissionlessly.
