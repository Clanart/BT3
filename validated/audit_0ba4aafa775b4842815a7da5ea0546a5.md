### Title
Missing slippage protection in `WombatPoolHelperV2.depositFor` enables MEV sandwich attacks on deposits - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor(_amount, _for)` hardcodes `_minimumLiquidity` to `0` when calling `WombatStaking.deposit`, removing any slippage protection on the underlying Wombat pool deposit. Since Wombat's stableswap deposit-to-liquidity conversion depends on the pool's cash/liability coverage ratio, an attacker can manipulate that ratio with a swap immediately before a victim's `depositFor` call and reverse it afterward, extracting value at the expense of the depositor.

### Finding Description
`depositFor` is a fully public, unprivileged function: [1](#0-0) 

It always calls `_deposit(_amount, 0, _for, address(this))`, which forwards `_minimumLiquidity = 0` straight into `WombatStaking.deposit`: [2](#0-1) 

`WombatStaking.deposit` then calls the underlying Wombat pool with that unprotected `_minimumLiquidity` and mints receipt tokens equal to the raw balance difference observed: [3](#0-2) 

The Wombat pool's deposit-to-liquidity conversion (`exactDepositLiquidityInEquilImpl`) is a function of the pool's current cash and liability for the deposited asset, i.e., it is coverage-ratio dependent, as shown in the mock's deposit flow: [4](#0-3) 

This is the exact mechanism Wombat's real stableswap uses in production: depositing when the asset's cash is pushed to a high coverage ratio (via a prior large swap into that asset) yields less liquidity per unit deposited than at equilibrium. Because `_minimumLiquidity` is hardcoded to `0` in this call path, the deposit transaction has zero protection against this manipulation — it will execute at whatever unfavorable rate the pool is in at that block, and `lpReceived` (and thus the receipt/staking tokens minted for `_for`) will be minimized. Note that other paths in the codebase (`WombatPoolHelperV2.deposit`, `depositNative`, and the equivalent functions in `WombatPoolHelper.sol` / `AnkrBNBPoolHelper.sol`) do accept `_minimumLiquidity` as a caller-supplied parameter, so this hardcoding in `depositFor` is an inconsistency that specifically strips protection from this one entrypoint.

Existing modifiers (`nonReentrant`, `whenNotPaused`, `_onlyActivePoolHelper`) do not address this — they guard against reentrancy/pausing/unauthorized helpers, not against price manipulation of the underlying AMM within a single block, which is the classic sandwich vector.

### Impact Explanation
A victim (or a naive integrator) calling `depositFor` receives fewer LP-backed receipt/staking tokens than the fair-value deposit would produce, while an attacker who sandwiches the transaction (swap-in to skew coverage ratio → victim's zero-slippage deposit executes at the skewed rate → attacker swaps back) can extract the difference minus swap fees and gas. This is a direct economic loss of principal for the depositor via MEV, matching the "direct theft of user funds" impact class. It does not break protocol-wide backing/solvency (the receipt token minted still equals the actual LP received by `WombatStaking`), but the depositing user is unambiguously worse off than they should be.

### Likelihood Explanation
The attack requires only a flash-loanable or self-funded amount of the pool's deposit-side asset and standard MEV/front-running capability (mempool visibility, ability to bundle transactions or use a builder). No privileged role is needed — any EOA calling `depositFor` (or observing someone else's `depositFor` call) can perform this. It is repeatable on every `depositFor` call made through this helper, making it a persistent risk rather than a one-off.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (and any other path that currently hardcodes it to `0`) so callers can specify their own slippage tolerance, and enforce that the underlying Wombat pool deposit reverts if `lpReceived` is below that threshold, consistent with how `deposit()` and `depositNative()` already work.

### Proof of Concept
Foundry fork test plan against a live/forked Wombat pool:
1. Deploy/point to real `WombatStaking`, `WombatPoolHelperV2`, and the underlying Wombat `Pool`/`Asset` for a stable pair.
2. Fund attacker with a large amount of the pool's deposit token (or simulate via flash loan) and fund a victim with a modest deposit amount.
3. Attacker swaps a large amount into the pool to push the deposit-asset's coverage ratio to a high (unfavorable-for-depositors) level.
4. Victim calls `WombatPoolHelperV2.depositFor(amount, victim)` in the next transaction (simulating same-block sandwich); record `lpReceived`/staking tokens minted to victim.
5. Attacker swaps back out, restoring the ratio, and records net token/LP gain minus gas and swap fees.
6. Compare victim's minted staking token balance against a baseline (a second run with no sandwich, same amount deposited at equilibrium ratio).
7. Assert: (a) victim's minted balance in the sandwiched run is measurably lower than baseline; (b) attacker's net gain (swap-out proceeds − swap-in cost − fees − gas) is positive, confirming profitable extraction correlated with the victim's loss.
