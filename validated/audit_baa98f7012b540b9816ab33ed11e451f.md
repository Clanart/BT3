## Finding

### Title
IntentGatewayV2 cross-chain settlement redeems escrow using pre-fee `order.inputs` while the source chain escrowed only the post-fee reduced amount, permanently locking user/solver funds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
The reported bug class is: an internal accounting value used to authorize a token payout diverges from the actual token amount held/escrowed for that purpose, so the payout either transfers more than is backed or the bookkeeping decrement underflows/reverts, permanently blocking a legitimate withdrawal. `IntentGatewayV2` reproduces this exact pattern in its cross-chain settlement path: escrow is credited with the *fee-reduced* input amount at `placeOrder`, but the `RedeemEscrow`/`RefundEscrow` message built on fill/cancel carries the *original, pre-fee* `order.inputs` amount, which is what `withdraw()` later uses to decrement `_orders[commitment][token]`.

### Finding Description
At order placement, when `protocolFeeBps` or a per-destination fee is configured, the contract escrows the **reduced** amount, not the order's nominal input amount: [1](#0-0) [2](#0-1) 

This is confirmed directly by the test suite, which asserts escrow storage holds the fee-reduced amount rather than the full order amount: [3](#0-2) 

However, when a solver fills a cross-chain order on the destination chain, the `RedeemEscrow` message dispatched back to the source chain is built from `order.inputs` — the original, **unreduced** amounts — not the reduced amounts that were actually escrowed: [4](#0-3) 

The same pattern repeats for both cancellation paths (`_cancelFromSource` and `_cancelFromDest`), which also populate `WithdrawalRequest.tokens` with `order.inputs` rather than the escrowed (reduced) amount: [5](#0-4) [6](#0-5) 

On the source chain, `onAccept` decodes this `WithdrawalRequest` and calls the internal `withdraw`/`_withdraw` routine, which validates only that the escrow slot is non-zero (`_orders[commitment][token] == 0`), transfers the amount taken from the message body, and only then decrements the escrow accounting by that same (larger) amount: [7](#0-6) 

Because Solidity 0.8's checked arithmetic reverts on underflow, `_orders[commitment][token] -= amount` reverts whenever `amount` (pre-fee `order.inputs[i].amount`) exceeds the actually-escrowed reduced value, rolling back the entire `withdraw()` call — including the token transfer that had just executed in the same call. The transaction as a whole fails.

### Impact Explanation
The destination-chain state (`_filled[commitment] = msg.sender`) is set irrevocably in `_fillCrossChain` **before** the cross-chain message is even dispatched: [8](#0-7) 

Once the order is marked filled on the destination chain, it can never be filled or refunded again there. If the corresponding source-chain `withdraw()` call permanently reverts due to the escrow-accounting mismatch described above, the escrowed input tokens on the source chain become permanently unredeemable: the solver who legitimately filled the order cannot claim the escrow (transaction always reverts), and the user cannot get a refund either (the order is already finalized as filled on the destination chain, and cancellation flows require the destination `_filled` slot to be empty). This is a genuine, protocol-only fund lock — not requiring any admin, governance actor, malicious relayer, or compromised operator.

### Likelihood Explanation
This is triggered by entirely ordinary, unprivileged usage — any order that carries a non-zero `protocolFeeBps` or per-destination fee and is settled cross-chain. No malicious actor is required: a normal solver calling `fillOrder` on the destination chain (or a normal cancellation flow) constructs the `WithdrawalRequest` directly from `order.inputs`, which is a pre-fee amount whenever fees are configured. Any Hyperbridge deployment of `IntentGatewayV2` that sets a nonzero protocol/destination fee for a route is exposed on every cross-chain order using that route.

### Recommendation
Build the `WithdrawalRequest.tokens` field (in `_fillCrossChain`, `_cancelFromSource`, and `_cancelFromDest`) from the same fee-reduced amounts that were actually credited to `_orders[commitment][token]` at `placeOrder` — not from the raw `order.inputs`. Alternatively, have `withdraw()` clamp the transferred/decremented amount to `min(amount, _orders[commitment][token])`, and settle any discrepancy explicitly (e.g., transferring only what is actually escrowed) rather than relying on an implicit revert-on-underflow to catch the mismatch.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps > 0` (or a nonzero destination-specific fee) for the target route.
2. User calls `placeOrder` with `inputs[0].amount = 1000 USDC`; the contract escrows the reduced amount (e.g., `990 USDC`) into `_orders[commitment][USDC]`, per the fee-reduction logic verified by the existing test: [3](#0-2) 
3. Solver calls `fillOrder` on the destination chain; `_fillCrossChain` sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` with `tokens: order.inputs` = `1000 USDC` (the pre-fee amount): [4](#0-3) 
4. On the source chain, `onAccept` → `withdraw()` attempts to transfer `1000 USDC` to the solver and then executes `_orders[commitment][USDC] -= 1000`, but `_orders[commitment][USDC]` only holds `990`, causing an arithmetic underflow revert: [9](#0-8) 
5. The entire settlement transaction reverts every time it is retried. Since `_filled[commitment]` is already permanently set on the destination chain, the order can never be re-filled or cancelled, and the escrowed `990 USDC` on the source chain is locked in the contract indefinitely.

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
