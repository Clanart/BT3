Based on the investigation, the closest verified analog to the reported bug class (attacker-controlled external input silently bypassing a validation invariant that other, similar fields *do* enforce) is in the app's deep-link/custom-protocol parser.

### Title
Deep-link `filepath` parameter is never sanitized before being used as a post-clone file path - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` handles the `x-github-client://openRepo/...` (and legacy `github-mac://openRepo/...`) deep link that GitHub.com's "Open in Desktop" button emits. It extracts `branch`, `pr`, and `filepath` query parameters and returns them in an `IOpenRepositoryFromURLAction`, whose `filepath` is documented as "the file to open after cloning the repository". Every other user-influenced field in this action is validated before being trusted — `branch` is checked with `testForInvalidChars` and `pr` is checked against `/^\d+$/` — but `filepath` is passed straight through unchecked.

### Finding Description [1](#0-0) 

Compare the treatment of the three query parameters inside the `openrepo` branch: `pr` is regex-validated, `branch` is passed to `testForInvalidChars`, but `filepath` is returned as-is with no validation of its shape (no traversal check, no null-byte check, no anchoring). This mirrors the pattern in the underlying report: a value that is supposed to be constrained to "inside the destination object" (there: the new strategy contract; here: the cloned repository directory) is carried through a migration/derivation step (there: `_connector_migrateToNewStrategy`; here: `parseAppURL` → whatever consumes `IOpenRepositoryFromURLAction.filepath`) without an invariant check that a sibling field in the same struct does enforce.

The codebase clearly has the primitives to prevent path escapes — `resolveWithin` in `app/src/lib/path.ts` explicitly guards against `..` traversal and symlink escapes and is exercised in `app/test/unit/path-test.ts`, and `sanitizeCloneName`/`isClonePathSensitive` in `app/src/lib/remote-parsing.ts` and `app/src/lib/git/clone.ts` guard the clone destination path against traversal. `filepath`, however, is not passed through `resolveWithin` (or any equivalent) at the point it is parsed, so if the consumer that later opens the file (referenced from `app/src/ui/dispatcher/dispatcher.ts`, which has matches for `filepath` but whose exact join/open call I was not able to fully inspect before the tool budget ran out) simply does `Path.join(repository.path, filepath)`, a value like `../../../../.ssh/id_rsa` or an absolute path would escape the freshly cloned repository directory.

### Impact Explanation
If the consuming code joins `filepath` onto the repository path without an anchoring check (as `clone.ts` and `remote-parsing.ts` do for the clone destination itself), a link crafted by an attacker (e.g., a malicious "Open in Desktop" button on a webpage, or a GitHub-hosted repo whose README/PR uses this URL scheme) could cause Desktop to open/read a file outside the intended repository directory once the user clicks it — matching the "link the user clicks... read outside the repo" impact category from the task's valid-impact list.

### Likelihood Explanation
Medium-to-low confidence: the click-through requirement (user must click a specially crafted `x-github-client://openRepo/...` link) is a normal, expected Desktop workflow (this is exactly how "Open in Desktop" buttons work on third-party sites), so no unnatural steps are required. However, I could not fully confirm within the available tool budget that the downstream file-open call actually joins `filepath` unsafely rather than sanitizing it separately — the `dispatcher.ts` references to `filepath` were located but not fully read before the iteration budget was exhausted. This is the main open uncertainty.

### Recommendation
Apply the same discipline already used for `branch`/`pr` and for the clone destination path: validate `filepath` in `parseAppURL` (reject values containing `..`, absolute-path prefixes, or null bytes) and/or route the final open call through `resolveWithin(repository.path, filepath)` before touching the filesystem, exactly as `clone.ts`'s `isClonePathSensitive` and `path.ts`'s `resolveWithin` already do for other user/attacker-influenced paths.

### Proof of Concept
1. Attacker publishes a page (or a GitHub repo README) with a link: `x-github-client://openRepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F..%2F.ssh%2Fid_rsa`.
2. Victim, who has Desktop registered as the protocol handler (default after any install, per `app/src/main-process/main.ts` lines 105-116 registering `x-github-client`), clicks the link.
3. `parseAppURL` (app/src/lib/parse-app-url.ts:98-124) returns `{ name: 'open-repository-from-url', url, branch, pr, filepath: '../../../../.ssh/id_rsa' }` with no rejection.
4. If the downstream handler naively joins this with the newly cloned repository path to "open the file after cloning" (as documented in the type's own comment), the file opened/read is outside the repository — this could not be fully re-verified against the exact `dispatcher.ts` sink within the remaining tool budget, so this PoC step is the unverified link in the chain and should be confirmed by a follow-up session that reads `app/src/ui/dispatcher/dispatcher.ts`'s `filepath` handling in full.

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
