### Title
Escrow release in Tron `IntentGatewayV2.withdraw()` sends native tokens before decrementing escrow accounting, violating checks-effects-interactions with no reentrancy guard - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements escrow release (`withdraw()`) with the external value transfer to an attacker-controlled `beneficiary` occurring *before* the corresponding `_orders[commitment][token]` escrow-accounting decrement, and with no `ReentrancyGuard` anywhere in the contract. This is the exact checks-effects-interactions ("check-then-act") ordering bug described in the seed report (act on external effect before persisting the state that prevents re-use), and the repository's own test suite documents that this precise class of bug was found and fixed in the primary EVM intents contracts but the fix was evidently not carried over to the Tron contract.

### Finding Description
`withdraw()` [1](#0-0)  is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` settlement message is delivered [2](#0-1) , and from `onGetResponse()` on cancellation [3](#0-2) .

Inside the per-token loop:
```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
    ...
}
_orders[body.commitment][token] -= amount;                // state updated AFTER
``` [4](#0-3) 

The `beneficiary` address is attacker-controlled: it is set to `msg.sender` of whoever calls `fillOrder`/cancels the order on the destination chain, and is carried unauthenticated (as data) inside `WithdrawalRequest.beneficiary` through the cross-chain message. When the escrowed asset is the native token, the low-level `.call{value: amount}("")` invokes arbitrary code at `beneficiary` *before* the escrow ledger is decremented and before `_filled[body.commitment]` accounting fully completes (it is set at line 684, but the per-token loop's un-decremented balance is the exploitable state). No `nonReentrant` modifier exists anywhere in this contract, unlike the guard pattern the project's own reentrancy regression test suite documents as the fix for this identical bug class.

Contrast this with the already-patched, checks-effects-interactions-compliant version used on the primary EVM contracts, where the escrow map is decremented *before* the external call:
```
_orders[body.commitment][token] = escrowed - amount;   // effects BEFORE interaction
if (token == address(0)) { beneficiary.call{value: amount}(""); ... }
else { IERC20(token).safeTransfer(beneficiary, amount); }
``` [5](#0-4) 

The project's own dedicated regression test explicitly documents that this ordering bug previously existed and was fixed by moving `_filled[...] = msg.sender` and the balance decrement to before the outbound calls, specifically to stop a malicious beneficiary from reentering and stealing funds: [6](#0-5) 

That fix was applied to `IntentsBase.sol`/`ExtrinsicIntents.sol`/`IntrinsicIntents.sol` but the Tron-specific contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` still contains the pre-fix ordering, uses raw `.call()` instead of `SafeERC20.safeTransfer`, and has no reentrancy guard.

### Impact Explanation
If the escrow contains a native-token input, a malicious solver can set the release `beneficiary` to a contract they control, fill (or cancel) the order, and have that contract's `receive()`/fallback fire mid-`withdraw()`, before `_orders[commitment][address(0)]` is decremented. Depending on what other state-mutating entry points remain reachable from that reentrant context on this Tron deployment (e.g., other escrow-accounting functions or a second token/fee branch in the same `withdraw()` call being triggered again through any callable path before the ledger update lands), the escrow balance can be drained beyond the amount actually owed — i.e., loss/theft of bridged funds, matching the "stealing or loss of funds" / "double-settlement" impact classes in scope. This is High impact because it directly threatens custody of bridged assets.

### Likelihood Explanation
Medium: exploitation requires the escrow to include native token, the malicious beneficiary contract to be reachable from `withdraw()`'s external call and to have some further callable state-mutating surface to exploit before the ledger decrement lands, and depends on the Tron contract's actual deployment status/parity with the audited EVM version (which the docs suggest is a real, separate deployment path — `evm/tron/contracts/apps/IntentGatewayV2.sol`). This is an unprivileged-attacker path (any solver/filler can pick their own beneficiary) requiring no relayer, prover, or admin cooperation. I could not fully confirm every downstream reentrant call target given tool-call limits, so treat the exact drain mechanics as partially unconfirmed pending deeper review, but the CEI-ordering defect itself and the missing guard are directly verified.

### Recommendation
- Apply the same checks-effects-interactions fix already used in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron contract: decrement `_orders[body.commitment][token]` (and set `_filled`/other idempotency markers) before performing any external call or token transfer.
- Add a `nonReentrant` guard (OpenZeppelin `ReentrancyGuard`) to `onAccept`, `onGetResponse`, and `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
- Replace raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with `SafeERC20.safeTransfer`, consistent with the rest of the codebase.
- Add a regression test mirroring `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` for the Tron contract to lock in the fix.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with a `receive()` that, upon receiving native tokens from `IntentGatewayV2.withdraw`, attempts to re-enter any reachable state-mutating function on the same contract (e.g., another escrow-adjacent call) while `_orders[commitment][address(0)]` still reflects the pre-withdrawal balance.
2. Attacker (as solver) calls `fillOrder(order, options)` on the destination chain for a cross-chain order whose `order.inputs` includes a native-token entry, setting `beneficiary = MaliciousBeneficiary` (`beneficiary: bytes32(uint256(uint160(msg.sender)))`) — see `_fillOrder`/`fillOrder` beneficiary assignment pattern shared across the intents contracts [7](#0-6) .
3. When the `RedeemEscrow` settlement message is delivered on the source (Tron) chain, `onAccept` → `withdraw` executes the native-token branch: `beneficiary.call{value: amount}("")` fires before `_orders[body.commitment][token] -= amount` [8](#0-7) .
4. `MaliciousBeneficiary.receive()` executes attacker logic while the escrow ledger for that commitment/token is still un-decremented, enabling re-use of stale escrow state to extract more value than owed, before the loop's final `-= amount` takes effect.

I was not able to fully trace, within the remaining tool budget, every possible reentrant target reachable from step 4 on the live Tron deployment; this should be verified with a Foundry/Tron-fork PoC analogous to `IntrinsicIntentsReentrancyTest.sol` before remediation is scoped.
