### Title
Checks-Effects-Interactions violation in `CW1155ERC1155Pointer.safeTransferFrom`/`safeBatchTransferFrom` enables reentrancy after CosmWasm state effect - (File: contracts/src/CW1155ERC1155Pointer.sol)

### Summary
The Sherlock report flags `BalancedVault.redeem` for mutating accounting state before the state-changing `_burn` call, so a revert inside `_burn` leaves inconsistent bookkeeping. The closest reachable, high-severity analog in sei-chain is the reverse ordering problem (effects-before-interaction) in the CW1155 EVM pointer contract: the pointer performs the actual CosmWasm ownership transfer (`_execute`, which calls the wasmd precompile and mutates the underlying CW1155 contract's state) *before* invoking the external, attacker-controlled `onERC1155Received`/`onERC1155BatchReceived` callback on `to`.

### Finding Description
`safeTransferFrom` in `contracts/src/CW1155ERC1155Pointer.sol`: [1](#0-0) 

performs the sequence: (1) `require(balanceOf(from,id) >= amount)` read, (2) `_execute(...)` which delegatecalls the wasmd precompile and commits the CW1155 `send` message (the actual ownership/balance change), and only then (3) calls `IERC1155Receiver(to).onERC1155Received(...)` if `to` is a contract. The same effects-before-interaction pattern exists in `safeBatchTransferFrom`: [2](#0-1) 

This is the mirror image of the audited bug class ("state updated before a call that can revert/reenter"): here the state-mutating CosmWasm `_execute` call happens *before* the external call to an untrusted receiver contract, so any attacker-supplied `to` contract gets control of execution while the pointer has already recorded the transfer as complete on-chain (in the CW1155 module). This is a classic reentrancy vector — the callback can re-enter the pointer (or any other contract that trusts the pointer's `balanceOf`/`ownerOf` view, e.g. a marketplace or lending contract built on top of the pointer) while the caller's original transaction is still unwound, using the now-updated balance/ownership state to perform actions (further transfers, approvals, listings, etc.) that the caller did not intend to be composable with the still-in-flight first transfer.

The `burn`/`burnBatch` functions of the same contract also read balance via a separate `query` call to the wasmd precompile and then perform a second, independent `execute` call: [3](#0-2) 
Because the "check" (`balanceOf` query) and the "effect" (`_execute` burn) are two independent precompile calls rather than one atomic operation, any reentrant call sandwiched between them (triggered from a prior `safeTransferFrom`'s receiver hook in the same transaction) operates on a state snapshot that may no longer match what was checked.

### Impact Explanation
An attacker who controls the `to` address in `safeTransferFrom`/`safeBatchTransferFrom` gains code execution after the CW1155 token has already changed ownership. This allows reentrant calls into the pointer contract (or any external contract depending on the pointer's token accounting) while the outer transfer is not yet finished, which can be leveraged to manipulate approvals, drain other tokens the attacker was already approved for, or interfere with any protocol built on top of the pointer that assumes non-reentrant, atomic transfer semantics. Because this affects any CW1155-backed pointer, and pointer contracts are a core, unprivileged, publicly reachable EVM<->CW bridge mechanism in sei-chain, a successful exploit can lead to unauthorized transfer/loss of pointer-wrapped CW1155 assets, satisfying the "unauthorized transfer via precompile or pointer" impact criterion.

### Likelihood Explanation
Likelihood is High: any unprivileged EVM account can deploy a malicious contract implementing `IERC1155Receiver`, receive a CW1155 pointer transfer from an unsuspecting counterparty (or from itself in a multi-step exploit contract), and reenter during `onERC1155Received`. No special privileges, governance, or validator behavior are required — only a standard `safeTransferFrom` call from a normal EVM transaction sender.

### Recommendation
Apply checks-effects-interactions ordering and/or a reentrancy guard to `CW1155ERC1155Pointer` (and the analogous `CW721ERC721Pointer`/`CW20ERC20Pointer` transfer paths that call `_execute` against the wasmd precompile):
- Add a `nonReentrant` modifier to `safeTransferFrom`, `safeBatchTransferFrom`, `burn`, and `burnBatch`.
- Where possible, perform the balance "check" and the state "effect" (`_execute`) as a single atomic CosmWasm message rather than a separate `query` followed by `execute`, to avoid any window where reentrant calls can observe a stale check.
- Consider moving the external `IERC1155Receiver` callback ordering guidance from OpenZeppelin's ERC1155 reference implementation, which already assumes internal balances are updated in the same atomic Solidity storage write (making reentrancy safe by invariant); since this pointer instead crosses into a separate CosmWasm state machine via the precompile, add an explicit reentrancy lock to compensate.

### Proof of Concept
1. Attacker deploys `MaliciousReceiver` implementing `onERC1155Received` that, upon being called, re-enters the `CW1155ERC1155Pointer` contract (e.g., calling `safeTransferFrom` again using an approval it holds, or calling `burn` on a token it does not fully own yet in the caller's view).
2. Attacker (or victim, via a crafted approval) calls `pointer.safeTransferFrom(victim, MaliciousReceiver, tokenId, amount, data)`.
3. Inside `safeTransferFrom`, the CW1155 `send` execute message commits the ownership change in the wasm module immediately (step at `contracts/src/CW1155ERC1155Pointer.sol:63`).
4. `to.code.length > 0` triggers `IERC1155Receiver(to).onERC1155Received(...)` (`contracts/src/CW1155ERC1155Pointer.sol:64-75`), handing control to `MaliciousReceiver` while the outer call is still on the stack.
5. `MaliciousReceiver` reenters the pointer (or a dependent protocol contract) and performs additional state-changing calls based on the already-updated CW1155 balance, before the original `safeTransferFrom` call returns — breaking any invariant that depended on transfer atomicity.

Note: I was not able to fully verify at what layer (EVM call frame vs. underlying Cosmos `CacheMultiStore`) a revert inside `_execute`'s delegatecall would be rolled back relative to the wasmd precompile's committed state, since that requires deeper inspection of the wasmd precompile's Go implementation, which was not part of the indexed context retrieved. This does not affect the reentrancy finding above, which does not depend on revert semantics.

    function safeTransferFrom(
        address from,
        address to,
        uint256 id,
        uint256 amount,
        bytes memory data
    ) public override {
        require(to != address(0), "ERC1155: transfer to the zero address");
        require(balanceOf(from, id) >= amount, "ERC1155: insufficient balance for transfer");
        require(
            msg.sender == from || isApprovedForAll(from, msg.sender),
            "ERC1155: caller is not approved to transfer"
        );
    
        string memory f = _formatPayload("from", _doubleQuotes(AddrPrecompile.getSeiAddr(from)));
        string memory t = _formatPayload("to", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(id)));
        string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount)));

        string memory req = _curlyBrace(
            _formatPayload("send", _curlyBrace(_join(f, ",", _join(t, ",", _join(tId, ",", amt)))))
        );
        _execute(bytes(req));
        if (to.code.length > 0) {
            require(
                IERC1155Receiver(to).onERC1155Received(
                    msg.sender,
                    from,
                    id,
                    amount,
                    data
                ) == IERC1155Receiver.onERC1155Received.selector,
                "unsafe transfer"
            );
        }
    }

    function safeBatchTransferFrom(
        address from,
        address to,
        uint256[] memory ids,
        uint256[] memory amounts,
        bytes memory data
    ) public override {
        require(to != address(0), "ERC1155: transfer to the zero address");
        require(
            msg.sender == from || isApprovedForAll(from, msg.sender),
            "ERC1155: caller is not approved to transfer"
        );
        require(ids.length == amounts.length, "ERC1155: ids and amounts length mismatch");
        address[] memory batchFrom = new address[](ids.length);
        for (uint256 i = 0; i < ids.length; i++) {
            batchFrom[i] = from;
        }
        uint256[] memory balances = balanceOfBatch(batchFrom, ids);
        for (uint256 i = 0; i < balances.length; i++) {
            require(balances[i] >= amounts[i], "ERC1155: insufficient balance for transfer");
        }

        string memory payload = string.concat("{\"send_batch\":{\"from\":\"", AddrPrecompile.getSeiAddr(from));
        payload = string.concat(payload, "\",\"to\":\"");
        payload = string.concat(payload, AddrPrecompile.getSeiAddr(to));
        payload = string.concat(payload, "\",\"batch\":[");
        for (uint256 i = 0; i < ids.length; i++) {
            string memory batch = string.concat("{\"token_id\":\"", Strings.toString(ids[i]));
            batch = string.concat(batch, "\",\"amount\":\"");
            batch = string.concat(batch, Strings.toString(amounts[i]));
            if (i < ids.length - 1) {
                batch = string.concat(batch, "\"},");
            } else {
                batch = string.concat(batch, "\"}");
            }
            payload = string.concat(payload, batch);
        }
        payload = string.concat(payload, "]}}");
        _execute(bytes(payload));
        if (to.code.length > 0) {
            require(
                IERC1155Receiver(to).onERC1155BatchReceived(
                    msg.sender,
                    from,
                    ids,
                    amounts,
                    data
                ) == IERC1155Receiver.onERC1155BatchReceived.selector,
                "unsafe transfer"
            );
        }
    }
