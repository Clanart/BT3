### Title
Authentication Bypass by Assumed-Immutable EVM↔Sei Address Mapping via EIP-7702 SetCode + associatePubKey Remap - ([File: x/evm/ante/preprocess.go])

### Summary
The Sei EVM↔Sei address association (`SetAddressMapping`) is treated by staking/distribution and other modules as an immutable identity binding, but it is not actually immutable: a `sdk.AccAddress` can first receive a "direct-cast" mapping (address bytes reinterpreted between EVM and Cosmos formats) via an EIP-7702 `SetCode` authorization, accumulate protocol state (e.g. become a validator operator/delegator) under that direct-cast identity, and later have the *same* EVM address remapped to a *different*, pubkey-derived Sei address via the `associate`/`associatePubKey` precompile calls or an `AssociateTx`. The remap silently orphans state tied to the old direct-cast identity. The code's own inline comment in `x/evm/ante/preprocess.go` acknowledges this exact class of bug and describes only a partial, "best-effort" mitigation.

### Finding Description
`SetAddressMapping` unconditionally overwrites both the forward and reverse KV entries for an EVM↔Sei pair with no check that the *target* EVM address was previously bound to different protocol state: [1](#0-0) 

The precompile `associateAddresses`/`AssociateAddresses` helper only guards against re-associating a Sei address that already has an association (`GetEVMAddress(ctx, seiAddr)`); it never checks whether the target EVM address already has an existing, meaningful reverse mapping (`GetSeiAddress(ctx, evmAddr)`) before calling `SetAddressMapping`: [2](#0-1) [3](#0-2) 

The EVM ante pipeline's own comment explicitly documents the hazard: an EIP-7702 `SetCode` authorization can install delegation code for an authority account before that authority has a "true" pubkey-derived Sei address, creating a *mutable* direct-cast EVM→Sei mapping. A later `associatePubKey` call by the real key owner remaps that identity, "orphaning any staking/distribution state created under the direct-cast identity (which can then halt the chain via the distribution validator-removal hook)": [4](#0-3) 

The mitigation added (`associateAuthorizationAuthorities`) pre-associates each `SetCode` authorization's true signer to its pubkey-derived Sei address *before* the delegation code is installed, but by its own documentation this is only **best-effort**: authorities with authorizations that don't match current chain id/nonce/account state are skipped (`AuthorityToPreAssociate` returns `!ok`), and a per-authority association failure silently skips that authority rather than aborting the transaction: [5](#0-4) 

Because pre-association is skipped whenever the authorization's nonce/state doesn't match "now" (by design, to mirror what EVM execution will/won't apply), and because EVM execution's own nonce/state checks happen later, there remains a window in which a direct-cast mapping is created by `SetCode` for an address that never got pre-associated, then later gets remapped by a legitimate `associate`/`associatePubKey` call — at which point any staking/distribution/other module state that was created against the old direct-cast `sdk.AccAddress` becomes orphaned, since only the EVM↔Sei bidirectional pointer is updated; no staking/distribution state migration occurs.

### Impact Explanation
If a direct-cast identity accumulates staking-module state (e.g., becomes a delegator or validator operator address, given `CanAddressReceive`/`SetAddressMapping` allow such an address to hold funds and be a valid `sdk.AccAddress` signer) and is later remapped, the module keeps referencing an address whose EVM↔Sei mapping has changed identity underneath it. The preprocess.go comment states this orphaning "can halt the chain via the distribution validator-removal hook," i.e., a validator-halt / chain-halt class impact, which meets the bug bounty's accepted impact criteria (validator halt / permanent chain split). It could also result in stuck/frozen funds or state permanently tied to an address that no longer round-trips consistently between the two address spaces.

### Likelihood Explanation
Exploitation requires crafting an EIP-7702 `SetCodeTx` whose authorization is deliberately shaped so `AuthorityToPreAssociate` skips pre-association (e.g. nonce/chain-id mismatch relative to current state, or account state such that the "best-effort" check declines to run) while EVM execution still ends up installing delegation code for that authority address, followed by staking/delegation actions against the resulting direct-cast `sdk.AccAddress`, and finally a normal `associatePubKey`/`associate` call by the real key owner. This is reachable purely through public JSON-RPC/EVM transaction submission (no privileged access needed), but requires precise sequencing across multiple transactions/blocks and exact knowledge of the `AuthorityToPreAssociate` skip conditions, which were not fully enumerable from the available code (the exact matching logic of `AuthorityToPreAssociate` in `utils/helpers/address.go` could not be inspected in this session). This uncertainty limits confidence in a fully reproducible, self-contained PoC.

### Recommendation
- Make the EVM↔Sei address mapping immutable for any Sei address once it holds non-trivial protocol state (staking delegations/validator bonding, distribution positions, etc.) rather than only checking `GetEVMAddress(seiAddr)`.
- In `associateAddresses`/`AssociateAddresses`, also reject association if `GetSeiAddress(ctx, evmAddr)` already resolves to a *different* Sei address that has non-zero staking/distribution state, or migrate/carry forward that state atomically as part of the remap.
- Remove the "best-effort" carve-outs in `associateAuthorizationAuthorities`: either reject `SetCodeTx`s whose authorizations cannot be safely pre-associated, or defer delegation-code installation until pre-association unconditionally succeeds.
- Add invariant checks / simulation tests that a validator-removal or delegation-slashing path cannot panic/halt when the underlying `sdk.AccAddress` identity has been remapped mid-life.

### Proof of Concept
A complete deterministic PoC could not be constructed without access to the exact skip conditions inside `AuthorityToPreAssociate` (`utils/helpers/address.go`), which was not retrievable in this session. Conceptually:
1. Submit an EIP-7702 `SetCodeTx` with an authorization for authority `A` shaped so `helpers.AuthorityToPreAssociate` returns `ok=false` (per its documented chain-id/nonce/account-state matching rules) while go-ethereum's own EVM execution still applies the authorization and installs delegation code for `A`, causing `SetAddressMapping` to create a direct-cast mapping for `A` (via `EVMAddressDecorator`/keeper logic elsewhere in the EVM execution path).
2. Cause `A`'s direct-cast `sdk.AccAddress` to accumulate staking-module state (e.g., delegate to a validator, or become a validator operator address if permitted).
3. Have the true key owner of `A` call `addr.associatePubKey`/`addr.associate` (precompile `0x1004`), which passes the `GetEVMAddress(seiAddr)`-only check in `associateAddresses` and calls `SetAddressMapping` to rebind `A` to a new, pubkey-derived Sei address, orphaning the staking state tied to the old direct-cast address.
4. Trigger validator set changes/slashing that hit the distribution validator-removal hook against the now-orphaned identity, per the risk explicitly called out in `x/evm/ante/preprocess.go` lines 103-109. [6](#0-5)

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))

		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)

	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

// associateAuthorizationAuthorities associates every EIP-7702 authorization authority in
// the transaction with its true (pubkey-derived) Sei address, so that a subsequent
// SetCode for the authority does not create a mutable direct-cast mapping. It is
// best-effort: authorities with invalid signatures (which EVM execution would also skip)
// or that are already associated are left untouched, and an association failure skips
// only that authority rather than rejecting the transaction, which go-ethereum would
// still accept.
func (p *EVMPreprocessDecorator) associateAuthorizationAuthorities(ctx sdk.Context, msg *evmtypes.MsgEVMTransaction, associateHelper *helpers.AssociationHelper) {
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return
	}
	setCodeTx, ok := txData.(*ethtx.SetCodeTx)
	if !ok {
		// Only SetCode (EIP-7702) transactions carry authorizations.
		return
	}
	ethTx := ethtypes.NewTx(setCodeTx.AsEthereumData())
	for _, auth := range ethTx.SetCodeAuthorizations() {
		// Only pre-associate authorities whose authorization the EVM will actually apply
		// (matching chain id, nonce, and account state). This prevents replaying a
		// publicly-visible authorization a user signed for another chain to force-associate
		// them, which the EVM would skip but which still recovers a valid authority.
		evmAddr, seiAddr, pubkey, ok := helpers.AuthorityToPreAssociate(ctx, p.evmKeeper, auth)
		if !ok {
			continue
		}
		cacheCtx, write := ctx.CacheContext()
		if err := associateHelper.AssociateAddresses(cacheCtx, seiAddr, evmAddr, pubkey, false); err == nil {
			write()
		}
	}
}
