### Title
Guest-controlled panic in BIP-340 FROST signing when the bound aggregate nonce sums to the point at infinity - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Wasmtime advisory (GHSA-m758-wjhj-p3jq) is a panic triggered when malformed input carries bit patterns outside an expected set during value lifting — i.e., an attacker-controlled value reaching a code path that assumes an invariant and panics rather than erroring. The analog in Serai's in-scope code is the BIP-340 `Hram`/`x`/`x_only` helpers in `networks/bitcoin/src/crypto.rs`, which `expect` that `R` and `A` are non-infinity `ProjectivePoint`s. During FROST `complete`/`verify`, the aggregate nonce `R` is an attacker-influenced linear combination of per-participant preprocess commitments; if a malicious participant drives that combination to the point at infinity, `x(R)` panics on `expect("point at infinity")`, a guest-controlled panic inside the host signer — precisely the same DoS shape as the Wasmtime bug (input violates an assumed-non-attainable invariant → panic instead of `Err`).

### Finding Description
`x()` at `networks/bitcoin/src/crypto.rs:13-16` extracts the x-coordinate of a point via `to_encoded_point(true).x().expect("point at infinity")`, and `x_only` at line 21-23 similarly panics. `Hram::hram` at lines 59-73 calls `x(R)` and `x(A)`, and the code documents that an infinity `R` or `A` panics (lines 52-54, 78-83). `Schnorr::verify` (lines 139-150) is invoked from `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs:465` with `nonces = self.Rs`, where `Rs` come from `B.nonces(&nonces)` — the per-generator sums `Σ (D_l + ρ_l·E_l)` over all participants' preprocess commitments (`crypto/frost/src/sign.rs:383`, `crypto/frost/src/nonce.rs:44-96`).

Individual commitments pass through `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`), which rejects identity points — but nothing rejects a *sum* of valid non-identity bound commitments being identity. There is no check on `Rs` between `B.nonces()` and `algorithm.verify(...)`, and no `Option`/`Result` path: the panic is unrecoverable and aborts the signing task (and, depending on the host, the process).

### Impact Explanation
A malicious signing participant (or an unprivileged party able to submit preprocess messages into a signing session, e.g., via a parallel-session/ROS-style setup where they observe honest preprocesses before finalizing their own) can crash the signer/coordinator mid-`complete`. Per Serai's own model — mirrored exactly by the Wasmtime advisory — a guest-controlled panic in the host is a DoS vector. It halts signature production for the whole multisig session; repeated triggers across sessions create a persistent liveness failure for the threshold group.

### Likelihood Explanation
Forcing `R = Σ(D_l + ρ_l·E_l)` to identity requires solving a hash fixpoint (the attacker's binding factor `ρ_l` itself depends on their commitments), which is infeasible in a single session. However, the FROST binding-factor construction here (`FROST_rho` transcript over `group_key`, `hash_msg`, and the `preprocesses` challenge, `crypto/frost/src/sign.rs:362-371`) is the standard scheme known to be vulnerable to ROS/Wagner-style attacks across parallel sessions: with enough concurrent signing sessions a malicious participant can select preprocess commitments so the bound nonce sums to a chosen point — including identity — with polynomial work. This is a recognized feasibility class for FROST, and the code itself acknowledges the panic is reachable "even with malicious participants present" only at negligible probability for well-reasoned callers — a claim that does not hold once the attacker manipulates the aggregate rather than relying on chance. Likelihood is therefore moderate-to-low but non-negligible; severity is a clean Medium DoS.

(Residual uncertainty: I verified the panic site and the absence of an identity check on `Rs`, but did not exhaustively trace `B.nonces`/`BindingFactor::calculate_binding_factors` internals; the analog stands on the documented panic plus the attacker-controlled aggregate.)

### Recommendation
- In `crypto/frost/src/sign.rs`, after computing `Rs = B.nonces(&nonces)`, reject any `R` that `is_identity()` and return `FrostError` (e.g., `InvalidSigningSet`/`InternalError`) instead of letting it reach `verify`.
- Alternatively/additionally, make `x()`/`x_only`/`Hram::hram` in `networks/bitcoin/src/crypto.rs` return `Option`/`Result` and propagate `None` from `Schnorr::verify` so an infinity `R` yields `FrostError` rather than a panic — matching the upstream fix pattern (error instead of panic on out-of-domain input).
