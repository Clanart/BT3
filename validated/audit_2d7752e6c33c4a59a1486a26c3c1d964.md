Based on the code I reviewed, there is a concrete Desktop analog: line-index-based `DiffSelection` state is cached and reused across working-directory refreshes without validating that it still corresponds to the same content, and is later applied against a freshly regenerated diff when staging/committing.

### Title
Stale line-index diff selection can be silently reapplied to a different diff, corrupting what gets committed - (File: `app/src/lib/stores/updates/changes-state.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop tracks which lines of a file's diff are selected for commit as an index-based `DiffSelection` object (selection state per absolute hunk-line index), not tied to the actual line content or diff hash. This selection is preserved across working-directory refreshes purely by matching the file's `id` (path + status kind), and is later re-applied to a newly generated diff of the file at staging/commit time. If the file's diff shape changes between the time the user reviewed/selected lines and the time Desktop stages the commit, the cached indices are reinterpreted against different lines with no revalidation, similar to how a rebasing token's fixed `scaledBalance` diverges from the real underlying balance.

### Finding Description
`WorkingDirectoryFileChange.selection` is a `DiffSelection` whose `isSelected(absoluteIndex)` check operates purely on line position within a hunk [1](#0-0) . When a new `git status` result is merged into app state, `updateChangedFiles` preserves the existing selection object for any file whose `id` matches, with no comparison of the underlying diff content: `return file.withSelection(existingFile.selection)` [2](#0-1) . The `diff` itself is only kept if the selected file id is unchanged and is otherwise nulled and lazily regenerated [3](#0-2) .

At commit time, `applyPatchToIndex` fetches a brand-new diff from the current working tree — `const diff = await getWorkingDirectoryDiff(repository, file)` — and then calls `formatPatch(file, diff)`, which walks the new diff's hunks and, for every non-context line, decides whether to include it purely via `file.selection.isSelected(absoluteIndex)` [4](#0-3) , [5](#0-4) . There is no check that the new diff's hunk/line layout matches the layout that existed when the selection indices were originally chosen by the user.

If a file's diff hunk boundaries or line count change between the point the user selects lines in the UI and the point Desktop stages/commits (e.g. because an attacker-controlled build tool, file watcher, git smudge/clean filter, or hook shipped with a cloned repository rewrites the file in the background), the same absolute indices in the stale `DiffSelection` will now point at different logical lines in the new diff. `formatPatch` will silently include lines the user never selected, or omit lines the user did select, producing a patch that no longer matches what the user reviewed and approved on screen.

### Impact Explanation
This breaks the core commit-integrity guarantee that "what you see selected is what gets committed." The corrupted patch is applied straight to the index via `git apply --cached` and then committed/pushed [6](#0-5) , so unintended content controlled by whatever process mutated the file (which, in the threat model, can be something delivered by a malicious cloned repository, e.g. a smudge filter or build script) can end up silently included in the user's commit, or intended fixes/redactions can be silently dropped. This matches "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Selection state is reused solely by file `id` (path+status), with no revalidation against diff content [7](#0-6) , and `applyPatchToIndex` always re-fetches a fresh diff right before staging rather than reusing the diff the selection was made against [8](#0-7) . This means any timing window between diff render and commit where the tracked file's content changes on disk (via a build/watch tool, a git filter defined by the repository, or another process) is enough to desynchronize the selection from the diff. I was not able to fully trace every trigger path (e.g., exact background-refresh cadence, whether the UI blocks staging while a refresh is pending) within the tool budget available, so this should be treated as a plausible, code-supported race rather than a fully verified end-to-end exploit.

### Recommendation
Tie `DiffSelection` to a fingerprint of the diff it was generated from (e.g. a hash of the diff/hunk text or the blob OID pair) rather than only the file id, and invalidate/re-derive the selection whenever the underlying diff changes instead of blindly reusing indices. `applyPatchToIndex`/`formatPatch` should refuse to apply a selection whose hunk layout doesn't match the freshly fetched diff, and surface a warning/refresh prompt to the user instead of silently proceeding.

### Proof of Concept
1. Clone/open a repository that contains a tool which mutates a tracked file shortly after it's touched (e.g. a `pre-commit`/smudge filter, or a running formatter/watcher committed to the repo's tooling).
2. In Desktop, open the Changes view for that file, view the diff, and select only specific lines/hunks (partial selection) via `DiffSelection`.
3. Before staging, let the external process change the file's diff shape (add/remove lines shifting hunk boundaries) without the user re-reviewing the diff in Desktop.
4. Trigger commit: `applyPatchToIndex` fetches the new diff and calls `formatPatch(file, diff)` [9](#0-8) , applying the stale index-based selection to the new hunk layout, producing a patch whose included/excluded lines differ from what was shown and selected in the UI.

```typescript
/** encapsulate the changes to a file in the working directory */
export class WorkingDirectoryFileChange extends FileChange {
  /**
   * @param path The relative path to the file in the repository.
   * @param status The status of the change to the file.
   * @param selection Contains the selection details for this file - all, nothing or partial.
   * @param oldPath The original path in the case of a renamed file.
   */
  public constructor(
    path: string,
    status: AppFileStatus,
    public readonly selection: DiffSelection
  ) {
    super(path, status)
  }

  /** Create a new WorkingDirectoryFileChange with the given includedness. */
  public withIncludeAll(include: boolean): WorkingDirectoryFileChange {
    const newSelection = include
      ? this.selection.withSelectAll()
      : this.selection.withSelectNone()

    return this.withSelection(newSelection)
  }

  /** Create a new WorkingDirectoryFileChange with the given diff selection. */
  public withSelection(selection: DiffSelection): WorkingDirectoryFileChange {
    return new WorkingDirectoryFileChange(this.path, this.status, selection)
  }

  public isIncludedInCommit(): boolean {
    return this.selection.getSelectionType() === DiffSelectionType.All
  }

  public isExcludedFromCommit(): boolean {
    return this.selection.getSelectionType() === DiffSelectionType.None
  }
}
```

```typescript
export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })
```
