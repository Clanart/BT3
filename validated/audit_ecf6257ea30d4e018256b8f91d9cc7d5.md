Webhook HMAC validation does not bind the `X-Shopify-Shop-Domain` header, enabling cross-shop identity spoofing via webhook replay - (File: `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
`ShopifyApp::WebhooksController#receive` relies solely on `ShopifyApp::WebhookVerification#verify_request`, which in turn calls `PayloadVerification#hmac_valid?`. That method validates only `request.raw_post` against the app's shared `client_secret`; it never verifies or binds `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` (or the topic) to the signature. Any party that can obtain one genuinely-signed `(body, HMAC)` pair for the shared app secret — e.g., a merchant who installs the app on their own shop and receives a real webhook — can replay that exact pair directly to the app's public webhook endpoint while substituting an arbitrary shop domain header, and the request will still pass verification.

### Finding Description
- `receive` (`app/controllers/shopify_app/webhooks_controller.rb:7-14`) has no authorization logic of its own; it depends entirely on the `before_action :verify_request` added by `ShopifyApp::WebhookVerification` [1](#0-0) .
- `verify_request` computes `hmac_valid?(request.raw_post)` and returns `:unauthorized` only if that check fails [2](#0-1) .
- `hmac_valid?` computes `HMAC-SHA256(secret, data)` where `data` is exclusively `request.raw_post`; the shop domain header, topic header, and webhook-id header are never included in the signed material [3](#0-2) .
- `shop_domain` is defined only as a raw header read, with no cryptographic tie to the HMAC: `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` [4](#0-3) .
- After verification, `receive` hands the raw body/headers to `ShopifyAPI::Webhooks::Registry.process`, which the maintained generator templates in this same repo show is dispatched to job handlers using `shop: <value derived from the shop-domain header>`. Those jobs use this attacker-controllable value to look up and act on shop records, e.g. `Shop.find_by(shopify_domain: shop_domain)` followed by `shop.with_shopify_session` in `webhook_job.rb.tt` and privacy-job templates [5](#0-4) , and even `shop.destroy` in `AppUninstalledJob` [6](#0-5) .

Exploit flow:
1. Attacker installs the target app on their own (unrelated) shop — a legitimate, unprivileged action.
2. Shopify sends the attacker's app instance a genuinely-signed webhook: `(raw_body, HMAC = HMAC_SHA256(client_secret, raw_body))`, with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this `(raw_body, HMAC)` pair (both attacker-observable, since the webhook is delivered to their own endpoint/logs).
4. Attacker crafts a direct `POST /webhooks/:type` request to the app, reusing the same `raw_body` and `HMAC` header, but replaces `X-Shopify-Shop-Domain` with a victim shop's domain (also an app installer).
5. `hmac_valid?` succeeds because it only checks `raw_post` against the shared secret — it is agnostic to which shop sent the header. `verify_request` passes, the action proceeds.
6. Downstream job processing trusts the (unverified) shop-domain header as the identity of the shop the event pertains to, looking up and operating on the victim shop's `Shop` record and session.

This directly violates the stated invariant: "the shop-domain header must not be trusted as identity without HMAC binding." No existing check (ID token verification, `sanitize_shop_domain`, scope comparison, `secure_compare` on domain) binds the domain header to the signed payload anywhere in this path.

### Impact Explanation
This is a cross-shop data/identity spoofing issue: an attacker who legitimately controls one shop can cause the app to process webhook business logic (including destructive privacy/uninstall jobs) as if it pertains to a different, victim shop, using only a header they fully control alongside a body+HMAC pair they legitimately obtained for their own shop. Depending on the job implementation this can range from misattributed data writes to destructive actions like session/shop record manipulation (`shop.destroy` in `AppUninstalledJob`). This matches the "forged webhook headers → cross-shop data spoofing" impact class.

### Likelihood Explanation
Feasible for any unprivileged attacker who can install the target app on an arbitrary shop (a normal, allowed action for any Shopify merchant/developer) and observe the resulting webhook payloads sent to their own endpoint — no leaked secrets, no host misconfiguration, and no victim interaction required. The replay itself is a single crafted HTTP POST. Repeatable for any topic the attacker's shop can trigger (e.g., `carts/update`, `app/uninstalled`) as long as the same secret is shared across installs, which is the default for `client_secret`-based HMAC.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` (or topic/webhook-id headers) as trusted identity independent of the signed payload:
- Prefer deriving shop identity strictly from data embedded in the verified body (or from a per-shop signing scheme) rather than from headers.
- If headers must be used, verify the `shop_domain` against a value looked up from an already-authenticated, session-bound record rather than blindly trusting the header for job dispatch, and additionally validate that the target shop's own installation-specific secret (if using per-shop or per-install secrets) matches — not merely the app's single shared client secret.
- At minimum, cross-check the shop domain against the set of currently-installed/active shops before performing destructive actions like `shop.destroy`, and consider rate-limiting/anomaly detection for repeated webhook replays across differing shop-domain headers with identical bodies/HMACs.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
