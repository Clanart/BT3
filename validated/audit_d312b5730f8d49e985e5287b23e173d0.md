### Title
Cross-chain escrow release permanently reverts (with no recovery path) when the beneficiary is blacklisted by the input ERC-20, permanently locking a solver's escrowed funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`onAccept` in `ExtrinsicIntents.sol` routes `RedeemEscrow`/`RefundEscrow` messages straight into `IntentsBase._withdraw`, which does an unconditional `IERC20(token).safeTransfer(beneficiary, amount)` with no try/catch and no fallback beneficiary. If the escrow token is a blacklist-capable stablecoin (e.g. USDC — used as a test input token in this exact codebase) and the beneficiary (the solver, or the user on refund) is or becomes blacklisted, the transfer reverts and — unlike Hyperbridge's own peer contracts (`HyperbridgeLzEndpoint`, `WrappedHyperFungibleToken`) — there is no retry/fallback/recovery mechanism and no timeout, so the escrowed funds are permanently stuck. [1](#0-0) 

### Finding Description
`_fillCrossChain` dispatches a `RedeemEscrow` `DispatchPost` back to the source chain with `timeout: 0` (no expiry), after the solver has already irrevocably delivered output tokens to the beneficiary on the destination chain: [2](#0-1) 

On the source chain, `onAccept` decodes this and calls `_withdraw`, unconditionally: [3](#0-2) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;
    ...
    IERC20(token).safeTransfer(beneficiary, amount);
    ...
}
``` [1](#0-0) 

`safeTransfer` reverts atomically if `token` implements a blacklist (e.g. USDC's `notBlacklisted` modifier) and `beneficiary` is on it. Because the whole `_withdraw` call reverts, `_filled[body.commitment]` is never persisted and `_orders[body.commitment][token]` is never decremented — the state rollback is clean, but the message can never be successfully re-delivered while the beneficiary stays blacklisted. ISMP's own model of "delete the receipt on `on_accept` failure so the request can be replayed" (confirmed for EVM in `EvmHost.dispatchIncoming`, which deletes `_requestReceipts[commitment]` on failure "so that it can be retried") means the message is retried indefinitely, but since `dest: order.source` was dispatched with `timeout: 0`, it can **never time out and never be routed to any other beneficiary** — the `WithdrawalRequest.beneficiary` is baked into the message body at fill time and cannot be changed by anyone. [4](#0-3) 

This is structurally identical to the seed report's USDC blacklist bug: an unconditional ERC-20 transfer to a bridge-determined beneficiary with no try/catch and no alternate-recovery path, where a blacklist event between dispatch and settlement (here, up to the order deadline plus arbitrarily long finalization delay) permanently locks the bridged/escrowed asset. Other Hyperbridge apps in this same repo already recognize and mitigate this exact class of failure — `HyperbridgeLzEndpoint.onAccept` wraps the analogous external call in `try/catch` and stores a retryable payload hash rather than reverting the whole delivery, and `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` have an explicit fallback path when a beneficiary can't accept a transfer: [5](#0-4) [6](#0-5) 

`IntentGatewayV2`/`IntentsBase` has no equivalent — the tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) has the identical unconditional-transfer pattern in its own `withdraw()`. [7](#0-6) 

### Impact Explanation
A solver who fills a cross-chain order delivers real output assets to the beneficiary on the destination chain immediately, before the source-chain settlement message lands. If, in the window between fill and settlement (which can be arbitrarily long since the `RedeemEscrow`/`RefundEscrow` post request has `timeout: 0`), the solver's address (or the user's, for refunds) gets blacklisted on the escrowed input token, the escrowed principal is irrecoverably locked in the `IntentGateway`/`ExtrinsicIntents` contract with no owner/governance function to redirect or release it to an alternate beneficiary. This is a direct "loss of funds" outcome matching the bounty's accepted impact class.

### Likelihood Explanation
Medium: it requires the escrowed token to be a blacklist-capable asset (explicitly demonstrated as USDC in this codebase's own test suite) and a blacklist event to occur after the solver has committed to filling the order but before settlement finalizes — exactly the same non-adversarial, non-privileged timing gap the original report identified as a real, fixed vulnerability elsewhere in a bridge adapter.

### Recommendation
Wrap the token transfer in `_withdraw` (and the tron `withdraw`) in a `try/catch`; on failure, credit an internal per-beneficiary "stuck funds" mapping instead of reverting the whole settlement, still finalize `_filled`/decrement escrow, and expose a permissionless or owner-assisted `withdrawStuckFunds(beneficiary, token)` function that lets a since-unblacklisted address (or a governance-redirected address) claim the funds later — mirroring the pattern already used in `HyperbridgeLzEndpoint` (retryable payload) and `WrappedHyperFungibleToken` (fallback delivery path) elsewhere in this same repository.

### Proof of Concept
1. User places a cross-chain order on chain A with `order.inputs = [USDC, 1000e6]`, `order.destination = chain B`. Escrow is locked in `IntentGatewayV2`/`ExtrinsicIntents` on chain A.
2. Solver calls `fillOrder` on chain B, delivering the required output tokens directly to `order.output.beneficiary`; `_fillCrossChain` dispatches a `RedeemEscrow` `DispatchPost` to chain A with `beneficiary = msg.sender` (the solver) and `timeout: 0`. [8](#0-7) 
3. Before the relayer delivers the proof to chain A, the solver's address is added to USDC's blacklist (e.g., by Circle for unrelated reasons).
4. A relayer submits the `RedeemEscrow` proof; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which calls `IERC20(USDC).safeTransfer(solver, 1000e6)`; this reverts because `solver` is blacklisted.
5. `dispatchIncoming` deletes the request receipt "so that it can be retried" — but the request never times out (`timeout: 0`) and the beneficiary field is immutably baked into the already-dispatched message, so every future relayer replay of the same proof reverts identically, forever.
6. The escrowed 1000 USDC remains permanently locked in the `ExtrinsicIntents` contract on chain A, unrecoverable by the solver, the user, or governance. [1](#0-0)

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
