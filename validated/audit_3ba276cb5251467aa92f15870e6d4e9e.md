### Title
Malformed per-input FROST messages can panic Bitcoin transaction signing - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`TransactionSignMachine` accepts one `Vec<Preprocess<Secp256k1, ()>>` per participant, but `sign` indexes each vector for every transaction input without first checking that its length equals `self.sigs.len()`. [1](#0-0) 

### Finding Description
A transaction with one or more inputs creates one `AlgorithmMachine` per input, and `preprocess` emits one FROST preprocess per input. [2](#0-1) [3](#0-2)  During signing, the wrapper iterates `0 .. self.sigs.len()` and evaluates `commitments[c]` for every participant before any per-input `AlgorithmSignMachine::sign` call validates its participant map. [4](#0-3)  A participant-associated vector containing fewer than `self.sigs.len()` elements therefore causes an out-of-bounds panic rather than returning `FrostError`. [1](#0-0) 

The same missing cardinality check exists in `TransactionSignatureMachine::complete`, where each supplied share vector is mutated with `shares.remove(0)` once per input and an empty vector panics. [5](#0-4) 

### Impact Explanation
An unprivileged signing participant that can supply a malformed per-input preprocess or signature-share collection can terminate the victim's signing operation with a panic. [6](#0-5)  This is an availability failure analogous to the reported remotely triggerable server crash, although it affects the local transaction-signing task/process rather than compromising signatures or keys. [1](#0-0) 

### Likelihood Explanation
The vector length is attacker-controlled message structure rather than an internally enforced invariant: the public `SignMachine` input type is `HashMap<Participant, Vec<Preprocess<...>>>`, while the implementation assumes every value contains exactly one preprocess for each transaction input. [7](#0-6)  No `FrostError` is produced before the indexing operation, and no threshold bypass is required because the crash occurs while arranging the already supplied participant messages. [1](#0-0) 

### Recommendation
Validate every participant's preprocess vector with `commitments.len() == self.sigs.len()` before indexing it, and return a structured error such as `FrostError::InvalidPreprocess` or `FrostError::InvalidParticipantQuantity` on mismatch. [1](#0-0)  Apply the same length validation to every share vector before calling `remove(0)` in `TransactionSignatureMachine::complete`. [8](#0-7) 

### Proof of Concept
For a `2`-of-`2` Bitcoin transaction signing session with at least one input, pass a preprocess map containing participant `2` but with an empty per-input vector:

```rust
use std::collections::HashMap;
use frost::{Participant, sign::SignMachine};

// machine: TransactionSignMachine for a transaction with >= 1 input.
let mut commitments = HashMap::new();
commitments.insert(Participant::new(2).unwrap(), vec![]);

// Panics at commitments[c] when c == 0 instead of returning Err(FrostError).
let _ = machine.sign(commitments, b"");
```

The panic is caused by evaluating `commitments[c]` while splitting the vector into per-input maps. [1](#0-0)
