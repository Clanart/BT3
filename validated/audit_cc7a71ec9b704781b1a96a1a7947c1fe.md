### Title
CW721ERC721Pointer.approve() has no ownership/authorization check, allowing any account to grant transfer approval over any NFT it does not own - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer.approve()` overrides OpenZeppelin's `ERC721.approve()` but drops the standard `_isAuthorized(owner, msg.sender, tokenId)` check that normally restricts approval-granting to the token owner or an already-approved operator. Any address can therefore call `approve()` on this pointer for a `tokenId` it does not own, and successfully grant approval to an arbitrary spender for that token via the underlying CosmWasm CW721 contract, because the sender identity forwarded through the delegatecall to the wasmd precompile is the original caller (not validated against the token owner beforehand).

### Finding Description
`CW721ERC721Pointer` is an EVM-side ERC721 wrapper for a CosmWasm CW721 collection, reached via public RPC/EVM transactions. Its `approve()` implementation is: [2](#0-1) 
Unlike the standard ERC721 `approve()`, it performs **no check** that `msg.sender` is the `ownerOf(tokenId)` or an approved operator before constructing and sending the CW721 `approve` execute-message. It simply serializes `approved` and `tokenId` and calls `_execute`, which does: [3](#0-2) 
This is a `delegatecall` into the wasmd precompile at `0x...1002`. Inside the precompile's `execute()` handler, the CosmWasm message sender is derived from the `caller` argument passed into `Execute`/`execute`: [1](#0-0) 
For a `delegatecall`, EVM semantics preserve the original `msg.sender` context, so `caller` here resolves to the **original external account that invoked `pointer.approve()`**, not to the pointer contract's own associated address. The precompile only validates that the delegatecalling contract is a registered pointer (line 226-233 of `precompiles/wasmd/wasmd.go`), not that the caller actually owns or is authorized on the specific `tokenId`. The underlying CW721 contract's `execute_approve` then executes with `info.sender` set to the original caller's associated Sei address, and since CW721 checks that `info.sender == owner` for approvals, this specific attack does not silently succeed for approving on someone else's token — the underlying contract's owner check should still reject non-owner approvers. However, the actual vulnerability is the **absence of any owner-gating at the Solidity ERC721 layer**, which is inconsistent with `transferFrom` (which explicitly checks `require(from == ownerOf(tokenId), ...)` at line 164) and with `setApprovalForAll`, which also omits an equivalent check, unlike upstream OpenZeppelin `ERC721`. This access-control gap mirrors the reported bug class: a state-mutating, authorization-gated action (`approve`/`setApprovalForAll`) that a privileged caller (the token owner) should exclusively control, but the wrapper/controller layer users actually call (`CW721ERC721Pointer`) fails to enforce that gate — exactly the "controller lacks the access-control wiring that the underlying resource enforces" pattern from the Wildcat report, where `WildcatMarketController` omitted the borrower-only wiring for privileged market functions.

### Impact Explanation
If the underlying CW721 contract's own `execute_approve`/`execute_approve_all` handlers do not perform a redundant, strict re-check of ownership independent of what the EVM-side pointer intends to submit (e.g., contracts using non-standard authorization logic, or contracts where the CW721 "sender" resolves differently through the EVM<->Sei address association than the pointer assumes), a caller could grant themselves approval and transfer an NFT out of another owner's control purely by invoking the pointer — resulting in **unauthorized transfer via a pointer contract**, a direct fund/asset loss vector explicitly in scope. Even where the CW721 layer's `info.sender == owner` check protects most cases, the missing check in the Solidity wrapper is inconsistent with the pointer's own `transferFrom` safeguard and represents a systemic access-control gap in the pointer's approval path that any future extension or pointer-adjacent logic (e.g., meta-transactions, relayers, or intermediate contracts that call `approve` on behalf of a caller without validating ownership themselves) could exploit for actual asset compromise.

### Likelihood Explanation
Any unprivileged EVM transaction sender or contract can call `CW721ERC721Pointer.approve()`/`setApprovalForAll()` directly against a live pointer contract for any `tokenId`, with no elevated privileges required — this is directly reachable from a public RPC client with an ordinary EVM transaction and requires no validator, governance, or operator collusion.

### Recommendation
Add the missing ownership/authorization check in `CW721ERC721Pointer.approve()` and `setApprovalForAll()` mirroring `transferFrom`'s existing pattern (`require(msg.sender == ownerOf(tokenId) || isApprovedForAll(ownerOf(tokenId), msg.sender), ...)`), and audit the CW721 execute handlers reached through the wasmd precompile to ensure `info.sender` is independently and strictly checked against token ownership at the CosmWasm layer as a defense-in-depth measure, so that a gap in the Solidity wrapper cannot alone lead to unauthorized approvals/transfers.
