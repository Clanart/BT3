### Title
Webhook HMAC verification does not bind shop domain or topic, enabling cross-shop webhook forgery via signature replay - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` (and the shared `PayloadVerification#hmac_valid?` it relies on) only authenticates the raw request **body**. Neither the `X-Shopify-Shop-Domain` header nor the `X-Shopify-Topic` header — both of which determine which shop and which job/topic a webhook is dispatched to — are included in the signed data. This mirrors the `prepareForMigration`/`addPeerByPeer` bug class: a signature that is valid for one context (one shop, one topic) can be replayed unchanged into a different context because the signing scheme does not bind all the security-relevant fields.

### Finding Description
The HMAC check is: [1](#0-0) 

which is invoked from `WebhookVerification#verify_request` using only `request.raw_post`: [2](#0-1) 

The shop identity used downstream is read straight from an **unsigned** header: [3](#0-2) 

`WebhooksController#receive` builds the topic/shop-bearing request object purely from headers and the (HMAC-verified) body, and dispatches to a job keyed by shop/topic from those headers: [4](#0-3) 

The generated declarative-webhook controller does the same, queuing a job with `shop_domain: webhook_request.shop` where `.shop` is derived from the `X-Shopify-Shop-Domain` header, not from anything covered by the HMAC: [5](#0-4) 

The route itself accepts any `:type` and always dispatches to the same `receive` action, so the actual topic used for job selection comes entirely from the `X-Shopify-Topic` header at runtime, not from anything the route or the signature constrains: [6](#0-5) 

Because the signature covers only `raw_post`, an attacker who owns *any* shop can legitimately trigger Shopify to sign an arbitrary body of their choosing (by causing events in their own store — e.g. cart/product/order updates whose payload they control to varying degrees) and obtain a valid `(body, HMAC)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain and/or the `X-Shopify-Topic` header with an unrelated topic. `hmac_valid?` still returns true because it never looked at those headers, and the job is enqueued as if it were a legitimate webhook for the victim shop/topic combination.

This is the same root cause as the reported issue: a signature/data-layout that omits a field which is supposed to disambiguate "which operation/target this signature is for" allows a signature obtained for one legitimate purpose to be repurposed for another, unintended one.

### Impact Explanation
Any background job wired via `ShopifyApp::WebhooksManager`/`WebhooksController` (privacy webhooks, `app/uninstalled`, custom shop/order/product webhooks, etc.) receives `shop_domain` and topic values that are **not cryptographically bound** to the signed payload. An attacker controlling one shop can force the app to process attacker-shaped webhook bodies under a victim shop's identity or under a different topic than the body actually represents. Depending on what the app's webhook jobs do with `shop_domain` (e.g., updating shop-scoped records, triggering uninstall cleanup, re-triggering GDPR data deletion/export for a shop other than the attacker's own), this enables cross-shop data corruption, spoofed lifecycle events (e.g., forged `app/uninstalled` for a victim shop), or topic confusion where a job parses a body under the wrong schema. This satisfies "cross-shop or cross-user access" / "accepted forged signed request" from the validation bar.

### Likelihood Explanation
Exploitation requires only that the attacker control (or have installed the app on) one Shopify store — a standard, unprivileged capability for anyone who can install a public app — plus the ability to capture and replay their own legitimately-signed webhook to the target app's public webhook endpoint with modified headers. No secret or elevated privilege is needed, and the vulnerable code path (`hmac_valid?` over `raw_post` only) is the default, unconditionally-used verification for every consumer of `ShopifyApp::WebhookVerification` and `ShopifyApp::PayloadVerification` (also shared by `ExtensionVerificationController`).

### Recommendation
Bind all security-relevant context into the authenticated data, not just the body:
- Compute/verify the HMAC over a canonical string that includes the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values in addition to `raw_post`, or otherwise cryptographically bind shop/topic to the signature before trusting them.
- At minimum, cross-check that the shop domain in the payload/session context matches an expected, already-known-installed shop before enqueuing shop-scoped jobs, and reject/log topic values that don't match the target route's expected topic.
- Consider following Shopify's own webhook verification guidance strictly and adding application-level deduplication/replay protection (e.g., tracking `X-Shopify-Webhook-Id` to reject repeats), analogous to the report's recommendation to track a `used`/nonce mapping to prevent signature reuse.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers an event (e.g., updates a cart) that causes Shopify to send a webhook: body `B`, headers `X-Shopify-Topic: carts/update`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: H` (valid, computed by Shopify over `B` with the app secret).
2. Attacker captures this request (e.g., via a debugging proxy on their own tunnel/webhook receiver, or by momentarily pointing the webhook URL to an attacker-controlled logger before restoring it).
3. Attacker replays the exact same `POST /webhooks(:type)` request to the app, unchanged body `B` and unchanged `Hmac` header `H`, but with headers rewritten to `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: <different topic>`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks `B` against `H` — this still passes because the body is unchanged. [7](#0-6) 
5. The app proceeds to process/enqueue a job using `shop_domain` = `victim.myshopify.com` (from the forged header) and the attacker-controlled body/topic, even though Shopify never signed anything for `victim.myshopify.com` or for that topic.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
