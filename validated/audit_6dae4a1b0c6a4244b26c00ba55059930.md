## Title
Unbounded CLVM execution in `Offer._get_offered_coins()` allows a malicious offer file to hang wallet processing - (File: chia/wallet/trading/offer.py)

### Summary
`Offer._get_offered_coins()`, invoked indirectly by `get_offered_coins()` / `get_offered_amounts()` / `summary()` / `arbitrage()` when a wallet user inspects or accepts an offer received from an untrusted counterparty, runs each offer's inner puzzle with `cost_left = INFINITE_COST` instead of the network's `MAX_BLOCK_COST_CLVM` limit. This mirrors the CVE-2017-3637 bug class: an unprivileged, low-effort input from a network-adjacent party (an X Plugin request there; here, an offer file/bech32m blob) reaches a code path lacking a resource bound and can cause a hang/DoS.

### Finding Description
`Offer.__post_init__()` bounds CLVM execution correctly, decrementing a shared `max_cost` budget (`DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`) across `compute_spend_hints_and_additions()` calls: [1](#0-0) 

However, `_get_offered_coins()`, a separate method used to identify which coin additions were "offered" (called from `get_offered_coins()`, which backs `get_offered_amounts()`, `arbitrage()`, `summary()`, and the trade manager's offer inspection/acceptance flow), initializes its own local cost budget to `INFINITE_COST` and runs the inner puzzle of every coin spend in the offer with no cost ceiling: [2](#0-1) 

`get_offered_coins()` lazily computes and caches this on first access: [3](#0-2) 

Because `run_with_cost(cost_left, inner_solution)` is called with `cost_left = INFINITE_COST` (see import at line 14: `from chia.types.blockchain_format.program import INFINITE_COST, ...`), a crafted `Offer` bech32m blob whose inner puzzle (of a CAT/NFT/DID/custom outer-puzzle-driver-matched coin spend) contains a computationally expensive but terminating loop, or an extremely deep/expensive CLVM structure, will be executed by the wallet with no cost limit at all. This differs from the mempool/full-node path, which strictly enforces `max_tx_clvm_cost` (see `mempool_manager.py:571-587`) and from `Offer.__post_init__`/`compute_additions_with_cost`, which do enforce `MAX_BLOCK_COST_CLVM`. The wallet-side offer-summary path is the outlier that omits the cost check present everywhere else in the same class.

Since offers are routinely exchanged out-of-band (dexie, offer files, chat, etc.) and examined by calling `get_offer_summary`/`get_offered_amounts`-style RPCs before a user decides to accept, an attacker can hand a victim a single crafted offer file that triggers this unmetered execution merely by being inspected, well before any signature or fee is validated.

### Impact Explanation
This is a spend-triggered (offer-triggered) transaction-processing halt: unmetered CLVM execution on attacker-controlled puzzle/solution data can consume CPU for an extended period or exhaust memory, hanging the wallet's async event loop/RPC (and, by extension, blocking the daemon and preventing prompt processing of legitimate offers or transactions during that time) — matching the "hang or repeatable crash" impact class in CVE-2017-3637 (Availability-only CVSS impact). This does not enable unauthorized coin movement or supply inflation, but is a legitimate availability defect in an unprivileged, remotely-triggerable code path.

### Likelihood Explanation
Likelihood is moderate: an attacker needs only to craft an `Offer` object with an outer/inner puzzle combination recognized by `match_puzzle()` (e.g., a CAT/NFT driver) whose inner puzzle solution runs a puzzle-hash-bounded-size but computationally heavy CLVM program, and get any wallet user or automated offer-book service to call `get_offered_amounts()`/`summary()`/`arbitrage()` on it — a normal, low-friction UX step (viewing an offer before deciding whether to accept). No signature validity or actual on-chain spendability is required, since this code executes before/independently of blockchain confirmation.

### Recommendation
Bound `cost_left` in `Offer._get_offered_coins()` to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` (or a comparably small "max tx cost") exactly as is already done in `Offer.__post_init__()` and `compute_spend_hints_and_additions()`, and fail fast (raising `ValidationError`) if the budget is exceeded rather than continuing to execute unmetered CLVM. Consider covering this with a resource/perf test analogous to `test_offer_rejects_spend_exceeding_max_cost` in `chia/_tests/wallet/test_util.py`, but targeting `_get_offered_coins()`/`get_offered_amounts()` specifically.

### Proof of Concept
1. Construct a `WalletSpendBundle` containing a `CoinSpend` whose puzzle reveal is a recognizable outer puzzle (e.g. CAT) wrapping an inner puzzle that, when run with its solution, performs a large but bounded-output CLVM loop (e.g., similar to the `deep_recursion`/`SINGLETON_MOD`-style loop programs used in `chia/_tests/core/mempool/test_mempool_manager.py:3479-3489`), sized so it would be rejected under `MAX_BLOCK_COST_CLVM` but not under `INFINITE_COST`.
2. Build an `Offer` from this bundle via `Offer.from_spend_bundle()` and serialize/bech32m-encode it as a normal offer file.
3. Send this offer file to a victim (wallet user or offer aggregator service).
4. Victim/service calls `offer.get_offered_amounts()` (or `summary()`/`arbitrage()`, all of which route through `get_offered_coins()` → `_get_offered_coins()`), triggering `inner_puzzle.run_with_cost(INFINITE_COST, inner_solution)` with no cost bound, hanging the process for a duration proportional to the crafted program's actual (unbounded) cost.
