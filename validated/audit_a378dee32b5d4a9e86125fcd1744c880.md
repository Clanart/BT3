### Title
Unvalidated PR-supplied file paths reach filesystem-affecting shell operations without repo-root containment check - ([File: app/src/ui/open-pull-request/pull-request-files-changed.tsx])

### Summary
The ERC-20 "scoop" bug is fundamentally an authorization/scoping failure: `settleAuction()` lets a caller supply an `outputToken` address that is never checked against the basket's actual token set, so an attacker can direct a privileged transfer at an unrelated asset. The GitHub Desktop analog is the same class of bug applied to file paths: several UI codepaths take a `path` string that originates from **attacker-influenced data** (a pull request's changed-file list, fetched from the GitHub API for a PR the current user did not author) and pass it straight into `Path.join(repository.path, file.path)` before invoking filesystem/shell operations (`revealInFileManager`, `dispatcher.openInExternalEditor`, `openFile`) — with no equivalent of the `resolveWithin()` containment check that Desktop *does* apply elsewhere (e.g. in `app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl`, and in `app/src/lib/copilot-conflict-context.ts`).

### Finding Description
`PullRequestFilesChanged.onFileContextMenu` and `onOpenFile` in [1](#0-0)  and [2](#0-1)  build a `fullPath` via `Path.join(repository.path, file.path)` where `file` is a `CommittedFileChange` populated from a pull request's file list. The only check performed before wiring up "Reveal in File Manager", "Open in External Editor", "Open with Default Program" and "Copy Path" menu actions is `pathExists(fullPath)` — there is no `resolveWithin()`/root-containment validation, unlike the deep-link handler in `dispatcher.ts`: [3](#0-2) 

and unlike the Copilot conflict-context reader, which explicitly guards against exactly this scenario: [4](#0-3) 

The same unguarded `Path.join(repository.path, path)` pattern recurs in `revealInFileManager` itself [5](#0-4) , in `AppStore`'s external-editor open call [6](#0-5) , and in the changes-list/history context menus (`filter-changes-list.tsx`, `selected-commits.tsx`), all of which trust `file.path` as a same-repo-relative path without verifying it stays within `repository.path`.

For local working-directory changes or local commits, `file.path` is constrained by git's own tree/index semantics (git refuses ".." components in tracked paths), so those callers are effectively safe in practice. The pull-request file list, however, is populated from a **remote GitHub API response describing files changed in someone else's PR** — a fork owner or malicious contributor controls the diff that produces that file list. `resolveWithin` documents that this exact scenario (join + escape) is a known risk class the app defends against elsewhere [7](#0-6) , and the accompanying tests confirm that plain `Path.join` does not stop traversal, including via symlinks [8](#0-7) .

### Impact Explanation
If a crafted PR/file-list entry can carry a path with traversal segments (e.g. `../../../../.ssh/id_rsa` or a path that resolves through a symlinked directory), the "Reveal in File Manager" / "Open in External Editor" / "Open with Default Program" actions in the "Files Changed" view for that PR would operate on a file **outside the repository working directory** the moment the user right-clicks or double-clicks the entry — without any warning that the target is outside the repo. Since `openFile`/`openInExternalEditor` invoke `shell.openExternal`/launch the OS default handler on that resolved path, this could expose or execute unintended files depending on file type and the user's default handler associations. This is a lower-severity, UI-interaction analog (it requires the victim to select the file in the PR viewer and click a menu action) rather than a silent, automatic write/exfiltration — but it matches the "attacker controls a GitHub API object" and "result is file read/action outside the repo" criteria in scope.

### Likelihood Explanation
Whether this is actually exploitable end-to-end depends on facts I could not verify from the indexed code alone: whether the GitHub API/Desktop's PR-file-list ingestion layer sanitizes or rejects filenames containing `..`/absolute-path segments before constructing `CommittedFileChange.path` (GitHub's API itself normally reflects git tree paths, which git disallows containing `..` components, making a literal traversal payload unlikely to originate from a real PR diff). I was not able to locate the specific parsing code that converts the GitHub "files changed" API response into `CommittedFileChange` objects to confirm whether any extra validation happens there. Given git's own tree-path restrictions, likelihood is moderate-to-low, and this should be treated as **defense-in-depth missing** (no `resolveWithin` check where one exists elsewhere in the same codebase) rather than a confirmed, currently-triggerable traversal.

### Recommendation
Apply the existing `resolveWithin()` helper (`app/src/lib/path.ts`) consistently to any path built from PR/commit file-list data before passing it to `revealInFileManager`, `openInExternalEditor`, or `openFile`, mirroring the pattern already used in `dispatcher.ts`'s `openRepositoryFromUrl` and `copilot-conflict-context.ts`. Reject and surface an error for any resolved path that does not stay within `repository.path`, instead of relying solely on `pathExists`.

### Proof of Concept
Conceptual (not confirmed against live GitHub API sanitization, per Likelihood section above):
1. A malicious/forked contributor opens a PR whose diff includes a file entry whose reported path resolves through directory traversal or a symlinked component when combined with the local repository root.
2. The victim opens that PR in Desktop's "Files Changed" view (`PullRequestFilesChanged`), which renders the file list directly from the GitHub API response.
3. Victim right-clicks the entry and selects "Reveal in File Manager" / "Open in External Editor" — `Path.join(repository.path, file.path)` (`app/src/ui/open-pull-request/pull-request-files-changed.tsx:162`) resolves outside the repo since no `resolveWithin` check is performed, unlike the analogous, already-hardened `openRepositoryFromUrl` codepath in `dispatcher.ts`.

        action: () => revealInFileManager(repository, file.path),
