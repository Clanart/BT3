## Analysis

The Tapioca finding's broken invariant is: **an attacker-controlled value that travels from an untrusted context (a market address chosen by the caller) is passed unchecked into a privileged sink** (`approve()` + external `call`), with no allow-list to ensure the target is a legitimate protocol contract.

The closest structural analog in GitHub Desktop is the "Open File" action, which forwards an **attacker-controlled filename from a cloned/fetched repository** directly into `shell.openExternal('file://' + fullPath)` — a privileged OS-level sink — with no allow-list/deny-list on file type and no confirmation step, unlike files downloaded through a browser (which get a quarantine/"Mark of the Web" attribute that triggers OS warnings before execution).

### Title
Unvalidated repository file paths passed to `shell.openExternal` allow execution of attacker-supplied files from a cloned repository - (File: app/src/ui/lib/open-file.ts)

### Summary
`openFile()` builds a `file://` URI directly from a path taken from the working directory of the currently open repository and hands it to Electron's `shell.openExternal`, which asks the OS to launch the item with its default handler. Since the path (and therefore the file's name/extension) originates from a cloned/fetched repository, an attacker who controls repository content controls what gets executed when the user invokes "Open File" from Desktop's UI.

### Finding Description
`openFile()` performs no validation on `fullPath` beyond string interpolation into a `file://` URL: [1](#0-0) 

`shell.openExternal` in the app-shell wrapper documents this exact risk on the neighboring `showItemInFolder`/`showFolderContents` methods ("Do not use this method with non-validated paths"), but `openExternal` itself carries no such guard and is exposed with the same "path" argument shape: [2](#0-1) 

`openFile` is wired up from multiple UI surfaces that display files belonging to a cloned/fetched repository or a diff (Changes sidebar, commit history, conflict resolution, PR files-changed view) — i.e., file names and paths that are fully attacker-controlled once the user has added or fetched a hostile repository: [3](#0-2) 

When `shell.openExternal('file://<path>')` is invoked, the OS launches the file using its registered default handler for that extension. Unlike files obtained via a browser download (which typically receive a quarantine attribute / "Mark of the Web" causing the OS to show a security prompt), files materialized by `git clone`/`git fetch` carry no such marker. An attacker who can get a victim to clone/open a malicious repository and click "Open File" on a crafted entry (e.g., a `.cmd`/`.bat`/`.vbs`/`.js` file on Windows, a `.command`/`.app` bundle or `.scpt` on macOS, or an executable `.desktop`/shell script on Linux with the execute bit set) can achieve code execution the moment the user opens that single file — no separate "run" confirmation is interposed by Desktop.

This mirrors the audited bug's invariant precisely: a value that arrives from an untrusted/attacker-influenced source (there: the LayerZero market parameter; here: a repository-supplied filename) reaches a privileged sink (there: `approve` + external call; here: OS-level `openExternal`) without any allow-list, extension check, or other validation.

### Impact Explanation
If exploited, this results in arbitrary code execution on the victim's machine under their own user privileges, triggered purely by normal use of Desktop's file-viewing/open features against a repository the attacker controls (a cloned repo, a fork added as a remote, or a repository opened via "Open in Desktop"). This satisfies the "unprivileged... attacker controls a cloned/fetched repository ... and the result is code execution" impact category.

### Likelihood Explanation
Likelihood depends on: (1) the victim cloning/fetching an attacker-authored repository (a very common workflow — reviewing forks, PRs, or unknown projects is one of Desktop's core use cases), and (2) the victim using "Open File" on the crafted entry, which is a single, expected click during normal review of changes/history — not an unusual or contrived interaction. No admin rights, local access, or pre-existing malware are required.

### Recommendation
- Do not call `shell.openExternal('file://...')` directly for repository-supplied paths. Prefer `shell.showItemInFolder` (reveal, don't execute) for files whose type/handler is not explicitly vetted, or restrict `openFile` to a safe allow-list of non-executable extensions.
- Where opening the file is required, apply the same protection browsers use: mark files originating from clone/fetch with a quarantine attribute (e.g., macOS `com.apple.quarantine`, Windows Zone.Identifier ADS) before exposing an "Open" action, so the OS surfaces its native "this file was downloaded from the internet, are you sure?" prompt.
- Add an explicit warning/confirmation dialog before opening any file whose extension is associated with a script/executable handler.

### Proof of Concept
Conceptual PoC (cannot be executed here, provided as a reproduction outline for a Devin session with repo/file access):
1. Attacker creates a public repository containing a file named `readme-update.cmd` (Windows) or `notes.command` (macOS) with a malicious payload, and an execute bit set where applicable.
2. Victim clones the repository in GitHub Desktop and opens the Changes/History view, where the crafted file appears as a normal file entry.
3. Victim selects "Open File" (wired through `openFile()` in `app/src/ui/lib/open-file.ts`) on that entry.
4. `shell.openExternal('file://.../readme-update.cmd')` causes the OS to execute the script via its default handler, with no additional warning, achieving code execution as the victim. [4](#0-3)

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
