### Title
Unauthenticated OP_RETURN payer attribution lets an attacker credit an arbitrary operator for a payout it never funded - (File: core/src/verifier.rs)

### Summary
`update_finalized_payouts` determines which operator "fronted" a withdrawal payout solely by parsing an `OP_RETURN` output from the confirmed payout transaction via `get_first_op_return_output`/`parse_op_return_data`, with no cryptographic check that the named operator's key signed or funded any input of that transaction. Because the user's authorizing signature uses `TapSighashType::SinglePlusAnyoneCanPay`, anyone possessing that signature (including the withdrawer themselves, per the threat model) can build and broadcast the payout transaction, add arbitrary funding inputs, and stamp any operator's `xonly_pk` in the `OP_RETURN`, causing `payout_payer_operator_xonly_pk` to be set to an operator who never funded the payout.

### Finding Description
The binding this code is supposed to enforce is: `payout_payer_operator_xonly_pk(withdrawal i) == the operator whose funds paid output_txout of withdrawal i`.

In `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`), for every payout transaction found spending a tracked withdrawal UTXO, the code does: [1](#0-0) 
It extracts the `OP_RETURN` payload and interprets it directly as the paying operator's `XOnlyPublicKey`, then persists it via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`). There is no signature verification, no check that any input of the payout transaction is spendable by or attributable to that key, and no linkage to the operator's registered identity beyond the raw bytes in the `OP_RETURN` script.

The payout transaction itself is built in `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which signs only the single withdrawal input with the user's `SinglePlusAnyoneCanPay` signature and appends an unsigned, uncommitted `OP_RETURN` containing whichever `operator_xonly_pk` the constructor chooses: [2](#0-1) 
Because `SinglePlusAnyoneCanPay` only commits to input 0 and output 0, the `OP_RETURN` output, any additional funding inputs, and the fee/anchor structure are entirely unconstrained by the user's signature. The verifier's own `Operator::withdraw` flow (`core/src/operator.rs:560-692`) confirms this: it verifies only the user's signature over the withdrawal input via `SECP.verify_schnorr` (`core/src/operator.rs:630-637`), then funds the rest of the transaction with `fund_raw_transaction`/`sign_raw_transaction_with_wallet` using whichever wallet broadcasts it — nothing on-chain proves that the `OP_RETURN` pubkey belongs to the party that supplied those funding inputs.

Exploit flow: the attacker, as the withdrawer, obtains their own `SinglePlusAnyoneCanPay` signature over the withdrawal UTXO (they control the outpoint, script, and sighash per the threat model). Instead of handing it to a legitimate operator off-chain, they construct the payout transaction themselves — funding the user output from their own coins if desired — and set the `OP_RETURN` to any real, registered operator's `xonly_pk`. Once mined, `update_finalized_payouts` reads this attacker-controlled `OP_RETURN` and records that operator as the payer in `withdrawals.payout_payer_operator_xonly_pk`. Downstream, `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) and `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` (`core/src/database/verifier.rs:315-346`) are the lookups an operator's reimbursement/kickoff logic uses to find withdrawals attributed to its own key — none of the code inspected re-verifies that the operator actually funded the transaction before it is treated as "this operator's payout to reimburse."

None of the existing guards mitigate this: `SECP.verify_schnorr` only checks the withdrawer's own signature over the withdrawal input, not the identity of whoever funds/broadcasts the rest of the transaction or writes the `OP_RETURN`; there is no database uniqueness constraint or musig2 session tying the `OP_RETURN` bytes to a key that signed anything.

### Impact Explanation
An operator can be credited (`payout_payer_operator_xonly_pk`) for a withdrawal it never funded, matching the Critical category "an operator reimbursed for a payout it never funded." If that operator's automated reimbursement flow trusts `get_first_unhandled_payout_by_operator_xonly_pk`/`get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` results to initiate a kickoff/reimburse claim (`core/src/builder/transaction/operator_reimburse.rs:341-385`), bridge collateral/deposit funds are paid out to a party that did not front the withdrawal, leaking value out of the bridge's escrowed funds. This is repeatable for every withdrawal and against any registered operator's known public `xonly_pk`, since operator keys are public protocol parameters, not secrets.

### Likelihood Explanation
The attacker needs no privileged role: they act as the withdrawer, which the threat model explicitly grants (choosing the withdrawal UTXO, signature, sighash flag, and `OP_RETURN`/script bytes, and calling `withdraw` on the Citrea Bridge contract). The only cost is standard Bitcoin transaction fees for the payout transaction; no special hardware, majority hashrate, or key compromise is required. The attack is directly reproducible with a locally constructed transaction and does not require mainnet or a live Citrea deployment, since `update_finalized_payouts` only depends on locally-cached block data and a locally running database.

### Recommendation
Do not treat the `OP_RETURN` operator key as authoritative payer attribution without cryptographic proof. Require that the operator claiming credit for a payout co-signs or otherwise cryptographically commits to the payout transaction (e.g., binding the `OP_RETURN`/reimbursement claim to a signature from the claimed operator's key over the payout transaction, or requiring the operator's own funding input(s) to be present and provably controlled by that operator's key) before `update_payout_txs_and_payer_operator_xonly_pk` or any downstream reimbursement logic accepts the attribution.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
