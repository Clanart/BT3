### Title
Submodule updates unconditionally enable `protocol.file.allow=always`, permitting attacker-controlled `.gitmodules` file:// URLs to read/leak local filesystem paths on submodule init - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  takes a caller-supplied `allowFileProtocol: boolean` and, when true, prepends `-c protocol.file.allow=always` to `git submodule update --init --recursive`. This flag exists specifically to bypass Git's own hardening (added upstream after CVE-2022-39253) which by default blocks `file://`-protocol submodules from being auto-initialized, because a malicious repository's `.gitmodules` can declare a submodule URL pointing at an arbitrary local path/git repo and have Git silently clone it into the working tree during `checkout`/`clone`/`pull`.

### Finding Description
Git added `protocol.file.allow`/`protocol.allow` restrictions as a defense against a repository's `.gitmodules` file specifying a `file://` (or bare local path) submodule URL that references another local git repository the victim has on disk (e.g. another cloned project, a config repo, or a repo containing secrets/hooks). Without the restriction, `git submodule update --init` will happily "clone" that local repository's contents into the attacker-controlled repo's working tree, exposing its data to whatever workflow (diffing, committing, pushing, AI features) subsequently touches the new submodule directory.

Desktop's `updateSubmodulesAfterOperation` re-enables this exact behavior via `-c protocol.file.allow=always` whenever it is invoked with `allowFileProtocol: true` [2](#0-1) . This function is called from multiple flows in `app/src/lib/git/checkout.ts` (7 references found), meaning a repository fetched/cloned by the user and merely checked out could trigger a submodule init that reads from other local git repositories the attacker specifies by path in `.gitmodules`, entirely from data the attacker fully controls (the cloned repo's `.gitmodules`).

### Impact Explanation
If the flag is applied broadly (e.g., for any checkout regardless of whether the remote/submodule URLs are trusted GitHub-hosted paths), an attacker who gets a victim to clone or open a crafted repository (a classic "attacker controls a cloned/fetched repository" primitive) can point a submodule at a local path such as another repository under the user's home directory. Git will copy that repository's tracked files, refs, and possibly hooks into the malicious repo's working tree, where they may be surfaced back to the attacker upon the next `push`, or used to trigger execution via hooks/build scripts bundled in that other local repo. This matches the requested impact class of "file read outside the repo" and potentially "silent corruption of what the user commits."

### Likelihood Explanation
The likelihood is uncertain without confirming exactly how the 7 call sites in `checkout.ts` compute `allowFileProtocol`. If Desktop only sets this to `true` for repositories/submodules it has already established are same-origin/trusted (mirroring the same-origin filtering pattern used elsewhere in the codebase, e.g. `installSameOriginFilter` in `app/src/main-process/main.ts` [3](#0-2) ), then this is not exploitable. I was not able to verify this within the available tool budget, so this should be treated as a code path requiring confirmation rather than a proven exploit.

### Recommendation
Audit every call site of `updateSubmodulesAfterOperation` in `app/src/lib/git/checkout.ts` to confirm `allowFileProtocol` is only ever `true` when the submodule/parent remote is a trusted GitHub host, never simply hardcoded `true` for arbitrary cloned/fetched repositories. If it is unconditionally true, gate it behind the same kind of remote-URL trust check already used for proxy/auth (`envForRemoteOperation`/`getFallbackUrlForProxyResolve`), and otherwise leave Git's default `protocol.file.allow=user`/blocked behavior in place.

### Proof of Concept
1. Attacker crafts a repository containing a `.gitmodules` entry: `url = file:///Users/victim/some-other-local-repo` (a path likely to exist on many dev machines, or discovered via other means).
2. Victim clones/opens this repository in GitHub Desktop and Desktop performs a checkout/pull that calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`.
3. Because `-c protocol.file.allow=always` is passed, `git submodule update --init --recursive` succeeds in copying the referenced local repository's contents into the malicious repo's working tree, despite Git's own default protections being designed to block exactly this.

**Confidence caveat:** I could not confirm from the index whether the `allowFileProtocol` argument is actually set to `true` unconditionally at the `checkout.ts` call sites, or whether it's already properly gated by trust checks — this needs direct code review of those 7 call sites to convert this from a plausible finding into a confirmed vulnerability. Given index size limits, if you need the exact `checkout.ts` code around each of these calls, a full Devin session with file access would be able to inspect it directly.
