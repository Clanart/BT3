## Title
Unauthenticated `SendMoveToVaultTx` accepts a `deposit_outpoint` unrelated to the submitted movetx, breaking the deposit-to-movetx attribution binding - (File: `core/src/rpc/aggregator.rs`)

### Summary
`ClementineAggregator::send_move_to_vault_tx` validates the *structure* of the submitted `movetx` (input/output counts, output amounts, and output script-pubkeys against the expected bridge/anchor scripts) but never checks that `movetx.input[0].previous_output` actually equals the caller-supplied `deposit_outpoint`. It then records the pair `(deposit_outpoint, movetx)` in the DB via `insert_try_to_send` with `TransactionType::MoveToVault`. Per the project's own documentation (`docs/usage.md`), "The aggregator does not enforce client certificates but does use TLS for encryption," meaning this RPC is reachable by any network caller without the mTLS identity check that gates verifier/operator RPCs.

### Finding Description
`send_move_to_vault_tx` in `core/src/rpc/aggregator.rs` (around lines 1974-2100) deserializes the attacker-supplied `raw_tx` and a separately supplied `deposit_outpoint` field from `clementine::SendMoveTxRequest`: [1](#0-0) 

It checks input/output counts and output amounts/scriptpubkeys: [2](#0-1) 

But it never compares `movetx.input[0].previous_output` to the `deposit_outpoint` parameter before persisting the pair: [3](#0-2) 

This breaks the equality that should hold: `deposit_outpoint (as recorded/attributed) == movetx.input[0].previous_output (the deposit UTXO actually being moved)`. Any properly-signed movetx observed by an attacker (e.g., broadcast for a *different* deposit, or one they legitimately co-signed for their own deposit) can be resubmitted here tagged with an arbitrary `deposit_outpoint` value, because the field is stored purely as metadata (`TxMetadata { deposit_outpoint: Some(deposit_outpoint), ... }`) without being cross-checked against the transaction's actual input.

Downstream code paths key off this DB attribution, e.g. `get_move_to_vault_txid_from_citrea_deposit`, used when validating withdrawals/optimistic-payout amounts against `deposit_id`: [4](#0-3) 

If the recorded `deposit_outpoint`↔`movetx` mapping can be forged to point to a *different* deposit than the one actually moved, then a deposit lookup for `deposit_id` can resolve to the wrong `move_to_vault` transaction/txid, misattributing which on-chain move-to-vault UTXO corresponds to which Citrea deposit record.

Reaching this RPC does not require a verifier, operator, aggregator, or watchtower role, nor key/cert compromise: the aggregator's server explicitly skips client-certificate enforcement (only verifier/operator servers wrap the service in the `OnlyAggregatorAndSelf` interceptor): [5](#0-4) [6](#0-5) 

### Impact Explanation
This maps to the "deposit presigned versus deposit minted once" / attribution-binding class explicitly called out in scope: the `deposit_outpoint` recorded for a `move_to_vault` transaction is meant to equal the outpoint that transaction actually spends, and it is not enforced. A mismatch here can cause a deposit's on-chain movement to be misattributed to the wrong `deposit_id`, corrupting the reimbursement/withdrawal bookkeeping that depends on `get_move_to_vault_txid_from_citrea_deposit`. Depending on how downstream consumers key off this mapping, this can result in a misattributed record for a deposit (an honest operator/verifier state depending on a false deposit↔movetx binding), which falls under the "a deposit presigned versus a deposit minted once" custody-binding class this scan targets.

### Likelihood Explanation
Reachability is high: the RPC is exposed on the aggregator's public gRPC endpoint without the certificate-pinning enforcement applied to verifier/operator servers, per the documented design. However, actually exploiting the missing check requires the attacker to already possess (or capture) a validly N-of-N-signed movetx — they cannot forge the witness/signature themselves. This limits the attack to replay/relabeling of a legitimately-signed transaction rather than pure forgery, which somewhat lowers likelihood but does not eliminate the attribution-binding break, since the check is structurally absent regardless of caller identity.

### Recommendation
In `send_move_to_vault_tx`, before calling `insert_try_to_send`, verify that `movetx.input[0].previous_output == deposit_outpoint`, returning `Status::invalid_argument` on mismatch, so the recorded deposit attribution always matches the actual spent outpoint.

### Proof of Concept
1. Obtain any validly-signed `move_to_vault` transaction `T` (e.g., observed on the network for deposit outpoint `D1`).
2. Call the aggregator's unauthenticated `SendMoveToVaultTx` RPC with `raw_tx = T` and `deposit_outpoint = D2` (an unrelated deposit outpoint).
3. Observe that the structural checks (input/output count, amounts, scriptpubkeys) pass since they only inspect `T`'s own outputs, and the DB now records `TxMetadata{ deposit_outpoint: D2 }` associated with `T`'s txid, even though `T` actually spends `D1`.

*Note: full exploitation impact (e.g., whether this can be leveraged into duplicate reimbursement credit or a frozen vault) depends on downstream consumers of `get_move_to_vault_txid_from_citrea_deposit`/`TxMetadata.deposit_outpoint` that were not fully traced in this session due to iteration limits; a Devin session with full repo access could confirm the exact blast radius by tracing all readers of this DB field.*

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
