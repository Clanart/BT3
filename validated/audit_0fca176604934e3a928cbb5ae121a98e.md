### Title
Unbounded byte-index reads in CLVM canonical-form checker can raise unhandled `IndexError` on malformed spend bundles - ([File: chia/full_node/mempool_manager.py])

### Summary
The GoBGP advisory describes a flowspec NLRI parser that reads fixed-size fields from a buffer without first confirming enough bytes remain, causing a crash when fewer than 20 bytes are supplied. The Chia analog is `is_clvm_canonical()` / `is_atom_canonical()` in [1](#0-0) , which walks an attacker-supplied CLVM byte buffer (a spend bundle's puzzle reveal / solution) and repeatedly indexes into it (`clvm_buffer[offset]`, and the multi-byte length-prefix loop in `is_atom_canonical`) without validating that `offset` stays within `len(clvm_buffer)` before each read.

### Finding Description
`is_atom_canonical()` computes a length-prefix size (`prefix_len`, 0–5 bytes) purely from the high bits of the first byte at `offset`, then loops `prefix_len` times reading `clvm_buffer[offset]` to build `atom_len`: [2](#0-1) 
There is no check that `offset + prefix_len < len(clvm_buffer)` before these reads. If the buffer ends in the middle of a multi-byte length-prefix atom header, indexing past the end of a `bytes` object raises `IndexError`.

`is_clvm_canonical()` has the same pattern in its main loop: [3](#0-2) 
`b = clvm_buffer[offset]` is called on each loop iteration with no bound check that `offset < len(clvm_buffer)`; a truncated pair/atom sequence (e.g. ending right after a `0xFF` pair marker, or with a partially-declared long atom) causes this to index out of bounds.

This mirrors the GoBGP CWE-1284 root cause exactly: a length-prefixed wire format is parsed by trusting the declared/derived length without validating that the underlying buffer actually contains that many remaining bytes, and the resulting out-of-range access is not caught before it manifests as an unhandled exception.

### Impact Explanation
Both functions are reachable directly from spend-bundle content submitted by an unprivileged peer/wallet client. If the caller path that invokes `is_clvm_canonical()`/`is_atom_canonical()` during spend-bundle admission does not wrap the call in a `try/except` for `IndexError` (only `AssertionError`/`ValueError` appear to be anticipated by the code's own asserts, e.g. the `assert clvm_buffer != b""` guard), a single malformed/truncated CLVM buffer in a submitted spend bundle can throw an uncaught `IndexError` inside the mempool-manager's spend-bundle admission pipeline, aborting validation of that transaction path unexpectedly rather than being rejected with a clean `Err`/`ValidationError`. This is a spend-triggered transaction-processing halt condition local to bundle intake — a denial-of-service class issue analogous to the referenced CVE, though bounded to Python-level exception propagation rather than the memory-unsafety of the Go original.

### Likelihood Explanation
Likelihood is high for triggering the exception itself, since any unprivileged submitter can craft a CLVM buffer (e.g., a puzzle reveal or solution with a byte sequence beginning `0xFF` or a long-atom prefix byte) that is truncated right before the parser expects more bytes; no signature or special privilege is needed to reach this parsing step. What is not fully confirmed from the available code is whether the immediate caller of `is_clvm_canonical()` already wraps it in a broad exception handler that would downgrade the `IndexError` into an ordinary rejection — this needs to be verified against the exact caller in the spend-bundle admission flow before treating this as a confirmed DoS rather than a benign parsing crash.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` and `is_clvm_canonical()` before each `clvm_buffer[offset]` access (e.g., raise/return a well-defined rejection such as `False`/`ValueError` when `offset >= len(clvm_buffer)`), so truncated CLVM buffers are turned into a normal validation failure instead of an unhandled `IndexError`. Additionally, audit and confirm that all call sites of these two functions in the mempool admission path catch `IndexError` (or that the functions themselves never raise it) so that malformed spend-bundle content cannot escape as an uncaught exception during transaction processing.

### Proof of Concept
Construct a spend bundle whose puzzle reveal / solution CLVM buffer is truncated mid-length-prefix, e.g. a buffer ending in `b"\xf8"` (declares a 4-byte length prefix per the mask table in `is_atom_canonical`) with zero trailing bytes, or a buffer consisting solely of `b"\xff"` (a pair marker with no following atoms) passed to `is_clvm_canonical()`:
```python
from chia.full_node.mempool_manager import is_clvm_canonical
is_clvm_canonical(b"\xff")  # loop reads clvm_buffer[1] -> IndexError, unhandled
```
Submit this as part of a spend bundle's serialized puzzle reveal/solution through the standard `push_tx`/mempool admission RPC path; if the calling code does not catch `IndexError`, the admission call raises unexpectedly instead of returning a clean `MempoolInclusionStatus`/`Err` result.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
