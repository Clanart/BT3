### Title
Submodule initialization can silently re-enable Git's blocked `file://` transport, letting a malicious repo exfiltrate local files - (File: `app/src/lib/git/submodule.ts`)

### Summary
Git hardened itself (CVE-2022-39253) by disabling the `file://` transport for submodules by default, because a malicious repository can define a submodule URL such as `file:///home/victim/.ssh` and have Git silently "clone" that local path — including its git-controlled files, hooks, and contents — into the working tree during `submodule update --init --recursive`. GitHub Desktop's `updateSubmodulesAfterOperation` function reintroduces this disabled transport by conditionally invoking `-c protocol.file.allow=always` [1](#0-0) , and this flag is threaded through `checkoutBranch` / `checkoutCommit` via an `allowFileProtocol` parameter [2](#0-1) .

### Finding Description
Git's `protocol.file.allow` guard is the exact analog of the missing `onlyOwner` check in the original report: it is the mechanism meant to prevent an untrusted, attacker-supplied object (here, a `.gitmodules` entry inside a cloned/fetched repository) from controlling a privileged operation (reading arbitrary local paths as a git remote). GitHub Desktop's `updateSubmodulesAfterOperation` explicitly re-enables this disabled transport when `allowFileProtocol` is `true`: [3](#0-2) 

That parameter is a plain boolean threaded from `checkoutBranch`/`checkoutCommit` down into the submodule update call with no independent verification of trust for the submodule URLs being initialized [2](#0-1) . If any UI code path that operates on a repository controlled or influenced by an attacker (e.g. a branch checked out after opening a link via the `x-github-client://openRepo/...` deep link, cf. `parseAppURL`/`openBranchNameFromUrl` in `dispatcher.ts` [4](#0-3) ) calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`, then a `.gitmodules` file with a `file://` (or UNC, on Windows) submodule URL pointing outside the repo would let Git copy the contents of that local path into the working directory as if it were a normal submodule.

The only confirmed use of `protocol.file.allow=always` I found is in test fixtures/helpers, e.g. `app/test/helpers/repositories.ts:299-309` and `app/test/unit/git/pull/pull-test.ts`, which deliberately set it up to simulate legitimate local submodules. **I was not able to confirm, in the time available, a production call site (dispatcher/app-store) that passes `allowFileProtocol=true` for a repository whose content originates from an untrusted remote** rather than a locally-created test/dev repository. This is the critical missing piece needed to promote this from "reintroduced dangerous capability" to "confirmed remotely triggerable vulnerability."

### Impact Explanation
If reachable from an attacker-controlled repo (clone, fetch, or "Open in Desktop" branch/PR checkout), this would allow silent disclosure of local files (SSH keys, credentials, config files) into the tracked working directory, and potentially corruption of what the user later commits/pushes — matching the "silent corruption of what the user commits" and "credential exfiltration" impact classes in scope.

### Likelihood Explanation
Likelihood is uncertain without confirming a reachable caller with `allowFileProtocol=true`. The presence of the flag and its wiring through submodule update strongly suggests it exists for a specific feature (e.g., allowing local nested repositories/monorepo tooling), which increases the risk that it could be enabled on a path that also handles untrusted remote content.

### Recommendation
- Audit every call site of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is `true` only for repositories/operations that are fully local and never for repositories obtained via clone/fetch/deep-link/PR checkout from a remote.
- If `allowFileProtocol` must be enabled for some feature, restrict it to submodule URLs that resolve within the same superproject boundary (equivalent to `resolveWithin` checks already used elsewhere, e.g. `app/src/lib/path.ts:95-100`), rather than allowing arbitrary local/UNC paths.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file:
```
[submodule "evil"]
    path = evil
    url = file:///Users/victim/.ssh
```
2. Victim opens/clones this repository in GitHub Desktop, or opens a branch/PR link that triggers `openBranchNameFromUrl` → `checkoutBranch(..., allowFileProtocol=true)` (path unconfirmed).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, causing Git to treat `/Users/victim/.ssh` as a git repository and copy its contents into `evil/` in the working tree.
4. The victim's private keys are now embedded in their working directory and could be committed/pushed, or read by any tooling that processes the repo.

**Note:** Because I could not verify a concrete attacker-reachable call site setting `allowFileProtocol=true` within the remaining search budget, this should be treated as a "verify-before-report" finding rather than a fully confirmed vulnerability. A background Devin session with full codebase access should grep all call sites of `allowFileProtocol` in `app/src/lib/stores/`, `app/src/ui/dispatcher/dispatcher.ts`, and `app/src/lib/git/pull.ts`/`fetch.ts` to determine whether any untrusted-remote-triggered flow sets this to `true`.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
