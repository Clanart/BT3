## Analysis

`SimplexPaymaster.sol` converts gas costs to ERC-20 stablecoin amounts using raw Chainlink `AggregatorV3Interface` price feeds, checking only the feed's own staleness window (`maxOracleAge`) and a non-positive-answer guard — the exact "just check `updatedAt`" pattern the M-13 report warns is insufficient on Arbitrum-class L2s, where price feed liveness is coupled to sequencer liveness. Hyperbridge explicitly supports Arbitrum as a first-class deployment target (`modules/ismp/clients/arbitrum`, `modules/ismp/clients/ismp-arbitrum`, `tesseract/consensus/arb-host`), and `SimplexPaymaster` is an upgradeable, permissionless ERC-4337 paymaster meant to be deployed to "any chain with a Chainlink feed" — its own comments call out BSC/Base/Ethereum heartbeats explicitly, confirming multi-chain, including L2, deployment intent. Nowhere in the contract is there an L2 sequencer-uptime check analogous to Chainlink's recommended `SequencerUptimeFeed`. [1](#0-0) [2](#0-1) 

### Title
Missing L2 Sequencer-Uptime Check in `SimplexPaymaster` Oracle Pricing — ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice()` only validates a Chainlink feed's own `updatedAt` timestamp against `maxOracleAge`; it never checks whether the underlying L2's sequencer was recently down (or is down), as recommended by Chainlink for any L2 (including Arbitrum, which Hyperbridge natively supports via its Arbitrum consensus client). This allows gas-to-token pricing (used both in `_fetchDetails`/`_tokenPrice` for every UserOp and in the treasury-triggered `swapAndDeposit`) to rely on a price that is technically "fresh enough" by `updatedAt` but stale relative to real market conditions during/after a sequencer outage.

### Finding Description
`_getOraclePrice` is the sole gate protecting every price read in the contract: [1](#0-0) 

It is called from `_tokenPrice` (used by `_fetchDetails`, invoked on every `_validatePaymasterUserOp`) and from `swapAndDeposit`: [3](#0-2) [4](#0-3) 

The only defense is `block.timestamp - updatedAt > maxOracleAge`. On Arbitrum-class rollups, when the sequencer stops posting batches, oracle keeper transactions that update `latestRoundData()` also stop landing, but `block.timestamp` on many L2s (and definitely once the sequencer resumes and catches up) does not track wall-clock market movement 1:1 with the feed's `updatedAt` staleness window — an attacker can submit `UserOp`s through the paymaster the moment the sequencer resumes (or via the L1 delayed-inbox path during an outage) while the feed is still within `maxOracleAge` but the true price has already moved materially (e.g., a native-asset or stablecoin price shock during the outage window). This is functionally identical to the Chainlink-documented Arbitrum sequencer risk cited in the source report: staleness-by-timestamp alone is not sufficient; a sequencer-uptime feed is required to detect the outage/grace-period condition that `updatedAt` cannot capture.

### Impact Explanation
Every unprivileged UserOp sender chooses `tokenPrice` implicitly through `_fetchDetails`, which prices the ERC-20 gas payment against a potentially mispriced-but-"fresh" oracle read. If the real off-chain price of the token or native asset has moved during a sequencer disruption, users can pay for gas with an outdated favorable rate, causing the paymaster to under-charge relative to actual gas expenditure — direct loss of paymaster-held funds. The same stale price feeds `swapAndDeposit`'s `expectedWei`/`amountOutMin` computation, so the treasury-only swap can also execute at a manipulated rate, though that path is gated to `treasury` and thus lower likelihood.

### Likelihood Explanation
The paymaster's `_validatePaymasterUserOp`/`_fetchDetails` path is a fully public entrypoint — any address can submit an ERC-4337 UserOp using this paymaster, with no privileged actor, relayer, or governance action required. The only precondition is that the deployment chain is an L2 with sequencer-dependent oracle updates (which Hyperbridge explicitly supports via Arbitrum) and that a sequencer disruption or restart window coincides with a real price move within the `maxOracleAge` tolerance (up to `MAX_ORACLE_AGE` = 7 days, or per-chain configured value). This is a realistic, self-triggerable condition rather than a contrived edge case.

### Recommendation
Add an L2 sequencer-uptime check (Chainlink `SequencerUptimeFeed`, or the chain-appropriate equivalent) alongside the existing `updatedAt`/`answer` checks in `_getOraclePrice`, requiring both that the sequencer is currently up and that a grace period has elapsed since it last came back online before trusting any price read, mirroring Chainlink's documented L2 data-feed guidance.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an Arbitrum-family chain configured with `maxOracleAge` = e.g. 24 hours (as the contract's own comments anticipate for some stablecoin feeds).
2. Simulate/await a sequencer outage or restart event where the Chainlink token/USD or native/USD feed's `updatedAt` is still within `maxOracleAge`, but the true market price has diverged (e.g., due to a stablecoin depeg or native asset price move during the outage).
3. Submit a UserOp through the paymaster (mode `0x01`/`0x00` in `paymasterData`) sized to maximize the token amount charged relative to actual gas consumed, using the stale-but-"fresh" price returned by `_tokenPrice`/`_getOraclePrice`.
4. Observe the paymaster settles gas at the stale rate, resulting in the paymaster over-refunding value relative to the token actually collected — net fund loss to the paymaster/treasury.

Note: I could not find any explicit deployment record confirming `SimplexPaymaster` is deployed specifically on Arbitrum mainnet (the mainnet contract-address docs reference it, but I was not able to fully enumerate the per-chain deployment list within the available iterations) — the finding rests on the contract's documented multi-EVM-chain design intent plus Hyperbridge's confirmed native Arbitrum support elsewhere in the codebase. A Devin session with full repo/file access could confirm exact deployment targets in `docs/content/developers/evm/contract-addresses/mainnet.mdx` and `evm/script/DeploySimplexPaymaster.s.sol`.

    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
