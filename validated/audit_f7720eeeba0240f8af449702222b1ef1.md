### Title
Reward-per-share front-running on `mWOMSVBaseRewarder.queueNewRewards` via `mWomSV.lock`/`MasterMagpie.depositMWomSVFor`, compounded by dead `_calExpireForfeit` - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
An unprivileged holder of mWOM can observe a pending `queueNewRewards`/`donateRewards` call to `mWOMSVBaseRewarder` and front-run it by locking mWOM via `mWomSV.lock()` (which calls `MasterMagpie.depositMWomSVFor`), instantly inflating their share of `totalStaked()` right before the reward-per-share bump, then immediately claim a disproportionate share of the reward via `multiclaim`/`getRewards`. Because `_calExpireForfeit` is dead code that always returns `0`, there is no penalty mechanism discouraging this just-in-time entry/exit, so the extracted yield is pure, unclawed-back profit.

### Finding Description
`mWomSV.lock()` calls `_lock()` which calls `IMasterMagpie(masterMagpie).depositMWomSVFor(_amount, _for)` [1](#0-0) , which in `MasterMagpie` immediately increases `user.amount` for the mWomSV pool via `_deposit` [2](#0-1) . `mWOMSVBaseRewarder.balanceOf()` reads this live `user.amount`/`staked` value from `MasterMagpie.stakingInfo` [3](#0-2) , so a deposit takes effect on the attacker's share of `totalStaked()` immediately, with no vesting or minimum holding period.

When `queueNewRewards` (restricted to `onlyManager`, e.g. the reward manager pushing WOM bribes) or the permissionless `donateRewards` executes, `_provisionReward` bumps `rewardInfo.rewardPerTokenStored` proportionally to `_amountReward / totalStaked()` [4](#0-3) . Any account whose `userRewardPerTokenPaid` was last synced *before* this bump (i.e., anyone who deposited right before the reward lands) captures its full proportional share via `_earned` on the next claim [5](#0-4) , even though they had zero economic exposure to the pool beforehand.

Normally, protocols mitigate this front-running/last-second-deposit pattern with an exit-forfeiture (haircut) mechanism on rewards claimed shortly after entry. `mWOMSVBaseRewarder` has such a mechanism, `_calExpireForfeit`, but it is dead code: `rewardableAmount` is initialized to `_amount` and never modified before the check `if (rewardableAmount > _amount) revert`, so `forfeitAmount = _amount - rewardableAmount` is always `0` [6](#0-5) . This is invoked from `_sendReward` on every `getReward`/`getRewards` claim, and always returns zero forfeiture [7](#0-6) . Thus there is no penalty at all on immediate claim-and-exit behavior — the anti-front-run safeguard exists in name only.

Existing modifiers (`onlyMasterMagpie`, `updateReward`, `nonReentrant`) only protect against reentrancy and unauthorized callers; none of them address time-weighted entitlement to a lump-sum reward injection, and `whenNotPaused`/`onlyManager` on `queueNewRewards` don't prevent an unprivileged attacker from observing and front-running the transaction in the public mempool.

### Impact Explanation
This enables theft of unclaimed/pending yield (bribes/rewards routed through `mWOMSVBaseRewarder`) at the expense of long-term mWomSV lockers, whose entitled share of the reward-per-share bump is diluted by the attacker's momentary stake. This matches the "theft of unclaimed yield" impact class, compounded by the fact that the attacker's principal is later withdrawn (after the standard cooldown via `startUnlock`/`unlock`) with zero forfeiture, since `_calExpireForfeit` is inert.

### Likelihood Explanation
Feasibility depends on the attacker being able to observe (front-run) a pending `queueNewRewards`/`donateRewards` transaction in the mempool before it lands, and having enough mWOM capital to meaningfully dilute `totalStaked()` at that moment. This is realistic on public chains without private-mempool relay for the reward manager's harvest/bribe transactions, and capital can be sized precisely for the observed reward amount. The attack is repeatable every time a reward/bribe distribution occurs. Note that withdrawing principal still requires going through `startUnlock` + `coolDownInSecs` + `unlock` [8](#0-7) , but claiming the disproportionate reward itself via `multiclaim`/`getRewards` is immediate and does not require unlocking, so the profit-taking step has effectively no delay.

### Recommendation
Restore a functioning exit-forfeiture in `_calExpireForfeit` (e.g., forfeit rewards accrued proportional to time-since-deposit below some minimum staking duration), and/or introduce a deposit-to-reward-eligibility delay (e.g., only balances held before a reward snapshot are eligible for that reward), similar to checkpoint/snapshot-based reward accounting used to prevent last-block deposit sniping.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `MasterMagpie`, `mWOMSVBaseRewarder` wired together as in production; seed an existing "honest" locker (`user1`) with a locked mWOM position established well in advance.
2. Simulate a pending reward: prepare a `queueNewRewards(amount, rewardToken)` call from the `rewardManager` but do not yet mine it (mempool simulation = just call it in a later step to model front-run ordering).
3. Attacker (`atk`), holding only purchased mWOM, calls `mWomSV.lock(bigAmount)` immediately "before" the reward call, inflating `totalStaked()`.
4. Execute `mWOMSVBaseRewarder.queueNewRewards(amount, rewardToken)` (via manager) — assert `rewardPerTokenStored` increases based on post-front-run `totalStaked()`.
5. Attacker immediately calls `MasterMagpie.multiclaim` (or rewarder `getRewards`) and receives reward tokens; assert `atk`'s claimed amount / `amount` ≈ `bigAmount / totalStaked()`, disproportionate to any time held.
6. Attacker calls `mWomSV.startUnlock(bigAmount)`, warps `coolDownInSecs`, calls `unlock(slotIndex)`; assert full principal `bigAmount` returned and `calExpireForfeit`/forfeit event never fired (zero forfeiture).
7. Assert net attacker profit (`claimedReward - gasCost`) is positive and strictly greater than the reward `user1` (long-term staker) receives proportionally to their actual time-weighted stake, demonstrating value extraction from legitimate stakers with zero clawback.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
