## Finding

### Title
Unchecked ERC20 return value in CosmWasm `EvmMsg::DelegateCallEvm` transfer flow leads to silent transfer failures - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The Sei CW20-wrapper contract's `transfer` and `transfer_from` handlers build a `DelegateCallEvm` message that invokes the underlying wrapped ERC20 contract's `transfer`/`transferFrom` function, but never inspect the ABI-encoded `bool` return value of that call. Any ERC20 token that follows the "silent failure" pattern (returns `false` instead of reverting on a failed transfer — a well-known non-compliant but common ERC20 behavior) will cause the CosmWasm layer to treat the operation as successful, emit success attributes, and finalize the response, even though no tokens moved.

### Finding Description
`transfer()` and `transfer_from()` in [1](#0-0)  build the raw ABI payload via `querier.erc20_transfer_payload(...)` and wrap it in `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, then unconditionally attach success attributes (`from`, `to`, `amount`) and return `Ok(res)`.

This message is routed through `EncodeDelegateCallEVM` into `MsgInternalEVMDelegateCall` [2](#0-1) , handled by `HandleInternalEVMDelegateCall`, which calls `k.CallEVM` [3](#0-2) . `CallEVM` only checks `res.Err != nil` (i.e., whether the EVM call reverted) and otherwise returns `res.ReturnData` as-is [4](#0-3) . Neither `CallEVM` nor the CW20 wrapper contract decodes and validates the returned `bool` from the ERC20 `transfer`/`transferFrom` ABI call.

Because a call that returns `false` (rather than reverting) does not set `res.Err`, this exactly matches the bug class described in the external report: an external token transfer's return value is not checked, so a failed transfer is treated as successful.

### Impact Explanation
If the wrapped ERC20 pointee returns `false` on failure instead of reverting (many real-world ERC20 tokens, and any bridged/pointer ERC20 contract without strict revert semantics), the CW20 wrapper will report a successful transfer via its emitted attributes and to callers relying on the Cosmos message result, while no value actually moved. This can be leveraged in CW20-composability integrations (e.g., DEXes, vaults) that trust the CW20 wrapper's execute-success semantics to credit balances or release funds, resulting in fund loss/inconsistent accounting for any wasm caller composing with this pointer path.

### Likelihood Explanation
This is reachable by any CosmWasm user/contract issuing `transfer`/`transfer_from` against the CW20-to-ERC20 wrapper for any target ERC20 token that uses non-reverting boolean failure semantics — no privileged access is required, only a standard wasm execute transaction.

### Recommendation
After the `DelegateCallEvm` sub-message executes, decode the ABI-encoded `bool` return value from the ERC20 `transfer`/`transferFrom` call and fail the CosmWasm execution (or use a reply handler with `SubMsg` + `ReplyOn::Success` combined with explicit boolean decoding) if the decoded result is `false`, rather than relying solely on the absence of a revert.

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

func EncodeDelegateCallEVM(rawMsg json.RawMessage, sender sdk.AccAddress, info wasmvmtypes.MessageInfo, codeInfo wasmtypes.CodeInfo) ([]sdk.Msg, error) {
	encodedCallEVM := bindings.DelegateCallEVM{}
	if err := json.Unmarshal(rawMsg, &encodedCallEVM); err != nil {
		return []sdk.Msg{}, err
	}
	decodedData, err := base64.StdEncoding.DecodeString(encodedCallEVM.Data)
	if err != nil {
		return []sdk.Msg{}, err
	}
	s := sender
	if origSender, err := sdk.AccAddressFromBech32(info.Sender); err == nil {
		s = origSender
	}
	internalCallEVMMsg := types.MsgInternalEVMDelegateCall{
		Sender:       s.String(),
		To:           encodedCallEVM.To,
		CodeHash:     codeInfo.CodeHash,
		Data:         decodedData,
		FromContract: sender.String(),
	}
	return []sdk.Msg{&internalCallEVMMsg}, nil
}

func (k *Keeper) HandleInternalEVMDelegateCall(ctx sdk.Context, req *types.MsgInternalEVMDelegateCall) (*sdk.Result, error) {
	var to *common.Address
	if req.To != "" {
		addr := common.HexToAddress(req.To)
		to = &addr
	} else {
		return nil, errors.New("cannot use a CosmWasm contract to delegate-create an EVM contract")
	}
	addr, _, exists := k.GetAnyPointerInfo(ctx, types.PointerReverseRegistryKey(common.BytesToAddress([]byte(req.FromContract))))
	if !exists || common.BytesToAddress(addr).Cmp(*to) != 0 {
		return nil, errors.New("only pointer contract can make delegatecalls")
	}
	zeroInt := sdk.ZeroInt()
	senderAddr, err := sdk.AccAddressFromBech32(req.Sender)
	if err != nil {
		return nil, err
	}
	// delegatecall caller must be associated; otherwise any state change on EVM contract will be lost
	// after they asssociate.
	senderEvmAddr, found := k.GetEVMAddress(ctx, senderAddr)
	if !found {
		err := types.NewAssociationMissingErr(req.Sender)
		evmKeeperMetrics.associationError.Add(ctx.Context(), 1, otelmetric.WithAttributes(attribute.String("scenario", "evm_handle_internal_evm_delegate_call"), attribute.String("type", err.AddressType())))
		return nil, err
	}
	ret, err := k.CallEVM(ctx, senderEvmAddr, to, &zeroInt, req.Data)
	if err != nil {
		return nil, err
	}
	return &sdk.Result{Data: ret}, nil
}
