## Title
Naive BEEFY MMR path accepts a stale `latest_mmr_leaf`, suppressing authority-set rotation while advancing `latest_beefy_height` - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`verify_mmr_update_proof`/`verify_mmr_leaf` in `modules/consensus/beefy/verifier/src/lib.rs` verify that `mmr.latest_mmr_leaf` is included in the signed MMR root, but never check that this leaf is the one actually appended at `commitment.block_number` (i.e., `parent_number + 1 == block_number`). Because an MMR is append-only, an older leaf remains provable against a newer root, so this check is a real, exploitable gap.

### Finding Description
`verify_mmr_leaf` (lib.rs:225-256) derives the MMR size purely from the attacker-supplied `leaf_index`/`parent_number_and_hash` inside `mmr.latest_mmr_leaf` [1](#0-0) , and never compares `latest_mmr_leaf.parent_number_and_hash.0 + 1` against `commitment.block_number`. `verify_mmr_update_proof` then unconditionally advances `trusted_state.latest_beefy_height` to `latest_height` (the commitment's `block_number`) and only rotates `next_authorities`/`current_authorities` if `mmr.latest_mmr_leaf.beefy_next_authority_set.id > trusted_state.next_authorities.id` [2](#0-1) .

This is explicitly contrasted with the SP1 path, `verify_sp1_consensus` (`modules/consensus/beefy/verifier/src/sp1.rs`), which contains a dedicated freshness check with an explanatory comment: "An mmr is append-only, so a historical leaf also proves against the commitment's root. Accepting one would advance `latest_beefy_height` while replaying an old leaf, suppressing the rotation below and stranding the client on a set the relay chain has retired." [3](#0-2) . The `Error::StaleMmrLeaf` variant's doc comment in `error.rs` describes this exact hazard generically ("the verifier"), not scoped to SP1 only [4](#0-3) , indicating the intended invariant applies to both proof types but is only implemented for one.

A dedicated regression test, `rejects_sp1_proof_carrying_a_stale_mmr_leaf`, exists for the SP1 path and asserts `Error::StaleMmrLeaf` is returned when an older leaf is substituted [5](#0-4) . No equivalent test exists for `verify_mmr_update_proof`/naive proofs in `test.rs`.

The naive proof type (`PROOF_TYPE_NAIVE = 0x00`) is a first-class, non-privileged proof type accepted by the ismp-beefy client dispatcher alongside `PROOF_TYPE_SP1` [6](#0-5) , and `PROOF_TYPE_NAIVE` is defined in `pallet-beefy-consensus-proofs`'s types module as a live, dispatchable proof kind [7](#0-6) , so this is a production, unprivileged-relayer-submittable code path, not a test-only artifact.

The equivalent Solidity `EcdsaBeefy.sol` (the naive on-chain BEEFY client) has the same gap: `verifyMmrLeaf` computes `leafCount` from `relay.latestMmrLeaf.parentNumber` rather than from `commitment.blockNumber` [8](#0-7) , and `verifyMmrUpdateProof` likewise unconditionally sets `trustedState.latestHeight = latestHeight` and only rotates authorities if `relayProof.latestMmrLeaf.nextAuthoritySet.id > trustedState.nextAuthoritySet.id` [9](#0-8) , confirming this is a systemic gap in the naive/ECDSA verifier design across both Rust and Solidity implementations, not a one-off omission.

### Impact Explanation
A malicious (but otherwise unprivileged) relayer submitting a naive BEEFY proof can select an older, already-superseded `latest_mmr_leaf` while still using the current, freshly signed commitment/root for a later `block_number`. The MMR inclusion proof for that older leaf against the new root will verify successfully because MMR trees are append-only and never invalidate historical leaf proofs. This lets an attacker:
- Advance `trusted_state.latest_beefy_height` to the new height (satisfying `StaleHeight` checks for all future proofs at or below that height).
- Suppress a pending authority-set rotation, since the stale leaf's `beefy_next_authority_set` is older and may not exceed `trusted_state.next_authorities.id`.
- Strand the light client's `current_authorities`/`next_authorities` on a retired validator set, later allowing acceptance of signed commitments from an authority set the relay chain has already rotated away from — a false-proof/false-state-acceptance condition, matching the "false proof/state acceptance" impact family in scope.

### Likelihood Explanation
The attack requires only a normal MMR inclusion proof construction using a historical leaf and a legitimately signed (fresh) BEEFY commitment — no privileged access, no compromised relayer infrastructure, and no malformed cryptography is needed. Any party that can submit an unprivileged naive BEEFY consensus proof (a first-class supported proof type per `allowed_proof_types`/`PROOF_TYPE_NAIVE`) can attempt this.

### Recommendation
Add the same freshness check used in `verify_sp1_consensus` to `verify_mmr_update_proof` in `lib.rs`: reject the proof (e.g., with `Error::StaleMmrLeaf`) unless `mmr.latest_mmr_leaf.parent_number_and_hash.0.saturating_add(1) == commitment.block_number`. Apply the equivalent fix to `EcdsaBeefy.sol`'s `verifyMmrUpdateProof`/`verifyMmrLeaf` by deriving `leafCount` from `commitment.blockNumber` (or asserting `parentNumber + 1 == commitment.blockNumber`) rather than from the leaf's own `parentNumber`.

### Proof of Concept
1. Trusted state at height `H`, current authority set `A`, next authority set `B` (about to rotate to `C` at block `H+K`).
2. At block `H+K`, the relay chain finalizes a new BEEFY commitment/root that includes a new MMR leaf whose `beefy_next_authority_set.id == C`.
3. Attacker constructs an `MmrProof` using this fresh, correctly-signed `signed_commitment` (so `commitment.block_number = H+K` and `mmr_root` matches the real root), but substitutes `latest_mmr_leaf` with an **older** leaf (e.g., appended at some `H+K-500`) whose `beefy_next_authority_set.id` is still `B` (i.e., pre-rotation), along with a valid MMR inclusion proof/`leaf_index` for that older leaf against the same (newer) `mmr_root`.
4. Submit via `verify_mmr_update_proof`: signature/authority-membership checks pass (signed by set `A`/`B` as appropriate), `verify_mmr_leaf` succeeds because the older leaf is still included in the append-only tree, and the function returns success — advancing `trusted_state.latest_beefy_height` to `H+K` while leaving `next_authorities = B` instead of rotating to `C`.
5. This exactly mirrors `rejects_sp1_proof_carrying_a_stale_mmr_leaf` in `test.rs` [10](#0-9) , but against `verify_mmr_update_proof` instead of `verify_sp1_consensus` — where the SP1 path correctly rejects with `Error::StaleMmrLeaf` and the naive path does not.
