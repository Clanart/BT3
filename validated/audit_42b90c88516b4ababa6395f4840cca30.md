### Title
Uncontrolled recursion in `AccountKeyRoleBased` RLP decoding allows resource-exhaustion DoS via a single AccountUpdate transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its role sub-keys through `rlp.DecodeBytes`, and if a sub-key is itself typed as `AccountKeyTypeRoleBased`, decoding recurses into `AccountKeyRoleBased.DecodeRLP` again with no depth limit. The check that rejects nested role-based keys (`ErrNestedCompositeType` / "roleBasedKey cannot contains a roleBasedKey") is only enforced *after* decoding completes, inside `CheckInstallable`/`checkAccountKeyZeroValues`, not during decode. An attacker can therefore craft a `TxTypeAccountUpdate` (or fee-delegated variant) transaction whose `Key` field contains a deeply/recursively nested `AccountKeyRoleBased` structure, and simply submitting this transaction (e.g., via public RPC `eth_sendRawTransaction`) forces every node that decodes it — during tx-pool ingestion and block/tx processing — to perform unbounded recursive decoding before any nesting-depth validation occurs.

### Impact Explanation
An unprivileged transaction sender can submit a single crafted `AccountUpdate`-family transaction whose `Key` payload nests `AccountKeyRoleBased` many levels deep. Because Go grows goroutine stacks dynamically, the immediate risk is not necessarily a hard crash but severe, attacker-amplified CPU/memory consumption (allocating a new `AccountKey` object and slice per nesting level, `[][]byte` per level, plus additional `rlp.DecodeBytes` overhead) on every node that decodes the transaction — including all peers receiving it via p2p relay and any node serving `DecodeAccountKey`/`EncodeAccountKey` RPCs. In the worst case this can produce out-of-memory conditions or multi-second decode stalls per transaction, which is a network-wide Denial of Service vector reachable from a single unauthenticated transaction, matching CWE-400/674 (Uncontrolled Resource Consumption / Uncontrolled Recursion).

### Likelihood Explanation
Likelihood is high for reachability (any public RPC caller can submit a raw signed transaction of type `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate*`), but I was unable to fully confirm within the available context whether: (1) global transaction/RLP-stream size limits (e.g., `tx_pool.go` max tx size) sufficiently cap the achievable nesting depth to a level that is not practically harmful, and (2) whether `rlp.Stream`'s general list-decoding machinery imposes any independent depth/size ceiling that would bound worst-case recursion before it reaches the `AccountKeyRoleBased` path. I searched for `maxTxSize`/related constants but did not get conclusive line-level confirmation of the effective per-transaction size cap or RLP stream depth guard in this codebase snapshot. A background engineer should verify the maximum raw transaction size accepted by `blockchain/tx_pool.go` and by the P2P/RPC ingestion layer, and empirically measure how many nesting levels of `AccountKeyRoleBased` fit within that size, to determine whether the resulting recursion depth/CPU cost is actually severe enough to constitute a practical DoS.

### Recommendation
Add an explicit depth counter/limit to `AccountKeyRoleBased.DecodeRLP` (and to the generic `AccountKeySerializer.DecodeRLP` dispatch it depends on) so that any attempt to decode a role-based key whose sub-key is itself of type `AccountKeyTypeRoleBased` is rejected immediately during decoding, rather than deferring the "no nested composite key" check to `CheckInstallable`/`checkAccountKeyZeroValues`. This mirrors the `IsCompositeType`/`ErrNestedCompositeType` check already present but currently applied too late in the pipeline. Threading a `depth` parameter through `DecodeRLP` (or exposing a package-level decode entrypoint that tracks recursion depth) and erroring out as soon as depth > 1 would close the recursion path with minimal disruption, since nested role-based keys are already disallowed by protocol semantics.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value `K0` containing three `AccountKeyPublic` sub-keys (valid, minimal).
2. Construct `K1 = AccountKeyRoleBased{K0}`, `K2 = AccountKeyRoleBased{K1}`, ... iteratively nesting `Kn = AccountKeyRoleBased{K(n-1)}` for as many levels as fit under the transaction size limit (this needs to be empirically determined against `blockchain/tx_pool.go`'s size cap, which I could not fully confirm from this context).
3. RLP-encode `Kn` via `AccountKeyRoleBased.EncodeRLP` (`blockchain/types/accountkey/account_key_role_based.go:110-118`) and embed it as the `Key` field of a `TxTypeAccountUpdate` transaction.
4. Sign the transaction with any valid key and submit it via `eth_sendRawTransaction`/`klay_sendRawTransaction` to a public RPC endpoint, or directly call `KaiaAPI.DecodeAccountKey` (`api/api_kaia.go:166-173`) with the encoded bytes.
5. Observe that `rlp.DecodeBytes` recurses `n` times through `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` before the transaction is ever checked by `CheckInstallable`, consuming CPU/memory proportional to `n` on every node that decodes it (mempool admission, propagation, and block processing), constituting the resource-consumption DoS.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
}
