## Finding

The core of the ETH‑refund bug report is: a **security bypass mechanism is used to force an unsafe transfer past a guard that the underlying primitive intentionally added**, and the caller does this unconditionally, on behalf of an untrusted actor. The Desktop analog is in the Git clone flow, where Desktop explicitly disables Git's own built‑in *clone protection* feature for every clone it performs — including recursive clones triggered by attacker‑controlled URLs (manual clone, and the `x-github-client://openRepo/<url>` deep link).

### Title
Recursive clone force-disables Git's built-in clone-protection guard (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling RCE-class submodule attacks from a malicious repository - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for every `git clone` invocation and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while also passing `--recursive`. [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the internal flag Git itself uses to gate the clone-time protections added to fix the case‑folding/Unicode‑normalization submodule attack class (the RCE fixed upstream as part of Git's 2024 clone-protection hardening, related to CVE‑2024‑32002/32004/32020/32021). That protection exists specifically to stop a malicious repository — with a submodule whose name collides with `.git` on case-insensitive or Unicode-normalizing filesystems (default on macOS/Windows) — from writing files (e.g. hook scripts) into the destination `.git` directory during a recursive clone, which would then be executed. By forcing this flag to `'false'`, Desktop is deliberately turning off the exact guard Git added to prevent exactly this kind of forced, attacker-triggered write/execution — mirroring the reported bug's pattern of forcing an unsafe path through a protective mechanism regardless of the recipient's (here, the local filesystem's) ability to safely receive it.

### Finding Description
The reported Solidity issue is: `forceSafeTransferETH()` is used to *force* value onto `msg.sender` even when that recipient cannot safely accept it, bypassing the natural failure/revert path that would otherwise let the caller choose a different, safe path. The broken invariant is "a protective failure mode (revert) is overridden by a mechanism that forces the unsafe outcome to happen anyway."

The same invariant is broken here: Git's `--recursive` clone path contains protections that are meant to *fail closed* (refuse the clone / refuse to check out) when a submodule structure attempts to write into `.git/` via a case-folding or Unicode-normalization collision. Desktop unconditionally sets: [2](#0-1) 
which disables this fail-closed protection for **every** clone, including:
- ordinary "Clone repository" from an arbitrary URL/GitHub org the user picked,
- and (per `app/src/lib/parse-app-url.ts` / `app/src/ui/dispatcher/dispatcher.ts`) the `open-repository-from-url` deep-link action reachable via `x-github-client://openRepo/<attacker-controlled-url>`, i.e. a link the user is lured into clicking. [3](#0-2) [4](#0-3) 

Because `--recursive` is always passed, an attacker who controls the cloned repository (any public repo, or a repo referenced by a crafted `openRepo` deep link) can craft a submodule tree designed to collide with `.git` under case-insensitive/Unicode-normalizing filesystem rules. With the upstream clone-time protection intentionally disabled by Desktop, the class of attack that protection exists to block is not mitigated by Desktop at all.

### Impact Explanation
If the underlying Git binary bundled with Desktop is otherwise vulnerable to the class of submodule/`.git`-collision attacks that `GIT_CLONE_PROTECTION_ACTIVE` was introduced to prevent, then simply cloning (or "Open in Desktop"-ing) a malicious, unprivileged, attacker-controlled repository could result in Desktop writing attacker-controlled files (e.g., hook scripts) into the destination `.git` directory and subsequently executing them — i.e., remote code execution purely from the act of opening a link/cloning a repo, with no other user action, credentials, or local access required. This squarely fits the "attacker controls a cloned/fetched repository ... resulting in code execution" impact category.

### Likelihood Explanation
The disabling is unconditional and silent — it happens on every clone, there is no opt-out, no user-facing warning, and no compensating check elsewhere in `clone.ts` (only `isClonePathSensitive()` is checked, which guards destination *path*, not submodule content). [5](#0-4) 
Exploitability ultimately depends on which Git version ships with Desktop (via `dugite`) and whether that version still contains a code path vulnerable absent this protection — but the fact that Desktop actively neutralizes a hardening flag that upstream Git added specifically for this attack class means Desktop is not relying on Git's own fail-closed default; it is explicitly opting back into the pre-fix behavior for all users, on all recursive clones.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default clone-protection behavior active (or explicitly set it to `'true'`) so that Git's built-in submodule/`.git`-collision defenses remain in effect during `--recursive` clones. If this override was added to work around a compatibility issue, gate it narrowly and only after independently re-validating submodule names/paths for `.git`-colliding entries before allowing recursive submodule checkout, rather than disabling Git's own guard wholesale.

### Proof of Concept
1. An attacker publishes a public Git repository (or crafts a URL for the `x-github-client://openRepo/<url>` deep link) containing a submodule configuration engineered to collide with `.git` under case-insensitive or Unicode-normalizing filesystem semantics (the same structural pattern used in the upstream Git clone-protection advisories).
2. A GitHub Desktop user clicks "Clone" (or clicks an "Open in Desktop" link pointing at the malicious URL).
3. Desktop calls `clone()`, which runs `git -c init.defaultBranch=... clone --recursive -- <attacker-url> <path>` with environment `GIT_CLONE_PROTECTION_ACTIVE=false` explicitly set. [1](#0-0) 
4. Because Desktop has explicitly turned off Git's clone-time protection, the submodule checkout proceeds without the guard that would otherwise refuse/abort the operation, allowing attacker-controlled content to be written into `.git/` (e.g., hooks) and executed as part of the recursive checkout — achieving code execution from merely cloning/opening the malicious repository.

*(Exact remote-code-execution reachability is contingent on the bundled Git/dugite version's underlying vulnerability status; this cannot be fully verified from the indexed source alone. What is verifiable and concerning regardless is that Desktop unconditionally force-disables a security-hardening environment variable that Git introduced specifically to prevent this attack class, for every clone including those driven by attacker-supplied URLs/deep links.)*

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
