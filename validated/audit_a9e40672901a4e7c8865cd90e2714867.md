### Title
`_addDeployment` overwrites the registered IntentGateway instance address with no check for outstanding escrow, permanently freezing pending cross-chain orders - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
This is a direct analog of the `TransmuterBuffer.setAlchemist` bug class: a governance-controlled function that switches a trusted counterparty address has no invariant check that all exposure (in this case, escrowed intent orders) tied to the *old* counterparty has been settled first. When the registered remote gateway address is rotated, orders still in flight against the previous address become permanently unauthenticatable and their escrow is stuck.

### Finding Description
`IntentsBase._addDeployment` unconditionally overwrites the trusted remote-gateway mapping used for authenticating incoming settlement messages: [1](#0-0) 

This function is invoked from `onAccept` when Hyperbridge dispatches a `NewDeployment` request: [2](#0-1) 

`_instances[keccak256(chain)]` is the sole source of truth used by `_instance()` to resolve where outbound settlement dispatches go, and by `_authenticate` (invoked on `RedeemEscrow`/`RefundEscrow` inbound messages) to decide whether an incoming settlement message is trusted: [3](#0-2) [4](#0-3) 

Just like `TransmuterBuffer.setAlchemist`, which flips `sources[alchemist]` to `false` with no check that `getAvailableFlow`/`getTotalCredit` are zero for the old Alchemist, `_addDeployment` flips the trusted gateway address for a state machine with no check that:
- no orders are currently escrowed (`_orders[commitment][token] != 0`) destined for/from that chain, and
- no in-flight `RedeemEscrow`/`RefundEscrow` messages are still expected from the address being replaced.

Once the mapping is rotated, `withdraw()` on the source chain will only accept a settlement message whose `incoming.request.from` equals the *new* `_instances` entry (via `_authenticate`). Any settlement message that a solver or destination gateway generates from the *old*, now-unregistered address will revert with `Unauthorized`, and the source-chain escrow entry in `_orders[commitment][token]` can never be released through the normal `RedeemEscrow`/`RefundEscrow` path.

### Impact Explanation
Funds escrowed for orders whose destination/source gateway registration changes underneath them become permanently locked: `withdraw()` cannot succeed because `_authenticate` will reject the settlement message from the stale gateway address, and there is no fallback recovery path in the contract. This is a direct fund-freeze/loss condition on user and solver funds held in `_orders`, matching the "stealing or loss of funds" and "logic attacks" categories in the bounty's impact gate.

### Likelihood Explanation
`NewDeployment` is a normal, expected operational action (e.g., redeploying/upgrading the counterpart IntentGateway on a remote chain, or correcting a misconfigured address) rather than a malicious or adversarial one — exactly analogous to how `setAlchemist` is a normal, expected admin action in the original report. Any redeployment while orders are still outstanding for that chain (a very plausible operational sequence, since there is no on-chain gate preventing it) triggers the freeze. No malicious peer, relayer, or leaked key is required — only the legitimate cross-chain governance flow operating without the missing invariant check, the same condition that made the original report valid despite being "admin-only."

### Recommendation
Before allowing `_addDeployment` (and generally before overwriting any `_instances[keccak256(chain)]` entry) to replace an existing non-zero gateway address for a state machine, require that all exposure to the old address is settled. Concretely:
- Track outstanding escrow count/amount per destination state machine (or per registered gateway address), and require it to be zero before allowing the instance address to change, or
- Keep a versioned/multi-valued mapping that still authenticates settlement messages from previously-registered gateway addresses until their associated orders are fully drained, rather than a single overwritable `address`.

### Proof of Concept
1. User places a cross-chain order on the source chain via `placeOrder`, escrowing tokens in `_orders[commitment][token]`, with `order.destination` pointing at chain `X` whose current registered instance is `gatewayOld` (`_instances[keccak256("X")] == gatewayOld`).
2. Before the order is filled/settled, Hyperbridge governance dispatches a `NewDeployment` request for chain `X` pointing to a redeployed gateway `gatewayNew`. `onAccept` → `_addDeployment` overwrites `_instances[keccak256("X")] = gatewayNew` with no check on outstanding `_orders` entries tied to chain `X`.
3. The solver fills the order on `gatewayOld` (destination chain) and the resulting `RedeemEscrow` settlement message is dispatched with `from = gatewayOld`.
4. On the source chain, `onAccept` → `_authenticate` compares `incoming.request.from` (`gatewayOld`) against the now-updated `_instances[keccak256("X")]` (`gatewayNew`) — mismatch — and reverts with `Unauthorized`.
5. The escrowed tokens for that commitment remain stuck in `_orders[commitment][token]` indefinitely; the source chain cannot process a valid settlement message referencing `gatewayOld` any longer, and there is no alternate recovery function.

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        }
    }
