### Title
Webhook `shop_domain` Not Covered by HMAC Verification Enables Cross-Shop Webhook Forgery - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates an incoming webhook by computing an HMAC over `request.raw_post` only, while the `shop_domain` value that downstream app code is expected to trust and act on is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. Because the same app secret is used to validate every shop's webhooks, any shop that has installed the app can obtain a genuinely-signed webhook for its own shop and then resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop, without invalidating the HMAC. This mirrors the reported `MerkleDistributor` issue, where a security-critical field (`rewardToken`) was excluded from the verification, letting an attacker substitute a value they control while the "verified" check still passes.

### Finding Description
`PayloadVerification#hmac_valid?` verifies only the raw body: [1](#0-0) 

`WebhookVerification#verify_request` calls this check exclusively against `request.raw_post`, and separately exposes a `shop_domain` helper that reads directly from the `X-Shopify-Shop-Domain` header, entirely outside the HMAC scope: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers using exactly this pattern — trusting `shop_domain` from the concern to route jobs by shop: [3](#0-2) 

Since `ShopifyApp.configuration.secret` (the app's client secret) is identical for every shop that installs the app, any shop is capable of producing a validly-HMAC'd body (by simply relaying a webhook Shopify already signed for them). The `X-Shopify-Shop-Domain` header carried alongside that body is not part of the signed material, so an attacker-controlled shop can swap in an arbitrary target domain and the `verify_request` check will still pass.

### Impact Explanation
An unrelated/anonymous merchant who has installed the app can cause the app to process attacker-supplied webhook body content under another shop's identity (`shop_domain`). Depending on the job implementation (matching the documented pattern), this leads to cross-shop data injection/confusion: a victim shop's records could be updated using data that actually originated from the attacker's shop, or an attacker could use their own legitimately-signed webhook to trigger shop-scoped processing (e.g. lookups, resource updates) against a shop they don't control. This is a direct cross-shop access violation caused by the verification not binding the value that downstream logic trusts.

### Likelihood Explanation
Exploitation requires only that the attacker run their own (or a colluding) shop installation of the app to obtain one legitimately HMAC-signed webhook, then replay it to the public webhook endpoint with a modified `X-Shopify-Shop-Domain` header — no secrets need to be known or brute-forced, and the endpoint is unauthenticated apart from the HMAC check. This is straightforward and matches the exact usage pattern documented by the gem itself.

### Recommendation
Bind the shop identity into the verified payload instead of trusting an unauthenticated header: derive the shop from data that is part of the HMAC-covered body (e.g., the webhook's own `shop_domain`/resource payload, as Shopify's webhook bodies typically include this), or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the signature (e.g., include it as additional HMAC input) before it is used by consuming jobs/controllers. At minimum, update `ShopifyApp::WebhookVerification#shop_domain` and the accompanying documentation to make clear that this value is unauthenticated and must not be used as an app-authorization boundary; ideally, verify shop_domain from the signed request context supplied by the underlying `shopify_api` webhook registry rather than the raw header.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`.
2. Attacker triggers a real event (e.g., product update) on their store; Shopify sends the app a webhook with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the shared app secret.
3. Attacker intercepts/replays this exact raw body to the app's webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which still matches because the body and secret are unchanged; the request passes.
5. The app's custom controller/job (per the documented pattern) reads `shop_domain` and treats the attacker-supplied body as legitimate data belonging to `victim.myshopify.com`, processing it under the victim's shop context.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
