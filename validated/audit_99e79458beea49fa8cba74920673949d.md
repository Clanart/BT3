### Title
PedPoP ECDH accepts the identity encryption key, letting a participant force the share-encryption secret to a known constant (non-contributory DH) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
This is the direct analog of CVE-2026-34872 (FFDH peer key not validated → shared secret confined to a small set). In Serai's PedPoP DKG, each participant registers an ECDH encryption key (`enc_key`), and senders derive the ChaCha20 key for a secret share as `ecdh = enc_key * ephemeral`. Neither `EncryptionKeyMessage::read` / `Decryption::register` nor `C::read_G` rejects the identity point (or, on cofactored suites like Ed25519, low-order points). A participant who registers `enc_key = identity` forces every sender's "shared" secret to `identity * k = identity` — a publicly known constant — making the ChaCha20 keystream derivable by anyone.

### Finding Description
- `EncryptionKeyMessage::read` reads `enc_key` with `C::read_G` and performs no further validation: `Ok(Self { msg: M::read(reader, params)?, enc_key: C::read_G(reader)? })` [1](#0-0) 
- `C::read_G` only enforces canonicality (`point.to_bytes() == encoding`), which the identity point satisfies [2](#0-1) 
- `Decryption::register` stores the key with no identity/subgroup check [3](#0-2) 
- The sender encrypts with `cipher(context, &ecdh(&key, to))` where `ecdh = public * private`; if `public` (the victim-registered `enc_key`) is identity, the result is `C::G::identity()` regardless of the ephemeral key [4](#0-3) [5](#0-4) 
- `cipher` deterministically derives the ChaCha20 key/IV from `context` (public) and the ECDH point bytes only [6](#0-5) 

The per-message PoP binds the *sender's* ephemeral key, not the recipient's encryption key, so it does not prevent this; the malicious recipient's contribution to the DH output is nil — precisely the "lack of contributory behavior" bug class.

### Impact Explanation
Every `EncryptedMessage<SecretShare>` addressed to the malicious participant is encrypted under a key derived from `context || identity_encoding`, computable by any observer of the (only authenticated, not confidential) channel. All `n-1` dealers' shares destined for that participant are plaintext-recoverable, exposing that participant's full secret share. For an attacker who is themselves a participant (or a passive observer colluding with any `t-1` participants), this reduces the effective threshold and can enable recovery/signing capability over the group key. It also undermines blame confidentiality: revealing an ECDH key for one message implicitly "reveals" nothing new since all keys were already public.

### Likelihood Explanation
Requires the attacker to be a DKG participant who registers an identity/low-order `enc_key` — a single crafted field element in `generate_coefficients`'s broadcast message, reachable purely with public protocol inputs. Honest participants' code provides no check that would detect or reject it, so the attack succeeds deterministically whenever mounted.

### Recommendation
In `Decryption::register` (and/or `EncryptionKeyMessage::read`), reject `enc_key` points that are identity; on cofactored ciphersuites, additionally multiply by the cofactor or require a prime-order subgroup check before accepting the key. Mirror Mbed TLS's fix: validate the peer's DH public key is in the correct subgroup and not the neutral element before computing the shared secret.

### Proof of Concept
1. Malicious participant `M` runs `KeyGenMachine::generate_coefficients`, but instead of `Encryption::new`'s honest `enc_pub_key = G * enc_key`, broadcasts `EncryptionKeyMessage { msg: commitments, enc_key: C::G::identity() }` (valid canonical encoding, passes `read_G`).
2. Every honest dealer `d` calls `self.encryption.encrypt(rng, M, share_bytes)`, computing `ecdh = identity * key_d = identity`.
3. An observer computes `cipher::<C>(context, &Zeroizing::new(C::G::identity()))` and XORs the keystream against each `EncryptedMessage.msg` addressed to `M`, recovering every `SecretShare<C::F>` in cleartext — no private input required.
4. The observer (or `M`, or anyone holding `t-1` other shares) adds the leaked share to reach threshold and recover the group secret / forge FROST signatures under the resulting `ThresholdKeys`.

  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
