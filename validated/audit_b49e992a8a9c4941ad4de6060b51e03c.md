## Analysis

The bug-class in the report reduces to: **an externally-supplied, unvalidated value is trusted and handed to a powerful primitive with no allow-list/guard**, and once handed off, the app has no way to intercept or veto it.

The closest analog in this GitHub Desktop code is `shell.openExternal()` being invoked with an unvalidated URL/scheme originating from attacker-influenceable data (a GitHub API object's `html_url` / check-run URL), while a sibling code path in the same app enforces a strict `https?:` protocol allow-list before doing the same operation — showing the guard exists conceptually but is not applied uniformly.

### Title
Unvalidated URL scheme passed to `shell.openExternal` from GitHub API-derived `html_url` fields — ([File: app/src/lib/stores/app-store.ts])

### Summary
`AppStore._openInBrowser` and the main-process `open-external` IPC handler call Electron's `shell.openExternal()` on a raw string with no protocol allow-list, whereas the app's own sandboxed-markdown link interceptor deliberately restricts navigable links to `^https?:` before forwarding them to the same sink. Several UI surfaces feed `htmlURL`/`html_url` values taken directly from GitHub API responses (check-run details URLs, repository ruleset URLs, PR URLs) into `dispatcher.openInBrowser`, which ultimately reaches the unguarded `shell.openExternal` call.

### Finding Description
`shell.openExternal` is called with no scheme check at: [1](#0-0) 
and in the main process IPC handler, which only logs (does not restrict) when the scheme is `http(s)`, and otherwise calls `shell.openExternal` unconditionally on whatever string the renderer sends: [2](#0-1) 

By contrast, the sandboxed markdown renderer — which is the component that displays actual GitHub API content (issue/PR bodies, comments) — explicitly filters clicked links to `https?:` before forwarding the URL for opening: [3](#0-2) 

This shows the project is aware that GitHub-API-sourced content must not be handed to `openExternal` with an arbitrary scheme — but that protection is not applied to every caller of `dispatcher.openInBrowser` / `_openInBrowser`. Multiple call sites pass `html_url`/`htmlURL` fields sourced from the GitHub API (check runs, repository rulesets, PRs) straight through: [1](#0-0) [4](#0-3) 

If a GitHub Enterprise server the user is authenticated against is malicious or compromised, or an API response is otherwise attacker-influenced, the check-run/ruleset/PR object's URL field is not guaranteed to be `https://`. `shell.openExternal` with an unexpected scheme is a well-known Electron footgun: passing it a Windows UNC path (`\\attacker\share\x`), a registered custom URI scheme, or other OS-handled protocol can trigger local application launches, credential-hash leakage (SMB auth), or, depending on installed handlers, command execution — entirely outside of any git/repo sandboxing.

### Impact Explanation
If reachable, clicking a single legitimate-looking UI element ("View check" / "View rule" / "View on GitHub") sourced from attacker-controlled API data could launch an arbitrary local handler or leak NTLM credentials via a UNC-style URL, i.e., code execution/credential exfiltration triggered by a link the user clicks — squarely in the "Valid Impact" category (attacker controls a GitHub API object; result is code execution or credential exfiltration via a link the user clicks).

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the user to be pointed at a malicious/compromised GitHub Enterprise Server (or a MITM'd, unauthenticated API response) that returns a crafted `html_url`/details URL for a check run, PR, or ruleset, and the user to click the corresponding "View on GitHub"/"View check" UI affordance. This is more constrained than a purely repo-controlled attack (e.g., a malicious commit/PR body), since PR body/comment markdown already goes through the protocol-filtered `sandboxed-markdown` path. I was not able to fully verify, within the available tool budget, whether *every* `dispatcher.openInBrowser` call site is reachable from data an untrusted/compromised GHES server or unauthenticated proxy could forge (e.g., `ci-checks.ts`'s exact field provenance), so this should be confirmed against the full source before treating it as an open vulnerability.

### Recommendation
Centralize `shell.openExternal` behind a single guarded helper that enforces an `https?:` (and possibly `mailto:`) allow-list — mirroring the check already present in `sandboxed-markdown.tsx`'s `setupLinkInterceptor` — and route every caller (`AppStore._openInBrowser`, the `open-external` IPC handler, `LinkButton`, release notes, editor-error, etc.) through it instead of calling `shell.openExternal` directly. Reject or strip non-`http(s)` schemes (including UNC-style `\\` paths) before ever reaching Electron's `shell.openExternal`.

### Proof of Concept
1. Point GitHub Desktop at a malicious/compromised GitHub Enterprise Server (or intercept an unauthenticated API call).
2. Have that server return a check-run (or repository ruleset) object whose `details_url`/`html_url` is set to a non-`https` value, e.g. `\\attacker-host\share\payload` or a registered dangerous URI scheme.
3. User clicks "View check" / "View rule" in `ci-check-run-popover.tsx` / `repo-ruleset-link.tsx`, which calls `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → `shell.openExternal(url)` with no scheme validation: [1](#0-0) 
4. Electron/OS resolves the scheme/UNC path, potentially triggering local file/handler execution or SMB credential leakage — unlike the markdown path, which would have blocked the non-`https?` scheme: [5](#0-4) 

**Caveat:** This finding depends on confirming that at least one of the `dispatcher.openInBrowser` call sites (`ci-check-run-popover.tsx`, `pull-request-checks-failed.tsx`, `repo-ruleset-link.tsx`, etc.) receives a URL field whose value is not independently re-validated/normalized to `https` elsewhere in `api.ts`/`ci-checks.ts` before display. I could not fully trace that in the remaining budget — a Devin session with full repo access should verify the exact data flow before filing this as a confirmed, fixable issue.
