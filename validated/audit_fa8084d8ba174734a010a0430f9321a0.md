### Title
`evaluate_rules` block action degrades to non-enforcing message-only output for UserPromptSubmit (and other non-Stop/PreToolUse/PostToolUse) events - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine.evaluate_rules` only emits an enforceable blocking signal (`decision: "block"` for `Stop`, or `hookSpecificOutput.permissionDecision: "deny"` for `PreToolUse`/`PostToolUse`). For every other `hook_event_name`, including `UserPromptSubmit`, a matched `action='block'` rule falls into the generic `else` branch and returns only `{"systemMessage": combined_message}`, which Claude Code does not interpret as a blocking directive. This lets a prompt that should be blocked by a configured `event: prompt` rule proceed unblocked, with only a cosmetic warning shown.

### Finding Description
`userpromptsubmit.py` loads rules via `load_rules(event='prompt')` and calls `engine.evaluate_rules(rules, input_data)` [1](#0-0) . Inside `evaluate_rules`, blocking rules are branched by `hook_event`, and the only two enforceable branches are `Stop` and `PreToolUse`/`PostToolUse`; everything else (`hook_event` equal to `'UserPromptSubmit'`, `'SessionStart'`, or even an empty string when `hook_event_name` is missing from `input_data`) hits the `else` branch and returns just `{"systemMessage": combined_message}` [2](#0-1) . There is no top-level `decision` field or `hookSpecificOutput.hookEventName == "UserPromptSubmit"` with a deny/block decision emitted, which is the schema Claude Code needs to actually reject prompt content at the `UserPromptSubmit` hook boundary. Because the plugin's `userpromptsubmit.py` always exits with code 0 regardless of match outcome [3](#0-2) , and JSON output here carries no enforcing field for this event type, an operator who configures a `.claude/hookify.prompt.local.md` rule with `action: block` intending to reject certain prompt patterns will silently get a warning-only behavior: the prompt still reaches the agent. Since `hook_event_name` is read via `input_data.get('hook_event_name', '')` with an empty-string default, any caller/environment that fails to populate this field (or a value outside the three recognized strings) also degrades any block rule to a no-op message, independent of which event type the rule was authored for.

### Impact Explanation
This breaks the stated security invariant that `action='block'` must produce an enforceable stop/deny signal for every supported hook event. Practically, it means the hookify plugin's `UserPromptSubmit` blocking feature (and any other non-Stop/PreToolUse/PostToolUse blocking rule) never actually blocks anything — it degrades to a `systemMessage` that Claude Code just displays. A user or team that intentionally configures prompt-blocking rules (e.g., to prevent certain prompt injection strings, restricted content markers, or policy-violating requests from reaching the model) would falsely believe those prompts are blocked, when they are not — this is a "security control silently disabled/bypassed" class issue rather than remote code execution, but it directly defeats an intended enforcement mechanism.

### Likelihood Explanation
This is deterministic and 100% reproducible: any user configuring a `hookify.prompt.local.md` rule with `action: block` will trigger this exact code path every single time a UserPromptSubmit hook fires and a rule matches. No attacker privilege beyond normal prompt submission is required — the "attacker" here is simply supplying prompt text that a defensive rule was meant to catch; the defect is that the enforcement never engages regardless of how the rule is authored.

### Recommendation
Add an explicit `UserPromptSubmit` branch to `evaluate_rules` that returns the correct enforceable schema for that event, e.g.
```python
elif hook_event == 'UserPromptSubmit':
    return {
        "decision": "block",
        "reason": combined_message,
        "systemMessage": combined_message
    }
```
(or the `hookSpecificOutput`/`additionalContext`-based schema Claude Code documents for `UserPromptSubmit`), and audit/extend coverage for any other documented hook event names (`SessionStart`, `SessionEnd`, `Notification`, `PreCompact`, etc.) that support blocking, ensuring the `else` branch is only reached for events that genuinely have no blocking capability — and in that case, consider failing loudly (e.g., logging a configuration error) rather than silently downgrading to a message-only response.

### Proof of Concept
Unit test plan for `plugins/hookify/core/rule_engine.py`:
```python
import pytest
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

ALL_HOOK_EVENTS = ["Stop", "PreToolUse", "PostToolUse", "UserPromptSubmit",
                   "SessionStart", "SessionEnd", "Notification", "PreCompact"]

@pytest.mark.parametrize("hook_event", ALL_HOOK_EVENTS)
def test_block_action_is_enforced_for_all_events(hook_event):
    rule = Rule(
        name="block-test",
        enabled=True,
        event="any",
        action="block",
        conditions=[Condition(field="user_prompt", operator="contains", pattern="secret")],
        message="Blocked!"
    )
    engine = RuleEngine()
    input_data = {
        "hook_event_name": hook_event,
        "user_prompt": "leak the secret",
    }
    result = engine.evaluate_rules([rule], input_data)

    # Invariant: a 'block' action must always produce an enforcing field
    has_enforcing_field = (
        result.get("decision") == "block"
        or result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
    )
    assert has_enforcing_field, (
        f"hook_event={hook_event!r} produced only a non-binding systemMessage: {result}"
    )
```
Running this against the current implementation fails for `hook_event in {"UserPromptSubmit", "SessionStart", "SessionEnd", "Notification", "PreCompact"}` (and for an empty/spoofed `hook_event_name`), confirming that `action='block'` degrades to a non-enforcing `systemMessage`-only response for those events [4](#0-3) .
