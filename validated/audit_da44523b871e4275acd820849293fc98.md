### Title
Attacker-controlled participant count in `ThresholdKeys::read` triggers quadratic Lagrange interpolation → CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes a fully attacker-controlled `t`/`n` pair and `Interpolation::Lagrange` tag from untrusted bytes, then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of `t` participants. With `Interpolation::Lagrange`, each `interpolation_factor` call iterates over all `t` included participants, giving O(n²) field arithmetic — up to ~4.3 billion field multiplications for `n = u16::MAX` — from a serialized payload of only ~2–4 MB. This is the same bug class as CVE-2014-3589 (crafted size field causing disproportionate resource consumption).

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` as raw `u16`s and an interpolation-method byte directly from the reader (crypto/dkg/src/lib.rs:591-616). For `interpolation == 1` it selects `Interpolation::Lagrange` and reads `n` verification shares. It then calls `ThresholdKeys::new` (line 625), which builds `t = 1..=params.t()` and computes `group_key` as `verification_shares[i] * interpolation.interpolation_factor(*i, &t)` summed over all `t` indexes (crypto/dkg/src/lib.rs:376-378). `interpolation_factor` for `Lagrange` loops over every element of `included` performing field multiplications (crypto/dkg/src/lib.rs:229-246), so total cost is Θ(t²) scalar operations. `ThresholdParams::new` only enforces `t <= n` and `i <= n` (crypto/dkg/src/lib.rs:166-179); there is no upper bound on `n` beyond `u16::MAX` and no limit relative to the actual validator set.

A malicious payload with `t = n = 65535`, `i = 1`, interpolation byte `0x01`, a scalar, and 65535 encoded points is accepted and forces ~4.3 × 10⁹ field multiplications plus inversions in a single `read`/`new` call — work orders of magnitude larger than the input, with no chunked reading or cap like the `TRANSACTION_SIZE_LIMIT` used elsewhere.

### Impact Explanation
Any context where `ThresholdKeys::read` (or `ThresholdKeys::deserialize`/borsh paths) is applied to bytes an unprivileged party supplies — e.g., keys embedded in messages/transaction data the node parses — lets the attacker pin a CPU core for an extended period per message with a few MB of input. Repeated submissions produce sustained denial of service of key-handling code paths. This is a pure resource-exhaustion DoS, matching the advisory class (crafted size field → denial of service, CVSS A:H).

### Likelihood Explanation
Reachability requires an integrator/node to deserialize `ThresholdKeys` from data influenced by an external party. The `read` function is public and specifically designed for deserialization of keys transported between parties, and the scope rules list `ThresholdKeys::read` as an untrusted-bytes sink. The attack needs no valid signature, key knowledge, or validator status — only the ability to feed crafted bytes to the reader. Cost to the attacker is bounded by message size (~2–4 MB); cost to the victim is quadratic in `n`.

### Recommendation
- Impose a sane upper bound on `n`/`t` in `ThresholdKeys::read` (e.g., the 150-participant bound the protocol assumes elsewhere) before constructing `ThresholdKeys`.
- Alternatively, compute the group key additively or cache Lagrange denominators so `ThresholdKeys::new` is O(n) rather than O(n²).
- Document and enforce that `ThresholdKeys` from untrusted input must be length-checked prior to calling `read`.

### Proof of Concept
```rust
// Construct a malicious serialized ThresholdKeys<Ristretto> payload:
// ID header (correct curve ID), then:
//   t = 0xffff, n = 0xffff, i = 1, interpolation = 0x01 (Lagrange)
//   secret_share = 32-byte scalar
//   65535 encoded verification-share points
let mut buf = vec![];
buf.extend(&(Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t
buf.extend(&u16::MAX.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                         // Interpolation::Lagrange
buf.extend(Scalar::ONE.to_repr());   // secret_share
let point = <Ristretto as Ciphersuite>::generator().to_bytes();
for _ in 0 .. u16::MAX {
    buf.extend(point.as_ref());      // n verification shares
}
// ~2.1 MB input -> ThresholdKeys::new performs ~4.3e9 field multiplications
// inside interpolation_factor summed over 65535 participants.
let _keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()); // CPU exhaustion
```

The amplification (quadratic work per linear input byte) is what makes this a practical DoS rather than a proportional cost, exactly mirroring the crafted-block-size primitive in the Pillow advisory.
