### Title
Missing secret-share/verification-share consistency check in `ThresholdKeys::new` lets attacker-crafted serialized keys silently redefine the group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, an interpolation method, a `secret_share`, and `n` verification shares entirely from untrusted bytes, then passes them to `ThresholdKeys::new`. `new` checks counts and participant ranges but never verifies that the provided `secret_share` is consistent with `verification_shares[i]` (i.e. that `C::generator() * secret_share == verification_shares[&i]`). The group key is derived solely as `Σ verification_shares[i] * interpolation_factor(i, 1..=t)` — a value fully controlled by whoever supplies the bytes. This is the Serai analog of the improper-input-validation bug class: untrusted key material is accepted without validating its internal consistency.

### Finding Description
`ThresholdKeys::read` reads every field of `ThresholdKeys` from the wire with only canonical-encoding and parameter-range checks:

- interpolation tag `0` reads `n` scalars into `Interpolation::Constant`, tag `1` selects `Lagrange` — `crypto/dkg/src/lib.rs:604-616`
- `secret_share` is read with `C::read_F` — `crypto/dkg/src/lib.rs:618`
- `verification_shares` for participants `1..=n` are read with `Ciphersuite::read_G`, which explicitly permits the identity point — `crypto/dkg/src/lib.rs:620-623`, `crypto/ciphersuite/src/lib.rs:91-101` (note `Curve::read_G`'s identity rejection at `crypto/frost/src/curve/mod.rs:125-131` is bypassed by calling the `Ciphersuite` impl directly)

`ThresholdKeys::new` then validates `verification_shares.len() == n` and `participant <= n`, requires `t == n` for `Constant` interpolation, and computes the group key purely from the verification shares:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(`crypto/dkg/src/lib.rs:376-378`). No statement binds `secret_share` to `verification_shares[&params.i()]`, and nothing prevents the verification shares from being identity points or low-order/attacker-selected points.

For Lagrange interpolation the factors sum to 1 (`Σ λ_i(0) = 1`), so an attacker who writes `verification_shares[l] = k_l * G` obtains `group_key = (Σ k_l·λ_l) * G` — a key whose discrete logarithm the attacker knows exactly. Combined with a `secret_share` they also choose, the resulting `ThresholdKeys` is fully self-consistent for `view()`, `sign()`, and `complete()`: `view()` derives the secret share via `interpolation_factor * secret_share` and re-derives each party's verification share from the same attacker-supplied map (`crypto/dkg/src/lib.rs:494-507`), so share validation in `AlgorithmSignatureMachine::complete` succeeds and valid signatures under the attacker-known group key are produced.

### Impact Explanation
Any path that restores/loads `ThresholdKeys` from bytes an attacker can influence (backup import, key sync, RPC-supplied blob) results in the node adopting a "threshold key" whose group key's discrete logarithm is known to the attacker. Funds sent to the corresponding address (e.g., a Bitcoin/Taproot output keyed by `group_key()`) are spendable by the attacker unilaterally, while the node believes they are protected by a `t`-of-`n` multisig. Conversely, an inconsistent blob yields shares that fail verification — a liveness break. Either way, the node signs and reports a group key the attacker controls: concrete key-share/group-key compromise via malformed input, matching the improper-input-validation class of CVE-2023-25696.

### Likelihood Explanation
Exploitation requires feeding crafted bytes to `ThresholdKeys::read`. The format is fully specified by `write`/`serialize` (`crypto/dkg/src/lib.rs:567-571`), so constructing the blob is trivial: pick `t = n = 1`, `i = 1`, `Interpolation::Lagrange`, `secret_share = 1`, `verification_shares[1] = generator`, producing `group_key = generator` (secret `1`). No PoK, proof, or interactive protocol gates deserialization. The severity of the outcome (silent adoption of an attacker-known key) is high whenever key blobs cross a trust boundary.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject identity verification shares by using the identity-rejecting read. Additionally reject `secret_share == 0`. This restores the invariant that every accepted `ThresholdKeys` represents a real sharing of `group_key`'s discrete log.

### Proof of Concept
```rust
// Attacker constructs a blob that deserializes into ThresholdKeys whose
// group key has a known discrete logarithm (1).
// C = any in-scope ciphersuite, e.g. Secp256k1.

let mut blob = vec![];
// C::ID length prefix + C::ID
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
// t = 1, n = 1, i = 1
blob.extend(1u16.to_le_bytes());
blob.extend(1u16.to_le_bytes());
blob.extend(1u16.to_le_bytes());
// interpolation = Lagrange (tag 1)
blob.push(1);
// secret_share = 1
blob.extend(C::F::ONE.to_repr().as_ref());
// verification_shares[1] = generator (DL known: 1)
blob.extend(C::generator().to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut blob.as_ref()).unwrap();
// group_key == generator * 1 -- attacker knows the "threshold" private key.
assert_eq!(keys.group_key(), C::generator());
// keys.view([1]), AlgorithmMachine::sign, and complete() all succeed,
// producing valid signatures under a key the attacker controls.
```

The deserialization path never calls `Curve::read_G` and never checks `generator * secret_share == verification_shares[i]`, so this blob is accepted and behaves as a fully functional 1-of-1 "threshold" key whose secret is `1`.
