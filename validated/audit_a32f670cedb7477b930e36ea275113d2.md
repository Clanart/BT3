### Title
Deterministic cached FROST preprocess reused for repeated `share`/`complete` calls under one context, enabling validator private-key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to Fei's `GenesisGroup.purchase`/`commit` remaining callable after `launch`, `SigningProtocol::preprocess_internal` remains callable after the preprocess it mints has already been consumed by `share_internal`. The cached nonce seed stored in `CachedPreprocesses` (keyed only by `context`) is never marked spent or deleted, so every subsequent call to `share`/`complete` under the same context regenerates the identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (a `ChaCha20Rng` re-seeded from the same 32 bytes). Any second call that reaches `machine.sign(preprocesses, msg)` with different attacker-influenced inputs (different `preprocesses` set, or a different `key_pair`/`msg` in `DkgConfirmer`) produces a second signature share over the same nonce — the classic Schnorr/FROST nonce-reuse condition that leaks the signer's secret.

### Finding Description
`preprocess_internal` at `coordinator/src/tributary/signing_protocol.rs:100-148` implements the "decide nonce once per context" design described in the file header (`signing_protocol.rs:25-55`). Safety relies entirely on `share` being invoked at most once per context: the comment states "In order for nonce re-use to occur, the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" and lists only BFT reorgs/rebuilds as causes — but nothing in code enforces single-use. `CachedPreprocesses::get` returns the seed on every call; there is no `CachedPreprocesses::kill`/consume and no "already shared" flag per context.

`share_internal` (`signing_protocol.rs:150-181`) then rebuilds the machine from the cached seed and calls `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:283`), which drains `self.nonces` into shares computed as `base + rho * actual` with the attacker's preprocess map and `msg`. `DkgConfirmer::share` and `DkgConfirmer::complete` (`signing_protocol.rs:288-327`) expose this publicly: `complete` even calls `share_internal` again internally, and both accept `preprocesses` and `key_pair` derived from finalized tributary transactions (i.e., validator-published data an attacker validator-equivalent input path supplies — and notably the header itself flags the missing check that the on-chain preprocesses match the presumed ones as a `TODO`, `signing_protocol.rs:51-54`).

A second finalized attempt of the same context — e.g., a `Share`-generating path invoked again with a different participant set or a different `key_pair` under the same `(b"DkgConfirmer", attempt)` context — causes the same `(d, e)` nonces to sign a second `(preprocesses, msg)` tuple. Because the binding factor `rho` and challenge change, the two published shares form two linear equations in the nonce scalars, which solve directly and then yield the MuSig private key via `share = nonce - challenge * key_share`.

### Impact Explanation
Recovery of a validator's Ristretto MuSig private key (the key used for on-chain DKG confirmation signing). This is exactly the secret-leakage consequence the FROST library documents for `CachedPreprocess` reuse (`crypto/frost/src/sign.rs:211-219`: "Reuse of it enables recovery of your private key share"), here triggered not by integrator misuse but by the coordinator's own stateless re-execution path lacking a spent-flag on the cached seed.

### Likelihood Explanation
Requires two `share`/`complete` executions under the same context with differing inputs — reachable when finalized tributary data changes which preprocesses or which `key_pair` are supplied across transactions within an attempt (multiple confirmation transactions, removed-set edge cases, or a second call before the attempt rolls over). The guard relies on BFT ordering assumptions documented in the file header rather than an explicit consumed-marker, so any logical path that re-enters `share_internal` (including `complete` after `share`) with distinct bytes suffices.

### Recommendation
Delete or tombstone the `CachedPreprocesses` entry (or record a "share published for context" flag) the first time `share_internal` successfully produces a share, and refuse to sign again for that context. Additionally implement the noted TODO: verify the regenerated on-chain preprocess/commitments match what was previously published before emitting a share, so any divergence aborts rather than reuses the nonce.

### Proof of Concept
1. For context `(b"DkgConfirmer", attempt)`, trigger `DkgConfirmer::share(preprocesses_A, key_pair_A)` — `preprocess_internal` stores seed S, signs, emits share s₁ over nonces `(d, e)`.
2. Trigger `DkgConfirmer::share(preprocesses_B, key_pair_B)` (or `complete` with different `preprocesses`) under the same context — `CachedPreprocesses::get` returns S again, `from_cache`/`seeded_preprocess` regenerates identical `(d, e)`, and `sign` emits s₂ over a different `rho`/challenge.
3. Given public commitments `D = dG`, `E = eG` (published in the first preprocess) and shares `sᵢ = (d + ρᵢ·e) − cᵢ·x`, solve for `e = (s₁ − s₂ + (c₁ − c₂)x)/…` — concretely, recover `d, e` from the two equations since `ρ` and `c` are recomputable public values, then solve `x` (the validator's secret) directly.
