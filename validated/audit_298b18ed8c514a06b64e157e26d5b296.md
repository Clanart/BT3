### Title
Incomplete `XY` status-code coverage in `mapStatus()` silently corrupts file-status classification for common index/worktree state combinations - (File: `app/src/lib/status-parser.ts`)

### Summary
The Freefall report's root cause is a "closed" invariant (cumulative weight must cover `[0, WEIGHT_DENOMINATOR)`) that is enforced only at initialization and not on every subsequent state mutation, so a gap in the covered domain causes the selector to fall into an unhandled path. `mapStatus()` in GitHub Desktop has the same structural defect: it is supposed to translate every possible two-character `git status --porcelain=2` `XY` code into a precise `FileEntry`, but it only special-cases an enumerated subset of codes and silently falls back to a generic, information-losing `{kind: 'ordinary', type: 'modified'}` result for anything it doesn't recognize [1](#0-0) .

### Finding Description
`mapStatus()` explicitly handles a finite list of `XY` codes (`??`, `.M`, `M.`, `.A`, `A.`, `.D`, `D.`, `R.`, `.R`, `C.`, `.C`, `AD`, `AM`, `RM`, `RD`, `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU`) [2](#0-1) . Two categories of legitimate, git-emitted codes are missing from this list:

- `MM` — a file staged with a partial/full modification in the index that has *further* unstaged edits in the working tree. This is a routine and extremely common git state (stage part of a change, keep editing), produced by plain `git status --porcelain=2` with no special configuration.
- `CM` / `CD` — copy-detected entries (index copied + worktree modified/deleted) emitted via the type `"2"` renamed-or-copied record parsed by `parsedRenamedOrCopiedEntry()`, which passes the same two-character code into `mapStatus()` [3](#0-2) . Only `C.`, `R.`, `RM`, `RD` are handled for this record type; `CM`/`CD` are not.

For any of these unhandled codes, `mapStatus()` returns the fallback object, which — unlike every other `'ordinary'` branch — omits the `index`/`workingTree` fields entirely and, in the copy/rename case, drops the parsed `renameOrCopyScore` and the `'copied'`/`'renamed'` kind altogether [1](#0-0) .

This corrupted `FileEntry` then propagates into `convertToAppStatus()`, which uses `entry.kind`, `entry.workingTree`, and `entry.renameOrCopyScore` to decide whether a file is `AppFileStatusKind.Copied`/`Renamed` (with `oldPath` and `renameIncludesModifications`) or a plain `AppFileStatusKind.Modified` [4](#0-3) . A copy/rename silently downgraded to `Modified` changes downstream behavior in `stageFiles()`, which only force-removes the old path from the index when `file.status.kind === AppFileStatusKind.Renamed` [5](#0-4) ; misclassification means this step is skipped, so the index/staged tree the user actually commits can silently differ from what Desktop displayed and from what the user intended to stage.

This exactly mirrors the Solidity bug-class: an invariant ("every reachable code path is covered by an exhaustive, precise mapping") is enforced for some entries but not for all, and the unhandled gap triggers a fallback that produces internally inconsistent state rather than failing loudly.

### Impact Explanation
Unlike the Solidity bug (which reverts and freezes funds), this Desktop analog fails *silently*: the UI shows an incorrect classification (`Modified` instead of `Copied`/`Renamed`, with no `oldPath`), and the staging/index logic that depends on that classification (`stageFiles()`) behaves differently for the misclassified case than it would for the correct one. This falls squarely under "silent corruption of what the user commits or pushes," since the set of paths added/removed from the index no longer matches the file's actual git-detected relationship, without any error surfaced to the user before the commit is made.

### Likelihood Explanation
`MM` requires no attacker-controlled configuration — it is produced by default `git status --porcelain=2` behavior whenever a file has both a staged and an unstaged change, a state that a maliciously prepared repository/branch can easily coax the user into (e.g., pre-staged content plus instructions or hooks that lead to further edits before commit). `CM`/`CD` require copy detection to be enabled (`status.renames`/`diff.renames = copies`), which narrows but does not eliminate reachability. No local/physical access, admin rights, or leaked credentials are required; the only inputs are the repository content and ordinary user staging/editing actions.

### Recommendation
Make `mapStatus()` exhaustive rather than allow-listed: enumerate all valid `X`/`Y` combinations per the `git-status` porcelain v2 specification (including `MM`, `CM`, `CD`, and any other index/worktree combination) and return a precisely-typed `FileEntry` for each, preserving `index`, `workingTree`, and `renameOrCopyScore` in every case. Replace the silent catch-all fallback with a hard failure (throw, matching the pattern already used elsewhere in this file for unparsable input, e.g. `parseChangedEntry`/`parseUnmergedEntry`) so an unrecognized code cannot silently masquerade as an ordinary modification.

### Proof of Concept
1. Initialize a repo, commit a tracked file `foo`.
2. Stage a modification to `foo` (`git add foo`), then modify `foo` again without staging the second change — git now reports status code `MM foo`.
3. Run `git status --branch --porcelain=2 -z`, feed the output through `parsePorcelainStatus`/`mapStatus` as Desktop does in `getStatus()` [6](#0-5) .
4. Because `MM` is not one of the explicit cases in `mapStatus()`, the function falls through to the generic fallback and returns `{kind: 'ordinary', type: 'modified', submoduleStatus}` with no `index`/`workingTree` fields [1](#0-0) , even though the file has distinct staged and unstaged changes that should be represented precisely.
5. For the copy-detection variant: with `diff.renames=copies` set, copy a tracked file to a new path and modify the copy (`CM`) or delete the original relative to the copy relationship (`CD`); `parsedRenamedOrCopiedEntry()` passes `CM`/`CD` into `mapStatus()`, which again falls through to the generic fallback, discarding `renameOrCopyScore` and reporting the file as plainly `Modified` in `convertToAppStatus()` instead of `Copied` [7](#0-6) , causing `stageFiles()` to skip the old-path force-remove step that only runs for `AppFileStatusKind.Renamed` [5](#0-4) .

**Note on verification limits:** I confirmed the code-path gap by static inspection of `status-parser.ts` and `git/status.ts`; I was not able to execute `git status --porcelain=2` in a live environment through the available tools to directly capture an `MM`/`CM`/`CD` byte stream, so the exact runtime output format is based on the documented porcelain v2 format and the existing regexes in this file rather than an observed test run.

// 2 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <X><score> <path><sep><origPath>
const renamedOrCopiedEntryRe =
  /^2 ([MADRCUTX?!.]{2}) (N\.\.\.|S[C.][M.][U.]) (\d+) (\d+) (\d+) ([a-f0-9]+) ([a-f0-9]+) ([RC]\d+) ([\s\S]*?)$/

function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
