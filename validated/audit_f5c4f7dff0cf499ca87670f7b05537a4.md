## Title
Credential-helper trampoline discloses stored generic git secrets keyed by an attacker-controlled username from a cloned repository's remote/submodule URL - (File: `app/src/lib/trampoline/find-account.ts`)

## Summary
The Sherlock finding is a "missing binding between the identity parameter and the actual authorized actor" bug: `_authenticateDeleverage()` trusted a caller-supplied `liquidator` address instead of tying it to `msg.sender`, letting an attacker force an action to be executed "as" someone else's approved funds. The Desktop analog is in the git credential-helper trampoline: when Git needs credentials for a host, it sends a `username` value taken straight from the remote/submodule URL of whatever repository is currently being operated on. Desktop's trampoline uses that untrusted `username` as the lookup key into the OS-level generic credential store, without checking that it belongs to the account/session that actually initiated the operation.

## Finding Description
`findGenericTrampolineAccount()` derives the credential lookup identity purely from the URL supplied by the git subprocess: [1](#0-0) 

```
export async function findGenericTrampolineAccount(
  trampolineToken: string,
  remoteUrl: string
) {
  const parsedUrl = new URL(remoteUrl)
  const endpoint = urlWithoutCredentials(remoteUrl)

  const login =
    parsedUrl.username === ''
      ? getGenericUsername(endpoint)
      : parsedUrl.username
  ...
```

The `login` variable is taken from `parsedUrl.username` whenever the URL contains an embedded user (`https://<username>@host/...`). This value is not chosen by the signed-in Desktop user nor validated against the accounts store — it is whatever string appears in the remote/submodule URL that Git is currently talking to, which is data controlled entirely by the content of the repository being cloned/fetched (a normal `.gitmodules` entry, `git remote` config, or a URL rewrite can embed any username).

That `login`, together with the `endpoint` (host), is then passed straight into `TokenStore` (OS keychain) to retrieve a secret: [2](#0-1) 

and the resulting credential is handed to Git without any additional confirmation: [3](#0-2) 

This mirrors the audited bug's root cause precisely: `_authenticateDeleverage()` accepted a `liquidator` parameter from an untrusted call path and used it as the "who benefits/who acts" identity without verifying it against `msg.sender`; here, the trampoline accepts a `username` sourced from an attacker-authored repository/submodule URL and uses it as the "whose stored secret to disclose" identity without verifying it against the currently signed-in Desktop account/session that is supposed to own the operation. The `endpoint` scoping (host) limits blast radius to hosts the machine has previously stored generic credentials for (e.g., a company's self-hosted Git server), but it does nothing to stop an attacker from choosing an arbitrary `username` on that same host.

## Impact Explanation
On any machine that has previously stored generic (non-GitHub.com/GHE) git credentials for a shared/internal git host (common for GitLab/Gitea/Bitbucket Server deployments used alongside GitHub Desktop), a malicious or compromised repository can declare a submodule or remote whose URL embeds a different, guessed/known username on that same host:
```
[submodule "x"]
    url = https://coworker-username@git.company.internal/some/repo.git
```
When the victim clones/fetches this repository (submodules are fetched with `--recursive`, see `app/src/lib/git/clone.ts`), Desktop's trampoline will silently look up and hand over whatever secret is stored under `coworker-username` for that host — impersonating a different identity than the one the user intended to use for the operation, without any prompt or confirmation. This is a credential-disclosure/account-confusion primitive: it lets an attacker-authored repo force git operations to authenticate "on behalf of" a different stored identity, analogous to forcing liquidation "on behalf of" an unwilling account.

## Likelihood Explanation
Requires the victim to have previously stored generic git credentials on the same machine under an identity guessable/known to the attacker (realistic in shared corporate self-hosted Git environments), and requires cloning/fetching an attacker-controlled repository or submodule — both are within the stated valid-impact class ("attacker controls a cloned/fetched repository ... or a git remote/proxy response"). It does not require local/physical access, admin rights, or social engineering beyond the normal act of cloning a repo.

## Recommendation
Scope generic credential lookups/writes to the account/session context that actually initiated the git operation rather than trusting the `username` embedded in the remote/submodule URL supplied by the repository content. At minimum, require explicit user confirmation (similar to `promptForGenericGitAuthentication`) whenever the credential-helper request's `username` does not match the previously-used/default username for that endpoint, instead of silently returning `credWithAccount()` in `getGenericCredential()`.

## Proof of Concept
1. On a machine, sign in normally to a self-hosted git host (e.g. `git.company.internal`) as `victim`, causing `setGenericCredential('https://git.company.internal', 'victim', '<password>')` to be stored via `app/src/lib/generic-git-auth.ts`.
2. Separately, another user's credentials for the same host end up stored on the same machine as `coworker` (shared workstation, or attacker has separate write access to the keychain namespace).
3. Attacker crafts/compromises a repository with a submodule: `url = https://coworker@git.company.internal/private/repo.git`.
4. Victim clones the attacker's repository with Desktop (`git clone --recursive`, `app/src/lib/git/clone.ts`).
5. During the recursive submodule fetch, Git asks the credential helper for `git.company.internal` with `username=coworker`.
6. `findGenericTrampolineAccount()` looks up and returns `coworker`'s stored password without prompting, and it is used to authenticate the fetch — the operation silently proceeds "as" `coworker`, not `victim`.

async function getGenericCredential(cred: Credential, token: string) {
  const endpoint = `${getCredentialUrl(cred)}`
  const account = await findGenericTrampolineAccount(token, endpoint)

  if (account) {
    info(`found generic credential for ${endpoint}`)
    return credWithAccount(cred, account)
  }

  if (getIsBackgroundTaskEnvironment(token)) {
    debug('background task environment, skipping prompt')
    return undefined
  } else {
    return promptForCredential(cred, endpoint)
  }
}
