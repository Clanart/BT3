## Title
Escrow release performs external token transfer before decrementing the escrow balance (checks-effects-interactions violation) — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The external report's core defect is a **claimable-value mapping that is not zeroed/updated until after the payout materializes**, leaving a window where the same value can be claimed again. The Tron variant of the IntentGateway contract has the same structural defect: `withdraw()` transfers escrowed tokens to the beneficiary via an external call/`.call{value:}` and only decrements the `_orders[commitment][token]` accounting **after** that external interaction returns, instead of before, as the corrected sibling contract (`IntentsBase.sol`) does.

## Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()` [1](#0-0)  executes, per token:

```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
// external interaction: native call or ERC20 transfer
...
_orders[body.commitment][token] -= amount;   // effect happens AFTER interaction
```

This is the opposite order from the corrected implementation in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw()`, which reads the escrow, **decrements it first**, and only then performs the transfer [2](#0-1) . The `IntentsBase` version is the direct local analog of the external report's fix ("adjust the claimable value to zero before/at the point of claim"); the Tron contract regressed that fix.

Because the guard is only `_orders[...][token] == 0` (a nonzero check) rather than the actual decrement happening first, any external call surface reached during the token transfer (native ETH `.call` to an arbitrary beneficiary address, or a token with hooks/callbacks) executes while `_orders[commitment][token]` still holds its pre-payout value. If that external call can re-enter a path that invokes `withdraw()` again for the same `commitment`/`token` before the first call's decrement executes, the escrow would be paid out more than once, draining protocol-held funds to the attacker-controlled beneficiary.

`withdraw()` is only reachable from `onAccept` (onlyHost) and `onGetResponse` (onlyHost) [3](#0-2) , so the exploit precondition is that the ISMP host on this chain permits re-entrant delivery of the same request (i.e., the request/response is not marked as received until after the module callback returns). I was not able to fully confirm the exact receipt-marking order for `handlePostRequests`/`handleGetResponses` in `HandlerV2.sol` within the available iterations — I only verified that other EvmHost paths (e.g. `dispatchTimeOut`) delete the commitment *before* the external module call, which is the safe CEI pattern [4](#0-3) . If the POST/GET-response delivery path follows the same "mark-received-then-call" order, direct reentry into `onAccept`/`onGetResponse` would be blocked and the practical impact narrows to callback-capable escrowed tokens (rather than the host's request dispatch itself). This should be verified directly against `HandlerV2.sol`'s post/get-response handling before treating this as fully exploitable.

## Impact Explanation
If exploitable, this allows unauthorized duplicate withdrawal of escrowed bridge funds to a single beneficiary — a direct "stealing/loss of funds" and "double-settlement" primitive matching the bounty's accepted impact categories. It affects the Tron deployment of the Intent Gateway custody contract specifically (the mainline EVM `IntentsBase.sol` already applies the correct effects-before-interactions order for this exact mapping).

## Likelihood Explanation
Moderate-to-uncertain. The code-level CEI defect is concretely present and provable from source. However, real-world exploitability hinges on (a) a reentrancy-capable escrowed asset (native TRX to an attacker contract, or an ERC-20/ERC-777-style token with transfer hooks) and (b) the underlying ISMP host allowing a request/response to be re-delivered/re-entered before it is marked received — a precondition I could not fully verify against `HandlerV2.sol` in the time available.

## Recommendation
- In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`, decrement `_orders[body.commitment][token]` (and clear `TRANSACTION_FEES`) **before** performing any external transfer, mirroring `IntentsBase.sol::_withdraw()`.
- Add a reentrancy guard on `onAccept`/`onGetResponse`, or verify (and if necessary enforce) that the host marks a request/response as received before invoking the destination module's callback, closing the reentry window regardless of internal ordering.

## Proof of Concept
1. A cross-chain order escrows a token controlled by the attacker (e.g., a token with a transfer hook, or native TRX to an attacker contract as beneficiary) via `IntentGatewayV2` on the Tron-deployed source chain.
2. The order is filled on the destination chain; a `RedeemEscrow`/`RefundEscrow` request is dispatched back to the source chain.
3. When the host delivers this request and calls `onAccept` → `withdraw()`, the native/token transfer in the loop triggers the attacker's callback before `_orders[commitment][token] -= amount` executes.
4. If the host has not yet marked the request as received/receipted at that point, the attacker's callback re-triggers delivery of the same request (or another path reaching `withdraw()` for the same commitment), and `_orders[commitment][token]` still shows the full pre-payout balance, allowing a second transfer of the same escrowed amount before the first decrement lands.

This proof-of-concept's final trigger step depends on confirming the host's receipt-marking order for post/get-response delivery, which I flagged as unverified above.
