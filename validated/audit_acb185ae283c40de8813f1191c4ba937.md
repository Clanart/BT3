Confirmed: the Tron `IntentGatewayV2.sol` deployment (`evm/tron/contracts/apps/IntentGatewayV2.sol`) computes `reducedInputs` from the *stated* `order.inputs[i].amount` (protocol fee subtracted from the requested amount) rather than from what the contract actually receives after `safeTransferFrom`, and never re-measures its own token balance before crediting escrow. This is the exact fee-on-transfer analog the report describes, and it is a real regression relative to the already-patched EVM mainline contract that does measure `balBefore`/`balAfter`.

### Title
Fee-on-transfer / deflationary ERC-20 inputs let `IntentGatewayV2.placeOrder` (Tron) over-credit escrow, draining other users' deposits - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder` in the Tron variant of `IntentGatewayV2` computes the escrowed amount for an order purely from the caller-supplied `order.inputs[i].amount` (minus the protocol fee), and then calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without ever comparing the contract's token balance before and after the transfer [1](#0-0) . For any ERC-20 that charges a transfer fee (fee-on-transfer / deflationary tokens), the actual amount received by the contract is less than the amount credited to `_orders[commitment][token]`. Because the ERC-20 balance is a single pool shared across all orders' escrow rows, this inflates the aggregate liability recorded in `_orders` beyond what the contract actually holds, and a later order's legitimate withdrawal can be shorted or entirely fail because an earlier order already drained the shared pool with an inflated escrow claim.

This is a genuine regression: the mainline EVM contract at `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this class of bug — it snapshots `balBefore`, transfers, then sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing fees and crediting escrow [2](#0-1) , and this exact scenario is covered by a dedicated Foundry test with a `FeeOnTransferToken` mock [3](#0-2) . The Tron deployment never received the equivalent fix.

### Finding Description
In the non-predispatch branch of `placeOrder`, the Tron contract:
1. Computes `reducedInputs[i].amount = order.inputs[i].amount - protocolFee`, using the caller-declared `amount` [4](#0-3) .
2. Pulls tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` with no pre/post balance check.
3. Unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — the nominal, not the actually-received, amount [1](#0-0) .

The predispatch branch is only partially better: it measures `balance = IERC20(token).balanceOf(dispatcher)` after the sweep and emits `DustCollected` for `balance - requiredAmount`, but still credits escrow with the nominal `reducedInputs[i].amount` rather than the measured `balance`, so the same over-crediting occurs whenever `token` charges a fee on the second (dispatcher→gateway) leg of the transfer [5](#0-4) .

Because `_orders[commitment][token]` values across *different* commitments all draw from the same underlying ERC-20 balance held by the contract, inflating one order's recorded escrow doesn't just corrupt that order's own bookkeeping — it creates a shortfall that is realized against whichever order withdraws later. `withdraw()` transfers `body.tokens[i].amount` (taken from the inflated ledger) via a raw `token.call(transfer, beneficiary, amount)` and reverts only on transfer failure, decrementing `_orders[body.commitment][token] -= amount` [6](#0-5) . There is no invariant anywhere enforcing `sum(_orders[*][token]) <= IERC20(token).balanceOf(address(this))`.

### Impact Explanation
An unprivileged user placing an order with a fee-on-transfer token causes the gateway to record more escrow than it actually holds. When a second order using the same token is later settled (via `fillOrder`'s `RedeemEscrow` response or a `cancelOrder`'s `RefundEscrow` response), its `withdraw()` can attempt to pay out more tokens than remain in the contract's shared balance for that token — either reverting (locking those funds, a loss for that beneficiary) or, if the first order's beneficiary withdraws first, siphoning tokens that were actually deposited by a different user's order. This is a direct loss/misallocation of user funds in escrow custody, matching the "stealing or loss of funds" bounty category, and requires no relayer, prover, or admin compromise — only an ordinary user placing an order with a known-deflationary token.

### Likelihood Explanation
Likelihood depends on a deflationary/fee-on-transfer token being configured as a supported input asset for the Tron IntentGateway deployment. Given the protocol's own EVM mainline codebase explicitly anticipated and patched this exact class of token (dedicated `FeeOnTransferToken` test), it is a realistic and known-relevant token category for this product, and the fix was evidently not ported to the Tron contract, making this a genuine, exploitable divergence rather than a hypothetical concern.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot the contract's ERC-20 balance immediately before `safeTransferFrom`, and use the *measured* delta (`balanceOf(address(this)) after - before`) as `order.inputs[i].amount` before computing `protocolFee`/`reducedInputs` and crediting `_orders[commitment][token]`, for both the direct-transfer and predispatch-sweep paths.

### Proof of Concept
1. Deploy a `FeeOnTransferToken` with, e.g., a 10% fee (as in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s mock) and register it as a supported input token on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 100e18}`. The contract's actual FOT balance increases by only 90e18 (10% fee burned/redirected), but `_orders[commitmentA][FOT]` is set to `100e18` (minus any protocol fee) per lines 444-463.
3. User B calls `placeOrder` with an identical 100e18 FOT input. Contract balance is now 180e18 total, but `_orders[commitmentA][FOT] + _orders[commitmentB][FOT] = 200e18` (minus protocol fees).
4. Order A is filled/cancelled and `withdraw()` pays out the full recorded 100e18 to A's beneficiary — succeeds because 180e18 is available.
5. Order B is filled/cancelled and `withdraw()` attempts to pay out its recorded 100e18, but only 80e18 of actual FOT remains in the contract — the transfer reverts (funds stuck) or, depending on token/beneficiary ordering, an attacker can front-run withdrawal ordering to guarantee they are "User A" and drain the shared pool at other depositors' expense.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
