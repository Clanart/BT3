Based on my investigation, I found an analogous issue in the auction (MEV) module's bid transaction generation, in `kaiax/auction/impl/getter.go`.

### Title
Bid transaction generation ignores `bid.MaxGasPrice`, causing valid MaxGasPrice-capped searcher bids to execute at uncapped gas prices - (File: kaiax/auction/impl/getter.go)

### Summary
The V3.0 auction protocol introduces `Bid.MaxGasPrice` [1](#0-0)  so a searcher can cap the gas price they are willing to pay for their bid transaction. However, `GetBidTxGenerator`, which actually constructs the on-chain `AuctionEntryPoint.call()` transaction submitted by the node's own key, never reads or enforces `bid.MaxGasPrice`. Instead it blindly copies the **target transaction's** `GasFeeCap`/`GasTipCap` into the generated bid transaction.

### Finding Description
`GetBidTxGenerator` builds the searcher's bid transaction using the target transaction's fee fields, not any value derived from the bid's own `MaxGasPrice`: [2](#0-1) 

The `MaxGasPrice` field is defined on `BidData` [1](#0-0)  and is accepted through the RPC `SubmitBid` input and copied into the `Bid` struct [3](#0-2) , and it is also EIP-712 signed and encoded into the v3.0 auction call data [4](#0-3) . This indicates `MaxGasPrice` is meant to be a binding, signed slippage/price-cap parameter the searcher relies on. Yet nowhere in the actual transaction-building path (`GetBidTxGenerator`) or in `validateBid`/`insertBid` [5](#0-4)  is the generated transaction's fee capped against `bid.MaxGasPrice`. The generated transaction fee is derived solely from whatever fee cap the *target* transaction happens to carry, which the target sender (a third, unrelated party) controls and can set arbitrarily high.

This mirrors the `createPair()`/`addLiquidity()` bug class: a caller-supplied guardrail meant to protect a party from adverse price movement (there: `amountAMin`/`amountBMin`; here: `MaxGasPrice`) is defined but not actually enforced at the point of execution, allowing the operation to proceed under conditions the party never agreed to.

### Impact Explanation
Because the bid transaction is signed and submitted by the node's own key (`a.InitOpts.NodeKey`) using `tx.GasFeeCap()`/`tx.GasTipCap()` taken from the target transaction, a malicious or careless target-transaction sender can set an arbitrarily high `GasFeeCap`, forcing the searcher's bid transaction (paid for by KAIA already deposited/associated with the searcher in the `AuctionEntryPoint` contract, per `gasBufferEstimate`/deposit model) to execute — and pay gas — at a price far above the `MaxGasPrice` the searcher explicitly capped and cryptographically signed for in their bid. This results in fee abuse: value (KAIA) is extracted from the searcher's on-chain balance/deposit beyond the price ceiling they authorized, which is a concrete unauthorized value movement.

### Likelihood Explanation
Reachable purely by a public, unprivileged actor: any transaction sender can craft a `targetTx` with an inflated `GasFeeCap`/`GasTipCap` and pair it (via the public `auction_submitBid` RPC or coordination with an auctioneer) with a v3.0 bid that specifies a lower `MaxGasPrice`. Since `MaxGasPrice` is never checked against the fields actually placed into the generated transaction, every such crafted bid/target-tx pair will silently bypass the price cap. No validator, node-operator, or consensus-message privilege is required — only a submitted transaction/bid pair.

### Recommendation
In `GetBidTxGenerator` (and/or in `validateBid`), when `bid.MaxGasPrice` is set (v3.0 bids), clamp/validate the generated transaction's `GasFeeCap` (and derived `GasTipCap`) to be `<= bid.MaxGasPrice`, rejecting or capping the bid transaction instead of inheriting the target transaction's fee fields unconditionally.

### Proof of Concept
1. Searcher signs a v3.0 bid with `MaxGasPrice = X` for a given `targetTxHash`.
2. Attacker (target tx sender) submits a target transaction with `GasFeeCap = 100 * X` and `GasTipCap = 100 * X` for the same hash space, or an accomplice submits it via `auction_submitBid`.
3. `AuctionModule.GetBidTxGenerator(tx, bid)` is invoked with `tx` = the attacker's target transaction; it sets `types.TxValueKeyGasFeeCap: tx.GasFeeCap()` and `types.TxValueKeyGasTipCap: tx.GasTipCap()` [2](#0-1)  — ignoring `bid.MaxGasPrice` entirely.
4. The resulting bid transaction is signed and broadcast at 100x the price the searcher capped, and the searcher's deposit is debited accordingly when the block proposer executes it.

Note: I was unable to fully trace the on-chain `AuctionEntryPoint` v3.0 Solidity contract itself (only the mock `AuctionEntryPointMock.sol` and Go bindings were indexed) to confirm whether the contract independently re-validates `maxGasPrice` at execution time; if it does, this specific client-side gap may be mitigated on-chain. A Devin session with full repository access should verify the real `AuctionEntryPoint` contract source (likely not present in this repo, possibly external/deployed separately) before treating this as fully confirmed.

func (bp *BidPool) validateBid(bid *auction.Bid) error {
	blockNumber := bid.BlockNumber

	bp.bidMu.RLock()

	// Check if the auction tx is already in the pool.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		bp.bidMu.RUnlock()
		return auction.ErrBidAlreadyExists
	}

	// 1. The `bid.Sender` must not be in the winner list of the same block number if the new bid isn't equal to the previous bid.
	if bp.senderHasDifferentWinner(bid) {
		bp.bidMu.RUnlock()
		return auction.ErrBidSenderExists
	}
	bp.bidMu.RUnlock()

	curBlock := bp.Chain.CurrentBlock()
	if curBlock == nil {
		return auction.ErrBlockNotFound
	}

	// 2. The `bid.BlockNumber` must be in range of `[currentBlockNumber + 1, currentBlockNumber + allowFutureBlock]`.
	curNum := curBlock.NumberU64()
	if blockNumber <= curNum || blockNumber > curNum+allowFutureBlock {
		return auction.ErrInvalidBlockNumber
	}

	// 3. The `bid.Bid` must be greater than 0.
	if bid.Bid.Sign() <= 0 {
		return auction.ErrZeroBid
	}

	// 4. The data size must be less than the maximum limit.
	if uint64(len(bid.Data)) > BidTxMaxDataSize {
		return auction.ErrExceedMaxDataSize
	}

	// 5. The gas limit must be less than the maximum limit.
	if bid.CallGasLimit > BidTxMaxCallGasLimit {
		return auction.ErrExceedMaxCallGasLimit
	}

	// 6. The `bid.SearcherSig` and `bid.AuctioneerSig` must be valid.
	if err := bp.validateBidSigs(bid); err != nil {
		return err
	}

	return nil
}
