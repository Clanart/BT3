### Title
`header_chain_proofs` Table Has No Reorg Awareness: Deep Reorg Permanently Halts Bridge with No Automated Recovery — (`core/src/bitcoin_syncer.rs`, `core/src/database/header_chain_prover.rs`)

---

### Summary

Clementine maintains two separate block-storage systems: the `bitcoin_syncer` table (which has an `is_canonical` flag and full reorg handling) and the `header_chain_proofs` table (which has **no** `is_canonical` flag, no deletion mechanism, and no reorg-aware queries). When a Bitcoin reorg exceeds `finality_depth`, `fetch_new_blocks` returns a hard error that permanently halts the `BitcoinSyncerTask`. Because `header_chain_proofs` has no recovery path and the error message only suggests a manual operator resync, the bridge enters a liveness-broken state: no new blocks are processed, no new Header Chain Proofs (HCPs) can be generated, and operators who have already fronted BTC for withdrawals cannot send their assert transactions or receive reimbursement.

---

### Finding Description

**Two-table asymmetry**

The `bitcoin_syncer` table has a proper `is_canonical` column and `update_non_canonical_block_hashes` to mark reorged blocks:

```sql
-- core/src/database/schema.sql:100-106
create table if not exists bitcoin_syncer (
    id serial primary key,
    blockhash text not null unique,
    ...
    is_canonical boolean not null default true
);
```

The `header_chain_proofs` table has **no such column**:

```sql
-- core/src/database/schema.sql:16-22
create table if not exists header_chain_proofs (
    block_hash text primary key not null,
    block_header text,
    prev_block_hash text,
    height bigint not null,
    proof bytea
);
```

**Hard halt on deep reorg**

`fetch_new_blocks` in `core/src/bitcoin_syncer.rs` walks backwards from the new tip until it finds a parent in the database. If the walk exceeds `finality_depth`, it returns an unrecoverable error:

```rust
// core/src/bitcoin_syncer.rs:281-288
if new_blocks.len() as u32 > finality_depth {
    return Err(eyre::eyre!(
        "Number of reorged blocks {} is greater than finality depth {}, ...",
        new_blocks.len() - 1,
        finality_depth,
        new_blocks
    ).into());
}
```

This error propagates out of `BitcoinSyncerTask::run_once()`, halting the task. No new `NewBlock` events are emitted, so `FinalizedBlockFetcherTask` stops advancing `next_finalized_height`, and `handle_finalized_block` is never called again.

**`header_chain_proofs` has no reorg-aware queries**

All queries that feed the HCP prover are height-range scans with no canonical filter:

```rust
// core/src/database/header_chain_prover.rs:124-128
let query = sqlx::query_as(
    "SELECT block_hash, block_header
    FROM header_chain_proofs
    WHERE height >= $1 AND height <= $2
    ORDER BY height ASC;",
)
```

```rust
// core/src/database/header_chain_prover.rs:177-178
let query =
    sqlx::query_as("SELECT height FROM header_chain_proofs ORDER BY height DESC LIMIT 1;");
```

There is no `is_canonical` guard, no `DELETE` path, and no equivalent of `update_non_canonical_block_hashes` for this table.

**`FinalizedBlockFetcherTask` silently drops `ReorgedBlock` events**

```rust
// core/src/bitcoin_syncer.rs:578
BitcoinSyncerEvent::ReorgedBlock(_) => {}
```

The task does nothing when a reorg is signalled. `next_finalized_height` is not reset, and no stale entries are removed from `header_chain_proofs`.

**Downstream effect on the operator reimbursement path**

`Verifier::handle_finalized_block` calls `save_unproven_block_cache` and `prove_if_ready` to build the HCP that the operator needs for `send_asserts`:

```rust
// core/src/verifier.rs:3096-3104
self.header_chain_prover
    .save_unproven_block_cache(Some(&mut dbtx), &block_cache)
    .await?;
while (self.header_chain_prover.prove_if_ready().await?).is_some() { ... }
StateManager::<Self>::dispatch_lcp_processed(&self.db, dbtx, block_height).await?;
```

If `BitcoinSyncerTask` is halted, `handle_finalized_block` is never called, no new HCPs are generated, and the operator cannot produce the assert transactions required to claim reimbursement from the vault.

---

### Impact Explanation

When a Bitcoin reorg exceeds `finality_depth` (default 6 blocks):

1. `BitcoinSyncerTask` halts permanently (no automated restart or recovery).
2. No new finalized blocks reach `header_chain_proofs`.
3. `HeaderChainProver::prove_if_ready` / `prove_till_hash` cannot advance past the last proven block.
4. Operators who have already broadcast kickoff transactions and fronted BTC for user withdrawals cannot generate the HCP needed for `send_asserts`.
5. Without assert transactions, the BitVM challenge window expires and operators cannot claim reimbursement from the bridge vault — their fronted BTC is effectively locked until a manual resync is completed.

This constitutes a **liveness break with material fund impact**: operator reimbursement outputs and bridge-controlled UTXOs are inaccessible for an indefinite period.

---

### Likelihood Explanation

Bitcoin reorgs of 6+ blocks are rare on mainnet but have occurred historically. On testnet4 or signet (where Clementine is also deployed), they are more common. An adversary with significant hash power could deliberately trigger a reorg of this depth. The `finality_depth` parameter is operator-configurable, but the default value of 6 is the same confirmation depth that has historically been considered "safe" — yet the ZetaChain report noted that even 14-confirmation thresholds are "dangerously low." The absence of any automated recovery path means even a single such event causes indefinite bridge downtime.

---

### Recommendation

1. **Add `is_canonical` to `header_chain_proofs`** (mirroring `bitcoin_syncer`) and update all queries (`get_block_info_from_range`, `get_latest_finalized_block_height`, `get_next_unproven_block`, `get_next_n_non_proven_block`) to filter `WHERE is_canonical = true`.

2. **Handle `ReorgedBlock` events in `FinalizedBlockFetcherTask`**: when a reorg is detected, mark the corresponding `header_chain_proofs` entries as non-canonical and reset `next_finalized_height` to the common ancestor height.

3. **Add automated recovery in `BitcoinSyncerTask`**: instead of returning a hard error on deep reorgs, attempt to roll back `header_chain_proofs` to the common ancestor and re-sync from there, emitting appropriate events.

4. **Expose a recovery RPC or admin endpoint** that allows operators to trigger a controlled resync of `header_chain_proofs` without requiring a full node restart and config change.

---

### Proof of Concept

**Step 1 — Normal operation**: `finality_depth = 6`. Blocks 1–100 are synced. Block 94 is finalized and saved to `header_chain_proofs`. `next_finalized_height = 95`.

**Step 2 — Deep reorg**: A competing chain of 7 blocks replaces blocks 94–100. `fetch_new_blocks` walks back 7 steps, finds `new_blocks.len() (8) > finality_depth (6)`, and returns:

```
"Number of reorged blocks 7 is greater than finality depth 6 ..."
```

**Step 3 — Halt**: `BitcoinSyncerTask::run_once()` returns `Err(...)`. The task runner logs the error and retries, but the reorg is still present, so every retry fails identically.

**Step 4 — Downstream freeze**: `FinalizedBlockFetcherTask` receives no new `NewBlock` events. `Verifier::handle_finalized_block` is never called. `header_chain_proofs` is frozen at block 94. `HeaderChainProver::prove_if_ready` returns `Ok(None)` indefinitely.

**Step 5 — Operator loss**: An operator who broadcast a kickoff transaction at block 95 (before the reorg) and fronted BTC for a user withdrawal cannot generate the HCP for `send_asserts`. The BitVM challenge window advances. Without assert transactions, the operator cannot claim reimbursement from the vault. Their fronted BTC remains locked until a human operator manually increases `finality_depth` and triggers a full resync of `header_chain_proofs`.
