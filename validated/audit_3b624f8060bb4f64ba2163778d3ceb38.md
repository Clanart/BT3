## Title
Unhandled uint64 overflow in `compute_assert_height()` causes a mempool spend-bundle-triggered crash - (File: `chia/full_node/mempool_manager.py`)

### Summary
`compute_assert_height()` sums an untrusted, attacker-controlled relative-time/height field taken directly from CLVM condition arguments (`spend.seconds_relative`, `spend.before_seconds_relative`, `spend.height_relative`, `spend.before_height_relative`) with a coin's confirmed timestamp/height, then casts the result with `uint64()`/`uint32()` without any bounds check [1](#0-0) . This is the same bug class as CVE-2025-47268: unchecked arithmetic on attacker-influenced time/interval values that can exceed the representable range, causing either an application error or corrupted data instead of a controlled, validated rejection.

### Finding Description
`ASSERT_SECONDS_RELATIVE` / `ASSERT_BEFORE_SECONDS_RELATIVE` / `ASSERT_HEIGHT_RELATIVE` / `ASSERT_BEFORE_HEIGHT_RELATIVE` condition arguments are parsed as CLVM integers and stored in `SpendConditions` as `uint64`/`uint32` values, so each individual relative-lock value is itself capped at `UINT64_MAX`/`UINT32_MAX`. However, `compute_assert_height()` adds this attacker-supplied value to the *coin's confirmed timestamp/height* before re-casting to `uint64`/`uint32`:

```python
s = uint64(removal_coin_records[bytes32(spend.coin_id)].timestamp + spend.seconds_relative)
``` [2](#0-1) 

If an attacker sets `seconds_relative` (or `before_seconds_relative`, or the height equivalents) close to `UINT64_MAX`/`UINT32_MAX`, the Python-level sum exceeds the maximum value representable by the target type. The `sized_ints` types used throughout the codebase (`chia_rs.sized_ints.uint64`) are confirmed to raise `OverflowError`/`ValueError` on out-of-range construction rather than silently wrapping, as demonstrated by `Coin`'s constructor behavior with an out-of-range amount:

```python
with pytest.raises(OverflowError, match="int too big to convert"):
    Coin(H1, H2, 0x10000000000000000)
``` [3](#0-2) 

`compute_assert_height()` is invoked from `MempoolManager`'s spend-bundle admission path, `validate_spend_bundle` / `add_spend_bundle`, immediately after `check_time_locks()` (the Rust consensus check) succeeds, with **no surrounding try/except**:

```python
timelocks: TimelockConditions = compute_assert_height(removal_record_dict, conds)
``` [4](#0-3) 

Because the individual relative values already pass the Rust `check_time_locks()` gate (that function only rejects if the resulting *lock is violated*, e.g. not enough time has passed — it does not need to know whether the sum overflows uint64/uint32 the way the Python helper does), a spend bundle can reach `compute_assert_height()` with a relative-lock value large enough that `coin.timestamp + spend.seconds_relative` (or the height equivalent) exceeds `UINT64_MAX`/`UINT32_MAX`, triggering an unhandled exception inside the mempool's per-spend-bundle admission routine.

### Impact Explanation
This maps to the "spend-triggered transaction-processing halt" impact category. A single unprivileged wallet user or RPC caller submitting one crafted spend bundle (a normal, otherwise valid CLVM condition with an oversized relative timelock argument) can raise an unhandled `OverflowError`/`ValueError` deep inside `MempoolManager`'s spend bundle admission pipeline, which is on the hot path for every incoming transaction (`new_transaction` / `send_transaction` RPC / P2P relay). Depending on how far up the call stack the exception propagates before being caught generically, this can disrupt mempool processing for that request, is a direct availability concern for the full node's transaction-processing, and is directly analogous to the CVE's "denial of service via crafted...packet causing application error."

### Likelihood Explanation
Reachable by any unprivileged spend-bundle submitter without requiring any signature validity beyond what's needed to get to the timelock-computation stage, and without needing to control block production or peer behavior — a single `push_tx` RPC call or P2P transaction relay containing a spend with `ASSERT_SECONDS_RELATIVE`/`ASSERT_BEFORE_SECONDS_RELATIVE`/`ASSERT_HEIGHT_RELATIVE`/`ASSERT_BEFORE_HEIGHT_RELATIVE` set near `UINT64_MAX`/`UINT32_MAX` is sufficient to reach the vulnerable addition.

### Recommendation
In `compute_assert_height()` (`chia/full_node/mempool_manager.py`), clamp/saturate the relative-lock sums instead of performing raw arithmetic followed by an unguarded type cast — e.g., use saturating addition (`min(coin_value + relative, UINT64_MAX)`) or explicitly catch overflow and treat it as an immediate/permanent validation failure (analogous to how `IMPOSSIBLE_HEIGHT_ABSOLUTE_CONSTRAINTS`/`IMPOSSIBLE_SECONDS_ABSOLUTE_CONSTRAINTS` are already handled) rather than allowing an exception to propagate out of the mempool admission path.

### Proof of Concept
1. Fund a wallet-controlled coin whose confirmed timestamp is a typical current epoch timestamp (e.g., ~1.7×10⁹).
2. Construct a coin spend whose puzzle reveals `(ASSERT_SECONDS_RELATIVE 18446744073709551615)` (i.e., `UINT64_MAX`) or a similarly maximal value close enough that `coin.timestamp + value > UINT64_MAX`.
3. Submit the resulting `SpendBundle` via RPC (`push_tx`) to a full node.
4. `MempoolManager.add_spend_bundle` → `validate_spend_bundle` calls `compute_assert_height(removal_record_dict, conds)` [4](#0-3) , which executes `uint64(removal_coin_records[...].timestamp + spend.seconds_relative)` [2](#0-1)  and raises an unhandled overflow exception instead of returning a structured `Err`.

Note: I was unable to directly inspect the Rust `check_time_locks()`/`sized_ints` implementation source (it lives in the external `chia_rs` crate, not indexed in this repository), so I could not confirm from source exactly which values pass the Rust-side gate before reaching the vulnerable Python-side sum, nor the exact exception-propagation/crash behavior at the RPC/API layer. This is inferred from the observed `uint64`/`Coin` overflow behavior in this repo's tests and the absence of any exception handling around `compute_assert_height()`'s call site.
