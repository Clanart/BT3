### Title
Legacy `event: file` block rules only check `new_string`, silently bypassed by delivering identical payload via `Write`'s `content` field - ([File: plugins/hookify/core/rule_engine.py])

### Finding Description
When a hookify rule uses the legacy simple `pattern` field with `event: file`, `config_loader.Rule.from_dict` auto-infers the condition field as `new_text` (never `content`) regardless of which tool actually triggers it: [1](#0-0) .

At evaluation time, `pretooluse.py` maps `Write`, `Edit`, and `MultiEdit` all to the same `event='file'` and loads the same rule set without tool-specific field remapping: [2](#0-1) .

`RuleEngine._extract_field` then resolves the `new_text` field for `Write`/`Edit` tools strictly to `tool_input.get('new_string', '')`, with no fallback to `tool_input.get('content')`: [3](#0-2) 

Note the asymmetry: the `content` field branch (line 236-238) correctly falls back across both tool shapes (`tool_input.get('content') or tool_input.get('new_string', '')`), but the `new_text`/`new_string` branch (line 239-240) does not have the equivalent fallback to `content`.

Since `Write` tool calls populate `tool_input['content']` (not `new_string`), a legacy `pattern`-based `file` rule (which is auto-mapped to field `new_text`) will evaluate `tool_input.get('new_string', '')` against a `Write` call, always resolving to the empty string `''`. `_check_condition` treats `''` as a valid (non-`None`) field value and applies `regex_match('' , pattern)`, which returns `False` for any non-trivial pattern. So the rule never matches for `Write`, while the identical payload delivered via `Edit`'s `new_string` field is correctly matched and blocked.

This breaks the "deny means deny" invariant: the same malicious content (e.g., a hardcoded secret, dangerous code pattern, or destructive snippet) that is blocked when written through `Edit` silently passes when the attacker chooses `Write` instead, with `evaluate_rules` returning `{}` (no block, no warning) for `Write`.

### Impact Explanation
A legacy simple-pattern `event: file, action: block` rule (the most common/legacy rule format documented in `README.md` and the `writing-rules` skill) can be bypassed entirely by using `Write` instead of `Edit` to introduce the exact content the rule was meant to block. This is a real hook/policy enforcement bypass: content-based guardrails (e.g. blocking hardcoded credentials, dangerous eval/exec patterns, or other flagged content) configured by the user/project are silently defeated for any new-file creation or full-file overwrite via `Write`, without any warning or block being surfaced to the user. This is a trust-boundary/enforcement bypass matching an "approval/hook bypass" impact class, since the PreToolUse hook is the mechanism relied upon to deny/warn on dangerous file operations.

### Likelihood Explanation
Highly likely and trivially repeatable: any project using the documented legacy single-`pattern` rule format for `event: file` (shown as the primary example format in `README.md` lines 171-185 and `SKILL.md`) is affected. The condition is met purely by how Claude (or an attacker steering Claude, e.g. via prompt injection or malicious repository content) chooses to perform a file write — no special privilege is needed, since Claude routinely chooses between `Edit` and `Write` based on context (e.g., creating a new file vs. modifying one). Any flow that results in `Write` being used instead of `Edit` for matching content silently bypasses the rule.

### Recommendation
In `RuleEngine._extract_field`, make the `new_text`/`new_string` branch tool-aware like the `content` branch, falling back to `tool_input.get('content')` when `new_string` is absent (i.e., for `Write` calls):
```python
elif field == 'new_text' or field == 'new_string':
    return tool_input.get('new_string') or tool_input.get('content', '')
```
Additionally, consider auto-inferring the legacy `pattern` field as `content` (not `new_text`) when the matching tool could be `Write`, or better, evaluate both `new_string` and `content` unconditionally for any `file` event rule so the same content is checked regardless of tool used.

### Proof of Concept
Differential unit test against `RuleEngine.evaluate_rules`:
```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret",
    enabled=True,
    event="file",
    conditions=[Condition(field="new_text", operator="regex_match", pattern="SECRET_KEY")],
    action="block",
    message="Secret detected",
)
engine = RuleEngine()

edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "a.py", "old_string": "x", "new_string": "SECRET_KEY=123"},
}
write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "a.py", "content": "SECRET_KEY=123"},
}

edit_result = engine.evaluate_rules([rule], edit_input)
write_result = engine.evaluate_rules([rule], write_input)

assert edit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
# BUG: this currently fails because Write bypasses the rule
assert write_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", \
    f"Write bypassed block rule that Edit correctly blocked: {write_result}"
```
Expected (fixed) behavior: both `edit_result` and `write_result` return the `hookSpecificOutput.permissionDecision == "deny"` block response. Current (vulnerable) behavior: `write_result` is `{}` (no block).
