### Title
Line-index diff selection reapplied to a re-fetched, possibly different diff can silently corrupt partial commits - ([File: app/src/lib/git/apply.ts])

### Summary
The bug report describes a broken invariant class: a value that represents a point-in-time decision (voting power / selected lines) is instead recomputed from live mutable state at action time, so the recorded action silently diverges from what the user actually approved. The direct analog in GitHub Desktop is in the partial-commit staging path: `applyPatchToIndex` re-fetches the working directory diff at the moment of staging and blindly reapplies the user's previously captured, index-based line `selection` to it, without verifying the new diff is the same one the selection was built against.

### Finding Description
When a user stages a subset of lines in a modified file, the UI builds a `DiffSelection` keyed by absolute line index (`hunk.unifiedDiffStart + lineIndex`) against the diff that was rendered to them [1](#0-0) . That `WorkingDirectoryFileChange` (carrying `file.selection`) is later passed into `stageFiles` → `applyPatchToIndex`, which does not reuse the diff the user reviewed; instead it calls `getWorkingDirectoryDiff` again to fetch a fresh diff immediately before formatting the patch: [2](#0-1) 

`formatPatch` then walks the *new* diff's hunks and tests `file.selection.isSelected(absoluteIndex)` using indices computed from the *new* hunk layout [3](#0-2) . If the file's on-disk content changed between when the selection was made and when staging runs (e.g. lines shifted due to a git clean/smudge filter, an LFS filter, or any background process that rewrites the file, all of which can be driven by content defined in a cloned/fetched repository via `.gitattributes`), the hunk boundaries and `unifiedDiffStart` offsets shift. The old index-based selection is then evaluated against unrelated lines in the new diff, so `formatPatch` builds a patch that stages/omits different content than what the user actually checked in the UI — with no error, warning, or re-validation.

This is in clear contrast to the store's other diff-consuming code paths, which explicitly guard against exactly this staleness:
- `updateChangesWorkingDirectoryDiff` recomputes `selectableLines` from the new diff and drops now-invalid selections before use [4](#0-3) .
- `_changeFileSelection` bails out entirely if the underlying selection state changed while the diff was loading [5](#0-4) .

`applyPatchToIndex` has no equivalent check: it re-derives a diff and immediately trusts the old selection's raw indices against it.

### Impact Explanation
This can cause GitHub Desktop to silently commit and push content the user never selected/approved — additions the user explicitly excluded could be included, or lines the user intended to include could be dropped or misapplied against the wrong hunk, resulting in corrupted commits pushed to a real remote under the user's identity. This matches "silent corruption of what the user commits or pushes," one of the explicitly valid impact classes.

### Likelihood Explanation
The precondition — file content changing on disk between the moment a partial selection is made and the moment `stageFiles`/`applyPatchToIndex` executes — is a realistic race in normal usage (Desktop continuously polls working-directory status/diffs, and many repositories configure git clean/smudge or LFS filters that rewrite file contents as part of ordinary git plumbing operations triggered from a cloned repository's `.gitattributes`). No index-shape validation or hash/oid check ties the re-fetched diff back to the diff the selection was built from, so nothing in the code path prevents the mismatch once the underlying content shifts.

### Recommendation
Before formatting the patch in `applyPatchToIndex`, validate that the diff used to build `file.selection` still matches the freshly-fetched diff (e.g. compare hunk boundaries/oids or line counts), and if it doesn't, refuse to stage/commit and force the UI to reload the diff and require the user to reconfirm their selection — mirroring the staleness guard already used in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. Clone/open a repository that has a `.gitattributes` clean/smudge filter (or any external tool) which non-idempotently rewrites tracked file content on checkout/read (e.g. reformats or reorders lines) each time git touches the file.
2. In Desktop, open the file's diff and select a subset of lines/hunks for a partial commit (builds `DiffSelection` with absolute indices tied to the currently displayed diff).
3. Trigger the filter/background process to alter the file's content on disk (naturally happens via Desktop's periodic status/diff refresh calling into git plumbing that invokes the filter) so hunk boundaries shift.
4. Commit the partial selection. `applyPatchToIndex` re-fetches the diff (now shifted) and applies the old absolute-index selection to it via `formatPatch`, producing a patch whose staged content differs from what was shown/checked in the UI, silently corrupting the resulting commit.
