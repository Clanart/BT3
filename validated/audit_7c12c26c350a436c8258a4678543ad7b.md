## Title
Unauthenticated `address` field in `pallet-state-coprocessor::handle_get_requests` lets anyone redirect relayer reputation-reward minting to an arbitrary account - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

## Summary
The `H-12` report is fundamentally about a value/credit being attributed to the wrong entity because the code trusts a field that does not actually reflect the real economic actor (vault-share holder). The same broken invariant — "credit is attributed based on caller-supplied data instead of a value derived from an authenticated identity" — exists in Hyperbridge's `pallet-state-coprocessor::handle_get_requests`, which mints `ReputationAsset` reward tokens to whatever `address` the caller places in the unsigned `GetRequestsWithProof` payload, with no signature or identity check binding that address to whoever actually produced the state proof.

## Finding Description
`handle_get_requests` verifies the source/response state proofs, meters bandwidth, and then mints reputation to a relayer: [1](#0-0) 

```rust
let rate = pallet_messaging_incentives::MintPerByte::<T>::get();
if !rate.is_zero() && total_bytes > 0 {
    if let Ok(bytes32) = <[u8; 32]>::try_from(address.as_slice()) {
        let relayer: T::AccountId = bytes32.into();
        ...
        <T as pallet_messaging_incentives::Config>::ReputationAsset::mint_into(&relayer, amount)
        ...
    }
}
```

`address` is the fourth field of `GetRequestsWithProof`, which is entirely attacker-controlled: [2](#0-1) 

This message is submitted via `handle_unsigned`, an **unsigned** extrinsic (`ensure_none(origin)`), so there is no signer account to fall back on, and `validate_unsigned` only dedups on the *set of request hashes* being certified — never on the submitter or the `address` field: [3](#0-2) 

Contrast this with the sibling pallet `messaging-incentives`, which mints the same reward asset but **cryptographically recovers the relayer's account from the sr25519 signature on the message**, so the mint recipient is provably the entity that produced the delivery: [4](#0-3) 

`handle_get_requests` has no equivalent authentication step for `address` — it is copied straight from caller-supplied bytes into the mint call. State proofs for Get requests are derived from already-public chain state (state commitments Hyperbridge already trusts), so constructing a valid `GetRequestsWithProof` does not require possession of any relayer-specific secret; it only requires knowledge of the commitment and the proof data, both of which are public once the source/destination state roots exist. Anyone monitoring pending `GetRequest`s can assemble the identical proof payload that a legitimate relayer would submit and simply substitute their own `address`.

## Impact Explanation
This is a "reward claims" / "logic attack" class bug per the impact gate: an unprivileged actor with no relayer registration, no signing key tied to any delivery, and no on-chain role can direct protocol reward minting (`ReputationAsset::mint_into`) to an account of their choosing, scaled by `bytes × MintPerByte`. This breaks the intended one-to-one binding between "did the verifiable off-chain work of assembling/relaying the proof" and "receives the reward," letting an attacker harvest the entire reward stream meant to incentivize honest relaying, purely by racing to submit the unsigned extrinsic first with their own address (no signature, no stake, no fee — the mint is `Pays::No`).

## Likelihood Explanation
Likelihood is high whenever `MintPerByte` is non-zero: the extrinsic is unsigned, callable by any full node/light client with mempool access, requires no economic bond, and the only prerequisite (a valid `GetRequestsWithProof` for an unanswered `GetRequest`) is derivable from public chain state. No relayer-set membership, no admin/governance compromise, and no malicious peer assumption is required — only correct, publicly-available proof construction plus fast submission.

## Recommendation
Bind the reward recipient to a value that is cryptographically verified as part of message validation, mirroring `messaging-incentives::on_executed`: e.g., require a signature over the request batch from the `address` being credited (or recover the submitter's account from a required signature on the unsigned extrinsic) before minting, and validate that recovered/attested identity against `address` rather than trusting the raw field.

## Proof of Concept
1. Wait for any dApp to dispatch a `GetRequest` (visible on-chain as a commitment on the source chain, per `RequestCommitments`).
2. Once the destination state root Hyperbridge trusts covers the requested height, construct the `source` membership proof and `response` state proof from public RPC data — no relayer credentials needed.
3. Submit `StateCoprocessor::handle_unsigned(GetRequestsWithProof { requests, source, response, address: <attacker_account_bytes32> })` as an unsigned extrinsic before the legitimate relayer's equivalent submission lands.
4. `handle_get_requests` verifies the proofs (they are valid, since attacker copied the real data), computes `total_bytes`, and mints `rate * total_bytes` of `ReputationAsset` to `attacker_account` — see the mint call at [5](#0-4) 
— with no check that the attacker performed any of the relaying/proving work.

```markdown
1. `pallet-ismp` finishes executing a batch of messages and invokes
   [`FeeHandler::on_executed`].
2. This pallet reads the current `MintPerByte` rate. If it is zero, nothing
   happens (the pallet stays installed but inactive).
3. For each `Request`/`Response` message it:
   - Computes `bytes = max(body_size, 32)` — the same floor `pallet-bandwidth`
     uses, so trivial payloads can't game the mint by costing zero.
   - Multiplies `bytes × MintPerByte` to get the mint amount.
   - Recovers the relayer's account from the sr25519 signature on the message's
     `signer` field.
   - Mints that amount of `ReputationAsset` to the relayer.
```
