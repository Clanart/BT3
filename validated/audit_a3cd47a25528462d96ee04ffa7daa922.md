## Title
Wallet trusts unvalidated, offer-embedded `driver_dict` metadata to persist CR-CAT authorization state - (File: `chia/wallet/trade_manager.py`)

### Summary
When a Chia wallet accepts or processes a trade offer, the `driver_dict` metadata bundled inside the offer — which declares an asset's type, TAIL, and, for Credential-Restricted CATs (CR-CATs), its `authorized_providers` and `proofs_checker` — is taken at face value and persisted into a brand-new local wallet record without ever being validated against the actual curried CR-CAT puzzle contained in the offer's own coin spends. This mirrors the Doorkeeper OIDC DCR flaw, where `scope` was persisted verbatim from client input with no check against the server's true, authoritative configuration.

### Finding Description
`TradeManager.maybe_create_wallets_for_offer` iterates the assets in an incoming offer and, for any asset the wallet does not yet track, calls `create_wallet_for_puzzle_info` using `offer.driver_dict[key]` directly: [1](#0-0) 

`WalletStateManager.create_wallet_for_puzzle_info` then dispatches to the asset-specific wallet class's `create_from_puzzle_info`, again using the caller-supplied `puzzle_driver` unmodified: [2](#0-1) 

For CR-CATs, `CRCATWallet.create_from_puzzle_info` reads `authorized_providers` and `proofs_checker` straight out of that driver info and persists them as the new wallet's authoritative `CRCATInfo`: [3](#0-2) 

Nowhere in this path is `puzzle_driver["also"]["authorized_providers"]` / `["proofs_checker"]` cross-checked against the actual `CREDENTIAL_RESTRICTION` layer curried into the real coin puzzle reveal that is part of the same offer's spend bundle (the way `CRCAT.get_next_from_coin_spend`/`match_cr_layer` derive these values from consensus data): [4](#0-3) 

Once persisted, this attacker-chosen `authorized_providers`/`proofs_checker` pair becomes the wallet's *local source of truth* for that asset, and is used later to decide which Verified Credential (VC) is eligible to authorize spends of that asset and whether a VC is even required, e.g. in `check_for_requested_payment_modifications` and `CRCATWallet.claim_pending_approval_balance`: [5](#0-4) [6](#0-5) 

This is structurally the same defect as the reported CVE: a piece of authorization-relevant configuration (`scopes` in Doorkeeper, `authorized_providers`/`proofs_checker` in Chia) supplied by an untrusted counterparty (a self-registering OAuth client / an offer-creating trading counterparty) is written into a persistent record without validating it against the actual authoritative source (the server's configured scope set / the coin's real curried CR layer).

### Impact Explanation
A malicious offer creator can cause a victim's wallet to record incorrect `authorized_providers`/`proofs_checker` for a CR-CAT it has never seen before, purely from unauthenticated offer metadata. This corrupts the wallet's local authorization bookkeeping for that asset: it can make the wallet believe a different DID/VC governs the asset than actually does on-chain, select the wrong (or an attacker-influenced) VC when later attempting `claim_pending_approval_balance`, or misjudge whether a VC is required at all when constructing/accepting further offers for that asset — all decisions that determine which VC is presented to authorize movement of value. While the underlying CLVM puzzle re-enforces the true curried restriction at spend time (limiting the worst-case outcome to a failed/rejected spend rather than an on-chain forged authorization), the wallet-side authorization state is nonetheless persisted from unvalidated, attacker-controlled input, which is the same root-cause class as the CVE and is a genuine trust-boundary violation reachable by any offer counterparty.

### Likelihood Explanation
Any wallet user who receives and processes an offer file (via `take_offer`/`respond_to_offer`) for an asset type they don't already track triggers `maybe_create_wallets_for_offer`, which is on the default acceptance path — no special configuration or privilege is required by the offer creator, and no signature/consensus check gates the `driver_dict` values before they are persisted locally.

### Recommendation
Before persisting driver info for a new wallet from `offer.driver_dict`, re-derive the puzzle info from the actual coin's puzzle reveal in the offer's spend bundle (as `Offer.from_spend_bundle`/`match_puzzle` already do) and reject or ignore any `driver_dict` entry that disagrees with the consensus-derived puzzle structure, rather than trusting the caller-supplied `PuzzleInfo` directly in `create_wallet_for_puzzle_info` / `CRCATWallet.create_from_puzzle_info`.

### Proof of Concept
1. Attacker crafts an `Offer` (or a `TakeOffer`/`CreateOfferForIDs` RPC request with an explicit `driver_dict`) that includes an asset id whose real on-chain CR-CAT puzzle curries `authorized_providers = [attacker_DID]`, but whose embedded `driver_dict[asset_id]` declares `also.authorized_providers = [victim_DID]` (or a different `proofs_checker`).
2. Victim wallet receives/takes the offer; since it has no existing wallet for that asset id, `TradeManager.maybe_create_wallets_for_offer` → `WalletStateManager.create_wallet_for_puzzle_info` → `CRCATWallet.create_from_puzzle_info` persists the attacker-declared, unvalidated `authorized_providers`/`proofs_checker` as the new local `CRCATInfo`.
3. Subsequent local wallet operations (`get_vc_with_provider_in_and_proofs`, `check_for_requested_payment_modifications`, `claim_pending_approval_balance`) now make authorization decisions — which VC to use, whether a VC is required — based on this false, offer-supplied configuration instead of the coin's true curried restriction.

def match_cr_layer(
    unknown_puzzle: UnknownPuzzle,
) -> tuple[list[bytes32], Program, Program] | None:
    if unknown_puzzle.mod is None or unknown_puzzle.curried_args is None:
        return None
    extra_unknown_puzzle = UnknownPuzzle(known_program=unknown_puzzle.mod)
    if extra_unknown_puzzle.mod == CREDENTIAL_RESTRICTION and extra_unknown_puzzle.curried_args is not None:
        return (
            [bytes32(provider.as_atom()) for provider in extra_unknown_puzzle.curried_args[1].as_iter()],
            extra_unknown_puzzle.curried_args[2],
            unknown_puzzle.curried_args[1],
        )
    else:
        return None
