## Analysis

The Pendle bug's root cause is a **positional/index-based state that is carried over across a mutation of the underlying indexed collection without validating that the identity behind each index is unchanged** — `postExpiry.firstRewardIndex[token]` is frozen while `rewardTokens` can still grow, so a stale numeric position gets reused for semantically different data, corrupting the computed delta.

GitHub Desktop has a structurally identical pattern in its **working-directory partial-commit line selection** logic.

`DiffSelection` tracks which lines a user has selected for a partial commit purely by **absolute numeric line index** into the diff, not by line content/identity: [1](#0-0) 

When the working directory diff is reloaded (e.g. after the underlying file's diff changes for any reason — pull/merge, checkout, external tool, stash pop), `updateChangesWorkingDirectoryDiff` explicitly acknowledges that the diff may have changed and only *filters* the previously diverging line indices against the new set of `selectableLines` — it does **not** verify that the content at a persisted index is still the same line: [2](#0-1) 

The filtering itself, `withSelectableLines`, is purely membership-based: [3](#0-2) 

That stale, index-keyed selection state is later used verbatim to build the actual patch that gets committed: [4](#0-3) 

If a hunk shifts (lines added/removed elsewhere in the file, e.g. due to a merge brought in by `git pull` from an attacker-controlled remote) between the time a user marks certain lines as selected/unselected and the time the diff is refreshed and the commit is created, an index that used to point at line X may now point at an unrelated line Y that happens to still be "selectable" (an addition/deletion line). The stale selected/unselected flag for that index carries over onto line Y with no identity check, so the user can end up **silently committing (or omitting) a line they never actually reviewed or intended** — this is the same "reuse of an unvalidated positional index across a state mutation" flaw as the Pendle report, just manifesting as commit-content corruption instead of frozen rewards.

### Title
Stale, index-based partial-commit line selection can silently include/exclude unreviewed lines after a diff refresh - (File: app/src/lib/stores/app-store.ts, app/src/models/diff/diff-selection.ts)

### Summary
`DiffSelection` identifies selected/deselected lines purely by absolute numeric index into the diff. When the working-directory diff is recomputed (e.g. following a `pull`/merge that changes surrounding file content), the persisted selection is re-validated only by checking whether an index is still "selectable", not whether it still corresponds to the same physical line. This mirrors the Pendle bug's core flaw of trusting a stale positional index against a mutated indexed collection.

### Finding Description
`updateChangesWorkingDirectoryDiff` reloads the diff for the selected file and preserves the prior `DiffSelection` by calling `withSelectableLines(selectableLines)` [2](#0-1) . The method's own comment admits the shortcut: it does not validate that "selected lines still exist," it only recomputes which indices are structurally selectable in the new diff. `withSelectableLines` then merely intersects the old `divergingLines` set with the new `selectableLines` set by index membership [5](#0-4) , with no comparison of line text/content between the old and new diff at that index.

Because hunk boundaries and `unifiedDiffStart` offsets shift whenever lines are added/removed anywhere earlier in a hunk or file, the same absolute index can point to a completely different line of code after a refresh. If that new line happens to also be an includeable (add/delete) line, the old True/False selection state is blindly reapplied to it.

`formatPatch`, which is the function that actually produces the patch handed to `git apply --cached` for the commit, consumes this selection state directly via `file.selection.isSelected(absoluteIndex)` [4](#0-3) , so the corrupted selection flows straight into what is committed.

### Impact Explanation
A user who has partially selected lines for a commit and then triggers any action that changes the underlying diff structure between selection and commit (most naturally a `pull`/merge bringing in remote — i.e. attacker/collaborator-controlled — commits that touch the same file) can end up committing a line they never selected, or omitting a line they explicitly selected, without any warning. This is a silent corruption of what the user commits/pushes, sourced from remote (fetched) repository content.

### Likelihood Explanation
Requires a specific but realistic sequence: user has a file open with a partial selection, and a diff-changing event (pull/merge/checkout/stash) occurs before the commit is made. No admin rights, local malware, or leaked credentials are needed — only ordinary use of "fetch/pull" against a repository whose remote content an attacker/malicious collaborator can influence.

### Recommendation
Do not carry over line-selection state by raw index across a diff refresh. Instead, key the diverging-lines state (or validate it) against a content-stable identity — e.g. line text plus its type/hunk context — and drop any prior selection whose underlying content at that index no longer matches, defaulting to unselected, similar to how the Pendle fix ignores unvalidated/uninitialized index state rather than trusting it blindly.

### Proof of Concept
1. User modifies `file.txt`, opens it in Desktop's Changes view, and partially selects lines 10–12 for commit while leaving the rest unselected.
2. Before committing, the user runs `git pull`, merging in a remote commit that also touches `file.txt` (adds lines earlier in the file), shifting all subsequent line offsets.
3. Desktop calls `updateChangesWorkingDirectoryDiff`, which calls `withSelectableLines` on the *old* `DiffSelection`, preserving the old absolute indices 10–12 as "selected" as long as those indices remain includeable lines in the new diff — even though they now refer to different content than what the user originally reviewed and selected.
4. The user commits; `formatPatch` uses `isSelected(absoluteIndex)` against the new diff, producing a patch containing lines the user never actually reviewed/selected.

   * Returns a copy of this selection instance with a specified set of
   * selectable lines. By default a DiffSelection instance allows selecting
   * all lines (in fact, it has no notion of how many lines exists or what
   * it is that is being selected).
   *
   * If the selection instance lacks a set of selectable lines it can not
   * supply an accurate value from getSelectionType when the selection of
   * all lines have diverged from the default state (since it doesn't know
   * what all lines mean).

  public withSelectableLines(selectableLines: Set<number>) {
    const divergingLines = this.divergingLines
      ? new Set([...this.divergingLines].filter(x => selectableLines.has(x)))
      : null

    return new DiffSelection(
      this.defaultSelectionType,
      divergingLines,
      selectableLines
    )
  }
