## Title
NFT minter can forge an eve NFT's owner/minter DID to an arbitrary DID without that DID's consent, enabling deceptive offer settlement - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
The Teller `updateCommitment()` bug allowed a party that fully controls a resource (a lending commitment) to unilaterally reassign the "owner" field of that resource to an arbitrary third-party address, without any consent/authorization from that third party, and then exploit the resulting mis-attribution against an unsuspecting counterparty. Chia's NFT ownership layer has the same class of gap at NFT minting time: an NFT minter can set the initial `current_owner` (DID) field of a brand-new "eve" NFT to any DID identifier — including a DID the minter does not control and that never approved the association — because the DID-consent check (a puzzle announcement from the DID's own singleton) that guards *later* ownership transfers is not enforced for the very first (eve) spend.

### Finding Description
When minting an NFT with DID support, `NFTWallet.generate_new_nft()` builds the eve inner puzzle with `current_owner` initially empty: [1](#0-0) 

and then spends that eve coin, passing `new_owner=did_id` as a magic `-10` condition. The code explicitly documents that this DID value is unauthenticated at this point: [2](#0-1) 

For a *non-eve* NFT (an NFT that already has an existing DID owner), the CLVM ownership/transfer-program layer requires an announcement produced by spending the *target* DID's own singleton coin before the new owner can be set — this is exactly what `test_default_transfer_program` demonstrates (all of DID/CAT/XCH announcements are required together, and the DID announcement can only be produced by spending the singleton whose launcher ID matches the target DID). This mirrors the "commitment must not be reassignable without the new party's consent" fix that Teller was missing.

However, for the eve spend, no such requirement exists: the minter directly curries `current_owner=b""` into the ownership layer and then, in the *same* mint transaction, sets `new_owner=did_id` via the standard -10 condition path with `did_inner_hash` derived from `get_did_approval_info()` — but that helper only looks up a DID *the minter's own wallet controls* (`self.did_id`), not the DID being assigned. If a caller supplies an arbitrary foreign `did_id` string/bytes for this parameter at the API layer, the wallet still performs the eve mint; the client-side "must own the DID" checks are wallet UX guards, not consensus-enforced requirements on the eve puzzle itself.

The resulting `owner_did` / `minter_did` value is trusted and displayed as if it were an authenticated attribution:

- `WalletStateManager.get_minter_did()` reads this same unauthenticated eve-spend value directly off-chain from the mint solution and stores it as `minter_did`: [3](#0-2) 
- It is persisted to the NFT store and surfaced through `NFTInfo.owner_did` / `NFTInfo.minter_did`, which are shown to users/marketplaces as "Owner DID" / "Minter DID": [4](#0-3) [5](#0-4) 

This is precisely the Teller pattern: a party that fully controls a resource (the eve NFT) can label it with a third party's identity (a DID) that never agreed to the association, and that forged identity is what counterparties (buyers, marketplaces, offer takers) rely on to evaluate the resource's legitimacy/value.

### Impact Explanation
A malicious minter can craft an NFT whose `owner_did`/`minter_did` falsely claims affiliation with a specific, recognizable DID (e.g., a verified collection, artist, or organization's DID) without that DID's owner ever approving or even being aware of it. A buyer who takes an offer for this NFT — trusting the DID attribution shown by their wallet/marketplace UI, exactly as NFT marketplaces are designed to be used — pays real value (XCH/CAT) for what is effectively a counterfeit, unaffiliated NFT. This is a concrete "forged asset identity" leading to "offer settlement theft": the victim's funds move to the attacker in exchange for an asset whose provenance/ownership claim is fabricated, with no cryptographic authorization from the impersonated DID. The comment in the source code itself acknowledges the trust gap ("WARNING: wallets should always ignore DID value for eve coins as they can be set to any DID without approval"), which is a defense that depends on every wallet/marketplace implementation to correctly special-case eve coins — a fragile, easily-missed mitigation, not a consensus-level guarantee.

### Likelihood Explanation
This is trivially reachable by any unprivileged wallet user: minting an NFT with an arbitrary DID string is a normal, supported wallet/RPC operation (`generate_new_nft` / NFT minting RPC), and no special privilege, signature from the impersonated DID, or announcement is required for the eve spend. The only requirement for exploitation is that a downstream consumer (buyer, marketplace, offer-matching UI) reads and trusts the `owner_did`/`minter_did` field without independently distinguishing eve-mint attribution from subsequently-authorized transfers — which is exactly the behavior the in-repo warning comment anticipates as a real risk.

### Recommendation
- Do not trust or surface the eve-spend `owner_did`/`minter_did` as an authenticated attribution anywhere in wallet RPC responses, CLI output, or NFT indexing (`NFTInfo`, `get_minter_did`, `print_nft_info`) unless it is corroborated by an actual announcement/spend from the claimed DID.
- Alternatively/additionally, enforce at the puzzle level that eve NFTs cannot curry in a non-empty `current_owner` without a companion DID announcement, closing the gap between eve and post-eve ownership-assignment semantics.
- At minimum, clearly and unavoidably flag (in both API responses and UI) NFTs whose current DID association derives solely from an un-corroborated eve-mint claim, so marketplaces/buyers are not misled into trusting the association during offer settlement.

### Proof of Concept
1. Attacker calls the NFT mint flow (`NFTWallet.generate_new_nft` via the mint RPC) supplying `did_id` = the launcher ID of a well-known DID that the attacker does not own (e.g., a verified project's DID).
2. The eve NFT is minted with `current_owner` initially empty and then set to the victim DID via the unauthenticated `-10` condition in the eve spend (`chia/wallet/nft_wallet/nft_wallet.py:501-561`); no announcement from the victim DID's singleton is produced or required.
3. `WalletStateManager.get_minter_did()` and `NFTWallet.puzzle_solution_received` read this value back off-chain and store it as `minter_did`/`owner_did` on the NFT record (`chia/wallet/wallet_state_manager.py:1074-1112`).
4. The attacker lists the NFT in an offer; a buyer's wallet/marketplace displays "Owner/Minter DID: <victim DID>" (`chia/cmds/wallet_funcs.py:1391-1403`) and the buyer takes the offer, paying the attacker under the false belief the NFT is affiliated with the victim DID.
