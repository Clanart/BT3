### Title
`Path.join` used instead of `resolveWithin` when opening working-directory files from the Changes sidebar / external editor allows a symlink in a cloned repo to redirect "Open File" outside the repo - ([File: app/src/ui/changes/sidebar.tsx], [File: app/src/ui/app.tsx])

### Summary
The report's underlying pattern is that a security-relevant guard (there, a non-null `rewardsManager` check) exists in some code paths but is missing in a structurally identical one, so attacker-influenced input reaches an unguarded operation. GitHub Desktop has the exact analog: it ships a dedicated path-containment helper, `resolveWithin`, specifically to stop a path derived from repository contents from escaping the repo root (including via symlinks), and uses it in several places, but two other call sites that build a full path from a repository-relative `path` string use plain `Path.join` instead, bypassing that guard.

### Finding Description
`app/src/lib/path.ts` defines `resolveWithin`, whose explicit purpose is to resolve a repo-relative path against the repo root and return `null` if the resolved, symlink-followed path escapes the root [1](#0-0) . Its own unit tests demonstrate the attack it defends against: a symlink placed inside the working tree that points outside the root, used to "traverse outside of the root" [2](#0-1) .

This guard is correctly applied in several places that consume repository-relative paths coming from external/attacker-influenced sources, e.g. deep-link file opening in `dispatcher.ts` [3](#0-2)  and Copilot conflict-resolution file reads/writes [4](#0-3)  and [5](#0-4) .

However, the "Open File" action from the Changes sidebar builds the full path with plain `Path.join` and no containment check before handing it to `openFile`: [6](#0-5) 

And the "Open in External Editor" action in `app.tsx` does the same before invoking the external editor: [7](#0-6) 

The `path` value in both cases ultimately originates from `WorkingDirectoryFileChange.path`, itself derived from `git status --porcelain=2 -z` output as parsed in `status-parser.ts`/`status.ts` [8](#0-7) . Git tracks and reports symlinked directory entries as ordinary working-tree paths; a maliciously crafted cloned/fetched repository can commit a symlink (e.g. a top-level directory symlink pointing to `/` or to a sensitive absolute path) and a tracked/untracked file "underneath" it. `git status` will surface that file's repo-relative path unchanged, `Path.join(repository.path, path)` will produce an absolute path, and because the join happens over a filesystem symlink, the actual file opened resolves outside the repository — exactly the scenario `resolveWithin`'s own symlink test is designed to catch, but which is not invoked on this path.

### Impact Explanation
An attacker who controls a repository the user clones or fetches (or an untrusted teammate's branch) can plant a symlink so that a file the user sees listed as an innocuous repo-relative path in the Changes list actually resolves to an arbitrary location on disk when the user double-clicks "Open File" or "Open in External Editor." Depending on the target and the app associated with the file extension, this can range from disclosing sensitive file contents (e.g. exposing an SSH private key or credential file to a text editor) to executing content if the symlink target is opened by an app that treats it as executable/interpretable. This is a read/open operation outside the intended repository root, matching the specified valid-impact class ("file write or read outside the repo").

### Likelihood Explanation
The trigger requires only that the victim clone/open an attacker-supplied repository and click on a file entry in the Changes sidebar or invoke "Open in External Editor" — both are core, expected Desktop workflows with no unusual user steps. No admin rights, local access, or prior compromise is needed; the attacker's contribution is entirely contained in the git repository content (a committed symlink), which is precisely the "attacker controls a cloned/fetched repository" primitive called out as in-scope.

### Recommendation
Route both `onOpenItem` (`app/src/ui/changes/sidebar.tsx`) and `onOpenInExternalEditor` (`app/src/ui/app.tsx`) through `resolveWithin(repository.path, path)` (as already done in `dispatcher.ts`'s `openRepositoryFromUrl` and in `copilot-conflict-context.ts`) and refuse to open the file (logging the attempt) when the resolved path is `null`. An audit of other `Path.join(repository.path, …)` call sites that consume git-status-derived paths (e.g. the diff viewers, "open pull request" file list, `stash-diff-viewer.tsx`) for the same missing containment check is warranted, since this appears to be an inconsistently-applied guard rather than an isolated omission.

### Proof of Concept
1. Attacker creates a git repository containing a symlink `evil` pointing to `/` (or, on the victim's likely home directory, to `..`), and a tracked/untracked "file" path such as `evil/Users/victim/.ssh/id_rsa` inside that symlinked tree, then pushes/hosts it for the victim to clone.
2. Victim clones the repository in GitHub Desktop and makes/discovers a change reported for `evil/Users/victim/.ssh/id_rsa` in the Changes list (or the attacker seeds an initial commit containing that path so it's visible without any edit).
3. Victim right-clicks the entry and selects "Open File" (`sidebar.tsx` `onOpenItem`) or "Open in External Editor" (`app.tsx` `onOpenInExternalEditor`).
4. `Path.join(repository.path, path)` resolves through the `evil` symlink to `/Users/victim/.ssh/id_rsa`, which is opened outside the cloned repository, without any `resolveWithin` containment check being applied — unlike the equivalent, already-guarded code paths in `dispatcher.ts` and `copilot-conflict-context.ts`.

Note: I was not able to execute this against a live Desktop build to confirm end-to-end OS-level symlink resolution behavior for every platform/editor combination; the analysis is based on the code paths and the project's own `resolveWithin` symlink-escape test, which documents this exact failure mode and confirms it is a class the project explicitly considers a vulnerability elsewhere.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

```typescript
function buildStatusMap(
  files: Map<string, WorkingDirectoryFileChange>,
  entry: IStatusEntry,
  conflictDetails: ConflictFilesDetails
): Map<string, WorkingDirectoryFileChange> {
  const status = mapStatus(
    entry.statusCode,
    entry.submoduleStatusCode,
    entry.renameOrCopyScore
  )

  if (status.kind === 'ordinary') {
    // when a file is added in the index but then removed in the working
    // directory, the file won't be part of the commit, so we can skip
    // displaying this entry in the changes list
    if (
      status.index === GitStatusEntry.Added &&
      status.workingTree === GitStatusEntry.Deleted
    ) {
      return files
    }
  }

  if (status.kind === 'untracked') {
    // when a delete has been staged, but an untracked file exists with the
    // same path, we should ensure that we only draw one entry in the
    // changes list - see if an entry already exists for this path and
    // remove it if found
    files.delete(entry.path)
  }

  // for now we just poke at the existing summary
  const appStatus = convertToAppStatus(
    entry.path,
    status,
    conflictDetails,
    entry.oldPath
  )

  const initialSelectionType =
    appStatus.kind === AppFileStatusKind.Modified &&
    appStatus.submoduleStatus !== undefined &&
    !appStatus.submoduleStatus.commitChanged
      ? DiffSelectionType.None
      : DiffSelectionType.All

  const selection = DiffSelection.fromInitialSelection(initialSelectionType)

  files.set(
    entry.path,
    new WorkingDirectoryFileChange(entry.path, appStatus, selection)
  )
  return files
```
