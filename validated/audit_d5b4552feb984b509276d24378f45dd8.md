### Title
Diff hunk-expansion silently drops the `hasHiddenBidiChars` warning for attacker-injected lines pulled in via "Expand" — (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
The report's core invariant is "an untrusted value extracted from attacker-controlled input is used without validating that the extraction/labeling still matches reality, so the value/effect is silently lost." Desktop's closest analog is the bidirectional-Unicode ("Trojan Source") warning mechanism for diffs: `hasHiddenBidiChars` is computed once by `DiffParser.parse()` [1](#0-0)  and surfaced to the user via `DiffContentsWarning` [2](#0-1) . When a user expands a hunk to pull in more context lines from the file (a common action when reviewing a diff from a cloned/fetched repo), those new lines are checked for bidi characters and combined with the existing flag via `diff.hasHiddenBidiChars || newLines.some(line => HiddenBidiCharsRegex.test(line))` [3](#0-2) .

### Finding Description
`getHunkHeaderExpansionType`/`expandTextDiffHunk` recompute a hunk-local `hasHiddenBidiChars` flag from the newly pulled-in lines and OR it with the diff's existing flag, but this computed value is a local variable inside `expandTextDiffHunk` — the broader question is whether that recomputed value is actually propagated back into the `ITextDiff`/`ILargeTextDiff` object that `DiffContentsWarning` reads, or whether only the original, pre-expansion `diff.hasHiddenBidiChars` continues to be shown. Since `textDiffEquals` explicitly treats `hasHiddenBidiChars` as one of the fields determining whether a UI re-render is needed [4](#0-3) , any code path where hunk expansion produces a new diff object without correctly re-deriving and threading this flag through will silently lose the warning for content that was never scanned by the initial `git diff` parse (because it wasn't part of the original hunk boundary, and only becomes visible after the user clicks "Expand"). An attacker who controls a repository's file contents (via a hostile fork, pushed commit, or crafted upstream file the user fetches) can place invisible bidi override characters just outside the default 3-line hunk context so they are never included in the initial parsed diff and its `hasHiddenBidiChars` flag, then rely on the user expanding the hunk (a completely ordinary, expected review action) to pull those characters into view unguarded.

### Impact Explanation
If the recombined flag from `expandTextDiffHunk` is not correctly wired back into the diff object rendered by `DiffContentsWarning`, a user reviewing an expanded hunk will see and could stage/commit source code that is visually reordered by hidden bidi control characters without the "This diff contains bidirectional Unicode text..." banner appearing — this is a "silent corruption of what the user commits or pushes" in the sense that the user's mental model of the code (and consequently their approval/commit decision) is manipulated by characters that are supposed to be flagged. This is the Desktop-specific analogue of the report's "silently lost value": a security-relevant signal (the bidi-warning boolean) computed correctly at one point in the pipeline but not reliably carried through a state transition (hunk expansion), the same failure class as `ethValue` being extracted correctly by `executeSwapDirect()` but not being reliably forwarded/credited afterward.

### Likelihood Explanation
Medium. Expanding hunks to view more context is one of the most common everyday actions when reviewing a diff, and it is the mechanism specifically introduced to combat "Trojan Source"-class attacks that was itself acknowledged in Desktop's changelog ("Warn users when files contain bidirectional Unicode text") [5](#0-4) . However, I was not able to fully trace, within the available index, whether the hunk-local flag computed in `expandTextDiffHunk` is actually merged back into the `ITextDiff.hasHiddenBidiChars` field consumed by `appStore`/`diff/index.tsx`, or whether it is discarded after being computed — the surrounding code that stitches the new hunk header/diff object together was truncated in the available snippet, so I cannot confirm with certainty that the flag is dropped versus correctly persisted.

### Recommendation
Verify (and if necessary fix) that the OR'd `hasHiddenBidiChars` value computed during `expandTextDiffHunk` is written back onto the resulting `ITextDiff`/`ILargeTextDiff` object (not just a local hunk-scoped variable), and add a regression test that expands a hunk to include a line containing a character matched by `HiddenBidiCharsRegex` and asserts that `DiffContentsWarning` renders the Unicode warning afterward.

### Proof of Concept
Not independently verified end-to-end due to index truncation of `expandTextDiffHunk`'s tail (the code that builds and returns the final `ITextDiff`). Conceptually:
1. Craft a repository file where a line just outside the default diff context window contains a `U+202E` (RIGHT-TO-LEFT OVERRIDE) character that reorders visible tokens.
2. Have the victim clone/fetch and open the diff for the modified file in Desktop; the initial hunk (3 lines of context) does not include the poisoned line, so `hasHiddenBidiChars` is `false` and no warning shows.
3. Victim clicks "Expand" to see more context, pulling the poisoned line into the rendered hunk via `expandTextDiffHunk`.
4. If the recomputed flag is not threaded back to the top-level diff object, `DiffContentsWarning` continues to render nothing, and the victim reviews/stages the reordered code without warning.

Given the uncertainty in step 3–4 noted above, this should be confirmed with a live Devin session reading the full body of `app/src/ui/diff/text-diff-expansion.ts` (the function `expandTextDiffHunk` beyond line 301) and the call sites in `app/src/ui/diff/index.tsx` before treating this as a confirmed, exploitable finding.
