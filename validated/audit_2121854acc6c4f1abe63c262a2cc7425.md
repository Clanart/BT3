### Title
Solver-selection session private key persisted in plaintext, unencrypted client storage — leak hijacks order fill authorization - ([File: sdk/packages/sdk/src/storage/index.ts])

### Summary
The external report's core broken invariant is: *a secret that is the sole authorization credential for a sensitive action gets copied into a broadly-readable surface (the OS clipboard), from which any co-resident process can read and exfiltrate it, bypassing the "only the owner can authorize" guarantee.* The direct on-chain analog in Hyperbridge is the IntentGatewayV2 solver-selection flow: the ephemeral **session private key** is the *only* credential that authorizes which solver may fill a user's order (`SolverSelection` EIP-712 signature), and the SDK persists that raw private key in plaintext inside browser `localStorage`/`indexedDB` (or a Node file driver), i.e. a shared, unencrypted, widely-readable storage surface — the same broken invariant as copying the mnemonic to the clipboard.

### Finding Description
`OrderPlacer.placeOrder` generates a fresh session key per order and immediately persists the raw `privateKey` via `sessionKeyStorage.setSessionKeyByAddress`: [1](#0-0) 

`createSessionKeyStorage` in the SDK stores this `SessionKeyData` (which embeds `privateKey` in cleartext) as a JSON string under a `session-key:` / `session-key-address:` prefix, using whatever driver `detectEnvironment()` picks — `localstorage` or `indexeddb` in the browser, a file/node driver otherwise: [2](#0-1) [3](#0-2) 

This session key is not incidental data — it is the cryptographic root of the on-chain authorization gate. `IntentsBase._select` recovers the session key address from an EIP-712 signature over `(commitment, solver)` and stores `keccak256(solver, sessionKey)` in transient storage: [4](#0-3) 

`IntentGatewayV2.fillOrder` then authorizes the caller purely by recomputing `keccak256(msg.sender, order.session)` and comparing it against that transient-storage value — there is no other check binding the filler to the user's actual intent: [5](#0-4) 

`CryptoUtils.signSolverSelection` shows any holder of the raw session private key can produce this signature unilaterally: [6](#0-5) 

Because the private key — the single artifact that gates who is allowed to fill the order — is stored unencrypted in a storage surface shared with arbitrary same-origin JavaScript (XSS payloads, malicious browser extensions, or any other code sharing that storage/profile), an attacker who reads it can sign `SelectSolver` for the victim's pending order and call `select()`/`fillOrder()` as an attacker-controlled solver address, hijacking the authorization the user intended to grant to a specific vetted solver. This is structurally identical to the clipboard bug: the sensitive secret is deliberately made available on a surface designed for other purposes and readable by unrelated code, and no additional "retype/confirm" or hardware-bound step exists before it becomes fully usable to sign a binding on-chain authorization.

### Impact Explanation
Leaking the session key lets an unprivileged attacker bypass the intended solver-selection authorization gate and become the exclusively-authorized filler of another user's live order (`select` → `fillOrder`), which is unauthorized execution of the fill path that was supposed to require the user's own signature. Since `fillOrder` accepts attacker-supplied `FillOptions` (including `options.outputs`), an attacker impersonating the solver controls what parameters are used to complete/settle the order, which can result in the order being filled or settled on terms the legitimate user never agreed to. This matches the bounty's "unauthorized transaction or execution" / "logic attacks" categories.

### Likelihood Explanation
Any environment where the SDK runs in a browser context (the primary target for `IntentGatewayV2` order placement per the docs) defaults to `localStorage`/`indexedDB`, both fully readable by any JavaScript executing in the same origin — a very low bar (a single XSS in the hosting dApp, a malicious extension, or a compromised dependency) compared to compromising a relayer, prover, or governance key. No malicious peer, relayer, or admin assumption is required — this is a pure client-storage exposure of an unprivileged, single-purpose signing key.

### Recommendation
- **Short term:** Never persist the raw session private key. Keep it only in memory for the lifetime of the order-placement flow, or require it to be supplied fresh by the caller for each signing operation instead of being written to `localStorage`/`indexedDB`.
- **Long term:** If session keys must be persisted (e.g., to survive page reloads), encrypt them at rest with a key derived from a user-controlled secret/passkey, and scope/expire them tightly. Avoid storing sensitive signing material in any storage surface shared with arbitrary same-origin code.

### Proof of Concept
1. User calls `OrderPlacer.placeOrder(order)`; the SDK generates a session key and stores `{ privateKey, address, createdAt }` in `localStorage` under `session-key-address:<address>` before the order is even placed on-chain: [1](#0-0) .
2. An attacker with same-origin JS execution (XSS/malicious extension) reads `localStorage`, extracts the plaintext `privateKey` for the pending order's session key address.
3. Attacker calls `CryptoUtils.signSolverSelection(commitment, attackerSolverAddress, domainSeparator, leakedPrivateKey)` to produce a valid `SelectSolver` signature naming themselves as solver: [6](#0-5) .
4. Attacker (or their `SolverAccount`) calls `IntentGatewayV2.select(...)` then `fillOrder(...)`; `fillOrder` only checks `keccak256(msg.sender, order.session) == storedSelectionHash`, which now matches the attacker: [5](#0-4) .
5. The attacker is now the exclusively-authorized filler of the victim's order and controls the `FillOptions` used to settle it — the same "steal the secret from an exposed surface, then perform the sensitive action the secret was supposed to gate" pattern as the clipboard-exposed mnemonic.

}

export function createSessionKeyStorage(options: SessionKeyStorageOptions = {}) {
	const key = options.env ?? detectEnvironment()
	const driver = loadDriver({ key, options }) ?? inMemoryDriver()
	const baseStorage = createStorage({ driver })

	const SESSION_KEY_PREFIX = "session-key:"
	const SESSION_KEY_ADDRESS_PREFIX = "session-key-address:"

	/**
	 * Gets a session key by order commitment
	 */
	const getSessionKey = async (commitment: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Gets a session key by session key address
	 */
	const getSessionKeyByAddress = async (address: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Stores a session key for an order commitment
	 */
	const setSessionKey = async (commitment: HexString, data: SessionKeyData): Promise<void> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		await baseStorage.setItem(storageKey, JSON.stringify(data))
	}

	/**
	 * Stores a session key for a session key address
	 */
	const setSessionKeyByAddress = async (address: HexString, data: SessionKeyData): Promise<void> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`

	}

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }

	static async signSolverSelection(
		commitment: HexString,
		solverAddress: HexString,
		domainSeparator: HexString,
		privateKey: HexString,
	): Promise<HexString | null> {
		const account = privateKeyToAccount(privateKey as Hex)

		const structHash = keccak256(
			encodeAbiParameters(
				[{ type: "bytes32" }, { type: "bytes32" }, { type: "address" }],
				[SELECT_SOLVER_TYPEHASH, commitment, solverAddress],
			),
		)

		const digest = keccak256(concat(["0x1901" as Hex, domainSeparator as Hex, structHash]))
		const signature = await account.sign({ hash: digest })

		return signature as HexString
	}
