### Title
Zero-amount input tokens permanently brick escrow withdrawal in the Tron `IntentGatewayV2` (`RedeemEscrow`/`RefundEscrow` always revert) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` validates that `order.inputs[i].amount != 0` only in the non-predispatch escrow branch of `placeOrder`, but omits this check in the predispatch (calldata) branch. A zero-amount input token can therefore be escrowed. When that order is later filled or cancelled, `withdraw()` iterates every token in the `WithdrawalRequest` and reverts with `UnknownOrder()` for any token whose escrowed balance is `0` — which is exactly the state produced by the missing validation. Because `withdraw()` processes the whole token array atomically, this permanently locks all of the order's other, real escrowed funds, mirroring the root cause of the referenced report: an unchecked zero-value amount reaching a transfer/accounting path that reverts and corrupts settlement.

### Finding Description
`placeOrder` computes `reducedInputs`/`order.inputs` and escrows tokens through two mutually exclusive branches:

- Predispatch branch (`order.predispatch.call.length > 0`): builds `transferCalls` for each `order.inputs[i]` using `requiredAmount = order.inputs[i].amount` with no zero check. [1](#0-0) 

- Non-predispatch branch: explicitly rejects zero-amount inputs. [2](#0-1) 

A user (order placer) can thus place an order with predispatch calldata containing one input token with `amount == 0` alongside other input tokens with real value. `_orders[commitment][token] += reducedInputs[i].amount` stores `0` for that token slot. [3](#0-2) 

Both fill (`RedeemEscrow`) and cancel (`RefundEscrow`) cross-chain messages carry `tokens: order.inputs` verbatim (including the zero-amount entry) to the source chain's `onAccept`, which calls `withdraw()`: [4](#0-3) [5](#0-4) 

`withdraw()` loops over every token and unconditionally reverts if the stored escrow for any single token is zero: [6](#0-5) 

Since the zero-amount token's escrow really is `0` (by design, not by accident), `_orders[body.commitment][token] == 0` is always true, so `UnknownOrder()` fires on every call to `withdraw()` for this order — both for a solver's fill attempt and for the user's own cancellation/refund attempt. Because the loop processes the full token array in one transaction, a single reverting entry aborts the transfer of the *other*, real escrowed tokens as well.

This is the same broken-invariant class as the seed report: token amounts that are (or can become) zero are pushed into a transfer/accounting path without a "skip if zero" guard, causing settlement to revert. The sibling EVM implementation (`IntentsBase.sol`, used by the non-Tron `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` contracts) already contains the fix that the Tron contract is missing: [7](#0-6) 

That version explicitly does `if (amount == 0) continue;` before touching `_orders[...]` or issuing a transfer, so a zero-amount token entry is a no-op instead of an `UnknownOrder()` revert. The Tron contract's `withdraw()` has no equivalent guard.

### Impact Explanation
This falls under "loss of funds" / "logic attacks" in the bounty scope: the order placer's genuinely escrowed assets (all input tokens other than the malformed zero-amount one) become permanently unrecoverable. Neither the solver can complete a legitimate fill and collect the escrow, nor can the user cancel and get a refund, because both settlement paths (`RedeemEscrow` and `RefundEscrow`) route through the same `withdraw()` function that will deterministically revert on the zero-amount entry every time it's attempted. The bug is triggerable by an ordinary, unprivileged user calling the public `placeOrder` entrypoint with attacker/user-controlled input data — no relayer, prover, or governance action is required.

### Likelihood Explanation
High reachability: `placeOrder` is a public, permissionless entrypoint, and the omission of the `amount == 0` check is confined to a single, easily-triggered code path (predispatch calldata with a zero-amount `TokenInfo` entry in `order.inputs`). No fee-on-transfer or oracle manipulation is needed — the zero amount is directly attacker-supplied. The only requirement is that the order also include valid `predispatch.call`/`predispatch.assets` data, which is a normal, documented feature of the protocol.

### Recommendation
Add the same `amount == 0` rejection (or a `continue`-style skip in `withdraw()`) to the predispatch branch of `placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, matching the validation already present in the non-predispatch branch. Additionally, harden `withdraw()` itself to skip zero-amount token entries (mirroring `IntentsBase._withdraw`'s `if (amount == 0) continue;`) so that a token with 0 escrowed balance never aborts the whole withdrawal for the order's other tokens.

### Proof of Concept
1. User calls `placeOrder` with `order.predispatch.call.length > 0` and `order.predispatch.assets` set up normally, but sets one entry in `order.inputs` to `TokenInfo({token: someToken, amount: 0})` alongside another entry with a real, non-zero amount (e.g. USDT).
2. `placeOrder`'s predispatch branch does not check `order.inputs[i].amount == 0`, so the order is accepted; `_orders[commitment][someToken] = 0` while `_orders[commitment][USDT] = <real amount>`. [1](#0-0) 
3. A solver fills the order (or the user cancels after expiry); the corresponding `WithdrawalRequest` includes `tokens: order.inputs`, i.e. both the zero-amount `someToken` entry and the real USDT entry. [4](#0-3) 
4. On the source chain, `onAccept` → `withdraw()` iterates `body.tokens`; for `someToken`, `_orders[commitment][someToken] == 0` is true, so it reverts with `UnknownOrder()` before the USDT transfer is processed. [8](#0-7) 
5. Every subsequent delivery attempt of this `RedeemEscrow`/`RefundEscrow` message reverts identically, so the escrowed USDT can never be released to either the solver or the user — permanent fund lock.
