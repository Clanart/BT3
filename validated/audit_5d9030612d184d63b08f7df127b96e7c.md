### Title
`IntentGatewayV2.withdraw()` accepts a `false`-returning ERC-20 `transfer` as success, finalizing escrow release without moving funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent tokens using a raw low-level call to `IERC20.transfer.selector` and only checks that the *call itself* did not revert (`success`), never inspecting the returned boolean. This is the inverse-but-related failure mode of the reported bug class (naive ERC-20 return-value handling): where the audited `SecondaryRewarder.recover()` used a bare `.transfer()` that *reverts* for no-return tokens like USDT, this contract uses a manual low-level call that silently *accepts* a `false` return as success, letting escrow accounting finalize a transfer that never happened.

### Finding Description
In `withdraw()`, escrowed funds are released to the beneficiary and the order state is immediately mutated to reflect a completed release: [1](#0-0) 

For every token in the withdrawal, the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and then decrements `_orders[body.commitment][token] -= amount;`. `_filled[body.commitment]` is also set to `beneficiary` at the top of the function unconditionally.

The `success` flag from a low-level `.call` only reflects whether the callee reverted — it does not decode or validate the returned ABI-encoded boolean. Any ERC-20 implementation that returns `false` on failure (rather than reverting) — a documented category of non-standard token behavior, the exact class flagged in the source report — will make this code treat a failed transfer as a success. The same unguarded pattern is repeated for the fee-token transfer and for `SweepDust`: [2](#0-1) [3](#0-2) 

By contrast, the canonical EVM implementation of the same logic correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which does validate the return data: [4](#0-3) 

The Tron file imports `SafeERC20` and even declares `using SafeERC20 for IERC20;` at the contract level, but the `withdraw()`/`onAccept` SweepDust/fee paths bypass it in favor of the raw `.call` pattern shown above.

### Impact Explanation
If the escrowed `token` returns `false` on a failed transfer without reverting, `withdraw()` will:
1. Mark the order as `_filled[body.commitment] = beneficiary` (a one-time, non-reversible state), and
2. Decrement `_orders[body.commitment][token]` as if the tokens were paid out,

while the beneficiary receives nothing and the tokens remain stuck in the `IntentGatewayV2` contract. Because `_filled` is now non-zero, the order can never be retried, refunded, or re-withdrawn (see `Filled()` checks used elsewhere in the fill/cancel paths), permanently locking the escrowed funds with no recovery path for the intended beneficiary. This is a direct loss/lock of bridged user funds triggered through the normal, unprivileged cross-chain settlement flow (`onAccept`/`onGetResponse` → `withdraw`), matching the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" categories.

### Likelihood Explanation
Exploitability depends on the escrowed/output token's ERC-20 implementation returning `false` instead of reverting on failure (e.g., insufficient balance edge cases, blacklist/pausable tokens, or any token adopting the "return false" convention rather than revert). This is a realistic scenario for intent-based bridging since order makers/solvers can specify arbitrary ERC-20 tokens as inputs/outputs, and the contract does not restrict tokens to a vetted allowlist. No malicious relayer, prover, or admin is required — the flaw is purely in how `IntentGatewayV2` interprets an ordinary ERC-20 response during normal settlement.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, the `SweepDust` branch, and the transaction-fee payout) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the EVM mainline implementation in `IntentsBase.sol::_withdraw`. This validates both call success and, when return data is present, that it decodes to `true`, while still tolerating tokens that return no data at all.

### Proof of Concept
1. A solver/user places an intent order whose input/output token is a non-standard ERC-20 that returns `false` (does not revert) when a transfer fails, e.g. due to an internal check the token enforces.
2. The order proceeds through fill/cross-chain settlement to the point where `onAccept`/`onGetResponse` calls `withdraw(body, isRefund)` on `IntentGatewayV2` (tron).
3. Inside `withdraw`, the token's `transfer(beneficiary, amount)` call executes without reverting but returns `false` (e.g., because the token's own compliance/allowance logic rejects the recipient).
4. `success` is `true` (the low-level call did not revert), so the `if (!success) revert TransferFailed();` check passes.
5. `_orders[body.commitment][token] -= amount;` executes, and (for `finalize`/top-level `withdraw`) `_filled[body.commitment]` is already set to the beneficiary — the order is now permanently finalized.
6. The beneficiary never received the tokens; they remain trapped in the `IntentGatewayV2` contract balance with no code path to reclaim them, since `_filled` blocks any further fill/refund/cancel attempt on that commitment.
