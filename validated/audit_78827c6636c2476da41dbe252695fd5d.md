### Title
Missing `nonReentrant` guard and duplicate-escrow check in Tron `IntentGatewayV2.placeOrder()` allows predispatch callback reentrancy to double-credit escrow off shared dispatcher balance - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2.placeOrder()` executes attacker/user-supplied `predispatch.call` calldata through the shared `CallDispatcher` contract *before* finalizing escrow accounting — a "push-based" flow structurally identical to the `onERC721Received` push-supply pattern in the seed report, where an external call made mid-flow can re-enter and create a second piece of state referencing the same underlying asset. The main EVM contract closed this class of bug with `nonReentrant` on `placeOrder` plus an explicit duplicate-input rejection (`if (_orders[commitment][token] != 0) revert InvalidInput();`), added as "Regression test for: same-chain partial fills over-release repeated input escrow" [1](#0-0) . The Tron fork of the same contract reimplements `placeOrder` with the identical predispatch-callback structure but **without** `nonReentrant` and **without** the duplicate/overwrite escrow check — it uses `_orders[commitment][token] += reducedInputs[i].amount` unconditionally [2](#0-1) .

### Finding Description
`placeOrder` in the main EVM contract is CEI-guarded and reentrancy-locked: [3](#0-2) 

Its predispatch flow transfers order assets into a single shared `dispatcher` contract, executes arbitrary attacker-controlled calldata via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, then measures `dispatcher`'s balance before/after to determine how much was actually escrowed: [4](#0-3) 

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the exact same balance-snapshot-based predispatch pattern against the same shared `dispatcher` contract: [5](#0-4) [6](#0-5) 

But this `placeOrder` function has **no `nonReentrant` modifier** (confirmed: the function signature at line 332 carries no modifier, and the contract does not import or inherit any `ReentrancyGuard`), and the escrow bookkeeping uses `+=` unconditionally rather than the main EVM version's guarded, one-time `_orders[commitment][token] != 0` check: [7](#0-6) [8](#0-7) 

Because `CallDispatcher.dispatch` performs a raw low-level `.call` to an arbitrary attacker-supplied target with attacker-supplied calldata [9](#0-8) , and the *same* `dispatcher` contract instance is shared by every order (`_params.dispatcher`), an attacker's predispatch target contract can re-enter `placeOrder()` on the very same `dispatcher` while the outer call's balance-based sweep is mid-flight. The outer transaction's `balanceOf(dispatcher)` reads (used both as the "sufficient balance" check and to compute `reducedInputs[i].amount` credited to `_orders`) can then observe tokens that a nested, re-entered `placeOrder()` call has already moved into (or is simultaneously moving out of) `dispatcher`. Because escrow crediting is additive (`+=`) and unguarded by reentrancy or duplicate checks, this lets a single real token balance in `dispatcher` back **two distinct order commitments** in `_orders`, exactly mirroring the seed bug's "one NFT tied to two liens" divergence — here, one custodied token balance is credited to two escrow ledger entries.

### Impact Explanation
`_orders[commitment][token]` is the ledger that authorizes real ERC20/native transfers on fill/withdraw (`_withdraw` in `IntentsBase.sol` unconditionally trusts `_orders[commitment][token]` to release funds via `safeTransfer`/`.call{value}`). If the ledger is inflated relative to actual custodied tokens through the reentrancy path above, a solver/attacker can later fill or withdraw against the phantom-credited commitment and drain real escrowed funds belonging to other users of the same gateway — a direct loss-of-funds / unauthorized-transfer outcome, matching the bounty's accepted impact categories (fund loss, double-settlement/double-claim off one deposit).

### Likelihood Explanation
The attacker only needs to call the public, unprivileged `placeOrder()` entrypoint with a `predispatch.call` pointing at their own contract — no relayer, prover, admin, or governance actor is required. The vulnerable code path (shared-dispatcher balance snapshotting with no reentrancy lock) is reachable by any user in a single transaction, which raises likelihood; the primary uncertainty is the exact reentrant sequencing needed to make the "credited but not actually deposited" delta line up cleanly across two commitments — this requires precise control of both calls' balance snapshots but is a standard reentrancy-arbitrage construction against shared-custody accounting.

### Recommendation
Port the same protections already applied to the canonical EVM contract into the Tron fork:
1. Add a `nonReentrant` guard (or equivalent reentrancy lock) to `placeOrder`, `fillOrder`, and any function that dispatches to `CallDispatcher` before finalizing escrow state.
2. Replace unconditional `_orders[commitment][token] += ...` with the guarded one-time write pattern used in the main EVM contract (`if (_orders[commitment][token] != 0) revert InvalidInput()`), and reject duplicate input tokens the same way `placeOrder` in `evm/src/apps/IntentGatewayV2.sol` does.
3. Consider giving each order its own isolated dispatcher/escrow context instead of a single shared `dispatcher` contract balance for snapshot-based accounting, removing the shared-resource race entirely.

### Proof of Concept
1. Attacker deploys `EvilPredispatchTarget`, implementing an arbitrary function that, when invoked by `CallDispatcher.dispatch`, calls back into `IntentGatewayV2.placeOrder()` with a second order (own funds/approval), whose `predispatch.assets` moves tokens into the same shared `dispatcher`.
2. Attacker calls `placeOrder(orderA, ...)` on the Tron `IntentGatewayV2`, where `orderA.predispatch.call` targets `EvilPredispatchTarget`.
3. During `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` for `orderA` [10](#0-9) , `EvilPredispatchTarget` re-enters `placeOrder(orderB, ...)` on the same gateway/dispatcher before `orderA`'s balance-based sweep (`balance = IERC20(token).balanceOf(dispatcher)`) executes.
4. Because there is no `nonReentrant` lock, both `orderA`'s and `orderB`'s sweeps read/credit against the same fluctuating `dispatcher` balance, and both `_orders[commitmentA][token] += ...` and `_orders[commitmentB][token] += ...` execute without any check that the credited amount is backed by unique, non-overlapping token custody.
5. The attacker ends up with two order commitments whose combined `_orders[...]` ledger entries exceed what was actually deposited into `dispatcher`, letting a colluding/attacker-controlled solver later `fillOrder`/trigger `withdraw` on both commitments and drain the excess from the gateway's genuine token reserves.

Note: Full step-by-step balance-drift math depends on exact solidity execution-order nuances of the two interleaved calls, which could not be dynamically verified in this read-only review (no test harness run against the Tron contract); the structural absence of `nonReentrant` and the duplicate-credit guard relative to the hardened main EVM contract is directly confirmed in the code cited above.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
