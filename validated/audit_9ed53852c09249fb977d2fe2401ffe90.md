## Analysis

The core, generalizable flaw in the `flashProof` finding is: **a security check is anchored to a coarse/spoofable identifier that does not correspond 1:1 to the specific resource being protected**, so a value chosen/observed by the attacker can be substituted for the real one and the protection silently applies to the wrong target.

Desktop's local analog is the "unsafe repository" trust flow. When Git refuses to operate on a repository due to dubious ownership, Desktop parses the *path string that Git itself reports* out of stderr and treats that string as "the directory the user is trusting" — without ever verifying it equals the path the user actually opened/cloned: [1](#0-0) 

That extracted `unsafeMatch[1]` value is then written verbatim into the **global** git config's `safe.directory` list via `addSafeDirectory`, which is not scoped to the repository the user reviewed — it's a global trust exception for whatever path string was captured: [2](#0-1) 

The UI code that drives the "Trust Repository" action even acknowledges that the reported `repositoryUnsafePath` can diverge from the path the user entered/selected (`convertedPath`), but still calls `addSafeDirectory(repositoryUnsafePath)` on trust: [3](#0-2) [4](#0-3) 

The same pattern repeats in the "missing repository" recovery flow, where `unsafePath` from `getRepositoryType` is trusted directly: [5](#0-4) 

This mirrors the `flashProof` bug class: the guard (dubious-ownership protection) is bypassed not by breaking cryptography but by feeding the check a value (the path Git chooses to report, which is influenced by repository structure — e.g., `.git` gitlinks, submodule/worktree redirection, or ownership resolution walking up parent directories) that the user believes refers to the reviewed resource, when it may not. Once trust is granted, it is stored **globally** in `~/.gitconfig`, disabling the safety check for that path for *all* future Desktop and command-line Git operations, not just the one directory the user intended to bless — precisely analogous to how `flashProof`'s `tx.origin` check granted a security guarantee at the wrong granularity.

### Title
Trust-on-click for "unsafe repository" writes an attacker-influenceable path into global `safe.directory`, not the reviewed directory - (File: app/src/lib/git/config.ts)

### Summary
`getRepositoryType` extracts the path Git reports as having "dubious ownership" straight out of `stderr` via regex, and the "Trust Repository" UI passes that raw string to `addSafeDirectory`, which appends it to the global `safe.directory` git config entry. Neither `getRepositoryType` nor the callers enforce that this reported path equals the directory the user opened/cloned/selected.

### Finding Description
`getRepositoryType` (app/src/lib/git/rev-parse.ts:57-63) matches `fatal: detected dubious ownership in repository at '(.+)'` from Git's stderr and returns it as `{ kind: 'unsafe', path: unsafeMatch[1] }`. Because ownership checks in Git resolve through `.git` file redirection (used for worktrees and submodules) and can walk up to enclosing directories, the path Git names in this message is not guaranteed to be the exact directory the user pointed Desktop at — it can be a different path derived from repository contents. Both `AddExistingRepository` (app/src/ui/add-repository/add-existing-repository.tsx:129-153) and `MissingRepository` (app/src/ui/missing-repository.tsx:35-50) surface this reported path to the user, and on "Trust Repository"/`onTrustDirectory` call `addSafeDirectory(repositoryUnsafePath)` (app/src/lib/git/config.ts:176-189), which permanently appends that string to the **global** `safe.directory` config entry — a machine/user-wide exception, not scoped to the single repository session.

### Impact Explanation
`safe.directory` is Git's core defense against executing configuration/hooks from directories owned by another user. If a crafted repository causes Git to report an unsafe-ownership path that differs from what the user believes they are trusting (e.g., a parent directory, a redirected worktree/submodule gitdir location), a single click on "Trust Repository" silently disables ownership protection for that other, unreviewed path for all future Git operations on the machine — not just within Desktop. This can re-enable use of malicious `core.hooksPath`, `alias`, or `insteadOf` settings from a location the user never consciously trusted.

### Likelihood Explanation
Requires an attacker to get the victim to open/clone a repository whose structure causes Git's ownership resolution to report a path other than the one the user is looking at (via `.git` gitlink/worktree/submodule redirection), which is a repository-content-only primitive — no local access, malware, or leaked credentials needed, consistent with the "attacker controls a cloned/fetched repository" threat model. It is somewhat constrained by needing the exact stderr path format Desktop parses and by the user still needing to click "Trust," but no other validation exists to stop it once that click happens.

### Recommendation
Before calling `addSafeDirectory`, verify that the path reported by Git (`type.path` / `repositoryUnsafePath`) is the same as (or a legitimate ancestor consistent with) the repository path the user explicitly opened, and surface a clear warning/abort instead of silently trusting when they diverge. Consider also scoping the trust more narrowly if Git/OS tooling allows it, rather than only ever appending to the global list.

### Proof of Concept
1. Craft a repository whose `.git` is a gitlink/worktree pointer (`gitdir: <redirected-path>`) such that Git's ownership check surfaces `<redirected-path>` (a directory outside the repo folder) in the "dubious ownership" error rather than the folder the user opened.
2. Have the victim clone/open this repository in Desktop; `getRepositoryType` returns `{ kind: 'unsafe', path: '<redirected-path>' }`.
3. The `AddExistingRepository`/`MissingRepository` UI shows the "Trust Repository" prompt (potentially even rendering the differing path per the `repositoryUnsafePath !== convertedPath` branch, but the button remains a single click away).
4. User clicks "Trust Repository" → `addSafeDirectory('<redirected-path>')` appends `<redirected-path>` to the user's global `safe.directory` config, disabling Git's ownership check for that path system-wide, even though the user never reviewed or intended to trust it.

```typescript
/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
```
