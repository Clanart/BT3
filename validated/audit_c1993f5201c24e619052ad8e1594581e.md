## Title
Cross-chain transfer timeout can permanently strand escrowed funds when a token's chain mapping is updated - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_timeout` callback must resolve the destination contract's asset mapping and per-chain decimals before it releases previously escrowed/burned funds back to the original sender. Both lookups key off state that is fully mutable via `update_token`'s `remove_chains` path [1](#0-0) . If that mapping is removed or replaced between the time a user calls `send()` and the time the resulting ISMP `PostRequest` eventually times out, `on_timeout` errors out before reaching the refund transfer, exactly mirroring the report's pattern: a validity check inside a mandatory recovery path reverts and the recovery (here, releasing escrowed funds) never happens — with no other mechanism in the pallet to release the funds afterward.

### Finding Description
`send()` escrows or burns the user's local asset and dispatches a `PostRequest` whose `to` field is the destination-chain token contract address read from `TokenContracts[dest][asset_id]` at that moment [2](#0-1) .

If that request later times out, `pallet_ismp` invokes the module's `on_timeout(request)`. This function re-derives the asset from `request.dest` / `request.to` via `ContractToAsset::<T>::get(dest, &to)` and the decimals via `Precisions::<T>::get(local_asset_id, dest)`, both of which must succeed *before* any refund transfer is attempted: [3](#0-2) 

```
let local_asset_id = ContractToAsset::<T>::get(dest, &to)
    .ok_or(HftError::UnknownContractOnTimeout)?;
...
let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
    .ok_or(HftError::DecimalsNotConfigured(dest))?;
```

The refund transfer (`NativeCurrency::transfer` / `Assets::transfer` / `Assets::mint_into`) only executes *after* these lookups succeed [4](#0-3) .

`ContractToAsset` and `Precisions` are exactly the entries `update_token`'s `remove_chains` branch deletes for a given `(asset_id, chain)` pair [1](#0-0) . This is an ordinary, expected lifecycle operation (deprecating a chain/contract for a token, or migrating to a new contract address), not a malicious act.

Sequence that permanently strands funds:
1. User calls `send()` while `TokenContracts[dest][asset]` / `ContractToAsset[dest][contract]` / `Precisions[asset][dest]` are all populated. Funds are escrowed in `Pallet::pallet_account()` and the ISMP request is committed.
2. Before the request is delivered or times out, governance calls `update_token` with `remove_chains` containing `dest` (e.g. to deprecate the chain, rotate the contract address, or fix a misconfiguration) — a routine, non-malicious operation.
3. The request eventually times out on the source chain. `on_timeout` is invoked, `ContractToAsset::get(dest, &to)` (or `Precisions::get`) now returns `None`, and the callback errors with `UnknownContractOnTimeout` / `DecimalsNotConfigured`.
4. Per the `pallet_ismp` timeout contract (demonstrated by `test_dispatch_fees_and_refunds`), when the module's `on_timeout` errors, the host-level refund of protocol fee/commitment state is never reached and the callback is left retryable [5](#0-4) .
5. Retrying does not help unless governance restores the *exact same* mapping. If the contract was deprecated intentionally (new deployment, chain sunset), the mapping can never be legitimately restored. The pallet exposes no admin/rescue extrinsic to manually release funds from `Pallet::pallet_account()` — `send`, `register_token`, and `update_token` are the only calls [6](#0-5) .

The user's escrowed/burned funds are now permanently locked with no code path to release them — the exact "revert blocks the only recovery action" failure mode from the source report, here applied to fund custody rather than collateralization.

### Impact Explanation
This is a direct loss/permanent lock of bridged user funds — escrowed native currency or burned/locked assets in `Pallet::pallet_account()` become unrecoverable once the (asset, destination-chain) mapping used at send time is retired while a transfer is still in flight. There is no governance or user extrinsic in this pallet capable of releasing funds once `on_timeout` cannot resolve the mapping, so the failure is unrecoverable by design rather than merely inconvenient.

### Likelihood Explanation
Triggering requires only an ordinary token/chain lifecycle update (`update_token` removing or changing a chain's contract mapping) racing against any in-flight `send()` whose request has not yet been delivered or timed out — a routine maintenance operation, not an attack requiring a malicious actor, leaked key, or compromised relayer. Any production deployment that ever needs to migrate a token's destination contract address or deprecate a chain is exposed to this race.

### Recommendation
- Decouple `on_timeout`'s refund path from the *current* `ContractToAsset`/`Precisions` state. Instead, persist the resolved `local_asset_id` and `erc_decimals` (or the full refund parameters) into the outgoing request state at `send()` time, so a later configuration change cannot invalidate the refund of an already-escrowed transfer.
- Alternatively, make `update_token`'s `remove_chains` refuse to remove a `(chain, asset)` mapping while there are unexpired in-flight requests referencing it, or retain the old mapping in a versioned/historical table that `on_timeout` can still consult.
- Add an emergency rescue path (governance-gated) capable of releasing funds from `Pallet::pallet_account()` for commitments whose timeout callback can never succeed, as a last-resort recovery mechanism.

### Proof of Concept
1. Register asset `A` with chain `Evm(X)` → contract `C1`, decimals `18` via `register_token`.
2. User calls `send(asset=A, destination=Evm(X), recipient=..., amount=100, timeout=T)`. Funds are moved into `Pallet::pallet_account()`; `PostRequest{to: C1, dest: Evm(X), ...}` is dispatched.
3. Before delivery/timeout, governance calls `update_token` with `remove_chains = [Evm(X)]` for asset `A` (e.g., deprecating that deployment) — `ContractToAsset[Evm(X)][C1]` and `Precisions[A][Evm(X)]` are deleted.
4. Request times out; `on_timeout` is invoked with `dest = Evm(X)`, `to = C1`; `ContractToAsset::get(Evm(X), C1)` returns `None` → `Err(HftError::UnknownContractOnTimeout)`.
5. Per the ISMP module-callback contract, the refund transfer inside `on_timeout` never executes, and the escrowed 100 units of `A` remain in `Pallet::pallet_account()` indefinitely with no extrinsic available to recover them.

					return Err(Error::<T>::NonEvmPeerChain.into());

					Error::<T>::ErcDecimalsBelowLocal

				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);

			for chain in update.remove_chains {

				}
				TokenContracts::<T>::remove(chain, update.asset_id.clone());
				Precisions::<T>::remove(update.asset_id.clone(), chain);
			}

			Ok(())
		}

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
					.ok_or(HftError::UnknownContractOnTimeout)?;

				let decimals = if local_asset_id == T::NativeAssetId::get() {
					T::Decimals::get()
				} else {
					<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
						local_asset_id.clone(),
					)
				};
				let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
					.ok_or(HftError::DecimalsNotConfigured(dest))?;
				let amount = convert_to_balance::<
					<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance,
				>(
					U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
					erc_decimals,
					decimals,
				)
				.map_err(|e| HftError::InvalidAmountConversion(format!("{e:?}")))?;
