## Analog identified: Tron `IntentGatewayV2.withdraw()` accepts a false-returning ERC20 `transfer()` as success, permanently losing escrowed funds

The external report's core class is: "tokens that don't follow a standard specification can misbehave when treated as compliant ERC20 in the protocol's code, and there is no systematic check for this." The closest local, code-verifiable analog is in the Tron port of the Intent Gateway's escrow-release path, which does exactly the anti-pattern that `SafeERC20` exists to prevent: it treats "the external call didn't revert" as proof of a successful token transfer, without inspecting the ABI-encoded boolean return value that ERC20's `transfer`/`transferFrom` are supposed to return.

### Title
Escrow release trusts a reverting-only check on `transfer()`, silently losing funds for non-reverting-false ERC20 tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` (Tron variant) imports `SafeERC20` and uses `safeTransferFrom` for escrow deposits, but the escrow-release code paths (`withdraw`, `sweepDust`, the fee-token payout) instead issue a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the low-level call did not revert. ### Finding Description
`withdraw()` finalizes the order (`_filled[body.commitment] = beneficiary`), decrements the internal `_orders[commitment][token]` escrow accounting, and attempts the payout via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

Per ERC20 (and explicitly per the pattern `SafeERC20` is designed to guard against), a `transfer` call can complete without reverting yet still return `false` to signal failure (e.g., insufficient allowance-adjacent internal checks, paused/blacklist tokens, or simply non-standard tokens that follow the letter but not the safety expectations of the spec — precisely the class of asset called out in the external report). The code here never decodes `returndata` to inspect that boolean; it only checks that the call itself didn't revert. A `call` to a contract that returns `abi.encode(false)` still reports `success == true` at the low level.

Because `_filled[commitment]` and `_orders[commitment][token]` are already mutated before/alongside this unchecked transfer, once `withdraw()` runs, the order is marked as filled and its escrow is decremented regardless of whether the beneficiary actually received the tokens. There is no retry path — `_filled` prevents any second attempt at settlement for that commitment.

This directly contradicts the file's own security posture: the contract deliberately imports `SafeERC20` and uses `safeTransferFrom` for the deposit side, showing the authors are aware that raw ERC20 return values must be validated, but the release side reverts to the unsafe pattern.

### Impact Explanation
This is a direct, permanent loss of escrowed user/solver funds: the tokens remain locked in the `IntentGatewayV2` contract balance (never actually transferred out) while the protocol's internal state believes the order is settled and the escrow released. The rightful beneficiary receives nothing, and no compensating code path exists to reclaim the funds, since `_filled` blocks re-processing. This matches the bounty's explicit "stealing or loss of funds" and "false ... acceptance" (of a completed transfer) impact categories.

### Likelihood Explanation
No malicious peer, relayer, prover, or admin is required. Any order (same-chain refund/redeem or cross-chain `onAccept`-triggered `withdraw`) that uses an input token which returns `false` on failure instead of reverting will trigger this silently — this is a realistic subset of ERC20 tokens in production (some proxy/upgradeable tokens, some legacy tokens, and tokens with soft-fail conditions such as pausability or allowlist checks that return `false`). Because the token address is user/order-supplied data (`order.inputs[i].token`), an ordinary user or solver constructing an order around such a token (intentionally or not) is enough to trigger the loss — no privileged actor or off-chain compromise needed.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` / `.transferFrom` pattern in this file with the already-imported `SafeERC20.safeTransfer` / `safeTransferFrom`, consistent with how deposits are already handled elsewhere in the same contract. This restores the boolean-return-value check (and handles missing-return-data tokens) uniformly across deposit and withdrawal paths.

### Proof of Concept
1. Deploy (or use) an ERC20-like token whose `transfer()` implementation returns `false` on some internal condition instead of reverting (e.g., a paused-transfer token, or a mock token built specifically to return `false`).
2. A user places a cross-chain order on the source chain using this token as an input asset via `placeOrder`, escrowing it in `_orders[commitment][token]`. [5](#0-4) 
3. The order is filled on the destination chain and a `RedeemEscrow` message is relayed back, causing `onAccept` to call `withdraw(body, false)` on the source chain.
4. Right before settlement, the mock token is toggled to have `transfer()` return `false` (simulating a real-world pause/blacklist condition) without reverting.
5. `withdraw()` executes: `token.call(...)` returns `success = true` at the low level (no revert) even though the encoded return value is `false`; the `if (!success) revert TransferFailed();` check passes; `_filled[commitment]` is set and `_orders[commitment][token]` is decremented, while the beneficiary's token balance never increases.
6. The beneficiary has no way to reclaim the escrowed tokens — `_filled` already marks the commitment as settled, permanently orphaning the funds inside the contract.
