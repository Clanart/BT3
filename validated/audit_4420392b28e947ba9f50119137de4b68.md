### Title
Per-nonce binding factors are identical across all nonce slots, letting a malicious signer correlate the group nonces of a multi-nonce signing session - (File: crypto/frost/src/nonce.rs)

### Summary
The Arbitrum bug class is "validation bound to a shared identifier (mutualId) rather than the specific edge, so any sibling/rival inherits the accumulated credit." The analog in Serai is `BindingFactor::calculate_binding_factors`, which claims to derive a *per-nonce, per-participant* binding factor `rho` but actually clones the same `rho_transcript` once per participant and squeezes `challenge(b"rho")` on an un-advanced transcript — producing the **identical scalar** for every nonce index `n`. Every nonce slot therefore "inherits" the same binding factor, exactly like every rival edge inheriting the same timer.

### Finding Description
In `crypto/frost/src/nonce.rs` lines 161-172:

```rust
pub(crate) fn calculate_binding_factors<T: Clone + Transcript>(&mut self, transcript: &T) {
    for (l, binding) in &mut self.0 {
      let mut transcript = transcript.clone();
      transcript.append_message(b"participant", ...);
      binding.binding_factors = Some(
        (0 .. binding.commitments.nonces.len())
          .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
          .collect(),
      );
    }
}
```

The `transcript.clone()` is outside the `.map()` and `challenge(b"rho")` does not absorb anything back into the transcript, so the mapped closure returns the same `rho` for all `0 .. nonces.len()`. This contradicts:

- `spec/cryptography/FROST.md` lines 31-33: "When additional nonces are used, this is actually a per-nonce per-participant binding factor."
- The in-code comment: "This generates a binding factor per nonce just to ensure it never comes up as a question" — it does not actually generate distinct factors.

The bound nonce per slot is `D_{l,i} + rho_l * E_{l,i}` (`bound()` at lines 180-190, `nonces()` at lines 194-212). Because `rho` is shared across slots, a malicious signer can enforce a **fixed, `rho`-independent additive relation between its own bound nonces in different slots**. Concretely, it chooses `E_{l,0} = E_{l,1} = E` and `D_{l,1} = D_{l,0} + X*G`; then its bound nonce for slot 1 equals `bound_0 + X*G` regardless of the (unknown-to-it-at-commitment-time) `rho` value. With genuinely distinct per-slot `rho_i`, no such relation can be forced, since the relation would need to hold simultaneously under two independent hashes of the same commitments.

The `rho_transcript` in `crypto/frost/src/sign.rs` lines 362-368 binds `group_key`, `hash_msg(msg)`, and a hash of all participants' commitments — it does *not* distinguish nonce index, which is the missing binding analogous to the missing `edgeId` check in `checkClaimIdLink`.

### Impact Explanation
Multi-nonce algorithms (the `nonces()` API returning `Vec<Vec<G>>`, exercised by `MultiNonce` in `crypto/frost/src/tests/nonces.rs`) treat each nonce slot as an independent Schnorr-style nonce to be combined into the share/signature. The security argument requires that a signer cannot force algebraic relations between the *group* nonces of different slots. With a shared `rho`, a malicious signer shifts the group nonce in slot `i` by an adversary-chosen `X*G` relative to slot 0. For any algorithm where the per-slot challenges differ (e.g., different HRAm outputs, different generator bases, or independent signature components), related nonces under distinct challenges produce shares whose differences leak `lambda_i * secret_share` — the classic related-nonce / ROS-style key-share recovery that the binomial `d + rho*e` construction exists to prevent. At minimum this is an incorrect binding-factor derivation: the verifier-side aggregation in `nonces()` uses weights that are not unique per nonce, breaking the documented per-nonce-per-participant binding and the FROST security reduction for `nonces.len() > 1`.

### Likelihood Explanation
Reachable by any unprivileged signing participant via public inputs only: preprocesses are attacker-controlled bytes fed through `read_preprocess`/`Commitments::read` into `sign()` (`crypto/frost/src/sign.rs` lines 276-287, 322-357). The attack requires a `Algorithm` implementation using more than one nonce (`nonces().len() > 1`); within the in-scope crates the shipped algorithms (IetfSchnorr, Schnorrkel, bitcoin Schnorr) use a single nonce, so exploitation depends on an in-scope multi-nonce algorithm being instantiated. The defect is deterministic — no grinding is needed since the relation `X` is fixed before `rho` is derived. This makes it a real-but-conditional Medium rather than a High: the identical-`rho` derivation is unconditionally wrong per the spec, but concrete share recovery additionally needs a downstream algorithm that derives independent challenges per nonce slot.

### Recommendation
Derive a distinct binding factor per nonce index, e.g. append the nonce index before squeezing:

```rust
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|n| {
      let mut t = transcript.clone();
      t.append_message(b"participant", C::F::from(u64::from(u16::from(*l))).to_repr());
      t.append_message(b"nonce", C::F::from(n as u64).to_repr());
      C::hash_binding_factor(t.challenge(b"rho").as_ref())
    })
    .collect(),
);
```

This binds each slot's `rho` to its specific index (the analog of binding the claim to the specific `edgeId` rather than the shared `mutualId`), so commitments for one nonce can no longer inherit/alias the binding factor of another.

### Proof of Concept
The defect is provable directly from the code, since `RecommendedTranscript`/`challenge` is a pure squeeze:

```rust
// Inside BindingFactor::calculate_binding_factors (nonce.rs:161-172)
let mut transcript = transcript.clone();          // cloned ONCE per participant
transcript.append_message(b"participant", ...);
binding.binding_factors = Some(
  (0 .. binding.commitments.nonces.len())
    .map(|_| C::hash_binding_factor(transcript.challenge(b"rho").as_ref()))
    //   ^^ `transcript` is not advanced between iterations and `challenge`
    //      does not mutate it: identical input => identical rho for all n
    .collect(),
);
```

Therefore `binding_factors(l)[0] == binding_factors(l)[1] == ...` for every participant `l`, verifiable by instrumenting `MultiNonce` (`crypto/frost/src/tests/nonces.rs`, which uses two nonce slots) and asserting on `B.binding_factors(l)`. Exploit sketch for a two-nonce algorithm: malicious signer `m` waits for honest preprocesses (rushing), then publishes `Commitments` with `nonces[0] = (D, E)`, `nonces[1] = (D + X*G, E)` for chosen scalar `X`. Because `rho_{m,0} == rho_{m,1}`, its bound nonces satisfy `bound_1 = bound_0 + X*G`, shifting the slot-1 group nonce by `X*G` — a relation impossible under distinct per-slot `rho`, since `rho_{m,1}` commits to the already-published commitments. Repeating this across sessions where the algorithm applies different challenges/weights to slot 0 vs. slot 1 (as `MultiNonce::sign_share` does at `tests/nonces.rs:110-119`) yields a solvable linear system in the victim's interpolated share `lambda_i * x_i`, recovering the honest participant's key share from public signature shares alone.

Caveat: I verified the identical-`rho` derivation and the binding structure in `nonce.rs`/`sign.rs`; the end-to-end share-recovery step assumes a multi-nonce `Algorithm` whose per-slot challenges differ (none of the shipped in-scope algorithms use >1 nonce, so a full exploit needs such an algorithm in the integrator). The root cause — shared binding factor across nonce slots — is unconditional.
