### Title
`IntentGatewayV2.withdraw()` on Tron does not validate ERC20 `transfer()` return data, allowing escrow to be marked released without the beneficiary receiving funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` settles escrowed tokens with a raw low-level `.call` to `IERC20.transfer`, checking only that the call did not revert (`success`), never decoding the ABI-encoded boolean return value. This is the same class of bug as the report's core invariant break: a failure signal from an external dependency is not properly caught/validated, so the contract proceeds to finalize state as if the operation succeeded.

### Finding Description
`withdraw()` is the single settlement path used for both fill-redemption (`RedeemEscrow`) and refunds/cancellations (`RefundEscrow`), reached from `onAccept()` (cross-chain settlement messages from the host) and `onGetResponse()` (cancel-from-source flow): [1](#0-0) 

For every escrowed input token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the low-level call reverted — it does **not** decode/verify the returned `bool` from `transfer()`. Many ERC20/TRC20 tokens (a very common pattern precisely on Tron/BSC-style chains, which is why this file is a separate Tron-specific implementation rather than using the mainline EVM `IntentGatewayV2`) return `false` on failure instead of reverting. In that case `success == true` even though the beneficiary received zero tokens.

Despite importing `SafeERC20` (`using SafeERC20 for IERC20;`), the withdrawal/settlement path deliberately avoids it and uses the raw `.call` pattern for both `withdraw()` and the `SweepDust` fee-transfer paths: [2](#0-1) 

Immediately after the unchecked transfer, `withdraw()` irrevocably finalizes accounting regardless of whether the token actually moved: [3](#0-2) 

- `_filled[body.commitment] = beneficiary` is set at the top of the function before any transfer is attempted.
- `_orders[body.commitment][token] -= amount` is decremented as if the transfer succeeded.
- `EscrowReleased`/`EscrowRefunded` is emitted, telling off-chain systems settlement is complete.

This exactly mirrors the external report's broken invariant: a call that can silently signal failure (via return value rather than revert) is not properly checked, so the wrapper/caller treats it as success and commits state that should have required the fallback/failure path (here: retry, revert the whole transaction, or route to a genuine failure handler).

### Impact Explanation
This is a direct, permanent loss-of-funds bug in the bridge's escrow custody logic:
- Once `withdraw()` runs, the escrow accounting (`_orders[...][token]`) is decremented and `_filled` is set, marking the order as settled — this is irreversible via any user-facing entrypoint.
- If the underlying token's `transfer()` returns `false` on failure (e.g., due to a paused token, an internal blacklist, or any non-reverting failure condition), the beneficiary receives nothing while the protocol's bookkeeping shows the escrow as released/refunded.
- The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path pointing back to the rightful beneficiary — a direct violation of the invariant that "bridged assets, order escrow, refunds ... must move exactly once and only to the rightful beneficiary and amount."
- No malicious relayer, prover, or governance actor is required — this can be triggered by ordinary use of a token whose `transfer()` implementation follows the non-reverting-boolean pattern, which is common precisely in the Tron/TRC20 ecosystem this contract targets.

### Likelihood Explanation
The settlement path (`onAccept` → `withdraw`, and `onGetResponse` → `withdraw`) is triggered automatically as part of ordinary cross-chain order fulfillment/cancellation flows once a valid ISMP message/proof arrives — no attacker privilege is needed beyond using or interacting with an order that involves a non-standard-compliant ERC20/TRC20 token. Given this file is Tron-specific, and many Tron/BSC-style tokens are known to return `false` instead of reverting, the probability of encountering such a token in production is non-trivial, and the resulting failure is silent (no revert, so it won't be caught by transaction-level monitoring).

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` usages in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, which already is imported (`using SafeERC20 for IERC20;`) but unused for these transfers. `safeTransfer` correctly decodes the return data and reverts on `false`, ensuring `_filled`/`_orders` accounting is only ever finalized after tokens are confirmed to have moved to the beneficiary.

### Proof of Concept
1. Register/escrow an ERC20-like token on the Tron `IntentGatewayV2` deployment whose `transfer()` implementation returns `false` (rather than reverting) when the transfer cannot be completed (e.g., recipient blacklisted, contract paused, insufficient allowance/quirky implementation).
2. Have the token enter a state where `transfer()` to the intended beneficiary would fail per that token's internal logic, but the call itself does not revert (returns `false`).
3. Trigger settlement via the normal flow: solver fills the order cross-chain, host relays the `RedeemEscrow` message, `onAccept()` calls `withdraw()`, or the order is cancelled and `onGetResponse()` calls `withdraw()`.
4. Observe: `token.call(...)` returns `success = true` (call succeeded) even though the internal `transfer()` returned `false` and moved no tokens.
5. `withdraw()` proceeds to decrement `_orders[commitment][token]`, mark `_filled[commitment] = beneficiary`, and emit `EscrowReleased`/`EscrowRefunded` — the protocol now believes settlement is complete.
6. The beneficiary's token balance is unchanged; the escrowed tokens remain locked in the `IntentGatewayV2` contract with no further code path to recover them for that beneficiary.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
