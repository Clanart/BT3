### Title
Unprivileged third party can forge a blame accusation that marks an honest DKG recipient faulty — (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

The Lemmy report describes a privileged-state-changing path reachable by signed remote input that omits an authorization/rank check present in the local API. The Serai analog lives in PedPoP's blame protocol: `BlameMachine::blame` / `AdditionalBlameMachine::blame` accept an accusation of the form "`sender` sent `recipient` an invalid share" from *anyone*, for *any* `(sender, recipient)` pair. When the accusation carries no `EncryptionKeyProof` — which only the true recipient could produce — `Decryption::decrypt_with_proof` returns `DecryptionError::InvalidProof` and `blame_internal` returns **`recipient`** as the faulty party. Because the `EncryptedMessage` shares are broadcast/publicly observable data, any party who can submit blame statements can get an honest recipient declared faulty with zero cryptographic evidence.

### Finding Description

`blame_internal` resolves an accusation purely from the message and an optional proof:

- If the message's per-message PoP signature is invalid → `sender` is faulty.
- If the proof is absent or the DLEq fails → `recipient` is faulty (`Err(DecryptionError::InvalidProof) => return recipient` at `crypto/dkg/pedpop/src/lib.rs:587`).
- Only if a valid proof exists and the decrypted share fails verification is `sender` blamed.

There is no check that the accuser is the `recipient`, or that the accuser holds anything only the recipient would hold. `AdditionalBlameMachine::new` (`crypto/dkg/pedpop/src/lib.rs:649-662`) explicitly constructs a blame evaluator for non-participants, and its `blame` (`lib.rs:674-682`) passes `sender`/`recipient` straight through. The docs only require that the `msg` "have been authenticated as actually having come from the sender" — nothing binds the accusation to the accused recipient's own claim.

Since `EncryptedMessage` shares are transmitted over broadcast/authenticated channels (and, in Serai's coordinator usage, are published on the tributary as `DkgShares`), the ciphertext and its PoP are public. An attacker takes the real `(sender → recipient)` message — whose PoP is valid — and submits `blame(sender, victim, msg, None)`. The PoP verifies, `proof` is `None`, `decrypt_with_proof` returns `InvalidProof`, and the honest `victim` is returned as faulty. In Serai's deployment this result feeds `RemoveParticipantDueToDkg` / fatal-slashing, so the forged blame removes a validator the attacker had no authority over — the same shape as a federated `Remove` stripping a higher-ranked moderator.

### Impact Explanation

An unprivileged party causes an honest DKG participant to be adjudicated faulty, aborting the DKG and, in Serai's usage, triggering removal/fatal slashing of a participant who did nothing wrong. This is unauthorized removal of a participant via public inputs — integrity impact on validator-set membership with no key compromise required.

### Likelihood Explanation

Requires only access to the publicly transmitted `EncryptedMessage` and the ability to submit a blame statement to the blame evaluation path. No threshold collusion, no secret knowledge, and no valid proof is needed — the missing proof is precisely what condemns the victim. Likelihood is bounded by how the integrator routes blame (Serai's coordinator additionally binds `accuser` to the signer, mitigating the exploit there), but the library API itself performs no such check and documents none.

### Recommendation

Require the blame submitter to prove they are the `recipient` before an accusation can fault the recipient — e.g., require a valid `EncryptionKeyProof` (DLEq over the recipient's registered encryption key) for the accusation to be evaluated at all, and return an error rather than blaming `recipient` when `proof` is `None`. Alternatively, take the accuser's identity as a parameter and verify `accuser == recipient`. Document that blame must only be accepted from the alleged recipient.

### Proof of Concept

1. Participants run PedPoP; `sender` publishes a valid `EncryptionKeyMessage<Commitments>` and a valid `EncryptedMessage<SecretShare>` addressed to `victim`. Both are public.
2. Attacker (any party, including a non-participant using `AdditionalBlameMachine::new(context, n, commitment_msgs)`) calls `blame(sender, victim, msg, None)`.
3. `decrypt_with_proof`: PoP verifies (message is genuine), `proof` is `None` → `Err(InvalidProof)`.
4. `blame_internal` returns `victim` as faulty (`crypto/dkg/pedpop/src/lib.rs:587`), and the integration removes/slashes the honest `victim`.
