### Title
Shared `BalanceHandler` instance across recursive/reentrant precompile calls causes stale `prevEventsLen` checkpoint, desyncing native bank balances from EVM `StateDB` balances - (File: precompiles/common/balance_handler.go)

### Summary
The reported `AntiSandwichHook` bug is a class of "stale mutable checkpoint persisted across calls that should be scoped per-invocation." The Cosmos EVM repository has a documented analog of exactly this bug class in its precompile balance-accounting layer: `BalanceHandler.prevEventsLen` [1](#0-0)  is a single mutable field that records an event-index checkpoint before a precompile call and is consumed after it. When the *same* `BalanceHandler` instance is reused across nested/recursive precompile invocations (rather than one fresh instance per call), the inner call's `BeforeBalanceChange` overwrites the checkpoint set by the outer call, exactly mirroring how `!zeroForOne` swaps overwrote `_lastCheckpoint.state.slot0` and corrupted the next `zeroForOne` swap's pricing.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` into `bh.prevEventsLen`, and `AfterBalanceChange` later replays `events[bh.prevEventsLen:]` to apply `StateDB.AddBalance`/`SubBalance` calls that mirror native bank-module balance changes into the EVM state DB [2](#0-1) .

The safe pattern instantiates a brand-new `BalanceHandler` for every single precompile invocation via `p.BalanceHandlerFactory.NewBalanceHandler()` inside `runNativeAction` [3](#0-2) . This is analogous to explicitly resetting `slot0` on every `zeroForOne` swap in the recommended fix for the reported bug.

However, the repository's own regression-test comment documents that an alternate/older code path used a single, shared `BalanceHandler` instance (obtained via a `GetBalanceHandler()` accessor stored on the precompile struct itself, as seen in the debug precompile `p.GetBalanceHandler()` calls [4](#0-3) ) rather than creating a fresh instance per call:

> "BalanceHandlerTestSuite tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [5](#0-4) 

Grep results show every production precompile (`staking`, `distribution`, `gov`, `slashing`, `ics20`, `erc20`) references `BalanceHandler` exactly once, consistent with the same `GetBalanceHandler()` singleton-accessor pattern used by the debug precompile, rather than the `RunNativeAction`/factory pattern that mints a fresh handler per call. I was not able to directly open `precompiles/staking/staking.go`, `precompiles/distribution/distribution.go`, `precompiles/gov/gov.go`, `precompiles/slashing/slashing.go`, `precompiles/ics20/ics20.go`, or `precompiles/erc20/erc20.go` in this session to confirm whether their `Run()` methods use a per-precompile-struct singleton `BalanceHandler` (vulnerable) or route through `runNativeAction` (safe). This is the critical unresolved fact needed to fully confirm live exploitability in production precompiles.

If any of these precompiles use the singleton pattern, an attacker-controlled contract can trigger the bug deterministically and without special privileges: a contract calls a precompile (e.g., staking `Delegate`), and from within that call (via a token hook, callback, or another contract call chain) triggers a second, nested call into the *same* precompile address before the outer call's `AfterBalanceChange` executes. The inner call's `BeforeBalanceChange` resets `prevEventsLen` to a later index. When the outer call's `AfterBalanceChange` finally runs, it replays `events[prevEventsLen:]` using the *inner* call's checkpoint — either skipping bank events that should have credited/debited the EVM `StateDB` (causing a state omission/loss) or, depending on ordering, re-processing events already consumed by the inner call (causing a double `AddBalance`/`SubBalance` in `StateDB`, i.e., balance duplication not backed by an actual bank-module movement).

### Impact Explanation
This maps directly to the required "Critical unauthorized minting, burning, duplication, or irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" bucket. A double-`AddBalance` desync would create EVM-visible balance not backed by the native `x/bank`/`x/precisebank` ledger (effectively unbacked minting of spendable EVM value), while a missed decrement/increment would permanently lose or freeze value reflected in EVM state relative to the bank keeper's true balance — breaking the 1:1 accounting invariant between native coins and EVM-visible balances that `x/precisebank`/precompile-mediated balances are supposed to preserve.

### Likelihood Explanation
Likelihood depends entirely on whether any production precompile's `Run()` method retrieves a `BalanceHandler` via a shared/singleton accessor (as the debug precompile does) instead of the safe per-call factory pattern in `runNativeAction`. The repository's own test suite name and doc comment ("tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance") indicates this defect existed and was significant enough to warrant a dedicated regression test, implying the vulnerable pattern was present in the codebase at some point (possibly still present for one or more precompiles, or fully replaced by the factory pattern — I could not confirm which, given remaining tool budget).

### Recommendation
- Audit every production precompile's `Run()`/dispatch entrypoint (`staking`, `distribution`, `gov`, `slashing`, `ics20`, `erc20`, `werc20`, `bank`, `bech32`) to confirm each precompile call obtains a **new** `BalanceHandler` instance per invocation (matching the `runNativeAction` factory pattern), never a field cached on the long-lived precompile struct.
- Remove/deprecate any `GetBalanceHandler()`-style accessor that returns a shared instance if still reachable from production code paths.
- Add a nonreentrancy guard or per-call unique handler at the EVM `StateDB` precompile-dispatch layer so that nested/recursive precompile calls cannot share event-index checkpoints, independent of any individual precompile's implementation choice.

### Proof of Concept
Not independently reproduced in this session (no execution environment available). The repository's own `TestRecursivePrecompileCallsWithDebugPrecompile` [6](#0-5)  is the existing PoC harness for this exact bug class — it deploys a caller contract that recursively invokes the debug precompile and asserts a specific count of resulting `debug_precompile`/balance-change events. Reusing this harness against a *production* precompile that shares a single `BalanceHandler` instance (once confirmed via source review not completed here) would demonstrate the same `prevEventsLen` corruption and resulting `StateDB` balance desync against real, spendable balances.

This is the single fact required to convert this from "documented historical bug class with matching root cause in the codebase" into a fully confirmed, currently-exploitable Critical finding in production precompiles. func (p Precompile) Run(evm *vm.EVM, contract *vm.Contract, readonly bool) ([]byte, error) {
	stateDB, ok := evm.StateDB.(*statedb.StateDB)
	if !ok {
		return nil, errors.Wrap(errors2.ErrUnauthorized, "could not create statedb in debug precompile")
	}

	// get the stateDB cache ctx
	ctx, err := stateDB.GetCacheContext()
	if err != nil {
		return nil, err
	}

	// take a snapshot of the current state before any changes
	// to be able to revert the changes
	snapshot := stateDB.MultiStoreSnapshot()
	events := ctx.EventManager().Events()

	// add precompileCall entry on the stateDB journal
	// this allows to revert the changes within an evm tx
	err = stateDB.AddPrecompileFn(p.Address(), snapshot, events)
	if err != nil {
		return nil, err
	}

	// commit the current changes in the cache ctx
	// to get the updated state for the precompile call
	if err := stateDB.CommitWithCacheCtx(); err != nil {
		return nil, err
	}

	// Start the balance change handler before executing the precompile.
	p.GetBalanceHandler().BeforeBalanceChange(ctx)

	initialGas := ctx.GasMeter().GasConsumed()

	// set the default SDK gas configuration to track gas usage
	// we are changing the gas meter type, so it panics gracefully when out of gas
	ctx = ctx.WithGasMeter(storetypes.NewGasMeter(contract.Gas)).
		WithKVGasConfig(p.KvGasConfig).
		WithTransientKVGasConfig(p.TransientKVGasConfig)
	// we need to consume the gas that was already used by the EVM
	ctx.GasMeter().ConsumeGas(initialGas, "creating a new gas meter")

	// This handles any out of gas errors that may occur during the execution of a precompile tx or query.
	// It avoids panics and returns the out of gas error so the EVM can continue gracefully.
	defer cmn.HandleGasError(ctx, contract, initialGas, &err)()

	res, err := p.Execute(ctx, stateDB, contract, readonly)
	if err != nil {
		return nil, err
	}

	if err != nil {
		return nil, err
	}

	cost := ctx.GasMeter().GasConsumed() - initialGas

	if !contract.UseGas(cost, nil, tracing.GasChangeCallPrecompiledContract) {
		return nil, vm.ErrOutOfGas
	}

	// Process the native balance changes after the method execution.
	if err := p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB); err != nil {
		return nil, err
	}

	return res, nil
}

	callerContract, err := contracts.LoadDebugPrecompileCaller()

		ConstructorArgs: []interface{}{},
