Bitcoin Schnorr adapter emits invalid signatures when the aggregate nonce `R` has odd Y - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin `Schnorr` algorithm wrapper in `bitcoin_serai::crypto` attempts to enforce BIP-340's even-Y `R` requirement by negating `s` after the FROST signature is assembled. This is mathematically incorrect: negating `s` negates the entire right-hand side of the verification equation, not just `R`. Whenever the aggregate nonce point is odd (probability ~1/2), the produced 64-byte signature fails on-chain verification, making the signed transaction unspendable.

### Finding Description
`FrostSchnorr::sign_share` produces `s = r + c·a` satisfying `s·G = R + c·A`, where `c = H(R.x || A || m)` per BIP-340 (`crypto/frost/src/algorithm.rs`, `sign_share`/`verify`, lines 201-217). [1](#0-0) 

Bitcoin consensus verifies `(R_x, s')` as `s'·G == R' + e·A`, where `R'` is the *even-Y* lift of `R_x`. When `R` is odd, `R' = -R`, so the required scalar is `s'` with `s'·G = -R + c·A = -r + c·a`. The wrapper instead outputs `s' = -s`: [2](#0-1) 

Then `(-s)·G = -R - c·A ≠ -R + c·A` unless `c·a = 0`. The inner `verify` call validates the un-negated relation (`s·G = R + c·A`, which holds regardless of parity), so `complete` in `TransactionSignatureMachine` happily emits the corrupted signature into the witness. [3](#0-2) 

This mirrors the Mithril bug class: data relied upon by the downstream verifier (the Y-parity of `R`, implicitly committed by the BIP-340 x-only encoding) is not correctly covered by the transformation applied to the authenticated/signed object — the signed `s` does not actually bind the parity-normalized `R'` that the network checks.

### Impact Explanation
Roughly half of all threshold-signed Bitcoin transactions produced via `SignableTransaction`/`TransactionMachine` carry a signature that Bitcoin nodes will reject (`non-mandatory-script-verify-flag (Invalid Schnorr signature)`), since the aggregate `R` is odd with probability ~1/2. The affected `ReceivedOutput` inputs are reportable as received but the spend transaction cannot be broadcast — funds are effectively unspendable until the signing session is re-run with a different nonce set. A malicious signing participant can additionally *choose* their hiding nonce to force the aggregate `R` to be odd, guaranteeing failure on demand (griefing every signing attempt).

### Likelihood Explanation
~50% per signing session by chance alone; ~100% with one malicious participant who observes others' hiding commitments and picks their nonce commitment to force odd aggregate `R`. No collusion or privileged access needed — just participation in the FROST session feeding `read_preprocess`/`sign`/`complete`.

### Recommendation
Do not post-hoc negate `s`. Instead, normalize parity before the challenge/signature: derive the BIP-340 nonce parity inside `sign_share`/`verify` by checking `needs_negation(nonce_sums[0][0])` *before* computing the share, and have each participant negate their combined nonce scalar (`d + ρ·e`) when `R` is odd — i.e., emit `s' = -(d + ρ·e) + c·a`. That yields `s'·G = -R + c·A` as required. If the trait shape prevents this, document that the algorithm must fail (return an error from `verify`) on odd `R` so callers retry rather than emit an invalid signature.

### Proof of Concept
Conceptually: run `key_gen` + `tweak_keys`, build a `SignableTransaction`, and sign via `TransactionMachine` (`networks/bitcoin/tests/wallet.rs`, `sign()`). Repeat until the completed transaction's input-0 witness signature has `R` with odd Y (inspect `sig[0..32]` lifted as a point). Submit to a regtest node: `sendrawtransaction` fails with a Schnorr verification error, while `FrostSchnorr`'s internal `sig.verify(group_key, c)` on the *un-negated* `s` passes — demonstrating the emitted signature does not satisfy `s·G = R' + e·A` for the even lift `R' = -R`.
