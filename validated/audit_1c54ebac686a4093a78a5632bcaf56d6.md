### Title
`SignableTransaction::new` omits the `OP_RETURN` data output from fee/weight estimation, underpaying the fee and producing transactions that can fail relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class in the external report is a hardcoded/stale assumption about external state causing funds to become stuck. The analog in `bitcoin-serai` is that `SignableTransaction::new` hardcodes its fee calculation over only `payments` (and optionally `change`), while the actual transaction it builds additionally includes an `OP_RETURN` output carrying up to 80 bytes of data. The fee therefore does not correspond to the transaction actually produced and signed.

### Finding Description
In `SignableTransaction::new`, the data output is pushed onto `tx_outs` before the fee estimate, but the estimate is computed from `payments` only:

- `networks/bitcoin/src/wallet/send.rs:194-202` pushes `TxOut { value: 0, script_pubkey: OP_RETURN <data> }` into `tx_outs` whenever `data` is present.
- `networks/bitcoin/src/wallet/send.rs:204` then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, which builds a throwaway `Transaction` containing only `payments` (lines 85-94) — the `data` output is never accounted for.
- The same omission occurs in the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` at line 226 also ignores the `OP_RETURN`.

`calculate_weight_vbytes` copies the real script_pubkeys but never receives `data`, so both `weight` and `vbytes` are underestimated by roughly `9 + len(data)` bytes (~36–360 weight units). `needed_fee = fee_per_vbyte * vbytes` (line 206) is therefore too low, and the `TooLowFee` check at line 211 compares against this underestimated `vbytes`.

When no change output is produced the absolute fee is still `input_sat - payment_sat`, which is large, so this mainly bites in the change path: at line 228 the change amount is `input_sat - payment_sat - fee_with_change`, leaving the actual paid fee equal to the underestimated `fee_with_change` while the real transaction is larger. An unprivileged user cannot choose `data` directly, but `data` is produced from on-chain/bridge instructions that external actors influence (deposits embed instruction data), so this is reachable via public transaction data the protocol signs.

### Impact Explanation
A signed transaction carrying a `data` output pays a fee rate lower than the `fee_per_vbyte` the protocol intended, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` even though the `TooLowFee` check passed — because the check itself used the underestimated `vbytes`. Such a transaction is rejected by node mempool policy, leaving the spent outputs unconfirmed/unusable until a new transaction is constructed and re-signed. This is a "funds temporarily unspendable / protocol operation breaks under reachable conditions" analog: the parameter assumed (transaction size) does not match the externally committed artifact (the actual signed transaction), mirroring how the hardcoded predicate silently mismatched the real bridge state.

### Likelihood Explanation
Any `SignableTransaction` constructed with `data` and a `change` output is affected. Whether the underpayment crosses the relay minimum depends on the requested `fee_per_vbyte`: at fees near 1 sat/vbyte the ~20–90 vbyte shortfall can drop the effective rate below the minimum. At higher fee rates the transaction still confirms but pays a lower effective rate than requested. Marginal Medium.

### Recommendation
Include the `data` output in the weight estimate: change `calculate_weight_vbytes` to take the full output list (or pass `data` and append the `OP_RETURN` `TxOut` inside it), and call it with the actual `tx_outs` (including the `OP_RETURN`) at both call sites (`send.rs:204` and `send.rs:226`). This makes `needed_fee`, the `TooLowFee` check, and the change computation all reflect the transaction that will actually be signed.

### Proof of Concept
```rust
// Construct inputs covering payments, a change script, and ~80 bytes of data
let tx = SignableTransaction::new(
  vec![output],
  &[(payment_script, payment_amount)],
  Some(change_script),
  Some(vec![0u8; 80]),      // OP_RETURN data
  1,                        // 1 sat/vbyte
).unwrap();

// tx.needed_fee() was computed over a transaction *without* the OP_RETURN output,
// but `tx.transaction()` contains it. The real vsize exceeds the estimated one by
// ~89 vbytes (OP_RETURN + pushdata + amount + varint), so:
assert!(tx.fee() < tx.transaction().vsize() as u64); // effective rate < 1 sat/vbyte
// If needed_fee was only marginally above DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000,
// the broadcast transaction is non-standard and will not relay.
```

Caveat: `processor/` code is out of scope, so whether the coordinator routinely attaches ~80-byte `data` outputs with change could not be fully verified; within the in-scope crate the miscalculation is unconditional whenever `data.is_some()`.
