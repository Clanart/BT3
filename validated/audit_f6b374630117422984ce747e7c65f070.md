### Title
Unvalidated duplicate/self participant index in `GeneratorPromotion::complete` causes a panic (host crash) — ([File: crypto/dkg/promote/src/lib.rs](crypto/dkg/promote/src/lib.rs))

### Summary

`GeneratorPromotion::complete` validates the untrusted `proofs` map only for *count* (`len() == n - 1`) and *range* (`key <= n`), but never checks that the keys are distinct from `params.i()` or that they cover every required index `1..=n`. A peer who submits their `GeneratorProof` under the victim's own participant index produces a map that passes both checks yet is missing some required index `j`, causing `proofs.get(&j).unwrap()` to panic. This is the Serai analog of CVE-2017-10917 (XSA-221): an untrusted index value is consumed without full validation, leading to a crash.

### Finding Description

In `crypto/dkg/promote/src/lib.rs`, `complete` performs two checks on the attacker-influenced `HashMap<Participant, GeneratorProof<C1>>`:

- Length check at `crypto/dkg/promote/src/lib.rs:125` — `proofs.len() == n - 1`.
- Range check at `crypto/dkg/promote/src/lib.rs:132-136` — every key `<= params.n()`.

It then iterates `1 ..= params.n()`, skips `params.i()`, and does an unconditional lookup:

```rust
let proof = proofs.get(&i).unwrap();   // lib.rs:146
```

Because `Participant` is merely a non-zero `u16` (`crypto/dkg/src/lib.rs:121-125`), a malicious participant can supply their proof keyed as `params.i()` (the victim's own index). The map then has `n - 1` entries, all `<= n`, all non-zero — both validations pass — but index `j` (the index that participant *should* have occupied) is absent. `proofs.get(&j)` returns `None` and `.unwrap()` panics, crashing the promotion ceremony on the victim's node.

Note the parallel construction in `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:361-365`) and `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:473-491`) does check `i > n`, duplication, and membership; `complete` is missing the equivalent "key must not be self / must cover all peers" validation.

### Impact Explanation

An unprivileged peer participating in a generator-promotion ceremony can remotely crash the victim's promotion path (panic = denial of service, analogous to the NULL-deref host crash in XSA-221). During a validator rotation or generator migration this aborts key promotion, and since it panics rather than returning an error, it can take down the calling process rather than failing gracefully. The promotion is `n`-of-`n`, so a single malicious participant suffices.

### Likelihood Explanation

Any participant in a `GeneratorPromotion` ceremony controls the `Participant` key under which their proof is inserted into the `proofs` map (the caller builds the map from received, serialized `GeneratorProof` messages — `GeneratorProof::read` at `lib.rs:72-77` imposes no index constraints). Triggering requires only sending one proof under a duplicate/self index. However, it only fires during promotion ceremonies and the impact is limited to a crash (no key material is leaked, no invalid keys are accepted — the verification at `lib.rs:147-154` still runs for present entries), so it is a Medium-severity availability issue rather than a critical key-compromise.

### Recommendation

In `GeneratorPromotion::complete`, extend the key validation loop to also reject `i == params.i()`, or replace the `unwrap()` at `lib.rs:146` with a checked lookup returning `PromotionError::InvalidParticipant`/`IncorrectAmountOfParticipants` when a required index is absent. Equivalently, verify `proofs.keys()` equals the set `{1..=n} \ {params.i()}` before iterating.

### Proof of Concept

```rust
// Setup: n = 3 participants, victim is participant 1.
// Victim calls GeneratorPromotion::<C1, C2>::promote(...) and receives
// GeneratorProofs from participants 2 and 3.
let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();

// Malicious participant 2 submits a well-formed proof but keyed under the
// VICTIM's index (1) instead of their own (2).
proofs.insert(Participant::new(1).unwrap(), malicious_proof);
// Participant 3 behaves honestly.
proofs.insert(Participant::new(3).unwrap(), honest_proof_from_3);

// proofs.len() == 2 == n - 1            -> passes count check (lib.rs:125)
// all keys (1, 3) <= n = 3              -> passes range check (lib.rs:132-136)
// Iteration reaches i = 2:
//   proofs.get(&Participant(2)) -> None
//   .unwrap() -> PANIC                    (lib.rs:146)
promotion.complete(&proofs); // thread panics; ceremony aborted
```

All other peers' proofs can be individually valid; the crash is caused purely by the unvalidated index set, mirroring the unvalidated event-channel port number in CVE-2017-10917.
