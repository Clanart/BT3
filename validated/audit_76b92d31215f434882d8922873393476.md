## Title
Vote Account Commission (bps) Can Be Raised With No Timing Restriction, Letting the Withdrawer Retroactively Grab a Larger Share of Already-Computed Epoch Rewards - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
The BeetleBattle report's broken invariant is: a state-mutating function (`markBeetleSafe()`) checks only *ownership*, not *timing/context*, letting the caller retroactively change an outcome-affecting parameter after the relevant event (battle) has already happened, denying the counterparty (the winner) their expected reward. The Agave analog is `update_commission_bps()` in the vote program, which — unlike the legacy `update_commission()` — was intentionally stripped of the epoch-timing guard (`is_commission_update_allowed`) that exists specifically to stop a validator from changing its take of rewards right before/around the point those rewards are computed for delegators.

## Finding Description
The legacy commission-update path enforces a timing rule: increases are only allowed in the first half of an epoch, decreases are always allowed: [1](#0-0) 
backed by: [2](#0-1) 

This rule exists precisely to prevent a validator operator from waiting until the outcome of an epoch's staking rewards is effectively known/close, then hiking their commission to capture a larger share, before reverting it — mirroring the "wait until the outcome is known, then mutate protection/ownership state" pattern in the BeetleBattle bug.

The newer SIMD-0291 `update_commission_bps()` instruction, however, performs **only a signer check** — no epoch-half timing restriction at all: [3](#0-2) 

The code comment inside it is explicit that this is a deliberate omission:
```
// No commission update rule, per SIMD-0249 and SIMD-0291.
```
and this is corroborated by the test suite's own docstring: [4](#0-3) 

So the only guard on `update_commission_bps` is `verify_authorized_signer(vote_state.authorized_withdrawer(), signers)` — analogous to BeetleBattle's `if (isStaked[_tokenId] != msg.sender) revert InvalidTokenOwner();`: an ownership/authority check with **no check on when** the call happens relative to the event whose outcome it affects (reward calculation).

Reward calculation for staking rewards reads the *current* commission split (`voter_commission_bps`) when it computes `staker_rewards`/`voter_rewards` for the epoch (`calculate_stake_rewards` in `runtime/src/inflation_rewards/mod.rs`, invoked from `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, both of which reference `commission_bps` extensively per the search results). That calculation happens at a fixed point (the reward-calculation block at epoch boundary), but stakers/delegators have no visibility into, or ability to react to, a commission change made in the window immediately preceding that block — because, unlike `update_commission`, `update_commission_bps` has zero forewarning/timing requirement.

## Impact Explanation
A vote account's authorized withdrawer — an "unprivileged" actor from the perspective of other participants (delegators/stakers who have staked to that vote account and have no say over commission changes) — can unilaterally and instantly raise `inflation_rewards_commission_bps` (or `block_revenue_commission_bps`) at any slot, including the slot(s) immediately preceding the epoch's reward-calculation block, then lower it again immediately after. This lets the validator capture an outsized share of the staking rewards that delegators would otherwise have earned, without any window for delegators to deactivate/redelegate stake in response — a fund-loss condition for third-party stakers analogous to the winner in BeetleBattle being denied their earned reward because the loser retroactively "protected" the asset after the outcome was fixed.

## Likelihood Explanation
Likelihood is high given: (1) the change requires only the withdrawer's own signature — no cross-party cooperation or race condition needed; (2) the guard that would prevent this (`is_commission_update_allowed`) already exists in the codebase for the sibling instruction, demonstrating the protocol authors recognize the timing-manipulation risk for commission changes, yet this equivalent protection was not carried over to `update_commission_bps`; (3) the omission is intentional per the SIMD-0291/SIMD-0249 comment, meaning it is not a corner case but the shipped, always-reachable behavior of the instruction whenever `block_revenue_sharing`/BLS/V4 vote accounts are used.

## Recommendation
Apply the same (or an equivalent, bps-aware) timing restriction used in `update_commission()` — i.e., call `is_commission_update_allowed(clock.slot, epoch_schedule)` before allowing commission-bps *increases* in `update_commission_bps()`, or otherwise bound how close to reward calculation/distribution a commission increase can take effect (e.g., apply commission changes only starting the following epoch) so delegators have a fair opportunity to react before an increased commission affects reward splits.

## Proof of Concept
1. Attacker controls a vote account (`VoteStateV4`, `block_revenue_sharing` enabled) with commission (`inflation_rewards_commission_bps`) set low (e.g. 0) to attract delegations.
2. Immediately before the epoch's reward-calculation block (any slot, since no `is_commission_update_allowed` check exists), the withdrawer submits `update_commission_bps(..., commission_bps = 10000 /* 100% */, CommissionKind::InflationRewards, ...)` — this succeeds unconditionally per `programs/vote/src/vote_state/mod.rs:827-859`.
3. The bank's reward-calculation logic reads this live commission value when computing `staker_rewards`/`voter_rewards` for the epoch (`runtime/src/inflation_rewards/mod.rs` / `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`), so all delegator stakers effectively receive 0 rewards for that epoch while the validator's vote account receives the full share.
4. The withdrawer then calls `update_commission_bps` again to lower the commission back to 0, with no restriction, restoring an attractive rate for the next epoch — repeating the extraction indefinitely.

Note: I was not able to fully trace the exact line where `voter_commission_bps` is fetched relative to the block boundary inside `calculation.rs` (the file's content beyond grep match counts was not retrievable within the available context), so confirmation that it always reads the value from the same block as the commission-bps call (rather than a snapshot from an earlier point) should be verified directly in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` before treating this as fully confirmed.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
