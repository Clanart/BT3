## Analog Found

### Title
Unvalidated URL scheme forwarded to `shell.openExternal()` allows attacker-controlled GitHub API objects to trigger local program execution - (File: `app/src/main-process/main.ts`)

### Summary
The Solidity report flags a generic, powerful `call()` primitive that should filter dangerous selectors before executing attacker-influenced data. The GitHub Desktop analog is the `open-external` IPC handler, which wraps Electron's `shell.openExternal()` — itself a well-known dangerous primitive capable of invoking arbitrary registered OS URI handlers/programs — but only inspects the URL to decide whether to *log* it; it never restricts which URI schemes are actually allowed to reach `shell.openExternal()`.

### Finding Description
`ipcMain.handle('open-external', ...)` only lower-cases the path to decide on a log message, then unconditionally forwards it to `shell.openExternal`: [1](#0-0) 

This handler is exposed to the renderer via `main-process-proxy.ts`'s `openExternal`, and is used throughout the UI as the generic "open link" primitive, e.g. `app-shell.ts`: [2](#0-1) 

Many UI surfaces feed values that ultimately originate from GitHub API responses (issue/PR bodies, check-run `details_url`, comment `html_url`, repository `homepage`) directly into `LinkButton`'s `uri` prop, which calls `shell.openExternal(uri)` with **no scheme check at all**: [3](#0-2) 

By contrast, the markdown renderer (`sandboxed-markdown.tsx`) *does* apply a scheme allowlist before invoking the callback that leads to `openExternal`: [4](#0-3) 

This shows the project is aware that arbitrary-scheme links reaching `openExternal` are dangerous and mitigates it in one place (markdown), but the mitigation is not centralized in the shared primitive (`app-shell.ts` / the `open-external` IPC handler / `LinkButton`). Any other call site that plumbs an API-supplied URL into `LinkButton` or `shell.openExternal` without first checking `https?:` bypasses the only guard that exists, exactly analogous to `LSSVMPair.call()` needing a centralized selector filter rather than relying on callers to be careful.

### Impact Explanation
`shell.openExternal` on Electron/OS is documented as risky because certain URI schemes cause the OS shell to execute arbitrary local handlers (e.g., custom-registered protocol handlers, `file://` targets, or platform-specific handler abuse patterns that have previously enabled RCE in other Electron apps). Because GitHub Desktop's central "open link" utility performs no scheme filtering, any code path that forwards a value taken from a GitHub API object (attacker-controlled repository metadata, PR/issue/comment fields, check-run URLs) into `shell.openExternal`/`LinkButton` without pre-validating the protocol becomes a vector for launching an arbitrary OS handler when the user clicks it — satisfying the "attacker controls a GitHub API object … result is code execution" impact class.

### Likelihood Explanation
Medium. Exploitation requires the user to click a link, and the strongest known mitigation (protocol check) is already applied in the sandboxed markdown renderer, which is the most obvious injection surface. However, `LinkButton` and `app-shell.ts`/`main-process-proxy.ts` — the shared low-level primitives — have no such guard, so the safety of the whole app rests on every future/existing call site individually remembering to validate the scheme before passing a value to `LinkButton`/`openExternal`. This is fragile in the same way the report describes: a single powerful function without built-in restriction, whose safety depends entirely on caller discipline.

### Recommendation
Move scheme validation into the shared primitive rather than relying on individual callers:
- In `app/src/main-process/main.ts`'s `open-external` handler, reject (return `false`, do not call `shell.openExternal`) for any URL whose scheme is not `http:`/`https:` (and `mailto:` if needed), mirroring the allowlist already used in `sandboxed-markdown.tsx`.
- Alternatively/also enforce the same check in `app/src/ui/lib/link-button.tsx` before invoking `shell.openExternal(uri)`.
- Audit call sites that pass GitHub API-derived strings (`details_url`, `html_url`, `homepage`, etc.) directly as `LinkButton` `uri` props to confirm they only ever contain `https://github.com/...`-style values, or add validation at the point of consumption.

### Proof of Concept
Conceptual (not confirmed executable without further reverse engineering of the currently-registered OS URI handlers, which is out of scope for static analysis):
1. Attacker sets a GitHub API–controlled field consumed by a `LinkButton` (e.g., a check run's `details_url`, or a PR comment's `html_url`) to a non-`http(s)` URI, such as `file://` pointing at a network share, or a locally-registered dangerous protocol handler.
2. GitHub Desktop renders this value directly as `<LinkButton uri={maliciousUrl}>`.
3. User clicks the link; `LinkButton.onClick` calls `shell.openExternal(uri)` with no scheme check [5](#0-4) , and the `open-external` IPC handler in the main process performs no additional filtering before invoking Electron's `shell.openExternal` [1](#0-0) .
4. Depending on OS-registered handlers for the chosen scheme, this can result in unintended program execution outside of Desktop's control.

Note: I was not able to fully enumerate every renderer call site (e.g., `ci-check-run-popover.tsx`, `pull-request-comment-like.tsx`) that feeds raw API-sourced URLs into `LinkButton` within the available indexed context, so confirming a concrete unsanitized end-to-end path from a specific attacker-controlled API field to `LinkButton` would benefit from a full-repository review in a Devin session.

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })

        const a = ev.target.closest('a')
        if (a !== null) {

        }
      }
    })
