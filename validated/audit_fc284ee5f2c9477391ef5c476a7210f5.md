### Title
Stale `gitHubRepositoryID`/`missing` association reused when re-adding a repository at a previously-tracked path - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
The bug class in the report is a state map (`loanDeployed[nft][id]`) that is cleared on one exit path (`repay`) but not on another (`liquidate`), so a later re-use of the same key inherits stale, uninitialized/partially-initialized state and gets bound to the wrong logical entity. The closest verifiable analog in GitHub Desktop is `RepositoriesStore.addRepository()`, which keys its persisted `IDatabaseRepository` row purely by filesystem `path` and, if a row for that path already exists, returns it unchanged — including whatever `gitHubRepositoryID` and `missing` flag were recorded for whatever content previously lived at that path — with no revalidation that the on-disk repository currently at that path is the same repository.

### Finding Description
`RepositoriesStore.addRepository()` looks up an existing row solely by `path`: [1](#0-0) 
and if `existing !== undefined`, it returns `this.toRepository(existing)` directly — carrying forward the previously-stored `gitHubRepositoryID` (the trusted GitHub API-backed repository association) and `missing` flag, without checking that the git content currently on disk at that path actually corresponds to the same remote/repository. `matchExistingRepository()`, used elsewhere in the app to find "the" repository for a given path, performs the same path-only comparison with no content check: [2](#0-1) 

The identity of a tracked repository is effectively `path` (and the numeric `id` derived from it), not the actual git remote/content. Once a `gitHubRepositoryID` is bound to a path, replacing the on-disk repository at that same path — deleting it and re-cloning a different (attacker-controlled) repository into the identical folder, or restoring a "missing" repository pointer to a different repo the user places there — does not clear or re-validate that binding at the `repositories-store.ts` layer, analogous to `loanDeployed[nft][id]` never being cleared in `liquidate`.

### Impact Explanation
If the stale `gitHubRepositoryID` binding is trusted downstream without an independent remote-URL check, actions gated on "this Repository is associated with GitHub repo X" (branch-protection lookups, PR/CI status association, API calls scoped to that GitHub repository, or credential/token use inferred from the associated account) could be performed against attacker-controlled local content that is not actually the repository the association was created for. This is exactly the invariant the OtterSec report flags: a per-key state record surviving past the lifetime of the entity it was created for, and being silently rebound to a new, different entity at the same key.

### Likelihood Explanation
I was only able to confirm the path-only keying at the `repositories-store.ts`/`repository-matching.ts` layer; I could not, within the available iterations, trace whether `AppStore._addRepositories` / repository refresh logic performs an additional remote-URL revalidation (via `repositoryMatchesRemote`/`urlMatchesRemote` in `repository-matching.ts`) before trusting `gitHubRepositoryID` on a re-added/restored repository, or whether `updateRepositoryMissing` is followed by a re-match step elsewhere. Without confirming or ruling out that downstream check, I cannot assert this is currently exploitable end-to-end in the shipped app — only that the persisted-state layer itself does not clear or defend against this class of stale-binding reuse.

### Recommendation
In `RepositoriesStore.addRepository()`, when an existing row is found for a `path` that was previously marked `missing` (or generally on any add), re-derive/re-validate the `gitHubRepositoryID` from the current on-disk remote via `repositoryMatchesRemote`/`urlMatchesRemote` before returning the cached association, and clear `gitHubRepositoryID` (and any dependent cached state such as branch-protection info) if the current remote no longer matches the previously bound GitHub repository — mirroring the report's fix of explicitly deleting the stale keyed state rather than leaving it to be silently inherited by a new entity.

### Proof of Concept
1. Add repository at path `P` whose remote points to GitHub repo `org/private-repo`; Desktop persists `{ path: P, gitHubRepositoryID: <id-for-org/private-repo> }` via `addRepository` (`repositories-store.ts:237-264`).
2. Delete the folder at `P` (repository becomes `missing`, row is *not* deleted — only `removeRepository` deletes rows, and that path is not taken here) — see `updateRepositoryMissing` at `repositories-store.ts:280-300`, which only flips the `missing` flag, leaving `gitHubRepositoryID` intact.
3. Clone/copy an unrelated attacker-controlled repository into the same path `P`.
4. Re-open/re-add path `P` in Desktop: `addRepository(P, ...)` finds the existing row by `path` alone (`repositories-store.ts:248-252`) and returns it with the old `gitHubRepositoryID` still attached, binding the new, attacker-controlled content to the previously trusted GitHub repository association without any remote/content check.

  public async addRepository(
    path: string,
    gitDir: string | undefined,
    opts?: AddRepositoryOptions

    const repository = await this.db.transaction(
      'rw',
      this.db.repositories,
      this.db.gitHubRepositories,
      this.db.owners,
      async () => {
        const existing = await this.db.repositories.get({ path })

        if (existing !== undefined) {
          return await this.toRepository(existing)
        }

        const dbRepo: IDatabaseRepository = {
          path,
          gitHubRepositoryID: null,
          missing: opts?.missing ?? false,
          lastStashCheckDate: null,
          alias: null,
          gitDir,
        }
        const id = await this.db.repositories.add(dbRepo)
        return this.toRepository({ id, ...dbRepo })
      }

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}
