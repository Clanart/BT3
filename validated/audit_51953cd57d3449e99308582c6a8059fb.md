Based on my research, I found a concrete stale-state-driven integrity gap in GitHub Desktop's Copilot merge-conflict resolution flow that mirrors the report's core defect class: a security-relevant decision (whether it is safe to overwrite a file with unreviewed, model-generated content) is gated on a **cached snapshot** rather than a fresh read of ground truth, creating a window where the guard no longer reflects reality.

I want to flag upfront that I could not fully trace, within my tool budget, exactly how often `changesState.workingDirectory` is refreshed relative to the Copilot resolution round-trip (which the code itself instruments as taking up to 120+ seconds via `copilotConflictResolutionOver120sCount`), so the precise staleness window size is not fully confirmed from the index alone. The write-time reliance on a cached snapshot instead of a fresh disk read is, however, directly visible in the code.

### Title
Stale in-memory working-directory snapshot lets AI-generated conflict resolutions silently overwrite/clobber file content during Copilot merge conflict resolution - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` decides whether to write an AI-generated (`Copilot`) conflict resolution to disk by checking a **cached** `state.changesState.workingDirectory.files` snapshot rather than re-reading the file's live status from disk at write time, mirroring the report's "stale value used for a security-critical decision" pattern.

### Finding Description
`_applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts` writes Copilot's conflict resolutions to disk when the user clicks "Continue Merge": [1](#0-0) 

The guard that is supposed to prevent clobbering a file the user already resolved themselves reads `onDiskFile` from `state.changesState.workingDirectory.files` — an in-memory, previously-cached representation of the working directory — not a fresh `git status`/file read performed immediately before the `writeFile` call: [2](#0-1) 

The comment above this block even acknowledges the race exists ("If the user resolved this file externally... while the result dialog was open, git status will report it with no remaining conflict markers... Overwriting it with Copilot's stored content would silently clobber their work"), but the mitigation relies on `state.changesState.workingDirectory.files` being current — it is not re-fetched at the point of the check, only whatever the last background/foreground refresh populated. Separately, `resolution.resolvedContent` itself is derived from AI resassembly of the on-disk conflicted file content and per-hunk model output, which the model reads from a repository the user cloned/fetched (potentially attacker-influenced, since conflicted content commonly originates from a fork/PR the user is merging): [3](#0-2) 

The resolution round-trip through the Copilot SDK can run for a long time (the app tracks buckets up to 120+ seconds), which widens the window between when the diff/resolution was computed and when it is finally written to disk: [4](#0-3) 

Because the write path in `_applyCopilotConflictResolutions` trusts the stale snapshot instead of revalidating current on-disk content, the same class of bug as the report exists: a check performed against outdated state is used to authorize a consequential write action, and the actual state at write-time may no longer match what was validated.

### Impact Explanation
If the cached working-directory snapshot is stale relative to the actual file content at write time, `_applyCopilotConflictResolutions` can silently overwrite content the user manually resolved (or content changed by some other process/hook) with AI-generated `resolvedContent`, and then immediately `git add` it into the pending commit: [5](#0-4) 
This matches the "silent corruption of what the user commits or pushes" category from the Valid Impact list, since the file that ends up staged is not necessarily the file the user believes they approved.

### Likelihood Explanation
The likelihood is moderate but not fully confirmed: it depends on the exact cadence of `changesState.workingDirectory` refreshes relative to the (potentially minutes-long) Copilot resolution session, which I was not able to fully trace within available tool calls. The existence of an explicit developer comment acknowledging this exact race, without a fresh on-disk re-check immediately preceding the write, indicates the authors were aware of a related risk but the mitigation implemented (stale cache check) does not fully close the window under all timing conditions.

### Recommendation
Before writing `resolution.resolvedContent` to disk in `_applyCopilotConflictResolutions`, perform a fresh, synchronous read of the file's current on-disk conflict-marker state (or run a fresh `git status` for the affected paths) rather than relying on the cached `state.changesState.workingDirectory.files` snapshot, so the "already resolved externally" check reflects the file's true state at the moment of write, not at some earlier point during the (potentially long) AI resolution session.

### Proof of Concept
Not independently reproduced/verified in this session — this is based on static code review of `app/src/lib/stores/app-store.ts` and `app/src/lib/copilot-conflict-resolution.ts`. A dynamic PoC would involve: starting Copilot conflict resolution on a merge with multiple conflicted files, externally editing/resolving one of the conflicted files during the (multi-second-to-minute) resolution wait, and observing whether `_applyCopilotConflictResolutions` still overwrites it with the stale AI-generated content depending on whether a background status refresh had run in that window.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
