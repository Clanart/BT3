### Title
Unbounded length-prefixed allocation in `SchnorrAggregate::read` enables remote memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` deserializes an aggregate Schnorr signature by first reading a little-endian `u32` count and then pushing `C::read_G(reader)?` results into a `Vec` in a loop bounded only by that attacker-controlled count (`crypto/schnorr/src/aggregate.rs:77-88`). There is no upper bound on the declared length and no relationship enforced between the declared count and the actual bytes available. An unprivileged party supplying untrusted bytes to this `read` API can force the host to allocate and retain a vector of up to 2^32 group elements (~128 GiB of heap for 32-byte encodings, plus `Vec` growth overhead), mirroring the OpenVPN memory-leak/DoS class in the external report (untrusted input → unbounded resource consumption → denial of service).

### Finding Description
```rust
// crypto/schnorr/src/aggregate.rs
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```
The declared `len` is never validated against a maximum. Other Serai parsers explicitly defend against this exact pattern — e.g. `Call::read` in `networks/ethereum/src/machine.rs:51-60` comments "A valid DoS would be to claim a 4 GB data is present" and reads in 1 KB chunks, and `coordinator/src/p2p.rs:264` rejects requests over `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating. `SchnorrAggregate::read` has no such guard. Because `io::Read` accepts streaming input, an attacker can continuously feed compressed point bytes, growing `Rs` without bound until the process OOMs. Every intermediate `read_G` failure only shortens the loop — but a cooperative stream never fails until the attacker chooses.

### Impact Explanation
A node or service that deserializes `SchnorrAggregate` signatures from peer-supplied or network-supplied bytes can be driven to memory exhaustion and killed, achieving an unauthenticated remote denial of service — the same impact class (A:H) as the reference advisory. All cryptographic verification happens after `read` completes, so the resource cost is paid before any rejection is possible.

### Likelihood Explanation
The trigger requires only a `Read` source the attacker controls: 4 bytes declaring `len = u32::MAX` followed by a sustained stream of valid point encodings. No valid key material, threshold position, or protocol state is needed — the crash occurs during parsing, before `verify` is ever reached. Exploitation is trivial for any deployment exposing this deserialization on untrusted input.

### Recommendation
Bound the declared count before looping (e.g., reject `len` greater than a protocol-sane maximum, or pre-check `len * C::G::Repr::size()` against remaining input/limits), matching the chunked-read/bounded-length patterns already used in `networks/ethereum/src/machine.rs` and `coordinator/src/p2p.rs`.
