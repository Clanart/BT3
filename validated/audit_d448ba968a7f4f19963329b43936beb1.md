Confirmed: `OrderedWebRequest.onBeforeSendHeaders` runs registered listeners **sequentially in registration order**, threading the (possibly mutated) `details` from one listener into the next [1](#0-0) . In `main.ts`, `installSameOriginFilter` is registered before `installAuthenticatedImageFilter` [2](#0-1) , so on a same/legit leg the ordering is safe. However, this does not eliminate the underlying design flaw described below.

### Title
Authenticated image filter attaches account tokens to any GitHub-shaped asset URL regardless of repository/account binding - (File: app/src/main-process/authenticated-image-filter.ts)

### Summary
`installAuthenticatedImageFilter` decides whether to attach a bearer token to an outgoing request purely by matching the request's **origin** and a **path-shape regex**, never validating that the path actually belongs to a repository/account the signed-in token is scoped to render, and never coordinating with `same-origin-filter`'s per-request-id origin tracking. Content whose path merely matches `/^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/` or `/^\/user-attachments\/assets\/[^/]+\/?$/` gets the user's PAT/OAuth token attached automatically whenever the request's origin equals a cached account origin.

### Finding Description
`installAuthenticatedImageFilter` builds a `Map<origin, token>` from signed-in accounts and, on every `onBeforeSendHeaders` invocation, independently re-decides (based only on the *current* leg's origin+pathname) whether to inject `Authorization: token <token>`: [3](#0-2) 

The path predicates are broad, string-shape checks with no ownership/scope validation: [4](#0-3) 

Any renderer-loaded `<img>` whose `src` is attacker-influenced markdown/HTML content coming from a GitHub API object (issue/PR/comment body, notification content, commit message rendered as markdown) — which an unprivileged attacker fully controls by opening an issue/PR/comment against any repo, or by uploading a `user-attachments/assets/{guid}` attachment (globally addressable, not repo/owner-scoped) — will match these regexes as long as its origin equals `github.com`/`api.github.com`/the enterprise endpoint the app happens to have a cached account for. The filter reattaches the signed-in account's live token to that request with no check that: (1) the embedded content actually originates from the repository currently open in Desktop, (2) the token's account actually has any relationship to that path, or (3) this is the *original* request rather than a redirected leg. This is architecturally the same broken invariant as the reported Vault bug: a value (`Authorization` header) is (re-)computed from state read at the moment of the callback (`onBeforeSendHeaders` firing per-leg) without re-validating the precondition that made the original grant safe (that the URL corresponds to the account's own resource), letting attacker-supplied objects trigger the same trusted code path with different payload data.

The `same-origin-filter` guard mitigates the specific cross-*domain redirect* leg (it strips `authorization`/`cookie` when the origin changes across a redirect chain) [5](#0-4) , and because it is registered first, a later filter cannot un-strip removed headers on that same leg. But it only protects the *redirect* case; it does nothing about the primary, non-redirected request to `github.com`/GHES where `authenticated-image-filter` attaches the token based solely on path shape, independent of which repository/account the image actually belongs to.

### Impact Explanation
Successful exploitation attaches the victim's live GitHub PAT/OAuth token as an `Authorization` header to an attacker-influenced request URL pointed at a first-party GitHub host. While the header itself is not sent to a third party in the common case (both `github.com` and `user-attachments` assets are served by GitHub), the check performed is not scoped to the currently-open repository or to any legitimate need — meaning any repo/PR/issue an attacker can get the victim to view in Desktop can force silent, unscoped use of the victim's credentials against arbitrary path shapes on the account's endpoint(s), widening the blast radius beyond "render my own private avatar/asset" to "authenticate to any URL matching this shape, chosen by attacker-controlled content." Because token attachment is content-triggered and invisible to the user, it also increases exposure if GitHub's own asset-serving infrastructure ever redirects to an attacker-influenced or unexpected location (the very risk `same-origin-filter` was built to address for `fetch`), since `authenticated-image-filter` runs on every leg of every request independently and does not track the redirect chain root of the request it is authorizing.

### Likelihood Explanation
Moderate to low, but the trigger requires no privileges beyond opening a public repository, issue, PR, or comment that Desktop renders (e.g., viewing a PR body, notification, or commit referencing an image). This satisfies the "attacker controls a GitHub API object" criterion of the ruleset. Actual token leakage to the attacker (as opposed to unscoped over-authorization to GitHub-owned infrastructure) depends on additional preconditions (a compromised or unusual redirect target) that are not proven purely from this code path, which is a limitation of this analysis based on static code alone — dynamic verification of GitHub's redirect behavior for `/user-attachments/assets/*` was not possible with the tools available.

### Recommendation
Scope token attachment to the specific repository/account context that legitimately needs it (e.g., pass the currently-relevant owner/repo or GitHub-Repository identifier down to the filter and compare it against the path components) rather than matching on path shape alone; also have `authenticated-image-filter` consult the same per-request-id origin tracking used by `same-origin-filter` so that a token is only attached to the *original* leg of a request, never re-derived independently on subsequent legs.

### Proof of Concept
1. Sign in to Desktop with a GitHub.com account (a token is cached by `installAuthenticatedImageFilter`'s `updateAccounts` callback).
2. As an unprivileged attacker, open any issue/PR/comment on any repository and embed an image referencing a `user-attachments/assets/{guid}` URL (obtainable by uploading any file via the GitHub comment UI) or craft a link matching `/{owner}/{repo}/assets/{id}/{guid}`.
3. Get the victim to view that PR/issue/notification inside Desktop, causing the renderer to issue a `GET` for the image `src`.
4. Observe (via `onBeforeSendHeaders` instrumentation) that `Authorization: token <victim token>` is attached to the request purely because origin+path matched, with no verification that the asset belongs to the repository open in Desktop or to the signed-in account's own content [6](#0-5) .

export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
