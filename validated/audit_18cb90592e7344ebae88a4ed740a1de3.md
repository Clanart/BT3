## Analysis

Reducing the Super DCA report to its core broken invariant: **a reward pool that accrues attribution across multiple contributors is paid out entirely to whichever single identity is sampled at the moment the distribution is triggered, instead of to the actual contributors.** In Super DCA that "sampled identity" was the current in-range tick holder; in Hyperbridge the structurally identical pattern shows up in `pallet-consensus-incentives`'s `FeeHandler::on_executed`. [1](#0-0) 

`execute()` in `pallet-ismp` accepts an arbitrary `Vec<Message>` from an unsigned, permissionless `handle_unsigned` call and feeds the *whole batch's* resulting events into `FeeHandler::on_executed` in one shot: [2](#0-1) [3](#0-2) 

Inside `on_executed`, the relayer credited for the reward is recovered **only from `messages.get(0)`**, then that single recovered account is paid for the block-span reward of *every* distinct `state_machine_id` whose `StateMachineUpdated` event appears anywhere in the batch (collapsed via `highest_per_state_machine`): [4](#0-3) 

### Title
Batch-reward misattribution in `pallet-consensus-incentives::on_executed` lets a single batch submitter capture rewards for consensus updates delivered by other relayers' messages - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`on_executed` recovers exactly one relayer identity — the signer of `messages[0]` — and pays that single account the full block-span reward for **every** state machine advanced anywhere in the batch, even when the batch contains multiple `Message::Consensus` entries with distinct embedded signers for distinct chains.

### Finding Description
`handle_unsigned` is a permissionless, unsigned extrinsic that lets anyone submit an arbitrary `Vec<Message>` [3](#0-2) . All resulting `Message`/event data from the entire batch is passed to `T::FeeHandler::on_executed(messages_with_weights, events)` in a single call [2](#0-1) .

`pallet-consensus-incentives::on_executed` then:
1. Looks at `messages.get(0)` only, and — if it is a `Message::Consensus` — recovers the sr25519 pubkey from its embedded `signer` field.
2. Collapses *all* `StateMachineUpdated` events in the batch (which may originate from `messages[1]`, `messages[2]`, … each carrying its own independently-signed consensus proof for a different chain) into `highest_per_state_machine`.
3. Pays the *single* recovered `relayer_account` from step 1 the full `calculate_reward` payout for **every** entry in that map. [5](#0-4) 

The batch's own `Message::Consensus` entries each embed an independent `signer` (a signature made by the relayer over the message content) [6](#0-5) , so the protocol already has the *correct* per-message attribution data on hand — but `on_executed` never uses it for any message beyond index 0. Any unprivileged account that assembles a `handle_unsigned` call combining its own (cheap/trivial) self-signed consensus message at index 0 with any other still-unprocessed, validly-signed consensus message(s) for other chains — which are just data plus a signature, not secrets, and are visible once broadcast/observed prior to inclusion — will, on success, be credited with the treasury payout for *all* of the batched chains' block-span advances, while the account that actually authored/signed the other message(s) receives nothing despite its `StateMachineUpdated` genuinely stemming from its own valid proof submission.

### Impact Explanation
This is a direct "unauthorized... reward" / "unfair distribution of rewards" outcome matching the bounty's logic-attack and fund-loss categories: the treasury pays the full multi-chain reward to one account instead of splitting it among the actual message signers, and the legitimate signer of the non-first message is silently denied a reward it earned by successfully advancing consensus for its chain. Because rewards are transferred from `T::TreasuryAccount` [7](#0-6) , this is a genuine treasury fund-flow misdirection to the wrong beneficiary, not merely a griefing/DoS effect.

### Likelihood Explanation
The attack requires no elevated permission — `handle_unsigned` is unsigned and open to anyone, and batching unrelated `Message::Consensus` entries from different signers into one call is not prevented anywhere in `execute()` or `on_executed`. The only friction is obtaining a second party's still-unconsumed signed consensus message before it lands (naturally occurs whenever an aggregator legitimately batches multiple relayers' pending proofs to save on extrinsic overhead, or whenever a batch happens to interleave messages this way), so this can occur in ordinary batching/aggregation usage, not solely as an adversarial race.

### Recommendation
`on_executed` should attribute reward per `Message::Consensus` entry to its own embedded signer, matching each entry's resulting `StateMachineUpdated` event(s) to that entry's signer instead of collapsing the whole batch under `messages[0]`'s identity.

### Proof of Concept
1. Relayer B constructs and signs a valid `Message::Consensus` proof advancing `StateMachineId::X` (a large block span, big reward) and broadcasts/submits it via `handle_unsigned`.
2. Before B's transaction is included, attacker A observes the fully-formed message (data + B's signature) and its own separately-authored trivial `Message::Consensus` for an unrelated chain `Y` (small/zero reward), then submits `handle_unsigned([A's message for Y, B's message for X])` themselves.
3. `execute()` processes both messages, producing `StateMachineUpdated` for both `Y` and `X`; `on_executed` recovers only A's signer from index 0 and pays A the combined reward for both `X` and `Y`'s block-span advance [8](#0-7) .
4. B's original submission, if it lands afterward, either fails as already-processed or yields zero new reward since the watermark for `X` has already advanced — B receives nothing despite having authored the proof that produced the bulk of the payout.

/// Implementation of the FeeHandler trait for the RelayerIncentives pallet
impl<T: Config> FeeHandler for Pallet<T>
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}

		// Return with actual weight information
		// We use Pays::No to indicate that someone (the message sender) doesn't pay for this
		// operation, though we're using this mechanism to reward relayers rather than charge fees
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

impl<T: Config> Pallet<T> {
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}
