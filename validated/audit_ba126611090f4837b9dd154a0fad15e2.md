### Title
Cloning an untrusted repository automatically clones all attacker-defined submodule remotes with no consent, protocol restriction, or per-host proxy/credential scoping - ([File: app/src/lib/git/clone.ts])

### Summary
When a user clones a repository through Desktop's Clone dialog, `clone()` in `app/src/lib/git/clone.ts` unconditionally invokes `git clone --recursive`. The `--recursive` flag causes Git to also fetch and initialize every submodule declared in the repository's `.gitmodules` file — content that is 100% attacker-controlled once the user points Desktop at a malicious repo URL. There is no user prompt, no review step, and no restriction on submodule URL protocols/hosts before this happens, analogous to the Timeswap report where an expensive, consequential action (deploying a new contract) is silently triggered as a side effect of an ordinary user action (minting) instead of requiring explicit opt-in.

### Finding Description
`clone()` builds its argument list with `--recursive` baked in unconditionally: [1](#0-0) 

Compare this to `updateSubmodulesAfterOperation()` in `app/src/lib/git/submodule.ts`, which explicitly gates risky submodule protocols behind an `allowFileProtocol` flag before running `submodule update --init --recursive`: [2](#0-1) 

No equivalent gating exists in `clone.ts` for the initial recursive clone — the `env` passed to the underlying `git()` call only resolves a proxy and authentication context for the *top-level* clone URL: [3](#0-2) [4](#0-3) 

`envForRemoteOperation`'s own doc comment acknowledges that a clone "could contain a submodule pointing to another host entirely," yet the function only resolves a proxy/credential context for the single primary URL, not for whatever additional hosts `.gitmodules` names: [5](#0-4) 

Because `git clone --recursive` recurses into `.gitmodules` before the user ever sees the repository contents, an attacker who gets a victim to clone their repo (a normal, unprivileged Desktop action) can define submodules pointing at arbitrary URLs/protocols/hosts of their choosing, and Desktop will silently connect to and fetch from every one of them as part of what the user believes is a single, contained clone operation on the destination path they chose. This mirrors the "deploy happens as an unconsented side effect of mint" pattern in the referenced report: an expensive/risky network operation (fetching from N attacker-chosen remotes) is triggered automatically by a routine user action, with no way to opt out or review beforehand.

### Impact Explanation
- The clone destination path itself is protected against traversal via `isClonePathSensitive()`, but this only protects the top-level checkout location; it does nothing about the network operations `--recursive` triggers. [6](#0-5) 
- Every submodule URL is fetched with no user visibility, unlike the explicit unsafe-repository warning shown for locally-owned-by-another-user repos: [7](#0-6) 
- Possible consequences: resource-exhaustion/"gas"-style cost via forcing dozens/hundreds of large recursive submodule clones the user never agreed to, outbound connections to arbitrary/internal hosts (SSRF-like behavior) triggered purely by cloning a public repo, and — depending on which Git version ships with Desktop and whether `protocol.file.allow`/`GIT_ALLOW_PROTOCOL` defaults are in effect — potential abuse of `file://`/`ext::` submodule URLs to read files or execute helper programs during the recursive fetch.

### Likelihood Explanation
Any user cloning any repository via the standard Clone dialog is affected; the attacker only needs to control the target repository's `.gitmodules`, which requires no elevated access, no local/physical presence, and no unusual user steps — cloning a repo is the primary intended workflow of the app.

### Recommendation
Do not pass `--recursive` to the initial `git clone` call by default. Instead, clone non-recursively, then inspect `.gitmodules` and prompt the user (or apply the same protocol/host allow-listing already implemented in `updateSubmodulesAfterOperation`) before running `submodule update --init --recursive`, resolving a proxy/credential/auth context per submodule URL rather than only for the top-level clone URL.

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with dozens of large or slow submodule remotes (or remotes pointing at internal/arbitrary hosts).
2. Victim clones this repository through Desktop's Clone dialog, supplying only the top-level URL.
3. `clone()` runs `git ... clone --recursive -- <url> <path>` with environment resolved only for `<url>`: [8](#0-7) 
4. Git recurses into `.gitmodules` and fetches every attacker-declared submodule immediately and automatically, with no Desktop-level confirmation, before the user has reviewed the repository's contents — unlike the explicit per-operation protocol gating used elsewhere in the codebase (`allowFileProtocol` in `app/src/lib/git/submodule.ts`).

I could not verify from the available index whether the bundled `dugite`/Git binary sets `protocol.file.allow=user` by default (a newer Git mitigation) or what Git version ships with this build, so I cannot confirm whether `file://`/`ext::` submodule abuse is currently blocked upstream — this would need to be checked in a full Devin session against the actual bundled Git binary version.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function envForRemoteOperation(remoteUrl: string) {
  return {
    ...envForAuthentication(),
    ...(await envForProxy(remoteUrl)),
  }
