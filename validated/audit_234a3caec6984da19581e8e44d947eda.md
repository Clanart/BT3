### Title
Aggregator gRPC server skips both TLS client authentication and interceptor checks when `client_verification` is disabled - (`core/src/servers.rs`)

### Summary
In `create_grpc_server`, when `config.client_verification` is `false`, `ServerTlsConfig` is built with only `.identity(server_identity)` and no `.client_ca_root(...)`, and the accompanying interceptor is set to `Interceptors::Noop`, which unconditionally returns `Ok(req)` without consulting `req.peer_certs()` at all. This means the TLS layer performs a plain one-way handshake (server authenticates to client only) and the application layer performs no identity check whatsoever, so any TLS client that can reach the aggregator's advertised port can invoke any `ClementineAggregator` RPC.

### Finding Description
The binding this configuration is supposed to guarantee is: `peer TLS client certificate ∈ {aggregator_cert, our_cert}` ⇒ `RPC call permitted`. When `config.client_verification == false`, this binding degenerates to `true ⇒ RPC call permitted` for every peer, since:

- `tls_config` is constructed as `ServerTlsConfig::new().identity(server_identity)` with no `.client_ca_root(...)` [1](#0-0)  — rustls/tonic will not request or validate any client certificate during the handshake in this mode, so an attacker only needs to validate the server's advertised cert and complete a normal one-way TLS handshake.
- The interceptor selected in this branch is `Noop`, which does not call `req.peer_certs()` at all and unconditionally returns `Ok(req)` [2](#0-1) [3](#0-2) .
- The only place `peer_certs()` is consulted is inside `only_aggregator_and_self`, which is exclusively used by the `OnlyAggregatorAndSelf` variant, itself only constructed when `config.client_verification` is `true` [4](#0-3) [5](#0-4) .

`config.client_verification` is read from the `CLIENT_VERIFICATION` environment variable and defaults to `false` unless explicitly set to `"true"` or `"1"` [6](#0-5) . `create_aggregator_grpc_server` only emits a warning log when `client_verification` is enabled; it takes no additional action to enforce authentication when it is disabled, and passes straight through to `create_grpc_server` with the same `config` [7](#0-6) . There is no other authentication or authorization layer in front of the aggregator's gRPC handlers (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `InternalSendTx`, `SendMoveToVaultTx`, etc.) — they rely entirely on the interceptor/TLS combination examined here for `CALLER_AUTHORITY`.

### Impact Explanation
With `client_verification` disabled, any internet-reachable, unprivileged party who can complete an ordinary one-way TLS handshake against the aggregator's port (i.e., anyone, since no client certificate is required or checked) can call every aggregator RPC as if they were the security council/operator/verifier orchestrator. This is a complete breach of `CALLER_AUTHORITY` for the aggregator service, and depending on which state-mutating RPCs are reachable this can let an attacker drive deposit setup, withdrawal orchestration, or transaction broadcasting flows that are meant to be restricted to the aggregator's authorized caller — matching the "unauthenticated state-changing or broadcasting call" category. The blast radius is global to the aggregator instance (every deposit/operator interaction routed through it), and the condition is repeatable on every connection while the flag remains disabled.

### Likelihood Explanation
The vulnerability is entirely gated by a deployment/configuration choice: `CLIENT_VERIFICATION` must be unset or not `"true"/"1"`. The default value of `client_verification` is `false` [6](#0-5) , and there is no compile-time or runtime enforcement forcing it to `true` for aggregator deployments — `create_aggregator_grpc_server` only logs a warning when it's *enabled*, implying it is expected/common for it to be disabled in some environments [8](#0-7) . I could not fully confirm from the indexed files whether the reference/production deployment configs (e.g., `scripts/docker/configs/testnet4/bridge_config.toml`) set this to `true` or `false`, since those are `.toml` files that are out of scope for citation/inspection depth here; this determines whether the issue is exploitable "out of the box" in the shipped configuration or only when an operator misconfigures/disables client verification.

### Recommendation
Do not allow the aggregator (or any service) to fall back to a TLS configuration with no `client_ca_root` and a `Noop` interceptor. Either make `client_verification` mandatory (remove the `false` branch and always require `.client_ca_root(...)` plus `OnlyAggregatorAndSelf`), or fail closed by refusing to start the aggregator's TCP gRPC server unless `client_verification` is `true`.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

    let Some(peer_certs) = req.peer_certs() else {

        } else {
            // If we're not in test mode, we need to check peer certificates

                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };
