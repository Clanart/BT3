## Title
Front-runnable referral code registration allows theft of referral rewards - (File: `rewards/ReferralStorage.sol`)

### Summary
`ReferralStorage.registerCode()` is a fully permissionless, unprivileged-wallet function that lets `msg.sender` claim any unclaimed `bytes32 _code` as their own, first-come-first-served, with no commit-reveal or signature check tying the code to the caller's intent beforehand.

### Finding Description
`registerCode` simply checks that the code slot is empty and assigns it to whoever calls the transaction: [1](#0-0) 

This is the exact bug class described in the external report: a "claim an identifier" transaction is publicly visible in the mempool before confirmation, so any observer can front-run it with a higher gas price and claim the same `_code` for themselves before the intended owner's transaction lands. Once claimed, the attacker becomes the permanent `codeOwners[_code]` (mirroring how the frontrunner in the report becomes "owner" of the collection).

The consequence is worse than a simple griefing/DoS, because `codeOwners[_code]` is not just a cosmetic identifier — it is the destination of real referral yield. Any user who later calls `useCode(_code)` (e.g. a marketing partner's referees who were told "use code X") will have their referral relationship bound to the attacker instead of the intended code owner: [2](#0-1) 

From that point on, every time `MasterMagpie` calls `trigger()` for that referee, the referrer-side reward share is credited to the attacker's `userInfos[_referer].rewardAmount`, which the attacker can withdraw via `claimReward()`: [3](#0-2) [4](#0-3) 

The only remediation path is the admin-only `forceSetCodeOwner`, which requires the protocol owner to notice the squat and manually intervene — it does not prevent the theft of rewards accrued in the interim, and depends on a privileged actor reacting in time: [5](#0-4) 

### Impact Explanation
An attacker monitoring the mempool can front-run any `registerCode` transaction for a code that is expected to be advertised/shared publicly (e.g. a memorable marketing code), permanently taking over that code identity via an ordinary, unprivileged transaction. Referees who subsequently call `useCode` with that string — believing it routes rewards to the legitimate referrer — instead divert their referrer-side share of referral yield to the attacker, who can withdraw it via `MGP.safeTransfer` in `claimReward()`. This is a direct theft of referral yield belonging to the intended referrer, reachable purely through normal wallet transactions with no admin/oracle/governance involvement.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to detect an incoming `registerCode(_code)` transaction in the mempool (or to pre-emptively squat commonly-used/branded codes) and win a gas-price race. Because `_code` values are typically short human-readable identifiers meant to be shared publicly, guessing/squatting valuable codes ahead of time is also feasible without even needing to observe a specific pending transaction.

### Recommendation
Adopt one of the mitigations suggested in the referenced report for identifier-claim front-running: require a commit-reveal scheme (commit `keccak256(code, msg.sender, salt)` first, reveal after a delay) or require the caller to submit a signature over `(code, msg.sender)` so a front-runner cannot reuse the intercepted call data to bind the code to their own address.

### Proof of Concept
1. Alice (a legitimate referral partner) submits `registerCode(code = "ALICE100")`.
2. Mallory observes this pending transaction in the mempool and submits her own `registerCode(code = "ALICE100")` with higher gas, which mines first; `codeOwners["ALICE100"] = mallory`.
3. Alice's original transaction reverts (`CodeOccupied`).
4. Users who trust the "ALICE100" code and call `useCode("ALICE100")` now have `myReferer[user] = mallory`.
5. When `MasterMagpie` later calls `ReferralStorage.trigger(referee, amount)` for these users, the referrer share accrues to `userInfos[mallory].rewardAmount` instead of Alice.
6. Mallory calls `claimReward()` and withdraws MGP tokens that were economically intended for Alice.

        if (_code == bytes32(0)) revert InvalidCode();

    function trigger(address _referee, uint256 _amount) external _onlyMasterMagpie {
        UserInfo storage refereeInfo = userInfos[_referee];
        address _referer = myReferer[_referee];

        if (_referer == address(0))
            return;

        UserInfo storage refererInfo = userInfos[_referer];
        uint256 tierId = userInfos[_referer].tier;
        uint256 basic = tiers[tierId].rewardPercentage;
        uint256 boostesd = _calBoosted(_referer);

        uint256 refererPercentage = (basic + boostesd) * (DENOMINATOR - sharePercent)  / DENOMINATOR;
        uint256 refereePercentage = (basic + boostesd) *  sharePercent / DENOMINATOR;
        uint256 refererAmount = _amount * refererPercentage / DENOMINATOR;
        uint256 refereeAmount = _amount * refereePercentage / DENOMINATOR;

        refererInfo.rewardAmount += refererAmount;
        refereeInfo.rewardAmount += refereeAmount;

        emit RefererRewardHarvested(_referer, refererAmount);
        emit RefereeRewardHarvested(_referee, refereeAmount);
    }
