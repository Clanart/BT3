### Title
Attacker-controlled count in `ThresholdKeys::read` enables amplified memory exhaustion — unrestricted writes to unbounded storage (File: crypto/dkg/src/lib.rs)

### Summary
The analog of the reported bug (a public, unrestricted function that lets anyone push unbounded data into storage) in Serai's in-scope code is `ThresholdKeys::<C>::read`. It deserializes an attacker-controlled `u16` participant count `n` and immediately calls `Vec::with_capacity(usize::from(n))` and then iterates `1 ..= n` performing `verification_shares.insert(...)`, with no bound check against the actual available bytes or any sane threshold limit before allocating. The function is public, takes arbitrary bytes from an `io::Read`, and is explicitly on the list of untrusted deserialization entry points reachable by unprivileged parties.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as three `u16`s directly from the input stream [1](#0-0) . `n` is then used unchecked to pre-allocate and populate the `Interpolation::Constant` vector and the `verification_shares` `HashMap` [2](#0-1) . With `n = 0xFFFF`, a handful of input bytes forces an allocation of ~65,535 field elements (~2 MB) plus `HashMap` growth before the first `read_F`/`read_G` even touches the stream. Only afterwards does `ThresholdParams::new(t, n, i)` validate the relationship between the values [3](#0-2) . Like the original `add()` finding, the write/insert path is public and gated by nothing — the byte count is trusted before the data exists. Compare the mitigated pattern elsewhere, e.g. the chunked read with the explicit comment "A valid DoS would be to claim a 4 GB data is present" [4](#0-3)  — `ThresholdKeys::read` has no such mitigation.

### Impact Explanation
An unprivileged party feeding crafted bytes to `ThresholdKeys::read` obtains roughly a 10⁵× memory amplification: ~10 bytes of input yield ~2 MB of committed heap plus hashmap insertion work. Replayed across many deserialization calls (key-exchange, recovery flows, any path that round-trips `ThresholdKeys::serialize`/`read`), the victim process is driven to OOM or memory-pressure degradation — the same "spam the storage until unusable" outcome as the original report, realized in memory rather than on-chain storage.

### Likelihood Explanation
`ThresholdKeys::read` is a public API documented for reading keys "from a type satisfying `std::io::Read`" [5](#0-4) , and the scan rules explicitly designate it as a sink for untrusted bytes. Any integration that deserializes keys from network messages, files, or coordinator-provided blobs reaches it. The exploit is a constant-cost one-liner: three `u16`s where `n = 0xFFFF` while `t`/`i` can even be left to fail validation later — the allocation happens regardless.

### Recommendation
Validate `n` (and `t`, `i`) against a bound — e.g. construct `ThresholdParams::new(t, n, i)` *before* allocating and reject `n` exceeding a protocol maximum — before calling `Vec::with_capacity` or looping `1 ..= n`. Alternatively, grow the vectors incrementally (`Vec::new()` + `push`) so memory usage tracks bytes actually present, mirroring the chunked-read defense in `Call::read` [6](#0-5) .

### Proof of Concept
```rust
// Bytes: t=1, n=0xFFFF, i=1, interpolation=Constant(0), then EOF.
// read() allocates Vec::with_capacity(65535) and a HashMap loop
// before ever failing on missing data.
let mut bytes = vec![];
bytes.extend(u32::try_from(Secp256k1::ID.len()).unwrap().to_le_bytes());
bytes.extend(Secp256k1::ID);        // curve id check passes
bytes.extend(1u16.to_le_bytes());   // t
bytes.extend(0xFFFFu16.to_le_bytes()); // n = 65535
bytes.extend(1u16.to_le_bytes());   // i
bytes.push(0);                      // Interpolation::Constant
// ~2MB committed heap from <50 bytes of input
let _ = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice());
```
The `Vec::with_capacity(usize::from(n))` at `crypto/dkg/src/lib.rs:608` commits ~2 MB before a single scalar is read, and the `1 ..= n` loop at line 621 scales `HashMap` insertion work identically — only then does `ThresholdParams::new` at line 626 get a chance to reject the parameters.
