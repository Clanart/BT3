### Title
Payout `OP_RETURN` operator attribution is not covered by the withdrawer's signature, allowing anyone to rebind a payout to an arbitrary operator xonly pubkey - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` only sets the user's key-spend witness on input 0 while requiring `SinglePlusAnyoneCanPay` as the sighash type, which under BIP-341 commits solely to `output[0]` (the user's payout) and never to `output[2]` (`op_return_txout`, which encodes `operator_xonly_pk`). Anyone who obtains the withdrawer's signature can therefore build an alternative, fully valid transaction that pays the same output[0] but embeds an arbitrary xonly pubkey in the `OP_RETURN`, breaking the attribution binding relied upon by `Verifier::is_kickoff_malicious`.

### Finding Description
The claimed binding is:
`op_return_txout.operator_xonly_pk == xonly_pk of the party whose BTC funded output_txout.value`

`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds the payout tx with input[0] (the withdrawer's dust UTXO, key-spend), `output[0]` (user payout), `output[1]` (anchor) and `output[2]` (`op_return_txout(operator_xonly_pk.serialize())`), then sets only `user_sig` as witness for input 0: [1](#0-0) 

The sighash type is enforced to `TapSighashType::SinglePlusAnyoneCanPay` both server-side and in the aggregator parser: [2](#0-1) 

Per BIP-341's signing algorithm (mirrored in this repo's own re-implementation), `SIGHASH_SINGLE` only commits `sha_single_output = sha256(serialize(output[input_index]))`, i.e. output 0 only - it never enumerates or hashes the remaining outputs, and `ANYONECANPAY` further removes any commitment to the full outpoint/sequence set: [3](#0-2) 

Consequently `user_sig` authorizes *any* transaction that spends the same `input_utxo` and pays the fixed `output[0]`; the number, order, and content of subsequent outputs (anchor, `OP_RETURN`) are unconstrained. An attacker who has seen the withdrawer's `(in_outpoint, in_signature, output_script_pubkey, output_amount)` - obtainable either as the withdrawer, by calling the aggregator's public `withdraw`/`OptimisticPayoutSign` gRPC endpoints, or simply by observing the real payout transaction in the mempool before it confirms - can construct a variant transaction with a self-chosen `operator_xonly_pk` in `op_return_txout`, add their own funding input(s) to cover `output_txout.value` (since the dust `input_utxo` alone cannot cover the withdrawal amount, per `generate_withdrawal_utxo`), and broadcast it, racing the real operator's transaction.

This is picked up unmodified by chain sync: `update_finalized_payouts` parses whatever `OP_RETURN` is present in the *confirmed* transaction and stores it as `payout_payer_operator_xonly_pk`: [4](#0-3) 

That value is then used as ground truth by `is_kickoff_malicious`, which requires an exact match between the stored `operator_xonly_pk` and the actual kickoff sender's `kickoff_data.operator_xonly_pk`, else it declares the (genuine) kickoff malicious and triggers a challenge: [5](#0-4) 

Existing guards do not close this gap: `Operator::withdraw`'s `SECP.verify_schnorr` check only validates that the signature is valid for the sighash of *the transaction the operator itself constructed* - it does not, and cannot, prevent a third party from constructing a different transaction that is equally valid under the same signature because `SIGHASH_SINGLE|ANYONECANPAY` never commits to `output[2]`. [6](#0-5) 

### Impact Explanation
- If attacker embeds an existing operator's public xonly pubkey (public, obtainable via `fetch_operator_keys`) while funding the withdrawal themselves, and that operator later relies on `get_first_unhandled_payout_by_operator_xonly_pk` to discover it owes a kickoff, the operator can be reimbursed (spending the deposit's `MoveToVault` UTXO) for a payout it never funded - Critical: "an operator reimbursed for a payout it never funded." [7](#0-6) 
- If an attacker front-runs the real, funding operator's broadcast with a variant carrying a bogus/mismatched `operator_xonly_pk` (or no valid one), the real operator's later kickoff for the same deposit will fail the `operator_xonly_pk != kickoff_data.operator_xonly_pk` check and be flagged malicious/challenged even though it legitimately funded the withdrawal - Critical: "an honest operator permanently unable to be reimbursed" (and potential collateral loss if the resulting challenge cannot be defended). [8](#0-7) 
- This is repeatable per deposit/withdrawal/operator: any withdrawal signature can be intercepted before its intended payout confirms, and the attack cost is only the fee/withdrawal-amount funding needed to win the race against the intended broadcaster.

### Likelihood Explanation
The attacker needs no special role: capturing a withdrawer's `SinglePlusAnyoneCanPay` signature (via the withdraw path or mempool observation) and funding/broadcasting a competing transaction with real fee-paying capital is all that's required; this matches the defined unprivileged attacker capabilities (broadcast transactions, choose UTXO/signature/OP_RETURN bytes, hit the aggregator's public `withdraw` RPC). The only cost is fronting the withdrawal amount plus fees and winning a standard fee-based mempool race, both of which are attacker-controllable and require no key compromise, no privileged role, and no majority hashrate.

### Recommendation
Bind the operator attribution cryptographically to the signature: either (a) require the withdrawer's signature to use `TapSighashType::AllPlusAnyoneCanPay` (or `Default`) so that all outputs, including `op_return_txout`, are committed, or (b) have verifiers/operators independently authenticate `operator_xonly_pk` for a payout (e.g., via a separate signed commitment from the depositor/withdrawer or a musig2 co-signature that binds all outputs) rather than trusting whatever `OP_RETURN` happens to be present in the first confirmed spend of the withdrawal UTXO.

    /// Checks if the kickoff is malicious and sends the appropriate txs if it is.
    /// Returns true if the kickoff is malicious.
    /// Sends a challenge tx if the kickoff is first malicious one in the current round, and the network is not mainnet or testnet4.
    pub async fn handle_kickoff<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        kickoff_witness: Witness,
        mut deposit_data: DepositData,
        kickoff_data: KickoffData,
        challenged_before: bool,
    ) -> Result<bool, BridgeError> {
        let is_malicious = self
            .is_kickoff_malicious(kickoff_witness, &mut deposit_data, kickoff_data, dbtx)
            .await?;

        let deposit_outpoint = deposit_data.get_deposit_outpoint();

        let (_signed_txs, tx_metadata, challenge_tx) = self
            .get_signed_txs_for_kickoff(dbtx, kickoff_data, deposit_data)
            .await?;

        if is_malicious {
            tracing::warn!(
                "Malicious {} detected. {} Challenge tx: {} for deposit {}",
                kickoff_data,
                match challenged_before {
                    false => "This is the first malicious kickoff in the current round.",
                    true => "This is not the first malicious kickoff in the current round.",
                },
                bitcoin::consensus::encode::serialize_hex(&challenge_tx),
                deposit_outpoint
            );
            // do not automatically send challenge txs on mainnet or testnet4
            if !challenged_before
                && !matches!(
                    self.config.protocol_paramset().network,
                    bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
                )
            {
                #[cfg(feature = "automation")]
                self.tx_sender
                    .add_tx_to_queue(
                        dbtx,
                        TransactionType::Challenge,
                        &challenge_tx,
                        &[],
                        Some(tx_metadata),
                        self.config.protocol_paramset(),
                        None,
                    )
                    .await?;
            }

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
