## Analysis

The Thrift bug class is uncontrolled recursion during deserialization of untrusted, self-referential input, leading to stack exhaustion. The closest reachable analog in kaia is RLP decoding of a nested `AccountKeyRoleBased` structure inside an `AccountUpdate` transaction.

### Title
Uncontrolled recursion in `AccountKeyRoleBased.DecodeRLP` allows attacker-controlled stack exhaustion via a crafted `AccountUpdate` transaction — (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key of a role-based account key by dispatching to `AccountKeySerializer.DecodeRLP`, which for a `RoleBased` sub-key type recurses back into `AccountKeyRoleBased.DecodeRLP`. There is no recursion-depth check anywhere in the decode path.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a `keyType` byte and dispatches to `NewAccountKey`/`s.Decode(serializer.key)`: [1](#0-0) 

When the decoded key type is `AccountKeyTypeRoleBased`, `AccountKeyRoleBased.DecodeRLP` decodes an inner `[][]byte`, and for every element calls `rlp.DecodeBytes(b, &serializer)` where `serializer` is a fresh `AccountKeySerializer` — re-entering the same dispatch above, with no depth tracking: [2](#0-1) 

Because each nesting level only costs a `keyType` byte plus small RLP list overhead, an attacker can construct a very deeply nested `RoleBased(RoleBased(RoleBased(...)))` byte blob and place it as the `AccountKey` payload of a `TxTypeAccountUpdate` transaction. `Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP` → the specific `TxInternalDataAccountUpdate`'s decode path will eventually reach `AccountKeySerializer.DecodeRLP`, triggering the unbounded recursive descent **before** any semantic validation occurs.

The only defense against nested `RoleBased` keys that exists in the codebase is `AccountKeyRoleBased.CheckInstallable`, which rejects composite (nested) key types with `kerrors.ErrNestedCompositeType`: [3](#0-2) 

However, this check runs only *after* the transaction has already been fully RLP-decoded (it's invoked during tx-pool admission / state-transition validation, e.g. as exercised in `TestAccountUpdateRoleBasedKeyNested`): [4](#0-3) 

By the time `CheckInstallable` runs and rejects the nesting, the recursive `DecodeRLP` call chain has already executed fully — the validation check cannot prevent the recursion from happening, it can only reject the *result* after decoding completes (or crashes).

### Impact Explanation
Any node (validator, full node, or RPC node) that decodes a raw transaction — via `eth_sendRawTransaction`, p2p transaction propagation, or block processing — with a maliciously deep `AccountKeyRoleBased` nesting will execute unbounded Go-level recursion in `AccountKeyRoleBased.DecodeRLP`/`AccountKeySerializer.DecodeRLP`. Depending on achievable nesting depth within transaction size limits, this can cause significant CPU/memory consumption or a stack overflow/panic, crashing the node process. If only some nodes in the network crash while others successfully process/reject the transaction (e.g., due to differing available stack/goroutine limits or resource pressure), this can lead to inconsistent processing behavior across the network — a denial-of-service risk reachable by any transaction sender.

### Likelihood Explanation
The attack requires only a single unprivileged, syntactically valid RLP encoding of a `TxTypeAccountUpdate` transaction with a deeply nested `RoleBased` account-key payload; no special privileges, prior on-chain state, or peer/validator position are needed. The transaction does not need to be economically valid or even pass signature checks for the vulnerable decode step to execute, since RLP decoding happens before signature/semantic validation in the standard tx ingestion pipeline (`UnmarshalBinary` → `DecodeRLP` → validation). This makes the path trivially reachable from a public RPC endpoint.

### Recommendation
Add an explicit recursion/nesting-depth counter (or a maximum encoded-size threshold per nesting level, or an explicit "no composite type inside RoleBased" check performed **during** decode rather than only after) to `AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP`, rejecting any account key whose type is `AccountKeyTypeRoleBased` when already inside a `RoleBased` decode context, before recursing further.

### Proof of Concept
1. Construct a deeply nested account key value at the Go level:
```go
key := accountkey.NewAccountKeyPublicWithValue(pub)
for i := 0; i < N; i++ { // N large, e.g. tens of thousands
    key = accountkey.NewAccountKeyRoleBasedWithValues(accountkey.AccountKeyRoleBased{key})
}
```
2. RLP-encode this key with `accountkey.NewAccountKeySerializerWithAccountKey(key)` and `rlp.EncodeToBytes`, and embed it as the `AccountKey` field of a `TxTypeAccountUpdate` transaction (bypassing the higher-level API's `checkAccountKeyZeroValues`/`CheckInstallable` guard, which only run *after* decode, by submitting a raw pre-built RLP transaction directly via `eth_sendRawTransaction` or p2p transaction propagation rather than via the account-key construction helpers).
3. Submit the raw transaction bytes to a node's public RPC (`eth_sendRawTransaction`) or via the tx-pool's `AddRemote`, triggering `Transaction.UnmarshalBinary` → `DecodeRLP` → recursive `AccountKeyRoleBased.DecodeRLP`/`AccountKeySerializer.DecodeRLP` calls, well before `CheckInstallable` is ever reached.

Note: I could not fully verify the exact maximum achievable nesting depth given kaia's transaction size limits (I was unable to locate a definitive `MaxTxDataSize` / RPC payload size cap value in the indexed portion of the codebase to compute whether Go's default max goroutine stack (1GB) is actually exceeded, versus this only causing severe CPU/memory overhead). A Devin session with full repository access would be needed to confirm the concrete transaction/payload size caps (`blockchain/tx_pool.go`, RPC max request size config) and empirically determine whether this reaches a true stack-overflow crash versus a resource-exhaustion-only DoS, which would affect the exact severity classification.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}
```

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
```
