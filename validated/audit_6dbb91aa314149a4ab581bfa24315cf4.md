### Title
mWOMSVBaseRewarder._calExpireForfeit never applies the cooldown forfeit, letting mid-unlock stakers keep 100% of unclaimed reward that should be forfeited to remaining lockers - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and never queries `mWOMSV`'s rewardable percentage, so `forfeitAmount` is always computed as `_amount - _amount = 0`. This is inconsistent with the sibling `vlMGPBaseRewarder._calExpireForfeit`, which correctly multiplies by `vlMGP.getRewardablePercentWAD(_account)` to reduce the payout for accounts mid-cooldown, forfeiting the difference back to the pool (`_queueNewRewardsWithoutTransfer`).

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
``` [1](#0-0) 

Compare with the parallel `vlMGPBaseRewarder._calExpireForfeit`, which reads the locker's cooldown state:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
``` [2](#0-1) 

`_calExpireForfeit` is invoked from `_sendReward` (used by both `getReward`/`getRewards`, reachable via `MasterMagpie.multiclaimFor` through `onlyMasterMagpie`) and does not read `mWOMSV` state at all: [3](#0-2) 

Because `rewardableAmount` is hardcoded to `_amount`, `forfeitAmount` is mathematically always `0` for every account, regardless of whether they are mid-cooldown (started `startUnlock` on `mWomSV` and not yet past `endTime`) or fully unlocked. `mWomSV` (in `wombat/mWomSV.sol`) does implement cooldown/unlock-slot tracking (`UserUnlocking`, `coolDownInSecs`, `StillInCoolDown` error, etc.), confirming the cooldown concept exists at the locker level, but `mWOMSVBaseRewarder` never wires this into its forfeit calculation the way `vlMGPBaseRewarder` does for `VLMGP`.

### Impact Explanation
This is a missing-feature bug, not an attacker-specific exploit path. Because the no-forfeit behavior applies uniformly to every caller of `getReward`/`getRewards`/`multiclaimFor` regardless of cooldown status, there is no differential advantage an unprivileged attacker can gain over any other legitimate holder by timing a `startUnlock` before claiming — every mWomSV staker, cooldown or not, already receives 100% of their accrued reward with zero forfeit. The "theft" framing in the question (an attacker specifically diverting funds that "remaining lockers" would have received) does not hold up: no user, attacker or otherwise, is ever charged a forfeit in this contract, so there is no protected balance being redirected to a specific attacker beyond what any other caller already receives under the existing code path.

### Likelihood Explanation
Any unprivileged account can trivially trigger this (call `startUnlock` then `getReward`/`multiclaimFor`), and it is 100% reproducible — but the resulting behavior (zero forfeit) is identical for every account, attacker or legitimate user, with no privileged precondition and no capital requirement to gain relative advantage. It represents a broken/no-op forfeiture mechanism system-wide rather than a targeted attacker exploit that shifts value from other lockers to the caller specifically.

### Recommendation
Add a `getRewardablePercentWAD(address)` (or equivalent cooldown-percentage) function to `mWomSV`/`ILocker` and have `mWOMSVBaseRewarder._calExpireForfeit` compute `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18`, mirroring `vlMGPBaseRewarder._calExpireForfeit`, so that accounts mid-cooldown are properly forfeited and the forfeited amount is queued back via `_queueNewRewardsWithoutTransfer` for remaining stakers.

### Proof of Concept
Not applicable as a distinct attacker-vs-victim PoC: a Foundry test would show `mWOMSVBaseRewarder.calExpireForfeit(account, token)` returns `0` for both a fully-unlocked account and a mid-cooldown account (post `startUnlock`, pre `endTime`), confirming the forfeit logic is a no-op for all callers uniformly — not a mechanism an attacker exploits to divert value specifically to themselves at other lockers' expense.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
