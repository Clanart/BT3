### Title
Unregistered/unbounded `Participant` index in blame resolution panics the node (DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP blame-resolution path (`BlameMachine::blame`, `AdditionalBlameMachine::blame`) takes attacker-supplied `sender` and `recipient` `Participant` indexes and uses them to index `HashMap`s (`enc_keys`, `commitments`) with the panic-on-missing `map[&key]` operator. An accusing participant can specify a `recipient` or `sender` index that was never registered (any value up to `u16::MAX`, including the local party's own index), causing a panic that aborts the process — a remotely reachable denial of service analogous to the reported crash/hang class.

### Finding Description
`BlameMachine::blame` forwards `sender`/`recipient`/`msg`/`proof` — all derived from a counterparty's accusation — directly into `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-631). `blame_internal` calls `Decryption::decrypt_with_proof(sender, recipient, msg, proof)` (crypto/dkg/pedpop/src/encryption.rs:366), which verifies the PoP signature and then evaluates `self.enc_keys[&decryptor]` at encryption.rs:388. `enc_keys` only contains entries for participants registered during `verify_r1` — i.e. indexes `1..=n` excluding the local `i` — yet `recipient` is unconstrained. Passing `recipient = params.i()` (oneself) or any `Participant > n` makes the `HashMap` index panic. If the proof path is skipped (`proof: None` returns `InvalidProof` before the index — but with `Some(proof)` the index occurs unconditionally), the panic is hit. Additionally, `blame_internal` later evaluates `self.commitments[&sender]` (lib.rs:599), which panics for any `sender` not in the commitments map. `AdditionalBlameMachine::new` populates `enc_keys`/`commitments` for `1..=n` only (lib.rs:654-660), so the same out-of-range panic applies to the third-party blame evaluator.

### Impact Explanation
A single crafted blame accusation (a validly-signed `EncryptedMessage` plus an out-of-range or unregistered `sender`/`recipient` `Participant`) panics the victim's key-generation/blame-handling task. In an embedded context (e.g. a processor node evaluating blame proofs from peers), this crashes the participant — complete denial of service, matching the "hang or frequently repeatable crash" availability impact of the analog class. The panic requires no collusion, no valid share, and only the ability to submit a blame statement.

### Likelihood Explanation
Blame evaluation is an explicitly supported public API (`pub fn blame`) whose inputs are "a copy of the encrypted secret share ... and proof" supplied by an accusing party. `Participant` admits any nonzero `u16`, and no bounds check against `params`/the registered set is performed before the `HashMap` indexing. Any peer able to trigger blame evaluation can pick indexes at will.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(...)` and return a defined blame/error result on absence; additionally validate `sender`/`recipient` against `params.all_participant_indexes()` (or the registered key set) at the top of `blame_internal` before any map access.

### Proof of Concept

// Setup: complete a PedPoP DKG (t, n) so the victim holds a BlameMachine,
// or build AdditionalBlameMachine::new(context, n, commitment_msgs).
// enc_keys then contains Participants 1..=n (minus the local i for BlameMachine).

let attacker_msg: EncryptedMessage<C, SecretShare<C::F>> =
  EncryptedMessage::read(&mut crafted_bytes, params)?; // any well-formed msg

// Crafted accusation: recipient index never registered (n+1 or the victim's own i).
let sender = Participant::new(1).unwrap();
let recipient = Participant::new(n + 1).unwrap(); // valid Participant, not in enc_keys

// Some(valid EncryptionKeyProof) so decrypt_with_proof reaches the index.
machine.blame(sender, recipient, attacker_msg, Some(proof));
// -> decrypt_with_proof: self.enc_keys[&recipient] -> panic: "key not found"
// Alternatively sender = Participant::new(n+1) with a passing proof reaches
// self.commitments[&sender] -> panic at lib.rs:599.
