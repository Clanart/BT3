### Title
Unchecked `u64` arithmetic in Bitcoin transaction construction enables attacker-triggered panic - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` performs unchecked summation, multiplication, and addition over attacker-influenced payment amounts and fee parameters. The workspace enables integer-overflow checks even in release builds, so overflowing these operations terminates execution with a panic. [1](#0-0) [2](#0-1) 

### Finding Description
The function accepts `payments: &[(ScriptBuf, u64)]` and `fee_per_vbyte: u64`, only rejecting payments below the dust threshold. [3](#0-2) 

It then calculates `payment_sat` with an unchecked `u64` sum and calculates `needed_fee` with unchecked multiplication. [4](#0-3) 

Two payment amounts of `u64::MAX` overflow `payment_sat`; alternatively, a large `fee_per_vbyte` can overflow `fee_per_vbyte * vbytes`, and `payment_sat + needed_fee` can overflow even when both operands are individually valid. [5](#0-4) 

The analogous change calculation also performs `payment_sat + fee_with_change` without checking for overflow. [6](#0-5) 

### Impact Explanation
An unprivileged party who can cause the application to construct a Bitcoin spend with attacker-selected payment amounts or fee parameters can trigger a deterministic panic. Because workspace release builds explicitly enable `overflow-checks`, this is not limited to debug builds. [1](#0-0) 

The panic occurs before `NotEnoughFunds` can reject the transaction, allowing a malformed spend request to interrupt wallet/signing execution rather than returning a recoverable error. [7](#0-6) 

### Likelihood Explanation
The vulnerable values are ordinary API inputs to `SignableTransaction::new`: payment amounts are unrestricted `u64` values above the dust lower bound, while `fee_per_vbyte` is also a `u64`. [8](#0-7) 

No cryptographic privilege, malformed curve point, malicious validator behavior, or invalid signature is required; two extreme payment amounts are sufficient. [4](#0-3) 

### Recommendation
Use checked arithmetic for all attacker-influenced amount and fee calculations:

- Replace `.sum::<u64>()` with a `checked_add` accumulation returning `TransactionError`.
- Replace `fee_per_vbyte * vbytes` with `checked_mul`.
- Replace `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add`.
- Reject payments above Bitcoin’s `Amount::MAX`/maximum-money bound before summation.
- Ensure all overflow paths return `NotEnoughFunds`, `TooLowFee`, or a dedicated arithmetic-overflow error instead of panicking.

### Proof of Concept
The following conceptual call reaches the first unchecked sum before any funds-sufficiency check:

```rust
// File: networks/bitcoin/src/wallet/send.rs
use bitcoin::ScriptBuf;
use bitcoin_serai::wallet::SignableTransaction;

let script = ScriptBuf::new();
let payments = [
  (script.clone(), u64::MAX),
  (script, u64::MAX),
];

// `input` can be any successfully deserialized `ReceivedOutput`.
// The payment sum overflows at `payments.iter().map(...).sum::<u64>()`.
let _ = SignableTransaction::new(
  vec![input],
  &payments,
  None,
  None,
  1,
);
```

With `overflow-checks = true`, the addition of the two `u64::MAX` payment amounts panics at the `payment_sat` calculation. [9](#0-8)
