## Analysis

The core broken invariant in H‑3 was: a function measured "how much became available to sweep" by reading the **raw current balance** of a shared/pooled account rather than the **delta attributable only to the caller's own action**, then handed the entire swept amount to the caller. `divider.combine()` credited the *entire* `target` balance of the adapter/AutoRoller (including yield already collected on behalf of *other* YT holders) to whichever user called `eject`.

I found the same broken pattern in Hyperbridge's Tron intent-gateway contract.

### The analog

`evm/src/apps/IntentGatewayV2.sol` (the canonical EVM version) correctly isolates the funds that arrive from a `predispatch.call` execution by taking `balanceOf(address(this))` **before** and **after** the dispatcher call and using only the delta: [1](#0-0) 

But `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` does **not** do this. It reads the dispatcher's **raw current balance** directly, with no "before" snapshot: [2](#0-1) 

`_params.dispatcher` is a single shared `CallDispatcher` contract used by every caller of `placeOrder` (and by the fill/execute paths elsewhere in the codebase, e.g. the analogous sweep pattern in `IntentsBase.sol`). `order.predispatch.call` is fully attacker-controlled calldata that gets executed through `ICallDispatcher(dispatcher).dispatch(...)`, which is designed to run an arbitrary `Call[]` (target, value, data) — the same mechanism used elsewhere in the codebase to build ERC‑20 `transfer`/`transferFrom` calls: [3](#0-2) 

Because `balance` is read as `IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance` with no pre‑call snapshot, whatever tokens/ETH happen to sit in the shared `dispatcher` at the moment of the sweep — regardless of who put them there — get swept into `address(this)` and attributed to the caller's order: `requiredAmount` is credited to the caller's own escrow (`_orders[commitment][token] += reducedInputs[i].amount`) and anything above it is emitted as protocol "dust" (`DustCollected`), but the caller pays nothing beyond triggering the sweep.

### Title
Unisolated dispatcher balance sweep lets `placeOrder` credit orders/dust from third-party or stale funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder`'s predispatch-asset sweep on the Tron `IntentGatewayV2` reads the shared `CallDispatcher`'s live `balanceOf`/`.balance` instead of measuring the delta caused by the caller's own `predispatch.call`, unlike the canonical EVM contract which explicitly snapshots balances before/after for this exact reason.

### Finding Description
`placeOrder` transfers the caller's `predispatch.assets` into the shared `dispatcher`, executes the caller-supplied `order.predispatch.call` through `ICallDispatcher(dispatcher).dispatch(...)`, and then sweeps whatever balance is now sitting in `dispatcher` for each input token:
```solidity
balance = IERC20(token).balanceOf(dispatcher);          // raw, unfiltered
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({to: token, ..., data: transfer(address(this), balance)});
uint256 dust = balance - requiredAmount;
_orders[commitment][token] += reducedInputs[i].amount;   // only own order credited
``` [4](#0-3) 

The `dispatcher` is a single, shared, reusable contract (`_params.dispatcher`) — it is not scoped per-order or per-caller. Because `order.predispatch.call` is attacker-supplied bytes executed via `dispatch()`, an attacker can direct the dispatcher to pull tokens from any account that holds a standing ERC‑20 allowance for `dispatcher` (a plausible condition, since the same dispatcher is reused by fill/execute paths elsewhere in the codebase and third parties may have approved it), or can simply exploit any residual token balance left in the dispatcher, and have that balance swept as if it were the attacker's own deposit. `requiredAmount` of the swept funds is credited to the attacker's escrowed order at no real cost to the attacker; the caller only needs the `dispatch()` call to end with `balance >= requiredAmount` in the dispatcher, not to have supplied that value themselves.

This is structurally identical to the AutoRoller bug: a function that should isolate "funds generated by my own action" instead reads an aggregate/shared balance and attributes all of it (or an amount bounded only by that aggregate) to a single caller, letting that caller capture value that belongs to someone else.

### Impact Explanation
An attacker can fund an escrowed order using tokens they never contributed themselves, provided they can get any balance into the shared dispatcher via their own attacker-controlled `predispatch.call` (e.g. pulling from a standing allowance granted by another party, or scooping up any token dust left behind by a prior order's predispatch flow). The result is an order backed by funds not paid by the order's creator — i.e., theft of funds/unauthorized transfer, and a wrong-beneficiary/wrong-amount fund movement, which is squarely inside the bounty's "stealing or loss of funds" / "transaction manipulation" categories.

### Likelihood Explanation
The entry point (`placeOrder`) is fully public and unprivileged; no relayer, prover, or governance actor is required. The only conditions needed are (a) a `predispatch.call` payload the attacker fully controls, and (b) some balance reachable in the shared `dispatcher` — either from a standing allowance held by another party or from residue of a prior/failed sweep. Because the canonical `evm/src/apps/IntentGatewayV2.sol` already fixed exactly this class of issue with a before/after balance snapshot, the omission in the Tron variant is very likely an unintentional divergence between forks rather than a deliberate design choice, making this a genuine regression that a straightforward code diff between the two files would confirm.

### Recommendation
Apply the same fix used in the canonical `evm/src/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` (or the dispatcher's balance) immediately before transferring the caller's `predispatch.assets` and again after `dispatch()` returns, and use only the delta as the amount available to sweep/credit. Never attribute the dispatcher's raw, unfiltered balance to a single caller's order.

### Proof of Concept
Not independently executable from static review alone — full confirmation requires checking `CallDispatcher.sol`'s exact call-forwarding semantics (whether it lets `predispatch.call` invoke arbitrary external contracts/tokens with arbitrary calldata) and whether any real integration grants standing allowances to the shared `dispatcher`. Conceptual PoC:
1. Some account `V` has approved `dispatcher` for `token` (plausible since `dispatcher` is reused by fill/execute flows elsewhere in the codebase).
2. Attacker calls `placeOrder` with `order.inputs = [{token, requiredAmount}]` and `predispatch.call` encoding a `Call` that makes `dispatcher` execute `token.transferFrom(V, dispatcher, requiredAmount)`.
3. `dispatch(order.predispatch.call)` runs, pulling `V`'s tokens into `dispatcher`.
4. The sweep loop reads `balance = requiredAmount` (from `V`, not the attacker), passes the `balance < requiredAmount` check, and credits `_orders[commitment][token] += reducedInputs[i].amount` — the attacker's order is now fully escrowed using `V`'s funds, at zero cost to the attacker.
