### Title
Forged OP_RETURN operator attribution in payout transactions - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` trusts the payout transaction's OP_RETURN output as the sole source of "which operator fronted withdrawal `idx`," but the withdrawal-claim signature that authorizes spending the withdrawal UTXO uses `SinglePlusAnyoneCanPay` sighash, which commits only to input 0 and output 0 of the payout tx. The OP_RETURN output (and any additional funding inputs) are completely unsigned/uncommitted, so anyone holding a valid withdrawal signature can construct and broadcast a payout tx that pays the correct user output while naming an arbitrary — possibly unrelated, honest — operator's x-only pubkey in the OP_RETURN.

### Finding Description
The binding assumed by the protocol is: `payout_payer_operator_xonly_pk[idx] == the party whose wallet funded payout tx for idx`.

`update_finalized_payouts` extracts `operator_xonly_pk` purely from the payout tx's OP_RETURN output via `get_first_op_return_output`/`parse_op_return_data`, with no cross-check against who actually supplied the paying funds: [1](#0-0) 

This value is persisted via `update_payout_txs_and_payer_operator_xonly_pk`: [2](#0-1) 

and later used to select which operator is credited/obligated for reimbursement via `get_first_unhandled_payout_by_operator_xonly_pk`, feeding `handle_finalized_payout`: [3](#0-2) [4](#0-3) 

The only other guard, `is_kickoff_malicious`, checks that the OP_RETURN's operator key matches the operator who later sends the kickoff — it never verifies that this operator actually supplied the payout funding: [5](#0-4) 

Root cause: `create_payout_txhandler` puts the OP_RETURN (operator pubkey) as output index 2, but the payout tx's only cryptographic authorization is the withdrawal owner's key-spend signature, enforced to be `SinglePlusAnyoneCanPay`: [6](#0-5) [7](#0-6) 

`SinglePlusAnyoneCanPay` commits only to input 0 (the withdrawal UTXO) and the output at the same index (output 0, the user's payout). It does not commit to output 1 (anchor), output 2 (OP_RETURN/operator pubkey), or to any additional funding inputs added later via `fund_raw_transaction(add_inputs: true, change_position: Some(1))`: [8](#0-7) [9](#0-8) 

Because the signature over output 0 remains valid no matter what appears in the OP_RETURN, any party in possession of a valid `(input_signature, input_outpoint, output_script_pubkey, output_amount)` tuple — which is exactly the payload the attacker (as the withdrawing user) supplies to the public `withdraw`/`WithdrawParams` gRPC — can independently construct a payout transaction that: spends the correct withdrawal UTXO with the valid signature, pays the correct user output, funds the transaction with the attacker's own money, and stamps an OP_RETURN naming any honest operator X's xonly_pk copied from public round/kickoff transactions. `update_finalized_payouts` will then record `payout_payer_operator_xonly_pk = X`, and X's `payout_checker` task will pick it up and drive X through `handle_finalized_payout`/kickoff/assert flow for a withdrawal X never funded.

### Impact Explanation
This breaks the "operator reimbursed for a payout it never funded" invariant explicitly listed as Critical. The DB attribution for withdrawal `idx` is corrupted, causing an honest operator to be scheduled (via `get_first_unhandled_payout_by_operator_xonly_pk`'s FIFO/`LIMIT 1` semantics) to process, kickoff, and get reimbursed for a payout it did not front, while a payout it did front may sit unprocessed behind the forged entry. Because reimbursement pays the credited operator out of the deposit's escrowed move-to-vault BTC regardless of who actually paid the withdrawal, an attacker can redirect that entry to any operator's queue and disrupt/misattribute the round-based reimbursement bookkeeping across deposits. The attack is repeatable for every withdrawal the attacker (as withdrawer) initiates, and the choice of framed operator is fully attacker-controlled.

### Likelihood Explanation
No special privilege is required beyond being the party requesting the withdrawal (already an unprivileged, in-scope actor) and being able to fund the payout output itself — the same capability any operator has. The attacker only needs to construct the transaction bytes themselves instead of letting the operator do it, substituting the OP_RETURN, which is trivial since the required signature is enforced/known to be `SinglePlusAnyoneCanPay` and thus doesn't cover that output. Cost is limited to the withdrawal amount + fees the attacker would pay to front it, which is inherent to fronting any payout.

### Recommendation
Do not rely on the payout tx's OP_RETURN as the trust anchor for operator attribution. Instead, cryptographically bind the operator identity to the transaction that actually supplies the funding, e.g., by requiring the OP_RETURN/operator claim to be covered by a signature/commitment sourced from the operator's own key (not solely the user's `SinglePlusAnyoneCanPay` signature), or by having `handle_finalized_payout`/kickoff validation trace the actual funding UTXOs of the payout tx back to a specific operator's known wallet/round chain before crediting reimbursement, rather than trusting unauthenticated OP_RETURN bytes.

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
