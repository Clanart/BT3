Audit Report

## Title
`Close` on an `UpgradeableLoaderState::Uninitialized` account drains lamports with no signer/authority check - ([File: programs/bpf_loader/src/lib.rs])

## Summary
`process_instruction`'s handling of `UpgradeableLoaderInstruction::Close` branches on the account's loader-state, and the `Uninitialized` branch unconditionally transfers the account's lamports to the caller-specified recipient at instruction account index 1 with no authority or signer check, unlike the `Buffer`/`ProgramData` branches which route through `common_close_account` and enforce authority presence, match, and signature.

## Finding Description
The `Close` handler matches on `close_account_state` and, for `UpgradeableLoaderState::Uninitialized`, directly calls `recipient_account.checked_add_lamports(close_account.get_lamports())?` and `close_account.set_lamports(0)?` with no authority/signer validation at all [1](#0-0) . This contrasts with the `Buffer` and `ProgramData` branches, which explicitly call `common_close_account`, requiring `authority_address` to be `Some`, to match the account at instruction index 2, and for that account to have signed [2](#0-1) [3](#0-2) .

The generic runtime guard in `set_lamports` only blocks a lamport decrease when the account is not owned by the invoking program: `if !self.is_owned_by_current_program() && lamports < self.get_lamports() { return Err(InstructionError::ExternalAccountLamportSpend); }` [4](#0-3) . Since the account being closed via `Close` is owned by `bpf_loader_upgradeable` (the invoking program), this check does not block the drain, so nothing in the runtime or in the `Uninitialized` branch itself validates that the caller is authorized to move the account's lamports.

The only pre-check before this match is `check_number_of_instruction_accounts(2)` and a check that the close account and recipient account are not the same index [5](#0-4) , neither of which validates ownership rights over the funds.

## Impact Explanation
This matches the fund theft/loss impact category: any writable account owned by `bpf_loader_upgradeable` whose deserialized state is `Uninitialized` and which holds lamports can have those lamports moved to an attacker-chosen recipient account, with no signature or authority check beyond the transaction fee payer. This is a direct, unprivileged fund-theft vector.

## Likelihood Explanation
Exploitation only requires submitting a standard `UpgradeableLoaderInstruction::Close` instruction naming any writable, `bpf_loader_upgradeable`-owned account currently in `Uninitialized` state as account index 0, and an arbitrary attacker-controlled account as the recipient at index 1. Such `Uninitialized`-state accounts naturally arise both before `InitializeBuffer` completes on a freshly allocated/assigned buffer account, and after `common_close_account` resets a closed `Buffer`/`ProgramData` account's state back to `Uninitialized` (since that account may not always be immediately reclaimed by the system program in the same slot). No privileged access or signatures other than the fee payer are needed, making this reachable by any unprivileged user.

## Recommendation
Add an explicit authorization check to the `Uninitialized` branch mirroring `common_close_account`'s pattern — e.g., require the account itself (or a designated authority) to be a signer on the transaction before allowing the lamport transfer, rather than allowing any caller to redirect funds from an `Uninitialized`-state loader-owned account to an arbitrary recipient.

## Proof of Concept
1. Create account `A` via `system_instruction::create_account` with `space = UpgradeableLoaderState::size_of_uninitialized()`, funding it with lamports and assigning it to `bpf_loader_upgradeable::id()`, without ever calling `InitializeBuffer` on it — its state remains `UpgradeableLoaderState::Uninitialized`.
2. An attacker submits a `UpgradeableLoaderInstruction::Close` instruction with accounts `[A (writable), attacker_recipient (writable)]`.
3. In `process_instruction`, `close_account_state` matches `UpgradeableLoaderState::Uninitialized`, and with no signer/authority check, `attacker_recipient` receives all of `A`'s lamports via `checked_add_lamports`/`set_lamports(0)` [1](#0-0) .
4. Result: the attacker drains `A`'s lamports to their own account without ever having held any authority over `A`.

```rust
fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,
) -> Result<(), InstructionError> {
    if authority_address.is_none() {
        ic_logger_msg!(log_collector, "Account is immutable");
        return Err(InstructionError::Immutable);
    }
    if *authority_address != Some(*instruction_context.get_key_of_instruction_account(2)?) {
        ic_logger_msg!(log_collector, "Incorrect authority provided");
        return Err(InstructionError::IncorrectAuthority);
    }
    if !instruction_context.is_instruction_account_signer(2)? {
        ic_logger_msg!(log_collector, "Authority did not sign");
        return Err(InstructionError::MissingRequiredSignature);
    }
```
