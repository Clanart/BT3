### Title
Unprivileged deposit to internal-purpose offset addresses causes received outputs to be misclassified as Branch/Change/Forwarded - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
CVE-2019-3880 is a bug class where an unprivileged party uses an exposed service surface to create an artifact at a location the service treats as authoritative (a registry hive written into the Samba share). The Serai analog is the `Scanner`/`get_outputs` path in `networks/bitcoin/src`: any Bitcoin output paying to one of the deterministic offset-derived addresses (External, Branch, Change, Forwarded) is accepted by `scan_transaction` and stamped with the corresponding internal `OutputType`, with no check on who created the output or why. An external party can therefore "write an artifact" (a received output) into an internal-purpose slot (Branch/Change/Forwarded) that the processor assumes only it can produce.

### Finding Description
`Scanner::new` seeds the script map with the external P2TR script (`Scalar::ZERO`), and `register_offset` inserts additional `script_pubkey -> offset` entries into `self.scripts` (networks/bitcoin/src/wallet/mod.rs:162-196). `scan_transaction` matches solely on `output.script_pubkey` and emits a `ReceivedOutput` carrying the stored offset (mod.rs:199-213). In the processor, `scanner()` deterministically registers `Branch`, `Change`, and `Forwarded` offsets via `Secp256k1::hash_to_F(KEY_DST, ...)` (processor/src/networks/bitcoin.rs:308-346), so every one of these internal addresses is publicly derivable from the public group key. `get_outputs` then classifies each scanned output by looking up `kinds[offset_repr]` — including `OutputType::Branch`, `OutputType::Change`, and `OutputType::Forwarded` — and pushes it into the received-output pipeline gated only by `N::DUST` (processor/src/networks/bitcoin.rs:686-700). Only `External` outputs receive the sender's `data`/`presumed_origin` semantics (lines 731-735); outputs sent by strangers to internal addresses are silently given internal-type classification.

### Impact Explanation
Downstream accounting treats `OutputType` as proof of provenance: Change outputs are assumed to be the processor's own change, Forwarded outputs are assumed to be processor-initiated forwards awaiting completion, and Branch outputs are assumed to be protocol-internal. An unprivileged party who sends ≥ `DUST` (10,000 sats) to the publicly-computable change/forward/branch address causes a `ReceivedOutput`/`Output` to be recorded with an internal kind it never earned, corrupting the wallet's internal accounting and potentially causing the scheduler to treat attacker-injected outputs as legitimate internal flows (e.g., triggering forward-completion or change-consolidation logic on artifacts the processor never created). This mirrors the CVE: attacker-controlled content materializing at a location reserved for internally-created objects.

### Likelihood Explanation
The internal addresses are fully deterministic: `hash_to_F(b"Serai Bitcoin Output Offset", b"branch"|"change"|"forward")` offsets over the public group key, so any observer can compute them and send a standard P2TR payment — no validator status, key material, or collusion required. The cost is limited to the dust threshold plus fees, and the attacker's funds remain recoverable only via the group key, so the attack is griefing/accounting-corruption rather than theft, consistent with Medium severity.

### Recommendation
In `get_outputs`, only emit outputs whose scanned offset corresponds to `OutputType::External` (or explicitly expected internal outputs, e.g., recognized by matching against outpoints/txids the processor itself created or expected eventualities), rather than trusting any on-chain payment to an internal offset address. Alternatively, record the internal-kind output but flag it as anomalous and exclude it from automated change/forward processing.

### Proof of Concept
1. Obtain the multisig group key `K` (public on-chain / from the network).
2. Compute `branch_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch")` (adjusting for the even-Y increment loop in `register_offset`), and derive `branch_addr = p2tr_script_buf(K + G*branch_offset)` — exactly as `Bitcoin::branch_address` does (processor/src/networks/bitcoin.rs:661-664).
3. Broadcast a transaction paying ≥ 10,000 sats to `branch_addr`.
4. When the processor scans the block, `get_outputs` → `scanner.scan_transaction` matches the script_pubkey and emits `Output { kind: OutputType::Branch, ... }` (processor/src/networks/bitcoin.rs:692-699), registering attacker-created funds as an internal Branch output without any provenance check.
