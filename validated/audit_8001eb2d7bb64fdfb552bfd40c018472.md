### Title
Unregistered decryptor index panics PedPoP blame decryption, crashing the validator - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Decryption::decrypt_with_proof` in the PedPoP encryption layer indexes `self.enc_keys[&decryptor]` directly. `enc_keys` is only populated by `Decryption::register`, which asserts single registration per `Participant`. When processing a blame proof for a message whose decryption target (`decryptor`) never registered an `EncryptionKeyMessage` — something a malicious DKG participant can arrange by sending shares addressed to a `Participant` index that published no encryption key, or by provoking a blame flow naming an arbitrary `Participant` — the `HashMap` index panics instead of returning a `DecryptionError`. This is a remotely triggerable crash (complete DoS of the DKG/blame evaluation on that validator), matching the bug class of CVE-2025-30687 (low-privileged, network-reachable, availability-only hang/crash).

### Finding Description
`decrypt_with_proof` handles all failure paths with `Result<_, DecryptionError>` — invalid PoP returns `DecryptionError::InvalidSignature` (encryption.rs:374-379), invalid/missing key proof returns `DecryptionError::InvalidProof` (encryption.rs:390, 395). But at encryption.rs:388 the shared key lookup for the decryptor is `self.enc_keys[&decryptor]`, which panics on a missing key rather than erroring. The same hazard exists on the encryption side at `self.decryption.enc_keys[&participant]` (encryption.rs:466), and `Decryption::register` hard-`assert!`s against re-registration (encryption.rs:356-359), so state can contain fewer entries than the set of `Participant` indexes an attacker can name. Since `EncryptedMessage::read` / `EncryptionKeyMessage::read` accept any `Participant`-derived context and the blame protocol (`EncryptionKeyProof`) is submitted by unauthenticated-in-advance accusers, a malicious participant can steer execution into a lookup on a `decryptor` that is absent from the map, turning a routine malformed-share/blame path into a process crash.

### Impact Explanation
A single crafted DKG shares message or blame submission causes a panic in validator code during PedPoP share verification or blame evaluation. Because the panic occurs inside `Result`-returning API intended to cleanly return `DecryptionError`, there is no graceful handling — the node crashes mid-DKG, halting key generation/signing availability. This is an availability-only impact reachable by a low-privileged DKG participant with only public messages, matching CVSS C:N/I:N/A:H.

### Likelihood Explanation
The attacker controls the `Participant` indexes used in share/blame flows and can simply omit, or target an index for which no `EncryptionKeyMessage` was registered (e.g., a participant beyond the registered set, or any inconsistent index introduced via a malformed shares payload). No cryptographic work or collusion is needed; the crash is deterministic once the poisoned map lookup is reached.

### Recommendation
Replace `self.enc_keys[&decryptor]` (encryption.rs:388) and `self.decryption.enc_keys[&participant]` (encryption.rs:466) with `get()` + `ok_or`-style error returns (`DecryptionError::InvalidProof` / a dedicated variant). Similarly, make `Decryption::register` return a `Result` (or silently dedupe with an explicit error) instead of `assert!`-ing on re-registration (encryption.rs:356-359), and ensure callers surface the error rather than panicking on attacker-controlled indexes.

### Proof of Concept
```rust
// Within a PedPoP session where `self` is a `Decryption<C>` whose `enc_keys`
// only contains entries for participants who registered EncryptionKeyMessages:
let mut decryption = Decryption::<C>::new(context);
// register keys for honest participants 1..=n, none for index X (e.g., X not
// among those who published an encryption key, or absent entirely)
let msg: EncryptedMessage<C, E> = EncryptedMessage::read(&mut attacker_bytes, params)?;
// Attacker-submitted blame proof referencing decryptor = X:
let proof = EncryptionKeyProof::read(&mut attacker_proof_bytes)?;
// PANIC: index into empty/absent entry instead of Err(DecryptionError)
decryption.decrypt_with_proof(accused, X, msg, Some(proof)); // self.enc_keys[&X] -> panic
```
The panic occurs at `self.enc_keys[&decryptor]` after the PoP check passes (attacker can sign a valid PoP over `key` for their own message), so no cryptographic barrier prevents reaching it.

Note: reachability of `decrypt_with_proof` with a fully attacker-chosen `decryptor` index depends on how `pedpop/src/lib.rs` drives blame evaluation (not fully verified); the panic on the indexing itself and the `assert!` in `register` are confirmed in `encryption.rs`.
