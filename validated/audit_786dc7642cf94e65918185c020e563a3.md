## Title
Desktop force-enables `protocol.file.allow=always` when auto-initializing submodules, letting an attacker-controlled `.gitmodules` in a checked-out branch pull arbitrary local filesystem paths into the working directory - (`File: app/src/lib/git/submodule.ts`)

### Summary
When GitHub Desktop checks out a branch or commit, it calls `updateSubmodulesAfterOperation` to auto-initialize/update submodules. When invoked with `allowFileProtocol = true`, this function explicitly re-enables Git's `file://` submodule protocol via `-c protocol.file.allow=always` [1](#0-0) , which overrides Git's own security default of `protocol.file.allow=user` (introduced after CVE-2017-1000117/CVE-2018-11235-class submodule attacks). No validation is performed on the submodule URLs recorded in `.gitmodules` before this flag is applied.

### Finding Description
`.gitmodules` is a file tracked inside the repository, so its contents are fully attacker-controlled by anyone who can push a branch/commit to a remote the victim fetches or clones (or send a PR the victim checks out). Git upstream deliberately restricts `submodule.<name>.url` values using `file://` protocol by default (`protocol.file.allow=user`) specifically to stop malicious repositories from making `git submodule update --init` read/copy files from arbitrary local paths on the victim's machine into the submodule's working tree.

Desktop's `updateSubmodulesAfterOperation` unconditionally passes `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true`, and calls this on `checkoutCommit`/`checkoutBranch` operations [2](#0-1) . There is no check of the runtime configuration (i.e., what URLs `.gitmodules` actually contains) before the elevated protocol permission is granted - the "unsafe" protocol allowance is applied blanket, defeating the purpose of Git's own opt-in safeguard. This directly parallels the report's root cause: a security-relevant configuration value (`protocol.file.allow`, analogous to `runtimeConfig`) is set to a permissive/unsafe value without validating what it will be used against (the attacker-supplied submodule URLs, analogous to unchecked `runtimeConfig`-driven mint functions).

### Impact Explanation
If a submodule entry in `.gitmodules` in an attacker-influenced branch specifies `url = file:///some/absolute/path` (e.g., pointing to another local git repository, a symlinked location, or path with sensitive files checked in as a bare repo), Desktop will happily clone/copy that local path's content into the victim's working directory tree during an ordinary checkout, without any prompt or warning. This is a "read outside the repo" primitive: private local repositories or files a user has git-cloned into predictable locations (dotfiles repos, credentials repos, CI checkouts) can be silently pulled into the visible working tree of the untrusted repo, from where they could be committed/pushed by the user unknowingly, or simply viewed/exfiltrated by the attacker via a subsequent PR/diff review workflow.

### Likelihood Explanation
The trigger requires only that the victim clone/fetch a repository (or check out a branch/PR) containing a crafted `.gitmodules` — a completely standard, low-friction Desktop workflow (`checkoutBranch`, `checkoutCommit`, `pull`). No local access, no admin rights, and no unusual user action beyond normal repo/branch checkout is needed, matching the "attacker controls a cloned/fetched repository" scenario in the accepted impact criteria.

### Recommendation
Do not blanket re-enable `protocol.file.allow=always`. Instead, before invoking `git submodule update --init --recursive`, parse `.gitmodules` submodule URLs and only allow `file://` when the target path is verified to be nested within, or explicitly trusted relative to, the repository being cloned (matching the original intent for local test fixtures/relative submodules), otherwise leave Git's default `protocol.file.allow=user` (or `deny`) in effect and surface a warning/prompt to the user when a submodule requests the file protocol.

### Proof of Concept
1. Attacker creates a public repo with a branch containing a `.gitmodules` entry:
   ```
   [submodule "evil"]
       path = evil
       url = file:///home/victim/.ssh-backup-repo
   ```
   (any local path/bare repo the attacker suspects or has confirmed exists on common victim setups).
2. Victim clones/fetches the repo in GitHub Desktop and checks out that branch, e.g. via `checkoutBranch`, which calls `checkoutCommit`/`updateSubmodulesAfterOperation` with `allowFileProtocol = true` [3](#0-2) .
3. Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive` [4](#0-3) , which clones the local path directly into `evil/` in the working directory, bypassing Git's built-in protection that would otherwise block this without explicit user opt-in.
4. The victim's file content is now materialized inside the tracked repo directory, where it can be committed, pushed, or leaked through normal repo operations.

Note: I was not able to fully trace, within the available iterations, every call site in `app/src/lib/stores/app-store.ts` that decides when `allowFileProtocol` is passed as `true` vs `false` for user-initiated checkouts (4 matches found but not inspected in detail) — confirming the exact conditions under which this flag is enabled for arbitrary/untrusted branch checkouts (versus e.g. only for known local fixture scenarios) would strengthen this finding. If it turns out `allowFileProtocol` is only ever `true` for a narrowly controlled internal path, this reduces the severity; a Devin session with full repo access would be needed to enumerate these call sites exhaustively.

export async function checkoutCommit(
  repository: Repository,
  commit: CommitOneLine,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out ${__DARWIN__ ? 'Commit' : 'commit'}`
  const target = shortenSHA(commit.sha)
  const opts = await getCheckoutOpts(
    repository,
    title,
    target,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, commit.sha]

  await git(args, repository.path, 'checkoutCommit', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    target,
    allowFileProtocol
  )
