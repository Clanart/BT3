### Title
Discard Changes trash/rm operations resolve attacker-influenced paths without repository-containment checks - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges()` moves working-directory files to the OS trash (or deletes them outright) using paths taken directly from `git status` output, resolved with plain `Path.resolve`/`Path.join` rather than the codebase's own safe-path helper `resolveWithin`. Elsewhere in the same codebase (`app-store.ts`) file writes derived from repository-relative paths are explicitly validated with `resolveWithin` — including a dedicated regression test proving it blocks symlink-based directory-traversal escapes. That containment check is missing from the discard-changes code path, so a maliciously crafted working tree (e.g. a tracked directory replaced by a symlink pointing outside the repo) can cause Desktop to move-to-trash or permanently delete/write files outside the cloned repository when the user performs the ordinary "Discard Changes" action.

### Finding Description
`GitStore.discardChanges` builds the on-disk paths to touch directly from `file.path`/`file.status.oldPath`, which originate from parsing `git status --porcelain=2 -z` output (`app/src/lib/status-parser.ts`, `app/src/lib/git/status.ts`). It resolves these with unchecked path joins: [1](#0-0) 

Specifically:
- `Path.resolve(this.repository.path, file.path)` is passed to `this.shell.moveItemToTrash(...)`.
- `rm(Path.join(this.repository.path, file.path))` is used for the "discard permanently" fallback for untracked files.

Neither call verifies that the resolved path actually stays underneath `repository.path`. Compare this to the pattern used for writing Copilot conflict resolutions, where the very same class of file-path input (repository-relative, attacker/report-influenceable) is passed through `resolveWithin`, which explicitly resolves symlinks via `fs.realpath` and rejects any result that escapes the root: [2](#0-1) [3](#0-2) 

The project's own test suite documents precisely the attack `resolveWithin` is meant to stop — a symlinked directory used to traverse outside the intended root — and confirms `resolveWithin` catches it while a naive `Path.resolve`/`Path.join` would not: [4](#0-3) 

Because `discardChanges` never calls `resolveWithin` (or performs any equivalent realpath containment check) before invoking `shell.moveItemToTrash` or `rm`, a working directory that an attacker can influence — for example a directory entry that git status reports as "Untracked" content sitting beneath a symlink that a hostile commit/checkout swapped in place of a previously tracked directory — will cause Desktop to resolve a path that lands outside the repository root. The subsequent trash-move or delete then operates outside the repo, following the symlink.

This is the same broken-invariant shape as the source report: a security-relevant guard/value (`projectCollateralFeeCollected` accounting in the Solidity report; `resolveWithin` containment checking in Desktop) is enforced in one code path but silently skipped in a sibling code path that performs the sensitive operation (fund transfer / file deletion), leaving the invariant "operations never affect what's outside the tracked scope" unenforced there.

### Impact Explanation
If reachable, this allows an attacker-controlled repository state to cause Desktop, acting on the ordinary, unprivileged "Discard Changes" user action, to delete or move-to-trash files outside the user's repository — i.e. file deletion/write outside the repo boundary, matching the "Valid Impact" criteria (attacker controls a cloned/fetched repository; result is file write/deletion outside the repo). The severity depends on what the symlink can be made to target (arbitrary paths reachable by the OS trash/`rm` call under the user's permissions), which can range from data loss to corruption of unrelated files/directories on the user's machine.

### Likelihood Explanation
The user must click "Discard Changes" (or "Discard All Changes") on a repository whose working tree contains the attacker-crafted symlinked path — this is a normal, expected Desktop workflow once a hostile repository has been cloned/fetched/checked out, not an unnatural or out-of-band step. The needed precondition (a tracked directory replaced by a symlink, or an untracked symlinked directory reported by `git status`) is achievable purely through repository content, matching the "attacker controls a cloned/fetched repository" trigger class explicitly allowed by the task's Valid Impact section.

### Recommendation
In `GitStore.discardChanges` (`app/src/lib/stores/git-store.ts`), resolve every path taken from `file.path` / `file.status.oldPath` through `resolveWithin(this.repository.path, file.path)` (already used in `app-store.ts` for the analogous Copilot-conflict write path) before calling `this.shell.moveItemToTrash(...)` or `rm(...)`, and skip/reject any file whose resolved path is `null` (i.e., escapes the repository root), mirroring the existing `absolutePath === null` guard pattern.

### Proof of Concept
1. Attacker prepares a repository/branch where a path previously tracked as a directory (e.g. `assets/`) is replaced by a symlink pointing outside the repo (e.g. `../../../../` or another sensitive location), and places or leaves untracked content addressed through that symlinked path.
2. Victim clones/fetches and checks out this branch in GitHub Desktop; `git status` reports the symlinked-path content as an `Untracked`/`Modified` file with `path` such as `assets/evil.txt`, exactly as parsed in `app/src/lib/status-parser.ts` / `app/src/lib/git/status.ts`.
3. Victim opens the Changes view and clicks "Discard Changes" (or "Discard All Changes") — the normal UI flow (`app/src/ui/discard-changes/discard-changes-dialog.tsx:158-168` → `dispatcher.discardChanges` → `GitStore.discardChanges`).
4. `Path.resolve(this.repository.path, 'assets/evil.txt')` follows the symlink at `assets/` and resolves to a location outside the repository; `shell.moveItemToTrash`/`rm` then acts on that external path instead of a path confined to the clone, without any `resolveWithin`-style containment check having been performed.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
