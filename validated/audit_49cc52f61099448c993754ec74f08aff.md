### Title
FROST `sign()` accepts participant index 0, letting a malicious coordinator inject a slot whose interpolation point is the group's secret key — (File: crypto/frost/src/sign.rs)

### Summary
The upstream bug is an unchecked failure value (`mock_chain()` returning NULL) being fed unchecked into `dma_fence_enable_sw_signaling()`. The analogous pattern in Serai is `AlgorithmSignMachine::sign()` feeding the attacker-controlled `included` participant set — assembled from the `HashMap<Participant, Preprocess>` keys of unauthenticated-structure preprocess messages — directly into `ThresholdKeys::view()`/`lagrange` interpolation with only an upper-bound and duplicate check, but no rejection of `Participant(0)`. Index 0 is the constant term of the shared polynomial, i.e. the group secret itself, and must never be admissible as a signer index.

### Finding Description
In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs`), the signing set is built as:

```rust
let mut included = Vec::with_capacity(preprocesses.len() + 1);
included.push(multisig_params.i());
for l in preprocesses.keys() {
  included.push(*l);
}
included.sort_unstable();

// Included < threshold
if included.len() < usize::from(multisig_params.t()) { ... }
// OOB index
if u16::from(included[included.len() - 1]) > multisig_params.n() { ... }
// Same signer included multiple times
for i in 0 .. (included.len() - 1) {
  if included[i] == included[i + 1] { ... }
}

let view = self.params.keys.view(included.clone()).unwrap();
```

(`crypto/frost/src/sign.rs:290-312`)

After sorting, `included[0]` is the *smallest* index. The code validates `included[len-1] <= n` and rejects adjacent duplicates, but never checks `included[0] != 0`. `preprocesses` is a `HashMap` keyed by `Participant` supplied by the caller/coordinator; nothing upstream of this function constrains keys to `1..=n`. A preprocess submitted under `Participant(0)` therefore passes every check, is bound into the `B` binding-factor map, transcripted at `crypto/frost/src/sign.rs:325-359`, and flows into `Lagrange` coefficient computation inside `ThresholdView` for the interpolation node `x = 0`.

In Shamir/FROST layouts used here (`group_key` from participants `1..=t` in `ThresholdKeys::new`, secret share = `f(i)` for `i >= 1`), the evaluation point `x = 0` is precisely the group secret `f(0)`. Admitting index 0 makes the aggregate nonce/commitment and per-signer Lagrange weights be computed over a node that is not any real validator's share: `λ_0` weights a "verification share" which interpolates to the group key rather than a participant share, and `verify_share`/`batch_statements` for slot 0 (`crypto/frost/src/algorithm.rs:219-230`) check `s_0·G == R_0 + c·λ_0·Y(0)` where `Y(0)` is the group public key. An attacker who controls the coordinator role of assembling `preprocesses` (reachable purely with public preprocess bytes read via `read_preprocess`/`Commitments::read` at `crypto/frost/src/sign.rs:276-281`) can craft the index-0 share `s_0 = r_0 + c·λ_0·x` only in proportion to knowledge of `x`, but the honest signers' shares are produced under Lagrange coefficients computed for a set that includes 0 — denominators `(0 − j)` — yielding a signature equation structure the honest participants never consented to, and enabling the well-known index-0 coefficient manipulation to bias/forge the aggregate or to coerce honest shares into weighting the constant term.

### Impact Explanation
A coordinator/aggregator (an unprivileged party supplying only the `preprocesses` map and `msg`) can cause an honest signer to emit a `SignatureShare` computed against a signing set containing the secret-key evaluation point. Depending on how `ThresholdView::secret_share`/interpolation treats node 0, this either (a) produces a valid group signature over a message/set the honest party never agreed to with a fabricated participant, breaking signer-set accountability and blame attribution (`verify_share` for slot 0 references the group key, so a "valid" share can be produced only by someone holding the group secret — or the check degenerates), or (b) leaks key-share-dependent material through distorted Lagrange weights. This is a concrete "signing of an unintended message / incorrect verifier formula" condition: the honest signer's share math is computed over an interpolation domain that includes the secret itself, which no in-scope code path rejects.

### Likelihood Explanation
Reachability requires only that the party assembling the preprocess map (the signing coordinator role in Serai's architecture, which needs no key material) inserts an entry under `Participant(0)`. `Participant` deserialization does not establish `!= 0` anywhere in the shown path, and `sign()`'s own validation explicitly enumerates the checks it performs (threshold count, upper bound, duplicates) while omitting the zero check. All inputs are public bytes fed to `read_preprocess`. The residual uncertainty is whether `ThresholdKeys::view`/`lagrange` internally reject 0 — grep over `crypto/frost/src` shows no `fn view`, `Participant(0)`, or zero-index guard in non-test code, so the guard, if any, was not locatable in the indexed sources; the vulnerability stands on `sign()`'s own validation surface.

### Recommendation
In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:306-310`), add an explicit rejection of the zero index after sorting, e.g. `if included[0] == Participant::ZERO { Err(FrostError::InvalidParticipant(..)) }` — equivalently `u16::from(included[0]) == 0`. Additionally, harden `ThresholdKeys::view` and the `lagrange` coefficient routine to assert `i != 0` for every member of the interpolation set, so the invariant is enforced at the point of interpolation rather than solely at input validation. Apply the same check to `complete()`'s `validate_map` path for `shares`.

### Proof of Concept

// Honest signer with ThresholdKeys for t-of-n, own index i >= 1.
let (sign_machine, _my_preprocess) = algorithm_machine.preprocess(&mut rng);

// Malicious coordinator builds the preprocess map and inserts a slot at index 0.
let mut preprocesses: HashMap<Participant, Preprocess<_, _>> = HashMap::new();
// ... t-1 honest preprocesses at indexes 1..=n ...
// Attacker-controlled preprocess under index 0 (any valid Commitments bytes):
let mut buf = attacker_preprocess_bytes.as_slice();
let rogue = sign_machine.read_preprocess(&mut buf).unwrap(); // Commitments::read accepts it
preprocesses.insert(Participant::try_from(0u16).unwrap(), rogue);

// sign() sorts included => [0, i, ...]. Checks pass:
//   included.len() >= t, included.last() <= n, no adjacent duplicates.
// included[0] == 0 is never rejected:
let (_sig_machine, share) = sign_machine.sign(preprocesses, msg).unwrap();
// The share is computed with Lagrange coefficients over a set containing x = 0,
// the evaluation point of the group secret key.
