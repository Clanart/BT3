### Title
Stale manual conflict resolutions carry over into an unrelated merge/rebase, causing silent auto-resolution of attacker-controlled content - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateConflictState` reuses the previous `manualResolutions` map whenever the new conflict state has the same *kind* (`merge` vs `merge`, `rebase` vs `rebase`) as the previous one, even when the underlying operation is clearly different (different branch, different tip). This is analogous to the reported Treasury bug: a one-shot/carried-over state value (`isRefundedInUSDT[user][projectId]` there, `manualResolutions.get(path)` here) is not properly re-scoped to the new "session" (a new stake / a new merge), so old state silently governs new operations.

### Finding Description
`getConflictState` builds the new conflict state by threading through whatever `manualResolutions` map was already present: [1](#0-0) 

```

  (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
  (newConflictState == null || isMergeConflictState(newConflictState))

```

The guard only checks that both states are of the same *kind* (`merge`/`rebase`), it does **not** check that `currentBranch`/`currentTip` match, i.e. that this is the *same* merge/rebase operation. The project's own test suite documents this exact scenario without recognizing it as a security-relevant bug: `'increments abort counter when branch has changed'` builds a `prevConflictState` on `old-branch` with a non-empty `manualResolutions` (`foo -> theirs`), then calls `updateConflictState` with a status for a **different branch** (`master`) and asserts only that a stats counter fires — the returned state still carries the same `manualResolutions` map forward unchanged (see also the `'preserves manual resolutions'` test which explicitly checks the map is preserved, and `MergeConflictState`/`RebaseConflictState` types definition): [2](#0-1) 

Once a path has an entry in `manualResolutions`, `hasUnresolvedConflicts`/`getResolvedFiles`/`getConflictedFiles` treat that path as already resolved for *any* conflict state, and the resolution is later applied via git checkout `--ours`/`--theirs` and staged at commit time without ever re-prompting the user, regardless of which merge/rebase produced the current conflict on that path: [3](#0-2) 

### Impact Explanation
If a user resolves a conflict on `path`, aborts (or the operation state transitions) and then starts an entirely new merge/rebase — for example fetching/merging a different, attacker-controlled branch/remote that also conflicts on the same `path` — Desktop will silently treat that path as already resolved using the *stale* choice (`ours`/`theirs`) from the prior, unrelated operation. If the stale choice was `theirs`, the *new* merge's incoming (attacker-controlled) content for that path is auto-staged and can be committed/pushed without the user ever seeing conflict markers or being asked to confirm resolution for the new operation. This is silent corruption of what the user commits/pushes, driven entirely by content in a git remote/branch the attacker controls, matching the accepted "unprivileged" impact class (no local access, no malware, no social engineering beyond having the user merge/fetch a branch — an ordinary git workflow action).

### Likelihood Explanation
Requires: (1) the user has previously manually resolved a conflict on a given file path during any merge/rebase/cherry-pick in the same session (a very common workflow action), and (2) they subsequently start a different merge/rebase that also conflicts on that same file path (also plausible, e.g. same config/lockfile path repeatedly conflicting across different branches). No special git repository layout or privilege is needed by the attacker beyond making sure their branch conflicts on the same path — an attacker fully controls the content of a branch/fork they offer for merging. The bug is directly demonstrated by the project's own unit test showing the branch-changed transition preserving `manualResolutions` unchanged.

### Recommendation
Scope `manualResolutions` (and conflict resolution reuse in general) to the specific in-flight operation, not just its `kind`. `updateConflictState` should reset `manualResolutions` to an empty map whenever `currentTip`/`currentBranch` (for merge) or `targetBranch`/`baseBranchTip`/`originalBranchTip` (for rebase) change between `prevConflictState` and the newly detected conflict, i.e. only carry the map forward when it is verifiably the same operation continuing (matching what `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` already use to decide "aborted" vs "continuing"). Additionally, `getResolvedFiles`/`hasUnresolvedConflicts` should not honor a manual resolution recorded for a path from a different operation/tip.

### Proof of Concept
1. Clone/open a repo with `master` checked out.
2. Merge attacker branch `A` which conflicts on `config.json`; in the Conflicts dialog, manually choose "Theirs" for `config.json` but do not finish the merge — abort it.
3. Immediately merge attacker branch `B` (different tip) which also conflicts on `config.json`, where `B`'s version of `config.json` contains malicious/altered content.
4. Because `updateConflictState` reused `manualResolutions` from step 2 (`config.json -> theirs`) into the new conflict state for branch `B` (still classified `kind: 'merge'`), Desktop's UI shows `config.json` as already resolved. The user commits the merge; `config.json` is silently staged with `B`'s (attacker-controlled) content via the manual-resolution checkout path, without the user ever reviewing branch `B`'s conflict on that file.

Note: I was unable to execute this scenario end-to-end in a live Desktop instance from static analysis alone; the conclusion is based on tracing `updateConflictState`/`getConflictState` and their existing unit tests, which confirm the map-carry-over behavior across a branch change but do not themselves assert on the subsequent commit-staging step (`stageManualConflictResolution` in `app-store.ts`), which was found in the codebase but not fully read due to iteration limits — that file should be reviewed to confirm the precise commit-time staging path.

```typescript
export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }
```

```typescript
/** Filter working directory changes for resolved files  */
export function getResolvedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      !hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}

/** Filter working directory changes for conflicted files  */
export function getConflictedFiles(
  status: WorkingDirectoryStatus,
  manualResolutions: Map<string, ManualConflictResolution>
) {
  return status.files.filter(
    f =>
      isConflictedFileStatus(f.status) &&
      hasUnresolvedConflicts(f.status, manualResolutions.get(f.path))
  )
}
```
