## Analog Found: `updateHostParamsInternal` fee-token migration can be perpetually DoS'd by a 1-wei donation

### Title
Cross-chain fee-token migration in `EvmHost.updateHostParamsInternal` can be permanently DoS'd via griefing donation - (`evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` blocks any change of the `feeToken` host parameter while the host still holds a non-zero balance of the *old* fee token, exactly the "balance must be exactly zero" pattern from the external report. Because the old fee token is an arbitrary ERC-20 that anyone can `transfer` to the host address, an unprivileged attacker can keep the balance non-zero forever by re-donating 1 wei every time governance drains it, permanently blocking a legitimate cross-chain governance action (fee-token migration) that is delivered as a one-shot `PostRequest` through `HostManager`.

### Finding Description
`updateHostParamsInternal` enforces: [1](#0-0) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

This function is only reachable through cross-chain governance via `updateHostParams`, restricted to `_hostParams.hostManager`: [2](#0-1) . The `HostManager` module executes exactly one governance action per incoming `PostRequest` — either `Withdraw` or `SetHostParam` — each dispatched from Hyperbridge as a separate message: [3](#0-2) .

Because `feeToken()` returns an arbitrary, non-privileged ERC-20 address, and any address can call `IERC20(oldFeeToken).transfer(host, 1)`, an attacker can watch the mempool/chain for the `Withdraw` message that governance uses to zero out the old fee-token balance (the intended remediation, per the existing test `testSweepFeeTokenBeforeUpdate`) and immediately re-donate 1 wei of the same token to the host before the subsequent `SetHostParam` message lands. Since the two governance actions arrive as independent transactions (not atomically batched), the attacker always has a window to re-poison the balance check, permanently blocking the fee-token migration.

The existing test confirms the intended mitigation requires the balance to be fully drained first: [4](#0-3) . In production, "draining" the balance uses `withdraw()`, which is also `restrict(_hostParams.hostManager)`-gated and processed as its own separate `PostRequest`: [5](#0-4) , [6](#0-5) . This leaves a gap between the `Withdraw` and `SetHostParam` messages that any unprivileged actor can exploit indefinitely.

### Impact Explanation
This blocks a core host-management execution path — cross-chain governance's ability to migrate the protocol's fee token (e.g., to move away from a deprecated, compromised, or depegged token). An attacker with no privileges and negligible cost (repeated 1-wei transfers) can indefinitely prevent this critical parameter update from ever landing, which is a logic/DoS attack directly against bridge governance execution, distinct from a generic gas-griefing complaint since it permanently blocks a specific, security-relevant admin action tied to fund-safety configuration (the fee token used for all bridge fee accounting).

### Likelihood Explanation
High: the attack requires only a public ERC-20 `transfer` call of 1 wei to the host contract address, timed after governance's `Withdraw` message executes and before its `SetHostParam` message executes. No special permissions, relayer/prover compromise, or malicious peer behavior is needed — only observing chain state/public mempool for governance's two sequential, unauthenticated-from-the-attacker's-perspective transactions.

### Recommendation
Remove the strict `balance != 0` revert from `updateHostParamsInternal`, or replace it with logic that force-sweeps/holds the residual old-fee-token balance internally (e.g., automatically transferring any leftover balance to a fixed treasury/beneficiary as part of the same `updateHostParamsInternal` call) so the migration path is not dependent on an externally-influenceable ERC-20 balance being exactly zero at call time.

### Proof of Concept
1. Host's current `feeToken` is `TokenA`; governance decides to migrate to `TokenB` due to a security issue with `TokenA`.
2. Governance sends a `Withdraw` `PostRequest` via Hyperbridge to `HostManager.onAccept`, which calls `EvmHost.withdraw` to drain the host's `TokenA` balance to 0: [7](#0-6) .
3. Before governance's second message (`SetHostParam` with `feeToken = TokenB`) is delivered, an attacker calls `TokenA.transfer(hostAddress, 1)`.
4. When `HostManager.onAccept` delivers `SetHostParam`, `updateHostParamsInternal` reads `IERC20(TokenA).balanceOf(host) == 1 != 0` and reverts with `CannotChangeFeeToken()`: [1](#0-0) .
5. Governance must issue another `Withdraw` message to sweep the new 1 wei, but the attacker repeats step 3 indefinitely, permanently blocking the fee-token migration.

```text
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
```

```text
    function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        }
    }
```

```text
    function testSweepFeeTokenBeforeUpdate() public {
        feeToken.mint(address(host), 1 * 1e18);
        HostParams memory params = host.hostParams();
        params.feeToken = address(this);
        // we can't set host params
        vm.prank(host.hostParams().admin);
        vm.expectRevert(EvmHost.CannotChangeFeeToken.selector);
        host.updateHostParams(params);

        feeToken.burn(address(host), 1 * 1e18);
        // we can set host params
        vm.prank(host.hostParams().admin);
        host.updateHostParams(params);
        assert(host.hostParams().feeToken == address(this));
    }
```
