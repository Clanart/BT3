### Title
Legacy bank precompile versions bypass tokenfactory `DenomAllowList` enforcement - ([File: precompiles/bank/legacy/v555/bank.go])

### Summary
The Sei bank precompile's `send` function is versioned (multiple `precompiles/bank/legacy/vXXX/bank.go` implementations exist for historical EVM replay/versioning). The current/newer versions (`precompiles/bank/bank.go`, and legacy `v601`+ through `v67`) route ERC20-pointer-triggered native sends through `p.bankMsgServer.Send(...)`, which enforces the tokenfactory `DenomAllowList` membership check via `IsInDenomAllowList` on both sender and receiver. However, the older legacy versions (`v555`, `v562`, `v580`) call `p.bankKeeper.SendCoins(...)` directly, skipping the msg-server-level allow-list check entirely.

### Finding Description
For any tokenfactory denom, an admin can restrict transfers to a specific allow-list via `MsgSetDenomAllowList`/`SetDenomAllowList`. The intended enforcement point is `msgServer.Send`, which explicitly checks both the sender and receiver against `IsInDenomAllowList` before calling the underlying `SendCoins` keeper method: [1](#0-0) 

The core `SendCoins`/`AddCoins`/`SubUnlockedCoins` keeper primitives do **not** themselves re-check the allow-list; the check is only applied at the message-server layer (`msgServer.Send`, `msgServer.MultiSend`): [2](#0-1) [3](#0-2) 

The current bank precompile correctly re-implements this check by constructing a `MsgSend` and dispatching it through `p.bankMsgServer.Send`, which internally performs the `IsInDenomAllowList` check: [4](#0-3) 

But the older legacy precompile implementations bypass the msg server and call the raw `SendCoins` keeper method directly, which — per the analysis above — performs no allow-list check: [5](#0-4) [6](#0-5) [7](#0-6) 

This is analogous to the Nextcloud Deck CVE-2021-37631 pattern: an authorization/membership check (there, Circle membership; here, tokenfactory `DenomAllowList` membership) is correctly enforced on one access path (`MsgSend`/`MsgMultiSend`, and the newer precompile path) but silently omitted on an alternate reachable path (the legacy precompile `send` implementations), letting unauthorized parties bypass the restriction.

### Impact Explanation
If the legacy bank precompile versions (`v555`/`v562`/`v580`) remain selectable/reachable at runtime (e.g., via historical-block EVM replay/versioned precompile dispatch, which is the reason these files exist alongside the current version), any ERC20 pointer contract holder can call `send` to transfer a tokenfactory denom that has an active `DenomAllowList` to or from an address that is explicitly NOT in the allow-list — completely defeating the denom's access-control invariant. This is an unauthorized-transfer-via-precompile bug, matching the "unauthorized transfer via precompile or pointer" impact category, since token issuers rely on `DenomAllowList` for regulatory/whitelisting guarantees (e.g., compliance-gated or restricted-distribution tokens).

### Likelihood Explanation
Exploitability depends on whether the versioned legacy precompile files (`v555`, `v562`, `v580`) are still dispatched for any live/replayable execution path (the presence of a `legacy` version-selection mechanism, seen in files like `v601`–`v67` which explicitly reference "legacy" behavior, indicates these are kept for backward-compatible/historical block replay). I was not able to fully confirm from the index whether these specific old versions are still routable in current mainnet execution or are strictly historical/replay-only, which limits certainty on live exploitability today. If they are reachable in any live dispatch table (not purely historical replay), the bug is trivially and permissionlessly triggerable by any pointer holder in one transaction.

### Recommendation
Either remove dispatch of the `v555`/`v562`/`v580` legacy bank precompile paths from any live execution route, or patch them to route through `bankMsgServer.Send` (or explicitly call `IsInDenomAllowList` for both sender and receiver) before invoking `SendCoins`, matching the behavior of the current precompile and `v601`+ legacy versions.

### Proof of Concept
1. Tokenfactory denom `factory/{creator}/foo` has `DenomAllowList` set to `{A, B}` via `SetDenomAllowList`.
2. Deploy/obtain the ERC20 native pointer contract for `factory/{creator}/foo`, and ensure the EVM execution path resolves to the legacy bank precompile version (`v555`/`v562`/`v580`).
3. From the pointer contract, call `send(A, C, "factory/{creator}/foo", amount)` where `C` is NOT in `{A, B}`.
4. Because this path calls `p.bankKeeper.SendCoins` directly (see `precompiles/bank/legacy/v555/bank.go:198-204`), the transfer succeeds despite `C` not being allow-listed, whereas the same call through `MsgSend` or the current precompile (`precompiles/bank/bank.go:230-245`) would fail with `"is not allowed to receive funds"`.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
