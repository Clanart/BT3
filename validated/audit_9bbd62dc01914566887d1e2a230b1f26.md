## Title
Unauthenticated `payout_payer_operator_xonly_pk` Attribution via Malleable OP_RETURN Output Not Covered by SIGHASH_SINGLE|ANYONECANPAY - (File: `core/src/verifier.rs`, `core/src/builder/transaction/operator_reimburse.rs`)

## Summary
The withdrawal/payout transaction's user signature is enforced to use `SIGHASH_SINGLE|ANYONECANPAY` [1](#0-0) . Under this sighash type, only input 0 and its *corresponding* output (output index 0, the user payout output) are cryptographically committed; the anchor output and the OP_RETURN output carrying the fronting operator's `xonly_pk` [2](#0-1)  are **not** covered by the signature. The verifier later determines which operator is credited for having funded ("fronted") a withdrawal purely by reading that unauthenticated OP_RETURN field from whatever transaction actually confirms on-chain [3](#0-2) , and stores it as the `payout_payer_operator_xonly_pk` used later to gate reimbursement [4](#0-3) .

## Finding Description
Because the OP_RETURN output is outside the signed message, anyone who observes the honest operator's broadcast payout transaction in the mempool (same `in_outpoint`, same user output) can construct and rebroadcast (e.g. via a higher-fee RBF-style replacement) an alternate version of the same transaction that keeps input 0 and output 0 identical (so the existing valid `input_signature` still verifies) but swaps the OP_RETURN payload for a different `xonly_pk`. If this attacker version confirms instead of the original, `update_finalized_payouts` records the attacker's (or an arbitrary/garbage) `xonly_pk`, or `None`, as the payer for that withdrawal [5](#0-4) .

The equality this breaks is: **operator credited with fronting a payout == the operator that actually paid the user.** Downstream, `validate_payer_is_operator`/`is_kickoff_malicious` gate reimbursement strictly on the DB-recorded `payout_payer_operator_xonly_pk` matching the signer's own key [6](#0-5) , and any kickoff whose embedded operator key doesn't match the recorded payer is treated as malicious [7](#0-6) . If the OP_RETURN field is overwritten by a third party with garbage/`None`, the honest operator who actually funded the user's output permanently loses the ability to be recognized as payer for that withdrawal, since the recorded value can never again equal their key.

## Impact Explanation
This maps to "an honest operator permanently unable to be reimbursed" (Critical), since the honest operator spent real BTC funding the user's payout output, but the on-chain record of who fronted it can be hijacked/erased by any unprivileged party who can observe and replace the mempool transaction before confirmation — no operator/verifier/aggregator role is required to perform the replacement itself.

## Likelihood Explanation
Requires only mempool visibility and standard fee-bumping/replacement ability (no signing key, no protocol role) to replace the pending payout transaction with a variant carrying a different OP_RETURN. This is a plausible, low-privilege network-level race condition given typical Bitcoin mempool propagation and RBF support.

## Recommendation
Bind the fronting-operator attribution to the same cryptographic commitment as the payout itself: either (a) require the user's signature to cover all outputs (e.g. use `SIGHASH_ALL` or a taproot annex/tapscript commitment including the OP_RETURN), or (b) do not derive payer attribution from an unauthenticated OP_RETURN at all — instead require the operator to additionally sign a commitment (e.g., in the subsequent kickoff transaction, already partly used) that is verifiable against the exact payout transaction's inputs and full output set, rejecting any payout tx whose non-committed outputs were altered from what the intended operator constructed and broadcast.

## Proof of Concept
1. Operator A calls `withdraw()` to construct and broadcast `payout_tx_A`: input = withdrawal UTXO + `user_sig` (SIGHASH_SINGLE|ANYONECANPAY), output0 = user's payout, output1 = anchor, output2 = OP_RETURN(A.xonly_pk) [8](#0-7) [9](#0-8) .
2. Attacker observes `payout_tx_A` in the mempool, extracts input 0 + output 0 + `user_sig`, and constructs `payout_tx_B`: identical input 0/output0/witness, but replaces output2's OP_RETURN with attacker's own `xonly_pk` (or garbage), and rebroadcasts with a higher fee/RBF.
3. Because the signature only commits to input 0 and output 0 under `SinglePlusAnyoneCanPay`, `payout_tx_B` is fully valid and can be mined instead of `payout_tx_A`.
4. `update_finalized_payouts` scans the confirmed block, finds `payout_tx_B`, and records the attacker's key (or `None`) as `payout_payer_operator_xonly_pk` for that withdrawal [10](#0-9) .
5. Operator A's subsequent kickoff attempt to be reimbursed fails `validate_payer_is_operator`/`is_kickoff_malicious` because the recorded payer no longer matches A's key [6](#0-5) [7](#0-6) , permanently denying A reimbursement for BTC it actually fronted.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
