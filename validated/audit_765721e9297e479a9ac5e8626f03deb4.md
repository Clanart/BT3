### Title
Diff-header parsing in `parse_diff_into_files` silently drops unicode/quoted-path and ambiguous rename diffs from security review - (File: plugins/security-guidance/hooks/gitutil.py)

### Summary
`get_git_diff`/`_git_diff_range` invoke `git diff` using the shared `GIT_CMD` prefix, which does **not** set `core.quotePath=false`, unlike `_git_name_only` and `_git_status_porcelain` which explicitly do so for the same reason. `parse_diff_into_files` (and its sibling `extract_file_paths_from_diff`) then parse the resulting diff text with a naive regex `^a/(.+?) b/(.+)$` that assumes an unquoted, unambiguous `diff --git a/PATH b/PATH` header line. Any file whose repo-relative path contains non-ASCII characters (or other C-quote-triggering bytes) produces a quoted header line that the regex never matches, silently excluding that file's diff from the LLM/pattern security review pipeline.

### Finding Description
`GIT_CMD` is defined once and reused by every git subprocess call in `gitutil.py`: [1](#0-0) 

Two call sites explicitly add `-c core.quotePath=false` because they know the default quoting would corrupt path parsing of non-ASCII/space filenames: [2](#0-1) [3](#0-2) 

However, the diff that actually feeds the security review — `get_git_diff` (used by the Stop-hook review, commit review, and push-sweep) and `_git_diff_range` (used by push-sweep range diffs) — build their `git diff` command from bare `GIT_CMD` without disabling quotePath: [4](#0-3) [5](#0-4) 

Git's default `core.quotePath=true` C-quotes any path containing non-ASCII bytes (or other special bytes) and wraps it in double quotes in the `diff --git a/PATH b/PATH` header line (e.g. `diff --git "a/caf\303\251.py" "b/caf\303\251.py"`). `parse_diff_into_files` (and `extract_file_paths_from_diff`) parse that header with: [6](#0-5) 

The regex `^a/(.+?) b/(.+)$` requires the line to start with the literal, unquoted `a/`. A quoted header starts with `"a/...` instead, so `header_match` is `None` and the loop does `continue`, dropping that file's entire diff — no warning, no fallback, no log entry — from the list returned to the reviewer. This means an attacker who can get a non-ASCII-named source file (e.g. `café.py`, or any file with Unicode/Cyrillic/Emoji characters in its name or a containing directory) modified in the session's diff can have that file's malicious content bypass both `analyze_code_security`/`agentic_review` (Stop hook) and the commit/push review, since none of them ever see it in `parse_diff_into_files`'s output.

A second, related header-parsing weakness exists even for ASCII paths: because a rename's `diff --git a/OLD b/NEW` line concatenates `OLD` and `NEW` with a literal `" b/"` separator, and the regex is non-greedy, a crafted `OLD` path containing the literal substring `" b/"` (e.g. a directory legitimately named `x b` inside a rename source, or one placed to contain `"node_modules/"` as leaked context) can cause the regex to split at the wrong `" b/"` occurrence. The reconstructed `file_path` value keeps the correct trailing basename/extension (so extension/basename checks in `_is_reviewable_source` still pass), but the `SKIP_PATH_PATTERNS` substring check operates over the full (corrupted) string and can be poisoned by attacker-chosen `OLD`-path fragments now embedded in the parsed `file_path`, causing `_is_reviewable_source` to incorrectly classify a genuinely new/renamed file as vendored/build output and skip it, e.g. renaming from `"x b/node_modules/foo.txt"` to `malicious.py` with content changes in the same commit. This is a lower-confidence secondary variant of the same root cause (fragile string-based header parsing instead of using git's machine-readable diff modes).

Both variants are reachable purely through the intended flow: `security_reminder_hook.py` imports and calls `parse_diff_into_files`/`extract_file_paths_from_diff` on the output of `get_git_diff`/`_git_diff_range` as part of the Stop-hook review, commit review, and push-sweep pipelines: [7](#0-6) 

No existing validation catches this: `_diff_pathspec` only guards against paths *outside* `cwd` for restricting the diff invocation, it does not validate or re-normalize the paths that come back out of `git diff`'s own text output, and there is no fallback/format-detection for quoted or C-escaped paths anywhere in the parsing code.

### Impact Explanation
This is a Security-control bypass: an attacker who can influence what files get written/renamed during a Claude Code session (via prompt injection from repo content, malicious PR instructions, or by simply naming files/directories with non-ASCII characters as part of legitimate-looking work) can have arbitrary malicious code changes silently excluded from the Stop-hook LLM security review, the commit-review, and the push-sweep review — with no error, warning, or metric indicating the content was skipped. This defeats the entire purpose of the security-guidance plugin for that file: dangerous code (secrets, injection, backdoors) introduced under a Unicode-named path is never shown to the reviewer.

### Likelihood Explanation
- Preconditions: only requires a file with a non-ASCII (or otherwise quote-triggering) name to be part of the diff being reviewed — a routine, unprivileged scenario (any repository using non-English filenames, or an attacker naming a payload file with Unicode characters).
- No admin/maintainer privilege, leaked keys, or social engineering required — purely repo content plus normal editing/committing flow.
- Fully repeatable/deterministic: git's `core.quotePath` default behavior is stable and well-documented; the regex mismatch is 100% reproducible for any qualifying filename.
- The rename-ambiguity variant requires a more deliberately crafted rename source path, making it lower likelihood but still fully attacker-controllable content.

### Recommendation
- Add `-c core.quotePath=false` to the `git diff` invocations in `get_git_diff` and `_git_diff_range` (or fold it into `GIT_CMD` globally), matching the treatment already given to `_git_name_only`/`_git_status_porcelain`.
- Stop parsing the human-oriented `diff --git a/... b/...` header with a regex entirely. Use `git diff --name-only -z`/`--raw -z` (NUL-delimited, unambiguous) to get the authoritative file list, and correlate that with per-file hunks (e.g., via `git diff` per-path or splitting on the raw `--z` boundaries), rather than relying on textual reconstruction of paths from a diff header that can be quoted or structurally ambiguous.
- If the header-regex approach must be kept short-term, at minimum detect and reject/unquote C-quoted (`"..."`) header lines using `git`'s C-quoting rules before applying the `a/`/`b/` split, and add a defensive check that "no header line matched but the raw diff --git count > 0" triggers a fail-closed (block or fallback to full review) rather than fail-open (silent skip).

```python
    Distinguishing failure from success-with-empty-diff matters: the push-sweep
```

```python
def parse_diff_into_files(diff_output):
    """
    Parse unified diff output into a list of (file_path, diff_content) tuples.
    Only includes files with source code extensions.
    """
    if not diff_output or not diff_output.strip():
        return []

    files = []
    file_diffs = diff_output.split("diff --git ")

    for file_diff in file_diffs:
        if not file_diff.strip():
            continue

        # Extract filename from first line: "a/path/to/file b/path/to/file"
        lines = file_diff.split('\n')
        header_match = re.match(r'^a/(.+?) b/(.+)$', lines[0])
        if not header_match:
            continue

        file_path = header_match.group(2) or header_match.group(1) or ''

        # Filter to source code files only
        if not _is_reviewable_source(file_path):
            continue
```
