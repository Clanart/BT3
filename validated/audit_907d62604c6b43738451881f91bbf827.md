### Title
PedPoP accepts identity encryption keys, making ECDH shared point the identity and leaving secret shares encrypted under a publicly derivable key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the Jenkins advisory (a missing validation check reachable by a low-privilege party), PedPoP never validates that a participant's registered encryption key is non-identity. `EncryptionKeyMessage::read` parses `enc_key` with `Ciphersuite::read_G`, which only enforces canonical/torsion-free encoding — unlike FROST's `Curve::read_G`, which explicitly rejects the identity. A malicious DKG participant registers `enc_key = identity`; every `EncryptedMessage` addressed to them then derives its ChaCha20 cipher key from `ecdh = msg.key * identity = identity`, a constant anyone can compute. The "encrypted" secret shares are recoverable by any observer of the wire bytes.

### Finding Description [1](#0-0) 
`EncryptionKeyMessage::read` reads `enc_key` via `C::read_G` with no identity rejection. [2](#0-1) 
`Ciphersuite::read_G` accepts any canonical, torsion-free point — including the identity.

Contrast with FROST's hardened decoder: [3](#0-2) 
`Curve::read_G` rejects identity points; PedPoP does not use it (it operates on the generic `Ciphersuite` trait). [4](#0-3) 
`ecdh(private, public) = public * private`. With `enc_key = identity`, any ephemeral `msg.key` yields `key * identity = identity`. [5](#0-4) 
`cipher()` derives the ChaCha20 key solely from `context` and the ECDH point (with a static IV). When the ECDH point is `identity`, the cipher key is a deterministic, publicly computable value.

The receiver-side flow: [6](#0-5) 
`decrypt()` computes `ecdh(&self.enc_key, msg.key)` and applies the keystream. When the recipient's registered key is identity, every ciphertext to them is XORed with a public keystream.

The malicious participant registers their identity key in round 1: [7](#0-6) 
`Decryption::register` stores `msg.enc_key` with no validity check. [8](#0-7) 
`encrypt()` ECDHs against `self.decryption.enc_keys[&participant]` — the attacker-supplied identity key — and `generate_secret_shares` uses it for all outgoing shares [9](#0-8) .

### Impact Explanation
The per-participant secret shares `f_j(i)` sent to the malicious participant are protected only by this ECDH-derived stream cipher. With `enc_key = identity`, the ECDH shared point is the group identity for every message regardless of the ephemeral `msg.key`, so `cipher(context, identity)` is computable by anyone who knows the public `context`. Any party observing the transmitted `EncryptedMessage` ciphertexts (the library explicitly encrypts shares because the channel is only assumed authenticated, not confidential) recovers the plaintext shares destined for the malicious slot — shares that reveal each honest sender's polynomial evaluation at the attacker's index. This is a protocol-confidentiality break driven purely by a missing input-validation check on attacker-supplied bytes fed through `EncryptionKeyMessage::read` → `register` → `encrypt`. Severity: Medium (disclosure of DKG share material to channel observers; exploitation requires the attacker to be a DKG participant and an observer of the authenticated channel).

### Likelihood Explanation
Any unprivileged DKG participant can set `enc_key = identity` in their broadcast `EncryptionKeyMessage`; no PoK is ever verified over `enc_key` (the Schnorr PoK covers `commitments`, not the encryption key — see `verify_r1`, which only batch-verifies `msg.sig` against `msg.commitments[0]`). The identity point is a canonical torsion-free encoding, so `read_G` accepts it, `Decryption::register` stores it, and all honest senders' `encrypt()` calls silently produce publicly-decryptable ciphertexts. The only requirement beyond participation is that ciphertexts traverse a channel observable by third parties — precisely the threat model the encryption layer exists for.

### Recommendation
Reject the identity element when parsing or registering encryption keys: either deserialize `enc_key` through an identity-rejecting reader (as `Curve::read_G` does) or add an `is_identity` check in `Decryption::register`/`EncryptionKeyMessage::read`. For defense in depth, also reject identity `msg.key` values in `EncryptedMessage::read`/`decrypt`, since `msg.key = identity` produces the same degenerate ECDH point. Optionally, bind `enc_key` into the round-1 PoK transcript so a participant proves possession of their encryption key.

### Proof of Concept
```rust

// identity encryption key. The Commitments PoK is over `commitments`, not
// `enc_key`, so this is fully valid:

msg_bytes.extend(C::G::identity().to_bytes().as_ref()); // enc_key = identity
let msg = EncryptionKeyMessage::<C, Commitments<C>>::read(
    &mut msg_bytes.as_ref(), params).unwrap(); // accepted by read_G

// Honest participant i, in generate_secret_shares -> encrypt():
//   ecdh = msg.key * identity = identity
//   cipher key = transcript("DKG Encryption v0.2" | context | "shared_key"=identity)
// An observer who knows `context` reconstructs the identical ChaCha20 keystream
// and XORs it against the transmitted ciphertext to recover SecretShare<F>
// bytes — participant k's secret share plaintext for every honest sender.
```

One caveat: this was derived from library-level reachability (any participant's broadcast bytes reach `EncryptionKeyMessage::read`); whether Serai's deployment transports DKG messages over a confidential channel determines whether exploitation leaks anything in practice — but the encryption layer's existence indicates confidentiality is not assumed of the channel.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
