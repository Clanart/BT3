### Title
HMAC Collision in App Proxy Signature Verification via Missing Delimiter - (File: lib/shopify_app/controller_concerns/app_proxy_verification.rb)

### Summary

### Finding Description
`ShopifyApp::AppProxyVerification#calculated_signature` builds the string that is HMAC-signed by concatenating each `key=value` query pair with **no delimiter between pairs**: [1](#0-0) 

```ruby
def calculated_signature(query_hash_without_signature)
  sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

  OpenSSL::HMAC.hexdigest(
    OpenSSL::Digest.new("sha256"),
    ShopifyApp.configuration.secret,
    sorted_params,
  )
end
```

This is exactly the "lack of padding between items" flaw described in the external report: `bytes.sort()` + concatenation with no separator lets two structurally different inputs serialize to an identical byte string, and therefore hash/HMAC to the same value. Here, because query params are simply `key=value` strings concatenated directly (`.sort.join` with no separator argument), a multi-key input and a single-key input can serialize to the identical string.

Concretely, given legitimate params `{"a" => "12", "b" => "3"}`, `collect` produces `["a=12", "b=3"]`, sorted and joined to `"a=12b=3"`. An attacker who has observed *any* valid app-proxy request (query string + `signature`, which travel in a plain URL and are not secret — e.g., visible in browser history, Referer headers, shared links, or server/proxy logs) can construct a **different** request with a single param `{"a" => "12b=3"}`. `Rack::Utils.parse_query` happily parses a value containing `=`, and `collect` on this single pair also yields `"a=12b=3"` — identical to the original concatenation. Because `query_string_valid?` recomputes the signature purely from the request's own query string using this collidable serialization, and compares it via `ActiveSupport::SecurityUtils.secure_compare`, the previously-observed signature is accepted for the new, semantically different, param set: [2](#0-1) 

### Impact Explanation
This allows an unauthenticated party to reuse a previously-observed, non-secret `(query, signature)` pair to construct a **different forged, accepted signed request** to any app-proxy controller (`ShopifyApp::AppProxyVerification`) — passing the app's built-in authenticity check with attacker-chosen parameter structure that differs from what actually produced the original signature. This directly matches the accepted "forged signed request" impact class: the app relies on `query_string_valid?` as its authenticity boundary for App Proxy requests [3](#0-2) , and that boundary can be bypassed via hash-input collision without knowledge of `ShopifyApp.configuration.secret`.

### Likelihood Explanation
App Proxy endpoints are public HTTP endpoints (no session/auth required beyond signature check), reachable directly by any anonymous requester, and prior valid signed URLs are routinely observable (they appear in plaintext in storefront-generated links). Building a colliding query requires only ordinary URL-encoding knowledge (encoding `=` inside a value), no cryptographic capability. This is a realistic, low-effort forgery path against a shipped, always-active controller concern used by any app that mounts app-proxy controllers.

### Recommendation
Fix `calculated_signature` to avoid ambiguous concatenation, mirroring the referenced patch's approach: include an unambiguous delimiter/length-prefix between fields before hashing (e.g., hash each `key=value` pair separately and then hash the concatenation of those digests, or join pairs with a delimiter guaranteed not to appear un-encoded, or include the count/length of each field). At minimum, join sorted pairs with a separator character that is escaped/rejected in both keys and values before concatenation.

### Proof of Concept
1. Legitimate request A: query `?a=12&b=3&signature=<SIG>` where `SIG = HMAC(secret, "a=12b=3")` (as computed by `calculated_signature`).
2. Attacker observes `SIG` from request A (e.g., via logs/Referer/shared link).
3. Attacker crafts request B: query `?a=12b%3D3&signature=<SIG>` (single key `a` with URL-encoded value `12b=3`).
4. Server-side, `Rack::Utils.parse_query` yields `{"a" => "12b=3"}`; `calculated_signature` computes `"a=12b=3"` — identical string to request A — producing the same `SIG`.
5. `query_string_valid?` returns `true` for request B even though its parameter structure is entirely different from request A, demonstrating signature verification bypass via HMAC input collision.
