No vulnerability found for this question.

**Reasoning:** The premise — that replaying the same GRANDPA finality proof/target height would refresh the state-commitment update time and thereby corrupt timeout-eligibility gating — doesn't hold, because both the EVM and Substrate storage paths explicitly guard against re-storing (and thus re-timestamping) an already-committed height.

On the EVM side, `HandlerV2.handleConsensus` short-circuits before touching any storage if the consensus proof doesn't advance state: `if (keccak256(previousState) == keccak256(verifiedState)) return;`, and even when intermediates are non-empty, `host.storeStateMachineCommitment` (which is what would update `_stateCommitmentsUpdateTime`) is only invoked when `intermediate.height > latestHeight` — a strictly-greater-than height check that a replay of a proof for an already-finalized target cannot satisfy. [1](#0-0) 

On the Substrate/pallet-ismp side, `update_client` explicitly skips both the state-machine-height progression and the update-time refresh for heights that are not strictly newer than the previous latest height, and separately skips any height for which a commitment already exists in storage: `if previous_latest_height > commitment_height.height { continue; }` … `if host.state_machine_commitment(state_height).is_ok() { continue; } … host.store_state_machine_update_time(state_height, host.timestamp())?;`. So a no-op re-verification of `verify_grandpa_finality_proof` for a `target` that has already been finalized and stored produces intermediate state that is skipped entirely — `store_state_machine_update_time` is never called again for that height. [2](#0-1) 

Consequently, the timestamp read by `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` via `host.stateMachineCommitmentUpdateTime(message.height)` (and its Substrate analogue `state_machine_update_time` used in `verify_delay_passed`) is fixed at first-commit time for that height and cannot be refreshed by a subsequent no-op resubmission of the same proof/target. [3](#0-2) [4](#0-3) 

Since the described attack path (resubmit proof → bump update time → distort challenge-period gate for pending timeouts) is already blocked by these existing guards on both chains, the claim does not demonstrate a bypassable invariant.
