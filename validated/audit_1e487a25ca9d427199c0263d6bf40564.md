### Title
Access-list slot removal on revert desyncs `Addresses` indices, causing an out-of-bounds panic (chain halt / node crash) - ([File: giga/deps/xevm/state/journal.go])

### Summary
`accessListAddSlotChange.revert()` removes an entry from the shared `Slots` slice by splicing it out (`append(slotsList[:idx], slotsList[idx+1:]...)`), which shifts every element after `idx` down by one position. It updates the `Addresses` map entry only for the address being reverted, leaving every other address's cached index into `Slots` stale — exactly the same class of bug as the reported Union Finance `cancelVouch()` issue, where an array is compacted by removing a middle element while an auxiliary index map that references positions in that array is left un-updated.

### Finding Description
The transient EIP-2929/2930 access list is stored as: [1](#0-0) 

`Addresses[addr]` stores the index of `addr`'s slot-set inside the parallel `Slots` slice. `AddSlotToAccessList` assigns new indices by appending to `Slots` (`al.Addresses[addr] = len(al.Slots)`): [2](#0-1) 

When an `accessListAddSlotChange` journal entry is reverted (e.g. because a nested EVM call/sub-context reverts), and the reverted slot was the only slot recorded for that address, the code removes the now-empty entry from the middle of `Slots` by splicing: [3](#0-2) 

This shifts down every `Slots` element with index greater than the removed `idx`, but only `Addresses[e.address]` is set to `-1`. No other address's `Addresses[otherAddr]` entry is corrected, so any address whose index was greater than the removed one now points to the wrong (or out-of-range) slot map.

Crucially, the read path that consumes this index performs no bounds check: [4](#0-3) 

If the stale index equals the new (shrunk) length of `Slots`, `al.Slots[idx][slot]` on line 28 indexes out of range and panics. This can be triggered purely by an ordinary EVM transaction: any transaction whose execution warms multiple addresses with slots (e.g. via `SLOAD`/`SSTORE` in different call frames) and then reverts one of the earlier-created slot entries (e.g., via a nested `REVERT`, an out-of-gas sub-call, or a failing `CALL`/`CREATE`) while a later-created address's slot entry survives, will desynchronize the two structures and can panic on the next warm/cold check for that later address.

### Impact Explanation
`SlotInAccessList` is invoked from core EVM opcode gas-accounting logic (SLOAD/SSTORE/CALL family) during ordinary transaction execution inside consensus state transition, not just in RPC-only code paths. An unrecovered panic there during block processing (as opposed to a safely isolated JSON-RPC `eth_call`) would crash the node executing the block, and because this is deterministic given the same EVM bytecode, every honest validator that includes/executes the transaction would panic identically — producing a chain-wide halt (all validators crash or refuse to progress) rather than a state fork. This satisfies the "validator halt" / "crash of default node" impact bar in the rules. Even absent a hard panic (i.e., in cases where the stale index happens to still be in range but points to a different slot map), the desync can silently corrupt warm/cold access-list bookkeeping for unrelated addresses within the same transaction, misclassifying storage access as "warm" vs "cold" and altering EIP-2929 gas costs — a fee/gas-accounting integrity issue.

### Likelihood Explanation
Any unprivileged EVM transaction sender can construct a contract-call sequence that: (1) warms address A with a slot, (2) later warms address B with a slot (assigned a higher `Slots` index), and (3) reverts only the `AddSlotToAccessList` call for A (e.g., by having A's warming occur inside a sub-call that gets reverted via a failing external call, `REVERT` opcode, or running out of gas) while B's slot-access change is kept. This requires only standard multi-call, revert-capable EVM bytecode (e.g., a Solidity `try/catch`, or a low-level `call` whose failure is not bubbled up) — well within reach of a single crafted transaction from any transaction sender, no special privileges needed.

### Recommendation
Do not use index-shifting splice removal for `Slots`. Either:
- Never physically remove or reorder slots on revert; instead keep the empty `map[common.Hash]struct{}{}` in place at its original index and only clear `Addresses[addr] = -1`, or
- If removal must be O(1) via swap-with-last (as originally intended for `cacheKV`-style journaling), correctly update the `Addresses` entry of whichever address previously owned the slot now moved into position `idx`, mirroring the same fix recommended for the original Union Finance report (swap-and-fixup the back-reference, not just delete the moved entry's old reference).
Additionally, `SlotInAccessList` should bounds-check `idx` against `len(al.Slots)` before indexing, to fail safe (treat as cold/absent) rather than panic, as defense in depth.

### Proof of Concept
Conceptual sequence (mirrors `TestAccessListAddSlotChangeRevert`'s state but with two addresses):
1. Address A calls `AddSlotToAccessList(A, S1)` → `Addresses[A] = 0`, `Slots = [{S1}]`, journal records `accessListAddSlotChange{A, S1}`.
2. Address B calls `AddSlotToAccessList(B, S2)` → `Addresses[B] = 1`, `Slots = [{S1}, {S2}]`, journal records `accessListAddSlotChange{B, S2}` (this call happens in a call frame that will succeed and NOT be reverted).
3. The call frame that touched A reverts (e.g., nested call to A failed). The EVM journal reverts entry 1 first (LIFO): B's entry is *not* reverted because it belongs to a still-successful frame — but suppose instead the ordering is such that A's `accessListAddSlotChange` entry is reverted while B's remains intact (achievable across nested call/revert boundaries where A's frame is nested inside and reverts, while B's frame is a sibling that commits): `accessListAddSlotChange{A,S1}.revert()` runs, `idx=0`, `slots={S1}`, deletes S1, `len(slots)==0`, so `Slots = append(Slots[:0], Slots[1:]...)` = `[{S2}]`, `Addresses[A] = -1`. Now `Slots` has length 1 but `Addresses[B]` is still `1`.
4. Any subsequent `SlotInAccessList(B, S2)` call within the same transaction executes `al.Slots[1][S2]` on a slice of length 1 → index out of range → panic during EVM opcode gas computation, propagating up through block/transaction execution.

This confirms the root cause: the index-compacting removal in `giga/deps/xevm/state/journal.go` lines 97-107 fails to fix up other addresses' stale indices in `Addresses`, and the unguarded read in `accesslist.go` line 28 turns that inconsistency into an exploitable panic.

```go
func (s *DBImpl) SlotInAccessList(addr common.Address, slot common.Hash) (addressOk bool, slotOk bool) {
	al := s.getCurrentAccessList()
	idx, addrOk := al.Addresses[addr]
	if addrOk && idx != -1 {
		_, slotOk := al.Slots[idx][slot]
		return addrOk, slotOk
	}
	return addrOk, false
}
```

```go
func (s *DBImpl) AddSlotToAccessList(addr common.Address, slot common.Hash) {
	al := s.getCurrentAccessList()
	idx, addrPresent := al.Addresses[addr]
	if !addrPresent {
		s.AddAddressToAccessList(addr)
	}
	if !addrPresent || idx == -1 {
		// Address not present, or addr present but no slots there
		al.Addresses[addr] = len(al.Slots)
		slotmap := map[common.Hash]struct{}{slot: {}}
		al.Slots = append(al.Slots, slotmap)
		s.journal = append(s.journal, &accessListAddSlotChange{address: addr, slot: slot})
		return
	}
```
