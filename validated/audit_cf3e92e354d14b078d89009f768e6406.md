### Title
Inverted `isActive` check in `unvote()` permanently locks vlMGP for users who voted on a pool later deactivated - (File: wombat/WombatBribeManager.sol)

### Summary
The reported Foundation bug is a "locked funds via another open commitment" bug class: a user's balance is unavailable for a needed action because it is tied up in a separate, still-open commitment (an NFT offer), and the protocol provides no path to release it automatically. The Magpie protocol has a structurally identical pattern between `WombatBribeManager.vote()`/`unvote()` and `VLMGP.startUnlock()`: a user's vlMGP is "locked" for governance voting, and `startUnlock()` explicitly refuses to let a user cool-down/unlock MGP that is still counted as voted, requiring the user to first call `unvote()` to release the commitment.

### Finding Description
`VLMGP.startUnlock()` blocks unlocking of MGP whose amount would fall below the caller's outstanding governance vote total: [1](#0-0)  The only way to reduce `userTotalVotedInVlmgp[msg.sender]` is to call `WombatBribeManager.unvote()`.

However, `unvote()` is gated by `if(!pool.isActive) revert PoolNotActive();` [2](#0-1)  This is the inverse of what the function's own docstring promises: *"Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing."* As written, `unvote()` only succeeds while the pool is still active, and reverts precisely in the scenario the comment says it is meant to handle — once a pool is deactivated.

Once a pool a user previously voted for is deactivated (a normal, non-malicious protocol operation such as delisting an LP or migrating a rewarder), that user's `userVotedForPoolInVlmgp[user][pool]` amount can never be reduced again: `unvote()` reverts, and `vote()` also requires `pool.isActive` to move votes in or out [3](#0-2) . Since `userTotalVotedInVlmgp[user]` therefore permanently retains that stuck amount, `VLMGP.startUnlock()` will permanently revert with `NotEnoughLockedMPG` for the corresponding portion of the user's vlMGP.

### Impact Explanation
This produces a permanent freeze of a portion of the user's MGP, structurally identical to the referenced bug's "locked balance due to an unrelated open commitment," except here there is no recovery path at all (the original bug at least allowed eventual expiration of the offer; here there is no expiration and no way to voluntarily cancel). Any ordinary wallet that voted for a pool that is later deactivated loses the ability to ever `startUnlock()`/`unlock()` the MGP amount equal to their stuck vote, unless the pool is later reactivated by an admin (outside the user's control).

### Likelihood Explanation
Reachable purely via ordinary wallet actions: (1) call `vote()` to allocate vlMGP votes to a pool, (2) protocol operator deactivates that pool during normal maintenance (not a malicious act — no special exploitation of admin powers required, just a normal lifecycle event), (3) any subsequent call to `unvote()` or `startUnlock()` for that stuck amount reverts indefinitely.

### Recommendation
Invert or otherwise fix the guard in `unvote()` so that unvoting is always permitted regardless of `pool.isActive` (or specifically permitted when the pool is inactive, per the docstring's stated intent), so users are never permanently prevented from releasing votes to unlock their vlMGP. Additionally, consider having `VLMGP.startUnlock()` auto-release/adjust stale votes for deactivated pools, mirroring the recommended fix in the original report (auto-cancel the conflicting commitment rather than requiring a separate, potentially blocked, user transaction).

### Proof of Concept
1. User locks MGP into vlMGP and calls `WombatBribeManager.vote()` to allocate votes to `PoolA`, increasing `userTotalVotedInVlmgp[user]` [4](#0-3) .
2. Protocol admin deactivates `PoolA` (sets `isActive = false`) as part of normal pool lifecycle management (code for this admin function was not directly fetched, but `pool.isActive` is referenced as a state field used across `vote`/`unvote` guards).
3. User calls `unvote(PoolA)` to release their vote; the call reverts with `PoolNotActive()` because of the `if(!pool.isActive)` check [5](#0-4) .
4. User calls `VLMGP.startUnlock()` for an amount that would bring `totalLockAfterStartUnlock` below `userTotalVotedInVlmgp[user]`; it reverts with `NotEnoughLockedMPG` [6](#0-5) .
5. The user's MGP corresponding to the stuck vote is now permanently unable to be unlocked through any user-controlled call.

Note: I was unable to fetch the exact admin function that sets `Pool.isActive` (e.g., a `removePool`/`setPool` function) before running out of tool iterations, so the exact mechanics of pool deactivation are inferred from the `isActive` field usage in `vote()`/`unvote()`/`getPoolsLength()` rather than directly confirmed. A Devin session with full file access should verify the pool-deactivation admin function to confirm there is no alternate unvote path.

    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
