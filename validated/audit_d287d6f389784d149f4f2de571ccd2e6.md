Based on my investigation, the strongest analog I found relates to how GitHub Desktop's git-credential-helper trust chain classifies a remote host as a "GitHub host" using **attacker-controlled data from the git server's own HTTP response**, and then uses that classification to kick off a privileged sign-in flow scoped to that untrusted host — a similar class of bug to the Sherlock finding, where a value/decision that should only be derived from trusted state (the seller/bull relationship) is instead derived from attacker-influenced input (the git server's `WWW-Authenticate` header).

### Title
Attacker-controlled `WWW-Authenticate` header from a git remote can force Desktop to classify an untrusted host as an "enterprise" GitHub endpoint and initiate a scoped OAuth sign-in flow for it - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper trampoline. `getEndpointKind()` decides whether the target host is `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'`. If none of the fast paths match, it inspects the `wwwauth[...]` values that Git forwards from the **remote server's own HTTP response** and, if any value contains `realm="GitHub"`, unconditionally classifies the host as `'enterprise'`: [1](#0-0) 

This classification is attacker-controlled: any HTTP(S) git remote (or a MITM/corporate proxy in front of one) can return a `401` with `WWW-Authenticate: Basic realm="GitHub"` and the check is satisfied without any further validation that the host is actually a real GitHub/GHE server.

### Finding Description
Once `endpointKind !== 'generic'` and there is no existing account matching that endpoint, `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`: [2](#0-1) 

`promptForGitHubSignIn` then routes non-`github.com` hostnames straight into the Enterprise sign-in flow and calls `setSignInEndpoint(origin)` with the attacker's own origin, bypassing `SignInStore.setEndpoint()`'s normal safeguards (`validateURL`, protocol checks, and connectivity checks against `getEnterpriseAPIURL`): [3](#0-2) 

Compare this to the legitimate GHE sign-in entry point, `SignInStore.setEndpoint()`, which validates the URL and rejects protocols/hosts before ever reaching the `Authentication` step: [4](#0-3) 

The credential-helper path skips all of that validation because it trusts the server-supplied `wwwauth[...]` realm string as proof the host is a GitHub-compatible endpoint. Once in the `Authentication` step, `authenticateWithBrowser()` builds an OAuth authorize URL from that same untrusted origin and opens it in the system browser: [5](#0-4) [6](#0-5) 

This is the same class of bug as the reported issue: a value that should only be set from a trusted source (here, "this host is really a GitHub/GHE endpoint," analogous to "this asset should go to the bull") is instead derived from attacker-controlled input (the `WWW-Authenticate` header from the remote/proxy, analogous to the manipulated settlement logic), and the resulting privileged action (initiating a GitHub Enterprise OAuth sign-in scoped to that host) executes without the checks that normally gate it.

### Impact Explanation
A malicious or compromised HTTPS git remote (or a network proxy/MITM sitting in front of any HTTPS remote a user clones/fetches) can, purely by returning a crafted `401 WWW-Authenticate: realm="GitHub"` response, cause Desktop to treat it as a legitimate GitHub Enterprise endpoint and surface Desktop's own native "Sign in to GitHub Enterprise" dialog scoped to the attacker's origin, entirely bypassing the URL validation path used everywhere else in the app for adding enterprise endpoints. If the OAuth/browser flow subsequently resolves, the resulting `Account` and its token get stored under the attacker's endpoint inside Desktop's normal account store, and future `requestOAuthToken`/API calls for that "enterprise" endpoint will be trusted by other parts of the app that key off `isGHE(endpoint)`/`isDotCom(endpoint)`.

### Likelihood Explanation
No local access or leaked credentials are required — the trigger is simply cloning/fetching from, or having a proxy in front of, an attacker-influenced HTTPS remote, which is squarely inside the "attacker controls a git remote/proxy response" category. The only conditions needed are: (1) the remote requires Basic auth over HTTPS, and (2) the user has no existing Desktop account already registered for that literal origin, which is the common case for a brand-new/unknown remote.

### Recommendation
Do not use the client-supplied `wwwauth[...]` realm string as sufficient evidence to classify an arbitrary host as an "enterprise" GitHub endpoint. At minimum, corroborate it with an actual API probe (the same `isGitHubHost(endpoint)` check already used as the fallback a few lines below) before routing into `promptForGitHubSignIn`, and ensure `setSignInEndpoint`/the credential-helper entry point applies the same URL validation (`validateURL`, protocol/host checks) that `SignInStore.setEndpoint()` enforces for manually-added enterprise accounts.

### Proof of Concept
1. Host an HTTPS git server (or place a MITM proxy in front of any HTTPS git URL) that responds to unauthenticated Git HTTP requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone or fetch from that URL when no existing account is registered for that origin.
3. Git invokes the trampoline credential helper; `getEndpointKind()` sees the forged `wwwauth[...]` value and returns `'enterprise'`.
4. `getCredential()` calls `ui.promptForGitHubSignIn(endpoint)`, which calls `dispatcher.beginEnterpriseSignIn()` and `setSignInEndpoint(origin)` for the attacker's host, skipping `SignInStore.setEndpoint()`'s validation, and shows Desktop's native GitHub Enterprise sign-in popup scoped to the attacker's origin.
5. If the user proceeds, `authenticateWithBrowser()` opens `getOAuthAuthorizationURL(attacker-origin, state)` in the browser and, on completion, an `Account` for the attacker's endpoint is created via `emitAuthenticate`/`fetchUser` and persisted by `AccountsStore`. [7](#0-6)

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}
