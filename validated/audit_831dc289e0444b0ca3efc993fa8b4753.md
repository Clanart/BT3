### Title
Partial-failure in multi-file `discardChanges` loop leaves trashed files unrestored, silently corrupting the working tree - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.discardChanges` iterates over the array of files to discard, moving each one to the OS trash *before* later performing a single batched `git reset` + `git checkout-index` to restore their contents from the index/HEAD. If the trash operation throws for one file partway through the loop (and the user has previously opted in to "always discard permanently on trash failure"), the function throws immediately and the batched restore step is never reached — leaving files already removed for prior loop iterations deleted from disk with no git-side restoration.

### Finding Description
`discardChanges` builds `pathsToCheckout`/`pathsToReset` and performs the actual trash removal in the same `for (const file of files)` loop: [1](#0-0) 

For each file that isn't a submodule or already-deleted, it calls `this.shell.moveItemToTrash(...)` — a destructive, main-process OS call — and only afterward records the path to later be checked out from the index: [2](#0-1) 

If `moveItemToTrash` throws (e.g. attacker-crafted filename in a cloned repository that breaks Electron's/OS's trash implementation — long paths, reserved device names on Windows such as `CON`/`NUL`, path/name edge cases, or a locked/immutable file) and `askForConfirmationOnDiscardChangesPermanently` is `true` (a setting the user enables after previously choosing "always discard permanently if trash fails"), a `DiscardChangesError` is thrown immediately, aborting the loop: [3](#0-2) 

Crucially, the actual restoration step — `resetPaths` + `checkoutIndex`, which re-populates the working directory with the index/HEAD content for every discarded path — happens only *after* the entire loop completes, in a single batched call: [4](#0-3) 

Because the exception propagates before this batched restore ever runs, any files successfully trashed in earlier loop iterations are never checked back out. They remain physically deleted from the working directory while Git's index/HEAD are untouched. `_discardChanges` in `app-store.ts` simply catches the error and emits it to the UI without any compensating rollback or partial-restore logic: [5](#0-4) 

This mirrors the reported bug class exactly: a loop over a heterogeneous, partially attacker-influenced collection where a single item's failure aborts the "commit" phase of the whole batch, but the destructive part of already-processed items has already taken effect — leaving the aggregate state inconsistent instead of either fully applied or fully rolled back.

### Impact Explanation
This results in silent, uncontrolled corruption of the user's working directory: files the user did **not** intend to lose (they only wanted the trash-failing file to remain) disappear from disk and show up as `Deleted` in Desktop's changes list. Electron's trash-move is at least nominally recoverable via the OS trash, but the operation gives the appearance to Git (and to Desktop's status view) that those files are now deleted from the repo. If the user is not paying close attention and stages/commits or pushes afterward, they will silently commit deletions of files they never asked to discard — matching the "silent corruption of what the user commits or pushes" impact category. No warning is given about which specific files were left in this half-restored state; the user only sees a generic error dialog for the one file that failed to trash.

### Likelihood Explanation
The trigger requires: (1) an attacker-controlled repository containing a file whose name/path is engineered to make `shell.trashItem` (invoked via `moveItemToTrash`) fail on the victim's OS, and (2) the victim selecting multiple files (including the malicious one) for "Discard Changes" while having previously enabled "always discard permanently if trash fails" (`askForConfirmationOnDiscardChangesPermanently`). This is a somewhat narrow combination of preconditions — it depends on a non-default setting and on the array ordering placing the poisoned file after at least one legitimate file — so likelihood is moderate rather than high, but it requires no unusual user action beyond a normal "Discard Changes on selected files" click, and the malicious filename ships entirely inside the cloned/fetched repository.

### Recommendation
Restructure `discardChanges` so that trash removal and index/working-tree restoration are interleaved per-file (or wrapped in a single transaction) rather than split into "destroy first, restore later" phases across the whole batch. At minimum, if a `moveItemToTrash` call throws mid-loop, immediately run `resetPaths`/`checkoutIndex` for all paths successfully processed so far before propagating the error, so the working directory is never left with orphaned deletions. Also surface to the user exactly which files were successfully discarded vs. which failed, rather than a single opaque error.

### Proof of Concept
1. Attacker publishes a Git repository containing a normal tracked file (`a.txt`) and a second tracked file whose name is engineered to make the host OS's trash operation fail on Windows (e.g. a filename that collides with a reserved device name pattern, or an extremely long path once combined with the repo's clone location) — call it `b.bad`.
2. Victim clones/fetches this repository with GitHub Desktop and enables "always discard changes permanently if trash fails" the first time they hit a trash failure (a realistic, one-time setting).
3. Victim modifies both `a.txt` and `b.bad`, selects both in the Changes list, and clicks "Discard Changes."
4. `discardChanges` (`app/src/lib/stores/git-store.ts:1545`) iterates: `a.txt` is moved to trash successfully; `b.bad`'s `moveItemToTrash` throws; because `askForConfirmationOnDiscardChangesPermanently` is `true`, `DiscardChangesError` is thrown at line 1566, aborting the loop before `resetPaths`/`checkoutIndex` (lines 1636-1648) ever run.
5. Result: `a.txt` is now missing from the working directory with no git-side restoration, appearing as `Deleted` in the next status refresh, while the user only intended to discard `b.bad`'s failure was surfaced but `a.txt`'s partial state was not.
