### Title
Distribution precompile `rewards()` view accepts native value and permanently strands it - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` method of the Distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without the non-payable check applied to every other query method on that precompile. A caller who attaches non-zero `value` to a `rewards(address)` call has that value debited from their EVM balance and credited to the precompile's own address, with no refund path — the funds are permanently lost, mirroring the "Bank cannot receive/return funds" bug class from the reference report.

### Finding Description
In `Execute()`, every other view method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) is routed through `p.validateInput`, which calls `pcommon.ValidateNonPayable(value)` and rejects any non-zero `value` before doing anything else: [1](#0-0) 

However `RewardsMethod` is dispatched directly to `p.rewards(ctx, method, args)`, skipping this check entirely: [2](#0-1) 

And the `rewards` implementation itself never validates or consumes `value`: [3](#0-2) 

This is a known, documented quirk in the test suite itself: [4](#0-3) 

For comparison, precompile methods that legitimately accept `value` (e.g. `staking.delegate`, `wasmd.execute`) explicitly consume it via `pcommon.HandlePaymentUsei`, which debits the payer, mints/uses a `sdk.Coin`, and is designed so the value is actually used for a purpose (delegation, contract funding): [5](#0-4) [6](#0-5) 

Precompiles in the go-ethereum/Sei EVM execution model receive `value` via the standard EVM `CALL` value-transfer semantics (the caller's balance is debited and the precompile address's balance is credited by the StateDB *before* `Run`/`Execute` is invoked) — the same mechanism `HandlePaymentUsei` relies on to subsequently refund the payer. Because `rewards()` never calls `HandlePaymentUsei` or otherwise moves the received value back to the caller, any wei/usei sent along with a `rewards()` call is left sitting on the precompile's own address with no code path in the repository that ever reads or moves it out.

### Impact Explanation
Any EVM transaction sender or any smart contract that calls `DISTR_CONTRACT.rewards(delegatorAddr)` with non-zero `msg.value` will have that value permanently and irrecoverably debited from their balance. This is a direct, concrete loss of funds reachable by a single unprivileged transaction against a public, well-known precompile address, matching the accepted "concrete fund loss" impact category. It is functionally identical to the reference report's core issue: value sent to an on-chain entity that has no mechanism to move it back out.

### Likelihood Explanation
Trivial to trigger and requires no special privilege: any account or contract capable of sending an EVM transaction can call `rewards()` on `0x...1007` with attached value. Because `rewards()` is a `view`-style ABI function, a wallet/dApp or a batching contract could reasonably (and mistakenly, or via crafted malicious contract logic) attach value to this call, and unlike the sibling query methods, the call will not revert. Likelihood is high given the low complexity and single-transaction reachability.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` check to the `RewardsMethod` case in `Execute()` (or inside `rewards()` itself) so that a value-bearing call reverts instead of silently stranding funds, consistent with every other read-only method on this precompile.

### Proof of Concept
1. Call the Distribution precompile at `0x0000000000000000000000000000000000001007` with function selector for `rewards(address)` and a non-zero `value` (e.g. `ethers.parseEther('1')`), passing any valid delegator address as argument.
2. Observe the transaction succeeds (no revert), unlike identical value-bearing calls to `params()`, `communityPool()`, etc., which revert with "sending funds to a non-payable function".
3. Observe the caller's EVM balance decreases by the attached value and no compensating credit or refund occurs anywhere in `rewards()`'s execution path — the value is unrecoverable through any documented precompile or module function. [2](#0-1) [4](#0-3)

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
