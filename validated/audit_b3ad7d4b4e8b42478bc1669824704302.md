## Finding: `IntentGatewayV2.withdraw()` on the Tron variant performs external token transfers before updating escrow accounting (checks-effects-interactions violation missing from the parallel EVM implementation)

### Title
Escrow accounting update happens after the external transfer in `withdraw()` (Tron `IntentGatewayV2`), unlike the hardened twin implementation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Ajna report's core pattern is: two functions perform the *same* bucket accounting operation, but only one of them was updated with the necessary safety/finalization step, leaving the other's accounting state incorrect/exploitable. Hyperbridge has an exact structural analog: the intents escrow-withdrawal logic is implemented twice — once in the hardened `IntentsBase._withdraw` used by the current EVM `IntentGatewayV2` stack, and once in the Tron fork `evm/tron/contracts/apps/IntentGatewayV2.sol`. The hardened version decrements the escrow mapping **before** making the external transfer; the Tron twin does the external transfer **before** decrementing the mapping, violating checks-effects-interactions.

### Finding Description
In the current, hardened path, `_withdraw()` zeroes/decrements the per-order escrow ledger before any external call: [1](#0-0) 

The Tron fork's `withdraw()`, which implements the identical `RedeemEscrow`/`RefundEscrow` accounting for the same `_orders[commitment][token]` ledger, instead makes the external call (native ETH send or ERC20 `transfer`) first and only decrements the balance afterward: [2](#0-1) 

The only guard before the transfer is `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — it does not zero or decrement the value before yielding control to `beneficiary` or an attacker-supplied `token` contract. `_filled[body.commitment]` is set at the very top of `withdraw()`, so a synchronous re-entry into `onAccept`/`onGetResponse` for the *same* commitment is blocked, but the escrow amount for that `(commitment, token)` pair remains non-zero on-chain during the entire external-call window: `_orders[body.commitment][token] -= amount;` only executes after the transfer returns. [3](#0-2) 

Orders can escrow arbitrary ERC20 tokens chosen by the order creator/solver (there is no token allowlist visible in this contract), so an attacker can supply a malicious ERC20 as one of the order's input/output tokens. During the low-level `token.call(...transfer...)`, that attacker-controlled token contract executes with `IntentGatewayV2` as `msg.sender` and can reenter other public entrypoints of the same contract while `_orders[commitment][token]` still reflects the pre-withdrawal (undeducted) balance.

### Impact Explanation
This is a checks-effects-interactions violation on the exact ledger (`_orders[commitment][token]`) that guards escrowed bridged assets, matching the "must move exactly once and only to the rightful beneficiary and amount" pivot for bridged assets/order escrow. If any reachable function reads or acts on `_orders[commitment][token]` during the reentrant window (e.g., accounting checks elsewhere that assume the value has already been debited), the stale, non-zeroed balance can be leveraged to extract more value than was actually escrowed for that order, i.e., fund loss from the escrow contract.

### Likelihood Explanation
Reduced from "certain" because the strongest single-call double-spend (re-entering `withdraw()` itself for the same commitment) is blocked by the `onlyHost` modifier on `onAccept`/`onGetResponse` and by `_filled[commitment]` being set up-front — an attacker cannot trivially call `onAccept` again as the "host." I was not able to fully verify, within the available search budget, whether this Tron contract exposes any *other* unprivileged entrypoint that reads/writes `_orders[commitment][token]` for the same commitment while it's still un-decremented (the file's same-chain cancel/fill logic differs from the newer `IntentsBase`/`IntrinsicIntents` split and I did not get to read it fully). The existence of a dedicated `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` suite for the current EVM intents path, with no equivalent test file for the Tron contract, indicates the team already treats this ordering as a real risk class for the current implementation but the Tron fork was not brought up to the same standard.

### Recommendation
Apply checks-effects-interactions in the Tron `withdraw()`: decrement/zero `_orders[body.commitment][token]` (and `_orders[commitment][TRANSACTION_FEES]`) before making the external native/ERC20 transfer, exactly as `IntentsBase._withdraw` already does, and add a `nonReentrant` guard consistent with the rest of the intents contracts. Add a Tron-specific reentrancy regression test mirroring `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
Not independently constructed/executed — this report is based on static code comparison between the two `withdraw` implementations found in the repository: [4](#0-3) [5](#0-4) 
A concrete exploit would need to identify (or confirm the absence of) a second unprivileged entrypoint in the Tron contract that touches the same `_orders[commitment][token]` slot mid-reentrancy; I could not complete that verification before the tool budget was exhausted, so treat the "Likelihood" section's caveat as the open item for a background agent/auditor to close before filing this as a full-severity bug.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
