### Title
Permissionless `donateRewards()` allows queued-reward capture by a dust depositor after `totalStaked()` transiently hits zero - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`_provisionReward` queues rewards into `rewardInfo.queuedRewards` whenever `totalStaked() == 0`, and only converts that backlog into `rewardPerTokenStored` the *next time* `_provisionReward` runs, dividing by whatever `totalStaked()` is at that later moment. Because `donateRewards(_amountReward, _rewardToken)` is a public, unrestricted, zero-amount-tolerant entry point into `_provisionReward`, an attacker can single-handedly control both the queuing step and the triggering step, and choose the triggering moment to be right after depositing a dust amount, making the divisor `totalStaked()` equal to their own tiny stake and capturing nearly the entire queued reward.

### Finding Description
`_provisionReward` (rewards/BaseRewardPoolV2.sol lines 290-314) contains: [1](#0-0) 
```
if (totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored =
        rewardInfo.rewardPerTokenStored +
        (_amountReward * 10**stakingTokenDecimals) /
        totalStaked();
}
```
`totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` [2](#0-1) , i.e. the live balance held by `MasterMagpie`, which can momentarily be `0` if all stakers withdraw in the same block.

`donateRewards` is unrestricted and reachable by any EOA: [3](#0-2) 
```
function donateRewards(uint256 _amountReward, address _rewardToken) external {
    if (!isRewardToken[_rewardToken]) revert MustBeRewardToken();
    _provisionReward(_amountReward, _rewardToken);
}
```
There is no minimum-amount check and no restriction on who calls it or how many times.

Exploit flow:
1. Attacker observes/front-runs the block where `totalStaked()==0` (all other stakers have withdrawn from `MasterMagpie` for this staking token).
2. Attacker calls `donateRewards(largeAmount, token)`. Since `totalStaked()==0`, the whole `largeAmount` goes into `queuedRewards` and `rewardPerTokenStored` is left unchanged.
3. Attacker deposits a dust amount (e.g. 1 wei) of `stakingToken` via `MasterMagpie.deposit`, becoming the sole staker (`totalStaked()` now equals the dust amount).
4. Attacker calls `donateRewards(0, token)` (or any small amount) again. Now `totalStaked() != 0`, so the `else` branch fires: `_amountReward (0) += queuedRewards (large)`, `queuedRewards` resets to 0, and `rewardPerTokenStored += queuedRewards * 10**decimals / totalStaked()` — with `totalStaked()` equal to the attacker's own dust stake, this produces a massive `rewardPerTokenStored` increment attributable entirely to the attacker's negligible balance.
5. Attacker calls `MasterMagpie`'s claim path, which calls `getReward`/`updateFor` on the rewarder (`onlyMasterMagpie`, protected by `updateReward`/`_updateFor`) [4](#0-3) . `_earned` computes `userShare * (rewardPerTokenStored - paid) / 10**decimals`, and since the attacker's `userRewardPerTokenPaid` was `0` before this jump, they receive essentially the full `queuedRewards` amount despite holding a dust stake [5](#0-4) .

None of `onlyMasterMagpie`, `updateReward`, or `nonReentrant` protections in `MasterMagpie.deposit`/`getReward` prevent this, because the vulnerability lies entirely in the reward-per-token accounting math inside `_provisionReward`, not in access control. The root cause is that queued-reward realization is driven by an attacker-controlled, permissionless trigger (`donateRewards`) rather than being amortized or gated by a minimum total-supply/time-weighted mechanism.

### Impact Explanation
This is a direct theft of unclaimed yield: legitimate rewards meant for pro-rata distribution to all future/returning stakers are instead captured almost entirely by an attacker who stakes only a dust amount at the precise moment `totalStaked()` is near zero. This matches the "theft of unclaimed yield" / "direct theft of user funds" Immunefi impact class for the rewarder scope.

### Likelihood Explanation
The attack requires:
- A transient state where `totalStaked() == 0` for the given staking token in `MasterMagpie` (all current stakers having withdrawn in the same block, or the pool being newly created/empty), which is a real but non-trivial precondition — likely at pool launch, migration, or contrived collusion/timing, but not requiring any privileged role.
- Capital equal to `largeAmount` of the reward token (attacker donates it themselves, so no net loss of that specific step — the extraction of value comes from displacing rightful *future* claimants) plus dust `stakingToken`.
- No special permissions; `donateRewards` is fully permissionless and repeatable for every reward token registered on any pool that experiences a zero-total-staked state.

Because `donateRewards` allows anyone to trigger the conversion of `queuedRewards` at a self-chosen moment (including immediately after their own dust deposit), the attack is fully reachable by an unprivileged attacker without owner/manager rights, matching the described PoC.

### Recommendation
- Do not let arbitrary callers trigger the queued-rewards-to-rewardPerToken conversion. Restrict `donateRewards`/`_provisionReward`'s realization step (the `else` branch) to `onlyManager`/protocol-controlled calls, or decouple "donation" (permissionless) from "queue realization" (privileged), similar to Convex's `queueNewRewards` separation.
- When converting queued rewards into `rewardPerTokenStored`, use a minimum total-staked threshold or time-weighted release, and consider snapshotting `totalStaked()` prior to any single-block dust deposit (e.g., require a cooldown/minimum stake duration before being counted for reward realization).
- Alternatively, disallow zero/negligible `_amountReward` donations from re-triggering the queued-rewards flush, and/or require `donateRewards` to only add to `queuedRewards` (never directly realize it) while a separate, access-controlled function performs realization.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPoolV2` for a `stakingToken`/`rewardToken` pair, register the pool.
2. Have staker A deposit some `stakingToken`, then fully withdraw in the same test step so `totalStaked() == 0` (asserts `IERC20(stakingToken).balanceOf(masterMagpie) == 0`).
3. As attacker, call `rewardPool.donateRewards(1_000e18, rewardToken)` — assert `rewards(rewardToken).queuedRewards == 1_000e18` and `rewardPerTokenStored` unchanged.
4. As attacker, `masterMagpie.deposit(stakingToken, 1)` (1 wei).
5. As attacker, call `rewardPool.donateRewards(0, rewardToken)` — assert `queuedRewards == 0` and `rewardPerTokenStored` jumped to `1_000e18 * 10**decimals / 1`.
6. As attacker, claim via `masterMagpie.multiclaim`/`getReward` path — assert attacker receives ~`1_000e18` reward tokens despite holding 1 wei of stake.
7. Have staker B deposit a normal amount afterward and assert they can claim only whatever new rewards are queued after step 5 — i.e., the original `1_000e18` is gone, proving the queued rewards meant for pro-rata future distribution were fully captured by the dust depositor.
