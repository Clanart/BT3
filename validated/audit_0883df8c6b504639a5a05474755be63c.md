### Title
Unvalidated `file://` submodule protocol re-enablement on checkout may allow arbitrary local Git repository disclosure - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` conditionally re-enables Git's `file://` transport for submodules via `-c protocol.file.allow=always` before running `git submodule update --init --recursive` [2](#0-1) . Modern Git disables the `file://` protocol for submodules by default specifically to stop a repository from silently pulling in the contents of an arbitrary local path/repository during clone/checkout (a known Git hardening measure). This flag is threaded through `checkoutBranch`/`checkoutCommit` as an `allowFileProtocol` boolean [3](#0-2)  and, per the test suite, is exercised specifically to let uninitialized submodules referencing local test fixture paths be checked out [4](#0-3) [5](#0-4) .

### Finding Description
`.gitmodules` is fully attacker-controlled content in any cloned/fetched repository. Normally, Git's own default (`protocol.file.allow=user`, effectively disabled for submodules since Git 2.38+ CVE-2022-39253 hardening) prevents a malicious `.gitmodules` entry such as `url = file:///home/victim/some-other-repo` from being used during `git submodule update --init`. GitHub Desktop's `updateSubmodulesAfterOperation` overrides this protection whenever `allowFileProtocol` is `true`, unconditionally passing `-c protocol.file.allow=always` to the submodule update invocation with no check on the submodule URL's origin or the repository's trust state [2](#0-1) . If a code path reachable from an untrusted/attacker-authored repository (fetched, cloned, or containing a branch with `.gitmodules` pointing at `file://<local path>`) ever calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`, Git will happily "clone" the referenced local path into the submodule directory of the working tree — copying its objects/history into the tracked repo. That content could then be committed and pushed by the user, corrupting/exfiltrating data the user did not intend to share, or simply become readable by anything (e.g. an extension, CI script, or the Desktop UI) that processes the working directory afterward.

### Impact Explanation
If reachable from attacker-controlled repository content, this would allow reading/copying arbitrary local Git repositories (potentially containing credentials, private code, or other sensitive material) into a tracked working directory, matching the accepted impact class of "file write/read outside the repo" and "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Low-to-uncertain. The only confirmed call sites with `allowFileProtocol=true` I could identify are in the unit test helper `setupRepositoryWithUninitializedSubmodule`/`checkout-test.ts`, simulating a legitimate "uninitialized submodule" recovery scenario using local fixture paths that the app already knows about [4](#0-3) . I could not verify from the indexed code whether any production, UI-triggered flow (e.g., opening a freshly cloned untrusted repository, or "Clone Again"/"Open Repository from URL") passes `allowFileProtocol=true` while the submodule URL itself is attacker-supplied and unvalidated. All the default checkout call sites I found in `app-store.ts` use the default `allowFileProtocol=false` [1](#0-0) .

### Recommendation
- Never re-enable `protocol.file.allow=always` for submodule operations on repositories that are not already fully trusted/local-only; if the feature is needed for an "uninitialized submodule" repair flow, restrict it to submodule URLs that were already recorded/resolved from `.git/modules` (i.e., known-good, previously-initialized paths) rather than arbitrary `.gitmodules` content from an untrusted checkout.
- If `allowFileProtocol` must remain, validate/allowlist the resolved submodule URL against the repository's own trusted remotes before passing `protocol.file.allow=always`.
- Add an invariant/regression test asserting that checking out an untrusted branch whose `.gitmodules` contains a `file://` URL never triggers a local clone unless the branch/commit is from the app's own git-dir history of a known submodule.

### Proof of Concept
Could not be fully constructed from index alone due to the uncertainty in call-site reachability noted above. Conceptually: an attacker crafts a repository with a branch/commit whose `.gitmodules` declares `[submodule "x"] path = x url = file:///home/victim/.ssh` (or any sensitive local git repo); if a Desktop code path checks out that branch/commit with `allowFileProtocol=true`, `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, copying the local path's git history into `x/` inside the tracked repository [6](#0-5) .

Given I could not conclusively confirm an unprivileged, UI-reachable trigger for `allowFileProtocol=true` with attacker-controlled `.gitmodules` content, I recommend treating this as a **candidate** finding requiring a Devin session with full repo/terminal access to trace every caller of `checkoutBranch`/`checkoutCommit`/`updateSubmodulesAfterOperation` and confirm reachability before treating it as a confirmed vulnerability.

    repository,

export async function setupRepositoryWithUninitializedSubmodule(
  t: TestContext
): Promise<Repository> {
  const repo = await setupTwoCommitRepo(t)

  // Create a submodule repository
  const submoduleRepo = await setupTwoCommitRepo(t)

  // Create a new branch and add the submodule
  await exec(['checkout', '-b', 'branch-with-submodule'], repo.path)

  await exec(
    [
      '-c',
      'protocol.file.allow=always',
      'submodule',
      'add',
      submoduleRepo.path,
      'test-submodule',
    ],
    repo.path
  )
  await exec(['commit', '-m', 'Add submodule'], repo.path)

  // Go back to main branch
  await exec(['checkout', 'master'], repo.path)

  // Remove the .git/modules directory for the submodule to make it uninitialized
  const modulesPath = join(repo.path, '.git', 'modules', 'test-submodule')
  await rm(modulesPath, { recursive: true, force: true })
  await rm(join(repo.path, 'test-submodule'), { recursive: true, force: true })

  return repo
}
