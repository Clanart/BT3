### Title
Direct `ERC20Burnable.burn()` calls on mint‑and‑burn service‑chain tokens permanently lock counterpart‑chain assets, bypassing the Bridge's `RequestValueTransfer` accounting - ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
In Kaia's service‑chain bridge, tokens deployed in "mint & burn" mode (`modeMintBurn == true`) must be `ERC20Burnable` so that the `Bridge` contract can burn tokens it holds when a user requests a withdrawal. `ERC20Burnable.burn(uint256)` is a public, unrestricted function inherited directly by any compatible token (e.g. `ServiceChainToken`), so any holder can burn their own balance directly on the token contract without ever calling the bridge's `requestERC20Transfer`/`requestValueTransfer` path. This destroys the child‑chain representation of value without emitting `RequestValueTransfer` or incrementing `requestNonce`, leaving the corresponding locked/minted value on the counterpart chain permanently stranded — the same root cause as the reported L2ECO issue.

### Finding Description
The bridge send‑path burns tokens itself once they are transferred to the bridge, and relies on this burn to be the sole path that reduces child‑chain supply and produces the `RequestValueTransfer` event the counterpart‑chain operator listens for: [1](#0-0) 

The withdrawal-intended path (`ERC20ServiceChain.requestValueTransfer`) transfers tokens to the bridge and calls `onERC20Received`, which internally invokes `_requestERC20Transfer` → `ERC20Burnable(_tokenAddress).burn(_value)` on the bridge's own balance, and only then emits `RequestValueTransfer`: [2](#0-1) 

However, the token contract itself (`ServiceChainToken`, and any conforming mint‑and‑burn token) inherits `ERC20Burnable` directly and unconditionally, exposing a public `burn(uint256 amount)`/`burnFrom` that any holder can call on their own balance: [3](#0-2) 

Because `ERC20Burnable.burn` has no caller restriction tying it to the bridge, a user who received minted child‑chain tokens (via `handleERC20Transfer`'s `ERC20Mintable(_tokenAddress).mint(_to, _value)`) can simply call `token.burn(amount)` on the token contract, destroying their tokens without routing through `_requestERC20Transfer`. No `RequestValueTransfer` event is emitted and `requestNonce` is not incremented, so the counterpart mainchain `Bridge` (which is holding the original locked assets, per `bridge_manager.go`'s `handleRequestValueTransferEvent`) never receives any signal to unlock or otherwise account for the burned value: [4](#0-3) 

This is structurally identical to the referenced L2ECO bug: the token's own unrestricted `burn` bypasses the bridge's accounting/notification path that is required to release the corresponding locked value on the other chain.

### Impact Explanation
Any unprivileged holder of a mint‑and‑burn bridged token can permanently destroy it while the corresponding value remains locked forever on the counterpart chain, because there is no bridge-side path to reconcile a burn that did not originate from `_requestERC20Transfer`. This is a permanent loss of the counterpart chain's real assets (locked ERC20/KLAY) with no recovery mechanism, i.e., unauthorized asset destruction / permanent fund lock — a High severity impact matching the original report's classification.

### Likelihood Explanation
Any user holding the bridged token can trigger this merely by calling the token's public `burn` function directly — no special privileges, no bridge operator collusion, and no protocol misconfiguration are required beyond the token being deployed in mint‑and‑burn mode (the documented/expected configuration for service‑chain bridging, per `contracts/test/Bridge/bridge.test.ts` fixtures). This makes the likelihood high once mint‑and‑burn mode is used with a token that exposes `ERC20Burnable.burn` publicly, which is the reference implementation shipped in this repository.

### Recommendation
- Restrict `burn`/`burnFrom` on bridge-compatible mint‑and‑burn tokens so it is only callable by the `Bridge` contract itself (e.g., via a `onlyBridge` modifier), removing the standalone `ERC20Burnable` public entry point, similar to how `handleERC20Transfer`/`_requestERC20Transfer` are the only sanctioned mint/burn callers.
- Alternatively, require that any token registered for `modeMintBurn` bridging implement burn access control tied to the bridge address, and validate this at `registerToken` time.
- If unrestricted user burns must remain supported for other purposes, implement a reconciliation/emergency-unlock mechanism on the counterpart chain bounded by `min(locked_supply, child_chain_burned_supply)` as suggested in the original report, to avoid unbounded trust in burn accounting.

### Proof of Concept
1. Bridge deployed with `modeMintBurn = true`; `ServiceChainToken` (or any compatible mint&burn ERC20) registered.
2. Mainchain user locks `X` tokens in the mainchain `Bridge`, triggering `handleERC20Transfer` on the child chain, which mints `X` `ServiceChainToken` to the user via `ERC20Mintable(_tokenAddress).mint(_to, _value)` (`contracts/service_chain/bridge/BridgeTransferERC20.sol:68-72`).
3. Instead of calling `token.requestValueTransfer(...)` (the sanctioned withdrawal path), the user calls `token.burn(X)` directly — a plain unrestricted call on `ServiceChainToken`, inherited from `ERC20Burnable` (`contracts/testing/sc_erc20/sc_token.sol:27`).
4. The child-chain balance of `X` is destroyed; no `RequestValueTransfer` event fires and `requestNonce` is unchanged.
5. The mainchain `Bridge` never observes a corresponding event (per `handleRequestValueTransferEvent` in `node/sc/bridge_manager.go`), so the originally locked `X` tokens on the mainchain remain locked permanently with no way to unlock them.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
