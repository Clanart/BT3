## Answer

`deleteLocalBranch` builds its git argument list without an end-of-options `--` guard: [1](#0-0) 

```ts
export async function deleteLocalBranch(
  repository: Repository,
  branchName: string
): Promise<true> {
  await git(['branch', '-D', branchName], repository.path, 'deleteLocalBranch')
  return true
}
```

### Finding Description
The argument vector is `['branch', '-D', branchName]` — `branchName` is appended immediately after the `-D` flag with no `--` separator. Compare this to sibling functions in the same git-wrapper layer that explicitly insert `--` before untrusted ref/path text before handing it to git: [2](#0-1) [3](#0-2) [4](#0-3) 

`deleteLocalBranch` lacks this pattern. If `branchName` were to begin with `-`, git would attempt to parse it as an additional option to `git branch` rather than as an operand.

`branchName` is populated from the repository's own ref namespace — e.g. in `branch-pruner.ts`, it is derived from `refs/heads/<name>` entries returned by `getMergedBranches` (a `for-each-ref` wrapper): [5](#0-4) 

Desktop does apply a `sanitizedRefName` helper (which strips a leading `-`/`+`) when the user creates a branch from within the app: [6](#0-5) 

However, that sanitizer only governs names Desktop itself writes when creating branches through the UI. It provides no protection for ref names that already exist inside a repository the user clones/fetches — refs are ordinary text entries in `packed-refs`/loose ref files, and `git branch <name>`'s own leading-dash rejection is a check performed by the `branch` porcelain command at *creation* time, not something re-validated by `for-each-ref` when merely listing existing refs. A ref written into the repository object store by other means (e.g. present in a maliciously crafted repository's `packed-refs` at clone time) is not guaranteed to have gone through that specific porcelain check, so `for-each-ref`/`getMergedBranches` can legitimately surface a short name beginning with `-` for `deleteLocalBranch` to consume unguarded.

### Impact Explanation
If a `refs/heads/` entry beginning with `-` reaches `deleteLocalBranch` (e.g., via the automatic `BranchPruner` background task, which runs unattended), the resulting `git branch -D <that-name>` invocation would parse the crafted text as an additional flag to `git branch` rather than a branch operand, i.e., attacker-controlled repository content is able to influence the invoked git process's option set — exactly the class of "argv injection without `--` guard" the question targets.

### Likelihood Explanation
This requires: (1) an attacker being able to seed a repository with a ref whose short name begins with `-`, surviving a normal clone/fetch into Desktop's ref store, and (2) that ref being classified by `BranchPruner`/`getMergedBranches` as merged and eligible for deletion. This is a narrower path than a fully generic "any ref triggers injection" scenario, and I was not able to fully verify within this review whether git's fetch/clone ref-writing path enforces `check_refname_format` restrictions strictly enough to block a leading `-` (which would make the bug unreachable) versus permitting it (which would make it reachable). This uncertainty affects confidence in exploitability, and I could not resolve it definitively from the code alone.

### Recommendation
Add an explicit `--` end-of-options separator before `branchName` in `deleteLocalBranch`, matching the mitigation pattern already used in `checkout.ts`, `clone.ts`, and `diff.ts`:
```ts
await git(['branch', '-D', '--', branchName], repository.path, 'deleteLocalBranch')
```

### Proof of Concept
Conceptual (not independently executed in this review):
```ts
await deleteLocalBranch(repo, '--edit-description')
// -> git(['branch', '-D', '--edit-description'], ...)
```
If a ref with that literal short name exists in the repository and is deemed "merged" by the pruning heuristic, `deleteLocalBranch` would invoke git with `--edit-description` treated as an option to `git branch -D` instead of as the branch operand. [1](#0-0)
