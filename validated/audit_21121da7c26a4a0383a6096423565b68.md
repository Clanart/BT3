### Title
Threshold key deserialization accepts a private share inconsistent with its public verification share - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes the local secret share and all public verification shares, but never verifies that the secret corresponds to this participant’s public share. [1](#0-0)  This is analogous to accepting a downloaded private key without checking that it belongs to the downloaded public key.

### Finding Description
`ThresholdKeys::new` validates only the participant count, participant indexes, and interpolation applicability before deriving `group_key` from the supplied verification shares. [2](#0-1)  It does not check `C::generator() * secret_share == verification_shares[params.i()]`, and `ThresholdKeys::read` calls this constructor directly after reading attacker-controlled fields. [3](#0-2)  Signing later uses the deserialized secret share while verification and address derivation use the independently supplied public shares. [4](#0-3) 

### Impact Explanation
Because `group_key` is derived from the verification shares rather than the private share, a malformed key package can preserve the expected group key and Bitcoin address while replacing the usable local secret. [5](#0-4)  The Bitcoin scanner reports outputs paying the resulting script as received outputs. [6](#0-5)  `SignableTransaction::multisig` accepts the output because it compares the script only with the public `group_key`, after which FROST signs with the mismatched private share. [7](#0-6)  The resulting signature share fails verification against the declared verification share, leaving reported funds unspendable by the threshold protocol. [8](#0-7) 

### Likelihood Explanation
An unprivileged party able to supply or alter a serialized `ThresholdKeys` package can trigger this using only public serialized fields; no malicious validator or leaked legitimate share is required. [9](#0-8)  The practical severity is bounded by whether an attacker can cause multiple participants or a wallet deployment to consume inconsistent key packages, but a successful setup causes deposits to be attributed to a key whose shares cannot complete valid FROST signatures.

### Recommendation
Validate the secret/public correspondence when constructing or deserializing keys by rejecting inputs where `verification_shares[params.i()] != C::generator() * secret_share`. [10](#0-9)  The check should be performed in `ThresholdKeys::new`, so `ThresholdKeys::read`, dealer code, promotion, and all other constructors inherit it. [11](#0-10) 

### Proof of Concept
```rust
// Construct a valid DKG result, then replace participant 1's private share
// while retaining the honest public verification shares.
let honest = dkg_dealer::key_gen::<_, Secp256k1>(&mut rng, 2, 3).unwrap();
let participant = Participant::new(1).unwrap();
let params = honest[&participant].params();

let verification_shares = (1 ..= params.n())
  .map(|i| {
    let i = Participant::new(i).unwrap();
    (i, honest[&i].original_verification_share(i))
  })
  .collect();

// This constructor accepts the inconsistent private/public key pair.
let wrong_secret = Zeroizing::new(Scalar::random(&mut rng));
let malformed = ThresholdKeys::new(
  params,
  Interpolation::Lagrange,
  wrong_secret.clone(),
  verification_shares,
)
.unwrap();

assert_ne!(
  malformed.original_verification_share(participant),
  Secp256k1::generator() * wrong_secret.deref(),
);
assert_eq!(malformed.group_key(), honest[&participant].group_key());

// The malformed object also round-trips through the untrusted read API.
let encoded = malformed.serialize();
let decoded = ThresholdKeys::<Secp256k1>::read(&mut encoded.as_slice()).unwrap();

// Scanning/tranasction setup follows the public group key.
let scanner = Scanner::new(tweak_keys(decoded.clone()).group_key()).unwrap();
let received = scanner.scan_transaction(&deposit_tx);
assert_eq!(received.len(), 1);

// The spend path accepts the output because its script matches group_key,
// but the FROST share is generated with `wrong_secret` and fails verification
// against `original_verification_share(participant)`.
let tx = SignableTransaction::new(
  received,
  &payments,
  None,
  None,
  fee_per_vbyte,
).unwrap();
let machine = tx.multisig(&tweak_keys(decoded)).unwrap();
```

The important steps are that `ThresholdKeys::new` accepts the mismatched pair and `ThresholdKeys::read` preserves it without a correspondence check. [3](#0-2)
