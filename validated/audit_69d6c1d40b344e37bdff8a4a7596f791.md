### Title
Permanent freezing of unclaimed bribe yield when `addPool` swaps a pool's `rewarder` for an already-active LP - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.addPool(lp, newRewarder, name)` unconditionally overwrites `poolInfos[lp].rewarder`, discarding the reference to the previous rewarder contract without any migration of state. `claimBribe`/`claimAllBribes` only ever call `getReward` on the current `poolInfos[lp].rewarder`, so any `userRewards`/`earned()` balance still sitting in the old rewarder contract instance becomes permanently unreachable, since `getReward` is gated by `onlyMasterMagpie` and only the `WombatBribeManager` contract itself is authorized to call it.

### Finding Description
`vote()` records a user's voting balance by calling `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, delta)` on whichever rewarder is currently stored in `poolInfos[lp].rewarder` [1](#0-0) . All reward accounting (`userRewards`, `userRewardPerTokenPaid`, `_balances`, `totalSupply`) lives per-contract-instance inside `BaseRewardPoolV2`/`BribeRewardPool` [2](#0-1) .

When the owner calls `addPool(lp, newRewarder, name)` for an LP that is already active (e.g. to upgrade/replace a rewarder implementation), the function simply overwrites the struct with no check for an existing rewarder and no attempt to migrate balances or unclaimed rewards: [3](#0-2) 

After this call, `_claimBribeFor` and `claimAllBribes` only ever resolve `poolInfos[lps[i]].rewarder` to the new instance: [4](#0-3) [5](#0-4) 

Any `earned()` balance still accrued in the old rewarder for that user (from `stakeFor` calls and reward distributions made before the swap) can no longer be reached: `getReward` on `BaseRewardPoolV2` is restricted to `onlyMasterMagpie` (i.e. `msg.sender == operator`, which is the `WombatBribeManager` contract address) [6](#0-5) . Since `WombatBribeManager` no longer stores the old rewarder's address anywhere after the overwrite in `poolInfos[lp]`, there is no code path — privileged or unprivileged — left in the manager that can call `getReward` on the stale rewarder. No EOA can call it directly either, because it is not `operator`. The funds/accounting for that balance are stuck forever in the abandoned contract.

There is no double-payment risk in the reverse direction: `userRewards`/`userRewardPerTokenPaid` are storage variables local to each separately-deployed rewarder contract, so the new rewarder starts at zero and cannot "inherit" or duplicate the old contract's balances.

### Impact Explanation
This matches the accepted impact class "theft or permanent freezing of unclaimed yield": once a pool's rewarder is swapped via `addPool` while users still have an unclaimed balance in the old rewarder, that balance is permanently frozen with no recovery path in the codebase, resulting in a real, quantifiable, and irreversible loss of legitimately owed bribe rewards for every user who voted on that pool prior to the swap.

### Likelihood Explanation
This requires only ordinary, publicly-documented protocol operations: a user votes for `lp` (accruing rewards under `rewarderA`), and the owner later calls `addPool(lp, rewarderB, name)` — a normal maintenance action supported by the function (there is no guard preventing re-adding an already active pool with a different rewarder). No malicious intent or special privilege is needed from the admin; this is the intended way to update rewarder addresses. Once that occurs, the loss is automatic and unavoidable for any affected user — it does not require any additional action by an attacker.

### Recommendation
Before overwriting `poolInfos[lp].rewarder` in `addPool`, either (1) require the old rewarder's `totalSupply()`/staked balances to be zero (force full `unvote` migration first), or (2) implement an explicit migration routine that sweeps/forwards each user's outstanding `earned()` balance from the old rewarder to the new one (or lets users claim from the old rewarder even after replacement, e.g. by keeping a `mapping(address => address[]) previousRewarders` and exposing a `claimFromOldRewarder` path), and (3) revert `addPool` if `poolInfos[_lp].rewarder != address(0) && poolInfos[_lp].rewarder != _rewarder` unless the old rewarder is fully drained/migrated.

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `rewarderA` (`BribeRewardPool`) with `operator = manager`, and register it via `addPool(lp, rewarderA, "poolA")`.
2. User calls `vote([lp], [X])` → `rewarderA.stakeFor(user, X)` records `_balances[user] = X`.
3. Simulate bribe distribution to `rewarderA` (e.g. `queueNewRewards`) so `earned(user, rewardToken) > 0` on `rewarderA`.
4. Owner calls `addPool(lp, rewarderB, "poolA")`, overwriting `poolInfos[lp].rewarder = rewarderB`.
5. User calls `claimBribe([lp])`.
   - Assert: `rewarderB.earned(user, rewardToken) == 0` and no tokens transferred (new rewarder has no stake/reward history).
   - Assert: `rewarderA.earned(user, rewardToken)` is still `> 0` (funds still exist there).
   - Assert: there is no function reachable from `WombatBribeManager` (public/external) that can call `rewarderA.getReward(user, user)` anymore, since `poolInfos[lp].rewarder` no longer references `rewarderA` and `rewarderA.getReward` reverts for any caller other than `manager` (`onlyMasterMagpie`).
6. Confirm the user's previously-accrued reward is permanently unclaimable (freeze), demonstrating the loss.
