### Title
Stale line-index selection applied against a freshly re-fetched diff allows silent inclusion/exclusion of unreviewed content when committing partial changes - ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex` re-fetches the working-directory diff at commit time and blindly re-applies the user's `DiffSelection` (which addresses lines purely by numeric "absolute" index) against that freshly-fetched diff, without validating that the indices still correspond to the same reviewed content. This mirrors the SecondSwap bug pattern: a positional/rate-based recalculation (`releaseRate` re-derived from raw counters) is reapplied to state that has silently drifted, producing an outcome the user never approved.

### Finding Description
GitHub Desktop lets a user stage a subset of lines from a modified file for commit. The selection is stored in `DiffSelection` purely as a set of numeric line indices (`divergingLines`) relative to a specific diff snapshot — it has no notion of the actual line *content*: [1](#0-0) 

When the app itself detects that the diff may have changed while a file is being actively viewed, it does bother to reconcile the selection against a new set of `selectableLines`: [2](#0-1) 

However, this reconciliation only happens for the file currently displayed in the Changes view. When the user actually commits, `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` runs a **second, independent** diff fetch and reuses the *original* `WorkingDirectoryFileChange.selection` object (built against whatever diff was on screen when the user made the selection) directly against this brand-new diff: [3](#0-2) 

`formatPatch` then walks the new diff's hunks and asks `file.selection.isSelected(absoluteIndex)` — an index into the *new* diff — using divergence data that was computed against the *old* diff: [4](#0-3) 

There is no revalidation step here comparable to the `withSelectableLines` reconciliation used for on-screen refreshes, and no check that the diff used to build the patch is the same diff the user actually reviewed. If the on-disk file content changes between the moment the user reviews/selects lines and the moment `_commitIncludedChanges` executes (e.g. seconds later when the user clicks "Commit"), hunk boundaries and `unifiedDiffStart` offsets shift. The stale `divergingLines` set is then reinterpreted against different content, causing `formatPatch`/`applyPatchToIndex` to stage lines the user never selected (or omit lines the user did select) — exactly analogous to the vesting report's core defect: a positional recomputation (`releaseRate` re-derived from step counters) being reapplied to state that has drifted since it was captured, silently producing a result the actor never authorized.

Concretely: the file content the user is committing from can change due to any process writing to the working tree in that window — a build tool, an editor autosave, a background linter/formatter, or (most relevant to the "attacker-controlled repository" threat model) a git clean/smudge filter (e.g. Git LFS, `.gitattributes`-driven filters) firing on a checkout/merge that intersects with a commit-in-progress, or another concurrent Desktop-triggered git operation (pull/merge/stash) touching the same file while a commit is queued. None of these require local/physical device access or leaked credentials — only that the working tree changes while a user-approved partial-commit selection is in flight, something an adversary who controls repository content (via `.gitattributes` filters, merge drivers, or files that provoke filter re-smudging) can influence.

### Impact Explanation
This breaks the core trust invariant of "partial commit"/"partial stage" — that only the lines a user explicitly reviewed and checked are the ones that end up in the commit. Silent inclusion of unreviewed content (e.g. secrets, debug output, or lines from an attacker-influenced filter/smudge rewrite) into a commit that later gets pushed is a direct "silent corruption of what the user commits or pushes," matching the explicit valid-impact criteria of this assessment.

### Likelihood Explanation
The race window exists on every partial commit and does not require any unusual user behavior — any background process (including git's own filter machinery, another Desktop-initiated git command, or an external tool) writing to the file between selection and the "Commit" click is sufficient. Likelihood of a benign accidental trigger is moderate; likelihood of deliberate attacker exploitation depends on the attacker being able to arrange filter/smudge or merge-driver based content churn timed to a commit, which is a real but not always trivially controllable trigger — hence Medium likelihood, matching the report's own Medium-severity classification for the analogous smart-contract bug.

### Recommendation
- Before calling `applyPatchToIndex`/`formatPatch`, re-fetch the diff and reconcile the stored `DiffSelection` against it the same way `app-store.ts` does for on-screen refresh (`withSelectableLines`), rejecting/re-validating divergent lines rather than blindly reapplying stale indices.
- Prefer content-hash or line-content anchoring instead of pure positional indices for `DiffSelection`, so a shifted diff cannot silently remap a user's selection onto different content.
- If the diff fetched inside `applyPatchToIndex` differs from the diff the selection was derived from (e.g. compare a diff/content hash captured at selection time), abort the partial commit and force the user to re-review instead of silently proceeding.

### Proof of Concept
1. Open a repository in GitHub Desktop with a modified file containing multiple hunks/lines.
2. In the Changes view, deselect specific lines that should NOT be committed (e.g. a debug `console.log` or secret), leaving other lines selected — this state is stored purely as a set of numeric `divergingLines` in `DiffSelection`.
3. Before clicking "Commit", trigger any process that rewrites the same file on disk such that hunk boundaries shift (e.g. an editor autosave that reformats/reindents earlier lines, or in the attacker-controlled scenario, a `.gitattributes` clean/smudge filter that rewrites the file as part of a concurrent `git` operation Desktop is running).
4. Click "Commit" immediately. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`) and applies the old `DiffSelection` object's line indices to the new diff via `formatPatch` (`app/src/lib/patch-formatter.ts:157`).
5. Inspect the resulting commit: because the line indices in the stale selection now point at different content in the new diff, the committed patch includes/excludes different lines than what the user checked in the UI — with no warning or diff re-validation shown to the user.
