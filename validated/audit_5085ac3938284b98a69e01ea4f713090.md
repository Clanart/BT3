### Title
Stale line-selection indices silently applied to a re-fetched diff, causing wrong lines to be staged/committed - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop lets users select specific lines/hunks of a modified file to include in a commit (partial staging) or to discard. That selection (`DiffSelection`) is stored purely as a set of *numeric line indices* relative to the diff that was displayed when the user made the selection. It carries no reference to the actual diff content. When the working-directory file changes (e.g. it is modified externally between the moment the user reviews/selects lines and the moment the commit/discard actually executes), Desktop's staging code re-fetches a brand-new diff for the file and reapplies the old numeric-index selection against it, without ever checking that the new diff's line layout still matches what the user saw and selected against.

### Finding Description
- The user's line selection is represented as a `Set<number>` of "diverging" line indices with no link to diff content (`app/src/models/diff/diff-selection.ts:78-84,121-136`). [1](#0-0) 
- When the repository status refreshes (which happens continuously via file-system watching and periodic refresh), `updateChangedFiles` preserves the *old* selection object verbatim on the file, even though the file's diff/hunks may now be structurally different: `return file.withSelection(existingFile.selection)`. [2](#0-1) 
- When the user commits or discards, `applyPatchToIndex`/`discardChangesFromSelection` re-fetch a **fresh** diff at execution time via `getWorkingDirectoryDiff` (not the one originally displayed to the user). [3](#0-2) 
- `formatPatch`/`formatPatchToDiscardChanges` then walk the *new* diff's hunks/lines and check `file.selection.isSelected(absoluteIndex)` using indices computed against the new diff's structure — but those indices were chosen by the user against the old diff. [4](#0-3) [5](#0-4) 

No guard compares the new diff to the diff the selection was computed from (no hash/line-count/content check), and the generated patch is applied with `git apply --cached --unidiff-zero` which uses only line numbers, not context, so a size/shape mismatch does not necessarily cause a hard failure — it can silently apply to the wrong lines. [6](#0-5) 

This is the structural analog of the reported bug class: a value (seat price / here, "which lines are selected") is computed against one state snapshot, but is applied against a later, potentially different state snapshot, with no validation that the two snapshots still agree.

### Impact Explanation
If the working tree file is modified between the time the user reviews a diff and selects lines to include/exclude and the time Desktop actually stages/commits or discards, the selected line indices from the old diff can now correspond to entirely different lines (different additions/deletions/context) in the freshly fetched diff. This can cause:
- Unintended lines being silently included in a commit that the user explicitly deselected, or
- Intended lines being silently excluded, or
- `discardChangesFromSelection` discarding the wrong changes.

This is "silent corruption of what the user commits" — the user is given no warning, and the resulting commit/discard does not match what they saw and approved in the UI.

### Likelihood Explanation
The race window exists any time something else touches the working file between selection and action: an editor autosave, a build tool/watcher, a formatter-on-save, a git hook, or another process (any of which are ordinary desktop workflows, not privileged/local-attacker scenarios). Desktop's own architecture invites this because status/diff refresh is asynchronous and decoupled from the moment the user actually triggers commit, and selection state is explicitly carried forward across refreshes without invalidation.

### Recommendation
Before generating/applying the patch in `applyPatchToIndex` and `discardChangesFromSelection`, compare the freshly fetched diff against the diff the current selection was computed from (e.g., by diff text/hash or hunk-shape comparison). If they differ, refuse to apply the stale selection and force Desktop to re-diff and require the user to re-review/re-select before staging or discarding, rather than silently reusing index-based selection across an unvalidated diff change.

### Proof of Concept
1. Modify a tracked file, open Desktop's Changes view, and select only a subset of lines (e.g., lines in hunk 2) for partial commit — this creates a `DiffSelection` with diverging indices tied to the currently-displayed diff (`app/src/models/diff/diff-selection.ts`).
2. Before clicking "Commit", externally modify the same file in a way that shifts line counts (e.g., an editor autosave, formatter, or background script inserts/removes lines above the selected hunk) — file-system watchers keep the file in the working directory list with the same `file.id`, and `updateChangedFiles` preserves the old selection object unchanged (`app/src/lib/stores/updates/changes-state.ts:56`).
3. Click "Commit". `applyPatchToIndex` fetches a fresh diff (`getWorkingDirectoryDiff`) reflecting the modified file, then `formatPatch` walks this new diff's hunks and applies the old selection's numeric indices to decide which lines to include (`app/src/lib/patch-formatter.ts:143-171`).
4. Because the line/hunk offsets shifted, the indices the user selected in step 1 now point to different content in the new diff — the resulting commit contains lines the user did not intend, or omits lines the user did intend, with no warning shown.

    private readonly defaultSelectionType:

    private readonly divergingLines: Set<number> | null = null,
    private readonly selectableLines: Set<number> | null = null
  ) {}

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
