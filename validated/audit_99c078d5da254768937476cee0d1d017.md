### Title
Governance-configurable `Kip71GasTarget = 0` causes a division-by-zero panic in `NextMagmaBlockBaseFee`, crashing block verification and public RPC gas-price queries - (File: params/kip71_config.go)

### Summary
The KIP-71 dynamic base fee calculation `NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without checking it for zero, and the governance parameter registry accepts any `uint64` value for `Kip71GasTarget` (including `0`) because it uses a no-op format checker. This mirrors the reported class of bug where a critical numeric/pricing computation is expected to fail gracefully (or be guarded) but instead can be driven into an unhandled runtime error, propagating unexpected failures to every caller/consumer of that computation (here: header verification, tx pool, block building, and public gas-price RPC endpoints) instead of behaving predictably.

### Finding Description
`NextMagmaBlockBaseFee` computes the delta to the base fee using `gasTarget` as a divisor in both the "used > target" and "used < target" branches: [1](#0-0) 

`gasTarget := kc.GasTarget` is taken directly from the `KIP71Config` with no zero-check before being used as a `big.Int` divisor via `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `big.Int.Div` panics when the divisor is zero.

The governance parameter that feeds `GasTarget` is registered with a `noopFormatChecker`, meaning no format/range validation is performed when governance sets this value: [2](#0-1) 

This differs from the KIP-71 config's own defensive handling of `BaseFeeDenominator == 0` (which is special-cased to avoid div-by-zero) — no equivalent guard exists for `GasTarget == 0`: [3](#0-2) 

`NextMagmaBlockBaseFee` is invoked from multiple consensus- and RPC-critical paths, including block header verification (`VerifyMagmaHeader`), the tx pool, block building (`worker.go`), and the public gas price RPC handlers (`node/cn/gasprice/gasprice.go`, `node/cn/gasprice/feehistory.go`).

### Impact Explanation
If `GasTarget` is ever set to `0` via governance (which is not prevented by the current `FormatChecker`), any block whose parent used nonzero gas will cause `NextMagmaBlockBaseFee` to divide by zero and panic. Because this function executes during header verification on every node, it results in a chain-wide crash/DoS across all nodes attempting to verify or build the next block — a full consensus halt rather than a localized error. It is also reachable via the public `eth_gasPrice`/`klay_gasPrice` RPC path, so any public RPC caller querying gas price after such a misconfiguration would crash the serving node process/goroutine.

### Likelihood Explanation
Triggering this requires the governance parameter `Kip71GasTarget` to be set to `0`, which is a governance action, not a plain unprivileged transaction. However, unlike a value-bounds check that would normally reject unsafe governance inputs, there is currently no such check (`noopFormatChecker`) — meaning a single governance vote/misconfiguration (accidental or malicious) is enough to brick the entire network's base-fee computation. Given governance parameter safety is explicitly in scope, and the absence of any validation is itself the vulnerability (paralleling the oracle's missing error-handling in the original report), likelihood is non-negligible for a chain that allows this parameter to be changed without bounds checking.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally all KIP-71 parameters) that rejects `0` (and any other value that could produce degenerate/unsafe results), consistent with the existing defensive fallback already present for `BaseFeeDenominator == 0`. Additionally, add a defensive zero-check directly inside `NextMagmaBlockBaseFee` before dividing by `gasTarget`, mirroring the existing fallback pattern used for `baseFeeDenominator`.

### Proof of Concept
1. Governance sets `governance.kip71.gastarget` to `0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, see `kaiax/gov/param.go`).
2. Once effective, a block is produced with parent `GasUsed > 0`.
3. During header verification, `KIP71Config.NextMagmaBlockBaseFee` is called; since `parentGasUsed (>0) > gasTarget (0)`, execution reaches `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing `big.Int.Div` to panic.
4. The panic propagates through header verification on every node validating the block, and separately through any RPC node servicing `eth_gasPrice`/`klay_gasPrice`, causing a crash/DoS.
