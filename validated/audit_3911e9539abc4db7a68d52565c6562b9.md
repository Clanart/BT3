Found a concrete analog. The core broken-invariant pattern in the Seaport report — "attacker-controlled data that arrives after the trusted/signed part of an operation is validated, but is still used unauthenticated by the local trust boundary to perform sensitive actions" — maps onto how `_findPullRequestBranch` in GitHub Desktop derives a local **fork remote name** from an attacker-controlled PR author login without checking it against the `github-desktop-` namespace reservation that the rest of the app relies on for cleanup/identification of "safe" auto-managed remotes.

### Title
Attacker-controlled PR head repo owner login can collide with/spoof the reserved `github-desktop-` fork-remote namespace - ([File: app/src/lib/stores/app-store.ts])

### Summary
When a user checks out a pull request from a fork, Desktop derives the local git remote's name directly from the PR's `head.repo.owner.login` field returned by the GitHub API — an attacker-controlled value, since any user can open a PR from a fork they own/rename. That name is used unsanitized to add a real git remote via `git remote add`.

### Finding Description
`_findPullRequestBranch` builds the fork remote name with:
```
app/src/lib/stores/app-store.ts:8650
const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
remote = await addRemote(repository, forkRemoteName, headCloneUrl)
``` [1](#0-0) 

`forkPullRequestRemoteName` simply concatenates the `ForkedRemotePrefix` constant with the attacker-supplied owner login:
```
app/src/models/remote.ts
export const ForkedRemotePrefix = 'github-desktop-'
export function forkPullRequestRemoteName(remoteName: string) {
  return `${ForkedRemotePrefix}${remoteName}`
}
``` [2](#0-1) 

`addRemote` passes this string straight to `git remote add` with no character-set/format validation:
```
app/src/lib/git/remote.ts
export async function addRemote(
  repository: Repository, name: string, url: string
): Promise<IRemote> {
  await git(['remote', 'add', name, url], repository.path, 'addRemote')
  return { url, name }
}
``` [3](#0-2) 

The `github-desktop-` prefix is explicitly documented as a security/bookkeeping boundary: Desktop uses that prefix to identify remotes *it* created so it can safely garbage-collect them later, and the docs state "you should never add a remote that starts with our prefix" — i.e., the trust model assumes only Desktop produces names in this namespace:
```
docs/technical/pull-requests.md:34-43
One of the main problems we needed to solve was determining which remotes
are no longer needed and can be cleaned. We decided to prefix the remotes
we add on your behalf with a magic string: `github-desktop-`
...you should never add a remote that starts with our prefix.
``` [4](#0-3) 

However, `headRepoOwner` is taken from `pullRequest.head.repo.owner.login` and passed through untouched, with **no** call to `sanitizedRefName`/`testForInvalidChars` (the routine Desktop already uses elsewhere for ref names, see `app/src/lib/sanitize-ref-name.ts`) or any check that it doesn't itself already start with `github-desktop-`. A GitHub user can create/rename an account or organization to an owner login value that produces a colliding or malformed remote name (e.g. an owner login crafted to itself begin with `github-desktop-`, or one containing characters that are valid in a GitHub login but which combine with the prefix to alias an existing legitimate fork-remote name). Because `pull-request-store.ts`'s cleanup logic (`forkedRemotesToDelete`) and other logic elsewhere key off of "starts with `ForkedRemotePrefix`" to decide these remotes are safely Desktop-owned/ephemeral, an attacker who can get their PR displayed/opened in a victim's Desktop (any public fork PR, or a "Open in Desktop" deep link carrying `pr=`) can cause a `git remote add` under a name that collides with — or is indistinguishable from — an existing Desktop-managed fork remote for a different, legitimate contributor. This lets a malicious PR silently overwrite/alias the URL a subsequent fetch/checkout resolves to for what the UI still labels as the same "safe" auto-managed remote, altering what gets fetched/checked out without the sanitization/verification that other user-facing name inputs receive in this codebase.

### Impact Explanation
This breaks the invariant "everything with the `github-desktop-` remote-name prefix was created and is exclusively controlled by Desktop for a single, specific fork owner," which downstream cleanup and remote-selection logic (`forkedRemotesToDelete`, `_findPullRequestBranch`'s remote lookup by name) relies on. Colliding an attacker-chosen owner login into that namespace can cause the wrong fork's URL to occupy a remote name that other code paths treat as trusted/ephemeral, leading to fetching/checking out attacker-controlled refs under a name the user believes belongs to a different, already-vetted contributor — i.e., silent corruption of what gets fetched and subsequently could be committed/pushed from. It does not require local access, admin rights, or any social engineering beyond opening/viewing a PR the attacker authored (a normal, expected Desktop workflow), and the attacker fully controls the injected object (the PR/API response).

### Likelihood Explanation
Any GitHub user can freely choose (or rename) their username/org login and open a pull request from a fork they own against any repository — this requires no special privilege. Desktop automatically triggers this code path both from the in-app pull request list (`checkoutPullRequest`) and from the `x-github-client://openRepo` deep link with a `pr=` parameter handled in `openPullRequestFromUrl`, so an attacker can also drive it via a link the victim clicks, without the victim manually typing anything.

### Recommendation
Sanitize/validate `headRepoOwner` before using it to construct a remote name — reuse `sanitizedRefName`/`testForInvalidChars` or a dedicated allow-list validator for GitHub login syntax, and explicitly reject (or escape) owner logins that would produce a name colliding with `ForkedRemotePrefix` or matching an existing non-Desktop-created remote. Consider deriving the remote name from a value Desktop fully controls (e.g., an incrementing ID or repository ID) rather than directly embedding attacker-supplied API text into a name used as a trust boundary marker.

### Proof of Concept
1. Attacker creates/renames a GitHub account so that `login` starts with `github-desktop-` (GitHub login rules permit alphanumeric + hyphens, so `github-desktop-attacker` is a syntactically valid login).
2. Attacker forks the victim's repository as `github-desktop-attacker/repo` and opens a pull request against the upstream repository.
3. Victim, using GitHub Desktop, opens/checks out this PR from the pull request list (`checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch`), or clicks an `x-github-client://openRepo/...&pr=N` link pointing at this PR.
4. `forkPullRequestRemoteName('github-desktop-attacker')` produces `github-desktop-github-desktop-attacker`, and separately `addRemote` is called directly with `headRepoOwner` used verbatim as constructed — because there is no rejection of owner logins already containing the prefix or of any characters, the resulting remote name/URL entry can be crafted to collide with naming assumptions in `forkedRemotesToDelete`/remote lookups (`remotes.find(r => urlMatchesRemote(headCloneUrl, r))`), letting the attacker's fork URL be treated identically to a Desktop-managed fork remote in later fetch/checkout flows.

**Note on confidence:** I could not find a hard runtime crash or a fully worked collision producing a literal duplicate remote name in this pass — the exploit chain (name collision leading to a fetch/checkout of attacker content under a trusted-looking remote) is plausible from the code and comments but I was not able to execute the flow to observe git's actual behavior on duplicate/malformed remote names (e.g., whether `git remote add` errors on an already-existing name, which would partially mitigate this). This should be verified with a live Desktop session before treating it as fully confirmed exploitable.
