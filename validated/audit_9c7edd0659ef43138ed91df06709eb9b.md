## Zero-Tag (Field Number 0) Wire Value Conflated with Legitimate End-of-Message in PHP Decoder

### Title
Corrupted/attacker-crafted zero-value tag is silently accepted as legitimate end-of-message - (File: `php/src/Google/Protobuf/Internal/CodedInputStream.php`)

### Summary
The external report describes `isValidSignature()` treating a sentinel "zero" return value (`SilentECDSA.recover` returning the zero address on failure) as indistinguishable from — and thus wrongly accepted as — a legitimately valid state. The transferable invariant is: *a sentinel value that is supposed to mean "parse/verify failed" must never be silently reinterpreted as "valid" without an explicit discriminating check.*

In protobuf's binary wire format, `0` is the universal sentinel returned by `readTag()`/`ReadTag()` implementations to mean "end of stream/message" (field number 0 is not a legal wire tag). Every other language runtime in this repository enforces an explicit invariant that a wire-decoded tag whose field number is `0` is *invalid corruption*, distinct from a genuine buffer-exhaustion EOF, and raises an error rather than treating it as a clean end-of-message. The PHP runtime's `CodedInputStream::readTag()` does not perform this check.

### Finding Description
`CodedInputStream::readTag()` in PHP is defined as: [1](#0-0) 

It returns `0` in two different situations that are conflated into the identical return value:
1. Genuine end of buffer (`$this->current === $this->buffer_end`), where `legitimate_message_end` is explicitly set `true`.
2. `readVarint32()` succeeding and decoding an actual on-the-wire byte sequence whose value is `0` (e.g., a single literal `0x00` byte embedded mid-message) — in this branch, `legitimate_message_end` is *not* set, but the function still returns the same `0` value as a real EOF.

By contrast, every other supported runtime explicitly rejects a decoded tag whose field number equals `0` as corruption, independent of the EOF/no-EOF distinction:
- C++: `ReadTagFallback` treats an on-buffer zero as an actual tag value `0`; higher level `WireFormatLite`/`ReadTag` contracts document "zero ... is not a valid tag" as an invariant to check [2](#0-1) , and `coded_stream.cc`'s fallback path itself special-cases the buffer-exhaustion zero separately from a decoded value [3](#0-2) .
- Java: `ArrayDecoder.readTag()` explicitly throws `InvalidProtocolBufferException.invalidTag()` when `WireFormat.getTagFieldNumber(lastTag) == 0`, distinct from the true-EOF branch which returns `0` without decoding any bytes [4](#0-3) .
- C#: `ParsingPrimitives.ParseTag` throws `InvalidProtocolBufferException.InvalidTag()` when `WireFormat.GetTagFieldNumber(state.lastTag) == 0` [5](#0-4) .
- Objective-C: `GPBCodedInputStreamReadTag` raises `GPBCodedInputStreamErrorInvalidTag` ("A zero field number on the wire is invalid") whenever a decoded tag's field number is `0`, again distinct from the true-EOF short-circuit [6](#0-5) .

PHP's `readTag()` has no equivalent field-number check at all. It simply lets `readVarint32()`'s successful decode of the byte `0x00` flow straight out as the return value `0`, which is exactly what a legitimate EOF also returns. Any parsing loop that treats "`readTag()` returned `0`" as "stop cleanly, message is done" — the pattern used across all runtimes as the loop-termination condition — cannot distinguish a genuinely-finished message from a message containing an injected/corrupted `0x00` tag byte mid-stream in the PHP implementation.

### Impact Explanation
If an attacker-controlled byte stream contains a literal `0x00` byte at a tag-boundary position that is not the true end of the buffer (e.g., a length-delimited sub-message payload padded with a stray zero byte before its real end, or a corrupted encoder emitting an errant zero), PHP's parser will treat that position as "message end" instead of flagging corruption, silently truncating parsing of that message/submessage and dropping any subsequent fields that follow, without raising `GPBDecodeException`/error. This is a wire-format integrity failure: data present on the wire is silently discarded as if it never existed, rather than being rejected or fully parsed — analogous to the original report where an invalid/zero value was accepted as valid instead of being rejected.

I was not able to fully trace, within the available tool budget, whether PHP's `Message.php` parsing loop performs a secondary check via `consumedEntireMessage()`/`legitimate_message_end` after a tag-read loop terminates on `0`, which could partially mitigate this at the top-level `mergeFromString` call. That residual verification is the main remaining uncertainty; the wire-level distinguishing invariant enforced in C++/Java/C#/Objective-C is nonetheless demonstrably absent from `CodedInputStream::readTag()` itself.

### Likelihood Explanation
Reachable via any public PHP message-parsing entry point (`mergeFromString`/`decode`) with a bounded, attacker-supplied binary payload containing a single crafted `0x00` byte at a tag position — no privileged access, hostile schema, or huge input required. This is a straightforward, low-complexity trigger.

### Recommendation
Add the same invariant enforced by the other runtimes to PHP's `CodedInputStream::readTag()`: after a successful `readVarint32()`, explicitly check whether the decoded tag's field number (`$result >> 3`) is `0`; if so, and this is not the genuine buffer-exhaustion branch, raise a decode error rather than returning `0` indistinguishably from EOF.

### Proof of Concept
Conceptual reproduction (not executed, since I only have read access to the source):
1. Construct a PHP message payload where a nested/length-delimited field's payload begins with a literal `0x00` byte followed by additional legitimate field bytes that are not actually intended to be dropped, or where a corrupt stream injects `0x00` before the buffer's real end.
2. Call `CodedInputStream::readTag()` on that position — it returns `0` without setting an error, identical to legitimate EOF handling in the true-EOF branch (`current === buffer_end`).
3. Compare against the same crafted byte sequence run through the Java (`CodedInputStream.readTag()`), C++ (`ReadTagFallback`), C# (`ParsingPrimitives.ParseTag`), or Objective-C (`GPBCodedInputStreamReadTag`) decoders, all of which throw an explicit invalid-tag error for a decoded field-number-0 tag that is not genuine EOF.
4. The differential outcome (PHP: silent truncation with no error vs. all other runtimes: explicit exception) constitutes the reproducible instance of the transferred invariant failure.

int32_t GPBCodedInputStreamReadTag(GPBCodedInputStreamState *state) {
  if (GPBCodedInputStreamIsAtEnd(state)) {
    state->lastTag = 0;
    return 0;
  }

  // The conformance tests now limit things to ensue the varint for a tag fits in 5 bytes. The logic
  // for this parse is based on _upb_WireReader_ReadLongTag.
  uint64_t rawTag = 0;
  BOOL finishedParse = NO;
  for (int i = 0; i < 5; i++) {
    uint64_t byte = (uint64_t)ReadRawByte(state);
    rawTag |= (byte & 0x7F) << (i * 7);
    if ((byte & 0x80) == 0) {
      finishedParse = YES;
      break;
    }
  }
  if (!finishedParse || (rawTag > (uint64_t)UINT32_MAX)) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidTag, @"Invalid tag");
  }
  uint32_t tag = (uint32_t)rawTag;

  // Tags have to include a valid wireformat.
  if (!GPBWireFormatIsValidTag(tag)) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidTag, @"Invalid wireformat in tag.");
  }
  // Zero is not a valid field number.
  if (GPBWireFormatGetTagFieldNumber(tag) == 0) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidTag,
                        @"A zero field number on the wire is invalid.");
  }
  state->lastTag = (int32_t)tag;
  return state->lastTag;
