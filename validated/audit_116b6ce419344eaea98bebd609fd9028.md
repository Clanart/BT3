### Title
Unauthenticated `InternalSendTx` broadcasts attacker-supplied Bitcoin transactions when `client_verification=false` - ([File: core/src/rpc/aggregator.rs])

### Summary
The `is_internal` authorization check in `only_aggregator_and_self` is only ever consulted when the aggregator's gRPC server is built with `Interceptors::OnlyAggregatorAndSelf`. When `config.client_verification` is `false`, `create_grpc_server` installs `Interceptors::Noop` instead, which passes every request through unchecked. This makes `ClementineAggregator::internal_send_tx` — intended to be callable only by the aggregator itself — reachable by any unauthenticated network client, allowing them to insert an arbitrary signed Bitcoin transaction into the tx_sender's fee-bumping/broadcast queue.

### Finding Description
The intended binding is: `caller-that-reached-internal_send_tx == aggregator-itself`, enforced by `is_internal(&req)` inside `only_aggregator_and_self`, which requires `leaf_cert == our_cert` [1](#0-0) .

This check is only wired in when the interceptor variant is `OnlyAggregatorAndSelf`. `create_grpc_server` picks the interceptor based on `config.client_verification`: if `false`, it installs `Noop`, which returns `Ok(req)` unconditionally for every request, and also skips setting `client_ca_root` on the TLS config, so no client certificate is required at the TLS layer either [2](#0-1) [3](#0-2) .

With `Noop` installed, an unauthenticated client can call `InternalSendTx` on the aggregator with an arbitrary `SendTxRequest{raw_tx, fee_type}`. `internal_send_tx` deserializes `raw_tx` into a `bitcoin::Transaction` and, when the `automation` feature is enabled, hands it directly to `self.tx_sender.insert_try_to_send(...)` with no further validation of its origin, structure, or relation to any bridge state [4](#0-3) . `insert_try_to_send` simply persists the transaction into the send/fee-bump queue for later broadcast by the tx-sender background loop [5](#0-4) ; the queue processing logic performs no bridge-specific authorization — it treats any inserted transaction as legitimate and works to get it confirmed via CPFP/RBF, then broadcasts it, as demonstrated by the existing e2e test that legitimately uses this exact call to broadcast a round tx [6](#0-5) .

No other guard intervenes: `is_internal` is dead code on this path (never invoked because `Noop` doesn't call it), and `internal_send_tx` itself performs no caller-identity check of its own — it relies entirely on the interceptor layer.

### Impact Explanation
On a deployment with `client_verification=false` and the `automation` feature enabled, any network-reachable unauthenticated attacker can submit arbitrary transactions to be broadcast through the aggregator's own wallet/fee-bumping infrastructure (CPFP/RBF), consuming the aggregator's fee-bumping UTXOs/funds and broadcasting transactions of the attacker's choosing. This is an unauthenticated, state-changing, broadcasting call — matching the High severity category directly. It is repeatable per request/connection and does not require any prior deposit, withdrawal, or key material.

### Likelihood Explanation
This requires the specific deployment configuration `client_verification=false` and network reachability to the aggregator's gRPC port, plus the `automation` cargo feature enabled (the default build path for a running node, since without it the endpoint is `unimplemented`). No BTC cost, credential, or on-chain precondition is needed by the attacker beyond crafting a valid `bitcoin::Transaction` byte encoding — an unprivileged attacker per the threat model can trivially do this. The only variable is whether operators deploy with `client_verification=true` (the documented/example default in `.env.example` and `bridge_config.toml` is `true`), which materially reduces exposure but does not eliminate the code-level defect: the `Noop` path exists and is a supported configuration.

### Recommendation
Do not rely solely on `client_verification`/mTLS to gate `Internal*` RPCs. Enforce the `is_internal` restriction unconditionally regardless of the `Noop`/`OnlyAggregatorAndSelf` choice (e.g., always require a valid self-certificate or a separate always-on authentication mechanism for methods whose gRPC method name starts with `Internal`), or refuse to start the aggregator's TCP server with `Internal*` methods exposed when `client_verification` is `false`.
