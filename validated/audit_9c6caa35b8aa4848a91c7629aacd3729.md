### Title
Cached DKG-confirmation nonces are reused across validator-set contexts, enabling validator-key recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
`DkgConfirmer` scopes its cached FROST preprocess only by the static label `b"DkgConfirmer"` and the DKG `attempt`, omitting the validator set/session/genesis. Consequently, confirmations for different validator sets that reuse the same attempt number reload the same 32-byte preprocess seed and regenerate identical nonce material. Multiple published signature shares can then be combined to recover the validator’s private MuSig key.

### Finding Description
`DkgConfirmer::signing_protocol` constructs `context = (b"DkgConfirmer", self.attempt)`, without binding it to `self.spec`, `self.spec.set()`, `self.spec.genesis()`, or the participant/key set. [1](#0-0) 

`SigningProtocol::preprocess_internal` uses that context both as the database key and as part of the cache encryption preimage. [2](#0-1) 

When a cache entry already exists, `preprocess_internal` decrypts it and calls `AlgorithmSignMachine::from_cache`, deterministically recreating the machine and preprocess from the same seed. [3](#0-2) 

`from_cache` reconstructs the preprocess through `seeded_preprocess`, which seeds `ChaCha20Rng` directly with the cached 32-byte value and derives the same nonce commitments from that stream. [4](#0-3) 

The FROST implementation explicitly warns that a cached preprocess must only be used once because reuse enables recovery of the private key share. [5](#0-4) 

The coordinator relies on deterministic nonces being uniquely context-bound; its own safety analysis states that reusing nonces across signing sessions is unsafe and that safety is derived from context binding. [6](#0-5) 

### Impact Explanation
A validator key reused by multiple validator-set confirmations can produce several signature shares under the same cached nonce seed whenever those confirmations use the same `attempt`.

Across sessions, the public signing data—including participant commitments, group-key context, and the `set_keys_message`—can differ, while the signer’s underlying seed-derived nonce pair remains identical. [7](#0-6) 

Each resulting share is a public linear equation involving the same seed-derived nonce components and the validator’s private key. Once enough independent sessions are observed, an observer can solve those linear equations for the validator’s private MuSig key. Possession of that key allows the attacker to impersonate the validator in subsequent root-of-trust confirmation signatures and related validator-controlled operations.

This reaches the protocol through ordinary DKG-confirmation messages: `share_internal` accepts serialized participant preprocesses, passes them through `read_preprocess`, and signs the constructed message. [8](#0-7) 

### Likelihood Explanation
The collision does not require malformed encodings, compromised storage, or control of the validator’s private key; it only requires multiple confirmation contexts that share an `attempt` value while using the same validator key and coordinator database.

Attempts are likely to repeat across independent validator sets or DKG sessions, especially at common values such as `0` or `1`. Because the cache key excludes the validator-set identity, an otherwise legitimate second confirmation at the same attempt silently reloads the old nonce seed rather than generating a new one.

The protocol explicitly intends to publish signature shares for aggregation, so no private datastore disclosure is required; the data needed for the linear key recovery is already part of the confirmation protocol. [9](#0-8) 

### Recommendation
Include the full confirmation identity in `DkgConfirmer`’s cache context, not merely the attempt.

At minimum, bind the context to:

- the tributary/spec genesis or other globally unique validator-set identifier;
- `self.spec.set()`;
- the DKG `attempt`;
- preferably the exact participant list or MuSig participant public keys and the key pair being confirmed.

For example, derive the context from a transcript/hash covering `spec.genesis()`, `spec.set()`, `attempt`, participant keys, removed keys, and `KeyPair`, then use that digest for both `CachedPreprocesses` and the cache-encryption preimage. Also consider deleting or marking a cached preprocess as consumed once a share has been emitted, so later re-execution fails closed instead of re-signing with reused nonce material.

### Proof of Concept
The collision can be expressed with two `DkgConfirmer` instances that represent different validator sets but use the same coordinator database, validator key, and attempt:

```rust
let attempt = 0;

let mut confirmer_a =
  DkgConfirmer::new(validator_key, spec_a, txn_a, attempt).unwrap();
let mut confirmer_b =
  DkgConfirmer::new(validator_key, spec_b, txn_b, attempt).unwrap();
```

Both construct the same cache key:

```rust
let context_a = (b"DkgConfirmer", attempt);
let context_b = (b"DkgConfirmer", attempt);
assert_eq!(context_a.encode(), context_b.encode());
```

The first call stores an encrypted random seed under that key; the second call reads and decrypts the same entry. [10](#0-9) 

Therefore, both invocations execute the equivalent of:

```rust
let seed = CachedPreprocesses::get(txn, &(b"DkgConfirmer", attempt)).unwrap();
let (machine, _) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(seed));
```

Even though the resulting `set_keys_message`, removed set, participant set, or group-key context differs, the FROST seed-derived nonce pair is regenerated identically. Repeating this across enough distinct same-attempt confirmation sessions produces independent public share equations over the same hidden nonce material and private key, enabling linear recovery of the validator key as warned by the FROST cache contract. [11](#0-10)

    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {

      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

/// A cached preprocess.
///
/// A preprocess MUST only be used once. Reuse will enable third-party recovery of your private
/// key share. Additionally, this MUST be handled with the same security as your private key share,
/// as knowledge of it also enables recovery.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
