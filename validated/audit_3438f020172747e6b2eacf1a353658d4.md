### Title
`ReceivedOutput::read` trusts a serialized scalar offset instead of re-deriving it from the output's `script_pubkey`, allowing phantom/unspendable outputs to be registered as spendable funds - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The bug class in the external report is *a tracked quantity is written from a locally-computed/claimed value under the assumption that an intervening operation could only preserve or increase it, rather than being re-queried from ground truth*. In `bitcoin-serai`, the analogous pattern is `ReceivedOutput`: a spendable-output record binds three fields — `offset` (the scalar that is supposed to satisfy `key + G·offset == output key`), `output` (`TxOut`), and `outpoint` — but no code path ever checks that the claimed `offset` actually derives the `script_pubkey` of the claimed `output`. `ReceivedOutput::read` deserializes all three fields from untrusted bytes with zero consistency check (`networks/bitcoin/src/wallet/mod.rs:122-134`), and `Scanner::scan_transaction` likewise trusts the *first-stored* offset for a script, which is not necessarily the offset the consumer logically registered (`mod.rs:180-214`). The "actual" spendability relation is never recomputed — exactly like `s.totalLiquidity` being set from a cached local instead of `_getTotalLiquidity()`.

### Finding Description
Two complementary halves form the analog:

1. **Stale/assumed offset from `Scanner`.** `register_offset` increments a requested offset until `key + G·offset` has even Y, and stores `script_pubkey → offset` in `self.scripts` (`mod.rs:180-196`). Because offsets are surjective (documented at `mod.rs:174-176`), two different *logical* offsets can converge onto the same script; the map keeps only the first. `scan_transaction` then reports every matching output with that stored `offset` (`mod.rs:205-211`), even though the caller may have intended a different registered offset for that script — the stored value is assumed correct rather than validated against intent. An output is reported as spendable under `offset`, and if the consumer re-keys per input using a *different* offset it associated with that script, the reported `ReceivedOutput` yields a tweaked key that does not match — funds reported received that are not spendable under the expected key.

2. **Unverified claimed offset from `ReceivedOutput::read`.** `read` is listed in scope as an untrusted-bytes sink. It accepts any `Scalar` via `Secp256k1::read_F`, any `TxOut`, and any `OutPoint`, and packages them into a `ReceivedOutput` that downstream code treats as a spendable receipt (`mod.rs:122-134`). Nothing verifies `p2tr_script_buf(key + G·offset) == output.script_pubkey`. An unprivileged peer can therefore supply a `ReceivedOutput` claiming receipt of funds whose offset does not correspond to the output's key — the deserialized field is trusted like the cached `_totalLiquidity`, never reconciled with the actual on-chain/script relation.

### Impact Explanation
Consumers of `ReceivedOutput` (the Serai processor's output-tracking and `send.rs` transaction building) treat `offset` as authoritative for spending. An output whose stored/claimed offset does not derive its `script_pubkey` is *reported received but not spendable*: either the spend fails BIP-340/341 verification on the Bitcoin network (signed with the wrong tweaked key), or — worse — the phantom `outpoint`/`value` claims inflate the tracked balance, causing the processor to construct transactions around inputs that can never confirm. This mirrors the report's downstream-corruption impact: the next process (deposit/share-minting there, transaction construction here) consumes a number that does not reflect reality.

### Likelihood Explanation
Reachable by unprivileged parties: any peer that can feed bytes to `ReceivedOutput::read`, and any sender who can craft outputs whose scripts collide with an already-registered offset script (the surjectivity means an attacker funding the multisig address can exploit ordering dependence). No malicious validator, collusion, or leaked key is required — only public transaction data or serialized messages. **Caveat:** the concrete harm level depends on how downstream code (out of `crypto.rs`/`wallet/` scope) consumes `ReceivedOutput`; if every consumer re-verifies, impact degrades to a lie about balances rather than unspendable funds. Within the wallet crate itself, the missing invariant check is real.

### Recommendation
Add a consistency check binding offset to script. In `ReceivedOutput::read` (and in any constructor), verify the relation before accepting:

```rust
// after decoding, given the scanner's key is known to the reader context
if p2tr_script_buf(key + (ProjectivePoint::GENERATOR * offset))
    != Some(output.script_pubkey.clone())
{
    return Err(io::Error::other("offset does not derive output script"));
}
```

This requires threading the base `key` into `read` (or exposing a `verify(key)` method and mandating its use, analogous to the report's `s.totalLiquidity = _getTotalLiquidity(s.tokenId)` fix). For `Scanner`, consider storing *all* offsets that map to a script (or rejecting a registration whose incremented offset collides with a previously registered logical offset) so `scan_transaction` reports the offset the consumer actually intended.

### Proof of Concept
```rust
// Attacker crafts a ReceivedOutput with an offset unrelated to the output's key
let fake = ReceivedOutput {
    offset: Scalar::ONE,               // arbitrary; does not derive the script below
    output: TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: victim_script,  // script_pubkey of an output the multisig does NOT control
    },
    outpoint: OutPoint::new(real_txid, 0),
};
let bytes = fake.serialize();
let parsed = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // succeeds: no check
// parsed.value() reports 100_000 sats received; any attempt to spend via offset=1
// produces a tweaked key that does not match victim_script -> unspendable / invalid sig.
```

Similarly, for the scanner side: register offset `o` (odd point → bumped to `o+1`, stored for script `S`), then register `o+1` directly — `register_offset` returns `None`, yet `scan_transaction` attributes outputs paying `S` to offset `o+1`, which the consumer may have assigned to a different logical purpose. The reported `ReceivedOutput.offset` is the scanner's cached assumption, not the caller's actual mapping.
