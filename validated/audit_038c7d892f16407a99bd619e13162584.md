### Title
Uncontrolled resource consumption in `ThresholdKeys::read`/`ThresholdKeys::new` via attacker-controlled threshold parameters - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to CVE-2020-28200 (Dovecot Sieve ReDoS), `ThresholdKeys::read` accepts attacker-supplied `t`/`n` values up to `u16::MAX` and then `ThresholdKeys::new` performs an O(t²) Lagrange-interpolation computation — including a scalar field inversion per participant — over attacker-inflated parameters. A small (~4 MB) untrusted blob forces billions of field operations, causing CPU exhaustion in any process that deserializes `ThresholdKeys` from untrusted input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the byte stream as `u16`s, then reads `n` verification shares and calls `ThresholdKeys::new` [1](#0-0) . `ThresholdParams::new` only enforces `t <= n`, `i <= n`, and non-zero values — no upper bound [2](#0-1) .

`ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation_factor(i, t_list)` for `i` in `1..=t` [3](#0-2) . For `Interpolation::Lagrange`, each `interpolation_factor` call iterates the full `t`-element `included` list, performing `t` field multiplications and one field inversion [4](#0-3) . Total cost is therefore O(t²) field multiplications plus O(t) field inversions and O(t) point multiplications.

With `t = n = 65535`, a serialized `ThresholdKeys` of roughly `n * point_size` (~2–4 MB for Ristretto/ed25519-class curves) triggers ~4.3×10⁹ field multiplications and ~65k scalar inversions inside a single `read` call. The same quadratic cost recurs in `ThresholdView::view`, which calls `interpolation_factor` once per included participant [5](#0-4) , so the cost is paid again on every signing operation over such keys.

### Impact Explanation
An unprivileged party that can get a victim node to deserialize `ThresholdKeys` (listed in scope as an untrusted-bytes sink) can stall the victim's CPU for an extended period with a few megabytes of input — a classic asymmetric-amplification DoS matching the CVE-2020-28200 shape (small input, disproportionate computation). If this runs in a consensus, DKG, or signing path, it can halt progress for the process handling the message.

### Likelihood Explanation
Reachability depends on `ThresholdKeys::read` being invoked on network/peer-supplied bytes, which the scope explicitly treats as an unprivileged-input sink. The parameters are fully attacker-chosen (all validation is `t<=n<=65535`, `i<=n`), so maximal cost is trivially achievable. No malformed structure is needed — a well-formed serialization with maximum `n` suffices. The read itself also forces `n` point decompressions and a `HashMap` of 65535 entries, but the dominant cost is the O(t²) interpolation in `new`.

### Recommendation
Bound `n` (and hence `t`) to a protocol-enforced maximum (e.g., the real validator-set cap) before performing interpolation in `ThresholdKeys::new`/`read`, and/or make `interpolation_factor` incremental so the group-key computation is O(n) (precompute products once, or use a single inversion via batch inversion). Reject `ThresholdKeys` whose `n` exceeds the network's configured limit at deserialization time.

```rust
// Conceptual: craft serialized ThresholdKeys for a Ciphersuite C
// id_len || C::ID || t=0xFFFF || n=0xFFFF || i=1 || interpolation=1 (Lagrange)
// || secret_share (one F repr) || n copies of a valid G encoding
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&u16::MAX.to_le_bytes()); // t
buf.extend(&u16::MAX.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                          // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref());
let g = C::generator().to_bytes();
for _ in 0 .. u16::MAX { buf.extend(g.as_ref()); }

// This call performs ~4.3e9 field multiplications and ~65k inversions
// inside ThresholdKeys::new before returning.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```
