### Title
Missing path-containment check in `revealInFileManager()` allows escape from repository root - (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager()` builds the file-manager target path with a raw `Path.join(repository.path, path)` and never verifies that the result stays inside the repository, whereas the two other call sites that resolve repository-relative, externally-influenced paths (`dispatcher.ts`'s `openRepositoryFromUrl`, `copilot-conflict-context.ts`'s `buildConflictContext`) both explicitly call `resolveWithin()` to reject any resolved path (via `..` or symlink) that escapes the repository root.

### Finding Description
`revealInFileManager` is defined as: [1](#0-0) 
It computes `fullyQualifiedFilePath` with `Path.join(repository.path, path)` and passes it straight to `shell.showItemInFolder`, with only a doc comment warning "Do not use this method with non-validated paths" — no runtime enforcement.

Compare this to the two other places in the codebase that resolve a repository-relative path coming from outside the local working tree (deep-link file paths, conflicted file paths from merges/rebases involving foreign refs): both explicitly reject any path that resolves outside the repository root using `resolveWithin()`: [2](#0-1) [3](#0-2) 

`resolveWithin()` itself performs `realpath` resolution against the root and rejects anything that isn't a descendant of the resolved root — this is exactly the guard that `revealInFileManager` lacks: [4](#0-3) 

`path` in `revealInFileManager` is a `WorkingDirectoryFileChange.path` / diff file path, which can originate from a symlink present in the working tree (a symlink such as `link -> ../../../../` committed by a malicious remote after `git clone`/`git checkout`) or a crafted rename/copy target. Because `Path.join` performs no `realpath`/containment check, a symlinked path component can walk `fullyQualifiedFilePath` outside `repository.path` before the string is handed to `shell.showItemInFolder`.

### Impact Explanation
`shell.showItemInFolder` operates on the raw filesystem path and will happily reveal/select a file outside the repository if `path` traverses through an attacker-planted symlink. This is a "reveal in file manager"-scoped disclosure primitive (confirming existence/location of files outside the repo, e.g. `~/.ssh`), which is a milder impact than full read/write, but it is the same *missing invariant* pattern the report flags: a security check (`resolveWithin`) that exists in sibling functions handling equivalent attacker-controlled input is silently absent in this one.

### Likelihood Explanation
Requires no privileged access: a malicious or compromised remote can ship a symlinked path in a normal clone/fetch, and the user only has to trigger "Show in Explorer/Finder" for a changed file — a completely ordinary, expected user action in Desktop's Changes view. No admin rights, no prior local malware, no social-engineering beyond opening a repository the user already intends to use.

### Recommendation
Route `revealInFileManager`'s path construction through `resolveWithin(repository.path, path)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) and bail out (matching the pattern used in `dispatcher.ts`) when the resolved value is `null`, instead of relying solely on the doc-comment warning.

### Proof of Concept
1. Attacker publishes a repository containing a tracked symlink `evil -> ../../../../../../etc` (or a Windows junction pointing outside the intended clone directory).
2. Victim clones the repository in GitHub Desktop; the symlink is materialized on disk as part of checkout.
3. Victim modifies/creates a file inside `evil/` (or the attacker crafts a rename/copy diff entry whose `path` traverses through `evil`), causing it to appear in the Changes list.
4. Victim right-clicks the entry and selects "Show in Explorer/Finder in Finder", invoking `revealInFileManager(repository, path)`.
5. `Path.join(repository.path, path)` resolves through the symlink to a location outside the repository, and `shell.showItemInFolder` opens/reveals that external path — with no containment check, unlike the equivalent `resolveWithin()`-guarded code paths elsewhere in the app.

**Uncertainty**: I could not fully confirm (from indexed content alone) every UI call site that feeds `path` into `revealInFileManager`, nor whether Desktop's checkout logic already strips or blocks symlinks generally at the git layer (which would mitigate this). If a global symlink-checkout protection exists elsewhere in the git wrapper, this finding would need to be revisited — starting a Devin session to inspect the full checkout/symlink-handling code would resolve this open question.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
