### Title
Missing 32-byte floor in `state-coprocessor::handle_get_requests` undercredits reputation relative to `pallet-messaging-incentives`, skewing Collator selection - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
Both `pallet-messaging-incentives` and `pallet-state-coprocessor` mint the same non-transferable `ReputationAsset` at the same governance-set `MintPerByte` rate, and that reputation balance is the sole ranking input `pallet-collator-manager` uses to select the next Collator set. The two pallets compute "bytes delivered" for minting differently: `messaging-incentives::message_bytes` applies a `max(body_size, 32)` floor per request/response so trivial payloads can't be minted for free/undercounted, while `state-coprocessor::handle_get_requests` sums the raw `encode_get_response(&response).len()` with no floor at all.

### Finding Description
`pallet-messaging-incentives` documents and enforces a deliberate invariant: every delivered request/response contributes at least 32 bytes to the mint calculation, applied per-request specifically to prevent gaming via splitting/packing: [1](#0-0) 

`state-coprocessor::handle_get_requests`, which mints from the *same* `MintPerByte` storage value and the *same* `ReputationAsset` (explicitly stated to share "one source of truth" with messaging-incentives), instead sums the raw encoded response size with no minimum floor: [2](#0-1) 

This is structurally the same class of bug as H-12: two code paths meant to compute the identical scaled quantity from a shared rate, where one path omits a scaling/floor term the other applies, silently producing a different (smaller) result for the same nominal "bytes delivered" unit.

### Impact Explanation
Reputation is not cosmetic — `pallet-collator-manager::new_session` ranks and selects the next block-producing Collator set purely by `ReputationAsset` balance, and successful selection burns that balance and grants ongoing `$BRIDGE` block rewards: [3](#0-2) 

A relayer that services small `GetResponse` payloads (state-coprocessor path) is systematically under-credited relative to an economically identical relayer delivering equally small Post request/response payloads (messaging-incentives path, floored to 32 bytes). This means the on-chain reputation ranking — which directly gates who gets to produce blocks and earn treasury-funded `$BRIDGE` rewards — is computed on an inconsistent, exploitable metric: an attacker/relayer can strategically prefer request/response traffic over Get-request traffic (or vice versa, depending on payload sizes) to inflate their relative standing versus honest competitors who split effort proportionally by real usage, distorting Collator selection and the flow of treasury funds without any privileged access.

### Likelihood Explanation
High under normal operation whenever `MintPerByte > 0` and any `GetRequest`/`GetResponse` traffic with body size < 32 bytes flows through `handle_get_requests` — this requires no malicious peer, prover, relayer, or admin action, only ordinary unprivileged use of two live incentive surfaces that governance intends to be equivalent ("share one source of truth").

### Recommendation
Apply the same `max(bytes, 32)` floor per `GetResponse` in `state-coprocessor::handle_get_requests` before charging the bandwidth gate and before summing into `total_bytes`, matching `pallet_messaging_incentives::message_bytes`'s floor logic exactly (ideally by extracting a shared helper both pallets call, to prevent future drift).

### Proof of Concept
1. Governance sets `MintPerByte = 1` (shared storage read by both pallets).
2. Relayer A delivers a Post request with `body.len() == 10` via the normal ISMP flow → `messaging-incentives::on_executed` computes `bytes = max(10, 32) = 32`, mints `32` reputation.
3. Relayer B delivers a `GetRequestsWithProof` whose resulting `GetResponse` ABI-encodes to `10` bytes → `state-coprocessor::handle_get_requests` computes `bytes = 10` (no floor), mints only `10` reputation for equivalent-scale work.
4. Over many such small Get-response deliveries, Relayer B accrues systematically less reputation than an equally-active Relayer A, or conversely a relayer who selectively routes traffic through whichever path underweights small payloads gains an artificial standing advantage in the next `new_session` ranking in `pallet-collator-manager`, materially affecting who is selected and paid as a Collator.
