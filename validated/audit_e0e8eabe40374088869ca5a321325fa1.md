## Analysis

The audit's core bug pattern — a decimals-scaling function that silently produces a wrong (inflated) amount when its scaling-direction assumption is violated — has a direct structural analog in the `hyper-fungible-token` pallet's cross-chain amount conversion.

### Title
Unpinned live decimals lookup lets `Precisions`/local-asset decimal drift break the `erc_decimals >= local_decimals` invariant, causing inflated ERC20 mint amounts on `send` - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`register_token`/`update_token` only validate `config.decimals >= local_decimals` **once**, at registration time, using whatever decimals the local asset happens to report then [1](#0-0) . But `send`, `on_accept`, and `on_timeout` all re-fetch `local_decimals` **live** from `fungibles::metadata::Inspect::decimals()` on every call [2](#0-1) [3](#0-2) , rather than trusting the value pinned at registration.

### Finding Description
`convert_to_erc20`, used on the outgoing `send` path, scales a local balance up to ERC20 precision by `value * 10^(erc_decimals.saturating_sub(local_decimals))`: [4](#0-3) 

This mirrors exactly the H-01 pattern: it silently degrades to a no-op scale factor (`saturating_sub` → 0 → `10^0 = 1`) whenever the "wrong side" is larger — i.e., whenever `local_decimals > erc_decimals`. The pallet's only defense against this is the one-time check in `register_token`/`update_token`: [1](#0-0) [5](#0-4) 

That check is evaluated against `local_decimals` as read **at registration time**, but `send` re-queries `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(asset_id)` fresh on every call [6](#0-5) . Nothing pins or freezes that value in `Precisions` or `TokenContracts` — only `erc_decimals` (the EVM side) is cached; the local side is trusted to stay constant forever after a single point-in-time check.

If the underlying local asset's metadata decimals can be changed after registration (e.g. via the runtime's `pallet-assets::set_metadata`, callable by the asset's `Owner`, which is a distinct, non-bridge-governance role that the HFT pallet has no visibility into or control over), the registered invariant `erc_decimals >= local_decimals` silently breaks without the HFT pallet ever re-validating it.

### Impact Explanation
Once `local_decimals > erc_decimals` for a registered asset, calling `send` computes `erc20_amount = value` (no scale-up, because `saturating_sub` clamps to 0). The `Message.amount` dispatched to the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract is then interpreted on the EVM side at the small `erc_decimals` precision registered in `Precisions`. A `value` that was small in local (high-decimal) units becomes enormous when read as a low-decimal ERC20 amount — e.g., escrowing/burning `1e18` local units (intended as "1 token" at 18 decimals) and having the EVM side mint `1e18 / 10^6 = 10^12` tokens if `erc_decimals = 6`. This is a direct amount-inflation / fund-creation bug on the receiving chain's mint/release path — matching the "false state acceptance / unauthorized execution / wrong amount" impact class.

### Likelihood Explanation
This requires the local asset's live decimals to diverge from the `Precisions` value recorded at registration/update time. The pallet's own extrinsics (`register_token`, `update_token`) cannot cause this on their own since they gate on `CreateOrigin`, and the fix (validate once) is otherwise sound *if* asset decimals are truly immutable in the runtime's `Config::Assets` implementation. The core defect — validating a live-queried value only once and never re-checking it on the hot path — is verifiable directly from the code; whether a given deployment's `pallet-assets` configuration permits post-creation decimal changes (via asset `Owner`/`set_metadata`) is runtime-specific and was not confirmed from the indexed code available. This is flagged as the strongest available local analog to the reported bug class, with that one external assumption noted explicitly.

### Recommendation
Freeze/pin the local asset's decimals into `Precisions` (or a new `LocalPrecisions` map) at `register_token`/`update_token` time instead of live-querying `fungibles::metadata::Inspect::decimals()` in `send`, `on_accept`, and `on_timeout`. Re-validate `erc_decimals >= local_decimals` using the pinned value on every dispatch, and reject (rather than silently clamp to a no-op scale) whenever `erc_decimals < local_decimals` in `convert_to_erc20`/`convert_to_balance`, mirroring the audit's recommendation to make the scaling function fail loudly instead of defaulting to an unsafe assumption.

### Proof of Concept
1. Governance registers asset `A` for EVM chain `C` via `register_token`, with `A` currently reporting `decimals() = 6` and EVM-side `config.decimals = 6` — passes the `config.decimals >= local_decimals` check [1](#0-0) ; `Precisions[A][C] = 6`.
2. Some time later, `A`'s metadata `decimals` is changed to `18` outside the HFT pallet's knowledge (e.g., via the underlying assets pallet's owner-controlled `set_metadata`).
3. Attacker (holding `A`) calls `send(asset_id = A, amount = 1e18, destination = C, ...)`. Inside `send`, `decimals = <T::Assets>::decimals(A) = 18` is fetched live [6](#0-5) , `erc_decimals = Precisions[A][C] = 6` is read from storage.
4. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes multiplier `10^(6.saturating_sub(18)) = 10^0 = 1`, so `erc20_amount = 1e18` [4](#0-3) .
5. The dispatched `Message.amount = 1e18` is delivered to the EVM contract, which treats it as a 6-decimal amount — minting/releasing `1e12` tokens' worth to the recipient from what should have been a 1-token transfer.

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
