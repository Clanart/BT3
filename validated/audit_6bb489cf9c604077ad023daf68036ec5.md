### Title
`OP_RETURN` data bypasses transaction fee and weight policy - ([File: `networks/bitcoin/src/wallet/send.rs`])

### Summary
Medium. `SignableTransaction::new` adds an `OP_RETURN` output but calculates virtual size, transaction weight, minimum relay fee, and requested fee using only the payment outputs. A caller can therefore produce a signed transaction whose actual fee rate and weight violate the policy that `new` claims to enforce. [1](#0-0) 

### Finding Description
`data` is validated as at most 80 bytes and appended as a zero-value `OP_RETURN` output. [2](#0-1)  The subsequent `calculate_weight_vbytes` call receives `payments`, not the already-created `tx_outs`, so the `OP_RETURN` output is omitted from `vbytes`, `needed_fee`, the minimum-relay-fee check, and the later maximum-standard-weight check. [3](#0-2)  The resulting `SignableTransaction` retains the omitted output in `self.tx`, and `TransactionSignMachine::sign` produces FROST shares over that actual transaction’s Taproot sighash. [4](#0-3) [5](#0-4) 

### Impact Explanation
When input value is selected to leave exactly the underestimated `needed_fee`, the signed transaction pays that fee despite having a larger actual virtual size. [6](#0-5)  At a requested rate of 1 sat/vbyte, the minimum-relay check passes against the smaller estimate but fails against the actual transaction, allowing construction and threshold signing of a transaction that does not meet the requested or default relay fee policy. [7](#0-6)  This can cause withdrawal or data-carrying transactions to be rejected by relay policy and remain unconfirmed despite being signed as though compliant. [8](#0-7) 

### Likelihood Explanation
The issue is reachable whenever an unprivileged requester can cause a transaction plan to include the public `data` parameter while inputs are selected tightly enough that no excess value masks the underestimated fee. [9](#0-8)  No malformed encoding, privileged validator behavior, leaked key, or cryptographic break is required; the bypass is a deterministic omitted-output accounting error. [1](#0-0) 

### Recommendation
Calculate weight and vbytes from the complete output list, including the optional `OP_RETURN` output, and perform the minimum-fee, sufficiency, and maximum-weight checks against that complete transaction shape. [10](#0-9)  When change is considered, calculate the complete with-change output set as well, then add a regression test asserting `tx.vsize() * fee_per_vbyte == tx.needed_fee()` for transactions carrying maximum-size `data`. [11](#0-10) 

### Proof of Concept
A focused unit test can first build a one-input transaction with a large input to learn the underestimated `needed_fee`, then rebuild it with an input worth `payment + needed_fee`, one dust-compliant payment, no change, and 80 bytes of `OP_RETURN` data. [12](#0-11) 

```rust
// Conceptual regression test for networks/bitcoin/src/wallet/send.rs.
let data = Some(vec![0u8; 80]);
let fee_rate = 1; // sat/vbyte

let probe = SignableTransaction::new(
    vec![large_received_output],
    &[(payment_script, DUST)],
    None,
    data.clone(),
    fee_rate,
)?;
let underestimated_fee = probe.needed_fee();

let exact_input = received_output_with_value(DUST + underestimated_fee);
let tx = SignableTransaction::new(
    vec![exact_input],
    &[(payment_script, DUST)],
    None,
    data,
    fee_rate,
)?;

assert_eq!(tx.fee(), underestimated_fee);
assert!(tx.fee() < u64::try_from(tx.transaction().vsize()).unwrap() * fee_rate);
```

The second assertion follows because the 80-byte payload and its output overhead are present in `tx.transaction()` but were absent from the `payments`-only estimate used for `needed_fee`. [13](#0-12) [1](#0-0)
