## Title
Native-token escrow release/refund can be permanently bricked by an unpayable beneficiary, locking cross-chain escrow funds forever - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` — the single function used to release or refund escrowed order funds on both same-chain fills and cross-chain `RedeemEscrow`/`RefundEscrow` message delivery — pays out native token legs with a raw `call{value: amount}("")` and unconditionally reverts the *entire* withdrawal (all tokens in the order, plus the fee release and the `_filled` finalization) if that single native transfer fails. There is no pull-payment fallback. Because the `beneficiary` address is attacker-supplied order data (chosen by the order creator or the filler, not validated to be capable of receiving plain ETH), a beneficiary that cannot accept a bare-ETH transfer permanently blocks settlement of that commitment.

### Finding Description
`_withdraw` is the shared settlement primitive: [1](#0-0) 

For any token leg equal to `address(0)` (native currency), the function does:
```
(bool sent,) = beneficiary.call{value: amount}("");
if (!sent) revert InsufficientNativeToken();
```
and this is the *only* release mechanism — there is no secondary pull-withdrawal, no per-token try/catch, and no way to retry with a different beneficiary. If `sent` is `false` the whole call reverts, which unwinds:
- the escrow debit (`_orders[...] -= amount`),
- the `_filled[commitment] = beneficiary` finalization flag,
- release of the accumulated `TRANSACTION_FEES` to the beneficiary,
- the `EscrowReleased`/`EscrowRefunded` event.

`_withdraw` is reached from cross-chain message delivery (`RedeemEscrow` / `RefundEscrow` request kinds handled in `onAccept`, per the `RequestKind` enum) and from same-chain fill/cancel paths in `IntentGatewayV2`. [2](#0-1) 

Per the documented ISMP callback contract, `onPostRequestTimeout`/`onAccept`-style callbacks "can be called multiple times until it succeeds" and "must be idempotent" — the protocol's only recovery mechanism for a reverting callback is retrying the same call: [3](#0-2) 

That retry model works for transient failures (e.g., out-of-gas), but it cannot recover a **permanently unpayable beneficiary** — a contract address with no `receive()`/payable `fallback()`, or one that unconditionally reverts on receiving ETH. This is the exact same broken invariant as the audited report: a receiving account/contract that lacks the interface/ability to accept an incoming asset transfer causes transfers to it to permanently fail, but here the failure aborts the entire cross-chain settlement instead of just the recipient's own inbound transfer.

### Impact Explanation
Once a native-token order commitment's `beneficiary` is unpayable:
- The escrowed input funds recorded in `_orders[commitment][address(0)]` can never be released or refunded — they are permanently locked in the `IntentGatewayV2` contract (loss of funds, no path to recovery since `_withdraw` is the sole release routine and reverts deterministically every time it's retried).
- Any `TRANSACTION_FEES` bundled with that commitment are likewise stuck forever, denying relayer/protocol fee settlement.
- On the cross-chain path, this also means the Hyperbridge relayer who delivered the `RedeemEscrow`/`RefundEscrow` message can never be reimbursed, since fee refund is gated on callback success per the documented handler behavior.
- Because `beneficiary` is set from order/fill data controlled by the order creator or filler (not the counterparty who ends up needing the payout), one party can grief the other: e.g. a filler that fulfills a user's order on the destination chain but is entitled to escrowed input tokens on the source chain via `RedeemEscrow` can have that entitlement permanently denied if the recorded beneficiary is unpayable — an economic loss inflicted on the settling party with no recourse, matching the bounty's "loss of funds" / "logic attack" category.

### Likelihood Explanation
The path requires only ordinary, permissionless use of the public `placeOrder`/`fillOrder`/`cancelOrder` entry points with a native-token (`address(0)`) leg and a beneficiary address that is a contract without ETH-receiving capability — no relayer, prover, governance, or admin compromise is needed. Many common contract wallets (e.g., ones without a `receive()`/payable fallback, or with a fallback that reverts under certain conditions) satisfy this trivially, and the condition can also be constructed deliberately by an attacker to grief a counterparty's expected settlement.

### Recommendation
- Replace the raw revert-on-failure native transfer in `_withdraw` with a pull-payment pattern: on `call` failure, credit an internal withdrawable balance for `beneficiary` instead of reverting the whole settlement, and expose a separate `claim()` function the beneficiary (or anyone, sending to that address) can call later.
- Alternatively, isolate the native-token transfer failure so it does not revert the ERC-20 legs, fee release, and `_filled` finalization for the same commitment — i.e., don't let one unpayable leg hold hostage the rest of the order's settlement.
- Consider capping forwarded gas and/or wrapping native token as WETH-equivalent when a raw transfer fails, so funds are never unconditionally stuck.

### Proof of Concept
1. Attacker (or a benign user) deploys a `Beneficiary` contract with no `receive()`/payable `fallback()` (or one that always reverts).
2. Attacker calls `placeOrder` with an `Order.inputs` entry using `token = address(0)` and escrows native ETH, or as a filler, ensures `WithdrawalRequest.beneficiary` for a `RedeemEscrow`/`RefundEscrow` resolves to the unpayable `Beneficiary` contract address.
3. When settlement is triggered — same-chain `fillOrder`/`cancelOrder`, or cross-chain `onAccept` processing a `RedeemEscrow`/`RefundEscrow` request — `_withdraw` executes `beneficiary.call{value: amount}("")`, which returns `sent = false`.
4. The call reverts with `InsufficientNativeToken()`, undoing the escrow debit and the `_filled` write.
5. Every subsequent retry (permissionless resubmission of the same message/fill) reverts identically — the escrowed native funds and any bundled `TRANSACTION_FEES` for that commitment are permanently locked, with no alternate withdrawal path available in the contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
