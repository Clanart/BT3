### Title
Searcher bid deposits held in a registry-swappable `AuctionEntryPoint`/`DepositVault` expose escrowed funds to governance/administrative address changes - (File: `kaiax/auction/impl/execution.go`, `contracts/bindings/auctionv3/Kip249V3.go`)

### Summary
The KIP-249 auction system holds searcher bid deposits in an `AuctionEntryPoint` contract's `depositVault`, but the address of both the `AuctionEntryPoint` itself and its `depositVault` is not fixed/immutable — it is resolved dynamically from the on-chain `SystemRegistry` and can be repointed via `changeDepositVault`/`changeAuctioneer`, or by registering a new `AuctionEntryPoint` implementation address in the registry. This mirrors the referenced report's "upgradable escrow" bug class: searchers deposit collateral (KAIA/bid amounts) into a contract trusting its current logic, while the entity/address actually holding and disbursing those funds can be swapped out from under them.

### Finding Description
Searchers deposit funds into the `AuctionEntryPoint` and its `depositVault`, and their balances are tracked per-address via `getNoncesAndDeposits(searchers)` [1](#0-0) . The entry point exposes a `depositVault()` getter [2](#0-1)  together with a state-changing `changeDepositVault(address)` function that repoints where escrowed deposits are held [3](#0-2) , and a `changeAuctioneer(address)` function that changes who is authorized to co-sign auction settlement [4](#0-3) .

At the node level, the `AuctionModule` never treats the `AuctionEntryPoint` address as fixed: every block it re-resolves the active `AuctionEntryPoint` address from the `SystemRegistry` via `system.ReadActiveAddressFromRegistry(backend, system.AuctionEntryPointName, num)`, then reads `Auctioneer` and `GasBufferEstimate` from whatever contract is currently registered [5](#0-4) . The module's own documentation confirms this is an expected, live-changeable configuration: "This module reads `SystemRegistry` and `AuctionEntryPoint` to detect any changes of `AuctionEntryPoint` address, `bidTxGasBuffer` and `Auctioneer` address. If the one of them is changed, the module will clear the existing bids in the bid pool." [6](#0-5) . Test fixtures confirm the `AuctionEntryPoint` address is simply a `Registry` record that can be re-registered to any address at any time [7](#0-6) .

This design is structurally identical to the referenced "upgradable escrow contract" issue: a user (searcher) deposits value into a contract under the assumption that a specific, audited set of withdrawal/settlement rules governs it, but the actual contract backing that escrow (`AuctionEntryPoint`/`depositVault`) can be swapped via a privileged registry update or `changeDepositVault`/`changeAuctioneer` call, without the depositor's consent, and with no mechanism visible in the reachable bindings/tests forcing an orderly migration of existing balances before the pointer change takes effect.

### Impact Explanation
If the `AuctionEntryPoint`/`depositVault` registry pointer is changed (via governance-controlled `SystemRegistry` update, or via `changeDepositVault`/`changeAuctioneer` if these are not appropriately access-controlled or are executed maliciously/erroneously), searcher deposits recorded under `getNoncesAndDeposits` for the old vault could become unreachable, or a new implementation could redefine withdrawal semantics for the still-existing deposits, resulting in unauthorized value redirection or loss of escrowed searcher funds. Because auction settlement directly moves KAIA (bid amounts) between searchers, the auctioneer, and the block proposer, a swapped vault/entry point creates a direct path to fee/bid theft or stranding of funds — a concrete unauthorized value movement scenario.

### Likelihood Explanation
This requires an administrative/governance action (registry update or a privileged `changeDepositVault`/`changeAuctioneer` call) rather than an ordinary unprivileged transaction, so likelihood depends on the access-control strength around these functions and the registry update process, which was not fully visible in the indexed bindings (only ABI/mock, no full production Solidity source was found). Given that the `kaiax/auction` module's own documentation treats such changes as a normal, expected event ("If the one of them is changed..."), the pointer-swap capability is clearly a first-class, reachable feature of the live system rather than a theoretical edge case.

### Recommendation
- Make `depositVault` (and ideally the `AuctionEntryPoint` binding itself) immutable per deposit epoch, or require an on-chain migration/drain of all outstanding searcher deposits before allowing `changeDepositVault`/`changeAuctioneer` or a `SystemRegistry` re-registration to take effect.
- Restrict `changeDepositVault`/`changeAuctioneer` to a timelocked governance path with mandatory advance notice, and emit a grace period during which searchers can withdraw before the switch is finalized.
- Add explicit invariant checks (verified by `kaiax/auction` on each `PostInsertBlock`) that outstanding deposits are non-zero before permitting an entry-point/vault change to proceed within the same block.

### Proof of Concept
Conceptual PoC (contract source for `IAuctionEntryPoint`/`depositVault` was not available in the index — only ABI bindings/mocks were found, so full exploit mechanics could not be verified from source):
1. Searchers call the auction deposit flow, and their balances are reflected via `getNoncesAndDeposits([searcher])` [8](#0-7) .
2. A privileged caller invokes `changeDepositVault(newVault)` on the `AuctionEntryPoint`, or the `SystemRegistry` owner re-registers `AuctionEntryPointName` to a different address (as done in tests via `Registry.Register`) [9](#0-8) .
3. On the next block, `kaiax/auction`'s `updateAuctionInfo` picks up the new `AuctionEntryPoint`/`Auctioneer`/vault without any check that prior searcher balances were settled [10](#0-9) , leaving searcher deposits recorded against the old vault effectively orphaned or subject to whatever logic the new vault/entry point implements.

**Note on limitations**: I was unable to locate the actual production Solidity source for `AuctionEntryPoint`/`DepositVault` (only compiled ABI Go bindings and a stripped-down `AuctionEntryPointMock.sol` were indexed) [11](#0-10) . Due to index size limits, some contract source files may not be available; a Devin session with full repository access would be needed to confirm exact access-control modifiers on `changeDepositVault`/`changeAuctioneer` and the precise fund-custody/withdrawal logic in the real (non-mock) contract before this can be escalated with full certainty.

// Solidity: function getNoncesAndDeposits(address[] searchers) view returns(uint256[] nonces_, uint256[] deposits_)
func (_IAuctionEntryPoint *IAuctionEntryPointCaller) GetNoncesAndDeposits(opts *bind.CallOpts, searchers []common.Address) (struct {
	Nonces   []*big.Int
	Deposits []*big.Int
}, error) {
	var out []interface{}
	err := _IAuctionEntryPoint.contract.Call(opts, &out, "getNoncesAndDeposits", searchers)

	outstruct := new(struct {
		Nonces   []*big.Int
		Deposits []*big.Int
	})
	if err != nil {
		return *outstruct, err
	}

	outstruct.Nonces = *abi.ConvertType(out[0], new([]*big.Int)).(*[]*big.Int)
	outstruct.Deposits = *abi.ConvertType(out[1], new([]*big.Int)).(*[]*big.Int)

	return *outstruct, err

}
