### Title
Attacker can sweep queued rewards accrued during a zero-`totalSupply` window in `DelegateVoteRewardPool` by front-running the first stake after deployment/zero-supply period - ([File: rewards/DelegateVoteRewardPool.sol])

### Summary
`harvestAll()` in `DelegateVoteRewardPool.sol` is fully public and unauthenticated, and pulls bribes from `WombatBribeManager.claimAllBribes(address(this))` regardless of whether anyone is currently staked. When `totalSupply == 0`, `_queueNewRewardsWithoutTransfer` diverts the entire harvested amount into `rewardInfo.queuedRewards` instead of distributing it via `rewardPerTokenStored`. An attacker who is the first (or dominant) staker once `totalSupply` transitions away from zero can capture this queued balance disproportionately to any real contribution when the next reward batch is queued.

### Finding Description
`harvestAll()` has no access control and can be triggered by anyone at any time: [1](#0-0) 

`_manageRewards` forwards any nonzero harvested amount to `_queueNewRewardsWithoutTransfer`: [2](#0-1) 

When `totalSupply == 0`, the reward is added to `rewardInfo.queuedRewards` rather than being folded into `rewardPerTokenStored`: [3](#0-2) 

`stakeFor` can only be invoked by the operator (`WombatBribeManager`), but this is reached through the normal, unprivileged `vote()`/lock flow available to any vlMGP holder — the attacker does not need any special role, only real vlMGP to lock and vote for the delegated pool: [4](#0-3) 

Crucially, staking itself does **not** convert `queuedRewards` into `rewardPerTokenStored` — that conversion only happens on the *next* call to `_queueNewRewardsWithoutTransfer` with `totalSupply > 0`, where `_amountReward += rewardInfo.queuedRewards` before dividing by the *current* `totalSupply`: [5](#0-4) 

Since `castVotes()` in `WombatBribeManager` unconditionally calls `harvestAll()` on the delegated pool after every vote cast, this "next accrual" event is a routine, unauthenticated action: [6](#0-5) 

Exploit flow:
1. `totalSupply == 0` in `DelegateVoteRewardPool` (most naturally right after deployment, before any voter has staked, or after all voters have unvoted).
2. Attacker (or anyone) calls `harvestAll()`; any nonzero bribes accrued flow entirely into `rewardInfo.queuedRewards`.
3. Attacker locks vlMGP and calls `vote()` through `WombatBribeManager`, which routes to `DelegateVoteRewardPool.stakeFor`, making the attacker the sole/dominant staker (`totalSupply` now equals attacker's stake).
4. On the next nonzero bribe accrual (triggered by any `harvestAll()`/`castVotes()` call, which anyone can call), `_queueNewRewardsWithoutTransfer` adds the accumulated `queuedRewards` plus the new reward, then divides by the *current* `totalSupply` — which is dominated by the attacker's stake — crediting the attacker a share of the queued reward pool disproportionate to their actual staking duration.

Existing checks (`onlyOperator` on `stakeFor`, `updateRewards` modifier) do not prevent this because the attacker never needs to call `stakeFor` directly; they only need to be a real, legitimate voter at the right time, and `harvestAll()` itself has no guard against zero-`totalSupply` harvesting.

### Impact Explanation
This falls under "theft or permanent freezing of unclaimed yield": rewards that accrue during a zero-supply window are non-time-weighted and can be swept almost entirely by whoever becomes the first/dominant staker afterward, at the expense of the intended proportional distribution model. The magnitude is bounded by the size of bribes claimable while `totalSupply == 0` and the attacker's ability to become sole staker at the transition point.

### Likelihood Explanation
Preconditions: `totalSupply == 0` in `DelegateVoteRewardPool` (realistic immediately post-deployment, or after mass unvoting), attacker must hold/lock vlMGP and call `vote()`, and a subsequent nonzero-bribe `harvestAll()`/`castVotes()` call must occur while the attacker's stake dominates `totalSupply`. This requires real capital (locking vlMGP, which is typically time-locked) rather than a flash-loanable action, and coordination around a specific state transition, making it feasible but not trivially/instantly repeatable — it depends on the pool actually reaching a zero-supply state and the timing of subsequent bribe claims.

### Recommendation
Do not allow `queuedRewards` accrued while `totalSupply == 0` to be distributed based on a future snapshot of `totalSupply` that could be dominated by a single new staker. Consider either (a) disallowing/no-op'ing bribe harvesting while `totalSupply == 0` (skip claim or hold funds in a separate escrow keyed by time, distributing later based on time-weighted stake), or (b) applying a vesting/streaming schedule to queued rewards so no single depositor can claim a disproportionate lump sum immediately after staking.

### Proof of Concept
Foundry test plan:
1. Deploy `DelegateVoteRewardPool` with a mock `WombatBribeManager` as operator; have all existing stakers `withdrawFor` until `totalSupply == 0`.
2. Configure the mock bribe manager's `claimAllBribes` to return a nonzero reward amount.
3. Call `harvestAll()` (unauthenticated) — assert `rewards[token].queuedRewards` equals the full harvested amount and `rewardPerTokenStored` is unchanged.
4. Have attacker EOA lock vlMGP and call `vote()` on the mock `WombatBribeManager`, which internally calls `stakeFor(attacker, amount)` on the pool, making attacker the sole staker.
5. Configure `claimAllBribes` to return a small/zero new reward, then call `harvestAll()` again (or trigger `castVotes()`), which folds `queuedRewards` into `rewardPerTokenStored` divided by current `totalSupply` (attacker's stake).
6. Assert `earned(attacker, token)` jumps to (approximately) the entire previously queued amount, disproportionate to the attacker's actual staking duration (e.g., staked for 1 block vs. reward accrued over a long period).

    function _manageRewards(
        address[] memory rewardTokensList,
        uint256[] memory earnedRewards
    ) internal {
        uint256 length = rewardTokensList.length;
        for (uint256 index = 0; index < length; ++index) {
            uint256 fees = (protocolFee * earnedRewards[index]) / DENOMINATOR;
            if (fees > 0 && feeCollector != address(0)) {
                earnedRewards[index] = earnedRewards[index] - fees;
                IERC20(rewardTokensList[index]).safeTransfer(
                    feeCollector,
                    fees
                );
            }
            if (earnedRewards[index] > 0) {
                _queueNewRewardsWithoutTransfer(
                    earnedRewards[index],
                    rewardTokensList[index]
                );
            }
        }
    }
