### Title
External deposits sent to internal offset addresses (Branch/Change/Forwarded) are silently misclassified and permanently unspendable - (File: `networks/bitcoin/src/wallet/mod.rs` + `processor/src/networks/bitcoin.rs` + `processor/src/multisigs/mod.rs`)

### Summary
Analogous to the Tokemak `recover()`/`_trackedTokens` issue — where adding a token to a set permanently blocked its recovery — the Bitcoin scanner registers a fixed set of internal offsets (Branch, Change, Forwarded) alongside the External (zero) offset, and classifies every received output purely by which offset's script it matched. An unprivileged sender can compute these internal addresses (the offsets are deterministic `hash_to_F` values of fixed public strings) and send funds to them. Those outputs are then classified as non-`External`, dropped from all crediting/scheduling paths, and never added to the UTXO pool — the multisig receives funds it will never spend.

### Finding Description
`Scanner::register_offset` builds `self.scripts: HashMap<ScriptBuf, Scalar>`, and `scan_transaction` matches outputs solely on `script_pubkey`, returning the offset [1](#0-0) . The processor registers three internal offsets derived from public constants: `BRANCH_OFFSET`, `CHANGE_OFFSET`, `FORWARD_OFFSET`, each `Secp256k1::hash_to_F(KEY_DST, b"...")` with `KEY_DST = b"Serai Bitcoin Output Offset"` [2](#0-1) . These are deterministic and publicly computable; `branch_address`, `change_address`, and `forward_address` expose them as deposit-able P2TR addresses [3](#0-2) .

In `get_outputs`, the scanned offset's repr is looked up in `kinds` and the output's `kind` is set accordingly [4](#0-3) . Downstream, only `OutputType::External` outputs become InInstructions and are retained for scheduling: `outputs.retain(|output| output.kind() == OutputType::External)` [5](#0-4) . `Change` outputs are only kept if they resolve a known plan's eventuality (`plan_by_key_with_self_change`), otherwise dropped [6](#0-5) ; `Branch` outputs are dropped unless the scheduler can currently use a branch of exactly that balance [7](#0-6) ; `Forwarded` outputs only map to a previously stored forwarding instruction [8](#0-7) . An outsider-sent output satisfies none of these conditions, so it is discarded everywhere and never enters the scheduler's UTXO pool.

### Impact Explanation
Funds sent to the Change, Branch, or Forwarded addresses are owned by the multisig key (key + G*offset), so they are technically controlled by the validators — but no code path ever schedules or credits them, so they are permanently locked exactly like Tokemak's tracked critical token: the "internal use" registry that exists to protect/set-aside flows becomes the mechanism that locks the funds. Any user who mistakenly (or is tricked into) depositing to these derivable addresses loses their deposit with no credited balance and no recovery path.

### Likelihood Explanation
The addresses are trivially computable by anyone (`hash_to_F` of public constants plus the public group key), and `change_address`/`forward_address` are exposed via the `Network` trait. Wallets, explorers, or confused users can send to any valid P2TR address. No malformed input, collusion, or privileged access is required — just a normal Bitcoin transaction to a valid address, matching the "public inputs they cause to be received" reachability model.

### Recommendation
- Do not expose `branch_address`/`change_address`/`forward_address` in ways that let external parties treat them as deposit addresses, and consider binding the classification to provenance rather than `script_pubkey` alone — e.g., only treat `Change`/`Branch`/`Forwarded`-kinded outputs as valid when their containing transaction is a known/expected plan transaction (the `Change` path already partially does this via `ResolvedDb`/`plan_by_key_with_self_change`).
- Alternatively, treat unexpected offset-matched outputs as `External` (crediting the depositor) rather than silently dropping them, so the internal-offset set cannot lock received funds.

### Proof of Concept
1. Observe the multisig group key `K` (public).
2. Compute `change_offset = hash_to_F(b"Serai Bitcoin Output Offset", b"change")` (incremented to the first even `K + G*o`, per `register_offset`), then `addr = p2tr(K + G*change_offset)` via `Bitcoin::change_address(K)`.
3. Send any amount `>= DUST` (10,000 sats) to `addr` in a normal Bitcoin transaction.
4. `get_outputs` scans it, sets `kind = OutputType::Change` [9](#0-8) ; no `ResolvedDb` entry for the txid exists, so `plan_by_key_with_self_change` fails and the output is dropped [6](#0-5) . It never reaches the scheduler, is never credited, and is never spent — the sats are locked under the multisig key indefinitely. The same holds for the `Branch` and `Forwarded` offsets.
