### Title
Order fee escrow paid out in the wrong token after `EvmHost.feeToken` is updated - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (used by `IntentGatewayV2`/`ExtrinsicIntents` for both fills and refunds) redeems the escrowed transaction fee by calling `IDispatcher(host()).feeToken()` live at redemption time, instead of using the fee token that was actually collected and escrowed when `placeOrder` ran. If the `EvmHost`'s `feeToken` is changed via `updateHostParams` between order placement and order settlement, the beneficiary is paid out `fees` amount in the *new* fee token, not the token that was actually deposited — this either strands the originally-escrowed fee token permanently in the contract, or drains an unrelated token balance that belongs to other users' escrowed funds, or reverts and locks the entire withdrawal (principal + fee) since both are released in one call.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder` (lines 345-361) and its Tron/Substrate counterparts, the transaction fee is collected in whatever token `IDispatcher(hostAddr).feeToken()` currently returns at placement time: [1](#0-0) 

The amount is stored as a raw `uint256` under `_orders[commitment][TRANSACTION_FEES]` — with **no record of which token it was collected in**.

Later, when the order is filled or refunded, `IntentsBase._withdraw` re-reads the *current* `feeToken()` from the host to determine which ERC20 to transfer out: [2](#0-1) 

The identical pattern exists in the Tron variant's shared `withdraw` function: [3](#0-2) 

`EvmHost.updateHostParamsInternal` only prevents changing `feeToken` while the **host contract itself** still holds a balance of the old fee token: [4](#0-3) 

This guard says nothing about balances escrowed inside downstream `IApp` contracts such as `IntentGatewayV2`/`IntentsBase`, `BandwidthManager`, or `SimplexPaymaster`. Nothing prevents governance from changing `feeToken` while `IntentGatewayV2` still holds unredeemed `TRANSACTION_FEES` balances from in-flight orders. This is exactly the broken invariant from the seed report: a mutable global token-address setting (`assetToken`/`feeToken`) is captured at accounting time in one place (escrow credit) but re-read live in another (escrow debit), with no per-order snapshot of the actual token address.

### Impact Explanation
Once `feeToken` changes while orders are in flight:
- `_withdraw`'s fee-transfer branch (`IERC20(newFeeToken).safeTransfer(beneficiary, fees)`) will either revert (if the gateway has no balance of the new fee token), which reverts the *entire* `_withdraw` call — locking the user's principal input/output tokens in the same transaction, not just the fee; or
- If the gateway happens to hold some balance of the new fee token (e.g., from newer orders placed after the change), the call succeeds and pays the beneficiary an amount of `newFeeToken` funded out of *other users'* escrowed fee balance, while the actual old-fee-token amount that was collected for this order remains permanently stuck and unaccounted for in the contract.

Both outcomes are direct loss/lock of user funds without any malicious peer, relayer, or attacker action — the trigger is a normal, documented governance parameter update.

### Likelihood Explanation
`feeToken` is an explicitly supported, documented configuration knob (`HostParams.feeToken`, updatable via cross-chain `updateHostParams`/host-executive governance, e.g. for migrating from one stablecoin to another). Any order that is placed before such an update and settled after it is affected — no adversarial conditions or timing tricks are required, only the normal operational lifecycle of open intents plus a routine parameter change.

### Recommendation
Snapshot the fee token address per order at `placeOrder` time (e.g., add a `feeToken` field alongside `TRANSACTION_FEES` in the `_orders`/`WithdrawalRequest` accounting, analogous to the seed report's recommendation to store `tokenAddress` in the `Application` struct), and use that stored value in `_withdraw`/`withdraw` instead of re-reading `IDispatcher(host()).feeToken()` live. Additionally, `EvmHost.updateHostParamsInternal`'s `CannotChangeFeeToken` guard should be extended (or a coordinated sweep/migration procedure enforced) to cover registered downstream `IApp` fee-token holders, not just the host's own balance.

### Proof of Concept
1. Deploy `EvmHost` with `feeToken = TokenA`, and `IntentGatewayV2` configured against it.
2. User calls `placeOrder` with `order.fees > 0`; `TokenA` is `safeTransferFrom`'d into the gateway and `_orders[commitment][TRANSACTION_FEES] = fees` is recorded (no token reference stored) — `evm/src/apps/IntentGatewayV2.sol` lines 345-361.
3. Before the order is filled/refunded, governance calls `EvmHost.updateHostParams` with `feeToken = TokenB`. This succeeds as long as `EvmHost`'s own `TokenA` balance is zero — it does not check `IntentGatewayV2`'s escrowed `TokenA` balance — `evm/src/core/EvmHost.sol` lines 617-621.
4. Solver fills the order (or user cancels/refunds it); `_withdraw` is invoked and executes `IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees)`, which now resolves to `TokenB` — `evm/src/apps/intentsv2/IntentsBase.sol` lines 412-417.
5. Either the transfer reverts (gateway holds no `TokenB`), reverting the whole withdrawal and locking the user's principal tokens too, or it succeeds by drawing down unrelated `TokenB` escrow belonging to other orders, while the original `TokenA` fee remains stranded in the contract forever.
