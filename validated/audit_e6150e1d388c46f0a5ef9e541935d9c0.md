### Title
Auto-adoption of GitHub API `clone_url` silently redirects a repository's git remote - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's associated GitHub metadata (e.g. after account/permission changes, periodic refresh, or reopening a repo), it calls `updateRemoteUrl()`, which will automatically rewrite the local git remote to whatever `clone_url` the GitHub API currently reports for that repository, as long as the URL scheme matches and the user hasn't diverged the remote from the last known clone URL. [1](#0-0) 
This mirrors the report's underlying pattern: a piece of state (`ThrusterFactory`'s yield-cut / here, the local `origin` remote URL) is silently updated to reflect an attacker/externally-controlled value (`apiRepo.clone_url`) without the user being consulted, based on stale/insufficient invariant checks.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the repository via `api.fetchRepository(owner, name)` and, if the local repo already has an associated `GitHubRepository`, unconditionally passes the freshly fetched `apiRepo` into `updateRemoteUrl()`: [2](#0-1) 

`updateRemoteUrl()` then decides whether to call `gitStore.setRemoteURL()` based only on:
1. `protocolsMatch` – comparing `URL.parse(...).protocol` of the old and new URL (e.g. both `https:`), and
2. `remoteUrlUnchanged` – whether the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL`. [3](#0-2) 

Neither check validates that the new clone URL's **host** is trustworthy or unchanged — it only checks that the scheme (`https:`/`http:`) matches. `urlMatchesRemote()` (used for the "already diverged" check) also only compares hostname/owner/name structurally, it does not pin to a known-good host list. [4](#0-3) 

Because the API response is the sole source of truth for `clone_url`, any actor who can influence that field for a repository the user already has cloned — e.g., a GitHub Enterprise Server admin/compromised GHES instance, a malicious enterprise proxy terminating TLS for an internal GHE endpoint, or a compromised/rogue API response via a MITM'd corporate proxy that Desktop trusts — can cause Desktop to silently `git remote set-url origin <new-url>` on the user's behalf. The test suite even encodes the fully-automatic acceptance path: an updated `clone_url` is adopted without prompting the user. [5](#0-4) 

The changelog confirms this is an intentional feature ("Update the remote url when a repository's name changes on GitHub"), designed for the benign case of repo renames, but it does not defend against a malicious clone_url value. [6](#0-5) 

### Impact Explanation
If exploited, the next `git fetch`/`git pull`/`git push` performed by the user through Desktop silently targets an attacker-controlled remote instead of the legitimate one. This can result in:
- Silent corruption of what the user pushes (code, secrets, or history sent to an attacker-controlled server).
- Fetching attacker-controlled objects/refs into the user's local repo (a git-remote-response-controlled primitive explicitly listed as in-scope), which combined with Desktop's other push/fetch/checkout code paths (hooks execution, submodules, etc.) is a supply-chain escalation vector.
- Because the change happens transparently in the background refresh flow (`refreshSelectedRepositoryAfterAccountChange` / periodic repository refresh), the user is not shown a diff or confirmation dialog akin to the "Repository Settings > Remote" screen — unlike the explicit, user-initiated `_setRemoteURL` path. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
This requires the attacker to control (or MITM) an API response for a repository the victim has *already* associated in Desktop with a matching hostname/owner/name and unmodified default remote — realistic for GHES/GHE deployments where the API host is attacker-influenced (malicious/compromised enterprise instance, or an org that can rename/transfer/recreate a repo under the same owner/name with a different backing clone target), and does not require local access, admin rights, or prior malware. It is a plausible but moderate-likelihood path since it depends on the specific enterprise/GHE trust model and requires the `protocolsMatch`/`remoteUrlUnchanged` gates to be satisfiable, which they are trivially for any `https`→`https` clone_url swap.

### Recommendation
- Do not silently rewrite `origin`/default remote URLs from API data; when `clone_url` hostname differs from the previously known-good hostname, prompt the user for explicit confirmation, similar to the manual "Repository Settings" flow.
- Pin/verify that the new `clone_url` host matches the account's configured endpoint (`account.endpoint`/`getHTMLURL(account.endpoint)`) rather than only comparing scheme.
- Log/telemetry an event whenever an automatic remote-URL update occurs, so unexpected redirections are auditable.

### Proof of Concept
1. User clones `https://ghe.example.com/org/repo` and opens it in Desktop; Desktop associates it with a `GitHubRepository` whose `cloneURL` is `https://ghe.example.com/org/repo`.
2. An attacker with control over the GHES/API host (or a MITM position on the enterprise API endpoint) alters the `clone_url` field returned for `GET /repos/org/repo` to `https://attacker.example.com/org/repo` (same scheme, different host).
3. Desktop performs a routine refresh (e.g., account switch, periodic repository refresh) calling `repositoryWithRefreshedGitHubRepository()` → `updateRemoteUrl()`. [2](#0-1) 
4. Since `protocolsMatch` is true (`https:` == `https:`) and `remoteUrlUnchanged` is true (user hadn't manually edited the remote), `gitStore.setRemoteURL('origin', 'https://attacker.example.com/org/repo')` executes without any prompt. [9](#0-8) 
5. The user's next push/fetch in Desktop now silently targets `attacker.example.com`, exfiltrating code or ingesting attacker-controlled objects.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
