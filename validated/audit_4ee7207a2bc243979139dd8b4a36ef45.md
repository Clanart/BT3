### Title
`SignableTransaction` bounds the fee only from below — the actual fee paid can be arbitrarily larger than `needed_fee` and is never checked - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Vault fee report's bug class — each constraint checked individually while the *aggregate* cost to the user is left unbounded — maps directly onto `SignableTransaction::new`. The code enforces only a *lower* bound on the fee (`TooLowFee`) and a *solvency* bound (`NotEnoughFunds`), but the actual fee, defined as `sum(inputs) - sum(outputs)`, is never upper-bounded against the caller-intended `fee_per_vbyte`. Any leftover that does not become a change output is silently burned as fee, and that leftover can be arbitrarily large.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256):

- `needed_fee = fee_per_vbyte * vbytes` is the caller's intended fee (line 206).
- `fee()` — the fee actually paid — is `sum(prevouts) - sum(outputs)` (lines 138-141).
- The change logic (lines 224-235) only creates a change output if the leftover `input_sat - payment_sat - fee_with_change` is `>= DUST` (line 229). If there is no change address, if `checked_sub` fails, or if the value is below `DUST`, **the entire remainder becomes fee** with no check comparing it to `needed_fee`.
- The only fee checks are `needed_fee < min_relay` → `TooLowFee` (line 211) and `input_sat < payment_sat + needed_fee` → `NotEnoughFunds` (line 215). Nothing rejects `actual_fee >> needed_fee`.

Additionally, `calculate_weight_vbytes` (lines 62-99) builds its weight-estimation `Transaction` from `payments` and `change` only — the OP_RETURN `data` output pushed at lines 194-202 is omitted — so `needed_fee` itself is systematically underestimated when `data` is present, weakening the already-lower-bound-only check further.

### Impact Explanation
A transaction built through this API can pay a fee vastly exceeding the intended `fee_per_vbyte` — e.g., inputs of 1 BTC, payments of a few thousand sats, and change omitted or rendered uneconomical by a marginal `checked_sub`/dust result, sends ~the entire input to miners. The signing flow (`multisig`, `TransactionMachine::sign`) commits to these outputs via `Prevouts::All`, so the excess-fee transaction is what gets threshold-signed. Funds are irreversibly lost to miners — strictly worse than the Vault case where the overpayment is at least protocol-defined.

### Likelihood Explanation
Any integrator or wallet flow that (a) doesn't pass a change script, (b) passes a change script but lands in the `value < DUST` or `checked_sub` failure branch — where the excess over `needed_fee` is still unbounded up to `fee_with_change + DUST - 1` — or (c) has a mismatch between input selection and payments will silently produce an overpaying transaction instead of an error. Unlike the Vault report, no attacker is needed; the hazard is the missing upper bound itself, which is exactly the acknowledged bug class.

### Recommendation
After finalizing `tx_outs`, compute `actual_fee = input_sat - sum(tx_outs)` and reject if it exceeds `needed_fee` (or `fee_with_change`) by more than a tight tolerance, returning a new `TransactionError::FeeTooHigh`. Also include the OP_RETURN output in `calculate_weight_vbytes` so `needed_fee` reflects the real transaction weight.

### Proof of Concept
```rust
// One 1 BTC input, a single dust-sized payment, NO change address.
let inputs = vec![output_worth_1_btc];
let payments = vec![(addr(), DUST)]; // passes the per-payment dust check
let tx = SignableTransaction::new(inputs, &payments, None, None, fee_per_vbyte).unwrap();

// needed_fee is fee_per_vbyte * ~150 vbytes (a few hundred sats).
// fee() == 100_000_000 - 546 ≈ 99_999_454 sats — the entire input — with no error.
assert!(tx.fee() > tx.needed_fee()); // never checked
```
Same result with a change address when `input_sat - payment_sat - fee_with_change` is `< DUST`: the leftover (`up to fee_with_change + DUST - 1` above `needed_fee`) is burned without error. With `data = Some(...)`, `needed_fee` is additionally undercharged because the OP_RETURN output is excluded from the weight estimate at send.rs:85-99.
