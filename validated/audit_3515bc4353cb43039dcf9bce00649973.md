### Title
`EncryptedMessage` proof-of-possession does not bind the intended recipient, allowing a ciphertext relay to frame an honest sender for blame - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The TLS hostname-verification bug class — a credential verified as "valid" but not checked against the identity it is supposed to belong to — maps onto the PedPoP DKG's per-message encryption-key proof of possession. `pop_challenge` binds the `context`, the nonce, the per-message key, the `sender`, and the message bytes, but never binds the intended `recipient`. A share ciphertext honestly produced for participant Bob can be fed to participant Carol's `calculate_share`/`blame` path (or to `AdditionalBlameMachine::blame` with `sender = Alice, recipient = Carol`) and every verification step still passes, because nothing in the transcript proves the message was addressed to the party now processing it.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `encrypt` produces `EncryptedMessage { key, pop, msg }` where `pop` is a Schnorr signature over `pop_challenge::<C>(context, msg.pop.R, msg.key, sender, msg)` [1](#0-0) . The transcript appends `context`, `nonce`, `key`, `sender`, and `message` — but the recipient `Participant` index never appears. The receiver's identity enters decryption only implicitly via `ecdh(&self.enc_key, msg.key)` [2](#0-1) , so any ciphertext with a valid `pop` for its claimed `sender` is accepted into the decryption/blame pipeline regardless of whom it was encrypted for.

In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-609`), after `decrypt_with_proof` succeeds — which it does whenever the accusing recipient honestly knows their own `enc_key`, since `EncryptionKeyProof` is a DLEq over `[G, msg.key]` / `[enc_keys[recipient], proof.key]` [3](#0-2)  — the decrypted bytes are garbage for a relayed message. `C::F::from_repr` then either rejects the bytes or yields a scalar that fails `share_verification_statements` [4](#0-3) . In both branches `blame_internal` returns `sender`, i.e. the honest party who produced a perfectly valid share for someone else.

The same gap exists in the interactive path: `Encryption::decrypt` batch-verifies only `pop` keyed on `from` [5](#0-4) , so a relayed share is silently decrypted to garbage in `calculate_share`, producing `PedPoPError::InvalidShare { participant: honest_sender, blame: Some(..) }` [6](#0-5) .

### Impact Explanation
An unprivileged party who can deliver a participant's published `EncryptedMessage` bytes into another participant's `shares` map (or trigger a `VerifyBlame`/blame evaluation naming the wrong recipient) causes an honest sender to be conclusively "proven" faulty. The blame verdict is externally verifiable — `AdditionalBlameMachine::blame` deterministically returns `sender` — so the honest party is identified as malicious and, in the Serai usage, slashed/removed, while the actual attacker is never identified. This is a concrete integrity failure of the blame mechanism reachable purely from public protocol messages, mirroring the advisory's "valid certificate accepted for the wrong identity."

### Likelihood Explanation
Exploitation requires only copying an existing valid ciphertext and presenting it under the same `sender` to a different `recipient` — no key knowledge, no collusion, and no broken transport assumptions. DKG share messages are routinely disseminated where observers or a misdelivering/malicious coordinator-equivalent can redirect them; the library itself states it "does not handle networking," so index-to-message misdelivery is exactly the untrusted-input surface it exposes. The only mitigating factor is that the surrounding authenticated channel must let a third party re-attribute the recipient, but the PoP is precisely the mechanism meant to make ciphertexts self-authenticating, and it fails to do so for the recipient dimension.

### Recommendation
Bind the recipient into the proof of possession: extend `pop_challenge` in `crypto/dkg/pedpop/src/encryption.rs` to `append_message(b"recipient", recipient.to_bytes())` and pass the recipient index through `encrypt` and `decrypt`/`decrypt_with_proof`. A ciphertext addressed to Bob then fails PoP verification when processed as addressed to Carol (`DecryptionError::InvalidSignature` → blamed party is the relayer/accuser path, not the honest sender). Alternatively, derive the cipher key in `cipher()` from a transcript also committing to the recipient, achieving the same binding at the ECDH layer.

### Proof of Concept
1. Run PedPoP with `n >= 3`; let honest Alice (`sender = 1`) produce `msg_ab = EncryptedMessage` encrypting her share to Bob (`recipient = 2`). The `pop` challenge commits only to `(context, R, key, sender=1, msg)`.
2. Attacker copies `msg_ab` and delivers it to Carol (`recipient = 3`) inside `shares` under key `Participant(1)`, or invokes `AdditionalBlameMachine::blame(sender=1, recipient=3, msg_ab, proof)` where Carol supplies her honest `EncryptionKeyProof` (DLEq verifies because it is over Carol's registered `enc_key`).
3. `pop.verify` succeeds — `sender` is still 1 and no recipient field exists to mismatch.
4. Decryption yields `ecdh(carol_enc_key, msg_ab.key) ≠ ecdh(bob_enc_key, msg_ab.key)` → garbage share bytes → `from_repr` fails or `share_verification_statements` is non-identity → `blame_internal` returns `Participant(1)`: Alice is blamed despite having sent a valid share.

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
