### Title
Partial-commit patch is built from a freshly re-fetched diff, letting an attacker-triggered change to the working file silently include unreviewed content in the commit - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop's partial-commit flow separates "line selection" (the user reviewing a diff in the UI and choosing which lines to include) from "patch construction" (turning that selection into a `git apply --cached` patch at commit time). The selection is stored as an index-based `DiffSelection` bound to a specific diff snapshot, but when the commit is actually executed, `applyPatchToIndex` re-reads the working directory diff from disk and reapplies the old index-based selection to this brand-new diff. This is structurally the same "accept input after the decision-relevant state has already been captured, but before the state is used" flaw described in the VRF report: the app commits to a decision (which lines to stage) based on a snapshot, but the actual state used to realize that decision is re-derived later from mutable, attacker-influenceable data.

### Finding Description
When a user partially selects lines to commit, the UI computes a `DiffSelection` against a diff obtained via `getWorkingDirectoryDiff` and stores it on the `WorkingDirectoryFileChange` (`app/src/lib/stores/app-store.ts:3444-3448`, `updateChangesWorkingDirectoryDiff`). Selection state (`isSelected(absoluteIndex)`) is keyed purely by **absolute line index** into that diff, not by line content or hash.

At commit time, `_commitIncludedChanges` (`app/src/lib/stores/app-store.ts:3680-3711`) passes the selected `WorkingDirectoryFileChange` objects — carrying the old selection — into `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) → `applyPatchToIndex` (`app/src/lib/git/apply.ts:12-84`).

Critically, `applyPatchToIndex` does **not** reuse the diff the user reviewed. It fetches a fresh diff at line 60:
```
const diff = await getWorkingDirectoryDiff(repository, file)
```
and then builds the patch via `formatPatch(file, diff)` (`app/src/lib/patch-formatter.ts:129-232`), which walks `diff.hunks` and asks `file.selection.isSelected(absoluteIndex)` — indices computed against the *old* diff — against the *new* hunk/line layout. There is no verification that the newly fetched diff still matches the hunk layout, line counts, or content that the user actually saw and selected.

Between the time the user finishes selecting lines (e.g., they open the Changes tab, pick lines to stage) and the moment the Commit button's async flow reaches `applyPatchToIndex`, the working tree file can be mutated by processes outside the user's direct, reviewed action: a `post-checkout`/`post-merge` hook, a `clean`/`smudge` filter defined via `.gitattributes`, an LFS or submodule operation, or a concurrent background operation Desktop itself runs (background fetch/fast-forward/`_refreshRepository`, see `app-store.ts:5924-5987`, `4047-4144`) that can trigger the changes list/diff to be recomputed for the same file while a commit is in flight. None of these paths re-validate that `file.selection`'s index set still corresponds to the same lines it corresponded to when the user made the selection — the only place that attempts to reconcile stale selections is `updateChangesWorkingDirectoryDiff` in the *live UI diff-refresh path* (`app-store.ts:3478-3497`, "the diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"), which is explicitly a best-effort placeholder and is not consulted by `applyPatchToIndex`, which re-diffs and re-applies indices independently.

This mirrors the report's broken invariant exactly: "outcome depends on user-supplied input [line selection] and data captured [the diff snapshot] — but the app re-reads that data at fulfillment time [patch application] rather than freezing it at request time [selection time]." The result is that the "index selection" invariant the user relied on when reviewing and approving a partial commit is not actually enforced against the content they saw.

### Impact Explanation
If the file content shifts between selection and patch construction (extra/removed lines, reordered hunks), `formatPatch`/`applyPatchToIndex` can produce a patch that stages **different lines than what the user selected and reviewed** — including lines the user explicitly chose to exclude, or omitting lines the user chose to include — because the index positions no longer line up with the reviewed content. This is a silent corruption of what the user commits, one of the explicitly valid impact classes for this exercise (an attacker-influenced repository/hook/filter can change on-disk content between review and commit without any additional prompt to the user, and the commit still succeeds with different content than approved).

### Likelihood Explanation
Medium: the change window between "user finishes selecting lines" and "patch construction runs" always exists (it's inherent to the two-phase design), and Desktop already performs multiple background operations (fetch, fast-forward, hooks) that can touch the working tree during this window; a repository author only needs to arrange for a filter/hook or a race with an app-driven refresh to land in that window. It does not require local/physical access or leaked credentials — it can be set up entirely from repository content (hooks/filters) fetched/cloned by the victim.

### Recommendation
Freeze the diff used for line-selection at the time the selection is made, and use that exact frozen diff (not a freshly re-fetched one) when generating the patch in `applyPatchToIndex`/`formatPatch`. If the working file has changed since the diff was captured (e.g., verify via mtime/hash or a content digest of the diff), refuse the partial commit and force the user to re-review the diff, rather than silently reapplying stale line indices to new content — directly analogous to the report's recommendation to decouple "user input" (the reviewed selection) from later, potentially different state, and only act on input captured before the state that determines the outcome was finalized.

### Proof of Concept
1. Open a repository with a modified tracked file `foo.txt` containing lines A, B, C.
2. In the Changes view, select only line B for a partial commit (this computes `DiffSelection` against the diff snapshot with absolute index for B) but do not commit yet.
3. Before the commit completes, cause the working copy of `foo.txt` to change out from under the selection — e.g., a `post-checkout`/`smudge` filter defined by the repo's `.gitattributes` rewrites the file, or a concurrent Desktop background fetch/fast-forward touches the file (`app-store.ts:5924-5987`) — inserting a new line before B, shifting all subsequent absolute indices by one.
4. Click Commit. `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) calls `getWorkingDirectoryDiff` again, getting the new diff, and calls `formatPatch(file, diff)` with the *old* selection object still saying "index N is selected."
5. Because of the line shift, index N in the new diff now corresponds to a different line (e.g., C instead of B). The resulting commit stages line C's content though the user selected and approved only line B — the user's approved selection has been silently substituted, with no warning shown before or after the commit. export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
