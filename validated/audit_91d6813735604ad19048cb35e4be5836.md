### Title
Untrusted per-participant preprocess/share vectors are indexed without length checks, letting any cosigner panic honest signers mid-protocol - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` treat each participant's `Vec<Preprocess>` / `Vec<SignatureShare>` as having exactly `self.sigs.len()` entries. The deserializers (`read_preprocess`, `read_share`) place no length bound on what a counterparty supplies, so a malicious cosigner in a Bitcoin multisig signing session can send a short or empty vector and cause an index-out-of-bounds / `remove(0)` panic on every honest participant, aborting the signing session.

### Finding Description
In `TransactionSignMachine::sign`, the peer-supplied commitments map is re-sliced per input:

```rust
// networks/bitcoin/src/wallet/send.rs:364-371
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
  .collect::<Vec<_>>();
```

`commitments[c]` indexes into a `Vec<Preprocess>` whose length is whatever the sender encoded. If any participant supplies fewer than `self.sigs.len()` preprocesses, `commitments[c]` panics. The same pattern exists in `TransactionSignatureMachine::complete`:

```rust
// networks/bitcoin/src/wallet/send.rs:419
shares.iter_mut().map(|(l, shares)| (*l, shares.remove(0))).collect::<HashMap<_, _>>()
```

`shares.remove(0)` panics on an empty vector. `read_share` (`send.rs:409-411`) reads `self.sigs.len()` shares on the *honest* side, but the produced `HashMap<Participant, Vec<SignatureShare>>` delivered to `complete` can contain an arbitrarily short vector per participant (e.g., constructed by a coordinator deserializing shares independently or a peer sending a truncated-but-valid encoding).

### Impact Explanation
Any unprivileged cosigner in a threshold signing session for a Bitcoin transaction can send a malformed preprocess or signature-share vector and deterministically panic all honest participants inside `sign`/`complete`. Because these machines consume messages that arrive over the wire (`read_preprocess`, `read_share`), the trigger is fully attacker-controlled bytes. The panic kills the signing attempt — and, since Rust panics unwinding into async/task contexts typically abort the signer task, it constitutes a repeatable remote denial of service against the multisig, preventing any Bitcoin spend from being signed. Severity: Medium (availability of the signing protocol; no secret leakage).

### Likelihood Explanation
Exploitation requires only participation in a signing session — the same trust level assumed for peers sending preprocesses/shares — and crafting a `Vec` shorter than the number of transaction inputs. No race or special timing is needed; `commitments[c]` panics on the first input beyond the attacker's vector length, and `shares.remove(0)` panics on the first `complete` call. The code contains no length validation anywhere between deserialization and indexing.

### Recommendation
Validate lengths before indexing:
- In `sign`, check `commitments.values().all(|v| v.len() == self.sigs.len())` and return `FrostError::InvalidCommitment`/equivalent instead of indexing blindly; prefer `get(c)` with an error path.
- In `complete`, verify each participant's share vector has exactly `self.sigs.len()` (or remaining) elements before `remove(0)`, or drain the vector and zip against `sigs`.
- Optionally enforce the expected vector length at the `read_preprocess`/`read_share` layer so malformed encodings fail at deserialization.

### Proof of Concept
1. Build a `SignableTransaction` with ≥2 inputs (`SignableTransaction::new` with two `ReceivedOutput`s), and create `TransactionMachine`s for a 2-of-3 FROST set via `tx.multisig(&keys)`.
2. Run `preprocess` on each honest signer. Have the attacker return a `Preprocess` vector of length 1 (e.g., serialize a single valid `Preprocess`, then deserialize it on the coordinator into a `Vec` of length 1).
3. Pass `commitments` including the attacker's short vector into `TransactionSignMachine::sign`; `commitments[c]` at `send.rs:368` panics with index-out-of-bounds on input index 1.
4. Alternatively, let `sign` succeed for honest parties, then have the attacker submit `vec![]` as their `SignatureShare` vector; `shares.remove(0)` at `send.rs:419` panics inside `TransactionSignatureMachine::complete`.
