## Finding

The GitHub Desktop analog of this bug class is a stale-diff / stale-selection race in the partial (hunk/line-level) commit path: the line selections a user makes are validated against one diff snapshot, but the actual patch applied to the index is generated from a **freshly re-fetched** diff of the working tree, with no check that the two are still consistent.

### Title
Partial-commit line selection is applied against a re-fetched, potentially different diff, silently corrupting what gets committed - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user partially stages a file (selects individual lines/hunks to commit), Desktop stores that selection as a `DiffSelection` bitmap keyed by *absolute line index* into a specific diff object [1](#0-0) . That selection is computed against the diff the UI rendered at selection time. However, when the commit is actually created, `applyPatchToIndex` does not reuse that diff — it calls `getWorkingDirectoryDiff` again, re-reading the file from disk at commit time [2](#0-1) , and then feeds the *old* selection into `formatPatch` against this *new* diff's hunks [3](#0-2) .

### Finding Description
The broken invariant is: "the line indices a user reviewed and selected for commit remain valid against the diff actually used to build the patch." Nothing enforces that. `stageFiles` iterates over the files with partial selections and calls `applyPatchToIndex(repository, file)` for each [4](#0-3) . Inside, the diff is regenerated from the live working directory rather than passed in from the state the user actually looked at and clicked on: [2](#0-1) 

`formatPatch` then walks `diff.hunks` (the *new* diff) and, for every non-context line, asks `file.selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` [1](#0-0) . `unifiedDiffStart` is a positional offset computed from the hunk layout of whichever diff produced it — if the file changed on disk between the moment the user made their selection and the moment `applyPatchToIndex` runs, hunk boundaries and line offsets shift, so the same absolute index no longer corresponds to the same logical line the user selected. The old bitmap is silently reinterpreted against new hunk geometry.

This exactly mirrors the smart-contract bug's shape: a value (`totalCoverTokens`/available funds) is validated at one point in time (claim creation) and consumed at a later point in time (claim settlement) after intervening state changes, with no guard tying the two together. Here, the "guard" (the diff snapshot backing the user's selection) is checked once, then a completely different, freshly-fetched snapshot is used for the actual write.

### Impact Explanation
This directly maps to the listed valid-impact category "silent corruption of what the user commits or pushes." If the working-tree file is mutated between the time Desktop renders the diff/selection UI and the time the user clicks Commit — e.g. by an automatic on-save formatter/linter configuration shipped inside a cloned/fetched repository (such as `.vscode/settings.json` enabling format-on-save, or a build/watch task defined by the project and started as part of normal workflow) — the resulting commit can include lines the user explicitly deselected, or omit/alter lines the user selected, without any warning. Because Desktop shows no re-confirmation of the actual patch that was applied, the user believes they committed exactly what they reviewed.

### Likelihood Explanation
The window between diff render and commit is arbitrarily long (the user can leave the Changes view open, review a diff, switch away, come back and commit later), giving ample opportunity for repo-shipped tooling to alter the file in the background. The code path performing the unsafe re-fetch-and-reuse is on every partial commit, not a rare corner case, since `stageFiles` invokes `applyPatchToIndex` for any file with `DiffSelectionType` other than `All`/`None` [5](#0-4) .

### Recommendation
`applyPatchToIndex`/`stageFiles`/`createCommit` should use the same diff object that was used to construct the `DiffSelection`, rather than re-fetching a new diff at apply time. If the working tree has changed since the diff was captured (compare mtime/hash or diff content), Desktop should refuse the partial commit and force the user to refresh their selection instead of silently reinterpreting stale line indices against new hunk data.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file with several independent changes; open the Changes diff and deselect specific lines/hunks for the commit (leave "Commit" pending, not yet clicked).
2. While the diff/selection is displayed, have the working-tree file mutated by another process associated with the same repository (e.g., a formatter/build task configured by the repo itself, or simply another editor tab auto-saving), changing line counts/positions in the file without the user re-opening the diff.
3. Click Commit. `stageFiles` → `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` [2](#0-1)  and `formatPatch` applies the old absolute-index selection to the new hunk layout [1](#0-0) .
4. Inspect the resulting commit: it differs from what was displayed/selected in the UI at review time, with no error or warning shown to the user.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
