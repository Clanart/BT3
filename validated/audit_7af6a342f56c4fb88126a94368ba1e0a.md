### Title
Unvalidated `ReceivedOutput` triple reports spendable funds for unrelated outpoints - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts attacker-controlled `offset`, `output`, and `outpoint` fields as three independent values, without proving that the referenced Bitcoin outpoint actually contains the claimed output. [1](#0-0) 

### Finding Description
`ReceivedOutput` is defined as a spendable output and consists of a scalar offset, a `TxOut`, and the `OutPoint` that should locate that `TxOut` on-chain. [2](#0-1)   
`ReceivedOutput::read` separately deserializes those three fields and immediately returns `Ok(ReceivedOutput { offset, output, outpoint })`, with no consistency check between the claimed output and the referenced outpoint. [1](#0-0)   
`SignableTransaction::new` then trusts `input.output.value` when calculating available funds, while using `input.outpoint` as the actual transaction input. [3](#0-2)   
`SignableTransaction::multisig` checks only that the supplied offset derives a key matching the claimed `prevouts[i].script_pubkey`; it does not check that `previous_output` resolves to that `TxOut`. [4](#0-3)   
Consequently, a byte string can describe an output that looks spendable under the vault key while pointing to a nonexistent, spent, lower-value, or otherwise unrelated UTXO. [5](#0-4) [3](#0-2) 

### Impact Explanation
An unprivileged party can cause an integrator to report or account for funds that cannot actually be spent. [6](#0-5)   
Because the claimed `TxOut` controls `input_sat`, an attacker can inflate the apparent input amount and cause payments, fees, or change to be calculated against funds that the referenced outpoint does not contain. [7](#0-6)   
If the `offset` and `script_pubkey` are made consistent, `multisig` accepts the input and signs for it, but the resulting transaction references the attacker-selected outpoint and is unspendable or invalid when the actual UTXO does not equal the claimed `TxOut`. [4](#0-3) [8](#0-7) 

### Likelihood Explanation
The attack requires only the ability to submit serialized `ReceivedOutput` bytes to a caller which treats them as a spendable-input description. [1](#0-0)   
The attacker does not need a validator key, malformed curve point, leaked secret, or control over the Bitcoin network; the scalar, `TxOut`, and `OutPoint` encodings can be chosen independently. [9](#0-8)   
The vulnerable path is reachable whenever deserialized wallet outputs are separated from scanner construction, because the authentic producer couples the fields while the deserializer does not verify that coupling. [10](#0-9) 

### Recommendation
Treat a serialized `ReceivedOutput` as unauthenticated witness metadata and require callers to resolve each `outpoint` against the Bitcoin UTXO set, verifying that the resolved `TxOut` exactly equals the encoded `output`. [5](#0-4)   
In addition, retain or recompute the authenticated `script_pubkey`-to-`offset` mapping produced by `Scanner`, rather than accepting the offset as an independently supplied field. [11](#0-10) 

### Proof of Concept
1. Let `key` be an even Taproot-compatible group key and let `script = p2tr_script_buf(key).unwrap()`. [12](#0-11) 
2. Construct an encoded `ReceivedOutput` containing `offset = Scalar::ZERO`, `output = TxOut { value: 10_000_000, script_pubkey: script }`, and an arbitrary `outpoint` which does not resolve to that `TxOut`. [2](#0-1) 
3. Feed those bytes to `ReceivedOutput::read`; deserialization succeeds because all three components are individually well-formed. [1](#0-0) 
4. Pass the object to `SignableTransaction::new`; `input_sat` becomes `10_000_000` while the transaction input spends the unrelated `outpoint`. [3](#0-2) 
5. Call `multisig` with the corresponding `ThresholdKeys`; it accepts because `offset = 0` makes `offset.group_key()` match the encoded script. [13](#0-12) 
6. The resulting transaction commits to the claimed `prevouts` in the Taproot sighash, but does not spend the claimed output because the actual input remains the attacker-selected outpoint. [8](#0-7)
