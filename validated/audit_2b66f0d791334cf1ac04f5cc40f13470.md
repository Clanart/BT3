### Title
Unvalidated attacker-controlled regex from `.claude/hookify.*.local.md` enables ReDoS on every Bash/Edit/Write hook call - (File: plugins/hookify/core/rule_engine.py)

### Finding Description
`config_loader.load_rules()` globs `.claude/hookify.*.local.md` and parses arbitrary YAML frontmatter into a `Rule`, taking the `pattern` (or `conditions[].pattern`) field verbatim with no length limit, complexity check, or safe-regex validation [1](#0-0) . `Rule.from_dict` stores this pattern unchanged into a `Condition` [2](#0-1) . On every `Bash`, `Edit`, `Write`, and `MultiEdit` tool call, `pretooluse.py` calls `load_rules(event=...)` and `RuleEngine.evaluate_rules`, which for `regex_match` conditions calls `_regex_match(pattern, field_value)` [3](#0-2) [4](#0-3) . `_regex_match` compiles the pattern with `compile_regex` (an `lru_cache`d `re.compile(pattern, re.IGNORECASE)`) and calls `.search(text)` against attacker/user-influenced input such as the full Bash `command` string or file `new_text`/`content` [5](#0-4) [6](#0-5) . The only exception handling is `except re.error`, which catches invalid syntax, not catastrophic backtracking — a pathological pattern (e.g. `(a+)+$`, `(a|a)*$`) paired with a long non-matching input causes exponential-time execution that is not an exception and is not caught anywhere in this code path.

The hook's outer `try/except` in `pretooluse.py` only guards against Python exceptions and always `sys.exit(0)`s on error/allow [7](#0-6) , so a hang inside `re.search` is not caught by that handler; the process will simply run past the hook's configured `timeout: 10` in `hooks.json` [8](#0-7) . Because `load_rules()` re-reads and re-evaluates the rule file on every single subsequent Bash/Edit/Write call (no caching of "this rule is slow", no per-pattern timeout, no static ReDoS detection), the same malicious rule degrades or hangs enforcement repeatedly until the file is deleted or `enabled: false` is set.

### Impact Explanation
A single committed `.claude/hookify.*.local.md` file with a catastrophic-backtracking `pattern` causes the PreToolUse (and PostToolUse/UserPromptSubmit/Stop) hookify hook to hang for up to the configured hook timeout on every matching tool invocation, degrading the reliability/availability of the approval-gate mechanism repo-wide for anyone who checks out the repository. This is a genuine availability/DoS issue in the enforcement hook itself, reachable purely from ordinary repository content (no admin privileges, no secrets, no social engineering needed beyond the victim cloning/using the repo). It does not by itself force an unauthorized command to execute (Claude Code's own hook-timeout handling, which is outside this repo, determines whether a timed-out hook fails open or closed), so the "user manually disables hookify" escalation described in the question is a plausible but unverified secondary consequence rather than a directly provable code-level bypass.

### Likelihood Explanation
Highly feasible and fully repeatable: creating the malicious rule file requires only write access to the repository's `.claude/` directory (e.g., via a PR, malicious clone, or any contributor with commit access to that directory), and the hookify plugin explicitly advertises that these rules take effect immediately on the next tool call with no restart required [9](#0-8) . No special crafting beyond a well-known ReDoS pattern is needed, and it will trigger on every subsequent Bash/Edit/Write call.

### Recommendation
Validate and bound regex patterns before compiling/using them: enforce a maximum pattern length, run a static ReDoS/complexity check (e.g., reject nested quantifiers like `(a+)+`, `(a*)*`), and/or execute `compile_regex(...).search()` in a subprocess/thread with a hard wall-clock timeout (or use a linear-time regex engine such as `re2`) so a single pathological rule cannot stall the hook beyond a bounded, small budget. Also cache "known slow" patterns and skip or disable rules whose evaluation previously exceeded the budget, logging a warning instead of silently re-attempting them on every tool call.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
1. Create a `Rule` with `pattern=r"(a+)+$"` (or `r"(a|a?)+$"`) and `event="bash"`.
2. Build `input_data = {"tool_name": "Bash", "tool_input": {"command": "a"*40 + "!"}}`.
3. Call `RuleEngine().evaluate_rules([rule], input_data)` wrapped with a wall-clock timer.
4. Assert the call completes within a bounded time (e.g., < 200ms); demonstrate that without a fix it exceeds many seconds/exponential growth as the `a` count increases (parametrize with 20, 30, 40 `a`s to show exponential blowup).
5. Extend as a fuzz test iterating over a corpus of known catastrophic-backtracking patterns (`(a+)+`, `(a*)*`, `(a|aa)*`, `([a-zA-Z]+)*$`) to assert none exceed the bounded execution time, and that `load_rules`/`RuleEngine` reject or safely time-box such patterns rather than hanging.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False
