## Title
`CallDispatcher.dispatch()` has no caller restriction, letting any unprivileged address drain residual ETH/ERC-20 balances left on the shared dispatcher by legitimate `IntentGatewayV2`/`HyperFungibleToken` flows - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report flags arbitrary target/arbitrary calldata external calls that can be abused to trigger `transferFrom` on tokens the victim previously approved. The direct Hyperbridge analog is `CallDispatcher.dispatch()`, which is a fully public, unrestricted function that executes attacker-supplied `Call[]` (arbitrary `to`, arbitrary `data`, arbitrary `value`) from the context of a single, shared, chain-wide singleton contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` for *all* users' predispatch/postdispatch/calldata-execution flows. [1](#0-0) 

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each call with `to.call{value: call.value}(call.data)`. It has no `onlyGateway`, `onlyHost`, or any other caller restriction — it is `external` and callable by anyone, from any account, at any time. [2](#0-1) [3](#0-2) 

This single dispatcher address is the shared execution context for unrelated users across multiple apps:
- `IntentGatewayV2.placeOrder` routes predispatch assets to the dispatcher and executes the order's calls there before sweeping known input tokens back: [4](#0-3) 
- `IntentsBase._execute` (postdispatch) executes an order's `output.call` via the same dispatcher and sweeps only the token types listed in the order's own output assets: [5](#0-4) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept` mint/unlock tokens to a beneficiary and, when that beneficiary is set to the dispatcher (as the docs explicitly recommend for swap flows), invoke `dispatch()` on attacker/sender-controlled calldata: [6](#0-5) 

The documented usage pattern itself shows native ETH being unwrapped and forwarded through the dispatcher via `Call.value`, explicitly noting "the CallDispatcher holds the unwrapped ETH": [7](#0-6) 

Because `dispatch()` has zero access control, any balance the dispatcher holds — even momentarily, or as leftover dust from slippage/rounding in a swap-then-forward call, a partial fill, or any calldata sequence that doesn't 100%-consume the amount it received — is a shared, unprotected pool. Any unprivileged third party can call `CallDispatcher.dispatch()` directly (bypassing `IntentGatewayV2` and `HyperFungibleToken` entirely) with `Call({to: token_or_attacker, value/data: transfer-out})` to sweep out ETH or ERC-20 tokens currently sitting on the dispatcher, regardless of which user's transaction put them there. The `NotContract`/`CallFailed` checks only validate that `to` has code and that the call succeeds — they provide no protection against unauthorized draining of the dispatcher's own funds.

### Impact Explanation
This directly matches the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" criteria: an unprivileged attacker can permissionlessly call a public entrypoint (`dispatch()`) to move value (ETH or ERC-20) that belongs to the protocol/other users out of the shared `CallDispatcher` to an address of their choosing, with no proof, relayer, or privileged role required.

### Likelihood Explanation
Likelihood is driven entirely by whether the dispatcher ever holds a non-zero balance between the moment funds land on it and the moment it is fully swept within the *same* transaction. Since sweeps in `IntentGatewayV2`/`IntentsBase` are scoped only to the token types declared in that specific order's `inputs`/`output.assets`, any other token or any ETH remainder (e.g., swap slippage, rounding, or a calldata sequence that doesn't route 100% of value out) is never swept and remains permanently exposed. Given `CallDispatcher` explicitly documents holding forwarded native ETH mid-flow, and its `dispatch()` is unrestricted, this is a realistic, monitorable, continuously-exploitable condition rather than a purely theoretical one.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized apps that own it (e.g., an allow-list of gateway/HFT addresses set at construction, or make the dispatcher single-use/ephemeral per call via `CREATE2`/clone-and-selfdestruct pattern so no residual state or balance can persist across transactions). Additionally, ensure every flow that routes funds through the dispatcher sweeps the *full* balance of every token/asset actually touched (not just the tokens declared in the order) before the transaction ends.

### Proof of Concept
1. Any user places an order or sends an `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer whose `data`/`predispatch`/`output.call` routes assets through the shared `CallDispatcher` (per the documented WETH-unwrap-and-forward pattern), and the calldata does not consume 100% of the value moved into the dispatcher (e.g., due to slippage/rounding), leaving a small residual ETH or token balance on the dispatcher after the transaction completes.
2. An attacker, with no relationship to that order, calls `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls = [Call({to: attacker, value: residualEthBalance, data: ""})]` (or `Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverBalance)})`).
3. Since `dispatch()` has no caller restriction, the call succeeds and the residual funds are transferred to the attacker, regardless of which user's transaction originally left them there. [3](#0-2)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
