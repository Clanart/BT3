### Title
Permanently Unresponsive Operator With Unspent Collateral Causes Irreversible DoS of All New Deposits - (`core/src/rpc/aggregator.rs`, `core/src/aggregator.rs`, `core/src/verifier.rs`)

### Summary

The `new_deposit` flow requires every registered operator to respond with signatures. If any operator becomes permanently unresponsive while its collateral UTXO remains unspent on Bitcoin, the verifier rejects any deposit that omits that operator, and the aggregator cannot collect signatures from it. There is no admin or protocol mechanism to force-remove such an operator. All new BTC peg-ins are permanently blocked.

### Finding Description

**Deposit signature collection requires all operators to respond.**

`Aggregator::collect_operator_sigs` in `core/src/rpc/aggregator.rs` opens a `deposit_sign` stream with every participating operator via `timed_try_join_all`. If any single operator's gRPC endpoint is unreachable or returns an error, the entire future resolves to `Err` and the deposit is aborted. [1](#0-0) 

`new_deposit` also calls `collect_and_distribute_keys`, which uses `timed_try_join_all` over all operator clients to fetch BitVM Winternitz keys. A single unresponsive operator causes this step to fail before signature collection even begins. [2](#0-1) 

**The verifier enforces that every operator with usable collateral must appear in the deposit.**

During `deposit_finalize`, each verifier iterates its local DB and calls `collateral_check` for every stored operator. If an operator's collateral UTXO is still unspent on Bitcoin but that operator is absent from the deposit's actor set, the verifier returns `BridgeError::InvalidDeposit` and refuses to sign the move-tx. [3](#0-2) 

This creates a two-sided deadlock:
- The aggregator cannot produce a deposit that excludes the broken operator (verifier rejects it).
- The aggregator cannot produce a deposit that includes the broken operator (operator does not respond).

**There is no admin path to force-remove an operator.**

The only production mechanism to remove an operator from the active set is for the operator to spend its own collateral UTXO (triggering the `operator_exit` state in the round state machine). If the operator has lost its private key or its infrastructure has permanently failed, it cannot spend the collateral. No privileged RPC endpoint, security-council action, or on-chain timeout allows a third party to evict the operator.

The test suite itself documents this limitation explicitly: [4](#0-3) 

The comment reads: *"remove an operator and try a deposit, it should fail because the operator is still in verifiers DB. To make it not fail, operator data needs to be removed from verifiers DB."* The only demonstrated recovery path is spending the operator's collateral — impossible if the operator's key is lost.

`fetch_operator_keys` / `fetch_pubkeys_from_entities` also hard-fails if any operator is unreachable, propagating the error all the way up to `new_deposit`. [5](#0-4) 

### Impact Explanation

A single permanently unresponsive operator with an unspent collateral UTXO causes a complete, irreversible DoS of the `new_deposit` RPC. No new BTC can be pegged into the bridge. Existing bridge users are unaffected for withdrawals, but the bridge's peg-in functionality is permanently broken until the operator's collateral is somehow spent — which is impossible without the operator's private key. This is a permanent liveness failure of a critical bridge path.

### Likelihood Explanation

Operators are long-running infrastructure services. Key loss, hardware failure, or a compromised-and-wiped server are realistic scenarios. Because the collateral UTXO is a standard Bitcoin UTXO spendable only by the operator's key, no recovery is possible without that key. A single such event among any operator in the set triggers the deadlock.

### Recommendation

1. **Introduce a force-exit mechanism**: Allow the security council (or an N-of-N verifier quorum) to mark an operator as exited in the verifier DB without requiring the operator's signature, provided a configurable timeout has elapsed with no activity from that operator.
2. **Relax the verifier's mandatory-inclusion check**: Instead of hard-failing when a collateral-holding operator is absent, allow the verifier to accept a deposit if a quorum of verifiers has attested that the operator is unreachable and a grace period has passed.
3. **Separate liveness from collateral state**: Track operator liveness independently of collateral UTXO status so that an unresponsive-but-not-malicious operator can be administratively suspended without slashing.

### Proof of Concept

1. Bridge is running with operators O₀ and O₁, both with unspent collateral UTXOs.
2. O₁'s private key is lost (infrastructure wipe). O₁'s gRPC endpoint is permanently down.
3. A user calls `new_deposit` via the aggregator.
4. `collect_and_distribute_keys` calls `timed_try_join_all` over all operators including O₁ → O₁ times out → `BridgeError` returned → deposit aborted. [6](#0-5) 
5. Even if the aggregator config is updated to remove O₁'s endpoint and restarted, each verifier's `deposit_finalize` checks its DB: O₁ is present with a usable collateral UTXO → `BridgeError::InvalidDeposit` → deposit aborted. [7](#0-6) 
6. O₁ cannot spend its collateral (key lost). No admin RPC exists to force-remove O₁. All future deposits are permanently blocked.
