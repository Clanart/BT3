## Finding

### Title
Escrow Withdrawal Uses Low-Level `.call` Instead of `safeTransfer`, Allowing Silent Transfer Failure and Permanent Fund Loss — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.sol` (the Tron deployment variant of the Hyperbridge Intent Gateway) already imports OpenZeppelin's `SafeERC20` and uses `safeTransferFrom` for escrow deposits, but its `withdraw()` function — the code path that actually pays out escrowed order inputs, transaction fees, and dust sweeps — reverts back to a manually constructed low-level `.call` with `IERC20.transfer.selector` and only checks that the *call itself* did not revert, never that the ERC20 `transfer` returned `true`.

### Finding Description
In `withdraw()`, token payouts are performed like this:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

This pattern is functionally identical to calling `IERC20.transfer()` directly without checking the return value: a low-level `.call` only reverts (`success == false`) if the callee itself reverts. Any TRC-20/ERC-20 token that signals failure by *returning `false`* instead of reverting will make `success == true` even though no tokens moved. This is exactly the bug class from the external report (`transfer()`/`transferFrom()` used without checking the boolean return), just reimplemented at the low-level-call layer instead of the high-level-call layer — and it is especially relevant here because this file targets the Tron/TRC-20 ecosystem, where non-reverting-on-failure token semantics are common.

Immediately after the unchecked transfer, the contract unconditionally decrements escrow accounting:

```solidity
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

The same unchecked `.call` + selector-encoded `transfer` pattern, followed by state mutation that assumes success, also appears in the native/ERC20 dust-sweep admin request handler:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

and for the transaction-fee redemption in the same `withdraw()` function:

```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [4](#0-3) 

By contrast, the deposit path in the very same file correctly uses `safeTransferFrom`:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
``` [5](#0-4) 

This inconsistency shows the withdrawal path was not updated to use `SafeERC20`, even though the import is present in the file.

### Impact Explanation
`withdraw()` is invoked from `onGetResponse` (a host-callback path reached once a GET response proves an order was not filled, triggering a refund) as well as from the fill-settlement flow, and is the sole mechanism releasing escrowed solver/user funds. If the escrowed token silently fails to transfer (returns `false` without reverting), the contract:
1. Marks the order/commitment as settled (`_filled[body.commitment] = beneficiary;`) [6](#0-5) 
2. Decrements the escrow accounting for that token as if funds were paid out [2](#0-1) 

The beneficiary never receives the funds, yet the on-chain accounting treats the escrow as fully released, and the commitment can no longer be replayed for a legitimate withdrawal (state has already advanced). This results in permanent loss of the escrowed bridge funds — the exact "loss of funds" impact class called out by the bounty scope, arising from state that falsely records a cross-chain settlement as complete.

### Likelihood Explanation
No privileged actor, relayer collusion, or malformed proof is required. Any TRC-20/ERC-20 token used as the order's input/fee token that implements the "return `false` on failure" convention (common historically among Tron TRC-20 tokens and some legacy ERC-20 tokens) triggers this path deterministically whenever a transfer condition that the token contract checks internally (e.g., blacklist, paused state, insufficient balance/allowance on the token's own internal ledger) causes it to return `false` instead of reverting. This is a standard token-integration hazard that the codebase's own use of `SafeERC20` on the deposit side demonstrates the developers were aware of and intended to guard against — the withdrawal path was simply missed.

### Recommendation
Replace the manual `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the deposit path's use of `safeTransferFrom`, e.g.:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

### Proof of Concept
1. An order is created and filled with a TRC-20 token `T` that returns `false` (rather than reverting) when the transfer cannot be completed (e.g. due to an internal blacklist check on the beneficiary, or a paused state) — a legitimate, standard-compliant-looking token property.
2. `withdraw()` is triggered (via refund on `onGetResponse` or fill settlement), calling:
   `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` [7](#0-6) 
3. Token `T.transfer()` executes without reverting and returns `false`; the outer `.call` reports `success == true` because the call did not revert.
4. The `if (!success) revert TransferFailed();` guard is bypassed, `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment]` is set — permanently marking the order as settled.
5. The beneficiary's token balance never increased; the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no remaining accounting entry or code path to reclaim them.
