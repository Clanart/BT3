Audit Report

## Title
Unbounded per-request work in `getVoteAccounts` RPC over an attacker-growable vote-account set - (File: `rpc/src/rpc.rs`)

## Summary
`get_vote_accounts` in `rpc/src/rpc.rs` iterates the full `bank.vote_accounts()` map and, for every entry, unconditionally deserializes the vote state and builds an `epoch_credits` vector before any stake-based filtering is applied. Since `StakesCache::check_and_store` inserts any correctly-sized, initialized vote-program account into this map regardless of stake, an unprivileged actor can grow the iterated set arbitrarily by creating zero-stake vote accounts, forcing disproportionate per-call CPU work on any node servicing the RPC method.

## Finding Description
The closure inside `get_vote_accounts`'s `.filter_map(...)` at `rpc/src/rpc.rs:1183-1223` calls `account.vote_state_view()`, computes `last_voted_slot()`, `num_epoch_credits()`, and builds the `epoch_credits` vector via `epoch_credits_iter()...collect()` for every entry in `vote_accounts`, before the `vote_pubkey` filter check is even fully effective for the general (unfiltered) call case, and unconditionally when no `vote_pubkey` filter is supplied. [1](#0-0) 

Stake-based filtering only happens after this expensive work, and only for the delinquent partition, via `keep_unstaked_delinquents`: [2](#0-1) 

The `current_vote_accounts` set — i.e., the common, default-path output of the call — has no stake filter at all, and both partitions require the full deserialization to occur first.

`bank.vote_accounts()` is backed by `Stakes<StakeAccount>::vote_accounts`, populated by `StakesCache::check_and_store`, which upserts any account owned by the vote program that passes `VoteStateVersions::is_correct_size_and_initialized`, with no stake-amount condition on insertion: [3](#0-2) 

This confirms the map can contain an attacker-controlled number of zero-stake vote accounts, since insertion depends only on account size/format, not stake. I was not able to independently re-verify the cited `runtime/tests/vote_account.rs` test or the `VoteInstruction::InitializeAccount` permission model in this session's remaining tool budget, but the `check_and_store` logic reviewed directly supports the claim that stake is not a gating condition for insertion into `bank.vote_accounts()`.

I found no size cap, count limit, or pagination on the number of entries `get_vote_accounts` processes — only `MAX_RPC_VOTE_ACCOUNT_INFO_EPOCH_CREDITS_HISTORY` bounds the epoch-credit history *within* a single account's entry, not the number of accounts processed: [4](#0-3) 

## Impact Explanation
This matches the "single-client low-rate RPC crash/degradation" impact category: a single unauthenticated `getVoteAccounts` call (the default call, with no `vote_pubkey` filter) forces the target RPC node to perform vote-state deserialization and epoch-credit extraction work that scales linearly with the size of `bank.vote_accounts()`, which is attacker-growable by creating cheap vote accounts. This can degrade RPC responsiveness for legitimate callers on that node.

## Likelihood Explanation
The insertion path in `StakesCache::check_and_store` confirms that any correctly-formed vote account, regardless of stake, is retained in the iterated map, which is the necessary precondition for the attack. I could not fully verify within this session whether `VoteInstruction::InitializeAccount` truly has no additional gating (e.g., minimum stake requirement, rate limiting elsewhere) beyond what's cited, since I was unable to re-inspect `programs/vote/src/vote_processor.rs` and the referenced unit test directly in this pass. Based on the `stakes.rs` insertion logic alone, however, the mechanism for growing this set with zero-stake accounts is real and unconditioned on stake in the code reviewed.

## Recommendation
- Apply stake-based (or other cheap) filtering before performing per-account vote-state deserialization and `epoch_credits` construction in `get_vote_accounts`.
- Introduce a cap or pagination on the number of vote accounts processed per `getVoteAccounts` call.
- Consider bounding the retention of zero-stake vote accounts in `StakesCache`/`Stakes::vote_accounts` itself, since this same unbounded map is referenced by other bank/RPC/consensus paths.

## Proof of Concept
1. Create a large number of rent-exempt, correctly-sized, initialized vote-program accounts with zero delegated stake, using distinct signer/authority keys, via ordinary vote-account creation transactions.
2. Confirm via `StakesCache::check_and_store` (`runtime/src/stakes.rs:118-127`) that each such account is upserted into `bank.vote_accounts()` unconditionally on stake.
3. Issue a single unauthenticated `getVoteAccounts` RPC call with no `vote_pubkey` filter against the target node.
4. Observe that `get_vote_accounts` (`rpc/src/rpc.rs:1155-1246`) performs vote-state deserialization and epoch-credit extraction for every one of the attacker-created accounts before any stake filter is applied to the `current_vote_accounts` result set, causing CPU cost proportional to the attacker-controlled account count.
