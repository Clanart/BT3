### Title
Missing `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` on `withdrawals` lets one Bitcoin payout satisfy two `idx` rows and double-credit reimbursement - (File: `core/src/database/schema.sql`, `core/src/database/verifier.rs`)

### Summary
`Database::get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, with no uniqueness constraint forcing that pair to identify at most one `idx`. If Citrea ever reports the same withdrawal outpoint for two different withdrawal indices, `update_withdrawal_utxo_from_citrea_withdrawal` happily writes it into both rows, and a single Bitcoin payout transaction spending that outpoint once will match both rows in the join, causing `PayoutCheckerTask` to mark both `idx`s handled and open two separate reimbursement paths for one fronted payout.

### Finding Description
Binding claimed broken: `count(withdrawals.idx rows marked is_payout_handled/payout_txid for a genuinely, distinctly-fronted payout) == count(distinct Bitcoin payout transactions actually broadcast for that operator)`.

Code path:
- `Database::update_withdrawal_utxo_from_citrea_withdrawal` (`core/src/database/verifier.rs:108-135`) is called once per `idx` from `Verifier::update_citrea_deposit_and_withdrawals` (`core/src/verifier.rs:2248-2262`), for every `(idx, outpoint)` pair returned by `CitreaClientT::collect_withdrawal_utxos`. It writes `withdrawal_utxo_txid/vout` unconditionally for the given `idx`, with no check against other rows already holding that outpoint.
- `withdrawals` (`core/src/database/schema.sql`) has `idx` as the primary/unique key but no `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)`, so two different `idx` values can carry byte-identical outpoints.
- `Database::get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` `ON bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`. Since `bsu` records exactly one spend per physical UTXO, if two `idx` rows share that UTXO, the join fans out to two `(idx, payout_txid)` rows carrying the *same* `payout_txid`.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) consumes that result and calls `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`), setting `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` identically on both `withdrawals` rows.
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) repeatedly calls `get_first_unhandled_payout_by_operator_xonly_pk` (ordered by `idx ASC LIMIT 1`), and for each unhandled `idx` independently runs `handle_finalized_payout` + `end_round` + `mark_payout_handled`. Because both rows independently satisfy "payout_txid IS NOT NULL AND is_payout_handled = FALSE", the task processes both `idx=5` and `idx=6` across two polling passes, opening two separate kickoff/reimbursement flows tied to two different deposits/move-to-vault txids, from a single physically-spent Bitcoin UTXO.

Root cause: the outpoint uniqueness invariant that `get_payout_txs_for_withdrawal_utxos`'s join silently assumes ("one physical UTXO belongs to exactly one withdrawal `idx`") is never enforced in the schema or in `update_withdrawal_utxo_from_citrea_withdrawal`, and Clementine trusts Citrea's per-index RPC returns verbatim via `collect_withdrawal_utxos` without deduplicating against previously-seen outpoints.

Why existing guards don't catch this: `Verifier::is_deposit_valid`, `SPV::verify`, and `verify_storage_proofs` only check that a claimed payout tx's input matches the outpoint *stored at that specific index* in Citrea's contract — they don't cross-check against other indices, so if Citrea's storage genuinely has the duplicate at both indices (which this scope stipulates it does not forbid), the disprove/challenge circuit path is equally satisfied for both `idx`s and provides no additional defense. `Operator::withdraw` (`core/src/operator.rs:560-627`) only checks that the caller's `in_outpoint` matches what Citrea reports for the given `withdrawal_index` (`core/src/operator.rs:589-596`); it performs no cross-index duplicate check either.

### Impact Explanation
A single Bitcoin payout transaction, fronted by the operator once, ends up marking two (or more) `withdrawals.idx` rows `is_payout_handled = TRUE` with the same `payout_txid`. Each handled row independently drives `Operator::end_round`/kickoff and eventually a Reimburse transaction claim, meaning the operator can be reimbursed via two separate kickoffs for value it fronted only once. This directly matches the Critical category "an operator reimbursed for a payout it never funded" (the second reimbursement has no separate, distinct fronted payout backing it). The blast radius scales with however many withdrawal indices Citrea's contract allows to collide on the same outpoint, across any deposits assigned to the same operator.

### Likelihood Explanation
This requires the external precondition (stipulated by the question's scope) that Citrea's Bridge contract does not reject two `withdraw()` registrations with byte-identical `in_outpoint` at the RPC-return layer Clementine trusts — a precondition outside this repo. Given that precondition, the attacker (an ordinary user who can call `withdraw` on the Citrea contract and control outpoint bytes) can trigger it deterministically and cheaply (normal bridge fees only), and it is repeatable per operator/per set of deposits sharing an operator.

### Recommendation
Add `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` to the `withdrawals` table, and make `update_withdrawal_utxo_from_citrea_withdrawal` reject (or fail loudly / flag as anomalous) an update that would create a duplicate outpoint across two different `idx`s, rather than silently persisting collisions returned by Citrea. Also harden `get_payout_txs_for_withdrawal_utxos` to only mark handled the single `idx` that can be proven, via the on-chain storage proof for its specific deposit index, to be the true owner of the spent outpoint, refusing to auto-handle any additional colliding `idx`.

db.upsert_move_to_vault_txid_from_citrea_deposit(None, 6, &move_txid_b).await?;
db.update_withdrawal_utxo_from_citrea_withdrawal(None, 5, shared_outpoint, height).await?;
db.update_withdrawal_utxo_from_citrea_withdrawal(None, 6, shared_outpoint, height).await?; // succeeds today, should fail after fix

// 2. Record one Bitcoin spend of shared_outpoint (insert into bitcoin_syncer_spent_utxos
//    with the single payout_txid, in a mined+finalized block_id).

let matches = db.get_payout_txs_for_withdrawal_utxos(None, block_id).await?;

// Pre-fix: matches.len() == 2 -> demonstrates the vulnerability.

// 4. Binding check B: run PayoutCheckerTask::run_once repeatedly and assert
//    at most one of {5, 6} ever becomes is_payout_handled = TRUE / gets a kickoff_txid.
let mut handled = vec![];

    if !task.run_once().await? { break; }
    if db.get_handled_payout_kickoff_txid(None, payout_txid).await?.is_some() { handled.push(...); }
