### Title
Unbounded fee rate derived from attacker-influenced block data causes payment drops and processor panic - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
`median_fee` computes the fee rate for `SignableTransaction` construction from the per-transaction fee rates of the previous block's `txdata`, taking the median with no upper-bound check. This value is passed unchecked into `SignableTransaction::new` as `fee_per_vbyte`, where `needed_fee = fee_per_vbyte * vbytes` can overflow, be rejected via `NotEnoughFunds` (dropping user payments), or burn an arbitrarily large amount as miner fee. The external report's bug class — an unconstrained fee/percentage parameter — maps directly onto this path, except here the unbounded value is supplied by untrusted on-chain data rather than a privileged owner.

### Finding Description
- `median_fee` iterates `block.txdata[1 ..]`, computes `(in_value - out) / vsize` per transaction, sorts, and returns `fees[len / 2]` with only a `max(1)` floor — no ceiling [1](#0-0) 
- The result is forwarded as `fee.0` into `BSignableTransaction::new` [2](#0-1) 
- `SignableTransaction::new` multiplies `fee_per_vbyte * vbytes` with no bounds check; a huge `fee_per_vbyte` either overflows or yields a `needed_fee` exceeding `input_sat`, returning `TransactionError::NotEnoughFunds` [3](#0-2) 
- The only validated direction is *too low* (`TooLowFee`); there is no `TooHighFee` / max-fee-rate guard anywhere in `SignableTransaction::new` [4](#0-3) 
- When `needed_fee`/`signable_transaction` returns `None`, `prepare_send` treats the plan as unfulfillable and drops the plan's branches — i.e., user payments are silently cancelled and re-accounted as operating costs [5](#0-4) 
- If `needed_fee` succeeds (fee estimated against a cheaper `calculating_fee` plan with dust-valued payments) but `signable_transaction` then returns `None` for the real amounts, `prepare_send` hits a hard `panic!`, killing the processor task [6](#0-5) 

### Impact Explanation
An actor able to populate roughly half of a Bitcoin block's non-coinbase transactions with extreme-fee transactions (a miner, or a well-funded fee-bumping attacker during low-activity blocks) forces `median_fee` to return an arbitrarily large rate. Consequences: (a) all pending Bitcoin plans are declared unfulfillable and their branch payments dropped — funds are never paid and users' expected outputs vanish; (b) when the median lands between the fee-estimation path and the real spend path, `prepare_send` panics, DoS-ing the signing pipeline; (c) in release builds the `fee_per_vbyte * vbytes` multiplication can wrap, producing an inconsistent fee where the change output absorbs a wrong amount. This matches the report's impact pattern (unconstrained fee parameter → DoS / wrong economics), but is reachable from public chain data, not just an owner.

### Likelihood Explanation
Low-to-medium. With `block.txdata.len() > 1` required and the median at index `len / 2`, the attacker must control ~half the transactions in the sampled block. During blocks with few transactions this is cheap; in congested blocks it requires miner cooperation or significant fee spend. The attack is economically self-justifying for a miner, since the inflated fee is paid to miners.

### Recommendation
- Clamp `median_fee` output to a documented maximum (e.g., a multiple of `DEFAULT_MIN_RELAY_TX_FEE` or a configurable cap), mirroring the existing `max(1)` floor.
- Add a `TooHighFee` bound check in `SignableTransaction::new` on `fee_per_vbyte`, and use `checked_mul` for `fee_per_vbyte * vbytes`.
- Treat `signable_transaction` returning `None` after successful fee estimation as a retryable condition instead of `panic!`.

### Proof of Concept
1. Attacker (or mining pool) crafts a block where ≥ half of `txdata[1..]` are transactions paying, e.g., 10^9 sat/vbyte in fees.
2. Processor calls `make_signable_transaction` → `median_fee` returns `Fee(10^9)` [2](#0-1) 
3. `SignableTransaction::new` computes `needed_fee = 10^9 * vbytes` → `NotEnoughFunds` → `signable_transaction` returns `Ok(None)` → plan's branches dropped via `drop_branches`, payments cancelled [5](#0-4) 
4. Alternatively, a fee rate near `u64::MAX / vbytes` makes the multiplication overflow/panic inside `SignableTransaction::new` [7](#0-6)

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
  }
