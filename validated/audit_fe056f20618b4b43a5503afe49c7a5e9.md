### Title
Missing bounds check in `is_atom_canonical`/`is_clvm_canonical` CLVM length-prefix parsing can crash spend-bundle processing - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the variable-length atom-length prefix of a CLVM-serialized solution byte buffer that originates from an attacker-submitted spend bundle. Like the reported CRAT parser bug — which trusted an advertised subtype length without checking it against the remaining image size before dereferencing — these functions trust the decoded `atom_len`/`prefix_len` value and advance `offset` into `clvm_buffer` without ever validating that the computed offset stays within `len(clvm_buffer)`.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads `b = clvm_buffer[offset]` and, depending on the top bits of `b`, decides a `prefix_len` (0–5 extra bytes) and a `mask`. It then loops `prefix_len` times, each time doing `offset += 1; atom_len |= clvm_buffer[offset]` with no check that `offset < len(clvm_buffer)`: [1](#0-0) 

The caller, `is_clvm_canonical()`, walks the whole buffer using this atom length to jump `offset += atom_len` between tokens, again without verifying that the returned atom length or the accumulated offset does not run past the end of `clvm_buffer`: [2](#0-1) 

If a submitted spend bundle's solution encodes a truncated or oversized atom-length prefix (e.g., a 5-byte prefix near the end of the buffer, or a length field that makes `atom_len` exceed the remaining bytes), both functions index past the end of `clvm_buffer`. In Python this raises an unhandled `IndexError` rather than causing memory corruption (Python bytes objects are bounds-checked at the interpreter level), but the code path itself has no defensive length validation before dereferencing attacker-controlled offsets — structurally the same missing-bounds-check pattern as the CRAT `sub_type_hdr + length` validation gap described in the report.

Per `.cursor/context/clvm-execution.md`, `is_clvm_canonical()` is invoked from mempool spend-bundle processing to determine DEDUP eligibility of a spend's solution bytes, meaning it runs on data taken directly from an untrusted, externally submitted spend bundle before/around cost-metered CLVM execution.

### Impact Explanation
An unhandled `IndexError` raised while processing a spend bundle in the full node's mempool/validation pipeline can propagate out of the canonicality check. Depending on whether the call site wraps this logic in a broad exception handler, this could abort processing of that spend bundle (best case) or, if uncaught in the relevant async task/thread-pool worker, disrupt mempool processing for other pending work — a spend-triggered transaction-processing disruption, which matches the accepted "spend-triggered transaction-processing halt" impact category. This is a DoS-class issue reachable by any unprivileged spend-bundle submitter, not a memory-corruption issue as in the original C/kernel bug, since Python has built-in bounds checking on `bytes` indexing.

### Likelihood Explanation
Any wallet user or RPC caller can submit a crafted spend bundle whose solution program contains a malformed CLVM atom-length prefix. Reaching `is_clvm_canonical()` only requires the mempool to consider the spend for DEDUP eligibility, which is part of normal spend-bundle intake, making the trigger straightforward. However, I could not fully confirm the exact call site and its exception-handling behavior (the file matches for `is_clvm_canonical` were only found within `mempool_manager.py` and `clvm-execution.md` context notes) — full node code may already catch broad exceptions around per-spend validation, which would lower the practical impact.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before reading `clvm_buffer[offset]` in the prefix loop, and in `is_clvm_canonical()` before advancing `offset` by `atom_len`, raising a controlled `ValueError`/returning non-canonical instead of relying on Python's `IndexError` to fail closed. Ensure the mempool call site catches and converts any parsing exception into a rejection of that specific spend bundle without affecting other in-flight mempool operations.

### Proof of Concept
Construct a spend bundle whose solution CLVM serialization ends with a byte matching the 5+8+8+8+8+8-bit length-prefix pattern (`0b111111xx`) placed near the very end of the buffer such that the subsequent `prefix_len` index reads (`clvm_buffer[offset]`) run past `len(clvm_buffer)`, e.g. a single trailing byte `0xFC` with fewer than 5 following bytes. Submitting this spend bundle to a full node's mempool causes `is_clvm_canonical()` → `is_atom_canonical()` to raise `IndexError` when evaluating DEDUP eligibility for that solution.
