Based on my investigation, the confirmed `copilot-conflict-context.ts` code path is **guarded**: it caps whole-file reads at `MAX_CONFLICT_FILE_READ_SIZE` (10MB) via a `stat()` check before `readFile()`, and further caps actual conflict content sent to the model via `MAX_CONFLICT_CONTENT_SIZE` (256KB) and `MAX_CONFLICT_LINE_LENGTH` [1](#0-0) , [2](#0-1) . This rules out a return-bomb analog in that flow.

However, `getResolutionDiff` in `app/src/lib/git/diff.ts` — used by the Copilot conflict-resolution "Changes" tab (`copilot-conflicts-changes.tsx`) — reads the on-disk working-tree file with `readFile(path, 'utf8')` with **no size check at all** before loading it fully into a V8 string, unlike every other diff path in the same file (`getCommitDiff`, `buildDiff`, `getFilesDiffText`) which all apply `isValidBuffer`/`isBufferTooLarge`/explicit byte caps before or immediately after reading git output [3](#0-2) , contrasted with the guarded pattern at [4](#0-3)  and the explicit 10MB cap in `getFilesDiffText` [5](#0-4) .

This is invoked automatically (no unnatural user step beyond opening a merge/rebase/cherry-pick with conflicts and viewing the standard "Changes" preview tab) whenever a file is selected in the conflict list: `loadDiffForFile` calls `getResolutionDiff(repository, file.path, ...)` for every conflicted file, including on initial mount [6](#0-5) , [7](#0-6) .

### Title
Unbounded working-tree file read in `getResolutionDiff` allows memory-exhaustion DoS via a maliciously large conflicted file - (File: `app/src/lib/git/diff.ts`)

### Summary
`getResolutionDiff` reads the entire on-disk content of a conflicted working-directory file with `readFile(path, 'utf8')` and no size limit, then also unconditionally writes it to a temp file and shells out to `git diff --no-index` on it. Unlike sibling functions in the same module, there is no pre-read `stat()` size gate and no post-read truncation before the content is held as a JS string in memory.

### Finding Description
`getResolutionDiff` is called for every file in a merge/rebase/cherry-pick conflict as soon as the user opens the "Changes" tab of the conflicts dialog (including automatically on `componentDidMount`) [6](#0-5) . Its implementation:

```
const baseContent = await readFile(
  Path.join(repository.path, filePath),
  'utf8'
)
``` [3](#0-2) 

reads the working-tree file (`baseContent`) fully into a string with no size check whatsoever — no `stat()`, no `MAX_CONFLICT_FILE_READ_SIZE`-style guard, and no `isValidBuffer`/`isBufferTooLarge` check that every other diff-producing function in this file applies to git-produced buffers (`buildDiff` at [4](#0-3) , `getFilesDiffText`'s explicit 10MB cap at [5](#0-4) , or `getResolutionDiff`'s own `isValidBuffer(stdout)` check that is applied only to the *git diff output*, not to the input file it read [8](#0-7) ).

This file is attacker-controlled: it is a file the user cloned/pulled/fetched that ends up conflicted during a merge/rebase/cherry-pick (e.g., an attacker-crafted branch or PR merges a multi-hundred-MB or multi-GB blob into a path that also collides with the local branch). The victim doesn't need to do anything unusual — opening the standard conflicts dialog and viewing a file (which happens by default) triggers the read. Because `baseContent` is decoded as UTF-8 into a single JS string and then also written whole to a temp file via `writeFile(tempBase, baseContent, 'utf8')` [9](#0-8)  and diffed via `git diff --no-index` (unbounded `maxBuffer` per the default options in `core.ts` when using string encoding — `kStringMaxLength`) [10](#0-9) , a single large file can drive multi-hundred-MB to gigabyte-scale memory allocations and CPU work in the renderer/main process, repeated for each file selection.

This is the direct Desktop analog of the OmniPortal "return bomb": an attacker-supplied object (here, a committed blob in a fetched/merged branch) causes the victim's process to unconditionally load an unbounded amount of attacker-controlled data into memory before any size check is applied, defeating the very guard pattern (`isValidBuffer`) that the codebase already uses elsewhere to prevent exactly this class of issue.

### Impact Explanation
A crafted repository/branch can cause GitHub Desktop to load an attacker-sized file (potentially hundreds of MB to GBs, limited only by disk/OS) fully into V8 string memory and then duplicate it again into a temp file, on simply viewing a merge conflict. This can freeze the renderer, exhaust memory, and crash the app (denial of service), and depending on file size can hit the ~256MB V8 string limit and throw uncaught exceptions in a code path other diff paths explicitly guard against (`MaxDiffBufferSize` at [11](#0-10) ). It is a DoS on the local app rather than remote code execution, but it is triggered purely by attacker-controlled repository content and requires no unusual user action beyond normal conflict resolution.

### Likelihood Explanation
High reachability: any conflicted file during merge/rebase/cherry-pick auto-loads through this path when the conflicts dialog's Changes tab is shown, which is the default/first view. No privilege or local access is needed — only that the victim merges/rebases against a branch or PR containing the oversized blob, a normal workflow action.

### Recommendation
Add a `stat()`-based size check (mirroring `MAX_CONFLICT_FILE_READ_SIZE` in `copilot-conflict-context.ts` or `isValidBuffer`/`isBufferTooLarge` already used elsewhere in `diff.ts`) before calling `readFile` on the working-tree file in `getResolutionDiff`, returning `DiffType.Unrenderable` or `LargeText` for oversized files instead of reading them unconditionally.

### Proof of Concept
1. Attacker creates a branch/PR that adds a several-hundred-MB (or GB) file at a path that also has divergent content on the victim's current branch, so merging produces a conflict at that path.
2. Victim fetches and starts a merge/rebase/cherry-pick against that branch, hits the conflict, and opens the standard "Changes" tab of the conflicts dialog (default view, `componentDidMount` triggers `loadDiffForFile` automatically).
3. `getResolutionDiff` executes `readFile(Path.join(repository.path, filePath), 'utf8')` on the full conflicted file with no size gate, loading the entire attacker-sized content into memory, then duplicates it to a temp file and diffs it — causing high memory/CPU usage and potential crash, scaling with attacker-chosen file size.

    const requestId = ++this.diffRequestId
    const choice = getResolutionChoiceForFile(
      file.path,
      this.props.manualResolutions
    )

    if (choice === 'ours' || choice === 'theirs') {
      this.setState({
        diff: null,
        fileContents: null,
        noResolution: false,
        diffError: false,
      })
      try {
        const result = await getResolutionDiff(
          this.props.repository,
          file.path,
          { stage: choice },
          this.state.hideWhitespaceInDiff

          this.setState({
            diff: result.diff,
            fileContents: this.buildFileContents(file, result),

          this.setState({ diff: null, fileContents: null, diffError: true })

    }
