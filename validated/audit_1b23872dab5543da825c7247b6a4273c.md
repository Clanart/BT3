### Title
Stash-creation success heuristic can be spoofed by attacker-controlled repository state, causing Desktop to silently believe uncommitted changes were saved when they were not - (File: app/src/lib/git/stash.ts)

### Summary
`createDesktopStashEntry` in `app/src/lib/git/stash.ts` does not check the actual outcome of `git stash push` through a reliable, unambiguous signal. Instead, when the command exits with code `1`, it infers success/failure by string-matching stderr for a line starting with `error: `, and if no such line is found it *assumes* a stash was created and returns `true`. [1](#0-0) 

### Finding Description
`createDesktopStashEntry` calls `git(['stash', 'push', '-m', message], ...)`. Instead of relying on `successExitCodes`, it catches `GitError`s and applies a heuristic:

```
if (e instanceof GitError && e.result.exitCode === 1) {
  const errorPrefixRe = /^error: /m
  const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
  if (matches !== null && matches.length > 0) {
    return Promise.reject(e)          // treated as real failure
  }
  // if no error messages were emitted by Git, we should log but continue because
  // a valid stash was created
  return e.result                     // treated as SUCCESS
}
``` [2](#0-1) 

This is structurally the same bug class as the reported ERC20 issue: a boolean-like success signal (git's exit code / stderr shape) is not authoritatively checked before the caller proceeds to trust it. The function's own code comment documents that this assumption is known to be wrong for at least one case — an "unborn" repository (`HEAD` has no commits yet):

```
% git stash push -m foo ; echo $?
You do not have the initial commit yet
1
```
No stash is created in that case, but there is no `error: `-prefixed line, so the exit-code-1 branch falls through and `createDesktopStashEntry` returns `e.result` — indistinguishable from success — and the outer function returns `true` ("a stash was created"). [3](#0-2) 

The precondition (exit 1, no `error:` line in stderr) is not something Desktop fully controls — it is a function of the exact wording Git emits, which depends on repository state (e.g., unborn HEAD, certain merge/rebase states, hooks, locale) that can be shaped by cloning/checking out an attacker-crafted repository or ref layout. Desktop's own code acknowledges this heuristic is fragile and was added specifically to work around unreliable exit codes/wording from `git stash push` (see the surrounding 2024 audit comment).

### Impact Explanation
Callers of `createDesktopStashEntry` (in `app-store.ts`) use the boolean return value to decide whether it is safe to proceed with an operation that discards or overwrites the working directory (e.g., switching branches, applying an update, or another flow that assumes "your uncommitted changes are safely stashed"). If the function reports `true` while no stash was actually created, Desktop can proceed to perform a destructive checkout/reset believing the user's uncommitted work is preserved in a stash, when it is not — resulting in silent loss of uncommitted local changes. This matches the "silent corruption of what the user commits" impact category: the corruption here is data loss disguised as a successful safety net, not a crash, so the user may not notice until they later go to `git stash pop` and find nothing there.

### Likelihood Explanation
The likelihood depends on how easily the "exit 1, no `error:` stderr line" state can be induced. The maintainers themselves flagged the unborn-repository scenario as a known instance and left it unresolved ("Here be dragons... I'm not going to mess with this now"). Because Git's exact stderr wording for various failure states is not a stable, versioned API, other Git versions/locales/edge cases can plausibly produce exit code 1 without an `error: `-prefixed line for reasons other than the intended "stash succeeded with conflicts" case. This is a heuristic gap acknowledged in the code, not a hardened, exhaustively-tested invariant, making it a realistic (if narrow) trigger surface, especially in less common repository states that a user can reach by opening/cloning a specially prepared repository.

### Recommendation
Do not infer stash success from the absence of a particular stderr substring. Instead:
- Verify success positively, e.g., by checking `git rev-parse -q --verify refs/stash` (or comparing `refs/stash` before/after) to confirm a new stash object was actually created, rather than pattern-matching stderr text.
- Treat any non-zero exit code as a failure unless positively confirmed otherwise, mirroring the intent of `successExitCodes`/`expectedErrors` used elsewhere in `app/src/lib/git/core.ts`.
- Add an explicit unborn-HEAD precheck before attempting the stash, since the code already knows this is a legitimate distinguishable case.

### Proof of Concept
1. Create/checkout a repository whose `HEAD` is unborn (no commits yet) but which has files staged/modified in the working directory (reachable by opening a specially prepared repository/branch in Desktop, e.g. via clone of a crafted ref state).
2. Trigger a Desktop flow that calls `createDesktopStashEntry` (e.g., a branch switch that stashes uncommitted changes).
3. `git stash push -m ...` exits with code `1` and stderr `"You do not have the initial commit yet\n"` — no `error: `-prefixed line.
4. `createDesktopStashEntry` falls into the "no error messages... continue" branch and returns `true`/`e.result`, signaling success even though `git stash list` shows no new stash was created.
5. If the caller subsequently performs a destructive operation predicated on "changes are stashed," the user's working-directory changes are silently lost.

Note: I could not fully trace every downstream caller path in `app-store.ts` within the available time to confirm which specific destructive operation is gated by this boolean in the current codebase; a Devin session with full file access would be needed to enumerate all call sites of `createDesktopStashEntry`/`_createStashEntry` and confirm the exact destructive action performed afterward.
