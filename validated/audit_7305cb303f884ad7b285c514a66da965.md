### Title
Hookify PreToolUse/PostToolUse rule engine keys enforcement on tool_name-to-event inference and untyped field-name lookup instead of the actual tool performing the action, allowing safety rules to be silently bypassed via tools not in the hardcoded mapping (File: `plugins/hookify/hooks/pretooluse.py`, `plugins/hookify/hooks/posttooluse.py`, `plugins/hookify/core/config_loader.py`, `plugins/hookify/core/rule_engine.py`)

### Summary
The hookify plugin implements user-defined `PreToolUse`/`PostToolUse` guard rules (e.g. "block `rm -rf`", "block writes containing secrets") that are supposed to gate dangerous tool actions. The gate that decides which rules are even loaded/considered is a hardcoded `tool_name -> event` mapping [1](#0-0) , and the gate that decides whether a loaded rule actually matches is a bare key lookup on `tool_input` that ignores which tool produced it [2](#0-1) . Like the `IchiVaultSpell` bug, where `_validateMaxLTV(strategyId)` checked an LTV limit against a caller-supplied `strategyId` instead of the id that actually matches the position, hookify's field-based condition check verifies a pattern against whatever field name happens to exist in `tool_input`, instead of validating that the field belongs to the tool the rule was written for. This decouples the "id" that the rule's author intended to be checked (a specific tool's parameter) from the actual identifier of the tool/action being executed, letting a functionally equivalent but differently-shaped tool call slip past the check entirely.

### Finding Description
`pretooluse.py` and `posttooluse.py` derive the effective `event` used to filter which rules are even loaded, from a hardcoded, incomplete tool list:

```python
tool_name = input_data.get('tool_name', '')
event = None
if tool_name == 'Bash':
    event = 'bash'
elif tool_name in ['Edit', 'Write', 'MultiEdit']:
    event = 'file'
``` [1](#0-0) 

Notably, `NotebookEdit` — a built-in tool that writes arbitrary cell source content to a real file on disk — is not in this list, so any call to it yields `event = None`.

`load_rules(event=None)` then disables event filtering entirely rather than failing closed:

```python
if event:
    if rule.event != 'all' and rule.event != event:
        continue
``` [3](#0-2) 

So when `event` is `None`, every enabled rule file is loaded regardless of the rule's declared `event`.

Whether a loaded rule actually "matches" the current tool call is then decided by `_rule_matches`, which only checks tool identity if the rule author explicitly set `tool_matcher` (rare for the documented "simple pattern" style rules, which only set `event`) [4](#0-3) . If `tool_matcher` is unset, tool identity is never validated — the rule proceeds straight to `_check_condition`.

`_check_condition` -> `_extract_field` resolves the field to inspect purely by key presence in `tool_input`, before any tool-specific logic:

```python
if field in tool_input:
    value = tool_input[field]
    ...
    return str(value)
``` [2](#0-1) 

Only after that generic branch does the code fall back to tool-specific field name mapping for `Bash` (`command`), `Write`/`Edit` (`content`/`new_string`), and `MultiEdit` (`edits[].new_string`) [5](#0-4) . `NotebookEdit`'s real parameters (`notebook_path`, `new_source`, `cell_type`, etc.) are never mapped in `_extract_field` at all.

The security-relevant consequence: a documented "file" rule such as `event: file, pattern: "AWS_SECRET|BEGIN PRIVATE KEY"` (intended to block secret-containing writes via `Write`/`Edit`) is written against the field name `content`/`new_string`. When Claude instead uses `NotebookEdit` to write the same forbidden content into a notebook cell's `new_source`:
1. `event` computed by the hook script is `None` (NotebookEdit isn't mapped) — but this doesn't block the rule, it just removes filtering, so the rule is still loaded.
2. `tool_matcher` is unset, so `_rule_matches` never checks that `tool_name == 'NotebookEdit'` is even a tool the rule cares about.
3. `_extract_field('content', 'NotebookEdit', tool_input, ...)` — `'content'` is not a key in `NotebookEdit`'s `tool_input` (which uses `new_source`) and there is no `NotebookEdit` branch, so `_extract_field` returns `None`.
4. `_check_condition` treats `None` as "condition fails" (no match), so the rule silently does not fire, and the operation is allowed with no warning or block.

The rule's author validated a policy against the identifier/field they assumed (`content`, tied conceptually to `Write`/`Edit`), but the actual tool performing the equivalent dangerous write (`NotebookEdit`) uses a different identifier/field, exactly mirroring how `_validateMaxLTV(strategyId)` validated against a `strategyId`/vault pairing that did not correspond to the actual collateral/strategy backing the position.

### Impact Explanation
This is a hook-bypass in the "unprivileged user / hook bypass" trust boundary explicitly called out as in-scope. hookify is documented and marketed as a safety mechanism ("block dangerous rm -rf", "block writes to .env/secrets", "deny path traversal") that a user or org relies on as their last line of defense against a Claude session (potentially influenced by prompt injection from untrusted web content, files, or a compromised MCP server) performing a destructive or data-exfiltrating action. Because rule enforcement is keyed on field-name presence and an incomplete/loose tool→event mapping rather than binding to the specific tool the policy was written for, an attacker who can influence Claude's tool choice (e.g., via prompt injection, or by getting Claude to use `NotebookEdit`, an unmapped MCP tool with a differently-named parameter, or any tool outside `{Bash, Edit, Write, MultiEdit}`) can achieve the functionally equivalent dangerous action while completely evading the user's configured hookify guard rule — with no warning, no block, and no record that the safety policy was checked and failed. This directly matches the "hook bypass" category the analysis rules call for, and yields unauthorized/unaudited file-system writes (or, for `Bash`-only rules and future/custom tools with a differently-named command parameter, unauthorized command execution) despite an active, user-authored safety control.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: hookify rule authors write rules using the documented simple `pattern`/`event` style shown in the plugin's own examples and skill docs (which do not require setting `tool_matcher`) [6](#0-5) . The mismatch is triggered merely by Claude invoking any tool outside the hardcoded four-tool mapping (e.g., `NotebookEdit`, or any MCP tool) to perform a semantically identical write/command action — no special privileges are required, and this is squarely within reach of a prompt-injection scenario where untrusted content steers which tool Claude selects to carry out the same operation the rule was meant to stop.

### Recommendation
- Fail closed instead of open when `tool_name` is not in the recognized set: either treat unmapped tools as `event = 'all'` so no rule is silently exempted from consideration, or explicitly extend the mapping to cover every built-in tool capable of writing files or executing code (`NotebookEdit`, `Task`, MCP tools, etc.).
- Require every rule to bind to an explicit `tool_matcher` (derived automatically from `event` if not set) rather than allowing `_rule_matches` to skip tool identity checks entirely when `tool_matcher` is empty.
- In `_extract_field`, validate that the field name is one the given `tool_name` is actually known to expose (mirroring the recommended `strategies[strategyId].vault == unwrappedCollToken` fix) rather than doing an untyped `field in tool_input` lookup across all tools; add explicit field mappings for `NotebookEdit` and any other built-in/MCP tool categories the plugin intends to guard.
- Document (and enforce at load time) that a rule's `event`/pattern is only meaningful for the specific tool(s) whose field names it references, and warn/reject rule files that reference a field not associated with any tool in their declared `event`.

### Proof of Concept
1. User installs the hookify plugin and adds `.claude/hookify.no-secrets.local.md`:
   ```
   ---
   name: no-secrets
   enabled: true
   event: file
   action: block
   pattern: "BEGIN PRIVATE KEY"
   ---
   Blocked: writing private key material to a file.
   ```
   This compiles (via `Rule.from_dict`) to `conditions=[Condition(field='content', operator='regex_match', pattern='BEGIN PRIVATE KEY')]` [6](#0-5) .
2. Verify the rule works as intended: Claude calls `Write` with `content` containing `"-----BEGIN PRIVATE KEY-----"`. `pretooluse.py` sets `event='file'` [7](#0-6) , `load_rules('file')` loads the rule, `_extract_field('content', 'Write', tool_input)` finds `content` directly [2](#0-1) , the regex matches, and the write is blocked.
3. Now have Claude (e.g., steered by an injected instruction in a fetched document) instead call `NotebookEdit` with `tool_input = {"notebook_path": "...", "cell_id": "...", "new_source": "-----BEGIN PRIVATE KEY-----\n..."}` to write the same secret content into a notebook cell (a real file on disk).
4. `pretooluse.py` computes `event = None` (NotebookEdit isn't in the mapping) [1](#0-0) ; `load_rules(None)` loads the `no-secrets` rule anyway (no filtering) [3](#0-2) ; `_rule_matches` skips the tool check because `tool_matcher` is unset [8](#0-7) ; `_extract_field('content', 'NotebookEdit', tool_input)` finds no `'content'` key and has no `NotebookEdit`-specific branch, returning `None` [9](#0-8) ; `_check_condition` treats this as non-matching, so `evaluate_rules` returns `{}` (allow) despite the file now containing the exact pattern the rule was written to block.

This is an analysis based on static reading of the plugin source in this repository; I was not able to execute the hooks end-to-end (no terminal access), so the exact JSON shape Claude Code sends for `NotebookEdit`'s `tool_input` should be confirmed against the current tool schema before relying on this as a final verified exploit trace.
