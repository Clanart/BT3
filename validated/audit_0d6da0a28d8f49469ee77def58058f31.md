### Title
Permissionless FIFO Eviction Destroys Victim's Prepaid Bandwidth Allowance - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` stores each `(app_chain, app)` bandwidth balance as a bounded FIFO list capped at `MAX_SUBSCRIPTIONS = 1024` [3](#0-2) . `push_subscription`, invoked from the permissionless `on_accept` purchase handler, unconditionally evicts and discards the oldest (index-0) subscription once the list is full [4](#0-3) . Because `purchase()`/the ISMP purchase message lets any caller target an arbitrary `app` on an arbitrary `chain` [1](#0-0) , an attacker with no privileged role (no admin, relayer, prover, or victim-key access) can flood a victim's `(chain, app)` bucket with 1024 cheap purchases to forcibly evict the victim's legitimate, unconsumed, already-paid-for subscription. This is the same broken-invariant class as the external report's unbounded `registeredCustodians` loop — an attacker-controlled, unbounded registration list whose growth degrades protocol correctness — but here the local analog produces a concrete fund-loss outcome rather than a mere gas DoS.

### Finding Description
- `Allowance` is a `StorageDoubleMap<StateMachine, AppKey, SubscriptionList>` where `SubscriptionList = BoundedVec<Subscription, ConstU32<1024>>` [5](#0-4) .
- Every `purchase()` from any registered source-chain `BandwidthManager` calls `Pallet::on_accept`, which decodes the message and calls `push_subscription(&msg.chain, &key, tier, bytes, duration)` — `msg.chain` and `msg.app` are attacker-supplied wire fields, not tied to `request.source`/`request.from` beyond the manager-address check [6](#0-5) .
- `push_subscription` checks `if list.len() == MAX_SUBSCRIPTIONS { Some(list.remove(0)) }` and unconditionally appends the new entry, discarding the victim's oldest (often least-consumed) subscription with an emitted `SubscriptionEvicted { lost_bytes }` event as the only trace [7](#0-6) .
- Nothing binds the eviction candidate to the purchaser: any address on any registered source chain can push new entries into someone else's `(app_chain, app)` bucket purely by naming that `app` in the purchase payload, since the manager-authorization check only validates that the *dispatching contract* is the registered `BandwidthManager` for its chain, not that the purchaser is authorized for the target `app` [8](#0-7) .
- The documentation itself acknowledges the eviction is a fund-loss event ("`lost_bytes` is what the user paid for and won't get to use") [9](#0-8) , but the assumption that this "only happens under pathological repeat-buy behavior" from the same buyer does not hold — any third party can trigger it against a victim's bucket.

### Impact Explanation
This causes irrecoverable loss of prepaid, unconsumed bandwidth allowance belonging to a legitimate app/buyer, purely from an unprivileged third party's transactions — no malicious relayer, prover, or admin is required. It maps directly to the bounty's "bandwidth balances must move exactly once and only to the rightful beneficiary" invariant: value paid by the victim is destroyed and never delivered to (or usable by) the rightful beneficiary. This is a logic attack enabling loss of funds for arbitrary bandwidth customers.

### Likelihood Explanation
Exploitation requires only calling `purchase()` 1024 times (any tier/`months=1`, minimal cost per call) targeting the victim's exact `(chain, app)` key, which is public knowledge (visible on-chain from the victim's own prior purchases/events). No governance, relayer collusion, or leaked keys are needed — a single unprivileged EOA with enough of the cheapest tier's price can execute the full eviction sequence. The cost is bounded and predictable (`1024 × cheapest tier price`), making it a feasible griefing/fund-destruction vector against any specific high-value target, especially since higher tiers cost proportionally more but the eviction cost is fixed at the cheapest tier.

### Recommendation
- Restrict `push_subscription`'s eviction so it can only evict entries whose `expires_at` has already passed, or otherwise refuse to evict live/unconsumed subscriptions — reject a purchase (or require an explicit force-credit governance path) instead of destroying paid-for allowance.
- Alternatively, bind purchase authorization to the app itself (e.g., require a proof the caller controls the target `app` address) rather than allowing an open `msg.app`/`msg.chain` write from any caller.
- At minimum, increase `MAX_SUBSCRIPTIONS` cap enforcement to fail the purchase (return an error / bounce the ISMP message) rather than silently evicting live, unexpired subscriptions, preserving the "funds move exactly once, to the rightful beneficiary" invariant.

### Proof of Concept
1. Victim purchases bandwidth for `app = "VictimApp"` on `chain = "EVM-8453"`, receiving a `Subscription` with real, unconsumed `remaining_bytes` inserted into `Allowance::(EVM-8453, VictimApp)`.
2. Attacker (unprivileged, unrelated address) repeatedly calls `BandwidthManager.purchase()` on any registered source chain, setting the purchase payload's `app = "VictimApp"` and `chain = "EVM-8453"` (both attacker-controlled wire fields, see `PurchaseMessage`/`BandwidthPurchaseMsg` [1](#0-0) ), each time buying the cheapest tier for `months = 1`.
3. Each purchase dispatches an ISMP POST that reaches `pallet-bandwidth::on_accept`, which calls `push_subscription(&"EVM-8453", &"VictimApp", ...)` [10](#0-9) .
4. After 1024 attacker purchases append entries to the FIFO list, the 1025th purchase (or fewer, if the victim's list already had entries) causes `list.remove(0)` to evict and permanently discard the victim's original (or any earlier) subscription, emitting `SubscriptionEvicted { lost_bytes }` [11](#0-10) .
5. The victim's paid, unconsumed `remaining_bytes` are permanently lost; the attacker never needed the victim's key, admin rights, or relayer/prover collusion.

Note: I could not fully verify from the index whether `BandwidthManager.sol`'s `purchase()` enforces any additional per-caller/per-app restriction beyond what is visible in the pallet-side ABI decoder (the Solidity source body of `purchase()` was not retrievable within the index size limits). If such a restriction exists client-side, it would need to be confirmed by reading `evm/src/apps/BandwidthManager.sol` directly — I'd recommend starting a Devin session with full repo access to confirm this before treating the PoC as fully validated end-to-end on the EVM side.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;

				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
