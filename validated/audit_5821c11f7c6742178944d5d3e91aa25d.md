### Title
Forged aggregate Schnorr signatures via attacker-controlled nonces excluded from aggregation weights - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives its aggregation weights only from the ordered challenge list, not from the public keys or attacker-supplied `Rs`. Because `SchnorrAggregate::read` accepts arbitrary canonical `Rs`, an unprivileged party can serialize an aggregate signature whose final nonce algebraically cancels the weighted public-key terms. The verifier then accepts an aggregate signature without any valid constituent signature. [1](#0-0) [2](#0-1) 

### Finding Description
`SchnorrAggregate::verify` initializes the weight transcript, domain-separates it, and appends only `challenge` values. For each `(key, challenge)`, it calculates `z = weight(&mut digest)` and queues `(z, R)` and `(z * challenge, key)`, finally requiring:

```text
Σ zᵢ·Rᵢ + Σ zᵢ·cᵢ·Aᵢ - s·G = identity
```

`R`, `A`, and the message are not included when deriving `z`. The serialized verifier input is therefore not bound to the values that determine the verification equation. [3](#0-2) 

For an ordered verifier input `(A₁,c₁),...,(Aₙ,cₙ)`, the attacker can calculate every `zᵢ` before choosing `Rs`, set `s = 0` and `R₁..Rₙ₋₁ = identity`, then choose:

```text
Rₙ = -zₙ⁻¹ · Σᵢ zᵢ·cᵢ·Aᵢ
```

All encodings are canonical, so `SchnorrAggregate::read` accepts the forged object, and the final multiexponentiation is identity even though no signer produced a valid Schnorr signature. [1](#0-0) [4](#0-3) 

### Impact Explanation
Any authorization path that treats `SchnorrAggregate::verify` as proof that the listed keys signed their corresponding messages can be bypassed with public verifier inputs. The attacker does not need private keys, valid constituent signatures, nonce discrete logarithms, malformed encodings, or control of server-side state; they only need to submit a crafted `SchnorrAggregate` byte stream. This produces a forged signature accepted by the verifier. [1](#0-0) [2](#0-1) 

### Likelihood Explanation
The attack is deterministic for each ordered key/challenge list except for the negligible case where the final aggregation weight is zero. Since the digest advances identically for prover and verifier and contains only the public challenge sequence, the attacker knows all weights before selecting the serialized `Rs`. [5](#0-4) 

### Recommendation
Bind the entire aggregate statement into every weight, including the aggregate length, ordered public keys, ordered nonces `Rᵢ`, challenges, and any protocol-specific message/context. Producers and verifiers must derive weights from identical fully framed transcripts before evaluating the multiexponentiation. Alternatively, retain per-signature verification or use an aggregation construction whose coefficient derivation already commits to the complete signature statement. Reject empty aggregates, identity/non-canonical points where prohibited, and trailing bytes at the protocol layer.

### Proof of Concept
For any nonempty verifier input `[(Aᵢ,cᵢ)]`:

```text
zᵢ = Weight(dst, c₁, ..., cᵢ)                    // independent of Rᵢ and Aᵢ
s  = 0
Rᵢ = identity                                    // for i < n
Rₙ = -zₙ⁻¹ · Σᵢ zᵢ·cᵢ·Aᵢ
```

Then:

```text
Σᵢ zᵢ·Rᵢ + Σᵢ zᵢ·cᵢ·Aᵢ - s·G
= zₙ·(-zₙ⁻¹·Σᵢ zᵢ·cᵢ·Aᵢ) + Σᵢ zᵢ·cᵢ·Aᵢ
= -Σᵢ zᵢ·cᵢ·Aᵢ + Σᵢ zᵢ·cᵢ·Aᵢ
= identity
```

Serialize the resulting `{ Rs, s }` with `SchnorrAggregate::write`. `SchnorrAggregate::read` accepts it because every point/scalar is canonical, while `verify` returns true because the multiexp is identity. [1](#0-0) [4](#0-3)

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
