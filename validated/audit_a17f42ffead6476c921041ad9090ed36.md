Based on my investigation, I found the analog vulnerability in the PoX-4 `handle_contract_call` logic.

### Title
Delegated stacking locks (`delegate-stack-stx`) bypass the `Staking` post-condition entirely - ([File: pox-locking/src/pox_4.rs])

### Summary
Just as the GoGoPool report showed a slashing calculation that quietly substituted the wrong period so the on-chain penalty diverged from the real economic event, PoX-4's `handle_stack_lockup_pox_v4` quietly substitutes "no post-condition record at all" for delegated locks, so the amount actually locked diverges from the amount the `Staking` post-condition can see and check.

### Finding Description
`handle_stack_lockup_pox_v4` in `pox-locking/src/pox_4.rs` is invoked for both `"stack-stx"` and `"delegate-stack-stx"` (dispatched from `handle_contract_call` at lines 415-416). It always calls `pox_lock_v4(...)` to actually lock `locked_amount` STX for `stacker`. However, it only records the amount into the asset map's staking ledger when `function_name == "stack-stx"`: [1](#0-0) 

The same asymmetry repeats in `handle_stack_lockup_extension_pox_v4` (gated on `"stack-extend"` only) and `handle_stack_lockup_increase_pox_v4` (gated on `"stack-increase"` only): [2](#0-1) [3](#0-2) 

`log_stacking` is what populates `AssetMap.stacking_map`, which the `Staking` post-condition (`TransactionPostCondition::Staking`) reads via `asset_map.get_stacking()` to enforce a sender-specified cap on how much STX may be locked in a transaction: [4](#0-3) 

Crucially, the coverage-enforcement pass at the end of `check_transaction_postconditions` only fires for entries actually present in `get_all_stacking()`: [5](#0-4) 

Because `delegate-stack-stx` (and `delegate-stack-extend`, `delegate-stack-increase`) never calls `log_stacking`, a real STX lock of arbitrary size on the `stacker`'s account produces **zero** entries in `stacking_map` for that principal. The equality that should hold — "amount actually locked for PoX == amount visible to/enforceable by the `Staking` post-condition" — is broken specifically for the delegated code path, mirroring the GoGoPool bug where "amount actually charged" diverged from "amount the calculation should have reflected."

### Impact Explanation
A contract-caller with delegation authority (an "allowed contract-caller" or the delegate itself, per `check-caller-allowed` in the PoX-4 Clarity contract) can call `delegate-stack-stx` on behalf of a stacker and lock STX up to the delegated amount without that lock ever being visible to a `Staking` post-condition attached to the outer transaction. If a wallet or dApp constructs a transaction in `Deny`/`Originator` mode with an explicit `TransactionPostCondition::Staking(origin, SentLe, cap)` intending to bound how much of the stacker's STX can be locked via any code path reachable in that transaction, the delegated path silently locks funds outside that cap's visibility — the post-condition passes (or is never required to cover the amount) even though STX genuinely became locked. This is an asset moving (into a locked/staked state) past its declared post-condition, which maps to the "asset moving past its post-conditions" Critical-impact category defined in the rules.

### Likelihood Explanation
This does not require a miner, signer, or admin — it only requires an unprivileged principal that has been granted delegate/contract-caller status by the stacker (a normal, expected PoX-4 usage pattern), or the stacker delegating to itself indirectly through a contract call inside its own transaction. The divergence is deterministic and always triggers whenever `delegate-stack-stx`/`delegate-stack-extend`/`delegate-stack-increase` succeeds, with no special timing or race condition needed.

### Recommendation
Log the locked/extended/increased amount into the asset map for **all** successful lock-establishing function names (`stack-stx` and `delegate-stack-stx`; likewise for the extend/increase variants), not just the direct, non-delegated variant, so that `get_stacking()`/`get_all_stacking()` faithfully reflects every amount actually locked in the transaction, matching what pox_4.rs already does correctly for the `delegate-stx` (non-locking, delegation-registration) call path, which does call `log_stacking` unconditionally: [6](#0-5) 

### Proof of Concept
1. Stacker A grants contract-caller allowance to contract B (`allow-contract-caller`, standard PoX-4 flow).
2. Stacker A signs a transaction in `Deny` mode with `post_conditions = [Staking(Origin, SentEq, 0)]` (intending to assert "this transaction must not lock any of my STX"), and calls contract B.
3. Contract B calls `delegate-stack-stx` on A's behalf, locking `N` STX via `pox_lock_v4`.
4. `handle_stack_lockup_pox_v4` executes the lock (`pox_lock_v4` succeeds, A's balance shows `N` STX now locked) but skips `global_context.log_stacking(&stacker, locked_amount)` because `function_name != "stack-stx"`.
5. `check_transaction_postconditions` evaluates the `Staking(Origin, SentEq, 0)` condition against `asset_map.get_stacking(&A)` which returns `0` (unwrap_or(0) at line 300 of `crates/stacks-transactions/src/lib.rs`), so the condition is reported as satisfied even though `N > 0` STX was actually locked — the post-condition the origin explicitly attached to prevent staking is bypassed.
