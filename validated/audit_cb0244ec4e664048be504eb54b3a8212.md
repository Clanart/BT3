### Title
`SignableTransaction::new` under-calculates `needed_fee` because `calculate_weight_vbytes` omits the OP_RETURN data output - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The reference finding is a pricing formula that produces a wrong result because it silently assumes an input has a fixed precision (18 decimals) instead of accounting for the input's actual scale. The same class of bug — a formula that computes a wrong value because it fails to account for one of its inputs — exists in `SignableTransaction::new`: when `data` is specified, an OP_RETURN output is appended to the transaction's outputs, but `calculate_weight_vbytes` is invoked with only `payments`, so the weight/vbytes used to derive `needed_fee` and the minimum-relay-fee check are computed on a transaction that is smaller than the one actually constructed and signed.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments` plus an optional OP_RETURN output carrying up to 80 bytes of caller-supplied `data`:

```rust
// networks/bitcoin/src/wallet/send.rs:193-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

However, the fee derivation uses `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (line 226), which build a scratch `Transaction` containing only the `payments` outputs (and optionally `change`). The data output is never included:

```rust
// networks/bitcoin/src/wallet/send.rs:204-211
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);

let mut needed_fee = fee_per_vbyte * vbytes;
...
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

`calculate_weight_vbytes` (lines 62-127) faithfully measures the scratch transaction's `weight()` — but that scratch transaction lacks the OP_RETURN output present in the real `tx` stored in `SignableTransaction` (lines 245-255). An OP_RETURN output adds `8 (value) + ~1 (len) + ~2-4 (script header) + data_len` bytes, i.e. up to ~93 bytes (~93 vbytes, 372 WU) for an 80-byte payload. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` under-pays by up to `fee_per_vbyte * ~93` satoshis relative to the requested fee rate.
2. The `TooLowFee` check compares an underestimated `needed_fee` against an underestimated `vbytes`, so a transaction whose *actual* fee rate meets the minimum can still be produced with a fee *rate* below what the caller requested, and the `MAX_STANDARD_TX_WEIGHT` check at line 241 uses a `weight` that excludes the data output.

An unprivileged caller reaches this purely through public inputs: the `data: Option<Vec<u8>>` argument to `SignableTransaction::new` (a public API of `bitcoin-serai`'s wallet), which the downstream `TransactionSignMachine::sign` binds into the Taproot sighashes and final transaction.

### Impact Explanation
The produced `SignableTransaction` commits (via `Prevouts::All` Taproot sighash in `sign`, lines 373-390) to a transaction whose actual vsize exceeds the size used for the fee calculation. The result is a threshold-signed transaction paying an effective fee rate lower than `fee_per_vbyte` — by up to ~93 vbytes worth of fee — and potentially below the mempool minimum relay fee even though `TooLowFee` did not fire. The signed transaction can therefore be rejected by `send_raw_transaction` or languish unconfirmed, while `needed_fee`/`fee()` report inconsistent values (`fee()` at lines 138-141 measures the *actual* fee, which differs from `needed_fee` only in that the residual went to change — wait, actually the shortfall materializes as a lower-than-intended effective fee rate, since the absolute fee stays `input_sat - payment_sat - change` while vsize grew). Funds are not lost, but the transaction's confirmation/fee-rate guarantee the API contract (`needed_fee` = fee achieving the requested rate) is violated — an incorrect-formula bug directly analogous to the oracle returning a mis-scaled price.

### Likelihood Explanation
Any caller of `SignableTransaction::new` supplying `data` triggers it deterministically; no adversarial condition beyond a non-empty `data` argument is required. The miscalculation scales linearly with `data.len()` (up to 80 bytes allowed by the `TooMuchData` check at line 171). The magnitude is bounded (~93 vbytes of underestimation), so this is a Medium-severity correctness/liveness issue rather than a fund-loss bug.

### Recommendation
Include the OP_RETURN output in the weight estimation. Pass the already-built `tx_outs` (or an equivalent `(ScriptBuf, u64)` list that includes the data output) into `calculate_weight_vbytes` for both the no-change and with-change calls, so `vbytes`, `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the final transaction.

### Proof of Concept
```rust
// Conceptual test for networks/bitcoin/tests/wallet.rs
let payments = [(p2tr_script_buf(key).unwrap(), 100_000)];
let data = vec![0xaa; 80]; // max allowed OP_RETURN payload

let tx = SignableTransaction::new(
  vec![output.clone()],
  &payments,
  None,           // no change: entire residual becomes fee
  Some(data),
  FEE,            // sat/vbyte
).unwrap();

// Actual signed transaction is ~93 vbytes larger than the estimated one
let actual_vsize = tx.transaction().vsize() as u64;
let actual_fee = tx.fee(); // input - payments (no change)

// The advertised needed_fee corresponds to a SMALLER transaction:
assert!(tx.needed_fee() < actual_vsize * FEE);
// i.e. the effective fee rate is below the requested FEE sat/vbyte:
assert!(actual_fee < actual_vsize * FEE); // because change was dropped,
// fee = input - payments, but vsize grew by the OP_RETURN output,
// so fee/vsize < FEE, and may dip below the relay minimum.
```
Concretely: with `needed_fee = FEE * vbytes_wo_data` and no change, the transaction pays `needed_fee` over `vbytes_wo_data + ~93` vbytes, yielding an effective rate of roughly `FEE * vbytes / (vbytes + 93)` sat/vbyte — strictly below the caller's requested rate, with the shortfall proportional to the attacker/user-controlled `data` length.
