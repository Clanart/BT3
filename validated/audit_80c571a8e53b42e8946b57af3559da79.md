### Title
mWomSV permanently locks slashed/forfeited penalty funds with no function to withdraw them - (File: `wombat/mWomSV.sol`)

### Summary
`mWomSV.sol` declares the same penalty-accounting state (`penaltyDestination`, `totalPenalty`) as `VLMGP.sol`, and accumulates penalty amounts whenever a user force-unlocks early [1](#0-0) . However, unlike `VLMGP.sol`, which implements `transferPenalty()` to sweep the accumulated `totalPenalty` out to `penaltyDestination` [2](#0-1) , `mWomSV.sol` has no equivalent `transferPenalty` (or any other withdrawal) function — a repository-wide search for `function transferPenalty` only matches `VLMGP.sol` and not `wombat/mWomSV.sol`.

### Finding Description
`mWomSV` is the "mWOM Stability Vault" lock contract, analogous to `VLMGP`, and both declare a `penaltyDestination` address and `totalPenalty` accumulator used to track mWOM forfeited from users who call `forceUnLock` before their cooldown period ends [1](#0-0) . In `VLMGP`, `forceUnLock` increments `totalPenalty`, and the owner later calls `transferPenalty()` to move the accumulated MGP penalty out of the contract to `penaltyDestination` [3](#0-2) [2](#0-1) . `mWomSV.sol` mirrors the same state layout (`penaltyDestination`, `totalPenalty`) but the codebase does not contain a corresponding `transferPenalty` (or `spend`/`sweep`) function for it. As a result, any mWOM tokens that accumulate as `totalPenalty` in `mWomSV` from ordinary users calling `forceUnLock` have no code path to leave the contract — they are permanently stuck in the vault's token balance, exactly the class of bug described in the referenced report (funds transferred into a contract that lacks any spend/withdraw method).

### Impact Explanation
Penalty mWOM forfeited by unprivileged users through the normal `forceUnLock` flow becomes permanently locked in `mWomSV` with no owner or user-callable function to retrieve it, since no `transferPenalty`-equivalent exists in this contract. This is a genuine, non-privileged-triggered permanent freezing of funds (the yield/penalty portion of protocol funds), meeting the "permanent freezing of funds" acceptance bar.

### Likelihood Explanation
This occurs deterministically any time a normal user (not privileged) calls `forceUnLock` on a slot before its cooldown ends, which is a standard, expected, and frequently-used unlock path for `mWomSV`, so the funds accumulation is highly likely to occur in normal operation.

### Recommendation
Add a `transferPenalty()` function to `mWomSV.sol`, mirroring `VLMGP.transferPenalty()`, that transfers `totalPenalty` of mWOM to `penaltyDestination` and resets `totalPenalty` to zero, guarded so that `penaltyDestination` must be set before use, matching the pattern already present in `VLMGP.sol` [2](#0-1) .

### Proof of Concept
1. Owner deploys/initializes `mWomSV` and sets `penaltyDestination` — but no code path in `mWomSV.sol` allows using it.
2. A user locks mWOM and later calls `forceUnLock` on an active slot before `endTime`, incurring a penalty added to `totalPenalty` (mirroring the logic verified in `VLMGP.forceUnLock` at [3](#0-2) ).
3. The penalty mWOM tokens now sit in the `mWomSV` contract balance.
4. There is no `transferPenalty` (or any other) function in `wombat/mWomSV.sol` to move these tokens out — confirmed by the absence of any `function transferPenalty` match in that file, versus its presence in `VLMGP.sol`.
5. The penalty mWOM remains permanently stuck in the contract, unrecoverable by any account.

```text
    function forceUnLock(uint256 _slotIndex) external whenNotPaused nonReentrant {
        _checkIdexInBoundary(msg.sender, _slotIndex);
        UserUnlocking storage slot = userUnlockings[msg.sender][_slotIndex];
        _checkInCoolDown(msg.sender, _slotIndex);

        _unlock(slot.amountInCoolDown);
        (uint256 penaltyAmount, uint256 amountToUser) = expectedPenaltyAmount(_slotIndex);

        IERC20(MGP).safeTransfer(msg.sender, amountToUser);
        totalPenalty += penaltyAmount;

        slot.amountInCoolDown = 0;
        slot.endTime = block.timestamp;

        emit ForceUnLock(msg.sender, _slotIndex, amountToUser, penaltyAmount);
    }
```
