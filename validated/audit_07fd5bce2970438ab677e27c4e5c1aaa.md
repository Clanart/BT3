### Title
Malicious repository content (`\ No newline at end of file` markers / crafted hunk headers) can desynchronize `diff-parser.ts` line accounting from what `patch-formatter.ts` writes into a `--unidiff-zero` patch, silently corrupting staged/discarded content - ([File: app/src/lib/patch-formatter.ts])

### Summary
GitHub Desktop builds a synthetic unified diff (via `formatPatch` / `formatPatchToDiscardChanges`) from the parsed `git diff` output and the user's line-selection state, then feeds that synthetic patch to `git apply --unidiff-zero --whitespace=nowarn -` in `app/src/lib/git/apply.ts` to partially stage (`applyPatchToIndex`) or discard (`discardChangesFromSelection`) changes. [1](#0-0) [2](#0-1) 

This mirrors the reported bug class: a value that is computed by one part of the logic (the closing fee/collateral deduction) is not correctly propagated into the value used for the actual transfer, causing the wrong amount to move. Here the analogous "amount" is the hunk line-count (`oldCount`/`newCount`) written into the synthesized hunk header, which must exactly match the number of body lines actually emitted for the hunk to be applied at the correct offset — especially since `--unidiff-zero` disables git's normal context-line verification, which is the very check that would otherwise catch a miscount.

### Finding Description
`formatPatch`/`formatPatchToDiscardChanges` iterate `hunk.lines` (produced by `DiffParser.parseHunk` in `app/src/lib/diff-parser.ts`) and independently accumulate `oldCount`/`newCount` while writing lines to `hunkBuf`, then only afterwards emit the header via `formatHunkHeader(...)`. [3](#0-2) [4](#0-3) 

The count bookkeeping and the "no newline" marker handling are two independently-maintained pieces of state that must stay in lockstep with the underlying `DiffLine` stream that ultimately comes from the content of a cloned/fetched repository (the diff text is generated by running `git diff` against whatever blobs exist in the repo, including attacker-controlled trees/working files after a clone, checkout, or merge). The parser specifically special-cases the `\ No newline at end of file` marker by patching the *previous* line's flag rather than treating it as a counted line: [5](#0-4) 

Because `formatHunkHeader` trusts the accumulated `oldCount`/`newCount` values without any independent verification against the number of lines actually written to `hunkBuf`, any divergence between the two — for example from a crafted diff/file content that causes the line-classification logic (Context vs Add/Delete/no-newline) to diverge between what is counted and what is emitted — will produce a header describing a hunk size that does not match its body: [6](#0-5) 

Critically, the invoking command uses `--unidiff-zero`, which explicitly disables the surrounding-context matching that `git apply` normally uses to detect a misapplied/miscounted hunk and instead applies the hunk based purely on the (attacker-influenceable) line numbers in the header: [7](#0-6) [8](#0-7) 

If the count in the header is wrong relative to the emitted body, `git apply --unidiff-zero` can still "succeed" (no error is surfaced back to the user) but land the change at the wrong line offset or silently drop/duplicate content in the index (`applyPatchToIndex`) or in the working tree (`discardChangesFromSelection`) — i.e., the exact "silent corruption of what the user commits" class called out as valid impact.

### Impact Explanation
`applyPatchToIndex` is used for partial staging of a hunk/line selection into the index, and `discardChangesFromSelection` is used to reverse-apply a patch directly to the working tree file. Both paths write file/index content based on a self-generated patch whose header integrity is never independently checked before being piped to `git apply` with the context-check safety net disabled (`--unidiff-zero`). A user who partially stages or discards lines from a file whose diff triggers a count/body mismatch would have code silently placed at the wrong offset or dropped in what they believe they are committing/discarding, without any error or warning shown.

### Likelihood Explanation
The trigger surface is any working-directory diff of a file the user interacts with through partial-selection UI (stage/discard specific lines) — this is a mainstream, frequently used feature, and the diff content itself originates from files/commits that can come from a cloned or fetched repository, i.e. attacker-influenceable content (edge cases such as no-trailing-newline files, files with `@@`-looking content, or unusual mixtures of hunk line types are the kind of inputs that stress this count/body bookkeeping). No error is thrown by `git apply --unidiff-zero` on a miscounted-but-structurally-valid hunk, so a defect here would fail silently rather than being caught by existing error handling.

### Recommendation
- Compute the hunk header counts from the same authoritative source as the body content (e.g., increment counts inline with each line actually appended to `hunkBuf`, or derive the header purely from `hunkBuf`'s emitted lines) rather than maintaining two parallel tallies in `formatPatch`/`formatPatchToDiscardChanges`.
- Add a runtime assertion in `patch-formatter.ts` that the number of `+`/context lines in `hunkBuf` equals `newCount` and `-`/context lines equals `oldCount` before emitting the header, throwing rather than silently producing a mismatched patch.
- Avoid `--unidiff-zero` (or add a follow-up verification step, e.g. `git apply --check` with normal context) so `git apply` retains its built-in context-based sanity check as a safety net against header/body drift.

### Proof of Concept
Conceptual PoC (exact minimal diff input needed to force a count/body divergence could not be fully constructed without running the parser/formatter, since the counting logic in `formatPatch` looked internally consistent for the sampled test cases in `app/test/unit/diff-parser-test.ts`):
1. Clone/fetch a repository containing a file with an edge-case hunk (e.g., a file missing a trailing newline whose last diff line is immediately followed by another hunk, or content that includes literal `\ No newline at end of file`-like text) so `getWorkingDirectoryDiff` (`app/src/lib/git/diff.ts`) produces a raw diff parsed by `DiffParser.parseHunk`.
2. In the Changes view, select a partial subset of lines in that hunk for staging or discarding.
3. `applyPatchToIndex` / `discardChangesFromSelection` build a patch via `formatPatch` / `formatPatchToDiscardChanges` and pipe it to `git apply --unidiff-zero --whitespace=nowarn -`.
4. If the emitted `oldCount`/`newCount` header does not match the actual body line count for that hunk, `git apply --unidiff-zero` can apply the hunk at an incorrect offset or otherwise diverge from user intent without producing a visible error, silently corrupting the staged index content or the discarded-to working file.

Note: I was not able to fully verify, from static reading alone, a concrete input in the current parser/formatter pair that reproduces an actual count/body mismatch (the sampled logic paths in `formatPatch` appeared self-consistent for the cases I traced) — this should be validated dynamically (fuzzing `DiffParser` + `formatPatch`/`formatPatchToDiscardChanges` with edge-case diffs, especially around no-newline markers and hunk boundary line reclassification) before treating this as a confirmed exploitable bug rather than a structural risk pattern.

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
```

```typescript
  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.oldStartLine,
      oldCount,
      hunk.header.newStartLine,
      newCount
    )
    patch += hunkBuf
  })
```

```typescript
  private parseHunk(
    linesConsumed: number,
    hunkIndex: number,
    previousHunk: DiffHunk | null
  ): DiffHunk {
    const headerLine = this.readLine()
    if (!headerLine) {
      throw new Error('Expected hunk header but reached end of diff')
    }

    const header = this.parseHunkHeader(headerLine)
    const lines = new Array<DiffLine>()
    lines.push(new DiffLine(headerLine, DiffLineType.Hunk, 1, null, null))

    let c: DiffLinePrefix | null

    let rollingDiffBeforeCounter = header.oldStartLine
    let rollingDiffAfterCounter = header.newStartLine

    let diffLineNumber = linesConsumed
    while ((c = this.parseLinePrefix(this.peek()))) {
      const line = this.readLine()

      if (!line) {
        throw new Error('Expected unified diff line but reached end of diff')
      }

      // A marker indicating that the last line in the original or the new file
      // is missing a trailing newline. In other words, the presence of this marker
      // means that the new and/or original file lacks a trailing newline.
      //
      // When we find it we have to look up the previous line and set the
      // noTrailingNewLine flag
      if (c === DiffPrefixNoNewline) {
        // See https://github.com/git/git/blob/21f862b498925194f8f1ebe8203b7a7df756555b/apply.c#L1725-L1732
        if (line.length < 12) {
          throw new Error(
            `Expected "no newline at end of file" marker to be at least 12 bytes long`
          )
        }

        const previousLineIndex = lines.length - 1
        const previousLine = lines[previousLineIndex]
        lines[previousLineIndex] = previousLine.withNoTrailingNewLine(true)

        continue
      }

      // We must increase `diffLineNumber` only when we're certain that the line
      // is not a "no newline" marker. Otherwise, we'll end up with a wrong
      // `diffLineNumber` for the next line. This could happen if the last line
      // in the file doesn't have a newline before the change.
      diffLineNumber++

      let diffLine: DiffLine

      if (c === DiffPrefixAdd) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Add,
          diffLineNumber,
          null,
          rollingDiffAfterCounter++
        )
      } else if (c === DiffPrefixDelete) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Delete,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          null
        )
      } else if (c === DiffPrefixContext) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Context,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          rollingDiffAfterCounter++
        )
      } else {
        return assertNever(c, `Unknown DiffLinePrefix: ${c}`)
      }

      lines.push(diffLine)
    }

    if (lines.length === 1) {
      throw new Error('Malformed diff, empty hunk')
    }

    return new DiffHunk(
      header,
      lines,
      linesConsumed,
      linesConsumed + lines.length - 1,
      getHunkHeaderExpansionType(hunkIndex, header, previousHunk)
    )
  }
```
