### Title
Missing key-coverage check in `GeneratorPromotion::complete` causes a reachable panic (DoS) when a peer's proof map omits a participant - ([File: crypto/dkg/promote/src/lib.rs](https://github.com/blackvul/serai--018/blob/master/crypto/dkg/promote/src/lib.rs))

### Summary
Analogous to the OpenSSL `SSL_CIPHER_find()` NULL dereference on an unexpected peer-supplied value, `GeneratorPromotion::complete` validates only the *count* and *upper bound* of the participant-keyed proof map, then unconditionally unwraps `proofs.get(&i)` for every expected index. A peer-supplied proof map that passes both checks while omitting an expected participant causes `Option::unwrap` on `None`, aborting the promotion (and potentially the host process).

### Finding Description
`complete` enforces two checks on the `proofs: &HashMap<Participant, GeneratorProof<C1>>` argument:

```rust
// crypto/dkg/promote/src/lib.rs:125-136
if proofs.len() != (usize::from(params.n()) - 1) {
  Err(PromotionError::IncorrectAmountOfParticipants { ... })?;
}
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() {
    Err(PromotionError::InvalidParticipant { ... })?;
  }
}
```

It then iterates every expected index and indexes the map with `unwrap`:

```rust
// crypto/dkg/promote/src/lib.rs:140-146
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() {
    continue;
  }
  let proof = proofs.get(&i).unwrap();   // panics on None
```

The two validation checks are not sufficient to guarantee `get(&i)` succeeds for all `i != params.i()` in `1..=n`. A map of the correct length (`n - 1`) whose keys are all `<= n` can still be missing an expected index — most simply by containing the *caller's own* participant index `params.i()`, which the loop then skips, leaving one of the other `n - 1` expected keys absent. The `HashMap` key set can also duplicate nothing yet still omit an index if it contains `params.i()`. There is no check that the key set equals `{1..=n} \ {params.i()}`, and `Participant` is `Copy`/`Eq` so an off-by-one substitution (`{1, 2}` instead of `{2, 3}`) trivially satisfies both guards.

### Impact Explanation
`proofs` is populated from `GeneratorProof` messages received from the other participants (deserialized via `GeneratorProof::read`, lib.rs:72-77) and keyed by the participant index each peer claims. An unprivileged peer that submits its proof under the victim's own index `params.i()` (or under any index such that some expected `j` is absent, while keeping the map length at `n - 1`) causes `proofs.get(&j).unwrap()` at line 146 to panic. Like the advisory's NULL dereference, the reachable consequence is abnormal termination of the running process — a denial of service against the promoting node, crashing it mid-protocol before the promoted `ThresholdKeys<C2>` are produced. Severity is bounded by DoS-only impact: no key material is exposed and no invalid keys are accepted.

### Likelihood Explanation
Reachability requires a participant in an in-progress generator promotion to send a proof keyed to a participant index that produces a non-covering map — a single malformed/unexpected identifier from a peer, directly paralleling the advisory's "unknown cipher suite from the peer" trigger. It does not require collusion, threshold corruption, or control of multiple participants: one mislabeled proof suffices. The main mitigation is whether the integrator filters keys before building the map, but the library performs its own validation and silently substitutes a panic for a `PromotionError`, so the crash is a defect in the library's own input handling on an untrusted input path (`complete` is an explicitly in-scope API).

### Recommendation
Before iterating, verify the key set exactly: check that `proofs` contains every `Participant` in `1..=n` except `params.i()` and no others — e.g., reject any key equal to `params.i()`, then for each expected `i` use `proofs.get(&i).ok_or(PromotionError::InvalidParticipant { n: params.n(), participant: i })?` instead of `unwrap()` at lib.rs:146. This converts the abort into a proper error identifying the faulty participant.

### Proof of Concept
With `params = ThresholdParams { t: n, n: 3, i: Participant(1) }`:

```rust
let mut proofs: HashMap<Participant, GeneratorProof<C1>> = HashMap::new();
proofs.insert(Participant::new(1).unwrap(), proof_from_peer_a); // victim's own index
proofs.insert(Participant::new(2).unwrap(), proof_from_peer_b);
// proofs.len() == 2 == n - 1  -> passes line 125
// all keys <= 3                -> passes lines 132-136
// loop: i=1 skipped (== params.i()), i=2 ok, i=3 -> proofs.get(&3) == None
// -> unwrap() panic at crypto/dkg/promote/src/lib.rs:146
let _ = promotion.complete(&proofs); // aborts instead of returning Err
```

Any single peer whose proof is keyed under `1` instead of `3` (whether maliciously or due to misconfiguration) triggers the panic, matching the report's pattern of a crash on an unexpected peer-supplied identifier.
