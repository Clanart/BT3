Confirmed: `Kip71BaseFeeDenominator` has a `FormatChecker` requiring `v != 0` (`kaiax/gov/param.go` line 314), but `Kip71GasTarget` uses `noopFormatChecker` (line 326), meaning governance voting can set `GasTarget` to `0` with no validation. That value flows unguarded into `NextMagmaBlockBaseFee`'s divisor.

### Title
Unvalidated `kip71.gastarget` governance parameter allows division-by-zero panic in KIP-71 base fee calculation - (File: params/kip71_config.go, kaiax/gov/param.go)

### Summary
`NextMagmaBlockBaseFee` in `params/kip71_config.go` explicitly guards against `BaseFeeDenominator == 0` but performs no equivalent guard for `GasTarget`, which is used as a divisor. The governance parameter `kip71.gastarget` (`Kip71GasTarget` in `kaiax/gov/param.go`) uses `noopFormatChecker`, so it accepts any `uint64` value including `0`, unlike the sibling parameter `Kip71BaseFeeDenominator` whose `FormatChecker` explicitly rejects `0`.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee based on gas usage relative to `gasTarget`: [1](#0-0) 
It guards `BaseFeeDenominator` against zero, replacing it with a safe default of `64`, but performs no such check for `gasTarget`: [2](#0-1) [3](#0-2) 
If `gasTarget == 0`, then whenever `parentGasUsed != gasTarget` (i.e., practically always, since any nonzero gas usage triggers the `parentGasUsed > gasTarget` branch), the code executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor. Go's `big.Int.Div`/`Quo` panics on division by zero (this is the exact bug-class match to the external report's Solidity "modulo by zero" panic — here it is Go's division-by-zero panic).

The root cause is that `Kip71GasTarget` is registered with `noopFormatChecker` in `kaiax/gov/param.go`, allowing any governance vote (including `0`) to be canonicalized and applied, whereas the neighboring, functionally identical divisor parameter `Kip71BaseFeeDenominator` explicitly enforces `v != 0`: [4](#0-3) 

This asymmetry means the developers were aware of the division-by-zero risk for one divisor but missed applying the same protection to `GasTarget`, an oversight structurally identical to the original report where only generation `0` of `numElements` was initialized/protected and other generations were left vulnerable.

### Impact Explanation
`NextMagmaBlockBaseFee` is called from `VerifyMagmaHeader`, which is part of block header validation on every block after the Magma hardfork, and is also used to compute the base fee to be embedded in newly proposed blocks. A panic in this function during block processing would crash the node process (or at minimum cause block validation to fail with a runtime panic rather than a graceful error), leading to consensus-critical denial of service: if a `kip71.gastarget` governance vote of `0` is ratified and activated, every honest node computing/verifying the next block's base fee will panic, halting the entire chain. This is a chain-halting availability/consensus failure reachable through the standard governance parameter voting path (a public, "governance parameters" reachable surface explicitly in scope).

### Likelihood Explanation
Reaching this requires a `kip71.gastarget` governance vote to be cast and pass under the network's governance rules (`GovernanceMode`/quorum requirements). This is not a fully permissionless single-transaction path like the original Solidity finding, but it is reachable by any account participating in governance voting per the module's design, and no additional validation anywhere in the vote/param pipeline (`Canonicalizer`, `FormatChecker`, or `kip71_config.go` itself) prevents `0` from being accepted and activated, unlike the explicitly-guarded `BaseFeeDenominator`.

### Recommendation
Add a `FormatChecker` to `Kip71GasTarget` in `kaiax/gov/param.go` rejecting `v == 0`, consistent with `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` (mirroring the existing `BaseFeeDenominator` fallback) so that even a pre-existing or externally injected `ChainConfig` with `GasTarget == 0` cannot cause a panic during header validation.

### Proof of Concept
1. Governance vote sets `kip71.gastarget` to `0` and the vote is ratified/activated per the governance module's rules (no `FormatChecker` rejects it, per `kaiax/gov/param.go` line 324-334).
2. On the block after activation, any block with `parentHeaderGasUsed != 0` triggers `NextMagmaBlockBaseFee`'s `parentGasUsed > gasTarget` branch (since `gasTarget = 0`).
3. `gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)`, then `x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `big.Int.Div(x, 0)`, which panics in Go's `math/big` package.
4. This panic occurs during `VerifyMagmaHeader`/header validation on every node, halting block processing chain-wide.
