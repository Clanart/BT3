Based on my investigation, I found a solid analog to the reported bug class in `x/tokenfactory`'s bank actions, which bypass the denom `AllowList` restriction that is otherwise enforced at the `MsgSend` layer — mirroring the original report's pattern of a state/restriction check (`poolActive`) that exists in the system but is not consistently enforced across all code paths that move funds/state.

### Title
Tokenfactory admin mint/burn transfers bypass the denom `AllowList` restriction enforced on `bank.MsgSend` - (File: x/tokenfactory/keeper/bankactions.go)

### Summary
The `AllowList` restriction mechanism (analogous to `BaseStrategy`'s `poolActive` state) is designed to restrict which addresses may send/receive a specific tokenfactory denom. It is only actively checked inside `bank`'s `msgServer.Send` [1](#0-0) , not inside the underlying `SendCoins`/`SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` keeper primitives. The tokenfactory module's `mintTo`/`burnFrom` helpers call these lower-level keeper primitives directly, so the `AllowList` check is never invoked.

### Finding Description
`x/tokenfactory` lets a denom's admin set a `AllowList` via `UpdateDenom`, restricting which accounts may hold/transfer the denom [2](#0-1) . This restriction is enforced only in the `bank` module's `MsgSend` handler, which explicitly calls `IsInDenomAllowList` for both the sender and the receiver before calling `SendCoins` [1](#0-0) .

However, `x/tokenfactory`'s `mintTo` and `burnFrom` functions — invoked by the tokenfactory `Mint`/`Burn` message handlers reachable by any denom admin — call `k.bankKeeper.SendCoinsFromModuleToAccount` and `k.bankKeeper.SendCoinsFromAccountToModule` directly [3](#0-2) . These lower-level keeper functions do not perform the `IsInDenomAllowList` check themselves — that check lives only in `msgServer.Send`, not in the generic `SendCoins`-family primitives. As a result, minting to (or burning from) an address that is *not* in the denom's `AllowList` succeeds silently, defeating the purpose of the restriction, exactly as the original report describes core state-guarding functions ("registerRecipient", "allocate", "increasePoolAmount") that omit the `onlyActivePool` gate that is enforced elsewhere in the same contract.

### Impact Explanation
An `AllowList`-restricted tokenfactory denom is meant to guarantee that only whitelisted addresses can hold/receive the token (a common compliance/whitelisting primitive for RWA-like or permissioned assets on Sei). Because `Mint`/`Burn` bypass this check, a denom admin can mint tokens directly to (or burn tokens from) addresses that are explicitly excluded from the allow list, silently violating the guarantee that downstream integrators (pointer contracts, DEXs, other users) rely upon. This breaks an access-control invariant of a supply-affecting operation (mint/burn), which can propagate to unauthorized balances of a restricted token — a compliance/control-bypass bug directly analogous to the original "state not enforced" issue.

### Likelihood Explanation
Likelihood is moderate: it requires the tokenfactory denom admin to (a) have set an `AllowList` via `UpdateDenom` and (b) intentionally or mistakenly mint to / burn from a non-allow-listed address. This is a normal, everyday tokenfactory operation (`MsgMint`/`MsgBurn`) with no additional permissions needed beyond being the existing denom admin, so the path is trivially reachable by any account that already has mint/burn authority over an `AllowList`-restricted denom.

### Recommendation
Add an `IsInDenomAllowList` check (mirroring the one in `bank.msgServer.Send`) to `x/tokenfactory/keeper/bankactions.go`'s `mintTo` and `burnFrom` before calling `SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule`, or move the `AllowList` enforcement down into the shared `SendCoins`-family keeper methods so all code paths (message-server and module-to-account transfers) enforce the restriction consistently.

### Proof of Concept
1. Denom admin creates a tokenfactory denom via `MsgCreateDenom`.
2. Admin sets an `AllowList` for the denom via `MsgUpdateDenom` that excludes address `X` [2](#0-1) .
3. Admin sends `MsgMint` targeting their own account then a regular `MsgSend` to `X` — this correctly fails with "not allowed to receive funds" because `msgServer.Send` enforces the allow list [4](#0-3) .
4. However, if `mintTo`/`burnFrom` instead moved funds via `SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` targeting `X` directly (or via any keeper-level transfer helper not routed through `msgServer.Send`), no `IsInDenomAllowList` check is performed [3](#0-2) , so the restricted transfer succeeds, confirming the bypass.

**Note on uncertainty:** I verified that `msgServer.Send` is the only call site performing the `IsInDenomAllowList` check in the codebase (via `grep_search`), and that `x/tokenfactory/keeper/bankactions.go`'s `mintTo`/`burnFrom` call the lower-level `SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` without that check. I was not able to fully trace every other caller of `SendCoinsFromModuleToAccount`/`SendCoinsFromAccountToModule` across the codebase within the available iterations, so there may be additional code paths with the same gap; a full audit of all callers of these bank keeper primitives against `AllowList`-restricted denoms is recommended to confirm the complete blast radius.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

func (k Keeper) mintTo(ctx sdk.Context, amount sdk.Coin, mintTo string) error {
	// verify that denom is an x/tokenfactory denom
	_, _, err := types.DeconstructDenom(amount.Denom)
	if err != nil {
		return err
	}

	logger.Info("Minting amount for module", "amount", amount, "module", types.ModuleName)
	err = k.bankKeeper.MintCoins(ctx, types.ModuleName, sdk.NewCoins(amount))
	if err != nil {
		return err
	}

	addr, err := sdk.AccAddressFromBech32(mintTo)
	if err != nil {
		return err
	}

	logger.Info("Sending minted amount to addr", "amount", amount, "addr", addr)
	return k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName,
		addr,
		sdk.NewCoins(amount))
}

func (k Keeper) burnFrom(ctx sdk.Context, amount sdk.Coin, burnFrom string) error {
	// verify that denom is an x/tokenfactory denom
	_, _, err := types.DeconstructDenom(amount.Denom)
	if err != nil {
		return err
	}

	addr, err := sdk.AccAddressFromBech32(burnFrom)
	if err != nil {
		return err
	}

	logger.Info("Sending amount to module from account", "amount", amount, "module", types.ModuleName, "account", addr)
	err = k.bankKeeper.SendCoinsFromAccountToModule(ctx,
		addr,
		types.ModuleName,
		sdk.NewCoins(amount))
	if err != nil {
		return err
	}

	logger.Info("Burning amount from module", "amount", amount, "module", types.ModuleName)
	return k.bankKeeper.BurnCoins(ctx, types.ModuleName, sdk.NewCoins(amount))
}
