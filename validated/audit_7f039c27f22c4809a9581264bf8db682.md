### Title
JSON duplicate-field detection compares raw key strings instead of resolved field identity, allowing alternate-name key confusion to silently bypass the uniqueness invariant - (File: python/google/protobuf/json_format.py)

### Summary
The Sherlock report's failed invariant is: two representations of "the same quantity" (spot price vs. oracle price) are compared without normalizing them to a common format, so a security check (pool-manipulation detection) is defeated by a representation mismatch. The closest Protobuf analog is in ProtoJSON parsing's duplicate-key/field-uniqueness check: the parser tracks *seen JSON key strings* to reject duplicate fields, but a single logical field can be addressed by two different string spellings (its `name` and its `json_name`/camelCase form). Because the "already seen" set stores the literal key text rather than the resolved `FieldDescriptor`, two differently-spelled keys that resolve to the *same field* are not recognized as duplicates, and the uniqueness check that is supposed to guard against this is silently bypassed.

### Finding Description
ProtoJSON parsing (`json_format.Parse` in Python, and the analogous C++/Java `JsonFormat` parsers) enforces that a JSON object may not specify the same field twice — this is explicitly a validation/uniqueness invariant, not just a convenience feature, and is documented as required behavior in `docs/design/editions/edition-zero-json-handling.md:26-31`, which states that "proto3 fully validates JSON mappings for uniqueness during parsing" and that conflicting mappings otherwise "lead to undefined behavior" that is "inconsistent across runtimes."

The implementation performs this uniqueness check by comparing the *textual JSON key* seen for each entry (a `names` set keyed by the raw string from the input, per `_ConvertFieldValuePair` in `python/google/protobuf/json_format.py`) rather than by comparing the *resolved field* the key maps to. A proto field can legitimately be referenced in JSON by either its original `name` (e.g. `int32_value`) or its computed/`json_name` (e.g. `int32Value`) — two different textual "formats" for identically the same underlying field, directly analogous to the report's "spot price" vs. "oracle price" being two different formats of the same economic quantity. Because the duplicate check compares the un-normalized string instead of the field it resolves to, submitting both spellings in the same JSON object passes the "not already seen" check twice and the field is silently overwritten ("last one wins") instead of being rejected as a duplicate.

This is explicitly confirmed as an implementation defect (not an intentional design choice) in the test suite itself: [1](#0-0) 
which states: "this behavior is non-spec and an oversight bug in the implementation... The duplicate field checker intends [to] reject inputs with duplicate key names, but it only catches keys that are exact matches and not alternate spellings that correspond to the same field," and demonstrates it both for a scalar field and for a map field.

The cross-runtime inconsistency is corroborated at the design-doc level: [2](#0-1) 

### Impact Explanation
This maps onto the report's threat model: an ordinary client sends bounded, well-formed ProtoJSON through a public parse API (`Parse`/`MergeFrom` JSON entry points), and a downstream application relies on Protobuf's stated uniqueness guarantee (no duplicate fields per message) to make a security-relevant decision — e.g., an allow/deny field, an amount field validated once and then reused, or a map-based access-control table. Because the checker's "duplicate" comparison operates on the wrong representation (raw key text) instead of the semantically correct one (resolved field/tag), an attacker can smuggle two values for the same field under different spellings; the parser accepts both instead of raising `ParseError`, and the *last* one silently wins. If application logic validates the first occurrence (or simply assumes at most one value is present, per the documented invariant) and later code paths observe the overwritten value, this is a classic "key-confusion" class of vulnerability (structurally similar to HTTP header/JSON key-smuggling issues) that can defeat validation checks built on top of Protobuf's JSON uniqueness guarantee — an integrity failure in the parser's own advertised invariant, not merely an "allowed interpretation difference."

### Likelihood Explanation
Likelihood is high for reachability (any application accepting ProtoJSON input and depending on duplicate-field rejection is affected) but the severity is bounded by the fact that it only causes overwrite/last-wins semantics rather than memory corruption; it is a logic/validation-bypass bug, not a crash or RCE. It requires no privileged access, malicious schema, or unbounded input — only a schema with a field whose `name` differs from its `json_name` (the common case for any snake_case-named proto field, since default JSON naming lowerCamelCases it), which is ubiquitous in real-world `.proto` schemas. It is explicitly called out by the project's own tests as a known, unfixed oversight, and the design doc confirms the underlying uniqueness guarantee is inconsistently enforced across language runtimes.

### Recommendation
Change duplicate-field detection in the JSON parser (Python `json_format.py`, and check the equivalent logic in C++ `json/internal/parser.cc` and Java `JsonFormat`) to track *resolved field identity* (e.g., `FieldDescriptor` object or field number) rather than the raw JSON key string, so that any two spellings (`name` and `json_name`) that resolve to the same field are correctly flagged as duplicates and rejected, consistent with the documented "proto3 fully validates JSON mappings for uniqueness" guarantee.

### Proof of Concept
Existing regression tests already demonstrate the bypass without any modification: [1](#0-0) 
- `testDuplicateFieldAlternateNames`: parsing `{"int32Value": 1,"int32_value":2}` into `TestMessage` does **not** raise the expected `Failed to load JSON: duplicate key` error; instead `parsed_message.int32_value` silently ends up `2` (last-one-wins), even though both keys refer to the identical field.
- `testDuplicateFieldAlternateNamesMap`: the same alternate-spelling bypass occurs for a map field (`int32Map` vs `int32_map`), producing a silently overwritten map entry (`{3: 4}`) instead of a parse error.

Both cases confirm: the "duplicate key" security/uniqueness check is bypassed whenever the same field is referenced through two different valid textual representations, exactly mirroring the reported class of bug — comparing two different formats of the same semantic entity defeats the intended validation check.
