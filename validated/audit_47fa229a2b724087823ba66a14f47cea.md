## Finding: `VWAPOracle.recordSpread` conflates unrelated input/output tokens into a single spread bucket [1](#0-0) 

### Summary
`VWAPOracle.recordSpread` is documented and designed to track "cumulative weighted average spreads for **same-token** swaps" (i.e., the same asset bridged cross-chain), but the contract never verifies that `inputs[i].token == outputs[i].token` before mixing their amounts into a single accounting bucket keyed only by the input token.

### Finding Description
`IntentGatewayV2.fillOrder` calls the oracle unconditionally after every fill with the raw, unpaired arrays `order.inputs` and `options.outputs`: [2](#0-1) 

Nothing in `_fillSameChain` or `_fillCrossChain` enforces that leg `i`'s input token equals leg `i`'s output token — only that `options.outputs[i].token` matches `order.output.assets[i].token` (the committed order's own output leg), which says nothing about the relationship between the input and output assets of that leg: [3](#0-2) [4](#0-3) 

Inside `recordSpread`, the bucket key is derived solely from `inputToken`, while the delta used to update that bucket is computed from `outputToken`'s normalized amount: [5](#0-4) 

If a user places (and a solver fills) an order whose leg has `input.token = TokenA` and `output.token = TokenB` (a genuine cross-asset swap, not a same-asset cross-chain repeg), `recordSpread` will:
- Key the update to `_tokenSpreads[sourceChainHash][TokenA]` (line 211),
- but compute the "spread" as the normalized difference between `TokenB`'s output amount and `TokenA`'s input amount (lines 197–207).

This pollutes/aliases `TokenA`'s accumulated VWAP bucket with price movement that has nothing to do with `TokenA` alone — violating the stated invariant that spread accounting must remain injective and same-token per `(sourceChain, token)`. Notably, the off-chain SDK strategy in `fx.ts` explicitly distinguishes and gates this case with `isSameTokenPair(leg.pair)` before doing same-token spread accounting, confirming the on-chain contract is missing an equivalent guard: [6](#0-5) 

Separately, for same-chain **partial fills**, `recordSpread` is fed `order.inputs` (the order's total/full committed input amount) rather than the actual partial `escrowedInputs` computed inside `_fillSameChain`, while `options.outputs` reflects only the solver's amount for that particular partial call: [7](#0-6) 

This means the volume/amount basis used for VWAP weighting during a partial fill does not correspond to the amount actually escrowed/released in that call, compounding the bucket-integrity problem across a partial-then-replay/partial-then-complete sequence.

### Impact Explanation
An unprivileged user can place an order with mismatched input/output tokens per leg, and any solver filling it (unprivileged) will cause the oracle's spread bucket for the input token to be corrupted with unrelated cross-asset price data. Whether this rises to direct fund loss depends on downstream consumers of `VWAPOracle.spread()`/`decimals()` — within the reviewed contracts, `spread()` is a pure view getter not consumed by `IntentGatewayV2` itself to gate amounts, beneficiaries, or rewards. I could not find, within the code retrieved in this session, an on-chain caller that uses `spread()` to directly move funds; it appears to be consumed off-chain (e.g., by the `fx.ts` solver strategy) for pricing decisions. This limits the finding to a state/data-integrity break of the documented invariant rather than a directly provable on-chain fund-movement exploit, based on what I was able to verify.

### Likelihood Explanation
High reachability: any user can construct an order with `input.token != output.token` per leg (nothing rejects this), and any solver willing to fill it triggers the corruption automatically as part of normal `fillOrder` execution — no privileged or malicious-infrastructure assumptions required.

### Recommendation
- In `VWAPOracle.recordSpread`, require `inputToken == outputToken` per leg (or key the bucket by an explicit `(inputToken, outputToken)` pair) and skip/reject legs where they differ, matching the interface's documented "same-token" assumption.
- In `IntentGatewayV2.fillOrder`, pass the actual per-fill escrowed/released amounts (e.g., `escrowedInputs`/`outputFills` for partial same-chain fills) to `recordSpread` instead of the order's full committed `order.inputs`, so partial fills don't corrupt the VWAP volume basis.

### Proof of Concept
1. Admin configures `decimals(sourceChain, TokenA)` in `VWAPOracle`.
2. User places an order with `order.inputs[0] = {token: TokenA, amount: 1000e18}` and `order.output.assets[0] = {token: TokenB, amount: 1000e6}` (a legitimate cross-asset swap leg — nothing prevents this at order creation).
3. Solver calls `fillOrder` with `options.outputs[0] = {token: TokenB, amount: 1000e6}`; fill succeeds normally.
4. `fillOrder` invokes `recordSpread(commitment, order.source, order.inputs, options.outputs)`, which updates `_tokenSpreads[sourceChainHash][TokenA]` using `TokenB`'s normalized output amount vs `TokenA`'s normalized input amount — mixing TokenB's exchange-rate data into TokenA's dedicated bucket, verifiable by calling `oracle.spread(sourceChain, TokenA)` and observing it reflects the unrelated TokenA/TokenB cross rate rather than any TokenA-only same-asset spread.
