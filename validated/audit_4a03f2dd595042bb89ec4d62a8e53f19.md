### Title
Unrestricted `WombatPoolHelperV2.depositFor()` allows force-staking dust into contract addresses with no withdrawal path, permanently freezing accrued rewards - (File: wombat/WombatPoolHelperV2.sol)

### Summary
`WombatPoolHelperV2.depositFor(uint256 _amount, address _for)` has no access control (unlike `SimplePoolHelper.depositFor`, which is gated by `onlyAuthorized`), so any unprivileged caller can force a deposit crediting an arbitrary `_for` address in `MasterMagpie`. Because `WombatPoolHelperV2.withdraw()` only supports `msg.sender`-based withdrawal (no `withdrawFor`/delegated path), if `_for` is a contract that cannot itself call `withdraw()` (e.g. `WombatBribeManager` or a vlMGP-locked contract with no generic call-execution capability), the staked position and any WOM rewards accrued to it in the `BaseRewardPool` become permanently unclaimable.

### Finding Description
`WombatPoolHelperV2.depositFor()` is declared external with no modifier: [1](#0-0) 
It pulls `depositToken` from `msg.sender`, then calls internal `_deposit(_amount, 0, _for, address(this))`, which deposits into `WombatStaking` and then stakes the resulting receipt token into `MasterMagpie` on behalf of `_for`: [2](#0-1) [3](#0-2) 
This calls `MasterMagpie.depositFor(stakingToken, amount, _for)`, gated only by `_onlyPoolHelper`, which is satisfied because the caller is a registered pool helper contract itself (not the depositing EOA): [4](#0-3) 
This credits `_for`'s `UserInfo.amount` in `MasterMagpie` and stakes into the reward pool, meaning `_for` starts accruing rewards regardless of whether `_for` requested it.

By contrast, `SimplePoolHelper.depositFor()` explicitly requires `onlyAuthorized`: [5](#0-4) 
`WombatPoolHelperV2` has no equivalent restriction, confirming the missing check is a code defect rather than intended design.

Critically, the only exit path, `WombatPoolHelperV2.withdraw()`, hardcodes `msg.sender` as both the withdrawer and reward recipient — there is no `withdrawFor()` analog that lets a third party trigger withdrawal for an arbitrary `_for`: [6](#0-5) 
So the only way to unwind a position credited to `_for` is for `_for` itself to call `withdraw()`. If `_for` is a contract without a way to invoke arbitrary external calls (e.g. `WombatBribeManager`, which has no generic "execute" function, or any non-EOA/non-multisig contract), that stake — and any WOM/bonus rewards it accrues via `BaseRewardPool` — can never be withdrawn or claimed.

### Impact Explanation
This is a permanent freezing-of-funds / unclaimed-yield vulnerability, not theft: an attacker can force a (typically small/dust) deposit into `_for`'s stake, after which that principal and any future/accrued rewards routed to `_for` in the reward pool become permanently locked because no code path exists for a third party to call `withdraw()` on `_for`'s behalf. This matches the "permanent freezing of unclaimed yield" impact class. The scope of loss is bounded by the deposited amount and reward accrual rate for that stake; it does not affect other users' balances or protocol solvency directly.

### Likelihood Explanation
Low capital and effort are required: the attacker only needs enough `depositToken` to pay for a nonzero deposit (dust amounts suffice), and a single transaction calling `depositFor(_amount, _for)` with `_for` set to a known non-EOA-non-callable contract address (e.g. `WombatBribeManager`, or any deployed contract lacking arbitrary-call functionality). The attack is fully repeatable against any qualifying contract address and requires no special permissions, front-running, or governance access — it is directly reachable from an unprivileged EOA's own transaction.

### Recommendation
Add the same `onlyAuthorized` access control used in `SimplePoolHelper` to `WombatPoolHelperV2.depositFor()`, restricting who may deposit on behalf of another address, and/or add a corresponding `withdrawFor`/rescue mechanism that lets an authorized recovery path unwind stakes credited to non-EOA addresses that cannot self-withdraw.

### Proof of Concept
Foundry test outline:
1. Deploy `WombatStaking`, register a pool producing a `WombatPoolHelperV2`, and deploy `MasterMagpie` + `BaseRewardPool` as in the existing test harness.
2. Deploy a minimal "no-call" contract (e.g. one with only a `receive()` and no other functions, simulating `WombatBribeManager`/a locked contract) as `victim`.
3. As an unprivileged EOA, approve `depositToken` and call `WombatPoolHelperV2.depositFor(amount, victim)`.
4. Assert `MasterMagpie.stakingInfo(stakingToken, victim).depositAmount == amount` (stake was force-credited).
5. Advance time/blocks so `BaseRewardPool` accrues WOM rewards to `victim`; assert `pendingTokens`/`earned(victim) > 0`.
6. Attempt to call `WombatPoolHelperV2.withdraw()` from `victim` (via low-level call) — expect it to revert or be impossible since `victim` has no logic to invoke it, and no `withdrawFor` exists for a third party to trigger it.
7. Assert the stake and its accrued rewards remain permanently locked (no code path drains them to any claimable address).
