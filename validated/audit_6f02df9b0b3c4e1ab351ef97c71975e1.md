### Title
JSON parser duplicate-field detection can be bypassed using alternate field-name spellings, allowing silent overwrite/oneof-integrity violation - (File: `python/google/protobuf/json_format.py`)

### Summary
The external report describes a WAF rule bypass where a security-relevant matcher (SQL-injection detection) compares literal syntax rather than canonical semantic meaning, letting `{`a`b}` evade detection because it's an alternate syntactic form of the same underlying call. The transferable invariant is: *a validator that is supposed to reject "the same target reached twice" must compare targets by resolved identity, not by the surface token used to reach them*. In the pure-Python ProtoJSON parser, the duplicate-field check in `_Parser._ConvertFieldValuePair` performs exactly this class of mistake: it tracks JSON object keys as raw strings (`names.append(name)` / `if name in names`) instead of tracking the resolved `FieldDescriptor`. Since a field can be addressed by more than one JSON key spelling (its `json_name` e.g. `int32Value`, and its raw proto `name` e.g. `int32_value`, both resolved via `fields_by_json_name.get(name)` / `message_descriptor.fields_by_name.get(name)`), an attacker-supplied payload containing both spellings for the same field bypasses the duplicate-key rejection and both values are applied, with the second silently overwriting the first.

### Finding Description
`_ConvertFieldValuePair` in [1](#0-0)  resolves each JSON key to a `field` descriptor through two independent lookup tables (`fields_by_json_name` and `message_descriptor.fields_by_name`), meaning the same underlying field can be reached through two different literal key strings. The duplicate check that follows, however, operates purely on the literal string form of the key: [2](#0-1)  only appends/tests `name` (the exact JSON key text), never the resolved `field` object. This is confirmed as a known behavioral gap by the project's own test, `testDuplicateFieldAlternateNames`, which documents that sending both `int32Value` and `int32_value` for the same field is *not* rejected and the second value silently wins: [3](#0-2) . The oneof-guard immediately below has the same weakness pattern (it does track `oneof_name`, which is at least semantic, but the base per-field check at line 663 is purely syntactic) — see [4](#0-3) .

This is the direct analog of the CVE's invariant failure: the "reject duplicate/conflicting input for the same target" check is implemented as a literal-string comparison instead of a comparison over the resolved semantic target, so an attacker who knows an alternate valid encoding of the same target (alternate JSON key spelling, just as `{`a`b}` is an alternate call syntax for the same function) defeats the check entirely.

Note this is isolated to the pure-Python `_Parser` implementation. The C++/upb JSON parser used by the default (and C++-accelerated Python) backend performs duplicate detection correctly by tracking already-seen state per resolved `Field`, not per string key — see `Traits::RecordAsSeen`/`SeenState` handling in [5](#0-4) , so this analog does not transfer to the upb backend.

### Impact Explanation
This is an integrity/consistency violation, not memory corruption. A consuming application that relies on the parser's documented behavior of rejecting a JSON payload that "should not have multiple ... fields" (per the raised `ParseError` message text itself) may treat a successfully-parsed message as having a single, unambiguous field assignment per key. An attacker able to submit ProtoJSON to such an application (e.g., anywhere spec compliance/duplicate-key rejection is used as a signal of well-formed/non-ambiguous input, similar to how the CRS bypass defeats a security gate) can silently smuggle two conflicting values for the same field past that gate, with the last one silently winning — a request/response or authorization-relevant field could be set differently than a naive readers/validators of the raw JSON text would expect (classic "parser differential" / key-confusion class of issue). It does not by itself cause disclosure or memory-safety impact, warranting Medium rather than Critical/High severity.

### Likelihood Explanation
High likelihood of triggering: this only requires calling the standard public `json_format.Parse` API with a bounded, well-formed JSON payload containing two keys that map to the same field (its `json_name` and its snake_case proto name), which is fully attacker-controlled and requires no privileged access. It is reachable through the pure-Python implementation path, which remains in use whenever the C++ implementation is unavailable/not selected.

### Recommendation
Track already-seen fields in `_ConvertFieldValuePair` by resolved field identity (e.g., `id(field)` or the `FieldDescriptor` itself) rather than by the raw JSON key string, so that all alternate spellings addressing the same field are correctly detected as duplicates and rejected, consistent with the C++/upb implementation's behavior.

### Proof of Concept
Using the pure-Python JSON parser:
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2

msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # silently overwritten; no duplicate-key ParseError raised
```
This matches the project's own regression test [3](#0-2) , which documents the exact bypass and asserts the resulting (undesired) overwrite rather than an exception, confirming the check at [2](#0-1)  fails to catch alternate-spelling duplicates.
