### Title
Unhandled AssertionError in `compute_spend_hints_and_additions` on malformed CREATE_COIN condition - ([File: chia/wallet/util/compute_hints.py])

### Summary
`compute_spend_hints_and_additions()` blindly asserts that the puzzle-hash argument of a `CREATE_COIN` condition is an atom. A coin spend whose puzzle can emit a `CREATE_COIN` condition with a non-atom (cons-pair) second argument causes an uncaught `AssertionError` instead of a handled `ValueError`/`ValidationError`, which is the same bug class as CVE-2018-20426 (missing null/None check before dereferencing a parsed value in `newVar3`, causing a crash instead of a graceful decode failure).

### Finding Description
`compute_spend_hints_and_additions` runs an untrusted `CoinSpend`'s puzzle/solution and iterates the returned conditions to compute hints for wallet-side coin tracking: [1](#0-0) 

For every `CREATE_COIN` condition it does:
```
rf = condition.at("rf").atom
assert rf is not None
```
`condition.at("rf")` returns the second element of the condition list (the intended puzzle hash). `.atom` is `None` whenever that element is itself a pair/list rather than a bytes atom (CLVM makes no guarantee about this — a spender fully controls the puzzle that produces the condition list, and CLVM conditions are not shape-checked before this code runs). This is exactly the same defect class as the libming NULL-pointer dereference: an assumption that a parsed value is present/of the expected shape, enforced with an `assert` rather than a recoverable check, so a crafted input flips it into an unhandled crash path.

Because it's a Python `assert` (not a `raise ValidationError(...)`), it is NOT caught by the narrow `except ValidationError` / `except ValueError` handlers that several call sites rely on:

- `Offer.__post_init__` catches `ValidationError` and generic `ValueError`/`Exception` around the same call, so it happens to swallow the `AssertionError` there via the trailing bare `except Exception: continue`: [2](#0-1) 

- `DIDWallet.identify()` calls it with **no exception handling at all**: [3](#0-2) 

`DIDWallet.identify` is invoked from `WalletStateManager.determine_coin_type`/`_add_coin_state` while processing incoming coin states/spends for a locally-tracked DID puzzle hash — i.e., triggered by data derived from a coin spend that an attacker fully controls the puzzle for (any spend that creates a coin hinted/paid to a puzzle hash the wallet is watching, e.g. as part of a DID-related interaction, offer settlement, or NFT/DID transfer flow the wallet is asked to process).

### Impact Explanation
An unhandled `AssertionError` thrown deep inside wallet coin-state processing aborts that code path with an unexpected exception type. Depending on the call site:
- In `Offer` construction, the exception is unintentionally swallowed by a catch-all `except Exception: continue`, silently producing incomplete `_additions`/`_hints` data for that coin spend — this can make the wallet miscompute additions/hints for an offer (a “coin-set divergence” style issue local to wallet state, since the crafted spend is simply skipped instead of properly rejected or accounted for).
- In `DIDWallet.identify` (and any other unguarded caller), the `AssertionError` propagates out of an `async` handler in the coin-state sync pipeline. This is a spend-triggered failure that disrupts processing of that coin/wallet sync step (a localized transaction-processing halt for the affected wallet flow) rather than a full-node consensus crash, since chia_rs performs the actual consensus-level condition validation independently of this Python helper.

Overall this is a reachable DoS/robustness bug triggerable by a single crafted coin spend a wallet is asked to evaluate (e.g., via an offer, a DID/NFT related coin the wallet tracks), matching "spend-triggered transaction-processing halt" from the validation criteria, though the blast radius is the wallet's own state-manager processing rather than full-node consensus/mempool admission.

### Likelihood Explanation
Any unprivileged actor who can get a crafted `CoinSpend` in front of a chia wallet's coin-state processing (e.g., by directing a payment/coin to a puzzle hash the victim wallet watches, or via an offer) can trigger this by simply having their puzzle emit `(CREATE_COIN (some_pair) amount)` instead of `(CREATE_COIN atom_puzzle_hash amount)`. No special privileges, signing keys, or malicious peer/node behavior are required — a standard spend bundle with an adversarial puzzle suffices.

### Recommendation
Replace the `assert rf is not None` in `compute_spend_hints_and_additions` with an explicit check that raises `ValidationError(Err.INVALID_CONDITION, ...)` (mirroring the handling already used for cost-exceeded conditions in the same function), and audit/wrap all call sites (especially `DIDWallet.identify`, `WalletStateManager` coin-state handlers, `trade_manager.py`) to catch this new exception type consistently, the same way `Offer.__post_init__` already does for `ValidationError`/`ValueError`.

### Proof of Concept
1. Build a puzzle whose only output is a non-standard condition list where the CREATE_COIN puzzle-hash argument is a cons pair, e.g. CLVM: `(list (list 51 (c 1 2) 100))` (opcode 51 = CREATE_COIN, second arg `(c 1 2)` is a pair, not an atom).
2. Construct a `CoinSpend` using this puzzle and a coin whose puzzle hash matches it, with any solution.
3. Feed this `CoinSpend` into `compute_spend_hints_and_additions` directly, or trigger it indirectly by:
   - constructing a `WalletSpendBundle`/`Offer` containing this spend and observing the swallowed-then-inconsistent `_additions`/`_hints` state, or
   - simulating wallet sync delivering this coin spend as the parent spend of a DID-tracked coin, causing `DIDWallet.identify()` to raise `AssertionError` uncaught (verifiable by unit-testing `chia.wallet.did_wallet.did_wallet.DIDWallet.identify` with such a crafted `coin_spend`).
4. Confirm the raised exception is `AssertionError` rather than a handled `ValidationError`, demonstrating the missing-check/crash-instead-of-graceful-failure defect analogous to CVE-2018-20426.
