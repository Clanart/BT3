## Title
UTF-8 encode/size mismatch on unpaired-surrogate strings silently corrupts serialized Protobuf output - (File: `java/core/src/main/java/com/google/protobuf/CodedOutputStream.java`)

## Summary
The external report describes ASP.NET Core's `TextEncoder.EncodeCore` miscalculating the *encoded byte length* for certain Unicode inputs, so a pre-computed size does not match what is actually written, corrupting output and causing a DoS. The Protobuf Java serializer contains an analogous invariant break: `CodedOutputStream.computeStringSizeNoTag()` (which calls `Utf8.encodedLength()`) can compute a different byte length than what `Utf8.encode()` / `CodedOutputStream.writeStringNoTag()` actually writes for strings containing unpaired UTF-16 surrogates, producing a corrupted, non-length-matching Protobuf wire stream rather than a rejected input.

## Finding Description
`Utf8.encodedLength(String)` is used by `CodedOutputStream.computeStringSizeNoTag` to precompute the varint length prefix for a string field: [1](#0-0) 

When it encounters characters ≥ `0x800`, it delegates to `encodedLengthGeneral`, and if that throws `UnpairedSurrogateException` it falls back to the JDK's own `string.getBytes(StandardCharsets.UTF_8).length` (which replaces unpaired surrogates with `U+FFFD`, 3 bytes each): [2](#0-1) 

Separately, the actual byte-writing paths (`UnsafeProcessor.encodeUtf8` / `encodeUtf8Internal`, used by `CodedOutputStream`'s fast-path writers) handle unpaired surrogates by falling back to `encodeUtf8Naive`, which also uses `String.getBytes(UTF_8)`: [3](#0-2) 

However, `CodedOutputStream.writeStringNoTag` implementations (e.g. the `ByteOutput`/streaming variant) contain a *fast path* that assumes the varint size computed from `value.length()` (UTF-16 code unit count) will match the actual encoded length, and only falls back to the exact `Utf8.encodedLength()`/full re-encode path if the min/max varint-size brackets disagree: [4](#0-3) 
and the allocation-free buffer-writing variant that writes directly into the pre-sized output buffer at a fixed offset determined by `computeUInt32SizeNoTag(value.length())`: [5](#0-4) 

The project's own test explicitly documents that this class of input is not rejected and does corrupt output — the invalid strings (lone high/low surrogates) are fed through `computeStringSizeNoTag` and `writeStringNoTag`, with a TODO acknowledging the bug: [6](#0-5) 

This is the direct structural analog of the CVE-2017-0247 root cause: a length-precomputation routine (`TextEncoder.EncodeCore` / `Utf8.encodedLength`) that miscounts bytes for a special-case code unit range (4-byte/non-character range vs. lone UTF-16 surrogates), while the actual writer encodes differently, breaking the invariant that "declared length == bytes actually written."

## Impact Explanation
Protobuf's wire format is length-prefixed: a length/value mismatch between the varint size prefix and the real payload bytes corrupts the message boundary for every subsequent field in the stream, and for streaming/multi-message contexts it corrupts framing for anything appended after. This is an availability/integrity issue on the producer side — an application that serializes attacker-influenced strings containing lone surrogates (e.g. from JSON/JS clients, where lone surrogates are common due to independent encoding of UTF-16 code units) can emit invalid or truncated protobuf payloads that downstream consumers fail to parse or parse incorrectly, i.e., a data-integrity/DoS analog to the .NET CVE, not memory corruption. Severity is bounded because Protobuf's own decoders reject genuinely malformed UTF-8 (`DecodeUtil`, `VerifyUTF8` in C++/`utf8_range`), so the primary externally observable effect is corrupted/rejected re-serialized output rather than remote code execution.

## Likelihood Explanation
Lone (unpaired) UTF-16 surrogates in Java `String` values are a realistic, attacker-reachable input class: they arise from JSON `\uD800`-`\uDFFF` escapes not paired correctly, from truncated UTF-16 decoding, or from direct construction (`new String(char[])`). The test in this repository (`CodedOutputStreamTest.testSerializeInvalidUtf8`) constructs exactly this scenario and, per its own TODO, does not assert correctness — only that no assertion is currently made confirms the mismatch is not yet fixed/enforced in this checkout, but I could not fully trace whether every `writeStringNoTag` variant (`CodedOutputStreamWriter`/streamed vs. array-backed) hits the divergent fallback in the same way for all surrogate positions; verifying an exact byte-level mismatch would require running the existing test with an assertion, which I was not able to execute in this environment.

## Recommendation
Make `Utf8.encodedLength()` and every `encodeUtf8`/`encodeUtf8Naive`/`encodeUtf8Internal` path use one single, shared, and provably identical replacement-character policy for unpaired surrogates (or, preferably, reject them outright, consistent with how the decoder side rejects invalid UTF-8) so the invariant `computeStringSizeNoTag(s) == writeStringNoTag(s).bytesWritten` always holds. At minimum, strengthen `CodedOutputStreamTest.testSerializeInvalidUtf8` (currently just a TODO) into a hard assertion that the written byte count always equals the precomputed size for all unpaired-surrogate fixtures, across every `Processor`/`Coder` variant.

      if (Utf8.ENCODES_VIA_INTERMEDIATE_ARRAY) {

        writeUInt32NoTag(encoded.length);
        write(encoded, 0, encoded.length);

        // the smallest prefix it could need, encode, and shift the bytes right if the real length

          position = oldPosition + minLengthVarIntSize;

          writeUInt32NoTag(length);

    @Override
    public void writeStringNoTag(String value) throws IOException {
      // UTF-8 byte length of the string is at least its UTF-16 code unit length (value.length()),
      // and at most 3 times of it. We take advantage of this in both branches below.
      final int maxLength = value.length() * Utf8.MAX_BYTES_PER_CHAR;
      final int maxLengthVarIntSize = computeUInt32SizeNoTag(maxLength);

      // If we are streaming and the potential length is too big to fit in our buffer, we take the
      // slower path.
      if (maxLengthVarIntSize + maxLength > limit) {
        // Allocate a byte[] that we know can fit the string and encode into it. String.getBytes()
        // does the same internally and then does *another copy* to return a byte[] of exactly the
        // right size. We can skip that copy and just writeRawBytes up to the actualLength of the
        // UTF-8 encoded bytes.
        final byte[] encodedBytes = new byte[maxLength];
        int actualLength = Utf8.encode(value, encodedBytes, 0, maxLength);
        writeUInt32NoTag(actualLength);
        writeLazy(encodedBytes, 0, actualLength);
        return;
      }

      // Fast path: we have enough space available in our buffer for the string...
      if (maxLengthVarIntSize + maxLength > limit - position) {
        // Flush to free up space.
        doFlush();
      }

      // Optimize for the case where we know this length results in a constant varint length as
      // this saves a pass for measuring the length of the string.
      final int minLengthVarIntSize = computeUInt32SizeNoTag(value.length());
      int oldPosition = position;
      final int length;
      try {
        if (minLengthVarIntSize == maxLengthVarIntSize) {
          position = oldPosition + minLengthVarIntSize;
          int newPosition = Utf8.encode(value, buffer, position, limit - position);
          // Since this class is stateful and tracks the position, we rewind and store the
          // state, prepend the length, then reset it back to the end of the string.
          position = oldPosition;
          length = newPosition - oldPosition - minLengthVarIntSize;
          bufferUInt32NoTag(length);
          position = newPosition;
        } else {
          length = Utf8.encodedLength(value);
          bufferUInt32NoTag(length);
          position = Utf8.encode(value, buffer, position, length);
        }
        totalBytesWritten += length;
      } catch (ArrayIndexOutOfBoundsException e) {
        throw new OutOfSpaceException(e);
      }
    }
