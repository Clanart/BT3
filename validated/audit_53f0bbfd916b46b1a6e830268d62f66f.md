### Title
Unauthenticated aggregate Schnorr signatures can be forged through deterministic per-signature weights - (File: `crypto/schnorr/src/aggregate.rs`)

### Summary
`SchnorrAggregate::verify` derives each per-signature weight only from the ordered list of challenges. Because the weights do not bind the public keys or nonce points, an attacker can algebraically cancel the verification error of one forged signature against another and submit an aggregate with `s = 0` that verifies for arbitrary `(key, challenge)` pairs.

### Finding Description
The verifier calculates `z_i = weight(challenges)` and checks:

```text
Σ z_i * R_i + Σ z_i * c_i * A_i - s * G = identity
```

where `A_i` is the claimed public key and `c_i` its supplied challenge. The aggregate format accepts attacker-controlled `Rs` and `s` from `SchnorrAggregate::read`. Since `z_i` is deterministic once the challenges are selected and does not cover `R_i` or `A_i`, the adversary can choose nonce points that make the per-signature residuals cancel exactly.

Relevant code:

- `SchnorrAggregate::read` accepts an attacker-controlled vector of nonce points and scalar without checking that any component signature was previously valid. [1](#0-0) 
- `verify` initializes the aggregation transcript only with the destination tag and `"signatures"` separator. [2](#0-1) 
- Only each challenge is appended before deriving all weights. [3](#0-2) 
- Verification then evaluates the linear combination `z_i R_i + z_i c_i A_i - sG`. [4](#0-3) 
- `weight` deterministically derives the weights from that transcript and can be computed offline by the verifier’s caller or attacker. [5](#0-4) 

### Impact Explanation
An attacker can produce a `SchnorrAggregate` that `verify` accepts as evidence that signatures exist for arbitrary supplied public keys and challenges, even though none of the component Schnorr signatures are valid. Any in-scope consumer that uses the aggregate verifier to accept signatures or proofs can therefore accept a forged aggregate for public inputs controlled by an unauthenticated party.

This is not merely signature malleability: the constructed aggregate does not require knowledge of any victim private key, nonce, or valid component signature.

### Likelihood Explanation
The attack requires only the ability to cause a verifier to process an attacker-supplied aggregate over attacker-selected public keys, challenges, or messages mapped to challenges. The construction is deterministic and works whenever the selected residual scalar avoids degenerate edge cases; no race, colluding validator, leaked key, malicious node, or probabilistic success condition is required.

### Recommendation
Bind every variable component of each component signature into its aggregation weight. At minimum, derive each weight from the ordered tuple of:

- the signature index,
- public key,
- challenge,
- nonce point,
- and the complete list of public keys, challenges, and nonce points.

Alternatively, derive one commitment over the full aggregate statement first and then derive independent nonzero per-signature weights from that commitment. Reject zero or identity nonce points where the ciphersuite’s semantics do not already reject them, and add a regression test that serializes the two-signature forgery described below and confirms verification fails.

### Proof of Concept
For two arbitrary public-key/challenge pairs `(A1, c1)` and `(A2, c2)`:

1. Compute the verifier’s deterministic weights `z1` and `z2` by replaying the same `DigestTranscript` challenge sequence used by `verify`.
2. Select any nonzero scalar `x`.
3. Set:

```text
R1 = xG - c1A1
R2 = -(z1 / z2)xG - c2A2
s  = 0
```

4. Submit `SchnorrAggregate { Rs: [R1, R2], s }` for `(keys_and_challenges = [(A1, c1), (A2, c2)])`.

The verifier computes:

```text
z1(R1 + c1A1) + z2(R2 + c2A2) - 0G
= z1(xG) + z2(-(z1 / z2)xG)
= z1xG - z1xG
= identity
```

Thus verification succeeds despite neither component representing a valid Schnorr signature for its corresponding key and challenge.

// Returns a unbiased scalar weight to use on a signature in order to prevent malleability
fn weight<D: Send + Clone + SecureDigest, F: PrimeField>(digest: &mut DigestTranscript<D>) -> F {
  let mut bytes = digest.challenge(b"aggregation_weight");
  debug_assert_eq!(bytes.len() % 8, 0);
  // This should be guaranteed thanks to SecureDigest
  debug_assert!(bytes.len() >= 32);

  let mut res = F::ZERO;
  let mut i = 0;

  // Derive a scalar from enough bits of entropy that bias is < 2^128
  // This can't be const due to its usage of a generic
  // Also due to the usize::try_from, yet that could be replaced with an `as`
  #[allow(non_snake_case)]
  let BYTES: usize = usize::try_from((F::NUM_BITS + 128).div_ceil(8)).unwrap();

  let mut remaining = BYTES;

  // We load bits in as u64s
  const WORD_LEN_IN_BITS: usize = 64;
  const WORD_LEN_IN_BYTES: usize = WORD_LEN_IN_BITS / 8;

  let mut first = true;
  while i < remaining {
    // Shift over the already loaded bits
    if !first {
      for _ in 0 .. WORD_LEN_IN_BITS {
        res += res;
      }
    }
    first = false;

    // Add the next 64 bits
    res += F::from(u64::from_be_bytes(bytes[i .. (i + WORD_LEN_IN_BYTES)].try_into().unwrap()));
    i += WORD_LEN_IN_BYTES;

    // If we've exhausted this challenge, get another
    if i == bytes.len() {
      bytes = digest.challenge(b"aggregation_weight_continued");
      remaining -= i;
      i = 0;
    }
  }
  res
