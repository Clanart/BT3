### Title
OAuth authorization code can be front-run/replayed to hijack or block a Desktop sign-in — (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
The report's broken invariant is: *a one-time-use, signature-bound authorization artifact (ERC-20 `permit()` signature) can be consumed by an unprivileged third party before the legitimate actor, causing the legitimate flow to revert (or worse, letting the attacker capture the effect of the artifact)*. The GitHub Desktop analog is the OAuth "web application flow" used for sign-in: GitHub issues a single-use `code` delivered to the app via a custom URL scheme deep link (`x-github-client://oauth?code=...&state=...`), and whichever party first POSTs that `code` (plus the bundled `client_id`/`client_secret`) to `/login/oauth/access_token` "wins" — exactly like whichever address first submits a given `permit()` signature wins.

### Finding Description
Desktop's sign-in flow:
1. `SignInStore.authenticateWithBrowser` generates a CSRF `state` and opens the OS browser to GitHub's authorize URL via `getOAuthAuthorizationURL` [1](#0-0) .
2. GitHub redirects the browser to the app's registered custom protocol, delivering a one-time-use `code` and the `state`, which `parseAppURL` extracts into an `IOAuthAction` [2](#0-1) .
3. `SignInStore.resolveOAuthRequest` validates only that `state` matches the value stored for the *current* sign-in session, then calls `requestOAuthToken(endpoint, action.code)` [3](#0-2) .
4. `requestOAuthToken` exchanges the code for an access token using the app-bundled `client_id`/`client_secret` [4](#0-3) . The client secret is not a per-user/per-request secret — it is compiled into every distributed binary as `__OAUTH_SECRET__`, with a hardcoded fallback (`devClientSecret`) checked into source [5](#0-4) .

The state check in `resolveOAuthRequest` only defends against a forged callback carrying an *unknown* `state` (classic CSRF) — it does nothing once the *genuine* `code`/`state` pair from the real redirect is observed or captured by another local process/app before Desktop's own token exchange completes. Since GitHub invalidates an OAuth `code` after first redemption, whichever caller reaches `login/oauth/access_token` first "wins" the exchange:
- If the attacker redeems it first, Desktop's own `requestOAuthToken` call fails, `resolveOAuthRequest`'s `if (token)` branch is not taken, and `onAuthError` fires — the direct analog of `PermitSubmitterHook.compose()` reverting because the signature was already consumed [6](#0-5) .
- Because the "secret" half of the exchange is not actually secret (bundled in the binary), an attacker who intercepts the code does not even need a server-side secret of their own — the same `client_id`/`client_secret` used by Desktop is sufficient to complete the redemption and obtain a valid `access_token` bound to the victim's GitHub account, turning a race/DoS primitive into an account-binding compromise, which matches the "unauthorized OAuth or account binding" impact category.

Unlike the smart-contract case, exploiting this requires an attacker to actually observe or race the deep-link callback (e.g., a second application registered for the same custom URL scheme, or another mechanism capable of intercepting the OS-level `x-github-client://oauth?...` invocation) — I could not verify from local code whether Desktop's protocol registration (`setAsDefaultProtocolClient` in `app/src/main-process/main.ts`) includes any hardening against scheme-hijacking by other installed applications, so the practicality of capturing the redirect itself is uncertain from the code alone.

### Impact Explanation
If the code is intercepted and redeemed first by another party, the legitimate user's sign-in attempt silently fails (`onAuthError`), and the intercepting party obtains a live GitHub OAuth token scoped to the victim's account — enabling unauthorized access to the victim's repositories/API on their behalf. This satisfies the "unauthorized OAuth or account binding" and "credential/token exfiltration" valid-impact categories.

### Likelihood Explanation
Medium/uncertain. The `state` value is a `crypto.randomUUID()` and is not guessable, so a blind attacker cannot forge the callback [7](#0-6) . The attack requires the attacker to actually see the genuine `code`/`state` pair as it transits the OS (e.g., another locally-registered handler for the same custom scheme, or a race enabled by protocol-handler ambiguity) rather than any user misstep — this is consistent with the "attacker controls ... a link or deep link" category, but I cannot confirm from the indexed code whether Desktop's protocol registration is exclusive enough to make interception practical on all platforms.

### Recommendation
- Adopt PKCE (`code_verifier`/`code_challenge`) for the OAuth flow so that redeeming the code requires a per-flow secret that never leaves the process, similar to wrapping `permit()` in try/catch — it removes the "whoever submits first wins with just the public artifact" property.
- Treat the bundled `client_secret` as non-secret and design the exchange so possession of the code alone (plus the public client_id) is insufficient, consistent with the report's core recommendation to not let a race on a public one-time artifact determine an outcome.
- On failure of `requestOAuthToken` due to an already-used code, do not just call `onAuthError` — detect and log/report this distinct failure mode so it can be monitored as a possible interception attempt.

### Proof of Concept
1. User starts GitHub Enterprise/`.com` sign-in in Desktop; Desktop opens the browser to the authorize URL with `state = S` [1](#0-0) .
2. User authorizes; GitHub redirects to `x-github-client://oauth?code=C&state=S`.
3. An attacker-controlled process capable of observing this deep link (e.g., a competing handler for the same custom scheme) races to POST `code=C` to `/login/oauth/access_token` with the same public `client_id`/`client_secret` before Desktop's own `requestOAuthToken(endpoint, C)` call completes [4](#0-3) .
4. GitHub invalidates `C` after the first redemption. Desktop's own call now fails, `resolveOAuthRequest` falls into the `else` branch and calls `onAuthError` [8](#0-7)  — the sign-in silently fails from the user's perspective, while the attacker holds a valid access token for the victim's account.

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
