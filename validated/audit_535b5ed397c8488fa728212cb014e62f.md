### Title
`ReceivedOutput::read` accepts a forged offset binding — attacker claims foreign outputs as spendable by the threshold key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` pairs a `Scalar` offset with a Bitcoin `TxOut`/`OutPoint`. The intended invariant — that `output.script_pubkey` is the P2TR script of `key + offset*G` — is only ever established inside `Scanner::scan_transaction`, which looks the script up in the pre-registered `scripts` map. `ReceivedOutput::read` deserializes all three fields from untrusted bytes with no consistency check, so any caller that ingests a serialized `ReceivedOutput` from an untrusted party (the explicitly in-scope `read` API) will accept an output whose declared spending key does not match the actual script on-chain — a direct analog of an IDOR/object-overwrite: the attacker supplies an identifier (the outpoint) plus an authorization claim (the offset) that is never verified against each other.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`:

- `ReceivedOutput` stores `offset`, `output`, `outpoint` (lines 89–97).
- `Scanner::scan_transaction` is the only place the binding is enforced: it looks up `output.script_pubkey` in `self.scripts` and attaches the *registered* offset (lines 199–213).
- `ReceivedOutput::read` accepts arbitrary bytes: `Secp256k1::read_F` for the offset and consensus decoding for the `TxOut`/`OutPoint` (lines 122–133). There is no group key available to `read` and no re-derivation of `p2tr_script_buf(key + GENERATOR * offset)` to compare against `output.script_pubkey`.

An unprivileged attacker can therefore serialize a `ReceivedOutput` that references a real on-chain outpoint they own (or any outpoint) while claiming `offset = 0` — i.e., claiming it pays to the group's external address. Downstream, `SignableTransaction`/`TransactionSignMachine` signs the input with `ThresholdKeys` offset by `offset` (`networks/bitcoin/src/wallet/send.rs`, sign path via `taproot_key_spend_signature_hash` with `Prevouts::All`), producing a signature valid for `key + offset*G`, which is not the key the output's script actually commits to.

### Impact Explanation
Any integrator that consumes serialized `ReceivedOutput`s (e.g., outputs relayed between processors or loaded from storage populated by an untrusted source) can be made to believe funds were received to the threshold wallet when they were not — the "funds reported received that are not spendable" outcome. The honest group then builds a transaction spending this input; the resulting signature verifies against `key + offset*G` but not the attacker-controlled script, so the input is unspendable. This can be used to inflate credited balances, poison the input set (any transaction including the forged input is invalid in full because `Prevouts::All` commits to it), and waste/donated-fee DoS the wallet.

### Likelihood Explanation
Reachable entirely with public inputs: the attacker only needs to produce bytes through `ReceivedOutput::read` — no keys, no validator status, no collusion. Success depends on the deployment actually deserializing `ReceivedOutput`s from an untrusted channel rather than only producing them via a local `Scanner`, but the type exposes `serialize`/`read` precisely for transport/persistence, and nothing in the API warns that `read` skips the scanner's binding check. Exploitation requires no user interaction, matching the report's CVSS profile.

### Recommendation
Either (a) make `ReceivedOutput` unforgeable by construction — remove the public `read`/`write` pair or gate deserialization behind a `Scanner`-associated method that re-verifies `p2tr_script_buf(self.key + GENERATOR * offset) == output.script_pubkey` before returning the object — or (b) add a `ReceivedOutput::verify(&self, key: ProjectivePoint) -> bool` performing that check and document that any `read` result MUST be verified before being fed to `SignableTransaction::new`. At minimum, document on `read` that the offset/script binding is unverified and that `Scanner` is the only trusted constructor.

### Proof of Concept
```rust
// Attacker-controlled input to a victim component that deserializes ReceivedOutputs.
// `key` is the victim group's tweaked external key; `attacker_addr` is a script the
// attacker alone controls (e.g. their own P2TR output already on chain).

let forged = {
    let mut buf = Vec::new();
    // Claim offset 0 => "this pays to `key`"
    buf.extend(Scalar::ZERO.to_bytes().as_ref());
    // Attacker's real TxOut and its real OutPoint (attacker owns/controls it)
    buf.extend(serialize(&TxOut {
        script_pubkey: attacker_script,   // NOT p2tr_script_buf(key).unwrap()
        value: Amount::from_sat(1_000_000),
    }));
    buf.extend(serialize(&real_outpoint));
    buf
};

// Victim side (e.g. processor reconstructing inputs):
let output = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
assert_eq!(output.offset(), Scalar::ZERO);

// The victim treats it as received funds:
let tx = SignableTransaction::new(vec![output], &payments, None, None, fee).unwrap();
// Signing succeeds (it signs under `key + 0*G`), but the input's script_pubkey
// commits to the attacker's key — the transaction can never be valid on-chain.
// The victim credited 1_000_000 sats that are not spendable.
```
The check that would catch this — `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` (the logic in `Scanner::new`/`register_offset`, mod.rs lines 80–86, 180–196) — is absent from `read` (lines 122–133).
