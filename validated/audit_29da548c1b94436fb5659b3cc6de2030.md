### Title
Java `Message.toString()` (and `TextFormat.printer()`) silently emit `debug_redact = true` sensitive field values unredacted by default - (File: `java/core/src/main/java/com/google/protobuf/TextFormat.java`, `java/core/src/main/java/com/google/protobuf/AbstractMessage.java`)

### Summary
Mattermost's audit-log redaction failure (CVE-2023-1831) is a case where a schema/config-declared "this field is sensitive" marker existed, but the code path that produced human-readable/log output for that data did not honor the marker unless a specific, non-default code path was used, so passwords leaked into logs. Protobuf's Java implementation contains a directly analogous gap: schemas can annotate a field `[debug_redact = true]` to declare it sensitive for debug/log output, but the default, most commonly used string-producing API — `Message.toString()` and `TextFormat.printer()` — does **not** apply that redaction. Only the separately-named, opt-in `DebugFormat` class or `ProtobufToStringOutput.callWithDebugFormat()` wrapper actually redact the field, mirroring "redaction requires an extra, non-default configuration knob" — the exact same class of bug as the report.

### Finding Description
`FieldOptions.debug_redact` is the schema-level mechanism protobuf provides for marking a field (e.g. `password`, `password_hash`) as sensitive so that debug/log-facing string dumps redact it (`src/google/protobuf/unittest.proto:2464-2492`, `TestNestedMessageRedaction`/`RedactedFields`) [1](#0-0) .

In the Java implementation, redaction of a `debug_redact` field is gated by an internal `enablingSafeDebugFormat` flag on `TextFormat.Printer`, checked in `shouldRedact()`:
```
private boolean shouldRedact(final FieldDescriptor field, TextGenerator generator) {
  FieldDescriptor.RedactionState state = field.getRedactionState();
  return enablingSafeDebugFormat && state.redact;
}
``` [2](#0-1) 

Three static `Printer` instances exist: `DEFAULT_TEXT_FORMAT` (used by `TextFormat.printer()`), `DEFAULT_DEBUG_FORMAT` (used by `TextFormat.debugFormatPrinter()`, backing `DebugFormat`), and `DEFAULT_FORMAT` (used by `AbstractMessage.toString()` via `getOutputModePrinter()`). Only `DEFAULT_DEBUG_FORMAT` sets `enablingSafeDebugFormat = true`; the other two — including the one backing plain `.toString()` — set it to `false`:
```
private static final Printer DEFAULT_TEXT_FORMAT = new Printer(..., /* enablingSafeDebugFormat= */ false, ...);
private static final Printer DEFAULT_DEBUG_FORMAT = new Printer(..., /* enablingSafeDebugFormat= */ true, ...);
private static final Printer DEFAULT_FORMAT = new Printer(..., /* enablingSafeDebugFormat= */ false, ...).setInsertSilentMarker(...);
``` [3](#0-2) 

`AbstractMessage.toString()` — the method invoked implicitly by loggers (`log.info("{}", request)`), `String.format`, string concatenation, and collection `toString()` — resolves to `getOutputModePrinter()`, which defaults to the *unredacted* `defaultFormatPrinter()` unless the caller has explicitly wrapped the call in `ProtobufToStringOutput.callWithDebugFormat(...)`:
```
public final String toString() {
  return TextFormat.Printer.getOutputModePrinter()
      .printToString(this, TextFormat.Printer.FieldReporterLevel.ABSTRACT_TO_STRING);
}
...
static Printer getOutputModePrinter() {
  if (ProtobufToStringOutput.isDefaultFormat()) {
    return defaultFormatPrinter();      // enablingSafeDebugFormat = false
  } else if (ProtobufToStringOutput.shouldOutputDebugFormat()) {
    return debugFormatPrinter();        // enablingSafeDebugFormat = true
  } else {
    return printer();                   // enablingSafeDebugFormat = false
  }
}
``` [4](#0-3) [5](#0-4) 

The `ThreadLocal` default in `ProtobufToStringOutput` is `OutputMode.DEFAULT_FORMAT`, i.e. unredacted, unless an application explicitly opts into `callWithDebugFormat` for the current call stack [6](#0-5) . The library's own comments confirm this is a known, currently-unfinished transitional state: "Eventually, we will make toString output DebugFormat, which is randomized and redacts SPII fields" [7](#0-6) .

This transfers the Mattermost invariant directly: a schema author marks a value as sensitive (`debug_redact = true` ≈ ExperimentalAuditSettings intent to redact passwords), but the widely-used default code path that stringifies the object for human/log consumption (`Message.toString()` ≈ Mattermost's audit log serializer) silently ignores that marker unless a separate, non-default API/flag is used (`DebugFormat`/`callWithDebugFormat()` ≈ enabling proper redaction).

### Impact Explanation
Any Java application relying on `debug_redact = true` and calling the ordinary `message.toString()` (directly, via logging frameworks' `{}`/`%s` placeholders, via `String.valueOf`, or via container `toString()`) will emit the "sensitive" field's plaintext value into logs/traces without any warning, because the default printer never checks `enablingSafeDebugFormat`. Given `debug_redact` is explicitly documented and tested as the schema-level control for exactly this purpose (`RedactedFields`, `DebugFormatTest`), the disclosure risk (credentials, tokens, PII pushed to logging/observability pipelines) mirrors the impact class of the reported Mattermost issue — information disclosure via un-redacted debug/audit output, not memory corruption.

### Likelihood Explanation
Likelihood is high: `.toString()` is the most common, implicit way Java code stringifies objects (loggers, exceptions, debuggers, `String.format`), and it is unredacted by default; explicit redaction requires callers to specifically know about and invoke `DebugFormat`/`ProtobufToStringOutput.callWithDebugFormat()`, which is easy to overlook — exactly the "opt-in feature not applied" pattern the external report flags. This is also acknowledged by protobuf's own code comments as an intentional, not-yet-completed migration rather than a hardened default.

### Recommendation
Treat `debug_redact` as a hard invariant enforced at all textual-output layers, not just the explicitly-opted-in `DebugFormat`/`callWithDebugFormat` paths. Concretely: make `Message.toString()`'s default output mode (`DEFAULT_FORMAT`) honor `debug_redact` by default (as C++'s `Message::DebugString()` already does via `SetRedactDebugString(true)` in `StringifyMessage()`), and reserve fully-unredacted TextFormat output for explicit, clearly-named unredacted APIs (`LegacyUnredactedTextFormat`, `UnredactedDebugFormatForTest`) rather than making unredacted output the silent default.

### Proof of Concept
Given the test schema field `RedactedFields.optional_redacted_string` annotated `[debug_redact = true]` (`src/google/protobuf/unittest.proto:2465-2467`):
```java
RedactedFields message = RedactedFields.newBuilder()
    .setOptionalRedactedString("super-secret-password")
    .build();

// Default path used pervasively by logging frameworks — NOT redacted:
System.out.println(message.toString());
// -> optional_redacted_string: "super-secret-password"

// Only redacted when explicitly opted in:
System.out.println(DebugFormat.multiline().toString(message));
// -> optional_redacted_string: [REDACTED]
```
This is corroborated by the project's own tests: `ProtobufToStringOutputTest.toStringFormat_defaultFormat` asserts that the default `message.toString()` output contains the raw value `"bar"` for a `debug_redact = true` field, whereas `toStringFormat_testDebugFormat` shows the value is `[REDACTED]` only under `ProtobufToStringOutput.callWithDebugFormat` [8](#0-7) .
