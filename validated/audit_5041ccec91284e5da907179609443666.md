Investigating further confirms a concrete local bug distinct from the external report but of the same bug-class ("hook not applied in a critical downstream call, inconsistent with a sibling implementation that does the safety check correctly").

### Title
Unbounded loop in `object::root_owner()` allows gas-exhaustion bricking of `code::publish_package` upgrades and `init::internal_maybe_initialize` self-init on objects with cyclic ownership - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks the object-ownership chain to find the ultimate (non-object) owner, but unlike the sibling functions `owns()` and `verify_ungated_and_descendant()` in the same module, it has **no bound on the number of iterations** (no `MAXIMUM_OBJECT_NESTING` counter/guard). Both `code::publish_package` (for any package published/upgraded at an object address, when `LAZY_MODULE_INITIALIZATION` is enabled) and `init::assert_may_self_initialize` unconditionally call `.root_owner()` on the object being published to / self-initializing. If that object's ownership chain contains a cycle (which is directly reachable on-chain via a normal, single `object::transfer` call that makes an object own itself), any future call into these code paths never terminates and burns all transaction gas, permanently bricking the object's ability to be upgraded or to self-initialize its modules.

### Finding Description
`root_owner` is defined as:
```move
// aptos-move/framework/aptos-framework/sources/object.move:742-748
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

Contrast with `owns()`:
```move
let count = 0;
while (owner != current_address) {
    count += 1;
    assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
    ...
}
``` [2](#0-1) 

and `verify_ungated_and_descendant()`, which uses the same `count < MAXIMUM_OBJECT_NESTING` guard. [3](#0-2) 

The framework's own tests prove a self-cyclic ownership state is reachable through the public `transfer` entry point in a single transaction (`test_cyclic_ownership_transfer_should_fail` shows the *first* self-transfer of `obj1` to itself succeeds, only the *second* attempt aborts because `verify_ungated_and_descendant` then detects the pre-existing cycle): [4](#0-3) 

Once an object's `ObjectCore.owner` points back to itself (directly or via a longer cycle), `root_owner()`'s `while (is_object(obj_owner))` loop never terminates functionally, because `is_object(obj_owner)` stays true and `obj_owner` never changes — the transaction can only stop via gas exhaustion.

This function is called from two security-relevant, publish-path locations:
1. `code::publish_package`, for every (re-)publish to an object address once `LAZY_MODULE_INITIALIZATION` is enabled:
```move
if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
    let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
    ...
}
``` [5](#0-4) 

2. `init::assert_may_self_initialize`, gating lazy module self-initialization:
```move
fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
    let recorded = recorded_deploy_owner(addr, module_id);
    let ok = if (recorded.is_some()) {
        object::is_object(addr)
            && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
    } else { ... };
    assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
}
``` [6](#0-5) 

Both `object_code_deployment::upgrade` and `object_code_deployment::publish` route through `code::publish_package_txn` → `code::publish_package`, so once an object's ownership chain becomes cyclic, every subsequent `upgrade` (or first-time lazy self-init) transaction against that object's code will hit the unbounded loop and abort on out-of-gas, regardless of the object's declared `upgrade_policy` (which may still say `compatible`). [7](#0-6) 

### Impact Explanation
This breaks the invariant, relied upon by `code::publish_package` and `init::assert_may_self_initialize`, that resolving an object's root owner always terminates. The practical effect is a permanent denial-of-service on the object's code-upgrade path and on lazy module self-initialization: the object's `PackageMetadata.upgrade_policy` still reports `compatible`/upgradable, but the object becomes de-facto un-upgradable and unable to run `init::internal_maybe_initialize`-based initialization, without ever going through the intentional, auditable `code::freeze_code_object` path. This is a metadata/behavior mismatch and an unintended, unrecoverable freeze of code-management state reached through a standard, permissionless object operation (`object::transfer`).

### Likelihood Explanation
Low-to-medium likelihood: creating the cyclic state requires the object's own owner (or extend-ref holder) to deliberately or accidentally perform a self-transfer or a multi-object transfer cycle, so it is largely self-inflicted rather than exploitable against an unrelated victim. However, it is trivially reachable (one `object::transfer` call, already demonstrated by the repo's own test) and, unlike the sibling `owns`/`verify_ungated_and_descendant` functions, has zero defense-in-depth against it.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop guard used in `owns()` and `verify_ungated_and_descendant()` to `root_owner()`, aborting deterministically with `EMAXIMUM_NESTING` (or a dedicated error) instead of relying on gas exhaustion when the chain exceeds the nesting bound or is cyclic. This keeps `code::publish_package` and `init::assert_may_self_initialize` behavior deterministic and consistent with the rest of the ownership-traversal functions in `object.move`.

### Proof of Concept
1. Enable `LAZY_MODULE_INITIALIZATION`.
2. Create object `obj1` and use `object_code_deployment::publish` to publish a package to it.
3. As `obj1`'s owner, call `object::transfer(owner, obj1, obj1.object_address())` — this succeeds once, per `test_cyclic_ownership_transfer_should_fail`, making `obj1` own itself. [4](#0-3) 
4. Attempt `object_code_deployment::upgrade` on `obj1`'s code object: `object::is_owner` still passes (direct-ownership check), but the internal `code::publish_package` call now invokes `object::root_owner()` on `obj1`, which loops forever chasing `obj1 -> obj1 -> obj1 ...` until the transaction runs out of gas and aborts. [5](#0-4) [8](#0-7)

    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
