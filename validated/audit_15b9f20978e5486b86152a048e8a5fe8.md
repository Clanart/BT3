### Title
Incomplete extension blocklist in `isSafeFileExtension` lets an attacker-controlled repo file be launched via "Open with Default Program" - ([File: app/src/ui/lib/context-menu.ts])

### Summary
The "Open with Default Program" action available in the Changes list, History file list, Pull Request file list, and Copilot conflict-resolution list is gated only by `isSafeFileExtension()`, which on Windows blocklists just four extensions (`.cmd`, `.exe`, `.bat`, `.sh`) and on macOS/Linux blocks nothing at all. A crafted file in an attacker-controlled repository (cloned, fetched, or checked out via a PR) with a script/shortcut extension not on that list (e.g. `.js`, `.vbs`, `.wsf`, `.scr`, `.pif`, `.msi`, `.jse`, `.hta`, `.ps1`, `.lnk` on Windows, or `.command`/`.app`-style bundles on macOS) is treated as "safe," and the app hands the path to `shell.openExternal('file://...')`, which invokes the OS's default handler/launcher for that file type — effectively executing attacker-supplied content.

### Finding Description
`isSafeFileExtension` is the sole guard used before enabling "Open with Default Program" across multiple file-list views: [1](#0-0) 

It is consumed identically in the Changes list, History commit file list, Pull Request files-changed list, and the Copilot conflict resolution dialog to decide whether the menu item is `enabled`: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Once enabled, clicking it calls `onOpenItem`, which joins the repository path with the attacker-supplied repo-relative path and hands it to `openFile`: [6](#0-5) [7](#0-6) 

`openFile` ultimately calls `shell.openExternal('file://' + fullPath)`, which for Electron/OS purposes is equivalent to double-clicking the file in the OS shell — it invokes whatever handler/interpreter is registered for that extension (e.g. `wscript.exe` for `.js`/`.vbs`, `mshta.exe` for `.hta`, direct execution for `.scr`/`.pif`/`.lnk`, PowerShell for `.ps1` if association exists, Terminal execution for `.command` on macOS).

The broken invariant: the menu item's "safety" gate is a narrow, hardcoded 4-item Windows-only blocklist rather than an allowlist or a check based on actual file executability, and it provides zero protection on macOS/Linux. Nothing in this path validates file *contents*, nor is there any confirmation prompt warning that the file will be executed rather than merely displayed/edited.

### Impact Explanation
An attacker who gets a victim to clone, fetch, or open a pull request containing a file with an unlisted dangerous extension can achieve code execution on the victim's machine once the victim performs the ordinary, expected action of viewing that file in the Changes/History/PR list and choosing "Open with Default Program" (a first-class, always-visible context menu action, not a hidden or unnatural step). This is arbitrary code execution outside of any sandbox, achieved purely through repository content the attacker controls — matching the report's core theme of "no entry checks" on attacker-controlled inputs (file path/extension) before performing a privileged/dangerous action (native `openExternal`/shell launch).

### Likelihood Explanation
Likelihood is meaningful but not "one click of any file": the victim must specifically select the file and choose "Open with Default Program" (as opposed to double-clicking a diff, which only opens the diff viewer). However, this is a standard supported workflow that users legitimately use to inspect files that Desktop cannot render (e.g., non-text or unrecognized formats), so an attacker only needs to plant an enticingly-named file (e.g. `Invoice.js`, `Resume-scr`, `install.hta`) with an extension outside the 4-item blocklist to have a good chance of the victim invoking this action. The Windows blocklist additionally demonstrates the developers' intent to prevent exactly this class of attack, but the implementation is incomplete, and macOS/Linux have no mitigation whatsoever.

### Recommendation
- Replace the extension blocklist with a much larger, actively maintained list of known dangerous/executable extensions (mirroring Windows' own list of "executable" file types used by Explorer/SmartScreen, e.g. `.exe .cmd .bat .com .scr .pif .msi .msp .js .jse .vbs .vbe .wsf .wsh .hta .ps1 .psm1 .lnk .cpl .reg .gadget .application .jar` etc.), or better, invert the model to an allowlist of extensions known to be safely opened by common viewers.
- Apply the same protection uniformly across `__WIN32__`, `__DARWIN__`, and `__LINUX__` (currently `isSafeFileExtension` unconditionally returns `true` on non-Windows).
- On macOS, extend the existing `isApplicationBundle`/executable-bit detection (`app/src/lib/is-application-bundle.ts`) to also cover single executable files (`.command` scripts, files with the executable permission bit set), not just application bundles, before allowing "Open with Default Program."
- Consider showing an explicit confirmation dialog when the resolved handler for a file type is known to interpret/execute it, rather than silently relying on a static extension list.

### Proof of Concept
1. Attacker creates a public repository containing a file `Reimbursement_Form.js` (or `.vbs`/`.hta`/`.scr`) whose content is a malicious script (e.g., spawns `calc.exe` or downloads/executes a payload).
2. Victim clones the repository (or fetches/checks out a branch/PR containing it) in GitHub Desktop and views the file in the Changes list, History file list, or Pull Request Files Changed list.
3. Victim right-clicks the file; because `.js`/`.vbs`/`.hta`/`.scr` are not present in `RestrictedFileExtensions`, `isSafeFileExtension` returns `true` and "Open with Default Program" is enabled.
4. Victim clicks "Open with Default Program." Desktop calls `openFile(fullPath, dispatcher)` → `shell.openExternal('file://' + fullPath)`.
5. The OS launches the default handler for the extension (e.g., Windows Script Host for `.js`/`.vbs`, `mshta.exe` for `.hta`, direct execution for `.scr`), running the attacker's script with the victim's privileges. [1](#0-0) [7](#0-6)

import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
