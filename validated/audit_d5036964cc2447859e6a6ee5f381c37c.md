### Title
Unchecked payment and fee arithmetic allows transaction-construction denial of service - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` performs unchecked `u64` summation, multiplication, and addition over caller-controlled payment amounts, fee rates, and computed transaction sizes. Large payment values or fee rates can overflow these calculations and panic in checked builds, while configurations that disable overflow checks can wrap the solvency calculation and produce a signable transaction which is invalid under Bitcoin consensus. [1](#0-0) 

### Finding Description
The constructor accepts `payments` as arbitrary `(ScriptBuf, u64)` pairs and only rejects individual amounts below `DUST`; it does not enforce Bitcoin's maximum money value or any aggregate bound. [2](#0-1)  It calculates `payment_sat` with `sum::<u64>()`, calculates `needed_fee` with `fee_per_vbyte * vbytes`, and checks solvency with `payment_sat + needed_fee`, none of which use checked arithmetic. [3](#0-2) 

The change calculation repeats the same unchecked pattern by adding `payment_sat + fee_with_change` before passing the result to `checked_sub`, so the checked subtraction cannot protect against overflow in its operand. [4](#0-3)  The resulting `SignableTransaction` is converted into a `TransactionMachine` and each input signs a Taproot sighash committing to the generated transaction and all previous outputs. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged caller that can cause the wallet to construct a transaction for attacker-selected payment amounts or an attacker-influenced fee rate can force an arithmetic panic during `SignableTransaction::new`, denying Bitcoin signing progress. [7](#0-6) [3](#0-2) 

If this code is compiled outside the workspace release profile with overflow checks disabled, the overflowing `payment_sat + needed_fee` comparison can instead wrap to a small value, bypass `NotEnoughFunds`, and produce a transaction containing outputs whose total value exceeds the inputs and Bitcoin's consensus limit. [8](#0-7)  The signing machine then commits signatures to that malformed transaction via `Prevouts::All`, producing a signed transaction which cannot be published or spent as intended. [6](#0-5) 

### Likelihood Explanation
The vulnerable values are public API inputs rather than secrets: `payments` carries arbitrary `u64` amounts, and `fee_per_vbyte` is caller-provided. [7](#0-6)  Triggering the panic only requires payment totals near or above `u64::MAX`, or a fee rate whose multiplication by the calculated virtual size exceeds `u64::MAX`. [3](#0-2) 

The workspace explicitly enables release overflow checks, making a panic the expected workspace behavior rather than wrapping arithmetic. [9](#0-8)  Nevertheless, `SignableTransaction::new` itself does not return a structured `TransactionError` for these overflows, so every overflow path can abort the caller instead of being handled. [10](#0-9) 

### Recommendation
Use checked arithmetic for every aggregate and derived value in `SignableTransaction::new`, and return a new `TransactionError` variant when any calculation overflows. [10](#0-9) 

Specifically, replace the payment and input summations with fallible `checked_add` accumulation, calculate `fee_per_vbyte` times `vbytes` with `checked_mul`, calculate total spend with `payment_sat.checked_add(needed_fee)`, and calculate `payment_sat.checked_add(fee_with_change)` before `checked_sub`. [11](#0-10)  Also reject individual and aggregate outputs above Bitcoin's maximum money value before constructing `TxOut`s. [12](#0-11) 

### Proof of Concept
Construct a transaction with two caller-controlled payments whose amounts sum past `u64::MAX`:

```rust
let payments = [
  (script.clone(), u64::MAX - 1_000),
  (script, 2_000),
];

let _ = SignableTransaction::new(inputs, &payments, None, None, 1);
```

Each payment individually passes the dust check, while `sum::<u64>()` overflows `payment_sat`; under the workspace's enabled overflow checks this panics during transaction construction. [13](#0-12) [9](#0-8) 

Similarly, choose `fee_per_vbyte` near `u64::MAX` so `fee_per_vbyte * vbytes` overflows at line 206, causing a panic even for otherwise valid payments. [14](#0-13)
