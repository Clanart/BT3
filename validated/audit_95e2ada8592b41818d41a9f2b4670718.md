## Analog Found: Symlink-Following File Read in Working-Directory Image Diff

### Title
Working-directory image diff follows attacker-controlled symlinks, reading files outside the repository - (File: `app/src/lib/git/diff.ts`)

### Summary
`VeloOracle.getOraclePrice` had a faulty invariant: "if the observation timestamp hasn't advanced, the value is safe to trust as-is," which skipped the additional integrity check that would have caught a manipulated value produced within the same unchanged observation window. The equivalent broken invariant in GitHub Desktop is: "a path returned by `git status` for a working-directory file change is safe to join with the repository root and read directly," which skips the containment check (`resolveWithin`) that the codebase itself defines and uses elsewhere for exactly this reason. `getWorkingDirectoryImage` in `app/src/lib/git/diff.ts` reads `Path.join(repository.path, file.path)` via Node's `readFile`, which transparently follows symlinks, while `resolveWithin` (in `app/src/lib/path.ts`), which explicitly resolves and validates against symlink escapes with `realpath`, is bypassed entirely.

### Finding Description
`getWorkingDirectoryImage` builds the file path with a plain `Path.join` and calls `readFile` directly: [1](#0-0) 

The same unguarded pattern exists for syntax-highlighted diff content in `getNewFileContent`, which uses `readPartialFile(Path.join(repository.path, file.path), ...)` for `WorkingDirectoryFileChange` entries: [2](#0-1) 

`file.path` in both cases originates from `git status --porcelain=2`, parsed into `IStatusEntry.path` and then into a `WorkingDirectoryFileChange`: [3](#0-2) [4](#0-3) 

Git tracks symlinks as ordinary blob entries (mode `120000`) whose content is the link target; the tests in `status-parser-test.ts` show Desktop already handles such entries (`.T` typechange for mode `120000`) as first-class tracked paths, meaning a symlink shipped inside a cloned/fetched repository is surfaced through the normal status/diff pipeline like any other file: [5](#0-4) 

Node's `readFile`/`createReadStream` follow symlinks by default, so if `file.path` (or any path component of it) is a symlink pointing outside the repository (e.g. `../../.ssh/id_rsa` or an absolute path), `getWorkingDirectoryImage` and `getNewFileContent` will happily read and base64-encode the *target* file's contents instead of a file inside the repo.

Critically, the codebase already contains the correct fix pattern — `resolveWithin`, which normalizes, rejects null bytes, and then calls `realpath` on both the root and the resolved path to confirm the *real* (symlink-resolved) path stays under the root: [6](#0-5) 

This exact symlink-escape scenario is covered by unit tests for `resolveWithin`: [7](#0-6) 

And `resolveWithin` is deliberately used elsewhere to guard reads of attacker-influenced, repo-relative paths — e.g. when opening a deep-link `filepath` and when reading conflicted files for Copilot conflict resolution: [8](#0-7) [9](#0-8) 

The inconsistency — `resolveWithin` used for deep-link file paths and Copilot conflict file reads, but bypassed for working-directory diff/image rendering — is the faulty assumption: Desktop implicitly trusts that any path reported by `git status` for the working tree is inherently safe to `Path.join` and read, without accounting for the fact that the path itself can be (or traverse through) a symlink checked into a hostile repository.

### Impact Explanation
An attacker who controls a cloned or fetched repository can commit a symlink (mode `120000`) with an image-like extension (e.g. `evil.png`) pointing to an absolute path such as the user's SSH private key, cloud credentials file, browser cookie store, or any other sensitive file readable by the Desktop process. When the victim opens the "Changes" or history view and Desktop renders that file as an image diff (`getWorkingDirectoryImage`) or attempts syntax highlighting (`getNewFileContent`), the target file's bytes are read, base64-encoded, and embedded into the renderer's diff view — a file-read-outside-the-repo primitive satisfying the stated impact criteria. Depending on what UI/context is capable of exfiltrating that base64 blob further (e.g. clipboard, screenshot, or any telemetry/logging path that touches diff content), this could escalate to credential/token exfiltration.

### Likelihood Explanation
Likelihood is elevated because no special user action beyond normal repository browsing is required: cloning/fetching an attacker's repository and viewing its changes (a routine workflow) triggers the vulnerable code paths. The attacker fully controls the symlink target and the file's apparent extension (to make it render as an "image" in the diff view). No admin rights, local access, or prior compromise is needed — it only requires the victim to add/open a hostile repository, which is within the "attacker controls a cloned/fetched repository" impact class explicitly permitted.

### Recommendation
Route `getWorkingDirectoryImage` and `getNewFileContent`'s working-directory branch through `resolveWithin(repository.path, file.path)` (as already done for deep-link file paths and Copilot conflict context) before calling `readFile`/`readPartialFile`, and treat a `null` result (symlink escape or traversal) as an unreadable/skip case rather than silently reading through the symlink.

### Proof of Concept
1. Attacker creates a repository containing a symlink `evil.png -> /home/victim/.ssh/id_rsa` (or a relative traversal like `../../.ssh/id_rsa`), commits it with mode `120000`, and hosts/pushes the repo for the victim to clone.
2. Victim clones the repository with GitHub Desktop and modifies/views changes so that `evil.png` shows up as a changed working-directory file (or the attacker ships it as tracked content that later gets modified locally, or simply views the committed blob's diff).
3. Desktop calls `getWorkingDirectoryImage(repository, file)` for `evil.png`, which executes `readFile(Path.join(repository.path, 'evil.png'))`.
4. Because `evil.png` is a symlink, Node's `fs.readFile` follows it and returns the contents of `/home/victim/.ssh/id_rsa` instead of repository content, which is then base64-encoded and rendered as an "image" diff inside the app. [1](#0-0)

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
