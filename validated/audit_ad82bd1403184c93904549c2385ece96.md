### Title
ReceivedOutput deserialization accepts arbitrary offset/output pair without binding offset to the output's script_pubkey - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an offset scalar, a `TxOut`, and an `OutPoint` from untrusted bytes but never validates that the offset actually derives the key committed to in the output's `script_pubkey`. This mirrors the Discourse bug class (a missing validation on an externally-supplied value that downstream code treats as authoritative): the scanner-derived invariant "`offset` spends `output`" is established only in `Scanner::scan_transaction`, yet the deserialized form bypasses it entirely.

### Finding Description
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map, and `scan_transaction` only constructs a `ReceivedOutput` when `output.script_pubkey` matches a registered script — i.e., when `offset` provably satisfies `key + offset·G → script_pubkey` via `p2tr_script_buf` (`mod.rs:199-214`). That is the sole place the semantic invariant "this offset spends this output" is enforced.

`ReceivedOutput::read` (`mod.rs:122-134`) reconstructs the same struct from raw bytes — `Secp256k1::read_F` for the offset, then consensus-decoded `TxOut` and `OutPoint` — and returns it with no check that `p2tr_script_buf(self.key + G·offset) == output.script_pubkey`. There is no field storing the scanner key and no re-derivation anywhere in `read`. Consequently, any consumer that ingests a `ReceivedOutput` via `read`/`serialize` rather than obtaining it directly from `scan_transaction` will trust an attacker-chosen pairing.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (explicitly within the reachable-input scope) can claim:

- A real on-chain output (valid `TxOut`/`OutPoint` paying to *someone else's* script) paired with an arbitrary offset → the wallet reports funds received that are not spendable by the threshold key; any downstream spend attempt produces a transaction whose input signature never verifies, burning the output from the wallet's accounting.
- An offset of `0` (or the tweak-negated offset) paired with an output the attacker controls → signer is driven to produce a BIP-340 signature over a sighash committing to an `OutPoint`/`TxOut` selected by the attacker, i.e., signing of an unintended message shaped by attacker-chosen transaction data.

### Likelihood Explanation
Reachable whenever a `ReceivedOutput` round-trips through untrusted storage, RPC payloads, or a coordinator-supplied plan rather than being used in-memory straight from `scan_transaction`. No cryptographic assumptions are needed — only control of the serialized bytes. Impact is bounded to a Medium because exploitation requires a consumer that trusts deserialized `ReceivedOutput`s; `scan_transaction` itself remains sound.

### Recommendation
Bind the invariant at deserialization time: either (a) require the scanner key at `read` time — `ReceivedOutput::read(r, &scanner_key)` — and verify `p2tr_script_buf(scanner_key + ProjectivePoint::GENERATOR * offset) == Some(output.script_pubkey)`, rejecting otherwise; or (b) make `ReceivedOutput::read` private to the wallet module so only `Scanner` can mint the type.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs — conceptual PoC
// Attacker crafts bytes: offset=1, output=an arbitrary TxOut paying to
// the attacker's own P2TR key, outpoint=that output's real outpoint.
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());                     // offset = 1
buf.extend(serialize(&attacker_txout));                  // not ours
buf.extend(serialize(&real_outpoint));                   // exists on-chain

// This succeeds today despite offset=1 almost certainly not deriving
// attacker_txout.script_pubkey from the threshold key.
let claimed = ReceivedOutput::read(&mut buf.as_slice()).unwrap();

// Wallet now treats `claimed` as a spendable input:
// - value() reports attacker-controlled funds as received
// - any spend signs a sighash over attacker-chosen outpoint/TxOut data
//   and the resulting input can never satisfy the script_pubkey.
```
The gap is precisely that `scan_transaction` performs a `self.scripts.get(&output.script_pubkey)` membership check (`mod.rs:205`) that `ReceivedOutput::read` (`mod.rs:122-134`) omits — the deserialized path never re-establishes the offset↔script binding.
