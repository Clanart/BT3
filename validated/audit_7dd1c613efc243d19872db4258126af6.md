### Title
Second-poll re-processing of an unhandled payout row lets an operator draw a second reimbursement for a payout it fronted only once - (File: core/src/task/payout_checker.rs)

### Summary
`PayoutCheckerTask::run_once` selects and processes exactly one unhandled withdrawal row per poll via `get_first_unhandled_payout_by_operator_xonly_pk`, and `mark_payout_handled` only flips `is_payout_handled` for the single `idx` just processed. If the upstream `get_payout_txs_for_withdrawal_utxos` join (index-conflation bug) has already written the *same* `payout_txid`/`payout_payer_operator_xonly_pk`/`payout_tx_blockhash` onto two distinct withdrawal rows `i` and `j` that in reality correspond to two different deposits, the task will process `i`, mark it handled, and then on the very next poll pick up `j` and issue a second, independent `handle_finalized_payout` / kickoff — this time against deposit `j`'s own move-to-vault collateral, even though the operator never actually funded a Bitcoin payout for withdrawal `j`.

### Finding Description
Binding that must hold: `number_of_kickoffs_issued_for_move_to_vault_txid(j) == number_of_real_on_chain_payouts_fronted_for_withdrawal(j)`.

The claimed break relies on a precondition already established by the separate join-conflation bug in `get_payout_txs_for_withdrawal_utxos` [1](#0-0) : this query joins `withdrawals w` to `bitcoin_syncer_spent_utxos bsu` purely on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, with no uniqueness enforcement across `idx`. If two withdrawal rows `i` and `j` end up carrying the same `(withdrawal_utxo_txid, vout)` value, a single spend event produces two output rows `(i, payout_txid)` and `(j, payout_txid)` for one real Bitcoin transaction. `update_finalized_payouts` then writes this to both rows via `update_payout_txs_and_payer_operator_xonly_pk` [2](#0-1) , which is a bulk `UPDATE ... FROM (VALUES ...) WHERE w.idx = c.idx` [3](#0-2)  that happily sets identical `payout_txid`, `payout_payer_operator_xonly_pk`, and `payout_tx_blockhash` on both rows `i` and `j`.

Given that state, `PayoutCheckerTask::run_once` reads one row at a time:
```
"SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
 FROM withdrawals w
 WHERE w.payout_txid IS NOT NULL
    AND w.is_payout_handled = FALSE
    AND w.payout_payer_operator_xonly_pk = $1
    ORDER BY w.idx ASC
 LIMIT 1"
``` [4](#0-3) 

First poll returns `i` (lower `idx`). `run_once` fetches `deposit_data` keyed by `move_to_vault_txid` for row `i` [5](#0-4) , calls `Operator::handle_finalized_payout` on deposit `i`'s outpoint, issuing a kickoff that pays the operator back from deposit `i`'s move-to-vault UTXO [6](#0-5) , then calls `mark_payout_handled(idx=i, kickoff_txid)`, which updates **only** `WHERE idx = $1` [7](#0-6) . Row `j` is untouched — its `is_payout_handled` is still `FALSE`, and it still has `payout_txid IS NOT NULL` and the matching `payout_payer_operator_xonly_pk`.

On the next poll (250ms in test, 60s in prod, per `PAYOUT_CHECKER_POLL_DELAY` [8](#0-7) ), the same query now returns `j`. `run_once` fetches deposit data for `move_to_vault_txid` of row `j` — a *different, legitimate* deposit — and issues a *second, independent* `handle_finalized_payout` call, spawning a second kickoff that claims reimbursement from deposit `j`'s vault, even though the operator's single real payout transaction only ever satisfied withdrawal `i`'s intended recipient.

Existing guards do not catch this: `Verifier::is_kickoff_malicious` validates a kickoff by looking up `get_payout_info_from_move_txid(move_txid)` [9](#0-8) , which is keyed by `w.move_to_vault_txid = $1` [10](#0-9)  — it reads the same corrupted row `j` that already (incorrectly) carries the operator's pubkey and the real payout's blockhash, so the check passes even though no payout for `j`'s own withdrawal recipient ever occurred.

### Impact Explanation
Deposit `j`'s move-to-vault UTXO is spent via a kickoff/reimburse-connector flow triggered for a payout that was never fronted to that deposit's withdrawer. This is BTC leaving a move-to-vault UTXO without a matching fronted withdrawal, and an operator reimbursed for a payout it never funded (Critical). It is repeatable per pair of conflated rows that the upstream join bug produces, and scales across every deposit whose withdrawal row happens to share a `(withdrawal_utxo_txid, vout)` pair with an already-processed row for the same operator.

### Likelihood Explanation
This finding is fully conditioned on the precondition supplied by the question — that the earlier `get_payout_txs_for_withdrawal_utxos` join bug has already produced two withdrawal rows `i`/`j` sharing `payout_txid`/`payout_payer_operator_xonly_pk`. Given that precondition, the double-processing traced above follows deterministically from `PayoutCheckerTask`'s one-row-per-poll design and `mark_payout_handled`'s single-idx `UPDATE`; no additional attacker action beyond what produces the precondition is needed. No mainnet or live Citrea is required to reproduce — it's a pure DB/task-logic race reproducible with `cargo test`.

### Recommendation
`mark_payout_handled`/`update_payout_txs_and_payer_operator_xonly_pk` should key off the actually-spent `(withdrawal_utxo_txid, vout)` pair with a uniqueness constraint (or dedupe/error in `get_payout_txs_for_withdrawal_utxos` when more than one withdrawal row maps to the same spent UTXO), and `get_first_unhandled_payout_by_operator_xonly_pk` should not return a second row associated with an already-consumed `payout_txid` for the same operator.

### Proof of Concept
`cargo test` in `core/src/database/verifier.rs`/`core/src/task/payout_checker.rs` style:
1. Seed two withdrawal rows `i`, `j` with distinct `move_to_vault_txid`s (two distinct deposits) but identical `withdrawal_utxo_txid`/`vout`.
2. Call `update_payout_txs_and_payer_operator_xonly_pk` with the same `(payout_txid, operator_xonly_pk, block_hash)` for both `i` and `j` (simulating the join-bug output).
3. Run `PayoutCheckerTask::run_once` — assert `Operator::handle_finalized_payout` is called with deposit `i`'s outpoint, and `mark_payout_handled(i, ...)` is written.
4. Run `PayoutCheckerTask::run_once` again — assert `get_first_unhandled_payout_by_operator_xonly_pk` returns `j`, `Operator::handle_finalized_payout` is called again with deposit `j`'s outpoint, and a second kickoff is issued — violating the binding `kickoffs_issued(j) == 0` (since the operator fronted no real Bitcoin payout for `j`).
