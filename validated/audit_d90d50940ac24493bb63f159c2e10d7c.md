## Title
Single global `maxOracleAge` staleness cap shared across all registered token oracles allows stale-price gas underpayment / paymaster fund drain - (File: `evm/src/utils/SimplexPaymaster.sol`)

## Summary
`SimplexPaymaster` prices ERC-20 gas payments using a single, contract-wide `maxOracleAge` bound that is applied identically to the native/USD oracle and to *every* registered token/USD oracle, regardless of that token's actual Chainlink heartbeat. The contract's own comment acknowledges the heartbeats vary wildly per token/chain ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"), yet there is only one staleness parameter for all of them — the exact "one-size-fits-all cap for multiple assets" pattern described in the seed report (Basin `MultiFlowPump`'s single `LOG_MAX_INCREASE`/`LOG_MAX_DECREASE` applied to all reserves).

## Finding Description
`Params.maxOracleAge` is a single `uint256` set once via governance (`_setParams`) and stored as `maxOracleAge`: [1](#0-0) 

It is enforced identically for the native oracle and for any token oracle in `_getOraclePrice`, which every `_tokenPrice()` call (used both in `_fetchDetails` for gas pricing and in `swapAndDeposit`) depends on: [2](#0-1) 

`maxOracleAge` is bounded only by a single global ceiling `MAX_ORACLE_AGE = 7 days`, and governance can set any value between 1 second and 7 days that must simultaneously "work" for every token registered via `RegisterToken`: [3](#0-2) [4](#0-3) 

Because tokens with very different natural heartbeats (a fast ~27s-updating BSC stablecoin vs. a slow 24h-updating Ethereum/Base stablecoin) are registered under the *same* `maxOracleAge`, governance is forced into one of two unsafe configurations:
- Set `maxOracleAge` loose enough to accommodate the slowest-heartbeat token (e.g. tens of thousands of seconds, up to the 7-day ceiling). This is then also applied to fast-heartbeat tokens, whose oracle can legitimately stall (keeper outage, chain congestion) for far longer than its normal ~27s cadence while still passing the staleness check, allowing a materially outdated price to be accepted as "fresh" for that fast-moving token.
- Set `maxOracleAge` tight enough for the fast token, which then spuriously fails staleness checks for the slow-heartbeat token even under completely normal update behavior.

There is no per-token `maxOracleAge` / heartbeat field in `TokenConfig` — only `tokenOracle`, `tokenOracleDecimals`, `tokenDecimals`, and `active`: [5](#0-4) 

`_registerToken` never records or validates a token-specific heartbeat, so nothing distinguishes a fast-moving token's staleness tolerance from a slow one's at registration time: [6](#0-5) 

This mirrors the seed bug precisely: a single hard-coded bound (`LOG_MAX_INCREASE`/`LOG_MAX_DECREASE` in the analog vs. `maxOracleAge` here) is used indiscriminately across multiple assets with different natural volatility/update cadence, either understaling the risk on volatile/fast assets or being unnecessarily restrictive on slow/stable ones.

## Impact Explanation
`_tokenPrice()` directly determines how much ERC-20 token is pulled from a UserOp sender's account via `PaymasterERC20`'s prefund `transferFrom` in exchange for sponsoring native gas. If the global `maxOracleAge` is loose enough to cover a slow-heartbeat token, then a fast-heartbeat token's oracle can go stale for a comparably long window (well beyond its normal update cadence) without tripping `StaleOraclePrice`. During that window the underlying market price can move materially away from the stale on-chain answer. Any UserOp sender who submits during such a window is charged based on a stale, mispriced ratio between the native asset and the token — this is a direct value-transfer bug: the paymaster/treasury either overpays gas relative to token collected (fund loss to the protocol) or the user is overcharged (loss/unauthorized-amount transfer to the user), both of which fall under "stealing or loss of funds" / "transaction manipulation" per the bounty scope. Because `swapAndDeposit` also relies on `_getOraclePrice` for `amountOutMin`, the same stale-price condition can also produce unfavorable swaps that leak treasury value during fee recycling.

## Likelihood Explanation
No privileged actor, relayer, prover, or governance action is needed — an attacker only needs to be an ordinary UserOp sender using this paymaster, timing their operation during a window where a low-heartbeat token's Chainlink feed has stalled beyond its normal cadence but still within the shared `maxOracleAge`. Given that Chainlink heartbeats for different tokens/chains genuinely differ by orders of magnitude (documented in-contract as ~27s vs 24h), any governance-chosen single `maxOracleAge` value that supports the full registered token set necessarily leaves either fast tokens under-protected or slow tokens falsely rejected — the vulnerable configuration is close to unavoidable once more than one token with disparate heartbeats is registered, which the contract explicitly anticipates supporting ("USDC, USDT, or any token with a Chainlink feed").

## Recommendation
Add a per-token staleness bound to `TokenConfig` (e.g., `uint256 maxAge`) set at `RegisterToken` time based on that token's actual Chainlink heartbeat, and check `block.timestamp - updatedAt` against the token-specific bound in `_getOraclePrice` instead of (or in addition to) the single global `maxOracleAge`. Apply the same per-oracle bound to the native oracle staleness check as well, so no single global constant is shared across assets with materially different update cadences.

## Proof of Concept
1. Governance registers two tokens: `TokenA` (BSC-style stablecoin, Chainlink heartbeat ~27s) and `TokenB` (Ethereum-style stablecoin, Chainlink heartbeat ~24h), both under the same `maxOracleAge` param, set to e.g. `90000` seconds (25h) so `TokenB`'s legitimate 24h heartbeat passes.
2. `TokenA`'s oracle keeper stalls for 5 hours (well beyond its ~27s cadence but far under the 25h global cap) while the true TokenA/USD or native/USD price moves 5%.
3. A UserOp is submitted using `TokenA` as the paymaster gas token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the 5-hour-old `TokenA` answer as "fresh" (`block.timestamp - updatedAt (5h) < maxOracleAge (25h)`), pricing gas at the stale, now-incorrect ratio.
4. `PaymasterERC20` pulls the mispriced token amount from the sender while the paymaster contract pays the actual (now different) native gas cost from its EntryPoint deposit, realizing a value loss to the paymaster/treasury (or an overcharge to the user) purely from the shared, non-token-specific staleness bound.     function _registerToken(address token, AggregatorV3Interface oracle) internal {
        if (token == address(0) || address(oracle) == address(0)) revert ZeroAddress();

        bool isNew = !tokenConfigs[token].active && address(tokenConfigs[token].tokenOracle) == address(0);

        tokenConfigs[token] = TokenConfig({
            tokenOracle: oracle,
            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        if (isNew) {
            registeredTokens.push(token);
        }

        emit TokenRegistered(token, address(oracle));
    }

    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
