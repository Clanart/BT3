## Analysis: ReDoS in Git remote push-rejection message parsing

I found a strong analog. `extractSecretScanningResults()` in `app/src/ui/dispatcher/error-handlers.ts` parses `stderr` text that originates from `remote: ` lines emitted by whatever Git server/proxy the user pushes to — this is attacker-controllable content when the "remote" is a malicious or compromised server/proxy in the push path.

### Title
Potential ReDoS in secret-scanning push-rejection message parser via attacker-controlled `remote:` output - (File: `app/src/ui/dispatcher/error-handlers.ts`)

### Summary
`secretScanningPushProtectionErrorHandler()` extracts `remote: ` lines from `git push` stderr with `getRemoteMessage()` [1](#0-0)  and feeds the resulting string, unbounded and unsanitized, into `extractSecretScanningResults()`, which runs it through a complex regex containing nested `[\s\S]*?` non-greedy wildcards and a repeated group with an inner `.*?` [2](#0-1) . The pattern is only triggered when `dugite` reports `GitError.PushWithSecretDetected` [3](#0-2) , meaning any server that returns Git's `SH::error` marker for that specific dugite-detected error class can drive an attacker-chosen `remote:` payload into this regex.

### Finding Description
The regex:
```
/—— (?<description>.*?) —+[\s\S]*?locations:(?<locationsGroup>(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+).*?(?<bypassURL>https[\s\S]*?) /g
```
combines several classic ReDoS-prone constructs:
- `[\s\S]*?` between `——…——+` and `locations:` — lazy wildcard that must backtrack character-by-character searching for a literal that may never appear.
- A **quantified group** `(?:\s+- commit: [a-f0-9]{40}\s+path: [\s\S]*?)+` where the inner alternative itself contains a lazy `[\s\S]*?`. Nesting a lazy wildcard inside a `+`-quantified group is a well-known catastrophic-backtracking pattern: for input that almost — but not quite — matches the "commit:/path:" sub-pattern repeatedly, the engine can explore exponentially many ways to split the input between repetitions of the outer group and the inner lazy wildcard.
- `.*?(?<bypassURL>https[\s\S]*?) ` at the end, another lazy scan for a literal (`https`) that requires backtracking through everything already consumed if the literal is absent or placed adversarially.

This is functionally the same defect class as CVE-2024-27351: a lazy/greedy regex with nested wildcards run against fully attacker-controlled text, with no length cap and no timeout, executed on Node's regex engine (V8, backtracking-based like Python's `re`).

### Impact Explanation
`git push` failure output (`stderr`) is attacker-influenceable whenever the destination remote — or a man-in-the-middle proxy/gateway sitting in front of it — is malicious or compromised, since Git clients trust whatever bytes the remote returns for error reporting. By crafting a `remote: ` line containing many near-matches of `——`/`locations:`/`- commit: ... path: ...`/`https` without ever completing a valid match, an attacker can force the regex engine into catastrophic backtracking, freezing the renderer's main thread (Desktop's Node/Electron main/UI process) for as long as the input size and crafted pattern dictate, since there is no truncation of `stderr` or the `remote:` message and no execution timeout on `matchAll`. This is a real availability impact (UI hang / app freeze) triggerable purely by controlling the push destination's error response — no local access, no malware, no user misstep required beyond a normal `git push` that gets rejected.

### Likelihood Explanation
Moderate-to-high: the path only activates when dugite classifies the push failure as `GitError.PushWithSecretDetected` [4](#0-3) , which depends on dugite/git's own stderr-pattern matching for that error class — I could not fully verify from the indexed code exactly which stderr signature dugite requires to classify an error as `PushWithSecretDetected`, so confirming that an attacker-controlled remote can freely choose the rest of the message while still satisfying that upstream classifier requires further investigation (e.g., in the `dugite` dependency, not part of this repo's indexed sources). If the classifier only checks a coarse marker (e.g., a specific substring near the start of stderr) and lets the remainder of `remote:` lines be attacker-controlled, the likelihood is high, since any Git server/proxy under attacker control can shape its rejection message to include a well-known GitHub secret-scanning marker plus a crafted degenerate tail.

### Recommendation
- Bound the input size before running `extractSecretScanningResults` (e.g., cap `remoteMessage` length before regex application).
- Replace the nested lazy-wildcard/quantified-group pattern with a linear, non-backtracking parser (line-by-line state machine) instead of a single monolithic regex, mirroring the eventual Django fix for `Truncator.words()` which moved away from vulnerable regex backtracking.
- Add a regex execution timeout or run the parsing off the main/UI thread.
- Add fuzz/adversarial-input tests specifically targeting the `——`, `locations:`, and `https` literals with long non-matching filler, to catch regressions.

### Proof of Concept
A push rejection whose `remote:` lines look like:
```
remote: —— <PADDING-A>·<PADDING-A>·<PADDING-A>...(no closing " —— ") ...
remote: locations:
remote:  - commit: <40 hex>
remote:  path: <PADDING-B>...(repeated many times, never hitting a literal "https")
```
fed as `stderr` from a malicious/compromised push destination, when passed through `getRemoteMessage()` then `extractSecretScanningResults()`, causes the regex engine to backtrack combinatorially over the padding sections, consistent with the same class of attack demonstrated in the original Django PoC (long strings of near-matching filler in front of a required-but-absent anchor literal). I was not able to execute this against the actual bundled `dugite`/Node regex engine within the available tools to measure concrete timing, so exact degradation (seconds vs. longer) is unverified and should be confirmed by a background agent with terminal access.

```typescript
/**
 * Extract lines from Git's stderr output starting with the
 * prefix `remote: `. Useful to extract server-specific
 * error messages from network operations (fetch, push, pull,
 * etc).
 */
function getRemoteMessage(stderr: string) {
  const needle = 'remote: '

  return stderr
    .split(/\r?\n/)
    .filter(x => x.startsWith(needle))
    .map(x => x.substring(needle.length))
    .join('\n')
}
```
