## Analysis

The external report's core broken invariant is: **a value carrying a chain identifier (`chain_hash`) is verified against a stored request without checking that the chain identifiers actually match**, allowing a state transition intended for one chain to be finalized based on data proven against a different chain.

Searching Hyperbridge's own relayer fee-accumulation pipeline in `modules/pallets/relayer/src/accumulate.rs` and `modules/pallets/relayer/src/withdrawal.rs` surfaces the same missing-binding pattern.

### Title
Relayer fee accumulation never verifies that `source_proof`/`dest_proof` chain identifiers match the actual request's recorded source/destination chains - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` lets an unsigned caller submit a `WithdrawalProof { commitments, source_proof, dest_proof, .. }` [1](#0-0)  to claim relayer fees. It validates that each `commitment` exists and is unclaimed in local storage [2](#0-1) , then independently validates `source_proof` and `dest_proof` as generic state proofs against whatever `state_id` each proof's height claims [3](#0-2) . At no point does the code assert that `source_proof.height.id.state_id` and `dest_proof.height.id.state_id` are the actual source/destination chains recorded for that specific request commitment — the same class of gap as the reported `chain_hash` vs `request.chain` mismatch.

### Finding Description
`accumulate()` derives a single `state_machine = withdrawal_proof.source_proof.height.id.state_id` and a single destination state machine from `dest_proof.height.id.state_id`, and applies these uniformly to the whole batch of commitments via `source_fee_commitment_keys` and `receipts_state_trie_key`: [3](#0-2) 

Both proofs are then verified purely as "does this key exist at this state root for this claimed state machine ID" via `verify_withdrawal_proof`, which trusts `proof.height.id.state_id` to select which registered consensus client/state machine to check against: [4](#0-3) 

`validate_results` then zips `commitments`, `source_keys`, and `dest_keys` positionally and extracts a fee amount and delivering relayer address purely from whatever bytes were proven at those keys, with no cross-check that the *specific* commitment in the loop actually corresponds to a request whose `source`/`dest` fields equal the `state_id`s used to build `source_proof`/`dest_proof`: [5](#0-4) 

The only membership requirement enforced on the commitment itself is `RequestCommitments::<T>::get(req).is_some() && !leaf_meta.claimed` [2](#0-1)  — this confirms the commitment is a real, locally-known, unclaimed request, but it never checks that request's actual recorded source/destination chain against the `state_id`s the caller supplied in `source_proof`/`dest_proof`. This mirrors exactly the reported defect: `process_withdrawal_confirmed` checked only the idempotence key/commitment existed, never that the event's chain matched `request.chain`.

### Impact Explanation
If a caller can supply a `source_proof`/`dest_proof` pair whose `state_id` diverges from the commitment's true source/destination chain, but whose keys still happen to resolve to a valid, provable value at that (wrong) chain's state root (e.g., a state machine that the caller can influence or that shares the same slot-derivation scheme), the pallet will credit relayer fees or record delivery attribution based on unrelated chain state instead of the state that actually reflects delivery of that specific request. Since `Fees` are subsequently withdrawn and disbursed via ISMP `DispatchPost` to external chains in `withdrawal.rs` [6](#0-5) , incorrect crediting directly converts into fund loss/misdirection from the fee pool — the same "wrong chain accepted as authoritative" outcome flagged as High impact in the original report.

### Likelihood Explanation
Exploitation requires the attacker to find or construct chain state where the request-commitment-derived storage key (a function purely of the commitment hash and a fixed slot offset, independent of which chain is being proven against, per `source_fee_commitment_keys`) [7](#0-6)  happens to hold an exploitable value on a different registered state machine than the true source/destination. This is a code-level gap present regardless of whether a concrete collision is trivial to construct today; the fix's cost (an explicit equality assertion) is low relative to the risk, and it is the direct structural analog of the confirmed/fixed bug in the seed report.

### Recommendation
In `accumulate()`, after decoding each request's stored metadata (or by reading `req.source`/`req.dest` if available from `RequestCommitments`), assert:
```rust
ensure!(source_proof.height.id.state_id == expected_source_chain, Error::<T>::ChainMismatch);
ensure!(dest_proof.height.id.state_id == expected_dest_chain, Error::<T>::ChainMismatch);
```
per commitment (or per-batch if all commitments in a batch are constrained to share source/dest), immediately after `RequestCommitments::<T>::get(req)` is loaded — mirroring the fix already applied to `process_withdrawal_confirmed` for `chain_hash` vs `request.chain`.

### Proof of Concept
Conceptual (cannot be executed without full trie/consensus-client fixtures, which are outside indexed code):
1. Identify a real, unclaimed request commitment `req` dispatched with `dest = ChainA`, minimal fee.
2. Submit `accumulate(WithdrawalProof { commitments: [req], source_proof: <proof from ChainB's state>, dest_proof: <proof from ChainA's state>, .. })`, where `ChainB` is a registered state machine whose commitment-derived slot (per `source_fee_commitment_keys`) can be made to resolve to an inflated fee value.
3. Because `accumulate()` never checks `source_proof.height.id.state_id` against `req`'s true source chain, the state proof from `ChainB` is accepted and the inflated fee is credited to `Fees::<T>`.
4. Withdraw the inflated `Fees` balance via `Pallet::withdraw`, causing the fee pool to disburse more than was actually earned for that delivery.

**Note:** I was unable to fully verify within the indexed code whether the EVM host contract address used in `derive_unhashed_map_key_with_offset` is deterministic/attacker-influenceable across chains, which affects how easily step 2 above is achievable in practice. The missing chain-identity assertion itself, however, is directly confirmed in the code shown above.

	pub fn verify_withdrawal_proof(
		state_machine: &dyn ismp::consensus::StateMachineClient,
		proof: &Proof,
		keys: Vec<Vec<u8>>,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, DispatchError> {
		let host = <T as Config>::IsmpHost::default();
		let state = host
			.state_machine_commitment(proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		// Select the trie root explicitly instead of letting the relayer-supplied proof choose
		// it. Fee accumulation reads ISMP request/receipt metadata, which lives in the global
		// state trie on EVM chains and in the ISMP child trie (overlay root) on substrate
		// chains.
		let root = if proof.height.id.state_id.is_evm() {
			state.state_root
		} else {
			state.overlay_root.ok_or(Error::<T>::ProofValidationError)?
		};
		let result = state_machine
			.verify_state_proof(&host, keys, root, proof)
			.map_err(|_| Error::<T>::ProofValidationError)?;

		Ok(result)
	}

	pub fn validate_results(
		proof: &WithdrawalProof,
		source_keys: Vec<Vec<u8>>,
		dest_keys: Vec<Vec<u8>>,
		source_result: BTreeMap<Vec<u8>, Option<Vec<u8>>>,
		dest_result: BTreeMap<Vec<u8>, Option<Vec<u8>>>,
	) -> Result<(BTreeMap<Vec<u8>, U256>, Vec<H256>), Error<T>> {
		let mut result = BTreeMap::new();
		// Only store commitments that were claimed
		let mut commitments = Vec::new();
		for ((commitment, source_key), dest_key) in
			proof.commitments.clone().into_iter().zip(source_keys).zip(dest_keys)
		{
			let encoded_metadata =
				if let Some(encoded) = source_result.get(&source_key).cloned().flatten() {
					encoded
				} else {
					// If fee is a null value skip it, evm returns non membership proof for
					// zero values
					continue;
				};

			let fee = match proof.source_proof.height.id.state_id {
				s if crate::is_pharos(&s) =>
					if encoded_metadata.len() == 32 {
						U256::from_big_endian(&encoded_metadata)
					} else {
						return Err(Error::<T>::ProofValidationError);
					},
				s if s.is_evm() => {
					use alloy_rlp::Decodable;
					let fee = alloy_primitives::U256::decode(&mut &*encoded_metadata)
						.map_err(|_| Error::<T>::ProofValidationError)?;
					U256::from_big_endian(&fee.to_be_bytes::<32>())
				},
				s if s.is_substrate() => {
					use codec::Decode;
					let fee: u128 = pallet_ismp::dispatcher::RequestMetadata::<T>::decode(
						&mut &*encoded_metadata,
					)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.fee
					.fee
					.into();
					U256::from(fee)
				},
				// unsupported
				_ => Err(Error::<T>::MismatchedStateMachine)?,
			};
			let encoded_receipt = dest_result
				.get(&dest_key)
				.cloned()
				.flatten()
				.ok_or_else(|| Error::<T>::ProofValidationError)?;
			let address = Self::decode_receipt_relayer(
				proof.dest_proof.height.id.state_id,
				&encoded_receipt,
			)?;
			let entry = result.entry(address).or_insert(U256::zero());
			*entry += fee;
			commitments.push(commitment);
		}
