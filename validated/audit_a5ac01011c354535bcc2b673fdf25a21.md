Confirmed: `CW20ERC20Pointer` is a production contract (deployed via `x/evm/artifacts/cw20`, registered/managed via `SetERC20CW20Pointer`/`GetERC20CW20Pointer`) that any EVM user can call as an ERC20-compatible wrapper around a CW20 token. Its `approve` implementation is directly analogous to — and worse than — the reported bug class.

### Title
`CW20ERC20Pointer.approve` recomputes allowance delta from live on-chain state, making it exploitable via front-running to grant a spender more than the token owner intended - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
The `CW20ERC20Pointer` contract wraps a CW20 token as an ERC20-compatible pointer reachable by any EVM transaction sender. Its `approve(spender, amount)` function reads the current allowance and issues an `increase_allowance`/`decrease_allowance` CW20 message for the delta between the current and requested amount, rather than atomically setting an absolute value. This preserves the classic ERC20 approve front-running race condition and — because the delta is computed from live state at execution time — actually converts any change-of-approval transaction into an implicit "increase by the newly observed gap" operation that a malicious spender can exploit for double-spend.

### Finding Description
`approve` in `contracts/src/CW20ERC20Pointer.sol` is: [1](#0-0) 

It queries `allowance(msg.sender, spender)` at execution time and issues `increase_allowance`/`decrease_allowance` for the difference to reach the target `amount`. If a spender front-runs the owner's `approve` transaction by calling `transferFrom` to drain the existing allowance first, the pending `approve(spender, newAmount)` transaction, when it executes afterward, will read `currentAllowance = 0` and issue `increase_allowance` for the *full* `newAmount` (not the originally intended delta). The spender thus ends up having spent the old allowance in full and still receiving the full new allowance — i.e., strictly more than the owner ever intended to have outstanding at once. This is the exact bug class from the report (`Pool.approve` in the referenced Surge protocol audit), reachable here through any EVM `approve` call routed through the CW20↔ERC20 pointer bridge.

### Impact Explanation
A spender who is granted an allowance can, via ordinary mempool front-running of the owner's approval-change transaction, obtain and spend more CW20 tokens (via the pointer's `transferFrom`, which delegates to the CW20 `transfer_from` message) than the owner ever authorized to be outstanding, resulting in direct fund loss for the token owner. This matches the accepted "concrete fund loss" impact bar since it results in unauthorized transfer of tokens through a pointer contract.

### Likelihood Explanation
Any account that has been granted a non-zero allowance via the pointer and monitors the mempool for the owner's subsequent `approve` call can exploit this deterministically; it requires no special privileges beyond being a public RPC/mempool observer and a currently-approved spender, which is a normal occurrence for token integrations (DEXes, routers, etc.) that already hold outstanding allowances.

### Recommendation
Change `CW20ERC20Pointer.approve` to not depend on the currently-read allowance for computing the CW20-side delta; instead, expose explicit `increaseAllowance(spender, addedValue)` / `decreaseAllowance(spender, subtractedValue)` functions (which take an explicit delta from the caller, not a target amount) as the primary safe interface, and document/deprecate `approve` as unsafe for allowance updates from a nonzero value, consistent with standard ERC20 guidance. Alternatively, require `approve` to first be set to zero before changing to a new nonzero value (matching some ERC20 tokens' mitigation), enforced at the pointer contract level.

### Proof of Concept
1. Owner calls `pointer.approve(spender, 50)` — CW20 allowance becomes 50.
2. Owner decides to change approval and submits `pointer.approve(spender, 100)`.
3. Spender observes the pending transaction in the mempool and front-runs it with `pointer.transferFrom(owner, spender, 50)`, draining the existing allowance to 0 (calls into CW20 `transfer_from`).
4. Owner's `approve(spender, 100)` transaction is then mined; at execution time `allowance(owner, spender) == 0`, so the contract computes `amount - currentAllowance = 100 - 0 = 100` and issues `increase_allowance` for 100, per [2](#0-1) .
5. Spender now has already extracted 50 tokens in step 3 and still holds an unspent allowance of 100 tokens — for a combined authorized-and-spent total of 150 against the owner's intended single outstanding cap of 100.

    function approve(address spender, uint256 amount) public override returns (bool) {
        // if amount is larger uint128 then set amount to uint128 max
        if (amount > type(uint128).max) {
            amount = type(uint128).max;
        }
        uint256 currentAllowance = allowance(msg.sender, spender);
        if (currentAllowance > amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(currentAllowance - amount)));
            string memory req = _curlyBrace(_formatPayload("decrease_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        } else if (currentAllowance < amount) {
            string memory spenderAddr = _formatPayload("spender", _doubleQuotes(AddrPrecompile.getSeiAddr(spender)));
            string memory amt = _formatPayload("amount", _doubleQuotes(Strings.toString(amount - currentAllowance)));
            string memory req = _curlyBrace(_formatPayload("increase_allowance", _curlyBrace(_join(spenderAddr, amt, ","))));
            _execute(bytes(req));
        }
        return true;
    }
