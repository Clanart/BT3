### Title
Dead `_calExpireForfeit` logic in `mWOMSVBaseRewarder` permanently prevents cooldown-slot forfeiture, letting users hold mWomSV indefinitely in cooldown while still farming the full, un-forfeited bonus-token stream - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` is a no-op: it sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` is always `0` regardless of the account or how long a position has sat in cooldown. Because `balanceOf()` in this rewarder counts a user's full staked mWomSV (locked + in-cooldown) identically via `IMasterMagpie.stakingInfo`, and no forfeiture is ever applied on claim, a user can remain in `mWomSV`'s cooldown slots indefinitely (refreshing via `cancelUnlock`/`startUnlock`) and still receive the exact same bonus-reward stream as a fully-locked user, while retaining full optionality to withdraw principal at any time.

### Finding Description
`_sendReward` computes the amount to forfeit on every claim: [1](#0-0) 

The forfeiture calculation itself is broken: [2](#0-1) 

`rewardableAmount` is assigned `_amount` and never modified before the `forfeitAmount = _amount - rewardableAmount` subtraction, so `forfeitAmount` is mathematically always `0`. The `_account` parameter is completely unused, meaning no per-user cooldown/expiry state (start/end time, slot occupancy) is ever consulted despite the function's name and the existence of `getFullyUnlock`/`getRewardablePercentWAD` in `wombat/mWomSV.sol` that compute exactly this kind of "rewardable percent" data (fully-locked vs in-cooldown vs expired-cooldown).

Reward accrual itself is agnostic to lock state: `balanceOf()` in the rewarder just reads `IMasterMagpie(masterMagpie).stakingInfo(stakingToken, _account)`, and `mWomSV.balanceOf()` sums `getUserTotalLocked` + `getUserAmountInCoolDown` identically. `startUnlock`/`cancelUnlock` in `wombat/mWomSV.sol` [3](#0-2)  let a user shuffle any portion of their stake between "locked" and "in cooldown" states across up to `maxSlot` slots without ever reducing their staked/reward-earning balance and without ever calling `unlock()` to actually withdraw, since `cancelUnlock` simply zeroes `amountInCoolDown` and resets state, restarting the cycle before `endTime` is reached.

Because the on-chain reward math never penalizes cooldown/expired positions, a user who never intends to fully unlock (i.e., never wants to be "fully locked") earns exactly the same bonus rewards as a genuinely committed, fully-locked user, and the intended redistribution of forfeited yield back into `rewardPerTokenStored` (via `_queueNewRewardsWithoutTransfer`) never occurs.

### Impact Explanation
This falls under "theft or permanent freezing of unclaimed yield": the yield that should have been forfeited by non-committed (cooldown/expired) positions and redistributed to fully-locked stakers via `_queueNewRewardsWithoutTransfer` is instead permanently retained by every claimant, indefinitely, since the forfeiture check can never trigger. Honest long-term lockers never receive the boosted `rewardPerTokenStored` that the forfeiture design intended, which is a systemic conservation violation of the reward-splitting invariant described by the protocol's own `_calExpireForfeit`/`calExpireForfeit` naming and unused cooldown-state getters (`getFullyUnlock`, `getRewardablePercentWAD`).

### Likelihood Explanation
This requires no special capital or attacker sophistication beyond normal protocol usage: any holder of mWOM can `lock()`, call `startUnlock()` for some/all of their position, and simply never call `unlock()` — optionally refreshing via `cancelUnlock`/`startUnlock` — while continuing to call `getRewards`/`getReward` through `MasterMagpie`. It is 100% reproducible and requires zero privileged access; it is in fact the default behavior for every current user of the pool, since the forfeiture code path is unconditionally dead for all callers, not just a crafted attacker.

### Recommendation
Implement the missing cooldown-based forfeiture logic in `_calExpireForfeit`: use `mWOMSV.getUserAmountInCoolDown`/`getFullyUnlock`/`getRewardablePercentWAD` (or equivalent) to compute the actual rewardable fraction of `_account`'s balance based on how much of their stake is fully locked vs. in cooldown vs. expired-but-unwithdrawn, and forfeit the remainder into `_queueNewRewardsWithoutTransfer` as originally intended, instead of the current tautological `rewardableAmount = _amount` assignment.

### Proof of Concept
Foundry test plan:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, and `MasterMagpie` fixtures with `maxSlot = N`.
2. User A: `lock(amount)` and never touches cooldown (fully locked, "honest long-term locker").
3. User B: `lock(amount)` equal to A's, then `startUnlock(amount)` on slot 0, and repeatedly before `endTime` call `cancelUnlock(0)` then `startUnlock(amount)` again (or spread across `maxSlot` slots) to remain perpetually "in cooldown" without ever calling `unlock()`.
4. Queue bonus rewards via `queueNewRewards`.
5. Advance time past several cooldown periods for B without B ever finishing `unlock()`.
6. Call `getReward`/`getRewards` for both A and B via `MasterMagpie`.
7. Assert: `userRewards` claimed by A and B are identical per unit staked (i.e., B is never penalized), and `calExpireForfeit(B, token)` returns `0` for all calls regardless of B's cooldown/expired state — demonstrating the forfeiture invariant (fully-locked users should end up with strictly higher effective `rewardPerTokenStored` due to redistributed forfeits from B) never holds.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
