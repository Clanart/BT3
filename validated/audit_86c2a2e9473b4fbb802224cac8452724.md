### Title
Flat gas pricing for `Bank.all_balances`/`spendableBalances` precompile enables unbounded KVStore-scan for fixed EVM gas cost via unbounded tokenfactory denom creation - ([File: precompiles/bank/bank.go])

### Summary
The `Bank` precompile's `RequiredGas` charges a constant, input-size-based gas cost (`pcommon.DefaultGasCost`) regardless of which method is called, but `all_balances` (and similarly `spendableBalances`/`totalSupply`/`denomsMetadata`) perform an unbounded iteration over an account's/module's coin balances via `p.bankKeeper.GetAllBalances` [3](#0-2) . Because any unprivileged tokenfactory user can mint an arbitrarily large number of distinct denoms to a single address (no per-address balance-count cap enforced at the bank/tokenfactory layer visible in this precompile), the actual number of KVStore reads performed by a single call to `all_balances` is attacker-controlled and unbounded, while the EVM gas charged for that call remains flat/minimal since it's derived only from the ABI-encoded input size and not from the resulting KVStore work [4](#0-3) .

### Finding Description
`RequiredGas` is the sole gas gate for this precompile call and is computed purely from `input` bytes and whether the method is a "transaction" method (`send`/`sendNative`) [1](#0-0) [5](#0-4) . The `all_balances` handler itself performs no bound on the number of coins returned by `GetAllBalances` before iterating and packing them into the ABI response [2](#0-1) . An attacker can:
1. Create an arbitrary number of tokenfactory denoms (tokenfactory denom creation is reachable by any account, bounded only by the fee/gas of the mint transactions themselves, executed over many separate transactions/blocks).
2. Mint a small amount of each of these denoms into one target address (their own address, or any address they choose to grief, e.g. a widely-used contract or pointer address).
3. Deploy a trivial EVM contract, or use an existing one, that calls `Bank.all_balances(targetAddress)` in a single transaction.

Because the precompile's declared/charged gas is flat (`DefaultGasCost`), and the actual iteration cost of `GetAllBalances` scales linearly (or worse, given underlying IAVL iterator overhead) with the number of distinct denoms held by `targetAddress`, a single, cheap-looking EVM call can force the node to scan and marshal an arbitrarily large balance set built up over prior blocks. This is the same root-cause class as the H-1 report: an unbounded loop over user-controlled/attacker-inflated state, driven by a single reachable entry point, whose cost is not properly bounded relative to the gas charged for triggering it.

### Impact Explanation
Repeated or crafted calls to `all_balances` against an address preloaded with a very large number of denoms can consume disproportionate block-processing time relative to the gas paid, since block-level EVM gas limits are meant to bound per-block CPU/IO work but here the actual cost is decoupled from the gas metered. This can degrade block production throughput and, at scale (thousands of denoms), push per-transaction/per-block processing time beyond acceptable bounds, risking block-time delay. It does not directly cause fund loss, but it is a resource-exhaustion / DoS-adjacent vector reachable by any unprivileged EVM caller using only public tokenfactory and EVM entry points.

### Likelihood Explanation
Likelihood is dependent on there being no cap on the number of denoms a single address can hold and no cap on `GetAllBalances`'s returned set size, both of which appear absent from the reviewed code paths. Exploitation requires the attacker to first spend gas/fees creating many tokenfactory denoms and minting tiny amounts to the target address across possibly many transactions/blocks — a real but not prohibitive cost, since tokenfactory denom creation fees are typically nominal and this can be amortized over time before the "attack" transaction is fired.

### Recommendation
Scale `RequiredGas`/the EVM gas actually charged for `all_balances`, `spendableBalances`, `totalSupply`, and `denomsMetadata` to the number of balance/denom entries actually scanned (e.g., charge gas proportional to iterator steps, or clamp/paginate results and require the caller to pay per page), and/or enforce a hard cap on the number of distinct denoms a single account can hold (or that a single precompile call will iterate) so that a bounded amount of state is scanned per call regardless of how many denoms an attacker has pre-seeded onto a target address.

### Proof of Concept
1. Use `x/tokenfactory` `MsgCreateDenom` repeatedly (any unprivileged account) to create N (e.g., 50,000) distinct denoms.
2. For each created denom, mint a minimal amount to a target Sei/EVM address using `MsgMint`.
3. From an EVM contract or `eth_call`, invoke `Bank.all_balances(targetAddress)` on precompile address `0x0000000000000000000000000000000000001001` [6](#0-5) .
4. Observe that `RequiredGas` for this call remains the flat `DefaultGasCost` value independent of N [1](#0-0) , while the underlying `GetAllBalances` iterates and marshals N coin entries [7](#0-6) , demonstrating gas-cost/actual-work mismatch that scales with attacker-chosen N.

```go
func (p PrecompileExecutor) all_balances(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) ([]byte, uint64, error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	addr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}

	coins := p.bankKeeper.GetAllBalances(ctx, addr)

	// convert to coin balance structs
	coinBalances := make([]CoinBalance, 0, len(coins))

	for _, coin := range coins {
		coinBalances = append(coinBalances, CoinBalance{
			Amount: coin.Amount.BigInt(),
			Denom:  coin.Denom,
		})
	}

	bz, err := method.Outputs.Pack(coinBalances)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
```
