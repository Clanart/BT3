### Title
Panic on point-at-infinity aggregate nonce in BIP-340 `Hram` allows a malicious signing participant to crash signers - (File: networks/bitcoin/src/crypto.rs)

### Summary
The FROST-BIP340 signing path used for Bitcoin spends computes its challenge via `Hram::hram`, which unconditionally calls `x(R)` / `x(A)` to extract x-coordinates. `x()` panics (`expect("point at infinity")`) if the point is the identity. The aggregate nonce `R` is a linear combination of per-participant nonce commitments read from untrusted preprocess bytes via `read_preprocess`/`Commitments::read`, with no identity or subgroup check. A malicious participant can therefore force the aggregate `R` (or their own bound contribution) to the point at infinity, triggering a panic that crashes the signing process mid-protocol — the Rust analog of the null-pointer dereference class (crafted input → unchecked dereference → availability loss).

### Finding Description
- `Hram::hram` calls `x(R)` and `x(A)` on every sign/verify ( [1](#0-0) ).
- `x()` panics on infinity: `(*encoded.x().expect("point at infinity"))` ( [2](#0-1) ). `x_only()` similarly `expect`s ( [3](#0-2) ).
- `R` for each input is built as `Rs = B.nonces(&nonces)`, i.e. sums of each participant's nonce commitments plus a binding-factor–weighted component ( [4](#0-3) ). The commitments come from `read_preprocess` → `Commitments::read`, which deserializes raw encodings with only `read_G` canonicity checks — no non-identity check ( [5](#0-4) , [6](#0-5) ).
- `sign_share`/`verify`/`verify_share` then invoke `hram` with these attacker-influenced points ( [7](#0-6) ).
- A participant choosing nonce commitments such that the per-input aggregate `R = sum_i (D_i + rho_i * E_i)` is the identity (e.g., supplying an identity/adversarially-cancelled commitment vector — a ROS-style contribution computed against the binding factors) forces `x(R)` to panic inside `TransactionSignMachine::sign`'s `sig.sign(...)` loop and inside `AlgorithmSignatureMachine::complete` → `Schnorr::verify` ( [8](#0-7) , [9](#0-8) ). Since `schnorr.verify` uses `Scalar::conditional_select` only for sign parity, the identity check is never performed.
- The docstring even acknowledges this: "This may panic if called with nonces/a group key which are the point at infinity" ( [10](#0-9) ) — and the codebase treats task panics as fatal (`std::process::exit(1)` panic hook pattern, [11](#0-10) ), so the panic is a node crash, not a caught error.

### Impact Explanation
A single malicious threshold participant can deterministically crash honest validator/processor nodes during any Bitcoin signing session they join, repeatedly aborting signing rounds and halting multisig operations (denial of service / availability). The panic occurs after the victim has committed its preprocess, so restart-and-retry loops are trivially re-triggered. No secret leakage, but sustained signing outage for the Bitcoin network key.

### Likelihood Explanation
Requires only the ability to participate in a signing session and broadcast a crafted preprocess — bytes fully under the attacker's control, parsed via `read_preprocess`. The adversary sees all other participants' preprocesses before `sign()` computes binding factors (simultaneous broadcast, but the attacker can also simply submit an identity nonce commitment, which is not rejected by `Commitments::read`/`read_G`, making `B.bound(l)` contributions degenerate). Exploitation cost is low and repeatable each session.

### Recommendation
In `x()`/`x_only()` (networks/bitcoin/src/crypto.rs), return `Option`/`io::Result` and propagate instead of `expect`; in `Hram::hram`, detect `R`/`A` identity and either return a deterministic challenge or signal `FrostError`. Additionally, reject identity nonce commitments in `Commitments::read` (crypto/frost) and reject identity aggregate `R` in `Algorithm::verify`/`verify_share` before calling into curve-specific code.

### Proof of Concept
```rust
// Participant i crafts preprocess bytes whose nonce commitments encode the
// identity point (canonical compressed encoding of infinity is rejected by
// read_G, so instead the attacker picks commitments D_i, E_i such that
// D_i + rho_i * E_i cancels the other participants' bound contributions —
// rho_i is computable by the attacker from the public rho_transcript inputs:
// group_key, hash_msg(msg), hash_commitments(preprocesses)).
//
// feed into victim's machine:
let preprocess: Vec<Preprocess<Secp256k1, ()>> =
    machine.read_preprocess(&mut crafted_bytes).unwrap(); // succeeds
// victim calls:
let (_machine, _share) = sign_machine.sign(preprocesses_with_crafted, b"").unwrap();
// -> taproot sighash computed, sig.sign(...) -> Schnorr::sign_share -> hram(R, A, m)
// -> x(R) where aggregate R == ProjectivePoint::IDENTITY
// -> panic: "point at infinity"  (process abort under fatal-panic hook)
```
Uncertain detail: whether `Commitments::read` bounds the nonce-commitment vector length against `algorithm.nonces().len()` was not verified (crypto/frost/src/nonce.rs not read); even with a length check, the identity/cancellation attack on the aggregate `R` stands, since it requires only validly-encoded points chosen algebraically.
