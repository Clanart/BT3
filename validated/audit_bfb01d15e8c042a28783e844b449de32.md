### Title
Zero-duration unlock slot causes `getRewardablePercentWAD` to undercount fully-unlocked MGP, forfeiting legitimate user reward yield - (File: `VLMGP.sol`)

### Summary
`VLMGP.getRewardablePercentWAD()` computes the fraction of a user's vlMGP position that is "rewardable" (i.e., still genuinely committed) versus what should be treated as forfeitable. This percentage directly drives how much of a user's pending MGP/reward tokens get paid out versus permanently redirected away from the user in `vlMGPBaseRewarder._calExpireForfeit`. When a user's unlock slot has `endTime == startTime` (a zero-length cooldown), the time-weighting term for a fully-unlocked slot evaluates to zero, silently dropping that slot's contribution from the rewardable percentage instead of counting it at full weight.

### Finding Description
In `VLMGP.sol`, for a fully unlocked slot (`block.timestamp > userUnlocking[i].endTime`), the percent contribution is: [1](#0-0) 

```
if (userUnlocking[i].amountInCoolDown > 0) {
    if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
        percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
            / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
    }
    else {// still in cool down 
        percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
    }
}
```

The numerator includes the factor `(userUnlocking[i].endTime - userUnlocking[i].startTime)`. If this slot was started when `coolDownInSecs == 0` (a valid, non-malicious configuration value — `coolDownInSecs` has no minimum enforced in `__vlMGP_init_`), then `endTime == startTime` at slot creation: [2](#0-1) 

```
if (_slotIndex < getUserUnlockSlotLength(msg.sender)) {
    userUnlockings[msg.sender][_slotIndex] = UserUnlocking({
        startTime: block.timestamp,
        endTime: block.timestamp + coolDownInSecs,
        amountInCoolDown: _amountToCoolDown
    });
} else {
    userUnlockings[msg.sender].push(
        UserUnlocking({
            startTime: block.timestamp,
            endTime: block.timestamp + coolDownInSecs,
            amountInCoolDown: _amountToCoolDown
        })
    );
}
```

Once `block.timestamp > endTime`, the "fully unlocked" branch is taken and the `(endTime - startTime)` factor is `0`, making the entire slot's contribution to `percent` equal to `0` — exactly analogous to the Behodler `adjustedRectangle` bug, where a zero component of a multiplicative term zeroes out an otherwise legitimate quantity used downstream.

This under-computed `percent` (rewardablePercentWAD) is then consumed in `vlMGPBaseRewarder._calExpireForfeit`: [3](#0-2) 

```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    
    if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
        forfeitAmount = 0;
        rewardableAmount = _amount;
    }

    return forfeitAmount;
}
```

Because the affected slot's amount is missing from `percent`, `rewardablePercentWAD` is smaller than it should be, so `rewardableAmount` is understated and `forfeitAmount` is overstated. The excess is then routed to `_queueNewRewardsWithoutTransfer`, permanently redistributing it away from the affected user instead of paying it out: [4](#0-3) 

### Impact Explanation
The affected user's legitimately earned MGP/reward-token yield (both from `queueMGP` and from `getReward`/`getRewards` via `_sendReward`) is wrongly classified as forfeitable and diverted into the reward pool for other stakers, permanently taking it away from the user who is entitled to it. This is a direct, permanent loss of unclaimed yield for the affected account, scaling with the size of the zero-duration unlock slot relative to the user's total vlMGP.

### Likelihood Explanation
The trigger condition (`coolDownInSecs == 0` at the time a user calls `startUnlock`) is a legitimate configuration state — nothing in `__vlMGP_init_` enforces a non-zero cooldown, and any ordinary user calling `startUnlock()` while that value is `0` reaches this path without needing any privileged action at the time of their own transaction. Once such a slot exists and time passes one block, every subsequent harvest/claim for that account computes an incorrect `rewardablePercentWAD` and forfeits yield until the slot is unlocked via `unlock()`.

### Recommendation
Guard the fully-unlocked branch against a zero-length duration, e.g., treat `endTime == startTime` slots as contributing their full `amountInCoolDown` at 1e18 weight (same as the "still in cool down" branch), or explicitly special-case `(endTime - startTime) == 0` before performing the division, rather than letting it silently zero out the numerator.

### Proof of Concept
1. Owner deploys/configures `VLMGP` with `coolDownInSecs = 0` (a valid non-restricted value at `__vlMGP_init_` time).
2. User locks MGP and calls `startUnlock(amount)`; the created slot has `startTime == endTime == block.timestamp`.
3. One block later, `block.timestamp > endTime` is true, so `getRewardablePercentWAD` computes `(endTime - startTime) = 0`, zeroing that slot's contribution to `percent`.
4. User calls `getReward`/`getRewards` on `vlMGPBaseRewarder`; `_calExpireForfeit` computes an inflated `forfeitAmount` because `rewardablePercentWAD` omits the unlocked slot's share, and that amount is permanently redirected via `_queueNewRewardsWithoutTransfer` instead of being paid to the user.
