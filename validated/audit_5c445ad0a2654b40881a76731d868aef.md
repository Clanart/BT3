## Analog Found

### Title
Recipient of a Credential-Restricted CAT (CR-CAT) cannot recover pending-approval funds if their Verified Credential is revoked or unavailable, with no way to redirect to another VC/address - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
The Sherlock report describes ERC20 `recoverERC20()` functions that always transfer to a hardcoded `recipient()`/`owner()` address with no ability to redirect, so if that address is blacklisted by the token contract, the funds are permanently stuck. Chia's CR-CAT (credential-restricted CAT) system has the same structural weakness: incoming CR-CATs sent to a user who is not yet approved are locked into a `construct_pending_approval_state()` puzzle that can *only* be released by that exact recipient spending it together with a valid, provider-authorized `VerifiedCredential` (VC). There is no alternate recovery path or ability to redirect the coin if the recipient's VC becomes invalid.

### Finding Description
When a CR-CAT is sent to an address the sender's wallet cannot itself verify (no matching VC), `CRCATWallet.generate_signed_transaction` wraps the output in `construct_pending_approval_state(puzhash, amount)` [1](#0-0) . This pending coin can later be released via `claim_pending_approval_balance`, but only after finding a VC that satisfies the CR-CAT's `authorized_providers`/`proofs_checker`:

```
vc: VerifiedCredential | None = await vc_wallet.get_vc_with_provider_in_and_proofs(
    self.info.authorized_providers, self.info.proofs_checker.flags
)
if vc is None:  # pragma: no cover
    raise RuntimeError(f"No VC exists that can approve spends for CR-CAT wallet {self.id()}")
``` [2](#0-1) 

The VC itself can be permanently invalidated by its `proof_provider` (typically a DID controlled by an issuer/regulator) via `activate_backdoor()`/`revoke_vc()`, which spends the VC through the revocation layer and removes the recipient's credential from circulation [3](#0-2) [4](#0-3) . `VCWallet.get_vc_with_provider_in_and_proofs` only returns a VC if `all(proof in vc_proofs.key_value_pairs for proof in proofs)` holds for some currently owned, provider-matching VC [5](#0-4) . If the recipient's only qualifying VC is revoked (or they simply never obtain one matching the CR-CAT's exact `authorized_providers`/flags), `claim_pending_approval_balance` can never succeed for that coin — there is no `beneficiary`/redirect parameter, no fallback inner puzzle, and no owner-level escape hatch analogous to the `recoverERC20(beneficiary)` fix recommended in the report.

This mirrors the reported bug class exactly: an unprivileged party (here, the CR-CAT recipient, or an offer counterparty per `check_for_requested_payment_modifications` in `trade_manager.py`, which forces CR-CAT proceeds of a trade into this same pending state [6](#0-5) ) has funds routed to a puzzle hash whose spendability depends entirely on an off-chain authorization (VC/blacklist-equivalent) that a third party (the DID/provider) can revoke, with no alternate destination ever encoded on-chain.

### Impact Explanation
Funds sent to a CR-CAT recipient (directly, or as offer settlement proceeds) become permanently unspendable if the recipient's VC is revoked by the issuing DID or if the recipient can no longer produce a VC satisfying the exact `authorized_providers`/`proofs_checker` combination baked into the coin. Because the claim path is the *only* spend path out of `construct_pending_approval_state`, this is a durable loss of funds for the affected wallet, matching the Medium-severity characterization in the source report (locked assets, no ability to redirect to a working address).

### Likelihood Explanation
This requires a CR-CAT deployment (an opt-in, credential-gated asset type) and a scenario where the provider revokes the VC or the recipient's credentials lapse/are never matched — a realistic administrative action for regulated/permissioned CR-CAT issuers, analogous to an ERC20 issuer blacklisting an address. It is not attacker-triggered against arbitrary users, but it is a foreseeable operational event for any CR-CAT deployment relying on VC lifecycle management.

### Recommendation
Add an escape/redirect mechanism for pending-approval CR-CAT coins, e.g., allow the pending coin to be claimed to an alternate destination once authorized by *any* currently valid VC satisfying the proofs checker (not solely one previously associated with the recipient), or add a sender-controlled reclaim path with a timeout, mirroring the `beneficiary` parameter pattern recommended in the source report so funds are not permanently bound to a single potentially-revoked credential.

### Proof of Concept
1. Sender A sends CR-CAT tokens to recipient B who does not yet have a matching VC; the coin is created in `construct_pending_approval_state(B_ph, amount)` per `generate_signed_transaction` [1](#0-0) .
2. Before B claims it, the DID acting as `proof_provider` calls `revoke_vc`/`activate_backdoor` on B's VC [4](#0-3) .
3. B calls `claim_pending_approval_balance`; `get_vc_with_provider_in_and_proofs` finds no valid VC and raises `RuntimeError` [2](#0-1) .
4. There is no alternate spend path for the pending coin — the CR-CAT amount is permanently locked, with no way to redirect it to B's or anyone else's spendable address.

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
```
