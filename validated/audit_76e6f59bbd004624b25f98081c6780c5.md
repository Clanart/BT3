### Title
`ThresholdKeys::read` accepts attacker-crafted key material without verifying `secret_share` matches `verification_shares` — deserialized keys bind to an attacker-controlled group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, an interpolation method, a `secret_share`, and `n` verification shares, then hands them to `ThresholdKeys::new`. `ThresholdKeys::new` validates the count/range of verification shares and the interpolation variant, but never checks that `generator() * secret_share == verification_shares[i]`, nor that the shares are mutually consistent. `group_key` is derived purely from `verification_shares[1..=t]` via interpolation — the secret share is trusted blindly.

### Finding Description
The Magento advisory class is missing sanitization in a data flow: attacker-supplied bytes flow into a trusted object without consistency checks. Here, `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) is a named untrusted-bytes sink. It reads:

- `t`, `n`, `i` → `ThresholdParams::new` (checked only for `0 < t <= n`, `i <= n`)
- `Interpolation::Constant(c)` reads `n` scalars; `ThresholdKeys::new` only checks `t == n` for Constant, never `c.len() == n` — `interpolation_factor` later indexes `c[i-1]` (`crypto/dkg/src/lib.rs:228`)
- `secret_share` — arbitrary canonical scalar, never related to anything
- `verification_shares` for participants `1..=n` — arbitrary points (canonical, but unrestricted)

`ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) computes `group_key = Σ verification_shares[i] * interpolation_factor(i, {1..=t})` and stores everything. No check binds `secret_share` to `verification_shares[i]` (`generator() * secret_share`) or to the group key at index 0 of the sharing polynomial.

In honest flows (PedPoP `calculate_share`, `crypto/dkg/pedpop/src/lib.rs:463-532`) the share is verified via `share_verification_statements` before `ThresholdKeys::new` is called — the invariant is maintained externally. The `read` path bypasses it entirely.

### Impact Explanation
An attacker who supplies a serialized `ThresholdKeys` blob controls the resulting `group_key` (set verification shares to interpolate to a key they know the discrete log of) while the `secret_share` is unrelated garbage. The victim's key store then reports a group key whose funds are spendable by the attacker and not by the victim — funds reported received that are not spendable by the holder. Alternatively, with consistent verification shares but a wrong `secret_share`, every FROST signature share the victim produces is invalid, poisoning signing sessions under the victim's identity.

### Likelihood Explanation
Requires the attacker to feed bytes to `ThresholdKeys::read` — the listed reachable sink — e.g., a malicious coordinator/peer-supplied key serialization. The cryptographic primitives (canonical scalars/points) are all valid, so no deserialization error is raised; the defect is purely the missing semantic consistency check.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), assert `C::generator() * secret_share == verification_shares[&params.i()]` and, for `Interpolation::Constant`, assert `c.len() == n`. Reject encodings where the share does not match its verification share.

### Proof of Concept
```rust
// Attacker builds a blob: t=2, n=3, i=1, Lagrange,
// secret_share = 0x01 (garbage), verification_shares chosen so
// group_key = attacker_pubkey (e.g., shares[1] = A, others identity-like
// or values interpolating to attacker key at x=0).
// Serialization per ThresholdKeys::write layout:
//   u32 id_len || C::ID || t || n || i || 0x01 || secret_share || n points
let keys = ThresholdKeys::<C>::read(&mut blob.as_ref()).unwrap(); // succeeds
assert_eq!(keys.group_key(), attacker_controlled_key);            // no error
// keys.params().i() share never equals generator * secret_share
```
