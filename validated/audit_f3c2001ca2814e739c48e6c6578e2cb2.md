Based on my investigation, the strongest analog to the M-6 pattern ("state committed to memory/action taken from data that was never re-validated against the ground truth before being used for a security-relevant operation") is in GitHub Desktop's Copilot merge-conflict-resolution feature.

### Title
AI conflict-resolution results are written to disk and staged without verifying the resolved path belongs to the actual conflicted file set - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The Zetachain bug was about a value (`gasPrice`) being committed to memory *before* it was validated/voted on, and later consumed by a security-sensitive operation (`VoteOutbound`) that assumed the value had already been validated. The Desktop analog is `_applyCopilotConflictResolutions`, which consumes `copilotResolutions` — data produced by an LLM response whose input includes attacker-influenceable repository content (the conflicting hunks of a cloned/fetched repo) — and writes/stages files based on that data without confirming each resolution's `path` actually corresponds to a file that is part of the current merge conflict.

### Finding Description
`_startCopilotConflictResolution` stores the model's resolutions directly into `multiCommitOperationState.copilotResolutions` after only an abort/ownership check [1](#0-0) , with the comment explicitly noting the actual disk write happens later, on user confirmation.

When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` iterates over `copilotResolutions` and, for each entry, performs a path-traversal check (`resolveWithin`) and then writes/stages the file: [2](#0-1) 

The only guard against writing to a file that is *not* actually part of the current conflict is:
```
const onDiskFile = state.changesState.workingDirectory.files.find(f => f.path === resolution.path)
if (onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)) {
  continue
}
```
This only skips a write when the file *is* a known conflicted path that has *already been resolved externally*. If `onDiskFile` is `undefined` — i.e., `resolution.path` does not correspond to any file the working directory currently reports as changed/conflicted — the loop does **not** skip; it falls through to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` followed by `git add`. `resolveWithin` only enforces that the path stays inside the repository root [3](#0-2) ; it does not restrict the path to files that were part of the conflict set sent to the model.

This mirrors the Zetachain bug's broken invariant exactly: a downstream, security-relevant action (`writeFile` + `git add`, which determines what enters the user's next commit) trusts a value (`resolution.path`/`resolvedContent`) that was accepted into state before it was checked against the actual, current ground truth (the real list of conflicted files).

### Impact Explanation
Because the conflict content fed to the model comes from a cloned/fetched repository (attacker-controlled branch content merged by the victim), a crafted conflict (prompt injection via conflict-marker content) could cause the model to emit a "resolution" entry whose `path` points to any repo-relative file the user hasn't touched (e.g. `.gitattributes`, `.gitignore`, a CI workflow file, or a git hook path under `.git/hooks/` — which is still "under" `repository.path` and thus passes `resolveWithin`). That content is then silently written to disk and `git add`-ed into the working tree, becoming part of what the user commits/pushes without their awareness — a silent corruption of the commit contents. If a git hook file is targeted, this can escalate to code execution on subsequent git operations (`post-checkout`, `pre-commit`, etc.) that invoke local hooks.

### Likelihood Explanation
Exploitation requires that (1) the victim uses the "Resolve with Copilot" conflict-resolution feature, and (2) the model can be induced (via content in the conflicting hunks of the fetched/merged branch) to emit an out-of-scope resolution path. Prompt-injection-style manipulation of LLM tool outputs is a known and increasingly demonstrated class of attack, and the existing safeguard (`onDiskFile` check) only handles the "already resolved externally" case, not "path was never a conflict at all" — so there is no structural check preventing this. I was not able to fully verify, within the tool budget, whether `app/src/lib/copilot-conflict-resolution.ts` (which contains `CopilotValidationError` and other validation logic) already filters/rejects raw model resolutions whose paths fall outside the set of files sent for conflict resolution; this is the key open question that determines actual exploitability and should be confirmed before treating this as conclusively unpatched.

### Recommendation
In `_applyCopilotConflictResolutions` (and/or in the reassembly step in `copilot-conflict-resolution.ts`), validate each `resolution.path` against the authoritative list of currently-conflicted file paths (from `conflictState`/`buildConflictContext`'s `files` list) before writing or staging, rejecting/skipping any resolution for a path that was not part of the actual conflict set — analogous to only trusting `gasPrice` after `PostVoteGasPrice` succeeds rather than before.

### Proof of Concept
1. Attacker publishes a branch that, when merged by the victim, produces a conflict in a normal file but includes crafted content in the conflict hunks designed to prompt-inject the resolution model into also emitting a resolution entry for an unrelated path such as `.git/hooks/post-checkout` with attacker-controlled script content.
2. Victim clicks "Resolve with Copilot" on the merge conflict; the model returns `resolutions` including the injected entry; this is stored via `_startCopilotConflictResolution` without path-membership validation.
3. Victim reviews the (likely truncated/summarized) dialog and clicks "Continue Merge".
4. `_applyCopilotConflictResolutions` finds no `onDiskFile` matching the injected path (since it was never actually conflicted), so the skip condition is false, and it proceeds to `resolveWithin` (passes, since the path is under the repo) and `writeFile`, then `git add`s it.
5. The injected file is now part of the working tree/staged changes; if it lands under `.git/hooks`, the next relevant git operation executes the attacker's script. [2](#0-1) [1](#0-0)

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
