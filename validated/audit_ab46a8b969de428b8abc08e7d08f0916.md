## Title
Cross-function signature replay between `withdraw_fees` and `accumulate_fees` beneficiary redirect drains a relayer's full fee balance using a scoped-redirect signature - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
The relayer pallet signs two different authorizations — a full fee **withdrawal** and a per-batch fee **accumulation-beneficiary redirect** — with byte-identical digests and against the exact same nonce counter. A signature a relayer produces to redirect one small batch's proceeds to a beneficiary can be replayed, before it is consumed, into the withdrawal path to drain the relayer's *entire* accumulated balance to that same beneficiary — a scope-amplification bug structurally identical to the KintoID/Faucet report's "missing function selector in the signed hash" flaw.

### Finding Description
`withdrawal::message` (used by `withdraw_fees`) and `accumulate::beneficiary_message` (used by `accumulate_fees`'s beneficiary redirect) both hash `(nonce, state_machine, beneficiary).encode()`: [1](#0-0) [2](#0-1) 

SCALE-encoding of `Vec<u8>` and `&[u8]` is identical, so for the same `(nonce, state_machine, beneficiary)` triple, `message(nonce, chain, Some(beneficiary))` and `beneficiary_message(nonce, chain, &beneficiary)` produce the exact same digest. Both call sites read the nonce from the **same** `Nonce` storage map keyed by `(address, state_machine)`: [3](#0-2) 

- In `accumulate()`, the signed message only authorizes redirecting the fee from **one specific batch** (`total_fee` of that `withdrawal_proof.commitments`) to the named beneficiary: [4](#0-3) 

- In `withdraw()`, the identical signed message authorizes withdrawing **whatever the current `Fees::<T>::get(dest_chain, address)` balance is** — which can include many prior batches, far larger than the amount the relayer intended when signing the accumulate-redirect message: [5](#0-4) 

Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics gated only by `ensure_none(origin)` and `validate_unsigned`, so anyone observing the cleartext calldata (in the mempool or a pending block) — not just the relayer — can resubmit the captured signature through the sibling call: [6](#0-5) [7](#0-6) 

Nothing in the signed payload binds it to which extrinsic/function it is for, mirroring the reported KintoID/Faucet flaw where "the name of the function for which the signature is given is missing," allowing the same signature to authorize a different, more damaging call.

### Impact Explanation
An attacker who intercepts a relayer's legitimately-produced beneficiary-redirect signature (visible in a pending `accumulate_fees` transaction, since these are unsigned/public calldata) can front-run it into `withdraw_fees` with the same `(nonce, dest_chain, beneficiary)` tuple. This causes the relayer's entire currently-accumulated `Fees` balance for that `(address, state_machine)` — not just the small batch amount the relayer intended to redirect — to be dispatched to the named beneficiary and zeroed out, and simultaneously consumes the nonce so the relayer's originally intended `accumulate_fees` call now fails or lands with unintended semantics. This is unauthorized/incorrect-amount fund movement triggered without the relayer's consent for the excess amount, matching the bounty's "stealing or loss of funds" / "logic attacks" impact class.

### Likelihood Explanation
No privileged role, malicious relayer, or leaked key is required — only public visibility of an in-flight unsigned extrinsic (a property Substrate mempools and block-building already provide) and submission of an equivalent extrinsic before the original is included. Both call paths are always reachable by any account since both are `ensure_none` unsigned calls.

### Recommendation
Bind the signed message to the specific call it authorizes (e.g., include a distinct domain separator/function tag such as `b"ACCUMULATE_REDIRECT"` vs `b"WITHDRAW"` in the hashed tuple), and/or bind the accumulate-redirect signature to the specific `total_fee`/commitment batch amount rather than leaving it interchangeable with an unscoped withdrawal of the full balance. Additionally, consider using disjoint nonce spaces (or including a call-specific salt) for `withdraw_fees` and `accumulate_fees`'s beneficiary path so a signature for one can never satisfy the other's verification.

### Proof of Concept
1. Relayer `R` delivers requests and accrues `Fees[chain][R] = 1000`.
2. `R` submits an `accumulate_fees` call for a new small batch (`total_fee = 10`) with `beneficiary_details = Some((X, sig))` where `sig` is over `beneficiary_message(nonce=N, chain, X)`.
3. Attacker observes this pending extrinsic (calldata is cleartext, unsigned) and immediately submits a `withdraw_fees` call with `WithdrawalInputData { signature: sig, dest_chain: chain, beneficiary: Some(X) }` before `R`'s transaction is included.
4. `withdraw()` recomputes `message(N, chain, Some(X))`, which hashes identically to `beneficiary_message(N, chain, X)`; signature verification passes.
5. `withdraw()` withdraws the full `Fees[chain][R] = 1000` (not 10) to `X`, zeroes the balance, and increments the nonce to `N+1`.
6. `R`'s original `accumulate_fees` call, still carrying nonce `N`, now fails signature/nonce checks — `R` loses control of 990 tokens beyond what was authorized for that batch redirect.

				requires: vec![],

				longevity: TransactionLongevity::MAX,
				propagate: true,
