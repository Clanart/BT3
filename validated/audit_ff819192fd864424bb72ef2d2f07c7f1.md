### Title
Unchecked `int` overflow in packed-field `endPos` computation lets a crafted length-delimited tag desynchronize `CodedInputStreamReader` list parsing - (File: `java/core/src/main/java/com/google/protobuf/CodedInputStreamReader.java`)

### Summary
`CodedInputStreamReader`'s packed-repeated-field readers compute the end-of-field position with a plain `int` addition, `int endPos = input.getTotalBytesRead() + bytes;`, where `bytes` is the attacker-controlled declared length read via `input.readUInt32()`. If `getTotalBytesRead() + bytes` exceeds `Integer.MAX_VALUE`, this wraps to a small/negative `int`, exactly mirroring the Astaria `yIntercept` unchecked-addition overflow pattern (attacker-controlled operand added to a running total without an overflow check, corrupting a boundary value used for downstream accounting/loop-termination logic).

### Finding Description
In `CodedInputStreamReader.java`, every packed-list reader (`readUInt64List`, `readInt64List`, `readFixed64List`, `readFixed32List`, `readSFixed32List`, `readSFixed64List`, etc.) follows this pattern: [1](#0-0) 

```java
case WIRETYPE_LENGTH_DELIMITED:
  final int bytes = input.readUInt32();
  int endPos = input.getTotalBytesRead() + bytes;
  while (input.getTotalBytesRead() < endPos) {
    plist.addLong(input.readUInt64());
  }
  requirePosition(endPos);
  break;
```

`bytes` comes directly from the wire as a `readUInt32()` varint decode — attacker controlled and can be as large as `0xFFFFFFFF` (interpreted as a signed `int`, i.e. up to `Integer.MAX_VALUE` or negative). `input.getTotalBytesRead()` is the current cumulative offset into the stream. The sum `getTotalBytesRead() + bytes` is computed as a plain `int` addition with no overflow guard analogous to `CodedInputStream.isBeyondLimit`'s overflow-conscious check: [2](#0-1) 

or `CodedInputStream.pushLimit`'s explicit overflow clamp: [3](#0-2) 

Because the fixed/varint-packed readers in `CodedInputStreamReader` never route `bytes` through `pushLimit`/`isBeyondLimit` before computing `endPos` — they only call `verifyPackedFixed32Length`/`verifyPackedFixed64Length` for fixed-width types to check divisibility, not overflow — the `getTotalBytesRead() + bytes` addition itself is unchecked in exactly the same way the Solidity report's `yIntercept += ...` addition was unchecked. This is the same failed invariant class: an attacker-controlled magnitude is added to an internal running total without confirming the sum does not wrap the integer type, and the wrapped value is then used to drive a boundary comparison (`while (getTotalBytesRead() < endPos)` / `requirePosition(endPos)`), analogous to `totalAssets` in the Astaria bug being computed too small and gating downstream logic incorrectly.

However, this must be checked against the actual reachable exploitation path in this checkout, which I was **not able to fully confirm** in this session: I could not locate the `requirePosition(...)` method body or `CodedInputStream.getTotalBytesRead()` implementation within the available tool budget to verify whether `requirePosition` re-validates the wrapped `endPos` against the stream's real limit (which is itself overflow-protected via `pushLimit`) and throws before any out-of-bounds effect occurs. Given that `CodedInputStream.pushLimit` already rejects a `currentLimit` that would make `getTotalBytesRead()` exceed `Integer.MAX_VALUE` for the enclosing message, `bytes` for any given field is bounded by the previously-validated outer limit, which constrains how large `getTotalBytesRead() + bytes` can actually get in practice for a single well-formed nested read. This significantly narrows or potentially eliminates the reachable overflow window.

### Impact Explanation
If reachable, a wrapped `endPos` (small or negative) would cause the `while (input.getTotalBytesRead() < endPos)` loop to be skipped entirely (treating a large packed field as empty), silently truncating list contents rather than causing memory corruption — the C++/upb backends use pointer-limit arithmetic with different overflow-check invariants (`ParseContext`/`EpsCopyInputStream`) and are not affected by this specific `int endPos` computation. This is at most a message-integrity/data-truncation issue, not memory corruption or RCE, and depends entirely on whether `pushLimit`'s existing overflow guard on the enclosing message already forecloses the wrap for any field read at that depth — a point I could not fully verify.

### Likelihood Explanation
Low-to-uncertain. Reaching an actual overflow of `getTotalBytesRead() + bytes` (both `int`) requires the stream to already have read close to `Integer.MAX_VALUE` bytes, which for array-backed `CodedInputStream` instances is bounded by the buffer/array length (typically far less than 2^31), and for stream-backed instances is separately guarded by `setSizeLimit`/`pushLimit` overflow checks upstream. I was unable to confirm within this session whether any code path allows `bytes` (attacker length prefix) to be added to a `getTotalBytesRead()` value close enough to `Integer.MAX_VALUE` to wrap, given the outer `pushLimit` overflow protection already in place.

### Recommendation
Route the `endPos` computation in `CodedInputStreamReader`'s packed-list readers through the same overflow-conscious check used elsewhere in `CodedInputStream` (e.g., `isBeyondLimit`) rather than a raw `int` addition, or compute the sum in a wider type (`long`) and validate it fits before truncating back to `int`, mirroring the mitigation pattern already applied in `CodedInputStream.pushLimit`.

### Proof of Concept
I was not able to construct and run a concrete Java reproduction in this session (no execution environment available, and I could not fully verify `requirePosition`'s implementation or `getTotalBytesRead()`'s exact semantics to determine whether the wrap is actually reachable end-to-end). This finding should be treated as a **candidate analog requiring further verification** — specifically, tracing `requirePosition` and confirming whether `pushLimit`'s existing `INT_MAX`-aware guard on the enclosing message forecloses this addition from ever overflowing for any legitimately-nested field read — before treating it as a confirmed, exploitable vulnerability.

    @CanIgnoreReturnValue
    public int pushLimit(int byteLimit) throws InvalidProtocolBufferException {
      if (byteLimit < 0) {
        throw InvalidProtocolBufferException.negativeSize();
      }
      int newLimit = pos + byteLimit;
      if (newLimit < 0) {
        // Absolute limit overflowed. Check if relative limit would have overflowed. This is
        // slightly odd but done this way to maintain the semantics of the prior implementation.
        if (byteLimit > Integer.MAX_VALUE - (pos - startPos)) {
          throw InvalidProtocolBufferException.sizeLimitExceeded();
        }
        // It wouldn't have overflowed relatively, so clamp it to Integer.MAX_VALUE.
        newLimit = Integer.MAX_VALUE;
      }
      final int oldLimit = currentLimit;
      if (newLimit > oldLimit) {
        throw InvalidProtocolBufferException.truncatedMessage();
      }
      setCurrentLimit(newLimit);

      return oldLimit;
    }

     * Helper to perform an integer-overflow-conscious check that {@code currentOffset + bytesToAdd}

    private static boolean isBeyondLimit(int currentOffset, int bytesToAdd, int limit) {
