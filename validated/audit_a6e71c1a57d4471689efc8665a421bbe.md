### Title
Self-reported, unvalidated `Fee.GasEstimate` lets an attacker desynchronize `ProcessProposal`'s block-gas admission check from real EVM execution cost, enabling block processing delay - ([File: app/app.go])

### Summary
`GasEstimate` is a field inside `AuthInfo.Fee` that is part of the signed transaction envelope and is fully attacker-controlled: any account building and signing its own Cosmos SDK transaction (e.g., wrapping a `MsgEVMTransaction`) can set it to an arbitrary value via `SetGasEstimate` [1](#0-0)  independent of the transaction's actual computational cost. `checkTotalBlockGas`, which gates block admission in `ProcessProposal`, prefers this self-reported estimate over the real `gasWanted` whenever it is between `MinGasEVMTx` and `gasWanted` [2](#0-1) , letting a malicious sender make an expensive transaction look cheap to the admission check while it still executes up to its real, much larger `gasWanted` limit during `DeliverTx`.

### Finding Description
This is the same bug class as the GMX H-3 report: a downstream, security/liveness-relevant admission decision is made from a gas estimate that does not reflect the actual resource consumption of the operation, and the estimate/consumption pair is not kept consistent.

In sei-chain, `checkTotalBlockGas` sums, for each EVM transaction, either `decodedTx.GetGasEstimate()` (if it is `>= MinGasEVMTx` and `<= gasWanted`) or the full `gasWanted`, and rejects the proposal if the sum exceeds `ConsensusParams.Block.MaxGas`: [3](#0-2) 

The intended honest path is `eth_sendRawTransaction`, where the RPC node itself computes `gasUsedEstimate` via a real `eth_estimateGas` simulation (`s.simulateTx`) before setting it on the outer Cosmos tx with `txBuilder.SetGasEstimate(gasUsedEstimate)`: [4](#0-3) 

However, `GasEstimate` lives in `AuthInfo.Fee`, a field the transaction's own signer fully controls and signs over — there is no re-derivation or independent verification of it anywhere in the ante/ProcessProposal pipeline. A transaction crafted and broadcast directly (bypassing `eth_sendRawTransaction`'s honest simulation, e.g. via `broadcast_tx_*`) can set an arbitrarily low `GasEstimate` (as low as `MinGasEVMTx = 21000`) while still declaring a very large `gasWanted` (`tx.Gas()`), and `21000 <= gasWanted` always holds, so the low, fake estimate is what counts toward the block's admission check.

Crucially, the actual gas limit enforced during real `DeliverTx` execution is derived from `txGas := txData.GetGas()` (i.e., real `gasWanted`), not from `GasEstimate`: [5](#0-4) 

So `GasEstimate` only affects the `ProcessProposal` sanity check, while the real EVM gas meter is sized off the full `gasWanted`. A validator/proposer (or any attacker whose crafted tx is chosen by a proposer, honest or malicious) can therefore submit many transactions that each execute expensive, gas-heavy contract logic (consuming gas close to their real `gasWanted`), while collectively declaring `GasEstimate`s that sum to well under `MaxGas`. `ProcessProposal` on every honest validator accepts such a block because `checkTotalBlockGas` only sees the deflated `GasEstimate` sum, but `FinalizeBlock`/`DeliverTx` then actually executes the full, much higher real gas cost.

### Impact Explanation
This breaks the invariant documented for block gas accounting — `MaxGas` is supposed to bound `(sum of GasUsed in a block)` per the ABCI spec assumptions referenced in the codebase [6](#0-5) . Because the `ProcessProposal` gate can be satisfied using a manipulated, unverified self-reported number instead of real execution cost, an attacker can cause blocks to be accepted by consensus that require substantially more real EVM execution work than `MaxGas` was meant to allow. This directly threatens block processing time across all validators (each of which must execute the full real gas amount in `FinalizeBlock`), which can push block processing delay beyond acceptable bounds, a liveness/availability impact.

### Likelihood Explanation
Exploitation requires only: (1) constructing and signing a Cosmos SDK transaction wrapping a `MsgEVMTransaction` (or any EVM tx) directly, without going through the RPC's honest `eth_sendRawTransaction` simulation path, and (2) setting `Fee.GasEstimate` to the minimum accepted value (`MinGasEVMTx`) while keeping the real gas-heavy operation's `gasWanted` high enough to actually execute at that cost. Both are fully within reach of a single unprivileged transaction sender using the public transaction-submission surface; no validator collusion or special privileges are required (though a cooperating/malicious proposer that batches many such transactions increases severity).

### Recommendation
Do not trust the self-reported `Fee.GasEstimate` as an unverified value for block-gas admission decisions. Either:
- Bound `GasEstimate` more strictly relative to a verifiable, reproducible quantity (e.g., require it be independently re-derived/re-simulated by the node before admission, similar to `s.simulateTx` in `evmrpc/send.go`), or
- Remove the preferential use of `GasEstimate` in `checkTotalBlockGas` and always account transactions by their real `gasWanted` for the block-gas invariant, accepting a possible reduction in effective block throughput in exchange for correctness of the `MaxGas` bound.

### Proof of Concept
Conceptual PoC (matches existing test patterns in the repo, e.g. `TestCheckTotalBlockGas_GasEstimatePreferredOverGasWanted` [7](#0-6) ):
1. Deploy a contract whose function consumes gas close to its supplied gas limit (e.g., a loop, similar to `GasBurner` used in `eth_estimateGas.spec.ts` tests [8](#0-7) ).
2. Craft several `MsgEVMTransaction`s calling that function with `gasWanted` set high enough to actually run to completion (e.g., several million gas each), and set the transaction's `Fee.GasEstimate` to `21000` (the `MinGasEVMTx` minimum) via `SetGasEstimate` [1](#0-0) , bypassing `eth_sendRawTransaction`'s honest simulation.
3. Submit enough such transactions that their summed `GasEstimate` (≈21000 × N) stays under `MaxGas`, but their summed real `gasWanted`/actual execution gas would be many times `MaxGas`.
4. `checkTotalBlockGas` in `ProcessProposal` accepts the block [9](#0-8) , but `FinalizeBlock` must actually execute the full gas-heavy logic (bounded by real `gasWanted`, per `x/evm/ante/gas.go` [10](#0-9) ), producing execution work far beyond what `MaxGas` was intended to bound.

// checkTotalBlockGas checks that the block gas limit is not exceeded by our best estimate of
// the total gas by the txs in the block. The gas of a tx is either the gas estimate if it's an EVM tx,
// or the gas wanted if it's a Cosmos tx. typedTxs must align with proposal order (nil = decode failure).
func (app *App) checkTotalBlockGas(ctx sdk.Context, typedTxs []sdk.Tx) (_result bool) {
	defer func() {
		if r := recover(); r != nil {
			logger.Error("panic recovered in checkTotalBlockGas", "panic", r)
			_result = false
		}
	}()

	var totalGas, totalGasWanted uint64
	for _, decodedTx := range typedTxs {
		if decodedTx == nil {
			return false
		}

		isEVM, evmErr := evmante.IsEVMMessage(decodedTx)

		// EVM classification failed (e.g. multi-msg containing an EVM message); such a tx won't be
		// processed and so contributes no gas to the block.
		if evmErr != nil {
			continue
		}

		var gasWanted uint64
		if isEVM {
			msg := evmtypes.MustGetEVMTransactionMessage(decodedTx)
			if msg.IsAssociateTx() {
				continue
			}
			etx, _ := msg.AsTransaction()
			gasWanted = etx.Gas()
		} else {
			feeTx, ok := decodedTx.(sdk.FeeTx)
			if !ok {
				// Non-fee tx won't be processed and thus won't consume gas. Skipping.
				continue
			}
			gasWanted = feeTx.GetGas()
		}

		// Overflow guards: gasWanted must fit in int64, and adding it to either accumulator
		// must not wrap uint64.
		if int64(gasWanted) < 0 || //nolint:gosec
			totalGasWanted > math.MaxUint64-gasWanted ||
			totalGas > math.MaxUint64-gasWanted {
			return false
		}

		totalGasWanted += gasWanted

		// Prefer the gas estimate when it's a valid EVM estimate (>= MinGasEVMTx) and not
		// inflated above gasWanted; otherwise charge full gasWanted.
		if est := decodedTx.GetGasEstimate(); est >= MinGasEVMTx && est <= gasWanted {
			totalGas += est
		} else {
			totalGas += gasWanted
		}

		blockParams := ctx.ConsensusParams().Block
		maxGasWanted := uint64(blockParams.MaxGasWanted) //nolint:gosec
		maxGas := uint64(blockParams.MaxGas)             //nolint:gosec
		if totalGasWanted > maxGasWanted || totalGas > maxGas {
			return false
		}

func NewGasDecorator(evmKeeper *evmkeeper.Keeper) *GasDecorator {

// Called at the end of the ante chain to set gas limit and gas used estimate properly
func (gl GasDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	msg := evmtypes.MustGetEVMTransactionMessage(tx)
	txData, err := evmtypes.UnpackTxData(msg.Data)
	if err != nil {
		return ctx, err
	}

	txGas := txData.GetGas()
	if txGas > math.MaxInt64 {
		return ctx, errors.New("tx gas exceeds max")
	}
	adjustedGasLimit := gl.evmKeeper.GetPriorityNormalizer(ctx).MulInt64(int64(txGas)) //nolint:gosec
	gasMeter := sdk.NewGasMeterWithMultiplier(ctx, adjustedGasLimit.TruncateInt().Uint64())
	ctx = ctx.WithGasMeter(gasMeter)
	if tx.GetGasEstimate() >= MinGasEVMTx {
		ctx = ctx.WithGasEstimate(tx.GetGasEstimate())
	} else {
		ctx = ctx.WithGasEstimate(gasMeter.Limit())
	}
	return next(ctx, tx, simulate)
