## Analog Bug Identified

### Title
Balance-tracking event replay in `BalanceHandler` can desync StateDB from bank ledger on reentrant/nested precompile calls, enabling incorrect mint/burn reconciliation - (File: `precompiles/common/balance_handler.go`)

### Summary
The Certora-style report describes a class of bug where a required state-accrual step (`charge`) is assumed to have run before a downstream operation consumes the resulting state, but a conditional branch can skip the accrual call, corrupting accounting. The Cosmos EVM analog is the `BalanceHandler` mechanism used by precompiles to translate Cosmos SDK bank events into `StateDB` balance deltas: it tracks a shared mutable cursor (`prevEventsLen`) that is assumed to bracket exactly one precompile call's bank events, but recursive/nested precompile invocations sharing the same handler instance can overwrite that cursor before the outer call reads it, causing the wrong slice of events to be replayed into the `StateDB`.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` into `bh.prevEventsLen` before a precompile executes, and `AfterBalanceChange` replays all bank events emitted since that recorded index into the `StateDB` via `AddBalance`/`SubBalance`: [1](#0-0) [2](#0-1) 

This design implicitly assumes `BeforeBalanceChange`/`AfterBalanceChange` are called in strict LIFO, non-overlapping pairs for a single call. However, the repository's own integration test explicitly documents that recursive precompile calls (a contract calling a precompile whose execution triggers another precompile call, e.g., via `ERC20RecursiveNonRevertingPrecompileCall.sol`/`ERC20RecursiveRevertingPrecompileCall.sol` patterns, or the `DebugPrecompileCaller` test harness) can share the *same* `BalanceHandler` instance across nested invocations, causing `prevEventsLen` to be overwritten by the inner call before the outer call's `AfterBalanceChange` executes: [3](#0-2) 

If the outer call's `AfterBalanceChange` runs using a `prevEventsLen` value that was advanced by the inner call, the outer call's own bank events (spent/received prior to the nested call) will never be replayed into the `StateDB` — the balance change happened at the bank-keeper level (real, spendable coins moved) but is never reflected in the EVM `StateDB`'s tracked balance. This is structurally identical to the source report's root cause: a required state-synchronization step is silently skipped under an execution-order edge case, and a downstream consumer (here, `StateDB`-to-bank reconciliation) operates on stale/incorrect state.

The corrupted `StateDB` balance is not inert: `x/vm/keeper/statedb.go`'s `SetBalance` reconciles StateDB-tracked balances back to the bank ledger by diffing the target balance against the current spendable coin balance and minting or burning the delta: [4](#0-3) 
Because this reconciliation trusts the `StateDB`'s balance as the "true" target and mints/burns whatever delta is required to match it, a `StateDB` balance that has drifted from the real bank balance (due to a missed `AfterBalanceChange` replay) can cause the keeper to mint coins that were never actually credited by the bank module, or burn coins that were never actually debited — an irreversible supply/accounting corruption of spendable user value.

### Impact Explanation
This falls squarely under the "Critical unauthorized minting, burning, duplication...or irreversible accounting corruption of spendable user value" impact bucket. An unprivileged user can trigger the divergence purely through ordinary contract/precompile call flows (any contract that nests one precompile call inside another sharing a `BalanceHandler`, e.g., ERC20 precompile / staking / distribution / gov / ics20 / slashing precompiles all instantiate and use a `BalanceHandler`): [5](#0-4) [6](#0-5) 
Once `StateDB` and bank-ledger balances diverge, subsequent EVM balance reconciliation (`SetBalance`) can mint or burn real coins to force-match the corrupted value, producing a permanent, irreversible discrepancy in user or module funds.

### Likelihood Explanation
Likelihood is moderate-to-high in principle (no privileged access required — just a contract that performs nested precompile calls), but I was unable to confirm in this session whether the currently-shipped `precompile.go` instantiates a *new* `BalanceHandler` per top-level call (via `BalanceHandlerFactory.NewBalanceHandler()`) versus reusing one shared instance across nested/reentrant calls — the final tool iteration was cut off before I could inspect `precompiles/common/precompile.go` in full. The existence of a dedicated regression test (`TestRecursivePrecompileCallsWithDebugPrecompile`) strongly suggests this exact bug was identified and is either fixed or actively guarded against, but I could not verify the current mitigation state (e.g., whether `prevEventsLen` overwrite is now prevented by allocating handler instances per-call, using a stack, or another safeguard).

### Recommendation
- Verify (in `precompiles/common/precompile.go`) whether a new `BalanceHandler` is allocated per precompile invocation, or if one instance is reused/shared across nested/recursive precompile calls within a single EVM call frame.
- If sharing is possible, replace the single `prevEventsLen int` field with a stack (LIFO) of event-index checkpoints, or allocate a new `BalanceHandler` per call frame, to guarantee correct bracket-matching under reentrancy/nested precompile calls.
- Add an invariant check post-reconciliation comparing `StateDB` tracked balances against bank-keeper spendable balances for all addresses touched during a tx, failing the tx (rather than silently minting/burning) if a mismatch is detected.

### Proof of Concept
A concrete, fully-worked PoC could not be finalized in this session because the tool budget was exhausted before confirming the exact `BalanceHandler` lifecycle in `precompiles/common/precompile.go`. The repository's own test, `TestRecursivePrecompileCallsWithDebugPrecompile`, is the closest available reproduction scaffold — it deploys a contract that recursively invokes a precompile that emits bank events, and asserts on the resulting event count/state, which is exactly the shape needed to demonstrate `prevEventsLen` corruption: [7](#0-6) 
Further work should extend this test to assert bank-keeper vs. `StateDB` balance equality for the outer caller/callee addresses after the recursive call completes, which would confirm whether the divergence (and downstream mint/burn corruption via `SetBalance`) is currently reproducible or already mitigated.

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}
