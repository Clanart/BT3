### Title
Empty aggregate signature deserializes and verifies successfully - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` accepts an aggregate with zero nonces, while `SchnorrAggregate::verify` treats an empty expected-key list plus a zero `s` scalar as valid. This creates a serializable aggregate that `SchnorrAggregator::complete` explicitly refuses to produce, yet still passes verification. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer reads a little-endian `u32` nonce count and then reads that many points. A count of zero is accepted without any lower-bound check. [1](#0-0) 

During verification, matching lengths are the only cardinality check. If both `self.Rs` and `keys_and_challenges` are empty, the verifier queues only `(-self.s, G)`. When `s = 0`, that statement evaluates to the identity and verification returns true. [2](#0-1) 

This behavior is inconsistent with the constructor path: `SchnorrAggregator::complete` returns `None` when no signatures were aggregated, indicating that an empty aggregate is not a legitimate aggregate signature. [3](#0-2) 

### Impact Explanation
An attacker can submit a short serialized object that verification accepts despite it not certifying any public key, nonce, message, or signer. Any caller that interprets `verify(...) == true` as proof that a nonempty aggregate signature exists can be induced to accept a forged aggregate authorization when the supplied `keys_and_challenges` list is empty. [2](#0-1) 

The issue is reachable entirely through public bytes supplied to `SchnorrAggregate::read`, followed by `verify`. [1](#0-0) 

### Likelihood Explanation
Exploitation requires a verifier path that permits an empty `keys_and_challenges` list. That precondition limits the impact because successful verification does not impersonate any particular nonempty signer set; however, the API itself is inconsistent because the producer refuses empty aggregates while the deserializer/verifier accepts them. [2](#0-1) [3](#0-2) 

Severity: Medium.

### Recommendation
Reject empty aggregates consistently:

- Return an error in `SchnorrAggregate::read` when the encoded `Rs` length is zero.
- Return `false` in `SchnorrAggregate::verify` when `self.Rs` or `keys_and_challenges` is empty.
- Add a regression test asserting that `00 00 00 00` followed by a canonical zero scalar fails deserialization or verification.
- Consider an explicit length cap before iterating over `u32` nonce count to reduce resource-exhaustion exposure from malformed inputs.

### Proof of Concept
For a ciphersuite whose scalar encoding is 32 canonical bytes, construct:

```text
len = 00 00 00 00    // zero Rs
s   = 00 ... 00      // 32-byte canonical zero scalar
```

Then deserialize and verify it against an empty signer list:

```rust
let mut encoded = Vec::new();
encoded.extend_from_slice(&0u32.to_le_bytes());
encoded.extend_from_slice(&[0u8; 32]);

let aggregate =
  SchnorrAggregate::<Secp256k1>::read(&mut encoded.as_slice()).unwrap();

assert!(aggregate.verify(b"example-dst", &[]));
```

Verification succeeds because the verifier builds only the statement `0 * G`, which is the identity. [2](#0-1)
