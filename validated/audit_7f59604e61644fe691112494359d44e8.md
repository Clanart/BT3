## Analog Identified: Missing Pair-Level `Enabled` Check in `ConvertCoinToERC20FromPacket`

### Title
Toggled Token-Pair Conversion Flag Is Not Enforced on IBC Timeout/Error-Ack Auto-Conversion Path - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the same bug class as the Mochi finding: a toggle flag exists to gate a state-changing operation, one code path checks it, but a second, reachable code path performs the same operation without checking the toggle.

### Finding Description
In `OnRecvPacket`, the module correctly enforces the per-pair `Enabled` toggle (set via governance `MsgToggleConversion`, implemented in `toggleConversion`) before converting an incoming IBC coin to its native ERC20 representation: [1](#0-0) 

However, the sibling conversion path `ConvertCoinToERC20FromPacket` — invoked from both `OnAcknowledgementPacket` (on error ack) and `OnTimeoutPacket` — only checks the module-wide `params.EnableErc20` flag and whether the denom is registered. It never checks `pair.Enabled`: [2](#0-1) 

The governance toggle is implemented generically per-pair, independent of the global param: [3](#0-2) 

So if governance disables a specific token pair (e.g., because its underlying ERC20 contract is misbehaving, upgraded maliciously, or otherwise unsafe) while leaving the module-wide `EnableErc20` param on, a failed/timed-out IBC transfer for that denom will still be silently auto-converted into the (disabled) native ERC20 representation via `ConvertCoinNativeERC20`, bypassing the exact safety control governance just activated.

### Impact Explanation
The pair-level toggle is the governance-controlled circuit breaker for a specific ERC20 contract's conversion path. Since `OnRecvPacket` treats a disabled pair as "must not auto-convert", the omission in the refund/timeout path is an inconsistency in enforcing the same invariant on the opposite direction of the same feature. Depending on why the pair was disabled (e.g., a broken/self-destructed or exploitable ERC20 implementation), forcing a conversion through this unguarded path can mint bank coins and push value through a contract the protocol has explicitly decided is unsafe to interact with, risking the ERC20 mint/escrow invariant maintained elsewhere (e.g. `convertERC20IntoCoinsForNativeToken`'s balance-invariance checks) — however, I was not able to fully inspect `ConvertCoinNativeERC20` itself within the available iterations to confirm whether it independently re-validates the pair status or contains equivalent balance-invariance guards; this must be confirmed before treating this as a confirmed Critical/fund-loss primitive.

### Likelihood Explanation
Reachable by any unprivileged relayer/user triggering an IBC timeout or error acknowledgment for a transfer denominated in a token whose pair has been disabled — no privileged access is required to trigger the timeout/ack callback path itself, only the pre-condition that governance has toggled the given pair off.

### Recommendation
Add the same `if !pair.Enabled { return nil }` guard used in `OnRecvPacket` to the `IsNativeERC20()` branch of `ConvertCoinToERC20FromPacket` in `x/erc20/keeper/ibc_callbacks.go`, so that disabling a token pair via `MsgToggleConversion` consistently blocks conversion on both the receive and the refund/timeout paths.

### Proof of Concept
1. Register a native ERC20 token pair for denom `X`.
2. Governance disables it via `MsgToggleConversion` (`pair.Enabled = false`), while `params.EnableErc20` remains `true`. [3](#0-2) 
3. Initiate an outbound IBC transfer of coin `X` that later times out or receives an error acknowledgment, invoking `OnTimeoutPacket`/`OnAcknowledgementPacket` → `ConvertCoinToERC20FromPacket`. [4](#0-3) 
4. Observe that despite `pair.Enabled == false`, the function proceeds to call `ConvertCoinNativeERC20`, since only `params.EnableErc20` and denom-registration are checked. [5](#0-4) 

**Note on confidence:** I was unable to locate and review the body of `ConvertCoinNativeERC20` (referenced but not found via search within the iteration budget) to fully confirm whether it independently enforces pair-enabled status or additional invariant checks that might mitigate the impact. This should be verified before treating the severity as definitively Critical; the code-path inconsistency itself (an existing toggle check applied in one direction but omitted in the other) is confirmed and directly analogous to the reported `withdrawLock()` issue.

// ToggleConversion toggles conversion for a given token pair
func (k Keeper) toggleConversion(
	ctx sdk.Context,
	token string,
) (types.TokenPair, error) {
	id := k.GetTokenPairID(ctx, token)
	if len(id) == 0 {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered by id", token,
		)
	}

	pair, found := k.GetTokenPair(ctx, id)
	if !found {
		return types.TokenPair{}, errorsmod.Wrapf(
			types.ErrTokenPairNotFound, "token '%s' not registered", token,
		)
	}

	pair.Enabled = !pair.Enabled
	k.SetTokenPair(ctx, pair)
	return pair, nil
}
