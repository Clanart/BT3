### Title
Missing Timeout on Alloy Contract Calls Blocks Verifier Block-Processing Loop — (`File: core/src/citrea.rs`)

### Summary

`CitreaClient::collect_deposit_move_txids` and `collect_withdrawal_utxos` issue unbounded `alloy` contract calls (`.call().await`) inside a loop using a provider built without any request timeout. If the Citrea node becomes unresponsive, both functions hang indefinitely, blocking the verifier's entire Bitcoin-block processing task and preventing it from issuing disproves within their timelocked windows.

### Finding Description

`CitreaClient` is constructed in `CitreaClientT::new` with two distinct HTTP handles:

- `self.client` and `self.light_client_prover_client` — built via `HttpClientBuilder::default().request_timeout(timeout.unwrap_or(Duration::from_secs(60)))` — **have** a 60-second timeout.
- `self.contract` — built via `ProviderBuilder::new().wallet(...).on_http(citrea_rpc_url.clone())` — **has no timeout configured**. [1](#0-0) 

`alloy`'s `on_http` transport uses `reqwest` with no default timeout, so any `.call().await` on `self.contract` can block forever.

`collect_deposit_move_txids` and `collect_withdrawal_utxos` both loop, calling `.call().await` on `self.contract` for every deposit/withdrawal index until an `execution reverted` error signals the end of the list: [2](#0-1) [3](#0-2) 

These are called from `update_citrea_deposit_and_withdrawals` in the verifier with no surrounding timeout: [4](#0-3) 

### Impact Explanation

`update_citrea_deposit_and_withdrawals` is invoked inside the verifier's Bitcoin-block processing loop. A hang there stalls the entire loop, preventing the verifier from:

1. Detecting new deposits and withdrawals (liveness — funds stuck).
2. Advancing its duty queue, which includes `VerifierDisprove` duties that must be executed within the `DISPROVE_TIMEOUT_TIMELOCK` window (default 720 blocks ≈ 5 days).

If a malicious operator posts a fraudulent assertion while the verifier is blocked, the disprove window can expire uncontested, allowing the operator to claim bridged BTC collateral and complete an invalid payout. The `OPERATOR_CHALLENGE_AMOUNT` (130 000 000 sat on regtest, scaling to full bridge amounts on mainnet) is at risk. [5](#0-4) 

### Likelihood Explanation

Any transient Citrea node unresponsiveness (network partition, node restart, RPC overload) is sufficient to trigger the hang. No privileged access is required. The condition is realistic in production and can be induced by a colluding operator who also controls or disrupts the Citrea RPC endpoint the verifier is pointed at.

### Recommendation

Apply the same `request_timeout` used for `self.client` to the `alloy` provider backing `self.contract`. For example, build the provider with a `reqwest::Client` that has an explicit timeout:

```rust
let http_client = reqwest::Client::builder()
    .timeout(timeout.unwrap_or(Duration::from_secs(60)))
    .build()?;
let provider = ProviderBuilder::new()
    .wallet(EthereumWallet::from(key))
    .on_client(RpcClient::new(Http::with_client(http_client, citrea_rpc_url), true));
```

Additionally, wrap the call-sites in `update_citrea_deposit_and_withdrawals` with `timed_request` (already used elsewhere in the codebase) so that a single slow Citrea response cannot block the entire block-processing task indefinitely. [6](#0-5) 

### Proof of Concept

1. Start a Clementine verifier pointed at a Citrea node.
2. After the verifier begins processing blocks, make the Citrea RPC endpoint unresponsive (e.g., firewall the port or pause the process).
3. Observe that the verifier's Bitcoin-block processing task hangs at the `collect_deposit_move_txids` call and never resumes.
4. While the verifier is hung, have an operator post a fraudulent assertion on-chain.
5. Wait for `DISPROVE_TIMEOUT_TIMELOCK` blocks to elapse; the verifier never issues a disprove, and the operator can claim the collateral/payout. [7](#0-6) [8](#0-7)

pub async fn timed_request<F, T>(
    duration: Duration,
    description: &str,
    future: F,
) -> Result<T, BridgeError>
where
    F: Future<Output = Result<T, BridgeError>>,
{
    timed_request_base(duration, description, future)
        .await
        .map_err(|_| {
            Box::new(Status::deadline_exceeded(format!(
                "{description} timed out"
            )))
        })?
}
