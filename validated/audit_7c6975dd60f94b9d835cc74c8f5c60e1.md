## Title
`discardChanges` trashes/deletes files by unvalidated repository-reported path, allowing a symlink-crafted repository to redirect deletions outside the repo - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The external report's broken invariant is: a destination value (`recipient`) supplied by/derived from the operation's own inputs is used directly for a state-changing, funds-moving action without checking that it stays within the intended safe boundary (the user's own margin/account), so the operation can be aimed at a location where the value becomes unrecoverable. The GitHub Desktop analog is `GitStore.discardChanges()`, which uses the file path reported by `git status` for a repository (attacker-controlled once a malicious repo is cloned/fetched/checked out) to build a filesystem destination for `moveItemToTrash`/`rm`, without ever confirming that the resolved real path stays inside the repository root — unlike other, more recently hardened code paths in the same codebase.

### Finding Description
`discardChanges` iterates over `WorkingDirectoryFileChange` entries (whose `.path` values originate from `git status` output for the currently open repository) and does: [1](#0-0) 

```ts
if (moveToTrash) {
  try {
    await this.shell.moveItemToTrash(
      Path.resolve(this.repository.path, file.path)
    )
  } catch (e) {
    ...
    if (file.status.kind === AppFileStatusKind.Untracked) {
      await rm(Path.join(this.repository.path, file.path))
    }
  }
} else if (moveToTrash === false) {
  if (file.status.kind === AppFileStatusKind.Untracked) {
    await rm(Path.join(this.repository.path, file.path))
  }
}
```

Both `Path.resolve(this.repository.path, file.path)` and `Path.join(this.repository.path, file.path)` are naive path concatenations. Neither call goes through `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32`, the project's own dedicated helper for validating that a resolved path (after following symlinks via `realpath`) still lives under a trusted root: [2](#0-1) 

The project clearly recognizes this exact risk class and has already patched several other code paths to use `resolveWithin` specifically to defend against symlink-based escapes from attacker-controlled repository content: the AI conflict-context file reader [3](#0-2) 

and the "open file from deep link" handler [4](#0-3) 

Both explicitly call out "path traversal and symlink escapes" as the threat being mitigated, and the test suite even documents and verifies that a directory component of a path can be a symlink pointing outside the intended root: [5](#0-4) 

`discardChanges` was never updated to use this guard. If a cloned/fetched repository contains, as a tracked or untracked entry, a symlinked directory component (e.g. `evil-dir` is a symlink to `/Users/victim` or another sensitive location) and a file living through that symlink shows up as modified/untracked in `git status`, `file.path` (e.g. `evil-dir/Documents/secret.txt`) will resolve, once concatenated with `repository.path`, to a real filesystem location entirely outside the repository. `moveItemToTrash`/`rm` will then act on that outside location when the user clicks "Discard changes" — the everyday, expected user action in this flow.

### Impact Explanation
This allows an attacker who only controls the contents of a repository (via a malicious clone URL, a crafted PR branch checked out into an existing repo, or a fetched ref) to cause GitHub Desktop to delete or send-to-trash arbitrary files outside of the repository working directory once the victim performs a normal "Discard changes" action — a file write/delete outside the repo triggered purely by opening/interacting with attacker-supplied repository content, with no unusual or unnatural steps required from the user.

### Likelihood Explanation
Discarding changes is one of the most common actions in Desktop's daily workflow, and the vulnerable code path is reached unconditionally whenever a non-deleted, non-submodule file is discarded (`AppFileStatusKind !== Deleted` and not a submodule) — no special dialog or confirmation exists that would validate the resolved path. The only real constraint is git/OS willingness to track and check out a symlinked directory as part of a repository, and other parts of this same codebase treat that scenario as realistic enough to explicitly test and guard against (see the `path-test.ts` symlink cases above), indicating the maintainers consider it a credible attack surface that was simply missed for this specific call site.

### Recommendation
- **Short term:** Route both destination paths in `discardChanges` (the `moveItemToTrash` call and both `rm` fallbacks) through `resolveWithin(this.repository.path, file.path)` (or the platform-specific variant), and abort the discard for that file (surfacing an error to the user) if the resolved path is `null`, exactly as done in `copilot-conflict-context.ts` and `dispatcher.ts`.
- **Long term:** Audit all remaining call sites that build filesystem paths from repository-reported (`git status`/`git diff`) file paths — including `discardChangesFromSelection`/`applyPatchToIndex` consumers — and standardize on `resolveWithin` as the single sanctioned way to turn a repository-relative path into an absolute path before any destructive filesystem operation.

### Proof of Concept
1. Attacker publishes a repository containing a tracked symlink, e.g. `payload` → an absolute path such as the victim's home directory (git supports storing symlinks as blobs with mode `120000`).
2. Victim clones/opens the repository in GitHub Desktop, then creates or modifies a file that, via the OS, is reachable through that symlink such that `git status` reports it as untracked/modified with a path like `payload/some-file` (this requires the symlink target to already contain files that git considers untracked relative to the repo, or the attacker to ship the symlink such that a subsequent `git checkout`/fetch produces such an entry).
3. Victim selects that file in the Changes list and clicks "Discard changes."
4. `discardChanges` in `app/src/lib/stores/git-store.ts` resolves `Path.resolve(repository.path, 'payload/some-file')`, which — because `payload` is a symlink — points to a file outside the repository, and passes it to `moveItemToTrash`/`rm`, deleting or trashing a file the victim never intended to touch, entirely outside the repository the victim is working in.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
