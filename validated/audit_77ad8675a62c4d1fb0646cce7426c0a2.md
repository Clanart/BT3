### Title
`CommitMentionLinkFilter.getRefFromComparePath()` throws on malformed `compare` URLs, breaking markdown rendering for attacker-controlled repository content - (File: app/src/lib/markdown-filters/commit-mention-link-filter.ts)

### Summary
`getRefFromComparePath` splits the `compare/...` URL path segment on `...` and unconditionally indexes `shas[1]` without checking that a second element exists.

### Finding Description
`getRefFromComparePath` matches a link path against `this.comparePath` (`/^compare\/(?<range>.+)$/`) and then does: [1](#0-0) 
`range.split('...')` only guarantees `shas.length >= 1`. There is a check that rejects `shas.length > 2`, but no check that `shas.length >= 2`. If an attacker supplies a link whose href and inner text both match the `commitMentionUrl` regex with a `compare/<something>` path that contains no `...` (e.g. `https://github.com/<owner>/<repo>/compare/foo`), `shas` becomes `['foo']`, and `shas[1]` is `undefined`. The next line `shas[1].indexOf('/')` then throws `TypeError: Cannot read properties of undefined (reading 'indexOf')`.

The entry point is `filter()`, which is invoked for any anchor node whose `href === innerText` and whose href matches `commitMentionUrl`: [2](#0-1) 
The `commitMentionUrl` regex requires `(commit|pull|compare)` followed by `(\d+/commits/)?` and a 7–40 char hex sha `\b`-bounded — but that boundary check is anchored at the *end* of the path match, not the *start* right after `compare/`. Because the regex has `.test()` semantics (not full-line anchoring) and JS `URL` parsing of `text` is done separately from the regex used to accept the node, a crafted href like `https://github.com/owner/repo/compare/deadbeef1234567` (a single 7–40 hex-char token, no `...`) can satisfy `commitMentionUrl` (since the trailing sha group matches) while `getRefFromComparePath`'s own more permissive `comparePath` regex (`/^compare\/(?<range>.+)$/`) captures the whole remainder as `range` with no `...`, producing `shas.length === 1` and the crash.

### Impact Explanation
`applyFilters()` in `sandboxed-markdown.tsx` awaits `nodeFilter.filter(node)` with no try/catch around the call: [3](#0-2) 
An unhandled exception here breaks rendering of that markdown body (issue/PR/commit description, comment, etc.) inside the sandboxed iframe for any GitHub-hosted repository content containing a crafted anchor tag whose href/text match this pattern. This is a renderer-level denial-of-service/crash-on-render bug reachable purely from GitHub API content (issue bodies, PR descriptions, commit messages) that an external, unprivileged actor controls (e.g., by opening an issue/PR against a repository the victim later views in Desktop), directly analogous to the reported `bn254.DeserializeG1()` panic caused by unchecked-length indexing of externally supplied data.

### Likelihood Explanation
Any GitHub user can create an issue, pull request, comment, or commit message containing an autolinked (or manually authored anchor with matching text/href) `.../compare/<token>` URL without `...`, and if it also happens to match the required trailing sha pattern in `commitMentionUrl`, viewing that content in GitHub Desktop's PR/issue/commit description panes triggers the crash path. The bar is a specific but achievable URL shape, requiring no local access, admin rights, or social engineering beyond normal GitHub content authorship.

### Recommendation
In `getRefFromComparePath`, validate that `shas.length === 2` (not just `<= 2`) before accessing `shas[1]`, returning `null` otherwise; similarly ensure `commitMentionUrl`/`comparePath` regexes are consistent about requiring the `...` separator for compare links. Additionally, wrap `nodeFilter.filter(node)` calls in `applyFilters()` with a try/catch so a single malformed node cannot abort the whole markdown-filtering pipeline.

### Proof of Concept
1. Construct GitHub markdown/HTML content (e.g. an issue body) containing an anchor whose `href` and `innerText` are identical: `https://github.com/<owner>/<repo>/compare/deadbeef1` (7+ hex chars, no `...`).
2. View this issue/PR/commit in GitHub Desktop, which renders it via `SandboxedMarkdown`/`applyFilters` using `buildCustomMarkDownNodeFilterPipe`, which includes `CommitMentionLinkFilter`.
3. `commitMentionUrl.test(el.href)` accepts the node because the trailing hex-sha pattern matches; `filter()` calls `getRefFromComparePath(path)`, `range.split('...')` yields a single-element array, and `shas[1].indexOf('/')` throws, breaking rendering of that markdown content.

*Note: full confirmation of the exact regex overlap between `commitMentionUrl` and `comparePath` (i.e., whether an unmatched no-`...` compare link can actually pass the `el.href` accept-node test) would benefit from running the regex against concrete test strings in a sandboxed session, since the index only exposes source snippets and not executable regex testing.*
