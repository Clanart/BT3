### Title
Attacker-flooded dust outputs are reported as spendable `ReceivedOutput`s and can stall transaction construction with `TooLargeTransaction` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Astaria finding — where an expired lien that nobody liquidates leaves `liensOpenForEpoch > 0` and makes `processEpoch()` revert until an external party intervenes — `Scanner::scan_transaction` reports every output paying to a watched `script_pubkey` as a "spendable" `ReceivedOutput` with no value floor. Any unprivileged Bitcoin user can send arbitrary numbers of dust outputs to the multisig's public P2TR deposit address. These outputs accumulate in the wallet's tracked set, and once enough are included as inputs, `SignableTransaction::new` fails with `TransactionError::TooLargeTransaction`, halting spend/withdrawal processing until someone manually intervenes — the same "stuck until an external cleanup call" shape.

### Finding Description
`ReceivedOutput` is documented as "A spendable output" (`networks/bitcoin/src/wallet/mod.rs:88-97`), but `Scanner::scan_transaction` pushes a `ReceivedOutput` for any transaction output whose `script_pubkey` matches a registered script, with no check on `output.value` (`networks/bitcoin/src/wallet/mod.rs:199-214`). There is no minimum-value/dust gate anywhere in the in-scope wallet code for *received* outputs; `send.rs` only enforces `DUST` on outgoing payments (`networks/bitcoin/src/wallet/send.rs:165-169`).

On the spend side, `SignableTransaction::new` sums all provided inputs and rejects the transaction once its weight exceeds `MAX_STANDARD_TX_WEIGHT` (`networks/bitcoin/src/wallet/send.rs:241-243`). Each input contributes ~230 weight units, so ≳520 inputs guarantee failure — matching the `MAX_INPUTS = 520` analysis in `processor/src/networks/bitcoin.rs:575`. An attacker who floods the public deposit address with dust outputs creates exactly this situation: every such output is reported as received, and any aggregation attempt that pulls them in fails deterministically, just as `processEpoch()` deterministically reverts while `liensOpenForEpoch > 0`.

### Impact Explanation
Unprivileged liveness denial of service plus a "received but not economically spendable" accounting error:

- Dust outputs (below the cost to spend them at reasonable feerates, e.g. < a few hundred sats) are reported as spendable `ReceivedOutput`s, so the wallet reports funds received that are not worth spending — paralleling "funds reported received that are not spendable."
- With enough attacker-sent outputs, any transaction built over the accumulated set fails `weight > MAX_STANDARD_TX_WEIGHT` → `TooLargeTransaction` (`send.rs:241-243`), stalling spending until an operator manually partitions inputs or writes off dust — the same recovery-by-external-action pattern as requiring someone to call `liquidate`.

### Likelihood Explanation
The attack requires only sending ordinary Bitcoin transactions to a publicly known deposit address — fully within the allowed reachability model ("Bitcoin transactions they send"). Cost is bounded by the dust the attacker donates (~546 sats per output at minimum relay standards, ~0.28 BTC for ~520 outputs), and the address is necessarily public for deposits. Likelihood is moderate: it requires deliberate griefing and the scheduler must naively include the outputs, but nothing in the in-scope code prevents or bounds the condition.

### Recommendation
Enforce a minimum value in `Scanner::scan_transaction`/`scan_block` (or on `ReceivedOutput` construction) so outputs below a spendability threshold are never reported — analogous to filtering expired liens at acceptance time rather than relying on a later `liquidate` call. Additionally, `SignableTransaction::new` should bound/select inputs (e.g., cap input count and skip uneconomical inputs) rather than failing on aggregate weight, so progress never depends on manual cleanup of attacker-created state.

### Proof of Concept
```rust
// Conceptual PoC against networks/bitcoin
// 1. Attacker learns the multisig's P2TR script_pubkey (public deposit address).
let scanner = Scanner::new(group_key).unwrap();

// 2. Attacker broadcasts N transactions, each with a dust output
//    (e.g., 546 sats) to that script_pubkey. For each confirmed tx:
let outputs = scanner.scan_transaction(&attacker_tx);
assert_eq!(outputs.len(), 1); // dust is reported as a spendable ReceivedOutput
received.extend(outputs);

// 3. Repeat until `received` holds > ~520 outputs. Any attempt to spend
//    the accumulated set in one transaction fails deterministically:
let err = SignableTransaction::new(
  received,                       // all scanned outputs, incl. attacker dust
  &[(payment_script, 100_000)],   // legitimate withdrawal
  change_script,
  None,
  fee_per_vbyte,
);
assert_eq!(err, Err(TransactionError::TooLargeTransaction));
// Spending halts until an operator manually curates the input set —
// the analog of processEpoch() reverting until someone calls liquidate.
```
