### Title
Unchecked wrapping/panicking arithmetic on attacker-controlled `u64` amounts in `SignableTransaction` lets a crafted `ReceivedOutput`/`TxOut` or payment set bypass the funds check and produce an underflowing `fee()` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes fee math that reverts on overflow/underflow because it assumed wrapping semantics. The Serai analog lives in `SignableTransaction`: `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `fee()` are all computed with plain `sum::<u64>()`, `+`, and `-` on `u64` amounts that originate from untrusted bytes (`ReceivedOutput::read` consensus-decodes a `TxOut` whose `value` field is any `u64`, not bound to the 21M BTC range) or from caller-supplied payment amounts. In debug builds these operations panic; in release builds they silently wrap, which lets the `NotEnoughFunds` check be bypassed and yields a `SignableTransaction` whose output total exceeds its inputs, so `fee()` underflows (panic in debug, ~`u64::MAX` garbage fee in release).

### Finding Description
`SignableTransaction::new` sums inputs and payments with unchecked `u64` arithmetic: [1](#0-0) 
and the funds check adds unchecked: [2](#0-1) 
`fee()` subtracts the output sum from the prevout sum without any checked math: [3](#0-2) 

`ReceivedOutput::read` accepts a consensus-decoded `TxOut`, whose `value` is an unrestricted `u64` (the `bitcoin` crate's `consensus_decode` does not enforce the 21M-coin cap), so `input.output.value.to_sat()` can be `u64::MAX`: [4](#0-3) 

Two overflow paths exist:
- `payment_sat`: payments summing past `u64::MAX` (e.g. `[u64::MAX, 2]` → wraps to `1` in release, panics in debug) makes `payment_sat + needed_fee` small, so `input_sat < payment_sat + needed_fee` is false and a `SignableTransaction` is constructed whose `tx.output` sums to ~2^64 while `prevouts` sum is tiny.
- `input_sat`: crafted `ReceivedOutput`s with huge `TxOut.value` wrap the input sum, likewise desynchronizing the check from the real `prevouts`/`outputs` totals.

The resulting transaction can never be valid on-chain (outputs exceed inputs), but `fee()` then computes `sum(prevouts) - sum(outputs)`, which underflows — panicking in overflow-checked builds or returning a near-`u64::MAX` "fee" in release. Downstream, Serai subtracts `tx.fee()` from a `SubstrateAmount` via `Amount::sub`, which is `checked_sub(...).unwrap()` and panics: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged party who can get attacker-controlled `TxOut` bytes into a `ReceivedOutput` (via `ReceivedOutput::read`, an explicitly exposed deserialization API) or attacker-influenced payment amounts into `SignableTransaction::new` can cause the wallet/signing path to panic or to report a wildly incorrect fee. The panic aborts transaction construction and any downstream balance arithmetic (`Amount::sub` unwrap), producing a denial of service of the spend pipeline; in release builds the wrapped fee is silently wrong and can corrupt accounting such as forwarded-output balances that deduct `tx.fee()`.

### Likelihood Explanation
Triggering requires only controlling a `TxOut.value` field in a deserialized `ReceivedOutput` or a payment amount — no cryptographic break is needed. However, exploiting it against a correctly configured deployment requires the integrator to feed attacker-controlled amounts into `SignableTransaction::new`/`fee()`; in-chain outputs alone are bounded by the 21M cap so real scanned outputs can't overflow the sums by themselves. Panic-on-overflow is guaranteed in debug builds; release builds wrap rather than panic but still produce an incorrect fee and an invalid transaction.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new` and `fee()`: `checked_sum`/`fold` for `input_sat` and `payment_sat`, `checked_add` for `payment_sat + needed_fee` and `fee_per_vbyte * vbytes`, and `checked_sub` in `fee()`, mapping failures to `TransactionError`. Additionally, validate in `ReceivedOutput::read` (or at `SignableTransaction::new` entry) that `output.value.to_sat()` is within Bitcoin's maximum money range, and validate that each payment amount itself is sane rather than relying solely on the aggregate sum.

### Proof of Concept
```rust
// networks/bitcoin — debug build: panics on overflow; release build: wraps.
use bitcoin_serai::wallet::ReceivedOutput;
use bitcoin::consensus::Encodable;

// Craft a ReceivedOutput whose TxOut.value is u64::MAX (consensus_decode does
// not bound value to MAX_MONEY).
let offset = [0u8; 32]; // Scalar 0 encoding... use a valid scalar encoding
let mut bytes = offset.to_vec();
// TxOut: value = u64::MAX, empty script_pubkey
bytes.extend(u64::MAX.to_le_bytes());
bytes.push(0); // empty scriptPubKey varint
// OutPoint: 32-byte txid + 4-byte vout
bytes.extend([0u8; 36]);

let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// output.value() == u64::MAX

// Two such inputs wrap input_sat to u64::MAX - 1... or:
// In release mode, payments [u64::MAX, 2] make payment_sat wrap to 1,
// so `input_sat < payment_sat + needed_fee` passes for a modest input,
// and SignableTransaction is built with outputs summing ~2^64.
// Calling tx.fee() then underflows: panics (debug) or returns ~u64::MAX (release).
```
The exact PoC is: construct `payments = [(script, u64::MAX), (script, 2)]` with a small legitimate input and call `SignableTransaction::new(...)` followed by `.fee()` — the former's `sum::<u64>()` wraps past the `NotEnoughFunds` guard and `fee()`'s subtraction underflows, mirroring the revert-on-overflow class of the original report.
