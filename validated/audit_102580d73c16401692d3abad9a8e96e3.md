### Title
`SignableTransaction` omits the OP_RETURN data output from fee/weight calculation, producing transactions that underpay fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a function that fails to account for value attached to a call (`msg.value != fromTokenAmount`), letting a contract's existing balance be drained. The analog in `bitcoin-serai` is the converse accounting error in `SignableTransaction::new`: an output that is added to the final transaction (the OP_RETURN data output) is never included when the transaction's weight, vsize, required fee, and min-relay-fee check are computed. The resulting transaction carries a real output whose cost the fee calculation never accounts for, so the signed transaction systematically underpays its fee.

### Finding Description
`SignableTransaction::new` appends an OP_RETURN output when `data` is provided, before any fee computation occurs (networks/bitcoin/src/wallet/send.rs:193-202). It then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204), which builds a template transaction using only `tx.input` and `payments` — it has no parameter for the data output at all (send.rs:62-99). The same omission occurs in the change path (send.rs:225-226).

Consequences, all derived from the stale weight/vbytes:

- `needed_fee = fee_per_vbyte * vbytes` undercounts by the vbytes of the OP_RETURN output (up to ~80 bytes of data plus output overhead, send.rs:206).
- The `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` is evaluated against the understated vbytes, so a transaction that would actually be below min-relay-fee is accepted (send.rs:211-213).
- `NotEnoughFunds` is checked against the understated fee (send.rs:215).
- The change-amount branch uses `fee_with_change` that is also understated, so change is credited more than it should be while the miner fee still comes up short (send.rs:227-232).
- The `MAX_STANDARD_TX_WEIGHT` check also excludes the data output's weight (send.rs:241).

The transaction is then signed via `taproot_key_spend_signature_hash` with `Prevouts::All` (send.rs:373-390). The sighash commits to the real transaction *including* the OP_RETURN output, so the signature is valid — but the broadcast transaction pays less than the requested fee rate, and can fall below the node's minimum relay fee despite the explicit `TooLowFee` guard.

### Impact Explanation
Any plan that attaches Serai data (`data: Option<Vec<u8>>` up to 80 bytes, reachable from processor-originated send plans) produces a transaction whose actual fee rate is strictly lower than the caller-specified `fee_per_vbyte`, and potentially below `DEFAULT_MIN_RELAY_TX_FEE`. Such a transaction will not relay/confirm, so the input UTXOs it spends are effectively locked: the threshold signature already consumed a FROST signing session bound to this exact transaction, and the protocol cannot spend those inputs again without a new signing round — while downstream logic may treat the payment as sent. This is "funds reported handled but not spendable in practice", the same medium-severity class as the report (balance value not correctly accounted for by the code path that moves it).

### Likelihood Explanation
The trigger is simply calling `SignableTransaction::new` with a non-`None` `data` argument, which is a supported, documented code path ("If data is specified, an OP_RETURN output will be added with it", send.rs:149). No adversarial conditions are needed; the underpayment is deterministic. Whether it crosses the relay-fee threshold depends on how tight `fee_per_vbyte` was set relative to the ~80-byte shortfall, so the impact ranges from a degraded fee rate to a permanently stuck transaction.

### Recommendation
Include the OP_RETURN output in the template transaction used by `calculate_weight_vbytes` — i.e., pass `data` (or the constructed `tx_outs`) into the weight calculation at both call sites (send.rs:204 and send.rs:225), so `needed_fee`, the `TooLowFee`/`NotEnoughFunds` checks, change computation, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// Construct a transaction paying to a script, with 80 bytes of OP_RETURN data.
let inputs = vec![received_output];            // one P2TR ReceivedOutput
let payments = [(payment_script, 10_000u64)];
let data = Some(vec![0xaa; 80]);

let tx = SignableTransaction::new(inputs, &payments, None, data, FEE_RATE).unwrap();

// The signed transaction has 2 outputs (payment + OP_RETURN), but needed_fee()
// was computed from a template containing ONLY the payment output.
assert_eq!(tx.transaction().output.len(), 2);

// Recompute the real vsize and show the shortfall:
let actual_vbytes = tx.transaction().vsize() as u64;
let underpaid = FEE_RATE * actual_vbytes - tx.needed_fee();
assert!(underpaid > 0); // fee undercounted by ~ (80 + overhead) * FEE_RATE sats
```
With `FEE_RATE` low enough that `needed_fee` just passes the `TooLowFee` check on the data-less template, the final transaction's true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and will be rejected by standard nodes, leaving the signed inputs unspendable until a new signing round.

Note: I verified this by inspection of `calculate_weight_vbytes` and `SignableTransaction::new`; I could not run the test suite in this mode, so the exact satoshi shortfall depends on the library's `weight()` accounting for the extra output.
