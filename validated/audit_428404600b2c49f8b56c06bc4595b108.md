### Title
Fee and minimum-relay check in `SignableTransaction::new` are computed on a transaction that omits the OP_RETURN output, so data-bearing transactions are signed with a lower fee rate than requested - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Like `claimDefaulted` computing interest on a `debt_` amount that already contains interest (distorting `outstandingDebt` accounting), `SignableTransaction::new` computes the transaction weight/vbytes — the base for the fee and the minimum-relay check — on an output set that excludes the OP_RETURN data output that is actually included in the final transaction. The result is a signed transaction whose real fee rate is systematically lower than `fee_per_vbyte`, and which can fall below the mempool minimum relay fee.

### Finding Description
`SignableTransaction::new` appends the OP_RETURN output to `tx_outs` at `send.rs:194-202`, but the vbyte estimates used for pricing are produced by `calculate_weight_vbytes(tx_ins.len(), payments, None)` at `send.rs:204` and, when change exists, `calculate_weight_vbytes(..., Some(&change))` at `send.rs:225-226`. `calculate_weight_vbytes` (`send.rs:62-127`) builds a template `Transaction` whose `output` list is built **only** from `payments` plus the optional change output — `data` is never passed in or modeled.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) prices a transaction smaller than the one returned in `Ok(SignableTransaction { tx: ..., output: tx_outs, ... })` (lines 245-255). The OP_RETURN output costs ~9 + len(data) vbytes (up to ~89 vbytes with the 80-byte limit enforced at line 171), none of which is charged for.
- `NotEnoughFunds` (line 215) is checked against an understated fee; change value at lines 228-230 is `input_sat - (payment_sat + fee_with_change)` where `fee_with_change` is also understated — so the change output is over-valued by the uncharged bytes. The change is still valid Bitcoin (the deficit just becomes extra fee), but the *rate* guarantee is broken.
- The `TooLowFee` check at line 211 compares the understated `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` on the understated `vbytes`, so it cannot detect that the *actual* rate `fee() / actual_vsize` has dropped below the relay minimum when `data` is large and `fee_per_vbyte` is near the minimum.

Reachable from public inputs: `SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)` takes attacker/instruction-controlled `data: Option<Vec<u8>>` and `payments`, and the resulting `tx` is what `sign` produces a Schnorr signature over — the multisig signs an unintended fee rate and a potentially non-relayable transaction.

### Impact Explanation
For any plan carrying data (e.g., `Shorthand`-encoded InInstruction payloads embedded as OP_RETURN), the network pays up to ~89 vbytes per transaction that were never priced. At boundary fee rates the produced transaction's real feerate falls below `DEFAULT_MIN_RELAY_TX_FEE`, so it will not propagate — inputs are locked behind a signed-but-unbroadcastable transaction until re-signed, and accounting that trusts `needed_fee()`/`fee()` records a rate the transaction does not achieve. This is the same distortion shape as the Cooler report: a derived quantity (interest / fee) computed over a base value that is not the true base (debt-including-interest / tx-outputs-minus-OP_RETURN), silently corrupting the downstream accounting.

### Likelihood Explanation
Every data-carrying send hits the undercount unconditionally — it is not an edge case. Whether it drops the effective rate below relay minimum depends on `fee_per_vbyte` and data length; with a full 80-byte payload and a fee rate within ~2× the minimum, the effective rate is measurably reduced. Even when the TX still relays, the paid rate is always lower than specified, degrading confirmation time under congestion.

### Recommendation
Pass the OP_RETURN output (or its serialized size) into `calculate_weight_vbytes` — e.g., extend it to accept the full output list including the data output, and call it with `data`-inclusive outputs at both the no-change site (`send.rs:204`) and the with-change site (`send.rs:226`). Ensure `needed_fee`, the `TooLowFee` check, and the change computation all price the identical output set that appears in the final `tx`.

### Proof of Concept
```rust
// networks/bitcoin — concept against SignableTransaction::new
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), FEE).unwrap();
// tx.needed_fee() == FEE * vbytes(tx without OP_RETURN)
// actual vsize includes the ~89-byte OP_RETURN output:
//   tx.fee() / actual_vsize < FEE
// With FEE ~= min relay rate, tx.fee() / actual_vsize < DEFAULT_MIN_RELAY_TX_FEE/1000
// → signed transaction is rejected by the mempool despite passing the TooLowFee check.
```
