### Title
Rounding-to-zero in same-chain partial-fill escrow release lets an early solver's input reward vanish and be absorbed by the completing solver - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents.sol`'s partial-fill path computes the escrowed input released to a solver as `(order.inputs[i].amount * fillAmount) / totalRequired`, the same integer-division-can-truncate-to-zero pattern flagged in the Locke.sol report. Unlike Locke.sol, which reverts with `ZeroAmount()` when the computed stream amount truncates to zero, this contract has no such guard: a solver whose `fillAmount` rounds `escrowedAmount` down to `0` still has their partial fill fully recorded in `_partialFills`, delivers real output tokens to the beneficiary, but receives zero input tokens in return. The un-debited escrow is later handed entirely to whichever solver happens to complete the order, because the final fill branch releases `_orders[commitment][token]` (the full remaining balance) rather than the proportional share.

### Finding Description
In `_fillSameChain` (`IntrinsicIntents.sol`):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

`escrowedAmount` is then passed into `_withdraw`, which silently skips zero-amount token releases without touching escrow accounting:

```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) continue;

uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
``` [2](#0-1) 

Whenever `order.inputs[i].amount * fillAmount < totalRequired` (low-decimal input token relative to a high-decimal output, or a small `fillAmount` relative to `totalRequired` — exactly the "low decimal / long duration" analog from the external report), `escrowedAmount` truncates to `0`. The solver's tokens are transferred to the beneficiary (`beneficiaryTotal`/`protocolShare` logic runs unconditionally), `_partialFills[commitment][outputToken]` is advanced, but no corresponding debit occurs against `_orders[commitment][token]`. That un-debited amount is not tracked per-solver; it simply remains in the escrow bucket. When the order is later fully completed, the *finishing* solver's branch (`amountFilled == totalRequired`) grabs the **entire remaining balance** in `_orders[commitment][token]`, which includes the dust that rightfully belonged to the earlier solver whose fill rounded to zero.

### Impact Explanation
This produces a wrong-beneficiary/wrong-amount fund transfer directly in escrow settlement: the solver who executed a legitimate partial fill and paid out real output tokens receives nothing for it (fund loss), while the solver who happens to complete the order is enriched by the escrow that should have gone to the earlier solver. Escrowed inputs must "move exactly once and only to the rightful beneficiary and amount," and this rounding path breaks that invariant without requiring a malicious relayer, prover, or admin — it can be triggered by any two unprivileged solvers filling the same public order.

### Likelihood Explanation
The condition is easy to hit: any order pairing a low-decimal input token (e.g., 6-decimal USDC) with a higher-decimal or high-denomination output token, filled in small increments, can produce `escrowedAmount == 0` on non-final fills. No special privileges or governance actions are needed — an attacker simply needs to submit (or wait for) a small partial fill and then be positioned to submit the completing fill, capturing the unaccounted dust.

### Recommendation
Mirror the fix already applied to same-chain full completion, but apply it to every fill: track the previously-released escrow amount (`alreadyReleased`) instead of deriving from `order.inputs[i].amount * fillAmount / totalRequired` afresh, and compute each release as `newAlreadyFilledEscrow - alreadyReleased`, or explicitly revert (`if (escrowedAmount == 0) revert ZeroAmount();`) when a non-final partial fill would release zero, forcing the fill to be batched into a size that doesn't truncate. Either approach prevents a completing solver from inheriting escrow that was already "spent" by an earlier truncated fill.

### Proof of Concept
1. Place an order with `inputs[0].amount = 100e6` (100 USDC, 6 decimals) and `output.assets[0].amount = 3e18` (3 DAI, 18 decimals), matching the pattern already exercised in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` `testPartialFill_RoundingDustReleasedToFinalSolver` [3](#0-2) .
2. Solver A fills with a `fillAmount` sized so `(100e6 * fillAmount) / 3e18 == 0` (e.g. `fillAmount = 1` wei of DAI) — Solver A transfers real DAI to the beneficiary but `escrowedAmount` computes to `0`, so Solver A receives no USDC and `_orders[commitment][usdc]` is left undebited for that fill.
3. Solver B (attacker) completes the remainder of the order. Because the `amountFilled == totalRequired` branch releases the entire `_orders[commitment][usdc]` balance, Solver B receives the full 100 USDC — including the share that was already "spent" (in DAI) by Solver A but never credited to anyone.
4. Net result: Solver A lost real DAI value with zero USDC compensation; Solver B received more USDC than their proportional DAI contribution justified.
