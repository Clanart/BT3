### Title
Daemon KeychainServer trusts client-supplied `kc_user`/`kc_service` identity without authorization, allowing cross-namespace keychain access - (File: `chia/daemon/keychain_server.py`)

### Summary
`KeychainServer.get_keychain_for_request()` selects which OS-backed `Keychain` instance to operate on based solely on the `kc_user`/`kc_service` fields present in the client-supplied request JSON, with no verification that the connecting daemon client is actually authorized to act as that user/service. This mirrors the CVE-2017-8422 pattern, where a privileged local helper (KAuth) trusted a caller-supplied identity ("callerID") instead of verifying it, letting an unprivileged local caller impersonate another principal and reach privileged operations under that spoofed identity.

### Finding Description
The Chia daemon (`chia/daemon/server.py`) is a local privilege concentrator reachable by any process holding a valid daemon private TLS client certificate (any locally-installed Chia service, plugin, or subprocess that shares the private CA — e.g. a plotter, harvester, or any component using `KeychainProxy`) [1](#0-0) . Keychain-related commands (`add_key`, `get_all_private_keys`, `get_first_private_key`, `delete_all_keys`, `delete_key_by_fingerprint`, `get_key`, `get_keys`, etc.) are dispatched to `KeychainServer.handle_command()` before normal command routing [2](#0-1) .

Every one of these keychain operations resolves its target `Keychain` instance via:

```python
def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
    user = request.get("kc_user", self._default_keychain.user)
    service = request.get("kc_service", self._default_keychain.service)
    ...
    keychain = Keychain(user=user, service=service)
    self._alt_keychains[key] = keychain
    return keychain
``` [3](#0-2) 

`kc_user` and `kc_service` are plain, unauthenticated fields taken directly from the attacker-controlled JSON `data` payload of the websocket message — the same envelope fields the legitimate `KeychainProxy` sets from its own locally-configured `user`/`service` [4](#0-3) . Nothing in `handle_command()`, `run_request()`, `add_key()`, `get_all_private_keys()`, `get_first_private_key()`, `get_key_for_fingerprint()`, or `delete_all_keys()`/`delete_key_by_fingerprint()` cross-checks that the requesting connection is entitled to operate under the claimed `kc_user`/`kc_service` pair [5](#0-4) . Any client that can reach the daemon websocket (which, per the daemon's own security model, is any process holding a private daemon cert — not scoped per-service) can therefore supply an arbitrary `kc_user`/`kc_service` string and have the daemon instantiate/query a *different* OS keyring namespace than the one it is legitimately entitled to, exactly as KAuth trusted an attacker-spoofed `callerID` to authorize a privileged action on someone else's behalf.

The `WebSocketServer`'s only gate is mutual TLS against the shared private CA [6](#0-5) ; there is no per-service authorization mapping a connected client's certificate identity to the `kc_user`/`kc_service` it is allowed to request. This means the "callerID" (here, `kc_user`/`kc_service`) is entirely self-asserted by the caller and blindly trusted by the privileged helper (`KeychainServer`), the same root cause as CVE-2017-8422.

### Impact Explanation
A local process that is merely a valid daemon client (e.g., a compromised or malicious plugin/subprocess granted daemon access for an unrelated purpose, or any service using `KeychainProxy`) can request keychain operations under a spoofed `kc_user`/`kc_service` identity. Depending on how the OS keyring backend partitions data by these strings, this can expose or delete private keys (mnemonics/entropy) belonging to a different keychain namespace than the caller's own, via `get_all_private_keys`, `get_first_private_key`, or `get_key_for_fingerprint` (impact: **C**), or destructively wipe another namespace's keys via `delete_all_keys`/`delete_key_by_fingerprint` (impact: **I/A**). Exfiltrated private keys enable unauthorized signing and unsigned/unauthorized coin movement from the victim namespace's wallet, matching the "concrete unsigned or unauthorized coin movement" acceptance criterion.

### Likelihood Explanation
Exploitation requires the attacker to already be a locally-authenticated daemon client (holder of a valid daemon private certificate) — this is the same starting position CVE-2017-8422 assumed ("local users"). No additional privilege beyond routine local daemon connectivity is needed; the attacker does not need to compromise the target's keyring credentials, only supply different `kc_user`/`kc_service` strings in an otherwise normal keychain RPC call, which is a documented, first-class parameter of the wire protocol (`KeychainProxy.format_request`) [7](#0-6) .

### Recommendation
Bind the `kc_user`/`kc_service` values to a server-verified identity for the connection (e.g., derived from the client's TLS certificate identity or a value fixed at daemon registration time) rather than accepting them verbatim from client-supplied JSON in `get_keychain_for_request()`. Alternatively, restrict `kc_user`/`kc_service` overrides to trusted/administrative connections only, and reject keychain requests where the claimed namespace does not match the connection's registered service identity.

### Proof of Concept
1. Establish a normal daemon websocket connection using any valid daemon private client certificate (as any locally-installed Chia component can).
2. Send a `get_all_private_keys` (or `get_key_for_fingerprint`, `delete_all_keys`, etc.) command payload with `data = {"kc_user": "<victim_user>", "kc_service": "<victim_service>"}` instead of the caller's own values, exactly like `KeychainProxy.format_request()` does for its own user/service pair [8](#0-7) .
3. `KeychainServer.get_keychain_for_request()` accepts these attacker-chosen values unconditionally and instantiates/looks up a `Keychain(user="<victim_user>", service="<victim_service>")` [9](#0-8) , returning that namespace's private key/mnemonic data (or deleting it) to the caller — without any check that the caller is authorized to act as `<victim_user>`/`<victim_service>`.

Note: full verification of whether distinct `kc_user`/`kc_service` pairs map to genuinely isolated OS-keyring secrets across different locally-registered Chia components (vs. always resolving to the same OS-level keyring for a single machine) would require exercising the live keyring backend, which was not directly observable from the indexed source; this should be validated experimentally before treating this as fully confirmed cross-tenant impact.

    def get_keychain_for_request(self, request: dict[str, Any]) -> Keychain:
        """
        Keychain instances can have user and service strings associated with them.
        The keychain backends ultimately point to the same data stores, but the user
        and service strings are used to partition those data stores. We attempt to
        maintain a mapping of user/service pairs to their corresponding Keychain.
        """
        user = request.get("kc_user", self._default_keychain.user)
        service = request.get("kc_service", self._default_keychain.service)
        if user == self._default_keychain.user and service == self._default_keychain.service:
            keychain = self._default_keychain
        else:
            key = (user or "unnamed") + (service or "")
            if key in self._alt_keychains:
                keychain = self._alt_keychains[key]
            else:
                keychain = Keychain(user=user, service=service)
                self._alt_keychains[key] = keychain
        return keychain
