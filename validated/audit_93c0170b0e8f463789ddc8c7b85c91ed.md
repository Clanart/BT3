### Title
`ReceivedOutput::read` accepts an unbound (offset, value, outpoint) triple, letting untrusted bytes claim arbitrary, unspendable Bitcoin funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The Mycodo CVE-2021-41185 class is an attacker-controlled locator escaping the intended namespace (a file path resolving outside its directory). The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 122-134): a `ReceivedOutput` is the "locator" that tells the wallet which on-chain UTXO to spend and under which key offset, yet deserialization binds none of its fields together. Any scalar `offset`, any `TxOut` (arbitrary `value` and `script_pubkey`), and any `OutPoint` are accepted independently.

### Finding Description
`ReceivedOutput::read` (mod.rs:122-134) performs three unchecked reads:

- `offset = Secp256k1::read_F(r)` — an arbitrary scalar, not verified against `self.output.script_pubkey`.
- `output = TxOut::consensus_decode(...)` — arbitrary `value` and `script_pubkey`.
- `outpoint = OutPoint::consensus_decode(...)` — arbitrary txid/vout, never checked to exist or to actually carry `output`.

The only consistency check in the spend path is `SignableTransaction::multisig` in `networks/bitcoin/src/wallet/send.rs:273-285`, which verifies `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — i.e., it binds the offset to the *claimed* script. Nothing binds the claimed `value`/`script_pubkey`/`outpoint` to a real UTXO. Downstream, `SignableTransaction::new` (send.rs:175-253) sums `input.output.value` for fee/balance math and stores the attacker-chosen `TxOut`s as `prevouts`, which `TransactionSignMachine::sign` (send.rs:373-390) commits into the BIP-341 sighash via `Prevouts::All`. `Output::balance` / `Output::key` in the consuming code likewise trust `output.value()` and `offset()` directly.

### Impact Explanation
Wherever serialized `ReceivedOutput`s are transported or reloaded across a trust boundary (network messages, coordinator-supplied data, or restored state), an unprivileged party can inject bytes describing an output that was never received: a fabricated or mis-valued outpoint with a self-consistent script/offset. The system will then (a) report a balance for funds that do not exist or are not spendable by the group key, and (b) construct and threshold-sign a transaction whose `Prevouts::All` commitment and input reference a nonexistent or misvalued UTXO — producing a transaction that is permanently invalid on-chain while consuming a signing session. This is the direct analog of "downloading files outside the intended directory": the deserializer resolves attacker-supplied locators outside the set of actually-received outputs.

### Likelihood Explanation
Reachable by any party able to feed bytes to `ReceivedOutput::read` / `Output::read` (which embeds it). The offset↔script check in `multisig` does not detect the attack because the attacker chooses a self-consistent pair; only value/outpoint-vs-chain consistency is missing, and the in-scope crate provides no such check. Exploitation requires an upstream consumer that trusts deserialized outputs without re-confirming them on-chain — the crate's own design (scanner → serialize → read → spend) makes that a supported flow.

### Recommendation
- Treat `ReceivedOutput` as a claim, not a fact: after `read`, require re-verification of the outpoint against a Bitcoin node (tx exists, `tx.output[vout]` equals the decoded `TxOut`) before crediting balance or signing.
- Alternatively, make `ReceivedOutput::read` private and expose construction only via `Scanner::scan_transaction`/`scan_block`, which derives `offset` from `self.scripts` and the real `TxOut`/`OutPoint` from the chain.
- At minimum, document that deserialization carries no chain-validity guarantee and add a `verify(rpc)` method that re-binds all three fields.

### Proof of Concept
```rust
use bitcoin::{
  consensus::encode::serialize, absolute::Amount, transaction::Transaction, OutPoint, ScriptBuf,
  TxOut, Txid, hashes::Hash,
};
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};
use k256::{ProjectivePoint, Scalar};

// Crafted bytes: offset/script are self-consistent (so `multisig` passes), but the
// outpoint references a txid the attacker invented and value is inflated.
fn forged_received_output(key: ProjectivePoint) -> Vec<u8> {
  // Offset 0 -> script = p2tr(key), internally consistent
  let offset = Scalar::ZERO;
  let fake_txout = TxOut {
    value: Amount::from_sat(1_000_000_000), // 10 BTC claimed
    script_pubkey: p2tr_script_buf(key).unwrap(),
  };
  let fake_outpoint = OutPoint { txid: Txid::all_zeros(), vout: 0 };

  let mut buf = vec![];
  buf.extend(offset.to_bytes());
  buf.extend(serialize(&fake_txout));
  buf.extend(serialize(&fake_outpoint));
  buf
}

// ReceivedOutput::read accepts this unconditionally:
//   let output = ReceivedOutput::read(&mut forged.as_slice()).unwrap();
//   output.value() == 1_000_000_000  // phantom balance reported
// SignableTransaction::new(vec![output], ...) then builds a tx spending txid 00..00:0
// and every signer commits to the fake prevout under Prevouts::All, yielding a
// permanently invalid transaction for "funds" that were never received.
```
Root cause: `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes a locator triple with no binding to actually-received chain data; the only downstream check (send.rs:277) validates offset↔script, not the outpoint/value against the chain.
