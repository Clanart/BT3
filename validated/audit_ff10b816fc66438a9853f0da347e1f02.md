### Title
OP_RETURN data output omitted from fee and weight calculation causes underpaid fees / non-relayable transactions - (networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to `tx_outs`, but then computes the transaction weight/vbytes (and hence the required fee and the `MAX_STANDARD_TX_WEIGHT` check) using only `payments` — the data output is never included. The resulting transaction is larger than what was paid for, so its effective feerate is lower than `fee_per_vbyte` and can fall below the mempool minimum relay fee, or exceed the standardness weight limit entirely, making the signed transaction non-relayable. This is the same bug class as the referenced finding: an uncharged marginal cost (`data`) lets a requester make the multisig emit a transaction whose paid fee does not cover its real cost.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the size/fee estimation:

- `networks/bitcoin/src/wallet/send.rs:194-202` — the OP_RETURN output is appended to `tx_outs`.
- `networks/bitcoin/src/wallet/send.rs:204` — `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` is called with `payments`, not `tx_outs`, so the OP_RETURN output contributes nothing to `weight`/`vbytes`.
- `networks/bitcoin/src/wallet/send.rs:206` — `needed_fee = fee_per_vbyte * vbytes` is therefore undercharged by the size of the data output (~90+ vbytes for an 80-byte payload plus output overhead).
- `networks/bitcoin/src/wallet/send.rs:241` — the `MAX_STANDARD_TX_WEIGHT` check uses the same underestimated `weight`, so a transaction that is actually non-standard passes validation.

Because `Prevouts::All` commits each input's signature to the full output set (`send.rs:375-386`), once signed, the underpriced/non-standard transaction cannot be amended without a new signing round — the inputs are locked to it.

### Impact Explanation
Any caller able to attach `data` to a transaction the multisig signs causes the threshold to produce a transaction whose actual feerate is materially below the requested `fee_per_vbyte` — up to ~90+ vbytes unpaid per transaction. At the margin this can push the transaction below the mempool minimum relay feerate or over the standardness weight cap, producing a fully signed, correctly-formed transaction that nodes refuse to relay/confirm. The prevouts committed in the inputs then sit unspendable until the plan is retried, and the value difference is burned to miners if the transaction does eventually confirm at the intended absolute fee on a larger transaction. Unlike the underpriced-VRF issue this is not a direct treasury drain, but it is a concrete economic miscalculation: a marginal cost (the data output) is imposed without being charged, reachable purely by supplying `data` bytes to `SignableTransaction::new`.

### Likelihood Explanation
`data` is a public, attacker-influenceable parameter of `SignableTransaction::new` (`send.rs:154`), bounded only by the 80-byte `TooMuchData` check (`send.rs:171`). Whether a deployment exposes it to unprivileged users depends on the integrator, but within this crate's trust model the bug deterministically misprices every transaction carrying data — low difficulty, moderate impact (fee underpayment / relay failure), consistent with Medium severity.

### Recommendation
Compute `calculate_weight_vbytes` over the final `tx_outs` (including the OP_RETURN output) rather than `payments`, and include the data output in both the change-aware recomputation at `send.rs:225-226` and the `MAX_STANDARD_TX_WEIGHT` check. Alternatively, serialize the candidate outputs directly for weight estimation so any future output types are automatically accounted for.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with maximal data.
let data = vec![0u8; 80];
let st = SignableTransaction::new(inputs, &payments, change, Some(data), fee_per_vbyte).unwrap();

// needed_fee was computed on a transaction WITHOUT the OP_RETURN output.
let declared = st.needed_fee(); // fee_per_vbyte * vbytes(payments only)
let actual_vbytes = st.transaction().vsize() as u64; // includes OP_RETURN
// effective feerate = fee() / actual_vbytes < fee_per_vbyte
assert!(st.fee() < fee_per_vbyte * actual_vbytes);
// With ~90 unpaid vbytes, effective feerate is reduced by ~fee_per_vbyte * 90 sats.
```
