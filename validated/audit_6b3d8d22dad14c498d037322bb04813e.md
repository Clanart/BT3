## Finding

Chia's offer object contains an unbounded, non-CLVM-cost-metered algorithm for computing which coins must be spent to cancel a trade. This is structurally analogous to the MongoDB `$trim`/`$ltrim`/`$rtrim` bug: an authenticated actor (there, an aggregation user; here, a wallet user/offer counterparty) supplies attacker-crafted input (a dense char mask; here, a spend bundle with many announcement dependencies) that drives a nested, quadratic-or-worse loop with no cost/iteration bound, pinning CPU.

### Title
CPU exhaustion via unbounded nested dependency resolution in `Offer.get_cancellation_coins()` - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` walk the coin-announcement dependency graph of an offer's `WalletSpendBundle` using plain Python nested loops with no bound tied to CLVM cost, unlike normal spend-bundle execution which is metered by `MAX_BLOCK_COST_CLVM`/`max_tx_clvm_cost`. A malicious offer file with many coin spends chained by `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions can force this function into worst-case behavior, consuming CPU disproportionate to the actual CLVM execution cost paid.

### Finding Description
`detect_dependent_coin()` at [1](#0-0)  performs a triple-nested scan over `names`, each coin's `deps`, and every `announcement_dict` entry — O(N·D·A) per call, where N is the number of non-addition coin spends, D is dependencies per coin, and A is announcements per coin.

`get_cancellation_coins()` calls `detect_dependent_coin()` inside an outer `while True` loop that can iterate up to N times (each iteration removes at least one coin), and for each hit runs a second inner `while True` loop at [2](#0-1)  that itself does another full scan of `dependencies.items()` intersected against `set(removed_announcements)` — repeated until no more announcements cascade.

Unlike CLVM puzzle execution (which is cost-metered per `chia/types/clvm_cost.py` / `MAX_BLOCK_COST_CLVM`), this dependency resolution runs entirely in the Python wallet layer, after `run_with_cost()` has already produced the conditions [3](#0-2) . There is no cap on the number of coin spends in the underlying spend bundle, nor on the number of announcement conditions per spend, nor on the depth of the dependency chain — an attacker fully controls all three by constructing an `Offer` (which is just a `WalletSpendBundle` plus `requested_payments`/`driver_dict` metadata) with many coins each creating and asserting chained announcements.

This is reachable by any wallet user who receives and processes an untrusted offer file from a counterparty — exactly the "offers and trades" surface flagged as in-scope. `Offer` objects are parsed from arbitrary bytes/files (`Offer.from_bech32`/`from_bytes` elsewhere in the class) supplied by a counterparty, and `get_cancellation_coins()` is invoked from `chia/wallet/trade_manager.py` when a wallet examines or attempts to cancel a trade — a normal, unprivileged, local-RPC-triggered wallet action.

### Impact Explanation
A crafted offer file can cause a wallet's `get_cancellation_coins()` call to consume disproportionate CPU relative to the size/cost of the underlying spend bundle, since the O(N·D·A) inner scan is repeated across cascading outer/inner while-loops without any cost accounting or iteration cap. This can pin a wallet process's CPU when a user merely inspects or attempts to cancel a received offer — a spend-triggered processing halt/degradation, matching the reachable "resource-only... spend-triggered transaction-processing halt" impact category allowed by the validation rules (offers and trades flow, reachable by an unprivileged offer counterparty).

### Likelihood Explanation
Likely exploitable: offer files are untrusted-by-design (received from arbitrary counterparties before acceptance/cancellation), the wallet already parses full `CoinSpend` lists and conditions from them, and there is no existing limit in this code path analogous to CLVM's cost metering. Constructing many coins with chained `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` pairs is straightforward using standard puzzle/solution construction and does not require any privileged access — only that the victim wallet loads/inspects the offer.

### Recommendation
Bound the dependency-resolution algorithm: cap the number of coin spends/announcements considered, replace the O(N·D·A) linear scan of `announcement_dict.items()` in `detect_dependent_coin()` with a hash-based reverse index (announcement value → owning coin) to make lookups O(1), and impose an overall iteration/time budget on `get_cancellation_coins()` proportional to the CLVM cost already charged for the underlying spend bundle, rejecting or truncating processing for offers that exceed sane spend/announcement counts.

### Proof of Concept
Not independently executed against a live node; based on static code review. A PoC would construct an `Offer`/`WalletSpendBundle` with N coin spends (e.g., a few thousand) where coin_i creates a `CREATE_COIN_ANNOUNCEMENT` consumed by an `ASSERT_COIN_ANNOUNCEMENT` in coin_(i+1), forming a long dependency chain, then call `offer.get_cancellation_coins()` (as `trade_manager.py` does) and observe superlinear wall-clock growth as N increases, disproportionate to CLVM execution cost of the bundle. I was not able to run this in this environment to confirm actual timing numbers; the structural nested-loop analysis above is the primary evidence.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```
