## Title
Line-index-based partial-commit selections are silently re-applied to a freshly fetched (and possibly different) diff, letting a mutated working file cause the wrong lines to be staged/committed — (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/updates/changes-state.ts`)

### Summary
The Angle report's root cause is that a *derived/displayed value* (`estimatedAPR`) is trusted without re-validating that the underlying condition it was computed from (`lockedProfit`) is still true. GitHub Desktop has a structurally identical pattern: a user's partial-commit line selection is computed against a specific diff snapshot (by absolute line index), but that selection is later re-applied to a *newly fetched* diff at commit time without verifying the two diffs still match. If the working file changes between the time the user makes a line selection and the time Desktop actually stages the patch, the line indices silently point at the wrong content.

### Finding Description
When a user partially selects lines/hunks to commit, the selection is stored as a `DiffSelection` keyed by absolute line index against the diff that was rendered in the UI [1](#0-0) . That selection is carried on the `WorkingDirectoryFileChange` object and is preserved across working-directory refreshes purely by file `id` (i.e., by path), with no linkage to which diff snapshot the selection was made against [2](#0-1) .

Crucially, `updateChangedFiles` explicitly reuses the *stale cached diff* (`state.selection.diff`) as long as the same single file id remains selected, deferring the real refresh to a separate async call: [3](#0-2) 

Meanwhile, at actual staging time, `applyPatchToIndex` does **not** reuse whatever diff the UI had — it fetches a brand-new, live diff from disk right before building the patch: [4](#0-3) 

`formatPatch` then walks that freshly-fetched diff's hunks and includes/excludes lines purely based on `file.selection.isSelected(absoluteIndex)` — i.e., the line-index selection captured earlier against whatever diff was displayed to the user: [5](#0-4) 

There is no check anywhere in this pipeline that the diff used to build `file.selection` (line indices) is the same diff being patched at commit time. `_commitIncludedChanges` simply takes whatever files/selection exist in `repositoryStateCache` at the moment "Commit" is pressed and hands them to `createCommit` → `stageFiles` → `applyPatchToIndex`: [6](#0-5) [7](#0-6) 

If the file's on-disk content changes between when the user's selection was made (against diff D1) and when `applyPatchToIndex` fetches the live diff (D2 ≠ D1) — e.g., because a git clean/smudge filter, a checkout/merge/pull hook, or an editor autosave rewrote the file in the interim — the absolute line indices in `file.selection` no longer point at the same logical lines in D2. `formatPatch` will silently include unintended lines (from D2) as "selected" or exclude lines the user actually meant to include, exactly the "corrupted value keeps being used after the state it was computed from has changed" class of bug described in the Angle report (stale `vestingProfit`/`vestingPeriod` re-used after `lockedProfit()` hit zero, with no invalidation check).

### Impact Explanation
This breaks the fundamental invariant that "what the user visually selected to stage is what gets committed." An attacker who controls a cloned/fetched repository can plant `.gitattributes` filters or git hooks (`post-checkout`, `post-merge`, `pre-commit`, clean/smudge filters) that rewrite a tracked file's content as part of normal git operations Desktop performs (checkout, pull, fetch+merge). If this mutation lands between the moment the user reviews/selects lines in the Changes view and the moment they click Commit, the resulting commit can silently contain different content than what the user saw and approved — satisfying the "silent corruption of what user commits" impact bucket. This is distinct from a UI-only staleness bug because the corrupted artifact (the actual git commit/patch) is a persistent, pushed change, not just a rendering glitch.

### Likelihood Explanation
Requires a race between a background diff/content change and a user-initiated partial commit — no local/physical access, admin rights, or pre-existing malware is required, only cloning/fetching and normally operating on an attacker-authored repository (which is squarely inside GitHub Desktop's threat model). The window is realistic because Desktop performs many implicit refreshes (file-watcher-triggered `_loadStatus`, periodic background refresh, post-fetch/post-checkout refresh) while the Changes view and its cached selection/diff persist across those refreshes without invalidation tied to diff identity.

### Recommendation
Tie `DiffSelection` to the diff snapshot it was computed against (e.g., a content hash or the diff object itself) rather than only to the file id. Before staging a partial selection in `applyPatchToIndex`, verify that the freshly fetched diff structurally matches (same hunk boundaries/hashes as) the diff the selection was made against; if it doesn't, force the UI to re-derive/discard the stale selection (similar to the existing `selectableLines` recomputation logic already present for the *display* path) rather than silently applying it to different content.

### Proof of Concept
1. Clone/open an attacker-authored repository in Desktop that includes a `post-checkout`/`post-merge` hook (or `.gitattributes` clean filter) which rewrites `file.txt` content shortly after a checkout/fetch operation.
2. User opens the Changes tab, Desktop renders diff D1 for `file.txt`, user manually selects a subset of lines to stage (e.g., excludes a sensitive line).
3. Trigger a background refresh (e.g., fetch/pull, or the hook fires from a prior checkout) that rewrites `file.txt` on disk, changing hunk structure to D2, while the UI keeps showing/preserving the old line-index selection (`updateChangedFiles` reuses `state.selection.diff`/selection by file id, see `app/src/lib/stores/updates/changes-state.ts` lines 90-104).
4. User clicks Commit before the UI's async diff refresh (`updateChangesWorkingDirectoryDiff`) completes and reconciles selection against D2.
5. `applyPatchToIndex` fetches D2 fresh from disk and calls `formatPatch(file, D2)` using the line indices computed for D1, producing a patch that stages different content than the user selected — verifiable by comparing the resulting commit's diff to what was displayed in the UI at selection time.

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
