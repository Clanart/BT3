### Title
Attacker-crafted offer with a cyclic removal-coin lineage causes an infinite loop / wallet hang in `Offer.get_root_removal` - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks the `parent_coin_info` chain of an offer's removal coins until it reaches a "non-ephemeral" removal (a coin whose parent is not itself in the removal set). Because `Coin.parent_coin_info` is an arbitrary field supplied by whoever constructs the `SpendBundle`/offer, a malicious offer can declare two (or more) removal coins whose `parent_coin_info` values point at each other, forming a cycle. Every removal in that cycle is excluded from `non_ephemeral_removals`, so the `while` loop in `get_root_removal` never terminates.

### Finding Description
`get_root_removal` computes: [1](#0-0) 

- `all_removals` is the raw set of `Coin`s taken from `self.removals()` of the offer's bundle — fully attacker controlled content of an offer file.
- `non_ephemeral_removals` = removals whose `parent_coin_info` is **not** the name of another removal in the set.
- The loop `while coin not in non_ephemeral_removals: coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)` walks "up" the parent chain.

`Coin.name()` is a hash of `(parent_coin_info, puzzle_hash, amount)`, but `parent_coin_info` itself is just a free-form 32-byte field — it is not required to correspond to a coin that ever existed on-chain, and nothing in `Offer.from_bytes`/parsing validates that the removal graph is acyclic. An attacker can therefore construct two synthetic coins A and B (with unrelated puzzle hashes/amounts so their names differ) such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`. Both A and B then have parents inside the removal set, so neither is ever added to `non_ephemeral_removals`, and the `while` loop in `get_root_removal` oscillates between A and B forever. This is the same bug class as the CVE reference: a self/mutually-referencing linked structure that a parser walks without cycle detection, leading to an unbounded loop.

`get_root_removal` is used by:
- `get_primary_coins()` [2](#0-1) 
- `get_pending_amounts()` [3](#0-2) 

Both are offer-summary/UI-facing helpers that a wallet is expected to invoke whenever a locally received offer (e.g., from a counterparty, marketplace, or DataLayer offer flow) is inspected, summarized, or accepted — i.e., reachable from ordinary offer-counterparty interaction without needing to broadcast anything to the mempool.

### Impact Explanation
A malicious offer counterparty can hand a victim wallet an offer file that never terminates being summarized/processed, freezing the wallet's async event loop thread that runs the calculation (Python coroutines run cooperatively; a tight infinite CPU loop like this will stall the whole wallet service, including RPC responsiveness). This is a spend-triggered transaction-processing halt reachable purely through offer inspection by a wallet user — no signature or actual on-chain event needed, since `Offer` construction/parsing does not validate the removal-coin lineage graph for cycles before this traversal is invoked.

### Likelihood Explanation
Constructing such an offer requires only fabricating a `WalletSpendBundle` with two or more `CoinSpend`s whose `Coin.parent_coin_info` fields reference each other's `name()`. This does not require any real coins, signatures over consensus rules, or full-node cooperation — the vulnerable code path executes purely on locally-held `Offer` object data before/without submission to the network. Any tool or workflow that displays offer contents to the user (offer summary, `get_offer_summary`, taking an offer) would be expected to trigger it, making it easy to weaponize for a targeted DoS against anyone who opens the crafted offer file.

### Recommendation
Add cycle detection (e.g., track visited coin names) in `get_root_removal`'s `while` loop and raise a `ValueError` if a cycle is detected instead of looping forever. Alternatively, validate at `Offer` construction/parsing time that the removal-coin parent graph is acyclic and bounded in depth by the number of removals in the bundle.

### Proof of Concept
Conceptually (not verified by execution, since this is a read-only analysis):
1. Build two `Coin` objects `A` and `B` with distinct `puzzle_hash`/`amount` such that `A.parent_coin_info = B.name()` and `B.parent_coin_info = A.name()`.
2. Wrap each into a `CoinSpend` (with any valid-looking puzzle reveal/solution) and place them among the offer's non-addition removals (i.e., ensure neither is an "addition" per `self.additions()`).
3. Include one of them (or a coin whose ancestor chain leads into the cycle) among the coins returned by `get_offered_coins()`.
4. Serialize this as an `Offer` and hand it to a victim wallet; when the wallet calls `offer.get_pending_amounts()` or `offer.get_primary_coins()` (e.g., during offer summary/inspection), `get_root_removal` enters an infinite loop between A and B.

**Uncertainty/limitations**: I was not able to fully trace every UI/RPC call site that reaches `get_primary_coins()`/`get_root_removal()` in this session (only `get_pending_amounts` and `get_primary_coins` were confirmed as direct callers within `offer.py`; a full-text search found no other callers of `get_primary_coins` outside `offer.py` in the indexed code, so confirmation that a remote/RPC-facing summary path calls it should be re-verified with a full repository checkout). I recommend a Devin session with full filesystem/RPC access to confirm the exact reachable entry point (e.g., `wallet_rpc_api.get_offer_summary` or `take_offer`) and to write a runnable reproduction test.

```python
    # This returns the non-ephemeral removal that is an ancestor of the specified coin
    # This should maybe move to the SpendBundle object at some point
    def get_root_removal(self, coin: Coin) -> Coin:
        all_removals: set[Coin] = set(self.removals())
        all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
        non_ephemeral_removals: set[Coin] = {
            c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
        }
        if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
            raise ValueError("The specified coin is not a coin in this bundle")

        while coin not in non_ephemeral_removals:
            coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

        return coin
```
