### Title
Missing StateDB-type check in `HandlePrecompileError` causes nil-pointer panic on precompile errors when EVM runs with a non-`DBImpl` StateDB - ([File: precompiles/common/legacy/v575/precompiles.go])

### Summary
`VersionedPrecompiles` keeps historical precompile implementations (`v5.7.5`, `v6.0.5`, `v6.0.6`, `v6.1.0`) live and reachable so that historical blocks (replay, state-sync catch-up, or any chain still transitioning through these upgrade heights) execute EVM transactions against the exact bytecode/logic that was active at that height, as wired in e.g. `precompiles/pointer/setup.go` `GetVersioned` [1](#0-0) . In these legacy versions, `HandlePrecompileError` dereferences the result of `state.GetDBImpl(evm.StateDB)` unconditionally instead of checking it for `nil`, unlike later versions which added the guard.

### Finding Description
`state.GetDBImpl` returns `nil` whenever the `vm.StateDB` passed to the EVM is not a `*DBImpl` (or a `HookedStateDB` wrapping one) [2](#0-1) . Callers elsewhere in the codebase treat this as expected and explicitly guard against it, e.g. `EmitEVMLog` returns an error instead of dereferencing a nil pointer [3](#0-2) , and the current (non-legacy) `HandlePrecompileError` was fixed to guard with `if sdb := state.GetDBImpl(evm.StateDB); sdb != nil` [4](#0-3) .

However, the legacy precompile implementations for `v5.7.5`, `v6.0.5`, `v6.0.6`, and `v6.1.0` still call `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)` without checking for `nil`: [5](#0-4) 
This exact unchecked-return pattern is analogous to CVE-2022-3107's root cause: a value produced by a lookup/allocation function is dereferenced without checking whether it is `nil`/failed, causing a nil-pointer dereference. Here, `HandlePrecompileError` is invoked from the `defer` in `Run`/`RunAndCalculateGas` any time the precompile executor returns a non-nil `err` [6](#0-5) . If `evm.StateDB` is not backed by `*DBImpl` (e.g. any EVM execution path — RPC `eth_call`/`eth_estimateGas` simulation, tracing endpoints, or other StateDB wrapper implementations used off the main deliver-tx path) at a block height where one of these legacy precompile versions is active, and any precompile method returns an error, `GetDBImpl` returns `nil` and the subsequent `.SetPrecompileError(err)` call panics with a nil-pointer dereference.

### Impact Explanation
A nil-pointer dereference inside EVM precompile-error handling causes the calling goroutine to panic. Depending on where the call originates (public JSON-RPC `eth_call`/`eth_estimateGas`/tracing handlers, which construct their own StateDB implementations rather than the deliver-tx `DBImpl`), this can crash or hang the RPC-serving goroutine of a default-configuration public RPC node, since the request is user/attacker triggered by merely calling a precompile method that errors while historical/legacy precompile logic is active. Repeated triggering by any unprivileged RPC client could produce a denial-of-service against public RPC nodes.

### Likelihood Explanation
Likelihood depends on whether any current or historically-replayed EVM execution path can present a non-`DBImpl` StateDB together with one of the legacy-version precompile builds (`v5.7.5`/`v6.0.5`/`v6.0.6`/`v6.1.0`) being the currently selected version for the executing height, and whether any RPC-facing simulation/trace call path routes through this same `VersionedPrecompiles` selection with a different `vm.StateDB` implementation. This dependency (which RPC call paths use a non-`DBImpl` StateDB, and whether legacy-version precompiles are still reachable at the chain's current live height vs. only during historical replay) could not be fully confirmed from the available code excerpts, so the exact reachability of the nil StateDB condition on the hot/live path remains uncertain.

### Recommendation
Apply the same nil-check fix used in the newer common precompile package (`precompiles/common/precompiles.go`) to the affected legacy `HandlePrecompileError` implementations in `precompiles/common/legacy/v575/precompiles.go`, `v605/precompiles.go`, `v606/precompiles.go`, and `v610/precompiles.go`:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
    if err != nil {
        if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
            sdb.SetPrecompileError(err)
        }
        metrics.IncrementErrorMetrics(operation, err)
    }
}
```

### Proof of Concept
1. Ensure the chain's currently applied precompile version (as selected via `GetVersioned`'s `latestUpgrade`/height mapping) resolves to one of `v5.7.5`, `v6.0.5`, `v6.0.6`, or `v6.1.0` for the target block (this occurs during historical block replay/state-sync, or on any chain that has not yet upgraded past these versions).
2. From any account, submit/simulate an EVM call to a precompile address handled by that legacy version, with input crafted so that `p.executor.Execute` (or the equivalent dynamic-gas executor) returns a non-nil `err` — the exact executor errors that are reachable are precompile-specific and not enumerated in the reviewed excerpts.
3. Trigger this call through a code path where `evm.StateDB` is not a `*DBImpl`/`HookedStateDB` (e.g., an RPC simulation/trace path using a different StateDB implementation) — the concrete such path could not be located/confirmed in the reviewed code and would need to be verified directly in the RPC server implementation.
4. Observe the panic in `HandlePrecompileError` when `state.GetDBImpl(evm.StateDB)` returns `nil` and `.SetPrecompileError(err)` is called on it [5](#0-4) .
