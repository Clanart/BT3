### Title
Hardcoded zero minimum-output in `ArbWomUp3` WOM→mWOM buyback swap enables MEV/sandwich theft of user funds - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3._deposit` (mode 2, reached from the unprivileged, user-facing `incentiveDeposit` function) calls `SmartWomConvert.convert` with the minimum-received parameter hardcoded to `0`, so the WOM→mWOM swap it triggers on the Wombat AMM accepts any output amount, including a heavily sandwiched/manipulated one.

### Finding Description
`ArbWomUp3.incentiveDeposit` is a public entry point (only gated by `_checkAmount`, `whenNotPaused`, `nonReentrant` — no privileged role) that any wallet can call to convert deposited WOM into mWOM/vlMGP rewards: [1](#0-0) 

For `_mode == 2`, half of the deposited WOM is routed through `SmartWomConvert.convert` with the min-received argument hardcoded to `0`: [2](#0-1) 

That call flows into `SmartWomConvert._convertFor`, which performs an actual AMM swap (`IWombatRouter(router).swapExactTokensForTokens`) using a hardcoded `0` as the router's own min-output parameter, and only checks the *aggregate* `_minRec` afterwards: [3](#0-2) 

Since `_minRec` is `0` (passed all the way from `ArbWomUp3`), the post-swap check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` can never fail — it is mathematically satisfied for any `amountRec >= 0`, exactly mirroring the referenced Orca `decreaseLiquidity` bug pattern where `token_min_a = token_min_b = 0` nullifies the slippage check. The Wombat router call itself also passes literal `0` as its minimum output, so the swap executes unconditionally regardless of price impact.

### Impact Explanation
Because the swap has no floor on output, an attacker (MEV searcher / validator, both viable on BSC and Arbitrum where these contracts are deployed) can sandwich the `IWombatRouter.swapExactTokensForTokens` call inside `_convertFor`, manipulating the WOM/mWOM pool price immediately before the victim's swap and reverting it immediately after. The victim's `toSwap` (half of their deposited WOM) is then converted into mWOM at an attacker-controlled unfavorable rate, and the extracted value goes to the attacker. This is a direct, deterministic loss of user funds triggered by an ordinary transaction, satisfying the "direct theft of user funds" impact bar.

### Likelihood Explanation
Likelihood is high: `incentiveDeposit(..., _mode == 2)` is a normal, unprivileged user action (part of the WOM-up incentive/airdrop-locking campaign), the swap pool (`womMWomPool`) is a standard, low-liquidity-relative AMM pool where price manipulation via flash/atomic sandwiching is straightforward, and MEV infrastructure (Jito-style on BSC/Arbitrum equivalents) is readily available, as also noted in the referenced report.

### Recommendation
Add a user-supplied minimum-received parameter for the WOM→mWOM buyback leg and thread it through instead of hardcoding `0`:
- In `ArbWomUp3.incentiveDeposit`/`_deposit`, accept a `_minSwapRec` argument (or compute an on-chain quote-based minimum with slippage tolerance) and pass it to `IConverter(smartWomConvert).convert(toSwap, _convertRatio, _minSwapRec, 0)` instead of `0`.
- In `SmartWomConvert._convertFor`, forward a non-zero, caller-derived minimum directly into `IWombatRouter.swapExactTokensForTokens` (currently hardcoded `0` at line 195) rather than relying solely on the aggregate post-swap check, which is bypassed entirely when `_minRec == 0`.

### Proof of Concept
1. Attacker monitors the mempool for calls to `ArbWomUp3.incentiveDeposit(_amount, _convertRatio, _bullMode, 2)`.
2. Victim's transaction internally calls `_deposit(..., 2)`, which computes `toSwap = _amount - _amount/2` and calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — `wombat/ArbWomUp3.sol:199`.
3. `SmartWomConvert._convertFor` executes `IWombatRouter(router).swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp)` — `wombat/SmartWomConvert.sol:194-196` — with `0` as the router-level minimum output.
4. Attacker front-runs with a large WOM→mWOM (or reverse) swap to skew the pool price, lets the victim's swap execute at the worse price, then back-runs to restore the price and capture the difference.
5. The post-swap check `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();` (`wombat/SmartWomConvert.sol:204-205`) never reverts because `_minRec == 0`, so the victim's transaction succeeds despite receiving a manipulated, unfavorable `amountRec`.
