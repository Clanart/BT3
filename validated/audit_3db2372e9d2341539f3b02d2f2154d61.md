Based on my research, the strongest analog I found relates to how GitHub Desktop's submodule-update logic can re-enable Git's `file://` protocol for submodules — the very same class of primitive that Git upstream restricted (CVE-2022-39253) to stop malicious repositories from reading files off the host filesystem via submodule "clones."

### Title
Submodule checkout can re-enable `protocol.file.allow=always`, reopening the local-file-read primitive Git's default protections were designed to block - ([File: app/src/lib/git/submodule.ts])

### Summary
Git's default `protocol.file.allow=user` (added upstream specifically as the fix for CVE-2022-39253, where a malicious repo's `.gitmodules` could point a submodule URL at `file://` and have Git silently "clone" arbitrary local paths into the working tree) is the same kind of protective invariant referenced by the source report: a fix was applied upstream, but GitHub Desktop exposes a caller-controlled flag that flips the restriction back off.

### Finding Description
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean and, when `true`, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, explicitly overriding Git's own safe default: [1](#0-0) 

This is called from `checkoutCommit`, which itself takes an `allowFileProtocol: boolean = false` parameter and forwards it unchanged to the submodule update step after checking out a commit: [2](#0-1) 

The parallel to the report is structural: just as `setStakingContract` let the owner silently redirect a "fixed" privilege (minting) back to an arbitrary trusted address, `allowFileProtocol=true` lets a caller silently redirect Git's submodule fetch back to the unrestricted `file://` transport that upstream Git deliberately locked down. The corrupted value is Git's `protocol.file.allow` config for the duration of the submodule update — flipped from the safe default (`user`, which blocks unprompted `file://` submodule fetches) to `always`.

### Impact Explanation
If a checkout path that sets `allowFileProtocol=true` is reachable while checking out a commit that originates from an untrusted/attacker-controlled repository (a fork, a PR branch, or any cloned/fetched ref containing a `.gitmodules` entry with a `file://` URL pointing at a sensitive local path such as `~/.ssh` or `~/.aws`), Git would copy the contents of that local path into the submodule directory inside the working tree. Because that directory is part of the repository the user is working in, the exfiltrated files could subsequently be viewed, committed, and pushed to a remote the attacker controls — turning a local file-read primitive into full exfiltration, which matches the "credential/token exfiltration" and "silent corruption of what the user commits" categories in the accepted impact list.

### Likelihood Explanation
I was not able to fully trace every call site that sets `allowFileProtocol=true` for `checkoutCommit`/`updateSubmodulesAfterOperation` within the available search results — `grep_search` only surfaced the definitions in `app/src/lib/git/checkout.ts` and `app/src/lib/git/submodule.ts`, not the call-site logic in the UI/store layers that decides when `true` is passed. This is a real gap: without confirming that some caller sets `allowFileProtocol=true` in a flow that can be reached with an attacker-supplied commit (e.g. checking out a fork/PR), I cannot confirm this is actually exploitable end-to-end versus being restricted to trusted/first-party flows (e.g. local-only test fixtures also use `protocol.file.allow=always` deliberately, as seen in test helpers). This is the main uncertainty in this analog.

### Recommendation
Confirm (via a Devin session with full repo access) every call site that passes `allowFileProtocol=true` into `checkoutCommit`/`updateSubmodulesAfterOperation`, and verify whether any of them can be triggered on a commit/branch that originates from an untrusted remote (fork checkout, PR checkout, etc.) rather than only from trusted, first-party flows. If such a path exists, remove the ability to override `protocol.file.allow` for untrusted refs, or scope the override to only locally-created submodules.
