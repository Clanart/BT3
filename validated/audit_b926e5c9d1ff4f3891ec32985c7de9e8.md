## Analysis

The GMX report's core broken invariant is: **a balance is debited/finalized before the corresponding payout is confirmed, and no recovery mechanism exists if that payout never lands** — so the value is silently and permanently lost. The closest local analog is `pallet-ismp-relayer`'s fee-withdrawal flow. [1](#0-0) 

`Pallet::withdraw` dispatches an ISMP `PostRequest` carrying the `WithdrawalParams`/`WithdrawRelayerFees` payload to the destination chain's `HostManager`/`HYPERBRIDGE_MODULE_ID`, with **`timeout: 0`** — an ISMP request with `timeout: 0` never expires and can never enter the ISMP timeout-handling path. Immediately after dispatch (not after any destination confirmation), the pallet zeroes the relayer's accounted balance: `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero())`. [2](#0-1) [3](#0-2) 

### Title
Relayer fee balance is zeroed before destination payout confirmation, with no timeout/retry path to restore it - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`Pallet::withdraw` accepts a relayer's signed withdrawal request, computes `available_amount` from `Fees::<T>`, dispatches a non-expiring (`timeout: 0`) ISMP `PostRequest` to the destination chain's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) to disburse the funds, and unconditionally zeroes `Fees` in the same call — before any proof that the destination actually paid out.

### Finding Description
The withdrawal flow treats dispatch success as if it were payout success. The accounting (`Fees::<T>::insert(..., U256::zero())`) happens synchronously and unconditionally right after `dispatch_request` returns `Ok`, with no dependency on the destination chain's `onAccept`/`withdraw` actually completing. Because the dispatched `DispatchPost` sets `timeout: 0`, the request is exempt from ISMP's timeout machinery entirely — there is no `on_timeout` callback that could ever re-credit `Fees` for this module. If the destination-side execution of the withdrawal fails or is indefinitely delayed (e.g., the `RELAYER_FEE_ACCOUNT`/host contract lacks the fee-token balance to cover `WithdrawParams`, the target `HostManager` reverts, or the message is simply never relayed because it has no fee/incentive attached to it — `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }`), the relayer's on-chain accounted balance is already gone and there is no code path in this pallet that restores it.

This differs from other ISMP flows in the same codebase that correctly guard funds until confirmed: `EvmHost.dispatchTimeOut` re-credits the fee to the sender only after a successful callback, and re-arms the commitment for retry on failure. The relayer-withdrawal path has no equivalent safety net because the underlying request cannot time out.

### Impact Explanation
A relayer that withdraws accrued fees to a destination chain that fails to actually process the payout (invalid/misconfigured `HostParams::<T>::get`, insufficient funds in the destination `RELAYER_FEE_ACCOUNT`, or a reverting `HostManager.onAccept`) permanently loses the `available_amount` that was zeroed out of `Fees`. This is a straightforward, unprivileged loss-of-funds condition matching the bounty's "stealing or loss of funds" / "false state acceptance without recovery" categories, and requires no malicious relayer, prover, or admin — only ordinary operational failure on the destination side of a withdrawal that any relayer can trigger themselves.

### Likelihood Explanation
Any legitimate relayer calling `withdraw_fees` triggers this path. Because the outgoing message has `fee: Default::default()` (zero relayer incentive) and `timeout: 0`, delivery is entirely dependent on altruistic/self-relaying and is not economically guaranteed — the same "no-fee system message" gap independently documented in `docs/outbound-request-incentivization.md`. Destination-side balance shortfalls in the fee-token reserve (`RELAYER_FEE_ACCOUNT` / EvmHost fee-token holdings) are plausible operational states, especially under heavy withdrawal activity, making this more than a purely theoretical edge case.

### Recommendation
Do not zero `Fees::<T>` until the destination confirms the payout (e.g., require a `WithdrawFundsResult`/receipt proof callback, mirroring the pattern used for `accumulate_fees`/delivery proofs elsewhere in this pallet) rather than crediting on dispatch. Alternatively, set a real `timeout` on the dispatched `DispatchPost` and implement an `on_timeout` handler for `MODULE_ID` that re-credits `Fees` on expiry, giving the relayer a guaranteed recovery path symmetric to `EvmHost.dispatchTimeOut`'s fee refund-on-failure behavior.

### Proof of Concept
1. Relayer accrues fee balance via `accumulate_fees`, leaving `Fees::<T>::get(dest_chain, relayer) = X ≥ min_withdrawal_amount`.
2. Relayer calls `withdraw_fees` targeting an EVM `dest_chain` whose `HostParams::<T>` `host_manager`/fee-token reserve cannot actually cover `X` (e.g., stale or misconfigured params, or a destination host manager that later reverts on `onAccept`/`withdraw`).
3. `Pallet::withdraw` dispatches the ISMP `PostRequest` with `timeout: 0` and immediately sets `Fees::<T>::insert(dest_chain, relayer, U256::zero())`.
4. Destination-side execution of the withdrawal fails or is never delivered (no fee incentive attached, `timeout: 0` so ISMP can never expire/re-open the request).
5. The relayer's `Fees` balance is permanently `0` with no on-chain path to reclaim `X` — funds are lost. (Full confirmation that the destination `HostManager.withdraw` cannot fail-safe/revert-and-retry the ISMP delivery itself was not verifiable from the indexed handler code; this should be checked against the live `IsmpHandler`/`HandlerV2` incoming-message processing to rule out an implicit retry mechanism outside this pallet.)
