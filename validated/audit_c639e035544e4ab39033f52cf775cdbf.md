### Title
Payout attribution (operator xonly-pk) is not covered by the user's withdrawal signature, allowing misattribution of the Bitcoin reimbursement credit - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The user's authorization for a Clementine withdrawal is a single Schnorr signature over the `payout_tx`'s sole spent input, using `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`. This sighash type commits only to input 0 and the output at the *same index* (output 0, the user payout). It does **not** commit to the transaction's other outputs, in particular the OP_RETURN output that encodes which operator's x-only pubkey "fronted" the withdrawal. Since that OP_RETURN value is the sole piece of on-chain data the verifier network later uses to decide which operator gets Bitcoin-side reimbursement, anyone who can construct/fund a transaction spending the pre-committed withdrawal UTXO with the user's signature can freely choose (or omit) the operator credited for the payout, independent of who actually supplied the BTC.

### Finding Description
`create_payout_txhandler` builds the payout transaction with three outputs: the user payout, an anchor, and an OP_RETURN carrying the fronting operator's x-only pubkey: [1](#0-0) 

The witness placed on input 0 is the caller-supplied `user_sig`, and `operator.rs::withdraw` explicitly requires `SinglePlusAnyoneCanPay`: [2](#0-1) 

`SIGHASH_SINGLE|ANYONECANPAY` signs only the spent input and the output with the matching index (output 0). It leaves the anchor (output 1) and, critically, the OP_RETURN operator-attribution output (output 2) completely unauthenticated. `fund_raw_transaction` is then used to add whatever inputs are needed to actually pay the withdrawal amount: [3](#0-2) 

Later, when a payout transaction confirms, the verifier network scans the block, parses the OP_RETURN to decide who "paid", and persists this attribution as the payer of record: [4](#0-3) 

That persisted attribution is exactly what drives which operator's automation later claims the Bitcoin-side reimbursement: [5](#0-4) [6](#0-5) 

Because the OP_RETURN bytes are unsigned by the user, and the additional funding inputs can come from any wallet (not cryptographically bound to any operator), the party that actually supplies the BTC to pay the user (the "payer") and the party credited with the reimbursement (the operator whose pubkey appears in OP_RETURN) are two independently-controllable values. The protocol's implicit invariant — `payer == credited operator` — is not enforced by any signature or consensus rule; it is enforced only by convention (that whoever builds the tx honestly writes their own pubkey).

### Impact Explanation
This breaks the binding "operator credited versus the party that paid" (a misattributed reimbursement), one of the explicitly accepted impact categories. Whoever races to construct and broadcast a valid payout for a pending Citrea withdrawal (funding it from any source) can name an arbitrary operator's public x-only key in the OP_RETURN. The verifier state machine and `is_kickoff_malicious` check will accept this attribution as genuine (it only checks that the OP_RETURN pubkey matches the kickoff operator and that the committed blockhash matches — both trivially satisfied since the data was chosen this way), causing that named operator's automation to proceed through Kickoff/Reimburse and claim the bridge amount from its own round-tx collateral for a payout it never actually funded. This is a concrete break of custody attribution inside the protocol's own bookkeeping, independent of who financially benefits in a given instance.

### Likelihood Explanation
Any unprivileged party who can observe a pending withdrawal's parameters (withdrawal index, `in_outpoint`, user signature, output script/amount) — obtainable once the operator's own `withdraw` broadcast enters the mempool, or via any leak of the off-chain-shared user signature — can independently rebuild and fund the payout transaction with a different OP_RETURN and replace/race the legitimate broadcast (the input/output committed by the signature is identical, so the transaction remains valid; only the uncommitted outputs and extra funding inputs differ). No verifier, operator, or aggregator role is required to construct this transaction; it only requires a Bitcoin wallet.

### Recommendation
Bind the OP_RETURN operator-attribution output to the same signature that authorizes the withdrawal input, e.g. by using `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY`) for the user's payout authorization so all outputs, including the operator pubkey commitment, are covered, or by having the operator co-sign/commit to the OP_RETURN value through a separate mechanism validated before the payout is treated as authoritative for reimbursement bookkeeping.

### Proof of Concept
1. Alice initiates a Citrea withdrawal; the withdrawal UTXO, required output script/amount, and Alice's `SinglePlusAnyoneCanPay` signature become known once Operator A's `payout_tx` appears in the Bitcoin mempool (input 0 + output 0 are fixed by the signature, per `operator.rs::withdraw` lines 577–637).
2. Attacker Mallory builds an alternative transaction spending the same input 0 with Alice's untouched signature, keeping output 0 identical (to remain sighash-valid), but sets the OP_RETURN output (`create_payout_txhandler`, `operator_reimburse.rs` lines 407–436) to Operator B's x-only pubkey instead of Operator A's, and funds/pays any extra required amount from Mallory's own wallet.
3. Mallory broadcasts with a higher fee (RBF) or races Operator A's broadcast; the network confirms Mallory's version.
4. `update_finalized_payouts` (`verifier.rs` lines 2298–2343) parses the OP_RETURN and records `payout_payer_operator_xonly_pk = Operator B`, even though Operator B never built, signed, or funded the transaction.
5. Operator B's `PayoutCheckerTask` (`payout_checker.rs` lines 41–47) and `validate_payer_is_operator` (`operator.rs` lines 1703–1729) accept this record as legitimate and proceed to claim Bitcoin-side reimbursement for a withdrawal Operator B never fronted, while the actual payer (Mallory) receives nothing back from the bridge.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
