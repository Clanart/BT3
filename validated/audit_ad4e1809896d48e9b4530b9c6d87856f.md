### Title
Unauthenticated `InitializeBuffer` instruction allows front-running of buffer authority, permanently bricking the buffer account - ([File: programs/bpf_loader/src/lib.rs])

### Summary
### Finding Description
The `InitializeBuffer` instruction handler in the upgradeable BPF loader sets the buffer's authority based solely on the pubkey supplied in account index 1, without requiring that account to be a signer, and without requiring any signature from the buffer account owner/creator: [1](#0-0) 

The only guard is that the buffer must still be in the `Uninitialized` state (`AccountAlreadyInitialized` otherwise). This is confirmed by the unit test/bench harness, which builds the `InitializeBuffer` instruction with both the buffer account and the authority account marked `is_signer: false`: [2](#0-1) [3](#0-2) 

Creating a buffer account is a two-step process: (1) `system_instruction::create_account` assigns ownership of the (still-`Uninitialized`) account to `bpf_loader_upgradeable`, and (2) `InitializeBuffer` sets the `authority_address` field, after which `Write`/`DeployWithMaxDataLen` require that authority to sign. The CLI helper `loader_v3_instruction::create_buffer` bundles both instructions into a single message so they are normally sent atomically: [4](#0-3) 

However, nothing in the runtime enforces that these two steps happen atomically in a single transaction — a caller (or wallet, or lower-level SDK usage) is free to send `create_account` and `InitializeBuffer` as separate transactions. Once step (1) lands, the buffer account is public, owned by the loader, and in `Uninitialized` state, and since `InitializeBuffer` has no ownership/signer requirement, any unrelated party can race a transaction that calls `InitializeBuffer` on that same buffer pubkey before the legitimate deployer's follow-up transaction lands.

### Impact Explanation
This is the same bug class as the Velodrome `Bribe.setGauge`/`Gauge` constructor griefing: a one-time "set owner/authority" call that is not access-controlled and not guaranteed to run atomically with account creation. An attacker front-running `InitializeBuffer` can:
- Set `authority_address` to their own key, hijacking control of the buffer (subsequent `Write`/`Deploy`/`SetAuthority` calls by the legitimate deployer will fail `IncorrectAuthority`), or
- Set `authority_address` to `None`, making the buffer permanently `Immutable` (see the `Write` handler's `authority_address.is_none()` check returning `InstructionError::Immutable`): [5](#0-4) 

In either case the victim's buffer account is permanently unusable for its intended program deployment/upgrade and, since the account is already funded and owned by the loader, it cannot be re-initialized — the victim must create (and fund) an entirely new buffer account and retry, exactly mirroring the "Bribe redeployment" remediation described in the source report.

### Likelihood Explanation
Exploitation requires only that the `create_account` and `InitializeBuffer` instructions are not submitted as a single atomic transaction — a realistic condition whenever tooling other than the bundled `create_buffer` CLI helper is used, when a transaction is retried/resent after a partial failure, or when the buffer pubkey is predictable/observable before the second instruction lands. No special privilege is needed by the attacker; any unprivileged party watching for newly created, still-`Uninitialized` loader-owned buffer accounts can race the initializer.

### Recommendation
Require the account being initialized (or a designated authority) to sign the `InitializeBuffer` instruction, or fold buffer creation and initialization into a single atomic instruction (as is already done for `DeployWithMaxDataLen`, which creates and initializes the ProgramData account within one instruction). At minimum, document/enforce that `create_account` + `InitializeBuffer` must always be submitted as a single transaction, and consider adding a runtime check that the payer/creator of the buffer account is the same as the caller of `InitializeBuffer`.

### Proof of Concept
1. Victim submits transaction A: `system_instruction::create_account(payer, buffer_pubkey, ..., owner = bpf_loader_upgradeable)`, intending to follow up with transaction B: `InitializeBuffer` naming themselves as authority.
2. Attacker observes transaction A land (buffer account now exists, owned by loader, state `Uninitialized`) and, before transaction B confirms, submits `InitializeBuffer` for the same `buffer_pubkey` with `authority_address = None` (or attacker's own key) — this succeeds because neither the buffer nor the authority account is required to sign, per `programs/bpf_loader/src/lib.rs:158-172`.
3. Victim's transaction B now fails with `AccountAlreadyInitialized`.
4. Victim's buffer account is permanently immutable/hijacked; they must fund and create a brand-new buffer account to proceed.
