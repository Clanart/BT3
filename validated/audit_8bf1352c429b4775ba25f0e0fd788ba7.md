## Finding

### Title
Decimals mismatch between registration-time validation and live asset metadata enables overminting in `on_accept` — ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`register_token`/`update_token` validate `config.decimals >= local_decimals` **once**, using whatever the underlying asset's decimals metadata happens to be at that moment, and store the ERC20-side decimals permanently in `Precisions`. But the local decimals used at settlement time in `on_accept` (and `on_timeout`/`send`) are re-read live from `pallet-assets`' `fungibles::metadata::Inspect::decimals()` on every call. Because asset decimals metadata is owned and mutable by the asset's own `Owner`/admin (a normal, non-bridge-privileged account under `pallet-assets`), an entity with no privilege over the `hyper-fungible-token` pallet can silently break the invariant the bridge relies on, after registration, with no re-validation anywhere in the pallet.

### Finding Description
At registration: [1](#0-0) 

the check `config.decimals >= local_decimals` (i.e. `erc_decimals >= local_decimals`) is only performed against the decimals value read from `Assets::decimals()` at that instant, then `Precisions` is populated with the fixed ERC20-side decimals.

At settlement time, `on_accept` re-derives `decimals` dynamically and reads the fixed `Precisions` entry, then performs the conversion: [2](#0-1) 

The conversion function clamps the exponent with `saturating_sub`: [3](#0-2) 

If `local_decimals` (read live) ever exceeds the fixed `erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` becomes `0`, and `convert_to_balance` divides by `10^0 = 1` — i.e., it stops scaling entirely and treats the raw ERC20 `U256` value as if it were already denominated in local balance units.

Since the asset that is bridged is a `pallet-assets` asset, its decimals are controlled by that asset's `Owner`/admin via the standard `set_metadata`-style call, which is *not* gated by the hyper-fungible-token pallet's `CreateOrigin`. Both production runtimes configure `pallet-assets`' asset-creation origin as permissionless (`AsEnsureOriginWithArg<EnsureSigned<...>>` in gargantua) while an asset's owner retains authority over its own metadata: [4](#0-3) 

Meanwhile `hyper-fungible-token::CreateOrigin` (governing `register_token`/`update_token`, i.e., `Precisions`) is `EnsureRoot` in both production runtimes: [5](#0-4) [6](#0-5) 

So the bridge operator (Root) only validates the decimals relationship once, at the moment it registers an asset. The asset's actual owner — an unprivileged party with respect to the bridge — can independently raise the asset's decimals afterward through `pallet-assets`, permanently invalidating the `erc_decimals >= local_decimals` invariant without ever touching the hyper-fungible-token pallet or requiring any bridge-operator privilege.

### Impact Explanation
Once `local_decimals > erc_decimals`, every subsequent `on_accept` for that `(asset, chain)` pair mints/releases a local balance equal to the raw ERC20 integer amount with no down-scaling, instead of the intended fraction. A legitimate small cross-chain transfer (e.g. `1` unit at high ERC20 precision) is credited to the beneficiary as a disproportionately large local balance — inflating supply and directly stealing value from the pallet's escrow/mint accounting, matching the "stealing or loss of funds" / "false … acceptance" impact class.

### Likelihood Explanation
Requires only that: (1) the bridged asset be a `pallet-assets` token whose owner is a third party distinct from the bridge's `CreateOrigin`/Root (an ordinary, expected configuration for non-native/bridged tokens registered on request), and (2) that owner calls a standard, unprivileged `pallet-assets` metadata-update extrinsic on their own asset. No compromise of relayers, provers, or the bridge operator is needed — this is a normal user-level action against a pallet the bridge blindly trusts for live decimals.

### Recommendation
- Snapshot and store `local_decimals` in `Precisions` (or a companion storage item) at `register_token`/`update_token` time instead of re-reading live asset metadata at settlement time, or
- Re-validate `erc_decimals >= local_decimals` on every `send`/`on_accept`/`on_timeout` before conversion and reject/fail closed if the invariant no longer holds, rather than letting `saturating_sub` silently clamp to zero, and
- Consider freezing/locking metadata mutability (`decimals`) for assets once registered with the bridge, or requiring the bridge pallet to own asset metadata control for bridged assets.

### Proof of Concept
1. Bridge operator (Root) registers asset `A` (owned by user `U` via permissionless `pallet-assets` creation) with `local_decimals = 6` at registration time; `register_token` validates `erc_decimals(=18) >= 6` and stores `Precisions[A][EvmChain] = 18`.
2. `U`, using only their ordinary `pallet-assets` asset-owner privileges (unprivileged w.r.t. the bridge), calls the standard metadata-update extrinsic to change asset `A`'s decimals to `24` (`> 18`).
3. A legitimate small cross-chain message arrives at `on_accept` carrying `message.amount = 1 * 10^18` (representing "1 token" at the registered 18 decimals).
4. `on_accept` reads live `decimals = 24` from `Assets::decimals(A)`, `erc_decimals = 18` from `Precisions`; `convert_to_balance` computes `18.saturating_sub(24) = 0`, so it divides by `10^0 = 1`, yielding a local mint amount of `1 * 10^18` local units instead of the intended `1 * 10^(18-6) = 10^12` (or whatever the correctly scaled figure should have been) — an amount inflated by a factor of `10^6`, disproportionate to the true source-chain value. [7](#0-6)  confirms the clamp-to-zero division behavior; [1](#0-0)  confirms the one-time-only validation.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
