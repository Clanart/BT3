### Title
Commit-review and Stop-hook dedup key collapses distinct vulnerabilities to `(filePath, category)`, allowing a new dangerous finding to be silently suppressed - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The commit-review (`handle_commit_review_posttooluse`) and Stop-hook (`handle_stop_hook`) finding-dedup logic records previously-flagged vulnerabilities keyed only on `(filePath, category)`, deliberately dropping `vulnerableCode` from the dedup key. Because diff content is fully attacker/model-controlled through normal edits and commits, a first (even minor) finding of a given category in a file permanently "uses up" that key for the rest of the session/TTL window, so a subsequent, unrelated, and more dangerous vulnerability of the same category in the same file is treated as "already known" and never surfaces a warning or triggers the exit-code-2 rewake.

### Finding Description
Both dedup call sites build the "seen" set from `(filePath, category)` only, explicitly to avoid re-flagging noise from diff-context drift in `vulnerableCode`: [1](#0-0) 

The same pattern is used by the Stop hook's `_record_fire`: [2](#0-1) 

The state (`previous_findings`) is shared across the Stop hook and commit-review, gated on `session_id` and a TTL (`PREVIOUS_FINDINGS_TTL_SEC`), and consumed via `_dedup_against_state(..., prompted=_finding_keys(previous_findings))` before a new set of findings is emitted: [3](#0-2) 

Because diff content across edits/commits/amends/pushes is entirely attacker/model-controlled, an attacker can:
1. Cause an initial commit/edit that introduces (or the LLM flags) a vulnerability of category `C` in file `F` — this gets recorded once, seeding `(F, C)` into `previous_findings`.
2. In a later commit/amend/push within the same session (and TTL window, default determined by `PREVIOUS_FINDINGS_TTL_SEC`), introduce a distinct, more severe vulnerability of the *same category* `C` in the *same file* `F` (different `vulnerableCode`, different line, different root cause).
3. Because the dedup key ignores `vulnerableCode`, `_dedup_against_state`/`_record_fire`/`_record_findings` treats step 2's finding as already-known and it is dropped from `new_vulns`/`vulns`, so `sys.exit(2)` (the rewake/block path) and the PROVENANCE_BANNER guidance never fire for it.

This directly matches the stated exploit idea — reuse of a prior warning key so a new dangerous action emits no warning — and defeats the intended invariant that every dangerous diff must remain reviewable/blockable across retries, amends, and pushes, since the SHA-level dedup (`.git/sg-reviewed-shas`, `_load_reviewed_shas`) only prevents re-reviewing the *same* commit, not the described category-collision within different commits.

### Impact Explanation
This is a Logic-level service disruption via bypassing a required guard: an attacker who can influence diff content (e.g., via a malicious PR, prompt injection, or normal iterative editing) can suppress the review/block mechanism for a genuinely new and dangerous change, as long as it shares `(filePath, category)` with an earlier, already-acknowledged finding in the same session. The security-guidance plugin's core promise — that dangerous edits/commands stay reviewable and blockable across retries, amends and pushes — is broken for this class of collision, since the guard silently no-ops instead of alerting.

### Likelihood Explanation
Feasible and repeatable: no privileged access is required, only the ability to drive two commits/edits in the same session where the second reuses the same file path and vulnerability category. This is very plausible in real usage (e.g., repeated fixes/refactors touching the same file, or an attacker deliberately priming the key with a low-severity issue before landing a higher-severity one). The condition is bounded only by `session_id` and `PREVIOUS_FINDINGS_TTL_SEC`, both of which are easily kept within range during ordinary iterative work.

### Recommendation
Tighten the dedup key so it cannot collapse distinct vulnerabilities: include a normalized/stable fingerprint of the vulnerable code (e.g., a hash of the affected line range or AST-based signature) alongside `filePath` and `category`, or additionally key on `severity`/line-number bucket so that a new, distinct instance of the same category in the same file is not treated as already delivered. At minimum, re-flag when severity of the new finding is higher than any previously recorded finding under the same coarse key.

### Proof of Concept
Integration test plan for `handle_commit_review_posttooluse` (and analogously `handle_stop_hook`):
1. Seed session state via `with_locked_state(session_id, ...)` with `previous_findings = [{"filePath": "app.py", "category": "SQL Injection", "vulnerableCode": "cursor.execute(q1)"}]` and a fresh `previous_findings_ts`.
2. Mock `analyze_code_security`/agentic review to return a new finding: `{"filePath": "app.py", "category": "SQL Injection", "vulnerableCode": "cursor.execute(q2_with_new_unsanitized_input)", "severity": "critical"}` for a commit touching `app.py`.
3. Drive `handle_commit_review_posttooluse` with a synthetic `input_data` simulating a successful `git commit` on `app.py`.
4. Assert that `sys.exit(2)` is NOT called and no guidance is written to stderr — demonstrating the new critical finding is suppressed — even though `vulnerableCode` differs entirely from the previously recorded one.
5. Expected (post-fix) assertion: the handler should exit with code 2 and emit guidance because the new finding, despite sharing `(filePath, category)`, represents a distinct/higher-severity vulnerability.
