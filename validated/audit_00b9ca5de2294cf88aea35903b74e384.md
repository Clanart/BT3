## Analysis

`vlMGPBaseRewarder` uses an instantaneous "reward-per-token" accounting model rather than a time-weighted rate model. `_queueNewRewardsWithoutTransfer` bumps `rewardInfo.rewardPerTokenStored` by `(_amountReward * 1e18) / totalStaked()` in a single step at the moment the forfeiture is queued [1](#0-0) , where `totalStaked()` reads the live `vlMGP.totalSupply()` [2](#0-1) . A user's `earned()`/`userRewards` update multiplies the **entire unclaimed delta** of `rewardPerTokenStored` by the user's **current** `balanceOf(_account)`, not by a time-integrated stake [3](#0-2) [4](#0-3) .

`VLMGP.lock()` → `_lock()` calls `IMasterMagpie(masterMagpie).depositVlMGPFor(_amount, _for)` before increasing `totalAmount` [5](#0-4) . This is the standard MasterChef-derivative pattern: the deposit call checkpoints the account's existing rewards at the *old* balance/`rewardPerToken`, then the new balance takes effect for all *future* `rewardPerTokenStored` increases — including one that occurs one transaction later.

Forfeiture is queued from `_sendReward`/`queueMGP`, both of which invoke `_queueNewRewardsWithoutTransfer` and immediately bump `rewardPerTokenStored` using the live `totalStaked()` [6](#0-5) [7](#0-6) . Because there is no per-second reward rate or duration weighting (unlike a Synthetix-style `rewardRate * timeElapsed` design), any account whose balance is large at the moment of this single-block bump captures the full pro-rata share of that forfeiture, regardless of how long — even zero blocks of economic time — it held that balance.

### Title
Instant reward-per-token model allows front-running of forfeiture distributions via `lock()` to steal disproportionate unclaimed yield - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
`vlMGPBaseRewarder._queueNewRewardsWithoutTransfer` (invoked from `_sendReward`/`queueMGP` on forfeiture) instantly distributes forfeited MGP into `rewardPerTokenStored` based on the live `totalStaked()` snapshot, and per-account rewards are computed using the account's current balance rather than a time-weighted stake. An attacker can front-run a pending forfeiting `getReward`/`queueMGP` transaction by calling `VLMGP.lock(largeAmount)`, then immediately claim a share of the resulting forfeiture proportional to their inflated balance despite holding it for effectively zero time.

### Finding Description
`_queueNewRewardsWithoutTransfer` credits `rewardPerTokenStored += (_amountReward * 1e18) / totalStaked()` at the exact block it runs [1](#0-0) . `totalStaked()` returns `vlMGP.totalSupply()` live at call time [8](#0-7) . Any account's owed rewards are computed as `balanceOf(account) * (rewardPerToken - userRewardPerTokenPaid[account]) / 1e18` [4](#0-3) , applied via the `updateRewards`/`updateReward` modifiers whenever `getReward`/`getRewards` is called [9](#0-8) [10](#0-9) .

`VLMGP.lock()` calls `MasterMagpie.depositVlMGPFor` before incrementing `totalAmount` [11](#0-10) [5](#0-4) , which (per the standard checkpoint pattern used throughout this rewarder) settles the account's existing reward accrual at its old balance/index and then applies the new, larger balance going forward. Because the reward index bump in `_queueNewRewardsWithoutTransfer` is not time-weighted, any balance present at the moment of that single bump captures its full proportional share.

Exploit flow:
1. Attacker observes a pending `queueMGP` or `getReward` transaction that will trigger `_calExpireForfeit` > 0 and thus call `_queueNewRewardsWithoutTransfer` [7](#0-6) .
2. Attacker front-runs with `VLMGP.lock(largeAmount)`, inflating their `balanceOf()` in the rewarder (which reads `MasterMagpie.stakingInfo`) [12](#0-11) .
3. Victim's transaction executes, `_queueNewRewardsWithoutTransfer` bumps `rewardPerTokenStored` using `totalStaked()` that already includes the attacker's newly locked amount.
4. Attacker calls `getReward`, and `_earned` multiplies the full forfeiture-driven `rewardPerTokenStored` delta by their inflated balance, capturing rewards disproportionate to any actual staking duration.

No existing modifier (`nonReentrant`, `whenNotPaused`, `onlyManager`, `onlyMasterMagpie`) prevents this because the attack does not depend on privileged access, reentrancy, or pausing — it exploits the lack of time-weighting in reward accrual, a design/logic issue rather than an access-control gap.

### Impact Explanation
This results in theft of unclaimed yield from other honest lockers: forfeited MGP that should be distributed proportionally to genuine holding duration is instead skimmed by an attacker who briefly inflates their balance immediately before the distribution event. This falls under "theft of unclaimed yield" impact.

### Likelihood Explanation
Feasibility depends on:
- Attacker must monitor the mempool and successfully front-run (achievable via higher gas/priority fee, standard MEV technique).
- Attacker needs sufficient MGP capital to lock a large amount for one block/transaction, then can immediately start unlocking again afterward.
- The forfeiture-generating transactions (`getReward` with expired-but-still-penalized rewards, or `queueMGP`) are user-triggered and visible in the mempool, so this is repeatable for every such event.
This is a moderate-capital, technically straightforward, and repeatable attack (bounded by the size of forfeiture events, which may be small per instance, limiting per-attack profit but allowing continuous skimming).

### Recommendation
Replace the instantaneous "credit full amount to current total-staked" distribution model with a time-weighted accrual (e.g., `rewardRate` streamed over a duration as in Synthetix-style `StakingRewards`), or require a minimum staking duration/checkpoint delay before newly deposited balance becomes eligible for a given pending reward bump. Alternatively, snapshot the eligible balance set before applying `_queueNewRewardsWithoutTransfer` so that balance changes in the same block/transaction cannot participate in that specific distribution.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder`; seed two lockers (`victim`, `bystander`) with locked MGP and let some time pass so both have non-trivial `userRewards` outstanding.
2. Fund the reward token and configure a scenario where `bystander` calls `getReward` and, due to `_calExpireForfeit`, a nonzero `forfeitAmount` will be queued.
3. Simulate front-running: in the same block (or immediately prior tx), have `attacker` call `VLMGP.lock(largeAmount)`.
4. Execute `bystander`'s `getReward` call, triggering `_queueNewRewardsWithoutTransfer` and bumping `rewardPerTokenStored`.
5. Call `attacker`'s `getReward` and assert `earned(attacker, rewardToken)` (or the actually paid amount) is disproportionately large relative to `attacker`'s zero prior staking duration, i.e., `attacker`'s share of the forfeiture ≈ `attackerBalance / totalStaked()` even though attacker staked for 0 blocks before the forfeiture — compare against a control run without the front-run lock to show the delta captured is entirely attributable to the front-run timing.

        return true;

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }
