### Title
Online user sessions are keyed only by `shopify_user_id`, collapsing distinct shops into a single storage row and enabling cross-shop session/access-token disclosure - ([File: lib/shopify_app/session/session_repository.rb])

### Summary
This is a structural analog of the reported bug class: a storage map that should be scoped by a *compound* key (channel + sequence in the bridge report; shop + user in `shopify_app`) is instead keyed by only one of the two dimensions. In `shopify_app`, online user sessions are persisted and retrieved using `shopify_user_id` alone, with the shop domain dropped entirely from the lookup key, exactly mirroring the report's root cause of "two entities that should be independent collapse into the same bucket."

### Finding Description
`ShopifyApp::SessionRepository.load_session` derives the lookup key from the session id and, for non-offline (online/user) sessions, **discards the shop-domain component and looks up strictly by the trailing user-id segment**: [1](#0-0) 

`retrieve_user_session_by_shopify_user_id` simply forwards to the configured user storage's `retrieve_by_shopify_user_id`: [2](#0-1) 

The default `UserSessionStorage` concern implements storage and retrieval with `shopify_user_id` as the *sole* key — `store` performs `find_or_initialize_by(shopify_user_id: user.id)` and unconditionally overwrites `shopify_domain` and `shopify_token` on that single row, and `retrieve_by_shopify_user_id`/`destroy_by_shopify_user_id` likewise only filter on `shopify_user_id`: [3](#0-2) 

`shopify_user_id` is a Shopify account/staff identifier, not a per-shop identifier — the same numeric id legitimately recurs across every shop where that person is a collaborator/staff member (e.g., Shopify Plus organizations, agencies, or partner staff with access to multiple installed shops). Because the storage key omits the shop dimension, the *same database row* is reused and overwritten across shops for that user, exactly as the bridge report's `revertReceive[chainId][sequence]` map collapsed distinct channels sharing a `counterpartyChainId`.

### Impact Explanation
When a user with online tokens enabled authenticates to Shop B after previously being authenticated to Shop A (same `shopify_user_id`, different shop), `store` overwrites the single row's `shopify_domain` and `shopify_token` from A's values to B's values. Any subsequent request that resolves to a session id built from that user id (via `ShopifyAPI::Utils::SessionUtils.current_session_id` and consumed by `load_session`) will fetch the same row and receive **Shop B's access token and domain**, then activate it via `ShopifyAPI::Context.activate_session` in `activate_shopify_session`: [4](#0-3) 

This is a cross-shop token/session confusion: a browser/JWT that should be tied to Shop A's session ends up being served with Shop B's `access_token` (or vice versa), which is both a cross-shop access issue and an access-token disclosure, matching the report's "irreversible loss of the correct entity's data because of ID collision" bug class.

### Likelihood Explanation
This requires the app to be configured for online tokens (`user_session_repository`/user storage configured, a common and documented setup — see `config.user_session_repository`) and for a single Shopify account to be staff/collaborator on more than one shop that both install/authenticate against the same app instance. This is a realistic, unprivileged-from-the-app's-perspective scenario (any legitimate merchant/staff member operating across multiple stores triggers it merely by using the app normally on both shops), not an attacker-crafted edge case, so likelihood is moderate rather than requiring any special attacker capability.

### Recommendation
Key the user-session storage (and the derived session id parsing in `SessionRepository.load_session`) by the compound `(shopify_domain, shopify_user_id)` pair rather than `shopify_user_id` alone — e.g., `find_or_initialize_by(shopify_domain: auth_session.shop, shopify_user_id: user.id)` in `store`, and require `retrieve_by_shopify_user_id`/`destroy_by_shopify_user_id` call sites to also pass/validate the shop domain extracted from the session id (mirroring the `offline_<domain>` prefix already used for shop sessions). Existing rows should be migrated so historical per-shop rows are not silently merged during the fix.

### Proof of Concept
1. Configure the app with `ShopifyApp::SessionRepository.user_storage` set (online tokens enabled) as documented in `docs/shopify_app/sessions.md`.
2. User "U" (Shopify account id `1234`) installs/authenticates the app on Shop A (`shop-a.myshopify.com`). `CallbackController#callback` → `save_session` → `SessionRepository.store_session` → `UserSessionStorage.store` creates a row: `shopify_user_id=1234, shopify_domain=shop-a.myshopify.com, shopify_token=<A's token>`.
3. The same user U (same Shopify account, id `1234`) later authenticates the app on Shop B (`shop-b.myshopify.com`), where U is also staff/collaborator. `UserSessionStorage.store` executes `find_or_initialize_by(shopify_user_id: 1234)`, finds the *same row*, and overwrites it to `shopify_domain=shop-b.myshopify.com, shopify_token=<B's token>`.
4. A previously-issued session id/JWT tied to Shop A (e.g., `"shop-a.myshopify.com_1234"`) is used in a subsequent request. `SessionRepository.load_session` strips the shop segment (`id.split("_").last` → `"1234"`) and calls `retrieve_user_session_by_shopify_user_id("1234")`, returning the row now containing **Shop B's** domain and access token.
5. `LoginProtection#activate_shopify_session` activates this session via `ShopifyAPI::Context.activate_session`, so the request believed to be operating in Shop A's context is actually authenticated and authorized with Shop B's access token — a cross-shop session/token exposure.

    class_methods do
      def store(auth_session, user)
        user = find_or_initialize_by(shopify_user_id: user.id)
        user.shopify_token = auth_session.access_token
        user.shopify_domain = auth_session.shop

        if user.has_attribute?(:access_scopes)
          user.access_scopes = auth_session.scope.to_s
        end

        if user.has_attribute?(:expires_at)
          user.expires_at = auth_session.expires
        end

        user.save!
        user.id
      end

      def retrieve(id)
        user = find_by(id: id)
        construct_session(user)
      end

      def retrieve_by_shopify_user_id(user_id)
        user = find_by(shopify_user_id: user_id)
        construct_session(user)
      end

      def destroy_by_shopify_user_id(user_id)
        destroy_by(shopify_user_id: user_id)
      end

    def activate_shopify_session
      if current_shopify_session.blank?
        signal_access_token_required
        ShopifyApp::Logger.debug("No session found, redirecting to login")
        return redirect_to_login
      end

      if ShopifyApp.configuration.check_session_expiry_date && current_shopify_session.expired?
        ShopifyApp::Logger.debug("Session expired, redirecting to login")
        clear_shopify_session
        return redirect_to_login
      end

      if ShopifyApp.configuration.reauth_on_access_scope_changes &&
          !ShopifyApp.configuration.user_access_scopes_strategy.covers_scopes?(current_shopify_session)
        clear_shopify_session
        return redirect_to_login
      end

      begin
        ShopifyApp::Logger.debug("Activating Shopify session")
        ShopifyAPI::Context.activate_session(current_shopify_session)
        yield
      ensure
        ShopifyApp::Logger.debug("Deactivating session")
        ShopifyAPI::Context.deactivate_session
      end
    end
